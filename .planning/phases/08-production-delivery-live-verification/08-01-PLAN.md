  <name>Task 1: Implement the import-safe manifest and content-addressed packager</name>
  <reversibility rating="reversible">The script is a new release seam with no public route contract; removing it leaves existing build verification intact.</reversibility>
  <files>scripts/release-artifact.js</files>
  <read_first>
- `.planning/phases/08-production-delivery-live-verification/08-CONTEXT.md` D-01 through D-03 and D-10 — manifest, identity, and fail-closed credential boundary.
- `.planning/phases/08-production-delivery-live-verification/08-RESEARCH.md` §Artifact packaging — tree/archive digest split and native tooling.
- `scripts/verify-guide-export.js` — exact variant/host/route projection and output path rules.
- `scripts/verify-release.js` — variant lifecycle and disposable output behavior.
  </read_first>
  <behavior>
- `prepare` validates `--out-dir`, `--variant io|cn`, `--source-commit`, `--rollback-target`, and expected host; it writes `__release/manifest.json` with schema version, timestamps, variant, source commit, content-addressed logical `releaseRevision`, rollback target, provider, exact Guide routes, tree digest, and `deploymentState: prepared`.
- `package` verifies the prepared output, creates a variant/revision content-addressed archive using native `tar`, computes an archive SHA-256 sidecar, and writes JSON evidence without placing the archive's own digest inside itself.
- `verify` re-computes the tree and archive digests, validates manifest/host/variant/route identity, rejects symlink or path traversal entries, and emits one concise success line with artifact identity. It accepts provider evidence only as a post-deploy companion record; the prepared manifest never claims a provider revision, while the companion receipt must bind the manifest's logical release/tree/archive identity to the actual provider revision and rollback target.
- All failures carry `variant`, artifact path, and surface context; import has no filesystem writes or logs.
  </behavior>
  <action>
Implement one small CommonJS module with `parseArgs`, `buildManifest`, `computeTreeDigest`, `prepareReleaseOutput`, `packageReleaseArtifact`, and `verifyReleaseArtifact` exports. Keep the manifest under `__release/manifest.json`; use `crypto.createHash('sha256')`, sorted relative POSIX paths, file-size/type metadata, and `fs.lstatSync` to reject symlinks. Derive `releaseRevision` from variant + tree digest + source commit; use `child_process.spawnSync`/`execFileSync` for `tar -czf` with a temporary staging directory and validate the resulting archive with a checksum sidecar. Keep archive identity in the sidecar/evidence record and use the manifest tree digest as the stable in-manifest artifact identity. Do not alter `registry.json`, authored HTML, or package-lock.
  </action>
  <acceptance_criteria>
- `node scripts/release-artifact.js --help` documents prepare/package/verify and required identity inputs.
- `prepare` creates a `deploymentState: prepared` manifest whose route inventory exactly matches the selected `io`/`cn` Guide projection and whose tree digest/releaseRevision are stable across repeated verification.
- `package` names the archive with a digest prefix, writes `<archive>.sha256` and JSON evidence, and `verify` accepts the untouched archive plus a provider receipt only when the receipt's artifact/release identity matches the prepared manifest and contains a provider-specific deployed revision/rollback target.
- Missing rollback target, wrong variant/host, missing Guide route, symlink, traversal, manifest drift, and checksum drift fail with scoped diagnostics.
- Importing the module is silent and side-effect free.
  </acceptance_criteria>
  <verify>
    <automated>node --test --test-name-pattern="manifest|archive|digest|invalid|import" scripts/release-artifact.test.js</automated>
  </verify>
  <done>Any Phase 7-verified variant output can be represented by one immutable archive identity and an inspectable release manifest.</done>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| Generated `out/` → release archive | Build output becomes a deployable object. |
| Manifest inputs → release identity | CI-provided revision and rollback values become audit evidence. |
| Archive filesystem → tar command | File names and symlink metadata could escape the staging root. |

## STRIDE Threat Register — ASVS L1

| Threat ID | Category | Severity | Mitigation |
|---|---|---:|---|
| T-08-01 | Tampering | high | Recompute sorted tree and archive SHA-256 digests before acceptance. |
| T-08-02 | Elevation of privilege | high | Reject symlinks/traversal and stage only contained regular files. |
| T-08-03 | Repudiation | medium | Persist source/deployed revision, rollback target, and evidence sidecars. |
| T-08-04 | Spoofing | medium | Whitelist `io`/`cn`, expected hosts, and registry-derived routes. |
| T-08-SC | Supply chain | high | Use Node built-ins/native tar and preserve package-lock. |
</threat_model>
