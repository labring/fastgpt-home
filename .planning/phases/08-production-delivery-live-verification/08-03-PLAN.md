  </read_first>
  <behavior>
- CLI accepts `--base-url-cn`, `--base-url-io`, `--manifest`, `--report`, `--timeout-ms`, and optional `--allow-blocked-baseline`; defaults use the two owned production domains and fail closed.
- For each variant it requests `/guide`, eight articles, `/sitemap.xml`, and `/__release/manifest.json` with bounded native fetch and records status, final URL, headers, body digest, and timestamp.
- HTML checks assert final 200, expected localized H1, self canonical, exact three alternates, indexable robots, and matching sitemap `<loc>`; article and hub failures identify variant/slug/path/surface.
- Header checks require `Cache-Control` with a positive max-age or explicit provider freshness evidence, record ETag/Last-Modified/Age/CF-Cache-Status/X-Cache-Status, and flag missing/stale evidence.
- Manifest checks require variant/host/source commit/logical releaseRevision/tree artifact identity/rollback target. A separate provider receipt is mandatory in production mode and must include the actual CN image digest plus Kubernetes reference or the actual IO Pages deployment ID/URL, the same artifact/release identity, and the rollback target; source-only evidence never satisfies the check.
- Production verification accepts provider receipts only through an explicit `--provider-evidence <cn.json|io.json>` input (one receipt per variant) and cross-checks each receipt's actual provider revision, artifact/archive/tree digest, logical `releaseRevision`, rollback target, and public `__release/manifest.json`/release headers. A public manifest that contains only source commit or logical identity cannot satisfy DEPLOY-02. CN receipt creation occurs after the image is pushed and its immutable digest is resolved, before the digest-pinned Kubernetes rollout, and the receipt records the rollout result/reference afterward; IO receipt creation occurs after Wrangler returns the immutable Pages deployment ID/URL. The verifier records those actual provider revisions and the exact public logical identity in the report.
- `--allow-blocked-baseline` writes a blocked report for known pre-deployment 404s while preserving every failed surface and exits with a distinct blocked code; production mode exits nonzero for any failure.
  </behavior>
  <action>
Implement `fetchWithTimeout` using `AbortController`, a small HTML attribute/text extractor, XML sitemap URL parser, manifest validator, and provider-receipt validator. Build the expected matrix from `registry.json` and the same `io=en`/`cn=zh` ownership projection used by Guide export verification. Parse `--provider-evidence` as a required production input, validate the receipt schema (variant, artifact/archive/tree digest, logical `releaseRevision`, rollback target, and provider-specific actual revision fields), validate one CN and one IO receipt, compare each receipt to the fetched public manifest and `X-Release-Revision`/`X-Release-Artifact` headers, and fail with variant-scoped diagnostics for provider ID, digest, rollback, or logical identity drift. Keep report JSON stable: schema version, started/finished timestamps, overall status (`passed`/`blocked`/`failed`), expected logical releaseRevision/artifact digest, actual provider revisions/rollback targets, receipt paths/digests, per-variant summary, and per-route checks. Log concise `[verify-guide-live]` lines; never print response bodies beyond bounded diagnostics. Use `--allow-blocked-baseline` only for recording the current public 404 baseline, never as a success override.
  </action>
