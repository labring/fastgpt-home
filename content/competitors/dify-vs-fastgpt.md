# Dify 与 FastGPT 怎么选：四种项目的分野与 POC 判据

**如果现成插件广度与全球生态是这个项目的第一优先级，Dify 应当进入最终候选。如果要把深度知识工程、Agent 文件工作区、Skills 全生命周期、业务交互工作流与中国企业渠道交付合成一套平台，FastGPT 更贴合这条链路。**

两者的产品形态重叠度在同类产品里最高——都提供 Cloud、社区自托管与企业路线，都有 Agent、RAG、可视化工作流与双向 MCP。正因为重叠度高，靠功能勾选表很难分出高下；真正决定选型的是产品重心的差异，以及这个差异是否正好落在项目的成败因素上。

本文只使用双方官方公开资料中可验证的事实，核验日 **2026-07-20**。文中「官方公开资料未列出」是一个事实陈述，不等于对方无法通过二次开发或企业版交付实现——涉及关键能力时，应向厂商书面确认。

---

## 1. 两者的产品重心分别是什么

**Dify 的重心是通用编排与插件生态。** 官方插件仓库、创作者中心、模板市场与国际社区的成熟度更高；Enterprise 路线的身份与审计集成在公开资料中明确列出 SAML/OIDC SSO、SCIM、防篡改审计日志与 SIEM 流式输出；通用数据库插件与模型插件的广度，以及面向海外开发者的品牌心智，都是其真实优势。对于优先依赖现成插件、团队分布在海外、采购语境偏全球生态的组织，这些优势是直接可用的。

**FastGPT 的重心是知识工程深度与中国企业交付闭环。** 产品路径覆盖 Cloud、社区自托管与托管/自托管商业版；渠道原生覆盖企业微信、微信公众号、个人微信、飞书、钉钉与 iframe；本地多模型接入已支持。它把 RAG 放在一个更完整的运行时里，让 Agentic RAG、交互状态恢复、Skills 与知识工程在同一套编排内协同，而不是各自作为插件挂载。

一句话概括这个分野：**Dify 更像一个通用的 AI 应用编排平台，FastGPT 更像一个把知识工程做深、并对中国企业落地路径负责的平台。** 两种重心都能做出可用的应用，差别在于走到生产时哪一类工作量落在企业自己身上。

---

## 2. 能力对照表

对照表分三列。这个分法本身就是一种表述纪律：把「只有一方公开列出」「双方都有但实现不同」「对方强项」分开写，避免用一句「对方不支持」掩盖版本与交付边界的复杂性。

### 2.1 截至核验日仅 FastGPT 官方公开资料列出的能力

| # | 能力 | 具体范围 | 对方公开资料状态（截至 2026-07-20） |
|---|---|---|---|
| 01 | **稳定 Skills 全生命周期** | 导入导出、版本、权限继承、引用分析、编辑沙箱与运行沙箱 | Dify Agent Skills 在项目核验时仅见于 1.16.0-rc1 实验版资料 |
| 02 | **Agent 会话文件工作区** | 文件树、多标签编辑器、交互终端、目录 ZIP、会话沙箱产物回传 | 官方公开资料未列出同等原生能力 |
| 03 | **图片知识库与原图向量检索链路** | 同时保存原图、VLM Caption 与 imageEmbedding，支持以图搜图及 Caption 降级 | 官方公开资料未列出同等原生能力 |
| 04 | **更细的知识数据维护链路** | 单正文多索引、索引独立编辑、训练队列修复、检索历史、各阶段 Token 成本拆分、引用粒度溯源 | 官方公开资料未列出同等粒度 |

**这四项为什么重要**：它们对应的是知识库上线之后的维护成本。答不准的时候能不能定位到是切分问题、索引问题还是检索配置问题；一份正文能不能挂多条索引而不重复入库；训练队列出错能不能单独修复而不是整库重跑；成本能不能拆到解析、向量化、检索、生成各阶段——这些能力在 Demo 阶段几乎看不出差别，在运营半年后差别很大。

### 2.2 双方都有、但实现路径不同

| 能力 | Dify 的实现路径 | FastGPT 的实现路径 |
|---|---|---|
| Agent + RAG + 可视化工作流 + 双向 MCP | 以通用工作流与插件生态为主 | 强调 Agentic RAG、交互状态恢复、Skills 与知识工程在同一运行时内协同 |
| 复杂文档解析 | 更多借助 LlamaParse、Mistral OCR 等插件管线 | 兼有本地 LiteParse / PDF.js 路径与 TextIn / Doc2x 增强路径 |
| 开放 API 与 Web 发布 | SSE、API、Web 应用与嵌入 | 同上，并额外强调 OpenAI SDK 兼容、中国 IM 原生渠道、应用反向发布为 MCP Server |
| 企业治理（RBAC / SSO / 多租户 / 审计） | Enterprise 提供 RBAC、SAML/OIDC、SCIM、防篡改审计与 SIEM、多工作空间/多租户 | 商业版提供 ABAC + RBAC、SSO、多租户与管理后台；高级云套餐公开 720 天团队操作日志 |

> **双方都有不等于实现等价。** 这四项必须用相同的数据集、模型、硬件、并发与验收标准跑 POC 才能得出结论。企业治理这一项尤其要逐项对照：成员、工作空间、资源、日志保留时长、外部 IdP 各自落在哪个版本，不同版本之间差别可能大于两个产品之间的差别。

### 2.3 Dify 的强项（如实列出）

- **全球插件与 Marketplace 生态**：官方插件仓库、创作者中心、模板市场与国际社区成熟度更高。
- **Enterprise 身份与审计集成**：公开资料明确列出 SAML/OIDC SSO、SCIM、防篡改审计日志与 SIEM 流式输出。
- **通用数据库插件与模型插件广度**：官方 Marketplace 路径更直接，适合优先依赖现成插件的团队。
- **国际化品牌与开发者心智**：面向海外开发者与全球生态采购更有优势。

这一节不加「但是」句式反转。如果项目的第一优先级确实是现成插件广度，那么正确的做法是让 Dify 进入最终候选，再用下面第 4 节的方法比较落地成本，而不是先否认对方的生态。

## 3. 许可证与商业边界

许可证是这类选型里最容易被一句「都是开源」带过、事后又最容易出问题的一项。**「开源」不等于「无商业限制」，两者的许可边界并不相同**，需要法务逐一审核 LICENSE 以及 SaaS、去品牌、二次开发分发这三条边界。

| 项 | Dify | FastGPT |
|---|---|---|
| 产品路径 | Cloud + Community + Enterprise | Cloud + 社区自托管 + 托管/自托管商业版 |
| 开源许可 | 修改版 Apache 2.0；用源码提供多租户服务、去除前端品牌需商业授权 | FastGPT Open Source License：允许作为其他应用的后端服务商用、允许作为应用开发平台交付给企业；未获书面授权不得用源码运营同类多租户 SaaS，不得移除或修改控制台内的 LOGO 与版权信息 |
| 自托管部署方式 | Community 用 Docker Compose；Enterprise 用 Helm | Docker Compose，支持多种向量后端；Kubernetes 的商业交付边界需确认 |
| 私有化 / 离线 | Enterprise 支持 VPC、本地与完全隔离 | 商业版可私有化并完全离线 |
| 采购形态 | Cloud 免费档 + 两档按工作空间年度订阅；Enterprise 询价，SLA 按合同 | Cloud 分免费与两档月度订阅；托管商业版按月起价；私有部署按单台服务器 License，分标准 / 专业 / 旗舰三版本（选型顺序是租户数 → 是否需要 SSO 与 OA 集成 → 是否需要独立开票与支付模块） |
| 原厂支持 | Enterprise 路线询价，SLA 按合同；社区版是否附带支持承诺需向对方确认 | 分四个档位，覆盖时段从工作日逐档扩到 7×24，首次响应目标按档位递进；所有付费档位含安全补丁、新功能支持与远程线上协助，付费档起有专属支持群、最高档增加客户经理；私有部署交付范围可含安装部署、调试与原厂技术维保 |

**关于价格，本文不列具体数字。** 价格、套餐与版本边界属高频变化数据，两侧都应以各自官方定价页当日页面为准；含税口径、授权期限、实施与维保范围需要联系对应厂商商务确认。下面第 4 节给的是同口径三年总成本的计算表，价格栏留空由采购方自行填入——这比在文章里印一个可能过期的数字更有用。

**关于原厂支持，要比的是能写进合同的那部分。** 公开的档位口径只说明支持形态，两侧都应索取责任矩阵、故障分级、恢复目标、升级回滚责任方与退出迁移条款，并把它们写进服务清单。**首次响应目标不等于在同一时限内完成修复，未书面约定的指标不构成承诺**——这条对两侧一视同仁，也包括上表引用的任何档位口径。

**社区版与商业版的边界也需要一并看清。** FastGPT 官方口径是「完整版应用 = 社区版镜像 + 商业版镜像」，商业版镜像需要 License 启动；客户可以修改社区版部分代码，但不支持修改商业版镜像。当前公开的版本差异中，Agent 辅助生成、Skill 专业辅助生成、系统工具本地远程调试属于商业版与云服务能力。判断标准不是「开源版能不能生产」——小团队内部使用、且能自行承担部署、升级、备份与安全时，社区版可能就够；当需求进入 SSO、多租户、审计、长周期日志、商业支持或明确 SLA 时，再评估商业版，不必一开始就过度采购。

## 4. 怎么自己验证

功能表不能替代验证。以下是建议的统一 POC 测量表，六个类别各自给出必测指标、统一条件与证据产物。**关键是「统一条件」这一列：两边不用同一份黄金集、同一个 Embedding 与 ReRank、同一个 LLM 与 TopK、同一台机型，得出的任何结论都不成立。**

| 类别 | 必测指标 | 统一条件 | 证据产物 |
|---|---|---|---|
| RAG 效果 | Recall@K、MRR / NDCG、引用正确率、幻觉率、无答案拒答率 | 同一黄金问题集、Embedding、ReRank、LLM、TopK | 可重放测试集 + 逐题结果 |
| 复杂文档 | 表格 / 标题 / 页码 / 图片保真率，解析成功率，每 100 页时间与成本 | 同一批扫描件、合同、研报、PPTX、XLSX | 原文与解析结果 diff + 人工抽检 |
| 在线性能 | P50 / P95 / P99 延迟、成功率、每秒请求、峰值并发 | 同一模型端点、向量库、机型、数据量与预热方式 | 压测脚本、原始报告、资源曲线 |
| 可靠性 | 节点失败恢复、重试幂等、队列积压、升级回滚、备份恢复 | 同一故障注入脚本与数据规模 | 故障时间线、丢数 / 重复记录、恢复时长 |
| 安全与治理 | 越权、SSRF、密钥泄漏、沙箱逃逸、租户隔离、审计覆盖 | 同一威胁用例与权限矩阵 | 用例结果、审计记录、整改项 |
| 三年 TCO | 许可、模型、解析 / OCR、存储、数据库、运维、升级与支持 | 统一三年业务增长假设 | 三年现金流 + 人天 + 风险准备金 |

针对插件生态这一项，还有一个更快的判据：**选出企业最常用的 5–10 个集成，逐个比较安装、鉴权、调试、版本锁定与故障定位的实际难度。** 插件总数是动态数字，对具体项目的意义远小于这 5–10 个真正要用的集成好不好接。

同时要注意，以下指标当前在两侧都没有可比的统一公开口径，应当保持「未公开 / 待 POC / 待合同」，不要在选型文档里填死：稳态与峰值并发、每秒请求数、每分钟 Token 吞吐、指定硬件下的解析与检索延迟、最大应用数与知识库数、可用性 SLA 与 RTO / RPO、各版本 API 完整覆盖率与插件实时总数。

## 5. 中性选型建议

| 项目的第一成败因素 | 建议 |
|---|---|
| 现成插件广度、海外协作栈、全球生态采购 | **Dify 应进入最终候选**，用第 4 节方法比较落地成本 |
| 知识库长期维护成本（多索引、训练队列、引用溯源、成本拆分） | FastGPT 的知识数据维护链路粒度更细，优势会在运营期显现 |
| Agent 需要真实文件操作与会话内产物回传 | FastGPT 的 Agent 会话文件工作区是当前可核验的差异点 |
| 中国企业渠道发布（飞书、钉钉、企微、公众号、个人微信） | FastGPT 原生覆盖，无需自行搭建渠道适配层 |
| 从低成本验证起步、后续迁到私有环境 | FastGPT Cloud 到私有化的交付路径完整，可先验证再迁移 |
| 严格的外部同步 + 部门信息隔离 + 强审计与成本管理同时要求 | 两侧都需要逐项核验版本边界；这类组合需求应在合同中写清，不能只比「支持私有化」一个勾 |
| 需要把响应时段、恢复责任与升级回滚写进合同 | 两侧都索取责任矩阵与服务清单；FastGPT 的支持档位结构已公开，Dify 的 Enterprise SLA 按合同确认 |

**最后一条纪律**：这篇文章不主张任何一方「准确率更高」或「性能更好」。这类结论没有同条件的第三方测试或可复现自测就不成立，正确的做法是用企业真实黄金集与统一压测条件自行验证。同样，选择了私有化也不等于「数据绝不出域」——外部模型、OCR、插件、连接器、版本更新与遥测都可能产生出站流量，选型时应逐项列出数据流、组件位置与出站策略，而不是只比「支持私有化」这一个勾。
