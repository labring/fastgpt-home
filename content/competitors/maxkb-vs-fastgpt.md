# MaxKB 与 FastGPT 怎么选：采购可预测性与生产细粒度

**如果这次采购的首要约束是形式简明、预算可预测——离线安装路径清楚、授权与支持档位公开、流程好过审，MaxKB 会直接进入比价，而且理由充分。如果系统要承担复杂生产场景——隔离代码沙箱、工作流中的人工确认与原地恢复、统一配额治理、图片向量与多索引检索，FastGPT 在这些细粒度上更贴合。**

两者的定位相当接近：都强调开源、私有化、知识库、工作流与 Agent。差别不在功能清单的长度，而在两件事——**采购形态的确定性**，以及**进入复杂生产场景后的能力粒度**。这两件事往往由企业内部的不同角色关心：前者是采购与财务，后者是技术与安全。选型分歧多数就出在这里。

本文只使用双方官方公开资料中可验证的事实，核验日 **2026-07-20**。文中「官方公开资料未列出」是事实陈述，不等于对方无法通过二次开发或项目交付实现。

---

## 1. 两者的产品重心分别是什么

**MaxKB 的重心是国内私有化交付的形式简明。** 离线安装路径清晰，专业版与企业版的授权形态、次年维保与原厂支持档位在官网公开，支持档位分 5×8 与 7×24 两级。对不喜欢订阅制的采购者来说，一次性授权的口径直观、易于内部审批；数据库查询工具在官方文档中明确列出，产品可见性高；对「装完就能用、预算一次报清」这类需求，它的产品形态匹配度很高。

**FastGPT 的重心是复杂生产场景下的细粒度控制。** 隔离代码沙箱、工作流的人工暂停与原地恢复、统一配额与用量治理、图片向量与多索引检索及成本解释，这几项都指向同一件事：系统在真实业务里长期运行时，出问题能不能定位、能不能干预、能不能算清账。同时它保留三条路径——Cloud、社区自托管、托管与自托管商业版，允许先低成本验证再迁到私有环境。

**采购可预测性本身是一种真实价值，不该被当成「只是形式」。** 一次性授权、公开的维保比例、写明的支持档位，让预算能一次报清、审批链条短、财务口径清楚；在很多国企与制造业的采购流程里，这几点决定的是项目能不能立项，而不只是花多少钱。所以这篇文章不会把它写成对方的短板。真正需要提醒的只有一件事：**可预测的是「付款方式」，不是「三年总支出」**——维保、硬件、模型消耗、实施人天、集群扩展与功能二开都在授权价之外，这部分不算进来，预算的确定性就是假的。第 3.2 节给出的就是把这些补齐的算法。

## 2. 能力对照表

### 2.1 截至核验日仅 FastGPT 官方公开资料列出的能力

| # | 能力 | 具体范围 | 对方公开资料状态（截至 2026-07-20） |
|---|---|---|---|
| 01 | **隔离代码沙箱** | 公开资料明确 JavaScript / Python 隔离执行及网络与文件限制 | 公开文档只能确认 Python 工具在其容器中执行，未证明是独立沙箱 |
| 02 | **工作流人工暂停与原地恢复** | 支持用户选择与多字段表单，穿透子应用、工具、循环保留状态后再恢复 | 公开节点资料未列出同类人工确认节点 |
| 03 | **统一配额与用量治理** | API Key 与分享链接额度、有效期、QPM，以及云套餐资源配额 | 官方版本表未列出匹配的统一配额管理 |
| 04 | **图片向量、多索引与检索成本解释** | imageEmbedding、Caption 降级、加权 RRF、检索阶段分数、Token 拆分 | 公开资料未证明同等粒度 |

**这四项为什么重要**：

- **隔离沙箱**是安全评审最难通过的一关。工具节点要执行代码，代码能不能碰网络、能不能读文件、跑挂了会不会影响主进程——这不是加个中间件能补的，涉及运行时架构。
- **人工暂停与原地恢复**决定了 AI 能不能进入有审批的流程。多数企业流程中间必须有人确认，如果暂停后只能从头重跑，这类场景就落不了地。
- **统一配额**是成本失控的唯一刹车。分享链接发出去之后调用量由谁承担、某个 API Key 一分钟能调多少次，没有额度与 QPM 就只能事后看账单。
- **图片向量与成本解释**对应两类真实需求：图表与截图里的信息能不能被检索到，以及每一次问答的成本能不能拆到解析、向量化、检索、生成各阶段。

### 2.2 双方都有、但实现路径不同

| 能力 | MaxKB 的实现路径 | FastGPT 的实现路径 |
|---|---|---|
| 知识库、Agent、可视化工作流、Skills、MCP | 均已覆盖，更强调知识库快速上手与工具扩展 | 均已覆盖，更强调独立工具类型、Skill 沙箱与双向 MCP |
| 文档与结构化数据 | 支持 Office / PDF / 表格，可通过 OCR、MinerU 等工具扩展 | 支持同类格式，强调本地解析、图片索引与训练队列 |
| 企业治理 | 专业版提供 RBAC、SSO 与操作日志；多租户与集群明确放在企业版 | 商业版提供 ABAC + RBAC、SSO、多租户与管理后台；高级云套餐公开 720 天团队操作日志 |
| 部署与渠道 | Docker、离线部署、Web / API 与国内 IM，形态更接近标准私有化产品 | Docker Compose、多向量后端，同时提供 Cloud、社区自托管与商业交付 |

> **双方都有不等于实现等价。** 企业治理这一行必须落到具体字段做实测：组织、部门、群组、资源、日志保留时长、操作类型各自覆盖到什么程度，以及多租户与集群落在哪个版本。**版本之间的差异经常大于产品之间的差异**——用同一组权限用例在两边各跑一遍，比对照功能表可靠得多。

### 2.3 MaxKB 的强项（如实列出）

- **国内私有化交付形式简明**：离线安装路径、授权形态、次年维保与原厂支持档位均在官网公开。
- **采购可预测性**：一次性授权的口径对不喜欢订阅的采购者有吸引力——但预算评估必须加上维保、实施、模型与硬件（见第 3 节）。
- **数据库查询工具的产品可见性**：官方文档明确列出数据库查询工具；FastGPT 的通用路径主要是 HTTP API 与工具封装，更开放但需多一层集成。
- **支持档位公开**：专业版 5×8、企业版 7×24 的口径对采购者更直观；具体响应与恢复目标仍需以合同为准。

## 3. 许可证、采购形态与三年总成本

### 3.1 两侧的公开边界

| 项 | MaxKB | FastGPT |
|---|---|---|
| 产品路径 | 社区自托管 + 专业版 / 企业版 | Cloud + 社区自托管 + 托管 / 自托管商业版 |
| 开源许可 | GPLv3；X-Pack 的商业边界需另行确认 | FastGPT Open Source License：允许作为其他应用的后端服务商用、允许作为应用开发平台交付给企业；未获书面授权不得用源码运营同类多租户 SaaS，不得移除或修改控制台内的 LOGO 与版权信息 |
| 自托管基础设施公开下限 | 至少 4 核 / 8GB / 100GB | 未固化统一最低 CPU / 内存，按向量库、文档量、模型与并发设计 |
| 部署方式 | Docker；企业版支持集群 | Docker Compose，支持多种向量后端；Kubernetes 商业交付边界需确认 |
| 私有 / 离线 | 社区版可离线自部署；专业版与企业版有原厂支持 | 商业版可私有化并完全离线 |
| 采购形态 | 专业版一次性永久授权 + 次年维保；企业版询价 | Cloud 分免费与两档月度订阅；托管商业版按月起价；私有部署按单台服务器 License，分标准 / 专业 / 旗舰三版本 |
| 支持档位 | 专业版 5×8、企业版 7×24；可用性、RTO / RPO 需合同确认 | 商业服务可交付；具体可用性、响应与恢复指标需合同确认 |

**关于许可证**：GPLv3 与 FastGPT Open Source License 的约束方向不同——前者的主要影响在分发与衍生作品的开源义务，后者的主要限制在多租户 SaaS 运营与去品牌。**「开源」不等于「无商业限制」**，两者的边界不能互相类推，需要法务逐一审核 LICENSE 以及 SaaS、去品牌、二次开发分发这三条边界，再结合企业实际的使用与交付方式判断。X-Pack 的商业边界属于需要另行确认的部分。

这件事对两类企业的影响完全不同，值得分开说。**企业只在内部使用、不对外分发**时，许可证差异的实际影响通常有限，法务重点核对的是二次开发的成果归属与升级路径。**企业要把平台封装进自己的产品对外交付**——例如系统集成商做行业方案、软件商把问答能力嵌进自家系统——那么分发义务、去品牌是否被允许、能否面向多个客户提供服务，这三条会直接决定商业模式能不能成立，必须在采购前拿到书面结论，而不是靠对许可证名称的通行理解推断。**判断顺序建议是：先写清企业自己打算怎么用与怎么交付，再拿这份用法去对每一份 LICENSE，而不是先看许可证名称再猜能不能做。**

**关于价格，本文不列具体数字。** 授权价、维保比例、订阅价与套餐边界都属高频变化数据，应以各自官方页面当日信息为准，并向对应商务书面确认含税口径、授权期限与实施维保范围。

### 3.2 买断与订阅怎么比才成立

「买断更划算」对预算模式确实有吸引力，但**价格不能只看首年许可**。正确的比较方式是把下列项目全部计入，再按同一三年规模比较：

| 成本项 | 说明 |
|---|---|
| 许可 / 订阅 | 买断侧是首年授权，订阅侧是三年订阅费；两边填各自官方当日实价 |
| 次年及第三年维保 | 买断侧的关键变量，必须计入第二、第三年 |
| 硬件 | 按最低资源要求换算实际服务器或云主机成本，含存储与备份 |
| 模型消耗 | 向量化与生成，按真实问答量估算，两边用同一假设 |
| 实施 | 部署、调试、知识库建设、权限配置的人天 |
| 集群 | 是否需要多节点，多节点是否需要额外授权 |
| 升级 | 三年内的版本升级路径与是否额外收费 |
| 功能二次开发 | 缺失能力自行补齐的人天，含长期维护 |
| 风险成本 | 版本边界不匹配、迁移成本、评审不通过的返工 |

**产出应当是一张三年 TCO 表，并对成员数、文档量、请求量与是否需要双节点做灵敏度分析。** 只比首年许可费，或只比月费乘以 36，两种算法都会得出错误结论。

**一条表述纪律**：本文不主张「订阅一定比买断便宜」，也不主张反过来。两种采购模式的优劣完全取决于企业的规模、增长假设与内部预算方式，只有同口径的三年表能给出答案。

## 4. 怎么自己验证

除了通用的统一 POC 测量表，针对这一对产品建议额外补三组用例——它们正好落在第 2.1 节的差异点上，也最容易在 Demo 阶段被跳过：

| 补测项 | 具体做法 | 判据 |
|---|---|---|
| **沙箱与工具安全** | 在工具节点里执行一段试图访问外网与读写本地文件的代码；再试一次越权与密钥读取 | 是否被隔离拦截；失败是否影响主进程；审计里是否留痕 |
| **流程中的人工确认** | 设计一个中途需要人工填多字段表单再继续的流程，且这个节点位于子应用或循环内部 | 暂停后能否原地恢复并保留状态，还是必须从头重跑 |
| **配额与成本可解释性** | 发一个分享链接并设置额度与有效期，跑一批问答后查成本 | 额度与 QPM 是否生效；成本能否拆到解析、向量化、检索、生成各阶段 |

完整的统一 POC 测量表：

| 类别 | 必测指标 | 统一条件 | 证据产物 |
|---|---|---|---|
| RAG 效果 | Recall@K、MRR / NDCG、引用正确率、幻觉率、无答案拒答率 | 同一黄金问题集、Embedding、ReRank、LLM、TopK | 可重放测试集 + 逐题结果 |
| 复杂文档 | 表格 / 标题 / 页码 / 图片保真率，解析成功率，每 100 页时间与成本 | 同一批扫描件、合同、研报、PPTX、XLSX | 原文与解析结果 diff + 人工抽检 |
| 在线性能 | P50 / P95 / P99 延迟、成功率、每秒请求、峰值并发 | 同一模型端点、向量库、机型、数据量与预热方式 | 压测脚本、原始报告、资源曲线 |
| 可靠性 | 节点失败恢复、重试幂等、队列积压、升级回滚、备份恢复 | 同一故障注入脚本与数据规模 | 故障时间线、丢数 / 重复记录、恢复时长 |
| 安全与治理 | 越权、SSRF、密钥泄漏、沙箱逃逸、租户隔离、审计覆盖 | 同一威胁用例与权限矩阵 | 用例结果、审计记录、整改项 |
| 三年 TCO | 见 3.2 | 统一三年业务增长假设 | 三年现金流 + 人天 + 风险准备金 |

以下指标两侧都没有可比的统一公开口径，应保持「未公开 / 待 POC / 待合同」：稳态与峰值并发、每秒请求数、每分钟 Token 吞吐、指定硬件下的解析与检索延迟、最大应用数与租户数、可用性 SLA 与 RTO / RPO、模板与插件实时总数。

## 5. 中性选型建议

| 项目的第一约束 | 建议 |
|---|---|
| 预算需要一次报清、内部审批偏好一次性授权 | **MaxKB 会直接进入比价**，但必须用 3.2 的三年表核算，而不是只比首年许可 |
| 离线安装路径与支持档位需要在采购前就明确 | MaxKB 的公开形态更直观 |
| 需要现成的数据库查询工具且不希望多一层集成 | MaxKB 的产品可见性更高 |
| 工具节点要执行代码，且需通过安全评审 | 隔离沙箱是可核验的差异点，FastGPT 公开资料明确 |
| 业务流程中间必须有人工确认，且节点在子流程或循环内 | 人工暂停与原地恢复决定这类场景能否落地 |
| 需要控制分享链接与 API 的调用量、按环节看成本 | 统一配额与成本拆分是可核验的差异点 |
| 图表、截图里的信息需要被检索到 | 图片向量与多索引检索是可核验的差异点 |
| 需要先低成本验证、再迁到私有环境 | FastGPT 的 Cloud 到私有化路径完整 |

**最后两条纪律**：本文不主张任何一方「更安全」或「更可靠」——公开资料未说明某项控制，正确的处理是把它纳入 POC 与合同验收，而不是写成负面断言。同样也不主张任何一方「准确率更高」，这类结论只能由企业真实黄金集与统一压测条件给出。
