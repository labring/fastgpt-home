# RAGFlow 与 FastGPT 怎么选：复杂文档与完整链路的分野

**如果这个项目的成败几乎完全由扫描合同、研报与复杂版式解析决定，RAGFlow 必须进入最终 POC。如果在解析检索之外还要交付交互式 Agent、定时自动化、中国渠道发布与运营治理，那么应当比较的是完整链路的综合成本，而不是单点解析质量。**

RAGFlow 是复杂文档 RAG 赛道里最需要正面承认的强手。它的产品中心就是「深度文档理解」，并已扩展到 Agent、MCP、Skills、连接器与 Cloud / Enterprise 路线。这篇文章不试图证明谁在所有文档上都更准——那种断言没有同条件测试就不成立。它要做的是把两者的重心差异说清楚，让选型落在项目真实的成败因素上。

本文只使用双方官方公开资料中可验证的事实，核验日 **2026-07-20**。文中「官方公开资料未列出」是事实陈述，不等于对方无法通过二次开发实现；RAGFlow 位于 main 分支但尚未进入正式发布版的能力，不计入已发布稳定版。

---

## 1. 两者的产品重心分别是什么

**RAGFlow 的重心是深度文档理解。** 复杂版式与扫描文档的解析是它的标志性强项：深度文档理解、可干预分块、扫描件 OCR 构成了明确的产品心智。它的多源增量同步连接器在公开发布记录中列出 Confluence、S3、Notion、Discord、Google Drive，对海外协作栈有直接吸引力；许可证是 Apache-2.0，对二次开发、内部平台化与避免专有云绑定的买家更宽松；公开文档明确支持 Langfuse 链路追踪，可追踪检索、排序、生成、Prompt 与响应，对已经使用 Langfuse 的团队是现成的收益。

**FastGPT 的重心是把 RAG 放进一个更完整的运行体系。** 同样具备混合检索、ReRank、可溯源引用、图片理解与多模型，但它把这些放在 Agent、工作流、渠道发布与运营治理的完整链路里，并针对中国企业的知识源与发布渠道做了原生覆盖。

这个分野决定了两者的适用边界：**当项目就是「把一堆难解析的文档变成可查的知识」，RAGFlow 的产品心智更集中；当项目是「把知识、Agent、自动化与渠道运营做成一套长期运行的业务系统」，需要比较的维度就多得多。**

还有一个容易被忽略、但会直接影响预算的差异：**自托管的资源门槛，两边的公开写法不同。** RAGFlow 在公开文档里给出了明确的最低配置——最低 4 核 / 16GB / 50GB，Docker 版本不低于 24，Compose 不低于 2.26.1，且预构建镜像仅提供 x86 架构。FastGPT 没有固化一个统一的最低 CPU 与内存数字，而是按向量库选型、文档量、模型部署方式与并发来设计。这两种写法各有取舍：给死最低配置的一方便于采购直接换算成服务器成本，但也意味着低于这条线就不受支持；按需设计的一方灵活度更高，代价是必须在 POC 阶段自己把资源规划做出来。**如果企业已有固定的服务器规格或信创环境约束（尤其是非 x86 架构），这一行应当在选型第一周就核对，而不是等到部署阶段。**

## 2. 能力对照表

### 2.1 截至核验日仅 FastGPT 官方公开资料列出的能力

| # | 能力 | 具体范围 | 对方公开资料状态（截至 2026-07-20） |
|---|---|---|---|
| 01 | **内置定时自动化** | 可为已发布应用配置 Cron、时区与默认问题 | 官方 Agent 组件资料未列出内置时间 / 事件调度器 |
| 02 | **管理员审计与统一配额闭环** | 商业版与 Cloud 公开操作日志、API Key 与分享链接限额、QPM | 管理文档未列出管理员审计日志与可配置统一配额 |
| 03 | **网站持续同步与中国知识源** | 网站同步，并覆盖飞书、语雀、钉钉与自定义 API 知识源 | 公开数据源文档未列出网站 / 站点地图的持续抓取 |
| 04 | **中国企业发布与运营闭环** | 原生覆盖飞书、钉钉、企业微信、微信公众号、微信个人号，并有用户反馈、会话标注、应用评测与运营看板 | 公开资料未列出同等的中国渠道与运营闭环组合 |

**这四项为什么重要**：它们对应的不是「知识库准不准」，而是「知识库上线之后能不能长期运营」。每天固定时间自动跑一遍整理任务、管理员能查到谁改了什么、知识源在飞书或语雀里更新后能自动同步、员工在企微里直接问而不必打开新系统、答得不好能被标注并回流改进——这些能力决定的是半年后这套系统还有没有人用。

### 2.2 双方都有、但实现路径不同

| 能力 | RAGFlow 的实现路径 | FastGPT 的实现路径 |
|---|---|---|
| 复杂文档 RAG | 产品中心是深度文档理解，混合检索、ReRank、可溯源引用、图片理解、多模型 | 同样具备上述能力，但把 RAG 放在更完整的 Agent / 工作流 / 运营体系中 |
| Agent、工作流、MCP、Skills、人工等待 | 均已覆盖；Skills Space 在项目核验时位于 main 分支，需先确认正式发布版边界 | 可核验到更完整的 Skill 版本、权限与沙箱链路 |
| 代码 / 数据库工具 | 官方有 Execute SQL 组件，代码执行可配 gVisor | 通用 HTTP 封装、Secret 分离、SSRF 防护与隔离进程池 |
| Cloud / 自托管 / 企业版三条路径 | 三种路径均有；自托管硬件门槛更高且明确（最低 4 核 / 16GB / 50GB，Docker ≥ 24，Compose ≥ 2.26.1，预构建镜像仅 x86） | 三种路径均有；未固化统一最低资源，按向量库、文档量、模型与并发设计；Cloud 更适合先低成本验证再迁到私有环境 |

这张表里有一行需要单独说明：**Skills 的边界要看发布状态，不要看仓库。** 项目核验时 RAGFlow 的 Skills Space 位于 main 分支，也就是已经在开发中、但不属于正式发布的稳定版。评估这类能力有一条通用做法：**只把「当期正式发布版 + 官方稳定文档」计入选型依据，main 分支或 rc 版本的能力记为「在路上」，并在 POC 验收或合同里写清期望到位时间。** 这条做法对两侧同等适用——拿未发布分支的能力去论证任何一方更强或更弱，都不成立。

> **双方都有不等于实现等价。** 复杂文档 RAG 这一行尤其如此——两边都写着「混合检索 + ReRank + 可溯源引用」，实际表现只能用同一批文档、同一个 Embedding 与 ReRank、同一个 LLM 与 TopK 跑出来比较。硬件门槛那一行的差异是公开事实：一边给出了明确的最低配置，另一边需要按数据规模自行设计，两种写法各有取舍，采购时都要换算成实际服务器成本。

### 2.3 RAGFlow 的强项（必须正面承认）

- **复杂版式与扫描文档的产品心智**：深度文档理解、可干预分块、扫描件 OCR 是其标志性强项，应正面承认，并用企业自己的黄金集做 POC 比较。
- **多源增量同步连接器**：公开发布记录列出 Confluence、S3、Notion、Discord、Google Drive 等，对海外协作栈更有吸引力。
- **Apache-2.0 许可证**：对二次开发、内部平台化与避免专有云绑定的买家更宽松。
- **Langfuse 链路追踪语义**：公开文档明确可追踪检索、排序、生成、Prompt 与响应，适合已使用 Langfuse 的团队。

**这一节不加反转。** 如果企业的文档主体就是扫描合同、扫描研报与复杂表格，那么正确的做法是让 RAGFlow 进入最终 POC，而不是先论证它「只擅长解析」。

## 3. 许可证与商业边界

| 项 | RAGFlow | FastGPT |
|---|---|---|
| 产品路径 | Cloud + Apache-2.0 自托管 + Enterprise | Cloud + 社区自托管 + 托管 / 自托管商业版 |
| 开源许可 | Apache-2.0 | FastGPT Open Source License：允许作为其他应用的后端服务商用、允许作为应用开发平台交付给企业；未获书面授权不得用源码运营同类多租户 SaaS，不得移除或修改控制台内的 LOGO 与版权信息 |
| 自托管基础设施公开下限 | 最低 4 核 / 16GB / 50GB；Docker ≥ 24；Compose ≥ 2.26.1；预构建镜像仅 x86 | 未固化统一最低 CPU / 内存，按向量库、文档量、模型与并发设计 |
| 部署方式 | Docker Compose + Helm | Docker Compose，支持多种向量后端；Kubernetes 商业交付边界需确认 |
| 私有 / 离线 | 自托管；Enterprise 提供 BYOC / 本地部署 | 商业版可私有化并完全离线 |
| 企业身份 / 治理 | RBAC、OAuth2 / OIDC、团队权限；审计日志与可配置配额在公开资料中未获证实 | 商业版 ABAC + RBAC、SSO、多租户与管理后台；高级云套餐公开 720 天团队操作日志 |
| 采购形态 | Cloud 免费档 + 两档月度订阅；Enterprise 专属支持与自定义 SLA，数值询价 | Cloud 免费与两档月度订阅；托管商业版按月起价；私有部署按单台服务器 License 分三版本 |

**关于许可证的一条纪律**：Apache-2.0 确实比多数同类许可更宽松，但**「开源」不等于「无商业限制」**，几家产品的边界并不相同。需要法务逐一审核 LICENSE 以及 SaaS 运营、去品牌、二次开发分发这三条边界，再判断哪一种许可真正匹配企业的使用方式。

**关于价格，本文不列具体数字**，两侧都应以各自官方定价页当日页面为准。下面第 4 节给出的是同口径三年 TCO 的成本项清单，价格栏由采购方自行填入。

## 4. 怎么自己验证

针对这一对产品，最有价值的验证方式非常具体：**让两家跑同一批复杂文档，同时记录四个量。**

| 记录项 | 为什么必须记 |
|---|---|
| **解析质量** | 表格、标题、页码、图片的保真率与解析成功率，逐份人工抽检 |
| **RAG 指标** | Recall@K、MRR / NDCG、引用正确率、幻觉率、无答案拒答率 |
| **人工调整时间** | 解析结果不理想时，把它调到可用状态需要多久——这一项常常比解析准确率本身更影响交付周期 |
| **后续应用开发时间** | 知识库可用之后，把它变成一个真正能用的应用（Agent、定时任务、渠道发布、权限）还需要多久 |

后两项是这一对比较里最容易被跳过、也最能区分总成本的部分。只测第一项，结论会偏向解析更强的一方；四项都测，结论才反映真实交付。

完整的统一 POC 测量表如下，六类各自的统一条件必须严格一致：

| 类别 | 必测指标 | 统一条件 | 证据产物 |
|---|---|---|---|
| RAG 效果 | Recall@K、MRR / NDCG、引用正确率、幻觉率、无答案拒答率 | 同一黄金问题集、Embedding、ReRank、LLM、TopK | 可重放测试集 + 逐题结果 |
| 复杂文档 | 表格 / 标题 / 页码 / 图片保真率，解析成功率，每 100 页时间与成本 | 同一批扫描件、合同、研报、PPTX、XLSX | 原文与解析结果 diff + 人工抽检 |
| 在线性能 | P50 / P95 / P99 延迟、成功率、每秒请求、峰值并发 | 同一模型端点、向量库、机型、数据量与预热方式 | 压测脚本、原始报告、资源曲线 |
| 可靠性 | 节点失败恢复、重试幂等、队列积压、升级回滚、备份恢复 | 同一故障注入脚本与数据规模 | 故障时间线、丢数 / 重复记录、恢复时长 |
| 安全与治理 | 越权、SSRF、密钥泄漏、沙箱逃逸、租户隔离、审计覆盖 | 同一威胁用例与权限矩阵 | 用例结果、审计记录、整改项 |
| 三年 TCO | 许可、模型、解析 / OCR、存储、数据库、运维、升级与支持 | 统一三年业务增长假设 | 三年现金流 + 人天 + 风险准备金 |

以下指标在两侧都没有可比的统一公开口径，应保持「未公开 / 待 POC / 待合同」：稳态与峰值并发、每秒请求数、每分钟 Token 吞吐、指定硬件下的解析与检索延迟、最大应用数与知识库数、可用性 SLA 与 RTO / RPO、连接器与插件实时总数。

## 5. 中性选型建议

| 项目的第一成败因素 | 建议 |
|---|---|
| 扫描合同、扫描研报、复杂表格与版式解析几乎决定项目成败 | **RAGFlow 必须进入最终 POC**，用企业自己的黄金集比较 |
| 知识源主要在 Confluence、S3、Notion、Google Drive 等海外协作栈 | RAGFlow 的连接器覆盖是现成收益 |
| 已在使用 Langfuse 做链路观测 | RAGFlow 的追踪语义可直接复用 |
| 需要严格的许可宽松度（内部平台化、深度二开） | Apache-2.0 边界更宽，但仍需法务逐条审 LICENSE |
| 知识源主要在飞书、语雀、钉钉，且需要持续同步 | FastGPT 原生覆盖这几类中国知识源与网站持续同步 |
| 需要每天定时自动跑、并把结果发到企业 IM | FastGPT 的内置定时自动化与中国渠道发布是可核验的差异点 |
| 需要管理员审计日志与统一配额（API Key、分享链接、QPM） | FastGPT 商业版与 Cloud 已公开这套闭环 |
| 上线后要持续运营（用户反馈、会话标注、应用评测、看板） | FastGPT 的运营闭环覆盖这条链路 |

**还有一种常被忽略的答案：两家都进 POC。** 当文档主体确实很难解析、同时又要交付自动化与渠道运营时，把两者放在一次 POC 里并行验证，往往比反复论证谁更强更省时间——解析这一段用同一批黄金文档比出高下，应用与运营那一段比人天与落地门槛，最后合成一张总成本表。这种做法的额外成本主要是一次部署与一批测试数据的准备，相对于选错平台后的迁移成本，通常是划算的。选型报告里写明「两家都进 POC 的理由与判据」，也比一句「已评估」更容易通过内部评审。

**一条表述纪律**：本文不主张「FastGPT 在所有文档上都更准」。解析质量的结论只能由企业真实黄金集与统一条件的实测给出，任何一方的产品文档都不能替代这次实测。同样，公开资料里没有列出某项能力，只说明截至核验日该能力未被官方公开列出，正确的处理是把它写进 POC 清单或向厂商书面确认，而不是当作对方的缺陷。
