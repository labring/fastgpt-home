# 自研或直接跑开源与用平台怎么选：四组必算成本

**只需要一个向量检索 Demo，自研不难，而且大概是最快的路。要长期维护解析与训练队列、工作流恢复、沙箱、权限、审计、评测、渠道与升级，那就是在自建一个平台团队——这一步的决策不该只看服务器和模型调用费。**

这篇文章不主张「自研一定做不成」。技术团队自己能搭是事实。真正需要摆清楚的是自研的边界在哪里：哪些工作是一次性的，哪些是长期的；哪些能力现在不需要，但上线半年后一定会被要求补上。

判断方法只有一个可靠版本：**用同一份三年需求清单，向自研方案与采购方案分别报价，把开发、测试、安全、运维、升级与值班的人天全部入账。** 不入账人天的对比，结论一定偏向自研。

本文所列成本项来自项目核验的公开事实与工程通例，核验日 2026-07-20。

---

## 1. 现状：为什么原型效果不错，一到生产就不稳定

自建 RAG 原型跑通得很快——装一个向量库，切分文档，接一个模型，几天就能演示。生产环境里出问题的通常不是这条主链路，而是围绕它的一圈工程：

- 文档换了一种版式，解析结果就崩了，但没人知道是哪一步崩的；
- 同一份文档换个问法就检索不到，因为一份正文只挂了一条索引；
- 训练队列里有几十份文档失败，只能整库重跑；
- 工作流跑到第五步失败，没有断点，只能从头再来；
- 有人问「上个月的调用花在哪」，答不出来，因为成本没有按解析、向量化、检索、生成分阶段拆开；
- 业务部门要求接飞书和企微，发现渠道适配要从零写；
- 安全评审来了，问代码执行节点有没有沙箱、外部工具有没有 SSRF 防护、密钥怎么管、审计日志留多久。

这些都不是「做不出来」的问题，是「要不要长期维护」的问题。**AI 知识库不能自动保证「上传资料后就一定答得准」**——效果受文档质量、切分方式、更新频率、权限边界、检索配置与模型能力共同影响，而上面每一条都需要有人负责调。

---

## 2. 四组必算成本

自研或直接跑开源的完整工作量，至少落在下面四组。建议按组逐项列人天，而不是估一个总数。

### 2.1 第一组：解析、检索与知识维护

文档解析、分块、索引、检索、ReRank、引用溯源与重训队列。

这一组最容易被低估，因为原型阶段只需要「能切能查」。进入生产后要补的是：多版式解析的兜底路径、切分策略的可干预性、一份正文挂多条索引、索引的独立编辑、训练队列失败后的单条修复、检索历史的可回溯、引用能定位到原文的哪一段。

### 2.2 第二组：Agent 与工作流运行时

Agent / 工作流运行时、失败恢复、人工交互、调试、日志与评测。

关键的三项：**失败恢复**（节点失败后能否重试且幂等，队列积压怎么处理）、**人工交互**（流程中间需要人工确认时能否暂停并原地恢复，能否穿透子应用、工具与循环保留状态）、**评测**（用固定问题集做回归，否则每次改动都是盲改）。

### 2.3 第三组：安全与治理

模型适配、工具安全、密钥、SSRF、代码沙箱、鉴权、RBAC、SSO、审计、多租户。

这一组通常不是技术团队自己提出来的，而是安全评审或客户合规提出来的，出现时间往往在上线前一个月。**代码沙箱与租户隔离是其中最难补的两项**：它们涉及运行时架构，不是加一个中间件能解决的。

### 2.4 第四组：发布、运维与支持

发布渠道、API 兼容、升级回滚、备份恢复、监控告警、值班与用户支持。

值班是最容易漏的一项。一个面向全员的知识库问答，答错了、答慢了、挂了，都会有人找；这部分人力必须计入长期成本，而不是算成「顺手看一下」。

**这一组里还有一项没有等价物：原厂支持。** 自研侧不存在「原厂」这一栏，社区 Issue 与社区群是善意的互助，写不进采购文件，也没有覆盖时段与首次响应目标。采购平台侧这一栏是可以谈的合同条款：

| 这一项 | 自研 / 直接跑开源 | 采购平台 |
|---|---|---|
| 覆盖时段与首次响应目标 | 自己的值班表与 on-call 轮换 | 按支持档位划分，覆盖时段可到 7×24，首次响应目标按档位递进 |
| 安全补丁与版本升级 | 自己跟踪上游、自己做升级与回滚演练 | 付费档位含安全补丁与新功能支持；升级支持范围以合同为准 |
| 故障定位与恢复责任 | 全部在自己一侧 | 由责任矩阵划分，需在服务清单中逐项写明 |
| 首次部署与调试 | 自己承担 | 交付范围可含安装部署、调试与原厂技术维保 |
| 支持渠道 | 社区渠道，无响应承诺 | 工单、专属支持群，最高档位增加客户经理 |

比较这一栏的正确做法不是问「哪个更好」，而是把自研侧那一列折算成人天与 on-call 排班，放进 4.1 的三年表里。**首次响应目标不等于在同一时限内完成修复，未书面约定的指标不构成承诺**——采购侧的这一栏同样要落到合同才算成立。

### 2.5 一条判断自研边界的实用标准

上面四组不必全部自建才算合格。把每一项按「必选 / 可选 / 未来」标注一次，会比逐项估人天更快得出结论：**必选项**是不做就无法上线的（解析、检索、基本权限、发布渠道）；**可选项**是可以先用简化方案、后续再补的（评测体系、成本拆分、会话标注）；**未来项**是当前业务规模还用不上的（多租户、集群、跨地域容灾）。

自研在「必选项少、可选项能砍、未来项确定不做」的场景里是合理选择——比如一个部门内部使用、文档版式统一、不接外部渠道、不涉敏感数据的知识库。反过来，如果必选项里已经出现 SSO、审计、多租户、代码沙箱中的任意两项，那么自研的实际范围就已经是一个平台，而不是一个应用；这时候再比较采购方案，结论往往和最初的直觉不同。**这份「必选 / 可选 / 未来」表也是后面第 4 节两边同时报价的输入——没有它，两份报价比的不是同一件事。**

## 3. 平台层的代价也要如实算

「多一个平台会增加延迟和成本」——**这个担心是成立的。** 编排、RAG、ReRank、外部工具与观测都会加长调用链，任何声称平台层没有性能开销的说法都不可信。

正确的验证方式是取一条真实业务链路，做三组对照：直接调用模型、自研编排、用平台。三组都测端到端 P95 / P99 延迟、Token 与解析与存储成本、失败率，同时记录开发与运维人天。**结论应当是「多出来的调用链开销，是否换来了可接受的开发与运维效率」，而不是「有没有开销」。**

同样要如实说的是平台迁移成本。用平台不等于被绑定模型或云——模型、存储、向量后端、API 与部署方式都可以按企业自身选择；但工作流配置与商业功能确实存在迁移成本，采购前就应当明确退出方案。POC 阶段就该要求验证：应用与数据能否导出、能否更换模型、能否更换向量后端、备份能否恢复、API 是否兼容。任何「完全没有锁定」的说法都不成立。

## 4. 怎么自己验证：同一份需求清单，两边同时报价

### 4.1 三年 TCO 计算表（价格栏自行填入）

| 成本层 | 自研 / 直接跑开源 | 采购平台 | 填表要求 |
|---|---|---|---|
| 基础设施 | 服务器或 GPU、数据库、向量库、对象存储、网络 | 同上（自托管）或订阅内含（云） | 按三年业务增长假设，不用当前用量 |
| 模型消耗 | 向量化 + 生成，按真实问答量估算 | 同上 | 两边用同一个问答量假设 |
| 许可 / 订阅 | 开源许可为零，但需核对二开与分发边界 | 按官方定价页当日价格 | 两边价格均由采购方填当日实价 |
| 解析 / OCR | 自建或调用第三方 | 同上 | 复杂版式比例越高，这一项差别越大 |
| 平台工程人力 | 第 2 节四组全部人天 | 集成与配置人天 | **这一项决定结论，不能省** |
| 安全与运维 | 沙箱、密钥、权限、审计、多租户、监控 | 版本内含部分 + 客户侧运维 | 按安全评审实际要求列 |
| 升级与值班 | 升级回滚、备份恢复、告警响应、用户支持 | 支持档位 + 客户侧一线 | 按三年计，不按首年计 |
| 风险准备金 | 关键人员流失、返工、评审不通过 | 版本边界不匹配、迁移成本 | 两边都要留 |

**最终产出是三年现金流 + 人天 + 风险准备金三张表**，并对成员数、文档量、请求量做灵敏度分析。只比首年许可费的对比没有意义。

### 4.2 六类必测项（两种方案用同一套条件）

| 类别 | 必测指标 | 统一条件 |
|---|---|---|
| RAG 效果 | Recall@K、MRR / NDCG、引用正确率、幻觉率、无答案拒答率 | 同一黄金问题集、Embedding、ReRank、LLM、TopK |
| 复杂文档 | 表格 / 标题 / 页码 / 图片保真率，解析成功率，每 100 页时间与成本 | 同一批扫描件、合同、研报、PPTX、XLSX |
| 在线性能 | P50 / P95 / P99 延迟、成功率、每秒请求、峰值并发 | 同一模型端点、向量库、机型、数据量与预热方式 |
| 可靠性 | 节点失败恢复、重试幂等、队列积压、升级回滚、备份恢复 | 同一故障注入脚本与数据规模 |
| 安全与治理 | 越权、SSRF、密钥泄漏、沙箱逃逸、租户隔离、审计覆盖 | 同一威胁用例与权限矩阵 |
| 三年 TCO | 见 4.1 | 统一三年业务增长假设 |

另外，判断一个产品「是否太早期」时，不要用 Star 数或发布频率代替生产证据。把「早期」拆成版本稳定性、升级回滚、数据恢复、并发、安全与支持响应六项，逐项在企业自己的环境里验证——做一次升级与回滚演练、一次备份恢复、一次长稳压测、一组安全用例与故障注入，比任何社区热度指标都可靠。

## 5. 中性选型建议

| 项目条件 | 建议 |
|---|---|
| 需求是小团队内部使用，能自行承担部署、升级、备份与安全 | 社区版自托管或自研都可能够用，不必过度采购 |
| 只需要向量检索 + 问答，且没有多渠道、多租户、审计要求 | 自研的边界清晰，可控 |
| 需求会进入 SSO、多租户、审计、长周期日志、商业支持或明确 SLA | 这些是平台工程的长期项，此时应把采购方案纳入比较 |
| 有严格的外部同步 + 部门信息隔离 + 强审计与成本管理组合要求 | 逐项写进合同与验收，不能只比「支持私有化」一个勾 |
| 技术团队有能力自建，但人手已满负荷 | 真正要比的是人天机会成本：这批人天投在平台工程上，还是投在业务上 |
| 业务方要求有可写进合同的响应时段与恢复责任 | 自研侧没有原厂这一栏，需自建值班与 on-call；此时应把支持档位与责任矩阵纳入比较 |

**一条表述纪律**：本文不使用「自研一定做不成」这类判断。自研能不能做成取决于团队与投入，能被客观比较的只有同一份三年需求清单下的成本与交付时间。
