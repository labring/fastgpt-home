# Let an ads page override the shared second screen

Every `/ads/` landing page renders the same second-screen template (a badge, a heading, and three checklist cards), which keeps eight paid pages consistent at a fixed cost. A paid visitor arriving on a keyword that matches a published `/compare/` article is better served by that comparison's own evidence than by the generic template, so the registry may now carry two optional page-level modules: `comparisonTable` renders a three-column semantic `<table>` (dimension, Dify, FastGPT) with the verification date and a public HTTPS source link directly under it, above the three checklist cards; `why` replaces the shared capability band's heading and three cards, and each card may carry a `verdict` line quoting the Dify-side finding. Both are optional fields on `AdsLandingPage`, validated in `src/content/ads/loader.ts` and asserted in `scripts/verify-ads.js`, so a page that supplies neither keeps rendering the shared template byte-for-byte.

The Dify comparison page is the first adopter: its five table rows and three capability cards are cut from `content/competitors/dify-vs-fastgpt.md`, and the hero's decorative comparison-matrix SVG was removed because it duplicated the band's real table. The first screen (H1, subtitle, the three paragraphs, trust line, and form copy) stays frozen and registry-sourced.

A third optional module, `cases`, does the same for the shared published-deployments band. A page that ships it renders three A-level customer cases from the customers centre — client name, case title, the case's own published figures, and a link to the case detail page on `fastgpt.cn` — with the band's badge and subtitle overridable per page. The Dify landing is the first adopter; the other seven ads pages keep the shared cards unchanged. The card thumbnails are the customers-centre CDN URLs, so the figures a paid visitor reads here are the same ones the case page publishes.
