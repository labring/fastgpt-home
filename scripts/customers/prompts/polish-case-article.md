# 排版硬性规范（逐条执行）

## 高亮块（blockquote callout）

- 模块 1 用 `> [!blue] 标题`（方案定位一句话 + 核心数字）；模块 2 用 `> [!red]`（核心痛点）；模块 3 用 `> [!purple]`（方案承接关系）；模块 4 用 `> [!green]`（落地价值）；模块 6 用 `> [!orange]`（选型价值）。
- 第一行必须是 `> [!颜色] 标题文字`，标题直接跟在 `[!颜色]` 后，**禁止**把 `> [!颜色]` 单独成行，**禁止**在第一行使用 `**` 加粗。第二行起可写正文，空 `>` 行分段。
- 正文关键数字与核心结论用 `<mark>数字或短语</mark>` 高亮：模块 1 ≥2 处、模块 2 ≥1 处、模块 3 ≥2 处、模块 4 ≥3 处、模块 5 ≥2 处、模块 6 ≥1 处、模块 7 ≥3 处。表格与图表里的数字不需要 `<mark>`。
- **强调一致性（高亮 + 加粗叠加）**：正文与表格里的所有强调统一写成 `<mark>**内容**</mark>`（mark 在外、strong 在内），实现「黄色背景 + 加粗」双重突出，如 `覆盖<mark>**70%**</mark>用户检索需求`。正文/表格里不允许出现只有 `**加粗**` 或只有 `<mark>高亮</mark>` 的单独强调。⚠️ 禁止写成 `**<mark>70%</mark>**`——markdown 的 `**` 无法跨越行内 HTML 标签，会变成字面星号。
- **高亮块标题行例外**：`> [!颜色] 标题` 第一行**禁止写 `**`**（标题已自动加粗），内部核心数字只写 `<mark>70%</mark>`；高亮块第二行起的正文按「正文/表格」规则处理（可用 `<mark>**…**</mark>`）。

## 表格

- 模块 1：落地效果摘要表（场景/覆盖入口/服务体量/核心效果，数据行 ≥4）。
- 模块 2：背景表（**≥5 数据行**，含企业类型、业务入口、体量、人工团队、系统来源）+ 痛点表（**≥8 数据行**，写足 8–10 行，覆盖知识分散、流程割裂、人工响应不稳定、数据安全顾虑、运营成本、质量波动等）。
- 模块 4：价值收益表（≥7 数据行，列必须含「落地前 / 落地后 / 改善幅度」）。
- 模块 5：真实使用场景表（≥3 数据行）。
- 模块 6：竞品对比表（≥7 数据行，**竞品一律用「商业 SaaS 客服」「自研方案」「传统人工」等通用指代，禁止出现真实竞品名**）+ 采购顾虑回应表（≥5 数据行）。

> 表格行数按「数据行」计（不含表头与分隔行），必须写满下限，宁多勿少。

## Mermaid（模块 3，必须 ≥1 张）

## ECharts（必须 ≥5 张，覆盖 ≥5 个模块）

- 围栏代码块标记**全小写 `echarts`**，内部直接是合法 option 对象（以 `{` 开头、`}` 结尾），**禁止** `const option=` / `export default` / 注释 / 尾部逗号 / emoji；key 与字符串值用双引号，布尔与数字不加引号；坐标轴图必须带 `"grid": { "containLabel": true }`。

- 模块-图表映射：模块 2 用问题分布图（pie/nightingale/stacked-bar 等）；模块 3 用 **graph（力导向或固定坐标）或 tree**（⚠️ 当前 echarts 版本 sankey/funnel 渲染异常会大面积空白，禁用）；模块 4 至少 3 张不同类型（落地前后对比 bar、趋势 line、雷达 radar 等）；模块 5 用场景图（horizontal-bar/pictorialBar 等，注意横向柱状图要把 `xAxis.type` 设为 `"value"`、`yAxis.type` 设为 `"category"`）；模块 7 用 half-doughnut/combo（核心 KPI），不要画成 POC 流程图。
- 模块 1 也放 1 张核心指标图（half-doughnut / combo），让 7 个模块都有图表覆盖。

- 图表中的数据只能来自原文或由原文数字合理演绎（如用原文百分比画对比图），**禁止凭空编造新指标**。

# 事实与内容纪律（最高优先级）

1. **引用数字必须逐字保留**：`{{citedNumbers}}` 中列出的每个数字串（空格归一后）都必须出现在正文、表格或图表里，缺一个即不合格。数字串整体保留（如 `70%`、`60%`、`52 万+`），`<mark>` 只能包裹完整数字串（如 `覆盖<mark>70%</mark>用户检索需求`），**禁止在数字中间插入标记或改写数字**。

   - 原文的编号/符号列表项（如模块 6 的选型价值 4 条）必须逐条保留原意，可以微调措辞但不能合并、删除或降级为一句概括；

   - 原文段落的核心观点（背景-原因-结果论证链、复用场景、选型前提、验证指标、效果免责声明等）必须保留；

# 写作风格

像资深售前顾问写给 CTO/CIO/业务负责人的落地案例：先讲场景与结果，再讲背景与方案，价值数据要解释「为什么变化」；场景要具体可感知；结尾只推动「预约免费 POC，用客户自身数据验证」，不生硬销售。
