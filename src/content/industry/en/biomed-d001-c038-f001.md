# HTTP Interface and External Systems for Rational Drug Use Clinical Trial Pre-screening

## Data Characteristics in This Category

Data for rational drug use clinical trial pre-screening primarily consists of drug inserts, clinical guidelines, medical literature, and patient electronic health records. These data sources vary in type and update frequency. Drug inserts and clinical guidelines typically update quarterly or annually, containing structured information such as drug indications, contraindications, dosage, and adverse reactions. Medical literature updates monthly or even weekly, including a large volume of unstructured or semi-structured research reports and case analyses. Patient electronic health record data generates in real-time, involving medication history, allergy history, diagnostic results, and laboratory indicators.

Data document structures are complex. They include standardized XML/JSON format data and a large amount of unstructured text in PDF and HTML formats. Fields and units involve drug dosages (mg, g) and laboratory results (mmol/L, U/L), making unit standardization critical for data processing.

## Constraints Imposed by Data Characteristics on "HTTP Interface and External Systems"

Rational drug use pre-screening requires high data timeliness and accuracy. Therefore, HTTP interface integration with external systems must consider data source update frequency. Real-time patient record data requires low-latency interface calls, while quarterly updated drug inserts can accept periodic batch synchronization.

Document structure complexity dictates that interfaces must support parsing multiple data formats. For example, for PDF-formatted drug inserts, the interface needs to call OCR services or preprocessing services for text extraction. Field and unit standardization requires strict data validation and conversion after data reception to ensure consistency of drug dosage and laboratory indicator units. For instance, if the drug dosage unit returned by an external system differs from the internal system, automatic conversion is necessary to prevent deviations in pre-screening results.

| Configuration Item | Suggested Value | Rationale |
|---|---|---|
| `AIPROXY_API_ENDPOINT` | `http://localhost:8080/v1/chat/completions` | For local development and testing environments, avoids direct calls to production APIs. |
| `MAX_RETRIES` | `3` | Addresses temporary external system failures or network fluctuations, improving interface stability. |
| `REQUEST_TIMEOUT_SECONDS` | `60` seconds | Most rational drug use rule calculations are complex, requiring longer response times. |
| `ACCESS_TOKEN` | Configure according to external API documentation | Ensures authentication and authorization for interface calls. |
| `DATA_FORMAT_CONVERSION` | `JSON to Internal Schema` | Unifies data structures from different sources, facilitating internal model processing. |
| `ERROR_NOTIFICATION_EMAIL` | `devops@example.com` | Notifies relevant personnel promptly for troubleshooting upon interface call failure. |

## Three Common Mistakes

*   The `Human` field is empty in the response record preview. This occurs because the conversation message structure returned by the external system does not match the internal expectation, leading to field mapping failure.
*   Frontend cannot display streamed SSE output HTTP requests added in Flow in real-time. This occurs because the HTTP client does not correctly handle the `Content-Type: text/event-stream` header and does not parse data blocks as an event stream.
*   HTTP interface calls frequently encounter `401 Unauthorized` errors. This occurs because the `ACCESS_TOKEN` parameter is incorrect or expired, failing external system authentication.

## How to Confirm Correct Configuration

*   For core rational drug use rules, simulate different patient medical record data, call the HTTP interface, and check if the returned pre-screening results match expectations.
*   In development mode, check if the local service pointed to by the `AIPROXY_API_ENDPOINT` configuration is running normally, accessible, and can correctly process requests.
*   Monitor interface call logs for status codes other than `200 OK` and check error logs for warnings regarding data parsing or conversion.
*   Submit a pre-screening request containing complex drug combinations via the frontend interface. Confirm that the streamed output displays pre-screening suggestions sequentially and that the final result is complete.
