# HTTP Interface and External Systems for GMP Compliant Products

## Data Characteristics
GMP compliant product data originates from production batch records, quality inspection reports, equipment calibration records, deviation investigation reports, and CAPA (Corrective and Preventive Action) documents. This data typically exists as structured documents (e.g., PDF, Word, Excel) or semi-structured data (e.g., CSV files exported from LIMS systems). Data update frequency varies by specific process. Production batch records generate upon batch completion, quality inspection reports upon inspection result issuance, and CAPA reports may update over longer periods. Document structures are rigorous, with high standardization of fields and units. Examples include batch number, production date, expiry date, inspection item, inspection result, judgment criteria, deviation description, root cause analysis, and improvement measures. Each field has clear definitions and units, such as `mg/L`, `pH`, `°C`, `%`. Data integrity, accuracy, and traceability are core GMP compliance requirements, often including audit trail information like timestamps and operator signatures.

## Constraints Imposed by "HTTP Interface and External Systems"
The strictness and high traceability of GMP compliant data impose specific constraints on HTTP interfaces and external systems. Since data often exists in document form, interface design must prioritize file upload, parsing, and structured extraction capabilities to handle diverse document formats. Varying update frequencies require interfaces with flexible triggering mechanisms. These mechanisms must support real-time data synchronization (e.g., LIMS results) and accommodate periodic or event-driven data updates (e.g., batch record archiving). The high standardization of fields and units means strict data type validation and unit consistency checks are essential during data transmission and reception to maintain data accuracy. Furthermore, data integrity and audit trail requirements necessitate that interfaces preserve original data source information when processing data and may need to support digital signatures or hash verification to ensure data immutability. Interface response speed and stability are also critical, as any data processing delay or failure can impact compliance assessment processes.

## Configuration Guidelines

| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| `UPLOAD_FILE_MAX_SIZE` | `50 MB` | Accommodates GMP documents that may contain numerous images or scanned files, ensuring large file uploads are possible. |
| `MAX_RETRIES_ON_FAILURE` | `3 times` | Addresses transient network fluctuations or occasional external system failures, enhancing data transfer robustness. |
| `HTTP_REQUEST_TIMEOUT` | `60 seconds` | Covers the processing time of most external systems, preventing timeouts due to excessive waiting. |
| `BATCH_PROCESS_SIZE` | `10 Records` | Balances processing efficiency with system load, particularly suitable for bulk uploading inspection reports. |
| `AUTH_TOKEN_EXPIRY_BUFFER` | `5 minutes` | Refreshes tokens before actual expiration, preventing authentication failures caused by expired tokens. |
| `ERROR_NOTIFICATION_RECIPIENT` | `合规团队邮箱` | Ensures the relevant team receives timely notifications and can intervene when interface calls fail. |

## Common Pitfalls
*   Symptom: External system receives empty or type-mismatched fields. Cause: JSON field names in the HTTP request body do not match the external system's expected field names, or data types (e.g., string vs. number) are not correctly converted.
*   Symptom: External system cannot recognize or parse files after upload. Cause: File encoding or format is incompatible with the external system's supported types, or the `Content-Type` HTTP header is not correctly set.
*   Symptom: Frequent `401 Unauthorized` errors during API calls. Cause: The authentication token obtained from the `tokenLogin` interface has expired and is not refreshed or re-obtained in subsequent requests.

## Verification Steps
*   Upload a GMP batch record document containing standard fields and units. Verify that the external system completely and accurately receives and parses all key information.
*   Simulate network interruptions or brief external system outages. Verify that the interface's retry mechanism functions as expected and that data successfully synchronizes after recovery.
*   Check external system or FastGPT internal logs. Confirm that HTTP request response times are within acceptable limits and that no unexpected error codes appear.
*   Upload a file exceeding the `UPLOAD_FILE_MAX_SIZE` limit. Confirm that the system correctly returns an error message indicating the file size limit has been exceeded.

The values provided are common starting points and should be measured against the reader's own samples.
