# Tool Calling and Plugins for Supplier Audit Products

## Data Characteristics in this Category
Supplier audit data in the biopharmaceutical sector typically originates from audit reports, supplier qualification documents, quality management system documentation, and historical audit records. Data update frequencies vary; qualification documents may update annually, while audit reports usually generate periodically, such as semi-annually or annually. Document structures are diverse, including PDF audit reports, Word quality manuals, and Excel compliance checklists. Data fields include supplier name, audit date, auditor, audit findings (defect description, risk level), corrective actions, completion date, batch number, product name, and reagent batch. Units may include dates, text descriptions, risk levels (e.g., high, medium, low), and quantity units (e.g., batch, item).

## Constraints Imposed by these Characteristics on Tool Calling and Plugins
The diversity and unstructured nature of supplier audit data impose specific requirements on tool calling and plugins. First, processing numerous PDF and Word documents demands robust document parsing capabilities. This ensures accurate extraction of critical audit findings and corrective actions. Second, descriptive text in audit findings requires natural language processing for semantic understanding and classification. This enables comparison against regulatory standards or internal policies. Structured data in Excel spreadsheets, such as audit items and scores, requires precise field mapping. Inconsistent update frequencies necessitate flexible data synchronization mechanisms. These mechanisms must trigger corresponding extraction and indexing processes based on different data source update cycles. Furthermore, the need for precise matching of specific fields like batch numbers and product names emphasizes accuracy and strictness in parameter passing during tool calls.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| :----- | :------- | :----------- |
| `maxContext` | `3000` | Supplier audit reports are often lengthy; a larger context window is necessary to understand the full context and relationships within the report. |
| `PARSE_FILE_TIMEOUT_SECONDS` | `600 seconds` | Large files take longer to parse. This avoids parsing failures due to timeouts, especially for PDF reports with many charts. |
| `similarityThreshold` | `0.75` | This ensures that recalled audit clauses or compliance requirements are highly relevant to the user query, reducing false positives. |
| `retrievalQuantity` | `top 8` | Considering the complexity of audit questions, increasing the number of recalled items helps cover more potentially relevant information. |
| `postRequestFormat` | `application/json` | Most modern API interfaces use JSON for data exchange. This ensures compatibility between tool calls and target services. |
| `pluginRetryCount` | `3 times` | Audit system interfaces may experience transient network fluctuations or service busy states. Multiple retries improve call success rates. |

## Three Common Pitfalls
*   Plugin calls return a 400 error code: This usually occurs when `postRequestFormat` does not match the target API's requirements, or due to incorrect field types or missing mandatory fields in the `payload`.
*   The model's response fails to mention critical defect numbers from audit reports: This can happen if document parsing does not accurately identify and extract specific defect number formats, or if `similarityThreshold` is set too high, preventing relevant text from being recalled.
*   Inaccurate results for retrospective queries on supplier compliance issues: This often results from inadequate data update mechanisms, leading the model to retrieve outdated data that does not reflect the latest audit remediation status.

## How to Verify Configuration
*   Perform simulated audit queries. Check if the model's response accurately cites specific clauses and findings from audit reports. Verify the cited document sources and page numbers.
*   Upload and index supplier audit documents in various formats (PDF, Word, Excel). Cross-check if key fields (e.g., supplier name, audit date, defect description) are correctly extracted and displayed.
*   Call a plugin for an audit system API with complex parameters. Check if the request sends successfully. Compare the `payload` in the tool logs against the expected parameters.

The values provided are common starting points and should be measured against your own samples.
