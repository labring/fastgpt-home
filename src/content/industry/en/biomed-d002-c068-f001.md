# Integrating HTTP Interfaces with External Systems for Smart Triage

## Data Characteristics for Smart Triage Systems

Smart triage systems require data primarily from official medical guidelines, drug inserts, medical journal articles, and clinical case studies. This data updates frequently, especially with new drug approvals or changes in treatment protocols. The data structure typically includes symptom descriptions, diagnostic criteria, differential diagnoses, treatment plans, and prognosis information for diseases. It also covers indications, contraindications, dosage, and adverse reactions for medications. Field design incorporates standardized medical terminologies like ICD-10 disease codes, ATC drug classification codes, and SNOMED CT clinical terms, ensuring data accuracy and interoperability. Units strictly follow medical measurement standards, such as milligrams (`mg`) or milliliters (`ml`) for drug dosages, and days (`days`) or hours (`hours`) for time.

## Constraints from "HTTP Interfaces and External Systems"

The specialized nature and high update frequency of smart triage data impose specific requirements on HTTP interface design and external system interactions. First, diverse and dispersed data sources necessitate interfaces capable of aggregating information from multiple origins, such as disease knowledge bases and drug databases simultaneously. Second, standardized medical terminology requires strict adherence to specific encoding standards during data transmission. For example, `Content-Type` must be set to `application/json` with `charset=utf-8` to support multiple languages and special characters. High update frequency demands external systems support scheduled or event-driven data synchronization mechanisms to ensure the timeliness of triage information. The complexity of fields means interface responses may have deep data structures, requiring robust parsing capabilities on the client side. Furthermore, patient privacy and medical safety concerns mandate strict authentication (`Authorization` header) and encrypted data transmission (HTTPS) mechanisms for data security.

## Configuration Guidelines

| Configuration Item | Recommended Value | Rationale |
| :----- | :------- | :----------- |
| `requestTimeout` | `60000 ms` | Prevents request timeouts due to slow responses or large data volumes from external medical knowledge bases. |
| `maxRetries` | `3 times` | Improves data retrieval reliability, addressing temporary network fluctuations or external service instability. |
| `Cache-Control` | `no-cache` | Ensures each request retrieves the latest triage information, preventing the use of outdated data. |
| `Authorization` | `Bearer Token` | Uses standard OAuth 2.0 token authentication to secure interface access permissions. |
| `responseBodySizeLimit` | `5 MB` | Limits the size of a single response body, preventing memory overflow or network congestion from very large medical documents. |
| `headers.Accept-Language` | `zh-CN,en-US` | Prioritizes Chinese content while also supporting English, adapting to multilingual medical resources. |

## Common Pitfalls

*   **Symptom**: Smart triage results lack information on newly launched drugs. **Reason**: The external drug database's synchronization policy fails to pull the latest data in time, or the interface call frequency is too low.
*   **Symptom**: Disease diagnosis codes in triage recommendations appear empty or in the wrong format. **Reason**: The JSON field names returned by the HTTP interface do not match system expectations, or medical terminology encodings like `SNOMED CT` are not parsed correctly.
*   **Symptom**: After uploading a patient's medical record file in a conversation, the system cannot analyze its content. **Reason**: The file parsing service (`PARSE_FILE_TIMEOUT_SECONDS`) timed out, or the file type (`UPLOAD_FILE_MAX_SIZE`) is unsupported, preventing extraction of valid information.

## Verification Steps

*   Use a simulator or a real environment to query with new drugs or the latest treatment protocols. Check if the triage results include the relevant latest information and verify its update timestamp.
*   Call the HTTP interface to retrieve disease or drug data. Check if the returned `ICD-10` or `ATC` codes conform to the expected format and validate the `Content-Type` header.
*   Upload medical files of different sizes and formats. Observe if the system successfully parses and extracts key information. Check the file parsing service logs for timeout errors.

The values provided are common starting points and should be measured against your own samples.
