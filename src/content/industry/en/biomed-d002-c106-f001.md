# HTTP Interface and External Systems for High-Value Consumables

## High-Value Consumables Data Structure

High-value consumables data originates from manufacturers' official databases, the National Medical Products Administration's (NMPA) medical device registration information, and hospital procurement and inventory management systems. This data updates infrequently, typically quarterly or annually. However, critical information such as prices, batch numbers, and expiration dates update more frequently.

Document structures typically include:
* Product name
* Model specifications
* Registration certificate number
* Manufacturer
* Scope of application
* Key parameters
* Unit
* Packaging
* Batch number
* Sterilization method
* Storage conditions
* Unique Device Identification (UDI) code

Field units are strict. For example, dimensions use millimeters or centimeters, and volumes use milliliters or liters, often with specific medical abbreviations. The UDI code is a core identifier; its format and parsing rules must precisely follow international standards.

## Constraints from HTTP Interface and External Systems

The low update frequency of high-value consumables data means interface calls do not need to be frequent. However, each call must ensure data completeness and consistency.

The uniqueness and complexity of UDI codes require interface parameters to accurately receive and parse code strings containing multiple segments of information.

Diverse data sources necessitate interface designs that include data cleaning and standardization. This unifies field naming and unit representation across different sources. For example, different systems may use different field names or date formats for "expiration date."

Queries involving batch numbers and expiration dates require a degree of real-time responsiveness. Interfaces must respond quickly.

This data often supports decision-making and compliance reviews. Therefore, data transmission security, accuracy, and traceability are critical. Secure HTTP protocols and strict authentication mechanisms are necessary.

## Configuration Settings

| Configuration Item         | Recommended Value                               | Rationale                                                                                                 |
| :------------------------- | :---------------------------------------------- | :-------------------------------------------------------------------------------------------------------- |
| `API_ENDPOINT`             | Official API address of manufacturer or regulator | Ensures authoritative and up-to-date data sources, e.g., `https://data.nmpa.gov.cn/api/medical_device`   |
| `AUTH_HEADER`              | `Authorization: Bearer <API_KEY>`               | Uses standard OAuth2 or API Key authentication to secure data interfaces                                  |
| `REQUEST_TIMEOUT_SECONDS`  | `60 seconds`                                    | Allows sufficient response time for potentially large data volumes, preventing timeouts due to network latency |
| `MAX_RETRIES`              | `3 times`                                       | Improves request robustness against network fluctuations or temporary service unavailability              |
| `UDI_PARAM_NAME`           | `udi_code` or `device_identifier`               | Clearly specifies the parameter name for receiving UDI codes, aiding clarity for API callers              |
| `DATA_SCHEMA_VALIDATION`   | Enabled (e.g., using JSON Schema for validation) | Ensures received data structure and field types conform to expectations, preventing processing errors from inconsistent data formats, e.g., `{"udi_code": {"type": "string", "pattern": "^\\(01\\)\\d{14}"}}` |

## Common Pitfalls

*   External interface calls return a `401 Unauthorized` error. This indicates an incorrect or expired API Key in the `Authorization` header.
*   Key fields (e.g., batch number, expiration date) are empty in the data returned by the interface. This occurs when the external system's API response structure does not match expectations, or data cleaning rules fail to process the data correctly.
*   Uploaded files to the knowledge base cannot be parsed or retrieved correctly. This happens if the file format is unsupported or if `Content-Type` is not set correctly during upload, leading to parsing failure.
