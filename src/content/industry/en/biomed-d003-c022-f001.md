# HTTP Interface and External Systems for On-Call Transfer in WeChat Work Group Automation

## Data Characteristics for This Category

On-call transfer scenarios involve several data types: on-call schedules, WeChat Work group member lists, external system event notifications, and transfer records. On-call schedules are typically structured data, such as JSON or CSV, containing staff names, IDs, on-call periods, and contact information. Update frequency depends on the scheduling cycle, potentially weekly or daily. WeChat Work group member data is usually retrieved via API, including member IDs and nicknames. External system event notifications are often real-time, pushed in JSON or XML format, and include event type, timestamp, related entity ID, and urgency level. Transfer records contain the initiator, recipient, transfer time, reason, and processing status.

## Constraints Imposed by "HTTP Interface and External Systems"

Periodic updates to on-call schedule data require the external system to support scheduled polling or receiving pushes to ensure on-call information remains current. If the on-call schedule is a manually maintained CSV file, file upload and parsing mechanisms require consideration. The dynamic nature of WeChat Work group member lists necessitates real-time querying before a transfer operation to ensure the validity of target groups or members. The real-time nature of external system event notifications requires the HTTP interface to have high availability and fast response capabilities to avoid event processing delays. The urgency field in event notifications may need mapping to FastGPT's internal priority strategies, affecting message sending frequency or transfer workflows. Storing and querying transfer records requires external database support and data synchronization via HTTP interfaces.

## Configuration Guidelines

| Configuration Item | Suggested Value | Rationale |
|---|---|---|
| `externalApiUrl` | `https://api.example.com/oncall/schedule` | The actual API address of the on-call schedule data source, ensuring accessibility. |
| `updateIntervalSeconds` | `3600` seconds | On-call schedules typically update hourly or less frequently, reducing unnecessary requests. |
| `timeoutMilliseconds` | `5000` milliseconds | Expected external interface response time, preventing task backlog due to long waits. |
| `requestHeaders` | `Authorization: Bearer <TOKEN>` | External API authentication requirements, ensuring data request security. |
| `responseBodyPath` | `$.data.oncall_list` | Parses the JSON response body to extract the core on-call staff list data path. |
| `maxRetries` | `3` times | Retry mechanism for temporary network fluctuations or service unavailability, improving stability. |

## Common Pitfalls

*   External system event notifications fail to trigger transfer workflows: The HTTP interface's configured listening path does not match the path pushed by the external system, preventing correct event reception.
*   On-call staff transfers are incorrect or fail: The retrieved on-call schedule data is outdated, or the mapping between WeChat Work group member IDs and on-call schedule staff IDs is incorrect.
*   Data loss after restarting Docker containers: Docker containers are not correctly configured with data volumes (`volumes`), preventing internal container data from persisting to the host.

## Verification Steps

*   Check FastGPT's log system to confirm successful HTTP requests to the external system and observe whether the response status code is 200.
*   Manually trigger a simulated external system event. Observe whether WeChat Work groups receive transfer notifications as expected and check if notification content includes correct on-call information.
*   Compare the on-call staff list stored within FastGPT with the latest external system on-call schedule data to confirm data synchronization accuracy and timeliness.
*   Simulate a network outage or temporary external system unavailability. Observe whether FastGPT's error handling mechanism performs retries as configured.
