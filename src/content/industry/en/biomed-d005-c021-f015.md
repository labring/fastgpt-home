# Deployment and Upgrade for Supplier Audit Regulations

## Data Characteristics

Supplier audit regulation data primarily originates from internal quality management system documents, supplier management manuals, audit report templates, non-conformance records, and relevant regulatory standards. These documents are typically in PDF, Word, or scanned image formats. Updates are driven by audit cycles and regulatory changes, usually occurring quarterly or annually. However, processes for handling major non-conformances might update in real-time. Document structures often include chapter headings, clause numbers, specific requirement descriptions, flowcharts, and attachments. Common audit items involve fields such as audit date, supplier name, auditor, non-conformance description, corrective actions, and completion date. There are no unified numerical units; descriptions are primarily text-based.

## Constraints from Data Characteristics on Deployment and Upgrade

The update frequency for supplier audit regulation documents is relatively low. However, a single update might involve revisions to multiple linked files. This requires a deployment solution that supports incremental updates and version management for document batches. Documents contain numerous flowcharts and tables, demanding strong complex layout recognition capabilities from the parser to ensure complete information extraction. Non-conformance descriptions in audit reports are often free-form text. This requires deep semantic understanding from the text vector model to accurately capture subtle compliance issues. Furthermore, due to compliance requirements, high demands exist for data security and isolation. Private deployment is a common choice, and attention is necessary for database connection stability and permission management.

## Configuration Recommendations

| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| `UPLOAD_FILE_MAX_SIZE` | `500 MB` | Supplier audit reports and regulation documents can be large due to numerous images and scanned pages. |
| `PARSE_FILE_TIMEOUT_SECONDS` | `600 seconds` | Complex PDF document parsing can be time-consuming; this prevents parsing failures due to timeouts. |
| `Chunk size` | `800–1200 characters` | Ensures each segment contains sufficient context while preventing individual segments from being too long and diluting key information. |
| `Recall count` | `Top 8 entries` | Audit regulation queries often require cross-verification from multiple angles; increasing recall improves hit rate. |
| `Similarity threshold` | `0.75` | Ensures retrieved results are highly relevant to the query intent, reducing interference from inaccurate information. |
| `maxContext` | `3000 Tokens` | Audit regulation Q&A typically requires a longer context to understand complex clauses and processes. |

## Common Pitfalls

*   After deployment, the login screen displays "Database Connection Failed" (Database connection failed), and logs show `ECONNREFUSED` or `Access denied`. This usually indicates the database service is not running, the database address is misconfigured, or the database username/password is incorrect.
*   Uploading a large audit report PDF file results in a `File parse timeout` error in the logs. This occurs when the `PARSE_FILE_TIMEOUT_SECONDS` parameter is set too low, not allowing enough time for complex document parsing.
*   Querying "vendor How to Handle Audit Non-Conformities" (How to handle supplier audit non-conformances) returns unexpected results or misses critical steps. This might be due to overly large document segmentation granularity, causing relevant information to be split across different segments, or insufficient understanding of specific technical terms by the vector model.
