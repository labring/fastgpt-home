# HTTP Interface and External Systems for Small Molecule Pharmaceutical Regulations

## Data Characteristics

Small molecule pharmaceutical regulations and Standard Operating Procedures (SOPs) originate from regulatory bodies, internal quality management systems, R&D process documents, and production specifications. Data updates are infrequent, typically occurring when regulations change or internal processes are optimized, with cycles ranging from months to years. Documents are primarily hierarchical text, often containing numerous clauses, definitions, diagrams, and appendices. Fields and units are highly specialized; for example, "half-life" is measured in hours (h), "dosage" in milligrams (mg), and batch numbers are usually alphanumeric. Strict version control and audit trails are common.

## Constraints Imposed by These Characteristics on "HTTP Interface and External Systems"

The specialized and structured nature of small molecule pharmaceutical regulations and SOP documents requires HTTP interfaces to strictly adhere to predefined field types and formats during data transmission. This includes accurate transfer of batch numbers or chemical structure strings. The low frequency of document updates means real-time requirements for interfaces are not high, but strong historical version traceability is crucial. The extensive hierarchical text necessitates that file upload interfaces support various document formats (e.g., `.pdf`, `.docx`) and ensure complete content parsing, especially for tables and embedded objects. The rigor of fields and units demands external systems perform effective data validation upon receipt, for example, ensuring correct dosage units to prevent semantic errors due to unit confusion.

## Configuration Guidelines

| Configuration Item | Recommended Value | Rationale |
| :----------------- | :---------------- | :-------- |
| `MAX_FILE_SIZE_MB` | `50 MB` | Accommodates large SOP documents that may include numerous diagrams and version histories. |
| `PARSE_TIMEOUT_SECONDS` | `300 seconds` | Allows sufficient time for parsing complex PDF or Word documents, preventing timeouts. |
| `CHUNK_SIZE_TOKENS` | `800–1200 characters` | Ensures the integrity of regulatory clauses, preventing critical information from being split. |
| `SIMILARITY_THRESHOLD` | `0.75` | Guarantees high relevance of retrieval results to regulatory clauses, reducing false positives. |
| `HTTP_REQUEST_TIMEOUT` | `60 seconds` | Provides ample response time for external systems that may involve database queries and complex logic. |
| `ERROR_RETRY_COUNT` | `3 times` | Addresses transient network fluctuations or occasional external system failures, improving interface stability. |

## Common Pitfalls

*   HTTP requests return `502 Bad Gateway` or `504 Gateway Timeout`: This indicates the external system's processing time exceeds the default timeout settings of the gateway or proxy server.
*   Knowledge base content is missing or garbled after document upload: This occurs when the parser fails to correctly handle specific fonts, embedded objects, or complex table structures within the document.
*   Calling an external interface returns `400 Bad Request` or `422 Unprocessable Entity`: This signifies that the data format, field types, or enumeration values in the request body do not match the external system's API definition, for example, an incorrect batch number format.

## Verification Steps

*   Upload a `.pdf` document containing complex tables and multi-level headings. Check if the hierarchical structure of the content in the knowledge base is complete and can be correctly retrieved.
*   Send a request containing all required fields to the external system via the HTTP interface. Verify that the external system successfully received and processed it, by checking the external system's logs.
*   Attempt to use the chat interface to ask a detailed question about a specific regulatory clause. Verify that the answer accurately cites the original text and provides supporting evidence, checking if the cited `doc_id` points to the correct file.
*   Call the external interface with a request containing intentionally incorrect data formats. Confirm that the error code and error message returned by the external system clearly indicate the specific problematic field.

The values provided are common starting points and should be measured against the reader's own samples.
