# HTTP API and External Systems for Stem Cell Therapy Regulations

## Data Characteristics in This Category
Regulatory and SOP documents for stem cell therapy originate primarily from legal frameworks published by the National Medical Products Administration (NMPA) and the National Health Commission, internal hospital quality management system documents, and guidelines from industry associations. These documents are typically in PDF or DOCX format, feature a rigorous content structure, and contain extensive specialized terminology, flowcharts, and tables. Update frequency is relatively low, usually quarterly or annually, but revisions have a broad impact. Fields often include batch numbers, cell line identifiers, patient IDs, operator qualifications, and environmental monitoring data. Units strictly adhere to biological and medical standards; for example, cell counts are expressed as `cells/mL`, temperature in `℃`, and time in `min` or `h`. Document length is generally substantial, with single files potentially exceeding `50 pages`.

## Constraints Imposed by These Characteristics on "HTTP API and External Systems"
The data characteristics of stem cell therapy regulatory documents impose specific requirements on HTTP API and external system integration. First, the specialized and rigorous nature of the documents demands that the model accurately understands context to avoid misinterpretations due to ambiguity. Long documents with complex structures require efficient chunking and indexing mechanisms to support precise retrieval. The low update frequency means data synchronization does not need to be frequent, but each update requires comprehensive and meticulous incremental or full replacement. The specialized fields and standardized units require the API to correctly identify and process this information during data parsing, for example, treating `5 x 10^6 cells/mL` as a single numerical expression. Furthermore, since documents often include charts, the system needs capabilities to process non-textual information or perform preprocessing before upload.

## Configuration Guidelines

| Configuration Item | Recommended Value | Rationale |
| :----------------- | :---------------- | :-------- |
| `UPLOAD_FILE_MAX_SIZE` | `100 MB` | Regulatory documents are often large; ensures full file upload. |
| `PARSE_FILE_TIMEOUT_SECONDS` | `600 seconds` | Parsing large files takes time; prevents timeout interruptions. |
| `Chunk Length` | `800 characters` | Balances context completeness and retrieval efficiency, improving recall accuracy. |
| `Similarity Threshold` | `0.75` | The domain is highly specialized; a higher threshold ensures highly relevant recall. |
| `Rerank Top K` | `Top 5` | For critical regulatory questions, ensures the most relevant information is displayed first. |
| `maxContext` | `4096 tokens` | Ensures the model can process longer contexts and understand complex regulatory clauses. |

## Three Common Pitfalls
1. Symptom: The HTTP API returns `404 Body Not Found`. Cause: The `Content-Type` request header is not correctly set to `application/json` or another expected type, preventing the server from parsing the request body.
2. Symptom: DeepSeek and similar models' reasoning process does not appear in the callback interface. Cause: The API request does not explicitly set the `stream` parameter to `true` or include a `detail` parameter to obtain detailed processing steps.
3. Symptom: After uploading documents, some specialized terms or numerical units have low matching scores during retrieval. Cause: Documents were not sufficiently preprocessed, for example, by standardizing unit representations, expanding specialized vocabulary synonym libraries, or performing OCR, leading to suboptimal vectorization.

## How to Verify Configuration
1. Upload a stem cell therapy SOP document containing complex flowcharts and specialized terminology. Verify successful parsing and generation of retrievable text content, and check if key fields are correctly extracted.
2. Simulate questions via the API interface. Questions should cover key clauses and operational details from the regulations. Verify the accuracy and completeness of the returned results and check if the reasoning chain is logical.
3. Test the incremental update function with a known revised regulatory document. Confirm the system correctly identifies and applies new content, and that old version content is no longer recalled.
