# Deployment and Upgrade for After-Sales and Warranty Smart Customer Service

## Data Characteristics

After-sales and warranty data in the biomedical field originates primarily from internal CRM systems, work order management platforms, and equipment logs. This data updates frequently. New product launches, regulatory changes, fault reports, and repair records generate real-time or near real-time updates. Document structures typically include fields such as product model, serial number, batch number, fault description (often involving specialized terminology and abbreviations), diagnosis results, repair solutions, replaced parts lists, warranty status, and service engineer records. This data often exists as a mix of structured (database records) and unstructured (user feedback text, engineer reports) formats. Critical fields, such as product batch numbers and equipment parameters, have strict formats and validation rules.

## Constraints Imposed by These Characteristics on Deployment and Upgrade

High-frequency data updates require FastGPT's knowledge base synchronization mechanism to support incremental updates after deployment. This avoids lengthy full rebuilds. Mixed structured and unstructured data necessitates flexible configuration of data source connectors. These connectors must parse database tables and effectively process PDF and DOCX engineer reports and user feedback. The extensive use of specialized terminology and abbreviations demands higher semantic understanding from the model. This requires targeted vocabulary expansion and domain adaptation. Strict field formats and validation rules require integrating data cleaning and validation logic during data preprocessing. This ensures accuracy of imported knowledge base data and prevents smart customer service response deviations due to data quality issues. During upgrades, changes in data schema or fields may require adjusting data mapping relationships and indexing strategies.

## Configuration Guidelines

| Configuration Item             | Recommended Value                                | Rationale                                                                      |
| :----------------------------- | :----------------------------------------------- | :----------------------------------------------------------------------------- |
| `UPLOAD_FILE_MAX_SIZE`         | `500 MB`                                         | Ensures upload of large equipment log files or repair reports with multiple images. |
| `PARSE_FILE_TIMEOUT_SECONDS`   | `300 seconds`                                         | Accommodates parsing time for complex documents (e.g., diagnostic manuals with diagrams). |
| `Chunk size` (Segment Length)    | `800–1200 characters`                                  | Balances completeness of specialized terminology with retrieval efficiency, reducing context loss. |
| `Recall count` (Recall Count)      | `10–15 entries`                                       | Covers multiple potential fault descriptions and solution matches.             |
| `Similarity threshold` (Similarity Threshold) | `0.75–0.85`                                      | Ensures accurate matching of specialized fault descriptions, reducing irrelevant recalls. |
| `LLM_MODEL`                    | `gpt-4o` or `glm-4`                              | Supports complex reasoning and multi-turn conversations, understands medical terminology. |

## Common Mistakes

*   After an upgrade, smart customer service returns empty results for specific product model warranty inquiries. This may be due to incorrect configuration of the new data synchronization task, preventing new product warranty information from being imported into the knowledge base in a timely manner.
*   A user submits a fault description containing an equipment serial number, but smart customer service fails to accurately identify it and provide a corresponding solution. The system responds with generic information. This occurs because critical entities like serial numbers were not effectively extracted and tagged during data preprocessing.
*   In a Docker environment, some knowledge base containers fail to start and display a `Reached the max retries` error. Common causes include incorrect database connection parameter configuration or insufficient storage volume permissions, preventing the container from persisting data or connecting to dependent services.

## Verification Steps

*   Select 5-10 recently updated product warranty policies or fault cases. Consult the smart customer service to verify its ability to accurately recall and integrate relevant information.
*   Simulate a user submitting an inquiry containing a specific product model, serial number, and fault code. Check if the smart customer service returns precise repair suggestions or guidance.
*   Review the FastGPT backend knowledge base synchronization logs. Confirm that incremental data update tasks execute successfully at the expected frequency and without parsing errors or data loss warnings.
*   During peak system load, monitor the smart customer service's response time. Ensure it maintains a smooth interactive experience even with a high volume of users.
