# HTTP Interface and External Systems for Solid Tumor Registration and Reporting

## Data Characteristics for This Category
Solid tumor registration and reporting data originates from multi-center clinical trials, pathology reports, imaging examinations, gene sequencing results, and adverse drug event reports. Data update frequencies vary: clinical trial data accumulates continuously during trials, while pathology and gene reports generate at specific time points. Document structures are complex, often including PDF clinical study reports, Word expert opinions, Excel raw data tables, and DICOM imaging files. Fields involve specific metrics like `Tumor_Size_mm`, `Histologic_Grade`, and `Mutation_Type`. Units must strictly adhere to international standards; for example, tumor size in millimeters (mm), and gene mutation information might use HGVSc or HGVSp nomenclature.

## Constraints Imposed by These Characteristics on "HTTP Interface and External Systems"
The complex data structures and diverse file formats of solid tumor registration and reporting data demand high data parsing capabilities from HTTP interfaces. For instance, processing DICOM imaging files requires specialized parsing libraries and APIs; standard JSON or XML parsers are insufficient. Varying update frequencies from multiple sources necessitate incremental synchronization and version control capabilities in interfaces to prevent data conflicts and duplication. Strict unit and field specifications mean interfaces must perform rigorous validation during data transmission and reception, such as ensuring the `Tumor_Size_mm` field only accepts numerical values with correct units. Furthermore, sensitive patient privacy information, such as `Patient_ID`, requires interfaces to support end-to-end encryption and strict access control to ensure data security and compliance.

## Configuration Guidelines

| Configuration Item             | Recommended Value                               | Rationale                                                                                             |
| :----------------------------- | :---------------------------------------------- | :---------------------------------------------------------------------------------------------------- |
| `UPLOAD_FILE_MAX_SIZE`         | `500 MB`                                        | Imaging files and clinical reports are often large, requiring sufficient upload capacity.             |
| `PARSE_FILE_TIMEOUT_SECONDS`   | `600 seconds`                                        | Large PDF reports and DICOM files take longer to parse; this prevents parsing timeouts and task failures. |
| `maxContext`                   | `4000–8000 characters`                                | Ensures the ability to process longer pathology diagnoses or clinical conclusions in one go, maintaining context integrity. |
| `Chunk size`                     | `800–1200 characters`                                 | Balances semantic integrity and processing efficiency for text, adapting to complex paragraph structures in medical documents. |
| `Similarity threshold`                   | `0.75`                                          | Ensures retrieved clinical trial data is highly relevant to user queries, reducing false positives.   |
| `API_KEY_ROTATION_INTERVAL`    | `90 days`                                         | Regularly rotating API keys reduces security risks and complies with medical data security standards. |

## Common Pitfalls
*   When calling an external gene sequencing API, a 401 Unauthorized error returns because the `API_KEY` is incorrectly configured or expired.
*   After uploading a large imaging file, the system displays a "file parsing failed" error. This occurs when `PARSE_FILE_TIMEOUT_SECONDS` is set too low, preventing DICOM file parsing completion.
*   When retrieving clinical trial data from an external database, some critical fields like `Tumor_Size_mm` are empty. This happens because the interface incorrectly maps or validates numerical fields and units from the external system.

## Verification Steps
*   Perform upload operations for files of different sizes and formats (e.g., PDF, DICOM). Check system logs to confirm file parsing is error-free and within expected timeframes.
*   Use queries containing specific medical terminology and numerical units. Call external knowledge bases via HTTP interfaces. Verify the accuracy of field values and units in the returned results.
*   Simulate concurrent requests. Test interface response times and error rates under high load to ensure external API call stability.
*   Regularly check `API_KEY` validity. Verify that its permission settings in external systems align with business requirements.

The values provided are common starting points and should be measured against the reader's own samples.
