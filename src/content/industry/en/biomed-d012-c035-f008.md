# Tool Calling and Plugins for Hospital Operations Drug Vigilance

## Data Characteristics

Hospital operations drug vigilance data originates from internal hospital information systems. These include Electronic Medical Records (EMR), physician order systems, pharmacy management systems, laboratory and imaging systems, and adverse event reporting systems. Data updates frequently. Adverse event reports typically log within 24–48 hours of an event. Medication records update in real time. Document types are diverse. They include structured database records (e.g., drug batch, patient ID, dosage, administration time, ICD-10 diagnosis codes), semi-structured clinical orders, and extensive unstructured text (e.g., doctor's rounds notes, nurse's observation records, patient complaints, adverse reaction descriptions). Key fields include `patient_id`, `drug_generic_name`, `drug_trade_name`, `batch_number`, `dose` (units mg/g/ml), `administration_route`, `administration_time`, `adverse_event_description`, `event_time`, and `management_action`.

## Constraints on Tool Calling and Plugins

High real-time data availability and diversity in hospital operations data impose strict requirements on tool calling and plugin response speed and data parsing capabilities. Rapid updates to real-time medication data and adverse event reports mean tools must frequently and efficiently retrieve the latest information and trigger analyses promptly. The large volume of unstructured text (e.g., doctor's rounds notes) requires plugins to have strong natural language processing capabilities. This includes accurately extracting key medical entities and events from free text, such as identifying drug names, adverse reaction symptoms, dosages, and temporal relationships. Structured and semi-structured data require flexible field mapping and data type conversion mechanisms to accommodate format differences between systems. Precise drug dosage units (mg/g/ml) and timestamp formats (`YYYY-MM-DD HH:MM:SS`) demand high accuracy and strict format validation during parameter passing. This prevents result deviations or call failures due to unit or format errors.

## Configuration Guidelines

| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| `tool_request_timeout` | `60 seconds` | Most internal hospital APIs respond within 30 seconds. This allows for complex queries and network fluctuations. |
| `max_api_retries` | `3 times` | Internal systems can experience transient network glitches or service busyness. Multiple retries increase success rates. |
| `text_extraction_model` | `Domain-specific pre-trained medical model` | Hospital medical record text is highly specialized. General models lack accuracy for medical entity and relationship recognition. |
| `json_schema_validation` | `Enabled` | Ensures data retrieved from APIs conforms to expected structures. This prevents subsequent processing failures due to inconsistent data formats. |
| `rate_limit_per_minute` | `120 times` | Most internal hospital APIs have call frequency limits. Configure based on actual API documentation to avoid triggering rate limits. |
| `datetime_format_standard` | `YYYY-MM-DD HH:MM:SS` | Standardizes time formats. This ensures consistent timestamp parsing across systems, for example, `administration_time`. |

## Common Configuration Pitfalls

*   Receiving a `404 Not Found` error when calling an external API often indicates an incorrect `base_url` or `path` configuration, or an invalid `API_KEY` preventing correct request routing.
*   Plugin execution returning empty or type-mismatched data fields usually results from insufficient entity extraction rules for unstructured text, failing to correctly parse critical information like `adverse_event_description`, or from `json_schema_validation` not strictly validating data types.
*   Frequent tool call timeouts or slow responses may indicate a `tool_request_timeout` set too short, or performance bottlenecks in the backend API itself, especially when processing large historical datasets or complex calculations.

## Verification of Configuration

*   Perform end-to-end testing on core tool calling paths. Simulate real medication records and adverse event reports. Verify that plugins successfully call backend APIs and return data with the expected structure.
*   Check log output. Confirm `tool_request_timeout` parameter effectiveness and the presence of network or request errors like `AxiosError`. Cross-reference the `status_code` of returned data.
*   Validate the accuracy of key fields extracted from unstructured clinical records, such as `drug_generic_name`, `dose`, and `event_time`. Ensure consistency with original text information and verify correct units and time formats.
*   Monitor tool call frequency. Ensure parameters like `rate_limit_per_minute` effectively control call behavior to avoid triggering rate limiting mechanisms of the target API.
