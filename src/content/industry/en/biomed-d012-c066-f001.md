# HTTP Interface and External Systems for Tender Bidding and Drug Vigilance

## Data Characteristics for This Category

Tender bidding data primarily originates from provincial and municipal drug procurement platforms, official medical insurance bureau websites, and third-party data service providers. This data is typically released in structured or semi-structured formats. Update frequencies vary; some provinces update monthly, while a few might update quarterly. Data documents are often in Excel, PDF, or web table formats. Key fields include generic drug name, dosage form, specification, manufacturer, winning bid price, listing status, and listing date. Units for fields are usually in RMB per minimum dosage unit, such as "RMB/tablet" or "RMB/vial." Some data may contain non-standardized text descriptions, requiring additional parsing.

## Constraints Imposed by These Characteristics on "HTTP Interface and External Systems"

The dispersed sources and varied update frequencies of tender bidding data require the HTTP interface to support multi-source data acquisition. It must also allow flexible configuration of scheduled tasks to adapt to different platform update cycles. The diversity of data formats, especially Excel and PDF documents, necessitates support for multiple parsers or preprocessing mechanisms. Numerical fields like price and specification, along with their units, require strict validation to prevent data import errors from affecting subsequent drug vigilance analysis. Non-standardized text descriptions demand robust text processing capabilities from the interface, potentially requiring natural language processing techniques for information extraction. Furthermore, since some platforms may implement anti-scraping mechanisms, flexible HTTP request headers and proxy configurations are crucial.

## Configuration Guidelines

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `HTTP_REQUEST_TIMEOUT` | `60 seconds` | Most tender platforms have longer response times; this prevents timeouts. |
| `MAX_BODY_SIZE` | `50 MB` | Accommodates potentially large individual Excel/PDF files. |
| `CRON_SCHEDULE_EXPRESSION` | `0 0 * * *` | Executes once daily at midnight, covering most provincial update cycles. |
| `HEADER_USER_AGENT` | `Mozilla/5.0...` | Simulates browser access, reducing the risk of being identified as a bot. |
| `DATA_PARSER_TYPE` | `excel, pdf, html_table` | Tender data comes in various formats, requiring multiple parser types. |
| `MAX_RETRIES_ON_FAIL` | `3 times` | Increases data acquisition success rate during network fluctuations or transient server failures. |

## Common Pitfalls

*   HTTP requests return 5xx status codes: This usually indicates target server overload or triggered anti-scraping mechanisms. Review `HEADER_USER_AGENT` and `HTTP_REQUEST_TIMEOUT` configurations, and consider implementing an IP proxy pool.
*   Key fields are empty or incorrectly formatted after data import: This occurs when the data parser fails to correctly identify table structures or field types in Excel/PDF. Adjust parsing rules or preprocessing scripts for specific data sources.
*   Inability to retrieve all qualifying listed records: This may be due to default API pagination limits. Check API documentation to ensure request parameters include pagination controls like `page` and `pageSize`, and implement loop requests.

## Verification Steps for Correct Configuration

*   Execute a complete data acquisition workflow. Check logs for HTTP status code 200 entries to confirm data source accessibility.
*   Randomly select recent tender bidding data files from several provinces. Compare them with the data imported into the system to verify the accuracy of key fields like drug name, price, and specification.
*   Review the execution frequency of data update tasks. Confirm it aligns with the actual update cycles of provincial tender platforms to avoid missed or duplicate acquisitions.
