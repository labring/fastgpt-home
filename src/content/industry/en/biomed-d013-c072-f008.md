# Tool Calling and Plugins for Cleaning Validation Quality Documents

## Data Characteristics

Cleaning validation quality documents include validation protocols, reports, deviation investigations, and risk assessments. These documents typically exist as PDFs, Word files, or structured text (e.g., XML). Data sources are often laboratory analysis systems, manufacturing execution systems (MES), and quality management systems (QMS). Update frequency is relatively low, with revisions usually occurring during new product introductions, process changes, or annual reviews. Document structures are highly standardized, adhering to regulatory requirements like GMP/GLP. They contain numerous fixed fields such as validation batch number, equipment ID, product to be cleaned, subsequent product, residue limit, sampling point, analytical method, recovery rate, acceptance criteria, and test results. Units are often international standard units (e.g., ppm, ppb, μg/cm², mg/L) with strict precision requirements. Some documents may include scanned handwritten signatures or charts, increasing the complexity of text recognition and structured extraction.

## Constraints on Tool Calling and Plugins

The low update frequency of cleaning validation documents means knowledge bases can use bulk import strategies. However, tool calls must ensure the data used is the latest approved version, avoiding outdated or draft data. The strict structure and fixed fields require high precision and strong constraints for parameter mapping and data extraction in tool calls and plugins. For example, when calculating residue concentrations or performing compliance checks, the system must accurately identify key fields like `residue limit` and `test results` and correctly handle their units. Handwritten signatures and charts necessitate robust OCR and image recognition capabilities to prevent critical information loss or misinterpretation. Furthermore, regulatory compliance requires plugins to cite or validate relevant regulatory clauses when making judgments or generating reports, ensuring accuracy and compliance of conclusions. Complex units and precision demands require strict type checking and unit conversion during numerical processing to prevent calculation errors.

## Configuration Guidelines

| Configuration Item           | Recommended Value | Rationale                                                    |
| :--------------------------- | :---------------- | :----------------------------------------------------------- |
| `UPLOAD_FILE_MAX_SIZE`       | `100 MB`          | Cleaning validation reports may contain many charts and scanned documents, leading to large file sizes. |
| `PARSE_FILE_TIMEOUT_SECONDS` | `600 seconds`          | Parsing complex PDF documents and performing OCR can be time-consuming. |
| `Chunk size` (Segment Length)  | `800–1200 characters`   | Preserves document context integrity, preventing truncation of critical information. |
| `Recall count` (Recall Count)    | `Top 8 entries`         | Ensures sufficient context recall, covering regulatory clauses and experimental data. |
| `Similarity threshold` (Similarity Threshold) | `0.75–0.85`       | Balances recall and accuracy, matching precise regulatory requirements and data fields. |
| `Rerank result count` (Reranked Return Count) | `Top 5 entries`         | Focuses on the most relevant key information, reducing the model's burden of processing irrelevant content. |

## Common Pitfalls

*   **Symptom:** API calls return answers with unit errors or inaccurate numerical values for key metrics (e.g., residue limits).
    **Reason:** The tool call did not standardize units or validate types for extracted fields, directly passing text values to calculation functions.
*   **Symptom:** The system generates compliance reports citing outdated or inapplicable regulatory clauses.
    **Reason:** The knowledge base did not differentiate document version states, and the tool call did not specify or validate the document's `approval date` field.
*   **Symptom:** Slow response times for dialogue APIs, leading to a poor front-end user experience.
    **Reason:** In streaming output scenarios, backend processing logic is not optimized, with fixed and long intervals between data returns.

## Validation Steps

*   Select a cleaning validation report with diverse data types (text, charts, tables). Verify if tool calls accurately extract key fields like `Device Number` (equipment ID), `residue limit`, and `test results`. Cross-reference extracted values with the original document for exact matches.
*   For numerical calculation scenarios, such as residue concentration calculations, manually verify the calculation results returned by tool calls. The error margin compared to expected results should be within acceptable precision limits.
*   Simulate user queries regarding the application of specific regulatory clauses or compliance judgments. Check if the regulatory provisions cited by the model are the latest versions and compare them against actual regulatory requirements to ensure accuracy and timeliness.
