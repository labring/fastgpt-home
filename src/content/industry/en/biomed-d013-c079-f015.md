# Deployment and Upgrades for Real-World Evidence (RWE) Quality Documentation

## Data Characteristics

Real-World Evidence (RWE) quality documentation originates from various sources, including Electronic Health Records (EHR), medical insurance claims databases, disease registries, and Patient-Reported Outcomes (PRO). Update frequencies vary; EHR data might update in real-time, while medical insurance claims data typically updates quarterly or annually in batches. RWE quality documents often include research protocols, data management plans, statistical analysis plans, ethics approvals, data traceability records, and study reports. These documents are commonly in PDF, DOCX, or structured text formats. Fields and units are highly specialized. For example, "diagnosis codes" use ICD-10, "drug dosage" is often in milligrams (mg) or grams (g), and "follow-up time" is measured in months or years.

## Constraints Imposed by Data Characteristics on Deployment and Upgrades

The diverse sources and varying update frequencies of RWE data necessitate a deployment solution that supports flexible data ingestion and incremental update mechanisms. Complex document structures, with extensive specialized terminology and cross-references, demand advanced text parsing and knowledge graph construction capabilities. Deployment must address the security and compliance of connections to different data sources, including de-identification of patient privacy data. During upgrades, the highly specialized content and rigorous terminology of these documents require strict semantic consistency testing after model updates. This ensures that the understanding of specialized terms remains accurate. Additionally, batch historical data updates may require index rebuilding, which necessitates evaluating the impact on system availability and planning for appropriate downtime or hot-update strategies.

## Configuration Guidelines

| Configuration Item         | Recommended Value              | Rationale                                                                      |
| :------------------------- | :----------------------------- | :----------------------------------------------------------------------------- |
| `UPLOAD_FILE_MAX_SIZE`     | `500 MB`                       | RWE research protocols and reports can contain numerous charts and attachments, leading to large file sizes. |
| `Chunk size` (Chunk Length)  | `800–1200 characters` (characters) | Ensures the integrity of specialized terminology and context, preventing semantic fragmentation. |
| `Similarity threshold` (Similarity Threshold) | `0.75`                         | Guarantees precise recall for highly specialized queries.                      |
| `PARSE_FILE_TIMEOUT_SECONDS` | `600 seconds` (seconds)             | Accommodates the longer parsing time for large PDF or DOCX files.              |
| `maxContext`               | `8192`                         | Supports the context of complex research backgrounds, methodologies, and analysis results. |
| `AI_PROXY_URL`             | `http://your_ai_proxy_service:port` | Ensures large language model requests are routed through a secure and compliant internal proxy. |

## Common Pitfalls

*   "Request Entity Too Large" errors when uploading large documents. This occurs if the web server or proxy's request body size limit is not adjusted.
*   After an upgrade, some specialized queries return empty or inaccurate results. This might be due to the new model version misinterpreting specific specialized terms, leading to invalid indexing or inaccurate recall.
*   Knowledge base links embedded in other web pages display "permission denied." This happens if FastGPT's configuration does not correctly set CORS policies or if the embedding page's Content Security Policy (CSP) restricts it.

## Verification Steps

*   Upload a typical RWE research report containing complex charts and specialized terminology. Confirm that the file parses successfully and that an index is built.
*   Query key specialized terms and concepts from the report. Verify the accuracy and completeness of the recalled content, and check if the results include the expected contextual information.
*   Call the knowledge base via API or embedding on a test page. Observe for cross-domain or permission errors, and ensure normal responses.
