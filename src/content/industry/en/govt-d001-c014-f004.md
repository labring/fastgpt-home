# Unit-Based System Retrieval Internal System and Data Q&A: Workflow Orchestration

## What the Data for This Category Looks Like
The data for unit-based system retrieval originates from official internal documents of subordinate units of state-owned enterprises and government departments, including management measures, operating procedures, red-headed official documents, and the like. The update rhythm is controlled independently by each unit, and synchronization is performed when new systems are released or existing systems are revised. Document structures typically include fields such as issuing unit, document number, effective date, main content, attachments, and others. Some documents mark the subordinate unit level and department code. Data is stored in the form of structured metadata paired with unstructured main content.

## What Constraints These Characteristics Impose on the "Workflow Orchestration" Link
Each unit’s data is stored dispersedly and has inconsistent update rhythms, which requires the workflow to support dividing the retrieval scope by unit dimension to avoid confusion of cross-unit data. Documents contain dedicated metadata fields, so the workflow must be configured with a metadata extraction node, using fields such as issuing unit and effective date as retrieval filter conditions. The presence of subordinate unit level and department code requires the workflow to pre-configure unit code mapping rules to ensure accurate matching of documents from the corresponding unit during retrieval. Additionally, document formats vary slightly across different units, so the workflow must be compatible with multiple document parsing formats to prevent parsing failures.

## How to Configure the Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| Variable Settings | Bind the unit code field in `variables` | Used to pass the target unit identifier for the current retrieval, accurately filter system documents of the corresponding unit |
| Node ID Configuration | Fill in the `nodeId` of the corresponding retrieval node | Ensure accurate calling relationships between nodes in the workflow, avoid node confusion |
| Unit Filtering Rule | Match by the unit code of the document | Match the unit code field in the document metadata to implement unit-based retrieval |
| Retrieval Timeout | 300–600 seconds | Adapt to the time consumption requirements of batch parsing of multiple documents during unit-based retrieval |
| Context Window Size | 8000–12000 token | Accommodate metadata and main content of multi-unit system documents, avoid truncation of key information |
| Retry Count | 2–3 times | Address scenarios of network fluctuations or temporary document parsing failures, improve workflow stability |

## Three Common Misconfigurations
- Phenomenon: A nested form input node in a workflow has a hidden dialog box when run independently, but displays the dialog box when nested within another workflow. Cause: The trigger condition for the form node is not configured in the nested workflow, so the dialog box settings from independent operation are retained by default.
- Phenomenon: The unit-based system retrieval workflow runs for an excessive duration and triggers a timeout error. Cause: A reasonable retrieval timeout is not configured, or retrieval tasks are not split by unit dimension, resulting in excessive document loading for a single task.
- Phenomenon: Results returned after the workflow runs include system documents from non-target units. Cause: The unit filtering rule is not configured correctly, or the correct `variables` parameter for passing the unit identifier is not bound.

## How to Verify a Correct Configuration
- Manually trigger the workflow, enter the identifier of the target unit, and confirm that the returned documents only cover the system content of that unit.
- View the workflow running logs to confirm that the `variables` parameter and `nodeId` configuration are correctly read and applied.
- Switch between nested call and independent operation scenarios, and confirm that the dialog box display status of the form input node matches expectations.
- Simulate retrieval scenarios with different document volumes, and verify that the workflow running status remains stable.

The values given are common starting points and should be measured against the reader's own samples.
