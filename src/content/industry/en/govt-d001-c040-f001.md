# Internal System and Data Q&A for Query Result Reports: HTTP Interfaces and External Systems

## What this category of data looks like
The data for this category comes from structured report datasets in the state-owned and public enterprise internal system document library and business data middle platform. The update rhythm has two modes: full synchronization every early morning, and real-time push after approval. Each single data entry includes fields such as unique identifier, content body, applicable scope, associated system number, and generation time. Units include characters, date formats, and department number identifiers. The number of detailed items per single data entry ranges from dozens to hundreds. The overall document structure has clear layers, making it suitable for structured extraction and interface transmission.

## How to set the configuration
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer {Internal interface token generated by FastGPT} | Adapts to the permission verification specifications of state-owned and public enterprise internal systems, ensuring interface access security |
| `variables` | `{"page_size": 100, "sync_type": "full"}` | Used to specify pagination size and synchronization type, adapting to the number of data detailed items and update rhythm |
| `responseData` | Only return `report_id, content, update_time, applicable_dept` | Filters invalid fields, reduces transmission traffic, and lowers parsing costs for external systems |
| Interface timeout setting | 600 seconds | A single data entry contains many detailed items, requiring sufficient response time |
| Incremental synchronization switch | Enabled | Adapts to real-time updated system and report data, reducing resource consumption from full synchronization |

## Three common mistakes
- Phenomenon: The interface returns duplicate report items, with an HTTP status code of 200. Cause: No pagination deduplication logic is configured, or the synchronization type in the `variables` parameter is set incorrectly, leading to repeated pulls.
- Phenomenon: External systems receive data with timeout errors, with a status code of 504. Cause: The interface timeout setting is not adjusted, and the large number of detailed items in a single data entry causes the response time to exceed the default threshold.
- Phenomenon: The interface returns empty fields, making it impossible to match internal system association relationships. Cause: The associated system number field is not retained in the `responseData` configuration, resulting in loss of core metadata.

## How to confirm the configuration is correct
- Initiate an interface call, confirm that the HTTP status code returned is 200 and there are no error prompts.
- Check the fields of the returned data, confirm that necessary metadata such as associated system number and generation time are included.
- Call the pagination query interface, check whether the number of returned items matches the page_size configured in `variables`.
- Trigger a real-time update event, call the incremental synchronization interface, confirm that the returned data includes the latest updated report items.
