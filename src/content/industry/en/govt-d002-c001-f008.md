# 12345 Citizen Hotline Ticket Handling: Service Inquiry and Response - Document Parsing and Chunking

## What this category of data looks like
Data for this category typically originates from the 12345 citizen hotline platform, contracting entity business systems, official knowledge bases, follow-up evaluation data, and local hotline management regulations. Commonly processed documents include request registration forms, dispatch records, handling responses, follow-up records, extension applications, return explanations, and knowledge base entries. Data is synchronized daily. Individual documents typically include fields such as request number, contracting entity, request content, handling node, response content, and follow-up evaluation. There is no unified fixed unit; fields and units adjust based on specific business scenarios.

## What constraints these characteristics impose on the document parsing and chunking link
The multi-source data and diverse document structures of this category require the parsing link to adapt to tickets, records, and policy documents in varying formats. The daily synchronization update rhythm requires the parsing process to support batch processing, to avoid delays that disrupt ticket circulation. Documents contain both structured tables (such as multi-column fields in dispatch records) and unstructured text (such as response content). Chunking must balance field integrity and contextual coherence, preventing splits that lose the association between requests and contracting entities. Government data accuracy requirements also mean the parsing link must retain key business fields, to avoid key information being broken by improper chunking. Such breaks could lead to ticket overdue or response rejection.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `chunkSize` | `800–1200 characters` | This category of documents includes short request entries and long response texts. This range balances contextual integrity and retrieval accuracy |
| `chunkSplitter` | Split by paragraph + title | Ticket documents are often segmented by business nodes. Splitting by title preserves the hierarchical association between requests, contracting information, and responses |
| `customPdfParse` | Enabled | This category includes policy document PDF files. Enabling this allows enhanced parsing to preserve table and text hierarchy |
| `PARSE_FILE_TIMEOUT_SECONDS` | `600 seconds` | Large dispatch summary documents take longer to parse. This duration prevents parsing failures from timeouts that disrupt ticket processing |
| `UPLOAD_FILE_MAX_SIZE` | `1000 MB` | Monthly ticket summary files imported in batches are usually large. This threshold covers conventional batch import requirements |
| `chunkSettingMode` | Manual configuration | This category of documents has large format differences. Manual configuration allows adjusting chunking rules for different document types |

This document is written based on FastGPT v4.17.0 configuration rules.

## Three common misconfigurations
- Symptom: Parsing fails after enabling `customPdfParse`, with logs showing minerU-related call errors. Cause: The minerU dependency environment was not configured correctly during local deployment, or the enhanced parsing option was not selected in the knowledge base settings.
- Symptom: Table fields in parsed ticket documents are missing, and contracting entities cannot be matched during retrieval. Cause: Multi-vector support was not enabled for table data, and the association between table columns and rows was not retained during chunking.
- Symptom: Empty results are returned when pulling the document library via API, and external table data cannot be synchronized. Cause: API call parameters were not configured correctly, or access permissions for the corresponding interface were not enabled.

## How to verify correct configuration
- Upload a dispatch record document containing structured tables, and check if the parsed data retains the full column and row contents of the table.
- View the knowledge base settings page, confirm that the `customPdfParse` option is selected, and that the `PARSE_FILE_TIMEOUT_SECONDS` parameter is set to the intended duration.
- Call the FastGPT file parsing API interface, upload a single ticket document, and check if the returned chunked results include complete business fields.
- Batch upload monthly ticket summary files, confirm that no timeout errors occur in parsing tasks, and that all documents have completed parsing.

The configuration values provided here are common starting points, and should be evaluated against the user's own sample data.
