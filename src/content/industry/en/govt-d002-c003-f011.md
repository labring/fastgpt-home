# Real Estate Registration Inquiry and Response: Forms and Interactions

## What the data for this category looks like
Data for this category comes from five sources: real estate registration information system, cadastral survey database, housing transaction online signing system, tax system, and electronic certificate library. The system updates this data daily. Daily interactions use several document types: registration application forms, ownership certificates, surveying and mapping results, tax payment vouchers, real estate ownership certificates, and registers. Data fields include real estate location, right holder information, ownership type, and registration type. Most units use standard real estate domain units, such as square meters, parcels, and pieces. The data structure associates homologous information across multiple systems. This ensures ownership status matches actual transactions and tax situations.

## What Constraints These Characteristics Impose on the Forms and Interactions Link
Form interactions must support cross-data source verification. This prevents conflicts between input information and cadastral or tax system data, per cross-system homologous data association rules.
Daily updated data requires form interaction nodes to use reasonable pull intervals. This ensures displayed ownership status is the latest.
Forms must split input modules by registration type. This matches upload and filling rules for different document types, such as application forms and ownership certificates.
Forms must preset standardized options for specific field units. This reduces manual input format errors.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `formInput` | Multi-stage input split by registration type | Matches the business structure of real estate registration with multiple documents and fields, avoids overly lengthy single-page input |
| User selection | Preset standard units and ownership type options from the real estate domain | Adapts to field unit and type requirements, reduces manual input format errors |
| Input verification rules | Associate cadastral and tax system data fields | Verifies consistency between input information and cross-source data, avoids registration conflicts |
| Data pull timeout | 15-20 seconds | Adapts to response delays of cross-system data pulls, ensures complete ownership status information is obtained |
| Single knowledge base recall limit | Top 8 entries | Covers common policy and process questions related to real estate registration, avoids excessive results interfering with inquiries |
| File upload restrictions | Only supports PDF and JPG formats, single file no larger than 10 MB | Matches general format and size requirements of daily business documents, reduces storage and parsing pressure |

## Three Common Mistakes
- Phenomenon: After configuring the `userSelect` interaction node, no selectable options load on the frontend page. Cause: No pre-data output node is configured in the workflow, so the interaction node cannot obtain optional data sources.
- Phenomenon: Workflow local debugging results are normal, but frontend actual testing returns mismatched inquiry results. Cause: Form variable configuration from the debugging environment is not synchronized to the formal environment, leading to inconsistent input parameters.
- Phenomenon: When real estate registration tax data obtained via HTTP request is passed to subsequent verification nodes, a large number of unnecessary backslashes appear. Cause: JSON automatic parsing configuration for response content is not enabled, so the original JSON string is passed as plain text.
