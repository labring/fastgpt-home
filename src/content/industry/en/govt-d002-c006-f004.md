# Infectious Disease Information Reporting and Monitoring Service Consultation and Response: Workflow Orchestration

## What the data for this category looks like
The core data for this category comes from the Chinese Center for Disease Control and Prevention Information System, medical institution HIS systems, infectious disease reporting systems, and laboratory testing systems, with a daily update frequency. Core documents circulated daily include infectious disease report cards, epidemic analysis reports, case correction records, clustered epidemic reports, and epidemiological investigation reports. Each document contains standardized fields such as case identifier, diagnosis time, reporting unit, and test results. Legal requirements apply to field priorities and validation rules across different document types.

## What constraints these characteristics impose on the "workflow orchestration" link
Daily updated data sources require workflows to include scheduled trigger nodes. Multi-source data access requires setting up cross-system data validation links. Standardized fields and legal rules require embedding hard-coded validation logic in workflows to avoid missed or delayed reports. Time-consuming case verification, duplicate card correction, and abnormal summary tasks need to be split into independent nodes to prevent single-node execution timeouts. Additionally, legal data reporting requirements mandate that workflows retain complete execution logs and traceable nodes for regulatory inspections.

## How to set configurations
This configuration is based on the FastGPT v4.17.0 workflow editor.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Single execution timeout | 1200–1800 seconds | Matches the upper time limit for daily multi-source data summary processing for this category |
| `variables` mapping | Bind case number, diagnosis time, and reporting unit fields | Corresponds to the core identifiers and validation fields of infectious disease report cards |
| `nodeId` binding | Specify the unique identifier of the core validation node | Ensures rapid localization of traceable links when exceptions occur |
| Data source retry count | 2–3 times | Addresses temporary network fluctuations that cause failed data pulls from disease control systems |
| Scheduled trigger frequency | 1 time per day | Matches the daily update rhythm of data for this category |
| Abnormal alert trigger | Bind workflow failure notifications | Meets the business requirement for timely disposal of errors in this category |

## Three common configuration mistakes
- Symptom: The workflow node interface displays `premature close` error logs. Cause: No timeout parameters adapted for disease control system data pulls are configured, leading to long connection interruptions.
- Symptom: When processing peak data, workflow execution time exceeds 1200 seconds and triggers an interruption. Cause: The single execution timeout value is not adjusted to match the time required for multi-source data summary.
- Symptom: After calling an external search node, the returned results do not include the case fields required for legal reporting. Cause: No dedicated data filtering rules for report cards are configured via `variables` mapping.

## How to confirm the configuration is complete
- Manually trigger the workflow for a single infectious disease report card, and check that no error messages appear in the execution logs for each node.
- Configure a temporary scheduled trigger task to verify that the daily automatic data pull, validation, and summary processes run normally.
- Import test samples with simulated peak data volume to confirm that workflow execution time does not exceed the preset timeout threshold.
- Simulate a node failure scenario to verify that abnormal alert notifications are triggered as configured and pushed to the specified channel.

The values listed here are common starting points, and should be evaluated against the user’s own operational samples.
