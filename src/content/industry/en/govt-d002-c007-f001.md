# Petition Matter Handling: Request Consultation and Response — HTTP Interface and External Systems

## What this category of data looks like
Data sources for this category include the national petition information system, local petition systems, the 12345 citizen hotline platform, grassroots governance platforms, and historical petition archives. The update frequency is daily. Associated daily documents include petition registration forms, acceptance notices, transfer and assignment notices, handling opinions, review and re-examination applications, and resolution plans. Data fields include information about the requesting party, request content, acceptance number, handling status, responsible unit, handling progress, and more. All fields follow the general format for petition business, with no additional custom statistical units.

## Constraints Imposed by These Characteristics on HTTP Interfaces and External Systems
Multi-source data access requires the interface to support request formats and authorization rules from different petition business systems, and to be compatible with field mapping logic for multiple document types. The daily update frequency requires the interface to support incremental pull mechanisms to avoid resource consumption from full synchronization. Structural differences across different documents require the interface to perform standardized validation on received petition data fields, ensuring core fields such as request content and acceptance number are complete. Handling errors can cause repeated petitions, petitions submitted beyond the appropriate hierarchy, and similar issues. The interface must have clear error return and retry mechanisms to ensure the reliability of data flow.

## How to Configure Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Interface timeout period | 600 seconds | Adapts to the standard response duration of petition business systems, preventing data synchronization interruptions caused by excessive waiting time |
| `Authorization` configuration | System key with Bearer prefix | Complies with the interface security specifications of most petition business systems, ensuring data transmission security |
| `variables` mapping rules | Match standard fields of petition documents | Ensures petition data pulled from external systems can be correctly mapped to the application's context variables |
| `responseData` parsing method | Extract a subset of core business fields | Standardizes the processing of petition data formats returned by different systems, unifying internal usage structures |
| Retry strategy | Retry 2 times after failure, with a 30-second interval | Addresses temporary interface call failures caused by network fluctuations, ensuring data synchronization integrity |
| Single pull limit | 1000 entries | Adapts to the single data return limit of petition business systems, avoiding interface overload |

## Three Common Configuration Mistakes
- A 401 Unauthorized status code is returned after the interface is called. The core cause is that the key format in the `Authorization` header is not correctly configured, and does not match the security verification rules of the petition business system.
- Data fields pulled by the interface are empty. The cause is that the `variables` mapping rules are not configured according to the standard fields of petition documents, resulting in structured data returned by the external system failing to correctly match the application context.
- Interface calls time out. The cause is that a reasonable timeout period is not set, exceeding the default response duration of the petition business system, leading to connection interruption.

## How to Confirm the Configuration Is Correct
- The test interface is invoked, and the returned `responseData` field is checked to confirm it includes core fields of documents such as petition registration forms and acceptance notices.
- Daily incremental data synchronization is simulated, and the interface is checked to confirm it only pulls newly added petition data for the current day, with no repeated pulls.
- An interface call failure is triggered, and checks are performed to confirm the configured retry strategy automatically retries, and that data synchronization completes normally after the retry.
- The `Authorization` header configuration is checked to confirm it completely matches the key format of the connected petition business system.
