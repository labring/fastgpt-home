# Petition Matter Handling: Inquiry and Response - Workflow Orchestration

## What this category of data looks like
Data sources include the national petition information system, local petition systems, the 12345 citizen hotline platform, grassroots governance platforms, and historical petition archives, with daily updates. Daily processed documents include petition registration forms, acceptance notification letters, transfer and assignment letters, handling opinions, review and re-examination applications, and resolution plans. Core fields include requesting party information, matter category, handling progress, review and re-examination status, and more. The data structure is designed around the statutory handling process, and must strictly align with the standardized steps of petition-related business.

## Constraints imposed by these characteristics on workflow orchestration
Multi-source data synchronization requires workflow configurations to include cross-system data pull nodes, to ensure accurate acquisition of daily incremental data.
Diverse business documents must be bound to generation rules based on process steps, to prevent mismatches between document types and process steps.
Standardization of core fields requires workflow nodes to enforce mandatory parameter verification, to avoid process exceptions caused by missing fields.
The most time-consuming screening and coordination steps require configuring parallel processing nodes, to improve workflow efficiency.
The serious potential consequences of errors require setting verification and traceability nodes, to avoid duplicate petitions or petitions submitted to higher-level authorities than required.
The traceability requirement for the review and re-examination link requires retaining associated nodes for historical handling records, to ensure full process traceability.

## How to configure the workflow
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Global Variables | Preset core field set for petition business | Matches mandatory fields of documents such as petition registration forms and handling opinions, uniformly manages reusable parameters via `variables` |
| Node Trigger Rules | Follow statutory process step order | Follows the standard process for petition matter handling, sequentially starts nodes bound to `nodeId` such as acceptance screening, responsibility coordination, and opinion generation |
| Context Window | 1000-1500 preceding characters | Stores historical petition records and handling materials to ensure AI responses comply with business specifications, calibrated via actual testing |
| Variable Binding Rules | Associate historical petition data to `variables` | Provides complete business background data for AI response nodes, improving response accuracy |
| Output Node Binding | Associate corresponding document templates | Binds dedicated output configurations for documents of different links such as acceptance notification letters and handling opinions |
| Exception Capture Configuration | Enable global exception capture, set timeout threshold to 300 seconds | Covers exceptions in cross-system data pulling, document generation, and other links to prevent process interruptions |

This configuration applies to FastGPT v4.17.0

## Three common configuration mistakes
- Symptom: The workflow throws a `Cannot convert undefined or null to object` error during runtime. Cause: Mandatory petition business fields are not configured in `variables`, resulting in missing parameters when nodes are called.
- Symptom: AI-generated responses are output directly to the dialog box, and cannot be output after secondary processing via the text splicing component. Cause: The automatic output switch of the AI dialogue node is not turned off, and the output result is not bound to the custom processing node.
- Symptom: Historical petition records cannot be passed as variables to workflow nodes. Cause: The storage node for historical petition data is not associated in global variables, and the data source binding of `variables` is not configured correctly.

## How to verify a successful configuration
- Manually trigger the workflow and check whether the input parameters of each node match the preset business fields.
- Simulate a complete handling process to verify whether documents for each link are generated according to rules and bound to corresponding output nodes.
- Trigger an exception scenario to verify whether the global exception capture node starts normally and records error information.
- View the final output interface to confirm that response content is displayed only after custom processing.
