# Petition Handling: Inquiry and Response — Tool Calling and Plugins

## What This Category of Data Looks Like
This category of data comes from the national petition information system, local petition systems, the 12345 citizen hotline, grassroots governance platforms, and historical petition archives.
It is updated daily.
Daily processed documents include petition registration forms, acceptance notices, transfer and assignment letters, handling opinions, review and re-examination applications, and resolution plans.
Core fields include petitioner identification, requested issue, acceptance number, handling stage, responsible unit, and policy basis.
The data structure is designed around statutory handling processes. It links requests and handling traces circulated across multiple platforms.

## Constraints for Tool Calling and Plugin Workflows
Multiple data sources require tool calling to adapt to interface specifications of different systems. This avoids data pull failures caused by format incompatibility.
Daily update frequency requires plugin configuration to use incremental synchronization logic. This prevents excessive resource usage from full data pulls.
Diverse document types require tools to support parsing different business documents. Examples include petition registration forms and handling opinions, to meet accurate field extraction needs.
Core links tied to statutory handling processes require tool calling results to strictly match business fields. This prevents repeated petitions or handling opinions being corrected during review due to missing or incorrect fields.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | Set to `auto` or specify a business tool name | Adapt to the need to on-demand call screening, policy query and other tools during petition handling, and flexibly match different handling stages |
| `functionCall` | Enable and bind the petition business-specific tool set | Ensure tool calling strictly follows the statutory petition handling process, and avoid irrelevant tools interfering with business logic |
| Plugin loading path | Point to the business plugin deployment directory | Resolve the community-reported issue of difficult plugin path finding, and facilitate quick deployment of petition-specific plugins |
| Tool call timeout | 600 seconds | Adapt to time-consuming scenarios of pulling data across multiple petition systems, and prevent handling process interruption from timeout |
| Recall result limit | Top 10 entries | Control the amount of returned historical petition data, and avoid context overload affecting tool calling accuracy |

## Three Common Misconfigurations
- Tool module fails to load, and the interface displays "corresponding plugin not found". The cause is incorrect plugin deployment path configuration, not pointing to the storage directory of petition-specific business plugins.
- Tool call fails to trigger, returning "parameter mismatch" error. The cause is failure to correctly configure the tool set bound by `functionCall`, with non-petition business tools mixed in.
- Tool call result count exceeds expectations, returning more than 20 historical data entries. The cause is failure to set a reasonable recall result limit, leading to context overload affecting processing logic.

## How to Confirm Configuration Is Complete
- Log in to the FastGPT v4.17.0 backend, enter the plugin management page, and confirm that the petition-specific business plugin is displayed in the loaded list.
- Initiate a test call, enter "Screen whether this petition matter falls within the acceptance scope", and confirm that the tool automatically calls the corresponding business plugin.
- View the tool call log, and confirm that the number of returned historical petition data entries complies with the preset limit rules.
- Check the `toolChoice` configuration item, and confirm that the corresponding tool has been selected based on the current handling stage or set to automatic mode.
