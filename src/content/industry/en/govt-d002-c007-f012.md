# Handling Petitions: Inquiry and Response — Deployment and Upgrade

## What the Data for This Use Case Looks Like
The data for this use case primarily originates from the national petition information system, local petition systems, the 12345 citizen hotline, grassroots governance platforms, and historical petition archives. The update frequency is daily. Commonly involved documents include petition registration forms, acceptance notices, transfer and assignment letters, handling opinions, review and re-examination applications, and resolution plans. Data fields cover information about the requesting party, request content, handling milestones, review results, and more. The overall structure is built around the statutory handling process, with no additional custom statistical indicators.

## Constraints Imposed by These Characteristics on Deployment and Upgrade
The data sources for this use case are scattered and involve statutory handling documents. During deployment, adapters must be configured for multi-system data synchronization interfaces to ensure complete retrieval of daily incremental data. Daily documents are mostly standardized statutory documents. Strict access permissions and storage encryption rules must be configured to prevent sensitive information leaks. Since the data is structured around the statutory handling process, field mapping configurations corresponding to petition handling milestones must be reserved during deployment. This ensures imported data matches workflow handling stages. During upgrades, compatibility with historical archive format changes must be maintained to avoid interruptions to the handling process.

## Configuration Guidelines
This document is written for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `200–300 connections` | Adapts to concurrent connection requirements for daily multi-system synchronization, preventing database connection exhaustion |
| `REDIS_URL` | Intranet-accessible Redis instance address for local deployments | Caches temporary petition handling statuses and user sessions to ensure synchronization efficiency |
| `STORAGE_S3_ENDPOINT` | Configured as the intranet access address of the local object storage | Stores standardized petition documents and historical archives, ensuring data storage security and traceability |
| `FILE_TOKEN_KEY` | Randomly generated 32-character string | Signs uploaded petition files to prevent unauthorized file access and tampering |
| `FE_DOMAIN` | Public or intranet access domain name of the deployment server | Configures valid domains for callback addresses in workflows, preventing cross-domain request interception |

## Three Common Misconfigurations
- The configured model does not appear in the workflow editing interface. The symptom is that the model configuration page shows an enabled status, but the model dropdown list in workflow nodes is empty. The cause is that the `FE_DOMAIN` parameter was not correctly configured during deployment, causing the frontend to fail valid domain checks when retrieving the model list interface.
- A file size limit error occurs when uploading petition documents. The symptom is a 413 Request Entity Too Large status code is returned. The cause is that the upload limit parameter for container startup was not adjusted. The default limit is 2MB, which does not meet the size requirements for standardized petition documents.
- The platform cannot be accessed via the specified address after local deployment. The symptom is a browser prompt indicating invalid certificates or failed connection. The cause is that an SSL certificate and port forwarding rules were not configured. The default startup only supports HTTP access.

## How to Verify Successful Configuration
- Run the multi-system data synchronization script, confirm that petition data can be retrieved normally and stored in the specified database, with no error logs.
- Upload a standardized petition document, confirm that the file can be stored normally and called in workflow nodes, with no size limit errors.
- Enter the workflow editing interface, confirm that the configured model appears in the dropdown list, and can be selected and tested for normal invocation.
- Access the configured `FE_DOMAIN` address, confirm that the platform loads normally with no security prompts.

The values provided are common starting points and should be measured against the user’s own samples.
