# Public Data Catalog and Disclosure: Service Consultation and Response via HTTP Interfaces and External Systems
Reference only; verify against the target FastGPT release and deployment documentation.

## What data in this category looks like
Data in this category comes from local public data disclosure platforms, integrated big data platforms, departmental business databases, and electronic credential repositories. The update frequency is once per month. Daily supporting documents include public data resource catalogs, data disclosure lists, data item descriptions, anonymization rules, interface documents, and update frequency descriptions.
Data fields include data item unique identifiers, affiliated departments, disclosure scope, anonymization requirements, call frequency limits, update cycles, and more. Most units follow standard government data formats: for example, JSON structured fields, interface call counts are measured in times, and data storage units are MB.

## What constraints these characteristics impose on HTTP interfaces and external systems
The monthly update requirement for data in this category means HTTP interfaces must support version verification of public data catalogs to avoid calling outdated data items.
Multi-source heterogeneous data sources require interface authentication to adapt to government unified identity authentication, and the token format of the `Authorization` parameter must be configured in accordance with specifications.
Data anonymization rules require secondary verification of returned `responseData` before sending, to prevent leakage of non-anonymized sensitive information.
Differences in data item fields across departments require configuring field mapping rules via `variables` to unify external output formats.
Interfaces must also match input and output parameter requirements listed in data disclosure lists, to ensure call results meet disclosure conditions.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {government unified token}`, validity period no more than 7200 seconds | Adapts to government authentication specifications, matches interface call requirements in data disclosure lists |
| `variables` | Configure data item field mapping rules, covering 10-15 common government data fields | Unifies output formats for multi-source heterogeneous data, complies with field definitions in public data catalogs |
| `responseData` | Configure field whitelists per data disclosure lists, returned data size no more than 1000 MB per call | Avoids returning non-anonymized or out-of-scope data, matches capacity limits in interface documents |
| Interface timeout setting | 60-120 seconds | Adapts to average response duration of government data queries, prevents single call interruptions |
| Data cache configuration | Set cache duration to 2592000 seconds (30 days) | Matches the monthly update frequency of data in this category, reduces repeated calls |

## Three common errors
- Discrepancies between platform test chat responses and API call results, with missing or incorrect returned fields. This occurs when unified field mapping rules are not configured via `variables`. API calls directly use raw, non-anonymized departmental database data, while platform tests use anonymized data sets from public data catalogs.
- API calls return 403 status code, indicating no access permission. This happens when the `Authorization` parameter is not correctly configured, a valid token from government unified identity authentication is not used, or the token has expired.
- Interface calls time out, returning 504 status code. This occurs when a reasonable timeout duration is not set, or the data volume returned in `responseData` exceeds the configured capacity limit.

## How to confirm configurations are correct
- Call the test interface, compare returned fields with requirements in the public data disclosure list, and confirm field names and formats comply with disclosure rules.
- Check the validity of the `Authorization` parameter token, simulate an expired scenario to verify whether the authentication logic takes effect.
- Call data interfaces from different departments, confirm whether the field mapping rules configured via `variables` take effect correctly and the output format is unified.
- After simulating a monthly data update, verify whether the interface can pull the latest catalog version, confirming that the data synchronization logic works properly.
