# Medical Insurance Expense Settlement Audit Service Consultation and Response: HTTP Interfaces and External Systems

## What this category of data looks like
This service category serves medical insurance handling institutions, designated hospital medical insurance offices, designated pharmacies, and medical insurance information platform operators. Data sources include the national medical security information platform, hospital HIS and medical insurance interfaces, medical insurance catalog coding database, and cross-regional medical settlement platform. Updates occur daily. Daily processed documents include medical insurance settlement lists, expense details, medical record homepages, prescriptions, rejection lists, and settlement reconciliation statements. Fields cover diagnosis and treatment item/drug consumable codes, expense amounts, insured person information, settlement status, and more. Single-piece data volume shifts with settlement batches. In batch scenarios, a single batch can reach thousands of entries.

## What constraints do these characteristics impose on the HTTP interface and external system link
Data sources for this service category are scattered, and multiple external systems require connection. Interfaces must support multi-format data parsing to adapt to different docking parties. Daily updated batch data requires interfaces to support batch calls and pagination processing, to avoid overload from single requests. Medical insurance settlement documents require fields to strictly match official coding databases. Interfaces must transmit standardized coding fields to prevent matching errors during audits. Different scenarios of single or batch settlement require interfaces to dynamically adjust request parameters to fit different data scales. Interfaces must also retain complete request and response logs for reconciliation and problem troubleshooting.

## How to set configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `Authorization` | A valid token with a Bearer prefix, set with a validity period of 7–30 days | Adapts to identity verification requirements of external systems, avoids frequent token refreshes that harm interface stability |
| `variables` | Preset medical insurance coding mapping rules, set a single batch request threshold of 500 entries per request | Standardizes docking with medical insurance data from different sources, controls load for single batch requests |
| `responseData` | Only return audit status, rejection reason, and settlement receipt number fields | Simplifies response content, reduces external system data parsing costs, and meets field needs for reconciliation scenarios |
| Interface timeout period | 600 seconds | Adapts to time requirements for batch settlement audits, avoids timeout errors triggered by delays in audit links |

## Three common mistakes
- Phenomenon: Interfaces return settlement audit results that do not distinguish between different handling institutions or insured persons, leading to cross-subject data confusion. Cause: No identity identification parameter is included in requests, and user-level verification rules are not configured via `variables`.
- Phenomenon: Interfaces return timeout errors and 504 status codes when submitting batch settlement data. Cause: Single request data volume exceeds the preset threshold, and the daily batch update business scale is not adapted to.
- Phenomenon: Interface responses include undefined medical insurance coding fields, causing errors in external system audit processes. Cause: Return fields are not specified via the `responseData` configuration, and full raw interface data is returned directly.

## How to confirm the configuration is correct
- Initiate a test request for single-piece settlement data. Verify that a valid audit result returns after `Authorization` token verification passes, and a corresponding error code returns when verification fails.
- Submit batch settlement data. Confirm that interface response fields match the `responseData` configuration, with no redundant fields.
- Simulate requests from different identities. Verify that returned audit results only include settlement data for the corresponding subject, with no cross-subject data leakage.
- Adjust the batch request threshold. Confirm that no timeout error triggers for the interface when requests run at 500 entries per request.

The values given are common starting points and should be measured against the reader's own samples.
