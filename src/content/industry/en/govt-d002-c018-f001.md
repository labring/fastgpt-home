# Service Consultation and Response for Social Insurance Enrollment and Payment Verification: HTTP Interfaces and External Systems

## What this category of data looks like
Data comes from social insurance management systems, tax social insurance premium collection systems, market entity registration information, and shared public security and civil affairs data. The update frequency is daily. Daily associated documents include social insurance enrollment registration forms, payment base declaration forms, personnel change forms, social insurance premium verification notices, and personal benefit records. Core fields cover personnel identity identifiers, payment bases, change types, verification order numbers, and more. The data structure is built around the business nodes of social insurance enrollment and payment verification.

## What constraints do these characteristics impose on the HTTP interfaces and external systems link
Since data originates from multiple independent systems, HTTP interfaces must be compatible with the return field formats and permission verification rules of different systems. The daily data update frequency requires interface calls to avoid peak business hours, preventing system rate limiting triggers. Business nodes linked to core documents require corresponding business identifiers to be included in interface requests, ensuring accurate data matching. Because errors can impact personal benefits, interfaces must support idempotent design and detailed error status returns to facilitate subsequent reconciliation and troubleshooting.

## How to configure settings
This configuration applies to FastGPT v4.17.0. Specific configuration items are listed below:

| Configuration Item | Recommended Approach | Rationale |
|---|---|---|
| `Authorization` | Configure a Bearer Token or static key per external system requirements, for example `Bearer sk-xxxxxx` | External social insurance or tax systems typically use token-based authentication to secure interface call safety |
| `variables` | Enter 1 to 5 core business parameters, such as the ID number of an insured person or the unified social credit code of a unit | Limiting the number of variables reduces interface request redundancy and improves business matching accuracy |
| Request timeout | 10-30 seconds, calibrated based on actual testing | Social insurance system interfaces have measurable response delays. An overly long timeout will block the conversation flow, while an overly short timeout will trigger false failures |
| `responseData` | Only extract core fields such as verification order numbers, payment bases, and change statuses | Filtering non-essential fields reduces data transmission volume and speeds up conversation context processing |
| Retry count | 2 to 3 times | Address network jitter or temporary system fluctuations, avoiding business interruptions caused by a single failed request |

## Three common misconfigurations
- Phenomenon: The conversation output does not display business data returned by the HTTP interface, only showing AI natural language responses. Cause: The mapping rules for the `responseData` field were not configured correctly, and core business fields returned by the interface were not injected into the conversation context.
- Phenomenon: Interface calls fail frequently, returning 403 or 429 status codes. Cause: The correct authentication parameter `Authorization` was not configured, or interface call frequency was not restricted, triggering permission verification or rate limiting rules of the external system.
- Phenomenon: Interface returned data contains a large number of non-essential fields, causing delays in conversation processing. Cause: Redundant fields were not filtered via the `responseData` configuration, and full returned data was used directly for context splicing.

## How to confirm the configuration is complete
- Call the test interface to verify that returned fields match the extraction rules configured in `responseData`.
- Initiate a request containing real business parameters to confirm that authentication failure or rate limiting error reports are not triggered.
- Simulate a single network jitter scenario to confirm that the retry mechanism takes effect and the request completes successfully.
- View the conversation log to confirm that core business data returned by the interface is correctly displayed in the conversation output.
