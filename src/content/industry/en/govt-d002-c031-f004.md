# Construction Project Environmental Impact Assessment Approval Inquiry and Response: Workflow Orchestration

## Data Overview for This Category
This category of data covers four stakeholder groups: ecological environment department EIA offices, administrative approval bureaus, project construction units, and EIA institutions. Daily documents include environmental impact assessment reports, environmental impact assessment report forms, approval applications, public participation statements, technical assessment opinions, and EIA approval documents.
Data sources include the national unified construction project EIA declaration and approval system, ecological environment zoning control results, pollution discharge permission platforms, and monitoring data. Update frequency is irregular.
Data fields include project category, EIA level, pollution prevention measures, public participation content, approval document number, and other relevant fields. There is no fixed single-document length. Processing must adapt to the actual format of submitted documents.

## Constraints on Workflow Orchestration
This category has multiple data sources and no fixed update cycle. Workflows must support real-time verification and association of multi-source data.
Document structures vary significantly. Reports and report forms have different field complexity levels. Configure differentiated parsing nodes based on document type.
The most time-consuming link—verifying project category and EIA level—accounts for a large share of total processing time. Set pre-verification nodes to reduce invalid workflow steps.
Data errors can cause serious consequences such as project suspension or approval revocation. Configure failure rollback and audit nodes.
This category focuses on compliance judgment before construction project commissioning, with clear business boundaries from other categories. Workflows must limit input and output business scope.

## Configuration Settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Visibility configuration | Configure by role groups. Open full source access for core approval nodes, hide referenced content for public participation-related nodes | EIA data contains sensitive public participation information. Viewing scope must be differentiated by permission roles |
| Timeout setting | `600 seconds` | EIA document parsing and cross-system data query take a long time. Sufficient processing time must be reserved |
| `variables` binding | Bind core identification fields such as project number and approval document number | EIA data uses projects as the only association dimension. Integrate multi-source system data through variables |
| Node trigger rules | Connect pre-verification, document parsing, and compliance comparison nodes in `nodeId` order | EIA approval processes follow a fixed sequence. Trigger each link in business logic order |
| Context length | `800–1200 characters` | Core content of EIA inquiry focuses on project compliance judgment. Excessively long context will distract the model from key information |
| Single search limit | Top 5 entries | The number of official EIA-related data entries is limited. Too many redundant results will interfere with judgment |

## Three Common Misconfigurations
- Some nodes in the workflow still display full source content. This occurs when node-level visibility scope is not configured by role groups. Only the global visibility switch is modified, and no separate restrictions are applied to sensitive information nodes.
- No nodes appear on the interface after importing the workflow template. This happens when `nodeId` values in the template are duplicated, or conflict with system node IDs in the current FastGPT environment, causing nodes to fail to load properly.
- The text extraction node cannot select an adapted model. This occurs when a dedicated model for EIA document parsing is not configured in the system, or the `variables` bound to the node are not associated with model call permissions.

## How to Verify Successful Configuration
- Submit test project data. Check that each node triggers in `nodeId` order, with no skipped steps or blockages.
- View the project number field bound to `variables`. Confirm that it can automatically associate corresponding data from multi-source systems.
- Log in with different permission roles. Verify that node visibility configuration takes effect according to preset rules.
- Simulate a timeout scenario. Check that the workflow triggers the preset failure rollback and prompt mechanism.
