# Tendering and Procurement Compliance Management: Service Consultation and Response — HTTP APIs and External Systems

## What data for this category looks like
Data sources for this category include enterprise procurement platforms, public resource trading platforms, supplier databases, contract management systems, and audit issue databases, with a daily update frequency. Daily involved documents include procurement plans, requirement specifications, bidding documents, bid evaluation records, contracts, acceptance documents, and supplier complaint materials. Data fields include project number, budget amount, procurement method, bid evaluation clauses, supplier qualification requirements, performance acceptance information, and more. Field content is strongly bound to the entire procurement workflow nodes, with no additional custom units.

## What constraints these characteristics impose on the HTTP APIs and External Systems link
Data sources are scattered and updated daily. HTTP APIs must be used to connect multiple systems and synchronize the latest procurement, bid evaluation, and contract data. APIs must adapt to the authentication rules of different systems. There are diverse document types. APIs must support receiving and parsing multi-format data to avoid field loss caused by format incompatibility. Data is strongly bound to the entire procurement workflow nodes. API calls must match the node sequence to ensure data integrity during compliance verification. API exceptions may trigger compliance risks. Call stability and data accuracy must be ensured to avoid interrupting the verification process.

## How to configure

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Authentication Method | Use the `Authorization` header to carry a Bearer token | Adapts to the general authentication specifications of most external systems, ensuring interface access security |
| Request Timeout | 600 seconds | Adapts to the time consumption requirements of multi-system data synchronization, avoiding data pull interruptions due to timeouts |
| Batch Push Data Limit | 200 groups/batch | Matches the official batch limit requirements of the `pushData` interface, avoiding triggering current-limiting errors |
| Context Variable Configuration | Bind procurement project-specific `variables` | Ensures that correct project context is passed during API calls, improving compliance verification accuracy |
| Response Data Processing | Extract the `responseData` field as core verification data | Standardizes the parsing process of interface return values, simplifying subsequent compliance verification logic |
| Structured Response Switch | Enable json_object format support | Meets the structured output requirements of compliance verification results, adapting to the viewing habits of audit and discipline inspection departments |

## Three common mistakes
- Phenomenon: Calling the collection creation interface returns a 404 status code, or prompts that the interface does not exist. Cause: Accidentally wrote the interface path as a non-official specified variant, and did not use the standard interface path.
- Phenomenon: Only some entries are successfully imported during batch data push, or current-limiting errors are triggered by the interface. Cause: Did not follow the 200 groups/batch limit of the `pushData` interface, and pushed more than the limit in a single request.
- Phenomenon: The interface returns structured data after being called, but the json_object format option does not appear in the interface. Cause: Did not enable the structured response switch in the interface configuration, or did not correctly pass the format requirement parameters.

## How to confirm the configuration is complete
- Call the authentication interface to verify the validity of the `Authorization` header, confirming that interface access permissions can be obtained normally.
- Initiate a single batch data push test of 200 groups, checking that the number of successful returns from the interface matches the number of pushed entries.
- View the `responseData` field in the interface return value, confirming that core procurement data has been correctly extracted.
- Trigger the compliance verification process, checking whether the structured response format configuration option appears in the interface.
