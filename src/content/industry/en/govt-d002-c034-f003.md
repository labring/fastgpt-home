# Enrollment and Student Status Management Inquiry and Response: Multi-turn Dialogue and Prompt Engineering

## Data Profile for This Category
Data for this category originates from the national primary and secondary school student status management system, local enrollment platforms, household registration and real estate data platforms, and school academic affairs systems. The update frequency is daily. Daily processed documents include enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, and student status change approval forms. Data fields focus on student identity, enrollment eligibility, and student status. The structure is fixed and tightly bound to individual students.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
Dispersed data sources and daily updates require multi-turn dialogue to bind a unique session identifier to distinguish context for different students, preventing cross-session data confusion. Fixed document structure tightly bound to individual students requires prompts to guide users to provide complete identity verification information, while limiting the model to only call knowledge base data associated with the current session. The most time-consuming verification process requires multi-turn dialogue to retain sufficient historical interactions to track user-submitted materials. Severe error consequences require the model to strictly respond based on knowledge base content, and must not generate unverified information.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Maximum Context Window | 8000–12000 characters | Covers typical length of student status and enrollment-related documents, avoids truncating critical verification information |
| Retained Context History Turns | Last 6 turns | Matches typical interaction turns for student identity verification and material submission, ensures dialogue coherence |
| Single Recall Result Count | Top 5 results | Focuses on most relevant enrollment and student status data, avoids redundant information interfering with model judgment |
| Session Identifier Binding | `chatId` | Distinguishes session context for different students, prevents cross-session data confusion |
| Variable Auto-fill | `variables` | Automatically imports individual information such as student status number and application number, reduces repeated user input |
| Session Timeout Duration | 600 seconds | Matches average processing duration for household registration and real estate verification, avoids premature clearing of context cache |
| Prompt Constraint Rule | Only respond using enrollment and student status data within the knowledge base | Meets strong compliance requirements for data in this category, avoids generating unverified content |

## Three Common Configuration Mistakes
- Inconsistent enrollment policy content returned across different sessions or different turns within the same session. The symptom is conflicting admission rules in model outputs. The cause is failure to bind `chatId` to distinguish session context, resulting in calls to knowledge base fragments that do not match the current student.
- The model returns policy interpretations or fabricated information outside the knowledge base. The symptom is unincluded content appearing even after prompt configuration. The cause is failure to explicitly limit the prompt to only use knowledge base data for this category, or failure to enable the content verification switch.
- Empty prompt fields appear after household registration and real estate verification dialogue timeouts. The symptom is inability to restore historical interaction information after session interruption. The cause is failure to set a reasonable session timeout duration, resulting in clearing of the context cache.

## How to Verify Correct Configuration
- In FastGPT v4.17.0, confirm that a multi-turn dialogue containing a student status number retains historical student identity information in the `messages` field.
- When an unincluded non-enrollment and student status-related question is submitted, confirm whether the model prompts that relevant answers cannot be provided.
- Review session logs, and confirm that each session is bound to a unique `chatId` identifier, with no cross-session data confusion.
- Trigger the daily synchronization task, and confirm that the knowledge base updates the latest enrollment plan data, ensuring the model calls the most up-to-date daily information.
- Test the variable auto-fill function, and confirm that student information imported in `variables` is correctly displayed in the dialogue.
