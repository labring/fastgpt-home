# Service Consultation and Response for Enrollment and Student Status Management: Model Access and Configuration

## What data falls under this category
Data for this category centers on student enrollment and student status transfers. Daily documents include enrollment application forms, student status information sheets, transfer applications, enrollment plans, admission rosters, and student status change approval forms. Data sources include the National Primary and Secondary School Student Status Management System, local enrollment platforms, household registration and property data, and school academic affairs systems. Data is updated daily. Core data fields focus on student identity identifiers, enrollment eligibility criteria, student status change statuses, admission results, and other key information. No financial fields are included. Core data links to external public data such as household registration and property information.

## What constraints these characteristics impose on model access and configuration
Data sources involve cross-department synchronization across multiple systems. Daily updates require model access and configuration to adapt to high-frequency data refreshes, so knowledge bases can sync the latest enrollment plans and student status change information. Core fields focus on identity and eligibility verification. Models must accurately match external data such as household registration and property information, to avoid eligibility determination errors caused by fuzzy matching. Document structures include structured form data and unstructured policy text. Different formatted input content must be processed separately. Data association accuracy must be maintained, to prevent duplicate or missing student status errors. In service consultation scenarios, user questions often involve policy interpretation and progress inquiries. Models must bind corresponding enrollment plan and student status data.

## How to set configurations
This guide applies to FastGPT v4.17.0, using the standard access process for this version:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to long-text contexts such as enrollment policies and student status files, to avoid truncation of critical enrollment eligibility information |
| `maxTokens` | 2000–3000 token | Meets the requirements for complete policy interpretation and process explanations in service consultation responses, to avoid incomplete output |
| `quoteMaxToken` | 1500 token | Limits the length of quoted student status documents and enrollment plan excerpts, to ensure quoted content is precise and not redundant |
| `toolChoice` | auto | Automatically selects whether to call tools to verify household registration and student status data, to adapt to multi-scenario consultations |
| `temperature` | 0.3–0.5 | Reduces randomness, ensures consistency in policy interpretation and eligibility determination, and meets the rigor requirements of service scenarios |
| `AIPROXY_API_ENDPOINT` | Fill in local or third-party proxy addresses based on the deployment environment | Adapts to multi-data-source access requirements, to ensure stable cross-system data calls |
| `AIPROXY_API_TOKEN` | Authentication key matching the proxy service | Ensures the security of data calls, to prevent unauthorized access to sensitive student status data |

## Three common configuration errors
- A 404 error is returned when calling voice input-related models. The cause is that `AIPROXY_API_ENDPOINT` is not correctly configured to point to a locally deployed Whisper service, or the proxy service has not opened the corresponding port.
- A 404 error is returned when accessing baidu-embedding-v1 or an ollama-deployed bge-large-zh-v1.5 model. The cause is that the model access address and authentication key are not correctly bound to FastGPT's proxy configuration, resulting in failed request forwarding.
- Duplicate or missing student status information appears in model outputs. The cause is that the `maxContext` parameter is not set to a reasonable value, resulting in loss of partial student status-related data after context truncation, or failure to correctly sync the latest data from the National Primary and Secondary School Student Status Management System.

## How to confirm successful configuration
- Submit test requests involving student status verification and policy consultation, and check whether the model output links to corresponding enrollment plan and student status data.
- Review proxy service logs, and confirm that requests sent to `AIPROXY_API_ENDPOINT` are correctly forwarded, with no 404 or timeout errors.
- Test consultation questions of different lengths, and check that the model output does not show truncation or incompleteness.
- Simulate high-frequency data update scenarios, and confirm that the knowledge base can sync the latest student status change and enrollment plan information.

The values provided here are common starting points, and should be evaluated against the user's own samples.
