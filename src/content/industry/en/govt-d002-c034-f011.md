# Enrollment and Student Status Management Service Inquiry and Response: Forms and Interactions

## What data for this category looks like
Data for this category originates from the National Primary and Secondary School Student Status Management System, local enrollment platforms, household registration and property data, and school academic affairs systems. Updates occur daily. Daily documents include enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, and student status change approval forms. All are structured form documents. Fields center on student identity identifiers, household registration and property association information, and student status transfer qualifications. Most field types are text, date, and selection options.

## What constraints these characteristics impose on the forms and interactions link
Multi-source data access requires form interactions to support cross-system verification, preventing data inconsistencies. Daily updates require real-time verification links to match the same day’s latest household registration and student status data, avoiding outdated returned information. The structure of multiple business document types requires forms to display in modules based on scenarios such as enrollment and student status changes, making it easier for users to fill out or submit inquiries. Fields focused on identity and qualifications require forms to strictly verify uniqueness, stopping duplicate or missing student status entries. Forms must also associate corresponding policy documents to provide accurate reference for user inquiries.

## Three common mistakes
- Phenomenon: A "Request Timed Out" pop-up appears when calling the form verification interface, with a status code of 408. Cause: The form input verification timeout setting is too short, and does not match the actual time required for multi-source data verification.
- Phenomenon: Recalled inquiry matching results only show a single student status information entry, and multiple associated contents cannot be selected for large model processing. Cause: The multi-selection parameter of `userSelect` is not configured correctly, and only single-selection mode is enabled.
- Phenomenon: The number of optional models in the tool call link is far fewer than the platform's built-in model list. Cause: The call permissions of dedicated models for the education scenario are not enabled in the configuration, and only a small number of general-purpose models are bound.

## How to confirm the configuration is complete
- Submit test enrollment application form data, verify whether the household registration and property association fields can normally call the corresponding data source to return results.
- Select the "Student Status Change" scenario to initiate an inquiry, confirm that the fields bound by `formInput` can correctly match the relevant content of the student status change approval form.
- Initiate a multi-field combined inquiry, check whether the number of recall results meets the configured recall limit requirements.
- Simulate submitting an application with the same student ID number repeatedly, confirm that the form will pop up a duplicate verification prompt.

The values provided are common starting points and should be measured against the operator's own samples.
