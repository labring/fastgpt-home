# Enrollment and Student Status Management Service Inquiry and Response: Deployment and Upgrade

## What this category of data looks like
This category of data is primarily sourced from the National Primary and Secondary School Student Status Management System, local enrollment platforms, household registration and property data, and school academic affairs systems. Daily processed documents include enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, and student status change approval forms. Data is updated on a daily basis. Data fields include student identity identifiers, household registration and property information, student status numbers, enrollment qualification verification conditions, change approval status, and other related items. All data revolves around the core of student enrollment and student status transfer.

## Constraints Imposed During Deployment and Upgrade
The data sources for this category are scattered and have high update frequencies. During deployment, APIs of multiple heterogeneous data sources must be connected. Connection parameters for each data source must be configured in advance to avoid connection timeouts or data format mismatches. Daily document types are diverse, so parsing rules for multiple document categories must be configured. This ensures that files of different formats such as enrollment application forms and student status change approval forms can be correctly read and indexed. Data is linked to student admission qualifications. Errors may lead to serious disputes. An additional data verification and exception monitoring link must be configured during deployment to ensure data consistency. The service must serve public education service scenarios and comply with official domain name and data security specifications. Front-end domain name and encryption configurations must be adjusted during deployment.

## Configuration Settings
This configuration guide applies to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://edu_admin:secure_pass@10.0.0.5:27017/edu_data?authSource=admin` | Stores semi-structured document data such as student status information and admission rosters |
| `PG_URL` | `postgresql://edu_user:db_pass@10.0.0.6:5432/edu_fastgpt?sslmode=require` | Stores user inquiry conversation and student status change approval process data |
| `REDIS_URL` | `redis://:redis_pass@10.0.0.7:6379/1` | Caches frequently queried enrollment policy and student status data to reduce data source access pressure |
| `FE_DOMAIN` | `https://edu.xxx.gov.cn` | Configures official education service domain names to comply with access specifications for public service scenarios |
| `FILE_TOKEN_KEY` | `32-bit random hexadecimal string` | Encrypts access tokens for uploaded student status and enrollment documents to ensure sensitive data security |
| `STORAGE_S3_ENDPOINT` | `https://s3-cn-south-1.amazonaws.com` | Stores large-volume document resources such as enrollment plans and admission rosters |

## Three Common Misconfigurations
- Phenomenon: Uncaught exception logs appear after deployment, and the backend reports an invalid configuration parameter error. Cause: Incorrect configuration file entries in a private deployment scenario, with the data source address format for student status data connection not correctly matched.
- Phenomenon: After upgrading the version, the knowledge base can query enrollment and student status related documents, but no response content is output after calling the large model. Cause: The data source configuration was not resynchronized after the upgrade, or the `REDIS_URL` parameter was modified incorrectly, causing cached query results to be unavailable for model calls.
- Phenomenon: The 3000 port page cannot be opened after Docker deployment, while the 3001 port works normally. Cause: Incorrect port mapping configuration, with the 3000 port of the FastGPT front-end service not mapped to the corresponding port on the host machine.

## How to Verify Successful Configuration
- Access the front-end address corresponding to the configured `FE_DOMAIN` and check whether the enrollment policy Q&A module on the service inquiry page loads normally.
- Run the built-in data source connection test script to verify whether the `MONGODB_URI`, `PG_URL`, and `REDIS_URL` parameters can connect to the corresponding services normally.
- Upload a simulated enrollment application form document and check whether the parsed fields match the preset student status data fields.
- Check the backend monitoring logs to confirm that there are no uncaught configuration-related exception errors.

The values provided are common starting points and should be evaluated against the user's own samples.
