# Government Service Item Catalog and Service Guide Maintenance: Inquiry and Response via HTTP Interfaces and External Systems

## What This Category of Data Looks Like
This category of data is primarily sourced from the national basic catalog of government service items, administrative licensing item list, power and responsibility list, and local government service item databases. Daily maintained documents include the basic catalog of government service items, implementation lists, service guides, standard material directories, flowcharts, and frequently asked questions. The data update cycle is usually monthly. Core fields include item code, implementing entity, acceptance conditions, application materials, handling process, etc. Some fields need to match the exclusive requirements of local government services. There is no unified fixed unit, and adjustments should be made based on the specific item type.

## Constraints on HTTP Interfaces and External Systems
The monthly update frequency requires HTTP interfaces to support periodic full or incremental data synchronization, and avoid timeouts caused by excessive data volume in a single request. Multi-source government data requires the interface to complete field mapping and consistency verification to ensure unified data caliber for item data from different channels. The rich document types and field requirements mean the interface needs to support multi-format data pulling and verification, and also return clear error identifiers to facilitate troubleshooting of missing fields or non-compliant formats. In addition, this category does not handle individual application cases, so the interface does not need to bind user identities, and only needs to complete data interaction based on identifiers such as item codes.

| --- | --- | --- |
| `Authorization` | `Bearer {API_KEY}` | Complies with HTTP interface standard identity authentication formats, and is compatible with most government service open interfaces |
| Single request data volume limit | `800–1200 items` | Adapts to the conventional traffic limits of government service interfaces, balancing synchronization efficiency and stability |
| Request timeout threshold | 600 seconds | Adapts to the conventional response delays of government data interfaces, avoiding synchronization process interruptions due to timeouts |
| `variables` | `{"updateCycle": "monthly", "dataSource": ["national", "local"]}` | Matches the monthly update and multi-source data characteristics of this category, facilitating interface adaptation to different data sources |
| `responseData` | Structured fields including item code, acceptance conditions, and application materials, with single field length not exceeding 2000 characters | Focuses on the core maintenance fields of this category, facilitating subsequent verification and synchronization processing |

## Three Common Misconfigurations
- Symptom: The configured HTTP interface returns a `401 Unauthorized` error, and the API_KEY and interface address have been confirmed to be correct. Cause: The `Bearer ` prefix was not added before the API_KEY, causing the authentication parameter format to not meet requirements.
- Symptom: When synchronizing service guide related documents, only docx format files can be recognized, and other types of files cannot be read. Cause: The corresponding format document parsing plugin was not enabled, or the interface did not open reading permissions for non-docx formats.
- Symptom: When initiating a test request while connecting to a locally deployed model, an empty result or error is returned. Cause: The intranet interface address of the local model was not configured as an accessible legal address, or the exclusive configuration parameters of the local model were not supplemented in `variables`.

## How to Verify a Successful Configuration
- Invoke the configured HTTP interface and check whether the returned `responseData` includes core fields such as item code and acceptance conditions, and whether the field formats meet expectations.
- Initiate a simulated incremental synchronization request, and confirm that the updated data volume returned by the interface matches the actual scale of monthly updates.
- Construct a request with missing required fields, and check whether the error information returned by the interface clearly points to the problematic field.
- Simulate a high-latency request scenario, and confirm that the request is not interrupted in advance, and meets the configured timeout threshold requirements.

The values provided are common starting points and should be measured against the reader's own samples.
