# Government Information Disclosure by Application: Service Consultation and Reply — Multi-turn Dialogue and Prompting

## What This Category of Data Looks Like
The core data for this category comes from government information disclosure platforms, official agency archive systems, document management systems, departmental business ledgers, and relevant specifications for government information disclosure. Daily processed documents include standard forms such as government information disclosure application forms, supplementary notice letters, third-party opinion solicitation letters, reply letters, service receipts, and administrative reconsideration response materials. Data update frequency is irregular, changing with individual application cases and archive filing schedules. Core data fields center on applicant subject, application matters, processing milestones, and reply content. There is no unified batch field format; all content revolves around individual requests from a single applicant.

## Constraints Imposed by These Characteristics on the "Multi-turn Dialogue and Prompting" Link
The documents in this category are standardized individual case materials, and data sources are scattered. Multi-turn dialogue must accurately bind the context of a single application to avoid cross-session confusion. Data updates are irregular, so the knowledge base's on-demand synchronization logic must be adapted to prevent expired data from interfering with retrieval. Core processing steps rely on associated information for specific applications, so prompts must accurately extract individual case-specific fields and cannot use generalized processing. Errors directly relate to administrative remedies, so the accuracy of information in multi-turn dialogue must strictly match official document content, and no information deviations are allowed.

## Three Common Misconfigurations
- Phenomenon: Multi-turn dialogue provides irrelevant answers starting from the second question. Cause: `chatId` is not correctly bound, so session context is not retained, or the context window upper limit is set too low to carry historical `messages` content.
- Phenomenon: Key information is truncated in uploaded standardized documents. Cause: Chunk length settings do not match the paragraph structure of documents in this category, causing core processing milestone information to be split and lost.
- Phenomenon: Conversation logs cannot be automatically cleaned according to the administrative processing cycle. Cause: No retention duration rules matching the application cycle of this category are configured, or the session's application status logic is not associated.

## How to Verify Proper Configuration
- Initiate a simulated government information disclosure application conversation, ask 3 consecutive related questions, and verify that the model can answer by associating historical application information.
- Upload a standardized document of this category, check that no key paragraphs are truncated after chunking.
- View the `messages` field records of the session, confirm that historical messages of the same session are fully retained and the `chatId` is consistent.
- After configuring prompt variables, initiate a test, verify that the model can correctly extract and use bound specific information such as the application number.
