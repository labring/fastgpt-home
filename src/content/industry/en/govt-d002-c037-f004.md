# Government Information Application-Based Disclosure: Service Consultation and Reply - Workflow Orchestration

## What This Category of Data Looks Like
Data for this category mainly comes from government information disclosure platforms, agency archive systems, document management systems, departmental business ledgers, and relevant specifications of the Regulation on Government Information Disclosure. Daily processed documents include standard format files such as government information disclosure application forms, correction notices, third-party opinion solicitation letters, reply letters, service receipts, and administrative reconsideration response materials. Data updates have no fixed cycle, changing with individual case applications, archiving progress, and policy adjustments. Data fields include applicant information, application content, information scope, public attribute judgment basis, reply content, relief path explanation, and more. Each document must meet legal format requirements.

## What Constraints Do These Characteristics Impose on the "Workflow Orchestration" Link?
Dispersed data sources and non-fixed update cycles require workflows to support connecting to multiple types of system data sources and triggering retrieval on demand, avoiding reliance on fixed-cycle batch data synchronization logic. Format requirements for standard documents require configuring fixed field validation rules in the workflow to ensure files generated in each link meet legal formats. The individual case handling characteristic requires workflows to support independent circulation per single application instance, adapting to personalized requests from different applicants. Significant time differences across links require setting node timeout reminders and circulation permission controls during orchestration to prevent compliance risks such as delayed replies.

## How to Set the Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Bind application ID, applicant information, and application content fields, extract from form submission data | Used to pass exclusive context for the current individual case, ensuring each workflow node can obtain core information of the corresponding application |
| Node timeout duration | 600–1200 seconds | Covers the conventional processing time for archive retrieval, public attribute verification, and reply document drafting |
| `nodeId` | Configure the knowledge base node ID of the archive system, the retrieval node ID of the government disclosure platform, switch as needed | Used to specify specific function nodes, adapting to retrieval and call requirements for multiple data sources |
| Field validation rules | Match legal document formats, set required fields for application forms and reply documents to be mandatory | Ensure generated handling documents meet format requirements and avoid compliance risks |
| Context window upper limit | Within 8000 characters, retain the first 10 retrieval results | Control context length, focus on the information scope of the current application, avoid redundant content interfering with replies |
| Timeout alert trigger | Trigger system alert when a node runs for more than 900 seconds | Prevent processing delays, complying with compliance control requirements for government services |

## Three Common Mistakes
- Phenomenon: After the workflow calls an HTTP node to obtain BLOB-format attachments, there is no download entry in the front-end dialog box, and the returned result is displayed as binary text. Cause: No file conversion node was added to convert BLOB data into accessible file links, and no `variables` were used to pass the file's MIME type and file name parameters.
- Phenomenon: The workflow cannot enable advanced orchestration functions, and cannot configure multi-node connected individual case circulation processes. Cause: Did not switch to advanced workflow mode, and the current FastGPT v4.17.0 version does not open corresponding permissions for advanced orchestration.
- Phenomenon: After calling the MCP tool to generate a reply document in the workflow, subsequent nodes cannot obtain the structured content returned by the tool, and the fields are empty. Cause: Did not specify the output binding of the MCP tool node through `nodeId`, and did not configure `variables` to receive the reply content returned by the tool.

## How to Confirm the Configuration Is Complete
- Trigger a single test application, check whether `variables` correctly pass core fields such as application ID and applicant information.
- Run the workflow test node, confirm that the timeout duration of each node meets the preset control interval, and there are no abnormal timeout alerts.
- Call the HTTP node to obtain the BLOB attachment, check whether a clickable download entry appears in the front end, and the file format matches expectations.
- Run the knowledge base retrieval node, confirm that the returned results only contain content related to the current application, with no irrelevant information.

The values provided are common starting points and should be measured against the reader's own samples.
