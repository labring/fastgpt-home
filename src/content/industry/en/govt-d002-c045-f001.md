# Land Pre-examination and Planning Permit Consultation and Response: HTTP Interfaces and External Systems

## What This Category of Data Entails
This category of data is primarily sourced from the national land and spatial planning one-map system, project approval and supervision platform, land use status database, and ecological protection redline data. Update frequency is irregular. Associated daily documents include Land Pre-examination and Site Selection Opinion, Construction Land Planning Permit, Construction Engineering Planning Permit, redline drawings, and planning conditions. Data fields include project subject information, site selection range coordinates, land use scale, planning control requirements, pre-approval associated information, and more. There is no unified fixed character length per document; it varies based on the actual project scale.

## Constraints Imposed on HTTP Interfaces and External Systems
Data sources for this category are scattered, and updates follow no fixed cycle. HTTP interfaces must support on-demand triggering of multi-source data pulling to avoid unnecessary synchronization. Associated daily document types are diverse, so interfaces must support file uploads in multiple formats and structured parsing. Data includes professional fields such as site selection coordinates and land use scale. Interface parameters must support transmission of high-precision numerical values and structured data. Business processes are linked to pre-approval links including development and reform, and housing and urban-rural development. Interfaces must support cross-system permission verification and data linkage to ensure information consistency during calls.

## Configuration Guidelines
The following configurations are formulated based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| Authorization | `Bearer {platform-assigned API key}` | Complies with industry-standard API authentication specifications to ensure interface call security |
| variables | `{"projectId": "specified project unique identifier", "planningType": "planning permit type"}` | Adapts to core business parameters for this category of projects, clarifies the business context of interface calls |
| responseData | `Return only compliance verification results and associated document IDs` | Reduces unnecessary data transmission and improves interface response speed |
| Single request timeout | `600 seconds` | This category of business involves multi-source data verification, which takes a long time, so sufficient response time must be reserved |
| File upload size limit | `1000 MB` | Documents such as redline drawings and planning conditions in this category contain high-definition vector data, so large file uploads must be supported |
| Maximum request text length | `800–1200 characters` | Adapts to the conventional text length of application consultations in this category to avoid parameter overflow |

## Three Common Misconfigurations
- Phenomenon: A cross-domain related error is returned when calling the interface using the fetch API, with the status code containing the CORS keyword. Cause: The allowed cross-domain request sources for the interface are not configured, or the authentication-related request headers are not set correctly.
- Phenomenon: The interface returns a 400 error when the uploaded file name is too long. Cause: The interface does not perform adaptive verification on the file name length, resulting in parameter parsing failure.
- Phenomenon: After uploading an image via markdown, a directly accessible static resource URL cannot be obtained. Cause: The storage path mapping after image upload is not configured, and the resource path is not correctly returned to the `responseData` field.

## How to Verify Successful Configuration
- Call the interface and pass test project parameters, check whether the `responseData` field returns expected business data.
- After configuring the cross-domain whitelist, use the front-end fetch API to send a request and confirm that there are no cross-domain errors.
- Upload test files of different lengths to verify whether the interface can process them normally and return results.
- Check whether the `Authorization` authentication header is correctly configured, and confirm that an expected authentication failure prompt is returned when calling an interface without permissions.
