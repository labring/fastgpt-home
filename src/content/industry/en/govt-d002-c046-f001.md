# Public Social Assistance and Minimum Living Security Review Service Consultation and Response: HTTP Interfaces and External Systems

## What this category of data looks like
Business data for public social assistance and minimum living security review originates from the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-departmental shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, tax and other relevant departments. The update frequency is once per month. Daily business documents include minimum living security application forms, family economic status verification reports, household investigation forms, democratic appraisal records, public notice materials, and assistance approval forms. Core fields cover family income, total property, member relationships and other related items. Most field units are yuan, people, square meters and other standard units. The data structure is centered around family economic status and assistance eligibility.

## What constraints do these characteristics impose on the "HTTP Interfaces and External Systems" link
Cross-departmental data sources require interfaces to adapt to multi-system identity verification and data formats, to avoid inability to pull core data due to permission issues. The monthly update frequency means interface synchronization frequency should not be too high, and must match the business review rhythm to avoid repeated calls that occupy shared resources. Core business fields focus on family economic status, so interface returned data must accurately filter non-essential content, otherwise transmission and processing costs will increase. Errors are directly linked to the risk of incorrect or missed assistance coverage, so interface calls must include verification and retry mechanisms to ensure data accuracy and call stability.

## How to set configurations
The following configurations are written based on the FastGPT v4.17.0 version specification.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| API request timeout | 600 seconds | Cross-departmental data pulling requires waiting for responses from multiple systems, to avoid early request termination |
| `Authorization` | Fixed secret rotation cycle of 30 days | Matches the monthly update rhythm of business data, reduces the risk of secret leakage |
| `responseData` | Only retain family income and member relationship fields | Filter non-core fields such as public notice materials and household investigation records to adapt to core business needs |
| Request retry count | 3 times | Balances cross-departmental interface fluctuations and business waiting costs, avoids excessive occupation of system resources |
| `variables` | Include core fields of verification reports and application forms | Provide accurate business data support for service consultation and response |
| Maximum number of returned entries | Top 10 entries | Avoids redundant data affecting consultation response speed, meets conventional business query requirements |

## Three Common Misconfigurations
- Failure to configure the `Authorization` parameter causes interface requests to be rejected, returning a 401 status code. This occurs because identity verification rules for civil affairs cross-departmental systems are not followed, and authorization requirements are not met.
- Failure to filter the `responseData` return fields causes the interface to return an overly large data volume, triggering a timeout error. This happens because non-core irrelevant fields such as public notice materials and household investigation records are pulled, exceeding the interface transmission limit.
- Setting an excessively high retry count causes cross-departmental interfaces to be rate-limited, returning a 429 status code. This occurs because call frequency limits of civil affairs shared data interfaces are not considered, and retry counts are increased blindly.

## How to Confirm Configurations Are Correct
- Call the test interface, check that the returned status code is 200, to confirm the `Authorization` parameter is configured correctly.
- View the `responseData` returned fields, confirm that only core business data is included, with no redundant fields.
- Simulate cross-departmental data pulling, verify that the interface response time meets the preset timeout setting.
- Call the interface multiple times, confirm that the retry logic triggers when the interface encounters an exception, and does not exceed the preset retry count.
