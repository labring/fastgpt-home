# Service Consultation and Response for Social Assistance and Minimum Living Security Review: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
The data related to service consultation for social assistance and minimum living security review mainly comes from the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-department shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, and tax authorities. Daily business documents include minimum living security application forms, family economic status verification reports, household survey records, democratic appraisal records, public notice materials, and assistance approval forms. Data update frequency is monthly. Core fields cover family income, property status, member relationships, and assistance qualification determination information. Common units include yuan, person-times, household-times, and similar units.

## Constraints on multi-turn dialogue and prompt engineering workflows
The cross-departmental monthly updated data source requires multi-turn dialogue to regularly synchronize the latest verification data. Prompts must clearly limit usage to valid data from the current cycle to avoid expired family economic status information. Structural differences across multiple business documents require multi-turn dialogue to call corresponding documents by conversation turn. For example, household survey records are called during the verification stage, and public notice materials are called during the notification stage. Core fields involve family privacy and accurate qualification determination, so prompts must include strict information desensitization rules. The context window of multi-turn dialogue must be limited to only retain data related to the current application family to avoid cross-household information confusion.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique identifier of the current assistance application | Ensure multi-turn dialogue context is tied to a specific application to avoid cross-application confusion |
| `messages` | Store user consultations and system responses by turn, retain the most recent 10 conversation turns | Adapt to the multi-turn inquiry scenario of assistance review, avoid context overload |
| `variables` | Pass in the verification ID and monthly update timestamp of the current application family | Dynamically call cross-department data and business documents for the corresponding cycle |
| Maximum context length | 8000–12000 characters | Accommodate the core content of multi-turn consultations and multiple business documents, avoid truncating critical information |
| Single search limit | Top 3 matching results | Focus on the most relevant family economic status verification data and application process documents, reduce information redundancy |
| Question optimization | Calibrate based on actual testing | Adapt to colloquial questions from civil affairs service consultations, convert residents' vague inquiries into standardized review queries |

## Three Common Configuration Mistakes
- Issue: The interface returns an `Unexpected end of JSON input` error, and the conversation response content contains a large number of line breaks. Cause: Line breaks in returned text are not escaped, causing the generated JSON request body to break format.
- Issue: An error is triggered when uploading business files such as minimum living security application forms and family economic status verification reports, but text input dialogue runs normally. Cause: The legal format whitelist for civil affairs business documents is not configured, or the file size exceeds the system's allowed upload limit.
- Issue: Response time becomes significantly longer during multi-turn consultations, with single dialogue waiting time exceeding 8 seconds. Cause: The number of matching results for single search is not limited, or the context caching mechanism is not enabled.

## How to Verify Successful Configuration
- Use the FastGPT v4.17.0 system, test binding `chatId` as the unique identifier of a single assistance application, execute multi-turn dialogue, then check if the context only contains content related to that application.
- Upload preset civil affairs business documents, confirm that the files can be parsed normally without errors, and verify that the format whitelist configuration takes effect.
- Initiate a test question containing line breaks, check if the returned JSON request body has escaped line breaks.
- Initiate multiple consecutive consultations, confirm that the response time meets business expectations, and verify that the context caching and search limit configurations take effect.
