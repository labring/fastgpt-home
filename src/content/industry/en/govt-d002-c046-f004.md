# Service Consultation and Response for Social Assistance and Minimum Living Security Review: Workflow Orchestration

## What the data for this category looks like
This category's data originates from the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-departmental shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, tax and other departments. The update frequency is monthly. Daily associated documents include minimum living security application forms, family economic status verification reports, household survey forms, democratic appraisal records, publicity materials, and assistance approval forms. Data fields focus on family income and property, member relationships, and assistance eligibility, and need to adapt to multi-source heterogeneous cross-departmental data structures.

## What constraints these characteristics impose on the "workflow orchestration" link
Obtaining cross-departmental multi-source data requires configuring multiple data source call nodes in the workflow to adapt to the return formats of different systems. The monthly update rhythm requires the workflow to support a monthly review sub-process triggered on a scheduled basis. The requirement for full-process traceability across multiple types of associated documents requires configuring context transfer and archiving nodes. For time-consuming links such as family income and property verification and household surveys, serial or parallel nodes need to be reasonably arranged to avoid process blocking. The risk of incorrect or missed security reviews requires configuring verification nodes in the workflow to perform legality checks on key fields such as family income and member relationships.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Configure field mapping rules for family income and member relationships | The data for this category is multi-source and heterogeneous, so variables are needed to unify field transfer and verification logic across nodes |
| Timeout Settings | 600 seconds | Cross-departmental data calls require sufficient response time to avoid process interruptions |
| Context Length | 1000–1400 characters | This category has many associated documents, so full process context of applications, verifications, and publicity must be retained |
| `nodeId` | Bind exclusive node IDs for household surveys, verifications, and publicity | Precise control over the execution order and status return of each business link is required |
| Retry Count | 2–3 times | Number of retries when cross-departmental data calls fail, adapting to the unstable nature of cross-system calls |

## Three common errors
- Symptom: Cross-departmental data call nodes in the workflow run normally in debug mode, but return empty results in production operation mode. Cause: Data source permission binding for the production environment is not configured, and the local permissions used in debug mode do not take effect in the production environment.
- Symptom: It is not possible to configure a node for circularly organizing household survey records in the workflow. Cause: The circular node configuration switch for the workflow is not enabled, and the loop termination condition is not defined via `variables`.
- Symptom: Only the last 6 entries are returned when exporting workflow conversation records, and all 88 conversations cannot be obtained. Cause: The context export length threshold is not adjusted. The default setting only retains recent conversation segments, and the full export rule is not configured.

## How to confirm the configuration is complete
- Trigger a simulated work order submission, and check whether the workflow starts each business node in the preset order.
- Call the cross-departmental data node, and verify whether the returned fields match the mapping rules configured in `variables`.
- Simulate a timeout scenario, and check whether the workflow triggers the preset retry or exception handling logic.
- Export the full-process conversation records, and confirm that the number of exported entries matches the actual number of conversations.
