# Public Social Assistance and Minimum Living Security Application Review Consultation and Reply: Tool Calling and Plugins

## What this category of data looks like
This category of data primarily comes from daily business documents of entities including civil affairs bureau relief sections, subdistrict and township civil affairs offices, community committees, and verification centers. The documents include minimum living security application forms, family economic status verification reports, household survey forms, democratic appraisal records, public notice materials, and assistance approval forms. Data sources include the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-department shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, tax authorities, and other departments. The update frequency is monthly. The data focuses on family economic status and assistance eligibility, including fields such as family member information, income and property details, and household verification records. It has no unified fixed unit, and changes according to the field requirements of specific business documents.

## What constraints do these characteristics impose on the tool calling and plugins link
The cross-department data sources, monthly update frequency, and multi-type business document structure of this category of data impose multiple constraints on tool calling and plugin configuration. Cross-department data requires tools to support multi-system interface docking, and preset calling rules adapted to different data sources. Automatic tool calling can be triggered via the `toolChoice` configuration. Multi-type business documents include structured fields and unstructured supporting content, requiring the use of `functionCall` to bind corresponding tools to complete format parsing and field extraction, with preset logic matching the structural characteristics of verification reports, application forms, and other documents. Family economic status verification is the core time-consuming link. Tool calling requires configuring reasonable timeout and retry mechanisms, while adding a result verification link to avoid the risk of incorrect or missed assistance approvals.

The following configurations are formulated based on FastGPT v4.17.0.

| `toolChoice` | `auto` | This category requires automatic selection of tool calling strategies based on business scenarios to adapt to the diverse needs of cross-department data retrieval and document parsing |

| Tool result post-processing rules | Match and extract according to business document fields | Accurately extract core information such as family members, income and property required for minimum living security applications to ensure data accuracy |

## Three common mistakes
- The symptom is empty tool calling return results or missing core fields. The cause is that no field extraction rules are preset for the business documents of this category, making it impossible to accurately match necessary information such as family income and member relationships from the cross-department data returned by the tool.
- The symptom is frequent timeout errors in tool calling. The cause is that the configured timeout duration is too short, failing to adapt to the actual processing cycle of cross-department data retrieval and multi-document parsing.
- The symptom is unstable tool calling results, with some batches of returned verification data being incomplete. The cause is that no consistency verification logic is configured for tool results, and no compliance verification is performed on the returned cross-department data.

## How to confirm the configuration is complete
- Initiate a tool calling test for a single minimum living security application, check whether the returned data covers the core fields required by the business, and adjust the field extraction rules until they match the structure of the corresponding business document.
- Initiate a multi-concurrent call test, observe the return status of the cross-department data interface, and adjust the concurrent upper limit until no abnormal errors occur.
- Trigger a tool calling timeout scenario, verify whether the configured timeout duration adapts to the business processing cycle, and adjust the timeout duration until no frequent timeouts occur.
- Call a locally deployed large model tool, verify whether the model context window adapts to the business text length of this category, and adjust to `4096 token` until tool calling triggers normally.
