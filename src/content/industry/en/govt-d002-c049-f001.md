# Legality Review of Normative Documents: Service Consultation and Response — HTTP APIs and External Systems
This page is written based on FastGPT v4.17.0, and is adapted for scenarios of legality review of normative documents in state-owned enterprises, government agencies, and public service sectors.

## What this category of data looks like
The core data for this category comes from regulatory and rule databases, higher-level law databases, departmental policy document databases, and administrative normative document filing systems. Updates occur on an irregular basis. Documents processed daily include normative document drafts, drafting explanatory notes, legality review opinions, summaries of solicited comments, and filing reports. Most document structures include fields such as article content, issuing authority, effective date, and review points. There is no unified fixed unit; fields adjust based on document type. The core focus revolves around the authority, procedures, and legality of policy provisions.

## What constraints do these characteristics impose on the "HTTP APIs and External Systems" link
Data sources are scattered and updates have no fixed cycle. HTTP APIs need to support dynamic pulling of multi-source data, and avoid hardcoding fixed data source addresses. Document structures vary greatly, so APIs must be compatible with different document field formats, and should not predefine fixed parsing rules. Core review logic relies on higher-level laws and authority references, so APIs need to support precise article-level comparison calls. The data volume per request should not be too small, otherwise call frequency will increase. API calls to government filing systems must comply with security specifications, require valid identity credentials, and prevent unauthorized access.

## How to configure
| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| `Authorization` | Carry an API key issued by the government system, formatted as `Bearer {key content}` | Complies with identity verification specifications for external government interfaces, prevents unauthorized access |
| `variables` | Configure as `{"target_docs": ["regulatory and rule databases", "higher-level law databases"]}` | Limits the data source scope of API calls, matches the data source characteristics of this category |
| `responseData` | Only return fields for article content, issuing authority, and review matching results | Reduces invalid data transmission, adapts to the core data requirements of review scenarios |
| Single request data limit | 800–1200 characters | Balances API call efficiency and data integrity, complies with request size limits of government systems |
| Request timeout | 600 seconds | Adapts to the time requirements of multi-source data comparison, prevents request interruption due to complex review content |

## Three common errors
- API returns `404 page not found`: The configured data source address does not correctly point to the interface endpoint registered with the government filing system, and does not match the specified regulatory database and higher-level law database addresses for this category.
- API returns empty result fields: The `variables` configuration for limiting the data source scope is not set correctly, causing the API to pull irrelevant non-compliant document data and fail to hit core review references.
- API request times out: The request timeout duration is not set to meet multi-source comparison requirements, or the volume of data per request exceeds the system default limit.

## How to confirm the configuration is correct
- Call the test API, check if the returned `Authorization` verification status is passed, confirm that the identity credential configuration is valid.
- View the `responseData` field in the API response, confirm that only core content required for normative document review is included, with no redundant data.
- Simulate submitting a normative document draft, verify that the returned higher-level law matching results cover the review dimensions required by this category.
- Simulate multiple API calls to different data sources, confirm that the configured request timeout covers normal review duration, with no active interruptions.
