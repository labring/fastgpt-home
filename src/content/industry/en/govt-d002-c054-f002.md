# Service Consultation and Response for Flood Prevention, Disaster Mitigation and Emergency Duty: Vector Models and Indexes

## What the data for this category looks like
This category’s core data comes from meteorological early warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Daily documents include duty records, early warning notices, coordination meeting minutes, rapid disaster reports, emergency response plans, and material allocation slips. Most fields include rainfall and water condition values, material numbers, safe shelter locations, personnel transfer ledgers, and similar content. Data update frequency is daily; some real-time monitoring data has shorter update intervals. Most data structures mix structured fields and unstructured text, with some documents including time stamps and responsible subject identifiers.

## What constraints these characteristics impose on the vector models and indexes link
The multi-source mixed nature of this category’s data and its daily batch updates will place demands on vector index write performance. The document structure combining structured fields and unstructured text requires targeted configuration of vectorization rules to avoid field confusion. The timeliness requirements of real-time monitoring data require support for incremental index updates to avoid response delays caused by full reindexing. Data synchronized from multiple systems has format differences, which increases preprocessing costs before vectorization. If unaddressed, this will reduce the accuracy of vector calculations, thereby affecting the accuracy of service consultation responses.

## Configuration Settings

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to the average length of coordination meeting minutes and rapid disaster reports in this category of documents, avoiding breakage of key information within chunks |
| Overlap Length | 100–150 characters | Retains contextual connections between chunks, preventing cross-chunk early warning or response information from being split |
| `maxToken` | 4096 token | Matches the input limit of most general embedding models, adapting to the long-text content of emergency response plans |
| Similarity Threshold | 0.75–0.85, calibrated via actual testing | Distinguishes valid disaster information from irrelevant content, avoiding false recalls or missed recalls |
| Single Retrieval Limit | Top 8 entries | Controls the number of returns per retrieval, adapting to the need for quick access to core information in emergency scenarios |
| `defaultToken` | 200 token | Sets the default context length for returns, ensuring information completeness during service consultations |

## Three Common Misconfigurations
- Symptom: Abnormal vector calculation scores, with excessively large gaps between similarity scores of different texts and some results being completely identical. Cause: No separate preprocessing was performed for the structured fields of this category (such as rainfall values, material numbers), leading to non-semantic features interfering with vector calculations.
- Symptom: Excessively long vectorization time after batch uploading documents, with page loading progress stuck. Cause: No adaptive parameters for chunk length and retrieval limit were configured, and full documents were vectorized in one go without sharding, exceeding the system's single-processing limit.
- Symptom: After batch importing CSV data, the final index data volume is less than the number of source file entries. Cause: Null fields or invalid rows in the source data were not filtered, and some entries that do not meet format requirements were automatically skipped without generating clear prompts.

## How to Verify Proper Configuration
- Upload a single typical document (such as that day’s rapid rainfall disaster report) and check if the vectorized chunk results cover the full content without obvious information truncation.
- Initiate a search for disaster-related keywords, verify whether the number and relevance of returned results meet the requirements of the business scenario, and adjust the similarity threshold until expectations are met.
- Import batch test data, compare the number of source data entries with the number of final index entries, and confirm there is no abnormal data loss.
- Check system logs to verify whether the time taken for incremental index updates meets the response requirements of daily business, with no timeout errors occurring.
