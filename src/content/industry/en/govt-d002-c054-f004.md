# Workflow Orchestration for Flood and Disaster Prevention and Emergency Duty Consultation and Response

## What the data for this category looks like
Service providers are mainly state-owned enterprises and public service entities such as emergency management bureaus, water affairs bureaus, meteorological bureaus, sub-districts, towns, and emergency command centers. Data for this category comes primarily from meteorological early warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Update frequency is daily. Daily business documents include duty records, early warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Data fields include rainfall and water condition monitoring values, early warning levels, disaster location points, material stock and allocation quantities, transferred and resettled population counts. Some documents are linked to real-time monitoring point numbers and responsible units.

## Constraints Imposed on Workflow Orchestration by These Characteristics
Multi-source data access requirements for this category mean workflows must be configured with multiple nodes to pull real-time data from different systems in parallel. Frequently updated monitoring data requires workflow trigger intervals to match business rhythms, to avoid data lag. Diverse business document types need workflows to support content parsing and extraction for different formats. Cross-departmental scheduling scenarios require workflows to pass dynamic parameters between links via `variables`, to ensure data synchronization across nodes. The high-risk nature of emergency response also requires workflows to include failure retry and alert nodes, to prevent interruptions in critical links. This configuration uses FastGPT v4.17.0.

## How to Configure the Workflow
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Global variable settings | Bind rainfall threshold 50 mm/12 hours, early warning level trigger rules, material allocation threshold 1000 units | Aligns with core business judgment logic for flood and disaster prevention, and dynamically passes parameters across workflow links |
| Knowledge base call | Bind custom emergency knowledge base, return top 5 results per search | Matches the need to quickly retrieve historical response plans and early warning specifications in emergency scenarios, and avoids interference from redundant data |
| AI chat module | Preset question template as "Current rainfall is XX mm, water condition is XX cubic meters per second, please generate consultation key points" | Follows the fixed structure of business documents, and standardizes the format and scope of AI-generated content |
| Failure retry configuration | Retry 2 times, interval 60 seconds | Addresses temporary fluctuations in system interfaces, and ensures stability of multi-source data pulling |
| Scheduled trigger node | Trigger workflow every 15 minutes | Aligns with the update frequency of monitoring data, and ensures timeliness of emergency information |
| Node ID configuration | Assign unique `nodeId` to each workflow node | Facilitates troubleshooting of abnormal workflow nodes, and enables precise scheduling of each workflow link |

## Three Common Configuration Mistakes
- Phenomenon: After configuring a file link in the AI chat module, the runtime displays "specified resource not found". Cause: The file link is not bound to a global variable, so the node cannot read the specified document.
- Phenomenon: After binding a knowledge base to global variables, the call returns "no matching knowledge base" or empty results. Cause: Correct knowledge base association parameters were not passed, or knowledge base access permissions were not configured for the current workflow.
- Phenomenon: Workflow runs automatically interrupt after exceeding the preset duration. Cause: The scheduled trigger interval is set unreasonably, causing multi-source data pulling tasks to pile up and exceed the node processing limit.

## How to Verify a Successful Configuration
- View workflow operation logs to confirm that no fields are missing from the pulling results of each data source.
- Trigger a test workflow to check whether the consultation key points generated by the AI chat module match the preset business scenario format.
- Manually modify global variable parameters to verify that parameters of all associated nodes update synchronously.
- Simulate an error returned by a data source interface to confirm that the failure retry node triggers the alert process as configured.
