# Work Inquiry and Response for Flood Control, Disaster Prevention and Emergency Duty: Model Access and Configuration

## What the Data for This Category Looks Like
The data for this category mainly comes from meteorological early warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Daily generated documents include duty records, early warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. The data update frequency is daily. Some real-time monitoring data has a shorter synchronization interval. Most document structures include fields such as event time, location, severity level, and disposal progress. Some documents include numerical parameters such as rainfall and water level.

## Constraints on Model Access and Configuration
The data for this category is scattered and diverse, including both real-time monitoring data and batch documents. Model access must support rapid integration and parsing of multi-source data. Documents include structured fields such as time, location, severity level, and numerical parameters. This requires adaptation to content extraction logic for different formats. The data update frequency is tightly tied to business disposal rhythms. Model calls and data synchronization processes must match the timeliness requirements of emergency scenarios. Documents such as consultation minutes and rapid disaster reports are relatively long. Reasonable context and slicing rules must be configured to avoid exceeding the model's supported context limit.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0, and are adapted to the emergency business scenario requirements of this category.

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Documents in this category mostly include multi-source monitoring data and consultation minutes, and need to cover at least 3 days of duty records and early warning information to avoid context truncation |
| `maxTokens` | 2000–3000 token | Used to generate emergency texts such as early warning responses and disposal plans, balancing response speed and content completeness |
| `quoteMaxToken` | 1500 characters | The content to be quoted, such as rapid disaster reports and hydrological data, is of moderate length, and limiting the quoted length ensures the coherence of the main response |
| `temperature` | 0.2–0.4 | Emergency scenarios require responses to be rigorous and accurate, reducing randomness to avoid expressions that do not comply with business specifications |
| `AIPROXY_API_ENDPOINT` | Fill in the proxy address of the corresponding model according to the deployment environment | Adapt to the model call path for local deployment, ensuring the security and stability of data transmission |
| `AIPROXY_API_TOKEN` | Fill in the exclusive token generated during deployment | Implement identity verification for model calls to prevent unauthorized access |

## Three Common Misconfigurations
- Issue: Model calls fail, returning authentication errors or invalid address errors. Cause: `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are not filled in correctly, or the proxy address does not match the port of the locally deployed model service.
- Issue: Uploaded flood control documents in conversations are truncated, and full content cannot be extracted. Cause: Reasonable context and slicing rules are not configured, and the document length exceeds the context limit supported by the model.
- Issue: Generated response content is overly casual, including inaccurate descriptions of disaster severity levels. Cause: The `temperature` parameter is set too high, leading to randomness in model-generated content that exceeds the rigor requirements of emergency scenarios.

## How to Verify Successful Configuration
- Initiate a test conversation that includes local hydrological data and early warning notices. Check whether the model correctly extracts key fields and generates corresponding responses.
- Upload a single long consultation minute. Verify that the system automatically completes slicing and correctly integrates context content.
- View the model call log. Confirm that the configurations for `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` have been correctly read.
- Adjust the `temperature` parameter and initiate a test. Observe changes in the rigor of the response content to confirm that the parameter takes effect.

The values provided are common starting points and should be evaluated against the reader's own samples.
