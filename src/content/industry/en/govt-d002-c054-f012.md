# Work Consultation and Response for Flood Prevention, Disaster Mitigation and Emergency Duty: Deployment and Upgrade

## What the data for this category looks like
The daily documents for this category include duty logs, early warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Fields mostly include timestamps, area codes, danger levels, material quantities, and others. Units include millimeters (for rainfall), cubic meters (for water volume), number of people (for relocated people), and more. Data sources include meteorological early warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. The update frequency is daily; some real-time early warning data has shorter update intervals.

## What constraints these characteristics impose during deployment and upgrade
The need to connect multiple data sources requires configuring multiple storage and connection parameters during deployment to ensure synchronization and persistence of data from different systems. The coexistence of daily batch data and real-time early warning data places clear requirements on storage capacity and concurrent processing capabilities. Upgrades must avoid data synchronization interruptions caused by configuration changes. Significant differences in document fields require compatibility with custom field mapping rules during deployment and upgrades to prevent business exceptions caused by data structure changes. Emergency scenarios have high stability requirements; frequent major version switches should be avoided after production environment deployment, and stable version branches must be locked to ensure service continuity.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Configure an independent high-availability cluster connection string | A large volume of unstructured documents such as duty logs and rapid disaster reports must be stored; a high-availability cluster ensures data persistence |
| `REDIS_URL` | Configure the address of a persistent caching cluster | Real-time meteorological and hydrological early warning data must be cached to reduce query pressure on downstream systems |
| `STORAGE_S3_ENDPOINT` | Configure an object storage endpoint suitable for large file storage | Large files such as video surveillance footage and consultation minute attachments must be stored, to meet storage requirements above 1000 GB |
| `DB_MAX_LINK` | `200–300 connections` | Handle multi-system data synchronization and concurrent consultation requests to avoid connection exhaustion |
| `FE_DOMAIN` | Enter the official domain name of the emergency duty platform | Ensure consistent domain names between the work consultation interface and internal systems to avoid cross-domain issues |
| `ROOT_KEY` | `At least 16 random characters` | Control background management permissions to prevent unauthorized access |

## Three common configuration mistakes
- After an upgrade, only a small number of entries appear in the global variable list. The symptom is that only 2 options are displayed in the global variable drop-down menu of the background configuration interface. The cause is that the variable storage path is not correctly associated in the `FILE_TOKEN_KEY` configuration, causing old version variables to fail to load.
- After local deployment, knowledge base file upload fails. The symptom is that the upload progress gets stuck at 90% before returning a connection timeout error. The cause is that write permissions for the storage bucket adapted to the `STORAGE_S3_ENDPOINT` configuration are not set, preventing normal file storage.
- Data synchronization exception occurs after cross-version upgrade. The symptom is that some fields are missing from rapid disaster report data. The cause is that old and new version document field mapping rules are not compatible, causing field conversion failures during the upgrade process.

## How to confirm that the configuration is correct
- Log in to the background management interface, check whether the global variable list includes all preset business fields such as rainfall, danger level, material quantity, and others.
- Upload a test duty log document to confirm that the upload progress completes and the file can be previewed normally in the retrieval interface.
- Call the internal data synchronization interface to verify that meteorological early warning and hydrological monitoring data can be written normally to the specified storage cluster.
- Check the system operation logs to confirm that there are no errors related to `DB_MAX_LINK` connection exhaustion or `REDIS_URL` connection timeout.
