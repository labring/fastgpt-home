# Food Safety Supervision Sampling Service Consultation and Reply: HTTP Interfaces and External Systems

## What data for this category looks like
Data for this category comes primarily from food safety sampling monitoring systems, the State Administration for Market Regulation sampling results query system, laboratory LIMS systems, and food producer and operator ledgers. Teams process daily documents including sampling plans, sampling slips, inspection reports, non-compliant food verification and disposal reports, and risk control announcements. Data updates occur monthly. Core fields include sampling locations, inspection items, non-compliance determination results, disposal measures, and more. No unified fixed units apply. Values must align with the field rules of corresponding documents.

## Constraints on HTTP interfaces and external systems
The monthly update rhythm means teams do not need to call interfaces frequently. Teams can configure reasonable cache durations to reduce external system load. Multiple data source access requirements mean interfaces must adapt to different system return formats, so teams must reserve field expansion space. Complex document structures require teams to implement multi-field validation logic. Interfaces must perform validity checks on core fields such as sampling numbers and inspection items. Errors in non-compliance disposal data may trigger regulatory risks. Teams must configure interfaces with error capture and reporting mechanisms to ensure traceability of abnormal situations.

## Configuration guidelines
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `Authorization` | `Bearer {regulatory system API key}` | External systems such as the State Administration for Market Regulation sampling query system typically use Bearer token authentication to secure interface access |
| Interface timeout duration | `600 seconds` | Documents such as inspection reports have large data volumes. Teams must reserve sufficient processing time for single requests to avoid timeout interruptions |
| `responseData` | Return core business fields in JSON structure | Teams must adapt to return formats from multiple source systems, and only extract necessary content such as sampling slip numbers and inspection results to reduce data parsing complexity |
| `variables` | Configure monthly update cycle variables | This matches the monthly data update rhythm. Teams can dynamically adjust interface call frequency and cache validity via variables |
| Maximum retry attempts | `3 attempts` | This allows recovery from temporary faults such as network fluctuations. Excessive retries increase processing burden on external systems |
| Field validation rules | Require mandatory checks for sampling numbers and non-compliance determination items | Missing core business fields will block subsequent verification and disposal processes |

## Three common mistakes
- Images of inspection reports uploaded via interfaces may become unavailable after a period of time, while they display normally on the official interface. This happens because the interface lacks a persistent storage strategy for image resources, and only temporary base64 data is cached, leading to expiration and failure.
- Interface calls return a `401 Unauthorized` error. This occurs because the `Authorization` parameter does not carry a valid regulatory system API key, or the key has expired.
- Business data returned by the interface lacks sampling location information. This happens because the interface configuration does not specify extraction of this core field, leading to omission of key content during data parsing.

## How to confirm configurations are properly set
- Teams can call the test interface to verify the `Authorization` parameter works, and receive a non-empty valid business response.
- Teams can simulate a monthly update node to trigger an interface call, confirm the cache duration matches the update cycle, and verify no duplicate invalid requests occur.
- Teams can submit test data with missing core fields to verify the interface returns clear validation error prompts.
- Teams can send 3 consecutive simulated timeout requests, confirm the interface stops calling after reaching the maximum retry limit, and verify it generates an error reporting record.
