# Service Consultation and Response for Food Safety Supervision and Sampling: Tool Calling and Plugins

## What the Data for This Category Looks Like
Data for this category comes from food safety sampling and monitoring systems, the State Administration for Market Regulation Sampling Results Query System, laboratory LIMS, and enterprise account books. Daily documents include sampling plans, sampling slips, inspection reports, unqualified food verification and disposal reports, and risk control notices. Core fields include sampling number, inspection items, unqualified judgment results, and disposal process nodes. Data is updated once per month. The core association chain is centered on sampling batches. Different documents are linked via sampling numbers.

## What Constraints These Characteristics Impose on Tool Calling and Plugins
The monthly data update cycle requires the tool calling cache strategy to match this period, avoiding expired data calls. Multiple document types require plugins to support routing calling logic by document type. Plugins must prioritize parsing unqualified item fields for inspection reports. Multi-data source access requires configuring unified data mapping rules to convert fields from different systems into a uniform format. The complexity of core fields requires limiting tool calling parsing scope, only extracting sampling, inspection, and disposal fields related to service consultation. This avoids redundant information interfering with user inquiries.

## Configuration Settings

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | Fixed as `{"type":"function","function":{"name":"get_sampling_info"}}` | Explicitly specify calling the sampling information query tool, prevent the model from independently selecting unrelated tools |
| `functionCall` | Enable forced function call mode | Ensure every consultation call executes the preset tool, prevent the model from generating invalid content that does not use tool calls |
| Document chunk length | 800–1200 characters | Match the single-page content length of inspection reports and sampling slips, avoid chunking that destroys complete document structure |
| Single tool call limit | First 3 entries | Limit the number of sampling batches returned per consultation, avoid information overload affecting user judgment |
| Context window size | 4000–6000 tokens | Adapt to context requirements for multi-document associated queries, cover associated content of sampling plans, sampling slips, and disposal reports |
| Timeout threshold | 60 seconds | Match the average interface response time of market supervision related systems, avoid interaction interruptions caused by excessive waiting time |

## Three Common Misconfigurations
- Issue: After tool calling completes, the associated sampling batch variable is not automatically updated, and the interface displays empty variable fields. Cause: No variable synchronization rule after tool calling is configured, and core fields such as sampling number and inspection items returned by the tool are not mapped to workflow variables.
- Issue: When calling the document query tool, the number of returned results exceeds the configured single call limit. Cause: The result truncation rule is not enabled in the tool calling configuration, or the single search limit parameter is not correctly bound.
- Issue: Uploading a sampling slip file via an API-triggered workflow fails, returning an error that the file format is not supported. Cause: The request is not encapsulated using multipart/form-data format as required, or the file field name is not correctly matched with the workflow node.

## How to Verify Correct Configuration
- Launch a simulated consultation, enter a known sampling number, check whether the tool returns the corresponding inspection report and disposal status information, confirm that the `toolChoice` parameter correctly triggers the preset tool.
- View the tool calling log, check whether the number of returned results matches the configured single call limit, confirm that the result filtering rule takes effect.
- Call the API interface with test parameters, check whether the returned results contain correct knowledge base data, confirm that the knowledge base ID configuration is correct.
- Trigger the workflow to execute tool calling, view the variable panel, confirm that the fields returned by the tool have been automatically synchronized to the workflow variables.

The values provided are common starting points and should be measured against the reader's own samples.
