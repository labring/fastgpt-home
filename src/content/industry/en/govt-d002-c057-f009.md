# Food Safety Supervision Sampling Service Consultation and Reply: Model Access and Configuration

## What this category of data looks like
Data for this category primarily comes from the Food Safety Sampling and Monitoring System, the State Administration for Market Regulation Sampling Results Query System, testing institution LIMS, and enterprise ledgers. The update frequency is monthly. Daily documents include sampling plans, sampling slips, test reports, unqualified food verification and disposal reports, and risk control notices. Core evidence consists of test reports issued by laboratories. Document fields cover sampling number, test items, unqualified judgment results, disposal measures, and other content. Typical users include food sampling departments of market supervision bureaus, testing institutions, and grassroots supervision offices. Some offline documents exist as scanned copies.

## What constraints these characteristics impose on model access and configuration
Monthly updated data sources require configuring monthly incremental sync scheduling rules during model access to avoid high-frequency syncs occupying computing resources. Multi-source data requires adaptation to interface formats of different systems, so data source mapping rules must be configured in advance to unify data structures. Core documents such as test reports are semi-structured files, which have clear requirements for long text processing parameters. Documents related to unqualified food disposal involve regulatory processes, so model output must strictly match preset fields in the documents, and content not included in source data should not be generated. Grassroots supervision office scenarios require lightweight configuration to reduce complex parameter adjustment steps.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to long text documents such as test reports, covering all information of complete sampling and disposal processes |
| `maxTokens` | 2000–3000 token | Controls the output length of single-round consultation replies, avoiding exceeding the field display limits of regulatory documents |
| `quoteMaxToken` | 1500 token | Limits the maximum length of referenced source documents, ensuring referenced content matches core fields of test reports |
| `toolChoice` | auto | Automatically selects tool calls, adapting to structured data extraction requirements for sampling slips and test reports |
| `vision` | Enabled | Supports content extraction from scanned copies of sampling slips and test reports, adapting to digital processing of offline paper documents |
| `temperature` | 0.2–0.4 | Reduces generation randomness, ensuring reply content strictly matches the preset format and field requirements of regulatory documents |

## Three Common Misconfigurations
- Phenomenon: When calling the vision model, the stamp area of the sampling slip cannot be recognized, and the sampling number is missing from the output content. Cause: The `vision` configuration item is not enabled, or visual preprocessing rules for structured documents are not configured.
- Phenomenon: The model occasionally interrupts output when calling tools, and only returns part of the test report content. Cause: The `maxContext` parameter is not set reasonably, and long text documents exceed the context window, leading to truncation and triggering call interruptions.
- Phenomenon: After accessing the mineru model, normal calls fail, and the tool returns a version incompatibility error. Cause: The specific version of mineru adapted to FastGPT v4.17.0 is not installed, and using the official latest version directly causes interface mismatch.

## How to Verify Successful Configuration
- Submit test text of a single test report, verify whether the unqualified items in the model output match the fields of the source document, and adjust related parameters until the output meets expectations.
- Upload a scanned copy of the sampling slip, verify whether the vision model can correctly extract core fields such as sampling number and testing institution, and confirm that the configuration takes effect.
- Trigger the monthly incremental sync task, verify whether the number of documents returned by the data source interface matches the actual number of updated sampling plans, and verify the correctness of the data source configuration.
- Call the speech-to-text tool to upload test audio, verify the completeness of the transcription result, and confirm that the association between the tool node and the model configuration is correct.

The values provided are common starting points and should be measured against the reader's own samples.
