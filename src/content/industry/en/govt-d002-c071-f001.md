# Service Consultation and Response for Power Generation Groups: HTTP APIs and External Systems

This document is written for FastGPT v4.17.0.

## What This Category of Data Looks Like

Data for power generation group service consultation and response mainly comes from internal ticketing systems, customer service conversation records, and officially published service guideline documents.
Data update rhythms fall into two categories: service guideline data is updated annually or quarterly, while ticket and real-time consultation conversation data is generated in real time.
Document structures include fields such as matter name, handling entity, required materials, handling deadline, consultation feedback channel, and frequently asked questions.
Field units are mostly workdays, pieces, times, and similar. There is no mandatory unified format template, and some data has multi-language or multi-version differences.

## Constraints Imposed by These Characteristics on HTTP APIs and External Systems

Dispersed sources of power generation group service consultation data require APIs to support integration with multiple internal systems. Configure API logic for multi-source data pulling and aggregation.
Non-real-time updated service guideline data requires configuring batch pulling trigger timing in the API. This avoids frequent requests occupying internal system resources.
The lack of unified field formats requires the API to use the `variables` parameter for cross-system field mapping. This adapts to data structure differences across different sources.
Real-time requirements for real-time consultation conversation data require adjusting API-related timeout configurations. This ensures request responses meet business timeliness requirements.
The existence of multi-version and multi-language data requires the API to support passing parameters for specified versions or languages. This returns corresponding content.

## How to Configure Settings

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {Group Internal API Key}` | Adapts to authentication specifications for power generation group internal systems, ensures API call legality |
| `variables` | `{"matter_name": "Matter Name", "handle_deadline": "Handling Deadline"}` | Completes cross-system field mapping, adapts to structure differences across data sources |
| `responseData` | Return specified field subset, filter redundant content | Reduces data transmission volume, adapts to internal system receiving limits and business requirements |
| Single request timeout | `30–60 seconds` | Meets real-time consultation conversation response timeliness requirements, avoids excessive business waiting time |
| Data pulling frequency | Triggered quarterly/annually for service guideline type, once per 1 minute for real-time consultation type | Matches update rhythms of different data types, balances resource occupation and data timeliness |

## Three Common Mistakes

- Passing knowledge base-related parameters when calling the API returns the error "Corresponding knowledge base not found". The cause is failing to correctly pass the knowledge base ID via the `variables` parameter, or failing to synchronize global variable configurations to the API request body.
- API calls return a 401 status code. The cause is incorrect `Authorization` parameter format, not following the Bearer token specification.
- The API returns redundant data exceeding internal system receiving limits. The cause is failing to configure the `responseData` parameter to filter fields, resulting in transmission of unnecessary content.

## How to Confirm Configuration Is Complete

- Call the API, check if the returned `responseData` field contains expected business data. Confirm that field mapping and filtering configurations take effect.
- View authentication logs, confirm that the `Authorization` parameter is correctly identified, with no authentication failure records.
- Adjust data pulling frequency, verify that updates of different data types meet configuration requirements.
- Pass test parameters, check if the API can correctly map fields and return content conforming to business format.
