# Service Consultation and Reply for Power Generation Groups: Model Integration and Configuration

## What the data for this category looks like
Service consultation and reply data for power generation groups comes primarily from four sources: internal work order systems, offline service window registrations, official hotline transcripts, and official website message boards. Data is submitted in real time, and archived in daily batches. The document structure includes eight core fields: consultation ID, submission time, consultation type tag, user's department (left blank when anonymous), consultation details, processing progress, reply content, and completion time limit. For field units: time-related fields use hours or days, consultation types use standardized classification codes, and reply content uses plain text plus attachment links.

## What constraints do these characteristics impose on the model integration and configuration link
Data from multiple channels has significant format differences. Models must support unified parsing and alignment of multi-source data during integration. Preset data format adaptation rules must therefore be added during the configuration phase. Real-time updated consultation data requires the model's context window to handle incremental content, preventing loss of key progress information due to window limits. Standardized classification tags and field structures require the model to accurately recognize the semantics of specific business fields. Corresponding business knowledge base content must therefore be bound during configuration. Confidentiality requirements for internal data mean model integration must use intranet-isolated API endpoints, to avoid data leaks.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale for This Setting |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | Adapts to multi-segment work orders, progress records, and policy reference content included in power generation group consultation data |
| `temperature` | `0.1–0.3` | Ensures rigor of service reply content, reduces ambiguous responses |
| `quoteMaxToken` | `2000–3000 characters` | Retains sufficient length of policy documents and work order content for reference in replies |
| `toolChoice` | `auto` | Automatically matches knowledge base content, adapts to policy query needs for service consultations |
| `AIPROXY_API_ENDPOINT` | Exclusive intranet address provided by the deployment service provider | Meets the isolation requirements for internal data of power generation groups |
| `AIPROXY_API_TOKEN` | Regularly rotated encrypted key | Ensures security of API access, prevents key leaks |

## Three common configuration errors
- Phenomenon: An authentication failure is returned when calling the configured model, the interface displays the API key is invalid, and the logs contain a 401 status code. Cause: `AIPROXY_API_TOKEN` is not configured as the exclusive key for the power generation group, or the key is not granted intranet access permissions.
- Phenomenon: After configuring the model mapping, actual calls still return replies from the default model, and the preset model rules are not matched. Cause: The global switch for model mapping is not enabled, or the matching order of the mapping rules is set incorrectly.
- Phenomenon: After uploading the technical specification documents of the power generation group, the model cannot correctly extract the parameter content, and the returned parsing result lacks key fields. Cause: `maxTokens` is not adjusted to adapt to long document parsing, or the value of `quoteMaxToken` is too small, causing key content to be truncated.
