# Service Inquiry and Response for Power Generation Groups: Deployment and Upgrade

## What the Data for This Use Case Looks Like
The data for power generation group service inquiry and response comes primarily from internal standardized service guideline documents, historical service work order records submitted by affiliated power plants, archived consultation dialogues from customer service teams, and publicly disclosed service process documents from the power industry government affairs sector.
Data updates follow three schedules: Daily submitted service work orders are updated in real time. Standardized service guidelines receive batch updates once per quarter. Archived historical consultation data is stored offline weekly.
Individual documents typically cover service item names, application conditions, required submission materials, time limits for completion, consultation channels, and other details. Some detailed service guideline documents can reach several thousand characters in length.
Structured fields include item unique identifiers, management hierarchy, completion time limit (unit: working days), consultation channel type, and other related information.

## Constraints During Deployment and Upgrade
These data characteristics create clear constraints during deployment and upgrade.
First, long-text service guidelines and cross-hierarchy massive work order data require sufficient database connection and storage resources during deployment. This prevents truncation of long text during processing or failed concurrent retrieval.
Second, data sources with different update schedules require support for both incremental synchronization and full import data access methods during deployment. Upgrade processes must be compatible with archived data formats from older versions to prevent failed loading of historical consultation records.
Additionally, the completion time limit field uses working days as the unit. Deployment must include corresponding time processing rules to avoid confusion between natural day and working day calculation logic.
Finally, internal service data for power generation groups involves sensitive business processes. Deployment and upgrade processes must ensure internal network isolation for data transmission and storage to prevent unauthorized external access.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `1200 connections` | Power generation group service inquiry data includes large volumes of historical work orders and long documents. A connection count of 1200 supports concurrent retrieval requirements and prevents database connection exhaustion |
| `STORAGE_S3_ENDPOINT` | `Group internal object storage address` | Internal power generation group service data involves sensitive business processes. Using internal storage ensures data transmission security and avoids public network exposure risks |
| `REDIS_URL` | `Internal Redis address with password authentication, timeout set to 300 seconds` | Used to cache frequently requested question-answer pairs and long document chunks. The 300-second timeout accommodates wait times for long text processing. Password authentication ensures cached data security |
| `FE_DOMAIN` | `https://fastgpt.energygroup.com` | Complies with internal group domain specifications, ensures unified domain names for published consultation services, and meets HTTPS protocol requirements for interface calls |
| `MONGODB_URI` | `Sharded cluster connection address determined through actual testing` | Historical work order data has a large volume. Sharded clusters support stable read/write performance and accommodate high-frequency write requirements for incremental synchronization |
| `ROOT_KEY` | `Group-wide API access key` | Restricts unauthorized application publishing and data modification, ensures security of internal deployments, and prevents tampering with sensitive configurations |

## Three Common Configuration Mistakes
- Symptom: When a several-thousand-character service guideline document is input into the deployed model, the output does not cover key process steps and provides irrelevant responses. Cause: The context window configuration was not optimized for long text, resulting in loss of core information after the long document is truncated.
- Symptom: After publishing the application, the built-in voice function cannot be called normally, and the interface returns a protocol mismatch error. Cause: `FE_DOMAIN` was not configured as an HTTPS address, leading to a mismatch between the voice interface call protocol and the front-end domain.
- Symptom: After upgrading FastGPT to v4.17.0, attempts to import a workflow application package exported from an older version result in a format incompatibility or insufficient permissions prompt. Cause: The older version application package was not exported according to version compatibility rules, or correct application import permissions were not configured.

## How to Verify Correct Configuration
- Log in to the database monitoring dashboard, check if the current database connection count stays stable within 80% of the `DB_MAX_LINK` configured value, to confirm the connection count configuration is active.
- Upload a several-thousand-character service guideline document, initiate a retrieval request, and verify that the returned results include complete application conditions and material lists, to confirm long text processing configuration is working correctly.
- Call the application publishing API, check if the returned interface address uses the HTTPS format, to confirm `FE_DOMAIN` configuration is correct.
- Attempt to import a workflow application package exported from an older version, check if the application configuration can be parsed and loaded normally, to confirm version compatibility and import permission configuration are active.
