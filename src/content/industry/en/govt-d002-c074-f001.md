# State-owned Asset Management Company Service Inquiry and Reply: HTTP Interfaces and External Systems

## What this category of data looks like
Service inquiry data for state-owned asset management companies comes primarily from three sources: the state-owned asset supervision comprehensive platform, internal office OA systems, and electronic registration records from offline service windows.
Non-emergency inquiries sync every hour on workdays. Emergency inquiries sync in real time to the interface data source.
The structure of a single data record includes these fields: unique inquiry identifier, inquiry initiator type, inquiry category (including asset disposal, personnel appointment and removal, policy consultation, etc.), question details, official reply content, processing progress, legal processing time limit, and service recipient feedback rating.
Field format rules:
- Unique inquiry identifier uses a string format
- Legal processing time limit is measured in days
- Service recipient feedback rating uses a numeric 1-5 star scale

## What constraints these characteristics impose on HTTP interfaces and external systems
Dispersed data sources across multiple internal state-owned asset systems require interfaces to support multi-source data aggregation and authentication. This avoids delays caused by cross-system requests in a single call.
Real-time synchronized emergency inquiry data requires interface timeout settings to accommodate cross-system interaction buffer duration. Do not set timeouts too short. Short timeouts will cause failures for emergency inquiry interface calls.
Data contains sensitive information related to state-owned asset supervision. Interface requests and responses must strictly filter non-essential fields. Only return content required by external systems to prevent sensitive data leaks.
Complex field structures with fixed classification rules require interface request parameters to precisely match field names. Parameter mismatches cause data parsing errors, disrupting external system business processing.

## How to set configurations
These configurations follow FastGPT v4.17.0 specifications.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Interface authentication method | Use the `Authorization` header with a Bearer token, set token validity to 7 days | Complies with security and compliance requirements of state-owned asset systems, avoids frequent token refreshes that reduce call efficiency |
| Request parameter filtering | Only return fields specified in `variables`, filter sensitive information fields | Reduces sensitive data transmission, complies with state-owned asset data privacy protection regulations |
| Response data format | Use `responseData` to wrap returned results, including status code, message, and business data | Facilitates unified parsing of response content by external systems, lowers docking costs |
| Interface timeout duration | 300 seconds | Adapts to average data query time within state-owned asset systems, reserves buffer space for cross-system interactions |
| Retry strategy | Retry 2 times after failure, with a 10-second interval | Avoids call failures caused by short-term network fluctuations, and prevents business conflicts from duplicate submissions |
| Data desensitization rule | Desensitize contact information and ID numbers of inquiry subjects, retain the first 3 and last 4 digits | Complies with personal information protection regulations, prevents sensitive data leaks |

## Three common configuration errors
- Calling the interface returns a "401 Unauthorized" status code, or the interface prompts "no authorization". The cause is failure to correctly carry a valid `Authorization` header token, or failure to add the external system IP to the allowed access list of the state-owned asset supervision system.
- The interface returns a "Model response empty" error prompt. The cause is that the `responseData` field is not correctly bound to the reply content of state-owned asset service inquiries, or the request parameter filtering rule excludes all valid business data.
- A timeout error triggers within 10 seconds after interface call. The cause is that the timeout configuration is set too short, failing to adapt to delays in cross-node data synchronization within state-owned asset systems, or network link fluctuations without reserved buffer time.

## How to confirm configurations are correct
- Call the interface with a valid `Authorization` header token, check that the returned HTTP status code is 200 OK.
- View the `responseData` field, which contains expected service inquiry items, official reply content, and processing progress information.
- Pass a test inquiry unique identifier, confirm that the returned data matches the internal records of the state-owned asset system.
- Simulate 3 consecutive calls, check that the retry strategy takes effect and there are no duplicate submission exception logs.
