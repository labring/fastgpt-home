# Work Consultation and Reply for State-Owned Capital Investment Companies: HTTP Interfaces and External Systems

## What this category of data looks like
State-owned capital investment company work consultation and reply data mainly comes from internal work guideline repositories, state-owned assets supervision policy documents, offline appeal work orders, and public state-owned assets service information. The data update rhythm varies: policy documents are updated quarterly, while appeal work orders and real-time consultation content are updated daily. Each single document includes four core fields: item code, processing time limit, appeal type, and reply specification. Processing time limit is measured in working days. The item code is an 18-digit field derived from the unified social credit code. The word count of individual documents ranges from several hundred characters for work order content to several thousand characters for complete policy texts.

## Constraints for HTTP Interfaces and External Systems
Data sources are scattered across multiple external systems including internal OA, work order systems, and state-owned assets supervision platforms. HTTP interfaces must support multi-source data docking and format unification, and compliance authentication must be configured via `Authorization`. The update rhythms of different data sources vary greatly, so interfaces must support both full pull and incremental pull modes, with the pull timestamp configured using the `variables` parameter. Core fields of work data have strict requirements: `responseData` must strictly map specified fields to avoid omissions that reduce the accuracy of subsequent consultation replies. For internal network deployment scenarios, adaptation to the internal network environment is required to prevent request failures caused by external dependencies.

## How to Configure Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale for This Setting |
| ---- | ---- | ---- |
| `Authorization` | Internal service token, valid for 7 days | Complies with authentication compliance requirements for internal systems of state-owned capital investment companies, preventing unauthorized access |
| `responseData` | Strictly map the three core fields: item code, processing time limit, and appeal type | Matches standard field specifications for work consultation data of state-owned capital investment companies |
| `variables` | Set the incremental pull timestamp to 24 hours | Adapts to the regular update rhythm of work consultation data, reducing invalid requests |
| Maximum data per single request | 1000 entries | Adapts to bandwidth limits for internal network deployment, avoiding request timeouts |
| Interface timeout period | 600 seconds | Matches the average response duration of internal state-owned assets supervision systems |
| Document chunk length | 800–1200 characters | Adapts to the average word count of work consultation documents, optimizing vector model embedding effects |

## Three Common Configuration Errors
- When calling the interface to upload work documents after internal network deployment, the status remains stuck in loading. The cause is that the internal domain whitelist is not configured, preventing FastGPT from accessing the internal resource synchronization interface.
- Incorrect `responseData` field mapping causes the returned work data to omit the processing time limit field. The cause is failure to strictly match the standard data fields of state-owned capital investment companies.
- After the `Authorization` token expires, the interface returns a 401 status code. The cause is failure to regularly update the token configuration and set up automatic refresh logic.

## How to Confirm Successful Configuration
- Initiate a test call and verify that the returned `responseData` fields include the three core fields: item code, processing time limit, and appeal type.
- Verify the validity of the `Authorization` token, confirming that the interface call returns a 200 status code.
- After configuring the incremental pull parameter, initiate two requests with a 24-hour interval, confirming that the second request only pulls newly added data.
- Send a batch request, confirming that the interface response duration does not exceed 600 seconds.
