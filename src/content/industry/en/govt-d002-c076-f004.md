# Handling Inquiries and Responses for State-owned Capital Operation Companies: Workflow Orchestration

## What the Data for This Category Looks Like
Data comes primarily from three sources: the internal handling inquiry ticket system of state-owned capital operation companies, the archived policy consultation library of the state-owned assets supervision platform, and handling application and response records submitted by subordinate enterprises.
Update schedule: Real-time synchronization occurs when a ticket is closed. Incremental synchronization of full archived data runs every early morning.
Each single data entry includes these fields: inquiry subject, inquiry item, submission time, response content, closing status, and associated policy document identifier. Inquiry item and response content are text fields. The associated policy document identifier uses a string type. Submission time follows the standard timestamp format.

## Constraints Imposed on Workflow Orchestration
Multi-source data access requires workflows to configure multiple knowledge base association rules, and automatically route to the corresponding data source based on the inquiry subject.
Real-time updated ticket data requires the retrieval step to support incremental refresh, to avoid loading expired response content.
The associated policy document identifier field requires workflows to trigger associated policy library retrieval using the field value, to supplement compliance basis for responses.
Text fields have large length variations. The context splicing step must adapt to different lengths of inquiry and response content to avoid exceeding context limits.
Internal compliance requirements mandate configuring approval nodes to verify response content compliance. The `variables` parameter must bind verification rules for the corresponding business domain.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Multi-knowledge base association | Divide 3 knowledge bases by subordinate enterprise type, bind the business domain parameter in `variables` | Adapt to the routing requirements of multi-source data, match the business domain division rules of state-owned capital operation companies |
| Context splicing length | 800–1200 characters | Cover the common length of inquiry and response content, adapt to the text scale of handling inquiries |
| Retrieval recall count | Top 8 entries | Cover associated responses and policy content for common inquiries, avoid redundant retrieval results |
| `variables` | Bind two fields: inquiry subject and closing status. Values use string type, calibrated based on actual testing | Implement routing and compliance verification for multi-source data, match the field structure of ticket data |
| Node timeout setting | 600 seconds | Match the average processing duration of the handling inquiry and response process, avoid workflow node blocking |
| `nodeId` trigger rule | Bind the `nodeId` of the response generation node to trigger compliance verification | Ensure all generated response content undergoes internal compliance review, meets state-owned assets supervision requirements |

## Three Common Configuration Mistakes
- Phenomenon: An error is returned when calling the workflow via API, prompting that the knowledge base is not specified. Reason: The routing rules for multiple knowledge bases are not configured via `variables`, so the workflow cannot automatically match the knowledge base for the corresponding business domain.
- Phenomenon: Memory overflow occurs when running a single node, and concurrent requests cannot be processed. Reason: Reasonable retrieval recall count and context splicing length are not set, causing a single task to load too much data and occupy system resources.
- Phenomenon: Workflow variables cannot be selected in the JSON input box, and input content cannot be dynamically replaced. Reason: JSON-format field binding rules are not configured in `variables`, so the system cannot recognize the variable mapping relationship.

## How to Verify Successful Configuration
- Submit a test inquiry ticket, check the workflow running log to confirm that the fields bound by `variables` have been correctly passed to subsequent nodes.
- Trigger the retrieval link, verify that the returned knowledge base results match the configured association rules.
- Call the API to access the workflow, check that the returned response format complies with preset output rules.
- Simulate multiple concurrent requests to confirm that workflow nodes do not experience blocking or timeout errors.
