# Public Transit Service Inquiry and Response: HTTP Interfaces and External Systems

## What the data for this category looks like
Service inquiry data for public transit originates from three core sources: on-vehicle scheduling terminals, station passenger flow collection devices, and official route network databases. The scheduling center updates real-time shift and vehicle location data synchronously, with update intervals aligned to actual transit operation scheduling rhythms. Operations teams compile station passenger flow statistics daily. Operations departments update basic configuration information for routes and stations regularly. Data documents include fields such as route number, station name, estimated arrival time, current vehicle latitude and longitude, and operation status. Units include minutes, degrees, passenger trips, and others. Some data uses nested structures for organization.

## What constraints these characteristics impose on HTTP interfaces and external systems
High-frequency real-time data updates require interface calls to use short timeout thresholds, preventing long waits that disrupt inquiry experiences. Nested field organization requires precise hierarchy matching when parsing `responseData`, otherwise field missing or parsing errors will occur. Differing update rhythms across multiple data types require external systems to separate caching of real-time and non-real-time data, reducing invalid interface calls. Transit system authentication specifications require use of exclusive interface keys and compliance with the standard `Authorization` format, otherwise authentication failures will be triggered. Fluctuating inquiry volumes during peak hours require interfaces to support reasonable concurrency control, preventing triggering of the operation system’s current limiting rules.

## How to set configurations
| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| `Authorization` | Bearer {exclusive interface key assigned by the transit system} | Complies with standard API authentication requirements of the transit operation system, to avoid invalid token errors |
| `responseData` | Extract route, station, and estimated arrival time fields according to nested hierarchies | Adapts to the nested structure of transit data, ensuring returned content can be correctly invoked |
| Interface timeout period | 5-10 seconds | Aligns with the update rhythm of real-time transit data, preventing long waits that disrupt user inquiry experiences |
| Number of items returned per single request | Top 6-10 items | Limits returned data volume to avoid interface return overload, while covering common user needs for shift and transfer inquiries |
| Context cache duration | 240-300 seconds | Aligns with the update cycle of real-time transit data, reducing the number of repeated interface calls |

## Three common errors
- Phenomenon: The FastGPT interface prompts an invalid token, and interface calls return a 401 status code. Cause: The key configured in `Authorization` has not been registered in the transit system, or the standard format with the Bearer prefix is not used.
- Phenomenon: Interface call results contain large amounts of irrelevant historical passenger flow data, with target route information from user queries missing from fields. Cause: The query range for routes or stations is not limited in request parameters, resulting in return of full transit operation data.
- Phenomenon: Interface calls frequently trigger current limiting, returning a 429 status code. Cause: Reasonable call frequency limits are not set, and high-frequency calls exceed the interface current limiting threshold of the transit system.

## How to confirm configuration is complete
- Call the configured HTTP interface, and check if the returned `responseData` includes expected fields such as route number, station name, and estimated arrival time.
- Send a test request, and verify the interface returns a 200 status code, with no abnormal status codes such as 401 or 429.
- View FastGPT interface call logs, and confirm correct `Authorization` information is carried in the request header.
- Simulate a user initiating a public transit shift inquiry, and confirm returned content matches real-time operation data of the transit system.
