# Municipal Public Transit Service Inquiry and Response: Tool Calling and Plugins

## What this category of data looks like
Municipal public transit service inquiry data primarily originates from transit operation scheduling systems, real-time GPS reporting platforms, and publicly available government service ledgers. Data updates follow two schedules: static information such as routes, stops, and fares is synchronized daily, while dynamic information including real-time arrival times and trip on-time rates refreshes every 30 seconds.

The standard structure of a single data entry includes these fields: route number, full stop name, current stop status, estimated arrival time, fare amount, and operating hours. Route number uses a string format. Estimated arrival time is measured in minutes. Fare amount is denominated in yuan, rounded to two decimal places.

## What Constraints These Characteristics Impose on Tool Calling and Plugin Workflows
The layered update of static and dynamic data requires tool calls to distinguish between static knowledge base and real-time interface call priorities, to avoid returning outdated information. The need for precise matching across multiple fields means tool call parameters must include key identifiers such as route number and stop name; valid results cannot be returned without these. The low-latency requirement for real-time data limits tool call timeout thresholds. Excessive waiting prevents users from accessing the latest transit dynamics. Additionally, the unified field format for transit data requires tool call output to strictly match the preset parameter structure, to avoid query failures caused by format errors.

## How to Configure Settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| toolChoice | `auto` | Allows the system to automatically select whether to call the transit data tool based on user queries |
| functionCall | Enabled | Enforces structured parameter output for tool calls, preventing query failures from non-standard formats |
| Single tool call timeout | 15 seconds | Typical real-time transit interface response times are under 10 seconds; 15 seconds covers network fluctuation scenarios |
| Context window size | 8000–12000 token | Covers key contextual information such as routes, stops, and locations across multi-turn conversations |
| Maximum single tool call return results | Top 10 entries | Reduces excessive redundant information that could disrupt user reading, prioritizing the most relevant routes or stops |
| Pre-query optimization | Enabled | Completes omitted key details such as route numbers and stop names in user queries, improving tool call accuracy |

## Three Common Misconfigurations
- Tool calls return empty results. Cause: `functionCall` is not enabled, or `toolChoice` is not set to `auto`, so the system fails to trigger the transit data tool call logic.
- Tool calls return a 504 timeout status code. Cause: Single tool call timeout is set too short, not matching real-time transit interface response times.
- Tool calls in multi-turn conversations do not inherit prior route information. Cause: The context window is not configured to retain historical tool call parameters, so subsequent queries cannot associate with prior search conditions.

## How to Verify Configurations
- Initiate a query such as "check the current trip of Route 10", and observe whether the system triggers a tool call and returns information including real-time arrival time and estimated arrival duration.
- Navigate to the tool call log page, confirm that the `toolChoice` parameter is set to `auto`, and the parameters output by `functionCall` include valid details such as route number and stop name.
- Simulate a timeout scenario by temporarily setting the single tool call timeout to 5 seconds, then verify that the system triggers fallback logic and returns transit information from the static knowledge base.
- Initiate a multi-turn conversation: first ask "public transit stops near the current location", then ask "the next trip from that stop", and confirm that the tool call successfully inherits the prior location information.
