# Municipal Water Services Inquiry and Response: HTTP Interfaces and External Systems

## What this category of data looks like
Water service inquiry and response data comes from internal customer service systems of water utilities, work orders transferred from government service hotlines, and offline window inquiry ledgers. Data is synchronized incrementally on an hourly basis. Each data entry includes inquiry subject content, submission time, inquiry channel, processing status, completion result, affiliated water supply district code, and inquiry type tag. The district code is a 6-digit numeric string. Inquiry types are fixed into four categories: water outage, payment, water quality, and pipe network maintenance. All user contact information is desensitized.

## Constraints Imposed by Data Characteristics on HTTP Interfaces and External Systems
The data uses fixed-format 6-digit district codes. HTTP interfaces must support filtering results by district code as a request parameter. If not, cross-district redundant inquiry data will be returned. This increases processing costs for external systems.
Data is synchronized incrementally every hour. Set the interface polling interval to 30 minutes or longer. This avoids frequent requests that trigger water utility system rate limits.
Inquiry types are fixed to four categories. Corresponding fields in returned `responseData` must match preset values exactly. External systems must set up verification rules ahead of time.
The data includes desensitized user information. The interface must return desensitized fields. External systems do not need extra processing of user privacy data.

## How to Configure Settings
| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| Request Authentication | Fill the `Authorization` field with the API key provided by the water utility system | Complies with the authentication specifications of the water utility system's external interfaces, ensuring data access security |
| Data Filtering Parameters | Filter by district code and inquiry type | Matches the field characteristics of water utility inquiry data, reducing the volume of returned data |
| Polling Interval | 30–60 minutes | Matches the hourly incremental synchronization rhythm of water utility data, avoiding rate limiting triggers |
| Interface Timeout | 10 seconds | Adapts to the typical response duration of water utility system interfaces, preventing long waits from blocking external processes |
| Response Data Extraction | Extract core fields from `responseData` | Only retain inquiry content, processing status and other information required by external systems, simplifying processing logic |
| Variable Passing | Pass the current inquiry's district code via `variables` | Allows FastGPT to accurately match inquiry data for the corresponding water utility district when calling the interface |

## Three Common Misconfigurations
- A 401 Unauthorized status code is returned when calling the interface. The error persists after confirming the `Authorization` field is filled correctly. The cause is that the water utility system's API key requires binding to a specified IP whitelist. The IP of the FastGPT deployment node is not configured, leading to authentication failure.
- The number of inquiries returned by the interface does not match preset filtering conditions. For example, cross-district data is still returned even after setting a district code filter. The cause is that the district code was not passed correctly as a request parameter, or the parameter format does not meet the water utility system's requirements.
- Interface calls continue to time out and data cannot be retrieved. The cause is that the polling interval is set too short. Frequent requests trigger the water utility system's rate limiting rules, causing interface response delays to exceed the preset duration.

## How to Confirm the Configuration is Complete
- Manually call the configured HTTP interface. Check if the returned `responseData` includes the preset district code and inquiry type fields, and if the field formats comply with the water utility system's specifications.
- Wait for one full polling cycle. Check if the inquiry data received by the external system matches the preset filtering conditions, with no redundant or missing data.
- Check the interface call logs in FastGPT v4.17.0. Confirm that the `Authorization` field is correctly carried, and there are no authentication-related errors.
- Simulate an abnormal data return from the water utility system interface. Verify whether the external system can correctly capture and handle the abnormal response.
