# Urban Gas Service Consultation and Reply: HTTP Interfaces and External Systems

## What this category of data looks like
Data for urban gas service consultation and reply originates from gas service hotlines, archived inquiries from online service halls, registration ledgers from offline service windows, and gas-related requests transferred from the 12345 citizen hotline. Data synchronizes to the system immediately after a single request is resolved. Each synchronization batch includes 10 to 50 archived records. The structure of a single record includes request ID, user desensitized mobile phone number, request type (such as account opening, payment, repair, safety inspection appointment, etc.), processing progress, official reply content, handling outlet address and contact phone number. For field units: request ID uses string format, processing progress uses enumerated values, reply content uses rich text format, and processing time is measured in hours.

## What constraints these characteristics impose on HTTP interfaces and external systems
First, the data contains user desensitized information and business-sensitive content. Interface transmission must carry a valid service token via the `Authorization` parameter to prevent unauthorized access and data leaks.
Second, there are over ten distinct request type scenarios. Interface requests must pass the `variables` parameter to deliver classification filter conditions, ensuring returned results match business requirements.
Third, data updates use batch synchronization after request resolution. Interface request frequency and cache duration must match the synchronization cycle to avoid service overload from frequent calls.
Fourth, some fields contain gas industry-specific terminology and compliance content. The `responseData` returned by the interface must retain the original field format to avoid parsing errors that disrupt subsequent business processing.
Additionally, some consultation data links to offline handling fee information. The interface must desensitize sensitive fee fields to ensure data compliance when called by external systems.

## How to set configurations

| Request header token | Bearer {Enterprise Service Token} | Uses the `Authorization` parameter to secure interface access permissions, complies with government service data security specifications |
| Request variable mapping | Map according to gas request classification | Matches the `variables` parameter rules, ensures the interface returns service consultation data for the corresponding classification |
| Response data filtering | Retain request ID, request type, and reply content fields | Filters desensitized information and sensitive fields, meets external system data usage requirements |
| Retry count | 2-3 times | Addresses temporary request failures caused by network fluctuations, avoids exceeding service current limiting thresholds from repeated calls |
| Cache duration | 15-30 minutes | Matches the synchronization cycle of gas service data, reduces resource consumption from repeated interface calls |

## Three common configuration mistakes
- Symptom: An upgrade prompt error returns when executing a curl command to call the interface. Cause: The interface path and parameter format compatible with FastGPT v4.17.0 are not used. Older version configurations cannot match the current service logic.
- Symptom: The `responseData` field returned by the interface lacks processing progress information for gas requests. Cause: Correct business field mapping rules are not configured in the `variables` parameter, and progress status parameters unique to gas service handling are not included.
- Symptom: The associated database query returns the "column vector does not exist" error. Cause: The vector extension initialization script for gas consultation data has not been executed in the associated PostgreSQL database, resulting in the vector field not being created correctly.

## How to confirm the configuration is complete
- Execute a curl command matching the current configuration, check that the interface returns a 200 OK status code.
- Verify that the `responseData` returned by the interface includes the preset core fields for gas service consultations.
- Simulate submission of different types of gas requests, check that the `variables` parameter correctly filters results for the corresponding classification.
- Call the interface three times consecutively, check that no abnormal errors trigger when the retry mechanism activates, and that returned results are consistent.
