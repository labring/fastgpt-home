# Municipal Gas Service Inquiries and Responses: Tool Calling and Plugins

## What This Category of Data Looks Like
Data for municipal gas service inquiries and responses primarily comes from local municipal gas operation and management platforms, offline service filing systems of gas companies, and customer service ticket databases. There are two update schedules:
Daily sync of daily service progress and ticket status at midnight. Statuses for real-time operations such as payment and new service connection are pushed after same-day completion.
Data documents use structured formats. Core fields include service item ID, item name, processing stage, estimated completion time (measured in days), required submission material list, and contact information for processing windows. Different city gas companies have slight differences in field naming, with no unified standard format.

## Constraints Imposed by These Characteristics on Tool Calling and Plugin Workflows
Variations in data field names across gas companies require configured field mapping rules for tool calling, to adapt to different data source formats. The dual update rhythm of data requires plugins to support both scheduled batch pulling and real-time callback data synchronization, to avoid information lag.
Inquiries about gas services mostly revolve around fixed service items. Tool calling must accurately match keywords to trigger corresponding tools, preventing irrelevant tool recall. Additionally, material lists use array formatting, so tool calling must correctly parse array content to avoid missing or incorrectly splicing material information.

## Configuration Settings
These configurations are based on the plugin and tool calling features of FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapts to multi-type gas service inquiries, automatically selects matching tools for invocation |
| `functionCall` | Call the top 3 tools sorted by match score | The number of gas service-related tools is limited; prioritizing the highest-match tools reduces context overhead |
| Tool calling timeout | `600 seconds` | Gas service data interfaces typically have long response times; prevents early termination of calls that causes missing data |
| Tool recall limit | Top 5 entries | The number of tools in gas service inquiry scenarios is small; excessive recall increases context burden |
| Real-time data sync interval | Once daily | Daily updates apply to gas service data; high-frequency sync provides no practical value |
| Material matching threshold | `0.85–0.90` | Gas service material requirements follow fixed formats; a higher matching threshold prevents incorrect material recommendations |

## Three Common Misconfigurations
- Empty material list fields returned after tool calling: This occurs when the material list field in gas service data is not correctly mapped, leading to missing array-formatted content during parsing.
- 504 timeout status code returned by tool calling: This happens when the set timeout period is shorter than the actual response time of the gas interface, failing to adapt to the data interface characteristics of this category.
- Interactive nodes unresponsive, unable to receive supplementary service item information from users: This is caused by not configuring interactive trigger rules for tool calling, preventing the subsequent information collection process from being triggered.

## How to Verify Proper Configuration
- Initiate an inquiry such as "What materials are needed for gas new connection?" Check if the tool returns the corresponding structured material list and processing stage information.
- Review plugin operation logs to confirm that the tool calling timeout setting matches the configured value, with no records of early-terminated calls.
- Test inquiries using different keywords such as "gas property transfer" and "gas payment" to check that the number of recalled tools does not exceed the configured limit.
- Manually trigger a data sync to confirm that the plugin completes data updates at the set interval, with no abnormal error reports.

The values given are common starting points and should be measured against the reader's own samples.
