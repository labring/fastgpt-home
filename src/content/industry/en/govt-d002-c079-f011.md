# Urban Gas Service Inquiries and Responses: Forms and Interactions

## What the data for this category looks like
Data for urban gas service inquiries and responses mainly comes from municipal gas company operation management systems, pipeline network operation platforms, user payment archives, and work order databases for installation, repair, and complaint handling. Data covers user basic information, gas usage addresses, payment records, fault work orders, and more. Update frequencies include real-time (work order status, payment confirmation), daily (gas usage statistics), and monthly (pipeline network inspection data).

The document structure primarily uses structured fields, including gas account number, user name, gas usage type, fault type, and other fields. Some fields have associated units: cubic meters for gas volume, yuan for payment amounts. Unstructured inquiry description text is also included.

## What constraints these characteristics impose on the forms and interactions link
The uniqueness requirement of structured fields means forms must include mandatory validation and format validation to prevent invalid submissions. Real-time updated work order data requires real-time pull logic in the interaction link to ensure returned inquiry answers match current statuses. Multiple inquiry scenarios require forms to preset common options to reduce the effort of unstructured user input. Fields with units need consistent unit prompts in interactions to prevent submission errors caused by unit confusion.

Additionally, gas service involves user privacy information. Forms must include data encryption interaction constraints to protect user information security.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `formInput` | Add 10-digit format validation, limit input length to 12 characters | Urban gas account numbers use a 10-digit format, which filters invalid inputs |
| `userSelect` | Preset 6 scenario options covering installation, repair, payment, policy inquiry, account transfer, and gas outage notice | Core service inquiry scenarios for this category are concentrated here, reducing user input barriers |
| Form prompts | Fixed prompt "Please enter your 10-digit gas account number and specific inquiry content" | Clearly guide users to provide required unique identifiers and scenario information |
| Interaction timeout setting | 15-20 seconds | Most gas service data is pulled from local systems, this timeout prevents excessive user waiting |
| Number of results displayed | Top 3 matching results | Answers to urban gas inquiries are mostly concentrated in common questions, a small number of results improves reading efficiency |
| Global variable assignment | Calibrated based on actual testing | Interface parameters of gas systems vary across enterprises, adjustments must be made based on actual docking conditions |

## Three common mistakes
- Phenomenon: Configured `formInput` component fails to display in conversations, interaction elements are blank. Cause: The form trigger node is not associated in the workflow, or the conversation context synchronization configuration is not enabled.
- Phenomenon: After enabling voice function, the application end cannot complete voice-to-text output. Cause: The global switch for voice input is not enabled in the configuration, or associated parameters for speech recognition are not configured.
- Phenomenon: No staff contact follow-up after submitting the form. Cause: The message push node after form submission is not configured, or the enterprise WeChat receiving interface is not associated.
- Phenomenon: Unable to specify the target knowledge base via global variable assignment. Cause: The global variable assignment code is not written in the required format, or the correct identifier of the corresponding urban gas knowledge base is not bound.
