# Urban Investment Platform Service Consultation and Reply: Workflow Orchestration

## What this category of data looks like
Service consultation data for urban investment platforms mainly comes from offline window registration, consultation tickets submitted via online government service platforms, policy consultation ledgers, and public documents. Data update rhythm varies by business scenario: real-time consultation tickets update immediately upon submission, policy documents sync at release time, and daily processing ledgers are summarized and archived each day. The document structure includes fields such as consultation subject identifier, original consultation content, processing stage nodes, official reply standards, and completion time limit identifier. Core units for fields are items, hours, and days.

## What constraints do these characteristics impose on workflow orchestration
Multi-source mixed data structures require workflow orchestration to support input formats for both structured ticket text and unstructured policy documents, to avoid classification bias caused by single-format adaptation. Real-time updated consultation data requires the workflow's `variables` node to dynamically pull the latest policy standards and processing ledgers, to prevent delayed reply content. The processing progress nodes included in fields require the workflow to configure transfer branches by stage, matching the full process nodes of window registration, preliminary review, reply, and completion. Differences in field weights across consultation types require the workflow's question classification node to be adjusted for business tags specific to the urban investment sector, complying with FastGPT v4.17.0 workflow orchestration specifications.

## Three common mistakes
- Symptom: External defined variables cannot be accessed inside a loop, with empty fields displayed during runtime. Cause: Global variable inheritance for the loop was not enabled, restricting the node's scope to inside the loop.
- Symptom: When historical records are included in code run node input, the interface shows a validation failure and cannot save the configuration. Cause: Historical records contain long text or unfiltered unstructured fields, triggering input validation rules for v4.8.14 and later versions.
- Symptom: After deploying the local open-source edition, business interface calls fail with permission errors returned. Cause: Environment variables were not configured using `fastgpt` and `fastgpt-` prefixes respectively, leading to incorrect service permission binding.

## How to confirm the configuration is correct
- Initiate a simulated consultation in the urban investment sector, verify that the workflow's automatic classification result matches the preset business tags.
- Call an externally defined `variables` parameter inside the loop node, confirm that the parameter can be read normally.
- Paste test input containing historical records into the code run node, confirm that the configuration can be saved normally without errors.
- View the environment variable configuration page, confirm that variables with `fastgpt` and `fastgpt-` prefixes have been correctly bound.
