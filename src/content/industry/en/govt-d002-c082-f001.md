# Basic Telecommunications Operations Inquiry and Response: HTTP Interfaces and External Systems

## What this category of data looks like
Basic telecommunications operations inquiry and response data has four primary sources: operator official hotline transcripts, offline service window work orders, official website online messages, and dedicated government and enterprise customer inquiry channels.
Full data synchronization runs every hour. Urgent work orders are pushed in real time.
Each data document includes six fields: desensitized user identifier, inquiry type, inquiry details, official response content, processing progress, and user feedback.
Inquiry duration is measured in seconds. Work order numbers use string format. Processing status is marked with enum values.

## What constraints these characteristics impose on HTTP interfaces and external systems
Multiple data sources require interfaces to support batch pulling of inquiry data across different channels, and compatibility with varied request parameter formats.
Real-time update features require interface timeout settings to adapt to longer business processing cycles, to avoid data synchronization interruptions due to timeout.
The special number and type of fields require interface request parameters to strictly map to basic telecommunications exclusive business fields. Otherwise, inquiry types and processing status cannot be correctly identified.
Desensitization requirements for user identifiers require corresponding data filtering rules during interface transmission and storage, to prevent sensitive information leaks.

## How to configure
This document applies to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {carrier internal API key}` | External interfaces for basic telecommunications operations require enterprise-level authentication to prevent unauthorized access |
| `variables` | `{"biz_type": ["package inquiry", "fault repair", "bill inquiry"]}` | Match core categories of basic telecommunications inquiry services, narrow search scope |
| `responseData` | `Only return inquiry details, official response content, processing status` | Filter redundant fields, reduce interface transmission overhead, focus on core business data |
| Request timeout | `600 seconds` | Adapt to longer processing cycles of some basic telecommunications work orders, avoid early request interruption |
| Field mapping rules | Calibrate based on actual testing | Basic telecommunications business fields differ from general RAG fields, need to match exclusive field names of local systems |

## Three common configuration mistakes
- A 403 Forbidden error occurs when calling the interface. Cause: The `Authorization` parameter is not configured correctly, and an invalid carrier internal API key is used.
- A 500 Internal Server Error occurs when calling the `/api/core/dataset/update` interface. Cause: Request parameters are not mapped according to basic telecommunications business fields, causing the system to fail to parse the business type field.
- A locally deployed model tests normally via oneAPI, but FastGPT returns a 404 error. Cause: The interface address is not correctly bound in FastGPT's external system configuration, or the interface path has spelling errors.

## How to confirm the configuration is correct
- Call the test interface, check if the returned `responseData` contains the expected inquiry details, official response content, and processing status fields.
- View authentication logs to confirm the `Authorization` parameter is correctly carried and verified.
- Trigger the data synchronization task, confirm the interface can pull the latest basic telecommunications inquiry and response data.
- Simulate a user inquiry request, check if the returned result matches basic telecommunications business rules.
