# Infrastructure Construction Inquiry and Response: Workflow Orchestration

## What this category of data looks like
The inquiry and response data for infrastructure construction mainly comes from project initiation approval documents, construction logs, supervision acceptance reports, and bidding record materials. The data update frequency changes with the project phase: weekly updates during the initiation phase, daily updates during the construction phase, and milestone-triggered updates during the acceptance phase. The document structure includes fields such as project number, section scope, construction milestone, approval status, and rectification requirements. Units include meters, cubic meters, workdays, ten thousand yuan, and some documents include construction site coordinates and on-site image attachments.

## What constraints these characteristics impose on the workflow orchestration link
Varying update frequencies across data sources require configuring differentiated trigger timing for different workflow nodes. The presence of multiple fields and specific units requires adding field validation steps during orchestration to ensure extracted construction milestones and construction quantity data meet format requirements. Storage format and size limits for on-site image attachments require workflow nodes to adapt to BLOB object transfer and export. Dispersed data source links require clearly defining the project ID in `variables` as a global parameter to avoid cross-node data misalignment. Additionally, some data sources include unstructured on-site images, which require separate node configuration to avoid occupying execution resources of general text nodes.

The following configurations are based on FastGPT v4.17.0.

## How to set the configurations

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Global Variables | Define `variables` as project ID and section code | Serve as the core business identifier shared across nodes to unify the data link |
| Tool Call Trigger Rules | Trigger based on construction milestone status | Adapt to the differentiated update frequencies of data sources in different project phases |
| Timeout Threshold | 600–1200 seconds | Adapt to the parsing and transmission duration of large construction documents and image attachments |
| Field Validation Rules | Match preset units and field formats | Ensure extracted construction quantity and construction location data meet business requirements |
| Attachment Export Configuration | Enable BLOB object transfer | Support dialog download functions for attachments such as on-site images |
| `nodeId` | Bind unique identifiers for each data source node | Avoid workflow node call misalignment and ensure correct data link |

## Three Common Mistakes
- Workflows cannot automatically trigger tool calls and only execute in a fixed linear sequence. This occurs because tool call trigger rules are not configured, only sequentially executed nodes are bound, and the model cannot independently select call links based on business status.
- DingTalk webhook node calls fail with a 403 status code. This happens because a project-specific webhook secret is not configured in the workflow, and notification permissions for the corresponding section are not bound.
- The dialog box cannot download BLOB-format on-site images, and there is no response after clicking. This occurs because BLOB object transfer configuration is not enabled in the attachment export node, and image data is not correctly mapped to the dialog box download interface.

## How to Confirm the Configuration is Correct
- Trigger a test project node status change, and check whether the workflow calls the corresponding data source node according to the configured rules.
- Call the DingTalk webhook node, and check whether the returned result contains the correct content for project notifications.
- Upload a test BLOB-format image, click download in the dialog box, and confirm that the file can be obtained normally.
- View the workflow log, and confirm that the project ID in `variables` and the node data bound to `nodeId` have no misalignment.
