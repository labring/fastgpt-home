# Work Consultation and Response for Construction Machinery: HTTP Interfaces and External Systems

## What the data for this category looks like
Work consultation data for construction machinery mainly comes from operating condition data collected by on-board sensors, factory maintenance archives, and on-site operation and maintenance work orders. Data sources include remote operation and maintenance platforms, enterprise ERP systems, and monitoring terminals built into equipment. Operating condition data is updated in real time or every 10 seconds. Maintenance and work order data is updated after a single task is completed. The document structure includes fields such as unique equipment identifier, cumulative operating duration, current load percentage, fault code, and last maintenance time. The unit of operating duration is hours. Load is a percentage value. Fault codes use the standard format of letters plus four digits. This document is written based on FastGPT v4.17.0.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
The high-frequency updates of real-time operating condition data require that the interface request interval does not exceed 10 seconds. Otherwise, the latest work consultation basis cannot be obtained. The strict format requirements for equipment IDs and fault codes mean that interface input parameters must undergo format verification to avoid invalid requests. When splicing data from multiple sources, operating condition, maintenance, and work order data must be associated by the unique equipment identifier. The interface return must include complete associated fields, otherwise accurate responses cannot be generated. Some older equipment has missing fields in sensor data. The interface must support empty field returns to avoid call interruptions.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Interface request timeout | 600 seconds | Matches the average response duration for multi-source data association in construction machinery, avoids early request termination |
| Input parameter format verification switch | Enabled | Prevents requests that do not comply with equipment ID and fault code formats from entering the system |
| Single interface return data limit | Top 20 entries | Adapts to the volume of historical work orders and operating condition data associated with a single device, avoids overload of returned content |
| `Authorization` | Fill in according to enterprise internal API gateway rules | Complies with identity verification requirements of external systems, ensures data transmission security |
| Response data parsing rule | Associate local knowledge base by equipment ID field | Quickly matches work consultation knowledge base content corresponding to the equipment |

## Three common mistakes
- Symptom: Interface returns status code 400, and logs show input parameter format error. Cause: No verification of the standard format for equipment IDs and fault codes, and non-standard parameters are passed directly.
- Symptom: Work consultation response content does not match actual equipment operating conditions, and the number of results is insufficient. Cause: Interface request interval exceeds 10 seconds, latest operating condition data is not obtained, and a reasonable return data limit is not configured.
- Symptom: Interface call times out, and the system returns an empty response. Cause: No reasonable timeout time is set, or missing fields of older equipment are not supported, leading to parsing failure and subsequent timeout.

## How to confirm the configuration is complete
- Send a test request that complies with the standard format of equipment ID and fault code, check whether the interface return status code is normal.
- Compare the interface return data with locally stored equipment data, confirm that the associated fields are complete and have the correct format.
- Simulate the field missing scenario of older equipment, check whether the interface can normally generate compatible response content.
- Send test requests at 5-second intervals continuously, check whether the interface response is stable and free of abnormalities.
