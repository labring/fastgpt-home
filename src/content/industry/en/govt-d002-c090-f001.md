# Work Consultation and Reply for Refined Oil Sales: HTTP Interfaces and External Systems

## What data for this category looks like
Refined oil sales work consultation and reply data mainly comes from gas station POS systems, fuel card management systems, customer service ticket systems, and oil price public announcement platforms.
Two update schedules apply. Real-time data includes fuel card balances, order statuses, and real-time consultation requests, which sync every second. Non-real-time data includes same-day oil prices and promotional activity information, which updates once daily.
The data document structure includes fields such as consultation ID, service station code, user identity identifier, consultation type enumeration, request content, response content, request time, and processing status. Station codes are 6-digit numeric strings. Balance units are yuan. Oil price units are yuan per liter.

## What constraints these characteristics impose on HTTP interfaces and external systems
Since data includes real-time fuel card balances and order statuses, HTTP interface response latency must align with business scenarios to avoid excessive waiting times.
Consultation types use fixed enumeration values. Interface request parameters must match preset enumerations, otherwise a clear error is returned.
Some consultations support voice input. Interfaces must support passing base64-encoded voice files or valid URLs in `variables`.
Multi-system data sources require interfaces to carry valid authentication tokens via the `Authorization` header to verify call legitimacy.
Daily updated oil price data requires interfaces to support cache configuration to reduce request pressure on upstream systems.

## How to set configurations
These configuration items are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {gas station-specific service key}` | Authentication requirement for connecting to internal gas station systems, ensuring interface call legitimacy |
| `variables` | `{"stationId": "6-digit numeric code", "queryType": "enumeration value", "voiceFile": "base64 string or URL", "maxWait": "30 seconds"}` | Matches business parameter format for refined oil sales consultations, passing station information, consultation type, voice file, and timeout limit |
| `responseData` | `{"code": 200, "msg": "Processing completed", "data": {"replyText": "string", "cardBalance": "yuan", "oilPrice": "yuan per liter"}}` | Adapts to structured data format returned by gas station systems, facilitating subsequent content extraction and display |
| Voice service API address | `https://minmax-tts.example.com/v1/synthesize` | Adapts to call format of third-party speech synthesis services, meeting reply requirements for voice consultations |
| Interface retry settings | `2 times`, interval `1000 milliseconds` | Addresses temporary fluctuations in gas station systems, reducing call failures caused by short-term network issues |
| Response data cache | `5 minutes`, only caches oil price query requests | Avoids frequent requests to upstream oil price systems, reducing interface call pressure |

## Three common mistakes
- Symptom: File type variable transfer fails during interface calls, returning `400 Bad Request`. Cause: Voice file base64 encoding or valid URL is not passed in `variables` as required, so the interface cannot recognize the file parameter.
- Symptom: Incorrect `Authorization` format from outdated distribution interfaces is used during authentication configuration, returning `401 Unauthorized`. Cause: Gas station-specific service key is not used as the authentication token, and authentication rules from other scenarios are followed instead.
- Symptom: Core business fields in returned `responseData` are empty after calls. Cause: The return data structure of gas station systems is not matched, and parsing rules for `responseData` are not correctly specified.

## How to confirm configurations are complete
- Call the test interface, pass valid station ID and consultation type, check if expected business fields are included in returned results.
- View interface call logs, confirm that the token format carried in the `Authorization` header meets requirements, with no authentication-related errors.
- Upload a test voice file, confirm that voice parameters in `variables` are correctly parsed, with no parameter missing errors.
- Simulate temporary network fluctuations, check if the interface performs retries according to configured retry times, with no direct call failures.
