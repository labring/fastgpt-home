# Service Inquiry and Reply for Refined Oil Sales: Workflow Orchestration

## What the data for this category looks like
Service inquiry data for refined oil sales mainly comes from gas station POS transaction systems, inventory management systems, and fuel card member systems. Data update rhythms are divided into two categories: real-time and scheduled. Real-time transaction data is generated immediately after a user completes refueling. Daily inventory checking data is updated after the day's business ends. The document structure includes three core document types: transaction records, inventory details, and member consumption records. Fields include fuel nozzle number, fuel grade (e.g., 92#, 95#), fuel volume (unit: liters), actual received amount (unit: yuan), transaction timestamp, member card number, inventory remaining volume (unit: liters), and all fields are bound with clear business units and value ranges. The configuration instructions on this page are based on FastGPT v4.17.0.

## What constraints these characteristics impose on workflow orchestration
The immediacy of real-time transaction data requires workflow nodes to support fast pulling of latest data, avoiding excessive delays that affect inquiry response. The scattered nature of multi-system data sources requires the workflow to be configured with cross-system data aggregation nodes, ensuring that consultation can retrieve transaction, inventory and member information simultaneously. The field unit binding characteristic requires the workflow to have built-in unit verification rules, preventing mixing of liters and kilograms, yuan and jiao. The fuel grade standardization requirement requires configuring a field mapping node in the workflow to convert colloquial expressions entered by users (such as "92 octane fuel") into system-recognizable standard grades.

## Three common mistakes
- Phenomenon: "Missing required parameters" error is returned when calling API, or inquiry results are not associated with specified gas station inventory data. Cause: Global variables such as the current fueling outlet ID are not passed into the request body via the `variables` parameter, causing the workflow to fail to filter corresponding data.
- Phenomenon: When consulting the same user's refueling records multiple times in a session, cross-user data confusion appears in the results. Cause: Session-level variable binding to the current user's fuel card number is not configured, resulting in no isolation processing for context data.
- Phenomenon: Status code 504 is returned when pulling daily inventory data, or node execution status shows timeout failure. Cause: The node timeout period is set to more than 60 seconds, which does not match the real-time data return speed of refined oil sales systems.

## How to confirm the configuration is correct
- Execute a simulated API request. Check whether the request body includes the `variables` field and corresponding global variable values, and confirm that parameter transfer is correct.
- Execute two consecutive user inquiries. Review returned results to confirm they only associate the current user's fuel card information, and verify that session-level variable configuration takes effect.
- Trigger a workflow node. Review system logs to confirm data is collected per the set cycle, and that complete node execution data and return results are included.
- Test input of colloquial fuel grades (such as "92 octane fuel"). Confirm that the workflow's field mapping node converts the input into system-recognizable standard grades.
