# Service consultation and reply for new energy development: Workflow orchestration

## What data for this category looks like
The data for this category comes primarily from new energy project service guides on local government service platforms, industry policy documents released by the National Energy Administration, regional new energy project filing archives, and public consultation records. Data updates trigger when industry policies adjust or local service procedures change, with no fixed cycle. Documents are grouped by service stage into modules such as project approval, grid connection, and acceptance. They include fields including item name, handling entity, required material list, handling time limit (unit: working days), and common question classification. Most individual documents range from 800 to 1500 characters in length.

## What constraints these characteristics impose on workflow orchestration
Since data is split by service stage and covers multiple policy dimensions, workflows must split call nodes according to stages such as project approval, grid connection, and acceptance to avoid mixing cross-stage data. Data updates have no fixed cycle, so workflows must configure a trigger node for scheduled data source synchronization to ensure consultation content matches the latest policies. Fields include clear units such as working days. The `variables` in workflows must bind unit verification logic to prevent unit errors in returned results. Individual document lengths vary significantly, so workflows must configure a context length limit node to avoid exceeding model processing limits.

## How to set the configuration
This configuration is formulated based on FastGPT v4.17.0.
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| Scheduled synchronization frequency | Every 3-7 days | Adapts to the feature of non-fixed data update cycles, balances timeliness and system resource usage |
| Context length limit | 8000-12000 characters | Matches the range of individual document lengths and total processing requirements for cross-stage calls |
| `variables` unit verification | Bind working day/calendar day unit rules | Adapts to document structures with clearly defined unit fields |
| Node call order | Trigger in sequence: project approval → grid connection → acceptance | Aligns with the standard service process logic for new energy projects |
| `nodeId` binding | Associate the node ID of the dedicated document library for each stage | Enables precise calling of corresponding data sources by service stage |
| Single recall count | Top 3-5 entries | Adapts to the number of common questions in individual documents, avoids redundant content interference |

## Three common mistakes
- When calling the workflow, the error "Key is error. You need to use the app key rather than the account key" is returned. Cause: The dedicated app key for the workflow application is not used, and the account login secret key is mistakenly used instead.
- Workflow execution takes too long, exceeding reasonable thresholds. Cause: Call nodes are not split by service stage, and full multi-stage document data is loaded in a single call.
- When configuring `variables`, only a small number of optional variables are displayed, and custom service-related fields cannot be added. Cause: FastGPT v4.9.10 or a later version is used, the global variable configuration entry location has been adjusted, and the correct menu is not searched for the entry.

## How to confirm configuration is complete
- Check the running logs of the scheduled synchronization node to confirm that the data source has completed updates according to the set cycle.
- Trigger a test call to verify that the units of returned results match the units of document fields.
- Call the document library for the stage bound to the specified `nodeId` to confirm that only content from the corresponding service stage is returned.
- Verify that the `variables` parameter can normally bind custom service fields, with no missing or abnormal prompts.
