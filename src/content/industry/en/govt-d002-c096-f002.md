# Administrative Inquiry and Response for Non-Ferrous Metal Smelting: Vector Models and Indexes

## What the data for this category looks like
Business data for non-ferrous metal smelting comes from production control system logs, batch quality inspection reports, internal process specifications, administrative inquiry ledgers, and regulatory submission documents.
Update cycles cover three categories: real-time, batch, and scheduled.
Control logs update hourly or per device node.
Quality inspection reports update with each production batch.
Process specifications are revised quarterly.
Inquiry ledgers sync with daily operations.
Document structures vary significantly.
Short entries are single-parameter records, including timestamps, device identifiers, process parameter values, and corresponding units.
Long entries are complete process specifications or batch quality inspection summaries, and do not include percentage-based statistical values.

## What constraints these characteristics impose on vector models and indexes
High-frequency writes from real-time control logs create incremental update pressure on indexes. Adjust configurations to match the processing rhythm of high-frequency data.
Long documents such as complete process specifications have large semantic unit spans. Avoid truncating critical process steps during chunking, as this will harm semantic retrieval accuracy.
Mixed multi-field quality inspection and ledger data require retaining the logical relationship between fields during chunking. Do not split complete business semantics across fields.
Datasets with 100,000 or more batches impose requirements on the batch processing capabilities of indexes. Avoid data loss or retrieval delays caused by improper configuration.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| Chunk Length | 800–1200 characters | Matches the semantic unit length of non-ferrous metal smelting process documents, avoids truncating critical process steps |
| Overlap Length | 100–200 characters | Retains semantic connections between adjacent chunks, prevents breaks in process logic |
| `defaultToken` | 8192 | Matches the context window limit of most embedding models, meets the vectorization requirements of long process documents |
| `maxToken` | 4096 | Limits the length of a single vectorized text, avoids exceeding the processing capacity bounds of the model |
| Similarity Threshold | 0.75–0.85 | Matches the numerical correlation characteristics of smelting parameters, filters low-match irrelevant retrieval results |
| Single Search Limit | Top 10 entries | Balances retrieval efficiency and recall completeness, adapts to dataset sizes of 100,000 or more |

## Three common mistakes
- Phenomenon: After uploading 100,000 CSV-format ledger data entries, the total vectorized data volume is less than the number of source data entries. Cause: Chunk configuration fails to correctly identify null fields in the CSV, or truncates business records with short fields, resulting in partial data not being fully vectorized.
- Phenomenon: Vectorization tasks remain in the indexing state for longer than expected. Cause: Fails to adapt the incremental indexing logic for high-frequency production data, and accidentally triggers repeated full indexing, leading to excessive system resource usage.
- Phenomenon: Vector calculation scores are abnormally high, and multiple retrieval results have identical scores. Cause: The similarity threshold is set too low, and the excessive chunk overlap length causes semantic duplication, making the model unable to distinguish business differences between different chunks.

## How to confirm correct configuration
In FastGPT v4.17.0, import a single 100,000-character process specification document, verify that the number of vectorized chunks matches the configured chunk length.
Upload a batch test dataset, verify that the total vectorized data volume after completion matches the number of entries in the source dataset.
Launch a test inquiry related to smelting parameters, check that the number of retrieved results matches the configured single search limit.
View system vectorization logs, confirm that no text truncation errors caused by the `maxToken` limit appear.
