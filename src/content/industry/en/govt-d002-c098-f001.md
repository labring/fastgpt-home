# Airports: Service Inquiries and Responses — HTTP Interfaces and External Systems

## What data for this category looks like
Airport service inquiry data comes from airport operations management systems, real-time flight platforms, official published inquiry knowledge bases, and historical interaction records from offline inquiry counters.
Data updates follow two patterns. Flight-related inquiry data is synchronized in real time. Announcement-style inquiry content is updated according to official release timelines.
Each inquiry document includes inquiry classification tags, associated business nodes such as check-in, security screening, and baggage claim, standard response text, associated flight number or terminal information, and a last updated timestamp.
Field units use Chinese standard expressions. Flight numbers use a combination of letters and numbers. Time efficiency is marked in minutes.

## Constraints for HTTP interfaces and external systems
Real-time requirements for flight-related data mean HTTP interfaces must use reasonable timeout configurations, to avoid delays that disrupt user inquiry response times.
Multi-source data synchronization needs require interfaces to support parallel calls to data sources from different business systems, while adapting to data formats with varying update frequencies.
Validation rules for associated flight number and terminal fields require interface request parameters to include classification tags or associated identifiers. Without these parameters, matching corresponding knowledge base content is not possible.
Batch pulling offline historical interaction data requires interfaces to support pagination parameters, to adapt to inquiry data synchronization of different scales.
Airport internal network deployment scenarios require interfaces to support internal domain name resolution, to avoid permission issues caused by public network access.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer ${<airport internal API key>}` | Airport internal business interfaces typically use Bearer token authentication to secure interface access |
| Request timeout | `30–60 seconds` | Flight-related inquiry response time requirements prevent excessive delays that harm user experience |
| `variables` | Pass inquiry classification, associated terminal or flight number | Civil aviation inquiry data must be bound to specific business scenarios to accurately match corresponding knowledge base content |
| Pagination limit | `Top 200 entries` | Controls load for a single interface request, matching the typical single synchronization scale for offline historical inquiry data |
| `responseData` | Extract only standard response text and associated identifiers | Only core inquiry content is needed to generate final responses, reducing unnecessary data transmission |
| Internal domain name resolution configuration | Use airport internal DNS addresses | FastGPT servers deployed in internal networks cannot access public networks, so business interfaces must be called via internal domain names |

## Three Common Misconfigurations
- Phenomenon: Interface returns 304 status code. Cause: Airport internal API authentication parameters are not configured correctly, leading to failed cache validation and inability to retrieve the latest inquiry data.
- Phenomenon: Database connection error with "Access denied" prompt. Cause: The internal IP address of the FastGPT server is not added to the airport database whitelist, leading to failed permission validation.
- Phenomenon: Empty inquiry content is returned after calling the interface. Cause: Associated terminal or flight number parameters are not passed via `variables`, so matching knowledge base content for the corresponding scenario is not possible.

## How to Confirm Configurations Are Correct
- Call the configured HTTP interface, pass test inquiry classification and associated parameters, check if the returned `responseData` includes standard response text suitable for civil aviation scenarios.
- Check FastGPT v4.17.0 system logs, confirm that the `Authorization` authentication parameter is correctly carried, with no authentication failure errors.
- Simulate user inquiries in the test environment, trigger interface calls, and verify that returned content matches standard responses from the airport's official knowledge base.
- Test interface timeout trigger logic in the internal network environment, confirm that requests complete responses within the set timeout period.
