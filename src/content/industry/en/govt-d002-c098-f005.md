# Civil Aviation Airport Service Inquiry and Response: Tool Calling and Plugins

## What data this category includes
Civil aviation airport service inquiry data is sourced primarily from official airport operation systems, terminal service manuals, airline collaboration rules, and real-time flight dispatch platforms. Data is grouped by service modules, covering check-in, security screening, baggage drop-off, boarding guidance, special passenger services, and other categories. Each entry contains fields including service name, specific location, operating hours, handling requirements, and contact details for inquiries. Units include hours, meters, pieces, passenger trips, and more. Real-time flight data is updated every 15 minutes. Process rule data is updated following major adjustments or every quarter.

## Constraints imposed on tool calling and plugins
The modular classification of civil aviation airport service inquiry data requires tool calls to match corresponding plugins based on service scenarios. This prevents information confusion from cross-module calls. The high-frequency updates of real-time flight data require strict control of plugin call cache durations, to avoid returning outdated information. The multi-field entry structure requires tool parameters to cover core fields such as service name, location, and operating hours, to ensure complete returned information. Service variations across different terminals require passing a terminal identifier as a required parameter during calls. This avoids returning incorrect venue guidance.

| --- | --- | --- |
| `toolChoice` | `auto` | Meets the automatic triggering needs of multiple types of airport service plugins, no need to manually specify a specific plugin |
| `functionCall` | Enabled | Supports structured transfer of airport service inquiry parameters such as terminal and service type |
| Plugin timeout duration | 15 seconds | Official airport service interfaces have fast response speeds; 15 seconds covers most normal call scenarios |
| Plugin call cache duration | 5–10 minutes | Flight dynamic data has a high update frequency; short cache avoids returning outdated flight information |
| Number of entries returned per plugin call | Top 3 entries | Service inquiries should focus on core guidance; too many entries increase user understanding burden |

## Three common mistakes
- Symptom: Tool call fails with `401 Unauthorized` error after configuring a custom secret key. Cause: The custom secret key was not correctly bound to the airport service plugin call chain, or the secret key was not granted access permissions for the corresponding interface.
- Symptom: When using API calls, the conversation log only shows a preset title with no valid service inquiry result content. Cause: Required fields such as terminal and service type were not passed in the tool call parameters, causing the plugin to fail to match the corresponding data.
- Symptom: After calling 3 or more airport service plugins consecutively, a model call error prompt is returned. Cause: The number of plugin calls per conversation was not limited, causing the context length to exceed the model's supported range.

## How to confirm configuration is complete
- Initiate a test conversation with a clear airport service request, such as "What are the operating hours of the baggage claim area at Terminal 2 of Shanghai Pudong Airport", and check whether structured information from the corresponding module is returned.
- View the tool call log, confirm that `toolChoice` automatically triggers the matching airport service plugin, and that the passed parameters include necessary information such as terminal and service type.
- Simulate consecutive calls to different types of airport service plugins, check for timeouts or authentication errors, and adjust the timeout duration or call count limit as needed.
- Compare the fields returned by the plugin with the official public service manual content of the airport, confirm that returned information such as location and hours matches official data.
