# Work Consulting and Reply for Oil and Gas Exploration and Development: HTTP Interfaces and External Systems

## What this category of data looks like
The work consulting and reply data for oil and gas exploration and development comes mainly from internal exploration and development management systems, geological reserve databases, and drilling engineering log databases. Updates are synchronized in real time or weekly as new drilling is completed, exploration blocks are adjusted, and approval nodes are updated. Each document corresponds to the work process for a single well or single exploration project. It includes well number, exploration horizon, approval node, and associated fields for consulting and reply. Field units follow petroleum industry standards: well depth is measured in meters, reserves in tons, and approval duration in hours.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Data comes from multiple heterogeneous exploration and development management systems. HTTP interfaces must adapt to the identity verification rules of internal systems. The `Authorization` parameter must use the Bearer token format consistent with internal systems.
Fields follow petroleum industry standard units. `responseData` must retain original unit fields. No forced conversion is allowed.
Interfaces that filter data by update time must support passing drilling completion time and approval node update time as query conditions. This adapts to the data update rhythm.
`variables` must support passing well numbers and exploration project IDs as filter parameters. This narrows the data range returned by a single interface call. It also avoids returning excessive associated data.

## How to set up configurations
These configuration items are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer <API key assigned by internal exploration system>` | Adapts to the identity verification rules of internal oil and gas exploration and development systems, ensuring legal interface call permissions |
| `variables` | `{"well_id": "target well number", "update_range": "last 7 days"}` | Narrows the data return range, avoids returning excessive exploration and development associated data in a single call, and meets the precise needs of business queries |
| `responseData` | `Retain original unit fields, no format conversion` | Follows petroleum industry data standards, ensuring downstream systems can directly use unit information in fields without additional conversion |
| Request timeout | `600 seconds` | Adapts to batch data pulling scenarios for exploration and development, avoiding interface call failures due to large data volumes |
| Data classification rule | `Return grouped by well number and approval node` | Matches the business classification logic of oil and gas exploration and development work consulting, making it easier for downstream systems to integrate data by project dimension |

## Three common misconfigurations
- A 400 status code (no body) is returned when calling the API. The `Authorization` parameter is not configured correctly. The internal system cannot verify the interface call permission, so the request is blocked and no content is returned.
- When configuring the `variables` parameter, no well number or exploration project ID is passed. The returned `responseData` contains excessive irrelevant exploration and development data. This leads to excessive processing load on downstream systems.
- An error "Permission denied by system" is prompted when calling the voice input API related to work consulting. The compliance verification switch exclusive to the oil and gas exploration scenario is not enabled in the interface configuration. The business permission requirements are not met.

## How to verify successful configuration
- Call the interface, then check whether the fields returned in `responseData` include petroleum industry standard units. Confirm that no forced conversion has been performed.
- Pass the `variables` parameter, then verify whether the returned data volume matches the expected business query range. Adjust the parameter values until they meet requirements.
- Verify that the format of the `Authorization` parameter matches the requirements of the internal exploration system. Ensure the interface call can pass identity verification normally.
- Simulate a work consulting business scenario. Pass the specified well number or project ID, then confirm that the returned data is associated with the target exploration project's work process.
