# Consulting and Response for Oil and Gas Exploration and Development: Model Access and Configuration

## What the Data for This Category Looks Like
Business data for oil and gas exploration and development originates primarily from exploration physical reports, drilling construction logs, trial production monitoring reports, and reserve assessment documents. Data update rhythms shift based on project phase. Updates follow single-well exploration cycles during pre-exploration phases, and are updated with monthly trial production data during development phases. Individual documents typically include fields such as block number, well ID, operating depth, formation pressure, and fluid composition. Units include meters, megapascals, cubic meters, and mass percentage. Some long documents contain multi-chapter operating parameters and historical monitoring data.

## Constraints Imposed by These Characteristics on Model Access and Configuration
The multi-field, multi-unit professional data used in oil and gas exploration and development requires model access to adapt to professional terminology and unit association logic, to prevent parameter parsing errors. The multi-chapter structure of long documents requires context window configurations to adapt to segmented professional content, avoiding truncation of key operating parameters. Business data updated per project cycle requires knowledge base synchronization mechanisms to match the update rhythms of exploration and development phases. Exclusive data for different well conditions must be tagged to avoid confusion between consulting content for different well conditions.

## How to Set the Configuration
| Configuration Item | Recommended Value Range | Rationale |
|---|---|---|
| `maxContext` | 8000–12000 token | Adapts to multi-chapter content of long oil and gas exploration documents to avoid truncation of key operating parameters |
| `maxTokens` | 2000–3000 token | Meets detailed response requirements for professional consulting and avoids truncation of output content |
| `quoteMaxToken` | 1500–2000 characters | Matches the core paragraph length of a single exploration report to ensure complete and accurate quoted content |
| `temperature` | 0.1–0.3 | Maintains the rigor of professional responses and reduces generation of irrelevant content |
| `AIPROXY_API_ENDPOINT` | Fill in according to the deployment environment | Adapts to the proxy interface configuration of FastGPT v4.17.0 to ensure normal model call access |
| `AIPROXY_API_TOKEN` | Fill in according to the assigned valid key | Completes identity verification for model access and ensures valid and legal call permissions |

## Three Common Misconfigurations
- Inconsistent returned content between the model debugging interface and external access channels. This occurs when the values of `maxContext` and `quoteMaxToken` are not unified, as context window limits differ across environments.
- Identity verification failure error during model testing. This is caused by incorrect entry of `AIPROXY_API_TOKEN` or failure to configure a valid key, which prevents completion of model call authorization.
- Unable to locate the channel option for model configuration. This happens when access permissions for the corresponding model are not enabled in the FastGPT backend, or the proxy interface has not completed basic configuration.

## How to Confirm Successful Configuration
- Enter the model debugging interface, input the core fragment of a single exploration report, check whether the context window loads the complete content normally, and confirm that the configuration parameters match the document length requirements.
- Initiate a professional consulting test, check whether the response content includes accurate professional terms and units, and confirm that the configured rigor aligns with the business scenario.
- Call the external access channel to initiate the same consulting request, compare the returned results from the debugging interface, and confirm that full-link configuration parameters remain consistent.
- View the knowledge base synchronization log, confirm that the data source update mechanism matches the business cycle, and verify that the configured synchronization logic is active.
