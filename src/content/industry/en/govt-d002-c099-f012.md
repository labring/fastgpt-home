# Matter Consultation and Response for Oil and Gas Exploration and Development: Deployment and Upgrade

## What this category of data looks like
Data related to matter consultation and response for oil and gas exploration and development originates from operation compliance documents, matter process guidelines, technical consultation response archives, and on-site operation records. Update frequency varies significantly by document type: compliance documents are updated regularly per regulatory requirements, operation records are synced in real time, and consultation archives are filed monthly. Most documents take the form of multi-chapter technical manuals, structured matter process tables, and job application forms with fields including operation area, well ID, application time, and compliance standards. Common units used are meters, cubic meters, megapascals, and days.

## These characteristics impose constraints during deployment and upgrade
This category of data has clear hot and cold data layering. Real-time well condition data is updated frequently, while static compliance documents have fixed update cycles. A storage strategy separating hot and cold data must be configured during deployment. Documents include structured process tables and long-text technical chapters, so different text parsing and chunking logic must be adapted during upgrades. Most deployments for oil and gas exploration and development scenarios run in internal network environments. Correct port mapping and access permission configuration for internal network services must be ensured during upgrades. Matter consultation data involves operation compliance information, so data encryption storage parameters must be configured during deployment to ensure data security.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 100–150 | Adapts to the concurrent read/write demands of multi-well condition data and matter consultation documents under FastGPT v4.17.0 for this scenario, and prevents database connection exhaustion |
| `MONGODB_URI` | Internal MongoDB instance address with authentication parameters | Stores matter consultation archives and well condition historical data; internal network deployments require specifying internal network addresses and access credentials |
| `REDIS_URL` | Internal Redis instance address, set to 600-second expiration time | Caches frequently accessed matter process documents and compliance standards to reduce database query pressure |
| `STORAGE_S3_ENDPOINT` | Internal object storage service address | Stores large unstructured data such as exploration reports and operation records, adapting to internal network storage requirements |
| `FILE_TOKEN_KEY` | Randomly generated 32-bit string | Used to generate file access tokens, ensuring secure download of matter-related documents |
| `FE_DOMAIN` | Public network/internal network domain name of the deployment node | Configures the frontend access address, adapting to access scenarios after internal or external network mapping |

## Three common configuration errors
- Symptom: Knowledge base indexing tasks remain in a running state with no progress updates. Cause: Database connection pool parameters for the oil and gas exploration and development scenario’s large-volume documents were not adjusted, causing indexing threads to be blocked.
- Symptom: In conversations orchestrated via HTTP requests, the output field is empty, and results cannot be displayed in the conversation interface. Cause: The `REDIS_URL` parameter was not configured correctly, leading to invalidation of conversation context caching and inability to persist output content.
- Symptom: Deployment via Docker fails, with a database connection timeout prompt. Cause: The `MONGODB_URI` was not configured as an internal network database address, and attempts to access an external database resulted in connection failure in the internal network environment.

## How to confirm configuration is correct
- Run the Docker container log viewing command, confirm that there are no error logs for database connection pools and Redis connections, and verify that the configured `DB_MAX_LINK` value matches the connection count in the logs.
- Send a test request for a matter consultation category, confirm that the output field content can be displayed normally in the conversation interface, and verify that the context cache configuration is effective.
- Conduct access tests in both the internal network environment and the external network mapped environment, confirm that the address configured in `FE_DOMAIN` can access the frontend interface normally.
- Run an indexing task, confirm that the indexing progress updates within a reasonable time frame, and verify that the database connection pool parameters adapt to the scenario requirements.

The values provided here are common starting points, and should be evaluated against the reader’s own samples.
