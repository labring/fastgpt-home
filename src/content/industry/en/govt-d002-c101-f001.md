# Port and Shipping Service Inquiry and Response: HTTP Interfaces and External Systems

## What the data for this category looks like
Port and shipping service inquiry and response data mainly comes from port production scheduling systems, port supervision APIs, and internal service knowledge bases of shipping enterprises. Voyage-related data is updated in real time per voyage. Port service policy data is updated temporarily per regulatory requirements. General service guides are synchronized every quarter.
The data uses a structure combining structured fields and unstructured text. Structured fields include voyage number, berth ID, declaration deadline, and document list. Unstructured text includes service process descriptions and common response scripts. Time fields use ISO 8601 format. Berths use numerical numbering. Document counts are counted as integers.

## What constraints these characteristics impose on HTTP interfaces and external systems
The real-time update feature of voyage data requires HTTP interface calls to support low-latency queries, to avoid information lag caused by cache expiration.
The combined structured and unstructured data feature requires interfaces to support both exact field matching and full-text keyword retrieval, to adapt to different types of service inquiry needs.
The irregular update rhythm of policy data requires external systems to dynamically verify the update time returned by the interface, to avoid using expired policy content.
In addition, port service data involves port supervision compliance. Interface requests must carry compliance verification parameters to ensure data interaction meets shipping regulatory requirements.

## How to configure settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Interface authentication configuration | Set to the Bearer token provided by the port platform | Port service interfaces require exclusive token authentication to ensure compliance of data access |
| Request parameter configuration | Bind fixed port code and query type variables in `variables` | Accurately match service data for the corresponding port, avoid confusion of cross-port data |
| Response data processing | Filter entries with update time later than the last synchronization time | Adapt to the real-time update feature of voyage data, reduce invalid data transmission |
| Interface timeout setting | Set to 30 seconds | Port interfaces require a certain amount of time to process scheduling data. Too short a timeout will cause query failures |
| Retry strategy | Retry 2 times after failure, with a 5-second interval | Respond to temporary fluctuations in port interfaces, improve query success rate |

## Three common mistakes
- Phenomenon: The interface returns status code 403, and logs show authentication failure. Cause: The exclusive `Authorization` token provided by the port platform is not used. General authentication configuration is used instead, which fails the compliance verification of the port interface.
- Phenomenon: The query results contain expired voyage information. The berth status field shows occupied but has actually been released. Cause: No configuration for filtering response data by update time. Cached old data is used directly, without adapting to the real-time update feature of voyage data.
- Phenomenon: The number of results returned by a single query is much lower than expected, only 1 to 2 test entries are returned. Cause: The correct query type is not specified in the request parameters, so the interface only returns the default small amount of test content.

## How to confirm the configuration is complete
- Call the configured HTTP interface in FastGPT v4.17.0, pass the test port code and query type, check that the returned `responseData` contains the expected service process descriptions and document lists.
- Compare the update time returned by the interface with the last synchronization time of the local cache, confirm that only entries with update time later than the synchronization time are returned.
- Simulate an authentication failure scenario, check that the interface returns the correct 403 status code, confirm that the authentication configuration takes effect.
- Call the interface three times consecutively, check that the retry strategy takes effect, with no consecutive failures.
