# Port and Shipping Services Inquiry and Reply: Multi-turn Dialogue and Prompt Engineering

## What this category of data looks like
Port and shipping service inquiry and reply data mainly originates from government affairs disclosure platforms under direct maritime administrations, official service guide systems of individual ports, and official announcement documents for port customs clearance. Data updates trigger alongside policy adjustments, with synchronous updates released when new customs policies are launched or port service workflows are optimized. Each document is typically split by service item, with a structure covering fields including item name, handling entity, required materials list, handling process, fee standards, and inquiry channels. Materials are counted in "items", handling time limits in "working days", and fee standards in "yuan/container" or "yuan/ton".

## What constraints do these characteristics impose on the multi-turn dialogue and prompt engineering link
Decentralized data sources mean multi-turn dialogue must retrieve relevant information across multiple data sources including maritime administrations, ports, and customs clearance hubs. Prompts must clearly define the data source scope to prevent confusion. Complex document structures and lengthy individual content require multi-turn dialogue to track the user’s current specific service step, avoiding context mix-ups. Fields include multiple sub-items, so prompts must guide users to clarify specific inquiry dimensions, such as distinguishing between declaration materials and handling time limits. Unfixed update frequencies require multi-turn dialogue to prompt users to confirm the timeliness of current policies in responses, preventing citation of expired information.

## How to Set Configurations
| Configuration Item | Suggested Setting | Rationale |
| --- | --- | --- |
| `chatId` parameter configuration | Fixed session ID | Ensures multi-turn dialogue in the same scenario shares context, avoids resetting conversation status for each session |
| `messages` array configuration | Only retain the most recent 10 turns of dialogue content | Reduces redundant data input, lowers model processing load, improves response speed |
| `variables` field binding | Port code field | Accurately locates exclusive service rules for the corresponding port, avoids policy confusion across ports |
| Maximum context length | 8000–12000 characters | Matches the average length of single chapters of port service documents, avoids truncating key process and material information |
| Single retrieval count | Top 6 entries | Covers relevant items for common service inquiries, avoids information overload |
| Context retention duration | 7200 seconds | Matches the average time required for users to complete a port service, retains context across cross-period dialogues |

## Three Common Misconfigurations
- Obvious dialogue response delay. Cause: Failure to limit single retrieval count, too many long document chunks are passed to the context, increasing model processing time.
- `Unexpected end of JSON input` error. Cause: Incorrect format of the `messages` array passed when calling the model, such as missing closing brackets or containing unescaped special characters, triggering parsing failure during ChatGLM2 model calls.
- Dialogue output results need to be manually opened in the sidebar, and each dialogue requires reinitiating a session. Cause: Incorrect configuration of the `chatId` parameter, failure to enable real-time message rendering, resulting in inability to retain context across sessions.

## How to Confirm the Configuration Is Correct
- Initiate a specific port service inquiry, such as "What materials are required for Ningbo Port export container declaration", check if the main dialog box displays reply content in real time.
- Submit 3 consecutive related questions, such as first asking about declaration materials, then handling time limits, then fee standards, check if the dialogue context is correctly retained without repeating prior information.
- Attempt to pass inquiry content containing special characters, such as "What is the difference between the <packing list> and <bill of lading> required for container declaration", check if a JSON parsing error is triggered.
- View the binding status of `variables` and `chatId` in the configuration panel, confirm that the corresponding port code field has been correctly associated.
