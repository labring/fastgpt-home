# Port and Shipping Inquiries and Responses: Forms and Interactions

## What this category of data looks like
Reference only; verify against the target FastGPT release and deployment documentation.

## Constraints on forms and interactions
The multiple sources and scenario-based update rhythms of port and shipping data require form interactions to support switching field sets by service scenario, to avoid irrelevant fields interfering with user input. Standardized identification fields such as vessel IMO number and berth number require built-in format validation rules in forms to block non-compliant inputs. Real-time updated vessel dynamic data requires the interaction link to display data update times synchronously, preventing users from submitting applications based on outdated information. Enumerated fields such as operation type and customs clearance status need preset standardized options to reduce format inconsistencies caused by free text input.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `formInput` | `800–1200 characters` | Port and shipping inquiry content typically includes vessel information and operation requirements; this length range fits standard inquiry text |
| `userSelect` | `Top 5 entries` | Optional port-related data such as berths and operation types can be quickly browsed and selected within 5 entries, avoiding information overload |
| Data update prompt | `Refresh every 15 seconds` | Matches the update rhythm of vessel dynamic data, timely displaying the latest status for user reference |
| Scene switch trigger | Switch by service type | Different service scenarios (such as berthing application, customs declaration inquiry) correspond to different field sets, improving input efficiency |
| Format validation rules | Calibrated based on actual testing | Port-specific fields such as IMO number and berth number have fixed formats, which need to match actual business specifications |
| Timeout setting | `60 seconds` | Port data queries usually require system integration time; 60 seconds covers most normal query scenarios |

## Three common mistakes
- Phenomenon: A 400 error is returned after form submission, prompting invalid field format. Cause: Format validation rules are not configured for port-specific fields such as IMO number and berth number, resulting in illegal input being submitted.
- Phenomenon: Port operation-related terms cannot be recognized after voice input. Cause: The voice recognition adaptation of `formInput` is not optimized for the port and shipping scenario, and no industry-specific thesaurus is preset.
- Phenomenon: Associated fields are not updated synchronously after selecting an operation type. Cause: The scene switch trigger logic is not bound to the corresponding field set, resulting in asynchronous interaction.

## How to confirm configuration is complete
- Enter a vessel IMO number that complies with port specifications; the validation rule should block inputs with invalid formats, confirming that format validation is active.
- Switch between different service types, confirm that the form field set is updated synchronously, confirming that the scene switch logic works normally.
- Wait for the specified duration, confirm that the data update prompt refreshes the latest vessel dynamic information synchronously, confirming that the update prompt configuration is active.
- Submit a standard service inquiry text, confirm that the returned result matches the input port business scenario, confirming that the interaction logic works normally.
