# Service Inquiry and Response for Refinery and Chemical Production: Workflow Orchestration

## What the data for this category looks like
Refinery and chemical production service inquiry-related data mainly comes from real-time device operation logs, equipment ledgers, process operation specifications, safety inspection records, and internal service approval archives. Real-time operation parameters are updated every 10 seconds. Ledger and specification documents are updated every quarter. Each single data entry includes fields such as equipment number, process parameters, inspection time, approval node, inquiry question, and response content. Pressure is measured in MPa, temperature in ℃, and flow in m³/h. Approval status uses a fixed enumeration value.

## What constraints these characteristics impose on the workflow orchestration step
Reference only; verify against the target FastGPT release and deployment documentation.
Real-time operation parameters update frequently. The workflow must specify the latest timestamp when calling data. Do not use expired parameters.
Fields use fixed units. Configure workflow parameter verification rules to match units such as MPa, ℃, and m³/h. This prevents call failures from parameter type mismatches.
Approval nodes use enumeration values. Configure workflow conditional branch nodes to strictly match defined approval status enumerations. This avoids branch logic errors.
Aggregate multi-source data by associating different data sources with equipment numbers. This prevents data misalignment.

## How to set the configurations
| Configuration Item | Recommended Practice | Rationale |
| ---- | ---- | ---- |
| `variables` | Bind the timestamp field of real-time operation data | Real-time data updates every 10 seconds. Ensure the latest parameters are used for each call |
| `nodeId` | Bind the unique identifier of the data pull node | Ensure the workflow calls the correct node for the specified data source. Avoid cross-node call errors |
| Global variable reference | Preset fixed refinery and chemical process parameters (such as the design pressure of the atmospheric tower at 3.2MPa) | Fixed parameters do not need real-time updates. Simplify repeated configuration processes |
| Node timeout setting | 60 seconds | The average time to pull refinery and chemical data across multiple data sources is 30-50 seconds. Calibrated based on actual measurements |
| Parameter verification rules | Match units such as MPa, ℃, m³/h | Data fields have exclusive units. Verify parameter format validity |
| Context length | 800–1200 characters | Service inquiry questions and response content are usually within 1000 words. Excessive length increases model call load |

## Three Common Mistakes
- The workflow call interface returns `chat:LLM_model_response_empty`. The symptom is an empty response field from the large model node. This happens when no retry mechanism is configured, or the timeout setting is too short. The workflow triggers the model call before data pulling finishes.
- Variable updates do not take effect. The symptom is that parameters bound to `variables` in the workflow do not update with real-time data. This happens when the workflow does not use a timestamp parameter to pull the latest data, and uses cached old values instead.
- Global variables are used incorrectly. The symptom is that referenced global variables do not match the fixed units of the refinery and chemical process. This happens when global variables are set to pure numerical values without units, causing verification failures.

## How to Verify Correct Configuration
- Call the test interface. Check if the returned `variables` parameters include the latest real-time operation data. Verify that the timestamp matches the current time.
- Trigger the workflow. Check the node logs. Confirm that the data source node pointed to by `nodeId` returns the correct process parameters for the corresponding equipment.
- Review the parameter verification rules. Confirm that all refinery-specific unit fields have matching verification logic. No format errors should be present.
- Simulate a large model call. Confirm that the preset retry process triggers when the response is empty. Verify that the exception handling logic works.
