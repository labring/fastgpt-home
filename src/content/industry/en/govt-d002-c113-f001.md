# Shipbuilding Administrative Inquiries and Responses: HTTP Interfaces and External Systems

## What this category of data looks like
Shipbuilding administrative inquiry data comes from three main sources: shipyard production scheduling systems, ship inspection department reporting platforms, and material supply ledgers.
There are two update schedules:
- Production process node data synchronizes in real time
- Ship inspection reporting and qualification review data updates in weekly batches

The document structure includes these fields: unique work order identifier, corresponding ship type model, current process node, original inquiry text, response status, and legal processing time limit.

Field unit rules:
- Work order ID uses pure string format
- Ship type model uses the naming convention of tonnage + ship type
- Processing time limit uses natural days as the unit.

## What constraints these characteristics impose on HTTP Interfaces and External Systems
Real-time synchronization of production process node data requires interface timeout settings to stay under 120 seconds. This avoids disrupting shipyard production workflows.
Batch transmission of ship inspection reporting and qualification review data needs support for pagination query parameters. This adapts to scenarios with large single-transmission data volumes.
The ship type model field uses a fixed enumeration range. Interfaces must align with external system enumeration values in advance, and verify parameter legitimacy to prevent invalid requests.
The legal processing time limit field must strictly map external compliance requirements. Interface return values must retain natural day units, and must not perform unauthorized conversions.
For sensitive data related to ship inspection, interfaces must enable authentication mechanisms. This ensures data transmission security.

## Configuration Settings
This guide applies to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Use the `Bearer ${token}` format, and rotate credentials every 7 days | Shipbuilding data involves production and compliance-sensitive information. Regularly rotating authentication credentials reduces the risk of data leaks |
| `variables` | Configure ship type enumeration values and legal processing time limit thresholds as editable variables | Adapt to differences in administrative processes for different ship types, and avoid increased maintenance costs caused by hardcoding |
| `responseData` | Only return work order ID, ship type model, response status, and processing time limit fields | Reduce invalid data transmission, and adapt to field restrictions of external system interface receivers |
| Timeout Duration | 60–120 seconds | Balance real-time production data synchronization and transmission needs for batch reporting data |
| Single Request Data Volume | No more than 20 entries | Adapt to the batch transmission upper limit for ship inspection reporting data, and avoid interface overload |

## Three Common Misconfigurations
- Interface return results lack contextual association. External systems receive responses that only contain single question-and-answer content, with no associated information from historical administrative inquiries. The cause is failure to configure historical session identification parameters in `variables`, so FastGPT cannot associate contextual data.
- Interface authentication returns 401 status code. Calls fail with an unauthorized prompt. The cause is failure to carry valid authentication credentials in `Authorization` according to specifications, or failure to synchronize credential rotations to external calling systems.
- Timeout occurs when batch fetching ship inspection data. Interfaces return 504 status codes or no response. The cause is that single request data volume exceeds the configured single upper limit, and request batches are not split.

## How to Verify Successful Configuration
- Call the interface with an `Authorization` credential, and check if the return result includes the specified configured fields, with no extra unrelated content.
- Pass test ship type models and work order IDs, and check if the `responseData` return fields fully include the configured mapping items.
- Configure session parameters in `variables`, initiate two consecutive calls, and check if the second response associates with the first inquiry content.
- Initiate a batch request, and check if the number of returned data entries does not exceed the configured single upper limit, with no truncation or overflow.

The values provided here are common starting points, and should be measured against the reader's own samples.
