# Shipbuilding Inquiry and Response: Multi-turn Dialogue and Prompt Words

## What the data for this category looks like
Shipbuilding inquiry data mainly comes from internal work process manuals for shipyards, construction specification documents released by authorized ship classification societies, order management ledgers, and on-site operation and maintenance inquiry records.
There are two update schedules: process documents are updated quarterly alongside industry specification revisions, while order and inquiry data is updated daily.
Most documents use structured forms and chapter-by-chapter guides, including fields such as application number, ship type parameters, construction cycle, approval time limit. Units include deadweight tons, meters, working days, and other standard units.

## Constraints on multi-turn dialogue and prompt configuration
Shipbuilding inquiry data includes structured professional parameters and unstructured process guides. Multi-turn dialogue must distinguish between two scenarios: parameter queries and process inquiries. Prompts need to clearly trigger different matching logic.
Frequently updated order and inquiry data requires that only valid information from the past 7 days is retained in dialogue context. This prevents referencing expired data.
Fields include professional units such as deadweight tons and meters. Prompts must enforce matching corresponding units in returned results to avoid parameter confusion.
Ship classification society specifications serve as authoritative references. Multi-turn dialogue must prioritize retrieving corresponding document fragments to support responses, ensuring content compliance.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Generate a unique identifier for each independent service staff. Use a `32-bit random string` | Isolate historical conversation records across different users, prevent cross-user access to session content |
| `messages` | Limit context to the first 15 dialogues or total token count not exceeding `6000–8000 token`. Calibrate based on actual testing | Shipbuilding inquiries often contain long parameters and process descriptions. Overly long context can cause model logic confusion. Limiting length improves response accuracy |
| `variables` | Pre-set variables including ship type, deadweight tonnage, approval time limit, ship classification society specification number | Match professional fields in shipbuilding inquiry services, quickly populate scenario-specific parameters |
| Maximum context retention duration | `7 days` | Order and process information for service inquiries is updated frequently. Expired data will interfere with current query results |
| Single retrieval upper limit | `Top 5 matching documents` | Professional shipbuilding documents have lengthy content. Excessive retrieval will cause context overload |

## Three Common Misconfigurations
- Issue: When calling via API, binding `chatId` only allows retrieval of conversation records initiated via the API. Historical sessions from the web interface cannot be viewed. Cause: The `chatId` identifier of the web session was not included in the API request, causing the session isolation logic to fail.
- Issue: In the API response record preview, the Human field is empty. Cause: The `messages` parameter was not populated correctly with user input content, or the parameter format did not meet requirements. The model cannot recognize historical user input.
- Issue: The custom-connected dialog box cannot generate scenario-appropriate inquiry responses. Cause: The standardized multi-turn dialogue interface was not called, and corresponding `variables` professional variables were not bound. Responses lack professional support for shipbuilding scenarios.

## How to Verify Proper Configuration
- Initiate API conversations for two different users. Use distinct `chatId` values for each. Confirm that each user can only view their own historical conversation records.
- Input inquiry content containing professional parameters. Confirm that the context window does not exceed the preset length limit and does not include expired data.
- Pass preset `variables` when calling the interface. Confirm that the response correctly matches professional shipbuilding fields and units.
- Check the `messages` parameter in the API response. Confirm that the Human field has been correctly populated with user input content.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
