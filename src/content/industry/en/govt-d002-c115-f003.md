# Inquiry handling and response for rail transit equipment: multi-turn dialogue and prompt engineering

## What this category of data looks like
Rail transit equipment inquiry data comes from three main sources: original equipment manufacturer official technical manuals, railway operation and maintenance department maintenance procedures, and component supplier maintenance documents. The data covers fault codes, maintenance processes, component parameters and other content for locomotives, EMUs, and urban rail vehicles. Teams organize data by train model. Individual documents can reach over ten thousand characters in length. Fields include train model number, fault code, component model, maintenance man-hours, and safety operation specifications. Units include millimeters, hours, times and others. The system updates full data synchronously when new train models launch. It refreshes partial content quarterly when daily operation and maintenance specifications change.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
Rail transit equipment data is organized by train model with clear fields. Multi-turn dialogue must confirm the specific train model used by the user in the initial stage. Otherwise, the system cannot accurately match corresponding documents. Fault codes follow strict numbering rules. Prompts must consistently require users to provide standard fault codes. This prevents the system from retrieving irrelevant content due to vague queries. Document update frequencies vary. The knowledge base must synchronize new train model data and daily operation and maintenance specifications in batches. Multi-turn dialogue context must not include expired train model parameters. Individual documents are lengthy. The system must limit the amount of content retrieved in the context window. This avoids redundant data interfering with dialogue logic.

## Three common misconfigurations
- Symptom: Different users see identical dialogue records after logging in, and cannot view their own historical conversations. Cause: The system does not assign an independent `chatId` to each user, so all sessions share the same identifier.
- Symptom: The Human field in API response dialogue previews displays as null, and the user's actual input content cannot be viewed. Cause: The system does not correctly pass the user's input content in the `messages` field, or the parameter format does not meet requirements.
- Symptom: Dialogue response is significantly delayed, with a long wait time after input before a result is obtained. Cause: The system does not limit the number of documents retrieved per session, so each dialogue loads excessive redundant rail transit equipment technical documents.

## How to verify correct configuration
- Assign different `chatId` values to two test users, launch identical fault queries, and confirm each user’s dialogue record only contains their own interactive content.
- Call the API to pass the complete `messages` field including the user’s actual input content, and check if the Human field in the response preview correctly displays the input content.
- After configuring the prompt template, launch a fault query that does not specify a train model, and confirm the reply requests supplementary train model number to verify the prompt is effective.
- Import the longest individual rail transit equipment technical document, test that the dialogue context fully loads the document’s key content without truncation.
