# Service Inquiry and Response for Rail Transit Equipment: Tool Calling and Plugins

## What the data for this category looks like
Rail transit equipment service inquiry data mainly comes from factory maintenance manuals, in-service equipment operation logs, and industry compliance standard documents. The data update rhythm is synchronized per single device with its maintenance cycle, and bulk devices are updated in batches quarterly. The document structure is categorized by device model, and includes fields such as device number, operation duration, fault code, disposal process, and compliance requirements. The unit of operation duration is hours, the fault level is an enumerated value, the unit of disposal timeliness is days. The overall document structure has clear levels, and fields are tightly bound to single devices.

## What constraints these characteristics impose on the tool calling and plugin workflow
Since the rail transit equipment data fields are tightly bound to single devices, an accurate device number must be passed as a required parameter when calling tools. Direct matching of corresponding data via fuzzy keywords is not supported. Since data is updated per maintenance cycle or quarterly, plugins must be configured with a scheduled pull mechanism to avoid using expired static cached data. Since compliance requirement fields are included, tool calls must additionally verify whether the returned compliance content matches the applicable scope of the inquiry scenario. Additionally, since there are multiple document levels, specified extraction of field content from target levels must be clearly configured in the plugin to avoid returning redundant information.

## How to set configurations

| ---- | ---- | ---- |
| `toolChoice` | Auto-match specified tools | Rail transit equipment inquiries require calling different interfaces for device data, compliance documents, and other resources. Auto-matching reduces configuration complexity |
| Plugin timeout period | 300–600 seconds | Rail transit equipment data interface response times are affected by network and device status. This range covers most query scenarios |
| `functionCall` | Enable parameter format validation | Ensure that parameters such as device numbers and fault codes meet requirements, and avoid invalid calls |
| Maximum number of tool return entries | Top 3 entries | The number of associated data entries for a single rail transit equipment is usually limited. Excessive returns increase context processing load |
| Cache duration | 7 days | In-service equipment data is updated quarterly. A 7-day cache balances data timeliness and call efficiency |

## Three common mistakes
- Symptom: A "parameter mismatch" error is returned when calling a custom plugin to query rail transit equipment data. Cause: The device number was not specified as a required parameter in the configuration, so the interface cannot match the corresponding device data.
- Symptom: Empty fields are returned after tool calling. Cause: `functionCall` parameter validation was not enabled, and a fault code or device number that does not meet the format requirements was passed.
- Symptom: Plugin call times out. Cause: A reasonable timeout period was not set, and an overly short default duration was used, which cannot cover the normal response cycle of rail transit equipment data interfaces.

## How to confirm the configuration is complete
- Initiate an inquiry targeting a single rail transit device, and verify whether the tool calls the matching external interface.
- Check the tool call log to confirm that the passed parameter format complies with the preset rules.
- Verify that the fields in the returned result match the standard structure of rail transit equipment data, and only include target content.
- Initiate an inquiry again after the cache update cycle, and confirm that the data has been synchronized with the latest maintenance or compliance information.
