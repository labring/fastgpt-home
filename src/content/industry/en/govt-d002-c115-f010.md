# Rail Transit Equipment Inquiry and Reply: Knowledge Base Retrieval and Recall

## What This Category of Data Looks Like
Rail transit equipment inquiry and reply data primarily comes from equipment operation and maintenance manuals, maintenance work procedures, operation parameter ledgers, fault handling guides, and on-site operation and maintenance records. Updates are triggered on demand when new models launch or maintenance specifications are revised, with no fixed schedule. Individual documents typically include structured fields such as equipment model, part number, fault code, handling steps, and test parameters. Units used include industrial standard units such as millimeters, megapascals, and operating hours. Some long documents are split into multiple chapters to explain operating requirements for different working conditions.

## Constraints Imposed on Knowledge Base Retrieval and Recall
Parallel operation of multiple rail transit equipment models requires retrieval to precisely match the equipment model field, to avoid interference from general maintenance documents. Structured fault code and parameter fields require retrieval to support both semantic matching and exact keyword matching, to accommodate both natural language inquiries and structured parameter queries. Long documents and multi-chapter structures require retaining contextual connections during chunking and recall, to avoid losing complete handling logic after splitting. The on-demand update feature requires the retrieval pipeline to quickly sync the latest dataset, without frequent full index rebuilds.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.72–0.85 | Matches the semantic precision requirement for rail transit equipment fault descriptions, filters low-relevance general maintenance content |
| `limit` | Top 8 entries | Individual fault handling steps are lengthy; too many results will exceed context window limits |
| `searchMode` | Semantic + keyword hybrid | Balances natural language inquiries and exact keyword matching for equipment models and fault codes |
| `usingReRank` | Enabled | Performs secondary ranking on initial recall results to filter irrelevant cross-model maintenance documents |
| `datasetSearchUsingExtensionQuery` | Enabled | Automatically expands equipment model and fault code keywords in user inquiries to improve precise recall rate |
| `collectionIds` | Bind dedicated rail transit equipment dataset ID | Prevents retrieval results from mixing with maintenance documents of other categories, ensures compliant data scope |

## Three Common Misconfigurations
- Phenomenon: Retrieval results include non-designated model rail transit equipment documents, with empty fields or incorrect matches. Cause: Failed to correctly configure `collectionIds` to bind the dedicated dataset, so the retrieval scope covers irrelevant maintenance knowledge bases.
- Phenomenon: After referencing configuration variables, retrieval fails to return documents for the target device, returning empty results. Cause: Failed to correctly associate the knowledge base variable with the scope of the corresponding dataset; the variable does not point to the rail transit equipment dedicated collection.
- Phenomenon: CSV-format maintenance ledger files cannot be retrieved after upload, with the system prompting field parsing failure. Cause: Did not use the template import function to upload CSV files, directly used text dataset upload, and did not match dedicated fields such as equipment model and fault code.

## How to Verify Proper Configuration
The FastGPT v4.17.0 dataset management interface may be accessed to confirm that `collectionIds` is bound to the dedicated rail transit equipment knowledge base collection.
A test query including specific equipment model and fault code may be submitted to verify that the number of initial recall results matches the `limit` configuration.
CSV-format maintenance ledger files may be uploaded, with import completed using the corresponding template, to confirm that field matching has no errors.
Retrieval logs may be checked to confirm that `usingReRank` and `datasetSearchUsingExtensionQuery` are active, with no abnormal errors.
