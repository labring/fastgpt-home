# Rail Transit Equipment Service Consultation and Reply: Deployment and Upgrade

## What the data for this category looks like
The data for rail transit equipment service consultation and reply mainly comes from on-site operation and maintenance work orders, customer service consultation records, equipment technical manuals, and operation and maintenance ledgers. The data update rhythm varies by business scenario: daily consultations are entered in real time, and technical documents are updated synchronously on a quarterly basis. Each data entry includes fields such as equipment model, fault phenomenon, consultation time, reply content, and processing result. Field units include set, hour, and occurrence, among others. Some documents include equipment parameter charts, and a single document page can contain several thousand characters.

## What constraints these characteristics impose on deployment and upgrade
The consultation data for rail transit equipment includes long-text technical documents and structured work orders. Deployments must adapt to storage and retrieval requirements for large-volume data. Real-time updated daily consultation content requires a stable synchronization link during deployment to prevent data delays. Structured data with multiple fields must support imports in different formats. During upgrades, retain original field mapping rules to avoid business data loss. For intranet deployment scenarios, ensure access permissions and data isolation for internal users. Also configure reverse proxy HTTPS settings to secure access.

## Three Common Mistakes
- Symptom: The channel model list only displays reranking models, and other language models cannot be selected. Cause: `ROOT_KEY` permissions are not configured, or the commercial version authorization is not bound to the usage permissions of the corresponding language model.
- Symptom: After configuring the channel, the local ollama model cannot be connected, and the chat box displays that the model does not exist. Cause: The container network is not connected to the local ollama service, or the intranet access address configured in `FE_DOMAIN` does not cover the local request link of the ollama service.
- Symptom: The container fails to start when deployed via Synology Docker, and the log prompts a database connection error. Cause: The intranet database address configured in `PG_URL` or `MONGODB_URI` has not been added to the container network access whitelist, or the database version is incompatible with FastGPT v4.17.0.

## How to Verify Successful Configuration
- Access the intranet address configured in `FE_DOMAIN`, confirm that the page loads normally with no certificate or domain resolution errors.
- Upload a technical document for rail transit equipment, confirm that the file can be stored normally and called for retrieval in the chat box.
- Enter the channel management page, confirm that the required language models and reranking models are displayed in the optional list, and the configuration can be saved normally.
- Initiate a simulated consultation, confirm that the system can return matching rail transit equipment operation and maintenance reply content, with no data delay or error reports.
