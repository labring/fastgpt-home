# Work Consultation and Response for Communication Towers and Infrastructure: HTTP Interfaces and External Systems

## What the data for this category looks like
The work consultation data for communication towers and infrastructure mainly comes from internal operation and maintenance management systems and grassroots site inspection reporting systems. Consultation work orders are submitted and updated in real time. Site basic information is synchronized monthly. Each piece of consultation data has a document structure including work order ID, site code, consultation content, submission time, processing status, and response content fields. Work order ID and site code are string types. Time uses ISO 8601 format. Processing status is a fixed enumeration value. There is no extra complex nested structure.

## What constraints these characteristics impose on HTTP interfaces and external systems
Because consultation work orders are updated in real time, interfaces must support real-time pulling of the latest consultation and response data. They cannot rely on cached old data. Site code is a core identification field. Request parameters must include this field to accurately match consultation content for the corresponding site. Otherwise, irrelevant data will be returned. The structure of individual data is simple but has fixed fields. The JSON format returned by the interface must strictly match the preset fields. Otherwise, FastGPT cannot parse it correctly. When pulling data in batches, control the number of returned entries. Avoid excessive data volume in a single request that causes FastGPT processing overload. Also adapt to the format requirements of the enumeration status field to avoid parsing errors.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Request timeout period | 300-600 seconds | Interfaces of internal communication tower systems usually have certain response delays. This setting reserves sufficient time to complete data pulling |
| Authorization | Bind tokens stored in environment variables | Used for identity verification when connecting to tower systems. Avoid hardcoding sensitive information. This complies with FastGPT v4.17.0 environment variable configuration specifications |
| variables | Bind the site code field of work orders | Dynamically pass the identification of the corresponding tower site. Ensure the consultation data returned by the interface matches the current site |
| responseData | Extract the response content field | Extract valid consultation response content from structured data returned by external interfaces. Adapt to FastGPT content processing logic |
| Retry count | 2-3 times | Address temporary interface fluctuations in tower systems. Reduce consultation interruptions caused by single request failure |
| Batch pull limit | First 20 entries | Control the amount of data returned by a single interface. Avoid overloading FastGPT context processing |

## Three common mistakes
- An interface call returns a 401 unauthorized error. The cause is incorrect configuration of the `Authorization` parameter. The token is not loaded via environment variables or the format does not meet system requirements.
- The interface returns empty response content. The cause is incorrect configuration of the `responseData` extraction field. The actual response content field returned by the external system is not matched.
- Interface calls frequently time out. The cause is an overly short request timeout period. It does not adapt to the average response delay of tower systems. This causes normal requests to be judged as timed out.

## How to confirm correct configuration
- Call the test interface. Check that the `Authorization` parameter is correctly carried in the request logs. Confirm the interface returns a 200 status code.
- Check the FastGPT debug logs. Confirm that the site code parameter bound to `variables` is correctly passed to the external interface request.
- View the structured data returned by the interface. Confirm that the field configured in `responseData` is correctly extracted. There are no null values or abnormal content.
- Simulate three consecutive interface calls. Confirm that the retry mechanism triggers normally during temporary interface fluctuations. There are no consecutive failures.
