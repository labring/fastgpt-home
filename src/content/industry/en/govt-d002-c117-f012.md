# Official Service Inquiry and Reply for Communication Towers and Infrastructure: Deployment and Upgrade

## What the data for this category looks like
Business data for communication towers and infrastructure comes from operation and maintenance work orders, base station inspection reports, user inquiry records, and base station operation logs. Data update rhythms fall into three categories: operation and maintenance work orders are generated in real time, inspection reports are updated daily or weekly, and base station operation logs are pushed at the minute level.
The document structure includes fields such as work order number, base station code, problem type, fault level, processing progress, user contact information, fault description, and on-site photo attachments. The base station code is an 11-digit numeric string. Fault levels are divided into three levels. Time fields use the UTC+8 time zone format. Attachments support image and document files up to 1000 MB in size.

## What constraints these characteristics impose during deployment and upgrades
The real-time data requirement means a high-concurrency database connection pool must be configured during deployment, to avoid connection exhaustion caused by concurrent inquiries from multiple base stations.
The large attachment size requirement means storage configuration must support large file upload and download, and must match a dedicated cloud storage endpoint.
The fixed field format requirement means compatibility with the original data structure must be retained during upgrades, to avoid import failures of work order and inspection data due to field mismatches.
The high-frequency push of real-time logs means cache configuration must update session and status data in a timely manner, to avoid inquiry delays or data inconsistency.
The upgrade phase must use a gray release strategy, to ensure that service interruptions do not affect core base station operation and maintenance inquiry services.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `120–180` | Supports concurrent inquiries and data queries across multiple base stations, avoiding connection exhaustion |
| `MONGODB_URI` | `mongodb://[account]:[password]@[host]:27017/comm_tower` | Stores dedicated operation and maintenance work orders and inspection data, specifies a dedicated database name |
| `REDIS_URL` | `redis://[account]:[password]@[host]:6379/1` | Caches real-time inquiry sessions and base station status, sets an expiration time of 300 seconds |
| `STORAGE_S3_ENDPOINT` | `https://s3-[region].cloudprovider.com` | Stores base station inspection photos and operation and maintenance documents, matches the access endpoint of the cloud storage service provider |
| `FILE_TOKEN_KEY` | `32-character random hexadecimal string` | Encrypts attachment download links to prevent unauthorized access |
| `ROOT_KEY` | `Strong key compliant with enterprise security specifications` | Manages the highest system permissions, ensuring secure access to configurations and data |

## Three common configuration errors
- Symptom: A newly deployed system cannot initiate a conversation, and the console prompts key verification failure. Cause: `ROOT_KEY` or `FILE_TOKEN_KEY` is not configured correctly, leading to an error in the session identity verification step, and a valid inquiry connection cannot be established.
- Symptom: Container startup fails when executing `docker run --gpus all -itd -p 7231:7231` to deploy marker_images:v0.1. Cause: GPU driver dependencies are not correctly installed on the host machine, or container permissions do not grant GPU access, so image parsing computing power cannot be called to process base station on-site photos.
- Symptom: After upgrading to FastGPT v4.17.0, background logs prompt `cannot fetch internal url` when importing base station operation and maintenance documents via URL. Cause: `FE_DOMAIN` is not configured as a domain name accessible within the internal network, and the system blocks URL requests from untrusted sources, leading to document capture failure.

## How to verify configurations are correct
- Execute the `docker ps` command, check that the marker_images container status is Up, with no abnormal exit records.
- Log in to the FastGPT backend, enter a test key to verify the `ROOT_KEY` configuration, with no permission error or session interruption issues.
- Upload a base station inspection photo, verify that attachments can be stored and downloaded normally, confirming that the `STORAGE_S3_ENDPOINT` configuration takes effect.
- Initiate a simulated base station inquiry conversation, verify that the session connection is normal, with no connection timeout or key error prompts.
