# 12345 Citizen Hotline Ticket Processing: Ledger Summary and Report Generation — Multi-turn Dialogue and Prompt Engineering
## What Data for This Category Looks Like
Data sources include the 12345 citizen hotline platform, contractor business systems, knowledge bases, return visit evaluation data, and local hotline management regulations. Update frequency is daily. Daily documents include request registration forms, dispatch records, handling responses, return visit records, extension applications, return explanations, and knowledge base entries. Fields include request number, request content, contracting entity, handling status, response content, return visit evaluation results, and others. No unified fixed numeric fields are set. Document fields for each processing link are subject to business requirements.

## What Constraints These Characteristics Impose on the Multi-turn Dialogue and Prompt Engineering Link
Daily updated ticket data must be processed in batches. Dialogue context length must be limited to avoid exceeding model carrying limits. Multi-source and heterogeneous document formats require prompts to clearly distinguish field rules for different documents such as request registration forms and dispatch records, to prevent format confusion during ledger summary. 12345 hotline tickets take closed-loop processing as their core. Multi-turn dialogue must associate full-process records through session identifiers to ensure ledger summary covers all links including dispatch, response, and return visit. Request type judgment relies on knowledge base and business system data. Multi-turn interaction must gradually retrieve corresponding documents; loading all data sources at once is not recommended. Abnormal processes such as ticket extensions and returns must be clearly marked in dialogue to ensure all abnormal links are covered during report generation.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique request number of a single ticket | Associate full-process dialogue and document data for the same ticket to avoid context interference |
| `messages` context window | Retain the last 15 dialogue records | The number of interaction rounds in the 12345 hotline ticket processing flow usually does not exceed 15; overly long context reduces response efficiency |
| `variables` | Pass three global variables: request number, contracting unit, and handling status | Quickly locate corresponding business documents without repeated data source retrieval |
| Maximum context length | 6000–10000 characters | Full-process document summary content for a single ticket usually falls within this range, adapting to the general context window limit of FastGPT v4.17.0 |
| Prompt template triggering | Trigger corresponding templates according to ticket processing stages | Ledger summary requirements differ across stages (dispatch verification, response drafting, return visit review); staged prompts improve report accuracy |

## Three Common Configuration Mistakes
- Issue: When viewing dialogue history associated with a ticket without logging in, request attachment images fail to load. Cause: The storage path of dialogue history is not bound through `variables`, causing the context to fail to obtain access permissions for offline images.
- Issue: When calling a sub-ticket summary application in a parent workflow, the sub-application does not generate dialogue logs for the corresponding ticket. Cause: The `chatId` parameter is not passed in the call node, causing the session context to fail to associate records.
- Issue: When calling a form input node in a nested workflow, the dialog box always displays. Cause: The context state is not passed through the `messages` parameter, and the node’s display trigger condition is not configured, causing it to fail to hide automatically.

## How to Verify Successful Configuration
- A test ticket’s request number is submitted, `chatId` binding is verified, and proper association of dialogue history is confirmed.
- Multi-turn dialogue is triggered, global variables in `variables` are checked for correct passing, and corresponding business documents are verified for quick retrieval.
- The nested workflow is called, and the form node is confirmed to only display on first trigger, automatically hiding during subsequent interactions.
- Dialogue logs are viewed, and `messages` for each round of interaction are confirmed to be correctly recorded with no context loss.
