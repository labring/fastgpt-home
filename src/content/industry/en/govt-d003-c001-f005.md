# 12345 Citizen Hotline Ticket Handling: Ledger Summary and Report Generation - Tool Calling and Plugins

## What the data for this category looks like
The data for this category is updated daily, and mainly comes from the 12345 citizen hotline platform, contractor business systems, knowledge bases, follow-up evaluation data, and local hotline management regulations. Daily documents include request registration forms, dispatch records, handling responses, follow-up records, extension applications, return explanations, and knowledge base entries. Fields cover request subject, matter content, handling progress, responsible unit, and evaluation results, and include full process data from ticket receipt, dispatch, handling to follow-up.

## What constraints these characteristics impose on the tool calling and plugins link
The daily update feature requires tool calling to support an incremental synchronization mechanism to avoid repeated processing of historical tickets. The mix of multiple document types and scattered data sources requires plugins to adapt to parsing ticket data in different formats, and support calling multiple business system interfaces to obtain associated information. The core requirement of full ticket handling process requires tool calling to link multiple link data such as dispatch, response, and follow-up to ensure the integrity of ledger summary. At the same time, errors in ticket handling directly affect public satisfaction, so exception verification and retry mechanisms must be added during the tool calling link to reduce order returns or overdue caused by data errors.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | auto | Adapt to tool calling needs for different ticket scenarios, automatically select appropriate plugins to perform tasks |
| Plugin timeout setting | 600 seconds | Match the standard processing duration for 12345 ticket verification and cross-unit coordination |
| Number of items returned per single tool call | First 10 entries | Cover the main daily ticket volume, avoid excessive returned data causing context overflow |
| `functionCall` format verification | Strict verification | Ensure that the field format of ticket data meets the unified requirements for ledger summary |
| Context window size | 8000–12000 token | Accommodate multiple ticket documents and associated data, support complete ledger generation logic |
| Number of failure retries | 2 times | Balance call success rate and system load, avoid repeatedly triggering ticket handling processes |

## Three common mistakes
- Phenomenon: Tool calling results only display when re-entering the conversation, with no content returned on the first call. Cause: The return format verification rules for `functionCall` are not configured correctly, resulting in the original tool calling results being filtered.
- Phenomenon: The code running plugin fails to extract specified elements from the ticket JSON data, and the output is empty. Cause: The nested hierarchy of ticket data is not matched, or the correct JSON path parameter is not specified.
- Phenomenon: The basic chart plugin returns `none`, and a valid chart URL cannot be generated. Cause: Qualified numeric statistical fields are not passed in, or correct ticket classification data is not associated.

## How to confirm the configuration is complete
- Trigger a tool call for the daily ticket ledger summary, check whether the returned results include core records such as daily dispatch, response, and follow-up.
- View the plugin calling logs in FastGPT v4.17.0, confirm that the `toolChoice` parameter takes effect as configured, with no format errors or timeout prompts.
- Simulate a single abnormal ticket data to verify whether the failure retry mechanism automatically triggers retries after a call failure.
- Call the basic chart plugin, pass in known ticket statistical data, and confirm that the returned chart link can be accessed normally.
