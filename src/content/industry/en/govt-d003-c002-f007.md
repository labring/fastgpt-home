# Ledger Aggregation and Report Generation for "One Thing Done Efficiently" Joint Services: Database and Operations

## What data falls under this category
Data typically comes from the national integrated government service platform's "One Thing" special section, local integrated government service platforms, electronic certificate repositories, and departmental approval systems. Daily processed documents include joint service item lists, one-time notice sheets, joint service application forms, material circulation forms, parallel approval opinions, and completion receipts.
Data is updated daily. Core fields include unique identifiers for joint service items, cross-department circulation node status, application material lists, processing duration for each link, and completion receipt numbers. No custom statistical units are used, and data is stored according to general government service field specifications.

## What constraints do these characteristics impose on the database and operations link
Daily updated multi-source heterogeneous data requires databases to support high-concurrency batch writes and low-latency real-time queries. This prevents delayed updates of joint service process status from affecting ledger aggregation.
Differences in fields across departmental documents require databases to support flexible schema adaptation. This avoids hard-coded fields limiting multi-source data access.
Cross-department circulation of joint service items requires associating approval data from multiple departments. A reasonable multi-table association structure must be designed to reduce query time.
Government data storage must comply with local regulatory requirements. Redundancy mechanisms must also be configured to ensure data availability, preventing single-node failures from disrupting joint service ledger generation.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://[username]:[password]@[cluster address]:27017/[government joint service document repository]?authSource=admin` | Stores unstructured documents from joint service processes, such as one-time notice sheets and completion receipts, to adapt to storage needs for multi-source heterogeneous government service documents |
| `PG_URL` | `postgresql://[username]:[password]@[cluster address]:5432/[government joint service business repository]?sslmode=require` | Stores structured joint service item circulation data, approval opinions, and similar data, supports complex associated queries to generate aggregated ledgers |
| `DB_MAX_LINK` | `50–80` | Adapts to concurrent connection requirements for daily batch data import, prevents data import failures caused by exhausted connections |
| `REDIS_URL` | `redis://[password]@[cache address]:6379/0` | Caches frequently queried joint service item lists and completion status data, reduces database query pressure and improves ledger generation efficiency |

## Three common mistakes
- Phenomenon: After installing a database connection plugin, testing fails, and the interface displays an internal server error. Cause: Incorrect authentication source not configured in `MONGODB_URI`, or firewall rules of the database cluster restrict external access to port 27017.
- Phenomenon: Service startup prompts a MongoDB error and fails to complete initialization. Cause: Database connection count exceeds the `DB_MAX_LINK` configuration limit, or database cluster node status is abnormal causing connection timeout.
- Phenomenon: Unable to locate the target tenant's storage table when exporting completed training text. Cause: Correct tenant repository name not specified in the connection string, or cross-tenant data access permission not configured.

## How to confirm configurations are correct
- Use the database connection test tool built into FastGPT v4.17.0 to verify connectivity for `MONGODB_URI` and `PG_URL` separately, adjust connection parameters based on test results.
- Import a test joint service item document, check if data can be correctly written to the corresponding repository and table, and whether field mapping complies with general government service specifications.
- View service operation logs, confirm there are no abnormal messages such as database connection timeouts or permission errors, adjust configurations such as `DB_MAX_LINK` based on log prompts.
- Trigger a joint service ledger aggregation task, check whether database read and write operations are normal during task execution, with no blocking or failures.
