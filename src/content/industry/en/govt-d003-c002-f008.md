# Joint Handling Ledger Summary and Report Generation for "One-Stop One-Thing" Initiative: Document Parsing and Chunking

## What the data for this use case looks like
Data typically originates from the national government service platform's "One-Thing" special zone, local integrated government service platforms, electronic certificate repositories, and departmental approval systems. The update frequency is daily.
Commonly processed documents include joint handling item lists, one-time notification sheets, joint handling application forms, material circulation forms, parallel approval opinions, and completion receipts. These documents contain fields such as cross-departmental item association identifiers, material details, processing nodes, and circulation order numbers. Document structures vary by source department, and some structured ledgers include multi-column associated data.

## What constraints these characteristics impose on the document parsing and chunking link

Daily updated batch data requirements demand sufficient timeout tolerance for parsing tasks, to avoid task interruptions during bulk imports.
Multi-column linked ledger data requires chunking rules to retain associations between fields, and must not break the logical links of cross-departmental items during splitting.
Some scanned approval documents require OCR recognition, so parsing processes must also support image text extraction.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `chunkSize` | 800–1200 characters | Adapts to the multi-field paragraph length of joint handling ledgers, avoids splitting cross-departmental linked item nodes |
| `chunkSplitter` | Chunk by title + paragraph | Retains the hierarchical structure of joint handling item lists, distinguishes processing requirements from different departments |
| `customPdfParse` | Enable OCR mode | Processes non-editable PDF documents such as scanned parallel approval opinions and completion receipts |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600 seconds | Adapts to parsing time for bulk imported multi-department joint handling documents, prevents large tasks from timing out mid-execution |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | Supports importing historical ledger packages for large joint handling items, meets bulk data import needs |
| `chunkSettingMode` | Manual configuration | Adjusts chunking rules for the multi-column structure of joint handling documents, avoids breaking data links from default row-wise splitting |

## Three common configuration errors
- Symptom: An error occurs when importing Excel format files indicating parsing failure, or some fields are empty after import. Cause: Parsing configuration for multi-column structured documents is not enabled. The default parsing rule only adapts to single-column tables, and cannot recognize multi-column linked joint handling ledger data.
- Symptom: Connection failure or request timeout occurs when calling the PDF parsing tool. Cause: `PARSE_FILE_TIMEOUT_SECONDS` is not configured to adapt to the parsing time of bulk documents, or port mapping for local deployment is not set correctly, preventing normal calls to the parsing service.
- Symptom: The generated report does not retain the original answer from knowledge base question-and-answer pairs, and extra generated content appears. Cause: Matching rules are not set correctly, so the model does not strictly call the original knowledge base content and generates non-preset response text.

## How to verify the configuration is correct
- Upload a single Excel-format joint handling ledger, check if the number of columns retained after parsing matches the source file, to confirm multi-column data parsing works correctly.
- Submit a batch of PDFs containing parallel approval opinions, check the execution status of parsing tasks to confirm no timeout errors occur.
- Import a preset question-and-answer pair dataset, trigger a question-and-answer test, confirm the returned content exactly matches the original answer from the knowledge base.
- Upload a file package with an expected total size, confirm the upload task does not fail due to size restrictions, to verify the configuration takes effect.
