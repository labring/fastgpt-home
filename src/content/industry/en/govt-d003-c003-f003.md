# Ledger Summary and Report Generation for Real Estate Registration: Multi-turn Dialogue and Prompt Engineering

## What the Data for This Category Looks Like
Data for this category originates from real estate registration information systems, cadastral survey databases, housing transaction online signing systems, tax systems, and electronic certificate repositories. Full daily business data is updated each day. Daily business documents include registration applications, ownership certificates, surveying and mapping results, tax payment vouchers, real property right certificates, and registration books. Fields cover right holder information, real estate location, right type, registered area, registration date, and more. Units include square meters, parcels, and others. Document structures combine structured forms and scanned file formats.

## How These Characteristics Create Constraints for Multi-turn Dialogue and Prompt Engineering
Multi-source data sources require multi-turn dialogue to gradually guide users to clarify key parameters for their target registration business. This avoids overloading the context by loading full cross-business data at once. Daily updated data rhythms require prompt templates to sync with the latest daily business data. This ensures called ledger information uses the same day’s updated version. Mixed-format documents require the dialogue flow to first confirm the document type, then retrieve corresponding data in a targeted manner. Ownership verification is a core business step. Prompt templates must embed steps to verify ownership sources and restriction statuses. Multi-turn dialogue must gradually confirm the completeness of supplementary materials.

## Configuration Settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` session binding rule | Bind to the unique registration number of the current business | Ensures multi-turn dialogue context is accurately linked to the corresponding registration business, avoiding confusion across cross-business data |
| `messages` historical dialogue organization rule | Retain only the last 3 rounds of dialogue content related to ownership verification, with a maximum context length of 8000–12000 characters | Reduces invalid context usage, focuses on core business steps, and covers all associated fields for a single batch of registration business |
| `variables` variable binding | Bind real estate location and right holder name as required fields | Ensures prompt calls accurately match target registration data, avoiding result deviations from generalized queries |
| Multi-turn session timeout | 7200 seconds | Matches the standard processing cycle for real estate registration businesses, preventing session failures mid-process that disrupt business workflows |
| Maximum return token count | 3000–4000 tokens | Meets the need to splice and display content from multiple documents during ledger summary |

## Three Common Configuration Mistakes
- Form input fields configured in the workflow do not appear in the dialogue interface. This occurs when form fields are not correctly bound to `variables` variables, causing the dialogue context to fail to load entered interactive content.
- API calls to the dialogue interface return empty results. This occurs when the `chatId` parameter is not specified to link the session for the target registration business, preventing the system from locating the corresponding ledger data.
- Redundant unrelated business data is returned during multi-turn dialogue. This occurs when historical dialogue content for `messages` is not filtered and organized, leading to the context containing too much historical information from non-target businesses, which interferes with accurate prompt matching.

## How to Verify Successful Configuration
- Initiate a test dialogue, enter preset form fields such as real estate location and right holder name, and confirm that the input content is properly displayed in the dialogue interface.
- Call the API to upload documents associated with the registration business, specify `chatId` as the test business number, initiate a query, and confirm that the returned results include ledger information for the corresponding registration business.
- Initiate 3 consecutive rounds of dialogue related to ownership verification, confirm that the system only retains the last 3 valid context entries, with no redundant historical information causing interference.
- Wait for the configured timeout period, then initiate a new dialogue, confirm that the session has expired and historical data can no longer be retrieved.
