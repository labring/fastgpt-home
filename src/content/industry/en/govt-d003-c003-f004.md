# Real Estate Registration Ledger Aggregation and Report Generation: Workflow Orchestration

## What the data for this category looks like
Real estate registration scenario data comes from multiple systems, including real estate registration information systems, cadastral survey databases, housing transaction online signing systems, tax systems, and electronic certificate repositories. Daily processed documents include registration applications, ownership certificates, surveying and mapping results, tax payment vouchers, real estate ownership certificates, and real estate registers. Data is updated daily. Structured fields include rights subject, real estate location, ownership status, surveying and mapping area, and other fields. Unstructured documents include various application and certification materials.

## What constraints these characteristics impose on the "workflow orchestration" link
Multi-system data sources require workflow orchestration to include cross-system data fetch nodes, and call logic must be configured according to the interface specifications of different systems. Daily update frequency requires the workflow to have a scheduled trigger mechanism to ensure that the latest data is aggregated every day. Diverse document types with fixed fields require the workflow to be configured with structured field verification rules to filter invalid or incorrectly formatted materials. Ownership verification is a core link, requiring the orchestration of sub-processes for comparing ownership sources and restriction statuses. Failure retry and exception alert links must also be configured to avoid property rights disputes or administrative litigation caused by registration errors.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Predefined field variable group including right holder, location, and ownership status | Matches the fixed field requirements of real estate registration ledgers, facilitating subsequent aggregation and report generation |
| `nodeId` | Unique identifier bound to cross-system data fetch nodes | Accurately locates the call nodes of each data source in the workflow, avoiding configuration confusion |
| Single request timeout | 600 seconds | Cross-system fetching of registration and surveying and mapping data takes a long time, adapting to the interface response cycles of most real estate systems |
| Concurrent request limit | 2–4 concurrent requests | Complies with the interface call rate limiting rules of real estate systems, avoiding triggering system interception |
| Number of failure retries | 3 times | Covers temporary network fluctuations or interface jitter in cross-system calls, reducing process interruptions caused by temporary exceptions |

## Three Common Misconfigurations
- Symptom: After the workflow is published for WeChat access, only the publisher can scan the code to trigger it, and other users cannot use it. Cause: Public access permission configuration for the workflow is not enabled. By default, only the publisher has call permissions.
- Symptom: No optional values appear when selecting reference variables for knowledge base search. Cause: No real estate registration-specific field variables are preconfigured in the workflow `variables`, so the system cannot identify referenceable ledger fields.
- Symptom: The database connection node cannot enter a port number. Cause: The current FastGPT version does not provide a custom input option for database ports. Upgrade to FastGPT v4.17.0 or later.

## How to Confirm the Configuration Is Complete
- Trigger the workflow to fetch cross-system data, check whether structured fields of documents such as registration applications and ownership certificates can be obtained normally.
- Call the workflow API, check whether the returned results include the real estate registration-specific fields preconfigured in `variables`.
- Simulate a temporary exception of a cross-system interface, test the failure retry logic, and confirm that the workflow will automatically rerun according to the configured number of retries.
- Publish the workflow to the WeChat end, invite other users to scan the code for testing, and confirm that it can be triggered normally and generate ledger reports.
