# Real Estate Registration Ledger Summary and Report Generation: Deployment and Upgrade

## What this category of data looks like
Data for this category comes from the real estate registration information system, cadastral survey database, housing transaction online signing system, tax system, and electronic certificate repository. The update frequency is daily. Commonly processed documents include registration applications, ownership certificates, surveying and mapping results, tax payment vouchers, real estate ownership certificates and registers. Data fields include real estate unit number, right holder name/title, location address, parcel area, building floor area, right type, restriction status, and more. Units include square meters, parcels, units, and others. Each document is linked to a unique real estate registration number.

## What constraints these characteristics impose on deployment and upgrades
Multi-source data docking requires configuring multiple cross-system connection parameters during deployment, to ensure stable synchronization with real estate registration, cadastral survey, tax, and other systems. Daily update frequency requires retaining incremental synchronization logic during upgrades, to avoid full re-runs that occupy excessive system resources. Diverse document types and structured fields require knowledge base parsing configurations to adapt to different formats of ownership certificates, surveying and mapping results, and other files, to ensure accurate extraction of core ledger fields. High-risk consequences of registration errors require configuring data verification rules and failure alerts during deployment, and reserving rollback nodes during upgrades to handle abnormal changes.

## Configuration Settings
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://reg_user:reg_pass@db-host:27017/reg_db?authSource=admin` | Stores incremental data of multi-source synced real estate registration ledgers, requires correct authentication information and target database |
| `PG_URL` | `postgresql://pg_user:pg_pass@db-host:5432/reg_struct?sslmode=require` | Stores structured real estate register and report template data. PostgreSQL structured queries adapt to multi-field association requirements |
| `REDIS_URL` | `redis://:redis_pass@cache-host:6379/0` | Caches daily updated cadastral survey snapshot data, reduces repeated query pressure on multi-source systems |
| `DB_MAX_LINK` | `20–30` | Adapts to concurrent connection requirements of multi-source systems, avoids synchronization interruptions caused by exceeding database connection limits |
| `STORAGE_S3_ENDPOINT` | Fill in according to the official endpoint of the local object storage service provider | Stores large files such as surveying and mapping results and electronic certificates, aligns with the file storage path of the real estate registration system |
| `ROOT_KEY` | Generate a random 32-bit string according to the deployment environment | Configures the platform administrator operation permission key, ensures operation security of ledgers and report generation |

## Three Common Misconfigurations
- An `embed ding error` error occurs when uploading surveying and mapping results or ownership certificate documents. The cause is that parsing rules adapted to real estate registration documents are not configured, causing the large model to fail to correctly extract core fields such as parcel area and right holder.
- A `'usage' Keye` error occurs when calling the large model after deployment. The cause is that the large model's request key and endpoint are not correctly configured, causing the returned data to lack the usage field and fail normal parsing by the platform.
- An error occurs when creating a new knowledge base after deployment using docker-compose. The cause is that authentication information for `PG_URL` and `REDIS_URL` is not correctly filled in, causing database connection failure and inability to initialize knowledge base storage.

## How to Verify Successful Configuration
- Run the multi-source data synchronization script, check whether the cache service normally pulls daily updated cadastral data, and verify that the cache update time aligns with the daily update frequency required by the business.
- Upload a real estate ownership certificate document, check whether the fields extracted by the knowledge base parsing include core information such as real estate unit number, right holder, and location address, with no missing or incorrect content.
- Attempt to generate a monthly ledger summary report, check whether the report associates multi-source data such as registration applications, tax payment vouchers, and surveying and mapping results, with fields matching business requirements.
- Trigger an upgrade rollback operation, confirm that the system can quickly restore to the pre-deployment operating state, with no data loss or configuration abnormalities.
