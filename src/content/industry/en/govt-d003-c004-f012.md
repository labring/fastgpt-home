# Ledger Aggregation and Report Generation for Proactive Public Disclosure and Policy Publication: Deployment and Upgrade

## What the data for this category looks like
Core data sources for this category include government portals, document management systems, government information disclosure directories, policy document repositories, and press conference materials. Daily processed documents cover policy documents, policy interpretation drafts, public disclosure directories, information release approval forms, press releases, and website column update records. Data updates occur daily. Unified structured and unstructured processing must be completed for multiple document types. Data fields include document confidentiality level, public disclosure attribute, publication time limit, column affiliation, approval status, and other attributes. Document fields vary across different sources, so adaptation to a unified ledger aggregation format is required.

## What constraints these characteristics impose on the deployment and upgrade link
Based on the FastGPT v4.17.0 deployment and upgrade process, adhere to the following constraints. The daily update frequency requires configuring stable scheduled synchronization tasks during deployment. This prevents synchronization delays from causing inconsistencies between public directories and actual files. Multi-source and multi-type document characteristics require the data access link to adapt to different document structures and field rules. During upgrades, retain the configuration mapping relationships of original data sources to avoid interrupting daily ledger aggregation processes. The business requirement for confidentiality and public attribute judgment requires configuring associated rules for permission verification and sensitive information identification during deployment. After upgrades, verify that these rules remain intact. The multi-platform synchronization business scenario requires configuring reasonable concurrency parameters. This avoids excessive system resource usage during synchronization that disrupts other government services.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://admin:password@mongodb-host:27017/gov_public?authSource=admin` | Adapts to government department self-built MongoDB databases for storing policy ledgers and publication logs |
| `REDIS_URL` | `redis://:redis-password@redis-host:6379/1` | Caches daily updated public directory and policy data to reduce overhead from repeated database queries |
| `DB_MAX_LINK` | `80–120` | Adapts to concurrent connection requirements for daily batch synchronization, avoiding database connection pool exhaustion |
| `STORAGE_S3_ENDPOINT` | `http://s3-cn-beijing.volces.com` | Adapts to mainstream domestic object storage services for storing attachments of policy documents and interpretation drafts |
| `ROOT_KEY` | `Randomly generated 32-character English string` | Ensures permission security for FastGPT API access, preventing unauthorized calls |

## Three common mistakes
- Issue: An error occurs when calling the AI interface after deployment, prompting that the One API configuration cannot be found. Cause: FastGPT v4.17.0 has removed the One API dependency, and `aiproxy` related parameters must be configured.
- Issue: The frontend page does not respond after calling the policy synchronization interface, with a 503 status code. Cause: The `DB_MAX_LINK` parameter was not adjusted, leading to database connection pool exhaustion and inability to respond to subsequent requests.
- Issue: When viewing policy publication details, log fields are empty or display garbled characters. Cause: The `FILE_TOKEN_KEY` parameter was not configured, causing attachment metadata to not be properly encrypted and stored, making normal reading impossible.

## How to confirm the configuration is complete
- Run the `docker logs fastgpt` command to check for the log message "Connected to MongoDB successfully" and verify that the database connection configuration is correct.
- Manually trigger a policy document synchronization task, wait for the task to complete, then check the public directory page to confirm that the latest policy files have been correctly synchronized to the ledger.
- Access the frontend domain configured in `FE_DOMAIN` to verify that the policy publication module loads normally without error prompts.
- Submit a test policy document and complete the approval process, confirming that the generated ledger record includes correct confidentiality level, public disclosure attribute, and publication time limit fields.
