# Ledger Summary and Report Generation for Infectious Disease Information Reporting and Monitoring: Vector Models and Indexes

## What data for this use case looks like
Data for this use case comes from the Chinese Center for Disease Control and Prevention Information System, hospital HIS systems, infectious disease reporting systems, and laboratory testing systems. The update frequency is daily. Daily documents include infectious disease reporting cards, epidemic analysis reports, case correction records, clustered epidemic reports, and epidemiological investigation reports. Data fields include case unique identifiers, diagnosis times, reporting units, statutory infectious disease categories, correction status, and more. Individual document lengths vary widely, ranging from hundreds of characters for report cards to tens of thousands of characters for epidemiological investigation reports.

## What constraints these characteristics impose on vector models and indexes
Daily high-frequency updated business data requires indexes to support incremental synchronization mechanisms, avoiding additional time costs from full reconstruction and adapting to the daily ledger update rhythm of disease control institutions. The wide range of document lengths requires flexible chunking rules to retain key information across different document types. Fields such as statutory infectious disease categories and case diagnoses have high compliance requirements, so vector retrieval must prioritize matching relationships between structured fields and unstructured text. Version differences in correction records require indexes to support multi-version data differentiation, preventing recall of outdated incorrect report content.

## How to configure settings
| Configuration Item | Recommended Value Range | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Adapts to the span of documents in this use case, retains key information for both report cards and epidemiological investigation reports |
| Overlap Length | 100–150 characters | Prevents chunk truncation of continuously critical content such as case diagnoses and correction notes |
| `defaultToken` | 4096 token | Matches the input upper limit of mainstream embedding models, adapts to long-text epidemiological investigation reports |
| `maxToken` | 8192 token | Covers context stitching requirements after chunking for the longest documents |
| Similarity Threshold | 0.72–0.80 range | Filters low-match irrelevant reports, retains content related to statutory infectious diseases |
| Single Recall Limit | Top 10 entries | Controls the number of retrieval results, adapts to batch processing needs for disease control ledger summary |

## Three common configuration mistakes
- Performing a full index rebuild daily causes server read-write load to rise continuously until resources are exhausted. This occurs because the incremental index mechanism is not enabled, and full synchronization is directly executed for daily updated disease control data, generating excessive disk read-write and memory occupancy requests.
- After upgrading to FastGPT v4.17.0, calling the voyage index interface returns a 400 status code with no body. This occurs because the interface parameter verification rules of the new version are not adapted to, and the value of `defaultToken` does not fall within the valid range required by the interface.
- When deploying the m3e-large model locally, uploaded epidemiological investigation reports or long documents get stuck in 1 or 2 index groups. This occurs because the chunk length setting exceeds the model's input upper limit, and the index task cannot complete chunk processing, entering a blocked state.

## How to confirm proper configuration
- Manually upload a standard infectious disease report card, check the progress logs of the system index task, and confirm that the chunk length matches the configured value.
- Initiate a retrieval request for statutory infectious disease categories, check whether the number of returned results conforms to the single recall limit configuration.
- Upload a corrected case record, verify that the retrieval results prioritize recalling the latest version of the report content.
- View the system resource monitoring panel, confirm that the server load does not exceed a reasonable range when the incremental index task is running.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
