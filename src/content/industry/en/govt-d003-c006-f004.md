# Ledger Summary and Report Generation for Infectious Disease Information Reporting and Monitoring: Workflow Orchestration

## What the data for this category looks like
Data for this category originates from China's National Center for Disease Control and Prevention Information System, hospital HIS systems, infectious disease reporting systems, and laboratory testing systems. Daily documents include infectious disease report cards, epidemic analysis reports, case correction records, clustered outbreak reports, and epidemiological investigation reports. Each record includes fields such as case number, diagnosis time, reporting unit, correction flag, and monitoring signal type. Field units include cases, hours, dates, and other standard units. Data is updated daily, and case verification, correction, and summary must be completed in accordance with legal regulations.

## Constraints imposed on workflow orchestration by this category's characteristics
Daily updated data sources require a stable scheduled trigger mechanism to maintain data synchronization timeliness. Multi-source heterogeneous data must be integrated through multiple nodes, and consistency checks for case numbers across different systems must be implemented to avoid data misalignment. Case correction records must retain version history to prevent loss of historical information due to data overwrites. Legal reporting regulations require the workflow to include diagnostic time limit checks and duplicate/incorrect record validation steps. Abnormal signal summaries must be categorized by monitoring type. The risk of underreporting or delayed reporting requires a failure alert node to ensure abnormal steps are detected promptly.

## Configuration Settings
All configurations below are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Scheduled Trigger | Daily 2:00-4:00 AM | Avoids peak business hours to reduce data conflicts |
| `variables` | References external incoming knowledge base ID parameters | Adapts to summary requirements for different infectious disease categories |
| `nodeId` | Binds to the unique identifier of the case data extraction node | Ensures accurate data flow during multi-node transfer |
| Text Extraction Rules | Field matching logic calibrated through actual testing | Adapts to format differences across multi-source documents |
| Timeout Threshold | 600 seconds | Prevents data processing backlogs and avoids workflow interruptions |
| Failure Alerts | Triggers pre-configured notification channels | Enables timely response to abnormal steps and reduces underreporting risks |

## Three Common Misconfigurations
- Phenomenon: A workflow configured with a knowledge base search node that uses the `variables` parameter to select the knowledge base returns empty results. Cause: The corresponding knowledge base identifier value was not configured in the workflow startup parameters, causing the variable to not be passed correctly.
- Phenomenon: The text content extraction node returns an error prompt after running, failing to parse target fields. Cause: The data source document format was not adapted, and the extraction rules did not cover line breaks or special characters in exported documents.
- Phenomenon: Manually added audio and video tags are not rendered correctly in the specified reply node, and original tag code is still displayed. Cause: The Markdown rendering switch for the specified reply node was not enabled, so audio and video tags were not parsed properly.

## How to Verify Proper Configuration
- Manually trigger the workflow once, review the running logs of each node, and confirm no errors appear in scheduled trigger, data extraction, and other steps.
- Pass preset monitoring type parameters, and verify that the content returned by the knowledge base search node matches the preset rules.
- Simulate input of abnormal data, and confirm that the failure alert node can trigger notifications normally.
- Check the rendering results of the specified reply node, and confirm that Markdown tags are parsed correctly.

The values provided above are common starting points, and should be evaluated against the user's own samples.
