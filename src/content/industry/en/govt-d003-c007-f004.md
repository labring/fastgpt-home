# Ledger Summary and Report Generation for Petition Matter Handling: Workflow Orchestration

## What data falls under this category
Systems and platforms providing data for this category include the national petition information system, local petition systems, the 12345 citizen hotline platform, grassroots governance platforms, and historical petition archives. Data updates occur daily.
Commonly involved documents fall into six categories: petition registration forms, acceptance notification letters, transfer and assignment notices, handling opinion letters, review and re-examination applications, and resolution plans. Each document includes standardized fields such as request number, submission time, responsible unit, and handling progress. The data structure changes dynamically with the handling stage, covering the full process from request acceptance to resolution and archiving.

## What constraints these characteristics impose on workflow orchestration
Workflows handling multi-source data must use unified field mapping rules. This prevents processing errors caused by differing parameter formats across systems.
The daily data update frequency requires scheduled daily triggers for workflows. This ensures ledger data stays timely.
Differing document structures require workflows to split parsing nodes by document type. This adapts to distinct field extraction logic for each document type.
Full process data coverage requires workflows to connect core stages including verification, coordination, and opinion issuance. It also requires verification nodes to avoid duplicate petitions or petitions filed without following authorized hierarchical processes.

## How to configure the workflow
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Workflow trigger mode | Daily at 2:00 AM | Matches the daily data update frequency, avoids peak business hours |
| Field mapping rules | Configure `variables` to uniformly map request number, submission time, and responsible unit | Resolves inconsistent field naming across multi-source data, standardizes ledger fields |
| Document parsing node configuration | Configure separately for the six document types: petition registration forms, acceptance notification letters, transfer and assignment notices, handling opinion letters, review and re-examination applications, and resolution plans | Adapts to differences in field structures across different documents, accurately extracts core information |
| Error retry count | 3 times, 60-second interval | Meets the stability requirements of petition system interfaces, reduces the impact of single call failures |
| Concurrent call limit | 1 running instance per workflow at a time | Prevents petition system rate limiting from concurrent calls, ensures stable data acquisition |
| Workflow call identifier | Configure `nodeId` as the node ID corresponding to the handling stage | Distinguishes workflows for different business nodes such as verification, coordination, and opinion issuance |

## Three common configuration mistakes
- Phenomenon: Calling the petition data interface returns a 400 error, and the interface displays request parameter format exceptions. Cause: Unified field mapping is not configured via `variables`. Inconsistent parameter formats from multi-source data cause interface verification failures.
- Phenomenon: After the AI dialogue node returns empty content or an error, the workflow terminates directly without generating exception logs. Cause: No error branch processing node is configured. No fallback logic is set for empty results or error statuses.
- Phenomenon: When configuring tool selection nodes, multiple tool calls are triggered simultaneously. This causes the petition system to receive duplicate requests. Cause: No mutually exclusive trigger rules are set for tool selection. No limit is placed on the number of concurrent execution instances.

## How to confirm the configuration is complete
- View workflow trigger logs to confirm that daily scheduled trigger execution records match the data update frequency.
- Import multi-source test data to check if fields mapped via `variables` conform to the preset standardized format.
- Simulate empty content or errors returned by the AI node to verify that the error branch triggers the preset fallback processing logic.
- Initiate multiple workflow invocation requests simultaneously to confirm that only a single instance runs, which aligns with the concurrent limit configuration.
