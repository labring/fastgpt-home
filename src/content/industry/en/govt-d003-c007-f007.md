# Petition Case Handling Ledger Summary and Report Generation: Database and Operations Maintenance

## What the data for this use case looks like
Data for this use case comes from the national petition information system, local petition systems, the 12345 citizen hotline platform, grassroots governance platforms, and historical petition archives, and is updated daily. Daily associated documents include petition registration forms, acceptance notification letters, transfer and assignment letters, handling opinion letters, review and re-examination applications, and resolution plans. Data fields include petition case number, request type, handling status, responsible entity, handling progress, and more. A single case is associated with multiple handling-related documents.

## Constraints imposed on database and operations maintenance by these characteristics
Multi-source data access requires the database to support cross-system format adaptation and incremental synchronization to avoid data conflicts. The daily update frequency requires the database to have stable batch write capabilities to prevent ledger delays caused by data backlogs. The structure where a single case is associated with multiple handling documents requires the database to support nested field storage and associated queries to ensure accurate ledger association relationships. The review and correction requirements during the handling process require the database to retain complete data change logs for retrospective verification. At the same time, data accuracy directly affects the compliance of petition case handling, so data verification rules must be strengthened in the operations link to prevent erroneous data from entering the ledger.

## How to configure the setup
The following configuration items apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://username:password@host:port/petition_ledger_db?authSource=admin` | Stores unstructured documents such as petition registration forms and handling opinion letters, supports nested fields to associate multiple handling materials |
| `PG_URL` | `postgresql://user:pass@host:5432/petition_business_db?sslmode=require` | Stores structured fields such as petition case numbers and handling status, as well as vector data, to ensure associated query efficiency |
| `DB_MAX_LINK` | `20–30 connections` | Adapts to the connection requirements of daily multi-source data batch synchronization, avoids synchronization interruptions caused by exhausted connections |
| `REDIS_URL` | `redis://:password@host:6379/0` | Caches high-frequency accessed petition case status data to reduce the load on the main database |
| Database backup frequency | Daily full backup at 2 AM + hourly incremental backup | Ensures recoverability of petition data, complies with business compliance requirements |

## Three common mistakes
- Phenomenon: After starting the service, the log prompts `column vector does not exist`, and petition data cannot be loaded. Cause: The vector extension was not initialized correctly in the PostgreSQL environment, or the initialization script was not executed after reinstalling the extension.
- Phenomenon: After deploying the service as a Docker image locally, the service cannot connect to the database, with errors showing connection timeout or permission denial. Cause: The host address, port, or permission configuration in the `PG_URL` or `MONGODB_URI` parameters is incorrect, and the database access port is not open.
- Phenomenon: Duplicate petition ledger entries appear after daily data synchronization. Cause: No incremental synchronization logic is configured, and existing petition numbers are not filtered during full synchronization, leading to duplicate data writes.

## How to confirm the configuration is correct
- Run the database connection test script to verify the connectivity of the `MONGODB_URI` and `PG_URL` configurations, and confirm there are no permission or address errors.
- Trigger a simulated petition data synchronization task, check whether documents and structured data with corresponding fields are generated in the database, and confirm the association relationships are correct.
- View the Redis cache monitoring to confirm that high-frequency petition case status data has been cached, and the main database connection count does not exceed the threshold set by the `DB_MAX_LINK` configuration.
- Check the database backup logs to confirm that the daily full backup and incremental backup tasks have been executed normally, and the backup files are complete and restorable.

The values provided here are common starting points and should be measured against the reader's own samples.
