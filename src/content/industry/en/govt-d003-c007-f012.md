# Petition Case Handling Ledger Summary and Report Generation: Deployment and Upgrade

## What Data This Category Includes
This category’s data primarily comes from the national petition information system, local petition systems, the 12345 citizen hotline platform, grassroots governance platforms, and historical petition archives. The update frequency is daily.
Commonly processed documents include petition registration forms, acceptance notices, transfer and assignment letters, handling opinions, review and recheck applications, and resolution plans.
Data fields include request identifiers, handling nodes, responsible entities, request content, handling results, and more. Data is aggregated by handling case as the core unit, and different documents are linked via unified request numbers.

## Constraints Imposed on Deployment and Upgrade
This category’s data sources involve multiple heterogeneous government systems. During deployment, adapt to different interface specifications and data formats to avoid synchronization conflicts.
The daily update frequency requires deploying stable scheduled synchronization tasks. During upgrades, ensure data synchronization is not interrupted to prevent missing processing of same-day petition cases.
Multiple types of business documents require deployment of storage and parsing configurations adapted to multi-format parsing. During upgrades, retain original document parsing rules to avoid historical archives becoming unreadable.
Data aggregation is closely linked to handling results. After upgrades, verify the accuracy of data field mappings to prevent misalignment of handling nodes, which would disrupt subsequent review and recheck processes.

## Configuration Settings
This configuration applies to FastGPT v4.17.0. Specific parameter configurations are listed below:

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 100–200 connections | Adapts to concurrent connection requirements for daily incremental petition cases, avoids exhausting database connections |
| `MONGODB_URI` | Database connection string with exclusive access permissions | Stores unstructured documents and historical archives of petition cases, ensures data isolation |
| `REDIS_URL` | Local cache instance connection string, timeout set to 300 seconds | Caches frequently queried petition case statuses, reduces database load |
| `STORAGE_S3_ENDPOINT` | Exclusive government cloud storage node address | Stores various electronic documents and scanned files from petition handling processes, complies with data security requirements |
| `FE_DOMAIN` | Publicly accessible service domain name | Configures frontend access address, ensures external access channels pass callback verification |
| `ROOT_KEY` | Randomly generated 32-character string | Sets system administrator access key, ensures post-deployment access security |

## Three Common Configuration Errors
- Phenomenon: After running a Docker deployment update, the system version displays a non-target version. Cause: Did not specify a clear version tag when pulling the image, accidentally pulled an unstable or older version image.
- Phenomenon: When configuring DingTalk integration, the open platform prompts "Receiving message address verification failed". Cause: Did not configure `FE_DOMAIN` as a valid publicly accessible domain name, causing external platforms to fail callback verification.
- Phenomenon: When multiple accounts collaborate to handle petition cases, ledger data is out of sync. Cause: Did not correctly configure `REDIS_URL` to enable session state sharing, causing operation states of different accounts to fail real-time synchronization.

## How to Verify Successful Configuration
- Run a database connection test command to verify that the configurations for `DB_MAX_LINK` and `MONGODB_URI` can establish normal connections.
- Access the configured `FE_DOMAIN` to confirm that the frontend page loads normally, and the callback address of external access channels is publicly accessible.
- Upload a petition handling opinion document to verify that the `STORAGE_S3_ENDPOINT` storage configuration can save files normally.
- Log in to the system backend using `ROOT_KEY` to confirm that administrator permission configurations take effect, with no abnormal access permission leakage risks.

The values provided are common starting points and should be measured against the reader's own samples.
