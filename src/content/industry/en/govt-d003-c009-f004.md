# Public Data Catalog and Opening: Ledger Summary and Report Generation - Workflow Orchestration

## What data looks like for this category
Data for this category primarily comes from local public data open platforms, integrated big data platforms, departmental business databases, and electronic certificate repositories. Daily produced documents include public data resource catalogs, data opening lists, data item descriptions, desensitization rules, interface documents, and update frequency descriptions. Data is updated monthly, with fields including data item unique identifiers, affiliated providing departments, desensitization processing requirements, open usage conditions, update cycles, interface call addresses, and more. All data uses structured format, with no large volumes of free-form text content.

## What constraints these characteristics impose on workflow orchestration
The monthly update frequency requires the workflow to support periodic automatic triggering, eliminating repeated manual startup configuration. Multi-source data requires the workflow to support parallel pulling across multiple nodes, integrating structured data from different platforms and databases. Diverse document types have fixed format differences between fields, so the workflow needs a unified field mapping node to align content from all sources to the standard public data catalog structure. Desensitization rules and open usage conditions must be embedded as fixed parameters in workflow nodes to ensure generated ledgers meet compliance requirements. The interface call link must handle response formats from different platforms, so the workflow needs a built-in format verification node to filter invalid data.

## How to set configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Includes data source identifier, desensitization rule ID, update cycle parameters | Used to pass exclusive parameters for each department's data source and compliance verification rules |
| Workflow parallel node count | 3–5 | Pull structured data from multiple sources simultaneously, avoiding blocking from single-node processing |
| HTTP request timeout | 300–600 seconds | Adapt to response durations of multi-platform interfaces, addressing the limitation of the original default 300 seconds |
| `nodeId` | Corresponds to the unique identifier of each data source node | Used for conditional judgment of branch workflows and cross-node result aggregation |
| Format verification matching threshold | 80% matching rate | Filter invalid data that does not conform to the standard public data catalog field structure |
| Report output format | Markdown table + downloadable PDF | Adapt to viewing and archiving requirements for ledger summaries and official reports |

## Three common mistakes
- Symptom: When calling a workflow via API to generate a public data ledger, the returned result is empty. Cause: The correct department data source identifier parameter was not configured in `variables`, causing the workflow to fail to pull structured data from the corresponding source.
- Symptom: A `quote type error` error occurs when configuring a knowledge base association node. Cause: The passed variable was not wrapped in standard format, causing the node to fail to recognize the variable type.
- Symptom: After the HTTP request node executes, the next-level branch workflow is triggered simultaneously and an AI reply is printed. Cause: No preconditions for branch triggering were set, and the workflow executes all subsequent nodes by default.

## How to confirm the configuration is complete
- Manually trigger the workflow once, check the execution logs of each data pulling node to confirm that structured data from multiple sources has been pulled normally.
- Call the test interface with preset `variables` parameters to verify whether the workflow correctly identifies and uses the passed data source identifier and compliance rules.
- Run the format verification node, input test data that does not conform to the standard public data catalog field structure, and confirm that invalid data is filtered.
- Adjust the HTTP request timeout to the recommended range, and verify that no timeout errors occur during interface calls.

The values provided are common starting points and should be measured against the reader's own samples.
