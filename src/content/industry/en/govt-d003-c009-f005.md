# Public Data Catalog and Opening: Ledger Summary and Report Generation — Tool Calling and Plugins

## What data in this category looks like
Data for this category primarily comes from local public data open platforms, integrated big data platforms, departmental business databases, and electronic certificate repositories. Daily maintained documents include public data resource catalogs, data open lists, data item descriptions, desensitization rules, interface documents, and update frequency descriptions. Data is updated once per month. Core fields include data item name, open subject, desensitization method, interface address, update cycle, and authorization conditions. There is no unified fixed unit; the corresponding format must be matched according to specific data items.

## What constraints these characteristics impose on tool calling and plugins
Data for this category has scattered sources, diverse document types, and a fixed update frequency, which creates multiple constraints for tool calling and plugin configuration. Plugins must support multi-protocol adaptation for multiple data sources to ensure catalog data from different platforms can be retrieved. Diverse document structures require tool calling to automatically recognize catalog files in different formats to avoid parsing errors. The fixed monthly update rhythm requires a scheduled synchronization mechanism to ensure ledger data matches actual open data. Field compliance requirements mandate that tool calling verify desensitization rules and authorization conditions to prevent data leakage risks.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `"auto"` | Automatically adapt to different types of public data catalog tool calls, no manual specification of calling method required |
| `functionCall` | `"strict"` | Enforce verification of tool call parameter format and public data field compliance to prevent unauthorized data from being exposed |
| Tool call timeout setting | `300 seconds` | Match the reasonable time required for batch sorting of public data catalogs, prevent timeouts caused by excessive data volume |
| Plugin data source synchronization frequency | `Once per month` | Match the monthly update rhythm of data in this category, ensure ledger data syncs with actual open data |
| Maximum number of returned results | `Top 20 entries` | Limit the number of data items returned per call to avoid excessive consumption of context resources |
| Desensitization rule matching threshold | `0.85–0.95` | Calibrated based on actual testing, ensure a balance between desensitization rule matching accuracy and call efficiency |

## Three common mistakes
- Tool calls return empty results. This occurs when synchronization rules for the corresponding data source are not configured, so valid data from the public data catalog is not retrieved.
- API calls return text slowly. This happens when reasonable tool call timeout and result pagination parameters are not set, leading to excessive time spent processing batch data.
- Function calls trigger parameter validation failures. This is caused by not enabling the strict mode for `functionCall`, so desensitization fields and authorization conditions of public data are not verified.

## How to confirm configuration is complete
- Trigger a preset public data catalog tool call, check if the returned results include all core fields.
- Simulate a monthly data update operation to confirm the plugin automatically syncs the latest open list data.
- Input test parameters that do not comply with desensitization rules to confirm the tool call triggers a compliance validation prompt.
- View the tool call logs in FastGPT v4.17.0 to confirm the timeout setting matches the preset 300-second threshold.

The values provided are common starting points and should be measured against the reader's own samples.
