# Ledger Aggregation and Report Generation for Pension, Work Injury, and Unemployment Benefit Verification: HTTP Interfaces and External Systems

## What this category’s data looks like
Data for this category originates from social insurance management systems, personal benefit records, labor relations and work injury verification systems, and the electronic social security card platform. It is updated daily. Daily associated documents include benefit application forms, payment duration certificates, retirement approval forms, work injury verification materials, and unemployment benefit application materials. Data fields include benefit type, verified amount, applicant identity identifier, review status, and payment cycle, among others. Units include yuan, month, and number of processed cases, among others. The size of a single data record changes based on the total number of verified individuals.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Data sources update daily and cover multiple business systems, so HTTP interfaces must support high-frequency, stable calls to avoid data synchronization delays from request backlogs. Differences in fields across multiple associated documents require interfaces to support flexible parameter passing to adapt to field requirements of different verification scenarios. Data includes sensitive identity information and benefit amounts, so interfaces must enable encrypted transmission to ensure data transfer security. Single record volume grows with the number of verified individuals, so the number of data entries per single request must be limited to prevent transfer timeouts or failures, and to avoid incorrect or missing benefit payments caused by missing fields.

## How to configure settings

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer sk-xxxxxx` (replace with actual generated API key) | Follow HTTP interface authentication specifications to verify the legitimacy of external system calls |
| `variables` | Pass structured parameters including verification cycle, benefit type, and document type, for example `{"startDate":"2024-01-01","endDate":"2024-01-31","certType":"resident ID card"}` | Adapt to business dimension requirements of different ledger aggregations, and flexibly match different scenarios |
| `responseData` | Preset return format `{"status":"success","data":[],"msg":""}` | Unify parsing logic for external systems, reduce cross-system adaptation costs |
| Interface timeout setting | `600 seconds` | Adapt to processing duration of batch benefit verification data, avoid request interruption mid-process |
| Maximum data per single request | First 800 entries | Match daily batch processing scale of social insurance management, ensure transfer stability |

## Three common mistakes
- Interface returns `Data too long for column` error. Cause: No limit on the length of incoming verification data fields, causing external system storage to exceed preset column width.
- Cross-device access to non-login links fails to load ledger data. Cause: No cross-domain access rules configured for the interface, causing browsers to block cross-domain requests.
- Ledger data returned by the interface is missing some fields. Cause: No complete field filtering parameters specified in `variables`, causing the interface to only return default fields.

## How to confirm correct configuration
- Call the test interface, verify that `Authorization` authentication succeeds, and confirm normal business status codes are returned.
- Pass custom `variables` parameters, verify if the interface completes ledger aggregation and report generation according to specified dimensions.
- Simulate batch data requests, confirm no timeouts or data truncation issues occur on the interface.
- Check if the `responseData` return format matches the preset specification, to facilitate data parsing by external systems.
