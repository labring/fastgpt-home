# Ledger Summary and Report Generation for Pension, Work Injury, and Unemployment Benefit Verification: Multi-turn Dialogue and Prompts

## What the data for this category looks like
Data for this category primarily comes from social insurance administration systems, personal benefit records, labor relations and work injury verification systems, and the electronic social security card platform. Data is updated daily. Documents processed daily include benefit application forms, payment period certificates, retirement approval forms, work injury verification materials, and unemployment benefit application materials. Data fields include benefit type, verified amount, applicant identity information, review status, business processing node, and more. Different benefit types correspond to exclusive data structures and verification logic.

## Constraints imposed on multi-turn dialogue and prompts by these characteristics
Data from multiple systems requires multi-turn dialogue processes to support dynamic cross-data source calls. Each interaction must obtain the latest administration system and benefit record information. The daily update frequency requires a real-time data pull mechanism in the dialogue link to avoid using expired verified data. Diverse business document structures require prompts to preset parsing rules for different materials, to accurately extract corresponding fields. Numerous and detailed business fields require clear field definitions during the dialogue process. This avoids matching deviations in core fields such as verified amount and application information, and ensures the accuracy of ledger summary.

## Configuration Setup
The following configurations are adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Maximum context length | 8000–12000 characters | Adapts to the total text length of multiple social insurance business documents, avoiding truncation of core verification information |
| `variables` bound parameters | Bind benefit type, applicant ID | Accurately pull personal benefit records and administration data for the corresponding insured person, narrowing the query scope |
| `messages` history retention count | First 20 dialogue turns | Retains core business interaction logic, filters redundant non-business content, and avoids interfering with verification judgments |
| `chatId` session isolation rule | Isolate by business batch | Distinguishes different benefit verification tasks, preventing confusion between dialogue data from different batches |
| Automatic question optimization | Enabled | Automatically organizes the user's multi-turn requests, clarifies core materials and verification parameters required for verification |

## Three Common Misconfigurations
- Symptom: After calling an HTTP request orchestration node, the output fields of the verification result are not displayed in the dialogue interface. Cause: The HTTP return content is not bound to the `variables` parameter in the dialogue node configuration, so the output is not connected to the dialogue context.
- Symptom: The same material verification question appears repeatedly in multi-turn dialogue. Cause: The `messages` history retention count is not limited, and redundant historical prompts repeatedly trigger the verification logic.
- Symptom: Cross-batch benefit verification data is mixed. Cause: The `chatId` isolation rule is not set by business batch, so data from different sessions overwrites each other.

## How to Confirm Proper Configuration
- Initiate a single-batch benefit verification test dialogue, and check whether the `variables` parameters called in the dialogue are bound to the correct applicant information and benefit type.
- View the session history record, confirm that the number of dialogue entries retained by the `messages` parameter meets the preset range, and there is no redundant non-business interaction content.
- Start two verification sessions from different batches, confirm that the `chatId` isolation rule takes effect, and data is not shared between sessions.
- Trigger the HTTP orchestration node, and check whether the fields related to the returned verification result are displayed in the dialogue interface.
