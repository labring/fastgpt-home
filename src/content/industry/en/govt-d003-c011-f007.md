# Ledger Aggregation and Report Generation for Pension, Work Injury, and Unemployment Benefit Verification: Database and Operations Maintenance

## What This Category of Data Looks Like
This data originates from social insurance management systems, personal benefit records, labor relations and work injury identification systems, and electronic social security card platforms. Daily associated documents include benefit application forms, payment period certificates, retirement approval forms, work injury identification materials, and unemployment insurance benefit application materials.
Data is updated daily. Core fields include personal identity identifiers, benefit verification types, corresponding amounts, review statuses, and processing node times. Fields vary by benefit type, and there is no universal fixed set of fields across all categories.

## What Constraints Do These Characteristics Impose on the Database and Operations Maintenance Link
Multi-source data access requires the database to support cross-system data pulling and format adaptation. Daily update frequency requires configuring incremental synchronization mechanisms to avoid excessive storage and computing resource usage from full synchronization.
Storage of unstructured associated documents requires the database to support binary large object or text field storage. Benefit verification data involves personal rights and fund management, so the database must have data audit and fine-grained permission isolation capabilities.
Ledger aggregation requires batch pulling of multiple batches of verification records, so the database must establish indexes for high-frequency query fields to reduce response latency.

## How to Configure the Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Multi-node connection string with authentication information, set `connectTimeoutMS=60000` | Adapts to multi-source unstructured document storage; long connection timeout accommodates latency from cross-system data pulling |
| `PG_URL` | Read replica connection address, set `statement_timeout=30000` | Used for batch queries of structured verification data; read replicas reduce load on the primary database |
| `DB_MAX_LINK` | 20–30 connections | Adapts to concurrent requests from daily batch ledger aggregation, avoids connection exhaustion |
| `REDIS_URL` | Local cache instance configuration, set `maxmemory-policy=allkeys-lru` | Caches frequently queried benefit verification rules and user permission information to reduce database access pressure |

## Three Common Misconfigurations
- Phenomenon: MongoDB connection timeout occurs. A connection cannot be established after configuring `MONGODB_URI`, but normal connection is possible via mongosh. Cause: The database access whitelist has not been added in the environment where FastGPT is deployed, or the database authentication database is not correctly specified in the connection string.
- Phenomenon: Workflow canvas dragging has significant latency, and node loading is stuttered. This issue is more prominent in FastGPT versions below v4.17.0. Cause: The `DB_MAX_LINK` parameter is not set appropriately. Exhausted concurrent connections cause database response delays, which in turn affect front-end rendering.
- Phenomenon: Ledger aggregation task execution fails, and the number of returned results does not match the actual verified data. Cause: Incremental synchronization mechanisms are not configured, leading to missing partial daily updated data during full pull, or database indexes for high-frequency query fields are not established, resulting in some records not being retrieved.

## How to Confirm Configurations Are Correct
- Run a local database connection test to verify connectivity for `MONGODB_URI` and `PG_URL`, and confirm there are no authentication or network errors.
- Run a single batch of ledger aggregation tasks, observe changes in database connection counts, and confirm that the `DB_MAX_LINK` configuration is not exceeded.
- Check data synchronization logs to confirm that daily updated data has been synchronized to the database via incremental methods, with no missing records.
- Test multiple users initiating ledger query requests simultaneously, confirm that the front-end interface has no significant stuttering, and that database responses meet expectations.
