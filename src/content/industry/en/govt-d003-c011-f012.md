# Ledger Summary and Report Generation for Pension, Work Injury, and Unemployment Benefit Verification: Deployment and Upgrade

## What data for this use case looks like
Data for this use case is sourced from social insurance management systems, personal benefit records, labor relations and work injury identification systems, and electronic social security card platforms. The update frequency is daily. Commonly processed documents include benefit application forms, payment period certificates, retirement approval forms, work injury identification materials, and unemployment benefit application materials. Data fields cover benefit type, verification standard, applicant identity information, review progress, and more. Adaptation is required for structured and unstructured business materials in multiple formats.

## Constraints on deployment and upgrade workflows
Multi-source data docking requires configuring connection parameters compatible with multiple systems during deployment to avoid data synchronization gaps. The daily update frequency requires deploying stable scheduled synchronization tasks. During upgrades, verify the compatibility of task scheduling logic. Diverse business document formats require adapting parsing rules for multiple file types during deployment. During upgrades, retain existing parsing adaptations to prevent business interruptions. Additionally, benefit verification results directly relate to fund payments. Deployment and upgrade workflows must include complete error capture and rollback mechanisms to reduce operational risks.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `STORAGE_S3_ENDPOINT` | Internal organization S3-compatible storage service access address, such as `http://internal-s3:9000` | Used to store all types of business documents related to benefit verification, matching the access rules of internal storage services |
| `DB_MAX_LINK` | `100–150 connections` | Adapts to concurrent requirements of daily batch synchronization of social insurance data, preventing database connection exhaustion |
| `REDIS_URL` | Standard connection format of the Redis service in the deployment environment, including authentication information | Used to cache daily updated personal benefit records and interim benefit verification data to improve query efficiency |
| `FILE_TOKEN_KEY` | `32-character random string` | Used to encrypt access tokens for business documents, ensuring the security of storage and access for application materials |
| `PG_URL` | Standard connection address of the locally deployed PostgreSQL database, including username and password | Used to store structured ledger summary data and historical benefit verification records |

## Three common misconfigurations
- Symptom: After upgrading FastGPT v4.17.0, an error `Failed to create post presigned url` is displayed when uploading benefit application files. Cause: `STORAGE_S3_ENDPOINT` is not configured correctly, or the storage service access permissions are not enabled, resulting in failure to generate pre-signed links for file uploads.
- Symptom: Connection timeouts occur during daily social insurance data synchronization after deployment. Cause: The value of `DB_MAX_LINK` is not set correctly, leading to database connection exhaustion during concurrent synchronization.
- Symptom: Reading fails when calling cached verification data in workflows. Cause: The authentication information for `REDIS_URL` is not configured correctly, preventing connection to the cache service.

## How to confirm configurations are correct
- Upload a test work injury identification material to verify that the `STORAGE_S3_ENDPOINT` configuration is functional, and confirm that file upload can be completed successfully.
- Check database connection monitoring to confirm that the current concurrent connection count meets business requirements, with no connection exhaustion observed.
- Trigger a manual synchronization task, and verify that the synchronized data covers the latest business documents and verification records.
- Log in to the management backend to confirm that the `FILE_TOKEN_KEY` configuration complies with internal security specifications, with no configuration errors present.
