# Ledger Summary and Report Generation for Internal Control Evaluation, Audit and Rectification: HTTP Interfaces and External Systems

## What data for this category looks like
Data for this category comes from enterprise internal control systems, ERP systems, financial sharing systems, audit management systems, and procurement contract project systems. The update frequency is annual.
Daily documents include internal control self-evaluation reports, audit notices, audit working papers, issue lists, rectification ledgers, and rectification closing certificates.
Data fields include issue number, rectification responsible person, rectification completion status, closing confirmation material association identifier, and more. The size of individual documents varies widely, ranging from hundreds to thousands of characters.

## Constraints on HTTP Interfaces and External Systems
The data sources for this category are scattered, document size varies widely, and update frequency is fixed. These factors create multiple constraints for HTTP interface and external system integration.
Dispersed data sources require interfaces to support different authentication rules and adapt to multiple sets of authentication credentials.
The annual update frequency eliminates the need for high-frequency calls, which reduces interface concurrency pressure.
Large-volume documents and attachment data require interfaces to support batch pulling and callback uploads. This avoids single-request timeouts or excessive server load.
Field association requires interface return data to include unique identifiers. This ensures accurate item matching during ledger summarization.

## Configuration Settings
Based on FastGPT v4.17.0, the following configuration items and recommendations apply:

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Configure multiple sets of authentication credentials based on the connected system type, set validity period to `30 days` | Adapt to multiple data source systems; no frequent credential refresh needed under annual update frequency |
| `variables` | Configure data source system addresses and document classification tags as fixed values, set dynamic parameters to `1–100 items/time` | Match the pagination pull limit of different systems, adapt to single-batch data volume |
| `responseData` | Only return issue number, rectification status, and closing time fields; filter redundant attachment content | Compress interface return load, reduce transmission time |
| Request timeout period | Set to `60–120 seconds` based on actual measurements | Adapt to pulling and parsing of large-volume rectification ledger documents |
| Batch pull interval | Configure to `5 seconds/time` | Avoid frequent calls triggering system rate limits |
| Attachment callback address | Fill in the enterprise internal storage system interface | Receive upload results of attachments such as rectification closing certificates |

## Three Common Misconfigurations
- Fail to correctly configure the `variables` parameter when using the HTTP toolset. This prevents passing audit system query conditions. The cause is that dynamic query conditions are not bound to the `variables` variable, leading to missing interface request parameters.
- Receive a `401 Unauthorized` status code from the interface, and cannot pull audit working paper data. The cause is that corresponding `Authorization` credentials are not configured for different data source systems, and general authentication rules are used instead.
- The rectification closing certificate field is empty in ledger summary results. The cause is that the `responseData` parameter is not configured to include the attachment association identifier, or the callback interface does not correctly receive upload results.

## How to Confirm Correct Configuration
- Call the configured interface, and verify that returned data includes preset issue number and rectification status fields. Ensure the field format matches the connected system.
- Simulate a rectification closing certificate upload, and check if the callback interface can correctly receive and associate the upload with the corresponding ledger item.
- Initiate multiple pull requests across different data sources, and confirm no `401` authentication errors occur.
- Adjust request parameters to the maximum single pull volume, and verify the interface does not experience timeout exceptions.
