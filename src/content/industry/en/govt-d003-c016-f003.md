# Medical Insurance Expense Settlement Audit Account Ledger Summary and Report Generation: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
This category of data is sourced from the national medical insurance information platform, hospital HIS and medical insurance interfaces, medical insurance catalog and coding library, and cross-regional medical settlement platform. The update frequency is daily. Daily processed documents include medical insurance settlement lists, expense details, medical record homepages, prescriptions, rejection lists, and settlement reconciliation statements. Data fields cover settlement numbers, insured person identity identifiers, expense detail items, diagnosis, treatment and pharmaceutical consumables codes, audit status, rejection reasons, and more. It includes multiple types of units such as amount, number of visits, and number of days, and there are no fixed unified format specifications.

## What constraints do these characteristics impose on the multi-turn dialogue and prompt engineering link
Load the latest settlement cycle data for each dialogue when working with daily updated data, and clearly specify the data source and time range in multi-turn dialogue. Distinguish the information priority of different channels in the prompt when making mixed calls of multi-source data to avoid data confusion. Guide users to confirm key links such as code matching and expense consistency step by step via multi-turn dialogue, given the diversity and non-standard format of fields, to prevent missing verification items. Control redundant information in context management for batch processed settlement items to avoid exceeding the model's processing limit and affecting audit accuracy.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum context length | 8000–12000 token | Adapts to the field volume and batch item count of medical insurance settlement data, and aligns with the context carrying limit of FastGPT v4.17.0 |
| `variables` | Includes settlement cycle, data source identifier, audit status filter | Adapts to real-time query of daily updated data and multi-source data differentiation, supports parameter transfer for multi-turn dialogue |
| `messages` | Retain the last 3 rounds of dialogue context | Avoids historical redundant information interfering with current audit logic, balances context completeness and processing efficiency |
| Single recall result limit | Top 10 entries | Matches the batch verification requirements of the medical insurance catalog, covers the number of common settlement items |
| Dialogue timeout period | 300 seconds | Adapts to the processing duration of batch settlement data, prevents request interruption due to excessive data volume |
| Result output format | Structured table + remark field | Adapts to the standardized requirements of account ledger summary and report generation, facilitates subsequent reconciliation and appeal |

## Three common mistakes
- Phenomenon: Reuse of settlement detail results generated by prior modules in multi-turn dialogue fails. Cause: Output variables from the preceding node are not bound via the `variables` parameter, so context cannot be passed to subsequent steps.
- Phenomenon: Interface calls return authentication failure or parameter errors. Cause: The application `chatId` is not obtained correctly, or the `messages` and `variables` parameters are not passed as required, which does not comply with interface call specifications.
- Phenomenon: The output account ledger format is chaotic and lacks key audit fields. Cause: Structured output is not clearly required in the prompt, or the result formatting module is not configured, resulting in output content without unified standards.

## How to confirm the configuration is correct
- Initiate a test dialogue for single settlement sheet audit, confirm that the loaded context fields match the preset `variables` parameters.
- Call the interface with the `messages` parameter to verify that historical dialogue content is correctly included in the current context.
- Trigger a batch audit task to check whether the output result conforms to the preset structured account ledger format.
- Simulate an authentication request to confirm that the `chatId` and key configuration can normally initiate dialogue requests.
