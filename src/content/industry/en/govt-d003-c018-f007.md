# Ledger Aggregation and Report Generation for Social Insurance Enrollment and Payment Verification: Database and Operations

## What Data for This Use Case Includes
Data sources include social insurance management systems, tax social insurance premium collection systems, market entity registration information, and shared public security and civil affairs data.
Daily processed documents include enrollment registration forms, payment base declaration forms, personnel change forms, social insurance premium verification forms, and personal benefit records.
Each document contains fields such as personnel identity information, labor relationship status, and payment base.
Data is updated daily. Personnel change and payment record information must be synchronized across multiple source systems.
Core time-consuming steps include verifying personnel identity and labor relationships, processing unit personnel changes and base declarations, and reconciling data with tax collection systems.

## Constraints for Database and Operations
Daily multi-source data synchronization creates bulk write and read pressure. Sufficient connection pool resources must be maintained to avoid task blocking.
Field differences across multiple source systems require unified validation rules to prevent database ingestion failures caused by format mismatches.
Personnel identity and labor relationship verification requires frequent associated data queries. Indexes must be optimized to reduce query latency.
Reconciliation operations with tax collection data must ensure transaction consistency to avoid underpayment or missed payment issues caused by data inconsistencies.
Data errors directly affect personal benefit records and benefit applications. Complete backup and rollback mechanisms must be established.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `MONGODB_URI` | Configure as a cluster connection string with authentication credentials, for example `mongodb://admin:SecurePass123@mongo-01:27017,mongo-02:27017/social_insurance?authSource=admin` | High-availability connections are required for multi-source data synchronization to avoid single points of failure disrupting ledger generation tasks |
| `PG_URL` | Configure as a read-replica connection string for tax or social insurance business databases, for example `postgresql://si_user:DbPass456@pg-read-replica-01:5432/social_insurance?sslmode=require` | Separate read and write operations to reduce pressure on the primary database and ensure response speeds for bulk queries |
| `DB_MAX_LINK` | Set to `200-300` | Adapt to concurrent connection requirements for daily bulk personnel changes and payment verification tasks, avoiding connection exhaustion |
| `REDIS_URL` | Configure as an authenticated single-node connection string, for example `redis://RedisPass789@redis-cache-01:6379/0` | Cache frequently queried personnel identity verification data to reduce direct database access requests |

## Three Common Misconfigurations
- Symptom: After starting the Docker container, the service status shows up, but accessing port 3000 returns a database connection failure. Logs show MongoDB authentication failure. Cause: The username and password configured in `MONGODB_URI` do not match the actual authentication information of the MongoDB instance, or MongoDB authentication mode is not enabled.
- Symptom: Bulk ledger generation tasks time out and return a 504 status code. Cause: The `DB_MAX_LINK` configuration value is too low, causing the connection pool to be exhausted and unable to process bulk write requests in a timely manner.
- Symptom: Some personnel information is missing from generated social insurance payment verification forms. Cause: `PG_URL` is not correctly configured to point to the correct table structure of the business database, preventing complete payment base declaration data from being read.

## How to Confirm Correct Configuration
- Run a local MongoDB connection command using the connection string configured for `MONGODB_URI` to verify successful authentication.
- Run a bulk personnel change data import script and monitor service logs to confirm no connection exhaustion related errors occur.
- Submit a single batch of social insurance payment verification ledger generation tasks, and verify that returned result fields match the standard structure of enrollment registration forms and payment base declaration forms.
- Review Redis monitoring data to confirm that the cache hit rate for frequent identity verification requests meets business requirement thresholds, and adjust based on actual measurements.
