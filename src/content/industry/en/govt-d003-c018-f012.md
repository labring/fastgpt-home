# Ledger Aggregation and Report Generation for Social Insurance Enrollment Registration and Payment Verification: Deployment and Upgrade

## What this category of data looks like
This category of data originates from social insurance management systems, tax social insurance premium collection systems, market entity registration information, and shared public security and civil affairs data, and is updated daily. Daily processed documents include enrollment registration forms, payment base declaration forms, personnel change forms, social insurance premium verification notices, and personal benefit records. Core fields cover personnel identity identifiers, enrollment status, payment base, verified amount, and more. Data is sourced from multiple cross-departmental systems, requiring matching of multi-dimensional information to complete verification.

## What constraints these characteristics impose on the deployment and upgrade phase
Multi-system cross-departmental data sources require configuring multi-data source connectivity verification during deployment, to avoid single-system interface fluctuations affecting ledger generation. Daily update frequency requires task scheduling cycles adapted to daily batch processing, to prevent task backlogs from causing data delays. Processing multiple types of structured documents requires preset parsing rules for corresponding fields; upgrades must be compatible with legacy document field mapping logic. Cross-entity verification logic must retain historical configuration compatibility, to prevent configuration changes from causing reconciliation deviations, which could lead to underpayment, missed payments, or incorrect personal benefit records.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `PG_URL` | `postgresql://username:password@host:5432/fastgpt?schema=public` | Adapts to FastGPT v4.17.0 structured data storage specifications, ensuring multi-table query efficiency for social insurance-related data |
| `REDIS_URL` | `redis://:password@host:6379/0` | Used to cache daily updated personnel enrollment status data, reducing repeated query overhead. It is recommended to set the cache validity period to 3600 seconds |
| `STORAGE_S3_ENDPOINT` | `http://minio.example.com:9000` | Stores document attachments such as enrollment registration forms and payment verification notices. It is recommended to set the single file maximum size to 1000 MB |
| `DB_MAX_LINK` | `20–30` | Adapts to multi-system concurrent query scenarios, avoiding task interruptions caused by exceeding connection limits |
| `MONGODB_URI` | `mongodb://username:password@host:27017/fastgpt?authSource=admin` | Stores unstructured original personal benefit record data, supporting flexible field expansion |
| `FILE_TOKEN_KEY` | `Custom random string` | Ensures interface security for document uploads, preventing unauthorized access to attachment files required for ledger generation |

## Three common configuration errors
- Phenomenon: After upgrading the version, executing a file upload operation returns the error `Failed to create post presigned url`. Cause: `STORAGE_S3_ENDPOINT` and corresponding storage keys are not configured correctly, making it impossible to generate valid pre-signed URLs for file access.
- Phenomenon: When batch processing personnel change data for social insurance enrollment, the system reports the error `worker terminated due to reaching memory limit`. Cause: The `DB_MAX_LINK` parameter has not been adjusted to limit concurrent connections, or the caching strategy corresponding to `REDIS_URL` has not been optimized, leading to exceeding memory usage limits.
- Phenomenon: When migrating deployment to a new server without using Docker, the original deployed data source configuration cannot be loaded, causing ledger generation tasks to fail. Cause: Original database configuration information and related parameters such as `PG_URL` and `MONGODB_URI` were not exported and imported, preventing the system from connecting to the original data sources.

## How to verify the configuration is correct
- Execute a test social insurance data synchronization task, check whether the data source connection status is normal, and confirm that configurations such as `PG_URL` and `MONGODB_URI` can normally access corresponding systems.
- Upload a standard enrollment registration form document, verify that the file upload interface can normally generate pre-signed URLs, and confirm that the `STORAGE_S3_ENDPOINT` configuration is valid.
- After adjusting the `DB_MAX_LINK` parameter, simulate multi-concurrent ledger generation tasks, observe system resource usage, and confirm that the configuration adapts to concurrent requirements.
- View system logs, confirm that the cache service connection status is normal, and verify that the `REDIS_URL` configuration is correct.
