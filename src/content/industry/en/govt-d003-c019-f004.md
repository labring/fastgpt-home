# Ledger Aggregation and Report Generation: Workflow Orchestration for Dual Random Inspection and Public Disclosure Regulatory Checks
This document is compatible with FastGPT v4.17.0.

## What data looks like for this use case
This use case sources data primarily from the dual random inspection and public disclosure regulatory platform, enterprise credit information public disclosure system, industry regulatory systems, and law enforcement officer directory. Data updates once per month.
Common generated documents include inspection plans, inspected object lists, inspection item lists, on-site inspection records, rectification notices, and inspection result public notices.
Typical fields include the unified social credit code of regulatory objects, inspection items, law enforcement officer ID number, inspection time, and rectification completion status. No custom statistical units appear, and all fields follow standard regulatory business formats.

## What constraints do these characteristics impose on workflow orchestration
Scattered data sources require cross-system data pulls. Configure multiple nodes to call different data source interfaces in sequence. This stops full workflow failure from single node failure.
Monthly fixed updates to inspected objects and item lists require scheduled trigger nodes. This ensures data timeliness.
Multiple document fields with cross-document relationships require using `variables` to bind field mapping rules. This ensures accurate field matching during ledger aggregation.
Dynamic updates to the law enforcement officer directory require workflows to pull latest personnel information in real time. This avoids non-compliant selections.
Add result verification nodes. This prevents missed inspection result public notices or duplicate report generation.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Scheduled Trigger Cycle | Monthly, 2-4 AM | Matches monthly regulatory data update rhythm, avoids resource usage during business peak hours |
| `nodeId` configuration | Assign unique identifiers to each data source, mapping, and verification node | Ensures execution order is controllable during multi-node runs, prevents mixed-up node calls |
| `variables` binding rules | Core fields including unified social credit code, inspection items, law enforcement officer ID number | Ensures accurate cross-document data association, prevents field misalignment during ledger aggregation |
| Node Failure Retry | Retry 2 times, 60 second interval | Addresses temporary network fluctuations or short-term data source interface errors, ensures workflow stability |
| Single Call Timeout | 300 seconds | Matches typical response duration for pulling large volumes of regulatory data across systems |
| Result Verification Node | Check completeness of inspection result public notice fields | Prevents regulatory compliance issues such as missed public notices |

## Three Common Misconfigurations
- Phenomenon: After configuring multiple workflow nodes, some nodes fail to trigger or execute in incorrect order. No corresponding node call logs appear. Cause: Dependency relationships between nodes are misconfigured, or execution links are not bound via `nodeId`. The system cannot recognize node trigger order.
- Phenomenon: After deploying with docker-compose, workflow and knowledge base pages show as empty, but interfaces function normally. Cause: Persistent storage directory was not mounted during deployment. Locally cached configuration data is lost after container restart.
- Phenomenon: Some regulatory object information is missing during ledger aggregation. Generated report fields are empty. Cause: Correct field mapping rules were not configured via `variables`. Cross-document pulled data cannot match corresponding ledger items.

## How to Confirm Proper Configuration
- Review the workflow node list. Confirm all configured data source, mapping, and verification nodes are arranged in expected order.
- Trigger a test run. Check logs for call records of all nodes, and confirm no error messages exist.
- Export a test report. Verify core fields match the preset `variables` mapping rules.
- Check the scheduled trigger node configuration. Confirm trigger time matches regulatory data update rhythm.
