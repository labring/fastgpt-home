# Random Inspection and Public Disclosure Supervision Check: Ledger Summary and Report Generation - Deployment and Upgrade

## What this category of data looks like
This category of data typically comes from the random inspection and public disclosure supervision platform, enterprise credit information public disclosure system, industry supervision system, and law enforcement officer directory. It updates monthly. Daily documents include inspection plans, inspection target lists, inspection item lists, on-site inspection records, rectification notices, and inspection result public notices. Core fields include unified social credit codes of inspection targets, law enforcement officer IDs, inspection item entries, rectification completion status, and more. The number of fields and their associated relationships per document vary based on inspection hierarchy and item type.

## What constraints these characteristics impose on deployment and upgrade
Monthly updated data sources need stable scheduled synchronization tasks configured during deployment, to keep core data like inspection targets and law enforcement officers up to date. Multi-source heterogeneous document structures need data parsing rules adapted to different formats during deployment, to avoid field matching errors. Core data compliance requirements need data verification logic retained during upgrades, to prevent non-compliant inspection target extraction or missed result disclosure caused by configuration changes. It also needs compatibility with interface call permissions of original supervision systems.

## How to configure
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `PG_URL` | Dedicated connection address pointing to the supervision data synchronization database | Used to store structured ledger data such as inspection targets and law enforcement officers, must be permission-isolated from the supervision platform database |
| `REDIS_URL` | Connection address configured for a local cache instance, with cache validity set to 7200 seconds | Caches frequently called inspection item lists and law enforcement officer directories, to reduce call frequency to external data sources |
| `STORAGE_S3_ENDPOINT` | Endpoint address bound to the local block storage service | Used to store unstructured documents such as on-site inspection photos and scanned copies of rectification notices, to meet supervision archive retention requirements |
| `DB_MAX_LINK` | 20 concurrent connections | Adapts to concurrent scenarios where multiple law enforcement officers query ledgers simultaneously, to avoid database connection exhaustion |
| Scheduled synchronization cycle | Triggered once every 720 hours | Matches the monthly update frequency, to ensure ledger data stays synchronized with the supervision platform |
| Document parsing rules | Field matching thresholds calibrated through actual testing | Adapts to format differences across multi-source documents, to improve field extraction accuracy for ledger summary |

## Three common mistakes
- First, unstructured documents like on-site inspection photos fail to parse correctly, with field extraction left empty. This happens when `STORAGE_S3_ENDPOINT` is not configured, or storage permissions are insufficient, so images cannot be synchronized to the parsing node.
- Second, inspection target lists do not update promptly after scheduled synchronization tasks run. This happens when the scheduled synchronization cycle does not match the monthly update rhythm, or the database pointed to by `PG_URL` has restricted permissions, preventing complete data from being pulled.
- Third, duplicate supervision target entries appear in generated inspection result public notice reports. This happens when data deduplication logic is not configured, or the cache validity period set for `REDIS_URL` is inappropriate, leading to repeated pulling of inspection target data from the same batch.

## How to confirm the configuration is correct
- Test the connection status of `PG_URL` in the background database management module of FastGPT v4.17.0, and confirm that test inspection target list data can be pulled.
- Manually trigger a scheduled synchronization task, check the update time of ledger data, and compare it with the latest update time of the supervision platform.
- Upload an on-site inspection record document, verify that core fields such as law enforcement officers and inspection items can be correctly extracted to generate structured ledger entries.
- Generate a monthly inspection report, and check whether the number of supervision targets in the report matches the actual number of entries in the ledger database.

The values provided are common starting points and should be measured against the reader's own samples.
