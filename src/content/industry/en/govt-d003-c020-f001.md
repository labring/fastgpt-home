# Ledger Summary and Report Generation for Territorial Spatial Planning Compilation and Implementation Evaluation: HTTP Interfaces and External Systems
Reference only; verify against the target FastGPT release and deployment documentation.

## What this category of data looks like
Data for this category comes from four core sources: territorial spatial basic information platform, natural resource survey and monitoring data, population and economic statistics, and remote sensing images. The update frequency is annual.
Documents processed daily include territorial spatial overall plans, detailed plans, special plans, planning implementation evaluation reports, public opinion summaries, and more. The data structure includes fields such as spatial coordinates, constraint indicators, population and economic statistical values, and remote sensing image metadata. Units match the data type, for example, hectares, ten thousand people, square kilometers.
Multi-source data have large format differences. Some spatial data are in binary format, while text data include structured public opinion summary entries.

## What constraints do these characteristics impose on HTTP interfaces and external systems?
The annual update business rhythm requires low interface call frequency. This avoids triggering rate limiting rules of connected platforms.
Multi-source data format differences and large volume require interfaces to support different types of data transmission and parsing. It also requires adaptation to complex authentication rules of natural resource department platforms.
The document structure includes multi-dimensional ledger fields. Interface requests must pass precise filter parameters. Otherwise, matching target data fails.
In addition, public opinion summary text may contain large amounts of Chinese content. Ensure interfaces support normal transmission of Chinese encoding to avoid parsing errors.

## Configuration recommendations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Configure according to the authentication rules of the connected platform, usually in the `Bearer {apikey}` format | Meets standard authentication requirements for most natural resource department platforms |
| `variables` | Include parameters such as planning area scope, data year, indicator type. Total length per transmission must not exceed 800 characters | Accurately matches multi-source data filter conditions for ledger summary, prevents requests from being blocked due to excessive length |
| `responseData` | Return in structured JSON format, including ledger entries, report summary, error log fields | Facilitates subsequent automatic organization of core content of planning reports |
| Request timeout period | 600–1200 seconds | Adapts to transmission requirements for large-volume spatial data and remote sensing images |
| Chinese filename handling | Pass filenames using UTF-8 encoding | Prevents garbled characters during knowledge base upload |
| Call frequency limit | No more than 10 times per day | Matches the annual update business rhythm, avoids triggering platform rate limiting |

## Three common mistakes
- Receiving two requests when calling an interface, with the second request missing or having an incorrect `Authorization` header. Cause: The interface retry mechanism was not configured correctly. Retried requests do not carry correct authentication parameters.
- Garbled characters appearing when uploading knowledge base files with Chinese names. Cause: Filename parameters were not passed using UTF-8 encoding, causing the system to fail to parse Chinese filenames correctly.
- The `responseData` field returned by the interface is empty or has an abnormal format. Cause: Planning data year or area parameters were not accurately passed in `variables`, leading to failure to match target ledger data.

## How to confirm correct configuration
- Initiate an interface request that includes planning area and data year parameters. Check if the returned `responseData` includes expected ledger entry fields.
- Upload a test file with a Chinese name. Confirm that the filename displays correctly in the knowledge base with no garbled characters.
- View interface call logs. Confirm that only one valid request was triggered, with no duplicate call records.
- Verify the `Authorization` header configuration. Confirm that it matches the authentication format required by the connected platform.
