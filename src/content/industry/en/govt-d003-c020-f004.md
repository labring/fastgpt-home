# Territory Spatial Planning Compilation and Implementation Evaluation: Ledger Summary and Report Generation — Workflow Orchestration

## What This Category's Data Looks Like
Data for this category originates from the territorial and spatial basic information platform, natural resource survey and monitoring data, population and economic statistical data sources, and remote sensing images. The update frequency is annual. Daily produced documents include territorial and spatial overall plans, detailed plans, special plans, planning implementation evaluation reports, and public opinion summaries. Data fields cover spatial coordinates, binding indicators, population and economic statistical values, and similar items. Common units include square kilometers, person-times, ten thousand yuan, and similar units. Document structures are typically split by regional hierarchy and planning timeline.

## What Constraints These Characteristics Impose on Workflow Orchestration
The annual update data source feature requires workflows to support batch data pulling and scheduled synchronization. Multi-source heterogeneous data includes spatial vector, statistical tables, and remote sensing images. Each data type needs a dedicated format parsing node. Unstructured text from public opinion summaries requires a pre-cleaning step. Regional-level data has a large volume. Single-node input scale must be limited to avoid runtime timeouts. Planning documents have multi-chapter structures. These must be split and transferred by module. A cross-department ledger data consistency check step must be added. This prevents binding indicator mismatches from affecting final planning approval.

|---|---|---|
| `variables` | Bind the territorial and spatial basic information platform interface address, annual data update cycle parameters | Match annual update data synchronization requirements, enable dynamic pulling of the latest ledger data |
| Single request data volume | `500–800 entries` | Match the single loading limit for regional-level ledger data, avoid runtime timeouts |
| Timeout threshold | `600 seconds` | Adapt to the average time required for multi-source spatial data parsing, prevent long-process task interruptions |

| Result output format | Generate HTML structure according to planning document templates | Match the standardized output requirements of planning reports, support direct embedding into final documents |

## Three Common Misconfigurations
- Workflow runtime errors report invalid key, with status code 401. Cause: The account access key was mistakenly bound to workflow variables, and the application-specific key was not used to configure interface access permissions.
- HTML code output mid-workflow is not displayed in the interface, and the process proceeds directly to the next processing branch. Cause: The trigger rules for the result output node were not configured correctly, causing the HTML fragment to be transferred to downstream nodes before being captured.
- Overall workflow runtime exceeds expected duration, and ledger summary cannot be completed on schedule. Cause: Single request data volume was not limited, causing batch loading of multi-source spatial data to occupy excessive runtime resources.

## How to Verify Correct Configuration
- Verify that the interface address bound to `variables` matches the official address of the data source, and confirm that parameters match the annual data update cycle.
- Test a single data pull request, confirm that the runtime duration does not exceed the configured timeout threshold.
- Trigger an abnormal data branch, confirm that the workflow diverts to the corresponding processing node according to preset rules.
- Generate a test version of the planning report, confirm that the HTML output fragment conforms to the preset document structure requirements.
