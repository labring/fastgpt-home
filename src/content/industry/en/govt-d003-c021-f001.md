# Ledger Aggregation and Report Generation for Centralized Treasury Payment and Reimbursement Audit: HTTP Interfaces and External Systems

## What data for this category looks like
Data for this category comes from the centralized treasury payment system, unified budget management system, electronic invoice platform, and contract management system. The update frequency is daily. Daily processed documents include payment applications, fund use plans, invoices, contracts, acceptance receipts, reimbursement approval forms, and payment vouchers. Core fields include budget indicator code, economic classification code, payment amount, approval status, refund flag, and more. Primary units are RMB yuan and business batch numbers.
This data is maintained daily by finance departments of budget units, treasury payment centers of finance departments, and finance review posts of competent departments. It focuses on the execution stage of individual fund payments, and is distinctly different from periodic aggregated data for budget final accounts.

## What constraints these characteristics impose on HTTP interfaces and external systems
Multiple external data sources require HTTP interfaces to support cross-system authentication and parsing of different data formats. The daily update frequency requires interfaces to support scheduled pulling or incremental synchronization to avoid performance loss from full data pulls. Compliance requirements for core business fields mean interfaces must transmit key information such as budget indicator code and economic classification code; failure to do so will lead to ledger aggregation errors. Compliance risks for individual payments require interfaces to include failure retry and data validation capabilities to prevent fund mispayment or audit issues caused by interface anomalies. Diverse business document types require interfaces to support flexible field extraction rules to ensure ledger data integrity.

## How to configure settings
| Configuration Item | Recommended Value | Basis for This Setting |
| --- | --- | --- |
| `Authorization` | `Bearer {external system API key}` | Complies with HTTP interface authentication standards, passes identity verification when connecting to the centralized treasury payment system |
| `variables` | `{"requiredFields": ["budgetCode", "paymentAmount", "approveStatus"], "syncMode": "increment"}` | Transmits required business fields and synchronization mode to meet parameter needs for ledger aggregation |
| `responseData` | `Only retain fields: paymentId, invoiceNo, refundFlag, reportDate` | Filters non-essential data to reduce interface transmission load and match field requirements for report generation |
| Interface retry threshold | 3 times, 60-second interval | Addresses temporary fluctuations in treasury systems to ensure successful data pulling |
| Scheduled pull interval | 86400 seconds | Matches daily business data update frequency to avoid repeated pulling or delayed synchronization |
| Data validation rules | Validate that paymentAmount is a positive number and budgetCode format is compliant | Avoids compliance risks such as fund mispayment |

## Three common configuration errors
- Phenomenon: After the FastGPT container restarts, the `Authorization` authentication configuration for external system interfaces is lost. Cause: The interface key and synchronization rules were not stored in a persistent storage volume, so temporary configurations are cleared after container restart.
- Phenomenon: Calling the treasury system interface returns a 400 error, prompting missing required fields. Cause: Required business fields were not declared in `variables`, so the interface does not return corresponding data.
- Phenomenon: The ledger aggregation report does not include payment records updated on the current day. Cause: The scheduled pull interval was set too long, not matching the daily update frequency of business data.

## How to confirm correct configuration
- Use the interface debugging tool of FastGPT v4.17.0 to check if `responseData` returns preset core business fields such as paymentId, invoiceNo, approveStatus.
- Trigger a manual pull task and review the generated ledger to confirm it includes payment and reimbursement records updated on the current day.
- Simulate an interface return of a 401 error to verify if the system triggers the preset retry mechanism.
- Check if the business rules configured in `variables` match the current business scenario, including the required field list and synchronization mode.
