# Ledger Summary and Report Generation for Centralized Treasury Payment and Reimbursement Audit: Multi-turn Dialogue and Prompting

## What this category of data includes
This category of data comes from centralized treasury payment systems, unified budget management systems, electronic invoice platforms, and contract management systems. The update frequency is daily. Daily processed documents include payment applications, fund allocation plans, invoices, contracts, acceptance reports, reimbursement approval forms, and payment vouchers. Single-item data includes fields such as payment application number, fund allocation plan quota, invoice amount, contract number, acceptance report number, reimbursement approval form number, and payment voucher number. This covers information across the full chain of budget indicator verification, document audit, and payment execution.

## Constraints on Multi-turn Dialogue and Prompting
Data sources are scattered and updated daily. Multi-turn dialogue must pull the latest data from centralized treasury payment and unified budget management systems for each call. This avoids using expired budget indicators or payment quotas. Daily documents include multiple types of related vouchers. Prompts must explicitly require the system to verify the corresponding relationship between invoices, contracts, and acceptance reports. Prompts must also associate the approval status of reimbursement approval forms. Single-item data has many fields. Multi-turn dialogue must gradually guide users to supplement missing fields. This prevents missing fields in generated ledgers or reports. The audit link involves fund compliance. Prompts must include compliance verification logic. This ensures coverage of budget indicator and economic classification verification requirements.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Maximum Context | First 10,000 characters | Covers voucher text across the full payment chain, avoiding truncation of critical contract and acceptance report information |
| Single Search Limit | Top 5 entries | Matches the latest payment records in the centralized treasury payment system, avoiding interference from redundant data |
| Query Optimization | Enabled | Organizes scattered user queries into standardized ledger summary requests, adapting to the field requirements of fiscal data |
| `variables` | Pass budget unit code, payment date range | Limits data scope, narrows the target dataset for search matching, and adapts to the variable call logic of FastGPT v4.17.0 |
| `messages` | Append historical interaction content by dialogue turn | Retains confirmed audit conditions from users, avoiding repeated inquiries of the same information |
| `chatId` | Bind current audit task ID | Associates ledger data for the corresponding task, ensuring context consistency across multi-turn dialogue |

## Three Common Misconfigurations
- Symptom: When initiating a dialogue via API, the generated ledger summary results do not associate with knowledge base documents from the centralized treasury payment system. Cause: Failed to pass the correct budget unit code or payment date range in `variables`, so the system cannot match documents from the corresponding data source.
- Symptom: When using a specific version of FastGPT, the dialogue page or knowledge base page crashes. Cause: The deployed version does not clear context cache properly. Cumulative text from multi-turn dialogue exceeds the system memory threshold.
- Symptom: When deploying a model via Ollama, preset reimbursement audit guiding prompts do not take effect. Cause: The forced enabling option for guiding prompts was not turned on in the dialogue configuration, or the thinking tags output by the model were not parsed correctly.

## How to Verify Proper Configuration
- Initiate a test dialogue including a specific budget unit code and payment date range. Confirm if returned ledger data includes voucher information from corresponding systems.
- Review multi-turn dialogue context records. Verify that the `messages` field correctly appends historical interaction content, with no repeated inquiries.
- Check if the task ID bound to `chatId` matches the current audit task. Ensure context is not mixed across tasks.
- Initiate a simulated query for order rejection or payment correction. Confirm that the system prompt covers compliance verification logic.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
