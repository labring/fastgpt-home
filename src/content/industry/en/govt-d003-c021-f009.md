# Ledger Consolidation and Report Generation for Centralized Treasury Payment and Reimbursement Audit: Model Access and Configuration

## What the data for this use case looks like
Core data for this use case originates from the centralized treasury payment system, unified budget management system, electronic invoice platform, and contract management system. The update frequency is daily. Documents processed daily include payment applications, fund use plans, invoices, contracts, acceptance receipts, reimbursement approval forms, and payment vouchers. Each document contains fixed fields such as budget indicators, economic classification, amount, and approval status. Data exists as a mix of structured forms and unstructured text. Export formats vary slightly across different systems. Integration is required to create unified ledgers and reports.

## What constraints do these characteristics impose on model access and configuration
High-frequency daily updated data requires the model access link to support scheduled batch processing, to avoid context overflow caused by excessive single-batch data volume. Multi-source heterogeneous data formats require the model to have cross-system data alignment capabilities. Configurations must therefore adapt to multi-tool call logic. The precise extraction requirement for fixed fields requires controlling the randomness of model output to a low range, to prevent missing or erroneous compliance fields. Access restrictions from different systems require API endpoint configuration to adapt to intranet environments, ensuring data transmission security and compliance. Strict adherence to financial data confidentiality specifications is also required.

## How to set the configuration
| Configuration Item | Recommended Setting Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Covers the context of multiple documents updated in a single daily batch, avoiding truncation of key compliance fields such as budget indicators and economic classification |
| `maxTokens` | 2000–3000 token | Meets the output length requirement for a single ledger consolidation report, adapting to standard financial report formats |
| `temperature` | 0.1–0.3 | Reduces output randomness, ensuring accuracy and compliance of financial data review, and avoiding field errors |
| `toolChoice` | auto | Automatically selects tools to handle format alignment and field extraction for multi-system data, adapting to multi-source data integration needs |
| `AIPROXY_API_ENDPOINT` | Fill in the official proxy address according to the deployment environment | Adapts to intranet access restrictions of financial systems, ensuring data transmission security |
| `AIPROXY_API_TOKEN` | Generate a dedicated token according to the authorization document | Verifies call permissions, preventing unauthorized access to financial-related data |

## Three common mistakes
- Phenomenon: The interface prompts "No available channel for model qwq:latest under current group default". Cause: The API endpoint and key for this model have not been added in FastGPT's model group configuration, resulting in missing call permissions.
- Phenomenon: A port occupied error is prompted when deploying a model with Ollama. Cause: Another local service occupies port 500, or the Ollama access port has not been modified in FastGPT configuration.
- Phenomenon: Key fields are missing in the generated ledger report. Cause: `maxContext` is set too small, truncating core information from multi-system documents, preventing the model from fully extracting compliant data.

## How to confirm the configuration is complete
- Staff access the FastGPT v4.17.0 backend, enter the model management page, and confirm the target model has been added to the corresponding group, and that `AIPROXY_API_TOKEN` has not expired.
- Staff run a test synchronization task for a single daily data batch, review system logs, and confirm no context truncation, API call failure, or timeout errors.
- Staff generate a simulated ledger consolidation report, verify field completeness and format, and confirm compliance with financial document specification requirements.
- Staff check the system scheduling record, confirm the daily update task triggers normally, with no abnormal exits or data loss.
