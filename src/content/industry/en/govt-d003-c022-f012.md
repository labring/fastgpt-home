# Ledger Summary and Report Generation for Land Use Rights, Mining Rights, and State-owned Property Rights Transactions: Deployment and Upgrade

## What this category of data looks like
This category of data mainly comes from the national public resource trading platform, natural resource trading systems, property right exchange systems, and state-owned asset supervision systems. The update frequency is daily. Daily processed documents include transfer announcements, trading notices, bid application documents, margin vouchers, transaction confirmation letters, listing result announcements, property right transfer specifications, and more. Core fields involve transaction object ownership, restriction conditions, margin amount, transaction confirmation information, and more. There are certain differences in document formats and field naming across different data sources.

## What constraints these characteristics impose on deployment and upgrades
Daily updated data requires stable scheduled synchronization tasks to ensure the real-time nature of ledger data. Integrations with multi-source systems must adapt to different interface specifications and permission verification rules to avoid data pull failures caused by interface incompatibility. Diverse document types require pre-configured multi-format parsing rules to adapt to structural differences in documents such as transfer announcements and transaction confirmation letters. Core fields such as ownership information and margin amount have high accuracy requirements. Targeted field verification logic must be configured during deployment. When upgrading versions, compatibility with previously connected trading system interfaces must be maintained to avoid synchronization link interruptions caused by version updates.

## How to set the configurations
All configurations below are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Configure a dedicated MongoDB cluster address, set `DB_MAX_LINK` to 50 | Store ledger and trading document metadata to ensure stability for concurrent synchronization |
| `PG_URL` | Configure a PostgreSQL instance address, set connection timeout to 600 seconds | Store transaction audit logs to ensure stability of long-running log storage |
| `REDIS_URL` | Configure a Redis instance with memory capacity of 1000–2000 MB, enable RDB persistence | Cache daily synchronized trading data and interface responses to reduce pressure on source system calls |
| `STORAGE_S3_ENDPOINT` | Configure an object storage endpoint in the same region as the public resource trading platform | Store original trading documents to ensure document access latency meets business requirements |
| `FILE_TOKEN_KEY` | Generate a 32-character random string as the secret key | Encrypt document access tokens to prevent unauthorized document downloads |
| `ROOT_KEY` | Configure a high-complexity string containing uppercase and lowercase letters, numbers, and symbols | Serve as the platform's highest permission secret key to ensure background configuration security |

## Three common configuration errors
- Symptom: After starting with docker-compose, the `aiproxy` container reports an error after running for a period of time, indicating curl execution failed. Cause: Network connectivity to the source trading system is not configured, or the storage endpoint configured in `STORAGE_S3_ENDPOINT` cannot be accessed normally.
- Symptom: Existing synchronization tasks cannot pull trading data after upgrading the version. Cause: The new version's interface call specifications are not compatible, or the connection configuration for `MONGODB_URI` was not adjusted along with the version update.
- Symptom: Margin fields in ledger data are empty or have incorrect formatting. Cause: No verification rules are configured for core fields of this category, resulting in non-standard format fields failing to be extracted correctly.

## How to verify a successful configuration
- View the scheduled synchronization task execution logs to confirm that daily data pull tasks from specified source systems have no abnormal interruptions.
- Upload typical documents of this category to verify that extraction results of core fields such as ownership information and margin amount meet business requirements.
- Check the connection status of `REDIS_URL` to confirm that the cache service is running normally.
- Test the login function using the highest permission secret key to confirm that the `ROOT_KEY` configuration is effective.

The values given are common starting points and should be measured against the reader's own samples.
