# Work Safety Hazard Inspection and Governance: Ledger Summary and Report Generation — HTTP Interfaces and External Systems

## What Data This Category Covers
Data for this category comes from work safety supervision systems, enterprise self-inspection systems for hazards, law enforcement inspection records, and accident statistics systems. The update frequency is daily. Commonly generated documents include hazard inspection lists, hazard governance ledgers, rectification notices, review records, and major hazard suspension and supervision notices. Data fields include hazard ID, hazard category, inspection time, rectification responsible person, rectification deadline, rectification measures, review results, supervision status, and more. Core indicators are counted in units of items and entries, covering full-process information from hazard inspection to case closure and archiving.

## Constraints Imposed on HTTP Interfaces and External Systems
Dispersed data sources require interfaces to accommodate format differences across multiple external systems, and support field mapping and standardization processing. The daily update frequency requires interface call cycles to align with business rhythms, to avoid excessive calls or missed data. The large number of daily document fields and fixed core fields require interfaces to support specifying returned fields to reduce transmission overhead. Enumeration values for rectification status must be uniformly standardized to ensure correct parsing by external systems. Additionally, business errors carry severe consequences, so interfaces must include failure retry and log recording capabilities to ensure complete and traceable data pulling.

| `Authorization` | `Bearer {custom API key}` | Follow HTTP interface authentication specifications to secure external system access |

| `responseData` | `return hazard ID, rectification deadline, review results, supervision status` | Match core fields of daily ledger documents, reduce invalid data transmission |
| Interface call cycle | `600 seconds to 14400 seconds` | Align with daily business data update frequency, balance data timeliness and system load |
| Failure retry configuration | `3 retries, 60 second interval` | Address temporary network fluctuations or short-term external system anomalies, ensure complete data pulling |

## Three Common Misconfigurations
- Issue: Duplicate entries or missing newly added daily data appear in ledger data after scheduled interface calls. Cause: No data deduplication or data range parameters configured via `variables`, and call cycles do not match the daily business update frequency, leading to repeated pulling of archived data or missed newly added daily hazards.
- Issue: No relevant logs can be queried after interface call failures. Cause: No persistent storage configuration for interface call logs enabled, only temporary in-memory logs retained, leaving no valid basis for troubleshooting failure causes.
- Issue: Interface return data received by external systems is blocked by validation checks. Cause: Core return fields not specified via `responseData`, and returning full data by default exceeds the field receiving limit of the external system.

## How to Confirm Proper Configuration
- Perform a manual interface call, and verify that returned fields match the core fields specified in `responseData`.
- Check the scheduled task execution logs to confirm that the call cycle matches the preset configuration, and there are no consecutive failure records.
- Connect to the hazard governance ledger module of the external system, and verify that the pulled data matches the core information of the local ledger.
- Simulate a scenario where the external system is temporarily unavailable, and confirm that the interface triggers the preset failure retry mechanism.
