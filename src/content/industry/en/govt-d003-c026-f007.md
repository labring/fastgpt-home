# Ledger Summary and Report Generation for Engineering Construction Project Approval: Database and Operations Maintenance

## What this category of data looks like
Data for this category originates from four data sources: the engineering construction project approval management system, construction drawing review system, enterprise qualification database, and credit platform. Daily documents include construction permit applications, construction drawing review qualification certificates, quality and safety supervision procedures, completion acceptance record filing forms, and more. Data is updated incrementally daily. Data fields include project unique identifier, participating unit qualification level, approval node status, submission time, record number, and others. Qualification level is an enumerated value, submission time uses standard date format, project identifier is a string type, and field names differ across various data sources.

## What constraints do these characteristics impose on the database and operations maintenance link
The heterogeneous nature of multiple data sources requires the database to support mixed storage of structured and unstructured data. The daily incremental update rhythm requires configuring a breakpoint resume mechanism to avoid repeated data pulling. The high-frequency query demand for participating unit qualifications and approval nodes requires establishing indexes for corresponding fields to improve query efficiency. Differences in field names across different data sources require configuring unified field mapping rules to prevent field mismatch issues during data writing. The ledger summary and report generation scenario requires ensuring data consistency, so a transaction mechanism must be configured to ensure atomicity of multi-table associated writes.

## Configuration Settings
This configuration applies to FastGPT v4.17.0. Specific parameter settings are as follows:

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://admin:securepass@db-host:27017/construction_approval` | Stores unstructured approval documents and metadata, adapts to multi-source heterogeneous data formats |
| `PG_URL` | `postgresql://admin:securepass@db-host:5432/ledger_db` | Stores structured ledger data, supports associated queries for participating unit qualifications and approval nodes |
| `DB_MAX_LINK` | `25` | Matches the concurrent connection peak of daily incremental synchronization, prevents database connection pool overflow |
| `REDIS_URL` | `redis://:securepass@cache-host:6379/0` | Caches incremental synchronization breakpoints and frequently queried approval statuses, reduces repeated database access pressure |

## Three Common Misconfigurations
- Phenomenon: When calling the ledger generation interface concurrently, the service returns `504 Gateway Timeout`, and the front-end page is unresponsive. Cause: No reasonable value set for `DB_MAX_LINK`, multiple requests occupy database resources simultaneously, causing service blocking.
- Phenomenon: The participating unit qualification field is missing in synchronized approval documents, resulting in incomplete ledger data. Cause: No index configured for the qualification field in the database corresponding to `MONGODB_URI`, causing verification failure during data writing.
- Phenomenon: Incremental synchronization tasks repeatedly pull historical data, leading to low synchronization efficiency. Cause: No `REDIS_URL` used to store synchronization breakpoint information, so each synchronization pulls all data from the data source in full.

## How to Verify Successful Configuration
- Run the database connection test script to verify the connectivity of `MONGODB_URI` and `PG_URL`, and confirm that corresponding database tables can be read and written.
- Check the logs of the incremental synchronization task to confirm that breakpoint information is correctly written to the cache corresponding to `REDIS_URL`, with no repeated pulling records.
- Simulate concurrent requests, adjust the value of `DB_MAX_LINK`, observe the usage of the database connection pool, and ensure that the number of connections does not exceed the configured limit.
- Randomly select an approval document, verify that the ledger data after field mapping is consistent with the source system data, and confirm that the field conversion rules take effect.

The values provided are common starting points and should be measured against the reader's own samples.
