# Tender Bidding for Engineering Construction Projects: Ledger Summary and Report Generation — Deployment and Upgrade

## What the data for this category looks like
Data sources for this category include the national public resource trading platform, local trading platforms, engineering approval systems, and bidding and tendering supervision systems. The update frequency is daily. Daily processed documents include tender announcements, qualification pre-qualification documents, tender documents, bid documents, bid evaluation reports, successful bid candidate announcements, and successful bid result announcements. Data fields include section division information, qualification requirements, bid evaluation expert records, successful bid results, and other content. The overall dataset is a mixed set of structured fields and unstructured documents, forming a dedicated business data link around the engineering project construction and bidding and tendering legal framework.

## What constraints these characteristics impose on the deployment and upgrade phase
The daily high-frequency update requirement mandates configuring a stable database connection pool and storage service during deployment, to avoid ledger data loss caused by data pull interruptions. Mixed document types require adapting parsing and storage for different formats; compatible processing pipelines for tendering, bidding, bid evaluation, and other documents must be planned in advance. Decentralized data sources require reserving configuration expansion capabilities for multi-platform interface docking during the deployment phase. During the upgrade process, compatibility with historical ledger data must be ensured, preventing historical data from becoming unreadable after version updates. For sensitive data such as bid evaluation reports and successful bid results, a storage encryption policy meeting regulatory requirements must be configured during deployment, and encryption rules must be updated synchronously during upgrades to ensure data compliance.

## How to set the configurations
The following configuration items are optimized for FastGPT v4.17.0:

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 10–20 connections | Addresses daily high-frequency ledger data pull and query operations, avoiding database connection exhaustion |
| `MONGODB_URI` | Local private deployment address, configured with replica sets | Stores unstructured documents such as bid evaluation reports and tendering documents, supporting high-concurrency read/write operations |
| `REDIS_URL` | Locally deployed Redis service address, configured with 4096 MB or more memory | Caches frequently queried tender announcements and successful bid result data, reducing database load |
| `STORAGE_S3_ENDPOINT` | Local object storage or compliant public storage endpoint | Stores attachments such as bidding documents and qualification pre-qualification documents, adapting to storage needs for multiple document types |
| `ROOT_KEY` | Configured as an internal supervision-specific key | Assigns ledger access permissions for business teams, ensuring compliance of data access |

## Three common mistakes
- Symptom: After starting the service, daily update data from the public resource trading platform cannot be pulled, and logs show connection timeout. Cause: A reasonable value for `DB_MAX_LINK` was not configured, leading to database connection pool exhaustion, which cannot support high-frequency data pull requests.
- Symptom: After updating a privately deployed service to a new version, historical ledger data cannot be displayed normally, with some fields showing empty on the page. Cause: The upgrade did not maintain compatibility with the storage structure of legacy data, and the data migration script was not backed up and verified in advance.
- Symptom: Internal business team members cannot access the ledger summary page, with a permission denied prompt. Cause: The permission rules for `ROOT_KEY` were not configured correctly, and corresponding teams were not assigned data view permissions.

## How to confirm configurations are correct
- Execute the daily data pull script, verify that documents such as tender announcements and bid evaluation reports can be successfully pulled, with no connection timeout or data missing errors.
- Upload different types of bidding and tendering documents, verify that they can be stored normally and corresponding fields are displayed in the ledger, with no format parsing errors.
- Access the configured `FE_DOMAIN` address, log in with an authorized account, and confirm that the ledger summary and report generation module can be accessed normally.
- Restart the service, verify that the caching function of `REDIS_URL` is working properly, and there is no significant delay in loading frequently queried successful bid result data.
