# Ledger Summary and Report Generation for Market Entity Registration and Licensing: HTTP Interfaces and External Systems

## What data for this category includes
Core data for this category comes from four external systems: the full-process electronic enterprise registration system, the national enterprise credit information public disclosure system, the electronic business license system, and the residence information database. Data is fully updated every day.
Documents processed daily include establishment registration applications, articles of association, shareholder resolutions, residence certificates, business licenses, food business license applications, and more. Data fields include entity name, unified social credit code, registration type, licensing item, residence address, legal representative information, application status, and more. Single-batch data volume varies with the size of market entities in the jurisdiction. There is no fixed single-data structure across all entries.

## What constraints these characteristics impose on HTTP interfaces and external systems
Multi-source data sources require HTTP interfaces to support connection to at least four external systems. The daily full-update rhythm requires interfaces to be configured with scheduled pull tasks to avoid missing data synchronization windows. The diversity of documents and fields requires interfaces to support flexible field mapping rules to adapt to differences in return formats across external systems. Data association rigor requires interface calls to carry complete identity verification information. This ensures the legitimacy of data sources and prevents risks of registration rejection or business restrictions caused by permission issues.

## How to set up the configuration
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {market supervision system API key}` | Complies with industry-standard identity verification requirements when connecting to external registration and licensing systems |
| `variables` | `{"stat_period": "2024-05-01 to 2024-05-31", "region": "XX jurisdiction"}` | Used to pass global ledger statistics cycle and geographic scope, adapting to report generation needs across multiple scenarios |
| `responseData` | Map return fields to `entity_name, credit_code, license_type, apply_status` | Standardizes registration and licensing data returned by external interfaces, unifying the field format for ledger summaries |
| Single request timeout | 300 seconds | Addresses response delays from multiple external systems, preventing task interruptions from overly long single requests |
| Automatic retry count | 3 times | Addresses request failures caused by temporary fluctuations in external systems, ensuring stability of data pulling |
| Batch pull limit | 1000 items per request | Complies with single-data return limits for market supervision external interfaces, avoiding request overload |

## Three common errors
- Returns a `401 Unauthorized` status code when calling external interfaces. This occurs when the `Authorization` parameter is not configured correctly, and an expired or unauthorized system key is used.
- Ledger summary results have empty fields or missing key information. This occurs when external interface return fields are not correctly mapped via `responseData`, leading to incorrect extraction and organization of data.
- Global variables do not take effect during interface calls. This occurs when the `variables` parameter is not nested in the corresponding node of the request body as required, so the system cannot recognize the passed global configuration.

## How to verify the configuration is correct
- Call the configured HTTP interface, check whether the returned identity verification status is normal, and confirm that the `Authorization` parameter is configured correctly.
- View the structured data returned by the interface, and check whether the fields mapped by `responseData` match the preset ledger fields.
- Trigger an interface call, view the request log, and confirm that the `variables` parameter has been correctly carried and passed.
- Simulate a temporary failure scenario of an external system, check whether the automatic retry mechanism triggers as per the set number of times, and verify that the fault-tolerant configuration takes effect.
