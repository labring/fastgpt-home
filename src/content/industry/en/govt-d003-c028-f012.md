# Ledger Summary and Report Generation for Market Entity Registration and Licensing: Deployment and Upgrade

## What the data for this category looks like
The data for this category comes from the enterprise registration fully electronic system, the national enterprise credit information publicity system, the electronic business license system, and the residence information database, and is updated daily. Commonly processed documents include establishment registration applications, articles of association, shareholder resolutions, residence certificates, business licenses, food business license applications, and more. Data fields cover subject qualification information, licensing items, residence information, and application material status. Units are mostly natural person names, unified social credit codes, dates, licensing categories, and similar items. No complex measurement units are included.

## What constraints these characteristics impose on the deployment and upgrade phase
The daily data update frequency requires configuring an incremental synchronization mechanism during deployment. This avoids excessive resource usage caused by full pull operations.
The scenario of processing multiple types of mixed documents requires storage configurations that support file storage and indexing for multiple formats.
The presence of unique identifier fields requires configuring data deduplication and verification rules. This prevents duplicate entries.
Business logic that relies on external registration system interfaces requires reserving adjustable call timeout parameters. This adapts to interface response speeds across different network environments.
For intranet deployment scenarios, access permission restrictions across systems must be addressed. This avoids failed data docking due to public network access requirements.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `STORAGE_S3_ENDPOINT` | Intranet-accessible object storage address, such as `http://minio:9000` | Adapts to storage needs for multiple types of registration documents, supports file access in intranet environments, avoids public network exposure risks, and complies with the storage configuration specifications of FastGPT v4.17.0 |
| `MONGODB_URI` | `mongodb://username:password@mongodb-host:27017/fastgpt?authSource=admin` | Stores market entity registration data and ledger records, supports high-concurrency read and write operations, and adapts to daily updated data volume |
| `REDIS_URL` | `redis://:password@redis-host:6379/0` | Caches frequently accessed registration information and licensing status, reduces the frequency of external system calls, and improves response speed |
| `FILE_TOKEN_KEY` | Randomly generated 32-byte string | Encrypts file access tokens, prevents unauthorized downloading of registration materials, and ensures data security |
| `ROOT_KEY` | Custom random string of at least 16 characters | Configures system administrator permission verification, prevents unauthorized modification of system configurations |
| `FE_DOMAIN` | Internal access domain name for deployment, such as `http://fastgpt.internal` | Configures the access address of the frontend page, ensures that links generated after ledger creation can be accessed normally |

## Three Common Configuration Mistakes
- Symptom: After deployment, external registration system documents cannot be synchronized, and logs prompt "storage service unreachable" or connection timeout. Cause: A public network address was entered when configuring `STORAGE_S3_ENDPOINT`, and the intranet deployment scenario was not adapted, causing the system to fail to access the local storage service.
- Symptom: A "missing parameter" error occurs when calling the market entity verification plugin, and the plugin cannot be triggered normally. Cause: The interface address of the external registration system was not correctly configured in the deployment configuration, or the permission switch of the plugin system was not enabled, causing the plugin to fail to read the required registration data.
- Symptom: When attempting to call a third-party large model to generate a report, the interface returns an "unauthorized" or "model does not exist" error. Cause: The API key and interface address of the third-party large model were not correctly configured in the deployment configuration, causing the system to fail to call the target model.

## How to Verify Correct Configuration
- Run the built-in database connection test script to verify that the database configured via `MONGODB_URI` can read and write registration data and ledger records normally.
- Upload a sample business license file to verify that the storage service configured via `STORAGE_S3_ENDPOINT` can store and read the file normally.
- Access the frontend address configured via `FE_DOMAIN` to verify that the page can be opened normally, and that the preview link generated after ledger creation can be accessed normally.
- Call the preset plugin interface to verify that the cache service configured via `REDIS_URL` can cache frequently accessed registration information normally.

The values provided are common starting points, and should be evaluated against the samples used in actual deployments.
