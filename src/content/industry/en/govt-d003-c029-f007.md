# Case Ledger Summary and Report Generation for Urban Sanitation and Urban Management Law Enforcement: Database and Operations

## What the data for this category looks like
The data for this category typically comes from urban management law enforcement platforms, urban operation grid platforms, video surveillance systems, and public complaint work orders.
Daily involved documents include inspection records, case filing approval forms, on-site photos, rectification orders, penalty decisions, and case closure reports.
Data is updated on a daily basis. Fields include case number, responsible entity, violation type, on-site location information, disposal status, penalty result, and more.
Some documents contain unstructured content such as images and longitude and latitude coordinates. Document field formats vary across different data sources.

## Constraints on Database and Operations Workflows
Multi-source data access requires the database to support flexible document structures and unstructured storage. This adapts to content in varying formats such as inspection records and on-site photos.
The daily update frequency requires scheduled synchronization tasks. These tasks ensure ledger data stays consistent with source platforms.
Differences in field formats require import tools to support custom field mapping. This prevents data misalignment.
Errors in case evidence-related data may trigger law enforcement disputes. Configure data verification and backup mechanisms, and enable geographic indexing to quickly locate on-site evidence information.

## Configuration Settings

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Connection string supporting geographic indexing, calibrated based on actual testing | Stores case location longitude and latitude, on-site photos and other unstructured data, and is compatible with multi-source document formats |
| `DB_MAX_LINK` | `20–30` connections | Matches concurrent import and query requirements for daily updated data, and prevents database connection exhaustion |
| `REDIS_URL` | Local or intranet cache service address, calibrated based on actual testing | Caches case statistics results and ledger data for high-frequency queries, to speed up report generation |
| Excel import field mapping | Bind Excel columns to core case fields, retain original naming | Compensates for differences in Excel export formats across different inspection and work order platforms |
| Scheduled synchronization task interval | `Every 24 hours` | Matches the daily update frequency of data for this category, ensuring consistency between ledgers and source data |

## Three Common Configuration Errors
- Symptom: Some fields are empty or import fails when importing case data via Excel. Cause: Import mapping is not configured according to the core fields of the category, and non-standard Excel column names are used.
- Symptom: MongoDB connection error prompts replica set configuration exception. Cause: Replica set parameters in `MONGODB_URI` are not configured correctly, or the database replica set mode is not enabled.
- Symptom: Historical case ledger records cannot be queried. Cause: Persistent storage for `REDIS_URL` is not configured, or the cache key is not associated with the unique case number, resulting in cleared cache data.

## How to Confirm Successful Configuration
- Perform a single case data import, verify that imported fields fully match source Excel columns, with no missing or misaligned data.
- View the MongoDB database, confirm that case location longitude and latitude fields and binary on-site photo data have been stored.
- Manually trigger a ledger summary task, check that the task execution log has no connection timeout or data missing errors.
- Check the connection status of the Redis cache service, confirm that case statistics data for high-frequency queries can be read normally.
