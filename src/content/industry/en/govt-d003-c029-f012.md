# Case Ledger Summary and Report Generation for Urban Sanitation and Urban Management Law Enforcement: Deployment and Upgrade

## What this category’s data looks like
Data for this category typically comes from urban management law enforcement platforms, urban operation grid platforms, video surveillance, and public complaint tickets. It updates on a daily basis. Common documents include inspection records, case filing approval forms, on-site photos, rectification orders, penalty decisions, and case closure reports. Common data fields cover case numbers, violation types, responsible parties, rectification progress, disposal results, and similar metrics. Units used include case counts, time nodes, photo quantities, and other standard metrics. Data flows and is stored using individual cases as the basic unit.

## Constraints imposed by these characteristics during deployment and upgrade
Data sources for this category are scattered and diverse. During deployment, multiple data source connection adapters must be configured to avoid format conflicts when synchronizing data from different channels such as law enforcement platforms and grid platforms. The daily update frequency requires reasonable configuration of scheduled synchronization task parameters to prevent excessive system resource usage. The need to handle multiple document types requires upgrades to support parsing and storage rules for different file formats. Additionally, data accuracy directly relates to law enforcement compliance. Deployment and upgrade processes must strengthen data verification configuration to prevent missing key fields from causing errors in subsequent ledger summaries.

## How to Set Configurations
This page applies to FastGPT v4.17.0, and provides the following configuration recommendations tailored to the characteristics of urban management law enforcement scenarios.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://username:password@host:port/city_admin` | Stores structured and unstructured data such as case ledgers and law enforcement documents. Must match the connection format and permissions of the existing urban management system database. |
| `REDIS_URL` | `redis://:your_password@redis-host:6379/0` | Caches synchronized case data and temporary processing results to reduce overhead from repeated database queries. |
| `STORAGE_S3_ENDPOINT` | `http://minio.chengguan.gov.cn:9000` | Stores attachments such as on-site photos and law enforcement videos. Must match the endpoint address of the existing object storage service in the urban management system. |
| `DB_MAX_LINK` | `20–30` | Limits concurrent database connections to avoid excessive database resource usage during daily batch case data synchronization. |
| `FILE_TOKEN_KEY` | `32-bit random string determined through actual testing` | Used to generate access tokens for attachments, ensuring access permissions for law enforcement documents are controlled. |
| `ROOT_KEY` | `Security key held exclusively by deployment administrators` | Configures the system's highest-privilege key for managing isolation of urban management law enforcement data across multiple tenants. |

## Three Common Misconfigurations
- Phenomenon: Containers fail to start after Docker deployment. Logs show database connection timeouts or permission denied errors. Cause: `MONGODB_URI` or `PG_URL` parameters are not configured correctly, and do not match the address, port, and access permissions of the existing urban management system database.
- Phenomenon: After uploading law enforcement documents in an offline environment, the file processing status remains stuck in a loading cycle with no progress. Cause: The system relies on external API interfaces by default for file parsing and dependency loading. No local dependency cache for offline deployment is configured, so document processing cannot be completed in an offline environment.
- Phenomenon: Markdown table content in generated law enforcement reports is truncated, and the interface displays prompts such as `[hide 38432 char]`. Cause: No adjustments are made to configurations adapted for long-text processing, so the model triggers a content truncation mechanism during output, failing to fully display case-related tables and details.

## How to Verify Successful Configuration
- Run a database connection test script to verify that the `MONGODB_URI` and `PG_URL` parameters can successfully connect to the urban management system database, with no connection failure or permission error messages.
- Upload a single law enforcement document in an offline environment, confirm that the file processing flow does not trigger external API access requests, and that the status transitions normally to completed.
- Generate a ledger summary report for a single case, check that all case fields are fully displayed in the Markdown tables in the report, with no content truncation.
- Review the running logs of scheduled synchronization tasks, confirm that the daily case data synchronization count and update time match the preset configuration.
