# Ledger Summary and Report Generation for Construction Engineering Quality and Safety Supervision: HTTP Interfaces and External Systems

## What this category of data looks like
Four sources provide core data for construction engineering quality and safety supervision: project quality and safety supervision systems, on-site construction real-name platforms, supervision logs, and test reports.
Processed daily documents include supervision plans, supervision inspection records, hidden danger rectification notices, quality problem handling forms, and completion acceptance supervision reports.
Data updates occur weekly. Each document includes fields such as supervision subject, inspection time, hidden danger content, rectification status, and acceptance conclusion.
No unified fixed unit applies. Match the corresponding field format to the business attributes of each individual document.
Data volume changes dynamically based on the number of ongoing construction projects.

## What constraints do these characteristics impose on the HTTP interfaces and external systems link
Diverse data sources require compatibility with interface formats of different external systems. Different document filtering rules must be specified via parameters during interface calls.
The weekly update frequency requires that interface synchronization cycles match business rhythms. This avoids frequent calls that occupy system resources.
Field differences across multiple document types require that interface returned data supports flexible field mapping. Unified field parsing rules cannot be used.
The rigor of data association requires that interfaces carry complete identity verification credentials. This prevents unauthorized access and resulting leakage of quality and safety data.
The serious consequences of errors require that interfaces have failure retry and data verification mechanisms. This avoids incorrect data flowing into the ledger summary process.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {API key assigned by the housing and urban-rural development system}` | Complies with identity verification specifications of external systems, ensures legitimacy of interface calls |
| `variables` | `{"docFilter": ["supervision inspection records", "hidden danger rectification notices"], "updateCycle": "weekly"}` | Matches the update rhythm of business data and the document types to be summarized, filters invalid data |
| `responseData` | `Top 100 records` | Controls the data volume returned by a single interface to avoid timeouts caused by excessive data |
| Interface timeout period | 600 seconds | Adapts to the batch processing time required for multi-document summary, matches the business processing rhythm of the housing and urban-rural development system |
| Multimodal model call parameters | Calibrated based on actual measurements | Adapts to the parsing requirements of on-site photos and test report images, matches the recognition accuracy of business scenarios |

## Three common errors
- Symptom: A string of red numeric errors is returned when calling an external system interface. The cause is incorrect configuration of the `Authorization` parameter format, and failure to follow FastGPT’s identity verification rules, resulting in identity verification failure.
- Symptom: Uploaded on-site construction photos cannot be correctly parsed into ledger data. The cause is missing document type filtering rules in `variables`, so the `responseData` returned by the interface does not match the corresponding business fields.
- Symptom: Interface calls frequently trigger timeouts. The cause is failure to set a reasonable interface timeout period, and failure to adapt to the batch processing time required for multi-document summary, resulting in request interruption before completion.

## How to confirm the configuration is correct
This document applies to FastGPT v4.17.0.
- Call the test interface, check whether the `responseData` contains ledger document data of the specified type, and verify that fields match the filtering rules configured in `variables`.
- Simulate a weekly data update trigger action, check whether the interface can correctly pull the latest documents such as supervision inspection records and hidden danger rectification notices, to verify the effectiveness of the update cycle configuration.
- Disconnect the network connection of the external system, check whether FastGPT can trigger a reasonable failure prompt, to verify the effectiveness of the `Authorization` parameter and timeout configuration.
- Upload on-site construction photos to the interface, check whether they can be correctly parsed into ledger fields, and verify that the multimodal model call parameter configuration matches business requirements.
