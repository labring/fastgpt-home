# Enrollment and Student Status Management: Ledger Aggregation and Report Generation — Model Access and Configuration

## What the data for this category looks like
Data for this category primarily comes from the national primary and secondary school student status information management system, local enrollment platforms, household registration and property verification systems, and school educational administration systems. Commonly processed documents include enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, and student status change approval forms. Fields include student identity identifiers, household registration and property information, student status status, enrollment qualification review results, and more. Data updates occur daily. Each document requires integrating multi-source associated information across multiple systems. Field formats are tightly bound to business logic.

## What constraints these characteristics impose on model access and configuration
The daily multi-source data update requirement means model access must support high-frequency, stable calls. It must prevent data synchronization interruptions caused by token expiration or interface rate limiting. Multi-dimensional associated fields and cross-system integration needs require reserving sufficient context space during configuration. This prevents critical student status and enrollment information from being truncated. Field formats vary across different documents. The model must accurately identify and process exclusive business fields such as enrollment qualifications and student status changes. This avoids generating incorrect ledger content. The total amount of associated information in a single document is large. Context parameters during calls must match the total number of fields. This prevents context overflow from affecting report generation.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `AIPROXY_API_ENDPOINT` | Fill in the official access address of the corresponding model | This category needs to connect to multi-source education system data, requiring a stable interface address to support high-frequency calls |
| `maxContext` | 8000–12000 token | A single ledger integrates multiple student status and enrollment documents, requiring space to hold complete associated fields |
| `temperature` | 0.2–0.4 | Ledgers and reports require strict accuracy, reducing random generation deviations |
| `toolChoice` | auto | The model must independently choose whether to call tools to handle exclusive business logic such as student status changes and enrollment plans |
| `quoteMaxToken` | 2000–3000 token | Sufficient source document reference content must be retained to ensure the traceability of reports |
| `vision` | Disabled | The core data of this category is structured documents, and visual model processing is not needed |

## Three Common Configuration Errors
- Phenomenon: An invalid token error displays when accessing a domestic model, while the oneapi interface test runs normally. Cause: `AIPROXY_API_TOKEN` is not configured correctly, or the token permission does not cover the model call scope required for enrollment and student status management.
- Phenomenon: After adding Zhipu and Qianwen 2 models to a channel, the corresponding models do not appear when creating a knowledge base and application. Cause: The channel list is not refreshed synchronously in FastGPT's model access configuration, or the configured model name does not match the name defined in the channel.
- Phenomenon: A rerank error prompts when calling the reranker model. The log shows the upload is successful, but the function button is unavailable. Cause: The configured `maxTokens` exceeds the support limit of the reranker model, or the interface timeout parameter is not configured correctly.

## How to Confirm Proper Configuration
- Call the test interface, pass the structured data of a single enrollment application form and student status information form, and verify that the returned result includes correct field association logic.
- View the model access logs of FastGPT v4.17.0, confirm that there are no format errors in the configuration of `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN`, and that there are no connection timeout records.
- Simulate the high-frequency call scenario of daily data updates, confirm that there are no token expiration or rate limiting errors during interface calls.
- Generate a simulated enrollment report, verify that the referenced source document fields are complete, and that there is no truncated or incorrectly generated content.
