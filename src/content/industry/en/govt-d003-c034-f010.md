# Enrollment and Student Status Management: Ledger Summary and Report Generation - Knowledge Base Retrieval and Recall

## What the Data for This Category Looks Like
The data for this category primarily originates from the National Primary and Secondary School Student Status Management System, local enrollment platforms, household registration and real estate data, and school educational administration systems. The update frequency is daily. Commonly processed documents include enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, and student status change approval forms. Core data focuses on student identities, admission qualifications, and student status transfer information, including fixed fields such as student ID number, household registration address, admission batch, and change type. No additional statistical numerical fields are included.

## Constraints Imposed on Knowledge Base Retrieval and Recall
Daily updated data requires the retrieval and recall process to support incremental data synchronization, to prevent excessive computing resource consumption from full scans. Multiple data sources require cross-dataset recall rules to be configured, ensuring that associated information from the student status system, enrollment platform, and household registration system can be retrieved simultaneously. Document fields are concentrated on student identities and student status transfers. Retrieval must prioritize matching precise fields such as student ID number and household registration address, to avoid generalized recall of irrelevant content. Complex business processes such as transfer changes involve multiple approval documents. Recall must link application and approval records to ensure information completeness, supporting the accuracy of ledger summary and report generation.

## Configuration Settings
This configuration is based on FastGPT v4.17.0, adapted to the ledger summary requirements of enrollment and student status management scenarios. The specific configuration items are listed below:

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Match precise fields such as student ID number and household registration address, filter low-relevance recall results |
| `limit` | Top 8–12 entries | Cover core information from multiple document types including enrollment plans and admission rosters, avoid recalling redundant data |
| `searchMode` | hybrid | Combine keyword and semantic recall, adapt to mixed retrieval needs for enrollment policy text and structured student status data |
| `usingReRank` | Enabled | Reorder initial recall results, improve the ranking priority of key documents such as admission rosters and student status change approval forms |
| `datasetSearchUsingExtensionQuery` | Enabled | Expand query scope, cover household registration and real estate associated data required for admission qualification verification |
| `collectionIds` | Bind the IDs of corresponding student status, enrollment, and household registration datasets | Limit recall scope, avoid mixing irrelevant documents from other categories |

## Three Common Configuration Errors
- Issue: The knowledge base output answer references files that do not match the actual retrieval results, with irrelevant documents appearing or key approval forms missing. Cause: `collectionIds` is not configured correctly, and the recall scope exceeds the specified student status and enrollment datasets.
- Issue: Retrieval latency for identical queries varies significantly, with some requests taking more than 20 seconds. Cause: The `limit` value is too high, or `usingReRank` is not enabled, leading to excessive data processing volume during initial recall and reordering.
- Issue: Streamed return results when `detail` is set to `true` cannot be parsed properly, with missing return fields or abnormal formatting. Cause: `datasetSearchUsingExtensionQuery` is not enabled, and no extended query parameters are configured, resulting in associated data not being retrieved and preventing the generation of complete structured reports.

## How to Verify Correct Configuration
- Retrieve the student status information of a specified student, verify that the recall results include the corresponding student status information form and enrollment application form, to confirm that the `collectionIds` configuration is active.
- Initiate multiple identical query retrievals, compare the range of latency fluctuations, to confirm that the `similarity` and `limit` values are compatible with the business data volume.
- Trigger a streamed return with `detail` set to `true`, check whether the returned fields include associated household registration and real estate data, to confirm that the `datasetSearchUsingExtensionQuery` configuration is correct.
- View the retrieval log, verify that the source of all recalled documents is from the specified datasets, to confirm that the `searchMode` and `usingReRank` configurations perform as expected.

The values provided are common starting points and should be evaluated against samples from actual deployments.
