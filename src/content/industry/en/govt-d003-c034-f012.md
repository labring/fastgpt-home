# Enrollment and Student Status Management: Ledger Summary and Report Generation - Deployment and Upgrade

## What This Category’s Data Looks Like
This category’s data primarily originates from the national primary and secondary school student status information management system, local enrollment platforms, household registration and property data, and school academic affairs systems. Daily processed documents include enrollment application forms, student status information sheets, transfer applications, enrollment plans, admission rosters, and student status change approval forms. Data is updated daily. Data fields cover student identity identifiers, household registration and residence information, student status, enrollment batches, admission results, and more. There are no additional custom statistical units. The core associated fields are the unique student status number and enrollment registration number.

## Constraints Imposed on Deployment and Upgrade
This category’s data sources are scattered. Configure multiple data source connection parameters during deployment to ensure data synchronization stability. The daily data update frequency requires scheduled tasks to adapt to the daily batch synchronization rhythm to avoid concurrent overload. Document types vary, and some files include structured fields. Adapt deployment settings to the parsing rules of different document types. Data errors can lead to serious consequences including duplicate student status entries and admission disputes. Complete a full data backup ahead of the upgrade phase, and verify that the post-upgrade data consistency check logic operates normally.

## Configuration Settings
This configuration guide is compatible with FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Fill in the local cluster connection string, including database authentication information | Ledger and student status data requires persistent storage, and multi-node deployment ensures business continuity |
| `REDIS_URL` | Configure as `127.0.0.1:6379`, a local Redis instance without a password | High-frequency reading of student status cache and scheduled task markers to meet low-latency synchronization requirements |
| `DB_MAX_LINK` | Take the value `50–80 connections` | Daily batch synchronization of enrollment and student status data to avoid exhausting the database connection pool |
| `STORAGE_S3_ENDPOINT` | Fill in the intranet access endpoint of the local object storage | Store large-volume documents such as enrollment application forms and admission rosters to ensure stable file access |
| `ROOT_KEY` | Set to a random string longer than 32 characters | Admin backend permission verification to prevent unauthorized access to configuration pages |
| `FILE_TOKEN_KEY` | Configure as a unique identifier string bound to the knowledge base | Associate parsed documents with corresponding knowledge base entries to ensure the model can call document content |
| `FE_DOMAIN` | Fill in the public or intranet domain name of the deployed service | Basic configuration for frontend page resource loading and callback interfaces |

## Three Common Misconfigurations
- An error prompt appears every 30 minutes after Docker deployment, and the service recovers after restarting. Cause: The persistence parameter for `REDIS_URL` is not configured, and the scheduled task cache is not persisted, leading to periodic exceptions.
- The old version number is still displayed after upgrading to the specified version. Cause: The latest version of the Docker image was not pulled, or the container tag was not updated during deployment.
- After file parsing is complete, the model does not generate responses based on the document content. Cause: `FILE_TOKEN_KEY` is not correctly configured to associate parsed files with the knowledge base, or the knowledge base synchronization task was not triggered.

## How to Confirm Successful Configuration
- Run `docker logs fastgpt` to view the service startup log, and confirm that there are no errors in database connection-related logs.
- Trigger an enrollment data synchronization task, and check that there are no data source connection failure prompts in the task execution log.
- Access the frontend page corresponding to `FE_DOMAIN`, and confirm that the admin backend can log in normally and the permission configuration takes effect.
- Upload an enrollment application form document, and confirm that the parsed fields can be viewed normally in the knowledge base.
