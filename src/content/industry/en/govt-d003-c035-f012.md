# Emission Permit Management: Ledger Summary and Report Generation - Deployment and Upgrade

## What the data for this category looks like
Data for this category primarily comes from the national emission permit management information platform, enterprise environmental protection ledgers, online monitoring systems, and environmental statistics systems. Daily documents include emission permit application forms, implementation reports, self-monitoring plans, ledger records, change applications, and permit copies. Data is updated quarterly. Fields cover emission limits, monitoring frequency, ledger time periods, permit items, and more. Units follow ecological environment industry standard units such as concentration, flow, and emission volume.

## What constraints do these characteristics impose on deployment and upgrade?
Quarterly bulk data, multi-source heterogeneous documents, and strict field verification requirements create multiple constraints for deployment and upgrade.
Full quarterly ledger and implementation report data volumes are large. Deploy sufficient concurrent connections and storage resources.
Multi-source data have obvious format differences. Reserve extended configurations for data cleaning and format conversion.
Fields must match ecological environment industry technical specifications and permit limits. Build corresponding verification rules into deployment.
Cross-department data docking requires stable cache and storage configurations. Avoid data synchronization delays or loss.

## How to configure the settings
| Config Item | Recommended Value | Basis for this setting |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–150 connections` | Adapts to concurrent connection needs for quarterly bulk data synchronization, prevents database connection exhaustion |
| `MONGODB_URI` | Points to a replica set instance mounted with SSD storage and capacity no less than 200 GB | Stores unstructured documents of ledgers and monitoring data, ensures read/write performance |
| `REDIS_URL` | Configured as a local high-availability cache node with memory no less than 8192 MB | Caches quarterly updated permit limits and industry specification data, reduces repeated query latency |
| `STORAGE_S3_ENDPOINT` | Deploys local object storage service address | Stores batch-uploaded implementation reports, monitoring plans and other documents, avoids excessive local disk usage |
| `ROOT_KEY` | Generates a strong random string according to the deployment environment | Ensures access security of background management interfaces, prevents unauthorized configuration modifications |

## Three common misconfigurations
- Symptom: Timeout errors occur when workflows process quarterly bulk ledgers. Cause: Failure to adjust the `DB_MAX_LINK` configuration leads to insufficient database connections and data synchronization blocking.
- Symptom: API services on the specified port cannot be accessed after deployment. Cause: Failure to synchronously update port mapping rules when modifying Docker configurations causes service ports to not be properly exposed.
- Symptom: Associated documents for batch-imported monitoring data are missing. Cause: Failure to configure storage access permissions associated with `STORAGE_S3_ENDPOINT` causes data to not be properly written after document upload failures.

## How to confirm the configuration is correct
Reference only; verify against the target FastGPT release and deployment documentation.
- Access the management backend address specified by `FE_DOMAIN`. Use `ROOT_KEY` to verify interface permissions, confirm that the security configuration takes effect.
- Upload a copy of the emission permit copy document. Check that the corresponding file is generated in the storage path, confirm that the `STORAGE_S3_ENDPOINT` configuration is correct.
- View the monitoring of the cache node associated with `REDIS_URL`. Confirm that quarterly specification data has been cached, and there are no repeated query records.
