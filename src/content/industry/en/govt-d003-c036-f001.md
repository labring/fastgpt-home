# Ledger Summary and Report Generation for Government Service Item Catalog and Service Guide Maintenance: HTTP Interfaces and External Systems

## What this category of data looks like
This category of data is generated for the full lifecycle maintenance of government service items. Daily documents include basic government service item catalogs, implementation lists, service guides, standard material catalogs, flowcharts, and frequently asked questions. Data sources are the national basic government service item catalog, administrative licensing item list, power and responsibility list, and local government service item databases. The update frequency is monthly. A single item record includes core fields such as item name, acceptance conditions, application materials, and service process. Some fields must strictly match the naming specifications of the superior catalog. The data structure primarily consists of hierarchically associated text records.

## What constraints do these characteristics impose on HTTP interfaces and external systems
The monthly update frequency requires interface calls to adapt to low-frequency batch synchronization scenarios, avoiding high-frequency requests that consume data source resources. The multi-document hierarchical association structure requires the interface to support pulling associated documents such as implementation lists and service guides by item ID. The requirement for fields to match superior catalog specifications means the interface must support field integrity verification, as well as custom field mapping to adapt to differences in local item databases. The multi-field text structure of a single item requires the interface to support paginated data returns, preventing excessively large payloads in a single request. The high time cost of comparing superior catalogs and local implementation lists requires the interface to support incremental synchronization logic, only pulling updated item data.

## How to configure settings

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `Authorization` | Carry application-level API Key with the `Bearer ` prefix | FastGPT official requirements: calling application interfaces uses application-level secrets, distinct from account-level secrets, to prevent permission escalation |
| Maximum number of items per single request | 20 items | Adapt to low-frequency monthly batch synchronization scenarios, avoiding single request timeouts |
| `variables` | Pass `{ "updateTime": "last day of previous month" }` | Specify synchronization of item data updated in the previous month, matching the monthly update frequency |
| Timeout period | 300 seconds | Match the response duration of multi-document associated pulls, preventing interruptions during batch requests |
| `responseData` | Only return `itemId, itemName, applyMaterials` fields | Reduce invalid data transmission, meeting core field requirements for ledger summary |
| Field mapping rules | Map local item database field names to general ledger fields | Adapt to field differences across regional government service item databases, improving data universality |

## Three common configuration mistakes
- The interface returns a `400 do request failed` error, and logs show secret key verification failure. The cause is using an account-level API Key instead of an application-level API Key, and failing to correctly configure the key type in the `Authorization` header.
- The number of returned results during batch synchronization is lower than expected. The cause is not setting a reasonable maximum number of items per single request, or not passing the update time parameter in `variables`, resulting in only partial updated data being pulled.
- The interface returns excessive redundant content in fields. The cause is not specifying required core fields via the `responseData` configuration, leading to return of associated document fields not needed for the ledger.

## How to confirm the configuration is correct
- After calling the interface, check if the `Authorization` header carries the correct application-level secret key, and confirm that an account-level API Key is not used.
- Check if the `responseData` field in the interface return only includes core item fields required for ledger summary, with no redundant content.
- Pass a test `updateTime` variable, confirm that the data update time returned by the interface matches the passed parameter.
- Initiate a batch request test, verify that the interface response duration does not exceed the configured 300 seconds, and confirm there are no timeout interruptions.
