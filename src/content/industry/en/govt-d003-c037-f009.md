# Ledger Summary and Report Generation for Government Information Application-Based Disclosure: Model Access and Configuration

## What data for this category looks like
Organizations source data for this category from government information disclosure platforms, agency archive systems, document management systems, departmental business ledgers, and standardized documents related to government public affairs. Data updates occur irregularly, triggered by application-based disclosure requests submitted by applicants. Daily, teams process documents including government information disclosure application forms, supplementary notice letters, third-party opinion solicitation letters, response letters, service receipt records, and administrative reconsideration response materials. Fields cover applicant information, application content, processing progress, response results, relief channel records, and more. No unified standardized format exists, so teams must adapt to multiple document structures.

## What constraints these characteristics impose on model access and configuration
Scattered data sources and inconsistent formats require model access configurations to support unified parsing and extraction of multi-source data. Irregular update rhythms mean batch processing tasks must support on-demand triggering to adapt to ad-hoc ledger summary needs. The rigor of government documents requires generated content to comply with official specifications, placing strict limits on model generation randomness. Errors directly relate to administrative compliance, so teams must configure complete error capture and retry mechanisms to ensure the accuracy of ledgers and reports. Furthermore, the case-specific nature of application-based disclosure requires model configurations to support precise association with individual applications, avoiding confusion across different application data.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Covers the contextual content of multiple government documents, ensuring complete application and processing workflows can be associated during ledger summary |
| `maxTokens` | 2000–3000 token | Adapts to the standard length requirements of government response letters and ledger reports, avoiding overly long or short generated content |
| `temperature` | 0.1–0.3 | Reduces randomness in generated content, ensuring the format and wording of government documents comply with official specifications |
| `AIPROXY_API_ENDPOINT` | Fill in according to the deployment environment | Adapts to the call paths of local or cloud-based models, supports access to models deployed via local Ollama |
| `AIPROXY_API_TOKEN` | Fill in according to authorization information | Ensures the identity legitimacy of model calls, preventing unauthorized access |
| `toolChoice` | Auto | Automatically triggers extraction and association across multiple documents, adapting to ledger data summary for the full application-based disclosure workflow |

## Three common configuration errors
- Symptom: A `401 Unauthorized` error returns when calling the model, and the API key and endpoint configurations are correct. Cause: The model access configuration is not bound to the knowledge base permissions exclusive to government ledgers, resulting in restricted cross-knowledge-base calls.
- Symptom: A locally deployed reranking model request fails, and the interface displays a connection timeout. Cause: Network access permissions for local Ollama models are not added in the FastGPT configuration, and the correct local port is not specified.
- Symptom: Ledger generation tasks encounter timeout errors as concurrent request volume increases. Cause: `maxContext` is not adjusted to adapt to context loading logic under concurrency, leading to intensified resource competition between model calls and database queries.

## How to confirm the configuration is complete
- Access the model management page of FastGPT v4.17.0, and verify that the `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` configurations match the actual deployment environment.
- Upload a sample government information disclosure application form and supporting response letter, trigger the ledger summary task, and check that all required fields are included in the generated result.
- Simulate 3-5 concurrent requests, observe that there are no timeout or permission errors in the task execution logs, and there is no significant fluctuation in database query latency.
- Adjust the `temperature` parameter to 0.2, generate a test response letter, and check that the content is expressed rigorously, with no redundant or casual content.
