# Government Procurement Project Ledger Summary and Report Generation: Deployment and Upgrade

## What the data for this category looks like
Data for this category primarily comes from China’s national government procurement website, local government procurement websites, the fiscal integration system, the procurer’s budget system, and supplier credit records. The update frequency is daily. Daily processed documents include procurement requirements, procurement plans, bidding documents, tender documents, bid evaluation reports, winning bid announcements, procurement contracts, and responses to objections. Data fields cover procurement project ID, budget amount, supplier qualifications, bid evaluation results, contract amount, and more. Different documents have dedicated fields: for example, bid evaluation reports include expert signature items, winning bid announcements require marking project budget and winning bid amount. Different entities summarize ledger data according to their respective responsibility dimensions.

## What constraints these characteristics impose during deployment and upgrade
Daily updated data requires a stable incremental synchronization mechanism to be configured during deployment, to avoid excessive system resource usage from full pull operations. Structured processing of multiple document types requires adapting parsing rules for different fields. During upgrades, the field mapping logic for older document versions must be compatible, to prevent historical ledger data from becoming unreadable. Real-time calls to supplier credit records require configuring reliable external interface permissions. During upgrades, interface verification rules must be updated synchronously to avoid synchronization failures. Sensitive fields in documents related to fiscal supervision require additional permission verification configurations. During upgrades, permission control logic must be updated synchronously to prevent unauthorized access. There are differences in ledger summary dimensions across different entities. During deployment, a configuration entry for custom summary templates must be reserved, to avoid hardcoding that limits usage scenarios.

## How to set the configurations
This guide is written based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://user:pass@host:27017/gov_purchase?authSource=admin` | Stores full ledger data for government procurement projects; requires a dedicated database name and authentication information |
| `REDIS_URL` | `redis://:redis_pass@redis_host:6379/0` | Caches incrementally synchronized daily data and interface call results, to reduce redundant request overhead |
| `DB_MAX_LINK` | `100–200 connections` | Adapts to the concurrent access volume of government procurement systems, to avoid exhausting database connections |
| `FILE_TOKEN_KEY` | A randomly generated 32-bit string | Encrypts and stores uploaded attachments such as bidding documents and tender documents, to prevent sensitive document leaks |
| `STORAGE_S3_ENDPOINT` | `http://s3-compatible-endpoint:9000` | Stores batch-exported ledger reports and original documents, to meet compliance storage requirements |
| `ROOT_KEY` | A complex key generated based on business scenarios | Configures the highest permission for system administrators, used to manage custom templates for ledger summary |

## Three common errors
- Symptom: After a Docker container starts, it always listens on port 3000, and the port cannot be modified via the configuration file. Cause: The port mapping parameter is not correctly configured in docker-compose.yml, or the default port environment variable built into the image is not overridden.
- Symptom: Supplier credit record fields are missing from ledger summary results. Cause: The data source synchronization task for supplier credit records is not configured, or the display permission for the corresponding fields is not enabled in the summary template.
- Symptom: Connection timeout errors occur during batch report generation. Cause: The configuration value of `DB_MAX_LINK` is not adjusted, leading to exhausted database connections and inability to process concurrent ledger generation requests.

## How to confirm the configuration is correct
- Run the `docker ps` command, check that the container status is normal and running, and that port mapping matches the parameters set in the configuration file.
- Upload a test bidding document attachment, verify that the attachment can be stored normally and accessed via an encrypted link.
- Trigger a manual data synchronization task, check that the system logs have no data pull or storage errors, and confirm that the data source configuration is effective.
- Use the administrator permission corresponding to `ROOT_KEY` to create and modify custom templates for ledger summary normally.
