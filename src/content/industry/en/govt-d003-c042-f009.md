# Ledger Summary and Report Generation for Legal Compliance and Major Risk Management: Model Access and Configuration

## What the data for this category looks like
The data sources for this category include enterprise contract management systems, compliance risk databases, legal and regulatory repositories, case management systems, and reporting platforms. Daily processed documents cover compliance risk lists, contract legal review opinions, legal opinions on major matters, compliance review forms, and violation report investigation results. The content includes two types: structured fields and unstructured text. Data updates occur monthly. Core data focuses on the legality and compliance of business operations, covering records of the entire risk identification, review, and investigation process. Documents are stored only in the actual workflow structure of the business, with no additional statistical supplementary content.

## What constraints these characteristics impose on model access and configuration
Monthly updated data means model calls do not need to be triggered frequently, but must adapt to multi-source heterogeneous document formats. Unified parsing logic must be configured. Compliance documents contain specialized legal terminology, so models must have accurate professional comprehension ability. Parameter configuration must prioritize output rigor. Data sources involve multiple internal enterprise systems, so intranet deployment security requirements must be considered to avoid sensitive data leakage. Compliance data errors may trigger major legal disputes or administrative penalties, so a failure fallback mechanism and permission control must be configured to ensure stable task execution.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Covers the core content of monthly compliance-related documents, avoiding context overflow that affects summary results |
| `maxTokens` | 4000 token | Meets the length requirements for compliance report generation, ensuring complete output of risk summaries or review opinions |
| `temperature` | 0.2–0.4 | Reduces generation randomness, ensuring accuracy and rigor of compliance statements, meeting professional document requirements |
| `AIPROXY_API_ENDPOINT` | Fill in according to the enterprise intranet mirror address | Adapts to the security requirements of intranet deployment for Chinese public sector and state-owned enterprise environments, preventing sensitive compliance data from leaking |
| `AIPROXY_API_TOKEN` | Exclusive keys assigned by role level | Meets data security and compliance requirements, restricting model call permissions for personnel in different positions |
| `toolChoice` | auto | Allows the model to automatically choose whether to call tools to process multi-source data, adapting to different types of compliance document formats |

## Three Common Misconfigurations
- Phenomenon: Tasks are directly interrupted after a model call fails, with no standby model to take over. Cause: The workflow’s exception capture mechanism is not enabled, and multi-model fallback logic is not configured.
- Phenomenon: Return formats do not meet expectations when calling domestic index models, making normal data parsing impossible. Cause: Interface specifications of domestic models are not properly adapted, and `AIPROXY_API_ENDPOINT` and the corresponding key are not configured as required.
- Phenomenon: Generated compliance ledger fields are missing or the format is chaotic, making direct system import impossible. Cause: Output format is only guided by prompts, and structured output rules are not enforced through configuration.

## How to Verify Configuration Completion
In FastGPT v4.17.0, configuration completion can be verified through the following executable actions:
- Run a monthly compliance ledger summary test task, and check whether the output includes all required document fields and core content.
- Simulate a model call failure scenario, and verify whether the fallback mechanism triggers to automatically switch to the standby model.
- Check the API key’s permission configuration, and confirm that only authorized roles can access the model interface to meet security requirements.
- Generate a compliance report, and verify whether the output format meets preset structured requirements without additional prompt adjustments.
