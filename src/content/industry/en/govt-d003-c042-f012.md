# Ledger Summary and Report Generation for Legal Compliance and Major Risk Management: Deployment and Upgrade

## What the data for this category looks like
This category of data originates from enterprise contract management systems, compliance risk databases, legal and regulatory repositories, case management systems, and reporting platforms. Daily documents include compliance risk lists, contract legal review opinions, legal opinions on major matters, compliance review forms, and violation investigation reports. Fields cover risk level, review subject, involved business segment, processing status, and more. Data is updated monthly, requiring batch synchronization of structured and unstructured documents across multiple systems. This data is used for ledger summary and compliance report generation.

## What constraints these characteristics impose on the deployment and upgrade phase
Data in this category involves sensitive content related to operational compliance, and must strictly follow internal network isolation requirements. Therefore, deployment must prioritize support for internal network environments. The monthly batch synchronization of data across multiple systems requires deployment configurations to support scheduled scheduling tasks, to avoid high-frequency data pulling that occupies system resources. The unstructured nature of compliance documents requires adaptation to storage and parsing of multi-format files. Data storage must also meet enterprise internal network security specifications. Errors may lead to major legal risks, so deployment must include failure alerts and data backup mechanisms to ensure the reliability of ledger summary and report generation.

## How to Configure Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `PG_URL` | Internal network compliance database dedicated connection string, formatted as `postgresql://username:password@internal IP:5432/compliance database name` | Legal compliance data is stored in the enterprise internal network PostgreSQL database, and public network access must be blocked to ensure data security |
| `REDIS_URL` | Internal network dedicated cache instance address, formatted as `redis://:password@internal IP:6379/0` | Cache high-frequency query results of monthly compliance risk lists to avoid pulling full database data for each request |
| `DB_MAX_LINK` | `20–30` | Synchronize data from multiple systems during monthly ledger summary. This value adapts to the connection requirements of batch tasks and avoids connection exhaustion |
| `STORAGE_S3_ENDPOINT` | Enterprise internal network object storage endpoint address, such as `http://s3.internal:9000` | Compliance documents must be stored on the internal network, and public network transmission is not allowed, in line with enterprise data security specifications |
| `ROOT_KEY` | Random 32-bit string | Restrict access permissions for internal network administrators to prevent unauthorized operations from affecting compliance ledger generation |
| `FE_DOMAIN` | FastGPT domain name deployed on the enterprise internal network, such as `http://fastgpt.internal` | Only accessible to internal network users, in line with internal network access control requirements for Chinese public sector and state-owned enterprise environments |

## Three Common Configuration Mistakes
- Issue: Database connection errors occur during internal network deployment, with logs showing connection refusal or timeout. Cause: The internal network database address was not used, and a public network database connection string was incorrectly configured, violating data isolation requirements
- Issue: Model API calls respond slowly, while curl tests run normally. Cause: The `REDIS_URL` cache for high-frequency compliance risk query results was not configured, causing full database data to be pulled for each request and increasing system overhead
- Issue: Monthly ledger summary tasks fail to execute, with logs showing connection exhaustion. Cause: The `DB_MAX_LINK` parameter was not adjusted, and the maximum database connection limit was exceeded during batch synchronization, preventing new connections from being established

## How to Verify a Successful Configuration
- Run an internal network database connection test using the configured `PG_URL` and `DB_MAX_LINK` parameters to verify that the specified number of database connections can be established normally
- Trigger the monthly ledger summary task and check the task execution logs to confirm there are no connection timeouts, data pull failures, or storage abnormalities
- Access the `FE_DOMAIN` to verify that only internal network IP addresses can log in to the system, and that the administrator backend can be accessed normally using `ROOT_KEY`
- Upload compliance documents to the system to verify that files can be stored normally in the internal network object storage configured via `STORAGE_S3_ENDPOINT`

The values provided are common starting points and should be measured against the reader's own samples.
