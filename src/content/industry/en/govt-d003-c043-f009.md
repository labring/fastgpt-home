# Special Equipment Safety Supervision: Ledger Summary and Report Generation — Model Access and Configuration

## What data for this category looks like
This category of data includes documents such as special equipment use registration certificates, periodic inspection reports, maintenance records, hidden danger rectification notices, accident reports, and operator certificates. Data sources are the special equipment safety supervision system, inspection and testing institution systems, user unit ledgers, and operator certificate databases, with a monthly update frequency. Each individual record includes fields such as a unique equipment identifier, inspection cycle node, maintenance execution time, operator qualification validity period, etc. Some documents contain both structured registration information and unstructured descriptive content.

## How to set the configurations
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | Must accommodate associated content from multiple special equipment documents, avoiding context overflow that disrupts association verification between equipment and inspection cycles |
| `maxTokens` | `2000–3000 token` | The generated length of a single ledger summary report must cover inspection and maintenance information for all equipment in the monthly cycle, avoiding truncation of critical content |
| `quoteMaxToken` | `1500 token` | Must retain sufficient original document reference fragments to support traceability verification for hidden danger rectification and operational qualifications |
| `temperature` | `0.1–0.3` | Regulatory reports require strict and accurate content, reducing the probability of randomly generated content |
| `AIPROXY_API_ENDPOINT` | Fill in the actual interface address based on the deployment environment | Must connect to compliant large model services, adapting to domestic deployed large model interface specifications |
| `AIPROXY_API_TOKEN` | Fill in the interface key applied for in actual use | Completes identity verification for model services, ensuring call permissions |

## Three common mistakes
- Phenomenon: A 401 status code is returned when calling the model, or a prompt indicating an invalid key is shown. Cause: The `AIPROXY_API_TOKEN` parameter was not filled correctly, or the key has expired and become invalid.
- Phenomenon: The device and inspection cycle association in the model-generated report is incorrect, and the number of results does not match the actual ledger. Cause: The `maxContext` parameter value is too small, causing the context to be truncated and losing some device association information.
- Phenomenon: Model call fails in a local non-Docker deployment environment, with a prompt indicating inability to connect to the specified interface. Cause: The `AIPROXY_API_ENDPOINT` parameter was not configured correctly, or local network restrictions prevent access to the target interface address.

## How to confirm the configuration is complete
- Perform a quick generation test for a single device ledger, and verify that the generated content includes core fields such as the device’s use registration certificate number and the date of the most recent inspection report.
- Import monthly batch ledger data, and check that the model call returns a successful status with no error prompts.
- Adjust the `temperature` parameter, then compare the content of two generated reports to confirm that content consistency meets the strictness requirements of regulatory documents.
- Verify the validity of `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN`, initiate a test request through the model’s interface debugging tool, and confirm that a normal response is returned.

The values provided are common starting points and should be measured against the reader's own samples.
