# Ledger Summary and Report Generation for Environmental Law Enforcement and Monitoring Supervision: Knowledge Base Retrieval and Recall

This document is written based on FastGPT v4.17.0.

## What This Category of Data Looks Like
Daily documents for ecological environmental law enforcement and monitoring supervision scenarios include on-site inspection records, sampling records, monitoring reports, order for correction decisions, and administrative penalty decisions. Data sources include online monitoring platforms, automatic pollution source monitoring data, ecological environmental law enforcement systems, and third-party test reports. Data is updated daily. Document structures combine structured monitoring parameters and unstructured law enforcement document content. Fields include law enforcement number, monitoring point, rectification requirements, and units are determined based on monitoring indicators and document specifications.

## Constraints on Knowledge Base Retrieval and Recall
Daily updated data sources require the retrieval process to support incremental synchronization and high-frequency update verification, to prevent ledger summary errors caused by data lag. Multi-source, multi-format document types require retrieval strategies to balance precise matching of structured data and semantic association of unstructured text. The evidence rigor requirement in law enforcement scenarios means recall results must cover key law enforcement and monitoring details, and avoid omitting core information such as excessive emissions and penalty basis. Omitting such information may lead to insufficient evidence or improper disposal. Additionally, ledger summary and report generation rely on associated recall across multiple documents, so data from different sources must be accurately linked.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Similarity Threshold | 0.75–0.85 | Law enforcement and monitoring data require high matching accuracy to avoid irrelevant records interfering with ledger summary. Adjust based on the scenario after calibration via actual testing |
| Single Search Limit | Top 10 entries | The number of core documents in this category is limited. Excessive recall results will exceed the context window and affect the logical coherence of report generation |
| Retrieval Mode | Hybrid Retrieval | Balance field matching of structured monitoring data and semantic association of unstructured law enforcement documents, to meet retrieval needs for multi-type documents |
| Reranking | Enabled | Perform secondary sorting on initial recall results, to improve the display priority of key evidence such as excessive emission records and penalty basis |
| Query Expansion | Enabled | Expand query semantics to cover professional term variants in law enforcement scenarios, and improve matching accuracy with custom retrieval templates |
| Chunk Length | 800–1200 characters | Adapt to the average paragraph length of monitoring reports and law enforcement documents in this category, avoid losing key information due to overly short fragments, or difficulty in matching due to overly long fragments |
| Bound Dataset | Bind three types of datasets: law enforcement, monitoring, and online monitoring | Accurately match data sources exclusive to this category, avoid recalling documents from unrelated business systems |

## Three Common Misconfigurations
- An error "Request failed with status code 400" occurs when uploading Feishu knowledge base documents. This happens when access permissions for the Feishu data source are not configured correctly, or the document format fails chunk verification.
- Setting a custom chunk length that is too large or too small causes recalled text fragments to fail to fully carry key information from monitoring reports or law enforcement documents. This occurs when parameters are not adjusted based on the average length of documents in this category.
- Local knowledge base conversation lag occurs. This is caused by failing to adjust the single search limit or enable reranking, leading to excessive redundant data being recalled and exceeding the system's context processing capacity.

## How to Verify Proper Configuration
- Import a single typical monitoring report or law enforcement document, and verify that core fields from the document appear in retrieval results, such as monitoring point, pollutant concentration, and law enforcement time.
- Trigger a professional query, such as "Records of excessive emissions from sewage outlets in a certain area", and confirm that the number of returned results matches the set single search limit.
- View the data source synchronization log to confirm that daily updated online monitoring data has been synchronized to the knowledge base as planned, with no delays or omissions.
- Test retrieval results with and without reranking enabled, to confirm that the sorting logic for key evidence aligns with business requirements.
