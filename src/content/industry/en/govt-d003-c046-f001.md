# Social Assistance and Minimum Livelihood Guarantee Audit: Ledger Summary and Report Generation - HTTP Interfaces and External Systems

## Data Profile
Data for this category originates primarily from the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-department shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, and tax authorities. Daily business documents include minimum livelihood guarantee application forms, family economic status verification reports, household survey forms, democratic appraisal records, public notice materials, and assistance approval forms.

Data is updated on a monthly basis. Core fields include family population information, income and property details, assistance qualification audit results, approval process nodes, and more. The statistical unit is natural person households. The data volume of a single document accumulates gradually as audit steps progress.

## Constraints for HTTP Interfaces and External Systems
Monthly updated data sources require interfaces to support scheduled batch pulling of full or incremental data. This prevents external systems from rejecting responses due to overload from single requests.

Cross-department multi-source data has format differences, so interfaces must support field mapping rules for different systems and adapt to return structures from public security household registration, human resources and social security social insurance, and other systems.

Accumulated document data across multiple steps requires that interface return fields fully cover core business items. Missing fields lead to missing key information in ledger summaries, creating risks of incorrect or missed assistance guarantees.

For low error tolerance business scenarios, interfaces must return clear status identifiers and error details to enable quick problem localization.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Carry a Bearer token with a 7-day validity period | Meets the identity verification requirements of external system interfaces, and avoids frequent token refreshes that impact synchronization efficiency |
| `variables` | Map two core variables: family ID and audit cycle | Adapts to monthly updated data source pulling requirements, and accurately locates ledger data for the corresponding cycle |
| Interface request timeout | 600 seconds | Covers the time required to pull cross-department multi-source data, and prevents request interruptions due to large data volumes |
| `responseData` | Extract a subset of core business fields | Standardizes document data returned by different systems, and facilitates quick completion of ledger summaries |
| Retry strategy | Retry 2 times after failure, with a 30-second interval | Addresses scenarios of temporary network fluctuations or temporary unavailability of external systems |

## Common Misconfigurations
- A 400 status code is returned with no response body when calling the interface. The cause is an incorrectly configured `Authorization` token, or `variables` passed in a format that does not meet external system requirements. This leads to request verification failure.
- Ledger summary data is missing cross-department shared income and property fields. The cause is failure to extract complete response fields according to `responseData`, with key data items returned by public security, tax, and other systems omitted.
- Interface requests frequently trigger timeouts. The cause is an unreasonably set timeout period, or a single request pulling a dataset larger than the monthly full data scale, exceeding the response limit of the external system.

## How to Verify Successful Configuration
Initiate a test request using the FastGPT v4.17.0 interface debugging tool. Check that the response header includes the correct identity verification identifier.
Compare the parameters passed in the `variables` variable with the corresponding fields of actual business documents. Confirm the mapping relationship is accurate.
Verify that the fields extracted by `responseData` cover core business items including family population and income and property.
Simulate a monthly data pulling request. Confirm the response data volume matches the expected scale of the business scenario.
