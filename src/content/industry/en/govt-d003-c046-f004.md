# Ledger Summary and Report Generation for Social Assistance and Minimum Living Security Audit: Workflow Orchestration

## What the data for this category looks like
The data for this category comes from the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-department shared public security, human resources and social security, medical insurance, housing construction, and tax data. The update frequency is monthly. Daily processed documents include minimum living security application forms, family economic status verification reports, household survey forms, democratic review records, public notice materials, and assistance approval forms. Core fields cover the number of family members, per capita income amount, family property details, approval circulation status, and more. Data is grouped by household, with multiple business documents linked to a single household's data.

## What constraints these characteristics impose on the "workflow orchestration" link
Integration of cross-department data sources requires workflows to configure multiple parallel data pull nodes. This prevents single-node timeouts from blocking the overall process, and aligns with the business requirement of this category for cross-department property verification.
The monthly update frequency means workflows must include scheduled trigger rules. This matches the periodic processing needs of civil affairs work.
The circulation of multiple document types requires workflows to support parsing different formats and extracting fields. This ensures accurate aggregation of core information.
The close link between family economic status and assistance eligibility requires strict field matching during variable transfer. This avoids errors such as incorrect or missed assistance caused by data misalignment.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Scheduled Trigger Rule | Execute at 09:00 on the 1st of each month | Matches the monthly update business cycle of civil affairs assistance ledgers, and adapts to the monthly synchronization rhythm of data sources |
| `variables` | Bind 8 core fields including household ID, per capita income, and total family property | Uniformly collect fields pulled from cross-system sources, avoiding repeated configuration of node parameters |
| `nodeId` | Bind in the order of data source nodes (verification system node → public security data node) | Ensure the correct order of variable transfer, avoiding audit errors caused by field misalignment |
| Field Validation Rules | Income field ≥ 0 yuan, family population ≥ 1 person | Avoid audit failure caused by empty or invalid data, and comply with mandatory requirements for assistance audits |
| Result Export Format | Export as Excel files of 1000–1500 KB | Adapt to the requirements of civil affairs ledger archiving and reporting, facilitating subsequent manual verification |

## Three Common Errors
- Symptom: A connection failure prompt pops up when entering the workflow editor in a Docker deployment environment. Cause: Cross-domain access permissions for workflow nodes are not configured correctly, or corresponding service ports are not opened for local container port mapping.
- Symptom: After setting global variables, subsequent nodes cannot read the updated variable values. Cause: The scope binding for `variables` is not enabled correctly, or the variable update node is not configured as a preceding trigger node.
- Symptom: Field missing occurs in node configuration after importing a preset workflow file. Cause: Compatibility rules for FastGPT v4.17.0 are not matched during import, or the `nodeId` of the preset workflow conflicts with the node ID of the current environment.

## How to Confirm the Configuration is Complete
- Manually trigger the workflow once. Check the node operation logs to confirm that all data source nodes have successfully pulled corresponding data.
- Check the `variables` pool. Confirm that all configured core fields have been correctly assigned, with no empty or abnormal values.
- Export the test result file. Verify whether the export format and field content meet the preset ledger requirements.
- Simulate abnormal data input. Verify whether the field validation rules normally trigger interception.
