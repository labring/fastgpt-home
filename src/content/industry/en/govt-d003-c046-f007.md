# Ledger Aggregation and Report Generation for Social Assistance and Minimum Living Security Review: Database and Operations

## What this category of data consists of
This category of data includes daily business documents such as minimum living security application forms, family economic status verification reports, household survey forms, democratic appraisal records, public notice materials, and assistance approval forms. Data sources include the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-department shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, and tax authorities. Most data consists of structured fields, including family income, property amount, personnel identity relationships, approval status, and other content. The update frequency is monthly. Some offline household survey materials require manual entry for supplementation.

## What constraints do these characteristics impose on the database and operations link
Cross-department multi-source data access requires the database to support multi-format data docking and field mapping. This prevents data import failures caused by inconsistent data formats. Monthly update frequency creates periodic data write peaks. Reasonable connection pool parameters must be configured to handle concurrent access. Daily documents include attachments such as scanned paper materials. Sufficient unstructured data storage capacity must be reserved. Data errors can lead to incorrect or missed assistance benefits, fund recovery, and other negative outcomes. Data verification, backup, and rollback mechanisms must be implemented in the operations link to ensure data consistency and traceability.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | Exclusive connection string with authentication information, pointing to replica set nodes | Used to store unstructured supporting materials and process records, adapts to the unstructured data storage requirements of FastGPT v4.17.0, and replica sets ensure data high availability |
| `PG_URL` | Instance connection address that supports JSONB fields | Used to store structured business data such as minimum living security applications and verification reports with complex fields, and JSONB can flexibly store extended business fields |
| `DB_MAX_LINK` | 50–80 | Addresses concurrent write peaks during monthly data updates to avoid data import failures caused by exhausted connections |
| `REDIS_URL` | Connection address pointing to an exclusive cache instance | Used to cache query results of cross-department shared data to reduce delays from repeated cross-system calls |

## Three common configuration mistakes
- Phenomenon: MongoDB connection timeout error, normal connection via mongosh. Cause: Cross-origin access whitelist not added in FastGPT configuration, or the configured `MONGODB_URI` does not include the correct database name.
- Phenomenon: Workflow canvas drag delay, slow node loading. Cause: `DB_MAX_LINK` configured too low, leading to exhausted concurrent connections, and status queries for workflow nodes cannot respond in a timely manner.
- Phenomenon: Some household survey materials are missing from ledger aggregation results. Cause: Storage path for unstructured data not configured, leading to attachment data not being correctly stored in the database.

## How to confirm the configuration is correct
- Perform a local connection test: use the configured `MONGODB_URI` and `PG_URL` to connect to the corresponding databases, and verify that read and write permissions are normal.
- Trigger a simulated monthly data update task, check the database connection pool monitoring metrics, and confirm that the number of connections does not reach the configured upper limit.
- Import a standard minimum living security application document, verify that structured fields and attachments can be correctly stored and retrieved.
- Check system logs to confirm that no timeout errors occur in cross-department data synchronization tasks.

The values given are common starting points and should be measured against the reader's own samples.
