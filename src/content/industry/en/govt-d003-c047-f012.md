# Administrative Penalty Case File Processing: Ledger Summary and Report Generation - Deployment and Upgrade

## What this category of data looks like
This category of data originates from administrative law enforcement case handling systems, law enforcement recorder footage, the national enterprise credit information publicity system, and departmental supervision databases. The update frequency is daily. Daily processed documents include on-site inspection records, inquiry records, evidence lists, prior administrative penalty notification letters, hearing notification letters, penalty decisions, and delivery receipts. Core fields cover illegal subjects, illegal facts, discretionary benchmark application status, penalty basis, penalty decision, delivery status, and similar items. No additional statistical fields are included.

## What constraints do these characteristics impose on the deployment and upgrade phase
Multi-source heterogeneous data sources require compatible interface formats for different systems during deployment, and multiple storage nodes must be configured to support separate storage of structured and unstructured data. The daily update frequency requires retaining incremental synchronization mechanisms during the upgrade phase to avoid business interruptions caused by full synchronization. The diverse types of case file documents require configuring field mapping rules to ensure core information from different documents can be extracted uniformly. The strict confidentiality and integrity requirements for law enforcement data require adding log auditing and data backup steps during deployment and upgrade to prevent data loss or tampering.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–200 concurrent connections` | Adapts to the daily incremental data pull concurrency of multiple law enforcement systems, avoiding database connection exhaustion |
| `MONGODB_URI` | `Cluster address with read-write separation configuration` | Stores structured data of case file ledgers; read-write separation balances query and write performance |
| `REDIS_URL` | `Instance address with RDB persistence enabled` | Caches law enforcement sessions and temporary ledger data to ensure traceability of daily update task status |
| `STORAGE_S3_ENDPOINT` | `Access endpoint corresponding to the internal storage system` | Stores unstructured data such as law enforcement recorder footage and scanned document copies |
| `FILE_TOKEN_KEY` | `Key aligned with the internal permission system` | Verifies access permissions for case file documents, preventing leakage of sensitive law enforcement data |

## Three common misconfigurations
- Phenomenon: After upgrading to FastGPT v4.17.0, running the initial script returns a 404 error. Cause: `STORAGE_S3_ENDPOINT` is not configured correctly, preventing static resource files from loading properly.
- Phenomenon: Ledger summary tasks time out. Cause: The value of `DB_MAX_LINK` is not adjusted; insufficient database connections cause slow data pulling.
- Phenomenon: Empty results are returned when using the case file knowledge base for question answering. Cause: Field mapping rules are not configured, so core fields from law enforcement documents cannot be correctly extracted and indexed.

## How to confirm the configuration is complete
- Run a database connectivity test to verify that the connections for `MONGODB_URI` and `REDIS_URL` are normal.
- Manually trigger a daily incremental synchronization task and check that there are no connection timeout or data loss errors in the logs.
- Upload a standard administrative penalty case file document and verify that the field extraction results match the preset rules.
- Check the `FILE_TOKEN_KEY` configuration to confirm that only authorized users can access confidential law enforcement documents.

The values provided are common starting points and should be measured against the reader's own samples.
