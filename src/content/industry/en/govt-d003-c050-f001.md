# Ledger Summary and Report Generation for Fiscal Expenditure Performance Evaluation: HTTP APIs and External Systems

## What data for this category looks like
This category’s data primarily comes from the unified budget management system, project declaration materials, fund payment data, business system ledgers, and satisfaction surveys. The update frequency is annual. Daily documents include performance target forms, self-assessment forms, performance evaluation reports, supporting material lists, and rectification reports. Data fields cover basic project information, fund allocation details, performance indicator completion status, satisfaction scores, and more. Each document is linked to a unique project code. Supporting materials must correspond to specific expenditure links. Ledger formats vary across different budget units, so multiple sets of field mapping rules need to be supported.

## What constraints do these characteristics impose on the HTTP APIs and External Systems link
The low-frequency annual update feature requires APIs to support on-demand triggering, to avoid invalid real-time polling calls. Heterogeneous data from multiple sources requires APIs to support parameter transmission in different formats, adapting to scenarios such as structured output from budget systems and semi-structured text output from business ledgers. The requirement that documents are linked to a unique project code means APIs must verify the legitimacy of the project identifier carried in `Authorization`, to ensure accurate data binding and avoid cross-project data confusion. The requirement for transmitting supporting material attachments requires APIs to support large file chunked uploads, while also limiting the total size of attachments per request to prevent exhaustion of service resources.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer token carrying the project code, valid for 365 days | Matches the annual data update rhythm, ensures request legitimacy |
| `variables` | Predefined project ID, report template ID variables | Adapts to ledger summary requirements for parallel processing of multiple projects |
| `responseData` | Structured format including project code, supporting material list, scoring fields | Aligns with the unique identifier field of performance evaluation documents |
| Request timeout | 600 seconds | Covers the time required for large attachment uploads and multi-ledger data merging |
| Attachment upload size limit | 1000 MB | Adapts to batch transmission requirements for supporting materials |
| API trigger method | Triggered according to the annual project cycle | Matches data update frequency, reduces invalid calls |

## Three Common Misconfiguration Issues
- API returns 502 Bad Gateway: Cause: HTTPS reverse proxy is not correctly configured in Nginx, and external requests are not forwarded to the listening port of the FastGPT service.
- POST /api/admin/initv4818 returns 404 after running the upgrade script: Cause: The FastGPT v4.17.0 base service is not deployed, and the initialization interface has not finished loading.
- Performance report data returned by the API is missing supporting material fields: Cause: Attachment association fields are not configured in `responseData`, and document field specifications are not matched.

## How to Verify Proper Configuration
- Send a test request with a valid `Authorization` token, confirm the returned status code is 200 OK.
- Pass the predefined `variables` project ID, confirm the ledger data returned by the API is bound to the corresponding project code.
- Upload an attachment not exceeding 1000 MB, confirm the API can receive it normally and return a success flag.
- Trigger an API call according to the annual project cycle, confirm the interface does not interrupt execution due to timeout or parameter errors.

The values provided are common starting points, and should be evaluated against relevant local samples.
