# Department Final Accounts and Financial Reports: Ledger Summary and Report Generation — Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
This category's data originates from the unified budget management system, centralized treasury payment system, accounting system, and asset management system. The update frequency follows an annual cycle. Daily produced documents include department final account statements, balance sheets, income and expenditure final account statements, final account explanations, and government financial reports. Each document contains fields such as income and expenditure details, asset and liability balances, and budget execution difference explanations. Units of measurement include ten thousand yuan, yuan, and other standard units. Data must be verified through multiple links before being summarized to the competent department or financial department.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
The annual update feature requires multi-turn dialogue to be limited to the context of the current accounting year, to avoid confusion from cross-year data. Data from multiple systems must be gradually aligned on field mappings across different systems via multi-turn interactions, to ensure consistency between ledger and statement data. Documents with fixed structures require prompts to clearly specify extraction fields and formats for each document, to reduce interference from unstructured content. Strict potential error consequences require adding a difference verification step in dialogue to confirm that budget execution difference explanations match actual payment data. The requirement to summarize reports from subordinate units requires gradually collecting ledger data from each unit through multi-turn dialogue before completing the overall summary.

## Three Common Misconfiguration Issues
- Newly deployed systems cannot initiate conversations, and the interface returns an invalid key error. The cause is that the correct FastGPT call key is not configured in the system backend.
- Chat records of different business users are cross-used, and independent sessions cannot be distinguished. The cause is that the `chatId` parameter is not bound according to the business user ID.
- A version update notice pops up automatically every time a new conversation is opened, and it cannot be closed. The cause is that the system's version update prompt configuration item is not disabled.

## How to Verify Successful Configuration
- Initiate a test conversation, enter a query for final account data of a specified year, check if the returned results are limited to the current accounting year, and confirm that the `variables` parameter is effective.
- Use two different business user IDs bound to `chatId` to initiate conversations, check that the chat records of both parties do not interfere with each other, and confirm that the session isolation configuration is effective.
- View the key configuration page in the system backend, confirm that the exclusive call key for the business system has been bound, and check that there are no key errors in the API call logs.
- Trigger the prompt loading action, check if the corresponding final account document format in the knowledge base is correctly read, and confirm that the dynamic prompt loading configuration is effective.
