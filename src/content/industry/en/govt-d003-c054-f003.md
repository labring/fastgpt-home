# Ledger Summary and Report Generation for Flood Control, Disaster Prevention and Emergency Duty: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Data for this category primarily comes from meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. It is updated daily. Daily documents include duty records, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Fields cover rainfall and water level values, danger severity levels, material types and quantities, number of transferred and resettled people, and more. Most formats are structured tables and semi-structured text. Some data requires cross-system alignment of units and field definitions.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
Since data sources are scattered and updated daily, multi-turn dialogue must continuously maintain the `messages` context to associate the latest rainfall and water level and disaster information. This avoids calling expired ledgers. Document types include structured tables and semi-structured text. Prompts must adapt to field extraction for different formats to ensure field alignment for content such as duty records and material allocation slips. Cross-department dispatch requirements demand that the dialogue process clearly distinguish the priority of data from different sources. The dialogue context length for a single session must also be limited to prevent redundant information from interfering with summary logic.

## Configuration Settings
The following configuration instructions apply to FastGPT v4.17.0. The specific configuration items are as follows:

| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| Maximum Context Length | 8000–12000 characters | Flood control ledger data is often spliced from multiple sources. Overly long contexts can cause the large language model to confuse field ownership |
| `messages` Context Maintenance | Retain the last 3 turns of dialogue and the latest 10 system data entries | Emergency scenarios require association with the latest warning and disaster information. Redundant old dialogue can interfere with summary logic |
| `variables` Variable Binding | Bind preset parameters such as daily rainfall thresholds and material inventory limits | Unified calling of fixed business-side values is required to avoid manual input errors |
| Single Dialogue Turn Limit | No more than 5 turns | Emergency duty scenarios require fast output. Too many turns will extend response time |
| Context Refresh Interval | 600 seconds | Data is updated daily. This interval balances timeliness and system load |
| `chatId` Session Isolation | Assign independent sessions per duty team | Prevent ledger data from different teams from interfering with each other |

## Three Common Configuration Errors
- Issue: A 500 error is returned when importing documents such as duty records or material allocation slips. Cause: The structured table format within the documents is not adapted, leading to failed chunk parsing.
- Issue: All historical dialogue results are included in the output after multi-turn dialogue, containing redundant past conversation content. Cause: The retention range of the `messages` context is not limited, causing the large language model to call all historical content.
- Issue: The first dialogue response delay exceeds 3 seconds, while subsequent responses perform normally. Cause: The context refresh interval is not configured, so the first call needs to load all historical ledger data.

## How to Verify Correct Configuration
- Import one simulated rapid disaster report document, and verify that the extracted fields align with the preset `variables` bound parameters.
- Initiate a multi-turn dialogue with no more than 3 turns, and check that the final output only includes the summary report for this dialogue, with no redundant historical content.
- Wait 600 seconds, then initiate the same query again, and verify that the returned data is the latest updated value.
- Test the first dialogue response speed, and confirm that the delay falls within the acceptable range for the business scenario.

All provided configuration values are common starting points, and should be evaluated against the reader's own samples.
