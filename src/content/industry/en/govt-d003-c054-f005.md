# Ledger Summary and Report Generation for Flood Prevention, Disaster Mitigation and Emergency Duty: Tool Calling and Plugins

## What this category's data looks like
The data for this category primarily comes from meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Daily processed documents include duty records, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Data updates occur daily; some real-time monitoring data has shorter update intervals. Document fields include rainfall and water level values, danger severity levels, material quantities, transferred and resettled population counts, and similar metrics. Common units are millimeters, cubic meters per second, pieces, people, and others. Field formats vary across documents from different sources.

## What constraints these characteristics impose on tool calling and plugins
Multi-source and heterogeneous data sources require tool calling to support parallel pulling from multiple data sources and format unification. Without this, cross-system ledger summary cannot be completed. The daily update frequency and short update intervals of some real-time data require configuring plugin scheduling rules that combine scheduled triggers and real-time triggers, to avoid data lag. Differences in document fields require plugins to have built-in field mapping rules, to convert documents from different sources into a unified ledger format. Additionally, errors in this category directly affect emergency response efficiency. Configure failure retry and alert mechanisms for tool calling, to ensure critical data is not lost.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | Adapts to varied task types in emergency scenarios, automatically selects matching tools to complete data pulling and summary |
| Tool calling timeout | `600 seconds` | Cross-system interaction is required for multi-source data pulling, reserve sufficient time to integrate hydrological, meteorological, and other data |
| Tool calling retry count | `2–3 times` | Addresses network fluctuations or temporary system response delays, prevents ledger generation from being interrupted by a single failed call |
| `functionCall` | `strict: true` | Strictly matches the preset field format of emergency documents, ensures generated ledgers and reports meet specifications |
| Plugin context window | `Last 8 chat records` | Retains key information from recent consultation minutes and rapid disaster reports, supports continuous generation of emergency response reports |
| Plugin trigger timing | Triggered at data update nodes | Matches the update rhythm of hydrological and meteorological data, ensures ledger content is synchronized with real-time disaster conditions |

## Three common mistakes
- Symptom: A 400 status code is returned when calling the tool interface, and the response body prompts a parameter format error. Cause: Field mapping for tool calling is not correctly bound, causing the request body to not match the field requirements of emergency documents.
- Symptom: The text content extraction node of the plugin returns empty fields. Cause: Field rules are not configured for specific document types in emergency scenarios, so target fields in duty records and material allocation slips cannot be identified.
- Symptom: Tool calling context is lost during continuous conversations. Cause: An appropriate context window size is not set, causing early consultation minutes and disaster information to be cleared, which prevents subsequent report generation.

## How to confirm configurations are correct
- Manually trigger tool calling, check if rainfall data for the specified time period can be pulled from the designated hydrological monitoring system, and format conversion is completed.
- Simulate a conversation with multiple rounds of emergency consultations, confirm that key information from the last 8 chat records is retained during tool calling.
- Disconnect the simulated data source connection, verify that the tool calling triggers the timeout retry mechanism and generates corresponding error logs.
- Check the backend configuration logs of FastGPT v4.17.0, confirm that the `toolChoice` and `functionCall` parameters have taken effect as configured.
