# Ledger Summary and Report Generation for Flood Control, Disaster Prevention and Emergency Duty: Database and Operations

## Data Overview for This Category
This category includes multi-source real-time and static ledgers. Data sources include weather warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Daily processed documents include duty logs, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Data is updated once daily. Structured fields include time, location, rainfall and water level values (units: millimeters, cubic meters per second), danger level, material quantities, and personnel information. Unstructured content includes meeting recording transcriptions, on-site video screenshots, and similar materials.

## Constraints for Database and Operations Workflows
Multi-source data access requires databases to support heterogeneous data storage and unified mapping. Separate storage solutions must be implemented for structured ledgers and unstructured documents. Daily data updates create demand for batch synchronization tasks. Proper connection pool configuration is required to avoid resource exhaustion. Specific numeric fields require unit-aware format validation to ensure accuracy of rainfall and water level data. Fast query needs during emergency scenarios demand caching frequently accessed real-time data to reduce load on underlying databases. Cross-departmental data integration requires fine-grained permission controls in operational configurations to protect sensitive disaster-related data.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Database connection address | Configure `MONGODB_URI` for MongoDB to store unstructured documents, and `PG_URL` for PostgreSQL to store structured ledgers | Adapts to storage needs for multiple data types in this category, separates read/write workloads |
| Maximum database connections | `DB_MAX_LINK` 20–30 | Balances resource usage between daily batch synchronization tasks and real-time queries |
| Redis connection address | `REDIS_URL` configured per actual deployment instance | Caches frequently queried real-time rainfall and water level data to reduce database load |
| PDF parsing memory threshold | 16–24 GB | Meets parsing requirements for large documents such as multi-page disaster reports and warning notices in this category |
| Concurrent request limit | First 60 | Matches stable response thresholds when local model servers are not at maximum capacity |
| Data synchronization interval | Daily at 00:00 | Aligns with the daily update frequency of data in this category |

## Three Common Misconfigurations
- Symptom: Returns an error similar to `Failed to connect to 192.168.xx.xx.:1433` when connecting to the database. Cause: Incorrect database connection address configuration, or the database instance does not allow access via the specified port.
- Symptom: High memory usage or service lag occurs after enabling PDF parsing. Cause: The parsing memory threshold was not adjusted to match the document length of multi-page disaster reports in this category. The default configuration cannot support parsing large documents.
- Symptom: No response or timeout occurs after concurrent requests exceed 60. Cause: The concurrent request limit was not configured appropriately based on local model server load, exceeding the carrying capacity of the database connection pool.

## How to Confirm Successful Configuration
- Use the built-in database connection testing tool in FastGPT v4.17.0 to verify that instances configured with `MONGODB_URI` and `PG_URL` can read and write the corresponding data types normally.
- Upload a typical multi-page rapid disaster report PDF document to trigger a parsing task, confirm that memory usage does not exceed the preset threshold and that parsing results are complete.
- Initiate a multi-concurrent request test, observe service response status, confirm that the concurrent request limit configuration matches the carrying capacity of local resources.
- Check the data synchronization logs to confirm that the daily 00:00 scheduled synchronization task runs normally, with no data missing or synchronization failure records.
