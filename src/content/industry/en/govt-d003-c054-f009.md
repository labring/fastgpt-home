# Ledger Summary and Report Generation for Flood Prevention, Disaster Mitigation and Emergency Duty: Model Access and Configuration

## What the data for this use case looks like
The daily business data for this use case includes multiple document types such as duty logs, warning notifications, consultation minutes, rapid disaster reports, emergency response plans, and material transfer orders. Data sources include meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Data updates occur daily. A single consolidated ledger must integrate structured fields from multiple sources: rainfall and water level values, disaster risk metrics, material quantities, number of people evacuated, and dispatch batches. Some documents also include unstructured on-site description content. Field units include millimeters, cubic meters, number of people, batches, and other categories. The data structure has a moderate degree of heterogeneity.

## What constraints these characteristics impose on the model access and configuration workflow
The multi-source, heterogeneous data structure requires model access to support input content in varied formats. The daily business update cycle requires configured model call latency to align with real-time summary requirements. Ledger summary and report generation integrate core information across multiple document types, so the model context length must fully contain complete input data to avoid truncation that loses critical disaster-related content. Variations in fields across documents require configured call rules to support extraction and integration logic for multiple data types. The strict requirements of emergency duty demand that model-generated content maintains high accuracy and avoids unnecessary divergence. Cross-departmental data collaboration needs require model access channels to support flexible configuration and permission management for third-party APIs.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | Adapts to the overall input and output length of multi-source ledgers and emergency reports, avoiding loss of core disaster data such as rainfall and water level values due to context truncation |
| `maxTokens` | `2000–3000 token` | Matches the standard generation length of a single consolidated report, ensuring coverage of complete business content including consultation minutes, material transfers, and evacuation plans |
| `temperature` | `0.2–0.4` | Reduces randomness in generated content, ensures accuracy of ledger data and disaster descriptions, and meets the rigorous work requirements of emergency duty |
| `toolChoice` | `auto` | Automatically calls built-in tools to integrate multi-source business data, eliminates the need for manually specified rules, and adapts to the collaborative summary requirements of cross-system data |
| `AIPROXY_API_ENDPOINT` | Fill in the corresponding address based on the deployment environment | Adapts to the access path of third-party models, ensuring the platform can normally call the target model |
| `AIPROXY_API_TOKEN` | Fill in the key assigned by the platform | Completes identity verification for model access, ensuring valid and compliant call permissions |

## Three common mistakes
- Issue: An error message stating "corresponding channel not found" or "API key invalid" appears during model calls. Cause: The `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` parameters are not filled correctly, or access permissions for the third-party model have not been configured on the platform.
- Issue: Some ledger fields are missing from the generated consolidated report, such as rainfall values and material transfer quantities. Cause: The `maxContext` setting is too small, resulting in truncation of input multi-source business data, which prevents the model from obtaining complete information to complete effective summary.
- Issue: The target model that has been accessed cannot be found in the model selection list of the text extraction or business dialogue module. Cause: The model access verification has not been completed on the platform’s model management page, or the model type supported by the current module does not match the accessed third-party model.

## How to confirm the configuration is complete
- Log in to the model management page of FastGPT v4.17.0, and confirm that the access status of the target model is "normal", with no error prompts such as "unauthorized" or "connection failed".
- Import a single test ledger containing multi-source business data, trigger the summary and report generation workflow, and check that the generated content includes all expected fields and business information.
- Review the platform backend logs to confirm there are no records of model call failures, parameter errors, or context truncation.
- Confirm that the accessed target model can be properly selected and called in the model selection list of the corresponding business module, with no missing or abnormal status.
