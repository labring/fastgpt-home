# Ledger Summary and Report Generation for Food Safety Supervision Sampling: HTTP Interfaces and External Systems

## What Data for This Category Looks Like
Data sources for this category include food safety sampling monitoring systems, the State Administration for Market Regulation sampling results query system, laboratory LIMS systems, and internal ledgers of food producers and operators.
Data is updated on a monthly basis.
Commonly used documents include sampling plans, sampling slips, inspection reports, non-compliant food verification and disposal reports, and risk control notices.
Data fields include sampling number, inspection items, non-compliant items, disposal results, and others.
Units are mostly batches, quantities, and number of inspection items.
Field structures vary across different documents.

## Constraints for HTTP Interfaces and External Systems
The monthly update frequency limits interface call rates to relatively low levels. Bulk data pulls must adapt to the standard scale of monthly data.
Multiple data sources require interfaces to support different authentication logic and data format adaptations. This enables connection to external platforms such as sampling systems and LIMS systems.
Diverse document structures require interfaces to support field mapping and extraction for multiple data types. This completes unified ledger summarization.
Delayed disposal of non-compliant food creates regulatory risks. This means interface stability and the accuracy of returned data have high requirements.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Fixed authentication token with Bearer prefix | Adapts to standard authentication requirements of external systems, ensures legitimacy of interface calls |
| `variables` | Configure sampling slip number and inspection report number as dynamically replaced variables | Matches bulk pull requirements for monthly ledgers, adapts to sampling data from different batches |
| `responseData` | Extract sampling number, inspection items, non-compliant items, and disposal results as output fields | Aligns with core data requirements for ledger summarization and report generation, simplifies subsequent processing workflows |
| Interface timeout period | 600 seconds | Adapts to pull delays for large-volume data such as inspection reports, prevents request interruptions mid-process |
| Single pull count | First 200 entries | Matches the regular scale of monthly sampling batches, avoids single requests exceeding interface load limits |
| Data format adaptation | Calibrated based on actual testing | Adapts to format differences such as JSON and CSV returned by different external systems |

## Three Common Misconfigurations
- The `IPROXY_API_ENDPOINT or AIPROXY_API_TOKEN is not set` error occurs: Corresponding external interface proxy endpoint or authentication token is not filled in the FastGPT configuration, preventing external system calls from being initiated.
- Mongo slow queries are triggered, accompanied by page unavailability and interface errors: Monthly ledger data is not pulled in pages. A single request pulls all batch data, exceeding database processing limits.
- Duplicate historical records appear in reports generated after API calls: Clearance rules for historical records are not correctly configured in request parameters, causing new historical context to be appended with each call.

## How to Verify Successful Configuration
In FastGPT v4.17.0, the following steps confirm whether configuration takes effect:
- Call the test interface, check if the returned `responseData` includes core fields such as sampling number and inspection items.
- View FastGPT runtime logs, confirm that the `Authorization` authentication header is correctly carried, and no unauthorized access errors occur.
- Initiate a bulk pull request, check that the number of entries returned per single request matches the configured range, and no interface overload prompts appear.
- Verify that dynamic `variables` parameters can be correctly replaced with specified sampling batch numbers, matching target data from corresponding data sources.

The values listed here are common starting points, and should be evaluated against the user's own samples.
