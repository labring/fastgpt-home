# Warehouse Logistics Ledger Summary and Report Generation: Knowledge Base Retrieval and Recall

## What this category of data looks like
Warehouse logistics ledger data primarily originates from warehouse management systems (WMS), inbound and outbound documents, monthly inventory reports, and similar sources. Data update frequency aligns with business batches: new ledgers are generated each time an inbound or outbound operation is completed, and full warehouse inventory summary data is updated after monthly inventory checks. Each ledger document follows a fixed structure, including fields such as inbound/outbound order number, material code, material name, specification and model, quantity, unit of measurement, operation time, handler, storage location, and more. Common units of measurement include piece, ton, cubic meter, box, and other business-standard units.

## Constraints on knowledge base retrieval and recall
Warehouse logistics ledgers have numerous structured fields and unique business-specific units. Retrieval must accurately match business attributes to prevent irrelevant material information from being included in reports via semantic recall. Data updates occur frequently, so the knowledge base must support incremental synchronization. Outdated recalled data will reduce report accuracy otherwise. The number of daily ledger entries per warehouse is relatively high. Retrieving too many documents in a single query will create redundant context during report generation, exceeding the model’s processing limit. Additionally, numeric fields in ledger data such as quantity require strict alignment with the business scenario. Generalized semantic retrieval cannot be used here, as it will lead to incorrect quantity matching.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Warehouse logistics ledgers have clear business attributes. This threshold filters low-match results to avoid irrelevant material information being included in summary reports |
| `limit` | Top 10 entries | Each ledger entry is concise. Retrieving too many entries will cause redundant context during report generation, exceeding the model's processing range |
| `searchMode` | vector_search | Vector retrieval is better suited for precise matching of business fields in structured ledgers compared to keyword retrieval |
| `usingReRank` | Enabled | Re-rank recalled results by relevance to ensure ledgers for core materials and frequent operations are prioritized for extraction |
| `datasetSearchUsingExtensionQuery` | Disabled | Ledger data has a fixed structure. Extended queries will introduce irrelevant business scenarios and reduce retrieval accuracy |
| `collectionIds` | Bind to the dedicated knowledge base collection for warehouse logistics ledgers | Isolate data from other categories to avoid cross-collection retrieval interfering with the business accuracy of ledger summary |

## Three Common Mistakes
- An error log is returned during knowledge base querying, or a 404 error occurs when running the initial script. The cause is that after upgrading FastGPT v4.17.0, the database script was not re-synced, or the pre-configured knowledge base collection was not re-bound.
- SearXNG returns empty search results. The cause is that a dedicated retrieval filtering rule for warehouse logistics ledgers was not configured, leading the recall range to cover non-target business data, or the `limit` parameter was set too low, resulting in incorrect truncation of results.
- The locally deployed chatglm2 model cannot be selected when creating a knowledge base. The cause is that the model access path was not correctly added to the FastGPT configuration file, or model permissions via one-api were not granted to the knowledge base retrieval module.

## How to Verify Successful Configuration
- Manually enter a known material code and verify that the retrieval results include the complete information of the corresponding ledger.
- Adjust the `similarity` parameter and observe changes in the matching degree of retrieval results to confirm the threshold meets business filtering requirements.
- View the knowledge base synchronization log to confirm that warehouse logistics ledger data has completed incremental synchronization in line with the business update rhythm.
- Test generating a ledger summary report to confirm that all recalled documents originate from the target collection, with no cross-category data included.
- Check the total storage size of the knowledge base, which aligns with the stock data scale of warehouse logistics business, and set a reasonable upper limit in megabytes.
