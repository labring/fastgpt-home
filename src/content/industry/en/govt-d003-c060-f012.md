# Ledger Summary and Report Generation for Warehousing and Logistics: Deployment and Upgrade

## What the data for this category looks like
Warehousing and logistics ledger data primarily comes from warehouse management systems (WMS), inbound and outbound document systems, and transportation scheduling terminals. Updates follow either daily batch updates or real-time single-ledger synchronization. A single ledger document includes fields such as material code, inbound and outbound time, actual receipt and shipment quantity, bin number, batch number, and handler ID. Units include pieces, cubic meters, tons, pallet counts, and more. Some ledgers include scanned paper documents as attachments.

## What constraints these characteristics impose on deployment and upgrades
The large number of fields in warehousing and logistics ledgers and their association with business processes require proper database connection pool configuration to support concurrent queries during deployment. Real-time synchronized ledger data requires vector database synchronization frequency to match business update rhythms to avoid data lag. Attached document files need a dedicated storage path to prevent excessive load on the primary database. During upgrades, the field format of older ledgers must be compatible to avoid missing key information in summary reports due to incorrect field mapping.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 15-20 | Meets concurrent query requirements for warehousing and logistics ledgers, prevents query failures caused by exhausted connection pools |
| `MONGODB_URI` | Fill in the MongoDB access address synchronized from the WMS system, with database authentication parameters | Core ledger data source for connecting to business systems |
| `REDIS_URL` | `redis://localhost:6379/0` | Caches frequently queried ledger entries and summary results to shorten response times |
| `STORAGE_S3_ENDPOINT` | Fill in the access address of the internal object storage service | Stores attachments such as scanned paper documents attached to ledgers |
| `FILE_TOKEN_KEY` | Custom 32-bit random string | Generates secure tokens for accessing attachments to prevent unauthorized access |

## Three Common Configuration Mistakes
- Symptom: Excessive time spent generating ledger summary reports. Cause: The `REDIS_URL` cache for high-frequency ledger data is not configured, causing each query to directly access the database and increasing system load.
- Symptom: 404 error returned when calling the ledger data source. Cause: The access whitelist for `MONGODB_URI` is not properly configured, or the database address is entered incorrectly, preventing connection to the data source.
- Symptom: Unable to load scanned document attachments attached to ledgers. Cause: `STORAGE_S3_ENDPOINT` or `FILE_TOKEN_KEY` is not configured, interrupting the attachment storage and reading process.

## How to Verify a Successful Configuration
- Use the background management function of FastGPT v4.17.0, log in to the data source management page, check the connection status corresponding to `MONGODB_URI`, and confirm that it shows a normal connection.
- Run a test query to pull 100 ledger entries from a specified time period, and verify that the response time meets expectations.
- Upload a test scanned paper inbound document, confirm that it can be stored normally and previewed in the ledger details.
- Check the system operation logs to confirm that the connection pool for `DB_MAX_LINK` does not show exhaustion errors, and there are no database connection exceptions.

The values provided are common starting points and should be measured against the reader's own samples.
