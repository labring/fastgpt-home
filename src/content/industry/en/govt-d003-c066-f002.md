# Ledger Summary and Report Generation for Advanced Chemical Materials: Vector Models and Indexes

## What data for this category looks like
Ledger and report data for advanced chemical materials primarily comes from internal enterprise production management systems, quality inspection systems, R&D document repositories, and supply chain management systems. Data update rhythms fall into three categories: production batch ledgers are synchronized and updated daily; R&D formula documents are updated on demand according to project progress; compliance test reports are updated per test batch. Individual documents are mostly semi-structured, containing fixed fields such as batch number, material grade, core performance parameters, raw material ratio, test date, and supplier information. Most performance parameter units are MPa, ℃, and parts per mass.

## What constraints these characteristics impose on vector models and indexing
The daily update feature of production ledgers requires indexes to support incremental updates, avoiding the time cost of full reconstruction. Semi-structured multi-field data requires binding field metadata during indexing to support subsequent filtered retrieval by field. Long-text R&D documents require setting a reasonable chunk length to avoid cross-semantic breakpoints. Differences in performance parameter units require unified unit handling during the preprocessing stage to ensure semantic consistency in vector model outputs. Large-volume supply chain data requires adjusting the index sharding strategy to improve retrieval efficiency.

## How to configure settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to semantic coherence of semi-structured documents for advanced chemical materials, avoids semantic fragmentation caused by overly short chunks |
| Overlap Length | 100–200 characters | Connects key information of adjacent chunks, retains business associations across chunk boundaries |
| Similarity Threshold | 0.75–0.85 | Balances retrieval recall accuracy and redundancy |
| Single Search Limit | Top 10 entries | Adapts to the context requirements of multi-field data for advanced chemical materials, avoids context overload from excessive results |
| `defaultToken` | 16384 | Adapts to the context length of long-text R&D documents |
| `maxToken` | 8192 | Controls the total token count spliced after retrieval, complies with input limits of mainstream large models |

## Three common misconfigurations
- Phenomenon: The number of retrieval results does not match expectations, and some key ledger data is not recalled. Cause: The similarity threshold is set too high, filtering out some business-relevant documents with low similarity.
- Phenomenon: Index reconstruction takes too long, unable to support daily updated production ledger data. Cause: Incremental indexing is not enabled, and full index reconstruction is performed each time, not adapted to the daily update frequency.
- Phenomenon: Inconsistent unit parameter data appears in the generated ledger reports. Cause: Performance parameter units are not unified during the preprocessing stage, and vectors generated by the vector model have semantic deviations, leading to retrieval results mixed with data with incorrect units.

## How to verify proper configuration
- The index management page of FastGPT v4.17.0 can be accessed to confirm that chunk length and overlap length settings match preset values.
- A typical quality inspection report for advanced chemical materials can be uploaded, indexing triggered, and ledger data for a specified batch retrieved to confirm that the number of recalled entries matches the single search limit setting.
- The similarity threshold can be adjusted, the same set of test data retrieved, and the business relevance of recall results compared to confirm that the threshold setting is reasonable.
- Daily updated production ledger data can be simulated, incremental indexing triggered, and index update time confirmed to meet expectations.

The values provided are common starting points and should be measured against the applicable samples for the respective use case.
