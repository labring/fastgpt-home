# Ledger Summary and Report Generation for Advanced Chemical Materials: Database and Operations

## What the data for this category looks like
The ledger data for advanced chemical materials comes from three sources. These sources are manufacturing execution systems, laboratory management systems, and warehouse management systems. Update frequency aligns with business milestones. Single ledgers are updated in real time after a production batch is completed. Daily production batch data is aggregated each day. Research and development project ledgers are updated irregularly alongside experiment milestones. Each single ledger document corresponds to one production batch. It includes fields such as batch number, raw material feeding weight, reaction temperature range, production completion time, quality inspection indicator values, and inventory storage location. Feeding weight uses kilograms as its unit. Reaction temperature uses degrees Celsius. Production duration uses hours.

## What constraints these characteristics create for database and operations workflows
Multi-source data access requires databases to support compatibility and mapping of heterogeneous data formats. This prevents data loss from field mismatches. The mixed update rhythm of real-time and batch operations requires databases to support both high-concurrency single-record writes and batch query capabilities. This avoids performance bottlenecks. Fields contain numerical values with different physical units. Operations workflows must configure unified unit conversion rules. This ensures consistency between stored and displayed data. Ledger data accumulates continuously with production batches. Long-term retention requirements mean operations strategies must adapt to backup and index optimization for large-volume data. This maintains query efficiency.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://username:password@host:port/dbname?authSource=admin` | Adapts to batched ledger storage needs for multi-system synchronization, and supports flexible expansion of document-type data |
| `PG_URL` | `postgresql://username:password@host:port/dbname?sslmode=require` | Used to store structured quality inspection and inventory fields, and supports complex associated queries and statistical analysis |
| `DB_MAX_LINK` | `20–30` | Adapts to the concurrent needs of chemical ledger bulk writes and frequent queries, and prevents database connection exhaustion |
| `REDIS_URL` | `redis://:password@host:port/0` | Used to cache frequently queried batch information, reducing load on core databases |

## Three Common Misconfigurations
- Symptom: After upgrading FastGPT v4.17.0, modifying the configuration file associated with `MONGODB_URI` and restarting the service results in login failure, with the interface returning a 500 status code. Cause: MongoDB authentication parameters were not configured correctly, or necessary connection string fragments were accidentally deleted during configuration modifications.
- Symptom: When importing monthly ledger data in bulk, some fields fail to display correctly, and query results do not match the number of batches from the source system. Cause: Field mapping rules were not configured for the multi-source heterogeneous format of chemical material ledgers, leading to some fields failing to be parsed and stored properly.
- Symptom: Frequent queries of batch inventory information result in database response timeouts. Cause: The `DB_MAX_LINK` parameter was not set appropriately, with the number of concurrent connections exceeding the database limit, causing new connection requests to be rejected.

## How to Verify Successful Configuration
- Perform a single production batch ledger write and query operation, to confirm data can be stored and read normally.
- Check database connection logs, to confirm current active connection counts meet business requirements.
- Trigger a monthly ledger summary task, to confirm the task completes normally without timeout errors.
- Compare imported ledger data against original source system data, to confirm field mapping and unit conversion comply with preset rules.
