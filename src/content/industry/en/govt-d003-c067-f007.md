# Fertilizer and Pesticide Ledger Summary and Report Generation: Database and Operations

## What Data for This Category Looks Like
Data sources include production feeding ledgers, pesticide and fertilizer quality inspection reports, warehouse inbound and outbound documents, and sales flow orders.
Data is updated when a production batch is completed, warehouse data is synced daily, and sales data is uploaded in real time after orders are generated.
Single records include fields such as batch number, production enterprise code, active ingredient content, production date, warehouse location, outbound quantity, and customer flow direction information.
Involved units include kilograms, tons, percentage content, date formats, and batch number identifiers.

## What Constraints These Characteristics Impose on Database and Operations Workflows
Data from multiple sources has significant format differences. Configure unified field validation and format conversion rules at the database layer. This increases the load of the data cleaning process.
Concurrent write peaks occur when production batches are submitted. Adjust connection pool parameters to handle sudden request volumes.
Batch number serves as the core unique identifier. Create indexes to improve query efficiency.
Historical ledger data grows continuously over time. Use sharded table storage to avoid single-table performance degradation.
Fields with varying units require unified conversion. Configure unit mapping rules in the database.

## How to Configure Settings

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://admin:securepass@db-host:27017/fertilizer_pest?authSource=admin` | Stores semi-structured data such as unstructured quality inspection reports and sales flow records, and specifies a dedicated business database |
| `PG_URL` | `postgresql://admin:securepass@db-host:5432/fertilizer_core?sslmode=require` | Stores structured ledger fields including batch number, quantity, date, etc., and supports complex associated queries and transaction operations |
| `DB_MAX_LINK` | `20–30 connections` | Balances concurrent write demands from batch production submissions and database connection resource usage, and avoids connection exhaustion |
| `REDIS_URL` | `redis://:securepass@cache-host:6379/0` | Caches frequently queried basic batch information and real-time inventory data to reduce query pressure on the primary database |

## Three Common Configuration Errors
- Phenomenon: After importing historical ledger data, some associated fields are empty, and preset report templates cannot be matched. Cause: No field validation was performed on the imported legacy data, and core associated identifier fields are missing, similar to issues where specified fields are missing in historical documents.
- Phenomenon: Database connection timeout errors occur when multiple batch ledger import tasks are submitted concurrently. Cause: The `DB_MAX_LINK` parameter is not set reasonably, and the connection pool cannot process new connection requests in time.
- Phenomenon: When generating summary reports via cross-database association, the number of returned results does not match the actual number of ledgers. Cause: No batch number index was created for the database corresponding to `PG_URL`, resulting in full table scans that miss some data.

## How to Verify Successful Configuration
Perform insertion and precise query operations for single structured ledger data. Confirm that database connection configurations can be established normally and return matching results.
Submit multiple batch ledger import tasks in batches. Check database connection occupancy. Confirm that the number of connections does not exceed the configured upper limit.
Generate a summary report corresponding to a single batch ledger. Confirm that the report contains all preset fields, with no empty values or missing items.
Access the shared link of the ledger report. Confirm that data can be loaded normally, with no connection timeout or error prompts.
