# Fertilizer and Pesticide Ledger Summary and Report Generation: Model Access and Configuration

## What the data for this category looks like
Ledger data for fertilizers and pesticides mainly comes from production feeding records, batch quality inspection reports, warehouse inbound and outbound documents, and sales flow archives. Production ledgers are updated daily. Quality inspection reports are generated synchronously with production batches. Warehouse and sales data are updated in real time along with business nodes. Each ledger document is grouped by batch, and includes fields such as production batch number, raw material name, active ingredient proportion, feeding weight, production time, quality inspection number, inbound and outbound quantity, and flow subject. Weight units are mostly kilograms or tons. Proportions are marked as percentages. The time format is uniformly year-month-day.

## What constraints do these characteristics impose on the "model access and configuration" link
The structured multi-field nature, specialized terminology attributes, and batch-wise update rhythm of fertilizer and pesticide ledgers bring multiple constraints to model access and configuration. First, ledgers include specialized fields with units such as active ingredient proportion and feeding weight. This requires the model to strictly match field names and units, limit generation randomness, and configure format verification. Second, multi-batch ledger summary needs to accommodate a large amount of context data, so the context length parameter must be set reasonably. Third, there are many specialized terms in the chemical industry, so a dedicated indexing model must be adapted to support non-general model access. Finally, the business chain involves multi-data source synchronization, so a failure retry and multi-model fallback mechanism must be configured to handle situations where a single model is unstable.

## How to set the configurations
This configuration guide is based on FastGPT v4.17.0.

| Configuration Item | Recommended Value Range | Rationale |
| ---- | ---- | ---- |
| `temperature` | 0.1–0.3 | Ledger summary requires strict matching of field names and units. A low temperature reduces generation randomness and avoids incorrect units or non-preset field values |
| `maxContext` | 8000–12000 token | Multi-batch ledger summary needs to accommodate context data from multiple documents. This range avoids truncating key batch-related information |
| `maxTokens` | 2000–3000 token | The output length of a single summary report meets business requirements and avoids premature truncation of generated content |
| `toolChoice` | auto | Ledger summary needs to link multiple data nodes such as batches, quality inspections, and inbound and outbound operations. Automatic tool selection improves the accuracy of data integration |
| `AIPROXY_API_ENDPOINT` | Fill in the domestic model proxy address adapted to the chemical industry | Optimize semantic understanding for fertilizer and pesticide specialized terms, and compensate for the adaptation shortcomings of general large models |
| `AIPROXY_API_TOKEN` | Fill in the valid authorization token of the corresponding proxy platform | Complete identity verification for model access and ensure normal call permissions |

## Three common mistakes
- Symptom: A 503 service unavailable error occurs when calling the model, or the generated result is empty or has incorrect formatting. Cause: The multi-model fallback mechanism is not configured, and the system cannot automatically switch to a standby model when a single model is unstable.
- Symptom: The recall accuracy of specialized terms (such as "tebuconazole", "NPK 15-15-15") is low, and retrieval results are irrelevant. Cause: A domestic indexing model adapted to the chemical industry is not configured, and a general embedding model is still used, which cannot accurately match specialized semantics.
- Symptom: The generated summary report does not output according to preset fields, with extra fields or incorrect units. Cause: The value of the `temperature` parameter is not restricted, leading to excessive generation randomness, and the fixed field and unit rules of the ledger are not enforced.

## How to confirm that the configuration is complete
- Launch a summary test for a single batch of ledgers, check whether the fields and units of the generated content match the preset ledger rules, and adjust the corresponding parameters until the requirements are met.
- Simulate a model call failure scenario, verify whether the system automatically switches to the standby model and completes the summary task without interruption.
- After connecting the domestic indexing model, retrieve ledger data related to chemical specialized terms, and check whether the relevance of the recall results meets business needs.
- Check the system logs to confirm that the configuration items related to model access have taken effect, and there are no call permission errors or address error prompts.

The values provided are common starting points and should be measured against the reader's own samples.
