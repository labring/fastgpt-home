# Agrochemical and Pesticide Ledger Consolidation and Report Generation: Deployment and Upgrade

## What this category of data looks like
Agrochemical and pesticide ledger data comes from manufacturing execution systems of production enterprises, inventory and sales management systems in circulation links, and agricultural and rural affairs departments' agricultural materials supervision reporting platforms. Data updates align with production batches, sales outbound actions, or supervision reporting cycles. A single ledger record includes fields including product common name, pesticide registration certificate number, fertilizer implementation standard, production batch number, inbound and outbound quantity, usage area, and test qualification mark. Units are mostly kilograms, tons, and batch numbers. Consolidated reports integrate category distribution, inventory turnover, and compliance check results by cycle. There is no fixed format template, and configurations must match local supervision requirements and internal enterprise ledger rules.

## What constraints do these characteristics impose during deployment and upgrade
Agrochemical and pesticide ledger data sources involve three types of heterogeneous systems: production, circulation, and supervision. During deployment, configure multi-source data synchronization rules to adapt to interface formats and permission requirements of different systems. Data updates trigger frequently with production batches and sales actions. During the upgrade phase, ensure the incremental synchronization mechanism does not interrupt core business processes, to avoid impacting ledger real-time performance. Single ledger fields are flexible and lack unified standards. During deployment, support custom field mapping and validation rules to prevent format errors during data import. Compliance requirements are strict. Data storage must match information security specifications for the agricultural sector. During upgrade, synchronize updates to storage encryption configurations to ensure sensitive data meets supervision requirements.

## How to set configurations
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://username:password@host:port/fastgpt?authSource=admin` | Stores raw ledger data and batch-generated report files, adapts to unstructured data storage needs |
| `PG_URL` | `postgresql://user:pass@host:5432/fastgpt` | Stores field mapping rules, user-defined configurations, and sync task logs, supports complex queries and transaction operations |
| `REDIS_URL` | `redis://:password@host:6379/0` | Caches frequently accessed ledger data and sync task status, reduces concurrent load on databases |
| `DB_MAX_LINK` | `20–30 connections` | Adapts to concurrent access volume of ledger data, prevents connection pool exhaustion from interrupting sync tasks |
| `STORAGE_S3_ENDPOINT` | Enterprise self-built object storage address or cloud service provider standard endpoint | Stores batch-generated report attachments and large-volume ledger files, supports cross-node file access |
| `ROOT_KEY` | Randomly generated 32-character string | Configures system administrator access key, ensures only authorized users can modify ledger sync and knowledge base import rules |

## Three common mistakes
- Frontend page loads indefinitely with no response: Accessing the configured `FE_DOMAIN` shows no interface, and the browser console reports cross-origin resource sharing errors. The cause is that `FE_DOMAIN` is not correctly matched with the backend service domain name, resulting in frontend resource loading being blocked.
- Incremental sync task times out and interrupts: Ledger data updates do not automatically sync to the knowledge base, and system logs show database connection timeout errors. The cause is that `DB_MAX_LINK` value is too low, and concurrent connection count is exhausted, preventing sync tasks from executing normally.
- Knowledge base import only shows fixed number of entries: After importing bulk ledger data, only 30 entries are displayed, and full content cannot be viewed. The cause is that the system backend was not logged into using `ROOT_KEY` to modify the default import limit configuration, or system permissions were not correctly configured.

## How to confirm configurations are correct
- Execute database connection test scripts to verify that `MONGODB_URI`, `PG_URL`, and `REDIS_URL` can establish normal connections, confirm current connection count does not exceed the range set by `DB_MAX_LINK`.
- Upload a single agrochemical and pesticide ledger data entry, trigger a manual sync task, check if corresponding data backup files are generated in object storage, verify that `STORAGE_S3_ENDPOINT` configuration is effective.
- Access the configured `FE_DOMAIN`, confirm the frontend interface loads normally with no cross-origin or resource loading failure prompts, verify that `FE_DOMAIN` configuration is correct.
- Log in to the system backend using `ROOT_KEY`, view the document import limit configuration item, confirm that import quantity can be adjusted according to business needs, verify that permission configurations are effective.
