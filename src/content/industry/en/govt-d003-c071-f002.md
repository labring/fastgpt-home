# Ledger Summary and Report Generation for Power Generation Groups: Vector Models and Indexes

## What this category of data looks like
Power generation group ledger data comes from four main sources: production operation systems, equipment maintenance work orders, fuel consumption reports, and environmental monitoring ledgers.
The update process follows a fixed cadence: real-time operation records for individual equipment are updated per shift, team-level aggregated data is updated daily, and monthly operation reports are generated each month.

Individual documents include fields such as unique equipment identifiers, timestamps, operation parameter values, maintenance operation records, and exception codes. Common units include megawatts, tons, degrees Celsius, and operating hours. Document length varies widely: single operation records are several hundred characters long, while monthly summary reports can reach tens of thousands of characters.

## What constraints these characteristics impose on vector models and indexes
High-frequency ledger updates require indexes to support incremental updates, avoiding time and resource waste from full index reconstruction.
Structured data with multiple fields and units needs vector models to encode both text content and metadata semantics. Retrieval processes must support filtering by metadata such as equipment ID and timestamp.
Wide variation in document length requires a chunking strategy that adapts to both short records and long reports.
Compliance rules demand accurate retrieval results, preventing non-target device ledger data from compromising summary quality.

## How to set the configurations
| Configuration Item | Recommended Value Range | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Adapts to the average length of individual power generation ledger records, avoiding including too many unrelated fields in a single chunk |
| Overlap Length | 100–150 characters | Preserves key parameter associations across chunks, such as continuous time period data for equipment operation |
| Similarity Threshold | 0.72–0.85 | Filters low-match irrelevant ledgers, avoiding mixing data from non-target devices during summary |
| Single Search Limit | Top 20 entries | Covers the retrieval needs of single-batch ledgers while controlling retrieval time |
| `defaultToken` | 8192 | Adapts to the context length of monthly summary reports, matching the default limit of FastGPT v4.17.0 |
| `maxToken` | 16384 | Supports vector retrieval and context concatenation for large annual reports |

## Three common configuration mistakes
- A 503 Service Unavailable error occurs during retrieval. Metadata filtering is not enabled, so the retrieval scope covers all historical ledgers, exceeding the vector database's concurrency processing limit.
- A token limit exceeded error triggers during vector data import. The chunk length is not adjusted for power generation ledger document lengths, so a single chunk exceeds the token limit supported by the model.
- Key exception data in summary reports is not retrieved. The similarity threshold is set too high, filtering eligible low-match exception ledger records.

## How to confirm the configuration is correct
- Import 3 days of operation ledgers for a single device, perform retrieval filtered by device ID and time range, and check that returned device identifiers exactly match the retrieval conditions.
- View the vector database connection logs to confirm there are no frequent timeout or disconnection errors, verifying that configured connection parameters are effective.
- Import a monthly summary report, check that no context truncation prompt from FastGPT v4.17.0 is triggered, verifying that the `defaultToken` and `maxToken` configurations are reasonable.
- Manually count the total number of imported ledgers, compare it with the total number of results returned by retrieval, confirming that the single search limit configuration covers conventional retrieval needs.
