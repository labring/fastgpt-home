# Ledger Summary and Report Generation for Power Generation Groups: Database and Operations Maintenance

## What this category's data looks like
Power generation group ledger data mainly comes from power plant SCADA monitoring systems, equipment inspection logs, fuel procurement and warehousing records, and compliance filing documents. Data update frequencies fall into three categories: equipment operating parameters refresh every 15 seconds, daily inspection ledgers are archived daily, and monthly financial and compliance ledgers are updated collectively at the end of each month. A single ledger document includes fields such as unique equipment identifier, operating parameter value, inspection personnel number, maintenance operation record, and associated report number. Parameters including active power and fuel consumption use MW and tons as units respectively.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://energy_user:secure_pass@node1:27017,node2:27017,node3:27017/admin?replicaSet=energy_rs` | Adapts to the storage needs of multi-source heterogeneous ledgers for power generation groups, supports replica set deployment to ensure high availability |
| `PG_URL` | `postgresql://compliance_user:encrypt_pass@pg-server:5432/energy_report?sslmode=require` | Used to store structured compliance ledgers and monthly report metadata, SSL encryption ensures sensitive data security |
| `DB_MAX_LINK` | `80–120` | Matches concurrent write requests from real-time operating data, avoids service interruptions caused by exhausted connections |
| `REDIS_URL` | `redis://cache_auth@redis-cluster:6379/0` | Used to cache device ledger snapshots for high-frequency queries, reducing direct database query pressure |

## Three common configuration mistakes
- A `MongoDB connection authentication failed` error occurs during deployment. The cause is that the generic `username` is incorrectly used as the MongoDB connection username, without replacing it with the dedicated account configured for the actual cluster.
- Mixing pgvector and Milvus dependencies in the Compose file deployment configuration causes dependency conflicts during container startup, preventing the container from starting. The cause is failing to split deployment configurations for different databases based on data storage scenarios.
- Query disconnection occurs when the primary node drifts after MongoDB replica set deployment. The cause is failing to configure the replica set parameter in `MONGODB_URI`, causing the client to fail to automatically reconnect to the new primary node.

## How to confirm the configuration is properly set
- Execute a database connection test script to verify that the clusters corresponding to `MONGODB_URI` and `PG_URL` can establish normal connections and perform read and write operations.
- Submit simulated power generation equipment ledger data, and confirm that the written data’s field formats and units match the preset rules.
- Check the database monitoring panel to confirm that the current number of connections does not exceed the `DB_MAX_LINK` configuration limit.
- Simulate a primary node drift scenario to verify that the MongoDB client can automatically switch to the new primary node and restore data querying.

The values provided are common starting points and should be measured against the reader's own samples.
