# Ledger Summary and Report Generation for Power Generation Groups: Model Access and Configuration

## What this type of data looks like
Ledger data for power generation groups mainly comes from the production operation systems, fuel management systems, and safety supervision platforms of affiliated power plants. Data is updated per production shift or natural day. Each individual ledger document includes fields such as power plant code, device serial number, daily operation parameters, fuel consumption records, and maintenance completion status. Operation parameters use megawatts and grams per kilowatt-hour as units, while fuel consumption uses tons as a unit. Documents are usually summarized monthly into single ledger packages, each containing dozens to hundreds of detailed entries.

## What constraints these characteristics impose on model access and configuration
Power generation group ledger data has many entries, with fields containing multiple types of professional power units, and monthly summary packages have large volume. This requires model access to adapt to long context processing. Data updates on fixed production cycles, so model calls must match the rhythm to avoid redundant requests. There are minor differences in ledger fields across different power plants, so the model must support identifying non-standard field mappings. At the same time, token usage per single request must be limited to avoid call failures caused by long documents exceeding model limits. Unified recognition of professional units requires the model to have domain term adaptation capabilities, and corresponding model adaptation rules must be clearly defined in the configuration.

## How to set the configuration
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | Adapts to the total character count of monthly ledger packages, avoiding exceeding the model's context window |
| `maxTokens` | `2000–3000 token` | Limits the output length of a single round of report generation, matching the output requirements of ledger summaries |
| `temperature` | `0.1–0.3` | Reduces generation randomness to ensure the accuracy of professional data output |
| `AIPROXY_API_ENDPOINT` | Fill in the official access address of the selected model | Matches the standard request path for model calls |
| `AIPROXY_API_TOKEN` | Fill in the exclusive key obtained from the model service provider | Completes identity verification for model calls |
| `quoteMaxToken` | `1500–2000 token` | Limits the total token count of recalled reference documents, avoiding context overload |

## Three common mistakes
- Phenomenon: A 500 error is returned when calling after adding a custom model in FastGPT v4.17.0. Cause: `AIPROXY_API_ENDPOINT` or `AIPROXY_API_TOKEN` is not configured correctly, leading to model identity verification failure or incorrect request path.
- Phenomenon: A 429 status code is returned when concurrent calls exceed 5. Cause: No concurrency limit is configured in the FastGPT application, and direct calls to the cloud service provider's interface trigger the official concurrency limit.
- Phenomenon: Incorrect mapping of professional units occurs when generating reports by importing ledger data. Cause: No adaptation is made to the professional power fields of the ledger, so the model cannot correctly recognize the business meaning of units such as megawatts and grams per kilowatt-hour.

## How to confirm the configuration is complete
- Initiate a call request for a single ledger parameter on the model testing page of FastGPT v4.17.0, and confirm that no error is returned.
- Import a small monthly ledger sample, trigger the report generation process, and check whether the output contains correct professional units and field mappings.
- Simulate multiple concurrent requests to verify that the configured concurrency limit takes effect, avoiding triggering 429 exceptions.
- Adjust the `temperature` parameter to 0.2, generate two reports using the same sample, and confirm that the output content has minimal differences, meeting the accuracy requirements for professional data.

The values provided are common starting points and should be measured against the reader's own samples.
