# Ledger Aggregation and Report Generation for Power Generation Groups: Deployment and Upgrade

## What the Data for This Category Looks Like
Ledger data for power generation groups comes from internal business systems including production operation systems, fuel management systems, and safety and environmental protection supervision systems. Updates occur once per shift or once per day. Each individual ledger document uses a structured table format, with fixed fields including unit number, operating hours, fuel consumption, maintenance times, and environmental emission values. The units for these fields are number, hour, ton, time, and milligram/cubic meter respectively. Multi-source data must be aggregated to generate reports. A single periodic report can cover all ledger information for multiple units. Document size varies with the number of units and the length of the reporting period, with no fixed upper limit.

## What Constraints These Characteristics Impose on Deployment and Upgrade
Multi-source and heterogeneous ledger data sources require multiple data source connections to be configured during deployment. During upgrades, existing data source mapping rules must be retained to avoid interrupting data aggregation processes. Frequently updated ledger data requires scheduled task intervals to match actual update rhythms. Core scheduling parameters must not be adjusted arbitrarily during upgrades. Structured fixed fields require the database schema to align strictly with ledger fields. Custom extended fields must be compatible during upgrades. Large-volume report documents require large-capacity storage services to be configured. During upgrades, storage service connectivity and read-write permissions must be verified. Data security compliance requirements for state-owned enterprises and public institutions require encryption parameters to be configured. During upgrades, encryption rules for sensitive data must be retained.

## How to Set the Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–150 connections` | There are many concurrent tasks for power generation group ledger aggregation. This value prevents concurrent connections from exhausting database resources |
| `PG_URL` | `jdbc:postgresql://power-plant-db:5432/fastgpt?currentSchema=energy_ledger` | Matches the deployment address and dedicated ledger schema of the internal PostgreSQL database for power generation groups |
| `REDIS_URL` | `redis://:redispass@internal-redis:6379/1` | Used to cache incremental ledger update data, isolating resource usage between the business database and cache service |
| `STORAGE_S3_ENDPOINT` | `http://s3.energy-group.com:9000` | Points to the internal object storage service of the power generation group, used to store large-volume ledger report files |
| `ROOT_KEY` | `32-character random string generated by the enterprise key management system` | Used to encrypt sensitive information in ledger configurations, complying with data security compliance requirements for state-owned enterprises and public institutions |

## Three Common Mistakes
- Phenomenon: When performing a private deployment upgrade of FastGPT v4.17.0, the configuration value of `DB_MAX_LINK` was modified incorrectly because the official upgrade guide could not be found. Subsequent ledger aggregation tasks encountered database connection timeouts. Cause: General deployment parameters were adjusted to values that do not match concurrent requirements without referring to exclusive configuration rules for power generation groups.
- Phenomenon: All historical ledger conversation logs and aggregation records were lost after the Docker container restarted. Cause: Persistent mounting of `REDIS_URL` was not configured, causing cached incremental data to be lost when the container was destroyed, and persistent storage for `MONGODB_URI` was not enabled.
- Phenomenon: Batch-imported ledger files could not be parsed normally, with a prompt that the file size exceeded the limit. Cause: The large file upload policy for `STORAGE_S3_ENDPOINT` was not configured, and the valid duration of `FILE_TOKEN_KEY` was not adjusted to adapt to large file transfers.

## How to Confirm the Configuration Is Correct
- Run the `docker ps -a` command, confirm that all FastGPT container statuses are Up, with no abnormal exits or restart records.
- Access the configured `FE_DOMAIN` address, enter the ledger aggregation management page, enter a test unit number, and query the ledger data for the corresponding period.
- Call the internal test interface to verify that the connections for `PG_URL` and `REDIS_URL` are normal, with no timeout or connection refused errors.
- Upload a 10MB test ledger file, confirm that the file is successfully stored in the storage service corresponding to `STORAGE_S3_ENDPOINT`, with no upload failure prompts.
