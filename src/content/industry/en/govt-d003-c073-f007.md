# Ledger Aggregation and Report Generation for State-owned Industrial Funds: Database and Operations

## What the data for this category looks like
State-owned industrial fund ledger data is sourced from fund fundraising filing systems, investment decision approval platforms, post-investment management modules, and state-owned asset supervision reporting ports. Two update schedules apply to this data:
- Incremental daily updates for post-investment capital flow and project progress data
- Trigger-based updates for event data such as fundraising and exit

Each ledger document includes fund subject code, investor details, investment project list, capital flow details, and supervision rating fields. Units follow standard formats required by state-owned asset supervision, including ten thousand yuan, quarter, and year.

## What constraints these characteristics impose on database and operations workflows
Multi-source data access creates a need for parallel connections, so database operation configurations must support simultaneous connections by multiple instances. Data with different update schedules requires separate incremental and full synchronization strategies to prevent full synchronization from consuming excessive system resources. Mandatory fields and fixed formats required by state-owned asset supervision mean the database schema must have strict verification capabilities to avoid missing fields or format errors. Mixed storage of semi-structured project documents and structured financial data requires the database to support both flexible expansion and strong transaction consistency, which increases operational complexity.

## Three common configuration mistakes
- Symptom: After deploying via Docker, modifying the database password without updating the associated environment variables results in `ECONNREFUSED` or authentication failure errors after restarting the container. Cause: The new password was not synchronized to the corresponding database connection configuration, and the container loads the old configuration, leading to connection failure.
- Symptom: Attempting to use an indigenous innovation database to replace MongoDB results in inability to read semi-structured project document data. Cause: The database storage schema was not adjusted to adapt to the field constraints of the indigenous innovation database, and the original semi-structured data format is incompatible.
- Symptom: After enabling the hybrid retrieval problem optimization and result rearrangement functions, a single ledger generation task times out, taking more than 30 seconds, and concurrent calls appear in the tool selection workflow. Cause: No distributed lock or task deduplication mechanism was configured, the database connection pool maximum size was not adjusted, and high-frequency queries did not hit the Redis cache, leading to excessive load on the core database.

## How to verify correct configuration
- Run the FastGPT built-in database connection test tool to verify that the databases corresponding to `MONGODB_URI` and `PG_URL` can establish normal connections, with no authentication or network errors.
- Check the Redis cache monitoring panel to confirm that supervision indicator data for high-frequency queries has been cached, and the cache hit rate reaches the preset threshold.
- Trigger a full ledger synchronization task, and confirm that the newly added ledger data in the database matches the source system data, with no missing fields or format errors.
- Check the workflow execution logs to confirm that the tool selection task was only triggered once, with no duplicate execution records.
