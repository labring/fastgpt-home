# Ledger Summary and Report Generation for State-owned Capital Investment Companies: Database and Operations
This document is written based on FastGPT v4.17.0.

## What this type of data looks like
Ledger data for state-owned capital investment companies originates primarily from state-owned assets supervision platforms, internal group investment management systems, and regularly submitted reports from wholly owned and holding subsidiaries.
Data update cycles fall into two categories: regular monthly or quarterly summaries, and temporary special ledger updates.
Each individual ledger document uses a structured table format, including fields such as main entity name, investment amount (unit: ten thousand yuan), shareholding ratio (unit: percentage), project progress (unit: days), and compliance status.
It also includes scanned documents with subsidiary seals as unstructured attachments.

## What constraints do these characteristics impose on the database and operations link
Multi-source data access requires support for cross-system synchronization, and connection parameters compatible with different database types must be configured.
The coexistence of regular and temporary update cycles requires the database to support batch writing and incremental updates, to avoid excessive resource consumption from full synchronization.
Fixed units for structured fields require the data validation process to match preset formats, preventing non-standard reported data from breaking summary logic.
The sensitivity of state-owned assets data requires permission isolation and encrypted storage strategies in the operations link, to ensure data security.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `MONGODB_URI` | Configure a dedicated replica set connection string that includes read-write split addresses | Ledgers contain structured data and unstructured attachments; replica sets ensure read-write performance and high availability |
| `PG_URL` | Configure the read-only access address of the group's financial synchronization database | Core structured ledger data requires strong consistency; read-only addresses avoid impacting business system operations |
| `DB_MAX_LINK` | `20–30` | Matches concurrent connection demand during peak reporting from subsidiary companies, with reasonable redundancy reserved to avoid connection exhaustion |
| `REDIS_URL` | Configure a local cache instance, set the key expiration time to `86400 seconds` | Temporary ledger cache update frequency is daily; expired old data is automatically cleaned up to free resources |

## Three common misconfigurations
- Batch summary of ledgers results in `ETIMEDOUT` error with status code 504. No reasonable value is configured for `DB_MAX_LINK`, and concurrent connections exceed the database upper limit, causing timeout.
- Null values or format errors appear in the shareholding ratio field of ledger data. No format validation is configured for synchronized data, and non-standard ratio formats reported by subsidiary companies are not parsed correctly.
- Historical ledger query response is slow, and cache is not effective. No caching mechanism is configured via `REDIS_URL`, and each query directly reads full database data.

## How to confirm the configuration is correct
- Log in to the database configuration page in the FastGPT backend, verify that the connection status of `MONGODB_URI` and `PG_URL` shows normal.
- Simulate concurrent requests at peak business volume, confirm that the database connection count does not exceed the configured upper limit of `DB_MAX_LINK`.
- Manually trigger a temporary ledger update, check that the expiration time of cached data meets the preset configuration requirements.
- View system operation logs, confirm that there are no error records of database connection exceptions or timeouts.
