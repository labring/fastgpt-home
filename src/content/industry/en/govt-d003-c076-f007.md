# Ledger Summary and Report Generation for State-owned Capital Operation Companies: Database and Operations

## What the Data for This Category Looks Like
Ledger data for state-owned capital operation companies mainly comes from the operating reporting systems, property right registration platforms, and major investment and financing filing modules of subordinate enterprises at all levels. Data updates are divided into two categories: monthly batch synchronization and real-time change push. Each individual ledger document includes fields such as main body identification code, affiliated group hierarchy, current period operating indicator value, statistical cycle, and filing associated number. Indicator units use standardized measurement methods such as ten thousand yuan, person-times, and natural days. Summary ledgers contain multiple detailed entries, and are ultimately used to generate group-level business analysis reports.

## What Constraints Do These Characteristics Impose on the Database and Operations Link
Decentralized data sources and mixed update modes require the database to support both high-concurrency real-time writes and batch read operations, to prevent single workloads from occupying resources. Fields include hierarchical subject information and standardized measurement indicators. A joint index must be created for the main body identification code and statistical cycle fields to reduce full table scan overhead. Monthly batch updates have high peak traffic, so the connection pool capacity must be adapted to concurrent requests to avoid connection exhaustion. Ledger data is strongly linked to final reports, so transaction consistency of data writes must be ensured to prevent report distortion caused by dirty data.

## Configuration Settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://[username]:[password]@host:port/[capital_db]?authSource=admin&replicaSet=rs0` | State-owned capital operation company ledger data requires multi-node redundancy to ensure availability. The replicaSet configuration adapts to mixed workloads of batch writes and real-time queries |
| `PG_URL` | `postgresql://[user]:[pass]@host:port/[report_db]?sslmode=require` | Associated queries for report generation require structured transaction support. sslmode=require ensures security of cross-node data transmission |
| `DB_MAX_LINK` | `200–300` | The number of concurrent connections from subordinate enterprises is high during monthly batch reporting. This range adapts to mixed read-write workloads and avoids database connection exhaustion |
| `REDIS_URL` | `redis://:[password]@host:6379/0?maxmemory-policy=allkeys-lru` | Cache ledger batch indexes and temporary calculation results. The allkeys-lru policy adapts to high-frequency pre-queries for report generation |

## Three Common Misconfigurations
- Phenomenon: Unable to log in to the system after version upgrade, and the interface returns a database connection failure error. Cause: Authentication parameters in `MONGODB_URI` were not updated synchronously when modifying the MongoDB configuration file, or container network policy changes after restart prevented connection establishment.
- Phenomenon: Some entry fields are empty when importing ledger data in batches, and complete reports cannot be generated. Cause: The database transaction rollback mechanism was not enabled. After batch write interruption, uncommitted partial data was not recovered, resulting in dirty data residue.
- Phenomenon: System response is slow when reporting ledgers concurrently, and timeout errors are returned directly after exceeding the threshold. Cause: The `DB_MAX_LINK` configuration value is too low, the database connection pool is exhausted, and new requests cannot obtain available connections.

## How to Verify Correct Configuration
- Execute the database connection test script to verify the connectivity of `MONGODB_URI` and `PG_URL`, and confirm there are no authentication or network errors.
- Simulate monthly batch import of multiple sets of ledger data, check the write success rate and time consumption, and confirm that the `DB_MAX_LINK` configuration adapts to concurrent workloads.
- View the Redis cache monitoring panel, confirm that the cache node corresponding to `REDIS_URL` is running normally, and there are no memory overflow or connection abnormality alerts.
- Trigger a complete ledger summary report generation process, check the consistency of associated data and the integrity of the final report.

The values provided are common starting points and should be measured against the reader's own samples.
