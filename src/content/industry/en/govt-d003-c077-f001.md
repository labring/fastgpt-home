# City Public Transit Ledger Aggregation and Report Generation: HTTP Interfaces and External Systems

## What This Category of Data Looks Like
Bus transit ledger data mainly comes from three types of data sources: in-vehicle smart terminals, scheduling management systems, and ticket settlement systems. Data update frequencies vary by business scenario: real-time passenger flow and location data are updated every second. Daily ledger data is generated after the day’s operations end. Weekly and monthly summary data is synchronized on fixed schedules.
A single ledger document includes fields such as route number, shift ID, departure time, arrival time, actual passenger count, revenue amount, and travel duration. Their respective units are: route number (no unit), shift ID (no unit), hours:minutes, hours:minutes, passenger trips, yuan, and minutes.

## What Constraints These Characteristics Impose on HTTP Interfaces and External Systems
The multi-data source access feature requires HTTP interfaces to support multiple endpoints for data pulling, to avoid overload on single requests. The daily, weekly, and monthly update cycles require interfaces to support scheduled triggering and batch pulling, to fit the cycle requirements of ledger aggregation. The large number of fields including sensitive information requires strict identity verification mechanisms for interfaces, and filtering non-essential fields in returned data to reduce transmission costs. The format requirements for numeric fields such as actual passenger count and revenue amount need clear mapping rules in interface configuration, to avoid data parsing errors.

## Configuration Settings

| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer {server-generated exclusive secret} | Bus ledger data involves public service information, so identity verification via request headers is required to prevent unauthorized access |
| `variables` | Map route number, shift time period, passenger capacity fields | Match the standard data structure of bus ledgers, enable variable replacement and data splicing to fit template requirements for report generation |
| `responseData` | Return aggregated data by shift | Adapt to the batch data requirements of ledger aggregation, simplify the field extraction process for subsequent report generation |
| Interface timeout period | 600 seconds | Handle the processing duration of batch ledger requests for multiple routes, avoid interrupting the aggregation process due to timeout |
| Callback trigger condition | Trigger at 24:00 daily | Match the business rhythm of bus operations generating daily ledgers, ensure the integrity of aggregated data |

## Three Common Misconfigurations
- Symptom: When debugging a workflow, text splicing variables return normally, but the variable parts are not returned when calling via API. Cause: The field mapping for the `variables` parameter is not configured correctly, and the API request does not carry valid values for the corresponding variables.
- Symptom: The API call returns `responseData` containing a read link, but the front end prompts "Only support .txt, .m" when accessing the link. Cause: The returned link points to a non-text file, and non-permitted format resources are not filtered in the interface configuration.
- Symptom: The preset synchronization callback is not triggered after ledger aggregation is completed. Cause: The trigger time node and target interface address for the callback are not set correctly, or the callback interface does not have public network access permissions.

## How to Verify a Correct Configuration
- Send a test request with a valid `Authorization` header, check that the returned status code is 200 and there are no identity verification failure prompts.
- View the field list returned in `responseData`, confirm that the preset core bus ledger fields are included and there is no redundant data.
- Trigger debug mode, verify that the fields mapped by the `variables` parameter are correctly replaced in the spliced text, with no null values or incorrect content.
- Wait for the preset trigger time, check whether the external system has received the callback notification of completed ledger aggregation.
