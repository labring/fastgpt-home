# Public Transit Bus Ledger Summary and Report Generation: Tool Calling and Plugins

## What Data for This Category Looks Like
Data for public transit bus ledgers comes from onboard smart terminals, scheduling management systems, and ticket settlement systems. Update frequencies fall into three categories: real-time (per-shift operation data), daily (same-day summary data), and monthly (monthly ledger reports).

Single operation data includes fields such as shift number, vehicle identification code, departure time, arrival time, passenger trips, and actual revenue amount. Units are: none, none, ISO 8601 formatted time, ISO 8601 formatted time, trips, and Chinese yuan.

Bulk operation data is often stored in CSV format. Monthly summary ledgers are often stored in PDF format. Single batch data volume can reach tens of thousands of entries.

## How These Characteristics Create Constraints for Tool Calling and Plugins
The fields of public transit bus ledgers are fixed and numerous. Tool calling must accurately match specified fields such as shift number and passenger volume. Otherwise, summary results will deviate.

Real-time operation data has a high update frequency. This requires tool calling to support low-latency triggering.

Large-volume files from monthly bulk ledgers require plugins to have large file parsing capabilities.

A single batch of tens of thousands of entries increases tool calling time. Batch processing sharding logic must be adapted to avoid single-call timeouts.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapts to automatic function matching for multiple types of transit ledger data, no need to manually specify call targets |
| Function call retry count | 3 times | Addresses scenarios where single data parsing fails or field matching is abnormal |
| Single batch data processing count | 500 entries per call | Matches the single batch data volume of transit ledgers, balances processing efficiency and call stability |
| `functionCall` | Enable mandatory validation | Ensures call parameters strictly match the fixed fields of transit ledgers, avoids format errors |
| Timeout threshold | 600 seconds | Adapts to parsing and summary time for large monthly ledgers, supported in FastGPT v4.17.0 |

## Three Common Mistakes
- Symptom: The interface shows successful tool calling, but no corresponding call record appears in system logs.
  Cause: The FastGPT tool call log collection switch is not enabled, so call information is not saved.
- Symptom: Uploaded bus operation CSV files display garbled text.
  Cause: UTF-8 encoding format is not specified during upload, leading to parsing abnormalities for Chinese shift numbers, station names, and other content.
- Symptom: Errors occur when using doc2x to parse PDF monthly bus ledgers with more than 300 pages.
  Cause: The doc2x plugin’s maximum single-parsing page count does not adapt to large ledgers, or the file volume exceeds 1000 MB.

## How to Confirm Proper Configuration
- Upload a single test bus operation data entry, trigger tool calling, and check if returned function call parameters match ledger fields such as shift number and passenger volume.
- View system tool call logs to confirm corresponding call entries are generated, and that parameter configurations match preset values.
- Run a test task with 500 entries, confirm there are no timeout, garbled text, or parsing failure errors.
- Adjust the `toolChoice` parameter to `none`, verify that tool calling only executes preset functions and does not trigger automatic matching logic.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
