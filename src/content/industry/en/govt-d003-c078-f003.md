# Water Utility Ledger Summary and Report Generation: Multi-turn Dialogue and Prompt Engineering

## What the data for this use case looks like
Water utility ledger data primarily comes from water plant operation logs, pipeline inspection terminals, wastewater plant water quality monitoring systems, and municipal drainage operation and maintenance platforms. Data update cadence includes real-time uploads after individual inspections and scheduled synchronization of daily summary reports. Individual ledger documents are stored in a structured format by operation site and time dimension, with fields including water supply pressure (unit: MPa), water turbidity (unit: NTU), average daily treatment volume (unit: m³/d), number of completed inspection items, and equipment operating duration (unit: hours). Document length ranges from tens of characters for a single inspection record to thousands of characters for monthly summary reports.

## Constraints imposed by these characteristics on multi-turn dialogue and prompt engineering
The decentralized sources and format differences of water utility ledger data require that multi-turn dialogue first complete unified mapping of cross-system fields to avoid confusion between indicator definitions from different operation sites. The varying update cadences of different data sets require that time filtering ranges be clearly specified in multi-turn dialogue, and prompts must preset guiding logic for time dimensions. The wide range of document lengths requires that the `messages` context window adapt to input lengths spanning from single inspection records to monthly summary reports. The presence of dedicated fields and units requires that prompts include built-in unit verification rules to avoid confusion between pressure and flow units in water utility scenarios.

| `variables` preset variables | Site name, time range, indicator type | Matches the core filtering dimensions of water utility ledgers, simplifies parameter passing during multi-turn interactions |
| `chatId` association rule | Bound by operation site | Ensures coherent context across multi-turn dialogue for the same site, avoids confusion between cross-site data |
| Number of results returned per single conversation | Top 3 | Focuses on core indicator data, avoids excessive information disrupting dialogue logic |

## Three Common Misconfigurations
- Calling the multi-turn dialogue interface without a logged-in status results in failed loading of conversation history images. Cause: Public access permissions for conversation history are not configured, only logged-in users can access associated resources.
- Nesting a configured ledger analysis application within a workflow causes the nested workflow to fail to record conversation logs. Cause: Log synchronization configuration for `chatId` is not enabled during nested calls, resulting in unassociated recording of conversation context.
- A form input node can hide dialog boxes normally in an independent workflow, but the dialog box still displays when nested into another workflow. Cause: Pop-up trigger rules are not reset in the nested configuration, so the original node’s display logic is not overwritten.

## How to Verify Proper Configuration
- Initiate a query covering multiple sites and time ranges, check that conversation context is coherent, confirm that the `chatId` binding rule is active.
- Enter a query containing water utility-specific units, check that the prompt correctly identifies and matches the corresponding fields, confirm that the `variables` preset logic is active.
- Switch to an unlogged-in status to initiate a query, check that conversation history resources can be accessed normally, confirm that public access permission configuration is correct.
- Nest a ledger analysis application, check that conversation context is synchronously recorded in workflow logs, confirm that `chatId` log synchronization configuration is enabled.
