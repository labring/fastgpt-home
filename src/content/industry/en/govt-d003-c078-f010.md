# Urban Water Utility Ledger Summarization and Report Generation: Knowledge Base Retrieval and Recall

## What This Category’s Data Looks Like
Data sources for urban water utility ledgers cover multiple business systems including pipeline monitoring systems, water plant operation logs, user payment records, and inspection and maintenance archives. Update frequencies fall into three categories: real-time (online monitoring data such as pipeline pressure and flow), daily (daily inspection records, water quality test data), and monthly (monthly operation summary reports). Most documents are structured tables, with fields including pipeline ID, monitoring time, pressure value (unit MPa), flow (unit m³/h), inspection personnel, and rectification status. They also include long-text inspection reports, user appeal records, and linked attached resources such as pipeline node photos and water quality test photos.

## Constraints for Knowledge Base Retrieval and Recall
Multi-source, multi-update-frequency data requires the knowledge base to support incremental updates and permission-based hierarchical management, to avoid performance loss from full retrieval. The coexistence of long-text ledgers and structured fields requires retrieval to balance semantic matching and precise keyword matching, to avoid missing key structured data. Attachments with image links require the retrieval pipeline to support OCR text extraction, converting image content into retrievable semantic features. Without this functionality, operational information related to images cannot be associated. Additionally, the business requirement for ledger summarization and report generation requires recall results to be aggregated by time and region, to avoid scattered, unstructured results.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Water utility ledgers mix structured fields and long text. This range balances semantic matching accuracy and recall coverage, avoids introducing irrelevant inspection records or missing key pipeline data, and is compatible with FastGPT v4.17.0’s semantic matching logic |
| `limit` | Top 10–15 entries | Ledger summarization requires covering multi-dimensional associated data. This value controls the context window size while retaining sufficient associated information for report generation |
| `searchMode` | Semantic + keyword hybrid retrieval | Adapts to the characteristics of water utility ledgers that combine structured and unstructured content, matching both keyword fields and semantically related content |
| `usingReRank` | Enabled | Re-ranks initial recall results to filter low-relevance entries, improves content accuracy of final generated reports, and is compatible with FastGPT v4.17.0’s re-ranking module |
| `datasetSearchUsingExtensionQuery` | Enabled | Automatically expands query terms to add water industry-specific terminology such as "pipeline leakage", "free chlorine value", improving retrieval recall rate for long-text ledgers |
| `collectionIds` | Bind dedicated water utility ledger dataset ID | Restricts retrieval scope to only water operation-related documents, avoiding interference from irrelevant data during summarization and report generation |

## Three Common Misconfigurations
- Phenomenon: Scattered recall results after retrieving a 10,000-row long-text inspection ledger, with disjointed semantics in individual results. Cause: Chunking strategies were not adjusted according to water utility ledger segmentation rules, leading to incorrect splitting of long paragraphs and destroyed semantic integrity.
- Phenomenon: Citation prompts are forcibly displayed at the end of question-and-answer replies, and an error "No permission to operate this conversation record" appears. Cause: The knowledge base citation display configuration was not disabled, and the conversation role was not granted access permissions for the corresponding dataset, resulting in permission verification failure.
- Phenomenon: Retrieval response takes too long, or no answer can be generated based on image links during question-and-answer testing. Cause: The former occurs when the recall limit is set too high and `usingReRank` optimization is not enabled, allowing a large amount of irrelevant data to enter the context window. The latter occurs when no image OCR parsing task is configured, and only image links are uploaded without extracting text features, making it impossible to associate operational information related to the images.

## How to Verify Proper Configuration
- Import a single water utility inspection ledger of approximately 10,000 characters, run a retrieval, and check the semantic coherence of recall results to confirm that chunking configurations adapt to long-text structures.
- Enable question-and-answer testing, view citation markers at the end of replies, confirm that citation display can be turned off via interface switches, and test with a role without permissions to confirm that error prompts align with configuration requirements.
- Run batch retrieval testing, count response times, confirm that no obvious timeouts occur, and check that the number of recall results matches the preset `limit` value.
- Upload an image link with OCR-extracted text, run associated retrieval, and confirm that the question-and-answer function can generate corresponding replies based on content extracted from the image.

The values provided here are common starting points and should be measured against the reader’s own samples.
