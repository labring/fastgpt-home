# Urban Water Utilities Ledger Aggregation and Report Generation: Deployment and Upgrade

## What the data for this use case looks like
Ledger data for urban water utilities comes from pipeline pressure monitoring nodes, water plant central control systems, drainage pump station collection equipment, and manual inspection records. Data update frequencies are divided into three categories: real-time (core monitoring points), hourly (regular inspection data), and daily (summary reports). A single device ledger document includes fields for monitoring point code, collection timestamp, water pressure value, flow value, turbidity value, and device operating status, with units of MPa, m³/h, NTU, and start/stop status identifiers respectively. Monthly aggregated ledgers are grouped by region and device type, integrating daily data to generate statistical entries.

## What constraints these characteristics impose during deployment and upgrade
The multi-source real-time access and high-frequency updates of urban water utility ledger data require reserving sufficient database connection resources during the deployment phase to avoid concurrent write timeouts. Data sources with different update frequencies need matching scheduled task scheduling rules. If the data source synchronization logic is adjusted during the upgrade process, the data collection link for core monitoring nodes must not be interrupted. The length of ledger documents varies widely, from single monitoring data entries to regional summary reports, requiring vector storage and context window configurations to adapt to text processing needs of different lengths. Additionally, water utility data has a relatively high degree of field standardization, so field mapping rules must be configured in advance during the deployment phase to avoid field parsing errors after upgrade.

## How to configure settings
These configuration items apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `200–300` | Adapts to database connection requirements for concurrent writes across multiple monitoring points, prevents connection pool exhaustion |
| `MONGODB_URI` | Points to a sharded MongoDB instance dedicated to water utility ledgers | Stores unstructured inspection records and summary reports, supports large text field queries |
| `REDIS_URL` | Configured as a high-availability cluster address | Caches real-time monitoring data and user session information, reduces database query pressure |
| `STORAGE_S3_ENDPOINT` | Points to the address of the water utility intranet object storage service | Stores original collected data and generated report files, ensures compliance with local data requirements |
| `ROOT_KEY` | Generate a high-strength random string based on the deployment environment | Used for system administrator identity verification, prevents unauthorized access caused by default keys |
| `FE_DOMAIN` | Enter the frontend access domain name deployed on the water utility intranet | Restricts cross-domain access scope for frontend resources, adapts to intranet usage scenarios |

## Three common misconfigurations
- A configuration error prompt appears when entering the workflow after upgrade, and data sources cannot be loaded: The cause is that the permission configuration for `MONGODB_URI` was not updated synchronously during the upgrade, causing the application to fail to connect to the water utility ledger database.
- The chat automatically switches to another large model after saving the model configuration: The cause is that the frontend configuration cache was not cleared after the upgrade, or `FILE_TOKEN_KEY` was not configured correctly, leading to abnormal session status.
- A username or password error prompt appears during login: The cause is that the administrator account associated with `ROOT_KEY` was not initialized correctly during deployment, or the database initialization script was not fully executed.

## How to verify proper configuration
- Run the database connection test script to verify that the connection pool configured with `DB_MAX_LINK` can support at least 200 concurrent connections simultaneously.
- Upload a water utility monthly aggregated ledger document to trigger a report generation task, confirm that the generated report file can be downloaded normally through the storage address corresponding to `STORAGE_S3_ENDPOINT`.
- Log in to the system using the administrator account, verify that the frontend page can be accessed normally through the domain name configured in `FE_DOMAIN`, and that the session login status is normal.
- Simulate real-time monitoring data writing, confirm that data can be synchronized to the database normally, with no field parsing or write failure log records.

The values provided here are common starting points and should be evaluated against the reader's own samples.
