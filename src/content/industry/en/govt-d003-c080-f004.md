# City Investment Platform Ledger Summary and Report Generation: Workflow Orchestration

## What the data for this category looks like
City investment platform ledger data primarily originates from financial accounting systems, project management platforms, and debt management systems. The update cadence is batch synchronization at the end of each month or quarter. A single ledger document contains a multi-table linked structure, covering fields such as project code, project name, investment amount, debt balance, collection cycle, approval status, and more. Amount fields mostly use ten thousand yuan or hundred million yuan as units. Some cross-regional project ledgers will additionally include compliance fields required by local regulatory requirements.

## What constraints these characteristics impose on workflow orchestration
The scattered nature of multi-source data requires workflow configurations to include cross-system data pull nodes. Unified field mapping rules must be defined via `variables` to adapt to differences in field naming across systems. The monthly or quarterly update cadence requires setting periodic trigger mechanisms for workflows to avoid ineffective repeated runs. The multi-table linked structure requires adding association matching nodes in workflows to ensure correct association of fields such as project codes and subject information across different ledger tables. The presence of compliance fields requires built-in verification links in workflows to perform format and value verification on fields required by local regulatory requirements.

## How to set the configuration
These configuration items apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Cross-system data pull node trigger timing | 00:00 on the 1st of each month | Matches the monthly update synchronization cadence of city investment platform ledgers |
| Field mapping rules | Map to unified field names defined via `variables` | Adapts to field naming differences across source systems |
| Association matching node matching key | Project code | The unique identifier field for city investment ledgers, ensuring accurate multi-table association |
| Periodic trigger interval | 720 hours (30 days) | Matches the monthly update time cycle |
| Verification node compliance fields | Required items specified by local regulatory requirements | Covers the compliance verification needs of city investment ledgers |
| Global variable storage path | Workflow cache directory bound to `nodeId` | Ensures temporary storage and subsequent call permissions for ledger data are controllable |

## Three Common Misconfigurations
- Creating a question classification node and running it with the default AI model causes an error, which is resolved after switching the model. The cause is that the context window of the default AI model is too small to accommodate the long text content of city investment platform ledgers, leading to node call failure.
- The workflow text content extraction node returns an empty JSON result. The cause is that no dedicated field extraction rule for city investment platform ledgers is configured, or the input text does not contain valid content for the target fields.
- The workflow global variable history does not show the output of a specified component. The cause is that the output log switch for that component is not enabled, or `variables` are not correctly bound to the component's output parameters.

## How to Confirm the Configuration is Correct
- Manually trigger the workflow, check if the cross-system data pull node successfully obtains the latest ledger data with no connection timeout prompts.
- View the output logs of the field mapping node, confirm that fields from different sources have been unified to the preset standard names.
- Run the association matching node, verify that the project code association results for multi-table ledgers match the manually checked results.
- Check the global variable storage directory, confirm that temporary files for ledger summary have been generated under the cache path bound to `nodeId`.
