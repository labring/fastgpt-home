# Basic Chemicals Ledger Summary and Report Generation: HTTP Interfaces and External Systems

## What This Category's Data Looks Like
Basic chemical ledger data primarily comes from three sources: production device distributed control systems (DCS), material inventory management systems, and quality control laboratory management systems. Data updates occur per production shift or daily. Each individual ledger document uses structured CSV or Excel format, and includes fields such as raw material batch number, net feeding weight (tons), production duration (hours), qualified product output (tons), and unit energy consumption (kg standard coal per ton of product). Fields are closely linked, with units standardized to industrial general standards, and there are no complex nested sub-tables.

## What Constraints These Characteristics Impose on HTTP Interfaces and External Systems
Multi-source data access requires interfaces to support independent endpoints for different systems. Exclusive authentication parameters must be configured for each system in advance. Fixed update frequencies require polling intervals to match ledger update cycles. This prevents excessive system resource usage from overly frequent requests, or data synchronization delays from overly long intervals. Specific field and unit requirements mandate precise field filtering rules in interface requests. Only core ledger fields should be returned to reduce invalid data transfer volume. Structured document formats require response parsing to match field names exactly. This prevents ledger summary tasks from failing due to changes in field order.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Interface Authentication Method | Bearer Token, carried via the `Authorization` header | Matches the general authentication standard for external systems in chemical enterprises, ensuring secure data access |
| Request Variable Configuration | Pass `variables` as `{"deviceId": "PXXX", "date": "YYYY-MM-DD"}` | Accurately locate ledger data for the specified production device on the target date |
| Response Data Processing | Extract the core ledger field array from `responseData` | Filter redundant metadata returned by the interface, only retain valid content required for summary |
| Polling Interval | 3600 seconds | Matches the hourly update cycle of basic chemical ledgers, balances data timeliness and system load |
| Timeout Setting | 120 seconds | Covers the typical response duration of chemical system data queries, prevents mid-request interruptions |
| Field Filtering Rules | Only return the net feeding weight, production duration, and qualified output fields | Reduces data transfer volume, adapts to the core business needs of ledger summary |

## Three Common Errors
- Calling the content interface returns a 400 status code, with a prompt indicating unsupported document format. Cause: The `Content-Type` header is not correctly configured as `application/octet-stream`, or the uploaded document is not packaged in the structured format of basic chemical ledgers.
- Calling the API after local deployment fails to upload documents. Cause: File upload permission for external system integration is not enabled in FastGPT v4.17.0's interface configuration, or the request body does not correctly carry the file binary stream.
- Ledger summary results have empty fields. Cause: The request's `variables` do not specify the correct production device ID or date range, resulting in the interface returning no valid data.

## How to Verify Successful Configuration
- Execute the preset curl command to call the configured interface, and check if the returned `responseData` contains the preset ledger fields.
- Review interface logs to confirm the `Authorization` header correctly carries the authentication token, with no 401 unauthorized errors.
- Simulate a single ledger summary task, and verify that the generated report fields match the requested `variables` parameters.
- Test the automatic synchronization triggered by the polling interval, and confirm that new ledger data is received at the set 3600-second cycle.
