# Basic Chemicals Ledger Summary and Report Generation: Vector Models and Indexes

## What This Category of Data Looks Like
Ledger data for basic chemicals mainly comes from production shift daily reports, raw material inbound and outbound orders, equipment inspection records, and monthly quality inspection reports. Data updates follow daily shift cycles. Some key indicators such as material inventory and equipment operating parameters are synchronized in real time. Most documents are structured tables containing fields including material code, batch number, inventory quantity, and inspection values. Units include tons, kilograms, percentages, operating hours, and others. Some long documents are cross-page monthly summary ledgers.

## What Constraints These Characteristics Impose on the Vector Models and Indexes Link
The structured fields of basic chemical ledgers are numerous and have fixed units. This requires the indexing process to retain associated information between fields and units to avoid losing semantic associations during embedding. Frequently updated real-time data requires indexes to support incremental synchronization, to avoid performance overhead caused by full reconstruction. Cross-page summary ledgers of long documents need to retain contextual coherence during chunking, to prevent damage to the correspondence between indicators and batches after splitting. Multi-dimensional inspection indicator data requires vector recall to balance matching accuracy for numerical values and text semantics.

## How to Configure the Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Basic chemical ledgers mostly combine structured tables and long text; this range retains complete indicator information for a single batch of materials |
| Overlap Length | 100–150 characters | Prevents split batch numbers and material codes across chunks, ensuring semantic coherence |
| Similarity Threshold | 0.72–0.85 | Adapts to the precise matching requirements of ledger fields, filtering low-correlation historical ledger data |
| Single Search Limit | Top 8 entries | Balances recall scope and context length, adapting to the multi-field retrieval requirements of basic chemical ledgers |
| `defaultToken` | 4096 token | Matches the average length of basic chemical monthly summary ledgers, ensuring complete embedding |
| `maxToken` | 8192 token | Meets the context length requirement after merging multiple knowledge bases under FastGPT v4.17.0, avoiding truncation of key indicators |

## Three Common Misconfigurations
- Symptom: A single large monthly ledger file remains in the indexing process for an extended period with no progress bar movement. Cause: The ledger contains nested tables and ultra-long text lines, and the duplicate verification logic is triggered during chunking, causing indexing blocking.
- Symptom: A 60-second timeout error prompt pops up when switching knowledge base indexing. Cause: The incremental indexing strategy is not configured, and full synchronization of multi-batch ledger files exceeds the default timeout limit.
- Symptom: Retrieval results include ledger data from non-specified knowledge bases. Cause: The knowledge base priority rule is not configured correctly, and the index content of the target knowledge base is not prioritized during recall.

## How to Confirm the Configuration Is Correct
- Upload a single standard ledger file, check whether the indexing progress bar completes within a reasonable time frame, and adjust the chunk configuration based on actual file size.
- Retrieve ledger data containing a specific material code, verify whether the recall results include target fields and unit information, and adjust the similarity threshold to meet matching requirements.
- Configure dual knowledge base priority rules, launch cross-knowledge base retrieval, confirm that results preferentially come from the specified knowledge base, and verify that the priority setting takes effect.
- View the vector embedding log, confirm that the configurations of `defaultToken` and `maxToken` do not trigger truncation warnings, and match the actual length of ledger documents.
