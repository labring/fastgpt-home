# Ledger Summary and Report Generation for Basic Chemical Industry: Workflow Orchestration

## What data for this category looks like
Basic chemical industry ledger data primarily comes from production shop distributed control systems (DCS), enterprise resource planning (ERP) material management modules, and laboratory information management systems (LIMS). The system synchronizes data once after each production shift ends, or receives bulk imports each early morning. Each individual ledger document includes fields such as material code, batch number, feeding weight, average reaction period temperature, and qualified output quantity, with corresponding units of numeric code, batch string, kilogram, degrees Celsius, and kilogram. A single bulk ledger is a structured table file containing multiple rows and columns of data.

## What constraints these characteristics impose on workflow orchestration
Since ledger data comes from multiple heterogeneous systems, workflow orchestration configures multi-source data pull nodes to complete unified format conversion. The data update rhythm limits workflow trigger frequency; scheduled tasks shorter than 4 hours are not recommended. Fixed fields and clear units require a variable verification step in the workflow. This step checks unit matching for fields such as feeding weight and output quantity to avoid cross-field unit confusion. The multi-row data structure of bulk ledgers requires workflow nodes to support bulk data traversal processing, preventing single-node processing timeouts. Ledger data involves production record retention, so workflow orchestration configures global parameter storage to avoid resetting key configurations each run.

## How to set configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | Scheduled trigger, interval 8–12 hours | Matches the update rhythm of basic chemical industry ledgers per shift or daily |
| `variables` mapping rules | Bind preset units by field name | Fixed ledger fields and units to avoid unit confusion |
| Maximum bulk processing rows | 1000–2000 rows | Adapts to the conventional data scale of a single bulk ledger |
| Node timeout | 600 seconds | Supports time requirements for multi-source data pulling and format conversion |
| `nodeId` binding | Assign a unique identifier to each data pull node | Distinguish multi-source data from DCS, ERP, and LIMS |

## Three common configuration mistakes
- Symptom: Global production parameters are cleared after workflow execution, and historical configurations cannot be reused. Cause: Global variable storage is not enabled, and only temporary `variables` are used to store parameters, which resets variables each time the workflow runs.
- Symptom: When configuring a knowledge base call node, referencing application variables returns an error prompting invalid parameters. Cause: Fields in `variables` are not correctly bound to the knowledge base retrieval parameters, or the variable format does not meet the knowledge base requirements.
- Symptom: After an HTTP request returns multiple sets of ledger data, variables for a specified batch cannot be bound to the corresponding knowledge base. Cause: `nodeId` is not used to distinguish data nodes of different batches, leading to chaotic variable mapping.

## How to confirm the configuration is complete
- View the workflow trigger log to confirm the trigger interval matches the preset update rhythm.
- Test the import and processing of a single bulk ledger to confirm the node does not trigger the timeout limit.
- Call the variable verification node to verify that field units in `variables` match the preset rules.
- Check the `nodeId` configuration to confirm each data pull node has a unique and traceable identifier.

The values provided here are common starting points and should be measured against the reader's own samples.
