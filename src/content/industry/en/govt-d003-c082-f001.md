# Ledger Aggregation and Report Generation for Basic Telecommunications Operations: HTTP Interfaces and External Systems

## What the Data for This Category Looks Like
Ledger data for basic telecommunications operations comes from three core systems: BOSS billing system, CRM customer management system, and base station operation and maintenance monitoring platform.
Data updates follow two rhythms: User bill ledgers are updated in batches every early morning. Base station operation and maintenance ledgers are synchronized every hour.
Single ledger documents use structured JSON format, and include fields such as unique ledger identifier, business type, operation time, involved resource code, processing status, settlement amount (CNY), and operation and maintenance time spent (minutes). Each record corresponds to a single independent business ledger.

## What Constraints Do These Characteristics Impose on the HTTP Interfaces and External Systems Link
Multiple data sources require HTTP interfaces to support identity verification rules and request formats from different systems.
Time-phased update rhythms require interface polling intervals to match data update frequencies, to avoid repeated data pulling or missed new data.
Structured fields and specific unit requirements mean interface requests must support filtering by business type and time range. Responses must verify the integrity of core fields to ensure the accuracy of subsequent aggregation and report generation.
Large single-data volume requires interfaces to support paginated pulling, to avoid transmission overload from single requests.

## How to Configure Settings
Configurations in this chapter are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
|----------------------|----------------------------------------------|--------------------------------------------------------------------------|
| `Authorization` | Configure Bearer token according to connected system requirements | Adapt to identity verification requirements of internal basic telecommunications operation systems, and ensure legitimacy of interface call permissions |
| `variables` | Bind business type and statistical time range variables | Accurately pull ledger data of corresponding dimensions, and reduce invalid data transmission |
| Single pull data volume | Set to 800–1200 records | Match reasonable data scale returned by a single interface, and avoid transmission timeouts caused by overly large response bodies |
| Request timeout | Set to 600 seconds | Adapt to maximum response duration for pulling basic telecommunications ledger data, and cover time consumption of multi-system joint queries |
| `responseData` validation | Enable core field validation | Ensure pulled data includes required fields such as ledger ID, business status, and amount, and guarantee accuracy of subsequent aggregation |
| Polling interval | Set according to data update frequency; for example, set daily ledgers to 3600 seconds | Match data update rhythm, and avoid repeatedly pulling old data or missing new data |

## Three Common Misconfigurations
- Interface call returns `messages is empty` error: Required ledger statistical time range parameters are not configured in `variables`, leading to missing core filter conditions in the request body, which triggers system verification failure.
- Interface call returns empty results: `responseData` validation is not enabled, and pulled ledger data lacks core fields, so FastGPT cannot identify valid data for aggregation.
- Interface call timeout: Single pull data volume exceeds 1500 records, which exceeds the response limit of internal operator systems, causing the request to time out and interrupt.

## How to Confirm Configuration Is Correct
- Call the test interface, check whether the response body includes core fields such as ledger ID and business type, and confirm that `responseData` validation is active.
- Configure a scheduled trigger rule, wait for one data update cycle, check whether the aggregated report includes the latest ledger data, and confirm that the polling interval matches the data update rhythm.
- View interface call logs, confirm that the `Authorization` parameter is correctly carried, and there are no error records of identity verification failure.
- Simulate pulling ledger data of different business types, confirm that parameters bound to `variables` can correctly filter corresponding data, with no redundant or missing records.
