# Ledger Summary and Report Generation for Basic Telecommunications Operations: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Ledger data for basic telecommunications operations originates primarily from billing and settlement systems, base station operation and maintenance monitoring platforms, and customer service ticket repositories. Detailed ledgers for individual base stations or customers are updated daily. Regional summary ledgers are generated weekly. Each individual ledger document includes structured fields such as base station ID, cumulative monthly traffic, total call duration, single fault repair time, and customer subscription tier. Traffic uses GB as its unit, and call duration uses minutes. Monthly summary ledgers aggregate fields by city and business type. Standard CSV and Excel formats are the primary document formats for all ledgers. This document is written based on the platform rules of FastGPT v4.17.0.

## What constraints do these characteristics impose on multi-turn dialogue and prompt engineering
Ledger fields include multiple types of measurement data with specific units. Prompts must clearly define unit validation rules for field values to avoid generating incorrect summary results. Data is updated daily or weekly. Multi-turn dialogue must limit the context window length to prevent loading expired or redundant historical ledger data from interfering with current queries. Two types of ledger structures exist: detailed and summary. Multi-turn dialogue must use a pre-prompt to clarify the ledger type the user is querying, to avoid confusion over data aggregation dimensions. Ledgers from different sources must be bound to corresponding calling plugins. The context of multi-turn dialogue must mark data source identifiers to ensure the called plugin matches the query requirements.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum conversation context length | 8000–12000 token | Adapts to the number of fields and single data length of basic telecommunications operation ledgers, prevents context overflow |
| Historical message retention duration | 600 seconds | Limits the scope of multi-turn dialogue context, focuses on recent ledger query needs |
| Session binding parameters | Bind `chatId`, `messages`, `variables` | Ensures context is bound to the current session during multi-turn dialogue, avoids cross-session data confusion |
| Plugin invocation trigger rule | Trigger based on explicitly mentioned ledger type by the user | Matches different data sources for detailed/summary ledgers, reduces invalid invocations |
| Prompt template update frequency | Updated weekly | Adapts to routine adjustments of basic telecommunications operation ledger fields, maintains alignment between prompts and data structures |

## Three Common Misconfigurations
- Issue: When nesting calls to other ledger summary applications, the target application does not record conversation logs. Cause: The session identifier is not passed in the `variables` parameter of the main workflow, so the target application cannot bind the current conversation context.
- Issue: When nesting a form input node into another workflow, the dialog box always displays. Cause: The pop-up trigger rule is not adapted in the nested configuration, and the default single-workflow trigger logic conflicts with the nested scenario.
- Issue: Web pages or text-to-image results cannot be rendered normally in the dialog box. Cause: The rich text rendering switch for conversation content is not enabled, and the prompt does not explicitly require generating content formats that comply with rendering rules.

## How to Confirm Proper Configuration
- Initiate a ledger detail query, verify that the conversation context window only contains valid messages from the current session, with no redundant historical data.
- When invoking a nested application, check if the target application's logs include the current session's `chatId` identifier to confirm normal log recording.
- Trigger the form input node, verify that the dialog box display status meets expectations in the nested workflow, with no abnormal pop-ups.
- Submit a query request that includes units, verify that the units of fields in the generated report match the standard units of the ledger data.
