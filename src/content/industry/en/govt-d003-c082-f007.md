# Ledger Aggregation and Report Generation for Basic Telecommunications Operations: Database and Operations Maintenance

## What the data for this category looks like
Ledger data for basic telecommunications operations comes primarily from base station operation monitoring systems, billing and settlement systems, user service record databases, and operations work order systems. Data update rhythms fall into three categories: real-time base station status data updates every second, billing and settlement data is generated in hourly batches, and monthly summary ledgers are archived on a calendar day basis. A single ledger document includes fields such as base station ID, timestamp, signal strength (unit: dBm), daily cumulative traffic (unit: GB), alarm level, and associated operations work order number. Some fields must strictly match preset enumeration values. Timestamps are stored uniformly in UTC format.

## What constraints these characteristics impose on the database and operations maintenance link
High-frequency writes of real-time base station data cause frequent database index updates. Optimize index structures to avoid degraded write performance. Data with different update frequencies requires separate storage. Real-time data and batch summary data have large IO requirement differences. Mixed storage triggers resource competition. Multi-field joint queries are common. Create composite indexes for commonly used query combinations, otherwise query latency will increase. Data retention periods vary significantly. Real-time data only requires short-term retention, while monthly ledgers need long-term archiving. Configure a hot-cold data separation strategy to reduce storage costs.

## How to set configurations
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://admin:securepass@db-node1:27017,db-node2:27017/telecom_ledger?replicaSet=rs0` | Adapts to a multi-node high-availability architecture, supports multiple real-time base station data writes per second |
| `PG_URL` | `postgresql://admin:securepass@report-db:5432/telecom_report?sslmode=require` | Stores structured summary ledgers, supports complex statistical SQL queries, and ensures data transmission encryption |
| `DB_MAX_LINK` | `200–300` | Matches the default maximum connection limit for database instances, avoids task failures caused by exhausted connections |
| `REDIS_URL` | `redis://:cachepass@redis-cluster:6379/0,redis://:cachepass@redis-cluster:6380/0` | Caches frequently queried base station status snapshots, reduces repeated read pressure on the database |

## Three common misconfigurations
- Symptom: A connection timeout error is returned when calling the database, but the database can be connected normally using the mongosh command. Cause: The network where the FastGPT process runs does not open the access port for the database instance, or the connection string contains incorrect authentication parameters.
- Symptom: When the ledger aggregation workflow node count exceeds a certain threshold, obvious lag appears during interface dragging, and operation response time exceeds 3 seconds. Cause: The `REDIS_URL` cache for workflow status is not configured, causing each interface operation to query the database for node information.
- Symptom: Partial failures occur in batch ledger generation tasks, and database logs show connection limit exceeded. Cause: The `DB_MAX_LINK` configuration value exceeds the maximum allowed connections for the database instance, preventing new connections from being established.

## How to confirm the configuration is correct
- Run the built-in database connectivity test tool to verify that the `MONGODB_URI` and `PG_URL` configurations can normally establish connections and read and write corresponding business tables.
- View cache monitoring metrics to confirm that the instances configured via `REDIS_URL` have continuous read and write requests, with no large number of connection failure records.
- Submit a single ledger aggregation task, and check that the task execution log contains no database connection timeout or connection pool exhaustion errors.
- After adjusting the `DB_MAX_LINK` configuration, observe changes in database connection counts to confirm that the actual connection count does not exceed the configured upper threshold.

The values given are common starting points and should be measured against the reader's own samples.
