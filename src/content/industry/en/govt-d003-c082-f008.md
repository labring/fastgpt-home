# Ledger Summary and Report Generation for Basic Telecommunications Operations: Document Parsing and Chunking

## What the Data for This Category Looks Like
The ledger data for basic telecommunications operations comes from billing systems, network operation and maintenance platforms, and customer service ticket systems. Update cycles include real-time traffic data, daily batch-summarized operation and maintenance fault ledgers, and monthly settlement reports. Document formats are primarily multi-page PDFs and structured Excel files, containing fields such as base station ID, call duration, traffic usage, fault code, and processing duration, with units including seconds, GB, counts, %, and others. Some ledgers include cross-page nested tables, network topology diagrams, and long-text fault descriptions. Data structures vary across different business modules.

## What Constraints These Characteristics Impose on the "Document Parsing and Chunking" Link
The multi-source and heterogeneous document formats require the parsing module to support mixed-format parsing, to avoid losing structural information from nested tables and topology diagrams. The feature of field-dense data with units requires that context associations be preserved during chunking, to prevent splitting that breaks the link between fields and their units. Frequently updated ledger files require controlling parsing duration and file size limits, to avoid timeouts or upload failures during batch processing. The presence of cross-page content requires chunking logic to balance page boundaries and business semantics, to avoid splitting the same business unit into different chunks. The default parsing configuration of FastGPT v4.17.0 cannot fully adapt to the above characteristics, and relevant parameters must be adjusted accordingly.

## How to Set the Configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `chunkSize` | 800–1200 characters | Basic telecommunications ledgers have dense fields and include units, to avoid losing the contextual link between fields and their units when splitting |
| `chunkSplitter` | Split by paragraph + table boundaries | Ledgers include nested tables and long-text fault descriptions, to preserve table integrity and paragraph semantics |
| `customPdfParse` | Enabled | Parse operation and maintenance ledger PDFs with cross-page tables and network topology diagrams, to restore original typesetting structure |
| `PARSE_FILE_TIMEOUT_SECONDS` | 300–600 seconds | Adapt to batch ledger parsing for single files under 100MB, to avoid timeout interrupts during long file parsing |
| `UPLOAD_FILE_MAX_SIZE` | 100 MB | Aligns with the conventional upload limit for single ledger files in daily basic telecommunications operations |
| `chunkSettingMode` | Manual configuration | Adjust chunking parameters for the structured characteristics of ledgers, to adapt to document structures of different business modules |

## Three Common Mistakes
- Symptom: Table data is returned as scattered text after parsing, with no complete table structure. Cause: `customPdfParse` is not enabled, and the default parsing engine cannot recognize the nested table format in ledgers.
- Symptom: After calling the knowledge base creation API, real-time updated parsing status is not obtained, only the initial submission status is returned. Cause: `PARSE_FILE_TIMEOUT_SECONDS` is not configured to adapt to the parsing duration of long ledger files, or the parsing callback interface is not monitored.
- Symptom: After uploading a ledger document containing HTTP interface response messages, the parsing result does not retain the Set-Cookie field content. Cause: The default document parsing module does not cover the special field extraction rules for HTTP response messages, and cannot accurately capture target fields.

## How to Confirm the Configuration Is Correct
- A test operation and maintenance ledger PDF containing nested tables may be uploaded, and the parsing result checked for complete table row and column structures and field correspondence.
- The knowledge base creation API may be called, and the returned parameters checked for a parsing status field, confirming that the status updates in real time alongside parsing progress.
- `chunkSize` may be adjusted to different ranges, and the contextual integrity of chunking results compared to select a value range that meets business requirements.
- A monthly settlement ledger compressed package with a 100MB single file size may be uploaded, confirming that the parsing process does not trigger timeout errors and the file completes parsing normally.
