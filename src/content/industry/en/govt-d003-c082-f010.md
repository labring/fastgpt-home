# Basic Telecommunications Operations Ledger Summary and Report Generation: Knowledge Base Retrieval and Recall

## What the data for this category looks like
Ledger data for basic telecommunications operations primarily comes from operation and maintenance systems, billing systems, and customer service ticket systems. Data updates follow a real-time sync or hourly batch update rhythm. Individual ledger documents include fields such as base station code, monthly traffic value, fault repair duration, and service response count. Units include GB, hours, and times. Most documents take the form of structured tables, while some associated ticket attachments are unstructured text. Clear hierarchical relationships exist between fields. Some ledgers require cross-system stitching to form complete report materials.

## What constraints do these characteristics impose on the knowledge base retrieval and recall link
The structured characteristics of basic telecommunications operation ledgers require retrieval to match field association relationships, to avoid recalling irrelevant content. Real-time or hourly update rhythms require knowledge base sync frequency to align with business update rhythms, to prevent recalling expired data. Cross-system stitched ledger materials require associating the collection ID of the corresponding dataset during retrieval, to ensure recalled content comes from a complete business chain. The presence of unstructured ticket attachments requires retrieval modes to support both structured field matching and full-text semantic recall, to cover different types of ledger materials. The large number of fields also causes significant fluctuations in single-block content length, requiring adjustments to retrieval block processing rules.

## Configuration Settings
| Configuration Item | Recommended Value Range | Rationale |
|---|---|---|
| `similarity` | 0.72–0.80 | Matches the field association and semantic relevance requirements of basic telecommunications ledgers, avoids recalling irrelevant base station data or ticket content |
| `limit` | 8–12 entries | Adapts to the characteristics of multiple ledger fields and variable single-block content length, controls the total context length of a single retrieval |
| `searchMode` | Hybrid retrieval | Covers both structured field matching and full-text semantic recall, adapts to mixed data of structured ledgers and unstructured attachments |
| `usingReRank` | Enabled | Re-ranks recall results by relevance, corrects ranking bias under a single similarity threshold, adapts to ledger data with multi-field associations |
| `datasetSearchUsingExtensionQuery` | Enabled | Automatically expands retrieval keywords, covers synonyms and field aliases for cross-system ledgers, avoids missing recall of cross-system associated content |
| `collectionIds` | List of collection IDs divided by business domain | Precise retrieval scope limitation, avoids recalling irrelevant customer service tickets or operation and maintenance log data |

## Three Common Misconfigurations
- Symptom: A `Cannot convert undefined or null to object` error pops up during workflow runtime. Cause: The `collectionIds` configuration is not correctly specified, so the retrieval cannot match valid dataset collections, returning an empty object that causes a conversion error.
- Symptom: After setting the `limit` recall count upper limit, knowledge base blocks exceeding the preset length threshold are still recalled and referenced. Cause: `usingReRank` is not enabled or block length filtering rules are not configured, only recalling by similarity without truncating long blocks, resulting in exceeding the context upper limit.
- Symptom: Knowledge base creation gets stuck, and the ollama log prompts `try reducing the size of the batch`. Cause: The value range of `limit` is not adjusted, the total length of single-recall blocks exceeds the batch processing limit of the embedding model, causing the embedding task to fail. This issue is common in FastGPT v4.17.0.

## How to Verify Correct Configuration
- Run a single retrieval test, check if the returned result fields match the current business ledger fields, adjust the `similarity` value until the recalled content meets business requirements.
- Check the total character count of the retrieval results, confirm it does not exceed the current workflow's context upper limit, adjust the `limit` value as needed.
- Check the logs for empty object conversion errors or batch processing failure prompts, verify that the `collectionIds` and `searchMode` configurations are correct.
- Compare manual retrieval results with system automatic recall results, confirm that the ranking results meet business relevance requirements after `usingReRank` is enabled.

The values provided are common starting points and should be measured against the reader's own samples.
