# Ledger Aggregation and Report Generation for Basic Telecommunications Operations: Deployment and Upgrade

## What this type of data looks like

## What constraints do these characteristics impose during deployment and upgrade?
Access to multiple data sources requires configuring multiple independent data connection parameters during the deployment phase to adapt to the interface specifications of different business systems. The high-frequency incremental update rhythm requires that the interval of scheduled synchronization tasks be adjusted to match the hourly update rhythm, to avoid data delays affecting operational decisions. The requirements for structured fields and fixed units necessitate enabling data format verification during deployment to ensure field consistency and readability of subsequent aggregation reports. The large volume of ledger data requires configuring sufficient storage resources and concurrent connection counts to prevent resource exhaustion during synchronization. The upgrade phase must be compatible with legacy ledger data formats to avoid interrupting daily operational aggregation tasks.

## How to configure settings
| Configuration Item | Suggested Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://username:password@host:port/telecom_ledger?authSource=admin` | Stores unstructured raw ledger data and historical archive files, adapts to high-frequency read/write requirements |
| `PG_URL` | `postgresql://username:password@host:port/telecom_stat?sslmode=require` | Stores structured statistical ledger fields and aggregated report metadata, ensures transaction consistency |
| `REDIS_URL` | `redis://:password@host:port/0` | Caches frequently queried ledger summary data to reduce repeated read/write load on databases |
| `DB_MAX_LINK` | `200–300` | Adapts to concurrent connection requirements for hourly incremental synchronization, prevents connection exhaustion during synchronization, complies with concurrent configuration requirements of FastGPT v4.17.0 |
| `STORAGE_S3_ENDPOINT` | `Fill in the address provided by the local object storage service provider` | Stores exported PDF reports of ledgers and raw data backups, adapts to large file storage requirements |
| `ROOT_KEY` | `Custom 32-character random string` | Ensures permission security for system background operations, complies with data security and compliance requirements of state-owned enterprises and public sector entities |

## Three common mistakes
- Phenomenon: No registration entry appears on the login interface after initial deployment, making it impossible to create an administrator account. Background logs return a `403 Forbidden` status code. Cause: The `ROOT_KEY` parameter was not configured correctly, causing the system's initial permission verification to fail.
- Phenomenon: Authentication failure is returned when connecting to an external large model, with logs showing `invalid api key`. Cause: Key verification rules for model access were not configured in accordance with the security requirements of state-owned enterprises and public sector entities, and the authentication format of the external platform was not matched correctly.
- Phenomenon: Ledger synchronization task fails, with logs showing missing fields. Cause: Database permissions for the `PG_URL` connection were not verified, making it impossible to read complete field data of the ledger.

## How to confirm configurations are correctly set
- Run the built-in database connection test script to verify the connection status of `MONGODB_URI` and `PG_URL`, confirm there are no connection timeout or permission error messages.
- Start the preset scheduled synchronization task, check whether there are records of successful incremental data synchronization in the task logs, confirm that the synchronization frequency matches the hourly update rhythm of the ledger.
- Attempt to generate a single base station ledger aggregation report, check whether the fields and units included in the report are consistent with the format of basic telecommunications operation ledgers.
- Access the domain configured in `FE_DOMAIN`, verify that the login interface loads normally, use the `ROOT_KEY` to create the initial administrator account, confirm that the permission configuration takes effect.
