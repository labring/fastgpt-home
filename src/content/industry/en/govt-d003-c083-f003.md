# Ledger Summary and Report Generation for Infrastructure Construction: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Ledger data for infrastructure construction comes primarily from paper or electronic forms such as on-site construction logs, material incoming acceptance receipts, progress payment approval forms, and process acceptance records. Data update rhythm adjusts with construction milestones. Daily updates occur during routine construction phases, and centralized summary takes place during monthly settlement phases. A single ledger document typically includes fields such as project number, construction area, material name, incoming quantity, acceptance result, responsible person, and submission date. Units cover multiple engineering-specific measurement units including tons, square meters, ten thousand yuan, and labor hours. Some ledgers are stored as structured Excel tables, while others are archived as scanned documents or PDF files.

## What constraints these characteristics impose on the multi-turn dialogue and prompt engineering link
The multi-field and multi-unit characteristics of infrastructure construction ledgers require clear specification of the current session’s associated project number and time range during multi-turn dialogue. This prevents cross-project data confusion. Ledgers with different update rhythms require confirmation of the data statistical cycle at the start of the dialogue. This prevents calling expired or incomplete construction records. The diversity of engineering-specific measurement units requires that prompt engineering mandates output results match the units of the original ledgers. This avoids unit conversion errors. The multi-source and heterogeneous ledger storage formats require confirmation of the data source type during multi-turn dialogue. Unstructured archived documents must first undergo structured parsing before querying can begin.

## Three Common Misconfigurations
- Phenomenon: Subsequent replies in multi-turn dialogue do not link to previously raised ledger query questions, and context is lost. Cause: The `chatId` parameter is not bound, or the number of retained historical messages is set below 15, causing the session context to be automatically truncated by the system.
- Phenomenon: After configuring the AIProxy proxy, the thinking process is not displayed in the conversation history, but relevant output exists in the running logs. Cause: The prompt template does not explicitly require hiding the thinking process, or the corresponding hidden switch is not configured in `variables`.
- Phenomenon: When attempting to generate a ledger report through dialogue, the measurement units in the returned results do not match the original ledger. Cause: The prompt template does not mandate matching engineering-specific units, or unit verification rules are not preset in `variables`.

## How to Verify Successful Configuration
- Initiate an initial query that includes a project number and statistical cycle. Confirm that replies in subsequent multi-turn dialogue all link to the specified project and cycle. Verify that the `chatId` and context configurations are effective.
- Trigger a test dialogue that includes a thinking process. Check the conversation history and running logs to confirm that the display status of the thinking process matches the preset requirements.
- Generate a ledger summary report. Verify that all measurement units in the report match the labels in the original ledger, confirming the prompt template and unit verification configurations are effective.
- Wait longer than the preset historical message retention duration, then initiate a new query. Confirm that the session context has been reset, verifying the session expiration configuration is effective.
