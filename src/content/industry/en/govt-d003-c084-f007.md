# Ledger Aggregation and Report Generation for Commodity Trading: Database and Operations

## What this type of data looks like
Ledger data for commodity trading primarily comes from business systems including trade contracts, warehouse receipts, delivery vouchers, settlement documents, and similar. Data is synchronized in real time when a single transaction is completed. Daily transaction summary ledgers are generated each day. Full-cycle reports are generated on a monthly and annual basis. Each ledger entry includes fields such as product code, product name, specification model, origin, transaction quantity, transaction unit price, transaction amount, transaction parties, delivery date, storage location, and more. Common units include tons, cubic meters, yuan, and similar standard units.

## What constraints these characteristics impose on database and operations work
Real-time synchronization of individual transactions generates high-frequency write requests. This requires database connection pools to support a sufficient number of concurrent connections. Batch queries for daily summaries and monthly reports require reasonable indexes on commonly used fields to reduce query latency. Multi-dimensional business fields require databases to support structured storage and flexible field expansion, to adapt to differentiated field requirements for different commodity categories. Data volume grows continuously with transaction frequency. This requires reserving storage resources that can be scaled quickly. Data change logs must also be recorded to meet compliance audit requirements.

## How to configure settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://trade_user:secure_pass@db-host:27017/commodity_ledger?authSource=admin` | Stores real-time transaction ledgers and original business data, specifies a dedicated business database and authentication source |
| `PG_URL` | `postgresql://report_user:secure_pass@pg-host:5432/trade_summary?sslmode=require` | Stores monthly/annual summary reports and data change audit logs, enables SSL to secure data transmission |
| `DB_MAX_LINK` | `180–250` | Adapts to concurrent write and batch query demands from high-frequency real-time transactions, prevents connection pool exhaustion |
| `REDIS_URL` | `redis://cache_user:secure_pass@redis-host:6379/1?maxmemory-policy=allkeys-lru` | Caches daily transaction summary data to reduce repeated query load on core databases |
| MongoDB Version | 6.0 or 7.0 | Meets database compatibility requirements for FastGPT v4.17.0, supports current business concurrency and storage demands |

## Three common mistakes
- Symptom: A `Connection refused` or `Authentication failed` error occurs after deployment on a Linux environment, and ledger data cannot be written or read. Cause: Authentication information in `MONGODB_URI` is not configured correctly, or the database port is not open to the business network segment.
- Symptom: Queries time out when generating monthly reports in batch, and the number of returned results is incomplete. Cause: Indexes are not created on commonly used fields such as product code and delivery date, leading to excessively long full table scan times.
- Symptom: Cached daily summary data frequently expires, leading to increased load on core databases. Cause: The memory eviction policy in `REDIS_URL` is not configured properly, or the cache expiration time does not match the business query frequency.

## How to verify configurations are properly set
- Run a single transaction data write test, verify that the corresponding ledger record is generated in the core database, and adjust the test frequency based on the business write frequency.
- Initiate a monthly summary report query, verify the completeness and timeliness of returned data, and adjust the verification rhythm based on the business report generation cycle.
- Check database connection pool monitoring, confirm that the number of active connections does not exceed the configured limit, and adjust connection pool parameters based on concurrent request volume.
- Check Redis cache hit rates, confirm that summary data for high-frequency queries is effectively cached, and adjust the cache strategy based on business query frequency.
