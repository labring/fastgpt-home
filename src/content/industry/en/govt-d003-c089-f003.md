# Construction Machinery Ledger Summary and Report Generation: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Construction machinery ledger data primarily originates from three data sources: equipment management systems, IoT operational sensors, and on-site maintenance work orders. Basic ledger fields include equipment ID, model, manufacturing date, rated power, and maintenance cycle. Operational data fields include real-time fuel consumption, cumulative operating hours, and fault count, with units mostly being hours, liters, and units. Basic ledger data is synchronized and updated daily. Real-time operational data is uploaded at a second-level frequency. A single complete ledger document is typically 500 to 1500 characters in length.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
Dispersed data sources require dialogue to associate context across multiple data types. During multi-turn interactions, the device ID corresponding to the current session must be continuously tracked to avoid confusing ledger data from different devices. Differences in update frequencies require prompts to explicitly specify the time range for retrieved data, ensuring that obtained operational data matches the basic ledger. The large number of fields and hierarchical structure require prompts to limit retrieval scope and output format, preventing large language models from confusing cross-field statistical logic. The long document characteristic requires that dialogue context is properly truncated to avoid exceeding the model's context window limit.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Maximum Context Length | 8000–12000 characters | Adapts to the length of single construction machinery ledger documents, and accommodates device IDs and query conditions from multi-turn dialogue |
| Single Retrieval Count | Top 8 entries | Balances retrieval efficiency and data completeness, avoiding excessive redundant fields that interfere with large language model statistical logic |
| `chatId` | Bind to the session's unique device ID | Differentiates dialogue contexts for different devices, ensuring each retrieval only matches data for the device specified in the current session |
| `variables` | Bind to statistical cycle and output word count | Limits the time range of retrieved data, while constraining the output format and length of the large language model |
| `messages` | Pass context by role | Standardizes the content format of multi-turn dialogue, ensuring the large language model can correctly identify historical queries and current requirements |
| Prompt Template | Calibrated through actual testing | Adapts to the fixed statistical logic of ledger fields, explicitly requiring the device ID to be listed first before outputting summary results |

This configuration is based on FastGPT v4.17.0.

## Three Common Mistakes
- Ledger data returned as empty in dialogue, but corresponding content can be retrieved in knowledge base testing. The cause is failure to bind the `chatId` parameter, leading to confusion in session context, and retrieval matches ledger data from other devices.
- Returns 404 Invalid URL (POST /api/chat/completions) when called. The cause is incorrect configuration of the role and content format of the `messages` parameter, or the interface path not being associated with the unique identifier of the current device.
- The workflow ends directly after reaching the large language model processing step, without generating a summary report. The cause is failure to bind the trigger conditions for subsequent workflow nodes via `variables`, resulting in the session context not being passed to the summary step.

## How to Verify Proper Configuration
- Initiate a ledger query for a single specified device, check if returned results only include field data for that device, with no redundant information from other devices.
- Call the interface and view logs, confirm that the `chatId` parameter is correctly passed with each session request, with no null or duplicate values.
- Configure the prompt to constrain the output format, initiate a test request, check if returned content complies with preset field order and statistical requirements.
- Simulate multi-turn dialogue, sequentially query ledgers for different devices, check if dialogue context correctly distinguishes retrieval results for different devices.
