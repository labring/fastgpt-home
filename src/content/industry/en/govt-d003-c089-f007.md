# Construction Machinery Ledger Summary and Report Generation: Database and Operations Maintenance

## What data for this category looks like
Construction machinery ledger data primarily comes from factory default parameter packages, real-time operating condition data uploaded by in-vehicle sensors, and inspection and maintenance records entered by operations staff.
Real-time fields including operating duration, fuel consumption, and lifting weight are synced after each single job ends. Daily inspection records are updated in bulk each early morning. Monthly maintenance ledgers and operating condition summary data are synced at the end of each month.
Each device's ledger document includes fields such as device ID, model, rated lifting capacity, cumulative operating duration, latest maintenance date, and affiliated project. Most field units are tons, hours, and date formats. Some fields are enumerated text, such as device operating status.

## Constraints imposed on database and operations workflows by these characteristics
High-frequency real-time operating data generates a large volume of write requests in a short period, requiring database connection pool configurations adapted for high-concurrency write scenarios.
The mixed multi-field ledger structure requires indexes on frequently queried fields such as device ID and affiliated project, to avoid query delays caused by full table scans.
Monthly bulk-synced maintenance ledgers and operating condition data have large volumes, so historical ledger data must be partitioned by month to reduce single-table query pressure.
Enumerated fields such as device operating status require unified validation rules to prevent invalid data from being written to the database, which would compromise the accuracy of subsequent summary and report generation.

## How to set configurations
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://admin:securepass@db-host:27017/construction_machinery?authSource=admin` | Construction machinery ledgers include unstructured maintenance photos and operating log snippets. MongoDB is suitable for storing semi-structured data, and a dedicated database name is specified to isolate business data |
| `PG_URL` | `postgresql://admin:securepass@db-host:5432/structured_assets?sslmode=require` | Structured fields such as device ID and rated lifting capacity are suitable for storage in PostgreSQL. SSL is enabled to ensure data transmission security |
| `DB_MAX_LINK` | `20–30 connections` | Real-time data write frequency per device is high, so the connection pool must cover concurrent read and write requests to avoid write failures caused by exhausted connections |
| `REDIS_URL` | `redis://:securepass@cache-host:6379/0` | Used to cache frequently queried basic device information, reducing direct database query pressure and accelerating ledger summary response times |

## Three common mistakes
- Phenomenon: Database connection timeout, returning status code 504, with single message processing taking over 30 seconds. Cause: The `DB_MAX_LINK` configuration was not adjusted based on real-time data update frequency, leading to exhausted connection pools that prevent new requests from obtaining connections.
- Phenomenon: Unable to create a dedicated ledger database after local deployment, with a permission denied prompt. Cause: An account with database creation permissions was not configured in `PG_URL` or `MONGODB_URI`, or the corresponding database instance was not created in advance.
- Phenomenon: Concurrent duplicate calls of the tool, leading to duplicate entries in ledger summary results. Cause: No Redis cache lock was used to mark the unique execution identifier of the current summary task, causing multiple processes to trigger identical ledger pull requests simultaneously.

## How to confirm proper configuration
- Run a database connection test script to verify that the `MONGODB_URI` and `PG_URL` configurations can establish normal connections, with no permission or address error prompts.
- Submit a simulated device operating data entry to confirm that data is correctly written to the corresponding database table or collection, with field formats and units matching preset rules.
- Initiate a bulk ledger summary request, observe the hit rate of the Redis cache, and confirm that frequently queried basic device information can be cached normally.
- Adjust the `DB_MAX_LINK` configuration to the recommended range, simulate 10 concurrent write requests, and confirm that no connection exhaustion errors occur.

The values provided are common starting points and should be measured against the reader's own samples.
