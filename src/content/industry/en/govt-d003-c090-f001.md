# Ledger Aggregation and Report Generation for Refined Petroleum Product Sales: HTTP Interfaces and External Systems

## What the data for this category looks like
Refined petroleum product sales ledger data primarily comes from gas station POS terminals, oil tank level monitoring systems, and headquarters inventory, procurement, and sales management systems. Transaction flow data is synchronized hourly. Oil tank inventory data is updated in real time. Inventory ledgers are synchronized in batches every early morning.

A single ledger document includes fields such as oil grade, daily sales volume, inventory balance, number of transactions, station code, and settlement amount. Units include liters, yuan, and tons. Cross-station aggregated data must be aggregated by oil product category.

## Constraints on HTTP Interfaces and External Systems Posed by These Characteristics

Real-time updated oil tank inventory data requires that the interface call interval does not exceed 1 hour. Otherwise, real-time ledger updates cannot be supported. The multi-field classified ledger structure requires that request parameters include dimensions such as oil grade and station code. Otherwise, corresponding data cannot be accurately matched.

Daily batch-synchronized inventory data has a large volume. The number of data items returned by a single interface request must be limited to avoid timeouts. Unit differences between different systems require that interface return data include standard unit identifiers to facilitate direct use by downstream systems.

## How to Configure Settings

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Fixed prefix `Bearer ` plus the API key assigned by the platform | Complies with FastGPT interface authentication standards to ensure valid requests |
| `variables` | Pass `{"target_oil_type": "92#", "station_id": "BJ001"}`, supports batch passing of multiple parameters | Adapts to query requirements for ledger data classified by oil product and station, facilitating dynamic adjustment of query dimensions |
| `responseData` | Only return `transaction_time, sales_volume, unit_price` fields | Reduces invalid data transmission and adapts to the field parsing logic of downstream systems |
| Request timeout | 600 seconds | Adapts to large-volume data transmission requirements for daily batch synchronization, avoiding timeouts caused by excessive data volume |
| Number of data items per request | 1000–2000 items | Balances data transmission efficiency and interface stability, suitable for batch synchronization scenarios of refined petroleum product sales ledgers |
| Knowledge base binding parameters | Calibrated based on actual measurements | Adapts to exclusive knowledge base configuration requirements for different stations |

## Three Common Misconfigurations
- Symptom: An error indicates the knowledge base cannot be referenced when calling the interface, and returned fields are empty. Cause: The knowledge base ID is not passed through the `variables` parameter, and the knowledge base is only set as a global variable without binding the corresponding parameter in the request.
- Symptom: An error occurs when running the upgrade script, with the curl command execution failing and a status code of 400 returned. Cause: The correct `Authorization` parameter is not configured before executing the script, or the network cannot access the official FastGPT upgrade source.
- Symptom: Scheduled WeChat Work messages fail to send, with a 403 status code returned. Cause: A valid WeChat Work application credential is not included in the interface request, or the sending permission for the external group is not configured.

## How to Verify Successful Configuration
- Call the test interface, check that returned fields match the preset `responseData` parameters, and confirm data filtering takes effect.
- Pass different `variables` parameters to verify whether returned data is correctly classified by oil grade and station code.
- Simulate a batch synchronization scenario, check that interface response time meets the preset timeout configuration, and no timeout errors occur.
- Verify authentication information, initiate a request using the `Authorization` parameter, confirm that the returned status code is 200, and no authentication failure prompt appears.
