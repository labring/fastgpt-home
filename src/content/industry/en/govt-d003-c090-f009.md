# Ledger Aggregation and Report Generation for Refined Petroleum Product Sales: Model Access and Configuration

## What the Data for This Category Looks Like
Refined petroleum product sales ledger data primarily comes from gas station POS terminals, oil tank level monitoring systems, inventory management systems, and electronic invoicing systems. Systems upload single retail transaction data in real time. Daily settlement sales ledgers complete summary updates every early morning. Monthly operating ledgers generate on the first day of each month. Each ledger entry includes fields such as transaction time, oil product grade, sales volume (liters or tons), unit sales price, revenue amount, payment method, and operating station ID. All fields bind to clear units of measurement, and ledger formats for stations in different regions have minor differences.

## Constraints for Model Access and Configuration
The real-time nature and multi-data-source characteristics of refined petroleum product sales ledgers create clear constraints for model access and configuration. High-frequency updates of real-time transaction data require the model invocation chain to have low latency, and context loading and response duration must be limited. The requirement that fields bind to units means the model must accurately identify and retain units of measurement. Clear field interpretation rules must be defined in configuration. Monthly summary ledgers have large data volumes, so the model must limit processed context length and output token count to avoid exceeding capacity limits. Differences in ledger formats across multiple stations require unified field mapping before access, preventing confusion during model parsing.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | A single refined petroleum product ledger entry uses approximately 50-100 tokens. Monthly summary ledgers typically contain hundreds of entries, so this range must cover the full context |
| `maxTokens` | `4000–6000 token` | Report generation requires including summary data and analysis conclusions, so sufficient output length must be reserved |
| `temperature` | `0.1–0.3` | Ledger aggregation requires accurate data matching, and excessive divergence should be avoided |
| `AIPROXY_API_ENDPOINT` | Fill in the official access address for the corresponding model deployment | Ensures normal connectivity of the model invocation chain |
| `AIPROXY_API_TOKEN` | Fill in a valid token obtained from the model service provider | Completes identity verification and permission checks |
| `toolChoice` | `auto` | Automatic invocation of the data aggregation tool is required to complete ledger consolidation and analysis |

## Three Common Configuration Mistakes
- Forcing stream output off when configuring `toolChoice`: When invoking a locally deployed Qwen3 model, an error stating "This model only supports streaming" is returned. The cause is failure to adapt to the model’s streaming output requirements, and non-streaming invocation is force-specified.
- Incorrect configuration of `AIPROXY_API_ENDPOINT` or `AIPROXY_API_TOKEN`: When invoking a ChatTTS model deployed via Xinference, a code 500 error "Cannot read p" is returned. The cause is incorrect access address or token configuration, which prevents normal invocation of the model service.
- Failure to clearly define field unit requirements in configuration: The generated report contains mixed units, such as liters converted to tons without annotation. The cause is failure to clearly define rules for retaining original field units of measurement in the system prompt.

## How to Verify Correct Configuration
- Pass a single standard refined petroleum product ledger entry to the test interface, and check whether the model correctly identifies the oil product grade, sales volume, and corresponding unit.
- View model invocation logs in FastGPT v4.17.0, and confirm that configured values for `maxContext` and `maxTokens` have not triggered upper limits.
- Invoke the health check interface corresponding to `AIPROXY_API_ENDPOINT` to verify the validity of the token and access address.
- Pass a monthly summary ledger dataset, and check whether the generated report contains complete field information and accurate summary results.
