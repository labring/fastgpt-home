# General Contracting of Building Construction Projects: Ledger Summary and Report Generation via HTTP Interfaces and External Systems

## What the data for this category looks like
Ledger data for general contracting of building construction projects originates from three external systems: on-site construction management systems, material procurement systems, and labor management platforms. The system updates data daily with that day’s construction progress, material delivery, and labor attendance figures. A full-cycle summary ledger is generated weekly. Documents use structured tables categorized by individual construction projects. Core fields include section code, project name, material name, delivery quantity, delivery date, and construction team headcount. Corresponding units are no code identifier, name, ton, batch, and man-day, respectively.

## Constraints imposed on HTTP interfaces and external systems by these characteristics
Multi-source, heterogeneous data sources for building construction general contracting require HTTP interfaces to support parallel pulling from multiple endpoints, or batch parameters filtered by section and cycle. This prevents incomplete data coverage from single calls. Fields with non-standard units require interfaces to retain original unit mappings. Unauthorized unit conversion causes unit errors in ledger summaries. The daily update rhythm requires interface call intervals to not exceed 24 hours. Interfaces must support filtering data by construction section and statistical cycle to reduce invalid data pulls. As data volume grows with project progression, interfaces must support pagination parameters. This prevents timeouts caused by overly large single return data sets.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {FastGPT v4.17.0 platform-assigned API key}` | Ledger data for building construction projects is internal sensitive data. Standard Bearer token authentication verifies identity and ensures compliant interface access permissions |
| `variables` | `{"construction section list":["Section A","Section B"], "statistical cycle":"last 7 days"}` | Precise limitation of the ledger scope for pulling, avoids irrelevant data interfering with subsequent summary processes |
| `responseData` | Retain only the section code, material name, delivery quantity, and construction team headcount fields | Filters redundant data and speeds up ledger summary processing within FastGPT |
| Single request limit | 1000 entries | A single construction section has many ledger entries. This avoids exceeding the rate limit threshold of external system interfaces in a single request |
| Request interval setting | 60 seconds | Prevents exceeding external system interface access frequency limits from frequent calls, ensuring stable data pulling |

## Three common configuration errors
- An interface returns a 401 Unauthorized status code. Cause: Authentication parameters are not configured correctly, or an expired or unauthorized API key is used.
- Interface response data includes a large number of redundant fields, leading to excessive ledger summary time. Cause: Response data is not filtered per requirements, and unnecessary project metadata is pulled.
- The target external system port cannot be accessed normally. Logs only show the connection establishment phase. Cause: Correct target system port and access path are not configured in FastGPT, so requests cannot reach the target service.

## How to confirm correct configuration
- Call the configured HTTP interface and check if returned data includes preset core fields and data scope.
- Review FastGPT workflow run logs to confirm that interface request variable parameters correctly pass construction section and statistical cycle values.
- Verify that interface call frequency matches the preset interval setting, and no external system rate limit rules are triggered.
- Test that interface returned field formats match the structured requirements for ledger summarization.
