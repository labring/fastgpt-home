# General Contracting of Building Construction Projects: Ledger Summary and Report Generation — Multi-turn Dialogue and Prompt Engineering

Reference only; verify against the target FastGPT release and deployment documentation.

## What this category of data looks like
Ledger data for general contracting of building construction projects comes from project management systems, construction log systems, material procurement systems, and progress accounting systems. Data update cadence is daily updates for construction progress and material delivery ledgers, and weekly updates for progress payment declaration and completion settlement ledgers. Each ledger entry includes fields such as project ID, section name, material specification and model, delivery quantity, acceptance date, construction team, budget unit price, actual expenditure, and more. Units include cubic meters, tons, yuan, man-days, square meters, and others. A single summary document typically contains tens to hundreds of ledger entries.

## Constraints imposed by these characteristics on multi-turn dialogue and prompt engineering
Building construction general contracting ledgers contain multi-dimensional fields and a large number of entries. Multi-turn dialogue must retain key context such as project ID and section via `messages` to avoid confusing ledger data from different sections. Fields have diverse units, so prompts must explicitly require the large model to uniformly use specified units for output results, preventing unit mixing issues. A single summary document has many entries, so the number of recalled ledger entries per search must be limited to avoid exceeding the context window. Data is updated daily, so the knowledge base must be configured to synchronize the latest ledger data regularly, preventing the large model from using outdated information to generate reports.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Single Search Limit | 15–25 entries | A single building construction project ledger document typically contains tens to hundreds of entries. This range balances retrieval accuracy and context length |
| Query Optimization | Enabled | Ledger fields are complex and diverse; optimization improves the large model's understanding accuracy of query intent |
| Maximum Context | 8000–12000 token | Adapts to project information retained during multi-turn dialogue and multiple ledger entries, avoiding exceeding window limits |
| Knowledge Base Refresh Cycle | 1–3 AM daily | Matches the daily update cadence of ledger data, ensuring the large model uses the latest ledger content |
| Prompt Template | Must include unit requirements and field list | Ledger fields and units are diverse; explicit requirements unify output formatting |
| `variables` | Pass project ID, section | Used to lock ledger data for a specific project, avoiding confusion between different sections during multi-turn dialogue |

## Three Common Mistakes
- Symptom: An unauthorized error is returned even though an API key was passed when calling the API. Cause: The API usage permission for the corresponding application is not bound on the FastGPT platform, or the API key has expired.
- Symptom: After increasing the single search limit to 2000, the report generated by the large model does not reference any recalled ledger entries. Cause: Too many recalled entries cause context overload, and the large model cannot locate valid relevant information.
- Symptom: Results returned during multi-turn dialogue include non-essential identifier fields such as talent ID 12356. Cause: Non-essential identifiers were not removed in the knowledge base chunking configuration, or the prompt did not explicitly require hiding such fields.

## How to Verify Proper Configuration
- Initiate a query that includes a specified project ID, and confirm that the returned results only contain ledger data for the corresponding section.
- Adjust the single search limit, then check that the report output by the large model references the expected number of ledger entries.
- View the knowledge base synchronization log to confirm that the latest ledger data has completed synchronization and update.
- Switch test projects via `chatId`, and confirm that the returned ledger data automatically matches the new project identifier.
