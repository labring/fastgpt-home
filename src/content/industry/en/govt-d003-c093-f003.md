# Ledger Summary and Report Generation for Government and Enterprise IT Services: Multi-turn Dialogue and Prompts

## What this category of data entails
Ledger data for government and enterprise IT services primarily originates from internal systems including operation and maintenance tickets, service response records, and resource usage reports for telecom government and enterprise customers. Data synchronization occurs primarily on a daily basis; some urgent tickets support real-time updates. Each ledger document uses a structured format, containing fields such as ticket number, customer affiliated unit, fault type, processing duration, and completion status. Field units include hours, counts, and entries, and some fields feature multi-level classification nesting.

## What constraints these characteristics impose on multi-turn dialogue and prompts
Structured ledger fields have multi-level classifications, so field matching rules must be clearly defined during multi-turn dialogue to prevent the model from confusing classification items across different levels. Data is updated at a high frequency, so the valid time range of multi-turn dialogue context must be limited to avoid calling outdated ledger data. Each document has a large number of fields, so prompts must explicitly specify that only fields requested in the dialogue be extracted, to avoid redundant information interfering with report generation. Additionally, government and enterprise ledgers involve sensitive customer information, so non-essential sensitive fields must be filtered during multi-turn dialogue to ensure output complies with data security standards.

The following configurations are adapted for FastGPT v4.17.0.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum Context | Previous 8 turns of dialogue + most recent 7 days of ledger data | Government and enterprise ledgers are updated daily; limiting the time range avoids calling outdated data while retaining necessary historical dialogue logic |
| Single Recalled Ledger Entries | Top 5 matching ledgers | Ledger fields have complex hierarchies; limiting recalled entries avoids redundant information interfering with model field matching |
| `messages` | Truncate to 12000 tokens | Structured ledger data has many fields; an overly long `messages` will distract the model and reduce report generation accuracy |
| `variables` | Enabled | Government and enterprise ledgers have fixed-format field variables; enabling this ensures field values in reports accurately correspond to actual data |
| `chatId` | Bind to the unique identifier of the current dialogue | Ensures multi-turn dialogue context is associated with the specified ledger dataset, avoiding cross-dialogue data confusion |
| Query Optimization | Enabled | Users may repeatedly mention ledger fields during multi-turn dialogue; optimization refines core query requirements and improves recall efficiency |

## Three common misconfigurations
- Phenomenon: Significant differences between online dialogue and API call return results. Large deviations in returned content occur when the API sets `stream` to false and `detail` to true. Cause: Online dialogue retains full context cache by default, while API calls do not correctly pass the historical `messages` parameter, preventing the model from associating previously queried ledger data.
- Phenomenon: After migrating a knowledge base, the dialogue prompts that the knowledge base is empty, but all content is visible on the page. Cause: Vector indexes were not regenerated after knowledge base migration, or the new knowledge base ID was not associated in the dialogue configuration, preventing the model from reading the migrated dataset.
- Phenomenon: The reply annotation trigger timing of the workflow AI dialogue component does not match expectations, triggering either early or late. Cause: The component's trigger logic was not correctly configured. Annotation triggers depend on the signal of complete reply output; if the component-bound variable does not correctly pass the reply status, trigger timing will be abnormal.

## How to confirm the configuration is correct
- Initiate a multi-turn dialogue that includes specified ledger fields, and verify that the returned report accurately extracts the corresponding field values and units.
- Switch between online dialogue and API call modes, pass the same `messages` parameter and prompt, and verify that the returned report content is consistent across both modes.
- After migrating a knowledge base, regenerate the vector index and associate the target knowledge base in the dialogue configuration, then initiate a query to verify that the model can recall the corresponding ledger data.
- Test the annotation trigger timing of the workflow component: send a complete dialogue and observe whether the annotation executes after the reply is fully output.
