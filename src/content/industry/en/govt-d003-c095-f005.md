# Ledger Summary and Report Generation for New Energy Development: Tool Calling and Plugins

## What the data for this category looks like
Ledger data for new energy development mainly comes from station SCADA systems, grid connection acceptance archives, daily operation and maintenance logs, and inspection records. Data is aggregated by individual wind and photovoltaic stations. Core operating indicators are synchronized once daily, and complete ledger archives are updated once monthly. Each ledger document includes fields such as station unique identifier, equipment model, installed capacity, monthly power generation, operation and maintenance duration, and fault handling records. The unit of installed capacity is megawatts (MW), power generation is megawatt-hours (MWh), and operation and maintenance duration is hours.

## What constraints these characteristics impose on the "tool calling and plugins" workflow
Multi-station, multi-dimensional ledger data must be pulled in batches during tool calling. Tool configuration must support passing parameters filtered by station ID to avoid pulling redundant data. Real-time indicators updated daily and monthly archived files require differentiated calling frequencies. Tools must support setting time range parameters for single calls to adapt to different data update rhythms. Fixed fields and units require structured data returned by tools to strictly match preset field names and units. Otherwise, format confusion will occur during report generation. The character volume of a single station's monthly ledger can reach thousands. The single return limit of tool calls must adapt to this scale to avoid incomplete report generation caused by data truncation.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | auto | Adapt to multi-tool collaboration scenarios for new energy development, automatically match tools for ledger pulling and data aggregation, no manual configuration required |
| `functionCall` | Calibrated based on actual measurements | Adapt to the return format of structured fields for new energy ledgers, ensure tool output can be directly used for report generation |
| Tool call timeout | 600 seconds | New energy station data needs to be pulled across SCADA and grid connection systems; 600 seconds covers most cross-system query durations |
| Single tool return count | First 20 entries | Adapt to the pulling requirements of multi-station monthly ledgers in a single batch, avoid timeouts caused by excessive single-batch data volume |
| Tool parameter validation | Enabled | Match the validation rules for fixed fields and units of new energy ledgers, prevent invalid data from entering the report generation stage |

## Three common mistakes
- Symptom: Tool call parsing failure, console shows Tool call Parser n error. Cause: The inference model wraps thinking content in think tags and places it in the content field, which does not meet the structured return format requirements of FastGPT tool calls.
- Symptom: Cross-origin error returned when calling the api/v1/chat/completions API externally, browser console shows same-origin policy block prompt. Cause: Cross-origin allow rules for the FastGPT gateway are not configured, causing external requests to be blocked.
- Symptom: Unable to pull new energy ledger data after configuring tool calls, returns empty results with no error message. Cause: The MCP server is not deployed as an intermediate service for tool calls, making it impossible to connect to external data sources such as station SCADA systems.

## How to confirm the configuration is correct
- Initiate a single tool call request, check if the returned structured data includes the preset fields of the new energy ledger, and that field units match the station data.
- After configuring the tool call timeout, initiate a call request containing multi-station data, confirm that the request is not interrupted within the expected time.
- After enabling tool parameter validation, pass test data that does not comply with field rules, confirm that the system intercepts invalid requests and returns prompts.
- Confirm that the currently deployed FastGPT version is v4.17.0, ensure that tool call configuration rules match the version.
- When using aiproxy to forward requests, check request headers and key parameters for correct transmission via logs, with no abnormal errors.
