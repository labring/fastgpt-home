# New Energy Development Ledger Summary and Report Generation: Database and Operations Maintenance

This configuration applies to FastGPT v4.17.0.

## What This Category of Data Looks Like

New energy development ledger data comes from four sources: station operation monitoring systems, equipment maintenance ticket systems, grid connection approval archive files, and monthly power generation reports.

Data uses two update cycles. Real-time station operation parameters update every 15 minutes. Maintenance tickets and approval files update periodically per project milestones.

Each ledger document includes these core fields: unique station identifier, equipment number, operation parameter value, timestamp, and affiliated project code. Fields cover active power (unit kW), maintenance duration (unit hours), and cumulative power generation (unit MWh). Some documents include binary attachments of equipment inspection photos.

## Constraints Imposed on Database and Operations Maintenance by These Characteristics

Database connection pools must adapt to high-concurrency scenarios to support new energy development ledgers’ high-frequency real-time writes and semi-structured storage. This prevents write interruptions caused by exhausted connections.

Index commonly queried fields such as station ID and timestamp for mixed structured and unstructured data. Cross-station summary queries will experience significant delays without these indexes.

Perform regular database defragmentation. Wide variation in ledger document lengths — from tens of characters of status markers to thousands of characters of inspection records — causes storage fragmentation.

Enforce strict database access whitelisting for private network-deployed station data. This prevents unauthorized access.

## How to Set Configurations

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://<db-user>:<db-pass>@<internal-ip>:27017/energy_ledger?authSource=admin` | New energy development ledgers contain semi-structured operation records and attachments. MongoDB adapts to flexible storage of such data. Using private IP avoids public network exposure |
| `PG_URL` | `postgresql://<db-user>:<db-pass>@<internal-ip>:5432/energy_report?sslmode=require` | Structured data such as grid connection approvals and statistical reports are suitable for transactional storage with PostgreSQL. SSL mode ensures secure internal network transmission |
| `DB_MAX_LINK` | `20–30` | Each station generates hundreds of records per hour. The connection pool upper limit matches concurrent write and query requirements, preventing connection exhaustion |
| `REDIS_URL` | `redis://<internal-ip>:6379/0` | Cache frequently queried station summary data, reduces repeated database query pressure, and improves summary response speed |

## Three Common Configuration Mistakes

- Phenomenon: Database connection is refused, with error `10061 Connection refused`. Cause: The private IP of the FastGPT deployment node was not added to the database whitelist. New energy development station data is mostly deployed in private networks. Failure to configure the whitelist will block access.
- Phenomenon: Syntax error returned when executing multi-line SQL statements, with error `You have an error in your SQL syntax`. Cause: Some database connection plugins only support single-statement execution by default. Multi-line query configuration was not enabled.
- Phenomenon: Knowledge bases and agents do not display after backup recovery. Cause: Only project files were restored, and knowledge base metadata and agent configuration in the database were not synchronized for recovery. New energy development ledger data is mostly stored in independent databases. The corresponding database snapshot must be restored synchronously.

## How to Confirm Configuration Is Successful

- Run the built-in database connection test tool. Enter the configuration values for `MONGODB_URI` and `PG_URL`. Verify that a connection success prompt is returned.
- Submit a batch ledger data write request. Observe that no connection pool exhaustion errors occur, and write delay meets preset business requirements.
- Access the Redis cache address. Confirm that frequently queried station summary data has been cached. Query response time is significantly shorter than direct database queries.
- Perform a full backup recovery test. Synchronously restore project files and the corresponding database snapshot. Verify that knowledge bases and agents can load and display original data normally.

The values provided are common starting points and should be measured against the reader's own samples.
