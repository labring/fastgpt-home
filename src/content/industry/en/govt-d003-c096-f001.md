# Non-ferrous Metal Smelting: Ledger Summary and Report Generation - HTTP Interfaces and External Systems

## What the Data for This Category Looks Like
Ledger data for non-ferrous metal smelting comes from PLC collection terminals at production sites, batching control systems, quality inspection laboratory systems, and finished product warehouse management systems. Updates are synchronized after each production batch completes, or performed via bulk update every 4 hours. The document structure uses standardized structured tables, with fields including furnace number, batch number, metal grade, unit energy consumption, shift output, quality inspection pass rate, material input quantity, emission indicators, and more. Field units strictly follow smelting industry standards: grade is measured in percentage, energy consumption in tons of standard coal per ton of product, and emissions in mg/m³. No additional non-standard custom fields are included.

## What Constraints These Characteristics Impose on HTTP Interfaces and External Systems
Multi-source heterogeneous ledger data requires interfaces to support bulk pulling of specified fields from different systems, to avoid summary errors caused by mismatched data formats. Fixed fields and units require interfaces to carry field verification logic, to prevent input of non-standard units or field values. The update rhythm based on batches or every 4 hours requires that the interface polling interval not be too short, to avoid repeatedly pulling old data or exceeding system load. Single-batch data volume can reach hundreds of MB, requiring interfaces to support chunked transmission or resumable uploads, to improve data transmission stability.

| `responseData` | Only return `["furnace number", "batch number", "metal grade", "unit energy consumption", "shift output", "quality inspection pass rate"]` | Only returns the core fields required for ledger summary, reducing data transmission volume and lowering processing pressure on downstream systems |

## Three Common Misconfigurations
- The phenomenon is returning HTTP status code 401 Unauthorized, or the interface prompts authentication failure. The cause is that the `Authorization` request header is not configured correctly, or the secret does not have the Bearer prefix added, which does not meet the authentication requirements of the FastGPT API.
- The phenomenon is missing fields in the returned ledger data or data that does not match expectations. The cause is that the correct data source range or time interval is not specified via the `variables` parameter, resulting in incomplete pulled data.
- The phenomenon is interface call timeout, or returned data being truncated. The cause is that the request timeout setting is too short, which does not adapt to the transmission duration of single-batch smelting ledger data, resulting in incomplete data pulling.

## How to Confirm Proper Configuration
- After calling the interface, check that the returned HTTP status code is 200 OK, to confirm that the authentication configuration is effective.
- Check that the fields returned by `responseData` match the preset core ledger fields, to confirm that the data filtering configuration is correct.
- Compare the data volume returned by the interface with the total volume of local ledger data, to confirm that the pull range meets the requirements.
- Call the interface 3 consecutive times, check for timeouts or errors, to confirm that the retry strategy is effective.
