# Ledger Summary and Report Generation for Nuclear Power Operations: Multi-turn Dialogue and Prompt Engineering

## What this category of data looks like
Nuclear power operation ledger data comes from operation data collection systems, equipment inspection terminals, and safety supervision records. It updates once every 15 minutes to once per hour. Each individual ledger document includes fields for unique equipment identifier, collection time, core operating parameters, abnormal status, and disposal process. Parameter units include kelvin, megapascals, hours, and others. Most individual documents range from hundreds to thousands of characters. A single day’s ledger data for one equipment can form a record set of tens to hundreds of entries.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
The real-time update feature of nuclear power operation ledgers requires multi-turn dialogue to limit the context time range. This avoids referencing expired historical data. Multiple fields and specialized units require prompts to clearly specify parameter names and their corresponding units. This prevents generating summary results that do not comply with nuclear power industry standards. The relatively long length of individual documents means the context window must match the document length. It must also avoid exceeding the model’s token processing limit. Multi-turn dialogue must associate equipment identifiers with collection times. This ensures summary reports correspond to the correct equipment and time interval, and avoids mixing data across devices or time periods.

## Configuration settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| Maximum number of context entries | First 10 entries | Individual nuclear power ledger documents are relatively long. Excessive context will exceed the model’s token limit. 10 entries cover approximately one hour of continuous operating ledger data |
| `messages` parameter | Only include conversation history from the past 1 hour | Nuclear power operation data updates in real time. Expired conversations introduce outdated parameters. The 1-hour range matches the ledger update rhythm |
| `variables` parameter | Bind equipment ID and time interval | Ledger data is categorized by equipment and time. Binding variables ensures multi-turn dialogue focuses on the specified range, avoiding cross-device confusion |
| `chatId` parameter | Generate unique ID per equipment + date | Ensures multi-turn dialogue for the same equipment shares context, preventing accidental session resets |
| Prompt template | Include parameter unit descriptions | Nuclear power parameters include specialized units such as kelvin and megapascals. Prompts must explicitly require retaining units to ensure report format compliance |

## Three common mistakes
- Symptom: The workflow sets the number of chat records to 0, and multi-turn dialogue cannot retain historical context. Cause: The `messages` parameter is not used correctly to pass conversation history, so each call is treated as a brand new session.
- Symptom: The result returned after calling the interface does not match the preset equipment or time range. Cause: The `variables` parameter is not used to bind the target equipment ID and time interval, and the prompt does not clearly limit the data retrieval range.
- Symptom: After configuring 6 chat records in the workflow’s text extraction node, the summary report contains redundant non-target time period data. Cause: The real-time update feature of nuclear power ledgers is not considered. Excessive context introduces expired operating data from non-specified time periods.

## How to verify proper configuration
- Initiate a first-round dialogue that includes a specific equipment ID and time interval. Check whether the returned context includes the operating parameters of the corresponding equipment.
- Initiate a follow-up question associated with the previous query. Check whether the model can associate the equipment information and parameter requirements from the historical dialogue.
- Check whether the `chatId` parameter remains consistent across multiple calls in the same session. This ensures the context has not been accidentally reset.
- Verify that the generated summary report includes the parameter units specified in the prompt. This complies with the format standards for nuclear power ledgers.
