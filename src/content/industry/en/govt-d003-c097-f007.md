# Ledger Summary and Report Generation for Nuclear Power Operations: Database and Operations Maintenance

## What the Data for This Category Looks Like
Ledger data for nuclear power operations comes primarily from four data sources: reactor real-time operation collection systems, equipment inspection handheld terminals, radiation monitoring stations, and fuel management systems. Core ledgers are divided into three categories: real-time parameter ledgers, monthly equipment maintenance ledgers, and radiation dose ledgers. Update frequencies are divided into three categories: real-time, daily, and monthly. Each individual ledger entry includes a unique device identifier, collection timestamp, value field, working condition tag, and abnormal mark field. Value fields have dedicated units: for example, core temperature uses Kelvin, and radiation dose rate uses microsieverts per hour.

## What Constraints These Characteristics Impose on the Database and Operations Maintenance Link
High-frequency writes of real-time parameters require database connections to have low latency and high concurrency capabilities, to avoid data packet loss or delay. Bulk imports of monthly ledgers generate large-volume data transactions, so databases need to support sharded writes and transaction rollback mechanisms to prevent single-write timeouts. Specialized units for fields require the database to establish format validation rules, to avoid mixing values with different units. Nuclear power data compliance requirements mandate that all database connections use encrypted transmission, and complete operational audit logs be retained to meet data retention requirements of nuclear safety regulatory authorities. Additionally, the sensitivity of ledger data requires the database to have fine-grained permission control to restrict unauthorized access.

## How to Configure the Settings
| Configuration Item | Recommended Value | Rationale for This Value |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb+srv://<username>:<password>@<cluster-url>/nuclear_ops?ssl=true&authSource=admin` | Adapts to unstructured inspection records and radiation monitoring data; enabling SSL encryption complies with nuclear power data security compliance requirements |
| `PG_URL` | `postgresql://<username>:<password>@<database-host>:5432/nuclear_equipment?sslmode=require` | Stores structured equipment ledgers and operating parameters; enforcing SSL ensures data transmission security |
| `DB_MAX_LINK` | `20–30 connections` | Meets concurrent demands of real-time parameter writes and monthly bulk ledger imports, prevents connection pool exhaustion |
| `REDIS_URL` | `redis://:<password>@<redis-host>:6379/0` | Caches frequently queried equipment working condition tags to reduce load on primary databases |

This configuration is based on FastGPT v4.17.0.

## Three Common Misconfigurations
- Phenomenon: A 400 status code is returned when calling the FastGPT built-in database query plugin. Log fragments contain `Messages with role '`. The cause is that database connection authentication parameters are not configured correctly, causing the role information carried in the request to fail interface validation rules.
- Phenomenon: No output is returned when calling the database connection tool after local deployment of FastGPT. The cause is that `REDIS_URL` is not configured or has incorrect parameters, causing the cache layer to fail to work normally and blocking the tool call chain.
- Phenomenon: Connection timeouts occur when concurrently executing ledger summary tasks. The cause is that the `DB_MAX_LINK` setting value is smaller than the number of concurrent requests. After the connection pool is exhausted, new requests cannot obtain available connections.

## How to Confirm the Configuration Is Correct
- Run the FastGPT v4.17.0 built-in database connection test tool, verify the connectivity of `MONGODB_URI` and `PG_URL` separately, and confirm that a test success prompt is returned.
- Submit a simulated nuclear power equipment inspection ledger entry, write it to the corresponding database, then perform an exact query. Confirm that data can be read normally, and field formats and units meet expectations.
- Initiate 25 concurrent ledger query requests, confirm no connection timeouts or errors occur, and verify that the `DB_MAX_LINK` configuration adapts to concurrent demands.
- Check the Redis monitoring panel, confirm that frequently queried equipment working condition tags have been cached, and the query load on the primary database has decreased significantly.
