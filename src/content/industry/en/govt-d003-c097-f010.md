# Nuclear Power Plant Operations: Ledger Summary and Report Generation - Knowledge Base Retrieval and Recall

## What Data in This Category Looks Like
Nuclear power plant operation ledger data originates from three core systems: reactor operation monitoring systems, equipment inspection management systems, and safety verification filing systems. Update frequencies are divided into three categories: real-time updates for operation parameters, daily archiving for inspection records, and monthly filing for safety verification reports. Documents use structured formats, including fields such as unique equipment identifiers, monitoring time, physical parameters, operator numbers, and verification results. Specialized units include megawatt thermal power (MWth), megapascal (MPa), kelvin (K), and others. No generic vague expressions are used, and strict matching of specialized identifiers is required.

## Constraints Imposed on Knowledge Base Retrieval and Recall by These Characteristics
Data sources are scattered across multiple independent systems, so multiple knowledge base collections must be linked to cover complete ledger data. Specialized units and equipment identifiers require precise retrieval matching to avoid invalid results caused by unit confusion. Real-time updated operation data requires the knowledge base to support incremental synchronization, preventing the recall of expired data. Individual ledger documents are lengthy, so the number of recalled entries must be controlled to fit the large model context window. There are many structured fields, so query variants must be expanded to cover specialized terms expressed in different ways.

## How to Configure the Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Meets the precision requirement for matching nuclear power specialized terms and units, filters low-correlation generic content |
| `limit` | Top 8–12 entries | Individual ledger documents are lengthy, control the number of recalled entries to avoid exceeding the large model context window |
| `searchMode` | semantic | Matches both semantic relevance and keywords, adapts to multi-dimensional expressions of nuclear power terminology |
| `usingReRank` | Enabled | Reorders initial recall results by relevance, filters content that best fits ledger fields |
| `datasetSearchUsingExtensionQuery` | Enabled | Automatically supplements query variants such as equipment numbers and specialized units, improves recall rate for structured fields |
| `collectionIds` | Fill in according to the knowledge base collections linked to the ledgers | Links the three core ledger knowledge bases for reactor operation, equipment inspection, and safety verification |

## Three Common Misconfigurations
- Phenomenon: A fixed initialization prompt text appears automatically at the start when generating a ledger report. Cause: The default guiding reply template was not removed in the system configuration, causing redundant content to be included when the large model is called.
- Phenomenon: A single ledger summary retrieval takes longer than 60 seconds, and the number of valid ledger entries returned is lower than expected. Cause: The `limit` value is set too large, and `usingReRank` is not enabled, causing the system to load too many irrelevant documents and extending retrieval time.
- Phenomenon: The output addresses of nuclear power equipment photos and design drawings in the knowledge base are truncated, showing only part of the storage path. Cause: `datasetSearchUsingExtensionQuery` is not enabled, and complete file storage path query conditions are not automatically supplemented, resulting in only partial path information being recalled.

## How to Verify Successful Configuration
- Initiate a query containing "reactor coolant pressure", check whether the returned results include ledger data with megapascal (MPa) units, and there is no redundant initialization reply text.
- View the retrieval log, confirm that the recalled documents come from the knowledge base collections corresponding to the pre-configured `collectionIds`, with no documents from irrelevant collections.
- Compare the result sorting before and after enabling `usingReRank`, confirm that equipment inspection records with higher relevance are ranked first.
- Test a query containing a unique equipment number, confirm that the system can automatically match the corresponding ledger entry with no matching failures.
