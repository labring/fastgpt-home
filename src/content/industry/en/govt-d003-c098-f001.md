# Ledger Summary and Report Generation for Civil Aviation Airports: HTTP Interfaces and External Systems

## What this category's data looks like
Civil aviation airport ledger data comes from business subsystems including flight support, security inspection, terminal operation, and ground transportation. The data updates once every 15 minutes to once per hour. Each pushed ledger document uses a structured format, containing fields such as flight number, takeoff and landing time, passenger throughput, number of baggage items, equipment number, and operating duration. The corresponding units are flight sorties, hours and minutes, passenger trips, items, equipment ID, and hours respectively. Some ledgers are also associated with operation log files for supporting analysis in subsequent reports.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Civil aviation airport ledger data has a high update frequency and a high degree of field standardization, but includes a small number of custom extension items. This requires HTTP interfaces to support batch data reception and paginated queries. Due to strict internal authentication requirements of business systems, the interface must configure the `Authorization` parameter to complete identity verification. At the same time, some operation logs associated with ledgers need to be transmitted as files, so the interface must support form-data format file parameter submission. In addition, ledger data has high timeliness requirements, so the interface response timeout must be controlled within a reasonable range to avoid data delays affecting the overall progress of report generation.

## How to set configurations
This article is written based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
|---|---|---|
| `Authorization` | Bearer access token issued by the airport's internal system | Complies with identity authentication requirements of civil aviation internal systems to prevent unauthorized access |
| Request timeout | 30–60 seconds | Adapts to the response duration of batch ledger data retrieval, avoiding task interruption due to large data volume |
| Request body format | form-data | Supports transmission of file-type parameters, adapting to the upload requirement of log files |
| `variables` | Configure custom query conditions such as flight number and time range | Adapts to filtering requirements for different ledger types |
| `responseData` | Extract only core ledger fields | Reduces invalid data transmission and improves report generation efficiency |
| Pagination parameters | Return 100–200 entries per request | Balances interface load and data retrieval efficiency |

## Three common mistakes
- Phenomenon: After configuring form-data for the HTTP request, the file parameter cannot be sent normally, and the interface returns a 400 error. Cause: The file parameter's type was not set to file format, only the local file path was filled in.
- Phenomenon: The interface call returns a 401 unauthorized error. Cause: The `Authorization` parameter was not configured correctly, or an expired internal system token was used.
- Phenomenon: The ledger retrieval request times out, and the workflow execution fails. Cause: The request timeout was not adjusted according to the data volume, and the default timeout duration is insufficient to complete batch data retrieval.

## How to confirm the configuration is correct
- Send a test request to check whether the `responseData` returned by the interface only includes the preset core ledger fields.
- Upload a test log file to confirm that the form-data format file parameter can be normally received by the interface.
- Check whether the `Authorization` parameter matches the authentication rules of the airport's internal system, with no unauthorized error reported.
- Adjust the query conditions to confirm that the `variables` parameter can correctly filter ledger data for the corresponding time period.
