# Ledger Summary and Report Generation for Civil Aviation Airports: Vector Models and Indexing

## What the data for this category looks like
Civil aviation airport ledger data comes from multiple business systems including flight scheduling, equipment maintenance, logistics support, and safety inspection. Data update cycles include real-time synchronization (such as real-time flight takeoff and landing records) and daily batch synchronization (such as monthly maintenance ledger summaries). Each single document contains structured parameters and semi-structured descriptions, with fields including flight number, takeoff and landing time, equipment number, fault type, maintenance duration, and consumable usage. Some fields have dedicated units such as sorties, hours, and unit counts. Document lengths vary significantly, ranging from just a few lines of parameter entries to dozens of pages of complete maintenance reports.

## What constraints these characteristics impose on the vector models and indexing link
Multi-source heterogeneous data sources require indexes to support unified mapping of cross-system fields to avoid semantic confusion. Mixed real-time and batch update cycles require indexes to have incremental construction capabilities, so that the latest ledger data can be synchronized without full reconstruction each time. The diversity of fields and units requires vector modeling to retain field semantic features, preventing incorrect association of similar data with different units. Significant differences in document length require flexible chunking strategies to adapt to the encoding needs of short parameter entries and long maintenance reports.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to the average length of single civil aviation airport ledger records, avoiding semantic breaks |
| Overlap Length | 100–200 characters | Retains contextual association between chunks, preventing loss of cross-block information |
| Similarity Threshold | 0.75–0.85 | Matches the semantic similarity of ledger records, filtering invalid duplicate entries |
| `maxToken` | 4096 | Adapts to the input length limit of mainstream embedding models, ensuring complete encoding of long maintenance records |
| Single Search Limit | Top 10 entries | Covers the retrieval needs of single-batch ledger summaries, avoiding redundant results |
| `defaultToken` | Calibrated via actual testing | Adapts to the default token allocation rules of different embedding models, ensuring index construction stability |

## Three common configuration mistakes
- A 503 error appears after starting the container, prompting that no available embedding model channel is available. The cause is that the CHAT_API_KEY environment variable is not configured correctly, or the channel permissions for the corresponding embedding model are not bound in the FastGPT backend.
- The number of retrieval results is abnormally small after index construction. The cause is that the chunk length is set too large, leading to semantic loss after long ledger records are truncated, making it impossible to match retrieval keywords.
- Index updates cannot be triggered after editing the knowledge base. The cause is that the incremental index switch is not enabled, or the synchronization operation is not performed on the knowledge base content page. Index reconstruction is not triggered after directly modifying content.

## How to confirm the configuration is correct
- Enter the knowledge base management page of FastGPT v4.17.0, view the index construction log, and confirm that there are no field mapping failure or token overrun error messages.
- Enter a typical ledger retrieval keyword, and check that the number of returned results and the similarity threshold matching meet expectations.
- Modify the content of one ledger record, wait for the index synchronization to complete, and perform retrieval again to confirm that the results have been updated.
- View the embedding model call log, and confirm that the `defaultToken` and `maxToken` configuration parameters are loaded correctly.

The values provided are common starting points and should be measured against the reader's own samples.
