# Ledger Summary and Report Generation for Civil Aviation Airports: Multi-turn Dialogue and Prompt Engineering

## What the Data for This Category Looks Like
Ledger data for civil aviation airports comes from sources including flight scheduling systems, security control systems, ground operations and maintenance systems, passenger service systems, and others.
Data updates are triggered by business nodes. Ledgers related to flight takeoffs and landings are updated in real time. Equipment maintenance ledgers are summarized and archived daily.
Each ledger document includes fields such as flight number, takeoff and landing time, passenger capacity, equipment number, maintenance duration, and safety inspection items. Units include sorties, passenger trips, minutes, and equipment counts, among others. Field associations cover the entire business chain of operations, safety, and service.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
Multi-source heterogeneous ledger data creates requirements for context differentiation. Multi-turn dialogue must clearly distinguish ledger contexts across different business categories such as flight operations, safety inspections, and equipment maintenance, to avoid mixing cross-category data.
Real-time updated flight-related ledgers require prompts to define a time window for data queries, ensuring that the latest records for the current period are retrieved.
The multi-field ledger structure requires prompts to clearly specify field mapping rules, to prevent unit or field correspondence errors when generating reports.
For ledger data with full-chain associations, multi-turn dialogue must retain context from previous business links, ensuring subsequent questions can build on the already defined business scope.

## Three Common Configuration Errors
- A MySQL tool call returns a 400 status code with no response body. The cause is failing to explicitly specify ledger data field mapping rules in the prompt, resulting in tool call parameter formats that do not meet database query requirements.
- After publishing a login-free link, deleting conversation content also clears the background operation logs. The cause is failing to configure independent storage rules for conversation logs, mistakenly binding conversation context and operation logs as the same storage object.
- Workflows cannot load historical global variables in new conversations. The cause is failing to enable the cross-session retention switch for global variables in conversation configuration, resulting in variable context being reset for each new conversation.

## How to Verify Proper Configuration
- Initiate a flight ledger query, verify that returned fields match the preset ledger fields, confirming context retention rules are active.
- Trigger a tool call, check that the returned response format matches expected database query results, confirming parameter mapping configuration is correct.
- After publishing a login-free link, delete a test conversation, check that background operation logs are not cleared synchronously, confirming independent log storage configuration.
- Initiate a cross-session ledger query, verify that historical global variables load normally, confirming the cross-session retention switch is enabled.
- Check that the conversation context bound to `chatId` is not incorrectly cleared, and that historical conversation content stored in `messages` is complete.
