# Ledger Aggregation and Report Generation for Civil Aviation Airports: Database and Operations

## What this category's data looks like
Civil aviation airport ledger data originates from business modules including flight scheduling systems, passenger service systems, ground support systems, facility inspection systems, and others. Data update cadence is divided by business nodes: real-time data such as flight takeoffs and landings and passenger passage is written immediately after operations complete, while batch data such as daily summary ledgers is fully updated each early morning. A single ledger document includes fields such as business identifier, timestamp, associated entity, quantitative metrics, and exception status. Units for quantitative metrics vary by type, such as takeoff and landing sorties, passenger trips, inspection duration, and equipment operating hours.

## What constraints these characteristics impose on database and operations workflows
Format differences across multiple data sources require the database to support mixed storage of structured and unstructured data, while adapting to field mapping rules from different systems. Business data with varying update frequencies creates concurrent peaks; real-time write requests during flight takeoff and landing peak periods consume a large number of database connections, so connection pool thresholds must be properly configured. Ledger data relates to airport operational compliance, requiring complete retention of operation logs and historical data, which sets clear requirements for database persistence and backup mechanisms. Additionally, ledger queries often perform batch statistics by time range and associated entity, so targeted index creation is needed to optimize query efficiency.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://username:password@host:port/airport_ledger?authSource=admin` | Stores unstructured ledger attachments and real-time business data for civil aviation airports, specifies the authentication source to ensure access permission compliance |
| `PG_URL` | `postgresql://username:password@host:port/airport_report?schema=public` | Stores aggregated report metadata, classification tags, and associated ledger indexes, supports multi-table join queries |
| `DB_MAX_LINK` | `200–300` | Handles concurrent write and query requests during flight takeoff and landing peak periods, prevents database connection exhaustion |
| `REDIS_URL` | `redis://:password@host:port/0` | Caches daily ledger aggregation results from high-frequency queries, reduces repeated computational load on the database |
| Database Index Configuration | Create joint indexes based on timestamp, flight number, and operation type | Accelerates ledger queries by time period and associated entity, adapts to batch statistical requirements for report generation |

## Three Common Misconfigurations
- Issue: FastGPT deployed via Docker displays a connection timeout error several minutes after connecting to MongoDB, with logs showing `connection closed`. Cause: No reasonable threshold is configured for `DB_MAX_LINK`; connections are not automatically recycled after being exhausted during peak periods, leading to subsequent connection request failures.
- Issue: An error occurs when saving a newly created question classification node; operations return to normal after switching the AI model. Cause: Database connection pool timeout parameters are not properly configured; batch database query operations during AI model invocation time out, and switching the model temporarily bypasses the connection pool bottleneck.
- Issue: In FastGPT v4.17.0, after updating the knowledge base configuration, ledger report generation still calls old data. Cause: Redis cache expiration policy is not configured; old ledger cache is not refreshed in a timely manner, causing report generation to read outdated data from the cache.

## How to Verify Proper Configuration
- Execute a database read-write test script, use `MONGODB_URI` and `PG_URL` to write test ledger records and read them for verification, confirming that connection permissions are normal.
- Initiate more than 100 concurrent ledger query requests, observe that the database connection count does not exceed the `DB_MAX_LINK` configuration threshold, and no connection error logs are generated.
- Trigger a ledger aggregation task, verify that after the Redis cache is updated, new report generation can obtain the latest ledger data.
- Check database index logs, confirm that joint indexes have been created as configured, and query latency meets business expectations.
