# Ledger Summary and Report Generation for Civil Aviation Airports: Deployment and Upgrade

## What data in this category includes
Civil aviation airport ledger data comes from airport operation management systems (AODB), ground dispatch systems, security and boarding data systems, passenger service systems, and other sources. Data update frequencies fall into three categories:
- Real-time: For flight takeoff/landing, gate assignment, and similar events
- Daily: For same-day operation summary ledgers
- Monthly: For monthly support statistics ledgers

Documents are split into two types: structured ledgers and unstructured support records. Structured fields include flight number, scheduled takeoff/landing time, actual takeoff/landing time, gate number, passenger count, support duration, and more. Units are hours and minutes, passenger count, and minutes, respectively. Unstructured documents are electronic or handwritten support team records, mostly in PDF or TXT formats.

## What constraints these characteristics impose during deployment and upgrade
Multi-source system access requires configuring multiple storage endpoints and permission rules during deployment, to adapt to data formats from different systems. Real-time updated data has high database concurrency requirements. Connection pool parameters must be adjusted to avoid request queuing. Mixed structured and unstructured documents require separate parsing rule configurations to ensure accurate field extraction. During upgrades, running real-time synchronization tasks must not be interrupted, to prevent ledger data loss. Civil aviation data security compliance rules require aligning platform configuration with the enterprise’s internal permission system, to avoid data leaks.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 100–150 connections | Adapts to concurrent requests from multiple real-time data access systems at civil aviation airports, avoiding database connection exhaustion |
| `MONGODB_URI` | Intranet connection string for the airport-specific MongoDB instance | Stores structured ledger data and parsed vector indexes, ensuring data isolation and access security |
| `STORAGE_S3_ENDPOINT` | Access endpoint for the airport’s internal object storage | Stores unstructured support record documents, adapting to intranet low-latency access requirements |
| `REDIS_URL` | Address of the airport’s intranet Redis cluster | Caches real-time flight data and session status, reducing repeated database query pressure |
| `FILE_TOKEN_KEY` | Airport-specific encryption key | Encrypts access tokens for ledger files, complying with civil aviation data security compliance requirements |
| `ROOT_KEY` | Configured per state-owned enterprise internal permission rules | Manages super permissions for the FastGPT platform, adapting to enterprise-level account systems |

## Three common configuration mistakes
- Symptom: After deploying FastGPT v4.17.0 via Docker, uploading ledger files for parsing produces continuous `slow operation xxxxms` logs, with high MongoDB response latency. Cause: The `DB_MAX_LINK` parameter was not adjusted, and the database connection pool configuration was too low, leading to queuing and blocking of concurrent data requests.
- Symptom: Some core fields are empty in synchronized ledger data. Cause: Generic field mapping rules were used during configuration, without matching the dedicated field naming specifications for civil aviation airport ledgers, so key information cannot be correctly extracted.
- Symptom: Real-time flight ledger synchronization tasks fail after platform upgrade. Cause: The Redis cache synchronization task was not paused prior to upgrade, causing data write conflicts and inconsistent cache and database states.

## How to verify correct configuration
- Log in to the FastGPT backend system monitoring panel, check the database connection status, and confirm the current connection count does not exceed the `DB_MAX_LINK` configuration limit.
- Upload a standard civil aviation airport operation ledger file, trigger the parsing task, and verify the parsed field list fully matches the airport’s standard ledger fields.
- Initiate a real-time flight data synchronization task, confirm the task completes within 5 minutes with no error logs.
- Test access permissions for `STORAGE_S3_ENDPOINT`, confirm that unstructured support record documents can be uploaded and read normally.
