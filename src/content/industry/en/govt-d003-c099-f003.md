# Oil and Gas Exploration and Development: Ledger Summary and Report Generation — Multi-turn Dialogue and Prompt Engineering

## What the Data for This Category Looks Like
Ledger data for oil and gas exploration and development comes primarily from seismic interpretation results and well logging reports during the exploration phase, plus daily production reports, monthly development statements, and well test analysis documents during the development phase. Full updates run when a single well is put into production, while incremental updates use daily production data for routine operations.
Document structures include structured ledger tables and accompanying unstructured attachments. A single structured ledger typically contains dozens of parameter rows, with fields covering well location coordinates, well depth, porosity, permeability, daily oil production, water cut, and more. Most units use meters, cubic meters, tons, and percentages. Accompanying unstructured attachments can reach tens of thousands of characters in text length, and include well logging images and professional analysis notes.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
The mixed structured and unstructured data structure requires clear communication of the current well ID and time interval being processed during multi-turn dialogue, to avoid mixing data from different batches. The multi-field, multi-unit parameter system requires prompt engineering to enforce unit validation rules, preventing the model from confusing measurement standards for different parameters. The incremental update data source characteristic requires retaining core identifiers of the current job in the dialogue context, to avoid misuse of data across cycles. Long document attachments require limiting context tokens per single call, preventing the model from exceeding its processing limit and ensuring generated summary reports match original data.

## Three Common Misconfigurations
- Issue: An error returns when calling after configuring an API token. OneAPI logs show the token field is set to "fastgpt". Cause: The dedicated API token was not correctly bound, and the platform's generic identifier was mistakenly entered into the token configuration field.
- Issue: Context rounds become disordered when the same conversation identifier is accessed multiple times. Cause: The unique job identifier was not bound via `chatId`, and unisolated conversation history was reused across different calls.
- Issue: Submitting a summary request for long ledger data results in an incomplete generated result or a token overflow error. Cause: The number of retained rounds for `messages` and the context length were not limited, resulting in the passed context exceeding the model's processing limit.

## How to Confirm Successful Configuration
- Initiate a query request for a single well ledger, and check that the dialogue context only contains relevant interactions for the current well ID, with no residual irrelevant historical data.
- Review call logs to confirm that the passed API token exactly matches the configured item, with no generic platform identifiers included.
- Submit a ledger summary request containing multiple fields, and check that the generated result clearly labels the units and field definitions for the corresponding parameters.
- Initiate queries for the same well ID multiple times using the same `chatId`, and confirm that the context retention rules comply with the preset round limits.
