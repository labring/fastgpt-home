# Ledger Summary and Report Generation for Oil and Gas Exploration and Development: Workflow Orchestration

This document is compatible with FastGPT v4.17.0.

## What the data for this category looks like
Ledger data for oil and gas exploration and development comes from drilling operation systems, logging interpretation platforms, and well test databases. A full update triggers after a single well operation completes. Daily inspection data syncs in daily batches. The document structure splits into structured ledger fields and unstructured attachments.
Structured fields include well ID, well depth, core section length, and formation pressure. Units are none, meters, meters, and megapascals, respectively.
Unstructured attachments include on-site operation photos, core scans, well test report PDFs, and similar files. The size of individual attachments varies significantly.

## Constraints Imposed on Workflow Orchestration by These Characteristics
Structured fields for drilling and logging data are numerous and have fixed units. Workflows must clearly define field mapping rules in `variables` to avoid summary errors from mismatched field names.
Single-well data update rhythms vary widely. Workflows must support both scheduled triggering and event triggering modes to fit daily batch synchronization and immediate updates after project completion.
Unstructured attachment sizes vary greatly. Some core scans reach hundreds of megabytes. Workflow nodes must limit the total size of attachments processed in one run to avoid timeouts.
Multi-source data must associate by well ID. Workflow orchestration must include an association verification node to prevent cross-well data confusion.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Bind well ID, well depth, formation pressure, core section length | Match core structured fields of oil and gas exploration ledgers to ensure the order and completeness of summarized data |
| `nodeId` | Assign a unique identifier to the association verification node | Enable quick location of abnormal links during workflow debugging |
| Total attachment size per run | No more than 400–600 MB, calibrated based on actual measurements | Adapt to common size ranges of core scans and operation logs to avoid node timeouts |
| Trigger mode | Run scheduled triggering and event triggering in parallel | Cover scenarios of daily batch synchronization and immediate updates after single well completion |
| Node timeout threshold | 600 seconds | Adapt to processing durations of multi-field summarization and large attachment reading |
| Knowledge base association configuration | Bind a dedicated knowledge base for oil and gas exploration and development | Provide standardized terminology and industry reference documents for report generation |

## Three Common Configuration Mistakes
- Calling a published workflow via an external API returns empty fields. This occurs when the externally passed well ID parameter is not configured in `variables`, preventing the workflow from locating the corresponding ledger data.
- No clear document filtering rules are specified when configuring knowledge base variable references. This happens when association between knowledge base documents and well ID is not specified, leading to search results that do not match the current ledger.
- Workflow node timeout triggering fails. This occurs when the timeout threshold is not adjusted based on attachment size; the reading duration of large core scans exceeds the default setting.

## How to Verify Successful Configuration
- Manually pass a test well ID, check whether the structured data returned by the workflow node includes preset fields.
- Upload a single simulated attachment, verify whether the file reading result after node processing is complete.
- Trigger a scheduled task and a manual event trigger, confirm that the workflow starts normally under both modes.
- Check workflow logs, confirm that no duplicate data error occurs in the association verification node corresponding to `nodeId`.

The values provided are common starting points and should be measured against the reader's own samples.
