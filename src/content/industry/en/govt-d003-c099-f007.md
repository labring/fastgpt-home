# Ledger Summary and Report Generation for Oil and Gas Exploration and Development: Database and Operations

## What this category of data looks like
Ledger data for oil and gas exploration and development comes from multiple types of business outputs, including drilling operation records, well logging analysis reports, oil test documentation, reserve calculation forms, and more. Updates are triggered by individual well project milestones, with bulk updates during the completion phase and weekly incremental syncs for daily well dynamics. Each ledger document includes professional fields such as well ID, well depth, formation, lithology, porosity, and permeability, with units of meters, %, %, and millidarcys respectively. Some documents include scanned attachment files. Data formats include structured tables and unstructured text, with significant variation in single-document length.

## What constraints these characteristics impose on database and operations
Multi-source heterogeneous data sources require the database to support both structured data storage and unstructured document indexing, which increases operational complexity. The coexistence of bulk updates per project milestones and daily incremental syncs requires database connection pools to handle sudden high-concurrency write requests, avoiding connection exhaustion. Precise query requirements for professional fields require creating dedicated indexes for core fields such as porosity and permeability; otherwise, full table scans will drastically reduce query efficiency. Storage and retrieval of long documents require the database to adapt to large-field storage, avoiding data truncation or retrieval errors.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://[username:password@]host1:port1,host2:port2/[authSource=admin]` | Supports distributed storage of multi-source structured ledgers for oil and gas exploration and development, adapts to bulk data imports |
| `PG_URL` | `postgresql://user:pass@host:port/dbname?sslmode=require` | Stores metadata for unstructured documents and professional field indexes, ensures precise queries |
| `DB_MAX_LINK` | `200–300` | Handles peak bulk data imports during the completion phase, avoids connection exhaustion |
| `REDIS_URL` | `redis://:password@host:port/0` | Caches statistical results of professional fields from high-frequency queries and session contexts, reduces database load |
| Question Optimization | Enabled, calibrate rounds based on actual measurements | Adapts to context association for long ledger documents, avoids off-topic responses during consecutive questions |
| Maximum Context | Set to twice the length of a single ledger document | Covers complete business context, ensures semantic coherence for multi-turn queries |

## Three common misconfigurations
- Phenomenon: After multiple consecutive questions, subsequent questions fail to associate context, resulting in off-topic responses. Cause: `REDIS_URL` is not configured to cache session data, or `DB_MAX_LINK` is set too low, causing session data to be cleared prematurely.
- Phenomenon: The database returns a connection timeout error (status code 504) when bulk importing single-well ledger data. Cause: The value of `DB_MAX_LINK` is smaller than the number of concurrent import connection requests, so the connection pool cannot allocate sufficient resources.
- Phenomenon: Queries for professional fields take too long, and the interface shows loading timeout. Cause: Dedicated indexes are not created for core fields such as porosity and permeability, so the database performs full table scans.
