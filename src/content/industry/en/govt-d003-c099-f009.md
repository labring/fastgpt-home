# Ledger Summary and Report Generation for Oil and Gas Exploration and Development: Model Access and Configuration

## What the data for this category looks like
Oil and gas exploration and development ledger data primarily comes from exploration well site files, original logging data, oil test analysis reports, development dynamic monitoring reports, and other sources. Single-well ledgers are updated per completion cycle, while regional development summary ledgers are updated monthly or quarterly. Documents include structured fields and unstructured attachments. Structured fields include well ID, well depth (unit: meters), daily oil production (unit: cubic meters), formation pressure (unit: megapascals), and more. Single-well documents are typically dozens of pages long, while regional summary documents can reach hundreds of pages.

## What constraints these characteristics impose on the model access and configuration workflow
The structured nature of the data varies widely, including both standardized table fields and semi-structured analysis text. This requires models to adapt to mixed-format inputs, so context length parameters must be set appropriately. Frequently updated data sources require call frequencies to match the update rhythm to avoid exceeding API call limits. Specialized fields and units require models to have accurate domain knowledge, so overly high randomness parameters should not be set. The high proportion of long documents also requires adjustments to maximum context and output token limits.

## How to Set Configurations
| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the long document splicing requirements of single-well and regional summary ledgers. FastGPT v4.17.0 supports context configuration within this range |
| `maxTokens` | 2000–3000 token | Ensures the output length of generated reports meets the full content requirements of ledger summaries |
| `temperature` | 0.3–0.5 | Reduces generation randomness to ensure accurate identification of fields such as well IDs and specialized units |
| `AIPROXY_API_ENDPOINT` | Exclusive node address assigned by the platform | Adapts to compliance transmission requirements for oil and gas exploration data, avoiding cross-region access restrictions |
| `AIPROXY_API_TOKEN` | Key bound with exclusive permissions | Limits call scope to prevent unauthorized access to sensitive exploration and development data |
| `toolChoice` | auto | Automatically selects appropriate tools to process structured tables and unstructured text, improving summary efficiency |

## Three Common Configuration Mistakes
- Error prompt: "No available channel for model whisper-1 under the default group". Cause: The speech recognition model is not bound to the corresponding group, or the configured model name does not match the name registered on the platform.
- Sustained API calls triggered at night leading to balance depletion. Cause: No call frequency limit configured for scheduled tasks, or the data source synchronization script does not set a reasonable interval, resulting in high-frequency repeated calls.
- Unit identification errors appear in generated reports, such as identifying "cubic meters" as "tons". Cause: The temperature parameter is set too high, leading to excessive randomness in model generation content and ignoring specialized unit rules for the oil and gas sector.

## How to Confirm Configurations Are Properly Set
- Upload single-well ledgers and regional summary documents to initiate a test call, and check whether the returned logs include accurate structured fields such as well IDs and well depths.
- Check API call logs to confirm that call frequencies meet the preset interval requirements, with no records of abnormal high-frequency triggers.
- Verify that the generated report format matches the preset ledger summary template, with no obvious field misalignment or unit errors.
- Test different types of data sources, including logging data and oil test reports, to confirm that the `toolChoice` automatic adaptation function works properly.

The values provided are common starting points and should be evaluated against in-house samples.
