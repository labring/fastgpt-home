# Oil and Gas Exploration and Development: Ledger Summary and Report Generation - Deployment and Upgrade

## What This Category of Data Looks Like
Data for oil and gas exploration and development ledgers comes from drilling operation logging systems, well logging analysis platforms, and formation test databases. Updates are generated either upon completion of individual well operation nodes or via daily batch aggregation. Document structures include core fields such as well identification, operating depth, lithology classification, physical property parameters, and fluid production volume. Field units include meters, tons, cubic meters, and others. The length of individual ledger documents expands gradually as operation phases progress.

## Constraints on Deployment and Upgrade
The multi-source dispersed nature, wide range of individual document lengths, and ongoing expansion of ledger data during oil and gas exploration and development impose multiple constraints on deployment and upgrade.
Multi-source data integration requires pre-configuring connection parameters compatible with different databases during deployment to avoid data synchronization interruptions.
The large size of individual documents requires adjusting database connection pool parameters to ensure stability during batch ledger reading.
The batch update rhythm requires supporting incremental deployment during upgrades to avoid full restarts interrupting ongoing summary tasks.
Sensitive operational data contained in ledgers requires strictly configuring access key-related parameters during deployment to strengthen data permission control.

## Configuration Settings
The following configurations apply to FastGPT v4.17.0, and meet the deployment and upgrade requirements for oil and gas exploration and development ledgers:

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `10–20 connections` | Meets concurrency requirements for batch reading of oil and gas exploration and development ledgers, and prevents connection pool exhaustion |
| `REDIS_URL` | Cached node address determined through actual testing | Stores large volumes of ledger metadata and summary intermediate results to reduce repeated database query pressure |
| `STORAGE_S3_ENDPOINT` | Access address corresponding to enterprise internal object storage | Stores large ledger documents and generated report files, ensuring localized data storage |
| `ROOT_KEY` | Random string with at least 16 characters of complexity | Controls highest-privilege platform access, meeting data security requirements for state-owned enterprises and public-sector entities |
| `FILE_TOKEN_KEY` | Encryption key independent of `ROOT_KEY` | Generates sharing tokens for ledger reports, separating permission levels |
| `FE_DOMAIN` | Internal enterprise access domain name or IP:8080 | Configures valid access paths for the workspace and sharing links |

## Three Common Misconfigurations
- Attempting to configure multiple API keys in docker-compose.yml causes the platform to fail calling services in preset model combinations. Not following the platform's required array format for key variable configuration, only adding a single key entry leads to configuration parsing exceptions.
- After restarting a Windows host, password-free sharing links generated by the FastGPT workspace cannot be accessed, with the page prompting that the resource does not exist. Not configuring `FE_DOMAIN` as a fixed local access address causes Docker container restarts to assign temporary port changes, rendering the originally linked ports invalid.
- Batch summary of large oil and gas exploration and development ledgers frequently triggers timeout errors, with logs showing connection pool exhaustion. Not adjusting the `DB_MAX_LINK` value based on ledger data volume causes the default connection count to be insufficient to support concurrent batch reading requirements.

## How to Verify Successful Configuration
- Log in to the platform backend, view the database connection status panel, confirm that the data sources corresponding to the configured `MONGODB_URI` and `PG_URL` have normal connections and no persistent errors.
- Upload a test oil and gas exploration and development ledger document, trigger a summary task, and check that the generated report includes all preset core fields with no abnormal missing data.
- Generate a password-free sharing link, restart the deployment environment, and access the link to confirm that the page loads normally and does not require repeated login verification.
- View the platform runtime logs, confirm that the storage service corresponding to the configured `STORAGE_S3_ENDPOINT` can normally read and write ledger and report files, with no permission or connection errors.

The values provided are common starting points and should be measured against the reader's own samples.
