# Oilfield Engineering Service Ledger Summary and Report Generation: Vector Models and Indexes

## What This Type of Data Looks Like
Oilfield engineering service ledger data primarily comes from on-site construction daily reports, equipment inspection records, material requisition documents, safety check ledgers, and construction logs. The system updates data daily per construction node. Each document contains structured fields: construction team number, equipment model, material usage (units: tons, cubic meters, hours), and inspection time. It also includes unstructured content: on-site working condition descriptions and hidden danger rectification records. Document fields have high fixity, with some fields using fixed enumeration values. The character count per single document varies widely.

## Constraints for Vector Models and Indexing
High proportions of structured fields with fixed enumeration values mean no vector indexes are required for enumeration fields. Exact matching can be used directly to filter data, reducing computational load on the vector database. Numeric fields such as material usage have clear units. General vector models may confuse the association between values and their units, so separate vectorization rules for numeric fields are required. Data updated per construction node requires incremental updates. An incremental indexing workflow that supports resuming from breakpoints is needed, to avoid resource consumption from full reindexing. Unstructured construction logs have wide character count ranges. Flexible chunking boundary rules are needed to prevent key working condition descriptions from being truncated.

## Configuration Settings
This page’s configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Adapts to the character count range of oilfield construction logs, avoids chunks that are too long or too short |
| Overlap Length | 100–200 characters | Preserves contextual connections between adjacent chunks, prevents loss of break point information in construction workflows |
| Similarity Threshold | 0.75–0.85 | Meets exact matching requirements for enumeration fields such as equipment numbers and hidden danger levels, avoids mismatches |
| `defaultToken` | 600 seconds | Configures the timeout period for vector indexing, adapts to batch data processing for incremental updates |
| `maxToken` | 4096 | Adapts to the input length limit of mainstream embedding models, avoids text truncation |
| Single Search Limit | Top 10 entries | Balances recall efficiency and batch query requirements for ledger data |

## Three Common Configuration Mistakes
- Symptom: Vector indexing tasks remain in a queued state with no progress in a Docker deployment environment. Cause: No reasonable timeout configured for `defaultToken`, leading to automatic termination of batch incremental indexing tasks by the system.
- Symptom: Unit-mismatched material usage data appears in vector recall results. Cause: No separate vectorization rules configured for numeric fields. General vector models confuse the association between values and their units.
- Symptom: Key information is missing from index results for long-text construction logs. Cause: Improper chunk length setting leads to truncation of long text and loss of core working condition descriptions.

## How to Verify Proper Configuration
- Check vector indexing task logs to confirm incremental updates only process new construction ledger data, and do not perform full reindexing.
- Randomly select a construction log document, and verify that chunked vector data retains complete contextual connections with no abnormal truncation.
- Test recall results for numeric fields, and confirm that matching results only associate business data with matching units, with no cross-unit mismatches.
- Verify the vector indexing timeout configuration, and confirm that task execution durations fall within the preset reasonable range with no forced interruptions.

Note: The configuration values provided are common starting points. Adjustments should be made based on specific samples and use cases.
