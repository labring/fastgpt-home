# Oilfield Engineering Services Ledger Aggregation and Report Generation: Database and Operations

## What this category of data looks like
Oilfield engineering service ledger data comes from on-site construction terminals, equipment operation and maintenance systems, and job scheduling platforms. A single ledger is generated after each individual well job is completed. Batch collaborative projects complete aggregated updates on a weekly basis. A single ledger document includes fields such as job number, equipment model, operation period, pressure parameters, consumable usage, and team information. Field units are uniformly MPa, hours, tons, cubic meters, and similar units. A single document typically contains 800 to 1500 characters, while batch aggregated documents can reach tens of thousands of characters.

## What constraints do these characteristics impose on the database and operations workflow
Ledger data from multiple terminals has format differences. This requires the database to support mixed writing of structured and semi-structured data to avoid field parsing errors caused by format differences. Weekly aggregated batch documents have large volume, so reasonable sharding rules must be configured to avoid single-node storage overload. Fields with specific units require the database to enable strict type validation to prevent non-standard unit values from being written, which would cause errors in subsequent report generation. High-frequency single-job writes and weekly batch aggregations coexist. The database must balance low-latency writes and high-throughput batch query capabilities. A backup strategy must also be formulated to match the update rhythm.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://admin:pass@db-host:27017/oilfield_fastgpt?replicaSet=rs0&authSource=admin` | Oilfield engineering ledgers require storage of semi-structured job data and conversation history. Replica set configuration ensures write availability, and specifying the database name isolates business data |
| `PG_URL` | `postgresql://admin:pass@pg-host:5432/oilfield_report` | Stores structured aggregated report metadata, supports complex statistical queries, and meets the performance requirements of batch aggregation |
| `DB_MAX_LINK` | `20-30` | Balances the concurrent demands of high-frequency single-job writes and weekly batch aggregations, and prevents database resource exhaustion caused by excessive connection counts |
| `REDIS_URL` | `redis://:pass@redis-host:6379/0` | Used to cache frequently queried job ledger indexes, reducing database query pressure and speeding up report generation |

## Three common mistakes
- Symptom: Database connection failure after migration deployment, with an error indicating the storage path is inaccessible. Cause: No persistent storage volume configured for the oilfield ledger database, resulting in data loss or unreadability after deployment restart.
- Symptom: MongoDB service fails to start with an error that the replica set is not initialized, preventing deployment completion. Cause: The replica set configuration that ensures concurrent writes was accidentally removed, failing to match the multi-terminal write requirements of oilfield engineering services.
- Symptom: No results returned when querying job ledgers or conversation history. Cause: The database namespace in `MONGODB_URI` was not configured correctly, resulting in data being written to an unspecified database instance.

## How to confirm the configuration is correct
- Use the FastGPT v4.17.0 deployment tool to run a database connection test, verify the connection status of `MONGODB_URI`, `PG_URL`, and `REDIS_URL`. No errors meet the basic requirements.
- Import a standard oilfield job ledger document, check whether the corresponding record is generated in the database, and that the field units match the original data.
- Simulate 10 single-job writes and 1 batch aggregation query, observe the database connection pool usage. No connection exhaustion prompts indicate a reasonable configuration.
- Check the backup script execution logs to confirm that daily incremental backups and weekly full backups are completed as scheduled.
