# Oilfield Engineering Services Ledger Summary and Report Generation: Knowledge Base Retrieval and Recall

## What the data for this category looks like
Ledger data for oilfield engineering services comes from on-site construction recorders, project ERP systems, and daily inspection reports. Data is synchronized once daily. Each document is a complete ledger for a single well’s single operation, including fields such as construction date, well ID, operation type, material usage, on-site personnel information, and acceptance conclusion. Well IDs use a fixed format combining letters and numbers. Material usage is measured in cubic meters and tons. Personnel information includes employee ID and name. Most individual documents range from 500 to 1200 characters. This configuration guide is based on FastGPT v4.17.0.

## What constraints do these characteristics impose on the knowledge base retrieval and recall link?
Oilfield engineering service ledger data creates multiple constraints for the retrieval and recall process. The fixed well ID format requires retrieval to support a combination of exact field matching and semantic retrieval, to avoid recall bias caused by well ID input errors. Individual document lengths vary widely. Long ledgers require proper splitting to maintain retrieval accuracy, while total character count of batch-recalled documents must be controlled to stay within context window limits. Daily updated real-time data requires the retrieval pipeline to support high-frequency knowledge base synchronization, and prioritize recalling construction ledgers from the past 7 days to ensure report generation timeliness. Diverse material usage units require associating unit fields during retrieval, to avoid result bias from semantic confusion.

## How to set the configurations
| Config Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` | `0.72–0.80` | High field precision is required for oilfield ledgers. This range filters low-correlation results while retaining valid recall entries |
| `limit` | `Top 8 entries` | Single ledger lengths vary widely. 8 entries balance recall quantity and context window usage, adapting to content needs for report generation |
| `searchMode` | `Semantic Retrieval` | Oilfield ledgers contain many technical terms. Semantic retrieval matches unstructured fields such as operation type and material usage, aligning with business scenarios |
| `usingReRank` | `Enabled` | Long documents split after processing may have scattered semantics. Reranking improves ranking of high-correlation entries and optimizes content priority for report generation |
| `datasetSearchUsingExtensionQuery` | `Disabled` | Ledger data has a fixed structure. No additional query expansion is needed, which avoids introducing irrelevant retrieval results |
| `collectionIds` | `Bind dedicated knowledge base collection for oilfield engineering services` | Isolate ledger data from different business lines, avoid cross-category retrieval interference, and ensure retrieval accuracy |

## Three common configuration errors
- Phenomenon: Retrieval time exceeds 60 seconds after consecutive questions in the same conversation window, and normal performance resumes when asking in a new window. Cause: No limit is set on historical information carried in conversation context, so each retrieval carries excessive redundant context, increasing processing load on the retrieval pipeline.
- Phenomenon: Semantic retrieval recall entries have extremely high similarity scores, but content does not match actual query requirements. Cause: The `usingReRank` reranking link is not configured, or the similarity threshold is set improperly. This results in only retaining literal matching entries while ignoring valid content with semantic relevance.
- Phenomenon: Retrieval results include ledgers not related to oilfield engineering services. Cause: No dedicated knowledge base collection is bound via `collectionIds`, so the retrieval scope covers documents from other business lines, leading to result confusion.

## How to confirm the configuration is correct

- Launch 3 or more consecutive similar queries, confirm there is no abnormal fluctuation in single retrieval time.
- Modify the `similarity` parameter range, verify that recall result correlation changes logically with parameter adjustments per business requirements.
