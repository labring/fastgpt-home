# Port and Shipping Ledger Summary and Report Generation: HTTP Interfaces and External Systems

## What the data for this category looks like
Port and shipping ledger data primarily comes from port operation management systems, vessel scheduling systems, freight forwarding systems, and customs declaration systems. Data is updated per voyage or daily batch. Individual ledger entries include fields such as voyage number, vessel name, total cargo loaded and unloaded (tons), operation start and end times, berth number, cargo category, number of containers (TEU), and some ledgers include loading and unloading operation photos or manifest files. Data is output in structured JSON or CSV format, with fixed field units tightly bound to port operation specifications, and no redundant fields.

## What constraints these characteristics impose on HTTP interfaces and external systems
The multi-source, heterogeneous nature of port shipping ledger data requires interfaces to support multiple authentication methods, including token authentication and signature verification. Fixed field units require interface requests to clearly specify field mapping rules to avoid unit conversion errors. Large data volumes updated per voyage or batch require support for pagination request parameters to prevent single-request timeouts. Some ledgers include binary file stream attachments, so interfaces must support receiving and parsing both structured data and binary streams.

## How to set up configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setup | Rationale |
| --- | --- | --- |
| Request header authentication | Configure the `Authorization` header as `Bearer {port system token}`, or configure custom signature parameters as required by the system | Adapt to secure access requirements for state-owned enterprise port systems, and comply with network access specifications |
| Response data format | Set `responseData` to `auto`, and enable both JSON structured data and binary stream receiving modes | Cover receiving needs for basic ledger fields and attachment files |
| Pagination parameters | Set the number of items returned per request to `100–200 items`, and pass the pagination offset dynamically via `variables` | Adapt to batch data volumes of port ledgers, and avoid single-request timeouts |
| Response field filtering | Only request preset core ledger fields | Reduce data transmission volume and improve interface response speed |
| Interface timeout | Set to `600 seconds` | Adapt to batch data return delays for port system interfaces |

## Three common mistakes
- Issue: When an HTTP interface returns a binary file stream, the attachment cannot be parsed correctly after reception. Cause: Binary response receiving mode is not enabled, and only JSON format data is processed by default.
- Issue: Calling the port ledger interface returns empty data, and logs show authentication failure. Cause: The `Authorization` header is not configured correctly, or the token has expired and has not been dynamically updated via `variables`.
- Issue: Units are displayed incorrectly in the generated ledger report, such as tons shown as cubic meters. Cause: Field unit mapping is not specified in the request parameters, and the original unit value returned by the interface is used directly.

## How to confirm correct configuration
- Send a test request to the target port system interface, and check that the returned JSON structure matches the preset ledger fields.
- Verify that `Authorization` header authentication succeeds, with a returned status code of 200.
- Simulate a batch ledger data request, confirm that pagination parameters take effect, and the number of returned data items matches the preset range.
- Test a ledger request that includes attachments, confirm that binary file streams can be received and parsed correctly.

The values provided are common starting points and should be measured against the reader's own samples.
