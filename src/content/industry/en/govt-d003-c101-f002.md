# Port and Shipping Ledger Summary and Report Generation: Vector Models and Indexes

## What this type of data looks like
Port and shipping ledger data is sourced from port production scheduling systems, ship agency systems, customs clearance systems, and port operation records. Three update frequencies apply:
Ship berthing ledgers are updated in real time.
Loading and unloading operation ledgers are updated upon completion of each batch of operations.
Yard statistics ledgers are updated via daily summary.
Documents exist as structured tables or database tables. Core fields include ship identification number, berth number, container throughput (unit: TEU), operation start and end time, yard block number, tugboat operation duration (unit: hours), and cargo category code. Some supporting scanned files are paper operation confirmation slips.

## What constraints do these characteristics impose on vector models and indexing
The multi-source update frequency of port and shipping ledgers requires indexes to support parallel incremental and full updates. This avoids index conflicts between high-frequency real-time data and low-frequency summary data.
There are many structured fields with clear business units. Vector models must adapt to vectorization conversion of mixed-type data. This prevents numerical units from interfering with business semantic association.
Single ledger entries are short in length, but total data volume is large. Index sharding must balance high-frequency writing and batch retrieval. It must also retain associated indexes for core business fields such as ship number and operation time. This ensures fast filtering by business dimension during retrieval.

## How to set configurations
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to the typical length of single port ledger operation records, avoids splitting core business fields |
| Overlap Length | 100–180 characters | Retains associated business information across adjacent chunks, ensures complete matching of operation links during retrieval |
| Similarity Threshold | 0.72–0.82 | Filters low-correlation entries, improves the accuracy of summary reports |
| Single Search Limit | Top 15 entries | Balances retrieval performance and coverage of ledger summaries |
| `defaultToken` | 3584 token | Adapts to the context length of single-batch ledger retrieval, complies with FastGPT v4.17.0 context length limits |
| `maxToken` | 7168 token | Supports generation of complete reports containing multi-period ledger summaries |

## Three Common Misconfigurations
- Symptom: Index tasks remain in "pending" or "processing" status for a long time, with no progress logs output. Cause: Incremental index rules are not configured for batch updates of port ledgers. Full index scans all historical data, resulting in excessive time consumption.
- Symptom: Retrieval results have semantic deviations, and cannot match associated ledger entries for the same ship and berth. Cause: The Alibaba Tongyi Qianwen emb3 model is not used for data vectorization. General vectorization models cannot adapt to the semantic features of port business fields.
- Symptom: Generated summary reports contain a large number of irrelevant operation records, and the number of results exceeds expectations. Cause: Retrieval result reordering and filtering are not enabled, or a reasonable similarity threshold is not set, resulting in low-correlation entries being included in the summary scope.

## How to Confirm Correct Configuration
- Check the progress logs of index tasks. Confirm that incremental indexes only process ledger data with update times later than the last index. No records of full repeated scans exist.
- Test query statements that include ship number and operation time. Confirm that all returned results are ledger entries within the corresponding business scope.
- Check the vector model configuration items. Confirm that the vectorization engine adapted to port business is specified. No incorrectly configured model parameters exist.
- Verify the single search limit configuration. Confirm that the number of retrieved entries meets the preset business coverage requirements.

The values given are common starting points and should be measured against the reader's own samples.
