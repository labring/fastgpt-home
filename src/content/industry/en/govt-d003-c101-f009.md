# Ledger Summary and Report Generation for Port and Shipping: Model Access and Configuration

## What the data for this category looks like
Port and shipping ledger data originates primarily from vessel berthing and departure scheduling systems, container terminal operation systems, cargo customs clearance management platforms, and similar tools. Data is generated in real time per operation node, with thousands of individual ledger records created daily. Individual ledger documents include structured fields such as vessel name, voyage number, berth number, container handling volume (TEU), berthing time, departure time, cargo type, and customs clearance status. Monthly summary reports include multiple pages of detailed tables and statistical items, with units including TEU, tons, hours, days, and others.

## Constraints imposed on model access and configuration
Port and shipping ledgers have many structured fields, high per-document token consumption, and fast data update rates. Model access and configuration must align with these characteristics.
1. A single ledger typically consumes between 3000 and 8000 tokens. Set limits on context and output token counts to avoid overflow.
2. Real-time data updates occur per operation node. The context refresh rule for model calls must match this update rhythm.
3. Monthly summary reports include multiple pages of structured tables. Adjust parameter configurations to support long-text processing.
4. Many structured numerical fields appear in ledgers. The model's tool call configuration must support accurate field extraction and numerical verification.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `maxContext` | `8000–12000 token` | A single port ledger summary document typically consumes between 3000 and 8000 tokens. This setting reserves enough space to hold context from multiple ledgers |
| `maxTokens` | `2000–3000 token` | Report generation requires complete output of summary results and analysis to avoid mid-process truncation |
| `toolChoice` | `auto` | Ledgers include structured fields and natural language descriptions. Automatic tool selection improves field extraction accuracy |
| `temperature` | `0.2–0.4` | Ledger summary requires consistent data accuracy. Avoid overly high randomness |
| `AIPROXY_API_ENDPOINT` | Domestic compliant node address | Port data must comply with domestic data security and compliance requirements. Prioritize proxy nodes deployed within the country |
| `AIPROXY_API_TOKEN` | Exclusive token configured per enterprise security policy | Ensure API call security and prevent unauthorized access |

## Three Common Errors
- Symptom: After a custom application's model configuration is saved as Qwen Plus, chat responses use GPT-4o instead. The model identifier displayed in the interface does not match the configured setting. Cause: Following the FastGPT v4.17.0 version update, global default model configurations have higher priority than application-specific custom configurations. Application-bound dedicated model settings are not properly retained.
- Symptom: After a port monthly ledger PDF is uploaded using the Marker tool, the task queue shows processing time exceeding 30 minutes, which is far longer than for standard documents. Cause: Port ledgers include multiple pages of structured container handling tables and complex formatting. Marker requires multiple stages of OCR and table reconstruction, leading to significantly increased parsing overhead.
- Symptom: After multiple port ledgers are batch imported, model calls return an error stating "context length exceeded". Cause: The `maxContext` parameter is not adjusted based on the actual token consumption of port ledgers. Using the generic default value directly causes context overflow.

## How to Confirm Correct Configuration
- A review of the application's model binding configuration page confirms the selected model matches the configured `AIPROXY_API_TOKEN` and `AIPROXY_API_ENDPOINT` parameters.
- Uploading a single typical port ledger document triggers a model call. The returned report is checked for inclusion of all preset ledger fields.
- Batch importing 3 to 5 ledgers of the same type allows observation of model call response times. Alignment with expected business processing speeds is confirmed.
- A review of system logs confirms the absence of error messages such as "context overflow" or "API call failure".

The values given are common starting points and should be measured against the reader's own samples.
