# Port and Shipping Ledger Aggregation and Report Generation: Deployment and Upgrade

## What data for this category looks like
Data used for port and shipping ledger aggregation and report generation primarily comes from three system types: port operation management systems, vessel scheduling platforms, and customs declaration portals. Data updates trigger per single voyage or at fixed daily intervals. The ledger for a single voyage includes full-process records such as vessel berthing, cargo loading and unloading, and container scheduling. Document structures use mostly structured fields, including dedicated fields like vessel name, IMO number, cargo loading/unloading volume, berthing time, berth number, and TEU count. Some files include semi-structured operation photos and scheduling instruction attachments.

## What constraints these characteristics impose on deployment and upgrades
The multi-source access, high-frequency updates, and dedicated field traits of port shipping ledger data create multiple constraints for deployment and upgrade workflows. Multi-source heterogeneous data requires configuring multiple storage connections to match the interface formats of different systems. Access permissions for data sources must be planned ahead during deployment. High-frequency updated operation data needs database connection pool configurations adapted for high-concurrency scenarios. Compatibility with original connection parameters must be maintained during upgrades. Metadata for dedicated fields must be retained during knowledge base parsing. When upgrading knowledge base plugins, ensure field mapping rules are not overwritten. Additionally, compliance requirements for port data mandate configuring local compliant storage media during deployment to avoid cross-region data transmission risks.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://port_admin:secure_pass@internal-mongo:27017/port_ledger?authSource=admin` | Port ledger data is mostly semi-structured operation records, and MongoDB adapts to storage requirements for non-fixed fields |
| `DB_MAX_LINK` | `200–300` | Port data has a high update frequency, and concurrent connection requirements exceed general scenarios, calibrated based on actual measurements |
| `STORAGE_S3_ENDPOINT` | `http://internal-s3.port.com:9000` | Port operation data must be stored on local compliant storage media to avoid cross-region data transmission risks |
| `REDIS_URL` | `redis://:redis_pass@internal-redis:6379/0` | High-frequency updated ledger caching requires low-latency key-value storage to support real-time aggregation needs |
| `FILE_TOKEN_KEY` | `Randomly generated 32-bit encrypted string` | Port operation files must prevent unauthorized access to secure sensitive operation data |

## Three common mistakes
- Symptom: After deploying FastGPT v4.17.0 via Docker, parsing port container ledger files produces continuous `slow operation xxxxms` logs, and MongoDB response delay increases. Cause: The `DB_MAX_LINK` parameter was not adjusted, and concurrent connection count is insufficient to support write requests for high-frequency operation data.
- Symptom: When configuring data sources in the knowledge base management interface, customs declaration ledger data cannot be pulled. Cause: `STORAGE_S3_ENDPOINT` was not correctly set to point to the port's internal compliant storage, leading to cross-system data pulls being blocked by security policies.
- Symptom: After updating vessel berthing ledgers, the generated aggregation report does not display the latest operation data. Cause: The caching logic was not adjusted to match the port data update frequency, so old cache fails to expire in time, and the report reads historical data from the cache.

## How to confirm the configuration is complete
- Run the `docker logs fastgpt` command to check for logs of database connection timeouts or storage service errors.
- Upload a CSV file of port container ledgers to confirm parsed fields fully include dedicated fields such as vessel name, cargo loading/unloading volume, and TEU count.
- Trigger a ledger aggregation task, wait for task completion, then check if the generated report includes the latest operation data.
- Access the domain configured in `FE_DOMAIN` to confirm the knowledge base management interface loads normally and associates with configured data sources.

The values provided are common starting points and should be measured against the reader's own samples.
