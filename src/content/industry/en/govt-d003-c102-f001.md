# Ledger Summary and Report Generation for Refinery and Chemical Production: HTTP Interfaces and External Systems

## What the data for this use case looks like
Refinery and chemical production ledger data originates from distributed control systems (DCS), tank farm metering systems, and laboratory information management systems (LIMS). Two update rhythms are used: real-time single-parameter push and hourly batch data synchronization. A single ledger document includes device code, material name, operating parameters (flow rate, temperature, pressure), laboratory indicators, shift identifier, and creation time. Field units include m³/h, ℃, MPa, t, and other standard units. There are no nested complex hierarchies, and the length of a single data entry typically falls between 200 and 500 characters.

## Constraints Imposed on HTTP Interfaces and External Systems by These Characteristics
Real-time parameter push requirements require interfaces to support short-connection high-frequency calls to avoid data delays. Hourly batch data synchronization requirements require interfaces to support batch data reception and paginated returns to prevent single-transmission overload. Structured fixed fields require interface request bodies to strictly match preset fields to avoid parsing failures caused by missing fields. Unified unit identifiers require interfaces to carry unit information when receiving or returning data to prevent cross-system unit conversion errors. Multi-device ledger summary scenarios require interfaces to support data filtering by dimensions such as device code and shift to improve summary efficiency.

## Three Common Configuration Mistakes
- Phenomenon: The interface returns structured JSON format after a call. Cause: No text extraction rule is specified in the response configuration, and the original interface's structured data is returned directly.
- Phenomenon: Some device parameter fields are empty after ledger summary. Cause: No device code parameter for the corresponding device is configured in the request variables, causing the interface to fail to match the corresponding data.
- Phenomenon: The indexing time of QA split file collections created via the OpenAPI interface is too long. Cause: No batch request limit is configured, and the number of documents submitted in a single request exceeds the interface's processing capacity.

## How to Verify a Successful Configuration
- Initiate a single ledger data synchronization request, check that the interface returns a response status code of 200.
- View the FastGPT knowledge base index logs to confirm that the created QA split file collection is generating indexes at the expected progress.
- Call the summary interface to check that the returned ledger data fields match the field structure of the source system.
- Simulate concurrent requests for multiple devices to confirm that no timeout errors occur on the interface.
