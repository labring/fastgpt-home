# Ledger Summary and Report Generation for Refinery and Chemical Production: Vector Models and Indexes

## What Data Looks Like for This Category
Refinery and chemical production ledger data primarily comes from equipment distributed control systems (DCS), tank farm monitoring systems, laboratory reports, and production dispatch logs. Key process parameters refresh in real time. Daily dispatch ledgers are generated each day, and monthly summary ledgers are archived in bulk each month.

Each individual ledger includes parameters such as equipment number, operation time, pressure, temperature, and liquid level, with professional units including ppm, m³, and MPa. Monthly ledgers are structured tables, and a single document can be dozens of pages long.

## Constraints for Vector Models and Indexing
The layered update schedule and structured nature of refinery and chemical production ledgers create three constraints for the vector models and indexing workflow.
First, real-time parameters and monthly archived data have different hot and cold storage properties. Indexing must support tiered storage to optimize retrieval efficiency.
Second, specialized fields and units are present in the data. Chunking processes must retain field metadata to avoid semantic loss from generic chunking.
Third, single monthly ledgers have large data volumes and tightly linked parameters. Chunking processes must split data by equipment or time. This prevents breaks in cross-chunk parameter association, which would harm the logical accuracy of subsequent report generation.

## Configuration Settings
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Refinery ledgers have dense parameters. Too long a chunk breaks process logic association for a single piece of equipment. Too short a chunk loses context information |
| Overlap Length | 100–150 characters | Retains process parameter associations between adjacent chunks, avoiding parameter breaks during cross-chunk retrieval |
| Similarity Threshold | 0.75–0.85 | Refinery process parameters have strong correlation. Low-match irrelevant ledger data must be filtered out |
| Single Search Limit | Top 8 entries | Matches operation records for multiple associated pieces of equipment, avoiding recall of excessive redundant data |
| `defaultToken` | 4096 | Adapts to the context length of single-batch ledger retrieval, complying with input limits of mainstream embedding models |
| `maxToken` | 8192 | Supports complete vector generation for long documents, covering all data in monthly summary ledgers |

## Three Common Misconfigurations
- Phenomenon: A 503 error is returned after deployment. Logs show the specified embedding model has no available channels. Cause: The vector model channel was not configured separately. The default model node integrated with OneAPI was called, and no dedicated model configuration was added in FastGPT vector settings.
- Phenomenon: The model still fails to load properly after modifying environment variables such as CHAT_API_KEY. Cause: The FastGPT container was not rebuilt or restarted after modifying the configuration. The new configuration was not read by the system.
- Phenomenon: Retrieved ledgers include parameters from multiple unrelated pieces of equipment. Cause: Chunking was not split by equipment number or timestamp. This results in mixed semantics in a single chunk and reduced matching accuracy.

## How to Confirm Proper Configuration
- Navigate to the vector model management page in FastGPT v4.17.0. Check if configured embedding model channels show a normal available status.
- Upload a test refinery monthly ledger document. Run a vector index construction task, and confirm the task completes normally with no error logs.
- Enter a targeted test query. Verify that recall results include ledger data for the corresponding equipment, with no irrelevant redundant content.
- View the storage usage of the vector index. Confirm it meets the total size requirements of the current ledger data.
