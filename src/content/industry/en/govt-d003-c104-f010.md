# Coal Chemical Industry Ledger Summary and Report Generation: Knowledge Base Retrieval and Recall

## What this category of data looks like
Coal chemical industry ledger data comes from real-time operation records of each production workshop, raw material feeding slips, product quality inspection reports, and monthly summary reports. The update rhythm falls into three categories: workshop-level operation ledgers are updated daily, monthly consumption and production ledgers are updated monthly, and annual compliance reports are updated annually. A single ledger document includes fields such as workshop name, timestamp, equipment number, operation parameters (temperature, pressure, flow rate), raw material usage, product output, and abnormal situation records. Parameter units are fixed as professional industrial units such as degrees Celsius, megapascals, cubic meters per hour, and tons.

## What constraints these characteristics impose on knowledge base retrieval and recall
The multi-field precise parameters and fixed unit requirements of coal chemical industry ledgers require that knowledge base retrieval enable exact match mode to avoid fuzzy matching introducing entries with unit errors or parameter mismatches. Ledger data with multiple update frequencies requires retrieval to support filtering by timestamp, and the knowledge base must be configured with an incremental update mechanism to prevent old data from being mixed into current summary tasks. Single ledger documents are long and associated with multiple workshops, requiring retrieved entries to support aggregation by workshop and timestamp to avoid fragmented data affecting report generation coherence.

## How to set configurations
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Coal chemical industry ledgers have high precision requirements for parameters. Filter out irrelevant entries with low matching scores to avoid incorrect data in summary results |
| `limit` | Top 10–15 entries | Cover ledger data associated with multiple workshops, ensuring the summary report can obtain sufficient associated parameters |
| `searchMode` | Exact match mode | Match professional parameters with fixed units, avoid unit or field errors caused by fuzzy matching |
| `usingReRank` | Enabled | Rearrange retrieved ledger entries by workshop and timestamp, prioritize returning associated data from the same production batch |
| `datasetSearchUsingExtensionQuery` | Enabled | Cover synonyms of coal chemical industry professional terms, such as "gasifier" and "gasification reactor", to improve recall coverage |
| `collectionIds` | Fill in the ID of the corresponding coal chemical industry ledger dataset | Limit the retrieval scope, avoid mixing in knowledge base data of other categories, and ensure accurate retrieval results |

## Three common errors
- Phenomenon: The reply generated by the API call does not reference ledger content in the knowledge base, only returning generic answers. Cause: The `collectionIds` configuration for limiting the retrieval scope is not set correctly, or the global switch for knowledge base retrieval is not enabled.
- Phenomenon: The retrieval results include old ledger data beyond the query time range. Cause: No retrieval rule for filtering by timestamp is set, or the incremental update task is not executed correctly, resulting in old data remaining in the knowledge base.
- Phenomenon: The ledger parameter units returned by retrieval do not match the query requirements, such as matching "megapascals" to entries labeled "kilopascals". Cause: `searchMode` is set to fuzzy match mode, and exact field matching is not enabled, resulting in matching parameters with incorrect units.

## How to confirm the configuration is correct
- Initiate a query for the ledger of a specific workshop on the current day, check whether the timestamps of the returned results fully match the query conditions.
- Call the API to view the metadata of the retrieval results, confirm that the `similarity` score is within the preset 0.75–0.85 range.
- Compare the retrieval results before and after enabling `usingReRank`, confirm that the rearranged results prioritize recalling associated entries from the same workshop and time.
- View the update log of the knowledge base dataset, confirm that the newly generated ledger documents have been correctly indexed.

The values provided here are common starting points and should be measured against the reader's own samples.
