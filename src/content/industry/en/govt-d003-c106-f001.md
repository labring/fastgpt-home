# Coal Power Integration: Ledger Summary and Report Generation - HTTP Interfaces and External Systems

## What this category of data looks like
Coal power integration ledger data comes from underground fully mechanized mining data collection terminals, coal-fired power unit DCS control systems, coal yard intelligent inventory systems, and environmental protection online monitoring devices. Data updates follow two schedules: real-time collection and daily summary. Single-device operating parameters for production links are updated every 15 minutes. A complete snapshot of the full mine and full unit comprehensive ledger is generated every early morning. Each ledger document includes fields such as coal extraction volume, coal calorific value sent to the furnace, power generation load, and flue gas emission concentration, with units of tons, kilocalories/kilogram, megawatts, and milligrams/cubic meter respectively. Fields are linked in production flow order to form a time-series data chain.

## What constraints these characteristics impose on HTTP interfaces and external systems
The high-frequency updates of real-time production parameters require HTTP interfaces to support short-interval polling. The response time of a single request must adapt to the 15-minute update cycle to avoid data lag affecting ledger summary efficiency. The requirement for batch pulling of full daily snapshots requires the interface to support filtering data by date range, to avoid returning redundant non-target time period data. The structure with multiple fields and specific units requires the `responseData` returned by the interface to fully retain the original field names and unit identifiers, without unauthorized simplification or conversion. In addition, most external docking systems for coal power integration projects are business systems deployed on enterprise internal networks. The interface must adapt to internal network security authentication rules to ensure compliance of data transmission.

## Configuration Settings
| Configuration Item | Recommended Value | Basis for This Setting |
| --- | --- | --- |
| Interface timeout period | 600 seconds | Adapts to the pull duration of full ledger snapshots, avoids request interruptions due to large data volume, and complies with the timeout configuration specifications of FastGPT v4.17.0 |
| Authentication method | Bearer Token bound to enterprise internal network key | Complies with security and compliance requirements of state-owned enterprise systems, and is consistent with the standard configuration logic of the `Authorization` parameter |
| Data pull frequency | Once every 10 minutes | Matches the update rhythm of real-time production data, balances data timeliness and the load pressure of external systems |

| Variable replacement configuration | Bind ledger date and unit number variables | Adapts to ledger query requirements for multiple units and multiple time periods, and matches the mapping rules of the `variables` parameter |
| Request method restriction | Only enable GET and POST methods | Disable request types not required for business, improving the security and compliance of the interface |

## Three Common Misconfigurations
- Phenomenon: Variables can be correctly inserted during workflow debugging via text concatenation, but variable content is not replaced when calling via API. Cause: The ledger-related variables to be replaced are not correctly configured in the `variables` parameter of the API request, causing the interface to not execute the variable mapping logic.
- Phenomenon: The document link returned by the HTTP interface only includes the domain name and path, without carrying the `http://` or `https://` protocol header. Cause: The external system's interface configuration does not add the protocol field when splicing links, causing the client to fail to recognize the complete access address.
- Phenomenon: External security scans prompt that the interface supports TRACE requests, posing a data leakage risk. Cause: The HTTP interface does not disable non-business-essential request methods, and does not restrict only request types that meet the business scenario.

## How to Verify Correct Configuration
- Call the test interface, check whether the fields returned by `responseData` include the core parameters of the ledger and their corresponding units, and confirm that the data structure is consistent with the expected ledger format.
- View the interface request logs, confirm that the `Authorization` parameter is correctly carried according to the configuration, and no authentication failure status codes appear.
- After adjusting the data pull frequency, compare the update time of real-time production data with the latest data time returned by the interface, and confirm that the matching degree meets business requirements.
- Trigger a batch pull request by date range, check whether the number of returned documents matches the number of ledgers in the specified time period, and confirm that the filtering logic takes effect.
