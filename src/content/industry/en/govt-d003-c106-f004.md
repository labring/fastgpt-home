# Coal-fired Power Integration: Ledger Aggregation and Report Generation — Workflow Orchestration

## What This Category of Data Looks Like
Coal-fired power integration ledger data originates from coal mining shift ledgers, power plant operation logs, fuel incoming plant quality inspection records, and environmental monitoring systems. Data update rhythms follow multiple tiers: mining and operation parameters are updated per shift, fuel settlement data is updated per calendar day, and environmental monitoring data is updated hourly. Each individual ledger document includes fields such as equipment code, operation time, core parameters, and exception tags. Core parameter units include kilocalories per kilogram, kilowatt-hours, milligrams per cubic meter, and others. No unified fixed format template exists, and extraction must be split by business module.

## Constraints Imposed on Workflow Orchestration by These Characteristics
Multi-source heterogeneous data sources require multiple independent data pull nodes to be configured in the workflow, to interface with coal mine, power plant, fuel, and environmental protection systems respectively. Differences in update rhythms across data sources require the workflow’s scheduled trigger node to support polling for data at varying cycles, to avoid repeated pulls or missed updated content. Inconsistent field units require embedding a parameter conversion step within the workflow to align units for identical parameters from different sources. Unfixed format ledger documents require the workflow to support dynamic configuration of report module order and content filling rules. ## How to Set the Configuration
| Configuration Item | Suggested Setting | Rationale |
| ---- | ---- | ---- |
| Scheduled trigger cycle | Configure by data source type: set shift data to `8 hours`, settlement data to `1 calendar day` | Match the shift update rhythm of coal mining and power plant operations, and the daily update rhythm of fuel settlement |
| `variables` | Bind core ledger fields such as in-furnace coal calorific value, power generation, and pollutant concentration as global variables | Adapt to unified calling of multi-source heterogeneous data, avoid repeated field extraction |
| `nodeId` | Assign unique identifiers to data pull, parameter conversion, and report generation nodes | Facilitate workflow debugging and quick location of abnormal nodes |
| Prompt template configuration | Write by report module, reserve placeholders for corresponding global variables | Adapt dynamic content filling for unfixed format ledgers |
| Exception retry count | Set to `2 times` | Address occasional failures in interface pulls or large model calls |
| Parameter conversion rules | Configure per unit alignment requirements, for example, unify calorific value from different sources to kilocalories per kilogram | Resolve inconsistent units across multi-source data |

## Three Common Misconfigurations
- Workflow runs produce empty ledger data fields. Log review confirms the `variables` parameter was not correctly bound. The root cause is that fields extracted from the data source were not mapped to global variables, preventing subsequent nodes from calling corresponding data.
- Global variables cannot be called during prompt configuration, with the interface displaying an undefined variable prompt. The root cause is that required global variables were not declared in the workflow’s variable configuration node in advance, or placeholder formats do not meet system requirements.
- The workflow returns the `chat:LLM_model_response_empty` error after triggering, with an empty large model response. The root cause is that no exception retry mechanism was configured, or the trigger node’s timeout setting was too short, causing the large model call to be interrupted before completion.

## How to Confirm the Configuration Is Complete
- Manually trigger the workflow once, review output logs for each data pull node to confirm successful extraction of ledger fields from the corresponding data source.
- Access the `variables` parameter configuration page to confirm all required ledger fields are correctly bound as global variables, with placeholders matching the prompt template.
- Simulate a large model call failure scenario to verify that the abnormal retry node triggers retries as configured, and confirm that error logs correctly locate the abnormal node’s `nodeId`.
- Review the workflow’s running history records to confirm the scheduled trigger node executes per the preset cycle, with no duplicate or missed running entries.
