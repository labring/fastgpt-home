# Coal Mine Production Ledger Summary and Report Generation: HTTP Interfaces and External Systems

## What the data for this category looks like
Coal mine production ledger data comes from underground IoT monitoring sensors, ground production scheduling systems, equipment operation and maintenance ledger modules, and safety inspection record systems. Data update frequencies vary by type: real-time operating parameters update every 15 minutes, daily operation and maintenance records are archived daily, and monthly summary ledgers are generated per natural month. Documents use structured formatting, with core fields including device ID, operating duration, ventilation volume, inspection date, hidden danger level, and rectification status. Corresponding units are none, hours, cubic meters per minute, date, level, and boolean value, with no redundant additional fields. This page is written based on FastGPT v4.17.0.

## Constraints on HTTP Interfaces and External Systems
Dispersed data sources require connecting to HTTP interfaces from multiple heterogeneous systems. Each interface has unique authentication rules and response formats, so request parameters must be configured individually. The short update interval for real-time data requires matching interface call frequency to avoid data lag or repeated pulls. Fixed core fields and units require explicitly specifying return fields in interface requests, to prevent redundant data from disrupting ledger summary logic. Monthly summary ledgers have large data volumes, so single interface calls should not return too many records. Pagination parameters must be used to control system load. Additionally, coal mine production data is sensitive state-owned assets data. Interface transmission must comply with state-owned enterprise security specifications, and authentication and encryption configurations must meet strict compliance requirements.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `Authorization` | Bearer {state-owned enterprise unified API key} | Coal mine production data is sensitive state-owned assets data; standard Bearer token authentication aligns with state-owned enterprise interface security specifications |
| `variables` | `{"device_type": "underground_pump", "time_range": "last_7_days"}` | Specifies the device type and time range for data pulls, adapting to batch pulls and filtering needs for ledger summaries |
| `responseData` | Return only the `device_id, run_hours, gas_concentration, inspection_date` fields | Filters redundant data, reduces interface transmission load, and matches the core field requirements of ledger summaries |
| Interface timeout | 15-60 seconds (real-time data interfaces), 300-600 seconds (monthly summary interfaces) | Interfaces with different update frequencies have large variations in response durations; this range avoids timeouts or excessive waiting periods |
| Pagination count | 100-200 records per page | Monthly ledger data volumes are large; pagination reduces single-interface load and improves call stability |

## Three Common Configuration Errors
- Symptom: The Set-Cookie field in the response header returned after calling the interface cannot be extracted, and no cookie information appears in `responseData`. Cause: Cookie persistence is not enabled in the HTTP request configuration; FastGPT does not automatically capture Set-Cookie fields in response headers by default.
- Symptom: Calling the create application interface returns a 401 unauthorized status code, and the interface call fails. Cause: The `Authorization` parameter is not configured correctly, and the key format does not meet state-owned enterprise API authentication requirements.
- Symptom: Third-party systems cannot display images uploaded to the knowledge base after calling, and the returned image links cannot be accessed directly. Cause: The image links generated by FastGPT are not configured to allow cross-domain access, and correct access permission headers are not included in the interface response.

## How to Verify Successful Configuration
- Call the test interface, and check if the returned `responseData` includes the preset core fields with no redundant data.
- Confirm the `Authorization` parameter is configured correctly, then call the interface and verify a 200 status code is returned with no authentication failure prompts.
- Simulate a third-party system call, and verify that the returned image links can be accessed normally with no cross-domain or permission issues.
- For monthly summary data, call the pagination interface and confirm the number of returned records matches the preset pagination count, with no data truncation or loss.
