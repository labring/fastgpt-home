# Coal Mine Production Ledger Summary and Report Generation: Workflow Orchestration

## What the data for this category looks like
Coal mine production ledger data comes from underground distributed sensors, ground dispatching management systems, equipment operation and maintenance logs, and safety inspection reports. Data update frequencies fall into three categories: real-time updates (such as gas concentration, equipment operating status), shift handover, and daily summary. Individual ledger documents use a structured format, containing fields like equipment number, operating duration, coal output, inspection personnel, and detection indicator values. Supported units include tons, hours, ppm, cubic meters, and others.

## Constraints on workflow orchestration from these data characteristics
High-frequency real-time sensor data updates require workflows to support both scheduled triggering and event triggering modes, to avoid delays from manual triggering.
Inconsistent fields across multi-source structured data require workflows to pre-configure unified mapping rules, to ensure consistent data formats for downstream summary steps.
Large single-pull sensor data volumes require workflow nodes to support batch processing, to avoid overloading individual nodes.
Shift-based safety inspection report updates require workflows to use shift-triggered scheduled tasks, to match the ledger summary cycle.
Sensitive production data requires permission checks for workflow invocation links, to prevent unauthorized access.

## Configuration guidelines
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | Combined shift-based scheduled triggering + real-time event triggering | Matches the dual requirements of real-time sensor data and daily ledger summary |
| Variable Mapping Rule | Unify multi-source data fields via `variables` configuration | Resolves differences in field names and formats across different systems |
| Node Timeout | 300 seconds | Adapts to the average time required for single-batch data pulling and processing in coal mines |
| Sub-workflow Invocation Permission | Bind parent workflow `nodeId` whitelist | Restricts unauthorized workflows from accessing sensitive ledger data |
| Tool Invocation Node Output | Only output structured results and the first 1000 characters of logs | Avoids unnecessary content interfering with subsequent report generation |
| Debug Node Linkage | Enable `variables` pass-through switch | Facilitates troubleshooting of result transfer issues between code execution nodes and subsequent nodes |

## Three common configuration mistakes
- Phenomenon: Sub-workflows automatically interrupt after approximately 180 seconds and fail to complete complex summary tasks. Cause: The node timeout setting was not adjusted, triggering the default timeout limit.
- Phenomenon: The code execution node generates output, but the specified reply node cannot retrieve this result. Cause: The variable pass-through configuration was not enabled, resulting in failed transfer of `variables` between nodes.
- Phenomenon: Tool invocation nodes output a large volume of redundant logs, causing disorder in report generation content. Cause: The default unstructured log output for tool invocations was not disabled, and only necessary structured data was retained.

## How to verify proper configuration
- Manually trigger the test workflow, check whether the trigger logs match the preset shift or event time points.
- Invoke a sub-workflow, verify whether a clear permission denial prompt is returned when an unauthorized parent workflow sends a request.
- Run the code execution node, check whether the downstream specified reply node can normally obtain and use the output result of this node.
- View the workflow runtime duration records, confirm that a single run does not exceed the preset 300-second node timeout.

The values provided here are common starting points and should be evaluated against the reader's own samples.
