# Coal Mine Production Ledger Summary and Report Generation: Deployment and Upgrade

## What data for this category looks like
Coal mine production ledger data primarily comes from downhole sensors, production scheduling systems, safety inspection terminals, and equipment operation and maintenance logs. Sensor data is pushed in real time. Inspection records are updated daily per shift. Equipment operation and maintenance logs are generated after fault handling or regular maintenance. Individual ledger documents include fields such as equipment number, runtime duration, fault count, and inspection item compliance rate. Units include hours, counts, tons, megapascals, and others. Some long documents include aggregated data across multiple consecutive shifts.

## What constraints these characteristics impose on deployment and upgrades
The real-time nature and long-document characteristics of coal mine production ledgers impose clear constraints on deployment and upgrade workflows. High-frequency real-time sensor data pushes increase database read/write pressure. Sufficient connection resources must be reserved to avoid read/write blocking. Uploading and parsing long shift summary documents can easily trigger interface timeouts. Related timeout configurations must be adjusted. Running ledger synchronization tasks must not be interrupted during upgrades, otherwise data gaps will occur. Field mapping configuration for multi-field ledger data must be completed in advance, otherwise subsequent retrieval and summary results will have deviations.

## How to set the configurations
This configuration applies to FastGPT v4.17.0, optimized for coal mine production ledger scenarios.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | 100–200 connections | Handle high-frequency real-time sensor data read/write requests and avoid connection pool exhaustion |
| `STORAGE_S3_ENDPOINT` | Fill in according to the intranet address of the local storage node | Adapt to the coal mine intranet storage service and ensure large document upload speed |
| `REDIS_URL` | Intranet Redis cluster address, set connection timeout to 60 seconds | Cache frequently queried ledger summary results to reduce database pressure |
| `FILE_TOKEN_KEY` | Randomly generated 32-bit string | Ensure the security of upload tokens and prevent unauthorized large file uploads |
| `MONGODB_URI` | Intranet connection address with read-write separation configuration | Separate real-time data writing and historical data query to improve system stability |
| `ROOT_KEY` | Security key generated according to the deployment manual | Initialize system administrator permissions and ensure permission control after deployment |

## Three common configuration errors
- The interface displays a timeout when uploading long shift summary ledgers, but the background shows the upload was successful. The cause is that the large file upload timeout configuration was not adjusted. The default timeout duration is insufficient to cover the parsing and transmission time of long documents.
- Workflows cannot trigger multi-round ledger summary conversations. The cause is that `REDIS_URL` was not configured correctly. Conversation context fails to be persistently cached, resetting to the initial state for each request.
- Services cannot be restarted normally after modifying the system password. The cause is that all associated FastGPT container processes were not stopped. A direct restart causes the configuration file to fail to load correctly, and the password change is not synchronized to all running instances.

## How to confirm the configuration is valid
- Upload a standard coal mine shift ledger document. Observe the interface upload status and background parsing logs to confirm that there is no upload timeout and parsing is completed.
- Initiate a multi-round ledger summary conversation. Observe whether the conversation context is retained to confirm that the `REDIS_URL` configuration takes effect.
- Check the database connection pool status to confirm that the current number of connections does not exceed the value set by `DB_MAX_LINK`.
- Log in to the system backend. Confirm that the administrator permission corresponding to `ROOT_KEY` is normal, and that ledger summary workflows can be created and edited normally.

The values provided are common starting points and should be measured against the reader's own samples.
