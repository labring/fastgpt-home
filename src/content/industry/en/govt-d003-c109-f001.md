# Ledger Summary and Report Generation for Power Grid Enterprises: HTTP Interfaces and External Systems

## What this category’s data looks like
Data sources include the SCADA dispatching system, marketing business application system, and equipment asset management system within power grid enterprises. Core equipment ledgers are updated quarterly. Operational ledgers are updated daily. Data uses structured JSON format, and includes fields such as unique device identifier, device name, rated capacity, commissioning date, affiliated line node, and cumulative operation and maintenance record count. Units include kVA, days, and units. The length of a single ledger entry typically falls between 800 and 1200 characters.

## What constraints these characteristics impose on HTTP Interfaces and External Systems
Multiple system sources require interfaces to support connections to multiple endpoints. A unified cross-system authentication mechanism must be implemented via the `Authorization` header. Different update frequencies require configured differentiated polling trigger rules. The trigger interval for core equipment ledger interfaces must be no shorter than 1 day. The trigger interval for operational ledger interfaces can be set to 1 hour. The large size of single data entries requires HTTP request timeout values of no less than 600 seconds, to prevent data truncation caused by transmission timeouts. Structured fields require that the `responseData` returned by interfaces follow preset field mappings, to avoid performance losses from full parsing.

## How to set up configurations
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `Authorization` header configuration | Carry a system-specific token in Bearer format | Adapt to unified authentication requirements for multiple external systems |
| Request timeout duration | 600-900 seconds | Match the transmission length of single ledger data |
| `variables` mapping rules | Bind ledger field names to application variables one-to-one | Enable accurate field transfer for structured data |
| `responseData` parsing rules | Only extract preset core business fields | Reduce parsing overhead for interface responses |
| Polling trigger interval | Core equipment ledgers: 1 day; Operational ledgers: 1 hour | Match the update frequencies of different ledger types |

## Three common configuration errors
- An interface call returns a connection error. This occurs when the token format in the `Authorization` header is not correctly configured, or when the external system interface does not open corresponding access permissions.
- Interface call results do not include preset ledger matching content. This occurs when ledger data source parameters are not bound to `variables`, leading to interface requests that do not carry correct data source trigger conditions.
- Platform test results do not match interface return results. This occurs when the context settings for interface requests do not match the context rules of the platform test, or when the external system’s ledger data source is not updated synchronously.

## How to confirm successful configuration
- Initiate a test interface request, and check whether the returned `responseData` includes preset core business fields.
- View interface call logs to confirm that the `Authorization` header is correctly carried and not intercepted.
- Initiate a request for the same business in the platform test environment, and compare field consistency between the interface return results and platform test results.
- Wait for the preset polling interval, then initiate a request again, and confirm that data has been synchronized and updated according to the set update frequency.
