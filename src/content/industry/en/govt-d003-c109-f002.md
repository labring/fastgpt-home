# Ledger Summary and Report Generation for Power Grid Enterprises: Vector Models and Indexing

## What the data for this category looks like
Organizations operating power grids collect ledger data from business systems including transmission inspection, substation operation and maintenance, and marketing payment. Update cycles vary: daily inspection reports, monthly equipment operation and maintenance reports, and quarterly archived annual operation ledgers.
A single ledger entry includes structured fields such as equipment ID, rated voltage, operating duration, and defect level, plus unstructured inspection photo summaries and troubleshooting records.
Field units include professional metering identifiers such as kV, A, hours, and sets. Document lengths range from hundreds to thousands of characters.

## What constraints do these characteristics impose on the vector models and indexing link?
Vector models must have domain semantic adaptation capabilities to avoid mismatching professional terms with general-purpose models, to match the structured fields and professional measurement units of power grid ledgers.
Indexes must support both incremental update and full update modes to adapt to the update frequencies of different ledgers, given data sources with multiple update cycles.
Chunking strategies must retain key context to prevent loss of device association information across chunks, to handle long-text ledgers and combined multiple fields.
Deployments must balance index recall efficiency and retrieval accuracy to avoid resource waste, given the large number of ledger entries.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale for This Setting |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Adapt to the text length of a single structured record plus attachment summary for power grid ledgers, to avoid semantic breaks |
| Overlap Length | 150–250 characters | Retain key context such as device ID and operating parameters of adjacent chunks, to prevent information fragmentation |
| `maxToken` | 8192 token | Match the context limit of mainstream open-source embedding models supported by FastGPT v4.17.0, to adapt to long ledger reports |
| `defaultToken` | Calibrated based on actual measurements | Adapt to the system's default token allocation rules, to avoid memory overflow during indexing |
| Embedding Model | Open-source vector model fine-tuned for the power grid domain | Adapt to semantic matching requirements for power grid professional terms such as kV, defect level, and transformer area ID |
| Similarity Threshold | 0.70–0.75 | Distinguish the similarity of ledger entries of the same type of equipment, to avoid redundant retrieval results |

## Three common mistakes
- Phenomenon: Retrieval response time exceeds 30 seconds after creating a QA split file collection via the OpenAPI interface.
  Cause: No reasonable chunk length and overlap length configured. The number of chunks exceeds the system threshold, increasing index loading and retrieval time.
- Phenomenon: The index model changes from `text-embedding-ada-002` to another version. Professional term matching errors appear in retrieval results.
  Cause: No domain-adapted embedding model specified. The system uses a general-purpose model after default update, which cannot adapt to power grid professional semantics.
- Phenomenon: Returned ledger entry fields in retrieval results are empty, such as missing device ID.
  Cause: Structured field complete information is not retained during chunking. Key identification fields are lost in vector embeddings.

## How to confirm the configuration is set correctly
- Access the knowledge base management page of FastGPT v4.17.0, view the current index configuration items, and confirm that the chunk length, overlap length, and embedding model match the preset values.
- Upload a substation equipment ledger document containing professional terms, perform a retrieval test, and check that the similarity of the returned results is within the preset threshold range, with no redundant similar entries.
- Review the background logs generated during indexing, confirm that there are no `maxToken` overflow errors, and that `defaultToken` allocation complies with system resource limits.
- Compare the retrieval results with and without the domain embedding model enabled, and confirm that the professional term matching accuracy meets business expectations.
