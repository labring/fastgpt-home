# Ledger Summary and Report Generation for Power Grid Enterprises: Multi-turn Dialogue and Prompt Engineering

Reference only; verify against the target FastGPT release and deployment documentation.

## What data in this category looks like
Power grid enterprise ledger data mainly comes from three types of data sources: dispatching automation system, marketing business application system, and equipment operation and maintenance ledger management system. Data updates are initiated by operation work orders or completed via daily scheduled synchronization. A single ledger document includes structured fields such as unique device identifier, operating parameters, maintenance records, and load monitoring data, as well as some associated unstructured on-site maintenance photos and reports. Fields include voltage level (unit kV), current (unit A), cumulative operating duration (unit hours), maintenance interval (unit days), and others. The data format is mostly structured tables, with a small amount of nested associated data.

## Constraints imposed by these characteristics on the "multi-turn dialogue and prompt engineering" link
The multi-source structured fields and fixed unit requirements for power grid ledgers require precise matching of field names and units in multi-turn dialogue, to avoid generating values that do not comply with power grid specifications. The update rhythm triggered by operation work orders requires that the dialogue context be associated with the ledger scope of the corresponding work order, to avoid confusion of cross-work order data. The existence of unstructured attachments requires prompts to clearly define the boundary between structured data extraction and attachment content analysis. The current work order's ledger ID context must be retained in multi-turn dialogue, to ensure that subsequent follow-up questions can accurately locate historical data of the corresponding device.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind the unique identifier of the current operation work order | Ensure multi-turn dialogue only associates with ledger data of the corresponding work order, avoiding cross-work order data confusion |
| `messages` | Retain the first 10 pieces of dialogue context | Power grid ledger data has a clear work order association scope; overly long context increases redundant computation, and 10 entries can cover the complete dialogue flow for a single operation |
| `variables` | Preset unit verification rules for three types of variables: voltage level, current, and maintenance interval | Power grid ledger fields have fixed unit requirements; pre-verification can avoid generating non-compliant report content |
| Single search limit | Top 3 matching device ledger data | The historical ledger data volume for a single device is large; limiting the number of entries can focus on core information and avoid context overload |
| Maximum context | 800–1200 characters | Power grid ledger has many fields and fixed units; limiting context length ensures matching accuracy between prompts and retrieved data, adjust based on actual measurements |

## Three Common Mistakes
- An "invalid parameter format" error occurs when applying the dialogue, and no corresponding log is generated. Cause: The `chatId` parameter is not correctly bound, the system cannot identify the currently associated ledger work order scope, and cannot generate abnormal log records.
- The prompt does not cover all ledger fields as expected. Cause: The complete power grid ledger field list is not preset in `variables`, resulting in the prompt missing extraction requirements for some required fields.
- The conversation record ID of the last AI reply cannot be accurately obtained. Cause: The context storage rule of the `messages` parameter is not correctly configured, and the system does not retain the unique identifier field of the last reply.
- Shared applications have cross-user dialogue data leakage. Cause: The user isolation configuration of dialogue data is not enabled, and the association relationship between `chatId` and the user's unique identifier is not bound.

## How to Verify Successful Configuration
- Initiate a test query dialogue, enter a ledger query request for a specified device, and verify that the context displayed on the dialogue interface only includes the ledger fields of the corresponding work order, with no irrelevant data.
- Trigger an abnormal input such as entering a value that does not comply with power grid standard units, and verify that the system returns a format prompt and generates corresponding abnormal logs.
- Initiate a multi-round follow-up question, and verify that historical data corresponding to the device ID mentioned in the last reply can be accurately obtained, with no data deviation.
- Share the application with a test account, and verify that the dialogue records of different accounts are invisible to each other, ensuring that the user isolation configuration takes effect.

All configuration values provided above are common starting points. Adjustments should be made based on the reader's own actual samples and testing.
