# Grid Enterprise Ledger Summary and Report Generation: Knowledge Base Retrieval and Recall

## What This Category of Data Looks Like
Ledger data for grid enterprises mainly comes from the PMS2.0 production management system, marketing business application system, and dispatching SCADA system. It covers three core document types: equipment operation and maintenance ledgers, power statistics ledgers, and line inspection ledgers.
Data updates use daily incremental sync as the primary method, with a full refresh performed once per week. Documents include standardized structured fields and unstructured attachments. Structured fields include equipment ID, operating voltage, inspection date, and defect level, with corresponding units such as kilovolts, kilowatt-hours, and kilometers.

## What Constraints Do These Characteristics Impose on the Knowledge Base Retrieval and Recall Workflow
Coexisting structured fields and unstructured attachments from multiple sources require the retrieval pipeline to support both structured field matching and full-text semantic recall. This covers different retrieval needs such as equipment ID and power value queries.
Daily incremental update requirements mean the recall process must connect to real-time data sync interfaces. This ensures retrieval results include the latest ledger entries.
Single ledger documents may contain long-text inspection report attachments. The context length of single recalled documents must be limited to avoid exceeding the model's input limit.
Standardized fields and units require associating field semantics with their corresponding units during retrieval. This prevents invalid recall results with mismatched units.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `similarity` | 0.72–0.80 | Matches structured fields and semantic content of grid enterprise ledgers, filters low-correlation recall results |
| `limit` | Top 12 entries | Covers the associated data volume of a single ledger report, avoids context overflow from too many recalled entries in a single request |
| `searchMode` | hybrid | Adapts to FastGPT v4.17.0's hybrid retrieval capability, covers the characteristics of structured and unstructured ledger data |
| `usingReRank` | Enabled | Performs re-ranking on initial recall results, improves the display priority of highly relevant ledger entries |
| `datasetSearchUsingExtensionQuery` | Enabled | Generates extended query terms based on user questions, covers retrieval needs for scenarios such as inspection reports and power statistics |
| `collectionIds` | Set via actual testing | Binds exclusive grid enterprise ledger knowledge base collections, isolates retrieval data across different business lines |

## Three Common Misconfigurations
- Phenomenon: Garbled characters appear in retrieved equipment ledger fields, with field values returned as “��” on the interface. Cause: No encoding parsing rules configured for grid enterprise ledger documents, so GBK-encoded inspection report attachments cannot be processed correctly.
- Phenomenon: A 400 error is returned when calling the retrieval interface, with the prompt “No matching vector database collection found”. Cause: The `collectionIds` parameter for the exclusive knowledge base collection was not correctly bound, and the access permissions and data mapping rules for the self-built Qdrant instance were not matched.
- Phenomenon: Segmented content of inspection reports is fragmented, with content from the same chapter split across different recall results. Cause: The Word document directory-based segmentation logic was not enabled, and only fixed-length segmentation rules were used, causing chapter semantics to be interrupted.

## How to Verify Successful Configuration
- Enter the equipment ID “10kV-001” to perform precise retrieval, and check whether the returned fields and units match the source ledgers.
- Trigger the daily incremental data sync, then retrieve the newly added line inspection ledgers to confirm the results include the latest updated entries.
- View the re-ranking scores of the retrieval results, and confirm that highly relevant ledger entries appear at the top of the result list.
- Test retrieval of long-text inspection reports, and confirm that the returned context length does not exceed the model's input limit.
