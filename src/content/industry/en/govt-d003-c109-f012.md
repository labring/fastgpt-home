# Grid Enterprise Ledger Summary and Report Generation: Deployment and Upgrade

## What this category of data looks like
Data comes from three grid enterprise systems: equipment operation and maintenance, marketing metering, and dispatching operation.
Frontline operation and maintenance personnel enter data manually, or the system automatically generates it via synchronization.
Updates follow two rhythms: daily incremental synchronization and monthly full update.
A single ledger document includes these fields: equipment number, installation location, rated voltage, commissioning date, operation and maintenance records, and detection data.
Accepted units include kilovolts, megawatts, hours, and counts.
Some fields support multilingual remarks.

## What constraints these characteristics impose on deployment and upgrades
Multi-source data access for grid ledgers requires configuring cross-system data synchronization authentication and format conversion parameters during deployment.
The layered update rhythm of daily incremental and monthly full updates requires preconfiguring scheduled task trigger rules and resource allocation strategies during deployment.
Fields include multiple numerical types and large text content, requiring database connection configurations to adapt to complex queries and large field storage needs.
Data involves sensitive grid operation information, requiring storage and key configurations to meet cybersecurity compliance requirements.
Synchronization tasks must not be interrupted during upgrades, so a rolling upgrade method must be used.

## How to set configurations
This page is compatible with FastGPT v4.17.0. All configuration items must be adjusted based on the actual environment of the grid enterprise.

| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| `PG_URL` | `postgresql://username:password@host:5432/grid_ledger?schema=public` | Grid ledger data structure is complex. PostgreSQL supports multi-field association and large text storage, adapting to the associated query needs of ledger summary |
| `STORAGE_S3_ENDPOINT` | `https://s3-cn-north-1.example.com` | Grid enterprises mostly use compliant domestic cloud storage services. A storage endpoint that meets cybersecurity compliance requirements must be configured to ensure ledger data storage security |
| `DB_MAX_LINK` | `50-80` | Daily incremental synchronization and monthly full update of grid ledger data generate high concurrent requests. A reasonable connection count prevents database connection pool exhaustion |
| `REDIS_URL` | `redis://:password@host:6379/0` | Used to cache frequently queried ledger summary results, reducing database pressure and adapting to scenarios where multiple users generate reports simultaneously |
| `FILE_TOKEN_KEY` | `32-bit random string` | Used to generate access tokens for ledger export files, ensuring secure file download |
| `ROOT_KEY` | `Generate a random string in accordance with enterprise internal key management specifications` | Used to manage the system's highest permissions, and must meet the key security requirements of grid enterprises |

## Three common errors
- Symptom: The container always listens on port 3000 after startup, regardless of changes to the port mapping configuration in docker-compose.yml. Cause: The default port configuration built into the image was not properly overwritten, or the mapped host port was not granted firewall access permissions.
- Symptom: After configuring multiple model keys, calls cannot be made by group, and the query interface returns a 401 status code. Cause: Corresponding model and ledger data access permissions were not assigned to different keys in the system permission configuration, or environment variables were not loaded correctly.
- Symptom: Ledger summary tasks time out, and logs show database connection timeouts. Cause: The `DB_MAX_LINK` configuration value is too low, causing the connection pool to be exhausted and unable to allocate database connections for new summary tasks.

## How to confirm the configuration is complete
- Run the container status check command to confirm that all associated services are running and match the configured connection addresses.
- Submit a single ledger summary test to verify that the generated content fields match the standard grid ledger structure.
- Adjust the database connection count configuration, observe the connection pool usage during task execution, and confirm that the configuration takes effect.
- Test the key permission configuration to verify that different keys can only access ledger data with corresponding permissions.
