# Mine Mining and Beneficiation Ledger Summary and Report Generation: HTTP Interfaces and External Systems
This document is written based on FastGPT v4.17.0.

## What this type of data looks like
Ledger data for mine mining and beneficiation comes from underground mining equipment PLC systems, mineral processing workshop DCS control systems, enterprise ERP production management modules, and geological survey reserve ledgers. Single records are generated per work shift, with daily ledgers compiled each day, and weekly summary documents generated each week. Each single ledger includes fields such as work shift, equipment number, raw ore grinding input, concentrate output, tailings discharge volume, and equipment operating duration. Units are uniformly tons, cubic meters, and hours, with no additional custom units. The data sync cycle is fixed: a single upload is completed within 1 hour after each shift ends, to avoid system load issues caused by real-time high-frequency pushes.

## What constraints do these characteristics impose on the HTTP Interfaces and External Systems link
The batch upload feature of mine mining and beneficiation ledgers requires HTTP interfaces to support receiving up to 50 ledger records per single batch, to avoid high-frequency single-request calls placing load on on-site PLC systems. Fixed fields and unit requirements mean the interface must include mandatory field validation rules, only allowing valid values for preset fields such as work shift, equipment number, and raw ore grinding input, to prevent dirty data from entering subsequent summary processes. Fixed sync cycle requirements mean the interface must support scheduled triggered batch requests, and also be compatible with supplementary upload scenarios, including duplicate data deduplication logic. On-site network fluctuations may cause request interruptions, so the interface must be configured with a retry mechanism to avoid repeated occupation of network resources of on-site systems.

## How to configure
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {exclusive API key generated by on-site mine systems}` | Matches the authentication specifications of on-site mine systems, avoids plaintext transmission of account passwords |
| `variables` | `{"batch_max": 50, "sync_trigger": "shift_end"}` | Adapts to the business rule of batch upload of mine ledgers per work shift |
| `responseData` | Returns fixed-format JSON: `{"code": 200, "received": integer}` | Facilitates on-site systems to quickly parse interface return results and complete data reception confirmation |
| Request timeout | 600 seconds | Adapts to the transmission duration of 50 ledgers per batch, avoids request interruptions caused by network fluctuations |
| Retry count | 3 times | Balances data transmission reliability and resource occupation of on-site systems |
| Field validation switch | Enable mandatory field validation | Filters invalid ledger data missing work shift or equipment number |

## Three common mistakes
- Phenomenon: The interface returns a `403 Forbidden` or `permission denied` error. Cause: The `Authorization` parameter is not configured correctly, an expired or unauthorized API key is used, and the on-site system authentication check fails.
- Phenomenon: The number of received records returned by the interface does not match the actual number of ledgers sent. Cause: The batch upper limit parameter in `variables` is not set correctly, causing excess data sent by the on-site system to be truncated or rejected by the interface.
- Phenomenon: File-format ledger data cannot be uploaded, or the interface prompts that file transfer is not supported. Cause: File transfer support for the interface is not enabled, or ledger data is not passed in the request body as a binary stream, causing the interface to fail to parse file-format ledger data.

## How to confirm the configuration is correct
- Send a single test ledger record, check whether the `responseData` returned by the interface includes valid reception status and received count.
- Check the request logs of the on-site system, confirm that authentication parameters are correctly carried, and there are no authentication failure error records.
- Simulate sending a batch of ledger data exceeding the preset upper limit, check whether the interface returns a response conforming to business rules.
- Wait for a complete work shift sync cycle, confirm that the FastGPT ledger summary module has obtained all data of the corresponding batch.
