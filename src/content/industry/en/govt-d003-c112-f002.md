# Grain Reserve Ledger Summary and Report Generation: Vector Models and Indexes

## What This Category’s Data Looks Like
Data primarily comes from inbound and outbound ledgers, inventory quality inspection reports, rotation execution documents, and policy reserve notices generated by daily grain warehouse operations. Update frequency changes with business nodes: inbound and outbound operations update ledgers in real time, monthly inventory checks update quarterly summary data, and annual rotation plans sync quarterly. Single documents mostly consist of structured tables paired with unstructured notes. Core fields include grain type, grade, storage quantity (unit: tons or kilograms), storage location, inbound date, and quality inspection metric values.

## Constraints for Vector Models and Indexing
The mixed structure of structured fields and unstructured notes requires vector encoding to balance field semantics and note details, to avoid breaking business associations during chunking. Coexisting real-time inbound and outbound data and bulk monthly summary documents requires indexes to support switching between incremental refresh and full rebuild modes. Storage quantities for different grain types have specific units, so unit information must be retained during vector preprocessing to prevent semantic confusion across categories. Longer single summary documents require adaptation to long text chunking and context stitching logic.

## Configuration Settings

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to the field density and note length of grain reserve ledgers, avoids overly scattered or overly long single chunks |
| Overlap Length | 100–150 characters | Retains business association information across chunks, such as batch handoff between adjacent ledgers |
| Similarity Threshold | 0.72–0.85 | Calibrated via actual testing, distinguishes semantic similarity across different grain types and storage states |
| Single Search Limit | Top 8 entries | Matches the number of core data entries in monthly summary reports, avoids interference from redundant results |
| `maxToken` | 4096 token | Adapts to context stitching requirements for long-text summary reports, complies with input limits of mainstream vector models |
| `defaultToken` | Configured according to business scenarios | Used for vector completion of missing fields, matches the fixed field format of grain reserve ledgers |

## Three Common Configuration Mistakes
- Phenomenon: The vector model service starts, but the interface shows a connection failure, and logs return a 404 status code. Cause: Interface address and permission parameters for Baidu embedding-v1 are not correctly configured, causing OneAPI forwarding requests to fail.
- Phenomenon: Vector index construction speed is slow, parsing a single 10MB ledger file takes more than 10 minutes. Cause: Adaptation configuration for CPU and GPU is not differentiated. Using GPU resources without enabling hardware acceleration scheduling, or not allocating enough threads to CPU cores.
- Phenomenon: An error prompt pops up when trying to add a vector model without a GPU environment. Cause: A lightweight vector model (such as m3e) is not deployed via OneAPI, and local GPU resources are called directly, causing loading failure.

## How to Confirm Proper Configuration
- Upload a single grain reserve ledger document, check if the chunked results after vector parsing retain core fields and note content.
- Initiate a ledger summary query in the test environment, verify whether the similarity distribution of returned results falls within the preset threshold interval.
- Check the running logs of the vector model service, confirm there are no error messages about connection failures or parameter errors.
- Configure an incremental index refresh task, verify whether real-time updated inbound ledgers can be synchronized to the index library.
