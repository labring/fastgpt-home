# Ledger Summary and Report Generation for Shipbuilding: HTTP Interfaces and External Systems

## What the data for this category looks like
Shipbuilding ledger data originates from multiple on-site execution systems including production scheduling systems, material requisition systems, station quality inspection systems, and welding process logging systems. Updates are triggered per shipbuilding node, synchronized after completion of each block construction or process node, with daily batch updates on regular days. Individual ship ledger documents include fields such as hull form code, block number, material code, requisition quantity, inspection items, and completed man-hours. Some fields are adjusted based on custom hull form requirements, with units including meters, tons, hours, pieces and other common engineering units.

## What constraints these characteristics impose on HTTP interfaces and external systems
Multi-source heterogeneous data sources require interfaces to support flexible authentication rules. The `Authorization` parameter must be used to adapt to the key or token format requirements of different systems. Fields are adjusted based on custom hull form requirements, so custom mapping rules must be passed via the `variables` parameter to avoid adaptation issues caused by hardcoding. Individual ship ledger data volumes are large and include long-text process logs, so the `responseData` parameter must be used to accurately filter required fields and reduce transmission overhead. Data update rhythms are tied to construction nodes, so interface call frequency must match the node rhythm, and timeout settings for single requests must adapt to the time required for returning long content.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Authentication Configuration | `Bearer {system key}` | Adapts to authentication rules of multi-source production systems and prevents cross-system call failures |
| Variable Passing Configuration | Pass custom parameters such as hull form code and block number | Adapts to ledger field mapping for different hull forms without modifying interface code |
| Response Data Filtering | Only return fields including ship name, material code, and inspection result | Reduces interface transmission data volume and improves retrieval efficiency |
| File Upload Configuration | Allow uploading HTML and JSON format files, with a size limit of 1000 MB | Meets upload requirements for shipbuilding interface documents and ledger backup files |
| Interface Timeout Setting | 600 seconds | Adapts to the return time required for long-text ledger data |
| Historical Context Optimization | Enable historical record association, with a context length of 2000 token | Resolves coreference resolution issues and optimizes question understanding for ledger searches |

This configuration applies to FastGPT v4.17.0

## Three common mistakes
- Phenomenon: After uploading HTML interface documents generated by javadoc, no matching content appears in knowledge base searches. Cause: Text extraction configuration for HTML files is not enabled, and static HTML files are only uploaded without being synchronized to the knowledge base via the interface.
- Phenomenon: When calling the chat interface with a file parameter, the interface does not respond or returns parameter errors. Cause: No file upload node is configured in the workflow, and file stream parameters are not passed correctly.
- Phenomenon: Model calls return parameter conflicts, prompting duplicate model configuration. Cause: Model parameters are configured in both config.json and platform settings, and unified synchronization rules are not followed.

## How to confirm the configuration is complete
- Call the configured HTTP interface and verify that the returned results include the preset filtered fields with no redundant data.
- Upload shipbuilding HTML interface documents, perform a knowledge base search, and retrieve relevant content within the documents.
- Call the chat interface to upload a file, and confirm that the workflow can normally read and parse the file content.
- Test a query with historical context, and confirm that the system can correctly associate historical conversations and resolve coreference ambiguities.

The values listed above are common starting points, and should be evaluated against the reader's own samples.
