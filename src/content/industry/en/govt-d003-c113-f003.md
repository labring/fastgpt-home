# Ledger Summary and Report Generation for Shipbuilding: Multi-turn Dialogue and Prompt Engineering

Reference only; verify against the target FastGPT release and deployment documentation.

## What the data for this category looks like
Shipbuilding ledger data originates from daily export files from production management systems (MES), warehouse management systems (WMS), and quality inspection systems. Update frequency is adjusted based on the construction progress of individual ships, with daily or weekly updates during a single ship’s construction cycle. Each individual ledger document contains multi-dimensional entries for a single ship section or entire ship. Fields include port of registry number, section process nodes, material specification and model, inspection pass rate, cumulative man-hours, and others. Units include meters, tons, hours, %, pieces, and more. The structure follows a standardized table format, with each entry bound to a unique section number and construction batch identifier.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
The multi-dimensional fields and mixed unit requirements of shipbuilding ledgers require multi-turn dialogue to first clarify core identifiers such as ship name and section number. This prevents mixing of data across different ships. Ledger data from multiple systems has minor format differences, so prompt settings must preset field mapping rules to ensure consistent recognition of data from different sources. A single ship’s ledger has a large number of entries, and long documents consume significant context space. The range of entries recalled each time must be limited to avoid exceeding the dialogue context capacity limit. Frequently updated ledger data requires pulling the latest dataset for each dialogue. Relying on expired context caching is not appropriate.

## How to configure the settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `chatId` | Bind to the exclusive chatId for individual ship construction | Isolate dialogue contexts for different ship types and sections to avoid data cross-interference |
| `variables` | Preset three variables: ship name, section number, and statistical cycle | Quickly locate target ledger entries and reduce repeated information input from users |
| Maximum context length | 8000–12000 characters | Adapt to the total entry length of multi-section ledgers for a single ship to avoid context overflow |
| Question optimization | Enabled | Convert colloquial ship process descriptions from users into standardized ledger field query conditions |
| Single recall limit | Top 20 entries | Control the volume of ledger data passed to each dialogue to ensure response speed |
| Session persistence | Calibrated based on actual testing | Adapt to the session storage requirements of login-free links and avoid accidental deletion operations affecting log retention |

## Three common misconfigurations
- After calling a tool to retrieve ledger data, subsequent dialogue turns cannot read the returned results. Cause: The tool output was not written to the assistant role content in the `messages` parameter, so tool execution results are not retained in the context.
- After configuring `chatId`, the parameter does not appear in background dialogue logs. Cause: The `chatId` field was not correctly included in the API request body, or the front-end interface was not bound to the corresponding session identifier.
- For sessions created via login-free links, deleting a single session causes the corresponding background log to disappear synchronously. Cause: No persistent session storage rules were configured, and login-free sessions use temporary storage logic by default.

## How to verify the configuration is complete
- Initiate a ledger query targeting a specific ship name and section, and check whether the `chatId` parameter is included in the dialogue logs to confirm that the context isolation configuration is active.
- Test the multi-turn dialogue workflow: first request detailed data for a single type of ledger, then request summary statistics for that data, and check whether the returned results are linked to the previous query conditions.
- Generate a login-free link and initiate a session, perform the delete session operation, and check whether the complete record of the session is retained in the background logs to confirm that the persistence configuration is correct.
- Test the form node submission function, check whether an interactive input control is generated on the dialogue interface to confirm that the rendering configuration is correct.
