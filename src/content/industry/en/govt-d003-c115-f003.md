# Rail Transit Equipment Ledger Summary and Report Generation: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Ledger data for rail transit equipment is primarily sourced from on-board operation sensors, offline maintenance record systems, and spare parts inventory management modules. Data update frequencies fall into three categories: on-board sensor data is uploaded in real time, maintenance records are synchronized daily, and monthly summary ledgers are updated at the end of each calendar month. The document structure for a single device’s ledger includes fields such as unique device ID, model, cumulative running mileage, annual maintenance count, replaced spare part models, and details corresponding to fault codes. Units include kilometers, days, occurrences, and more. Some fields require cross-system association and verification.

## What constraints these characteristics impose on the multi-turn dialogue and prompt engineering link
Decentralized data sources mean users must gradually clarify core parameters such as device ID and statistical cycle. Multi-turn dialogue must use progressive questioning to guide users to supplement necessary information, avoiding generalized requests. The text length of a single device’s monthly ledger can reach tens of thousands of characters. Excessively long context will cause the model to confuse field information across different devices, so the retention range of dialogue context must be limited. Field units are inconsistent, so prompts must explicitly require output results to strictly match preset units, avoiding unit conversion errors. Cross-system data requires association and verification, so multi-turn dialogue must confirm that all associated data has been synchronized before generating a report.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind the device-specific knowledge base ID for the current session | Ensure dialogue context is associated with the corresponding device’s ledger data, preventing cross-device data from being mixed in |
| `messages` | Retain the last 12 rounds of dialogue context, truncate old messages exceeding 8000 characters | Rail transit equipment single-device ledger data has a large volume; excessively long context easily causes the model to confuse device IDs and field information |
| `variables` | Preset two required variables: device ID and statistical cycle | Ledger summary requires clear target device and time range, avoiding erroneous results spanning multiple devices or time ranges |
| Maximum context length | 8000–12000 token | Adapt to the text length of a single device’s monthly ledger, avoiding dialogue interruptions caused by context overflow |
| Single recall count | Top 6 matched knowledge base entries | Rail transit equipment ledger fields are fixed; too many recalled entries will interfere with core field extraction and summary |
| Dialogue timeout period | 60 seconds | Prevent dialogue failure caused by delays in cross-system data retrieval |

## Three Common Mistakes
- Phenomenon: The device ID returned in the dialogue result does not match the one specified by the user, and field units are inconsistent. Cause: The context in `messages` is not explicitly limited to only the current device’s dialogue history, and the prompt does not enforce matching the parameters in the preset `variables`.
- Phenomenon: An empty result is returned after calling the API interface, with a status code of 400. Cause: The required parameters in `variables` are not passed correctly, or the `messages` format does not meet the system requirements of FastGPT v4.17.0.
- Phenomenon: The generated report includes ledger data from unrelated devices. Cause: The prompt does not explicitly require only the current device’s knowledge base entries to be used, and recalled knowledge base entries are not filtered by device ID.

## How to Confirm Configurations Are Properly Set
- Manually trigger a dialogue, enter the specified device ID and statistical cycle, and verify whether the returned result only contains the ledger data for that device.
- View the dialogue log to confirm that `messages` only retains the context of the current session and does not include historical dialogue content from other devices.
- When calling the API interface, check whether the `variables` parameter includes the required device ID and statistical cycle fields, and that the format complies with FastGPT v4.17.0 specifications.
- Test requests with different statistical cycles, confirming that the time range of the returned result matches the input `variables` parameter.
