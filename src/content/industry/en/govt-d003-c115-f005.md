# Rail Transit Equipment Ledger Summary and Report Generation: Tool Calling and Plugins

## What the data for this category looks like
Rail transit equipment ledger data primarily comes from on-board operation sensors, operation and maintenance management systems, and regular maintenance records. There are two update cycles: operation parameters are pushed in real time by sensors, while maintenance ledgers are summarized and updated daily. The document structure has two formats: structured CSV ledgers with fields including equipment ID, operation duration, maintenance cycle, component status, and more; unstructured PDF maintenance reports. Field units are mostly hours, days, and counts, with some custom fields requiring additional mapping and conversion.

## What constraints these characteristics impose on the "tool calling and plugins" workflow
Real-time operation data pushes require tool calling response delays to stay below a preset threshold, otherwise real-time ledger summary cannot be supported. Daily updated maintenance ledgers require plugins to support a scheduled synchronization mechanism to avoid reading outdated data. Structured CSV ledgers contain multiple types of fields, so the functions used for tool calling must accurately match the query and summary logic for different fields. Unstructured PDF maintenance reports require plugins to support text extraction and structured conversion, otherwise their content cannot be included in summary reports. Calls to multi-source data require coordinating permissions and frequency across different interfaces to prevent exceeding the interface limits of the equipment system.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | Auto mode | Adapts to tool matching requirements for multi-field ledgers, automatically selects the corresponding function |
| `functionCall` | Bind 3 preset functions | Covers three core scenarios: equipment ledger query, data summary, and report generation |
| Timeout setting | 600 seconds | Addresses parsing and interface call time consumption for large structured ledgers |
| Concurrency control | Concurrent requests per request ≤ 2 | Avoids exceeding the interface limits of the equipment system by sending multiple requests simultaneously |
| Document parsing plugin | Enable CSV and PDF parsing | Adapts to the two mainstream document formats for ledgers |
| Cache period | 24 hours | Matches the daily update rhythm of maintenance ledgers |

## Three common mistakes
- Symptom: Concurrency conflicts occur during tool calling, returning status code 429 or duplicate results. Cause: The concurrency count per request is not limited, and multiple ledger query requests sent simultaneously exceed the interface limits of the equipment system.
- Symptom: Calling the document reading plugin returns empty content, and ledger data cannot be parsed. Cause: The correct document parsing format is not configured, or ledger files are not uploaded to the storage path specified by the plugin.
- Symptom: A connection error is returned when calling the large model. Cause: The tool calling API channel is not configured correctly, or the timeout setting duration is insufficient, causing the request to be interrupted.

## How to confirm the configuration is complete
- Send a ledger query request for a single rail transit equipment ID, and check if the tool call return fields include core content such as operation duration and maintenance cycle.
- Upload a standard format rail transit equipment ledger CSV file and PDF maintenance report, call the document reading plugin, and confirm that structured fields and text content can be extracted correctly.
- Send 3 concurrent ledger summary requests, and check that no errors or abnormal results occur.
- View the tool call logs in FastGPT v4.17.0, confirm that the `toolChoice` parameter takes effect as configured, and there are no abnormal call records.
