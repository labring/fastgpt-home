# Rail Transit Equipment Ledger Summary and Report Generation: Deployment and Upgrade

## What the data for this category looks like
Ledger data for rail transit equipment comes from on-board operating sensors, offline maintenance systems, and spare parts management modules. The update cadence is real-time collection of operating parameters, daily synchronization of maintenance records, and monthly updates of spare parts inventory. Each individual ledger document includes fields such as unique device ID, model specification, cumulative operating hours, last maintenance date, and spare parts replacement details. Units include operating hours, maintenance counts, spare part dimensions in millimeters, and lubricant volume in liters. Some documents include high-resolution maintenance photos and operating log attachments.

## What constraints these characteristics impose during deployment and upgrade
Data sources for rail transit equipment ledgers are scattered, and update frequencies vary. During deployment, support for multiple data source connections and concurrent writes is required, so database connection pool configuration must adapt to high-concurrency scenarios. During upgrades, real-time data synchronization cannot be interrupted, so a rolling upgrade strategy must be used to avoid loss of operating parameters due to service restarts. The mixed storage of structured fields and attachments requires the knowledge base to support indexing for both relational and unstructured data. Upgrades must be compatible with old data formats to avoid migration failures. Additionally, ledger data fields and units follow industry-specific rules. During deployment, the knowledge base’s field mapping rules must align with industry standards to avoid data parsing errors.

## Three Common Mistakes
- Symptom: `connection refused` error appears when starting the container, unable to connect to the database. Cause: The address specified in `MONGODB_URI` or `REDIS_URL` does not correctly point to the locally deployed service container, or the corresponding ports are not open in the firewall.
- Symptom: Historical conversation records and device ledger cache are not cleared after executing Docker Compose restart. Cause: No persistent volume configured for the `REDIS_URL` corresponding service, so session cache data is not cleared when the container is deleted.
- Symptom: Generated ledger report attachments cannot be downloaded normally. Cause: Incorrect `FILE_TOKEN_KEY` configuration, leading to failed attachment download permission verification and inability to generate valid access links.

## How to Confirm the Configuration is Correct
- Execute the `docker ps` command to confirm that the MongoDB, Redis, front-end service, and API service containers are all in a running state.
- Call the ledger synchronization interface, pass a simulated rail transit equipment device ID, and check that the returned fields include required items such as device model and operating hours, with no null values.
- Upload a rail transit equipment maintenance report PDF, trigger the ledger summary task, confirm that the task status shows completed, and the generated report contains correct summary data.
- Access the address configured in `FE_DOMAIN`, confirm that the front-end page loads normally, and can call the API to retrieve device ledger data.
