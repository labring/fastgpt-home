# Ledger Summary and Report Generation for Telecommunications Engineering Construction: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Telecommunications engineering construction ledger data primarily comes from project management systems, on-site inspection terminals, and material procurement and acceptance systems. Update frequency aligns with project milestones, with daily or weekly updates during a single project cycle. Document formats include acceptance reports over 100,000 Chinese characters in length, and Excel material ledgers with over 15,000 rows. Data is structured by project section, with core fields including section number, material name, specification and model, incoming quantity, acceptance date, construction team, and supervisor signature status. Units include engineering-specific measurements such as meters, sets, tons, and workdays.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompt Engineering
The large volume and specialized fields of telecommunications engineering ledgers create multiple constraints for multi-turn dialogue and prompt configuration. First, individual documents have large file sizes. Directly passing full datasets will exceed model context limits, so data must be split via chunked parsing and session state management. Second, specialized fields and units can cause ambiguity. Prompts must clearly specify field definitions and measurement units to avoid incorrect summary results. Third, data updates occur frequently. Multi-turn dialogue must call the latest data source each time, so prompts must include instructions to pull the most recent data. Finally, users may switch between sections or query different material types during multi-turn dialogue. Session identifiers must retain historical query states to ensure context continuity.

## Three Common Mistakes
- Issue: After uploading a 15,000-row telecommunications engineering ledger Excel via the dialogue interface, returned material quantity results do not match the original data. Cause: File chunk parameters adapted to engineering ledgers were not configured, leading to loss of associated information from adjacent rows during data splitting.
- Issue: Dialogue output delay exceeds the set threshold, and the interface displays a timeout status. Cause: Timeout duration configuration was not adjusted. Large file parsing and multi-turn data queries were not adapted to the volume of telecommunications engineering ledgers, and chunking and query logic were not optimized.
- Issue: Session token consumption statistics are inaccurate. Token usage for some conversations is not correctly recorded. Cause: Session token statistics function was not enabled, or token consumption from historical messages in the `messages` array and chunked files was not included in calculations.

## How to Verify Proper Configuration
- Upload a 15,000-row telecommunications engineering ledger Excel, initiate a multi-turn dialogue to query the total material quantity for a specified section, and confirm that returned results match the statistical results of the original data.
- View the session details page, confirm that `chatId` is automatically generated and persistently stored with each dialogue, and that session status updates correctly after switching sections to return data for the corresponding section.
- Initiate a dialogue including an acceptance report of 100,000 Chinese characters, and check that the token consumption data returned by the interface matches the character count conversion result of the actual parsed content.
- Adjust the timeout duration to 90 seconds, initiate a dialogue including a large file, and confirm that the response time does not exceed the set threshold and no timeout errors occur.
