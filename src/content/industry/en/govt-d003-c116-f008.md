# Ledger Summary and Report Generation for Telecommunications Engineering Construction: Document Parsing and Chunking

## What this category of data looks like
Ledger and report data for telecommunications engineering construction mainly comes from full project process documents such as construction logs, material purchase vouchers, acceptance reports, and supervision inspection records. Updates follow project milestone progress. Single project documents are mostly multi-page PDFs, structured Excel files, or Word documents with tables.

Document fields include project number, construction section, equipment model, engineering quantity, acceptance date, responsible team, and more. Units involve common engineering measurement standards such as meters, cubic meters, kilowatts, and batches.

## What constraints do these characteristics impose on the document parsing and chunking link
Mixed-format documents from multiple sources require the parsing process to support multiple file types including PDF, Excel, and Word. This avoids missing ledger information caused by format loss.

Single project documents have wide length differences. Ranges from short temporary inspection records of a few pages to long completion reports of dozens of pages. Chunking must adapt to content of different lengths.

Incorrect splitting of structured table documents will break ledger field associations, making it impossible to restore key data such as complete engineering quantity and acceptance information.

Documents also contain a large number of engineering-specific terms and measurement units. Chunking must retain context association to avoid term truncation that affects subsequent summary logic.

## How to set configurations
The following configurations are formulated based on the functional logic of FastGPT v4.17.0:

| Config Item | Recommended Value | Rationale |
| --- | --- | --- |
| `chunkSize` | 800–1200 characters | Telecommunications engineering ledgers often contain structured tables and long paragraphs. This range balances the completeness of content per chunk and retrieval accuracy |
| `chunkSplitter` | Chunk by paragraph + semantic meaning | Ledger documents have a large number of logically independent construction records and acceptance entries. Semantic chunking preserves the complete logic of single records |
| `customPdfParse` | Enable structured parsing mode | Telecommunications engineering PDF ledgers often contain nested tables and stamped signatures. Enabling this mode preserves table structure and text content, and avoids parsing failures caused by digital signatures |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | Single project completion documents may include large numbers of drawings and attachments. This upper limit covers most file requirements for large-scale projects |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600 seconds | Large completion documents take longer to parse. This duration avoids parsing interruptions caused by timeouts |
| `chunkSettingMode` | Custom mode | Allows adjustment of chunking parameters for different types of ledger documents such as purchase ledgers and acceptance reports, to adapt to diverse document structures |

## Three common mistakes
- Symptom: After uploading a PDF file with a digital signature, the parsing result has no valid text content. Cause: The structured parsing mode of `customPdfParse` is not enabled. The encrypted layer of the digital signature interferes with basic PDF parsing logic, resulting in failed text extraction.
- Symptom: The API returns a file reading link, and clicking it returns the error message "Only support .txt, .m". Cause: The uploaded file format is not compatible with the basic parsing module, and no parsing adaptation rules for the corresponding format are configured, so the link cannot be rendered normally.
- Symptom: After parsing an uploaded Excel ledger, the chunking result loses some table column data. Cause: The `chunkSize` setting is too small, splitting cross-column table row content into multiple chunks, breaking the structured association of the table.

## How to confirm the configuration is correct
- Upload a single typical telecommunications engineering PDF ledger, check the table structure and text integrity in the parsing result, and confirm that valid content of digital signature files is retained.
- Adjust the `chunkSize` parameter, compare chunking results under different values, and ensure that a single chunk contains complete single engineering record or table row.
- Upload the maximum allowed size project document, verify that the parsing process does not trigger a timeout error, and confirm that the value of `PARSE_FILE_TIMEOUT_SECONDS` matches the current file scale.
- Call the API to test the file upload and parsing process, confirm that the returned reading link can be accessed normally, with no format restriction errors.

The values provided are common starting points and should be measured against the reader's own samples.
