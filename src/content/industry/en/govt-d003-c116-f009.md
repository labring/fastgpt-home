# Ledger Summary and Report Generation for Telecommunications Engineering Construction: Model Access and Configuration

## What this category of data looks like
Telecommunications engineering construction ledger data comes from multiple internal business systems, including construction management, material requisition, and completion acceptance. Updates are synchronized daily or weekly, aligned with construction milestones. A complete ledger document includes dozens of fields: project number, project name, construction area, material specification, requisition quantity, acceptance status, responsible person, and more. Supported units include meters, cubic meters, sets, and man-hours. Some fields use mixed units.

## Constraints on model access and configuration
The multi-source, high-frequency update and multi-field characteristics of telecommunications engineering construction ledgers impose three constraints on model access and configuration.
1. Ledger text compiled from multiple systems has wide length fluctuations. Strictly limit the context window size to prevent model inference failures caused by overly long inputs.
2. Field units are inconsistent and numerous. The model must automatically align units when generating reports, so configure appropriate randomness parameters.
3. Data updates occur frequently. Configure cache strategies properly to avoid using outdated ledger data that reduces report accuracy.

## How to Set Configurations
| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | A single telecommunications engineering construction ledger document can reach thousands of characters, requiring compatibility with long context inputs |
| `maxTokens` | 2000–3000 token | Ledger summary reports require organizing multiple fields and drawing conclusions, requiring sufficient output length |
| `quoteMaxToken` | 1500 characters | Sufficient original ledger fragments must be retained as reference basis for reports |
| `temperature` | 0.2–0.4 | Ledger data requires accurate alignment of fields and units, so the randomness of generated results must be reduced |
| `AIPROXY_API_ENDPOINT` | Fill in the access address provided by the cloud platform service provider | Adapt to the cloud large model inference address for private deployments |
| `AIPROXY_API_TOKEN` | Fill in the key generated by the cloud platform | Complete identity verification for model calls |

## Three Common Configuration Errors
- A 404 error appears during model testing. This occurs when the entered model ID does not match the model identifier configured on the cloud platform, and no matching available model name is found.
- A container error with the message `Api response error: /api/core/ai/model/test?model=Doubao-l` occurs. This is caused by incorrect `AIPROXY_API_TOKEN` configuration, or the cloud platform not granting call permissions for the target model.
- Generated reports display inconsistent field units. This happens when the `temperature` parameter value is too high, causing the model to fail to strictly align with the original unit fields from the ledger.

## How to Verify Correct Configuration
- A normal response is returned after navigating to the model provider configuration page, entering `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN`, and clicking the test button.
- A generated report that fully includes all core fields is confirmed after uploading a typical telecommunications engineering ledger document to trigger a model call.
- The consistency of fields and units in generated results meets expectations after adjusting the `temperature` parameter and calling the same ledger document multiple times.
- Valid results are returned for all model calls after switching between different cloud platform models, and the model switching function in the chat dialog box is verified to work properly.
