# Ledger Summary and Report Generation for Telecommunications Engineering Construction: Deployment and Upgrade

## What the data for this category looks like
Ledger data for telecommunications engineering construction comes from project approval documents, on-site construction logs, material incoming inspection receipts, equipment installation and commissioning records, completion acceptance filing forms, and similar materials. Data updates follow the construction progress of individual projects. Each project’s ledger document includes independent fields such as project number, construction area, material batch, equipment model, and acceptance node. Field units include engineering-specific units such as meters, units, days, and ten thousand yuan. A single ledger document typically contains dozens of structured fields and attachment materials.

## What constraints do these characteristics impose on deployment and upgrades
Telecommunications engineering construction ledger data has a complex structure, with fields using specialized units. During deployment, configure storage and parsing rules that support multi-field mapping. Data is updated in batches according to project progress. During upgrades, retain incremental synchronization configuration items to avoid business interruptions caused by full re-import. Some engineering scenarios require offline deployment. During upgrades, ensure compatibility between local models and storage. Data involves engineering-sensitive information. Configure strict access permission control during deployment and upgrades to prevent unauthorized access.

## How to set configurations
The following configuration items are formulated based on the deployment specifications of FastGPT v4.17.0.

| Configuration Item | Suggested Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 100–150 connections | The single-batch import volume of telecommunications engineering ledgers is large, so the database connection pool must be sufficient to support concurrent imports |
| `STORAGE_S3_ENDPOINT` | Local object storage intranet address | Telecommunications engineering data includes a large number of engineering drawings and construction logs, so intranet high-speed storage is required to avoid latency |
| `REDIS_URL` | Locally deployed port 6379 address | Used to cache ledger field mapping rules to improve batch processing speed |
| `FE_DOMAIN` | Engineering site intranet domain name | Ensure that internal personnel can access the ledger summary page via the intranet |
| `ROOT_KEY` | Random string generated according to enterprise security policies | Used to configure administrator permissions to avoid unauthorized access |

## Three common mistakes
- Front-end pages keep loading indefinitely and fail to load. The symptom is that after accessing the configured `FE_DOMAIN` address, the page continuously displays a loading animation, and the browser console returns an error that cross-origin requests are blocked. The cause is that `FE_DOMAIN` was not correctly configured as the intranet access address, resulting in cross-origin request interception.
- Local model tests return errors, and the deployed model cannot be called. The symptom is that the model test step returns connection timeout or parameter error. The cause is that `MONGODB_URI` was not pointed to the local model storage repository, or the offline deployment network whitelist was not configured.
- Field units are missing after ledger import. The symptom is that fields such as material length and equipment quantity in the generated summary report have no corresponding units. The cause is that field mapping rules to map engineering-specific units to system preset fields were not configured in advance.

## How to confirm the configuration is correct
- Access the configured `FE_DOMAIN` address, confirm that the page loads normally with no console errors.
- Import a test telecommunications engineering ledger file, confirm that data can be parsed normally and generate a structured preview.
- Check the database connection logs, confirm that the connection count configured for `DB_MAX_LINK` is not continuously exhausted.
- Test the local model call function, confirm that returned results match the preset format with no connection timeout errors.
