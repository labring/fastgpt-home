# Ledger Summary and Report Generation for Communication Towers and Infrastructure: Multi-turn Dialogue and Prompts

## What Data This Category Includes
Ledger data for communication towers and infrastructure comes from three sources: base station operation and maintenance inspection reporting systems, tower asset right confirmation registration platforms, and operator resource management databases.
Update cycles fall into two categories: real-time updates from daily inspections, and bulk updates from monthly asset inventories.
Common document formats include structured Excel ledgers, JSON-format inspection reports, and PDF-format qualification documents.
Fields include tower ID, latitude and longitude, installation height, load capacity parameters, inspection date, maintenance personnel, and fault status. Common units are meters, kilograms, square meters, and standard date formats.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompts
The multi-source structured nature of communication tower ledgers requires clear context boundaries between real-time inspection data and monthly inventory data during multi-turn dialogue.
Fields include physical parameters with units. Prompts must mandate that output results retain corresponding units to avoid confusion between parameters such as latitude and longitude, and height.
For processing multi-format documents, multi-turn interactions must gradually guide users to upload files of the correct type. Prompts must also limit the scope of field extraction to prevent cross-category data from being included.
Data with different update cycles must be marked with time attributes in the session to ensure the timeliness and accuracy of summary reports.

## Configuration Settings
This configuration applies to FastGPT v4.17.0. Details are listed below:

| Configuration Item | Recommended Approach | Rationale |
|---|---|---|
| `messages` | Append by conversation turn, retain no more than 10 historical messages per turn | Communication tower ledger data volume is large; limiting historical message count avoids context overflow |
| `variables` | Bind two global variables: tower ID and inspection cycle | Quickly locate dedicated ledger data for this category, reduce repeated input |
| `chatId` | Create independent session IDs for different inspection teams | Isolate ledger summary tasks across teams, avoid data confusion |
| Maximum context length | 8000–12000 token | Adapt to bulk processing requirements for multi-source ledger documents |
| Prompt optimization | Calibrate based on actual testing | Adjust instructions to match the field characteristics of tower ledgers, ensure accurate field extraction |
| Multi-turn session timeout | 600 seconds | Avoid long-term resource occupation, adapt to complex ledger summary workflows |

## Three Common Misconfigurations
- Issue: Cannot upload inspection reports and asset ledger files separately during multi-turn dialogue. Cause: No independent upload entry configured for different ledger file types, leading to mixed file binding in the session.
- Issue: The dialog box throws a `Cannot read properties of null (reading 'q)` error. Cause: The `messages` parameter does not correctly populate user question fields, leading to failed session context parsing.
- Issue: Ledger classification results do not match actual inspection statuses. Cause: Prompts do not explicitly limit classification to only tower-specific fields, mixing in parameter rules from other categories.

## How to Verify Proper Configuration
- Initiate a test dialogue, input a specified tower ID, and confirm that the global variables bound via `variables` automatically populate corresponding parameters.
- Upload two ledger files of different types, and confirm that the session automatically identifies the file type and assigns it to the correct upload entry.
- Check the historical message count for the `messages` parameter, confirm that it does not exceed the preset per-turn limit.
- Trigger a session timeout test, confirm that the session automatically terminates after 600 seconds with no residual data.
