# Ledger Summary and Report Generation for Communication Towers and Infrastructure: Database and Operations

## What this category of data looks like
Data sources include tower inspection terminals, power environment monitoring platforms, operation and maintenance work order systems, and basic surveying and mapping data. There are two update cycles: real-time inspection data is synchronized every 15 minutes, and basic ledger data is updated in batches every early morning. Each single document contains these fields: unique tower identifier, installation location longitude and latitude, tower height, number of mounted antennas, previous inspection records, maintenance work order number, and current health status. Some fields support nested storage of binary data for inspection photos. Units are uniformly meters, degrees, counts, and entries. Field types are categorized as character, numeric, and time-based to prevent format conflicts across data sources.

## Constraints imposed on database and operations by these characteristics
High-frequency synchronization of real-time inspection data requires database connection pools to support short connection reuse. This prevents excessive resource usage caused by frequent connection establishment.
Large volumes of basic ledger data updated in batches daily require configured database sharding rules. Split data storage by tower affiliation area to avoid reduced query efficiency from excessive single-table data volume.
Strict field type differentiation requires mandatory format verification during database writes. This prevents longitude and latitude format errors from causing subsequent retrieval exceptions.
Multi-source data synchronization requires configured data verification rules. Compare tower ID consistency across systems to avoid duplicate or missing ledger entries.
Frequent queries of historical inspection records during operations require indexes covering longitude and latitude, and inspection time fields. This improves query response speed.

## How to set configurations
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://admin:***@mongodb-cluster:27017/iron_tower_log?authSource=admin` | Stores unstructured data such as inspection photos and work order attachments, in compliance with MongoDB non-relational data storage specifications |
| `PG_URL` | `postgresql://admin:***@pg-cluster:5432/iron_tower_base?sslmode=require` | Stores structured ledger fields, longitude and latitude, numeric metrics and other relational data; enables SSL to secure data transmission |
| `DB_MAX_LINK` | `20–30` | Adapts to concurrent demand from high-frequency inspection data synchronization, avoiding connection pool overload or resource waste |
| `REDIS_URL` | `redis://:***@redis-cluster:6379/0` | Caches frequently queried basic tower information to reduce database read pressure |

## Three common misconfigurations
- Phenomenon: An internal server error with 500 status code is returned when installing database connection plugins. Cause: Authentication information for `MONGODB_URI` or `PG_URL` is not correctly configured, or the corresponding port access permission for the database cluster is not enabled.
- Phenomenon: A MongoDB connection failure prompt appears when starting FastGPT service, with connection timeout shown in logs. Cause: The `DB_MAX_LINK` configuration value is too high, causing the MongoDB connection pool to be exhausted and unable to establish new connections.
- Phenomenon: Duplicate tower entries appear in ledger summary results. Cause: No data deduplication rule is configured, and tower ID uniqueness is not verified during multi-source synchronization.

## How to confirm configurations are correct
- Run the built-in database connectivity detection tool to verify the connection status of `MONGODB_URI` and `PG_URL`, and confirm there are no authentication failure or network timeout prompts.
- Import a simulated tower inspection data entry, check the write result of corresponding fields in the database, and confirm the format and units comply with preset rules.
- View system cache monitoring metrics, confirm that frequently accessed basic tower information has been cached in Redis, and no duplicate database query logs appear.
- Adjust the `DB_MAX_LINK` configuration value, observe changes in database connection count, and confirm the connection pool is within a reasonable range.

The values provided are common starting points and should be measured against the reader's own samples.
