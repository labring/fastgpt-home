# Ledger Aggregation and Report Generation for Communication Towers and Infrastructure: Model Access and Configuration

## What this category of data looks like
Data sources include base station operation and maintenance management systems, on-site inspection terminal reports, power environment monitoring equipment, and tower ownership registration archives. Update cadence falls into three categories: basic ownership ledgers are updated quarterly, inspection records are submitted with each on-site operation, and alarm and operating status data is synchronized in real time. Individual ledger documents include fields such as unique tower number, latitude and longitude coordinates, construction time, maintenance responsible person, inspection record list, alarm logs, supporting power supply and antenna parameters, etc. Units include meters, hours, counts, decimal degrees, etc. A complete single ledger contains multiple long text sections.

## What constraints these characteristics impose on the model access and configuration link
The differing update cadences of multi-source data require model calls to adapt to the timeliness of different data types. The sudden volume of real-time alarm data may cause context overflow. The large number of structured fields with varying units requires model output to strictly match field formats and units to avoid data confusion. The concatenation of long-text inspection records and multi-entry alarm logs will significantly increase the total context length, so the context range loaded in a single session must be limited. Ledger data for different towers is independent of each other, so cross-task data mixing must be avoided to ensure reports only include tower information within the specified scope.

## How to set the configuration
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the long-text concatenation requirements of multi-source ledgers, prevents context overflow |
| `maxTokens` | 2000–3000 token | Meets the generation length requirements for a single structured report, aligns with ledger aggregation output needs |
| `temperature` | 0.2–0.4 | Reduces random generation probability, ensures accuracy and format consistency of ledger data |
| `AIPROXY_API_ENDPOINT` | Fill in the address provided by the deployment service provider | Adapts to the access paths of domestic large model proxy services, resolves cross-region access latency issues |
| `AIPROXY_API_TOKEN` | Exclusive key bound to the proxy service | Ensures identity verification security for model calls, prevents unauthorized access |
| `toolChoice` | auto | Allows the model to autonomously decide whether to call tools to process structured ledger data, improves aggregation efficiency |

## Three common mistakes
- Symptom: When multiple large models with the same name are configured, a key mismatch error occurs during calls, or returned results do not meet expectations. Cause: Each model is not assigned an independent `AIPROXY_API_TOKEN` and exclusive identifier, so the system cannot accurately distinguish between different model instances.
- Symptom: Reports generated by workflow nodes mix ledger data from other towers. Cause: The context is not limited to only loading tower data associated with the current task, and the default global context causes irrelevant information to be included.
- Symptom: Model vendor icons display as gray placeholders in the interface. Cause: The resource access path for `AIPROXY_API_ENDPOINT` is not configured correctly, so the front end cannot pull icon resources for the corresponding vendor.

## How to confirm the configuration is complete
- Submit a single specified tower's ledger data for testing, verify that the generated report includes all core fields of that ledger, with no irrelevant data mixed in.
- Configure multiple models with the same name and initiate multiple calls, verify that each call uses the model corresponding to the specified `AIPROXY_API_TOKEN`, and returned results meet expectations.
- Check that model icons in the front-end interface display correctly, confirm that the resource path configuration is accurate.
- Simulate batch import of multiple ledger data entries, verify that model calls process data normally within the set context range, with no context overflow errors.

The values provided are common starting points and should be measured against the reader's own samples.
