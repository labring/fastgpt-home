# Ledger Summary and Report Generation for Communication Towers and Infrastructure: Deployment and Upgrade

## What this category of data looks like
Ledger data for communication towers and infrastructure originates from the tower operation and maintenance management system, base station inspection terminals, and geographic information service platform. There are three update rhythms:
Basic ledger data updates in real time alongside tower construction and renovation. Daily inspection data syncs once per day. Fault alert data pushes in real time.
Each single data entry includes structured fields and unstructured attachments. Structured fields include tower ID, longitude and latitude (degrees), tower height (meters), load capacity (kilonewtons), installation date, previous inspection records, fault count, and maintenance work order number. Attachments include inspection photos, test report PDFs, and similar files.

## What constraints these characteristics impose on deployment and upgrade
Because data includes structured fields with units such as longitude, latitude, and physical parameters, configure field mapping and unit validation rules in advance during deployment. This prevents unit mismatch errors during statistics.
Because inspection data pushes in real time and covers all national sites with large volume, configure high-concurrency database connection pools and incremental sync tasks. This ensures data sync efficiency.
Because attachments include large numbers of inspection photos and reports, adapt to high-capacity, high-availability storage services. During upgrade, synchronously maintain compatibility with old version attachment reading logic. This prevents attachment loading failures.
Because ledger data involves cross-department collaboration, configure permission-isolated storage and query nodes during deployment. This ensures data security.

## Configuration Recommendations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `200 connections` | Adapt to multi-site concurrent ledger query and sync requests, avoid database connection exhaustion |
| `MONGODB_URI` | `mongodb://admin:xxx@mongodb:27017/tower_data?authSource=admin&maxPoolSize=100` | Store unstructured attachment data such as inspection photos and fault reports, support high-concurrency writes |
| `PG_URL` | `postgresql://admin:xxx@postgres:5432/tower_ledger?sslmode=require&pool_size=80` | Store structured ledger fields, support complex multi-condition queries and statistics |
| `REDIS_URL` | `redis://:xxx@redis:6379/0?maxmemory=10240mb&maxmemory-policy=allkeys-lru` | Cache frequently accessed basic tower information to reduce database query pressure |
| `STORAGE_S3_ENDPOINT` | `https://s3-cn-beijing.aliyuncs.com` | Store inspection attachments and generated ledger reports, adapt to domestic cloud storage access rules |
| `FILE_TOKEN_KEY` | `32-bit randomly generated secure string` | Encrypt download links for attachments and reports, prevent unauthorized access |

## Three Common Mistakes
- Phenomenon: Pulling the FastGPT v4.17.0 Docker image displays a manifest unknown error. Cause: The correct image tag was not specified, or the domestic network cannot directly access the official image repository. Configure an image accelerator to resolve this.
- Phenomenon: Password-free shared ledger reports fail to load properly in overseas-deployed systems. Cause: `STORAGE_S3_ENDPOINT` was not configured to an overseas-region-adapted storage node, resulting in cross-region access to attachment resources being blocked.
- Phenomenon: Load capacity parameters for some towers show abnormalities after upgrade. Cause: The database schema and the new version's field mapping rules were not validated in advance during upgrade, and unit fields of old data were not automatically converted.

## How to Confirm Proper Configuration
- Run the `docker ps` command, confirm all FastGPT-related containers are running with no abnormal restart records.
- Access the health check interface of `FE_DOMAIN`, confirm that the connection status of databases, caches, and storage services is normal.
- Upload a simulated tower inspection data entry, trigger the ledger summary task, and check whether the expected structured report and attachment links can be generated.
- View Redis monitoring metrics, confirm that the cache hit rate for frequently accessed basic tower information meets standards, with no frequent database queries.

The values provided are common starting points and should be measured against the reader's own samples.
