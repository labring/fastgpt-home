# Steel Smelting Ledger Summary and Report Generation: Document Parsing and Chunking

## What Data for This Category Looks Like
Steel smelting ledger data primarily comes from PLC production control systems, quality inspection center reports, material inventory management systems, and production work order systems. Data update frequency is every shift (8 hours) or real-time synchronization. Supported document formats include CSV structured tables, PDF quality inspection reports, and Excel production ledgers. Fields included in documents cover furnace number, smelting duration, steel grade, alloy addition amount, tapping temperature, and more. Units include tons, degrees Celsius, minutes, kilograms, and others. Some documents contain handwritten annotations and cross-page continuous records.

## Constraints Imposed by These Characteristics on Document Parsing and Chunking
The mixed multi-source formats of steel smelting ledgers require the parsing process to adapt to both structured tables and unstructured annotations. Frequent real-time updates may cause individual document volume to increase as batches accumulate. Cross-page continuous process records require chunking logic to retain field context associations, avoiding splitting complete production data across furnace runs. Mixed units and field naming require the parsing process to accurately identify field boundaries, preventing field misalignment or missing fields. Additionally, scenarios with batch document uploads require the parsing process to support batch processing, avoiding single-file limits that impact overall efficiency.

## Configuration Guidelines

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `chunkSize` | 800–1200 characters | Matches the typical length of a single smelting process description, avoiding splitting complete production records across furnace runs |
| `chunkSplitter` | Split by paragraph + table boundaries | Adapts to the mixed text and structured table format in ledgers, retaining the association between adjacent fields |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | Covers the volume requirements of batch ledger uploads, preventing large file uploads from being blocked |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600 seconds | Adapts to the time required for long document parsing, preventing mid-process interruptions that cause incomplete data |
| `customPdfParse` | Enable structured table parsing mode | Accurately extract cell fields from PDF quality inspection reports, avoiding misidentification of table content as plain text |
| `chunkSettingMode` | Manual configuration mode | Manually adjust chunking parameters for the high-density field characteristics of steel smelting ledgers |

## Three Common Misconfigurations
- After uploading a multi-page PDF smelting ledger, only the first 3 pages are parsed, and the interface displays a parsing timeout. The cause is failure to adjust the `PARSE_FILE_TIMEOUT_SECONDS` parameter; the default duration is insufficient to complete full parsing of long documents.
- After importing a CSV-format ledger, only the first two columns of data are displayed, and the remaining fields are empty. The cause is failure to configure `chunkSplitter` to align parsing by CSV column boundaries; the default chunking logic misjudges column separators, causing subsequent fields to be truncated.
- After uploading a ledger archive larger than 500 MB, a 413 error is returned. The cause is failure to adjust the `UPLOAD_FILE_MAX_SIZE` parameter to match the size of the archived file; the default limit cannot cover the upload requirements of large-volume batch files.

## How to Verify Proper Configuration
- Upload a single 100 MB PDF smelting ledger, and check that the parsed text fully extracts all tables and cross-page process descriptions.
- Import a test CSV ledger, and verify that all preset fields are fully displayed with no missing or misaligned columns.
- Check the system operation logs to confirm that the parsing task duration does not exceed the configured `PARSE_FILE_TIMEOUT_SECONDS` value.
- Upload a packaged multi-ledger archive, and confirm that the upload proceeds normally with no 413-type upload block errors.

The values provided are common starting points and should be measured against the reader's own samples.
