# Ledger Summary and Report Generation for Railway Operations: Vector Models and Indexes

## What Data for This Category Looks Like
Railway operation ledger data originates from three core data sources: train dispatching systems, passenger and freight ticketing systems, and line equipment inspection systems. Update frequencies fall into three categories: real-time (train commands, equipment alerts), daily (passenger and freight shift settlement), and periodic inspection (line switch and catenary maintenance). Individual ledger documents have a fixed structure, including line number, unique equipment identifier, collection time, operation type, detection value, and remark field. Each detection value includes its associated unit, such as degrees Celsius, kilopascals, or passenger trips.

## How These Characteristics Impact Vector Models and Indexes
Heterogeneous data formats across multiple sources require vector models to adapt to structured fields and numerical text with units, to avoid semantic embedding bias. High-frequency updates of real-time data require indexes to support low-latency incremental writes, to avoid blocking regular queries. Fixed document structure and field rules require index splitting to preserve field boundaries, preventing damage to data associations after splitting. Batch import of large-scale periodic inspection ledgers requires indexes to support parallel construction to reduce time consumption. Some duplicate records from the same equipment and period require controlled deduplication logic, to avoid disrupting the original chronological order of the ledgers.

## How to Configure
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to the total field length of individual railway ledger records, avoiding splitting that breaks complete semantics of core fields such as line number and equipment ID in a single ledger |
| Overlap Length | 50–80 characters | Retains field association information between adjacent chunks, preventing loss of cross-chunk equipment numbers and collection times |
| Similarity Threshold | 0.75–0.85 | Filters duplicate inspection ledger records while retaining similar detection data from different time periods on the same line |
| Single Search Limit | Top 20 entries | Matches the single-batch query data volume for railway operation ledgers, avoiding return of excessive redundant information |
| `defaultToken` | 1024 token | Adapts to the vector length of individual ledger embeddings, meeting input requirements of mainstream vector models |
| `maxToken` | 4096 token | Covers context length requirements during ledger summary report generation, avoiding truncation of critical data |

## Three Common Misconfigurations
- Phenomenon: After custom splitting railway ledger documents, the knowledge base automatically deletes duplicate document chunks, causing index order to be inconsistent with custom splitting results. Cause: The system enables global document chunk deduplication logic by default, with no exemption rules configured for periodic repeated inspection records of railway ledgers.
- Phenomenon: A 401 status code returns when connecting to the m3e vector model. Cause: The vector model access key is not configured correctly, or the key permissions do not cover the embedding request interface.
- Phenomenon: After deploying multiple FastGPT replica instances, inconsistent duplicate records appear in the knowledge base index. Cause: No shared storage is configured to mount the vector index directory, causing index files generated by each replica to be unsynchronized.

## How to Confirm Correct Configuration
- Upload a single complete railway inspection ledger document, and check whether core fields such as line number and equipment ID retain their semantics in the vector embedding result.
- Submit a query containing duplicate inspection records, and verify whether the deduplication logic of returned results matches the preset similarity threshold range.
- View vector model call logs, confirm that request paths and parameters match configured items, with no 401 permission errors.
- Batch import 100 periodic inspection ledgers, and check whether index construction time meets business expected time requirements.
