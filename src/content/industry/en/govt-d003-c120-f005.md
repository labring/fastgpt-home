# Railway Operations Ledger Aggregation and Report Generation: Tool Calling and Plugins

## What the data for this category looks like
Data sources for railway operation ledgers include real-time train operation logs, ticket sales records, equipment inspection archives, dispatch order sheets, revenue settlement documents, and more. Update rhythms vary significantly: dispatch logs update in real time, ticket data syncs hourly, equipment maintenance ledgers are archived daily, and revenue reports are generated monthly. Individual ledger documents contain fields such as train number, timestamp, equipment code, operating mileage, fault code, and revenue amount. Units include kilometers, passenger trips, hours, yuan, and others. Field types fall into three categories: string, numeric, and enumeration.

## What constraints these characteristics impose on tool calling and plugins
Plugins must support connecting to data sources using different protocols, including real-time stream interfaces, batch file storage, and internal business system APIs, to accommodate the multi-source, decentralized nature of railway operation ledgers. Tool calling parameter validation must match the exclusive field rules of railway ledgers, to avoid parameter type mismatches or unit conversion errors, given the diversity of fields and units. Plugins must be configured with differentiated scheduled trigger rules for ledger data with different update frequencies, to ensure the timeliness of aggregation and report generation meets business requirements. Every tool calling operation must retain calling logs, to facilitate subsequent audits and traceability, to comply with compliance requirements.

## How to Set the Configuration
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | Adapts to multi-scenario calling requirements for railway ledger aggregation and report generation, automatically matches preset tool functions |
| `functionCall` | `["generate_railway_summary", "generate_railway_report"]` | Corresponds to the two core tool functions for railway operation ledgers, clearly limits the calling scope |
| Plugin Key Verification | Enable and bind to internal system whitelist | Complies with identity verification requirements of railway systems, prevents unauthorized access |
| Plugin Timeout | 300–600 seconds | A single batch of railway ledger data has a large volume and long processing time, calibrated based on actual measurements |
| Number of Entries Returned per Call | First 20 entries | Controls the single context length to avoid exceeding the model's processing limit |

## Three Common Mistakes
- A 401 status code is returned when calling a tool, because the plugin's key verification rules are not configured correctly, preventing FastGPT from passing identity verification by the railway internal system.
- The preset ledger aggregation function is not triggered during tool calling, because `toolChoice` and `functionCall` are configured as disabled, making it impossible to call custom tool functions.
- Ledger data from the railway internal system cannot be pulled, because the plugin's internal network proxy is not configured, preventing access to protected internal data sources.

## How to Confirm the Configuration is Correct
- View the FastGPT plugin running logs to confirm that the tool calling request carries the correct internal system key and identity identifier.
- Pass simulated railway operation ledger data, call the test tool, and check whether the returned aggregation results include the preset fields and units.
- Adjust the `toolChoice` configuration to specify a function, verify that the corresponding ledger generation tool can be triggered accurately.
- Check the plugin's data source connection status to confirm that real-time or batch ledger data from the railway system can be pulled normally.
