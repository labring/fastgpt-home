# Ledger Aggregation and Report Generation for Expressway Operations: Database and Operations

## What this category of data looks like
Expressway operation ledger data has four sources: toll station toll systems, road section monitoring platforms, maintenance inspection terminals, and road law enforcement terminals. Data updates follow three rhythms:
- Toll data is pushed hourly or in real time
- Maintenance data is updated per daily inspection cycle
- Road law enforcement event data is uploaded immediately when an event triggers

A single ledger document corresponds to one business event or periodic statistical result. Its fields include business ID, occurrence time, involved road section, quantitative indicators such as toll amount, maintenance mileage, passage duration, and processing status. Units include yuan, kilometers, hours and other category-specific standards. Some fields must comply with transportation industry ledger specifications.

## Constraints on database and operations workflows
Multi-source heterogeneous data sources require databases to support storage and joint query of both unstructured logs and structured numerical values. Differentiated update rhythms require flexible write policies to prevent high-concurrency real-time data from blocking low-priority periodic statistical tasks. Strict requirements for segmented fields and units mandate unified field mapping rules at the database level to avoid unit confusion or missing fields during aggregation. Data volume grows linearly with the number of operating road sections, so advance planning for database horizontal scaling paths is required. Ledger data must meet industry compliance requirements, so regular full backup and incremental synchronization mechanisms must be configured to ensure data traceability.

|---|---|---|
| `MONGODB_URI` | `mongodb://admin:securepass@db1.example.com:27017,db2.example.com:27017/highway_db?replicaSet=rs0` | Adapts to storage needs for multi-source unstructured ledger data; sharded clusters support horizontal scaling |
| `PG_URL` | `postgresql://admin:securepass@pg-primary.example.com:5432/highway_meta?sslmode=require` | Stores structured ledger metadata and statistical rules; primary-replica synchronization ensures query availability |
| `DB_MAX_LINK` | `200–300` | Average daily connections per road section are approximately 150; redundancy is reserved for peak holiday traffic |
| `REDIS_URL` | `redis://:securepass@redis.example.com:6379/0?maxmemory-policy=allkeys-lru` | Caches frequently queried ledger statistical results; LRU policy prevents memory overflow |

## Three Common Configuration Mistakes
- Attempting to connect to a domestic database returns a protocol incompatibility error. The default configuration only includes standard PostgreSQL and MongoDB drivers, with no dedicated adaptation packages for domestic databases integrated.
- Running `npm list mongoose` in a deployed container returns no output. The mongoose package required by FastGPT is bundled in the base image's node_modules directory and not installed globally. Verify versions using the package.json file inside the container.
- Calling the ledger aggregation API returns some empty fields. No field mapping rules were configured in advance, so non-standard business fields fail to be correctly read and included in the aggregation.

## How to Verify Proper Configuration
- Access the FastGPT configuration interface, enter the corresponding database connection parameters, and run a connectivity test. Confirm no error messages are returned.
- Import a standard expressway maintenance ledger data set, run an aggregation query, and verify the returned results include preset business fields and compliant units.
- Initiate 150 concurrent ledger read requests, and check the database connection pool does not show timeout or exhaustion errors.
- Access the file system of the deployed container, open the package.json file, and confirm the mongoose version matches the compatible version listed in FastGPT v4.17.0 official documentation.
