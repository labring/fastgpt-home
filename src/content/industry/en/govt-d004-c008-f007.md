# Patrol Monitoring and Alarm Judgment for Health Diagnosis Reports: Database and Operations

## What constraints these characteristics impose on the database and operations link
Multi-source data access requires the database to support mixed storage of structured and unstructured data. High-frequency updated real-time metrics require the database connection pool to handle concurrent write operations. Diverse and standardized fields require index creation to optimize query efficiency. Real-time queries related to alarms need caching mechanisms to reduce database load. Long-term storage of historical reports requires a data archiving strategy to avoid system response slowdowns caused by full data queries.

## How to set configurations

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://admin:securepass@mongodb-cluster.example.com:27017/health_diagnosis?retryWrites=true&w=majority&maxPoolSize=20` | Stores unstructured patrol logs and historical report snapshots, supports batch writes for multi-node data |
| `PG_URL` | `postgresql://dbuser:dbpass@pg-db.example.com:5432/health_db?sslmode=require` | Stores structured patrol metrics and alarm rules, ensures data consistency and transaction security |
| `DB_MAX_LINK` | `15–25` | Matches concurrent write volume of real-time patrol data, prevents database connection pool exhaustion |
| `REDIS_URL` | `redis://redispass@redis-cache.example.com:6379/1` | Caches patrol snapshots from the last 10 minutes and active alarms, reduces pressure from high-frequency database queries |

## Three common misconfigurations
- Database queries return a 504 Gateway Timeout status code. This occurs when connection pool size is not adjusted for the high-frequency updates of health diagnosis reports, leading to connection exhaustion and failed request responses.
- Structured fields such as CPU usage and memory usage in patrol reports are empty. This occurs when write permissions for `PG_URL` are not properly configured, preventing structured patrol metrics from being stored in the relational database.
- Alarm judgment requests take too long. This occurs when `REDIS_URL` caching of recent snapshots is not enabled, requiring full historical data queries directly from the relational database.

## How to confirm configurations are set correctly
- View the database connection pool monitoring dashboard. Confirm that current active connection count does not reach the `DB_MAX_LINK` limit. Adjust based on the actual number of patrol nodes.
- Submit a simulated patrol data entry. Check that data is correctly stored in the corresponding database. Verify connectivity and write permissions for `MONGODB_URI` and `PG_URL`.
- Trigger a simulated alarm judgment request. Check that the response time of cached queries meets business requirements. Adjust based on the service level agreement standard for alarm responses.
- View system operation logs. Confirm there are no database connection error or permission denial logs. Verify the effectiveness of the configurations.
