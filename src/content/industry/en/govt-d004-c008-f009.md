# Health Diagnostic Report Inspection Monitoring and Alarm Judgment: Model Access and Configuration

## What This Category of Data Looks Like
The data for health diagnostic reports comes from real-time operational data collected by inspection equipment and sensors in state-owned enterprises, government, and public service sectors. It is supplemented by ledger information entered through manual inspections.
Data update frequency aligns with inspection cycles. Updates can be done in real time, hourly, or daily.
The document structure is fixed. It includes device unique identifier, inspection timestamp, multi-dimensional sensor readings, preset alarm thresholds, abnormal point annotations, and preliminary judgment conclusions.
All fields have clear units. For example, temperature uses degrees Celsius, and vibration values use millimeters per second.

## Constraints Imposed by These Characteristics on Model Access and Configuration
The fixed structure and clear fields of health diagnostic reports require model access to adapt to mixed input formats of structured data and unstructured text.
High-frequency updated data sources create batch processing requirements. These requirements must match the frequency and response delay limits of model calls.
Report length varies widely across different inspection scenarios. Sufficient context space must be reserved to accommodate complete data and system prompts.
State-owned enterprises, government, and public service sectors have strict data security requirements. Model access must adapt to internal network environments to prevent data exfiltration.

## Configuration Settings
| Configuration Item | Recommended Values | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Health diagnostic reports contain multiple sets of inspection data and system prompts, requiring space to accommodate complete input content |
| `temperature` | 0.1–0.3 | Alarm judgment requires consistent conclusions to avoid random fluctuations |
| `AIPROXY_API_ENDPOINT` | Fill in the dedicated address according to the deployment node | Adapt to the internal network environment of state-owned enterprises and government sectors to ensure data does not leave the domain |
| `AIPROXY_API_TOKEN` | 64-bit random secret key | Comply with internal security compliance requirements and reduce the risk of token leakage |
| `toolChoice` | auto | Allow the model to independently choose whether to call associated judgment tools to adapt to different inspection scenarios |

## Three Common Misconfigurations
- Phenomenon: After upgrading the FastGPT version, the configured dedicated model automatically switches to another model during calls. Cause: The specified model was not locked in the application configuration, or the model parameter in the global environment variable overrides the application-level configuration.
- Phenomenon: Processing speed of health diagnostic reports is too slow to meet real-time alarm judgment requirements. Cause: The `maxContext` parameter was not adjusted to adapt to report length, causing the model to repeatedly truncate input data, or local cache for accelerating structured data retrieval was not configured.
- Phenomenon: A data length error is prompted during token configuration. Cause: The used token length exceeds the preset field limit of the database, a short secret key was not used, or the database field was not configured for expansion.

## How to Confirm Configuration Is Completed
- Enter the application model configuration page of FastGPT v4.17.0, and verify that `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` match the deployment configuration exactly.
- Upload a standard-format health diagnostic report to trigger a model call, and check that the returned judgment results match the preset alarm logic.
- View the application's model call logs to confirm there are no error messages, and that call delay meets the preset response requirements.
- Simulate a high-frequency call scenario, check that system resource usage is normal, and there are no timeouts or current limiting issues.
