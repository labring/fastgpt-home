# Multi-source Monitoring Data Fusion for Patrol Inspection and Alarm Judgment: Tool Calling and Plugins

## What data for this category looks like
Data sources for multi-source monitoring data fusion include four categories: industrial IoT sensors, on-site video surveillance, industrial control system operation logs, and data reported by handheld patrol terminals. Data update frequencies cover three types: real-time (sensors, logs), minute-level (some environmental parameters), and hour-level (patrol summaries).
Single data is in structured format, containing fields such as device unique ID, collection timestamp, monitoring value, alarm threshold baseline, and data source channel. Units include physical quantities such as ℃, mm/s, A, percentage, and status codes.

## What constraints do these characteristics impose on tool calling and plugin workflows
The multi-source attribute of data requires tool calling to support passing multi-channel data parameters simultaneously, to avoid logical fragmentation caused by split calls. Coexistence of data sources with different update frequencies requires plugins to have configurable custom polling cycle parameters, to adapt to call timings of second-level real-time data and hour-level summary data. The feature of many structured fields requires clear target field mapping rules during tool calling, to ensure accurate matching of threshold conditions during alarm judgment. Small single data volume but large total data batches require limiting the number of returns per tool call, to avoid context overflow affecting model inference.

## How to set configurations
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Multi-source data channel mapping | Bind corresponding fields one by one by collection source | Adapt to structured field differences across multiple data sources, ensure accurate parameter transfer |
| Tool call timeout | 10–30 seconds | Cover the regular collection interval of real-time sensor data, avoid data loss from short timeouts |
| Number of returns per single call | Top 20 entries | Match the regular batch data volume of patrol inspections, prevent context overflow |
| `toolChoice` | auto | Allow the model to independently select tools adapted to multi-source data, improve judgment flexibility |
| `functionCall` | Specify specific tools as needed | Use when a specific type of monitoring data processing tool needs to be called fixedly, improve call stability |
| Polling cycle configuration | Set in groups by data source type (5 seconds - 1 hour) | Match the update rhythm of different data sources, avoid invalid calls |

## Three common errors
- Symptom: Parameter error prompt returned during HTTP tool call. Cause: File input parameter configuration not enabled, unable to handle unstructured inputs such as patrol videos or log files.
- Symptom: Unable to view detailed logs of MCP services. Cause: Detailed output switch for tool call logs not enabled in workflow settings.
- Symptom: Long model thinking time, inference delay exceeds expectations. Cause: Number of data entries returned per single call not limited, excessive monitoring data occupies the context window, increasing model inference load.

## How to confirm configurations are set correctly
- Initiate a test call, check if the structured data returned by the tool includes preset fields such as device ID and monitoring value, confirm that the mapping rule takes effect.
- View tool call logs, confirm that the polling cycle matches the update rhythm of each data source, with no duplicate or missing call records.
- Adjust the `toolChoice` parameter to auto and specific for testing separately, confirm that the model can correctly select the tool logic adapted to multi-source data.
- Test the chained logic of the RAG knowledge base and MCP tools in the workflow, confirm that the flow of multi-source data and knowledge base retrieval results operates normally.
