# Multi-source Monitoring Data Fusion for Patrol Monitoring and Alarm Judgment: Deployment and Upgrade

## What the Data for This Category Looks Like
The core data sources for multi-source monitoring data fusion come from multiple collection nodes, including industrial sensors, video surveillance cameras, fire alarm systems, and access control and attendance devices. Data update cycles range from real-time millisecond-level to minute-level. Offline archived historical logs are uploaded in batches hourly. The document structure includes three categories: structured time-series data, semi-structured alarm logs, and unstructured video frame metadata. Core fields include device unique identifier, collection timestamp, monitoring value, alarm level, and data source node. Supported units include ℃, Hz, mA, entries, and others.

## What Constraints Do These Characteristics Impose During Deployment and Upgrade
In FastGPT v4.17.0, deployment and upgrade for multi-source monitoring data fusion scenarios must adapt to the heterogeneous nature of the data. Format differences across multiple data sources require configuring compatible access adapters during deployment to prevent data parsing failures. The high update frequency of real-time data requires adjusting cache and queue parameters to reduce database write pressure and prevent data accumulation. Large-capacity time-series alarm data requires selecting an appropriate storage engine. During upgrade, field mapping rules for historical data must be retained to avoid interrupting the real-time monitoring link.

## Configuration Guidelines
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://admin:yourpassword@host:27017/fastgpt_monitor?authSource=admin` | Adapts to high-concurrency writes and queries for multi-source time-series alarm data, ensuring data persistence |
| `REDIS_URL` | `redis://:yourredispassword@host:6379/0?maxmemory-policy=allkeys-lru&maxmemory=10240 MB` | Caches real-time collected monitoring data to reduce database pressure; sets cache expiration time to 600 seconds |
| `STORAGE_S3_ENDPOINT` | `https://s3-cn-beijing.aliyuncs.com` | Stores unstructured video frames and log backup files, adapting to large-capacity cold data storage requirements |
| `ROOT_KEY` | `Custom complex string of 16 or more characters` | Configures platform administrator permissions to ensure access security after deployment |
| `FE_DOMAIN` | `https://internal-monitor-domain.com` | Configures frontend access domain, adapting to access paths within internal office networks |
| `FILE_TOKEN_KEY` | `Random 32-character string` | Generates file access tokens to secure access permissions for unstructured monitoring data |

## Three Common Configuration Mistakes
- Symptom: Services fail to provide normal external access after startup, and the frontend page returns 404 or 502 errors. Cause: The mapping between `FE_DOMAIN` and the server port is not configured correctly, or the server’s port 3000 is not open, preventing the frontend from connecting to the backend service.
- Symptom: Connected sensor data fails to display normally, and logs indicate field parsing failures. Cause: The access adapter for the corresponding data source was not enabled during deployment, and format verification rules for multi-source data were not configured, preventing heterogeneous data from being processed uniformly.
- Symptom: Some historical alarm data cannot be queried after upgrade. Cause: The database instance corresponding to `MONGODB_URI` was not backed up before upgrade, and the upgrade script does not support field mapping rules for legacy data, resulting in lost or unparseable historical data.

## How to Confirm Successful Configuration
- Run the `docker-compose ps` command to confirm that all associated containers (including databases, caches, and the FastGPT main service) have a status of Up.
- Connect a test sensor device and upload a set of simulated monitoring data to check if the platform can normally receive and display core information such as device ID, collection time, and monitoring values.
- Upload a test monitoring log file to confirm that the platform can correctly parse core fields, with no missing fields or parsing error prompts.
- Use the `ROOT_KEY` to call the administrator interface to verify that the permission configuration takes effect, with no error prompts related to unauthorized access.
