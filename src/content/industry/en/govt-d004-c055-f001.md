# Tunnel Alert Filtering: Patrol Monitoring and Alert Judgment - HTTP Interface and External Systems

## What This Category of Data Looks Like
Reference only; verify against the target FastGPT release and deployment documentation.

## Constraints on HTTP Interface and External System Integration
The second-level update rhythm of tunnel alerts requires the HTTP interface to have low latency, to avoid losing real-time alert data due to timeouts. Each alert document contains multi-dimensional fields, which requires the field formats of the interface request body and response body to align with external operation and maintenance systems. The volume of original alert data is large, so the number of requests per batch must be limited to avoid overloading the interface and external databases. Additionally, most tunnel scenarios are deployed in intranet environments, so the interface must support intranet access authentication to prevent unauthorized leakage of sensitive data. These characteristics require the configuration process to balance real-time performance, data format compatibility, and access security.

## Configuration Recommendations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer sk-xxxxxx (32-bit fixed secret key) | Meets intranet data access authentication requirements for tunnel scenarios |
| Interface timeout duration | 2000–3000 milliseconds | Matches the second-level update rhythm of tunnel alerts, avoids dropping real-time alerts due to timeouts |
| Batch request limit | First 80 original alerts | Controls the volume of data per interface request, prevents overloading external system processing |
| `responseData` | Return only alert ID, tunnel pile number, filter result, trigger time | Aligns with the field format of external operation and maintenance platforms |
| `variables` | Configure region codes, alert type whitelist | Implements scenario-specific tunnel alert filtering logic |
| Maximum retry count | 2 times | Adapts to occasional tunnel network fluctuations, avoids repeated submission of duplicate alerts |

## Three Common Configuration Mistakes
- Symptom: Interface returns the `AIPROXY_API_TOKEN is not set` error message. Cause: The secret key value of the `Authorization` parameter is not configured correctly, or interface authentication-related variables are not filled in `variables`
- Symptom: A large number of slow query operations appear in the associated database, the page cannot open normally, and the interface returns a 504 status code. Cause: No batch request limit is set, pushing too much original alert data in a single request causes database write overload
- Symptom: Returned alert results include non-preset alert types. Cause: No alert type whitelist is configured in `variables`, resulting in unfiltered unrelated alerts

## How to Confirm Successful Configuration
- Call the configured HTTP interface, check that the request header contains correct `Authorization` authentication information
- Send simulated tunnel alert data, verify that the fields returned in `responseData` match the preset filtering rules
- Send multiple batches of simulated alerts consecutively, check that the interface response time does not exceed the set 2000–3000 millisecond threshold
- View the alert data received by the external system, confirm that only tunnel alert types that match the whitelist are included
