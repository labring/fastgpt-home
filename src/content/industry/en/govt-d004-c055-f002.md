# Tunnel Alert Filtering: Patrol Monitoring and Alert Judgment - Vector Models and Indexes

## What this category of data looks like
Tunnel alert filtering data comes from online monitoring terminals such as temperature sensors, displacement sensors, and smoke detectors deployed along the tunnel, as well as daily patrol reports and video intelligent analysis results. Updates are generated in real time when monitoring triggers, or synced in batches at fixed intervals. Each data entry is a structured field set, including device ID, alert type, trigger threshold, current measured value, point coordinate, associated patrol task ID, and other fields. Field units vary by monitoring item: temperature uses degrees Celsius, displacement uses millimeters, and time uses standard timestamp format. Single batch data volume changes based on tunnel length and number of monitoring points, and the overall data is high-frequency structured time-series data.

## Constraints on Vector Models and Indexing from Data Characteristics
The high-frequency structured data characteristics of tunnel alert filtering impose multiple constraints on the vector model and indexing workflow. First, the high proportion of structured fields requires adaptation to multi-field fusion encoding, to avoid losing key monitoring threshold and point information when relying only on text fields. Second, the real-time and high-frequency update rhythm requires indexing to support incremental synchronization and low-latency writing, to avoid performance loss caused by full reconstruction. Third, differences in multiple types of monitoring units and fields require unified normalization processing before vector generation, to ensure that monitoring data of different dimensions can be effectively encoded. Finally, the frequent occurrence of similar alerts requires indexing to support fast similarity search and deduplication, to improve the efficiency of subsequent alert judgment.

## Configuration Guidelines
This configuration applies to FastGPT v4.17.0

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapt to the total length of structured fields for a single alert, to avoid truncation of key monitoring threshold and point information |
| Overlap Length | 100–200 characters | Ensure that associated information of adjacent alert segments is not lost, covering threshold deviation associations across chunks |
| Similarity Threshold | 0.75–0.85 | Filter similar alerts at the same point and of the same type, to reduce redundant judgment volume |
| Single Recall Limit | Top 20 entries | Control the number of returns per search, to avoid excessive server load |
| `defaultToken` | 4096 | Adapt to context encoding for long time-series alerts, covering the total length of single-batch patrol data |
| `maxToken` | 8192 | Support vector generation for batch alert data, meeting the batch processing requirements of high-frequency updates |

## Three Common Configuration Mistakes
- Phenomenon: Server memory usage continues to rise during vector generation or search, and resource exhaustion is triggered at fixed times every day. Cause: Incremental indexing is not configured for high-frequency updated alert data, and full vector reconstruction is performed for each update, leading to overload of disk and memory load.
- Phenomenon: Index interface returns 400 status code with no response body. Cause: Multi-field normalization processing is not performed for structured alerts, and some field formats do not meet the input requirements of the vector model, triggering interface verification failure.
- Phenomenon: Old vector database data cannot be properly migrated to the new index after version upgrade. Cause: Adaptation is not made for the structured field mapping rules of alert data, and there are differences in vector generation logic between old and new versions, leading to incorrect encoding of old data.

## How to Confirm Correct Configuration
- Check vector generation logs to confirm that all fields of each alert data are correctly encoded, with no truncation or format errors.
- Simulate high-frequency data writing, observe server resource usage, and confirm that no continuous upward anomalies occur.
- Perform similar alert search to verify that the similarity of returned results meets the preset threshold range.
- Perform historical data migration operations to confirm that index data of new and old versions can be synchronized normally, with no format errors.
