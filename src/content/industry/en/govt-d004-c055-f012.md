# Tunnel Alarm Filtering: Patrol Monitoring and Alarm Judgment - Deployment and Upgrade

## What the data for this category looks like
Tunnel alarm filtering data comes from temperature and humidity sensors, smoke concentration sensors, structural displacement sensors, video analysis systems, and operation and maintenance collection systems deployed inside tunnels. Data is updated in real time or synchronized at minute-level intervals. A single alarm document includes 8 core fields: unique alarm identifier, associated device code, alarm type code, trigger time, threshold reference value, current measured value, affiliated tunnel ID, and alarm level. Field units vary by alarm type: temperature and humidity alarms use degrees Celsius and percentage, displacement alarms use millimeters, and time fields follow the ISO 8601 standard format.

## What constraints these characteristics impose during deployment and upgrade
The real-time update rhythm of tunnel alarm data requires high-concurrency database connections and caching mechanisms to be configured during deployment, to avoid alarm packet loss or delays. The multi-field alarm structure requires full-field data verification rule configurations to be completed during deployment, to prevent abnormal fields from entering the filtering logic. The need to associate multi-device data across multiple tunnels requires a rolling update strategy to be adopted during upgrades, to avoid alarm interruptions caused by full service restarts. Additionally, alarm data has no unified fixed unstructured additional content, so no additional large file storage parameters need to be configured during deployment. Only read and write performance for structured data needs to be adapted.

## How to configure the settings
The following configuration items are formulated based on the deployment specifications of FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 100–150 connections | Adapts to the real-time high-concurrency read and write requirements of tunnel alarms, and avoids database connection exhaustion |
| `MONGODB_URI` | Intranet IP:27017/fastgpt_tunnel_alarm | Tunnel alarms are structured time-series data, and MongoDB is suitable for high-frequency writes and multi-condition queries |
| `REDIS_URL` | Intranet IP:6379/0 | Used to cache the mapping relationship between tunnel devices and alarm types, reducing repeated database query overhead |
| `STORAGE_S3_ENDPOINT` | Leave blank | Tunnel alarms have no large-volume attachment data, so no object storage service needs to be configured |
| `ROOT_KEY` | Randomly generated 32-bit string | Used for interface authentication between services, ensuring access security of the alarm filtering logic |
| `FE_DOMAIN` | Intranet domain name of the deployment node | Used to generate alarm detail jump links, linking to the operation and maintenance management page of the corresponding tunnel |

## Three common configuration mistakes
- Phenomenon: After deployment, the alarm filtering configuration fails to take effect after saving, and default parameters are still displayed after the service is restarted. Cause: The environment variable configuration file was not loaded correctly, causing parameters such as `ROOT_KEY` to not be read by the service.
- Phenomenon: Database connection timeout errors occur after upgrade, with a 503 status code returned. Cause: The `DB_MAX_LINK` parameter was not adjusted to adapt to the concurrent load after upgrade, causing the connection pool to be exhausted.
- Phenomenon: No corresponding jump link is generated after submitting a simulated alarm. Cause: `FE_DOMAIN` was not correctly configured as the actual access address of the deployment node, causing link generation to fail.

## How to confirm successful configuration
- Execute the database connection test command to verify that the services pointed to by `MONGODB_URI` and `REDIS_URL` can connect normally.
- Submit a piece of simulated data that conforms to the tunnel alarm format, and check whether the filtering logic completes screening and marking according to the configured rules.
- Access the operation and maintenance page bound to `FE_DOMAIN` to confirm that the alarm jump link can normally open the management interface of the corresponding tunnel.
- View the service operation logs to confirm that there are no connection exhaustion errors related to `DB_MAX_LINK`, and the service status is stable.

The values provided are common starting points and should be measured against the reader's own samples.
