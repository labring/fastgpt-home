# Policy and Regulatory Basis Q&A for Real Estate Registration: Knowledge Base Retrieval and Recall

## What the Data for This Category Looks Like
This category covers all resources related to the full real estate registration workflow. Data sources include real estate registration information systems, cadastral survey databases, housing transaction online signing systems, tax systems, and electronic certificate repositories. Updates occur daily. Daily documents include registration applications, ownership certificates, surveying and mapping results, tax payment vouchers, real estate ownership certificates, and registers. These include both structured form documents and semi-structured certificates, plus structured data exported from systems. Fields cover real estate location, right holders, ownership sources, restriction status, and more, with units such as area and parcel number.

## Constraints Imposed on Knowledge Base Retrieval and Recall
The multi-source, daily updated data requires the retrieval link to support real-time recall of the latest data. This prevents ownership verification errors caused by outdated data. Diverse document structures include both standardized form fields and non-standardized certificate text. The retrieval chunking strategy must adapt to the information density of different documents, to avoid information fragmentation or oversized chunks from a single granularity. The large volume of structured system data requires precise control of the recall scope, to prevent irrelevant data from occupying context resources. The high-risk nature of ownership verification also requires recall results to have high matching accuracy, reducing mismatches.

## Configuration Settings
The following configurations are adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Matches the precise semantics of real estate ownership and policies, avoids mixing irrelevant content with low similarity, and meets the high accuracy requirements of ownership verification |
| `limit` | Top 6 entries | Controls the number of results recalled in a single request, reduces token consumption, while covering sufficient ownership-related reference information |
| `searchMode` | semantic | Prioritizes matching semantically relevant policy clauses and business data for semantic policy Q&A related to real estate registration |
| `usingReRank` | Enabled | Re-ranks initial recall results to improve the display priority of high-match content, adapting to the high-risk ownership verification scenario |
| `datasetSearchUsingExtensionQuery` | Disabled | This scenario must be strictly limited to the policy and internal data scope of real estate registration, no need to extend the query scope |

## Three Common Misconfigurations
- Initial recall chunks are too large, leading to excessive token consumption. Symptoms include interface return token limit errors or prolonged response times. The cause is failure to adjust the chunking strategy for structured form data of real estate registration, using generic chunking parameters that cause single chunk content to exceed the context bearing limit.
- Recall results do not filter irrelevant chat content, leading to invalid information being included. Symptoms include retrieval results containing daily conversation content unrelated to policies and ownership verification. The cause is not setting a reasonable `similarity` threshold, or not limiting the retrieval scope to only cover real estate registration policies and business data.
- No recall limit or re-ranking configured, leading to redundant data occupying context. Symptoms include context window overflow, with core ownership information being pushed to a secondary position. The cause is not setting the `limit` parameter or not enabling `usingReRank`, leading to recall of excessive low-match content.

## How to Verify Correct Configuration
- Upload a single real estate registration application or ownership certificate document, initiate a query with corresponding semantics, and check whether the `similarity` score of the recall results falls within the preset range.
- Initiate a daily chat-style query, confirm that the retrieval result is empty or returns no irrelevant content, to verify that the filtering logic is effective.
- Initiate multiple ownership verification queries, count the number of results recalled in a single request, and confirm that it matches the `limit` parameter setting.
- Check the knowledge base synchronization log, confirm that daily updated data has been correctly included in the retrieval scope, to verify data timeliness.

The values provided are common starting points and should be measured against the reader's own samples.
