# Policy and Regulatory Basis Q&A for Real Estate Registration: Deployment and Upgrade

## What the data for this use case looks like
Business data for the real estate registration scenario comes from the real estate registration information system, cadastral survey database, housing transaction online signing system, tax system, and electronic certificate repository. Daily processed documents include registration applications, ownership certificates, survey results, tax payment vouchers, real estate ownership certificates, and real estate registers. Data updates once per day. Fields cover right holder, location, right type, area, and other items. Units include square meters, parcel count, and others. Each individual business data entry links to multiple cross-system documents and verification information.

## What constraints these characteristics impose on deployment and upgrade
Because business data comes from multiple cross-departmental collaborative systems, the deployment phase must configure multi-data source connection capabilities to ensure synchronous consistency of data across systems. The daily data update frequency requires deploying scheduled synchronization tasks to maintain data freshness. Execution times for synchronization tasks must be scheduled outside business peak hours to avoid occupying government system resources. Diverse business document types and some large file sizes require adapting chunking and storage strategies for different document types, to prevent vector database storage overload. Ownership information links to multiple types of verification data. Sufficient database connection pool resources must be reserved during deployment to prevent connection conflicts caused by concurrent calls from multiple systems.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Exclusive connection string pointing to the real estate registration business database, with read-write split node addresses configured | Core business data is stored in the MongoDB business database, requiring stable connection and read-write performance |
| `REDIS_URL` | Configured as the local cache instance address, with connection timeout set to 300 seconds | High-frequency queries of policy documents require cached results to reduce pressure from cross-system calls |
| `STORAGE_S3_ENDPOINT` | Points to the government cloud object storage endpoint, with storage bucket permissions set to read-only access | Large files such as survey results and electronic certificates are stored in government cloud object storage, requiring secure access |
| `DB_MAX_LINK` | Set to 20-30 connections | Daily synchronization of cross-system data requires controlling connection pool usage to avoid competing for resources with business systems |
| Scheduled synchronization task configuration | Set to run full synchronization at 2:00 AM daily, with incremental synchronization interval set to 1 hour | Matches the daily business data update frequency, balancing data timeliness and system load |

## Three common configuration errors
- Symptom: FastGPT v4.17.0 Docker container restarts continuously, and the frontend page fails to load. Cause: `REDIS_URL` or `MONGODB_URI` is not configured correctly, causing the service to fail to connect to dependent databases or cache instances, resulting in startup self-check failure.
- Symptom: Ownership information returned by policy Q&A is incomplete, with some survey result content missing. Cause: `STORAGE_S3_ENDPOINT` is not configured, making it impossible to read survey result files stored in object storage, resulting in incomplete chunked index data.
- Symptom: Permission exception is returned when calling the non-commercial version policy Q&A interface. Cause: Key usage duration and call frequency limits are not configured for business requirements, resulting in non-compliance with compliance verification rules for government scenarios.

## How to confirm the configuration is complete
- Log in to the FastGPT backend management page, check the data source configuration module, and confirm that the connection status of parameters such as `MONGODB_URI` and `REDIS_URL` shows normal.
- Run a manual full synchronization task once, and verify that the number of synchronized documents matches the registered data volume in the real estate registration business system.
- Initiate a test query, enter a standardized business question, and confirm that the returned result includes relevant associated document fragments such as ownership certificates and survey results.
- View container runtime logs, and confirm that there are no error messages related to database connection timeouts, storage access failures, or missing configuration items.
