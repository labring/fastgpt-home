# Policy and Regulatory Basis Q&A for Property Rights, Asset and State-owned Capital Management: HTTP Interfaces and External Systems

## What this data category looks like
This data category mainly originates from state-owned assets supervision information systems, enterprise asset management systems, property rights exchange systems, evaluation agency reports, and financial statements. Daily processed documents include property rights registration forms, asset evaluation reports, property rights transfer plans, on-site transaction announcements, and asset disposal approval documents. It contains both structured fields and unstructured text content. Core fields cover asset numbers, ownership status, evaluation results, transaction approval numbers, and similar items. The update frequency is monthly. The scale of data pulled in a single request varies based on the total number of assets.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Multi-source, heterogeneous data sources require interfaces to support authentication rules and data formats from different systems. This prevents call failures caused by differences in access protocols. The monthly update frequency does not require frequent interface calls. However, a single request may involve batch asset data, so request limits and timeout durations must be configured appropriately. Documents include both structured fields and unstructured text formats. Interfaces must support precise queries using structured fields, while also handling parsing requests for unstructured documents. Data accuracy requirements are high. Interfaces must include error retry and verification mechanisms to avoid compliance risks from data transmission errors.

## How to configure settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer {custom secret}, rotate every 600 seconds | Interface security must be ensured when connecting to state-owned assets systems, and the monthly updated data source does not require frequent secret rotation |
| `variables` | Pass 8–12 core fields including asset numbers and ownership status | Matches the core identifiers and business attributes of this data category, ensuring Q&A calls can associate the policy basis of the corresponding asset |
| `responseData` | Return policy article fragments and business document summaries, in JSON array format | Adapts to the text extraction needs of policy and regulatory basis Q&A, facilitating subsequent processing and display |
| Timeout setting | 300–600 seconds | Handles batch asset data queries and long document parsing, matching the response rhythm of state-owned assets systems |
| Retry count | 2 times | Copes with temporary fluctuations in state-owned assets systems, reducing the probability of single request failure |
| Batch request limit | First 50 entries of data | Matches the monthly updated data scale, avoiding interface overload that affects other business calls |

## Three common configuration errors
- Failing to configure the asset number field in `variables` when calling the interface, resulting in returned policy bases not matching the target asset. The cause is failure to associate the unique core business identifier of this data category.
- Attempting to directly pass a PDF file of an asset evaluation report as an input parameter without success, with a 400 status code returned. The cause is failure to explicitly declare the `Content-Type: multipart/form-data` request header. The FastGPT HTTP tool requires this format to process file input parameters.
- Failing to set a reasonable timeout duration, with no retry mechanism triggered after request timeout, resulting in a 504 status code returned. The cause is that the default timeout duration is too short, not matching the response rhythm of state-owned assets systems.

## How to verify a successful configuration
- A test request is initiated with a known asset number, and the returned `responseData` is checked for policy basis fragments corresponding to the asset.
- Interface logs are reviewed to confirm that the `Authorization` parameter is correctly carried, with no authentication failure related logs present.
- A batch request is tested with 5 entries of asset data, and the number of returned results is verified to match the number of requested entries.
- Temporary network fluctuations are simulated to verify whether the retry mechanism is triggered, with no consecutive failure error reports observed.
