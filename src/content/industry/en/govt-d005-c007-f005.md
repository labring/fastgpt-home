# Policy and Regulatory Basis Q&A for Petition Matter Handling: Tool Calling and Plugins

## What this category of data looks like
This category of data mainly comes from the national petition information system, local petition systems, the 12345 government service platform, grassroots governance platforms, and historical petition archives. Daily processed documents include petition registration forms, acceptance notices, transfer and assignment letters, handling opinions, review and recheck applications, and resolution plans. Fields cover request content, acceptance number, responsible unit, handling progress, policy basis association items, and other relevant details. Data is synchronized daily. Core data is generated around the full-process handling nodes of petition matters, and no additional statistical fields are included.

## Constraints on tool calling and plugins
The data sources for this category are scattered, and updates occur daily. Tool calling must support real-time pulling of multi-source data and unified format parsing to avoid data misalignment or omissions. Daily processed document types are diverse, and their fields are fixed. Tools must adapt to different document structures to ensure accurate extraction of core business information. Policy basis Q&A must strictly match legal policy documents. Tool calling must link to the official petition policy library to ensure returned content complies with the legal procedure requirements of petition handling. Petition matter handling processes have clear stages. Tool calling results must align with existing handling nodes, and content beyond the legal scope must not be generated.

## Configuration settings
The following configurations are based on FastGPT v4.17.0.

| --- | --- | --- |
| `toolChoice` | `auto` | Adapt to the dynamic needs of petition matters, allowing the model to independently determine whether to call tools to obtain policy basis |

| Custom plugin timeout | 60 seconds | Match the response rhythm of petition system interfaces, preventing process interruptions caused by excessive waiting time |
| `functionCall` | Enable mandatory format validation | Ensure that tool call return results comply with the field specifications of petition business |
| Question optimization | Calibrate based on actual testing | Optimize colloquial expressions of petition requests to improve policy matching accuracy |

## Three common misconfigurations
- Symptom: A 504 timeout error is returned when calling a custom plugin to query petition policies. Cause: No reasonable plugin timeout value is set, exceeding the response threshold of the petition system interface.
- Symptom: The number of policy items returned after tool calling far exceeds expectations. Cause: The single search limit is not configured, or the set number of entries exceeds the business requirement range.
- Symptom: The model cannot accurately determine whether it needs to read petition archive files. Cause: No file reading trigger rules are configured, or the automatic decision-making mode of `functionCall` is not enabled.

## How to verify successful configuration
- Submit a test petition request, check the tool calling log to confirm whether the expected plugin or tool call is triggered.
- Review the returned policy basis content to confirm that the source is the official petition system or the designated policy library, and the format complies with business document requirements.
- Simulate a timeout scenario to verify that the plugin returns results within the set timeout period, with no unresponsive situations occurring.
- Adjust the `toolChoice` parameter to verify whether the model can independently determine whether to call tools to obtain policy basis based on the request.

The values provided here are common starting points and should be measured against the reader's own samples.
