# Policy and Regulatory Basis Q&A for Public Data Catalog and Opening: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Data for this category originates primarily from local public data opening platforms, integrated big data platforms, departmental business databases, and electronic certificate repositories. Updates occur once per month. Daily managed documents include public data resource catalogs, data opening lists, data item descriptions, desensitization rules, interface documents, and update frequency descriptions. Data fields include openable data item names, opening conditions, desensitization requirements, corresponding interface addresses, update cycles, and additional relevant details. All content centers on the sharing and opening boundaries of public data.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompt Engineering
Monthly data updates require that the latest update node is clearly stated in multi-turn dialogue to prevent sharing outdated opening information. Multiple structured document types mean prompts must guide conversations to focus on clear fields like data items, opening conditions, and interface rules, avoiding vague queries. Data assets from multiple sources must have their respective departments’ opening permission boundaries clarified during conversations to prevent unauthorized queries. Public data desensitization rules must be included in prompts to ensure conversation outputs meet data security requirements.

## How to Configure Settings
| Configuration Item | Recommended Approach | Basis for This Approach |
| ---- | ---- | ---- |
| `chatId` | Generate a unique identifier per conversation session | Used to distinguish public data query sessions of different users and avoid context confusion |
| `messages` | Retain the first 3 rounds of conversation context | Adapt to the monthly updated data feature and avoid introducing outdated historical information |
| `variables` | Preset "data update time" and "opening department" variables | Match the fixed fields of category documents to improve the accuracy of query results |
| Maximum context length | 800–1200 characters | Adapt to the content length of single public data documents and avoid context overflow |
| Single recall limit | Top 5 matching results | The number of public data catalog entries is controllable; too many results will disrupt conversation logic |

## Three Common Misconfigurations
- Symptom: Conversation returns "You do not have permission to operate this conversation record". Cause: The `chatId` parameter is not correctly bound, so the conversation context cannot be associated with the corresponding data permission verification logic.
- Symptom: Outdated opening data items appear in multi-turn dialogue. Cause: The number of context rounds is not limited, so expired data from previous conversations is included in new queries.
- Symptom: Returned opening interface addresses do not match the actual catalog. Cause: The prompt does not explicitly require matching data items to their corresponding interfaces, leading to incorrect recalled entries.

## How to Verify Proper Configuration
Reference only; verify against the target FastGPT release and deployment documentation.
- Initiate a single-round public data catalog query, and verify if returned results include the latest updated data items for the current region.
- Initiate two consecutive queries, and verify if the `chatId` parameter is generated for the session and if context is correctly associated.
- Trigger a query for a non-open data item, and verify if a permission prompt compliant with rules is returned.
- Check if the prompt includes clear guidance on data update time and desensitization rules.
