# Policy and Regulatory Basis Q&A for Highway Maintenance and Road Property Rights Management: Deployment and Upgrade

## What the data for this category looks like
Core data for this category comes from the highway maintenance management system, bridge and tunnel monitoring system, road administration patrol system, and traffic flow monitoring data. The update frequency is daily. Daily generated documents include maintenance plans, patrol logs, defect disposal orders, road construction permits, and road damage compensation orders. Patrol logs contain fields such as patrol section, defect location, and disposal measures. Road construction permits contain fields such as construction scope and time limit. Units include kilometers, square meters, working days, and others.

## What constraints these characteristics impose on the deployment and upgrade phase
Since data sources include multiple independent systems, deployment requires adapting to multi-data source access configurations to avoid data synchronization interruptions. Daily updated high-frequency data requires configuring incremental synchronization mechanisms during deployment to reduce resource consumption from full pulls. Diverse document types and fields require presetting multiple document parsing rules during deployment to adapt to the structural characteristics of different business documents. At the same time, the accuracy of policy and regulatory basis Q&A is directly linked to road safety and fund management. The deployment phase must ensure configuration stability and upgradability. The following configuration plan is developed based on FastGPT v4.17.0.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `10–15 connections` | Adapts to database load from high-frequency access such as daily patrol logs and defect disposal orders, preventing connection exhaustion |
| `MONGODB_URI` | Enter the cluster database address within the private network | Stores structured business data such as patrol logs and road construction permits, ensuring access security |
| `REDIS_URL` | `Local cluster cache address using port 6379` | Caches frequently queried policy clauses and search results to reduce repeated database query pressure |
| `STORAGE_S3_ENDPOINT` | Enter the endpoint address of the self-built object storage | Stores unstructured documents such as maintenance work orders and patrol photos, enabling unified file management |
| `ROOT_KEY` | Generate a complex random string | Ensures access permission security for background management interfaces, preventing unauthorized operations |
| `FILE_TOKEN_KEY` | Configure an encryption key matching the storage service | Protects access tokens for uploaded business documents, avoiding file leaks |

## Three common configuration mistakes
- Symptom: Returns a `404 Not Found` status code when calling the model service. Cause: The associated model service address is not configured correctly, preventing vector retrieval of policy clauses from triggering normally.
- Symptom: Q&A response time exceeds `600 seconds`. Cause: The `DB_MAX_LINK` parameter is not adjusted, exhausting the database connection pool and causing query queuing and blocking.
- Symptom: Inconsistent session data between nodes after cluster deployment. Cause: A unified `REDIS_URL` is not configured, and cache states across nodes cannot be shared, leading to lost Q&A context.

## How to confirm the configuration is complete
- Test the network connectivity of the configured `MONGODB_URI` and `REDIS_URL` to confirm normal access to the corresponding services.
- Upload a maintenance plan document to verify that the file access token generation function works correctly, confirming that the `FILE_TOKEN_KEY` configuration is valid.
- Initiate a policy query related to road construction permits to confirm that there is no obvious blocking in the response, verifying that the `DB_MAX_LINK` configuration is appropriate.
- Start a multi-node deployment to verify that session and cache data can be synchronized normally between nodes, confirming that the cluster configuration takes effect.
