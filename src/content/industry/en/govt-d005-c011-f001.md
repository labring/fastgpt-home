# Policy and Regulatory Basis Q&A for Pension, Work Injury, and Unemployment Benefit Verification: HTTP Interfaces and External Systems

## What this category of data entails
Data sources for this category include social insurance management systems, personal benefit records, labor relations and work injury identification systems, and the electronic social security card platform. The update frequency is once per day. Commonly processed documents include benefit application forms, payment duration certificates, retirement approval forms, work injury identification materials, and unemployment insurance benefit application materials. Data fields cover cumulative payment duration, benefit calculation rules, eligibility review judgment basis, and other related content. There is no fixed unified statistical caliber or preset values. All fields are generated around the core business logic of benefit verification.

## What constraints do these characteristics impose on the HTTP interface and external system link
The data sources for this category are scattered and updated daily. HTTP interfaces must adapt to multi-system authentication and data synchronization logic, and avoid returning expired or cross-region incorrect regulatory basis. There are various types of daily documents, so interfaces must support parsing business materials in different formats to ensure the accuracy of field extraction. At the same time, errors in benefit verification directly affect fund security and public rights and interests. Interfaces must add multi-layer parameter verification to block call requests that do not comply with business rules, and prevent incorrect or missed benefit payments caused by parameter errors.

## Three common mistakes
- Phenomenon: After calling the interface to create a knowledge base, the conversation interface cannot associate the newly created knowledge base. Cause: The correct knowledge base association identifier is not passed in the interface request parameters, or the binding configuration between the knowledge base and the target application is not completed.
- Phenomenon: A 400 status code is returned when uploading an image link, and the log contains `message": "400 do request failed: Post "https://xxx stre`. Cause: The format of the uploaded link is non-standard, or the public access permission of the image resource is not configured, causing the interface to fail to normally pull the image content.
- Phenomenon: Under the same application, model, and knowledge base, the results returned by online conversation and API call differ significantly. Cause: The `stream` and `detail` parameters are not correctly set during API calls, or the context window configuration is inconsistent with the online conversation scenario.
