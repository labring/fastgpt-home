# Policy and Regulatory Basis Q&A for Pension, Work-related Injury, and Unemployment Benefit Verification: Workflow Orchestration

## What this category of data looks like
Data sources for this category include social insurance management systems, personal benefit records, labor relations and work-related injury identification systems, and the electronic social security card platform. The update frequency is daily. Daily processed documents include benefit application forms, payment period certificates, retirement approval forms, work-related injury identification materials, and unemployment insurance benefit application materials. Data fields include cumulative insured duration, benefit calculation benchmark parameters, qualification review material identifiers, and benefit distribution cycle identifiers. Associated units for fields include year and distribution count. The number of fields in a single business document varies slightly based on business type.

## What constraints do these characteristics impose on the workflow orchestration link
Data sources for this category are scattered. Update frequency is high. Business document types are diverse. These factors create multiple constraints for workflow orchestration.
Configure cross-system data pull nodes to synchronously pull multi-source business data. This ensures complete matching of policy basis.
Set a scheduled synchronization step to meet the daily update requirement. This ensures timeliness matching between business data and policy texts.
Use `variables` to define parameter rules for different business scenarios when processing multiple types of business documents separately. This avoids field confusion.
Embed the qualification review verification node into the workflow. This intercepts material data that does not meet policy requirements. It reduces the risk of subsequent errors.

The following configurations are based on FastGPT v4.17.0.

| `variables` | Define parameters separately for pension, work-related injury, and unemployment businesses. | Timeout setting | 600 seconds | Cross-system data pulling and policy matching require a certain amount of time. This duration covers most normal business processes |
| Question optimization component position | After the user input node | First optimize user questions related to benefit verification. Clarify core demands before executing subsequent processes |

## Three common misconfigurations
- Symptom: Workflow conversation logs show no content, and no return content is generated. Cause: Trigger rules for cross-system data pull nodes are not configured. This prevents acquisition of business-related data. The workflow cannot execute normally.
- Symptom: The model works normally during individual testing, and model response logs can be received in the background, but workflow conversation shows a failure. Cause: `nodeId` configuration between workflow nodes is incorrect. This interrupts data flow. The model response result cannot be passed to subsequent nodes.
- Symptom: Policy matching results do not match actual business requirements. Benefit calculation deviations occur. Cause: Parameter rules for the corresponding business are not defined via `variables`. Unified matching logic is used across different business scenarios.

## How to confirm correct configuration
- Manually trigger the workflow. Check log output for each node. Confirm that `variables` parameters load correctly based on business type.
- Simulate user input for pension, work-related injury, and unemployment businesses. Verify whether the workflow triggers the corresponding policy matching node.
- Adjust the context length limit value. Check whether core information in matching results is complete. Confirm the value meets current business scenario requirements.
- Check the timeout setting value. Simulate a cross-system data pull scenario. Confirm the workflow does not experience unresponsive states.
