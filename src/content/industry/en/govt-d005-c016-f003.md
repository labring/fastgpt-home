# Policy and Regulatory Basis Q&A for Medical Insurance Expense Settlement Audit: Multi-turn Dialogue and Prompt Engineering

## What This Category of Data Looks Like
Data is sourced from the national medical security information platform, hospital HIS and medical insurance interfaces, medical insurance catalog and coding library, and cross-regional medical settlement platform, with daily updates. Daily processed documents include medical insurance settlement lists, expense details, medical record homepages, prescriptions, rejection lists, and settlement reconciliation statements. These contain standardized fields such as diagnosis and treatment item codes, drug and consumable codes, expense amounts, insured person identifiers, and settlement times, with no custom non-standard units.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompt Engineering
The daily updated medical insurance coding library requires prompts to synchronize the latest version data regularly, to avoid using expired codes for expense matching. Mixed input of multiple types of business documents requires the dialogue flow to clearly distinguish the field attribution of different documents, to prevent confusion between settlement data and medical record data. Multi-source data access requires prompts to specify the verification rules for each interface’s data, to ensure consistency between expenses, prescriptions, and settlement documents. The processing requirements for single or batch settlements require multi-turn dialogue to track the full audit process nodes of a single business, to avoid context loss.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Maximum Context Length | 800–1200 characters | Adapts to the total text volume of a single batch of settlement documents, to avoid exceeding the model’s context capacity limit |
| Dialogue variables `variables` | Inject the daily updated medical insurance coding library version number | Ensure the dialogue always uses the latest policy basis data, matching the daily updated data sources |
| Dialogue history `messages` | Retain the most recent 20 rounds of interactions | Track multi-turn audit requests for a single settlement expense, avoid repeated questions and context breaks |
| Session ID `chatId` | Bind to each settlement business order number | Enable full-process dialogue traceability for a single business, matching the business archiving requirements of medical insurance handling agencies |
| Dialogue Log Retention Period | 30 days | Complies with the business log archiving cycle of medical insurance handling agencies, meeting compliance traceability requirements |

## Three Common Misconfigurations
- Prompts fail to correctly identify code fields separated by spaces in expense details, leading to failed code matching. The cause is that the prompt does not explicitly require retaining the original text format and does not specify the identification rules for code fields.
- Multi-turn dialogue context cannot be maintained when calling the application across sessions, leading to interruption of the audit process. The cause is that the `chatId` parameter is not correctly bound, and a new independent session is generated for each call.
- Dialogue logs are lost and cannot be used to trace the business audit process. Post-investigation shows that the log retention duration is not configured, or the docker container is not correctly mounted to the log directory. The cause is that the dialogue log retention rules are not configured as required, or the container configuration does not correctly map the log storage path.

## How to Verify Correct Configuration
- This test uses FastGPT v4.17.0. A simulated settlement document is submitted, and the dialogue’s automatic association with the corresponding medical insurance coding library data is verified, confirming whether `variables` correctly injects the latest version identifier.
- Multi-round follow-up questions are initiated, and the dialogue history is checked for retention of previous audit requests, confirming that the round limit setting for the `messages` parameter is reasonable.
- The session list is reviewed, confirming that each settlement document corresponds to a unique `chatId`, achieving binding between the business and the session.
- The system log directory is checked, confirming that the dialogue logs are retained for the configured duration, and that the docker mount path is correctly configured.

The values provided here are common starting points, and should be evaluated against the samples used in the actual deployment scenario.
