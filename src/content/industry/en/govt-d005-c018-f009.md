# Policy and Regulatory Basis Q&A for Social Insurance Participant Registration and Payment Verification: Model Access and Configuration

## What Data for This Category Looks Like
Data sources for this category include social insurance handling systems, tax social insurance premium collection systems, market entity registration information, and shared public security and civil affairs data. Daily processed documents include social insurance participant registration forms, payment base declaration forms, staff change forms, social insurance premium verification notices, and personal benefit records. Data updates occur once daily. Core fields include personal identity information, labor relationship status, payment base, verified amount, and other related items. Typical users are social insurance handling agencies, human resources and social security bureaus, tax authorities, and personnel and finance departments of employing units. Core data processing links include identity verification, staff changes and base declaration, and cross-system reconciliation.

## Constraints on Model Access and Configuration
Multiple heterogeneous data sources require model access configuration to support cross-system data retrieval, avoiding limitations of a single data source. The daily data update frequency requires knowledge base synchronization tasks to be configured for incremental updates, ensuring the model can access the latest participant and payment data. Differences in structure across business documents require chunking strategies adapted to form field structures, preventing context fragmentation. The strictness of core fields requires model responses to strictly match policy basis, reducing randomness to lower error potential. The cross-system reconciliation requirement demands the model to associate data from different systems, avoiding responses that rely solely on a single data source.

## Three Common Misconfigurations
- Symptom: The system cannot select a local model configured via OpenAPI, and defaults to calling a generic model. Cause: `AIPROXY_API_TOKEN` is not bound to the corresponding model instance in the model access configuration, causing the system to fail to recognize the configured model.
- Symptom: A locally deployed 14b model attached to a social insurance knowledge base returns a call error. Cause: The `maxContext` parameter is not adjusted to fit the local model's context limit, and intranet access permissions are not configured, causing knowledge base data to fail to load normally.
- Symptom: Responses include irrelevant benefit verification content, deviating from the social insurance participant payment scenario. Cause: The retrieval data source is not limited to social insurance handling systems and tax social insurance premium collection systems, leading to unintended retrieval of knowledge base data from adjacent categories.

## How to Confirm Successful Configuration
- Check model access configuration items, confirm that `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` match the deployed model instance.
- Trigger a knowledge base synchronization task, verify that category-specific documents such as social insurance participant registration forms and payment base declaration forms appear in the synchronization log.
- Submit a test query, verify that the model's returned responses only associate policy basis from the social insurance participant payment phase, and do not include content from other business scenarios.
- Adjust the `temperature` parameter, verify response consistency, and confirm that policy reference accuracy is not impacted by randomness.
