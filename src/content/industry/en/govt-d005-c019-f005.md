# Q&A on Policy and Institutional Basis for "Double Random, One Public" Regulatory Inspections: Tool Calling and Plugins

## What this category of data looks like
This category of data mainly comes from the "Double Random, One Public" regulatory platform, enterprise credit information disclosure system, industry regulatory systems, and law enforcement officer directory. The update frequency is monthly.
Daily documents include inspection plans, inspection object lists, inspection item lists, on-site inspection records, rectification notices, and inspection result announcements. The inspection object list must include fields such as main entity name and unified social credit code. The inspection item list must clearly specify regulatory item categories and inspection standards. The inspection result announcement must mark content such as inspection time, inspectors, and rectification requirements.

## Constraints imposed on the tool calling and plugins link by these characteristics
Monthly updated data sources require the plugin's synchronization cycle to match the monthly rhythm. This avoids calling expired data.
Differences in the structure of multiple document types require differentiated parsing rules for tool calling. Rules must be configured for different documents such as inspection plans and inspection object lists, to ensure accurate field extraction.
Decentralized data sources require the plugin to connect to multiple regulatory systems. This allows aggregation of required inspection item, object, and law enforcement officer information.
Calls to the law enforcement officer directory must be linked to the inspection task generation logic. This ensures extracted law enforcement officers meet regulatory qualification requirements, and avoids issues where law enforcement officer qualifications do not match.

## How to set configurations
The following configurations are formulated based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| `toolChoice` | `auto` | This scenario requires automatic matching of tool calls for corresponding regulatory documents based on user questions. No mandatory specification of a single function is needed. |
| `functionCall` | `["get_check_list", "get_object_list", "get_punish_notice"]` | The core tools for this scenario are three types of documents: obtaining inspection item lists, inspection object lists, and rectification notices. A pre-defined list of callable functions is required. |
| Data source synchronization cycle | `30 days` | The update frequency of this category of data is monthly. A 30-day synchronization matches the data update rhythm, avoiding calls to expired information. |
| Document parsing rules | Set based on actual testing | The document structures of this category vary greatly. Exclusive parsing rules must be configured for different documents such as inspection plans and inspection result announcements. |
| Single tool call upper limit | `Top 5 entries` | This scenario requires prioritizing returning the latest monthly inspection-related data. Too many entries will exceed the context length. |
| Plugin timeout threshold | `60 seconds` | Regulatory system interface responses usually take a certain amount of time. 60 seconds covers most normal call scenarios. |

## Three common mistakes
- Symptom: The tool call returns the "chat:llm-model-response-empty" error. Cause: The callable function list for `functionCall` is not configured correctly. This causes the large language model to fail to match the corresponding tool and generate valid call content.
- Symptom: Fields in the inspection object list returned by tool calls are missing. Cause: Exclusive parsing rules are not configured for the inspection object list. This results in incomplete structured field extraction.
- Symptom: The number of results returned by tool calls exceeds the expected upper limit. Cause: No single tool call upper limit is set. This results in pulling too much historical data that exceeds the context carrying capacity.

## How to confirm correct configuration
- Trigger a test call with the input "Query this month's inspection item list". Confirm that the tool automatically calls the corresponding function and returns correct inspection item data.
- Check the data source synchronization log. Confirm that the latest regulatory platform data is automatically pulled every 30 days, with no expired data errors.
- Check the return results of tool calls. Confirm that the extracted inspection object list includes required fields such as main entity name and unified social credit code.
- Test the timeout scenario. Confirm that the plugin triggers reasonable timeout handling logic when the interface response exceeds 60 seconds.

The values provided are common starting points and should be measured against the reader's own samples.
