# Policy and Regulatory Basis Q&A for Centralized Treasury Payment and Reimbursement Audit: Workflow Orchestration

## What the data for this category looks like
Business data for this category comes from the centralized treasury payment system, unified budget management system, electronic invoice platform, and contract management system. Daily processed documents include payment applications, fund appropriation plans, invoices, contracts, acceptance reports, reimbursement approval forms, and payment vouchers. Data updates daily. Core service targets include budget unit finance staff, finance treasury payment center staff, and department finance audit positions. This use case focuses on compliance audits for individual fund payment execution stages: verifying budget indicators and economic classification codes, reviewing the complete chain of invoices, contracts, and acceptance reports, and processing return orders and payment corrections. This page is written using the workflow orchestration features of FastGPT v4.17.0.

## What constraints do these characteristics impose on the workflow orchestration link
The multi-source nature of business data requires the workflow to connect multiple independent data source nodes, ensuring retrieved policy documents match current business system data. The daily update frequency requires the knowledge base to be configured with daily incremental sync tasks to avoid retrieving outdated policy references. Diverse document types require the workflow to set retrieval filtering rules based on document categories, to accurately match different types of business documents such as payment applications and reimbursement vouchers. Single-payment audit scenarios require the workflow to trigger retrieval for individual business data, avoiding resource waste and matching confusion caused by batch retrieval. High demand for exception handling requires the workflow to preset branch nodes for return orders, payment corrections, and other scenarios, ensuring exception scenarios automatically route to corresponding processing links.

## How to configure the settings
| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| `variables` | Bind single payment ID, budget indicator code, economic classification code | Audits for this category require precise matching of core fields for individual businesses. Passing data via `variables` allows direct calling of corresponding business data in knowledge base retrieval nodes, avoiding manual input errors |
| `nodeId` | Set as the unique identifier of the knowledge base retrieval node | When multiple retrieval nodes exist in the workflow, `nodeId` is required to distinguish call paths for different data sources, avoiding parameter transfer confusion |
| Number of results returned per retrieval | Top 3 | Policy references for this category require precise matching; too many results increase audit burden, and the top 3 results cover core compliance references |
| Knowledge base sync frequency | Daily sync | Business data updates daily, so the retrieved knowledge base must stay synchronized with business system data |
| Exception branch trigger threshold | Trigger when matching confidence is below 70% | Errors in this category have serious consequences, so low matching results require manual review to ensure compliance |
| Retrieval trigger condition | Trigger upon submission of a single business item | This category focuses on single payment audits, so retrieval must start when each payment application is submitted to avoid invalid retrieval |

## Three common configuration mistakes
- Phenomenon: The knowledge base retrieval node in the workflow cannot reference global `variables`, and an error indicating an undefined field is reported during runtime. Cause: The corresponding centralized treasury payment business field was not bound in the workflow's global parameter configuration, or the retrieval node did not correctly call the parameter name in `variables`.
- Phenomenon: A timeout error occurs during workflow runtime, with the log showing status code 504. Cause: A reasonable retrieval timeout period was not set, or the response delay of the connected multiple systems exceeded the threshold.
- Phenomenon: The retrieved policy documents do not match the economic classification of the current payment. Cause: No limiting condition for the economic classification was added to the retrieval prompt, or the retrieval scope was not filtered by business document type.

## How to confirm the configuration is complete
- Enter the workflow's parameter configuration page and verify that the business fields bound in `variables` match the fields in the centralized treasury payment system.
- Submit a test payment application and check whether the documents returned by the retrieval node include policy references corresponding to the budget indicators.
- Check the exception branch trigger logic to confirm whether it automatically routes to the manual review node when the matching confidence is below the set threshold.
- View the workflow runtime log to confirm that the retrieval node call path corresponding to `nodeId` is correct, with no parameter transfer errors.
