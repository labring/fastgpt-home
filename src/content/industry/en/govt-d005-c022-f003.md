# Policy and Regulatory Basis Q&A for Land Use Rights, Mining Rights, and State-Owned Property Transactions: Multi-Turn Dialogue and Prompting

## What this category’s data looks like
Core data for this category comes from the national public resource trading platform, natural resource trading systems, property right exchange systems, and state-owned asset supervision systems. The update frequency is daily. Daily processed documents include transfer announcements, trading notices, bid application materials, margin vouchers, transaction confirmation documents, listing result announcements, and property right transfer specifications. Common data fields include trading subject ownership information, trading process requirements, margin rules, transaction confirmation clauses, and similar content. There is no unified fixed format, but all content revolves around the full transaction workflow.

## What constraints these characteristics impose on the multi-turn dialogue and prompting link
Daily updated data requires multi-turn dialogue to link to the latest transaction documents, and avoid using expired information. Diverse document types and scattered fields mean prompts need to match retrieval rules for different documents separately, to accurately locate core content such as ownership, margin, and transaction confirmation. The uniqueness of trading subjects requires multi-turn dialogue to bind a unique identifier, to avoid context confusion between different subjects. At the same time, errors directly relate to state-owned assets and transaction compliance, so prompts must strictly limit the retrieval scope to only policy and transaction documents.

## Configuration Settings
These configurations are formulated based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique ownership number of the trading subject | Ensure multi-turn dialogue always links to the same trading subject, avoiding cross-context confusion |
| `messages` | Retain the first 20 turns of dialogue content | Cover the full transaction workflow context from subject query, ownership verification to margin confirmation |
| Single search limit | Top 8 entries | Match the conventional number of retrieval entries for this category’s transaction documents, filtering redundant information |
| Context window size | 8000–12000 token | Accommodate multi-turn dialogue and multiple transaction document contents, calibrated based on actual testing |
| Question optimization | Enabled | Convert scattered user queries about ownership or processes into standardized policy matching questions, improving retrieval accuracy |
| `variables` | Pass in trading subject type and number | Limit the retrieval scope to only transaction documents of the specified category, avoiding interference from irrelevant data |

## Three Common Misconfigurations
- Empty conversation logs: Phenomenon: The interface displays empty conversation logs for yesterday and today after invoking the workflow. Cause: The `chatId` is not correctly bound, causing the conversation context to not be persistently stored.
- Tool call failure: Phenomenon: The workflow conversation shows a failure, and response logs exist in the model backend. Cause: The trading subject parameters in `variables` are not correctly passed to the search node, causing the retrieval scope to deviate from the target documents.
- Missing historical dialogue: Phenomenon: Historical conversation content cannot be obtained when invoking `searchTest`. Cause: The `messages` parameter is not correctly included in the request, causing context loss.

## How to Verify Proper Configuration
- Initiate a query for a specific trading subject, check if the associated `chatId` identifier is displayed on the conversation interface.
- Launch 3 consecutive follow-up queries related to the same subject, verify that the full content of previous questions and answers is retained on the conversation interface.
- Trigger a search action, confirm that the returned documents come from specified data sources such as the national public resource trading platform.
- View the workflow running logs, confirm that the `messages` and `variables` parameters have been correctly passed to the corresponding nodes.
