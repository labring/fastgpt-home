# Policy and Regulatory Basis Q&A for Work Safety Hazard Investigation and Governance: Model Access and Configuration

## What the data for this category looks like
This category of data includes daily documents such as hazard investigation checklists, hazard management ledgers, rectification notices, review records, and major hazard listing and supervision notices. Data comes from safety production supervision systems, enterprise self-inspection systems for hazards, law enforcement inspection records, and accident statistics systems. The data update frequency is daily. Most documents are in structured format, with fields including hazard identification, rectification requirements, responsible parties, time limits, review conclusions, and others. No unsubstantiated statistical figures are included.

## What constraints these characteristics impose on model access and configuration
The data for this category comes from multiple dispersed sources and is updated daily. Model access and configuration must support batch loading of multi-source structured documents, to avoid delayed Q&A content caused by data synchronization delays. Daily documents contain clear responsible parties and time limits. Configuration must ensure the model can accurately extract field information, without missing key constraints. Since incorrect outputs could lead to major accidents and administrative penalties, configuration must strengthen verification steps to prevent the model from generating investigation or rectification suggestions that do not align with regulatory basis. Additionally, the fixed fields in structured documents require that context truncation rules in configuration match document lengths, to prevent key information from being cut off.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `maxContext` | `8000–12000 characters` | Daily documents for this category are mostly structured ledgers, with individual document lengths concentrated in thousands of characters. Sufficient context must be retained to ensure complete matching of regulatory basis |
| `quoteMaxToken` | `2000–3000 token` | Sufficient fragments of original regulatory text must be retained as supporting reference to match specific judgment standards for hazard investigation |
| `temperature` | `0.1–0.3` | Regulatory basis Q&A requires strict alignment with official standards. Generative content should not be divergent, to maintain output rigor |
| `AIPROXY_API_ENDPOINT` | Official access address provided by the corresponding model service provider. For local ollama calls, enter `http://localhost:11434/v1` | Ensures stable model call links, adapting to synchronous requests for multi-source data |
| `AIPROXY_API_TOKEN` | Exclusive authentication key provided by the service provider. Leave blank for local ollama calls | Ensures interface call security, preventing unauthorized access |
| `toolChoice` | `auto` | Can automatically call retrieval tools based on Q&A needs, matching the retrieval requirements of multi-source regulatory documents |

## Three common configuration errors
- The configured model entry does not appear in the backend model provider list. Cause: `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are not filled correctly, or the key has not been granted access permission for the corresponding model.
- No reply content appears on the frontend after Q&A is completed, only the original message is displayed in the detail panel. Cause: `maxContext` is set too small, leading to key context being truncated, so the model cannot generate valid replies.
- Call fails when attempting to access a local ollama model after upgrading to FastGPT v4.17.0. Cause: `AIPROXY_API_ENDPOINT` does not point to the correct local API address, or authentication parameters are not configured as required.

## How to confirm the configuration is complete
- Enter the model management page, check if the configured model appears in the provider list, and verify that the filled content of `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` matches the information provided by the service provider.
- Import one structured document of this category, initiate a regulatory basis Q&A, and check if the reply includes field information from the corresponding document, confirming that the context truncation rules meet the document length requirements.
- Adjust the `temperature` parameter to the set range, initiate a test Q&A, and confirm that the reply content is rigorous and free of divergent statements.
- Restart the deployment service, then initiate a test Q&A again, confirming that no uncaught exceptions occur and the reply can be normally displayed on the frontend.
