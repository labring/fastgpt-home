# Policy and Regulatory Basis Q&A for Engineering Construction Project Bidding and Tendering: Model Access and Configuration
This document applies to FastGPT v4.17.0.

## What this category of data looks like
This category of data originates from national public resource trading platforms, local public resource trading platforms, engineering approval systems, and bidding and tendering supervision systems. Updates occur daily. Daily business documents include bidding announcements, pre-qualification documents, bidding documents, tender documents, bid evaluation reports, successful bid candidate notices, and successful bid result announcements. Core business fields cover section division, qualification requirements, bid evaluation expert records, objection and complaint handling, notice corrections, and more. All documents are standardized business documents with no additional custom statistical values.

## What constraints these characteristics impose on model access and configuration
Daily updated data sources require model access to support incremental data synchronization. Full data pulling must be avoided to prevent resource occupation and synchronization delays. Multiple types of structured business documents exist in mixed formats. Configurations must adapt to the field structures of different documents such as bidding announcements and bid evaluation reports, to ensure accurate extraction of core information including qualification requirements and bid evaluation records. Bidding and tendering scenario compliance requirements mandate that Q&A results strictly match the original text of officially published documents. No unsubstantiated content may be generated. Q&A related to successful bid results must strictly link to corresponding sections and public notices. Incorrect cross-project or cross-section links must be avoided to prevent compliance risks.

## How to set the configurations
| Configuration Item | Recommended Value Range | Rationale |
| ---- | ---- | ---- |
| `maxContext` | `8000–12000 token` | Bidding and tendering documents are mostly long texts. This range covers complete context such as full bidding documents and bid evaluation reports |
| `maxTokens` | `4000–6000 token` | Policy Q&A requires generating complete and compliant responses, to avoid truncation of key content |
| `quoteMaxToken` | `2000–3000 token` | Sufficient official document original text reference fragments must be retained to ensure Q&A compliance |
| `temperature` | `0.1–0.3` | Policy Q&A must strictly match original texts, to avoid generating divergent or irrelevant content |
| `AIPROXY_API_ENDPOINT` | Set based on actual testing | Adapt to exclusive API access addresses of different cloud service providers |
| `AIPROXY_API_TOKEN` | Set based on actual testing | Used for identity verification. Must match the key provided by the service provider |

## Three common configuration errors
- Phenomenon: The Azure OpenAI model returns a protocol incompatibility error with a status code of 400. Cause: `AIPROXY_API_ENDPOINT` is not correctly configured as the Azure-specific API address, and the request format for the non-standard OpenAI protocol is not adapted.
- Phenomenon: The policy Q&A content returned by the model does not match official documents, and reference fragments are empty or incomplete. Cause: The `quoteMaxToken` parameter is not set reasonably, causing reference fragments to be excessively truncated or valid content not extracted.
- Phenomenon: The system prompts insufficient context and cannot process long bidding documents or bid evaluation reports. Cause: The `maxContext` parameter is set too low, failing to cover the full business document context length.

## How to confirm the configuration is successful
- After accessing the API of a specified cloud service provider, call the test interface to return a normal response, and verify that `AIPROXY_API_TOKEN` matches the key provided by the service provider.
- Upload a single bidding document, test that the Q&A function returns results containing fields such as qualification requirements and section division in the document, confirming that the configuration adapts to the context length of this type of document.
- Upload multiple different types of bidding and tendering documents, test that the extracted fields after parsing match the business structure of the corresponding documents, confirming that the configuration adapts to multiple document types.
- Trigger an incremental synchronization task, verify that only newly added daily documents are loaded, confirming adaptation to the daily updated data source requirement.

The values provided are common starting points and should be measured against the reader's own samples.
