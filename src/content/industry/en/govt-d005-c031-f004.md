# Policy and Regulatory Basis Q&A for Construction Project Environmental Impact Assessment Approval: Workflow Orchestration

## What this category’s data looks like
Typical participants in this category include ecological and environmental department EIA offices, administrative approval bureaus, project sponsors, and EIA institutions. Daily processed documents include environmental impact assessment reports or report forms, approval applications, public participation statements, technical assessment opinions, and EIA approvals.
Data sources cover the national unified construction project EIA declaration and approval system, ecological and environmental zoning control results, pollution discharge permit platform, and monitoring data. Update frequency is irregular, requiring dynamic synchronization with approval progress.
Data fields include core information such as project category, EIA level, pollution prevention measures, and public participation status.

## What constraints do these characteristics impose on workflow orchestration
The data characteristics of this category impose multiple constraints on workflow orchestration.
Multi-source official data sources require workflows to support parallel access to multiple interfaces and dynamic data pulling, to ensure the authority of Q&A bases.
Irregular update properties require workflows to have configurable on-demand data node refreshing, to avoid using expired policy documents.
Complex document structures require splitting processing nodes for different document types, to adapt to content parsing for different formats such as reports and approval applications.
The existence of core time-consuming links requires splitting steps such as verifying project category and EIA level, reviewing pollution prevention measures and public participation into independent nodes, to facilitate step-by-step verification and optimization.

## Three common errors
- Workflow fails to retrieve historical records after running: The symptom is that nodes return empty historical Q&A data. The cause is that the unique identifier field of the approval process is not bound in `variables`, so corresponding link historical data cannot be associated.
- Code running node passes debugging but retains think tags in formal operation: The symptom is that formal output still contains thinking content starting with `think:`. The cause is that the formal environment has not synchronized the code logic of the debugging environment, or the switch to remove thinking tags is not enabled in the node configuration.
- Knowledge base and agent are lost after project backup recovery: The symptom is that the background knowledge base and agent list are empty after restoring the project file. The cause is that the backup only contains the project configuration file, and the associated knowledge base files and agent deployment data are not synchronized, and the associated resource option is not checked during recovery.

## How to confirm the configuration is correct
- Trigger the workflow, then check if the returned policy basis comes from the preset official data source interface, to confirm the data source is correct.
- View the workflow log, confirm that the project fields in `variables` have been correctly bound and passed to subsequent nodes, to verify that the parameter configuration takes effect.
- Simulate approval process node switching, verify that historical records are normally associated and loaded, to confirm the history call configuration is correct.
- Test the exception retry mechanism, simulate temporary interface fluctuations, confirm that the workflow can automatically retry and restore normal operation.
