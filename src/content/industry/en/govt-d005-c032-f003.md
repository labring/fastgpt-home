# Policy and Regulatory Basis Q&A for Investment Project Approval and Post-Evaluation: Multi-turn Dialogue and Prompt Engineering

## What this category of data looks like
This category of data covers the entire investment process materials of entities including central enterprise strategic investment departments and state-owned asset supervision departments. Data sources include state-owned asset supervision and administration commission investment supervision systems, enterprise ERP and project management systems, industry market data, audit and financial statements. Daily documents are divided by project lifecycle into annual investment plans, project proposals, feasibility study reports, due diligence reports, asset appraisal reports and post-investment evaluation reports. Update frequency is quarterly. Documents are archived by approval, implementation and post-evaluation stages. They include core information such as project identifiers, investment scale and approval nodes.

## What constraints do these characteristics impose on the multi-turn dialogue and prompt engineering link
Quarterly updated data sources require dialogue context to be limited to valid data from the most recent two quarters. This avoids referencing outdated materials.
Multi-stage document structures require prompt words to be split and guided by approval, implementation and post-evaluation stages. This ensures dialogue focuses on policy basis for the current stage.
Multiple data sources require clear specification of retrieval scope during multi-turn dialogue. This prevents unrelated cross-system data from being included.
Risks related to state-owned assets require dialogue outputs to strictly match official policy document text. This avoids arbitrary interpretation that could lead to accountability or state-owned asset losses.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `messages` | Retain the most recent 10 dialogue turns, total tokens not exceeding 8000 | Adapt to this category's multi-stage, multi-turn policy inquiry scenarios, avoid context overload that causes model output deviation |
| `variables` | Bind the current project's approval number and affiliated industry fields | Limit retrieval scope, match this category's multi-source, staged document structure, accurately locate target policy documents |
| Maximum context length | 800–1200 characters | Adapt to the average length of single-stage documents for this category, prevent redundant data from occupying excessive model resources |
| Single search limit | Top 5 results | Correspond to the conventional retrieval result volume for core policy documents in this category, avoid excessive unrelated materials disrupting dialogue logic |
| Dialogue file expiration time | 30 days | Adapt to quarterly update frequency, balance data timeliness and storage costs |
| `chatId` | Bind the project's unique identifier | Distinguish dialogue contexts for different projects, prevent cross-project data interference |

## Three common mistakes
- Symptom: Unclosed half-width quotation mark garbled text appears at the end of dialogue output. Cause: Failure to clearly specify punctuation closure rules for output format in prompt words, leading the model to generate unexpected punctuation.
- Symptom: Token billing for a single dialogue exceeds the preset threshold. Cause: Failure to limit the retained turns of `messages`, leading to excessive accumulated tokens in the context, exceeding the model call limit of FastGPT v4.17.0.
- Symptom: After inserting a multi-task dialogue array into a batch execution node, some dialogues do not execute as expected. Cause: Failure to bind a unique identifier to each dialogue branch via `chatId`, leading to mutual interference of contexts from different projects.

## How to verify correct configuration
- Test a single-round policy inquiry, confirm that the output matches the text of the specified document, with no abnormal punctuation garbled text.
- Review the `messages` context record, confirm that only the most recent specified number of dialogue turns are retained, with no redundant historical data.
- Adjust the dialogue file expiration time configuration, verify that the system automatically cleans dialogue files for expired projects after the set number of days.
- Call the batch dialogue test interface, confirm that each dialogue branch's `chatId` is unique, with no context interference.

The values provided are common starting points and should be measured against the reader's own samples.
