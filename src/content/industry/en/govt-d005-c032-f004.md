# Policy and Regulatory Basis Q&A for Investment Project Approval and Post-Evaluation: Workflow Orchestration

## What the Data for This Category Looks Like
This category’s data primarily originates from state-owned assets supervision authority investment supervision systems, enterprise ERP and project management systems, industry market data, audit and financial statements. It is updated on a quarterly basis.
Daily processed documents include annual investment plans, project proposals, feasibility study reports, due diligence reports, asset appraisal reports, and post-investment evaluation reports. Most document structures contain fields such as project ID, investment scale, approval node information, and post-evaluation indicators. The length of individual documents varies widely, ranging from thousands to tens of thousands of characters.

## Constraints Imposed on Workflow Orchestration by These Characteristics
Data sources cover multiple systems and update quarterly. Workflows must support cross-system data pulling and scheduled synchronization mechanisms.
Wide variation in document length requires configuring processing nodes adapted to different text lengths. This avoids loss of key information caused by long text truncation.
For policy Q&A related to state-owned assets, workflows must include built-in compliance verification steps. This ensures output content meets relevant state-owned asset supervision requirements and matches the management rules of central enterprise board investment decisions and negative lists.
When processing multiple project data in batches, workflows must support node error capture and retry mechanisms. This prevents single project exceptions from affecting the overall process.
Cross-link data transfer must use `variables` to ensure accurate synchronization of information such as project IDs and approval status between nodes.

## Three Common Configuration Errors
- Phenomenon: After a workflow node executes, it returns a "model request timed out" or "interface call failed" status code, and the process terminates directly. Cause: No node error capture and retry rules configured, and no exception branch processing logic set up.
- Phenomenon: After a loop node finishes executing, nodes outside the loop cannot obtain the project post-evaluation results for each sub-item, and the corresponding fields are empty. Cause: Did not use `variables` configured for append-only storage, only used single-time variable overwriting which leads to data loss.
- Phenomenon: The workflow cannot load multiple feasibility study reports or due diligence reports at the same time, and only processes a single document. Cause: No multi-file upload and parsing nodes configured, and no batch file traversal rules set up.

## How to Confirm Proper Configuration
- Trigger a test workflow, check the log output of each node, confirm that the project data stored in `variables` is complete and not missing.
- Simulate a node error scenario, verify whether the exception branch triggers a retry or jumps to the specified processing node.
- Upload multiple typical documents of this category, confirm that the workflow can parse them simultaneously and associate them with the corresponding Q&A tasks.
- Adjust the model thought control switch, check whether the output of the policy Q&A node matches the expected thought enabled or disabled state.
