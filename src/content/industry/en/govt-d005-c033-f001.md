# Policy and Regulatory Basis Q&A for Tendering and Procurement Compliance Management: HTTP Interfaces and External Systems

## What this category’s data covers
Data for this category covers end-to-end procurement process documents for state-owned enterprise (SOE) and public sector procurement centers, tendering offices, business requirement departments, audit and discipline inspection departments, and tendering agencies. This includes procurement plans, requirement specifications, tender documents, bid evaluation records, contracts, acceptance documents, and supplier complaint materials.
Data sources include enterprise procurement platforms, public resource trading platforms, supplier databases, contract management systems, and audit issue databases. The update frequency is daily.
Data fields include procurement method, budget basis, scoring rules, supplier qualification requirements, performance acceptance records, and more. Data field formats vary across sources, so structured processing for multi-source data is required.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Multi-source data sources require interfaces to support integration with multiple external systems such as internal enterprise procurement platforms and public resource trading platforms. Different systems have different authentication and request formats, so diverse interface specifications must be supported.
Daily update frequency requires interfaces to support scheduled pulling or trigger-based updates, to avoid exceeding system limits from frequent calls.
Diverse document structures require interfaces to handle business data in different formats, so flexible field mapping rules must be configured.
Strict compliance verification requirements mean interfaces must have reliable failure handling mechanisms. This avoids compliance verification interruptions caused by interface anomalies, which could lead to audit rectification or personnel accountability risks.

## Three Common Mistakes
- Symptom: Interface call returns `self-signed certificate in certificate chain` error. Cause: The connected internal system uses an untrusted self-built SSL certificate, and the corresponding trust chain has not been added in the FastGPT interface configuration.
- Symptom: The `responseData` field returned by the interface is empty or does not contain compliance-related content. Cause: The response data filtering rules are not configured correctly, resulting in compliance-related fields being accidentally filtered, or the return fields of the external system are not mapped correctly.
- Symptom: The question-and-answer process does not terminate after calling the stop output interface. Cause: The official stop output interface provided by FastGPT is not called, or the interface parameters are not associated with the currently running question-and-answer process instance.

## How to Verify Proper Configuration
- Call the test interface on the interface debugging page of FastGPT v4.17.0, check if the returned `responseData` includes compliance-related fields such as procurement method and budget basis.
- Simulate the scenario of a self-built SSL certificate, add the corresponding trust chain in the interface configuration, then initiate a call, verify that no certificate-related errors occur, and the interface normally returns compliance verification related data.
- Trigger the scheduled task, check if the interface pulls the latest procurement platform data daily, and the returned update time matches the update time of the data source.
- Call the stop output interface, verify that the currently running question-and-answer process can terminate normally, with no abnormal log output.
