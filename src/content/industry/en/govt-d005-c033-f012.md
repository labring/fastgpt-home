# Policy and Regulatory Basis Q&A for Tendering and Procurement Compliance Management: Deployment and Upgrade

## What the data for this category looks like
This category covers all documents related to the full lifecycle of public sector and state-owned enterprise (SOE) procurement, including procurement plans, requirement specifications, bidding documents, bid evaluation records, contracts, acceptance documents, and supplier complaint materials. Data sources include enterprise procurement platforms, public resource trading platforms, supplier databases, contract management systems, and audit issue repositories. The update frequency is daily. Data fields include procurement method, budget amount, scoring rules, supplier qualification requirements, contract performance clauses, and more. There is no unified fixed format, so adaptation to multiple document structures and content characteristics is required.

## How to configure the settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `10–15` | Adapts to daily high-frequency compliance data queries and synchronization tasks, avoiding connection pool exhaustion |
| `MONGODB_URI` | `mongodb://fastgpt:your-secure-pwd@mongo-host:27017/fastgpt?authSource=admin` | Stores multi-type documents and vector data for the full tendering and procurement lifecycle to meet compliance query requirements |
| `REDIS_URL` | `redis://:redis-pwd@redis-host:6379/0` | Caches frequently queried policy clauses and compliance basis to reduce database load |
| `FE_DOMAIN` | `https://internal-gov-procurement-fastgpt.your-company.com` | Adapts to SOE and public sector intranet domain rules to ensure internal access and access control |
| `ROOT_KEY` | `32-bit randomly generated secure string` | Used for administrator permission verification to ensure operational security of the compliance management backend |

## Three common configuration errors
- Issue: Unable to modify administrator password after deployment, with an error prompt indicating insufficient permissions. Cause: The `ROOT_KEY` parameter was not configured correctly, causing the administrator permission verification logic to fail.
- Issue: Docker deployment container fails to start, returning status code 139. Cause: The `MONGODB_URI` parameter is configured incorrectly, preventing normal connection to the database for storing compliance data.
- Issue: After exposing the external network via ngrok, iOS devices always display a blank page when accessing the page, while macOS and Windows devices can access normally. Cause: The `FE_DOMAIN` configuration does not adapt to cross-domain requests for mobile devices, or ngrok forwarding does not properly handle the websocket protocol, resulting in failure to load front-end resources.

## How to verify the configuration is correct
- Execute the built-in database connection test tool to verify that the `MONGODB_URI` and `REDIS_URL` configurations can connect normally, with no timeout or permission errors.
- Upload a sample bidding document to confirm that the multi-format parsing function works correctly, and that core fields such as procurement method and budget basis can be extracted and vector indexes generated.
- Access the configured `FE_DOMAIN`, log in with the administrator account, and attempt to modify the password to verify that the permission verification process works normally.
- Trigger a manual data synchronization task to confirm that daily updated data from enterprise procurement platforms and contract management systems can be imported normally and update the vector database.

The values provided are common starting points and should be evaluated against local deployment samples.
