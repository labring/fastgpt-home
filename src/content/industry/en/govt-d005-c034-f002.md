# Policy and Regulatory Basis Q&A for Student Enrollment and Student Status Management: Vector Models and Indexing

## What this category of data looks like
This category of data primarily originates from the National Primary and Secondary School Student Status Management System, local enrollment platforms, household registration and property verification data, and school academic affairs systems. Updates occur daily. Service entities include education bureau basic education departments, school academic affairs offices, and similar institutions. Daily documents include enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, student status change approval forms, and similar items. Core fields focus on student identity, enrollment eligibility, and student status status, covering information such as household registration, property, enrollment periods, and change records. No non-business redundant fields are included.

## What constraints do these characteristics impose on the vector models and indexing link
The daily update feature of this category of data requires indexes to support incremental synchronization, to avoid excessive resource occupation from full reconstruction. Documents contain both structured forms and policy text content. Chunking must distinguish between policy clauses and form fields, to avoid retrieval bias caused by mixed cross-type content. Core data revolves around student identity and enrollment eligibility. Retrieval must prioritize matching policy documents associated with identity, and ignore generalized content. Multiple official source data requires index confidence to align with official data authority, while avoiding duplicate indexing of multi-source data for the same student.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |

| Chunk Length | 800–1200 characters | Adapts to the mixed policy text and structured forms of this category, avoids single chunks spanning multiple content types |
| Overlap Length | 50–80 characters | Covers the connected front and back portions of policy clauses, prevents cross-chunk policy logic from being split |
| Similarity Threshold | 0.75–0.85 | Matches the rigor of official policies, avoids low-relevance non-official content from being retrieved |

## Three common mistakes
- Custom index configuration leads to no valid retrieval results, with the interface showing 0 retrieved entries. The cause is failure to distinguish chunking between enrollment policy text and student status form data, resulting in the vector model being unable to match associated policy basis.
- Connection timeout errors occur when attempting to connect an external vector database. The cause is failure to configure correct database access keys and port parameters, and failure to verify version compatibility between the database and FastGPT v4.17.0.
- Vector model calls fail, returning parameter error prompts. The cause is failure to pass model call parameters in the format required by the platform, or use of a vector model not included in the platform's supported list.

## How to confirm proper configuration
- Upload a single enrollment policy text, manually trigger index construction, and check whether the chunk preview splits policy clauses and form fields into different chunks.
- Input the test question "What policy basis must be met for a transfer?", verify that the retrieved results include corresponding enrollment plan and student status change policy content, and that the number of retrieved entries matches the configured single search limit.
- After configuring the vector model channel, initiate a test call, check that normal vector embedding results are returned with no error prompts.
- Import a student status data set updated on the current day, check that the index completes incremental synchronization automatically, with no full reconstruction log prompts.
