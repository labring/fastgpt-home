# Policy and Regulatory Basis Q&A for Enrollment and Student Status Management: Multi-turn Dialogue and Prompt Engineering

## What This Category's Data Looks Like
This category serves entities including local education bureau basic education departments, school academic affairs offices, enrollment examination institutions, and street community collaborative windows. Data covers the full enrollment and student status management workflow. Daily documents include enrollment registration forms, student status information sheets, transfer applications, enrollment plans, admission rosters, and student status change approval forms. Data sources are the national primary and secondary school student status information management system, local enrollment platforms, household registration and property data, and school academic affairs systems. Updates occur daily. Core data fields focus on student identity, admission eligibility, and student status. Fields link to unique identifiers such as household registration address, property certificate number, and student status change type. No cross-category financial subsidy fields are included.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
Daily updated real-time data requires dialogue contexts to pull the latest student status and enrollment information synchronously. This prevents policy interpretation errors caused by referencing expired data. Multiple linked documents must be recalled incrementally during multi-turn dialogue based on user questions. Loading all data at once causes context overflow and slows dialogue response speeds. Unique fields for student identity and student status require prompts to clearly define retrieval scopes. Only documents related to enrollment and student status management may be called. This avoids confusion with data from other education categories. Single-turn dialogue handles complex logic such as household registration verification and student status changes. Historical dialogue context must be retained to support user follow-up questions. For example, if a user first asks about transfer policies and then asks about out-of-region transfer materials, the system must connect the policy premise from the prior round.

## Configuration Settings
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Value Range | Rationale |
| ---- | ---- | ---- |
| Maximum Context Length | 8000–12000 token | This category has many document fields. This range accommodates multi-turn dialogue and retrieved student status and enrollment document content, avoiding context truncation |
| Single Recalled Document Count | Top 3–5 documents | Data in this category is closely linked. A small number of precise documents can cover user questions about enrollment policies and student status changes |
| Context Retention Duration | 24 hours | Data in this category updates daily. This duration ensures the system refreshes the latest student status and enrollment information on the same day, ensuring content referenced in dialogue is up to date |
| Variable Binding Rule | Bind student ID and enrollment batch fields | Data in this category centers on student identity. The `variables` parameter must be used to accurately match corresponding student status and enrollment data |
| Conversation ID Association Method | Bind `chatId` | Multi-turn dialogue context must be linked to specific user student status query requests. This avoids confusion between different users' queries |

## Three Common Misconfigurations
- Issue: When referencing multi-turn dialogue context in a prompt, the system returns empty results or a field undefined error. Cause: The system did not bind historical dialogue context variables using the `variables` or `messages` parameters. This prevents the prompt from accessing existing dialogue content.
- Issue: Batch deleting conversation records also clears large volumes of associated system logs. Cause: The system did not configure independent storage association rules for conversations and logs. Logs and conversation records are tied to the same storage path.
- Issue: Batch calls to text content extraction modules return `undefined` for code block parameters. Cause: The prompt’s code block did not correctly specify the data source field. The system used an unbound `any` parameter, so it cannot identify the extraction target.

## How to Verify Successful Configuration
- Launch a test dialogue with a preliminary question and follow-up question. Confirm the system links the historical question’s context and retrieves matching student status or enrollment documents.
- Check the configured context retention duration. Manually trigger data synchronization, then verify the dialogue loads the day’s updated student status information.
- Bind `chatId` to user sessions. Confirm different users’ dialogue contexts do not overlap.
- Test deleting a single conversation record. Verify the system logs retain full interaction records.
