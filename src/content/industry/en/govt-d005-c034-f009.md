# Policy and Regulatory Basis Q&A for Enrollment and Student Status Management: Model Access and Configuration

## What this category of data looks like
This category of data covers the full lifecycle of enrollment and student status management. Daily documents include structured forms and policy texts such as enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, and student status change approval forms. Data sources include the National Primary and Secondary School Student Status Management System, local enrollment platforms, household registration and property data, and school educational administration systems. The update frequency is daily. Data fields include student identity identifiers, household registration and property information, student status status, enrollment batches, admission results, etc. Data is stored strictly in accordance with official standard formats, with no additional custom statistical values.

## What constraints do these characteristics impose on model access and configuration
The data characteristics of this category impose multiple constraints on model access and configuration. Multi-source datasets updated daily require enabling real-time data pull logic during configuration and disabling fixed cache modes to ensure the timeliness of policy and student status information. The document structure that combines structured forms and policy texts requires targeted recall weight settings, giving priority to matching policy text keywords to accurately answer regulatory basis-related questions. Sensitive fields involving student identity and household registration and property information require strict restrictions on the scope of context recall to avoid privacy information leaks. Additionally, since errors directly affect student enrollment and admission, result verification steps must be added during configuration to ensure that recalled data fully matches the business scenario.

## How to set configurations
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the long-text context requirements of enrollment policies and student status documents, avoiding truncation of key policy clauses |
| `maxTokens` | 2000–3000 token | Ensures responses include complete policy basis and student status verification logic, while controlling single-round response length |
| `quoteMaxToken` | 1500 token | Limits the total length of recalled reference texts, focusing on core policy clauses and student status data to avoid interference from redundant information |
| `temperature` | 0.1–0.3 | Maintains response rigor, meets standardized policy interpretation requirements, and avoids generating uncertain custom content |
| `AIPROXY_API_ENDPOINT` | Fill in according to the official deployment address | Adapts to domestically compliant API call links, ensuring data transmission meets the network security requirements of education systems |
| `toolChoice` | auto | Allows the model to independently choose whether to call tools for verifying student status data or querying the latest enrollment policies, improving response accuracy |

## Three common configuration mistakes
- Phenomenon: Irrelevant numeric prefixes appear in post-tool-call results that do not match the original model's response. Cause: The trigger scope of `toolChoice` is not restricted, causing the model to mistakenly call irrelevant tools or splice unintended system log content.
- Phenomenon: Recalled policy texts include expired enrollment batch information that does not match the current active enrollment cycle. Cause: Real-time data pull configuration is not enabled, and locally cached old data is used without refreshing the data source at the daily update frequency.
- Phenomenon: Corresponding student status data fields are missing from responses, making it impossible to accurately explain the basis for enrollment qualification determination. Cause: A reasonable value for `quoteMaxToken` is not set, resulting in truncated recalled student status form content and missing key fields.

## How to verify successful configuration
- Trigger a test policy Q&A request, check whether the policy text cited in the returned results matches the latest content of the current data source. This can be confirmed by comparing the data source's update records.
- View the tool call logs to confirm that no irrelevant redundant content is present in the returned results, verifying that the `toolChoice` configuration meets expectations.
- After adjusting configuration parameters, compare Q&A results across different batches to ensure response rigor meets policy interpretation requirements, verifying that the `temperature` value is suitable for the business scenario.
- Check the recall status of sensitive fields to ensure no student privacy information is leaked, verifying that the context recall scope configuration is compliant.
