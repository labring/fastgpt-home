# Policy and Regulatory Reference Q&A for Enrollment and Student Status Management: Deployment and Upgrade

## What the Data for This Category Looks Like
This category’s data centers on enrollment and student status management workflows. Daily documents include enrollment registration forms, student status information sheets, transfer applications, enrollment plans, admission rosters, student status change approval forms, and similar items. Data comes from the national primary and secondary school student status information management system, local enrollment platforms, household registration and property data, and school educational administration systems. Data updates daily. Data fields include student identity identifiers, household registration and property information, student status numbers, enrollment batches, change types, and similar items. The data organizes around student enrollment eligibility and student status transfer status, with no extra non-business quantitative indicators.

## Constraints for Deployment and Upgrade
This category’s data sources are scattered and update daily. The deployment phase requires stable synchronization of multi-source data and strict access permission control, to prevent data delays from connection interruptions. Daily documents include structured forms and policy texts. Deployments must support document parsing configurations for different formats, to ensure accurate extraction of policy clauses and student status information. Errors here can affect student admission eligibility, so deployments must reserve redundant resources to handle peak requests. The upgrade phase requires a full data backup, to avoid duplicate or missing student status records during transfers. Some scenarios use intranet deployment, so deployments must support HTTP proxy configuration with username and password, to enable normal access to external policy knowledge bases and model services.

## How to Set Configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `10–15` | Matches daily high-frequency student status data queries and synchronization requests, to avoid connection pool exhaustion |
| `MONGODB_URI` | Points to a local or intranet-hosted MongoDB instance with additional authentication parameters | Stores structured data such as student status information and enrollment plans, to ensure secure data access |
| `REDIS_URL` | Configured as the intranet Redis service address, with a connection password set | Caches frequently queried policy clauses and student status information, to reduce database load |
| `FE_DOMAIN` | Fill in the internal access domain name for intranet deployment, or the public domain name for public network deployment | Ensures normal access and resource loading for the Q&A interface |
| `ROOT_KEY` | Generate a high-strength random string based on the deployment environment | Restricts access to backend management interfaces, to prevent unauthorized operations |
| `STORAGE_S3_ENDPOINT` | Fill in the local object storage address for intranet deployment, or the cloud service provider endpoint for public network deployment | Stores attached files such as enrollment registration forms and student status change approval forms |

## Three Common Misconfigurations
- After configuring an HTTP proxy with a username and password, the model service cannot access external policy knowledge bases. Symptoms include empty results or timeout errors. The cause is that the proxy configuration was not correctly added to the FastGPT environment variables, or complete proxy authentication parameters were not included.
- After upgrading to FastGPT v4.17.0, the large language model called by the Q&A interface does not match the configured one. Symptoms include that after saving the qwenplus configuration, the chat automatically switches to another model when initiated. The cause is that environment variables were not fully synchronized during the upgrade, or configuration cache was not refreshed in a timely manner.
- Duplicate entries appear during daily student status data synchronization. Symptoms include multiple records with the same student status number in the system. The cause is that `DB_MAX_LINK` is configured too low, causing connection interruptions during data synchronization, which triggers repeated synchronization tasks.

## How to Confirm Successful Configuration
- Access the Q&A interface corresponding to `FE_DOMAIN`, attempt to query local enrollment policy texts, and confirm that structured results are returned normally.
- Run the daily student status data synchronization script, check whether the database corresponding to `MONGODB_URI` has added that day’s student status and enrollment data, and confirm there are no error log outputs.
- After configuring an HTTP proxy with a username and password, attempt to access an external policy knowledge base link, and confirm that document content loads normally.
- Enter the backend management interface, use `ROOT_KEY` to initiate an interface request, and confirm that only requests with the correct key can return management interface data.
