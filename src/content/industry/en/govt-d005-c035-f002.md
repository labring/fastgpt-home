# Policy and Regulatory Basis Q&A for Pollution Discharge Permit Management: Vector Models and Indexes

## What this category of data looks like
This category of data covers all process documents for pollution discharge permit management, including pollution discharge permit application forms, implementation reports, self-monitoring plans, ledger records, change applications, and permit copies. Data sources are the national pollution discharge permit management information platform, enterprise environmental protection ledgers, online monitoring systems, and environmental statistics systems. The update frequency is quarterly. Documents include dedicated fields such as permit limits, emission boundaries, monitoring indicators, and ledger cycles. All content is generated around pollution discharge compliance management requirements, with no extra non-business statistical values.

## What constraints do these characteristics impose on the vector models and indexes link
The multi-source heterogeneous nature of the data in this category requires vector indexes to support document formats exported from different systems, to avoid losing key compliance-related information due to format differences. The quarterly update frequency requires index configurations to support batch incremental updates, to avoid resource consumption from full reconstruction. Most documents are compliance clauses, monitoring data, and ledger records, with a high proportion of long texts. Chunking must retain clause integrity, avoiding splitting core fields such as permit limits and emission boundaries. Additionally, the accuracy requirement for compliance Q&A is high, so the retrieval link must ensure vector matching accuracy for core fields, to avoid outputting incorrect information.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Adapts to the natural segment length of compliance clauses and ledger records in pollution discharge permit documents, avoiding splitting core compliance fields |
| Overlap Length | 100–150 characters | Retains associated information such as permit limits and emission boundaries across chunks, ensuring context is not lost during retrieval |
| `maxToken` | 4096 token | Matches the context window upper limit of most open-source vector models, adapting to vector generation requirements for long documents |
| Similarity Threshold | 0.75–0.85 | Filters low-match non-compliance documents, ensuring retrieval results focus on content related to policy and regulatory basis |
| Single Search Limit | Top 6 entries | Controls the number of returned results, avoiding redundant information interfering with the accuracy of compliance Q&A |
| `defaultToken` | Calibrated via actual testing | Adapts to vector generation request timeout scenarios in different environments, avoiding index failure due to token limits |

## Three Common Mistakes
- The symptom is a 401 status code returned when calling the vector model, while curl tests can normally generate vectors. The cause is failing to correctly fill in the vector model's API key in the FastGPT configuration, or the key's permissions not covering index generation requests.
- The symptom is duplicate document chunks appearing in the knowledge base, with the custom split document order inconsistent with the index storage order. The cause is failing to disable the knowledge base's automatic deduplication function, or the split logic not matching the index generation's deduplication rules.
- The symptom is vector index generation timing out, with the task status always pending. The cause is the chunk length being set too large, exceeding the vector model's `maxToken` limit, resulting in generation requests being interrupted.
