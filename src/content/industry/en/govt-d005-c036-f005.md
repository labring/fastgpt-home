# Policy and Regulatory Basis Q&A for Government Service Item Catalog and Service Guide Maintenance: Tool Calling and Plugins

## What this category of data looks like
The core data for government service item catalog and service guide maintenance comes from the national basic catalog of government service items, administrative licensing item list, power responsibility list, and local government service item databases. Daily maintenance documents include the basic catalog of government service items, implementation lists, service guides, standard material directories, flowcharts, and frequently asked questions. Data is typically updated once per month. Each document contains fields such as item unique code, acceptance conditions, application material list, service process, and some fields include quantifiable service requirements.

## What constraints do these characteristics impose on the "tool calling and plugins" workflow
The multi-source nature of government data requires tool calling to support interface formats of different levels, to avoid cross-source data adaptation errors. The monthly update frequency requires the tool calling cache cycle to match the data update rhythm, to avoid returning outdated policy content. The multi-type documents and complex field structure requires tool calling to support pulling multiple document types and field validation, to ensure returned content complies with government item specification requirements. The core work of comparing upper-level catalogs with local implementation lists requires tool calling to have data comparison capabilities, to quickly identify catalog differences and ensure local items comply with upper-level policy requirements.

## How to set the configurations
The following configurations apply to FastGPT v4.17.0, for the policy Q&A scenario of government service item catalog and service guide maintenance:

| `functionCall` | Enable mandatory parameter validation | Government item fields have strict requirements, need to verify the completeness and compliance of tool return parameters |

| Number of items returned per tool call | `Top 6–10 items` | The number of government item documents is moderate; too many will increase context load, too few will fail to cover complete policy basis |
| Context cache cycle | `30 days` | Matches the monthly update frequency of government data, to ensure returned content is the latest version |
| Tool result validation switch | Enabled | Filters returned content that does not comply with government specifications, to ensure consistent Q&A standards |

## Three common misconfigurations
- A 400 status code with an empty response body is returned when calling a tool. The cause is incorrect configuration of the request header for the government data interface, or the passed item code format does not comply with the specification requirements of the government catalog.
- Missing service guide fields are returned by tool calls. The cause is that the correct document pulling range is not set, only some types of government documents are obtained, and complete policy basis is not covered.
- Timeout errors occur during tool calls. The cause is that the timeout period is not adjusted to match the response rhythm of the government data interface, and the default timeout duration is insufficient to complete data pulling.

## How to confirm the configuration is correct
- Send a simulated policy Q&A request, check whether tool calling is automatically triggered and returns relevant data for the corresponding government item.
- View the tool calling logs, confirm that the response status code is 200 and the response body contains complete government item field information.
- Verify whether the content returned by the tool matches the current government data update cycle, to ensure no outdated content is returned.
- Manually trigger a tool call, check whether the returned result contains required fields for government items such as acceptance conditions and application materials.
