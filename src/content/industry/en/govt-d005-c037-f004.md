# Policy and Regulatory Basis Q&A for Government Information Disclosure Upon Application: Workflow Orchestration

## What the data for this category looks like
The data sources for this category are government information disclosure platforms, agency archive systems, document management systems, and departmental business ledgers. Daily processed documents include government information disclosure application forms, supplementary notice letters, response letters, service receipt forms, etc. The structure includes fields such as application identifier, application item, related document number, response basis text, etc. Data updates have no fixed cycle, and are synchronized with new applications, archived documents, or policy adjustments. The character count per document varies widely, with no unified fixed length.

## What constraints do these characteristics impose on the "workflow orchestration" link
The multi-source nature of data and lack of fixed update cycles require workflows to support real-time data pulling from various systems on demand, avoiding reliance on static datasets from fixed synchronizations. Diverse document types with significant structural differences require configuring multi-format parsing nodes in workflows to adapt to different business documents. The core is individual case requests from single applicants, so workflows must use individual applications as trigger units, avoiding batch processing logic that interferes with accurate judgment. At the same time, responses must strictly match corresponding policy basis, so workflows need to link matching verification links between policy documents and application items.

## How to set the configuration

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Bind to exclusive fields for a single application, such as `{"application number": "example value", "application content": "example value"}` | This category handles individual cases, so exclusive information for a single application must be injected into the context to ensure accurate matching of Q&A |
| HTTP request node address | Configure as the API interface address of the corresponding government service system, such as `https://xxx.gov.cn/api/archive` | It is necessary to connect to data sources such as agency archive systems and document management systems to ensure correct data pulling permissions and paths |
| JSONPath extraction rule | Configure as `$.[*].content`, extract the top 3 matching results | The document structure of this category varies greatly, limiting the number of extractions can avoid context overload |
| Timeout setting | Set to 600 seconds | Government data pulling may have delays, reserve sufficient time to complete multi-source data retrieval |
| Single search limit | Set to the top 5 entries | Limit the search scope to avoid too many irrelevant documents interfering with matching |
| Maximum context length | Set to 8000 characters | Control context scale to ensure model processing efficiency and accuracy |

## Three common mistakes
- Phenomenon: The HTTP request node returns a 404 status code or times out, and government system data cannot be pulled. Cause: The access address of the node is not configured correctly, or the permission whitelist of the government system is not connected, resulting in failed interface calls.
- Phenomenon: Variables received by downstream nodes are empty, and parameters cannot be passed normally. Cause: The output fields of the upstream node are not correctly bound via `variables`, or the `nodeId` configuration is incorrect, resulting in failure to obtain upstream data.
- Phenomenon: The Q&A results contain a large amount of irrelevant content, and context matching accuracy decreases. Cause: No JSONPath extraction rule is configured, and full response content is directly injected into the context, resulting in information overload that interferes with matching logic.

## How to confirm the configuration is complete
- Trigger a single test application, check whether the upstream node correctly extracts the application number and item, and verify that the `variables` binding takes effect.
- Call the HTTP request node, check whether the returned result contains expected government document content, and confirm that the interface address and permission configuration are correct.
- After configuring the JSONPath extraction rule, check whether the variables output by the node are the expected document fragments, and verify that the extraction range is reasonable.
- Export the workflow configuration package, check whether the included nodes cover the complete Q&A process for policy basis, and confirm that the export function works normally.
