# Policy and Regulatory Basis Q&A for Government Information Disclosure Upon Application: Tool Calling and Plugins

## What the data for this category looks like
The core data for this category comes from government information disclosure platforms, official archive systems, document management systems, departmental business ledgers, and relevant texts of the Regulations on Government Information Disclosure. Update frequency is irregular. Daily processed documents include government information disclosure application forms, supplementary notice letters, third-party opinion solicitation letters, reply letters, service receipts, administrative reconsideration response materials, etc. Each individual case corresponds to an independent set of materials, with exclusive fields such as application number, applicant information, application content, reply opinions, relief channels, etc. There is no unified batch data format.

## What constraints do these characteristics impose on the "tool calling and plugins" link?
Data sources are scattered across multiple independent systems. Tool calling must support multi-source interface docking to avoid information loss caused by reliance on a single data source. The irregular update frequency means plugins do not need fixed-cycle synchronization, and can trigger data pulling on demand. The individual-case-specific document structure requires tool calling to accurately locate target data using fields such as application number and applicant information. Generalized keyword searches cannot cover these requirements. At the same time, error consequences are directly linked to administrative relief. Tool calling results must be clearly associated with their source to avoid generating unsupported reply content.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | Automatically select tools suitable for government data retrieval, no need to manually specify call items |
| `functionCall` | `required` | Force tool calling to obtain policy and business data, avoid generating unsupported reply content |
| Call timeout | `600 seconds` | Multi-source retrieval requires sufficient time to pull scattered data from archive and document systems |
| Multi-source data sync trigger mode | On demand | Adapt to the irregular update feature of data in this category, avoid ineffective synchronization |
| Retrieval result return limit | Top 3 entries | The policy basis for each application disclosure case is relatively concentrated, too many results will interfere with answer accuracy |
| Context window length | `8000–12000 characters` | Accommodate the complete content of multiple application materials, reply letters and other documents |

## Three common mistakes
- Symptom: Tool calling logs cannot be viewed in the interface. Cause: The storage function for tool calling logs was not enabled in the FastGPT v4.17.0 system settings.
- Symptom: API calls return empty results. Cause: Access permissions for the corresponding government system were not configured, making it impossible to pull data from the official archive system or document management system.
- Symptom: The generated reply does not include the source of the answer. Cause: The traceability configuration for tool calling was not enabled, and the source field of the retrieval results was not bound.

## How to confirm the configuration is complete
- Initiate a Q&A related to application disclosure that includes a specific application number, to verify whether the system triggers a tool calling action.
- Enter the tool calling record page, confirm that the request parameters and returned data of each call are fully stored.
- Check whether the generated reply is associated with the retrieved document source information, to ensure that the data source can be traced.
- Simulate a retrieval scenario containing multiple documents, to verify that the call does not exceed the set timeout period.
