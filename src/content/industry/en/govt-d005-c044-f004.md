# Policy and Regulatory Basis Q&A for Environmental Law Enforcement and Monitoring Supervision: Workflow Orchestration

## What this category of data looks like
This category of data comes from online monitoring platforms, automatic pollution source monitoring data, ecological environment law enforcement systems, and third-party test reports. The update frequency is daily. Daily documents include on-site inspection records, sampling records, monitoring reports, rectification order decisions, and administrative penalty decisions. Each document contains fields such as law enforcement subject, inspection or sampling time, monitoring point, pollutant value, rectification requirements, and penalty basis. Data is stored as a mix of structured ledgers and unstructured text.

## What constraints these characteristics impose on the workflow orchestration link
Multi-source data and daily updates require the workflow to include a scheduled trigger node. This node pulls the latest data from each system each day. Document types cover the full law enforcement, monitoring, and penalty process. Fields vary significantly across document types, so exclusive text splitting and field extraction rules must be configured for each type.
There is a clear requirement to link law enforcement data to policy basis. The workflow must include a variable tracking link to record call frequency for different policy clauses. It must also verify matching logic between data and policy clauses to avoid mismatches between evidence and basis.
Questions in law enforcement scenarios must use standard business terminology. The workflow must include a standardization conversion link to ensure matching accuracy between query statements and the policy library.

## How to set configurations
The following configurations apply to FastGPT v4.17.0, and are tailored to the business characteristics of this category.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Configure counting rules by classified question type, record call counts for each policy basis type | This category tracks call frequency of different policy clauses for compliance verification and subsequent analysis of law enforcement documents |
| `nodeId` | Bind to the ID of the daily data pull node, set to scheduled trigger | Data updates daily, so latest law enforcement and monitoring data must be synchronized daily to ensure timeliness of policy basis matching |
| Single search limit | Top 6 entries | Law enforcement-related policy basis needs to cover core law enforcement clauses. Too many entries increase context redundancy and reduce query efficiency |
| Maximum context length | 8000–10000 token | Law enforcement documents and policy texts are lengthy. Sufficient context must be retained to ensure matching completeness and accuracy |
| Question optimization | Enabled | Spoken questions in law enforcement scenarios must be converted to standard policy query statements to improve matching accuracy with the policy library |
| Reranking | Calibrated through actual testing | Policy matching logic differs across law enforcement scenarios. Reranking rules must be adjusted via actual testing to optimize matching results |

## Three common errors
- The `variables` configured classification counting rule fails to take effect, and the variable value is not automatically updated. This occurs because the variable update node is not bound to the trigger node of the corresponding classified question, so the counting logic is not invoked normally.
- Workflow execution times out and returns status code 504. This happens because a reasonable data pull timeout period is not set, and parallel execution nodes are not split when pulling multi-source data, leading to total execution time exceeding system thresholds.
- Recalled policy basis does not match law enforcement documents, and the number of results deviates significantly. This is caused by not configuring exclusive text splitting rules for different document types, leading to deviations in context extraction and reduced matching accuracy.

## How to confirm the configuration is complete
- Manually trigger the workflow for the corresponding classified question, and check whether the count recorded in `variables` increases as expected.
- Check whether the scheduled trigger node bound to `nodeId` starts the pull task at a fixed time each day.
- Randomly select an on-site inspection record to verify whether the recalled policy basis matches the law enforcement scenario in the document.
- View workflow logs to confirm that the execution time of each node does not exceed the preset reasonable range.
