# Policy and Regulatory Basis Q&A for Land Pre-examination and Planning Permit: Tool Calling and Plugins

## What the data for this category looks like
Data for this category comes from the national land spatial planning unified map, project approval and supervision platform, land use status database, and ecological protection redline data. Update frequency is irregular. Daily connected documents include land pre-examination and site selection opinions, construction land planning permits, construction engineering planning permits, redline drawings, and planning conditions. Core fields cover project site selection scope, land scale, planning control requirements, prior approval conditions, and similar items. Most units use standard measurement units for land spatial planning, such as square meters and hectares. Data must match preliminary approval workflows across the full lifecycle of projects.

## What constraints these characteristics impose on the tool calling and plugins workflow
Data sources for this category are scattered, and updates follow no fixed schedule. This means tool calling must support connecting to multiple data sources and on-demand refreshes. Daily document formats and fields vary widely. Plugins must adapt to different parsing logic for text-based approval documents and vector-based redline data. Core data involves key constraints for project preliminary approval. Parameter validation and failure handling for tool calling must be more strict to avoid approval errors caused by data deviations. Additionally, data updates follow no fixed rhythm. Plugins must support manually triggering data synchronization to adapt to temporarily added project approval data.

## Three common configuration errors
- An input error pop-up displays after plugin calls are initiated. This occurs because plugin data source connection parameters are not correctly configured, preventing the plugin from recognizing incoming project codes or site selection range fields.
- Full web content cannot be read after searching policy documents. This occurs because the plugin's web content pull switch is not enabled. Only search summaries are retrieved, and the full page parsing logic is not triggered.
- A 502 error is returned when calling an external API. This occurs because API request header parameters are not correctly configured, or the plugin's timeout setting is shorter than the external interface's typical response duration, causing the request to be blocked mid-process.

## How to confirm configuration is properly set up
- Manually enter a known project code to trigger plugin calls, and confirm returned data includes the planning control requirements for the associated project.
- Review logs following plugin calls, and confirm the number of pulled data sources matches the configured single pull limit.
- Check the plugin's request timeout setting, and confirm it exceeds the typical response duration of connected external interfaces.
- Enable the plugin's debug mode, and confirm parsed document fields match the core approval data fields for this category.
