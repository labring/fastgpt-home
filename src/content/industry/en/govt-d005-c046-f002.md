# Policy and Regulatory Basis Q&A for Social Assistance and Minimum Living Security Review: Vector Models and Indexes

## What data for this category includes
Data for this category originates from daily business documents of civil affairs bureau assistance sections, subdistrict and township civil affairs offices, community committees, and verification centers. These documents include minimum living security application forms, family economic status verification reports, household investigation forms, democratic review records, public notice materials, and assistance approval forms.

Data sources include the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-department shared data. Shared data comes from public security, human resources and social security, medical insurance, housing and urban-rural development, tax authorities, and other relevant departments. The update frequency is monthly.

Data fields include household income, total property, member identity information, and more. The core organizational unit is the household. Most documents combine structured forms and unstructured supporting materials.

## What constraints these characteristics impose on the vector models and indexes link
Monthly updated data must be synced to the vector database regularly. This prevents Q&A content from conflicting with latest policies or resident status due to data lag.

Cross-department shared data has inconsistent field formats. Field alignment must be completed before indexing. Otherwise, vector generation deviation will occur.

The household-centric document structure requires retaining household-related context during chunking. This avoids losing the correspondence between members and property after splitting.

Sensitive resident property information needs desensitization rules configured during the indexing stage. This prevents privacy leaks.

Integration of multi-source data increases the computational load of index construction. Configuration parameters for chunking and recall need to be matched appropriately.

## How to set the configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `defaultToken` | 1000 token | Matches the average semantic length of policy documents in this category. Ensures a single recall context covers core assistance clauses |
| `maxToken` | 4000–6000 token | Adapts to the total document length after cross-department data integration. Avoids truncation of critical family verification information |
| Chunk overlap length | 100–150 characters | Retains associated information of adjacent paragraphs in household documents. Prevents chunk boundaries from cutting off the correspondence between members and property |
| Similarity threshold | 0.72–0.80 | Filters low-relevance policy entries. Adapts to the demand for precise policy matching in minimum living security review scenarios. Calibrated based on actual testing |
| Single search limit | Top 6 entries | Controls the number of recalled documents. Balances retrieval accuracy and system response speed |
| Reranking | Enabled | Performs semantic ranking on recall results. Improves the display priority of highly relevant policy documents |
Reference only; verify against the target FastGPT release and deployment documentation.

## Three common mistakes
- Phenomenon: Retrieval logs show matching policy documents are recalled, but the final answer prompts that no relevant content was found. Cause: A reasonable value for `maxToken` was not configured. The total length of recalled documents exceeds the model context limit, causing critical matching information to be truncated.
- Phenomenon: The relevance of retrieval results does not meet expectations. Low-relevance household property verification documents are displayed first. Cause: A reasonable similarity threshold was not set, or the reranking function was not enabled. This causes the semantic matching ranking logic to fail.
- Phenomenon: Significant system response delay occurs. Background errors of context token overflow appear. Cause: The single retrieval token usage was not limited. An excessively large retrieval reference configuration was used directly, exceeding system processing capacity.

## How to confirm the configuration is properly set
- Log in to the system backend to view vector index synchronization records. Confirm that monthly updated business documents have completed full indexing with no abnormal failure status.
- Input typical questions related to household income verification. Check whether the number of recalled documents matches the single search limit configuration.
- Trigger a query containing sensitive property information. Verify whether privacy desensitization processing has been completed in the returned results.
- Adjust the chunk overlap length parameter. Test the context coherence of retrieval results, and confirm that household-related information has not been cut off by chunking.

The values listed above are common starting points, and should be evaluated against the user's own samples.
