# Policy and Regulatory Basis Q&A for Social Assistance and Minimum Living Security Review: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
This category belongs to civil affairs public services. Service subjects include civil affairs bureau assistance sections, subdistrict and township civil affairs offices, community neighborhood committees, and verification centers. The civil affairs system provides core data via its internal low-income population dynamic monitoring platform, resident family economic status verification system, and cross-department shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, tax authorities, and other relevant departments. Data updates occur monthly. Daily processed documents include minimum living security application forms, family economic status verification reports, household investigation forms, democratic appraisal records, public notice materials, and assistance approval forms. Data centers on the family unit, including fields such as family member information, income and property details, application and approval process records, and other fields. No fixed quantitative standards apply, and all work revolves around assistance qualification determination.

## What constraints these characteristics impose on the multi-turn dialogue and prompt engineering link
Cross-department data updated monthly requires dialogue context to stay limited to valid current-cycle information, avoiding expired data references. Mixed paper and system document sources demand prompts clearly distinguish fields and uses of different documents, preventing confusion between application materials and verification reports. A family-centric data structure requires multi-turn dialogue to link family member information with overall economic status details, ensuring complete review logic. Cross-department data integration needs dialogue to gradually guide supplementation of necessary verification dimensions, avoiding missed key cross-department verification content. Responses must strictly follow policy basis when generated, preventing incorrect or missed assistance approval risks.

## Configuration settings
| Configuration Item | Recommended Approach | Rationale |
|---|---|---|
| `chatId` | Generate a unique identifier per session, bind to the family application number | Used to distinguish dialogue context for different minimum living security applications, to avoid cross-session data confusion |
| `messages` | Retain the most recent 10 rounds of dialogue content, concatenate in reverse chronological order | Adapt to the monthly updated data cycle, to avoid overly long context leading to reference of expired information |
| `variables` | Inject family ID, verification batch number, and application status variables | Used to link corresponding family records in cross-department shared data, to ensure accurate data matching |
| Context memory length | 800–1200 characters | Adapt to the field length of family economic status data, to avoid exceeding model processing limits |
| Prompt template | Fixed binding to minimum living security application documents, verification reports, and policy basis | Ensure responses strictly follow provided documents and shared data, avoid unsubstantiated content, and align with FastGPT v4.17.0 template binding logic |

## Three common misconfigurations
- Dialogue return results fail to link to family economic status verification data. Cause: No family ID, verification batch number, or other associated parameters are injected via `variables`, so the system cannot match corresponding family records in cross-department shared data.
- Multi-turn dialogue cannot continue previous application review progress. Cause: No `chatId` configures a unique session identifier, so each request generates an independent context and loses historical dialogue association information.
- Responses contain unspecified handling time limits or amount standards. Cause: The prompt fails to strictly limit use to only category-specific documents and data sources, leading the model to generate unsubstantiated content.

## How to confirm proper configuration
- Initiate a simulated minimum living security application dialogue, confirm `chatId` stays consistent across multiple round requests, and check that context is not lost.
- Inject a preset family ID variable, run a family economic status query, and confirm returned results link to the corresponding family’s verification report data.
- Submit a dialogue with multiple rounds of supplementary information, check that responses gradually integrate historical input family member, income, and other details.
- Verify that prompts only reference category-specific document types and data sources, and do not generate unsubstantiated quantitative content.
