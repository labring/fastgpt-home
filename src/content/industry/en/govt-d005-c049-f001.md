# Policy and Regulatory Basis Q&A for Legality Review of Normative Documents: HTTP Interfaces and External Systems

## What data does this category process
This category processes data mainly from regulatory and rule repositories, higher-level law databases, departmental policy document repositories, and administrative normative document filing systems. Commonly processed documents include normative document drafts, drafting explanations, legality review opinions, summaries of solicited comments, and filing reports. Data updates have no fixed cycle, and must be synchronized in real time with higher-level law revisions and policy adjustments. Data fields include document number, issuing authority, effective date, text content, review opinions, etc. There is no unified fixed unit, and extraction must be based on the actual content of each individual document.

## How to configure
| Config Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `Authorization` | Fixed prefix plus valid token, formatted as `Bearer {token}` | Identity verification requirements for connecting to external regulatory repository and filing system interfaces |
| `variables` | Preset review scenario variables, such as `{"target_doc_type": "normative document draft"}` | Limit the document types processed by the interface, filter non-target data |
| `responseData` | Return only review results and matching basis document numbers | Reduce invalid data transmission, adapt to the receiving format of the filing system |
| Timeout period | 600 seconds | Adapt to the time requirements of large text comparison and multi-source data pulling |
| Single file upload limit | 1000 MB | Adapt to the storage requirements of complete normative document drafts and supporting explanations |
| Maximum number of matching entries | Top 10 entries | Control the number of returned higher-level law basis entries to avoid context overflow |

## Three common errors
- Symptom: When calling the file upload interface in an offline environment, the interface continuously displays a loading status with no return results. Cause: The interface relies on access to external regulatory repositories and filing systems, and identity verification and data pulling cannot be completed in an offline environment.
- Symptom: The `responseData` return field is empty after calling the matching interface. Cause: The target document type in `variables` was not specified correctly, and the interface filtered valid data.
- Symptom: Fields are missing after parsing an uploaded normative document draft. Cause: Correct document parsing rules were not enabled in the configuration, so the interface did not extract the field content required for the target review.

## How to confirm the configuration is complete
- Call the interface configured with `Authorization`, receive a 200 status code, confirm that the identity verification logic is active.
- Upload a test normative document draft, check whether the `responseData` return results include matching higher-level law basis document numbers.
- Simulate an offline network environment, call the interface and confirm that a clear access failure prompt is returned, confirm that the dependent service verification logic is working properly.
- Import the preset review workflow template, confirm that the nodes and configuration items displayed on the page match, with no missing content.
