# Policy and Regulatory Basis Q&A for Department Final Accounts and Financial Reports: HTTP Interfaces and External Systems

## What this category of data looks like
This scenario targets entities including finance departments of budget units, treasury departments of finance bureaus, government agencies, and public service sectors in state-owned enterprises, government, and public service fields. Data is sourced from the unified budget management system, centralized treasury payment system, accounting system, and asset management system. The update frequency is annual. Daily output documents include department final account statements, balance sheets, income and expenditure final account statements, final account explanations, and government financial reports. These materials consist of structured reports paired with textual explanations. Fields include revenue and expenditure details, asset and liability items, difference explanations, and more. Units follow unified regulations issued by finance departments.

## What constraints do these characteristics impose on the "HTTP Interfaces and External Systems" link?
The annual update feature requires HTTP interfaces to support periodic full data synchronization. Request parameters must clearly specify the corresponding final account year to avoid mixing data across periods. The multi-system data source feature requires interfaces to connect to multiple external system endpoints, and unify handling of differences in data formats returned by different systems. The coexistence of structured reports and textual explanations requires interfaces to support both structured field queries and context transfer for unstructured text. Data errors can lead to returned final account statements and audit risks, so interfaces must have clear failure retry mechanisms and exception alert rules to ensure call stability.

This configuration applies to FastGPT v4.17.0. Specific configuration items are as follows:
## How to Set the Configuration
| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| `Authorization` | Format as `Bearer {external system token}`, configure token validity period according to the rules of the connected finance system | Complies with identity authentication standards for external interfaces, ensures legitimate call permissions |
| `variables` | Includes fixed parameters such as final account year, budget unit code, etc., with values within the range allowed by the corresponding finance system | Ensures interface calls point to correct annual and unit data, avoiding cross-period or cross-entity queries |
| `responseData` | Only return final account fields and explanatory text matching policy bases, return quantity calibrated via actual testing | Filters irrelevant data, reduces context length, improves Q&A accuracy |
| Timeout Period | 60–120 seconds | Adapts to average response delays from multiple system connections, avoids overall call failure due to single system lag |
| Retry Strategy | Retry 2–3 times after failure, with a 5–10 second interval | Addresses temporary network fluctuations or short-term unavailability of external systems |

## Three Common Misconfigurations
- Phenomenon: Interface calls return `403 Forbidden` with a prompt that the token does not have permission to use the corresponding resource. Cause: Access permission for department final account data has not been configured for the current token in the external finance system, or the token has expired.
- Phenomenon: Using `{{}}` format to reference variables in the HTTP node returns empty values. Cause: Corresponding variables such as final account year and unit code have not been pre-defined in FastGPT's `variables` configuration, or the variable format does not meet interface requirements.
- Phenomenon: The final account data returned by the interface does not match the actually queried year. Cause: The request parameters do not clearly specify the corresponding final account year, or the system has cached data from previous years and has not refreshed in time.

## How to Verify Successful Configuration
- Call the test interface, check that the `Authorization` parameter is correctly included, and the returned status code is 200 OK.
- View the fields returned in `responseData`, confirm that only data related to the configured final account year and unit is included.
- Simulate a policy basis Q&A request, verify that the returned content includes information from corresponding documents such as department final account statements and explanatory text.
- Trigger the failure retry logic, confirm that the interface can automatically resume normal calls after the external system is temporarily unavailable.
