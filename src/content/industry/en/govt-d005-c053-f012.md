# Policy and Regulatory Basis Q&A for Departmental Budget Preparation: Deployment and Upgrade

## What the data for this category looks like
The data for this category primarily comes from the unified budget management system, departmental staffing establishment system, prior-year final accounts, project repository, and the Ministry of Finance's annual budget preparation notice. Organizations such as the budget department of the finance bureau and the finance department of budget units typically use this data. Daily processed documents include departmental budget drafts, project application forms, performance target forms, personnel expense calculation forms, budget approvals, and similar items. The data update cycle is annual, with a full refresh only when the new year's budget preparation process starts. Data fields include unit establishment numbers, project expenditure details, performance target indicators, budget approval amounts, and similar items. There is no universal cross-category unified format, and matching the internal field specifications of the financial system is required.

## What constraints these characteristics impose on the deployment and upgrade phase
The annual update feature requires deployments to support full offline data synchronization and incremental update adaptation, to avoid repeated loading of historical data that consumes storage resources. Multi-source financial system data requires cross-source data verification rules to be configured, preventing incorrect answer results caused by field mismatches. Specialized document formats require knowledge base chunking to match the paragraph structure of financial reports, avoiding loss of core fields such as budget amounts and establishment numbers after chunking. When deploying or upgrading, space for interface adaptation with internal financial systems must be reserved, to ensure data synchronization permissions comply with government security specifications. Additionally, since data is only updated annually, frequent data reprocessing does not need to be triggered during upgrades, which can optimize the downtime window for the upgrade process.

## Three common mistakes
- Interface calls return errors of type `code500 Cannot read p`. The cause is that the authentication parameters for `REDIS_URL` are not configured correctly, leading to a failed cache connection and inability to load policy basis cache data.
- Alibaba Cloud model tests return 400 errors. The cause is that the `STORAGE_S3_ENDPOINT` node for government cloud storage is not adapted, leading to failure to properly read knowledge base files and triggering parameter verification failure.
- The agent backend freezes during API file uploads. The cause is that the connection limit for `DB_MAX_LINK` is not set, leading to exhaustion of the database connection pool when uploading budget documents concurrently, resulting in service unresponsiveness.

## How to confirm the configuration is complete
- Log in to the FastGPT backend to check the database connection status. Confirm that there are no errors in the connection logs for `PG_URL` and `REDIS_URL`, and that the number of connections does not exceed the configured `DB_MAX_LINK` limit.
- Upload a departmental budget draft document to verify that the storage node configured via `STORAGE_S3_ENDPOINT` can properly store and read files, with no permission errors.
- Initiate a test Q&A about budget preparation policies, confirming that the returned results associate knowledge base documents from the configured data sources, with no missing fields.
- After upgrading to FastGPT v4.17.0 and restarting the service, check that the frontend domain configured via `FE_DOMAIN` can properly access the backend management interface, with no cross-domain errors.
