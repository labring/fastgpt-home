# Policy and Regulatory Basis Q&A for Flood Control, Disaster Prevention and Emergency Duty: Multi-turn Dialogue and Prompts

## What the Data for This Category Looks Like
The data for this category primarily comes from meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Daily supporting documents include duty logs, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips.
Data is updated daily. Most document structures include fields such as event time, location, disposal progress, and associated responsible persons. Some documents include numeric fields such as rainfall volume and material stock, with units including millimeters, pieces, person-times, and others.

## What Constraints These Characteristics Impose on the Multi-turn Dialogue and Prompts Link
Scattered data sources and fixed update frequencies require multi-turn dialogue to call real-time latest meteorological and hydrological data, and prompts to clearly define the time range of used data.
Multiple types of daily documents require prompts to distinguish call priorities for different documents, such as prioritizing consultation minutes as the basis for disposal.
Fields include numeric and event-based content. Multi-turn dialogue must support field-based filtered queries, while also limiting context length to avoid including expired data.
The cross-department scheduling feature requires the dialogue flow to link data from multiple systems. Prompts must clearly define the authority and responsibility boundaries of each link.

## How to Configure Settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum context length | 800–1200 characters | Matches the typical length of daily consultation minutes and rapid disaster reports, avoids expired data occupying context space |
| Single search limit | Top 6 entries | Matches the frequency of associated documents in emergency scenarios, balances query efficiency and information completeness |
| Question optimization switch | Enabled | Automatically refines colloquial disaster descriptions into standardized queries suitable for policy document retrieval |
| Timeout threshold | 600 seconds | Adapts to the time required for cross-system data retrieval, prevents dialogue interruptions in emergency scenarios |
| Variable binding | Bind `chatId` and `messages` | Retains context association for multi-turn dialogue, ensures subsequent questions can reference earlier disaster information |
| Context variable | Enable `variables` parameter | Passes custom parameters such as disaster location and current warning level, adapts to emergency response rules for different regions |

## Three Common Misconfigurations
- Attachments uploaded via the dialogue window cannot be recognized, and work only in the local development environment. The cause is incorrect configuration of the attachment storage path during image deployment, which prevents the system from reading uploaded document files.
- The pre-judgment module cannot pass the initial user question to the AI dialogue link. The cause is incorrect binding of the `variables` parameter to pass context variables, which prevents the output of the judgment module from being synchronized to the dialogue flow.
- Dialogue logs cannot obtain associated user identifiers. The cause is missing configuration of identity verification parameters, which prevents the system from capturing user identity information.

## How to Confirm Configurations Are Correctly Set
- Upload a test warning notice document, confirm that returned content includes key disposal requirements from the document after submitting a question.
- Initiate 3 consecutive related questions, confirm that each response references the disaster information from the previous round.
- Trigger cross-system data retrieval, confirm that the dialogue flow returns complete results within 600 seconds with no timeout errors.
- Check the configuration panel, confirm that parameters such as maximum context length and single search limit match the preset values.
