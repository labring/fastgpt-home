# Policy and Regulatory Basis Q&A for Flood Control, Disaster Prevention and Emergency Duty: Model Access and Configuration

## What the data for this category looks like
Typical data for this category comes from meteorological early warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Daily processed documents include duty records, early warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Fields include rainfall and water level values, warning levels, response time limits, material categories and quantities, and more. Data updates occur daily; some real-time early warning data has shorter update intervals. Most document structures mix structured fields and unstructured text.

## What constraints these characteristics impose on model access and configuration
Data for this category is mostly real-time updated mixed-format text, and must quickly support consultations and early warning responses. Model access must therefore adapt to high-frequency updated data sources. Mixed-structure documents require configuration that supports multi-type text parsing, to avoid losing structured fields or truncating unstructured content. The timeliness requirements for early warnings and responses also limit the context window and generation duration, requiring a balance between content completeness and response speed. Additionally, data sources span multiple internal systems, so interface stability for model calls must be ensured, and format conversion needs for multi-source data must be supported.

## How to set the configuration

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to context requirements for splicing multiple documents such as consultation minutes and rapid disaster reports, and avoids truncation of key policy basis |
| `maxTokens` | 2000–3000 token | Meets the content length requirements for policy clause interpretation and response plan generation, and avoids incomplete generation |
| `quoteMaxToken` | 1500 token | Limits the fragment length of referenced documents, ensuring that retrieved policy basis matches the business scenario |
| `temperature` | 0.2–0.4 | Reduces generation randomness, ensuring accuracy of policy interpretation, and avoiding statements that do not comply with regulatory requirements |
| `toolChoice` | auto | Automatically calls retrieval tools to obtain the latest policies and real-time data, adapting to the rapid response needs of emergency scenarios |
| `AIPROXY_API_TOKEN` | Exclusive key applied for according to permissions | Ensures the security of interface calls, and avoids unauthorized access to internal emergency data |

## Three common configuration errors
- When calling the knowledge base index generation interface, changing the model. The symptom is that retrieval results differ from those under the original configuration. The cause is that the embedding model configuration of the original knowledge base was not updated synchronously, resulting in a mismatch between old and new vector spaces.
- Configuration failure when calling third-party large model APIs. The symptom is the interface returning a 401 status code or connection timeout. The cause is incorrect filling of `AIPROXY_API_TOKEN` or `AIPROXY_API_ENDPOINT`, or failure to configure access permissions for cross-departmental systems.
- Abnormal Docker deployment of the proxy service. The symptom is the service restarting continuously and unable to access the interface. The cause is incorrect mounting of configuration files or incorrect port mapping, resulting in the service failing to start normally.

## How to confirm the configuration is successful
- Initiate a test call, input questions related to flood control policies, and check whether the returned results include retrieved latest policy basis and real-time data.
- View the knowledge base index logs, confirm that the embedding model and configuration items are consistent, and there are no error messages.
- Adjust the `temperature` parameter, check the randomness change of generated content, and confirm that the configuration takes effect.
- Simulate cross-departmental data access, verify whether the `toolChoice` configuration automatically triggers the retrieval tool to obtain data from the corresponding system.
