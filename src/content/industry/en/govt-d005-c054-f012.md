# Policy and Regulatory Basis Q&A for Flood Prevention, Disaster Mitigation and Emergency Duty: Deployment and Upgrade

## What the data for this category looks like
The data for this category primarily comes from meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Daily processed documents include duty logs, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material transfer orders. Duty logs contain fields for duty periods, disaster severity levels, and disposal statuses. Warning notices include fields for warning levels and effective periods. Some documents use units such as millimeters of rainfall and transferred person-times. Data updates occur daily, requiring synchronization of the latest rainfall and water conditions, warning information, and response updates for the current day.

## Constraints on Deployment and Upgrade from These Data Characteristics
The data characteristics of this category impose clear constraints on the deployment and upgrade process. Multi-source data docking requires configuring connection parameters compatible with multiple systems to avoid interface call conflicts. The daily update frequency requires setting a reasonable incremental sync cycle to ensure the timeliness of policy and regulatory basis information. The diverse document types and unit-attached fields require the parsing process to adapt to different formats such as structured tables and plain text, while supporting unit semantic matching. The real-time requirements of emergency scenarios require retaining compatibility with legacy interfaces during upgrades to avoid disrupting daily duty and warning response.

## How to Configure Settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 100–200 connections | Flood prevention and disaster mitigation scenarios need to connect to multiple data sources such as meteorological and hydrological systems. This parameter limits the upper limit of the database connection pool to avoid resource exhaustion |
| `REDIS_URL` | Local Redis service address, port 6379 | Used to cache real-time warning information and user sessions to ensure fast response in emergency scenarios |
| `STORAGE_S3_ENDPOINT` | Local object storage service address | Used to store unstructured documents such as duty logs and rapid disaster reports, adapting to the daily incremental update data volume |
| `FILE_TOKEN_KEY` | Randomly generated 32-bit string | Used to encrypt file upload requests to prevent unauthorized access to sensitive emergency-related documents |
| `ROOT_KEY` | Randomly generated 64-bit string | Used to configure system administrator permissions to secure access to the emergency duty backend |
| `FE_DOMAIN` | Public network domain name of the deployment server | Used to configure callback addresses for external platform calls, adapting to the interface docking requirements of emergency command platforms |

## Three Common Misconfigurations
- Symptom: Interface calls return empty responses, and full Q&A content can only be viewed by expanding details. Cause: `FILE_TOKEN_KEY` is not configured correctly, resulting in insufficient file parsing permissions. Policy and regulatory basis documents cannot be properly retrieved, and underlying error information is only exposed on the detail page.
- Symptom: External platforms encounter timeout errors when calling chat interfaces after deployment. Cause: The `DB_MAX_LINK` parameter is not adjusted, and the connection pool is exhausted, causing database requests to block and failing to return policy basis Q&A results in a timely manner.
- Symptom: An error occurs when parsing document addresses after enabling workflow file upload. Cause: `STORAGE_S3_ENDPOINT` is not configured correctly, making it impossible to access locally stored flood prevention documents, interrupting the file parsing process.

## How to Verify Successful Configuration
- Log in to the FastGPT backend, check if the `REDIS_URL` configuration item points to a normally running Redis service. The connection status can be verified using the redis-cli ping command.
- Upload a local flood prevention warning notice document to test the file upload and parsing process, and confirm there are no permission or storage-related errors.
- Call the chat interfaces for external platforms to verify that the response duration meets the real-time requirements of emergency scenarios. Stability can be compared through multiple requests.
- Check system logs to confirm that the usage of the database connection pool does not exceed the configured upper limit of `DB_MAX_LINK`.
