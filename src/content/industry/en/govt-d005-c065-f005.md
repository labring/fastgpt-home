# Policy and Regulatory Basis Q&A for Survey and Design: Tool Calling and Plugins

## What the Data for This Category Looks Like
Survey and design policy and regulatory basis data comes from official announcements of the Ministry of Housing and Urban-Rural Development, official announcements of provincial housing and urban-rural development authorities, industry standard specifications, and special survey and design management measures. Data updates align with industry specification revisions and policy document releases. Content is added to the knowledge base promptly after major policy launches. Document structure uses core fields including specification number, issuing authority, effective date, clause chapter, clause content, and application scenario. Clause chapters use Arabic numeral hierarchical numbering. Effective dates follow standard date formats. Single policy documents vary widely in length, with some special specifications reaching tens of thousands of characters.

## What Constraints These Characteristics Impose on the Tool Calling and Plugins Workflow
First, all data sources are official public documents. Configure parameter validation when calling tools to check the legitimacy of the request source, preventing calls to non-official data sources. Second, documents have fixed hierarchical chapter number fields. Tools must support accurately locating target clauses by chapter number. If fuzzy keyword matching fails, additional conditional filtering is required. Third, data updates have no fixed cycle. Plugins must be configured with scheduled synchronization tasks to ensure retrieved content is the latest effective version. Fourth, single policy documents are lengthy. When calling tools, limit the number of returned clauses to avoid content truncation or request timeouts caused by exceeding the context window.

## Configuration Settings
The following configurations apply to FastGPT v4.17.0:

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Tool calling mode | `functionCall` | Adapts to structured extraction requirements for survey and design policy clauses, accurately matches preset fields |
| Parameter validation switch | Enabled | Filters requests from non-official data sources, ensures compliance of called content |
| Data source whitelist | Official website of the Ministry of Housing and Urban-Rural Development, official announcement addresses of provincial housing and urban-rural development departments | Limits calls only to official public policy documents, avoids invalid or non-compliant content |
| Maximum returned clauses | Top 3 entries | Matches the context carrying capacity of single-round Q&A for survey and design policies, prevents information overload |
| Scheduled synchronization cycle | Every 7 days | Adapts to the update rhythm of industry policies, ensures retrieved content is the latest effective version |
| Field extraction rules | Extract only specification number, effective date, clause content | Aligns with core fields of survey and design policy documents, reduces redundant information in returned results |

## Three Common Misconfigurations
- Phenomenon: A `400 <400> InternalError.Algo.InvalidParameter: messages with role error is thrown when starting the project. MongoDB visualization tools can connect normally. Cause: The role parameter format for tool calling does not comply with preset validation rules, and the message role type is not correctly specified.
- Phenomenon: After importing policy documents returned by the HTTP interface into the knowledge base, accurate analysis cannot be completed. Cause: Field extraction rules are not configured, and unstructured long text is imported directly, resulting in failure to locate core policy clauses during retrieval.
- Phenomenon: Calls to model APIs not included in the platform's built-in list return call failures. Cause: Custom request parameter formats and keys for the model are not configured in the plugin settings, and the built-in model calling logic is used.

## How to Confirm Successful Configuration
- Run a tool calling test, check that returned content only includes preset policy fields with no redundant information.
- View the running logs of the scheduled synchronization task, confirm that the most recent synchronization data source address matches the configured whitelist.
- Trigger the parameter validation switch, pass a request from a non-official data source, confirm that the system intercepts invalid calls.
- Adjust the maximum returned clauses, verify that the number of returned clauses complies with the configured value range.

The values provided are common starting points and should be measured against the reader's own samples.
