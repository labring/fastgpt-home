# Policy and Regulatory Basis Q&A for Power Generation Groups: Tool Calling and Plugins

## What the data for this category looks like
Data sources for policy and regulatory basis data of power generation groups include energy industry policy documents released by the National Energy Administration and the State-owned Assets Supervision and Administration Commission of the State Council, as well as internal management system documents from the group headquarters and affiliated power plants. Updates are synced in real time when official policies are released or internal systems are revised. Document structures typically include fields such as document number, issuing authority, effective date, scope of application, and core clauses. Clauses are divided by article, paragraph, and subparagraph levels. Individual document lengths range from thousands to tens of thousands of characters. Some historical policies only exist as scanned copies, which require optical character recognition conversion first.

## What constraints these characteristics impose on the tool calling and plugins workflow
The hierarchical structure of policy documents requires precise matching of clause numbers and effective dates during tool calls, to avoid returning expired or inapplicable content. Mixed calls of multi-source data require plugins to configure different interface authentication and access permissions, distinguishing between public data sources and internal private document libraries. Large differences in document lengths require limiting the number of documents and character volume returned in a single tool call to prevent context overflow. Policy updates have no fixed cycle, so plugins must support manual triggering or scheduled pulling of the latest policy documents to ensure the timeliness of Q&A content.

## Configuration settings
This page's configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` or a dedicated policy parsing tool | Power generation group policy Q&A requires fixed calls to policy parsing capabilities. `auto` automatically matches the corresponding tool, while specifying a tool avoids accidental calls to other unrelated functions |
| `functionCall` | Enabled, limit calls to two types of plugins: policy query and clause parsing | Focus on the policy and regulatory basis Q&A scenario, restrict tool call scope to improve result accuracy |
| Number of documents returned per call | Top 3 | Power generation group policy documents have large individual lengths; returning too many will occupy the context window, leading to truncation of core content |
| Character count returned per call | 2000–3000 characters | Policy clauses have relatively long single-section content; limiting the returned character count prevents context overflow |
| Context window limit | 8000–12000 token | Adapt to the large language model's ability to process long documents, avoiding generation failure due to overly long context |
| Interface timeout period | 30–60 seconds | Group internal document library interfaces carry risks of intranet delay; the timeout period must match the average response duration of intranet access |
| Plugin authentication method | Authenticate via group intranet token | Internal policy documents are sensitive information; a dedicated authentication method is required to ensure unauthorized users cannot access them |

## Three common configuration errors
- Phenomenon: Irrelevant code execution or general document search plugins are triggered during tool calls, returning non-policy-related content. Cause: The `toolChoice` parameter is not configured correctly, and the tool call scope is not restricted, causing the model to call unauthorized functions.
- Phenomenon: A 403 Forbidden error is returned when calling the internal policy document interface, or private document content cannot be obtained. Cause: The dedicated intranet token authentication method of the group is not used, and the authentication rules of the public interface are directly applied, failing to match the verification logic of the internal system.
- Phenomenon: The Set-Cookie field in the response cannot be parsed after calling the HTTP interface, leading to authentication failure in subsequent interface calls. Cause: The session cookie automatic storage and carrying function of the HTTP request module is not enabled, only a single interface call is completed without retaining session credentials, and access permissions cannot be continued.

## How to verify the configuration is complete
- Initiate a query containing a specific policy document number, check whether the tool call returns the accurate content of the corresponding clause, and confirm that the authentication configuration and document pulling function are effective.
- View the tool call log, confirm that only the two types of plugins, policy query and clause parsing, are called, and no other unrelated tools are triggered, to verify the configuration effect of `toolChoice` and `functionCall`.
- Manually trigger a policy document sync, check whether the latest policies in the internal document library are successfully pulled into the Q&A knowledge base, and confirm that the update mechanism is working properly.
- Simulate an interface delay scenario, confirm that the tool call returns a response within 30–60 seconds, and no timeout error occurs, to verify that the timeout period configuration is reasonable.
