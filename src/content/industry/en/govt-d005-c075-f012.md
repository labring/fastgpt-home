# Policy and Regulatory Basis Q&A for State-owned Capital Investment Companies: Deployment and Upgrade

## What this type of data looks like
The policy and regulatory basis data for state-owned capital investment companies mainly comes from normative documents issued by the State-owned Assets Supervision and Administration Commission of the State Council and local state-owned assets supervision institutions at all levels, as well as internal systems formulated by the group for investment operations, risk control, performance evaluation, and other aspects. Data updates are triggered when new policies are issued or systems are revised, with no fixed cycle. Single documents are mostly a mix of structured and unstructured formats, including fields such as policy document number, issuing authority, effective date, clause details, and scope of application. Clauses are organized in a hierarchy of articles, paragraphs, and sub-paragraphs. Attachments are mostly in PDF or Word formats.

## What constraints do these characteristics impose during deployment and upgrade
Multi-source and heterogeneous data sources require support for connecting different file formats and external data sources during deployment. Upgrades must add synchronization interfaces adapted to the latest state-owned assets policy release channels.
The mixed structured and unstructured document format requires configuring parsing rules that balance text chunking and structured field extraction during deployment. Upgrades must optimize recognition accuracy for special document numbers and clause hierarchies used in state-owned assets policies.
The non-fixed cycle update requirement requires configuring incremental synchronization and incremental indexing parameters during deployment. Upgrades must be compatible with new update trigger mechanisms to avoid resource occupation caused by full reindexing.
Fields including document numbers, effective dates, and other metadata require the vector database to support metadata filtering. Corresponding storage fields must be configured during deployment. Upgrades must be compatible with newly added metadata fields.

## Three Common Mistakes
- Phenomenon: After upgrading Docker to the specified version, knowledge base retrieval triggers errors of the type `text index required for $text qu`. Cause: No full-text index was created for the text fields of policy documents in MongoDB. After the upgrade, FastGPT's retrieval logic relies on this index for keyword matching.
- Phenomenon: After local deployment, it is not possible to select large model providers other than the default list. Cause: No API access parameters for the corresponding model provider were added to the configuration file, or the configuration permission for custom models was not enabled, which does not meet the flexible access requirements of local deployment.
- Phenomenon: Retrieval results only cover the initially imported policy documents, and do not include subsequent updated internal systems. Cause: No trigger rules for incremental synchronization were configured, only initial batch import was performed, and subsequent revised systems were not automatically synchronized to the system.

## How to Verify Successful Configuration
- Access the frontend address corresponding to the configured `FE_DOMAIN`, confirm that the system interface loads normally, with no domain name resolution or cross-domain errors.
- Upload a test state-owned assets policy document, confirm that the system can correctly parse the file content and generate vector indexes, with no format parsing failure prompts.
- Initiate a policy-related retrieval request, confirm that the retrieval results include matching policy clauses, and that metadata such as document numbers and effective dates is displayed normally.
- Trigger an incremental synchronization task, check the system logs to confirm that the synchronization task executed successfully, with no synchronization failure error messages.
