# Policy and Regulatory Basis Q&A for Urban Public Transit: Tool Calling and Plugins

## What this category of data looks like
Data sources include the Ministry of Transport’s Urban Bus Passenger Transport Management Measures, local bus operation specifications released by provincial and municipal transport bureaus, and internal service management rules of bus enterprises. The update rhythm synchronizes with national or local policy revisions, with no fixed cycle. A single policy document includes a document number, issuing authority, effective date, applicable region, and core clauses. Clauses are divided by chapter, with each clause corresponding to specific operation requirements. Fields include policy ID, issuing entity, effective time, applicable scope, clause content, and implementation details. Clauses are counted in "articles", and files are stored in "copies".

## What constraints do these characteristics impose on the tool calling and plugins workflow
Local policy field differences require tool calling to adapt to different regional knowledge base structures, to avoid cross-region retrieval confusion. Precise clause numbering for policies requires tool calling to only support precise recall by clause number, and full-text fuzzy retrieval is not allowed. No fixed update cycle requires plugins to support manual knowledge base refresh, ensuring the latest policies are included in retrieval in a timely manner. Long policy documents require tool calling to limit the number of clauses recalled per single request, to avoid exceeding context window limits.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Automatically select a tool calling strategy matching the business scenario |
| `functionCall` | Only call the policy knowledge base plugin | Limit the scope of tools to avoid calling unrelated plugins |
| Tool trigger keywords | Questions containing "policy", "basis", "document number", "effective time" | Precisely match the business scenario, reduce false triggers |
| Knowledge base recall limit | Top 10 articles | The number of bus policy clauses is limited; too many will exceed the context window |
| Timeout setting | 600 seconds | Reserve processing time for cross-region policy retrieval |
| Field binding rules | Bind policy document number, applicable region, effective time | Ensure recalled results meet the user's required region and timeliness |

## Three Common Mistakes
- Phenomenon: When a query containing "bus policy basis" is initiated, the returned results mix real-time bus operation data. Cause: The tool calling is not limited to only retrieving the policy-specific knowledge base, and the general operation knowledge base is mistakenly included in the recall scope.
- Phenomenon: An API call returns a 514 status code. Cause: The tool calling timeout setting is too short, and no processing time is reserved for cross-region policy retrieval.
- Phenomenon: The policy results returned after plugin invocation do not include a document number or effective time. Cause: No field binding rules are configured, and regional and timeliness keywords from the user's question are not extracted.

- Initiate a test query containing "Guangzhou bus policy document number", and check that the returned results only include Guangzhou municipal bus policy documents.

- Simulate an API call, and check that the returned results include specified fields such as policy document number and effective time.
- Manually trigger the knowledge base refresh operation, and confirm that newly revised policy files can be retrieved quickly.
