# Policy and Regulatory Basis Q&A for Urban Gas: Tool Calling and Plugins

## What this category of data looks like
Data for urban gas policy and regulatory basis primarily comes from the Ministry of Housing and Urban-Rural Development’s Regulations on Urban Gas Management, gas management measures issued by provincial, municipal, and county-level housing and urban-rural development and urban management departments, and local normative documents. Updates occur irregularly alongside national and local policy adjustments, with no fixed cycle. Documents are normative official papers with official document numbers, issuing entities, and effective dates. Fields include policy title, issuing unit, effective date, applicable region, full core clause text, with clauses divided by article numbering.

## Constraints Imposed on Tool Calling and Plugin Workflows
Policy data is divided by effective region. Tool calling must include the city or regional parameter corresponding to the request to accurately match relevant policy documents. Official documents have strict, fixed clause numbering structures. Tools must extract content using exact clause numbers; generalized matching cannot return accurate results. Data updates have no fixed cycle. A scheduled synchronization plugin must be configured to regularly update the local policy library, to avoid returning outdated content. Single policy documents can be lengthy. Tool call return content must have length limits, to prevent exceeding the context window.

## Configuration Settings
These configurations are formulated for FastGPT v4.17.0:

| Configuration Item | Recommended Approach | Rationale |
|---|---|---|
| Region parameter binding | Match against the city name in the request | Urban gas policies take effect by region, so accurate matching of regional policy documents is required |
| `functionCall` configuration | Bind to the clause extraction function | Policy documents have strict clause numbering, so the function must be called to extract specific clauses accurately |
| Single return clause limit | Top 3 clauses | Most policy documents have many clauses; limiting return quantity prevents context overflow |
| Synchronization frequency setting | 7–14 days, calibrated based on actual testing | Policy updates have no fixed cycle, so adjust based on local policy update rhythm |
| Timeout threshold | 600 seconds | Policy database interface responses may take longer due to large data volume |
| `toolChoice` configuration | Set to forced call mode | Ensure tools trigger policy extraction according to preset logic, avoiding unsupported answers |

## Three Common Configuration Errors
- HTTP module calls to the policy database interface fail. Postman calls work normally. Symptoms include 400 status code returns or empty response bodies. The cause is failure to carry correct region parameters in the request, or parameter format not meeting interface requirements.
- Basic chart plugins return no valid data after configuration. Symptoms include blank generated charts or prompts for "no data". The cause is failure to convert structured policy clause content into key-value pair formats recognizable by the chart plugin.
- `toolChoice` parameter is configured incorrectly. Symptoms include tools not triggering the preset policy extraction function. The cause is failure to set the parameter to the correct call mode, or specifying an incorrect function identifier.

## How to Verify Correct Configuration
- Initiate a policy query request with a specific city name. Check if returned results include gas policy clauses for that city.
- Review tool call logs. Confirm that `functionCall` is triggered correctly, and parameters match the request's region and clause scope.
- Manually trigger the synchronization plugin. Check if the local policy library has updated to the latest policy documents.
- Call the chart plugin. Confirm that generated charts correctly display extracted policy clause data.
