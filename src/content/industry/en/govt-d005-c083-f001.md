# Policy and Regulatory Basis Q&A for Infrastructure Construction: HTTP Interfaces and External Systems

## What This Category of Data Looks Like
Policy and regulatory basis data for infrastructure construction comes from official public documents issued by competent infrastructure departments at all levels, including housing and urban-rural development, transportation, water resources, and others. Teams add this data to the repository within 3 working days after a new policy is released.

Documents follow a structured format split by policy hierarchy, document number, issuing authority, effective date, applicable infrastructure scenarios, core binding clauses, and supporting implementation rules. Fields include policy number, issuing unit, effective date, applicable region, clause summary, and source link. No unified business unit field exists. Only the date field uses ISO 8601 format.

## What Constraints Do These Characteristics Impose on HTTP Interfaces and External Systems
HTTP interfaces must support segmented return of large-volume content to avoid request timeouts, due to the long-form, scenario-split nature of infrastructure construction policy data.

Interfaces must provide query parameters for scenario filtering and issuing unit screening, to match the field structure where policies are split by issuing authority and applicable scenarios.

External synchronization systems must use a polling period of no more than 5 working days, to align with the 3-working-day update cycle and ensure data timeliness.

Interfaces must return complete, accessible URLs when delivering data, to handle the policy source link field, and must address cross-domain access restrictions.

Interfaces must support version query parameters, to retrieve policy content for a specified effective date, to accommodate policies with multiple revised versions.

## Configuration Settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {custom secret}` | Complies with the standard identity authentication format for FastGPT external interface calls, ensuring lawful access permissions for the interface. |
| `variables` | `{"apply_scene": "infrastructure construction", "update_cycle": "3 days"}` | Passes scenario and update cycle parameters, matches the applicable scenario and update rhythm fields of policy data, filtering out non-target category policy content. |
| `responseData` | `["policy_number", "publish_unit", "effective_date", "core_clause", "source_link"]` | Only returns core fields required for business purposes, compresses data transmission volume and improves interface response efficiency. |
| Timeout | `60 seconds` | Adapts to the wide variation in length of infrastructure policy documents, covering return requests for most long documents. |
| Retry Count | `2 times` | Addresses call failures caused by network fluctuations, reducing the probability of single request failure. |
| Scenario Filtering | `Filter by detailed infrastructure scenarios` | Matches the applicable scenario field of policy data, ensuring returned content only covers policy basis for the target category. |

## Three Common Misconfigurations
- A `curl error 7` connection failure appears when debugging workflows. Cause: HTTP proxy parameters are not configured, or the secret in the `Authorization` parameter is not bound to corresponding permissions, preventing access to the external policy data interface.
- Returned policy content does not cover target infrastructure scenarios. Cause: Correct scenario filtering parameters are not configured in `variables`, resulting in return of policy files that do not belong to the target category.
- Returned content is truncated after calling the interface. Cause: The timeout configuration is not adjusted, and the response for long documents exceeds the default time limit, leading to incomplete policy content being returned by the interface.

## How to Verify Correct Configuration
- Call the configured HTTP interface, and check whether returned data includes core fields such as policy number and issuing unit. Confirm that the `responseData` configuration meets business requirements.
- Review the applicable scenario field of returned policy content, and confirm that it matches the target infrastructure scenario. Verify the filtering effect of the `variables` parameter.
- Simulate multiple interface calls, and check for repeated connection timeouts or permission errors. Confirm that the retry count and timeout configuration are reasonable.
- Compare the official release time of policy data, and confirm that the latest policy returned by the interface meets the preset update cycle requirements. Verify that the synchronization logic is correct.
