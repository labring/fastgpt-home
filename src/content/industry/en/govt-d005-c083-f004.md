# Policy and Regulatory Basis Q&A for Infrastructure Construction: Workflow Orchestration

## What the data for this category looks like
The policy and regulatory basis data for infrastructure construction is primarily sourced from official announcements, construction specifications, quota standards, and industry guidelines released by the Ministry of Housing and Urban-Rural Development, the Ministry of Transport, and housing and urban-rural development departments of various provinces and cities. Data updates occur irregularly, and are synchronized whenever new policies are issued or specifications are revised. The standard structure of a single document includes fields such as policy document number, issuing authority, effective date, main text of clauses, and attachment descriptions. The policy document number uses the format `Jianshi〔XXXX〕XX No.`. Effective dates follow the YYYY-MM-DD format. The main text length of a single document ranges from several hundred characters to tens of thousands of characters. Attachments mostly include content such as construction drawing requirements and budget quota details.

## What constraints these characteristics impose on the workflow orchestration link
Infrastructure construction policy documents are generally lengthy, so the workflow's context window must support long text parsing to avoid truncating critical clauses. Policy fields include dynamic attributes such as applicable region and construction scenario, which must be bound to corresponding field parameters via `variables` configuration. Without this binding, user questions about project scenarios will not be accurately matched. Data updates occur without a fixed cycle, so the workflow must be configured with a node that synchronizes data sources regularly to ensure recalled policies are the latest versions. Policies vary across different construction scenarios, so the workflow must limit the recall scope based on input project types to avoid redundant results from full retrieval.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Pass the project location and construction type from the user's question | Enable dynamic matching of policy documents for different scenarios, complying with the parameter binding specifications of FastGPT v4.17.0 |
| Context Window Length | 8000–12000 characters | Cover the full main text of lengthy policy clauses to avoid truncating critical construction requirements |
| Debug Mode Timeout | 600 seconds | Accommodate the time required for long document parsing and multi-round policy recall |
| Data Source Synchronization Frequency | Once per month | Match the official policy update rhythm to ensure data timeliness |
| Recall Scope | Limit to current province + construction scenario | Narrow the retrieval scope to improve the accuracy of policy matching |
| `nodeId` | Match the actual ID of the policy recall node | Facilitate quick location of abnormal nodes in debug logs and simplify troubleshooting procedures |

## Three common configuration errors
- Symptom: The workflow returns "parameter format error" during runtime, but executes normally in debug mode. Cause: The policy fields are not bound in the `variables` format required by FastGPT, and non-standard variable reference syntax is used instead.
- Symptom: The workflow cannot consistently perform policy verification operations, and no action is triggered after selecting the corresponding work order. Cause: The policy verification node and the recall node are not bound via clear input and output parameters, and no trigger conditions are set.
- Symptom: The workflow cannot iterate through multiple matching policy clauses, only returning the first result. Cause: The workflow's loop node configuration is not enabled, or the loop trigger conditions and termination threshold are not set correctly.

## How to confirm the configuration is complete
- Navigate to the workflow debug mode, submit a test question containing specific province and construction type, and verify that the recalled policy documents match the target scenario and are not truncated.
- View the running logs of workflow nodes to confirm that the `variables` parameter has correctly passed the bound field values, with no null values or incorrect formats.
- Manually trigger the data source synchronization, and check that the update time of policy documents in the knowledge base after synchronization matches the official release time.
- Switch to runtime mode, perform multiple batch tests, and confirm that the workflow has no timeout or parameter error issues.
