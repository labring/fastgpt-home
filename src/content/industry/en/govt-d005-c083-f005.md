# Policy and Regulatory Basis Q&A for Infrastructure Construction: Tool Calling and Plugins

This configuration solution is compatible with FastGPT v4.17.0.

## What the data for this category looks like
Policy and regulatory basis data for the infrastructure construction sector is primarily sourced from public official documents issued by the Ministry of Housing and Urban-Rural Development, the Ministry of Transport, provincial and municipal housing and urban-rural development departments, and industry competent authorities. New policies prompt an immediate sync of the data to the repository, with multiple policy documents added at different administrative levels each month. Each individual document includes fields such as release document number, issuing authority, release date, applicable project type, enforcement clauses, and penalty standards, presented in a clause-based structured format. Some cross-regional policies also include regional adaptation details. Field units are mostly "article", "paragraph", "item", and standard document number formats.

## What constraints these characteristics impose on tool calling and plugin workflows
Infrastructure construction policy documents are lengthy and have rich fields. Redundant content must be avoided during tool calling, otherwise the model's context window will be exceeded. Policies are time-sensitive, so tool calling must support regularly pulling the latest policy library, otherwise the returned basis may be outdated. Policies at different levels (national, provincial, municipal) have different priority levels, so tool calling must support filtering by level. At the same time, the number of documents per single call must be limited to avoid excessive data volume in a single request. In addition, the standardization of policy fields varies, so tool calling must support specifying specific fields to extract, reducing interference from invalid information.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Tool calling order | Sorted in reverse chronological order of policy release date | Infrastructure construction policies are time-sensitive, and newly released policies have higher priority |
| Number of policy documents returned per single call | Top 3 entries | Individual policy documents are lengthy, too many results will exceed the context window limit |
| Tool calling timeout | 120–180 seconds | Retrieving policy documents requires loading full clauses, which takes longer than general question answering scenarios |
| `toolChoice` | auto | Allow the model to independently determine whether to call tools, adapting to the flexible interaction needs of policy Q&A |
| `functionCall` | Enable specified field extraction | Extract document number, applicable project type, and enforcement standard fields from policy documents, filtering out redundant content |

## Three Common Misconfigurations
- Phenomenon: Multiple tools are configured, but only some are called, and they do not execute in the preset order. Cause: The trigger logic for tool calling is not explicitly configured, so the model does not trigger all configured tools in the preset order.
- Phenomenon: The tool calling returns overly long results, and the model returns a context overflow error. Cause: The number of policy documents returned per single call is set too high, exceeding the model's supported context window.
- Phenomenon: The large model call prompts an overdue balance, and tool calling fails directly. Cause: The bound API key has exhausted its balance, and no alternate key switching logic is configured.

## How to confirm the configuration is complete
- Submit a test query that includes a policy retrieval requirement, check the tool calling logs to confirm that all configured tools are triggered and execute in the preset order.
- Review the tool return results to confirm that only the preset policy fields are extracted, with no redundant or irrelevant content.
- Simulate an API key overdue balance scenario to verify that the tool calling triggers an exception prompt and confirm that the alternate configuration takes effect.
- Switch between streaming and non-streaming modes to verify that the execution logic of the tool node meets the model configuration requirements.
