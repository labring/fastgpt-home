# Policy and Regulatory Basis Q&A for Engineering Consulting Supervision: HTTP APIs and External Systems

## What the data for this category looks like
The policy and regulatory basis data for engineering consulting supervision mainly comes from official documents released by the Ministry of Housing and Urban-Rural Development, housing and urban-rural development authorities of various provinces and cities, and industry associations. Updates are synchronized with the release of new policies, with no fixed cycle. Individual documents mostly follow a chapter-based structure, including fields such as document number, issuing authority, effective date, applicable supervision scenarios, and specific clause content. Clauses are divided into articles, paragraphs, and sub-paragraphs as units. The length of individual document content ranges from thousands to tens of thousands of characters.

## What constraints these characteristics impose on the "HTTP APIs and External Systems" link
Because policy documents include structured fields such as document numbers and effective dates, API requests must carry corresponding filter parameters to accurately match the content required for supervision scenarios. The wide span of individual document lengths requires API pagination parameters to adapt to different lengths of returned content, avoiding data overload from a single return. Data updates have no fixed cycle, so API pull configurations must support on-demand triggering or flexible adjustment of pull intervals, and cannot rely on fixed scheduled tasks. At the same time, the unit of clauses divided by articles requires the API returned content to retain the hierarchical structure, and cannot be flattened. Otherwise, it cannot meet the precise query needs of supervision consulting.

## How to set the configuration
| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| `Authorization` | `Bearer {Exclusive API Key for Engineering Supervision Policy Data Source}` | Most engineering supervision policy data sources are official interfaces that require authentication. The exclusive key ensures identity verification passes |
| `variables` | `{"scene": "Engineering Supervision Policy", "valid_date": "Current Date"}` | Limits the query scope to engineering supervision related policies, and filters valid clauses whose effective dates match the current time |
| `responseData` | Only return document number, clause content, and effective date fields | Reduces invalid data transmission, and adapts to the precise query needs of supervision consulting |
| Request timeout setting | 600 seconds | Policy documents have long content. API return time may exceed standard durations, so the timeout period needs to be extended |
| Pagination pull limit | Top 20 entries | Returning too much content in a single query increases the context processing burden. Supervision consulting usually only requires core policy clauses |
| Update trigger timing | Triggered by new policy release notifications | Policy updates have no fixed cycle. On-demand triggering avoids unnecessary pull operations |

## Three Common Mistakes
- Calling the policy data API returns a 401 status code, prompting invalid credentials. The cause is failing to configure the `Authorization` parameter with the exclusive key, and using universal credentials instead, leading to authentication failure.
- API timeout occurs even after setting up question classification branches in the workflow. The cause is continuing to use the universal short timeout configuration, without adjusting it to the 600-second timeout setting adapted for long documents.
- The returned policy content has no hierarchical structure, which cannot meet the clause query needs of supervision consulting. The cause is failing to retain the field hierarchy as required, directly flattening and returning all content.

## How to Confirm the Configuration is Correct
- Call the test API, check the authentication result, confirm that the `Authorization` parameter verification passes.
- View the `responseData` field returned by the API, confirm that it includes the required fields such as document number, effective date, and clause content.
- Verify the filter conditions passed by the `variables` parameter, confirm that the returned content only matches the engineering supervision policy scenario.
- Simulate multiple calls, confirm that the timeout setting adapts to the API return duration, with no frequent timeout errors.
