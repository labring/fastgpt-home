# Policy and Regulatory Basis Q&A for General Contracting of Building Construction Projects: HTTP Interfaces and External Systems

## What the data for this category looks like
Policy and regulatory basis data for general contracting of building construction projects is sourced from official documents collected on the official website of the Ministry of Housing and Urban-Rural Development, government disclosure platforms of provincial housing and urban-rural development departments, and the National Construction Market Supervision Public Service Platform. Updates are synchronized when new policies are released, or old policies are revised or revoked. Documents take a single policy document as the basic unit, and include policy document number, issuing authority, effective date, clause hierarchy (article, paragraph, sub-paragraph), applicable scenario description, and core clause content. Fields include unique policy identifier, issuing entity type, effective time range, applicable region, and clause classification tags. The minimum content unit is a clause, and regions are counted at the provincial administrative level.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Data sources cover multi-level official platforms, so HTTP interfaces must support configuring multiple domain name whitelists to access policy interfaces from different sources. Documents have a clear clause hierarchy structure, so interface returned content must retain hierarchy fields to support subsequent classification processing. Update schedules have no fixed cycle and require accurate matching of policy status, so interfaces must support filtering parameters based on release time, effective time, and policy status. Policy document content lengths vary widely, so interface request timeout settings must adapt to scenarios with long content returns. Interfaces must also support dynamically passing filter conditions to match policy ranges corresponding to different building construction projects.

## How to set the configurations
| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| Request timeout time | 600 seconds | Long content of building construction policy documents requires adaptation to long text return scenarios |
| `Authorization` configuration | Fill in the access token for the corresponding interface, leave blank if no token | Most official policy interfaces require identity verification to ensure legitimate requests |
| `variables` settings | Configure policy document number and effective time range as custom variables | Facilitate dynamic filtering of policy documents corresponding to different building construction projects |
| `responseData` parsing rules | Extract clause hierarchy and core content according to the native fields returned by the interface, no additional code logic required | Adapt to the hierarchy structure of building construction policy documents, while meeting configuration requirements without additional coding |
| Retry times | 3 times | Address request failures caused by network fluctuations |
| Domain name whitelist | `*.gov.cn`, public network domain name of the deployed interface | Ensure access to official policy platforms and internally deployed interfaces |

## Three common mistakes
- Phenomenon: Interface request returns connection timeout, status code shows 504 or prompt that the target domain name cannot be resolved. Cause: The domain name of the target interface has not been added to the FastGPT domain name whitelist, or dynamic domain names such as peanut shells have not been configured.
- Phenomenon: `responseData` returns empty fields or format does not meet expectations. Cause: Parsing rules are not configured according to the hierarchy structure of building construction policy documents, directly extracting plain text leads to loss of key hierarchy information.
- Phenomenon: Filtered policy range does not match expectations, no policy content corresponding to the target building construction project is returned. Cause: The `variables` parameter is not configured correctly, and the correct policy document number or effective time variable is not passed.

## How to confirm the configuration is correct
- A single test request is initiated, and the returned `responseData` is checked for the expected policy clause hierarchy and core content fields.
- Interface request logs are reviewed, confirming that the `Authorization` parameter is correctly carried, with no identity verification related errors.
- Different `variables` parameter values are passed, verifying that filter conditions take effect and returned policy content matches the expected range.
- The domain name whitelist configuration is checked, confirming that the domain name of the target interface has been added to the allowed list.
