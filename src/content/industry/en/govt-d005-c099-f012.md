# Policy and Regulatory Basis Q&A for Oil and Gas Exploration and Development: Deployment and Upgrade

## What This Category of Data Looks Like
Oil and gas exploration and development policy and regulatory basis data primarily comes from industry specifications released by the Ministry of Natural Resources and the National Energy Administration, internal production management rules of various oilfield enterprises, and oil and gas industry standards. Updates occur without a fixed schedule, synchronized when new policies are released or standards are revised. A single policy document typically includes structured fields such as document number, issuing authority, effective date, applicable exploration block scope, and core clauses. Document length ranges from 5000 to 20000 characters. Some industry standards include multi-chapter technical requirements and compliance clauses, with metering units related to exploration such as square kilometers, cubic meters, and tons.

## Constraints Imposed by These Characteristics During Deployment and Upgrade
Multiple dispersed sources of policy data require deployment support for batch import of multi-format documents and unified metadata management. The lack of a fixed update cycle requires incremental synchronization configuration in upgrade workflows, to avoid service interruptions caused by full re-import. Long documents and multi-field structures require vector databases and relational databases to respectively adapt to storage needs for unstructured text and structured metadata. Sufficient connection pool and cache resources must be configured to handle high-frequency queries during compliance retrieval. FastGPT v4.17.0 deployment templates have been optimized for multi-source data import in this scenario. Additionally, exploration-related metering fields must retain unit associations during retrieval. Accurate mapping configuration for metadata fields must be ensured during deployment.

| `MONGODB_URI` | `mongodb://admin:securepass@db-host:27017/og_policy?authSource=admin` | Stores unstructured policy document text and vector indexes, adapts to complex metadata storage for multi-source documents |
| `PG_URL` | `postgresql://admin:securepass@db-host:5432/og_metadata` | Stores structured fields including policy document numbers, release dates, applicable blocks, supports precise retrieval by document number |
| `REDIS_URL` | `redis://:securepass@cache-host:6379/0` | Caches high-frequency policy Q&A pairs, reduces repeated query load on databases |
| `STORAGE_S3_ENDPOINT` | `https://s3-cn-north-1.amazonaws.com` | Stores uploaded original policy documents in PDF, Word formats, adapts to storage and retrieval of large-volume documents |
| `DB_MAX_LINK` | `20–30` | Matches concurrent query volume for oil and gas exploration policy data, prevents service instability caused by connection pool overload |
| `FILE_TOKEN_KEY` | `32-bit randomly generated hexadecimal string` | Encrypts access tokens for uploaded policy files, prevents unauthorized document access and parsing |
| `FE_DOMAIN` | `https://og-policy.example.com` | Configures frontend access domain, ensures correct loading paths for frontend resources |

## Three Common Misconfigurations
- Symptom: Container startup fails with database connection error, and policy document list fails to load in the interface. Cause: Connection parameters for `MONGODB_URI` or `PG_URL` are not configured correctly, or the database does not allow access from the network segment where the container is deployed.
- Symptom: After uploading a policy PDF during local deployment, search returns no results. Cause: `FILE_TOKEN_KEY` is not configured correctly, causing the file parsing service to fail to obtain access permissions for uploaded documents, and unable to complete text splitting and vectorization.
- Symptom: Cloud version login prompts that initial password does not exist, preventing administrator login. Cause: `ROOT_KEY` is not configured during the deployment workflow to generate initial administrator credentials, or initialization configuration steps are not completed.

## How to Verify Successful Configuration
- Run the `docker ps` command to confirm all dependent database, cache, and storage service containers are in running state.
- Upload a test oil and gas exploration policy document, enter keywords in the search interface, confirm matching document fragments and metadata information are returned.
- Access the frontend address corresponding to `FE_DOMAIN`, log in to the backend using the configured administrator account, confirm metadata has been synchronized to the relational database.
- View the cache monitoring panel corresponding to `REDIS_URL`, confirm there are cache hit records, indicating high-frequency queries have been properly cached.

The values provided are common starting points and should be measured against the user's own operational samples.
