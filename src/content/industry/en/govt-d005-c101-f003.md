# Policy and Regulatory Basis Q&A for Port and Shipping: Multi-turn Dialogue and Prompt Engineering

## What this category of data looks like
Port and shipping policy and regulatory basis data is sourced from publicly released documents from the Ministry of Transport Water Transport Bureau, official announcements from directly affiliated port administrations, and official translations of International Maritime Organization conventions. Updates are synchronized immediately after a policy is officially released. Regular industry announcements are updated weekly.
Individual documents typically include document numbers, issuing entities, effective dates, applicable port area scopes, clause details, and other content. Fields include policy numbers, release dates, covered port areas, core constraint conditions, and units involving professional parameters such as twenty-foot equivalent units (TEU), ship deadweight tonnage, and navigation time windows.

## Constraints on multi-turn dialogue and prompt engineering
The applicable port area, effective date, and professional unit characteristics of port and shipping policy data create clear constraints for multi-turn dialogue and prompt configuration.
Policy applicable scope must be matched against the port area specified by the user. Multi-turn dialogue must retain port area and query time information from the context to prevent cross-regional policy confusion or expired clause references.
Add preset verification logic in prompts to ensure unified matching of professional units and avoid unit conversion errors. Policy clauses have hierarchical details, so multi-turn dialogue must support users to ask follow-up questions layer by layer, and preset context recall trigger rules.
High policy update frequency requires prompts to explicitly call the latest synchronized knowledge base entries to ensure answer timeliness.

## Configuration settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Chunk length | 800–1200 characters | Most individual port and shipping policy documents range from 1000 to 5000 characters. This chunk length preserves clause integrity and avoids splitting across clauses. |
| Overlap length | 150–200 characters | Policy clauses include associated applicable scope descriptions in preceding and following text. Overlapped chunks preserve context coherence. |
| Max context | 6000–8000 characters | Can cover key information from 3 to 5 rounds of dialogue, including core parameters such as port area and query time. |
| Context message storage | Retain the first 10 entries of the `messages` array | Fully stores interaction history between users and the system, ensuring multi-turn dialogue coherence. |
| Global variable binding | Bind the port area code field in `variables` | Automatically passes user-specified port information, avoiding repeated input. |
| Session identifier binding | Bind `chatId` as the unique identifier | Associates session-specific context to enable cross-turn information synchronization. |

## Three common misconfigurations
- Symptom: The AI can only retrieve the current round's user query during multi-turn dialogue, and cannot recall port area or time information from the initial query. Cause: The context transfer logic for the `messages` array is not configured in the orchestration workflow, so the judgment component cannot pass historical queries to subsequent AI dialogue links.
- Symptom: Response timeouts occur when calling the local policy knowledge base, or single-round query time exceeds a reasonable range. Cause: No reasonable maximum context length is set, causing the system to load excessive policy document chunks and consume excessive computing resources.
- Symptom: The applicable scope of policy clauses returned in dialogue is incorrect, such as applying Shanghai Port policies to Ningbo Port. Cause: No `variables` are bound to pass user-specified port information, so the system cannot match policy files for the corresponding port area.

## How to verify correct configuration
- Initiate a query that specifies a target port area and policy type, and confirm that the system matches policy clauses for the corresponding port area.
- Initiate consecutive multi-turn interactions, and confirm that the system retains key information from the previous round without requiring repeated input of the same parameters.
- View session logs, and confirm that `chatId` is bound to the current session and that `variables` correctly pass user-input parameters.
- Trigger consecutive multi-round queries, and confirm that system response time falls within the preset reasonable range.
