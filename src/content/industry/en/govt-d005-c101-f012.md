# Policy and Regulatory Basis Q&A for Port and Shipping: Deployment and Upgrade

## What the data for this category looks like
Policy and regulatory basis data for the port and shipping sector is primarily sourced from normative documents, industry regulatory announcements, and official policy interpretations released by the Ministry of Transport, direct maritime safety administrations, and port authorities at port locations. The data update schedule aligns with policy releases from national and local transport authorities. Documents follow formal official document formats, and include document numbers, issuing bodies, effective dates, applicable port areas, specific regulatory clauses, fee standards, and other content. Some documents include attachment lists, with fields covering policy ID, release time, applicable scope, core requirements, and more.

## What constraints these characteristics impose on deployment and upgrade
The formal official document format and regionally applicable nature of port shipping policy data impose multiple constraints on deployment and upgrade workflows.
Formal official documents have widely varying structures across formats including PDF, Word, and official web pages. During deployment, parsing rules must be configured to match document hierarchies, ensuring accurate chunking of policy clauses.
Regionally applicable fields require regional filter parameters to be configured during deployment, limiting Q&A responses to only policy content for the corresponding ports.
The synchronized update schedule tied to policy releases requires upgrade workflows to support incremental synchronization, avoiding resource consumption from full data rebuilding.
Some policies include attachment lists, so dedicated storage paths must be configured during deployment to ensure attachments can be properly retrieved and linked.

## Configuration Settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://<username>:<password>@<host>:27017/admin` | Port policy data must be stored in MongoDB. This parameter configures the database access address, compatible with local or cloud deployment instances |
| `STORAGE_S3_ENDPOINT` | `http://<minio-host>:9000` or the endpoint address of the corresponding cloud storage service | Port policy documents and attachments must use S3-compatible storage. This parameter configures the storage service access path |
| `DB_MAX_LINK` | `80–120` | Limits the number of linked connections loaded during database queries, avoiding excessive load from multiple associated attachments in port policy documents |
| `REDIS_URL` | `redis://<host>:6379/0` | Used to cache session and vector retrieval results for port policy Q&A. This parameter configures the Redis service access address |
| `FILE_TOKEN_KEY` | `32-character random string` | Generates access tokens for port policy document uploads, ensuring security during the document upload process |
| `ROOT_KEY` | `Secure key generated based on the deployment environment` | Used for administrator interface permission verification, ensuring security of post-deployment management operations |

## Three Common Misconfigurations
- Symptom: Service startup logs display MongoDB replica set configuration errors, with prompts including "no reachable servers" or "replicaSet not configured". Cause: Replica set parameters in `MONGODB_URI` are not configured correctly, or the MongoDB replica set was not initialized during local deployment.
- Symptom: After uploading port policy documents, the data processing step returns empty results with no error messages. Cause: The `STORAGE_S3_ENDPOINT` parameter is not configured, leading to abnormal document storage paths, and the parsing service cannot read uploaded files.
- Symptom: Vector index results work normally locally, but when packaged as a Docker image, all query vector scores are identical. Cause: The `REDIS_URL` parameter is not configured correctly, leading to the cache service failing to start, and vector retrieval results not being properly isolated.

## How to Confirm Proper Configuration
- Run a database connection test script to verify that the address configured in `MONGODB_URI` is accessible, with no connection timeouts or permission errors.
- Upload a test port policy document, check that the storage service receives the file normally, and that the path configured in `STORAGE_S3_ENDPOINT` can read the file content normally.
- Start a session cache test to verify that the service configured in `REDIS_URL` can write and read cache data normally.
- Use the administrator key to call the interface, verify that the permission verification logic configured in `ROOT_KEY` takes effect normally.

The values provided are common starting points and should be measured against the reader's own samples.
