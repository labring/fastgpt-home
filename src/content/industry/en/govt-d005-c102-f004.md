# Policy and Regulatory Reference Q&A for Refinery and Chemical Production: Workflow Orchestration

## What This Category of Data Looks Like
Data for policy and regulatory reference in refinery and chemical production comes from official policy documents released by the National Energy Administration, the State-owned Assets Supervision and Administration Commission of the State Council, and competent industry authorities for the petroleum and petrochemical sector. It also includes internal production safety regulations and environmental control rules from refinery and chemical enterprises.
External policies are updated quarterly to annually. Internal regulations are adjusted every six months alongside process upgrades.
Document structure includes release document number, effective date, applicable production link, clause number, and compliance requirements. Units include milligrams per cubic meter for emission limits, megapascals for equipment operating parameters, hours for working hours, and others. All data pulling and processing adapts to FastGPT v4.17.0 workflow rules.

## What Constraints These Characteristics Impose on Workflow Orchestration
The multi-source and categorized structure of policy documents requires configuring multiple data source pull nodes to route content by release entity and applicable production link.
The effective date field requires embedding an automatic verification node to filter expired policy documents.
Diverse unit standards require configuring a parameter conversion node to unify unit benchmarks for compliance verification.
When batch pulling multiple long documents, limit the processing duration of each single node to avoid timeout interruptions.
Dedicated policies for different production links require conditional branch nodes to accurately match verification logic for corresponding scenarios, preventing cross-link compliance judgment errors.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Refinery policy documents mostly contain long clauses. Too short chunks split compliance logic, while too long chunks exceed large model context limits |
| Overlap Length | 100–150 characters | Ensures compliance clauses in adjacent chunks are not truncated, maintaining logical coherence |
| Single Search Limit | Top 8 results | The number of policy documents is relatively fixed. Excessive recall increases context load |
| `variables` | Bind `production link type`, `document effective date` | Accurately match policy documents for the corresponding link, filter expired content |
| `nodeId` | Bind the ID of the corresponding policy data source node | Accurately locate the data source to be called, avoid cross-node call confusion |
| Concurrent Execution Switch | Enabled, set concurrency to 2–4 nodes per minute based on actual testing | Improve operating efficiency when batch processing multiple policy documents, avoid single node blocking |

## Three Common Configuration Mistakes
- Phenomenon: Only a single node runs sequentially during batch policy verification, with no concurrent effect. Cause: The workflow's concurrent execution switch is not enabled, or the concurrency setting exceeds node resource limits.
- Phenomenon: Workflow run logs return an `offset 17` related error. Cause: Mismatched chunk length and overlap length leading to abnormal chunk index calculation, or damaged file format in the data source.
- Phenomenon: Policy data source node icons do not display in the workflow canvas. Cause: The plugin package for the corresponding version was not imported correctly, or `nodeId` configuration error caused abnormal node loading.

## How to Confirm Proper Configuration
- Manually trigger the verification process for a single policy document, check if the returned results match the compliance requirements of the current production link.
- View workflow run logs, confirm that the `variables` parameter is correctly bound to the required production link and document effective date fields.
- Batch trigger the verification process for multiple policy documents, check if nodes run in parallel according to the configured concurrency rules.
- Upload a test policy document in TXT format, confirm that the parsed content can be properly read by the large model and generate corresponding summaries.
