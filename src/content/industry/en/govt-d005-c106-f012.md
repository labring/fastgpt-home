# Policy and Regulatory Basis Q&A for Coal-Electric Integration: Deployment and Upgrade

## What the Data for This Category Looks Like
Coal-electric integration policy and regulatory basis data comes from three main sources. These are public documents from the National Energy Administration, the State-owned Assets Supervision and Administration Commission of the State Council, and provincial and municipal energy authorities. They also include standard specification documents from authoritative industry associations.
The data update schedule adjusts with new policy releases. There is no fixed cycle. New policies for coal-electric joint operations, project approval, or capacity regulation will trigger updates.
Each document includes structured fields. These are issuing authority, document number, effective date, applicable scenarios, and core clauses. Clause content is mostly long-form text.
Field units mostly use "article", "paragraph", or "item". Some time-related fields use "year" or "month".

## Constraints on Deployment and Upgrade
The multi-source official nature of coal-electric integration policy data requires configuring `STORAGE_S3_ENDPOINT` during deployment. This stores original document copies, preventing data loss from official source changes.
The non-fixed update schedule requires supporting incremental sync configuration. This avoids resource waste from full re-imports.
The structured fields and long text content require retaining metadata associations during knowledge base import. It also requires adjusting database connection pool parameters to adapt to concurrent read/write of long texts.
For the upgrade phase, synchronously update metadata table structures. This avoids query exceptions from version differences. Control concurrent connection counts when batch importing large numbers of long documents. This prevents database blocking.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 10–15 connections | Adapts to concurrent read/write requirements when batch importing coal-electric integration policy documents, avoiding database connection pool exhaustion |
| `STORAGE_S3_ENDPOINT` | Official access address of self-built object storage | Used to store complete copies of original policy documents, supporting file comparison during incremental updates |
| `REDIS_URL` | `redis://127.0.0.1:6379/0` | Used to cache matching results of high-frequency policy Q&A, shortening query response times |
| `PG_URL` | PostgreSQL connection address linked to metadata storage | Used to store structured metadata such as policy document numbers, issuing authorities, and effective dates |
| `ROOT_KEY` | Random string customized per business security requirements | Used to configure FastGPT administrator operation permissions, ensuring access security of the deployment environment |

## Three Common Mistakes
- After upgrading to FastGPT v4.17.0, visual statistical charts for policy Q&A display errors. This happens because the metadata table structure linked to `PG_URL` was not synchronously updated. The chart API cannot read newly added policy statistical fields.
- In Docker deployment scenarios, the indexing progress of the coal-electric integration policy knowledge base stagnates for long periods. This occurs because the connection count limit for `DB_MAX_LINK` was not adjusted. Batch import of long documents exhausts database connections, blocking the indexing process.
- When orchestrating policy Q&A workflows with HTTP requests, the configured output field does not appear in conversation results. This happens because the result write-back switch was not enabled in the orchestration node. Output content is not written to the conversation context.

## How to Confirm Proper Configuration
- Run a test task to batch import a single coal-electric integration policy document. Check database connection logs to confirm the connection count does not exceed the `DB_MAX_LINK` limit.
- Access the frontend address configured in `FE_DOMAIN`. Log in to the administrator backend. Check if imported policy documents include metadata fields such as document numbers and issuing authorities.
- Initiate a high-frequency policy Q&A query. Check Redis cache logs to confirm query results are properly cached.
- Run the Docker container health check command. Confirm that connection configurations such as `PG_URL` and `REDIS_URL` can connect to their corresponding services.

The values provided above are common starting points, and should be evaluated against the user's own samples.
