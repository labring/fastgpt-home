# Policy and Regulatory Basis Q&A for Mineral Mining and Processing: Knowledge Base Retrieval and Recall

## What data for this category looks like
Policy and regulatory basis data for mineral mining and processing mainly comes from industry safety regulations and environmental emission standards released by the Ministry of Natural Resources and the Ministry of Emergency Management, as well as internal mining and processing operation management systems of state-owned mining enterprises. Update rhythm aligns with policy revisions, with no fixed cycle. Core policy documents complete version iteration every 1–2 years. Each individual document includes fields such as policy document number, issuing authority, effective date, applicable mining area type, compliance requirements for mining and processing links, penalty clauses, and more. Units used include cubic meters (tailings reservoir storage capacity), ten thousand tons per year (production scale), meters (safety distance), and others.

## What constraints do these characteristics impose on knowledge base retrieval and recall?
Policy documents from multiple departments have field differences. When conducting retrieval, divide the scope by issuing entity or compliance category to avoid mixing policy clauses from unrelated fields. The non-fixed update rhythm requires an incremental synchronization mechanism: only recently revised documents are updated each time, to avoid full repeated imports that consume resources. Documents contain both structured fields and full-text descriptions, so balance keyword matching and semantic retrieval. A single retrieval mode cannot cover all query scenarios. The length of individual documents varies greatly; properly split long documents to avoid exceeding context window limits.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| `similarity` | 0.75–0.85 | Policy documents for mineral mining and processing have dense technical terminology. A threshold that is too low will introduce irrelevant compliance clauses, while a threshold that is too high will miss policies in the same category |
| `limit` | Top 8–12 results | Individual policy documents have relatively long lengths. Too many results will exceed the context window, while too few will fail to cover all compliance requirements for the same scenario |
| `searchMode` | `keyword+vector` | Balance keyword matching for structured fields such as policy document numbers and effective dates, and semantic retrieval for compliance requirement descriptions |
| `usingReRank` | Enabled | Policy documents in the same category have high semantic similarity. Re-ranking can filter out results with weak relevance and improve ranking accuracy |
| `datasetSearchUsingExtensionQuery` | Disabled | Technical terms for mineral mining and processing are fixed, so query extension is unnecessary. This avoids introducing irrelevant content from non-target fields |
| `collectionIds` | Bind exclusive collection IDs for mineral mining and processing policies | Split datasets by safety, environmental protection, and production management. Specifying a collection narrows the retrieval scope and prevents mixing documents from other categories |

## Three common mistakes
- Symptom: The number of retrieval results is insufficient, only returning some compliance entries within the specified range. Cause: `collectionIds` is not configured, the retrieval scope covers policy documents unrelated to mineral mining and processing, and the system automatically filters a large number of irrelevant results.
- Symptom: Document grouping is lost after backup import to the knowledge base, and original policy classifications cannot be retained. Cause: Datasets are not split by mining and processing links or policy categories, and all documents are stored in a single collection. The original grouping logic cannot be restored during import.
- Symptom: A MongoServerError prompt related to $ operators appears when the plugin loads. Cause: Connecting MongoDB 4.4.29 with FastGPT v4.13.0 or earlier versions, there is a compatibility conflict between the database version and the plugin. This issue has been fixed in FastGPT v4.17.0 and later versions.

## How to confirm the configuration is correct
- Submit a test query that includes policy document numbers and keywords related to mining and processing links, and check whether the returned results only include mineral mining and processing policy documents within the specified scope.
- Check whether the number of retrieval results falls within the value range specified by the `limit` configuration, with no obvious excess or shortage.
- Review whether the re-ranked results prioritize core compliance requirements; the initial similarity score only serves as a supplementary reference.
- Confirm that the `collectionIds` configuration is bound to the exclusive dataset, and no policy documents from other industries are mixed in.

The values provided are common starting points and should be measured against the reader's own samples.
