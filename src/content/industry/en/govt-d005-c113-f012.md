# Policy and Regulatory Basis Q&A for Shipbuilding: Deployment and Upgrade

## What the data for this category looks like
Policy and regulatory basis data for the shipbuilding sector comes primarily from official regulatory documents, mandatory industry standards released by the Ministry of Industry and Information Technology, the Ministry of Transport, and the National Maritime Administration, as well as guidance documents from national shipbuilding industry associations.
Updates trigger synchronously with new policy releases, and a single update covers multiple documents.
Document structures include fields such as document number, issuing authority, effective date, applicable vessel type categories, technical indicator requirements, and compliance determination clauses.
Some standard documents contain tabulated quantitative indicators such as deadweight tonnage and main engine power.

## How These Characteristics Create Constraints During Deployment and Upgrade
The long-text structure and quantitative field features of shipbuilding policy data require adapted chunking and metadata binding logic during deployment. This prevents loss of key associated information such as document numbers and effective dates after splitting.
Structured parameter threshold fields require metadata filtering rules configured during retrieval. This ensures recalled results only match compliance requirements for the target vessel type.
The non-fixed update cycle requires upgrade support for incremental sync configuration items. This avoids resource usage caused by full re-crawling.
Additionally, tabulated content in some standard documents must retain row and column structure during preprocessing. This prevents information breaks during retrieval.

| `REDIS_URL` | `redis://default:password@host:6379` | Caches retrieval results and sync task status, reduces database concurrent load |
| `STORAGE_S3_ENDPOINT` | `https://s3.example.com` | Stores original policy documents and structured metadata, adapts to cross-node file access needs |
| `DB_MAX_LINK` | 40–60 | Limits database concurrent connection count, adapts to batch sync tasks for policy documents, avoids resource overload |
| Incremental Sync Threshold | Calibrated based on actual testing | Adapts to non-fixed policy update cycles, triggers incremental pull on demand, reduces resource consumption from full sync |

## Three Common Misconfigurations
- Symptom: Content is lost after knowledge base chunking, and displayed document fragments are incomplete. Cause: When the chunk length is set to 3000 characters, preprocessing logic adapted for long texts is not configured. This causes trailing content of long policy files to be truncated or skipped.
- Symptom: Redis connection errors occur, and sync task logs for policy documents cannot be pulled. Cause: The address or permission parameters configured for `REDIS_URL` are incorrect. It does not adapt to network access restrictions of the deployment environment, leading to connection timeouts.
- Symptom: Custom model access fails, and locally deployed image recognition tools cannot be called. Cause: The network address and port of the local service are not correctly filled in FastGPT's model configuration, and cross-domain access permissions are not enabled.

## How to Verify Proper Configuration
- Upload a shipbuilding policy standard document, check that chunked fragments fully cover the original content with no obvious missing parts.
- Access the Redis management interface, check if FastGPT-generated sync task cache key-value pairs exist, and confirm the connection is working.
- After configuring `STORAGE_S3_ENDPOINT`, upload a test document to the corresponding storage bucket, check that it can be pulled and indexed normally.
- Trigger an incremental sync task, check that the task log only syncs newly added policy files, with no full re-crawling records.
