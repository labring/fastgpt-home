# Policy and Regulatory Basis Q&A for Metal Material Processing: HTTP Interfaces and External Systems

## What This Category of Data Looks Like
Metal material processing policy and regulatory basis data is sourced from steel and non-ferrous industry policy documents issued by the Ministry of Industry and Information Technology and the National Development and Reform Commission, compliance guidelines from local industrial and information departments, and industry standard documents from the Chinese Society for Metals. Updates are synchronized when new policies are released. Industry standards are calibrated quarterly. Document structure includes policy document number, issuing authority, effective date, applicable processing technology scope, core clause content, and compliance judgment basis. Fields include policy unique identifier, applicable material grade, processing procedure requirements, and units such as tons, millimeters, cubic meters, and others.

## What Constraints These Characteristics Impose on HTTP Interfaces and External Systems
The applicable material grade and processing procedure fields of the data require corresponding parameters to be passed in HTTP interface requests. This ensures accurate matching of policy clauses and avoids returning irrelevant content. Data updates do not follow a fixed schedule. External systems must verify the policy library version before calling to avoid using expired clauses. Multiple unit types are included in the fields. The compliance judgment content returned by the interface must include unit information to prevent ambiguity. The policy document structure includes document numbers and effective dates. The interface must support filtering results by document number or effective date to meet external system query needs.

## How to Configure
| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| `Authorization` | `Bearer sk-xxxxxx` or a valid key assigned by the platform | Used for interface identity verification, ensuring access permissions for metal processing policy data |
| `variables` | `{"material_grade": "Q235", "process": "hot_rolling"}`, adjust parameters according to actual processing scenarios | Pass material grade and processing procedures to accurately match corresponding industry policy clauses |
| `responseData` | Includes `policy_content, policy_number, effective_date` fields | Match the standard field structure of metal processing policy documents, facilitating parsing by external systems |
| Request timeout setting | 30 seconds | Policy documents are relatively long, avoiding request interruption due to content pull timeout |
| Number of returned results | Top 3 entries | Metal processing single-scenario policies usually correspond to a small number of core clauses, avoiding returning redundant content |
| Third-party key configuration | Fill in the API address and key assigned by OneAPI when connecting | Adapt to third-party call requirements for metal processing policy data, supporting multi-platform key management |

## Three Common Mistakes
- An API request returns an "invalid key" error. The cause is that the OneAPI address and key filled in during third-party key configuration do not match, and correct link configuration was not completed.
- The returned policy content lacks the applicable material grade field. The cause is that the `responseData` configuration does not include the corresponding field, and the standard data structure of metal processing policies was not matched.
- Some regions encounter connection timeout or 403 status codes when initiating API requests. The cause is that the `Authorization` parameter was not carried correctly, or the external system's egress IP is not included in the FastGPT access whitelist.

## How to Confirm the Configuration Is Complete
This verification process applies to FastGPT v4.17.0:
- Initiate a test request carrying the `variables` parameter, and check whether the returned results include policy clauses corresponding to the material grade.
- Check whether the `responseData` field returned by the interface includes preset fields such as policy document number and effective date.
- Verify that the `Authorization` parameter is carried correctly, and the request does not return 401 or 403 status codes.
- After testing the call, confirm that the external system can correctly parse the returned policy content and accompanying unit information.
