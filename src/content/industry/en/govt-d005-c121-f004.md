# Policy and Regulatory Basis Q&A for Expressway Operations: Workflow Orchestration

## What this category of data looks like
Expressway operation policy and regulatory basis data mainly comes from the official website of the Ministry of Transport, provincial transport departments, and public announcements from local expressway operation management agencies. Data updates trigger when policies are revised or local detailed rules are released, with no fixed schedule. The document structure includes fields such as policy document number, issuing authority, effective date, clause text, and applicable road section scope. Some documents have attachments like toll standards and maintenance specifications, with units including kilometers, yuan, and working days.

## What constraints these characteristics bring to the workflow orchestration link
Policy documents come from dispersed sources covering national, provincial/municipal, and local levels. Configure workflows with multi-source recall nodes to ensure coverage of all policy tiers. Policy updates have no fixed schedule, so add regular source synchronization steps to workflows to avoid using expired clauses. Some policies have road section scope restrictions, so configure variable filtering nodes to match corresponding policy clauses based on operating road sections in `variables`. Long policy documents have multiple chapters and clauses, so complete text splitting and key field extraction in workflows in advance to avoid context overflow affecting Q&A accuracy.

## How to set the configuration
The content on this page is compatible with FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Basis for This Approach |
|---|---|---|
| Multi-source recall sources | Specify official sources of the Ministry of Transport, provincial transport department, and local operating institutions | Expressway operation policies cover national, provincial/municipal, and local levels |
| Variable filtering rules | Match policy applicable scope based on operating road section ID in `variables` | Most policy clauses have applicable restrictions for specific road sections |
| Context window length | 8000–12000 token | Single policy documents have relatively long average length, need to retain complete clause context |
| Node timeout | 300–600 seconds | Multi-source recall needs to pull data across multiple official websites |
| Result filtering condition | Keep the top 3 policy clauses with relatively high matching degrees | Policy Q&A needs to accurately correspond to specific clauses, avoid redundant information |
| Branch trigger node | Trigger based on the result returned by the node with `nodeId` as "Policy Recall" | Need to execute subsequent Q&A generation links based on policy recall results |

## Three common mistakes
- Phenomenon: A specified reply node is configured to output HTML code, but no content is displayed during runtime and it directly proceeds to the next branch. Cause: The allow raw HTML output configuration for the specified reply node is not enabled, causing content to be automatically filtered.
- Phenomenon: Workflow runtime exceeds the preset threshold, leading to slow overall response. Cause: The number of multi-source recall sources is not limited, and no result filtering condition is set, resulting in pulling too much redundant policy document data.
- Phenomenon: The final answer after tool call includes input and response reference content from knowledge base search. Cause: The configuration to display retrieval context is not turned off in the Q&A generation node, causing original retrieval information to be included in the final output.

## How to confirm the configuration is correct
- Manually trigger the workflow, enter a policy consultation question with a specific road section number, check if the recall results include policy clauses for the corresponding road section.
- View the workflow runtime logs, confirm that the multi-source recall node successfully pulled official source data of the specified level, with no timeout errors.
- Enable the test branch, configure a test road section ID, verify whether the variable filtering node correctly filters matching policy clauses.
- After calling the tool node, check that the final answer only contains policy clause content, with no redundant fields related to retrieval.
