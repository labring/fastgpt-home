# Document and Material Drafting for 12345 Citizen Hotline Ticket Handling: Multi-turn Dialogue and Prompt Engineering

## What the data for this category includes
The data for this category primarily comes from the 12345 citizen hotline platform, contractor business systems, dedicated knowledge bases, return visit evaluation data, and local hotline management regulations. Daily processed documents include request registration forms, dispatch records, handling responses, return visit records, extension applications, return explanations, and knowledge base entries. Data is updated daily. Individual ticket data includes fields such as request number, request content, contractor unit, handling status, return visit result, and others. Relevant business information is updated synchronously as tickets progress through their workflow, with no fixed quantitative statistical values.

## What constraints these characteristics impose on the "multi-turn dialogue and prompt engineering" link
The data for this category originates from multiple sources and is updated daily. Daily documents have fixed format fields, and the core workflow centers on the full-process handling of public requests. Multi-turn dialogue must first match the contractor unit and request type associated with a ticket, so it is necessary to gradually guide clarification of the current ticket status during dialogue to avoid confusing ticket data from different workflow stages. At the same time, generated documents must strictly correspond to the fixed fields of documents such as request registration forms and handling responses, and cannot generate unsubstantiated content based on existing business data. Additionally, the data update frequency requires that dialogue context be limited to current and recent tickets to avoid calling outdated business information.

## How to set up the configuration
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Unique ticket number | Binds a unique conversation ID to avoid confusing context across tickets, ensuring dialogue only associates with the currently handled ticket |
| `messages` | First 3 rounds of dialogue content + core data of same-day tickets | 12345 hotline tickets progress quickly; excessive historical dialogue will interfere with current response generation. Limiting the scope improves response accuracy |
| Single search limit | Top 3 knowledge base entries | Hotline policy entries are concise; excessive entries will cause context overload and reduce response precision |
| Maximum context length | 800–1200 characters | Matches the typical word limit for single-ticket response content, avoiding content truncation caused by exceeding model processing limits |
| `variables` | Inject ticket number, contractor unit fields | Generated documents must include fixed business fields to ensure generated content complies with government document formatting requirements |
| Question optimization | Enabled | Public requests may be vaguely phrased; optimization allows more accurate matching of policy content in the knowledge base |

## Three common errors
- Phenomenon: The model prompts that the knowledge base is empty during dialogue, but all text content can be viewed on the knowledge base page. Cause: The newly migrated local hotline management regulation knowledge base was not associated with the current 12345 ticket dialogue workflow.
- Phenomenon: AI response content annotations only trigger execution after all streaming responses are completed. Cause: The trigger timing of annotations was not correctly bound to each round of dialogue response nodes, making it impossible to provide real-time feedback of key information to contractors.
- Phenomenon: After uploading an xlsx-format ticket template or statistical file, core fields such as ticket number and contractor unit cannot be extracted for dialogue. Cause: No field mapping rules were configured for government affairs tables, so parsed content cannot match the business variables required for dialogue.

## How to confirm the configuration is complete
- Manually create a simulated ticket, fill in common public request content, and verify that the generated response includes required fields such as ticket number and contractor unit.
- Switch the status of the simulated ticket (such as pending response, returned order) and verify that the dialogue can correctly match knowledge base policy content for the corresponding stage.
- Upload a simulated local hotline management regulation file and verify that the dialogue can accurately reference its clause content to assist in responses.
- View the conversation log to confirm that the `variables` parameter has correctly injected core ticket fields, and that `chatId` matches the current ticket number.

The values provided are common starting points and should be measured against the reader's own samples.
