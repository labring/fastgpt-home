# Document and Material Drafting for Infectious Disease Information Reporting and Monitoring: Workflow Orchestration

## What Data Looks Like for This Category
The data for this category comes from the Chinese Center for Disease Control and Prevention Information System, medical institution HIS and infectious disease reporting systems, and laboratory testing systems, with a daily update frequency. Daily generated documents and materials include infectious disease report cards, epidemic analysis reports, case correction records, clustered epidemic reports, and epidemiological investigation reports. The document structure includes fixed fields such as case identity information, diagnosis details, reporting time limits, and correction explanations. Some documents need to be associated with laboratory test result data. The number of fields in a single report card is fixed. Epidemic analysis reports aggregate multiple case data according to the monitoring cycle.

## What Constraints These Characteristics Impose on Workflow Orchestration
The daily updated data requires the workflow to be configured with a scheduled trigger node to ensure timely processing of same-day case data. The fixed-field document structure requires adding a field verification step in the workflow to prevent missing legally required items such as reporting time limits and case diagnosis information. Multiple system data sources require configuring multi-node parallel pulling to integrate associated data from HIS and laboratory systems. Legal reporting rules require embedding time limit verification logic in the workflow to trigger alerts for cases exceeding reporting time limits, preventing regulatory risks caused by delayed or missed reports.

## Configuration Settings

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Single Search Limit | Top 8 entries | Matches the recall demand for daily case data, avoids redundant information interfering with verification |
| Maximum Context | 7000–11000 characters | Carries the complete content of multiple report cards, correction records, and aggregated analysis |
| Variable | `variables` | Stores dynamic monitoring data such as daily abnormal case count and reporting time limit overtime count |
| Node ID | `nodeId` | Marks core nodes such as scheduled triggers, multi-system data pulling, and field verification |
| Timeout Setting | 500–700 seconds | Adapts to the time consumption of multi-system data integration, prevents accidental workflow interruption |
| Knowledge Base Search Citation Limit | 3000 characters | Complies with context length limits in workflow scenarios, differentiated from application-side configuration |

## Three Common Misconfigurations
- Phenomenon: Multimodal data cannot correctly call multimodal models in the workflow, and plain text tasks are assigned to text-only models. Cause: The model calling rules are not divided by data type in the node configuration, and `variables` is not used to mark data modality attributes.
- Phenomenon: The number of knowledge base references returned after workflow execution does not match the configured single search limit. Cause: The application-side knowledge base reference limit parameter was mistakenly applied to the workflow node, and the workflow-specific reference limit configuration item was not used.
- Phenomenon: The workflow runtime prompts that text content triggers document parsing logic. Cause: The automatic parsing switch for non-document text was not turned off in the node, causing plain text descriptions of case reports to be incorrectly chunked.

## How to Verify Correct Configuration
- Check the scheduled trigger configuration of the workflow, confirm that the trigger frequency is set to daily to match the data update frequency.
- Run a test workflow, check if the pulled data sources include the two core sources: Chinese Center for Disease Control and Prevention Information System and HIS system.
- Trigger the field verification node, input test data with missing reporting time limits, confirm whether the corresponding alert is triggered.
- View the node logs, confirm that the dynamic data stored in `variables` matches the daily monitored case count.

The values provided are common starting points and should be measured against the reader's own samples.
