# Document and Material Drafting for Petition Case Handling: Workflow Orchestration

## What the Data for This Category Looks Like
This category of data comes from the national petition information system, local petition systems, the 12345 citizen hotline platform, grassroots governance platforms, and historical petition archives, and is updated daily. Commonly processed documents include petition registration forms, acceptance notice letters, transfer and assignment notices, handling opinions, review and re-review applications, resolution plans, and similar materials. Data fields include the requesting party, case content, handling milestones, responsible units, and other details. Each single data entry is associated with all document materials for the complete handling process.

## How These Characteristics Impact Workflow Orchestration
Workflows must support multi-data-source synchronization nodes to pull petition archives and real-time requests from different systems, as data sources are decentralized and linked to full-process documents.
Diverse document types require branch judgment nodes that match corresponding document templates to the petition case handling stage.
Daily updated data sources mean workflows must support scheduled triggering or real-time pulling to avoid data lag.
Handling errors can lead to repeated or escalated petition cases. Verification links must be configured at key nodes to ensure document content complies with statutory handling procedures.

## Configuration Guidelines
This guide applies to FastGPT v4.17.0. The following configuration items can be adjusted based on actual scenarios.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum Context | Last 8 conversation records | Multiple rounds of petition case handling requests require retaining complete conversation history of handling milestones to avoid loss of key information |
| Text Content Extraction | Chat records: 6 entries | Matches the number of historical requests and handling records commonly used in petition handling, covering core handling information |
| Scheduled Trigger Interval | 120 seconds | Adapts to the daily update rhythm of petition data, balancing real-time performance and system load |
| `variables` | Bind petition case ID | Used to pass unique case identifiers between workflow nodes, ensuring documents are associated with the corresponding handling process |
| `nodeId` | Bind current document generation node | Used to locate specific links in the workflow, facilitating subsequent verification and traceability |
| Branch Judgment Condition | Match by document type | Corresponds to the document template requirements of different stages in petition handling, accurately calling corresponding generation rules |

## Three Common Misconfigurations
- Phenomenon: Multi-round conversations cannot retain context after a text content extraction node is configured in the workflow. Cause: The conversation history bound to `variables` is not correctly passed to subsequent nodes, so the context only retains single-round request data.
- Phenomenon: No latest petition data is pulled after the workflow is triggered. Cause: The scheduled trigger interval is set too long, not matching the daily update rhythm of petition data, leading to data lag.
- Phenomenon: The branch judgment node fails to correctly match the document type. Cause: Corresponding judgment conditions are not configured according to the handling stage of the petition case, causing the generated documents to not match the handling link.

## How to Verify Successful Configuration
- Trigger a test petition case request, check the input and output logs of workflow nodes to confirm that the case ID bound to `variables` is correctly passed.
- Initiate two consecutive petition request rounds, check whether the workflow retains the handling milestone information from the previous round to verify normal context transfer.
- Trigger the scheduled pulling task, check whether the pulled document types correspond to the expected petition handling stages.
- Check the running logs of the text content extraction node to confirm that the number of extracted chat records meets the configured requirements.

The values provided here are common starting points and should be evaluated against the reader's own samples.
