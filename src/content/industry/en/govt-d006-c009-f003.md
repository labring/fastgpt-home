# Document and Material Drafting for Public Data Catalogs and Open Data: Multi-turn Dialogue and Prompt Engineering

## What Data Belongs to This Category
This category of data originates primarily from local public data open platforms, integrated big data platforms, departmental business databases, and electronic certificate repositories. Core documents include public data resource catalogs, data open lists, data item descriptions, desensitization rules, interface documentation, and update frequency descriptions.
Data updates follow a monthly schedule. Most document structures include fields such as data item identifiers, open permissions, desensitization requirements, interface addresses, and update cycles. These fields must fully cover the structured attributes and authorization boundaries of available open data assets.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
The monthly update requirement means multi-turn dialogue workflows must support regular synchronization of the latest data source content. This prevents document generation based on outdated data.
The combination of multiple document types and structured fields requires prompts to clearly distinguish processing logic for different documents, such as public data resource catalogs and desensitization rules. This avoids field confusion.
In scenarios with data sources from multiple departments, multi-turn dialogue must gradually guide clarification of data item ownership and open permissions. This ensures generated content matches actual data.
Prompt engineering must also strictly restrict data leakage risks and catalog consistency, to avoid negative outcomes from errors.

## Configuration Setup
This configuration uses FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Maximum context length | 8000–12000 characters | Covers the total length of multiple monthly public data documents, and avoids truncation of critical data items, desensitization rules, and interface addresses |
| `variables` binding scope | Bind only the departmental data item list for the current session | Isolates public data assets from different data-providing departments, prevents cross-departmental data confusion, and supports referencing multi-turn dialogue context |
| `messages` history turn limit | First 10 dialogue turns | Controls context token consumption, while retaining sufficient multi-turn sorting logic to clarify data item ownership and open conditions |
| `chatId` session isolation rule | Divide sessions by data-providing department | Ensures public data catalog generation workflows for different departments are independent, and prevents data cross-use |
| Prompt template switching trigger | Match by document type | Distinguishes generation logic for different documents such as public data resource catalogs and interface documentation, and reuses standardized reference templates |

## Three Common Errors
- Generated public data catalogs fail to reference preset desensitization rule templates. This happens when the prompt template is not correctly bound, so standardized reference logic cannot be reused.
- Multi-turn dialogue token consumption exceeds the platform limit, causing session interruption. This occurs when the `messages` history turn limit is not set, and context token isolation is not enabled. Cross-session token statistics are not isolated in this case.
- Departmental business database export files cannot be uploaded to supplement data items. This happens when the file upload permission for the dialogue interface is not configured, so local data source content cannot be imported.

## How to Verify Correct Configuration
- Manually trigger a public data resource catalog generation, and confirm the generated content only includes data items for the currently bound department.
- Check the session context length to confirm it stays within the preset maximum context length limit.
- Generate a desensitization rule document, and verify it includes clear desensitization processing requirements, and does not directly output raw data.
- Switch the `chatId` for different departments, and confirm content generated in different sessions is independent with no data cross-use.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
