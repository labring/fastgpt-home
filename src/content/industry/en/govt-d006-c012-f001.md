# Document and Material Drafting for Elderly Care Service Institution Supervision: HTTP Interfaces and External Systems

## What the data for this category looks like
This category of data typically comes from elderly care service information platforms, civil affairs statistics systems, fire safety inspection records, and institution operation ledgers. Daily generated documents include filing materials, operation subsidy applications, service quality inspection forms, safety hazard rectification ledgers, and elderly admission files. The data update cycle is monthly. Document fields usually cover basic institution information, number of beds, inspection results, rectification status, and other details. Some documents need to be associated with specific care staff and elderly archive information. Field units mostly follow standard civil affairs supervision formats, such as beds (units), inspection dates (year-month-day), and similar general formats.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Since data sources are scattered and the update cycle is monthly, HTTP interface calls must adapt to low-frequency batch acquisition scenarios to avoid occupying system resources with high-frequency requests. Documents need to be associated with multiple types of business data, so interface responses must include complete fields such as basic institution information, bed data, and inspection records. Otherwise, compliant filling of documents cannot be completed. There are format differences between data from different sources, so unified field mapping rules must be established during interface docking to ensure that incoming business data matches document template fields. At the same time, errors in supervision-related documents may lead to compliance risks. Interface call success rate and data verification mechanisms must be included as key configuration items.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer supervision platform exclusive API key` | Used for identity verification when connecting to external systems such as elderly care service information platforms, complies with general external interface authentication standards |
| Interface timeout period | `600 seconds` | Needs to batch acquire multiple types of monthly aggregated business data; a longer timeout period can prevent request interruptions caused by large data volumes |
| `responseData` | `Return only the three core fields of filing materials, operation data, and inspection records` | Reduces invalid data transmission, improves the efficiency of interface calls and document generation, complies with the external interface configuration specifications of FastGPT v4.17.0 |
| `variables` | `Map the institution name and number of beds returned by the interface to document template variables` | Ensures that the business data filled in the template fully matches the supervision data returned by the external system |
| Retry trigger rule | `Status code is 5xx or response timeout` | Automatically triggers retries for temporary external system failures or network fluctuations to improve call success rate |

## Three common mistakes
- An external supervision interface call returns 404 body not found. The cause is that the `Authorization` parameter is not configured correctly, or the bound API key does not match the permissions of the target platform.
- Generated supervision documents are missing some business data. The cause is that the field mapping rule for `variables` is not set correctly, resulting in the fields returned by the interface not corresponding to the template variables.
- The external interface callback does not return complete business data fields. The cause is that all required fields are not retained in the `responseData` configuration, and only simplified core data is returned, leading to missing information.

## How to confirm the configuration is complete
- Manually trigger an interface call, and check whether the returned `responseData` includes required fields such as filing materials and operation data.
- Check whether the format of the `Authorization` parameter complies with the Bearer token specification, and confirm that identity verification is effective through an interface authentication test.
- Generate a test supervision document, and verify whether the filled business data matches the content returned by the external system.
- Simulate an interface timeout or 5xx status code, and confirm whether the system automatically triggers the retry mechanism.
