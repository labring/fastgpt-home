# Document and Material Drafting for Internal Control Evaluation, Audit and Rectification: HTTP Interfaces and External Systems

## What data falls under this category
Data sources for this category include enterprise internal control systems, ERP, financial sharing systems, audit management systems, and procurement contract project systems. Update frequency is annual.
Daily produced documents include internal control self-assessment reports, audit notices, audit working papers, issue lists, rectification ledgers, and rectification closure certificates. Core fields include business sample voucher number, audit issue description, rectification responsible person, rectification completion deadline, and closure voucher number, among others.
Core time-consuming steps include extracting business samples and vouchers, formulating audit issues and rectification requirements, and tracking rectification evidence and closure processes. This category focuses on issue discovery and rectification closure, with an emphasis on post-event inspection and evidence sampling.

## How do these characteristics impose constraints on HTTP interfaces and external systems
Multi-source data integration requires interfaces to support authentication and data format adaptation for different systems, to prevent data pull failures caused by system compatibility issues. The annual low-frequency update cycle means interfaces do not need high-frequency calls, but single pull data volume is large, so pagination or batch pull mechanisms must be supported.
Core time-consuming steps involve extracting structured business data. Fields returned by interfaces must strictly match required fields of document templates, to reduce subsequent manual sorting costs. At the same time, error consequences include regulatory notifications and liability investigation, so interfaces must have reliable retry mechanisms and exception alert capabilities.

## Configuration settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `Authorization` | `Bearer {service account token issued by the enterprise internal system}` | External business systems must verify caller identity via authentication to prevent data leaks or pull failures caused by unauthorized access |
| Timeout configuration | `600 seconds` | Audit data pull involves cross-system interactions including voucher extraction and ledger query, which take a long time. Short timeouts will cause data pull interruptions |
| `variables` | `key-value pairs containing internal control system ID and audit cycle range` | Pass business context parameters to ensure data pulled by interfaces matches the current audit task scope |
| `responseData` | `only return structured fields for issue lists and rectification ledgers` | Reduce invalid data transmission volume, adapt to document drafting field requirements, and avoid redundant data interfering with subsequent generation processes |
| Batch pull limit | `top 50 entries` | Pulling too much data at once increases interface response time. Setting a reasonable limit balances data completeness and transmission efficiency |
| Retry count | `3 times` | Respond to network fluctuations or temporary system failures, and avoid process interruptions caused by single call failures |

## Three common configuration mistakes
- Phenomenon: Request timeout, returns status code 504 or the interface prompts "request timeout". Cause: Did not adjust timeout configuration for the scenario of pulling audit data across multiple systems, and used generic short timeout settings instead.
- Phenomenon: `responseData` returns missing fields, resulting in generated rectification ledgers lacking closure certificate associated fields. Cause: Did not specify required core business fields to return in interface configuration, and default pulled redundant data or missed required items.
- Phenomenon: `variables` passed parameter format is incorrect, resulting in pulled audit cycle range not matching, and generated audit notice times have deviations. Cause: Did not perform format verification on context parameters passed by external systems, and used them directly for interface calls.

## How to confirm configuration is complete
- Call the configured HTTP interface, check if `Authorization` authentication passes, and returns correct business data list.
- Check the `responseData` field returned by the interface, confirm it includes all core fields required for issue lists and rectification ledgers.
- Simulate 3 consecutive batch requests, verify that requests under the timeout configuration can complete normally, with no frequent timeout errors.
- Verify business parameters passed via `variables`, confirm that the pulled data range matches the preset audit cycle.

The values provided are common starting points and should be measured against the reader's own samples.
