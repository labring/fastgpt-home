# Document and Material Drafting for Medical Insurance Fund Supervision and Audit: Deployment and Upgrade

## Data Profile for This Category
Data sources for this category include the medical insurance intelligent monitoring system, fund supervision rule base, medical insurance settlement data, drug and consumable traceability codes, and complaint clues. The update frequency is monthly.
Daily produced documents include audit notices, inspection work working papers, suspicious point lists, interview records, handling decision letters, and rectification reports. Document fields cover supervision object information, violation descriptions, evidence lists, handling opinions, and other content. There is no unified fixed standard unit. Configurations must align with the specific requirements of the target supervision scenario.

## Constraints Imposed by These Characteristics on Deployment and Upgrade
The monthly updated supervision rule base and settlement data require a stable batch data synchronization link during deployment to avoid single synchronization overload.
Field differences across multiple document types require retaining a custom editing entry for document templates during upgrades to adapt to format requirements for different documents.
The time-consuming process of screening suspicious points from massive settlement data requires reserving sufficient computing resources during deployment to support fast retrieval and comparison.
Errors may lead to fund losses and administrative penalties. An operation log and rollback mechanism must be configured during upgrades to ensure traceability of changes.

## Configuration Settings
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | Point to a dedicated instance storing medical insurance settlement data and supervision rule base | Ensure isolation and access stability of supervision data, avoid conflicts with other business data |
| `REDIS_URL` | Configure as a dedicated cache instance with `16384 MB` memory | Support high-frequency suspicious point retrieval and rule matching, reduce database query pressure |
| `STORAGE_S3_ENDPOINT` | Bind to a compliant local storage or compliant cloud storage endpoint | Meet storage compliance requirements for medical insurance data, ensure secure storage of documents and evidence materials |
| `DB_MAX_LINK` | Set to `20–30 connections` | Adapt to concurrency requirements for monthly batch data synchronization, avoid exhausting database connections |
| `FE_DOMAIN` | Configure as the dedicated domain name of the internal supervision system | Limit access scope, ensure operational safety of the supervision scenario |
| `ROOT_KEY` | Generate a random 32-bit secure string | Ensure permission safety of platform background management operations, prevent unauthorized access |

## Three Common Mistakes
- After an upgrade, the plugin editing interface always displays an unsaved status, and no changes take effect after clicking save. The cause is that `FILE_TOKEN_KEY` was not correctly configured during deployment, preventing the plugin save status from synchronizing to the cache.
- An error indicating the rehype-raw module cannot be found is prompted when building the deployment image, even after executing the installation command. The cause is failure to correctly mount the dependency cache directory during deployment image building, causing npm-installed modules to not be recognized or loaded by the platform.
- Accessing the platform with a low-version browser, or continuous container restarts preventing normal access. The respective causes are that the browser version does not meet compatibility requirements, and incorrect `MONGODB_URI` configuration leading to database connection failure.

## How to Verify Successful Configuration
- Run a test task for batch synchronization of monthly medical insurance settlement data, and confirm that the database connection count does not exceed the set value of `DB_MAX_LINK`.
- Try to create and save an audit notice template, and confirm that the interface no longer displays the unsaved prompt, and the template can be exported normally.
- Access the domain name corresponding to `FE_DOMAIN`, and confirm that the platform interface loads normally with no cross-domain request errors.
- Upload a rectification report to the storage endpoint, and confirm that the file can be read and downloaded normally.
