# Document and Material Drafting for Medical Insurance Expense Settlement Audit: Deployment and Upgrade

## What the data for this category looks like
The data processed by this category comes from the national medical security information platform, hospital HIS systems and medical insurance docking interfaces, the medical insurance catalog and coding database, and the cross-provincial medical settlement platform. The update frequency is daily. Daily processed documents include medical insurance settlement lists, expense details, medical record homepages, prescriptions, rejection lists, and settlement reconciliation statements. Data fields cover diagnosis and treatment project codes, drug and consumable codes, expense amounts, insured person identity identifiers, settlement status, and more. Each document contains multiple structured and unstructured contents, and official unified codes are required for matching and verification.

## What constraints these characteristics impose on deployment and upgrades
The daily data update requirement means scheduled synchronization tasks must be configured during deployment to ensure the timeliness of medical insurance catalog codes and business data. The need to match codes across multiple types of structured documents requires pre-integrating the official medical insurance catalog and coding database during deployment, to avoid lacking matching basis after parsing. When batch processing settlement lists and rejection lists, sufficient file parsing and storage resources must be reserved to prevent task interruptions from excessive data volume. Data verification accuracy directly affects fund payments and insured persons’ rights and interests. The upgrade process must retain the old version’s data verification logic as a backup, to avoid errors caused by configuration changes.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `10–15 connections` | This category processes large daily business data volumes, requiring a reasonable load on the database connection pool to avoid connection exhaustion |
| `REDIS_URL` | `Local Redis node, timeout set to 30 seconds` | Used to cache medical insurance catalog codes and high-frequency settlement data, reducing the frequency of repeated calls to medical insurance interfaces |
| `STORAGE_S3_ENDPOINT` | Connect to hospital intranet compliant storage nodes | Store sensitive medical data such as medical insurance settlement lists and rejection lists, in compliance with government data storage specifications |
| `FILE_TOKEN_KEY` | Use the same AES encryption key as the medical insurance interface | Verify the legitimacy of uploaded medical documents to prevent unauthorized files from accessing the system |
| `PG_URL` | Deploy an independent PostgreSQL instance to store structured settlement data | Separate from unstructured document storage, enabling precise query and statistics by medical insurance coding dimension |
| `ROOT_KEY` | Configure a key accessible only from internal network segments | Restrict access to background management interfaces to ensure the security of government data |

## Three common mistakes
- A 413 error is returned when uploading a medical insurance settlement list. The cause is that the maximum upload file size limit of the container was not adjusted in Docker deployment mode, and the single-file volume limit of medical insurance settlement lists was not adapted.
- After upgrading to FastGPT v4.17.0, the medical insurance catalog code matching task fails. The cause is that the database connection pool configuration was not updated synchronously, and the old version of the `DB_MAX_LINK` parameter cannot adapt to the new batch data processing logic.
- A connection exception occurs when calling the medical insurance interface. The cause is that `REDIS_URL` was not configured as a cache node compatible with the medical insurance platform, causing the identity verification token to fail to generate normally.

## How to confirm the configuration is complete
- Upload a standard medical insurance settlement list, confirm the file parses without errors and the diagnosis and treatment project code field is extracted correctly.
- Check database connection pool monitoring to confirm active connections stay within the `10–15 connections` range.
- Call the medical insurance catalog code matching interface to verify cache data updates occur at the daily synchronization frequency.
- Check background management interface access logs to confirm only internal network segments can authenticate using the `ROOT_KEY`.

The values provided are common starting points and should be measured against the reader's own samples.
