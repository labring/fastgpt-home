# Centralized Treasury Payment and Reimbursement Review: Document and Material Drafting via Multi-turn Dialogue and Prompt Engineering

This document outlines configuration, constraints, and implementation key points for multi-turn dialogue and prompt engineering for this specific scenario, based on FastGPT v4.17.0.

## Data Profile for This Category
Data for this category comes from centralized treasury payment systems, unified budget management systems, electronic invoice platforms, and contract management systems. Updates occur daily.
Daily processed documents include payment applications, fund use plans, invoices, contracts, acceptance receipts, reimbursement approval forms, and payment vouchers. A single business links to multiple types of associated documents.
Data fields include budget indicator codes, economic classification codes, payment amounts, ticket numbers, contract numbers, and other relevant fields. All data supports compliance review for a single fund payment, with no additional statistical fields.

## Constraints for Multi-turn Dialogue and Prompt Engineering Links
Data from multiple systems with daily updates requires real-time synchronization of the latest budget indicator, ticket status, and other information in multi-turn dialogue. This prevents audit errors caused by expired data.
The structure where a single business uses multiple associated documents requires prompts to clearly identify all linked materials for the current business. This prevents missed audit steps.
Errors can lead to fund returns, incorrect payments, or violations of financial discipline. Multi-turn dialogue must gradually verify key fields to avoid single-judgment mistakes.
This category focuses on daily payment execution. Dialogue must focus on a single business, and does not need to handle cross-budget-cycle batch data. Context scope must be strictly limited to the current business.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Maximum context | 8000–12000 characters | Total length of documents related to a single payment (such as payment applications and reimbursement approval forms) is usually several thousand characters. This setting ensures full coverage of core review materials |
| Question optimization | Enabled | Converts colloquial questions from financial personnel into standardized treasury payment review queries, improving system data retrieval accuracy |
| Single search limit | Top 3 results | Treasury payment review only needs to match system data for the current single business. Excessive search results will interfere with compliance verification |
| Conversation ID (`chatId`) | Bound to the single payment business number | Ensures multi-turn dialogue context is only linked to the current business, avoiding confusion across different orders |
| Context messages (`messages`) | Only retain interactions and associated data for the current business | Prevents irrelevant historical dialogue from interfering with compliance judgments for the current review |
| Custom variables (`variables`) | Inject current budget unit code and economic classification code | Lets the model directly use standard fields from the business system, reducing manual input errors |

## Three Common Misconfigurations
- When the knowledge base retrieval returns system documents in image format, the model prompts that no answer was found. Cause: No parsing process for image content is configured. Only text-based knowledge base retrieval is supported, and key information such as payment vouchers and contracts in images cannot be extracted.
- Sending multiple reimbursement review requests consecutively in a short period causes subsequent requests to wait for the previous generation to complete. Cause: `chatId` is not used to bind the single business number. The system groups all requests into the same dialogue context, resulting in sequential request execution and no support for concurrent processing.
- An error prompt "No permission to operate this conversation record" appears when operating the review dialogue. Cause: Conversation permissions are not bound to the business jurisdiction scope of the current review post. Only conversation data for the corresponding budget unit is allowed to be accessed, and operations beyond the permission scope are intercepted.

## How to Verify Successful Configuration
- A query for a single payment review is initiated. The model’s retrieval results are checked to confirm they only link to data such as budget indicators and contracts for the current business, with no irrelevant content.
- Two review requests for different businesses are submitted at the same time. The contexts of the two conversations are confirmed to be independent, with no data confusion.
- The permission verification logic is triggered. An account without corresponding business permissions is used to access the conversation, and a permission interception prompt is confirmed to appear.
- A reimbursement voucher in image format is uploaded. The model is confirmed to correctly parse key information in the image, without prompting that no answer was found.

The values listed above are common starting points, and should be evaluated against applicable samples.
