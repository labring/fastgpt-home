# Document and Material Drafting for Centralized Treasury Payment and Reimbursement Audit: Tool Calling and Plugins

## What this category of data looks like
Daily documents for this category include payment applications, fund use plans, invoices, contracts, acceptance receipts, reimbursement approval forms, payment vouchers, and more. Core fields cover budget indicators, economic classification, fund amount, contract number, and other relevant items. Data sources include centralized treasury payment systems, unified budget management systems, electronic invoice platforms, and contract management systems. Update frequency is daily. A single payment audit requires linking the verification chain of multiple document types, involving heterogeneous data integration across different systems, and must strictly comply with compliance requirements.

## What constraints these characteristics impose on the tool calling and plugins link
Data for this category comes from multiple heterogeneous systems. Tool calling or plugins must connect interfaces of different data sources to ensure accurate acquisition of data such as budget indicators and invoice information. There are various document types and complex associated verification chains. Tool calling must adapt to field parsing rules for different documents. Data updates daily, so tool calling synchronization frequency must match business rhythms to avoid using expired data. Compliance requirements for single payments are strict. Tool calling must be triggered forcibly to ensure every audit undergoes external data verification. It must also support historical data traceback for return and correction scenarios. Additionally, it must support connecting MCP plugins in workflows to adapt to daily audit process nodes.

## How to set configurations
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `required` | Forcibly trigger tool calling to ensure every payment audit checks external system data and meets compliance requirements |
| MCP Client Access Permissions | Grant only read-only access to connected systems | Only need to read data from centralized treasury payment systems and electronic invoice platforms to avoid unauthorized operations |
| Workflow Tool Calling Trigger Timing | Trigger at document submission node | Matches the daily audit process of budget unit finance, starts tool calling only when receiving a payment application or reimbursement approval form |
| Single Tool Call Return Result Count | `Top 3` | A single payment audit only corresponds to a single contract and invoice data. Excessive results will interfere with compliance verification |
| Tool Call Timeout Setting | `600 seconds` | Centralized treasury payment system interface responses typically take under 5 minutes, ensure sufficient wait time to obtain complete data |
| `functionCall` | `Enabled` | Map fields returned by external systems, such as budget indicators and invoice amounts, to drafted payment vouchers and reimbursement forms to ensure accurate document content |

## Three common misconfigurations
- Calling a configured API returns a permission denied error. Cause: No read-only access permission for the corresponding system is configured for the MCP client, or the caller address is not added to the FastGPT API access whitelist.
- External MCP plugins cannot be connected in the workflow. Cause: The MCP function switch for FastGPT workflows is not enabled, or the interface address and port configured for the plugin do not have network access open.
- Tool calling returns empty fields. Cause: External system document fields are not correctly mapped to the drafted document template, or the data update frequency does not match the daily update requirement, resulting in expired data being read.

## How to confirm the configuration is complete
- Submit a test payment application, check whether the workflow triggers tool calling as configured.
- View tool calling logs to confirm returned data comes from specified data sources such as centralized treasury payment systems and electronic invoice platforms.
- Call the test API to confirm no permission-related errors are returned, which matches the configured access rules.
- Check automatically generated documents to confirm necessary fields such as budget indicators and invoice amounts obtained from external tools have been filled in.
