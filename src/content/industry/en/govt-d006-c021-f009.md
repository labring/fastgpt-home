# Document and Material Drafting for Centralized Treasury Payment and Reimbursement Audit: Model Access and Configuration

## What the data for this category looks like
Core data for this category comes from centralized treasury payment systems, unified budget management systems, electronic invoice platforms, and contract management systems. The update frequency is daily. Daily processed documents and materials include payment applications, fund use plans, invoices, contracts, acceptance receipts, reimbursement approval forms, and payment vouchers. All documents include standardized fields such as budget indicator code, economic classification code, payment amount, and approval node status. They must also be linked to unique identifiers from corresponding business systems to complete full-link verification.

## What constraints these characteristics impose on model access and configuration
Data for this category is scattered across multiple business systems. When accessing models, adapt to multi-source data formats and permission requirements. Configure appropriate context windows to carry complete document content across system links. Daily high-frequency business data requires model call latency to match daily audit rhythms, to avoid slowing overall processes. Document fields are standardized but business links are complex. Limit the context length processed per session to prevent redundant information from interfering with accurate matching of budget indicators and economic classifications. Compliance requirements for single payments are strict. Adjust model generation rigor parameters to reduce error risks, such as payment returns or fund misallocation.

## How to set configurations
| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to total document length for cross-system links in this category, avoids truncating key information including budget indicators and approval chains |
| `maxTokens` | 2000–3000 token | Controls generated output length for single audit documents, matches information density requirements for single payment audits |
| `temperature` | 0.1–0.3 | Reduces generation randomness, ensures consistency of compliance statements, meets rigor requirements for fiscal audits |
| `AIPROXY_API_ENDPOINT` | Locally deployed FastGPT proxy address, port set to 11434 | Adapts to local deployment business data security requirements, prevents sensitive fiscal data from being sent externally |
| `quoteMaxToken` | 1000–1500 token | Limits length of referenced original document fragments, focuses core invoice and contract verification information |
| `vision` | Disabled | Core processing for this category is text-based documents, visual model capabilities are not temporarily required, reduces call complexity |

## Three common mistakes
- Phenomenon: Returns 404 no body error when calling locally deployed models. Cause: `AIPROXY_API_ENDPOINT` parameter is not configured correctly, proxy address points to incorrect model service port, or local model service is not started.
- Phenomenon: Generated audit documents have errors where budget indicators do not match actual payment amounts. Cause: `maxContext` parameter value is too small, truncating key context fragments containing budget indicators.
- Phenomenon: Unmarshal_resp error occurs during speech-to-text processing. Cause: `vision` configuration is not disabled, model attempts to parse speech-to-text text that is not image input, causing response format parsing failure.

## How to confirm configuration is complete
- Verify the `AIPROXY_API_TOKEN` parameter matches the key of the local model service, and confirm the key field in the FastGPT v4.17.0 configuration page.
- Trigger a document drafting test for a single payment application, and confirm the generated content includes complete core fields such as budget indicators and economic classifications.
- Review model call logs to confirm no truncation prompt appears in the context window, and that the response format meets expectations.
- Simulate a multi-document link scenario, and confirm the configured context carrying capacity covers all linked contract and invoice information.
