# Document and Material Drafting for Land Use Rights, Mining Rights, and State-owned Property Transactions: HTTP Interfaces and External Systems

## What the data for this category looks like
The core data for this category comes from the national public resource trading platform, natural resource trading systems, property right exchange systems, and state-owned asset supervision systems, and is updated daily. Daily generated documents include transfer announcements, trading guidelines, bid application forms, margin vouchers, transaction confirmation letters, listing result announcements, property right transfer prospectuses, and similar materials. The structure centers on trading subject ownership, valuation, margin rules, and transaction processes. Most data fields include subject numbers, ownership status, transaction amounts, public notice periods, and similar details. Units mostly use industry standard units such as square meters, ten thousand yuan, and natural days.

## What constraints do these characteristics impose on the HTTP Interfaces and External Systems link
The multi-system nature of data sources requires interfaces to adapt to different authentication rules and field formats. The daily update frequency requires call frequency to match the system synchronization rhythm. The diversity of document structures means interfaces must support flexible field extraction configurations to avoid hard-coded fixed templates. The sensitivity of ownership information requires strict verification of authentication parameters. The severity of error consequences requires that interface calls be configured with complete failure retry and alert mechanisms.

## How to set configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {API key assigned by the platform}` | Most public resource platforms connected to this category use Bearer token authentication |
| `variables` | Pass subject ID, transaction type, public notice period | Core documents for this category are all generated based on these fields, which can reduce redundant data transmission |
| `responseData` | Extract subject ownership, margin amount, transaction status | Core verification links for this category rely on these fields, which can simplify subsequent processing logic |
| Timeout setting | 300-600 seconds | Retrieving ownership data across systems requires waiting for approval processes; this range covers most normal response durations |
| Retry count | 2-3 times | Public resource platform interfaces have occasional fluctuations; this count can reduce the probability of call failures |
| Context window | First 1000-1500 characters | The effective information length of core trading documents for this category mostly falls within this range |

## Three common misconfigurations
- Symptom: Interface calls return the `400 invalid image` error. Cause: Failed to properly filter unstructured ownership scan files, or the passed image format does not meet the requirements of the connected platform.
- Symptom: The HTTP module runs with an error, and logs show core fields are empty. Cause: Did not configure the required subject ID parameter in `variables`, causing the interface to fail to locate the corresponding transaction data.
- Symptom: Only the first conversation node can be triggered after connecting to the external system. Cause: Did not properly configure the field mapping rules for `responseData`, causing subsequent nodes to fail to obtain valid context information.

## How to confirm the configuration is complete
- Call the test interface, check that the `Authorization` authentication header is correctly included, and confirm that the return status code is 200.
- View the fields extracted by `responseData`, and confirm that they include core transaction information such as subject ownership and margin amount.
- Simulate batch calls to verify whether the timeout setting and retry count can cover occasional interface fluctuations.
- Connect to real transaction data and check whether the generated document fields match the content returned by the system.
