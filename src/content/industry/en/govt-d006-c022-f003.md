# Document and Material Drafting for Land Use Rights, Mining Rights, and State-Owned Property Transactions: Multi-Turn Dialogue and Prompts

## What this category of data looks like
This category of data comes from the national public resource trading platform, natural resource trading systems, property right exchange systems, and state-owned assets supervision systems. The update frequency is daily. Daily generated documents include transfer announcements, trading guidelines, bid application forms, security deposit vouchers, transaction confirmation letters, listing result announcements, and property right transfer specifications. Most document structures include transaction subject ownership information, trading process nodes, amounts and qualification requirements, and most fields are standardized such as ownership numbers, transaction base prices, and bid qualification requirements.

## What constraints do these characteristics impose on the "multi-turn dialogue and prompts" link
Data for this category is updated daily. The multi-turn dialogue link must ensure that the latest ownership and trading rule data is called, to avoid generating documents using expired information. The standardized document structure requires prompts to clearly correspond to the exclusive fields of different documents. For example, a transfer announcement must include subject location and transfer conditions, and a transaction confirmation letter must match the subject information from the bid application. The error tolerance rate for verifying ownership and transaction amounts is very low. Multi-turn dialogue must gradually guide users to supplement subject details to reduce deviations in generated content. At the same time, the standardization of trading processes requires prompts to fix the order of nodes, to avoid missing key links such as listing, bidding, and public announcement.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Pass subject type, trading platform ID | Match the query scope of the corresponding data source, accurately call the ownership data of the subject |
| `messages` | Split dialogue turns by trading process nodes | Focus on only one document link per turn, avoid prompt length causing model confusion |
| Maximum context length | First 20 turns of dialogue context | Documents in this category need to associate multiple rounds of trading applications and review information, retain sufficient context to ensure logical coherence |
| Single recall result count | Top 6 matching results | Data in this category has a high degree of standardization, a small number of accurate results can cover the ownership and rule information required for documents |
| Question optimization | Enabled | Automatically convert users' colloquial requests into standardized document generation instructions, adapting to the fixed field requirements of this category |
| Timeout threshold | 300 seconds | Need to call multiple system data sources to query ownership information, reserve sufficient interface response time |

## Three Common Mistakes
- Uncaught exceptions triggered by dialogue components: Common manifestation is an uncaught exception prompt popping up on the interface. The cause is that the exclusive data source path of this category is not correctly bound in the configuration file, resulting in failure when calling ownership data.
- Generated documents not associated with knowledge base content: Common manifestation is that the reply does not reference trading rules from the knowledge base. The cause is that the correct subject type parameter is not passed in `variables`, causing the model to not trigger the knowledge base recall logic.
- Frequent dialogue page crashes: Common manifestation is dialogue page loading failure or forced closure in FastGPT v4.17.0. The cause is that the single recall result count is not limited, and excessive redundant data causes context overflow, exceeding the system processing limit.

## How to Confirm the Configuration is Correct
- Initiate a dialogue to generate a bid application form, check whether the generated content includes the standardized ownership fields of the subject, and confirm that the correct data source is called.
- View the dialogue log, confirm that the `messages` parameter splits turns by trading process, with no mixed instructions across links.
- Test delayed data source call scenarios, confirm that the system completes the response within the 300-second threshold, and no uncaught exceptions are triggered.
- Verify the question optimization function: input a colloquial request such as "Help me write a bid application for XX plot", confirm that the generated content conforms to the standardized document format.
