# Document and Material Drafting for Land Use Rights, Mining Rights and State-owned Property Transactions: Workflow Orchestration

## What the data for this use case looks like
Data for this use case mainly comes from national public resource trading platforms, natural resource trading systems, property right exchange systems, and state-owned assets supervision systems, with a daily update frequency. Commonly involved documents include transfer announcements, trading notices, bid applications, margin vouchers, transaction confirmation letters, listing result announcements, property right transfer descriptions, and more. Document fields typically include transaction subject ownership information, restriction conditions, valuation amounts, margin standards, transaction subject information, and similar details. Some documents must match unified regulatory format specifications.

## What constraints do these characteristics impose on the "workflow orchestration" link
Data sources for this use case are scattered and updated daily. Workflows must support cross-system scheduled data pulling to avoid delays and errors from manual synchronization. There are many document types with differing fields, so unified field mapping rules must be configured in orchestration to ensure document data from different sources can be correctly identified and integrated. Information such as transaction subject ownership and valuation directly affects document legality, so a pre-check link must be added to the workflow to prevent erroneous data from entering the drafting process. Additionally, since errors may impact state-owned asset rights and interests, a failure fallback and alert mechanism must be configured to ensure abnormal situations can be traced and addressed.

## How to configure the workflow
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Include three core fields: transaction subject ownership, margin amount, and transaction time | Documents in this use case require core matching of ownership, fund, and time-related fields to ensure accurate and compliant drafting content |
| `nodeId` | Bind cross-system data pulling nodes and document generation nodes | Enable automatic flow of data pulling results to the drafting link, reducing manual intervention |
| Scheduled trigger settings | Execute during the daily 2:00-4:00 AM interval | Avoid peak business hours and reduce system resource consumption |
| Pre-check configuration | Trigger condition: pre-node returns non-empty data | Avoid invalid drafting processes triggered by empty data |
| Failure handling configuration | Retry 2 times, interval 60 seconds, push alerts to specified nodes after failure | Respond to temporary system fluctuations and notify operations staff in a timely manner |
| Output format configuration | Match the unified template of the national public resource trading platform | Ensure generated documents meet regulatory requirements |

## Three common mistakes
- Phenomenon: After upgrading FastGPT, importing an old version workflow displays `nodeId` binding abnormalities, and node configuration is lost. Reason: Node ID mapping rules have changed between versions, and cross-system data pulling and generation nodes were not rebound.
- Phenomenon: The output of the HTTP request node is not displayed in conversation results, and returned fields are empty. Reason: No mapping rule for the output field was configured in `variables`, so the generated result was not included in the context output.
- Phenomenon: The pre-check link frequently triggers errors, returning field mismatch prompts. Reason: No dedicated check rules were configured for the ownership and valuation fields of this use case, and general check logic was used by mistake.

## How to confirm the configuration is complete
- Manually trigger the workflow once, check if the pulled data source includes the day's updated transaction subject information, and verify that the fields in `variables` match the actual data.
- View the workflow's failure logs to confirm that the retry and alert mechanism can trigger normally during simulated exceptions.
- Export the generated test document and check if it matches the regulatory required format and field completeness.
- Verify that the `nodeId` binding of the cross-system node is correct, ensuring data can automatically flow from the pulling node to the generation node.
