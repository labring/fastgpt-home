# Document and Material Drafting for Work Safety Hazard Inspection and Governance: Deployment and Upgrade

## What the data for this category looks like
This category's data originates from work safety supervision systems, enterprise hazard self-inspection systems, law enforcement inspection records, and accident statistics systems. It routinely generates documents including hazard inspection lists, hazard management ledgers, rectification notices, review records, and major hazard suspension and supervision orders. Data updates occur daily. Core fields include hazard ID, hazard type, rectification responsible person, rectification deadline, review result, and more. Individual document lengths vary widely, from hundreds to thousands of characters, and require association with basic information of corresponding production and business entities.

## What constraints these characteristics impose during deployment and upgrade
Multi-source data with high daily update frequency requires stable database connection configuration during deployment, to avoid data synchronization failures from connection interruptions. Mixed storage of multiple document types requires adaptation to file processing logic for different formats. During upgrades, original document field mapping rules must remain compatible. The uniqueness of core business fields requires completing data deduplication configuration during deployment, to prevent duplicate entry of hazard information. Cross-version upgrades must retain the archive path of historical ledgers, to ensure historical data such as review records can be retrieved normally. This content is based on the deployment logic of FastGPT v4.17.0.

## Configuration Settings
These configurations apply to FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Cluster connection address with authentication information, set connection pool timeout to 300 seconds | Adapt to daily high-frequency hazard data writes and queries, prevent business interruptions from connection timeouts |
| `DB_MAX_LINK` | 20–30 | Match concurrent request volumes of daily multi-source data, prevent service lag from exhausted connection slots |
| `REDIS_URL` | Independent cache instance address with password, set key expiration time to 86400 seconds | Cache daily updated hazard judgment standards and entity basic information, reduce database query load |
| `STORAGE_S3_ENDPOINT` | Configure per the object storage service provider of the deployment environment | Adapt to storage needs for multiple document types including rectification notices and review records |
| `ROOT_KEY` | Randomly generated 32-bit string | Used for interface authentication, secure access to internal management interfaces |

## Three Common Misconfigurations
- MongoDB connection failure errors appear several hours after startup. The cause is failure to set a reasonable value for `DB_MAX_LINK`, leading to exhausted connection pools that cannot create new connections, and no automatic reconnection mechanism configured.
- Historical hazard ledgers become unretrievable after cross-version upgrade. The cause is skipping database script execution for intermediate versions, meaning new field mapping rules are not synchronized to the existing database.
- Uploaded rectification notices cannot be parsed normally. The cause is failure to configure the correct key for `FILE_TOKEN_KEY`, resulting in failed file storage authentication and inability to read uploaded document content.

## How to Verify Proper Configuration
- Run the database connection test script to confirm that connection pool counts stay within the configured range, with no persistent errors.
- Import a historical hazard inspection list to verify that data fields are correctly mapped to the system's business fields.
- Trigger a document upload operation to confirm that the generated file link is accessible normally and the content is complete.
- Check the version upgrade log to confirm that all database migration scripts executed successfully with no error messages.

The values provided are common starting points and should be evaluated against the deployment’s own operational samples.
