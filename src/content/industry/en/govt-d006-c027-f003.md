# Document and Material Drafting for Engineering Construction Project Bidding and Tendering: Multi-turn Dialogue and Prompt Words

## What the Data for This Category Looks Like
Core data for this category comes from the national public resource trading platform, local public resource trading platforms, project approval systems, and bidding and tendering supervision systems. The update frequency is daily.

Commonly processed documents include bidding announcements, qualification pre-qualification documents, bidding documents, tender documents, bid evaluation reports, successful bid candidate notices, and successful bid result announcements. These documents contain structured fields such as bid section division, qualification requirements, bill of quantities, and bid evaluation expert performance records. They also include corresponding unstructured text content for notice-type materials.

## Constraints on Multi-turn Dialogue and Prompt Words
Daily data updates require multi-turn dialogue to link to the latest official bidding and tendering data in real time. Expired information must not be used.

Documents include multiple types of professional fields. Prompts must clearly distinguish generation rules for different document types. This ensures output matches the requirements of corresponding links.

The most time-consuming links, such as bid section splitting and bid evaluation record verification, require support for multi-turn step-by-step interaction. This allows gradual confirmation of parameters and verification results.

Error risks must be pre-checked through the dialogue process. This prevents generation of non-compliant document content.

Unlike government procurement scenarios, professional fields such as qualifications, performance records, and bill of quantities must be strictly matched. Prompts must adapt to compliance requirements under the bidding and tendering law framework.

## Configuration Settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum Context Length | 8000–12000 token | Matches the average length of a single core bidding and tendering document. Prevents information loss caused by context truncation. |
| Maximum Single Match Result Count | Top 3 entries | Corresponds to the core entry count for single-type documents such as bid evaluation reports and successful bid notices. Avoids information overload that reduces generation efficiency. |
| Dialogue History Retention Duration | 24 hours | Matches the daily data update frequency. Ensures dialogue uses the latest official trading data from the current day. |
| Variable Binding Parameters | Preset `chatId`, `messages`, `variables` | Supports context transfer and parameter binding for multi-turn dialogue. Adapts to the interaction logic for step-by-step verification of bidding and tendering documents. |
| Knowledge Base Data Source Filter | Restrict to public resource trading platform data sources | Ensures calls use official and compliant bidding and tendering data. Avoids interference from unauthorized information on generation results. |
| Context Validation Switch | Enabled | Performs matching verification between generated document content and knowledge base data. Reduces compliance risks. |

## Three Common Misconfigurations
- Misconfiguration 1: No knowledge base is selected for dialogue after official release, while debug preview operates normally. The interface displays no associated knowledge base when a dialogue is initiated in the official environment. No abnormalities occur during the preview stage. This happens when the knowledge base is not bound to the officially released application node, or the configured data source filter rules do not cover the request sources of the official environment.
- Misconfiguration 2: Multi-turn dialogue context is lost. Previously confirmed parameters such as bid section division and project name are not retained during cross-turn calls. This occurs when the `chatId` parameter is not configured correctly for transfer, or the dialogue history cleanup rule has an excessively short duration.
- Misconfiguration 3: Generated documents contain non-compliant fields. The generated bidding documents include bill of quantities entries or qualification requirements that do not appear in the bound knowledge base. This happens when the prompt does not explicitly limit use of only structured data within the bound knowledge base, or the context validation switch is not enabled.

## How to Verify Proper Configuration
- Initiate a test dialogue, input "Generate a bidding announcement for a certain project", and check if the returned result only includes official bidding and tendering document content from the bound knowledge base.
- Initiate a cross-turn dialogue: first confirm the bid section division parameters, then request generation of a qualification pre-qualification document for the corresponding bid section, and check if the subsequent dialogue retains the previously confirmed bid section information.
- Check the application logs, and confirm that the `chatId` and `messages` parameters are correctly passed in each round of dialogue.
- Trigger the knowledge base to re-pull the day's data, and verify that the dialogue calls the latest version of the trading data.
