# Document and Material Drafting for Market Entity Registration and Licensing: Workflow Orchestration

## What this category's data looks like
Data for this category comes from the enterprise registration full-process electronic system, national enterprise credit information publicity system, electronic business license system, and residence information database. The update frequency is daily. Commonly processed documents include establishment registration applications, articles of association, shareholder resolutions, residence certifications, business licenses, food business license applications, and more. Document structure is split into two parts: structured application fields and supporting attachments. Structured fields include main entity name, residence address, shareholder identity information, licensing item type, and other items. Attachments are mostly scanned documents or files with electronic signatures.

## What constraints these characteristics impose on workflow orchestration
Daily updated multi-source official data requires workflow configuration of scheduled trigger nodes to pull incremental data daily and avoid duplicate processing. The mixed document structure of structured fields and attachments requires splitting the workflow into two parallel sub-nodes: field extraction and attachment verification, to handle text information and electronic files separately. Differences in fields across application types require configuring branch judgment nodes to match corresponding processing logic. Repeated submission requirements for correction processes require workflow support for loop nodes to handle repeated verification and correction. An exception interception node must also be configured to trigger a rollback or notification link when data does not meet requirements.

| Scheduled trigger cycle | Daily 2:00-4:00 AM | Match the daily update rhythm of official systems, avoid peak business hours |
| Attachment verification timeout | 300 seconds | Adapt to loading and verification duration of electronic signature files |
| Loop termination condition | Triggered by correction completion marker | Adapt to application correction processes with multiple revisions |
| Context window size | 8000-12000 token | Accommodate complete application documents and historical correction records |

## Three Common Misconfigurations
- Workflow runs correctly in preview, but returns an error after publishing the non-login access window. The symptom is that application data cannot be retrieved in non-login scenarios, returning empty results or permission error prompts. The cause is that variable authorization rules for non-login scenarios are not configured. Local permissions used during preview do not take effect after publishing.
- Loop termination condition fails to work properly. The symptom is that the loop cannot recognize the specified termination marker, continuing execution until a timeout is triggered. The cause is that the loop termination condition parameters are not set correctly, and the status field of correction notifications is not associated.
- Tool call parameter binding error. The symptom is that the `q` parameter passed to the tool is not bound to the correct application material field, causing the tool to return results unrelated to the current application. The cause is that specific submitted application content is not accurately bound to tool parameters, only generic query text is passed.

## How to Verify Proper Configuration
- Manually trigger the workflow once, check whether the pulled data matches the daily incremental data from official systems.
- Simulate submission of different types of application documents, confirm that branch judgment nodes correctly match corresponding processing logic.
- Simulate submission of an application requiring correction, confirm that the loop node can trigger repeated verification processes and exit normally after correction is completed.
- Publish the non-login access window, use a test account to submit an application, confirm that the process runs normally without errors.

The values listed above are common starting points. They should be evaluated against the reader's own samples.
