# Document and Material Drafting for Investment Project Approval and Post-Evaluation: HTTP Interfaces and External Systems

## What data for this category includes
Data sources for this category include state-owned assets supervision and administration investment supervision systems, enterprise ERP and project management systems, industry market data, audit and financial statements. The update frequency is quarterly. Daily produced documents include annual investment plans, project proposals, feasibility study reports, due diligence reports, asset evaluation reports, and post-investment evaluation reports. These documents are divided into four parts: basic project information, feasibility analysis, investment decision support materials, and post-evaluation data. Fields include project number, investment amount, construction period, evaluation conclusions, and related units include ten thousand yuan, year, and others.

## What constraints do these characteristics impose on the HTTP interfaces and external systems link
Data sources for this category are scattered, documents are lengthy, and update frequency is fixed, creating multiple constraints for HTTP interface and external system integration. Connect multiple external systems to obtain business data from different dimensions, and `Authorization` parameter verification rules vary across different systems. Split lengthy document content and transmit it in batches to avoid exceeding interface limits in a single request. Configure call cycles reasonably for quarterly updated data to prevent frequent requests from triggering system rate limits. Embed integrity verification for core business fields in the interface call process to prevent missing key information from compromising document quality.

## Configuration Settings

| Configuration Item | Recommended Practice | Rationale |
| ---- | ---- | ---- |
| `Authorization` | Configure according to the authentication rules of the connected system, for example using the Bearer token format | Authentication requirements differ across external systems, and must match the authentication specifications of the corresponding interface |
| Single request text length | 800–1200 characters | Adapts to the text transmission limits of most external interfaces, avoiding request timeouts or truncation |
| `responseData` field filtering rules | Only extract the project number, investment amount, and construction period fields | Focus on core business information required for documents in this category, filtering out redundant data |
| Interface call timeout | 600 seconds | Adapts to the time requirements of lengthy document processing and multi-system data aggregation |
| Failure retry count | No more than 3 times | Addresses temporary network fluctuations or temporary interface unavailability scenarios, avoiding excessive occupation of system resources |
| `variables` parameter passing format | Pass project ID and cycle range parameters in JSON structure | Standardizes the request parameter format for external interfaces, improving compatibility |

## Three Common Misconfigurations
- Phenomenon: After receiving long text from an HTTP interface, sending it directly without splitting causes request timeouts or rejection by the interface. Cause: No text chunking rules configured for the lengthy document characteristics of this category, exceeding the single transmission limit of the interface.
- Phenomenon: When attempting to connect to a self-built domestic model, interface calls return authentication failure. Cause: The `Authorization` parameter is not configured correctly, or the connection configuration between the model and the corresponding path is not completed.
- Phenomenon: The `responseData` field returned after calling an external interface is empty, making it impossible to generate document content. Cause: Correct field filtering rules are not configured, or core business identifiers specified by `variables` are not passed in the request parameters, causing the interface to fail to return valid data.

## How to Verify Proper Configuration
- Initiate a single test request, check whether the `Authorization` parameter is correctly carried, and confirm that the interface returns a status code of 200.
- Check whether the fields returned in `responseData` include the preset core business information, confirming that the field filtering rules are in effect.
- Simulate a long text request, check whether the system automatically splits the content and sends it in batches.
- Trigger a temporary failure scenario, confirm that the system executes retry operations according to the configured retry count.
