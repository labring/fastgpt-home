# Document and Material Drafting for Student Enrollment and Student Status Management: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Business data for the student enrollment and student status management scenario comes from the national primary and secondary school student status information management system, local student enrollment platforms, household registration and property data systems, and school academic affairs systems. The update frequency is daily. Documents processed daily include enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, and student status change approval forms. Most document fields are structured, with fixed fields such as student ID number, student status number, household registration address, property certificate number, guardian information, and application type. There is no high proportion of semi-structured or unstructured free text.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
Since data sources are scattered and updated daily, multi-turn dialogue must pull the latest student status and enrollment data in real time to avoid errors caused by expired information. Document fields are fixed and require strict verification, so prompts must explicitly specify the required fields for each document to prevent missing materials. Different application types correspond to different document templates, so multi-turn dialogue must switch prompt logic based on application type. Additionally, each conversation must be bound to a unique student identity to avoid mixing up different students' application materials and ensure accurate context.

## How to set configurations
These configurations apply to FastGPT v4.17.0:
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the student ID number of the currently processed student | Ensure the multi-turn conversation is bound to a unique student identity, avoiding confusion between different students' application materials |
| `variables` | Pass in student status ID, household registration address, application type | Provide accurate contextual data for prompts, adapting to different enrollment, transfer, or status change scenarios |
| `messages` | Retain the first 8 rounds of dialogue + the last 3 system response contents | Avoid context overload while retaining key application progress and collected field information |
| Question optimization | Calibrate based on actual testing | Enrollment-related questions mostly involve structured field completion; optimization can improve field collection efficiency |
| Single search limit | Top 3 results | Enrollment-related data sources are mostly structured tables; excessive results will interfere with field verification |
| Timeout duration | 600 seconds | Enrollment-related data sources are mostly internal systems; this duration prevents request failures caused by network delays |

## Three common errors
- Phenomenon: Multiple students' student status information is mixed in the conversation, and the returned material draft includes fields from unrelated students. Cause: The `chatId` is not bound to the student status number of the currently processed student, leading to context confusion between different application identity information.
- Phenomenon: The question classification model in the workflow has low recognition accuracy, and the returned application type does not match the actual submission. Cause: No exclusive prompt for the student enrollment scenario is used, and the optional classification types are not limited to enrollment, transfer, student status change, etc., leading to generalized recognition errors by the model.
- Phenomenon: Uploaded household registration or property certificates cannot correctly extract specified fields, and the returned draft lacks required certificate numbers. Cause: The prompt does not explicitly specify the document fields to be extracted, and the structured parsing configuration for file content is not enabled.

## How to confirm the configuration is complete
- Initiate a test conversation, enter the student status number, check whether `chatId` is bound to this student status number, and whether the context retains this ID as the core identifier.
- Trigger the multi-round field collection process, enter the required basic information in sequence, and check whether the returned material draft includes all required fields of the corresponding document.
- Upload a test household registration certificate file, check whether specified fields such as household registration address, householder name, and certificate number can be correctly extracted.
- Switch the test application type to transfer, check whether the prompt automatically adapts to the transfer application document template and generates the corresponding transfer application draft.

The values provided here are common starting points and should be measured against the reader's own samples.
