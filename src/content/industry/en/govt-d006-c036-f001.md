# Document and Material Drafting for Government Service Item Catalog and Service Guide Maintenance: HTTP Interfaces and External Systems

## What data for this category looks like
This category draws core data from the national basic catalog of government service items, administrative licensing item list, power and responsibility list, and local government service item databases. Daily maintained documents include the basic government service item catalog, implementation lists, service guides, standard material catalogs, flowcharts, and frequently asked questions. Data is updated monthly. A single service guide document typically includes standardized fields such as item name, acceptance conditions, application materials, and handling process. Fields must strictly match unified specifications issued by superior authorities, with no custom units.

## What constraints do these characteristics impose on the HTTP interfaces and external systems link
The monthly update cadence requires interface calls to adapt to low-frequency batch synchronization scenarios, avoiding high-frequency requests that consume government system resources. Standardized field rules require that the `variables` and `responseData` passed by the interface strictly match preset government service item fields, with no undefined parameters added. Multi-source data docking requires a unified authentication method to ensure data circulation between different systems complies with government data security specifications. The interface must also support integrity verification of returned fields to prevent errors in service guide maintenance caused by missing fields.

## How to set configurations
| Configuration Item | Recommended Practice | Rationale |

| `variables` | Pass fields in the order of government service item standard fields, including item code, acceptance conditions, application materials, with a value range of 800–1500 characters | Ensures interface parameters fully match the local maintained item data structure, avoiding field misalignment |

## Three common mistakes
- Phenomenon: Unable to maintain the same session context after multiple API calls, and parameter misalignment occurs for items in the same batch. Cause: Session persistence configuration is not enabled, or the timeout period is set too short, resulting in a new session being generated for each call and unable to reuse previous parameter context.
- Phenomenon: The HTTP request component cannot receive parameters passed by the plugin, and the corresponding fields in the request body are empty. Cause: The target parameter is not correctly bound to the `variables` configuration item, or the parameter format does not match the interface requirements, resulting in parameter loss.
- Phenomenon: An illegal parameter prompt is returned after calling the interface, and the `metadata` parameter is not correctly recognized. Cause: The `metadata` parameter is not included in the set of parameters passed via the `variables` configuration, or the parameter is not sent in the format required by the interface.

## How to confirm the configuration is correct
- Call the test interface, check whether the `Authorization` parameter conforms to the specified format, and confirm that the authentication status is normal.
- Pass in preset government service item test data, confirm that the fields in the `variables` parameter fully match the local data structure, with no omissions or misalignments.
- View the `responseData` return result, confirm that it only contains standardized fields, and the number of returned entries conforms to the preset limit.
- Call the interface three consecutive times, confirm that the session persistence configuration takes effect, and the context of calls in the same batch has not changed.
