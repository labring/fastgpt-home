# Document and Material Drafting for Government Service Item Catalog and Service Guide Maintenance: Model Access and Configuration

## What this category's data looks like
The core data for this category comes from the national basic catalog of government service items, administrative licensing item list, power and responsibility list, and local government service item databases, with a monthly update frequency. Daily maintained documents include the basic catalog of government service items, implementation lists, service guides, standard material directories, flowcharts, and frequently asked questions. These documents use structured fields as their core, including fixed fields such as item codes, acceptance conditions, application material lists, and service procedures. Some documents require cross-level comparison to verify consistency between higher-level catalogs and local implementation lists.

## Constraints for Model Access and Configuration
The monthly update frequency of the data requires that the configuration supports regular synchronization of multi-source heterogeneous data, and must adapt to format differences across documents from different sources. The large number of fixed structured fields requires model calls to accurately match the field rules of government affairs items, to avoid generating non-compliant content. The core requirement of cross-level comparison means the model must handle long-text contexts, while also controlling output accuracy to ensure reliable verification results. This category supports background rule base maintenance work, and does not process individual applicant-specific application cases. As such, the configuration does not need to adapt to personalized needs for single applications, and only needs to focus on rule verification and document standardization. Maintenance errors can lead to inconsistent online service standards, so the configuration must balance call efficiency and result rigor.

## How to Configure the Settings
The model access configuration logic in FastGPT v4.17.0 adapts to the maintenance needs of this category. The specific configuration items and recommendations are listed below:

| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Government service item documents are mostly structured long texts, requiring complete context to be retained for cross-level directory comparison |
| `maxTokens` | 3500–4500 token | A single service guide contains multiple fixed fields, controlling output length to avoid truncation of key compliance information |
| `quoteMaxToken` | 1200–1800 token | It is necessary to quote the original text of higher-level directories as a verification basis, retaining sufficiently long original reference content |
| `temperature` | 0.1–0.3 | It is necessary to maintain consistency in document format and fields, avoiding generation of significantly deviated verification conclusions |
| `toolChoice` | auto | Automatically select tools to handle structured field comparison and material list verification, improving processing efficiency |
| `AIPROXY_API_ENDPOINT` | Fill in according to the deployment environment | Adapt to model call paths for local or cloud deployments, supporting access to overseas and domestic models |

## Three Common Misconfigurations
- The symptom is a call error after connecting a local model, returning a 401 status code or an unauthorized prompt. The cause is incorrect configuration of the `AIPROXY_API_ENDPOINT` or `AIPROXY_API_TOKEN` parameters, failing to match the actual path and permission credentials of the model deployment.
- The symptom is missing fields or chaotic formatting in the generated service guide. The cause is an excessively low `maxTokens` value, resulting in truncation of key fields or compliance descriptions.
- The symptom is inconsistent verification conclusions generated by multiple calls to the same document. The cause is an excessively high `temperature` value, leading to random deviations in the logic generated by the large language model.

## How to Verify a Correct Configuration
- Call the test interface, input a single local government service item document, and check whether the returned result contains complete field verification conclusions and compliance descriptions.
- View the model call log to confirm that the `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` configuration parameters match the deployment environment, with no parameter errors.
- Adjust the `maxContext` parameter, test whether long-text input can be fully loaded and generate valid results, with no context truncation issues.
- Call the same document multiple times, check whether the generated verification conclusions remain consistent, and verify the rationality of the `temperature` parameter value.

The values provided are common starting points and should be measured against the reader's own samples.
