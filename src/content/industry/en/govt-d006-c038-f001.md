# Document and Material Drafting for Government Procurement Projects: HTTP Interfaces and External Systems

## What Data for This Category Looks Like
Data sources for this category include the China Government Procurement Network, local government procurement websites, the fiscal integration system, the procurer’s budget system, and supplier credit records. The update frequency is daily. Commonly processed documents include procurement requirements, procurement plans, bidding documents, tender documents, bid evaluation reports, winning bid announcements, procurement contracts, and responses to inquiries. Documents fall into two categories: structured field types (such as project number, supplier qualifications) and unstructured description types (such as evaluation rules, inquiry response content). Fields cover dimensions including transaction subjects, procurement content, qualification requirements, and result information.

## What Constraints These Characteristics Impose on HTTP Interfaces and External Systems
Data sources for this category are scattered and require integration with multiple official and internal systems. HTTP interfaces must support multi-source authentication adaptation to avoid call failures caused by differences in `Authorization` rules across different systems. Data is updated daily, so interfaces must support incremental pull logic to reduce resource consumption from full synchronization. Documents include structured fields and unstructured text, so interfaces must be compatible with both structured parameter transfer and large text upload format requirements. Since document errors can lead to serious consequences such as invalid bids and regulatory penalties, interfaces must be configured with clear failure retry and exception log retention mechanisms to ensure data interaction stability.

## How to Configure Settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Configure Bearer Token or custom signature key according to the requirements of the connected system | Government procurement-related systems generally require identity verification, and authorization rules must be matched accordingly |
| `variables` | Pass business fields such as project number and supplier credit code | Adapt to structured parameter transfer for procurement documents, facilitating accurate matching of business logic |
| `responseData` | Only return verification-passed results and exception error information | Simplify result parsing for external systems and reduce invalid data processing |
| Interface timeout setting | 60–120 seconds | Government procurement documents contain multiple associated texts, requiring sufficient processing time |
| Number of failure retries | 2–3 times | Address temporary network fluctuations or system load fluctuations, improving call stability |
| Single pull data limit | 1000 entries | Avoid exceeding interface traffic limits of government procurement systems and ensuring call stability |

## Three Common Mistakes
- A 400 status code is returned when calling the HTTP interface with no response body. Cause: The `Authorization` parameter is not configured correctly, or the format of the passed `variables` field does not meet the verification rules of the government procurement system.
- The document content returned by the interface does not match the preset procurement document type. Cause: The task orientation of the model is not clearly specified, resulting in generated documents that do not meet the format requirements of the government procurement law system.
- An embeddable government procurement document preview interface cannot be directly generated after integration. Cause: Only API call capabilities are provided at present. Front-end pages must be developed independently to complete document display and interaction.

## How to Confirm Configuration Is Complete
- Call the interface with a test project number and `variables` parameters, and check whether the returned `responseData` contains the expected structured fields.
- Simulate a temporary network interruption to verify whether the interface triggers the retry mechanism and returns results normally after system recovery.
- Connect to the test environment of the fiscal integration system, and check whether the `Authorization` parameter can pass identity verification and pull test data.
- View interface call logs to confirm that all abnormal requests are correctly recorded and corresponding error messages are generated.
