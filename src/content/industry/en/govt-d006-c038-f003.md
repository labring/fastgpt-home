# Document and Material Drafting for Government Procurement Projects: Multi-turn Dialogue and Prompt Engineering

Reference only; verify against the target FastGPT release and deployment documentation.

## What this category of data looks like
Data sources for this category include the Chinese government procurement website, local government procurement websites, fiscal integration systems, procurer budget systems, and supplier credit records. The update frequency is daily. Daily documents cover procurement requirements, procurement plans, bidding documents, tender documents, bid evaluation reports, bid award announcements, procurement contracts, and responses to inquiries. Document structures center on project-specific fields, including procurement target lists, budget amounts, qualification requirements, bid evaluation rules, and other modules. Field definitions across different documents follow the requirements of the government procurement law framework, with no unified cross-document general format.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
Daily updated data sources require multi-turn dialogue to limit context scope, to avoid mixing outdated project information. Differentiated fields across multiple document types require prompt engineering to be subdivided and adapted for different drafting scenarios. General templates cannot cover all requirements. Serious consequences of errors require that dialogue-generated content undergo pre-verification. Complete conversation history must be retained for traceability. Access restrictions on multi-source data limit the scope of context calls. Content must only be generated using government procurement-specific data sources.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum context length | 800–1200 characters | Adapt to the field density and length of government procurement documents to avoid context overflow |
| Session binding parameter | Enable `chatId` to bind the current application session | Ensure that multi-turn dialogue context is only associated with the current procurement project, avoiding cross-application interference |
| Context transfer switch | Enable the `messages` field to pass historical content | Retain pre-submitted procurement requirements, qualification requirements, and other information to support iterative multi-turn drafting |
| Variable input configuration | Call `variables` to pass project-specific numbers | Accurately match exclusive information for the current procurement project, avoiding generic content generation |
| Generation timeout threshold | 600 seconds | Address the time required to generate and verify complex bid evaluation reports and procurement contracts |

## Three Common Misconfigurations
- Conversation history cannot be cleaned for the specified application, and the interface shows the target conversation history as empty. The cause is that the `chatId` parameter is not bound. The conversation context is not associated with the corresponding application, so the cleanup operation cannot locate the target session.
- Multi-turn dialogue cannot build on conclusions from the previous turn. Subsequent generated results deviate from current procurement project requirements. The cause is that context transfer via the `messages` field is not enabled. Each dialogue executes independently, without retaining pre-verification or requirement information.
- The completion reason field of the dialogue component cannot be referenced by subsequent components, causing workflow interruption. The cause is that the `variables` field is not configured to capture the completion reason value. The field value is not written to the reusable variable pool.

## How to Verify Proper Configuration
- Initiate a dialogue for drafting procurement requirements. Check that the conversation history only displays content from the current session, with no historical records from other applications.
- Enter a follow-up question that references conclusions from the previous turn. Confirm that generated results build on pre-submitted procurement target information.
- Trigger dialogue generation. Check that subsequent components can read the completion status and result content of this dialogue.
- Simulate a generation result that does not meet requirements. Confirm that the workflow triggers secondary generation or termination logic.
