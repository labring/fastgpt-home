# Document and Material Drafting for Land Pre-examination and Planning Permit: HTTP Interfaces and External Systems

## What the Data for This Category Looks Like
Core data for this category comes from the national land and spatial planning one-map platform, project approval and supervision platform, land use status database, and ecological protection redline data. Update frequency is irregular.
Commonly processed documents include land pre-examination and site selection opinions, construction land planning permits, construction engineering planning permits, redline drawings, and planning conditions. Text documents include structured fields such as project site selection scope, land use scale, and control requirements. Drawing documents include spatial data such as vector redlines and planning zones.
Data is maintained jointly by the natural resources authority’s land use control and planning permit division, administrative examination and approval bureau, and project units. Fields must align with standardized business requirements for project approval.

## Constraints Imposed on HTTP Interfaces and External Systems
Since data sources include multiple government platforms and spatial databases, interfaces must support cross-system data pulling and format conversion. Interfaces must adapt to authentication methods of different data sources.
Irregular update frequency requires interfaces to prioritize incremental pulling mode. This avoids reprocessing already verified project data.
Documents include two formats: structured text and spatial drawings. Interfaces must support multiple input types such as PDF and vector files. Interfaces must retain the original business meaning of fields, to avoid losing key information such as land use scale and redline coordinates.
The strict constraints of project approval require that verification results returned by interfaces must be fully consistent with original data. No field deviations are allowed.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Carry a Bearer token exclusive to government platforms | Meet authentication requirements for natural resource government interfaces, ensuring lawful interface access permissions |
| `variables` | Pass exclusive parameters such as project number and land scope coordinates | Align with structured fields of data in this category, enabling precise association of interface calls with planning data for corresponding projects |
| `responseData` | Retain only core business fields and standardize the format | Simplify data processing in subsequent examination and approval links, avoiding redundant information interfering with verification logic |
| API timeout setting | 300–600 seconds | When connecting to interfaces such as the national land and spatial planning one-map platform, spatial data queries take a long time, so sufficient response time must be reserved |
| Drawing analysis threshold | Calibrate based on actual measurements | Adapt to the complex structure of planning drawings such as redline drawings and planning conditions, ensuring complete fields after analysis |

## Three Common Mistakes
- After calling an interface, the knowledge base chunking does not add planning document content. This occurs because the dedicated parameter for spatial planning data associated with the project is not correctly passed via `variables`, causing the interface to fail to match corresponding business data.
- The interface returns a 401 Unauthorized status code. This occurs because the `Authorization` parameter does not carry a valid government platform token, or the token format does not meet interface requirements.
- After uploading a PDF-format redline drawing, the analysis result lacks coordinate fields. This occurs because enhanced analysis configuration for planning drawings is not enabled, causing spatial data to not be correctly extracted.
