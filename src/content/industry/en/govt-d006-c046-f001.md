# Document and Material Drafting for Social Assistance and Minimum Living Security Review: HTTP APIs and External Systems

## What this category of data includes
The service subjects for this category include civil affairs bureau assistance sections, sub-district/township civil affairs offices, community committees, and verification centers. Daily documents cover minimum living security application forms, family economic status verification reports, household survey forms, democratic appraisal records, public notice materials, and assistance approval forms. The document structure includes fields such as applicant family basic information, income and property details, member relationships, verification results, and approval opinions. Units include monetary amounts, population counts, and time points. Data sources are the low-income population dynamic monitoring platform, resident family economic status verification system, and shared data from public security, human resources and social security, medical insurance, housing construction, and tax authorities. The update frequency is once per month.

## What constraints these characteristics impose on HTTP APIs and external systems
Multiple departmental data sources require APIs to connect to multiple external systems. APIs must be compatible with different systems' request formats and response rules. The monthly update frequency means API call frequency should not be too high. This avoids placing unnecessary load on external systems. The large number of structured document fields requires API request parameters to accurately match the core fields of each document. This prevents redundant data transmission. Cross-departmental data consistency requirements mandate verifying the integrity of returned data at the API level. This prevents risks of incorrect or missed assistance coverage. Errors directly impact assistance funds and public rights and interests, so APIs must include failure retry and exception alert mechanisms.

## How to configure settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `Authorization` | `Bearer {API key assigned by the platform}` | Standard authentication method when connecting to multiple external systems, to ensure data access security |
| `variables` | Includes applicant ID and verification cycle parameters, with a value range of 1–20 key-value pairs | Matches the structured field requirements of minimum living security review documents, to accurately pull verification data for the corresponding cycle |
| `responseData` | Only returns three core fields: family income, member relationships, and property details | Filters redundant data, reduces API transmission load, and adapts to the core information needs of document drafting |
| Call timeout | 600 seconds | Cross-departmental data verification requires multi-system coordination, which takes a long time; avoids prematurely interrupting requests |
| Retry attempts | 2–3 times | Addresses temporary network fluctuations or short-term unavailability of external systems, reducing API call failure rates |
| Single request data volume | Within 100 entries | Adapts to batch data processing under the monthly update frequency, avoiding API overload |

## Three common configuration mistakes
- Phenomenon: The API returns status code 403 and the response data is empty. Cause: The `Authorization` parameter is not configured correctly, and authentication failure prevents pulling cross-departmental shared data.
- Phenomenon: The `source` field returned by the API only marks a general identifier, and cannot be associated with a specific verification system source. Cause: No external system source parameter is configured in `variables`, resulting in the response data being unable to accurately mark the data channel.
- Phenomenon: The API call times out and is interrupted. Cause: No reasonable timeout period is set, and cross-departmental data coordination time exceeds the default threshold, causing the request to be terminated early.

## How to verify correct configuration
- Call the test API, check that the response header contains the correct authentication identifier, and confirm that the `Authorization` configuration takes effect.
- View the `responseData` field returned by the API, confirm that it only includes the three core fields of family income, member relationships, and property details, which meets the configuration requirements.
- Simulate a request for the monthly verification cycle, check that the number of returned results conforms to the single request data volume configuration limit.
- Trigger a simulated temporary exception request, confirm that the API can normally return compliant response data after retries.
