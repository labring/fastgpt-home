# Document and Material Drafting for Social Assistance and Minimum Living Security Review: Workflow Orchestration

## What data for this category looks like
Core data for this category comes from the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-departmental shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, tax and other departments. The update frequency is monthly.
Daily processed documents include minimum living security application forms, family economic status verification reports, household survey forms, democratic appraisal records, public notice materials, and assistance approval forms. Documents are organized by family. Fields cover family income, property status, member relationships, and basis for assistance eligibility determination. There is no unified standardized format. Cross-validation using multi-source data is required.

## Constraints imposed on workflow orchestration by these characteristics
Access to cross-departmental multi-source data requires workflow orchestration to configure multiple nodes to connect different data sources. It also requires handling format differences in data returned by each system.
The monthly update frequency requires workflow data pulling and verification links to match the monthly cycle. This avoids frequent calls that exceed interface limits.
The need to process multiple types of documents requires the orchestration to include information extraction nodes adapted to different document structures. It also requires configuring differentiated extraction rules for different document types.
The strict requirement for assistance eligibility determination requires adding multiple rounds of verification links to the workflow. These links cross-validate extracted family information to prevent incorrect or missed eligibility approvals.

## How to set configurations
| Configuration Item | Recommended Setting | Basis for This Setting |
| --- | --- | --- |
| Multi-document batch processing switch | Enabled | Adapt to the batch processing needs of multiple household survey forms and verification reports in minimum living security review |
| Variable binding rule | Bind family ID and corresponding document set | Match the family-based business logic, pass family identification parameters through `variables` |
| Node ID configuration | Assign a unique `nodeId` to each extraction node | Facilitate locating the execution status of the corresponding node in workflow logs |
| Node trigger condition | Trigger based on monthly data update time | Match the monthly update frequency of business data, reduce invalid calls |
| Maximum number of documents processed per run | Top 20 | Calibrated based on actual testing, avoid excessive load on single workflow nodes |
| Failure retry configuration | Retry 3 times, 60-second interval | Address scenarios where cross-departmental data interface calls fail occasionally |
| Node timeout configuration | 120 seconds | Match the average response duration of cross-departmental data interfaces |

This configuration is developed based on the workflow functionality of FastGPT v4.17.0.

## Three common misconfigurations
- Phenomenon: The workflow returns extraction results for only one document, with fields of other documents empty. Cause: The multi-document batch processing switch is not enabled, and information extraction is only performed for a single document.
- Phenomenon: The workflow editing interface displays "Application error: a client-side exception" in a private deployment environment. Cause: The access whitelist for cross-departmental data interfaces in the intranet environment is not configured, causing nodes to fail to call external data sources normally.
- Phenomenon: Workflow execution times out, and logs show response delays exceeding thresholds. Cause: The maximum number of documents processed per run is set too high, exceeding the allowed runtime of the node, and not matching the response delay of cross-departmental interfaces.

## How to confirm the configuration is correct
- Trigger a test run of the workflow, check whether the number of extracted documents matches the number of uploaded documents, and adjust the maximum number of documents processed per run to a range suitable for the business scale.
- View the workflow logs, confirm whether the family ID parameter bound by `variables` is correctly passed to each extraction node, and verify the validity of the variable configuration.
- After assigning a unique `nodeId` to each node, locate the execution status of the corresponding node through logs, and confirm the uniqueness and correctness of the node configuration.
- Trigger a single monthly cycle workflow execution, check whether the data pulling time matches the update rhythm of business data, and adjust the time parameters of the node trigger condition.
- Simulate a scenario where a cross-departmental interface call fails, confirm whether the failure retry configuration takes effect, and verify the execution logic of the error handling link.

The values provided here are common starting points and should be measured against the reader's own samples.
