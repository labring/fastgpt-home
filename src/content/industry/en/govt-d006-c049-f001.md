# Document and Material Drafting for Legality Review of Regulatory Documents: HTTP Interfaces and External Systems

## What the data for this category looks like
Core data for this category comes from regulatory rule repositories, higher-level law databases, departmental policy document repositories, and administrative regulatory document filing systems. Update frequency is irregular. Daily processed documents include regulatory document drafts, drafting explanatory notes, legality review opinions, solicited comment summaries, and filing reports. Most documents are structured text, with fields such as document title, issuing authority, article content, authority basis, and solicited comment content. There is no unified fixed unit field; corresponding information must be extracted based on specific business scenarios. The review process requires comparing article consistency across multiple data sources. The most time-consuming steps focus on authority verification and article legality review.

## What constraints these characteristics impose on the HTTP Interfaces and External Systems link
Irregularly updated multi-source data sources require interfaces to support on-demand data pulling, to avoid redundant data transmission. Diverse document structures require interfaces to adapt to different formats of text input and output, without enforcing a unified document structure. The lack of fixed unit fields requires parameters passed by the interface to include business context tags, to help external systems identify corresponding content. Time-consuming review steps require interfaces to support long request timeouts, to avoid prematurely interrupting the review process. The need for collaborative processing of multiple document types requires interfaces to transmit multiple business data entries simultaneously, to support batch verification scenarios.

## How to configure settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {valid system authentication token}` | Identity verification is required when connecting to external regulatory repositories and filing systems, to prevent unauthorized access. This applies to the HTTP tool configuration for FastGPT v4.17.0. |
| `variables` | `Key-value pairs containing regulatory document draft text, higher-level law keywords, and authority basis tags` | Pass core business data required for review as variables to the interface, to adapt to parameter requirements for different review scenarios. |
| `responseData` | `Structured JSON returning legality check results, comparison article markers, and compliance explanations` | Standardize review results to facilitate subsequent generation of review opinions, filing reports, and other documents. |
| Request timeout | `600 seconds` | Review involves multi-source data comparison, so single requests take a long time. This setting avoids prematurely interrupting the review process. |
| Batch request limit | `First 5 entries` | Single review involves a limited number of higher-level law and policy document entries. Too many entries will increase interface load. |

## Three common mistakes
- When calling the interface, a connection error is returned with status code 500 or request timeout. The cause is that when connecting to a locally deployed model service, the network mode of the FastGPT container is not configured to communicate with the local service, resulting in inability to access the target interface.
- When attempting to pass a local file as an interface input parameter, the interface cannot receive the file content. The cause is that the HTTP tool has not enabled file upload support, and only supports text-type parameter transmission.
- After calling the interface, an empty result or missing fields is returned. The cause is that the parsing rules for `responseData` are not correctly configured, and the required result fields are not specified, resulting in the original data returned by the interface not being correctly mapped.

## How to confirm the configuration is correct
- Initiate a test request, pass standard regulatory document draft text, and check if the interface returns the expected structured result.
- View the FastGPT interface call log, confirm that the `Authorization` authentication parameter has been correctly carried, and there are no authentication failure errors.
- Test passing different types of business data, confirm that the `variables` parameter can be correctly transmitted and recognized by the external system.
- Verify that the interface request timeout setting meets the requirements of the business scenario, and no premature interruptions occur.
