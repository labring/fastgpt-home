# Document and Material Drafting for Flood Prevention, Disaster Mitigation and Emergency Duty: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
This category’s data mainly comes from meteorological early warning, hydrological monitoring, emergency command, grassroots disaster reporting, and video surveillance systems. The update frequency is daily. Daily generated documents include duty logs, early warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Data fields include rainfall magnitude, hydrological peak value, danger level, number of transferred people, material category, inventory quantity, and more. Some fields have dedicated units: rainfall is measured in millimeters, and hydrological data is measured in cubic meters per second.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
Real-time updates of multi-source data require dialogue contexts to quickly filter redundant information, avoid loading outdated monitoring data, and ensure generated documents always use the latest rainfall, hydrological, and disaster information. The differentiated structures of various documents require prompt engineering to preset field rules for different scenarios. For example, a material allocation slip must clearly specify category, quantity, and receiving unit. A consultation minute must summarize rainfall and hydrological conditions and response progress. A duty log must record duty periods and abnormal situations. The presence of dedicated unit fields requires multi-turn dialogue to retain unit information, preventing unit errors in generated documents. The need for cross-departmental data association also requires multi-turn dialogue to retain source identifiers from different systems, ensuring the credibility of document data.

## How to configure settings
This section is written based on the functionality logic of FastGPT v4.17.0. The specific configuration items are as follows:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum context length | 800–1200 characters | Daily documents for this category have consistent single-piece length. Overly long contexts will slow response speed. |
| `chatId` session binding | Generate independently per user identity, associate with the current session | Ensure different users can only view their own conversation records, meeting persistent storage requirements. |
| `variables` variable configuration | Bind real-time system fields for rainfall, hydrology, and material allocation | Directly call native monitoring data to avoid manual entry errors. |
| `messages` context recall | Only recall the first 5 entries of history from the current session | Filter redundant history, focusing on the latest duty and disaster information. |
| Conversation record pagination offset | Use a step size of the first 20 entries each time | Adapt to the data update frequency of this category, avoiding returning too many invalid historical records. |

## Three common mistakes
- Returning irrelevant session data when calling the conversation record list interface. This occurs because the current session is not bound via `chatId`, causing the offset parameter to not associate with the correct user session.
- Generating document content with unit errors during dialogue. This occurs because dedicated unit information for data is not retained in multi-turn dialogue, and the prompt engineering does not specify unit rules for fields.
- Failing to match user questions with corresponding AI replies. This occurs because the `messages` context is not properly organized in session order, resulting in mixed-up associations between historical records.

## How to verify correct configuration
- A simulated duty conversation is initiated to generate a rapid disaster report document. The generated content is checked to confirm it includes rainfall and hydrological data bound to the current session, and that the `variables` variables function correctly.
- Multiple test users initiate conversations. Each user’s ability to only view their own conversation records is verified, confirming the `chatId` user isolation configuration operates correctly.
- The conversation record list interface is called with the preset offset step size. The number of returned records is checked to match the set value, confirming the offset logic works correctly.
- The `messages` field returned by the interface is reviewed. The order of each AI reply and user question is confirmed to match the conversation history, verifying context association functions correctly.
