# Document and Material Drafting for Flood Prevention, Disaster Mitigation and Emergency Duty: Model Access and Configuration

## What this category's data looks like
The core data for this category comes from meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. The update frequency is daily. Some real-time warning data has shorter update intervals. Daily documents include duty records, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Most document structures include fields for time, location, numerical values (such as rainfall in millimeters, water level in meters, number of personnel) and response measure entries. Field units mostly follow general standard units for meteorology and hydrology.

## Constraints on model access and configuration from these characteristics
The data sources for this category are scattered and have high update frequencies. Model access must adapt to the context loading rhythm of multi-source real-time data to avoid generation interruptions caused by context overflow. Daily documents contain a large number of structured numerical values and standardized response entries. Configuration must limit the upper limit of generated tokens to ensure outputs comply with emergency document format specifications. There are slight differences in data field units across different sources. Configuration must clarify data alignment processing logic to avoid unit confusion in generated content. The timeliness requirements of emergency scenarios also require adjusting relevant parameters to balance generation accuracy and response speed, to adapt to frequently updated business data.

## How to set configurations
| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Needs to load multi-source hydrological, meteorological, and grassroots disaster reporting data from the current day; this range covers the complete daily business dataset |
| `maxTokens` | 2000–3000 token | Emergency documents primarily consist of structured entries and response processes; this range covers the reasonable length of standard documents and avoids redundant output |
| `quoteMaxToken` | 1500 token | Needs to accurately reference specific monitoring values for rainfall and water conditions; this length retains complete information from key data sources |
| `temperature` | 0.3–0.5 | Emergency documents must remain rigorous and accurate; a lower temperature reduces irrelevant content generation and ensures outputs comply with business specifications |
| `AIPROXY_API_ENDPOINT` | Local vllm deployment service address | Adapted to self-deployed large models for FastGPT v4.17.0, to ensure data processing meets internal security requirements |
| `vision` | Disabled | Core documents for this category are based on structured text and numerical data; no image input processing is required, which reduces resource usage |

## Three common configuration mistakes
- Enabling the `vision` parameter causes the interface to fail to display the image upload option, and generated results do not include image analysis content. Cause: This business scenario does not require image input. After the parameter is accidentally enabled, the system does not adapt to the image processing logic for the corresponding scenario, causing the function to fail to trigger properly.
- After configuring a locally deployed large model, test sessions return a connector error. Cause: `AIPROXY_API_ENDPOINT` or `AIPROXY_API_TOKEN` is not filled correctly, or the local service has not opened the corresponding port, causing the system to fail to establish a connection.
- Context truncation occurs when generating consultation minutes, and key monitoring data is missing. Cause: The value of `maxContext` is too small, failing to cover complete hydrological and meteorological data from the current day, causing the system to fail to load all necessary business information.

## How to confirm successful configuration
- Run a local model connection test to confirm normal response content is returned, and verify that the configuration of `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` matches the local service.
- Import a set of current-day hydrological monitoring data and duty records, test generating a rapid disaster report, and check whether the generated content includes all key fields and numerical values.
- Adjust the `temperature` parameter, compare generated results across different values, and confirm that outputs comply with the rigor requirements of emergency documents.
- Check the configuration status of the `vision` parameter, confirm that unrelated image processing functions are not enabled, to avoid resource waste.
