# Document and Material Drafting for Food Safety Supervision and Sampling: HTTP Interfaces and External Systems

## What the data for this category looks like
This category's data originates from food safety sampling monitoring systems, the State Administration for Market Regulation's sampling results query system, testing institution LIMS, and food producer and operator ledgers. Data updates occur monthly. Core documents include sampling plans, sampling slips, inspection reports, unqualified food verification and disposal reports, and risk control announcements.
Document fields cover sampling locations, inspection items, non-conformity judgment items, production enterprise information, and more. Required fields differ across documents. For example, sampling slips must record sampling dates and sampling personnel information, while inspection reports must list detected values and compliance conclusions.

## Constraints for HTTP Interfaces and External Systems
The monthly update frequency means interface calls do not need to run frequently. Calls must comply with each system's call frequency limits to avoid being blocked.
Multi-source data integration requires interfaces to adapt to authentication rules and return formats of different systems. Parameter structures differ between the sampling monitoring system and LIMS, for example.
Fixed field requirements for different documents mean interface request parameters must strictly match the required items for the target document. The target system will reject requests that do not meet this standard.
Failed interface calls can delay sampling plans or delay disposal of unqualified food, leading to regulatory risks. Retry and fault-tolerant mechanisms must therefore be configured.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer fixed token, valid for 7 days | Adapts to the authentication rules of the food safety sampling monitoring system, avoiding frequent token acquisition |
| `variables` | Includes fields such as sampling number, inspection items, non-conformity judgment values, dynamically filled per task | Matches the required fields of sampling documents, ensuring request parameters meet target system requirements |
| `responseData` | Only extracts sampling slip ID, inspection report URL, and verification and disposal status fields | Reduces invalid data transmission and improves interface processing efficiency |
| Retry count | 3 times, 60 second interval | Addresses temporary system current limiting or network fluctuations, ensuring task execution stability |
| Interface call frequency | No more than 10 calls per minute | Matches the call limits of the State Administration for Market Regulation systems, avoiding being blocked |

## Three Common Mistakes
- HTTP interface calls return a 200 status code but do not generate the corresponding sampling plan document. This occurs when required fields for the sampling plan are not configured in `variables`, so the target system cannot recognize the request content.
- Calling the testing institution LIMS interface returns empty fields. This happens when extraction rules for `responseData` are not set correctly, failing to match the target system's return field structure.
- Interface calls time out, causing task execution to fail. This is due to missing a properly configured retry mechanism, with no automatic retry triggered after a single call fails.

## How to Verify a Successful Configuration
- Fill in test sampling slip parameters, initiate an interface call, and check if the returned `responseData` includes the preset sampling slip ID field.
- Simulate a temporary network interruption to verify whether the interface automatically sends retry requests per the configured retry count.
- Review interface call logs to confirm the `Authorization` token format is correct, with no authentication failure errors.
- Compare interface return data with the local sampling document template to confirm field matching meets business requirements.

The values provided are common starting points and should be measured against the reader's own samples.
