# Document and Material Drafting for Survey and Design: HTTP Interfaces and External Systems

## What this category of data looks like
Survey and design document and material drafting data mainly comes from project site survey reports, construction drawing design files, submission and approval materials, engineering change notices, and similar sources. Data update rhythm adjusts based on project progress. High-frequency updates trigger before submission and after changes.
Single documents mostly use a mixed structure, with fixed fields: project number, survey point coordinates, design parameters, approval batch number, signatory, generation date. Supported units include meters, megapascals, square meters, and others.
Document length varies widely. Small submission documents are around several thousand characters. Large full sets of design instructions can reach tens of thousands of characters.

## What constraints these characteristics impose on HTTP interfaces and external systems
Survey and design data includes structured coordinate and parameter fields, plus unstructured text. This requires HTTP interfaces to support field validation and multi-format data transmission.
The wide range of document lengths means request body sizes may exceed conventional thresholds. Large-volume transmission configurations must be adapted.
Data updates have no fixed cycle and rely on project unique identifiers. Interfaces must support dynamically passing custom parameters such as project numbers to complete data matching.
Connected external approval systems and BIM platforms often have exclusive authentication and data format requirements. Corresponding interface specifications must be strictly followed.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| API Address | Fill in the official interface address of the external survey and approval system, such as `https://xxx.com/design/report/submit` | Match the interaction path of the connected system to ensure requests reach the target service |
| `Authorization` | Fill in the authentication string in the format Bearer {oneapi secret} | Comply with HTTP interface authentication standards to complete identity verification with external systems |
| Request Timeout | 600 seconds | Cover the full duration of survey and design document upload and external system processing, to avoid premature timeout interruptions |
| `variables` | Pass custom business parameters such as project number and survey point coordinates | Match the data matching rules of the external system to enable accurate association of corresponding project documents |
| `responseData` | Configure to extract the approval number and review status fields returned by the interface | Capture processing results from the external system for status tracking in subsequent workflows |
| Retry Count | 2 times | Handle request failures caused by temporary network fluctuations, preventing repeated submission of duplicate data |

## Three common configuration errors
- Only the secret value is filled in without adding the Bearer prefix when configuring `Authorization`. The interface returns a 401 Unauthorized status code. This occurs because the configuration does not meet the standard format requirements for HTTP authentication.
- The project number field is not passed in `variables`. The external system returns empty data or mismatched project documents. This occurs because survey and design data relies on the project number as the unique identifier, and the missing parameter prevents location of the corresponding business data.
- The request timeout is set to a short value such as 30 seconds. A timeout error triggers when submitting large documents. This occurs because processing and transmission time for survey and design submission documents is lengthy, and a short timeout cannot cover the full workflow.

## How to confirm the configuration is complete
- A test request is sent. The HTTP status code returned by the interface is checked for 200, confirming the authentication configuration is active.
- A test project number and small test document are passed. The external system backend is checked for receipt of the corresponding parameters, confirming the `variables` configuration is correct.
- The fields extracted by `responseData` are checked for inclusion of the approval number and review status, confirming the response processing configuration is correct.
- A temporary network interruption is simulated, then the request is retried. The preset retry mechanism is checked for triggering, confirming the timeout and retry configurations are active.

The configuration values provided here are common starting points, and should be evaluated against local samples.
