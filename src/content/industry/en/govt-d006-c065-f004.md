# Document and Material Drafting for Survey and Design: Workflow Orchestration

## What the data for this category looks like
Data for survey and design comes from on-site survey point records, structural calculation documents, construction drawing submission files, and project approval application forms. Data update rhythm proceeds with project submission milestones, with a full update completed before official submission. Document structure is divided into three categories: preface page, core calculation module, and attached drawing pages. Fields include unique project ID, survey point latitude and longitude, structural load parameters, and drawing version number. Units uniformly use universal engineering measurement standards such as millimeters, megapascals, and cubic meters.

## What constraints these characteristics impose on workflow orchestration
Survey and design documents contain a large number of structured calculation parameters and unstructured drawing attachments. The total character count of a single submission document can reach tens of thousands. This requires the workflow to adapt to mixed-format input during the data reading stage. Project data is updated in batches alongside submission milestones. The workflow must bind to project status to trigger execution, preventing reading of incomplete temporary data. Multiple engineering parameters require the workflow’s `variables` configuration to accurately map field names, avoiding document generation deviations caused by parameter matching errors. Most engineering databases store structured project data. When the workflow connects to the database, it must adapt to the exclusive table structure, avoiding connection exceptions caused by field mismatches.

## How to set the configuration
This configuration guide is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Node trigger timing | Trigger based on project submission milestones | Matches the update rhythm of survey and design projects proceeding by milestones |
| `variables` mapping rules | Bind engineering-specific field names | Accurately match the structured parameters of survey and design documents |
| Database connection timeout threshold | 600 seconds | Adapts to the time-consuming requirements of large table queries in engineering databases |
| Single data read limit | First 200 entries | Avoid timeouts caused by loading too much data at once |
| Workflow field validation switch | Enable format validation | Adapts to the format requirements of professional units such as millimeters and megapascals |
| `nodeId` binding rules | Associate with unique project ID | Ensure workflow execution is bound to the corresponding project |

## Three common mistakes
- The error `Failed to connect to jyfkk:1433 - 38BBDDC3AF7F0000` appears. The cause is that the database table connected by the workflow does not match the storage table structure of the survey and design project, and engineering-specific fields are not correctly mapped.
- The workflow-generated document lacks core load parameters. The cause is that the corresponding engineering parameter name is not bound during `variables` mapping, leading to omission of core content when reading data.
- The workflow execution times out and terminates. The cause is that the single data read count is set too high, exceeding the response limit of large table queries in engineering databases.

## How to confirm the configuration is correct
- Trigger a test workflow, check whether the generated document includes all preset engineering fields, and confirm that field content matches values stored in the database.
- View workflow logs, confirm there are no database connection errors, and all node execution statuses show success.
- Adjust the workflow’s trigger timing to test node, verify that execution starts only when the specified project status is met.
- Enter parameters that do not comply with professional unit standards, confirm that the workflow triggers a format validation prompt.
