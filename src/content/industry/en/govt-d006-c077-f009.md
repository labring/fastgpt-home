# Document and Material Drafting for Urban Public Transit: Model Access and Configuration

## What Constraints These Characteristics Impose on Model Access and Configuration
Scattered data sources with inconsistent update frequencies require model access to support real-time pulling and batch aggregation of multi-source data. This prevents missing the latest temporary route adjustment information during document generation. Minor differences exist in field formats across different documents. For example, departure time uses both HH:MM format and full date-time format. Unified mapping of field formats must be completed during configuration. Otherwise, documents generated by the model will have format inconsistencies. The content length of single documents varies widely, ranging from short safety summaries to detailed route adjustment announcements. Model context and output length configurations must adapt to the needs of different scenarios.

## Recommended Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `maxContext` | `8000–12000 token` | Public transit documents typically contain multiple linked pieces of information such as route data, historical shifts, and passenger flow statistics. Sufficient context is required to hold complete business background |
| `maxTokens` | `1500–2000 token` | The output length of single public transit documents such as route adjustment announcements and rectification notices usually falls within this range, preventing truncated or redundant generated content |
| `temperature` | `0.3–0.5` | Public transit documents require strict, accurate formats and content. This parameter range balances generation standardization and flexibility |
| `AIPROXY_API_ENDPOINT` | `https://internal-proxy.company.com:8080` | Access to the large model must go through the enterprise intranet proxy, ensuring operation data does not exit the external network |
| `AIPROXY_API_TOKEN` | Fill in the exclusive assigned key | Authenticate identity via the key, ensuring interface call security and permission controllability |
| `toolChoice` | `auto` | Allow the model to independently determine whether to call data retrieval tools to supplement real-time public transit operation data, improving document content accuracy |

## Three Common Configuration Mistakes
- Phenomenon: A 401 status code is returned when calling the large model interface, with a prompt of insufficient permissions. Cause: `AIPROXY_API_TOKEN` is not filled in correctly, or the assigned key does not have access permission for the corresponding model.
- Phenomenon: Fields such as route number and departure time are missing or have incorrect formats in the generated documents. Cause: Unified mapping of data source field formats was not completed during configuration, leading to the model failing to correctly extract business data.
- Phenomenon: The accuracy of driver name matching results is low, and the number of matching entries does not meet expectations. Cause: The semantic matching configuration range was not adjusted based on the field characteristics of public transit data, leading to the model failing to correctly match associated data.

## How to Verify Successful Configuration
- Call the test interface, input basic data for a single bus route, and check if the generated route adjustment announcement includes correct fields such as route number and departure time.
- Review the interface return log, confirm that `AIPROXY_API_TOKEN` verification passed, and that no permission errors such as 401 or 403 are present.
- Adjust the `temperature` parameter, compare the two generated document sets, and confirm that the rigor of the generated results meets expectations after the parameter change.
- Upload a real public transit operation data document, and check if the generated document length falls within the range set by `maxTokens`.

The values provided are common starting points and should be measured against the reader's own samples.
