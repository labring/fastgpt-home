# Document and Material Drafting for Basic Telecommunications Operations: Document Parsing and Chunking

## What the data for this category looks like
Data related to document and material drafting for basic telecommunications operations comes from network operation logs, customer service tickets, annual network assessment reports, device configuration documents, and commercial contracts.
Data update rhythms vary by business scenario: operation logs are generated in real time, tickets update alongside customer inquiries, and annual reports release quarterly or annually.
Document structures include multi-level heading hierarchies, embedded network topology diagrams, and bandwidth usage tables. Standard fields mostly include device ID, port number, traffic value (unit: Mbps or GB), ticket number, and other standardized identifiers. Some documents mix long paragraphs and fragmented text.

## Constraints on document parsing and chunking
Multi-level heading structures require chunking logic to match document hierarchies, to avoid splitting associated content across headings.
Embedded images and tables require the parsing module to support format restoration, otherwise critical operation and maintenance information will be lost.
Long documents and large files increase parsing time, so timeout and size limits must be adjusted.
Standard field usage requires that chunking does not destroy field integrity, otherwise subsequent retrieval accuracy will be affected.
Real-time updated ticket documents need to adapt to fast parsing processes, to avoid delays impacting business response.

## How to configure
The following configuration items apply to FastGPT v4.17.0.
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chunkSize` | 1000–1500 characters | Adapts to the field density and long paragraph structure of basic telecommunications operation documents, avoiding splitting critical operation and maintenance parameters or contract clauses |
| `chunkSplitter` | Split by heading hierarchy | Matches the multi-level directory structure of tickets and operation and maintenance reports, retaining contextual association of content at the same hierarchy |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600 seconds | Addresses large-volume annual network assessment reports and offline operation and maintenance log packages, avoiding parsing interruptions due to timeout |
| `customPdfParse` | Enabled | Adapts to telecommunications industry PDF documents with topology diagrams and structured tables, improving parsing integrity of non-standard format content |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | Supports upload of large offline operation and maintenance log packages and multi-document compressed packages |
| `chunkSettingMode` | Manual configuration | Flexibly adjusts chunking parameters for different document types (tickets/reports/contracts), adapting to differentiated content structures |

## Three common configuration mistakes
### Mistake 1
Phenomenon: When configuring an external pdf-maker parser, the key setting entry cannot be found, and the parsing function cannot take effect.
Reason: The third-party parser key is not configured in the file parsing module of FastGPT system settings. Only filling the key in the third-party tool platform does not synchronize it to the system.

### Mistake 2
Phenomenon: Feishu multi-level directory documents only parse top-level content, and ticket details under subdirectories cannot be retrieved.
Reason: The chunking configuration does not enable recursive parsing hierarchy. The default setting only grabs text content under first-level headings, without covering lower-level directories.

### Mistake 3
Phenomenon: Split-related errors occur when using the marker parsing module. The parsing module in the Docker-deployed FastGPT version does not properly pass text content.
Reason: There is network configuration isolation between the parsing container and the main service. The correct file transfer port or shared storage path is not configured, resulting in parsed text being unable to be returned to the main system.

## How to confirm configuration is successful
1. Upload a typical telecommunications operation and maintenance PDF document that includes multi-level headings, embedded tables, and topology diagrams. Check if the parsed text completely retains all hierarchical headings and table content.
2. Call the file parsing API to upload a standard doc document. Check if the returned result includes complete chunked text and metadata fields such as device ID and traffic value.
3. Adjust the `chunkSize` parameter, upload the same operation and maintenance report, and compare the length changes of the parsed chunked results twice to confirm that the parameter takes effect.
4. Check the `PARSE_FILE_TIMEOUT_SECONDS` parameter in the system settings. Simulate uploading a 1000 MB-level log package, and verify whether a timeout error is triggered or the parsing succeeds.

The values provided are common starting points and should be measured against the reader's own samples.
