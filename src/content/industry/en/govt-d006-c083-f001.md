# Document and Material Drafting for Infrastructure Construction: HTTP Interfaces and External Systems

## What the data for this category looks like
Data for infrastructure construction documents and materials is primarily sourced from construction logs, site visa forms, sub-project acceptance reports, completion archiving materials, and other records generated during construction.
Update frequency aligns with construction milestones. Daily construction documents are updated each day. Acceptance documents are synced once the corresponding sub-project acceptance is completed.
Document structures include fixed fields: project number, construction section, operation date, material specification and model, acceptance conclusion, and site condition description. Most field units follow general construction industry standards, such as meters, cubic meters, tons, workdays, and others.

## What constraints these characteristics impose on HTTP interfaces and external systems
Fixed fields for infrastructure construction documents require that HTTP interface requests must carry required project identification fields like project number and construction section. Missing these fields will cause generated content to deviate from the project context.
Data update frequency fluctuates with construction milestones. Interface call frequency must match the work cycle to avoid excessive calls consuming system resources.
Document length varies widely. Some construction logs are only a few hundred characters, while completion materials can span tens of thousands of characters. Interfaces must support dynamic adaptation to request body size.
Industry-specific unit requirements mean field units returned by the interface must strictly follow general construction industry standards to prevent parsing errors in external systems.

## How to configure the settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| ------ | -------- | ------------ |
| `Authorization` | `Bearer {valid CHAT_API_KEY}` | Complies with FastGPT interface authentication specifications to ensure requests are properly identified |
| `variables` | `JSON object containing project number, construction section, and operation date, with field values filled per construction standards` | Binds exclusive project context for document generation to avoid content disconnected from actual engineering work |
| `responseData` | `Return only structured document body and corresponding field mapping, filter out non-essential debug fields` | Meets archiving and circulation requirements of external systems, reduces invalid data transmission |
| Maximum Context | `8000–12000 characters` | Adapts to the length range of infrastructure construction documents, prevents truncation of critical engineering data |
| Single Search Limit | `Top 8 entries` | Matches the volume of associated data for engineering documents, balances generation quality and interface response speed |
| Question Optimization | `Enabled` | Standardizes engineering terminology to avoid output that does not conform to construction specifications |

## Three common mistakes
- Phenomenon: After startup, interface calls return 401 Unauthorized, and container logs show authentication failure. Cause: The CHAT_API_KEY environment variable was not correctly configured in docker-compose.yml, and the container was not rebuilt to apply the new configuration.
- Phenomenon: After calling the document generation interface, returned content lacks engineering-specific fields, or generated content is unrelated to the project. Cause: Required engineering fields such as project number and construction section were not passed in `variables`, leading to generation logic lacking valid context.
- Phenomenon: Results returned by the knowledge base file list interface do not match the actual number of engineering documents. Cause: The single search limit parameter was not correctly set, or returned results were not filtered using the classification fields of engineering documents.

## How to confirm the configuration is correct
- Send a test request that includes the engineering-specific `variables` field, check if the returned `responseData` from the interface contains document content tailored to the project.
- View interface authentication logs to confirm the `Authorization` field was correctly parsed, with no authentication failure related errors.
- Compare the fields received by the external system against the standard field list for construction documents, confirm all required fields are fully returned.
- Adjust the maximum context parameter, test generation requests for engineering documents of different lengths, confirm no forced truncation or interface errors occur.
