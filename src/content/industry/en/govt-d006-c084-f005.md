# Document and Material Drafting for Commodity Trading: Tool Calling and Plugins

## What data looks like for this category
Commodity trading documents and materials mainly originate from transaction ledgers including purchase and sales contracts, warehouse receipts, customs declarations, settlement statements, and goods ownership certificates. Updates occur synchronously with the completion of a single transaction or batch delivery. The fixed document structure includes core fields: information of both transaction parties, target commodity category (such as iron ore, crude oil, steel), transaction quantity, unit price, delivery terms, and liability for breach of contract. Field units mostly use physical or pricing units such as ton, cubic meter, barrel, yuan per ton. Some documents include unique cross-system identification numbers, such as goods ownership numbers and transport order numbers.

## What constraints these characteristics impose on tool calling and plugins
Commodity trading documents’ structured fields and cross-system association attributes require tool calls to accurately match the exclusive data of the target transaction, preventing field errors from generalized retrieval. The fixed document structure requires plugins to call tools that support templated field filling, and cannot rely on unregulated natural language generation. Real-time data updates tied to transactions require plugins to set data source cache durations that match the transaction cycle, avoiding calls to expired warehouse receipts or settlement information. Different commodity categories have differing trading document fields, so tool calls must support dynamic adaptation to category-specific field mapping rules.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `toolChoice` | `auto` | Adapt to document generation requirements for different commodity categories, automatically match the corresponding tool node |
| `functionCall` | `enabled` | Force tool calls to complete structured field filling, avoid generating unstructured content that does not comply with trading specifications |
| Tool call timeout | `300–600 seconds` | Pulling data such as warehouse receipts and customs declarations across systems takes a long time, reserve sufficient request duration |
| Tool call retry count | `2 times` | Respond to temporary network fluctuations in cross-system calls, reduce the probability of single call failure |
| Bound data source scope | Current transaction ledger + corresponding warehouse receipt database | Only associate exclusive data of the current transaction, avoid interference from irrelevant information on document generation |

## Three common mistakes
- Symptom: An authentication failure error message appears when calling a tool. Cause: The application-level app key was not used, and an account-level key was incorrectly used for interface calls.
- Symptom: The application interface embedded via iframe cannot display avatars and interface images, and only a small number of niche browsers can load normally. Cause: FastGPT v4.17.0 or higher is not used, and browser security policies block compliant static resource loading.
- Symptom: Workflow-generated documents include intermediate return content from first-level tool calls. Cause: The intermediate output switch for tool nodes in the workflow was not turned off, causing intermediate step logs to be spliced into the final output.

## How to confirm the configuration is correct
- Trigger the document generation process for a test transaction, check whether the tool call log carries correct application-level app key authentication information.
- Call the bound workflow, verify that the final returned document content only contains the standardized trading document structure, with no fragments from intermediate tool calls.
- Open the embedded application interface in multiple mainstream browsers, confirm that avatars and interface images load and display normally.
- Pull the structured data source for the test transaction, check whether the fields in the generated document fully match the corresponding relationship with the data source.
