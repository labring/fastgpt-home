# Document and Material Drafting for General Contracting of Building Construction Projects: Tool Calling and Plugins

## What data looks like for this category
The documents and materials for general contracting of building construction projects mainly originate from full-cycle project files such as project bidding documents, construction logs, site visa forms, progress payment application forms, and completion acceptance reports. Data updates follow project node progress: construction-related documents are updated weekly, while progress payment and settlement-related documents are updated monthly. The document structure uniformly includes fields such as project number, section name, full name of participating construction units, signing date, core matter description, and legal signature and seal column. Some materials require quantitative information including floor area (unit: ㎡), project cost (unit: ten thousand yuan), and construction period (unit: calendar days).

## What constraints do these characteristics impose on the tool calling and plugin process
The characteristics of documents for general contracting of building construction projects impose multiple constraints on the tool calling and plugin process. Multi-source and heterogeneous project files have significant format differences, so plugins must preset format verification rules for different document types to avoid generated content that does not match the template structure. Data updated according to project nodes requires that plugin calls be associated with the current progress node of the project, to prevent calling outdated templates or project data from non-current stages. Documents with quantitative fields require plugins to automatically identify and fill in the correct units, to avoid compliance issues caused by unit mismatches. The fixed format requirement of the legal signature and seal column requires that the content generated by the plugin reserve corresponding signing positions, and must not alter the original compliance typesetting requirements.

## How to set the configuration
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | There are many types of documents involved in general contracting of building construction projects; automatic tool selection can adapt to the calling needs of different templates |
| `functionCall` | `enabled` | Plugins are required to fill in project-specific quantitative fields and compliance information through preset function calls |
| Plugin call timeout | `600 seconds` | Generating some large settlement and completion acceptance documents requires a long processing time |
| Plugin input context length | `800–1200 characters` | The core business information of building construction project documents usually falls within this character range |
| Number of results returned per single call | `Top 3–5` | The number of core information items in building construction documents should not be too large, to avoid content redundancy |
| Plugin context cache duration | `7 days` | The latest version of historical data for building construction projects is usually retained within 7 days, to avoid calling outdated information |
| Plugin result reordering rule | Reorder by compliance field priority | Building construction documents need to prioritize displaying legally required items such as project number and participating construction units |

## Three common mistakes
- Symptom: Parameter errors or connection timeouts occur when calling the Doc2X plugin. Cause: The dedicated document storage path for building construction projects is not bound in the plugin configuration, causing the plugin to fail to read the source files of the corresponding section.
- Symptom: An error is triggered when clicking the input box after referencing a plugin in a workflow and connecting a code running node. Cause: The correct trigger mode is not set for the `toolChoice` parameter, causing the input parameter format to not match the plugin's expectations.
- Symptom: Incorrect units appear in quantitative fields of generated documents, such as replacing ㎡ with other units. Cause: The unit verification rule of the plugin is not enabled, or the context length configuration is too short to recognize the unit field.

## How to confirm the configuration is correct
- Upload a construction log template for a building construction project, trigger a plugin call, and check whether the generated content includes required fields such as project number and participating construction units.
- View the plugin running logs, confirm that the `functionCall` parameter is in the enabled state, and no format verification failure prompts appear.
- Adjust the project progress node tag, trigger a plugin call, and check whether the generated document matches the template requirements of the current progress stage.
- Verify that the units of quantitative fields are automatically filled correctly, and confirm that the reordering rule has sorted according to compliance requirements.
