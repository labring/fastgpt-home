# Document and Material Drafting for New Energy Development: HTTP Interfaces and External Systems

## What this type of data looks like
Document and material data for new energy development primarily comes from full-process project approval documents, engineering execution records, and compliance reports. Data sources include project approval systems, engineering management platforms, and compliance archives. Update frequency adjusts based on project milestones: weekly updates during the feasibility study preparation phase, daily updates during grid connection preparation. Single document lengths vary widely, from progress reports with hundreds of characters to feasibility study reports with tens of thousands of characters. Core fields include project ID, site latitude and longitude, installed capacity (unit: MW), approval document number, and submission date.

## Constraints Imposed by These Characteristics on HTTP Interfaces and External Systems
The wide variation in new energy development document data length, specialized units in fields, and fluctuating update frequency based on project milestones create multiple constraints for HTTP interface and external system integration. First, single document volume varies significantly. Interface request and response size limits must accommodate feasibility study reports with tens of thousands of characters to avoid truncating core compliance content. Second, fields include specialized formats such as latitude and longitude, and installed capacity (MW). Interface parameter validation must match corresponding data types and unit rules to prevent invalid values from being passed. Third, the high-frequency update requirement during the grid connection preparation phase requires flexible adjustment of interface call frequency, along with reasonable timeout and retry configurations to avoid external system rate limiting triggered by high-frequency requests.

## Configuration Settings
The following configurations apply to FastGPT v4.17.0, and support HTTP interface and external system integration for new energy development scenarios.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {API token assigned by external system}` | Matches the identity verification requirements of new energy development external systems, ensuring interface call permissions are valid |
| Request timeout duration | `300 seconds` | Adapts to the transmission and parsing duration of tens of thousands-character feasibility study reports and environmental impact assessment documents, preventing mid-transmission interruptions |
| `variables` | `{"project_id": "{{external.project_id}}", "installed_capacity": "{{external.capacity}}"}` | Maps exclusive new energy project fields returned by external systems, ensuring accurate project parameters are used for document drafting calls |
| `responseData` extraction rule | `Retain project ID, approval document number, and installed capacity fields` | Meets core compliance requirements such as grid connection approval and feasibility study review for new energy development documents, filtering non-essential content to improve interface efficiency |
| Retry threshold | `2 times` | Addresses temporary external system rate limiting, adapting to high-frequency call scenarios during the grid connection preparation phase |

## Three Common Configuration Mistakes
- An interface call returns the `AIPROXY_API_ENDPOINT or AIPROXY_API_TOKEN is not set` error. This occurs when external system authentication parameters are not configured correctly, and the corresponding key is not filled into the `Authorization` related configuration items.
- Slow queries or timeouts occur during interface calls. This occurs when the transmission volume of long new energy development documents is not accommodated, and the request timeout setting is too short, failing to reserve sufficient parsing time.
- Missing fields occur during knowledge base synchronization. This occurs when exclusive fields of new energy development documents are not mapped correctly, and core data such as project ID and installed capacity is not passed through the `variables` configuration items.

## How to Verify Configurations Are Correct
- Call the test interface, check if the returned `responseData` includes core fields of new energy development documents, confirming field mapping is correct.
- Simulate a single long document transmission, verify that the interface request is not truncated, confirming the timeout setting adapts to document volume.
- Trigger a high-frequency call scenario, check if the retry mechanism takes effect, confirming continuous errors are not triggered by rate limiting.
- View external system call logs, confirm that the `Authorization` authentication token is correctly carried.

The values provided are common starting points and should be measured against the operator’s own samples.
