# Document and Material Drafting for New Energy Development: Tool Calling and Plugins

## What the data for this category looks like
The documents and materials for new energy development originate primarily from internal project management systems, government approval platforms, and third-party testing institutions. Data update frequency shifts based on project phase. Feasibility study reports are updated weekly during project initiation. Safety acceptance documents and grid connection application materials are updated on demand during grid connection acceptance. Document structures combine fixed sections and dynamic fields. Fixed fields include project ID, installed capacity (unit: MW), construction location, and approval document number. Dynamic fields include on-site test data, environmental assessment attachment links, and similar items. Single-document length varies widely, from application letters with thousands of characters to feasibility study reports with hundreds of thousands of characters.

## What constraints these characteristics impose on the tool calling and plugins workflow
Decentralized data sources require integration with multiple interface sets. Tool calling must support cross-system data retrieval. Complex document structures and fields with specific units demand that plugins accurately match unique fields to prevent errors from general extraction logic. Wide variation in single-document length requires adaptive segmented processing logic to avoid API call timeouts. Irregular data update cycles mean tool calling must retrieve the latest data version in real time, and cannot rely on cached content.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| Tool call timeout duration | 120–180 seconds | New energy development document interfaces return large data volumes including long text content. Standard short timeout durations cannot complete full data retrieval |
| Field extraction rules | Map according to project-specific fields | New energy development documents include unique fields such as project ID and installed capacity. Corresponding mapping rules must be specified |
| `toolChoice` | auto | Adapt to different types of document drafting scenarios, automatically select matching tools to complete data processing |
| Plugin request retry count | 3 times | Address occasional temporary fluctuations in government approval interfaces, and ensure call success rates |
| Upload file size limit | 500–1000 MB | New energy development documents include large attachments such as CAD drawings and environmental assessment atlases, which require adaptation to large-capacity file upload requirements |
| `functionCall` | Force specification | For core approval field extraction scenarios, force tool calling to avoid deviations caused by large model autonomous selection |

## Three Common Configuration Errors
- Phenomenon: A "413 Request Entity Too Large" error is returned when calling the MinerU container interface. Cause: The upload file size parameter was not configured when starting the container. The default limit is 2 MB, which cannot adapt to the large attachments included in new energy development documents.
- Phenomenon: The HTTP request component calls successfully, but the extracted new energy-specific fields are empty. Cause: No specific field mapping rules were configured. The default extraction logic cannot recognize unique fields such as project ID and installed capacity.
- Phenomenon: Call timeout occurs after publishing as an API interface. Cause: The default timeout duration was not adjusted. The response duration of the new energy document interface exceeds the default threshold.

## How to Confirm Correct Configuration
- Initiate a test call for new energy development documents, check the tool call logs, and confirm that the specified unique fields are correctly extracted.
- Upload a new energy development document that includes typical attachments, check whether the plugin can process normally and return expected results.
- Call the published API interface, verify that the timeout duration setting matches the actual interface response duration.
- In the tool calling module of FastGPT v4.17.0, check the trigger records of the retry mechanism, and confirm that automatic retry works normally in abnormal scenarios.
