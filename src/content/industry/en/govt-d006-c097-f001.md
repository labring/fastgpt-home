# Document and Material Drafting for Nuclear Power Operations: HTTP Interfaces and External Systems

## What the data for this category looks like
Nuclear power operation document and material drafting data mainly comes from on-site operation terminals, safety inspection systems, and equipment ledger and procedure management systems. Data updates occur every 8 hours, aligned with shift cycles. Document structures are fixed, including fields such as equipment ID, operating condition parameters, inspection time, anomaly records, and approval nodes. Most units use standard engineering units like MPa, ℃, and hours. Single document length ranges from hundreds to tens of thousands of characters.

## What constraints these characteristics impose on HTTP interfaces and external systems
Fixed fields and standard engineering unit requirements for nuclear power operation data mean HTTP interface requests must carry standardized parameters that match business fields. This prevents parsing errors caused by incompatible parameters. The shift-based update rhythm limits external system data pull frequency to no more than once per hour. This avoids overusing system resources. The wide range of document lengths requires interfaces to support long-text context transfer. It also requires configuring reasonable parameters to limit the text volume per request, preventing timeouts. Multi-source data synchronization needs require interfaces to support data format conversion for different external systems. This adapts to the output formats of on-site equipment.

## Three Common Mistakes
- Phenomenon: When calling the `/api/v1/chat/completions` interface, the generated document does not include preset business fields. The status code is 200 but the content does not comply with nuclear power operation document specifications. Cause: The prompt template was not correctly embedded in the `variables` parameter, or business data was not passed to the context variables.
- Phenomenon: After an external system calls the interface, empty chat history is returned, and it is impossible to distinguish session content from different users. Cause: User-specific API keys were not used for authentication, or the `Authorization` parameter was not carried in the request to associate user identity.
- Phenomenon: Interface calls frequently trigger timeout errors, with a status code of 504. Cause: The request timeout was not set reasonably, and the document length passed in a single request exceeded the system processing limit, resulting in excessive processing delay.

## How to Verify the Configuration is Correct
- Call the interface and pass a known equipment ID and threshold parameters. Check if the response data includes the operating parameters of that equipment to confirm that the `responseData` parameter configuration is effective.
- Initiate requests using different API keys. Check if the returned chat history is only associated with the session corresponding to the current key to confirm that the session isolation rule configuration is effective.
- Simulate a single long-text request. Check if the interface response time meets the delay requirements of the business scenario to confirm that the timeout configuration is reasonable.
- Pass a preset prompt template and business data. Check if the generated document content matches the document format and field requirements of nuclear power operations.
