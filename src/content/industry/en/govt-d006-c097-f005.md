# Document and Material Drafting for Nuclear Power Operations: Tool Calling and Plugins

## What the data for this category looks like
Documents and materials for nuclear power operations originate primarily from unit operation logs, nuclear safety supervision reports, on-site operation tickets, emergency response records, and equipment operation and maintenance archives. Data updates trigger with on-site operations and events. Corresponding documents generate immediately after a single operation completes. Document structures include fixed fields: unit number, operation execution time, event classification, approver signature, and execution result record. Used units include megawatts (for unit power), hours (for operation duration), standard cubic meters (for gas emission volume), and other industry-specific units.

## Constraints on Tool Calling and Plugins From These Characteristics
Fixed fields in nuclear power operation documents require tool calls to accurately match required items such as unit number and execution time. Missing fields will make documents fail to meet nuclear safety compliance requirements. Industry-specific units require plugins to complete standardized unit conversion during data parsing and output. This prevents issues like confusion of power units. The large volume of long-term operation logs and multi-page reports requires tool calls to support segmented retrieval and context splicing. This stops the model from exceeding its context limit. Real-time updated on-site data requires plugins configured for event-triggered calls. This ensures document content matches current on-site status.

## Configuration Settings
The following configurations apply to FastGPT v4.17.0:

| `toolChoice` | `auto` | Adapts to multi-tool calling scenarios for nuclear power documents, automatically matches corresponding tools to complete field filling |
| `functionCall` | `enabled` | Triggers tool calling logic to realize real-time retrieval of operation and maintenance data and compliance verification |
| Tool call timeout period | 600 seconds | Nuclear power data needs to be retrieved across multiple intranet systems, reserve sufficient response time |
| Maximum number of returns per single tool call | First 8 entries | Avoids excessive data exceeding the context window, while covering core operation and maintenance fields |
| Document parsing trigger rule | Match by document type | Nuclear power documents have fixed formats, call corresponding parsing plugins by types such as operation tickets and safety reports |
| Context window limit | 8000–12000 token | Adapts to the processing requirements of long-term operation logs, calibrated based on actual measurements |

## Three Common Configuration Mistakes
- Symptom: Tool calls return `400 Bad Request` with a prompt for missing required fields. Cause: The fixed field requirements for nuclear power documents are not met, and required parameters such as unit number and execution time are not included in tool calls.
- Symptom: Locally deployed large models return no tool call results. Cause: The `functionCall` parameter is not configured correctly, or tool calling support is not enabled for the model.
- Symptom: Parsed result fields are empty after uploading nuclear power documents. Cause: No matching parsing plugin is configured for the document type, so nuclear power-specific fields and units cannot be identified.

## How to Verify Proper Configuration
- Submit a simulated nuclear power document drafting request. Confirm that the tool call automatically matches the correct tool, and returned results include required fields such as unit number and execution time.
- Review tool call logs. Confirm that the 600-second timeout threshold is not triggered, and the number of returned entries matches the first 8 entries setting.
- Upload a test document using nuclear power-specific formatting. Confirm that the parsing result correctly identifies industry-specific units such as megawatts and standard cubic meters.
- Run tests using a locally deployed large model. Confirm that the `functionCall` parameter works as expected, and tool calling logic triggers normally.
