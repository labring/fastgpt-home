# Document and Material Drafting for Civil Aviation Airports: HTTP Interfaces and External Systems
This document is written for FastGPT v4.17.0.

## What the data for this category looks like
Civil aviation airport document and material data primarily comes from three core business data sources: flight operation management systems, security inspection systems, and ground service scheduling systems. Data updates follow flight plan execution. Full updates for documents related to a single flight are completed between 12 hours before takeoff and 2 hours after landing. Documents use a standardized structured format, with five required fields: flight number, takeoff and landing time, station number, document type, and responsible team. The time field uses ISO 8601 standard format. Station numbers are 6-digit numeric codes. The character count for a single document typically falls between 800 and 1500 characters.

## What constraints these characteristics impose on HTTP interfaces and external systems
The multi-source data nature of civil aviation airport documents requires HTTP interfaces to adapt to the calling protocols of different business systems, increasing adaptation costs for external system integration. The real-time update rhythm requires interface timeout settings to match the flight scheduling time window, to avoid delays in document generation caused by timeouts. The requirement for structured fixed fields means request parameters must strictly match required items such as flight number and takeoff and landing time, otherwise corresponding documents cannot be generated. The character count range for single documents requires context parameters passed via the interface to adapt to this length, to avoid truncation and loss of critical business information.

## How to configure settings
| Configuration Item | Recommended Value | Rationale for This Setting |
| --- | --- | --- |
| `Authorization` | Bearer {Airport business system temporary token}, valid for 15 minutes | Adapts to the authentication rules of airport business systems, avoiding risks of long-term token leakage |
| `variables` | Contains three variables: flightNo, departTime, stationId, with values being valid values of corresponding business fields | Matches the structured field requirements of civil aviation airport documents, ensuring complete and valid parameters |
| `responseData` | Only returns the documentContent and updateTime fields, single data size does not exceed 1000 KB | Reduces transmitted data volume and improves interface call efficiency |
| Timeout Duration | 600 seconds | Matches the flight scheduling time window, avoiding delays in document generation caused by timeouts |
| Context Length | 800–1500 characters | Adapts to the character count range of single civil aviation airport documents, avoiding content truncation |

## Three common mistakes
- Symptom: Interface call returns 401 Unauthorized status code, unable to obtain document data. Cause: Temporary token generated by the airport business system is not used, or the token has expired.
- Symptom: Generated document content is missing flight number or takeoff and landing time information. Cause: The `variables` parameter does not pass the corresponding required fields, or the field format does not meet standard requirements such as ISO 8601.
- Symptom: Interface call times out, returning 504 Gateway Timeout error. Cause: The timeout setting is too short and does not match the flight scheduling time window, or the returned document data volume exceeds the limit.

## How to confirm the configuration is correct
- Call the configured HTTP interface, pass valid flightNo, departTime, and stationId parameters, and check that the returned response status code is 200 OK.
- Check whether the returned `responseData` contains complete documentContent and updateTime fields, with no redundant unrelated fields.
- Pass parameters for different flights, verify that the interface can correctly return document data for the corresponding flight, with no missing fields or content truncation.
- Call the interface 10 times consecutively, check that there are no 401 or 504 errors, confirming that the authentication and timeout configurations are effective.
