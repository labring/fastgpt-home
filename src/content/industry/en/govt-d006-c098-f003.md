# Document and Material Drafting for Civil Aviation Airports: Multi-turn Dialogue and Prompt Engineering

This document is written for FastGPT v4.17.0, addressing document and material drafting needs in civil aviation airport scenarios, and explaining configuration, constraints, and issue handling for multi-turn dialogue and prompt engineering links.

## What the data for this category looks like
Civil aviation airport document and material data mainly comes from operation manuals, air traffic control reporting templates, flight support process documents, passenger service notices, security inspection operation specifications, and similar sources. Data is updated twice annually in conjunction with flight season changes, and updated temporarily when new routes are launched or control regulations are adjusted. Most documents follow fixed formats, including fields such as flight plan number, takeoff and landing time, airport three-letter code, support equipment model, and more. Units include hours, passenger trips, meters, kilograms, and others. The length of a single document ranges from hundreds to thousands of characters.

## What constraints these characteristics impose on the "multi-turn dialogue and prompt engineering" link
The fixed format fields of civil aviation airport documents require exclusive entities such as airport three-letter codes and flight numbers to be accurately tracked in multi-turn dialogue, to avoid confusing information from different flights or airports. Data has a relatively high update frequency, so prompt engineering must include version verification logic to ensure referenced operation manuals or control regulations are the latest versions. The wide span of document lengths requires multi-turn dialogue to retain sufficient historical context, to avoid truncating key process descriptions. Documents for temporary control or special support require multi-round confirmation of details, and prompt engineering must guide users to supplement unspecified field information.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `messages` history length | 8000–12000 characters | Civil aviation airport documents are mostly long-form, requiring retention of sufficient historical dialogue and reference content to avoid truncating key process descriptions |
| `variables` bound fields | Airport three-letter code, flight plan number, takeoff and landing time | Used to bind exclusive entities in civil aviation scenarios, avoiding confusion of information from different flights or airports in multi-turn dialogue |
| `chatId` session isolation rule | Create per flight | Ensure that the context of document drafting sessions for the same flight is not interfered with by other sessions, avoiding cross-flight information confusion |
| Question optimization switch | Enabled | Automatically complete necessary format fields for vague document requirements, and guide users to supplement unspecified information |
| Single recall limit | Top 3 entries | Airport documents are mostly standard process documents; accurately recalling prior specifications meets requirements and avoids introducing irrelevant content |
| Response timeout threshold | 60 seconds | Adapt to the operating rhythm of airport operation and maintenance personnel, avoiding timeout errors due to excessive waiting time |

## Three common mistakes
- Phenomenon: Request Timeout error occurs during dialogue, with status code 408 or 504. Cause: No reasonable response timeout threshold set, or too many bound `variables` fields leading to context parsing timeout.
- Phenomenon: Preset form input items cannot be displayed in dialogue, and interactive fields are empty. Cause: No civil aviation scenario exclusive fields bound in `variables` configuration, or session not correctly associated with `chatId` leading to context loss.
- Phenomenon: Recalled document content does not match the current flight scenario. Cause: `chatId` not isolated per flight, leading to confusion of context from different flights, or single recall limit set too high, introducing irrelevant documents.

## How to confirm the configuration is correct
- Initiate a test dialogue, input "Draft a takeoff and landing support application for flight CA1234 at PEK airport", check if the `variables` fields for airport three-letter code and flight number are automatically bound in the dialogue.
- Initiate 10 consecutive document drafting requests for different flights, confirm that `chatId` isolation is correct for each session, and contexts do not interfere with each other.
- Wait 60 seconds and check the dialogue response, confirm no timeout errors occur.
- Upload an airport operation manual document, test if the recalled content matches the current dialogue's document requirements.
