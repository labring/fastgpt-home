# Document and Material Drafting for Civil Aviation Airports: Workflow Orchestration

## What Data Looks Like for This Category
Civil aviation airport documents and materials mainly come from four categories: operation support ledgers, air traffic control coordination documents, passenger service forms, and safety compliance manuals. Operation ledgers and real-time support forms update in real time with flight takeoffs and landings. Compliance manuals and fixed templates update quarterly or annually.

Documents are split into two types: standardized templates and customized forms. Standardized templates include flight delay notices, safety rectification notices, and similar items. Customized forms include bridge dispatch sheets, passenger complaint handling sheets, and similar items. Core fields include flight number, takeoff and landing time, support node, responsible department, approver, and timestamp. Units include flight shifts, minutes, passenger counts, and others.

## What Constraints These Characteristics Impose on Workflow Orchestration
The above data characteristics impose three core constraints on workflow orchestration.
First, real-time updated ledgers and forms require workflows to support real-time data source pulling, and avoid using static cached data.
Second, dynamic fields in customized forms require workflows to support global `variables` binding to automatically fill core operation data.
Third, wide variation in document length — from tens of characters for complaint sheets to hundreds of pages for safety manuals — requires workflow context processing modules to have flexible adaptation capabilities.
Additionally, civil aviation documents require audit trail retention. Workflows must record execution status and operator information for each node.

| Configuration Item | Recommended Value | Basis for This Setting |
| --- | --- | --- |
| Question Optimization | Keep flight number and support node keywords, delete redundant modifiers | Core information of civil aviation documents is flight, responsible department, and time. Optimization improves retrieval accuracy |
| Single Search Limit | Top 8 entries | Civil aviation support documents have few entries per category. Top 8 entries cover core reference content |
| Maximum Context | 1200–1500 characters | Most civil aviation documents range from 800 to 1600 characters per copy, which fits conventional processing scope |
| `variables` | Bind flight number and takeoff and landing time fields | Civil aviation documents require dynamic filling of core operation data. Variables enable automatic assignment |
| `nodeId` | Bind unique identifier of approval node | Workflows need to jump based on approval status. Node ID accurately locates execution branches |
| Timeout Setting | 600 seconds | Some civil aviation documents require cross-system ledger retrieval. 600 seconds covers most cross-system query durations |

## Three Common Mistakes
- Symptom: Workflow terminates directly after reaching the knowledge base search node, with no subsequent output. Cause: The flight number field in `variables` is not bound as a retrieval keyword, leading to empty retrieval parameters and triggering node termination.
- Symptom: Workflow runtime displays "Cannot convert undefined or null to object". Cause: The execution order of nodes is not specified via `nodeId`, leading the system to fail to recognize node dependencies and throw an empty object error.
- Symptom: Historical conversation records cannot be passed as variables to subsequent code execution nodes. Cause: Historical conversation content is not mounted to global `variables`, leading the code execution node to fail to read corresponding data.

## How to Confirm Configuration Is Complete
- Manually enter a valid civil aviation flight number and support node, trigger workflow execution, and check if each node runs in the preset order.
- View workflow logs to confirm that flight number and takeoff and landing time fields in `variables` are correctly filled with no null values.
- Simulate different approval node statuses, check if the workflow jumps to the corresponding link via the branch specified by `nodeId`.
- Test cross-system data retrieval, confirm that retrieval is completed and valid results are returned within 600 seconds.
