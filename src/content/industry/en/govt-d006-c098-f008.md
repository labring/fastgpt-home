# Document and Material Drafting for Civil Aviation Airports: Document Parsing and Chunking

## What the Data for This Category Looks Like
This category of data mainly comes from daily documents of airport operation management departments, including flight support sheets, passenger service manuals, safety operation procedures, ground crew scheduling sheets, material application ledgers, and more. The update rhythm follows daily operations: flight plan documents are updated daily, and professional procedure documents are revised quarterly or annually. Document structures include plain text long paragraphs, structured tables, and formatted PDF scans. Fields cover flight numbers, takeoff and landing times, support posts, passenger trips, material weights, and other items, with specific units such as hours, tons, and passenger trips.

## What Constraints These Characteristics Impose on Document Parsing and Chunking
The multi-structure nature of civil aviation airport documents requires that document parsing does not damage the association between tables and paragraphs. Otherwise, structured data such as scheduling sheets and material lists cannot be correctly identified. Frequently updated documents require the parsing process to have sufficient response speed, to avoid data failing to be stored in the database due to parsing timeouts. Specific fields and units require retaining contextual associations during chunking. Complete cross-field business logic must not be split; for example, the header and specific scheduling data of a scheduling sheet cannot be split into two independent chunks. Large scanned PDF files will occupy more parsing resources, so relevant configurations need to be adjusted to adapt to file size and parsing duration.

## How to Set the Configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `chunkSize` | 800–1200 characters | Civil aviation airport documents mostly contain tables and long procedure texts. This range can retain the complete semantics of a single process or a single table |
| `chunkSplitter` | Mixed splitting by table and paragraph | Airport documents include mixed structures such as scheduling sheets and safety procedures. Mixed splitting avoids damaging table integrity |
| `customPdfParse` | Enabled | In FastGPT v4.17.0, enabling this option retains the original layout and table structure of formatted PDFs |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | Airport operation documents may include multi-page scans or large scheduling datasets. This upper limit covers conventional upload requirements |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600 seconds | Parsing large airport documents takes a long time. This duration prevents parsing from being interrupted midway due to timeout |
| `chunkSettingMode` | Manual configuration | Parameters need to be adjusted according to the table and long text characteristics of airport documents. Manual configuration provides greater flexibility |

## Three Common Mistakes
- Uploading an Excel file containing post scheduling results in empty data processing. The cause is that structured table parsing mode is not enabled, and the default text chunking logic fails to recognize the association between Excel columns and cells
- Uploading a large safety procedure PDF results in overly slow vectorization. The cause is that the `chunkSize` parameter is not adjusted. Using an excessively small chunk length generates an excessive amount of chunk data, increasing the vectorization calculation load
- After local deployment, uploading airport operation documents for the first time results in empty data processing. The cause is that `PARSE_FILE_TIMEOUT_SECONDS` is not configured with a sufficient duration. Large document parsing is terminated by the system before completion

## How to Confirm the Configuration Is Set Correctly
- Upload an airport document containing a scheduling table, and check whether the parsed data retains the column and row structure of the original table
- Upload a single airport safety manual PDF not exceeding 1000 MB, and confirm that there are no error prompts after the parsing progress bar completes
- Adjust `chunkSize` to the 800–1200 character range, compare the number of chunks and parsing duration of the same document, and confirm that the results meet expectations
- After enabling `customPdfParse`, check whether the parsed text retains the title hierarchy and format annotations of the original document

The values provided here are common starting points and should be measured against the reader's own samples.
