# Document and Material Drafting for Oil and Gas Exploration and Development: HTTP Interfaces and External Systems

## What the data for this category looks like
Oil and gas exploration and development documents and materials mainly come from on-site operation systems, geological databases, and third-party exploration reports. Data updates are triggered according to single-well operation and block evaluation nodes, and are synchronized immediately after a single operation is completed. The document structure includes four modules: operation number, operation period, core geological parameters, and operation conclusion. Core fields include well depth (unit: meter), formation pressure (unit: megapascal), and permeability (unit: millidarcy). The character count of a single document varies widely, with no fixed uniform length.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
The naming and format of core fields such as operation number and well depth follow strict industry specifications. Request parameters for HTTP interfaces must fully match the field rules of the target system, otherwise data interaction cannot be completed. The immediacy of data updates requires the interface timeout period to adapt to the synchronization window of on-site operations. An overly long timeout setting will occupy system resources, while an overly short one will cause failed incomplete synchronization requests. The wide variation in document character counts requires limiting the number of documents per single request during batch calls to avoid exceeding the load limit of the target interface. Differences in the format of third-party exploration reports require the interface to support multi-type input parsing, and the pre-verification link must cover common format exception scenarios.

## How to set configurations
| Configuration Item | Recommended Approach | Basis for This Approach |
|---|---|---|
| `Authorization` | Account and password string in Basic Auth format, encoded and placed in the request header | Most external systems for oil and gas exploration and development use basic authentication to ensure data security, which complies with industry general specifications |
| `variables` | Pass fixed variable names of core business fields such as well number and operation period | Match the field rules of the target system to avoid interaction failures caused by parameter mismatches |
| `responseData` | Extract the operation conclusion field in the returned result as the context for document drafting | Quickly obtain valid data for generating standardized exploration materials |
| Batch execution node | No more than 20 documents per single request, with an interval of 10 seconds | Adapt to the load and synchronization rhythm of oil and gas exploration documents, calibrated based on actual measurements |
| API call timeout period | 60-120 seconds | Adapt to the synchronization window of on-site operations, avoid timeouts or excessive resource occupation |
| File upload parameters | Configure allowed document formats as PDF and TXT, with a maximum size of 1000 MB | Match the common format and size range of oil and gas exploration documents |

## Three Common Misconfigurations
- Issue: HTTP request returns 401 Unauthorized error, interface call fails. Cause: The encoded string for Basic Auth configured in the `Authorization` field is not used correctly, and the account and password format does not meet the authentication rules of the target system.
- Issue: When running the API call workflow, the batch execution node does not complete all loop steps, but it runs normally in online debugging. Cause: The API call timeout period is set too short, and the total execution duration of the batch node exceeds the limit, causing the workflow to be forcibly interrupted.
- Issue: After the interface call workflow is completed, the running data field in the conversation log is empty. Cause: The field to be extracted is not specified in the `responseData` configuration, so the system does not collect valid running data.

## How to Confirm Proper Configuration
- Initiate a single HTTP interface call, check the status code of the returned result. After confirming the status code meets expectations, verify whether the returned fields include the preset business data.
- Enable online debugging mode, run the workflow containing the batch execution node, confirm that all loop steps are completed normally with no error or interruption prompts.
- After calling the API interface, check the conversation log, confirm that the fields configured in `responseData` are correctly filled with no null values.
- Use the FastGPT v4.17.0 workflow editor to test the file upload function, confirm that documents passed through the API can be correctly read by the agent for document drafting.
