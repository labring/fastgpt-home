# Document and Material Drafting for Oil and Gas Exploration and Development: Tool Calling and Plugins
## What Data for This Category Looks Like
Data for oil and gas exploration and development document and material drafting comes from exploration project approval reports, real-time drilling logs, oil test analysis reports, reserve assessment documents, and compliance approval documents. There are two data update cadences: full batch updates of all reports after a single exploration project is completed, and daily real-time log updates per well during routine drilling operations. Most documents have a multi-chapter nested structure, including three main parts: geological parameters, engineering operation data, and attachment materials. Core fields include well ID, operating depth (unit: meters), permeability (unit: millidarcy), recoverable reserves (unit: tons), and metadata such as operating team ID and observation date.

## Constraints for Tool Calling and Plugins
Data is isolated per project and contains many specialized fields. Tool calling must bind to the exclusive knowledge base for the corresponding project to avoid cross-project data interference. Document length varies significantly, from hundreds of characters for drilling logs to tens of thousands of characters for reserve reports. Tool calling must support parsing documents of different lengths. Specialized units and field formats are fixed. Plugins must include standardized field mapping rules to avoid unit errors or field misalignment in extraction results. Real-time logs require frequent calls, while batch reports require high-concurrency parsing. Tool calling must support switching between synchronous and asynchronous modes on demand.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Knowledge Base Binding Scope | Only the exclusive knowledge base for the current exploration project | Oil and gas exploration data is isolated per project to avoid cross-project data confusion |
| `toolChoice` | Enforce tool calling | Specialized document drafting requires precise extraction of exploration fields to avoid incorrect content generated by the model |
| Tool Call Timeout | 120–180 seconds | Single exploration report documents have large length, so parsing and retrieval require longer time |
| Field Mapping Rules | Bind preset specialized fields such as well ID, permeability, and reserves | Oil and gas data has fixed specialized field formats, and unified mapping can improve extraction accuracy |
| SQL Query Timeout | 60 seconds | The single-table data volume of the exploration log database is moderate, and a reasonable timeout can ensure query completion |

## Three Common Configuration Mistakes
- Calling the API with incorrect knowledge base parameters returns empty fields or permission errors. The cause is failure to correctly bind the exclusive knowledge base ID of the current exploration project to the workflow global variable, or only configuring the global variable without specifying the project exclusive identifier.
- After configuring a MySQL database connection, SQL extraction fails, returning empty results or connection timeouts. The cause is failure to configure the access whitelist for the exclusive oil and gas exploration data database, or using a database account without sufficient permissions.
- Continuous conversation requests cannot interrupt generation, and subsequent requests wait in queue. The cause is failure to enable asynchronous call configuration, or failure to set a request timeout interrupt mechanism.

## How to Verify Successful Configuration
- View the workflow configuration page, confirm that the knowledge base binding scope is set to the exclusive knowledge base for the current exploration project, with no cross-project associated configurations.
- Trigger a test call, check the tool call log to confirm that the `toolChoice` parameter is active and the preset specialized field extraction tool is called.
- Run an SQL query test, check that the returned results include correct exploration data fields with no unit or format errors.
- Send two consecutive test requests, verify that the previous generation process can be interrupted and a new request can be executed.

The values provided are common starting points and should be measured against the reader's own samples.
