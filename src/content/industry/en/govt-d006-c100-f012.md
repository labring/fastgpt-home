# Document and Material Drafting for Oilfield Engineering Services: Deployment and Upgrade

## What this category of data looks like
Oilfield engineering service documents and materials originate primarily from well site operation logs, construction plans, acceptance reports, safety compliance documents, and equipment maintenance records. Data updates per single construction job node, and new document batches generate after each job completes. Document structures include fixed metadata fields: operation number, well ID, construction time, formation depth (unit: meters), construction duration (unit: hours), plus structured construction parameters, material lists, and compliance clauses. Some documents include high-definition construction drawing scans, with single document sizes reaching tens of megabytes.

## What constraints these characteristics impose on deployment and upgrade
Fixed metadata fields for oilfield engineering documents require precise matching of the data source’s table structure during deployment, to avoid loss of critical business identifiers in vector storage. Data updates occur frequently and batches are scattered, so adjust incremental sync trigger rules during upgrades to prevent excessive intranet bandwidth usage from full syncs. Large-volume drawing files require configuring appropriate object storage paths to avoid local storage overflow. Specialized terminology and fixed units require the vector model to retain field semantic associations during generation, so configure industry-specific word segmentation rules in advance for adaptation.

## Three common mistakes
- Pulling the Redis image fails when executing `docker-compose up -d`, with logs showing public network image repository connection timeout. The cause is failure to configure the Alibaba Cloud intranet mirror address; oilfield intranets restrict public network access, leading to failed image pulling.
- Unable to select a created Deepseek channel model within the application, with an empty model list. The cause is failure to save the associated configuration of the channel model in the application’s AI model settings, or incorrect `MONGODB_URI` configuration leading to failure to read channel model data.
- The reranking function outputs nothing after deploying bge-reranker, with backend logs showing model path errors. The cause is incorrect mapping of the local model directory in the docker-compose.yml environment configuration, so the container cannot load the specified reranking model file.

## How to confirm the configuration is complete
- Execute the `docker ps` command, confirm that the redis, PostgreSQL, FastGPT main service, and bge-reranker containers are all in running state.
- Access the backend management address corresponding to `FE_DOMAIN`, log in and enter the data source management page, perform connection tests for `PG_URL` and `REDIS_URL`, confirm the test results show success.
- Upload an oilfield well site operation log document, trigger the vector generation task, check that the backend task queue has no errors and the task status is completed.
- Enter the channel model management page, confirm that the created Deepseek model is displayed normally, and it can be selected normally in the AI model settings of the application editing page.
