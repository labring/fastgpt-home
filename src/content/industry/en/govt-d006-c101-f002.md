# Document and Material Drafting for Port and Shipping: Vector Models and Indexes

## What Data Looks Like for This Category
Port and shipping documents and materials mainly come from port operation systems, vessel scheduling platforms, maritime declaration portals, and cargo owner declaration systems. Update frequencies are categorized as real-time (such as berth scheduling instructions, temporary operation notices), shift-based (operation ledgers for three daily shifts), and monthly (monthly throughput reports). Most documents include fixed fields: vessel name, voyage number, berth number, cargo category, billing weight (unit: ton), operation time, alongside long-text operation descriptions and compliance declaration notes. Some documents also contain text fragments transcribed from structured attachments.

## Constraints for Vector Models and Indexing
The multi-source, heterogeneous nature of port and shipping documents requires the vector model and index workflow to support mixed embedding of multiple fields, preventing single semantic representations from deviating from business scenarios. Real-time updated operation instructions and ledgers require indexes to support incremental refresh, reducing resource consumption from full index reconstruction. Single documents often contain hundreds to thousands of words of operation descriptions, which may exceed the token limit of basic vector models. This necessitates designing segmentation rules for long texts. Structured fields such as cargo weight and berth number have clear semantic features, so separate embedding weights must be configured to strengthen business relevance. Documents with different update frequencies need to adapt to differentiated index update strategies, balancing retrieval timeliness and resource utilization.

## Configuration Settings
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Most long-text operation descriptions in port and shipping documents are under 1,000 words. This range balances semantic completeness and embedding efficiency |
| Overlap Length | 100–150 characters | Prevents loss of contextual association after long text segmentation, and adapts to the coherent semantics of port operation descriptions |
| Similarity Threshold | 0.72–0.78 | Semantic similarity of port business terms is relatively high. This range filters low-relevance results while retaining business matching items |
| Single Retrieval Upper Limit | Top 8 entries | Port document retrieval needs to cover relevant documents of the same voyage and same berth. 8 entries meet multi-dimensional business association requirements |
| `defaultToken` | 512 | Adapts to the default input limit of basic vector models, ensuring embedding stability for structured fields |
| `maxToken` | 4096 | Covers the post-segmentation token count of most port long-text operation descriptions, avoiding truncation of key business information |

## Three Common Misconfigurations
- Issue: A 404 status code is returned when configuring an external embedding model. Cause: The model's interface path and request parameter format were not correctly matched. Professional embedding models commonly used in port and shipping business require additional configuration of a dedicated interface prefix.
- Issue: Only one GPU card is utilized during index construction, and the second 3090 card is not scheduled for use. Cause: Multi-GPU device mapping was not specified in the deployment configuration, causing the system to only recognize the default graphics card resource.
- Issue: Content truncation prompts appear when importing large operation ledger documents. Cause: The `maxToken` parameter was not adjusted. The default token limit cannot cover the post-segmentation content of port documents.

## How to Verify Successful Configuration
- Upload a single port operation description document, review the post-embedding segmentation results, and confirm that the chunk length and overlap length align with the semantic coherence of business documents.
- Start an index construction task, check GPU/CPU resource usage via the system monitoring panel of FastGPT v4.17.0, and confirm that the multi-GPU configuration has taken effect (if using multi-card deployment).
- Initiate a document retrieval for a specific voyage, review the similarity distribution of returned results, and confirm that the threshold configuration filters irrelevant documents.
- Test the external embedding model call link, and confirm that the vector data format returned by the interface matches the system requirements.

The values provided are common starting points and should be measured against the reader's own samples.
