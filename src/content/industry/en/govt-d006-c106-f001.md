# Document and Material Drafting for Coal-Electric Integration: HTTP Interfaces and External Systems

## What this category of data looks like
Document data for coal-electric integration scenarios primarily originates from internal production scheduling systems, coal purchase and sales ledgers, and power generation operation reports. Data is updated per production shift, with multiple archived documents generated daily. Document structures include fixed fields such as unit number, coal received quantity, unit load, power generation duration, and compliance check items. Coal received quantity uses tons as its unit, unit load uses megawatts, and power generation duration uses hours. Most documents are PDF or Word files with structured fields, and some are synced to internal enterprise databases. This page is compatible with FastGPT v4.17.0.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" workflow
Since data comes from production systems and ledgers on the enterprise internal network, HTTP interfaces must be configured with internal network access permissions. Direct connection via public domain names is prohibited. The fixed document structure requires request parameters to strictly match preset field names, to avoid data extraction failures from field mismatches. The shift-based update rhythm means interface polling intervals must align with production shift cycles. Do not set request intervals too short or too long. The multiple supported document formats require interfaces to pull PDF and Word attachments, with additional configuration for format parsing adaptation parameters.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer enterprise internal API key` | Internal interfaces require authentication to prevent unauthorized access |
| `variables` | Bind preset field variables such as unit number, coal received quantity | Match the fixed field document structure of the scenario to ensure accurate data extraction |
| Request timeout | 600 seconds | Internal data pulling typically takes 300-500 seconds, reserve sufficient buffer time |
| `responseData` | Extract structured fields from the first 5-7 matching documents | The number of archived documents generated per shift typically falls within this range, calibrated based on actual testing |
| Format parsing adaptation | Enable PDF and Word format support, single file size no more than 1000 MB | Single documents in this scenario typically do not exceed this size to avoid request overload |

## Three common configuration errors
- Symptom: HTTP response returns a 200 status code, but downstream extracted variables are empty. Cause: The correct field extraction path was not specified via the `responseData` configuration item, or request fields do not match the preset fields in the scenario.
- Symptom: Network connection failure error logs appear when starting container services. Cause: Internal network access permissions are not configured, and attempting to access public network interfaces prevents connection establishment.
- Symptom: Interface requests are forcibly terminated within 300 seconds. Cause: Request timeout is set too short, not matching the actual time required for internal data pulling.

## How to confirm the configuration is complete
- Manually trigger an HTTP request in the FastGPT v4.17.0 workflow, view the returned response body, and verify that the extracted fields configured in `responseData` match the preset fields of scenario documents.
- Check that the key configured in `Authorization` matches the authentication format required by the internal interface, to ensure no format errors exist.
- Initiate requests at the simulated production shift time interval, to confirm the interface can normally pull document data for the corresponding time period.
- Enable format parsing logs, to confirm that PDF and Word documents can be properly identified and their fields extracted.

The values provided are common starting points and should be measured against the reader's own samples.
