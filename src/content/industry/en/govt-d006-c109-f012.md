# Document and Material Drafting for Power Grid Enterprises: Deployment and Upgrade

## What this category of data looks like
Power grid enterprise document and material drafting involves multiple types of business documents. Sources include maintenance and operation reports, dispatch orders, safety regulations, and project submission materials. Document update cadence falls into two categories: routine operation type (updated daily or weekly) and major project type (updated periodically). Most documents use fixed template structures, with dedicated fields such as equipment ID, voltage level, maintenance team, and operation duration. Units include kV, MW, and hours. Some non-standard documents such as research reports have flexible structures, but must link to specific power grid business nodes.

## What constraints these characteristics impose on deployment and upgrade
Fixed templates and dedicated fields require support for custom knowledge base tags and field mapping during deployment, to adapt to classification and parsing of different business documents. Differences in document update frequency require compatibility with both incremental sync and full update modes during upgrades, to avoid repeated full data sync consuming system resources. Document lengths vary widely: from hundreds-of-word maintenance work orders to tens-of-thousand-word project reports. This requires chunking and retrieval configurations to have flexible adjustment space. Power grid data involves production safety and compliance requirements. All storage and database configurations are limited to internal network environments to prevent unauthorized access.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `STORAGE_S3_ENDPOINT` | `Internal network S3 storage node address, e.g. http://10.10.10.10:9000` | Power grid documents contain sensitive production data, internal storage complies with security and compliance requirements |
| `MONGODB_URI` | `Internal network MongoDB cluster connection string, configured with read-write separation` | Document data volume grows with maintenance frequency, read-write separation ensures retrieval performance |
| `REDIS_URL` | `Internal network Redis cluster address, set 1800-second expiration time` | Cache document metadata and retrieval results to reduce database access pressure |
| `DB_MAX_LINK` | `800–1200` | Adapt to concurrent retrieval requests for power grid documents, avoid exhausting database connections |
| `PG_URL` | `Internal network PostgreSQL address, configured with read-only replica` | Store structured work orders and dispatch data, ensure efficient structured queries |
| `FE_DOMAIN` | `Internal network domain, e.g. fastgpt.grid.local` | Only accessible via internal network, complies with power grid enterprise network security specifications |

## Three Common Mistakes
- Issue: After upgrading FastGPT v4.17.0, the same power grid work order CSV file fails to chunk normally, and a field parsing error prompt is returned. Cause: The structured document parsing logic in the new version was adjusted, and the non-standard power grid-specific field format included in the legacy CSV was not compatible.
- Issue: Pulling the fastgpt-minio image results in slow download speeds, eventually triggering a timeout error. Cause: No internal network image acceleration address was configured, and pulling public network images directly led to insufficient cross-region bandwidth.
- Issue: The privately deployed knowledge base interface has no image dataset add entry. Cause: The `FILE_TOKEN_KEY` parameter was not configured correctly, or the image storage directory was not mounted, causing image upload-related functions to remain disabled.

## How to Confirm the Configuration Is Successful
- Access the configured internal network `FE_DOMAIN` address, confirm that the FastGPT console loads normally with no page loading errors.
- Upload a test power grid maintenance work order CSV file, confirm that dedicated fields such as equipment number and voltage level can be parsed normally, and chunking is completed without parsing errors.
- Call the storage interface corresponding to `STORAGE_S3_ENDPOINT`, upload a test document file, confirm that it can be stored and read normally.
- Check the monitoring indicators corresponding to `REDIS_URL`, confirm that the cache connection count stays within a reasonable range, with no connection overflow.
