# Document and Material Drafting for Grain Reserve: HTTP Interfaces and External Systems

## What the Data for This Category Looks Like
The data for grain reserve document and material drafting mainly comes from internal warehouse management systems, quality inspection systems, and superior transfer notices. The data includes fixed required fields such as warehouse code, grain type, inbound batch, inventory weight (unit: ton), approval document number, storage cycle, etc. The structure of each document is uniform, with no custom extension items. Inventory data is updated in real time with inbound and outbound operations. Monthly summary reports are updated according to the natural month. The length of a single document ranges from hundreds to thousands of characters, and core fields cannot be missing.

## Constraints Imposed on HTTP Interfaces and External Systems
The fixed field structure requires that HTTP interface request parameters must include required items such as warehouse code and grain type. Otherwise, the placeholders of the document template cannot be matched, resulting in missing core information in the generated content. Real-time updated inventory data requires the interface to support low-latency queries, to avoid generated document data lagging behind actual inventory status. The difference in document length requires the interface response body to adapt to variable-length returned data. The `variables` parameter can pass dynamic field values to adapt to document requirements in different scenarios. Grain reserve data is internal sensitive information, which requires strict permission verification for the interface to prevent unauthorized calls from leaking storage-related information.

## How to Configure the Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${Internal Warehouse System API Key}` | Grain reserve data is sensitive internal data. Access permissions are verified via standard Bearer tokens to prevent unauthorized calls |
| `variables` | `{"warehouseCode": "WH001", "grainType": "corn", "batchNo": "202403"}` | Pass required fields such as warehouse code, grain type, and batch number to match the placeholders of the document template and ensure accurate generated content |
| `responseData` | `Object containing stockWeight (unit: ton), approvalNo, inspectionResult` | Map the core fields of grain reserve documents to ensure that the returned data can be directly used for document splicing without additional processing |
| Request timeout | `600 seconds` | Grain reserve data query involves multi-system linkage. 600 seconds covers the time required for batch data pulling and avoids mid-process interruptions |
| Retry count | `first 2 times` | Network fluctuations may cause interface call failures. Limited retries can improve call success rates while avoiding repeated triggering of duplicate document generation |
| Response data format | `Standard JSON format` | Adapt to the parsing logic of FastGPT v4.17.0 to ensure that the extracted fields can be directly used for document template filling |

## Three Common Mistakes
- Phenomenon: The client actively closes the connection after calling the HTTP interface, and the generated document draft is not saved to the database. Cause: The interrupt callback logic is not configured. FastGPT waits for the interface request to complete before writing data, and directly closing the connection will cause incomplete document data to be lost.
- Phenomenon: The generated document lacks core information such as inventory weight, and the fields are displayed as template placeholders. Cause: The required fields are not specified via the `responseData` configuration, causing FastGPT to fail to extract the corresponding data from the interface return.
- Phenomenon: The interface call returns a 401 unauthorized error. Cause: The `Authorization` parameter format is incorrect, the Bearer prefix is not used, or the key is invalid.

## How to Confirm the Configuration Is Correct
- Call the configured HTTP interface, and verify that the returned `responseData` includes preset core fields such as warehouse code and inventory weight.
- View FastGPT system logs to confirm that the `Authorization` parameter verification passes, and no unauthorized related error messages are present.
- Generate a test document using the real data returned by the interface, and confirm that all template placeholders are correctly replaced.
- Simulate multiple interface calls in a short time window to confirm that the request timeout and retry configuration take effect, and no consecutive call failures occur.

The values provided are common starting points and must be evaluated against local samples.
