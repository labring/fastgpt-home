# Document and Material Drafting for Shipbuilding: HTTP Interfaces and External Systems

## What this category of data looks like
Shipbuilding document and material drafting data primarily originates from ship design drawing libraries, construction process logs, classification society compliance documents, and production work order systems. Data updates are triggered by construction batches, with daily updates aligned to process nodes during a single ship’s construction cycle. Document structures fall into three categories: standardized technical parameter tables, process execution records, and inspection reports. Core fields include ship name, construction number, process name, inspection date, and qualification status. Most units use standard industrial units recommended by the International Maritime Organization, such as meters, kilowatts, and hours.

## Constraints imposed on HTTP interfaces and external systems
Individual shipbuilding documents can reach thousands of characters in length, and often include binary file streams such as drawings and inspection photos. This requires HTTP interfaces to support multipart form data transmission. Standardized core fields mean interface request parameters must strictly match fixed fields like ship name and construction number, with no arbitrary adjustments. The data update rhythm tied to process nodes requires interfaces to support targeted pulling by construction batch and process ID, to avoid bandwidth consumption from full-scale pulling. Transmissions of binary files need reasonable timeout thresholds configured to prevent interruptions during large file transfers.

## Three common configuration mistakes
- Phenomenon: When the HTTP interface returns binary drawing or photo streams, the return result is empty or has abnormal formatting. Cause: `responseData` is not configured to support binary mixed responses, and only JSON format data is parsed.
- Phenomenon: After calling the external document interface, logs show incomplete response fields or truncated error messages. Cause: Parameter transmission length limits are not properly configured, causing core fields of long documents to be truncated during requests.
- Phenomenon: When pulling shipbuilding documents in batches, interface calls frequently trigger timeout errors. Cause: Timeout thresholds adapted to large file transfers are not set, or targeted pulling by construction batch is not used, leading to timeout during full-scale data pulling.

## How to confirm configurations are correct
- Initiate a test request for a single document, check that the returned parameters include preset core fields such as ship name and construction number, and that the field format matches results returned by the external system.
- Upload or pull documents that include drawings and photos, confirm that binary files can be parsed normally and associated to the corresponding document entries.
- Review interface call logs, confirm there are no frequent timeout errors, and that response data is complete without truncation.
- Initiate pull requests for different construction batches, confirm that only document data for the corresponding batch is returned, with no redundancy or omissions.
