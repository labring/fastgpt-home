# Document and Material Drafting for Shipbuilding: Multi-turn Dialogue and Prompt Engineering
This document is written based on FastGPT v4.17.0.

## What the data for this category looks like
Document and material data for shipbuilding mainly comes from ship design drawings, block construction process cards, classification society specification documents, production scheduling tables, block inspection reports, and similar sources. The data update rhythm adjusts based on the construction phase. Core parameters such as ship type and main dimensions are updated once a week during the design phase. Production progress, welding inspection records, and similar content are updated daily during the block construction phase.
Document structures include fixed fields: ship type number, ship length (meters), draft depth (meters), steel plate thickness (millimeters), inspection batch number, process sequence number, and similar items. Some long documents such as final assembly process cards can reach thousands of characters per single section. These documents must strictly follow the format requirements of professional classification societies, with no arbitrary adjustment of field order or units.

## What Constraints These Characteristics Impose on Multi-turn Dialogue and Prompt Engineering
Scattered data sources for shipbuilding documents require multi-turn dialogue to gradually align professional fields across different documents, avoiding mismatches between ship type parameters and process requirements. Frequently updated production data requires dynamic pulling of the latest content during dialogue. Static knowledge base caching cannot be relied on, and each dialogue must ensure access to the latest production schedules and inspection records.
Strict requirements from professional standards mean prompts must explicitly lock industry-standard units. This prevents non-standard expressions such as mixing meters and millimeters, or tons and kilograms in outputs.
The existence of long documents requires limiting the cumulative length of the `messages` array in multi-turn dialogue, to avoid exceeding the model's processing limit and causing key parameters to be truncated.

## How to Configure the Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Maximum Context Length | 8000–12000 characters | Matches the per-section length of shipbuilding documents and the cumulative content of the `messages` array, avoiding truncation of professional parameters |
| Single Recall Limit | Top 6 entries | Adapts to the recall volume of scattered process, specification, and drawing data, avoiding redundant information interfering with dialogue logic |
| Variable Binding Toggle | Enabled | Used to bind dynamic fields such as ship type number and block number, ensuring parameter consistency across multi-turn dialogue via the `variables` parameter |
| Query Optimization | Calibrated based on actual testing | Adapts to shipbuilding professional terminology, optimizing alignment and understanding of dialogue context |
| Context Cache Duration | 3600 seconds | Matches the daily work cycle of the shipbuilding phase, preventing continuous dialogue interruptions caused by cache expiration |

## Three Common Mistakes
- Phenomenon: Dialogue output carries a large number of format symbols such as # and *, which cannot be displayed normally on external channels. Cause: The native Markdown format switch for dialogue output is not turned off, causing document annotation symbols to be returned directly.
- Phenomenon: No associated knowledge base identification field is returned when calling the dialogue interface. Cause: The return option for knowledge base reference logs is not enabled in the configuration, and the `variables` parameter is not correctly bound to associate the metadata of the corresponding knowledge base.
- Phenomenon: Image URLs uploaded to the knowledge base cannot be displayed normally in dialogue. Cause: The image URL is not converted to the absolute path format required by the platform, and the prompt does not explicitly require returning accessible image links.

## How to Confirm the Configuration Is Correct
- Initiate a multi-turn dialogue containing ship type parameters and process requirements, check whether the output uses unified engineering units.
- Call the dialogue interface, check whether the returned results include relevant identification fields of the associated knowledge base.
- Upload a knowledge base document with an image URL, initiate a dialogue containing image descriptions, check whether accessible image links can be returned correctly.
- Test continuous dialogue with a `chatId`, check whether the context correctly retains previous ship type parameters and process requirements.
