# Document and Material Drafting for Shipbuilding: Tool Calling and Plugins
Reference only; verify against the target FastGPT release and deployment documentation.

## What the data for this category looks like
Shipbuilding document data originates from project-specific construction ledgers, block manufacturing records, shipowner requirement letters, and industry-wide general construction specification documents. Data updates align with project construction milestones, with triggers at stages including block completion, final assembly completion, and delivery acceptance. Document structures are organized by fields such as project number, block code, material list, process parameters, inspection nodes, and acceptance standards. Units include professional engineering units like tons, meters, hours, and pieces. A single document can span dozens of pages.

## What constraints these characteristics impose on tool calling and plugins
Shipbuilding documents are updated per project milestones. This means tool calls must pull the latest data for the target project in real time, and cannot rely on static caching. Single documents are lengthy and contain numerous professional fields, so tool calls must accurately match field names to avoid parameter confusion. Document types cover multiple categories including construction plans, block inspection reports, and delivery acceptance files. Tools must support parameter mapping across multiple templates to adapt to the field requirements of different documents. Fields vary across different projects, so tool calls must bind project-specific identifiers to ensure data accuracy.

## How to configure settings

| Tool return result cache duration | 7 days | Data update frequency is low during the project construction cycle; 7-day caching reduces repeated call overhead |
| Document field mapping rules | Match using project-specific templates | Shipbuilding document fields change with project type and shipowner requirements; specific templates avoid parameter misalignment |
| `toolChoice` | auto | Adapt to tool calling requirements for multiple document types, automatically matching corresponding processing logic |
| `functionCall` | Bind project ID and document type | Accurately pull target document data for the corresponding project, avoiding cross-project data confusion |
| Maximum number of returned results | Top 3 entries | A single shipbuilding document contains multiple types of sub-documents; limiting the number of entries avoids context overload |

## Three common errors
- Tool calls return empty fields, with no target data matched. The cause is failure to bind the specific document mapping rules for the corresponding project, making it impossible to recognize professional fields such as shipbuilding document block codes and material specifications.
- Tool calls return a timeout, with a 504 status code displayed. The cause is that the single tool call timeout setting is too short, failing to adapt to the pull and parsing process for long shipbuilding documents.
- Interaction nodes do not respond, and subsequent document generation steps cannot be triggered. The cause is incorrect configuration of the tool call trigger logic, failing to adapt to the multi-link verification requirements of shipbuilding documents.

## How to verify correct configuration
- Enter a test project ID and document type, call the tool, and check whether the returned results include the professional fields for the corresponding project.
- Simulate a long document pull scenario to verify whether the tool call timeout meets the configured requirements.
- Trigger an interaction node to check whether the corresponding tool can be correctly called and generate a document framework compliant with shipbuilding specifications.
- View tool call logs to confirm that parameters are bound correctly, with no cross-project data confusion.
