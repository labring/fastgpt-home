# Document and Material Drafting for Shipbuilding: Model Access and Configuration

## What Data Looks Like for This Category
Data related to document and material drafting for shipbuilding mainly comes from general ship design drawings, block construction process cards, classification society specification documents, shipbuilding contract appendices, block inspection reports, and other sources. The data update rhythm aligns with project construction milestones, such as block inspection, launching, sea trial, and other nodes. Single documents are mostly long texts, containing professional fields like ship type, main engine model, weld number, inspection batch, and more. Units involve shipbuilding industry-specific units such as millimeters, tons, knots, and some documents include structured tables and drawing annotations.

## What Constraints These Characteristics Impose on the "Model Access and Configuration" Link
The long text and dense professional terminology characteristics of shipbuilding documents require that model access must adapt to a longer context window to avoid truncating core professional content. The feature of data updated according to project milestones requires that the knowledge base synchronization frequency matches the project rhythm, to avoid calling outdated specifications or process data. The existence of structured fields and specialized units requires that the text recalled by the model must accurately match the field requirements, while also limiting the total length of recalled text to prevent exceeding the model's processing limit.

## How to Set the Configuration
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `maxContext` | 8000–12000 token | Adapts to the context requirements of long shipbuilding documents and avoids truncating professional content |
| `maxTokens` | 2000–3000 token | Matches the output length of a single shipbuilding document and ensures complete coverage of inspection instructions |
| `quoteMaxToken` | 1500 characters | Limits the total length of recalled knowledge base text to avoid exceeding the model's context limit |
| `temperature` | 0.3–0.5 | Maintains the accuracy of professional terminology and reduces irrelevant divergence |
| `AIPROXY_API_ENDPOINT` | Fill in according to the deployment environment | Adapts to the address requirements for local or cloud-based model calls |
| `toolChoice` | auto | Allows the model to call tools as needed to process structured data, such as extracting weld parameters |

## Three Common Misconfigurations
- Symptom: The available model list is empty, and conversation cannot be started. Cause: `AIPROXY_API_TOKEN` or `AIPROXY_API_ENDPOINT` is not configured correctly, preventing the platform from pulling local or cloud model metadata.
- Symptom: The parsed `detail` field of streaming returns has no content. Cause: The `detail` return switch is not enabled in the call parameters, or the parsing logic does not match FastGPT's streaming return format.
- Symptom: Timeouts and no response occur when calling a local model. Cause: `maxContext` is not adjusted to adapt to long document recall, causing the model's processing load to exceed the timeout threshold.

## How to Confirm Successful Configuration
- Check the model management interface of FastGPT v4.17.0 to confirm that the target model has been loaded into the available model list.
- Initiate a test request to verify that the streaming return contains the complete content of the `detail` field, confirming that the parsing logic matches the return format.
- Upload a typical block inspection report to trigger the model to draft inspection instructions, and check whether the output includes professional fields such as accurate weld numbers and inspection batches.
- Simulate processing a long-text shipbuilding process document to confirm that the `maxContext` configuration does not trigger truncation errors and that the model response meets expectations.
