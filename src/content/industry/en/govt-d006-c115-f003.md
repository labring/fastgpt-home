# Document and Material Drafting for Rail Transit Equipment: Multi-turn Dialogue and Prompt Engineering

## What data for this category looks like
The document and material data for rail transit equipment primarily originates from R&D design documents, production process files, operation and maintenance records, compliance submission materials, and bidding documents. Data updates are adjusted dynamically based on R&D milestones, production batches, and operation and maintenance cycles. Document update frequency during the R&D phase shifts with design iterations, while maintenance records for the operation phase are updated monthly. Most documents follow a chapter-based structure, with fields including component model, production serial number, technical parameters, and compliance standard number. Units include professional metering identifiers such as millimeters, kilonewtons, and operating hours.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompt Engineering
The presence of professional fields and units requires prompts for multi-turn dialogue to clearly define parameter formats and units, avoiding generation of content that does not meet industry specifications. The dynamically updated document structure requires the multi-turn dialogue workflow to regularly trigger knowledge base synchronization, ensuring recalled content aligns with current equipment status. The chapter-based document structure with unique identifiers requires multi-turn dialogue to first guide users to clarify the target component’s model or production serial number, narrowing the retrieval scope and avoiding cross-component information confusion. The practice of archiving operation records per batch requires prompts to be bound to the batch dimension, ensuring recalled content corresponds to equipment data for the specified production batch. ## Three Common Misconfigurations
- Phenomenon: Generated document content exceeds the scope of the knowledge base, including non-preset external professional information. Cause: The prompt fails to clearly restrict the LLM to only use knowledge base recalled content for generation, causing the LLM to call its own general knowledge.
- Phenomenon: Generated operation and maintenance documents include component serial numbers and production batch identifiers from knowledge base paragraphs. Cause: The prompt fails to clearly require hiding internal metadata fields, causing the LLM to directly reference non-public identifiers in retrieval results.
- Phenomenon: Outputs from the custom model differ between the chat interface and workspace. Cause: `chatId` and the project-specific knowledge base collection are not uniformly bound, leading to inconsistent retrieval data sources across the two scenarios.

## How to Verify Successful Configuration
- Initiate a document drafting request for a specified component model, verify that the generated content includes the target component’s professional parameters and has no internal identifier fields.
- Upload a professional technical drawing, confirm that the dialog box can load and display the corresponding content normally.
- Use the same custom model to initiate the same request in both the chat interface and workspace, verify the consistency of the two output results.
- Adjust the preset values of the `variables`, confirm that the retrieval dimension can be updated in real time during multi-turn dialogue to match the corresponding documents.
