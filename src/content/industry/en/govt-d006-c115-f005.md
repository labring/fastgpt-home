# Document and Material Drafting for Rail Transit Equipment: Tool Calling and Plugins

## What the data for this category looks like
Rail transit equipment documents and materials mainly originate from design and development documents, manufacturing process specifications, factory acceptance reports, operation and maintenance manuals, and compliance certification documents. Data updates are triggered by new model project initiation, process iteration, or annual compliance reviews, with no fixed cycle. The length of individual documents varies widely, ranging from a few pages of component descriptions to hundreds of pages of complete vehicle operation and maintenance specifications. Core fields include component number, rated load, operating speed, and material grade. Supporting parameters mostly use industry-specific units such as track gauge (mm), axle load (t), and traction force (kN).

## Constraints Imposed on Tool Calling and Plugins by These Characteristics
The wide-ranging document structure of rail transit equipment paperwork requires tool calling to adapt to different input and output lengths, to avoid losing core technical parameters due to fixed truncation. Industry-specific units and fields require plugins to include built-in rail transit domain term mapping rules, to prevent parameter parsing errors. The non-fixed update cycle requires the tool calling data source to support dynamic pulling of the latest process and acceptance documents, without relying on static caching. The uniqueness of component numbers requires binding precise component identifiers during tool calling, to ensure that the called paperwork matches the target equipment.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `"required"` | Enforce tool calling to ensure that dedicated parameter tools for rail transit equipment are invoked during the paperwork drafting process |
| `functionCall` | Set based on actual measurement | Adapt to segmented calling of long-text paperwork, avoid overload from single calls |
| Tool calling timeout | `120 seconds` | Parameter queries for rail transit paperwork involve multi-dimensional process and compliance data, reserve sufficient pull time |
| Term mapping switch | Enabled | Automatically convert general parameter terms to rail transit-specific units, such as mapping "load" to "axle load (t)" |
| Long text processing threshold | `8000 characters` | Adapt to segmented processing of single hundreds-of-page operation and maintenance manuals, avoid truncating core compliance clauses |
| Tool calling retry count | `2 times` | Address scenarios of network fluctuations or temporary unavailability of data sources, reduce call failure rates |

## Three Common Misconfigurations
- Symptom: The tool calling return result contains unintended reasoning content, and the model cannot be restricted to calling only tools. Cause: `toolChoice` is not configured as `"required"`, so the model autonomously selects reasoning mode.
- Symptom: Connection failure is displayed when calling external tool services, and the log returns status code 502. Cause: A correct data source access whitelist is not configured, resulting in interception of the rail transit equipment process document interface.
- Symptom: Parameter fields returned by tool calling lack unit information. Cause: The term mapping switch is not enabled, and the automatic conversion rule for rail transit-specific units is not activated.

## How to Verify Correct Configuration
- With the FastGPT v4.17.0 platform, a tool call may be manually triggered, and the returned parameters checked for rail transit-specific units to confirm that the term mapping switch is active.
- An ultra-long operation and maintenance manual document may be uploaded, and the tool observed for automatic segmented calling to confirm that the long text processing threshold configuration is reasonable.
- A scenario where the data source is temporarily unavailable may be simulated, and the tool observed for retries initiated according to the configured retry count to confirm that the timeout and retry configurations are active.
- Model call logs may be reviewed to confirm that the `toolChoice` parameter is correctly set to `"required"`, and no autonomous reasoning log entries are present.
