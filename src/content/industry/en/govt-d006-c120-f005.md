# Document and Material Drafting for Railway Operations: Tool Calling and Plugins

## What the data for this category looks like
Railway operations document data comes from daily production ledgers. This includes train dispatch orders, passenger and freight operation reports, locomotive maintenance records, line inspection logs, and more. Update frequency varies by document type. Dispatch orders are generated in real time. Operation reports are updated per shift or daily. Maintenance records are submitted immediately upon work completion.

Document structure is split into two categories: fixed-format forms and free-text analysis reports. Fixed forms contain standardized fields. Free reports mostly cover fault analysis or summary content. Fields include items with clear units, such as line number (e.g., KXXX+XXX), train number, operating speed (km/h), and operation duration (minutes).

## What constraints these characteristics impose on tool calling and plugins
Fixed-format form documents require tool calling to accurately extract standardized fields. This prevents field misalignment caused by generalized extraction. Real-time updated dispatch orders require plugins to pull the latest data first when invoked. Reasonable cache strategy configuration is needed. Fields with units require plugin parsing logic to support unit verification. This prevents errors where values do not match their associated units. Long-text fault analysis reports require plugins to support sufficient context windows. This avoids truncation of critical information.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapts to mixed calling scenarios of fixed-format dispatch orders and free-text fault reports |
| `functionCall` | Bound to railway document field extraction functions | Accurately extracts core operation fields such as train number, line mileage, and operation duration |
| Plugin call timeout | `30–60 seconds` | Railway operation data requires cross-system interface pulls, with higher latency than general scenarios |
| Single call result return limit | `Top 10 entries` | Focuses on core operation document content, avoids interface overload |
| Context window length | `8000–12000 token` | Adapts to full context requirements of long-text locomotive maintenance reports |

## Three common misconfigurations
- Symptom: Plugin call fails after adding the Doc2X plugin, with logs showing "plugin initialization failed". Cause: No dedicated file format adaptation parameters for railway operation documents are configured. Doc2X cannot recognize the standardized header structure of railway-specific ledgers.
- Symptom: An error occurs when clicking input after referencing a plugin in a workflow, with a 400 status code returned. Cause: `toolChoice` is set to `auto`, but no corresponding railway document function definition is bound. The system cannot match valid calling logic.
- Symptom: Only a summary is displayed after searching for plugin return results, and complete web page content cannot be read. Cause: No long-text crawling rules are configured for the plugin. The long-form nature of railway operation documents is not adapted, so only limited summary information is returned.

## How to confirm the configuration is correct
- Manually trigger a plugin call, submit a railway dispatch order template, and check whether preset core fields are accurately extracted in the returned results.
- View plugin call logs to confirm the timeout period matches the configured range, with no frequent timeout errors.
- Submit a long-text locomotive maintenance report, verify that the returned content fully covers the input document structure, with no critical information truncated.
- Switch between calling different types of railway documents, confirm that the `toolChoice` mode automatically adapts the function calling logic, with no manual configuration changes required.
