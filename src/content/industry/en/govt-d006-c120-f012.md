# Document and Material Drafting for Railway Operations: Deployment and Upgrade

## What the data for this category looks like
Railway operation documents and materials mainly come from various documents generated during daily operations, including travel logs, dispatch orders, passenger service notices, equipment inspection reports, emergency plans, and more. Data sources include multiple intranet nodes such as dispatch centers, station operation points, and operation and maintenance teams. Update frequency varies by operation type: real-time dispatch orders update synchronously with command issuance, while inspection reports and passenger service notices update per shift or daily. Most documents follow fixed structures, with fields including train number, operation section, equipment number, responsible person, and operation time. Units use operation-specific measurement standards such as kilometers, hours, and passenger trips.

## What constraints these characteristics impose on deployment and upgrade
The fixed field structure of railway operation documents requires adapting structured data parsing during deployment to prevent generic parsing tools from losing key operation information. High-frequency real-time updated dispatch documents require the vector database to support incremental synchronization configuration, stopping full updates from occupying excessive intranet bandwidth. Document length spans a wide range, from notices of tens of characters to emergency plans of thousands of words, requiring flexible adjustment of chunking logic during deployment. Railway data also has intranet compliance requirements that restrict external storage and cross-network access, so teams should prioritize configuring intranet-compatible storage and database services.

## How to set the configurations

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 20–30 connections/second | Adapt to high-frequency document retrieval and storage requests for railway operations, avoiding database connection pool exhaustion |
| `MONGODB_URI` | Intranet-accessible MongoDB instance address | Store structured metadata of railway operation documents, ensuring data does not leave the intranet |
| `REDIS_URL` | Local intranet Redis cluster address | Cache frequently queried dispatch document results, reducing access pressure on the core database |
| `STORAGE_S3_ENDPOINT` | Railway intranet object storage endpoint | Store sensitive documents such as equipment inspection reports and emergency plans, complying with intranet data storage compliance requirements |
| `FE_DOMAIN` | Railway intranet specified domain name | Limit front-end access scope, only allowing internal operation personnel to access the system |
| `ROOT_KEY` | Custom strong password string | Generate the initial administrator account, ensuring initial permission security for local deployment |

## Three common mistakes
- Unable to register an account after local deployment, with the interface prompting that the account does not exist. The cause is that the `ROOT_KEY` parameter was not configured correctly, and the initial administrator account was not automatically generated.
- Knowledge base search response times out, taking more than 30 seconds. The cause is that the value of `DB_MAX_LINK` is too low, and the database connection pool is exhausted, failing to process batch document retrieval requests in a timely manner.
- Unable to integrate the indexing model after Docker deployment, with model loading failure after startup. The cause is that the local model directory was not mounted into the container, or the intranet-compatible cache service address was not configured correctly.

## How to confirm the configuration is complete
- Access the railway intranet specified `FE_DOMAIN` address, use the initial administrator account to complete login, verifying that account creation and permission configuration take effect.
- Upload a railway travel log document, trigger vector index generation, and check that the background logs have no database connection error or storage abnormality prompts.
- Initiate a retrieval request for a dispatch order document, confirm that the response time meets the real-time requirements of intranet operations, with no timeout errors.
- Check the intranet storage bucket corresponding to `STORAGE_S3_ENDPOINT`, confirm that the uploaded documents have been successfully synchronized to the specified storage location.
