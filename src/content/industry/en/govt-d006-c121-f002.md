# Document and Material Drafting for Expressway Operations: Vector Models and Indexes

## What the data for this category looks like
Expressway operations document data sources include daily road patrol logs, toll operation reports, emergency response archives, maintenance technical documents, traffic policy documents, and others. Update frequencies cover real-time, daily, monthly, and irregular categories. Document structures fall into three types: structured tables, semi-structured logs, and formal reports. Fields include road section number, disposal time, traffic volume, amount, responsible person, and others. Units involve kilometers, trips, yuan, hours, and others.

## What constraints these characteristics impose on vector models and indexing
Mixed document structures require the indexing stage to support multi-format parsing and adaptation. This prevents field information in structured tables from being split and having its semantic associations broken. The mix of real-time and irregular update rhythms requires index configurations to support flexible incremental update trigger rules. This adapts to differing update frequencies across data types. Fields with dedicated units require retaining field semantics during vector modeling, to avoid unit information interfering with similarity calculations. The wide range of document lengths requires chunking strategies that can adjust dynamically based on document type. This prevents over-splitting short documents or losing context in long documents.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Chunk length | 300–800 characters | Adapt to documents of different lengths such as patrol logs and toll reports, avoid over-splitting or losing context due to excessive length |
| Overlap length | 50–100 characters | Retain semantic association between adjacent chunks, adapt to the continuous recording characteristics of road patrol logs |
| Similarity threshold | 0.72–0.85 | Match professional semantic similarity of expressway operation documents, filter low-relevance search results |
| Single search limit | Top 8 entries | Control the number of returned results per search, adapt to the precise reference needs during document drafting |
| `maxToken` | 3500–4000 token | Limit the total context passed to the large model in a single call, avoid exceeding the model's input limits |
| Vector model normalization | Enabled | Adapt to the output of non-normalized embedding models, comply with FastGPT v4.17.0 configuration specifications |

## Three common mistakes
- Phenomenon: The retrieval backend shows that the target document is hit, but the large model reply prompts that no relevant content is retrieved. Cause: The field association between the hit chunk and the original document is not retained during context splicing, or the similarity threshold is set too high to filter valid hits.
- Phenomenon: Knowledge base query response times out, or the large model output is truncated. Cause: The single search limit is set too high, and the total context passed to the large model exceeds the `maxToken` limit.
- Phenomenon: The retrieval results have a large deviation in matching degree with the professional needs of document drafting. Cause: The vector model normalization configuration is not enabled, leading to errors in semantic similarity calculation for non-normalized embedding model outputs.

## How to confirm the configuration is correct
- Upload a typical road patrol log, manually verify whether the retrieval results include records of the corresponding road section and time, and adjust the similarity threshold to the range that matches the requirements.
- Import documents of different lengths, check whether the chunked results retain complete semantic units, with no over-splitting or excessive truncation.
- Check the vector model configuration items, confirm that the normalization switch is enabled, to adapt to the output format of the currently used embedding model.
- Simulate batch retrieval requests, check whether the context incoming volume complies with the `maxToken` limit, to avoid exceeding the model's input limits.

The values provided are common starting points and should be measured against the reader's own samples.
