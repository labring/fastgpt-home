# 12345 Citizen Hotline Ticket Handling: Declaration Materials and Case Review, Multi-turn Dialogue and Prompt Engineering

## What this category of data looks like
This category of data comes from the 12345 citizen hotline platform, contractor business systems, official knowledge bases, follow-up evaluation data, and local hotline management regulations. Staff process daily documents including demand registration forms, dispatch records, handling responses, follow-up records, extension applications, return explanations, and knowledge base entries. The system updates data daily. Core fields include demand number, contractor unit, demand type, handling progress, and evaluation results. The overall structure follows a closed-loop circulation process for public demands.

## What constraints these characteristics impose on the multi-turn dialogue and prompt engineering link
This category of data receives daily updates and follows a closed-loop circulation process for public demands. Multi-turn dialogue requires binding the current ticket context via `chatId` to avoid retrieving irrelevant historical data, and ensure interactions focus on the current demand. There are many document fields covering multiple circulation stages. Prompts must clearly limit processing scope to only declaration material verification and case organization for 12345 hotline tickets, and must not exceed the demand scope. Data formats vary across different sources. Each round of dialogue requires verifying the completeness of input fields to ensure compliance with ticket standard formats. Additionally, handling errors can cause ticket overdue or return. Prompts must include guidance logic for abnormal scenarios, covering cases such as ticket return and re-dispatch, and unsatisfactory follow-up evaluations.

| `chatId` | Bind the unique number of the current ticket | Ensure multi-turn dialogue context is bound to the current ticket, avoiding cross-ticket confusion of interaction data |
| `messages` | Retain the most recent 20 interaction records | Balance context completeness and response speed, adapting to the multi-turn verification needs of 12345 hotline tickets |
| `variables` | Inject three fixed variables: demand number, contractor unit, demand type | Allow prompts to accurately call data exclusive to the current ticket, without repeated inquiries to users |

| Single interaction output limit | Top 3 review conclusions | Focus on core review results, avoiding redundant information that affects ticket handling efficiency |

## Three Common Mistakes
- Phenomenon: The top title of the embedded mini-program dialogue page is accidentally modified and cannot be restored. Cause: The page title parameter was not locked in the configuration, causing the front-end rendering to call the global default title for overwriting.
- Phenomenon: The AI output content exceeds the preset review scope, introducing information unrelated to 12345 hotline tickets. Cause: The prompt did not clearly limit processing to only the specified fields of declaration materials and case review, and did not constrain the output boundary.
- Phenomenon: The context and reply output of the AI dialogue node are confused, leading to incorrect binding of ticket data. Cause: The storage logic of the `messages` parameter and reply content was not properly distinguished, and context content was incorrectly written to the reply field.

## How to Confirm the Configuration is Complete
- Bind the `chatId` of a test ticket to initiate a multi-turn dialogue, check that the context only retains interaction records for that ticket.
- Inject test ticket variables, confirm that the prompt can correctly call the variable content to generate review conclusions.
- Trigger a test scenario of ticket return and re-dispatch, check that the prompt guides the corresponding processing logic.
- View the configuration items of the embedded page, confirm that the title parameter has been locked, with no risk of automatic modification.
