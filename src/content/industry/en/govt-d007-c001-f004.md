# 12345 Citizen Hotline Ticket Handling: Declaration Materials and File Review — Workflow Orchestration

## What the data for this category looks like
Data for this category primarily comes from the 12345 citizen hotline platform, business systems of undertaking units, the hotline knowledge base, follow-up evaluation data, and local hotline management regulations. The data updates daily. Documents processed daily include appeal registration forms, dispatch records, handling responses, follow-up records, extension applications, return explanations, and knowledge base entries. Typical data fields include appeal number, appeal content, undertaking unit, handling time limit, response content, follow-up result, and more. Field mapping rules must be adjusted based on the specific connected business systems.

## Constraints imposed by these characteristics on workflow orchestration
Since data sources involve multiple business systems, workflow orchestration must support connecting to interfaces of different data sources. This enables automatic data pulling and synchronization. The daily update frequency requires the workflow to use a scheduled trigger or real-time listening mechanism. This avoids data delays that cause ticket overdue. Diverse document structures require the workflow to include multiple node types. These adapt to different ticket data formats and cover the full process of appeal classification, dispatch, response, and follow-up. The most time-consuming step of judging appeal types and responsible units needs an independent verification node in the workflow. This reduces errors from manual intervention. Exception branch handling must also be configured for scenarios like returned tickets for re-dispatch and unsatisfactory follow-up results.

## Configuration Settings
This page’s configuration examples use FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| `variables` | Map appeal number, appeal content, and undertaking unit as global variables | Adapt to fixed fields of ticket data, facilitating cross-node calling and verification |
| `nodeId` | Assign unique identifiers to text classification nodes and follow-up verification nodes | Facilitate locating abnormal nodes and troubleshooting logs |
| Text classification node threshold | 0.75-0.85 | Distinguish common types of citizen appeals, avoid misjudgment or missed judgment |
| Timeout setting | 600 seconds | Match the average response duration of daily ticket handling |
| Knowledge base recall upper limit | Top 5 entries | Match the common number of entries in the hotline knowledge base, avoid information overload |
| Variable verification rule | Check if the appeal number in `variables` is non-empty | Filter invalid empty ticket data |

## Three Common Configuration Errors
- The text classification extraction node outputs empty content. This happens when the appeal content field in `variables` is not correctly bound to the node’s input parameters. The node then has no valid text to process.
- Importing an older version workflow fails after an upgrade. This occurs when the original workflow’s `nodeId` identifiers are not retained. Node association relationships break, and the configuration cannot load normally.
- Custom tool variables do not take effect. This happens when the ticket’s undertaking unit field is not mapped to the tool’s input parameter configuration. The tool cannot call query data from the corresponding business system.

## How to Verify Proper Configuration
- Submit a test ticket. Check if the fields in `variables` are correctly mapped to the input parameters of each workflow node.
- Trigger the text classification node. Confirm the output appeal type matches the test ticket’s content.
- Simulate a ticket overdue scenario. Check if the preset timeout reminder and exception handling branch activates.
- Export the current workflow configuration. Verify that the `nodeId` matches the identifier in the node logs. This ensures normal node association relationships.

The values provided here are common starting points, and should be evaluated against the reader’s own samples.
