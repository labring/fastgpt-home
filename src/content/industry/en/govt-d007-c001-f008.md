# 12345 Citizen Hotline Ticket Handling: Declaration Materials and File Review — Document Parsing and Chunking

## What the data for this category looks like
Documents processed daily for this category include request registration forms, dispatch records, handling responses, delay applications, return explanations, knowledge base entries, and more. Data sources include the 12345 citizen hotline platform, contracting entity business systems, hotline knowledge bases, follow-up evaluation data, and local hotline management regulations.

Data is updated on a daily schedule. Individual case or ticket documents typically include fixed fields such as request number, contracting entity, request content, handling steps, response content, and follow-up evaluation results. Some batch-exported documents may have format differences.

## What constraints these characteristics impose on the document parsing and chunking step
Daily batch-updated ticket data requires parsing processes to have stable timeout settings, to prevent task interruptions from bulk processing.

Multiple document types are covered, including scanned documents, standard docx files, exported spreadsheets, and more. Parsing logic must adapt to non-standard documents.

Field differences across ticket documents are significant. Chunking must retain contextual connections to ensure business logic integrity during retrieval.

Long-text handling responses and case content may exceed standard chunk lengths. Chunking parameters must be adjusted appropriately to avoid truncating critical information.

## How to set up configurations
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `chunkSize` | 800–1200 characters | Adapts to the typical text length of 12345 hotline ticket responses and case files, avoiding overly long single chunks that harm semantic retrieval |
| `chunkSplitter` | Paragraph + semantic chunking | Retains contextual connections for requests, responses, and dispatches, aligning with ticket business processing logic |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600–900 seconds | Matches parsing durations for case files in PDF or DOCX format under 10MB, preventing timeout errors during large file parsing |
| `customPdfParse` | Enabled | Adapts to scanned ticket documents and formatted case files, preserving original layout and field structure |
| `UPLOAD_FILE_MAX_SIZE` | 100 MB | Matches the single-file upload limit for batch-exported tickets, preventing upload task failures |
| `chunkSettingMode` | Manual configuration | Adjusts chunking rules for the fixed fields of ticket documents, adapting to business scenarios |

## Three common configuration mistakes
- Uploading case PDFs larger than 10MB results in the error `timeout of 900000ms exceeded`. This occurs because `PARSE_FILE_TIMEOUT_SECONDS` has not been adjusted to a reasonable range. The default timeout duration is insufficient for parsing large files.
- Individual DOCX ticket documents have empty fields after parsing. This occurs because `customPdfParse` is not enabled, so the system cannot adapt to non-standard formatted ticket export files.
- Long-text handling responses are excessively truncated, leading to incomplete retrieval results. This occurs because `chunkSize` is set too small, and does not match the actual length of ticket responses.

## How to confirm the configuration is correct
- Upload a single case DOCX file under 10MB, and verify that parsing completes within 900 seconds.
- Upload a request registration form in scanned format, and confirm that the original stamp, layout, and field information are preserved after parsing.
- Import 10 ticket knowledge base entries in Q&A format, and test that retrieval returns the original response content.
- Adjust `chunkSize` to 1000 characters, and verify that long-text ticket responses are evenly chunked while retaining contextual connections.
