# Declaration Materials and File Review for Proactive Public Disclosure and Policy Publication: Workflow Orchestration

## What this category of data entails
Daily documents for this category include policy documents, policy interpretation drafts, public disclosure directories, information release approval forms, press releases, and website column update records. Data sources are government portals, document management systems, government information disclosure directories, policy document repositories, and press conference materials. The update frequency is daily. Document fields include public attribute tags, confidentiality levels, approval form numbers, associated website column attributions, and core content consisting of policy texts and associated approval and publication records.

## What constraints these characteristics impose on workflow orchestration
This category targets proactive public release to the public. Unlike application-based public disclosure, it does not wait for individual applications, and prioritizes public directories and publication time limits. Data sources are scattered, covering internal document management systems and external government platforms. This requires workflow configurations to include multi-data source connection nodes for batch pulling documents from different channels. The daily update frequency requires workflows to support scheduled triggering, while retaining manual triggering capabilities to handle temporary release needs. Documents contain sensitive verification fields. This requires splitting core steps such as public attribute judgment and confidentiality review into independent nodes, setting verification rules, and binding `nodeId` to accurately locate core nodes. Business errors have serious consequences, so exception capture and alert nodes must be configured to intercept abnormal processes and notify operations and maintenance personnel in a timely manner.

## Three Common Configuration Mistakes
- Phenomenon: The AI chat node in the workflow cannot retrieve the output content of the code running node, with a prompt that the field is empty. Cause: The output of the code node was not mounted to the `variables` scope, so subsequent nodes cannot read the corresponding parameters.
- Phenomenon: When the judgment node matches a string, using "equals" or "starts with" rules triggers the ELSE branch, while using "contains" or "ends with" triggers the IF branch. Cause: The judgment rule matching logic was not configured correctly, and the forward matching rule was mistakenly set as a reverse trigger condition.
- Phenomenon: Global variables have mixed values under multiple concurrent requests. Cause: Shared variables were not adjusted to session-level isolation, causing `variables` parameters from different requests to interfere with each other.

## How to Verify a Correct Configuration
- Manually trigger the test workflow, check the output logs of each node, and confirm that expected policy documents and approval form field contents are included.
- Simulate multiple concurrent requests, verify that `variables` parameters do not interfere between different sessions, and no mixed value situations occur.
- Adjust the public attribute field in the test case, confirm that the judgment node triggers the corresponding branch according to preset rules.
- Trigger an abnormal process, verify that the abnormal alert notification is sent normally to the specified receiving channel.
