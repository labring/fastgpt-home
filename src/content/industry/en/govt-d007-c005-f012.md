# Declaration Materials and File Audit for Property, Asset and State-owned Capital Management: Deployment and Upgrade

## What this category of data looks like
Data for this category comes from state-owned asset supervision information systems, enterprise asset management systems, property rights exchange systems, valuation firm reports, and financial statements. The update frequency is monthly. Commonly processed documents include property right registration forms, asset valuation reports, property right transfer plans, on-site trading announcements, and asset disposal approval slips. Data fields cover asset ownership identifiers, categories, valuation results, transaction approval statuses, and more. The word count of individual documents varies widely, ranging from hundreds of words for approval slips to tens of thousands of words for asset valuation reports.

## What constraints these characteristics impose on deployment and upgrade
Heterogeneous multi-source data requires configuring multi-system integration parameters during deployment to ensure stable data synchronization from state-owned asset supervision, enterprise asset, and property rights exchange systems. Wide variation in document types requires storage and indexing configurations that accommodate content from hundreds of words to tens of thousands of words, to avoid index failure or reduced retrieval accuracy. Monthly update frequency requires batch synchronization task scheduling aligned with business cycles, to prevent excessive system resource usage. The strict requirements for state-owned asset audits also require built-in data validation logic during deployment, to prevent erroneous data from entering the audit workflow.

| `DB_MAX_LINK` | 20–30 connections | Accommodates concurrent connection requirements for multi-system synchronization |
| `FILE_TOKEN_KEY` | A 32-character random string owned by the enterprise | Secures access to uploaded state-owned asset documents |

## Three Common Configuration Mistakes
- Symptom: A MongoDB connection timeout alert appears after startup, with status code 503. Cause: The internal database access whitelist was not configured, preventing FastGPT from establishing a connection to the MongoDB instance integrated with the state-owned asset system.
- Symptom: When deploying via Synology Docker, the container fails to start after configuring PG_URL. Cause: Special characters in the database password were not escaped, causing configuration parsing to fail.
- Symptom: After configuring an external model channel, connection to the local ollama instance fails, with a connection timeout prompt. Cause: The Docker container was not started in host network mode, or the correct ports were not mapped, preventing access to the locally deployed ollama service.

## How to Verify Successful Configuration
- Run the `docker logs fastgpt` command, check that there are no errors in the database connection logs, and confirm that the `MONGODB_URI` and `PG_URL` configurations are correct.
- Upload an asset valuation report document, verify that the storage path matches the `STORAGE_S3_ENDPOINT` configuration, and confirm that the document can be previewed normally.
- Trigger a batch synchronization task, check that the number of synchronized entries matches the data volume of the data source, and confirm there are no interruption errors.
- Test the external model channel connection, confirm that the local ollama instance can be called normally, and that there are no connection timeout errors.
