# Declarations and File Review for Infectious Disease Information Reporting and Monitoring: Multi-turn Dialogue and Prompt Engineering

## Data Structure for This Use Case
Data for this use case comes from the Chinese Center for Disease Control and Prevention Information System, hospital HIS systems, infectious disease reporting systems, and laboratory testing systems. The update frequency is daily. Daily documents include infectious disease reporting cards, epidemic analysis reports, case correction records, clustered epidemic reports, and epidemiological investigation reports. Core fields include case number, diagnosis time, reporting time limit, correction flag, case classification, and others. Fields must strictly follow the standardized format for statutory infectious disease reporting, with no custom redundant fields.

## Constraints for Multi-turn Dialogue and Prompt Engineering
Daily updated data sources require multi-turn dialogue to access the latest case data in real time, and avoid using expired review results. Mixed processing of multiple document types requires prompts to distinguish field rules for different documents. For example, case correction records must match the original reporting card number to complete verification. The rigor of statutory reporting requires that multi-turn dialogue prompts embed field verification logic to prevent underreporting and delayed reporting risks. Additionally, high-frequency processing of duplicate and incorrect corrected case records requires dialogue contexts to retain recent historical records, ensuring that past case information can be linked during the review process.

| `messages` History Truncation Threshold | Retain the last 7 days of dialogue context | Matches the daily update frequency of business data, covering the standard cycle for case corrections |

| Single-turn Dialogue Token Limit | 16000 tokens | Covers the multi-turn analysis and verification requirements for clustered epidemic reports, and complies with dialogue model token calculation rules |
| `chatId` Session Identification Rule | Generate unique identifiers based on case numbers | Facilitates associating multi-turn review dialogues for the same case |
| Dialogue File Expiration Days | 7 days | Matches the daily update frequency of business data, avoiding redundant storage usage |
| Multi-turn Dialogue Timeout Setting | 600 seconds | Adapts to the multi-turn review rhythm for complex epidemiological investigation reports |

## Three Common Configuration Errors
- Empty case reporting time limit field in dialogue return results. Cause: Standard field mapping is not configured according to the `variables` field binding rules, so the prompt cannot extract field content from the corresponding data source.
- Timeout errors in batch review tasks. Cause: A reasonable single-turn dialogue token limit is not set, and the text of clustered epidemic reports processed in a single round is too long, leading to dialogue call timeouts.
- Case correction records are not included in the review scope. Cause: The last 7 days of dialogue context are not retained according to the `messages` history truncation threshold, and previously submitted case correction information is omitted, resulting in duplicate or incorrect case cards not being identified.

## How to Confirm Successful Configuration
- Import a single standard infectious disease reporting card, trigger multi-turn dialogue review, and check whether the preset standard field content is included in the return results.
- Submit a dialogue request containing historical correction records, and verify that the `messages` context correctly loads past review information.
- Simulate a single-turn long-text review task, and check whether the dialogue execution duration complies with the preset timeout setting.
- Adjust the `variables` field mapping rules, and verify that the prompt can correctly call the corresponding data fields to complete verification.
- Submit a batch review task, and verify that parallel scheduling of multiple dialogue nodes complies with the preset grouping rules.
