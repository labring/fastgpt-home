# Declaration Materials and Case File Review for Petition Matter Handling: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Data sources include the national petition information system, local petition systems, the 12345 citizen hotline, grassroots governance platforms, and historical petition archives, with daily updates. Daily processed documents include standard official documents such as petition registration forms, acceptance notices, transfer and assignment letters, handling opinions, review and re-review applications, and resolution plans. Some data is in structured form. Data fields include petitioner identification, demand content, acceptance status, responsible unit, handling process records, and others. Document formats vary slightly across sources, requiring unified parsing adapted for multi-source data.

## What constraints these characteristics impose on the multi-turn dialogue and prompt engineering link
Multi-source data sources require prompts to adapt to document parsing across different formats, with preset unified field extraction rules. Daily update frequency requires dialogue context to sync with the latest petition data to avoid calling expired case file information. The fixed structure of standard official documents requires multi-turn dialogue to strictly follow preset process nodes, ensuring extracted fields meet legal handling requirements. Data differences across sources require prompts to include format-compatible guidance logic to avoid parsing errors. Additionally, the legal handling process for petition matters constrains that multi-turn dialogue must proceed in the order of acceptance, transfer, investigation, handling, and review, with no skipped steps.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the petition matter number as the unique identifier | Petition matters have unique number attributes, facilitating association with historical case files and dialogue context |
| `messages` | Retain the most recent 30 rounds of dialogue content, truncate portions exceeding 12000 characters | Petition dialogue and case file content are lengthy; balances context completeness and call resource usage |
| `variables` | Inject structured field variables from petition registration forms and handling opinions | Fixed information from standard official documents must be called to ensure prompts accurately match business scenarios |
| Maximum context length | 8000–12000 token, calibrated via actual testing | Adapts to the overall length of petition documents and dialogue, avoiding content loss from context overflow |
| Single recall document limit | Top 6 entries | Controls the number of recalled associated case files, avoiding redundant information interfering with dialogue generation |
| System prompt template | Designed according to the legal process for petition handling, including fixed guidance for acceptance scope screening, responsible unit coordination, and policy explanation | Ensures dialogue generation complies with legal handling requirements for petition matters |

## Three common mistakes
- Symptom: The interface prompts "No permission to operate this dialogue record". Cause: The `chatId` is not bound to the system permission variable exclusive to the petition matter, resulting in the dialogue context not being associated with the access permissions of the corresponding petition subject.
- Symptom: The generated handling opinion text cannot generate a Word download link at the bottom of the dialogue. Cause: The document export node of the workflow is not configured, or the generated text is not correctly mapped to the corresponding fields of the export template.
- Symptom: After upgrading FastGPT v4.17.0 and refreshing the page, dialogue records are lost and displayed as a new dialogue. Cause: The dialogue data in the `messages` array was not exported before the upgrade, or the association between the original `chatId` and the petition matter number was not re-bound after the upgrade.

## How to confirm the configuration is correct
- Initiate a test dialogue, enter the basic information of the petition matter, check whether the context correctly binds the petition matter number corresponding to `chatId`, and verify whether the permission association logic takes effect.
- Upload test petition registration forms and handling opinions, check whether `variables` can be correctly injected into the specified positions of the system prompt, and verify whether document information calls work normally.
- Trigger dialogue to generate handling opinion text, check whether the generated content complies with the structural requirements of standard official documents, and verify whether the workflow node normally triggers the export function.
- Refresh the page, check whether the dialogue record retains the historical content associated with the original `chatId`, and confirm that the configuration has not lost the context binding relationship.
