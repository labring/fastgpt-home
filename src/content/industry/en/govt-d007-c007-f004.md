# Petition Case Handling: Declaration Materials and File Review - Workflow Orchestration

## What this category's data looks like
Data for this category primarily comes from the national petition information system, local petition systems, the 12345 citizen hotline, grassroots governance platforms, and historical petition archives. The update frequency is daily.

Commonly involved documents include petition registration forms, acceptance notices, transfer and assignment letters, handling opinion letters, review and re-examination applications, and resolution plans. Data stakeholders include petition bureaus, departmental petition offices, subdistrict and township offices, and responsible unit offices.

Document structures are built around the full process of petition case acceptance, handling, review, and re-examination. Fields include case number, appeal content, handling subject, handling identifier, and others.

## What constraints do these characteristics impose on the workflow orchestration link
The diversity of data sources requires the workflow to configure multi-source data synchronization nodes to ensure complete access to daily updated petition data.

Significant structural differences exist between different types of petition documents. The workflow must set up document type recognition branches to match corresponding field extraction rules.

Errors in petition case handling are directly linked to repeated petitions, petitions submitted beyond the authorized hierarchy, or review and correction requests. The workflow must include compliance verification links, and set mandatory checks for core links such as acceptance scope identification, responsible unit coordination, and handling opinion formulation.

Additionally, this category must strictly follow legal handling procedures. Workflow nodes must be connected in process order, and node order cannot be adjusted arbitrarily.

## How to set the configurations
| Configuration Item | Recommended Practice | Rationale |
| ---- | ---- | ---- |
| Global Variables | Store core fields such as petition case number, appeal content, handling subject | Match the fixed field structure of petition documents to facilitate cross-node invocation |
| Node ID (`nodeId`) | Name according to node function, such as "Acceptance Scope Verification", "Document Extraction" | Facilitate troubleshooting error logs and quickly locate abnormal links |
| Timeout Setting | 600 seconds | Adapt to the conventional time consumption of petition data synchronization and document processing to avoid long-term unresponsiveness |
| Form Component | Configure fields for case number, appeal description, proof material upload, with a single file limit of 100 MB | Match the conventional material requirements of petition declarations to avoid blocking the workflow from oversized files |
| Context Window | Previous 10 historical records | Adapt to the historical appeals and handling tracks of petition cases to avoid context overflow |
| Retry Count | 2 times | Balance the success rate of interface calls and processing time to avoid system pressure caused by repeated triggers |

## Three common mistakes
- Workflow runtime encounters gpt-4o-mini call error logs, but the model call is not actively configured. The cause is that the workflow calls an unconfigured model node by default, or the model call scope is not restricted in the `variables` configuration.
- Cannot modify the global variable historical records in the workflow. The cause is that the historical record editing permission is not enabled in the `variables` configuration, or the modifiable attribute is not set for cross-node variable transfer.
- Cannot extract proof material files from petition cases. The cause is that the form component is not configured with a file upload field, or the workflow node is not bound to a file extraction logic, resulting in materials not being recognized and stored normally.

## How to confirm the configuration is complete
- Check the `nodeId` naming of workflow nodes, confirm they match the node names in the configuration items. Abnormal nodes can be quickly located via system logs.
- Submit a test petition case, confirm that core fields in global variables can be normally passed and modified across nodes.
- Upload test petition proof materials, confirm that the form component can normally receive and store files, with no size limit error.
- Simulate a timeout scenario, confirm that the workflow completes node processing within 600 seconds, and triggers the preset retry logic after timeout.
