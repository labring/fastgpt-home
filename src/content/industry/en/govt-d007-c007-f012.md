# Petition Case Handling: Declaration Materials and File Review - Deployment and Upgrade

## What Data for This Category Looks Like
Typical entities for this category of data include petition bureaus, departmental petition offices, subdistrict and township offices, and responsible unit offices. Daily documents include petition registration forms, acceptance notices, transfer and assignment letters, handling opinions, review and re-review applications, and resolution plans.
Data sources include the national petition information system, local petition systems, the 12345 citizen hotline platform, grassroots governance platforms, and historical petition archives. The update frequency is daily.
Data fields include appeal statements, handling nodes, responsible subject identifiers, policy basis association items, and more. Single case document lengths vary widely. Deployments must accommodate parsing requirements for different formats.

## Constraints on Deployment and Upgrade
The data characteristics of this category impose multi-dimensional constraints on the deployment and upgrade phase.
Multi-source data access requires configuration of format parsing rules adapted to different systems, to avoid field misalignment during data import.
Daily update frequency requires deployment of incremental synchronization mechanisms, to prevent excessive system resource usage from full synchronization.
Diverse document types need category-specific parsing and storage rules, to ensure correct identification and archiving of different case materials.
Potential errors include repeated petitions, petitions submitted outside the authorized hierarchy, or handling opinions being corrected through review. Therefore, a field verification step must be added during deployment, to ensure information accuracy for core processes such as acceptance scope screening and responsible unit coordination.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Set to `mongodb://localhost:27017/fastgpt_letter` | Petition data accumulates with daily updates, requiring a dedicated MongoDB instance to host session and case metadata. Associating with a Docker-deployed instance during local deployment reduces operational costs. |
| `REDIS_URL` | Set to `redis://localhost:6379/0`, with a timeout threshold of `300 seconds` | Petition handling processes require real-time caching of session status and case shards. The 300-second timeout accommodates the interaction interval of multi-step review workflows. |
| `STORAGE_S3_ENDPOINT` | Fill in the local object storage address, for example `http://192.168.1.100:9000` | Multiple types of attachments such as petition registration forms and handling opinions need to be stored. Local S3-compatible storage supports offline deployment requirements. |
| `DB_MAX_LINK` | Set to `200–300` | Accommodates batch case imports from daily updates, limiting database connection count to avoid resource exhaustion. |
| `ROOT_KEY` | Fill in a custom 32-character string key | Used to configure exclusive data source permissions for the petition system, isolating business data from general knowledge bases. |

## Three Common Configuration Errors
- Symptom: Frontend unresponsiveness when calling workflow APIs, with normal CPU and memory usage shown in container resource monitoring. Cause: Incorrectly configured timeout parameters for `REDIS_URL`, leading to session cache blocking and failure to synchronize review status normally.
- Symptom: Failure to load details when viewing session logs, with system prompt indicating database connection failure. Cause: `MONGODB_URI` does not correctly point to the MongoDB instance inside Docker Desktop, and incorrect storage path configuration prevents reading of case metadata.
- Symptom: Failed large model API calls after upgrading to FastGPT v4.17.0, with a missing dependency prompt. Cause: Failure to switch to `aiproxy` configuration per the version instructions, and failure to update corresponding environment variables to replace the original One API calling method.

## How to Confirm Successful Configuration
- Run the built-in database connectivity test script to verify connectivity for `MONGODB_URI` and `REDIS_URL`, with no timeout or connection refused errors.
- Upload a single petition registration form attachment, confirm that the `STORAGE_S3_ENDPOINT` configuration can store files normally, and return a valid access path.
- Log in to the admin backend using `ROOT_KEY`, confirm access to the exclusive configuration page for the petition data source, with no permission intercept prompts.
- Trigger a single case review workflow, check system logs for no database connection anomalies or timeout records, and confirm review steps proceed normally.

The values provided are common starting points, and should be evaluated against the user's own samples.
