# Public Data Catalog and Disclosure: Declaration Materials and File Review - HTTP Interfaces and External Systems

## What This Category’s Data Looks Like
This category covers publicly shareable structured data assets. Data sources include local public data disclosure platforms, integrated big data platforms, departmental business databases, and electronic credential repositories. Daily maintained documents include public data resource catalogs, data disclosure lists, data item descriptions, anonymization rules, interface documentation, and update frequency descriptions. A single data entry includes fields such as data item name, disclosure permission, anonymization method, call interface address, and update cycle. The update frequency is monthly, and the catalog and interface configuration must be updated synchronously as departmental data changes.

## Constraints for HTTP Interfaces and External Systems
The monthly update rhythm requires HTTP interfaces to support regular verification of consistency between the catalog and actual interfaces. This prevents calling expired disclosure addresses, which would delay declaration material and file review progress. Differences in interface formats from multiple data sources require external systems to adapt to different request headers and response structures. This ensures correct parsing of returned structured data. Anonymization rules attached to data items require interfaces to automatically filter sensitive fields according to configuration. This prevents data leaks and violations of government data security requirements. Markings of disclosure permissions require interfaces to carry authorization parameters. This ensures that only eligible entities receive corresponding data, maintaining compliance with data disclosure rules. Additionally, the timeliness requirements of declaration materials and file reviews require interface responses to meet time limits for business scenarios, avoiding delays in review workflows.

## How to Configure Settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Include a Bearer token with a validity period not exceeding 30 days | Complies with security authorization specifications for government data interfaces, and matches authorization boundary requirements in actual business scenarios |
| `variables` | Pass data item IDs and caller permission identifiers in JSON object format. Do not pass more than 10 data item IDs in a single request | Adapts to dynamic call needs for multiple data items, and matches disclosure permission configurations in public data catalogs |
| `responseData` | Only return anonymized data fields, filter non-disclosed items. Do not return more than 100 entries in a single request | Ensures returned data complies with anonymization rules and disclosure permission requirements, preventing data leaks |
| Request timeout setting | 600 seconds | Public data interface responses include multi-field validation, so sufficient time is reserved to avoid mid-request interruptions |
| Retry count configuration | First 2 attempts | Addresses temporary network fluctuations on public data platforms, avoiding overloading the platform with repeated requests |

## Three Common Configuration Mistakes
- An interface returns a 401 Unauthorized status code. This occurs because the `Authorization` parameter is not configured correctly, or an expired authorization token is used.
- Interface returned fields include unanonymized sensitive information. This occurs because the `responseData` filter configuration is not enabled, and the anonymization rules marked in the data catalog are not matched.
- Interface calls continue to fail after multiple attempts without triggering retries. This occurs because reasonable retry counts are not configured, or retry rules do not adapt to temporary fluctuations on public data platforms.

## How to Verify Configurations Are Correct
- Manually call the configured interface, and check if the returned status code complies with the interface documentation specifications for the corresponding data item.
- Compare the returned fields with the content marked in the data catalog, confirm that sensitive fields have been filtered and non-disclosed items are not returned.
- Check if the `variables` parameter correctly passes data item IDs and caller permission identifiers, matching the permission scope of the current call.
- Call the interface multiple times, observe if the response time meets business scenario requirements, and adjust timeout settings and retry counts as needed.
