# Public Data Catalog and Opening: Declaration Materials and Case Review - Deployment and Upgrade

## What data in this category looks like
Data for this category primarily comes from local public data open platforms, integrated big data platforms, departmental business databases, and electronic certificate repositories. Daily documents include public data resource catalogs, data opening lists, data item descriptions, desensitization rules, interface documents, and update frequency descriptions.
Data is updated monthly. Core fields include data item name, opening scope, desensitization requirements, interface address, update cycle, and authorization boundary. All data uses structured or semi-structured formats, and must adapt to different field definitions across multiple departments.

## What constraints do these characteristics impose on deployment and upgrade
Monthly update frequency requires configuring scheduled synchronization tasks during deployment to avoid data lag.
Heterogeneous data from multiple sources requires adaptation to different database connection parameters to ensure consistency between metadata and actual data.
Structured fields and authorization boundaries require configuring field mapping rules during deployment to adapt to case review query logic.
Storage of desensitization rules and interface documents requires dedicated storage services to ensure data security.
Additionally, deployments in government scenarios must strictly follow access control requirements to limit access to sensitive data.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://catalog_user:secure_pass@db-host:27017/public_data_catalog?authSource=admin` | Stores full metadata for public data catalogs, supports associated queries for multi-department data items |
| `REDIS_URL` | `redis://:redis_pass@cache-host:6379/1` | Caches frequently accessed public data opening lists to reduce database query latency |
| `STORAGE_S3_ENDPOINT` | `https://s3-cn-shanghai.mycloud.com` | Stores desensitized interface documents and desensitization rule files, compatible with domestic compliant cloud storage services |
| `FILE_TOKEN_KEY` | `32-bit random hexadecimal string` | Encrypts access tokens for catalog files to prevent unauthorized downloading of sensitive data |
| `DB_MAX_LINK` | `20–30` | Adapts connection pool configuration for monthly batch sync tasks, avoids exhausting database connections |
| `PG_URL` | `postgresql://meta_user:meta_pass@db-host:5432/data_item_meta` | Stores structured metadata for data items, supports complex conditional queries for case reviews |

## Three common mistakes
- Phenomenon: The initialization script returns a `connection refused` error after local deployment. Cause: Connection parameters for `PG_URL` or `MONGODB_URI` are not correctly configured, and access permissions for the corresponding database ports are not enabled.
- Phenomenon: Unable to directly edit the index configuration corresponding to search results when retrieving the public data catalog. Cause: Edit permissions for the front-end knowledge base are disabled by default. Adjust front-end access configurations to access the editing interface.
- Phenomenon: The system prompts for the CVE-2024-46982 vulnerability after deployment. Cause: Uses the NextJS 14.2.5 version released prior to FastGPT v4.17.0, and dependency packages have not been updated in time to fix the vulnerability.

## How to confirm configurations are properly set
- Run the built-in database connection test script to verify normal connection status for `PG_URL` and `MONGODB_URI`, with no timeout or permission errors.
- Upload a test public data item description file, confirm that the storage bucket configured via `STORAGE_S3_ENDPOINT` can normally upload, download, and delete files.
- Access the front-end page corresponding to `FE_DOMAIN`, retrieve the public data catalog, and confirm that cached catalog data loads and displays normally.
- Trigger a manual synchronization task, confirm that the connection pool configured via `DB_MAX_LINK` does not show exhaustion errors, and the synchronization task completes normally.

The values provided are common starting points and should be measured against the reader's own samples.
