# Declaration Materials and Case Review for Highway Maintenance and Road Property Rights Management: Vector Models and Indexing

## What this category of data looks like
This category of data typically comes from highway maintenance management systems, bridge and tunnel monitoring systems, road administration patrol systems, and traffic flow monitoring systems, and is updated daily. Daily documents include maintenance plans, patrol logs, disease disposal forms, road-related construction permits, and road property damage compensation forms. Most fields include facility numbers, disease types, disposal nodes, permit numbers, compensation amounts, and similar details. Some documents are structured forms, while others are unstructured text such as patrol records.

## Constraints on vector models and indexing
Data such as daily high-frequency patrol logs and disease disposal forms require the indexing process to support incremental updates, avoiding resource consumption caused by full index reconstruction. The mixed multi-source heterogeneous data format requires the vector model to handle encoding for both structured form fields and unstructured patrol text. Road-related construction permits and road property damage compensation forms involve compliance reviews, which have elevated requirements for vector recall accuracy. Redundant recall results must be limited. Additionally, individual document lengths vary widely, from short forms to patrol records thousands of characters long. This requires a flexible chunking adaptation mechanism.

## How to set configurations
The following configurations are formulated for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to the common length of documents in this category, avoiding chunk loss issues |
| Overlap Length | 150 characters | Retains semantic connections between adjacent chunks, covering the full logic of maintenance workflows |
| `defaultToken` | 8192 | Matches the context window upper limit of mainstream vector models, supporting long text slicing |
| `maxToken` | 4096 | Limits token consumption per vector, controlling call costs |
| Single Recall Limit | Top 8 entries | Filters redundant results, focusing on core maintenance and road-related case information |
| Vector Call Thread Count | 2–4 | Reduces system resource usage, preventing embedding rate limit errors. If using a third-party proxy service, adjust this value based on the proxy’s concurrency limits |

## Three common configuration errors
- The knowledge base stays in the indexing state for an extended period after upload. This happens when chunk length is set too large, exceeding the vector model’s processing capacity and leading to excessively long chunking times.
- A rate limit error appears during vectorization. This occurs when the vector call thread count is set too high, with concurrent requests exceeding the service provider’s call limits.
- Text chunks are lost after chunking. This happens when the chunk length does not match the actual document length, resulting in key information not being properly retained after long text is truncated.

## How to verify a correct configuration
- Upload a typical patrol log document. Check that the number of chunked text blocks matches expectations, with no obvious truncation or loss.
- Review vector call logs. Confirm that the token count per call does not exceed the `maxToken` setting, and that there are no frequent rate limit errors.
- Run a retrieval related to case review. Check that the number of recall results matches the single recall limit, and that results include core maintenance and road-related information.
- Test an incremental upload of a new disease disposal form. Confirm that the indexing state finishes updating within a reasonable timeframe.

The values provided are common starting points and should be measured against the reader's own samples.
