# Declaration Materials and File Review for Internal Control Evaluation, Audit and Rectification: Workflow Orchestration

## What data for this category looks like
Typical stakeholders for this category include central enterprise internal control departments, audit departments, finance departments, subordinate enterprises, and external audit institutions. Daily processed documents include internal control self-assessment reports, audit notices, audit working papers, issue lists, rectification ledgers, and rectification closure certificates.
Data comes from enterprise internal control systems, ERP, financial shared services systems, audit management systems, and procurement contract project systems. Update frequency is annual.
Document structures and fields vary across source systems, with no unified standard format.

## What constraints do these characteristics impose on workflow orchestration
Data comes from multiple heterogeneous systems, with inconsistent document structures. Workflow orchestration must support flexible access to multiple data sources and field mapping configuration.
Since data updates annually, workflows do not need high-frequency triggering. They can be set to scheduled trigger mode.
Steps including extracting business samples and vouchers, forming audit issues and rectification requirements, tracking rectification supporting materials and closure take a long time. These steps must be split into independent nodes, with timeout handling configured.
Errors in this category can lead to repeated audit issues, regulatory notifications, and other negative outcomes. Validation nodes must be added to the workflow to perform consistency checks on output audit issues and rectification ledgers, ensuring data accuracy.

## Configuration settings

| `variables` | Use custom global variables selected from the knowledge base, covering fields of core documents such as internal control self-assessment reports and audit working papers, calibrated based on actual measurements | Business documents for this category have diverse structures. The `variables` configuration enables unified mapping of fields from different source systems, adapting to the conditional configuration needs of judge nodes |
| `nodeId` | Bind the `nodeId` of the preceding node to each subsequent node, configured in process order | Ensures node execution order follows business logic, preventing workflow interruptions |
| Node timeout settings | `600 seconds` | The steps to extract business samples and vouchers take a long time, so sufficient execution time must be reserved |
| Workflow trigger method | Scheduled trigger, executed annually | Data for this category updates annually, so high-frequency workflow execution is unnecessary |
| Failure handling configuration | Configure exception alerts and retry mechanisms, with `2 retries` and a retry interval of `300 seconds` | Errors in this category have serious consequences, so workflow execution stability and recoverability must be ensured |
| Judge node condition configuration | Configure conditions based on document fields in `variables`, such as the closure status field of the rectification ledger | Validates the completeness of rectification closure, ensuring consistency between audit issues and rectification records |

## Three common misconfigurations
- Judge nodes in the workflow cannot be configured with conditions, and the interface shows no available fields. The cause is that global variables configured in `variables` are not bound to the document fields of the corresponding knowledge base, so the judge node cannot recognize valid configuration items.
- The workflow terminates directly after reaching the AI reply node, with no subsequent process triggered. The cause is that the trigger association of subsequent nodes is not configured via `nodeId`, or the preceding node state relied on by the trigger rule is not set correctly.
- After publishing the workflow to the Feishu bot, requests cannot be received, and a `404` status code is returned. The cause is that the callback address of the Feishu bot is not configured correctly, or external call permission settings are not enabled in the workflow.

## How to confirm the configuration is complete
- Check the global variable configuration, confirm that each option in `variables` is bound to the fields of the corresponding business document. Verify field mapping effectiveness by pulling a single test document.
- Trigger the local test mode of the workflow, view the execution logs of each node, and confirm that all nodes have an execution status of "Success" with no timeout or error messages.
- Call the workflow test interface, pass simulated business data, and verify that the conditional logic of the judge node correctly triggers the corresponding branch.
- Publish the workflow to the specified channel, initiate a test request, and confirm that the workflow executes completely to the end node with no mid-run termination.
