# Medical Insurance Fund Supervision and Audit: Declaration Material and Case File Review - Deployment and Upgrade

## What data for this category looks like
Data for this category comes from medical insurance intelligent monitoring systems, fund supervision rule bases, medical insurance settlement data, drug and consumable traceability codes, and complaint leads. The update frequency is monthly. Daily processed documents include audit notices, inspection work papers, suspicious item lists, interview records, decision letters, and rectification reports. Documents are mostly a mix of structured forms and unstructured text. Fields cover violation types, involved matters, rectification status, and other content. There is no unified fixed format, so adaptation is required for parsing and archiving of multiple document types.

## What constraints these characteristics impose on deployment and upgrade
Monthly updated supervision rules and settlement data require configuring a stable regular synchronization link during deployment, to avoid data lag affecting audit timeliness. Processing mixed document types requires adapting dual parsing configurations for structured forms and unstructured text during deployment. Access to multiple data sources requires pre-configuring connection parameters such as `REDIS_URL` and `MONGODB_URI` to ensure stable data pulling. Audit errors may lead to fund losses or administrative penalties, so a complete log retention and error alert mechanism must be configured during deployment to facilitate quick problem troubleshooting. ## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Exclusive connection string pointing to the medical insurance settlement data repository | Used to store suspicious item lists and rectification records during the audit process, ensuring stability for multi-terminal access |
| `REDIS_URL` | Connection address of the local cache cluster, with an expiration time configured to `600 seconds` | Caches frequently accessed supervision rules and complaint leads to reduce database query pressure |
| `STORAGE_S3_ENDPOINT` | Node address adapted to the internal object storage of the medical insurance system | Used to archive audit case files and original declaration materials to meet compliance storage requirements |
| `DB_MAX_LINK` | `100–150` | Adapts to the concurrency requirements of monthly batch data synchronization, avoiding synchronization failures caused by exhausted connections |
| `FILE_TOKEN_KEY` | Configured according to the internal key standards of the medical insurance system | Used to verify the legality of uploaded declaration materials and prevent unauthorized file access |
| `ROOT_KEY` | Exclusive key accessible only to deployment nodes | Ensures the security of system background configuration and prevents unauthorized modifications |

## Three common configuration mistakes
- The symptom is that the downloaded configuration file during deployment only displays a 404 status code and cannot load normally. The cause is that the storage node permission pointed to by `STORAGE_S3_ENDPOINT` is not correctly configured, leading to failed configuration file pulling.
- The symptom is that some historical audit data is lost after updating the image version and executing `docker-compose up -d`. The cause is that the persistent storage directory bound to the database corresponding to `PG_URL` was not mounted in advance, so data was not persistently stored.
- The symptom is that an unknown error is returned when calling the audit rule verification interface, and credential verification fails. The cause is that `FILE_TOKEN_KEY` is not correctly configured and does not match the system internal key, resulting in failed interface authentication.

## How to confirm configuration is complete
- Execute the `docker-compose config` command to check whether the configuration file syntax is correct, and confirm that all parameters such as `MONGODB_URI` and `REDIS_URL` have been correctly filled in.
- Upload a standard audit notice, initiate a single parsing test, check whether the parsing result includes core business fields, and confirm that the document parsing configuration is adapted to the current business scenario.
- Trigger a monthly data synchronization task, check the system logs, and confirm that there are no errors such as failed data pulling or connection timeouts.
- Log in to the background management interface, use `ROOT_KEY` to attempt to modify the system configuration, and confirm that the permission verification takes effect.
