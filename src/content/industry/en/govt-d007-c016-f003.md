# Medical Insurance Expense Settlement Audit: Declaration Materials and File Audit — Multi-turn Dialogue and Prompt Engineering

## What This Category's Data Looks Like
This category's data originates from the national medical insurance information platform, hospital HIS and medical insurance interfaces, medical insurance catalog and coding library, and cross-regional medical settlement platform. The update frequency is daily. Commonly processed documents include medical insurance settlement lists, expense details, medical record homepages, prescriptions, rejection payment lists, and settlement reconciliation statements. Core fields cover diagnosis and treatment item codes, pharmaceutical and consumable codes, expense amounts, insured person identifiers, settlement times, and other relevant items. Field names and formats have minor variations across documents from different sources.

## Constraints on Multi-turn Dialogue and Prompt Engineering Imposed by These Characteristics
Decentralized data sources lead to inconsistent field formats across different documents. Multi-turn dialogue must unify field parsing standards during interaction. Daily updated data sources require associated knowledge bases to perform daily incremental synchronization, to ensure the timeliness of audit rules and coding libraries. Documents contain multiple types of audit-related content. Prompt engineering must clearly distinguish the logical boundaries of verification links. Different scenarios of single or batch settlement require dynamic adjustment of context length, to avoid redundant information interfering with core verification. Audit results are directly linked to fund security, so multi-turn dialogue must strictly retain verification records for each step, to prevent audit deviations caused by lost context.

## Configuration Settings
This configuration is based on FastGPT v4.17.0. Specific parameter settings are as follows:

| Maximum Context Length | 800–1200 characters | Matches the number of fields and content length of single batches of medical insurance audit documents, avoids redundant information interfering with code matching |
| Context Recall Count | Top 3–5 entries | Medical insurance audit requires a limited number of associated catalog codes and settlement rules. Excessive recall increases verification burden |

| Conversation Timeout | 600 seconds | Adapts to the multi-turn verification time required for batch settlement audits, avoids mid-task interruptions |
| `chatId` Binding Rule | Assigned per single audit task | Distinguishes conversation contexts for different insured persons or settlement batches, avoids information confusion |
| Knowledge Base Update Frequency | Daily incremental synchronization | Matches the daily update rhythm of medical insurance data, ensures timeliness of audit rules and coding libraries |

## Three Common Misconfigurations
- A 401 No auth credentials found error occurs. The cause is failure to correctly configure interface authorization credentials for medical insurance data sources, and failure to bind valid session permission associations.
- Too many recalled medical insurance catalog entries from the knowledge base cause audit logic confusion. The cause is failure to set a reasonable context recall count, introducing irrelevant outdated coding rules.
- Parsed expense fields in multi-turn dialogue do not match the original documents. The cause is failure to specify the field range to be verified in prompt engineering, leading to context confusion between different settlement batches.

## How to Verify Proper Configuration
- A simulated medical insurance settlement detail is submitted, and code matching results returned by the dialogue are verified against the preset medical insurance catalog.
- The session details page is reviewed, and `chatId` binding to the unique identifier of the current audit task is confirmed, with no cross-session information confusion.
- `messages` context records are reviewed, and it is confirmed that all verification fields for each step are fully retained, with no omissions or confusion.
- A knowledge base synchronization task is triggered, and it is verified that the update is completed according to the daily incremental synchronization configuration.
- A continuous multi-turn verification request is initiated, and it is verified that the dialogue is not interrupted within 600 seconds, and the full audit process is completed.
