# Declaration Materials and File Review for Social Insurance Enrollment Registration and Payment Verification: HTTP Interfaces and External Systems
This document applies to FastGPT v4.17.0.

## What This Category of Data Looks Like
This category of data covers documents including social insurance enrollment registration forms, payment base declaration forms, personnel change forms, social insurance payment verification forms, and personal benefit records. Data sources include social insurance handling systems, tax social insurance collection systems, market entity registration information, and shared data from public security and civil affairs departments. The update frequency is daily. Data fields include personnel identity identifiers, labor relationship information, payment base, verified amount, and more. Units involve counts of people, monetary amounts, dates, and more. Data must be matched and verified against homologous data from multiple systems.

## Constraints on HTTP Interfaces and External Systems
Multi-source data docking requirements for this category mean HTTP interfaces must adapt to multiple external system types, including social insurance handling, tax collection, and government shared systems. Interface call frequency must align with the daily update rhythm. Precise matching of document fields requires interface parameters to cover all necessary fields such as personnel identity, labor relationship, and payment base. Interfaces must strictly align with the data format definitions of each system. The core reconciliation link with tax collection data requires interfaces to have stable response capabilities, to avoid reconciliation interruptions caused by delays. The personnel identity and labor relationship verification link requires calling external government data interfaces, which requires handling cross-system data format differences. Given the severe potential consequences of errors, interfaces must include complete exception capture and retry mechanisms.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| `Authorization` | Bearer plus access token obtained from government interfaces | Complies with identity authentication standards for government HTTP interfaces, ensuring legitimate interface call permissions |
| `variables` | Configure business variables such as insured personnel ID, declaration cycle, mapped to request fields required by external systems | Enables dynamic parameter injection to adapt to business requirements of different declaration batches |
| `responseData` | Extract three-level return fields: `code`, `message`, `data` | Standardizes parsing of external interface results to facilitate exception judgment and data extraction |
| Interface timeout period | 300-600 seconds | Adapts to actual time consumption of multi-system data verification, avoiding single call interrupting the workflow |
| Request retry count | 2-3 times | Addresses temporary call failures caused by network fluctuations, while avoiding duplicate submission risks |
| Parameter validation rules | Validate required field formats and completeness | Filters invalid requests in advance to reduce call pressure on external systems |

## Three Common Mistakes
- Phenomenon: The interface call returns a 504 Gateway Timeout status code. Cause: The timeout configuration was not adjusted based on multi-system verification time, and the default timeout duration is insufficient.
- Phenomenon: The business fields extracted from `responseData` are empty. Cause: Complete parameter mapping was not configured in `variables`, and request fields do not match the requirements of external systems.
- Phenomenon: Duplicate payment verification documents appear after multiple calls to the reconciliation interface. Cause: No idempotency handling logic was configured, and retry requests do not carry unique business identifiers.

## How to Confirm the Configuration is Correct
- Call the test interface address to verify that the token configured in `Authorization` passes the external system identity verification and returns normal business data.
- Pass preset test business variables to confirm that the parameters configured in `variables` are correctly mapped to the request fields of the external interface.
- Check the parsing rules of `responseData` to confirm that business data and exception prompt information returned by the external interface can be correctly extracted.
- Simulate temporary network fluctuation scenarios to verify that the configured retry mechanism can automatically restore calls without triggering duplicate submission issues.

The values provided are common starting points and should be measured against the reader's own samples.
