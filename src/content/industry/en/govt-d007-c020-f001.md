# Declaration Material and File Review for Territorial Spatial Planning Compilation and Implementation Evaluation: HTTP Interfaces and External Systems

## What this category of data looks like
This category of data primarily originates from the National Territorial Spatial Basic Information Platform, natural resource survey and monitoring data, population and economic statistics, and remote sensing imagery. Its update cycle is annual. Commonly processed documents include territorial spatial overall plans, detailed plans, special plans, planning implementation evaluation reports, and public opinion summaries. Most data combines spatial attributes and statistical attributes, covering fields such as spatial coordinates, planning indicators, and departmental comments. Units include hectares, square kilometers, population counts, and similar units. Some documents involve classified spatial information.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Annual updated data means interface call frequency should not be too high, and batch synchronization scenarios must be supported. Multi-source mixed data formats require interfaces to support receiving and parsing multiple types of data, including structured statistical data and unstructured spatial documents. Uploading large-volume documents such as public opinion summaries requires interfaces to support large file transfer capabilities. The classified nature of planning data requires interfaces to support local area network (LAN) deployment scenarios to ensure data transmission security. Regional-level planning data has a large volume, so interfaces must support chunked transfer and resumable upload to avoid request timeouts for single requests.

## How to configure settings
The following configurations are based on FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Carry a Bearer token with a 7-day validity period | Meet the permission control requirements of natural resource departments, and avoid risks of classified data access caused by token leakage |
| `variables` | Configure the data source address as an internal network resource path | Match the internal network deployment characteristics of the National Territorial Spatial Basic Information Platform, and ensure data transmission security |
| `responseData` | Verify that returned fields include preset planning review identifiers | Ensure interface returned data meets the review requirements of planning files, and prevent invalid data from entering the review process |
| File upload chunk size | 100–200 MB | Adapt to the upload requirements of large-volume spatial data for this category, and reduce transmission pressure on single requests |
| Timeout period | 600 seconds | Match the time consumption requirements of multi-source data synchronization, and avoid request interruptions caused by large data volumes |
| Retry count | 3 times | Address interface call failures caused by network fluctuations, and ensure the stability of data synchronization |

## Three common mistakes
- Symptom: `net::ERR_INCOMPLETE_CHUNKED_ENCODING` error occurs when other devices on the local network access the interface service, and the page fails to load. Cause: Cross-domain rules for internal network access are not configured, causing the browser to fail to properly receive chunked data returned by the interface.
- Symptom: Key parameters are returned empty when calling the file upload interface, making file submission impossible. Cause: The data source storage path in `variables` is not configured correctly, causing the interface to fail to read the local storage address of planning documents.
- Symptom: Request current limiting occurs when calling interfaces in batch, and single requests cannot be completed on time. Cause: A reasonable request interval strategy is not set, and multi-key request load balancing is not used, causing the interface call frequency limit to be exceeded.

## How to confirm configurations are correct
- Call the test interface to verify that the `Authorization` token can normally access the configured data source, and the returned `responseData` includes the pre-agreed planning review fields.
- Upload a document matching the characteristics of this category, and confirm that the interface can complete the upload and return a success identifier.
- Simulate simultaneous access by multiple devices, and confirm that the service can respond normally without cross-domain errors.
- Check the interface logs to confirm that the `variables` parameter of the request has correctly passed the data source configuration.
