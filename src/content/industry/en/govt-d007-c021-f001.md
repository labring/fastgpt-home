# Declaration Materials and File Review for Centralized Treasury Payment and Reimbursement Audit: HTTP Interfaces and External Systems

## What this category’s data looks like
Data for this category comes from centralized treasury payment systems, unified budget management systems, electronic invoice platforms, and contract management systems. The update frequency is daily. Commonly processed documents include payment applications, fund allocation plans, invoices, contracts, acceptance reports, reimbursement approval forms, and payment vouchers. This covers declaration and file review across the full chain of budget indicator verification, compliance check of documents, and payment execution. Data fields focus on the compliance and execution progress of fund payments.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Multi-source data access requires interfaces to adapt to the different data formats and authentication rules of four external system types, to prevent cross-system data alignment errors. The daily update frequency requires interface call frequency to match business processing rhythm. Do not occupy system resources too frequently, and do not cause audit delays by lagging behind processing timelines. Differentiated verification requirements for multiple document types require interfaces to support loading corresponding field verification rules based on document type, to ensure accurate matching of review logic for different materials. Additionally, the potential consequences of errors related to fund payments require interfaces to have complete exception capture and feedback mechanisms, to ensure the accuracy of audit results.

## How to set configurations

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Use Bearer Token format, set token validity period to 3600 seconds | Matches general authentication security requirements for financial systems, avoids frequent token refreshes that impact interface call efficiency |
| `variables` | Configure system identification and document type mapping variables, with a value range of 10–20 | Adapts to multi-system docking and verification logic switching requirements for multiple document types |
| `responseData` | Split response fields by document type, set maximum return field length to 800–1200 characters | Ensures the review system can accurately parse core verification results for different documents, avoids field overflow |
| External system call frequency | Set to 1 call every 5 minutes, total daily calls not exceeding 288 | Matches the daily update business frequency, avoids exceeding call limits of external systems |
| Field verification rule configuration | Calibrate based on actual testing | Adapts to differentiated verification requirements for different documents, ensures accurate review logic |
| Exception retry threshold | Set to 3 retries, with a 60-second retry interval | Addresses temporary network fluctuations or system response delays, reduces audit failure rate |

## Three common errors
- Phenomenon: The interface returns an empty `responseData` field, and the audit process triggers a payment reversal. Cause: Corresponding response field mapping rules are not configured for different document types such as payment applications and invoices, causing the format returned by the external system to fail to be parsed correctly, thus failing to complete compliance verification.
- Phenomenon: A 401 status code is returned when calling `Authorization` authentication, and interface calls are interrupted. Cause: The token validity period does not comply with the security specifications of financial systems, or automatic refresh logic is not configured, leading to expired authentication credentials.
- Phenomenon: A single interface call times out, and the file review task fails. Cause: No reasonable single call duration limit is set, and no exception retry mechanism is configured, leading to failure to complete data retrieval when the external system has high load.

## How to confirm the configuration is correct
- Initiate an interface test request for a single document type, confirm that `Authorization` authentication passes normally, and `responseData` returns the verification results for the corresponding document.
- View the `variables` configuration item, confirm that all connected external systems and document types are covered.
- Simulate a batch call scenario, verify that the number and format of returned interface fields meet business processing requirements.
- Trigger abnormal scenarios such as authentication expiration and network fluctuations, confirm that the exception retry logic takes effect as configured.
