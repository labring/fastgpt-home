# Declaration Material and File Review for Centralized Treasury Payment and Reimbursement Audit: Tool Calling and Plugins

## What data looks like for this category
Daily documents for this category include payment applications, payment plans, invoices, contracts, acceptance receipts, reimbursement approval forms, and payment vouchers. Data sources include centralized treasury payment systems, unified budget management systems, electronic invoice platforms, and contract management systems, with daily updates. Each document contains fields such as budget index number, economic classification code, invoice amount, contract number, and acceptance order number. Amounts are denominated in Renminbi yuan. Documents exist as a mix of structured forms and scanned copies.

## Constraints for tool calling and plugin workflows
Multiple system data sources require tool calling to support integration with multiple external system interfaces. This avoids repeated data pulling or data inconsistency. The daily update frequency requires plugin configuration to use scheduled trigger tasks. This ensures the latest data is used for audits. Mixed-format documents require tool calling to support both structured field extraction and unstructured text parsing. This adapts to document structures from different sources. The need for multi-field validation requires adding parameter validity checks in the tool calling step. This prevents audit failures caused by missing fields or incorrect formatting.

## Configuration settings
This configuration is based on FastGPT v4.17.0, with settings for core parameters such as `toolChoice` and `functionCall` as follows:
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `toolChoice` | `auto` | Adapts to multiple tool calling scenarios including payment application verification, invoice comparison, and contract validation |
| `functionCall` | Enabled | Supports structured parameter passing, facilitating validation of core fields such as budget indexes and economic classifications |
| Single tool call timeout | 60 seconds | Addresses response delays from multiple system interfaces, preventing mid-task audit interruptions |
| Tool call failure retry count | 2–3 times | Addresses temporary network fluctuations or interface jitter, reducing audit failure rates |
| Tool call result context retention length | 800–1200 characters | Retains sufficient audit-related information while controlling context usage |

## Three common configuration mistakes
- Phenomenon: A `connect ECONNREFUSED 172.23.0.2:3001` error is returned during tool calling. Cause: The plugin's target service address was not configured correctly, or the target service is not running normally.
- Phenomenon: A parameter parsing error is returned during tool calling. The original verification logic cannot be recognized. Cause: The embedding model version used for tool calling was not locked. After the system automatically updates the model, the adaptation logic was not adjusted synchronously.
- Phenomenon: Interface call current limit errors occur during high-frequency batch audits. Cause: Reasonable call frequency limits were not set, exceeding the call upper limit of external systems or platforms.

## How to confirm the configuration is correct
- Manually trigger a single tool call. Check whether document data from the corresponding system can be pulled correctly. Verify that returned result fields match business requirements.
- Simulate a tool call failure scenario. Check whether the preset retry logic is triggered. Confirm the retry count meets configuration requirements.
- View system logs. Confirm the actual effective status of the `toolChoice` and `functionCall` parameters, with no abnormal errors.
- Run a batch audit task. Check that the tool call context length meets expectations, with no overflow or truncation.

The values provided are common starting points and should be measured against the reader's own samples.
