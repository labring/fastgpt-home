# Declaration Materials and File Audit for Centralized Treasury Payment and Reimbursement Review: Deployment and Upgrade

## What Data for This Category Looks Like
The data for this category comes from centralized treasury payment systems, unified budget management systems, electronic invoice platforms, and contract management systems. The update frequency is daily. Documents processed daily include payment applications, fund appropriation plans, invoices, contracts, acceptance receipts, reimbursement approval forms, and payment vouchers. Each individual document contains fields such as budget indicator code, economic classification code, ticket number, and contract performance amount. Individual business data is associated with multiple types of business documents, requiring matching of information consistency across systems.

## What Constraints These Characteristics Impose on Deployment and Upgrade
The cross-system data source nature of this category requires configuring stable links for multi-source data docking during deployment, to avoid data synchronization failures caused by system compatibility issues. The daily update frequency requires ensuring that incremental synchronization tasks are not interrupted during the upgrade process, or performing a full backup before executing the upgrade operation. The associated verification requirement for multiple types of business documents requires presetting field matching rules in the knowledge base configuration, and synchronously updating the rule templates during upgrades to avoid audit logic failure. The adaptation requirements for domestic chips and operating systems require pre-verifying the compatibility of the deployment package in the Kunpeng 920 chip and Kylin V10 operating system environment, to avoid runtime exceptions after deployment.

| `FILE_TOKEN_KEY` | `32-character random string` | Encrypted access tokens must be generated for downloaded ticket and contract files to prevent unauthorized access to sensitive financial data |
| `DB_MAX_LINK` | `20–30 connections` | The number of database connections synchronized daily for this category must adapt to concurrent requests from multiple systems, to avoid synchronization failures caused by exhausted connections |

## Three Common Mistakes
- Symptom: After upgrading to FastGPT v4.9.13, incremental synchronization tasks fail frequently, and logs show database connection timeouts. Cause: The `DB_MAX_LINK` configuration was not adjusted according to version iteration requirements, and the connection threshold from the old version cannot adapt to the new multi-system synchronization tasks.
- Symptom: Tool calls for speech input or attachment parsing fail inside a Docker deployment container, with a permission denied prompt. Cause: The container was not started with root privileges, and the mount directory for dependent tools was not configured in the deployment script, resulting in the inability to install necessary tools inside the container.
- Symptom: After deployment on the Kylin V10 system with Kunpeng 920 chips, the knowledge base cannot load contract documents. Cause: The architecture compatibility of the deployment package was not verified in advance, and non-adapted binary dependency packages were used, resulting in document parsing failure.

## How to Confirm Configurations Are Correct
- Run a database connection test command to verify that the `MONGODB_URI` and `REDIS_URL` configurations can establish normal connections.
- Upload a test invoice and contract document to verify that the `STORAGE_S3_ENDPOINT` configuration can properly store the files and return access links.
- Trigger an incremental synchronization task, check the task logs to confirm that data synchronization is normal, and verify that the `DB_MAX_LINK` configuration adapts to current concurrent requirements.
- Access the frontend configured domain name to verify that the `FE_DOMAIN` configuration can properly load the interface and call backend APIs.
