# Student Financial Aid and Subsidy Review: Application Materials and Case Review – Vector Models and Indexing

## What Data for This Category Looks Like
Data for this category comes from the national student funding management information system, school student status systems, civil affairs low-income and special hardship data, and fiscal payment systems. Updates occur once per semester. Daily processed documents include family economic hardship certification forms, aid application forms, scholarship and grant review forms, disbursement lists, and public notification materials. Data fields include student status identifiers, hardship certification numbers, bank card information, aid application information, and more. The structure of individual documents is relatively fixed; some associated data requires cross-system stitching to complete verification.

## Constraints on Vector Models and Indexing
Documents from cross-system sources have minor format differences. Field standardization must be completed before building valid indexes. Semester-level batch updates involve large data volumes, so index construction must adapt to batch import processes to improve efficiency. Some documents contain sensitive personal information, so corresponding permission verification rules must be configured for vector storage. Individual associated documents, such as complete application materials stitched across systems, have long lengths. Chunking rules must be planned appropriately to avoid splitting core information. Review scenarios require precise matching of core fields such as hardship certification and student status, so index recall must prioritize frequently associated business fields.

The following configurations are compatible with FastGPT v4.17.0.

| Chunk Length | 800–1200 characters | Adapts to the typical length of student financial aid application materials, preventing information from being split across chunks |

| Similarity Threshold | 0.75–0.85 range | Balances precision and recall for review scenarios, filtering low-relevance invalid matches |

| `defaultToken` | Calibrated based on actual testing | Adapts to resource constraints for local deployments, avoiding vector model call timeouts |

## Three Common Configuration Mistakes
- Symptom: Vector model-related errors are prompted when calling the knowledge base, or valid retrieval results cannot be generated. Cause: The `defaultToken` parameter is not correctly configured in the configuration file, or the text-embedding-ada-002 model is not added to the legal call channels, resulting in vector generation failures.
- Symptom: Search response times out after the knowledge base index is completed, and search speed is too slow. Cause: Index batch import parameters are not adjusted for semester-level batch data, or a reasonable single search limit is not configured, leading to excessive resource occupation after vector recall.
- Symptom: The relevance of retrieval results does not meet review requirements, with too many irrelevant materials or too few valid matches. Cause: A reasonable similarity threshold is not set based on the review scenario, or chunk length configuration is improper, leading to core information being split.

## How to Confirm Configurations Are Properly Set
- Import a typical document set from a single semester to complete indexing, and check that the system logs have no abnormal errors.
- Enter a query statement targeting a specific student financial aid application, check whether the retrieval results match the core business requirements, and adjust configuration items as needed.
- View the vector model call records, confirm that the `maxToken` and `defaultToken` parameters do not trigger call restrictions, and the process proceeds normally.
- Test retrieval requests related to sensitive information, confirm that permission configurations meet data security requirements.
