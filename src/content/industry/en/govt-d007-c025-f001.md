# Declaration Materials and Case Review for Work Safety Hazard Inspection and Governance: HTTP Interfaces and External Systems

## What this category of data looks like
Data sources for this category include work safety supervision systems, enterprise hazard self-inspection systems, law enforcement inspection records, and accident statistics systems. The update frequency is daily. Commonly processed documents include hazard inspection lists, hazard management ledgers, rectification notices, review records, and major hazard suspension and supervision orders. Fields include hazard ID, rectification responsible entity, rectification deadline, review results, supervision level, and others. A unique identifier from the corresponding supervision system must be associated. There are no fixed uniform unit requirements.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Data for this category comes from multiple business systems and is updated daily. This requires interfaces to support incremental pulling and multi-source data integration. Commonly processed document types are diverse, and fields must be associated with supervision system unique identifiers. This requires interfaces to support parameter transfer for different document structures. The consequences of business errors are severe. This requires interfaces to have clear error returns and retry mechanisms. Core fields such as rectification deadline and supervision level must be matched accurately. This requires interface requests to carry complete business fields to avoid audit process interruptions caused by missing parameters.

## How to configure settings
The following configurations are based on the interface setup logic of FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {{secret_key}}` | Complies with HTTP interface standard identity authentication methods, and adapts to permission verification requirements of multiple business systems |
| `variables` | Preset business fields including hazard ID, rectification responsible entity, rectification deadline | Documents in this category must be associated with supervision system unique identifiers and core business fields to ensure complete parameter transfer |
| `responseData` | Return a three-level structure of `code`, `message`, `data` | Facilitates quick identification of interface call results and error causes, and adapts to the verification requirements of severe business error consequences |
| Interface timeout period | 600 seconds | Some documents in this category require integration of data from multiple systems, and pulling and integration take a long processing time to avoid process interruptions due to timeout |
| Number of documents per request | First 50 entries | The daily updated document volume requires reasonable control of single interface load to avoid overloading external systems |
| Single pull data volume | 800–1200 characters | Adapts to the average length of single documents in this category, balancing interface transmission efficiency and data integrity |

## Three common mistakes
- An interface call returns `Request failed with status code 400`. The cause is missing core business fields required by this category (such as hazard ID, rectification responsible entity) or field formats that do not comply with the verification rules of the external supervision system.
- Interface proxy requests experience sustained lag. The cause is that the number of documents submitted in a single request exceeds the load limit of the external system, and the limit on the number of documents per request specified in the configuration is not followed.
- An exception occurs during the final step of interface file upload. The cause is that the `Authorization` authentication parameter is not configured correctly, leading to identity verification failure and inability to complete the upload process.

## How to confirm correct configuration
- Call the test interface, check whether the `Authorization` parameter can pass the identity verification of the external system and return normal authentication results.
- Pass preset business fields to verify whether the `variables` parameter can be correctly transferred to the external system, with no missing fields or format errors.
- Trigger an interface call, check whether the `responseData` can correctly parse the returned three-level structure to quickly locate the call result.
- Simulate the daily updated document volume, submit according to the configured number of documents per request, and confirm that the external system does not report overload errors.
