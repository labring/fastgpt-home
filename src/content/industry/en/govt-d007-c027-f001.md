# Bidding and Tendering for Engineering Construction Projects: Declaration Materials and File Review — HTTP Interfaces and External Systems

## Data Details for This Category
Data for this category originates from national public resource trading platforms, local public resource trading platforms, project approval systems, and bidding and tendering supervision systems. The update frequency is daily.

Commonly processed documents include tender announcements, qualification pre-qualification documents, bid documents, bid evaluation reports, and successful bid candidate announcements. Bid documents require verification of qualifications, performance, and bills of quantities. Bid evaluation reports require validation of expert scoring records and check-in information. Data fields cover core business items such as project sections, qualification requirements, and bid evaluation rules.

## Constraints on HTTP Interfaces and External Systems
These characteristics impose constraints on the HTTP interfaces and external systems link.

Dispersed data sources require interfaces to support return formats from multiple platforms. Unified request headers must be configured to adapt to authentication rules of different data sources. The daily update frequency requires interface scheduling to align with the daily business update rhythm, to avoid repeated data pulls or missed data.

The need to process multiple types of business documents requires interface request parameters to support switching verification logic based on document type. Errors in this link can lead to suspension of bid results and project delays. Interfaces must be configured with clear timeout and retry mechanisms to ensure stability of data pulling and verification.

## Configuration Settings
The following configurations are organized based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `Authorization` | Carry authentication tokens from the business system | Adapt to authentication requirements of multiple data sources and ensure legitimacy of interface calls |
| `variables` | Configure business variables such as project sections and qualification requirements | Implement personalized verification logic for different bidding and tendering projects |
| `responseData` | Filter return fields by business document type | Only retain core data required for declaration materials and file review |
| Interface timeout period | 600 seconds | Match the maximum time required for business data pulling and avoid process interruptions due to network fluctuations |
| Retry count | 3 times | Address temporary network anomalies and ensure success rate of data pulling |
| Request frequency limit | 100 times per 10 minutes | Comply with interface call frequency requirements of public resource trading platforms |

## Three Common Misconfigurations
- After calling the interface, `responseData` does not include knowledge base association fields. The symptom is that the file review knowledge base referenced in this review cannot be traced. The cause is that no knowledge base binding parameter was configured in `variables`, and no association was established between the interface and the corresponding file review knowledge base.
- The interface frequently triggers rate limit errors. The symptom is a 429 status code returned. The cause is that the request frequency was not configured according to the public resource trading platform's frequency limits, exceeding the platform's allowed call upper limit.
- The document data pulled by the interface is incomplete. The symptom is that bid documents for some sections were not pulled. The cause is that no filtering rules in `variables` were configured according to the business document type, leading to failure to recognize declaration materials for some sections.

## How to Confirm Configurations Are Correct
- View the `responseData` returned by the interface, confirm that it includes core business fields of bidding and tendering projects, and verify that the fields match the configured filtering rules.
- Simulate temporary network interruptions or delays, verify that the interface triggers the retry mechanism after timeout, and that the retry count meets the configured requirements.
- Send a request carrying an incorrect authentication token, confirm that the interface returns a 401 status code, and verify that the verification logic of the `Authorization` parameter is effective.
- Compare the pulled documents with the daily updated data from the public resource trading platform, confirm that the update frequency meets the business scheduling requirements.
