# Market Entity Registration and Licensing: Declaration Materials and File Review - HTTP Interfaces and External Systems

## What data for this category looks like
The daily documents for this category include establishment registration applications, articles of association, shareholder resolutions, residence certificates, business licenses, food business license applications, and similar materials. Data sources are the full-process electronic enterprise registration system, the National Enterprise Credit Information Publicity System, the electronic business license system, and the residence information database. The update frequency is daily. Data fields include entity name, residence address, shareholder information, license type, and other relevant items. Most document structures combine structured forms and unstructured supporting materials. Some fields must undergo cross-verification with public data from external systems.

## What constraints these characteristics impose on HTTP interfaces and external systems
Since data sources include multiple independent external systems, HTTP interfaces must support parallel calls to multi-source data and result aggregation, to avoid interruptions caused by a single request relying on one data source. Documents include structured forms and unstructured supporting materials, so interfaces must support parameter submission and parsing in different formats. Daily updated data sources require interfaces to use appropriate caching strategies, balancing data timeliness and call frequency. The verification link relies on cross-checking multiple fields, so interfaces must support batch parameter verification and accurate positioning of error returns, to facilitate issue tracing during subsequent file review.

## How to configure settings
The following configurations are based on FastGPT v4.17.0.
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| Interface authentication method | `Authorization` header carrying Bearer token | Complies with general external system authentication specifications, and adapts to permission verification requirements for multiple data sources |
| Request timeout duration | 600 seconds | Covers total time for multi-source data calls, and prevents request failures due to delayed responses from external systems |
| Cache validity period | 24 hours | Matches the daily update frequency of data sources, and ensures data timeliness |
| Single request character limit | 800–1200 characters | Matches the average length of a single document in declaration materials, and prevents data overload during single-batch processing |
| Variable parameter scope | `variables` limited to preset fields including entity name, residence address, etc. | Matches the fixed field structure of declaration materials, and reduces invalid parameter transmission |
| Response data parsing rule | `responseData` only extracts core fields required for verification | Filters redundant data, and improves processing efficiency for file review |

## Three common configuration mistakes
- Symptom: After calling the interface, the specified knowledge base and question-and-answer process are not associated, and the returned results do not match the preset file review rules. Cause: The knowledge base association parameter is not configured in `variables`, or the context binding between the interface and the conversation process is incorrect.
- Symptom: Text-to-SQL queries return empty results, the interface call shows no errors but no data matches. Cause: The fields of declaration materials are not mapped to valid conditions for SQL queries, and parameters have not undergone format verification.
- Symptom: The speed of knowledge base QA split indexing is too slow, and timeouts occur when batch creating file collections. Cause: The character limit for single split documents is not set, leading to excessive data volume in a single batch exceeding the interface's carrying capacity.

## How to confirm correct configuration
- Call the interface and pass simulated declaration material parameters, check whether the fields returned in `responseData` include preset verification items.
- View interface logs, confirm that the `Authorization` authentication header is correctly carried, and there are no authentication failure error reports from external system calls.
- Trigger the retry logic, simulate a 5xx status code returned by an external system, and confirm that the interface automatically initiates a retry request.
- Bind the interface to the conversation guidance process, verify whether the corresponding knowledge base content can be correctly associated after declaration information is entered.
