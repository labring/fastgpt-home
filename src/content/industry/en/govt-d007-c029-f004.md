# Submission Materials and Case File Review for Urban Environmental Sanitation and Urban Management Law Enforcement Cases: Workflow Orchestration

## What this category of data looks like
This category of data typically originates from urban management law enforcement platforms, urban operation grid platforms, video surveillance systems, and public complaint work orders. The update frequency is daily. Commonly processed documents include inspection records, case filing approval forms, on-site photos, rectification orders, penalty decisions, and case closure reports. Common fields include case number, violation location, party information, evidence collection time, and rectification status. Some documents include unstructured image and video attachments.

## What constraints do these characteristics impose on the workflow orchestration link
Multi-source data access requires workflows to adapt to diverse input formats, including structured tabular data and unstructured image and video attachments. Corresponding parsing nodes must be configured. High-frequency daily updated data requires workflows to support scheduled or real-time triggering to avoid data backlogs. Diverse and closely related document types require nodes to be orchestrated in the order of the case process. This ensures field validation and data transfer for each stage of filing, evidence collection, review, and case closure. Additionally, errors in this category of cases directly impact law enforcement compliance. Workflows must include validation steps to prevent law enforcement disputes caused by missing evidence or incorrect parameters.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| File link variable | Bind to case attachment fields returned by the law enforcement platform | Adapt to this category’s primary data source of law enforcement platform attachments, and call external links via `variables` |
| HTTP request node timeout | 600 seconds | Reserve sufficient time for local image base64 encoding and law enforcement platform interface calls, and comply with node rules for FastGPT v4.17.0 |
| Context window | First 1000–1500 characters | Case file review requires association with case history records; limiting window length avoids context overflow |
| Classifier keyword threshold | 0.80–0.90 | Violation types for urban management law enforcement cases are mostly fixed categories, with matching accuracy calibrated via actual testing |
| `nodeId` mapping rules | Bind unique identifiers for each business stage | Ensure precise association between each workflow node and avoid execution confusion |
| Attachment size limit | 50 MB | Match the standard attachment size for on-site photos and law enforcement documents in this category |

## Three common misconfigurations
- Symptom: HTTP request returns empty results or status code 400. Cause: Case attachment links are not correctly bound via `variables`, leading to missing parameter values in the request body.
- Symptom: Workflow displays duplicate execution node logs. Cause: Trigger rules for `nodeId` are not correctly configured, leading to multiple data sources triggering the same stage simultaneously.
- Symptom: AI chat node fails to recognize initial case queries. Cause: Case information submitted by users is not passed to the AI chat node, leading to a lack of contextual basis for review.

## How to confirm the configuration is complete
- Manually enter an attachment link for a test case, and check if the file link variable can correctly extract the address and trigger subsequent parsing nodes.
- Call the local image base64 encoding script interface, and verify that the HTTP request node can correctly return the encoded result.
- Trigger the workflow, and check if the classifier can associate initial case information with the context of the AI chat node.
- View the workflow run logs, and confirm that each node executes in the preset order, with no timeout or duplicate trigger records.
