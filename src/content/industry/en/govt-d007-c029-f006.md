# Declaration Materials and Case File Review for Urban Environmental Sanitation and Urban Management Law Enforcement Cases: Citation Sources and Traceability

## What this category of data looks like
This category of data is typically sourced from urban management law enforcement platforms, urban operation grid platforms, video surveillance systems, and citizen complaint work orders. Updates occur daily. Daily documents include inspection records, case filing approval forms, on-site photos, rectification orders, penalty decisions, and case closure reports. Common data fields include case unique identifiers, violation location information, responsible entity records, and disposal process node markers. Some documents include multimedia evidence materials and timestamps.

## What constraints these characteristics impose on the citation sources and traceability link
Data sources for this category are scattered, and update frequency is high. This requires the traceability link to support rapid synchronization of newly added law enforcement data each day. Document types include text and multimedia materials. An association mapping must be established between text fragments and corresponding on-site photos and official documents. Some multimedia materials require additional association with timestamps and location identifiers. Core case fields such as case number and violation location must be used as key identifiers for traceability matching to avoid confusion across cases. At the same time, the rigor of law enforcement procedures requires that traceability results be directly linked to the originally entered document version, and cannot rely solely on sliced text fragments.

## How to set the configurations
These configurations are adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | Matches the core fragment length of a single law enforcement document, avoids truncating critical evidence |
| `responseData` | Enabled | Used to associate the storage path and metadata of original documents, supports traceability viewing |
| `detail` | Enabled | Displays the specific location of cited fragments in the original document, assists in verifying evidence validity |
| Maximum single recall count | Top 5–7 entries | Covers the number of associated documents common to a single case, avoids redundant recall |
| Context window | 12000–15000 token | Adapts the splicing length of multi-source law enforcement data, prevents context overflow |

## Three common configuration mistakes
- A string of red numbers is returned when calling the system. The cause is that the `responseData` configuration is not enabled correctly, causing the system to fail to return valid source metadata fields.
- The original file details corresponding to the cited fragment cannot be viewed. The cause is that the storage path of the original document is not associated, or the original document metadata was not retained during knowledge base import.
- The number of recall results does not match expectations. The cause is that the maximum single recall count is set to top 3 entries, or precise filtering is not performed based on the case unique identifier, leading to recall of unrelated law enforcement documents.

## How to confirm the configuration is correctly set
- After triggering case review questions and answers, check whether the reply includes the source document identifier of the cited fragment.
- Click the source link in the reply, verify that you can jump to the storage location of the corresponding original document.
- Adjust the `quoteMaxToken` parameter to 1000 token, observe whether the truncation of the cited fragment meets expectations.
- Check the knowledge base import log, confirm that the original document metadata has been fully synchronized to the system.

The values provided are common starting points and should be measured against the reader's own samples.
