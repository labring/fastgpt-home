# Tendering and Procurement Compliance Management: Declaration Materials and File Review - Workflow Orchestration

## What This Category of Data Looks Like
Data for this category comes from enterprise procurement platforms, public resource trading platforms, supplier databases, contract management systems, and audit issue databases, with a daily update frequency.
Commonly processed documents include procurement plans, requirement specifications, bidding documents, bid evaluation records, contracts, acceptance receipts, and supplier complaint materials.
Data fields cover procurement methods, budget basis, supplier qualification requirements, scoring methods, performance acceptance standards, and more.
Some documents require association with cross-system procurement process numbers and supplier filing information.

## What Constraints These Characteristics Impose on the Workflow Orchestration Step
Cross-system data sources require workflows to support cross-data source call nodes. This ensures fields from different documents such as procurement plans and bid evaluation records can be reused across nodes.
Daily data update rhythms require workflows to be configured with scheduled trigger nodes. This avoids using outdated supplier database or audit issue database data.
Differential verification needs for multiple document types require workflows to set branch judgment nodes. Exclusive compliance verification rules are configured for different documents such as bidding documents and acceptance receipts.
Compliance risk-related accountability mechanisms require workflows to retain complete node execution logs and file archive entry points.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Scheduled Trigger Cycle | Daily 2:00 AM - 4:00 AM | Matches the daily business data update rhythm, and avoids peak procurement business hours |
| `variables` | Bind procurement process numbers and supplier filing IDs | Enables cross-node field reuse, and avoids duplicate entry of cross-system data |
| Branch Judgment Rules | Split verification branches by document type | Adapts to differentiated verification logic for multiple document types such as procurement plans and bidding documents |
| `nodeId` | Assign a unique identifier to each verification node | Facilitates log tracking and node association for file archiving |
| View Source Switch | Configure according to the node's business scenario | Disables view source permissions for discipline inspection and audit-related nodes, retains visibility for procurement execution-related nodes |
| Text Extraction Model | Calibrate based on actual testing | Adapts to field extraction requirements for long texts such as bidding documents and bid evaluation records |

## Three Common Mistakes
- No usable nodes appear after importing a workflow template. The symptom is that the import prompt shows success, but no nodes appear on the canvas. The cause is that the `nodeId` configuration in the template does not match the built-in node ID rules of the current environment, and node mapping has not been completed.
- Confused configuration of the view source switch for some nodes. The symptom is that sensitive verification nodes accidentally open original text view permissions, or business nodes are incorrectly disabled. The cause is that visibility is not distinguished and configured according to the node's business scenario, and general rules are applied directly.
- The text extraction node cannot select a model. The symptom is that there are no available model options in the drop-down menu. The cause is that the call permission for the corresponding model has not been configured in the system backend, or the node is not bound to the correct data source type.

## How to Confirm the Configuration Is Complete
- Trigger a test workflow. Check whether the `variables` fields are correctly passed across nodes, and whether procurement process numbers match the source data.
- View node logs. Confirm that the scheduled trigger node executes according to the preset cycle, with no timeout or call failure records.
- Randomly select documents of different types. Verify whether the branch judgment node correctly triggers the corresponding verification branch.
- Check the view source switch configuration for sensitive nodes. Confirm that discipline inspection and audit-related nodes do not have original text view permissions enabled.
- All verification actions must be performed in the workflow editor of FastGPT v4.17.0.
