# Enrollment and Student Status Management: Application Materials and File Review - Deployment and Upgrade

## What the data for this category looks like
Data sources for this category include the National Primary and Secondary School Student Status Management System, local enrollment platforms, household registration and real estate data platforms, and school academic affairs systems. Daily processed documents include enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, and student status change approval forms. Data is updated daily. Core fields cover student identity identifiers, household registration and real estate association information, student status change approval status, and admission batches. Each document typically contains multi-dimensional associated fields. Cross-system verification of information consistency is required during review.

## What Constraints These Characteristics Impose on Deployment and Upgrade
Data for this category is sourced across multiple systems and updated daily. During deployment, ensure stable multi-source data docking to avoid review process blockages caused by database connection interruptions. Core documents include multi-dimensional associated fields. File storage must support batch associated data transmission for single documents. The daily review process handles large volumes of structured and semi-structured materials. Reserve sufficient resources during deployment to handle concurrent requests. During upgrades, retain the original student status data verification logic to avoid risks of duplicate or missing student status from configuration changes.

## How to Set Configurations
These configurations are based on FastGPT v4.17.0. Adjust specific parameter values based on actual deployment environments.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | 20–30 connections | Meets concurrent access requirements for daily updated student status and enrollment data, prevents connection pool exhaustion |
| `MONGODB_URI` | Point to a local or dedicated hosted MongoDB instance | Stores bulk documents such as enrollment plans and admission rosters, ensures data read/write performance |
| `REDIS_URL` | Configure to the local Redis service address | Caches frequently accessed student status verification rules and user session information to reduce database load |
| `STORAGE_S3_ENDPOINT` | Endpoint address adapted to local file storage or dedicated object storage services | Stores uploaded paper scans and electronic documents such as enrollment application forms and transfer applications |
| `FILE_TOKEN_KEY` | Random string calibrated through actual testing | Ensures access permissions for uploaded files, prevents unauthorized access to sensitive student status materials |
| `ROOT_KEY` | Configure as a high-complexity string | Restricts access to backend management interfaces, prevents unauthorized modification of review configurations |

## Three Common Configuration Mistakes
- The agent backend cannot access uploaded files after calling the file upload API. The interface returns timeout or permission errors. This occurs when `FILE_TOKEN_KEY` is not correctly configured, causing token verification failure, or the storage service referenced by `STORAGE_S3_ENDPOINT` has not opened the required port.
- Workflow and knowledge base configurations are cleared after deploying with docker-compose. This occurs when the database storage volume for `MONGODB_URI` is not persisted, leading to data loss after container restart, and persistent caching for `REDIS_URL` is not configured.
- FastGPT fails to start on a server without a GPU, returning an OCI runtime create failed error. This occurs when container resource limits are not correctly configured, the image version is incompatible with the host kernel, or correct startup parameters for the GPU-free environment are not specified.

## How to Verify Correct Configuration
- Run a local file upload test: upload a simulated enrollment application form, confirm the storage service receives the file normally and returns a valid access path.
- Connect to the database instance specified by `MONGODB_URI`, verify that core collections and data such as enrollment plans and student status information exist.
- Call the backend management interface, use `ROOT_KEY` to confirm permission verification takes effect, and reject requests without the correct key.
- View Redis connection logs to confirm the service configured via `REDIS_URL` has established a normal connection and cached verification rules.
