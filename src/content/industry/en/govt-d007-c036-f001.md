# Administrative Service Item Catalog and Service Guide Maintenance: Declaration Materials and File Review via HTTP Interfaces and External Systems

## What This Category of Data Includes
The daily operation and maintenance documents for this category include six types: basic administrative service item catalogs, implementation lists, service guides, standard material catalogs, flowcharts, and frequently asked questions. Data sources are the national basic administrative service item catalog, administrative licensing item list, power and responsibility list, and local administrative service item databases, with a monthly update frequency. Data fields cover standard administrative service entries such as item codes, acceptance conditions, application material lists, and service processes. Data formats vary slightly across different levels of government service platforms, so synchronization must strictly follow the field structure defined by official specifications. This category falls under the rule base maintenance work for government services, and does not handle individual applicant’s specific application cases. It is only responsible for standardized updates to official item catalogs and guides. This document is written based on FastGPT v4.17.0.

## Constraints for HTTP Interfaces and External Systems
The monthly update rhythm requires interface calls to adapt to a fixed cycle, and call frequency should not be set too high to avoid exceeding the rate limiting thresholds of government service platforms. The need to synchronize multiple types of documents requires interfaces to support pulling by data type, ensuring unified field validation rules for different documents. The strict requirements for standard government service fields mean that returned interface data must be filtered and validated to prevent non-standard fields or empty fields from causing inconsistencies between the local catalog and the standards of higher-level authorities. Format differences across platforms at different levels require interfaces to support custom field mapping to adapt to the data structures of local government systems. The time-consuming process of comparing higher-level catalogs with local implementation lists requires interfaces to support incremental synchronization to reduce resource consumption from full pulls.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {Government Platform Exclusive Token}` | Matches the standard authentication format for government service interfaces to secure access permissions |
| `variables` | `{"targetData": ["catalog", "guide", "material"], "updateCycle": "30 days"}` | Adapts to the multi-type document and monthly update requirements of this category |
| `responseData` | `filterEmptyFields: true, includeMeta: true` | Filters invalid fields and retains audit-related metadata for subsequent validation |
| Batch Pull Limit | No more than 800 items per request | Adapts to the single-interface return limit of local government service item databases to avoid interface timeouts |
| Call Timeout Setting | 600 seconds | Adapts to the time requirements of batch pulls for government interfaces to avoid premature synchronization interruptions |

## Three Common Misconfigurations
- Empty fields returned by interfaces, leading to incomplete local service guide fields. This occurs when the empty field filtering rule for `responseData` is not configured, and redundant empty fields returned by the government service platform are synchronized.
- Frequent 429 status codes triggered by interface calls, interrupting synchronization tasks. This occurs when the monthly update rhythm is not adapted to, and an excessively high call frequency is set, exceeding the rate limiting thresholds of the government platform’s interfaces.
- Inconsistent item standards between synchronized local data and higher-level authorities, resulting in rectification notices. This occurs when the `variables` configuration is not used to specify standard data types for synchronization, and non-official temporarily adjusted documents are mistakenly synchronized.

## How to Verify Proper Configuration
- Call the test interface, check that the request header carries the correct `Authorization` token, and confirm the returned status code is 200.
- Review the fields returned in `responseData`, confirm that only standard administrative service item fields are included, with no redundant empty values.
- Simulate a monthly synchronization task, confirm that the call interval is no less than 28 days, and no rate limiting errors are triggered.
- Compare the locally synchronized catalog with the public catalog of the higher-level government service platform, confirm that field matching meets requirements.
