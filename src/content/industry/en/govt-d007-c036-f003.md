# Maintenance of Government Service Item Catalog and Service Guide: Declaration Material and File Review - Multi-turn Dialogue and Prompt Engineering

## What This Category of Data Looks Like
Daily documents for government service item catalog and service guide maintenance include basic government service item catalogs, implementation lists, service guides, standard material catalogs, flowcharts, and frequently asked questions.
Data sources include the national basic government service item catalog, administrative licensing item list, power and responsibility list, and local government service item databases. Updates occur monthly.
Document structures contain fixed fields such as item code, item name, acceptance conditions, application material list, and service process. Each field must strictly match the corresponding relationship between the superior catalog and the local implementation list.

## Constraints for Multi-turn Dialogue and Prompt Engineering
The monthly update frequency requires multi-turn dialogue tools to support regular full synchronization of item data, to avoid expired context.
The multi-field document structure requires prompts to focus strictly on validating a single field, to prevent LLMs from diverting attention.
Cross-level data sources require multi-turn dialogue tools to differentiate between superior catalogs and local implementation lists, to prevent inconsistent standards.
The time-consuming comparison process requires multi-turn dialogue tools to support field-by-field validation, to reduce manual repetitive work.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Generate a unique identifier for the current maintenance item | Distinguish maintenance conversation contexts for different items, to avoid cross-item data confusion |
| `messages` | Retain the first 12 rounds of dialogue, truncate old field comparison drafts | Government service item documents have many fields; overly long contexts reduce LLM validation accuracy |
| `variables` | Bind two global variables: item code and update cycle | Automatically import specific current maintenance item information and monthly update rhythm, to match business rules |
| Single recall count | Top 6 entries | Local government service item database has moderate scale; excessive recall increases LLM processing load |
| Timeout threshold | 700 seconds | Full item comparison and field validation require long processing time, to avoid mid-process interruptions |
| Maximum context length | 10000 characters | Adapt to the number of fields in government service item documents, to avoid exceeding LLM context limits |

## Three Common Misconfigurations
- Symptom: Unable to query conversation history in MongoDB storage. Cause: `chatId` is not bound to a specific maintenance item, so conversation contexts are not correctly associated with storage identifiers.
- Symptom: Knowledge base search works normally, but the AI conversation link does not reference government service item documents. Cause: The prompt does not explicitly specify prioritizing calls to the local government service item database documents, so the LLM calls irrelevant knowledge base content.
- Symptom: Unable to implement continuous multi-turn questioning and result merging for the same input content. Cause: `variables` are not configured to bind global task variables, so multi-turn questioning cannot share context information for the current item.

## How to Verify Proper Configuration
- Access the conversation debugging interface of FastGPT v4.17.0, enter the test item code, and check if `chatId` automatically generates a unique identifier and displays in the context panel.
- Trigger a field validation conversation, and check if the knowledge base recall results include relevant documents from the local basic government service item catalog.
- Configure a continuous questioning task, enter test content, and check if tasks execute sequentially in the preset prompt order and merge final results.
- View system logs to confirm that conversation history is correctly written to storage, with no missing fields or timeout errors.
