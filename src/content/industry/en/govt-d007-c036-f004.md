# Maintenance of Government Service Item Catalogs and Service Guidelines: Declaration Materials and File Review — Workflow Orchestration

## What the data for this category looks like
The core data for this category originates from the national basic government service item catalog, administrative licensing item list, power and responsibility list, and local government service item databases. The update frequency is monthly. Daily maintained documents include the basic government service item catalog, implementation list, service guidelines, standard material catalog, flowcharts, and frequently asked questions. Data fields cover item codes, item names, acceptance conditions, application material lists, service processes, and more. Individual item documents have a large number of fields, and must align with the standards of superior catalogs.

## Constraints for Workflow Orchestration
Because data sources include national and local government service catalogs, workflows must include cross-source data pull steps to ensure consistent standards between local-level items and superior catalogs. The monthly update cycle requires workflows to support scheduled batch task triggers, reducing manual repetitive work. The multi-field document structure that requires integrity checks needs embedded field verification nodes to block non-compliant item data. Additionally, the time-consuming task of comparing superior catalogs with local implementation lists should be split into single-item processing units, to prevent overall process disruption from single-node timeouts.

## Configuration Settings
This configuration is based on FastGPT v4.17.0. The following are workflow configuration recommendations tailored to this category:

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `variables` | Bind workflow global token and item code variables | Meet the requirement of passing global parameters when calling MCP tools |
| Tool call trigger rule | Automatically trigger based on node output results | Adapt to business scenarios where the model independently selects tool calls |
| Single-node timeout period | 600 seconds | Match the reasonable maximum time limit for a single comparison between superior catalogs and local lists |
| Field verification threshold | 800–1200 characters | Match the standard length requirements for service guideline fields |
| DingTalk webhook request timeout | 30 seconds | Prevent workflow blocking from prolonged waiting |
| `nodeId` | Bind the IDs of verification nodes and data pull nodes | Precisely control workflow transition order and execution logic |

## Three Common Misconfigurations
- Symptom: Global variables are empty when calling MCP tools in the workflow, and logs show "target variable not found". Cause: The required token or item code variables were not bound in the `variables` configuration item.
- Symptom: The workflow cannot automatically trigger tool calls and always executes a fixed process. Cause: The automatic trigger rule based on node output results was not configured, and only manual triggering was set.
- Symptom: The DingTalk webhook does not push exception notifications, and logs show "request succeeded but no message sent". Cause: The DingTalk webhook trigger condition was not set to node failure, and only node completion triggering was configured.

## How to Verify Successful Configuration
- Manually trigger the single-item maintenance workflow, review the MCP tool call logs, and confirm that the global token and item code variables were passed correctly.
- Simulate a node verification failure scenario, and check if the DingTalk webhook sends an exception notification to the specified recipient channel.
- Adjust the transition order of workflow nodes, verify that the `nodeId` configuration works as expected, and confirm that the process jumps according to plan.
- Trigger a batch update task, check the single-node runtime duration, and confirm that it does not exceed the preset 600-second threshold.
