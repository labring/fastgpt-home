# Declaration Materials and File Review for Government Procurement Projects: Workflow Orchestration

## What this category of data looks like
Data for this category comes from the China Government Procurement Network, local government procurement websites, fiscal integration systems, procurer budget systems, and supplier credit records. The update frequency is daily. Documents processed daily include procurement requirements, procurement plans, bidding documents, tender documents, bid evaluation reports, winning announcements, procurement contracts, and responses to inquiries. Each document type has fixed business fields: for example, procurement requirements include project budget and procurement content, while tender documents include qualification certificates and quotation lists. The data links four types of stakeholders: procurers, fiscal supervision departments, procurement agencies, and evaluation experts. Each file case entry is tied to a unique procurement project identifier.

## What constraints these characteristics impose on the workflow orchestration link
Daily updated data sources require workflows to be configured with scheduled pull rules to avoid missing the latest procurement announcements or inquiry information. Data formats vary across multiple source systems, so workflows need a unified format verification node to ensure consistent processing of file case data from different channels. Different document types require dedicated parsing rules: for example, tender files need to verify qualification fields, while bid evaluation reports need to extract evaluation opinions. Strict error consequences require adding pre-verification steps in workflows to avoid bid invalidation or regulatory penalties caused by data errors. File case data must also be fully retained for retrospective review, so workflows must keep complete call context and operation records.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| Context Retention Rounds | First AI call node `1 round`, second AI call node `5 rounds` | Matches the business needs of single material verification and multi-round file case review in government procurement audits, and aligns with actual usage scenarios |
| File Upload Limit | `1000 MB` | Adapts to the upload requirements of large bidding and tender documents in government procurement projects |
| `variables` | Bind procurement project ID, supplier unified social credit code | Accurately match corresponding file case data, prevent confusion of review content across different projects |
| Workflow Trigger Rule | Triggered on new data updates, interval `600 seconds` | Fits the daily update frequency of data, balances real-time performance and system load |
| Exception Node Retry Count | `3 times` | Prevents the overall review process from being interrupted by a single failed AI call, meets the rigor requirements of government procurement processes |

## Three Common Errors
- Phenomenon: When accessing the workflow for the same procurement project ID multiple times, the historical data returned by the first AI call node is inconsistent. Cause: The context scope bound by `variables` is not configured per business needs, and redundant multi-round conversation data is incorrectly retained.
- Phenomenon: After local deployment, the `CUSTOM_READ_FILE_URL` environment variable is configured, but an analysis failure error appears when uploading government procurement files. Cause: The environment variable is not set to the correct `config.json` path, or external access permissions for the corresponding port are not enabled.
- Phenomenon: The problem classification node in the workflow returns empty results. Cause: The node’s data source is not bound to the official government procurement data source, so it cannot match the classification rules for corresponding business documents.
