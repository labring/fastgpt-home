# Declaration Materials and Case File Review for Legal Compliance and Major Risk Management: Multi-turn Dialogue and Prompt Engineering

## Data Profile for This Category
This category covers daily work documents from entities including central enterprise legal compliance departments and chief compliance officer offices. Documents include compliance risk lists, contract legal review opinions, major issue legal opinions, compliance review forms, and violation report investigation reports. Data sources include enterprise contract management systems, compliance risk databases, legal and regulatory repositories, case management systems, and reporting platforms. Update frequency is once per month. Document structures vary widely by use case. Compliance review forms include approval workflow fields. Violation report investigation reports include clue details and processing progress fields. Contract legal review opinions include risk point annotations and modification suggestions.

## Constraints for Multi-turn Dialogue and Prompt Engineering
Data sources are diverse and heterogeneous. Document formats and fields differ across systems. Multi-turn dialogue must first confirm the current document type before calling corresponding context for analysis. Data updates monthly. Prompts must explicitly specify only using synced compliance repository data to avoid introducing outdated information. The most time-consuming risk identification and review process includes multiple steps. Multi-turn dialogue must split tasks by review phase, focusing only on the current phase per turn. This avoids overloading inference with too much context loaded at once. Error consequences are severe. Multi-turn dialogue context must be strictly linked to the corresponding review batch. This ensures each round of compliance recommendations matches the current materials and avoids logical deviations.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Conversation ID Binding | Use the `chatId` parameter to bind the current review batch | Ensures multi-turn dialogue is linked to the same review task and avoids context confusion |
| Historical Dialogue Context Limit | First 20 turns of dialogue | Compliance review proceeds in phases; excessive historical content dilutes the core logic of the current review |
| Prompt Variable Binding | Use the `variables` parameter to bind the compliance data source version | Compliance data updates monthly; explicitly specifying the current compliance repository version avoids using outdated data |
| Dialogue Context Cache Duration | 7200 seconds | A single major issue review workflow typically takes no more than 2 hours; automatically releases context resources after timeout |
| Multi-turn Trigger Condition | Trigger based on the latest user input from the `messages` parameter | Review workflows must advance based on the currently submitted material phase to ensure each dialogue focuses on the current task |
| Context Recall Count | First 3 similar review records | Valid reference materials for similar compliance reviews typically do not exceed 3; excessive content increases inference load |

## Three Common Misconfigurations
- Workflow dialogue shows failure but model backend has response logs: The interface displays a call failure, but backend logs show model return content. The cause is incorrect configuration of the `chatId` parameter for binding dialogue context, which prevents the workflow from linking to historical dialogue status.
- Cannot pass historical dialogue into nodes: When calling the searchTest node, past dialogue content cannot be retrieved. The cause is failure to specify the `messages` parameter in the configuration to pass the historical message list, only using a single input to trigger the workflow.
- Exception errors are not logged: Application dialogue encounters errors but no corresponding log entries exist. The cause is failure to enable dialogue log storage configuration, or setting the cache duration too short which causes logs to be cleaned up early.

## How to Confirm Proper Configuration
- Trigger a test dialogue, check if the historical dialogue displayed on the interface includes the expected `messages` parameter content.
- View backend logs to confirm the compliance data source version bound by the `variables` parameter matches the current configuration.
- Simulate multi-turn input, check if the prompt for each dialogue loads according to the phase, and does not repeat pre-executed logic.
- Submit an exception test case, confirm that error information is correctly recorded in the logs.
