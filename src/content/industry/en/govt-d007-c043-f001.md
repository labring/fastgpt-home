# Special Equipment Safety Supervision: Declaration Materials and File Review - HTTP Interfaces and External Systems

## What Data for This Category Looks Like
Data for this category primarily comes from special equipment safety supervision systems, inspection and testing institution systems, user unit ledgers, and operator certificate databases. The data update frequency is once per month. Daily circulated documents include use registration certificates, periodic inspection reports, maintenance records, hidden danger rectification notices, accident reports, and operator certificates. Core fields include device unique ID, inspection validity period, operator qualification ID, hidden danger rectification completion status, and more. All documents must match associated information across the full device lifecycle to ensure consistency of verification logic.

## Constraints Imposed on HTTP Interfaces and External Systems
Decentralized data sources require interfaces to support integration with multiple external systems with different data formats and authentication rules. The once-per-month update frequency means interface calls do not need to be triggered frequently, and can be run on a fixed schedule or in response to business events. The need for associated verification across multiple document types requires that parameters passed by the interface include associated fields such as device unique identifier and verification type, to avoid errors in cross-document verification. The accuracy of core business fields directly affects supervision results, requiring that interface return data include complete verification fields, and that failure retry and exception alert mechanisms be configured to handle severe errors such as device deactivation or administrative penalties.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer example value` | Complies with HTTP interface authentication standards, adapts to FastGPT v4.17.0 interface call specifications, and ensures consistent authentication for multi-system integration. |
| `variables` | Fixed parameter set including device ID, verification type, and document source identifier, for example `Device ID=TS2024001,Verification Type=Periodic Inspection` | Clarifies the business context of interface calls, avoids parameter ambiguity, and adapts to verification requirements across multiple scenarios. |
| `responseData` | Structured data including device verification status and document integrity verification results, formatted as standard JSON | Enables quick parsing of verification results, and adapts to automated data access requirements of supervision systems. |
| Interface call timeout | `300-600 seconds` | Parsing and verification of documents related to special equipment may involve pulling data from multiple systems, so sufficient response time must be reserved to avoid timeout interruptions. |
| Interface retry count | `2-3 times` | Addresses temporary fluctuations in external systems, ensures core verification processes are not interrupted by single exceptions, and aligns with the low-frequency call scenario of monthly updates. |
| Number of documents passed per call | `Top 5` | Aligns with the business volume of single verification, avoids excessive interface load, and adapts to the typical volume of declaration materials in supervision scenarios.

## Three Common Mistakes
- Symptom: The interface returns a 401 Unauthorized status code, or the interface prompts authentication failure. Cause: The `Authorization` parameter is not configured correctly, or a dedicated secret key is not generated for different business scenarios, leading to authentication conflicts that prevent normal integration with external systems.
- Symptom: The `responseData` returned by the interface lacks the device inspection validity period field, or the field is empty. Cause: The correct verification type parameter is not specified in `variables`, and the external system does not return complete business fields, causing the verification logic to fail to execute normally and preventing completion of declaration material and file verification.
- Symptom: The docx-format declaration material provided in the URL cannot be parsed, and the interface returns a document parsing failure prompt. Cause: Parsing rules adapted for docx format are not configured, or the full path of the document URL is not correctly passed in the call parameters, leading to failure to pull the target file and complete material verification.

## How to Verify Proper Configuration
- Call the test interface, check that the `Authorization` parameter is correctly included, and that the returned HTTP status code is 200 OK.
- Review whether the fields returned in `responseData` include core business required information such as device ID and verification result, and that the field format matches expectations.
- Pass call parameters including the docx document URL, and confirm that the interface can normally pull and parse the target file.
- Simulate a temporary exception scenario for external systems, and check whether the interface triggers the preset retry mechanism and alert.

The values given are common starting points and should be measured against the reader's own samples.
