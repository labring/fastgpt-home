# Submission Materials and Case Review for Social Assistance and Minimum Living Standard Guarantee: HTTP Interfaces and External Systems

## What Data for This Category Looks Like
The core business documents for this category include minimum living standard guarantee application forms, household economic status verification reports, household survey forms, democratic appraisal records, public notice materials, and assistance approval forms. Data mainly comes from the low-income population dynamic monitoring platform, resident household economic status verification system, and cross-department shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, and tax authorities. Data update frequency is monthly. Documents focus on household economic status, member relationships, and assistance application processes. Fields cover applicant subject information, income and property details, verification results, approval opinions, and similar items. Common units include natural person identification numbers, monetary amounts, and dates.

## Constraints for HTTP Interfaces and External Systems
Data sources include multiple cross-department shared systems, so interfaces must be compatible with return formats and identity verification rules of different data sources. The monthly update requirement means interface call frequency should not be too high, to avoid triggering call restrictions from cross-department systems. Documents include multiple types of verification materials, so interfaces must support precise filtering of field data for corresponding cases to avoid invalid information overload. Fields related to household economic status and member relationships involve privacy compliance, so interfaces must carry identity verification parameters that meet regulatory requirements to ensure secure data transmission. In addition, field naming varies across departments, so interfaces must support basic field mapping logic to adapt to business processing workflows.

## Configuration Settings
The following configurations apply to FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {cross-department data interface API key}` | Meets identity verification requirements for cross-department shared systems and ensures data access compliance |
| Request timeout setting | 300–600 seconds | Adapts to the average response duration of cross-department data pulling and prevents interrupted calls |
| `variables` | Pass the unique identifier of the applying household and the application batch number | Precisely filter verification data for the corresponding case and narrow the interface return scope |
| `responseData` | Only retain applicant subject information and income and property detail fields | Streamline returned content to align with FastGPT's context processing rules |
| Data cache period | 30 days | Matches the monthly update rhythm of data for this category and balances data timeliness and call overhead |

## Three Common Configuration Errors
- Interface calls return empty fields. This occurs when the correct unique identifier of the applying household is not passed in `variables`, so the interface cannot locate verification data for the corresponding case.
- Interface calls return a 401 Unauthorized status code. This happens when the `Authorization` parameter is not configured correctly, and an expired or unauthorized API key is used.
- Frequent current limiting prompts from cross-department systems appear during interface calls. This occurs when the call frequency is not adjusted to match the monthly update business rhythm, and too many duplicate requests are sent in a short period.

## How to Confirm Configurations Are Correct
- Initiate a test call and check whether the returned fields cover the core document fields required for the business. Set field matching rules according to business requirements.
- Verify the validity of the `Authorization` parameter, confirm that identity verification is passed when calling cross-department interfaces, and follow the requirements of the corresponding platform for verification methods.
- Test the effectiveness of the request timeout setting, confirm that the call duration falls within the response range of cross-department systems, and adjust rules based on actual call results.
- Verify the data cache period setting, ensure that the data update frequency aligns with business requirements, and adjust logic according to the monthly update business rhythm.
