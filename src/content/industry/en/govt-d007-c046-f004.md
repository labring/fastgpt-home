# Declaration Materials and Case Review for Social Assistance and Minimum Living Standard Allowance Audit: Workflow Orchestration
Reference only; verify against the target FastGPT release and deployment documentation.

## What this category of data looks like
Data for this category comes from the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-department shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, and tax authorities. The update frequency is once per month.
Documents processed daily include minimum living standard allowance application forms, family economic status verification reports, household investigation forms, democratic appraisal records, public notice materials, and assistance approval forms. Document fields cover family income and property details, family member relationships, household investigation records, appraisal opinions, approval node information, and other standard fields. No additional custom non-standard fields are included.

## What constraints these characteristics impose on the "workflow orchestration" link
Cross-department multi-source data access requires configuring multi-node data pulling and integration links in workflow orchestration to avoid single-node request overload or insufficient permissions.
Monthly updated data requires setting timed trigger variable synchronization nodes to ensure the workflow calls the latest verification data.
Processing multiple types of documents requires configuring different parsing and verification rules by document type to adapt to the verification logic of different fields.
Family economic status verification and household investigation are the most time-consuming links. The workflow must split and process subtasks in parallel, and set timeout retry nodes to prevent process interruption.
The consequences of incorrect or missed assistance require adding multi-level verification links in the process, and triggering manual intervention branches for abnormal data.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Variable synchronization trigger timing | 2 AM on the 1st of each month | Matches the monthly update cycle of cross-department data to ensure the latest data is called |
| Multi-source data node configuration | Call by data source groups defined in `variables` | Splits nodes by data source to avoid excessive single-node request load |
| Document parsing rules | Match corresponding field extraction templates by document type | Adapts to the field structures of different documents such as minimum living standard allowance application forms and verification reports |
| Verification node threshold | Calibrate family income difference threshold based on actual measurements, member relationship matching degree ≥90% | Covers conventional verification requirements of civil affairs business and reduces manual review workload |
| Timeout retry configuration | Set single-node timeout to 600 seconds, retry count 2 times | Adapts to the delay of cross-department data requests and prevents early process termination |
| Branch trigger condition | Bind abnormal data nodes by `nodeId` to trigger manual review branches | Accurately locates error links and speeds up intervention processing |

## Three common mistakes
- Phenomenon: When calling cross-department shared data via an HTTP node, returned fields cannot be correctly referenced using {{}} format in subsequent nodes. Cause: Did not use / pattern to extract variables, still relied on {{}} format for reference, resulting in variable parsing compatibility failure.
- Phenomenon: The workflow terminates directly after reaching the family economic status verification node, without triggering subsequent approval or public notice processes. Cause: No timeout retry rules configured, cross-department data request delay exceeds the preset threshold, causing the process to end directly.
- Phenomenon: A global variable configured as a knowledge base selection type cannot set condition matching rules in the judge. Cause: Did not bind this variable to the workflow's input node, causing the judge to fail to read variable parameters for verification.

## How to confirm the configuration is correct
- Manually trigger the workflow once, check if the variable synchronization node loads the latest cross-department data of the current month.
- Simulate abnormal data input, confirm that the judge triggers the corresponding manual review branch.
- View node logs, confirm that the request delay of multi-source data nodes does not exceed the preset threshold, and the retry mechanism triggers normally.
- Test different types of declaration documents, confirm that the parsing rules correctly extract information from corresponding fields.
