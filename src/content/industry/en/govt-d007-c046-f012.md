# Social Assistance and Minimum Living Standard Guarantee Application Materials and Case Review: Deployment and Upgrade

## What the data for this category looks like
Data sources for this category include the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-departmental shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, and tax authorities.
The update frequency is once per month.
Daily processed documents include minimum living security application forms, family economic status verification reports, household survey forms, democratic appraisal records, public notice materials, and assistance approval forms.
Core fields cover family income, total property, family member relationships, and assistance qualification judgment items.
All data must be linked to household entities. No scattered business data across multiple entities is permitted.

## Constraints on Deployment and Upgrade
These characteristics impose the following constraints on the deployment and upgrade phase:
Cross-departmental multi-source data access requires configuring multiple types of database connections during deployment, to adapt to the interface formats of different systems.
Monthly update cycles require configuring regular synchronization tasks after deployment, to ensure data timeliness.
Fixed field structures for core documents require matching corresponding data storage rules during deployment, to avoid field omissions or association errors.
Error consequences must be strictly controlled. The upgrade phase must retain a rollback mechanism, and configure failure alerts and log retention rules, to prevent sensitive review data leaks or processing errors.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | 15–25 connections | Cross-departmental multi-source data access requires a stable connection pool, to avoid frequent connection disconnections that affect verification efficiency |
| `MONGODB_URI` | Fill in according to the locally deployed MongoDB instance address | Used to store case review historical records and temporary processing data, adapting to the unstructured storage needs of multiple documents |
| `REDIS_URL` | Configure as the local Redis service address, set timeout to 300 seconds | Used to cache frequently accessed verification data and session status. Monthly updated data caching reduces the number of repeated calls to cross-departmental systems |
| `STORAGE_S3_ENDPOINT` | Fill in according to the endpoint of the local object storage service | Used to store uploaded scanned paper application materials and public notice photos, adapting to the storage needs of large-capacity unstructured documents |
| `ROOT_KEY` | Generate a dedicated key according to the deployment environment | Used to manage system permissions, ensuring only authorized personnel can access sensitive assistance review data |

## Three Common Mistakes
- Uploading application materials fails. Logs show the file size exceeds the limit. The cause is failure to adjust the local deployment file upload threshold. The default configuration only supports small files, which cannot accommodate documents such as scanned household survey forms.
- After upgrading to FastGPT v4.17.0, parameter exceptions occur when calling third-party model channels. The cause is that the new version adjusted the configuration format for model channels, and the original associated configuration was not updated synchronously.
- After configuring multiple data source connections, cross-departmental data synchronization tasks fail frequently. The cause is that a reasonable `DB_MAX_LINK` connection count was not set, leading to connection pool exhaustion and inability to establish new database connections.

## How to Verify Configuration Completion
- Test uploading a 2 MB scanned application material. Confirm the upload succeeds and the storage path is accessible normally.
- Run a simulated family economic status verification task. Check whether the data synchronization result matches the data source from the cross-departmental system.
- Check the system logs. Confirm that the number of connections in the database connection pool is within the preset range, with no frequent disconnections or exhaustion.
- Trigger a rollback test. Confirm that the post-upgrade configuration can be rolled back normally to the previous stable version.

The values provided are common starting points, and should be evaluated against the deployment’s own sample data.
