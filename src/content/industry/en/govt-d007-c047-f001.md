# Administrative Penalty Case File Handling: Declaration Materials and Case File Review — HTTP Interfaces and External Systems

## What data for this category looks like
Data for this category comes from administrative law enforcement case handling systems, law enforcement recorder footage, the National Enterprise Credit Information Publicity System, and departmental supervision databases. The update frequency is daily. Daily documents include on-site inspection records, interrogation records, evidence lists, prior administrative penalty notification letters, hearing notification letters, penalty decisions, and service receipts. Core fields focus on illegal fact determination, discretionary benchmark application, and penalty decision content. All documents must be linked to corresponding law enforcement subjects and involved subject information. No custom units are used.

## What constraints do these characteristics impose on HTTP interfaces and external systems
The data characteristics of this category impose multiple constraints on HTTP interface and external system configuration. Multiple data sources require interfaces to support authentication methods for different external systems, and adapt to transmission formats for structured fields and unstructured image files. The daily update frequency requires interfaces to set reasonable request cycles, to avoid frequent calls that exceed external system load. Diverse daily document structures require interfaces to pass mapped fields for law enforcement subjects, involved subjects, and document content, to ensure accurate data association. Law enforcement case files have strict compliance requirements. Interface transmission must guarantee data integrity and traceability, and retain complete request and response logs for subsequent case file reviews.

## How to configure settings
Based on the HTTP node functionality of FastGPT v4.17.0, configuration items and recommendations are as follows:

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Request timeout | 600 seconds | Matches the average interface response duration of administrative law enforcement case handling systems, to avoid process blocking caused by long waits |
| Retry strategy | Retry 2 times after failure, 30 second interval | Addresses temporary network fluctuations or short periods when external systems are unavailable |
| Maximum single request data size | 1000 MB | Adapts to conventional transmission size limits for law enforcement image files, to avoid exceeding external system reception limits |
| `Authorization` | Bearer {Law Enforcement System API Key} | Complies with standard authentication specifications for external administrative law enforcement case handling systems, to secure interface access permissions |
| `variables` | Structured fields including case ID, evidence list, and penalty decision content | Meets core data transmission requirements for administrative penalty case files |
| `responseData` | Fixed format including review status, review results, and error information | Facilitates automated aggregation and review of subsequent case file review results |

## Three common configuration errors
- Symptom: The interface call returns the error `tls: failed to verify certificate: x509: certificate signed by unknown authority`. Cause: Trusted certificate verification rules for the external system are not configured, or self-signed certificates are not imported into the trust list.
- Symptom: The `variables` field received by the HTTP interface is empty, and case file core data cannot be matched. Cause: Case fields returned by the administrative law enforcement case handling system are not correctly mapped in the workflow node, or the variable transmission format does not meet interface requirements.
- Symptom: No expected review result feedback is received after the interface call, and the returned status code is 400. Cause: Required fields are not passed in accordance with the administrative penalty case file document structure, such as case ID, evidence list, etc., causing the external system to fail to recognize the request content.

## How to confirm correct configuration
- Send a simulated request with test data that conforms to administrative penalty case file formats, and check if the interface returns the expected response structure.
- View interface call logs, and confirm that the `Authorization` authentication information is correctly included, and request parameters match the configured items.
- Verify that the external system has received the passed `variables` field data, and that the field content matches the test data.
- Simulate an interface call failure scenario, and check if the preset retry and log retention mechanisms are triggered.

The values provided are common starting points, and should be evaluated against the sample data of the relevant deployment.
