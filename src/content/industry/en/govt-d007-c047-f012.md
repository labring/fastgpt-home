# Administrative Penalty Case File Handling: Declaration Materials and Case File Review - Deployment and Upgrade

## What the data for this category looks like
Core data for this category originates from administrative law enforcement case handling systems, law enforcement recorder footage, the national enterprise credit information publicity system, and departmental supervision databases. Updates are synchronized daily.
Commonly processed documents include on-site inspection records, interrogation records, evidence lists, prior administrative penalty notification letters, hearing notification letters, penalty decisions, delivery receipts, and similar materials. The core structure centers on illegal facts and penalty decisions, with fields including law enforcement subject, illegal circumstances, discretion basis, penalty content, delivery status, and more. A single case file entry includes multiple types of associated documents and metadata.

## What constraints these characteristics impose on deployment and upgrade
Data sources for this category are scattered. They include unstructured footage and transcript files. Deployment requires adaptation to multi-data source connection configurations.
Daily updated case file data requires a scheduled synchronization mechanism during deployment. This avoids data lag.
Diverse document types and sensitive law enforcement information require upgrade steps to ensure storage and permission parameters comply with confidentiality requirements.
Errors directly impact law enforcement legality. Deployment and upgrade links must include failure rollback and data backup mechanisms. These prevent case file data loss or review process interruptions caused by configuration changes.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `20–30` | Administrative penalty case file data updates daily, and each entry has a relatively large size. Maintaining this connection count balances query efficiency and server resource usage |
| `MONGODB_URI` | Address of the MongoDB instance linked to the local unit's administrative law enforcement case handling system | Used to store metadata for law enforcement recorder footage, evidence lists, and other unstructured documents, adapting to storage needs for multiple types of case file data |
| `REDIS_URL` | Access address configured for the local private Redis service | Used to cache frequently accessed case file summaries and discretion benchmark data, reducing query pressure on the primary database |
| `STORAGE_S3_ENDPOINT` | Official endpoint address corresponding to the local unit's unified cloud storage service | Used to store large files such as law enforcement recorder footage and scanned penalty decision documents, meeting cross-departmental file sharing requirements |
| `FILE_TOKEN_KEY` | Randomly generated 32-bit encrypted string | Used to generate temporary access tokens for case file documents, ensuring only authorized personnel can access sensitive law enforcement materials |
| `ROOT_KEY` | Super permission key configured per the local unit's permission hierarchy specifications | Used to manage core system configurations and permissions, complying with security management requirements for law enforcement agencies |

## Three common configuration mistakes
- Symptom: After upgrading FastGPT v4.17.0, running `docker compose down` followed by `up` causes case file data loss. Cause: The database directory corresponding to `MONGODB_URI` was not backed up in advance, and persistent storage parameters were not configured. Local database files are cleared during the upgrade process.
- Symptom: When running a custom case file review script, external parameters print as empty. Cause: Permission parameters for `FILE_TOKEN_KEY` or `ROOT_KEY` are not configured correctly. The script cannot obtain valid system access permissions, so it fails to read configuration parameters.
- Symptom: Multiple law enforcement personnel cannot share access to the same knowledge base. Cause: `FE_DOMAIN` is not configured to the local unit's unified domain name. Cross-account session permission verification fails, preventing collaborative sharing of the knowledge base.

## How to confirm configurations are correct
- Run a database connection test script to verify that configurations for `MONGODB_URI` and `PG_URL` can successfully read historical case file data.
- Upload a simulated on-site inspection record file to verify that `STORAGE_S3_ENDPOINT` can store the file normally and generate a valid access token.
- Submit a single case file review request, observe system logs, and confirm that the `DB_MAX_LINK` configuration does not trigger connection limit exceeded errors.
- Log in to the system using two different accounts, verify that shared access to the same knowledge base is possible, and confirm that the `FE_DOMAIN` configuration is active.
