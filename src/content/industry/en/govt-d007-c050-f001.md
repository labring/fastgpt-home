# Performance Evaluation of Fiscal Expenditures: Declaration Materials and File Review — HTTP Interfaces and External Systems

## What this category of data looks like
Data for this category comes from the unified budget management system, project declaration materials, fund payment data, business system ledgers, and satisfaction surveys. The update frequency is annual. Commonly processed documents include performance target forms, self-assessment forms, performance evaluation reports, supporting material lists, and rectification reports. Fields involved include budget units, project numbers, performance indicators, fund allocation amounts, and others. There is no unified fixed unit. The corresponding field format must be matched based on specific business scenarios. Data is jointly maintained by the fiscal bureau’s performance division, budget units, third-party evaluation institutions, and competent departments. The number of documents involved in a single review batch fluctuates with project scale.

## What constraints these characteristics impose on the HTTP Interfaces and External Systems link
The annual update requirement means interfaces must support batch pulling of full annual data. This avoids triggering system rate limits from frequent calls.
Connecting multiple data sources requires adapting to identity verification rules of different fiscal systems. The `Authorization` parameter must comply with each system’s token format.
Documents have many fields and complex relationships. Interface requests must carry complete `variables` parameters, including identifiers such as budget units, project numbers, and review cycles. This ensures accurate data is pulled.
Verifying the correspondence between fund expenditures and performance targets requires interfaces to support cross-data-source associated queries. Review logic cannot be completed using only a single data source.

## How to configure settings

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Interface timeout | `600 seconds` | Annual batch data transfer takes a long time. 600 seconds covers full data transfer and processing |
| Request header configuration | Include the `Authorization` parameter | All fiscal systems require identity verification. The token rules of the corresponding system must be matched |
| Request variable mapping | Bind `variables` parameters such as annual cycle, budget units, and project numbers | This ensures the interface pulls review data for the corresponding cycle and entity |
| Response data validation | Check if `responseData` contains core fields such as performance targets and supporting materials | This prevents missing fields from preventing completion of the review process |
| Batch request threshold | `10 items per request` | Excessive single-batch data volume easily triggers system rate limits. 10 items per request is a safe range |
| Retry count | `3 times` | This covers occasional network fluctuations and temporary interface failures |

## Three common configuration errors
- Phenomenon: The HTTP interface call returns the `401 Unauthorized` status code, or prompts that the token is invalid. Cause: The `Authorization` parameter is not configured correctly. The token verification rules of the corresponding fiscal system are not matched.
- Phenomenon: The `responseData` returned by the interface lacks performance target form fields. This causes subsequent review links to fail to complete verification. Cause: The request `variables` parameter does not carry complete identifiers such as budget units and review cycles. The system returns incomplete data as a result.
- Phenomenon: Timeout interruptions occur during batch interface calls. This causes workflow execution to fail. Cause: A reasonable interface timeout period is not set. The single-batch data pull volume exceeds the system’s carrying limit.

## How to confirm the configuration is correct
- Call the test interface. Check if the `Authorization` parameter is included in the request header. Confirm that the returned result includes an identity verification pass identifier.
- Verify that the `variables` parameter covers all necessary identifiers for the current review task. Ensure the interface pulls the correct data range.
- Check if the fields in `responseData` include performance targets, supporting materials, and other content required for this review. Confirm data integrity.
- Simulate a batch call scenario. Check if the interface returns complete data within the set timeout period. Verify that the retry logic takes effect.
