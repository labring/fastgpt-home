# Declaration Material and Case Review for Flood Prevention, Disaster Mitigation and Emergency Duty: Model Access and Configuration

## What this category of data looks like
Data for this category primarily comes from meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Daily processed documents include duty logs, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Data update frequency is daily; some real-time monitoring data updates at the second level. Document fields include rainfall and water level values, disaster severity levels, material quantities, number of transferred and resettled people, and similar items, with corresponding units such as millimeters, cubic meters per second, tons, people, and others.

## What constraints these characteristics impose on the model access and configuration step
Data in this category is multi-source, heterogeneous, and updates frequently. Some monitoring data is pushed in real time, so model access configuration must support multi-format data input. Documents contain professional hydrological and meteorological fields, so the model must support professional term parsing. The configuration must therefore balance context carrying capacity and content accuracy. Case review requires retrospective review of historical duty and consultation records, so the configured context window must be large enough to hold summarized content from multiple historical documents. At the same time, since review results are directly linked to emergency response, the configuration must prioritize output accuracy and avoid excessive randomization.

## How to set the configuration
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Must carry summarized content from multiple rapid disaster reports, consultation minutes and historical duty records to avoid truncation of critical information |
| `maxTokens` | 4000 token | Adapts to the output length requirement of a single review material to ensure complete response for case review |
| `quoteMaxToken` | 2000 token | Must reference original disaster data and warning notices as review basis, reserve sufficient space for original text citations |
| `temperature` | 0.2–0.4 | Ensures rigor of review results, avoids deviation in disaster judgment caused by randomization |
| `vision` | Enabled | Adapts to review requirements for disaster scenes captured by video surveillance, supplements visual evidence |
| `AIPROXY_API_ENDPOINT` | API address of locally deployed model | Meets compliance and data security requirements for local deployment |
| `AIPROXY_API_TOKEN` | Custom authentication key | Ensures access security of the model interface and prevents unauthorized calls |

## Three common configuration mistakes
- A 401 unauthorized error is returned when testing a locally deployed model. The cause is that the `AIPROXY_API_TOKEN` is not correctly configured and does not match the authentication key of the local model.
- The model cannot be called normally after connecting to the transit service. The cause is that the maintenance status of the service was not confirmed, resulting in invalid interface address or key.
- The `maxContext` configuration is set too small, leading to truncation of review results. The cause is that the total length of multi-source disaster documents was not considered, resulting in missing critical rainfall and hydrological data.

## How to confirm the configuration is properly set
- Call the model interface test, input a standard rapid disaster report, and check whether the returned result contains a complete review conclusion and cited original text fragments.
- View the model call log to confirm that the configurations of `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` have not been tampered with, and there are no 401 error records.
- Upload multiple documents from different sources (such as warning notices and material allocation slips) and check whether the model can correctly identify professional fields and complete summarization.
- After enabling the `vision` configuration, upload a disaster scene photo and confirm that the model can return corresponding text descriptions and review opinions.

The values provided are common starting points and should be measured against the reader's own samples.
