# Declaration Materials and Case Review for Flood Prevention, Disaster Mitigation and Emergency Duty: Deployment and Upgrade

## What the data for this category looks like
Daily documents for this category include duty logs, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Data sources include meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. The update frequency is daily. Documents are typically organized by event batch and timeline. Fields include rainfall and water level values, material allocation quantities, and personnel transfer data, with specific measurement units such as millimeters, cubic meters, and number of people.

## What constraints these characteristics impose on deployment and upgrade
Multiple heterogeneous data sources require compatible interface protocols for various systems during deployment, and adaptation to different formats of reported data. The daily update frequency requires configuring reasonable intervals for scheduled synchronization tasks to avoid data lag that impacts emergency judgments. Diverse document types and professional measurement fields require pre-configured format parsing rules and field mapping logic to ensure correct data ingestion into storage. Real-time requirements for emergency scenarios require controlling the latency of the deployment link within a reasonable range. At the same time, the upgrade process must ensure business continuity and avoid disrupting daily duty operations. Cross-departmental scheduling characteristics require configuring layered permissions to ensure that the access scope of different roles aligns with their respective responsibilities.

| `DB_MAX_LINK` | `100–200` | Adapts to concurrent connection requirements for multi-source data, supports daily batch synchronization tasks for disaster data |
| `MONGODB_URI` | Intranet address for local deployments | Stores classified or sensitive emergency duty data, ensures security of intranet access |
| `REDIS_URL` | 600-second timeout configuration | Caches real-time warning information and temporary consultation data, avoids delays caused by frequent reads from source systems |
| `STORAGE_S3_ENDPOINT` | Local object storage intranet node | Stores large volumes of video surveillance clips and disaster records, reduces latency risks from public network transfers |
| `FE_DOMAIN` | Emergency command intranet domain name | Restricts frontend access scope, only available to intranet operation and maintenance and duty personnel |

## Three common misconfigurations
- Symptom: Frontend page is inaccessible after deployment, returns 404 status code. Cause: The downloaded deployment configuration file is corrupted, or an exception occurs during file parsing, leading to incorrect resource paths loaded during service startup.
- Symptom: Attempting to add an external model service returns connection refused. Cause: Intranet access rules are not configured, or the model service port is not opened to the network environment where FastGPT is deployed, resulting in failed link connectivity.
- Symptom: Vector search returns an unexpected number of results. Cause: The `DB_MAX_LINK` configuration is not adjusted based on the daily volume of updated disaster data, leading to connection exhaustion or cache expiration, preventing normal data recall.

## How to confirm the configuration is complete
- Run the multi-source data synchronization script, check whether daily data from meteorological and hydrological systems can be pulled normally, and verify that data formats and field mappings match expectations.
- Access the configured frontend domain name, confirm that the page loads normally and internal interface requests have no abnormal errors.
- Test the external model call link, confirm that vector and language models respond normally, with no connection timeout or refusal prompts.
- Check service logs, confirm that the connection counts for database and cache services fall within the configured reasonable range, with no abnormal disconnections.
