# Warehouse Logistics Declaration Materials and File Review: HTTP Interfaces and External Systems

## What the data for this category looks like
The data comes from inbound and outbound declaration forms in warehouse management systems, inventory approval files, and documents from customs declaration docking platforms. Updates are triggered by business processes. Single declaration materials are updated in real time after generation. Monthly files are updated in batches at archive nodes.
Document structure includes two categories: structured fields and attachments. Structured fields include declaration number, cargo category, pallet count, inbound weight, and approval status. Their respective units are: none, category name, pallet, kilogram, none.
Attachments are mostly packing list scans and certificates of origin. Single attachment sizes mostly fall within the 10-50 MB range.

## What constraints these characteristics impose on HTTP interfaces and external systems
Field names and units of structured data must be fully aligned with connected external WMS and customs systems. Mismatched fields during HTTP interface transmission will cause data parsing failures.
The maximum attachment size must match the file upload limits of the external system. Otherwise, transmission errors will trigger.
Single declaration data generated in real time requires the HTTP interface to use a short timeout period. This avoids excessive waiting for business processes.
Monthly batch archived file data requires the interface to support paginated pulling. This prevents connection timeouts caused by overly large single request data volumes.
Data from multiple sources must be unified into a standard format via the interface. This eliminates differences in field naming across systems.

## How to set configurations
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Fill in according to the Bearer Token format provided by the connected system, valid for 7 days | Matches the identity verification rules of external systems to avoid unauthorized access |
| `variables` | Configure declaration number and pallet count as dynamic variables | Adapts dynamic parameter transfer for single declaration materials |
| `responseData` | Only return approval status and review opinion fields, control return size to 200-500 characters | Reduces invalid data transmission and improves interface response speed |
| Interface timeout period | 600 seconds | Adapts to the transmission requirements of real-time declaration data and avoids excessive waiting for business processes |
| Attachment upload limit | 1000 MB | Matches the common size range of warehouse logistics declaration attachments |
| Paginated pulling count | First 50 entries | Adapts to the pulling scale of monthly batch files and prevents overload from a single request |

## Three common errors
- Phenomenon: When calling a downstream HTTP interface, the JSON data returned by the upstream system includes a large number of backslash escape characters. This causes parsing failures in the downstream interface. Cause: No escape cleaning was performed on the `responseData` returned by the upstream interface. It was directly passed into the `variables` parameter, triggering secondary escaping.
- Phenomenon: The interface call returns the `aiPointsNotEnough` error prompt. Cause: The volume of declaration file data passed in a single request exceeds the token consumption limit allowed by the system, triggering the point limit.
- Phenomenon: When pulling monthly batch files, only a fixed number of entries are returned. All archived files cannot be obtained. Cause: The offset parameter for paginated pulling was not configured. Only the preset fixed number of entries are pulled by default.

## How to confirm the configuration is valid
- Send a test request for single declaration data. Verify that the returned `responseData` fields fully match the expected structured fields.
- Upload a single XLSX attachment smaller than 10 MB. Confirm that the interface can receive it normally and trigger the parsing process.
- Initiate a batch pull request. Verify that the number of returned entries matches the configured paginated pulling count.
- Replace an expired `Authorization` token. Confirm that the interface returns an unauthorized error prompt, to verify that the identity verification configuration is effective.

The values provided are common starting points and should be measured against the reader's own samples.
