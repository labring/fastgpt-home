# Warehouse and Logistics Declaration Materials and File Review: Vector Models and Indexes

## What this category of data looks like
Data primarily comes from warehouse in-and-out vouchers, customs declaration forms, logistics waybills, and approval file ledgers. Data updates follow business execution batches or daily batch synchronization. Documents are mainly structured tables and semi-structured text, including fields such as waybill number, cargo category, declared weight, declared amount, approval node, handler, creation time, and more. Units include pieces, tons, yuan, cubic meters, batch numbers, and other units.

## What constraints these characteristics impose on vector models and indexing
Structured and semi-structured data makes up a large share of the dataset. Different fields have significant semantic differences. Configure targeted field-level embedding rules to prevent irrelevant fields from interfering with vector matching. The length of individual documents varies widely. Short documents only contain tens of characters, while long files can reach thousands of characters. Adapt chunking strategies for different document lengths. Data update frequency fluctuates with business batches. Support incremental index updates to reduce duplicate calculation costs. Declaration materials follow fixed approval processes. Retain semantic association characteristics of process nodes in the index.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Matches the average semantic unit of warehouse declaration documents and files, avoids splitting core approval logic |
| Overlap Length | 100–150 characters | Retains cross-chunk cargo information and approval process associations |
| Similarity Threshold | 0.72–0.78 | Matches the semantic similarity distribution of warehouse logistics data, calibrated based on actual testing |
| Single Search Limit | Top 10 entries | Balances comprehensive retrieval needs for file review and interface response speed |
| `maxToken` | 8000 | Adapts to the context limit of FastGPT v4.17.0, meets review requirements for long files |
| Reranking | Enabled | Filters similar cargo codes and declared amount entries, improves retrieval accuracy |

## Three common errors
- Phenomenon: After configuring the embedding model, a prompt indicating no available channel appears, and vector tasks show failure. Reasons include: the embedding model is not bound to the current scenario group, or the API key has not been granted permission to call the corresponding embedding service.
- Phenomenon: The number of retrieval results is far lower than expected, or returned content is unrelated to the query. Reasons include: the chunk length setting does not match the semantic units of warehouse documents, leading to core declaration information being split and unable to form complete semantic vectors.
- Phenomenon: Retrieval speed slows down after reranking is enabled. Reasons include: the single search limit is set too high, or the chunk overlap length is too large, leading to increased redundant data volume and longer reranking calculation time.

## How to confirm the configuration is complete
- Upload a single warehouse declaration document, wait for the embedding task to complete, and check that the log has no error prompts.
- Enter the test query "View the approval files for a specified batch of cargo", and verify that the returned retrieval results include the core field information of the corresponding batch.
- On the FastGPT v4.17.0 configuration page, confirm that the `maxToken` value meets the requirements for long file review, and that the embedding model has been bound to the correct API key.
- Batch upload 5 different types of warehouse documents, check that the index update progress is normal, with no interruptions or failure records.

The values provided are common starting points and should be measured against the reader's own samples.
