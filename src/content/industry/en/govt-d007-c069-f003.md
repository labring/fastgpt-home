# Hazardous Chemicals Storage and Transportation Declaration Materials and File Review: Multi-turn Dialogue and Prompts
## What the data for this category looks like
Hazardous chemicals storage and transportation declaration materials and file data mainly come from enterprise electronic declaration forms, emergency management department filing archives, and warehouse in-outbound logs. Declaration files are archived after each declaration batch is completed. Filing data is updated monthly, and in-outbound logs are synchronized daily. The document structure of a single file includes declaration unit information, hazardous chemical name, 5-digit UN number, storage warehouse and location, transportation and storage volume (unit: ton), approval document number, and validity period. All fields use standardized formats. The UN number must comply with UN dangerous goods coding rules, and the storage and transportation volume is accurate to two decimal places.

## Constraints for multi-turn dialogue and prompt workflows
Standardized UN number and storage volume fields require multi-turn dialogue to guide users to input content that meets the format, avoiding vague statements. There are time dimension differences between monthly updated filing data and daily updated in-outbound logs, so prompts must clearly specify the data time range to prevent confusion between historical filings and current real-time data. The text size of a single file is moderate, so multi-turn dialogue must retain the complete declaration-verification process while avoiding excessive context that causes processing delays.

| Maximum context length | 800–1200 characters | Matches the average text size of a single hazardous chemicals storage and transportation declaration file, avoids truncating core approval fields |

| Dialogue permission association | Bind declaration batch via `chatId` | Ensures users can only access their own submitted declaration dialogue records |

| Timeout threshold | 600 seconds | Matches the average response duration of declaration review, prevents timeout caused by long text parsing |

## Three common mistakes
- Phenomenon: Declaration dialogues submitted by different users cannot be viewed individually, or dialogues created via API are not displayed in the page session. Cause: The user's corresponding declaration batch permission is not bound via `chatId`, causing the permission verification logic to fail.
- Phenomenon: The Human field is empty in the response record preview after an API call. Cause: The `messages` parameter does not correctly pass the user's question content, or the parameter structure does not meet system requirements.
- Phenomenon: Context truncation or verification failure occurs frequently during dialogue interaction. Cause: A reasonable maximum context length or single search limit is not set, resulting in truncation of core declaration fields, or `variables` fields are not bound, leading to missing verification.

- Adjust the context length and single search limit parameters, submit declaration materials of different lengths, confirm that core fields are not truncated and the associated data volume meets expectations.
