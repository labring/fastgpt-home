# Urban Public Transit Declaration Materials and Case Review: Tool Calling and Plugins

## What the data for this category looks like
Data sources are archived cases and declaration materials from urban public transit operation management systems and government declaration platforms.
Update cadence follows two patterns: immediate archiving after a single declaration is completed, and weekly batch updates for daily review cases.
The document structure has three parts:
- Declaration form fields: route number, applicant entity, operation plan
- Attachment materials: vehicle inspection report, station blueprint
- Approval cases: review node, comment annotation

Fields include unique identification codes and timestamps. File attachment size is measured in MB. Most text content uses structured forms paired with unstructured attachments.

## Constraints on Tool Calling and Plugins From These Characteristics
The coexistence of structured fields and unstructured attachments requires tool calling to support both structured form field extraction and multi-type attachment parsing.
Immediate archiving of single-declaration data requires plugin data source synchronization to support both on-demand and scheduled triggering modes. This adapts to timeliness requirements for different review nodes.
The unique identification code field requires tool calling to specify associated matching fields. This prevents cross-batch data confusion.
The wide range of attachment sizes requires plugins to set a reasonable size filtering threshold in the file processing link. This stops large files from consuming excessive calling resources.

## Configuration Settings
The following configurations apply to FastGPT v4.17.0

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapts to recognition needs for mixed structured and unstructured content in declaration materials, automatically matching the corresponding tool |
| Chat history range for text content extraction node | First 6 entries | Covers contextual information for a single review, avoiding redundant data from consuming calling quotas |
| Plugin trigger timing | 10 minutes after declaration submission, or 00:00 every Monday | Matches the two data update cadences of immediate archiving and batch updates |
| Maximum file parsing size | 100–200 MB | Adapts to the common size range of public transit declaration attachments, calibrated via actual testing |
| `functionCall` | `strict: true` | Ensures tool call return formats comply with approval case field specifications, reducing format errors |
| Single tool call timeout | 60 seconds | Adapts to parsing durations for medium-sized attachments, preventing timeout interruptions to review workflows |

## Three Common Configuration Errors
- Scenario: After configuring a text content extraction node in a plugin, the workflow runs and returns empty results. Cause: No chat history context range is specified, so tool calling cannot retrieve historical review information.
- Scenario: API calls return format error prompts. Cause: Strict mode for `functionCall` is not enabled, so returned content fails to meet approval field format requirements.
- Scenario: Content cannot be parsed after submitting a document link. Cause: No parsing plugin for the corresponding file type is configured. Public transit declaration attachments often include CAD drawings and PDF scanned documents, requiring additional loading of corresponding parsing tools.

## How to Verify Correct Configuration
- Run test data for a single simulated declaration, check if tool call return fields include preset content such as route number and approval status.
- Review plugin run logs, confirm that no size limit or timeout errors occur during the file parsing link.
- Compare tool call return results with fields from the original declaration materials, check for matching errors or omissions.
- Test the scheduled trigger plugin synchronization task, confirm that weekly updated batch case data can be pulled normally.

The values provided are common starting points and should be evaluated against the reader's own samples.
