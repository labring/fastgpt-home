# Urban Water Utilities Application Materials and File Review: Model Integration and Configuration

## What the data for this category looks like
Urban water utility application materials and file data mainly come from business scenarios such as water service connection applications, water quality testing commissions, drainage permit applications, and pipeline inspection records. Data sources include structured forms exported from business systems, scanned paper documents, on-site photos of water quality tests, and pipeline survey images. Data is updated in real time upon business submission, and archived materials are organized in quarterly batches. Document structures include fixed-template application letters, qualification certificates, and structured test reports. Fields cover project number, water usage address, water quality indicators (such as mg/L, MPa), file number, disposal status, and more. Some documents include multi-format attachments.

## What constraints these characteristics impose on model integration and configuration
Mixed multi-format data requires models to support both structured field recognition and unstructured content parsing. Multimodal capabilities must be configured specifically for this use case. Fields with specific units require models to accurately identify and associate unit information to avoid review deviations. The length of files and application materials varies widely, from dozens-of-word inspection records to dozens-of-page test reports. Reasonable control of context length is needed to avoid information truncation. Real-time submitted business data requires the model call chain to have low latency characteristics. Appropriate parameters must be configured to ensure response speed.

## How to set the configurations
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| `maxContext` | 8000–12000 token | Adapts to the average length of urban water utility application materials and files, avoiding truncation of key review information |
| `maxTokens` | 2000–3000 token | Meets the output length requirements for review results, covering all review points and feedback content |
| `vision` | Enabled | Adapts to multimodal attachments such as water quality test photos and on-site survey photos often included in application materials |
| `toolChoice` | auto | Supports the model to independently judge whether to call the file reading tool to process uploaded PDF files |
| `temperature` | 0.2–0.4 | Ensures the rigor of review results, reducing the randomness of generated content |
| `AIPROXY_API_ENDPOINT` | Fill in the official access address of the corresponding model | Ensures the connectivity and correctness of the model call chain |
| `AIPROXY_API_TOKEN` | Fill in the valid token bound to the model | Completes identity verification and ensures the legality of model calls |

## Three common mistakes
- Phenomenon: When calling a VL model, photo content parsing fails, and the interface displays a prompt that multimodal input is not supported. Cause: The `vision` parameter is not enabled, and multimodal capabilities are not configured, so the model cannot process photo attachments in application materials.
- Phenomenon: Batch uploading a 3MB PDF file triggers a call failure, and the log returns an error of context limit exceeded. Cause: The `maxContext` parameter is not adjusted to the range suitable for long documents, causing a single batch call to exceed the model's context upper limit.
- Phenomenon: The model does not automatically read the uploaded application PDF file, only returning text prompts. Cause: The `toolChoice` parameter is incorrectly set to none, which restricts the model's ability to independently call the file reading tool.

## How to confirm the configuration is correct
- Upload a water quality test photo, trigger a model call, and check whether the recognition result of the photo content is returned, confirming that the `vision` parameter configuration takes effect.
- Upload a PDF file with more than 5 pages, check whether the model automatically reads the file content and conducts review, confirming that the `toolChoice` parameter configuration takes effect.
- Submit structured application data containing water quality indicators, check whether the model's output review result accurately recognizes the fields and corresponding units, confirming that the parameter configuration meets business requirements.
- Check the platform's model call logs, confirm that the returned status code is 200, and there are no identity verification-related errors, confirming that the `AIPROXY_API_TOKEN` and `AIPROXY_API_ENDPOINT` configurations are correct.

The values given are common starting points and should be measured against the reader's own samples.
