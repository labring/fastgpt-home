# Application Materials and Case Review for Basic Telecommunications Operations: HTTP Interfaces and External Systems

## What the data for this category looks like
This category of data comes from the internal business support system of basic telecommunications operations, and includes user network access archives, business change application forms, billing verification records, and similar items. The update rhythm is triggered by actual business processing flows, supporting real-time or daily batch updates. The document structure is split into two parts: structured business fields and attachment materials. Structured fields include application number, operator main body code, business type, submission time, case number, review status, and other items. Attachment materials are mostly PDF or scanned documents, with a wide range of single-file sizes.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
The application materials and case review data for basic telecommunications operations include structured business fields and large-volume attachments, which requires HTTP interfaces to support multipart form submissions to transmit business parameters and material files simultaneously. The data originates from internal business support systems, so interface docking must pass legal identity verification, and the `Authorization` credential must be configured. The data update rhythm is flexibly triggered according to business processing, so the interface timeout setting must adapt to the processing duration of large file uploads and multi-material reviews to avoid interrupting the process mid-execution. There are many structured fields, so the interface must support passing complete business identification parameters through `variables` to ensure accurate association between cases and application forms. `responseData` must return standardized review result fields to facilitate external systems to automatically circulate review progress.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Carry a Bearer token from the operator's internal API gateway | Legal identity verification is required for docking with internal state-owned enterprise and public sector business systems, in compliance with security specifications |
| `variables` | Pass business identifiers such as application number and case number | Matches the structured fields of basic telecommunications operation application materials to ensure accurate business association |
| `responseData` | Configure as JSON structured format, including review status fields | Facilitates external systems to automatically parse review results and adapt to automated circulation of case reviews |
| Request timeout | 600 seconds | Adapts to the processing duration of large attachment uploads and multi-material reviews to avoid interruptions mid-execution |
| Maximum single request payload | 1000 MB | Matches the common size range of business material attachments for basic telecommunications operations |
| Retry strategy | Calibrate based on actual testing | Respond to temporary fluctuations in internal gateways and avoid duplicate reviews caused by repeated submissions |

## Three common mistakes
- Issue: The interface returns a 404 status code, prompting that the interface path does not exist. Cause: The exclusive API path of the internal business system of basic telecommunications operations is not used, and a general interface is mistakenly used as the docking address.
- Issue: When retrieving historical sessions, all records are returned, and filtering by customUid is not possible. Cause: The customUid parameter is not correctly passed in `variables`, or the logic for filtering by custom identifier is not enabled in the interface configuration.
- Issue: Large attachment material upload fails, prompting request timeout. Cause: The request timeout setting is too short and does not adapt to the upload processing duration of basic telecommunications operation business materials.

## How to confirm the configuration is correct
- Under FastGPT v4.17.0, send a test request carrying a valid `Authorization` credential and business variables, and check whether the `responseData` returned by the interface includes the expected structured review fields.
- Upload a test attachment of a common business size, confirm that the request is not interrupted, and return a normal review result identifier.
- Pass the specified customUid parameter, and verify that the returned session records only include content associated with this identifier.
- Simulate multiple repeated requests, confirm that the interface does not throw abnormal errors, and the retry logic triggers normally.
