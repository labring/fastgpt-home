# Basic Telecommunications Operation: Declaration Materials and File Review - Multi-turn Dialogue and Prompts

## What this category of data looks like
Data for declaration materials and file review in basic telecommunications operations originates from operator business acceptance systems, billing support systems, and customer archive databases. Declaration materials are submitted in real time when users complete business handling, and files are archived in monthly batches. Each individual document includes fields such as main qualification number, business type code, list of supporting document attachments, and review node records. Units include characters, days, MB, and some files contain mixed content of multi-page scanned documents and structured forms.

## What constraints these characteristics impose on the multi-turn dialogue and prompts link
Decentralized data sources require multi-turn dialogue to transfer cross-system context parameters. The `variables` tool must be used to bind return fields from different systems. Real-time submitted declaration materials require the dialogue flow to support real-time verification. The context length of a single round of dialogue must be limited to avoid redundancy. Mixed structured and unstructured document content requires prompts to clearly distinguish trigger logic for field extraction and text review, to avoid confusing processing rules for scanned document text and structured fields. Fixed-format business code fields require prompts to include built-in matching rules, to prevent review results from having code mismatch issues.

## How to Configure the Settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Bind two system variables: business acceptance number and qualification number | The data includes fixed business code fields, and cross-system review context must be transferred |
| `messages` | Retain the first 3 core review dialogue contents | The review logic for a single file does not exceed 3 core nodes, to avoid context redundancy |
| `chatId` | Use the business acceptance number as the unique identifier | Full-process review records for a single file must be associated for easy traceability |
| Maximum context length | 800–1200 characters | Matches the length range of core review content for a single declaration material |
| Dialogue timeout threshold | 60 seconds | Meets the response time requirements for real-time review |

## Three Common Configuration Mistakes
- Symptom: The final output of the multi-turn dialogue workflow includes redundant content from the previous AI dialogue. Cause: The number of retained `messages` rounds was not limited, causing the context to carry non-core pre-dialogue content.
- Symptom: The configured HTTP network request in the workflow is not triggered, and the built-in AI dialogue is directly called to generate results. Cause: The return result of the HTTP request was not bound as an input parameter for subsequent dialogue via `variables`, causing the flow to not follow the preset logic.
- Symptom: Business code mismatch errors appear in review results. Cause: No built-in matching rules for business codes were included in the prompts, causing the dialogue to fail to correctly identify field formats.

## How to Confirm the Configuration is Complete
- Verify the variable binding configuration of the workflow, confirm that the system fields required for the business have been associated.
- Initiate a test review request, check that the final output only includes core review results with no redundant pre-dialogue content.
- Simulate cross-system data transfer, confirm that the return result of the HTTP request is correctly passed to the subsequent dialogue link.
- Call the dialogue interface, confirm that no cross-domain related error prompts are returned.
