# Declaration Materials and Case Review for Bulk Commodity Trading: HTTP Interfaces and External Systems

## What data looks like for this category
Declaration materials and case review data for bulk commodity trading primarily originate from internal enterprise ERP systems, customs clearance ports, warehouse management platforms, and quality inspection institution interfaces. A single declaration document includes fields such as contract number, product category, declared quantity (unit: ton/bucket), declared unit price, customs declaration number, quality inspection report number, and warehouse receipt number. Cases additionally include audit process nodes, approval opinions, and filing time. Data updates trigger when a single transaction declaration is submitted. Synchronized filing updates occur after review completes. A single document typically ranges from 800 to 1500 characters.

## Constraints on HTTP interfaces and external systems
Declaration and case data for bulk commodity trading comes from multiple heterogeneous sources. Integration with multiple external HTTP interfaces is required, including ERP, customs, and warehouse systems. Different systems use distinct authentication rules and return field formats. This increases interface adaptation difficulty. Single data sets include multiple unit fields. Unified unit identifiers are required during interface transmission to avoid parsing errors. Real-time update requests triggered by single transactions create peak interface calls that fluctuate with business activity. Adapted timeout and retry strategies must be configured. Long document structures require interface request bodies to support large capacity. This prevents data truncation. Audit process node data must be synchronized in chronological order. Interfaces must support filtering return results by status.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer ${custom docking key}` | Complies with standard authentication specifications of external systems, ensuring interface call security |
| `variables` | `{"defaultUnit": "ton", "maxRetryCount": 3}` | Unifies unit identifiers for multi-source data, adapting to field differences across commodity categories |
| `responseData` | `filter(status: "submitted")` | Only filters case data that has been submitted and pending review, reducing invalid interface requests |
| Request timeout | 60 seconds | Adapts to the full processing cycle of a single bulk commodity trading declaration document, avoiding early call termination |
| Retry count | 2 attempts | Addresses temporary call failures caused by network fluctuations, reducing interface call failure rates |
| Maximum request body capacity | 1000 KB | Matches transmission requirements corresponding to the character length of a single declaration document, avoiding data truncation |

## Three Common Configuration Mistakes
- Symptom: When using `variables` to pass bulk commodity trading declaration parameters, the interface returns empty fields or parsing failures. Cause: No category and unit mapping rules are configured in `variables`, leading to inability to correctly match multi-unit data returned by external systems.
- Symptom: Calls to customs or warehouse interfaces return a 403 status code. Cause: The `Authorization` parameter is not configured correctly, or the docking key is not updated synchronously with changes from external systems.
- Symptom: Cross-domain errors occur when the frontend calls the review interface. Cause: The deployment domain of FastGPT is not added to the cross-domain access whitelist of the external system, resulting in request interception.

## How to Verify Successful Configuration
- In FastGPT v4.17.0, call the test interface. Check if the returned `responseData` only includes pending review case data. Adjust the filtering rule until it matches expected results.
- Submit test parameters with different units. Use `variables` to configure mappings. Confirm that interface parsing results have no unit conflicts.
- Initiate a simulated declaration transaction to trigger an interface call. Verify that authentication parameters function normally, and no 403 errors occur.
- Review interface logs. Confirm that the request body capacity does not exceed the preset limit, and no data truncation takes place.
