# Engineering Consulting Supervision Declaration Material and File Review: HTTP Interface and External Systems

Reference only; verify against the target FastGPT release and deployment documentation.

## What this category of data looks like
The data for engineering consulting supervision declaration material and file review originates from various supervision documents submitted for review at project sites. The update rhythm follows project submission review milestones. The material update frequency for a single review batch is 1 to 3 days per update. Each archive document includes two parts: structured form and attachments. The structured fields include project filing number, supervision section scope, review item type, attachment file size, and submitter identification. The unit for section scope is square meters, and the unit for attachment size is MB. The review item type is a fixed enumeration value, covering categories such as hidden work acceptance, progress payment application, material incoming inspection, and similar items.

## Constraints on HTTP Interface and External Systems Integration
The data characteristics of this category create clear constraints for HTTP interface and external system integration. The fixed fields of the structured form require the request body to strictly match the preset field format. Missing or incorrectly formatted fields will cause interface verification to fail. The size limit of attachment files requires the interface to configure a reasonable upload threshold to prevent large file transfer timeouts. The enumeration type of review items requires the external system to return fixed optional values to block invalid parameter input. Supervision data is classified as internal sensitive information, so the `Authorization` parameter must be configured for interface calls to complete permission verification and avoid unauthorized access. Data updates follow review milestones, so interface calls must adapt to the project's review cycle to prevent frequent invalid requests.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${pre-configured internal interface key}` | Supervision data is internal sensitive information. Bearer tokens are used for identity verification to prevent unauthorized access |
| `variables` | `{"project_id": "${project number variable}", "attach_limit": "1000 MB"}` | Match the structured field requirements of supervision archives, pass project identification and attachment size limit parameters |
| `responseData` | Extract the `$.data.audit_result` and `$.data.attach_list` fields | Only retrieve core data of audit results and attachment lists, filter redundant interface return content |
| Request retry count | 2 times | Respond to request failures caused by temporary network fluctuations, avoid interrupting the review process with a single failed request |
| Timeout threshold | 600 seconds | Supervision archive attachments may have large volumes, so sufficient time must be reserved for transmission and processing |

## Three Common Misconfigurations
- Phenomenon: Interface calls return `Failed to fetch`. Cause: The `Authorization` parameter is not configured correctly, or the corresponding access permission is not enabled for the internal interface.
- Phenomenon: The returned audit result field is empty. Cause: The correct project number parameter is not passed through `variables`, causing the interface to fail to match the corresponding archive data.
- Phenomenon: BLOB-format attachments cannot trigger downloads in the dialog box. Cause: The correct file stream extraction path is not configured in the HTTP node's `responseData`, causing the returned content to not be recognized as a downloadable resource.

## How to Verify Correct Configuration
- Invoke the test interface, check whether the returned `responseData` contains the expected audit result and attachment list fields.
- Pass an invalid project number parameter, confirm that the interface returns a clear parameter error prompt to verify that the verification logic is effective.
- Upload a test attachment within 1000 MB, confirm that the interface can receive the attachment normally and return processing results.
- Check whether the configuration of the `Authorization` parameter matches the verification rules of the internal interface to avoid permission verification failure.
