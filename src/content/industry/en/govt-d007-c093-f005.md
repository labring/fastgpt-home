# Declaration Materials and Case Review for Government and State-Owned Enterprise IT Services: Tool Calling and Plugins

## What this category of data looks like
Declaration materials and case review data for government and state-owned enterprise IT services mainly come from government affairs declaration systems and case management platforms of state-owned enterprises and government bodies. Data updates follow government affairs declaration batches or case completion cycles, with no fixed daily update frequency. Each document includes two parts: structured fields and attachments. Structured fields have enumerated fields such as the unified social credit code of the declaring entity, item type, submission time, and review status. Attachments are typically in formats like images, PDFs, and scanned documents. The size of a single attachment usually does not exceed 1000 MB.

## What constraints these data characteristics impose on tool calling and plugins
These data characteristics create three constraints for the tool calling and plugin workflow.
First, the combination of structured fields and mixed attachments requires tool calling to support both text parameter verification and file stream parsing. It cannot rely solely on general text interfaces.
Second, the batch-based data update pattern requires tool calling to support batch triggering and batch result summarization, to fit the batch processing needs of government review work.
Third, the diverse attachment formats and wide size range require plugins to support multiple file parsing logic, while setting reasonable size and quantity limits. The presence of enumerated fields requires tool calling to include built-in parameter legitimacy checks to prevent invalid interface calls.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | Auto-select | Adapts to automatic scheduling of multi-type tasks in declaration material review, no need to manually specify tools, reducing configuration complexity |
| Single tool call timeout | 120–180 seconds | Matches the average processing duration of case review, avoids call failures caused by overly long attachment parsing time |
| Maximum attachment processing size | 1000 MB | Covers the demand for large-volume attachments common in declaration materials, avoids being blocked due to exceeding size limits |
| Maximum number of attachments per tool call | First 5 | Matches the average number of attachments in a single batch of declaration materials, avoids loading too many resources in a single call |
| Environment variable call permission | Enabled | Supports reading sensitive information such as third-party service keys and system parameters configured during deployment |
| `functionCall` parameter verification | Enabled | Verifies the legitimacy of enumerated values of declaration material fields, avoids passing invalid parameters to third-party interfaces |

## Three common misconfigurations
- Phenomenon: When calling a tool that returns an image stream, the workflow output result field is empty. Cause: The receiving and parsing logic for file streams is not configured, and only text-type interface responses are processed.
- Phenomenon: After connecting to a third-party API and completing application testing, the API call returns an empty response. Cause: Environment variables configured during deployment are not correctly referenced in the workflow, so the third-party service key is not loaded.
- Phenomenon: A workflow with a specific large language model works normally during application configuration testing, but throws an error when called via API. Cause: Correct authentication parameters are not included in the API call, or the workflow trigger mode does not match the parameter format required by the API call.

## How to confirm your configuration is correct
- In the tool debugging panel of the application configuration, upload a single declaration material attachment, and verify that the tool can correctly parse the file stream and return structured review results.
- Insert an environment variable call node in the workflow, enter the preset third-party service key variable name, and verify that the parameter values configured during deployment can be read correctly.
- Trigger the workflow for batch declaration material review, and check that the tool call logs show correct parameter verification results and attachment parsing progress.
- Use the FastGPT v4.17.0 API debugging tool to call the workflow containing the target large language model, and confirm that the return results from application testing and API calls are consistent.
