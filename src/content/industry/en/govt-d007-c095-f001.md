# Declaration Materials and File Review for New Energy Development: HTTP Interfaces and External Systems

## What this category of data looks like
Declaration materials and file review data for new energy development primarily originates from new energy project initiation and approval systems, national land spatial planning databases, wind/solar resource survey reports, environmental impact assessment (EIA) approval documents, and grid connection application materials. Data updates follow project declaration batch cycles. Within the cycle from project initiation to archiving, data is updated incrementally alongside approval nodes. Document structures include basic project information, declaration document lists, approval node records, and compliance verification materials. Core fields include project code, site longitude and latitude, installed capacity, and EIA approval document number. Installed capacity is measured in megawatts (MW), floor area in hectares (ha), and longitude and latitude are recorded in degrees-minutes-seconds format.

## What constraints these characteristics impose on HTTP interfaces and external systems
Declaration materials and file review data for new energy development comes from scattered sources. It includes both structured approval fields and unstructured survey reports and EIA documents. HTTP interfaces must support access and parsing of multiple data source types. Core fields have fixed formats and unit requirements. Interface parameters must strictly match business field names, otherwise verification will fail. File review processes involve multi-node approval. Real-time status synchronization with government approval systems is required. Interfaces must support status callbacks and data return. Some declaration materials include large survey reports and EIA files. Interfaces must adapt to large file transfer or file link delivery requirements. They must also comply with current limiting rules of government systems to avoid interception caused by frequent calls.

## Three Common Mistakes
- Phenomenon: Interface requests return empty fields or fail verification. Cause: Body parameter names are incorrectly bound to local file names, and do not correspond to official business field names of declaration materials.
- Phenomenon: Frequent 429 status codes are triggered during interface calls. Cause: Reasonable request intervals are not configured, and continuous requests trigger current limiting rules of government systems.
- Phenomenon: Review results cannot be synchronized to the local file management system. Cause: Parsing rules for `responseData` are not correctly configured, leading to failure to extract core business fields properly.

## How to Confirm Proper Configuration

- Initiate a simulated request, pass a test project code, and check if the returned `responseData` includes the preset review status field.
- View interface call logs to confirm that the `Authorization` authentication header is correctly included in the request headers.
- Check if fields configured in `variables` such as project code and installed capacity are correctly passed to the request body.
- Upload a small test declaration material file, and check if business fields are correctly mapped in the request body.
- Simulate an interface timeout scenario to confirm that the retry mechanism triggers according to the configured number of times.
