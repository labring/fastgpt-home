# Civil Aviation Airport Declaration Materials and File Review: Tool Calling and Plugins

## What this category of data looks like
Data for civil aviation airport declaration materials and file review mainly comes from three types of data sources: airport operation management systems, air traffic control reporting platforms, and customs supervision ports. Data updates are triggered by individual declaration workflows. File data for a single declaration is archived after review is completed. A single declaration package includes two parts: structured fields and attachments. Structured fields contain flight number, takeoff and landing time, declaring unit, review status, and other items. Attachments are mostly security filing documents, scanned takeoff and landing permits, and similar files. Single attachments are usually large in size. Field formats follow strict industry specifications. For example, flight numbers must conform to ICAO standard formats, and takeoff and landing times use ISO 8601 time formats.

## What constraints these characteristics impose on the "tool calling and plugins" link
The multi-source nature of civil aviation airport declaration data requires that multiple cross-system plugins be configured in the tool calling link to pull corresponding materials from different data sources. The real-time data update requirement means tool calling request timeout settings must adapt to cross-system interaction delays, to avoid interrupting the review process due to timeout. The large size of attachments means plugins must support large file upload and parsing, to avoid missing materials due to file size limits. The strict format requirements for structured fields mean parameter validation in tool calling must match industry specifications, to avoid data parsing failures due to format errors.

## Three common mistakes
- Symptom: A `The dollar ($) prefixed field '$schema' in 'modules.7.inputs.0.value.i'` error is returned when executing a curl call. Cause: The `$schema` field in the JSON request body was not properly escaped, causing FastGPT parsing to fail.
- Symptom: Non-civil aviation airport declaration data is included in results returned by tool calls. Cause: Filter rules for multi-data-source plugins were not configured, and the data source was not limited to airport-specific ports.
- Symptom: Tool calls cannot be triggered after connecting to MCP. Cause: The dedicated communication port for civil aviation airports was not added to the plugin whitelist, causing cross-domain requests to be blocked.
- Symptom: The civil aviation terminology dictionary configured in environment variables cannot be called during the problem optimization phase. Cause: The environment variable key was not bound in the FastGPT plugin configuration, resulting in insufficient permissions.

## How to confirm the configuration is complete
- Execute a local curl call test, check if the returned JSON format includes correct civil aviation declaration fields, and there are no `$schema` related parsing errors.
- Trigger a simulated airport declaration material review workflow, verify that the number of results returned by tool calls matches the preset filter rules.
- Check the FastGPT plugin logs, confirm that the port connected via MCP has established a normal connection, with no timeout or connection rejection prompts.
- Test calling the civil aviation terminology dictionary bound to the environment variable, confirm that the problem optimization phase can correctly recognize professional terms.
