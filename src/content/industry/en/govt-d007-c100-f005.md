# Declaration Materials and File Review for Oilfield Engineering Services: Tool Calling and Plugins

Reference only; verify against the target FastGPT release and deployment documentation.

## What Data for This Category Looks Like
Data for declaration materials and file review in oilfield engineering services originates from documents including project approval applications, on-site construction records, and completion acceptance reports generated during drilling, fracturing, workover and other operation phases. These documents are stored in internal oilfield project management systems or archives. Data is updated in stages as projects progress: initial materials are submitted during the approval phase, progress materials at construction milestones, and final files during the acceptance phase. Documents include fixed fields: unique project ID, operation area, construction unit, material submission time, and review status. Some fields use professional units such as square kilometers, cubic meters, and tons. Each file ranges in size from tens of megabytes to hundreds of megabytes, and contains structured tables and unstructured text.

## What Constraints These Characteristics Impose on Tool Calling and Plugins
Data sources are scattered across multiple project phases. Tool calling must accurately match the corresponding document set according to review nodes, to avoid pulling irrelevant historical materials. Documents have fixed fields and professional units. Plugins must include built-in field extraction rules and unit verification logic to ensure extracted data meets format compliance requirements. File sizes vary widely. Tool calling must support batch filtering of a specified number of documents to avoid exceeding context limits. In scenarios where multiple versions of materials exist, plugins must support version comparison functions to prevent expired declaration materials from being used in reviews. When configuring tool calling, explicitly set the `toolChoice` and `functionCall` parameters to adapt to the unique data characteristics of this category.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `required` | Oilfield declaration materials require accurate extraction of fixed fields. Forcing tool calling prevents the model from directly generating unstructured results, and ensures the accuracy of review data |
| Timeout Duration | `120 seconds` | Parsing and field extraction for medium-sized oilfield engineering files takes a long time. 120 seconds covers the needs of most standard review scenarios |
| `functionCall` | Bound to a dedicated function set for oilfield engineering materials | Tool calling must be limited to extracting specific fields such as project ID and operation area. This avoids parsing errors from generic functions, and adapts to the document characteristics of this category |
| Maximum Documents per Call | `First 8` | Too many documents will exceed context limits. 8 documents covers the typical material set for single-batch reviews, balancing data completeness and calling efficiency |
| Plugin Retry Count | `2 times` | Minor fluctuations may occur in internal oilfield network environments. Retries reduce the failure rate of external interface calls |
| Result Verification Switch | Enabled | Professional units and format compliance of extracted fields must be verified to prevent incorrect data from entering subsequent review processes |

## Three Common Misconfigurations
- Symptom: Tool calling returns unstructured text, and no preset project fields are extracted. Cause: `toolChoice` is not set to `required`, so the model does not trigger the preset tool calling process and directly generates generic responses.
- Symptom: Plugin calls time out, and logs show request duration exceeds the set threshold. Cause: Timeout configuration is not adjusted for oilfield engineering document sizes. Using the default shorter timeout duration fails to cover the parsing needs of medium-sized files.
- Symptom: Tool calling cannot be triggered after frontend embedding, and the console reports a cross-origin error. Cause: The domain name of the Vue3 project is not added to the cross-origin whitelist in the FastGPT backend, so the browser same-origin policy blocks interface requests.

## How to Confirm Proper Configuration
- Upload a test oilfield engineering declaration material, initiate a tool call, and check if the returned result includes preset structured fields such as project ID and operation area.
- View the plugin call logs in the FastGPT backend, confirm that each call's duration does not exceed the set 120-second threshold, and no timeout errors occur.
- Initiate a test interface request in the Vue3 project, confirm that structured data returned by tool calling can be obtained normally, and no cross-origin interception prompts appear.
- After triggering tool calling, check if the returned result fields include correct professional units, such as square kilometers for operation area, with no format errors.
