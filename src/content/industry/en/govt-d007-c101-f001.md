# Port and Shipping Declaration Document and File Review: HTTP Interfaces and External Systems

## What this category of data looks like
Data primarily comes from port operation management systems, maritime online declaration platforms, and container scheduling systems, updated per single job batch or daily. A single declaration document includes structured fields and attachments. Structured fields include vessel name, voyage number, container number, declaration number, cargo category, and billing weight, with units mostly tons or standard containers (TEU). File review data is linked to declaration records, inspection receipts, and release certificates. The overall data structure has clear hierarchy and high field correlation.

## What constraints these characteristics impose on the HTTP Interfaces and External Systems link
The binding relationship between structured fields and linked files is strong. HTTP interface requests must carry core associated parameters such as vessel name and declaration number, otherwise corresponding declaration and review data cannot be accurately matched. Data is updated per single job batch or daily, so interface call frequency must adapt to port operation rhythms to avoid exceeding the rate limiting thresholds of external systems. Attachment files include multiple formats such as PDF and scanned documents, so interfaces must support binary data transmission and multi-type file uploads. Real-time performance requirements for review status changes are high, so interface timeout settings must match the conventional response cycles of maritime and port systems.

## How to configure
This configuration explanation is based on FastGPT v4.17.0. The specific configuration items are as follows:

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Maximum data per single request | 1000–1500 characters | Adapts to the average text length of a single declaration document to avoid request content truncation |
| Interface timeout duration | 60–120 seconds | Matches the conventional response cycles of port and maritime systems, reducing the probability of invalid retries |
| Authentication method | `Authorization` header carries token | Complies with the security access specifications of port systems, ensuring compliance of interface call permissions |
| Context variable binding | Pass declaration number via `variables` parameter to link corresponding files | Accurately matches declaration and review data, avoiding query failures caused by parameter confusion |
| Response data filtering scope | Extract core information from `responseData` field | Only retain key fields required for review, reducing invalid data transmission volume |
| Custom retrieval limit | Top 6 matching results | Adapts to the conventional number of linked port declaration files, avoiding resource consumption from redundant retrieval |

## Three common mistakes
- Phenomenon: After setting the custom retrieval limit to 6 entries, the number of interface return results is less than the configured value. Cause: The retrieval limit parameter was not updated synchronously in the interface configuration, causing the external system call to still use the default threshold.
- Phenomenon: A connection timeout error is returned when calling the interface, with a status code of 504. Cause: The interface timeout setting is too short, and does not match the actual response delay of the port and maritime system.
- Phenomenon: Structured data fields returned by the interface are empty, making it impossible to match the corresponding declaration files. Cause: Core associated fields were not correctly passed via the `variables` parameter, causing the external system to fail to locate target data.

## How to confirm the configuration is complete
- Initiate a single test request carrying a real declaration number parameter, and check whether the file data returned by the interface matches the records stored in the external system.
- Simulate batch interface calls to check whether rate limiting errors are triggered, confirming that the call frequency adapts to the rules of the external port system.
- Upload attachment files in the format required by the port, confirming that the interface can normally receive and parse binary data.
- View interface call logs to confirm that the `Authorization` header correctly carries the token, with no abnormalities in the authorization verification process.
