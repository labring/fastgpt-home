# Port Shipping Declaration Material and Case Review: Vector Models and Indexes

## What the data for this use case looks like
Port shipping declaration material and case review data primarily originates from port document systems, ship safety inspection platforms, and goods declaration ports. It includes two categories: structured declaration forms and unstructured case attachments. Structured data fields include ship name, voyage, bill of lading number, cargo weight (unit: tons or TEU), and declaration category. Cases contain multi-page review records, manifest scans, inspection reports, and similar content. Data updates are grouped by single ship declaration or safety inspection batch. A single batch contains several to dozens of entries. Document lengths vary widely, from short declaration forms with hundreds of characters to long review cases spanning dozens of pages.

## Constraints imposed on vector models and indexing by these characteristics
The constraints imposed on the vector model and indexing link include the following:
Mixed structured fields and unstructured attachments require indexing to retain the association between field semantics and attachment content, and avoid splitting critical identifiers such as bill of lading numbers. Batch-based update rhythm requires index triggering to be tied to the completion node of the declaration batch, otherwise index inconsistency within the batch will occur. Documents contain fixed-unit numeric fields, requiring vector models to retain unit-related semantics during embedding to avoid matching deviations caused by missing units. The presence of long case documents requires chunking logic to adapt to the continuity of cross-page content, preventing splitting of the complete logic chain of review records. Additionally, the `defaultToken` configuration must match the average semantic embedding length of port data to avoid overflow.

## Configuration Settings
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Covers core field combinations of port declaration forms, avoids splitting critical identifiers such as ship name and bill of lading number |
| Overlap Length | 100–200 characters | Connects cross-page case review records, retains continuity of context semantics |
| Similarity Threshold | 0.72–0.85 | Matches the precision requirements of port business for review information, filters low-correlation redundant content |
| Single Search Limit | Top 10 entries | Adapts to the range of case quantities that need to be associated for a single review, avoids returning excessive irrelevant data |
| `maxToken` | 4000 token | Adapts to the total context length of single-batch declaration materials, ensures complete recall of core information within the batch |
| `defaultToken` | Calibrated via actual testing | Adapts to the average semantic embedding requirements of port declaration materials |
| Reranking | Enabled | Filters duplicate or low-correlation index fragments, improves the accuracy of review queries |

## Three Common Misconfigurations
- Phenomenon: After uploading a single-batch declaration case, the interface shows the number of chunks changing from 8 to 13, with duplicate index fragments. Cause: The system did not truncate chunks according to the pagination boundaries of declaration documents, causing content from the same manifest scan to be split repeatedly.
- Phenomenon: After upgrading from an older version to FastGPT v4.17.0, previously queryable ship safety inspection case content can no longer be recalled. Cause: The default embedding rules of the vector model were adjusted in the new version, and the old index was not automatically triggered for regeneration, resulting in incompatible semantic matching logic.
- Phenomenon: Only manual trigger of vector model retraining for a single file is supported, and batch index updates cannot be performed by declaration batch. Cause: Batch-level index triggering rules were not configured, only the trigger logic tied to single-file upload was bound, which cannot adapt to the update requirements of port batch declarations.

## How to Verify Correct Configuration
- Upload a standard container declaration form, check the chunk preview interface to confirm that core fields such as ship name and bill of lading number are not split across different chunks.
- Initiate a query containing cargo weight and voyage information, verify that the chunk length of the recall results falls within the configured 800–1200 character range.
- Batch upload 10 declaration cases from the same batch, check that there are no abnormal duplicates in the number of chunks after index completion, and the correlation of data within the batch meets expectations.
- Adjust the similarity threshold, verify that the matching precision of the recall results meets the actual requirements of port review business.

The values listed above are common starting points and should be evaluated against the reader's own samples.
