# Port and Shipping Declaration Document and File Review: Tool Calling and Plugins

## What the data for this category looks like
Data sources for port and shipping declaration documents and file review include port EDI operation systems, customs declaration platforms, and maritime supervision archives. Data updates are triggered by the declaration process, and corresponding documents are generated immediately after a single declaration is completed. Documents contain structured fields and unstructured attachments: structured fields include declaration number, ship IMO number, cargo category, billing weight (unit: ton), number of containers (unit: TEU), and other fields that comply with international shipping industry standards; unstructured attachments are mostly files in various formats such as bill of lading scans, manifest PDFs, and inspection records.

## What constraints these characteristics impose on the "tool calling and plugins" link
Structured fields of port and shipping declaration documents follow strict industry standards. Tool calling must accurately match fixed field formats, and cannot support non-standard field mapping. Unstructured attachments come in various formats, so plugins must include built-in parsing logic adapted to PDF and scanned images. Declaration processes have clear time requirements, so tool calling must set reasonable response timeout thresholds. Data is scattered across multiple independent systems, so plugins must configure permissions and interface routing rules for multi-source data docking. File review requires comparison with historical similar declaration records, so tool calling must support interface calls for precise queries by declaration number, ship IMO number, and other identifiers.

## Three common mistakes
- Phenomenon: An error `{"object":"error","message":"Only allowed now"}` is returned when calling an external model interface. Cause: The whitelist permission for the corresponding model has not been added in the FastGPT plugin configuration, or the configured model interface does not open the calling permission for the current account.
- Phenomenon: The HTTP tool call shows successful parameter parsing, but the target interface is not actually triggered for execution. Cause: The request method of the interface has not been correctly configured, or a required authentication token field is missing in the request header.
- Phenomenon: Multimodal image recognition tasks return empty results or format errors. Cause: The image has not been converted to base64 encoding format as required, or the field name of the image data has not been correctly specified in the interface parameters.

## How to confirm the configuration is complete
- Initiate a single simulated declaration document parsing request, check whether tool calling automatically matches the corresponding fields and returns structured extraction results.
- View plugin logs to confirm that the calling requests and responses of multi-source data interfaces comply with preset field format requirements.
- Test the unstructured attachment upload and parsing process, confirm that PDF or scanned images can be correctly identified and key information extracted.
- Adjust the tool calling timeout threshold, verify that the error prompt in timeout scenarios matches the expected configuration.
