# Port and Shipping Declaration Material and File Review: Model Access and Configuration

## What this category of data looks like
Port and shipping declaration material and file data mainly comes from port operation systems, customs clearance platforms, and electronic and scanned paper documents submitted by shipping agents. Data update rhythm follows declaration nodes. Single vessel single-declaration data is submitted in real time. Batch voyage files are updated per voyage cycle or daily. Documents are a mix of structured forms, unstructured text, and images. Fixed fields include IMO number, voyage number, container number, gross cargo weight (unit: ton), customs declaration number, and declaration date. Some attachments are also included, such as manifest scans, cargo inspection reports, and container seal photos.

## What constraints these characteristics impose on model access and configuration
The mixed structured and unstructured nature of port shipping declaration materials requires models to support both text parsing and image recognition. Visual-related configurations must be enabled. The large number of fixed fields and strict formatting rules mean model output must strictly match preset field rules. Adjust the context length to accommodate multi-field associated information. The difference in update rhythms between real-time declaration data and batch files requires configuration items to support dynamic adjustment of context refresh thresholds. This avoids timeouts caused by excessive data volume. Some attachment files have large sizes, so limit the total file size for a single upload. This prevents parsing failures or interface request timeouts.

## How to set the configurations
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the context length requirements of multiple fields and multiple attachments in port declaration materials, avoiding truncation of key voyage and cargo information |
| `vision` | Enabled | Required to parse image attachments such as manifest scans and inspection reports, matching the unstructured attachment characteristics of port shipping data |
| `toolChoice` | auto | Supports automatic tool calls to complete structured field verification and format matching, adapting to fixed rules of customs declarations and manifests |
| `maxTokens` | 2000–3000 token | Controls the output length of single-round review results, preventing interface lag or parsing timeout caused by overly long content |
| `AIPROXY_API_ENDPOINT` | Fill in the proxy interface address of the corresponding model | Adapts to data compliance requirements of the port industry, forwards requests via a proxy to avoid direct exposure of sensitive customs clearance data |
| `temperature` | 0.1–0.3 | Maintains the rigor of review results, avoiding field matching errors or format deviations caused by randomness |

## Three common configuration mistakes
- Symptom: A file parsing failure prompt appears after uploading a manifest scan or batch customs declarations. Cause: The `vision` configuration item is not enabled, or the total file size for a single upload exceeds the interface limit.
- Symptom: Structured field verification operations cannot be triggered after deploying an ollama model locally and enabling the tool call switch. Cause: `toolChoice` is not set to auto or a specified tool call mode, or the deployed model does not correctly load the tool call plugin.
- Symptom: A 400 Bad Request error is returned when forwarding model requests via a proxy. Cause: The request parameters contain unsupported fields, or the `AIPROXY_API_TOKEN` configuration is incorrect, causing identity verification failure.

## How to confirm the configuration is correctly set
- Upload a single manifest scan, check whether preset fields such as IMO number and voyage number can be correctly extracted, to confirm that the visual parsing function is working properly.
- Submit batch customs declaration data, check whether the length of the single-round review result matches the expected value, to confirm that the context and output length configurations are reasonable.
- Trigger the field verification operation, check whether the model automatically calls tools to complete format matching and field verification, to confirm that the tool call configuration is working.
- Check the interface request log, confirm that the request address and token match the values set in `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN`, with no identity verification exceptions.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
