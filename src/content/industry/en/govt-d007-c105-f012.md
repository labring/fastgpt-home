# Coal Transportation and Sales Declaration Materials and File Review: Deployment and Upgrade

## What this category of data looks like
Coal transportation and sales declaration materials and file data mainly come from internal transportation and sales management systems, weighing terminals, and ownership qualification databases. Data is generated when each batch of transportation and sales business is triggered, with no fixed batch update cycle. A single file contains fixed fields: mine site name, actual transportation volume (unit: ton), declaration batch number, verification node time. Supporting attachments include weighing slip scans, VAT invoices, and ownership certification documents. Some aggregated file texts can reach thousands of characters.

## What constraints do these characteristics impose on deployment and upgrade
The dynamic generation of single-batch data for coal transportation and sales declaration materials and files, multi-type attachments, and structured fields with units imposes multiple constraints on deployment and upgrade. Dynamic single-batch data requires support for dynamic interface access during deployment to adapt to real-time data pushes from business systems. Fields like transportation volume with tons as the unit, and file structures mixing scans and text, require configuration of vector generation logic that supports multi-format file parsing and retention of unit semantics during deployment. The upgrade process must be compatible with newly added transportation and sales qualification fields to avoid failure of knowledge base field mapping, while ensuring the original data parsing link is not damaged. For local deployment scenarios, local file upload configuration must match local network access paths to prevent file upload failures.

## Three common mistakes
- Symptom: Uploading a weighing slip scan fails during local deployment, with the interface showing cross-origin errors or file access failures. Cause: The `FE_DOMAIN` configuration does not match the actual access address of the local server, preventing the frontend from generating correct upload requests.
- Symptom: An ERRO-level log appears after executing `docker-compose up -d` in a Windows environment, and the service fails to start. Cause: Database or storage connection parameters are not configured correctly, preventing FastGPT from initializing the storage and index link for transportation and sales files.
- Symptom: FastGPT prompts a mkdir failure when starting in a WSL2 environment, unable to create mount directories. Cause: Improper file system permission configuration for WSL2, or the mount path contains unsupported special characters, preventing the creation of temporary directories for file storage.

## How to confirm configurations are correct
- Upload a coal transportation and sales weighing slip scan, check if the file can be stored normally and indexed, confirming that core storage and access configurations are effective.
- Perform a database connection verification operation, confirm that the database connection parameters can establish a normal link.
- Review service running logs, check for errors related to file uploads or database connections, confirming that basic configurations are correct.
- Initiate a simulated declaration material review request, confirm that the service can normally parse structured fields and attachment content in files.
