# Coal-Fired Power Integration Project Declaration Materials and Dossier Review: Deployment and Upgrade

## What the Data for This Category Looks Like
Coal-fired power integration project declaration materials and dossier data mainly originate from official completed forms and on-site inspection reports from project approval, capacity verification, safety acceptance, and other links. Data updates follow individual project declaration cycles, with core dossiers uploaded in batches. Supplementary materials are synchronized on demand during daily reviews. Each individual dossier includes fields such as project number, associated mine and power plant information, capacity parameters, and approval node records. Some attachments contain multi-page scanned documents and structured reports, with field units including industry-specific metering identifiers such as megawatts, tons of standard coal, and ten thousand kilowatt-hours.

## What Constraints These Characteristics Impose During Deployment and Upgrade
The batch document structure and specialized metering fields of coal-fired power integration declaration dossiers require deployment to adapt to large-file storage and structured data association requirements. High-frequency batch upload scenarios create database concurrent access pressure. Upgrade processes must avoid interrupting ongoing synchronization tasks. The verification logic for specialized metering fields must match FastGPT’s document parsing module; otherwise, field parsing failures will occur. Cross-linkage dossier data across workflow links requires database configuration to support multi-table associated queries. Upgrade processes must maintain compatibility with existing data structures.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `200–300` | Adapts to concurrent access volume of coal power declaration dossiers, prevents connection exhaustion |
| `STORAGE_S3_ENDPOINT` | Internal network access endpoint corresponding to object storage | Reduces upload and download latency for large-sized dossier attachments |
| `REDIS_URL` | Internal network connection address with access password | Caches dossier review status and synchronization task progress, reduces repeated database queries |
| `MONGODB_URI` | Replica set formatted connection string | Ensures multi-replica storage and high availability of dossier metadata |
| `FILE_TOKEN_KEY` | 32-bit randomly generated string | Protects download links for dossier attachments, prevents unauthorized access |
| `PG_URL` | Configured connection pool timeout set to `600 seconds` | Adapts to long connection requirements during batch import of declaration materials |

## Three Common Mistakes
- Symptom: After upgrading FastGPT v4.17.0, previously uploaded coal power declaration dossier content does not appear in search results, and no corresponding entries are visible on the knowledge base page. Cause: The database migration script required by the new version was not executed, resulting in failure to synchronize dossier metadata from the old knowledge base to the current version.
- Symptom: The tei-deployed bge-reranker model passes testing, but each search result’s reranking mark is `false`, with no valid reranking results. Cause: `REDIS_URL` was not configured to an address in the same network segment as the reranking service, causing cross-node communication latency and preventing the reranking logic from triggering normally.
- Symptom: After docker deployment, batch-imported dossier attachments cannot be downloaded normally, and the page returns a 403 error. Cause: The key length configured for `FILE_TOKEN_KEY` is insufficient, causing the download link verification logic to fail.

## How to Verify Correct Configuration
- Run FastGPT’s built-in database connectivity detection tool to verify that connections for `MONGODB_URI` and `PG_URL` are normal, with no timeout or authentication failure errors.
- Upload an attachment file from a single coal power declaration dossier, confirm that a valid download link can be generated and the corresponding file can be accessed.
- Trigger a batch update task, check whether the latest task status entries are generated in the cache service corresponding to `REDIS_URL`.
- Call the reranking model test interface, confirm that the returned results include valid reranking scores, with no null values or abnormal marks.
