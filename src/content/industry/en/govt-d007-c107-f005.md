# Declaration Materials and File Review for Coal Mine Production: Tool Calling and Plugins

## What this category of data looks like
Coal mine production declaration materials and file review data primarily originate from mine safety supervision systems, production scheduling platforms, underground monitoring terminals, and official approval systems.
Data update cycles cover three categories: real-time monitoring (such as gas concentration, equipment operating status), daily reporting (such as shift output, maintenance records), and periodic declarations (such as monthly safety reports, quarterly capacity declarations).
Each file includes four core modules: main information, production data report, safety inspection attachments, and approval process logs.
Fields include mine number, shift output, gas concentration value, approval status, and more. Units include tons, ppm, days, and other standard units.

## Constraints imposed by these characteristics on tool calling and plugins
Scattered data sources and diverse data types require tool calling to support integration with multiple data source plugins, preventing single calls from only covering partial data dimensions.
High-frequency updates of real-time monitoring data require plugins to use reasonable timeout and retry mechanisms, avoiding audit interruptions caused by data synchronization delays.
Fixed document fields and unit requirements demand strict parameter format matching during tool calling, preventing invalid audit results from field misalignment.
Multimodal attachments such as underground site photos included in files require plugins to support multimodal vector embedding and parsing, adapting to complex audit scenarios.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | Limited to specified tool ID | Coal mine review requires fixed calls to safety supervision and scheduling plugins. Limiting this avoids model selection bias |
| `functionCall` | Enable strict parameter matching | Declaration material fields are fixed and uniformly formatted. Strict matching ensures correct data format |
| Plugin timeout period | 600 seconds | Some underground data retrieval requires waiting for backend synchronization. 600 seconds covers most conventional scenarios |
| Multimodal model access configuration | Calibrated based on actual testing | File review includes underground photos, requiring adaptation to the parsing logic of multimodal vector models |
| Cross-domain access settings | Allow specified internal network IP ranges | Third-party system API calls need limited access scope to ensure production data security |

This configuration applies to FastGPT v4.17.0.

## Three common configuration mistakes
- When calling multimodal tools, an "unsupported model type" error is returned. The cause is failure to correctly configure the access parameters of the multimodal vector model, and confusion of model adaptation logic from different vendors.
- Tool calling does not trigger the specified tool, returning empty results. The cause is failure to correctly set the `toolChoice` parameter, leading the model to autonomously select tools that deviate from review requirements.
- Third-party browser API calls return cross-domain errors. The cause is failure to configure allowed access domains or IP ranges, violating FastGPT's cross-domain security policy.

## How to confirm configuration is complete
- Submit a standard declaration file including production data reports and underground photos, check if tool call logs successfully retrieve data from safety supervision and scheduling systems.
- Upload underground site photos, confirm that the multimodal model can correctly parse image content and include it in the review scope.
- Adjust the `toolChoice` parameter to the specified tool ID, verify that the model prioritizes using this tool to execute the review process.
- Call the third-party API interface, confirm that the cross-domain configuration takes effect and there are no permission interception issues.
