# Declaration Materials and Case Review for Power Grid Enterprises: Workflow Orchestration

## What the data for this category looks like
The data for power grid enterprise declaration materials and case review comes from three main sources: marketing business systems, customer installation archives, and power dispatching archived files. Updates happen in real time when a single installation task is created. Batch review tasks are synchronized once daily.
Documents are split into two parts: structured metadata and attachments. Structured fields include customer number, installed capacity, applied voltage level, submission date, and review node opinions. Most attachments are PDF files: test reports, construction drawings, and identity documents.

## Constraints imposed on workflow orchestration
These data characteristics create clear constraints for workflow orchestration.
Highly standardized structured fields require built-in variable extraction rules to accurately match preset fields.
A large number of large-sized attachments require filtering rules for attachment parsing, to prevent invalid files from consuming resources.
The fixed node transfer logic of the review process requires binding `nodeId` to enable precise triggering between nodes.
Fast update frequency requires the workflow trigger cycle to align with data update rhythms, to avoid processing expired materials.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Variable extraction rules | Match structured fields declared via `variables`, extract content within the first 1000 characters | The structured field format of power grid declaration materials is unified, so core business parameters must be accurately extracted |
| Node trigger configuration | Bind each review node via `nodeId`, trigger the next node only after material verification passes | Power grid review processes have clear hierarchical transfer requirements, so node trigger logic must be precisely controlled |
| Timeout setting | 600 seconds | The average review time for a single declaration material falls within this range, to prevent unlimited task waiting |
| Attachment parsing rules | Parse only the first 3 core attachments, with per-attachment size not exceeding 1000 MB | Case review only requires core test reports and application forms; filtering non-essential attachments saves resources |
| Branch judgment configuration | Trigger a return node when fields are missing | Complies with power grid review compliance requirements, automatically routing incomplete applications to the supplementary document process |

This configuration was completed using the workflow interface of FastGPT v4.17.0.

## Three Common Configuration Mistakes
- An error `localStorage is not defined` occurs when calling custom code in a workflow. The FastGPT workflow code runs in a node environment, which does not provide the browser-side localStorage global object. Direct calls to this API are not supported.
- Abnormal node transfer occurs after workflow triggering, with result counts differing from expectations. This happens when trigger conditions for review nodes are not correctly bound via `nodeId`, leading to chaotic branch judgment logic and incorrect node trigger order.
- Target field values are not retrieved after configuring variable extraction. This occurs when the required power grid declaration material fields are not correctly declared in `variables`, or when field matching rules do not align with actual document structure details.

## How to Verify a Correct Configuration
- Trigger a test workflow, upload a single standard declaration material, and confirm that field values extracted in `variables` match the material’s actual content.
- Click the test button for each node to verify that nodes bound via `nodeId` trigger transfers as expected, and confirm branch judgment logic is correct.
- Upload a test material with multiple attachments, check that the attachment parsing node only extracts core files and filters non-essential attachments.
- Set a timeout threshold, simulate a long-duration review task, and confirm the workflow completes within the set time or triggers timeout processing.

The values listed here are common starting points. Adjust configurations based on your own specific samples and requirements.
