# Mining and Mineral Processing Declaration Materials and Case Review: Vector Models and Indexes

## What this category of data looks like
Data sources include mining permit application documents, geological exploration ledgers, monthly mineral processing production reports, safety supervision case files, and environmental emission test reports.
Two update schedules apply: declaration materials are updated in batches during project initiation, annual inspection, and expansion. Daily case files are updated with daily mining records and weekly safety inspection archives.
Document structures mostly combine structured forms and long-text reports. Fields include mining depth (unit: meters), daily mineral processing throughput (unit: tons), and tailings pond storage capacity (unit: cubic meters).

## How These Characteristics Impose Constraints on Vector Models and Indexing
Fixed fields in structured forms must be matched precisely, and cannot be split into chunks. The indexing process must handle structured fields and unstructured text separately.
Long-text report segmentation must follow the inherent chapter logic of mining documents to prevent cross-chapter association failures.
Batch-updated declaration materials require incremental indexing support to avoid excessive resource usage from full reconstruction.
Daily updated mining records need low-latency index synchronization to ensure data timeliness during review meets regulatory requirements.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Chunk length | 800–1200 characters | Matches the average chapter length of mining and mineral processing documents, avoiding context breaks caused by cross-chapter chunking |
| Overlap length | 50–80 characters | Ensures text continuity between adjacent chunks, adapting to the paragraph logic of case files |
| Similarity threshold | 0.72–0.80 | Filters low-match irrelevant case files, adapting to the high-precision review requirements of declaration materials |
| Maximum search results per request | Top 10 | Controls the number of returned results to avoid information overload during review |
| Maximum context size | 4000 token | Adapts to long-text input from declaration materials, fitting the adjustment range of FastGPT v4.17.0 |
| `defaultToken` | 1500 | Ensures vector-generated text covers core review fields, meeting the field length requirements of mining documents |

## Three Common Configuration Mistakes
- Phenomenon: Index results only return flat entities, without associating approval workflow relationships between case files. Cause: Document association indexing configuration is not enabled, and only single documents are chunked and vectorized.
- Phenomenon: Parsed mining document fields are missing, such as mining depth and daily mineral processing throughput being empty. Cause: Structured form parsing switch is not enabled, and parsing rules are not configured for the form structure of mining documents.
- Phenomenon: Index update takes too long, with a single full update exceeding 600 seconds. Cause: Incremental indexing rules are not configured, and full vector reconstruction is triggered every time review materials are updated.

## How to Verify Configuration Correctness
- Upload a single mining declaration document, check if chunk results match the document's inherent chapters, and adjust chunk length to fit actual document length.
- Submit a review request, verify that the number of returned results matches the maximum search results per request configuration, and adjust the threshold to fit review requirements.
- Upload new mining records, check if the index completes synchronization within the preset time, and confirm that the incremental indexing configuration is effective.
- View the vector generation log, confirm that the value of `defaultToken` meets the text length requirements of core fields.

The values provided are common starting points and should be measured against the reader's own samples.
