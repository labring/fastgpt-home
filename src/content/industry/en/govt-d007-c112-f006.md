# Grain Reserve Declaration Material and File Review: Citation Source and Traceability

## What this category of data looks like
Data related to grain reserves mainly comes from grain reserve in-and-out warehouse ledgers, annual rotation plan documents, third-party quality inspection reports, and filing documents from local grain and material reserve departments. Data updates are synchronized in real time or weekly along with grain reserve in-and-out warehouse and rotation operations. Most individual documents are structured tables or official documents with fixed formats, with fields including grain category, storage quantity (unit: ton or kilogram), batch number, quality inspection date, warehouse number, in-and-out warehouse time, and other relevant details, with little redundant unstructured content.

## What constraints do these characteristics impose on the citation source and traceability link
The high proportion of structured documents requires that citation traceability strictly match field dimensions, to avoid generalized recall of irrelevant data. Frequently updated reserve data requires regular refreshing of the vector database to prevent referencing expired ledgers. The requirement for fixed fields and units requires retaining the original data's unit identifiers during traceability, to avoid confusion between reserve data with different measurement standards. At the same time, a single document mostly corresponds to a single batch or single business scenario, so the number of recalled documents must be controlled to avoid redundant information interfering with review judgments.

## Configuration Settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `quoteMaxToken` | 800–1200 token | The content length of a single grain reserve ledger or official document mostly falls between 500-1000 token. This range can fully retain the key review information of a single document |
| `responseData` | Return batch number, storage quantity, quality inspection date, file name | Core concerns of grain reserve review include batch, measurement, and quality inspection information. Specifying returned fields can filter redundant content |
| `detail` | Enabled | Full display of the warehouse number and in-and-out warehouse time of the cited document is required to ensure complete details for review and traceability |
| Single search limit | Top 3 entries | A single grain reserve ledger corresponds to a single business scenario. Excessive recall will cause confusion in review logic |
| Reranking | Sort by field matching degree | Field matching priority for structured data is higher than general semantic matching, ensuring core review fields are recalled first |

## Three Common Misconfigurations
- Phenomenon: The number of cited documents returned by the API exceeds the range required for review. Cause: No reasonable single search limit is set, resulting in recall of multiple irrelevant grain reserve ledgers.
- Phenomenon: The cited content does not include the batch number and measurement unit of the grain reserve. Cause: Core fields are not specified via the `responseData` configuration, filtering out traceability information necessary for review.
- Phenomenon: The returned citations are not the high-matching content in the knowledge base. Cause: No dedicated recall sorting rule is configured for structured fields, and relying solely on general semantic matching causes core field matching items to be ranked lower.

## How to Verify the Configuration is Correct
- Submit a standard grain reserve declaration material review request, check whether the fields of the cited documents in the returned results include the preset core traceability information.
- Call the API to view the returned citation data, confirm that the specified file name, batch number, and measurement unit fields are included.
- Simulate multiple review requests, check that the number of recalled cited documents meets the preset single search limit requirement.
- Adjust the vector database refresh cycle, verify that newly updated grain reserve ledgers can be correctly recalled and cited.

The values provided are common starting points and should be measured against the reader's own samples.
