# Shipbuilding Declaration Materials and File Review: HTTP Interfaces and External Systems

## What this category of data looks like
Shipbuilding declaration materials and file review data mainly come from classification society specification documents, shipyard construction ledgers, and shipowner order requirement documents. The data update cadence is bulk updates when new ship type projects are initiated, with quarterly syncs for routine maintenance. Documents are mostly in structured table and mixed text-image formats. Core fields include ship type number, construction batch, material specification, and inspection date. Units include millimeters, kilowatts, tons and other general engineering units. This document is written based on FastGPT v4.17.0.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
The mixed text-image structure of shipbuilding declaration materials requires HTTP interfaces to support binary stream or base64 encoded file transfer, to accommodate attachments such as hull drawings and inspection reports. The characteristics of multiple fields and engineering units require that interface request parameters strictly match preset field names, to avoid parsing failures caused by field misalignment. The bulk update and routine sync cadence requires interfaces to support both full pull and incremental sync invocation modes, to adapt to data sync needs for different business scenarios.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {Exclusive API Key}` | Shipbuilding declaration data involves engineering sensitive information, so Bearer token verification is required to validate call legitimacy |
| `variables` | `{"ship_type": "bulk_carrier", "update_range": "quarterly"}` | Matches the classification and quarterly update cadence of shipbuilding data, and limits the target scope of interface queries |
| `responseData` | `include_attachments: true` | Declaration materials include attachments such as hull drawings and inspection reports, so attachment encoded content needs to be included in the return results |
| Interface Timeout Setting | `600 seconds` | Shipbuilding file review data volume is large, so a longer processing cycle is required for full parsing and return |
| Maximum Request Body Size | `1000 MB` | Single shipbuilding declaration drawings can reach hundreds of megabytes, so large file transfer needs need to be accommodated |
| Request Content Type | `multipart/form-data` | Mixed text-image declaration materials need to be transferred, supporting mixed submission of files and parameters |

## Three Common Mistakes
- Phenomenon: Incomplete base64 encoded drawing content is returned after calling the HTTP interface. Cause: The attachment inclusion parameter is not configured in `responseData`, only text-based declaration fields are returned.
- Phenomenon: 401 Unauthorized error is returned by the interface. Cause: The `Authorization` parameter is not configured correctly, and an invalid or expired API key is used.
- Phenomenon: Only partial entries are returned when synchronizing declaration data in batches. Cause: The query scope is not limited via `variables`, and the default number of entries returned by the interface exceeds the system processing limit.

## How to Confirm Proper Configuration
- Call the test interface, check if the `Authorization` parameter is correctly carried in the request header. Request header content can be viewed via a packet capture tool.
- Initiate a request containing ship type parameters, confirm that the parameters in `variables` are correctly recognized by the interface. The query scope field in the return result can be used for verification.
- Upload a small hull drawing, check if `responseData` returns the corresponding base64 encoded content. Integrity can be verified via an online decoding tool.
- Adjust the timeout setting and initiate a large data volume request, confirm that the interface does not disconnect prematurely. Response duration can be verified via viewing interface logs.

The values provided are common starting points and should be measured against the reader's own samples.
