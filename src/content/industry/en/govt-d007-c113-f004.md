# Declaration Materials and File Review for Shipbuilding: Workflow Orchestration

## What data looks like for this category
Declaration materials and file review data for shipbuilding mainly comes from shipyard design drawings, construction qualification documents, classification society inspection reports, maritime approval files, and similar sources. It is updated in batches according to the single-ship construction cycle. Document formats include mixed types such as PDF design drawings, Word approval forms, Excel inspection ledgers, and others. Core fields include ship type, construction number, inspection item, approval node, displacement, ship length, and similar items, with corresponding units such as tons, meters, pieces, and others.

## What constraints these characteristics impose on the "workflow orchestration" link
Mixed-format documents require the workflow to pre-configure multi-source parsing nodes to adapt to material extraction from different formats. The data updated in single-ship batches requires the workflow to use variable binding to accurately match materials of the corresponding batch. Fields with exclusive unit attributes require the workflow to add format verification nodes to avoid review failures caused by unit errors. The multi-level transfer logic of file review requires the workflow to orchestrate node order and conditional branches to enable automatic transfer of approval status.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Chat history context count | First 6 entries | Core communication for ship declaration and approval usually focuses within 6 rounds of conversation, covering the entire process of material submission, correction, and approval |
| `variables` binding rule | Bind single-ship construction number global variable | Shipbuilding declaration materials and files are managed in single-ship batches, and variables are required to accurately pull data of the corresponding batch |
| Workflow loop variable reference | Allow referencing external global variables | File review requires cross-node calls of cross-link data such as approval status and inspection reports |
| Environment variable configuration | FastGPT backend system settings - Environment Variables module | Standard configuration path for FastGPT v4.17.0 version, used to load interface keys for shipbuilding data |
| Question classification node classification threshold | 0.7-0.9, calibrated based on actual testing | Ship declaration terminology is highly professional, and thresholds need to be adjusted through actual testing to adapt to exclusive classification scenarios |
| Maximum timeout period | 600 seconds | Full set of declaration materials for large ships takes a long time to parse, so sufficient node execution time needs to be reserved |

## Three Common Errors
- Phenomenon: Text content extraction node returns empty fields. Cause: The single-ship number variable in `variables` is not correctly bound, resulting in incorrect matching of pulled data sources.
- Phenomenon: Workflow loop cannot obtain external variables. Cause: The global variable reference permission for the loop body is not enabled, or the upstream node output corresponding to `nodeId` is not correctly referenced in the loop body configuration.
- Phenomenon: Workflow execution times out and reports an error. Cause: The maximum timeout configuration is not adjusted, and the parsing duration of large ship files exceeds the default threshold.

## How to Confirm the Configuration Is Complete
- Trigger the workflow and pass a test single-ship construction number, check whether the text content extraction node returns the material content of the corresponding batch.
- Add a debug log to the loop node to check whether the global variable value of the upstream approval node can be obtained.
- Enter the environment variable configuration page, confirm that the key configuration of the shipbuilding data interface has been loaded, and there are no error prompts.
- Simulate a timeout scenario to check whether the workflow timeout prompt matches the configured 600-second threshold.

The values provided here are common starting points and should be measured against the reader's own samples.
