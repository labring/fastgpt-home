# Declaration Materials and File Review for Rail Transit Equipment: HTTP Interfaces and External Systems

## What this category's data looks like
Data for rail transit equipment declaration materials and file review primarily comes from production quality inspection logs, compliance qualification documents, and project declaration forms. It is updated per single production batch cycle. Each batch of documents includes two types of content: structured fields and attachments. Structured fields include equipment model, production batch number, inspection date, and compliance inspection item results. Attachments are mostly CAD drawings and scanned quality inspection reports. Structured fields must match general compliance standards for national rail transit equipment manufacturing. This adaptation supports FastGPT v4.17.0.

## Constraints imposed by these characteristics on HTTP interfaces and external systems
Structured fields for rail transit equipment declaration data must match national compliance standards. HTTP interfaces must pass parameters using agreed field names exactly. Field mapping errors will cause audit failures.
Attachments include CAD drawings and large-volume quality inspection reports. Interfaces must support large file transfer configuration to prevent transfer interruptions.
Data updates follow single production batch cycles. Interface call frequency must match production batch rhythms to avoid repeated submissions of the same batch data.
Interfaces must return structured audit result fields. This enables subsequent file archiving and compliance traceability.

## Three common mistakes
- When calling the interface to insert documents into the knowledge base, an `Invalid` format error is returned. The cause is failing to pass the `variables` parameter according to rail transit equipment field structures. This prevents the model from recognizing structured declaration data.
- Interface calls frequently trigger timeouts. The cause is not setting a reasonable timeout duration, and not adapting to the time requirements of large attachment transfer.
- After parsing response data, the compliance verification field is empty. The cause is failing to correctly extract the corresponding field from `responseData`. Unstructured attachment content is mistakenly used as the parsing target.

## How to confirm configuration is complete
- Call the test interface to submit single-batch declaration data. Check if the request header carries the `Authorization` parameter. Confirm the returned status code meets expectations.
- View the target knowledge base. Confirm the newly added document includes the submitted structured fields and attachment content. Confirm field names match preset rules.
- Parse the `responseData` returned by the interface. Confirm it includes relevant fields for compliance audit results.
- Simulate submitting multiple batches of data consecutively. Check if interface call logic matches production batch update rhythms. Confirm there are no abnormal repeated requests.
