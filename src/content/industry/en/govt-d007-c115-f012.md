# Submission Materials and File Review for Rail Transit Equipment: Deployment and Upgrade

## What the data for this category looks like
The submission materials and file review data for rail transit equipment mainly comes from vehicle model development documents, production quality inspection records, and official approval files. The data includes structured technical parameters such as axle load, rated power, and material strength, as well as unstructured text such as test reports and approval instructions. The update schedule adjusts based on new vehicle model project launches or batch production runs. Document fields include specialized professional units including kN, km/h, and MPa. A single file review document can reach several thousand characters.

## What constraints these characteristics impose on deployment and upgrade
Since the data includes many structured technical parameters and long-text files, deployment must adapt to structured data storage and large file uploads. Since submission materials are updated with vehicle batches, upgrades must support incremental synchronization to avoid excessive resource occupation caused by full replacement. Since fields include professional units, parameter verification rules must be configured to avoid parsing errors. Since file review needs to associate multi-batch documents, deployment must optimize associated query performance and ensure stability during simultaneous access by multiple users.

This configuration applies to FastGPT v4.17.0.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `20–30 connections` | Adapts to parallel query requirements for multi-batch submission materials |
| `STORAGE_S3_ENDPOINT` | `Dedicated domain name provided by the object storage service provider` | Required to store long-text test reports and batch file review files |
| `FILE_TOKEN_KEY` | `32-character random string` | Protects upload and download permissions for submission materials |
| `REDIS_URL` | `Authenticated single-node or cluster address` | Caches frequently called technical parameters and approval statuses |
| `MONGODB_URI` | `Replica set connection address` | Ensures stable reading and writing of structured submission data |
| `FE_DOMAIN` | `Public access domain name of the deployment node` | Associates the front-end interaction entry for file review |

## Three common mistakes
- Symptom: The specified port cannot be accessed after container startup, and the log only shows partial startup phase information. Cause: `FE_DOMAIN` was not correctly configured as the access address for the corresponding port, leading to front-end service binding failure.
- Symptom: Structured parameters cannot be parsed after submission materials are uploaded. Cause: The permission verification rule for `FILE_TOKEN_KEY` was not configured, resulting in insufficient file read permissions.
- Symptom: Workflows cannot implement multi-round file review conversations. Cause: The connection count for `DB_MAX_LINK` was not adjusted, leading to context query timeouts for multi-round conversations.

## How to confirm the configuration is complete
- Access the configured `FE_DOMAIN` address, confirm that the front-end interface can normally load the submission material upload and file review modules.
- Perform a database connection test, confirm that the connection status of `MONGODB_URI` and `PG_URL` is normal.
- Upload a rail transit equipment test report file, confirm that the file can be normally stored and complete structured parsing.
- Initiate a multi-round file review conversation, confirm that the context can normally associate historical queries and approval records.
