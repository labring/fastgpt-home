# Declaration Materials and Case Review for Communication Towers and Infrastructure: HTTP Interfaces and External Systems

## What the data for this category looks like
Declaration data for communication towers and infrastructure originates from the declaration system of the local communications administration department, tower operation and maintenance ledgers, and scanned paper materials submitted by declaring units. Data updates proceed according to the single declaration process cycle. One single declaration corresponds to a complete set of case files.
The document structure is divided into two parts: structured declaration fields and unstructured attachments.
Structured fields include declaration batch number, base station longitude and latitude, tower height (meters), applicant unit qualification level, and case archive number.
Unstructured attachments include on-site survey photos, scanned ownership certificates, and scanned qualification certificates. Some attachments are converted to retrievable text via OCR recognition.
This document is based on FastGPT v4.17.0.

## Constraints imposed by these characteristics on HTTP interfaces and external systems
The coexistence of structured fields and unstructured attachments requires HTTP interfaces to support both form parameter submission and file upload functions. This avoids issues where only supporting pure JSON requests prevents attachment transmission.
The feature of batch-based updates requires interfaces to support precise queries by batch number and case archive number. This avoids performance losses caused by full data pulls.
The feature of fields with standardized units such as tower height measured in meters requires interfaces to implement unified field mapping rules. This prevents audit data anomalies caused by unit conversion errors.
The feature of large variation in unstructured attachment sizes requires interfaces to set reasonable timeout and retry policies. This adapts to large file transfer scenarios.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {service token generated by internal system}` | Connecting to external declaration systems must comply with HTTP authentication specifications to prevent unauthorized access |
| `variables` | `{"applyBatch": "current declaration batch", "archiveNo": "unique case number"}` | Precisely pull data by declaration batch and case ID, matching the query logic of the review process |
| `responseData` | Return only structured fields and OCR results for the first 2 core materials | Reduce invalid data transmission, adapting to the lightweight data requirements of review systems |
| Interface timeout | 600 seconds | Declaration materials include multiple scanned copies, requiring sufficient time for file transfer and processing |
| Retry policy | 2 retries, 30-second interval | Address call failures caused by network fluctuations, while avoiding repeated submission of review requests |

## Three Common Configuration Mistakes
- Symptom: No matching declaration data is returned after calling the interface, with an empty result. Cause: The key names in `variables` are not aligned with the parameter names of the external system, leading to incorrect global variable mapping.
- Symptom: The interface returns a 403 or 401 error. Cause: The `Authorization` parameter is not configured correctly, or the used service token has expired and not been updated, leading to authentication failure.
- Symptom: The interface call times out and remains unsuccessful after retries. Cause: The timeout period is not set long enough, or declaration materials include oversized scanned copies that exceed the interface transfer limit, leading to request interruption.

## How to Confirm Correct Configuration
- Enter the configured `Authorization` and `variables` parameters in the FastGPT interface debugging interface, initiate a test request, and check that the returned HTTP status code is 200.
- Review the returned `responseData` content, confirming that it includes core structured fields such as declaration batch number and case archive number, as well as expected material OCR text.
- Submit test declaration data to trigger an interface call, and verify whether matching request records and parameters exist in the logs of the external system.
- Simulate a large file upload scenario to verify whether the interface completes the response within 600 seconds, or triggers the preset retry logic.
