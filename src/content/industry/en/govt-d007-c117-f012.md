# Declaration Materials and Case Review for Communication Towers and Infrastructure: Deployment and Upgrade

## What the data for this category looks like
The data for declaration materials and case review of communication towers and infrastructure comes from project approval systems, on-site survey ledgers, operation and maintenance inspection records, and approval circulation logs. A single declaration package includes tower foundation parameter documents, site selection certification documents, power supply agreement attachments, and more. A case is a collection of batch-declared materials, with fields including tower height (unit: meters), load capacity (unit: kilowatts), approval status, upload time, and other relevant fields. The update rhythm is real-time synchronization after a single declaration material is uploaded, and case batch data is updated according to the approval cycle.

## What constraints these characteristics impose on the deployment and upgrade link
The exclusive data characteristics of declaration materials and case review for communication towers and infrastructure impose three constraints on the deployment and upgrade link.
First, single materials include multi-format attachments such as CAD drawings and Word approval forms. This requires configuring a multi-file parsing queue during deployment, and retaining full-format compatibility logic during upgrades to avoid failure to parse exclusive files after a new version is released.
Second, fields carry specific physical units (meters, kilowatts). This requires retaining field unit verification rules after upgrades to prevent unit loss or confusion after parsing.
Third, batch case data is updated according to the approval cycle. This requires adapting database connection configurations to high-concurrency batch queries, and verifying connection stability during upgrades to avoid timeouts during batch review.

## Three common mistakes
- Phenomenon: Model vendor icon loading fails after upgrade, the interface displays broken icons or blank placeholders. Cause: The FastGPT built-in model icon resource package is not updated synchronously, or the `FE_DOMAIN` configuration does not point to the correct static resource address.
- Phenomenon: The prompt `fail to create post presigned url` appears when uploading declaration attachments. Cause: The storage node configured by `STORAGE_S3_ENDPOINT` has insufficient permissions, or the expiration time of the token generated by `FILE_TOKEN_KEY` is too short, causing the pre-signed URL to fail to generate normally.
- Phenomenon: Database connection timeout occurs during batch case review. Cause: The number of connections configured by `DB_MAX_LINK` is lower than the actual concurrent demand, and the parameter value is not adjusted based on actual measurements.

## How to confirm the configuration is correct
- Run a batch upload of 10 tower declaration attachments in different formats, check whether they can be parsed normally and stored to S3 storage, and confirm that the `STORAGE_S3_ENDPOINT` configuration takes effect.
- Initiate a batch case query request, check whether the database connection count dynamically adjusts with concurrent requests, and confirm that the `DB_MAX_LINK` configuration adapts to the current business scale.
- Generate an access token for a declaration file, try to access the corresponding file through the token, and confirm that the token generation logic configured by `FILE_TOKEN_KEY` works normally.
- Restart the service and check the logs, confirm that the connection statuses of Redis, PostgreSQL, and S3 storage are normal, with no error messages.
