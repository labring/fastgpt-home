# Declaration Materials and Case Review for Expressway Operations: Deployment and Upgrade

## What the data for this category looks like
Expressway operations declaration materials and case review data primarily originates from toll audit systems, road law enforcement terminals, traffic record databases, and enterprise OA systems. Data updates follow two modes: real-time trigger and daily batch processing. Real-time data includes individual toll payment supplement applications and law enforcement site photo metadata. Batch data consists of monthly case summary packages. Each document contains two parts: structured fields and attachments. Structured fields include case number, vehicle license plate, traffic section, and payment amount, with units of none, character, kilometer, and yuan respectively. Most attachments are PDF-format law enforcement documents and payment vouchers, and single attachment sizes vary significantly.

## What constraints these characteristics impose on deployment and upgrade
The mixed structured and unstructured data characteristic requires adapting both relational databases and object storage during deployment, to avoid performance bottlenecks from single storage solutions. Real-time updated case data requires high-frequency synchronization with the vector database. If sufficient connection pool resources are not reserved during deployment, data synchronization delays may occur, which impacts review timeliness. The wide variation in attachment sizes requires adjusting file upload timeout thresholds and chunk size parameters during upgrade, to prevent large file transfer failures. Additionally, the need for multi-system data docking requires configuring unified authentication rules during deployment, to avoid permission issues during cross-system calls.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `20–30 connections` | Adapts to the concurrent query volume of expressway operation systems, prevents database connection exhaustion |
| `REDIS_URL` | `cluster address with access password` | Caches case review results and file upload status, reduces database load from repeated queries |
| `STORAGE_S3_ENDPOINT` | `internal network endpoint corresponding to the cloud service provider` | Reduces upload and download latency for large case attachments, improves review efficiency |
| `FILE_TOKEN_KEY` | `32-bit random string` | Ensures authentication security for the file upload interface, prevents unauthorized file submissions |
| `ROOT_KEY` | `key only known to internal operations staff` | Restricts sensitive operation permissions in the FastGPT backend, prevents accidental configuration changes |
| `FE_DOMAIN` | `public domain name of the deployment instance` | Configures valid domains for frontend access, prevents cross-origin request interception |

## Three Common Mistakes
- Phenomenon: After deploying FastGPT locally, when adding a new model, the test interface returns a 403 status code (no body). Cause: `ROOT_KEY` or `FE_DOMAIN` is not configured correctly, leading to failed interface authentication verification.
- Phenomenon: The upgrade plan cannot be found in the documentation interface, and the current latest FastGPT version v4.17.0 cannot be confirmed. Cause: The latest code or image has not been pulled from the official Git repository, or the version identification field in the configuration file has not been updated.
- Phenomenon: After calling the file upload API, it is impossible to determine whether file data and indexing are complete. Cause: The callback interface associated with `FILE_TOKEN_KEY` is not configured, or file processing status in the Redis queue is not monitored.

## How to Confirm Configurations Are Correct
- Run the database connection test script, confirm that the current connection count stays within the range of `20–30 connections`, with no connection timeouts or disconnections.
- Upload a case attachment of approximately 100 MB, verify that the storage bucket configured via `STORAGE_S3_ENDPOINT` can normally receive files, and that file metadata is correctly written to the database.
- Call the test interface for adding a new model, send a request using a valid `ROOT_KEY`, confirm that no 403 error is returned, and the interface functions normally.
- View the Redis queue logs, confirm that cache data for case review has been correctly written, and that the file processing status marker has been updated to completed.
