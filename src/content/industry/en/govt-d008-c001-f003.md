# 12345 Citizen Hotline Ticket Handling Business Process Guidance: Multi-turn Dialogue and Prompt Engineering

## What the Data for This Category Looks Like
This category of data mainly comes from the 12345 citizen hotline platform, contractor business systems, official knowledge bases, follow-up evaluation data, and local hotline management regulations. Daily business documents include request registration forms, dispatch records, handling responses, follow-up records, extension applications, return instructions, and knowledge base entries. These cover the full process from request receipt to closure.
Data is updated daily. Core fields include request content, responsible unit, handling status, response content, follow-up evaluations, and more. There are no fixed statistical percentages or quantitative indicators. Data flows naturally according to business processes.

## Constraints Imposed by These Characteristics on the Multi-turn Dialogue and Prompt Link
Dispersed data sources and daily updates require multi-turn dialogue to regularly synchronize the latest knowledge bases and contractor business data. This avoids using outdated response standards.
The multiple, fixed-structure daily document fields require prompts to clearly distinguish different types of business data such as requests, dispatches, and responses. This prevents context confusion.
The most time-consuming business links are request type and responsible unit judgment, and response content generation. Multi-turn dialogue should focus on these links to reduce invalid interactions.
The data update frequency requires that dialogue context only retains valid ticket records from the past 3 days. This avoids redundant data slowing response speed.
Ticket errors can lead to overdue deadlines, order returns, or repeated complaints. Prompts must clearly remind business compliance requirements.

## Configuration Settings
This setup is based on FastGPT v4.17.0. Specific parameters are listed below:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum Context Length | 1000–1500 token | Adapts to the number of fields in ticket-related documents, avoiding context overflow |
| Historical Message Filtering | Only retain content related to requests, dispatches, and responses in `messages` | Filters redundant non-core conversations such as follow-ups and extensions, improving understanding efficiency |
| Variable Injection | Inject ticket number, request type, and responsible unit via `variables` | Quickly locates corresponding business data, reducing retrieval costs |
| Question Optimization Switch | Enabled, set response threshold based on actual testing | Optimizes user request expressions, improving understanding accuracy |
| Interface Timeout Setting | 600 seconds | Matches the conventional cycle of ticket handling, avoiding mid-process interruptions |
| Tool Call Permissions | Bind business system interface whitelist | Supports automatic operations such as reading ticket directories and updating handling status |

## Three Common Configuration Errors
- Outputting model thinking processes during dialogue: Conversation records include non-business-related reasoning steps. This occurs when thinking log fields in `messages` are not filtered.
- Tool call failing to execute directory reading: No response follows entering an instruction to read a code directory. This occurs when business system directory access permissions are not bound via `variables`.
- Excessively slow dialogue response speed: Noticeable delay appears after initiating a ticket request. This occurs when redundant historical conversations are not filtered, causing context length to exceed a reasonable range.

## How to Verify Proper Configuration
- Initiate a simulated request ticket. Confirm the conversation interface only displays request content, processing steps, and response results, with no extra reasoning logs.
- Call the tool for testing. Enter an instruction to read a specified business directory, and verify that corresponding ticket data is returned.
- View the conversation history associated with `chatId`. Confirm only valid business conversations from the past 3 days are retained, with no redundant content.
- Initiate 3 consecutive ticket requests of different types. Confirm response times meet business expectations, with no noticeable delays.

The values provided here are common starting points and should be measured against the reader's own samples.
