# Business process guidance for 12345 citizen hotline ticket handling: Workflow orchestration

## What data this category includes
This category’s data primarily comes from the 12345 citizen hotline platform, contractor business systems, government knowledge bases, public feedback and review data, and local hotline management regulations. Daily processed documents include request registration forms, dispatch records, handling responses, return visit records, delay applications, return explanations, and knowledge base entries.

Data updates occur daily. Core processing steps focus on request type and responsible unit determination, business fact verification and response, return and re-dispatch, and handling of dissatisfied return visit cases. The overall process relies on multi-source data linkage verification.

## What constraints these characteristics impose on workflow orchestration
Multi-source data access requires workflows to support cross-system data pulling and field mapping to avoid manual entry errors. Daily updated data requires workflows to include scheduled synchronization nodes, ensuring knowledge bases and policy references always match current valid rules.

Different ticket types have widely varying processing logic. Branch nodes must be used to implement differentiated process orchestration after request classification.

Error consequences such as overdue tickets and returned responses require workflows to have built-in timeout reminders and exception handling branches, covering special scenarios like return and re-dispatch and return visit follow-up.

## Configuration guidelines
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Node | Trigger on ticket creation event | Matches the business rhythm of real-time ticket circulation |
| Variable Mapping | Bind the `variables` field to associate cross-system data | Enables automatic alignment of fields from request registration forms and dispatch records |
| Branch Judgment Configuration | Divide execution paths by request type, recall up to 5 associated data entries | Adapts to differentiated processing logic for different tickets |
| Timeout Alert Configuration | Push alerts 7200 seconds after ticket assignment, set request timeout to 600 seconds | Covers time limits for core processing links, avoids ticket blockage from long waits |
| Context Reset | Clear conversation context by `nodeId` | Isolates conversation data for different tickets to avoid information confusion |
| Knowledge Base Synchronization | Run synchronization at 2:00 AM daily | Matches the daily data update frequency |

## Three common configuration mistakes
- Phenomenon: Conversation contexts for different tickets within the workflow are not isolated, and historical conversation information interferes with current processing. Cause: The context reset node is not configured by `nodeId`, resulting in residual conversation data across tickets.
- Phenomenon: After configuring cross-knowledge base search, tickets of different categories repeatedly execute the same result processing logic. Cause: Process isolation after classification is not implemented via branch judgment nodes, leading to redundant calculations and logical conflicts.
- Phenomenon: Tool call nodes fail to trigger normally, returning call failure errors. Cause: The `variables` field is not bound to pass necessary ticket parameters, resulting in missing required information for tool calls.

## How to confirm proper configuration
- Trigger the corresponding ticket creation event, check whether the workflow starts automatically and pulls associated ticket data.
- For different types of requests, verify that the branch node correctly jumps to the corresponding processing path.
- Simulate a ticket timeout scenario, check whether the preset alert or exception handling process is triggered.
- View the knowledge base synchronization logs to confirm whether the daily synchronization task runs normally according to the configured time period.
