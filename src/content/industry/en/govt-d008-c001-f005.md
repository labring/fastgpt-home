# 12345 Citizen Hotline Workorder Processing: Business Process Guidance - Tool Calling and Plugins

## What this category of data looks like
This category of data is sourced from the 12345 citizen hotline platform, business systems of contracted handling entities, official knowledge bases, citizen feedback and evaluation data, and local hotline management regulations. The update frequency is daily. Daily associated documents include request registration forms, dispatch records, handling responses, return visit records, deferral applications, return explanations, and knowledge base entries. Common fields include request number, responsible entity, request category, processing progress, response content, and citizen evaluation results.

## Constraints on tool calling and plugins from these characteristics
Multi-source data access requires tool calling to support interface formats of different business systems, to avoid data parsing errors. Daily updated datasets require tool calling frequency to match business rhythm, to prevent excessive resource usage from overly frequent calls. Rich document fields require tool calling to accurately match core fields such as request number and handling entity, to prevent misalignment between call results and workorder information. Error consequences such as overdue workorders and returned responses require tool calling to configure failure retry mechanisms and exception verification logic, to ensure workorder processes are not interrupted.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0

| --- | --- | --- |
| `toolChoice` | `auto` | Adapts to the need for dynamic tool selection in 12345 workorder scenarios, no manual specification of called functions required |
| `functionCall` | `["query_12345_workorder", "query_undertake_unit"]` | Presets a list of callable tool functions for core business scenarios including workorder query and responsible unit query |
| Tool call timeout | `300 seconds` | 12345 workorder business responses typically need to be completed within a reasonable time frame; timeouts will affect workorder circulation efficiency |
| Maximum number of returned entries per tool call | `Top 3` | Workorder-related data is usually concentrated in the latest 3 records; excessive returns will increase context burden |
| Tool result cache duration | `86400 seconds` | Matches the daily update frequency of workorder data, prevents calling outdated cached data |

## Three Common Misconfigurations
- Phenomenon: Both tool call logs and AI response content are displayed in the interface after tool calling. Cause: Output filtering rules were not configured correctly, so original tool call code snippets were not blocked.
- Phenomenon: Parameter verification failure prompts are returned when calling the workorder query interface. Cause: The correct request number field was not passed in the tool call parameters, so the interface cannot match the corresponding workorder data.
- Phenomenon: Tool call results do not match actual workorder data. Cause: No cache verification logic was set for tool results, so outdated cached data was called.

## How to Verify Successful Configuration
- Initiate a workorder query request, check whether the fields returned by the tool call match the fields on the request registration form.
- Simulate a timeout scenario, check whether the tool call triggers the retry mechanism and generates exception logs.
- View the tool call logs, confirm that only AI-generated response content is displayed, with no original tool call code.
- Upload a test attachment, confirm that the tool can synchronize attachment information to the corresponding workorder process node.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
