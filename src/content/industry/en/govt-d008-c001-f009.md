# 12345 Citizen Hotline Ticket Handling Workflow Guidance: Model Integration and Configuration

## What this category of data looks like
This category of data mainly comes from the 12345 citizen hotline platform, contractor business systems, official knowledge bases, public follow-up evaluation data, and local hotline management regulations. Daily generated documents include request registration forms, dispatch records, handling replies, follow-up visit records, delay applications, return explanations, and knowledge base entries. Data is updated daily. Document fields usually include request number, request content, responsible unit, handling progress, reply standards, follow-up evaluation results, etc. There is no unified legal format, and it adjusts according to local hotline operation rules.

## Constraints on model integration and configuration
The daily data update requirement means knowledge base synchronization must match the daily refresh rhythm to prevent outdated data from affecting ticket judgment. The multi-source heterogeneous document structure and fields require the model to accurately identify core fields such as request type and responsible unit. As a result, retrieval and context length must adapt to the information density of different document types. The risk of errors such as overdue tickets or rejected replies means timeout configurations must strictly align with hotline handling response requirements. Configurations must also adapt to data format differences across contractor business systems to avoid field parsing exceptions.

## Configuration settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Config Item | Suggested Value | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the total information volume of multi-source ticket documents, preventing truncation of core dispatch, reply, and follow-up visit records |
| `maxTokens` | 4000 token | Matches the standard length requirement for hotline ticket replies, preventing generated content from exceeding business communication scope |
| `quoteMaxToken` | 1500 token | Limits the length of a single quoted document, ensuring retrieved content focuses on core fields such as request type and responsible unit |
| `temperature` | 0.2–0.4 | Reduces generation randomness, ensuring reply standards comply with hotline management regulations, avoiding uncertain statements |
| Rerank model toggle | Enabled | Targets the short text characteristics of ticket requests, improving the matching accuracy between retrieved content and requests |
| `AIPROXY_API_ENDPOINT` | Fill in the local or cloud interface address according to the deployment environment | Adapts to the large model call link in the 12345 hotline scenario, ensuring data transmission compliance |

## Three common configuration mistakes
- No matching results in online retrieval testing after enabling the rerank model: This is usually caused by an incorrectly bound rerank model call link, or the number of original retrieved entries failing to meet the minimum input requirement of the rerank model, resulting in the rerank step not being triggered.
- When `quoteMaxToken` or `maxContext` values are set too large, the context cannot be sent to the large model normally: The platform has a limit on the total token count for a single request. Exceeding the threshold will automatically truncate or discard the context content.
- Frequent request timeouts when deploying a large model locally: This is caused by insufficient local hardware resources, or API timeout configurations not adapting to the large model response duration, resulting in request timeout errors during the waiting process.

## How to confirm the configuration is complete
- Knowledge base index logs are reviewed to confirm that rerank model call records exist and have no errors.
- A single ticket test conversation is initiated, and the length of retrieved documents displayed in the context panel is verified to match the `quoteMaxToken` configuration value.
- Large model call logs are reviewed to confirm that the total token value of the request does not exceed the platform limit, and the response duration meets expectations.
- A combination of multiple ticket documents is imported for testing, and no truncation or discard prompts are observed.

The values provided are common starting points and should be measured against the reader's own samples.
