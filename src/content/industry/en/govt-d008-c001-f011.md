# 12345 Citizen Hotline Ticket Handling Process Guidance: Forms and Interactions

## What this category of data looks like
Data for this category primarily comes from the 12345 citizen hotline platform, contractor business systems, public knowledge bases, follow-up evaluation data, and local hotline management regulations. Data is updated on a daily basis. Daily documents include request registration forms, dispatch records, handling responses, follow-up records, extension applications, return explanations, and knowledge base entries. Common data fields include request type, responsible unit, handling progress, response content, follow-up evaluation results, and more. There is no unified fixed format, so adaptation to the field definitions of each region’s hotline platform is required.

## What constraints these characteristics impose on the "forms and interactions" link
The multi-source and scattered nature of data requires the forms and interactions link to support field mapping configuration for multiple data sources, to adapt to non-standardized fields of different regional hotline platforms. The daily update frequency requires the interaction link to configure timed synchronization trigger logic, to ensure ticket data is available in real time. The diverse document types require support for interactive components that dynamically load different document templates, to adapt to form requirements for scenarios such as request registration, dispatch, and response. The non-uniform field characteristics require the interaction link to provide custom field configuration capabilities, to meet the personalized form needs of each contractor. At the same time, consequences of errors such as overdue tickets or returned responses require adding mandatory field verification and progress reminders in form interactions, to reduce the probability of operational mistakes.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
|---|---|---|
| `formInput` | Preset field groups by request type. The request registration group includes contact information and request description. The response group includes handling content and response basis | Adapts to the document structure of different ticket links, reducing manual configuration workload |
| `userSelect` | Preset options by contractor hierarchy, including sub-districts/townships, industry competent departments, and direct contractor units | Matches the responsible unit field in data sources, simplifying request assignment processes |
| Form field verification rules | Mandatory fields include request description and contact phone number. Set the verification timeout threshold to 600 seconds | Prevents ticket overdue caused by missing fields or overly slow operations |
| Multi-source data synchronization trigger | Automatically synchronize at 2:00 AM daily. Manual trigger can update ticket data in real time | Matches the daily update frequency of data, balancing real-time performance and system load |
| Template switching configuration | Support switching between 3 templates: request registration, dispatch, and response. Maximum input per template is 800–1200 characters | Adapts to document length requirements for different links, meeting content input needs for daily handling |
| Follow-up reminder configuration | Trigger follow-up forms within 24 hours after a ticket is completed | Matches the business process of follow-up records, improving the completeness of evaluation data |

## Three common misconfigurations
- Phenomenon: When configuring text extraction interactions for ticket responses, the optional model list only includes GPT series models, and other connected models cannot be selected. Cause: The model configuration of the text extraction module is not associated with the globally connected model pool, and only the default model group is bound.
- Phenomenon: A timeout error occurs after form submission, with a returned status code of 504. Cause: A reasonable multi-source data synchronization trigger range is not configured. Synchronization covers too much historical ticket data, exceeding the system's single-processing limit.
- Phenomenon: Submission of a custom form with empty mandatory fields still passes verification. Cause: No verification trigger condition is configured for mandatory fields, or the trigger condition is only set to take effect during the editing phase, and does not cover the official ticket submission phase.

## How to confirm the configuration is complete
- Enter the ticket handling application configuration page of FastGPT v4.17.0, check whether the field groups of the `formInput` module are preset according to request type.
- Manually trigger multi-source data synchronization, and check whether the latest dispatch records and request data can be pulled from the configured data sources.
- Submit a test ticket that includes mandatory fields, confirm that the verification rules trigger normally, and a prompt pops up when submitting with empty fields.
- View the model selection list, confirm that all connected models are displayed in the optional range, with no omissions.
