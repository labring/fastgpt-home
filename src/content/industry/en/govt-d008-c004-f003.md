# Business Process Guidance for Active Public Disclosure and Policy Publication: Multi-turn Dialogue and Prompt Engineering

Reference only; verify against the target FastGPT release and deployment documentation.

## What data in this category looks like
Data sources for this category include government portal websites, document management systems, government information disclosure directories, policy document repositories, and press conference materials. Commonly processed documents cover policy documents, policy interpretation drafts, public disclosure directories, information release approval forms, press releases, and website column update records.

The data update frequency is daily. Documents include fields such as public attribute flag, policy document number, publication time limit requirement, corresponding website column affiliation, and other related fields. Strict compliance with public review process specifications is required.

## What constraints do these characteristics impose on the multi-turn dialogue and prompt engineering link
The daily data update requirement means multi-turn dialogue context must synchronize the latest policy document numbers, public attribute flags and other information in a timely manner. This avoids caliber deviations caused by calling outdated content.

Documents include process-related data such as information release approval forms and column update records. Prompts must clearly distinguish the permission boundaries between business process guidance and release review. They must not handle confidential or review-stage content beyond authorized scope.

The positioning of active public release for the general public means dialogue logic should target general audiences. There is no need to adapt exclusive processes for individual applications. At the same time, the dialogue logic must strictly match the column affiliation rules of the public disclosure directory to ensure generated content corresponds to the correct release channel.

## How to configure settings

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Context window length | 8000–12000 characters | Policy documents and interpretation drafts have relatively long length, need to cover complete context to avoid information gaps |
| Global variable loading | Enabled, bound to `variables` parameter | Need to synchronize fixed business fields such as public disclosure directories and column affiliations, use global variables to reduce repeated configuration |
| Historical message invocation | Bound to `messages` parameter, retain the first 5–15 dialogues | Multi-turn process guidance needs to trace back the user's earlier query intent, fully loading historical context can improve guidance accuracy |
| Tool call timeout | 30–60 seconds | Policy document retrieval and public attribute judgment require certain processing time, timeout can interrupt abnormal requests |
| Conversation ID binding | Bound to `chatId` parameter, isolate context per session | Different business scenarios or users require independent conversation contexts to avoid information confusion |
| Prompt template configuration | Calibrated based on actual testing | Need to adapt guidance logic for different business scenarios such as policy interpretation and public disclosure directory updates |

## Three common misconfigurations
- Phenomenon: A 400 status code is returned when calling the MySQL tool with no response body. Cause: Database connection parameters are not configured correctly, or the tool call timeout setting does not match the actual business processing duration.
- Phenomenon: Saved global variables from historical conversations cannot be loaded in new conversations. Cause: The `variables` parameter is not bound, or global variables have not been mapped and configured in the workflow.
- Phenomenon: Inconsistent policy caliber appears across multi-turn dialogues. Cause: The `chatId` parameter is not bound, and context from different sessions is incorrectly shared, leading to confusion of historical messages.

## How to confirm the configuration is correct
- Initiate a test dialogue, query the public attribute of a certain policy, confirm that the returned content includes the correct public disclosure directory affiliation field.
- Trigger a tool call, check the tool log, confirm that the returned response body is normal with no 400 status code error.
- Open two independent conversations, query different policy content separately, confirm that the contexts of the two sessions do not interfere with each other.
- View the global variable configuration panel, confirm that the `variables` parameter is bound to required fixed fields such as public disclosure directories and column affiliations.
