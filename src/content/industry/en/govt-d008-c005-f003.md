# Business Process Guidance for Property Rights, Assets and State-owned Capital Management: Multi-turn Dialogue and Prompting

## What this category's data looks like
This category of data mainly comes from state-owned assets supervision information systems, enterprise asset management systems, property rights exchange systems, evaluation agency reports and financial statements. Commonly processed documents include property rights registration forms, asset evaluation reports, property rights transfer plans, on-site transaction announcements, and asset disposal approval documents. Fields include ownership number, asset category, evaluation value, transaction status and others. The update frequency is monthly. The data must cover the registration, evaluation, transfer and disposal stages of the full life cycle of stock assets, and fields must match the unified reporting specifications of state-owned assets supervision.

## What constraints these characteristics impose on the multi-turn dialogue and prompting link
The monthly update frequency requires the dialogue system to support regular synchronization of stock data to avoid using expired asset and transaction information. The structural differences across multiple types of documents mean prompts must be adapted to the field extraction logic for different documents. The decentralized nature of data sources requires multi-turn dialogue to guide users to supplement missing cross-system fields and complete verification step by step. Processes such as ownership verification and evaluation filing take a long time, so dialogue must guide users to upload corresponding approval documents and reports in stages, avoiding requesting too much information at once which could cause operation interruptions. Missing required fields may lead to transaction suspension or accountability, so each dialogue turn must clearly verify required items.

## How to set configurations
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Context window size | 8000–12000 token | Adapt to the text length of multiple asset documents and approval processes |
| Multi-turn dialogue history retention duration | 7 days | Match the monthly data update cycle, retain dialogue records for the full business handling cycle |
| Number of recalled results | Top 5 entries | Cover document fragments from core links such as property rights registration, evaluation, and transaction |
| Variable binding scope | Global application variables | Uniformly call asset fields and approval status synchronized from state-owned assets systems |
| Prompt template triggering rule | Match by dialogue stage | Corresponding to different handling links such as property rights registration, evaluation filing, and on-site transaction |
| Dialogue timeout threshold | 600 seconds | Provide sufficient time for users to upload multiple documents and fill in complex fields |

## Three common mistakes
- Issue: Dialogue history fails to load for unauthenticated users, the interface shows a blank screen or displays the error "Session does not exist". Cause: Anonymous session persistent storage for `chatId` is not configured, or cross-session historical data synchronization permission is not enabled.
- Issue: When nesting a sub-app call in a parent workflow, the sub-app does not record dialogue logs. Cause: Context passthrough configuration for the parent workflow and sub-app is not enabled, causing the `messages` parameter to not be passed correctly.
- Issue: The form input node continuously displays dialog boxes in a nested workflow. Cause: The trigger condition for the form node is not set to only execute at the top level of the current workflow, or the display control logic for the `variables` parameter is not bound.

## How to confirm configurations are set correctly
- Upload typical documents from this category, such as property rights registration forms or asset evaluation reports, to verify that the dialogue can automatically extract corresponding business fields.
- Initiate an unauthenticated session, complete one interaction, exit the page, then re-enter to confirm that historical records load normally.
- Configure a nested call scenario to verify that interactive data from the sub-app is correctly recorded by the parent workflow.
- Simulate a timeout operation to confirm that system prompts comply with expected business handling logic.
