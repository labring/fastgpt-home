# Business Process Guidance for Property Rights, Assets and State-owned Capital Management: Workflow Orchestration

## What this category of data looks like
This category of data mainly comes from state-owned assets supervision information systems, enterprise asset management systems, property rights exchange systems, evaluation agency reports and financial statements, with a monthly update frequency.
Daily business documents include property registration forms, asset evaluation reports, property rights transfer plans, on-site transaction announcements, and asset disposal approval documents.
Data fields cover asset ownership numbers, evaluation values, transaction base prices, approval statuses, and more. Units include ten thousand yuan, square meters, pieces, and others.
The data structure is primarily a mix of structured forms and unstructured reports. Some core fields require cross-system consistency verification.

## What constraints do these characteristics impose on workflow orchestration
The monthly update frequency requires scheduled data source synchronization tasks in workflow configuration. This avoids using expired asset and transaction data.
The mixed data structure of structured forms and unstructured reports requires the workflow to integrate two types of nodes: structured field extraction and unstructured content parsing. These nodes process standardized forms and documents such as evaluation reports separately.
The cross-system verification requirement for multiple business fields requires the workflow to split into independent nodes. The nodes correspond to business links such as property rights registration, evaluation filing, and on-site transaction. Each node uses the verification logic for its specific fields.
The strict accountability requirements for state-owned assets require the workflow to add an abnormal interception node. This node triggers an alarm for abnormal fields, process deviations, or cross-system data inconsistencies. It also blocks subsequent processes.

## How to set configurations
This document’s configuration instructions apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Data source synchronization cycle | 30 days | Matches the monthly update frequency of this category of data |
| Multi-model conversation token strategy | Independent token counting | Meets the requirement of isolating large model calls for different business links (evaluation, transaction) |
| Specified database query binding | Bind database connections corresponding to relevant systems | Adapts to exclusive data sources such as state-owned assets supervision and property rights exchange systems |
| Workflow node timeout | 600 seconds | Covers the time required for unstructured report parsing and cross-system data pulling |
| Variable binding | Bind core business fields via the `variables` parameter | Uniformly manages core business data such as asset ownership and transaction base prices |
| Node trigger rule | Trigger based on the verification result of the previous node’s output | Ensures the process proceeds to the next link only after pre-verification is passed |

## Three common configuration mistakes
- Phenomenon: When calling a workflow via a channel link, the return shows "undefined" is not valid JSON. Cause: The `variables` parameter in the workflow is not bound to required business fields. This results in missing parameters during channel calls and serialization failure.
- Phenomenon: Token overrun errors occur when orchestrating multiple large model nodes in a workflow. Cause: The independent token counting strategy is not configured. Large model calls for different links share token quotas, exceeding the per-round call limit.
- Phenomenon: No results are returned when the workflow attempts to initiate a query to a specified database. Cause: The database connection corresponding to the relevant system is not correctly bound. Or the node trigger rule is not configured to allow cross-system data pulling.

## How to confirm the configuration is correct
- Manually trigger the workflow. Check whether the business fields output by each node match the fields in the original documents.
- Call the channel link. Check whether the JSON format of the returned result meets expectations. Confirm that the `variables` parameter is passed normally.
- Configure a test expired data source. Verify whether the workflow triggers a synchronization alarm or intercepts the process.
- Test a series of multiple large model nodes. Confirm that the token counting for each node is independent. No overrun errors should occur.
