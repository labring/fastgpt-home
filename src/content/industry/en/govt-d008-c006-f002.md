# Business Process Guidance for Notifiable Infectious Disease Information Reporting and Monitoring: Vector Models and Indexes

## What data for this category looks like
Data for this category originates from the Chinese Center for Disease Control and Prevention Information System, medical institution HIS and infectious disease reporting systems, and laboratory testing systems. Updates occur daily. Daily documents include infectious disease reporting cards, epidemic analysis reports, case correction records, clustered outbreak reports, and epidemiological investigation reports. The data covers structured case fields and unstructured epidemiological investigation text. Relevant content must be processed in strict accordance with legal notifiable infectious disease reporting rules. Data links to core business information such as case diagnosis and reporting time limits.

## What constraints these characteristics impose on vector models and indexing
The multi-source data with daily incremental updates requires indexes to support incremental synchronization logic. This avoids resource consumption and time delays caused by full index rebuilding. Multi-source and heterogeneous document types require adaptive chunking strategies. Long-text epidemiological investigation reports must retain contextual connections. Structured reporting cards must accurately match core business fields. Data must comply with legal notifiable infectious disease reporting rules. Indexes must retain vector mappings for key fields such as case numbers and reporting time limits. This ensures retrieval results meet business compliance requirements. Frequent case correction records generate duplicate data chunks. Indexes must support deduplication logic. This prevents redundant retrieval results from interfering with abnormal signal aggregation.

## Configuration Recommendations
| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | This category includes long-text epidemiological investigation reports and structured reporting cards. This range balances contextual completeness and retrieval accuracy |
| Overlap Length | 100–150 characters | Case-related information often spans chunks. Overlap preserves core links such as case numbers and reporting time limits across chunks |
| Similarity Threshold | 0.72–0.80 | Keywords related to case diagnosis and legal reporting rules must be matched accurately. This avoids low-relevance results interfering with abnormal signal aggregation |
| Single Search Limit | Top 8 results | Daily updated multi-source data volume is moderate. This quantity covers the retrieval needs for core abnormal signals |
| `defaultToken` | `2000` | Adapts to the contextual length of epidemic analysis reports for this category. Prevents truncation of key analysis content |
| `maxToken` | `8000` | Aligns with the default contextual upper limit of FastGPT v4.17.0. Meets completeness requirements for long-document retrieval |

## Three Common Misconfigurations
- Phenomenon: A large number of irrelevant historical case records appear in retrieval results, with no clear relevance sorting. Cause: No reasonable similarity threshold is set. Low-relevance document chunks are recalled, interfering with abnormal signal aggregation.
- Phenomenon: Index tasks remain stuck in "pending" status for long periods, with no progress updates. Cause: No incremental indexing strategy is configured. Full indexing is performed on daily fully updated multi-source data, consuming large amounts of computing resources.
- Phenomenon: Key case correction records are missing from retrieval results, and the latest diagnosis information cannot be matched. Cause: Chunk length is set too small. Descriptions linked to case corrections are truncated, preventing vector retrieval from matching complete business logic.

## How to Verify Successful Configuration
- Import a single epidemic analysis report, perform a retrieval test, and verify the chunk integrity and relevance sorting logic of returned results.
- Simulate daily incremental data import, check the execution progress and resource usage of index tasks, and confirm that the incremental synchronization logic is active.
- Search for keywords that include case correction records, verify that returned results contain the latest correction information, and confirm that vector mappings for linked fields are correct.
- Check index logs, confirm there are no redundant index records for duplicate document chunks, and verify that the deduplication logic is working properly.
