# Business Process Guidance for Petition Matter Handling: Tool Calling and Plugins

## What the data for this category looks like
Data sources for this category include the national petition information system, local petition systems, the 12345 citizen hotline platform, grassroots governance platforms, and historical petition archives. The update frequency is daily.
Documents processed daily include petition registration forms, acceptance notices, transfer and assignment letters, handling opinions, review and re-examination applications, and resolution plans. Document fields include appeal content, acceptance ID, responsible unit, handling progress, review and re-examination status, and others. Most field types are string or enumeration values, and field naming varies across different platforms.

## What constraints these characteristics impose on the "tool calling and plugins" link
Plugins must support cross-system field mapping to address multiple data sources and inconsistent field naming, preventing extraction errors caused by field name differences.
Plugins must be configured with scheduled synchronization tasks to match the daily data update frequency, ensuring the latest petition business data is used during calls.
Tool calls must accurately match key parameters for petition handling, aligned with the fixed field structure of core documents. Use `toolChoice` to automatically match the current workflow link, and combine with `functionCall` to strictly validate fields.
Failure to follow these requirements may disrupt time-consuming steps such as identifying acceptance scope and coordinating responsible units, and even lead to repeated petitions or petitions submitted at a higher level than allowed.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | Auto | Adapt to the multi-link workflow of petition matter handling, automatically select appropriate tools for steps including appeal identification, responsibility coordination, and opinion generation |
| Single tool call parameter limit | First 6 parameters | Match the number of core fields in the petition registration form, to avoid redundant parameters interfering with business processing |
| `functionCall` | Strict mode | Ensure extracted fields comply with petition business specifications, prevent invalid parameters from entering the handling workflow |
| Plugin data synchronization cycle | Daily 0:00 | Align with the daily update frequency of business data, to ensure the latest system data is used during calls |
| Tool call timeout threshold | 300 seconds | Match the interface response duration of petition systems, to avoid handling workflow interruptions caused by waiting timeouts |

## Three common configuration errors
- Phenomenon: The `q` parameter is empty during tool calling, and valid petition appeal content cannot be retrieved. Cause: User input questions are not mapped to the plugin's preset `q` parameter position, and only unstructured original text is passed.
- Phenomenon: Regeneration of the plugin schema file in OPENAI V3 format fails. Cause: The option to export the complete configuration package is not selected in the plugin editing interface, and only code snippets are copied without retaining original parameter mapping and field rules.
- Phenomenon: The responsible unit field returned by plugin calling falls outside the legal acceptance scope. Cause: The `functionCall` strict mode is not enabled, causing fields extracted by the tool to not meet the legal subject requirements for petition handling.

## How to confirm the configuration is complete
- Import a single petition registration form test sample, check that the tool call correctly extracts core fields including appeal content and acceptance ID.
- Trigger the plugin export operation, confirm that the generated schema file complies with the OPENAI V3 format specification.
- Simulate the daily data synchronization task, check that the plugin automatically pulls the latest petition system data and completes the update.
- Input a structured test petition appeal, check that the `q` parameter is correctly populated with the core question content submitted by the user.
