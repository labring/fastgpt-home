# Business Process Guidance for Public Data Catalogs and Open Data: HTTP Interfaces and External Systems

## What data in this category looks like
Data in this category comes from local public data open platforms, integrated big data platforms, departmental business databases, and electronic credential repositories. Maintained documents include public data resource catalogs, data open lists, data item descriptions, desensitization rules, interface documents, and update frequency descriptions.
Data updates occur once per month. The overall format is structured, with core fields including data item unique identifiers, open usage scopes, desensitization processing rules, interface call permission requirements, and update cycles. The description length for single data entries typically falls within the hundreds of characters range.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Monthly updated data means interface call frequency should not be too high. This avoids repeated full data pulls that increase system load. Multiple data sources require interfaces to adapt to authorization verification rules of different departments, and support multiple authentication methods. Structured data fields require returned interface content to strictly match data item descriptions in the public data catalog. This prevents missing fields or format deviations. Desensitization rules require interfaces to complete preset desensitization processing before returning data, to prevent sensitive information leaks. Clear data open access boundaries mean interfaces must strictly restrict call permissions per open conditions, to prevent unauthorized access.

## How to configure settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Carry department-specific API keys | Adapt to authentication requirements of different data providing departments, comply with authorization boundaries of public data opening |
| `variables` | Bind data item identifiers from the data catalog | Ensure interface requests accurately match target data, avoid pulling irrelevant data |
| `responseData` | Filter desensitized fields per catalog requirements | Strictly follow desensitization rules, prevent sensitive data leaks via interfaces |
| Timeout period | 600 seconds | Adapt to time required for pulling multi-source data, avoid request interruptions due to large data volume |
| Retry attempts | First 3 attempts | Address scenarios where interfaces are temporarily unavailable, reduce probability of single request failure |
| Data paging | Split into 100 items per page | Match batch pulling logic for structured data, reduce load on single request |

## Three common mistakes
- Phenomenon: Garbled characters appear when uploading public data catalog content via web pages, local files, or APIs. Cause: Request headers do not specify UTF-8 encoding format, causing Chinese or special characters to fail correct parsing.
- Phenomenon: `responseData` fields returned by API calls do not match data item descriptions in the public data catalog. Cause: Data item identifiers in `variables` are not bound, causing the interface to pull data beyond the open scope.
- Phenomenon: API calls return 403 Forbidden status code. Cause: Authentication information in `Authorization` is not configured correctly, failing permission verification from the data providing department.

## How to confirm configuration is complete
- Send a test request, check if returned `responseData` fields match data item descriptions in the public data catalog.
- Review authentication logs, confirm the `Authorization` parameter is correctly carried and passed verification.
- Verify that identifiers bound to request `variables` point to entries in the target data catalog.
- Simulate a pull request after monthly updates, check if data can be synchronized normally.

The values provided are common starting points, and should be evaluated against samples from the respective deployments.
