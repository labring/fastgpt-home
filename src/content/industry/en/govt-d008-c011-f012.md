# Business Process Guidance for Pension, Work Injury, and Unemployment Benefit Verification: Deployment and Upgrade

## What data for this category looks like
Data for this category originates from social insurance management systems, personal benefit records, labor relations and work injury identification systems, and electronic social security card platforms. It updates once daily.
Daily processed documents include benefit application forms, payment period certificates, retirement approval forms, work injury identification materials, and unemployment insurance benefit application materials. These contain fields such as insured person identity information, payment period length, work injury identification results, and unemployment insurance insured status. Units involved include payment months, benefit calculation base, and application amount. Structured and semi-structured data from multiple systems must be linked together.

## What constraints these characteristics impose on deployment and upgrade
Data sources for this category are scattered and updated daily. During deployment, cross-system scheduled synchronization links must be configured to ensure data timeliness.
Daily document types are varied. Parsing rules for different formats must be supported. During upgrade, parsing compatibility for each document type must be validated.
Since data is directly tied to benefit disbursement, accuracy requirements are high. Data format verification and consistency verification steps must be added during deployment and upgrade to prevent incorrect or missed disbursements.
Additionally, the service must be deployed on an internal office network. Internal network access permissions must be configured to protect sensitive information security.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `DB_MAX_LINK` | `300–500` | This category synchronizes data from multiple systems daily. A stable database connection pool must be maintained to avoid business disruption from exhausted connections |
| `STORAGE_S3_ENDPOINT` | Corresponding internal network storage node address of the social insurance system | Daily documents are mostly generated by internal systems. Using internal storage ensures data security and access speed |
| `REDIS_URL` | `600-second timeout configuration` | Session data for benefit verification processes requires short-term caching. The timeout setting matches the average time required for business processing |
| `FILE_TOKEN_KEY` | Generate a key according to business document encryption rules | Application materials involve personal sensitive information. Encrypted storage and transmission are required to comply with compliance requirements |
| `FE_DOMAIN` | Internal network domain name of the social security service window | Deployment scenarios are mostly internal office networks. Matching internal network access addresses ensures normal usage |

## Three common configuration mistakes
- Symptom: After upgrading to FastGPT v4.17.0, the chat window returns the error `Failed to parse URL from /model/getProviders`. Cause: `MONGODB_URI` or `REDIS_URL` is not configured correctly, causing the model service chain to fail to resolve internal interface addresses.
- Symptom: Uploading documents such as benefit application forms and work injury identification materials fails, but the template import function works normally. Cause: `FILE_TOKEN_KEY` or `STORAGE_S3_ENDPOINT` is not set correctly, and access permissions for the internal network storage node are not enabled.
- Symptom: The index model channel configuration entry cannot be found. Cause: The corresponding plugin switch was not enabled during deployment, or the associated configuration for the basic data source was not completed.

## How to confirm configuration is complete
- Run a database connection test to verify that the connection pool configured via `DB_MAX_LINK` can normally pull payment period and work injury identification data from the social insurance system.
- Upload a test benefit application form document, and check that the access address returned by the storage node can normally download the file.
- Start the scheduled synchronization task, and check the data update log to confirm that daily personal benefit records and insured status data can be synchronized normally.
- Call the model service interface to confirm that the `/model/getProviders` interface can normally return a list of available model channels.
