# Business Process Guidance for Elderly Care Service Institution Supervision: HTTP Interfaces and External Systems

## What this category of data looks like
Typically, business data for elderly care service institution supervision comes from four sources: elderly care service information platforms, civil affairs statistics systems, fire safety inspection records, and institution operation ledgers. The update frequency is monthly.
Commonly involved documents include filing materials, operation subsidy applications, service quality inspection forms, safety hazard rectification ledgers, and elderly admission files. Most data consists of structured fields, including core fields such as institution filing number, bed count, rectification deadline, and subsidy application information. Some documents include unstructured attachments such as scanned files.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
The monthly update frequency means interface call frequency must be kept low, to avoid triggering rate limiting rules of source systems.
Data from multiple sources requires integration with multiple heterogeneous interfaces. Authentication rules vary across different interfaces, so the `Authorization` parameter must be configured appropriately.
Documents include both structured and unstructured content, so interfaces must support both field parsing and attachment upload.
The accuracy of supervision data is directly linked to subsidy distribution and safety rectification. Interface calls must include failure retry and data verification capabilities, to prevent supervision process interruptions caused by single call exceptions.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `Authorization` | Institution-specific Bearer token | Standard authentication requirement for integrating with civil affairs systems and fire safety inspection interfaces |
| `variables` | Structured variable groups grouped by filing number | Matches core associated fields of elderly care supervision data, adapts to the need for binding multiple variables to a knowledge base |
| `responseData` | Parsing rule to extract status, data, hiddenDanger fields | Unifies data formats for integrating with multi-source interfaces, extracts core supervision information such as safety hazards |
| Interface timeout period | 600 seconds | Adapts to response delays of monthly batch data interfaces, prevents single call failures |
| Retry count | 3 times | Prevents duplicate submission of supervision data, while covering temporary network fluctuations |
| Knowledge base binding rule | Match the corresponding knowledge base by the filing number in `variables` | Resolves workflow rearrangement issues where multiple variables correspond to a single knowledge base |

## Three common mistakes
- Scenario: After an HTTP request returns multiple variables, knowledge base matching becomes chaotic, and data for some institutions is bound to the wrong knowledge base. Cause: No association is made using the filing number field in `variables`, and all variables are directly bound to a single knowledge base.
- Scenario: The interface call returns a 504 timeout error, and batch data synchronization fails. Cause: The interface timeout period was not adjusted, and the default short timeout configuration of FastGPT v4.17.0 was used, which cannot adapt to the transmission delay of monthly batch data.
- Scenario: After deploying FastGPT via Docker, connection to the internal MySQL database fails, and elderly care institution operation data cannot be synchronized. Cause: The database connection port and account password were not configured correctly, and the database port inside the container was not mapped.

## How to confirm the configuration is correct
- Initiate a test call for a single institution’s data, and check whether `responseData` correctly extracts core fields such as the filing number and bed count.
- Verify that the filing numbers in `variables` correspond one-to-one with the entries in the bound knowledge base, with no matching anomalies.
- Simulate a network fluctuation scenario to trigger an interface timeout, and confirm that the system automatically executes retry actions, with the retry count matching the configured requirements.
- Check the interface authentication logs for error messages indicating missing `Authorization` parameters or authentication failures.
