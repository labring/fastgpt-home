# Business Process Guidance for Internal Control Evaluation, Audit and Rectification: HTTP Interfaces and External Systems

## What this category of data looks like
The data for this category primarily comes from enterprise internal control systems, ERP, financial sharing systems, audit management systems, and procurement contract project systems. Its update frequency is annual. Commonly involved documents include internal control self-assessment reports, audit notices, audit working papers, issue lists, rectification ledgers, and rectification closure certificates. Most data fields include business sample identifiers, issue descriptions, rectification statuses, closure certificate links, and similar items. There are no unified standardized fields, so extraction must follow the native field structure of the connected systems.

## Constraints on HTTP Interfaces and External Systems
Data sources for this category are scattered, requiring connection to multiple external business systems. HTTP interface call frequency must align with the annual update rhythm to avoid occupying system resources with high-frequency calls. Daily document formats vary, and interface return structures differ significantly. Flexible field mapping rules must be configured via `responseData` to adapt to the return formats of different systems. Data fields have no unified standard, so dynamic field mapping parameters must be passed via `variables` to adapt to the native fields of each connected system. The data update cycle is fixed, so interface calls must match the annual update nodes to reduce invalid requests. Additionally, interface exceptions must trigger alerts to avoid impacting audit and rectification processes.

## How to Configure Settings
The following configuration examples are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {Enterprise Internal API Key}` | Completes identity verification when connecting to internal enterprise systems, preventing unauthorized access |
| `variables` | `{ "systemType": "Internal Control System", "updateCycle": "Annual" }` | Passes parameters for connected system type and update cycle to adapt to dynamic field mapping logic |
| `responseData` | Map to native fields of the connected system, retain issue ID and rectification status fields | Extracts core business fields from the audit and rectification process to ensure accuracy of subsequent process guidance |
| Interface timeout period | `300–600 seconds` | Reserves sufficient response time when connecting to multiple enterprise systems, avoiding timeouts due to large data volumes |
| Retry count | `2–3 times` | Adapts to occasional network fluctuations in enterprise systems, ensuring interface call success rate |
| Single data pull limit | `First 500 entries` | Adapts to the paging return rules of enterprise systems, avoiding excessive single data pulls |
| Retry interval | `60 seconds` | Adapts to the response rhythm of enterprise systems, preventing resource occupation from frequent retries |

## Three Common Configuration Errors
- Phenomenon: Interface calls return HTML format content. Cause: The parameter to skip self-signed certificate verification is not configured, causing certificate verification failure and returning an error page.
- Phenomenon: Business data fields returned by the interface are empty. Cause: Dynamic field mapping rules are not configured via `variables`, making it impossible to adapt to the native field structure of the connected system.
- Phenomenon: Duplicate data appears when calling interfaces in a loop. Cause: Calls are not triggered according to the annual update cycle, leading to repeated pulling of processed audit and rectification data.

## How to Verify a Successful Configuration
- Execute a curl command to call the configured interface, check if the returned JSON format includes the preset core business fields.
- Simulate the return structures of different connected systems to verify whether the `responseData` field mapping rules take effect.
- View interface call logs to confirm whether timeout and retry configurations trigger corresponding logic in exception scenarios.
- Check interface call frequency to confirm it matches the annual data update cycle, with no high-frequency invalid calls.

The values provided are common starting points and should be evaluated against the reader’s own samples.
