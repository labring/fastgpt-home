# Business Process Guidance for Medical Insurance Expense Settlement Audit: HTTP Interfaces and External Systems

## What this category's data looks like
Data for this category originates from the national medical insurance information platform, hospital HIS systems, medical insurance interfaces, medical insurance catalogs and coding libraries, and cross-regional medical settlement platforms. The update frequency is daily.
Daily processed documents include medical insurance settlement lists, expense details, medical record homepages, prescriptions, rejection lists, and settlement reconciliation statements. Fields cover diagnosis and treatment project codes, drug and consumable codes, expense amounts, settlement order numbers, insured person identity identifiers, and additional relevant fields. Units include yuan, dates, standard coding numbers, and similar units.

## Constraints on HTTP Interfaces and External Systems
The diversity of data sources requires adaptation to multiple external interface format specifications. The daily update frequency requires scheduled pull tasks to cover all same-day settlement data. Business requirements for multi-field coding verification mandate that interface parameters carry standardized diagnosis and treatment project and drug/consumable codes. The scale of single or bulk settlement processing must match the medical insurance platform’s interface rate limiting rules to avoid triggering call restrictions. Errors may lead to fund disputes or delayed payment returns, so interface calls must include exception retry and complete log retention configurations.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer ${external_token}` | Complies with identity verification requirements for medical insurance external interfaces, prevents unauthorized access |
| `variables` | `{"batch_size": 150, "settle_date": "2024-05-20"}` | Adapts to daily update data pull requirements for bulk settlement audits, controls single request scale |
| `responseData` | `$.data.list[*]` | Matches the standard data structure returned by most medical insurance interfaces, extracts valid settlement details |
| Request timeout | `30-60 seconds` | Adapts to interface response load fluctuations on the medical insurance platform, reserves sufficient processing time |
| Bulk request limit | `100-200 items per request` | Complies with interface call rate limiting specifications of the medical insurance platform, avoids triggering interception |
| Variable injection rule | Dynamically inject based on business parameters | Adapts to dynamic parameter requirements for different settlement batches, supports parameter differentiation for bulk tasks |

## Three Common Configuration Errors
- Empty interface return fields prevent extraction of valid settlement details. This occurs when the `responseData` parsing path is misconfigured, making target data unextractable from interface results.
- Requests return a 401 Unauthorized error. This happens when dynamic external interface tokens are not injected via `variables`, and fixed expired identity credentials are used.
- Duplicate Bearer tokens appear in request headers. This occurs when automatic Bearer supplement configuration remains enabled, causing manually configured `Authorization` headers to conflict with automatically added tokens, leading to identity verification failure.

## How to Verify Successful Configuration
- In FastGPT v4.17.0, call the test interface and confirm the returned `responseData` contains business fields such as settlement details and expense amounts.
- Trigger a bulk request task and check if the `variables` parameters in the interface call logs match the preset business parameters.
- Verify the `Authorization` header format complies with external interface identity verification requirements, with no duplicate tokens or formatting errors.
- Simulate an interface timeout scenario and confirm the system triggers the preset retry mechanism and retains complete call logs.
