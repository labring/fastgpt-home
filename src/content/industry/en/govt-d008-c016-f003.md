# Business Process Guidance for Medical Insurance Expense Settlement Audit: Multi-turn Dialogue and Prompt Engineering

## What This Category of Data Looks Like
This category of data originates from the national medical security information platform, hospital HIS and medical insurance interfaces, medical insurance catalog and coding library, and cross-regional medical treatment settlement platform, with a daily update frequency. Documents processed daily include medical insurance settlement lists, expense details, medical record homepages, prescriptions, rejection lists, and settlement statements. Data fields cover diagnosis and treatment item codes, pharmaceutical and consumable codes, expense amounts, insured person identity identifiers, treatment institution information, and more. The length of a single document varies with the number of settlement transactions. The volume of data processed in a single batch scenario fluctuates significantly.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
The data sources for this category are scattered. Document types are diverse. Updates follow a fixed daily schedule. These factors create multiple constraints for the multi-turn dialogue and prompt engineering phase.

Use multi-turn dialogue to gradually verify the consistency of diagnosis and treatment items and pharmaceutical/consumable codes from different sources. This avoids fund risks caused by matching errors.
Configure logic in prompts to call the daily updated medical insurance catalog library in real time. This ensures the timeliness of code matching.
Guide users to submit materials in the order of settlement lists, expense details, and rejection lists. This adapts to the field verification logic of different documents.
For batch processing scenarios, split tasks through multi-turn dialogue. This prevents exceeding the context carrying limit in a single processing, which can cause format or index errors.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique identifier of the current settlement audit task | Associate multi-turn dialogue context to ensure session isolation between different audit tasks and avoid data confusion |
| `messages` | Concatenate in the order of "system prompt + user input + intermediate verification results" | Adapt to the multi-step verification logic of medical insurance audit, and fully retain each round of code matching and expense verification records |
| `variables` | Inject the daily snapshot of the medical insurance catalog coding library | Match the daily update frequency of business data, ensuring that the audit uses the latest medical insurance coding and catalog rules |
| Context window size | 8000–12000 token | Accommodate the complete content of single or batch settlement-related documents, avoiding truncation of key codes and expense fields |
| Single conversation processing limit | 50 settlement details per time | Adapt to the carrying capacity of system interfaces, avoiding abnormal errors caused by excessive data volume |
| Error retry count | 3 times | Handle scenarios of interface call or code matching failures, reducing the probability of manual intervention |

## Three Common Misconfigurations
- Phenomenon: When executing a batch settlement audit task, the interface shows the task completed normally but returns the error `The value of "offset" is out of range`. Cause: The batch settlement sheets are not split by batch, and the incoming context length exceeds the system's carrying limit, resulting in an index offset error.
- Phenomenon: When submitting multiple files for audit, only some documents are recognized and processed by the system. Cause: The content identifiers of multiple files are not nested in the required format in the `messages` parameter, causing the system to fail to fully read all submitted settlement-related materials.
- Phenomenon: Dependency missing prompts appear during the dialogue process, causing the audit process to interrupt. Cause: A fixed operating environment is not configured before task startup, and the dependency packages required for medical insurance catalog matching are missing after the dialogue virtual machine is reinitialized each time.

## How to Verify Successful Configuration
- View the session context record to confirm that `chatId` is bound to the unique identifier of the current settlement audit task, and there is no cross-task context confusion.
- Test submitting a single settlement list, check whether the `messages` parameter is concatenated in the order of system prompt, user input, and intermediate verification results, with no missing key fields.
- Trigger a batch audit task, verify that the variables call real-time access to the daily medical insurance catalog data, ensuring that the latest rules are used for code matching.
- Simulate a dependency missing scenario, confirm that the required dependency packages are loaded when the task starts, and no interrupt errors occur.
