# Business Process Guidance for Medical Institution Supervision and Public Health Inspection: Deployment and Upgrade

## What the data for this category looks like
The entities served by this category include health supervision agencies, medical administration divisions of health commissions, medical institutions, and disease control collaboration departments. Data mainly comes from health supervision information systems, medical institution electronic registration systems, complaint reporting platforms, and law enforcement inspection records. The data update frequency is monthly. Daily processed documents include supervision inspection forms, medical institution practice licenses, rectification notices, supervision opinions, and penalty case files. Document fields cover institution qualification information, on-site inspection content, rectification requirements and feedback, penalty basis, and more. There is no unified standardized field template, and adaptation is required for document structures from different sources.

## What constraints these characteristics impose on deployment and upgrade
Data sources involve multiple government affairs systems. During deployment, adaptation to the interface permissions and data formats of different systems is required to avoid cross-system data synchronization exceptions. The monthly updated batch data volume is large. During upgrade, sufficient database connection resources must be reserved to prevent blocking during synchronization. Government affairs documents have high compliance requirements. During deployment, a file storage path that complies with government data storage specifications must be configured to ensure sensitive data is not leaked. There are large field differences across different documents. During knowledge base upgrade, document parsing rules must be adjusted to avoid field matching errors affecting the accuracy of process guidance.

## How to set the configurations
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://[health system database username]:[password]@[database host]:27017/fastgpt?authSource=admin` | Connecting to the health system database requires account and password verification, which complies with the access permission requirements for government data |
| `REDIS_URL` | `redis://:[cache service password]@[cache host]:6379/0` | Used to cache the parsing results of government documents and process guidance sessions, ensuring response speed for batch data processing |
| `DB_MAX_LINK` | `100–200 connections` | Adapts to the request volume of monthly batch data synchronization, avoiding database connection exhaustion |
| `STORAGE_S3_ENDPOINT` | Endpoint address pointing to the government cloud storage service | Stores sensitive government documents such as supervision inspection forms and penalty case files, complying with data compliance requirements |
| `FILE_TOKEN_KEY` | Custom 32-character random string | Generates file access tokens to restrict unauthorized users from accessing sensitive government documents |
| `ROOT_KEY` | Authorization key matching the front-end deployment domain name | Verifies the legitimacy of interface requests, preventing unauthorized system access |

## Three common mistakes
- After local deployment, adding a model test returns a 403 status code with no response body. The cause is that the `ROOT_KEY` parameter is not configured correctly, or the front-end domain name does not match the back-end authorization rules.
- Dependency loading failure errors occur when deploying on Arm64 architecture servers. The cause is that a container image adapted for the Arm64 architecture is not used, or corresponding architecture runtime parameters are not configured.
- Docker-deployed MongoDB cannot complete the connection, prompting an account and password verification failure. The cause is that the database account and password are not correctly configured in `MONGODB_URI`, or the MongoDB container does not have the authentication function enabled.

## How to confirm the configurations are set correctly
- Run the built-in database connectivity detection tool to verify that the connection parameters configured in `MONGODB_URI` and `REDIS_URL` can connect normally.
- Upload a supervision inspection form document to check that the storage service configured in `STORAGE_S3_ENDPOINT` can complete upload and download operations normally.
- Call the file token generation interface to verify that the token generated using `FILE_TOKEN_KEY` can normally authorize access to uploaded documents.
- Check the system background logs to confirm that interface requests are not intercepted by the authorization rules configured in `ROOT_KEY`.

The values provided here are common starting points and should be measured against the reader's own samples.
