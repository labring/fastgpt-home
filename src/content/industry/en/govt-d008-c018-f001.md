# Business Process Guidance for Social Insurance Enrollment Registration and Premium Verification: HTTP Interfaces and External Systems

This document is compatible with FastGPT v4.17.0.

## What this category of data looks like
Data for this category originates from social insurance management systems, tax social insurance premium collection systems, market entity registration information, and shared public security and civil affairs data. Its update frequency is daily. Daily interactive documents include enrollment registration forms, payment base declaration forms, personnel change forms, social insurance premium verification forms, and personal benefit records. Data fields cover personnel identity identifiers, labor relationship association information, payment base parameters, unit registration information, personnel change status, and more. Most formats are structured forms or batch-imported table files.

## What constraints do these characteristics impose on HTTP interfaces and external systems
The multi-source data characteristics of this category require HTTP interfaces to support authentication protocols from different external systems. This prevents data synchronization failures caused by system differences. The daily update frequency means interface call cycles must align with business synchronization rhythms. Cycles should not be too frequent or delayed. Structured business documents require interface request bodies to strictly match preset fields. Adding unnecessary additional parameters will trigger data validation failures. Core business reconciliation requirements also demand interfaces support two-way data interaction. This enables two-way verification and return transmission of enrollment registration and premium data.

## How to configure settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {API key assigned by the social insurance system}` | Complies with general API authentication specifications for human resources and social security systems, ensures legitimacy of interface calls |
| `variables` | `{"requiredFields": ["personnel identity identifier", "payment base", "unified social credit code of the unit"]}` | Matches the required field requirements of business documents in this category, simplifies dynamic parameter verification logic |
| `responseData` | `Return only structured business data that has passed validation` | Filters invalid data, reduces redundant processing in subsequent reconciliation links, and improves business processing efficiency |
| Interface timeout setting | `600 seconds` | Matches the average response duration of multi-source system data interactions, prevents data synchronization interruptions from timeouts |
| Retry count setting | `3 times` | Addresses temporary network fluctuations, ensures data synchronization success rate, and meets the stability requirements of social insurance business |

## Three common misconfigurations
- Calling the interface returns empty content, and no expected enrollment or premium data is obtained. Cause: The validation rules for `responseData` are not configured correctly. This causes all fields that do not meet business requirements to be filtered out, and no valid return content is retained.
- Interface calls frequently trigger timeout errors, with a 504 status code. Cause: The interface timeout setting duration is too short, and does not match the average response delay of multi-source social insurance systems.
- Interface requests are rejected by external systems, returning a 401 authentication failure prompt. Cause: The `Authorization` parameter does not use the correct Bearer format, or the key configuration is incorrect.

## How to confirm correct configuration
- Call the preset test interface, pass test data that conforms to the business document format, and check whether the returned content includes expected business fields.
- Simulate a single data synchronization process, verify the field matching degree between the interface request body and response body, and confirm that the parameter configuration is correct.
- Verify the authentication parameter configuration, and confirm that no 401 authentication failure prompt is returned by calling the interface.
- Simulate a temporary network interruption scenario, check whether the interface triggers retries according to the configuration, and confirm that the stability configuration takes effect.

The values provided are common starting points and should be measured against the reader's own samples.
