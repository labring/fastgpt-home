# Business Process Guidance for Insurance Registration and Premium Verification: Workflow Orchestration

## What data for this category includes
Daily documents for this category include insurance registration forms, premium base declaration forms, personnel change forms, social insurance premium verification notices, and personal benefit records. These documents contain fields such as personnel identity identifiers, registration status, premium base, and personnel change flags.
Multiple systems provide data for this category: social insurance handling systems, tax social insurance premium collection systems, market entity registration information, and public security and civil affairs data sharing. The platform updates this data daily.
Data links basic social insurance benefit information for insured units and individuals. It supports information verification and circulation across the full process of insurance registration and premium verification.

## Constraints on workflow orchestration from these data characteristics
Multiple data sources and daily updates require workflows to connect to multiple system interfaces to fetch real-time data, and avoid using expired information.
Multiple associated fields in daily documents require workflows to strictly validate field formats and cross-system matching rules, to prevent errors in personnel identity or labor relationship verification.
Close connections between process nodes for insurance registration and premium verification require workflows to follow business sequence, triggering links such as personnel changes, base declaration, and tax reconciliation in order. Any error in a link must immediately block the workflow.
Direct linkage of data to personal benefits requires workflows to retain complete operation logs for subsequent traceability.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Bind the insured unit's unified social credit code and personnel ID number as fixed variables | Serve as core identifiers for cross-system data matching, to avoid confusion between different business data |
| `nodeId` | Assign a unique `nodeId` to multiple knowledge base nodes, and bind corresponding knowledge bases by business link | Differentiate knowledge base data for different business links, enable accurate variable reference, and comply with FastGPT v4.17.0 node call rules |
| Single call limit | Top 5 entries | Control the number of data entries returned per link, to avoid excessive workflow load |
| Timeout threshold | 600 seconds | Adapt to the average response duration of multi-system interface calls, to prevent unexpected workflow interruption |
| Error branch configuration | Set based on actual testing | Configure corresponding processing nodes for scenarios such as identity verification failure and empty data |

## Three Common Configuration Mistakes
- Phenomenon: When outputting multiple variables after an HTTP request node, errors occur or returned results do not match expectations after referencing variables and binding to a knowledge base. Cause: Unique `nodeId` is not assigned to different knowledge base nodes, leading to confusion of knowledge base data from different nodes during variable reference.
- Phenomenon: When configuring variable references, the knowledge base ID is directly written instead of binding business identifier fields through `variables`, leading to returned knowledge base data that does not match the current business being processed. Cause: Core business identifiers are not used as variable matching basis, only hard-coded knowledge base IDs are used, which cannot adapt to business scenarios with multiple units or multiple personnel.
- Phenomenon: When judging whether a knowledge base returns an empty result, only a single judge is used, and scenarios such as interface timeout and data format exception are not covered, leading to no blocking being triggered after a workflow exception. Cause: Multi-branch error handling is not configured, only empty data scenarios are covered, and other abnormal conditions cannot be addressed.

## How to Confirm Proper Configuration
- Call test insured unit identifiers and personnel identity information, check whether the workflow triggers corresponding nodes according to business sequence.
- View workflow logs, confirm that fields bound to `variables` correctly match data returned by multiple systems.
- Trigger abnormal scenarios such as entering invalid identity information, check whether corresponding processing is executed according to configured error branches.
- Verify `nodeId` values of multiple knowledge base nodes, confirm that variable references for each node correspond one-to-one with business links.
