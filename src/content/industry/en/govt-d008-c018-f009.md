# Business Process Guidance for Social Insurance Registration and Payment Verification: Model Access and Configuration
This document is compatible with FastGPT v4.17.0.

## What this category of data looks like
Data for this category comes from social insurance management systems, tax social insurance premium collection systems, market entity registration information, and shared public security and civil affairs data.
Daily business documents include registration forms, payment base declaration forms, staff change forms, social insurance premium verification forms, and personal benefit records.
Fields cover personal identity identifiers, labor relationship information, payment base, declaring unit information, verified amounts, and more.
The update frequency is daily.
Data is generated across multiple departmental systems, with minor differences in format and field specifications. Each individual document contains a relatively large number of fields.

## Constraints on model access and configuration
Access to cross-source data requires models to support verification and matching of data from multiple systems.
Daily high-frequency updated data requires configurations to support stable real-time calls.
Splicing multiple types of business documents requires setting a reasonable upper limit for context length, to avoid exceeding the model's carrying capacity.
Documents with a large number of fields require models to have accurate field extraction capabilities. A fault-tolerance mechanism must be configured to respond to minor differences in data formats.
Errors directly affect personal benefits and payment compliance. Model output must have high accuracy and traceability.

## Configuration Settings
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 characters | Adapts to the spliced length of multiple registration and payment verification documents, avoiding call failures caused by context overflow |
| `maxTokens` | 4000–6000 | Limits the number of tokens per round of response, adapting to the output length of payment verification results and staff identity verification conclusions |
| `temperature` | 0.2–0.4 | Reduces the randomness of model output, ensuring the accuracy of core business judgments such as identity verification and data reconciliation |
| `AIPROXY_API_TOKEN` | Exclusive call key issued by the corresponding model service provider | Completes model identity authentication, ensuring the legitimacy and compliance of the call link |
| `toolChoice` | auto | Allows the model to automatically determine whether to call tools to complete cross-system data verification and matching |
| `quoteMaxToken` | 1500 characters | Limits the length of a single referenced document, filters redundant information, and focuses on core business fields |

## Three Common Misconfigurations
- Phenomenon: The knowledge base can retrieve business data, but the model outputs nothing. Cause: `maxContext` is not set reasonably. The spliced multiple retrieved documents exceed the upper limit of context length and cannot be fully transmitted to the model.
- Phenomenon: A call failure prompt appears when rearranging models in offline configuration. Cause: `AIPROXY_API_ENDPOINT` is not filled correctly, or the permission configuration of the corresponding model's call key is incorrect.
- Phenomenon: Custom models cannot be accessed directly, and forced reliance on OneAPI services is required. Cause: The OneAPI forwarding switch is not turned off in the model configuration. The system forwards all custom model requests to the transit link by default.

## How to Verify Successful Configuration
- Enter the FastGPT model configuration page, check that the content of `AIPROXY_API_TOKEN` and `AIPROXY_API_ENDPOINT` matches the official information provided by the model service provider.
- Upload a typical registration form and payment verification document, initiate a test call, and check whether the model can correctly extract core business fields such as staff identity and payment base.
- Simulate the scenario of multi-document splicing, adjust the `maxContext` parameter, and confirm that the system will provide a clear error prompt when context overflow occurs.
- Trigger a test request for cross-system data verification, and confirm that the model can automatically call tools to complete data verification and reconciliation operations.

The values provided are common starting points and should be evaluated against the reader's own samples.
