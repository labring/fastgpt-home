# Business Process Guidance for Random Inspection and Public Disclosure Supervision Checks: Knowledge Base Retrieval and Recall

## What This Type of Data Includes
This type of data primarily comes from the random inspection and public disclosure supervision platform, enterprise credit information publicity system, industry supervision system, and law enforcement officer directory. It is updated monthly. Daily documents include random inspection plans, inspection target lists, inspection item checklists, on-site inspection records, rectification notices, and random inspection result announcements. It covers two format categories: structured lists and unstructured records. Fields include supervision target identifiers, inspection item entries, law enforcement officer information, inspection result status, and more. There is no unified fixed single-document field standard.

## What Constraints Do These Characteristics Impose on Knowledge Base Retrieval and Recall
The monthly update frequency requires the knowledge base to support incremental synchronization every 30 days, to avoid resource consumption from full reindexing. The structural differences across multiple document types require the retrieval mechanism to balance structured field matching and unstructured text semantic understanding. Scattered data sources and the need to restrict access to supervision-specific data require retrieval to support precise recall of specified datasets, to avoid interference from irrelevant data. Additionally, the supervision process has high accuracy requirements for inspection result announcements. The matching precision of recalled results directly affects the compliance of subsequent law enforcement workflows, so low-precision results must be strictly excluded.

## Configuration Settings
The following configurations are based on the functional logic of FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Matches the accuracy requirements for supervision target information and inspection items, to avoid low-precision irrelevant results |
| `limit` | Top 8–12 results | Adapts to the document call volume for a single inspection task, balancing recall completeness and model context capacity |
| `searchMode` | Hybrid retrieval | Balances field matching for structured list documents and semantic retrieval for unstructured record documents |
| `usingReRank` | Enabled | Performs secondary ranking on recalled results, corrects deviations from single vector matching, and ensures high-priority inspection items appear first |
| `datasetSearchUsingExtensionQuery` | Enabled | Expands the range of retrieval terms, covers synonyms of inspection items and common expressions used in law enforcement scenarios, and improves recall coverage |
| `collectionIds` | Bind the corresponding supervision-specific dataset | Restricts the retrieval scope to documents related to random inspection and public disclosure supervision, to avoid interference from non-supervision data |

## Three Common Configuration Mistakes
- When inspection target list files are uploaded, the `failed to create post presigned url` error occurs. This happens when cross-origin resource sharing rules are not properly configured after migrating S3 storage, which causes failure to generate pre-signed URLs.
- Retrieval results fail to match the specified inspection item checklist documents. This occurs when the dedicated dataset is not bound via `collectionIds`, so the retrieval scope includes non-supervision related documents.
- Too many recalled results in a single request cause context overflow. This happens when a reasonable `limit` parameter is not set, and the default number of recalled results exceeds the model's context capacity limit.

## How to Verify Correct Configuration
- A test random inspection plan document is uploaded, and successful upload and parsing are confirmed, with no `failed to create post presigned url` errors.
- The keyword "2024 Q2 market supervision random inspection plan" is entered, and retrieval results are confirmed to only include relevant documents within the bound dataset.
- The number of returned retrieval results is checked, and confirmed to match the 8–12 result limit set in the configuration.
- Retrieval is triggered, result ranking is checked, high-priority inspection item entries are confirmed to appear at the top of results, and the `usingReRank` function is verified to be active.

The values listed above are common starting points. Always validate against specific samples and use cases relevant to the actual deployment.
