# Workflow Guidance for Centralized Treasury Payment and Reimbursement Audit: HTTP Interfaces and External Systems

## What this category of data looks like
Data for this category comes from centralized treasury payment systems, unified budget management systems, electronic invoice platforms, and contract management systems. It is updated daily. Daily processed documents include payment applications, fund use plans, invoices, contracts, acceptance records, reimbursement approval forms, and payment vouchers. Data fields include budget indicators, economic classification, ticket information, contract terms, acceptance results, and more. There is no unified universal format. The structure must match the native field layouts of each system. A single transaction is associated with multiple business documents from different sources.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Multiple data sources require interfaces to support integration with multiple external systems. Interfaces must be compatible with different authentication methods and field mapping rules. The daily update frequency means interface call frequency must align with the daily business processing rhythm. Call intervals should not be set too short. The feature of a single transaction being associated with multiple documents requires interfaces to support associated queries across multiple systems. This reduces the workload of manual cross-system verification. Errors can lead to capital risks. Interfaces must be configured with idempotency and failure retry mechanisms to avoid duplicate payments or data loss.

## How to configure settings
The following configurations are adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {external system API key}` | Complies with standard authentication specifications for centralized treasury payment systems, electronic invoice platforms, and similar systems. Ensures secure data access |
| `variables` | `["budget indicator verification", "ticket compliance check", "payment process guidance"]` | Covers core business processing links for this category. Matches key steps in daily audits |
| `responseData` | `First 6 associated business fields` | Matches the feature of a single transaction in this category being associated with multiple documents. Reduces manual data completion workload |
| Interface call timeout | `300 seconds` | Cross-financial system interface responses have delays. Prevents business process interruptions due to timeouts |
| Retry count | `2 times` | Covers temporary network fluctuations. Avoids duplicate trigger of payment or audit operations |

## Three common configuration mistakes
- Symptom: The `responseData` field returned after calling the interface contains duplicate ticket information. Cause: No field filtering rules are configured. Redundant data returned by external systems is returned directly.
- Symptom: Interface calls time out, returning status code 504. Cause: The set timeout period is shorter than the average response time of cross-financial systems. It does not match the interaction characteristics of data in this category.
- Symptom: The AI's process guidance content overlaps with previous audit results. Cause: Context variables are not cleared. The `variables` field carries historical session data. This does not meet the independent processing requirements for a single business transaction.

## How to confirm the configuration is complete
The following verification actions are adapted for FastGPT v4.17.0.
- Call the test interface. Check whether the fields returned in `responseData` include the necessary information for core business documents in this category. Adjust field matching rules until all required content is covered.
- Simulate a cross-system call scenario. Verify whether the interface call timeout period matches the actual response duration. Adjust the value until frequent timeout errors stop occurring.
- Initiate multiple test sessions. Confirm that the `variables` field does not carry historical session data. The context for each call only includes parameters related to the current business transaction.
- Check whether the format of the authentication parameter `Authorization` meets the requirements of external systems. Verify that calls can normally retrieve data from external systems.
