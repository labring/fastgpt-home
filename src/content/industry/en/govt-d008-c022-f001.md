# Business Process Guidance for Land Use Rights, Mining Rights, and State-Owned Property Rights Transactions: HTTP Interfaces and External Systems
This documentation is developed for FastGPT v4.17.0.

## What Data for This Category Looks Like
Data for this category typically comes from the national public resource trading platform, natural resource trading systems, property right exchange systems, and state-owned asset supervision systems. Updates occur on a daily basis.
Commonly encountered documents include transfer announcements, trading guidelines, bid application submissions, margin payment vouchers, transaction confirmation certificates, listing result announcements, and property right transfer descriptions. Most documents focus on core content such as trading object ownership, transaction processes, and fund vouchers.
Common fields include object number, ownership status, transaction type, and application deadline. There is no unified mandatory format. Data must match the native structure output by each connected system.

## Constraints Imposed by These Characteristics on HTTP Interfaces and External Systems
Decentralized data sources and daily updates require interfaces to support batch pulling and incremental synchronization of data from multiple systems. This prevents full-volume data pulls from consuming excessive internal network resources.
Diverse document types and inconsistent structures require interfaces to support parsing and adaptation of multiple data formats. Single field mapping rules cannot be relied upon.
Transaction-related data involves ownership and fund security. Interfaces must be configured with strict permission verification mechanisms to prevent unauthorized access or data leaks.
Daily update frequency requires interface call frequency to match the business rhythm. This avoids frequent calls that exceed the load limits of each trading system.
Data synchronization errors may lead to ownership verification mistakes, invalid transactions, and other consequences. Interfaces must include verification logic to ensure data accuracy.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Use a fixed Bearer token format, with the value being the exclusive key assigned by the system | Matches the general authentication specifications for state-owned asset and public resource trading systems, prevents unauthorized interface calls |
| `variables` | Configure as `["Object ID", "Transaction Type", "Ownership Status", "Margin Amount"]` | Covers the core business fields for this category, enabling accurate matching of user-inquired transaction links during process guidance |
| `responseData` | Limit returned results to the first 8 matching documents | Avoids excessive returned documents causing context overflow, adapts to the single-call volume of public resource trading documents |
| Timeout period | 60 seconds | Adapts to the average response time of multi-system data pulling, avoids interface call failures caused by internal network delays |
| Log storage path | Specified internal network directory, retain logs for 7 days | Facilitates troubleshooting of interface errors and data synchronization exceptions, complies with security management requirements for internal network deployments |

## Three Common Configuration Mistakes
- A 401 status code is returned after calling the interface, and no business documents can be obtained. The cause is incorrect configuration of the `Authorization` parameter, with no authentication key required by the system attached.
- File upload fails in the chat window when accessing via nginx reverse proxy in an internal network deployment environment. The cause is failure to adjust the file upload size limit in the nginx configuration, which cannot meet the transmission requirements for large files such as margin vouchers.
- Empty fields are returned when calling the interface to add content to the knowledge base. The cause is failure to configure the corresponding business fields in `variables`, preventing the system from extracting valid transaction information.

## How to Verify Successful Configuration
- Run a curl command to call the configured interface, check that the `responseData` in the returned results includes the expected trading document fields.
- View system operation logs, confirm that the `Authorization` parameter of interface call requests is correctly parsed, with no authentication failure records.
- Upload a margin voucher file, check that the voucher number and amount information are successfully extracted in the knowledge base.
- Simulate a user inquiry about land use rights transfer procedures, confirm that the returned guidance content matches the `variables` fields currently configured.
