# Business Process Guidance for Land Use Rights, Mining Rights and State-owned Property Rights Transactions: Workflow Orchestration

## What this category of data looks like
Data for this category primarily comes from the national public resource trading platform, natural resource trading systems, property right exchange systems, and state-owned asset supervision systems. The update frequency is daily. Common business documents include transfer announcements, trading guidelines, bid application documents, margin payment vouchers, transaction confirmation notices, listing result announcements, and property right transfer descriptions. Typical data fields include subject ownership number, restriction conditions, margin amount, transaction price, and other information related to resource asset right transactions. There are clear differences between these fields and those of procurement projects.

## What constraints these characteristics impose on workflow orchestration
Multiple data sources require workflows to support cross-data source pull configuration, and independent node adaptation rules must be configured for interfaces of different systems. Daily update frequency requires workflows to include scheduled trigger logic for variable synchronization, to ensure downstream nodes use the latest data. Diverse business document types require workflows to include parsing nodes adapted to different document formats, to process transfer announcements, transaction confirmation notices and other content separately. Splitting of core time-consuming links requires separating ownership verification, listing bidding, material review and other steps into independent nodes, to facilitate separate adjustment and monitoring. Severe consequences of errors require configuring failure branches for each critical node, to automatically trigger a manual review process when exceptions occur.

## How to set configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| Global variable configuration | Bind daily synchronized trading data, with variable pool capacity not exceeding 1000 MB | Data update frequency is daily, and single-batch trading data volume is large, so variable storage limits must be controlled |
| Node ID mapping | Use `nodeId` to name according to trading links, for example `nodeId: "check_ownership"` | Workflows split into multiple links require clear node identifiers to facilitate troubleshooting and adjustment |
| Variable update trigger timing | Trigger after data pull is complete, with delay no more than 600 seconds | Must ensure latest trading data is synchronized to downstream nodes, to avoid using outdated information |
| Failure branch configuration | Trigger manual review nodes when a node returns an abnormal status | Errors in trading links have severe consequences, so timely intervention is required |
| Context call limit | Call the top 5 core business documents | Core business documents include transfer announcements, transaction confirmation notices, etc. Excessive calls will cause context overload |
| Global variable binding | Bind the output of the code running node to the `variables` global scope | Ensure downstream nodes such as AI chat can read verification results generated by code |

## Three Common Misconfigurations
- Phenomenon: After workflow execution, subsequent business nodes still read the initial value of `variables` and do not update to the latest trading data. Cause: No explicit variable synchronization trigger step is added after the variable update node, so variable changes are not passed to downstream nodes.
- Phenomenon: After importing workflow configuration, some nodes have empty configuration items and cannot start execution normally. Cause: The `nodeId` mapping rules of the current environment are not matched during import, causing node identifier conflicts that prevent configuration loading.
- Phenomenon: Results returned by the AI chat node do not include ownership verification content generated by the code running node. Cause: The output of the code running node is not correctly bound to the global `variables` scope, so the chat node cannot obtain the corresponding data.

## How to Verify Configurations Are Correct
- Manually trigger a data pull node, and check whether the latest trading documents and subject information are synchronized in `variables`.
- Simulate an abnormal node status, and check whether the preset failure branch and manual review process are triggered.
- Export and re-import the workflow configuration file, and check whether all node configuration items are fully retained.
- Run the business link including code running and AI chat, and check whether the chat node can obtain the verification results generated by the code.

The values given are common starting points and should be measured against the reader's own samples.
