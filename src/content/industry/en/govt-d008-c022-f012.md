# Business Process Guidance for Land Use Rights, Mining Rights, and State-Owned Property Rights Transactions: Deployment and Upgrade

## What Data for This Category Looks Like
This category of business data typically originates from the national public resource trading platform, natural resource trading systems, property right exchange systems, and state-owned assets supervision systems. The update frequency is daily. Daily processed documents include transfer announcements, trading notices, bid applications, margin vouchers, transaction confirmation letters, listing result announcements, and property right transfer descriptions. Data fields usually cover transaction subject ownership information, valuation parameters, margin amounts, bidding rules, and transaction confirmation content. Most units use common standard units for area, monetary value, and time.

## Constraints Imposed by These Characteristics During Deployment and Upgrade
The daily update frequency requires configuring stable incremental synchronization tasks during deployment, to avoid excessive system resource usage from full data pulls. Multi-source business data requires configuring multiple data source connection parameters to ensure compatibility when pulling data from different trading systems. Diverse business documents require pre-configuring corresponding parsing rules to ensure accurate extraction of core fields such as ownership and margin. Additionally, errors in transaction data can lead to ownership disputes or asset loss. As such, deployment and upgrade processes must include a data verification link and retain a historical data backup mechanism, to prevent data loss from disrupting subsequent transfer or ownership confirmation workflows.

## Three Common Misconfigurations
- After deploying the open-source version, startup fails with an error indicating that the commercial version link is not configured, and returns the `getPluginGroups 500` status code. This occurs because the open-source version does not include the proAPI-related directory, and basic connection parameters are not correctly configured, leading to plugin call failures.
- Cluster deployment plan is missing, leading to data inconsistency when multiple nodes synchronize transaction data. This occurs because Redis shared sessions and MongoDB sharding strategies are not configured, which cannot support high-concurrency transaction data pulling and synchronization.
- A startup prompt indicates that the MongoDB version is too low to use the MongoDB 5 image. This occurs because the MongoDB 4.4.29 image is not selected as required, and the connection configuration corresponding to `MONGODB_URI` is not correctly modified.

## How to Confirm Configurations Are Correct
- Run a local interface test by calling the `/api/system/config` interface, and check whether core configuration items such as `MONGODB_URI` and `REDIS_URL` are loaded correctly.
- Trigger an incremental synchronization task, and check whether there are records of successful data pulling in the logs, with no error prompts.
- Upload a trading notice document, and verify whether core fields such as subject ownership and margin amount are correctly extracted after parsing.
- Access the business guidance page, confirm that the domain configured for `FE_DOMAIN` is accessible normally, with no resource loading failure prompts.
