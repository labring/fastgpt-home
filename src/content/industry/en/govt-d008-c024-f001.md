# Business Process Guidance for Student Aid and Subsidy Review: HTTP APIs and External Systems

## What Data for This Category Looks Like
Core data for this category comes from the National Student Aid Management Information System, school student status systems, civil affairs subsistence allowance and extreme poverty assistance data, and fiscal payment systems. It daily processes documents including family economic hardship certification forms, aid application forms, scholarship and grant review forms, disbursement lists, public notice materials, and others. Data updates follow the semester schedule. Core fields include student identity identifiers, student status, family economic situation, bank card information, and aid amounts. The core business is subsidy qualification verification and fund disbursement, which requires connecting multiple systems for cross-departmental data verification. Errors may lead to incorrect or missed aid disbursements, student complaints, or audit issues.

## How These Characteristics Create Constraints for the "HTTP APIs and External Systems" Link
The data sources for this category are scattered, requiring integration with multiple external systems to obtain student status, subsistence assistance, fiscal and other information. Therefore, APIs must support multi-address configuration and multiple identity verification methods. Data updates follow the semester cycle, so API call frequency must align with the business cycle to avoid excessive calls that cause high system load. Core documents include fixed-format review materials and list data. API parameters must strictly correspond to business fields, otherwise verification will fail. Additionally, the consequences of business errors are severe, so APIs must have failure retry and exception log recording capabilities to ensure data processing reliability. ## How to Set Configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${API key assigned by the connected system}` | Implements identity verification with external aid and student status systems |
| `variables` | Includes student ID number, family economic status identifier, disbursement amount fields | Matches the transmission requirements of core business data for this category |
| `responseData` | Returns only verified student lists and exception status identifiers | Filters redundant data to improve API processing efficiency |
| Request timeout | `600 seconds` | Adapts to long-duration scenarios with multi-system joint verification |
| Request retry count | `2–3 times` | Addresses temporary network fluctuations or short-term system anomalies |
| Request body format | Select form-data or json based on business document type | Matches the receiving format requirements of external systems |

## Three Common Mistakes
- Symptom: API calls return uncaught exceptions, with logs showing parameter verification failures. Cause: The `variables` parameter in the configuration file does not correctly include required fields such as family economic hardship certification form and student ID number, causing the external system to fail to recognize the request content.
- Symptom: API requests have no response in the Safari browser, and the interface shows loading failure. Cause: Cross-domain parameters in the request header are not correctly configured, triggering the browser's same-origin policy interception.
- Symptom: After Docker deployment, accessing the page keeps spinning before failing. Cause: Container ports are not correctly mapped, or the external system address in the configuration file is not set to an accessible intranet or public network address.

## How to Confirm the Configuration Is Complete
- Call the test API, check whether the fields returned in `responseData` include student aid-related data required for the business.
- Simulate an abnormal request, verify whether the configured timeout and retry mechanisms are triggered, and confirm that exception logs are generated normally.
- Connect to an external system in a local test environment, verify that file parameters in form-data format can be transmitted correctly.
- Check whether the `Authorization` parameter in the configuration file matches the key assigned by the connected system, ensuring identity verification passes.
