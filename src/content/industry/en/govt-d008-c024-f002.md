# Business Process Guidance for Student Financial Aid and Subsidy Review: Vector Models and Indexing

## What This Category of Data Looks Like
Data for this category originates from the national student financial aid management information system, school student registration systems, civil affairs low-income and special hardship datasets, and fiscal payment systems.
Service entities include education bureau financial aid centers, school student affairs offices or financial aid teams, and fiscal departments.
Daily processed documents include family economic hardship certification forms, financial aid application forms, scholarship and grant review forms, disbursement lists, and public notification materials.
Fields cover student registration identifiers, family economic status, low-income/special hardship certification status, bank card information, review grades, and more.
Data is updated once per semester.

## Constraints for Vector Models and Indexing
Scattered data sources and per-semester updates require indexes to support regular full or incremental updates. This prevents cross-semester data from being included in current review workflows.
Documents include both structured and unstructured types. This requires hybrid retrieval logic that supports both field-level matching and vector semantic retrieval.
Some fields contain sensitive information. Sensitive data must be desensitized before indexing to prevent leakage of original private information.
Fields from multiple system sources have naming differences. Administrators must complete unified mapping in advance to avoid retrieval failures caused by field mismatches.
A single review batch involves multiple documents. Indexes must support long context concatenation and retrieval.

## Configuration Settings
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Matches the per-page content length of family economic hardship certification forms and financial aid application forms, to avoid semantic breaks within chunks |
| Overlap Length | 100–150 characters | Preserves cross-chunk context associations, ensuring semantic coherence for review process-related text |
| `defaultToken` | 4096 | Matches the context window of mainstream large models, to accommodate concatenated content from multiple review materials |
| `maxToken` | 8192 | Supports batch retrieval and context integration for full academic year financial aid materials |
| Similarity Threshold | 0.75–0.85, calibrated via actual testing | Distinguishes valid financial aid qualification matches from noise matches, adapting to semantic matching requirements for low-income and registration status |
| Single Search Limit | Top 10 results | Controls the number of returned search results, to avoid excessive non-critical information interfering with review judgments |

## Three Common Misconfigurations
- Phenomenon: Retrieval results include non-current semester financial aid application materials, leading to incorrect review judgments. Cause: Index update rules are not configured per semester cycle, and vector data from previous semesters is reused.
- Phenomenon: The system returns empty search results, unable to match student registration or low-income information. Cause: Unified mapping of fields from multiple system sources is not completed, leading to student identifier fields not being properly indexed.
- Phenomenon: Vector retrieval results include original sensitive information such as bank card numbers and family income details, triggering compliance risks. Cause: Index documents are not desensitized, and original sensitive fields are stored directly in the vector store.

## How to Verify Proper Configuration
- Manually upload a current semester family economic hardship certification form, perform a retrieval test, and confirm returned results match current semester relevant materials.
- Check the index update log, confirm full or incremental updates are completed per semester cycle with no failed records.
- Review the field list in the vector store, confirm sensitive fields have been filtered or desensitized, and original raw data is not stored directly.
- Simulate a review scenario by concatenating multiple documents, confirm retrieved context length meets the `maxToken` setting requirements.

The values provided here are common starting points, and should be evaluated against the user's own samples.
