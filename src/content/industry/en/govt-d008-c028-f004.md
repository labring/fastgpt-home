# Business Process Guidance for Market Entity Registration and Licensing: Workflow Orchestration

## What the Data for This Category Looks Like
This category’s data originates from the enterprise registration full-process electronic system, the national enterprise credit information publicity system, the electronic business license system, and the residence information database. Data updates occur daily. Daily processed documents include establishment registration applications, articles of association, shareholder resolutions, residence certificates, business licenses, food business license applications, and similar materials. Fields covered include entity name, residence address, shareholder information, license type, and more. All fields follow government service standard formats, with no custom special units.

## Constraints Imposed on Workflow Orchestration
The multi-source, daily updated data requires workflow configurations with scheduled synchronization nodes to ensure called enterprise credit and residence information uses the latest versions. The need to process multiple standardized document types requires workflows to set up differentiated field extraction and verification rules for distinct business scenarios: establishment, change, and license application. Links that take significant time, such as verifying names, residences, and shareholder materials, must be split into independent workflow nodes, with support for configuring manual intervention trigger conditions. Since errors directly impact an entity’s business operation qualifications, workflows must include pre-verification links to block non-compliant application materials and prevent invalid progression of subsequent processes.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Condition | Trigger the corresponding verification process based on the application material type | This category has multiple business scenarios, and verification rules vary significantly across application types |
| Timeout Setting | 300–600 seconds | Links such as verifying names and residences require calling multiple system interfaces, so sufficient response time must be reserved |
| `variables` | Bind query parameters for the residence information database and enterprise credit database | Ensure the data source called by the workflow uses government standard interfaces, matching the business data source |
| Node Retry Rule | Retry 2 times after failure, with a 60-second interval | Occasional fluctuations in system interfaces can recover automatically, avoiding directly rejecting applications due to a single failure |
| `nodeId` | Assign a unique identifier to each verification node | Facilitate locating abnormal links and quickly troubleshooting workflow operation issues |
| Exception Branch Handling | Jump to the manual review node | Scenarios such as complex corrections and prior license judgment require manual intervention, which aligns with actual business needs |

## Three Common Configuration Errors
- Workflow runs timeout, and the interface shows a request timeout prompt. This occurs when no reasonable timeout threshold is set for the multi-source data verification link, and the wait time for calls to the enterprise credit information publicity system interface exceeds the configured duration.
- Queries unrelated to registration and licensing trigger knowledge base AI responses, without jumping to the designated reply node. This occurs when no classification trigger rule is configured at the workflow entry, and irrelevant requests are not directed to the preset fallback reply branch.
- The workflow is set to a context count of 0, but historical conversation content is still included during actual calls. This occurs when the call scope of the context is not clearly limited via `variables`, and the global conversation history parameter is inherited by default.

## How to Verify Correct Configuration
- Trigger a test application matching the target business type, and check if the workflow automatically jumps to the correct verification node.
- Simulate an interface timeout scenario to confirm if the workflow follows configured rules to retry or jump to the manual review node.
- Review the workflow operation log to verify that data source parameters bound via `variables` match government system interfaces.
- Test queries unrelated to registration and licensing to confirm if they jump to the preset fallback reply branch.
