# Business Process Guidance for Urban Sanitation and Urban Management Law Enforcement Cases: HTTP APIs and External Systems

## What this category of data looks like
Data is typically sourced from urban management law enforcement platforms, urban operation grid platforms, video surveillance, and public complaint work orders, with daily updates. Daily documents include inspection records, case filing approval forms, on-site photos, rectification notices, penalty decisions, and case closure reports. Core fields cover case number, violation type, responsible entity, rectification progress, disposal result, and other items. These are dynamically generated alongside case disposal stages and do not follow a unified fixed format.

## What constraints do these characteristics impose on the "HTTP APIs and External Systems" link
The requirement for multi-source data access means APIs must support common data protocols of different business systems, and adapt to the return formats of urban management law enforcement platforms, grid platforms, and similar systems. The daily update frequency limits API call frequency to avoid pulling duplicate or expired case data. The diverse document types require APIs to support synchronous transmission of text and image parameters, while also verifying the integrity of returned fields to ensure no core information required for case disposal is missing. Additionally, process guidance needs to link with on-site evidence collection, violation determination, and other stages, so APIs must support collaborative calls of cross-system data to assist information verification for core disposal processes.

## How to set configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {API key assigned by the external urban management system}` | Follow the identity authentication specifications of the external system to verify request legitimacy and prevent unauthorized access |
| `variables` | `{"filter_status": ["case filed but not closed"], "include_fields": ["inspection records", "penalty decisions"]}` | Limit the case status and document types pulled by the API, to accurately match the core data needs of business process guidance |
| `responseData` | `Return the top 80 entries sorted by disposal priority` | Control the volume of data returned by a single API to avoid system overload, and adapt to the daily case disposal workflow |
| API call frequency | `1 call every 600 seconds` | Match the daily update frequency of this category of data, to avoid pulling duplicate or expired case information |
| Response timeout threshold | `300 seconds` | Cover the maximum time required for on-site evidence upload and cross-system data verification, preventing request interruptions that cause process stalls |

## Three common mistakes
- Symptom: The API returns an empty `responseData` field. Cause: No correct case status filter parameter configured in `variables`, resulting in no matching case data being pulled.
- Symptom: API requests throw errors after timing out for more than 10 seconds continuously. Cause: No reasonable response timeout threshold set, or failure to adapt to the latency characteristics of cross-regional data transmission from urban management systems, causing requests to be terminated before completion.
- Symptom: Image fields returned by external systems cannot be parsed normally. Cause: Multi-format data transmission configuration for the API is not enabled, only text parameter reception is supported, making it unable to handle document types such as on-site photos.

## How to confirm the configuration is correct
- Call the test API, check if the returned `responseData` includes preset case fields and document types, and verify that they match the filter rules configured in `variables`.
- Simulate multiple calls, check if the API call interval meets the preset frequency, and confirm that no duplicate pulling or timeout interruptions occur.
- Connect a single typical case data set, verify that the API can normally receive and return the corresponding documents, and confirm that the multi-format data transmission function works properly.
- Check system logs to confirm that the `Authorization` authentication request returns a 200 status code, with no identity verification failure errors.

The values provided here are common starting points and should be measured against the reader's own samples.
