# Business Process Guidance for Construction Project Environmental Impact Assessment (EIA) Approval: Workflow Orchestration

## What this category of data looks like
Data for this category comes from the national unified construction project EIA declaration and approval system, ecological environment zoning control results, pollution discharge permit platform, and monitoring data. Update frequency is irregular. Daily circulated documents include environmental impact assessment reports or report forms, approval applications, public participation explanations, technical evaluation opinions, and EIA approval documents. Core fields include project category, EIA level, pollution control measures content, public participation records, approval node status, and others. There are no fixed unified unitized fields, and field content adjusts dynamically based on the type of declared project and approval stage.

## What constraints do these characteristics impose on workflow orchestration
Since data sources are scattered and updates have no fixed cycle, workflows must support dynamic pulling and verification of multiple data sources. This prevents process interruptions caused by data lag or inconsistent formats. Daily circulated document types are diverse, and fields adjust dynamically. Workflows must configure nodes that can flexibly adapt to different document structures, without hard-coding fixed field rules. Core time-consuming steps involve verifying project category and EIA level. Workflows must set pre-verification nodes to intercept applications that do not meet classification rules in advance. At the same time, since errors directly affect project construction and approval validity, workflows must configure clear failure rollback and alert paths.

## How to set the configuration
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Global variables include project code, call token, approval node ID, no more than 20 in total | EIA approval processes only need to pass core business identifiers and call credentials; too many variables will increase context load and reduce tool call efficiency |
| Tool call trigger rule | Automatically trigger based on approval node status, call tools when the node enters the pending verification stage | Matches the fixed process node sequence of EIA approval, to avoid false or missed triggers |
| `nodeId` | Bind to the node ID of the national unified construction project EIA declaration system, value range 1001-9999 | Corresponds one-to-one with internal system approval nodes, to prevent mismatches between process nodes and actual approval links |
| DingTalk webhook alert threshold | Trigger when approval node timeout exceeds 1200 seconds | Single stage of EIA approval takes a relatively long time; setting a reasonable alert window allows handlers to be notified promptly |
| Tool call retry count | Maximum 3 retries, 60 seconds interval between each attempt | Prevents system rate limiting caused by frequent calls, while ensuring the process can automatically recover after temporary failures |

## Three common misconfigurations
- The symptom is that when the workflow calls the MCP tool, the token field defined in `variables` is empty, and interface authentication cannot be completed. The cause is that global variables were not correctly mounted to the parameter configuration of the tool call node, so the node cannot read the credential information stored globally.
- The symptom is that the workflow triggers tool calls at non-verification nodes, and the returned project category data does not match the current approval stage. The cause is that the tool call trigger rule is not bound to the approval node status, and only triggers tools in a fixed sequence.
- The symptom is that the DingTalk webhook does not push timeout alerts, and approval node timeouts are not handled promptly. The cause is that the callback address was not filled correctly in the DingTalk webhook configuration, or the alert threshold was set outside a reasonable window.

## How to confirm the configuration is correct
- Enter the workflow editing page, check whether the `variables` configuration item includes core business parameters such as project code, call token, and approval node ID.
- Simulate switching the approval node to the pending verification stage, verify whether the tool automatically triggers according to the configured rules and returns corresponding data.
- Fill in a test DingTalk webhook address, manually trigger the timeout scenario, and verify whether alert messages are pushed normally.
- Check whether the `nodeId` configuration matches the node ID range of the national unified construction project EIA declaration system.

The values provided are common starting points and should be measured against the reader's own samples.
