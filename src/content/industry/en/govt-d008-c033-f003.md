# Business Process Guidance for Tendering and Procurement Compliance Management: Multi-turn Dialogue and Prompt Words

## What This Category of Data Entails
This category of data covers full-process procurement business for entities including central state-owned enterprise (SOE) procurement centers, tendering offices, business demand departments, audit and discipline inspection departments, and tendering agencies. Daily documents include procurement plans, demand specifications, tender documents, bid evaluation records, contracts, acceptance documents, and supplier complaint materials.
Data sources include enterprise procurement platforms, public resource trading platforms, supplier databases, contract management systems, and audit problem databases, with daily updates.
Data fields include procurement methods, budget basis, scoring methods, supplier qualification conditions, performance acceptance records, and more. Each type of document has dedicated verification fields.

## Constraints for Multi-turn Dialogue and Prompt Words
Data sources are scattered and updated daily. Multi-turn dialogue contexts must integrate the latest tendering, contract, and audit risk data in real time, to ensure the timeliness of compliance verification bases.
There are diverse document types with dedicated fields. Prompt words must adapt to the verification logic of different documents, guiding users to gradually check key information according to business links.
The most time-consuming verification links require multi-turn follow-up questions to supplement details of budget basis and scoring methods, while associating past compliance risks from the audit problem database.
Error consequences are severe. Compliance verification nodes must be embedded in the dialogue to avoid missing key compliance items.

## Configuration Settings
These configurations are formulated based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `messages` | Retain the most recent 15–20 dialogue turns | Adapt to the process tracing needs of multi-link tendering and procurement, avoid repeated confirmation of prior procurement information |
| `variables` | Bind procurement method, budget basis, and scoring method variables | Quickly call compliance verification rules for the corresponding category, match dedicated fields of business documents |
| Maximum context length | 6000–10000 characters | Cover core content of multiple types of business documents including procurement plans, tender documents, and bid evaluation records |
| Single conversation log storage | Single application log within 100 MB | Meet the compliance requirements of enterprise audit log retention, facilitate subsequent review and problem troubleshooting |
| Historical conversation recall limit | Top 8–12 conversation records | Balance context completeness and response latency, avoid redundant data interfering with compliance verification logic |
| Log recording switch | Enable full-link logging | Retain complete records of dialogue interactions, workflow execution, and model responses, for audit and problem location |

## Three Common Misconfigurations
- Dialogue logs display empty content after calling a workflow. Cause: Full-link logging is not enabled, or the log storage path is not correctly bound to the application container mount directory.
- Workflow execution shows a failure, but response logs exist in the model backend. Cause: The `variables` parameter is not correctly bound to workflow nodes, preventing model output from mapping to corresponding business compliance verification rules.
- Historical conversation content cannot be passed when calling a verification node. Cause: The delivery logic for the `messages` parameter is not enabled in workflow configuration, so past procurement demands and verification records are not carried into the current interaction context.

## How to Confirm Successful Configuration
- Initiate a simulated tendering and procurement dialogue, check if dialogue content is fully recorded in the log panel, and confirm the log storage path configuration is correct.
- Call a workflow node and pass a test historical dialogue fragment, check if the `messages` parameter is correctly loaded into the current interaction context.
- Bind test business variables, check if the model triggers corresponding compliance verification logic based on the variables.
- Trigger a simulated abnormal error, check if complete interaction and execution records are retained in the logs, and confirm the log switch is enabled.
