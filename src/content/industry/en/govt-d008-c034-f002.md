# Business Process Guidance for Enrollment and Student Status Management: Vector Models and Indexing
Reference only; verify against the target FastGPT release and deployment documentation.

## What data in this category consists of
This category’s data mainly comes from four sources: the national primary and secondary school student status management system, local enrollment and admission platforms, household registration and property data, and school educational administration systems. Staff process these documents daily: enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, and student status change approval forms. Data updates occur daily. Fields include student identity identifiers, household registration and property association information, student status change records, and enrollment batch rules. Most data is structured or semi-structured business forms. Some documents include cross-system associated data.

## Constraints on vector models and indexing
This category’s data sources are scattered and update daily. The indexing system must support incremental updates and cross-system data association matching. Most documents are structured forms. The vector model must adapt to field-level precise matching to avoid breaking business associations through chunking. The data directly relates to student admission eligibility. Recall accuracy directly impacts admission disputes and student status compliance. The proportion of irrelevant recall results must be strictly controlled. The daily update feature also requires indexing scheduling to align with business data generation rhythms. Index lag that causes mismatches between policies and student status information must be avoided.

## How to set configuration values
| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| Chunk Length | 800–1200 characters | Most documents in this category are structured forms. Overly long chunks break field associations for student identity and household registration information. Overly short chunks lose contextual logic |
| Overlap Length | 100–150 characters | Documents such as student status information forms and transfer applications contain continuous identity fields. Overlapping chunks preserve cross-block association information |
| Similarity Threshold | 0.75–0.85 | Precise matching of core business fields such as student identity and household registration conditions is required. Irrelevant admission records or student status information must not interfere with recall results |
| `maxToken` | 4000 | Enrollment policy documents are lengthy. Full loading of policy text ensures response accuracy |
| `defaultToken` | 1000 | The context length requirement for single business process guidance adapts to daily consultation content scope |
| Single Search Limit | Top 10 entries | Data in this category grows with daily updates. Too many recall results exceed context carrying capacity and affect response logic |

## Three common configuration errors
- Search results display duplicate student status registration records. The cause is missing deduplication indexing rules for duplicate data from the national primary and secondary school student status management system. The same student status information is recalled multiple times via indexing.
- Search returns policy content that does not match the current enrollment batch. The cause is missing index refresh tasks configured for the daily update frequency. Old batch enrollment plans remain in the index library.
- Search results for household registration and property verification are empty. The cause is missing association fields for household registration and property data in the vector index’s metadata filter conditions. Cross-system associated business data cannot be matched accurately.

## How to verify correct configuration
- Import a single student status information form. Execute targeted search queries. Verify the field integrity and matching degree of returned results. Adjust relevant configuration items until they meet business expectations.
- Simulate the daily updated data import process. Check the execution status of index update tasks. Confirm the update cycle matches business data generation frequency.
- Test the import of duplicate student status data. Verify that deduplication logic takes effect. Ensure no duplicate recall results appear.
- Query the latest batch of enrollment policy content. Verify the timeliness of returned results. Confirm the index covers the latest business data.
