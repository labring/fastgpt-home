# Business Process Guidance for Enrollment and Student Status Management: Multi-turn Dialogue and Prompt Words

## What this category’s data looks like
Data for this category comes from the national primary and secondary school student status management system, local enrollment platforms, household registration and real estate data platforms, and school academic affairs systems. Data updates occur daily.
Commonly used documents include enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, and student status change approval forms.
Core fields cover student identity, household registration and real estate information, student status status, enrollment batch, and more.
Maintenance is performed by coordinated windows under the basic education division of education bureaus, school academic affairs offices, enrollment examination institutions, and street communities.

## Constraints for multi-turn dialogue and prompt configuration
Data sources for this category are scattered and require cross-system verification. Multi-turn dialogue must guide users to provide required materials in sequence according to enrollment processing steps, to avoid missing verification items.
Data updates daily. Dialogue must call the latest enrollment plans, student status rules, and other content in real time to ensure accurate responses.
Multiple document types are used. Prompt configurations must be split for different scenarios such as registration, student status registration, status changes, and policy explanations.
Core fields involve student identity and student status. Dialogue must strictly verify that input content matches system data, to prevent duplicate or missing student status issues.

## How to set up configurations
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind student status ID + enrollment batch | Ensure dialogue context links to a unique processing subject and item, avoid cross-user data confusion |
| `messages` | Retain the first 20 rounds of dialogue content, filter invalid duplicate messages | Adapt to context memory requirements for multi-step enrollment interaction |
| `variables` | Bind fields such as household registration address, real estate certificate number, student status ID | Automatically fill exclusive business parameters required for cross-system calls |
| Maximum context window | 8000–12000 characters | Accommodate long text reference content such as enrollment policies and student status management rules |
| Dialogue timeout | 60 seconds | Adapt to response delays from cross-system data verification |
| Supported material upload types | Images, PDF documents | Support users to upload enrollment-related certification materials |

## Three common misconfigurations
- The default official icon is displayed in the dialogue window, and custom styles cannot be used. The cause is that the corresponding icon resource was not uploaded in the non-login dialogue component configuration.
- Policy explanations and student status verification results output in multi-turn dialogue are spliced chaotically, with field misalignment or redundant content. The cause is that the `messages` context was not split according to enrollment processing steps, and corresponding `variables` parameters were not bound to fill exclusive business data.
- Calling the dialogue log interface returns empty data, and full historical records cannot be exported. The cause is that the batch export permission for dialogue logs was not enabled, and the `chatId` range was not specified to filter logs for corresponding processing items.

## How to verify correct configuration
- Launch an enrollment policy consultation dialogue, verify that the dialogue window icon uses the custom style.
- Enter a question related to student status change application, check that the reply automatically fills in preset `variables` field data such as household registration and real estate information.
- Export the dialogue log for the specified `chatId`, confirm that complete multi-turn interaction content is included.
- Upload an enrollment material image, verify that the dialogue module can recognize and associate it with the corresponding processing step.
