# Business Process Guidance for Enrollment and Student Status Management: Knowledge Base Retrieval and Recall

## What Data Looks Like for This Category
Data sources include the national primary and secondary school student status information management system, local enrollment platforms, household registration and property verification data, and school academic affairs systems.
Commonly processed documents include enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, and student status change approval forms.
Core fields cover student identity identifiers, household registration addresses, property information, student status change types, and admission batches.
Data updates occur daily. A single update covers newly added student status registration, admission, and verification data from the current day.

## Constraints for the Knowledge Base Retrieval and Recall Link
Daily high-frequency data updates require the retrieval and recall pipeline to support near-real-time index refreshes. This prevents recalling outdated student status or enrollment data.
Multi-source heterogeneous data formats—including structured student status tables, unstructured policy documents, and property verification materials—require retrieval to support mixed-format matching. This balances precise field matching and semantic understanding.
Business logic centered on student identity and admission qualifications requires retrieval to prioritize matching keywords related to identity identifiers.
Single business links involve multiple related documents. Recall results must associate multiple types of business data for the same student, avoiding fragmented information.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` | `0.72–0.80` | This category requires matching precise fields such as student identity and property address. A threshold that is too low will introduce irrelevant results, while a threshold that is too high may miss valid matching items, calibrated based on actual testing |
| `limit` | `Top 8` | A single business process involves multiple related documents such as student status form, transfer application, and admission roster. Enough related entries must be recalled while avoiding context overload |
| `searchMode` | `Hybrid Retrieval` | Adapt to mixed retrieval needs for structured student status data and unstructured policy documents, covering precise field matching and semantic retrieval |
| `usingReRank` | `Enabled` | Semantic similarity sorting for multi-source data requires re-ranking model optimization to improve the ranking priority of results related to student identities |
| `datasetSearchUsingExtensionQuery` | `Enabled` | Automatically expand synonyms related to student status and enrollment based on user questions, such as expanding "transfer" to "student status change", to improve recall coverage |
| `collectionIds` | `Bind exclusive dataset IDs for enrollment and student status management` | Isolate knowledge base data from other categories to avoid recalling irrelevant content such as funding or academic scheduling |

## Three Common Mistakes
- Phenomenon: Retrieval result accuracy fluctuates significantly, and some student status field matching results rank low. Cause: No exclusive matching weight is configured for student identity identifiers such as student ID numbers, and only general semantic matching logic is relied on.
- Phenomenon: Duplicate student status information entries appear in recall results. Cause: The knowledge base index merging component is not enabled, and duplicate data for the same student is not automatically deduplicated during multi-source synchronization.
- Phenomenon: Retrieval times out or external enrollment platform data cannot be obtained. Cause: No access adaptation rules for external data sources are configured, and recalling full multi-source data at the same time causes pipeline overload.

## How to Verify Proper Configuration
- A single student status data entry and its corresponding enrollment policy document are imported. A retrieval test is performed, and the recall results are confirmed to include the target student status fields and policy entries.
- The knowledge base index logs in FastGPT v4.17.0 are reviewed. The daily incremental update task is confirmed to execute normally with no data synchronization failure errors.
- A test question containing a duplicate student ID number is submitted. The retrieval results are confirmed to contain no duplicate entries.
- The bound external enrollment platform test interface is accessed. Retrieval is confirmed to normally obtain external document content.

The values provided are common starting points and should be measured against samples specific to the deployment.
