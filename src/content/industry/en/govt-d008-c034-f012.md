# Business Process Guidance for Enrollment and Student Academic Record Management: Deployment and Upgrade

## What the data for this category looks like
Core data for this category originates from the national primary and secondary school student academic record management system, local enrollment platforms, household registration and property data, and school educational administration systems. The update frequency is daily. Commonly processed documents include enrollment application forms, student academic record information forms, transfer applications, enrollment plans, admission rosters, and student academic record change approval forms. Data fields cover student identity identifiers, household registration and property information, academic record status, enrollment qualification verification results, and similar items. Fields do not have unified fixed units, and are based on the actual meaning within the relevant business scenario.

## Constraints imposed on deployment and upgrade by these characteristics
Multi-source data access requires configuring multiple database connections during deployment, and adapting to permission verification rules of different systems. The daily update frequency requires deploying scheduled synchronization tasks to avoid data lag disrupting business processing. Documents with multiple fields and sensitive student information require strict access permission controls to prevent data leaks. The core business logic of student academic record changes requires prioritizing configuration of identity verification and academic record change process guidance modules during deployment, and reserving a data verification link to avoid duplicate or missing student academic record issues.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://localhost:27017/fastgpt_edu?maxPoolSize=200` | The academic record data volume for this category is large, and non-relational databases are suitable for storing multi-dimensional student academic record and enrollment information |
| `PG_URL` | `postgresql://edu_user:secure_pass@192.168.1.20:5432/edu_enroll` | Structured data such as enrollment plans and admission rosters is suitable for storage in relational databases, to adapt to data synchronization requirements across multiple systems |
| `REDIS_URL` | `redis://localhost:6379/0?timeout=600 seconds` | Cache frequently queried household registration verification and student academic record status data to reduce latency from cross-system calls |
| `DB_MAX_LINK` | `200 connections` | The daily updated data for this category includes cross-system synchronization requests, to avoid synchronization interruptions caused by exhausted connection pools |
| `STORAGE_S3_ENDPOINT` | `http://192.168.1.100:9000` | Store attachment files such as enrollment application forms and student academic record change approval forms, to adapt to file upload and download requirements across multiple scenarios |
| `FE_DOMAIN` | `http://192.168.1.100:3000` | Configure the frontend callback address for business process guidance, to ensure normal user operation workflows |

## Three Common Misconfigurations
- Symptom: The `mkdir /run/desktop/mnt/host/wsl/docker` error appears after running `docker-compose up -d`. Cause: WSL2 mount permissions are not configured correctly, preventing FastGPT containers from accessing locally mounted data source directories.
- Symptom: Some fields are missing during student academic record data synchronization. Cause: Access permissions for `PG_URL` or `MONGODB_URI` are not configured correctly, preventing full data reading from local enrollment platforms or educational administration systems.
- Symptom: Tasks time out when processing transfer applications in bulk. Cause: The `DB_MAX_LINK` value is not adjusted, leading to insufficient connection pools to process synchronization requests for multiple student academic record change approval forms in parallel.

## How to Verify Successful Configuration
- Run the `docker ps` command to confirm that all FastGPT v4.17.0 related containers are in running state.
- Access the frontend address configured in `FE_DOMAIN`, test calling the student identity verification interface, and confirm that normal student identity verification results are returned.
- Upload an enrollment application form attachment, confirm that the file can be stored normally in the storage service configured in `STORAGE_S3_ENDPOINT`.
- View the cache service logs corresponding to `REDIS_URL`, confirm that frequent student academic record status query requests are cached normally.

The values provided are common starting points, and should be evaluated against the user's own samples.
