# Business Process Guidance for Discharge Permit Management: Deployment and Upgrade

## Data Characteristics for This Category
This category’s data originates from the national discharge permit management information platform, enterprise environmental protection ledgers, online monitoring systems, and environmental statistics systems. Daily associated documents include discharge permit application forms, implementation reports, self-monitoring plans, ledger records, change applications, and permit copies. Data updates occur quarterly. Core fields cover permitted emission limits, monitoring indicator thresholds, ledger time ranges, and more. Corresponding units include emission concentration units, annual emission limits, and others. Document structures are divided into three categories based on processing stages: application, implementation, and supervision.

## Constraints on Deployment and Upgrade
The data for this category is scattered across multiple sources, has a fixed update cycle, and includes diverse document types. During deployment, access configuration for multi-source data must be adapted to ensure stable operation of quarterly data synchronization tasks. Since core data is tied to discharge permit compliance, reliable database connection and storage solutions must be configured during deployment to avoid data loss or synchronization errors. During the upgrade process, continuity of business process guidance must be maintained; existing user access to processing flows cannot be interrupted. Upgrades must also be compatible with legacy document parsing logic and adapt to different versions of discharge permit document structures. Additionally, data field units are strongly bound to compliance requirements. Parsing rules must be aligned with industry technical specifications during deployment to prevent limit matching errors.

## Configuration Settings
This configuration applies to FastGPT v4.17.0. Specific parameter details are as follows:

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://username:password@host:port/ep_db?authSource=admin`, compatible with mongo:4.4.29 | Stores structured data from enterprise environmental protection ledgers and online monitoring systems; meets MongoDB version requirements for low-CPU environments |
| `PG_URL` | `postgresql://username:password@host:port/<discharge_permit_management_db>` | Stores structured application and change data from the national discharge permit management information platform; supports complex queries and permission control |
| `REDIS_URL` | `redis://:password@host:port/0` | Caches quarterly updated permit limit data and user session information to reduce database query load |
| `STORAGE_S3_ENDPOINT` | `Configure according to local storage or cloud storage service provider address` | Stores unstructured documents such as self-monitoring reports and ledger records; supports upload and download of multiple file types |
| `DB_MAX_LINK` | `20–30 connections` | Adapts to concurrent request volume for quarterly data synchronization; prevents database connection exhaustion |
| `ROOT_KEY` | `Generate a random string according to system security requirements` | Configures system administrator permission verification to prevent unauthorized access to the deployed service |

## Three Common Configuration Mistakes
- Symptom: After deploying the open-source container, a `getPluginGroups 500` error is returned, and the interface prompts that the commercial version link is not configured. Cause: The open-source code does not include the proAPI-related modules. Directly using commercial version deployment scripts or configuration items leads to interface call failures.
- Symptom: Data synchronization exceptions occur between nodes during cluster deployment. Cause: Multi-node shared `REDIS_URL` and `STORAGE_S3_ENDPOINT` are not correctly configured, leading to inconsistent cache and storage data across nodes.
- Symptom: After replacing the MongoDB image with mongo:4.4.29, the service fails to start, and a version verification exception prompt is displayed. Cause: FastGPT's built-in mandatory MongoDB version verification logic is not disabled, or the database pointed to by the configured `MONGODB_URI` has not been initialized.

## How to Verify Successful Configuration
- Execute `docker logs container name` to check database connection-related logs, and confirm there are no `connection timeout` or `authentication failed` error messages.
- Access the frontend address corresponding to `FE_DOMAIN`, attempt to load the discharge permit-related document parsing and preview function, and confirm there are no format parsing errors.
- Trigger a simulated quarterly data synchronization task, and check whether a new synchronization log file is generated in the storage directory corresponding to `STORAGE_S3_ENDPOINT`.
- Use `ROOT_KEY` to call the system management interface, and verify that the administrator permission verification logic functions correctly.
