# Workflow Guidance for Government Information Application Disclosure: HTTP Interfaces and External Systems

## What this category’s data looks like
Data for this category originates from government information disclosure platforms, internal agency archive systems, document management systems, departmental business ledgers, and relevant specifications of the Regulations on Government Information Disclosure. Commonly processed documents include government information disclosure application forms, correction notices, third-party opinion solicitation letters, reply documents, service receipts, administrative reconsideration response materials, and similar items. Data updates follow no fixed schedule, adjusting based on the timing of individual application submissions, archive filing, and process changes. Core operations revolve around the generation and circulation of individual information disclosure requests from specific applicants.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Because data sources are scattered across multiple internal business systems and public disclosure platforms, HTTP interfaces must support unified adaptation logic for cross-system data retrieval. Document types are diverse with inconsistent structures, so interfaces must support transmission and parsing of application materials and reply documents in different formats. Data updates follow no fixed schedule, so interfaces must avoid hard-coded caching logic and pull the latest data on demand in real time. Additionally, errors may lead to administrative reconsideration or judicial proceedings, so interfaces must have complete request traceability and exception reporting capabilities to ensure every workflow operation can be traced.

## How to configure settings
The following configurations are based on the interface setup logic of FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {Exclusive API Key Assigned by Government Platform}` | Follow identity authentication standards for government system interfaces, block unauthorized interface requests |
| `variables` | `{"applicant_id": "Unique Applicant Identifier", "apply_keyword": "Retrieval Keyword for Applied Information"}` | Pass business-specific parameters to adapt to personalized request logic for individual application cases |
| `responseData` | `Only return three core fields: application acceptance status, reply content, and delivery voucher identifier` | Follow the minimum necessary principle for government data transmission, reduce exposure risk of sensitive data |
| Interface timeout setting | `600 seconds` | Government affairs processing involves multi-stage review and cross-system collaboration, reserve sufficient response time |
| Retry trigger rule | `Trigger when response times out or returns a 5xx status code` | Address occasional temporary maintenance or network fluctuations of government systems, ensure call stability |

## Three common mistakes
- Phenomenon: No valid return data after calling the interface, with status codes 401, 403, or 500 returned. Cause: The `Authorization` parameter is not configured correctly, an invalid or unauthorized API key is used, or the application retrieval keyword in `variables` is not correctly bound, making it impossible to locate the corresponding government information.
- Phenomenon: The reply content returned by the interface has formatting errors and cannot be directly used to generate official government documents. Cause: The interface does not adapt to document formats returned by different government systems, and the content in `responseData` is not standardized.
- Phenomenon: Subsequent business process nodes are not triggered after the interface call is completed. Cause: The application status returned by the interface is not mapped to the process logic of the external business system, and status synchronization is not completed.

## How to confirm correct configuration
- Call the test interface with a valid `Authorization` parameter, confirm that the return status code is 200, and the `responseData` contains the preset core business fields.
- Pass different combinations of `variables` parameters, verify whether the interface can adapt to retrieval requirements for different individual application cases and return corresponding data results.
- Simulate the temporary maintenance scenario of the government system, trigger interface timeout or 5xx status code, confirm that the interface triggers the retry logic as configured.
- Check the interface's exception reporting logs, confirm that traceability information for all call requests is fully recorded, and parameters and return results of each request can be traced.
