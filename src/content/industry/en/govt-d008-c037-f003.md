# Government Information Disclosure Application Process Guidance: Multi-turn Dialogue and Prompt Engineering
This document is compiled based on the configuration specifications of FastGPT v4.17.0.

## What Data for This Category Looks Like
This category of data is sourced from government information disclosure platforms, agency archive systems, document management systems, departmental business ledgers, and relevant government disclosure regulations. Daily processed documents include government information disclosure application forms, supplementary notice letters, third-party opinion solicitation letters, reply letters, service receipts, and administrative reconsideration response materials. Data updates follow no fixed cycle, and only change with new applications, archived documents, or policy adjustments. Most documents are structured forms and standardized official documents. Core fields include applicant information, application content, public attribute judgment basis, reply opinions, and relief pathway explanations.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompt Engineering
Data for this category is scattered across multiple government systems and standardized documents. Multi-turn dialogue must support context-aware retrieval and invocation of cross-source data. Standardized documents have fixed field requirements, so prompts must clearly define required items and formatting for generated content. Since no fixed update cycle exists, dialogue calls must use the latest archived data. Case-by-case processing requires that dialogue context only binds to the specific information of the current application, to avoid mixing data across different applications. Strict compliance requirements mandate adding a content verification link to the dialogue process, to mitigate risks of overdue or non-compliant replies.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Context Window Limit | First 20 dialogue turns or 8000 characters | Avoid mixing data across applications, adapt to the content length of standardized government documents |
| Context Recall Limit | Top 5 related documents | Adapt to the length of government documents, avoid interference from redundant information |
| `messages` Field Population Rule | Only include session history and related documents for the current application | Ensure dialogue context only relates to this individual case, prevent data misuse |
| `variables` Configuration | Bind current application's applicant information and application number | Automatically populate required fields in standardized documents, reduce manual data entry |
| `chatId` Binding Rule | One-to-one correspondence with government information disclosure application numbers | Ensure multi-turn dialogue context only serves a single application |
| Prompt Template | Clearly specify that generated replies must include relief pathways and compliance basis | Match compliance requirements for this category, avoid deficiencies in replies |

## Three Common Misconfigurations
- Issue: After orchestrating multi-turn dialogue in a workflow, token consumption per single request exceeds expected levels. Cause: The number of dialogue turns or character count of the context window is not limited, causing repeated counting of historical content in token statistics.
- Issue: Generated reply letters omit third-party interest solicitation explanations or relief pathways. Cause: The prompt fails to clearly bind the standardized document field requirements for this category, and does not link to compliance basis.
- Issue: Associated application form files cannot be passed when calling the dialogue interface. Cause: The file upload configuration for the dialogue interface is not enabled, or the binding rules for file parsing are not correctly configured.

## How to Verify Proper Configuration
- Initiate a simulated government information disclosure application dialogue. Confirm the returned context only includes session content for the current simulated application, with no data from other unrelated applications.
- Generate a standardized reply letter. Verify the content includes required fields such as applicant information, corresponding explanations for application content, and relief pathways.
- Call the dialogue interface with a simulated application form file. Confirm the interface can parse the file normally and include its content in the dialogue context.
- Review the binding relationship between `chatId` and application numbers. Confirm that the dialogue context for each application is independently isolated, with no reuse of data across applications.
