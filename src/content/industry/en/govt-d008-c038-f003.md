# Business Process Guidance for Government Procurement Projects: Multi-turn Dialogue and Prompt Engineering

## What the Data for This Category Looks Like
The data sources for this category include national government procurement websites, local government procurement websites, the fiscal integration system, the procurer’s budget system, and supplier credit records. The update frequency is daily. Daily business documents cover procurement requirements, procurement plans, bidding documents, bid submission documents, bid evaluation reports, winning bid announcements, procurement contracts, and question responses. Four core stakeholder groups are involved: procuring entities, the government procurement supervision division of the finance department, procurement agencies, and evaluation experts. Data structure varies significantly by document type, with dedicated fields for each document type.

## What Constraints These Characteristics Impose on Multi-turn Dialogue and Prompt Engineering
The daily updated data sources require dialogue processes to synchronize latest announcements and contract data in real time, preventing use of expired information. The varied structure of different business documents requires prompts to adapt field recognition logic for each document type, ensuring accurate extraction of key information. The distinct business requirements of the four core stakeholder groups require multi-turn dialogue to differentiate roles via context, matching corresponding process rules. Business errors carry serious consequences, so process guidance generated via dialogue must strictly align with general procurement-related rules, with no deviations allowed.

## Configuration Recommendations
Based on the configuration logic of FastGPT v4.17.0, the following configuration items are recommended:
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `chatId` | Bind the procurement project number as the session identifier | Multi-turn dialogue for the same procurement project must maintain context consistency, avoiding context confusion across projects |
| `messages` | Retain the first 10 turns of dialogue context, with each turn’s content not exceeding 1500 characters | Procurement-related documents have long length; overly long context will interfere with the model’s understanding of core rules |
| `variables` | Bind dedicated business variables such as procuring entity ID, supervision department ID, etc. | Procurement processes vary slightly across different procuring entities; dedicated variables allow prompts to accurately adapt to the rules of specific projects |
| Question Optimization | Enable the question optimization feature | Procurement business terms are highly professional; this reduces the threshold for non-professional users, converting vague questions into standard procurement terminology |
| Single Recall Limit | Recall the top 5 matching documents | There are many procurement-related documents; excessive recall will cause context overload and reduce dialogue response efficiency |
| Maximum Context Length | Set to 8000–12000 characters based on actual testing | This range must cover the core content of a single bidding document, while avoiding model processing timeouts |

## Three Common Misconfigurations
- Scenario: An interface call returns the error "400 Knowledge Base Not Associated". Cause: The dedicated government procurement document library is not bound to the current dialogue application, only a separate general knowledge base has been created.
- Scenario: Cross-project context drift occurs during multi-turn dialogue. Cause: The procurement project number is not used as `chatId`, leading to incorrect reuse of session context across different procurement projects.
- Scenario: Professional term deviations appear in generated process guidance. Cause: The question optimization feature is not enabled, and vague user questions are not converted into standard procurement terminology, leading to incorrect model understanding.

## How to Verify Successful Configuration
- View the identifier field in the session details, confirm that `chatId` is bound to the procurement project number.
- Trigger variable calls during test dialogue, confirm that the returned content includes pre-bound dedicated parameters such as procuring entity, supervision department, etc.
- Initiate consecutive questions, first ask about procurement requirements and then about bidding document-related content, confirm that the dialogue context remains consistent with no content drift.
- Call the interface to test knowledge base recall, confirm that all returned documents are dedicated government procurement-related documents, with no irrelevant business content.
