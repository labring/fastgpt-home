# Business Process Guidance for Environmental Law Enforcement and Monitoring Supervision: Multi-turn Dialogue and Prompt Engineering
This document is written based on FastGPT v4.17.0.

## What data looks like for this use case
Data sources for environmental law enforcement and monitoring supervision scenarios include online monitoring platforms, automatic pollutant emission monitoring data, ecological environment law enforcement systems, and third-party test reports. The update frequency is daily. Daily documents include on-site inspection records, sampling records, monitoring reports, order for correction decisions, and administrative penalty decisions. On-site inspection records include inspection time periods, site information, and operating condition records. Sampling records include sampling sites and sample numbers. Monitoring reports include test items and results. Law enforcement documents include identification of illegal facts and rectification requirements. Data fields cover scenario information across the entire law enforcement process. There is no unified fixed format. Content must be extracted according to different document types.

## What constraints do these characteristics impose on multi-turn dialogue and prompt engineering
Since data is updated daily and sourced from multiple locations, multi-turn dialogue must call the latest online monitoring and law enforcement system data in real time. This ensures dialogue content matches current law enforcement scenarios. Document types are diverse and fields have no unified standard. Prompt engineering must adapt to extraction logic for different documents. This avoids confusion between different types of law enforcement information. Law enforcement scenarios have high requirements for evidence rigor. Multi-turn dialogue must retain a complete context chain. This ensures each operation is supported by corresponding data. Key verification links cannot be omitted.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Generate a unique identifier based on user identity | Isolate conversation history for different law enforcement personnel or pollutant discharge units, avoid data sharing confusion |
| `messages` | Retain the most recent 20 turns of conversation context | Adapt to the needs of multi-step verification in law enforcement processes, ensure coherent and complete dialogue logic |
| `variables` | Inject same-day online monitoring data and current inspection site information | Call real-time, use case-specific latest data, improve the accuracy of dialogue content |
| Maximum context length | 8000–12000 characters | Accommodate multiple law enforcement documents and multi-turn dialogue content, avoid truncation of key information |
| Single dialogue response time | Within 60 seconds | Match the needs of real-time interaction during law enforcement site operations, avoid waiting timeouts that affect law enforcement progress |

## Three common misconfigurations
- Symptom: The `Human` field is empty in the response record preview during API calls, with no user input content displayed. Cause: The user message body for the `messages` parameter was not properly encapsulated, or conversation format data was not passed as required.
- Symptom: Different test accounts see exactly the same conversation history after logging in. Cause: An independent `chatId` was not generated for each user, causing different sessions to share the same data storage node.
- Symptom: Response interruption or no result occurs mid-multi-turn dialogue. Cause: The data range for single dialogue calls was not restricted, causing excessive non-essential law enforcement documents to load and result in a timeout.

## How to verify proper configuration
- Initiate a test conversation using two different test accounts to ask law enforcement-related questions. Confirm that the conversation histories of the two accounts do not overlap. This verifies the isolation effect of `chatId`.
- Call the API interface to initiate a conversation. Check if the returned `messages` parameter contains complete user and assistant dialogue content, and that the `Human` field is not empty. This verifies the configuration correctness of the `messages` parameter.
- Inject use case-specific data variables during the conversation. Confirm that the dialogue content correctly calls the same-day online monitoring data or sampling record information. This verifies the configuration effect of `variables`.
- Simulate a continuous multi-turn law enforcement process conversation. Check that the context is fully retained, with no key information loss or logical disconnection.
