# Business Process Guidance for Social Assistance and Minimum Living Security Review: HTTP Interfaces and External Systems

## What this category of data looks like
Business data for social assistance and minimum living security review comes from the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-departmental shared data from public security, human resources and social security, medical insurance, housing construction, tax, and other departments. Daily business documents include the minimum living security application form, family economic status verification report, household survey form, democratic appraisal records, public notice materials, and assistance approval form. Core fields cover family income, total property, member relationship, application time, and other items. The data update frequency is once per month.

## What constraints do these characteristics impose on the HTTP interfaces and external systems link
HTTP interfaces must connect to multiple external systems due to cross-departmental data sources, and must carry authentication parameters to ensure data access permissions. Interface calls must not be too frequent due to the monthly update frequency, to avoid triggering current limiting rules of cross-departmental systems. Core fields involve family privacy and assistance eligibility, so interface transmission must strictly follow data security specifications, and returned data must accurately match the field structure of business documents. Errors directly relate to incorrect or missed assistance guarantees and public complaints, so interfaces must have failure retry and exception alert mechanisms to ensure the stability of the verification process.

## Configuration Settings
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Method | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {service key assigned by the civil affairs shared platform}` | Authentication is required when connecting to cross-departmental shared systems, which complies with data security access requirements |
| `variables` | `{"familyId": "example value", "applyMonth": "example value"}` | Pass core business parameters to ensure cross-departmental systems return verification data for the corresponding family |
| `responseData` | `$.Verification Result.Total Family Income, $.Verification Result.Total Property, $.Verification Result.Member Relationship` | Extract core fields required for business, filter invalid data to improve transmission efficiency |
| Request Timeout | `600 seconds` | Cross-departmental data queries require long response times, avoid early interruption leading to verification failure |
| Failure Retry Count | `3 times` | Address temporary fluctuations of cross-departmental interfaces, reduce risks of incorrect or missed assistance guarantees |
| Response Field Format | `Match the field structure of the family economic status verification report` | Ensure downstream nodes can directly use the extracted variables to complete the review process |

## Three Common Mistakes
- Phenomenon: Variables extracted from the HTTP request node in the workflow cannot be passed to downstream nodes, and downstream fields are empty. Cause: The JSONPath extraction rule for `responseData` is not correctly configured, and does not match the actual field hierarchy of data returned by cross-departmental systems.
- Phenomenon: Connection timeout or 502 status code error occurs when starting the workflow, and container logs show inability to access external systems. Cause: Outbound network permissions for connecting to the civil affairs shared system are not open, or the `Authorization` parameter is not correctly configured, leading to authentication failure.
- Phenomenon: The number of interface returned data entries does not match expectations, and family economic status verification cannot be completed. Cause: The unique family ID parameter is not configured in `variables`, so cross-departmental systems cannot return verification data for the corresponding family.

## How to Confirm Proper Configuration
- Initiate a simulated request with a test unique family ID, check if the interface response content includes the fields extracted by the `responseData` configuration.
- Verify that the `Authorization` parameter is correctly carried, and the cross-departmental system returns a 200 status code with no authentication errors.
- Trigger downstream nodes, check if the extracted variables can be received, and the field format matches the requirements of business documents.
- Simulate a temporary interface interruption scenario, confirm that the system automatically triggers the failure retry mechanism, and can normally obtain data after retries.
