# Business Process Guidance for Social Assistance and Minimum Living Allowance Audit: Workflow Orchestration

This document is based on FastGPT v4.17.0, and provides configuration guidance for workflow orchestration for business process guidance in social assistance and minimum living allowance audit scenarios.

## What the data for this category looks like
Data for this category comes from the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-department shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, and tax authorities. The update frequency is monthly. Daily processed documents include minimum living allowance application forms, family economic status verification reports, household survey forms, democratic appraisal records, public notice materials, and assistance approval forms. Core fields focus on family economic status, member relationships, and assistance eligibility, with no additional custom statistical indicators.

## What constraints these characteristics impose on the "workflow orchestration" link
Monthly updated cross-department shared data requires workflows to adapt to scheduled triggers for batch verification nodes, to avoid resource consumption from repeated real-time interface calls. Circulation of multiple types of paper and electronic documents requires workflows to clarify node permissions, distinguishing operating subjects for entry, review, public notice and other links. Time-consuming links such as family economic status verification and household surveys require setting wait nodes and timeout reminders to prevent process stagnation. Dependence on cross-department data requires workflows to add data verification nodes to ensure the accuracy of verification results and reduce the risk of incorrect or missed assistance eligibility determinations.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `variables` | Set family income and member relationship as required global variables, with a default empty value | Core minimum living allowance audit relies on family economic and member information, requiring verification of variable integrity when the process starts |
| Node timeout setting | 600 seconds | The average time required for cross-department data retrieval and household survey material organization ranges from 300 to 500 seconds, with redundant time reserved to avoid process interruption |
| `nodeId` | Assign a unique identifier to each business node, incrementing according to the business execution sequence | Facilitates process tracing and error location, adapting to the orchestration logic of multi-node parallel or serial execution |
| Batch processing threshold | 100 items per batch | The upper limit of single batch processing for monthly updated cross-department data is 100 items, avoiding excessive interface pressure |
| Context clearing rule | Clear historical conversations after each branch node completes execution | Prevents interference between knowledge base search results of different branches, adapting to business requirements for unified processing after classification |
| Knowledge base call scope | Call the civil affairs assistance exclusive knowledge base, recall the top 5 results per request | This category of business focuses on assistance eligibility audit, limiting the scope improves result accuracy and reduces invalid information |

## Three common errors
- Self-hosted deployment fails to open the workflow editing interface, displaying a client-side error | Cause: Static resource proxy is not configured for the intranet environment, causing front-end resource loading failure.
- Using the Qwen2.5 model deployed via Ollama fails to enable tool calling | Cause: The trigger condition of the tool calling node is not correctly bound in the workflow, or the tool calling permission is not enabled in the model configuration.
- After calling different knowledge bases by question category in the workflow, the unified processing logic shows result deviations | Cause: Context variables are not uniformly reset before the branch merge node, causing residual branch information to interfere with subsequent processing.

## How to confirm proper configuration
- Start a process test to verify whether the required verification logic for global variables is triggered.
- Simulate a cross-department data retrieval node to confirm that the timeout reminder is triggered according to the preset duration.
- Execute the branch classification and merging process to verify that the context is reset after branch switching.
- Check the node permission configuration to ensure that different operating subjects can only access workflow nodes with corresponding permissions.
