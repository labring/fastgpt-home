# Workflow Guidance for Legality Review of Regulatory Documents: HTTP Interfaces and External Systems

## What this category of data looks like
This category of data comes from regulatory document repositories, higher-level law databases, departmental policy document repositories, and administrative regulatory document filing systems, with an irregular update frequency. Daily processed documents include regulatory document drafts, drafting explanatory notes, legality review opinions, summary of solicited comments, and filing reports. Fields cover document titles, issuing entities, article content, solicited comment feedback, filing numbers, and more. The length of individual documents varies widely, so the system must adapt to transmission requirements for content of different lengths.

## Constraints imposed on HTTP interfaces and external systems by these data characteristics
The data characteristics of this category impose multiple constraints on the HTTP interfaces and external systems link. Decentralized data sources and irregular updates require interfaces to support multi-source data pulling and incremental synchronization configuration, and adapt to the interface formats of different systems. The wide variation in daily document lengths requires interface request bodies to support variable-length text parameters, to avoid content truncation or request overflow. Review requires comparison of multi-dimensional legal bases, so interface returned data must include complete article association information, and cannot return only summaries. The consequences of errors directly affect policy release and filing, so interfaces must have reliable retry mechanisms and detailed error reporting fields.

## How to configure settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Use a fixed Bearer token format, with the value being the application key generated by the platform | Complies with external system standard authentication specifications, ensuring interface call security |
| Request timeout duration | 600–1200 seconds | Adapts to the time required for multi-source legal basis comparison, avoiding timeout interruptions mid-process |
| `variables` | Pass fixed review parameters such as document source and issuing entity | Simplifies repeated configuration for interface calls, and transmits business context information |
| `responseData` | Return all full fields including article associations and comment summaries | Meets the legality review's requirement for multi-dimensional data verification |
| Retry count | 2–3 times | Addresses scenarios where external systems are temporarily unavailable, reducing the impact of single request failures |
| Streaming return interval | Calibrated based on actual testing | Adapts to front-end display rhythm, optimizing user interaction experience |

## Three common configuration errors
- Scenario: When calling a streaming interface, the return interval is fixed at 4 seconds and cannot be adjusted to 1–2 seconds. Cause: The streaming return interval parameter was not configured correctly, and the platform's default general interval threshold was used.
- Scenario: When calling an external system interface, a `do request failed` error is returned, with a status code of 502 or 503. Cause: A reasonable request timeout duration was not set, or the external system was temporarily unavailable and the retry mechanism was not enabled.
- Scenario: No expected knowledge base index is generated after creating a training order, and the function for adding data to collections is confused with this operation. Cause: The applicable scenarios of the two operations were not clearly distinguished. Creating a training order is used for batch index generation for large files, while adding data to collections only applies to single short texts.

## How to confirm configurations are correct
- Verify the format of the `Authorization` parameter before calling the interface, confirming it matches the application key generated by the platform.
- Test document requests of different lengths, confirming that the interface does not trigger content truncation or request overflow.
- Simulate a scenario where an external system is temporarily unavailable, confirming that the interface triggers the retry mechanism and returns valid results.
- View the `responseData` field returned by the interface, confirming that it includes all full business information required for review.

The values provided are common starting points and should be measured against the reader's own samples.
