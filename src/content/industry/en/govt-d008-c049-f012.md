# Business Process Guidance for Legality Review of Normative Documents: Deployment and Upgrade

## What the data for this category looks like
This category processes data from regulatory and rule repositories, higher-level law databases, departmental policy document repositories, and administrative normative document filing systems. Daily processed documents include normative document drafts, drafting explanations, legality review opinions, solicited opinion summaries, and filing reports. Data updates have no fixed cycle, and are triggered by policy formulation and filing processes. Data fields focus on document formulation authority, article content, and review workflows. No custom units are required, and core fields are all text type.

## What constraints these characteristics impose during the Deployment and Upgrade phase
Most data sources are official authoritative databases. When deploying, configure trusted external data source access permissions, and adapt to connection protocols for different databases. Data updates have no fixed cycle. During upgrades, retain incremental synchronization configurations to avoid interrupting review workflows. Daily document structures are fixed but have many fields. When deploying, preset corresponding data parsing templates to avoid field matching errors. Documents involved in reviews have high compliance requirements. During deployment, strictly configure access controls to prevent unauthorized document tampering.

## How to set configurations
| Configuration Item | Recommended Value | Rationale for This Setting |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://username:password@host:port/database?authSource=admin` | Adapts to document storage needs for normative document review. Correct authentication source configuration ensures data access security |
| `REDIS_URL` | `redis://:password@host:port/0` | Used to cache review results and frequently accessed regulatory data. The default database 0 avoids conflicts with other business caches |
| `STORAGE_S3_ENDPOINT` | `Fill in according to the object storage service address of the deployment environment` | Used to store attachments such as normative document drafts and review opinions. Must match the storage endpoint of local or cloud service providers |
| `DB_MAX_LINK` | `20–30` | Adapts to concurrent scenarios where multiple departments submit review requests. Prevents database response timeouts caused by excessive connection counts |
| `ROOT_KEY` | `Generate a high-strength random string through actual testing` | Used for system administrator permission verification. Avoid weak passwords to ensure background configuration security |

*Note: This document applies to FastGPT v4.17.0*

## Three Common Mistakes
- Phenomenon: A connection timeout prompt appears when connecting to the database. Logs show IP access was denied. Cause: The public IP of the FastGPT deployment server was not added to the whitelist configuration of the database instance, so the database rejected external access requests.
- Phenomenon: After upgrading to the specified version, the system still attempts to read the `config.json` file and throws an error. Cause: Residual configuration from old version startup scripts was not fully cleaned up, or the official guide for switching to environment variable configuration was not followed.
- Phenomenon: The version number displayed after local deployment does not match the downloaded version. Cause: The correct tag or branch was not specified when cloning the repository, and old branch code was pulled by default.

## How to Confirm Configuration is Complete
- Execute the database connection test script to verify connectivity for the `MONGODB_URI` and `REDIS_URL` configurations. Confirm there are no authentication or address errors.
- Upload a test normative document draft to trigger the review process. Check if the system can normally pull associated regulatory data.
- View the system backend running logs. Confirm there are no error messages such as database connection failures or storage permission exceptions.
- Attempt to use the `ROOT_KEY` to complete administrator permission verification. Confirm the configuration takes effect normally.
