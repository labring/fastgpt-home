# Business Process Guidance for Department Final Accounts and Financial Reports: Tool Calling and Plugins

## What data does this category include
Data for this category comes from the budget management integrated system, centralized treasury payment system, accounting system, and asset management system. The update frequency is once per year. Daily output documents include department final account statements, balance sheets, income and expenditure final account statements, final account explanations, and government financial reports. Fields cover revenue and expenditure details, asset and liability balances, budget execution difference explanations, and more. Units are based on Chinese renminbi yuan. Standardized business fields such as unit hierarchy and project code are included.

## What constraints do these characteristics impose on the tool calling and plugins link
The annual update feature means tool calls do not need to be triggered frequently, and only need to be called on demand during the annual final account cycle. Multi-source data sources require plugins to adapt to the database connection format of each system to avoid cross-system data alignment errors. The complex document structure includes multiple statements and explanations, so tool calls need to accurately match the dedicated fields of each statement, while supporting batch processing of multiple documents. The highly time-consuming account statement verification link requires plugins to support batch SQL execution and result comparison, and strictly verify the caliber consistency of returned data to prevent statement returns caused by format deviations.

## Configuration guidelines
This configuration is based on FastGPT v4.17.0. Specific configuration items and their rationales are as follows:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapts to multi-step final account process guidance, automatically selects appropriate tools for data query, verification and aggregation |
| `functionCall` | Enabled | Supports structured output of statement verification results to facilitate subsequent difference analysis and reporting |
| Data source plugin adaptation | Configured according to the JDBC connection format of each system | Adapts to database access for systems such as budget management integrated system, enabling cross-system data pulling |
| Call timeout | 600 seconds | Covers time requirements for cross-system data pulling and batch statement processing |
| Batch processing limit | First 10 subordinate unit statements | Adapts to annual final account aggregation processes, avoiding overload from single processing |
| Dynamic parameter binding | Enable token dynamic replacement | Adapts to permission verification requirements for external interface calls, avoiding fixed token expiration issues |

## Three common misconfigurations
- Plugin returns database connection metadata but no SQL execution results: The plugin output includes table structures and field lists but no actual business data. This occurs when SQL execution configuration for the plugin is not enabled, and only basic data source connectivity verification is completed.
- External interface call returns 401 Unauthorized error: A permission insufficient prompt is returned when calling centralized treasury payment system interfaces. This occurs when dynamic parameter binding is not configured in the workflow, and fixed expired token values are used.
- Model call returns 422 error code: The interface prompts a request format error when configuring `deepseek R1` API calls. This occurs when the request body parameter structure is not configured as required, and required fields are missing.

## How to confirm successful configuration
- Trigger a final account statement data pull, check if the plugin return result includes actual revenue and expenditure data for the specified statement, with no unrelated table structure information returned.
- Test dynamic parameter binding in the workflow, pass a test token to call external interfaces, confirm normal business data is returned with no permission errors.
- Call the `deepseek R1` model, check if request headers and parameter formats meet API documentation requirements, confirm no 422 errors are returned.
- Perform batch processing of subordinate unit statements, confirm single processing quantity matches the configured limit, with no overload errors returned.
