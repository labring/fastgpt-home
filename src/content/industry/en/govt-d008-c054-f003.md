# Business Process Guidance for Flood and Disaster Prevention and Emergency Duty: Multi-turn Dialogue and Prompt Engineering

## What the data for this use case looks like
Typical data sources include meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Data updates daily. Daily documents include duty logs, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Data fields include rainfall amount, flow rate, disaster severity level, material quantity, number of displaced people, with corresponding units such as millimeters, cubic meters per second, and number of people.

## Constraints for multi-turn dialogue and prompt engineering
The daily update feature of multi-source real-time data requires multi-turn dialogue to pull latest data in real time. Avoid using expired information. Diverse document structures require prompts to handle structured and unstructured content differently. Cross-departmental scheduling business logic requires the `messages` context to retain departmental input and feedback from each stage. Severe error consequences require strict control of context window size to avoid redundant or incorrect model outputs. Monitor token consumption to comply with model limits. ## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `messages` context retention rounds | Top 10 rounds | Covers key communication stages of emergency response, avoids context overload |
| Maximum context window | 8000–12000 characters | Meets requirements for multi-turn dialogue and real-time data splicing |
| `variables` data binding rules | Bind real-time rainfall and hydrological fields | Automatically pulls latest monitoring data to populate prompts |
| Token statistics configuration | Enable input and output statistics | Facilitates monitoring token consumption to avoid exceeding model limits |
| Timeout threshold | 600 seconds | Accommodates longer business processes such as consultations and disaster summary |

## Three common configuration mistakes
- Closing the AI chat window still results in conversation text being output. The cause is that the context isolation rule for `chatId` is not configured correctly, leading to residual cross-dialogue data.
- Using Markdown formatting in prompts produces plain text output. The cause is that the prompt rendering switch is not enabled, or the bound `variables` data does not properly escape Markdown syntax.
- Unable to query required data after starting a conversation. The cause is that the context window is set too small and does not include key historical dialogue or real-time data, or the data binding field configuration is incorrect.

## How to verify correct configuration
- Initiate a simulated test conversation, enter a rainfall query request, and check if the returned results automatically populate the latest monitoring data.
- View the conversation log, confirm that the `messages` list saves complete multi-turn interaction records without redundant data.
- Check the in-page token statistics module, confirm that input and output token counts are displayed separately, with no abnormal consumption.
- Simulate a longer business process, verify that the conversation completes a response within 600 seconds without timeout errors.
