# Business Process Guidance for Flood Control, Disaster Prevention and Emergency Duty: Workflow Orchestration

## What this category of data looks like
The data sources for this category are meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. The update frequency is daily. Commonly processed documents include duty logs, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material transfer orders. Common data fields include rainfall and water level parameters, danger level markers, material stock and transfer quantities, and resettlement numbers. Data is stored in a structured format only for business scenarios, with no unified mandatory statistical standards.

## Constraints on Workflow Orchestration
Dispersed data sources, mostly accessed via real-time system interfaces, require workflows to support parallel calls to multiple data sources to avoid response delays caused by serial calls.
The standard update frequency is daily, but temporary updates may be triggered in emergency scenarios. Node trigger logic must be configured to support on-demand execution to meet rapid processing needs for sudden disasters.
Diverse document types with large field differences require configuring unified data parsing nodes in the workflow to adapt to materials in different formats such as duty logs and warning notices.
Cross-departmental scheduling needs require workflows to support permission verification and data transfer between nodes, ensuring sensitive information is only transmitted in authorized links.

## Configuration Settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Preset two types of global variables: rainfall threshold and material transfer limit | Adapt to fixed rules for disaster response, support cross-node calls to unified parameters, and avoid repeated configuration |
| `nodeId` | Assign a unique identifier to each system access node | Facilitate locating problematic nodes during exception troubleshooting, and meet the needs of sorting out links for parallel calls to multiple data sources |
| Batch execution node | Process 8-12 sub-items per single execution | Adapt to the batch reporting scale of grassroots disaster reporting systems, and avoid triggering interface rate limiting rules |
| Error capture configuration | Capture two types of exceptions: 429 status code and node timeout | Correspond to common error scenarios in tool calls, and meet the rapid fault tolerance needs of emergency scenarios |
| Trigger rule | Support both scheduled execution and manual trigger modes | Meet the needs of both fixed updates for daily duty and temporary processing for sudden disasters |

## Three Common Configuration Errors
- A 429 Request rate increased too quickly error occurs in tool call nodes. The cause is that the sub-item quantity limit of the batch execution node is not configured, resulting in too many interface requests being initiated in a short period of time.
- The batch execution results within the loop node cannot be passed outside the node. The cause is that the append logic for global variables is not configured via `variables`, and only single-use variables are used, resulting in data being overwritten.
- No exception handling process is triggered after a node error occurs. The cause is that no error capture node is mounted in the workflow, making it impossible to capture exception states from model requests or interface calls.

## How to Verify the Configuration Is Complete
- Trigger a test workflow once, check whether the return data of each data source node matches the real-time data of the corresponding system, and confirm that the access logic is normal.
- Simulate batch submission of sub-item tasks, observe whether the processing results of the batch execution node are split and executed according to the configuration, and confirm that the node configuration matches the business scale.
- Manually trigger an error scenario, such as disconnecting the test interface of a certain data source, and confirm whether the error capture node triggers the corresponding processing process according to the configuration.
- View the storage logs of global variables, confirm whether the sub-item results in the loop node are appended to `variables` according to the rules, and there is no data overwriting.
