# Business Process Guidance for Flood Control, Disaster Prevention and Emergency Duty: Model Access and Configuration

This documentation applies to FastGPT v4.17.0 for model access and configuration.

## What data in this category looks like
Data for this category primarily comes from meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Daily stored documents include duty logs, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Data updates follow a daily cycle, with some real-time warning data synchronized at high frequency. Document fields include rainfall and water level values, warning levels, affected areas, material stock levels, personnel transfer records, and other relevant fields, with dedicated units such as millimeters, cubic meters per second, and number of people.

## What constraints do these characteristics impose on the "model access and configuration" link
Multi-source and heterogeneous data sources require configuring access rules compatible with different interface formats to avoid data parsing errors. High-frequency updated real-time warning and disaster data requires adapting model context length to short-cycle business scenarios, to avoid interference from expired data in decision-making. The presence of specialized fields and units requires configuring model adaptation rules for professional terminology recognition, to ensure accurate understanding of professional content such as rainfall and water conditions. Cross-departmental dispatch business requirements require tool call response delays to meet the real-time needs of emergency response, to avoid process lag.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the multi-source data aggregation needs of flood control operations, avoiding truncation of key consultation minutes and rapid disaster report content |
| `maxTokens` | 4000–6000 token | Meets the generation needs of long texts such as emergency response plans and material allocation slips, while controlling single inference costs |
| `toolChoice` | auto | Supports automatic invocation of hydrological and meteorological related tools, adapting to the business scenario of real-time warning response |
| `temperature` | 0.2–0.4 | Reduces random output, ensuring strict and accurate expression of warning information and dispatch instructions |
| `AIPROXY_API_ENDPOINT` | Fill in according to the actual access address of the deployment platform | Adapts to the call paths of different model services, ensuring interface connectivity |
| `AIPROXY_API_TOKEN` | Fill in according to the key allocated by the platform | Completes identity verification, avoiding access denied issues |

## Three common configuration errors
- Symptom: An access denied prompt appears when configuring model access, and no such issue occurs when using other platform access. Cause: `AIPROXY_API_TOKEN` or `AIPROXY_API_ENDPOINT` path parameters are not configured correctly, leading to identity verification failure or abnormal interface calls.
- Symptom: When using the Qwen3 model, it is impossible to restrict the model from using inference mode, and the output content deviates from business requirements. Cause: The `toolChoice` parameter is not configured correctly, or the trigger rule for prohibiting inference mode is not specified, causing the model to enable the inference link by default.
- Symptom: When repeatedly configuring the `Qwen/Qwen3-Embedding-8B` embedding model, the original configuration is overwritten, and multiple embedding models with the same name cannot be used simultaneously. Cause: A unique identifier is not configured for each embedding model. The platform uses the model name as the default unique key, resulting in overwriting of configurations with the same name.

## How to verify a successful configuration
- Call the test interface, input simulated rainfall data and rapid disaster reports, and check whether the model can correctly recognize professional fields and units.
- View the interface log, confirm that the call requests for `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` return normal status codes, with no identity verification errors.
- Test multi-round conversation scenarios, check whether the `maxContext` parameter can retain key content from multi-round consultation minutes, with no truncation occurring.
- Try adding embedding models with different identifiers, confirm that the configuration will not be overwritten by models with the same name, and ensure each model has an independent configuration item.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
