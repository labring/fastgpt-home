# Business Process Guidance for Flood Prevention, Disaster Mitigation and Emergency Duty: Deployment and Upgrade

## What this category of data looks like
Data for this category originates primarily from weather warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. The update frequency is daily.
Commonly processed documents include duty logs, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips.
Data fields cover rainfall and water level values, disaster location coordinates, material types and quantities, lists of evacuated and transferred personnel, and other relevant details. Some documents require association with real-time monitoring timestamps and regional codes. The primary format is a mix of structured reports and unstructured text.

## Constraints Imposed on Deployment and Upgrade
The multi-source mixed data characteristics of this category require the deployment phase to adapt to the interface formats of different systems. Storage parameters such as `STORAGE_S3_ENDPOINT` must be configured in advance to unify access to monitoring data from multiple sources.
The daily data update rhythm requires reserving a data synchronization window during the upgrade phase, to avoid performing version updates during peak business hours.
The diversity and real-time requirements of document fields require differentiating processing logic for structured reports and unstructured text during knowledge base configuration. Permission configurations must also cover the access scope of cross-department collaboration, to prevent sensitive disaster data leaks.
This guide applies to FastGPT v4.17.0.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `STORAGE_S3_ENDPOINT` | Address of the storage node corresponding to the internal hydrological/meteorological system | Adapts to the unified storage requirements of multi-source monitoring data, ensuring disaster data from different systems can be synced and accessed |
| `REDIS_URL` | `redis://:custom password@internal server IP:6379/0` | Supports cached reading of real-time warning notifications, ensuring low-latency response in emergency scenarios |
| `DB_MAX_LINK` | `200` | Handles batch write requests from large volumes of daily rapid disaster reports and consultation minutes, preventing database connection exhaustion |
| `MONGODB_URI` | Connection address of the internally deployed MongoDB instance | Stores unstructured documents such as consultation minutes and response plans, adapting to query requirements for semi-structured data |
| `ROOT_KEY` | Random string generated by the internal permission management system | Restricts access to background management, preventing unauthorized personnel from modifying core emergency duty configurations |
| `FE_DOMAIN` | FastGPT frontend access domain specified on the government intranet | Limits frontend access scope, complying with the security isolation requirements of the government intranet |

## Three Common Configuration Mistakes
- Symptom: An `Error response from daemon: Get https://registry-1.docker.io/v2/: net/` error is returned when executing `docker pull` to pull the FastGPT image. Cause: No internal mirror source is configured, or government extranet access permissions are not enabled, preventing official image retrieval.
- Symptom: A permission error is returned when testing the configured local DeepSeek model in FastGPT. Cause: The model access key is not correctly configured in `config.json`, or the API port of the local model is not granted intranet access permissions.
- Symptom: Missing fields appear after the knowledge base synchronizes disaster data. Cause: No dedicated field mapping rules are configured for structured reports from hydrological and meteorological systems, leading to failure to correctly recognize some data fields.

## How to Verify Successful Configuration
- Log in to the FastGPT background management page, check whether storage configuration items such as `STORAGE_S3_ENDPOINT` match the storage nodes of internal monitoring systems. Manually upload a test rapid disaster report document to verify the synchronization function.
- Execute a model test request in the intranet environment, confirm that the configured local model can return normal responses without permission or connection timeout errors.
- View the knowledge base synchronization logs, confirm that daily rainfall and water level data can be automatically synchronized according to preset rules, with no connection failure or field parsing exception records.
- Check whether the frontend access domain `FE_DOMAIN` can be opened normally in the intranet environment, and only allows access from authorized IP ranges.

The values provided are common starting points and should be measured against the reader's own samples.
