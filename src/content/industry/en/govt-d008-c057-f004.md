# Business Process Guidance for Food Safety Supervision and Sampling Inspection: Workflow Orchestration

FastGPT v4.17.0

## What data for this category looks like
Core data for this category comes from the food safety sampling and monitoring system, the national market supervision administration sampling results inquiry system, the laboratory information management system (LIMS) of inspection institutions, and the account books of food producers and operators. Daily processed documents include sampling plans, sampling slips, inspection reports, non-compliant food verification and disposal reports, and risk control announcements. Data is updated monthly. Core fields include sampling number, inspection items, non-compliance determination results, disposal progress, and more. Participating entities include the food sampling division of the market supervision bureau, inspection institutions, grassroots supervision institutes, and food producers and operators. Data flow covers the entire process of sampling, inspection, and disposal.

## What constraints these characteristics impose on workflow orchestration
The monthly update frequency requires the workflow to adapt to the trigger logic of periodic sampling tasks, and must be bound to the global variables of the monthly plan. The multi-source data system requires workflow nodes to support interfacing with different systems, to automatically pull and verify documents such as sampling slips and inspection reports. Core links rely on laboratory inspection reports as evidence, so a separate report compliance verification node must be set up to prevent non-compliant data from entering subsequent processes. The division of labor differences among participating entities requires the workflow to set permission nodes for different roles, to adapt to the different operational needs of grassroots supervision institutes and inspection institutions. The serious consequences of errors require configuring exception trigger branches, which automatically jump to the verification and disposal link when non-compliant reports are detected.

## Configuration settings
| Configuration Item | Recommended Setting | Rationale for This Setting |
| --- | --- | --- |
| `variables` | `{"globalCycle": "1 month", "coreFields": ["sampleId", "reportResult"]}` | Adapts to the monthly business rhythm, marks core circulation fields |
| `nodeId` | `"sampleVerify": "node_002", "reportCheck": "node_003", "disposeTrigger": "node_005"` | Fixes the node IDs of core links to facilitate sub-process association and exception jumps |
| Global variable sharing settings | Bind all sub-processes to the `variables` configuration of the main process | Ensure that core fields such as sampling slip number and inspection report ID are unified across the entire process |
| Large model token management | Allocate 1000 token quota for each large model node | Differentiate token consumption across different links such as sampling prompts, report interpretation, and disposal notifications |
| Timeout threshold | `300 seconds` | Adapts to the conventional response time of inspection report pulling and LIMS data return |
| Exception trigger configuration | Non-compliant report fields trigger the verification and disposal sub-process | Avoid the risk of non-compliant food continuing to circulate |

## Three common mistakes
- Phenomenon: Sub-processes cannot read the sampling slip number field passed by the main process. Cause: The `variables` configuration of the main process was not synchronized to the parameter binding items of the sub-process.
- Phenomenon: Token consumption of multiple large model nodes is counted together, exceeding the single-node quota and causing call failures. Cause: Independent token management rules were not configured for each large model node in each link.
- Phenomenon: The process fails to complete the inspection report verification within the preset time after startup. Cause: A reasonable timeout threshold was not configured for LIMS data return, or the completeness of required fields in returned data was not verified.

## How to verify correct configuration
- Access the workflow editing page, view the `variables` configuration item, and confirm that the global variables include core fields such as sampling plan number and sampling slip ID.
- Associate the sub-process node, check whether the global variable parameters of the main process have been bound, and trigger a test process to verify that field transfer is normal.
- Configure the token rules for large model nodes, test the call of each node separately, and confirm that token consumption is counted independently.
- Simulate the scenario of a non-compliant report, trigger the process, and confirm that the verification and disposal sub-process starts normally.

The values provided are common starting points and should be evaluated against available samples.
