# Survey and Design Business Process Guidance: Tool Calling and Plugins

## What data looks like for this category
Survey and design data primarily originates from full-cycle project survey reports, construction drawing design documents, and project management ledgers. Data updates align with project progress, with triggers occurring during the preliminary survey, detailed survey, and construction drawing issuance stages. Individual documents contain structured fields including project number, survey point coordinates, geotechnical mechanical parameters (units: kPa, m), design load limits, drawing version numbers, and change records. Some drawing-type documents must be transcribed into structured text before being added to the knowledge base.

## Constraints on tool calling and plugin workflows from these characteristics
Survey and design data characteristics impose constraints on tool calling and plugin configuration across three dimensions. First, geotechnical parameters include professional units such as kPa and m. Unit validation logic must be built into tool calls to prevent parsing errors. Second, individual structured documents or transcribed drawing text can be lengthy. Tool calls must limit the length of valid data fragments returned in a single call to avoid context overflow. Third, project data is dynamically updated alongside survey and design phases. Tool calls must be linked to the latest version identifier of the project ledger to prevent calling outdated survey or design parameters.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | Adapts to the need for automatic scheduling of multiple tools in survey and design scenarios |
| `functionCall` | `[{"name":"query_geotechnical_param"},{"name":"query_design_load"}]` | Binds dedicated geotechnical parameter query and design load query tools for survey and design use cases |
| Single tool call return length | 800–1200 characters | Matches the typical valid fragment length of a single parameter document for survey and design projects |
| Tool call timeout threshold | 60 seconds | Covers most scenario durations for cross-project ledger retrieval |
| Plugin cache validity period | 7 days | Matches the phase update cycle of survey and design projects |

## Three common configuration errors
- Phenomenon: The survey data fragment returned by a tool call is excessively long, triggering context overflow, and the reranking model is not activated. Cause: The length of text returned by a single tool call is not limited, exceeding the system context upper limit.
- Phenomenon: The console reports the error "400 Messages with role 'tool' must be a response to a preceding message". Cause: The tool call reply does not immediately follow the corresponding user question, or a gap exists in the tool call sequence.
- Phenomenon: Geospatial plugins cannot be called to obtain survey point coordinates. Cause: Dedicated calling rules for the corresponding plugin are not bound, or the plugin configuration is not linked to the point data fields for survey and design.

## How to verify correct configuration
- Initiate a test query that includes a geotechnical parameter lookup, and check whether the return value of `toolChoice` in the tool call log matches the preset configuration.
- Review the text length of the tool call return, confirm whether it falls within the preset range, and adjust parameters based on actual test results.
- After triggering a tool call, check the console for the specified tool call error. No errors indicate the configuration meets requirements.
- Verify the call result of the geospatial plugin, confirm that the returned survey point coordinates match the data stored in the project ledger.

The values provided here are common starting points and should be measured against the reader's own samples.
