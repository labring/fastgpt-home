# Business Process Guidance for Fertilizer and Pesticide: Workflow Orchestration

## What the Data for This Category Looks Like
Business data for fertilizers and pesticides mainly comes from the agricultural product supervision and filing platform, enterprise production ledgers, pesticide registration databases, and fertilizer quality inspection reports. Data updates trigger immediately when a business approval node is completed, with no unified fixed cycle. Document structures primarily use structured tables, including fields such as registration certificate number, active ingredient content, production batch, and implementation standard. Some fields have fixed units: active ingredient content uses % or g/L, production batch is a string combining letters and numbers, and filing numbers are fixed-length unique identifiers.

## What Constraints Do These Characteristics Impose on Workflow Orchestration
The table-dominated document structure requires the workflow’s document parsing node to prioritize table recognition, and avoid general chunking that breaks field association relationships. Fields with fixed units require the workflow to add a unit verification step to prevent input values from mismatching required units. The real-time data update triggered by approvals requires the workflow to configure a regular data source pull step to maintain data timeliness. The unique filing number requires the workflow to bind the corresponding field via `nodeId` to ensure accurate data matching and avoid cross-category data confusion. Additionally, compliance requirements for agricultural data require the workflow to filter sensitive fields, and only expose necessary business information for invocation.

## How to Configure Settings
| Configuration Item | Recommended Approach | Basis for This Approach |
|---|---|---|
| `variables` | `{"registration_code": "", "batch_number": "", "nutrient_content": ""}` | Matches core identifiers and business fields for fertilizer and pesticide filings, to simplify workflow node calls |
| Document Parsing Mode | Table-first recognition | Most category data uses structured table documents, which preserves field association relationships |
| `nodeId` | Bind to the filing number field | Fertilizer and pesticide registration certificate numbers are unique business identifiers, ensuring accurate data matching |
| Regular Pull Cycle | Every 12 hours | Agricultural product filing data changes with approvals; regular pulling maintains data timeliness |
| File Upload Limit | Maximum 1000 MB per file | Fertilizer and pesticide inspection reports are typically high-definition scanned documents or large ledger files |
| Field Verification Rules | Verify against national standard implementation standards | Category data requires strict alignment with industry standards to prevent invalid data from entering the workflow |

## Three Common Configuration Errors
- Issue: The workflow throws an error after enabling the file upload node and running. Cause: The `CUSTOM_READ_FILE_URL` environment variable is not configured to point to the local file storage path, so uploaded fertilizer and pesticide inspection report files cannot be read.
- Issue: The workflow returns invalid data after parsing a ledger file. Cause: Table-first recognition mode is not enabled, and general text chunking splits structured filing fields, causing loss of association between fields such as active ingredient content and production batch.
- Issue: Workflow nodes cannot access category-specific data. Cause: The `nodeId` is not bound to the filing number field, so the model cannot match registration information for the corresponding category.

## How to Verify Correct Configuration
The following verification steps are performed on FastGPT v4.17.0:
- Log in to the FastGPT backend, view the workflow’s `variables` configuration, and confirm that core fields including fertilizer and pesticide filing numbers and active ingredient content are bound.
- Upload a standard fertilizer inspection report, run the workflow, and check the parsing results to confirm that table fields are fully recognized with no format errors.
- Manually trigger the regular pull task, and check if the data source node successfully pulls the latest filing data without abnormal errors.
- Test the file upload function: upload a ledger file not exceeding 1000 MB, confirm no errors occur and the file is read normally.
