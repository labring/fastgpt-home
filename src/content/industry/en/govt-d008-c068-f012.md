# Business Process Guidance for Pharmaceutical Distribution: Deployment and Upgrade

## What the data for this category looks like
Pharmaceutical distribution business data primarily comes from internal enterprise inventory, sales and procurement systems, drug regulatory authority filing platforms, logistics waybill systems, and business qualification documents. Data updates trigger per business batch. A single processing flow updates documents once per batch, while routine qualification data syncs every 30 days. Individual business documents include fields such as generic drug name, approval number, distribution batch number, processing node status, and handler ID. Units include piece, box, batch validity period (days), and business qualification number. Some documents use structured table format, while others are text transcribed from scanned documents.

## What constraints these characteristics impose on the deployment and upgrade phase
Pharmaceutical distribution business data contains multi-source structured and unstructured content, and involves sensitive information such as business qualifications and distribution batches. As a result, the deployment phase must prioritize data storage isolation. Frequent batch updates require vector index incremental synchronization mechanisms to adapt to short-cycle refreshes, preventing data lag from reducing the accuracy of process guidance. Different document formats also require dedicated parsing rules. The upgrade phase must maintain compatibility with the interface formats of original data sources to avoid interrupting business processing. Additionally, compliance requirements for pharmaceutical distribution data mandate that deployment environments meet industry data storage standards, so configuration must prioritize local storage or compliant cloud storage options.

## How to configure the settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | Local deployment dedicated instance connection string, configured with read-write separation nodes | Pharmaceutical distribution data includes high-frequency write business documents and static qualification data; read-write separation reduces query latency |
| `REDIS_URL` | Local cache instance with 1000 MB memory specification | Used to cache frequently queried drug qualification and processing node data, avoiding repeated calls to external systems |
| `PG_URL` | Local relational database connection string, configured with a maximum connection pool size of 20 | Stores structured business processing flow node data; the connection pool adapts to concurrent windowed processing scenarios |
| `STORAGE_S3_ENDPOINT` | Compliant local object storage service address | Adapts to storage compliance requirements for pharmaceutical distribution data, ensuring local storage permissions for sensitive business documents |
| `ROOT_KEY` | Randomly generated 32-bit string, injected via environment variables | Used to manage the highest-privilege access to the system, avoiding security risks from hardcoding |
| `FILE_TOKEN_KEY` | Encryption key matching the storage service | Used to encrypt access tokens for business documents, preventing unauthorized access to sensitive documents |

## Three common configuration errors
- Phenomenon: A `502 Bad Gateway` error appears after startup, and the knowledge base list fails to load in the interface. Cause: `REDIS_URL` is not configured correctly, causing the cache service to fail to connect and leading to timeout of high-frequency business data queries.
- Phenomenon: After migrating the knowledge base to the local environment, the parsing results of original business documents are empty. Cause: The `STORAGE_S3_ENDPOINT` configuration was not updated synchronously, making it impossible to read pharmaceutical distribution document files from the original storage.
- Phenomenon: After running the upgrade script, the system cannot start the business process guidance function. Cause: `ROOT_KEY` was not injected via environment variables, and the default hardcoded value was used directly, triggering permission verification failure.

## How to confirm the configuration is correct
- Run the environment variable print command to confirm that configuration items such as `ROOT_KEY` and `MONGODB_URI` have been correctly injected. This document applies to FastGPT v4.17.0.
- Send a simulated business document upload request to check whether the storage service receives the request normally and returns a valid file access link.
- Start the cache service health check script to confirm that the cache instance configured via `REDIS_URL` can read and write data normally.
- After running the upgrade script, check the system logs to confirm that there are no error messages about missing configuration items or failed permission verification.
