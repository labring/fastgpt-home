# Business Process Guidance for Hazardous Chemical Storage and Transportation: HTTP Interfaces and External Systems

## What data for this category looks like
Business process data for hazardous chemical storage and transportation originates primarily from internal enterprise storage and transportation management systems, compliance approval platforms of local emergency management departments, and third-party hazardous chemical traceability platforms. Data update frequencies fall into three categories: approval documents are generated in real time, storage and transportation ledgers are updated daily, and regulatory verification data is pulled in weekly batches. The document structure includes fixed fields: approval number, common hazardous chemical name, packaging specification, total storage and transportation volume, departure location, destination, approval validity period, and list of compliance verification items. Most field units use industrial standard measurements such as tons, cubic meters, and hours.

## What constraints these characteristics impose on HTTP interfaces and external systems
Real-time approval document pulling requires interfaces to support short polling configurations with millisecond-level response times, or webhook modes with callback authentication. Daily updated storage and transportation ledgers have large data volumes, so interfaces must support pagination query parameters to avoid overloading responses with single requests. Weekly batch regulatory verification data requires interfaces to support request formats for pulling data in batches by time range. Additionally, fields include fixed units. Interface request parameters must strictly match preset field names, and carry unit verification logic to prevent data format incompatibilities.

## Configuration Settings

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {enterprise-specific compliance authentication token}` | Hazardous chemical storage and transportation data involves regulatory compliance. Standard Bearer tokens are used for identity authentication to secure data access |
| `variables` | Set to `{"query_type": "approval", "time_range": "7d"}`, adjusted based on actual testing | Used to pass business type and time range parameters to external interfaces, matching the pulling format for hazardous chemical storage and transportation regulatory data |
| `responseData` | Extract fields `data.approval_status, data.compliance_check` | Only return approval status and compliance results required for business process guidance, filter non-essential fields to improve interface processing efficiency |
| Single request data limit | `Top 500 entries` | Prevent excessive single response data from causing interface timeouts, adapt to the typical data volume of hazardous chemical storage and transportation ledgers |
| Request timeout period | `30-60 seconds` | Reserve sufficient response time when pulling weekly batch regulatory data, prevent failures caused by data transmission delays |
| Retry trigger condition | Trigger only when status code is `500` or `503` | Match common abnormal return types of hazardous chemical regulatory interfaces, avoid ineffective retries |

## Three Common Configuration Errors
- Symptom: A 401 Unauthorized status code is returned when executing a curl command to call the interface. Cause: The `Authorization` parameter is not configured correctly, or the used authentication token does not have permission to access hazardous chemical data.
- Symptom: Compliance verification result fields are missing from the interface response, and corresponding prompt content cannot be displayed in the business process guidance. Cause: The complete field extraction path is not specified in the `responseData` configuration, resulting in filtering of necessary business data.
- Symptom: Request timeout errors occur when pulling weekly batch regulatory data. Cause: The single request data limit is set too high, exceeding the single return limit of the external interface, and not adapting to the batch pulling requirements of hazardous chemical storage and transportation data.

## How to Confirm Configurations Are Properly Set
- The preset authentication token is entered into the FastGPT interface debugging panel, a test request is executed, and the return status code is confirmed to be 200.
- The original interface response data is reviewed, and core fields such as approval number and compliance verification items required for business processing are confirmed to be included.
- A batch data pulling request is simulated, and the returned data volume is confirmed to meet the preset single request data limit.
- An abnormal request is triggered (such as using an expired token), the interface is confirmed to return the corresponding error status code, and the authentication logic is verified to be functional.
