# Business Process Guidance for State-owned Asset Management Companies: HTTP APIs and External Systems
Reference only; verify against the target FastGPT release and deployment documentation.

## What This Category of Data Looks Like
Business processing data for state-owned asset management companies is primarily sourced from the state-owned asset supervision reporting system, internal asset ledger, and approval workflow system. Data updates fall into two categories: real-time push for asset ownership and status changes, and monthly batch updates of aggregated business data per natural month. Each individual business document includes the unique asset identifier, affiliated group entity, current processing node, approval circulation records, and deadline field. The deadline is measured in natural days, and the approval status uses a fixed enumeration format.

## What Constraints Do These Characteristics Impose on HTTP APIs and External Systems
Real-time change data requires APIs to support millisecond-level response times to avoid business workflow lag. Large monthly batch data transfers require configuring reasonable request sharding thresholds. Enumerated approval status fields require external system return values to exactly match FastGPT’s preset enumerations; otherwise, processing nodes cannot be correctly identified. The unique asset identifier is the core query field, and it must be a required parameter in API requests. Without this parameter, the corresponding business workflow cannot be located. Cross-system calls must comply with the identity authentication rules of the state-owned asset system to prevent API calls from being blocked.

## How to Configure
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {state-owned asset system API key}` | Complies with state-owned asset system identity authentication specifications to avoid call blocking |
| Single request timeout | `30-60 seconds` | Adapts to transfer duration of monthly batch data to avoid mid-transfer timeout interruptions |
| `responseData` parsing rule | Extract `processing node` field first | Quickly locates core steps of current business guidance |
| `variables` passed parameters | `asset ID, deadline` | Covers core query conditions for business processing to improve guidance accuracy |
| Request pagination size | `First 20 items` | Adapts to default pagination limits of state-owned asset system APIs to avoid excessive returned data |
| Failure retry count | `2 times` | Addresses temporary network fluctuations causing call failures to reduce business interruption probability |

## Three Common Misconfigurations
- Phenomenon: API call returns `401 Unauthorized` status code. Cause: `Authorization` parameter not configured as required, or API key expired and not updated in a timely manner.
- Phenomenon: AI-generated business guidance content does not match the actual workflow. Cause: `processing node` field in `responseData` not extracted correctly, with non-core business fields used by mistake.
- Phenomenon: Data crossover occurs in multiple concurrent requests. Cause: Independent request business identifiers not passed via the `variables` parameter, leading to accidental overwriting of global data.

## How to Confirm Configuration Is Complete
- Invoke the test API, review the authentication result to confirm the `Authorization` configuration is active.
- Manually pass the asset ID from the `variables` parameters, verify returned business data matches the corresponding asset’s processing workflow.
- Simulate batch requests, check whether the number of returned data items aligns with preset pagination rules.
- Trigger a temporary network failure simulation to verify the failure retry logic activates normally and restores calls.

All provided configuration values are common starting points, and should be evaluated against the reader’s own sample data.
