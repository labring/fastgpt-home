# Business Process Guidance for Urban Public Transit: Multi-turn Dialogue and Prompt Engineering

## What data for this category looks like
Data sources include internal business systems of urban public transit operators, public transit service guide documents released by the transportation bureau, and official real-time route APIs. Update schedule: route and stop information is synced once per month, while real-time schedule data is pulled every 5 minutes.
Document structure is divided into four modules: route information, card application process, card loss reporting and replacement, complaint and suggestion. Fields include route number, stop sequence, operating start and end time, fare range, card application outlet address, processing time limit, and more. Units include minutes, yuan, kilometers, and others.

## Constraints imposed by these characteristics on the "multi-turn dialogue and prompt engineering" link
First, structured fields have clear definitions and fixed units. Prompts must require responses to use specified units to avoid vague statements.
Second, real-time schedule data must be pulled dynamically. Latest data must be injected via `variables` during multi-turn dialogue to ensure response timeliness.
Third, business processing workflows follow linear steps. Multi-turn dialogue must retain the current process node state. Context management for `messages` should only retain interaction content from the current session, to avoid interference from redundant information.
Fourth, the update frequency is once per month. The knowledge base must be synced regularly. Multi-turn dialogue contexts should not include expired route or outlet information.

## How to configure settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum Context Length | `800–1200 characters` | Urban public transit business processes have multiple steps. This range retains the current process node and previously confirmed information, preventing missed completed steps while avoiding off-topic responses caused by overly long contexts. |
| `messages` | Store conversation history by process node, only retain interaction content from the current branch | Multi-turn dialogue for public transit business processes typically follows a single linear workflow. This configuration ensures coherent context, aligns with `messages` session state management logic, and avoids cross-session information confusion. |
| `variables` | Bind real-time schedule API and card application outlet data interface | Real-time schedule and outlet information for urban public transit must be updated dynamically. Injecting real-time data via `variables` ensures response timeliness, matching real-time query needs for business processing. |
| `chatId` | Bind unique process instance by user session ID | Ensures coherent context for multi-turn dialogue, resolves the issue of needing to start a new session for each conversation, and aligns with continuous interaction requirements. |
| Markdown Output Toggle | Turn off | Responses for business process guidance must be concise and straightforward. Markdown formatting is unnecessary, aligning with daily user usage habits. |
| Single Dialogue Timeout | `60 seconds` | Questions about public transit business processing typically do not require long thinking times. This configuration avoids ineffective waiting and improves dialogue fluency.

## Three common configuration mistakes
- Phenomenon: Historical interaction content cannot be retained after starting a new conversation, requiring repeated notification of the current business type being processed. Cause: `chatId` is not configured to bind the session instance, causing the system to generate an independent context for each conversation.
- Phenomenon: Response content automatically uses Markdown formatting, including bold, lists and other layout elements. Cause: The Markdown output toggle is not turned off, and the prompt does not explicitly require disabling Markdown formatting.
- Phenomenon: Results returned after calling the knowledge base are not displayed directly in the dialogue box, requiring manual viewing via the sidebar. Cause: The direct output logic for dialogue results is not configured, with results incorrectly bound to sidebar components instead of embedded into the main dialogue window as required by the business scenario.

## How to confirm configurations are correct
- Start a multi-turn dialogue, sequentially inquire about route queries, card application process, and loss reporting steps. Confirm that the system retains historical interaction information without requiring repeated questions.
- After configuring `variables` to bind real-time data interfaces, send a schedule query request. Confirm that the returned schedule time matches official real-time data.
- Submit a business processing inquiry. Confirm that the response content uses only plain text without Markdown formatting.
- Start a new session. Confirm that the system automatically generates an independent context that does not mix with content from previous sessions.
