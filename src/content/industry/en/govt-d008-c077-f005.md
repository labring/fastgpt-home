# Business Process Guidance for Urban Public Transit: Tool Calling and Plugins

## What the data for this category looks like
Data related to urban public transit service handling comes from the public transit operation management system of the corresponding city. Core information such as schedules, stops, and ticket service status is updated in real time. The data uses standard JSON structure. Core fields include:
- Route number (string format)
- Full stop name
- Estimated arrival time (ISO 8601 time format)
- Service handling type
- Charging standard (marked in yuan)

## Constraints imposed on tool calling and plugins
Real-time updated transit data requires setting reasonable timeout thresholds for tool calls. This prevents retrieving outdated schedule or ticket information. Fixed-field JSON data requires `functionCall` to predefine parameter templates matching service handling scenarios. This ensures returned data can be parsed correctly. Field naming differs across city transit operation systems. Plugins must configure field mapping rules to align fields returned by external interfaces with parameters required by the service guidance workflow. Transit service handling covers multiple scenarios including ticketing and card services. Tool calling must support switching the set of called interfaces based on service type.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Tool call timeout | 15–30 seconds | Matches the real-time update rhythm of transit data, avoids returning outdated information due to excessive waiting |
| `functionCall` parameter template | Preset fixed fields according to service handling scenarios | Adapts to the fixed JSON structure of transit data, ensures returned results can be parsed by business processes |
| Request retry count | 2 times | Addresses occasional temporary fluctuations in city transit interfaces, reduces call failure probability |
| Plugin authentication method | API key authentication | Complies with general authentication specifications for urban public service interfaces |
| `toolChoice` | auto | Allows the model to automatically select the appropriate tool based on the business scenario, covering multiple transit service needs |
| Batch return limit | First 3 route/stop entries | Avoids excessive data returning that causes context overload, meets the simplicity requirements of service guidance |

## Three common misconfigurations
- Symptom: Calling the public transit service interface returns a 502 status code. The same interface works normally when called in APIFOX. Cause: The FastGPT plugin configuration failed to correctly include the authentication parameters required by the interface in the request header. The gateway blocks the request.
- Symptom: Only a small number of available models load during tool calling. All compatible models cannot be selected. Cause: The plugin's model call range configuration did not grant full interface permissions, or did not correctly associate the model quota required for the business.
- Symptom: Transit data fields returned by tool calling are empty. Complete process guidance cannot be generated. Cause: The field names in the `functionCall` parameter template do not match the fields returned by the external interface. Parsing fails.

## How to verify proper configuration
- Manually trigger a service call in the plugin debugging panel of FastGPT v4.17.0. Verify that the returned data fields match the preset `functionCall` template.
- Check the plugin's call logs. Confirm that configuration items such as request timeout and retry count follow the preset rules.
- Test multiple public transit service scenarios including ticketing and card services. Confirm that `toolChoice` can automatically match the calling interface for the corresponding business.
- Verify the plugin's authentication parameters. Ensure they match the authentication requirements of the external public transit interface.
