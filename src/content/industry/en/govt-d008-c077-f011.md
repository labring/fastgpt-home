# Business Process Guidance for Urban Public Transit: Forms and Interactions

## What this category of data looks like
Data related to urban public transit business processing comes from the bus operation management system, citizen card/public transit card business backend, and line scheduling database. There are two update rhythms for this data: line stops and fare rules are updated irregularly alongside line adjustments, while business data for card applications, top-ups, and abnormal appeals is updated in real time. The document structure uses a structured table, with fields including business processing type, required processing materials, processing channel, review cycle, and completion time limit. Common units are "times", "working days", and "yuan".

## What constraints these characteristics impose on the "forms and interactions" link
Urban public transit data characteristics impose three constraints on the forms and interactions link.
First, options such as lines and processing types must be pulled in real time, and cannot be hard-coded. Hard-coding will lead to information lag when lines are adjusted.
Second, different business processing types correspond to different input fields. Dynamically display `formInput` items based on user selections to avoid form redundancy.
Third, business fields have fixed units and scope limits. Configure input verification rules to prevent users from submitting non-compliant content. Some businesses require uploading credential materials, so file upload capabilities must be adapted. Otherwise, the complete processing flow cannot be completed.

## How to set the configuration

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `formInput` | Configure input fields by business type. Enable the corresponding switch when file upload is supported | Urban public transit business requires collecting materials such as ID cards and payment vouchers. File upload capabilities are required in some scenarios; different processing types correspond to different input items |
| `userSelect` | Configure as single-select mode, pull options in real time from the public transit business backend | Bus lines and processing types are updated irregularly with operations. Hard-coding will cause information lag, and real-time pulling ensures data accuracy |
| Single interaction response duration | 600 seconds | Public transit business processing needs to connect to the backend review system. Some processes require waiting for review results. Reserve sufficient time to avoid timeouts |
| Form conditional rendering rules | Display corresponding `formInput` based on the processing type selected in `userSelect` | Materials required for different public transit businesses vary greatly. Conditional rendering simplifies form complexity |
| Input verification rules | Match the units and scope of business fields. For example, limit top-up amounts to 10-500 yuan | Prevent users from entering content that does not comply with public transit business rules, and reduce subsequent review exceptions |

## Three common mistakes
- Phenomenon: The free version of the form cannot upload payment vouchers or ID photos required for public transit business. A prompt of incomplete fields appears after submission. Cause: The file upload configuration for `formInput` is not enabled. The default `formInput` only supports text input.
- Phenomenon: After selecting a bus line or processing type, the corresponding input fields are not displayed correctly, and redundant blank items appear in the form. Cause: The conditional rendering association rules between `userSelect` and `formInput` are not configured. Fields cannot be dynamically switched based on user selections.
- Phenomenon: A timeout error occurs after waiting more than 300 seconds when submitting the form. Cause: The single interaction response duration is not configured to a value that matches the public transit backend review cycle. The default duration is not sufficient to cover the business process.

## How to confirm the configuration is complete
- Switch between different public transit business processing types, check that the corresponding input fields are displayed correctly, with no redundant or missing items.
- Try uploading image files, confirm that `formInput` supports file upload and can submit normally.
- Simulate form submission, check that the interface call can correctly obtain real-time data from the public transit backend, with no delays or errors.
- Enter content that does not comply with business rules (such as a top-up amount exceeding 500 yuan), confirm that the input verification rules take effect and provide prompts.
