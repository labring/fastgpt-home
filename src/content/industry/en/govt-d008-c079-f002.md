# Business Process Guidance for Urban Gas Services: Vector Models and Indexes

## What the Data for This Category Looks Like
Data related to urban gas service processing comes from official processing guides of gas operation enterprises, offline window forms, and online business system logs. Updates trigger when municipal gas policies are adjusted or processing workflows are optimized. There is no fixed update cycle. A single update covers all process documents for one service item.
Each document has a fixed structure. It includes the service name, processing conditions, required materials (including quantity and format requirements), processing steps, processing time limit, processing location, and consultation channels.
Fields include processing department, link serial number, gas usage area, and others. Units include workdays, square meters, copies, and others.

## What Constraints These Characteristics Impose on Vector Models and Indexing
Fixed document structures and multi-field features require retaining semantic relationships between fields during indexing. Do not break the binding between material lists and corresponding processing steps.
Numeric fields such as processing time limits and gas usage areas require vector models to have encoding capabilities adapted to numeric semantics.
Data sources with no fixed update cycle require indexing to support incremental updates. This reduces resource consumption from full reindexing.
Wide variation in single document length requires flexible adjustment of chunking rules. This adapts to text features of both short and long process workflows.

## How to Set Configurations
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to the average length of urban gas service documents. Avoids breaking the association between processing steps and required materials |
| Overlap Length | 100–200 characters | Retains semantic continuity between adjacent chunks. Prevents breaks in cross-step workflow logic |
| Similarity Threshold | 0.72–0.80 | Filters low-match irrelevant service items. Enables precise matching of user queries for business types |
| `defaultToken` | 8192 | Adapts to the context window upper limit of mainstream embedding models. Avoids truncation of critical process information |
| `maxToken` | 16384 | Meets context integration needs after long document chunking. Covers the semantic scope of complete processing workflows |
| Reranking | Enabled | Performs semantic reranking of recall results. Improves the ability to accurately match user-specific processing needs |

## Three Common Misconfigurations
- Phenomenon: When adding a locally deployed M3E embedding model via Docker, the interface shows a configuration failure prompt or the model fails to load. Cause: The local access port and path of the model are not correctly configured. Local model call permissions are not enabled in FastGPT.
- Phenomenon: After repeatedly adding models with the same name, existing configurations are overwritten. Multiple embedded models of the same type cannot be used at the same time. Cause: The current FastGPT version does not support multi-instance configuration of embedded models with identical names. Set a unique identifier name for each deployed model.
- Phenomenon: After importing gas service data in Excel format, chunks are too large. This leads to insufficient semantic granularity and redundant recall results. Cause: Chunking rules are not adjusted based on the number of fields per Excel data entry. Default chunk parameters do not adapt to the short text characteristics of tabular data.

## How to Verify Proper Configuration
- Upload a single urban gas service processing document. View the chunk preview interface. Confirm that chunk lengths fall within the preset range, and no critical steps are split.
- Initiate a simulated user query, such as "What materials are required for gas service installation". Check the number and matching degree of recall results. Adjust the similarity threshold to a range that meets business requirements.
- Test the incremental update function. Modify a single service document and trigger an update. Confirm that only the modified document is updated, and no full reindexing is initiated.
- View the model call log. Confirm that the `defaultToken` and `maxToken` parameters of the embedding model do not trigger truncation errors. Returned vector dimensions meet expected standards.

The values listed above are common starting points. They should be evaluated against the user’s own samples.
