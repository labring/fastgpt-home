# Business Handling Process Guidance for Urban Investment Platforms: Workflow Orchestration
Reference only; verify against the target FastGPT release and deployment documentation.

## What the data for this category looks like
Business handling data for urban investment platforms mainly comes from in-house government service systems, project ledger databases, citizen complaint ticket platforms, and public resource transaction databases. Data update frequency varies by scenario: daily handling tickets are synced in real time, while project ledgers are updated once per week. Each individual business data entry includes fields such as request number, item type, handling node, required submission material list, statutory handling time limit, and responsible handling department. Most fields are text, array, and time types, with units including working days, items, copies, and others.

## What constraints these characteristics impose on the "workflow orchestration" link
The multi-field and hierarchical structure of business data requires workflows to bind business fields of different nodes via `variables` to avoid parameter confusion. Real-time synced ticket data requires workflow trigger response speed to match business handling timelines; the runtime of individual nodes should not be too long. Array-type material list fields require loop nodes to complete batch verification and submission. Handling nodes vary significantly across different items, so workflows must implement branch jumps based on `nodeId` to adapt to multiple business scenarios. The responsible department field must be bound to a designated approval node to ensure the workflow routes to the corresponding responsible entity.

## How to set configurations
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| Variable Binding | Bind grouped business fields to `variables` | Matches the multi-field hierarchical structure of urban investment business data to avoid parameter confusion |
| Branch Trigger Node | Match item type based on `nodeId` | Adapts to node differences across different business handling processes to enable workflow branch jumps |
| Loop Processing Node | Traverse no more than 50 material list entries | Completes batch material verification and submission, adapts to array-type business data |
| Node Timeout Setting | 600 seconds | Matches the standard response timeline for government service handling to avoid workflow interruptions |
| Sub-workflow Call Configuration | Enable synchronous wait mode | Ensure the main workflow returns results only after the sub-workflow finishes executing |
| Log Output Switch | Enable full node logging | Facilitates troubleshooting workflow execution exceptions and locating problematic nodes |

## Three common mistakes
- Symptom: The main workflow calls a sub-workflow, but the main workflow returns results before the sub-workflow finishes executing. Cause: Synchronous wait mode for the sub-workflow is not enabled, so the main workflow skips the sub-workflow and proceeds to subsequent nodes.
- Symptom: The code execution node produces output, but the designated reply node cannot display this output. Cause: The output of the code execution node is not bound to the `variables` parameter, and the designated reply node does not reference the corresponding variable.
- Symptom: Complex business workflows automatically interrupt after exceeding 180 seconds of execution. Cause: Node timeout settings are not adjusted; the default timeout duration is insufficient to cover the execution cycle of complex business processes.

## How to confirm the configuration is correct
- Trigger a test business ticket, view the workflow execution log, and confirm all nodes run in the expected order.
- After calling a sub-workflow, wait for the sub-workflow to finish executing, then verify that subsequent nodes of the main workflow run normally.
- Adjust the output variable of the code execution node, reference the variable in the designated reply node, and confirm the result displays correctly.
- Simulate a long-running business scenario to verify the workflow does not automatically interrupt.
