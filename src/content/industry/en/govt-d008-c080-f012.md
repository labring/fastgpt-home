# Business Process Guidance for Urban Investment Platforms: Deployment and Upgrade

## What the data for this category looks like
The business handling data for urban investment platforms comes from three main sources: government service window ledgers, completed case data from online service halls, and officially published service guidelines.
Data updates when a batch of business is completed, or when government affairs items are adjusted quarterly. There is no fixed high-frequency update cycle.
Each data entry includes these fields: item name, handling entity, application material list, handling process nodes, time limit requirements, and consultation channels.
Material items use "copies" and "original/duplicate copies" as units.
Handling time limits use "working days" as units.
Process nodes are arranged as a continuous text sequence in the order of handling.

## What constraints these characteristics impose during deployment and upgrade
The business data of urban investment platforms has fixed fields, but allows regional custom adjustments.
During deployment, support custom field mapping. This avoids hardcoding adaptations for different regional service item structures.
Non-high-frequency updated data does not need real-time synchronization.
During deployment, configure on-demand data source pull logic. This avoids excessive server resource usage.
The sequential structure of process nodes requires retaining node order during knowledge base retrieval.
During upgrade, ensure retrieval result sorting logic matches the original process.
Some handling material units have regional differences.
Reserve adjustment space for custom units in the configuration. This adapts to service specifications of different prefecture-level cities.

## How to set the configuration
| Configuration Item | Recommended Value | Rationale for this setting |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | 100–200 connections | The concurrent query volume of urban investment platform business handling data is relatively high. This parameter limits the maximum number of database connections to avoid resource exhaustion |
| `MONGODB_URI` | For local deployment: `mongodb://localhost:27017/fastgpt`; for cloud deployment: use the connection address provided by the corresponding cloud service provider | Most service guidelines and completed records of urban investment platforms are semi-structured data. MongoDB is suitable for the storage needs of this type of data |
| `REDIS_URL` | For local deployment: `redis://localhost:6379/0`; for cloud deployment: use a cloud Redis address with authentication | Used to cache frequently queried service process nodes and reduce repeated query pressure on the database |
| `ROOT_KEY` | Custom random string of 32 characters or more | Used for administrator privilege verification. Business data of urban investment platforms involves government affairs information, so the security of background configuration must be ensured |
| `STORAGE_S3_ENDPOINT` | For local deployment: use local object storage address; for cloud deployment: use the S3 endpoint provided by the corresponding cloud service provider | Used to store scanned copies or electronic documents of handling materials, adapting to the material storage needs of urban investment platforms |
| `FE_DOMAIN` | For local deployment: `http://localhost:3000`; for online deployment: use the official domain name | Used to configure the front-end access address to ensure normal access to the business handling guidance page |

## Three Common Mistakes
- Modifying `ROOT_KEY` and restarting the service still does not take effect, and the log prompts a privilege verification failure. The cause is that only the parameters in docker-compose.yml were modified, and all associated service containers were not restarted synchronously, resulting in the configuration not taking effect globally.
- A database connection failure error appears after startup, and the log shows connection timeout or authentication failure. The cause is incorrect configuration of the `MONGODB_URI` or `PG_URL` parameters, failure to check whether the database service is running normally, or failure to configure correct access permissions.
- Windows local deployment fails to load handling process data after startup, and the interface displays an empty list. The cause is incorrect configuration of the local file storage path, resulting in the system being unable to read electronic documents of service guidelines, or failure to enable access permissions for the corresponding directory.

## How to Confirm the Configuration is Correct
- Run the docker compose ps command to confirm that all service containers are in a running state, with no abnormal exits or restart records.
- Access the domain name or local address configured in `FE_DOMAIN`, and try to log in to the background management interface using `ROOT_KEY` to verify that administrator privilege verification works normally.
- Upload one urban investment platform service guideline document to the knowledge base, perform a retrieval test, and confirm that correct process nodes and application material lists are returned.
- View Redis monitoring indicators to confirm that the cache hit rate of frequently queried service process nodes reaches the threshold preset for the business scenario (calibrated through actual testing).
