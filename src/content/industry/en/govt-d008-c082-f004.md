# Business Process Guidance for Basic Telecommunications Operations: Workflow Orchestration

## What the data for this category looks like
Business process data for basic telecommunications operations comes from internal operation support systems (OSS/BSS), offline service center ticket repositories, and logs from online self-service pages. Data updates sync in real time with business configuration changes. Package, processing node, and tariff rule data receives a full refresh daily. Ticket status data is pushed in real time. Documentation uses structured JSON format. Core fields include `nodeId`, node name, pre-verification rules, required processing materials, processing time limit (unit: hour), and connected system interface address. Each process node uses a unique `nodeId` as its identifier.

## What constraints these characteristics impose on the "workflow orchestration" link
This page is written for FastGPT v4.17.0.
Structured node IDs and real-time updated business data require workflow orchestration to strictly bind `nodeId` to match business process nodes, to prevent process interruptions caused by misplaced nodes.
Real-time synced ticket status data requires that real-time interfaces are called in workflow configuration to pull the latest status. Do not rely on static caching, otherwise discrepancies will appear between process nodes and actual business progress.
Pre-verification rules and unitized processing time limits for each node require workflow orchestration to execute checks in node order, automatically trigger exception branches for timed-out nodes, and uniformly handle unit conversions across different nodes to avoid duration calculation deviations.
The interface address field for multi-system integration requires that interface call parameters configured in the workflow exactly match the addresses in the data. Otherwise, business data cannot be pulled normally.

## How to set the configurations
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `variables` | Bind `nodeId` and the package ID of the current processing business | Match node identifiers and package fields in business data to enable dynamic calling of corresponding processes |
| Node trigger condition | Match business process nodes by `nodeId` | Strictly correspond to unique node identifiers in the data to avoid process misalignment |
| Interface call timeout | 10–15 seconds | Adapt to response delays of basic telecommunications system interfaces to avoid process interruptions due to timeouts |
| Maximum context length | 800–1200 characters | Match the single-node information length of business process documentation to avoid context overflow |
| Knowledge base dynamic assignment | Dynamically assign by business type in `variables` | Adapt to exclusive knowledge bases corresponding to different packages to enable precise guidance |
| Code run trigger condition | Execute only when `nodeId` matches a check node | Trigger code logic only at process nodes that require verification to avoid unnecessary computations |

## Three common errors
- Phenomenon: The knowledge base does not automatically switch by business type during workflow runtime, and the knowledge base parameter in `variables` is empty. Cause: The mapping relationship between business type and knowledge base is not configured in `variables`, causing the dynamic assignment logic to fail to take effect.
- Phenomenon: Truncation errors occur during AI model calls, and code run results are not passed into user queries. Cause: The output variables of the code node are not correctly referenced in the AI model's user query configuration, and the variable binding format is incorrect.
- Phenomenon: Process node execution order is disrupted, and some pre-checks are not triggered. Cause: Workflow nodes are not configured in the order of `nodeId` in the business data, leading to misplaced node matching.

## How to confirm the configuration is correct
- Check the `variables` configuration item, confirm that `nodeId` and business type parameters are bound. Trigger variable assignment by simulating real business requests, and verify whether variables are generated as expected.
- Pass test data with different `nodeId` values, run the workflow, and verify that the trigger order of each process node matches the node order in the business data.
- Enable log output for code nodes, run the test process, and check logs to confirm that code run results are generated normally.
- Review the input configuration of the AI model, confirm that output variables of the code node are correctly referenced, with no format errors.
