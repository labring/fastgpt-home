# Business Process Guidance for Infrastructure Construction: Workflow Orchestration

## What the data for this category looks like
Data primarily comes from on-site construction management systems, BIM collaboration platforms, and government approval portals. Construction log data is updated daily. Approval process node data is updated when an item processing event is triggered. Project ledgers are summarized and archived monthly. Each data document includes unique project identifier, construction phase code, approval item name, handler ID, processing timestamp, and approval status field. Units include days, yuan, hours, and other units. Some fields are linked to third-party construction permit numbers.

## What constraints these characteristics impose on workflow orchestration
Multi-source data access imposes format compatibility constraints. Dedicated adaptive pull nodes must be configured for construction management systems, BIM platforms, and government portals to avoid field parsing exceptions. Daily updated construction logs must be bound to scheduled trigger nodes. Approval data must be bound to event trigger rules to ensure process startup timing matches data update rhythm. Multi-field association attributes require a variable mapping step in the workflow: map third-party platform construction permit number fields to associated fields in internal approval processes. Additional validation rules must be configured for some numerical fields with units to prevent calculation errors caused by inconsistent cross-system units.

## How to set configurations
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Data source trigger method | Triggered by data update event / Scheduled trigger (every 24 hours) | Matches the update rhythm of infrastructure construction project data: construction logs are updated daily, approval data is triggered by processing events |
| `variables` field mapping | Map "Project ID → Unique Project Identifier", "Approval Status → Process Node Status" | Adapts to the field structure of this category data, ensures smooth cross-system data transfer |
| `nodeId` node association | Assign unique `nodeId` to each approval link, bind to corresponding form node | Ensures workflow jump logic matches project approval links one-to-one |
| Numerical unit validation | Validate that duration fields use days as unit, amount fields use yuan as unit | Prevents process calculation errors caused by inconsistent cross-system units |
| Process timeout threshold | 600 seconds | Adapts to typical approval time for infrastructure construction projects, reserves sufficient response window |

## Three common configuration mistakes
- No output results after workflow node runs, with a prompt stating no run results. The cause is incorrect `variables` field mapping, which prevents the node from reading construction or approval data for the corresponding project and triggers an empty input error.
- Incorrect environment variable configuration after deployment, leading to failed external interface calls by the workflow. The cause is not adding the CHAT_API_KEY environment variable to the docker-compose startup configuration, and not rebuilding the container to apply the new configuration.
- Empty graphs generated after chart tool usage. The cause is not correctly binding structured project data returned by the workflow to the chart's data source configuration, resulting in no valid data for the chart to render.

## How to confirm configuration is correct
- Manually trigger the workflow once, view node run logs, and confirm that the data source node can pull valid data for the corresponding project.
- Review the `variables` field mapping configuration, confirm that all associated project fields have been correctly bound, with no missing or incorrect mappings.
- Simulate a project approval trigger scenario, verify that workflow node jump logic matches project approval links, with no abnormal interruptions.
- After configuring the timeout threshold, simulate a run scenario matching the typical time consumption of this category, confirm that the process does not terminate abnormally due to timeout.
