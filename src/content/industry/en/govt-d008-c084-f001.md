# Business Process Guidance for Bulk Commodity Trading: HTTP Interfaces and External Systems

## What the data for this category looks like
Business process data for bulk commodity trading primarily comes from internal trade management systems, port logistics scheduling systems, customs declaration ports, and third-party bulk commodity trading platforms. Update frequencies vary by data type. Transaction order data syncs in real time. Inventory and logistics node data updates every hour. Declaration data pushes per declaration batch.
Data documents include fields such as transaction order number, product code, transaction quantity, unit price, trading party qualifications, and processing node status. Most units use industry standard values including tons, yuan per ton, and batch numbers.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Data sources cover internal systems and multiple external ports. HTTP interfaces are required to unify pull and sync multi-source data. This means adapting to authentication rules of different systems.
Differences in update frequencies across data types require interface request polling intervals to match the update rate of corresponding data.
Industry data fields include many dedicated codes and units. Interface request parameters must strictly match field definitions to avoid data parsing failures from mismatched fields.
Additionally, single bulk commodity transaction data volume is large. The amount of data returned per interface request must be controlled within a reasonable range to prevent timeouts or transmission failures.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` configuration | Use the authentication token provided by the connected system. Configure separately when connecting to multiple systems | Authentication requirements vary across external systems, so corresponding tokens must be configured individually |
| `variables` mapping | Map transaction order numbers and product codes to process variables | Business process guidance generates content based on core fields returned by external systems |
| `responseData` parsing | Extract business data under the `responseData` node in the response body | External interfaces for bulk commodity trading mostly use standard nested structures, so business fields must be located accurately |
| Single request limit | 1000 entries | Single transaction data volume is large, so controlling per-request volume avoids transmission timeouts |
| Request timeout | 600 seconds | Interface response times for large-scale trading businesses are long, so a reasonable timeout threshold must be used |

## Three common mistakes
- Phenomenon: Interfaces frequently return 429 status codes, or business process guidance triggers repeatedly. Cause: Polling intervals are not adjusted based on data update frequencies, leading to too many invalid requests in a short period.
- Phenomenon: The latest business node status does not appear in the process guidance. Cause: `responseData` parsing rules are not configured correctly, and node status fields returned by external systems are not extracted.
- Phenomenon: Incorrect product units or quantities appear in the process guidance. Cause: Fields returned by external systems are not correctly mapped to the `variables` parameter, leading to mismatched core business fields.

## How to confirm the configuration is complete
- Connect the test interface, check that the `Authorization` header carries the authentication token correctly, and confirm authentication passes.
- Send a test request, verify that business fields under the `responseData` node are correctly extracted and mapped to the `variables` parameter.
- Simulate different types of business data, confirm that node prompts in the process guidance match the status returned by external systems.
- Adjust the request interval parameter, observe if interface request frequency meets expectations, and check for no abnormal timeouts or repeated triggers.

All configuration values provided are common starting points and should be evaluated against the user's own operational samples.
