# Commodity Trading Business Process Guidance: Tool Calling and Plugins

## What the data for this category looks like
Business data for commodity trading originates from internal ERP contract systems, third-party commodity spot trading platforms, and port logistics manifest systems. The data primarily uses structured fields, including product category, specification model, transaction quantity (unit: tons, cubic meters, or barrels), unit price (unit: yuan/ton, yuan/cubic meter), counterparty, signing date, logistics node status, and more. Spot quotation data updates in real time alongside market transactions. Logistics manifests update alongside loading and unloading nodes. Contract ledgers update alongside internal approval processes.

## What constraints these characteristics impose on the tool calling and plugins link
Structured commodity trading data relies on precise transaction IDs to associate multi-dimensional information such as contracts, quotations, and logistics. Tool calls must bind a fixed transaction ID as an input parameter to avoid data confusion. Real-time updated spot quotation data requires tool call response speeds to match the update rhythm, preventing the return of outdated information. Multi-node logistics data has a large number of entries, so tool calls must limit returned entries to prevent context overflow. Sensitive transaction data requires strict validation of input parameter legality to prevent unauthorized data access via malicious calls.

## Three common mistakes
- Phenomenon: Unable to bind input parameter variables from HTTP responses when adding an MCP service, with logs showing empty input parameter fields. Cause: Core fields of commodity trading such as transaction ID and product specifications were not preset as input parameter templates, so the large model cannot extract correct variables from the context.
- Phenomenon: The large model does not trigger tool calls and directly returns vague responses. Cause: `toolChoice` was not configured as auto, or the context does not carry sufficient business trigger signals such as not mentioning a transaction ID or specific business requirements.
- Phenomenon: The number of results returned by tool calls exceeds expectations, leading to context overflow. Cause: The number of logistics nodes or quotation entries returned by a single call was not limited, failing to match the multi-entry characteristic of commodity trading data.

## How to confirm the configuration is complete
- Initiate a test request with a clear transaction ID, and check whether the tool call log carries correct input parameter fields and values.
- Simulate business scenarios such as commodity price inquiries or logistics tracking, and confirm that the large model automatically triggers tool calls and returns corresponding data.
- Check whether the tool return results include commodity-specific fields such as specification models, transaction quantity units, logistics node status, and more.
- Simulate a network delay scenario of more than 10 seconds, and confirm that the tool call returns valid results within the preset timeout period.
- Use Python to write a test script to call the FastGPT chat interface, pass in business questions including transaction IDs, and verify whether the tool call process works normally.
