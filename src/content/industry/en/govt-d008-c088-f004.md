# Business Process Guidance for Engineering Consulting Supervision: Workflow Orchestration

## What the Data for This Category Looks Like
Engineering consulting supervision data mainly comes from four categories: on-site supervision logs, sub-project acceptance reports, progress payment approval forms, and on-site image materials. Data sources cover two channels: manual filling by on-site supervision personnel, and submission and upload by construction units. The update rhythm follows project milestones: on-site logs are updated daily, acceptance reports are updated after sub-project completion, and approval forms are submitted with payment milestones. The document structure includes fields such as project number, supervision unit, construction unit, sub-project name, acceptance milestone, number of rectification items, rectification closure status, and units including days, items, ten thousand yuan and other engineering-specific units.

## Constraints on Workflow Orchestration From These Characteristics
Engineering consulting supervision data is scattered across multiple types of heterogeneous documents. Workflow configuration must pull data from different data sources in parallel across multiple nodes to avoid single-node data overload. Fields include engineering-specific units. Workflow configuration must include variable validation rules to ensure matching of input and output units and avoid mixed data usage. Some data includes on-site image file streams. Workflows must support binary file stream processing nodes to adapt to common formats such as PDF and JPG. Data updates are triggered by project milestones. Workflows must bind node events as trigger conditions to ensure data timeliness meets supervision business requirements.

## How to Configure Settings
| Configuration Item | Recommended Approach | Basis for This Approach |
| ---- | ---- | ---- |
| `variables` | Bind the three fields of project number, number of rectification items, and acceptance duration, and configure validation rules based on measured and calibrated units | Supervision data fields have clear engineering-specific units, and verification is required to avoid parameter mixing |
| Trigger node settings | Bind the sub-project acceptance completion event | Supervision data updates with project milestones, and event triggering aligns better with business rhythm than scheduled triggering |
| HTTP request node | Set a timeout of 300 seconds | Parsing multi-page PDF documents for supervision takes a long time, and 300 seconds covers most scenarios |
| File stream processing node | Support JPG and PDF formats, set the maximum file size to 100 MB based on measured calibration | Single on-site supervision images do not exceed 20 MB, and aggregated submission files do not exceed 100 MB |
| `nodeId` | Assign a unique `nodeId` to each data source node | Avoid data confusion when pulling data across multiple nodes, and ensure correct workflow execution |
| Single data pull volume | Pull the first 20 data entries | Supervision single-node data volume is moderate, and 20 entries cover the core information of a single business process |

## Three Common Configuration Mistakes
This section covers three common errors in workflow orchestration for this scenario, tested and verified based on FastGPT v4.17.0.
- Phenomenon: The workflow returns empty fields and cannot load business data. Cause: `variables` are not bound to the corresponding fields of supervision data, resulting in failed variable loading.
- Phenomenon: The HTTP request node returns format errors and cannot parse image files. Cause: No file stream processing node is configured, and binary image streams are directly attempted to be parsed as text data.
- Phenomenon: Workflow node transfer interrupts after triggering. Cause: A unique `nodeId` is not assigned to each data source node, resulting in node ID conflicts and failed normal transfer.

## How to Verify Correct Configuration
- Enter the workflow debugging page, enter a test project number, and check whether `variables` correctly load structured data of corresponding fields.
- Upload a rectification report PDF or on-site image JPG file, and test whether the file stream processing node normally parses and returns structured information.
- Simulate the sub-project acceptance completion event, and check whether the workflow starts as expected and completes multi-node data pulling.
- Check whether the `nodeId` of each data source node is unique and there are no duplicate configuration items.

The values given are common starting points and should be measured against the reader's own samples.
