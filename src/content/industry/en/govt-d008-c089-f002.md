# Business Process Guidance for Construction Machinery: Vector Models and Indexes

## What the Data for This Category Looks Like
Business process-related data for construction machinery comes primarily from manufacturer official operation and maintenance manuals, on-site after-sales work orders, spare parts inventory lists, and equipment installation and commissioning documents. These data sources cover business scenarios across the full equipment lifecycle. Update rhythms fall into three categories: official manuals are synced when new models launch, after-sales work orders are updated based on daily new entries, and spare parts lists are updated monthly. Documents are structured hierarchically by model, part number, fault code, and operation steps. Fields include part model, serial number, working hours, consumable unit, and more. Some documents contain multilingual reference content.

## Constraints on Vector Models and Indexes from These Data Characteristics
Because the data includes precise model and part number fields, vector chunking must retain key business scenario identifiers. This avoids breaking the binding between identifiers and operation steps. Diverse update rhythms across data sources require indexes to support incremental updates. Daily new after-sales work orders and monthly updated spare parts lists can be synced without full index rebuilding. Long texts in operation manuals and work orders require vector models to support long-context encoding. This prevents encoding failures caused by overly long chunks. Additionally, unit information in fields must be bound to the index as metadata. This ensures different consumable measurement standards are not confused during retrieval.

## Three Common Configuration Errors
- No options appear in the interface index model dropdown menu, making model binding impossible. The cause is that the access path and authentication parameters of the local vector model are not configured correctly. The system cannot pull the list of available vector models, which is a common configuration exception issue in corresponding business scenarios.
- Retrieval results include operation and maintenance documents for non-target models, leading to incorrect business guidance. The cause is that the model field of the document is not bound as a metadata filter condition. Vector recall does not use precise identifiers of the business scenario for screening.
- Vector encoding fails for a single long document, and the system returns a token limit exceeded error. The cause is that the chunk length setting exceeds the `maxToken` configuration value. The appropriate chunk size is not split according to the document structure, leading to the encoding process exceeding system limits.

## How to Verify Successful Configuration
- Upload an operation and maintenance manual for a specific excavator model. Check that the chunked text retains complete operation steps without obvious content breaks.
- Initiate a test query for "XX model excavator hydraulic oil replacement steps". Confirm that the retrieval results only include document content for the corresponding model, and the operation steps are coherent and complete.
- View the vector model operation logs. Confirm that there are no token limit exceeded errors, and the retrieval response time meets business expectations.
- Check the index model configuration interface. Confirm that the dropdown menu displays the configured local vector model options, with no blank or abnormal prompts.
