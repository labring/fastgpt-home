# Business Process Guidance for Construction Machinery: Workflow Orchestration

## What the Data for This Category Looks Like
Data related to construction machinery business processing mainly comes from equipment operation and maintenance systems, job scheduling platforms, and factory parameter libraries. Data sources cover three categories: real-time equipment operating condition collection, daily job logs, and regular maintenance records. Update frequency varies by scenario: real-time operating condition data updates every second, job log data syncs daily, and factory parameters and maintenance records are statically updated. A single data entry includes fields such as unique equipment identifier, job duration, cumulative fuel consumption, fault code, job area code, and trigger timestamp. The units for these fields are hours, liters, no code identifier, square kilometers, and ISO 8601 format timestamp respectively.

## What Constraints These Characteristics Impose on Workflow Orchestration
Real-time operating condition data updating every second requires that workflow trigger nodes be configured with millisecond-level interval listening to avoid missing key operating condition changes. The daily update attribute of job logs requires that batch processing workflows be configured with daily scheduled trigger nodes. There are multiple format differences for unique equipment identifiers and job area codes, requiring the addition of a field standardization node before the workflow to unify data formats before proceeding to subsequent links. The low-frequency update attribute of static parameters requires that static parameter call nodes in the workflow be set with a reasonable cache period to avoid repeated pulling and increasing system load. The standardized attribute of fault codes can be used for workflow branch judgment, but mapping rules between fault codes and corresponding disposal processes must be configured in advance to ensure accurate triggering of branch logic.

| Trigger Interval | 100–500 milliseconds | Adapts to the second-level update rhythm of construction machinery real-time operating conditions, avoiding missing key changes |
| Scheduled Trigger Cycle | 24 hours | Matches the daily update attribute of job logs, suitable for batch data processing scenarios |
| `variables` Binding | Unique equipment identifier, job duration, fault code | Binds core business data fields to support subsequent branch judgment and data calling in the workflow |
| `nodeId` Configuration | Set by grouping equipment job scenarios | Distinguishes workflow branches for different job scenarios, matching the multi-operating-condition business needs of construction machinery |
| Field Standardization Rules | Unify job area code format | Adapts to format differences of multi-source data, ensuring data consistency in subsequent workflow links |
| Static Parameter Cache Period | 7 days | Adapts to the low-frequency update attribute of factory parameters, reducing system load caused by repeated pulling |

## Three Common Configuration Mistakes
- Phenomenon: The knowledge base search node returns normal results in the debug interface, but fails to return matching construction machinery operation and maintenance data when the workflow is formally called. Cause: The unique equipment identifier is not bound as a retrieval restriction parameter in `variables`, resulting in the retrieval scope not covering the exclusive data of the target equipment.
- Phenomenon: The real-time operating condition listening node has an excessively high trigger frequency, causing system resource usage to exceed the threshold. Cause: The trigger interval is set below 100 milliseconds, exceeding the actual update frequency of construction machinery real-time data, resulting in a large number of invalid triggers.
- Phenomenon: The fault code branch logic is triggered incorrectly, matching the wrong disposal process. Cause: No standardized conversion is performed on the original fault code, and unstandardized code values are directly used for branch judgment, resulting in matching result deviations.

## How to Verify a Correct Configuration
- View workflow trigger logs to confirm that the trigger interval matches the preset range, with no abnormally high-frequency trigger records.
- Call the workflow API to check whether the returned results include the equipment data fields corresponding to the bound `variables` parameters, and the field format conforms to the preset standards.
- Simulate fault code input to verify whether the branch logic triggers the corresponding disposal process according to the preset rules, with no matching errors.
- Check the refresh records of the static parameter cache node to confirm that the cache is automatically refreshed after parameter updates, with no outdated data returned.
