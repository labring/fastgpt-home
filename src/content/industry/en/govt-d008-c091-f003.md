# Business Process Guidance for General Contracting of Housing Construction Projects: Multi-turn Dialogue and Prompt Engineering
This document is written based on the configuration rules of FastGPT v4.17.0.

## What the data for this category looks like
The business data for general contracting of housing construction projects comes from internal project management systems of state-owned and public enterprises, construction documents filed with housing and urban-rural development authorities, general contracting contracts, and phased acceptance reports. Data updates follow project milestones: construction progress and material submission records are updated weekly, while settlement and acceptance ledgers are updated monthly. The document structure is divided into four categories: project basic ledgers, process node lists, submission forms, and acceptance reports. Fields include project number, section division, submission time, material specifications, and acceptance results. Units include professional engineering measurement units such as square meters, tons, and working days.

## What constraints do these characteristics impose on the "multi-turn dialogue and prompt engineering" link?
The general contracting process for housing construction projects has many process nodes, dense professional terminology, and significant differences between projects. These characteristics impose clear constraints on multi-turn dialogue and prompt engineering configurations. First, single-turn dialogue needs to carry a large amount of professional information. An overly long context window can easily confuse the current process steps, so the retention range of historical dialogue must be limited. Second, professional terms such as CFG piles, static pressure piles, and others must be clearly marked in the prompt to prevent the classification module from misjudging the process type. In addition, submission processes vary between different projects. Project-specific configurations must be passed through session parameters to avoid confusion between cross-project processes.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `chatId` | Bind to the unique project identifier | Housing construction project process data is isolated by project. `chatId` ensures that dialogue context for the same project does not cross between projects |
| `messages` | Retain the first 6 rounds of dialogue related to the current process | Housing construction business has many process nodes. Excessive historical dialogue will interfere with current process judgment. 6 rounds can cover complete process context |
| `variables` | Pass fields such as project section and submission type | Housing construction general contracting processes have different rules due to differences in sections and submission types. `variables` can transmit project-specific configurations |
| Maximum characters per single dialogue | 1500 characters | Form filling content for housing construction business processing is lengthy. Limiting single-turn input prevents context overflow |
| Dialogue timeout period | 900 seconds | Users may take a long time to fill in housing construction submission materials. The timeout retains the session state |
| Question classification matching threshold | 0.85 | Housing construction professional terms have high recognizability. This threshold can accurately distinguish process types such as submission, acceptance, and settlement |

## Three common mistakes
- The process operations returned by the dialogue do not match the business type entered by the user. For example, a material submission request is incorrectly guided to the completion acceptance process. The cause is that the prompt does not include housing construction-specific process classification terms, or the `messages` parameter includes cross-project historical dialogue fragments.
- The dialogue page fails to load or returns an abnormal status code. The cause is that `chatId` is not correctly bound to the unique project identifier, causing the system to fail to load the process data for the corresponding project.
- Duplicate user or assistant messages appear in the dialogue history after starting a dialogue via API. The cause is that the `messages` parameter does not correctly filter redundant fragments of the initial system prompt, or the session initialization interface is called repeatedly.

## How to confirm the configuration is correct
- Initiate a test dialogue containing housing construction professional process keywords, and verify that the dialogue history only retains content related to the current process.
- Pass `chatId` with different project identifiers, and confirm that the dialogue context only associates with the process data of the corresponding project.
- Enter a lengthy business description, and check that the system imposes reasonable restrictions on input length.
- Pause the session for longer than the set timeout period, then re-enter, and check that the session state is retained normally.
