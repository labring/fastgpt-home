# Business Process Guidance for New Energy Development: HTTP Interfaces and External Systems

## What this category of data looks like
Data for new energy development business processes comes primarily from three sources: the project initiation approval system, the territorial space planning verification platform, and the grid connection application portal. Data updates are triggered by business process nodes, and are synchronized when an application is submitted, verification is completed, or approval is passed. Each individual data record includes fields such as a unique project identifier, land scope coordinates, installed capacity, approval status, current processing link, and handler information. Most field units are kilowatts, hectares, and natural days.

## What constraints these characteristics impose on HTTP interfaces and external systems
New energy development business process data originates from multiple external systems. Each system uses different authentication rules, so different verification logic must be adapted in HTTP interface configurations. Business data updates when processing nodes change, so interfaces must support on-demand calls to retrieve the latest approval status. Fixed-cycle pulling cannot be relied on. Some systems return field formats for land coordinates, installed capacity, and other metrics that do not match business requirements. Field mapping and unit conversion rules must be configured in advance to ensure normal data access.

## How to configure the setup
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | Configure according to the connected system. Leave blank for public interfaces, fill `Bearer {token}` for private interfaces, fill `Basic {base64-encoded account password}` for internal systems | Different external systems use different authentication standards. Matching the corresponding rules ensures requests are valid |
| `variables` | Pass three core variables: project number, processing link, and land scope | Business process flows require association with dynamic data for specific projects. Passing variables enables precise matching of interface parameters |
| `responseData` | Configure field mapping and unit conversion rules, convert installed capacity to kilowatt units | Field names and units returned by external systems may not align with business requirements. Mapping ensures data is parsed correctly |
| Request timeout | 60–120 seconds | New energy project data interfaces return large data volumes. A timeout that is too short causes request failures, while a timeout that is too long occupies system resources |
| Retry count | 2–3 times | External interfaces may experience temporary failures due to network fluctuations. Retries improve request success rates |
| Trigger timing | Configure to trigger when business is submitted or approval is completed | Business data updates with processing nodes. On-demand triggering retrieves the latest processing status |

## Three common configuration errors
- A `Failed to fetch` error occurs after calling the interface. The cause is incorrect authentication parameter configuration, or a request timeout setting that is too short to complete data pulling.
- Project drawing images cannot be downloaded when connecting to multimodal models. The cause is that binary stream response processing is not enabled, so BLOB-format image data cannot be parsed correctly.
- The process does not trigger the next step of guidance after the interface returns data. The cause is that the approval status field is not mapped correctly, so the node jump rules for business process flows cannot be matched.

## How to confirm the configuration is correct
- Manually call the configured HTTP interface, check whether the fields and units of the returned data meet business requirements, and confirm that the mapping rules take effect.
- Simulate a business node to trigger an interface call, check whether the latest approval status data can be retrieved correctly, and verify that the trigger logic operates normally.
- Upload project drawings to test the multimodal analysis function, confirm that images load normally and are recognized by the model, and verify that BLOB data processing works correctly.
- View the FastGPT log panel, confirm that there are no abnormalities in the interface request's authentication parameters and variable passing, and that no error messages are present.

Note: The configuration values provided are common starting points and should be evaluated against samples specific to the deployment.
