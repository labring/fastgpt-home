# Business Process Guidance for Civil Aviation Airports: Tool Calling and Plugins

## What the Data for This Category Looks Like
The business process data for civil aviation airports comes from two sources: public airport operation data interfaces released by the civil aviation administration, and real-time interfaces from the airport’s own check-in, security check, boarding and other business systems. There are two update rhythms: flight dynamic data is updated in real time, while business process rule data is updated daily. The document structure uses a standardized format, including fields such as flight number (IATA format string), current processing link (enumerated values: check-in, security check, waiting area, boarding), waiting duration (unit: seconds), required processing materials (string list), and processing window number. All fields have clear value ranges and units, with no ambiguous text content.

## Constraints Imposed on Tool Calling and Plugins
Real-time flight data requires that the response delay of tool calling be controlled within a reasonable range, otherwise guidance information will lag behind actual business progress. The `toolChoice` configuration must be used to automatically match the plugin corresponding to the current business, to avoid process errors caused by manual selection. Structured fields require that tool calling parameters strictly match preset enumerated values and data types, and non-expected results cannot be returned via fuzzy matching. Multi-node business processes require multiple internal airport interfaces to be linked via plugins, such as the check-in reservation plugin, security check queue duration query plugin, and boarding gate guidance plugin. Therefore, tool calling must support chained linkage. In addition, frequently updated real-time data requires that plugin cache duration not be too long, to avoid returning outdated business information. Interface call frequency must also be controlled to comply with the airport system’s current limiting rules.

## Three Common Mistakes
- Phenomenon: The tool call return result includes the input and response fields from knowledge base search. Cause: The non-essential knowledge base call switch was not turned off in the workflow configuration, resulting in mixed output of static knowledge base content and real-time tool call results.
- Phenomenon: After importing the airport business plugin via CURL, the interface cannot trigger the confirmation button. Cause: The required authentication parameters in the CURL were not filled correctly, or the interface address format does not comply with FastGPT’s verification rules, causing the import process to stall.
- Phenomenon: When calling an MCP client plugin, a type mismatch error is returned for the numeric waiting duration parameter. Cause: The numeric type of the parameter was not explicitly declared in the plugin configuration, resulting in parameter format verification failure during tool calling.

## How to Confirm Proper Configuration
- Send a simulated flight query request, check that the return result only includes business data from tool calls, with no redundant knowledge base search fields.
- Import the preset airport business CURL plugin, confirm that the interface displays "Import Successful" and all configuration items can be edited and saved normally.
- Call an MCP client plugin with numeric parameters, verify that the numeric type parameters can be correctly identified and return corresponding business results.
- View the tool call logs, confirm that the response duration meets the preset timeout threshold, and there are no records of frequent timeout retries.
