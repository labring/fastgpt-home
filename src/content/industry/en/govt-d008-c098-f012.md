# Business Process Guidance for Civil Aviation Airports: Deployment and Upgrade

This document is based on FastGPT v4.17.0, and adapts to the business process guidance scenario deployed on civil aviation airport internal networks.

## What the Data for This Use Case Looks Like

Data sources for civil aviation airport business process guidance include flight scheduling systems, check-in counter terminals, security gate logs, and interaction data from public service terminals in airport terminals.

Data updates are triggered by business nodes. Real-time push updates occur when flight information changes. Daily business data is synchronized once per hour.

Data uses a structured format, including fields such as flight number, takeoff and landing time, terminal number, counter number, security channel number, and guidance step sequence. Flight number uses a string format. Takeoff and landing time uses ISO standard time format. Terminal number uses a two-digit numeric code. Guidance steps use an ordered numeric sequence.

## Constraints Imposed by These Characteristics on Deployment and Upgrade

Real-time flight data requires database connections configured to support high-concurrency writes. Do not use read replicas as primary storage nodes.

Structured fixed fields require unified mapping rules defined in advance. Arbitrary modification of field mappings during upgrades will cause guidance step matching errors.

Multi-system integration requires a pre-configured data format validation link. Deploy validation logic during deployment to prevent dirty data from entering the knowledge base.

The airport internal network deployment scenario requires all configurations to adapt to internal network access rules. Do not rely on external network resources. Retain compatibility with internal network caching policies during upgrades.

## Configuration Settings

| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| `DB_MAX_LINK` | 100–150 connections | Adapts to concurrent business requests from multiple airport terminals, prevents database connection exhaustion |
| `MONGODB_URI` | Includes the read replica address of the airport business database, adds read-write separation parameters | Ensures read/write performance of real-time flight data, avoids excessive pressure on the primary database |
| `REDIS_URL` | Configured as a local cache node, set expiration time to 300 seconds | Caches guidance data for popular flights, reduces database query frequency |
| `FE_DOMAIN` | Airport terminal internal network domain name | Limits front-end access scope, adapts to the airport internal network deployment scenario |
| `STORAGE_S3_ENDPOINT` | Internal network address of the airport’s internal object storage | Stores multimedia materials for guidance processes, complies with internal network data security requirements |
| `ROOT_KEY` | Generated according to the airport’s internal network permission rules | Restricts background management access permissions, prevents unauthorized configuration modifications |

## Three Common Misconfigurations

- Front-end pages load indefinitely with a spinning indicator, and the guidance interface fails to display. The cause is incorrect configuration of the `FE_DOMAIN` parameter, preventing front-end resources from loading via the internal network domain, or the cache node pointed to by `REDIS_URL` failed to start normally.
- Model connection tests report errors, and locally deployed models cannot be called. The cause is that internal network model access permissions were not enabled in the configuration, or `MONGODB_URI` did not correctly point to the local data cache link, causing the model call chain to break.
- Guidance step matching errors occur, and outdated flight information is displayed. The cause is that the original data mapping rules were not retained during the upgrade, leading the new configuration to overwrite the field correspondence, allowing dirty data to enter the knowledge base.

## How to Verify Successful Configuration

- Access the internal network address specified by `FE_DOMAIN`. Verify that the front-end page loads normally with no spinning indicator or error prompts.
- Run a model connection test. Verify that locally deployed models can be called, and return expected guidance step results.
- Simulate a flight change operation. Verify that the system completes guidance data refresh within the configured update cycle, with no delays or data loss.
- Check database connection logs. Verify that the concurrent connection count for `DB_MAX_LINK` does not exceed the set threshold, and no connection timeout errors occur.

The values provided are common starting points and should be validated against local deployment samples.
