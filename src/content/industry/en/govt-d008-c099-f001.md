# Business Process Guidance for Oil and Gas Exploration and Development: HTTP Interfaces and External Systems
## What the data for this category looks like
Oil and gas exploration and development data is primarily sourced from on-site real-time collection systems, professional exploration and development databases, and third-party geological modeling platforms. Well location and seismic exploration data from the exploration phase are updated quarterly. Production monitoring data from the development phase is updated hourly.

Data is stored in structured JSON format. Each entry includes fields including unique business identifier, timestamp, well ID, logging depth, acoustic travel time, and permeability. The unit for logging depth is meters, permeability is millidarcies, and acoustic travel time is microseconds per foot.

## Constraints imposed by these characteristics on HTTP interfaces and external systems
Multiple heterogeneous data sources require HTTP interfaces to support multiple authentication methods, to avoid conflicts with permission checks across different systems. Differences in update frequencies require interfaces to support dynamic adjustment of request intervals. This accommodates batch query needs during the exploration phase and real-time polling needs during the development phase.

The special field unit requirements mean interfaces must return metadata for returned fields. This prevents unit errors during cross-system conversion. Large-volume seismic exploration data requires interfaces to support chunked transfer, while setting a long timeout period to prevent transmission interruptions.

## How to configure the setup
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Authentication Method | Bearer Token, carry fixed secret via `Authorization` header | Oil and gas exploration data is sensitive information. Identity verification must be completed via the `Authorization` parameter to prevent unauthorized access |
| Request Variable Configuration | Bind well ID and monitoring time range as `variables` | Business processes require querying data by different well locations or cycles. Use `variables` to enable dynamic replacement of request parameters |
| Response Data Parsing | Extract structured fields via `responseData`, filter invalid null values | Exploration and development data has many fields and a fixed format. Use `responseData` to accurately extract required monitoring metrics |
| Request Timeout | 600-1800 seconds | Seismic exploration data files have large volume, leading to long request response times. A sufficiently long timeout period must be set |
| Error Retry Strategy | Retry 3 times on connection timeout, retry 2 times on 5xx errors | External systems may experience errors due to network fluctuations or high load. This aligns with stability requirements for oil and gas data transmission |
| Result File Storage Path | Name by well ID + date, mount to local storage directory | Business processes require retaining request result files. Classifying by well ID facilitates subsequent review |

## Three common configuration errors
- Symptom: Calling an external exploration database interface returns `Failed to fetch` with a status code of 401 or 502. Cause: The `Authorization` parameter is not configured correctly, or the external system experienced a connection interruption due to high load.
- Symptom: Exploration data files returned by the HTTP interface cannot be saved as local files, or the business process cannot retrieve result files. Cause: The file stream parsing rule for `responseData` is not specified in the configuration, leading to truncated response data or format errors.
- Symptom: Oil and gas data query requests fail when calling a privately deployed model interface. Cause: The privately deployed model does not grant dynamic replacement permission for the `variables` parameter, resulting in failure to correctly pass request parameters.

## How to confirm the configuration is correct
- Send a test request, check whether the `Authorization` parameter is correctly carried in the request header, and verify that the returned authentication check results meet expectations.
- Check whether the `variables` in the request parameters are replaced with dynamic values such as the well ID and time range required for the current business process, confirming that the request parameters match expectations.
- Parse the `responseData` field, confirm that the extracted exploration data fields are complete and the units conform to oil and gas industry standards.
- Trigger a simulated error scenario to verify that the error retry strategy takes effect as configured, and that timeout or abnormal requests correctly trigger the retry process.
