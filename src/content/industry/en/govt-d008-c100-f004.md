# Business Process Guidance for Oilfield Engineering Services: Workflow Orchestration

## What the data for this category looks like
Oilfield engineering service business process data mainly comes from on-site construction logs, equipment operation and maintenance ledgers, project approval documents, and exploration test reports. Data updates progress alongside the operation cycle of individual projects, and single-project data is archived after job completion. Document structures primarily use structured forms, including fields such as construction order number, equipment number, operation type, approval status, and operation duration. Field units include engineering-specific measurement standards such as hours, cubic meters, and counts. Some unstructured attachments are on-site captured construction images and test reports.

## What constraints these characteristics impose on workflow orchestration
Multi-field structured data and project-cycle-based updates are core traits of oilfield engineering service data. Workflow orchestration must accurately match field verification rules for each operation link. To access unstructured attachments such as on-site construction images and test reports, configure independent file parsing nodes in the workflow. These nodes must adapt to common formats of engineering images and documents. Single-project data volume fluctuates with operation complexity. Workflow concurrent processing must reserve elastic space to avoid timeouts caused by excessive single-call data volume. The approval status field requires real-time synchronization. Enable the real-time update configuration of `variables` for variable transfer between workflow nodes. This ensures downstream nodes obtain the latest operation parameters and approval results.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Global variable synchronization | Enable `variables` real-time update | Matches the characteristic that oilfield engineering service project data updates dynamically with operation nodes, ensuring each workflow node obtains the latest approval status and operation parameters |
| Opening statement generation node | Bind the operation type field as the trigger condition | Generates guidance statements for links such as drilling and workover based on the operation type field in business process data, fitting the professional scenario of engineering services |
| External API call concurrency | Set healthy concurrency to 3–5 requests/second, maximum concurrency to 8–12 requests/second | Adapts to the fluctuating single-call data volume characteristic of oilfield engineering services, avoiding interface timeouts or data truncation caused by excessive concurrency |
| Node ID binding | Fix `nodeId` as the approval status synchronization node | Ensures that multiple variable update nodes are uniformly connected to the specified reply node, resolving the issue where variables cannot be synchronized to a single reply |
| File parsing configuration | Adapt to JPG, MP4, and PDF format parsing | Matches common formats of on-site construction images, log documents, and test reports, ensuring unstructured attachments can be read and referenced normally |

## Three Common Misconfigurations
- Phenomenon: The output of multiple variable update nodes cannot be synchronized to a single AI reply, and some fields are displayed empty on the interface. Cause: The real-time update configuration of `variables` is not enabled, causing downstream nodes to fail to obtain the latest variable values.
- Phenomenon: A parameter missing error is returned when calling the API for obtaining opening statements. Cause: The operation type field in the business process data is not bound as the trigger condition for opening statement generation, causing the node to fail to generate guidance content matching the scenario.
- Phenomenon: A 504 timeout error occurs when calling the workflow API externally. Cause: The concurrency threshold is not adjusted according to the single operation data volume, and excessive concurrency exceeds the system carrying capacity leading to request backlog. This threshold can be adjusted in the API configuration page in FastGPT v4.17.0.

## How to Confirm the Configuration Is Complete
- Trigger the business process of a test project, check the debug logs of each workflow node, and confirm that fields such as approval status and operation duration in `variables` are all the latest values.
- Call the API for obtaining opening statements, check whether the returned content matches the operation type of the current test project, and confirm that the bound fields of the node are correct.
- Launch a multi-concurrency external API call test, observe the interface return status, and adjust the concurrency threshold to a range without timeout errors.
- Check the node connection relationship of the workflow, confirm that all variable update nodes are connected to the specified reply node, and there are no disconnected or misconnected situations.
