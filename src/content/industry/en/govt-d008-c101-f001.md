# Port and Shipping Business Process Guidance: HTTP Interfaces and External Systems

## What the data for this category looks like
Business process handling data for ports and shipping mainly comes from internal business systems such as terminal operation systems, maritime supervision platforms, and customs declaration agency systems. The data update frequency varies by business type: real-time business application submission data is updated immediately, berthing plans are synchronized every hour, and manifest data is updated 24 hours before the vessel departs. Data is stored in structured JSON format. Core fields include voyage number, berth number, business type, processing status, submission time, and others. Business type is an enumerated value, time fields use the ISO8601 standard format, and container volume-related fields use TEU as the unit.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Data sources for port and shipping business process handling are scattered, covering multiple systems including terminal operations, maritime supervision, and customs declaration agencies. The data update frequencies of different systems differ significantly: real-time processing applications are updated upon submission, berthing plans are synchronized every hour, and manifest data is updated 24 hours before vessel departure. Data is stored in structured JSON format, with core fields including enumerated fields such as voyage number, berth number, business type, and processing status, and time fields using the ISO8601 standard format. These characteristics require HTTP interfaces to support format adaptation for multi-source data, polling intervals to match the update frequency of corresponding data, request parameters to strictly verify enumerated values and formats, and to pass the context of the current processing node, to avoid process guidance errors caused by data inconsistency or format errors.

## How to Configure
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {API key provided by the port EDI system}` | Bearer token authentication is commonly used for port external business interfaces, to ensure requests are called by legitimate systems |
| `variables` | Pass core business identifiers such as vessel name, voyage number, and business order number | Business process guidance needs to generate steps based on specific business context, so variables must match the unique identifier fields of port business |
| `responseData` | Extract processing status, current processing node, and remaining processing time limit | Process guidance needs to dynamically adjust based on real-time business status; extracting only core fields reduces context transmission load |
| Interface timeout setting | `600 seconds` | Port business process handling usually includes multi-link interactions; a longer timeout avoids interrupting guidance due to temporary network fluctuations |
| Data polling interval | `30–60 seconds` | Matches the update frequency of real-time port processing data, balancing real-time performance and external system call load |
| Response format verification | Configure according to the interface documentation provided by the port system | Port business data has strict field format requirements; non-compliant responses will cause process guidance logic exceptions |

## Three Common Errors
- Symptom: The HTTP request module fails to parse the Set-Cookie field in the interface response, and subsequent requests cannot carry session credentials. Cause: Automatic cookie management configuration of the FastGPT HTTP request module is not enabled, and session identifiers are not persisted.
- Symptom: Calling the FastGPT application creation interface returns authentication failure, and the application key cannot be obtained. Cause: The `Authorization` parameter is not configured correctly, or an invalid authentication token is used.
- Symptom: The business processing status returned by process guidance is empty, and corresponding steps cannot be generated. Cause: Core business fields are not correctly extracted from `responseData`, or the data polling interval does not match the update rhythm of the port system.

## How to Confirm the Configuration is Properly Set Up
- Call the configured HTTP interface, check if the returned `responseData` includes the preset core business fields, and that the field format matches the interface documentation provided by the port system.
- Simulate different business processing nodes, verify that parameters such as vessel name and voyage number passed in `variables` are correctly transmitted to the interface request, triggering the corresponding process guidance.
- View the interface call logs, confirm that the `Authorization` parameter is correctly carried, and no authentication failure error messages appear.
- Adjust the data polling interval, compare with the real-time data update status of the port system, and confirm that the business status update of the process guidance matches the actual progress.
