# Port and Shipping Business Process Guidance: Deployment and Upgrade

## What the data for this category looks like
Port and shipping business processing data mainly comes from port production scheduling systems, maritime supervision platforms, and customs clearance systems. The data primarily consists of structured fields, including vessel name, voyage number, berth number, operation type, processing node, estimated duration, and more. Some supporting unstructured data consists of scanned paper documents. Data updates are triggered per single operation workflow; relevant data for a single processing task is synchronized and archived after the workflow ends. Regular business data is batch synchronized hourly. Field units uniformly follow industry standards: time fields use the ISO 8601 format, and operation volume fields use TEU or standard containers.

## What constraints these characteristics impose on the deployment and upgrade link
Port and shipping business data has a high degree of structuring and strict field specifications. During deployment, ensure database connection configurations adapt to structured query logic to avoid reduced query efficiency. Real-time or high-frequency synchronized business data requires configuring reasonable connection pool parameters during deployment to prevent server overload. When upgrading across versions, back up the full data directory in advance to prevent data loss during the upgrade process. Large-sized unstructured document scan files require configuring storage services that support large file read/write operations during deployment; during upgrade, synchronize storage configurations to ensure normal business operation. Port business workflows usually do not allow long interruptions, so the upgrade process must maintain compatibility with the configuration logic of old-version business processing nodes.

## How to set the configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://username:password@host:port/fastgpt?authSource=admin` | Port business data is stored in a structured MongoDB database, requires specifying the authentication source and corresponding business database |
| `REDIS_URL` | `redis://:password@host:port/0` | Used to cache high-frequency queried vessel schedule and berth data, specifies database index 0 to isolate business cache |
| `STORAGE_S3_ENDPOINT` | Port internal object storage domain name | Ports usually deploy private S3-compatible storage services internally, used to store document scans and business logs |
| `DB_MAX_LINK` | `20–30 connections` | Port business concurrency is relatively high, avoid too many connections causing database overload, while reserving sufficient connections for business processing workflows |
| `FE_DOMAIN` | `https://port business processing system domain name` | Used to generate jump links for business processing pages, must comply with internal domain name rules |
| `ROOT_KEY` | Calibrated via actual testing | Used to initialize administrator permissions, must comply with port internal key management specifications |

## Three common mistakes
- Phenomenon: After upgrade, historical data of business processing workflows cannot be loaded, and the interface returns a 500 status code. Cause: Failed to properly migrate the MongoDB data directory during cross-version upgrade, or failed to update the `MONGODB_URI` configuration to point to the new database instance.
- Phenomenon: Upload of large-sized document scan files fails, and the interface prompts insufficient storage space. Cause: Did not configure `STORAGE_S3_ENDPOINT` to point to the port's internal private storage, and mistakenly used a public storage service resulting in insufficient quota.
- Phenomenon: Node configuration of business processing workflows is lost, and subsequent links cannot be triggered normally. Cause: Did not back up Redis cache data before upgrade, causing cached node configuration to be lost after restart.

## How to confirm the configuration is correct
- Log in to the FastGPT admin backend, run the database connection test, confirm that the connection tests for `MONGODB_URI` and `REDIS_URL` pass.
- Upload a standard port document scan, confirm that the file can be stored normally and called in the nodes of the business processing workflow.
- Trigger a simulated business processing workflow, confirm that the configuration of each node can be loaded normally with no error prompts.
- Check the FastGPT version information, confirm that the currently running FastGPT version is v4.17.0, which meets the target upgrade version requirements.

The values provided are common starting points and should be measured against the reader's own samples.
