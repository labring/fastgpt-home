# Business Process Guidance for Coal Transportation and Sales: HTTP Interfaces and External Systems

## What This Category of Data Looks Like
Coal transportation and sales business data mainly comes from three internal systems: transportation plan management system, weighing system, and contract settlement system. Data updates are primarily triggered by individual waybill processing nodes. Batch statistical data is synchronized hourly. Individual business data includes fields such as waybill number, coal type, departure location, arrival location, actual shipped weight, settlement amount, and current processing node status. Weight is measured in tons, amount in yuan. Time fields use the YYYY-MM-DD HH:mm:ss format. This page is compatible with FastGPT v4.17.0.

## Constraints Imposed on HTTP Interfaces and External Systems
Coal transportation and sales business data comes from dispersed sources. Multiple external system interfaces must be connected. Request endpoint configurations must distinguish addresses and authentication methods for different data sources. Real-time updated business data requires interface response delays to meet business processing tolerance thresholds. This prevents workflow blocking. Fields include clear physical quantities and units. Interface request parameters must strictly match field names and unit rules. Otherwise, external system verification fails. The circulation logic of processing node status must be synchronized via interfaces. Request bodies must carry current node identifiers and change timestamps. This ensures external systems correctly identify business progress.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `Authorization` | Carry a system access token in Bearer format | Complies with authentication standards for internal coal transportation and sales systems, ensuring secure interface calls |
| `variables` | Bind waybill status fields returned by external interfaces | Enables automatic synchronization of workflow global variables and external business data |
| `responseData` | Extract specified fields for workflow judgment | Quickly retrieves core business data such as actual shipped weight and settlement amount returned by external systems |
| Timeout | 600 seconds | Matches average response durations for weighing and settlement links in coal transportation and sales, preventing workflow blocking |
| Request Field Mapping | Match units and formats as required by external systems | Ensures transmitted data such as weight (tons) and amount (yuan) complies with external system verification rules |
| Retry Mechanism | Retry 2 times after failure, with a 30-second interval | Addresses network fluctuations or temporary external system failures, improving interface call success rates |

## Three Common Misconfigurations
- Phenomenon: Workflow global variables are not assigned after interface calls, and the returned result is empty. Cause: The `variables` configuration item is not correctly bound to the fields returned by the external interface, or the field names do not match correctly.
- Phenomenon: Interface calls return a 400 error, prompting parameter format mismatch. Cause: Units and formats of weight and amount are not transmitted as required by external systems. For example, actual shipped weight is not transmitted in tons.
- Phenomenon: Interface calls time out, and the workflow is interrupted. Cause: The timeout configuration is too short, failing to match the long response duration of coal transportation and sales settlement links, or external systems have temporary high load.

## How to Verify Correct Configuration
- Call the test interface. Check if the returned `responseData` includes expected core waybill fields. Verify that field formats and units comply with external system requirements.
- Check workflow global variable values. Confirm that fields bound via `variables` have correctly synchronized data returned by external interfaces.
- Simulate business node triggers for interface calls. Check if the retry mechanism is activated. Confirm that timeout and retry configurations meet business scenario tolerance ranges.
- View interface call logs. Confirm that the `Authorization` header carries the token correctly, and authentication verification passes.

All configuration values provided here are common starting points. They should be evaluated against local operational samples.
