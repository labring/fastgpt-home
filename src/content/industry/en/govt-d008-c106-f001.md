# Workflow Guidance for Coal-Electricity Integrated Business: HTTP Interfaces and External Systems

## What the Data for This Category Looks Like
Data is sourced from the internal production scheduling system, business approval platform, and materials management system used for coal-electricity integrated operations. Data updates are triggered at business process nodes, and syncs when an approval is submitted, routed, or completed. This is a structured business form that includes fields such as application number, mine code, power generation plan volume, and approval node status. Units include business-specific metrics like tons, megawatts, and pieces. The size of a single record varies based on business complexity, with no fixed length.

## What Constraints These Characteristics Impose on HTTP Interfaces and External Systems
The structured fields and custom units of coal-electricity integrated business data require that HTTP interface requests strictly match the field names and units of the business form to avoid parameter mapping errors. The node-based update rhythm requires interface calls to be bound to business event triggering mechanisms to support real-time update requirements. The large fluctuation in single record size requires interfaces to support dynamic parsing of return data with varying structures. It also requires preset targeted parameter mapping templates to ensure external systems can correctly identify the core content of business requests.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` configuration | Use Bearer token format, set token validity period to 7 days | Comply with internal security and compliance requirements of state-owned enterprises and government institutions, match access permissions for business data |
| Request timeout | 60–120 seconds | Coal-electricity business processes involve cross-system collaboration, and response delays are generally higher than general scenarios |
| `variables` mapping configuration | Bind dedicated business fields such as mine code, power generation plan volume | Match the field structure of structured business forms to avoid parameter mapping errors |
| `responseData` parsing rules | Extract core business fields such as approval status, application number | Adapt to the standardized data structure returned by external systems and simplify downstream processing |
| Retry trigger condition | Triggered by status code 5xx or timeout, retry count is 2 times | Avoid repeated submission of business process requests and prevent duplicate approvals or data anomalies |

## Three Common Misconfigurations
- Phenomenon: An API error is returned when calling the interface, all configuration parameters are filled according to specifications, and the authentication token and interface address are both verified correctly. Cause: The dedicated `variables` field mapping for coal-electricity business is not bound, causing the external system to fail to recognize the business meaning of the request parameters.
- Phenomenon: Field values of business process data are empty or units do not match. Cause: The `responseData` rule is not used to extract core business fields, and redundant data returned by the external system is directly parsed.
- Phenomenon: Frequent retries are triggered by interface calls, leading to repeated submission of business processes. Cause: 4xx status codes are included in the retry trigger conditions, mistakenly judging parameter errors as network exceptions.

## How to Verify Correct Configuration
- Call the test interface, check whether the request header carries a token that conforms to the `Authorization` format, and verify that the authentication configuration takes effect.
- Send a simulated business request, check whether core business fields such as mine code and power generation plan volume are extracted from the returned data, and verify that the `responseData` parsing rules take effect.
- Simulate the return result of timeout or 5xx status code, check whether the retry mechanism is triggered, and verify that the retry trigger condition configuration is correct.
- Submit a real business process request, check whether the external system correctly receives and parses the request parameters, and verify that the overall configuration matches business requirements.
