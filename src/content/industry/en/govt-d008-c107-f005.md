# Business Process Guidance for Coal Mine Production: Tool Calling and Plugins

## What the data for this category looks like
Coal mine production business process data mainly comes from four types of systems: underground operation dispatching systems, safety supervision ledgers, equipment operation and maintenance archives, and license approval platforms. Data update rhythm falls into two categories: data such as operation applications and approval progress are updated in real time with process nodes, while data such as equipment qualifications and personnel licenses are updated according to approval cycles. A single business document includes fields such as operation type, operation area, equipment number, approval node, and applicant qualifications. Most field formats are coded content combining letters and numbers, with units including hours, pieces, equipment units, person-times, and similar units.

## What constraints these characteristics impose on the tool calling and plugins workflow
Multiple independent systems store coal mine production business data. Different systems use widely varying interface field formats, so tool calling requires configuring multiple sets of field mapping rules to avoid request failures caused by parameter mismatches. Real-time updated operation process data requires tool calling to bind to the corresponding approval node trigger. Fixed-cycle calls cannot cover the entire process scenario. At the same time, coal mine business data involves production safety and personnel qualification privacy. Tool calling only runs in an intranet environment, and additional permission verification rules must be configured. The length and format of coded fields have no unified standard, so tool calling requires dynamic adaptation to the parameter requirements of different systems during execution.

## Configuration Settings
The following configurations are based on the `toolChoice` and `functionCall` parameter logic of FastGPT v4.17.0, adapted to the business handling scenario of coal mine production:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Tool calling trigger timing | Triggered by business approval nodes | Matches the approval process logic of coal mine business handling to avoid invalid calls |
| `toolChoice` | auto | Automatically matches API tools available at the current node to adapt to multi-system docking requirements |
| Timeout period | 180–300 seconds | Matches the conventional response duration of coal mine business approval to avoid process blocking |
| Response field mapping rules | Match according to system preset templates | Adapt to the field format differences of different business systems and reduce manual adjustment costs |
| Permission verification switch | Enabled | Complies with coal mine data security compliance requirements and restricts access only to the intranet |
| `functionCall` | Bind interfaces by node | Accurately bind the API of the corresponding approval node to ensure that requests carry correct business parameters |

## Three Common Misconfigurations
- Calling a third-party API fails to parse the Set-Cookie field, resulting in subsequent requests returning a 401 status code. The cause is that the HTTP request module’s Cookie persistence rule is not configured correctly, so session credentials are not retained.
- Triggering tool calling at process start returns no valid data, shown as empty fields on the business handling page. The cause is that tool calling is not bound to the API parameters of the corresponding business node, so requests do not carry required fields such as operation number and equipment ID.
- Business pictures obtained via API calls cannot display in third-party systems, shown as an access restricted prompt for the link. The cause is that the intranet access whitelist is not configured, so external systems cannot access the coal mine intranet’s picture storage interface.

## How to Verify Successful Configuration
- Submit a simulated underground operation application form, and check whether the tool calling log displays correct API request parameters and response results.
- Initiate a tool calling request, and check whether the interface returns Cookie fields that are correctly stored and applied to subsequent API requests.
- Access the bound third-party business system page, and verify that picture links obtained through the API load normally.
- Trigger a tool call configured with streaming output, and check whether the returned result displays in a segmented push format.
