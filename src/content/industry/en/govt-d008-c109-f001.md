# Business Process Guidance for Power Grid Enterprises: HTTP Interfaces and External Systems

## What this category of data looks like
Data related to power grid enterprise business process guidance comes from the internal power grid marketing business application system and the 95598 customer service ticket system. Data updates occur via real-time push after business submission, or hourly batch synchronization. The document structure includes fields such as ticket ID, business category, current processing node, associated user ID, processing status, and estimated completion time. The business node code is a 6-digit numeric string. Processing status uses fixed enumeration values. The unit for estimated completion time is hours. Business categories cover common power grid service scenarios such as electricity installation, power outage repair, and business expansion installation.

## What constraints these characteristics impose on HTTP interfaces and external systems
The internal source of power grid business process data requires interfaces to configure authentication parameters to connect to the internal system’s permission framework. The real-time or near-real-time update rhythm requires interface response latency to stay within a reasonable range to prevent lag in the process guidance link. Structured fields including business node code and processing time limit require the `responseData` returned by the interface to strictly match the field definitions of the business system. Otherwise, guidance content for the corresponding process node cannot be triggered. The multi-category business structure requires dynamic parameters to pass business context, enabling differentiated process guidance configuration for different businesses.

## Three Common Mistakes
- Phenomenon: The interface call gets stuck for 10 seconds before returning an empty response. Cause: No reasonable interface timeout period is configured, or the timeout period is set too long, causing the process guidance link to wait for timeout and fail to handle empty results correctly.
- Phenomenon: The `responseData` field lacks the business node code, causing process guidance to fail to match the corresponding steps. Cause: The response field mapping is not configured according to the field definitions of the power grid business system, and non-key fields are incorrectly extracted.
- Phenomenon: Occasional interface call failures directly return errors without triggering the retry mechanism. Cause: No interface retry strategy is configured, or the retry count is set to 0, resulting in no remediation after a single call failure.

## How to Verify Correct Configuration
- Call the configured HTTP interface, check whether the returned `responseData` contains key fields such as business node code and processing status, and whether the field format complies with the definitions of the power grid business system.
- Simulate calls for different business types, pass different business category parameters through `variables`, and check whether the guidance content returned by the interface matches the corresponding business scenario.
- Simulate network fluctuations or temporary system unavailability scenarios, check whether the interface triggers the retry mechanism, and whether data can be normally obtained after retries.
- View the FastGPT running logs to confirm that the `Authorization` parameter for interface calls has been correctly carried, and there are no authentication failure error messages.
