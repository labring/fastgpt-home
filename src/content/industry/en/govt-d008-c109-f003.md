# Business Process Guidance for Power Grid Enterprises: Multi-turn Dialogue and Prompt Engineering

## What the Data for This Category Looks Like
The business process data for power grid enterprises mainly comes from internal marketing systems, offline service counters, and public service platform publicized power application process information. The latest power application process changes are synced daily, and the common problem and consultation script library is updated weekly. Individual business data entries are split by power application type, and include fields such as business code, applied voltage level, required material list, processing steps, processing time limit, consultation channel, etc. The business code uses a 12-digit numeric format, processing time limit is measured in working days, and the material list is stored as a structured list.

## What Constraints These Characteristics Impose on Multi-turn Dialogue and Prompt Engineering
Power grid business data is segmented by power application type and has strict compliance requirements. Multi-turn dialogue must first identify the user's specific power application scenario via keyword matching to avoid calling incorrect process data. Data fields have clear unit and format constraints, and prompts must strictly follow field formats when generating guidance content, such as requiring users to provide a 12-digit business code or explicitly stating that processing time limits use working days. Due to the high update frequency of the data, dialogue context must filter expired process information. Additionally, the `messages` parameter must distinguish between user input and system prompt content to avoid confusing interaction logic. The context management mechanism of FastGPT v4.17.0 must adapt to the storage and calling of this structured data.

## Configuration Setup
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Maximum context length | 8000–12000 token | Power grid business process documents have relatively long individual content, requiring retention of complete process and historical interaction information |
| Context retention turns | Last 3–5 dialogue turns | Avoids redundant old data interfering with current business judgment, and adapts to the interaction scenario of multi-turn guidance |
| Variable binding configuration | Bind the business type field in `variables` | Quickly locate the dedicated knowledge base data for the corresponding power application process |
| Dialogue trigger rule | Match business categories via power grid power application keywords | Accurately call process and script data for the corresponding scenario |
| Session timeout setting | 600 seconds | Power grid business processing requires users to supplement materials, reserving sufficient interaction time |
| History record isolation | Clean specified application conversations individually by `chatId` | Isolate context from different business scenarios to avoid data confusion |

## Three Common Mistakes
- Symptom: Historical dialogue fields displayed in the debug preview are empty. Cause: The `messages` parameter is not configured correctly, and user input and system prompt content are not stored separately, resulting in failure to load context normally.
- Symptom: Dialogue contexts from different businesses interfere with each other, and the returned power application process does not match the current business. Cause: Session data from different applications is not isolated by `chatId`, resulting in incorrect reuse of context from different businesses.
- Symptom: The previous round's business conclusion cannot be used as input for the next round's prompt. Cause: Historical interaction conclusions are not passed via `variables`, and the context reuse rule is not declared in the system prompt, resulting in the inability to continue business logic in the dialogue.

## How to Verify Correct Configuration
- Access the debug preview interface, input power grid power application business keywords, and check whether the context area retains the last 3 rounds of dialogue content.
- After binding the `variables` field, input a specific business type keyword to verify whether the dialogue matches the dedicated data of the corresponding power application process.
- Copy the session identifier of the specified `chatId`, clean the historical records of this session via the application management interface, and verify whether the old content of this session is no longer displayed in the debug preview.
- After setting a 600-second timeout, pause input and wait for interaction, and verify whether the dialogue triggers a timeout prompt after the specified time.
