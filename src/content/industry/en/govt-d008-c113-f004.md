# Business Process Guidance for Shipbuilding: Workflow Orchestration

## What this category of data looks like
Data sources include ship block construction ledgers, classification society inspection documents, component delivery records from main engine supporting suppliers, and internal production scheduling work orders of shipyards. Updates advance with production milestones. Document lengths vary widely, ranging from dozens-of-page specialized inspection reports to thousands-of-page assembly design drawings. Document fields include block number, construction progress milestone, inspection item status, spare part model, and supplier information. Units used include millimeters, tons, operating hours, and voyages.

## What Constraints These Characteristics Impose on Workflow Orchestration
Shipbuilding data has dispersed sources, wide variation in document length, and uses engineering-specific units. These factors create multiple constraints for workflow orchestration. Dispersed multi-source heterogeneous data requires workflows to configure multiple nodes to pull data from different sources, avoiding overloading single nodes. Wide variation in document length requires workflow context processing nodes to dynamically adapt to input scale, preventing content truncation or excessive resource usage. Engineering-specific units require workflows to include built-in unit validation rules, ensuring accurate field matching across data sources. Data updates driven by production milestones require workflows to support on-demand triggering, adapting to temporary production data synchronization needs.

| Trigger Rule | Trigger on production milestone update events | Match the data update rhythm of shipbuilding to enable on-demand synchronization |

## Three Common Configuration Mistakes
- Workflows fail to return image recognition results after triggering, and interface display fields are empty. The cause is that no binding rule for image paths is configured in `variables`, causing nodes to fail to obtain target image resources.
- Processes are terminated during single-node operation, and server load alerts are triggered. The cause is that the configured node concurrency exceeds the server's hardware carrying limit, and the value is not adjusted based on actual testing.
- API calls to published workflows return timeout status codes. The cause is that the API access timeout setting is too short, failing to adapt to processing durations for large shipbuilding documents.

- Adjust the node concurrency to the set value, and use a stress testing tool to verify whether the single-node load falls within a reasonable range.
