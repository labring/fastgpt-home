# Business Process Guidance for Rail Transit Equipment: HTTP Interfaces and External Systems

## What data for this category looks like
Business-related data for rail transit equipment comes primarily from on-board sensor systems, operation and maintenance records, and production scheduling systems. Real-time operating parameters update every second. Repair and process node data syncs daily. Data documents are stored in structured JSON format. Core fields include unique device ID, axle temperature (unit: ℃), cumulative operating mileage (unit: km), business process node ID, and process status code. Some fields require association with corresponding repair batch numbers. There are no redundant nested levels.

## What constraints these characteristics impose on HTTP interfaces and external systems
High-frequency updates of real-time operating parameters require interface request intervals to stay below a preset threshold. This avoids process guidance deviations caused by data lag.
Structured fields must strictly match preset key names. If a request does not include the associated repair batch number, the interface returns an empty dataset.
For scenarios with parallel processing of multiple devices, the interface must support requests grouped by device ID. Otherwise, the single returned data volume will exceed the transmission limit.
Process status codes must correspond one-to-one with business nodes. The interface response must retain the original status code field, and no unauthorized conversion is allowed.

## How to configure
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Interface timeout period | 60 seconds | Matches the update interval of real-time rail transit equipment data, prevents process interruptions caused by wait timeouts |
| Request header configuration | Carry the `Authorization` field with a preset API key as its value | Complies with identity verification requirements of external systems, prevents unauthorized access |
| Variable mapping rule | Map device IDs and repair batch IDs to the `variables` parameter | Adapts to the multi-device parallel request logic of external systems, ensures accurate data association |
| Response data parsing path | Extract business status fields from the `responseData` root node | Matches the structured storage format of rail transit equipment data, simplifies field extraction |
| Failure retry count | 3 times | Offsets the impact of network fluctuations or temporary unavailability of external systems, improves process guidance stability |
| Batch request device count | First 20 devices | Controls the data volume of a single request, avoids exceeding interface transmission bandwidth limits |

These configuration items are designed based on the interface logic of FastGPT v4.17.0.

## Three common configuration mistakes
- An interface returns a 500 status code with a prompt that the commercial version link is not configured. The cause is that the external system's non-commercial version interface permission was not added in the FastGPT configuration, causing the request to be blocked.
- The interface returns an empty dataset, and business process nodes cannot be identified. The cause is that the request does not carry the repair batch ID field, so the external system cannot match the corresponding business data.
- Tool call results have deviations, leading to incorrect process guidance. The cause is that the `variables` parameter was not mapped according to device IDs, causing incorrect data association and returning business information for unrelated devices.

## How to confirm the configuration is complete
- Send a test request, check whether the `Authorization` field is correctly carried in the request header.
- View the interface response, confirm that business fields under the `responseData` root node have been correctly extracted.
- Simulate a multi-device request, verify that the number of batch request devices meets the preset rules.
- Trigger a failure scenario, confirm that the retry mechanism executes according to the configured number of times.

The values provided are common starting points and should be measured against the reader's own samples.
