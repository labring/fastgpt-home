# Business Process Guidance for Communication Towers and Infrastructure: HTTP Interfaces and External Systems

## What the data for this category looks like
The business data for communication towers and infrastructure primarily comes from three data sources: tower operation and maintenance management platforms, base station inspection reporting systems, and resource scheduling centers. Data update frequencies fall into two categories: real-time (base station load, available bandwidth) and daily (site basic information, rental status). The document structure is organized per single site, including fields such as site ID, longitude and latitude coordinates, rated load power, available bandwidth, business process progress, and more. Longitude and latitude use decimal degrees as the unit, power is measured in kilowatts, bandwidth in Mbps, and business progress uses a status percentage format.

## What constraints these characteristics impose on the HTTP Interfaces and External Systems link
Multi-data source access requires interfaces to support different authentication rules and field mapping logic. Pulling real-time data requires controlling request intervals to avoid triggering rate limits. Units for fields such as longitude and latitude and power must strictly match external system standards, otherwise the process guidance will display incorrect information. Daily updated basic data does not require frequent pulling, and a reasonable cache cycle can be set to reduce interface call pressure. Real-time load data, however, requires short-interval requests to ensure the real-time performance of business processing.

## How to configure the settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer Token, carrying the exclusive key assigned by the platform | Matches the standard authentication specification of communication tower operation and maintenance systems |
| `variables` | Map site ID and business type as request input parameters | Matches the parameter verification rules of external interfaces |
| `responseData` | Extract site status and available bandwidth fields as process guidance data sources | Ensures correct reading of business data |
| Interface timeout period | 30 seconds | Adapts to the average response delay of real-time load interfaces |
| Request retry count | 2 times | Addresses request failures caused by temporary network fluctuations |

## Three common mistakes
- An interface returns a 401 Unauthorized error. The root cause is that the `Authorization` parameter is not configured correctly, and an expired or invalid authentication key is used.
- The base station longitude and latitude displayed in the process guidance have excessive deviation. The root cause is that correct unit conversion rules are not configured in `variables`, and original degree-minute-second format data is used directly.
- The interface triggers rate limit interception. The root cause is that a reasonable request interval is not set, and frequent calls exceed the call frequency limit of the tower operation and maintenance system.

## How to verify successful configuration
- Call the configured test interface, and check whether expected fields such as site ID and available bandwidth are included in the returned `responseData`.
- Check whether the format of the `Authorization` parameter conforms to the Bearer Token specification, and whether the key matches the one assigned by the external system.
- Simulate a business processing request to confirm that the process guidance can correctly pull and display the real-time business status of the corresponding site.
- Adjust the request interval to 10 seconds, call the interface 5 times consecutively, and confirm that no rate limit interception is triggered.
