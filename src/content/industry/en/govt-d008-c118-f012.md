# Business Process Guidance for Metal Material Processing: Deployment and Upgrade

## Data Characteristics for This Category
Business processing data for metal material processing primarily originates from internal enterprise production scheduling systems, quality inspection platforms, and order management modules. Data updates trigger alongside production batches. The update frequency for single delivery order data is once per day.
Each business document includes fields such as order number, metal grade, processing procedure requirements, delivery deadline, and quality inspection report number. Units include tons, millimeters, hours, batch numbers, and others. Document length typically ranges from 500 to 1500 characters. Some documents include attached quality inspection scan files.

## Constraints Imposed on Deployment and Upgrade
The characteristics of metal material processing business data impose three core constraints on the deployment and upgrade phase.
First, data sources are scattered. During deployment, API permissions for multiple internal systems must be integrated. Configure `STORAGE_S3_ENDPOINT` to connect to the enterprise’s internal object storage for storing quality inspection attachments.
Second, data updates trigger with production batches. Set `DB_MAX_LINK` to limit the number of concurrent connections for cross-system data pulling, to avoid occupying core resources of production systems.
Third, document structures include multiple business fields and attachments. During upgrades, verify the knowledge base field mapping logic. Also configure `REDIS_URL` to cache parsed text and improve retrieval efficiency.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| `STORAGE_S3_ENDPOINT` | `http://internal-metal-storage:9000` | Connect to the enterprise’s internal object storage for storing quality inspection scan files and procedure documents related to metal material processing |
| `REDIS_URL` | `redis://:securepass@internal-redis:6379/0` | Cache parsed business document text to reduce repeated parsing overhead |
| `DB_MAX_LINK` | `10–15` | Limit concurrent data pulling connections across production systems to avoid occupying core resources of the enterprise production database |
| `MONGODB_URI` | `mongodb://fastgpt:dbpass@internal-mongo:27017/fastgpt?authSource=admin` | Store business process guidance configurations and user interaction logs |
| `PG_URL` | `postgresql://fastgpt:pgpass@internal-pg:5432/fastgpt` | Store knowledge base metadata and retrieval statistics data |
| `FE_DOMAIN` | `https://fastgpt-metal.enterprise.com` | Configure the frontend access domain name to comply with enterprise internal domain rules |

## Three Common Misconfigurations
- Issue: After upgrading FastGPT v4.17.0, calling a local m3e model returns empty results. Cause: `REDIS_URL` is not correctly configured to cache intermediate parameters for model calls, leading to loss of model loading status.
- Issue: When executing batch business process guidance tasks, a null value returns after the loop index increments by 1. Cause: `DB_MAX_LINK` is not set to limit concurrent connections, leading to exhaustion of the database connection pool and failure of some requests to obtain valid data.
- Issue: After Docker deployment, the file parsing module fails to correctly upload quality inspection attachments. Cause: `STORAGE_S3_ENDPOINT` is not configured to connect to the enterprise internal storage, leading to incorrect attachment upload paths and failure to correctly store parsed text.

## How to Verify Proper Configuration
- Access the configured `FE_DOMAIN` to confirm the frontend page loads normally, with no domain resolution or cross-origin errors.
- Upload a metal material quality inspection scan file, and check for the presence of parsed text fragments in the cache service corresponding to `REDIS_URL`.
- Call the built-in database connection test interface to confirm that databases configured with `MONGODB_URI` and `PG_URL` can establish normal connections.
- Submit a batch business processing request, and verify that the concurrent connection count corresponding to `DB_MAX_LINK` in the system logs does not exceed the set upper limit.
