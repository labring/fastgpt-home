# Railway Operations Business Process Guidance: Tool Calling and Plugins

## What the data for this category looks like
Railway operations business process data is sourced from official scheduling systems, ticket service interfaces, and station business operation logs. Update frequencies are split into real-time (remaining tickets, queue progress) and fixed daily cycles (timetable adjustments, train number changes). The data document structure includes fields such as train ID, departure and arrival stations, processing time, business type (ticket sale/rescheduling/refund/ticket checking), remaining quota, and more. Train ID is a string combining letters and numbers. The unit for remaining quota is "tickets". The time format is YYYY-MM-DD HH:MM. Business type is a fixed enumeration value.

## What constraints these characteristics impose on the tool calling and plugins link
Real-time requirements for railway business data mean tool calling response latency must not be excessive. Otherwise, returned data such as remaining tickets and queue progress will become invalid, leading to errors in the guidance process. Enumerated business fields require the large model to match preset values when calling tools, otherwise parameter verification failures will be triggered. The fixed field structure requires input parameter mapping to strictly correspond to preset key names, otherwise business data cannot be correctly obtained. Railway business data also has permission restrictions. Tool calling must carry valid identity verification parameters to avoid unauthorized access.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | Railway business process guidance includes multiple steps, requiring the large model to independently select corresponding tools to complete the guidance |
| `functionCall` | `Only allow specified functions` | Strict permission restrictions exist for railway business data, to avoid security issues caused by calling unauthorized tools |
| Timeout Setting | `10-15 seconds` | Matches the return latency of real-time railway data, avoiding data invalidation caused by timeouts |
| Input Parameter Variable Mapping | `Bind by preset railway business field names` | Railway business data fields are fixed, and preset key names must be strictly matched to correctly obtain data |
| Result Verification Rule | `Filter business type fields that are not enumeration values` | Railway business types are fixed enumeration values, and verification can avoid returning invalid guidance information |

## Three common misconfigurations
- Phenomenon: Ticket-related images returned by MCP are not fully displayed, and a 403 status code appears in logs. Cause: No session identity verification field for railway business is carried in tool calling parameters, resulting in interception of image resource access.
- Phenomenon: MCP calls are unstable, and the interface frequently displays "tool not responding". Cause: The timeout setting does not match the return latency of real-time railway data, and the default timeout is too short, causing requests to be terminated early.
- Phenomenon: Input parameters from HTTP responses cannot be added to the MCP configuration. Cause: Preset railway business field names are not used as input parameter keys, resulting in the configuration being unable to recognize valid variables.

## How to confirm the configuration is complete
- Trigger a simulated business processing request, and check whether preset railway business field parameters are correctly carried in tool calling logs.
- Perform a complete process guidance test, and confirm that the tool selected by the large model fully matches the current business node.
- Simulate a delayed request, verify that no timeout errors occur during tool calling, and confirm that the timeout setting meets requirements.
- View the input parameter mapping list of the MCP configuration, and confirm that all required railway business fields have been correctly added.
