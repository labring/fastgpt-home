# Business Handling Process Guidance for Expressway Operations: Deployment and Upgrade

## What the data for this category looks like
Business handling data for expressway operations mainly comes from three types of data sources: toll collection systems, road network operation and maintenance ledgers, and offline business window archives. Data update frequencies are divided into three categories: real-time (toll transactions, real-time work orders), daily (window business statistics), and monthly (operation and maintenance compliance reports). The document structure uses a structured format. Core fields include handling number, handling type (ETC activation, pass card reissue, abnormal appeal, etc.), handling time, handling location (toll station code), handling status, applicant information, and review result. The format of each field is string, enumeration value, ISO 8601 time format, toll station code string, status enumeration, natural person information string, and review result enumeration.

## Constraints imposed by these characteristics during deployment and upgrade
Dispersed data sources require connecting multiple heterogeneous systems during deployment. Cache services must be configured to reduce cross-system query latency. Multiple update frequencies require supporting switching between incremental and full synchronization during upgrades, to avoid full synchronization occupying business bandwidth. Structured fields contain sensitive natural person information, so permission control rules must be configured during deployment. Data volume grows as new toll stations are added, so sufficient database connections and storage resources must be reserved to adapt to business scale expansion.

## Three Common Misconfigurations
- Symptom: Returns curl error 60 or 7 when calling business data sources, unable to pull business data normally. Cause: Intranet SSL certificate not configured, or SSL verification for intranet services not skipped, causing requests to be blocked.
Reference only; verify against the target FastGPT release and deployment documentation.
- Symptom: Returns permission denied error when starting the service after deployment, unable to connect to the database or cache service. Cause: FastGPT deployment server IP not added to the intranet whitelist of the business database or cache service, or insufficient account permissions.

## How to Verify Successful Configuration
- Execute a local curl command to connect to `REDIS_URL`. A return of PONG indicates normal cache service connectivity.
- Access the database management page in the FastGPT backend, check the connection status of `PG_URL` or `MONGODB_URI` to confirm the database configuration takes effect.
- Upload a test identity proof image to verify that the signature logic of `FILE_TOKEN_KEY` operates normally, and that the file can be stored and accessed normally.
- Trigger a simulated ETC activation business handling process to confirm that the system can correctly pull the business rules for the corresponding toll station and return guidance steps.
