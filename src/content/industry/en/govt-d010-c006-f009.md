# Party Building Learning Q&A for Infectious Disease Information Reporting and Monitoring: Model Access and Configuration

## What data for this category looks like
Data for this category comes from the Chinese Center for Disease Control and Prevention Information System, medical institution HIS and infectious disease reporting systems, and laboratory testing systems. The update frequency is daily. Daily documents include infectious disease reporting cards, epidemic analysis reports, case correction records, clustered epidemic reports, and epidemiological investigation reports. Core fields cover basic case information, clinical diagnosis results, reporting time limits, correction notes, clustered epidemic association information, etc. Data must strictly comply with legal infectious disease reporting rules.

## What constraints these characteristics impose on the model access and configuration link
This category of data is updated daily and has dispersed sources. Model access configuration must adapt to the daily knowledge base refresh mechanism to avoid using expired data. Daily documents include structured reporting cards and semi-structured epidemiological investigation reports. The configuration link must support accurate parsing of multiple document types and field extraction. Data must strictly follow legal infectious disease reporting rules. Model output must retain the integrity and accuracy of original data fields, and must not arbitrarily alter or omit key information. The requirement for multi-source data docking also means the configuration link must support unified access and verification of multi-system interfaces to ensure consistency of data synchronization.

## Three common configuration mistakes
- The symptom is a `[FATAL] failed to get`-type error when starting the oneapi container, with logs pointing to lines related to `build/model/main.go`. The cause is that the deployment environment has no network access, and no internal proxy or offline deployment solution is configured, resulting in failure to pull models or interface resources.
- The symptom is that after connecting external conversation channels, the output of party building learning Q&A and disease control content contains a large number of meaningless punctuation marks such as # and *, and the interface display format is abnormal. The cause is that no cleaning rules are configured for residual marks after document parsing, causing format errors to be carried into the output content.
- The symptom is that after the rerank model is deployed, the matching degree between the recall results and case reports and party building learning content does not meet expectations. The cause is that no matching weights are configured for the rerank model for the core fields of this category, such as case diagnosis and reporting time limit, resulting in deviation of recall priority.

## How to confirm the configuration is complete
- Perform a parsing test on a single infectious disease reporting card, and check whether the output fields cover core content such as basic case information, diagnosis results, and reporting time limits.
- Trigger a daily knowledge base refresh task, and confirm that data synchronization and model update can be completed normally in the deployment environment.
- Launch a Q&A test related to party building learning, and check whether the output content complies with specifications and does not carry redundant punctuation marks.
- Call the model interface to view the return logs, and confirm that the `AIPROXY_API_TOKEN` verification is passed and the interface response meets expectations.
