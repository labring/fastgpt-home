# Party Building Learning Q&A for Petition Matter Handling: Multi-turn Dialogue and Prompt Engineering

## What the data for this use case looks like
Data for this use case comes from the national petition information system, local petition systems, the 12345 citizen hotline, grassroots governance platforms, historical petition archives, and party building learning-related policy documents. The update frequency is daily.
Commonly processed documents include petition registration forms, acceptance notices, transfer and assignment letters, handling opinions, review and re-examination applications, resolution plans, and party building-related policy documents. Covered fields include requester subject, matter content, handling progress, review results, and policy basis. Most content is structured text, with some unstructured content from scanned document transcriptions.

## Constraints on Multi-turn Dialogue and Prompt Engineering
Scattered data sources with daily updates require multi-turn dialogue to real-time link to the latest petition system data and party building policy documents, to avoid using outdated information. Diverse document types require prompts to adapt to different document field formats. For example, extract requester subject from petition registration forms, extract reply basis from handling opinions, and extract relevant guidance from party building policy documents.
Petition matters must strictly follow legal procedures. Multi-turn dialogue must retain historical conversation context to ensure consistency of handling opinions, while limiting context length to avoid exceeding model processing limits and preventing logical confusion. Additionally, prompts must incorporate party building guidance requirements to clarify rules for verifying petition acceptance scope, reducing risks of repeated petitions or petitions submitted outside the proper hierarchy.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Max Context Length | `8000–12000 characters` | Petition matter conversations need to retain multi-turn context including historical requests, handling progress, and party building policy references, to avoid exceeding model processing limits |
| Max Search Results per Request | Top 6 entries | Relevant documents for petition matters are mostly structured entries; the top 6 entries cover core handling basis, historical records, and party building policy-related content |
| Question Optimization | Enabled | Petition requests may use colloquial language; optimizing questions improves recognition accuracy for legal procedures, document fields, and party building policies |
| `variables` Configuration | Bind petition matter number, handling phase, and party building policy keyword fields | Dynamic transmission of current specific matter information and party building-related keywords during multi-turn dialogue ensures context consistency |
| Conversation Timeout Threshold | `600 seconds` | Petition matter handling conversations typically require long processing times; sufficient response duration ensures proper association of policies and matters |
| Reference Content Template | Calibrated based on actual testing | Needs to adapt to field formats of petition documents and party building policy documents, such as extracting reply content and party building policy basis from handling opinions |

## Three Common Misconfigurations
- Phenomenon: Significant discrepancy between online chat responses and API call results. Cause: The `messages` parameter is not correctly passed in API requests, so the API only uses a single prompt to generate content without retaining historical conversation context.
- Phenomenon: Referenced content does not match the current petition matter or party building policy. Cause: The configuration logic of reference content template and reference prompt template is confused, and extraction rules are not set for the exclusive fields of petition documents and party building policy documents.
- Phenomenon: Failure occurs during concurrent multi-turn dialogue requests. Cause: Node resource configuration is not adjusted to match the concurrent handling capacity of FastGPT v4.17.0, exceeding the system's load limit.

## How to Verify Proper Configuration
- Initiate a multi-turn dialogue simulating a petition request, check that the `chatId` remains consistent to ensure context is correctly retained.
- Call the API interface to send a request, confirm that the `variables`-bound petition matter number, handling phase and other fields are correctly passed to the conversation content.
- Test dialogues in different handling phases, check that referenced content comes from the corresponding document type, such as handling opinions and party building policy content during the handling phase.
- Review system operation logs to confirm no error messages about excessive context or missing parameters appear.

The values provided are common starting points and should be measured against the reader's own samples.
