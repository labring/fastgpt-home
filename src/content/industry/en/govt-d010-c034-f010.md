# Party Building Learning Q&A for Student Enrollment and Student Records Management: Knowledge Base Retrieval and Recall

## What This Category of Data Looks Like
This category of data comes from the National Primary and Secondary School Student Records Management System, local student enrollment platforms, household registration and property databases, and school academic affairs systems. Daily documents include enrollment application forms, student records information forms, transfer applications, enrollment plans, admission rosters, and student records change approval forms. Data is updated daily. Core fields include student ID number, household registration address, enrollment plan count, change approval status, and more. The core association dimension is based on student identity and admission eligibility.

## Constraints Imposed on Knowledge Base Retrieval and Recall
The daily update frequency requires the knowledge base to support incremental synchronization. This avoids time-consuming issues caused by full refreshes.
Establish unified field mapping rules for multi-source data. This ensures consistent formatting of core fields such as student ID numbers and household registration addresses across different sources.
Use adapted chunking logic for diverse document types. This ensures accurate recall of content such as enrollment policies and student records change approval forms.
Focus search keywords on student identity and student records transfer dimensions. This avoids mixing in unrelated data from other categories.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Meets precision requirements for core texts such as enrollment policies and student records rules |
| `limit` | Top 6 results | Controls total character count of recall results, adapting to context length limits of party building Q&A |
| `searchMode` | hybrid | Combines keyword and vector retrieval to meet recall needs for multiple document types |
| `usingReRank` | Enabled | Performs secondary ranking on recall results to improve relevance of policy-related texts |
| `datasetSearchUsingExtensionQuery` | Enabled | Automatically expands search keywords related to party building learning to cover policy interpretation content |
| `collectionIds` | Bound to category-specific knowledge base collection | Limits retrieval scope to avoid mixing in documents from other categories |

## Three Common Misconfigurations
- Symptom: Vector model call failure error occurs during knowledge base retrieval. Cause: The vector model was not correctly specified in the retrieval configuration, or environment parameters for model calls were not configured.
- Symptom: Recall results include large amounts of unrelated student records or enrollment content. Cause: The retrieval knowledge base collection was not limited via `collectionIds`, resulting in mixing of documents from other categories.
- Symptom: After calling MySQL student records data via Function CALL, the large language model cannot reference original database text snippets. Cause: The MySQL query results were not imported into the corresponding knowledge base collection, and `datasetSearchUsingExtensionQuery` was not enabled to associate retrieval results.

## How to Confirm Proper Configuration
- In the FastGPT v4.17.0 retrieval configuration interface, confirm that `collectionIds` is bound to the category-specific knowledge base collection ID.
- Enter enrollment policy keywords related to party building learning, and check whether the `similarity` score of recall results falls within the preset 0.75–0.85 range.
- After importing MySQL student records data via Function CALL, perform a retrieval, and confirm that the large language model output includes references to original database text snippets.
- Check the retrieval logs to confirm that the status of `usingReRank` and `datasetSearchUsingExtensionQuery` is enabled.
