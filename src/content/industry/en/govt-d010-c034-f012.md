# Party Building Learning Q&A for Enrollment and Student Status Management: Deployment and Upgrade

## What the data for this category looks like
The core data for this category comes from the National Primary and Secondary School Student Status Management System, local enrollment platforms, household registration and property data, and school academic affairs systems. Data is updated daily. Daily processing covers documents including enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, and student status change approval forms. Document fields include student ID numbers, household registration addresses, student status status, approval progress, and other details. There is no unified cross-system field format. Format adaptation is required for each data source.

## Constraints on the deployment and upgrade link
Deployments must include incremental synchronization tasks for daily updated data sources. This avoids excessive system resource usage from full data pulls. Deployments must support format conversion and index adaptation across multiple data sources to handle multi-source, heterogeneous document formats. Without this support, recalled content may be missing. Deployments must comply with government data storage compliance requirements for core data involving student identity and student status information. Clear constraints apply to encryption of sensitive fields and access permission configuration. Errors in student status change, admission verification, and other links may trigger compliance risks. Deployments must include log retention and exception alert mechanisms to ensure traceable operations.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `20–30 connections` | Meets concurrent connection needs when connecting multiple academic affairs and student status systems, preventing index failures caused by exhausted connections |
| `REDIS_URL` | `Local 6379 port instance, or managed Redis service` | Caches Q&A sessions and index metadata, reduces database query pressure, and supports session synchronization for multi-replica deployments |
| `STORAGE_S3_ENDPOINT` | `Configure per local object storage service address, such as 192.168.1.100:9000` | Stores enrollment application forms, student status change approval forms, and other data source documents uniformly, facilitating subsequent index updates |
| `PG_URL` | `Local PostgreSQL instance, port 5432` | Stores conversation logs and user permission configurations, complying with persistent storage specifications for government data |
| `ROOT_KEY` | `Random string generated for the deployment environment, 32 characters long` | Validates highest-level access to the system backend, preventing unauthorized configuration changes |

## Three common configuration mistakes
- Symptom: Running the `docker compose up` command results in image pull timeout, with progress stuck for more than 10 minutes. Cause: No domestic mirror acceleration source is configured. Access to the official image repository is slow, so service images required for FastGPT v4.17.0 cannot be pulled quickly.
- Symptom: Q&A recall results are insufficient in number, failing to cover full student status change approval process documents. Cause: The `DB_MAX_LINK` parameter was not adjusted. Low concurrent connection counts cause some data sources to fail indexing, so only partial document content is recalled.
- Symptom: Duplicate student status information matching errors occur after deploying multiple replicas. Cause: No distributed lock mechanism is configured for `REDIS_URL`. Multiple replicas process the same student status verification request at the same time, leading to duplicate data writes or matching conflicts.

## How to confirm successful configuration
- Run the `docker compose ps` command. Confirm all service containers are running, with no abnormal exits or restarts.
- Upload a standard enrollment application form document. Check the index progress via the backend index management page. Confirm the document was parsed successfully and a vector index was created.
- Submit a test query including "student status transfer process". Check if returned results match content from the local academic affairs system's transfer application documents.
- Access the domain name configured in `FE_DOMAIN`. Confirm the frontend page loads normally, and the backend login portal is accessible after validation via `ROOT_KEY`.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
