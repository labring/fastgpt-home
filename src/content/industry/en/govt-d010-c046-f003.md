# Party Building Learning Q&A for Social Assistance and Minimum Living Standard Verification: Multi-turn Dialogue and Prompt Engineering

## What data for this category looks like
Data for this category comes from the low-income population dynamic monitoring platform, resident family economic status verification system, and shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, and tax authorities. The update frequency is monthly. Daily processed documents include minimum living security application forms, family economic status verification reports, household survey forms, democratic appraisal records, public notice materials, and assistance approval forms. Data fields cover core information such as family income, property status, member relationships, and assistance qualification verification. Documents exist in a mixed format of structured forms and supporting materials.

## Constraints imposed on multi-turn dialogue and prompt engineering links
Monthly updated cross-department shared data requires dialogue systems to support regular synchronization of the latest verification data sources. This prevents use of expired information. The mixed multi-type document structure requires prompts to clearly distinguish call priorities between form fields and supporting materials. This ensures accurate information during the verification process. Multi-turn dialogue for sensitive fields such as family income and property must retain contextual associations. This reduces repeated inquiries. For scenarios combining party building policy learning and minimum living standard verification business, prompts must distinguish dialogue turns between policy Q&A and business verification. This avoids confusion.

## Three common misconfigurations
- Symptom: A parsing failure error is returned when calling the API to upload documents such as minimum living security application forms and family economic status verification reports. Cause: Chunking parameters are not adjusted for structured form documents, resulting in incomplete field recognition.
- Symptom: The response from the conversation application created via the API does not associate with the minimum living standard verification knowledge base content. Cause: The `variables` parameter is not correctly passed in the request to bind the data source of the corresponding knowledge base. Assistance verification related documents are not automatically mounted by default.
- Symptom: Differences exist between platform test conversations and API call results. Cause: The `chatId` of the test session and API call are not bound to the same context, resulting in inconsistent matched knowledge base entries.

## How to confirm correct configuration
- Initiate a simulated multi-turn dialogue. Check whether the dialogue context retains historical interaction information. Confirm that the `messages` parameter is configured correctly.
- Pass preset family information variables. Verify whether the dialogue automatically calls verification data from the corresponding data source. Confirm that the `variables` parameter takes effect.
- Upload a test verification document. Check whether the parsing result covers the core fields in the document. Confirm that the document parsing configuration is correct.
- Use the same `chatId` for both platform testing and API calls. Confirm that the results of the two calls are consistent. Confirm that the session binding logic is correct.
