# Party Building Learning Q&A for Social Assistance and Minimum Living Security Review: Forms and Interactions
This document is written based on FastGPT v4.17.0.

## What this category's data looks like
This category serves the full process of civil affairs assistance. Core participating entities include civil affairs bureau assistance departments, sub-district/township civil affairs offices, community neighborhood committees, and verification centers. Daily business documents include minimum living security application forms, family economic status verification reports, household survey forms, democratic review records, public notice materials, and assistance approval forms. Core fields cover family income, property status, member relationships, assistance qualification determination, and other related content. Data sources include the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-department shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, tax authorities, and other departments. The update frequency is monthly. Data must be cross-checked against offline household surveys and public notice records.

## What constraints these characteristics impose on the forms and interactions link
The monthly update requirement for cross-department shared data means forms must support regular synchronized verification data to avoid incorrect or missed assistance due to expired information. Field differences across multiple types of business documents require forms to adapt to input items for different stages. For example, the household survey stage needs to collect on-site supporting information. The public notice stage needs to collect mass feedback fields. The verification requirement for sensitive data such as family income and property means forms must support multi-field linkage verification, while ensuring the compliance of data interaction processes. The multi-entity participation in the assistance approval process requires forms to configure hierarchical permission interaction logic. This ensures that personnel in different positions can only operate content corresponding to their respective stages.

## Three common mistakes
- Phenomenon: After submitting the party building learning Q&A related to family economic status verification for the first time, the system does not return matching results. It returns normally after submitting the same question again. Cause: Real-time synchronization of cross-department shared data was not completed during the first query, and the knowledge base did not load the latest monthly updated verification data.
- Phenomenon: When submitting a test form, the verification prompt for the family income field is missing. Data omission is found after submission. Cause: Required verification was not set for the core fields configured in `formInput`, and key information related to family economic status was omitted.
- Phenomenon: The classify module in the workflow cannot select a model. It can normally call the specified model after publishing the workflow. Cause: Model permission configuration was not completed in the development environment. Publishing automatically inherits the model permission configuration from the production environment.

## How to confirm the configuration is correct
- Submit a test form containing family income and member relationship fields. Check whether the required field verification prompt is triggered, and confirm that the `formInput` configuration takes effect.
- Switch test accounts with different positions. Check whether only the form interaction entrance corresponding to the respective stage can be accessed, and confirm that the `userSelect` permission configuration is correct.
- Submit minimum living security policy Q&A related to party building learning. Check that matching business document content is returned on the first submission, and confirm that data synchronization and retrieval configurations are normal.
- View the classify module in the workflow. Confirm that the model options in the development environment and production environment are consistent, and confirm that the module configuration is correct.
