# Party Building Learning Q&A for Social Assistance and Minimum Living Allowance Review: Conversation Logs and Auditing

## What Data This Category Includes
This category's data comes from the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-department shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, and tax authorities. The update frequency is monthly. Daily documents include the minimum living allowance application form, family economic status verification report, household survey form, democratic review records, public notice materials, and assistance approval form. Core fields cover family income and property details, member relationships, household verification status, and approval flow node information. All data is linked to specific assistance application subjects and processing links.

## Constraints for Conversation Logs and Auditing
Monthly updated cross-department shared data requires logs to bind to corresponding assistance application batches and data access cycles. This ensures audits can match monthly verification actions. Multi-source data access requires logs to clearly distinguish call nodes from different systems, to avoid data confusion. Rich business documents and core fields require logs to record call parameters, return content, and associated application numbers for each conversation link. This supports traceability of incorrect or missed assistance guarantees. Strict accountability for assistance review requires logs to not lose key interactive information. Logs must fully retain conversation flow and decision basis, to facilitate subsequent inspection work for petitions or fund recovery.

## Configuration Settings
This configuration follows the log auditing module specifications for FastGPT v4.17.0. Specific configuration items are listed below:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind the assistance application number as a supplementary suffix, in the format `[application number]-[conversation session ID]` | Link to specific assistance applications, enabling quick location of conversation logs for the corresponding batch during audits |
| `responseChatItemId` | Generate a unique `responseChatItemId` for replies from each business node, such as the household verification node or public notice review node | Distinguish replies from different business links within the same conversation, enabling split auditing of content from each stage |
| `detail` | Enable `detail` log collection to store original return content from cross-department data calls | Meet the requirement of verifying cross-department data consistency during audits, and restore the full picture of data calls |
| Log storage period | Retain complete logs for 12 months | Match the review cycle of monthly assistance reviews, and meet regulatory traceability requirements |
| Log source tag | Mark log sources by access system tags, such as "verification system" or "tax shared data" | Quickly locate call exceptions from different data sources, and resolve issues with multi-source data confusion |
| Concurrent queue limit | Set the log write queue length for a single node to 200 entries, calibrated based on actual measurements | Adapt to concurrent call volume of 2-3 calls per second, avoiding data loss caused by log write overload |

## Three Common Configuration Errors
- Phenomenon: Cannot view detailed logs of MCP service components, only basic running status is displayed. Cause: `detail` parameter collection is not enabled, detailed content fields for log output are not configured, and only basic call identifiers are retained.
- Phenomenon: Specified replies are not saved to the history, and auto-replies are empty when reopening the conversation. Cause: `chatId` is not bound to a specific assistance application, or the log storage period is set too short, causing session-related data to be automatically cleaned up.
- Phenomenon: Returns none when calling MCP service concurrently, with no clear error message. Cause: Concurrent queue limits are not configured, log write threads are overloaded leading to data loss, log sources are not distinguished by access system tags, making it impossible to quickly locate abnormal nodes.

## How to Confirm Successful Configuration
- Randomly select one assistance application, retrieve conversation logs via `chatId`, and confirm that the associated application number matches the business link.
- Trigger a cross-department data call, check if the log contains the original return content of the `detail` field to verify that the collection configuration is effective.
- Simulate 2-3 concurrent calls per second, check that the log queue has no backlog, and all calls have unique and fully retained `responseChatItemId` values.
- View the log storage directory, confirm that the retention period matches the 12-month setting, and there is no configuration for automatically cleaning up expired logs.

The values listed here are common starting points and should be measured against the reader's own samples.
