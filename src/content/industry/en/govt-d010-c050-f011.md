# Party Building Learning Q&A for Fiscal Expenditure Performance Evaluation: Forms and Interactions

## What the data for this category looks like
This category involves entities including finance bureau performance departments, budget units, third-party evaluation institutions, and competent authorities. Daily generated documents include performance target forms, self-assessment forms, performance evaluation reports, supporting material lists, and rectification reports. Data sources include the integrated budget management system, project declaration materials, fund payment data, business system ledgers, and satisfaction surveys. The update frequency is annual. The most time-consuming steps are collecting project output and effect supporting materials, verifying the correspondence between fund expenditure and performance targets, and drafting issues and rectification suggestions. Consequences of errors include low project scores, budget cuts, tracked rectification, or accountability. The difference from audit categories is that this category focuses on performance targets and evidence of fiscal fund use, and does not involve fund compliance verification.

## What constraints these characteristics impose on forms and interactions
The annual update frequency means forms do not need frequent real-time data synchronization. Offline batch upload interaction can be adopted. The existence of multiple document types requires forms to support differentiated field mapping, to adapt to files of different formats such as performance target forms and self-assessment forms. The time-consuming supporting material collection process requires forms to support multi-file batch upload and tag classification functions, to reduce manual organization costs. Verifying the correspondence between funds and performance targets requires forms to have built-in field association verification rules, to avoid data mismatches. Strict error consequences require forms to set required field verification and data consistency checks, to reduce the probability of manual errors.

## Three common mistakes
- When deploying associated DingTalk bots, the interface returns the error "Message receiving address verification failed". The cause is that no publicly accessible service address is configured, or the corresponding port is not properly opened, so the platform cannot receive robot callback messages.
- Some fields are empty after form submission, and corresponding performance evaluation content cannot be generated. The cause is that the `formInput` component is not correctly bound to the background data fields, so input content is not collected.
- Parameter parsing errors occur when using third-party model interfaces, and model tools cannot be called normally. The cause is that the input format required by the model is not matched, or the permission range of tool calls is not correctly configured.

## How to confirm the configuration is complete
- Upload a standard performance target form, check whether the form automatically recognizes corresponding fields and completes initial mapping.
- Trigger the `userSelect` component, confirm that the selectable role options cover all business subject types including finance bureaus and budget units.
- Submit test data, check whether verification rules matching the configuration are triggered and clear prompts are returned.
- Call the configured model tool, confirm that internal data sources can be accessed normally and associated performance data is returned.
