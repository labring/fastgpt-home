# Party Building Learning Q&A for Flood Prevention, Disaster Mitigation and Emergency Duty: Multi-turn Dialogue and Prompt Engineering

## What this category of data entails
Data sources for this category include meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Updates occur daily.
Daily processed documents include duty logs, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips.
Most data fields include rainfall and water level values, danger level, number of people transferred, material types and quantities, and similar metrics. Units include millimeters, cubic meters, person-times, tons, and other standard units.

## What constraints do these characteristics impose on multi-turn dialogue and prompt engineering
Dispersed data sources require real-time integration. Multi-turn dialogue must fully track variables including rainfall, water conditions, and dangers within the conversation to avoid losing context.
Document fields are subdivided with specific units. Prompts must explicitly specify extraction of corresponding fields and units to prevent parameter confusion.
Data updates occur daily. Prompts must limit queries to the latest 24 hours of data to avoid calling outdated information.
In cross-departmental scheduling scenarios, multi-turn dialogue must support retrieving parameters classified by data sources from different systems. This ensures information accuracy.

## How to configure settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Approach | Rationale |
|---|---|---|
| `variables` | Dynamically bind and update across conversation turns | Flood prevention scenarios require continuous tracking of variable parameters such as rainfall periods, affected locations, and remaining material stocks. Dynamic binding ensures parameter consistency across multi-turn dialogue |
| `messages` | Retain the most recent 15–20 conversation turns | Emergency duty dialogue needs to recall recent rainfall reports and danger records. This turn range covers complete response workflows without consuming excessive resources |
| `chatId` | Bind to the unique ID of the corresponding duty task | Ensures multi-turn dialogue contexts for the same emergency task do not mix, preventing cross-task parameter crossover |
| Maximum context length | 8000–12000 token | Needs to accommodate long-form content such as consultation minutes and rapid disaster reports. This range covers context requirements for typical scenarios |
| Speech-to-text timeout | 30–60 seconds | Audio parsing for voice input must complete within a reasonable timeframe. This range covers parsing requirements across most network environments |
| Parameter extraction rules | Field matching logic calibrated through actual testing | Flood prevention scenario parameters include unit-bearing fields such as rainfall millimeters and number of people transferred. Extraction rules must be configured specifically for this use case |

## Three common configuration mistakes
- Phenomenon: Extracted keyword variables such as rainfall periods and affected areas are empty or matched incorrectly. Cause: Prompt engineering does not explicitly specify flood prevention-specific fields and units to extract, leading the model to confuse general parameters with scenario-specific parameters.
- Phenomenon: No text conversion result after voice input. Cause: Voice model invocation parameters are not configured, or the in-session speech-to-text function is not enabled, preventing audio parsing from completing.
- Phenomenon: Critical context is lost after multi-turn dialogue, making early rainfall reports unavailable for review. Cause: `chatId` is not correctly bound, or conversation retention turns are restricted, leading to session context being cleared prematurely.

## How to verify successful configuration
A test dialogue including variable parameters such as rainfall periods and affected locations is initiated, to verify that parameters are correctly bound and updated, and that extraction results match input content.
Session history records are reviewed, to confirm that retained conversation turns meet configuration requirements, with no early redundant content or loss of critical context.
The voice input function is triggered, to verify that audio is successfully converted to text, and that the configuration logic aligns with scenario requirements.
A query including flood prevention-specific fields is submitted, to verify that the parameter extraction rule correctly extracts corresponding fields and units.
