# Party Building Learning Q&A for Flood Prevention, Disaster Mitigation and Emergency Duty: Deployment and Upgrade

## What the data for this category looks like
Data sources for this category include meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Daily documents include duty logs, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Data updates occur daily; some real-time monitoring data is synced at high frequency. Document fields include rainfall and water level values, warning levels, material allocation quantities, transferred personnel information, and more, with corresponding units such as millimeters, cubic meters, pieces, and people.

## What constraints these characteristics impose on deployment and upgrades
Data for this category comes from multiple sources, with both real-time and daily update frequencies. During deployment, configure format compatibility for cross-system data access to avoid data parsing failures. Mixed storage of daily documents and real-time monitoring data increases database read and write pressure. Adjust database connection parameters during deployment to ensure load balancing. Standardization requirements for professional fields such as rainfall and water level values and warning levels require configuring data cleaning rules during deployment to ensure accurate field matching for subsequent Q&A. During upgrades, optimize scheduled data pulling tasks synchronously to meet real-time response needs in emergency scenarios.

## How to set configurations
These configurations are adapted for FastGPT v4.17.0. The specific configuration items and recommended settings are as follows:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `20–30` | Adapt to the high-frequency read and write requirements of multi-source data, avoid exhausting database connections |
| `MONGODB_URI` | `mongodb://localhost:27017/fastgpt` | Store unstructured documents such as rapid disaster reports and consultation minutes, meet the storage requirements for semi-structured data |
| `REDIS_URL` | `redis://localhost:6379/0` | Cache real-time warning information and user sessions, reduce database query pressure |
| `FE_DOMAIN` | Public IP of the deployment server or bound domain name | Ensure normal cross-domain access between front-end pages and back-end interfaces, meet remote access requirements for emergency duty |
| `ROOT_KEY` | Random string of 32 or more characters | Serve as the core key for administrator login, ensure background access security after deployment |
| `STORAGE_S3_ENDPOINT` | `http://localhost:9000` | Store files such as video surveillance screenshots and material allocation slips, meet the file data requirements within this category |

## Three common errors
- Front-end port 3000 is inaccessible, and logs show a database connection failure: The connection address for `MONGODB_URI` or `REDIS_URL` is not configured correctly, causing the service to fail initialization.
- Local Docker deployment fails to start, and container logs prompt a database connection timeout: `DB_MAX_LINK` is set too low, or the database connection pool does not adapt to concurrent requests from multi-source data.
- Q&A results cannot match the latest disaster data: No scheduled task for daily data synchronization is configured, or the data pulling update frequency does not match business requirements.

## How to confirm the configuration is complete
- Run the `docker ps` command to confirm that all relevant containers are running and have not exited abnormally.
- Access the front-end address, use the administrator key `ROOT_KEY` to log in, and verify that the background management page loads normally.
- Submit a Party Building learning-related Q&A, and verify that the returned results include document content corresponding to this category, with no missing fields or format errors.
- Check database connection logs to confirm that the configured value of `DB_MAX_LINK` matches the actual number of concurrent requests, with no connection exhaustion errors.
