# Party Building Learning Q&A for Survey and Design: Vector Models and Indexing

## What this category of data looks like
Survey and design firm party building learning Q&A data comes from three main sources: internal party building management platforms, study ledgers of temporary project party branches, and party building policy documents issued by superior state-owned assets supervision departments.
Regular party branch activities generate weekly study briefings.
Superior state-owned assets supervision departments release updated policy documents quarterly.
Party member study files are archived annually.
Each individual document includes fields such as title, publishing entity, main content, associated project number, and publishing date.
The primary file formats are PDF and DOCX.
Single-document length varies widely, ranging from short study reminders of a few hundred characters to detailed policy interpretations of tens of thousands of characters.

## What constraints these characteristics impose on vector models and indexing
Single-document length varies widely. Chunking strategies must adapt to different content densities to avoid semantic fragmentation from overly long chunks or loss of contextual association from overly short chunks.
Documents include an associated project number field. This metadata must be retained during indexing to support targeted Q&A for project-related party building scenarios.
Frequent update cycles require incremental indexing rules. These rules distinguish trigger times for full synchronization and incremental synchronization to reduce unnecessary computing resource consumption.
Dispersed data sources require unified metadata verification rules. These rules ensure consistent formatting for fields such as project number and publishing date, to avoid matching deviations during retrieval.

## How to set configurations

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Adapts to the length variation of survey and design party building documents, balancing semantic completeness and chunk granularity |
| Overlap Length | 100–150 characters | Prevents contextual breaks after chunking, ensuring semantic association between adjacent chunks |
| `maxToken` | 8192 token | Adapts to the input limit of mainstream embedding models under FastGPT v4.17.0, matching the character-to-token ratio after document chunking |
| `defaultToken` | Calibrated via actual testing | Adapts to custom embedding models with no clear token limit, avoiding truncation of key semantics |

## Three common errors
- Phenomenon: Indexing tasks remain in the "in progress" status with no progress updates. Cause: Incremental indexing rules are not configured, and full indexing scans a large number of historical documents, or chunk length is set too large leading to excessively long processing time per chunk.
- Phenomenon: A 503 status code is returned when calling the embedding model, or logs show a text-embedding model call failure under the default group. Cause: API timeout parameters for the embedding model are not configured correctly, or network policies restrict FastGPT container access to external embedding model services.
- Phenomenon: A large amount of general party building content unrelated to project party building appears in retrieval results. Cause: Associated project number metadata is not retained during indexing, or the similarity threshold is set too low, leading to recall of low-match content.

## How to confirm the configuration is correct
- View indexing task logs to confirm that the number of chunked documents matches the number of documents in the data source, with no abnormal truncation prompts.
- Manually submit a party building-related query, check whether the retrieval results include associated project number metadata and meet expected matching degrees.
- Test embedding model calls, confirm that returned vector data is not empty, and there are no timeout or error messages.
- Trigger an incremental indexing task, confirm that only newly added documents are included in the index, with no logs of full repeated synchronization.
