# Party Building Learning Q&A for Survey and Design: Multi-turn Dialogue and Prompt Engineering

## What this category’s data looks like
The data for this category comes primarily from internal party building management systems of survey and design units, study documents issued by superior party organizations, and temporary party building study records from projects.
Update cadence is monthly for superior policy documents, and quarterly for branch study ledgers and assessment records.
Most documents are hierarchical structured text, with fields including document title, issuing authority, release date, main content, and applicable project type.
Metrics include study duration (hours) and assessment scores (points). Some documents include attachments for party building activities linked to specific projects.

## What constraints do these characteristics impose on the multi-turn dialogue and prompt engineering link?
Structured documents are bound to project and branch fields. Multi-turn dialogue must use `chatId` to bind context for the corresponding project and branch, to avoid confusion across cross-project party building Q&A.
The relatively high update frequency requires prompts to explicitly prioritize the latest released document content, to avoid referencing outdated policies.
Documents include a project type field. Prompts must adapt to party building requirements for different survey and design scenarios such as municipal engineering and architecture, and cannot use generic phrasing.
Some documents have long length. The context window for multi-turn dialogue must be limited to a reasonable length, to prevent content overflow that causes answer deviations.

## How to set up the configuration
This page’s configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `chatId` | Generate a unique identifier based on the project + branch combination | Bind context for the corresponding project and branch, avoid confusion across cross-scenario Q&A |
| `messages` | Retain the most recent 20 rounds of conversation content | Adapt to the length of survey and design party building documents, prevent context overflow |
| `variables` | Pass two variables: project type, branch name | Adapt to party building Q&A requirements for different survey and design scenarios |
| User key binding | Generate a dedicated key based on user ID | Prevent sharing of conversation records and keys across different users |
| Maximum context | 8000–12000 token | Accommodate medium and long party building documents and multi-turn conversation content |
| Question optimization | Enabled | Correct ambiguous party building questions in multi-turn dialogue, improve answer accuracy |
| Single search limit | Top 3 matching documents | Match the moderate data volume of survey and design party building data, avoid interference from redundant content |

## Three common misconfigurations
- Calling the OpenAPI to initiate a conversation returns a 422 error. Cause: `chatId` or `messages` parameters are not passed correctly, or the parameter format does not meet specifications.
- Multi-turn dialogue context contains cross-project party building content. Cause: A unique identifier is not generated for each project and branch combination, leading to shared context across different scenarios.
- Conversation results reference outdated party building policy documents. Cause: The prompt does not explicitly prioritize the latest released content, or the knowledge base has not synced updated party building documents.

## How to confirm the configuration is complete
- Initiate a single-round test conversation, input a party building question bound to a specific project and branch, check if the returned result matches the corresponding content, confirm that the `variables` and `chatId` configurations are active.
- Initiate consecutive multi-turn conversations, ask related party building questions in sequence, check if the answer references the context from the previous round, confirm that the `messages` configuration is active.
- Trigger a knowledge base update operation, then initiate a conversation, check if the result includes the latest released party building document content, confirm that the data update mechanism is active.
- Call the OpenAPI interface to test a conversation, check if the returned status code is 200, confirm that the parameter configurations meet specifications.
