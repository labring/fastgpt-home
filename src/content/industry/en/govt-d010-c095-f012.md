# Party Building Learning Q&A for New Energy Development: Deployment and Upgrade

Reference only; verify against the target FastGPT release and deployment documentation.

## What this category of data looks like
Party building learning Q&A data for the new energy development sector primarily originates from internal party building knowledge bases of state-owned and state-controlled enterprises, industry party building policy documents issued by superior party committees, and archived party building activity materials from new energy project sites. Data is updated once per month. Most documents use structured formats, including fields such as title, body paragraphs, and attachment descriptions, alongside metadata including file number, issuing unit, and release date. The word count of individual documents varies widely, measured in characters and MB.

## What constraints do these characteristics impose on the deployment and upgrade phase
Most party building data for new energy development is stored in internal controlled storage systems of state-owned and state-controlled enterprises. During deployment, configure connection parameters adapted to internal storage to ensure data access complies with security and compliance requirements. Monthly updated documents include fixed metadata fields. When upgrading versions, verify that the new framework supports parsing structured metadata to avoid field loss or parsing errors. Archived party building materials from project sites are mostly text transcribed from scanned documents. Reserve sufficient text parsing computing power during deployment. After upgrading, re-test document parsing accuracy to maintain Q&A matching accuracy. The confidential nature of party building content requires strict restrictions on external access permissions during deployment. During the upgrade process, synchronously validate the effectiveness of access control configurations.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `1000 entries` | Adapts to the upper limit of document association count for new energy party building knowledge bases, preventing timeouts caused by loading too much associated data in a single Q&A round |
| `STORAGE_S3_ENDPOINT` | Access address of the internal controlled storage service | Matches the deployment environment of state-owned and state-controlled enterprise internal storage to ensure compliant access to party building data |
| `REDIS_URL` | Connection address of the internal network Redis service | Used to cache high-frequency requests for party building Q&A to reduce database load |
| `ROOT_KEY` | Internal access key | Restricts access to the party building Q&A system by unauthorized users, complying with data security requirements of state-owned and state-controlled enterprises |
| `FILE_TOKEN_KEY` | Encryption key consistent with internal storage | Ensures the security of document access tokens, preventing unauthorized downloading of party building learning materials |
| `FE_DOMAIN` | Enterprise internal network domain name | Limits valid domains for front-end access, adapting to internal office network environments |

## Three common mistakes
- After upgrading the version, clicking on the knowledge base's file details displays "Invalid dataset file key". The cause is that the `FILE_TOKEN_KEY` configuration value was not updated synchronously during the upgrade process, causing a mismatch in the document access token verification logic.
- Failing to configure a reasonable upper limit for `DB_MAX_LINK` during deployment, leading to loading too many associated documents in a single party building Q&A round, resulting in response timeouts or truncated results.
- Not pointing `REDIS_URL` to the cache service deployed on the internal network, causing cache hit failures for Q&A requests and increasing database query pressure.

## How to confirm the configuration is correct
- Run a connectivity test for the internal storage to verify that the access address configured in `STORAGE_S3_ENDPOINT` can normally read party building documents.
- Initiate a single party building Q&A request to check whether the cache service corresponding to `REDIS_URL` can normally store and read request caches.
- Check system logs to confirm that the access verification logic of `ROOT_KEY` does not block access requests from authorized internal users.
- After upgrading the version, re-upload a test party building document to verify that the file details page can load normally without the "Invalid dataset file key" error.
