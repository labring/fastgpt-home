# Coal-Electric Integration Party Building Learning Q&A: Conversation Logs and Auditing

## What this category of data looks like
Data comes from the internal party building knowledge base of coal-electric integration enterprises. It includes central committee study materials, party lesson courseware, internal party policy documents, branch activity records, and similar content. The update schedule is to sync newly released party building materials monthly, and update revised versions of existing documents quarterly. Each single document has four core fields: title, main text, issuing unit, and release date. The formats of these fields are plain text, character count, plain text, and date format respectively. The typical size of a single document ranges from hundreds of KB to several MB.

## What constraints these characteristics impose on the conversation logs and auditing link
Documents in the internal party building knowledge base have hierarchical permission divisions. The auditing link must match the document access permissions corresponding to the conversation to avoid unauthorized access to content. Documents are updated on a monthly basis. Conversation logs must associate the document version in use at the time of the Q&A to ensure the timeliness of audit basis. The multi-field document structure requires logs to simultaneously record metadata such as the document title and issuing unit triggered by the Q&A, to facilitate subsequent traceability. At the same time, the conversation context of party building Q&A must be fully retained, to ensure that the complete question and reply link can be traced during auditing.

## How to set up the configuration
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind exclusive branch session ID | Ensure conversation logs for the same branch are stored in groups, facilitating auditing by organizational unit |
| `responseChatItemId` | Associate unique identifier for a single Q&A | Enable precise binding of questions and replies, meeting audit requirements for one-by-one verification |
| `detail` | Enable full logs | Record conversation metadata, associated document information, and permission check results, covering all dimensions of auditing |
| Context recall limit | Top 4 entries | Balance log storage volume and traceability completeness, adapting to the short context characteristics of party building Q&A |
| Timeout threshold | 60 seconds | Adapt to the typical time required for internal party building document loading and Q&A generation |
| Log retention period | 365 days | Comply with archive retention specifications in public service sectors |

## Three common errors
- The symptom is that the association between user questions and AI replies cannot be matched in the audit log. The cause is failure to correctly bind `responseChatItemId` to the conversation node, resulting in logs only recording individual questions or replies.
- The symptom is that expired party building document content is recalled in conversation logs. The cause is failure to associate the document version identifier at the time of the Q&A, leading to the use of updated document versions for audit traceability by mistake.
- The symptom is that incomplete log data is returned when calling the conversation record list interface. The cause is failure to set the `detail` parameter to enabled, so only basic session information is returned without detailed Q&A content.

## How to confirm the configuration is complete
- Initiate a party building-related question, check whether the conversation log contains complete values of the `chatId` and `responseChatItemId` parameters, and confirm that the association between questions and replies is correct.
- Call the conversation record list interface, verify that each returned record includes unique session and reply identifiers, and use the offset parameter to paginate queries for complete log content.
- Check whether the log retention period meets the preset 365-day requirement, and confirm that the automatic archiving logic for expired logs is effective.
- View the details of a single log, confirm that it includes metadata such as the associated document title and issuing unit, and verify that the `detail` parameter configuration is effective.
