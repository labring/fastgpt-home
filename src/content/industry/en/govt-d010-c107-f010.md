# Party Building Learning Q&A for Coal Mine Production: Knowledge Base Retrieval and Recall

## What the data for this category looks like
Party building learning data for coal mine production scenarios is sourced from:
- Party building learning materials archived by party committee offices of state-owned coal enterprises
- Policy documents issued by superior party committees
- Party building learning records from pre-shift meetings in underground work areas
- Monthly summary documents of party branches

Update frequency follows set rules:
- Superior documents are updated quarterly
- Internal learning materials are updated weekly
- Pre-shift meeting records are generated daily

All documents include standard fields: title, issuing unit, release date, applicable scenario, and main content. Release dates use the YYYY-MM-DD format. Main content is measured in characters. The applicable scenario field is a text enumeration, marked for scenarios such as underground work or party branch offices.

## What constraints these characteristics impose on knowledge base retrieval and recall
Multi-source, heterogeneous data sources require the retrieval link to support batch import of documents in different formats, to avoid missing internal record-type data.
Daily pre-shift meeting records require incremental synchronization frequency matched to the daily generation rhythm, to prevent data lag.
The applicable scenario field requires matching during retrieval, to avoid recalling party building content unrelated to the target scenario.
A large volume of party building professional terms and coal mine production-specific expressions exists in documents. Retrieval must retain term matching accuracy to avoid generalized recall of irrelevant content.

## How to set configuration values
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Similarity threshold | 0.75-0.85 | Matches the density of professional terms in coal mine party building documents, filters low-correlation results |
| Single recall limit | Top 10 entries | Controls context length, avoids model inference delay, and adapts to the short, focused Q&A needs of the scenario |
| Search mode | Hybrid retrieval | Balances keyword matching and semantic matching, covering different retrieval needs for party building policies and on-site records |
| Rerank switch | Enabled | Performs secondary sorting on recall results, improving accuracy of professional term matching |
| Question optimization | Enabled | Expands party building-related expressions of user questions, adapting to the specific question habits of coal mine party building scenarios |
| Dataset ID | Corresponding dedicated coal mine party building dataset | Isolates knowledge bases of different categories, avoiding recall of irrelevant content |

## Three common configuration mistakes
- Phenomenon: Knowledge base retrieval calls trigger response timeouts, with the interface displaying a request timeout prompt. Cause: The single recall limit parameter is not adjusted. Too many documents are recalled, creating an overly long context and causing model inference delay.
- Phenomenon: Retrieval results omit document titles, only returning main body fragments. Cause: Retrieval mapping for the title field is not configured, so only main body content is retrieved.
- Phenomenon: API calls automatically carry a Bearer token, causing failure to connect to external knowledge bases. Cause: The setting to automatically add Bearer tokens remains enabled, which does not meet external data source authentication requirements.

## How to verify a complete configuration
- Upload a test party building document that includes title and release date fields, enter a relevant question, and check whether the number of returned results matches the configured single recall limit.
- Check whether returned results include the document title field, confirming that the search mode and retrieval mapping configurations are correct.
- Test a query using a local large model, check whether response time meets expectations, and confirm that the similarity threshold and rerank switch configurations are reasonable.
- Review API call logs, confirm no extra Bearer tokens are automatically carried, meeting external data source authentication requirements.
