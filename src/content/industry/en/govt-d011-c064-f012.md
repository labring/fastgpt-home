# Administrative Document Format Checking and Assistance: Deployment and Upgrade

## Data for This Use Case
The data sources for administrative document format checking primarily come from draft documents awaiting review from state-owned enterprises, government agencies, and public service institutions, as well as official standard documents for the format of Party and government administrative documents. Data updates primarily use single upload or batch import workflows. The document structure of single tasks strictly follows fixed specifications, including three modules: header, main body, and footer. Fields include document serial number, date of issuance, receiving organization, attachment note, and more. Some fields have mandatory format requirements: for example, the document serial number must follow the structure of agency abbreviation + year + sequence number, and main body text must use size 3 FangSong_GB2312 font.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale for This Setting |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://localhost:27017/fastgpt?maxPoolSize=20` | Administrative document format checking requires storing large volumes of format rules and verification logs. For local deployments, use a local MongoDB instance, with the connection pool setting adapted for batch processing scenarios |
| `REDIS_URL` | `redis://localhost:6379/0?maxMemoryPolicy=allkeys-lru` | Cache commonly used format verification rules and user sessions to reduce duplicate computation overhead and adapt to high-frequency verification requests |
| `STORAGE_S3_ENDPOINT` | `http://localhost:9000` | Store batch-uploaded administrative document drafts and verification results. For local private deployments, use a local object storage service |
| `ROOT_KEY` | `Set based on actual testing` | Configure the administrator permission key for managing format rule library updates and version synchronization, to prevent unauthorized modifications |
| `FILE_TOKEN_KEY` | `Randomly generated 32-character string` | Used to encrypt temporary tokens for document uploads, preventing unauthorized access to documents awaiting verification |
| `FE_DOMAIN` | `http://localhost:3000` | Specify the frontend access domain, adapting to local deployment access paths and ensuring normal loading of verification result pages |

## Three Common Configuration Mistakes
- Customized format verification rules are lost after upgrading the version. This occurs because the format rule library data corresponding to `MONGODB_URI` was not backed up before upgrading, and the upgrade script did not retain customized configurations.
- The format verification rule library fails to load after Docker deployment. This occurs because `STORAGE_S3_ENDPOINT` was not correctly configured to point to the local storage path, causing rule files to fail to load properly.
- Verification tasks cannot be triggered after configuring third-party keys. This occurs because the key was not associated with the administrator permission context corresponding to `ROOT_KEY`, leading to insufficient tool call permissions.

## How to Verify Successful Configuration
- Access the backend configuration page and verify that configured database, storage, cache and other parameters match the preset values.
- Upload a sample administrative document that complies with official format standards, trigger the verification process, and confirm that results are output normally.
- Execute the version upgrade script, then verify that existing customized format rules were not overwritten.
- Check the storage service connection status to confirm that administrative document drafts and verification results can be accessed and stored normally.

The values provided here are common starting points and should be evaluated against the deployment's own samples.
