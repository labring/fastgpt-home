# Internal Office and Employee Services for "One Thing Done Efficiently" Joint Handling: Deployment and Upgrade

## What this category of data looks like
The data for this category mainly comes from the "One Thing" special zone of the national government service platform, local integrated government service platforms, electronic certificate repositories, and approval systems of various departments. The update frequency is daily. Daily processed documents include joint handling item lists, one-time notice sheets, joint handling application forms, material circulation sheets, parallel approval opinions, and completion receipts. Common data fields include associated departments for items, material reuse requirements, handling circulation nodes, and completion status identifiers. No additional custom statistical units are used.

## What constraints do these characteristics impose on the deployment and upgrade process
Daily updated cross-department government data requires configuring stable database and cache connections during deployment to avoid data synchronization failures caused by connection interruptions. The need to parse multiple types of government documents requires retaining format-compatible preprocessing modules during upgrades to adapt to files with different structures such as lists, forms, and receipts. The strongly associated nature of cross-department data circulation requires configuring unified permission verification rules during deployment to prevent unauthorized access to sensitive government materials. Additionally, the handling status of joint handling items relies on real-time data. The upgrade process must reserve a rollback window to avoid process blockages after updates that would affect work progress.

## How to set the configurations
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Exclusive MongoDB cluster connection string for government intranets | Stores unstructured government data such as joint handling item lists and approval opinions. Intranet clusters can ensure data transmission and storage security |
| `PG_URL` | Connection address of the high-availability read-only replica group of government cloud PostgreSQL | Stores joint handling process node data that is queried frequently. Read-only replicas can alleviate query pressure and adapt to the high-frequency access requirements of daily updates |
| `REDIS_URL` | Intranet address of government cloud cache instances | Caches temporary verification data for electronic certificates, reducing database query frequency and adapting to real-time verification scenarios with daily updates |
| `STORAGE_S3_ENDPOINT` | Intranet endpoint of government cloud object storage | Stores files such as joint handling application forms and material circulation sheets. Intranet access can improve transmission speed and avoid public network exposure risks |
| `DB_MAX_LINK` | `20–30` | Adapts to the database connection requirements of parallel queries across multiple departments, avoiding joint handling process blockages caused by exhausted connections |
| `FE_DOMAIN` | Government service intranet domain name | Configures the frontend access address, limiting access to the joint handling office system only to the government intranet, which complies with government data security management requirements |

## Three common mistakes
- Symptom: When migrating to a new server and not using Docker for deployment, the joint handling office service fails to start. Cause: Environment parameters such as `MONGODB_URI` and `PG_URL` are not configured correctly, and a full migration of database and cache data is not completed manually.
- Symptom: An error `worker terminated due to reaching memory limit` occurs when creating a joint handling item knowledge base. Cause: The joint handling item list contains a large number of cross-department associated fields. The single data loading volume exceeds the service process memory threshold, and the `DB_MAX_LINK` is not adjusted to limit the number of concurrent connections.
- Symptom: After upgrading to a new version, uploading a joint handling application form in the workflow throws an error `Failed to create post presigned url`. Cause: `STORAGE_S3_ENDPOINT` is not updated to adapt to the new government cloud storage configuration, or the file storage key permissions are not synchronized for update.

## How to confirm that the configuration is correct
- Run the built-in database connection test tool to verify that `MONGODB_URI` and `PG_URL` can access the corresponding clusters normally, with no connection timeout or permission error logs.
- Upload a standard joint handling application form to the system, confirm that the file can be stored normally and a preview link is generated, and verify that the `STORAGE_S3_ENDPOINT` configuration takes effect.
- After starting the service, check the system logs to confirm that the number of connections configured by `DB_MAX_LINK` is not exhausted, and there are no frequent connection reconstruction or timeout logs.
- Access the government intranet address corresponding to `FE_DOMAIN`, confirm that the frontend page can load the joint handling item list normally, with no resource loading failure prompts.

The values given are common starting points and should be measured against the reader's own samples.
