# Internal Office and Employee Services for Infectious Disease Information Reporting and Monitoring: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
The data for this category primarily comes from the Chinese Center for Disease Control and Prevention Information System, medical institution HIS systems, infectious disease reporting systems, and laboratory testing systems. Daily processed documents include infectious disease report cards, epidemic analysis reports, case correction records, clustered epidemic reports, and epidemiological investigation reports. Data is updated daily. Document fields include basic patient information, diagnosis results, report submission time, correction notes, and more. Strict compliance with legal infectious disease reporting rules is required, and data formats must meet standardized requirements.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompt Engineering
Data is updated daily, so multi-turn dialogue must maintain continuous context via `chatId` to ensure the latest case correction and report card data can be called during the conversation. Document fields are fixed and must match legal reporting rules, so prompts must clearly specify field extraction verification logic, such as checking the match between patient diagnosis and reporting time limits. Data from multiple systems must be cross-checked during dialogue to avoid duplicate or incorrect report cards. An abnormal signal summary link must also be added to the dialogue flow to ensure abnormal data can be identified in a timely manner.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Automatically generated per conversation session | Maintains context continuity for multi-turn dialogue, ensuring different dialogue rounds can be linked to the same case data |
| `messages` | Retain the first 20 rounds of dialogue content | Covers the necessary context for multi-round interactions of case verification and correction in daily office work |
| `variables` | Preset legal reporting rule verification variables and JSON format constraints | Embeds legal verification logic into prompts and standardizes response formats |
| Maximum context length | 8000–12000 characters | Matches the total character count of single report cards and epidemiological investigation reports processed daily |
| Single interaction timeout | 30 seconds | Adapts to the response duration of cross-system data retrieval |
| Question optimization | Calibrated based on actual testing | Optimizes terminology for infectious disease reporting scenarios to improve dialogue understanding accuracy |

## Three Common Misconfigurations
- Symptom: Dialogue context is lost, and historical data for the same case cannot be linked. Cause: `chatId` is not configured correctly, so different dialogue rounds cannot be bound to the same session, and session memory is not retained.
- Symptom: Dialogue workflow runs slower than standalone workflow debugging. Cause: The number of retained `messages` rounds is not optimized, and excessive historical context is loaded for each dialogue, increasing processing time.
- Symptom: Generated summary results include missed or delayed reporting anomalies. Cause: The prompt does not include reporting time limit verification logic, does not check the match between patient diagnosis and reporting time limits, and does not complete cross-source data consistency checks.

## How to Confirm Proper Configuration
- Check that the `chatId` configuration for FastGPT v4.17.0 is enabled, ensuring that session IDs are automatically generated with each dialogue.
- Initiate two or more rounds of case data verification dialogue, input interactions related to case correction, and confirm that historical dialogue data is correctly called and context is not lost.
- Configure the JSON format constraint in `variables`, generate a response, and check that the format matches the preset fields and verification rules.
- Test the single interaction response duration, and confirm that it does not exceed the preset 30 second threshold.

The values provided are common starting points and should be measured against the reader's own samples.
