# Internal Office and Employee Services for Infectious Disease Information Reporting and Monitoring: Tool Calling and Plugins

## What this category of data looks like
Data for this category primarily originates from China’s National Disease Prevention and Control Information System, hospital HIS and infectious disease reporting systems, and laboratory testing systems. It is updated daily. Daily documents include infectious disease reporting cards, epidemic analysis reports, case correction records, clustered epidemic reports, and outbreak investigation reports. Core fields cover case diagnosis information, report submission time limits, correction status, clustered epidemic association identifiers, and more. The data structure must strictly match the field specifications for legal infectious disease reporting, with no additional custom expansion space.

## What constraints these characteristics impose on tool calling and plugins
Since data comes from multiple independent systems, tool calling must support batch docking of multiple data source interfaces to avoid data silos. The daily update frequency requires tool triggering logic to align with the fixed daily update cycle to ensure data timeliness. Strict legal reporting field specifications require tool calling parameter verification to strictly match specified fields, with no non-compliant custom fields allowed. The need for verification in core time-consuming links requires integrating data comparison and duplicate record identification plugins into tool calling, to automatically complete checks on case diagnosis and reporting time limits. At the same time, strict accountability requirements for legal reporting require supporting abnormal alarm plugins to timely synchronize risks of underreporting or delayed reporting.

## Configuration guidelines
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `toolChoice` | `"auto"` | Adapts to automatic multi-tool selection logic, matches the multi-step task requirements of infectious disease reporting scenarios |
| `functionCall` | `"strict"` | Enforces matching of fixed fields for legal infectious disease reporting, prevents non-compliant parameters from being passed |
| Plugin Trigger Timing | Daily 02:00-04:00 | Aligns with the system low-peak period of daily data updates, reduces resource occupancy and conflict probability |
| Data Source Verification Switch | Enabled | Ensures field compliance of data from connected disease control information systems and hospital HIS systems |
| Abnormal Alarm Threshold | Calibrated based on actual testing | Adapts to differences in case volumes across institutions, accurately identifies abnormal signals such as underreporting and delayed reporting |
| Scheduled Task Execution Count | 1 time per day | Matches the daily data update frequency, avoids resource waste from repeated calls |

## Three common misconfigurations
- Calling the Claude 4 model returns an error starting with software.amazon.awssdk.services.bedrockruntime.model. This occurs because Bedrock plugin permissions and region parameters are not configured correctly, interrupting the model calling chain.
- Interface calls return the `aiPointsNotEnough` status code. This occurs because the allocated plugin service call quota is insufficient, and corresponding quota has not been replenished in a timely manner.
- Multimodal system plugins fail to properly parse image attachments in outbreak investigation reports. This occurs because the plugin's image format adaptation switch is not enabled, or parsing dependencies for corresponding formats are not configured.

## How to confirm successful configuration
- Perform a single tool calling test, verify that the returned results match the field requirements of legal infectious disease reporting, and confirm that the strict mode of `functionCall` is active.
- Check the scheduled task logs, confirm that the plugin automatically triggers during the preset low-peak period, matching the daily data update rhythm.
- Simulate input of abnormal data, confirm that the abnormal alarm plugin triggers alerts normally, and verify the configuration logic of the abnormal threshold.
- Check the system plugin list, confirm that the `MCP` function is enabled and the connection key is configured correctly, and verify that the tool calling trigger chain is complete.
