# Internal Office and Employee Services for Petition Matter Handling: Multi-turn Dialogue and Prompt Engineering

## What this category's data looks like
Data sources for this category include the national petition information system, local petition systems, the 12345 citizen hotline platform, grassroots governance platforms, and historical petition archives. The update frequency is daily. Daily documents include petition registration forms, acceptance notices, transfer and assignment letters, handling opinions, review and re-examination applications, and resolution plans. Single data entries include structured fields such as appeal content, handling progress, responsible unit, and policy basis, alongside unstructured formal document content. The overall data structure supports both form filling and official document formatting.

## What constraints these characteristics impose on the "multi-turn dialogue and prompt engineering" link
Data comes from multiple systems and updates daily, so sessions must bind a unified context via `chatId` to avoid cross-system data confusion. Documents mix structured forms and official papers, so prompt engineering needs to distinguish between field validation and policy interpretation logic. The most time-consuming steps of verifying acceptance scope and coordinating responsible units require multi-turn dialogue to guide users to supplement necessary information, while avoiding overly long session contexts interfering with core judgments. It must also adapt to the business habits of petition offices at different levels, ensuring prompt engineering complies with legal handling procedures.

## How to set up the configuration

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Session context retention duration | 24 hours | Matches the daily data update frequency to ensure session continuity for same-day petition matters |
| `messages` context truncation threshold | First 8 rounds of dialogue | Prevents overly long contexts from interfering with policy basis matching and handling logic judgment |
| `variables` field binding scope | Associated required fields of the petition registration form | Matches the structured form structure of category documents to ensure complete information |
| Maximum tokens per single session | 8000–12000 token | Adapts to content carrying for long documents such as handling opinions and resolution plans |
| `variables` validation switch | Enable required field validation | Reduces handling process delays caused by missing information |
| Question optimization switch | Calibrate based on actual testing | Adapts to communication styles and business habits of petition offices at different levels |

## Three common mistakes
- After enabling `variables` field validation, a 422 status code is returned when submitting a simulated appeal. The cause is that required fields of the petition registration form are not bound, resulting in missing session parameters.
- Attempting to modify the new conversation popup style but seeing no effect. The cause is that the wrong code file was modified instead of the front-end rendering module for private deployment.
- Using title hierarchy separators for knowledge base chunking leads to overly inaccurate retrieval results. The cause is that petition documents mix structured forms and official papers, with inconsistent title hierarchies causing chunk breaks and loss of key policy basis content.

## How to confirm the configuration is complete
- Initiate a simulated petition appeal, check if the session binds historical dialogue context via `chatId`.
- Enter required fields of the petition registration form and submit, verify if `variables` validation triggers correct completion prompts.
- Import a handling opinion document, check if chunked content retains complete policy basis paragraphs.
- View session logs, confirm that the `messages` context does not exceed the set first 8 rounds truncation threshold.
