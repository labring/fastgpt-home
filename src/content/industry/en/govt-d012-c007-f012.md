# Internal Office and Employee Services for Petition Matter Handling: Deployment and Upgrade

## What this category’s data looks like
Data for this category comes from the national petition information system, local petition systems, the 12345 platform, grassroots governance platforms, and historical petition archives. Updates are performed daily via incremental or full sync. Unlike the 12345 hotline, this category focuses more on legal handling procedures and review and reconsideration stages.

Daily processed documents include petition registration forms, acceptance notices, transfer and assignment letters, handling opinions, review and reconsideration applications, and resolution plans. Each document contains fields such as requester, request matter, handling progress, responsible unit, and policy basis. Some historical archives have unstructured text fragments that must be parsed before being added to the system.

## What constraints do these characteristics impose on the deployment and upgrade phase
Multi-source data access requires adapting interface permission configurations for different systems during deployment to ensure compliant data pulling.
Daily update frequency requires configuring incremental sync scheduled tasks to avoid excessive resource usage from full data pulls.
Diverse document types require preset corresponding field extraction rules to adapt to document formats for different handling stages.
Unstructured features of historical archives require adding compatible text parsing modules during upgrades.
Cross-platform data linkage needs clear parameter verification logic to prevent format errors during data synchronization.
This category focuses on legal handling procedures, so a corresponding permission audit module must be configured during deployment to ensure handling processes are traceable.

## How to set the configurations
| Configuration Item | Suggested Setup | Rationale |
|---|---|---|
| `MONGODB_URI` | Fill in the MongoDB connection address for storing petition data, including username and authentication information | Data for this category requires persistent storage. MongoDB is the default unstructured document storage medium for FastGPT, and it adapts to the multi-field storage needs of petition archives |
| `REDIS_URL` | Configure the connection address for the local Redis service, set connection timeout to `300 seconds` | Daily incremental sync scheduled tasks rely on Redis for task scheduling and status caching. A 300-second timeout balances task execution efficiency and resource usage |
| `DB_MAX_LINK` | Set to `10–20` | The daily incremental update volume of petition data is large. A connection count of 10-20 avoids exhausting database connection pools while ensuring the execution efficiency of sync tasks |
| `STORAGE_S3_ENDPOINT` | Fill in the endpoint address of the local object storage | Documents related to petitions such as acceptance notices and handling opinions require persistent storage. S3-compatible storage adapts to batch document upload and download needs |
| `ROOT_KEY` | Generate a random 32-bit string as the internal access key | Restrict access to the petition matter handling module to internal employee accounts only, ensuring access security for sensitive handling data |
| `FILE_TOKEN_KEY` | Generate a random 16-bit string as the file access token key | Download links for petition documents must bind access permissions to prevent unauthorized personnel from obtaining sensitive handling materials |

## Three common misconfigurations
- After container deployment, running `npm list` cannot return the Mongoose version. A dependency entry exists in package.json, but the runtime reports a missing module. This occurs if the local dependency directory is not correctly mounted during docker-compose deployment, or if the image build script skips the dependency installation step.
- When attempting to add a new internal employee account, a permission verification failure prompt appears, and account creation cannot be completed. This occurs if the `ROOT_KEY` parameter is configured incorrectly, or if the account’s administrator permission scope is not synced in the internal office system.
- Petition data search results are empty, and logs show index creation failed. This occurs if the connection user configured in `MONGODB_URI` only has read permissions and cannot perform index creation operations, or if the incremental sync task fails to correctly map data fields.

## How to confirm the configuration is complete
- Log in to the FastGPT v4.17.0 backend, enter the system settings page, and check the connection status of `MONGODB_URI`. Confirm it displays a normal connection.
- Trigger a manual incremental sync task. Wait for the task to finish, then check the petition data list. Confirm the number of documents matches the source system’s statistics, and all field information is complete.
- Attempt to upload a standard petition registration form document. Confirm the file can be stored normally, and the generated download link can be accessed normally within the internal office network.
- Check the Redis service runtime logs. Confirm the scheduled sync task status is running, with no timeout or connection failure error messages.
