# Internal Office and Employee Services for Pension, Work Injury, and Unemployment Benefit Verification: HTTP Interfaces and External Systems

## What this category of data looks like
Data for this category originates from social insurance management systems, personal social insurance benefit records, labor relations and work injury identification systems, and electronic social security card platforms. The update frequency is daily. Documents processed daily include benefit application forms, payment period certificates, retirement approval forms, work injury identification materials, and unemployment insurance benefit application materials. Core fields include insured person identity identifiers, payment periods, work injury identification results, unemployment insurance participation duration, pending verification benefit amounts, and more. Field formats must match the native definitions of each source system, with no unified cross-system field aliases.

## What constraints do these characteristics impose on HTTP interfaces and external systems
The data sources for this category are scattered, and formats are inconsistent. This requires HTTP interfaces to support multi-source data format adaptation and field mapping. The daily update frequency means interface call frequency must align with business data update rhythms. This avoids excessive calls or delayed access to the latest data. The strictness of core fields requires interfaces to include strict parameter verification and data cleaning logic. Without these measures, issues such as incorrect or missing benefit payments may occur. The need to distinguish between multiple business document types requires interface request parameters to carry clear benefit type identifiers. This prevents data confusion across different business scenarios.

## How to configure
This configuration scheme is compatible with FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `Authorization` | `Bearer {Social Insurance-specific Interface Secret Key}` | Adapts to the standard authentication format for public human resources and social security department external interfaces, ensuring call legitimacy |
| `variables` | Bind core business fields such as insured person ID, benefit type, payment period | Accurately match the parameter conditions required for benefit verification, reducing invalid requests |
| `responseData` | Verify that required fields such as benefit amount and insured status are non-empty and comply with format specifications | Filter invalid data to avoid errors in subsequent benefit calculation processes |
| Batch call batch size | 100-200 items per call | Adapts to the concurrent processing limit of social insurance systems, calibrated based on actual testing |
| Interface call frequency | 1 call per day | Matches the daily update frequency of business data, avoiding redundant requests |
| Error retry mechanism | Retry 3 times, with a 60-second interval | Address temporary network fluctuations or system lag, reducing call failure rates |

## Three common configuration errors
- The benefit amount field in the interface-returned `responseData` is empty. This occurs because the integrity of required fields returned by the external system is not verified, leading to missing critical data in subsequent benefit calculation links.
- A 503 Service Unavailable status code is returned during batch calls. This occurs because the call batch size exceeds the concurrent limit of the social insurance system, and requests are not initiated using the configured batch parameters.
- Verification results for different benefit types are mixed. This occurs because the accurate benefit type parameter is not bound in `variables`, leading to incorrect matching of interface returned data.

## How to verify a successful configuration
- Call the test interface, verify that `Authorization` authentication passes, and return expected business data.
- Trigger the batch call process, confirm that the request batch and call frequency comply with configuration requirements, with no frequent errors.
- Simulate abnormal data input to the interface, confirm that the `responseData` verification rules take effect, and return clear error prompts.
- Check the business parameters bound in `variables`, confirm that they fully match the fields required for benefit verification.
