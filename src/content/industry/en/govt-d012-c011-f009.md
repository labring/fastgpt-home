# Internal Office and Employee Services for Pension, Work Injury, and Unemployment Benefit Verification: Model Access and Configuration

## What data looks like for this category
Data for this category comes from social insurance handling systems, personal benefit records, labor relations and work injury identification systems, and the electronic social security card platform. Data updates occur daily.
Daily handled business documents include benefit application forms, payment period certificates, retirement approval forms, work injury identification materials, and unemployment insurance benefit application materials.
Data fields cover insured status, payment period, work injury identification grade, benefit calculation base, and more. Units include year, month, and yuan.
Core field priorities vary across different documents. For example, payment period certificates must strictly match payment record fields in social security systems.

## Constraints for model access and configuration
Data sources covering multiple government systems require access configuration to support cross-system data association verification. This prevents calculation errors caused by information deviation from a single data source.
The daily update frequency requires configuration recall logic to prioritize same-day updated personal benefit records and identification materials. This ensures the timeliness of calculation data.
Structural differences across multiple business document types require configuration to adapt to exclusive field extraction rules for different documents. For example, extract disability grades from work injury identification materials, and extract deemed payment periods from retirement approval forms.
Requirements for professional fields and units require configuration to lock field mapping rules consistent with social insurance handling systems. This prevents unit confusion or field misalignment. It also ensures model output calculation logic complies with general government service handling specifications.

## How to set the configuration
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | This category requires association of multiple social security documents and cross-system records; sufficient context ensures the model can fully match fields and calculation logic |
| `maxTokens` | `2000–3000 token` | Benefit verification responses need to include clear calculation steps and results; overly long output increases reading costs for handling staff, and also avoids exceeding system interface limits |
| `temperature` | `0.1–0.3` | This scenario requires strict alignment with social insurance handling rules; a lower temperature reduces random outputs, ensuring consistency and accuracy of calculation results |
| `AIPROXY_API_ENDPOINT` | Exclusive proxy node address for government intranets | Social security data is government-sensitive information; transmission must go through compliant proxy nodes to ensure data transmission security |
| `AIPROXY_API_TOKEN` | Exclusive access token bound to the government intranet | Access permissions for model interfaces must be strictly controlled to prevent unauthorized access to sensitive social security data |
| `quoteMaxToken` | `4000 token` | Recalled social security document content must fully cover key information required for calculation such as payment periods and identification results, to avoid truncation of core fields |

## Three common configuration errors
- Phenomenon: The benefit calculation result returned by the model does not match the records in the social security system, with numerical or unit errors in fields such as payment period and benefit standard. Cause: Field mapping rules aligned with social insurance handling systems were not configured, causing information extracted by the model to not match actual business data.
- Phenomenon: A 403 permission error or connection timeout occurs when calling the model interface. Cause: `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` were not configured correctly; non-compliant proxy nodes or invalid tokens were used, preventing normal access to the model service.
- Phenomenon: Multiple calls to the model for the same calculation request return different results. Cause: The `temperature` parameter was set too high, causing random model outputs that do not meet the requirement of strict alignment with handling rules for this scenario.

## How to confirm the configuration is correct
- Import a real benefit application form and its corresponding payment period certificate, trigger model calculation, and check whether returned core fields match social security system records.
- Call the model interface, check whether returned result field formats align with social insurance handling system output fields, with no unit confusion or field misalignment.
- Call the same calculation request three consecutive times, check whether returned results are consistent, to confirm parameter configuration stability.
- View model call logs, confirm interface request proxy nodes and tokens use government intranet compliant configurations, with no abnormal access records.
