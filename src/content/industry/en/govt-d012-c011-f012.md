# Internal Office and Employee Services for Pension, Work Injury, and Unemployment Benefit Verification: Deployment and Upgrade

## What the Data for This Category Looks Like
Data for this category originates from social insurance administration systems, personal benefit records, labor relations and work injury identification systems, and the electronic social security card platform. The update frequency is daily. Daily processed documents include benefit application forms, payment duration certificates, retirement approval forms, work injury identification materials, and unemployment insurance benefit application materials. Core fields include insured person identity identifiers, cumulative payment durations, work injury identification conclusions, unemployment insurance participation periods, and benefit calculation benchmark values. Data fields must align with native fields from social insurance administration systems, with no additional custom fields added.

## What Constraints These Characteristics Impose on Deployment and Upgrade
The data sources for this category are scattered and require daily synchronization. During deployment, adaptation to docking configurations for multiple system databases is necessary to avoid synchronization conflicts and data loss. Daily processed documents have diverse formats, so parsing rules compatible with various business forms must be configured to ensure accurate field extraction. Data fields must strictly align with the native structure of social insurance administration systems. During upgrades, field mapping logic must be retained to prevent failure of benefit calculation logic. Additionally, since errors directly relate to fund security and public interests, an exception alert and rollback mechanism must be pre-configured during the deployment phase to ensure rapid recovery from abnormal situations.

## How to Set Configurations
The following configuration items apply to FastGPT v4.17.0, optimized for internal office scenarios for pension, work injury, and unemployment benefit verification:

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `20–30` | This category requires daily synchronization of data from multiple social insurance systems. A stable connection pool prevents concurrent requests from exhausting database resources |
| `MONGODB_URI` | Configure according to the MongoDB access address of the social insurance administration system | Used to store unstructured business documents such as work injury identification materials and benefit application forms |
| `PG_URL` | Configure according to the address of the locally deployed PostgreSQL instance | Used to store structured core data such as insured person payment records and benefit calculation results |
| `REDIS_URL` | `redis://:custom password@local IP:6379/0` | Used to cache frequently queried personal benefit records to reduce query pressure on social insurance systems |
| `STORAGE_S3_ENDPOINT` | `local object storage address:9000` | Used to store batch-uploaded business forms and approval materials, meeting offline deployment requirements |
| `FILE_TOKEN_KEY` | `Random 32-character string` | Used to generate access tokens for business documents, controlling access permissions for sensitive social insurance materials |

## Three Common Mistakes
- Symptom: After starting the Docker image, a database connection failure is displayed, with the log returning `connection refused`. Cause: The access address for `PG_URL` or `MONGODB_URI` is not configured correctly, and the container cannot resolve the database service address on the host machine.
- Symptom: When initiating a benefit verification query, the request takes more than 40 seconds and eventually returns a timeout error. Cause: The connection count for `DB_MAX_LINK` is not limited, and concurrent synchronization tasks and query requests seize database resources, leading to response delays.
- Symptom: Local stored business documents cannot be loaded after offline deployment. Cause: `STORAGE_S3_ENDPOINT` is not correctly configured to point to the local object storage, and a public cloud storage address is used instead, resulting in inability to access local files.

## How to Verify Successful Configuration
- Run a database connection test script to verify that configurations for `PG_URL` and `MONGODB_URI` can establish normal connections.
- Initiate a simulated benefit verification query and confirm that the response time meets the expected threshold for the business scenario.
- Upload a work injury identification material to verify that `STORAGE_S3_ENDPOINT` can properly store and read files.
- Generate an access token for a business document to confirm that `FILE_TOKEN_KEY` can correctly generate and validate token validity.

The values provided are common starting points and should be measured against the reader's own samples.
