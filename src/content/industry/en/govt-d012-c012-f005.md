# Internal Office and Employee Services for Elderly Care Service Institution Supervision: Tool Calling and Plugins

## What the Data for This Category Looks Like
Core data for this category comes from elderly care service information platforms, civil affairs statistics systems, fire safety inspection records, and institution operation ledgers. The update frequency is once per month. Daily processed documents include institution filing materials, operation subsidy applications, service quality inspection forms, safety hazard rectification ledgers, and elderly admission files. Data fields include institution name, number of beds, license number, application subject, rectification time limit, and more. Data formats from different sources have minor differences. Cross-source integration and verification must be completed via tool calling.

## What Constraints These Characteristics Impose on Tool Calling and Plugins
The monthly update frequency requires tool calling to adapt to a fixed data pull cycle. This avoids resource waste from frequent calls. Multi-source heterogeneous data formats require tool calling to support flexible parameter matching and format conversion. This ensures records from different platforms can be verified uniformly. Core business documents have strong field correlations. Tool calling must accurately link filing, subsidy, rectification and other data. Otherwise, issues such as incorrect subsidy distribution or missed safety hazard judgments may occur. Cross-department collaboration scenarios require plugins to support integration with external systems such as fire safety and market supervision. This further increases configuration complexity.

## Configuration Settings

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Automatically adapts to multiple tool calling requirements in elderly care supervision scenarios, no need to manually specify individual tools |
| `functionCall` | Strictly match the field format of elderly care supervision documents | Ensures tool calling parameters correspond one-to-one with fields in filing, subsidy and other documents, avoiding format errors |
| Tool call timeout threshold | 600 seconds | Data pulling in this scenario involves cross-source queries across multiple platforms, so sufficient response time must be reserved |
| Number of items returned per tool call | Top 3 | The core documents in this scenario are the three core materials of filing, subsidy and rectification, so no redundant calls are needed |
| Content length returned per tool call | No more than 800 characters | Avoids slow speeds caused by too much content returned via API calls |
| Run log output switch | Only return tool execution results | Avoids redundant run records interfering with supervisors' viewing of core business content |

## Three Common Misconfiguration Issues
- Issue: The tool calling module continuously outputs redundant run records. Cause: Non-core run log configurations are not disabled, resulting in large amounts of debug information being included in returned content.
- Issue: Connection timeout errors occur when calling MCP tools. Cause: The delay of cross-platform data queries in elderly care supervision scenarios is not adapted, the timeout threshold is set too low, or valid access permissions are not configured.
- Issue: API calls return text too slowly. Cause: The length of content returned per tool call is not limited, resulting in the system needing to process excessive data.

## How to Verify a Successful Configuration
- Initiate a tool call for elderly care institution filing data. Check that returned content only includes core business data with no redundant run records.
- Call a cross-department MCP tool. Confirm that fire safety inspection record data can be returned normally within the 600-second timeout threshold.
- After configuring the `functionCall` parameter, initiate a tool call for subsidy application review. Confirm that the returned parameter format fully matches the business document fields.
- Test API calls. Confirm that the output speed of returned content meets the response requirements of the business scenario.
