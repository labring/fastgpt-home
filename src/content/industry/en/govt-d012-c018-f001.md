# Internal Office and Employee Services for Enrollment Registration and Payment Verification: HTTP Interfaces and External Systems

## What the data for this category looks like
This category of data covers business documents and system interaction data across the full workflow of enrollment registration and payment verification. Sources include social insurance handling systems, tax social insurance premium collection systems, market entity registration databases, and shared public security and civil affairs data. The update frequency is daily. Business documents include enrollment registration forms, payment base declaration forms, personnel change forms, social insurance premium verification slips, and personal benefit records. Fields include natural person identification, labor relationship status, payment base, verified amount, enrollment status, and more. Units include identity codes, currency units, timestamps, and more.

## What constraints do these data characteristics impose on HTTP interfaces and external systems?
These data characteristics create multiple constraints for HTTP interfaces and external systems in this link. Multi-source, cross-department data sources require interfaces to adapt to format specifications and identity verification rules of different systems. The daily update frequency requires matching interface call frequency and synchronization rhythm to avoid data lag or repeated pulls. Business documents have many fields and involve sensitive information, so interfaces must include permission verification and data desensitization rules. Large data volumes in time-consuming scenarios such as batch personnel changes and cross-system reconciliation require interfaces to support batch transmission and segmented processing. The need to reconcile with tax collection data requires interface return fields to align with tax system fields, reducing secondary conversion costs.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Authorization | Carry the `Authorization` header field with the value `Bearer {system-assigned interface secret}` | Adapt to identity verification requirements of multi-source social insurance systems, comply with industry interface security standards |
| Interface timeout period | 600 seconds | Cover time-consuming scenarios such as batch personnel changes and cross-system reconciliation |
| variables | Configure as `{"target_systems": ["social insurance handling system", "tax collection system"]}` | Clarify target data sources for interface calls, avoid cross-system confusion |
| responseData | Only return the `personnel identity information, payment base, verification status` fields | Simplify returned content, reduce data transmission load, adapt to fast processing needs of internal office work |
| Batch request threshold | 100 items per request | Match the conventional batch processing scale of personnel change forms, avoid interface overload |

## Three common configuration errors
- Symptom: Interface returns `403 Forbidden` error. Cause: The `Authorization` header field is not configured correctly, or an expired interface secret is used.
- Symptom: Pulled payment data does not match tax system reconciliation results. Cause: Interface call time is not aligned with system data update time, and a scheduled pull task is not set according to the daily update frequency.
- Symptom: Interface returns missing fields or abnormal format. Cause: The `responseData` filter is not configured according to the field rules of business documents, or field naming differences across systems are not adapted.

## How to confirm the configuration is correct
- Initiate a test request in the interface debugging tool of FastGPT v4.17.0, check the `Authorization` header verification result to confirm identity authentication passes.
- Pull daily personnel change data, verify whether returned fields match the field definitions of business documents.
- Run a scheduled pull task to confirm the data update frequency matches the daily update rhythm required by the business.
- Initiate a batch data transmission request to confirm the interface does not trigger overload errors and the returned results match the expected number of items.
