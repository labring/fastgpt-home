# Internal Office and Employee Services for Territorial Spatial Planning Compilation and Implementation Evaluation: Deployment and Upgrade

## What the data for this category looks like
The daily documents for this category include territorial spatial overall plans, detailed plans, special plans, planning implementation evaluation reports, and public opinion summaries. Data sources are the territorial spatial basic information platform, natural resource survey and monitoring data, population and economic statistics, and remote sensing images. Fields include planning constraint indicators such as spatial coordinates, construction land scale, and cultivated land retention quantity. Units are mostly square kilometers and hectares. Each planning document contains multi-layer spatial data and statistical indicators, with an overall large data volume. It requires collaborative verification of multi-source data before use, and the update frequency is annual.

## What constraints these characteristics impose on the deployment and upgrade link
Annual updated data sources require configuring trigger rules for scheduled synchronization tasks during deployment to ensure data timeliness. Format compatibility requirements for multi-source spatial data require pre-adapting standard spatial file formats such as shp and geojson to avoid import failures. The large data volume of planning documents requires configuring sufficient storage resources and database connection pools to support high-concurrency read and write operations. Internal office scenarios require limiting access scope while ensuring permission configuration for cross-department collaboration. During upgrades, the index structure of original spatial data must be compatible to avoid interruptions to synchronization tasks affecting daily office workflows.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Set to a cluster address with read-write separation; set the maximum connection pool size to `200` | The large data volume of spatial planning documents and remote sensing images requires support for high-concurrency read and write operations |
| `REDIS_URL` | Set to a local cluster address with a cache expiration time of `600 seconds` | Annual updated planning data does not require frequent cache refreshes, which can reduce database pressure |
| `FE_DOMAIN` | Enter the secondary domain name of the internal office system; only allow internal IP access | Meet the access scope requirements for internal office and employee services, and ensure data security |
| `STORAGE_S3_ENDPOINT` | Connect to the cloud storage service endpoint specified by the natural resources department; adapt to storage space above `1000 GB` | Comply with departmental storage specifications for spatial data, and ensure data compliance |
| `ROOT_KEY` | Set to a strong random string of 32 or more characters | Generate initial administrator credentials to ensure permission security for the internal system |
| `PG_URL` | Set to a local PostgreSQL cluster address; enable slow query logging | Used to store large model call logs and planning data synchronization records, facilitating troubleshooting |

## Three common mistakes
- Failure to retrieve login credentials after deployment: The symptom is that the username and password fields appear empty on the backend management page login portal. The cause is that `ROOT_KEY` was not configured prior to deployment to generate initial administrator credentials, so the system did not initialize an administrator account.
- DingTalk robot deployment fails message receiving address verification: The symptom is a verification failure prompt when publishing the DingTalk application. The cause is that `FE_DOMAIN` was not set to a publicly accessible address, or internal network penetration configuration was not completed, preventing DingTalk from calling the service address.
- Abnormal large model calls after switching the OneAPI address: The symptom is model response timeouts during conversation flows. The cause is that `PG_URL` was not correctly configured to link the storage path for large model call logs, making it impossible to locate issues after call failures.

## How to confirm the configuration is complete
- Log in to the FastGPT v4.17.0 backend management page, and complete login verification using the initial administrator credentials.
- Upload a shp-format test file of a territorial spatial overall plan, and confirm that the file storage path matches the endpoint configured in `STORAGE_S3_ENDPOINT`.
- Initiate a planning data synchronization task, and check whether the corresponding data index is generated by the cache service corresponding to `REDIS_URL`.
- View the backend system logs, and confirm that the database connection status of `MONGODB_URI` is normal.

The values provided here are common starting points, and should be measured against the reader's own samples.
