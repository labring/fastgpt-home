# Internal Office and Employee Services for Centralized Treasury Payment and Reimbursement Audit: Tool Calling and Plugins

## What this category’s data looks like
Data for this category comes from the centralized treasury payment system, unified budget management system, electronic invoice platform, and contract management system. It updates once daily. Daily processed documents include payment applications, fund appropriation plans, invoices, contracts, acceptance receipts, reimbursement approval forms, and payment vouchers. Core fields include budget indicator code, economic classification code, ticket verification code, contract performance amount, and acceptance batch number, among others. All data is generated around the compliance and execution progress of individual fund payments.

## Constraints on tool calling and plugin workflows
Data originates from multiple independent systems, so tool calling must support parallel pulling of corresponding documents across interfaces to prevent cross-system data inconsistency. Compliance audits for single payments rely on precise matching of individual data entries. Limit tool calling to process one payment or reimbursement document per operation, and do not handle multiple entries at once. Daily updated datasets have stable scale. Set the tool calling timeout threshold to match the field parsing duration of a single document. Validate raw pulled data formats to avoid audit failures caused by differences in system fields.

## Configuration settings
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `toolChoice` | `auto` | Allow the model to independently select tools to complete compliance verification |
| `functionCall` | Only specify the fiscal compliance verification tool | Limit the model to calling dedicated tools, avoiding unrelated function calls |
| Single tool call timeout | 600 seconds | Match the time required for pulling data from multiple systems and verifying documents |
| Number of tool call results returned | Top 3 entries | Match the scenario where only core verification results are needed for single-entry audit |
| Context window size | 8000–12000 token | Accommodate all fully associated document data for a single document |

These configurations apply to FastGPT v4.17.0.

## Three common configuration errors
- Tool calling interface returns 413 error: The interface displays a request entity too large prompt. The cause is failure to limit the total size of tool return results, where associated document data pulled for a single operation exceeds the transmission threshold allowed by the interface.
- Unable to force the model to skip inference mode when using the qwen3 model: The model generates inference results directly without calling the specified tool. The cause is failure to lock the tool calling scope via the `functionCall` parameter, so the model independently selects a non-tool-calling inference path.
- Missing MCP streamable HTTP adaptation: Tool calling cannot achieve streaming returns. The cause is failure to enable the corresponding protocol configuration switch, and failure to adapt to the streaming transmission requirements of fiscal system interfaces.

## How to verify correct configuration
- Submit a simulated payment application audit, and check if the model calls the specified fiscal compliance verification tool.
- View tool calling logs to confirm the number of returned results matches the configured requirements, and no timeout exceptions are triggered.
- Check the conversation interface to confirm intermediate tool calling request and return logs are not displayed, only the final audit result is shown.
- Verify multi-system data pulling functionality, confirm data can be normally pulled from both the centralized treasury payment system and electronic invoice platform.

Note: The values listed above are common starting points, and should be evaluated against the user’s own samples.
