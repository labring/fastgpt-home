# Internal Office and Employee Services for Land Use Rights, Mining Rights, and State-Owned Property Transactions: HTTP Interfaces and External Systems

## What the Data for This Category Looks Like
Daily documents for this category typically include transfer announcements, transaction notices, bid applications, margin vouchers, transaction confirmation letters, listing result announcements, property transfer descriptions, and similar materials. Data is usually sourced from national public resource trading platforms, natural resource trading systems, property exchange systems, and state-owned asset supervision systems, with an update frequency of once per day. Data fields typically center on transaction subject ownership, restriction conditions, margin amounts, and transaction status. Field naming varies slightly across different systems, so interface mapping is required to unify formats.

## Constraints Imposed on HTTP Interfaces and External Systems
Multiple data sources require interfaces to support authentication and data format adaptation for multiple systems, to prevent data parsing failures caused by system differences. The daily update frequency requires interface calls to align with business rhythms, avoiding excessive frequency or delays that would prevent timely access to the latest transaction information. Diverse document structures and significant field differences require interfaces to support custom field extraction and mapping, to ensure internal office systems can obtain standardized transaction data. Severe consequences of transaction errors require interfaces to include failure retry and data verification mechanisms, to prevent transaction process interruptions or data errors caused by interface anomalies.

## How to Set Configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {API key assigned by the platform}` | The trading systems connected to this category typically use standard Bearer token authentication, which ensures valid and compliant interface access permissions. |
| `variables` | `{"target_type": ["land use rights", "mining rights", "state-owned property"]}` | This limits the transaction subject types returned by the interface, filters out irrelevant data from non-target categories, and improves the accuracy of internal office data. |
| `responseData` | `Only extract core fields from transaction confirmation letters, listing result announcements, and bid applications` | Internal office systems only require core transaction document fields, which reduces data transmission volume and parsing complexity. |
| Request timeout | 30-60 seconds | The transaction data for this category typically has a large volume, so sufficient interface response time must be reserved. |
| Failure retry count | 2 times | Trading system interfaces occasionally experience fluctuations. Retries can reduce failure rates while avoiding transaction abnormalities caused by repeated submissions.

## Three Common Mistakes
- Interface calls return a 401 Unauthorized error. This occurs when the `Authorization` header is not configured correctly, an incorrect API key is used, the authentication format is invalid, or the authentication rules of the connected trading system are not matched.
- Local deployments cannot connect to external trading system interfaces. This occurs when the default local database configuration is not adjusted, or network permissions for external system access are not enabled, preventing direct requests to external trading services.
- Webhook-received transaction data has missing or disorganized fields. This occurs when the target type is not limited via `variables`, resulting in mixed transaction data from non-target categories, or when the field extraction rules for `responseData` are not configured correctly, leading to loss or redundancy of core transaction information.

## How to Confirm Configurations Are Correct
- Initiate a test call for the target category, and check if the returned `responseData` only includes the preset core transaction fields, with no excess non-target data.
- Review interface call logs, confirm that the `Authorization` header is correctly included, the authentication status code is 200, and no unauthorized errors are present.
- Simulate requests for multiple category subjects, and confirm that the system only returns data related to land use rights, mining rights, and state-owned property as limited in `variables`.
- Trigger a timeout scenario test, confirm that the system completes responses within the preset timeout period, and triggers the retry mechanism when an interface failure occurs.
