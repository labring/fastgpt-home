# Internal Office and Employee Services for Land Use Rights, Mining Rights, and State-owned Property Rights Transactions: Deployment and Upgrade

## What this category of data looks like
This category of data primarily comes from the national public resource trading platform, natural resource trading systems, property right exchange systems, and state-owned asset supervision systems. The update frequency is daily. Documents processed daily include transfer announcements, trading instructions, bid application forms, margin vouchers, transaction confirmation documents, listing result announcements, property right transfer specifications, and more. Common data fields include ownership number, trading target type, margin amount, bid qualification restrictions, etc. Some documents have a mixed structure of structured forms and announcement-style text. Units involved include square meters, ten thousand yuan, and other measurement standards related to resource and asset transactions.

## What constraints do these characteristics impose during deployment and upgrade
This category of data originates from multiple official systems and is updated daily. Deployment processes must include configuration for pulling data from multiple sources to avoid service lag caused by excessive single-pull data volume. The mixed structured and unstructured document structure requires adjustments to text parsing logic during upgrades to support different trading document formats. Trading data has strict ownership attribute requirements. Deployment phases must include data verification rule configuration to prevent incorrect target information from entering the knowledge base. Additionally, trading data errors can cause state-owned asset disputes or delayed property transfers. Upgrade processes must reserve one-click rollback configuration and daily data backup paths to maintain service stability.

## How to set configurations
The following configurations are based on FastGPT v4.17.0, adapted to the characteristics of trading data in this category:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Read-only connection address pointing to the state-owned asset supervision synchronization database | Transaction ownership data in this category requires strict isolation from business write operations; the read-only connection ensures data security |
| `DB_MAX_LINK` | Set to 20–30 | High-frequency daily pulling of trading data requires controlling the number of connections to avoid occupying excessive resources of the business system |
| `REDIS_URL` | Configure as the internal cache cluster address, with a cache validity period of 8–12 hours | Daily updated trading data does not require long-term caching; this range balances query efficiency and data freshness |
| `STORAGE_S3_ENDPOINT` | Point to the official storage node of the public resource trading platform | Adapt to the unified storage protocol for trading attachments in this category, ensuring compliant storage of voucher files |
| `FILE_TOKEN_KEY` | Use a symmetric encryption key aligned with the state-owned asset system | Restrict trading attachments to only be accessible to internally authorized employees, preventing leakage of sensitive ownership documents |

## Three common mistakes
- Issue: A 404 not found error occurs after Vercel automated deployment. Cause: The `FE_DOMAIN` parameter was not correctly configured to point to the internal office domain, resulting in a failure to match front-end resource paths.
- Issue: After upgrading to a new version, configuration items related to `systemEnv` in the configuration file cannot be recognized. Cause: The configuration structure was not updated according to official documentation, and old version parameters were directly copied to the new configuration file without adapting the dedicated data source connection parameter format for this category.
- Issue: When accessing the application via a non-login share link, the trading attachment reference and view original text functions do not work properly. Cause: The `FILE_TOKEN_KEY` parameter was not correctly configured, causing the attachment permission verification logic to fail and failing to bind internal employee access permission rules.

## How to confirm the configuration is complete
- Test the connection validity of `MONGODB_URI` to confirm that trading data can be read and there are no write permission exceptions.
- Check the cache service logs to confirm that the cache duration of trading data matches the 8–12 hour configuration, with no abnormal expiration or uncached situations.
- Generate an internal non-login share link to verify that access to trading attachments is only open to internally authorized personnel, with external access triggering permission interception.
- Check the storage service connection logs to confirm that the storage node configured via `STORAGE_S3_ENDPOINT` can normally store trading voucher files.
