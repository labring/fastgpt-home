# Internal Office and Employee Services for Student Financial Aid and Grant Review: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Data for this category originates from the National Student Financial Aid Management Information System, school student status systems, civil affairs low-income and extremely poor assistance data, and financial payment systems. It updates per semester.
Staff process daily documents including family economic hardship certification forms, financial aid application forms, scholarship and grant review forms, distribution lists, and public notification materials.
Core fields include student identity information, family economic status certification results, student status, aid amount, and bank card information. Data associates structured fields output by multiple departmental systems, with no additional unstructured redundant content.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompt Engineering
The per-semester data update rule limits multi-turn dialogue contexts to the current semester range. This prevents cross-cycle data from interfering with review results.
Multiple departmental data sources require prompt engineering to clearly specify field verification logic for corresponding systems. This ensures alignment between student status, low-income information, and certification form content.
Diverse document structures require multi-turn dialogue to guide users step-by-step through the certification, application, review, and distribution processes. It sequentially verifies required fields for each form to prevent missing key information.
The correlation of core fields requires prompt engineering to configure association verification rules. These rules automatically compare field consistency across different systems. This reduces repetitive manual verification work.

## Configuration Settings
Configuration references for FastGPT v4.17.0 are as follows:

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Initialize global variables including current semester and business subject ID, with values set according to the current service cycle | Data is updated per semester, to limit the valid cycle of dialogue context |
| `messages` | Retain the first 10 historical dialogue messages, automatically truncate excess content | Avoid overly long contexts causing confusion in verification logic |
| Maximum context length | 8000–12000 token, set based on actual testing | Adapt to the text length of multiple form fields and multi-turn dialogue content |
| Single dialogue timeout | 300 seconds, set based on actual testing | Match the average processing duration of financial aid review processes |
| Non-login link configuration | Restrict access to internal office IPs only, retain 7 days of operation logs | Comply with internal office security requirements, prevent accidental deletion of logs |
| `chatId` | Bind the unique identifier of the current dialogue, used to associate operation logs | Track the complete operation trajectory of the review process |

## Three Common Misconfigurations
- Phenomenon: In non-login link scenarios, operation logs are deleted synchronously when a user deletes dialogue content. Cause: No log retention rule is configured for non-login links, and the deletion logic incorrectly binds dialogue content and operation logs.
- Phenomenon: When a workflow node attempts to load historical global variables in a new dialogue, the variable fields are empty. Cause: The cross-dialogue retention permission for global variables is not enabled in the dialogue configuration, and the persistence rule for the `variables` parameter is not bound.
- Phenomenon: After adding a MySQL tool call node, the dialogue returns a 400 status code with no response body. Cause: The permission scope of the database connection is not configured correctly, or the prompt engineering does not limit query fields to structured tables related to financial aid review, leading to illegal queries triggering interception.

## How to Confirm Proper Configuration
- Launch a simulated dialogue, enter student identity information and the current semester, check whether the dialogue context automatically loads the global variables corresponding to the `variables` parameter.
- Trigger the non-login link, delete a test dialogue, check whether the background log retains the operation record to confirm that the log retention rule is effective.
- Call the MySQL tool node, enter query conditions related to financial aid review, check whether the returned results only include structured data for the current semester.
- Test the workflow node, call historical global variables in a new dialogue, confirm that the variable content loads normally.
