# Internal Office and Employee Services for Safety Production Hazard Inspection and Governance: Vector Models and Indexes

## What the data for this category looks like
This category involves entities including emergency management departments, industry competent departments, safety management departments of production and business entities, and park management committees.
Daily generated documents include hazard inspection lists, hazard governance ledgers, rectification notices, review records, and major hazard rectification supervision notices.
Data sources cover safety production supervision systems, enterprise hazard self-inspection systems, law enforcement inspection records, and accident statistics systems.
The update frequency is daily.
Documents include structured fields such as hazard ID, rectification deadline, responsible entity, inspection date, and review result. They also include semi-structured text content such as rectification descriptions and hazard details.

## Constraints on vector models and indexes
Multi-source and heterogeneous data sources require the index system to support unified vectorization of cross-system data. This avoids vector deviation caused by differences in data formats.
Daily updated incremental data requires configuration of an incremental index strategy. This ensures real-time synchronization of hazard inspection and rectification records.
Differences in the structure of different document types require chunking strategies to adapt to mixed scenarios of structured fields and semi-structured text. This avoids cutting off core business fields.
High-risk error consequences require the confidence of vector recall to match business judgment standards. This reduces the probability of missed or false recalls.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Matches the average content length of documents such as hazard inspection lists and rectification notices, and avoids cutting off core business fields during chunking |
| Overlap Length | 100–200 characters | Retains overlapping content of adjacent chunks, ensuring that key information across chunks such as rectification deadlines and hazard IDs is not split |
| `maxToken` | 8192 | Matches the input limit of mainstream embedding models, and meets the needs of vectorizing multiple combined documents |
| Similarity Threshold | 0.75–0.85 | Matches the matching accuracy of major accident hazard judgment standards, and reduces the recall of irrelevant hazard records |
| Single Search Limit | Top 10 entries | Balances recall efficiency and business association needs, covering historical rectification and review records of the same type of hazards |
| `defaultToken` | Calibrated based on actual testing | Adapts to the token consumption limit of local deployment or external API calls, and avoids call timeouts |

## Three Common Misconfigurations
- When configuring baidu-embedding-v1, a 404 status code is returned. This occurs if the model's API call address is not filled in correctly, or if permission filing for the corresponding model is not completed in the system.
- After running the m3e vector model in docker, it cannot be added in the system. This occurs if the model container port is not mapped to the host machine, or if the system whitelist for accessing local models is not configured.
- Search results only return a single document, and cannot associate multiple business records for the same hazard. This occurs if the single search limit is not adjusted, leading to a limited recall scope.

## How to Confirm Proper Configuration
- Upload a single hazard inspection list, and check if the core fields such as hazard ID and rectification deadline are fully retained in the chunked text displayed by the system.
- Initiate a query for "track the rectification status of a specific hazard", and check if the returned search results include associated content from the corresponding rectification notices and review records.
- Check the system's vector model call logs, and confirm that there are no error reports related to `maxToken` overlimit or `defaultToken` configuration abnormalities.
- Deploy a lightweight vector model in an arm soft router environment, and confirm that FastGPT v4.17.0 can load normally and generate vector embeddings.
