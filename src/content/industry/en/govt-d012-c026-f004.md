# Internal Office and Employee Services for Engineering Construction Project Approval: Workflow Orchestration

## What the data for this category looks like
Data sources for this category include the engineering construction project approval management system, construction drawing review system, enterprise qualification database, and credit platform. The system updates data daily. The platform processes daily documents including construction permit applications, construction drawing review qualification certificates, quality and safety supervision procedures, and completion record forms. Data fields cover approval node status, participating construction unit qualification numbers, personnel practicing qualification certificate numbers, material submission status, and more. There is no unified fixed format template, and field structures must be adapted to different approval stages.

## How these characteristics impose constraints on workflow orchestration
Since data comes from multiple heterogeneous systems and updates daily, configure cross-system data pull nodes in workflow orchestration to ensure real-time access to the latest approval materials and participating unit information. The non-uniform field structure of multiple document types requires adding field verification nodes during orchestration to avoid invalid process startup. Embed pre-review nodes to verify participating unit qualifications and personnel information, preventing qualification mismatches in subsequent processes. The approval process’s node transfer relies on system status triggers, so ensure the mapping relationship between workflow nodes and approval nodes is accurate.

## How to set configurations

| Global variable configuration | Bind the `variables` of the engineering approval system and qualification database | Pull core data such as construction permit applications and participating unit qualifications across systems |
| Node trigger condition | Trigger based on material submission completion status | Match the engineering approval process’s node transfer logic, ensuring the process starts according to actual progress |
| Timeout setting | 600 seconds | Adapt to the average response time of cross-system data pulls, avoiding process interruptions caused by network delays |
| Retry count | 2 times | Resolve call failures caused by temporary network fluctuations or temporary system interface faults |
| `nodeId` mapping configuration | Map approval node IDs to workflow nodes | Achieve precise binding between engineering approval processes and workflow nodes, ensuring correct transfer order |
| Parameter verification rule | Verify that participating unit qualification fields are not empty | Filter invalid applications in advance, preventing missing key information mid-process |

## Three common misconfigurations
- Workflow terminates at an intermediate node, and the session ends directly without triggering subsequent approval nodes. The cause is that no node exception fallback branch is configured. When cross-system data pull fails, the process directly enters the end state.
- Workflow published to Feishu bot cannot be triggered for execution. The cause is that the callback `variables` of the Feishu bot are not configured correctly. The bot cannot receive user-triggered approval requests.
- Running the upgrade script fails and returns an authentication error. The cause is that the `example value` in the environment variable is not replaced. The HTTP request cannot pass interface authentication.

## How to confirm the configuration is correct
- Trigger a simulated engineering approval process, and check whether each workflow node transfers in sequence according to the preset order.
- View workflow operation logs to confirm that cross-system pulled data such as construction permit applications and participating unit qualifications is complete and field-matched.
- Simulate a node exception scenario, such as disconnecting the temporary network, and check whether the preset retry or fallback branch is triggered.
- Initiate an API call to verify that the workflow creation or startup request normally returns the expected node ID or execution status.
