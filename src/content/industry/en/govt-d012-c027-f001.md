# Internal Office and Employee Services for Construction Project Bidding: HTTP Interfaces and External Systems

This document is written for FastGPT v4.17.0.

## What This Category’s Data Looks Like
The entities involved in this category include development and reform departments, industry competent departments such as housing and urban-rural development, transportation, water resources, public resource trading centers, and bidding agencies. Daily generated documents include bidding announcements, pre-qualification documents, bidding documents, submission documents, bid evaluation reports, successful bid candidate announcements, and successful bid result announcements.
Data sources include the national public resource trading platform, local trading platforms, project approval systems, and bidding and tendering supervision systems, with an update frequency of once per day. Common data fields include project number, section information, qualification requirements, expert bid evaluation records, and more. Document formats from different sources follow unified industry specifications.

## Constraints Imposed on HTTP Interfaces and External Systems
Since data sources include multiple official platforms, interfaces must adapt to the authentication rules and data formats of different platforms to avoid request failures caused by format incompatibility.
Daily updated business data requires interfaces to be configured with a scheduled pull mechanism, ensuring internal office systems can obtain the latest bidding information.
The need to transfer multiple types of business documents requires interfaces to support large-volume file uploads and parsing of multiple document formats.
Additionally, errors in bidding data can lead to serious consequences such as suspended bid results and project delays. Interfaces must be configured with complete validation and retry mechanisms to ensure the accuracy and stability of data transmission.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
|---|---|---|
| `Authorization` | `Bearer {API key assigned by the platform}` | Official interfaces such as public resource trading platforms and project approval systems typically use Bearer tokens for identity authentication |
| `variables` | Inject business variables such as project number, section ID | Bidding data must be bound to specific project identifiers to ensure interface requests accurately match corresponding business data |
| `responseData` | Return only core business fields | Internal office scenarios only require specified data such as bid evaluation reports and successful bid results, reducing invalid data transfer volume |
| Single request timeout period | 300-600 seconds | Documents such as submission documents and bid evaluation reports are typically large, resulting in longer data generation and transfer times |
| File upload size limit | 1000 MB | Bidding-related documents often contain large content such as engineering drawings and bill of quantities |
| Request retry count | 2-3 times | Official trading platform interfaces may experience temporary fluctuations, and retries reduce the probability of request failures |

## Three Common Misconfigurations
- Phenomenon: After using the API to upload a file, the agent backend cannot access the file, and the service freezes. Cause: Cross-domain access permissions for file storage are not configured, or uploaded files are not synchronized to the shared directory of the backend service.
- Phenomenon: After deploying with Docker-compose, workflow and knowledge base configurations become blank after a period of time, but interfaces function normally. Cause: The configuration volume mounted by the container does not have persistent storage enabled, and local configuration is lost after the container restarts.
- Phenomenon: When calling the chat API, returned results contain extra reference markers, which negatively impacts user viewing experience. Cause: The reference display configuration is not disabled in the interface request, or reference-related fields in `responseData` are not filtered.

## How to Verify Proper Configuration
- Initiate a test interface request, and check if the returned `responseData` only contains preset core business fields with no redundant data.
- Upload a test bidding announcement file, and confirm that the backend service can normally read the file content and complete parsing.
- Restart the deployed FastGPT container, and check if workflow configurations and knowledge base information are fully retained.
- Call the chat API, and confirm that returned results have no extra reference markers, meeting internal office usage requirements.
