# Internal Office and Employee Services for Construction Project Bidding and Tendering: Multi-turn Dialogue and Prompting

## What this category of data looks like
This category of data originates from the national public resource trading platform, local trading platforms, project approval systems, and bidding and tendering supervision systems, with daily updates. Daily documents include bidding announcements, qualification pre-qualification documents, bidding documents, tender documents, bid evaluation reports, successful bid candidate announcements, and successful bid result announcements. Core fields include section division, qualification requirements, bill of quantities, bid evaluation expert records, and other items. Typical users are development and reform departments, industry competent departments such as housing and urban-rural development, transportation, and water resources, public resource trading centers, and bidding agency institutions.

## Constraints on Multi-turn Dialogue and Prompting
Data is updated daily and sourced from multiple dispersed locations. Multi-turn dialogue must associate with the latest project-related documents to avoid using expired information. Documents have diverse types and include specialized fields. Prompts must clearly distinguish the format and field rules of different documents to ensure accurate parsing. Some documents involve compliance verification. Multi-turn dialogue must retain complete historical interaction records for subsequent verification. The bidding and tendering process involves multiple linked steps. Dialogue context must cover information across the full cycle from bidding to successful bid award, to avoid loss of key content.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind to a project-specific ID | Distinguish dialogue contexts for different bidding and tendering projects, avoid cross-project information confusion |
| `messages` | Retain the most recent 20 rounds of interaction records | The bidding and tendering process involves multiple linked steps. Historical interaction content such as bid evaluation and objection handling must be retained |
| `variables` | Pass project section and announcement date parameters | Precisely limit the scope of prompt retrieval, match exclusive documents for the corresponding project |
| Maximum context length | 8000–12000 characters | Cover the core content of a single bidding document plus bid evaluation report, avoid context truncation |
| Streaming output toggle | Enabled | Adapt to the gradual display requirement for long texts in bidding and tendering scenarios |
| Response speed control | Return data once every 1–2 seconds | Optimize front-end display experience, align with actual user usage habits |

## Three Common Misconfigurations
- Phenomenon: Links returned by streaming output only cover the current page, and cannot jump to new pages. Cause: Front-end event binding for streaming output is not configured correctly, and new window trigger logic is not added for links.
- Phenomenon: The content displayed in the dialogue log details page does not match the actual response content, and the details content does not change after multiple conversations. Cause: `chatId` is not bound to a project-specific identifier, causing all dialogues to reuse the same context record.
- Phenomenon: The streaming output return speed is fixed at 4 seconds per return, and cannot be adjusted. Cause: The response speed control configuration item is not enabled, and the default return interval parameter is used.

## How to Verify Successful Configuration
- Initiate a multi-turn dialogue for a single project bidding and tendering process. Check whether `chatId` remains consistent as the dialogue progresses, to ensure that the context does not cross projects.
- View the dialogue log details. Verify that the returned content matches the actual response generated by the interaction, to confirm that historical records are synchronized correctly.
- Test the streaming output function. Observe the interval time of returned data, and adjust the configuration items to meet front-end display requirements.
- Import a single bidding document for testing. Confirm that the prompt can accurately extract core fields such as section division and qualification requirements, with no content truncation.
