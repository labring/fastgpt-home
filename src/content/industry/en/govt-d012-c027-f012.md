# Internal Office and Employee Services for Construction Project Bidding: Deployment and Upgrade

## What the data for this category looks like
The data for this category mainly comes from national public resource trading platforms, local trading platforms, engineering approval systems, and bidding supervision systems. The update frequency is daily. Documents processed daily include bidding announcements, pre-qualification documents, bidding documents, bid documents, bid evaluation reports, bid winner candidate notices, and bid result announcements. Core fields include section division, qualification requirements, bid evaluation expert records, objection and complaint content, bill of quantities, and construction period, among others. The field structures of different documents vary. Some documents contain structured parameters and unstructured text content.

## What constraints these characteristics impose on deployment and upgrade
Deployments must include task scheduling rules adapted for high-frequency synchronization, to avoid data lag affecting internal office efficiency. Multiple types and structures of documents require targeted parsing rule configuration to ensure accurate extraction of core fields across different documents. Core fields involve compliance content under the bidding law system. Data processing workflows must comply with industry regulatory requirements during deployment. Errors in this category directly affect project progress and compliance responsibilities. A complete error alert and rollback mechanism must be configured during the deployment phase.

## How to set configurations
| Configuration Item | Suggested Value | Basis for This Setting |

| `FE_DOMAIN` | `Intranet or public network domain name of the deployment server` | Adapt to internal office access scenarios, ensure employees can access the platform via specified addresses |

## Three common mistakes
- Phenomenon: Request errors occur when calling marker-pdf, and connection failure prompts appear during Docker deployment. Cause: `STORAGE_S3_ENDPOINT` is not correctly configured to point to the local storage node, or the corresponding port is not mapped for the Docker container, resulting in network connectivity issues.
- Phenomenon: Uploaded bidding documents cannot be parsed via chat, and core fields such as section division and qualification requirements cannot be extracted. Cause: Parsing rules are not configured for specific document types such as bidding announcements and bid evaluation reports, and general parsing templates are used, leading to failed field extraction.
- Phenomenon: Gpt-4o-mini call error logs appear during workflow operation, but the model is not actually called. Cause: The model parameters configured in the workflow node do not match the actually deployed model, or environment variables are not correctly loaded, resulting in invalid model call configuration.

## How to confirm the configuration is complete
- Run the `docker ps` command, confirm that the FastGPT v4.17.0 container and dependent database and cache containers are all running.
- Upload a standard bidding announcement document, verify that core fields such as section division and qualification requirements can be accurately extracted after parsing.
- Configure a daily synchronization task, check whether the latest announcement data from the public resource trading platform can be pulled at the preset frequency.
- Trigger a test workflow, check that there are no unconfigured model call error messages in the platform logs, and confirm that the workflow runs normally.
