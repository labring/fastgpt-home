# Internal Office and Employee Services for Market Entity Registration and Licensing: Forms and Interactions

## What the Data for This Category Looks Like
Daily processing documents for this category include establishment registration applications, articles of association, shareholder resolutions, residence certificates, business licenses, food business license applications, and similar materials. Data sources include the full-process electronic enterprise registration system, the National Enterprise Credit Information Publicity System, the electronic business license system, and the residence information database. The update frequency is daily. Data fields cover subject qualification information, business license application elements, shareholder and capital contribution information, and similar categories. Different documents correspond to distinct field combinations, requiring adaptation to structural differences across multi-source data sets.

## Constraints Imposed on Forms and Interactions
Multi-source data requirements mean forms must support cross-system data pulling and real-time verification to ensure consistency between entered information and official databases. Daily updated data sources require forms to sync the latest residence and credit information to avoid using expired data. Diverse document types require forms to adapt to different field structures and support on-demand switching of field groups. High-risk error outcomes require interactions to include multi-layer confirmation steps to block abnormal inputs that could lead to registration rejection or identity fraud risks. The most time-consuming verification steps require forms to perform pre-verification of key information to reduce subsequent manual processing costs.

## Configuration Setup
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `formInput` validation rules | Set required fields and format checks separately by document field type, such as matching residence address format against the residence information database | Must verify the accuracy of residence information to avoid registration rejection due to incorrect format |
| `formInput` character limit | 800–1200 characters | Adapts to the field length requirements of daily documents and prevents overly long entered content |
| User selection trigger conditions | Trigger pre-licensing judgment after shareholder information is filled out, or trigger corresponding processes based on verification results output by AI | Must determine pre or post licensing conditions based on shareholder materials, and adapt to automatic workflow transitions following AI verification |
| `userSelect` data source | Associate with daily updated data from the National Enterprise Credit Information Publicity System and the residence information database | Data is updated daily, so latest official information must be synced to ensure accuracy |
| `userSelect` pull limit | Top 5 entries | Controls the volume of data pulled in a single request to avoid excessive system resource usage |
| Timeout setting | 600 seconds | Cross-system data pulling requires sufficient response time to prevent mid-process interruptions |

## Three Common Configuration Errors
- Symptom: Workflow runs with the prompt `Cannot convert undefined or null to object`. Cause: No null value handling logic is configured for the `userSelect` data source, and no blocking or conversion is applied to empty data pulled from cross-system sources.
- Symptom: Pre-licensing judgment is not triggered after form submission. Cause: The user selection trigger conditions were not correctly bound, with no association made to the shareholder information filling completion node or the AI verification result node.
- Symptom: Form validation does not block incorrectly formatted residence addresses. Cause: Format validation rules for `formInput` were not configured based on document field types, and the default validation logic was used directly.

## How to Verify Proper Configuration
- Verify that the `formInput` validation rules cover all required fields and format requirements for daily documents.
- Verify that the `userSelect` data source is associated with the specified daily updated system data.
- Verify that trigger conditions are bound to operation nodes corresponding to business workflows.
- Test empty data submission scenarios to confirm that the exception handling logic takes effect.
