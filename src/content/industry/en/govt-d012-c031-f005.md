# Internal Office and Employee Services for Construction Project Environmental Impact Assessment Approval: Tool Calling and Plugins

## What the data for this category looks like
Entities involved in this category include ecological environment department EIA offices, administrative examination and approval bureaus, construction units, and EIA institutions. Daily processed documents include environmental impact assessment reports/statement forms, approval applications, public participation explanations, technical assessment opinions, EIA approvals, and similar materials. These cover both structured approval fields and unstructured text content.
Data sources include the national unified construction project EIA declaration and approval system, ecological environment zoning control results, pollution discharge permission platform, and monitoring data. Update frequency is irregular, with no fixed cycle. Core verification fields include project category, EIA level, pollution prevention measures, public participation status, and similar items.

## What constraints these characteristics impose on the tool calling and plugins workflow
Multiple data sources and irregular update cycles require tool calling to support plugins connecting multiple heterogeneous systems, adapting to output from data sources in different formats. Daily documents have both structured and unstructured characteristics, so tools must have multi-format parsing capabilities to extract key fields such as project category and EIA level from approval applications.
The most time-consuming verification link relies on cross-system data comparison, so tools must automatically pull historical data from corresponding systems to assist verification. Errors directly affect project construction and compliance, so tool calling needs configuration verification mechanisms and failure retry logic to prevent incorrect data from entering the approval process.

## How to configure the setup
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapts to scenarios where system data must be automatically pulled during EIA approval, balancing trigger logic between tool calling and AI responses |
| `functionCall` | Enable structured output | Ensures results returned by tool calling conform to the structured field format of EIA documents, facilitating subsequent verification |
| Tool calling timeout | 600 seconds | Corresponds to the long waiting time required for pulling EIA data across systems, preventing call interruptions due to slow data source responses |
| Plugin trigger condition | Match project category keywords | Only trigger tool calling when approval applications or basic project information are detected, reducing invalid call attempts |
| Number of documents returned per call | Top 5 entries | Controls the volume of tool returned results, avoiding redundant data interfering with verification work |
| Result screening threshold | Top 3 matching results | Focuses on EIA data most relevant to the current project, improving verification efficiency |
| Reranking model configuration | Calibrate based on actual measurements | Adapts to the long text characteristics of EIA documents, optimizing the sorting accuracy of retrieval results |
| Plugin call frequency limit | 100 times per hour | Adapts to the daily business volume of EIA approval, avoiding triggering system rate limits |

## Three common configuration errors
- Outputting both AI-generated content and preset responses after calling a tool: The phenomenon is that after submitting an approval application, the interface displays both model-generated text and pre-configured specified responses. The cause is that the `toolChoice` parameter is not correctly configured, failing to restrict only tool calling or only preset responses.
- Excessive video memory usage after reranking model calls: The phenomenon is that after starting the reranking model, video memory usage quickly grows to 6-7 GB with each call, and this occurs across multiple GPUs. The cause is that model lightweight loading parameters are not configured, or the text batch size for single calls is not limited.
- Tool returning irrelevant EIA data: The phenomenon is that data pulled by the tool does not match the category or level of the current approval project. The cause is that trigger filtering conditions based on project fields are not set, resulting in an overly broad tool call scope.

## How to verify the configuration is correct
- Submit a test approval application, check whether the tool only triggers calls when project category keywords are detected.
- View tool calling logs, confirm that returned results are in structured format and include core fields required for EIA approval.
- Simulate a scenario where the tool has no matching data, confirm that the system automatically outputs the pre-configured specified responses.
- View server monitoring, confirm that video memory usage of the reranking model does not exceed the server configuration threshold.
