# Internal Office and Employee Services for Tendering and Procurement Compliance Management: Model Access and Configuration

## What this category of data looks like
Teams source data for this category from state-owned and public sector procurement centers, tendering offices, business requirement departments, audit and discipline inspection departments, and tendering agencies. Data sources include enterprise procurement platforms, public resource trading platforms, supplier databases, contract management systems, and audit issue databases.
Daily processing covers procurement plans, requirement specifications, tender documents, bid evaluation records, contracts, acceptance documents, and supplier complaint materials. Data updates occur daily.
Data fields include procurement methods, budget basis, scoring methods, supplier qualification requirements, performance acceptance clauses, and additional relevant items. No unified external format exists. Adaptation to internal enterprise procurement rules and group centralized procurement regulations is required.

## What constraints these characteristics impose during model access and configuration
Decentralized data sources and daily updates require synchronization logic for multi-source heterogeneous data when accessing models. This avoids compliance check failures caused by expired data.
Diverse document types and significant field differences require configuration of context loading rules adapted to different document structures. This ensures key compliance clauses are not truncated.
Procurement compliance involves discipline inspection and audit requirements. Full traceability links must be retained for model calls. This ensures every check result can be traced and reviewed.
In multi-department collaboration scenarios, context isolation for different business nodes is required. This prevents cross-link information interference.
Additional adaptation to internal enterprise network security rules is needed. This restricts model call scope for sensitive compliance data.

## How to set configurations
These configurations are developed for FastGPT v4.17.0, and are adapted to internal office scenarios for state-owned and public sector tendering and procurement compliance management.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `maxContext` | `8000–12000 token` | Adapts to context requirements for long procurement documents, avoiding truncation of key compliance clauses and historical bid evaluation records |
| `maxTokens` | `2000–3000 token` | Controls the length of single-round generated content, ensuring readability and completeness of compliance review results |
| `temperature` | `0.1–0.3` | Reduces randomness of generated results, ensuring consistency in scoring method and supplier qualification condition judgments |
| `toolChoice` | `auto` | Automatically triggers tool calls required for compliance checks, adapting to business scenarios requiring cross-document verification |
| `AIPROXY_API_ENDPOINT` | Enterprise internal proxy address | Adapts to internal network environments of state-owned and public sector entities, ensuring transmission security of sensitive compliance data |
| `AIPROXY_API_TOKEN` | Configured per enterprise permission rules | Implements permission control for model calls, restricting unauthorized access to compliance data |

## Three common mistakes
- Phenomenon: Model vendor icons displayed in the interface fail to load normally, appearing as blank or error placeholders. Cause: Internal enterprise network restrictions block access to external static resources, or the resource path for model vendors is not correctly specified in configurations.
- Phenomenon: Workflow nodes cannot use exclusive context, and cross-node information interference occurs. This causes compliance check results to include irrelevant historical procurement data. Cause: The global context reuse switch is not turned off, leading all nodes to share the same context pool. This does not meet information isolation requirements for procurement processes.
- Phenomenon: Multiple models with the same name but different secrets cannot be called normally. Call failures or abnormal results are returned. Cause: Exclusive `AIPROXY_API_TOKEN` is not bound to each model individually. The system cannot distinguish call credentials for different models.

## How to confirm configurations are correctly set
- Submit a compliance check request for a procurement plan. Verify that the returned result includes check content for procurement methods and budget basis, confirming that context is not abnormally truncated.
- Call the configured multi-model interface. Verify that models with different secrets can normally return check results, confirming that the call logic for models with the same name is correct.
- View context logs for workflow nodes. Confirm that only input information from the current node is loaded, with no redundant data from other nodes.
- Check network logs for model calls. Confirm that requests are sent through the configured internal proxy address, complying with enterprise network security requirements.
