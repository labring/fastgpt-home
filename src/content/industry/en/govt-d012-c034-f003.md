# Internal Office and Employee Services for Student Enrollment and Student Status Management: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Data for this category originates from the National Primary and Secondary School Student Status Management System, local enrollment platforms, household registration and property data, and school educational administration systems, with a daily update frequency. Daily processed documents include enrollment application forms, student status information forms, transfer applications, enrollment plans, admission rosters, and student status change approval forms. Data fields cover student identity identifiers, household registration and residence-related information, student status numbers, enrollment batches, change types, and more. The number of fields per document is fixed and fully matches the format of officially registered forms.

## What Constraints These Characteristics Impose on Multi-turn Dialogue and Prompt Engineering
The daily data update requirement means multi-turn dialogue must real-time link to the latest student status, enrollment, household registration and property data to avoid using outdated information. Document fields are strongly bound to official formats, so prompts must clearly specify field extraction rules to ensure returned content matches the official registered field structure. The core business links are household registration and property verification, and student status transfer and change processing. Multi-turn dialogue must guide step-by-step according to business processes to avoid cross-link confusion. Data errors can cause serious consequences such as duplicate or missing student status entries and admission disputes. Dialogue output must include a data source verification step to ensure information accuracy.

## How to Set Up the Configuration
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Maximum Context Length | 8000–12000 characters | Adapts to long text contexts related to enrollment and student status in multi-turn dialogue |
| Number of Single Recalled Entries | Top 3–5 entries | Matches the number of core fields in a single business document to avoid information overload |
| `messages` Context Management | Limit historical message rounds to 5–7 | Prevents overly long contexts from occupying server resources |
| Conversation History Cache Duration | 120 seconds | Adapts to the single interaction cycle of business processing, avoiding interference from expired history |
| `variables` Binding Configuration | Link student status, enrollment, and household registration data sources | Ensures dialogue calls real-time updated official data |
| `chatId` Session Identifier | Bind the unique number of the handled business | Distinguishes student status processing sessions for different students to avoid data confusion |
| Prompt Template Verification | Enable field matching rules | Matches the fixed field structure of business documents to ensure output format compliance |

## Three Common Mistakes
- Interface calls return format errors, with prompts not matching business requirements. Cause: No prompt is written for the fixed field structure of enrollment and student status documents, and no field matching verification configuration is enabled.
- Online dialogue has no response for a long time, with the interface continuously displaying search status. Cause: No limit is set on the number of single-recalled data sources or historical message rounds, leading to timeout when calling multiple external systems, or excessive resource occupation from caching.
- Generated student status information cannot strictly follow the preset JSON structure. Cause: No preset JSON verification rules are bound via `variables`, only relying on natural language prompts to guide output format.

## How to Confirm the Configuration Is Complete
- An enrollment plan document is uploaded, dialogue field extraction is tested, and returned content is checked to include fixed fields such as enrollment batch and planned number of students.
- Multi-round interaction is simulated, household registration information and student status number are asked in sequence, and dialogue is checked to guide step-by-step according to the business process without cross-link confusion.
- The interface is called with `chatId` bound to the unique business number, and returned data from different sessions is checked to avoid confusion.
- The prompt template in the configuration backend is viewed, and the field matching verification rule is confirmed to be enabled, matching the official format of business documents.
