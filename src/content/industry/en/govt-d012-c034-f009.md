# Internal Office and Employee Services for Enrollment and Student Academic Record Management: Model Access and Configuration

## What the data for this category looks like
Data sources for this category include the National Primary and Secondary School Student Academic Record Management System, local enrollment platforms, household registration and property data, and school academic affairs systems. The data updates daily. Commonly processed documents include enrollment application forms, student academic record information forms, transfer applications, enrollment plans, admission rosters, and student academic record change approval forms. Data fields center on student identity, enrollment eligibility, and academic record status. Fields include identification and status fields such as student academic record numbers, household registration addresses, property certificate numbers, and enrollment batches. No additional non-business attached data exists. All data are compliant business fields generated by official business systems.

## What Constraints These Characteristics Impose on Model Access and Configuration
Most data for this category comes from official business systems and updates daily. Model calls must accurately associate multi-source data fields to avoid cross-system data misalignment. Commonly processed documents use fixed-format business forms. Model input must adapt to structured fields and approval flow association logic. Configuration must prioritize data mapping accuracy. At the same time, errors affect student enrollment advancement and academic record compliance. Model call stability and output rigor require higher standards. Non-essential random generation parameters must be restricted to avoid output that conflicts with business rules.

## How to Set Configuration Values
The following configuration guidelines apply to FastGPT v4.17.0, formulated for model access and configuration needs in enrollment and student academic record management scenarios.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | Adapts to batch field splicing of multiple academic record and enrollment documents, avoiding context overflow that causes data truncation |
| `maxTokens` | 2000–3000 token | Meets the length requirements for outputs such as student academic record change approval and enrollment policy interpretation, covering complete business explanations and verification results |
| `quoteMaxToken` | 1500 token | Limits the length of referenced business documents, ensuring core academic record and enrollment fields are not truncated and verifying logic remains complete |
| `temperature` | 0.1–0.3 | Reduces random generation probability, ensuring output rigor for academic record verification and policy explanations, avoiding content that does not comply with enrollment rules |
| `AIPROXY_API_ENDPOINT` | Local or remote interface addresses configured based on the deployment environment | Adapts to proxy configuration requirements for multi-source model calls, supporting access to deployment methods such as local ollama and vllm |
| `toolChoice` | auto | Allows the model to independently choose whether to call tools for structured data verification, adapting to multi-dimensional verification needs for student academic record information |

## Three Common Configuration Errors
- The symptom is empty content returned when calling a local ollama model, with a status code of 200 but no valid output. The cause is that the ollama service fails to correctly bind the default port after restart, or the proxy address configured in FastGPT does not point to the actual running port of ollama.
- The symptom is that the image upload option cannot be opened when enabling the image model. The cause is that the `vision` configuration item is not enabled, or the currently used model does not support visual inference capabilities.
- The symptom is that after configuring `AIPROXY_API_ENDPOINT`, the local vllm model can be called normally but the ollama model fails. The cause is that the ollama API path does not correctly add the `/v1/chat/completions` suffix, or the proxy fails to correctly forward the ollama request path.

## How to Verify Successful Configuration
- Execute a model test request, input simulated form data including student academic record numbers and household registration addresses, and check whether the output includes associated verification results for the corresponding fields.
- View the model call log to confirm that the actual usage values of `maxContext` and `maxTokens` do not exceed the configured upper limits.
- Check whether the address and token of the proxy configuration item match the deployed model service, and verify the connectivity of multi-source model calls.
- Trigger a simulated request for batch student academic record change approval, and check whether the format of the output result complies with the field requirements of the business document.

The values provided are common starting points and should be evaluated using local test samples.
