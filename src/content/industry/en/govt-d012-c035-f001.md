# Internal Office and Employee Services for Pollution Discharge Permit Management: HTTP Interfaces and External Systems

## What this category of data includes
This category of data covers the entire post-issuance supervision process for pollution discharge units. Daily documents include pollution discharge permit application forms, implementation reports, self-monitoring plans, ledger records, change applications, and permit copies. Data sources are the national pollution discharge permit management information platform, enterprise environmental protection ledgers, online monitoring systems, and environmental statistics systems. The update frequency is quarterly. The data includes core fields such as permit limits, emission ledgers, and monitoring results, and mostly combines structured forms and unstructured text.

## What constraints do these characteristics impose on HTTP interfaces and external systems?
Data sources for this category are scattered across multiple business systems. HTTP interfaces must support multi-source authentication and data aggregation. The quarterly update frequency creates demand for batch data synchronization. Interfaces must support pagination pulling and breakpoint resumption mechanisms. Diverse document types require interfaces to support multi-format file transfer and verification. The accuracy of core data such as permit limits and emission ledgers directly affects supervision outcomes. Interfaces must include built-in parameter verification logic to prevent erroneous data from entering internal office workflows and reduce manual verification time.

| `Authorization` | `Bearer {platform key stored in environment variables}` | Complies with cross-system interface authentication specifications and avoids unauthorized access risks |
| Timeout | `300 seconds` | Adapts to synchronization processing requirements for batch pollution discharge ledgers and monitoring data |
| `responseData` | Return only core fields such as permit limits and ledger records | Reduces data parsing load for internal office systems |
| File upload size limit | `1000 MB` | Supports large-volume documents such as complete self-monitoring plans and implementation reports |
| `variables` | Configure quarterly data synchronization trigger rules | Matches the quarterly data update rhythm of this category |
| Request retry count | `3 times` | Addresses temporary fluctuations in cross-system interfaces and ensures synchronization stability |

## Three common misconfigurations
- Phenomenon: When calling an external system interface, parsed pollution discharge ledger JSON data contains a large number of extra backslashes. The target Flask service cannot parse the data normally. Cause: No escape cleaning is performed on the HTTP response's `responseData`. The original response is directly spliced into the request body, causing a JSON format error.
- Phenomenon: When obtaining an uploaded self-monitoring plan file via FastGPT, the returned relative path carries additional authentication token parameters. The file cannot be directly submitted to the internal office system for processing. Cause: No file path desensitization rules are configured. The temporary access path carries a token by default, which does not meet the unauthenticated access requirements of internal systems.
- Phenomenon: When passing the URL of a pollution monitoring site image in the conversation interface, the interface returns an error of access blocked or resource not found. Cause: No allowed domain name whitelist is configured in `variables`. Only domains accessible by internal systems are permitted. URLs from external or unauthorized domains are blocked.

## How to confirm the configuration is complete
- Call the predefined test interface to pull basic pollution discharge permit data. Check whether the configured authentication parameters are included in the request header, and confirm that cross-system access permissions are normal.
- Upload a standard self-monitoring plan document. Verify that the file upload process has no errors, and that the returned file path does not carry additional authentication identifiers.
- Construct test JSON data containing escape characters, submit it to the internal system interface, and check whether the parsing result of `responseData` conforms to the expected format.
- Configure a temporary quarterly data synchronization trigger rule. After triggering, verify whether the interface performs batch data pulling according to the preset rules, with no timeouts or interruptions.
