# Internal Office and Employee Services for Land Pre-examination and Planning Permit: Tool Calling and Plugins

## What the data for this category looks like
This category's data mainly comes from the national land spatial planning unified map, project approval and supervision platform, land use status database, and ecological protection redline data. Update frequency is irregular. Daily processed documents include land pre-examination and site selection opinions, construction land planning permits, construction engineering planning permits, redline diagrams, and planning conditions. Document structures include standardized fields such as land scale, control boundaries, and approval status. Some drawing-type documents contain coordinate-based non-text fields.

## What Constraints Do These Characteristics Impose on the Tool Calling and Plugins Link
The data characteristics of this category impose clear constraints on the tool calling and plugins link. Multi-source data with irregular updates requires tools to support on-demand pulling of the latest official data, avoiding the use of expired planning information. Diverse document types and field formats require plugins to adapt parsing rules for text-based approval documents and coordinate-based drawings. Errors in core approval links have serious consequences, so tool calling must be configured with verification and retry mechanisms. Precondition requirements for cross-departmental coordination require plugins to link with multiple official platform interfaces to obtain collaborative data.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | Auto | Adapt to the on-demand calling needs of multi-data source tools in land pre-examination scenarios, no manual specification of tool types required |
| `functionCall` | Enabled | Extract standardized fields from various approval documents, such as core parameters including land scale and redline coordinates |
| Tool call timeout duration | 600 seconds | Match the average time spent querying cross-departmental official platforms, avoid call failures due to response delays |
| Number of returns per single tool call | Top 3 entries | Focus on query results for core preconditions of approval, avoid redundant data interfering with the review process |
| Context window size | 8000–12000 token | Adapt to the integrated processing needs of multiple approval documents and planning data |

*This document is formulated based on the tool calling logic of FastGPT v4.17.0*

## Three Common Misconfigurations
- Symptom: No call result is displayed after tool calling, only empty context content is returned. Cause: The result storage logic of `functionCall` is not configured correctly, causing the call result to not be retained in the conversation context.
- Symptom: Coordinate fields cannot be extracted from redline diagram documents, and the parsing result is empty. Cause: Dedicated parsing rules are not configured for the special format of drawing-type documents, causing field matching to fail.
- Symptom: Tool calling triggers a timeout error, returning status code 504. Cause: The set timeout duration is shorter than the actual time spent querying cross-departmental platforms, not adapting to the data pulling delay characteristics of this category.

## How to Verify Correct Configuration
- Upload a single land pre-examination and site selection opinion document, trigger the tool calling process, and check whether core fields such as land scale and site selection range can be correctly extracted.
- Simulate a cross-departmental data query scenario, set the tool call timeout duration to 600 seconds, and confirm that the call is not interrupted due to timeout.
- View the tool call logs, confirm that `toolChoice` automatically triggers queries for the corresponding data sources, and no tool call omissions occur.
- Input test fields that do not conform to the planning data format, and verify whether the tool call result verification logic normally triggers prompts.

The provided values are common starting points and should be evaluated against individual deployment samples.
