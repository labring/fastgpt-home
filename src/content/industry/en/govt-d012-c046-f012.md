# Internal Office and Employee Services for Social Assistance and Minimum Living Allowance Review: Deployment and Upgrade

## What the Data for This Category Looks Like
The data for this category mainly comes from the low-income population dynamic monitoring platform, resident family economic status verification system, and cross-departmental shared data from public security, human resources and social security, medical insurance, housing and urban-rural development, tax, and other departments. The update frequency is monthly.

Daily processed documents include minimum living allowance application forms, family economic status verification reports, household survey forms, democratic review records, public notice materials, and assistance approval forms. Core fields focus on family income, property status, member relationships, and assistance eligibility. Most single documents combine structured forms and supporting materials.

## Constraints Imposed by These Characteristics on Deployment and Upgrade
The monthly updated cross-departmental shared data requires configuring scheduled synchronization rules during deployment to ensure the timeliness of review data.

The need to process multiple types of structured documents and supporting materials requires retaining compatibility with the original form parsing logic during the upgrade phase. This avoids interrupting daily office workflows.

The decentralized nature of cross-departmental data sources requires configuring multiple data source connection parameters during the deployment phase. This ensures the stability of data pulling.

The strict requirements for assistance review require strengthening data verification and backup mechanisms during deployment. This reduces the risk of incorrect or missed assistance guarantees.

Monthly batch data updates may cause server load fluctuations. This requires reserving reasonable resource quotas during deployment to avoid service freezes.

| `FILE_TOKEN_KEY` | `Calibrate based on actual testing` | Generates temporary tokens for image access. Must ensure the token validity period matches the duration of the review process |

## Three Common Configuration Mistakes
- Symptom: Docker containers restart continuously and cannot start services normally. Cause: The server is configured with 2 cores and 8 GB of memory. Insufficient memory resources are reserved for loading verification data and models, causing the process to be forcibly terminated by the system.
- Symptom: The Rerank model does not take effect normally. Search result sorting does not meet expectations. Cause: The deployment address of the rerank model is not specified in the configuration, or the model is not connected to the FastGPT retrieval link.
- Symptom: Image URLs configured in the knowledge base cannot be displayed normally in conversations. Cause: The `FILE_TOKEN_KEY` for generating temporary access tokens is not configured, or the front-end domain name `FE_DOMAIN` is not correctly bound to the image storage address. This causes the browser to fail to load image resources.

## How to Confirm the Configuration Is Complete
- Run the database connection verification script to verify the validity of the connections configured via `MONGODB_URI` and `PG_URL`.
- Manually trigger a data synchronization task to confirm that cross-departmental shared data can be pulled according to the configured scheduling logic.
- Upload a standard minimum living allowance application form to confirm that the parsed fields match the structure of the business form.
- Configure the storage address and access token for test images to verify that image resources can be loaded normally in conversations.
