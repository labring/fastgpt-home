# Internal Office and Employee Services for Legality Review of Regulatory Documents: HTTP APIs and External Systems

## What This Category of Data Looks Like
Data for this category primarily comes from the regulatory and rule repository, higher-level law database, departmental policy document repository, and administrative regulatory document filing system, with updates occurring irregularly. Commonly processed documents include draft regulatory documents, drafting explanations, legality review opinions, summaries of solicited comments, and filing reports. Drafts include article content and drafting background. Review opinions include review points and modification suggestions. Each document must be linked to corresponding higher-level legal basis and departmental authority documents.

## How These Characteristics Create Constraints for HTTP APIs and External Systems
The diversity of data sources requires HTTP APIs to support dynamic configuration of data source addresses and authentication methods to meet the call requirements of different regulatory repositories. The complexity of document types requires APIs to pass classification identifiers for different documents via `variables` to distinguish processing logic for draft regulatory documents, legality review opinions, and other types. The irregular update frequency requires APIs to support on-demand triggering of data pulling to adapt to temporary document update needs. The feature of long content per single document requires APIs to support large payload transmission, while also supporting parameter passing for linking higher-level laws and authority basis documents. Additionally, the feature of severe consequences from errors requires APIs to return detailed `responseData` to facilitate locating error points in legality review.

## How to Set Configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {custom API key}` | Complies with general HTTP API authentication specifications and meets identity verification requirements of external systems |
| `variables` | `{"doc_category": "draft regulatory document", "data_source": "regulatory and rule repository"}` | Passes document classification and source identifiers to distinguish processing logic for different types of review tasks |
| `responseData` | Includes review results, error details, and linked basis documents | Returns complete review information to facilitate subsequent filing, archiving, and issue localization |
| Timeout Setting | 600 seconds | Legality review requires comparing multiple higher-level laws and authority basis documents, which takes a long time; this avoids process interruption |
| Maximum Characters per Request | 8000 characters | Adapts to the content length of a single review document to avoid transmission failure caused by overly long request bodies |
| FastGPT Version | FastGPT v4.17.0 | This version optimizes external interface parameter passing and error capture mechanisms |

## Three Common Configuration Mistakes
- Symptom: The API returns the `messages is empty` error. Cause: The `variables` parameter for document classification and linked basis documents required for review was not passed, so the API cannot recognize valid review task types.
- Symptom: The API request times out and returns a 504 status code. Cause: The timeout setting was not adjusted to 600 seconds; the multi-regulatory document comparison process for legality review was interrupted before completion.
- Symptom: The returned review results lack linked regulatory basis documents. Cause: The return fields of `responseData` were not configured correctly, and detailed content of higher-level laws and authority basis documents was not specified to be returned.

## How to Confirm the Configuration Is Correct
- Call the test API to check if the `Authorization` parameter is carried correctly. API logs can be viewed to confirm if authentication information matches the preset value.
- View the `responseData` returned by the API to confirm if it includes review results, error details, and linked regulatory basis documents. Adjust return fields based on review requirements.
- Submit a test draft regulatory document to check if the API processing duration meets expectations. Adjust the timeout setting based on actual time spent.
- Verify that the parameters passed via `variables` match the classification and source of the test document, to ensure the API correctly recognizes the task type.
