# Internal Office and Employee Services for Flood Control, Disaster Prevention and Emergency Duty: Workflow Orchestration

## What Data for This Category Looks Like
Data for this category primarily comes from meteorological warning systems, hydrological monitoring systems, emergency command platforms, grassroots disaster reporting systems, and video surveillance. Daily processed documents include duty logs, warning notices, consultation minutes, rapid disaster reports, emergency response plans, and material allocation slips. Data updates occur daily. Document fields cover duty period, reporter, danger location, water level value, rainfall value, number of affected people, and other items. Some fields have fixed units: water level is measured in meters, rainfall in millimeters.

## What Constraints These Characteristics Impose on Workflow Orchestration
Multi-source data access requirements mandate configuring multiple cross-system pull nodes in the workflow to ensure complete synchronization of data from all sources. Fixed field and unit requirements require predefined standardized `variables` in the workflow to avoid chaotic data formats. The daily data update rhythm dictates that the workflow trigger on a fixed schedule, preventing invalid starts. High-frequency cross-department scheduling needs require the workflow to support parameter transfer between nodes and cross-workflow calls, ensuring collaborative efficiency of emergency response. The serious consequences of errors require the workflow to include failure retry and verification links to prevent process interruptions from affecting emergency response.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Variable definition | Configure fields from duty logs and rapid disaster reports, including duty period, danger location, water level value in `variables` | Matches the daily document structure of this category, unifies data formats |
| Single database pull upper limit | Top 10 hydrological monitoring data | Avoids data overload on a single node, adapts to multi-source data processing volume |
| Node trigger rule | Trigger after data update is complete | Corresponds to the daily data update rhythm, ensures complete data when the workflow starts |
| Cross-workflow call parameters | Pass the top 5 core pieces of data from rapid disaster reports | Adapts the reasonable data volume that needs to be shared across multiple nodes during emergency response |
| User selection node configuration | Retain the options "Confirm danger level" and "Confirm material allocation quantity" | Matches the conventional process of consultation and decision-making, simplifies manual operations |
| Failure retry configuration | Retry 2 times after failure, 60-second interval | Addresses temporary faults in multi-source system calls, ensures process progression |

This configuration is based on FastGPT v4.17.0.

## Three Common Misconfigurations
- Phenomenon: After workflow A calls workflow B, the running status of the [User Selection] node in B shows pending submission, and subsequent nodes do not start. Reason: No automatic submission trigger condition is configured for the user selection node, or the start signal of subsequent nodes is not bound.
- Phenomenon: When trying to set the AI model output to an empty value via the variable update node, the target field still retains the original content. Reason: The "Override empty values" option of the variable update node is not checked, or the target field is not correctly bound.
- Phenomenon: When orchestrating a database query node, the number of returned disaster data entries is much more or less than expected. Reason: No reasonable query filter conditions are configured, or the field format of disaster data in the database is not matched.

## How to Confirm Configuration Is Complete
- Trigger the workflow, check the running logs of each node, confirm that data is pulled successfully and fields match the predefined `variables`.
- Call the cross-workflow node, verify that the passed rapid disaster report data is complete and conforms to the preset format requirements.
- Simulate a user selection operation, confirm that subsequent nodes after the [User Selection] node start and execute normally.
- Test passing the `data` variable via URL parameters, confirm that the global variable correctly receives the incoming parameter value.
