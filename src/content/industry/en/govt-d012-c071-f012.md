# Internal Office and Employee Services for Power Generation Groups: Deployment and Upgrade

## What the data for this use case looks like
Data for internal office and employee services at power generation groups comes primarily from internal OA systems, employee service ticket platforms, equipment repair management systems, and attendance and compensation modules.
Data is updated at three intervals: real-time, daily, and periodic.
Real-time updates include ticket submission and equipment repair responses.
Daily updates include attendance statistics and compensation calculations.
Periodic updates include monthly equipment inspection records.
A single document typically includes fields such as ticket ID, submitter department, issue category, associated equipment number, processing progress, and response duration.
Field types include strings, enumerations, and numeric values. Units include seconds, count, identification numbers, and similar.

## Constraints Imposed by These Characteristics During Deployment and Upgrade
This configuration specification is based on FastGPT v4.17.0.
The combination of real-time performance and batch processing characteristics of internal office data for power generation groups requires database connections to support mixed high-concurrency short and long connections. This avoids blocking real-time ticket requests.
The long single-document length of batch monthly inspection documents has clear capacity requirements for vector embedding and storage.
The requirement for exact matching of associated equipment numbers requires retrieval configurations to balance exact recall and semantic recall.
Rolling upgrade or gray release strategies must be used during upgrades. This avoids interrupting real-time ticket processing processes.
Ticket and equipment association data must be backed up in advance. This prevents data loss during upgrades.

## How to Set the Configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 800–1200 connections | Multiple concurrent requests such as real-time tickets and equipment repairs exist in internal office work for power generation groups. This parameter controls the maximum number of database connections to adapt to high-concurrency scenarios. |
| `MONGODB_URI` | mongodb://internal-group-mongo:27017/oa_data?authSource=admin | Most internal office tickets and documents are unstructured data. MongoDB adapts to such storage requirements, and a dedicated database instance deployed within the group must be used. |
| `STORAGE_S3_ENDPOINT` | http://internal-oss:9000 | Office data includes large files such as equipment inspection photos and ticket attachments. A private storage service deployed within the group must be used to ensure data compliance. |
| `REDIS_URL` | redis://internal-group-redis:6379/1 | Used to cache real-time ticket status and employee permission information to reduce database query pressure and adapt to high-frequency access scenarios. |
| `ROOT_KEY` | Generated in accordance with the group's internal key management specifications | Used for platform administrator permission verification, must comply with the group's information security requirements, and default keys are prohibited. |

## Three Common Misconfigurations
- An error occurs when running the initialization script after upgrading the container, prompting "database connection limit exceeded" or "connection timeout". The cause is that `DB_MAX_LINK` is not configured to adapt to the connection limit of the group's internal database, resulting in the initialization script failing to establish sufficient connections.
- Calling external retrieval tools fails to return valid results, and background logs show "connection reset" or "resource not found" errors. The cause is that `STORAGE_S3_ENDPOINT` is not configured to the storage address accessible within the group, resulting in failure to load local attachment data during retrieval, or `REDIS_URL` is not correctly configured to cache retrieval request status.
- After upgrading, existing knowledge base content cannot be retrieved. The number of interface search results is 0, and the knowledge base list displays normally. The cause is that the authentication parameters of `MONGODB_URI` were not synchronized during the upgrade, resulting in failure to read the document metadata of the original knowledge base.

## How to Confirm the Configuration is Valid
- Run the initialization script, check that the console output has no errors related to database connections or storage service connections, to confirm that the configuration items have taken effect.
- Submit a test ticket, check that the system can normally store and associate the corresponding equipment number, to confirm that the database and storage configurations are normal.
- Call the external retrieval tool, check that the returned results include local attachments and knowledge base content, to confirm that the retrieval configuration complies with requirements.
- Log in to the administrator backend, verify that the administrator permission verification process works normally, to confirm that the security configuration has taken effect.
