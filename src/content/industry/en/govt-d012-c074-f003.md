# Internal Office and Employee Services for State-owned Asset Management Companies: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
The internal office and employee service data for state-owned asset management companies primarily comes from internal OA systems, financial ledgers, asset registration systems, and employee attendance and permission databases. Data updates follow a fixed cadence: asset status is synchronized daily, while employee permissions and process configurations are updated weekly. The document structure includes fields such as asset number, using department, purchase date, maintenance records, employee ID, job level, and approval process nodes. Units include yuan, units, person-times, days, and similar standard units.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
The data includes many fields across three core categories: assets, employees, and processes. Prompts for multi-turn dialogue must clearly define query scope to prevent the model from confusing irrelevant information. Multi-turn conversation context must bind unique identifiers for employees and assets; otherwise, accurate return of targeted data is not possible. Data updates occur at a relatively high frequency. Dialogue workflows should prioritize retrieving recent asset status and permission configurations. Old historical messages that exceed a set threshold must be appropriately truncated to avoid context overload that slows response speeds.

## How to set the configurations
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Generate a unique string identifier for each session | Used to bind historical messages for the same session, ensuring multi-turn dialogue contexts are not confused |
| `messages` | Concatenate the first 15–20 historical interaction messages in session order | Matches the interaction density of internal office dialogues, avoiding model response delays caused by overly long context |
| `variables` | Pass the current employee ID, affiliated department, and asset classification permissions | Retrieve asset data and office permission information associated with that employee |
| System prompt configuration | Clearly specify asset field scope and employee permission rules | Adapts to the data structure of state-owned asset management companies, filtering out irrelevant information |
| Maximum context length | Set to 8000–12000 characters | Adapts to the average length of internal office documents, ensuring critical asset and process information is not truncated |

## Three common misconfigurations
- Failing to include historical `messages` in the request body when calling `/api/v1/chat/completions`, only submitting the current user query. Returned results cannot be linked to historical dialogue, and "no relevant context found" errors may appear in some scenarios. This occurs because historical interaction messages are not concatenated in session order, and context association information is not retained.
- Not binding a unique `chatId` for each independent session, instead reusing the global default session ID. This causes dialogue contexts from different employees and processes to overlap. This occurs because a dedicated identifier is not generated for each session, and the need for session isolation is ignored.
- Using a universal global key to initiate cross-application dialogue, without isolating sessions from different applications via `chatId`. This leads to dialogue contexts from application A being accessible to application B. This occurs because `chatId` is not bound to the application ID, and session permission isolation is not implemented for the global key.

## How to confirm the configuration is correct
- Initiate a test dialogue that includes historical asset queries, and check if returned results link to previously mentioned asset numbers and approval processes.
- Review session logs to confirm each independent test session generates a unique `chatId`, with no duplicates or reuse.
- Pass the test employee’s ID and department, and check if returned asset data aligns with that employee’s permission scope, with no cross-permission information included.
- Call the dialogue interfaces of two different applications, and confirm their respective dialogue contexts are not accessible to each other, ensuring data isolation works properly.
