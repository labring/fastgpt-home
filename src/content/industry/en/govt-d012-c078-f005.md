# Internal Office and Employee Services for Urban Water Utilities: Tool Calling and Plugins

## What the data for this category looks like
The internal office data for urban water utilities mainly comes from pipe network monitoring equipment, water meter metering systems, water quality testing laboratories, and water utility dispatching platforms. Data update frequencies cover multiple levels: real-time monitoring data such as pipe network pressure and flow is updated at the minute level, water meter reading data is updated daily, and water quality testing batch data is updated immediately after sampling is completed. The document structure includes fields such as site ID, monitoring time, pressure value (unit kPa), flow (unit m³/h), pH value (dimensionless), turbidity (unit NTU), water meter number, and meter reading (unit m³). Minor differences in field names and units exist across different data sources.

## What Constraints These Characteristics Impose on Tool Calling and Plugins
Minute-level updates for real-time monitoring data require tool calling response times to stay within a reasonable range, otherwise real-time pipe network dispatching and anomaly alerts cannot be supported. Multi-source heterogeneous data field and unit differences require plugins to include built-in field mapping and unit conversion logic to avoid parsing failures due to format mismatches. Large single pull volumes for batch meter reading and water quality testing data require limiting the number of single return entries for tool calls to avoid interface timeouts or excessive returned data. Different business scenarios correspond to different data subsets, so filter conditions must be specified via plugin parameters to ensure call results match the specific needs of current internal office work.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapts to FastGPT v4.17.0 tool calling logic, reduces manual configuration workload |
| `functionCall` | No more than 800 data entries returned per single call | Matches the single pull volume of water utility monitoring data, avoids interface timeouts |
| Tool call timeout setting | 600 seconds | Covers the pull and processing duration of batch water quality testing data |
| Tool result sorting | Sort by monitoring time in descending order | Matches the requirement to view the latest data first in water utility dispatching scenarios |
| Tool parameter validation | Enable field format validation | Avoid call failures caused by unit mismatches or missing fields |

## Three Common Mistakes
- A 400 error is returned when a tool is called in a workflow. Investigation shows that required fields for water utility data (such as site ID) are missing from the request parameters. The cause is that required parameter validation rules are not preset in the plugin configuration, resulting in illegal requests being intercepted by the interface.
- An error occurs when calling a tool with a non-qwen model, and the returned result is empty. The cause is that some models do not support structured data parsing formats for water utility scenarios, and fail to correctly map fields and units.
- Concurrent calls occur in the tool selection workflow, leading to multiple pulls of monitoring data for the same site. The cause is that the number of concurrent tool calls is not limited, and a locking mechanism for single calls of a single tool is not configured.

## How to Confirm Proper Configuration
- Send a simulated tool call request, pass typical parameters for water utility scenarios (such as specifying a site ID and monitoring time range), and verify that the fields and units of the returned data conform to preset rules.
- View the tool call log to confirm that the value of the `toolChoice` parameter matches the configured setting, with no incorrect tool selection.
- Test the batch data pull scenario, verify that the number of data entries returned per single call does not exceed the preset upper limit, and no timeout errors occur.
- Adjust the concurrent parameters for tool calls, confirm that only one tool call request is allowed to be initiated at the same time to avoid concurrent conflicts.
