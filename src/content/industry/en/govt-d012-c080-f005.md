# Internal Office Work and Employee Services for Urban Investment Platforms: Tool Calling and Plugins

## What This Category of Data Looks Like
The internal office data of urban investment platforms mainly comes from OA systems, project management platforms, financial accounting systems, and employee attendance systems.
Data update rhythms fall into three categories: triggered by daily operations (such as attendance submission, progress reporting), daily batch synchronization of financial data, and weekly updates of employee performance data.
Documents primarily use structured tables, which include fields such as employee ID, department, position, project number, project name, budget amount, and approval status.
Field units include yuan, ten thousand yuan, person-times, working days, and others. Some fields use fixed enumeration values.

## Constraints Imposed on Tool Calling and Plugins
High proportions of structured data require clear field mapping rules during tool calls. This avoids result deviations caused by fuzzy matching.
Wide variation in data update rhythms means some scenarios need real-time calling support, while others require scheduled synchronization plugin configuration.
Many enumeration fields mean tool call parameters must limit the range of optional values, to reduce invalid input.
Large single-table data volumes require tool calls to support paged query configuration. This prevents excessive system load from returning too much data.
Employee data involves privacy permissions, so tool calls must bind access permission checks for departments or positions.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | Specified as `["query_employee", "query_project", "query_finance"]` | Tool calls for internal office work of urban investment platforms are concentrated in three scenarios: employee, project, and finance. Limiting the tool range improves calling accuracy |
| `functionCall` | Enable strict mode | Tool calls for urban investment platforms require strict matching of parameter formats. Enabling strict mode reduces parameter errors |
| Database connection timeout | `300 seconds` | Queries for urban investment financial data usually involve multi-table joins. A longer timeout prevents connection interruptions caused by large data volumes |
| Plugin call retry count | `2 times` | Internal office networks may experience occasional fluctuations. Limited retries reduce call failures caused by temporary network issues |
| Parameter validation switch | Enable | Most fields in urban investment platform data are enumerations or have fixed formats. Enabling validation filters invalid parameters and reduces erroneous calls |
| Batch query page size | `First 20 entries` | Single calls in internal office scenarios do not need to return too much data. Limiting the number of entries reduces data transmission load |
| Deployment version | v4.17.0 and above | This version fixes compatibility issues with intranet plugin calls, and adapts to the intranet deployment environment of urban investment platforms |

## Three Common Misconfigurations
- Symptom: No output when calling a database via a tool, with the interface showing "Connection successful but no results returned". Cause: Intranet access permissions for the database are not configured. Internal databases of urban investment platforms are usually deployed in isolated intranets. Failing to add the IP whitelist of the FastGPT deployment node causes connection failures.
- Symptom: SQL syntax errors trigger when passing SQL statements via variables. The same SQL runs normally when executed manually. Cause: Variables are not escaped. The SQL syntax of urban investment databases has strict requirements for special characters. Unescaped variables break SQL statement structure.
- Symptom: "Corresponding tool not found" displays when calling a plugin in a workflow. Cause: The corresponding internal office interface is not registered on the plugin management page. Internal interfaces of urban investment platforms usually require custom plugin configuration. Unregistered interfaces cannot be identified or called by workflows.

## How to Verify Successful Configuration
- Enter the tool call test page, manually enter a valid employee ID, call the employee information query tool, and confirm returned fields match internal system values.
- After configuring the database connection, run the preset test query statement, and check that the number and units of returned results match expectations.
- Simulate passing SQL queries via variables, confirm correct results return and no syntax error prompts appear.
- View plugin call logs, confirm call parameters match the configured tool list, and no unauthorized call records exist.
