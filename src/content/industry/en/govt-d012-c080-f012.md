# Internal Office and Employee Services for Urban Construction Investment Platforms: Deployment and Upgrade

## What the data for this category looks like
Data for internal office and employee services of urban construction investment platforms comes from four primary sources: internal OA systems, financial reimbursement platforms, project management ledgers, and employee attendance systems.
Update rhythms differ across sources. Employee attendance data syncs in real time on workdays. Reimbursement data updates daily. Project ledgers receive full updates each month.
Data falls into two categories. Structured data includes fields such as employee ID, project number, attendance duration, and reimbursement amount. Project numbers use a fixed format of "region code + year + project serial number". Attendance duration is measured in minutes.
Unstructured data includes office documents, project report materials, and similar content, stored in PDF and Word formats.

## What constraints these characteristics impose on deployment and upgrade
The data characteristics of urban construction investment platforms create multiple constraints for deployment and upgrade processes.
First, the coexistence of structured and unstructured data requires deploying both relational and document databases to support storage needs for different data types.
Second, varied update frequencies require upgrade scripts to support incremental synchronization logic. This prevents overloading internal systems caused by full synchronization operations.
Third, most internal systems of urban construction investment platforms run on government intranets, with strict compliance rules prohibiting data from leaving the intranet. Deployment must therefore include dedicated intranet access paths and storage endpoints.
Fourth, unified internal coding rules require permission configurations to be strongly bound to fields like employee ID and project number. Existing permission mapping relationships must not be broken during upgrades.
FastGPT v4.17.0’s deployment tool supports intranet environment configuration, and can directly align with these constraints.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | 10–20 connections | High concurrent volume of internal office data for urban construction investment platforms requires sufficient connections to support simultaneous access from multiple systems |
| `MONGODB_URI` | Replica set connection address deployed on government intranet | Stores unstructured office documents and project ledgers, complies with intranet data storage compliance requirements |
| `PG_URL` | PostgreSQL connection address deployed on government intranet | Stores structured employee information, attendance and reimbursement data, aligns with internal structured data management practices of urban construction investment platforms |
| `FE_DOMAIN` | Government intranet domain name or government cloud load balancer address | Ensures internal employees access the frontend interface via the government intranet, avoids public network exposure risks |
| `STORAGE_S3_ENDPOINT` | Government cloud object storage intranet endpoint | Stores office attachments and project materials, meets data non-exfiltration compliance requirements |
| `ROOT_KEY` | Random key generated according to internal permission rules of the urban construction investment platform | Initializes system administrator permissions, aligns with internal account management systems |

## Three common mistakes
- A `POST /api/admin/initv4818 404` error occurs when running the upgrade script. The cause is incorrect configuration of `FE_DOMAIN` and intranet access path, leading to the upgrade interface failing to be called normally via the internal network.
- Initial login username and password cannot be queried after deployment. The cause is failure to correctly generate and write `ROOT_KEY` to the configuration file, leading to the system failing to initialize the administrator account.
- DingTalk robot deployment fails with message receiving address verification failure. The cause is failure to configure `FE_DOMAIN` as an address accessible via the government intranet, and failure to disable SSL certificate verification as prompted (if no valid SSL certificate is configured).

## How to confirm configurations are correct
- Run database connection test commands to verify that storage services corresponding to `PG_URL`, `MONGODB_URI` and `REDIS_URL` can be connected normally.
- Access the configured `FE_DOMAIN` address, confirm that the frontend interface loads normally and no permission intercept prompts appear.
- Upload an internal office document of the urban construction investment platform, verify that the storage service corresponding to `STORAGE_S3_ENDPOINT` can receive and store files normally.
- Run the pre-check command of the upgrade script, confirm that the interface path can be called normally with no 404-level errors.
