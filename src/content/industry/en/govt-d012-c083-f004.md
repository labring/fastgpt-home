# Internal Office and Employee Services for Infrastructure Construction: Workflow Orchestration

## What the data for this category looks like
Internal office data for infrastructure construction primarily originates from construction log systems, personnel attendance systems, material management ledgers, and progress report systems. Data update cycles cover real-time (clock-in records), daily (construction logs), weekly (material inventory checks), and monthly (progress summaries). Each document structure is split into two parts: structured fields and free text. Structured fields include employee ID, material code, working hours, inventory quantity, and more, with units of hours, tons, and cubic meters respectively. Free text includes daily operation abnormality descriptions and safety inspection details. Most data storage formats are CSV, PDF scans, and structured database tables.

## What constraints these characteristics impose on the "workflow orchestration" link
Construction-related data sources are scattered across multiple internal systems. Workflows must support pulling data across data sources to avoid errors caused by manual copy-pasting. Data update frequencies vary greatly: real-time clock-in data needs to be synchronized every hour, while monthly summary data only needs to be updated once a month. Workflow trigger timing must adapt to the update rhythms of different data sources. Some data is stored as PDF scans, so workflows must include built-in OCR parsing components to extract valid fields. Field naming differs across systems. For example, "working hours" in construction logs and "attendance hours" in attendance systems refer to the same metric. Unified field mapping rules must be configured in the workflow to avoid data confusion.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Timing | Trigger on a daily schedule, 24-hour interval | Adapts to the daily update rhythm of construction logs and material ledgers |
| Variable Binding | Bind employee ID and material code fields from `variables` | Unifies data identifiers within the workflow to avoid field name conflicts |
| Data Source Pull Range | Pull construction records from the last 7 days | Covers the latest data required for daily office work while avoiding redundancy |
| Node Execution Order | Sort by `nodeId` in ascending order | Ensures workflow nodes execute in sequence according to preset logic |
| Timeout Setting | 300 seconds | Matches the average response time for pulling data across three or more internal systems |
| Retry Strategy | Retry up to 2 times | Prevents repeated requests from occupying internal system resources |

## Three common mistakes
- The knowledge base content extracted after the workflow runs is empty. This occurs because the structured fields of the knowledge base are not bound to the corresponding fields in the workflow's `variables`.
- When debugging workflows in FastGPT v4.17.0, a configuration error pop-up appears. This occurs because the node trigger logic corresponding to `nodeId` is not correctly configured.
- The workflow's unit conversion results do not meet expectations. This occurs because unit conversion parameters are not specified in the mapping rules, and the units of the original data are used directly for data transfer.

## How to confirm the configuration is complete
- Manually trigger the workflow and check if there are records of successful data source pulls in the run logs.
- Check the `variables` binding fields of the workflow to confirm they exactly match the field names in internal systems.
- Simulate a scenario where a data source is temporarily unavailable to verify whether the workflow's retry mechanism takes effect as configured.
- Compare the workflow output results with the original construction data to confirm that field mapping and unit conversion comply with preset rules.
