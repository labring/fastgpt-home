# Internal Office and Employee Services for Infrastructure Construction: Forms and Interactions

## What data for this category looks like
Internal office data for infrastructure construction primarily comes from on-site job terminals, labor management systems, material entry ledgers, and equipment operation and maintenance logs. Data is updated alongside project construction cycles, either synced per single job or daily. The document structure uses hierarchical forms, with fields including project unique identifiers, work team information, material specification parameters, acceptance status, work hour records, and more. Field units include cubic meters, machine shifts, person-times, square meters, and others. Some fields are linked to project-specific acceptance criteria, such as fixed field combinations for entry acceptance slips, labor attendance sheets, and equipment maintenance records.

## What constraints these characteristics impose on forms and interactions
The hierarchical structure of the data requires forms to support nested fields and groups, to adapt to specialized field combinations for different job scenarios. Specialized unit fields must pre-configure category-specific units such as cubic meters and machine shifts, to avoid manual input errors. The project unique identifier is a required pre-item, to ensure data is linked to the corresponding construction node. Forms in weak network environments must support offline staging, which automatically links to project ledgers after syncing, to prevent data loss. The acceptance status field must pre-configure fixed judgment options, aligned with acceptance rules in the backend ledgers.

## How to set the configuration
This document applies to FastGPT v4.17.0

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `formInput` | Configure as multi-nested field groups, bind project numbers, team names, and material parameters, pre-configure units such as cubic meters, machine shifts, and person-times, with a single text field limit of 1000 characters | Adapt to the hierarchical data structure of infrastructure construction forms, avoid manual input errors for units and field lengths |
| `userSelect` | Configure as a drop-down list for registered teams and material models, display up to 10 options | Match fast selection by on-site workers, reduce manual input errors |
| Timeout Setting | Configure a 600-second timeout threshold | Adapt to form submission during on-site network fluctuations, avoid timeout errors |
| Offline Staging | Enable offline staging, with a staging duration of 72 hours | Adapt to on-site weak network environments, store unsynced job data |
| Form Required Validation | Enable required fields for acceptance status and entry quantity | Ensure completeness of core job data |
| Variable Selection Configuration | Configure a single-choice option to skip knowledge base retrieval | Meet user needs for switching retrieval logic as needed |

## Three common misconfigurations
- An SSL connection error occurs during form submission, with a status code starting with SSL_ERROR_. The cause is an incorrectly configured form submission timeout threshold. In a weak on-site network environment, the request is terminated before completion, triggering an SSL verification exception.
- The user's choice to skip knowledge base retrieval does not take effect; knowledge base retrieval is still triggered after submission. The cause is that the selection result from `userSelect` is not correctly passed to the retrieval trigger logic, causing the switch to not function properly.
- An error occurs when configuring automatic knowledge base switching, with the prompt common:core.chat. The cause is that the knowledge base name selected via `userSelect` is not correctly bound to the system's internal knowledge base configuration, leading to a retrieval target matching failure.

## How to confirm the configuration is complete
- Enter the form configuration page, check that the field groups and pre-configured units in `formInput` align with the category-specific data structure.
- Simulate a weak network environment to submit a form, confirm that the offline staging function works normally, and that data is automatically synced after reconnecting to the network.
- Trigger a selection in `userSelect`, verify that the selection result is correctly passed to the subsequent retrieval logic.
- Intentionally leave core fields such as acceptance status and entry quantity blank, confirm that a required validation prompt is triggered during submission.
