# Internal Office and Employee Services for Construction Machinery: Forms and Interactions

## What the data for this category looks like
Internal office data for construction machinery comes from three main sources: real-time operating parameters collected by equipment sensors, maintenance and procurement records stored in ERP systems, and employee attendance logs synced from on-site terminals. Update frequencies vary significantly: sensor data updates in real time at millisecond intervals, maintenance records are synced after each individual job, and attendance logs are updated daily. Individual data entries include fields such as device ID, operating duration, fault code, responsible person, and attendance duration. Most field units are hours, counts, and dates, while some sensor data uses floating-point numeric values.

## What constraints these characteristics impose on the forms and interactions link
Device IDs follow a fixed prefix plus numeric format, so form format validation rules must be configured to prevent invalid input. Submissions of real-time operating parameters require low latency to avoid disrupting on-site workflow handoffs. Form content varies widely across scenarios such as maintenance, attendance, and equipment logs, so fields should be grouped by scenario to reduce filling complexity. On-site mechanical noise interferes with speech recognition accuracy, so noise reduction configuration must be adapted. Form calls in nested workflows must match the current context, otherwise interaction errors will occur.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `formInput` trigger rule | Bind to current workflow context variables | Adapt to form call scenarios for single and nested workflows |
| `userSelect` optional scope | Restrict to internal employee ID list | Match the employee system and permission rules of construction machinery enterprises |
| Form submission latency threshold | 300–800 milliseconds | Meet the fast submission requirements of real-time equipment data |
| Speech input noise reduction level | Medium level | Offset noise interference from on-site mechanical operations |
| Form field grouping | Classify by maintenance/attendance/equipment logs | Match filling logic across multiple scenarios |
| Production environment version lock | FastGPT v4.17.0 | Ensure functional stability and avoid unnecessary updates |

## Three common mistakes
- Phenomenon: The `formInput` node dialog box nested in another workflow continues to display, while the status is normal within a single workflow. Cause: Current workflow context variables are not bound, and the trigger rule is not limited to the current workflow context.
- Phenomenon: After deployment in the production environment, the number of optional configuration items for prompts and global variables decreases, which is inconsistent with the interface display of version 4.8.10. Cause: After upgrading from version 4.8.10 to 4.9.10, the configuration entry location was adjusted, and the operation path was not updated synchronously.
- Phenomenon: After enabling the speech recognition function, the browser pops up a prompt that speech input is not supported. Cause: Microphone access permission is not granted to the browser, or Web Speech API support is not enabled in the current environment.

## How to confirm the configuration is correct
- Test the `formInput` node in single and nested workflows to confirm that the dialog box display status meets expectations.
- Fill in the device ID field with a fixed format to confirm that the format validation rule takes effect and invalid inputs cannot be submitted.
- Test the speech input function in an environment simulating mechanical noise to confirm that the recognition result meets expectations.
- Check the production environment version lock status to confirm that no automatic update to an unstable version has occurred.
