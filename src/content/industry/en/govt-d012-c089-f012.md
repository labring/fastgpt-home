# Internal Office and Employee Services for Construction Machinery: Deployment and Upgrade

## What the data for this category looks like
Construction machinery-related data primarily originates from equipment operation sensor logs, offline maintenance work order systems, internal office documents, and employee attendance systems. Equipment operation logs are updated per minute or hour. Maintenance work orders are synced in real time as processing progresses. Office documents and employee information are updated on a fixed daily schedule or synced as needed.

The data document structure includes three core field categories: equipment ledger (including equipment number, model, operating parameters with units such as revolutions per minute, degrees Celsius, etc.), work order records (including work order ID, associated equipment, processing duration), and employee files (including employee ID, position, scheduling information). All fields are bound with clear business attributes and units of measurement.

## What constraints these characteristics impose during deployment and upgrade
High-frequency writes from equipment operation logs create demands for database storage performance. During deployment, adjust the connection pool parameters corresponding to `MONGODB_URI` to adapt to high-concurrency writes. The strong association between maintenance work orders and equipment ledgers requires configuring database association indexes during deployment to avoid increased query delays after upgrade.

The daily batch synchronization requirement for employee information means pre-setting the trigger interval for scheduled tasks during deployment. Compatibility with the original synchronization rules must be maintained during the upgrade process. Additionally, the unit binding feature of equipment parameters requires configuring field verification rules during data import and processing to prevent unit mismatch errors after upgrade.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| `DB_MAX_LINK` | `100–150` | Adapts to concurrent connection demands from high-frequency construction machinery equipment logs, prevents connection exhaustion from disrupting business operations |
| `MONGODB_URI` | `mongodb://admin:pass@host:27017/engineering_db?maxPoolSize=120` | Matches high-frequency write storage for equipment log data, balances connection count and memory usage |
| `PG_URL` | `postgresql://erp_user:erp_pass@host:5432/erp_db?statement_timeout=60000` | Handles associated queries for maintenance work orders, sets a timeout to avoid long transactions blocking business processes |
| `REDIS_URL` | `redis://:redis_pass@host:6379/0?maxmemory-policy=allkeys-lru` | Caches employee scheduling information and equipment status data, prevents service interruptions caused by cache overflow |
| `FE_DOMAIN` | `https://internal-engineering.example.com` | Matches the domain name of the internal office system, ensures normal page jump and file download functions |
| `STORAGE_S3_ENDPOINT` | Configured according to the actual address of the enterprise's internal object storage | Adapts to large-capacity storage demands for construction machinery documents and logs, ensures data persistence |

## Three common mistakes
- The symptom is that workflow nodes run without output results, only prompting "no running results", and even simple function nodes cannot execute. This issue occurs more frequently when using FastGPT v4.17.0. The cause is incorrect configuration of `ROOT_KEY` permissions, or incorrect `REDIS_URL` connection parameters leading to cache failure, which prevents storage of workflow operation context.
- The symptom is failure to log in to the backend after Docker deployment, with a database connection failure. The cause is failure to modify the account passwords in `MONGODB_URI` or `PG_URL` as required, or insufficient database permissions to access the corresponding business database.
- The symptom is that after Nginx proxy, knowledge base original text download links cannot be accessed normally. The cause is failure to update `FE_DOMAIN` to the proxied domain name, resulting in the use of the internal original address when generating links, which cannot be accessed through the proxy path.

## How to confirm the configuration is correct
- Run the built-in database connectivity detection tool to verify whether the configurations of `MONGODB_URI`, `PG_URL`, and `REDIS_URL` can establish normal connections. Set the connection timeout threshold according to business concurrency demands.
- Upload a standard equipment ledger test document, check whether the parsed fields match the preset structure, and configure verification rules according to the field requirements of the data documents.
- Trigger a simple workflow test, check whether valid output is generated in the operation log, and confirm that the configurations of `ROOT_KEY` and `FILE_TOKEN_KEY` meet permission requirements.
- Access the configured `FE_DOMAIN`, test the page jump and file download functions of the internal office system, and confirm that the domain name configuration matches the proxy settings.
