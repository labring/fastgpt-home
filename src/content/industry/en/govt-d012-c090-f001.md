# Internal Office and Employee Services for Refined Oil Sales: HTTP Interfaces and External Systems

## What the Data for This Category Looks Like
The business data for refined oil sales primarily comes from gas station POS terminals, inventory management systems, employee attendance systems, and fuel card management platforms. Transactional data such as fueling transaction records is generated in real time. Inventory ledgers are updated after daily stocktakes. Employee scheduling and attendance data is synced on a calendar day basis. Individual business documents include fields such as fuel grade, fuel volume (liters), actual received amount (yuan), transaction time, employee ID, and fuel nozzle number. All fields are bound to clear business units, with no redundant empty fields.

## Constraints Imposed on HTTP Interfaces and External Systems by These Characteristics
The high-frequency generation of real-time transactional data requires interfaces to support low-latency calls, to avoid data synchronization delays impacting employee service response times. Fields bound to fixed business units require interface return data to be strictly tied to unit identifiers, to prevent cross-system parsing discrepancies. Daily updated inventory and attendance data does not require high-frequency pulling, and a calendar-day sync trigger can be configured. In scenarios with multiple system integrations, a unified authentication parameter format is required, to ensure interface calls for all business modules complete identity verification via `Authorization`. This configuration applies to FastGPT v4.17.0.

## How to Set the Configuration
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer token obtained from the enterprise internal API gateway, valid for 7200 seconds | Complies with the authentication specifications of refined oil sales systems, ensuring secure interface calls |
| `variables` | Bound to fuel card number, employee ID, and fuel grade, with a value range of 1-15 | Matches the personalized parameter requirements of employee services and business queries |
| `responseData` | Parsed in the format `{transactionTime: string, fuelVolume: number, unit: string}` | Matches the field structure and unit requirements of refined oil sales data |
| Interface timeout period | 60-120 seconds | Adapts to the pull and response rhythm of real-time transaction data, avoiding timeout interruptions |
| Interface call frequency | Configured per business scenario: 1 call/second for real-time transaction interfaces, 1 call/day for inventory interfaces | Differentiates business data update rhythms, avoiding resource waste and interface rate limiting |

## Three Common Mistakes
- Calling the employee scheduling interface returns a 404 status code, caused by failing to carry a valid `Authorization` parameter, resulting in identity verification failure.
- Calling the inventory sync interface returns a 500 status code, caused by the `responseData` configuration not matching the field structure of refined oil sales data, resulting in parsing exceptions.
- Querying fuel card balance returns an empty result, caused by failing to bind the correct fuel card number parameter in `variables`, resulting in the interface being unable to match target business data.

## How to Confirm the Configuration Is Correct
- Call the test interface, check if the returned data fields and units match those of the business system, and adjust the `responseData` configuration until they match.
- Submit a test request with business parameters, verify that the parameters bound in `variables` are correctly included in the interface request.
- View the interface call logs, confirm that the `Authorization` parameter has been correctly carried, with no authentication failure records.
- Simulate peak business calls, observe the interface response duration, and adjust the timeout period configuration to meet business requirements.
