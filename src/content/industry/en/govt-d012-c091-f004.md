# Internal Office and Employee Services for General Contracting of Building Construction Projects: Workflow Orchestration

## What the data for this category looks like
The internal office data for general contracting of building construction projects mainly comes from project construction logs, labor attendance ledgers, material requisition documents, subcontract contracts, progress visa forms, and similar sources. The data update rhythm follows project node progress. Daily attendance and material requisition data are updated daily, while construction logs and visa forms are updated weekly or upon completion of individual project nodes. Most documents use structured fields, including project number, building number, construction team, material model, usage quantity, operation date, and other fields. Units include person, ton, square meter, day, and others. Some documents are attached with construction drawings, acceptance reports, and other attachments.

## What constraints these characteristics impose on workflow orchestration
The multi-type, phased data characteristics of general contracting of building construction projects require that workflows first support splitting branches by document type and construction phase, to avoid interference between different processes. Structured data fields need pre-configured validation rules to ensure that numerical fields such as team size and material usage comply with format requirements. Project processes have multiple parallel subtasks, such as material approval, attendance verification, and progress reporting that need to be carried out simultaneously. This requires workflows to support a limited number of parallel branches. Data must be archived by project number, and workflows must be configured with corresponding storage paths to facilitate subsequent traceability and query.

The following configurations are formulated based on FastGPT v4.17.0.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale for This Setting |
| --- | --- | --- |
| Trigger Mode | Triggered by project node events; scheduled trigger at 00:00 daily when no events occur | Building construction project processes progress according to construction nodes. Event triggering matches actual work rhythms, while scheduled triggering covers daily data synchronization that is not triggered manually |
| Variable Validation Rules | Validate that "labor team size" in `variables` is a positive integer, and "material usage" is a non-negative numerical value | Personnel and material data for building construction projects are both numerical fields, and pre-validation is required to prevent invalid data from entering the workflow |
| Branch Node Configuration | Split branches by the "construction phase" field, covering phases such as foundation, main structure, and decoration | Processes and documents vary significantly across different construction phases, and splitting by phase simplifies workflow logic |
| Node Timeout Setting | Timeout period of 1200 seconds for each approval-type node | Internal approval processes for building construction projects usually take a long time; this duration covers conventional approval links |
| Number of Parallel Branches | Maximum 3 parallel branches | Excessive parallel branches will occupy too many system resources; 3 branches balances process efficiency and resource usage |
| Result Storage Path | Archive to the corresponding folder by project number | Building construction project data needs unified management by project, and archiving by number facilitates subsequent query and traceability |

## Three common misconfigurations
- Text classification extraction node failure, with empty extraction results. The interface shows that the node output field is empty, and there is no clear error in the logs. No classification rules are configured for fields dedicated to building construction projects such as "visa form number" and "main material entry batch", resulting in failure to recognize target text.
- Parallel branches run without improved speed, or even with reduced speed. Workflow runtime is longer than single-branch runtime, and system resource usage is too high. The number of parallel branches exceeds the resource limit of the current deployment, and the number of simultaneously running branches is not restricted.
- Workflow loop enters the problem classification node. After the AI dialogue returns content, the workflow automatically returns to the initial problem classification node, and cannot complete the closed loop. No logic to jump to the end node is configured after the AI dialogue node, causing the workflow to repeatedly trigger the classification logic.

## How to confirm the configuration is complete
- Trigger a test workflow, and check whether each branch node jumps correctly according to the preset construction phase.
- View the validation results of the `variables` field, and confirm whether numerical fields such as "labor team size" and "material usage" have passed legality validation.
- Run the parallel branch workflow, and check whether the start time and end time of parallel tasks meet expectations.
- View the result storage path, and confirm that the documents output by the workflow have been archived to the corresponding location by project number.
