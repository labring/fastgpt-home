# Internal Office and Employee Services for Nuclear Power Operations: HTTP Interfaces and External Systems

## What this category of data looks like
Data for internal office and employee services in nuclear power operations primarily comes from enterprise OA systems, employee attendance terminals, safety training platforms, and equipment operation and maintenance ledger databases. Data update rhythms fall into three categories:
- Attendance check-in data is synced in real time
- Operation and maintenance ledgers are updated in batches every day at midnight
- Training assessment records are pushed immediately after a single training session is completed

A single data document includes five fields: employee ID, job code, operation time, associated equipment number, and operation type.
- Employee ID is an 8-digit numeric string
- Operation time uses the YYYY-MM-DD HH:MM:SS format
- Associated equipment number is a 12-character combination of uppercase letters and digits

## What constraints these characteristics impose on HTTP interfaces and external systems
The above data characteristics create multiple constraints for the HTTP interface link.
First, employee ID and equipment number have fixed format requirements. The interface must enforce matching corresponding regular expressions during request verification to prevent invalid data from entering the system.
Second, the difference in update rhythm between real-time attendance data and batch operation and maintenance data requires the interface to support both single data submission and batch data import request modes.
In addition, nuclear power operation data involves internal security compliance requirements. The `Authorization` parameter of the interface must use the Bearer token authentication method, and the token validity period must match the rotation cycle of data access permissions.

## How to set configurations
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `Authorization` | Bearer {custom token}, set token validity period to 7200 seconds | Matches the security compliance requirements of internal nuclear power operation data, limits token usage cycles, and reduces the risk of sensitive data leakage |
| `variables` | Pre-set employee ID regex `^[0-9]{8}$`, equipment number regex `^[A-Z0-9]{12}$` | Enforce field format verification for request data, filter invalid requests that do not comply with nuclear power operation data specifications |
| `responseData` | Only return status code and error information fields, do not return original request data | Complies with internal data confidentiality specifications, avoids carrying sensitive employee and equipment information in interface responses |
| Maximum data volume per single request | 500 items/request | Balances interface transmission load and processing efficiency of batch operation and maintenance data, prevents request timeouts caused by excessive data volume in a single request |
| Request timeout period | 300 seconds | Adapts to the time consumption requirements of batch data transmission, avoids request interruptions caused by large data volumes |
| Number of request retries | 3 times | Addresses temporary connection failures caused by network fluctuations, improves the stability of interface calls |

## Three common misconfigurations
- Phenomenon: The interface returns 400 Bad Request when called, and the request body contains employee ID or equipment number that does not meet format requirements. Cause: The field verification rules corresponding to `variables` are not configured, resulting in invalid format data being submitted.
- Phenomenon: 504 Gateway Timeout is returned when submitting operation and maintenance data in batches. Cause: The request timeout period is set too short, which does not adapt to the transmission time consumption of batch data.
- Phenomenon: The interface call returns 401 Unauthorized, and normal data acquisition or submission cannot be performed. Cause: The `Authorization` parameter does not use the Bearer token format, or the token has expired and has not been updated in time.

## How to confirm the configuration is correct
- Send a test request with correctly formatted data, check that the interface returns a 200 OK status code, confirm that the `Authorization` verification and field format verification have passed.
- Submit batch test data, check that the interface response time meets the preset timeout threshold requirements, confirm that the request load configuration is reasonable.
- View the interface logs, confirm that only the status code and error information are returned, and no sensitive data from the original request is carried, confirm that the `responseData` configuration is effective.
- Simulate a token expiration scenario, check that the interface returns 401 Unauthorized, confirm that the authorization verification rules are working properly.
