# Internal Office and Employee Services for Nuclear Power Operations: Deployment and Upgrade

## What the Data for This Category Looks Like
Data for internal office and employee services in nuclear power operations comes primarily from internal OA systems, team operation logs, safety training records, and employee attendance systems. Data update rhythms fall into three categories:
- Real-time: attendance checks, instant communication
- Daily: team daily reports, operation records
- Monthly: safety assessments, training summaries

Each individual data document includes employee ID, affiliated team, job type, operation duration, compliance check item ID, and completion status. Duration is measured in minutes, operation count is measured in times. No unified aggregate statistics field is configured.

## Constraints Imposed by These Characteristics During Deployment and Upgrade
The high concurrency of real-time attendance and instant communication data requires sufficient database connection pool configuration during deployment. This prevents connection exhaustion from concurrent requests.
Batch daily team reports and monthly assessment data require reasonable storage sharding and single-file size configurations. This prevents storage overflow during bulk imports.
Structured employee and operation fields require pre-built indexes. During upgrades, retain original data association relationships to avoid broken links between compliance check records and employee files.
Additionally, the sensitivity of nuclear power operation data requires enabling built-in data encryption configurations during deployment.

## How to Configure the Settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `200–300 connections` | Matches the concurrent request volume during nuclear power operation team shift handovers and daily inspections, meeting the concurrent connection requirements for real-time data |
| `MONGODB_URI` | `Cluster connection string with authentication parameters` | Stores sensitive data such as employee files and operation logs, requires enabling access authentication and cluster high availability |
| `REDIS_URL` | `Intranet connection address with 600-second cache expiration time` | Caches real-time attendance session data to reduce the frequency of repeated database queries |
| `STORAGE_S3_ENDPOINT` | `Intranet storage endpoint compliant with nuclear power data compliance requirements` | Stores operation logs and training records to ensure data storage meets industry compliance standards |
| `ROOT_KEY` | `32-bit or stronger strong key generated per enterprise security specifications` | Manages the highest permission control for the system backend, meeting the permission audit requirements of nuclear power operations |
| `FE_DOMAIN` | `Intranet domain dedicated to internal office use` | Restricts system access to internal employees only, preventing unauthorized external access |

## Three Common Misconfigurations
- Symptom: FastGPT deployed via Docker shows normal MongoDB connections initially, then throws connection timeout errors several hours later. Cause: No reasonable value set for `DB_MAX_LINK`. Concurrent requests exhaust the database connection pool without automatic release, preventing subsequent requests from establishing connections.
- Symptom: After upgrading to FastGPT v4.17.0, the frontend page still displays the old version number. Cause: Frontend static resource cache was not cleared during upgrade. The old version identifier file was not overwritten, causing the frontend to load old cached content.
- Symptom: An `Error response from daemon: error from registr` error occurs when upgrading from FastGPT v4.9.10 fix2 to FastGPT v4.17.0. Cause: The original container's registration service was not stopped during upgrade. Port conflicts cause image pulling or container startup failures.

## How to Verify Successful Configuration
- View FastGPT container startup logs. Confirm there are no errors in database connection logs, and the connection pool parameters match the configured `DB_MAX_LINK` value.
- Upload a test operation log data entry. Check that the storage path matches the configured `STORAGE_S3_ENDPOINT` endpoint, and confirm data writing is successful.
- Access the intranet address corresponding to `FE_DOMAIN`, log in, and check the version information on the system settings page. Confirm it matches the target upgraded version.
- Initiate simulated concurrent requests. Confirm the system has no timeout responses, and the connection pool does not experience exhaustion.

The values provided are common starting points and should be measured against the reader's own samples.
