# Internal Office and Employee Services for Civil Aviation Airports: Forms and Interactions

## What the Data for This Category Looks Like
Civil aviation airport internal office and employee service data mainly comes from the airport operation management system, ground service scheduling platform, employee attendance system, and equipment operation ledger. Data update frequencies cover three categories: real-time, daily, and on-demand. Real-time data includes flight dynamics and equipment operating status. Daily updated data includes scheduling plans and attendance records. On-demand updated data includes fault repair tickets.

Structured forms are the core carrier of documents. Fields include employee ID, job type, scheduling time slot, equipment number, and fault level. Units include hours, person-times, unit-times, level codes, and others. The number of fields per single business form ranges from 10 to 30.

## Constraints on Forms and Interactions
The multi-source nature, dynamic update characteristics, and diverse field units of civil aviation airport internal office data create multiple constraints for the forms and interactions link. Cross-system data sources require forms to support linked retrieval of existing ledger information, to avoid duplicate data entry by employees. Diverse field types and units require forms to have built-in unit verification rules, to block non-compliant input content. Real-time updated flight and equipment operation data require forms to have no obvious interaction delay, so backend verification duration before single-form submission must be limited. Business differences across roles such as ground service, maintenance, and administration require forms to support dynamic display of exclusive fields based on permissions, reducing interference from irrelevant information during operations.

## Three Common Mistakes
- Phenomenon: Custom knowledge base selection variables fail to associate with the target knowledge base after submission, or the field displays as empty. Cause: The data type of the global variable is not set to the matching string or array format, causing the variable to not be recognized by the knowledge base call logic.
- Phenomenon: When uploading batch corpus, the first dozen entries are processed normally, but subsequent entries have no response or trigger timeout errors. Cause: The upper limit of batch processing corpus is not restricted, exceeding the system processing threshold causing task queue blocking.
- Phenomenon: In iframe nested scenarios, after clicking the preset test text to trigger a pop-up window, the input box has pre-filled content but the send button remains gray. Cause: The correct click event for passing parameters is not bound, or the input box content change verification logic is not triggered synchronously, causing the system to fail to recognize the input content.

## How to Confirm Successful Configuration
- Open the form editing page, select any field, enter content that does not meet the format requirements, confirm that the real-time verification function pops up a prompt immediately.
- Configure the global variable as a knowledge base selection type, select the corresponding knowledge base, then call the variable in subsequent conversation nodes, confirm that the target knowledge base can be associated normally.
- Upload batch corpus, select entries exceeding the conventional single batch quantity, submit and confirm that the system does not have unresponsive or blocking situations.
- In iframe nested scenarios, click the preset test text, confirm that the pop-up window appears and the input box automatically fills in the corresponding content, and the send button can be activated normally.
