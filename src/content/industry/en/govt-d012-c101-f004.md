# Internal Office and Employee Services for Port and Shipping: Workflow Orchestration

## What the data for this category looks like
Internal office data for port and shipping operations mainly comes from port operation scheduling systems, crew personnel management systems, vessel berthing systems, and internal OA platforms. Data update rhythms fall into three categories:
- Real-time data such as vessel dynamics and operation instructions updates every second or minute
- Personnel data such as employee scheduling and attendance updates daily
- Administrative data such as document approvals and reimbursement submissions updates as submitted

The data document structure is mainly structured tables, with exclusive fields including vessel name, berth number, berthing time, operation tonnage, employee ID, position, shift, etc. Some fields have fixed units such as tons, person-times, and hours.

## What constraints these characteristics impose on workflow orchestration
High-frequency real-time operation data updates require workflows to have low trigger latency and support flexible configuration based on time or event triggers.
Multi-category data requires workflows to support splitting parameter scopes by business scenario, to avoid parameter conflicts between different data types.
The professional format requirements of exclusive fields require workflows to include targeted parameter verification rules to filter invalid data.
The need for cross-system data linkage requires workflows to call data sources from multiple different sources, to ensure coordinated circulation of operation, personnel, and administrative data.

## How to set the configurations
Workflow orchestration configurations under FastGPT v4.17.0 are as follows:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` scope configuration | Split into three categories: operation, personnel, and administration, limit the effective range of each `variables` | Port and shipping data has clear classification; splitting avoids global variable conflicts and adapts to multi-system linkage |
| `nodeId` binding | Bind `nodeId` of core nodes such as berth schedule verification and approval initiation | Facilitate workflow debugging and exception location, accurately control process direction |
| Trigger condition | Trigger based on vessel berthing time + employee on-duty status, latency no more than 60 seconds | Port operations require real-time response to berthing schedule changes; 60 seconds of latency aligns with on-site scheduling rhythm |
| Parameter verification rules | Match exclusive fields such as vessel name, berth number, and operation tonnage, verify format and units | Port data fields are professional and have fixed formats, filter invalid data |
| Timeout setting | Single node timeout 120 seconds, overall workflow timeout 300 seconds | Cross-system calls require sufficient time to avoid process interruption |
| Result output format | Follow port operation standard templates, include vessel name, operation volume, approval status | Unified format facilitates subsequent system docking and archiving |

## Three common errors
- Phenomenon: After a workflow calls an external API, the returned HTTP content cannot be correctly passed to subsequent nodes, and the interface prompts that the parameter is unrecognized. Cause: The HTTP response content is not bound to the corresponding scope of `variables`, resulting in failure to pass return data between nodes.
- Phenomenon: During multiple concurrent requests, global variable values have cross-interference, and different sessions return incorrect results. Cause: The scope of `variables` is not limited, and the default global variable does not isolate sessions, resulting in mutual influence of data between requests.
- Phenomenon: When using a matcher to match strings, the "contains" rule triggers the ELSE branch, and the "equals" rule triggers the IF branch, which is opposite to expectations. Cause: The matching logic of the matcher is not configured correctly, and the positive and negative logic of the matching result is reversed.

## How to confirm the configuration is complete
- Trigger test: Simulate trigger conditions that match the business scenario, check whether the workflow starts and flows as expected.
- Parameter verification test: Enter fields that do not conform to port data formats, check whether the workflow intercepts invalid data and prompts exceptions.
- Variable scope test: Initiate multiple concurrent test requests, check whether the values of `variables` are isolated by session without cross-interference.
- Timeout test: Simulate the delay scenario of cross-system calls, check whether the workflow completes within the set timeout period or triggers exception handling.

The values provided are common starting points and should be measured against the reader's own samples.
