# Internal Office and Employee Services for Port and Shipping: Model Access and Configuration

## Data Profile for This Category
Port and shipping internal office and employee service data primarily originates from port dispatch logs, crew schedules, vessel berthing plans, container ledgers, channel hydrological monitoring data, and similar sources. Update rhythms vary significantly: dispatch logs and real-time operation data update every hour, crew schedules update daily, vessel berthing plans update 7 to 30 days in advance, and monthly operation summaries update monthly. Most documents use structured formats, containing fields such as berth number, operation tonnage, vessel draft, wind speed, and wave height, with each field paired with clear physical units.

## Constraints Imposed on Model Access and Configuration
Real-time updated operation data requires model access context synchronization frequency to match data update rhythms, preventing return of outdated information. Structured multi-field documents require models to accurately identify and match fixed terms and units, avoiding generation of incorrect operation guidelines. Long documents such as monthly summaries consume significant token counts, so total context length per single-round call must be limited to avoid overflow. Varying update cycles across different document types require configuration of distinct index update strategies for each document type.

## Configuration Settings
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | Adapts to total length of spliced documents including port dispatch logs and vessel ledgers, avoiding context overflow |
| `temperature` | `0.1–0.3` | Aligns with structured fields and fixed terms for port operations, reducing generation randomness |
| `maxTokens` | `2000–3000 token` | Covers full length of content required for internal office replies, such as operation instructions and process guidelines |
| `quoteMaxToken` | `1200–1800 characters` | Matches average length of single document blocks for port materials, ensuring quoted document fragments are not truncated |
| `toolChoice` | `auto` | Supports automatic calling of internal tools to query real-time berth and crew schedule data, meeting office scenario requirements |
| `AIPROXY_API_ENDPOINT` | `Locally deployed proxy access address` | Adapts to access needs for locally deployed models, ensuring internal data is not exposed externally |

## Three Common Configuration Errors
- Model responses do not reference uploaded port operation document content, only outputting generic replies. This occurs when the `maxContext` parameter is incorrectly configured, leaving the context window without parsed document fragments, or when `quoteMaxToken` is set too small, truncating quoted content.
- Components other than the language model return the `Message field is required` error or status code 40. This occurs when the `AIPROXY_API_TOKEN` parameter is incorrectly configured, with invalid token format or missing valid permissions, leading to failed interface calls.
- Workflows released via API fail to return normal results, with interface call timeouts or empty data returned. This occurs when `maxContext` or `maxTokens` parameters are incorrectly set, leading to model call timeouts, or when the correct `AIPROXY_API_ENDPOINT` address is not bound in the workflow.

## How to Verify Correct Configuration
- A port berth dispatch log document is uploaded, a test query is initiated, and the response is verified to include specific fields from the document such as berth number and operation duration.
- Model call logs are reviewed to confirm that actual values of parameters including `maxContext` and `maxTokens` match configured values, with no truncation or overflow.
- A test request is initiated via the API interface, and the returned result format is verified to match expectations, with no errors of the `Message field is required` type.
- The `temperature` parameter is adjusted to different ranges, changes in response randomness are observed, and configuration effectiveness is confirmed.

The values provided are common starting points and should be evaluated against samples relevant to the specific deployment.
