# Internal Office and Employee Services for Coal Transportation and Sales: Workflow Orchestration

## What data for this category looks like
Coal transportation and sales business data comes from four systems: waybill management, truck scale ticket, coal dispatching, and financial settlement.
Data updates follow two rhythms: real-time and scheduled.
Waybill and scale ticket data is generated in real time for each truck shipment.
Dispatching plans are updated daily.
Settlement data is summarized weekly.
Documents primarily use structured tables.
Core fields include coal type name, shipment origin, shipment destination, carrier number, actual shipment weight, shipment time, and settlement unit price.
Some fields have fixed-format concatenated suffixes. For example, the waybill status field uses the format "status_date".

## What Constraints These Characteristics Impose on Workflow Orchestration
Multiple heterogeneous data sources require workflows to use multiple parallel nodes to pull data from different systems. Serial execution causes delays.
Real-time waybill and scale ticket data require workflow node timeout settings to match system response speeds. Excessively long timeouts block subsequent processes.
Fixed formats and units for structured fields require workflows to include built-in parameter validation rules. These rules ensure pulled data formats match business fields.
Cross-system data correlation requires workflows to use unified parameter binding to associate data across different nodes. This prevents data disconnection.

## How to Set Configurations

| Configuration Item | Recommended Practice | Basis for This Practice |
| --- | --- | --- |
| Global variable configuration | Bind `variables` to core fields for waybills, scale tickets, and dispatching | Uniformly manage cross-node business data, adapt to correlation requirements of multi-source data |
| Node timeout setting | 30–60 seconds | Match the interface response speed of coal transportation and sales systems, use a reasonable range calibrated through actual testing |
| Judgment rule matching method | Contains, ends with | Match fields with concatenated suffixes such as waybill status, cover judgment scenarios for business workflows |
| System parameter passing | Extract from context and mount to `variables` | Supplement required system parameters such as waybill ID and truck number beyond user conversations |
| Failure retry configuration | Up to 2 retries, 10-second interval | Address temporary interface fluctuations in coal transportation and sales systems, ensure process stability |
| Global variable lifecycle | Destroy within a single session | Avoid data interference between concurrent requests, comply with the session isolation mechanism of FastGPT v4.17.0 |

## Three Common Misconfigurations
- Phenomenon: When configuring "equals" or "starts with" rules for the judge node, all waybill status judgments trigger the ELSE branch. Reason: Waybill status fields in coal transportation and sales typically use concatenated formats such as "shipped_20240520". Matching only the start or exact value cannot cover business judgment needs.
- Phenomenon: The workflow calls the scale ticket system interface and returns empty data, causing the node to fail. Reason: No default fallback value is configured for `variables`. When the scale ticket system has no temporary data, missing placeholder parameters cause process interruption.
- Phenomenon: Waybill data from different sessions appears interleaved when multiple concurrent workflow requests are initiated. Reason: Session isolation configuration is not enabled, and `variables` are not bound to the current session identifier, leading to shared in-memory data.

## How to Verify Successful Configuration
- Manually trigger the workflow, check if business data pulled by each node matches the source system, and verify that field formats and units meet business requirements.
- Simulate a scenario where the source system interface is temporarily unresponsive, check if the workflow triggers the failure retry logic or executes a preset fallback process.
- Initiate multiple concurrent test requests, check if `variables` are isolated between sessions with no data interleaving.
- View workflow execution logs, confirm that the node corresponding to `nodeId` has normal execution status, and system parameters have been correctly passed to workflow nodes.
