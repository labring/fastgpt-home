# Integrated Coal and Power Internal Office and Employee Services: HTTP Interfaces and External Systems

## What Data for This Category Looks Like
Data sources for integrated coal and power scenarios cover four core systems: underground coal mine monitoring systems, power plant operation logs, employee attendance management systems, and material scheduling platforms. Update frequencies vary by scenario: equipment operating condition data updates minute-by-minute, attendance data updates daily, and material scheduling data syncs on demand. Each data record has a flat structure with no nested fields, including fields such as equipment code, timestamp, operating parameter value, employee ID, shift identifier, and material flow direction. Units include tons, kilowatt-hours, person-times, minutes, and others.

## Constraints Imposed by These Characteristics on HTTP Interfaces and External Systems
The mixed update rhythm of integrated coal and power scenarios requires HTTP interfaces to support both short-cycle high-frequency requests (for example, equipment operating condition data) and long-cycle low-frequency requests (for example, attendance data). The flat, non-nested field structure simplifies data parsing, but differences in field naming across multiple source systems mean the interface must support custom field mapping. Minute-level real-time data can have a large single-request return volume, so the interface must limit the number of entries returned per request to avoid timeouts. Data related to employee services must bind employee IDs and permission identifiers, so the interface must validate the legitimate access scope of the request subject to prevent unauthorized calls.

## How to Configure Settings

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${access_token}` | Adapts to general OAuth2 security authentication specifications for state-owned enterprises and public institutions, ensuring the legality of interface calls |
| Request timeout | 600 seconds | Covers the maximum response time for batch collection of equipment operating conditions and batch queries of material scheduling, preventing forced interruption of requests |
| `variables` | `{"query_scope": "on_site", "time_range": "last_1h"}` | Adapts to general query scope requirements for employee services and equipment monitoring in integrated coal and power scenarios |
| `responseData` | Return only core business fields | Matches the flat structure characteristics of data sources in the scenario, simplifying the data parsing process |
| Field mapping rules | Custom mapping based on original system field names | Compatible with different naming conventions of coal mines, power plants, and attendance systems, unifying data formats |
| Maximum number of entries returned per request | First 100 entries | Avoids excessive data volume in a single return causing interface timeout, adapting to the return scale of real-time monitoring data |

## Three Common Misconfigurations
- Symptom: A 401 status code returns when calling the application history interface, with a prompt indicating invalid credentials. Cause: Incorrect configuration of the `Authorization` parameter, confusion between general credentials and application-specific credentials, and failure to bind the permission scope of the corresponding application.
- Symptom: The number of context entries displayed on the interface does not match the number of entries actually sent to the external system. Cause: Incorrect setting of the `responseData` filtering rule, inclusion of non-business fields in context statistics, leading to counting deviations.
- Symptom: The HTTP request does not trigger as expected after the question classification branch runs. Cause: Failure to bind the trigger condition of the HTTP request node in process orchestration, and failure to pass the output of the question classification as an input parameter to `variables`.

## How to Verify Proper Configuration
- Call the test interface, check that the `Authorization` parameter carries the correct authentication token, and confirm the returned response status code is 200.
- View the interface log, and compare the sent request parameters to the query conditions configured in `variables`.
- Verify that the returned `responseData` fields match the preset core fields, with no redundant non-business fields.
- Simulate a multi-branch process, and confirm that the HTTP request node triggers normally under all question classification branches.
