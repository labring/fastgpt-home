# Internal Office and Employee Services for Mining and Ore Processing: Deployment and Upgrade

## What the Data for This Category Looks Like
Data sources for mining and ore processing operations include mining ledgers from production scheduling systems, shift-by-shift inspection records from equipment maintenance departments, employee scheduling and training archives from the human resources department, and on-site regulations and hidden danger investigation reports from the safety management department.

Update cadence follows multiple tiers: mining ledgers are updated hourly, inspection records are updated per shift, and training archives and safety regulations are updated quarterly.

Document structure includes two categories: structured and unstructured. Structured documents contain fields such as equipment number, runtime, inspection point number, and scheduling date. Unstructured documents include hidden danger investigation photos and ore processing process videos.

## Constraints Imposed on Deployment and Upgrade by These Characteristics
Mixed storage of structured and unstructured data requires configuring two separate database types for adaptation, which increases deployment complexity.
High-real-time inspection and scheduling data require adjusting cache and database connection parameters to ensure concurrency capabilities.
Document fields contain professional units and specific identifiers. Field integrity must be preserved during chunking and retrieval to avoid information loss.
Internal mine networks may have bandwidth restrictions. Object storage must be configured to adapt to internal data transfer and reduce public network transmission delay.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 20–30 connections | Supports high concurrent access for the large volume of real-time inspection and scheduling data in mining and ore processing operations |
| `MONGODB_URI` | Fill in the cluster connection string according to the deployment environment | Stores unstructured business data such as hidden danger investigation reports and ore processing process documents |
| `PG_URL` | Fill in the primary-secondary cluster address according to the deployment environment | Stores structured business data such as employee scheduling and mining ledgers |
| `REDIS_URL` | Configure as a local high-availability cluster address | Caches real-time inspection data and user session information to reduce database access pressure |
| `ROOT_KEY` | Calibrate based on actual testing | Initial administrator key for the management backend, must be configured during the initial deployment process |
| `STORAGE_S3_ENDPOINT` | Configure the enterprise internal object storage address | Stores large-volume ore processing process videos and equipment maintenance photos, adapting to internal data transfer |

## Three Common Configuration Mistakes
Reference only; verify against the target FastGPT release and deployment documentation.
- Phenomenon: After deploying with Docker, the 3000 port page cannot be accessed, but the 3001 port loads normally. Cause: The front-end service port mapping rules were not configured correctly, or the `FE_DOMAIN` configuration did not match the internal access domain name and port.
- Phenomenon: Login fails after modifying the root administrator password, and the configuration does not take effect. Cause: Only the configuration file inside the container was modified, and the administrator credentials stored in the database were not updated synchronously, causing the configuration to fail to persist.

## How to Verify Proper Configuration
- Access the internal access address configured in `FE_DOMAIN` to confirm the front-end page loads normally.
- Run the built-in database connectivity test tool to confirm that the clusters configured in `MONGODB_URI` and `PG_URL` can establish normal connections.
- Upload a mining equipment inspection document, trigger the knowledge base retrieval process, and confirm that the retrieval results return normally and the large language model outputs complete content.
- Modify `ROOT_KEY`, restart the service, and attempt to log in to the management backend with the new key to confirm the credentials take effect normally.
