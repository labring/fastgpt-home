# Internal Office and Employee Services for Shipbuilding: Deployment and Upgrade

## What the data for this category looks like
The data for internal office and employee services in shipbuilding comes from five main sources: production scheduling systems, equipment maintenance platforms, crew scheduling systems, office OA, and ship design document libraries. Data is split into two categories.
Structured data includes fields such as work order numbers, workstation numbers, maintenance cycles, and working hours. It updates in real time or daily to align with production progress.
Unstructured data includes ship design PDF drawings, maintenance log text, training courseware, and similar materials. It updates on project cycles or a monthly basis.
Document structures include fixed fields and free text. Some fields use dedicated units: maintenance cycles are measured in days, and working hours are measured in hours. Total data volume changes dynamically based on the scale of shipbuilding projects.

## Constraints on deployment and upgrade
The mixed data types and dynamic data volume in shipbuilding create multiple constraints for deployment and upgrade workflows.
High-frequency structured work order data requires adjustments to database connection pool configurations to avoid connection exhaustion that disrupts business operations.
Large unstructured design drawings require dedicated storage node configurations to support large file uploads and reads.
Multi-source data that flows across departments requires separation between business databases and general storage to enforce data access permissions.
During upgrades, unit mapping rules for existing fields must be retained to prevent data parsing errors that disrupt internal office processes.
Additionally, shipbuilding deployments often need to work within intranet environments. Offline deployment images and dependency packages must be prepared in advance.

## Configuration Settings
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 150–200 | Adapts to high-frequency work order and scheduling data in shipbuilding, prevents database connection exhaustion |
| `MONGODB_URI` | Full connection string including dedicated business database | Isolates shipbuilding office business data from general system data, ensures secure access permissions |
| `STORAGE_S3_ENDPOINT` | Enterprise intranet storage node address | Stores large unstructured files such as ship design drawings and maintenance logs |
| `FE_DOMAIN` | Enterprise internal office subdomain | Unifies front-end access entry, aligns with internal office domain name rules |
| `FILE_TOKEN_KEY` | 32-bit randomly generated string | Encrypts internal file access tokens, blocks unauthorized access to sensitive documents |
| `ROOT_KEY` | Configured per enterprise permission rules | Manages system super administrator permissions, supports hierarchical control for internal office scenarios |

## Three Common Configuration Mistakes
- Symptom: After starting a Docker container, the image shows normal operation but port 3000 is inaccessible. Logs indicate a MongoDB connection failure. Cause: The account and password parameters for `MONGODB_URI` are not configured correctly, or the connection format is incompatible with the database version.
- Symptom: After configuring an external model, an error is prompted during testing, but normal operation occurs when using the model for conversation. Cause: The test process does not load full context configuration, leading to failed parameter verification. Actual runtime automatically completes missing configurations.
- Symptom: No response after submitting a commercial deployment consultation. Cause: The request was not submitted through the official designated channel, or the large file storage and intranet deployment requirements for the shipbuilding scenario were not clearly stated.

## How to Verify Successful Configuration
- Run a database connection test to confirm that the connection string configured in `MONGODB_URI` can properly access the corresponding business database, and that the number of test connections does not exceed the `DB_MAX_LINK` setting.
- Upload a single ship design drawing file larger than 100MB, confirm that the storage node configured in `STORAGE_S3_ENDPOINT` can receive the file and return a valid access link.
- Access the front-end address configured in `FE_DOMAIN`, confirm that the login interface loads normally, and that the super administrator can complete initial permission configuration using `ROOT_KEY`.
- Simulate submitting more than 10 high-frequency production work order data entries, confirm that the system has no connection timeouts or data parsing errors.

The values provided are common starting points and should be measured against the reader's own samples.
