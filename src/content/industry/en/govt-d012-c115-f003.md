# Internal Office and Employee Services for Rail Transit Equipment: Multi-turn Dialogue and Prompt Engineering
## What the Data for This Category Looks Like
The internal office and employee service data of rail transit equipment enterprises mainly comes from the enterprise OA system, equipment operation and maintenance ledger database, employee attendance system, and process standard document library. The data update rhythm varies by type: equipment operation and maintenance ledgers are synchronized in real time with on-site operations, while process standard documents are updated once per quarter. The document structure includes fields such as equipment number, operation and maintenance period, fault type, processing flow, responsible team, employee ID, attendance period, and others. Units include units, hours, person-times, kilometers, days, and more.

## What Constraints These Characteristics Impose on Multi-turn Dialogue and Prompt Engineering
The multi-turn dialogue and prompt configuration for rail transit equipment scenarios must adapt to constraints imposed by the data's characteristics. Real-time updated equipment operation and maintenance ledgers require multi-turn dialogue to call the latest on-site operation data, and prompts must explicitly specify retrieval of real-time data sources. Multi-type data includes multiple fields with strict unit requirements, so prompts must clearly define field extraction and unit verification rules to avoid missing key information or format errors in dialogue results. The update rhythms of different data vary widely, so the knowledge base synchronization cycle must match the update frequency of the corresponding data to prevent dialogue calls of outdated content.

## How to Set Configurations
| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| Maximum Context Length | 8000–12000 token | Rail transit equipment data has many fields, and single-turn dialogue needs to carry a large amount of content such as equipment numbers and operation records. This avoids context overflow and complies with the context processing rules of FastGPT v4.17.0 |
| Conversation Log Retention Period | 180 days | Internal office work requires retaining compliance records such as operation and attendance, which matches the general cycle requirements of enterprise file management |
| `chatId` Association Rule | Bind employee ID and equipment number | Ensure that dialogue context accurately matches specific operating personnel and corresponding equipment, avoiding confusion of conversation context |
| `messages` Processing Strategy | Retain the last 10 rounds of dialogue, automatically truncate historical messages that exceed the length | Early operation records have low reference value for current requests in multi-turn dialogue, reducing invalid context occupancy and improving response speed |
| `variables` Population Rule | Automatically populate context variables such as equipment number and employee ID | Rail transit equipment scenarios need to associate specific operating resources, improving dialogue accuracy and complying with the variable calling rules of FastGPT v4.17.0 |
| Knowledge Base Synchronization Cycle | Real-time (operation data), quarterly (process documents) | Match the update rhythm of different types of data to ensure the timeliness of called content |

## Three Common Misconfiguration Issues
- Symptom: Cross-time-period dialogue cannot continue the previous conversation flow, and historical dialogue content is not loaded. Cause: The association rule between `chatId` and employee ID and equipment number is not configured, resulting in lost conversation context and inability to associate dialogue records from months prior.
- Symptom: Single-turn dialogue response time exceeds 10 seconds, and the interface displays a loading timeout status. Cause: The number of historical dialogue rounds for `messages` is not limited, and excessive context content causes the model processing time to exceed the conventional response threshold.
- Symptom: Dialogue logs cannot be saved for the specified duration, or the storage directory has no corresponding log files. Cause: Dialogue log saving parameters are incorrectly configured, failing to match the cycle requirements of internal enterprise file management, or the log storage path is not correctly specified.

## How to Verify Successful Configuration
- Initiate two dialogue requests with a long interval, using the same `chatId`, confirm that the second request can read the conversation context from the first request.
- Adjust the retention round parameter for `messages`, observe whether the context content in the model response only includes the specified number of historical records, with no early invalid content.
- View the dialogue log storage directory, confirm that logs are generated according to the preset retention duration and include key fields such as equipment number and employee ID.
- Trigger a dialogue request that includes multiple fields, confirm that the model response content complies with the preset field unit verification rules, with no format errors.
