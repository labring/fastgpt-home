# Internal Office and Employee Services for Communication Towers and Infrastructure: Tool Calling and Plugins

## What the data for this category looks like
Data for communication towers and infrastructure primarily comes from three core data sources: tower operation and maintenance management platforms, base station power and environment monitoring systems, and tower inspection archive databases. Update frequencies fall into three categories: real-time inspection data updates every 15 minutes, base station operating parameters update every hour, and asset ledger data updates daily. The structure of individual data records includes fields such as tower unique ID, longitude and latitude coordinates, operating temperature, inspection time, fault level, and associated maintenance work order number. The unit for operating temperature is degrees Celsius, the unit for tower height is meters, and inspection time uses the ISO 8601 format.

## Constraints on tool calling and plugin workflows
Differences in update frequencies across data sources require that tool calling use distinct caching strategies. Real-time data must use a short cache duration to avoid returning expired information. The tower ID is a unique identifier field. When calling a tool, the exact tower ID must be passed as a query parameter, and data cannot be retrieved via fuzzy matching. The fault level is an enumeration type field. The function parameters for tool calling must strictly match the preset enumeration values, otherwise a parameter verification failure will be triggered. There are many fields in individual data records, so tool calling must specify a return field list to reduce unnecessary data transmission and meet the lightweight requirements of internal office scenarios.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Supports automatic matching of available tools, adapts to calling requirements across multiple internal office scenarios such as inspections, work orders, and ledgers |
| `functionCall` | Configure according to the target tool template | Matches the interface parameter format of communication tower data to ensure request validity |
| Tool call timeout | 30 seconds | Adapts to the quick return of real-time operation and maintenance data, avoids waiting delays in internal office scenarios |
| Return field filtering | Only include tower ID, operating temperature, inspection time, work order status | Reduces invalid data transmission, meets the lightweight query requirements of internal office scenarios |
| Data cache duration | 1 hour (real-time inspection data), 24 hours (asset ledger) | Matches the update frequencies of different data sources, balances timeliness and calling costs |
| Parameter verification switch | Enabled | Prevents passing fault level parameters that do not comply with enumeration rules, avoids tool calling failures |

## Three common configuration mistakes
- Phenomenon: Calling the API interface that stops output returns an empty response, with a status code of 200 but no valid content. Cause: The termination parameters for tool calling are not configured correctly, causing the large model to not trigger the preset stop instruction.
- Phenomenon: When calling an MCP service, numeric type parameters such as tower ID are forcibly converted to string format. Cause: The parameter type is not explicitly specified in the tool template, so it is converted to a string format by default, which does not meet the query requirements of communication tower data.
- Phenomenon: The streaming output of tool calling cannot be turned off, and segmented content fragments are returned continuously. Cause: The stream return switch is not turned off in the FastGPT v4.17.0 configuration, causing the large model output to be pushed in continuous segments.

## How to confirm correct configuration
- Initiate a tool calling request that includes a valid tower ID, check whether the fields of the returned result exactly match the configured filtered fields.
- View the tool calling logs to confirm that the parameter type matches the configured template, with no forced conversion to string format.
- Test the API interface that stops output, confirm that the returned content meets expectations, and there is no empty response issue.
- After turning off the stream output switch, initiate a call, check whether the returned result is complete single-segment content, with no segmented pushing.
