# Internal Office and Employee Services for Communication Towers and Infrastructure: Deployment and Upgrade

## What the data for this category looks like
Internal office data for communication towers and infrastructure comes from four main sources: base station operation and maintenance management systems, daily inspection records, employee work order ledgers, and asset inventory systems. Data updates follow three frequency patterns: real-time (inspection reports, fault work orders), daily (attendance, scheduling), and weekly (asset inventory). Most individual documents are structured tables, with fields including base station number (unit: number), inspection time, fault level, processing duration (unit: minutes), employee ID, work order status, and others. Some attachments include high-definition on-site inspection photos and fault location annotation files.

## What constraints these characteristics impose on deployment and upgrade
This category includes both multi-source structured data and high-definition attachments. During deployment, configure both a relational database and object storage service to meet storage needs for different data formats. Use a low-latency caching service for real-time updated inspection and fault work orders to ensure fast data query responses. Set up flexible scheduled synchronization tasks for diverse update frequencies to avoid data lag. Adjust file upload limits in advance, as individual attachments have large file sizes, to prevent upload failures after deployment. Pre-configure permission rules for multi-account collaboration based on clear employee scales and department divisions, to meet hierarchical management needs for internal office work.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale for This Setting |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `20–30 connections` | This category has frequent data connection requests. Reserve sufficient connection pool capacity to handle concurrent queries for inspections, work orders, and other tasks |
| `MONGODB_URI` | `Connection string of MongoDB instances from domestic cloud providers, single-instance storage capacity no less than 500 GB` | Store unstructured attachments such as high-definition inspection photos. Domestic instances reduce cross-region access latency, and sufficient capacity supports long-term data accumulation |
| `REDIS_URL` | `persistent Redis instance address with at least 8 GB memory` | Cache real-time updated work order status and base station online information to ensure low-latency queries. Use persistent configuration to prevent cached data loss |
| `STORAGE_S3_ENDPOINT` | `Corresponding domestic cloud service provider object storage node address` | Support unified storage of structured data and attachments, simplify post-upgrade migration workflows, and reduce cross-region access costs |
| `FILE_TOKEN_KEY` | `32-character random string` | Secure identity verification for uploaded files, and prevent unauthorized access to inspection attachments |
| `ROOT_KEY` | `Strong random key exclusively for initial admin configuration` | Initialize the multi-account collaboration permission system, and support hierarchical management needs for internal office work |

## Three common errors
- Phenomenon: Uploading inspection photo attachments larger than 2 MB triggers an upload failure, and the interface returns the "File size exceeds limit" error. Cause: The default file upload threshold remains unadjusted. FastGPT v4.17.0 sets a default file upload limit of less than 2 MB.
- Phenomenon: Pulling the FastGPT image in a Linux environment triggers a timeout, and the issue persists even after configuring a domestic mirror source. Cause: `STORAGE_S3_ENDPOINT` is not pointed to a domestic node. Dependency resource requests during image pulling still target overseas nodes.
- Phenomenon: Creating multiple employee accounts fails to enable department permission isolation, and some accounts can view base station work orders from non-local regions. Cause: The permission system is not initialized using `ROOT_KEY`, and access control rules for hierarchical accounts are not configured.

## How to confirm the configuration is complete
- Run the container status check command to confirm that all associated database, caching, and storage service containers run normally, with no abnormal exit records.
- Upload office attachments of the volume required for the category's business to verify that the upload process has no errors, and that attachments can be stored and accessed normally.
- Log in to the system using the initial administrator key, create a test account, and assign the corresponding permission scope. Verify that the test account can only access internal data within the authorized range.
- Call the system's built-in health check interface to confirm that all service connection parameter configurations are correct, with no connection timeout or authentication failure errors.
