# Internal Office and Employee Services for Steel Smelting: Tool Calling and Plugins

## What the data for this category looks like
Steel smelting data comes from on-site PLC control systems, manufacturing execution systems (MES), enterprise resource planning (ERP), and equipment inspection ledgers. The update rhythm falls into two categories: real-time production parameters such as furnace temperature and feeding volume are updated from second-level to minute-level. Static data such as process documents and monthly energy consumption reports are updated daily. The document structure includes structured fields and unstructured content. Structured fields include furnace number, smelting batch number, steel grade, temperature (℃), energy consumption (kWh), and feeding volume (tons). Unstructured content includes inspection photos and process specification PDFs.

## What constraints these characteristics impose on tool calling and plugins
The second-level update of real-time parameters requires tool calling to use a short timeout period. This avoids affecting office responses due to long waiting times. Structured data with multiple fields requires tool calling to accurately match field names. Otherwise, parameter parsing errors will occur. Unstructured inspection photos and process documents require supporting image recognition and document parsing plugins for processing. Data with different update rhythms needs to correspond to different tool calling frequencies. Offline report tools should not be triggered frequently. Real-time parameter tools need to adapt to short-interval calls.

## How to set the configuration
The following configurations are written for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapts to automatic tool calling needs across multiple categories in steel smelting scenarios |
| Tool calling timeout period | 30–60 seconds | Real-time production data has low pull latency. An overly long timeout will reduce office response efficiency |
| Historical conversation transfer configuration | Enable and transfer the first 8 rounds of conversations | Smelting process adjustments rely on historical batch data. Limiting the number of rounds controls context overhead |
| Knowledge base call billing method | Consume via third-party API key | Enterprise internal knowledge bases have large data volumes. Platform points cannot meet long-term usage needs |
| Workflow log pull range | Pull natural day logs from the last 7 days | Internal office troubleshooting focuses mostly on operation records from the past week |

## Three common configuration mistakes
- When calling the searchTest tool, returned results are not associated with historical smelting parameters. The symptom is that the batch number field from historical conversations is absent from tool input parameters. The cause is that the historical conversation transfer configuration is not enabled, or the number of transferred rounds is set to 0.
- The workflow log query interface displays no content. The symptom is that the number of search results is 0. The cause is that the set time interval for the pull range exceeds the system's retained log duration, or the correct natural day range is not selected.
- A prompt indicates insufficient knowledge base call points. The symptom is a point consumption pop-up appears on the interface. The cause is that the knowledge base call permission bound to the third-party API key is not configured, and the platform's default point billing mode is still used.

## How to confirm the configuration is complete
- Enter a question containing historical smelting batches in the tool calling test interface. Check whether the batch number field from historical conversations is included in the tool input parameters.
- View the knowledge base settings page. Confirm that the billing method has been switched to consume via third-party API key.
- Trigger a workflow, then select the corresponding time interval on the log query interface. Check whether corresponding records can be pulled.
- Adjust the `toolChoice` parameter to `auto`, then test calling multiple types of tools. Confirm that the system automatically matches available tools.

The values provided are common starting points and should be measured against the reader's own samples.
