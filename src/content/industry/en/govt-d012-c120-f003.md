# Internal Office and Employee Services for Railway Operations: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
The data for internal office and employee services in railway operations mainly comes from dispatch command systems, equipment inspection logs, employee attendance management, ticket operation and maintenance work orders, and post scheduling systems. Data update frequencies vary across scenarios: real-time dispatch data syncs every 10 seconds, inspection logs update after a single inspection task is completed, and attendance and scheduling data syncs in batches every early morning. A single document includes fields such as equipment number, inspection point, work order number, employee ID, processing duration, and post type. Units include kilometers, hours, person-times, and unit counts, among others.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
High-frequency updates to real-time dispatch data require multi-turn dialogue contexts to pull the latest information in real time, to avoid using expired dispatch instructions and equipment status. Multiple types of heterogeneous data cover dimensions such as equipment inspection, operation and maintenance work orders, and attendance scheduling, with a large number of fields and clear business boundaries. Prompts must clearly define field call scope and return format to prevent confusion between different business data. Some data updates by shift or daily, so the retention duration of dialogue contexts must match the data update cycle to avoid calling invalid historical information. For employee service scenarios, personal employee IDs and post permissions must be associated, and prompts must specify reading corresponding identification parameters from `variables` to ensure dialogues match individual business scopes.

## How to set configurations
Reference only; verify against the target FastGPT release and deployment documentation.

| Configuration Item | Recommended Approach | Rationale |
|---|---|---|
| `messages` | Retain the most recent 8 turns of dialogue content, with each turn not exceeding 1200 characters | Railway operation business data has many fields. Overly long contexts can easily cause the model to confuse key business information. Limiting the number of turns and length improves dialogue accuracy |
| `variables` | Bind three variables: employee ID, current inspection point, and work order type | Employee service scenarios need to associate individual business permissions and current work scenarios. Passing information via variables ensures dialogues return targeted content |
| Maximum context | 8000–12000 tokens, calibrated based on actual testing | Multi-turn dialogue for railway operations needs to carry multiple types of business information such as dispatch, inspection, and work orders. Sufficient context fully retains historical interactions and business details |
| Question optimization | Enabled, supplement equipment number and inspection time restrictions for operation and maintenance-related questions | Railway operation and maintenance data requires clear equipment identification and time ranges. Optimized questions more accurately match corresponding business data |
| Context refresh timing | Trigger real-time refresh via `chatId` | Railway dispatch data updates in real time. The latest dispatch and equipment status information must be pulled each time a dialogue is initiated |

## Three common configuration mistakes
- The configured prompt does not take effect, and the content returned by the model does not match preset requirements. Cause: The prompt is not bound to business fields in `variables`, or the prompt does not limit the scope of railway operation-specific fields such as equipment and work orders.
- Dialogue history cannot be exported, or exported records have missing fields. Cause: Full storage configuration for dialogue logs is not enabled, or the session scope corresponding to `chatId` is not specified.
- After uploading an attachment, subsequent associated dialogue cannot be carried out. Cause: The binding rule between parsed attachment fields and `messages` is not configured, so the model cannot obtain business information from the attachment.

## How to confirm configuration is complete
- Initiate a multi-turn dialogue containing dispatch, inspection, and work order information, check whether returned content includes preset business fields, and adjust prompts and context configurations until they match.
- Call `chatId` to query the context list of the corresponding session, confirm that retained turns and content meet preset requirements.
- Bind the employee ID variable in `variables`, initiate a question related to personal attendance, check whether returned content matches the business permissions of the corresponding employee.
- Upload railway operation and maintenance-related attachments, initiate associated questions, check whether the model can reference information from attachments to answer.

The values provided here are common starting points and should be evaluated against the reader's own samples.
