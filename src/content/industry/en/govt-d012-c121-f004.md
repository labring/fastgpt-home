# Internal Office and Employee Services for Expressway Operations: Workflow Orchestration

## What this category of data looks like
Core data for expressway operations comes from four types of data sources: toll lane systems, pavement monitoring systems, maintenance work order systems, and employee attendance and scheduling systems. Data update rhythms fall into three categories: real-time (lane traffic volume, device alerts), hourly (road section traffic statistics), and daily (attendance reports, closed maintenance work orders). A single data document structure includes three types of fields: unique identifier fields, business attribute fields, and status fields. Examples of fields include lane ID, number of passing vehicles, fault level, and scheduling shift, with units of number, vehicles, level, and hours respectively. Most data uses structured JSON format, with a small amount of unstructured data being monitoring video clips.

## What constraints these characteristics impose on workflow orchestration
Workflow triggers for real-time data must match the data source's update rhythm to avoid resource waste from polling. The workflow binds corresponding business fields via `variables` for structured data with multiple fields to ensure the data called by nodes matches the business scenario accurately. Cross-system data interaction, such as retrieving maintenance data across road sections, uses clear `nodeId` to distinguish task instances of different road sections and avoid data confusion. The workflow configures branch judgment rules based on work order priority to adapt to different response time requirements for employee service scenarios with hierarchical processing needs. Separate nodes handle unstructured data to avoid occupying resources for structured data flow. This configuration logic is compatible with FastGPT v4.17.0 workflow node rules.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| Trigger mode | Trigger on work order status change | Adapt to real-time processing needs of real-time alerts and traffic data, no polling required |
| Variable binding | Bind lane ID and traffic volume fields in `variables` | Match structured data fields of the toll system to ensure accurate data called by nodes |
| Tool call switch | Enable tool call, disable knowledge base automatic reference | Meet scenario requirements of only using tool return results, avoid redundant references |
| Single pull quantity | Top 20 work order records | Limit data volume to avoid excessive processing time for workflow nodes |
| Timeout period | 600 seconds | Adapt to average time required to retrieve cross-section maintenance data, avoid forced task termination |
| Branch judgment condition | Match nodes by work order priority | Correspond to hierarchical processing rules for expressway operation work orders, ensure high-priority work orders are processed first |

## Three common mistakes
- Workflow outputs HTML code mid-process but does not display it, directly proceeding to the next branch: The symptom is that node logs show HTML content has been generated, but the process state jumps directly to the next node without a rendering step. The cause is that the rendering trigger rule for the output node was not configured, only data transfer was set, and the front-end display node was not bound.
- Workflow runs too slowly: The symptom is that work order processing time exceeds the preset timeout, and node status remains in running for a long time. The cause is that the number of pulled work orders per single time was not limited, or parallel tasks of different road sections were not distinguished by `nodeId`, leading to resource competition.
- Knowledge base reference content still appears after tool call: The symptom is that knowledge base-related prompts appear in the response, including input and response fields. The cause is that the automatic knowledge base retrieval switch in the workflow was not closed, and only using tool call return results was not specified.

## How to confirm the configuration is correct
- Trigger a test work order, check if the workflow node logs correctly retrieve the traffic data of the corresponding lane, and the field values bound via `variables` match the test data.
- Call the tool to generate HTML code, check if the node output contains complete HTML fragments, and the process does not directly jump to the next branch.
- Execute the tool call task, check that the return result has no knowledge base-related reference fields, and only displays the content returned by the tool.
- Simulate 3 parallel work orders, check if the running time of workflow nodes meets the preset timeout period, with no lag caused by resource competition.

The values provided are common starting points and should be measured against the reader's own samples.
