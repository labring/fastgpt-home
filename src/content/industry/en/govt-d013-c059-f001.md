# Employee Service Desk for Personnel Policy Q&A: HTTP Interfaces and External Systems

## What this category of data looks like
Personnel policy Q&A data primarily comes from internal enterprise personnel management records, officially released policy announcements and revision notices. Updates are triggered by new policy releases or existing policy revisions, with no fixed cycle. Document structures typically include policy titles, scope of application, specific clauses, exception notes and consultation channels. Fields include policy number, effective date, applicable job category, units involving natural days, working days, number of application materials, etc. Content focuses on structured clauses and process descriptions, with no redundant unstructured descriptions.

## What constraints do these characteristics impose on the HTTP Interfaces and External Systems component
Because personnel policy data includes structured fields such as clear effective dates and applicable job categories, HTTP interfaces must support carrying job category and effective date range as query parameters to achieve precise matching of the policy scope applicable to the user. Since data updates have no fixed cycle, interfaces must support scheduled synchronization or real-time pulling of the latest policy documents to avoid returning expired content. Documents are primarily structured clauses, so the interface return content must retain the original clause numbers to facilitate accurate reference to corresponding policy entries during subsequent Q&A. When connecting to the enterprise HR system, information such as the employee's department and job level must be passed as filtering conditions to ensure that the returned policies only apply to the current user and avoid cross-job policy leaks or mismatches.

## How to configure the settings
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer token issued by the enterprise internal API gateway | Used to verify interface call permissions and prevent unauthorized access |
| `variables` | Key-value pairs containing employee job category and department information | Used to pass user context and filter applicable policy clauses |
| `responseData` | Only return the policy_content, policy_number, effective_date fields | Streamline returned content and reduce transmission overhead |
| Timeout period | 15-30 seconds | Adapt to the loading and query time of personnel policy documents and avoid request interruptions |
| Synchronization frequency | 2:00 AM daily | Aligns with the daily release rhythm of enterprise policy updates to ensure data timeliness |
| Document filtering rules | Only synchronize policies with effective dates later than the current date | Filter expired policies to ensure returned content is compliant and valid |

## Three common errors
- An interface call returns a 404 status code. The cause is that the `Authorization` parameter is not configured correctly or an expired token is used, causing the API gateway to reject the request.
- A call to the `/api/core/dataset/update` interface returns a 500 status code. The cause is that required policy document fields are not passed, or the interface parameter format does not meet system requirements.
- After uploading a local policy file, the interface returns empty fields. The cause is that the `Authorization` parameter and `baseURL` configuration item are not obtained correctly, causing the interface call to fail to point to the correct service address.

## How to confirm the configuration is complete
- Before calling the interface, check that the `Authorization` parameter matches the token issued by the enterprise internal API gateway to ensure permission verification passes.
- Check that the `variables` parameter includes necessary information such as the user's job category and department to ensure the interface can correctly filter policy content.
- Initiate a test request and check that the `responseData` returned fields include the expected policy content and number to confirm the data return meets requirements.
- View the scheduled synchronization task logs to confirm that the daily policy document update is completed normally with no failed records.
