# Hotline Knowledge Base and Ticket Assistance for Ticket Auto-Classification: Model Access and Configuration

## What the data for this category looks like
This category of data comes from call transcripts from hotline call centers and ticket entries from internal ticket management systems. Data is updated in real time whenever a new user call or ticket submission is made. Each individual ticket document includes fields such as appeal title, detailed description, call time, user ID, initial dispatch candidate tags. The call time format is YYYY-MM-DD HH:MM:SS. The appeal description is plain text with no fixed length and no unified format constraints.

## What constraints these characteristics impose on model access and configuration
Ticket data contains colloquial user appeal transcripts. This requires models to have text understanding capabilities adapted to Chinese colloquial language. A correspondingly optimized model must be selected during configuration. The real-time data update feature requires model calls to have low latency. The timeout parameter for single calls must be reasonably limited. Each individual ticket contains multiple field types. Configuration must explicitly specify that models only extract content related to classification to avoid interference from irrelevant fields with classification results. Ticket content length varies widely. Context and output length parameters must be reasonably configured to prevent content truncation that causes classification failure. This page is compatible with FastGPT v4.17.0.

## Configuration Settings
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `maxContext` | 4000–6000 token | A single ticket usually includes a title, detailed description and historical interactions, and needs to cover the complete context of a single ticket |
| `maxTokens` | 1000–1500 token | Classification results need to include first-level classification tags, second-level classification tags and a brief matching explanation, so output length must meet requirements |
| `temperature` | 0.1–0.3 | Ticket auto-classification requires stable and consistent results to avoid classification errors caused by random deviations |
| `AIPROXY_API_ENDPOINT` | Fill in the standard API address provided by the deployed model service provider | Adapt to self-built or third-party hosted large model interfaces to ensure correct call chains |
| `AIPROXY_API_TOKEN` | Fill in the valid access key generated by the service provider | Complete identity verification for the model interface to prevent unauthorized access |
| `toolChoice` | none | Ticket auto-classification only requires text classification capabilities and does not need to call external tools |

## Three Common Configuration Mistakes
- A 401 Unauthorized error is returned when calling the model. This is caused by an incorrect or expired `AIPROXY_API_TOKEN`, or failure to properly configure the interface access key.
- The classification result is empty or has no clear classification tag. This is caused by an overly small `maxTokens` setting, which truncates the classification result so it cannot be output completely, or an overly high `temperature` setting which causes unstable output.
- The third-party model cannot be called normally after configuration, and the page shows model loading failure or call timeout. This is caused by an incorrect `AIPROXY_API_ENDPOINT` that does not correctly point to the proxy address, or failure to enable call permissions for the corresponding model on the third-party platform.

## How to Confirm Proper Configuration
- Upload a real test ticket text, trigger a single call on the model configuration page, and check whether the returned classification results meet business expectations.
- The content filled in for `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` can be verified using standard HTTP request tools to test interface connectivity and confirm no access errors occur.
- Adjust the value of the `temperature` parameter, observe the classification results of multiple calls to the same ticket, and confirm that the output has no obvious random deviations.
- Simulate a batch ticket inflow scenario, check the latency of model calls, and confirm that no timeout errors affect business processes.

The values provided are common starting points and should be evaluated against local samples.
