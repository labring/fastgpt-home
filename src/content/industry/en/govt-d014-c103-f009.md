# Hotline Knowledge Base Maintenance: Hotline Knowledge Base and Ticket Assistance - Model Access and Configuration

## What the data for this category looks like
Data for hotline knowledge base maintenance comes primarily from historical hotline tickets, customer service standard script libraries, official policy documents, and user inquiry records.
Two update rhythms are used: on-demand updates and scheduled bulk updates.
On-demand updates trigger when policies adjust, new service items launch, or high-frequency inquiry questions change.
Full synchronization runs once weekly or every two weeks.
Single data entries have a document structure with fields including problem description, standard answer, ticket classification tags, accepting department, and handling time limit.
Fields have no unified fixed units. Some fields must match exclusive coding rules for administrative regions or business lines.

## Constraints for Model Access and Configuration
The multi-source mixed data structure requires model access to support parsing and retrieval of multi-format content, and adaptation to mixed input of structured ticket fields and unstructured scripts.
The high-frequency update feature requires model call context synchronization frequency to match the knowledge base update rhythm, to avoid content lag.
The rich set of business fields requires clearly specifying the field range for model calls during configuration, to prevent irrelevant information from interfering with model output.
The combination of professional terminology and colloquial language in hotline services requires model parameters to balance professionalism and communication approachability, to avoid overly rigid official scripts.

## How to Set Configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `maxContext` | 15000–20000 token | Accommodates multi-turn hotline conversation context and multiple retrieved knowledge base entries, avoids context overflow, and meets hotline service long-context requirements |
| `maxTokens` | 800–1200 token | Controls single-turn customer service reply length, adapts to hotline colloquial communication scenarios, and avoids overly long output that impairs readability |
| `quoteMaxToken` | 3000 token | Limits total length of knowledge base content retrieved in one call, ensures it stays within the model context window limit, and prevents content truncation |
| `toolChoice` | auto | Allows the model to independently determine whether to call knowledge base tools, adapts to multiple business scenarios including ticket classification, problem answering, and progress query |
| `temperature` | 0.6–0.7 | Balances reply professional rigor and colloquial approachability, aligns with hotline service communication styles, and avoids overly rigid or casual output |
| `AIPROXY_API_ENDPOINT` | Fill in the official access address provided by the platform | Matches network request path requirements for model calls, ensures requests reach the model service normally |
| `AIPROXY_API_TOKEN` | Fill in the exclusive token generated by the platform | Completes identity verification for model calls, ensures legitimate service access permissions |

## Three Common Configuration Errors
- A 403 error "This token does not have permission to use the model" appears when calling the model. This occurs when model permissions for the current FastGPT instance are not added to the token configuration on the model platform, or the model version bound to the token does not match the configured version.
- Generated customer service replies exceed the preset length. This occurs when the `maxTokens` parameter is not set correctly, or the total length of retrieved knowledge base content is not limited via `quoteMaxToken`.
- The model does not automatically call the knowledge base to complete the answer. This occurs when the `toolChoice` parameter is fixed to `none`, and the automatic tool call capability is not enabled.

## How to Confirm Configuration Is Complete
- Enter a common hotline question in the FastGPT model test interface, and verify that the returned result includes matching content fragments from the knowledge base.
- View the model call log, and confirm that the verification request for `AIPROXY_API_TOKEN` returns a 200 status code, with no permission-related errors.
- Adjust the `temperature` parameter and observe changes in the reply style, to confirm the parameter configuration takes effect.
- Simulate a multi-turn hotline conversation scenario, check that the context is loaded correctly, and no context overflow prompt appears.

The values provided here are common starting points, and should be evaluated against sample data from the target deployment.
