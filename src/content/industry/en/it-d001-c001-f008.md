# Code and Change Review Assistance for CDN and Edge Acceleration Configuration: Workflow Orchestration
This document applies to FastGPT v4.17.0.

## What the data for this category looks like
Data for this category comes primarily from CDN consoles, DNS resolution records, user access logs, and monitoring alert systems. Daily produced documents include domain name access forms, cache rule configuration tables, refresh and preheating operation records, and fault analysis reports.
Data updates occur either via daily synchronization or when a configuration change is triggered. Common fields include domain name, cache rule identifier, refresh and preheating volume, alert level, and node status. No fictional statistical figures or percentages are included.

## Constraints imposed by these characteristics on workflow orchestration
Data sources for this category are scattered. The workflow must connect to distinct APIs of CDN consoles, DNS resolution systems, and access log platforms. It must adapt to permission verification and return formats of each system.
Data updates trigger when configuration changes occur. This requires the workflow to support on-demand node execution to meet real-time synchronization needs.
Daily documents have inconsistent structural consistency. Domain name access forms are semi-structured forms. This requires the workflow to configure text extraction nodes to handle non-standardized fields.
The most time-consuming steps of domain name record verification and cache rule debugging require the workflow to string together multiple verification nodes. This reduces manual repetitive operations.
Public network access errors have direct consequences. The workflow must configure failure alerts and rollback nodes to ensure exceptions are blocked promptly.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `variables` | Define a global counter variable with an initial value of 0 and a step size of 1 | Adapt to the statistical requirements of CDN change counts |
| `nodeId` | Bind the unique identifier value of the corresponding cache rule verification node | Ensure accurate invocation of workflow nodes |
| Text extraction model | Select a general large model with a context window of no less than 8000 tokens | Adapt to text extraction from long-format cache rules and access logs |
| Workflow timeout threshold | Set to 300 seconds | Adapt to the response duration of CDN console APIs |
| Failure trigger action | Trigger an alert and pause subsequent nodes, with an alert delay of 60 seconds | Prevent incorrect configurations from impacting public network services |
| Variable scope | Limit to the current workflow instance | Avoid variable conflicts across workflows |

## Three common misconfigurations
- Phenomenon: No optional options appear in the model selection dropdown menu of the workflow text extraction node, making it impossible to configure extraction rules. Cause: The API key of the corresponding large model is not bound in the system's global configuration, causing the node to fail to load the optional model list.
- Phenomenon: The global counter variable does not update automatically after an AI response, and the value remains at the initial value. Cause: The update trigger node for `variables` is not correctly bound in the workflow, or the step size is not set to 1.
- Phenomenon: After importing an external workflow configuration, intermediate results do not match expectations, such as missing cache rule parameters. Cause: The variable scope is not specified in the `variables` configuration, leading to variable overrides across workflows.

## How to confirm the configuration is complete
- Manually trigger the workflow once, and verify that the text extraction node can correctly parse domain names and rule content in cache rule documents.
- Check the workflow logs to confirm that the global counter variable updates at the set step size after each AI response.
- Inspect the workflow debugging panel to confirm that the `nodeId` configuration of the code running node matches the actual node, and that logs display normally.
- Simulate a configuration failure scenario to verify that the workflow triggers an alert and pauses subsequent execution steps.
