# Code and Change Review Assistance for IT Service Desk Ticket Handling: Multi-turn Dialogue and Prompt Engineering

## What the data for this use case looks like
Enterprise IT service desk ticket processing data sources include ITSM systems, phone or chat logs, asset systems, and internal knowledge bases. Update frequency is daily or real-time. Daily generated documents include service request forms, incident tickets, processing records, and user satisfaction surveys. Each document includes fixed fields such as ticket number, submitter information, problem classification, fault symptoms, and processing progress.

## What constraints these characteristics impose on the multi-turn dialogue and prompt engineering link
Multi-source heterogeneous data sources require multi-turn dialogue to integrate ticket information across different systems. Prompts must clearly specify data extraction priorities to avoid missing critical content. Real-time updated ticket data requires session variables to sync the latest ticket status, preventing expired data from being used for change reviews. Ticket documents contain multiple fixed fields. Prompts must consistently extract key fields to ensure review consistency. The most time-consuming links include problem classification, remote troubleshooting, and escalation dispatching. Multi-turn dialogue must focus on the core issues of the current ticket to avoid interference from irrelevant content.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Store fixed configuration items in global variables, store temporary ticket data in session variables | IT service desk tickets have fixed default configurations (such as asset system interface addresses) and temporary data (such as current ticket ID). Separating storage prevents temporary data from being reset with each dialogue |
| `messages` | Retain the 20 most recent dialogue contexts | Ticket processing context typically focuses on recent interactions. Excessive old context increases retrieval and generation time |
| Maximum context token count | 8000–12000 token | Calibrated based on average ticket document length, multi-turn dialogue information density, and on-site testing |
| Historical Conversation Binding | Bind to the current `chatId` | Ensures context consistency for the same conversation, preventing cross-session data from interfering with current ticket reviews |
| Tool Call Context Limit | Associate only current ticket processing records per single call | Prevents irrelevant historical data from interfering with current ticket code and change reviews |

## Three Common Misconfigurations
- Symptom: Global default variables are lost in the conversation and cannot take effect continuously. Cause: Failed to distinguish between `variables` global variables and session temporary variables. Fixed configurations were written to session variables, causing variable content to reset with each dialogue.
- Symptom: Multi-turn dialogue responses slow down, and knowledge base retrieval takes more than 1 minute. Cause: Failed to limit the number of retained dialogue contexts for `messages`. Excessive historical conversations lead to context bloat, increasing computational overhead for retrieval and generation.
- Symptom: AI dialogue content remains after tool calls, making it impossible to directly obtain tool return results. Cause: Failed to disable unnecessary dialogue generation links in tool call configurations, causing tool call results to be overwritten or interfered with by additional AI replies.

## How to Confirm the Configuration is Correct
- Submit a test ticket, check if global default variables persist in the conversation and are not lost as dialogue rounds increase.
- Initiate 10 consecutive interactions related to the ticket, observe if response latency remains stable with no noticeable increase.
- Trigger a tool call, verify that the output only contains the ticket processing results returned by the tool, with no additional AI dialogue content.
- Switch to a new conversation window and initiate the same ticket question, confirm that the response speed of the new window is consistent with the first interaction.
