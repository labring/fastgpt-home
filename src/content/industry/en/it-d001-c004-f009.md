# Code and Change Review Assistance for IT Procurement and Supplier Management: Tool Calling and Plugins

## What this category of data looks like
This category covers end-to-end data for enterprise internal IT procurement and supplier management. Data sources include procurement systems, supplier quotations, budget sheets, and contract systems. Daily processed documents include procurement requests, price comparison records, contracts, and acceptance documents. Common document fields include procurement order number, supplier name, budget amount, contract clause number, and acceptance date. Data updates occur once per order or per month. The document volume involved in a single process typically ranges from hundreds to thousands of characters.

## Constraints on tool calling and plugin workflows
Since most data sources are internal enterprise systems, tool calling must adapt to internal permission verification rules to prevent unauthorized access to sensitive procurement data. Data updates are tied to individual procurement processes, so tool triggers must be bound to key stages of procurement workflows to align with data update rhythms. Different types of procurement documents have varying field structures, so tool calling must support dynamic matching of field rules for different documents. Tool call failures may lead to procurement delays or budget overruns, so a complete failure handling mechanism must be configured.

## Configuration Guidelines
This document is written for FastGPT v4.17.0. Below are configuration recommendations for tool calling and plugins:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Supports adaptation to calling requirements for different document types such as procurement requests and contracts |
| `functionCall` | `enabled` | Supports extraction of core fields from procurement data including budget and supplier information |
| Tool call trigger timing | Bound to procurement workflow nodes | Matches the update frequency of once per order or per month to avoid invalid calls |
| Failure retry count | 3 times | Offsets network or system fluctuations affecting single tool calls |
| Supplier record recall limit | Top 5 entries | Balances price comparison efficiency and data coverage |
| Document field mapping rules | Calibrated based on actual testing | Adapts to differences in field structures across different procurement documents |

## Three Common Misconfigurations
- Phenomenon: The review results returned by the API do not match the results in the platform test interface. Cause: The bound procurement knowledge base data source was not synchronized in the API call configuration.
- Phenomenon: The specified change review workflow cannot be triggered in multi-workflow scenarios. Cause: Independent trigger conditions for procurement document types were not configured for each workflow.
- Phenomenon: Local procurement documents cannot be uploaded for review during API calls. Cause: The document upload permission configuration for API calls was not enabled.

## How to Verify Successful Configuration
- Submit a simulated procurement request code review request, and check whether the API return results match the results in the platform test interface.
- Trigger the corresponding workflow for different types of procurement documents, and check whether the correct change review process is called.
- Upload a local procurement document in the API call scenario, and check whether document analysis and review can be completed normally.
- View the tool call logs, and check whether core fields from procurement data have been successfully extracted.
