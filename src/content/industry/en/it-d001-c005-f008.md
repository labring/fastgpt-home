# Code and Change Review Assistance for Issue Triage and Response: Workflow Orchestration

## What this category of data looks like
The data for this category primarily comes from GitHub or Gitee Issues, code repository version logs, environment information submitted by users, and problem reproduction descriptions. Daily maintained documents include Issue submission templates, tag classification rules, historical response records, and standardized problem descriptions. The data update frequency is daily or weekly. Core fields include Issue number, associated code modules, priority tags, reproduction steps, and response status, and only contains structured and unstructured content related to issue triage and response.

## Constraints imposed on workflow orchestration by these characteristics
The data sources for this category are scattered across code repositories and third-party platforms, requiring workflow configurations to support cross-source data fetch nodes and adapt to the access formats of different data sources. Differences in data update frequencies (daily or weekly) require workflows to have configurable flexible polling intervals or trigger mechanisms to match the synchronization rhythms of different data sources. The non-standardized nature of fields requires workflows to include built-in format verification and standardization conversion steps to ensure consistency of triage rules. The real-time response requirement for Issues requires workflows to support trigger-based execution to avoid delays caused by fixed-cycle polling.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Polling Interval | 600–1800 seconds | Adapts to daily or weekly updated Issue data sources, avoids frequent fetching that consumes system resources |
| Single Fetch Limit | Top 20 entries | Adapts to the processing scale of single-batch Issues, avoids node overload |
| Timeout Threshold | 300 seconds | Adapts to the average response duration of tool calls, avoids process blocking |
| Context Window | 8000 token | Adapts to the average length of Issue content, avoids exceeding model processing limits |
| Trigger Condition | On new Issue creation events | Matches real-time response requirements, reduces invalid polling executions |
| Variable Binding | `variables` binds Issue tag fields | Directly calls preset tag rules, no need to reconfigure classification logic |
| Node ID Configuration | `nodeId` binds core triage nodes | Precise control over workflow execution paths and branch jumps |
| Format Verification Threshold | Calibrated based on actual measurements | Adapts to differences in Issue templates across projects, avoids misjudging problem classifications |
| Log Output Level | Detailed mode | Facilitates troubleshooting of tool call or node runtime exceptions |

## Three common mistakes
- Symptom: Tool call node returns Invalid JSON: Bad control character error. Cause: Special characters in fetched Issue content are not escaped, resulting in invalid JSON format for generated call parameters.
- Symptom: No connection small circle appears on tool call nodes in the workflow editing interface, making it impossible to drag and create connection lines. Cause: Required field verification for node configuration is incomplete, or the function is not used in FastGPT v4.17.0 or later.
- Symptom: Unable to view detailed runtime logs for MCP services in the workflow. Cause: Log output level is not configured to detailed mode, or log collection function for the corresponding node is not enabled.

## How to confirm proper configuration
- Manually submit a test Issue that conforms to the project template, check whether the workflow automatically triggers the triage and response process.
- View workflow runtime logs, confirm that Issue fields bound via `variables` have been correctly passed to corresponding nodes, and no Invalid JSON errors occur.
- Check that node connection lines are displayed normally, confirm that the `nodeId` configuration has taken effect.
- View the model ID information in the advanced configuration area of the corresponding node, confirm that the correct service node has been bound.
- View detailed logs for the MCP service, confirm that the log output level has been configured to detailed mode.

The values provided are common starting points and should be measured against the reader's own samples.
