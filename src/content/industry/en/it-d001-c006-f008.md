# Code and Change Review Assistance for Pull Request Reviews: Workflow Orchestration

## What the data for this category looks like
This category of data primarily originates from code repositories, CI pipelines, Issue links, and change submissions from contributors. Associated daily documents include PR descriptions, code review comments, CI results, and merge records. Data fields include PR numbers, lists of changed files, review comment status, CI pass rates, contributor account information, and similar items. The update cycle is typically daily or weekly. The review data for a single PR completes its full lifecycle when the PR is merged or rejected.

## What constraints do these characteristics impose on workflow orchestration?
Decentralized data sources require workflow orchestration to integrate with multiple external interfaces such as code repositories and CI systems, and use `nodeId` to mark the execution order of different data source nodes. The update cycle limits the workflow’s trigger frequency: the workflow should only run when a PR is created, updated, or a merge request is initiated, to avoid unnecessary executions. The diverse range of field types requires the workflow to use `variables` to centrally store cross-node review data, enabling access in subsequent workflow steps. Additionally, the most time-intensive links, such as change intent confirmation and test result validation, must be split into separate sub-workflows to prevent overall process timeouts that would reduce review efficiency.

## How to configure the workflow
| Configuration Item | Recommended Setting | Rationale |
| ---|---|--- |
| Trigger Condition | When a PR is created, updated, or a merge request is initiated | Matches the event cycle of PR reviews to avoid unnecessary execution |
| Global Variable Storage | `variables` node | Uniformly manages review data and field mappings across workflow steps |
| Changed File Pull Limit | Top 10 entries | Controls the volume of data pulled per request to avoid timeouts |
| Process Timeout Threshold | 600 seconds | Adapts to the typical execution duration of CI pipelines |
| Merge Pre-check Rules | 100% CI pass rate, no unresolved review comments | Meets standard pre-requirements for PR merging |
| Secondary Review Trigger Condition | When more than 5 changed files are present | Adds additional validation steps for complex changes |
| Interface Compatibility Configuration | FastGPT v4.17.0 standard nodes | Ensures workflow compatibility with the platform version |

## Three common configuration mistakes
- Symptom: The workflow runs but does not return branch difference content for the specified project. Cause: No data source configuration for code repository branch comparison was added to the workflow orchestration.
- Symptom: The workflow cannot retrieve contributor names, only returning account IDs. Cause: No mapping was configured for code repository contributor public information fields via the `variables` node.
- Symptom: The thought process display in the guest chat window cannot be disabled. Cause: No parameter to hide the thought process was configured in the workflow’s chat node.

## How to verify the configuration is correct
- Manually create a test PR to trigger workflow execution, and check if the node logs pull the correct changed files and CI data.
- Review the stored content in the `variables` node to confirm that expected fields such as PR descriptions and review comments are present.
- Simulate a scenario with more than 5 changed files, and confirm whether the workflow automatically initiates the secondary review link.
- Check the guest chat window configuration, and confirm that the avatar and thought process switch have been set as required.

The values provided are common starting points and should be evaluated against local samples.
