# Code and Change Review Assistance for SLA and Service Reports: Tool Calling and Plugins

## What this category of data looks like
Data for this category comes from monitoring systems, ticket systems, contract documents, and customer communication records. The update frequency is monthly or quarterly. Daily produced documents include detailed SLA clauses, monthly service reports, availability statistics reports, and customer review minutes. Data fields cover SLA indicator items, statistical cycles, service event traceability identifiers, contractually agreed thresholds, etc. There is no fixed unified format, and the structure must be adjusted according to customer contracts and review requirements.

## What constraints these characteristics impose on the "tool calling and plugins" workflow
Data sources for this category are scattered, covering monitoring, tickets, contracts, and customer communication records. Tool calling must adapt to permission verification and format parsing rules of multiple types of systems. The update frequency is monthly or quarterly, and the volume of data processed in a single run is large. Tools must support batch pulling and full verification. Daily document structures have no unified standards, so plugins must support custom field mapping and caliber alignment logic. SLA indicator calculation and abnormal attribution require association of multi-source data. Tool calling must support cross-system data association queries to avoid statistical bias from a single data source.

## How to configure the setup
This configuration applies to FastGPT v4.17.0

| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| `toolChoice` | `auto` or specify a service report tool set | Clarify the scope of tool calls to avoid calling irrelevant tools that interfere with SLA indicator calculation |
| `functionCall` | Enable grouped by SLA indicator items | Accurately match the calculation logic of different indicators to reduce invalid calls |
| Data source interface timeout threshold | 300–600 seconds | Adapt to response delays of multi-source systems and avoid interrupting data pulling due to timeouts |
| Field mapping rules | Map one-to-one according to contractually agreed fields | Align report calibers to avoid statistical bias |
| Data verification trigger condition | Trigger after full data pulling is completed | Ensure data integrity within the cycle and prevent missing fields from affecting SLA calculations |
| Multi-source data association method | Associate by customer ID and statistical cycle | Accurately associate service events from different systems to support abnormal attribution |

## Three common misconfigurations
- Symptom: A garbled code error is returned when calling the dataset import interface to upload a CSV file, while the original file displays normally locally. Cause: The tool calling parameter for specifying the file encoding format is not included, resulting in encoding mismatch during cross-system transmission.
- Symptom: After calling the service report generation tool, there is no corresponding record in the call log, but service data pulling has actually been triggered. Cause: The full collection configuration for tool call logs is not enabled, and only core interface calls are recorded.
- Symptom: An error is reported when calling doc2x to parse large PDF files, while small files work normally. Cause: The single-processing file size threshold for tool calls is not adapted to large documents, exceeding the system's carrying limit.

## How to confirm the configuration is correctly set
- Initiate a test data pull to check whether the tool pulls data from the corresponding system according to the configured data source interface.
- View the tool call log to confirm that the tool set specified by `toolChoice` has been triggered, and no irrelevant tools are called.
- Verify the field mapping rules to check whether the pulled data fields are consistent with the calibers agreed in the contract.
- Trigger a full data verification to check whether the tool automatically executes the verification logic after data pulling is completed.

The values provided here are common starting points and should be measured against the reader's own samples.
