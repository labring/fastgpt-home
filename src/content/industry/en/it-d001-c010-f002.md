# Code and Change Review Assistance for Incident Response and Troubleshooting: Context and Token

## What Data Looks Like for This Category
Core data for this category comes from monitoring alerts, log platforms, APM tools, and user feedback. Daily processed documents include incident tickets, event timelines, emergency response plans, and incident notifications. Core fields include incident ID, occurrence time, impact scope, stop-loss operation records, and notification recipients.

Data updates use real-time synchronization of alert information. A complete incident document and disposal record are generated after each incident is triggered. There is no fixed batch update cycle. Latest alerts and disposal data must be prioritized to ensure timeliness.

## Constraints on Context and Token Workflows
Data in this category updates in real time, and the volume of associated documents for a single incident expands gradually as disposal progresses. The context and token workflow must adapt to dynamically changing input sources.

Document types such as incident tickets and timelines have large differences in field types. Associated fields must be accurately matched to extract valid information and avoid irrelevant data occupying token quotas. High-frequency pushes of real-time alerts may cause frequent context refreshes. The volume of valid data loaded in a single session must be limited to prevent request failures due to token overrun.

Additionally, compliance requirements for external notifications require that the context only contains confirmed disposal information, to avoid unvalidated content affecting decision accuracy.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | The total volume of associated documents for a single incident in this category is large, so sufficient token must be reserved to accommodate core disposal information and avoid truncation of critical incident and stop-loss content |
| `quoteMaxToken` | 1500–2000 characters | The length of individual records in incident tickets and timelines varies widely, so limiting token usage per single quote balances context completeness and request efficiency |
| Number of incident documents loaded per session | First 3–5 entries | Prioritize loading the latest alerts and disposal records to reduce token quota usage by non-core historical data |
| Context refresh interval | Calibrated based on actual testing | Adapt to the update rhythm of real-time alerts and avoid token consumption fluctuations caused by frequent refreshes |
| Context content filtering threshold | Retain content with a relevance score ≥70% to the current incident | Filter irrelevant historical alerts and non-associated documents to reduce invalid token usage |

## Three Common Configuration Errors
- Phenomenon: A token overrun error is returned during a call, with a response status code of 413. Cause: The `maxContext` quota was not adjusted for the real-time associated documents of this category, causing the token usage of a single request to exceed the preset limit.
- Phenomenon: A 404 error is returned when accessing a privately deployed FastGPT application. Cause: The application access context was not configured as `/fastgpt`, causing route matching failures and preventing normal loading of the application interface.
- Phenomenon: Search results do not associate context information for the current incident. Cause: Real-time alerts and event timeline content were not integrated into the context parameter of the search request, causing searches to generate results based only on general queries and fail to match exclusive information for the current incident.

## How to Verify Proper Configuration
- The FastGPT v4.17.0 application management backend can be accessed to review the configuration values of `maxContext` and `quoteMaxToken`, and confirm they fall within the preset ranges of 8000–12000 token and 1500–2000 characters.
- A test alert can be simulated to trigger context loading, then the number and content of loaded context documents can be reviewed to confirm only the first 3–5 latest core incident disposal records are included.
- The `/fastgpt` path of the application can be accessed to confirm the application interface loads normally with no route error prompts.
- A request based on a test incident ticket can be initiated, then returned results can be reviewed to confirm they associate context information for the current test incident, with no irrelevant content included.

The values provided are common starting points and should be evaluated against samples from the target deployment.
