# Code and Change Review Assistance for Incident Response and Troubleshooting: Source Citation and Traceability

## What this category of data looks like
The core data for this category comes from operation and maintenance monitoring alerts, log platforms, APM tools, and user feedback. Updates occur in real time or synchronize after a single incident is triggered. Associated daily documents include incident tickets, event timelines, emergency response plans, and incident notifications. Fields include incident number, impact scope, stop-loss operation records, notification time, and others. No additional statistical quantitative fields are included; only real operations and statuses across the full incident process are recorded.

## What constraints do these characteristics impose on the "source citation and traceability" link
Since data sources are scattered and updated in real time, citation and traceability must accurately match incident timestamps and operation contexts to prevent cross-incident confusion. Most daily documents are structured tickets and timelines, so support for quickly locating relevant knowledge base fragments by incident number is required. High update frequencies create version differences, so the time range of cited content must be limited. The core business goal of incident response is to restore service first, so the traceability link cannot consume excessive response time. This requires simplifying the retrieval process. Because the consequences of errors are severe, the confidence of cited content must align with business requirements to avoid citing irrelevant data and delaying stop-loss operations.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | 1000–1500 token | This category of data is mostly structured short text, and this setting balances context richness and troubleshooting response speed |
| Cited content time range | 30 minutes before and after the incident occurs | This category of data is updated in real time, which avoids introducing irrelevant historical data to interfere with judgment |
| Maximum number of recalled entries | Top 3 entries | Troubleshooting requires quickly obtaining core information; too many entries will prolong retrieval time |
| `detail` | Enabled | It is necessary to clearly indicate the source document and location of the cited content to facilitate subsequent incident post-incident review |
| `responseData` | Includes incident number, impact scope | Ensure that the corresponding incident ticket can be quickly matched during traceability, improving matching efficiency |
| Context filtering rules | Filter by incident tags | Avoid citing irrelevant data across incidents, which meets the accuracy requirements of incident handling |

## Three common errors
- Scenario: After setting `quoteMaxToken` to 1500 token, knowledge base fragments that exceed the length limit are still cited. Cause: The automatic single-fragment truncation configuration is not enabled, or the configuration is not bound to the dedicated retrieval process for incident response, resulting in over-length fragments not being filtered.
- Scenario: Matching fault-related documents exist in the knowledge base, but the retrieval results only return a citation prompt with no specific content. Cause: The context filtering rule for filtering by incident tags is not configured, causing matching results to be incorrectly judged as irrelevant data.
- Scenario: After connecting a code running node to the citation plugin, an error prompt pops up when clicking the input box. Cause: The input parameter format is not configured according to the FastGPT v4.17.0 plugin call specification, resulting in parameter verification failure.

## How to verify successful configuration
- Initiate a simulated incident retrieval, and check whether the returned citation and traceability information includes the incident number and source document location.
- Submit a test text that exceeds the preset maximum citation token count, and confirm that the system automatically truncates or filters the fragment.
- Trigger the plugin call process, and verify that the code running node can normally receive and process the parameter format returned by the retrieval.
- Adjust the cited content time range, and confirm that the retrieval results only include relevant documents within 30 minutes before and after the incident occurs.

The values provided here are common starting points, and should be evaluated against the user’s own samples.
