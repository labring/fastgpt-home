# Code and Change Review Assistance for Cloud Network and Load Balancer Configuration: Multi-turn Dialogue and Prompt Engineering

## What this category of data looks like
Data for this category comes from several sources: VPC planning documents exported from cloud platform consoles, security group rule lists, load balancer configuration files, plus network topologies, traffic monitoring reports, and architecture diagrams provided by relevant stakeholders.
Data updates sync with every change order or configuration order.
Each individual change corresponds to a set of structured fields. These fields include network segment ranges, port mapping rules, health check thresholds, access control policies, and other related items.
Field details vary slightly across cloud service providers. The core of all fields revolves around network connectivity and traffic distribution logic.

## Constraints imposed by these characteristics on multi-turn dialogue and prompt engineering
Data sources are scattered, and structure varies across cloud service providers. Multi-turn dialogue must support dynamic loading of configuration document fragments in different formats.
Updates trigger in real time alongside changes. Context windows must be limited to prevent interference from expired data.
Core fields include network segments, ports, and health check parameters. Prompts must accurately match the validation logic for these fields, to avoid generic questions.
Historical configurations linked to change orders must be traceable within dialogue. This allows reviewers to compare pre- and post-change configuration differences, and avoid missing key change points.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Maximum context | Retain the first 20 dialogue history entries | Avoid excessive historical content interfering with current change reviews, and align with the review rhythm of a single change |
| Single dialogue return limit | Match the first 10 configuration documents | Focus on configurations related to the current change, and avoid irrelevant data interfering with review judgments |
| `chatId` | Bind to the unique identifier of the current change order | Ensure dialogue context for a single scenario does not mix with other change orders, and maintain dialogue coherence |
| `variables` | Inject structured configuration fields of the current change order (single entry no more than 1000 characters) | Let the model directly access raw data awaiting review, without extra retrieval of redundant content |
| `messages` | Split dialogue turns by review phase | Follow the standard engineer workflow: confirm requirements first, load historical configurations, then perform validation checks |
| System prompt | Only validate specified fields for cloud network configurations | Target validation logic for network segment planning, security group rules, and health check configurations, and clarify the scope of responses |

## Three common mistakes
- Exceeding the expected limit of dialogue return results: The model returns too many irrelevant historical configuration documents. This occurs when the single dialogue return limit is not configured, leading to loading of redundant data.
- Failing to limit the dedicated validation scope for prompts: The model provides generic answers unrelated to cloud network configurations. This happens when clear validation rules are not set for network segment, security group, and health check configurations.
- Incorrect context binding: Dialogue contexts from different change orders interfere with each other, with incorrect cross-scenario references. This occurs when `chatId` is not used to bind the unique identifier of the current change order.

## How to confirm correct configuration
- Use the test environment of FastGPT v4.17.0, submit a test change order, and check if the dialogue automatically loads fragments of the corresponding configuration document. Verify that context association works correctly.
- Adjust the single dialogue return limit setting, submit the same test request, and check if the number of returned matching documents matches the set value.
- Switch the `chatId` of different change orders, confirm that the dialogue context is not disturbed by historical content from other change orders, and verify that the binding logic takes effect.
- Input a question outside the scope of cloud network configuration fields, check if the model rejects irrelevant answers, and verify the constraint effect of the prompt.
