# Code and Change Review Assistance for Cloud Network and Load Balancing Configuration: Workflow Orchestration

## What this category of data looks like
Cloud network and load balancing configuration data comes from cloud platform consoles, network topology files, traffic monitoring reports, and customer architecture diagrams. Daily maintenance documents include VPC planning sheets, security group rule lists, load balancing configuration files, and change tickets. Data is updated per change ticket. Each configuration contains fields such as network segment ranges, port mapping rules, health check thresholds, and backend server groups. Fields must comply with the format requirements of the corresponding cloud platform. Overlapping network segments or invalid port values are not allowed.

## What constraints these characteristics impose on the "workflow orchestration" link
Since data is updated per change ticket, and each change corresponds to a unique configuration set, workflows must be bound to change ticket trigger events. Only a single configuration set can be processed per run. Configuration fields have strict format requirements. Workflows must include pre-validation steps to filter incorrect configurations such as overlapping network segments and invalid ports. Data comes from consoles of different cloud platforms. Workflows must support adaptation to multiple cloud platform configuration formats to prevent review failure due to format differences. Additionally, configuration updates occur frequently. Workflows must pull the latest cloud platform baseline configuration in real time. Expired cached data must not be used.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Workflow trigger condition | Trigger on change ticket submission event, process one configuration set per run | Data is updated per change ticket, single change corresponds to a unique configuration set |
| Variable validation rules | Validate the validity of network segment ranges and port ranges, filter overlapping configurations | Configuration fields have strict format requirements; errors will cause review failure |
| Node execution order | Pull the current cloud platform configuration baseline first, then compare change content | Reviews must be based on the latest baseline to avoid outdated data |
| Timeout setting | 600 seconds | Cloud platform API pulling and configuration validation require a certain amount of time, calibrated based on actual testing |
| Result output format | Output review reports in HTML format | Adapt to the document format used by engineers for daily viewing |
| Node identifier | `nodeId` | Used to locate specific validation nodes in the workflow to ensure correct execution order |

## Three common mistakes
- The error prompt "Key is error. You need to use the app key rather than the account key" occurs because an account key is mistakenly used as the application API Key for authentication in a workflow node.
- No HTML output appears after the workflow runs. This is because the output format of the specified reply node is not configured correctly, or the node execution order is incorrect, causing the output step to not trigger.
- Failure to configure `AIPROXY_API_ENDPOINT` or `AIPROXY_API_TOKEN` will trigger an App/Admin service startup validation failure.

## How to confirm configurations are set correctly
- Check the environment variables on the App/Admin server. Confirm that `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are correctly configured and not empty.
- Trigger a workflow for a test change ticket. View the node execution logs to confirm that no errors occur in the configuration validation step.
- Cross-check the review report output by the workflow. Confirm that all configuration items and validation results for the current change are included.
- Check the workflow trigger conditions. Confirm that they are correctly bound to the change ticket submission event, with no duplicate or missing trigger rules.
