# Code and Change Review Assistance for Cloud Billing and Cost Accounting: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
The data for this category primarily comes from cloud billing systems, tag data, order systems, and resource monitoring platforms. Daily produced documents include billing details, cost allocation tables, resource utilization reports, and optimization suggestion sheets. Fields include billing items, resource IDs, tag values, allocation coefficients, consumption duration, and more. Units involve yuan, GB, hours, and others. The data update frequency is usually daily or monthly, with different update rhythms for different types of reports.

## What constraints these characteristics impose on the "multi-turn dialogue and prompt engineering" link
The data sources for this category are scattered and fields are diverse. Multi-turn dialogue needs to accurately pass context information from different systems to avoid confusing the field definitions of different reports. Since the data update frequency is daily or monthly, dialogue context should not retain data beyond the current billing cycle, otherwise analysis results will be disconnected from the latest data. Tag ownership verification and abnormal cost troubleshooting are the most time-consuming steps. Prompts need to guide dialogue to follow a fixed process step by step, and prioritize core tasks. At the same time, errors can trigger customer billing disputes or budget overruns. Prompts and dialogue logic must ensure the accuracy of data references, and must not arbitrarily assume field meanings.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale for This Setting |
| --- | --- | --- |
| Maximum context length | 8000–12000 token | Cloud billing and cost accounting data includes multiple detailed reports; overly long context will exceed the large model's window limit |
| Variable passing | Pass current billing cycle, resource tag rules, allocation coefficient template | Need to dynamically substitute category-specific business variables to ensure dialogue analysis matches the current business scenario |
| Dialogue context binding | Bind the unique identifier of the corresponding cost accounting project | Distinguish cost data of different customers or teams, avoid mutual interference of contexts |
| Prompt template optimization | Calibrate based on actual testing | Different teams have different cost analysis logic, need to match actual business processes |
| Multi-turn dialogue turn limit | Focus on tag ownership verification in the first 3 turns, handle abnormal troubleshooting in subsequent turns | The most time-consuming link for this category is tag ownership verification; prioritize core tasks to improve efficiency |

## Three Common Mistakes
- Calling the `api/v1/chat/completions` interface returns cloud resource billing data for non-target projects. Cause: Did not pass the tag rules of the corresponding cost project as context filtering conditions, so cannot accurately screen target data.
- When orchestrating vllm inference nodes, after entering a prompt and running, a 400 status code is returned. Cause: There are unclosed variable placeholders in the prompt template, or undefined fields unique to the cloud billing category are referenced.
- After orchestrating multiple AI large model dialogue nodes in a workflow, the total token consumption exceeds the limit. Cause: Did not bind an independent `chatId` for each dialogue node, causing context data to accumulate repeatedly and exceeding the large model's window limit.

## How to Confirm Configuration Is Complete
- Initiate a test dialogue, enter a question about tag ownership verification, check if the returned results only include resource tags and corresponding billing data for the target project.
- Submit a prompt containing variable placeholders, run the test node, confirm there are no 400 status code errors, and the returned results match the preset business logic.
- Orchestrate two independent cost analysis dialogue nodes, check that their respective context data does not interfere with each other, and the results correspond to different cost projects respectively.
- View the dialogue logs in FastGPT v4.17.0, confirm that each dialogue node is bound with an independent context identifier, and token consumption meets expectations.
