# Code and Change Review Assistance for Product Usage Data Analysis: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
This category's data primarily comes from tracking systems, data warehouses, CRM systems, and ticket systems. Most updates run on a daily or weekly schedule. Associated daily documents include product usage analysis reports, tracking plans, indicator definition tables, and dashboard requirement tickets. Data fields include customer ID, feature access frequency, operation duration, ticket request type, and more. Some fields require matching dedicated definition standards; there are no universal units, so adjustments must align with specific indicators. This category delivers cross-customer feature and behavior insights, differing from management categories focused on single-customer renewal health.

## How These Characteristics Impact Multi-turn Dialogue and Prompt Engineering Workflows
Multiple data sources require multi-turn dialogue to support cross-system data integration. Prompts must clearly specify call rules for each data source. Daily or weekly update cycles require prompt templates to adapt to batch data update rhythms, and avoid using outdated definition standards. Diverse document types require multi-turn context to associate content from different documents. For example, link tracking data to definitions in the indicator definition table. Special field rules require prompts to enforce field standard validation, to prevent incorrect indicator judgments. Cross-customer insight requirements require multi-turn dialogue to support filtering data by customer dimension, to avoid mixing behavior data from different customers.

## Recommended Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Bind dedicated data source variables for tracking systems, data warehouses, and CRM systems | Covers the multi-source data acquisition needs of this category, and ensures multi-turn dialogue can call content from different systems |
| `messages` | Retain the last 10 turns of dialogue context | Supports coherent interaction needs for multi-turn standard discussions and data troubleshooting during code and change reviews |
| Maximum context length | 8000–12000 characters | Matches the average document length of daily product usage analysis reports and indicator definition tables, and prevents content truncation |
| `chatId` | Bind unique session identifiers | Ensures multi-turn dialogue context is not lost, and maintains interaction continuity |
| Prompt template update frequency | Sync with indicator definition tables once per week | Adapts to the weekly update rhythm of this category's data, and ensures timeliness of definition standards |
| Multi-turn dialogue trigger rules | Calibrate based on actual testing | Adapts to differences in customer segmentation logic and business scenarios across clients |

## Three Common Misconfigurations
- Issue: After connecting an external dialogue interface, only the first dialogue turn runs, and multi-turn interaction fails to continue. Cause: The `chatId` parameter is not correctly bound, resulting in loss of session context for each dialogue.
- Issue: An error occurs where the deployed local model is automatically switched. Cause: No dedicated identifier for the local model is configured in `variables`, leading to incorrect scheduling logic matching.
- Issue: Input analysis reports or JSON data are truncated after exceeding limits. Cause: The maximum context length configuration is not adjusted, so the preset character limit is exceeded.

## How to Verify Successful Configuration
- Navigate to the application debugging interface of FastGPT v4.17.0, initiate a first turn of questions about indicator definitions, and verify that the reply links to preset definition table content.
- Initiate multiple consecutive questions, and observe whether the reply links to customer segmentation rules or data sources mentioned in previous dialogue turns.
- Submit a query containing multi-source data fields, and verify that the reply does not contain inconsistent standard descriptions.
- View session logs, and confirm that the `chatId` parameter remains consistent across each dialogue turn.
