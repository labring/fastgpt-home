# Code Review and Merge Management: Code and Change Review Assistance, Workflow Orchestration

## What This Category of Data Looks Like
Data for code review and merge management comes from Git repositories, CI pipelines, static scanning reports, and defect databases. Associated daily documents include merge requests, code review comments, commit records, and branch strategy descriptions. Data fields include merge request IDs, source and target branch information, commit hashes, reviewer identifiers, review comment statuses, static scanning defect severity levels, and more. The data update frequency is daily or per commit, generated throughout the full code change process, and only related to the current project’s codebase.

## What Constraints Do These Characteristics Impose on Workflow Orchestration?
The data characteristics of code review and merge management impose clear constraints on workflow orchestration. Data originates from real-time updated Git repositories, so workflows must use webhooks to trigger execution and match the real-time update rhythm of code commits. Data updates frequently, so workflow node execution duration must stay within a reasonable range to avoid blocking the review process. Data includes manual review steps, so workflows must support manual approval nodes to connect the business logic of automatic scanning and manual judgment. Data ties to the project-specific codebase, so workflows must bind to the corresponding project’s knowledge base and permissions to prevent cross-project data leaks. The most time-consuming change impact assessment step requires workflows to support parallel or serial configurations for automatic scanning and manual review, to optimize review efficiency.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Scope isolated by user ID | Matches the requirement of R&D teams isolating review variables by individual permissions to avoid global variable conflicts |
| Node trigger condition | Triggered by merge request status changes | Corresponds to the data update frequency after Git repository commits, enabling real-time startup of the review process |
| Knowledge base association | Bind project-specific datasets | Matches the business characteristic that code review only uses data from the current project’s codebase |
| Timeout duration | 300–600 seconds | Adapts to the average time required for static scanning and knowledge base retrieval during code review |
| Retry count | 2–3 times | Addresses temporary fluctuations in CI pipelines or Git interfaces, reducing the probability of process interruptions |
| `nodeId` | Match the interface node identifier exactly | Ensures correct execution order of workflow nodes and avoids confusion in process logic |

## Three Common Misconfigurations
- Phenomenon: When different R&D personnel use the same workflow, review variable values overlap between users. Cause: The `variables` configuration is not set to a user ID-isolated scope, and global variables are used.
- Phenomenon: Knowledge base retrieval in the workflow only triggers on the first review question, and subsequent questions cannot associate code data. Cause: Loop nodes are not configured to reuse retrieval logic, only one retrieval operation is performed, which does not match the business requirements of multi-round reviews.
- Phenomenon: Workflow node execution order is disrupted, and the review process terminates early. Cause: An incorrect node identifier is referenced when configuring `nodeId`, leading to errors in workflow scheduling logic.

## How to Verify Correct Configuration
- Log in to different R&D accounts to test if review variable display for the same merge request is isolated per account.
- Submit a simulated merge request to verify if the workflow automatically triggers execution after a status change.
- In the workflow settings panel of FastGPT v4.17.0, check that `nodeId` matches the interface node identifier exactly.
- View workflow run logs to confirm that the timeout duration and retry count configurations have taken effect, with no frequent timeouts or retry failures.
