# Code and Change Review Assistance for Supplier and Equipment Arrival Management: Tool Calling and Plugins

## What the data for this category looks like
Core data for this category comes from ERP systems, supplier shipping invoices, logistics tracking information, and device manufacturer backends.
Daily circulating documents include purchase orders, arrival acceptance forms, serial number lists, and invoice materials.
Data updates are grouped by single batch arrivals.
Weekly synchronization runs during a single project cycle.
Data fields include purchase-related order numbers, device models, device serial numbers, arrival dates, acceptance statuses, and supplier identifiers.
This category serves specific integrated project delivery.
It differs from enterprise IT procurement for all staff.
It updates only at delivery milestones, and has no additional custom statistical fields.

## How these characteristics create constraints for tool calling and plugin workflows
Dispersed data sources require separate configuration of access permissions for multiple interface types during tool calling. This avoids cross-system data confusion.
Single-batch data updates require binding purchase order numbers as context identifiers during tool calling. This ensures each call only associates arrival data for the corresponding batch.
Diverse document types require specifying the target document type during tool calling. This prevents accidental parsing of serial number lists as invoice content.
Model verification is the most time-consuming step. Real-time comparison of fields between purchase orders and arrival forms must run after tool calling. This intercepts mismatch risks early.
Delayed data updates may cause tools to return expired information. A timeout retry mechanism must be configured to ensure timeliness for acceptance processes.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | Adapts to multi-type tool calling scenarios, no manual specification of specific tools required, covers interface calling needs for ERP, logistics, device manufacturers, and other systems |
| Tool call timeout duration | `60-120 seconds` | Most data sources are internal systems and third-party logistics interfaces; this interval covers normal response times for most interfaces |
| Context binding identifier | Purchase order number | This category's data uses purchase orders as the core association dimension, preventing cross-order data confusion and ensuring call results accurately match the corresponding batch |
| Document parsing type | Auto-match by document suffix (.xml corresponds to serial number lists, .pdf corresponds to arrival acceptance forms) | Daily document formats are fixed; auto-matching reduces manual configuration costs and improves calling efficiency |
| Retry trigger threshold | First 2 call failures | Single interface fluctuations do not affect overall workflows; retries reduce the probability of data acquisition failure, aligning with the single-batch delivery rhythm of this category |
| Result verification rule | Compare device model fields between purchase orders and arrival forms | The most time-consuming step in this category is model configuration verification; this rule intercepts mismatch risks early and ensures delivery accuracy |

## Three common configuration errors
- Symptom: Empty results when calling a specified document parsing tool. Cause: No document type matching rule is configured, so the tool cannot identify the parsing target for serial number lists.
- Symptom: The HTTP call parameter field for optional parameters disappears when configuring a custom tool. Cause: Advanced parameter editing mode is not enabled in the tool configuration interface, so the configuration entry for optional parameters is hidden.
- Symptom: Java API calls remain in a waiting response body state. Cause: No reasonable timeout duration is set, or no timeout retry mechanism is configured, causing process blocking when an interface does not respond.

## How to confirm configurations are correctly applied
In FastGPT v4.17.0, configuration effectiveness can be verified through the following steps:
- Initiate a simulated call, pass test purchase order numbers and corresponding documents, and check if the tool returns correct device model and serial number information.
- Review tool call logs, confirm that the context-bound purchase order number matches the test data, with no cross-order data included.
- Trigger a failed simulated call, check if the retry mechanism activates as configured, and that retry counts meet expectations.
- Compare tool return results with fields from original purchase orders and arrival acceptance forms, confirm that the model verification rule functions normally.
