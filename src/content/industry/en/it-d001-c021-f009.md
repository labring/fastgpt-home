# Code and Change Review Assistance for Supply Chain Security and Open Source Dependency Governance: Tool Calling and Plugins

## What data this category includes
The data for this category comes primarily from package managers, code repositories, public vulnerability databases, and license databases. Update frequency is daily or when a new version is released. Daily generated documents include SBOM manifests, dependency risk reports, license compliance lists, and repair tickets. Fields cover dependency package names, version numbers, vulnerability CVE IDs, license types, impact scopes, and repair suggestions. Document formats vary slightly across different entities. Security teams prioritize vulnerability and license fields. R&D efficiency teams prioritize dependency versions and impact scopes. Data is stored in a structured manner by asset dimension, with no additional statistical values.

## Constraints Imposed on Tool Calling and Plugins Workflows
Data sources for this category are scattered, and update rhythms are flexible. Tool calling must support scheduled pulling of the latest package metadata, vulnerability, and license information to avoid using expired cached data. Multiple types of structured document outputs require plugins to adapt parsing logic for formats such as SBOM JSON and risk report CSV. Plugins must also support custom field mapping to match document differences across entities. The dependency identification and vulnerability matching process takes significant time. The number of dependency assets processed in a single tool call must be limited to prevent execution timeouts. Additionally, the risk of high-risk dependencies being deployed requires compliance checks to run before tool calling, to prevent unfiltered risk data from entering the review process.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` or `top 3 candidate tools` | Adapt to parallel tool calling needs in dependency governance scenarios, balancing coverage and execution efficiency |
| `functionCall` | `forced enable` | Ensure tool calls return structured results, simplifying parsing of SBOM and vulnerability report data |
| Number of dependencies processed per tool call | `50–100` | Match time constraints of the dependency identification process, avoiding execution timeouts |
| Tool call timeout duration | `120 seconds` | Align with average execution durations of vulnerability matching and upgrade impact assessment |
| Risk data pre-check | `enabled` | Filter invalid or expired dependency data, reducing review risks |

## Three Common Mistakes
- Tool calls return empty results, and logs show no matched dependency data. Cause: Incorrectly configured package manager data source, or the number of processed dependencies exceeds the limit, leading to execution interruption.
- Blank output occurs when calling chart tools in a workflow to generate dependency risk visualization results. Cause: `functionCall` forced structured output is not enabled, so unstructured data returned by the tool cannot be parsed and rendered.
- A 400 error is returned when calling an external data upload interface. Cause: Required fields such as dependency package name and version number are missing, or the submitted SBOM format does not meet parsing specifications.

## How to Confirm Correct Configuration
- Execute a dependency identification tool call in the FastGPT v4.17.0 environment, and verify that the returned results include core SBOM manifest fields such as package name, version number, and license information.
- Simulate a change review process to confirm that tool calls automatically intercept high-risk dependency versions and generate risk prompts.
- Review tool call logs to confirm that the timeout duration setting is active, with no interruption records caused by excessively long execution times.
- Submit non-compliant dependency data to verify that the pre-check switch triggers interception prompts.
