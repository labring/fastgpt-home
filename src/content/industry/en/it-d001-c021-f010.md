# Code and Change Review Assistance for Supply Chain Security and Open Source Dependency Governance: Citation Sources and Traceability

## What data for this category looks like
The data for this category primarily comes from package managers, code repositories, vulnerability databases, and license databases. Four core documents are routinely generated: SBOM lists, dependency risk reports, license lists, and repair tickets. The data update cycle is typically daily or aligned with software version releases. The core fields of the document structure are component identifier, version information, risk level, and license type. There are no uniform mandatory units, and fields vary slightly based on the data source type.

## What constraints do these characteristics impose on the citation sources and traceability link?
Data sources are scattered across multiple external systems. The traceability link must establish cross-source component identifier matching rules to avoid association errors. The high update frequency requires the traceability link to pull the latest dependency status in real time, preventing the use of outdated risk data in citations. Scenarios where multiple document types are used together require traceability to accurately link cited content to specific entries in the corresponding document. The lack of uniform units for fields requires adding field mapping rules during traceability to ensure component information from different sources can be correctly identified.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | Matches the average length of single dependency component information for this category, avoiding context overflow |
| `responseData` | Enabled | Synchronously returns the source document and component details corresponding to citations, meeting traceability requirements |
| `detail` | Enabled | Supplements fields such as component risk level and license type to improve traceability information |
| Multi-source matching threshold | Calibrated via actual testing | Adapts to component identifier differences across data sources, ensuring accurate cross-system association |
| Single recall limit | Top 10 entries | Covers traceability needs for core dependency components, avoiding interference from redundant information |

## Three common misconfigurations
- Phenomenon: The number of returned citation sources is insufficient to cover all core dependency components. Cause: The `quoteMaxToken` configuration value is too low, resulting in truncation of single citation content, or the single recall limit is set too small.
- Phenomenon: Citation sources cannot download corresponding document fragments. Cause: The `responseData` switch is not enabled, so the interface does not return traceable document identifiers and access paths.
- Phenomenon: Component traceability matching across package managers fails. Cause: No multi-source data matching rules are configured, so component identifiers from different sources cannot be aligned.

## How to verify the configuration is correctly applied
- Call the corresponding interface of FastGPT v4.17.0, check if the `responseData` field is present in the returned results, and that the field includes component identifiers and source document information.
- Adjust the `quoteMaxToken` configuration value, verify that the length of the returned citation content matches expectations.
- Import a test SBOM list, check if traceability results are linked to the correct component entries and corresponding documents.
- Check the `detail` switch status, confirm that the detail display function is enabled and can return supplementary information such as component risk levels.
