# Code and Change Review Assistance for Trusted Innovation Replacement Adaptation: Context and Token

## What the data for this category looks like
The core data for trusted innovation replacement adaptation comes from existing system inventories, domestic hardware and software directories, test environments, and vendor materials. Updates follow either a single project cycle or quarterly schedule. Daily deliverables include adaptation inventories, compatibility test reports, migration plans, and issue ledgers. Adaptation inventories contain fields such as original system components, domestic replacement components, and compatibility verification results. Test reports mark verification status using version numbers and test dates as units. The overall data structure is flexibly adjusted based on project requirements, with no unified mandatory format.

## How These Characteristics Create Constraints for Context and Token Handling
Data for trusted innovation projects is scattered and structurally flexible. Context loading must adapt to documents in multiple formats, to avoid losing key adaptation information due to format incompatibility. Update frequency is tied to project progress, and must align with the document refresh schedule for single projects or quarters. This prevents recalling outdated compatibility test results. Long-text documents make up a large share of the dataset, such as migration plans and full adaptation inventories. It is necessary to reasonably control token usage, ensuring the context window covers all critical content, and avoiding missing review information due to token overflow.

## How to Set the Configurations
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `maxContext` | 1.2–1.5 times the total character count of project documents (calibrated via actual testing) | Adapts to the total length of cross-system documents for trusted innovation projects, covering full project context scope |
| `quoteMaxToken` | 8000–12000 token | Matches the base context window of domestic large models, preventing recalled content from exceeding limits |
| Maximum response tokens | 4000–6000 token | Used to output complete code change review and compatibility assessment reports |
| Single search upper limit | Top 8 entries | Adapts to the typical number of entries in project documents, avoiding redundant recall of low-relevance content |
| Knowledge base refresh frequency | Triggered per project phase | Matches the quarterly update rhythm of test reports and adaptation inventories for trusted innovation projects |

## Three Common Misconfigurations
- Scenario: A 413 status code is returned when calling the code review API, and context content is truncated. Cause: The `maxContext` parameter is not adjusted to fit the total document length of the current project, exceeding the configured context limit.
- Scenario: Knowledge base content recalled during code change review includes outdated compatibility test results that are irrelevant to the current project. Cause: The knowledge base refresh frequency matching the project rhythm is not set, recalling old documents from prior quarters.
- Scenario: Adaptation inventory image links in the knowledge base are displayed incompletely, truncated to short addresses. Cause: The `quoteMaxToken` setting is too small, causing long links to be truncated during recall.

## How to Verify Configurations Are Properly Set
- Upload a single complete trusted innovation adaptation inventory document, test in FastGPT v4.17.0, confirm there are no content truncation prompts and all fields are fully loaded.
- Initiate a code change review request, verify that the recalled knowledge base content includes the current project's compatibility test reports and migration plans.
- Check the application runtime logs, confirm that the `maxContext` and `quoteMaxToken` parameters passed during API calls match the configured values.
- Test the output of long-text review results, confirm that the response content is not arbitrarily truncated and covers the complete assessment conclusions.
