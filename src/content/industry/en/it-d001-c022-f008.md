# Code and Change Review Assistance for Independent Innovation Replacement Adaptation: Workflow Orchestration

This documentation applies to FastGPT v4.17.0.

## What the Data for This Category Looks Like
The data for this category mainly comes from enterprise existing IT system inventories, official directories of domestic hardware and software, output results of project test environments, and publicly available manufacturer materials. The daily produced documents include four categories: adaptation lists, compatibility test reports, migration plans, and issue ledgers. Adaptation lists must record the version correspondence between existing systems and replacement hardware and software. Compatibility test reports must mark the compatibility status of individual nodes. The data update frequency is adjusted per single project or quarterly cycle. Incomplete migration projects must synchronously update existing system inventory data.

## What Constraints Do These Characteristics Impose on the Workflow Orchestration Link
Since data sources are scattered and update cycles are flexible per project, workflow orchestration must support dynamic access to multi-source heterogeneous data, and avoid hard-coding fixed data sources. Daily documents include multiple types of structured and unstructured content. Workflows must adapt to field parsing rules for different documents. For example, extract version fields from adaptation lists, and extract compatibility status tags from test reports. The migration risk assessment link relies on real-time data verification. Workflows must set pre-check nodes to ensure that existing system inventory and compatibility test data are synchronized before review. Otherwise, the review link cannot be entered. In addition, incorrect review results may cause issues such as unavailability of business systems. Workflows must add failure rollback and alert nodes to prevent incorrect content from triggering subsequent migration steps.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| Variable Definition | Associate data sources from existing system inventories and domestic hardware and software directories | Adapt to the scattered data source characteristics of this adaptation category, and avoid hard-coding fixed parameters |
| Node Trigger Condition | Match review node type by `nodeId` | Ensure that different types of reviews (such as compatibility review, version matching review) trigger corresponding processing logic |
| Context Call Limit | Top 10 entries | Adapt to the single-node data volume of compatibility test reports, and avoid excessive redundant information interfering with reviews |
| Timeout Threshold | 600 seconds | Match the average time consumption of the existing system inventory link, and prevent review processes from being interrupted due to data pull delays |
| Result Filtering Rule | Only retain entries with a compatibility status of "Pass" | Correspond to exception records in the issue ledger, filter invalid data to improve review efficiency |
| Workflow Trigger Method | Trigger by project ID in `variables` | Align with the feature of data updated per single project cycle, ensure each migration project corresponds to an independent review process |

## Three Common Misconfigurations
- Workflow judges always return non-empty results: No null value check rule is configured for the judge, and unfiltered data sources are directly used as the judgment basis. This causes the corresponding branch to trigger regardless of input content.
- Knowledge base references cannot be selected as variables in code run nodes: The workflow call permission of the knowledge base is not bound during the variable definition stage, or the knowledge base call switch is not enabled. This causes the variable list to fail to load knowledge base content.
- Project isolation rules are not configured when creating a workflow via API: The project ID in `variables` is not specified as a trigger condition via API. This causes multiple migration projects to share the same set of review logic, and cannot distinguish adaptation data for different projects.

## How to Verify Proper Configuration
- Log in to the FastGPT v4.17.0 workflow management page, view the currently configured variable list, and confirm that it includes data source fields from existing system inventories and domestic hardware and software directories.
- Submit a simulated review request, verify that the judge triggers the correct branch only when the matching review type's `nodeId` is present.
- View the workflow run logs, confirm that the timeout threshold setting aligns with the time consumption range of a single project cycle, and no premature interruptions occur.
- Enter the variable configuration interface of the code run node, confirm that the knowledge base call permission is bound, and that knowledge base content can be loaded normally.
