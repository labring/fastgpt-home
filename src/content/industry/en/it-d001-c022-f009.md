# Code and Change Review Assistance for Trusted Innovation Replacement Adaptation: Tool Calling and Plugins

## What data for this category looks like
This category of data is created and used by enterprise IT architects, domestic localization project teams, and system integrators. Daily maintained documents include adaptation lists, compatibility test reports, migration plans, and issue logs. Data sources cover existing system lists, domestic hardware and software directories, test environments, and vendor public materials. Update frequency is adjusted per individual project or quarterly. Data fields typically include hardware and software models, compatibility status, migration steps, exception records, and more. There is no unified mandatory format, and data must be organized to fit the actual project scenario.

## What constraints these characteristics impose on the "tool calling and plugins" link
Documents such as adaptation lists and compatibility test reports have limited structural completeness. Tool calling must support reading non-standard local or private documents, so plugins require custom parsing rules. Data updated per project or quarterly requires that tool calling supports dynamic switching of data sources, avoiding hard-coded fixed addresses for domestic hardware and software directories. The high time consumption of inventory system inventory and compatibility testing requires that the batch processing capability of tool calling adapts to multi-node parallelism. Exception record logs must support real-time synchronization to review processes, reducing the lag of migration risk assessment. It is also necessary to be compatible with test environment interfaces from different vendors, reducing additional development costs for cross-environment adaptation.

## How to configure the settings
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapts to scenarios where different adaptation tools are called dynamically during code review, no manual tool specification required |
| `functionCall` | `strict: true` | Enforces that tool call parameters conform to pre-defined adaptation document formats, reducing parsing errors |
| Document parsing rules | Match the field structure of adaptation lists | Fits the non-standard field formats of daily maintained adaptation lists and compatibility test reports |
| Batch call limit | Top 20 entries | Adapts to the scale of inventory system inventory data for a single project, avoiding interface overload |
| Timeout threshold | 300–600 seconds | Covers long-duration compatibility testing links, adapts to response delays in test environments |
| Data source switch | Enabled per project | Matches data update frequency per project, supports dynamic switching of domestic hardware and software directory data sources |

## Three common errors
- A 514 status code is returned when calling a tool. The cause is that access permissions for the adaptation data source are not configured, making it impossible to read domestic hardware and software directory or test environment data.
- Attempting to call a third-party API not registered in the adaptation list causes tool call failure. The cause is that compliant interfaces included in the domestic hardware and software directory were not used.
- When configuring a knowledge base search node in a workflow, a fixed knowledge base is used incorrectly, and variable references are not configured. This prevents dynamic switching of the knowledge base for the adapted project. The cause is that the requirement for data update frequency per project was not understood.

## How to confirm proper configuration
- Initiate a tool call test, check whether the returned results include core fields from the adaptation list, and adjust field matching rules according to the current project's adaptation list.
- Trigger a batch call process, confirm that the concurrency number and timeout threshold of tool calls match the operating status of the current test environment, and adjust parameters to match actual load.
- Switch the project data source, verify that the tool can correctly read the domestic hardware and software directory data for the corresponding project, and confirm that the data source switch is effective.
- Check the knowledge base search node in the workflow, confirm that variable reference parameters have been configured to receive externally passed knowledge base identifiers.
