# Code and Change Review Assistance for Duty Scheduling and Handover: Context and Token

## What This Category's Data Looks Like
Core data for this category comes from daily operations outputs of SRE teams and operations managers, including duty schedules generated by scheduling systems, handover records linked to fault tickets, escalation contact lists exported from organizational directories, and daily updated duty reports. Data update frequencies are divided into daily (duty schedules, duty reports) and weekly (escalation contact lists). Document structures include fields such as duty time slots, handover items, contact information, alarm trigger times, unresolved ticket numbers, and more. Data from different sources has minor field differences, with no unified standardized format.

## Constraints on Context and Token
This category’s data comes from scattered sources with inconsistent formats, and update cycles vary widely across different sources. When splicing contexts, timeliness of data must be distinguished to avoid outdated duty schedules or expired handover records occupying token quotas. Unresolved fault ticket numbers associated with items are key business information, which must be retained in full first to prevent token truncation from causing loss of key fields. Time-sequential duty time slot data requires contexts to be sorted by time, ensuring that corresponding events can be linked in duty order during reviews. Additionally, data volume grows with team scale, so total context length must be strictly controlled to avoid call failures due to exceeding token limits.

## How to Configure
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the total length of duty scheduling-related documents, including multiple sets of data such as duty schedules, handover records, and escalation lists |
| `quoteMaxToken` | 1500–2000 token | Prioritizes retaining complete content of unresolved handover items and associated fault tickets, preventing key fields from being truncated |
| Maximum Context Sorting | Time descending order | Matches the time-sequential data characteristics of duty scenarios, prioritizing displaying the latest handover records and duty arrangements |
| Context Update Frequency | Daily synchronization | Matches the daily update cycle of duty schedules, avoiding outdated data occupying token quotas |
| Single Recall Limit | Top 5 entries | Controls token consumption while covering core duty and handover data from the past week |

## Three Common Misconfigurations
- Phenomenon: After internal deployment, system logs display a token verification failure prompt, and abnormal restarts occur during startup. Cause: No context synchronization whitelist for internal data sources is configured, and the system attempts to pull external resources, triggering the default token verification rule, leading to call failure.
- Phenomenon: After configuring a custom openAPI token, the token consumption of the code review assistant is still counted under the default account. Cause: The custom token is not bound to the context call permissions of the duty scheduling scenario in system settings, so the system still uses the default quota.
- Phenomenon: The handover records returned by the code review assistant lack the unresolved ticket number field. Cause: The `quoteMaxToken` setting is too small, truncating the handover record content containing key fields, leading to loss of core business information.

## How to Confirm Successful Configuration
- View the system configuration logs of FastGPT v4.17.0 to confirm that the `maxContext` and `quoteMaxToken` configuration parameters have been loaded correctly.
- Manually trigger a handover record retrieval task, and check that the token occupancy of the returned content matches the preset `quoteMaxToken` value range.
- Compare context data from different time periods to confirm that retrieval results are sorted in time descending order, with the latest duty arrangements and handover records displayed first.
- Test the data source synchronization process in an internal network environment to confirm that no error prompts related to token verification appear.
