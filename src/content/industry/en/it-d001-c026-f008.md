# Code and Change Review Assistance for Level Content Creation: Workflow Orchestration

## What the data for this category looks like
The data for this category mainly comes from level editors, art resource libraries, player test data, and defect systems. Daily output documents include level design drafts, resource requirement sheets, test feedback forms, and version submission records. Data fields cover level path node coordinates, resource mount identifiers, test feedback level node numbers, version submission change hashes, and more. The data update rhythm is weekly iterations or synchronization before each version release. Core data is generated around specific map layouts, task trigger logic, and resource placement rules.

## What constraints these characteristics impose on the "workflow orchestration" link
Data sources are scattered, and update rhythms fluctuate with versions. Workflow orchestration must adapt to format alignment requirements for multi-source data. Level design drafts and version submission records have large field differences, so unified data mapping rules must be set in the orchestration. Player test data and defect system feedback contain unstructured content, so preprocessing nodes must be added to the workflow to filter invalid information. At the same time, version submission change hashes must be bound to review nodes to ensure each review corresponds to clear code or resource changes, preventing a disconnect between review content and actual submitted content. The centralized update rhythm of weekly or per-version updates requires the workflow to have the ability to batch process multiple related documents, avoiding excessive single-review time that affects version delivery progress.

## How to Configure Settings
| Configuration Item | Recommended Practice | Rationale |
| ---- | ---- | ---- |
| Global variable binding | Bind boolean fields in `variables` | Adapt to the review node's need to judge level status, ensure switch status syncs with the current version's level configuration |
| Node ID binding | Bind the `nodeId` field | Ensure review nodes correspond one-to-one with specific change entries, avoid review confusion |
| Trigger condition configuration | Trigger based on version submission change hashes | Align with the business rule that every change in this category requires review, avoid invalid reviews |
| Multimodal recognition settings | Enable image recognition | Recognize layout screenshots exported from level editors, help reviewers quickly locate resource placement issues |
| Tool output processing | Hide tool call results | Avoid redundant information in the review process interfering with core review logic |
| Retry threshold setting | 3 retries, 60-second interval | Address disconnection issues during MongoDB replica set primary node switching, ensure stable data pulling |
| Batch processing limit | First 10 related documents | Adapt to weekly or per-version update rhythms, avoid overload from single workflow processing |

All configuration items are formulated based on the functional logic of FastGPT v4.17.0.

## Three Common Misconfigurations
- The workflow judge node cannot correctly recognize the boolean global variable status in `variables`. The cause is that the target variable is not bound to the judge node's condition configuration, causing the judge logic to fail to read the corresponding status.
- After enabling image recognition in the multimodal recognition node, a prompt indicating that image content cannot be provided is returned. The cause is that no image format verification step is configured in the workflow, so non-standard format level layout screenshots cannot be parsed correctly.
- A MongoDB connection interruption and automatic reconnection failure error occurs during workflow runtime. The cause is that no reconnection logic is configured for the replica set primary node switching scenario, so the connection cannot be restored after the primary node drifts.

## How to Confirm the Configuration is Complete
- Submit a test version submission record, check whether the workflow automatically triggers the review node.
- Upload a standard format screenshot exported from the level editor, confirm that the multimodal recognition node can return valid parsing results.
- Configure boolean global variables in `variables` with different values, verify whether the switch logic of the judge node triggers correctly.
- Run a tool call process, confirm that the call results are not displayed in the interface, only core review content is retained.
