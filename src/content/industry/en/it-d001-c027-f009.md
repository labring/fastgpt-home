# Code and Change Review Assistance for Content Moderation Rule Operations: Tool Calling and Plugins

## What this type of data looks like
Core data for content moderation rule operations includes moderation rules, disposal guidelines, appeal records, and quality inspection reports. Data sources include content moderation backends, user reporting channels, public regulatory policy documents, and custom sample libraries. Data updates occur daily, or when policy changes trigger updates. Core daily processing links include rule interpretation, difficult sample determination, and appeal review. Data processing deviations may lead to the spread of violating content, harm to creators, or regulatory rectification requirements.

## What constraints do these traits place on the "tool calling and plugins" workflow
Scattered and frequently updated data sources require tool calling to support multi-data-source pulling and real-time synchronization. This avoids using expired moderation rules or sample data. Varied document structures include structured rule entries and unstructured appeal records. Plugins must adapt to data parsing for different formats. Core processing links account for a high proportion of total time. Tool calling must cover scenarios such as rule interpretation and batch sample determination to improve processing efficiency. Processing deviations can cause serious consequences. Tool calling must be configured with strict parameter verification and failure handling mechanisms to ensure data processing accuracy and compliance.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Allow the tool to automatically determine whether to call plugins to process moderation rule-related tasks |
| `functionCall` | `enabled` | Enable structured function calls to ensure returned moderation rule parsing results conform to preset formats |
| Plugin call timeout threshold | `300 seconds` | Match typical time spent pulling and parsing moderation rule data, avoid unnecessary timeouts from network delays |
| Plugin retry count | `2 times` | Balance call success rate and resource consumption, address call failures caused by temporary network fluctuations |
| Plugin data source filtering rules | `Only pull moderation rules updated on the current day` | Align with daily or policy-triggered data update frequencies, avoid using expired rules |
| Tool calling permission scope | `Only access content moderation backend APIs` | Limit data access boundaries to ensure the security of moderation rule data |

## Three common misconfigurations
- Empty structured results or unformatted text are returned after tool calling. Troubleshooting: Check whether the `functionCall` parameter is set to `enabled`.
- Authentication failure is returned when calling the external application API. Troubleshooting: Check whether the AI Proxy admin Token is mistakenly used as the application API Key for authentication.
- The content extraction node fails to load moderation rule data from the self-built model interface. Troubleshooting: Check whether model channel configuration is confused with AI Proxy environment variables, and upstream model supplier credentials and addresses are not configured through the model channel page.

## How to confirm the configuration is set correctly
- Check the App/Admin server environment variables for FastGPT v4.17.0. Confirm that `AIPROXY_API_ENDPOINT` (root address of the AI Proxy service) and `AIPROXY_API_TOKEN` (admin token matching the AI Proxy server configuration) are correctly configured and not empty.
- Trigger a tool call. Verify that the returned result includes structured moderation rule parsing fields to confirm the `toolChoice` and `functionCall` parameters are active.
- Simulate a data update scenario. Confirm that the plugin can pull moderation rules updated on the current day to verify the data source filtering rules are active.
- Disconnect the network and trigger a tool call. Confirm that the system triggers the retry mechanism and returns a clear failure prompt to verify the timeout and retry configurations are active.

The values provided are common starting points and should be measured against the reader's own samples.
