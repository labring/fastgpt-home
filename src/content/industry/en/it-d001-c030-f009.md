# Code and Change Review Assistance for Internal Network and WiFi Operations: Tool Calling and Plugins

## What this category of data looks like
Business data for internal network and WiFi operations comes primarily from switch consoles, wireless controllers, office monitoring systems, and frontline user trouble reporting channels. Daily produced documents include network topology diagrams, change tickets, fault records, and wireless coverage inspection forms. Data is updated daily or synchronized with individual network changes. Data fields include port numbers, VLAN configurations, wireless signal strength, fault reporting times, and other items. No standardized additional statistical metrics are used.

## What constraints these characteristics impose on tool calling and plugin workflows
Since data sources include hardware consoles and user trouble reports, tool calling must adapt to multiple data source interfaces. It cannot rely on generic text parsing logic. Data updates occur daily or when changes are triggered. Plugin polling intervals must match this update rhythm to avoid excessive system resource consumption. Daily documents include structured content such as topology diagrams and change tickets. Tools must support parsing specific formats of operations documents to extract valid fields. Fault location and VLAN verification are the most time-consuming steps. Tool calling must first trigger the pulling of corresponding device data. A failure retry mechanism must be configured to address the risk of office network interruptions.

## How to Configure Settings
This configuration is based on FastGPT v4.17.0, and is adapted for code review scenarios for internal network and WiFi operations:

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | Automatically routes across multiple operations data sources such as switches and wireless controllers, and supports multi-tool linkage requirements in code reviews |
| `functionCall` | `enabled` | Forces tool calling to ensure core operations data such as switch port and VLAN configurations can be pulled |
| Tool call timeout threshold | `300–600 seconds` | Network device data pulling typically requires long response times. This avoids prematurely timing out and interrupting the review process |
| Plugin polling interval | `Every 15 minutes` | Matches the daily or change-triggered data update rhythm, and prevents invalid polling from consuming system resources |
| Context window length | `8000–12000 characters` | Accommodates long-text operations documents such as network topology diagrams and fault records, and ensures complete parsing of critical information |
| Data source mapping rules | Grouped by device type | Differentiates between different data sources such as switches and wireless controllers, and improves the accuracy of tool calling |

## Three Common Configuration Mistakes
- The symptom is a grayed-out tool call button, with the interface prompt "Tool calling not enabled". The cause is configuring the `toolChoice` parameter as `none`, which does not enable tool calling permissions.
- The symptom is empty results returned after calling a search plugin, with no network fault information pulled. The cause is incorrect data source mapping configuration. The plugin is not linked to a valid interface for a switch console or wireless controller.
- The symptom is a failed locally deployed model call, with logs showing parameter mismatch. The cause is that FastGPT v4.17.0 adjusted the trigger logic for `functionCall`, and existing configuration parameters were not updated synchronously.

## How to Confirm Correct Configuration
- Submit a simulated network change review request, and check the tool call logs to confirm whether switch port or wireless controller configuration data was successfully pulled.
- Enter the plugin management page, check the connection status of each operations data source, and confirm there are no abnormal error or disconnection prompts.
- Upload a fault record document, trigger tool calling, and confirm that the parsed results include corresponding VLAN configurations or fault location information.
- Simulate a long-text data pulling scenario, and verify that tool calling completes responses within 300–600 seconds, with no timeout errors triggered.
