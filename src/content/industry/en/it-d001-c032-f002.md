# Code and Change Review Assistance for Creator Incentive Settlement: Context and Token

## What the data for this category looks like
Data for creator incentive settlement comes from content data, advertising revenue sharing systems, financial systems, and account backends. Daily maintained documents include incentive rules, settlement details, appeal records, and payment lists. Common fields include creator identifiers, revenue accounting calibers, settlement cycles, appeal statuses, and payment amounts. Units are usually yuan, person-times, and similar. Data updates happen monthly or aligned with activity cycles. Single-batch document volume fluctuates with activity scale. Core documents are mostly batch-generated structured data.

## Constraints on context and token management
Structured batch documents, cross-system data sources, and monthly/activity-aligned updates create multiple constraints for context and token management. First, single batches of settlement details and appeal records use high token amounts. Total context token volume must be strictly limited to avoid exceeding model limits. Second, cross-system data has inconsistent formats. Field structures must be unified during context loading to prevent parsing errors. Third, infrequently updated incentive rules do not need frequent context refreshes. Real-time settlement data must be recalled quickly during reviews. Unrelated data must be excluded to avoid excessive token usage that slows review efficiency.

## Configuration settings
| Configuration Item | Recommended Values | Rationale |
| --- | --- | --- |
| `maxContext` | 10000–12000 token | Covers the total token volume of a single batch of settlement details, appeal records, and incentive rules, to avoid exceeding the context limit of general large models |
| `quoteMaxToken` | 3000–4000 token | Adapts to the token length of a single settlement detail or appeal record, ensuring core fields are not truncated |
| Context refresh trigger timing | Triggered per activity or monthly | Matches the category's data update frequency, reducing unnecessary context refresh operations |
| Associated document recall limit | Top 6 entries | Controls the total token volume of documents recalled in a single operation, balancing completeness of associated data and token usage |
| Single document load timeout threshold | 120 seconds | Adapts to the typical time required to pull financial and account backend data across systems, preventing request interruptions |

## Three common misconfigurations
- A 422 status code is returned during calls, with an error message containing "Messages token length must". The cause is failure to limit the total token volume of `maxContext`, leading to passed context exceeding model support limits.
- Context data related to creator appeals is lost during multi-turn code review sessions. The cause is failure to bind core documents such as settlement details and payment lists to context persistence configurations, only temporarily loading data for single-turn requests.
- A parameter error occurs when calling the model after a judge in a workflow. The cause is failure to filter historical settlement data unrelated to the current review, leading to context token usage exceeding the configured limit.

## How to verify correct configuration
- On the workflow configuration page of FastGPT v4.17.0, check if the configured values for `maxContext` and `quoteMaxToken` fall within the preset ranges.
- Submit a simulated code change review request, verify that the context module loads complete incentive rules, corresponding settlement details, and appeal records.
- Trigger a cross-system data pull operation, confirm that request duration does not exceed the configured timeout threshold, and no interruption-related errors occur.
- Run multi-turn review tests, verify that context data remains complete across multiple sessions, with no field loss or truncation.
