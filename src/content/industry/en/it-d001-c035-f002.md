# Code and Change Review Assistance for Unit and Component Testing: Context and Token

## What Data Is Included in This Category
Data for this category primarily comes from code repositories, test framework reports, requirement specifications, and interface definitions.
Update frequency is daily or per code commit.
Daily associated documents include test cases, coverage reports, Mock documentation, and defect tickets.
Test cases contain case identifiers, preconditions, execution steps, and validation rules.
Mock documentation contains dependent interface definitions and mock return rules.
Defect tickets contain associated commit hashes and test phase identifiers.
Most data fields are tied to code commit or test execution actions, with no redundant cross-stage associated fields.

## Constraints Imposed on Context and Token Handling
The high-frequency update nature of this category’s data requires context to sync the latest test cases, Mock documentation, and defect tickets. This prevents use of expired test configurations or execution records.
Data tied to code commits requires context to associate test data with the corresponding commit. This prevents cross-version test logic confusion.
The decentralized document structure requires limiting recalled document types. Only test cases, coverage reports, and Mock documentation related to unit and component testing should be included. This avoids irrelevant data consuming token space.
Data scale increases alongside code commit volume. Strict controls must be placed on the number of recalled entries and total context token count. This prevents exceeding the model’s capacity limits.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `maxContext` | 16000–32000 token | Matches the context capacity limits of current mainstream large models, and adapts to the multi-document recall needs of unit and component testing |
| Single search recall limit | Top 8 entries | Controls token consumption per recall round, avoiding exceeding the `maxContext` limit |
| Chunk length | 800–1200 characters | Adapts to the typical content length of test cases and Mock documentation, reducing invalid associations after chunking |
| Overlap length | 100–200 characters | Ensures cross-chunk test logic associations are not truncated |
| `quoteMaxToken` | 2000–4000 token | Limits the maximum token count for a single recalled document, preventing single entries from occupying excessive context space |
| Similarity threshold | Calibrated via actual testing | Adapts to semantic matching accuracy for test data, avoiding recall of unrelated test cases or defect tickets |

## Three Common Misconfigurations
- Symptom: A "Reached the max retries per request limit" error is triggered during invocation. Cause: Incorrect association with the context update frequency of test data, leading to frequent retry validation checks that exceed the request retry limit.
- Symptom: Token consumption per single conversation exceeds expectations. Cause: No `quoteMaxToken` limit is set, and overly long coverage reports or defect ticket data are recalled, resulting in excessive token usage.
- Symptom: The number of recalled test case results is abnormal. Cause: The single search recall limit is not properly configured, leading to recall of excessive irrelevant data, or the similarity threshold is set too low, resulting in recall of non-target test cases.

## How to Verify Proper Configuration
This verification process is compatible with FastGPT v4.17.0:
- Review system logs to confirm that all recalled document types are test cases, Mock documentation, coverage reports, and defect tickets, with no irrelevant data included.
- Cross-check token consumption data for single conversations to confirm they do not exceed the `maxContext` limit. Adjust values based on actual test data scale as needed.
- Submit a single code change to trigger the review assistance workflow. Confirm that recalled test data is associated with the current commit, with no cross-version historical data included.
- Simulate a review of boundary condition test cases. Confirm that recalled relevant test data covers the corresponding boundary scenarios.

The values provided are common starting points and should be measured against the reader's own samples.
