# Code and Change Review Assistance for Unit and Component Testing: Multi-turn Dialogue and Prompt Engineering

## What data for this category looks like
Relevant data for unit and component testing comes primarily from code repositories, test framework reports, requirement specifications, and interface definitions. Associated daily documents include test cases, coverage reports, Mock instructions, and defect tickets. Data updates occur daily or each time code is submitted. Each data entry includes fields such as code snippets, test expected results, coverage metrics, Mock dependency descriptions, and more. There are no unified fixed units; values adjust based on the test framework and project standards.

## Constraints imposed on multi-turn dialogue and prompt engineering by these characteristics
Data sources are scattered and updates are frequent. Multi-turn dialogue must associate the latest code commits and test reports in real time. Prompts must clearly specify the time range and source type of data.
Daily document types are diverse. Prompts must distinguish usage scenarios for different documents such as test cases and coverage reports to avoid confusion over field meanings.
Data entry fields adjust per project. Multi-turn dialogue context transfer must support dynamic loading of specified fields to avoid redundant information interfering with dialogue logic.
Change reviews must associate all relevant test data for a single commit. Prompts must limit context scope to ensure review results focus on the current change content.

## Configuration settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Session ID (`chatId`) | Generate a unique identifier for each conversation | Used to associate multi-turn dialogue context, ensuring historical test data is bound to the current review task |
| Message List (`messages`) | Retain the most recent 20 rounds of conversation content | Covers historical test cases and change records required for current reviews, avoiding context overflow |
| Variable Configuration (`variables`) | Pass the current project's test framework version and code repository address | Enables prompts to adapt to project-specific testing specifications and data formats |
| Advanced Configuration Permissions | Enable custom prompt templates | Adapts to dedicated review logic for unit and component testing. Only supported in FastGPT v4.17.0 and later versions |
| Context Length | 8000–12000 token | Balances completeness of test data and dialogue response speed, calibrated via actual testing |
| Session Tracking | Enable log recording | Facilitates subsequent troubleshooting of parameter configuration issues during the review process |

## Three common mistakes
- Session logs do not display conversation records associated with the `chatId` parameter when calling the API. This occurs when the request body does not correctly carry the `chatId` field, or when session tracking configuration is not enabled.
- Custom prompt templates cannot be edited, and only simple parameters can be adjusted. This occurs when the FastGPT version is lower than v4.17.0, and advanced configuration permissions are not available.
- Form nodes in the dialogue interface do not render as expected. This occurs when form structure parameters are not defined in `variables`, or form variables are not correctly referenced in the prompt template.

## How to confirm configurations are properly set
- Initiate a test case generation request, check whether the returned results include project-specific test parameters defined in `variables`.
- View the FastGPT backend session logs, confirm that the `chatId` parameter has been correctly recorded and associated with the current conversation.
- Trigger a review after submitting code changes, verify that multi-turn dialogue automatically loads the latest test framework report data.
- Modify and save the prompt template, initiate a new review request, confirm that the new template content takes effect.
