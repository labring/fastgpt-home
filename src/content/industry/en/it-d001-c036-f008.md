# Code and Change Review Assistance for Prototyping and Interaction Design: Workflow Orchestration

## What the Data for This Category Looks Like
Typically, core data for prototyping and interaction design comes from Figma or Axure files, internal team design systems, user feedback, and usability test records. Daily deliverable documents include interactive prototypes, page flowcharts, component descriptions, and review records. Data updates follow weekly or per-version iteration cycles. Data fields include page node layouts, interactive action configurations, component attribute descriptions, review opinions, and modification statuses. No unified fixed standardized fields exist, and they adjust based on team design specifications.

## What Constraints These Characteristics Impose on Workflow Orchestration
Because data sources rely on exported files from design tools such as Figma and Axure, the workflow must support parsing unstructured design files, and dedicated format compatibility nodes must be configured. Data updates occur weekly or per version, so workflow triggers must be bound to version update or file upload events. Documents focus on page structure and operation paths, so the workflow must center on interactive logic verification and review status transitions. Broad requirement text processing is not required. Status changes to review records must act as trigger conditions for process branches, which increases the configuration complexity of branch judgments.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale for This Setting |
| --- | --- | --- |
| Trigger Node | Set to file upload/version update node | Matches the primary update sources of prototyping and interaction design data |
| `variables` | Bind the modification status field of review records | Enables process branch jumps based on review status |
| Knowledge Base Recall Limit | Top 5 entries | Adapts to the concise content volume of interaction design documents, avoids redundant recall |
| `nodeId` | Bind the unique identifier of the AI chat node | Associates AI node output with context content |
| Timeout Threshold | 600 seconds | Covers the average time range for prototype file parsing and knowledge base search |
| Context Length | 800–1200 characters | Matches the conventional content length range of single-page interactive prototypes |

## Three Common Misconfigurations
- After the workflow calls knowledge base search, returned results do not match prototype interaction content. Cause: The `variables` are not bound to the interaction keyword field of the prototype file, so the recall scope does not focus on the core content of the design document.
- The workflow cannot obtain the node value returned by an MCP tool call. Cause: The unique identifier of the tool node is not correctly specified in `nodeId`, so the context cannot associate with results returned by the tool.
- The AI node system prompt does not adapt to the interaction design review scenario. Cause: Generic business prompts are used directly, without adding exclusive rules for prototype verification and interactive logic compliance judgment.

## How to Verify Proper Configuration
- In the FastGPT v4.17.0 workflow editor, a test Axure prototype file is uploaded, the workflow is triggered, and whether subsequent knowledge base search and AI verification links start automatically is checked.
- Fields bound to `variables` are checked to confirm they correctly display prototype interactive actions, component attributes, and similar information.
- After an MCP tool is called, the workflow context is checked to confirm it carries the parsing results returned by the tool.
- The context length parameter is adjusted to verify that output content matches the information coverage range of a single-page prototype.

The values given here are common starting points and should be measured against the reader's own samples.
