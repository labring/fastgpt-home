# Code and Change Review Assistance for Prototyping and Interaction Design: Tool Calling and Plugins

## What core data this category includes
Core data typically comes from Figma or Axure files, internal team design systems, user feedback, and usability test records. Daily deliverables include interactive prototypes, page flowcharts, component specifications, and review records. Data is organized hierarchically by page nodes, interaction actions, and component attributes. Update frequency is usually weekly or per release. The most time-consuming steps include sorting out state transitions, completing abnormal scenarios, and revising design reviews. If there are deviations in the transmission of interaction logic, it can easily lead to developer misunderstanding, incorrect post-launch operation paths, or rework.

## What constraints these characteristics impose on tool calling and plugins
The hierarchical organization of prototyping and interaction design data by page nodes and interaction actions requires tool calling to support parsing structured prototype files, to avoid missing hidden abnormal interaction configurations. The weekly or per-release update rhythm means tool calling must support incremental synchronization capabilities, reduce the overhead of repeated full-file processing, and improve review efficiency. The strong binding between review records and prototype files requires tool calling to associate review comments for corresponding changes, ensuring that code reviews cover all design modifications and historical feedback. At the same time, the consequences of developer rework or incorrect post-launch paths caused by interaction deviations require that tool calling results undergo basic verification, ensuring that parsed interaction logic matches actual design, and reducing the risk of review errors.

## Three common mistakes
- Troubleshooting item: Tool call returns a missing context error, and the tool call result does not include historical prototype review records. Verify whether the context association parameters for tool calls are correctly configured, and whether change code is bound to corresponding prototype nodes.
- Troubleshooting item: Tool call returns a 400 status code with no response content, and the API request has no return data. Verify whether the required `AIPROXY_API_ENDPOINT` (root address of the AI Proxy service, no path suffix allowed) and `AIPROXY_API_TOKEN` (AI Proxy administrator Token, consistent with server configuration and not empty) environment variables are configured on the App/Admin server, or whether the tool call parameter format meets model requirements.
- Troubleshooting item: Tool function call fails, and the model does not generate tool call instructions. Verify whether the target model supports tool call formats, and whether the corresponding capability is enabled in the model channel configuration.

## How to confirm correct configuration
- Check whether the `AIPROXY_API_ENDPOINT` (root address of the AI Proxy service, no path suffix allowed) and `AIPROXY_API_TOKEN` (AI Proxy administrator Token, consistent with server configuration and not empty) environment variables are configured on the FastGPT v4.17.0 App/Admin server.
- Upload a modified prototype file to trigger a tool call, and check whether the returned result includes parsed interaction logic content for prototype nodes.
- Verify that the tool call parameter format meets configuration requirements, and ensure that `functionCall` or tool call trigger rules are correctly set.
- Simulate a prototype change containing abnormal interaction configurations, and confirm whether the tool call can correctly identify and return abnormal items.
