# Code and Change Review Assistance for Change Management and Release Windows: Multi-turn Dialogue and Prompt Engineering

## What This Category of Data Looks Like
The data for this category comes from change management systems, CI pipelines, business monitoring data, and business calendars. Daily associated documents include change request forms, change risk assessment forms, production release window schedules, and rollback execution plans. Data updates occur weekly or are triggered by individual changes. Document fields include change ID, impact scope, risk level, window time period, rollback trigger conditions, and more. All fields use standardized text and time formats with no additional custom units.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering by These Data Characteristics
The data sources for this category are scattered and updated per individual change. This requires multi-turn dialogue to bind `chatId` to implement session isolation, preventing confusion across change review data. Document fields use standardized formats, so prompts must consistently call fields such as change ID and window time period to avoid format deviations. Data is linked to production change risks, so prompts must include risk validation rules to ensure output content complies with change approval requirements. Additionally, since data updates are triggered by changes, dialogue context must support dynamic refresh per session to adapt to the review process for individual changes.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `chatId` | Bind the unique identifier of the current change | Implement session isolation for multi-turn dialogue, preventing confusion between review data from different changes |
| `messages` | Store historical interactions and associated document fragments for the current change | Support multi-turn review of risk assessments, approval opinions, and other content from the review process |
| `variables` | Preset standardized fields such as change ID, window time period, and rollback conditions | Adapt to the fixed format of category documents and simplify prompt writing |
| Maximum context length | 8000–12000 token | Cover the complete review documents and interaction history for a single change, prevent critical information truncation, and comply with FastGPT v4.17.0 context processing rules |
| Session update trigger rule | Triggered upon submission of a single change | Match the update rhythm of category data per change, ensuring context is synchronized with the current change |

## Three Common Misconfigurations
- Symptom: When initiating a conversation using a universal global key, review data from different changes interferes with each other, and risk assessment content from non-current changes appears. Cause: Session isolation was not implemented by binding `chatId`, leading to incorrect differentiation of context across different changes.
- Symptom: After configuring a bilingual opening, only a single language version of the opening loads in the workflow. Cause: Bilingual trigger conditions were not bound in workflow variables, causing the language switching logic to fail.
- Symptom: After a tool call, both tool execution logs and AI reply content are displayed in the interface, instead of only AI conversation results. Cause: The prompt did not explicitly require hiding tool call process information, leading to redundant content being shown.

## How to Verify Proper Configuration
- Initiate a simulated change review conversation, check that the dialogue context only includes documents and interaction content related to the current change.
- Call preset variables, confirm that fields such as change ID and window time period configured in `variables` load correctly.
- Trigger the tool call workflow, check that the output only retains AI conversation results with no tool execution logs.
- Switch between different change sessions, confirm that session data bound to `chatId` does not interfere with each other.
