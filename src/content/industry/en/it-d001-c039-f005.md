# Code and Change Review Assistance for Backend Service Development: Multi-turn Dialogue and Prompt Engineering

## What Data Looks Like for This Category
Data related to code and change reviews for backend service development primarily comes from code repositories, API gateway logs, databases, and configuration centers. Update frequency follows a daily or per version release cycle. Daily associated documents include interface design documents, database change orders, code review records, and release notes. Interface design documents contain fields such as request parameters and return codes. Database change orders include table names and DDL statement content. Code review records include change scope and review opinion entries.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
The diversity of data sources requires multi-turn dialogue to support association with different data formats, while also enabling filtering of valid context by project branch and change version. Frequently updated review data requires prompts to regularly sync the latest change orders and code snippets to avoid using outdated information. Time-consuming steps such as interface contract confirmation and transaction boundary processing require multi-turn dialogue to gradually sort out details, so token consumption of the context must be limited to prevent the model from truncating critical information. Errors in backend services directly affect business stability, so prompts for multi-turn dialogue must accurately associate with the currently reviewed code and log data to avoid irrelevant content interfering with judgment.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| Maximum context token count | 8000–12000 tokens, calibrated via actual testing | Backend service review data includes code snippets, change orders, and logs. Excessively long context will cause the model to truncate critical information |
| Single-response token limit | 3000–5000 tokens | Covers reply requirements for long code reviews and change descriptions, avoiding complex issues being automatically restricted to low thresholds |
| `chatId` binding rule | Bind the unique identifier of a single review session | Ensures consistent context for multi-turn dialogue, avoiding data confusion between sessions |
| `variables` input parameters | Input the current change's project ID and branch name | Accurately locate project data associated with the current review, improving context relevance |
| Knowledge base association scope | Bind the current project's code repository and API gateway log library | Matches the source of backend service review data, ensuring recalled content aligns with the current review scenario |
| Global token statistics viewing path | FastGPT v4.17.0 system settings global monitoring module | Facilitates real-time viewing of session token consumption to adjust configurations promptly |

## Three Common Misconfigurations
- Phenomenon: Response tokens for some complex questions are automatically restricted to 200, resulting in overly short reply content. Cause: The response token limit for complex questions is not separately set, triggering the global low-threshold limit by default.
- Phenomenon: Review opinions in conversations cannot be added to the knowledge base. Cause: The switch for synchronizing conversation content to the knowledge base is not enabled, or the association path for the target knowledge base is not specified.
- Phenomenon: Advanced orchestration cannot send two messages in one go. Cause: The array structure of the `messages` parameter is not correctly configured, and two message objects to be sent are not added in session order.

## How to Verify Proper Configuration
- Initiate a test conversation containing a long code snippet, check whether the response content is complete and no early truncation occurs.
- Enter the global monitoring module, view the current session's token consumption statistics, and confirm it matches the configured limit.
- Add a review opinion to the conversation, check whether it can be manually synchronized to the bound knowledge base.
- Configure `chatId` then initiate a multi-turn dialogue, confirm that subsequent messages are all associated with the same session context.

The values provided are common starting points and should be evaluated against the reader's own samples.
