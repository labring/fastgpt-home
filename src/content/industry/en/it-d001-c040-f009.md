# Code and Change Review Assistance for Pre-Sales Technical Proposals: Tool Calling and Plugins

## What data for this category entails
This content is based on FastGPT v4.17.0. Data for this category typically comes from customer interviews, tender documents, vendor product materials, and historical project plans. Update frequency is per order or weekly. Daily produced documents include technical proposal documents, customer requirement research forms, quotation lists, and demo scripts. Most document fields cover technical routes, implementation boundaries, quotation details, and demo scenarios. There are no uniform mandatory units. Adjustments must match actual project needs. Typical users are system integrator pre-sales consultants, solution architects, and sales teams. Core documents dynamically adjust boundaries and configurations based on customer requirements.

## What constraints these characteristics impose on the tool calling and plugins workflow
Multiple scattered data sources require tool calling to integrate information from different channels and quickly aggregate customer requirements and vendor product parameters. The per-order or weekly update rhythm requires plugins to pull the latest tender documents and product materials dynamically, avoiding outdated data use. Diverse document structures require tool calling to support custom field mapping, adapting to the proposal formats of different projects. Severe potential error consequences require tool calling to include configuration verification mechanisms. These mechanisms intercept out-of-scope technical commitments and incorrect quotation configurations in advance.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Tool calling trigger timing | 24 hours before the proposal review node | Matches the per-order update rhythm of pre-sales proposals, reserves time for verification and adjustment |
| `toolChoice` parameter configuration | Automatic | Adapts to the usage habit of pre-sales consultants who do not need to manually select tools, improving operational efficiency |
| Plugin data source pull interval | Every 12 hours | Balances data timeliness and system resource usage, matches the weekly update frequency |
| `functionCall` output mapping rule | Configured by data source type | Adapts to the return formats of different data sources, ensuring output meets proposal review requirements |
| Abnormal result interception threshold | Calibrated based on actual testing | Adapts to differences in requirement boundaries across different projects, avoiding false interception of valid configurations |

## Three common misconfigurations
- Phenomenon: The data source plugin returns the database connection structure, but does not return SQL execution results. Cause: The output parsing rules for `functionCall` are not configured, only the metadata information of the database connection is pulled.
- Phenomenon: Unable to pass dynamically changing token parameters when the workflow calls external interfaces. Cause: The token is not set as a passable input item for the workflow, and the parameter is fixed to a single project value, making it unable to adapt to multi-scenario calls.
- Phenomenon: Frontend unresponsiveness occurs after concurrent tool calls. Cause: No concurrency control and timeout interception mechanism is configured for tool calling, and the per-order update rhythm of pre-sales proposals is not matched, leading to temporary system resource overload.

## How to confirm configurations are correct
- Manually trigger a data source plugin call, check if the returned results contain the expected SQL execution content, confirming that the `functionCall` output mapping configuration is effective.
- Pass a dynamic token parameter to call an external interface, check if the correct parameter value is carried in the interface request header, confirming that the workflow's parameter transfer rules are configured correctly.
- Simulate multiple concurrent tool calls, observe system resource usage and frontend response status, confirming that the concurrency threshold and timeout mechanism configuration meets project requirements.
- Check if the pulled data source is the latest tender document or vendor product material, confirming that the pull interval configuration matches the update rhythm.
