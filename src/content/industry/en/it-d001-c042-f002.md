# Code and Change Review Assistance for Backup Recovery and Disaster Recovery Drills: Context and Token

## What data falls under this category
This category of data originates from backup systems, database logs, object storage, and disaster recovery platforms. Four core document types are created regularly: backup policies, recovery drill reports, disaster recovery switchover plans, and data verification records.
Data updates follow three rhythms: daily, monthly, and quarterly. Backup system logs update daily. Drill reports and switchover plans update monthly or quarterly, aligned with drill cycles.
Document fields include backup window, recovery point objective, verification hash value, drill execution duration, and additional fields. Some fields require matching measurement standards based on business scenarios.

## Constraints on context and token handling
Multi-source data for backup recovery and disaster recovery drills has large format differences. It includes both structured backup policy parameters and unstructured drill report text. This requires context loading to support both structured field extraction and unstructured content parsing.
The layered update frequency of data requires context caching to support dynamic refreshing based on update cycles. This avoids loading outdated old drill data.
The accuracy of core fields such as recovery point objective and verification hash value directly affects business continuity. Context token allocation must prioritize complete loading of core fields, to prevent loss of critical information due to token overflow.
Cross-system disaster recovery data typically has a large volume. The total `maxContext` size for a single context load must be limited, to avoid triggering platform token upper limit restrictions.
For intranet deployments without network access, external token services cannot be called. Local token quotas must be configured to adapt to local loading needs.

## How to configure the settings
| Configuration Item | Recommended Value Range | Rationale |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | Adapts to the total token size after combining multiple documents such as disaster recovery drill reports and backup policies, to avoid overflow during single loading |
| `quoteMaxToken` | 1500–2000 characters | Corresponds to the effective content length of a single core document such as a data verification record, to ensure complete extraction of key fields |
| Context refresh cycle | 24 hours / 7 days | Set 24-hour refresh for daily updated data, 7-day refresh for monthly updated data, to match the layered update rhythm of data in this category |
| Context recall count | Top 4 entries | Matches the core documents corresponding to the three most time-consuming links in this category, to avoid token occupation from too many irrelevant recalled contents |
| Local token quota | Calibrated based on actual measurements | For intranet deployments without network access, adapts to the total size of locally loaded documents, to avoid triggering memory limits |

This configuration applies to FastGPT v4.17.0.

## Three common misconfigurations
- Services continue to restart after deployment on a network-free intranet, with logs showing failed errors. The cause is failure to correctly configure the token quota for local context loading, causing the platform to attempt calling external token services unsuccessfully and triggering the restart mechanism.
- After configuring a custom OpenAPI token, knowledge base search and question optimization still incur fees. The cause is failure to bind the token quota for context calls to the custom token, so the platform default billing token pool remains in use.
- Context information for the current session cannot be cleared. The cause is failure to locate the context reset entry for the corresponding session, or failure to correctly trigger the token cache clearing command, causing old data to still be loaded.

## How to verify successful configuration
- Upload a single backup policy document, check the token consumption value displayed after context loading, to confirm it does not exceed the configured maximum context limit.
- Trigger a recovery drill review, check whether the returned content includes core fields such as recovery point objective and verification hash value, to confirm the quote maximum token configuration is active.
- Manually trigger context refresh, wait for the corresponding cycle, then load the document again, to confirm new updated content has been loaded.
- Start the service in a network-free intranet environment, check that logs show no token service call failure prompts, to confirm the local token configuration is working correctly.

The values provided are common starting points and should be measured against the reader's own samples.
