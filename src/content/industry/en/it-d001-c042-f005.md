# Code and Change Review Assistance for Backup Recovery and Disaster Recovery Drills: Multi-turn Dialogue and Prompt Engineering

## What this category’s data looks like
This category serves operations teams, database administrators, and business continuity leads. Daily documents produced include backup policies, recovery drill reports, disaster recovery switchover plans, and data validation records. Data sources cover backup systems, database logs, object storage, and disaster recovery platforms. Update frequencies fall into three categories: daily, monthly, and quarterly. The most time-consuming steps in core workflows are recovery point confirmation, drill script execution, and data consistency verification. Errors can result in data loss, recovery timeouts, business continuity failures, and other adverse outcomes. The core difference between this category and database operations categories is its focus on cross-system overall recoverability.

## What Constraints These Characteristics Impose on Multi-turn Dialogue and Prompt Engineering
Multi-source data requirements mandate that multi-turn dialogue support cross-system data association retrieval, to avoid incomplete information caused by only calling a single data source. Documents with varying update frequencies require prompts to adapt to content updates at different rhythms, such as daily validation records and monthly drill reports. Fixed-structure daily documents require prompts to clearly define rules for identifying dedicated fields including backup policies and recovery point parameters. The most time-consuming core steps require multi-turn dialogue to focus on scenarios like recovery point confirmation and data consistency verification, reducing irrelevant information interference. Cross-system capability requirements mandate that dialogue context integrate configuration information from different disaster recovery platforms, ensuring review content covers the full end-to-end chain.

## How to Configure Settings
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum context length | 8000–12000 characters | Adapts to the average single-document length of disaster recovery documents, avoiding truncation of critical recovery point parameters and validation records |
| Single knowledge base recall count | Top 6 results | Covers typical recall volumes for multi-source data such as backup systems and database logs, ensuring sufficient review basis |
| `variables` binding rules | Assign values by disaster recovery scenario | Matches backup policy parameters across different disaster recovery scenarios, improving prompt targeting |
| `messages` history truncation threshold | Retain the last 7 days of dialogue content | Adapts to the daily update rhythm of validation records, filtering redundant historical dialogue information |
| `chatId` session isolation rule | Divide by disaster recovery project | Differentiates recovery point confirmation workflows for different businesses, preventing session data confusion that interferes with reviews |

## Three Common Configuration Errors
- Phenomenon: A 422 status code is returned when triggering a code review dialogue, and the interface shows no matching search results. Cause: Disaster recovery-related knowledge base data sources are not correctly bound, making it impossible to call core data such as backup system logs and drill reports.
- Phenomenon: Unable to switch knowledge base content for different disaster recovery projects in real time during multi-turn dialogue. Cause: Session isolation rules are not configured according to `chatId`, causing session data from different projects to mix with each other.
- Phenomenon: Search matching accuracy is low for long documents such as recovery drill reports, and key steps are not recalled. Cause: The title hierarchy separators of disaster recovery documents are not adapted, leading to semantic block breaks and failure to fully match query intent.

## How to Verify Successful Configuration
- Initiate a recovery point confirmation dialogue, and confirm whether the latest validation records from the backup system and configuration information from the corresponding disaster recovery platform can be recalled.
- Switch sessions for different disaster recovery projects, verify that session data does not cross over, and confirm that the `chatId` isolation rule is in effect.
- Upload a complete disaster recovery switchover plan document, and verify that the search matching results after long text segmentation meet expectations.
- Review the dialogue history record, confirm that only the last 7 days of valid dialogue content are retained, with no redundant information interfering with the current review.
