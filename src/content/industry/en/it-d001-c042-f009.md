# Code and Change Review Assistance for Backup Recovery and Disaster Recovery Drills: Tool Calling and Plugins

## What data looks like for this category
This category draws data from backup systems, database logs, object storage, and disaster recovery platforms. Daily associated documents include backup policies, recovery drill reports, disaster recovery switchover plans, and data validation records. Update frequencies cover daily, monthly, and quarterly cycles.
Data fields align with core document requirements. Backup policies include backup windows and retention periods. Drill reports include execution times and abnormal nodes. Data validation records include the number of validation items and execution status. Field dimensions vary across different documents. This category focuses on cross-system recoverability, which differs from single database operation and maintenance scenarios.

## What constraints these characteristics impose on tool calling and plugin workflows
This category’s data sources are scattered across multiple types of systems. Tool calling must adapt to format differences across source data to avoid parsing errors. Daily documents have significant structural differences. Plugins must support dynamic matching of fields from different documents, and cannot directly use uniform parsing rules.
Validation steps such as recovery point confirmation and data validation take time. Tool calling must set reasonable timeout parameters to prevent single-step blocking from delaying review progress. High availability requirements in disaster recovery scenarios mean plugin failure handling must align with business continuity goals. A single failed call must not interrupt the overall review process.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | Set to `auto` | Adapt to dynamic calling needs for multi-source disaster recovery data, no need to manually specify specific tools |
| `functionCall` | Restricted to recovery and validation tools | Avoid calling unrelated tools that disrupt review workflows, align with core requirements of disaster recovery scenarios |
| Timeout threshold | 300–600 seconds | Adapt to execution durations of time-consuming steps such as recovery point confirmation and data validation |
| Retry count | 2 attempts | Address occasional fluctuations in backup system interfaces, without impacting overall review rhythm |
| Plugin context limit | First 10 historical records | Control input scale for tool calling, avoid exceeding system processing limits |
| Parameter type switch | Enable custom mode | Adapt to delivery needs for different parameter types in disaster recovery scenarios |

## Three common configuration mistakes
- Large models return empty tool calling results. The cause is incorrect configuration of the `toolChoice` parameter, which prevents the large model from matching available disaster recovery tools.
- The `type` parameter is fixed to `string` when calling MCP services. The cause is that the custom parameter type switch was not enabled in the FastGPT v4.17.0 plugin configuration, and the system converts all parameters to string type by default.
- Tool calling streaming output cannot be disabled. The cause is that the streaming output switch was not disabled in the configuration, so all tool calls use streaming returns by default.

## How to confirm configuration is complete
- Manually trigger a change review, check tool calling logs, and confirm that all called tools are exclusive to disaster recovery scenarios.
- Submit test data containing abnormal parameters, verify whether tool calling triggers interruption or retry according to the configured timeout threshold.
- View the plugin configuration interface, confirm that the `toolChoice` and `functionCall` parameter settings match the recommendations in the configuration table.
- Simulate a tool calling failure, check whether the preset retry mechanism is triggered, and the review process is not directly interrupted.
