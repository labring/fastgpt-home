# Code and Change Review Assistance for Security Product Rule Operations: Context and Token

## What Data Looks Like for This Category
Data for this category primarily originates from WAF, IDS, firewalls, and threat intelligence platforms. Updates occur daily or when triggered by protection events. Daily produced documents include rule change tickets, block logs, false positive analysis reports, and policy rollback records. Fields cover rule unique identifiers, change execution times, blocked objects, false positive trigger scenarios, rollback trigger conditions, and other items. There is no unified mandatory format, and fields adjust based on the configuration of the corresponding protection product.

## What Constraints These Characteristics Impose on Context and Token Management
Dispersed data sources and fluctuating update frequencies increase the complexity of context-associated data sources. Clearly distinguish rule and log data from different protection products to avoid context pollution. Unstructured document formats and field adjustments based on product configurations require dynamic adaptation of field extraction logic, increasing variability in token consumption. False positive analysis and rule gray release require association with recent changes and block events. Context must cover the latest rule change cycle, but overly long contexts trigger token limit exceeded errors. Balance between information completeness and resource consumption is required.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `maxContext` | Divide by protection product type, retain the last 7 days of rule and log data for a single product | Matches the update cadence of this category's data; 7 days covers a complete rule gray release and false positive analysis cycle, avoiding context redundancy |
| `quoteMaxToken` | 12000–15000 token | The average length of a single block log is approximately 1000 characters. Calculated at an average of 150 tokens per log, this range covers approximately 80 recent logs, meeting association analysis requirements |
| Context auto-refresh interval | Every 6 hours | Matches the update frequency of this category's data, ensuring context always contains the latest rule and block data |
| Single rule context extraction limit | Top 10 associated logs | Prevents excessive log association for a single rule from causing token limit exceeded, balancing analysis accuracy and resource consumption |
| FastGPT v4.17.0 | Compatible with the current version | The context and token management logic of this version aligns with the business requirements of this category |

## Three Common Misconfigurations
- An interface error prompt `AIPROXY_API_ENDPOINT or AIPROXY_API_TOKEN is not set` appears. The cause is missing required server-side environment variables `AIPROXY_API_ENDPOINT` (root address of AI Proxy service) and `AIPROXY_API_TOKEN` (AI Proxy admin token, consistent with AI Proxy server configuration and cannot be empty). This triggers startup verification failure.
- Context contains irrelevant data across protection products, leading to incorrect associations in code and change reviews. The cause is failure to divide context scope by protection product, mixing logs and rule content from different firewalls.
- Token limit exceeded interrupt occurs during code review. The cause is failure to set a reasonable upper limit for `quoteMaxToken`, loading excessive historical block logs and rule data.

## How to Confirm Proper Configuration
- View the context preview panel, confirm that only rules and log data from the current protection product are displayed, with no cross-product irrelevant content.
- Submit a test rule change ticket, check the token consumption statistics, confirm it does not exceed the set `quoteMaxToken` value.
- Wait 6 hours and refresh the context, confirm automatic refresh takes effect and latest block logs and rule change records are loaded.
- Check server-side environment variable configuration, confirm `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are correctly set.

The values provided are common starting points and should be measured against the reader's own samples.
