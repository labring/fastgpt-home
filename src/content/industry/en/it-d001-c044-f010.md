# Code and Change Review Assistance for Security Product Rule Operations: Citation Sources and Traceability

## What the Data for This Category Looks Like
Typical users of this category include security operations engineers, WAF or IDS product administrators, and SOC teams. Daily documents produced include rule change tickets, block logs, false positive analysis reports, and policy rollback records. Data is primarily sourced from WAF, IDS, firewalls, and threat intelligence platforms. Updates occur daily or when triggered by protection events. Document fields include rule unique identifiers, block trigger conditions, false positive associated samples, and policy version numbers. Units are mostly rule counts, event counts, and timestamps. Traceability must be split by individual protection entities.

## How These Data Characteristics Create Constraints for Citation and Traceability
Data sources are scattered and updated in real time with events. Citation and traceability must precisely match the unique identifier of individual rules or events to avoid cross-rule confusion. Daily documents are mostly unstructured logs and analysis records. Citation scope must be limited to prevent irrelevant data from entering the context. Real-time update frequency requires the traceability link to quickly pull the latest policy versions. It must also support cross-version citation of historical rollback records to prevent referencing expired old rule data. Additionally, the sample association feature of false positive analysis requires traceability to link to the context of specific trigger events, ensuring review accuracy.

## Configuration Guidelines
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | 8000–12000 token | Adapts to the average content size of single-batch rule changes or block logs for security products, prevents model context overflow |
| `detail` | Enabled | Used to pull full field information for block logs and false positive analysis, ensures traceability links can view complete event details |
| `responseData` | Limited to rule change tickets, block logs, policy rollback records | Narrows response data scope, retains only documents related to security product rule operations, eliminates interference from irrelevant data sources |
| Single recall limit | Top 15 entries | Matches the daily rule processing volume for single reviews, avoids excessive data consuming context resources |
| Context matching rule | Match by rule unique identifier | Precisely links historical data for corresponding protection entities, prevents cross-rule confusion |

## Three Common Misconfigurations
- Phenomenon: The number of citation context entries displayed on the page does not match the number actually sent to the model. Cause: The matching relationship between `quoteMaxToken` and the single recall limit is not correctly configured, leading to a mismatch between the front-end display and the back-end pulled data source scope.
- Phenomenon: `quoteMaxToken` is set to 1500, but rule logs exceeding this length in the knowledge base are still cited. Cause: Single-content truncation configuration for data sources is not enabled, or filter rules do not cover overly long single log entries.
- Phenomenon: The referenced rule data does not match the change ticket currently under review. Cause: Context filtering by rule unique identifier is not configured, leading to the pulling of historical data for irrelevant rules.

## How to Verify Correct Configuration
- Confirm that the current FastGPT version is v4.17.0 to avoid parameter configuration incompatibility.
- Review model invocation logs to verify that pulled data sources only include content related to WAF, IDS, firewalls, and threat intelligence.
- Submit a test rule change ticket, check that the referenced context includes historical block logs and false positive analysis records for the corresponding rule.
- After adjusting the `quoteMaxToken` parameter, compare whether the number of context entries displayed on the front end matches the actual token count from back-end calls.

The values provided are common starting points and should be measured against the reader's own samples.
