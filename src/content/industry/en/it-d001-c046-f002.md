# Code and Change Review Assistance for Security Baseline Checks: Context and Token

## What Data for This Category Looks Like
Data for this category originates from server configurations, middleware configurations, security device policies, and baseline tool outputs. Four standard document types are produced regularly: baseline checklists, configuration verification records, rectification suggestions, and exception approval forms. Fields include configuration item ID, compliance status, verification time, rectification requirements, and no unified fixed unit. Data updates occur monthly or quarterly, synced with organizational security baseline adjustments or compliance audit cycles. Single verification data volume increases as device scale expands.

## What Constraints These Characteristics Impose on the Context and Token Workflow
Security baseline check data comes from dispersed sources with varying formats. Integrating multi-source configuration information as context will consume significant token quota. Update frequency is low, but single verification data volume is large, so context windows must be controlled to avoid overflow while covering cross-cycle compliance records. There are many document types with scattered fields, so retrieved baseline checklists, verification records, and similar content must be accurately matched to limit invalid token consumption. In audit scenarios, historical exception approval forms must be associated. Context length must balance completeness and token usage efficiency to avoid loss of compliance information due to truncation.

## How to Configure
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Range | Rationale |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | Security baseline checks require integrating configuration data and historical compliance records from multiple devices. This range covers the core context of a single batch of checks and prevents key configuration items from being truncated |
| `quoteMaxToken` | 2000–3000 token | Core field content for a single baseline checklist or configuration verification record falls within this range, prioritizing loading key information such as compliance status and rectification requirements |
| Single search limit | Top 8 entries | Core configuration items for security baseline data are approximately 5-7 per device. Retrieving 8 entries covers verification results from multiple devices and avoids token usage by redundant data |
| Search result reordering | By compliance priority | Prioritize retrieving configuration items that failed compliance checks, reducing token usage for non-critical information and improving review efficiency |
| Question optimization toggle | Enabled | Automatically optimize question wording for compliance questions related to baseline checks, reducing token usage from invalid context |

## Three Common Misconfigurations
- Phenomenon: Context token limit exceeded during invocation, returned content truncated, or status code 429 returned. Cause: The `maxContext` parameter was not adjusted based on the multi-source nature of security baseline data, and excessive irrelevant historical configuration records were loaded, leading to token quota exhaustion.
- Phenomenon: Search results fail to match core compliance fields of baseline checklists, with empty or incomplete returned results. Cause: The `quoteMaxToken` parameter was not set to limit the token length of a single reference, leading to truncation of long documents that prevents matching of key configuration items.
- Phenomenon: Default token deduction occurs when using a custom model in an intranet deployment. Cause: The token billing logic for the custom model was not properly associated, and the platform's default token deduction switch was not turned off, leading to additional token consumption.

## How to Verify Successful Configuration
- Upload a complete baseline checklist document, trigger the code review assistance function, and check whether the loaded context content includes core configuration items and compliance status fields.
- View the platform's token consumption logs, and verify whether the token usage of a single call falls within the preset ranges of the `maxContext` and `quoteMaxToken` parameters.
- Simulate a change review scenario, enter the configuration items to be verified, and check whether the search results prioritize returning content that failed compliance checks.
- In the intranet deployment environment, verify whether the token billing logic of the custom model takes effect, and confirm that no additional default token consumption occurs.

The values given are common starting points and should be measured against the reader's own samples.
