# Code and Change Review Assistance for Security Baseline Checks: Workflow Orchestration

## What Data for This Category Looks Like
Data for this category originates from server configurations, middleware configurations, security device policies, and baseline tool outputs. Update frequency is monthly or quarterly. Routine deliverables include baseline checklists, configuration verification records, rectification suggestions, and exception approval forms. Data fields include baseline item unique identifier, current configuration value, verification result, and exception approval status. No additional custom units are used; values are recorded using only the original units of standard configuration items.

## Constraints Imposed by These Characteristics on Workflow Orchestration
The scattered data sources and low-frequency update nature of this category require workflows to be configured with multiple data source connection nodes. These nodes pull configuration data from different devices sorted by baseline item. The fixed monthly or quarterly update rhythm allows workflows to use a fixed periodic trigger, with no need for high-frequency execution. The need for multiple types of deliverables requires workflows to support generation and storage of content in different formats, including baseline checklists and verification records. The multi-stage verification process requires workflows to link together configuration verification, exception reason confirmation, and rectification result review steps. This ensures outputs from each stage are traceable.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Cycle | Once per month or once per quarter | Matches the monthly/quarterly data update frequency of this category |
| Data Source Nodes | Create separately for servers, middleware, and security devices | Corresponds to the multi-source data collection requirement |
| `variables` | Bind baseline item ID and verification result fields | Used to pass fixed baseline check parameters |
| `nodeId` | Assign a unique identifier to each data source node | Facilitates workflow node status tracking and exception troubleshooting |
| Exception Alert Threshold | Trigger after 2 consecutive failed checks | Corresponds to the consequences of long-standing weak configuration issues |
| Result Storage Limit | Do not exceed 1000 MB of storage per node | Adapts to the retention requirement for configuration verification records |

## Common Misconfiguration Issues
- After a workflow triggers, no data is returned. The symptom is that node status shows empty fields. The cause is that corresponding nodes were not configured to match the multi-data-source characteristics of this category, and only a single type of configuration source was connected.
- A disconnection error occurs during workflow execution. The symptom is a MongoDB connection exception indicating primary node switch failure. The cause is that automatic reconnection parameters for MongoDB connections were not configured, and the replica set primary node drift characteristic was not adapted to.
- The output of the tool call module cannot be hidden. The symptom is redundant tool execution logs are displayed during the review stage. The cause is that the workflow's output filtering rules were not correctly configured, and intermediate return content from tool calls was not blocked.
- MinIO-related node configuration errors occur in the workflow. The symptom is that the specified storage bucket cannot be read. The cause is that the environment variable name updated in FastGPT v4.17.0 was not used, and the old version naming rule was retained.

## How to Confirm Proper Configuration
- Review the workflow's node configuration list, confirm that corresponding nodes have been created separately by data source type.
- Trigger a test execution, check whether the output fields of each node include baseline item ID and verification result.
- Manually modify one baseline configuration item, verify whether the exception alert rule triggers normally.
- Check the result storage path, confirm that test execution records have been correctly written to the specified storage location.
