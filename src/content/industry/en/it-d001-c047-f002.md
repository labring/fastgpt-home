# Code and Change Review Assistance for Security Vulnerability Disclosure Handling: Context and Token

## What This Category’s Data Looks Like
Data for this category is generated around individual vulnerability incidents. Sources include private vulnerability reporting channels, project code repositories, CVE numbering bodies, and official release channels. Daily produced documents include security advisories, vulnerability reports, fix patches, and CVE application materials. Individual data entries include fields such as vulnerability ID, impact scope, fixed code snippets, and disclosure time. Updates follow the full lifecycle of individual vulnerability incidents. New update content is generated each time a phase of an incident is completed.

## What Constraints Do These Characteristics Impose on Context and Token Workflows
This category’s data includes private vulnerability reports, code snippets, and CVE-related fields. Context retrieval must strictly limit authorization scope to prevent exposure of undisclosed sensitive vulnerability information. Individual incident data has high correlation. Context must precisely match all content related to the current vulnerability’s full lifecycle. Mixing unrelated incident data will cause evaluation bias. Additionally, fixed code snippets account for a large share and have long length. Token allocation must prioritize effective retrieval of code snippets. Prevent loss of critical patch information due to token limit exhaustion. Data updates progress with incidents. Context must support dynamic appending of latest disclosure coordination information to avoid outdated content.

## Configuration Settings
Corresponding core parameters in FastGPT include `maxContext`, `quoteMaxToken`, and others. Specific configuration recommendations are listed below.

| Configuration Item               | Recommended Value Range               | Rationale |
| -----------------------------------|----------------------------------------|--------------------------------------------------------------------------- |
| Maximum Context Length            | 8000–12000 token                       | This category’s single-incident data includes code snippets, CVE application materials, etc. Must cover all content related to a single vulnerability’s full lifecycle. Avoid critical information loss due to insufficient tokens. Calibrated for different scale project code repositories based on real-world testing. |
| Maximum Quoted Token Count        | 2000–3000 token                       | Fixed code snippets are core data. Must ensure complete retrieval of single patch code. Avoid truncation that impacts patch validation. |
| Context Retrieval Count           | Top 6 entries                          | This category’s data is aggregated by incident. Retrieving too many unrelated incident entries will interfere with vulnerability impact assessment. Limiting the count improves context accuracy. |
| Context Refresh Timing            | After each vulnerability phase update  | Data updates as incidents progress. Refreshing the context ensures inclusion of the latest disclosure coordination information and patch progress. |
| Private Data Filter Toggle        | Enabled                                | Data includes undisclosed private vulnerability reports. Enabling the filter prevents sensitive information from being exposed in public contexts. |

## Three Common Misconfigurations
1.  Phenomenon: Token limit exhaustion error occurs during context loading, preventing completion of vulnerability impact assessment. Cause: Failed to adjust the `maxContext` parameter based on single-incident data volume. Used default values for general scenarios directly. This causes vulnerability data with long code snippets to fail to load completely.
2.  Phenomenon: Knowledge base search uses custom tokens but still incurs additional fees. Cause: Failed to bind valid tokens for the corresponding service in context configuration. Authorization verification was not enabled for private vulnerability report retrieval. This leads to requests being sent using default tokens.
3.  Phenomenon: Redundant data appears after context refresh, including vulnerability information from non-current incidents. Cause: Failed to configure incident matching rules for context retrieval. Retrieved all historical data directly. This causes context content from different vulnerabilities to be mixed together.

## How to Verify Proper Configuration
This verification process applies to FastGPT v4.17.0.
- Upload complete data for a single vulnerability incident. Check that the context preview module includes all core document content for that incident, with no redundant data from other incidents.
- Review service logs. Confirm that token usage does not exceed the configured maximum context length limit, with no limit exhaustion error messages.
- Manually trigger a vulnerability phase update. Check that the context automatically appends the latest disclosure coordination information.
- Verify the private data filter toggle. Confirm that unauthorized external requests cannot access undisclosed vulnerability report content.
- Check that the `quoteMaxToken` parameter is configured to match the length of single fixed code snippets. Ensure code loads completely.

The values provided are common starting points. They should be evaluated against the sample data relevant to the respective deployment.
