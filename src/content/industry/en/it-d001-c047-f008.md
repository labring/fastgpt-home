# Code and Change Review Assistance for Security Vulnerability Disclosure Handling: Workflow Orchestration

## What this category of data looks like
This data comes from private vulnerability reports, code repositories, CVE numbering authorities, and official release channels. Daily produced documents include security advisories, vulnerability reports, fix patches, and CVE application materials. Each entry corresponds to a single independent vulnerability event. Data updates are triggered by vulnerability events, with no fixed cycle. Core fields include vulnerability ID, impact scope, fix branch, and disclosure timeline. All data is only circulated within the project security response team until official patch release.

## What constraints these characteristics impose on workflow orchestration
The non-public nature of private vulnerability reports requires workflow nodes to be configured with permission isolation. Only authorized members can access corresponding data. The characteristic that a single event corresponds to a complete data link requires the workflow to be bound to a unique event identifier. This prevents cross-event data confusion. CVE numbers must be synchronized from official authorities. The workflow must include an external data pull node, and validate the number format for validity. The patch preparation phase involves code change reviews. The workflow must connect code repository pull and change comparison nodes. It must also lock the data version before disclosure. This prevents project reputation damage caused by premature patch releases.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Initialize a dedicated variable group per event, with an initial empty value and a capacity cap of 1500 tokens | Matches the data isolation requirements of single vulnerability events to avoid global variable conflicts |
| `nodeId` | Bind the unique identifier of the corresponding vulnerability event | Ensures workflow nodes are tied to a single vulnerability data entry, preventing cross-event data confusion |
| Node permission configuration | Only accessible to project security response team members | Adapts to the non-public nature of private vulnerability reports, preventing unauthorized access |
| Validation rule configuration | Enable format validation for the CVE number field, set a timeout threshold of 30 seconds | Meets official format requirements for CVE numbers, avoiding invalid data entering the workflow |
| Data pull trigger condition | Trigger when the private vulnerability report status is updated to "pending review", pull the first 3 code changes per single pull | Aligns with vulnerability event processing workflows, pulling code repository and announcement data as needed |

## Three common mistakes
- Workflow code execution nodes fail validation and cannot start the process when input includes historical records. Cause: The current FastGPT v4.17.0 code execution node does not support passing global variables or historical context data. Input parameters must be strictly limited to dedicated variables for the current event.
- Global variable initial values do not take effect, and no changes appear after variable updates. Cause: Workflow variables must be bound to the context of the corresponding node. Global variables only take effect during workflow initialization. Updates must be made by reassigning values via the `variables` parameter.
- Workflow nodes are not bound to the `nodeId` identifier, resulting in cross-mixing of data from multiple vulnerability events. Cause: No unique event identifier is configured, so the workflow cannot distinguish processing data for different vulnerabilities, leading to process chaos.

## How to confirm correct configuration
- Trigger a simulated vulnerability event, check that the workflow only pulls code change and vulnerability report data for the corresponding event, with no redundant information from other events.
- Attempt to input historical context content into the code execution node, confirm that parameter validation failure is triggered, matching the preset restrictions.
- Manually update the initial value of the global variable, check whether the variable value of the corresponding workflow node is synchronized to the new configuration.
- Input a CVE number that does not meet the format requirements, confirm that the workflow intercepts execution of the node and throws a format error prompt.
