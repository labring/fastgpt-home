# Code and Change Review Assistance for Customer Provisioning and Tenant Initialization: Multi-turn Conversations and Prompt Engineering

This documentation applies to FastGPT v4.17.0.

## What the data for this use case looks like
Service subjects for this use case primarily include SaaS implementation consultants, customer success managers, and operations provisioning staff. Daily documents include provisioning request forms, tenant configuration sheets, admin account lists, and delivery confirmation slips. Data sources include CRM, contract orders, identity management systems, and product backends.
Update frequency is per order/day. Core fields include customer unique identifier, tenant code, permission scope, provisioning status, and admin account information, among others. Fields are updated in real time per the configuration requirements of individual provisioning processes, with no fixed values under a unified statistical framework.

## What constraints these characteristics impose on multi-turn conversation and prompt engineering
Standardized operating procedures for service subjects require multi-turn conversations to organize content in the order of steps from the provisioning request form, to avoid missing required configuration items.
Multi-source data input requires conversations to support separate calls to real-time data from CRM and identity management systems, to ensure accuracy of customer information and permission configurations.
The per order/day update frequency requires conversation context retention duration to be limited, to avoid using expired historical data.
The fixed nature of core fields requires prompts to explicitly specify extracted fields, to prevent generating irrelevant content that disrupts the provisioning confirmation phase.

## How to configure
| Config Item | Suggested Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique identifier of the current tenant | Ensure conversation context is tied to the specified tenant, prevent cross-tenant data confusion |
| `messages` | Organize content in stages according to the provisioning workflow | Match the step order of provisioning request forms and tenant configuration sheets, cover all required steps |
| `variables` | Inject real-time fields from CRM and identity management systems | Call the latest customer information and permission data, adapt to the per order/day update frequency |
| Maximum context retention length | 1500–2500 characters | Match the total document length of a single tenant provisioning workflow, avoid truncating critical configuration information |
| Timeout threshold | 60 seconds | Match the typical time required for customer information verification, prevent workflow stalls |
| Result output scope | Only return configuration verification and initialization results | Filter irrelevant content, focus on the provisioning confirmation phase |

## Three common misconfigurations
- Output content from intermediate steps in multi-turn conversations is displayed synchronously. This occurs because the visible scope of `messages` is not configured correctly, causing conversation content from non-target steps to not be hidden.
- The conversation icon after tenant initialization is not updated as required. This occurs because the custom icon parameter is not bound in the tenant configuration fields, causing the system default icon to be used instead.
- The model returns a connection error prompt. This occurs because the model interface configuration in `variables` is not verified correctly, or proxy-related parameters are not updated synchronously. Configuration deviations may remain even if the proxy is enabled.

## How to confirm correct configuration
- Check if the `chatId` bound to the conversation matches the unique identifier of the current tenant, to confirm correct context binding.
- Trigger a test conversation, verify that `variables` are injected with the latest field data from CRM and identity management systems.
- Simulate the full provisioning workflow, confirm that conversation output only includes configuration verification and initialization results, with no irrelevant content.
- Trigger a model call test, confirm that no connection error prompts appear.

The values provided here are common starting points, and should be evaluated against the user’s own samples.
