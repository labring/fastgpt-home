# Code and change review assistance for customer onboarding and tenant initialization: Workflow orchestration

## What the data for this category looks like
Data for this category typically comes from CRM systems, contract order databases, identity management systems, and the FastGPT product backend. Daily associated documents include onboarding application forms, tenant configuration sheets, administrator account lists, and delivery confirmation forms.
Data updates occur per order or daily. Common fields include customer unique identifier, tenant ID, administrator account, permission scope, onboarding time, and others. No fixed unified statistical caliber exists. Fields are generated only in accordance with business handling processes.

## Constraints on workflow orchestration from these characteristics
Data sources are scattered. Workflow orchestration must connect multiple external system interfaces to complete information verification and synchronization. Nodes for cross-system data pulling must be configured.
Data update frequency varies per order. The workflow must support on-demand triggering to adapt to the rhythm of single customer onboarding operations.
Document structures are fixed. Workflow nodes must match the required fields of each document to avoid missing key configurations.
The most time-consuming steps, such as customer information verification and permission initialization, can use workflow-configured automatic verification nodes to reduce manual intervention time.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `variables` | Include the three required fields: customer ID, tenant ID, administrator account | Match the field requirements of the tenant configuration sheet and administrator account list |
| `nodeId` | Assign unique identifiers in the order of the onboarding process, such as 1001, 1002 | Facilitate workflow node tracking and failure rollback |
| Trigger timing | Trigger after the customer submits the onboarding application form and it is approved | Align with standard business handling processes |
| Timeout threshold | 600 seconds | Cover the conventional time required for cross-system data pulling and configuration writing |
| Number of failure retries | First 3 attempts | Avoid system resource occupation caused by repeated triggering |
| Context cache duration | 3600 seconds | Prevent configuration reading failures caused by cache expiration |
| Single synchronization limit | 100 entries | Adapt to the single data writing limit of the identity management system |

## Three Common Mistakes
- A `localStorage is not defined` error occurs when running custom code in workflow nodes. The FastGPT workflow code execution environment does not expose the browser-side localStorage object. Direct calls to this object trigger an exception.
- The workflow cannot retrieve the shared application URL address. The workflow does not configure the context parameter for the corresponding node, or the application sharing permission field is not correctly bound.
- Customers cannot log in after tenant initialization completes. The workflow did not synchronize and write account permissions to the identity management system, or the configured administrator account field does not match the identity system’s verification rules.

## How to Confirm Configuration Completion
- Trigger a test onboarding process under FastGPT v4.17.0. Check if workflow logs show all nodes executed successfully.
- Compare data from the CRM system’s onboarding application form with the tenant configuration sheet written by the FastGPT workflow. Confirm all fields match exactly.
- Log in to the test tenant’s administrator account. Verify that basic permissions and configuration items are correctly initialized.
- View the tenant list in the FastGPT product backend. Confirm the new tenant’s status is normally enabled.

The values provided are common starting points. They should be assessed against local test samples.
