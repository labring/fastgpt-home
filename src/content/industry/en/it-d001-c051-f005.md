# Code and Change Review Assistance for Customer Data Import and Migration: Multi-turn Dialogue and Prompt Engineering

## What the data for this use case looks like
This type of data mostly originates from customer legacy systems, CSV or Excel templates, database exports, and product import logs. Update frequency is per order or irregular. Associated daily documents include data templates, migration plans, field mapping tables, and migration validation reports. Core work steps include field mapping confirmation, dirty data cleaning, and post-import sampling verification. Data structure varies across customer business systems. There are no unified fixed fields or unit standards. Adaptation must be performed based on the customer's actual business scenarios.

## What constraints do these characteristics impose on the multi-turn dialogue and prompt engineering link
The diversity of data sources requires multi-turn dialogue to adapt to inputs in formats such as CSV, Excel, and database exports. Prompts must clearly guide corresponding format verification rules. The irregular update frequency means dialogue context must fully retain each field mapping and dirty data cleaning record to avoid repeated communication. The multi-type nature of daily documents requires multi-turn dialogue to gradually guide the organization of key information in data templates and migration plans, reducing information omissions. The non-standardized nature of fields and units requires prompts to repeatedly confirm field correspondence to avoid field misalignment or data loss during subsequent import.

## How to configure the settings
The following configurations are adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Context window size | First 8 turns of dialogue + latest 1200 characters | Adapts to multi-step communication during migration, retains key mapping and cleaning records, avoids context overflow |
| `variables` scope | Dialogue-level isolation | Prevents confusion of import data variables across different customers, ensures each user can only access their own dialogue data |
| `messages` format verification rules | Force splitting by role (user/assistant) | Ensures dialogue history can be parsed correctly, facilitating subsequent interface calls and record tracing |
| Multi-turn verification trigger frequency | Trigger field mapping verification every 3 interactions | Matches the rhythm of the time-consuming field mapping confirmation step, avoids overly interrupting the communication flow |
| Dialogue persistence binding | Enable and bind `chatId` | Ensures different users in shared applications only view their own dialogues, meeting business security requirements |

## Three common configuration errors
- Symptom: Different users in a shared application can view each other's dialogue records. Cause: The dialogue was not bound to `chatId` and dialogue-level variable isolation was not enabled, resulting in variable scopes not being divided by user.
- Symptom: When calling the "Get Dialogue Record List" interface, the returned dialogue order does not match expectations, and user questions cannot be matched with AI replies. Cause: The offset parameter was not correctly set to retrieve dialogues sorted by time, or complete role identifiers were not included in `messages`, leading to disorganized data correspondence.
- Symptom: After modifying global variables in the same dialogue, subsequent components cannot read the updated values. Cause: Variable updates were not synchronized in real time via the `variables` parameter during multi-turn dialogue, only the initially passed variable values were retained.

## How to confirm the configuration is valid
- Call the "Get Dialogue Record List" interface, pass the `chatId` parameter, and verify that only the current user's dialogue data is returned.
- Pass the offset parameter to retrieve the dialogue list, check that the number of returned entries matches the offset setting, confirming the parameter functions as expected.
- Modify global variables in the dialogue, pass the updated values via the `variables` parameter, and verify that subsequent components can read the new variable values.
- Check the format of the `messages` parameter, confirm that each message is labeled with the correct role (user/assistant), ensuring normal parsing of dialogue history.

The values provided are common starting points and should be evaluated against the reader's own samples.
