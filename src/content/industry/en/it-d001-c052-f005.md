# Code and Change Review Assistance for Customer Permission and Organizational Structure Configuration: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Data for this category is generated from configuration records for customer permissions and organizational structures. Data sources include customer HR systems, identity directories, product backends, and audit logs. Daily output documents include permission matrices, organizational structure tables, role configuration records, and permission change tickets. Data updates occur per ticket or irregularly, with no fixed schedule. Data fields include department hierarchy, role permission items, effective time, change approval status, and more. There are no unified mandatory units; values adjust based on the customer’s business configuration.

## What constraints do these characteristics impose on the multi-turn dialogue and prompt engineering link
The characteristics of this category’s data impose multiple constraints on the multi-turn dialogue and prompt engineering link. Because data sources are scattered and updates are irregular, multi-turn dialogue must pass the current session’s associated customer identifier via `variables` to ensure only the target customer’s permission data is loaded. Because document types vary, `messages` must split context blocks by document category to avoid mixing different types of data such as permission matrices and organizational structure tables. Because data has no fixed units and adjusts based on customer configurations, prompt engineering must explicitly require verifying the customer adaptability of fields during dialogue to prevent incorrect cross-business scenario mappings. Additionally, session context must associate the customer’s organizational scope bound to `chatId` to prevent cross-customer leakage of permission data.

## Three common mistakes
- Phenomenon: The permission configuration results returned by online dialogue and API calls differ significantly. Results remain inconsistent when the API is set to `stream` = false and `detail` = true. Cause: The customer identifier parameter for the API call is not passed via `variables`, causing the API session to load permission data for a non-target customer by default, which does not match the customer context of the online session.
- Phenomenon: The comment trigger timing of the workflow AI dialogue component does not match expectations, with prompts triggering only after the stream reply completes. Cause: The permission change record context for triggering comments is not correctly configured in `messages`, causing the component to only read the latest configuration data after the full dialogue flow ends.
- Phenomenon: After migrating the knowledge base, the model prompts that the knowledge base is empty during dialogue, but all content is visible on the knowledge base page. Cause: The migrated knowledge base is not bound to the current customer’s session via `chatId`, causing the dialogue session to fail to read the migrated permission configuration knowledge base data.

## How to confirm the configuration is complete
- Check if `chatId` is bound to the organizational structure ID of the current customer. This can be confirmed by viewing the associated identifier in the session log.
- Verify that context blocks in `messages` are split by permission document category. This can be confirmed by printing the content structure of the session context.
- Confirm that `variables` pass the root node identifier of the current customer’s permissions. This can be confirmed by triggering a test dialogue and viewing the variable transfer log.
- Test parameter consistency between API calls and online dialogue, ensuring both pass matching customer identifiers and context configurations.
