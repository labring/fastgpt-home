# Code and Change Review Assistance for Container Platform Operations: Multi-turn Dialogue and Prompt Engineering

This page configuration is based on FastGPT v4.17.0.

## What the data for this category looks like

Core data for container platform operations comes from Kubernetes API, image registries, monitoring systems, and CI pipelines. It updates daily or after each cluster change completes. Daily operation documents include cluster change tickets, namespace quota tables, deployment records, and fault reports. Fields cover cluster node count, Pod running status, image tags, change ticket numbers, and resource quota values. Units include servers, cores, MB, and others. The content of each document updates in real time alongside cluster status and change operations.

## Constraints These Characteristics Impose on Multi-turn Dialogue and Prompt Engineering

Data sources for container platform operations are scattered and update frequently. Multi-turn dialogue must strictly limit context scope to avoid introducing outdated cluster status information. Daily document structures vary, but core fields are consistent. Prompts must adapt to each document’s field formats to correctly identify key content such as change tickets and quota tables. The most time-consuming resource quota adjustment and Pod exception troubleshooting workflows require multi-turn dialogue to retain breakdown keywords from historical questions, eliminating repeated questions. Errors directly impact business operations. Dialogue results must clearly link to data sources to help reviewers verify information accuracy.

## How to Configure Settings

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique ID of the cluster change ticket | Daily operation documents take cluster change tickets as the core. `chatId` can be used to associate the full process context of the corresponding change |
| `messages` | Retain the last 3 rounds of dialogue content related to the current review | Container platform operation data updates daily or per change. Excessive historical content will introduce outdated information |
| `variables` | Automatically inject current namespace quota and Pod exception type fields | Core fields in operation scenarios can be batch passed via `variables`, simplifying prompt writing |
| Context window length | 800–1200 characters | The effective content length of a single cluster change ticket usually falls within this range, adapting to model context limits |
| Dialogue timeout | 60 seconds | Troubleshooting operations for container platform operations require timely feedback. Excessive timeout will reduce review efficiency |
| Data source identifier binding | Enable resource ID association | Data sources include Kubernetes API, image registries, and others. Clearly marking information sources helps reviewers |

## Three Common Configuration Mistakes

- Dialogue requests do not return reference identifiers: The interface return result lacks a unique identifier field for associated resources. This occurs when the data source identifier binding configuration is not enabled, and resource IDs from sources such as Kubernetes API are not injected into the dialogue context.
- Multi-turn dialogue loses historical question keywords: The second round of dialogue does not associate the content of the question breakdown raised in the first round. This occurs when the context of the corresponding session is not bound via `chatId`, resulting in historical messages not being loaded correctly.
- Agent thinking process is not hidden: Thinking process output is configured, but thinking logs are still displayed in the front-end dialogue. This occurs when the display filtering rules in `variables` are not correctly configured, and the context settings of the corresponding agent are not associated.

## How to Verify the Configuration Is Complete

- Initiate a test dialogue that includes cluster change ticket content. Check if the return result associates the unique identifier of the corresponding change ticket.
- Initiate two rounds of related test dialogues. Confirm whether the second round of replies is based on the question raised in the first round.
- Configure the agent and initiate a test request. Check if thinking process logs are not displayed in the dialogue record.
- View the `messages` field returned by the interface. Confirm that only dialogue content related to the current review is retained.
