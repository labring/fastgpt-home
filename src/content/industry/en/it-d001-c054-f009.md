# Code and Change Review Assistance for Container Platform Operations: Tool Calling and Plugins

This document is written for FastGPT v4.17.0.

## What Typical Data for This Category Looks Like
Typical data sources for this category include Kubernetes APIs, image registries, monitoring systems, and CI pipelines. Daily generated documents include cluster change tickets, namespace quota tables, deployment records, and failure reports. Updates are triggered daily or after each cluster change.
Data fields include cluster node IDs, Pod running status, resource quota thresholds, change execution times, and more. Units include CPU cores, memory in MB, number of changes, and others. The field structure varies across different documents, with no unified standard format.

## Constraints Imposed on Tool Calling and Plugins Workflow
Multiple data source calling requirements mean plugins must support integration with multiple external interfaces, and adapt to authentication and response formats of different interfaces.
Non-standardized document structures require flexible field parsing rules to be configured during tool calling, to prevent data extraction failures due to format differences.
Uncertain update frequencies mean plugins must support on-demand data pulling, without relying on fixed-cycle caching mechanisms.
High-frequency, time-consuming tasks require tool calling to prioritize scenarios such as resource quota adjustment, Pod exception troubleshooting, and cluster upgrade verification. An exception alert mechanism must also be configured to address business interruption risks.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | Automatically match available tools for the current review scenario, adapting to multi-data-source calling requirements for container operations |
| `functionCall` | `enabled` | Enable explicit function call mode, ensuring the change review process follows preset rules strictly |
| Plugin timeout duration | 600 seconds | Match the typical response duration of container cluster APIs, avoiding interruptions to complete review workflows |
| Tool call retry count | 2–3 times | Address temporary fluctuations in cluster API availability that cause call failures, reducing review blocking |
| Data pull time range | Previous 7 days | Align with the typical historical data reference cycle for container operation change reviews |

## Three Common Misconfigurations
- Symptom: The `functionCall` parameter is not correctly configured when calling the FastGPT session interface, causing the tool to fail to trigger change review-related logic. Cause: Explicit function call mode is not explicitly enabled, and preset container operation plugins are not called in the default mode.
- Symptom: The plugin timeout duration is set to less than 300 seconds, leading to frequent call timeout errors. Cause: The typical response duration of container cluster APIs is not matched, causing normal calls to be incorrectly identified as timeouts.
- Symptom: Workflow orchestration logic is directly written into plugin configurations, causing plugin execution exceptions. Cause: The responsibility boundaries between workflows and plugins are confused. Plugins are only responsible for single tool calls and data acquisition, not full workflow orchestration.

## How to Verify Successful Configuration
- Submit a simulated cluster change review request, check if the tool call logs show the matching `toolChoice` and `functionCall` parameters.
- View the timeout duration setting on the plugin configuration page, confirm it matches the typical response duration of container cluster APIs.
- Test the data pull range, confirm only change records and cluster data from the previous 7 days are returned.
- Trigger a simulated API call failure scenario, check if retry logic is executed as configured.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
