# Code and Change Review Assistance for Object Storage and Backup Services: Tool Calling and Plugins

## What data for this category looks like
Core data for object storage and backup services typically originates from object storage consoles, backup systems, access logs, and customer policy tables. Daily maintenance documents include storage bucket configurations, backup policies, recovery records, and lifecycle rules. Fields cover storage bucket names, backup execution cycles, recovery status, permission rules, and more. Update frequency is daily or real-time when policies are changed. Data exists as structured text and log files. The number and format of fields per record vary slightly based on service configuration rules.

## Constraints on tool calling and plugins
Multiple data sources require plugins to be compatible with API formats of different systems, preventing call failures due to mismatched data formats. Uncertain update frequencies require tool calling cache policies to adapt to real-time and batch pull scenarios, avoiding retrieval of expired storage bucket configurations or backup records. Unique document field characteristics require tool parameters to explicitly map storage-specific fields. Using generic document parsing parameters will fail to accurately pull storage data related to code reviews. Data compliance requirements mean tool calls must follow storage service permission rules, preventing unauthorized access to sensitive backup and recovery records.

## How to configure
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapts to the need to dynamically select storage-related tools during code reviews, automatically triggering corresponding tools based on context |
| `functionCall` | `required` | Code and change review assistance must forcibly obtain real data from storage services, and cannot rely solely on speculative content generated by large models |
| Tool call timeout setting | `300 seconds` | Cross-system storage data pulling has network latency, reserve sufficient response time to avoid mid-call timeouts |
| Tool call retry count | `2 times` | Addresses temporary fluctuations in storage console access, reduces call failures caused by single network jitter |
| Tool return data filtering rules | `Only retain storage fields associated with the current review` | Reduces redundant data occupying context space, improves response efficiency for code reviews |

## Three common misconfigurations
- Symptom: Custom plugins added to a workflow do not display input and output parameters. Cause: Storage-specific fields such as bucket configurations and backup policies were not correctly mapped in plugin configurations, and only generic parameter templates were used.
- Symptom: An error with empty return parameters occurs after calling the file upload tool. Cause: The tool's object storage file access path parameters were not correctly configured, making it impossible to locate uploaded file resources.
- Symptom: Tool call timeouts occur during code reviews. Cause: No reasonable tool call timeout duration was set, or redundant storage access log data was not filtered, leading to context overload.

## How to confirm correct configuration
- Submit a simulated code review request, check if tool call logs successfully pull configuration data for the corresponding storage bucket.
- Manually modify one backup policy, verify that the plugin can automatically retrieve the updated policy information and include it in review references.
- Test the plugin's input and output parameter mapping, confirm that storage-related fields can be properly passed and called in the workflow.
- Trigger a tool call timeout scenario, verify that the retry logic automatically retries the configured number of times and returns valid results.

The values provided here are common starting points and should be measured against the reader's own samples.
