# Code and Change Review Assistance for Ticket Acceptance and Problem Tiering: Tool Calling and Plugins

## What this category of data looks like
Data for this category originates from ticketing systems, chat logs, product logs, and customer contract SLAs. Update frequency is daily or real-time. Daily documents include customer tickets, problem tiering tables, processing records, and service reports. Customer tickets include fields for customer identification, problem description, and submission time. Problem tiering tables include priority tags and responsible team mapping fields. Processing records include fields for response duration and resolution results. Service reports include fields for SLA compliance statistics. Data structure adjusts based on a team’s tiering rules, with no fixed unified format.

## What constraints these characteristics impose on the tool calling and plugins workflow
Dispersed data sources with no fixed format require tool calling to support dynamic field extraction. Hardcoding to adapt to a single team’s document structure must be avoided. Update frequency falls into two categories: real-time and daily. Plugin trigger timing must align with these categories. Real-time tickets require immediate tool calls to complete tiering. Daily service reports can be processed using batch plugin tasks. Data volume fluctuates with ticket peaks. The concurrency threshold for tool calls must match a team’s daily load. Some data relies on historical processing records. Plugins must support cross-data source association queries. They must also handle exceptions for missing fields, and adapt to open-source MCP server-type plugin templates.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | Adapts to the dynamically changing ticket fields in this category, automatically selecting matching tool calling logic |
| `functionCall` | `disabled` | Prevents calling failures caused by dynamic fields; enable only when fixed calling is explicitly required |
| Tool call timeout duration | 600 seconds | Matches common timeout scenarios, preventing task interruptions from overly long single calls |
| Number of results returned per call | First 5 entries | Adapts to the core associated data volume required for problem tiering, avoiding excessive redundant information that disrupts judgment |
| Context window size | 800–1200 characters | Adapts to the typical content length of tickets and tiering tables, balancing information completeness and calling efficiency |
| Batch task interval | 1 day | Aligns with the processing rhythm of daily service reports, avoiding resource occupation from frequent calls |
| FastGPT version | FastGPT v4.17.0 | Ensures compatibility and functional completeness of plugin configurations |

## Three common configuration mistakes
- Symptom: Knowledge base call returns do not match ticket content. Cause: Failed to associate the correct data source, and incorrectly called unrelated product logs or historical records.
- Symptom: Single tool call duration exceeds 600 seconds. Cause: No reasonable timeout limit set, or cross-data source query tasks beyond the current configuration range were called.
- Symptom: Third-party model call failed. Cause: Model calling parameters were not configured correctly, or the model’s interface format requirements were not adapted to.

## How to confirm configurations are correct
- Submit a test ticket, check the tool calling logs, confirm that the automatic selection logic for `toolChoice` works properly.
- Simulate a timeout scenario, verify whether the plugin’s timeout handling mechanism triggers preset exception alerts.
- Adjust the tiering tag of a ticket, confirm whether the plugin can correctly associate the corresponding historical processing record.
- View the FastGPT plugin management page, confirm that the configuration item values match the current settings.
