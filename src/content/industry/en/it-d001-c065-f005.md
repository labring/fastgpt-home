# Code and Change Review Assistance for Interface Integration and Data Docking: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Data for this category comes primarily from client system interfaces, API documentation, test data, and integration debugging logs. Daily maintained documents include interface lists, integration debugging records, field mapping tables, and issue tracking tables. Data updates occur daily or are adjusted based on project phases. Data fields include interface addresses, request methods, parameter names, data types, return codes, and mappings between business fields and system fields. Some data includes units, such as request timeout milliseconds and data transmission byte count.

## Constraints on Multi-turn Dialogue and Prompt Engineering
The data characteristics of this category create multiple constraints for multi-turn dialogue and prompt configuration. Data sources are scattered and require real-time alignment. Multi-turn dialogue must be used to gradually integrate interface information from different sources. Field mapping involves converting between business and system terminology. Prompts must clearly guide alignment of terminology standards. Data update frequency is not fixed. Dialogue must support dynamic loading of the latest interface lists and integration debugging records. Issue tracking tables are linked to exception troubleshooting information. Prompts must support associating context from historical issues.

## How to Set Configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Generate a unique identifier per integration debugging session | Used to associate context for a single round of debugging validation |
| `messages` | Retain the first 15 rounds of dialogue content | Covers history of field alignment and link troubleshooting during integration debugging |
| `variables` | Load the current project's interface list and field mapping table | Provides real-time business data support for dialogue |
| Timeout Setting | 600 seconds | Adapts to long-link troubleshooting and data pull time consumption during interface integration |
| Maximum Context Length | 8000–12000 characters | Covers core content of interface lists, integration debugging records, and field mapping tables |
| Issue Optimization Switch | Calibrate based on actual testing | Automatically organizes exception descriptions and troubleshooting steps during integration debugging |

## Three Common Misconfigurations
- Phenomenon: Request timeout error occurs during dialogue, with prompt text containing Request Time. Cause: The timeout threshold is not adjusted for long-link troubleshooting during interface integration, and the default timeout duration is insufficient to cover troubleshooting time for complex interfaces.
- Phenomenon: Form input content of workflow configuration cannot be displayed in dialogue. Cause: The variable call switch is not enabled, causing dynamic fields in integration debugging scenarios to fail to load into the dialogue context.
- Phenomenon: After uploading the interface list document, the dialogue cannot correctly identify parameter mapping relationships. Cause: The maximum context length is not adjusted to the range adapted to the total word count of the document, causing core field information to be truncated.

## How to Verify Configurations Are Correct
- Initiate a single round of debugging dialogue, input interface parameters to query requests, and check whether the dialogue context includes the current project's interface list and field mapping table.
- Simulate exception troubleshooting during the integration debugging process, and check whether the dialogue can associate historical issue tracking records.
- Adjust the timeout setting, initiate a dialogue involving long-link troubleshooting, and confirm that no timeout errors occur.
- After enabling the issue optimization switch, input an integration debugging exception description, and check whether the dialogue automatically organizes it into structured troubleshooting steps.

The values provided are common starting points and should be measured against the reader's own samples.
