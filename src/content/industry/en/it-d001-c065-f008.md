# Code and Change Review Assistance for Interface Debugging and Data Integration: Workflow Orchestration

## What this category of data looks like
The data for this category typically comes from customer system interfaces, API documentation, test data, and debugging logs. Update frequency is daily or within each phase delivery cycle. Documents maintained daily include interface inventories, debugging records, field mapping tables, and issue tracking sheets. Data fields cover interface addresses, request methods, parameter definitions, return field mappings, exception status codes, and more. There are no uniform mandatory units, with adjustments made based on specific integration scenarios.

## What constraints do these characteristics impose on workflow orchestration
This category of data originates from multiple sources and updates frequently. This requires workflows to support dynamic pulling of the latest interface configurations and debugging logs. Daily documents are primarily structured tables, so workflows must adapt to structured data reading nodes to enable automatic verification of field mapping relationships. The most time-consuming field specification confirmation step requires workflows to add field consistency verification nodes to reduce manual verification costs. As this involves continuous real-time interface interaction between systems, workflows must support cyclic calls and batch orchestration. Exception capture and rollback mechanisms must also be configured to prevent data inconsistency or business interruptions.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Include interface addresses, request parameters, field mapping rules, file upload paths | Used to pass dynamic data required for debugging, adapting to multi-interface parallel debugging scenarios |
| `nodeId` | Assign a unique `nodeId` by interface group, label the interface name | Used to locate each interface debugging node, facilitating troubleshooting of call links and log backtracking |
| Retry Count | 3 times | Addresses temporary interface jitter or network fluctuations, meeting conventional exception recovery needs for debugging scenarios |
| Timeout Duration | 300 seconds | Adapts to response times of complex interfaces, avoiding workflow interruptions due to excessive waiting |
| Context Window | Retain the first 3 debugging logs of the current session | Used to review historical operations during reviews, avoiding association with irrelevant global historical records |
| File Upload Limit | Support uploading interface documents and test case files ≤1000 MB | Used to supplement reference materials required for debugging, adapting to file size requirements for conventional integration scenarios |

## Three Common Mistakes
- Only retaining 1 chat record in workflow configuration, but reviews still associate with outdated historical debugging logs. This occurs because the context window configuration range is not limited to the current debugging session, and global historical data is pulled by default.
- Unable to upload files when calling the workflow via API, and unable to pass parameters for file-type variables. This occurs because the parameter format for file uploads is not correctly declared in `variables`, or the corresponding file storage node is not bound.
- After upgrading to FastGPT v4.14.0, an error prompt of Failed to create post presigned url appears when uploading files. This occurs because the workflow's file presign configuration does not adapt to the storage rules of FastGPT v4.17.0, requiring re-verification of node configurations.

## How to Confirm Proper Configuration
- After triggering the workflow, check whether the interface parameters passed in `variables` match the configuration of the current debugging task.
- View the workflow node logs to confirm that the interface call links corresponding to each `nodeId` are correct, with no node misalignment or missing parameters.
- After uploading a test file, verify that the workflow can correctly read the file content and participate in the debugging verification link.
- Simulate interface timeout or abnormal return scenarios, and confirm that the workflow can normally resume execution after triggering the retry mechanism.
