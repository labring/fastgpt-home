# Code and Change Review Assistance for Database Cloud Service Operations: Multi-turn Dialogue and Prompts

## What Data Falls Under This Category
Data for this category typically comes from cloud database consoles, slow query logs, cluster monitoring metrics, and operation ticket systems. Daily generated documents include instance change orders, backup and restore records, performance diagnosis reports, and parameter adjustment records. Each document contains fields such as unique instance identifier, change time, operation content, and associated ticket number. Monitoring metrics and slow logs update per minute or hour, while instance change data updates in real time with each change operation.

## What Constraints Do These Characteristics Impose on Multi-turn Dialogue and Prompt Workflows
Dispersed data sources require multi-turn dialogue to gradually pull information from different systems. For example, first obtain basic instance information from the console, then query slow logs to locate issues. Large differences in document structure mean prompts must adapt to different formats of change orders and diagnosis reports, and field extraction rules must be clarified during multi-turn interactions. Differences in update frequencies require dynamic filtering of the latest data during dialogue to avoid referencing expired monitoring metrics or completed change records. In multi-tenant scenarios, strict isolation of different customers’ operation data is required, and prompts must be bound to the tenant identifier of the corresponding session.

## How to Configure
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique identifier of the cloud database instance | Ensure multi-turn dialogue context only associates with the specified instance, avoiding cross-tenant data confusion |
| `messages` | Limit the single-turn context window to the first 20 dialogue records | Adapt to the concise and efficient interaction in operation scenarios, avoiding response delays caused by overly long context |
| `variables` | Preset operation-specific variables such as instance ID and ticket number | Reduce repeated input and improve the accuracy of multi-turn dialogue |
| Maximum context length | 8000–12000 characters | Cover the content length of common documents such as instance change orders and performance reports, calibrated based on actual testing |
| Single dialogue return limit | Top 3 matched slow log records | Avoid returning excessive data that causes dialogue lag, aligning with the conventional granularity of operation troubleshooting |

## Three Common Misconfigurations
- Uploaded files such as change orders and backup records cannot be correctly read or associated during dialogue. The cause is that correct session storage binding rules are not configured, resulting in files not being archived according to the storage logic of cloud operation scenarios.
- Uncaught exceptions occur when calling the AI dialogue component in a workflow. The common cause is an incorrect format for preset variables in the configuration file that does not match the field requirements of cloud database operations.
- Frequent crashes occur on the dialogue page or knowledge base page. The cause is that the context window length for `messages` is not limited, causing the session context to occupy excessive memory resources.

## How to Verify Successful Configuration
- A test dialogue containing an instance ID may be initiated, and the session log can be reviewed to confirm the instance identifier bound to `chatId` is correctly displayed.
- The AI dialogue component within a workflow can be tested by calling it, and uncaught exceptions can be checked to confirm they are absent, and the preset operation variables in `variables` can be verified to be passed correctly.
- A slow log document can be uploaded and a query initiated, and the generated review results can be checked to confirm they include slow SQL-related information from the document.
- More than 10 consecutive dialogues may be initiated, and the page can be checked to confirm no crashes occur, verifying that the context window configuration takes effect.
