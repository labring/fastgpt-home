# Code and Change Review Assistance for Database Cloud Service Operations: Workflow Orchestration

## What data for this category looks like
This category of data typically comes from cloud database consoles, slow logs, monitoring metrics, and ticketing systems. Daily produced documents include instance change orders, backup and recovery records, performance diagnosis reports, and parameter adjustment records. Data fields include instance unique identifiers, change execution times, slow SQL response durations, backup file capacity, tenant permission scopes, and more. The update rhythm is daily synchronization or updates triggered by a single change. Operation and maintenance data from different tenants are isolated from each other and not shared across tenants.

## What constraints these characteristics impose on the "workflow orchestration" link
Because data sources are scattered and multi-tenant isolation is in place, workflow orchestration must connect at least three types of data source nodes to complete console configuration, slow log parsing, and ticketing status pulling. Data updates are triggered by single changes, so the workflow must bind the submission event of an instance change order as the startup condition. Fixed scheduled triggers cannot adapt to on-demand change scenarios. Operation and maintenance data from different tenants are isolated from each other, so workflow node identifiers must be associated with tenant permission scopes to prevent cross-tenant data access. At the same time, daily document fields vary widely, so unified field mapping rules must be configured during orchestration to reduce format conversion costs.

## How to configure settings
| Configuration Item | Recommended Approach | Basis for This Approach |
| ---- | ---- | ---- |
| Trigger Condition | Triggered by instance change order submission | Matches the rhythm of data updates triggered by single changes, ensuring the workflow starts only in valid operation and maintenance scenarios |
| Data Source Node Configuration | Deploy 3-5 data source nodes | Covers the three core data sources: cloud database console, slow logs, and ticketing system |
| `variables` | Uniformly map instance ID, change time, slow SQL list | Resolves inconsistencies in field formats across multi-source data, simplifying subsequent data calls for review nodes |
| `nodeId` Binding Rule | Associate tenant ID and instance unique identifier | Complies with the business requirements of multi-tenant isolation, preventing unauthorized cross-tenant data access |
| Timeout Threshold | 600 seconds | Adapts to the typical business time consumption of slow log parsing and backup and recovery record pulling |
| Field Validation Rules | Filter null values and invalid characters | Ensures the validity of input data for subsequent code review links |

## Three common mistakes
- The phenomenon is that the code execution node returns a permission denied or missing parameter log when running custom JS code. The cause is that the access token and instance permissions for the cloud database console are not configured in `variables`, causing the code node to fail to call compliant data source interfaces.
- The phenomenon is that the AI model selection dropdown list for the workflow is empty. The cause is that the model permissions for the corresponding cloud service are not bound, or FastGPT v4.17.0 has not been upgraded.
- The phenomenon is that calling the API to create a workflow returns a 404 status code. The cause is that the officially specified API path is not used, or the correct authentication token is not carried in the request header.

## How to confirm the configuration is complete
- Manually trigger the workflow bound to an instance change order, and check whether each data source node successfully pulls the corresponding data content.
- View the mapped fields in the `variables` configuration item, and confirm that the field names and formats of all core operation and maintenance data meet expectations.
- Verify the `nodeId` binding rule by attempting to access the workflow across tenants, confirming that operation and maintenance data from other tenants cannot be obtained.
- Submit a test instance change order, and check whether the workflow starts normally and completes the preset review process.
