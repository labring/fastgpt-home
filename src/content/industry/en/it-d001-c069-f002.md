# Code and Change Review Assistance for Database Operations: Context and Token

## What data belongs to this category
This category of data originates primarily from database monitoring, audit logs, SQL execution plans, and ticketing systems. Daily associated documents include database change orders, slow SQL reports, backup records, and permission application forms. These are maintained by DBAs, data platform operations teams, and backend teams.
Data updates occur daily, or synchronize with individual database changes. Each data entry includes fields such as SQL statements, execution duration, permission identifiers, and change content. There are no universal fixed units, as values vary by data type.

## What constraints these characteristics impose on context and token handling
Database operation and maintenance scenarios often use long-text contexts, including SQL fragments, full change order content, and historical operation records. The length of a single context often exceeds standard thresholds.
Frequent changes and daily updated data require contexts to sync latest ticketing and monitoring data promptly. This avoids associating outdated information.
Data formats vary widely across different sources. Contexts must use a unified structure during concatenation. Otherwise, token limits may be exceeded, or model parsing may fail.
DBAs must associate multiple historical changes and slow query records during reviews. The number of context entries must match actual review needs. Too many entries consume excessive tokens and slow model response. Too few fail to cover required associated logic.

## How to set configurations
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value Range | Rationale |
| ---|---|--- |
| `maxContext` | Top 10-15 entries | A single database operation review typically uses fewer than 10 historical changes and monitoring data entries. Excessive entries consume too many tokens and slow model response |
| `quoteMaxToken` | 8000-12000 token | A single SQL execution plan or full change order content usually falls within this range. This avoids exceeding the token limit supported by the model |
| Context synchronization frequency | Synchronize on change trigger, once daily for routine updates | Database changes have strict timeliness. Outdated data causes review deviations, so associated contexts must be updated promptly |
| Context filtering threshold | Calibrated based on actual testing | Data density varies across different database instances. Must match actual recall results to avoid mixing irrelevant data |
| Context concatenation format | Unified "source + time + content" structure | Ensures the model can clearly identify different types of context data, avoiding parsing confusion |

## Three common configuration errors
- Symptom: The number of context entries displayed in conversation details does not match the configured value. For example, only 2 entries appear when 30 are configured. Cause: The context synchronization logic fails to correctly connect ticketing systems and database monitoring data sources, only recalling a portion of the latest data.
- Symptom: The AI reply includes unexpected JSON-formatted content. Cause: The context concatenation process did not standardize data formats. Unstructured original audit log content was mixed in, causing model parsing failures.
- Symptom: A context token limit exceeded error is triggered. Cause: The `quoteMaxToken` value was not restricted. Ultra-long SQL execution plans and multiple change orders were directly concatenated, exceeding the token limit supported by the model.

## How to confirm configurations are properly set
- Review context recall logs to confirm that recalled data sources include target documents such as database change orders and slow SQL reports.
- Test a single review request to check that the number of returned context entries matches the configured `maxContext` value.
- Simulate concatenation of ultra-long SQL and multiple historical data entries to verify that no token limit exceeded error is triggered.
- Manually modify a historical change order to confirm that subsequent review requests can access the updated content.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
