# Code and Change Review Assistance for Database Operations: Multi-turn Dialogue and Prompt Engineering

## What Data Looks Like for This Use Case
Data for database operations scenarios comes from database monitoring, audit logs, SQL execution plans, and ticket systems. Daily associated documents include database change orders, slow SQL reports, backup records, and permission application forms. Change orders include fields such as instance identifiers, change statements, and application times. Slow SQL reports include metrics such as response duration and scanned row counts. Data updates occur daily or with each database change. The volume of data associated with a single change fluctuates based on instance scale, with no fixed unified threshold.

## Constraints on Multi-turn Dialogue and Prompt Engineering
These characteristics impose constraints on multi-turn dialogue and prompt engineering. Multi-turn dialogue must gradually integrate information from different sources, as data comes from dispersed locations and single changes are linked to multiple document types. This prevents missing key constraints. Data update frequency aligns with changes, so dialogue context must be limited to the time range of the current change. This avoids introducing irrelevant historical data. Document structures vary significantly, so prompt engineering must clearly specify rules for extracting corresponding fields. This prevents models from confusing field definitions across different documents. Review errors can lead to data corruption or permission overreach, so multi-turn validation steps must be added to the dialogue process. This ensures each change request meets compliance requirements.

## Configuration Settings
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| Context window size | 8000–12000 characters | Based on the typical document size of database change orders, avoids context overload while covering all critical information for a single review |
| Variable binding rules | Only bind associated data for the current ticket in `variables` | Isolates permissions and change data across different tickets, prevents context pollution |
| Dialogue trigger logic | Triggered by user input in `messages` | Aligns with the interaction rhythm of manual reviews, triggers model responses only when user requests are made |
| Maximum interaction rounds | 15 rounds | Based on the fact that troubleshooting steps for complex change reviews typically do not exceed 15, terminates dialogue after timeout to avoid unnecessary resource usage |
| Response format validation | Enable JSON format validation | Requires structured output for operation review results, facilitating subsequent integration with ticket systems |
| Session ID binding | Bind the `chatId` parameter | Ensures correct context association for multi-turn dialogue, avoids session confusion |

## Three Common Misconfigurations
- Multi-turn dialogue context is lost, only the most recent 3 messages are retained. This occurs when context retention rules are not configured correctly, only the latest interaction content is loaded, and historical data from the `messages` parameter is not associated.
- Generated JSON responses do not match the preset format, and cannot be parsed by ticket systems. This happens when field constraints are not clearly specified in the prompt, or response format validation is not enabled, leading to chaotic output formatting.
- Single-turn dialogue responses time out, taking longer than 30 seconds. This occurs when too many unrelated database monitoring data points are bound, leading to model context overload, and no reasonable timeout threshold is set.

## How to Verify Correct Configuration
- Import a test database change order, initiate the first dialogue, check if all interaction content is retained in the conversation history, and verify that the `chatId` parameter correctly binds the session ID.
- Trigger a review request, check if the generated response matches the preset JSON structure, and confirm that `variables` only loads associated data for the current ticket.
- Simulate multi-turn interactions, observe if response times fall within a reasonable range, and confirm that maximum interaction rounds and timeout threshold configurations align with actual business rhythms.
- Input an unauthorized SQL statement, check if the model correctly identifies and alerts to the risk, and verify that the configured constraints take effect.
