# Code and Change Review Assistance for Database Operations: Tool Calling and Plugins

## What data for this use case looks like
Core data for database operations scenarios comes from database monitoring systems, operation audit logs, SQL execution plan files, and ticketing systems. Daily generated documents include database change orders, slow SQL analysis reports, backup and recovery records, and permission application forms. Change orders include instance identifiers, change statements, approval status, and execution time. Slow SQL reports record query duration, scanned row counts, and blocking duration. Data updates are triggered by operations: a single database change corresponds to one update, and daily monitoring data is aggregated on a daily basis.

## What constraints these characteristics impose on the tool calling and plugins link
Data sources for database operations are scattered and have varying formats. Tool calling plugins must adapt to parsing rules for multiple data source types to avoid data pull failures due to format mismatches. Data updates are triggered by changes or on a daily schedule. Tool calls must match the corresponding trigger timing to ensure the latest change and monitoring data is available during reviews. Document fields are numerous and closely linked. Tool calls must accurately extract specified fields for analysis to avoid redundant information interfering with reviews. Additionally, errors in this scenario directly affect database stability. Tool calls must include built-in parameter validation logic to prevent illegal operations from being triggered.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `["function"]` | Force lock the tool calling mode to prevent the AI from generating both direct replies and tool calling requests |
| `functionCall` | Only pass database-related parameters | Ensure tool calls only process requests for database operations scenarios to avoid interference from unrelated parameters |
| Tool call timeout duration | 600 seconds | Match the average processing duration of database change reviews to prevent review process interruptions due to timeout |
| Number of data items returned per tool call | First 10 items | Adapt to the single-batch data volume of slow SQL reports and change orders to avoid context overload affecting analysis |
| Context window size | 8000 token | Accommodate complete change order and slow SQL data to ensure complete analysis during tool calls |
| Data source plugin binding rules | Match by database instance type | Adapt to monitoring and audit log formats for different databases to ensure accurate data pulling |

## Three common mistakes
- After configuring fixed reply rules, the tool still automatically generates direct AI replies. Troubleshooting items include: failing to use the `toolChoice` parameter to force lock the tool calling mode, causing the AI to trigger both direct reply and tool calling logic.
- Missing fields in slow SQL data returned by tool calls. Troubleshooting items include: failing to match the audit log plugin format for the corresponding database, resulting in inability to extract specified fields during parsing.
- Frequent tool call timeouts. Troubleshooting items include: setting a timeout duration shorter than the average processing duration of database change reviews, or failing to configure connection timeout parameters for data sources.

## How to confirm the configuration is complete
- Check the environment variables of the App/Admin server. Confirm that `AIPROXY_API_ENDPOINT` (root address of the AI Proxy service, for example http://aiproxy:3000; do not append paths such as /v1 or /chat/completions) and `AIPROXY_API_TOKEN` (AI Proxy administrator token, must match the AI Proxy server configuration and cannot be empty) are correctly configured and not empty, and meet the deployment requirements of FastGPT v4.17.0 and above.
- Submit a test database change order to trigger the tool calling process. Check whether the returned tool results include expected slow SQL data or change order information.
- View the AI Proxy service logs to confirm that tool calling requests have been sent normally, the returned status code is 200, and no error messages are present.
- Adjust the `toolChoice` parameter to `none` to verify that the tool will not trigger automatically at this time, and only return preset content according to the configured rules.
