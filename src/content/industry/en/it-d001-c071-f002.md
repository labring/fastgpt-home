# Code and Change Review Assistance for Data Masking: Context and Token

## What This Category’s Data Looks Like
Data originates from databases, data dictionaries, masking tools, and access approval systems. Update frequency follows per-batch or per-project cycles. Daily produced documents include masking plans, field mapping tables, masking validation reports, and approval records. Field mapping tables contain two core fields: sensitive field identifiers and masking rule codes. Masking validation reports include validation batches, compliance item matching results, and similar content. All data updates as projects progress or batch tasks complete.

## Constraints on Context and Token
Dispersed data sources cause large fluctuations in single-batch context data volume. The per-batch or per-project update rhythm demands context loading adapt to task cycles and avoid redundant loading. Diverse document structures have significant field differences between mapping tables and validation reports. This requires precise matching of field types for context fragments to prevent invalid token usage. Sensitive field recognition relies on multi-source data correlation. Excessively long contexts cause excessive token consumption, slowing review assistance response times. The timeliness of approval records also demands prioritizing the latest compliant approval data in context loading, further limiting context cache scope.

## Configuration Settings
The following context and token configuration scheme is tailored to the characteristics of this category, based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | 2000–5000 token | Adapts to total data volume fluctuations per batch or project, avoids exceeding single-context token limits |
| `quoteMaxToken` | 800–1200 characters | Matches the average length of single document segments from field mapping tables and masking validation reports |
| Context Loading Priority | Load latest approval records first | Adapts to the update rhythm of per-batch or per-project data, ensures compliant data takes effect first |
| Single-Context Segment Truncation Threshold | 1500 characters | Filters non-core redundant fields, reduces invalid token consumption |
| Token Exceedance Handling Method | Automatically truncate non-core masking plan segments | Ensures basic functionality of code review assistance operates normally |

## Three Common Misconfigurations
- Phenomenon: Token exceedance error occurs when starting the code review assistance service, with logs showing context loading failure. Cause: The `maxContext` parameter was not adjusted based on per-project data volume, causing total token count of loaded masking data to exceed thresholds.
- Phenomenon: Token consumption is duplicated for masking data context in multi-model orchestration workflows. Cause: No context sharing rules were configured, causing each model to independently load identical field mapping table data.
- Phenomenon: Core fields in masking validation reports fail to match correctly in review code. Cause: No single-context segment truncation threshold was set, excessively long document segments consume too many tokens, leading to accidental truncation of core fields.

## How to Verify Proper Configuration
- Review context loading logs to confirm loaded data types match current project’s masking document types.
- Trigger a code review task, check that token consumption falls within preset ranges and no exceedance prompts appear.
- Cross-check token usage across multi-model workflows, confirm masking data context is not loaded repeatedly.
- Simulate a token exceedance scenario, verify that preset truncation logic triggers and core sensitive fields are not lost.
