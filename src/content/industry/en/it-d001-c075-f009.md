# Code and Change Review Assistance for Documentation Site Maintenance: Tool Calling and Plugins

## What the data for this category looks like
The core data for documentation site maintenance usually comes from code repositories, documentation site build logs, user feedback, and version release records. Daily produced documents include installation documentation, API documentation, migration guides, and FAQs. Each document contains fields such as version number, update time, sample code blocks, and interface paths. Data update frequency is mostly weekly or triggered by version releases, with update rhythms varying across different document types. The most time-consuming links are often sample verification, version difference synchronization, and expired content cleanup. Errors may lead to users being unable to install software, misusing interfaces, or an increase in the number of issues.

## What constraints these characteristics impose on the "tool calling and plugins" workflow
Since data sources include code repositories and build logs, tool calling needs to support pulling documentation content from specified repository branches, and parsing error information in build logs. The data update frequency is weekly or per version, so tool triggering timing must match this rhythm to avoid frequent pulling of redundant data. There are diverse document types with code examples, so plugins need to adapt to parsing rules for different documents and automatically verify the validity of sample code. User feedback and version records require the tool to synchronize updates for expired content and version difference information, reducing manual cleanup costs.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale for This Setting |
| ---- | ---- | ---- |
| Tool calling trigger timing | Set according to documentation version release nodes or 2:00 AM every week | Matches the weekly/per-version update frequency of documentation, avoids redundant pulling |
| `toolChoice` | Automatic mode | Adapts to parsing needs for different document types, no need to manually specify individual functions |
| Plugin input parameter format | Include documentation path, repository branch, build log ID | Corresponds to field requirements for data sources from code repositories and build logs |
| Timeout threshold | 600 seconds | Covers full pull and parsing time for large documentation sites, calibrated based on actual testing |
| Maximum number of documents pulled per call | 50 entries | Controls resource consumption for tool calls, adapts to the conventional data scale of documentation sites |
| `functionCall` | Enable only when custom parsing logic is required | Adapts to customized processing needs for complex documents |

## Three common mistakes
- Unable to pass file-type input parameters when calling HTTP tools, resulting in incorrect return parameter formats. Cause: No file validation rules configured for plugin input parameters, causing the tool to fail to recognize binary file streams.
- Confused execution order of RAG knowledge base and tool calls in workflows, unable to obtain the latest documentation data synchronously. Cause: Trigger timing not set according to documentation update frequency, causing the called knowledge base content to lag behind the current code version.
- Individual plugin export failure, with exported files being empty or having abnormal formats. Cause: Incorrect configuration of plugin output format parameters, or missing session ID leading to lost context association.

## How to confirm the configuration is correct
This verification process applies to FastGPT v4.17.0.
- Trigger a tool call, check if the returned documentation content matches the latest commit of the current repository branch.
- View workflow run logs to confirm that the execution order of the RAG knowledge base and tool calls conforms to the preset configuration.
- Try exporting an individual plugin, check if the format and content of the exported file meet the requirements for documentation site maintenance.
- Initiate a session, check if the current session ID is correctly passed when the LLM is called, ensuring normal context association.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
