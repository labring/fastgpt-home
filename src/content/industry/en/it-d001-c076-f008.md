# Code and Change Review Assistance for Log Platforms and Observability: Workflow Orchestration

## What the data for this category looks like
Data for this category primarily comes from log systems, trace platforms, metrics systems, and application SDKs. Daily maintenance documentation includes log collection specifications, link tracing guidelines, metric dictionaries, and dashboard configuration records. Data updates occur daily or when each version is released.
Log data includes timestamps, service names, log levels, and context correlation IDs. Trace data includes global trace IDs, node latency, and call chain paths. Metric data includes metric names, sampled values, and statistical cycles, with units including milliseconds, bytes, request counts, and other common units.

## Constraints Imposed on Workflow Orchestration by These Characteristics
Dispersed data sources and inconsistent formats require workflow orchestration to support multi-data source format conversion nodes, adapting to field mapping rules of different systems.
Volatile update frequencies require configuring dynamic trigger mechanisms, supporting process startup on a schedule or via version release events.
Data correlation relies on context IDs and trace IDs. Workflows must include built-in field validation nodes to ensure correlation fields are not empty before executing subsequent steps.
Unified field naming standards do not exist for log and trace data. Custom field mapping configuration items must be reserved in orchestration to adapt to collection specifications for different businesses.
Batch pulling log and trace data has fluctuating latency. Reasonable timeout configuration space must be reserved to prevent process interruptions caused by data pull delays.
Field types differ between log and metric data. Type conversion nodes must be configured in orchestration to ensure fields from different data sources can be processed uniformly, adapting to code and change review assistance scenario requirements.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Globally shared scope | Supports sharing global variables between workflows and nested sub-workflows, adapting to data transfer needs across multiple steps |
| `nodeId` | Named by data source type | Facilitates locating execution exceptions across multiple nodes, matching the node correlation logic for log and trace data |
| Global variable scope | Effective across nodes | Adapts to field transfer across different data sources, aligning with the business scenario of log platform data correlation |
| Multi-model token management | Independent counting | Independently counts token consumption for different large model calls, preventing single-model quota limit triggers from exceeding usage |
| Timeout threshold | 600 seconds | Adapts to batch pull durations for log and trace data, covering the time range for conventional data collection |
| Single-model token limit | 8000 token | Aligns with the general large model context window standard for FastGPT v4.17.0 |

## Three Common Configuration Mistakes
- Symptom: A "variable undefined" prompt appears after the process starts. Cause: Global shared variables are not pre-declared in the `variables` configuration item, preventing sub-workflows from reading parameters passed by the main workflow. This is a common misunderstanding of global variable configuration.
- Symptom: Token counts stack abnormally after multi-model calls. Cause: The multi-model token independent counting configuration is not enabled, causing token consumption from different large models to be counted together and exceeding the single-model context limit. This corresponds to the issue of shared AI model tokens.
- Symptom: No associated log data is returned after the process executes. Cause: No context correlation validation node is configured, causing empty correlation IDs to be passed to subsequent links, failing to match valid log or trace data.

## How to Confirm Proper Configuration
- Start a test process, check whether the global variables configured in `variables` can be read normally in the sub-workflow.
- Trigger a multi-model call node, confirm whether the token consumption statistics for each model are displayed independently.
- Pass test data with an empty correlation ID, confirm that the process terminates at the context correlation validation node and throws a prompt.
- Wait 600 seconds, confirm that the batch data pull process is not forcibly terminated due to timeout.
