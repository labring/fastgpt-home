# Code and Change Review Assistance for Cabinet Rack Installation and Cabling: Workflow Orchestration

## What the data for this category looks like
The typical users of this category are IDC operations engineers, network engineers, and equipment implementation specialists. They handle daily documents including rack installation applications, cabinet cabling diagrams, port label sheets, and construction records. Data mainly comes from DCIM systems, asset systems, network topologies, and customer work orders. The update frequency is per order or per day. Common data fields include rack position number, port number, cable type, construction date, and equipment model. No unified cross-system standardized format exists. Adjust field mapping rules based on the source system.

## What constraints these characteristics impose on workflow orchestration
Data sources involve multiple systems, and the update frequency is per order or per day. The workflow must adapt to the independent processing cycle of a single work order. Do not configure long-running batch tasks. The non-standardized fields of daily documents require the workflow's `variables` to be configured with flexibly adjustable mapping rules. Adapt to document formats from different sources. Split the most time-consuming steps of rack planning and cable label verification into independently configurable verification nodes. Avoid process blocking. At the same time, errors may lead to incorrect port connections or delayed customer service activation. The workflow must include mandatory data verification and exception alert links. Differentiate trigger conditions from equipment room inspection workflows. Only respond to new or modified equipment rack installation work orders.

## How to set configurations
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| Variable definition | Configure `variables`: rack position number, port number, cable type, work order number | Match fixed fields in rack installation applications and port label sheets, adapt to multi-source data mapping |
| Node ID configuration | Assign unique `nodeId` to data pull, verification, and push nodes | Facilitate workflow debugging and log tracking, avoid node conflicts |
| Data pull trigger timing | Trigger by submitted rack installation work order, execute after a `600 seconds` delay | Match the daily data update rhythm of DCIM and asset systems, avoid pulling unsynchronized old data |
| Verification rule thresholds | Port label matching rate no less than `90%`, cable length deviation no more than `50 centimeters` | Avoid consequences of incorrect port connections and mismatched cables |
| Timeout settings | Single node timeout `120 seconds`, overall workflow timeout `3600 seconds` | Adapt to the processing cycle of a single work order, avoid occupying system resources for long periods |
| Result push method | Push to the specified interface of the construction record system | Meet the requirement to synchronously update construction record fields and complete the process loop |

## Three common misconfigurations
- Phenomenon: The workflow calls the DCIM interface and returns a `400` error, unable to pull rack position data. Cause: The correct work order number parameter was not configured in `variables`, resulting in empty interface request fields. This is a common exception scenario for workflow API calls.
- Phenomenon: The port labels output by the workflow do not match the cabinet cabling diagram, with misalignment. Cause: No label matching verification rule was set. The workflow did not strictly generate verification results according to the format of the port label sheet. This aligns with the logical issue of marker misalignment in long subtitle translation.
- Phenomenon: The workflow works normally during debugging but does not trigger data push during formal operation. Cause: No unique `nodeId` was configured for the push node, causing the process to stop at the result push link. This is a process exception related to node configuration.

## How to confirm the configuration is complete
- Check if `variables` includes the required fields from rack installation applications and port label sheets, ensuring all parameters for interface requests are correctly defined.
- Verify that all workflow nodes have unique `nodeId` values, avoiding process execution exceptions caused by node ID conflicts.
- Trigger a test work order, check the workflow logs in FastGPT v4.17.0, and confirm that the three core links of data pull, verification, and push have complete execution records.
- Compare the workflow output results with actual data from DCIM systems and asset systems, confirming the accuracy of port label matching and rack planning.
