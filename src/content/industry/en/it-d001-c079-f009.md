# Code and Change Review Assistance for Architecture Design and Technical Solutions: Tool Calling and Plugins

## What Data for This Category Looks Like
This category of data is primarily sourced from historical traffic data, service topologies, monitoring metrics, and business growth plans. It is circulated daily through technical solution documents, architecture diagrams, capacity assessment forms, and technical review minutes. The data update frequency is monthly or when triggered by major requirements. Fields cover cross-service boundary definitions, resource quotas, constraint conditions, evolution paths, and more. Some fields are labeled with percentages, node counts, or bandwidth values, with no unified fixed unit.

## Constraints Imposed on Tool Calling and Plugins by These Characteristics
Since data sources are mostly cross-service topologies and traffic metrics, tool calling must support format conversion for multi-source heterogeneous data, and field mapping rules must be defined in advance. Because update frequency is not fixed, plugins must support on-demand triggering and be compatible with unstructured text parsing of review minutes. The closed-loop review of architecture design relies on the traceability of tool calling results, so calling logs and parameter records must be retained. At the same time, the consequences of errors in architecture solutions are severe, so a multi-layer retry and alert mechanism must be configured for tool calling failure handling to avoid impacting subsequent review processes. This configuration applies to FastGPT v4.17.0.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | Adapt to dynamic requirements for multi-type tool calling in architecture solution reviews, no manual tool specification required |
| Tool call timeout | 120 seconds | Match the average time upper limit for batch parsing of architecture data and cross-service queries |
| `functionCall` | Enabled | Force structured output of tool call parameters to facilitate automatic organization into review minutes |
| Maximum tokens per tool call | 8000–12000 tokens | Adapt to the average length of architecture solution documents, prevent context overflow |
| Plugin input field mapping | Bind using "service topology → architecture boundary" and "traffic data → capacity assessment" | Align with field definitions in architecture solution documents to ensure accurate data transfer |
| Failure retry count | 2 times | Balance call success rate and review process waiting time, avoid excessive delays |

## Three Common Misconfigurations
- Plugin input values cannot be passed to HTTP request components, resulting in `Request failed`-type errors. This occurs because the plugin input parameters are not mapped and bound to the corresponding fields in the architecture solution document, causing the request to carry empty or invalid parameters.
- Tool call results are not output in structured format, making it impossible to automatically organize them into technical review minutes. This occurs because the `functionCall` configuration is not enabled, resulting in the tool returning non-standardized text content.
- The retry count is set to 0, with no recovery mechanism after a single call failure, causing the architecture review process to stall. This occurs because network fluctuation risks in cross-service data queries are not considered.

## How to Verify Correct Configuration
- Upload a test architecture solution document, trigger the tool call flow, and check whether the plugin input fields correctly load the corresponding data from the document.
- View the tool call logs to confirm that the `toolChoice` and `functionCall` configuration parameters match the preset values.
- Simulate a call failure scenario to verify whether the preset retry mechanism and alert notifications are triggered.
- Check the output format of the tool call results to confirm that they are structured content that can be directly imported into review minutes.

The values provided are common starting points and should be measured against the reader's own samples.
