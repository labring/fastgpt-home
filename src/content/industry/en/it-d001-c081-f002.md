# Code and Change Review Assistance for Penetration Testing Services: Context and Token

## What data looks like for this category
Penetration testing service data typically originates from target systems, public vulnerability databases, automated scanner results, and manual verification records. Documents produced during daily work include test authorization letters, penetration test reports, vulnerability reproduction records, and rectification suggestions. Fields covered include authorization scope, vulnerability IDs, reproduction steps, risk levels, and additional relevant details. Data updates follow cycles tied to individual projects or major version changes. Documents within a single project are incrementally added and refined as testing proceeds.

## What constraints these characteristics impose on the context and token workflow
Documents for penetration testing services contain long-text reproduction steps, structured vulnerability data, and sensitive authorization information. The total volume of content within a single project is relatively high. Different types of documents require strict context isolation to prevent authorization information from being included in unauthorized scenarios. Splitting long-text vulnerability reproduction steps will cause logical breaks, so adapted token allocation and chunking rules are necessary. Data updated per project requires context to refresh alongside project milestones, to avoid interference from old data during current reviews.

## How to set the configurations
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the long-text content of penetration test reports and vulnerability reproduction records |
| `quoteMaxToken` | 3000–5000 token | Ensures complete inclusion of vulnerability verification steps and scanner result snippets in the context |
| Context refresh timing | Triggered per project milestone | Matches the project-based data update rhythm of penetration testing services |
| Chunk overlap length | 200–300 characters | Prevents logical breaks after vulnerability reproduction steps are split |
| Single recall limit | Top 6 entries | Adapts to the number of documents within a single project and controls token usage |

## Three common configuration mistakes
- Context loss after each MCP tool call: The symptom is that historical project-related content cannot be retrieved after tool invocation. The cause is that rules for binding context to projects are not configured, causing tool invocation to reset the global context.
- Output content truncation: The symptom is that generated review results do not include complete vulnerability reproduction steps. The cause is that the `maxContext` parameter is not adjusted based on document length, resulting in content being truncated after exceeding the token limit.
- Uploaded file path parsing failure: The symptom is a 404 error returned when reading uploaded test documents via HTTP requests. The cause is that the token parameter attached to FastGPT uploaded files is not handled correctly, leading to abnormal path parsing.

## How to confirm configurations are set correctly
- View the current project's context configuration, confirm that the `maxContext` parameter value matches the estimated total token count of the current project's documents.
- Test retrieving historical project-related content after invoking an MCP tool, confirm that the context has not been reset.
- Upload a single long document such as a complete vulnerability reproduction record, generate review content, confirm that no critical steps are truncated.
- Test reading an uploaded test authorization letter via HTTP request, confirm that the request path does not carry extra token parameters that cause parsing failure.

The values provided are common starting points and should be evaluated against local test samples.
