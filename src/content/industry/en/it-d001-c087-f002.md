# Code and Change Review Assistance for Game Design and Numerical Design: Context and Token

## What This Category of Data Looks Like
Daily documents for game design and numerical design include gameplay design documents, structured numerical tables, version requirement sheets, and balance test records. Data sources include player behavior data, public competitor materials, battle logs, and version feedback. Update frequency is weekly or per version cycle. Fields and units vary widely across documents: numerical tables have structured fields with units such as damage coefficients and growth curve parameters, while gameplay design documents primarily consist of unstructured rule descriptions. Version requirement sheets are linked to specific version iteration nodes.

## What Constraints These Characteristics Impose on the Context and Token Link
This category has mixed document structures and multi-source data. Context processing must balance token allocation for structured numerical fields and unstructured rule descriptions, avoiding insufficient coverage from a single token quota. Weekly or version-level update cycles require the context window to match the length of historical version review records. A window that is too narrow will lose key rules. A window that is too wide will cause context overload. Data from different sources has strong correlations. Context recall must link multiple documents from the same version to avoid context contamination. Review results directly affect gameplay balance and user retention. Context accuracy is directly tied to the severity of error consequences, raising higher requirements for context recall precision and token allocation rationality.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `maxContext` | First 30 context dialogs | Adapts to the length of historical review records at the game version level, avoiding mixing content from unrelated versions |
| `quoteMaxToken` | 1200–1500 token | Covers the key rule content of a single core numerical table or gameplay design document, ensuring complete review basis |
| Context recall count | First 5 historical review records | Balances context relevance and processing efficiency, avoiding excessive historical data interfering with current reviews |
| Chunk overlap length | 100–150 characters | Retains cross-chunk associated fields in numerical tables, avoiding loss of key numerical parameters after splitting |
| FastGPT Version | FastGPT v4.17.0 | Adapts to the context storage and recall logic of the current version, compatible with file path token stripping rules |

## Three Common Configuration Mistakes
- Phenomenon: Uploaded file relative paths include token parameters, leading to Flask service processing errors. Cause: FastGPT file path token stripping rules are not configured, and original paths are used directly to send requests.
- Phenomenon: `maxContext` is set to 30 entries, but only 2 context entries appear in conversation details. Cause: Context persistent storage is not enabled, or the storage threshold does not match the configured recall count.
- Phenomenon: AI replies include unexpected JSON format content. Cause: Output format is not clearly defined in the review prompt, and context does not link to the current version’s review rule requirements.

## How to Verify Proper Configuration
- A test numerical table document is uploaded, a review request is initiated, and the recalled context is checked for inclusion of the document’s prior version records
- Context logs in the FastGPT backend are viewed, and the `maxContext` configured entry count is confirmed to match the actual recalled context entries
- A file path with token parameters is tested for upload, and correct extraction of the file path with exclusion of extra token parameters is verified
- A review request is initiated, and the AI reply is checked for compliance with the current gameplay design document’s rule constraints, with no unexpected JSON format content present
