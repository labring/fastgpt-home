# Code and Change Review Assistance for Game Operation Activity Configuration: Workflow Orchestration

## What the data for this category looks like
Daily documents for game operation activity configuration include activity plans, reward configuration tables, launch checklists, and activity post-mortems. Core data comes from operation backends, player segments, payment data, and activity logs. Data updates do not follow a fixed cycle, and are usually adjusted weekly or around holiday event nodes. Fields include activity ID, reward type, distribution value, activity time range (usually no more than 7 days), target player group, and more. Some fields need to be associated with real-time player data and historical activity records. The overall structure is mainly structured tables and configuration items.

## What constraints do these characteristics impose on workflow orchestration
Activity configuration data comes from scattered sources and updates flexibly. This requires workflows to support both manual trigger and change event trigger modes, to accommodate temporary adjustments and scheduled launch requirements. Structured configuration documents and multi-source data reading requirements mean workflows need to integrate multi-data source reading nodes and structured data verification links, to prevent non-standardized data from entering the review process. Since errors in activity configuration can cause reward distribution mistakes, player complaints, and other consequences, workflows need to have pre-verification and review traceability nodes. They also need to adapt to disconnection and reconnection logic for MongoDB replica set scenarios, to ensure data reading stability.

## How to configure this
This configuration is based on the workflow node capabilities of FastGPT v4.17.0. Specific parameters are as follows:
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | Manual trigger + change event trigger | Activity configuration updates have no fixed cycle, to accommodate temporary launches and scheduled release requirements |
| Data Source Read Timeout | `300 seconds` | Activity data needs to read operation backend and player segment interfaces, reserve sufficient response time |
| `variables` configuration | Include activity ID, environment identifier, reward threshold | Adapt to activity configuration calls for different environments, pass core verification parameters |
| Tool Output Control | Hide tool call original responses | Only display verification results during the review process, avoid redundant information interference |
| Reconnection Retry Strategy | Retry 3 times, interval 60 seconds | Address disconnection scenarios caused by MongoDB replica set primary node drift |
| `nodeId` binding | Bind dedicated node ID for activity configuration | Avoid workflow node confusion, ensure change review points to the correct configuration |

## Three Common Mistakes
- Symptom: Workflow nodes return empty values and cannot obtain knowledge base ID. Cause: No knowledge base ID transfer parameter configured in `variables`, causing nodes to fail to read corresponding configuration items.
- Symptom: The original response of the tool call module is forcibly displayed and cannot be hidden. Cause: The tool output control configuration is not enabled, or the option to display original output was mistakenly selected during configuration.
- Symptom: After the MongoDB replica set primary node drifts, the workflow disconnects and cannot recover. Cause: No reconnection retry strategy configured, or retry interval and number of retries are set unreasonably, failing to adapt to the delay scenario of primary node switching.

## How to Confirm the Configuration is Set Up Correctly
- Manually trigger the workflow, verify that the returned activity configuration data matches the document exported from the operation backend.
- Submit a simulated change, check whether the verification node intercepts according to the configured field rules.
- Simulate a MongoDB disconnection scenario, confirm that the workflow triggers the reconnection logic and resumes data reading.
- View the workflow running logs, confirm that the `variables` parameters have been correctly passed to the corresponding nodes.
