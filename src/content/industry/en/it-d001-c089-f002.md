# Code and Change Review Assistance for Vulnerability Scanning Services: Context and Token

## What the data for this category looks like
Data for this category originates from vulnerability scanners, asset inventories, CVE databases, and patch announcements. Unlike penetration testing services, this category centers on tool-based scanning and re-scan closed loops. Daily produced documents include scan plans, vulnerability lists, rectification work orders, and re-scan reports. Each document contains fields such as asset scope, vulnerability ID, impact scope, and rectification status. Data updates run on a weekly or monthly cadence, synchronized with scan plan execution and patch announcement releases. Core data revolves around asset vulnerabilities linked to reviewed code and change impact scope. It must include comparison information for asset status before and after changes.

## Constraints imposed on context and token workflows
Dispersed data sources and inconsistent update rhythms create time gaps between asset information and vulnerability data during context assembly. This requires limiting the scope of context loading across data sources. Daily document fields are numerous and closely interconnected. Loading full data without restrictions will exceed token limits and cause the model to truncate critical information. Cross-document context is required for associated verification of re-scan reports and rectification work orders. Insufficient token allocation prevents complete matching of vulnerability status before and after changes. Additionally, code snippets for change reviews must be accurately bound to associated vulnerability data. Excessive irrelevant historical scan data will occupy token quotas for valid context, reducing review accuracy.

## How to configure
These configurations apply to FastGPT v4.17.0:
| Configuration Item | Recommended Range | Rationale |
| ---- | ---- | ---- |
| `maxContext` | `8000–12000 token` | Covers total data volume of single-batch scan plans, vulnerability lists, and changed code snippets for this category, prevents the model from truncating critical review information |
| `quoteMaxToken` | `2000–3000 token` | Retains core associated information such as vulnerability IDs, asset impact scopes, and rectification work order numbers, reserves sufficient quotas for code context |
| Context Refresh Cycle | `7 days` | Matches weekly or monthly data update rhythms of this category, ensures loaded context stays synchronized with latest vulnerability data |
| Associated Document Recall Limit | `Top 3 entries` | Focuses on latest scan results and rectification work orders linked to current changes, prevents irrelevant data from occupying token quotas |
| Context Filter Threshold | Calibrated via actual testing | Filters historical scan data unrelated to current code changes, improves token utilization efficiency for valid context |

## Three common misconfigurations
- Phenomenon: The interface displays a context token limit exceeded alert, and model return results are truncated. Cause: Quotas for `maxContext` and `quoteMaxToken` are not adjusted based on scan data volume of this category, causing total token usage to exceed model limits.
- Phenomenon: After calling the MCP tool, context associated with current code changes and vulnerability links is cleared. Cause: Automatic context save parameters are not configured, and the binding relationship between scan plans and changed code is not retained during tool calls.
- Phenomenon: HTTP requests return 404 errors when reading uploaded associated files, with random token strings appended to the end of file paths. Cause: Token stripping processing is not performed on uploaded file paths, causing paths to point to invalid temporary storage addresses.

## How to verify proper configuration
- View the platform's context quota statistics panel, confirm that configured `maxContext` and `quoteMaxToken` values match preset values.
- Run a simulated change review process, check that associated scan plans, vulnerability lists, and rectification work orders load completely, with no truncation or loss.
- Trigger an MCP tool call, verify that context is not cleared, and can complete vulnerability association and code review verification.
- Upload associated files and initiate an HTTP request, confirm that temporary tokens in file paths are correctly stripped, and the service can read files normally.

The values listed are common starting points and should be evaluated against local test samples.
