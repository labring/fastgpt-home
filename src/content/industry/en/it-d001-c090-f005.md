# Code and Change Review Assistance for Version Releases and Release Notes: Multi-turn Dialogue and Prompt Engineering

## What the Category Data Looks Like
This category's data primarily comes from Git repository version tags, merge commit records, artifact packages generated by CI pipelines, and associated Issue milestones. Daily output documents include officially released Release Notes, change logs, version tag descriptions, and release checklists. Data is updated with each version iteration, with each version corresponding to a complete set of changes. Fields include version number, change category, breaking change flag, associated commit hash, artifact checksum, and more.

## Constraints Imposed on Multi-turn Dialogue and Prompt Configuration
The aggregated dataset characteristics of this category by version require that multi-turn dialogue strictly limit the context scope to avoid confusion between cross-version change content. The data includes structured fields such as breaking change flags and artifact checksums, so prompts must preset format validation rules to prevent misinterpretation of non-standard fields. The update rhythm triggered by each version requires the dialogue flow to support targeted retrieval of the corresponding dataset using a specified version number. The presence of short fields such as commit hashes and version tags also requires prompt configurations with precise matching rules to ensure consistency between associated change entries and version information.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique identifier of the current version session, recommended value is version number + session timestamp | Ensures multi-turn dialogue context is strongly bound to the specified version, complies with FastGPT v4.17.0 session context management rules, and avoids cross-version data interference |
| `messages` | Limit the context window to the most recent 3 version-related dialogues, or truncate change data by version range | Change entries for each version of this category typically range from 10 to 30 items. Limiting the context reduces irrelevant information interference and improves response accuracy |
| `variables` | Preset two global variables: version number and change category | Allows dynamic insertion of currently processed version information into prompts, adapting to multi-version parallel review scenarios |
| Single search limit | Top 10 change records | Balances recall efficiency and information completeness, avoiding excessive redundant content exceeding model processing limits |
| Maximum context | 8000–12000 characters | Change sets and Release Notes content for each version mostly fall within this range, preventing truncation of critical information |
| Question optimization | Enable version-filtered optimization mode | Automatically supplements version restriction conditions before retrieval, adapting to the data organization characteristics of this category by version |

## Three Common Misconfigurations
- Symptom: After adjusting the single search limit, the model does not return the corresponding number of recall results, and does not associate the currently processed version data. Cause: The version number global variable is not bound via `variables`, resulting in the retrieval scope not being limited to the change set of the current version.
- Symptom: Retrieval results include non-business fields such as paragraph IDs. Cause: No instruction to filter non-business fields is configured in the prompt, causing metadata from the original data to be output together.
- Symptom: After deploying a custom model, the model version displayed in the dialogue interface and workspace is inconsistent. Cause: The `messages` model binding parameter is not updated synchronously in the session configuration, resulting in inconsistent model instances called across different scenarios.

## How to Verify Correct Configuration
- Initiate a change review dialogue targeting a specified version, check that returned change entries only include content from that version, with no cross-version data mixed in.
- Review the output of retrieval results, confirm that non-business fields such as paragraph IDs are not included, and only core change-related information is returned.
- Switch between the dialogue interface and workspace scenarios, verify that the called model version remains consistent with no configuration deviations.
- Adjust the single search limit parameter, check that the number of returned change entries matches the preset value range.

The values provided are common starting points and should be measured against the reader's own samples.
