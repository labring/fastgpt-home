# Code and Change Review Assistance for Version Releases and Release Notes: Workflow Orchestration

## What the data for this category looks like
The data for this category primarily comes from version tags in Git repositories, merge commit records, artifact packages generated by CI/CD workflows, and associated Issue milestones. Daily deliverables include officially released Release Notes, change logs, version tag lists, and release checklists. Core fields include change classification tags, breaking change identifiers, artifact checksum values, version numbers, and release times. The data update rhythm aligns with the version release cycle; one round of data updates is completed after each version iteration.

## What constraints these characteristics impose on workflow orchestration
The data sources for this category are scattered and tied to the version release cycle. Configure workflows to trigger based on version release nodes instead of using generic scheduled scheduling. Configure nodes to complete automatic classification and verification for data fields that include non-standardized change classifications and breaking change identifiers. Public release attributes require workflows to include a pre-review step to ensure change descriptions match artifact information and avoid community misunderstandings. The data update frequency is fixed at once per version, eliminating the need for high-frequency synchronization and optimizing workflow resource usage.

## How to Configure
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Trigger Condition | Trigger on Git tag push events | Matches the update rhythm of this category tied to version releases, ensuring workflows only start during version iterations |
| variables | Bind Git repository address, CI artifact storage path | Directly obtains core data sources for this category, no manual data entry required |
| nodeId | Associate Git merge record node, artifact verification node | Clarifies dependency relationships between workflow links, ensuring correct data flow order |
| Timeout Setting | 1200 seconds | Adapts to the typical time required for Git data pulling and CI artifact verification, prevents workflow interruptions due to network fluctuations |
| Output Filtering | Retain change classification results, breaking change identifiers, artifact verification status | Only outputs core fields required for releases and Release Notes, streamlines final document content |

## Three Common Configuration Mistakes
- Phenomenon: Upstream workflow nodes output normally, but downstream nodes cannot obtain upstream results. Cause: The `variables` parameter is not correctly configured to bind upstream node outputs, resulting in data not being passed to downstream links.
- Phenomenon: Tool call module output is forcibly returned to the final result. Cause: Output filtering configuration is not enabled, and redundant return information from tool calls is not blocked.
- Phenomenon: CI artifacts cannot be pulled normally after environment variable configuration. Cause: The environment variable naming rules updated in FastGPT v4.17.0 are not matched, resulting in storage path verification failure.

## How to Confirm the Configuration is Correct
- Manually trigger a simulated Git tag push event, check whether the workflow starts normally and completes data pulling.
- Review the workflow variable mapping configuration, confirm that upstream node output fields are correctly bound to downstream node input parameters.
- Generate a test version of Release Notes, verify that core fields match Git tag and CI artifact information.
- Simulate a network delay scenario, check whether the workflow completes core link execution within 1200 seconds.
