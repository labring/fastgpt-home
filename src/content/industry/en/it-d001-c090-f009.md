# Code and Change Review Assistance for Version Releases and Release Notes: Tool Calling and Plugins

## What the Data for This Category Looks Like
The core data for this category is created and maintained daily by open-source maintainers, release managers, and documentation maintainers. It primarily includes four types of documents: Release Notes, change logs, version tags, and release checklists. Data sources typically include tag records in Git repositories, merge request merge records, artifact packages generated by CI/CD workflows, and milestone items linked to Issues. The data update rhythm aligns with version release cycles, with one update per released version. Individual data entries usually include fields such as version number, change category, breaking change description, and linked artifact hash value. There is no unified fixed unit; the data exists only in text and structured identifier formats.

## How These Characteristics Impact Tool Calling and Plugin Configuration
This category’s data sources rely on external systems such as Git repositories, CI/CD artifacts, and Issue milestones. As a result, tool calling must bind plugin permissions corresponding to these data sources, and cannot rely solely on built-in knowledge base retrieval. Data updates are triggered according to version release cycles. Tools must be configured to trigger on version tagging or release events; scheduled pulling does not align with this category’s update rhythm. Individual data entries contain both structured and unstructured fields. Tool calling must support both text extraction and structured field matching, such as extracting breaking change identifiers from Issues. Additionally, the most time-consuming steps for this category—change categorization and breaking change descriptions—require tools to automatically pull and categorize change records to reduce manual workload.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Timing | Within 10 minutes after a Git tag is created for a version | Aligns with the version-based update rhythm of this category, and reserves time for CI/CD workflow completion |
| `toolChoice` | `auto` | Adapts to the model’s need to autonomously select tools, without requiring manual specification of each tool |
| `functionCall` | Bound to Git data source plugin | Directly pulls core data such as tags and merge records from Git repositories |
| Change Record Recall Limit | Top 10 entries | Prevents excessive change information from exceeding context length limits |
| Timeout Duration | 600 seconds | Reserves sufficient time for Git data pulling and artifact validation |
| Plugin Access Whitelist | Only allow FastGPT service IP ranges | Ensures security of internal plugin calls and prevents unauthorized access |

## Three Common Misconfigurations
- Empty tool calling results: Failed to correctly bind the Git data source plugin, or failed to configure the trigger conditions for `functionCall`, resulting in inability to pull change data for the target version.
- Plugin call timeout: Did not set a reasonable timeout duration, or Git repository network latency is too high, exceeding the 600-second configured threshold.
- Abnormal requests caused by exposed internal plugin ports: Did not configure port access whitelists, directly exposed internal plugin ports, introducing unauthorized access risks.

## How to Verify Successful Configuration
This verification process is compatible with FastGPT v4.17.0.
- Manually create a test version tag in the Git repository. Confirm whether FastGPT automatically triggers tool pulling of change records.
- View plugin logs. Confirm that the `toolChoice` parameter has been correctly passed, and that `functionCall` has invoked the bound Git data source plugin.
- Generate a test version Release Notes. Verify that the output includes change logs, version tags, and linked artifact information.
- Attempt to send a request from an unauthorized IP range. Confirm that the request is blocked, verifying plugin port access restrictions.

The values provided are common starting points and should be validated against samples from the target deployment environment.
