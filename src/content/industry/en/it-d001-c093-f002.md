# Code and Change Review Assistance for User Growth and Retention Operations: Context and Token

## What the data for this category looks like
The core data for this category comes from user behavior logs, push systems, experiment platforms, and CRM systems. Daily produced documents include growth experiment plans, user segmentation tables, outreach copy, and retention analysis reports. User segmentation tables contain fields such as user ID, segmentation tags, and outreach frequency. Outreach copy marks delivery channels and trigger conditions. Data update frequencies are divided into daily and weekly levels. Daily level data mostly consists of real-time collected user behavior logs. Weekly level data consists of aggregated experiment reports and segmentation reports.

## What constraints these characteristics impose on the context and token link
This category has large data volumes. A single Excel file can reach ten thousand rows. Daily updated user behavior logs continuously add new data. If context stitching granularity is too coarse, token consumption will be too high. Document structures are diverse. There are both structured user segmentation tables and long-text experiment plans. A single chunking rule cannot adapt to all document types. This easily leads to key information being truncated or redundant content being mixed into the context. Frequently updated data requires the context to synchronize the latest user segmentation and experiment results in a timely manner. Otherwise, outreach strategies will be generated based on outdated information, which will cause user dissatisfaction. The core goal of this category is to improve in-app user retention. Recalled associated data must accurately match current operational needs. Too much irrelevant historical data will additionally occupy token quotas.

## How to set configurations
The following configurations are formulated based on the interface and parameter rules of FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---|---|--- |
| Chunk Length | 800–1200 characters | Adapts to the mixed scenario of structured and unstructured documents in this category, avoids excessive token consumption caused by oversized single chunks |
| Chunk Overlap Length | 100–200 characters | Retains cross-chunk field associations, prevents loss of cross-row and cross-column information in user segmentation tables |
| `maxContext` | 8000–12000 token | Matches the total volume of operational documents and log data in this category, controls the upper limit of token usage for the overall context |
| `quoteMaxToken` | 2000–3000 token | Focuses on core content of outreach copy and experiment plans, ensures that key operational information is fully recalled |
| Single Recall Limit | Top 8 entries | Reduces token quota occupied by redundant data, accurately matches current operational consultation needs |
| Reranking Switch | Enabled | Improves relevance of recalled content, filters irrelevant historical data, reduces invalid token consumption |

## Three common misconfigurations
- Symptom: When chunk length is set too large, token consumption for a single data chunk becomes too high, and the `Reached the max retries per request limit` error appears. Cause: The default parameter chunk size exceeds interface limits, failing to adapt to the small chunking needs of ten-thousand-row Excel files in this category.
- Symptom: Too much recalled data causes token consumption to exceed the quota. Cause: No reasonable single recall limit and `maxContext` parameter are set, leading all irrelevant historical user behavior logs to be included in the context.
- Symptom: Cross-row and cross-column information in user segmentation tables is lost, leading to incorrect outreach strategy matching. Cause: Chunk overlap length is set too small, failing to retain cross-chunk field association information.

## How to confirm proper configuration
- Upload a typical ten-thousand-row Excel user segmentation table, check the preview content after chunking, confirm that each data chunk length falls within the preset range.
- Initiate a simulated operational consultation, check the token consumption data for context stitching, confirm that it does not exceed the preset `maxContext` quota.
- Test the recall results for outreach copy, confirm that core copy content and trigger conditions are fully included in the context.
- Check the knowledge base update log, confirm that the synchronization frequency of daily and weekly level data meets configuration requirements.

The values listed are common starting points and should be evaluated against the reader's own samples.
