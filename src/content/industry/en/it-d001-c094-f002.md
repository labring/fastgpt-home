# Code and Change Review Assistance for User Acceptance Testing Support: Context and Token

## What data for this category looks like
Data for this category comes from requirement specifications, test environment configurations, customer business sample materials, and defect management systems. It is updated once per delivery phase or version iteration. Core daily deliverables include UAT test cases, acceptance issue tickets, acceptance reports, and signed confirmation forms. Document fields cover business scenario descriptions, test steps, defect details, acceptance conclusions, and more. There are no unified fixed units; values adjust based on customer business scenarios. Core context associated with code change review mostly comes from review records, test script snippets, and customer feedback content. Data volume fluctuates with project scale.

## What constraints do these characteristics impose on the context and token link
Multi-source and scattered data sources require integration of requirements, test environments, defect systems and other content, which increases token carrying pressure. Phased update cycles require context to be refreshed with version iterations. Expired associated content must be cleaned regularly to avoid invalid token occupation. Daily document structures are non-standardized. Fields for UAT test cases, acceptance issue tickets and other items vary widely. Context slicing must adapt to diverse text formats. Compliance documents from the acceptance link must be fully included in context and cannot be truncated arbitrarily, which further limits token allocation quotas. If context overflows, core processes such as test case preparation and issue categorization will be directly blocked, leading to acceptance delay risks.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `maxContext` | Regular projects use `8000–12000 token`, large-scale acceptance projects use `15000–20000 token` | Adapts to the volume requirements of multi-source documents for this category, ensures full loading of core context such as UAT test cases and defect tickets, and aligns with the context processing logic of FastGPT v4.17.0 |
| `quoteMaxToken` | `2000–3000 token` | Context fragments for code change review are mostly test scripts and defect descriptions. Single-segment references do not need to be too long, to avoid occupying excessive total token quota |
| Context slice overlap length | `200–300 characters` | Documents such as UAT test cases contain continuous business logic. Overlapping slices avoid context breaks and ensure review logic consistency |
| Context refresh cycle | 1 day before each phase delivery | Data for this category is updated per phase. Context must be refreshed before the phase starts to ensure association with the latest requirement and defect content |

## Three common misconfigurations
- Phenomenon: An error about context overflow is returned when calling code review-related tools, or generated content truncates key acceptance test case steps. Cause: The `maxContext` parameter is not adjusted based on the volume of multi-source documents for this category. The token quota is insufficient to carry complete context of UAT test cases and defect records.
- Phenomenon: After consecutive follow-up questions related to acceptance reviews, subsequent answers fail to associate previous defect ticket information, resulting in off-topic responses. Cause: A reasonable context refresh cycle is not configured, or the `maxContext` setting is too small, causing old context to be automatically cleaned up.
- Phenomenon: After uploading customer business sample documents, associated code change review fragments lose part of the business scenario description. Cause: The context slice overlap length is set unreasonably, causing key business logic to be truncated, and complete context association is not retained.

## How to confirm correct configuration
- Initiate a test question that includes UAT test cases and defect ticket content, and check whether the answer covers previously associated business scenario information.
- View the context display module, and confirm that core data such as current phase requirement specifications and test environment configurations are included.
- Trigger a context call for code change review, and check whether the returned content includes complete acceptance-related document fragments without truncation.
- Simulate multiple consecutive follow-up questions, and confirm that subsequent answers can associate previous acceptance issue ticket information without off-topic responses.

These values represent common starting points, and should be validated against samples tailored to the specific deployment context.
