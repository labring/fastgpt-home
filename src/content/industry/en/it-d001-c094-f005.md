# Code and Change Review Assistance for User Acceptance Testing Support: Multi-turn Dialogue and Prompts

## What the data for this category looks like
This category's business data comes from requirement specification documents, test environment configurations, customer business samples, and defect management systems. The update rhythm is synchronized per project phase or software version. Daily processed documents include UAT test cases, acceptance issue tickets, acceptance reports, and signed confirmation forms. The document structure is fixed. Core fields include test case steps, issue numbers, test environment addresses, and acceptance conclusions. There are no extra custom redundant fields. Data volume accumulates gradually as the project phase progresses.

## What constraints these characteristics impose on the multi-turn dialogue and prompt engineering link
Decentralized data sources tied to customer-side business require multi-turn dialogue to strictly bind to the corresponding acceptance phase. This prevents cross-phase data confusion. The fixed document structure requires prompts to accurately match standard fields of UAT test cases and issue tickets. This reduces model recognition errors for non-standard fields. The phase-adjusted update frequency requires that dialogue contexts cannot be reused across phases. Session contexts must be reset for each phase. This prevents expired data from interfering with current reviews. The most time-consuming test case preparation and issue categorization processes require multi-turn dialogue to call prompt templates for corresponding scenarios in a targeted way. This focuses on core business fields to improve processing efficiency.

## How to configure the settings
This document is written based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum Context Window | 800–1200 characters | Matches the standard single-page length of UAT test cases, prevents model context overflow |
| `chatId` Binding Rule | Bind by acceptance phase, reuse sessions within the same phase | Business data updates per phase, cross-phase sessions introduce expired data |
| `variables` Injection Scope | Only inject current acceptance ticket ID and defect system number | Focus on core business fields, reduce prompt redundancy |
| `messages` Context Truncation Strategy | Retain the last 2 rounds of dialogue (200–300 characters) and current UAT test case content | Filter redundant dialogue from early non-critical stages |
| Multi-turn Session Timeout Setting | 600–900 seconds | Matches the single discussion cycle of UAT reviews, prevents session failure mid-discussion |
| Prompt Template Trigger Condition | Trigger by acceptance issue ticket status, call issue reproduction template when pending categorization | Focus on the most time-consuming issue reproduction and categorization process, improve processing efficiency |

## Three Common Misconfigurations
- The symptom is that after calling the dialogue interface, the returned result does not associate UAT test case content from the knowledge base. It only returns generic Q&A. The cause is failing to inject retrieved knowledge base context into the dialogue prompt via `variables`. This prevents the model from accessing business-related data.
- The symptom is that when calling the session query interface, the session record corresponding to `chatId` does not appear in the storage collection. Historical dialogue content cannot be viewed. The cause is failing to enable session persistence configuration. This causes `messages` to not be written to storage media.
- The symptom is that after entering a single acceptance issue, only a single independent response is obtained. No multi-turn associated review assistance output is generated, and reference content for related issues is not merged. The cause is failing to specify merge logic for multi-turn questions in the prompt. It also fails to pass the contextual association of previous dialogue via `messages`.

## How to Verify Successful Configuration
- Initiate a dialogue request for the corresponding acceptance phase. Enter a question related to UAT test cases. Check if the returned result includes the current test case's steps or number information.
- Call the session query interface. Pass the corresponding `chatId`. Verify that the session record exists in the storage medium, and includes the `messages` and `variables` fields.
- Submit the same question for different acceptance phases. Check if sessions are isolated by phase. No cross-phase UAT test case data confusion occurs.
- Trigger the prompt template call for the issue reproduction scenario. Enter an acceptance issue ticket. Check if the returned result includes core number information from the defect system.

The values provided here are common starting points. They should be evaluated against the reader's own samples.
