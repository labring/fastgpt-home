# Code and Change Review Assistance for Monitoring Alert Configuration: Context and Token

## What this category of data looks like
Data for this category comes from Prometheus, Zabbix, cloud monitoring, application logs, and CMDB systems. The update frequency is daily or after each alert rule change. Daily produced documents include monitoring metric lists, alert rule files, on-duty manuals, and alert change records. Single alert rule data includes fields such as threshold parameters, trigger conditions, associated metrics, and notification link configuration. There is no unified fixed length, and it increases as the monitoring scale grows.

## What constraints do these characteristics impose on the "context and token" link
In FastGPT v4.17.0, scattered data sources require consolidating metrics from multiple systems in a single call. Unstable update frequencies may cause context data to lag. Alert rule document structures vary widely, so fixed chunking cannot adapt to all scenarios. This easily leads to key configurations being split and lost. Single data length increases with monitoring scale. If the total context token amount is not limited, it will exceed the large model input limit, resulting in empty responses or truncated content. Additionally, the timeliness requirement of alert change records means context must retain recent change operations to avoid referencing outdated configurations during reviews.

## How to set the configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to mainstream large model input limits, covers the average total length of alert configuration-related documents |
| `quoteMaxToken` | 1500–2000 token | Limits token usage of a single quoted content, prevents key configurations from being lost during splitting |
| Context refresh timing | Triggered by changes + daily full synchronization | Matches the daily/change-level update frequency of alert configurations, ensures context timeliness |
| Single recall quote count | Top 3–5 entries | Focuses on core alert rules and recent change records, reduces noisy information |
| Context content priority | Retain recent change records and core threshold configurations | Prioritizes the most critical configuration information during alert reviews, avoids redundant content occupying tokens |

## Three common misconfigurations
- The `LLM model response empty` error occurs. This is caused by not limiting the `maxContext` parameter, leading to total context token exceeding the large model input limit, so the model cannot generate valid responses.
- Single recalled content exceeds the preset token limit, causing truncated answers or empty returned fields. This is caused by not configuring the `quoteMaxToken` parameter, even after splitting, single quoted content still exceeds the token limit.
- Context cannot retain historical configuration information from continuous conversations. This is caused by not enabling the context synchronization mechanism; each call only loads the current knowledge base content, and does not associate alert configuration context from previous interactions.

## How to confirm the configuration is properly set
- Submit a review request for an alert rule change, check if the returned content includes the last 3 change records and core metric configurations, with no redundant irrelevant information.
- Check the platform operation logs, confirm there are no `LLM model response empty` errors, and the response content is not truncated.
- Manually modify the alert configuration, initiate a new review request, check if the returned content includes the latest change information.
- Adjust the `maxContext` parameter, test monitoring configuration documents of different scales, confirm the model can normally generate responses and no key configurations are lost.

The values listed above are common starting points, and should be evaluated against your own specific samples.
