# Code and Change Review Assistance for Community Report Handling: Context and Token

## What the data for this use case looks like
Core data for community report handling comes from report systems, content details, user historical records, and audit rules. Update frequency is daily or real-time. Daily processing documents include report tickets, handling records, appeal forms, and user notification templates. Individual ticket data includes fields such as report submission time, involved content fragments, user identifiers, associated violation types, and disposal status. Each ticket is linked to 3 to 5 historical records or rule entries. Overall data has no unified standardized format, so key information must be extracted by field.

## What constraints these characteristics impose on context and token management
Community report handling processes specific user-submitted content on a per-ticket basis. The volume of linked data per ticket varies widely. Full loading of involved content, user history, and audit rules is required to complete validity judgment. Real-time updated data requires context to dynamically pull the latest information, to avoid using expired audit rules or user historical records. Non-standardized document structures make fixed-length chunking impossible. Core information must be filtered by field, otherwise irrelevant token usage will be introduced. Context requirements for a single ticket focus on precise information within a short time frame. Full community data does not need to be loaded. Context quotas must be adapted to the actual scale of a single ticket, and should not reference configuration standards for general content pools.

## How to configure settings
The following configurations are based on the context and token management logic of FastGPT v4.17.0.

| Configuration Item | Recommended Range | Rationale |
| ---|---|--- |
| `maxContext` | `8000–12000 token` | Matches the average total token volume of involved content, user historical records, and audit rules linked to community report tickets, ensuring full context for a single ticket can be loaded |
| `quoteMaxToken` | `2000–3000 token` | Limits the token length of referenced violation content and handling records in a single request, preventing a single reference from occupying too much context quota |
| Context filtering rules | Only retain report ID, involved content, user historical records from the past 30 days, and associated audit rules | Filters irrelevant data, reduces unnecessary token usage, and focuses on core information for report handling |
| Real-time data pull trigger condition | Pull updated data from the past 1 hour relative to the ticket submission time | Matches the real-time update frequency of report data, avoiding pulling expired or irrelevant historical records |
| Context truncation priority | Prioritize retaining involved content fragments and audit rule entries | Ensures core information for report validity judgment is not truncated, supporting accurate disposal suggestions |

## Three common misconfigurations
- The symptom is an interface prompt "Context token exceeds limit". The cause is failing to configure `maxContext` based on the actual linked data of a single report ticket, and incorrectly using large context quotas for general content review. This prevents full information for a single ticket from being loaded.
- The symptom is that returned disposal suggestions do not include user historical report records. The cause is failing to configure context filtering rules, or incorrectly excluding user historical fields in filtering rules. This causes key linked information to not be included in the context.
- The symptom is abnormally high token consumption during calls. The cause is failing to set the `quoteMaxToken` limit, leading to repeated references of large volumes of duplicate audit rule content in a single request, which wastes token quotas.

## How to verify correct configuration
- Import a single typical report ticket, check the context preview interface, and confirm that full information including involved content, user historical records, and associated audit rules is included.
- Simulate 10 consecutive requests, check the token consumption statistics, and confirm that the token volume for a single request falls within the configured `maxContext` range.
- Modify the value of `quoteMaxToken`, observe the reference length of returned content, and confirm that the token count of referenced content matches the configured limit.
- Simulate triggering real-time data pulling, check system logs to confirm that only updated data within the ticket submission time range is pulled, avoiding invalid pulls.

The values listed here serve as common starting points, and should be evaluated against deployment-specific samples.
