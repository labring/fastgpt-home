# Code and Change Review Assistance for Community Report Handling: Workflow Orchestration

## What the data for this category looks like
Core data for community report handling comes from report systems, content details, user historical records, and audit rules. Update frequency is daily or real-time. Daily processing documents include report tickets, processing records, appeal forms, and user notification templates. Report tickets contain fields such as report ID, associated content ID, report type, and reported content snippet. Processing records include fields like node execution time, operator ID, and disposal result. Data structure adjusts dynamically based on report scenarios, with no fixed, unified full field set.

## What constraints these characteristics impose on workflow orchestration
Decentralized data sources and real-time updates require workflows to support dynamic pulling of multi-source data and format unification. Diverse daily document structures and non-fixed fields demand flexible variable mapping rules to adapt to fields across different documents. The most time-consuming steps include report validity judgment, violation evidence extraction, and disposal result notification. These steps require workflows to split into independent nodes and support parallel or serial scheduling. Errors may trigger user complaints or community conflicts, so failed retry and exception alert nodes need to be configured.

## How to set configurations
This chapter’s configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| Variable Mapping | Bind report ticket fields to `variables` | Adapt structured fields from daily documents, unify multi-source data formats |
| Node Timeout | 600 seconds | Cover standard processing durations for report validity judgment and violation evidence extraction |
| Routing Rule Configuration | Match `nodeId` by report type | Differentiate dedicated processing flows for different report scenarios |
| Node Retry Count | 2 times | Balance efficiency of exception recovery and resource usage |
| Content Extraction Length | 800–1200 characters | Match typical lengths of reported content snippets |
| Notification Trigger Configuration | Trigger by disposal status | Adapt call logic for user notification templates |

## Three common misconfigurations
- Symptom: Multiple report types trigger the same workflow node. Cause: Routing rules based on report type and `nodeId` are not configured, so different scenarios cannot match their corresponding processes.
- Symptom: Workflow node input fields are empty. Cause: Report ticket fields are not correctly mapped to `variables`, and multi-source data format binding is not completed.
- Symptom: Workflow stops directly after a node execution fails. Cause: Node retry count is not set, and exception recovery logic is not configured.

## How to confirm configurations are correct
- Upload a test report ticket, check if the corresponding workflow node is triggered based on report type.
- Open the workflow variable panel, confirm that report ticket fields are correctly mapped to `variables`.
- Simulate a node exception scenario, check if the preset retry mechanism is triggered.
- Trigger the disposal completion node, check if the corresponding type of user notification is generated.

The values provided are common starting points, and should be evaluated against the reader’s own samples.
