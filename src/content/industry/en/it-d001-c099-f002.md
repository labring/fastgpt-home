# Code and Change Review Assistance for Mobile Development: Context and Token

## What the data for this use case looks like
Core data for mobile development teams comes from PR change records in code repositories, review rule documents from app store backends, stack logs from crash monitoring platforms, and system version distribution information from device coverage data platforms. Daily output documents include app version release notes, multi-device adaptation checklists, crash analysis reports, and app store listing materials. Data updates follow the version release cycle, with some monitoring data synced daily. A single PR change may include adaptation code across iOS and Android. App store listings include multilingual descriptions and permission statements. Crash analysis reports contain structured fields such as device model, system version, and error stack traces.

## How these characteristics impose constraints on context and token
The review context for mobile development must cover multiple types of content including code changes, adaptation rules, and historical crash data. The total length of a single context is generally higher than that of general development scenarios. Multi-device adaptation code and complete app store review materials will consume a large number of tokens. Insufficient context length will lead to core review information being truncated. Additionally, data updates follow the version release cycle, so the context must support recalling historical documents by version to avoid context confusion across versions. Furthermore, structured fields in crash analysis reports require precise matching. An overly long context will reduce recall accuracy, so a balance must be struck between context length and information completeness.

## How to configure the settings
| Config Item | Recommended Value | Rationale |
| --- | --- | --- |
| Max Context Length | 8000–12000 tokens | Mobile PR changes often include multi-device adaptation code across iOS and Android, plus complete version release notes, resulting in high total single context length |
| `maxContext` | Calibrated based on actual measurements | The scale of code repositories and quantity of documents differ between teams, so adjustments should be made using actual invocation logs |
| Max Reference Token Count | 1500 characters | Code snippets for mobile device adaptation and permission configuration documents have limited single-item content length, so token consumption per reference must be controlled |
| `quoteMaxToken` | 2000–3000 tokens | Core content from app store review materials and crash analysis reports requires full recall, so the per-reference token limit must be matched |
| Context Recall Count | Top 3–5 entries | Change reviews for mobile development only require the most recent version release notes, adaptation checklists, and corresponding code changes; excessive entries will consume unnecessary tokens |

## Three common misconfigurations
- Model context cleared after invoking MCP tools: After each invocation of external tools to obtain device permissions or adaptation information, the model cannot continue the previous review topic. This occurs because the `maxContext` configuration is not set up to support context retention after tool invocation.
- Uploaded file paths include extra token parameters: File paths for app store listings or crash reports uploaded via FastGPT have random token parameters appended to the end. These paths cannot be directly passed to backend processing services via HTTP requests. This occurs because the token attachment configuration for file uploads is not disabled.
- Accidentally setting context limit to 4000 tokens: Long PR changes and complete adaptation checklists cannot be fully passed to the model, resulting in missing core adaptation rules or code change content during reviews. This occurs because the token limit was not adjusted based on the document characteristics of mobile development.

## How to confirm the configuration is properly set up
- Submit a PR change containing multi-device adaptation code, and check whether the context recalled by the model includes the adaptation checklist and historical crash analysis report for the corresponding version.
- Invoke the MCP tool to obtain device permission information, and confirm that subsequent review conversations can continue the previous context without topic interruptions.
- Upload app store review materials, and check that the file path received by the backend has no extra token parameters and can read the file content normally.
- View the context configuration panel in FastGPT v4.17.0, and confirm that the values of `maxContext` and `quoteMaxToken` meet the preset configuration standards.
