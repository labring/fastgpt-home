# Code and Change Review Assistance for Mobile Development: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Data related to mobile development code and change reviews comes primarily from code repositories, app store backends, crash monitoring platforms, and device coverage data.
Update frequency is daily or per version release cycle.
Daily associated documents include device version release notes, device adaptation checklists, crash analysis reports, and app store review materials.
Data fields include device OS version numbers, permission application statuses, crash log unique identifiers, app store review progress statuses, and more. There is no unified fixed format, so corresponding fields must be extracted based on different review scenarios.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
Scattered data sources and inconsistent update frequencies require multi-turn dialogue to bind the current review task using a unique identifier, to avoid confusing contexts across different sessions.
Daily document structures vary. Prompts must explicitly specify referenced document fields to ensure the model accurately matches review requirements. For example, extract target device versions from device adaptation checklists, and retrieve review rules from app store backends.
Core focus areas for mobile reviews are device adaptation and app store compliance. The context length of multi-turn dialogue must be kept within a reasonable range to prevent response delays from loading excessive historical data, which reduces review efficiency.
Errors in data association directly impact app launch. Prompts must strengthen verification logic for permission calls and review rules to ensure review results meet launch requirements.

## Configuration Settings
This configuration references the functional logic of FastGPT v4.17.0. Specific parameters and recommendations are listed below:

| Configuration Item | Recommended Value | Rationale |
| ---|---|--- |
| `chatId` | Bind the unique identifier for the current code review session | Ensure multi-turn dialogue associates the context of the same review task, avoiding message confusion across different review tasks |
| `messages` | Retain the most recent 15–25 conversation messages | Mobile review context typically focuses on recent code changes and adaptation issues; excessive length causes model response delays |
| `variables` | Pass the current review’s device list, app store review requirements, and crash log keywords | Cover core reference data for mobile development reviews, improving the relevance of model reviews |
| Temperature setting | 0.6–0.8 | Balance review rigor and flexibility, adapting to the needs of code rule verification and adaptation scheme derivation |
| Session timeout duration | 600 seconds | Adapt to the processing duration of mobile review tasks, avoiding data loss from mid-session interruptions |

## Three Common Misconfigurations
- The symptom is that global variables modified in a single conversation do not take effect in subsequent interactions. The cause is that dynamic in-session updates for `variables` are not enabled in the configuration, and only initial passed variable values are retained.
- The symptom is that different rounds of user questions and AI replies cannot be distinguished. The cause is that no unique session identifier is bound via `chatId`, causing the message list to mix content from multiple review tasks.
- The symptom is that individual question contents cannot be retrieved. The cause is that the context extraction rule for the `messages` parameter is not configured correctly, so only the last message is retained and historical question records are lost.

## How to Confirm Proper Configuration
- Initiate the first code review query, and verify that the `messages` parameter correctly loads historical context and the current query content.
- Modify global variables, then initiate a second query, and confirm that the variable values are correctly referenced in the model’s response.
- Switch between different review sessions using `chatId`, and confirm that contexts between sessions do not mix.
- Check the temperature setting, and confirm that the value falls within the 0.6–0.8 range to meet current review requirements.

The values provided are common starting points and should be measured against the reader's own samples.
