# Code and Change Review Assistance for Mobile Development: Workflow Orchestration

## What the data for this category looks like
The data sources for this category mainly include code repositories, app store backends, crash monitoring platforms, and device coverage data. Daily produced documents include device version release notes, device adaptation lists, crash analysis reports, app store submission materials, and similar items. Data update frequency follows a daily or per-version release cycle. Document fields mostly include specific content such as device version numbers, permission configuration items, crash log stacks, app store submission status, and there are no unified fixed format requirements.

## What constraints do these characteristics impose on the workflow orchestration link
The data sources for this category are scattered and diverse, requiring workflow orchestration to support integration with multiple external data sources. The structure of daily documents varies significantly, so `variables` configuration must be used to adapt to mapping rules for different fields. The data update rhythm is not fixed, so workflows must support both scheduled triggering and code commit event triggering. At the same time, links such as device adaptation verification and app store material compliance checks must be embedded in the workflow to prevent non-compliant outputs in subsequent processes. This configuration guide applies to FastGPT v4.17.0.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| ---|---|--- |
| Trigger node type | Code commit event + scheduled triggering | Adapt to dual scenario requirements for code repository updates and version releases |
| `variables` configuration | Includes three variables: device version number, permission list, crash log path | Match the core field requirements of daily documents |
| Data source pull timeout | 600 seconds | Adapt to interface response delays for code repositories and app store backends |
| Node execution order | Follow the sequence: device adaptation → permission verification → audit material generation | Align with standard review processes for mobile development |
| Error retry count | 3 times | Address execution failures caused by temporary interface fluctuations |
| Output document character length | 800-1200 characters | Adapt to format requirements for app store submission materials |

## Three common misconfigurations
- An error occurs when entering the edit interface after creating a workflow template. The cause is that the initial values of `variables` are not configured correctly, causing the system to fail to recognize subsequently referenced variable fields.
- An error occurs in the input box when connecting a code run node after referencing a created plugin in another workflow. The cause is that the fields output by the plugin are not mapped and bound to the `variables` of the current workflow.
- After local deployment, opening the workflow page displays the error "Cannot read properties of undefined (reading 'incl')". The cause is that the required `nodeId` field is missing from the workflow configuration, causing the system to fail to locate the corresponding execution node.

## How to confirm the configuration is complete
- Trigger the corresponding event (such as submitting code to a specified development branch) and check whether the workflow starts automatically.
- View the workflow execution log to confirm that fields such as the device version number and permission list in `variables` can correctly pull content from the corresponding data sources.
- Simulate permission adaptation and device verification links, and check whether the output review documents meet the format requirements of daily used device version release notes.
- Test error trigger scenarios (such as disconnecting the data source connection for the app store backend) and confirm that the workflow will perform retries according to the configured retry rules.
