# Code and Change Review Assistance for Renewal Health Management: Context and Token

## What the data for this category looks like
Data for renewal health management typically comes from CRM systems, product usage data, ticket statistics ledgers, and contract management systems. Update cycles run weekly or monthly. Daily deliverables include customer health reports, renewal forecast sheets, high-risk customer lists, and cross-departmental communication minutes. Data fields include customer identifiers, contract cycles, usage frequency, ticket counts, and snippets of communication records. Formats are inconsistent, with both structured tabular data and unstructured text content.

## What constraints these characteristics impose on the "context and token" link
The mixed structured and unstructured data structure of this category causes large fluctuations in context token consumption. Balance must be struck between recall scope and token limits. Weekly or monthly update cycles mean single tasks must cover several weeks or months of historical data. Without context size limits, long-running tasks risk timeouts. Core documents such as meeting minutes and risk lists have high content density. Improper chunking creates large numbers of invalid fragments, further increasing token consumption. Task results directly tie to customer retention. If context truncates critical risk clues, analysis bias occurs, creating customer churn risk.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `maxContext` | 12000–15000 token | Aligns with the output limits of common large language models, preventing response truncation during task execution |
| `quoteMaxToken` | 8000–10000 token | Covers complete customer communication records and contract snippets, ensuring key renewal risk-related clues are not missed |
| Similarity threshold | 0.5–0.7 | Matches the field density characteristics of this category’s data, balancing precision and coverage of recalled content |
| Single recall limit | Top 5 entries | Controls total context token scale, preventing timeouts during long task execution |
| Chunk length | 1200–1500 characters | Aligns with the paragraph structure of renewal forecast sheets and health reports, reducing fragmented content after chunking |

## Three common misconfigurations
- Setting `maxContext` above 16384 token causes large language models to trigger truncation at 12288 token, displaying an output limit exceeded error. This occurs because the configuration is not adjusted to match the large language model’s own output limits, and does not align with the actual token consumption needs of this category’s data.
- Setting the similarity threshold to 0.4 recalls large volumes of irrelevant non-renewal-related tickets and communication records, making it impossible to reference required customer risk content. This happens because the threshold is too low, and does not match the structured characteristics of this category’s data, leading to excessive recall noise.
- Failing to set a single recall limit includes all customer health reports from the full cycle in the context, causing task execution timeouts. This occurs because the configuration does not account for the update frequency and document scale of this category’s data, and fails to control total context token consumption.

## How to confirm proper configuration
- Import a single typical customer health report, run the code review assistance task, and check if recalled context fragments include core renewal-related fields such as contract expiration dates and ticket counts.
- Test the execution duration of long tasks, confirm no timeout errors occur, and that output content is not truncated early.
- Adjust the similarity threshold to 0.5, check if recalled document fragments are directly related to renewal risks, with no excessive irrelevant content.
- Review FastGPT v4.17.0 task logs, confirm that the `quoteMaxToken` configuration does not cause single quoted fragments to exceed the preset range.

The values listed above are common starting points, and should be validated against sample data from the actual deployment environment.
