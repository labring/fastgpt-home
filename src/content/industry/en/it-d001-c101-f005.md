# Code and Change Review Assistance for Renewal Health Management: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
This category's data typically comes from CRM systems, product usage data, ticket statistics, and contract ledgers. Update frequencies are mostly weekly or monthly. Daily deliverables include customer health reports, renewal forecast sheets, high-risk customer lists, and communication records. Fields cover customer contract cycles, recent cycle usage frequency, ticket response time, renewal deadlines, and more. There are no fixed standard units; values adjust based on document type and business requirements.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
Data sources are scattered and update cycles are long. Multi-turn dialogue must adapt to non-real-time historical data calls. Prompts must explicitly limit usage to weekly or monthly updated datasets. Document structures vary, so prompts must support different formats of health reports and lists to avoid field confusion. Risk categorization and renewal follow-up rely on precise contextual association. Multi-turn dialogue must retain prior risk judgments and communication records to prevent duplicate or conflicting analysis results.

## How to Configure Settings
The following configurations are based on the functional logic of FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Maximum Context Length | 1000–1500 characters | Adapts to the need for concatenating multiple weekly updated documents, avoids exceeding model processing thresholds |
| `messages` | Retain the most recent 4 rounds of historical content | Ensures coherent context for multi-turn dialogue, covers prior communication and data records |
| `variables` | Inject exclusive data fields for the current customer | Ensures prompts only call CRM and product usage data for the corresponding customer, avoids cross-customer interference |
| `chatId` | Bind to the customer's unique contract identifier | Locks the context scope of multi-turn dialogue, prevents data confusion |
| Message Format Conversion | Enable automatic escaping | Adapts to message display rules for third-party channels, avoids leftover syntax symbols |

## Three Common Configuration Errors
- Symptom: The conversation interface displays a "Data not found" error. Cause: Failed to bind `variables` to the current customer's exclusive data fields, causing prompts to fail in calling corresponding business data.
- Symptom: Third-party channels receive messages containing unrendered Markdown syntax symbols. Cause: Did not enable the message format conversion configuration, directly outputting native Markdown content.
- Symptom: Multi-turn dialogue calls the model twice consecutively and returns completely identical risk categorization results. Cause: Did not set a historical dialogue retention limit, redundant context causing the model to repeatedly read old data.

## How to Verify Proper Configuration
- Test binding the `chatId` of a specified customer, check if only that customer's health report data loads in the conversation.
- Initiate more than two rounds of multi-turn dialogue, verify that historical messages are retained according to the set round limit, with no redundant old data.
- Send a Markdown-formatted risk list, confirm that the receiving end receives content without unparsed syntax symbols.
- Trigger a data query action, verify that returned results only include weekly updated data for the current customer.
