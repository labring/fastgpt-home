# Code and Change Review Assistance for Defect Management and Regression Testing: Context and Token

## What the data for this category looks like
The core data for this category comes from defect management systems, test reports, code commit records, and user feedback. The update frequency is daily or per version iteration cycle. Daily processed documents include defect tickets, regression checklists, repair verification records, and defect statistical reports. Defect tickets contain fields such as reproduction steps, priority, and associated code snippets. Regression checklists are linked to test cases and defects to be verified. The text length of a single document ranges from hundreds to thousands of characters. Code commit diff fragments use line-level code blocks as basic units.

## What constraints do these characteristics impose on the context and token workflow
Diverse data sources lead to significant differences in text formats. It is necessary to retain key context such as defect reproduction steps and associated code logic to avoid information fragmentation caused by splitting. The high-frequency update feature requires the token processing workflow to adapt to real-time synchronized defect and test data, preventing review delays caused by processing latency. Fields across different documents are closely related. For example, defect tickets and code commits must be recalled simultaneously to complete a review. Therefore, context recall needs to balance the token proportion of multi-source data, avoiding overload from a single data type.

## How to set the configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to the typical text length of defect tickets and regression checklists, avoiding splitting of key logic |
| Overlap Length | 100–200 characters | Retains contextual connections between chunks, preventing key information from being truncated |
| `maxContext` | 4000–6000 token | Covers the total number of defects, code, and test data required for a single code review |
| `quoteMaxToken` | 1500 token | Limits the total token count of recalled associated defects and code snippets, avoiding context overload |
| Calibrated via actual testing | Calibrated via actual testing | Adapts to the scale of defect and code data for teams of different sizes |

## Three common misconfigurations
- Symptom: The fullTextTokens field is empty after importing data to the knowledge base. Cause: No specified non-splitting rule for text is configured, and the system forcibly splits key content, making it impossible to generate valid tokens.
- Symptom: A context limit exceeded error is prompted when calling the code review function. Cause: The value of `maxContext` exceeds the reasonable range adapted to the team’s data, and no adjustment was made based on the total token scale of defects and code.
- Symptom: Key code functions are split into multiple fragments after chunk processing. Cause: The statistical unit for chunk length is confused, and no chunking strategy adjustment was made for code fragments.

## How to confirm the configuration is valid
- View the knowledge base data processing logs to confirm that the chunked text does not split defect reproduction steps or core code functions.
- Access the knowledge base configuration page of FastGPT v4.17.0, and verify that the values of `maxContext` and `quoteMaxToken` match the preset configuration.
- Initiate a simulated code change review, and check that the total token count of recalled associated defects and test data conforms to the configured limits.
- Manually mark a section of key text as non-splittable content, and verify that the fullTextTokens field is generated normally after the system imports the data.
