# Code and Change Review Assistance for Configuration Management and CMDB Maintenance: Tool Calling and Plugins

## What Data for This Category Includes
Core data for this category includes configuration item lists, service component relationship topologies, change records, and asset inventory sheets. Data sources cover CMDB systems, cloud resource lists, auto-discovery tools, and procurement ledgers. Update frequency is daily or weekly.

Data fields include asset unique identifiers, configuration parameters, dependency relationships, and change timestamps. Different sources have varying data formats, so unified integration via tool calling is required. Daily maintenance uses this data to complete configuration item collection, relationship verification, and post-change updates. The core goal is to ensure asset consistency between records and actual state, and accurate service dependency relationships.

## Constraints Imposed on Tool Calling and Plugins by These Characteristics
This category’s data is multi-source heterogeneous and requires alignment with update frequencies. Tool calling must support multi-data source adaptation and periodic configuration refresh.

The core process focuses on verifying configuration items and dependency relationships. Plugins must have the ability to pull associated topology data, covering dependency relationships between service components. Change review context relies on historical operation records, so tool calling must support carrying session context to ensure data consistency during reviews.

Differences in data update frequencies require the tool calling cache strategy to align with the update rhythm of CMDB and cloud resource lists. This avoids using expired data for reviews.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Automatically select tools to adapt to multi-source CMDB data, no manual plugin call specification required |
| `functionCall` | `[{"name":"fetch_cmdb_config"},{"name":"sync_asset_topology"}]` | Match pull requirements for configuration item lists and relationship topologies, covering core review data |
| Tool call timeout threshold | `300 seconds` | Match the average response time of CMDB interfaces, avoid call failures due to network fluctuations |
| Cache refresh cycle | `24 hours` | Match the daily update frequency of CMDB data, avoid using expired data for reviews |
| Historical conversation carry switch | Enabled | Retain change review context records, ensure tool calls can associate historical operation data |
| Multi-source data merging strategy | Merge after deduplicating by asset ID | Avoid duplicate configuration item data interfering with review results, ensure data consistency |
| Plugin execution failure retry count | `2 times` | Address temporary CMDB interface fluctuations, reduce the need for manual intervention |

## Three Common Configuration Mistakes
- Issue: When calling the CMDB query plugin, the tool call log does not carry the session ID of the historical change review, and the returned configuration items lack associated dependency data. Cause: The historical conversation carry configuration is not enabled, or the configuration item is not correctly associated with the current review session ID.
- Issue: The plugin execution returns a 401 authentication failure status code, and core data from the CMDB system cannot be pulled. Cause: MCP-formatted authentication parameters are not correctly configured, or the parameters do not match the verification rules of the target CMDB interface.
- Issue: The configuration item data returned by tool calling contains a large number of duplicate entries, causing redundant interference in review results. Cause: The multi-source data deduplication strategy is not configured, or the strategy does not match by asset unique identifier.

- A simulated change review is initiated, and the tool call log in FastGPT v4.17.0 is checked to confirm that the historical session context is correctly carried in the plugin request.

- A plugin execution failure scenario is simulated, and the system is confirmed to automatically retry the operation according to the configured retry count.
- The merged result after plugin execution is checked to confirm that multi-source data has been deduplicated and integrated according to the configured strategy.
