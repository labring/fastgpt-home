# Code and Change Review Assistance for Incident Management and Root Cause Analysis: Workflow Orchestration

## What this category's data looks like
Data for this category comes from fault timelines, operational logs, monitoring metrics, and code commit records. Update frequency is either after each major fault or once per month. Daily deliverables include RCA reports, incident tickets, review minutes, and rectification tracking sheets. Document fields include fault occurrence time, root cause location results, rectification measures, tracking status, and more. There are no uniform mandatory units. Fields adjust based on specific fault scenarios. The core focus is on post-fault root cause analysis and prevention actions.

## Constraints on workflow orchestration
Data sources are scattered and update frequencies vary. Workflow orchestration must support flexible configuration of multi-source data pull nodes, and avoid forced fixed pull cycles. Daily deliverables have no uniform format. Allow custom field mapping nodes to adapt to document generation needs across different fault scenarios. Core root cause analysis steps have fluctuating time costs. Workflows must support manual approval and pause nodes between steps to accommodate manual verification for root cause hypothesis validation. Rectification tracking requires cross-cycle linkage. Configure status synchronization nodes to ensure real-time synchronization of rectification item status to tracking sheets. Unlike incident response workflows, this process does not cover real-time fault handling. It only focuses on post-fault root cause analysis and prevention actions.

## How to configure settings

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Global variable configuration | Bind incident ID, code repository address, monitoring metric prefix; value range is `1-10` | Adapt to dynamic data pull across multiple fault scenarios, reduce repeated configuration |
| Node ID binding | Assign a unique `nodeId` to each data pull and document generation node | Facilitate workflow debugging and abnormal node location, comply with FastGPT v4.17.0 platform orchestration specifications |
| Multi-source data pull trigger rule | Trigger by incident ticket creation; set timeout to `300 seconds` | Match the business requirement of collecting evidence immediately after a fault in this category |
| Document field mapping rule | Custom map fault timelines, log keywords, and code commit records to RCA report fields | Adapt to the business characteristic of no uniform document format, flexibly generate review documents |
| Manual approval node configuration | Configure in the root cause hypothesis verification link; set timeout to `24 hours` | Match the time-consuming manual verification step required for root cause analysis, avoid process blocking |
| Status synchronization trigger condition | Trigger when rectification item status changes; synchronize to rectification tracking sheet | Ensure real-time and accurate tracking data, avoid delays in rectification item tracking |

## Three common misconfigurations
- Phenomenon: Returns an interface does not exist error when calling the workflow API. Cause: Failed to correctly match the workflow orchestration API path provided by the platform, failed to reference official documentation when configuring the trigger interface.
- Phenomenon: Workflow cannot execute loop logic, resulting in repeated execution of invalid nodes when batch processing code commit records. Cause: Failed to enable the workflow's loop node configuration, failed to correctly set loop trigger conditions.
- Phenomenon: Knowledge base selection items in global variables are empty, unable to assign values dynamically. Cause: Failed to bind the association rule between knowledge base ID and incident scenario in variable configuration, failed to configure the dynamic update logic for variables.

## How to verify a correct configuration
- Trigger a test incident ticket, check whether the workflow starts the multi-source data pull node according to the configured trigger rules.
- Check the global variable panel, confirm that variables such as incident ID and code repository address have been correctly bound and support dynamic updates.
- Simulate the root cause hypothesis verification link, check whether the manual approval node triggers normally and whether the timeout setting takes effect.
- Submit a rectification item change, confirm whether the status synchronization node synchronizes the change content to the rectification tracking sheet.
