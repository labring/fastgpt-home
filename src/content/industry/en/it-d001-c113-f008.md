# Code and Change Review Assistance for Integration and API Testing: Workflow Orchestration

## What this category of data looks like
Data sources for this category include API management platforms, test environment logs, databases, and message queues. Update frequency is daily or when a version is released. Daily associated documents include API test cases, joint debugging issue tickets, environment descriptions, and test reports. API test cases contain API addresses, request methods, input parameter fields, and expected response codes. Joint debugging issue tickets include problem nodes, reproduction steps, and associated API IDs. Each document’s fields are independent, and cross-document relationships exist between them.

## What constraints do these characteristics impose on the workflow orchestration link
Dispersed data sources require the workflow to support connecting to multiple types of data source pull nodes, to ensure synchronized access to API test case, log, and issue ticket data. High update frequency requires trigger timing to match version release or scheduled rules, to avoid data lag. Diverse document structures and field associations require the workflow to configure parameter passing rules, to accurately bind cross-document associated IDs. Unlike unit testing and component testing, integration testing verifies cross-module interactions, so the workflow must include serial call nodes for multiple APIs. The dependent service preparation phase is time-consuming and error-prone, so the workflow must include a pre-environment check node to validate dependent service status in advance, reducing the risk of joint debugging delays.

## How to configure settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | Trigger on version commit / Trigger every 24 hours | Matches the daily or version-based update rhythm of API test cases and joint debugging issue tickets |
| Global Variable Configuration | Configure environment identifiers and API root address via `variables` | Unify the calling environment for integration testing, and avoid repeated configuration of the same parameters across nodes |
| Inter-node Parameter Passing | Bind upstream node output fields via `nodeId` | Accurately pass cross-node dependent data such as associated API IDs and test case IDs, and avoid parameter misalignment |
| Issue Optimization Configuration | Enabled, calibrate parameters based on actual testing | Extract key error fields from API testing to assist in quickly locating parameter verification issues |
| Failure Retry Settings | Retry 2 times, 60 second interval | Address occasional timeouts in the dependent service preparation phase, and reduce the risk of joint debugging delays |
| History Record Binding | Associate with the current test case ID | Pass historical joint debugging issues as context to nodes, to assist AI in locating current issues |

## Three common misconfigurations
- The workflow terminates after reaching the AI chat node, with the interface showing an incomplete process and no subsequent node output. The cause is that context parameters for the current test case are not configured via `variables`, so the AI node cannot access associated data.
- Historical records cannot be passed as variables to code execution nodes, and there is no historical record entry in the global variable options. The cause is that the output of the historical record node is not bound to the `variables` parameter.
- A "Cannot convert undefined or null to object" error pop-up appears during runtime. The cause is that the output of the upstream node is not bound via `nodeId`, resulting in empty passed parameters.

## How to confirm correct configuration
- Manually trigger the workflow, check if parameters for the corresponding API test case and joint debugging issue ticket data can be pulled, to confirm that the data source configuration is effective.
- View the global variable configuration item, confirm that `variables` includes environment identifiers and API root address, to verify that the global parameter configuration is correct.
- Simulate a missing parameter scenario, check if failure retry and alerts are triggered, to confirm that the failure handling configuration is effective.
- View workflow logs, confirm that the upstream node output bound via `nodeId` is correctly passed to downstream nodes, to verify that the parameter passing configuration is correct.
