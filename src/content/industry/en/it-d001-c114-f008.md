# Code and Change Review Assistance for Requirements Analysis and PRD Management: Workflow Orchestration

## What Data Looks Like for This Category
Typical users include internet product teams, business analysts, and product managers. They regularly create documents such as requirements research notes, PRDs, user story lists, and requirement change forms.
Data sources include customer interview records, ticketing systems, competitor public pages, and analytics dashboards. Update frequency is weekly or per version cycle.
Documents contain multiple types of fields including business goals, acceptance criteria, and change details. The most time-consuming steps focus on categorizing interview information, confirming boundary conditions, and syncing requirement changes.
Incorrect handling may lead to development rework, schedule delays, or acceptance disputes.

## Constraints Imposed on Workflow Orchestration by These Characteristics
Multi-type documents and non-fixed update cycles for this category require workflows to support dynamic access to multi-source data and regular synchronization. This prevents review deviations caused by expired data.
The diversity and complexity of document fields require precise extraction of matching content via workflow parameter configuration. This reduces manual screening workload.
The high frequency of requirement change synchronization requires workflows to include built-in loop or trigger mechanisms. These respond to changes in a timely manner.
The serious impact of errors requires workflows to include failure handling and status tracking nodes. This ensures the stability of the review process.
This configuration uses FastGPT v4.17.0 workflow functionality.

## Configuration Settings
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `variables` | Bind structured fields from requirements research notes and PRDs | This category’s data includes multiple document types, requiring extraction of corresponding fields as workflow inputs |
| Loop termination condition | Detect requirement change completion identification fields | Requirement change synchronization is a core time-consuming step, requiring early termination of invalid loops |
| Single execution timeout | 600 seconds | Requirement document processing covers multiple rounds of information categorization, avoiding long-term blocking |
| `nodeId` | Assign values sequentially according to workflow node order | Requires precise positioning of each review step’s execution node to avoid process confusion |
| Tool call parameters | Pass core PRD content fragments from the current node | Requires precise delivery of specific content required for requirements analysis, improving review accuracy |
| Single recall count | Top 5 entries | Adapts to the typical proportion of core review content in PRD documents |
| Maximum context length | 800–1200 characters | Calibrated through actual testing, adapts to the typical length of PRD documents |
| Single execution retry count | 3 times | Adapts to temporary adjustment needs during the requirements review process |
| Guest access configuration | Enable as needed | Adapts to requirements for some teams to publicly preview workflow effects |

## Three Common Configuration Mistakes
- Workflow runs correctly in preview but has no response after publishing the guest access window. The cause is incorrect configuration of guest access permission parameters, leading to blocked anonymous access.
- Loop body fails to terminate per the specified condition. The cause is failure to bind the loop termination condition to the requirement change identification field in the category’s data, preventing trigger of the termination logic.
- Tool call return results do not match input content. The cause is failure to associate corresponding document fields via `variables`, leading to passed parameters not covering core requirement content.

## How to Verify Successful Configuration
- Trigger workflow execution, check the `variables` binding results for each node, confirm whether corresponding fields from PRDs and requirements research notes are correctly extracted.
- Simulate triggering the loop body termination condition, verify whether the loop terminates normally after the specified identification is met, to avoid invalid execution.
- After configuring guest access, use the anonymous link to access the workflow, test whether review results can be returned normally.
- Check workflow node logs, confirm whether `nodeId` positioning matches preset review steps one-to-one, with no misalignment.
