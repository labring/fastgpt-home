# Code and Change Review Assistance for Project Document Handover and Archiving: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Data for this category comes from project document libraries, configuration lists, meeting minutes, and test reports. Updates occur at the end of each project phase or upon overall project completion. Daily produced documents include as-built documents, configuration manuals, training records, and acceptance certificates. Most document structures are categorized by project number and phase milestones. Fields include project identifier, version number, signing status, and delivery date. There are no fixed mandatory units; adjust based on actual project configuration.

## Constraints imposed on multi-turn dialogue and prompt engineering
Scattered data sources and phase-based updates require multi-turn dialogue to trace historical documents by project phase, avoiding context breaks. Daily documents include multiple deliverable types, so prompts must clearly define validation rules for different documents such as as-built documents and acceptance certificates. Non-real-time update frequency requires limiting the expiration range of dialogue context to prevent loading outdated phase documents. Fields include version number and signing status, so prompts must include version consistency check logic to ensure reviews cover version matching items. Project identifier is the core classification field, which must be accurately bound to the corresponding project’s document library content during dialogue to avoid cross-project data confusion.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Maximum Context Length | 8000–12000 characters | Single-phase document volume for this category is moderate. Overly long contexts may introduce irrelevant historical data and reduce review accuracy |
| Variable Injection Rules | Bind project number and phase milestone variables | Data for this category is categorized by project identifier, requiring precise targeting of the corresponding project’s document library content |
| Historical Message Filtering | Retain the last 3 phase review dialogues | Data for this category updates in phases. Full historical loading is unnecessary, avoiding context redundancy |
| Question Optimization Toggle | Enabled | Daily documents have diverse types. Optimized prompts can clearly distinguish validation logic for as-built documents and acceptance certificates |
| Single Dialogue Token Limit | 14000–18000 tokens, calibrated via testing | Multi-turn dialogue requires loading multiple types of document content simultaneously, requiring sufficient tokens to complete validation and review |
| Dialogue File Expiration Time | 7 days, calibrated via testing | Matches typical intervals between project phases, preventing phase documents from expiring prematurely |

This configuration is based on the interface logic of FastGPT v4.17.0.

## Three Common Misconfigurations
- Symptom: Token limit exceeded error appears in dialogue, with status code 413 or prompt "Single call token limit exceeded". Cause: The single dialogue token limit was not adjusted for this category’s multi-document loading scenario, and the underlying model’s token calculation rules were not matched, leading to a single-round call exceeding the limit.
- Symptom: Historical phase documents fail to load in dialogue, with prompt "File does not exist". Cause: The dialogue file expiration time was set to a duration shorter than the project phase interval, causing phase documents to expire prematurely.
- Symptom: Execution order of multiple AI dialogue tasks in batch execution nodes is chaotic, and results cannot be matched to project identifiers. Cause: Exclusive dialogue identifiers were not bound per project, leading to confusion of dialogue contexts across different projects and failure of task assignment.

## How to Confirm Correct Configuration
- Initiate a document integrity check dialogue for a single project, verify that returned content only includes document data for the current project.
- View the dialogue context panel, confirm that only historical messages related to the current project phase are retained, with no redundant cross-project content.
- Initiate a validation request covering multiple document types, verify that returned results cover inspection items for different types such as as-built documents and acceptance certificates.
- Adjust the dialogue file expiration time, wait beyond the set duration, then initiate a historical dialogue again, confirm that document loading status meets expectations.
