# Code and Change Review Assistance for Project Document Handover Archiving: Tool Calling and Plugins

## What this category of data looks like
This category of data primarily comes from project document libraries, configuration lists, meeting minutes, and test reports. Commonly processed documents include completion documents, configuration manuals, training records, and acceptance certificates. Data updates trigger at the end of each project phase or when the overall project is completed. A single document typically includes fields such as project number, document version number, associated delivery node, and signature verification status. Some acceptance-related documents also include third-party verification identifiers.

## What constraints these characteristics impose on tool calling and plugins
This category of data only updates at the end of project phases or when a project is fully completed. Tool calling must support pulling target data by specified project batches, without requiring high-frequency full synchronization. Daily processed document types are diverse, including files with different structures such as completion documents and configuration manuals. Some acceptance-related documents include signature verification fields. Plugins must support parsing mixed-structure documents to avoid missing key verification information. Data is associated with fields such as project number and delivery node. Tool calling must support filtering target content by project ID to ensure the review scope accurately matches the current handover project and prevent interference from cross-project data.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Automatically matches the tool calling logic for the current document type, adapts to formats including completion documents and acceptance certificates, based on FastGPT v4.17.0 automatic tool matching functionality |
| Single retrieval limit | Top 10 entries | Covers core delivery document entries for a single project, avoids redundant data disrupting reviews |
| `functionCall` | `enabled` | Supports structured extraction of key fields such as document version number and signature status, to improve review efficiency |
| Single parsing character limit | 8000 characters | Adapts to the content length of a single large configuration manual, prevents truncation of key information |
| Batch call batch size | 5 projects per call | Adapts to the volume of phase-updated data, reduces resource usage per call |
| Call timeout threshold | 300 seconds | Adapts to the parsing duration of a single large completion document, avoids mid-call interruptions |

## Three common misconfigurations
- A call to `/api/core/dataset/update` returns a 500 error. The browser can access normally, but the API call fails. This occurs because correct API authentication parameters are not configured in the workflow, causing interface verification to fail.
- A file read error occurs when calling the Doc2x tool, with a content parsing failure prompt. This happens because mixed structured and unstructured content in project documents is not adapted. The tool cannot correctly identify specific format files such as configuration manuals and acceptance certificates, leading to read failures.
- Semantic retrieval and full-text retrieval tools return a Connection error. This is because the retrieval scope is not configured by project batch. The tool attempts to pull full historical project data, exceeding the resource limit of the interface call.

## How to confirm the configuration is correct
- Trigger a tool call filtered by the specified project ID. Check if the returned results only include target files such as completion documents and acceptance certificates from the current handover phase.
- View the tool call log. Confirm that the `toolChoice` parameter is set to `auto`, and that the `functionCall` function correctly extracts key fields such as document version number and signature status.
- Test batch calling documents for 5 projects. Confirm that the interface does not return resource overlimit or timeout errors, and that the single call duration meets expectations.
- Simulate a call to the Doc2x tool to parse a single acceptance certificate. Check if the signature verification status field can be correctly extracted, with no parsing errors.
