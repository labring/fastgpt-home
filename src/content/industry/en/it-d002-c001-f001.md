# Release Notes and Operation Report Summary for CDN and Edge Acceleration Configuration: HTTP Interfaces and External Systems

## What data for this category looks like
Data for this category mainly comes from CDN consoles, DNS resolution records, user access logs, and monitoring alert systems. Daily produced documents include domain access forms, cache rule configuration files, refresh and preload operation records, and fault analysis reports. The update rhythm is usually daily summary or real-time updates with configuration changes. Fields include domain identifiers, cache policy parameters, node status, access traffic statistics, and other items. There are no unified mandatory units; fill content according to corresponding document specifications.

## What constraints these characteristics impose on HTTP interfaces and external systems
Data sources for this category are scattered, and update rhythms vary greatly. HTTP interfaces must support pulling logic for multiple types of data sources, and adapt to different update frequency settings. Daily document field structures are not uniform. The `responseData` returned by interfaces must support format conversion for multiple types of data including domains, cache rules, and access logs. Additionally, configuration changes or data abnormalities may cause public network access issues. Interfaces must include clear error status codes and `Authorization` authentication mechanisms to prevent unauthorized calls from leading to incorrect configuration changes. External system calls must comply with CDN node load limits to avoid service stalls from frequent requests.

## How to set configurations
| Configuration Item | Suggested Value | Basis for This Setting |
| --- | --- | --- |
| `Authorization` | `Bearer ${token}` | Complies with industry-standard API authentication specifications to secure calls to CDN configuration interfaces. |
| `responseData` field mapping | Map corresponding fields separately for domain access forms, cache rules, and access logs | Matches daily document structures to facilitate external system parsing and use of various CDN data. The CDN interface in FastGPT v4.17.0 has adapted to this mapping rule. |
| Interface polling interval | `300–600 seconds` | Adapts to the daily or real-time update rhythm of this category of data, balancing data timeliness and system load. |
| Interface timeout threshold | `10 seconds` | Prevents external system blocking caused by CDN node response delays, and complies with general timeout settings for public network interfaces. |
| `variables` parameter range | Restricted to valid domain names and cache policy identifiers | Prevents configuration errors caused by passing invalid parameters, ensuring the accuracy of interface calls. |

## Three common mistakes
- Calling the CDN configuration query interface returns empty fields. The cause is failure to correctly map `responseData` to the field structure of daily CDN documents, resulting in the external system being unable to parse valid data.
- The interface returns a 401 Unauthorized error. The cause is incorrect configuration of the `Authorization` parameter, or use of an expired authentication token.
- Frequent interface calls trigger node current limiting. The cause is failure to set a reasonable polling interval, exceeding the request bearing limit of CDN nodes.

## How to confirm configurations are set correctly
- Call the authentication interface to verify that the `Authorization` parameter is configured correctly, and a 200 status code is returned.
- Initiate a cache rule query request, and check that the fields returned in `responseData` fully match the local cache rule documents.
- View external system logs to confirm that the interface polling interval is within the `300–600 seconds` setting range, with no frequent call records.
- Simulate a domain configuration change request, verify that the error prompt returned by the interface meets expectations, and there are no unauthorized call situations.
