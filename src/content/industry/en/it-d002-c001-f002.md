# Release Notes and Operations Report Summary for CDN and Edge Acceleration Configuration: Context and Token

## What data for this category looks like
Data for this category comes from CDN consoles, DNS resolution records, public network access logs, and edge node monitoring alerts. Daily generated documents include domain name access forms, cache rule configuration tables, refresh and preload operation records, and node failure analysis reports.
Data updates occur either daily in aggregate, or in real time after each configuration change. Common fields include domain name, cache validity period, request volume, node IP, alert level, and trigger time. Only raw operation and runtime data is recorded. No fixed percentage statistics are included.

## How these characteristics impose constraints on context and token management
The data characteristics of this category create multiple constraints for context and token management.
Decentralized multi-source data requires temporal alignment during context aggregation to avoid wasted token usage.
Varied daily document structures cause fluctuating token proportions across different fragments. A maximum token limit for single context segments must be set in advance.
Flexible data update rhythms require context windows to be adjustable on demand, to accommodate sudden configuration changes or node alert data.
Additionally, the public network content distribution business nature requires real-time edge node status to be included in context. This further increases token consumption, so effective information must be filtered precisely.

## How to set configurations
| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | Covers the typical total token volume of core documents such as daily aggregated domain name access forms and cache rule tables, to avoid truncation of critical configuration information |
| `quoteMaxToken` | `2000–3000 token` | Matches the standard token length of single refresh/preload records and node failure analysis reports, to ensure referenced fragments are complete |
| Maximum context update interval | `10–30 minutes` | Aligns with the update rhythm of this category's data (daily updates or real-time updates after changes), balancing context timeliness and token consumption |
| Context fragment filter limit | `Top 5 entries` | Filters redundant access log data, to control total token usage per round of context |
| High-priority data toggle | `Enable only domain name configuration and alert data` | Reduces token usage from non-core node logs, focusing on business-related context information |

## Three common configuration mistakes
- Symptom: Large model output is truncated, or a token limit exceeded prompt is displayed. Cause: The `maxContext` parameter was not adjusted based on the token consumption of this category's data. Default configurations cannot cover the aggregated token volume of multi-source CDN data.
- Symptom: Context is lost after calling an MCP tool, and subsequent replies cannot associate previous CDN configuration information. Cause: The context persistence toggle was not configured. Tool calls trigger context resets, so historical CDN node configuration information cannot be retained.
- Symptom: CDN configuration files uploaded via FastGPT have token parameters in their file paths, causing the backend service to fail to read files normally. Cause: The token attachment toggle for uploaded files was not disabled. Verification parameters attached to the path interfere with the backend file reading logic.

## How to confirm configurations are correctly set
- View the FastGPT v4.17.0 console context statistics panel, confirm that the current context token total does not exceed the configured threshold. The threshold must be calibrated based on the daily data volume of this category.
- Initiate a query that includes multi-source CDN data, verify that returned context fragments include core fields such as domain name, cache rules, and alert information, with no obvious truncation.
- Call an MCP tool to perform a cache refresh operation, confirm that subsequent conversations can still associate previous CDN configuration context, with no context interruptions.
- Upload a CDN configuration file, check that the generated file path does not carry additional token parameters, to ensure the backend service can access the file normally.
