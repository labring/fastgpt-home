# Release Notes and Operations Report Summary for CDN and Edge Acceleration Configuration: Scheduled Tasks and Automation

## What Data for This Category Looks Like
Data for this category typically comes from CDN consoles, DNS resolution records, public network access logs, and monitoring alert systems. Daily generated documents include domain name access forms, cache rule configuration files, refresh and preload operation records, and fault analysis reports. Data fields include domain names, cache duration, request volume, alert levels, edge node IP addresses, and more. Data update frequencies are mostly daily updates or real-time updates following configuration changes. Single data volume fluctuates based on the number of domain names and access scale.

## Constraints for Scheduled Tasks and Automation
Scattered data sources and diverse field dimensions require scheduled tasks to integrate multi-source data to ensure summary completeness. Data update frequencies are not fixed, so both periodic triggering and event triggering modes must be supported. The structure and fields of daily documents must strictly match the output format of automated tasks to avoid field misalignment. The most time-consuming domain name record verification and cache rule debugging links should be prioritized for inclusion in automated tasks to reduce manual operation costs. A failure retry mechanism must also be reserved to prevent task interruptions caused by fluctuations in CDN APIs.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Task Trigger Timing | 2:00 AM daily + 10 minutes after cache rule changes | Matches off-peak hours for CDN business, complies with FastGPT v4.17.0 scheduled task scheduling specifications |
| Data Pull Scope | Previous day’s access logs, refresh and preload records from the past 7 days | Covers the regular summary cycle for operation reports, facilitating business trend analysis |
| Failure Retry Count | 3 times, 600-second interval | Filters occasional fluctuations in CDN nodes, avoids repeated occupation of API quotas |
| Abnormal Node Troubleshooting Threshold | 3 consecutive alerts + node response delay > 500 milliseconds | Focuses on real anomalies, filters temporary network fluctuations |
| Task Execution Window | 00:00 to 06:00 daily | Avoids public network access peaks, reduces impact on business |
| Report Generation Granularity | Summarized per individual domain name | Aligns with the business logic where domain names are the smallest unit of CDN configuration |

## Three Common Mistakes
- Symptom: Manually submitted domain name access form data disappears from summary reports several hours later. Cause: No data persistence rule was configured, temporarily cached access form data was not synchronized to long-term storage, and was cleared as the cache expired.
- Symptom: Cache rule configuration fields are empty in regularly generated release notes. Cause: Cache rule change events were not bound to the scheduled task triggering logic, only static data from a fixed time period was pulled.
- Symptom: Duplicate entries appear in summarized refresh and preload records. Cause: No deduplication rule was configured for log pulling, resulting in repeated pulling of logs for the same batch of refresh requests.

## How to Confirm Proper Configuration
- Manually trigger a scheduled task, check whether the generated release notes and operation reports include all configured data source fields.
- Simulate a cache rule change, confirm whether the task automatically executes within the specified time window and generates corresponding records.
- Simulate a node alert, check whether the failure retry mechanism is triggered and an abnormal troubleshooting log is generated.
- View task execution logs, confirm that the task starts during off-peak hours and does not occupy excessive CDN console API quotas.
