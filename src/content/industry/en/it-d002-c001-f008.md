# Release Notes and Operations Report Summary for CDN and Edge Acceleration Configuration: Workflow Orchestration

## What this category of data includes
Data for this category is collected from CDN consoles, DNS resolution records, public network access logs, and edge node monitoring alerts. Daily produced documents include domain access forms, cache rule configuration forms, refresh and preheat operation records, and node failure analysis reports. Included fields are domain name, cache policy type, refresh and preheat volume, alert trigger threshold, and more.
Data updates occur either as a daily summary or in real time when configuration changes. Core data focuses on the full process nodes of public network content distribution, covering access, caching, distribution, and fault troubleshooting stages.

## Constraints imposed on the workflow orchestration link
The multi-source nature of this category of data requires workflows to support cross-console data pulling. Multi-data source pull rules must be configured via `variables`.
Differences in fields across document types require built-in format verification and conversion nodes in workflows.
Flexible update frequencies require support for both scheduled trigger and change trigger modes.
Core data is bound to domain names and edge nodes. Workflows must use `nodeId` to associate configuration and logs of corresponding nodes during execution.
Additionally, time-consuming stages such as domain name record verification and cache rule debugging require workflows to support parallel branch processing. This avoids overall delays caused by serial execution.

## How to configure the settings
The following configuration items are designed for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Multi-data source pull rules | Configure pull intervals of 300-600 seconds separately for CDN consoles, DNS logs, and monitoring alerts | Covers core data sources, avoids frequent pulls that occupy node resources |
| Parallel branch trigger mode | Start all branch nodes simultaneously | Adapts to multi-stage parallel processing needs, reduces overall workflow execution time |
| `variables` | Bind three core fields: domain name, cache rule ID, and alert level | Unifies core identifiers for workflow execution, enabling subsequent nodes to associate data easily |
| `nodeId` | Bind the unique identifier of the corresponding edge node | Accurately associates node configuration with matching monitoring and fault data |
| Change trigger threshold | Triggered by configuration change operations | Adapts to real-time update requirements for operations report summary |
| Scheduled trigger cycle | Perform full summary at 2:00 AM daily | Covers the summary cycle for daily updated data, avoids resource usage during business peak hours |

## Three common misconfigurations
- Symptom: Only one branch node of the workflow runs, while other branches do not respond. Cause: The parallel branch trigger mode was not configured correctly, and the default single-branch execution rule was enabled.
- Symptom: Runtime logs prompt missing parameters, and workflow execution fails. Cause: `variables` or `nodeId` were not bound correctly, preventing nodes from retrieving required data identifiers.
- Symptom: Cache confusion or node matching errors appear in summary data. Cause: Field formats of different data sources were not verified, and data was directly spliced, leading to incorrect associations.

## How to confirm the configuration is complete
- Enter the workflow test page, trigger the parallel branch nodes, and verify all branches start execution.
- Review workflow runtime logs, confirm that the bound fields for `variables` and `nodeId` loaded correctly.
- Trigger a configuration change operation, confirm the workflow automatically starts the summary process.
- Check daily scheduled trigger summary results, confirm data covers all core stage data from the current day.
