# Release Notes and Operational Report Summary for IT Service Desk Ticket Processing: Workflow Orchestration

## What the data for this category looks like
Data for this category comes from enterprise ITSM systems, phone or online chat logs, asset systems, and internal knowledge bases. Update frequency is daily or real-time. Corresponding documents include service requests, incident tickets, processing records, and user satisfaction surveys. Core fields include unique ticket identifier, submitter information, problem classification tags, processing status, elapsed time, and satisfaction score. The ticket identifier is a string type. Elapsed time is measured in minutes. Satisfaction score uses a 1 to 5 point range.

## What constraints these characteristics impose on workflow orchestration
Data sources are scattered, and their update rhythms vary significantly. Workflows must support multi-source data access and real-time triggering, ensuring automatic process startup when a ticket is submitted or its status changes. Tickets include multi-dimensional fields, so workflows must support dynamic parameter passing to synchronize core information such as user questions and knowledge base IDs to corresponding nodes. Processes must cover the most time-consuming links including problem classification, remote troubleshooting, and escalation and dispatching. Failure handling branches must be configured to avoid ticket stagnation that causes SLA timeouts or employee work interruptions. Additionally, setups must adapt to HTTP script invocation scenarios, ensure parameter names and values match interface definitions, and resolve cross-node data transfer issues.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Workflow trigger mode | Trigger on ticket status change, or trigger on real-time request | Matches the real-time update rhythm of IT service desk tickets, supports automatic process startup for new tickets or status updates |
| Variable passing configuration | Bind the `variables` parameter to pass ticket ID, user question, and knowledge base ID | Covers dynamic parameter passing requirements, synchronizes externally passed ticket data to all nodes in the workflow |
| Node timeout setting | 600 seconds per node, 3600 seconds for the entire workflow | Matches the SLA requirements of enterprise IT services, avoids timeouts caused by process blocking |
| Failure branch configuration | Configure branches that trigger alerts and transfer to manual processing when a node fails | Prevents ticket processing stagnation, avoids impacting employee work or causing SLA timeouts |
| HTTP request parameter configuration | Follow interface documentation to define parameter names and values, bind corresponding fields in `variables` | Resolves parameter matching issues for cross-script calls, ensures functions such as base64 conversion operate correctly |
| Knowledge base parameter binding | Bind the knowledge base ID passed by the workflow to the search node | Enables dynamic specification of knowledge bases, adapts to ticket query requirements for different scenarios |

## Three Common Configuration Mistakes
- Phenomenon: HTTP request nodes return empty parameters or format errors. Cause: Failed to correctly bind dynamic variables in `variables` to parameter names and values in the request body, mistakenly using fixed strings instead of ticket-related data.
- Phenomenon: AI conversation nodes cannot obtain initial user questions. Cause: Failed to pass user input variables from the start of the workflow to the AI conversation node, resulting in no valid context input for the node.
- Phenomenon: Admin service startup verification fails. Cause: Failed to configure the `AIPROXY_API_ENDPOINT` (root address of the AI Proxy service, for example http://aiproxy:3000, do not append /v1 or other paths, do not use single-model service addresses such as VLLM/Ollama/Xinference) and `AIPROXY_API_TOKEN` (AI Proxy administrator token, must match the AI Proxy server configuration and be non-empty, do not use model vendor keys or application API Keys) environment variables on the Admin server side. Mistakenly filled model vendor keys or application API Keys into the AI Proxy-related environment variable configuration items.

## How to Confirm Proper Configuration
- Log in to the FastGPT Admin backend, check the service startup logs, confirm there are no missing required environment variable error reports related to AI Proxy, and adapt to FastGPT v4.17.0 and later versions.
- Manually trigger a test ticket, check the workflow node operation logs, confirm that the ticket ID, user question, and knowledge base ID in the `variables` parameter have been correctly passed to the corresponding nodes.
- Simulate a node failure scenario, confirm that the failure branch triggers alerts or transfers to manual processing and executes normally.
- Call the bound HTTP script interface, verify that parameter passing and base64 encoding conversion functions output results correctly.
