# Summary of Release Notes and Operational Reports for IT Procurement and Supplier Management: Context and Token

## What the data for this category looks like
This category’s data primarily comes from internal enterprise procurement systems, supplier quotation documents, budget spreadsheets, and contract systems. Daily processed documents include purchase requisitions, price comparison records, formal contracts, and acceptance documents. Data is updated per procurement workflow. Documents associated with a single procurement include fields such as purchase order number, supplier qualifications, quotation details, contract terms, and acceptance criteria. There are no unified fixed field units; adjustments are made based on document type.

## What constraints these characteristics impose on the context and token workflow
This category’s data is scattered across multiple independent systems. A single procurement workflow requires integrating multiple types of documents including purchase requisitions, price comparison records, contracts, and acceptance documents. The context must cover all associated content from the full procurement cycle, leading to token consumption increasing with the number of documents. Data update frequency is per order per month. Frequent incremental refreshes are not needed. However, the context must fully cover all information from a single procurement’s full workflow, so total context token volume must be limited to avoid overflow. The token proportion varies significantly across different documents. Contract term documents have a higher token proportion. It is necessary to allocate token resources by priority, while avoiding call timeouts or truncated results caused by overly long contexts.

## How to set the configurations
The following configurations are based on the interface parameters of FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum Context | Cover all documents from a single procurement workflow within 30 days | This category’s data is updated per order per month, so full coverage of all associated documents for a single procurement cycle is required to avoid missing critical information |
| `maxContext` | 12000–15000 token | Adapts to the total token consumption of multiple types of procurement documents, avoiding exceeding the model’s upper limit for a single call |
| `quoteMaxToken` | No more than 3000 token per document | Contract term documents have a high token proportion; limiting per-document token volume avoids context overflow |
| Single Document Chunk Length | 800–1200 characters | Balances semantic completeness after document splitting and token usage efficiency |
| Context Recall Limit | Top 8 associated documents | Focuses on core documents for the current procurement order, avoiding irrelevant data occupying token resources |
| Context Priority | Prioritize matching contract and budget fields | Errors in this category are mostly related to budget overruns and contract risks, so prioritizing recall of core fields is necessary |

## Three common misconfigurations
- An ACCESS_TOKEN invalid error is returned during calls. Cause: The supplier interface secret key was mistakenly entered into the context configuration item of the procurement system, and the API key corresponding to the FastGPT platform was not used.
- Total token exceeds the limit after multi-model orchestration, or context is lost for a single model. Cause: `maxContext` was not configured to limit total token volume. There is an incorrect assumption that multi-model tokens are automatically allocated independently, and no individual context upper limit was set for each model.
- The Reached the max retries error is returned after multiple calls. Cause: The `maxContext` parameter was not adjusted based on the token consumption of procurement documents. An overly long context causes model call timeouts and failed retries.

## How to confirm the configuration is correct
- Upload a single purchase contract document, check if the number of recalled context documents matches the associated documents for the current procurement order, and adjust the recall limit to a reasonable range.
- Simulate a multi-model orchestration workflow, check if the context token consumption of each model complies with the preset `quoteMaxToken` limit.
- Verify that a process ID filtering rule for the current procurement order is bound in the configuration items, ensuring that recalled documents are only associated with the current business.
- Trigger a complete release note summary task, check if the returned result includes all critical clauses from core documents, with no missing or truncated content.

The values provided are common starting points and should be measured against the reader's own samples.
