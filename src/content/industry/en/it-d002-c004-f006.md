# Release Notes and Operations Report Summary for IT Procurement and Supplier Management: Scheduled Tasks and Automation

This configuration solution is designed based on the scheduled task and automation capabilities of FastGPT v4.17.0.

## What data for this category looks like
Data for this category typically comes from internal enterprise procurement systems, supplier quotation documents, budget spreadsheets, and contract systems. Daily processed documents include purchase requisitions, price comparison records, formal contracts, and project acceptance documents. A single document usually contains fields such as procurement category, quantity, budget amount, supplier qualifications, and contract terms. The data update rhythm follows individual purchase orders: updates occur when a procurement process completes or during monthly aggregation, with no fixed bulk update cycle.

## Constraints on scheduled tasks and automation
Data sources are scattered across multiple internal systems. Scheduled tasks must adapt to API call permissions and return formats of different systems to avoid cross-system call conflicts. The per-order update rhythm requires task trigger logic to be bound to procurement process nodes, otherwise invalid executions will occur. The monthly aggregation requirement means scheduled tasks must support pulling full data in batches according to natural cycles, while retaining detailed traceability fields for individual purchase orders to ensure accuracy of aggregated data. Additionally, document fields include sensitive budget and contract term information. Data transmission and storage compliance must be ensured during task execution to prevent information leaks.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| Task Trigger Method | Trigger by procurement process node + monthly fixed trigger | Adapt to the dual requirements of single-order updates and monthly aggregation, matching the data update rhythm of this category |
| Single Task Execution Timeout | 300-600 seconds | Cover the time required for multiple API calls across procurement and contract systems, avoid task interruption due to slow system responses |
| Data Pull Scope | Filter by specified procurement department/project dimension | Focus on data from target business units, reduce invalid data processing volume |
| Failure Retry Count | 2-3 times | Address call failures caused by temporary system fluctuations, avoid direct task termination |
| Result Storage Path | Enterprise-specified internal document directory | Ensure storage compliance for sensitive procurement data, facilitate subsequent traceability |

## Three common configuration errors
- Phenomenon: A prompt that the knowledge base ID is empty appears when the scheduled task runs, making it impossible to pull corresponding data. Cause: The correct knowledge base ID associated with the procurement project is not bound in the task configuration, or the mapping configuration between the knowledge base and procurement process has not been completed in advance.
- Phenomenon: The task is automatically terminated after exceeding 180 seconds, failing to complete full data aggregation. Cause: The task timeout threshold is not adjusted, and the default short timeout setting is used, which cannot cover the total time required for multi-system API calls.
- Phenomenon: The purchase entries in the monthly aggregation report do not match the actual situation, with duplicates or omissions. Cause: The task trigger logic is not bound to the completion node of the procurement process, leading to repeated pulling of uncompleted purchase requisitions or omission of archived acceptance document data.

## How to confirm the configuration is correct
- Manually trigger a test task, check whether the pulled data entries match the currently active purchase order list.
- View the task execution log to confirm that the timeout setting matches the average response duration of current system APIs.
- Check the task failure retry configuration, simulate a temporary system fluctuation, and confirm that the task will automatically retry and complete eventually.
- Verify the storage path of sensitive data, confirm that only authorized business roles can access the generated operation reports.
