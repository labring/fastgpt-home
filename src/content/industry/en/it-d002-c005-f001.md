# Summary of Release Notes and Operation Reports for Issue Triage and Response: HTTP Interfaces and External Systems

## What data this category contains
The data for this category primarily comes from GitHub or Gitee Issues, code repository version logs, user-submitted environment information, and problem reproduction descriptions. Daily maintenance documents include Issue templates, tag rules, and historical reply records. The data update frequency is daily or weekly. Fields cover Issue numbers, titles, statuses, associated tags, submission times, reproduction steps, as well as version numbers, change content, and release times in version logs. The data structure is built around the full problem handling workflow, and no additional statistical aggregation fields are included.

## What constraints these characteristics impose on HTTP interfaces and external systems
This category’s data sources rely on external code hosting platforms and user-submitted content. HTTP interfaces must adapt to platform authentication rules. Data updates occur daily or weekly. Interface call frequency must align with this rhythm to avoid triggering external platform rate limits. The data includes sensitive information such as user environments and reproduction steps. Valid tokens must be configured via the `Authorization` header to complete permission verification. Cross-platform differences exist for Issue fields. Local fields and external interface parameters must be mapped using `variables`. The final output is used for release notes and operation reports. The structure consistency of `responseData` must be verified to ensure complete, usable fields. FastGPT v4.17.0 and later versions support the full verification logic for this configuration.

## How to configure
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Use a fixed Bearer token or read from environment variables | Adapt to external platform permission verification requirements to prevent interface calls from being blocked |
| `variables` | Map Issue numbers, tags, and submission times to external interface parameters | Unify cross-platform differences in Issue fields and meet the field requirements of operation reports |
| `responseData` | Only return structures with a 200 status code and including issue_id and update_time | Ensure consistent data source formats for release notes and operation reports |
| Call timeout period | 600 seconds | Adapt to the pull duration of complex Issue data to avoid mid-process interruptions |
| Call frequency | 1 time per day or 3 times per week | Match the data update frequency to avoid triggering external platform rate limits |
| Single pull quantity | Top 100 entries | Adapt to the conventional display and operation statistics requirements of Issue lists |

## Three common configuration errors
- Phenomenon: Automatic addition of Bearer tokens when calling external interfaces, leading to authentication failure or 401 status code return. Cause: Failed to turn off the platform's default Bearer automatic supplement configuration, and failed to manually specify a valid token via the `Authorization` item.
- Phenomenon: The data source plugin returns a database connection structure instead of SQL execution results. Cause: Failed to configure the correct query logic via the `variables` configuration item, only basic database connection parameters were configured.
- Phenomenon: The custom token passed in the workflow does not take effect, and the external interface returns a 401 status code. Cause: The workflow variables were not bound to the `Authorization` or `variables` configuration items, causing the interface call to use default parameters.

## How to confirm the configuration is correct
- Manually trigger an interface call and check if the returned results include the expected Issue fields and operation data.
- Check if the `Authorization` item configuration matches the token format required by the external platform.
- Verify that the field mapping configured in `variables` covers all fields required for operation reports.
- View the interface call logs to confirm that the timeout period and call frequency match the preset configuration.
