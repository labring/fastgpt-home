# Release Notes and Operation Report Summary for Issue Triage and Response: Workflow Orchestration

## What the data for this category looks like
The typical stakeholders for this category are open source maintainers, community operators, and core contributors. Data sources include GitHub or Gitee Issues, release notes, user environment information, and code repositories. Daily documentation covers Issue templates, label rules, response records, and problem reproduction instructions. Data updates occur daily or weekly. Core fields include Issue number, status, classification labels, reproduction steps, and submission time. Field verification and workflow transitions must be completed per project preset rules.

## What constraints these characteristics impose on the workflow orchestration link
Data sources rely on external code repositories and Issue platforms. Workflow configuration requires connecting to the API permissions of the corresponding platforms. The update frequency is daily or weekly. The scheduling cycle must be matched to avoid data lag or redundancy. Templates and rules for daily documentation must be embedded in the workflow verification link to ensure classification and tagging comply with project specifications. The most time-consuming steps include problem classification, completion of reproduction information, and marking of responsible modules. These steps must be automated via workflow nodes to reduce manual labor. Errors may lead to problem backlogs, user churn, or delayed defect localization. Failure retry and alert nodes must be configured. This category prioritizes problem description and priority. The trigger logic differs from that of Pull Request reviews. The workflow must use new Issue creation as the core trigger condition.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Problem classification prompt | Set to 800–1200 characters, calibrated via actual testing | Adapts to the workflow node logic of FastGPT v4.17.0, and aligns with project preset label rules |
| MCP plugin access | Enable external plugin calls, bind the secret key parameter in `variables` | Supports calling external tools to complete auxiliary operations such as environment verification and code reproduction |
| Code execution timeout threshold | Set to 600 seconds | Matches the typical time range for code debugging in open source projects |
| `variables` binding | Associate core fields such as Issue number and repository address | Ensures that the workflow reads correct data from the corresponding data source |
| `nodeId` association | Bind the unique identifier ID of the triage node | Enables data transfer and status synchronization between workflow nodes |
| Scheduling cycle | Update daily or weekly, matching the data update frequency | Aligns with the update rhythm of Issues and release notes |

## Three common configuration errors
- Code execution node fails with status code 500, caused by failure to bind preset code execution environment parameters in `variables`.
- No return result after MCP plugin call, with corresponding fields empty, caused by incorrect configuration of external plugin access permissions and secret keys.
- Problem classification results have significant deviation, with insufficient matching accuracy, caused by classification prompts not aligning with project preset Issue label rules.

## How to verify successful configuration
- Trigger a test Issue creation, and verify that the workflow automatically pulls the title and description of the corresponding Issue.
- Run the MCP plugin call node, and confirm that correct external tool execution results are returned.
- View the logs of the code execution node, and confirm that the execution duration does not exceed the 600-second threshold.
- Confirm that the classification results comply with project preset Issue label rules.

The values listed above are common starting points and should be evaluated against the reader's own samples.
