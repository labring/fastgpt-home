# Pull Request Review Release Notes and Operations Report Summary: Workflow Orchestration

## What the data for this use case looks like
Operational and release data for Pull Request reviews comes primarily from code repositories, CI pipelines, Issue linked links, and contributor submission records. Under FastGPT v4.17.0, daily generated documents include PR description documents, code review comments, CI execution results, merge operation records, and similar content. Data updates run daily or weekly, matching the rhythm of code submissions and CI scheduling. Data fields include PR unique identifier, submitter information, changed code scope, review comment details, CI status, merge time, and other items. There are no additional custom extended fields, and the structure is relatively fixed.

## What constraints do these characteristics impose on workflow orchestration
Data sources are scattered across multiple external systems such as code repositories and CI pipelines. Configure multiple workflow nodes to interface with different data sources. This avoids incomplete data pulling.
The fixed document structure requires workflow nodes to bind preset fields. It cannot flexibly adapt to non-standard format review data.
Daily or weekly update frequencies mean workflow scheduling cycles should not be too short. This prevents unnecessary resource consumption.
Split the most time-consuming links into independent workflow nodes: change intention confirmation, test result inspection, and merge conflict handling. Configure verification logic separately for each node. This prevents a single link error from blocking the overall process.
Review results directly affect code trunk stability. Configure exception branch processing logic in the workflow. Intercept PRs with failed CI runs or unresolved conflicts.

## How to set up the configuration
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Trigger Timing | Trigger on code push events | Match the update rhythm of PR submissions, avoid invalid polling |
| `variables` | Bind PR number, submitter, change scope fields | Pull full associated data for the corresponding PR from the code repository |
| Parallel Branch Count | 2–3 parallel branches | Process three core links simultaneously: review comment pulling, CI result verification, conflict checking |
| Timeout Duration | 600 seconds | Cover the conventional time consumption of CI pipeline execution and code pulling |
| Result Export Scope | Full review records | Export all PR descriptions, review comments, and merge records |
| `nodeId` | Bind unique identifiers for each node | Ensure accurate node addressing during workflow execution |

## Three common mistakes
- Insufficient exported review record count: Only the last few conversation entries are exported. This occurs because full data pulling parameters are not configured in `variables`, and only the latest fragment cached in the current conversation is read.
- The workflow only executes a single branch: Parallel flow configuration is not enabled when connecting multiple nodes, causing the workflow to execute branches sequentially and unable to process multi-dimensional review data simultaneously.
- Model call errors occur: Model calls are triggered without verifying the return status of CI results, or correct model parameters are not configured in the workflow, resulting in invalid calls that generate error logs.

## How to confirm the configuration is correct
- Trigger a new PR push event, check if the workflow starts all configured parallel branch nodes simultaneously.
- Export the review data for the corresponding PR, verify that the number of exported documents matches the number of review records for that PR in the code repository.
- View the workflow run logs, confirm there are no error messages about `nodeId` addressing failures or missing `variables` parameters.
- Wait for a complete scheduling cycle, check that an operational report summary file matching the update frequency requirements has been generated.

The values provided are common starting points and should be measured against the reader's own samples.
