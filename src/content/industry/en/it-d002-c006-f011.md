# Pull Request Review Release Notes and Operations Report Summary: Database and Operations
This document applies to FastGPT v4.17.0.

## What This Category of Data Looks Like
Data for this category typically originates from code repositories, CI pipelines, Issue links, and contributor submissions. Daily generated documents usually include PR descriptions, code review comments, CI execution results, and merge records. Data update frequency is usually daily or weekly. A single data entry typically contains fields such as PR number, submitter identity, change scope, review status, CI pass rate, and merge time. No pre-set statistical percentages or quantitative indicators are included.

## Constraints Imposed by These Characteristics on Database and Operations Workflows
Multi-source data access requires the database to support both structured and unstructured storage formats. This allows adaptation to different input types such as code repository metadata and CI logs. Daily or weekly update cycles usually create periodic read/write peaks. Reasonable connection pool and caching strategies must be configured to balance resource usage and response speed. Data fields include key business identifiers such as review status and CI pass rate. Indexes must be created for high-frequency query fields to reduce the time required to confirm change intentions and check test results. Data consistency requirements are directly linked to project main branch stability. Data write delays or losses must be avoided to ensure complete traceability of merge records and review comments.

## How to Set Configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Database connection pool size | `10–20 connections` | Matches daily/weekly data update peaks, avoids exhausting database resources with excessive connections, ensures concurrent query response speed |
| MongoDB connection address | Instance address calibrated to business data volume | Meets storage needs for unstructured review comments and CI logs from PR reviews, must match permission configurations for the corresponding repository's MongoDB instance |
| PostgreSQL connection address | Instance address adjusted to business query frequency | Used to store structured fields such as PR numbers, merge records, and review status, must match access configurations for the PostgreSQL instance |
| Redis connection address | Instance address set based on cache query volume | Used to cache high-frequency queried PR statuses and CI results, reduces time required to confirm change intentions |
| Cache expiration time | `300–600 seconds` | Balances cache hit rate and data freshness, adapts to the daily/weekly update cycle of PR review data |
| Single query return limit | `Top 100 entries` | Controls query return volume for operation reports, avoids excessive data occupying database and network resources |
| Database storage space quota | `1000–2000 MB` | Meets storage needs for unstructured logs and structured records from PR reviews, prevents data write failures due to insufficient storage space |

## Three Common Misconfigurations
- Symptom: `Access denied` error returned when debugging database connection components. Cause: Database connection username and permissions are not configured correctly, and read/write access permissions for corresponding PR review data are not granted.
- Symptom: No response when executing batch PR data synchronization tasks. Cause: Database connection pool is configured too small, cannot support concurrent requirements for batch data writes, leading to task blocking.
- Symptom: Excessively long query time for PR review operation reports. Cause: No database indexes created for high-frequency query fields such as PR numbers and review statuses, leading to full table scans that slow down query speed.

## How to Verify Proper Configuration
- Execute a database connection test to verify that the configured connection address and permissions allow normal read/write of corresponding business data.
- View real-time connection count of the database connection pool, confirm that peak connection count does not exceed the configured maximum connection threshold.
- Execute high-frequency PR status queries, verify that query response time meets expected business time standards.
- Check execution logs of data synchronization tasks, confirm there are no write failure or timeout records.

The values provided are common starting points and should be measured against the reader's own samples.
