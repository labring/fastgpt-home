# Release Notes and Operation Report Summary for SLA and Service Reports: Database and Operations

## What This Category of Data Looks Like
Raw service logs are stored in a document database connected via `MONGODB_URI`. SLA terms and caliber mappings are stored in a relational database connected via `PG_URL`. A cache service connected via `REDIS_URL` accelerates summary calculations.

Data sources include service monitoring systems, ticket systems, service contracts, and customer communication records. The update cycle is monthly or quarterly.

Daily output documents include full SLA clause texts, monthly service summary reports, system availability statistics tables, and customer service review minutes.

Data fields include service cycle identifiers, SLA agreed metrics, actual service achievement items, abnormal event numbers, response and processing durations. Common units are natural days, hours, and counts.

Documents exist as a mix of structured tables and plain text minutes. Some fields require alignment with contract clause calibers.

## What Constraints These Characteristics Impose on the Database and Operations Link
The monthly or quarterly batch update requirement demands databases support periodic batch data pulling and summarization. This avoids high-frequency real-time writes consuming excessive resources.

The need to integrate data from multiple sources demands databases support cross-system data association queries. It also requires compatibility with imports of raw data in different formats.

Fields need alignment with contract clause calibers. An additional mapping between data and contract clauses must be stored to ensure consistent data calibers.

Abnormal event attribution requires review of historical tickets and monitoring logs. Databases must retain at least two full quarters of historical data to prevent expired data loss.

Service-related data requires compliance verification. Modification permissions for historical data must be restricted. Read-only snapshot views must be enabled to ensure data traceability. The cache service connected via `REDIS_URL` can reduce database load from repeated queries.

## How to Configure Settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| Batch query concurrency | 50–80 concurrent connections | Matches monthly batch summary task volume, avoids exhausting database connections |
| Historical data retention period | 3–6 quarters | Meets abnormal event attribution review needs, controls storage costs |
| Data write permissions | Only accessible to operations accounts | Prevents unauthorized modification of service data, avoids errors in caliber alignment |
| Snapshot view configuration | Generate read-only snapshots monthly | Retains original data for historical reports, supports compliance verification and traceability |
| Cached intermediate results | Enable Redis caching | Reduces response time for repeated queries, lowers database load |
| Caliber mapping storage | Store in structured tables | Ensures consistent association between SLA clauses and actual data |

## Three Common Misconfigurations
- Symptom: Slow operation logs appear when generating monthly reports in bulk, and database responses time out. Cause: Batch query concurrency is not limited, leading to exhausted database connections and delayed processing of summary requests.
- Symptom: Exported service reports only include partial statistical fields, with missing abnormal event details. Cause: Historical data retention period is not configured, and expired data is automatically cleaned, preventing complete event information from being retrieved.
- Symptom: SLA compliance rate calculations do not match contract clause calibers. Cause: No mapping between data and contract clauses is stored, leading to caliber alignment deviations across different cycles.

## How to Verify Proper Configuration
- Run the monthly data summary script included with FastGPT v4.17.0. Check if database connection counts stay within preset ranges, and confirm no connection blocking errors occur.
- Randomly select report data from historical cycles. Verify the mapping relationship between raw data and contract clauses to confirm consistent calibers.
- View the cache monitoring dashboard. Confirm that intermediate calculation results are properly cached, and there are no frequent repeated queries to the database.
- Attempt to modify service data from historical cycles. Confirm that modification permissions are denied, ensuring data cannot be altered.
