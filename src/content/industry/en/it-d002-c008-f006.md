# Publishing Instructions and Operation Report Summary for Special Event Operations: Scheduled Tasks and Automation

This document applies to FastGPT v4.17.0.

## What the data for this category looks like
Core data for special event operations comes from four sources: content libraries, event backends, traffic data, and user feedback. Daily produced documents include event plans, resource slot schedules, event page copy, and post-event review reports. Document fields include unique event identifiers, resource slot numbers, schedule times, traffic metrics, user feedback tags, and more. Data update rhythms adjust based on event cycles. Updates are typically triggered weekly or around holiday nodes, with no fixed daily update frequency. Some event-exclusive data is only generated during the full event cycle.

## What constraints these characteristics impose on scheduled tasks and automation
Because data sources are scattered and update rhythms change with event cycles, scheduled tasks must support multi-source pulling and flexible cycle adjustments. Documents contain clear event cycle fields. Task triggers must be bound to event time nodes to avoid ineffective execution. Data has no fixed update frequency. Tasks cannot be set to fixed daily triggers. Different pulling logic must be matched to event preparation, execution, and review phases. Additionally, task execution failures may lead to incorrect event resource slot configurations or delayed review data. Failure retry and alert mechanisms must be configured to ensure stability.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Task trigger timing | 7 days before event, daily during event, 3 days after event | Matches the full cycle of special event preparation, execution, and review |
| Pull data source scope | Content library, event backend, traffic data, user feedback | Covers all data sources for this category |
| Single task execution duration limit | 600 seconds | Avoids occupying system resources for extended periods and affecting other tasks |
| Failure retry count | 2 times | Reduces ineffective repeated executions while covering temporary network fluctuations |
| Alert trigger threshold | Trigger after 1 task failure | Responds to anomalies promptly to avoid impacting event progress |
| Data validation rules | Check that event ID is not empty, traffic data is a positive integer | Ensures validity and completeness of aggregated data |

## Three common mistakes
- Phenomenon: Knowledge base content fails to update after scheduled task runs. Cause: Static page change detection logic is not configured, so only unrecognized content changes are pulled on a fixed schedule.
- Phenomenon: API call returns empty fields. Cause: The model type in task parameters is not configured correctly. The question classification model is mistakenly used for operation report generation tasks.
- Phenomenon: Human <Instruction> related errors occur during tool calls. Cause: The default guidance instruction for tool calls is not disabled, causing redundant content to be mixed into the task context.

## How to confirm configuration is complete
- Manually trigger a scheduled task bound to an event cycle, and check whether the latest data from the corresponding data source is pulled in the task log.
- Simulate a task failure scenario, and check whether the alert configuration normally triggers notifications.
- Submit test data that does not meet format requirements, and confirm that the task intercepts anomalies and records logs.
- View the event management interface, and confirm that the scheduled task is bound to the time node of the corresponding event.

The values provided are common starting points and should be measured against the reader's own samples.
