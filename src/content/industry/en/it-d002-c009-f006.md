# Summary of Release Notes and Operation Reports for Personal Information Protection Compliance: Scheduled Tasks and Automation

## What the data for this category looks like
Data sources for this category include business systems, App permission lists, privacy policies, and user request records. Updates are triggered on a quarterly cycle or when a product change occurs. Daily processed documents include personal information lists, processing rules, impact assessment reports, and user authorization texts. Field structures vary across different documents, covering core content such as information category, processing scenario, legal basis, and storage period. The size of a single document fluctuates with business scale, and no unified fixed single-data length exists.

## What constraints do these characteristics impose on the "scheduled tasks and automation" link?
Dispersed data sources require scheduled tasks to adapt to multi-system pulling logic, and avoid introducing unauthorized data sources. Ununified update rhythms require support for a combination of fixed-cycle scheduling and event-triggered scheduling, to meet the dual needs of quarterly updates and product change triggers. Differences in the structure of multiple document types require automated processes to have dynamic field mapping capabilities, to adapt to format differences of documents from different sources. Data processing for this category involves high-risk compliance scenarios. A clear alarm and retry mechanism must be triggered after a task fails, to prevent compliance process interruptions. At the same time, resource usage during task execution must be balanced, to avoid affecting business system operations. Task scheduling runs on FastGPT backend services, and does not rely on local boot or continuous Docker container operation.

## How to configure settings
This document is explained based on the functions of FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Task Trigger Cycle | Set according to business update frequency: set quarterly update tasks to `90 days`, set product change-triggered tasks to manual trigger | Match data update rhythm, avoid unnecessary execution |
| Data Source Pull Range | Limit to authorized business systems, App permission lists and other specified sources | Prevent introduction of non-compliant data sources, avoid compliance risks |
| Document Processing Concurrency | Set to `2–4` | Balance processing efficiency and system resource usage, avoid overload |
| Failure Retry Count | Set to `3 times`, retry interval `60 seconds` | Respond to temporary network fluctuations or short-term system exceptions |
| Task Alarm Threshold | Trigger alarm after `2 consecutive failures` | Detect compliance process abnormalities in a timely manner, avoid problem escalation |
| Output Document Format | Use standardized templates that meet compliance review requirements | Simplify subsequent manual review links, improve compliance efficiency |

## Three common misconfigurations
- Phenomenon: No alarm is triggered after a task fails. The FastGPT interface only shows the "Terminated" status, and no in-site or email notifications are sent. Cause: Failure alarm thresholds are not configured, and only manual task status checks are relied on.
- Phenomenon: Automatically generated compliance reports lack legal basis fields, and the content is incomplete. Cause: Dynamic field mapping rules are not configured, so differences in fields of documents from different sources cannot be adapted.
- Phenomenon: Scheduled tasks do not execute on time. Checking the scheduling log shows "Scheduling service not started". Cause: Misconception that scheduled tasks rely on local boot or continuous Docker container operation, and the FastGPT backend scheduling service running status is not confirmed.

## How to confirm proper configuration
- Manually trigger a test task, and check whether the output document includes expected core content such as personal information lists and processing rules.
- Check the scheduling log to confirm that the task starts normally according to the set trigger cycle or event trigger timing.
- Simulate a task failure scenario, and verify whether the preset alarm notification is triggered.
- Check the data source pull range to confirm that only authorized compliant data sources are included.
