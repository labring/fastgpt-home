# Release Notes and Operations Report Summary for Cloud Host Provisioning and Resource Onboarding: Workflow Orchestration

This document is written based on FastGPT v4.17.0.

## Data Structure for This Category
Data for this category originates from cloud management platforms, order systems, IAM permission systems, and billing systems. Updates are synced in real time per order.
Daily associated documents include resource onboarding tickets, instance configuration tables, account permission tickets, and delivery confirmation tickets.
Data fields include instance ID, compute specification, permission scope, delivery status, and billing cycle. Units correspond to CPU cores, memory GB, duration, and similar metrics.
This scope only covers compute resource provisioning and onboarding data, and does not include configuration content for other cloud service categories.

## Constraints for Workflow Orchestration
Due to scattered data sources and real-time updates, workflow orchestration must pull data across systems and configure trigger-based execution nodes to avoid delays from manual synchronization.
The multi-field structure of daily documents requires workflows to bind variable mappings for corresponding tickets, to ensure accurate data transfer.
Failures directly impact customer resource deployment and billing accuracy, so failure retry and alert mechanisms must be configured.
This category only focuses on compute resource provisioning, so workflows do not need to include configuration steps for other cloud service categories such as network load balancers. Execution scope of nodes must be clearly defined.

## Configuration Specifications
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Bind fields from resource onboarding tickets and instance configuration tables, formatted as `{"instanceId": "", "spec": "2核4GB", "expireTime": "2024-12-31"}` | Match the field structure of daily documents to enable automatic cross-system data synchronization |
| Node trigger timing | Trigger on order status changes | Match the real-time data update rhythm to avoid pulling invalid data repeatedly |
| Failure retry count and interval | Retry 3 times, interval of 60 seconds | Address temporary cloud API jitter, balance retry costs and delivery efficiency |
| `nodeId` | Bind the unique identifier of the cloud host creation node | Accurately locate the core compute resource creation step in the workflow to facilitate troubleshooting |
| Result filtering configuration | Only retain final status fields from delivery confirmation tickets | Filter redundant data from intermediate steps to avoid outputting irrelevant content |
| Alert trigger threshold | Trigger alert after 1200 seconds timeout | Match the typical time range for cloud host provisioning, to notify operations staff in a timely manner |

## Three Common Misconfigurations
- Symptom: An AI chat node is inserted into the workflow, and the final output includes intermediate chat content. Cause: Result filtering rules are not configured, and output fields from only specified nodes are not specified.
- Symptom: A permission verification failure error occurs during workflow execution. Cause: Variables from the IAM system are not bound, and a permission pull step is not configured in the workflow.
- Symptom: Fields from resource onboarding tickets are not automatically populated into workflow nodes. Cause: The `variables` parameter is not correctly bound, and field mappings for corresponding documents are not associated.

## How to Verify Proper Configuration
- Trigger a test resource onboarding order, check whether the workflow automatically pulls configuration fields from the corresponding order into `variables`.
- Simulate a cloud API call failure, check whether the workflow executes retries according to the configured retry count, and triggers an alert if retries fail.
- View workflow output logs, confirm that only final status fields from delivery confirmation tickets are included, with no redundant content from intermediate AI chats.
- Verify that the node corresponding to `nodeId` is the cloud host creation step, and confirm that the execution order of workflow nodes aligns with the resource provisioning process.
