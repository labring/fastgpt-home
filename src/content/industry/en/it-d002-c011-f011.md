# Release Notes and Operations Report Summary for Cloud Host Provisioning and Resource Activation: Database and Operations

## What data for this category looks like
Data for this category typically originates from cloud management platforms, order systems, IAM permission systems, and billing systems. Updates are synced in real time per order. Daily generated documents include resource activation tickets, instance configuration sheets, account permission tickets, and delivery confirmation sheets. Core fields include instance unique identifier, vCPU and memory specifications, permission role scope, delivery timestamp, order number, and billing node information. Data flows as structured tickets. Different tickets use distinct field combinations. Most field units are cores and GB. Identifier fields use string data types.

## What constraints these characteristics impose on the database and operations workflow
Multi-source data access requires databases to support cross-system data synchronization and format adaptation. This prevents data errors caused by differing field naming across systems. Real-time update requirements demand databases deliver low-latency single-operation write and query performance. This prevents blockages in the resource activation process. Differences in fields across multiple ticket types require databases to support flexible table structure expansion. No hardcoding is needed to adapt fields for each ticket category. Data accuracy directly ties to customer deployments and billing results. Configure data validation rules during operations to avoid issues like incorrect specifications or missing permissions.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://[username:password@]host1[:port1][,host2[:port2],...]/fastgpt?retryWrites=true&w=majority` | Adapts to cloud vendor-hosted MongoDB clusters, ensures write availability across multiple nodes |
| `PG_URL` | `postgresql://username:password@cloud-pg-host:5432/fastgpt?sslmode=require` | Complies with cloud database secure connection standards, encrypts transmission of sensitive configuration information |
| `DB_MAX_LINK` | `20–50 connections` | Matches default maximum connection limits for cloud databases, prevents service interruptions caused by exhausted connections |
| `REDIS_URL` | `redis://:redis-password@redis-host:6379/0` | Used to cache instance status and permission data, reduces high-frequency query pressure on the primary database |

## Three common misconfigurations
- Workflow stalls after executing a tool call node. Logs show connection timeout or refusal errors. The cause is an incorrect `MONGODB_URI` or `PG_URL` configuration. Cloud database access addresses, ports, and permission information are not properly configured.
- Cannot complete connection configuration for domestic databases. The tool call step cannot read cloud host resource data. The cause is that the default driver only supports standard MongoDB and PostgreSQL protocols. No dedicated connection driver packages for domestic databases are included.
- Cannot query the mongoose version using npm list inside the container, even though a dependency declaration exists in package.json. The cause is that dependencies are only installed in the project's local directory. No global environment variables are configured to point to the project dependency path.

## How to confirm configurations are properly set
- Log in to the FastGPT v4.17.0 system configuration page. Verify connectivity for `MONGODB_URI`, `PG_URL`, and `REDIS_URL`. Check the connection status prompt returned by the page.
- Submit a test resource activation ticket. Log in to the corresponding cloud database console. Check if corresponding instance configuration records are generated, and if core fields are complete.
- Execute a simulated tool call node. Check system logs for no database connection errors. Confirm returned results match the preset resource information format.
- Navigate to the FastGPT container's project directory. Run the npm list mongoose command. Confirm the locally installed version matches the declaration in package.json.
