# Release Notes and Operation Report Summary for Cloud Billing and Cost Accounting: Scheduled Tasks and Automation

## What the data for this category looks like
The data for this category primarily comes from cloud billing systems, tag data, order systems, and resource monitoring platforms. Regularly produced documents include billing details, cost allocation tables, resource utilization reports, and optimization suggestion sheets.
Data update cycles are divided into daily and monthly categories. Billing details and resource utilization reports are typically updated daily. Cost allocation tables and optimization suggestion sheets are mostly generated monthly.
Document fields include billing item identifiers, resource unique identifiers, billing cycles, expense amounts, tag key-value pairs, and more. Expense amounts are denominated in yuan. Some reports include dimension fields such as allocation ratios and resource utilization rates.

## What constraints these characteristics impose on scheduled tasks and automation workflows
The need to pull data from multiple sources requires scheduled tasks to adapt to the interface rate limits of different data sources, to avoid throttling caused by frequent calls.
The dual daily and monthly update cycles require task scheduling to support flexible cycle configuration, to match the update rhythms of different documents.
Complex document structures and multi-dimensional fields require automated processing workflows to include built-in field verification logic, to prevent invalid data from entering subsequent stages.
Tag ownership verification and abnormal expense troubleshooting are the most time-consuming steps. Automated rules must replace manual operations, and failure retry and alert mechanisms must be configured to prevent billing disputes or budget overruns caused by data anomalies.

## How to configure settings
| Configuration Item | Recommended Value | Basis for This Configuration |
| ---- | ---- | ---- |
| Task Trigger Cycle | Daily 02:00 or Monthly 1st 01:00 | Matches the update rhythm of daily/monthly documents, avoids peak business hours, and complies with the scheduling configuration specifications of FastGPT v4.17.0 |
| Data Source Pull Batch | Pull the first 100 records each time | Balances data pull efficiency and system load, avoids overload from single requests |
| Abnormal Alert Threshold | Trigger alert after 3 consecutive pull failures | Filters temporary network fluctuations, and notifies operations personnel to handle abnormalities in a timely manner |
| Failure Retry Count | 3 times | Balances retry cost and data integrity, avoids invalid retries that occupy resources |
| Task Timeout Duration | 3600 seconds | Covers the pull and processing duration of full billing data, prevents task interruptions mid-execution |
| Tag Matching Rule | Match by resource ID + tag key | Aligns with the tag ownership verification requirements of cloud billing, improves the accuracy of cost allocation |

## Three Common Mistakes
- Phenomenon: A large number of empty fields appear in billing details generated after scheduled tasks run. Cause: No field filtering rules were configured when pulling data sources, so expired or invalid billing data was included in the processing workflow.
- Phenomenon: The scheduled task queue does not automatically recover after a server restart, and cost allocation report generation stalls. Cause: Task persistent storage was not enabled, so unfinished task status was lost after restart.
- Phenomenon: Single task processing duration exceeds expectations, leading to backlog of subsequent tasks. Cause: No reasonable data source pull batch was set, and the amount of data pulled in a single time exceeded the system's single-processing limit.

## How to Verify Successful Configuration
- Check the task scheduling log to confirm that the task executed successfully during the preset trigger period, with no error messages.
- Randomly select 10 generated billing detail records, and verify that the field content matches the original data exported from the cloud billing system.
- Simulate a single pull overload scenario to verify that the task timeout duration and retry mechanism take effect as configured, and that corresponding alerts are received after the alert is triggered.
- Restart the service, check the task management interface, and confirm that the unfinished task queue loads automatically, with no stalled tasks.
