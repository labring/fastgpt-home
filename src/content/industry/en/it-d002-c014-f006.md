# Release Notes and Operations Report Summary for Cloud Resource Compliance Audit: Scheduled Tasks and Automation

## What the Data for This Category Looks Like
The data sources for this category are cloud audit logs, IAM permission systems, CMDB resource inventory libraries, and security baseline scan results. Four core types of documents are produced regularly: compliance checklists, permission audit reports, cloud resource inventories, and rectification tracking forms. Fields include resource ID, permission configuration items, exception status, rectification deadlines, and links to supporting materials. The data update cycle is monthly or quarterly. The number of fields and associated resource entries in a single compliance document varies based on the scale of an enterprise’s cloud assets.

## Constraints Imposed by These Characteristics on Scheduled Tasks and Automation Workflows
Data sources are scattered and require cross-system pulling. Scheduled tasks must be configured with multi-API call permissions and retry mechanisms. The update cycle is monthly or quarterly, so task execution frequency does not need to be high. A single task must process a large number of resource entries, so set reasonable sharding thresholds to avoid timeouts. Daily document formats are inconsistent. Some rectification tracking forms require association of data from multiple sources, so automated workflows must adapt to field mapping rules. Resource inventory checking and permission exception identification are the most time-consuming steps. Allocate sufficient computing resources to tasks to prevent execution interruptions caused by insufficient memory. Error consequences include audit failures and unauthorized access. Configure failure alerts and rollback mechanisms.

## How to Set Configurations
These configurations apply to FastGPT v4.17.0:
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Task trigger cycle | 00:00 on the 1st of each month / 00:00 on the 1st of the first month of each quarter | Matches the monthly/quarterly update frequency of business data, avoids repeatedly pulling unchanged resource data |
| Maximum single task execution duration | 3600 seconds | Adapts to time consumption requirements when processing a large number of cloud resource entries in a single run, prevents task interruptions due to timeouts |
| Concurrent resource pull count | Top 200 entries | Balances pull efficiency and system load, avoids triggering cloud service provider API rate limits due to excessive concurrency |
| Failure retry count | 3 times | Addresses temporary network fluctuations or temporary unavailability of cloud APIs, reduces the probability of task failure |
| Sharding processing size | 800–1200 characters | Adapts to the field length range of compliance documents, avoids context overflow caused by excessively long content processed in a single run |
| Failure alert trigger threshold | Trigger immediately after task execution fails | Matches the severity of error consequences, notifies cloud security operation teams in a timely manner to handle exceptions |

## Three Common Misconfigurations
- Phenomenon: A content length limit exceeded error occurs when pulling cloud resource inventories in batches, returning the `413 Request Entity Too Large` status code. Cause: No sharding processing rules are configured, and too many resource entries pulled in a single run cause content to exceed system limits.
- Phenomenon: Automatically generated compliance reports do not match the preset Word template format, and some fields are empty. Cause: No cross-source document field mapping rules are configured, causing pulled IAM permission data to fail to align with the fields in compliance checklists.
- Phenomenon: The reranking model is not automatically unloaded from video memory after retrieval is completed, causing subsequent tasks to trigger insufficient memory errors. Cause: No rules for automatically unloading the model after retrieval tasks are completed are configured, and video memory resources are not released in a timely manner.

## How to Confirm Configurations Are Correct
- Manually trigger a scheduled task, check for sharding processing records in the task log, and confirm that the sharding size configuration is effective.
- Check the alert channel configuration, simulate a task failure scenario, and confirm that corresponding alert notifications can be received.
- Verify that cross-system pulled data is complete, and confirm that the concurrent pull count configuration does not trigger cloud service provider API rate limits.
- Validate whether the format of automatically generated compliance reports matches the preset template, and confirm that the field mapping rules are configured correctly.

The values provided are common starting points and should be validated against on-site sample data.
