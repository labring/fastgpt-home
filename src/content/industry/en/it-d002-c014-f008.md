# Release Notes and Operations Report Summary for Cloud Resource Compliance Audit: Workflow Orchestration

## What Data for This Category Looks Like
This category’s data originates from cloud audit logs, IAM permission systems, CMDB resource inventory libraries, and security baseline scan results. Four standard document types are produced regularly: compliance checklists, permission audit reports, resource inventory lists, and rectification tracking forms. Each document includes fields such as resource identifiers, permission configuration items, compliance status, and rectification status. Data updates occur monthly or quarterly. Core data must cover the permission and configuration status of all cloud resources. Uncleaned raw logs must first undergo format standardization.

## Constraints These Characteristics Impose on Workflow Orchestration
Decentralized data sources require the workflow to integrate multiple system interfaces. Split nodes by cloud resource type and permission dimension to avoid request overload. The monthly or quarterly update frequency requires the workflow to support scheduled triggering. Reserve a data validation link to handle format exceptions in raw logs. The strong interdependence of compliance documents requires the workflow to retain field mapping rules, to ensure consistent fields between resource inventories and audit reports. The time-consuming nature of rectification evidence verification requires configurable batch evidence retrieval nodes. Set an exception retry mechanism to prevent single request timeouts from breaking the workflow. The risk of failed audits requires workflow output reports to include full compliance judgment basis, and omit no key fields.

## How to Configure Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Scheduled Trigger Cycle | Monthly/quarterly triggering, single execution duration no more than 3600 seconds | Matches the monthly or quarterly update frequency of this category, avoids excess costs from frequent cloud API calls |
| Batch Request Limit | Pull the first 20 resource data entries per request | Adapts to API rate limiting rules for CMDB and cloud audit logs, prevents request blocking |
| `variables` Configuration | Bind three types of variables: cloud resource ID, compliance threshold, and rectification status identifier | Ensures field consistency across documents, supports downstream nodes in reusing variable values |
| Retry Count and Interval | Retry 2 times after failure, 60-second interval | Addresses temporary cloud API fluctuations, prevents single request failure from interrupting the full workflow |
| `nodeId` Association | Bind the IDs of the data validation node and report generation node | Ensures workflow node execution order aligns with compliance document generation logic |
| Evidence Retrieval Scope | Filter evidence to retrieve based on entries in the compliance checklist | Reduces invalid data retrieval, cuts down time spent on rectification evidence verification |

## Three Common Misconfigurations
- The `variables` configuration in the workflow only passes the model name, without binding parameters such as MaxToken and temperature. The symptom is that the node returns status code 400 during execution, prompting missing model configuration parameters. The cause is that additional model configuration items are not added to the variable configuration.
- Not configuring the `nodeId` association rule causes global variable updates to not take effect. The symptom is that the custId parameter carried in the embedded system's share link is not updated synchronously. The cause is that variable transfer between nodes is not bound to the correct node ID, so upstream variables are not passed to downstream configuration links.
- The HTTP request node is not configured with a jsonPath extraction rule. The symptom is that the response result cannot be read by downstream nodes, and the fields are empty. The cause is that no jsonPath extraction rule is configured in the node settings, so the returned JSON content is not parsed into usable variables.

## How to Verify Correct Configuration
- Manually trigger the workflow once, check if the exported compliance checklist includes all configured resource fields, and confirm that the variable mapping rules are active.
- View the workflow execution logs, confirm that the scheduled trigger cycle matches the preset monthly or quarterly rhythm, and that the retry count and interval align with the configured requirements.
- Call the test interface of the HTTP request node, input simulated cloud audit log responses, and confirm that the jsonPath extraction rule can correctly extract target fields.
- Check that the `variables` configuration item includes all necessary compliance-related variables, ensuring that downstream nodes can directly reuse these variables to generate reports.
