# Release Notes and Operation Report Summary for Product Usage Data Analysis: HTTP Interfaces and External Systems

## What Data for This Category Looks Like
Data for this category primarily comes from tracking systems, data warehouses, CRM systems, and ticket systems. Updates follow a daily or weekly batch synchronization schedule. Regularly produced documents include usage analysis reports, tracking plans, indicator definition tables, and dashboard requirement forms. Common data fields include customer identifiers, function module codes, operation types, session durations, and indicator statistics. Units include counts, minutes, user counts, and similar units. Data must strictly align with the definitions in the indicator definition table to avoid inconsistent metrics across documents.

## Constraints for HTTP Interfaces and External Systems
Data for this category comes from multiple dispersed sources and must align with metric definitions across multiple business document types. HTTP interfaces must support pulling data from multiple sources and field filtering. Data updates follow daily or weekly batch synchronization schedules. Interfaces must adapt to batch request load limits to prevent timeouts from overly large single-request data volumes. Data must strictly follow definitions in the indicator definition table. Fields and units returned by interfaces must match business documents, otherwise incorrect metric judgments may occur. Interfaces must also support exception data reporting and retry mechanisms to reduce risks of operational errors from abnormal data.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Authentication Header | `Authorization: Bearer ${FastGPT_API_KEY}` | Complies with FastGPT v4.17.0 official API authentication specifications to ensure the legality of interface calls |
| Request Parameter Set | `variables={"start_time":"2024-01-01","end_time":"2024-01-07"}` | Matches the time range parameters of operation reports and adapts to batch pulling requirements |
| Return Field Filter | `responseData=["customer_id","module_name","operate_count"]` | Only returns fields specified in dashboard requirement forms to reduce data transmission volume |
| Batch Pull Limit | Top 1000 data entries, calibrated via actual testing | Adapts to the maximum load of single batch exports from data warehouses to avoid interface timeouts |
| Interface Timeout Duration | 60 seconds | Adapts to the response time requirements of daily data pulling to avoid request interruptions caused by long waits |

## Three Common Mistakes
- The `responseData` returned by the callback interface is missing the thought process field. This occurs because the corresponding return switch was not enabled in the request parameters, resulting in the interface not returning additional content required by the business.
- A 401 Unauthorized error is returned when calling the API interface. This occurs because the `Authorization` parameter format is incorrect, with the Bearer prefix missing or the secret key filled in incorrectly.
- A parameter error is returned when batch adding or deleting knowledge base collection data. This occurs because the correct knowledge base ID and collection ID were not passed in accordance with the `variables` requirements, causing the interface to fail to locate the target resource.

## How to Verify Proper Configuration
- Call the authentication interface, check that the returned status code is 200, confirming the secret key configured for `Authorization` is valid.
- Initiate a data pulling request, check that the returned `responseData` fields exactly match the configured filtered fields.
- Trigger a batch data synchronization, check that the number of results returned by the interface does not exceed the configured pull limit.
- Simulate a callback request, check that the receiving end can properly parse the returned business fields and format.
