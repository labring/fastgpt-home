# Release Notes and Operations Report Summary for Code Security Auditing: Context and Token

## What this type of data looks like
Typical users of code security auditing include security R&D teams, security service providers, and enterprise R&D teams. Daily produced documents fall into four categories: code audit reports, vulnerability proofs, repair suggestions, and retest records.
Data sources include source code repositories, dependency lists, static application security testing (SAST) tool output logs, and public vulnerability databases. Update frequency is once per project version or after completion of a single audit task.
Data fields include dangerous function location results, data flow tracking paths, repair solution details, and retest verification results. No fixed unified unit format exists. Some fields are pure code snippets, while others are structured technical entries.

## What constraints these characteristics impose on context and token processing
Document types for code security auditing vary widely, ranging from short vulnerability proofs to long data flow tracking reports. Updates per project version mean a single conversation must associate multiple related documents. This easily exceeds the model’s token limit.
Code snippets from source code repositories have significant length differences. Long files may contain thousands of lines of code. Using them directly as context quickly depletes token quotas.
Manual review requires complete business logic and attack path context. Key information cannot be truncated arbitrarily. This increases the difficulty of precise control over token consumption. A balance must be struck between context completeness and token usage efficiency.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum Context Token | 8000–12000 token | Adapts to the full associated data length of a single project audit, prevents single conversations from exceeding the model’s token limit |
| `quoteMaxToken` | 1500–2000 characters | Matches the typical length of single documents such as vulnerability proofs and repair suggestions, prevents a single quoted entry from accounting for an overly high proportion |
| Chunk Overlap Length | 100–200 characters | Retains contextual association for code snippets and data flow paths, avoids chunk truncation of critical logic |
| Single Recall Limit | Top 6 entries | Controls total token consumption, adapts to the single-batch data volume used in daily audits by R&D teams |
| `maxContext` | Calibrated based on project scale | Small-scale projects can be set to 6000 token, large-scale projects can be adjusted to 15000 token |
| Maximum Token per Quoted Entry | Adjusted based on document type | Set to 1800 token for code snippet documents, 1200 token for vulnerability report documents |

## Three Common Misconfigurations
- Phenomenon: Data blocks are too large during RAG classification matching. The interface displays a context overflow error. Background logs show token consumption exceeding the preset limit. Cause: Chunk length was not adjusted for code audit report long texts. Default parameters do not adapt to the field density of structured technical documents. This causes single block data to exceed token limits.
- Phenomenon: Token consumption details for each conversation cannot be viewed after private deployment. The system monitoring panel has no corresponding statistical fields. Cause: The context token statistics configuration switch was not enabled. The log collection link was not correctly associated with the monitoring system.
- Phenomenon: The conversation returns the Reached the max retries per request limit error. Response times out with no results. Cause: The single recall entry count was not limited. The `quoteMaxToken` parameter was not used to control the token upper limit for single quoted entries. This causes excessive request load triggering retry restrictions.

## How to Confirm Proper Configuration
1.  In FastGPT v4.17.0, upload a single typical code audit report. Test the total token count after chunking. Verify the count does not exceed the configured maximum context token value.
2.  Initiate a vulnerability review conversation. Review the number of context quotes returned. Confirm the count matches the configured single recall limit.
3.  Inspect system operation logs. Confirm each conversation includes token consumption statistical fields. No context overflow or retry limit exceeded error messages are present.
4.  Adjust the `quoteMaxToken` parameter, then upload a long code snippet. Validate that the single chunk data length matches the expected setting.

The values provided are common starting points and should be measured against samples from the target deployment environment.
