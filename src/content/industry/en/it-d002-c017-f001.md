# Release Notes and Operations Report Summary for Code Review and Merge Management: HTTP Interfaces and External Systems

## What the data for this category looks like
Target users of code review and merge management include development teams, Tech Leads, and open source project maintainers. Core data is sourced from Git repositories, CI pipelines, static scanning reports, and defect databases. Daily output documents include merge request details, code review comments, commit records, and branch strategy descriptions. Common data fields include merge request ID, commit hash, review status, associated defect number, and change content summary. Data updates are triggered by commit actions or run automatically once daily. The volume of data updated in a single operation varies based on team collaboration scale.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Data sources rely on open interfaces of external services such as Git repositories and CI pipelines. External system calls must be compatible with the authentication and data formats of the corresponding platforms. Data update frequency is high. Interfaces must support real-time callbacks or polling at appropriate intervals to avoid delayed summary information. Data fields include sensitive code change and defect association information. Interface transmission must configure security verification rules. Data volume varies with team size. Interfaces must support paginated returns to avoid overload from single requests that affects stability.

## How to configure settings
This configuration rule applies to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Callback URL | Fill in the HTTPS address of the external service that receives the summarized data | Ensure external systems can obtain updated code review and merge management data in real time |
| Authorization Credential | Configure the Bearer token for the `Authorization` field, using the authentication key assigned by the external system | Ensure the security of interface calls and prevent unauthorized access |
| Request Timeout | Set to 300-600 seconds | Adapt to data loading delays from CI pipelines and Git repositories, avoid call failures caused by timeouts |
| Return Data Filter | Specify the `responseData` field to only return the first 10 merge request IDs, review statuses, and change summaries | Filter sensitive information and comply with data usage specifications of external systems |
| Variable Mapping Rule | Map repository names and branch names in `variables` to project identifiers used by external systems | Enable cross-system project association and ensure correct data matching |
| Retry Count | Set to 2-3 times | Address temporary network fluctuations or short periods of unavailability of external services |

## Three Common Misconfigurations
- Phenomenon: The content returned after calling the interface contains unescaped HTML tags, such as `<p>How to switch from large model responses to human support during customer service integration</p>`. Cause: No text escaping rule was added to the return data filter configuration, causing format tags in original review comments to be exposed directly.
- Phenomenon: The interface call returns empty data. Cause: No correct repository branch filter parameters were configured in the variable mapping rules, so merge request data for the corresponding team was not matched.
- Phenomenon: Interface calls frequently trigger timeouts. Cause: No reasonable request timeout was set, and no retry mechanism was configured, causing call failures when CI pipeline data loading is delayed.

## How to Verify Successful Configuration
- Send a test request to the configured callback URL, check whether the returned data includes core fields such as merge request ID and review status.
- Trigger a code commit action and observe whether the external system receives the corresponding code review and merge management summary data.
- Call the interface using an incorrect `Authorization` credential, confirm that the returned status code conforms to authentication failure specifications.
- Simulate a scenario where CI pipeline data loading is delayed, confirm that the interface triggers the retry logic.
