# Release Notes and Operations Report Summary for Code Review and Merge Management: Scheduled Tasks and Automation

## What Data for This Category Looks Like
Data for this category comes primarily from Git repositories, CI pipelines, static scanning reports, and defect databases. Daily documents include merge requests, code review comments, commit records, and branch strategy descriptions. Core fields include merge request unique identifiers, reviewer lists, commit hashes, associated defect numbers, and branch names. Updates happen either when a code commit is triggered, or as a daily full summary of changes. Each record uses a standard timestamp format. Branch strategy descriptions cover branch naming rules and merge permission configurations.

## Constraints Imposed by These Characteristics on Scheduled Tasks and Automation
Data sources for this category are scattered, with varying update rhythms. High-frequency updates triggered by code commits mean scheduled tasks cannot use long intervals. Long intervals prevent timely summary of change information. The association logic between merge requests and review records is complex. A single task must process multi-dimensional associated data, which creates timeout risks. Branch strategies differ across projects. Tasks must support filtering target data by branch rules, and avoid redundant processing from repeated execution.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Task Trigger Mode | Event-triggered on commit + daily full re-scan | Adapts to high-frequency commits and missing data completion requirements, based on FastGPT v4.17.0 task scheduling logic |
| Single Task Execution Duration Limit | 600 seconds | Matches the conventional timeout threshold of CI pipelines, prevents tasks from being forcibly terminated |
| Retry Count | 2 times | Balances failure recovery and system resource usage |
| Data Pull Scope | Merge requests and review records from the past 7 days | Aligns with the conventional review cycle of development teams, reduces the data volume of a single task |
| Exception Notification Trigger Threshold | 2 consecutive execution failures | Avoids invalid notifications from single temporary exceptions, improves notification effectiveness |

## Three Common Misconfigurations
- Repeated scheduled task execution: The task status repeatedly switches to pending in the interface. This happens when no deduplication identifier is set in the task trigger configuration, leading to repeated triggers.
- Long-running task timeout: The interface returns a 504 status code. This occurs when the single task execution duration is not adjusted, exceeding the system default limit and resulting in forced task termination.
- Missing fields in operation reports: The merge request count field in generated release notes is blank. This happens when the data pull scope does not cover change records for the target branch, so no valid data is returned.

## How to Confirm Proper Configuration
- Manually trigger a scheduled task, and check if the task log includes merge request data for the target branch.
- After configuring exception notifications, simulate a task execution failure to verify receipt of the corresponding notification.
- Check the task trigger log to confirm triggers only occur at commit events or preset times, with no repeated execution records.
- Review the generated release notes and operation reports, and confirm core fields such as reviewers and commit hashes are correctly populated.
