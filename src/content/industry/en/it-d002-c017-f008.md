# Release Notes and Operations Report Summary for Code Review and Merge Management: Workflow Orchestration

## What Data for This Category Looks Like
Data for this category originates from Git repositories, CI pipelines, static scanning reports, and defect databases. Daily generated documents include merge requests, code review comments, commit records, and branch strategy descriptions. Data fields include merge request ID, submitter, changed file list, review status, CI execution results, defect severity and location, and more. Update frequency is daily or triggered by each code commit. Data formats vary across sources: Git commit records are text logs identified by hashes, while CI results include build duration and failed node information.

## Constraints Imposed on Workflow Orchestration by These Characteristics
Data sources for this category are scattered and have inconsistent formats. Workflow orchestration must support multi-source data pulling and format conversion. Configure `variables` to adapt to field mapping across different data sources. Update frequencies are flexible and triggers occur frequently. Workflows must support triggering via commit events or on a scheduled basis. Set reasonable node execution timeouts to prevent blocking. Merge requests and review comments are strongly correlated. Workflows must connect data according to their association, and handle exception branches such as empty review comments or abnormal CI results. Different teams have distinct branch strategies. Workflows must support custom branch filtering rules to adapt to different team development processes. Reserve manual review node entrances to meet business semantic judgment and maintenance boundary requirements.

## Configuration Settings
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | Trigger on merge request update events, or schedule a trigger every 12 hours | Adapt to data update frequency and avoid redundant data pulls |
| `variables` | Map merge request ID, changed file list, and review status to unified variables | Adapt to multi-source data formats and ensure consistent data transfer between nodes |
| Node Execution Timeout | 600 seconds | Prevent blocking when pulling CI pipeline results |
| Branch Filtering Rules | Only match main branches and feature branches | Adapt to general development branch strategies and exclude temporary test branches |
| Review Comment Summary Count | Top 20 entries | Avoid workflow execution lag caused by excessive summarized data |
| `nodeId` | Assign a unique identifier to each data pull node | Facilitate debugging and locating abnormal workflow nodes |

## Three Common Misconfigurations
- Symptom: The changed file link parameter received by workflow nodes is empty, making it impossible to pull static scanning reports for corresponding files. Cause: No mapping rule for changed file links is configured in `variables`, so uploaded files are not correctly parsed into transferable parameters.
- Symptom: An error indicating empty input occurs when global variables are passed between workflow nodes. Cause: Global variables are not initialized before node startup, or variable scope configuration is incorrect, causing nodes to fail to read corresponding values.
- Symptom: The AI review component cannot configure the large model temperature parameter, resulting in fixed style for generated review comments. Cause: The temperature parameter configuration item is not bound via variable reference, or no default value for the temperature variable is defined in the workflow's preceding nodes.

## How to Verify Proper Configuration
- Manually trigger the workflow once, check the log output of each node, confirm that all fields mapped via `variables` can be transferred normally.
- Simulate a merge request update event, verify that the workflow starts normally according to the configured trigger rules.
- Check the exception branch handling logic, manually simulate a CI failure scenario, confirm that the workflow terminates as configured and generates corresponding alerts.
- Check the node status identified by `nodeId`, confirm that each data pull node has a unique and recognizable identifier.

The values provided are common starting points and should be measured against the reader's own samples.
