# Release Notes and Operation Report Summary for Crowdsourced Annotator Management: Workflow Orchestration

## What data for this category looks like
This category’s data primarily comes from crowdsourcing platform backends, annotation quality spot-check records, annotator training exam results, and financial settlement systems. Daily maintained documents include annotator access rules, pre-job training materials, monthly performance statistics tables, and settlement detail lists.
Data updates follow daily and monthly schedules. Daily data mostly covers same-day annotation quality feedback and staff attendance records. Monthly data covers full-cycle performance rankings and settlement verification lists.
Data fields include staff ID, access qualifications, training assessment scores, daily completion volume, quality pass rate, settlement amount, and more. Management rules vary across different projects, with no unified fixed format.

## Constraints imposed on workflow orchestration
Workflows must include cross-source data pull nodes. These nodes adapt to interface formats of different systems, due to dispersed data sources.
Workflows must support flexible field mapping rules for inconsistent document formats. Core field correspondences can be manually configured.
Workflows must support both scheduled and real-time trigger modes. Daily tasks run during fixed early morning hours. Monthly tasks trigger on fixed dates each month.
Core time-consuming links include staff screening, quality ranking, and settlement verification. Workflows must split these links into independently orchestratable nodes. They must support grouping by staff and triggering subsequent processes based on quality thresholds.
Errors directly impact project delivery. Workflows must include failure retry and exception alert nodes. These nodes prevent incorrect or missed payments and project delays.

## How to set configurations
This document is written based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Data pull trigger timing | Daily tasks set to 02:00-04:00 daily; monthly tasks set to 01:00 on the 1st of each month | Adapts to business data update schedules, avoids occupying system resources during peak hours |
| Field mapping rules | Map three core fields: staff ID, quality pass rate, settlement amount | Matches fixed fields in core business documents for this category, reduces format adaptation costs |
| Node retry count | 3 retries, 60-second retry interval | Addresses temporary fluctuations in crowdsourcing platform interfaces, prevents process interruptions from single failed calls |
| Exception alert threshold | Trigger alert when quality pass rate is below 80% | Aligns with core indicators for annotation quality control, enables timely detection of abnormal staff |
| `variables` | Include three core variables: staff ID, performance score, settlement amount | Supports sharing business data across different links in workflows, simplifies workflow orchestration logic |
| Workflow timeout duration | 1200 seconds | Covers the longest time-consuming scenarios for full staff data pull and settlement verification |

## Three common misconfigurations
- Symptom: Workflow loop nodes cannot access externally passed staff list variables. An error indicating empty variables appears after execution. Cause: Cross-node variable transfer configuration for the workflow is not enabled, so the loop body cannot read output variables from preceding nodes.
- Symptom: After setting the text content extraction node to 6 chat history entries, the output result is empty or missing some chat content. Cause: The node’s `variables` parameter is not correctly bound, and the storage index or path for chat history is not configured in the node settings.
- Symptom: A timeout error with status code 504 appears when the workflow runs the settlement verification link. Cause: A reasonable workflow timeout duration is not set, and large settlement verification tasks are not split into subtasks, causing single-node execution duration to exceed system limits.

## How to confirm correct configuration
- Manually trigger the workflow once. View execution logs for each node, confirm that data pull, field mapping, exception alert, and other links run normally.
- Import a test set of staff performance data. Verify that cross-node variable transfer works correctly, and that the loop body can properly iterate through all test data.
- Simulate an exception scenario, such as setting the quality pass rate below the threshold. Confirm that the exception alert node triggers as configured.
- View the workflow’s operation statistics panel. Confirm that execution durations for each node meet expectations, and no timeout issues occur.

All provided configuration values are common starting points. Adjustments should be made based on local specific samples and operational requirements.
