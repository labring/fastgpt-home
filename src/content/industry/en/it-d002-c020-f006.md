# Release Notes and Operations Report Summary for Supplier and Equipment Delivery Management: Scheduled Tasks and Automation

## What data for this category looks like
Data for this category primarily comes from ERP systems, supplier shipping documents, logistics tracking information, and device manufacturer backends. Daily involved documents include purchase orders, delivery acceptance slips, serial number lists, and invoice materials. Data updates use individual orders as the basic unit; some bulk procurement scenarios update data on a weekly basis. Data fields include purchase order numbers, supplier entity information, device models and serial numbers, delivery times, acceptance statuses, invoice association numbers, and more. There are no unified fixed units, as they vary by device category and procurement requirements.

## What constraints these characteristics impose on scheduled tasks and automation
Scattered multi-source data requires scheduled tasks to adapt to the interface call frequencies of different systems, to avoid triggering rate limits. The update rhythm of individual orders or weekly updates means task trigger cycles must match the actual circulation rhythm of procurement and delivery, to avoid ineffective repeated execution or data lag. Differences in field structures across documents require automated summary processes to configure targeted field mapping rules, to adapt to the validation logic of different documents such as purchase orders and acceptance slips. The strong business attributes of data association mean that a clear alert and retry mechanism must be triggered after task execution fails, to prevent project delays or book-actual discrepancies caused by data mismatches.

## How to set configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Task trigger cycle | Set to `15 minutes` for individual procurement, `1 day` for bulk procurement | Adapt to the real-time requirements of individual orders and the weekly update rhythm of bulk procurement, avoid frequent external interface calls |
| Data source pull scope | Only pull order data pending acceptance or summary | Reduce invalid data processing, match the individual-order update feature of this category |
| Field validation rules | Configure corresponding validation items by document type | Adapt to field differences across documents such as purchase orders and serial number lists |
| Failure retry count | `3 times`, retry interval `60 seconds` | Address temporary interface fluctuations, avoid task interruption from a single failure |
| Summary report output format | Supports PDF and structured tables | Adapt to viewing requirements of different roles such as business and warehouse staff |
| Alert trigger threshold | Trigger an alert after 2 consecutive task failures | Notify relevant personnel of exceptions in a timely manner, prevent business delays |

## Three common mistakes
- Phenomenon: "Field is empty" error logs appear after scheduled task execution, and device serial number information is missing from the summary report. Cause: No field mapping rules for the serial number list are configured, and the required field integrity for this document is not validated.
- Phenomenon: Task execution times out in bulk procurement scenarios, returning status code 504. Cause: The task trigger cycle is set too short, and full historical order data is pulled at the same time, exceeding interface call limits.
- Phenomenon: When configuring an automatic summary task in a workflow, the corresponding order data source is not bound, resulting in no data available for task processing. Cause: The workflow trigger node is not correctly associated with the data source pull node, and the order ID transfer rule is not configured.

## How to confirm configurations are correct
- Manually trigger a test task, verify that the output summary report includes all required fields for the current test order, including purchase order numbers, device models, and serial numbers.
- View task logs, confirm that the trigger cycle matches the configured requirements, with no exceptions of frequent repeated execution or long periods of no execution.
- Simulate a data source interface exception, confirm that the task failure alert logic works correctly, and the alert information includes the abnormal order number and error type.
- Check the field mapping configurations for different document types, confirm that the associated fields for purchase orders and delivery acceptance slips are correctly bound.
