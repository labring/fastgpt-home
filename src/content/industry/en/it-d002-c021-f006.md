# Release Notes and Operations Report Summary for Supply Chain Security and Open Source Dependency Governance: Scheduled Tasks and Automation

## What this category of data looks like
The core data of this category includes four types of documents: SBOM manifests, dependency risk reports, license lists, and repair work orders.
Data sources cover package managers, code repositories, vulnerability databases, and license databases.
Updates occur daily or alongside software version releases.
Document fields include component name, version number, vulnerability severity, license type, repair status, and others.
There are no unified fixed units. Some fields must be associated with external data sources for generation.

## What constraints do these characteristics impose on scheduled tasks and automation
Multi-source data pulling requires scheduled tasks to support parallel calls to multiple data sources. This prevents single-source access exceptions from slowing the overall process.
Links such as dependency asset identification and vulnerability version matching take extended time. The processing scale of a single task must be limited to avoid execution timeouts.
Update rhythms vary across different document types: SBOM is updated with version releases, while risk reports are updated daily. Differentiated trigger frequencies and execution logic must be configured for each document type.
Repair work orders need to be linked to the latest vulnerability and dependency data. Data synchronization dependencies must be set between tasks to ensure processing logic accuracy.

## How to configure settings
The following configurations are designed for the scheduled task module of FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Task trigger frequency | Set separately by document type: SBOM tasks trigger with version releases, risk report tasks trigger daily at 02:00 | Match data update rhythms to avoid repeated pulling or missed updates |
| Maximum single-task processing data volume | 1000 dependency components | Match the time limit of the dependency asset identification link to prevent execution timeouts |
| Task timeout threshold | 1800 seconds | Reserve redundant space to handle time fluctuations in vulnerability version matching, and prevent tasks from being forcibly terminated |
| Number of failure retries | 3 times | Respond to temporary access exceptions for package managers or vulnerability databases |
| Task parallelism | 2 parallel tasks | Balance cluster resource usage and processing efficiency |
| Task association configuration | Auto-generated code tasks only trigger after SBOM and vulnerability data pulling are completed | Ensure code analysis uses the latest dependency governance data |

## Three common misconfigurations
- Phenomenon: Scheduled tasks trigger multiple times at the specified time. Cause: No task deduplication mechanism is configured, or trigger rules match multiple scheduling sources at the same time, causing the task to be called multiple times.
- Phenomenon: A single task is forcibly terminated after its execution duration exceeds 1200 seconds. Cause: The task timeout threshold is not adjusted based on the actual time spent on dependency asset identification and vulnerability matching, or the single-task processing data volume exceeds a reasonable range.
- Phenomenon: Automatically generated analysis code does not link to the latest dependency governance data, leading to inaccurate operation report results. Cause: The code generation link is not bound to the scheduled SBOM and vulnerability data pulling tasks, causing the code to use outdated dependency information.

## How to confirm the configuration is correct
- Check the scheduling log to confirm that tasks trigger at the preset frequency, with no repeated execution records.
- Manually trigger a test task, and verify that the execution duration does not exceed the preset timeout threshold.
- Compare the generated SBOM manifest with the latest dependency data from the code repository to confirm that the data source is correct.
- Check the configuration of the auto-generated code task, confirm that it is linked to the latest dependency governance data to ensure accurate analysis results.
