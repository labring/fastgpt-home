# Release Notes and Operations Report Summary for Supply Chain Security and Open Source Dependency Governance: Workflow Orchestration

## What the Data for This Category Looks Like
Data for this category primarily comes from package managers, code repositories, public vulnerability databases, and license databases. Four core document types are regularly produced: SBOM lists, dependency risk reports, license compliance lists, and repair tickets.
Data updates follow a daily sync schedule or are triggered by software version releases. Each document includes fields such as dependency package name, version number, vulnerability CVE ID, license type, and risk level. There are no unified fixed units; fields are labeled based on the actual attributes of dependency assets.
Data volume fluctuates with the size of the project codebase. Core processing time is concentrated in three links: dependency asset identification, vulnerability version matching, and upgrade impact assessment. This guide is written using the workflow features of FastGPT v4.17.0.

## Constraints These Data Characteristics Impose on Workflow Orchestration
The data characteristics of this category directly restrict the core logic of workflow orchestration.
Multi-source data pull links must adapt to format differences across data sources such as package managers and code repositories. They must support triggering tasks on a scheduled basis or via version release events.
The multi-field document structure requires workflow nodes to be configured with unified field mapping and validation rules. This prevents missing key information such as dependency package names and vulnerability levels.
Fluctuating processing times for core links require workflows to be set with reasonable timeout thresholds and retry strategies. This prevents blocking of the overall process.
An exception alert node must also be configured to trigger corresponding notifications when high-risk dependencies or license violations are detected.
Additionally, the workflow must support queries across multiple knowledge bases to complete cross-source data matching verification.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | Scheduled daily / triggered by version release events | Matches the update schedule of this category's data, which occurs daily or with version releases |
| `variables` | Preset global variables including dependency package name, vulnerability level, license type, etc. | Supports passing core business data across multiple workflow nodes |
| Field Validation Rules | Enforce non-empty checks for dependency package name and CVE ID fields | Prevents missing core document fields from causing errors in subsequent links |
| Timeout Threshold | 1800 seconds | Adapts to the average time fluctuation range of core processing links for this category |
| Retry Count | 2 times | Reduces task failure rates caused by temporary network fluctuations or delayed responses from data sources |
| `nodeId` | Assign a unique identifier to each data source node | Differentiates pull tasks from different sources such as package managers and code repositories to avoid data confusion |

## Three Common Misconfigurations
- Symptom: Workflow runtime displays "global variable undefined" error. Cause: Failed to preset global variables related to dependency assets in the `variables` configuration item, or the variable name does not match the spelling used in node references.
- Symptom: Workflow node shows failure, and restarting does not resolve the issue even after confirming the model configuration is correct. Cause: Failed to assign a unique `nodeId` to each data source node, leading to data confusion from multi-source pulls and triggering field validation failures.
- Symptom: Some high-risk vulnerability information is missing from the generated dependency risk report. Cause: Failed to configure a reasonable timeout threshold, causing the vulnerability database pull link to time out and fail to fully retrieve vulnerability data.

## How to Confirm Proper Configuration
- Manually trigger the workflow once, view the runtime logs of each workflow node, and confirm that links such as data source pull and field validation have completed normally.
- Verify the `variables` configuration item, confirm that all global variables referenced in workflow nodes have been preset, and that there are no spelling errors in the names.
- Check that each data source node has a unique `nodeId` to avoid confusion between task data from different data sources.
- After adjusting configurations such as timeout thresholds and retry counts, simulate abnormal scenarios to verify that the task recovery strategy takes effect.
