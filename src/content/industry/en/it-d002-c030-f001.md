# Release Notes and Operation Report Summary for Internal Network and WiFi Operations: HTTP Interfaces and External Systems

## What this category of data looks like
Internal network and WiFi operations data primarily comes from switch consoles, wireless controllers, office network monitoring systems, and user trouble reporting channels. Data is updated daily or immediately following network changes. Common documents include network topology diagrams, change tickets, fault records, and wireless coverage inspection reports. Data fields include device ID, port number, VLAN configuration, signal strength (unit: dBm), fault type, inspection time, and more. Data formats vary across sources. Raw data returned by some device consoles requires format conversion to meet operational summary requirements.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Dispersed data sources and varying formats for internal network and WiFi operations require HTTP interfaces to support unified pulling and format conversion of multi-source data. Data update cycles are inconsistent, so interfaces must support both incremental and full pull modes to adapt to different scenarios of daily inspections and immediate network changes. Data fields include specific units and identifiers, so interface parameters must validate field legitimacy to prevent invalid data transmission. Additionally, operational data directly relates to office network stability, so interfaces must have stable concurrent processing capabilities to avoid disrupting normal office network operations due to request overload.

## How to configure settings

| --- | --- | --- |
| Application API Key Authentication | Configure as Bearer token format, carrying an API Key issued by the application | Complies with external system authentication specifications. AI Proxy administrator Tokens must not be used. |
| Request Parameter Filtering | Pass scenario parameters such as device ID, time range, and fault type | Accurately pull targeted network operational data and reduce invalid requests |
| Return Field Restriction | Limit returned fields such as device ID, signal strength, fault type, and update time | Meets the field requirements of operational documents and reduces invalid data transmission |
| Interface Timeout Setting | Configure as 300-600 seconds | Adapts to pull latency of devices such as switches and wireless controllers, preventing pull failures caused by short timeouts |
| Concurrent Request Control | Configure as 5-10 concurrent requests per node | Avoids exceeding the interface request limit of network devices and prevents triggering rate limiting |
| Incremental Pull Switch | Enable incremental pull mode | Adapts to the update rhythm of operational data based on changes, reducing repeated data pulls |

## Three common misconfigurations
- Partial JSON data returned in interface responses: The received response is not closed, with a 200 status code but incomplete data. The cause is failure to configure chunked reception processing and fail to validate JSON integrity of the response.
- Concurrent requests trigger interface rate limiting: Returns a 429 status code. The cause is failure to set a reasonable concurrent request threshold, exceeding the interface carrying limit of switches or wireless controllers.
- Unable to pull full operational records: The number of records returned by the interface is less than the actual generated records. The cause is failure to correctly configure pagination parameters or enable the full pull switch, only pulling data from the current page.

## How to confirm proper configuration
- Send an HTTP request, check that the response header includes `Content-Type: application/json`, confirm that the authentication configuration is effective.
- Compare the fields returned by the interface with the restricted configured fields, confirm that only specified operational related data is returned.
- Send multiple concurrent requests, check that no rate limiting errors are triggered, confirm that the concurrent threshold configuration is reasonable.
- Pull data for a specified time range, compare with local operational records, confirm that the data update time matches the actual change time.
