# Release Notes and Operations Report Summary for Internal Network and WiFi Operations: Database and Operations

## What the data for this category looks like
Core data for internal network and WiFi operations comes from switch consoles, wireless controllers, monitoring systems, and user trouble report channels. Update frequency is daily or after each network change. Daily produced documents include network topology diagrams, change tickets, fault records, and wireless coverage inspection forms. Data fields include device MAC addresses, port numbers, SSID names, fault types, inspection times, change content, and more. Some fields have fixed format constraints. For example, port numbers use integer ranges, and inspection times follow standard timestamp formats.

## What constraints these characteristics impose on the database and operations link
Multi-source heterogeneous data input requires the database to support both structured storage and unstructured log parsing. This adapts to different types of operations documents. High-frequency daily updates and change-triggered updates require database connection pool configurations to match peak concurrent access. This avoids connection exhaustion. Diverse field formats require predefined table structures and data validation rules. This reduces data import exceptions. Network outages directly impact office business, so database deployments must include high-availability mechanisms. These ensure real-time availability of operations data.

The following configurations follow the standard specifications for FastGPT v4.17.0.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://admin:securepass@db-host:27017/fastgpt?replicaSet=rs0` | Adapts to replica set storage requirements for internal network device logs, supports automatic reconnection after primary node failover |
| `PG_URL` | `postgresql://it-admin:dbpass@pg-host:5432/it_ops?sslmode=disable` | Stores structured operations data such as change tickets and fault records, supports complex conditional queries |
| `DB_MAX_LINK` | `20–30` | Matches the concurrent reporting frequency of internal network devices, avoids connection pool resource exhaustion |
| `REDIS_URL` | `redis://:redispass@redis-host:6379/0` | Caches high-frequency query wireless coverage inspection data, reduces database access load |

## Three common configuration errors
- Symptom: Database connection count continues to rise, and disk read/write utilization is too high. Cause: The `DB_MAX_LINK` parameter is not adjusted based on the concurrent reporting volume of internal network devices, leading to unlimited expansion of the connection pool and excessive disk read/write operations.
- Symptom: Database configuration conflicts occur during deployment, and initialization cannot be completed. Cause: Storage configurations for structured operations data and vector indexes are mixed, and the `PG_URL` and vector database connection parameters are not distinguished.
- Symptom: Connections cannot automatically recover after a MongoDB replica set primary node failover. Cause: The correct replica set parameter is not configured in `MONGODB_URI`, leading to inability to automatically reconnect after disconnection.

## How to verify a successful configuration
- View the database connection monitoring panel, confirm that the current active connection count falls within the range specified by `DB_MAX_LINK`, with no continuous overflow.
- Execute a query operation for structured operations data, verify that the database corresponding to `PG_URL` can normally read change tickets, fault records, and other content.
- Simulate a MongoDB primary node failover scenario, verify that connections can automatically recover with no disconnection error logs.
- Check the Redis cached wireless coverage inspection data, confirm that high-frequency query requests hit the cache and reduce database access pressure.
