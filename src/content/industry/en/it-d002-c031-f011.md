# Release Notes and Operation Report Summary for Creator Onboarding and Verification: Database and Operations

## What the data for this category looks like
Common data sources include onboarding applications submitted via creator dashboards, identity qualification materials, account history records, and synchronized data from enterprise credit information platforms and partner contract systems. Update cadence falls into two categories: daily single audit records are updated per application, and bulk operation reports are generated daily. Document structure includes structured fields for audit status, creator ID, contract number, plus unstructured materials such as qualification scan copies and partner agreement attachments. Most fields focus on identity credibility and access permissions. No settlement-related amount fields are included. Data relationships must cover four core entities: creators, qualifications, audits, and contracts.

## Constraints on database and operations processes
Access to multi-source heterogeneous data requires compatibility with both structured and unstructured storage. Thus, both relational and document databases must be configured. Mixed update cadences—per-application updates and daily bulk updates—require database support for both on-demand and scheduled synchronization to avoid resource waste. Qualification verification and account risk judgment are the most time-consuming steps. In high-concurrency query scenarios, connection limits and timeout settings must be enforced to prevent service avalanches. Data errors can lead to outcomes such as false certifications and partner disputes. Therefore, data verification and backup mechanisms must be configured. This category must be separated from adjacent categories such as creator incentive settlements, so no settlement-related fields or transaction logic need to be designed.

## Configuration settings
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Use a replica set connection string with read-write separation configuration, set read-to-write node ratio to `1:3` | Adapt to unstructured storage of multi-source qualification materials and high-frequency queries, improve concurrent processing capability |
| `PG_URL` | Configure an SSL-encrypted connection string pointing to an independent structured data storage repository | Ensure transaction consistency and security for structured data such as audit records and contract information |
| `DB_MAX_LINK` | Set to `100–150` | Match the concurrent audit request limit for a single instance, avoid service lag caused by connection pool exhaustion |
| `REDIS_URL` | Configure memory limit to `1024 MB`, set cache expiration time to `24 hours` | Cache high-frequency queries of enterprise credit information and audit status, reduce repeated API call latency |

## Three common configuration mistakes
- Symptom: The exported CSV operation report only contains the index field, with no content fields. Cause: The database query did not associate the qualification material storage table, only pulled the index field of the audit record.
- Symptom: In Docker deployment environments, the qualification verification step logs a slow operation xxxxms error. Cause: The `DB_MAX_LINK` configuration value is lower than the actual concurrent request count, connection pool exhaustion causes query wait timeouts.
- Symptom: Qualification verification results are empty for some onboarding applications. Cause: `REDIS_URL` does not have a reasonable expiration time configured, high-frequency temporary cached data is automatically cleaned up, leading to subsequent queries failing to retrieve cached data.

## How to verify successful configuration
- Run the connection test script corresponding to `MONGODB_URI` to verify that the load balancing function of the replica set read-write separation nodes operates normally.
- Check the database logs corresponding to `PG_URL` to confirm that the transaction commit success rate for new and modified audit record operations remains stable.
- Run the bulk operation report export script to verify that the returned results include all required fields such as creator ID, qualification status, and contract number.
- Observe the memory usage monitoring for `REDIS_URL` to confirm that the cache data expiration policy matches the daily update cadence requirements.

The values provided are common starting points and should be measured against the reader's own samples.
