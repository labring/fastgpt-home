# Release Notes and Operations Report Summary for Unit and Component Testing: Context and Token

## What data this category includes
Teams source data for this category from code repositories, test framework reports, requirement specifications, and interface definitions. Update frequency is daily or per commit. Daily deliverables include test cases, coverage reports, Mock instructions, and defect tickets. Data fields cover test case numbers, execution results, coverage values, defect severity levels, and associated code paths. Units include test case counts, lines of code, defect severity identifiers, and similar metrics. Data structures vary slightly based on the test framework and specifications used by the team.

## How these characteristics create constraints for context and token handling
Test data updates frequently per commit or daily. The context must dynamically pull the latest test document fragments to avoid referencing expired test cases or coverage reports. Test data fields have tight associations: one defect ticket can link to multiple test cases and code paths. The context must accurately match associated information to prevent redundant data from consuming token quotas. Individual test documents are small, but total volume grows with commit count. Limit the context’s total token quota to avoid loading excess data and causing call timeouts. Test data also has diverse field types. The context must support filtering by specific fields to ensure recalled content aligns with the current testing task.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the total volume of daily updated test reports and case data for unit and component testing, avoids token overflow, based on the context processing logic of FastGPT v4.17.0 |
| `quoteMaxToken` | 1500–2000 token | Limits the length of a single referenced test document fragment, prevents excessive token quota consumption by a single defect ticket or coverage report |
| Context refresh interval | Per commit or 1 day | Matches the update frequency of test data, ensures the latest test cases and coverage reports load during calls |
| Recall matching threshold | 0.75–0.85 | Accurately filters associated code paths, test cases, and defect information, reduces redundant data loading |

## Three common configuration mistakes
- When calling the workflow API, the returned context field is empty. The interface response’s context field contains no test case or coverage report content. The cause is failure to bind the test data source in the workflow, so no associated test documents are pulled.
- When querying credit consumption, a 403 status code returns. The interface provides a permission denied prompt. The cause is the used token lacks the permission scope to access credit documents, so consumption details cannot be retrieved.
- Test report recall results have an abnormal count. The number of returned test cases is far fewer than the actual submitted number. The cause is incorrect recall matching threshold configuration, which filters out eligible test data.

## How to confirm correct configuration
- Initiate a context call for test data, verify the returned context field includes target content such as test cases and coverage reports.
- Access the FastGPT configuration interface, confirm the values of `maxContext` and `quoteMaxToken` match the preset configuration.
- Submit new test code, check if the context automatically updates to the latest test document data.
- Call the associated interface, confirm the returned status code and prompt meet expectations, with no abnormal errors.

The values provided are common starting points and should be measured against the reader’s own samples.
