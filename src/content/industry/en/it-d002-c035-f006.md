# Release Notes and Operations Report Summary for Unit Testing and Component Testing: Scheduled Tasks and Automation

## What the data for this category looks like
This category’s data comes primarily from code repositories, coverage reports generated by test frameworks, requirement specification documents, and interface definition files. Daily output documents include standardized test cases, coverage statistics reports, Mock interface descriptions, and defect tracking tickets. Data updates occur daily or after each code commit. Test cases must link to corresponding requirement IDs and interface paths. Coverage reports include quantitative metrics such as line coverage and branch coverage. Defect tickets must record reproduction steps and repair status.

## What constraints these characteristics impose on the scheduled tasks and automation link
Data sources rely on code repositories and test framework outputs. Scheduled tasks must support two modes: code commit triggering or fixed-cycle pulling. This avoids repeatedly processing unchanged test data. Data updates happen daily or after a single commit. Task trigger intervals must match this rhythm to prevent missing the latest test results. Standardized test documents and defect tickets require the automated summary process to check required field completeness. Examples include the requirement ID linked to test cases and the reproduction steps on defect tickets. Different test frameworks use varying report formats. Format conversion rules must be configured to unify the summary data structure.

## Configuration Settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| Task trigger mode | Code commit trigger + daily full verification | Matches the data update rhythm of post-commit or daily updates, balancing real-time performance and completeness |
| Trigger interval | 300–600 seconds | Adapts to the test result generation cycle after a single commit, avoiding frequent triggers that consume resources |
| Data pull scope | Test reports and defect tickets from the past 7 days | Covers test data within a regular release cycle, avoiding pulling excessive historical data |
| Field verification rules | Verify the requirement ID associated with test cases and the reproduction steps of defect tickets | Complies with the standardized field requirements of documents in this category, ensuring the availability of summary data |
| Report format adaptation | Automatically identify coverage reports in Jest and Pytest formats | Adapts to the output formats of mainstream test frameworks, compatible with test tools used by different R&D teams |
| Failure retry count | 3 times, 60-second interval | Addresses temporary interface call failures or report generation delays, ensuring the stability of the summary process |

## Three Common Mistakes
- After triggering an upgrade command, the `POST /api/admin/initv4818 404` error occurs. The root cause is that the scheduled task fails to correctly load the initialization interface configuration for the corresponding version, leading to the interface path not being registered.
- After adding a custom plugin in a workflow, no input or output parameters are displayed. The root cause is that the automated summary process fails to synchronously pull the plugin’s metadata configuration, resulting in parameter definitions not being included.
- Older documents in the team’s cloud historical versions lack the `tmbId` field. The root cause is that the scheduled task does not handle the field completion logic for old version data, failing to automatically populate the missing associated fields.

## How to Confirm the Configuration Is Complete
- Submit a test code, then check if the scheduled task generates the corresponding test summary report within 10 minutes. This confirms the trigger logic is working.
- Manually create a test case with missing required fields. Verify if the automated process triggers an alert or skips invalid data.
- View historical version data in the corresponding MongoDB collection. Confirm that older documents have automatically populated the `tmbId` field.
- Simulate a scenario with an abnormal test framework report format. Verify that the configured format adaptation rules can correctly parse and convert the data.
