# Release Notes and Operations Report Summary for Change Management and Release Windows: Database and Operations

## What data for this category looks like
Data for this category comes from four types of systems: change management systems, CI pipelines, monitoring data, and business calendars. Update frequency is weekly or when a single change is triggered. Core daily documents include four types: change requests, risk assessments, launch window plans, and rollback plans. Data fields include change unique ID, application time, risk level, effective window period, rollback trigger conditions, and more. Field types cover strings, timestamps, and enumeration values. There are no unified statistical values; data is generated only in correspondence with change process nodes.

## What constraints these characteristics impose on the database and operations link
Multi-source data access requires databases to support cross-system data writing and format compatibility, to avoid data format conflicts across different systems. Non-fixed update frequency requires databases to use on-demand writing strategies, adapting to real-time writing needs for sudden changes without relying on fixed batch synchronization tasks. Multi-type document structures require databases to create indexes for high-frequency query fields, reducing latency for operations such as risk rating and window queries during change processes. Change operations are associated with production environment risks, requiring databases to provide transaction consistency guarantees, preventing change process interruptions or data inconsistencies caused by failed data writes. Additionally, data must correspond one-to-one with business documents, facilitating subsequent audits and quick queries of rollback plans.

## How to configure settings
The following configurations apply to the change management and release window module of FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---|---|--- |
| `MONGODB_URI` | `mongodb://change_user:secure_pass@db-host:27017/change_ops_db` | Stores unstructured documents such as change requests and risk assessments, matching MongoDB's document storage capabilities |
| `PG_URL` | `postgresql://pg_user:pg_pass@pg-host:5432/change_monitor` | Stores strongly associated relational data such as monitoring data and business calendars, ensuring data consistency |
| `DB_MAX_LINK` | `20–30 connections` | Adapts to the concurrency of change operations, preventing request queuing caused by exhausted connection pools |
| `REDIS_URL` | `redis://redis_pass@redis-host:6379/1` | Caches frequently accessed launch window plan data, reducing query pressure on relational databases |

## Three common configuration errors
- Symptom: Cannot distinguish source data from the change management system and CI pipelines in MongoDB logs. Cause: No source identification field is included when writing data, and no corresponding index is configured to differentiate data from different systems.
- Symptom: Database connection plugins experience timeouts, with execution time far exceeding older versions. Cause: The `DB_MAX_LINK` configuration value is too low. The connection pool cannot support concurrent requests from current change operations, leading to request queuing.
- Symptom: No matching results are returned when querying rollback plan data. Cause: No database index is created using the change unique ID. A full table scan is performed, resulting in excessive query latency and failure to return valid data.

## How to confirm configurations are properly applied
- Connect to the MongoDB client, run a filtered query that includes the source field, and verify that change data from different systems is stored correctly and differentiated.
- Review the database connection pool monitoring dashboard, confirm that the current active connection count is lower than the `DB_MAX_LINK` configuration value.
- Submit a simulated change request, verify that data is correctly written to the specified database collection and corresponding fields.
- Access the launch window plan data interface, verify that cache hit rates meet expected standards, with no frequent penetration to the underlying database.
