# Release Notes and Operational Report Summary for Security Incident Response: Scheduled Tasks and Automation

## What this category's data looks like
This category's data primarily comes from SIEM, EDR, firewall logs, and host images. Update frequency is real-time or event-triggered. Daily produced documents include incident response reports, forensic records, disposal plans, and notification materials. Core fields cover unique incident identifiers, attack path details, disposal execution nodes, and evidence chain association numbers. Units are mostly event counts, timestamps, byte counts, and similar metrics. There is no unified fixed batch statistics unit. Corresponding fields are matched for each individual document.

## What constraints these characteristics impose on scheduled tasks and automation
Data sources for this category are scattered, and update frequencies are inconsistent. The category supports both real-time push and event-triggered updates. Scheduled tasks must support both trigger modes, and cannot rely solely on fixed time interval execution.
Unlike security monitoring and SOC on-duty operations, this category requires disposal and forensic work only after an incident is confirmed. Scheduled tasks must prioritize processing confirmed incident data.
Daily documents have diverse structures and no unified field standards. During automated summarization, formatting and field mapping logic for different documents such as incident response reports and forensic records must be adapted to avoid missing or misaligned fields.
Core links such as attack path restoration and evidence chain organization rely on multi-source data stitching. Automated summarization must prioritize associating core fields to avoid missing critical information.
Real-time generated logs and image data may create performance pressure from batch processing. The processing scale of a single task must be limited to prevent system resource exhaustion.
Additionally, errors in incident response documents can cause serious consequences. A task failure must trigger an alert mechanism, rather than only silently retrying.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Trigger Mode | Real-time event trigger + 15-minute rescan | Adapt to the real-time/event-based update rhythm of this category, while covering missed offline incidents |
| Single Processing Limit | Process up to 100 logs/image files per run | Avoid excessive system resource usage from batch processing, prevent business impact |
| Field Mapping Rules | Preset mapping templates by document type | Adapt to field differences across documents such as incident response reports and forensic records |
| Failure Retry Count | Retry 2 times, 60-second interval | Balance task success rate and resource usage, avoid ineffective retries |
| Alert Trigger Threshold | 2 consecutive task failures | Notify relevant personnel in a timely manner to handle anomalies, prevent disposal delays |
| Result Storage Path | /fastgpt/secure_response/report/ | Store security documents by category for subsequent traceability and compliance checks |

## Three Common Mistakes
- Symptom: When calling external SIEM/EDR interfaces, the request header automatically carries a Bearer token, returning a 401 authentication failure. Cause: The automatic token supplement function for FastGPT API calls was not disabled, which forcibly adds a preset token to all API requests.
- Symptom: The summarized incident response report has messy formatting, with misaligned or redundant fields. Cause: No field mapping rules for the corresponding document type were configured, and all original document content was directly concatenated.
- Symptom: Only a small number of documents are generated after the scheduled task runs, failing to cover all pending incidents. Cause: The single processing limit was set too low, or the trigger mode only selected real-time events, missing offline generated log data.

## How to Confirm Configuration is Complete
- Manually trigger a test task using FastGPT v4.17.0, check whether the task log displays the correct trigger mode and processing quantity, and verify that the trigger mode includes real-time events and scheduled rescan.
- Check the generated summary documents to confirm that field mapping conforms to the preset template, with no obvious misalignment or missing fields.
- Simulate an interface authentication failure to check whether a preset alert notification is triggered, verifying that the alert rule is active.
- View the generated files in the task storage path to confirm that documents are stored by category in accordance with preset rules.
