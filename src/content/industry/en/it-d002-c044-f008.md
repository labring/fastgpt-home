# Release Notes and Operation Report Summary for Security Product Rule Operations: Workflow Orchestration

This page is written based on FastGPT v4.17.0.

## What the data for this category looks like
Data for this category primarily comes from WAF, IDS, firewalls, and threat intelligence platforms. Update cadence follows either daily summary or real-time trigger via protection events. Daily output documents include rule change tickets, intercept logs, false positive analysis reports, and policy rollback records. Data fields include rule unique identifier, change execution time, single rule intercept volume, false positive trigger frequency, and rollback trigger conditions. No additional statistical percentage metrics are included.

## How these characteristics constrain workflow orchestration
Multi-source data access requires workflows to support cross-platform API pulls for logs and intelligence from different protection devices. Real-time update triggers require nodes to support event triggering, to align with the update cadence tied to protection events. Field differences across multiple document types require `variables` to support custom field mapping, to avoid data format conflicts. Single execution must handle full-link data for a single rule, requiring no parameter loss between workflow nodes. A validation step must be reserved to block abnormal data. This prevents incorrect rule deployment from blocking normal business or missing attacks.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Preset 12 custom fields by protection rule type, including rule ID, intercept volume, false positive rate | Matches the fixed field structure of documents for this category, reduces runtime field mapping time |
| Trigger Mode | Event-triggered, with full daily resync at midnight | Supports both real-time event updates and daily full summary requirements |
| `nodeId` | Assign unique identifiers to log pull, false positive analysis, and report generation nodes | Facilitates locating specific workflow execution failure points |
| Retry Count | 3 times, 60-second interval | Addresses temporary API call failures caused by network fluctuations |
| Result Storage | Classified storage by rule dimension, retained for 180 days | Meets document retention needs for policy rollback and historical auditing |

## Three common configuration errors
- An exported workflow cannot be imported on other instances. This occurs when global sharing configuration for `variables` is not enabled. The export package will not include custom field mapping rules.
- Global variables fail to load into the workflow after an API call. This occurs when the API access link is not bound to the corresponding `variables` assignment node. Only node trigger parameters are configured.
- Interactive nodes show no response after execution. This occurs when the trigger condition for the interactive node corresponding to `nodeId` is not configured. No association is made with protection event trigger rules.

## How to verify correct configuration
- Manually trigger the change process for a test rule. Check if `variables` correctly loads rule ID and intercept volume data.
- Call the bound API link. Verify that global variables are correctly assigned and synced to workflow nodes.
- View workflow execution logs. Confirm that each node associated with a `nodeId` has execution records, with no failed statuses.
- Wait for the daily full resync task to complete. Check if operation report files for the corresponding date are generated in the configured storage path.

The configuration values listed above are common starting points. They should be validated using the target environment’s own test samples.
