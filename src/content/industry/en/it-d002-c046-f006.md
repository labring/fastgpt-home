# Release Notes and Operation Report Summary for Security Baseline Checks: Scheduled Tasks and Automation

## What data this category includes
Data for this category comes from server basic configurations, middleware operating parameters, security device access policies, and dedicated baseline check tools.
Daily output documents include standardized baseline checklists, single-check configuration records, rectification suggestion sheets, and exception approval sheets.
Data updates occur monthly or quarterly.
Core fields include baseline item unique identifier, current configuration value, check result, rectification status, approver, and approval time. No additional statistical percentage fields are included.
This category differs from vulnerability scanning services. It focuses on whether configurations meet organizational security baselines, with a core focus on configuration compliance checks.

## Constraints imposed by these characteristics on scheduled tasks and automation
Since data sources cover multiple heterogeneous systems, scheduled tasks must support cross-source configuration data pulling to avoid manual import errors.
The monthly or quarterly update cycle means task execution frequency should not be too high. Excessive frequency will consume excessive operational resources.
Standardized document fields require automated summary tools to strictly follow field mapping rules. This ensures uniform formatting for output operation reports.
Time-consuming steps such as configuration verification, exception reason confirmation, and rectification result review must use automated scripts to pull associated data from exception approval sheets. This reduces manual intervention steps.
The system must also support alert reminders for unassociated data. This prevents risk accumulation caused by missed exception items.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| Task execution cycle | Once per month, or once per quarter | Matches the monthly or quarterly data update frequency, avoids unnecessary resource consumption |
| Data source pull timeout threshold | 300-600 seconds | Adapts to pull durations for multi-source heterogeneous data, prevents single tasks from blocking due to network fluctuations |
| Exception data automatic matching rule | Calibrated based on actual testing | Adapts to field differences in exception approval sheets across organizations, avoids mismatches or omissions |
| Report generation format | Standardized PDF or structured Excel | Matches common formats for daily operation and maintenance documents, simplifies archiving and review |
| Failure retry count | 2 times | Addresses temporary network fluctuations or temporary data source unavailability, reduces task interruptions |
| Task alert trigger condition | Two consecutive execution failures | Notifies operation and maintenance personnel in a timely manner to handle exceptions, prevents problem accumulation |

## Three Common Misconfiguration Issues
- Phenomenon: Configuration item fields are empty in operation reports generated after scheduled task execution. Cause: Data source and report field mapping rules are not correctly configured. Pulled data cannot match preset document fields.
- Phenomenon: Tasks terminate directly after execution timeout, without triggering the retry mechanism. Cause: Failure retry count is not set, or threshold is set too low. This cannot handle temporary network fluctuations or data source outages.
- Phenomenon: A large number of unassociated exception approval sheet data appears after monthly task execution. This eventually leads to long-term non-rectification of weak configurations. Cause: Exception data automatic matching rules are not enabled. Manually confirmed exception items are not automatically included in summary reports. This creates audit failure risks.

## How to Verify Proper Configuration
- Confirm that the currently used FastGPT version is v4.17.0. This ensures the scheduled task module functions match the documentation.
- Manually trigger a test task. Verify that pulled configuration data matches actual configurations on servers, middleware, or security devices.
- Check task execution logs. Confirm no error messages appear in data source pulling, field mapping, or report generation steps.
- Generate a test report. Check that report fields fully match the format of preset baseline checklists and rectification suggestion sheets.
- Simulate a temporary data source outage scenario. Confirm the task triggers the retry mechanism and executes normally after data source recovery.
