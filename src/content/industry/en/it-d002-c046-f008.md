# Release Notes and Operations Report Summary for Security Baseline Checks: Workflow Orchestration

## What this type of data looks like
Security baseline check data originates from server configurations, middleware configurations, security device policies, and dedicated baseline tools. Daily produced documents include baseline checklists, configuration verification records, rectification suggestions, and exception approval forms. Core fields include baseline item ID, compliance status, rectification measures, exception reason, and approval status. Data update frequency is monthly or quarterly. A single verification record contains check results for dozens to hundreds of configuration items.

## What constraints do these characteristics impose on the workflow orchestration link
As data sources are scattered, the workflow must be configured with multiple nodes to pull configuration data from different sources. Since data updates occur monthly or quarterly, the workflow must support scheduled trigger or on-demand trigger scheduling configurations. Processing multiple types of documents requires distinguishing input and output formats such as baseline verification results and approval forms. The most time-consuming steps of configuration item verification and exception reason confirmation require embedding manual review nodes and approval flow logic. Failure alert nodes must also be configured to prevent long-term retention of weak configurations that could lead to audit failures or increased intrusion risks.

## How to configure
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | `{"baselineResult": "${nodeId:scan_baseline}", "approvalFlow": "${nodeId:approval_node}"}` | Bind output data from baseline scan nodes and approval nodes to enable cross-node variable passing |
| HTTP request timeout | 600 seconds | Baseline data pull involves configuration queries across multiple devices and middleware, resulting in longer single request durations |
| JSONPath extraction rule | `$..complianceStatus, $..exceptionReason` | Accurately extract compliance status and exception reason fields for downstream node comparison and review |
| Workflow trigger timing | 00:00 on the 1st of every month | Aligns with the monthly baseline data update frequency to ensure data timeliness |
| Failure alert configuration | Push notification after node run failure | Notify operations personnel promptly to handle configuration verification anomalies |

## Three common configuration errors
- Phenomenon: After the HTTP request node returns results, the compliance status field cannot be extracted as a downstream variable. Cause: Incorrect JSONPath extraction rule configuration, or variable output permission not enabled.
- Phenomenon: Baseline data is empty after workflow runs. Cause: Failed to bind upstream node output data via the `variables` parameter, or incorrect `nodeId` configuration caused variable reference failure.
- Phenomenon: Workflow startup verification fails. Troubleshooting: In FastGPT v4.17.0 and later versions, check if `AIPROXY_API_ENDPOINT` (root address of the AI Proxy service, do not append /v1 or other paths, do not configure as a single model address such as VLLM/Ollama/Xinference) and `AIPROXY_API_TOKEN` (consistent with the AI Proxy server configuration, cannot be empty, do not use non-administrator token content such as model vendor keys or application API Keys) environment variables are configured on the App/Admin server side, and the above variables are not configured in non-server-side environment variable locations such as workflow global variables, application API request headers, or the general model management page.

## How to confirm the configuration is complete
- Run a test workflow, and check if the output panel includes complete fields of baseline check results and approval records
- Check the workflow trigger logs to confirm that scheduled or manual trigger requests are submitted normally
- Simulate a configuration exception scenario to verify that failure alerts are pushed to the specified channel as configured
- Verify the HTTP request timeout duration to confirm it matches the actual time taken for baseline data pull in the current environment
