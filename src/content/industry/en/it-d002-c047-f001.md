# Release Notes and Operations Report Summary for Security Vulnerability Disclosure Handling: HTTP Interfaces and External Systems

## What this category of data looks like
Data for this category is generated around the full lifecycle of a project’s own security vulnerabilities. Sources include private vulnerability reports, code repositories, CVE numbering bodies, and official release channels. Daily documents include security advisories, vulnerability reports, fix patch packages, CVE application materials, and more. Each piece of data corresponds to a single independent vulnerability event, with updates triggered following the vulnerability disposal workflow. Data fields include vulnerability IDs, impact scope, patch versions, disclosure times, disposal statuses, and other similar items. Units are mostly identifier-type content such as events, version numbers, and dates.

## What constraints these characteristics impose on the HTTP interfaces and external systems link
The data characteristics of this category impose multiple constraints on the HTTP interfaces and external systems link. Since the data includes private vulnerability reports, interfaces must be configured with authentication parameters to ensure transmission security. Each single vulnerability event corresponds to an independent data update, so interfaces must support push or pull logic triggered by a single event. Documents include large files such as fix patches, so interfaces must adapt to binary file transfer formats. Data must be integrated with external systems such as CVE numbering bodies and code repositories, so interfaces must set reasonable timeout thresholds to avoid blocking of the disposal workflow, and must also ensure call traceability to meet audit requirements.

## How to configure the settings
| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| Authentication Configuration | Enable Bearer token authentication using the `Authorization` header, with tokens generated from the security response team’s dedicated secret key | Ensure transmission security for private vulnerability data, and comply with the interface specification of FastGPT v4.17.0 |
| Business Variable Population | Populate fields such as vulnerability ID, affected versions, patch versions | Meet the data transfer requirements for single independent vulnerability events |
| Response Data Extraction | Extract disposal status, patch version numbers from the `responseData` field | Facilitate status verification and synchronization logic for external system integration |
| File Upload Threshold | 1000 MB | Adapt to the typical size range of fix patch packages |
| Request Timeout | 600 seconds | Match the typical maximum time required for vulnerability impact assessment |
| Failure Retry Strategy | Retry 3 times, with a 30-second interval between retries | Prevent disruption of the disposal workflow caused by temporary network fluctuations |

## Three Common Misconfigurations
- A `permission denied` error appears, and the external interface cannot be connected. The cause is incorrect authentication parameter configuration, or the secret key permissions do not match the security response team’s access rules.
- Fix patch packages in file format cannot be transferred when calling the interface. The cause is that the upload threshold for large files is not configured, or related settings for binary data transfer are not enabled.
- No available disposal status data is returned by the interface. The cause is that the correct vulnerability event identifier is not passed via `variables`, causing the external system to fail to match the corresponding data.

## How to Confirm Proper Configuration
- Call the test interface, pass business parameters for a simulated vulnerability event, and check if the returned `responseData` field contains the expected disposal status content.
- Upload a test patch file, confirm that the interface can receive it normally and there is no error prompt about exceeding the size limit.
- Initiate a call using an invalid authentication token, confirm that the interface returns a corresponding permission error prompt.
- Simulate a temporary network interruption scenario, confirm that the interface triggers the retry logic and completes data synchronization after network connectivity is restored.
