# Release Notes and Operation Report Summary for Security Vulnerability Disclosure Handling: Workflow Orchestration

## What data for this category looks like
Data for this category comes from private vulnerability reports, code repositories, CVE numbering authorities, and public disclosure channels. Updates follow the rhythm of individual vulnerability events. Daily documents include security advisories, vulnerability reports, fix patches, and CVE application materials. Core fields include unique vulnerability identifiers, impact scope, patch versions, disclosure times, and impact assessment results. Units include version numbers, days, character counts, and more. There is no fixed batch update cycle. Updates are only triggered by vulnerability events.

## What constraints these characteristics impose on the workflow orchestration link
Because data updates are tied to individual vulnerability events, workflows must bind independent contexts to avoid cross-event data confusion. Because sensitive information such as private vulnerability reports is included, workflows must configure permission verification nodes to limit access scope. Because data from official CVE authorities is involved, workflows must add field validity verification links to ensure data format compliance. Because vulnerability impact assessment and patch preparation are the most time-consuming steps, workflows must set timeout reminders and manual approval nodes to ensure process efficiency.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Include CVE ID, vulnerability severity, patch version (3–5 characters), impact scope fields | Match standard fields of core category documents to ensure workflow nodes can read valid data |
| `nodeId` | Corresponding unique trigger node identifier for the workflow, 16–32 characters long | Ensure precise targeting of the target workflow during external calls to avoid misalignment |
| Trigger Mode | Triggered upon submission of private vulnerability reports | Match the private nature of category data sources, prioritize processing undisclosed vulnerability information |
| Timeout Setting | 72 hours | Cover the typical time range for vulnerability impact assessment and patch preparation to avoid unlimited process waiting |
| Result Verification | Verify CVE ID format, patch version existence, and field length not exceeding 1024 characters | Match the characteristics of data from CVE authorities and code repositories to ensure input data compliance |
| Permission Configuration | Only project security response team members can edit and trigger | Ensure access security of private vulnerability data, align with the sensitive nature of category data |

## Three common mistakes
- When calling the workflow, `Key is error. You need to use the app key rather than the account key` is returned. The cause is that an account key instead of an application key was used to initiate the call, resulting in interface authentication failure.
- An empty result is returned after workflow execution. The cause is that core fields were not correctly configured in the passed `variables`, causing workflow nodes to fail to read valid data.
- After upgrading to FastGPT v4.17.0, the number of global variable display items is reduced. This causes `variables` parameters configured in older versions to fail to load normally, resulting in workflow trigger exceptions.

## How to confirm proper configuration
- Initiate a simulated call, pass test data including CVE ID and vulnerability severity, verify that the workflow triggers normally and returns execution results for corresponding process nodes.
- View the `nodeId` configuration of the workflow, confirm that it fully matches the node identifier parameter passed in the external call interface.
- Attempt to access the workflow using an unauthorized account, confirm that the workflow cannot be triggered or edited, to verify that the permission configuration takes effect.
- Manually trigger the workflow and wait more than 72 hours, confirm that the system triggers a timeout reminder to verify that the timeout setting takes effect.
