# Release Notes and Operations Report Summary for Security Monitoring and SOC Duty: Scheduled Tasks and Automation

## What This Category of Data Looks Like
Data sources for this category include SIEM, EDR, NDR, and third-party threat intelligence feeds. Update cadence falls into two categories: real-time alert streams and daily summary documents. Daily produced documents include alert disposition sheets, duty logs, threat intelligence bulletins, and daily/weekly reports. Document fields include alert ID, threat level, disposition status, duty personnel, notification time, and more. Units include event count, response duration, number of bulletins, and others.

## What Constraints Do These Characteristics Impose on Scheduled Tasks and Automation
The data characteristics of this category impose multiple constraints on the scheduled tasks and automation link. Real-time alert streams require high-frequency polling but need interval controls to avoid excessive system resource usage. Daily summary tasks must trigger at fixed times to align with SOC team’s daily and weekly report production cycles. Multi-source heterogeneous data sources require scheduled tasks to have unified format adaptation capabilities. Without this, field matching failures will occur during the alert triage process. SOC duty has strict timeliness requirements. Scheduled task failures directly lead to missed real attacks or false alert accumulation, so supporting retry and alert mechanisms is necessary. Additionally, the fixed field structure of daily documents requires scheduled tasks to strictly match field rules when pulling data, to avoid data association failures.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Scheduled trigger frequency | Real-time alert tasks use `30-60 seconds`, daily summary tasks use `Daily 02:00` | Aligns with SIEM/EDR real-time push intervals and daily report generation cycles, avoids system resource overload |
| Single pull data limit | `Top 1000 alert events` | Matches the daily triage volume of SOC analysts, prevents task timeouts caused by excessive single-task data volume |
| Task failure retry count | `3 times` | Addresses network fluctuations or temporary data source unavailability scenarios, reduces missed alert risk from single failures |
| Alert filtering rules | Only pull high and medium-severity alerts | Focuses on core disposition tasks, reduces processing pressure from false alert accumulation |
| Task log retention period | `30 days` | Meets security operation audit and traceability requirements, facilitates post-incident anomaly troubleshooting |
| Result push channel | Enterprise internal IM tools, SIEM console | Aligns with SOC team’s daily work scenarios, ensures timely delivery of disposition notifications |

## Three Common Misconfigurations
-  Symptom: A scheduled task cannot be found in the management interface after configuration. Cause: The scheduled task plugin was not enabled in FastGPT v4.17.0, or the correct trigger type was not selected during configuration.
-  Symptom: A 404 error is returned for `POST /api/admin/initv4818` after running the upgrade command. Cause: The current FastGPT version does not match the access path of the corresponding initialization script, or valid administrator authentication parameters were not included when running the command.
-  Symptom: Alert data pulled on a scheduled basis has empty fields or abnormal formatting. Cause: No field mapping rules were configured between the data source and alert disposition sheets, causing pulled raw data to fail to match the preset document structure.

## How to Confirm the Configuration is Correct
-  Navigate to the FastGPT scheduled task management interface, confirm that the created task status is "Enabled".
-  Manually trigger a test task, check that the pulled data source data format matches the preset alert disposition sheet fields.
-  View the task execution logs, confirm that the most recent execution has no errors and the returned result count matches the configured pull limit.
-  Verify the result push channel, confirm that the test task output has been successfully sent to the specified receiving location.

The values provided are common starting points and should be measured against the reader's own samples.
