# Release Notes and Operations Report Summary for Security Monitoring and SOC Duty: Workflow Orchestration

## What Data for This Category Looks Like
Data sources for this category include SIEM, EDR, NDR, and threat intelligence feeds. Update cycles fall into two categories: real-time and daily. Commonly processed documents include alarm disposal tickets, duty logs, threat intelligence notifications, daily and weekly reports. Each document contains fixed fields such as unique alarm identifier, disposal status, event occurrence time, threat level, and duty personnel identifier. Data volume changes dynamically based on the number of real-time alarms.

## What Constraints These Characteristics Impose on Workflow Orchestration
Real-time updated alarm data requires workflows to support trigger-based startup to avoid resource waste from invalid polling. Format differences across multiple data sources require workflows to have built-in standardized processing nodes, unifying field structures before entering the analysis phase. Daily updated weekly and daily report data requires binding nodes triggered at fixed time periods to ensure summary timeliness. Fixed fields in alarm disposal tickets require workflows to associate the `variables` parameter to ensure accurate data mapping. The continuous operation nature of SOC duty requires workflows to support breakpoint resumption, avoiding disposal interruptions caused by single-run timeouts.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Condition | Real-time alarm push trigger, fixed daily 00:00 trigger | Matches the update cycles of real-time alarms and daily reports, compatible with FastGPT v4.17.0 trigger rules |
| Parallel Processing Limit | `2` nodes running simultaneously | Prevents third-party interface rate limiting caused by concurrent reading of multi-source data |
| `variables` Binding | Associate alarm ID, disposal status, threat level | Matches the fixed field structure of alarm disposal tickets, ensuring accurate data mapping |
| Failure Retry Rule | Retry `2 times`, interval of `30 seconds` | Addresses temporary data reading failures caused by fluctuations in SIEM and EDR interfaces |
| Workflow Invocation Method | Specify the target workflow by `nodeId` | Separates independent orchestration for alarm analysis and report summary scenarios |

## Three Common Mistakes
- Symptom: Workflow returns empty results after running, with `empty` status displayed in the interface. Cause: No binding relationship configured between `variables` and alarm fields, causing the workflow to fail to read valid data.
- Symptom: Multiple tool nodes trigger simultaneously, causing concurrent conflicts and interface errors. Cause: No serial execution rule set for tool nodes, causing multiple tools to call interfaces simultaneously and trigger rate limiting.
- Symptom: Incorrect workflow triggers when invoking a workflow. Cause: The target workflow is not accurately specified via `nodeId`, causing mixed invocation of workflows for different scenarios.

## How to Confirm the Configuration Is Correct
- Submit a test alarm, check whether the workflow automatically triggers and completes standardized processing.
- Simulate a temporary error in the SIEM interface, verify whether the workflow triggers the retry mechanism and completes data reading.
- Invoke workflows corresponding to different `nodeId` values, confirm that only the target workflow starts correctly.
- Check the workflow operation logs at the fixed daily time period, confirm that the report summary process starts and completes on schedule.
