# Summary of Release Notes and Operational Reports for Customer Activation and Tenant Initialization: HTTP Interfaces and External Systems

## What this category’s data looks like
Typical data sources for this category include CRM systems, contract order systems, identity management systems, and product backends. Update frequency is per order or once daily. Associated daily documents include activation request forms, tenant configuration sheets, administrator account lists, and delivery confirmation forms. Core fields include customer unique identifier, tenant identifier, permission configuration scope, activation status, and more. Data structure primarily uses structured forms; some scenarios require integration with non-standard external system fields. This document applies to FastGPT v4.17.0.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Multi-source data requires interfaces to support field formats and authentication rules of different systems, to prevent data mapping errors. Per-order or daily update frequency requires interfaces to support both on-demand single invocation and batch invocation modes, to adapt to requirements of different delivery scenarios. Core field validation requirements require interfaces to include basic field validity verification capabilities, to reduce manual verification time. Activation failure directly affects customer login and delivery acceptance. Interfaces must include status synchronization and exception retry mechanisms to ensure data consistency between external systems and product backends.

## How to set configurations
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| Authentication Method | Use `Authorization` header with Bearer token | Adapt to multi-tenant isolated permission verification, prevent different tenant configurations from overwriting each other |
| Incoming Variables | Include customer ID, tenant identifier, administrator account list | Match structured field requirements of daily documents, simplify data mapping process |
| Return Fields | Include activation status, error code, tenant access link | Synchronize activation results between external systems and product backends, facilitate delivery confirmation |
| Timeout Duration | 30-60 seconds | Cover normal processing time for customer information verification, prevent single request interruption |
| Retry Strategy | Retry 2 times after failure | Address temporary network fluctuations, reduce probability of activation failure |

## Three common misconfigurations
- Symptom: Different tenant configurations overwrite each other, and the tenant identifier returned by the interface does not match the request parameters. Cause: No dedicated authentication token is carried via the `Authorization` header, so the system cannot distinguish requests from different tenants.
- Symptom: Interface invocation returns activation failure with no error code. Cause: Required fields such as customer ID and tenant identifier are not included in incoming variables, so the system cannot complete customer information verification.
- Symptom: Interface request interrupts after a long period of no response. Cause: Timeout duration is set too short, failing to cover normal processing time for customer information verification.

## How to confirm configuration is complete
- Invoke the test interface, pass a valid `Authorization` token and structured incoming variables, check if the returned `responseData` includes the expected activation status field.
- Simulate requests from different tenants, verify that configurations do not overwrite each other, and ensure each tenant’s configuration takes effect independently.
- Trigger an abnormal request, check if the interface returns the corresponding error code, confirm that the verification logic operates correctly.
- View activation records in the product backend, confirm that requests from external systems are synchronized with backend data.
