# Release Notes and Operation Report Summary for Container Platform Operations: Workflow Orchestration

## What the data for this use case looks like
Daily operational data for container platform operations comes primarily from Kubernetes APIs, image registries, monitoring systems, and CI pipelines. Core documents include cluster change tickets, namespace quota tables, deployment records, and failure reports.

Cluster change tickets include fields such as change time, target namespace, and image version. Namespace quota tables record CPU and memory quotas and real-time usage. Deployment records include Pod startup status, resource usage, and restart counts. Failure reports include abnormal node IDs and recovery durations.

Data updates occur daily or after each cluster change, with no fixed bulk synchronization cycle. Fields are adjusted dynamically based on cluster scale and operational rules.

## What constraints these characteristics impose on workflow orchestration
Workflow orchestration for container platform operations must adapt to multiple dispersed data sources. Multiple nodes must be configured to pull deployment data from the Kubernetes API, version information from image registries, and failure logs from monitoring systems separately. This avoids single-node pull timeouts or permission issues.

The non-fixed data update frequency requires workflows to support flexible triggering. Workflows can be bound to CI pipeline change events, or set up as scheduled pull tasks.

The dynamic nature of daily document fields requires orchestration to bind mutable fields via `variables`, instead of using hardcoded parameters. Space must also be reserved for field expansion.

Additionally, the high-risk nature of operational tasks requires workflows to configure failure handling branches. Alarms must be triggered when resource quota adjustments fail or Pod startups fail, to prevent business interruptions.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Triggering method | Trigger by CI change events, or scheduled triggering at 00:00 daily | Aligns with the frequency of daily data updates or updates tied to cluster changes |
| Variable binding | Bind `variables` to the namespace and image version fields of cluster change tickets | Adapts to the dynamic field requirements of daily documents, avoids using hardcoded parameters |
| Data pull scope | Pull deployment records and failure reports from the last 7 days | Covers the core analysis cycle of recent operational activities, calibrated based on actual testing |
| Failure handling configuration | Configure alarms to be pushed to the monitoring system after an exception, terminate after `3 retries` | Matches the high-risk nature of operational tasks, reduces the probability of business interruptions |
| Node ID configuration | Assign a unique `nodeId` to each data pull node | Facilitates workflow debugging and log tracing, quickly locates abnormal nodes |
| Execution log caching | Retain the most recent `20` workflow execution logs | Facilitates retrospective review of operational process execution details |

## Three common configuration mistakes
1. After importing a workflow file from legacy version v4.6.7 into FastGPT v4.17.0, node configurations are lost or parameters become invalid. The symptom is that workflow nodes display as blank, or errors occur during triggering. The cause is that the legacy node parameter structure is incompatible with the new version, and migration was not completed via the built-in version compatibility conversion tool.
2. After configuring a form input component and passing variables, no user prompt is included when calling via the API release channel. The symptom is that the API response does not include the user's input content from the form. The cause is that the variable return switch was not enabled in the interaction node, causing the passed variables to not be synchronized to the request body.
3. Attempting to pass a knowledge base ID variable triggers a parameter validation error. The symptom is a "parameter invalid" prompt when the workflow starts. The cause is that the parameter type and legal value range of the knowledge base ID were not declared in the `variables` configuration, leading to parameter validation failure.

## How to confirm the configuration is complete
- Manually trigger the workflow once. Check that the latest deployment records and failure reports can be pulled from the Kubernetes API, and that the data fields match those in the cluster change tickets.
- View the workflow execution logs. Confirm that the namespace and image version fields bound via `variables` can be correctly extracted and passed to subsequent nodes.
- Simulate a failed cluster change operation. Verify that the failure handling node can normally push alarms to the monitoring system.
- Call the API to trigger the workflow and pass form input variables. Check that the passed variable parameters are included in the API request body.
