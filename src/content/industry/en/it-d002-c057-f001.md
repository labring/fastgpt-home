# Release Notes and Operational Report Summary for Ticket Acceptance and Issue Tiering: HTTP Interfaces and External Systems

## What the data for this category looks like
Data for this category comes from ticketing systems, chat logs, product logs, and customer contract SLAs, with an update frequency of daily or real-time. Daily documents include customer tickets, issue tiering tables, processing records, and service reports. Core fields include unique ticket identifiers, issue classification tags, tiering levels, processing statuses, response time limit requirements, and assigned responsibility team information. All data is generated around the full process of customer feedback issue acceptance and tiering.

## What constraints these characteristics impose on HTTP interfaces and external systems
Dispersed data sources and varying update rhythms require HTTP interfaces to support pulling or pushing multi-source data, and to adapt to authentication and data format specifications of different systems. The real-time requirements for ticket and tiering data mean the interface must be configured with reasonable timeout thresholds to avoid process interruptions caused by upstream system delays. Fields include structured information such as tiering levels and responsibility teams, requiring the interface transmission format to support basic field validation to ensure accurate circulation of tiering data. SLA-related data must strictly match time limit requirements, and the interface must record request and response times to facilitate subsequent aggregation and analysis of operational reports.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer format carrying the application API Key | Used for authentication when external systems call FastGPT interfaces, conforming to general HTTP interface authentication specifications |
| `variables` | Pass business parameters such as ticket ID, issue tiering level, and responsibility team | Used to pass core business data for ticket acceptance to the interface workflow, enabling data linkage |
| `responseData` | Structured format including ticket status, tiering results, and processing duration | Used to standardize output of aggregated data required for operational reports, facilitating subsequent statistical analysis |
| `AIPROXY_API_ENDPOINT` (AI Proxy service root address environment variable) | `http://aiproxy:3000` or the actual root address after deployment | Meets the mandatory environment variable requirements starting from FastGPT v4.17.0, do not append /v1 or other path suffixes, this is not a single-model service address |
| `AIPROXY_API_TOKEN` (AI Proxy administrator Token environment variable) | Non-empty string consistent with the AI Proxy server configuration | Mandatory environment variable for the App/Admin server, used for service startup verification, not to be used for authentication of external calls to the application API |
| Request timeout duration | 600 seconds | Adapts to the real-time requirements of ticket data pulling, avoiding process interruptions caused by upstream system delays |

## Three common mistakes
- Symptom: An error indicating message receiving address verification failure is prompted when calling an external interface, or ticket push data cannot be received normally. Troubleshooting items: Check whether the interface address has public network access capabilities, or whether the SSL certificate verification rules are correctly configured.
- Symptom: The interface returns empty fields or abnormal formats, making it impossible to generate operational reports that meet requirements. Troubleshooting items: Check whether the correct business fields are passed via the `variables` parameter, or whether the structured output format of `responseData` is configured as required.
- Symptom: The App/Admin service fails to start, prompting that the AI Proxy configuration is missing. Troubleshooting items: Check whether the AI Proxy environment variables are filled in the application API request header or workflow global variables, or whether the corresponding mandatory environment variables are not configured during the App/Admin server deployment phase.

## How to confirm the configuration is complete
- Check the App/Admin service startup logs to confirm there are no error messages about missing mandatory AI Proxy environment variables or format errors.
- Initiate a test HTTP request, passing preset ticket business parameters, and verify whether the fields returned by `responseData` match the structure required for operational reports.
- Verify the AI Proxy environment variable configuration, ensure that `AIPROXY_API_ENDPOINT` does not have additional path suffixes appended, and that `AIPROXY_API_TOKEN` is completely consistent with the configuration on the AI Proxy server.
- Simulate a ticket data push or pull action, confirm that the interface can normally receive and process business data without abnormal errors.
