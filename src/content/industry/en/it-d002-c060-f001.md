# Release Notes and Operation Report Summary for Ad Account Opening Audit: HTTP Interfaces and External Systems

## What this category of data looks like
This category of data originates from advertising platform backends, the National Enterprise Credit Information Publicity System, customer-submitted account opening application materials, and industry access rules. Daily associated documents include account opening application forms, scanned business licenses, matching industry qualification certificates, and account opening audit record ledgers. Data updates trigger once per individual account opening application. Daily operation data is summarized on a daily basis. Data fields include the main body’s unified social credit code, industry category, audit status, correction attempts, audit completion time, and more. There are no fixed unified unit bindings. Field formats adjust dynamically based on submitted materials and audit stages.

## Constraints imposed by these characteristics on the HTTP Interfaces and External Systems link
The characteristics of this category of data create multi-dimensional constraints for interface configuration. First, data sources are scattered and require cross-system retrieval. Interfaces must support permission configuration for multi-source data pulling to prevent unauthorized access to different data sources. Second, update triggers have no fixed cycle. Interfaces must support on-demand calls to meet the real-time requirements of individual account openings. Third, daily document formats are inconsistent. Interfaces must support multiple types of file uploads and structured field parsing to meet submission requirements for different materials such as business licenses and industry qualifications. Fourth, the most time-consuming steps of main body qualification verification and industry access judgment extend processing duration. Interfaces must reserve sufficient response time to avoid process interruptions caused by timeouts.

## Configuration Settings
This configuration applies to FastGPT v4.17.0, with the following details:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Interface authentication method | Use Bearer Token authentication, with the key securely stored in environment variables | Complies with HTTP interface security standards, avoids risks of hard-coded keys |
| Request parameter template | Include three required fields: main body information, industry category, and material identifier | Aligns with the core verification logic of account opening audits, reduces invalid calls |
| Return field configuration | Only return three core fields: audit status, correction instructions, and update time | Streamlines returned data, reduces parsing complexity for external systems |
| Timeout duration | 600 seconds | Covers processing duration of the most time-consuming steps including qualification verification and rule judgment |
| Retry count | 3 times | Addresses interface call failures caused by temporary network fluctuations |
| Callback URL | Fill in the interface address of the external system that receives audit results | Enables real-time synchronization of audit status, avoids data lag |

## Three Common Configuration Mistakes
- Symptom: 401 Unauthorized error returned after calling the interface. Cause: Authentication parameters are not configured correctly, or the key has expired and become invalid.
- Symptom: Interface response time far exceeds expected test durations, reaching over 600 seconds. Cause: A reasonable timeout duration is not set, or the asynchronous callback mechanism is not enabled. Synchronous waiting for audit results causes blocking.
- Symptom: Core business fields returned by the interface are empty. Cause: Correct return field rules are not configured, or the audit process has not completed, so no valid data is returned.

## How to Confirm Configuration is Complete
- Call the interface and check the returned HTTP status code to confirm that the 200 status code is returned normally.
- Check whether the external system can receive synchronized callback data of audit status, to confirm that the callback URL is configured correctly.
- Compare the account opening audit results submitted on the interface with the business fields returned by the interface, to confirm data consistency.
- Simulate a temporary network fluctuation scenario to verify whether the interface retry mechanism triggers normally.
