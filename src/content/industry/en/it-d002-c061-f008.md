# Release Notes and Operation Report Summary for Performance Testing and Capacity Evaluation: Workflow Orchestration

## What the data for this category looks like
Data for the performance testing and capacity evaluation category comes primarily from pressure testing platforms, APM monitoring systems, database slow logs, and production traffic baselines. Regularly produced documents include pressure testing plans, capacity evaluation reports, pressure testing data records, and optimization suggestion sheets.
Data update frequency is monthly, or after each major version iteration.
Data fields include pressure testing throughput, average response latency, peak memory usage, and concurrent connection count. These correspond to units of requests/second, milliseconds, GB, and count, respectively.

## What constraints these characteristics impose on workflow orchestration
Data sources for this category are scattered, update rhythms are inconsistent, and document structures are fixed. These factors create multiple constraints for workflow orchestration.
First, multi-data source docking requires using `variables` to uniformly pass pressure testing batch identifiers, to avoid data mismatches across nodes.
Second, the monthly or major version update rhythm requires workflows to support on-demand execution triggering, while retaining historical configuration snapshots to be compatible with different report format versions.
Third, fixed document structures require workflows to preset field mapping rules, to automatically fill pressure testing throughput, latency, and other data into corresponding document positions.
Fourth, the potential for severe failure consequences requires workflows to bind a failure alert node via `nodeId`, to trigger notifications when a node executes abnormally.

## How to set the configuration
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` configuration | Bind core parameters such as pressure testing batch ID and average response latency threshold, with a value range of 3 to 6 core fields | Uniformly transfer data across nodes to avoid data mismatches |
| Data source node timeout | 600 seconds | Pressure testing data pulling usually takes a long period, to avoid process interruption due to timeout |
| Document field mapping rules | Match preset field correspondences from pressure testing plans and report templates | Match the fixed document structure of this category to automatically fill data |
| Failure retry count | 2 times | Address call failures caused by temporary fluctuations in pressure testing platforms |
| `nodeId` bound alert node | Bind the failure alert node to pressure testing data pulling and report generation nodes | Trigger notifications promptly to avoid impacting subsequent processes |
| Context transfer configuration | Retain the most recent 1 workflow execution context | Comply with context dependency requirements of some nodes |

## Three common mistakes
- Phenomenon: Global variables are not updated after tool calls, and subsequent nodes read initial old values. Cause: Variable update configuration is not enabled in the tool call node, or fields bound via `variables` are not correctly mapped to tool return values.
- Phenomenon: Database connection nodes return an Access denied error. Cause: Database connection account and password parameters are not correctly configured, or the database permission list does not include the access address of the server hosting the workflow.
- Phenomenon: Context data cannot be obtained when calling the workflow API, even if context settings are enabled for the workflow. Cause: The context session identifier bound via `variables` is not included in the API request, causing the workflow to fail to associate historical execution data.

## How to confirm the configuration is complete
- Manually trigger the workflow, and check whether the `variables` parameters of each node correctly transfer the preset core fields.
- Run the database connection node, confirm that no permission error is returned, and pressure testing related data can be pulled normally.
- Simulate a node execution failure, confirm that the alert node bound via `nodeId` can trigger notifications normally.
- Check the document generation node, confirm that pressure testing data has been automatically filled into the preset field positions of the corresponding document.
