# Publishing Instructions and Operational Report Summary for Search Ad Keyword Management: HTTP Interfaces and External Systems

## What the Data for This Category Looks Like
The data for this category is primarily sourced from search ad backends, search term reports, bidding ranking data, and landing page data. Daily generated documents include keyword lists, negative word lists, bid records, and search term reports. Each document typically contains thousands of entries with matching types and bid amounts. Negative word lists mark categories of search terms that require blocking. Data update frequencies are generally daily or weekly; some real-time bidding scenarios use hourly synchronization. Most data fields are text or numeric types, including core metrics such as keyword text, matching mode, click volume, and conversion cost. The overall structure is relatively flat.

## Constraints Imposed on HTTP Interfaces and External Systems
The data characteristics of this category impose multi-dimensional constraints on HTTP interface and external system integration. First, data sources cover multiple search ad backends and business systems. Configure multiple sets of authentication methods via the `Authorization` parameter to adapt to the authentication rules of different platforms. Second, data update frequencies range from daily, weekly, to real-time. Interface polling intervals must support flexible configuration to avoid exceeding platform rate limits due to frequent requests. Third, single keyword list documents contain many entries. Interface request bodies and response bodies must support pagination parameters. Field length checks are also required to prevent storage errors caused by overly long data. Finally, most core metrics are numeric or text types. Interfaces must predefine basic parameter validation rules to adapt to data format requirements for different business scenarios.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| ---|---|--- |
| `Authorization` | `Bearer {token}` or `Basic {base64_credential}` | Adapts to standard authentication formats for most search ad platforms, and is compatible with FastGPT v4.17.0 external interface call rules |
| Maximum entries per single request | `500–1000 entries` | Matches interface rate limits of most search ad backends to avoid request blocking |
| Data update synchronization interval | `3600 seconds` or set based on business scenario | Adapts to daily/weekly data update frequencies, balancing real-time performance and interface call costs |
| `variables` | Bind business variables such as keyword list ID, negative word list path | Enables dynamic loading of business data for the corresponding category during interface calls, eliminating the need for hardcoded configurations |
| `responseData` parsing rules | Map response fields according to search term report field configurations | Directly maps interface return data to the operational report format recognizable by FastGPT, reducing secondary processing costs |
| Interface timeout threshold | `60 seconds` | Adapts to the average interface response time of search ad backends, avoiding call failures caused by long wait times |

## Three Common Configuration Mistakes
- An `Error 1406 (22001): Data too long` error is returned when calling the interface. This occurs because field length validation is not configured, and the text length of keywords or bid records exceeds the storage field limits of the external system.
- The number of operational report data entries returned by the interface does not match expectations. This occurs because pagination parameters are not set or the pagination threshold is configured incorrectly, resulting in only partial data being returned.
- Interface calls frequently trigger rate limit blocking. This occurs because the synchronization interval is set too short, exceeding the interface call frequency limits of the search ad backend.

## How to Confirm Successful Configuration
- Call the test interface, and check whether the `Authorization` parameter is correctly carried. Request header content can be viewed via FastGPT’s interface debugging logs.
- Compare the `responseData` returned by the interface with the locally stored keyword list to confirm whether the field mapping meets configuration requirements.
- Adjust the synchronization interval parameter, and observe whether the interface call frequency matches expectations. Request counts can be viewed via the external system’s backend logs.
- Simulate a request with an overly long keyword, verify whether the interface triggers field length validation, and confirm that the configuration takes effect.

All provided configuration values are common starting points. They should be evaluated against the reader’s own samples and business requirements.
