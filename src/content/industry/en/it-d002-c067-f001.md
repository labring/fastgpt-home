# Release Notes and Operation Report Summary for Data Security Classification and Grading: HTTP Interfaces and External Systems

## What this category of data looks like
This category of data primarily comes from data asset inventory results, database metadata, business system descriptions, and compliance reference documents. Daily maintained documents include data catalogs, classification and grading rules, important data identification tables, and review minutes. The data update frequency is quarterly or after each business system change. Core fields include data asset unique identifier, sensitive data level, affiliated business domain, and compliance adaptation items. There are no fixed unit constraints, and adjustments must be made dynamically based on business and compliance requirements.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Data from this category comes from scattered sources, so it is necessary to connect to multiple types of business system metadata interfaces. HTTP calls must support multi-source authentication configuration. Data updates have no fixed cycle, so call modes that trigger on demand or pull at scheduled intervals must be supported. Core fields must be adjusted dynamically with business, so parameter rules for custom field mapping must be allowed. Consequences of compliance errors are severe, so a failure retry mechanism and status synchronization callback must be configured. Additionally, interface response results must be written to process variables for subsequent classification and grading rule verification, while compatibility with response formats of different third-party systems is required.

## How to set configurations
| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| `Authorization` | `Bearer ${APP_API_KEY}, do not carry AIPROXY_API_TOKEN` | Official requirements state that external calls to application APIs must use the application API Key, and AI Proxy administrator Token must not be used. Applies to FastGPT v4.17.0 and above versions |
| `variables` | Map core business fields such as data catalogs and classification and grading rules | Business data returned by third-party interfaces must be bound to FastGPT process variables for subsequent classification and grading verification |
| `responseData` | Extract status fields (such as parseStatus) and core data fields | Quickly obtain key information returned by the interface for synchronizing data classification and grading status |
| HTTP request timeout | 300–600 seconds | Data asset inventory interfaces usually return large amounts of data, so sufficient response time must be reserved |
| Number of failure retries | 2–3 times | Avoid call failures caused by temporary network fluctuations, while preventing repeated submission of compliance-sensitive data |
| Single pull data volume limit | 1000–2000 MB | Avoid interface timeout or memory overflow caused by pulling too large data in a single request |

## Three common mistakes
- Symptom: After calling the HTTP interface to create a classification and grading knowledge base, it is not possible to obtain the parsing in progress, ready, or parsing failed status. Troubleshooting items: Check whether the interface request is configured with `responseData` to extract status fields, and check whether process variables have been bound to synchronize status.
- Symptom: HTTP template interface response results cannot be used by subsequent process nodes. Troubleshooting items: Check whether the response results are mapped to process-available variables via the `variables` configuration.
- Symptom: After the process starts, calling the third-party API fails, and the retry mechanism is not triggered. Troubleshooting items: Check whether reasonable failure retry times and timeout periods are configured, and check whether the automatic retry rule of the process is enabled.

## How to confirm that the configuration is complete
- Initiate a test call, and check whether the response header and `responseData` field returned by the interface include expected status and data fields.
- Check whether process variables have been bound to the return results of the third-party interface, and confirm that subsequent nodes can normally read variable content.
- View the startup logs of the AI Proxy and App/Admin services, and confirm that `AIPROXY_API_ENDPOINT (root address of the AI Proxy service)` and `AIPROXY_API_TOKEN (AI Proxy administrator Token)` configurations are not missing, and there are no startup verification failure errors.
- Simulate temporary network interruption, confirm that the interface call triggers the preset failure retry mechanism, and the call can be completed normally after the network is restored.

All configuration values provided here are common starting points, and should be evaluated against the reader's own samples and requirements.
