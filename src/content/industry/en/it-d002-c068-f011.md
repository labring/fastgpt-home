# Release Notes and Operational Report Summary for Database Cloud Service Operations: Database and Operations Maintenance

## What the data for this category looks like
Data for this category primarily originates from cloud database consoles, slow logs, monitoring metrics, and ticketing systems. Update frequency is daily or upon each instance change. Daily operation and maintenance documents include instance change orders, backup and recovery records, performance diagnosis reports, and parameter adjustment records. Core fields include instance ID, change time, backup size (MB), slow SQL execution time (seconds), tenant identifier, and pre- and post-adjustment parameter values. Console data structures vary slightly across cloud service providers, but core fields cover the full workflow of operation and maintenance operations. No additional non-operation and maintenance business data is included.

## What constraints these characteristics impose on the "database and operations maintenance" link
Multiple data sources require integrating return formats from different interfaces to prevent distorted aggregated data caused by field mapping errors. Differences in update frequencies require designing incremental synchronization mechanisms to ensure consistent timeliness of data from different sources. Differences in document structures require unified parsing templates to adapt to import formats for different operation and maintenance documents. Inconsistent field units require standardization conversions to ensure readability of aggregated data. The time-consuming pain point of identifying slow SQL requires associated queries linking slow logs and monitoring metrics to reduce manual troubleshooting time. The potential consequences of backup and recovery errors require configuring verification mechanisms to avoid missing records from misoperations.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| MongoDB connection configuration | `mongodb://<username>:<password>@<cloud-host>:<port>/<db-name>?authSource=admin` | Adapts to the standard authentication connection format for cloud MongoDB instances, compatible with access rules for multi-tenant consoles |
| PostgreSQL connection configuration | `postgresql://<username>:<password>@<cloud-host>:<port>/<db-name>?sslmode=verify-full` | Complies with encrypted transmission specifications for cloud PostgreSQL, ensuring secure transmission of operation and maintenance data |
| Maximum database connections | `40–70` | Matches the default connection limit for cloud database instances, avoiding tenant connection over-limit alarms |
| Redis cache configuration | `redis://:<auth-password>@<cache-host>:<port>/0` | Used to cache operation and maintenance monitoring metrics and slow log snapshots, improving aggregated query efficiency |
| Slow log pull threshold | `1000 milliseconds` | Filters valid records from cloud database slow logs, focusing on slow SQL statements that affect operation and maintenance efficiency |
| Instance change synchronization cycle | `86400 seconds` | Matches the daily update frequency of cloud database instance change records, ensuring completeness of change data |

This configuration guide applies to FastGPT v4.17.0.

## Three common mistakes
- Symptom: No output when calling database tools, with no error prompts in the interface. Cause: FastGPT access whitelist is not configured in the cloud database console, resulting in blocked connection requests.
- Symptom: Syntax errors occur when passing SQL statements using variables, but the same SQL runs without errors manually. Cause: Special characters in variables are not escaped, causing syntax conflicts during SQL parsing.
- Symptom: Database connection fails in the workflow, with a connection timeout prompt. Cause: Redis cache parameters are not configured correctly, preventing normal synchronization of operation and maintenance configuration information to workflow nodes.

## How to confirm configurations are correct
- The built-in database connection test tool included with FastGPT is executed, configured connection parameters are entered, and verification is performed to confirm whether database instance lists can be pulled normally or simple query statements can be executed.
- Access logs are reviewed after logging in to the cloud database console, and confirmation is made that FastGPT's request IP has been recorded and no blocked records exist.
- A SQL query with variables is executed, and verification is performed to confirm that the statement after variable replacement can run normally and return expected results.
- The operation and maintenance summary panel is reviewed, and confirmation is made that slow logs, backup records, and other data are updated normally according to the configured cycle.

The values provided are common starting points and should be measured against the reader's own samples.
