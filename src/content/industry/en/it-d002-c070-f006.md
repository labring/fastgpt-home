# Release Notes and Operations Report Summary for Data Cleaning and Quality Inspection: Scheduled Tasks and Automation

## What the data for this category looks like
Data sources for this category include raw datasets, ETL operation logs, annotation platform output results, and sampling quality inspection results. Data updates occur daily or per single batch task. Daily generated documents include cleaning rule configurations, quality inspection sampling tables, abnormal data lists, and delivery reports. Data fields cover raw data identifiers, abnormal type tags, quality inspection scores, processing status, and other items. There are no unified fixed units, and values adjust according to the specific business dataset. This category serves data engineers, quality inspectors, and project managers. Daily operations focus on data quality verification and delivery document generation.

## What constraints these characteristics impose on scheduled tasks and automation
Decentralized data sources and inconsistent update rhythms require scheduled tasks to adapt to multi-source data access verification logic, to avoid repeated processing of unchanged datasets. Daily documents have varying levels of structural consistency. Automated workflows must support configuration imports in different formats such as cleaning rules and sampling tables, and cannot rely on a unified parsing logic. The generation of abnormal data lists and delivery reports must be tied to specific task batches. The time window for scheduled triggers must match the processing cycle of single batch tasks, to avoid mixing data across batches. ETL logs have high real-time requirements. The task retry mechanism must adapt to the delay characteristics of log collection, to reduce task failures caused by short-term network fluctuations. The update frequency of quality inspection sampling results determines the scheduling interval of scheduled tasks, to avoid repeated triggering of unfinished task batches.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Task Scheduling Cycle | Set to `Daily 02:00` or `Triggered after each batch task completes` based on business update frequency | Matches the update rhythm of raw datasets and sampling results, avoids repeated processing of unchanged data |
| Log Collection Timeout | `600 seconds` | Adapts to the conventional collection delay of ETL logs, prevents task failures due to short delays |
| Task Retry Count | `3 times` | Balances task success rate and resource consumption, avoids invalid retries from occupying computing resources |
| Abnormal Data Threshold | Calibrated based on actual testing | Adapts to the abnormal tolerance of different businesses, avoids misjudging normal data |
| Report Generation Scope | Top 1000 abnormal data entries | Controls the output size of delivery reports, meets daily review needs |
| Trigger Condition Check | Execute only when the raw dataset is updated | Avoids meaningless task runs, saves platform resources |

## Three common mistakes
- Phenomenon: Abnormal data fields are empty in regularly generated delivery reports. Cause: No field mapping rules for abnormal data lists and delivery reports are configured, causing the automated workflow to fail to extract corresponding data.
- Phenomenon: Tasks remain in running status for a long time after triggering, and finally trigger a timeout error. Cause: No reasonable log collection timeout is set, and ETL log collection delay exceeds the preset threshold.
- Phenomenon: Single batch tasks are executed multiple times, causing duplicate entries in the abnormal data list. Cause: No deduplication logic for task triggers is configured, and no check is performed to verify whether the current task batch has been processed.

## How to confirm the configuration is complete
- Review the task scheduling logs of FastGPT v4.17.0, confirm that scheduled tasks trigger according to the preset cycle.
- Initiate a test task manually, verify that the fields in the abnormal data list and delivery report are complete.
- Simulate a raw dataset update, confirm that tasks trigger only when data is updated, with no meaningless runs.
- Review the task retry records, confirm that abnormal tasks complete or terminate after retrying the preset number of times.
