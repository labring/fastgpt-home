# Release Notes and Operations Report Summary for Data Masking: HTTP Interfaces and External Systems

## What this category of data looks like
Data for this category comes from internal enterprise databases, data dictionaries, data masking tool run results, and access approval systems. Updates are issued per batch data processing task or individual project. Daily supporting documents include masking plans, field mapping tables, masking validation reports, and approval records. Data fields include sensitive field identifiers, masking rule IDs, hashed values of processed data, approval status, and other relevant fields. There are no uniform fixed units; values adjust based on the field types of specific projects.

## What constraints these characteristics impose on HTTP interfaces and external systems
Since data sources include multiple disparate systems, HTTP interfaces must support integration with different authentication methods and adapt to data source addresses across different deployment environments. Data updates are issued per project or batch, so interface requests must support dynamic adjustment of request scope and parameters to accommodate non-fixed update rhythms. Supporting document structures vary by project, so interfaces must support custom field mapping to adapt to masking plans and field mapping tables for different projects. Approval records must sync with the masking workflow, and interface responses must include an approval status field to enable external systems to sync compliant data.

## How to configure settings
| Configuration Item | Suggested Practice | Rationale |
| --- | --- | --- |
| Request Address | Actual address for connecting to internal masking tools and databases, supports penetrative domain names | Adapts to dispersed data source deployment scenarios |
| Authentication Configuration | Carries the `Authorization` header, uses Bearer tokens | Meets security and compliance requirements for data access |
| Custom Tool Variables | Configure optional parameter ranges based on masking field types | Adapts to field mapping requirements for different projects |
| Return Data Processing | Only return masked fields and approval status from `responseData` | Prevents leakage of unmasked raw data |
| Timeout Setting | 30-60 seconds | Adapts to time consumption requirements for batch data processing |

## Three common configuration mistakes
- Phenomenon: An HTTP node calls a penetrative domain address and returns a getaddrinfo ENOTFOUND error. Cause: Correct domain resolution environment is not configured, or the port for the penetrative address is not open.
- Phenomenon: The `variables` parameter for custom tools cannot have optional values set, and no corresponding configuration item appears in the interface. Cause: Not switched to the new tool configuration mode, or advanced settings for custom parameters are not enabled.
- Phenomenon: Configured models do not appear on the platform, and no effect is seen after only modifying the BASE_URL. Cause: Environment variables in docker-compose have not been updated synchronously, or services have not been restarted to load new configurations.

## How to confirm configurations are correct
- Initiate a test request, check that the returned results only include masked fields and approval status, with no raw sensitive data.
- Verify that the request header carries the `Authorization` header, and no authentication token information is leaked in logs.
- Check that the `variables` parameter for custom tools covers all masking fields requiring mapping for the current project.
- After restarting FastGPT v4.17.0, validate that configurations in docker-compose take effect, and the platform can load the corresponding models normally.
