# Release Notes and Operations Report Summary for Penetration Testing Services: Database and Operations

## What Data for This Category Looks Like
Penetration testing service data sources typically include target system logs, public vulnerability databases, automated scanner output results, and red team engineer manual verification records. Daily produced documents fall into four categories: test authorization letters, official penetration test reports, vulnerability reproduction step records, and vulnerability rectification suggestions.
Data updates follow individual test project cycles, or are triggered when major version vulnerability databases are updated. Common data fields include project unique identifier, authorization number, vulnerability CVE code, risk rating, reproduction environment parameters, and rectification plan. There is no unified mandatory unit requirement, and some fields must adapt to the output formats of different scanners.

## What Constraints These Characteristics Impose on the Database and Operations Link
Penetration testing service data characteristics impose multi-dimensional constraints on the database and operations link.
Multi-source heterogeneous data sources require the database to support flexible field mapping and format compatibility, to avoid storage failures caused by format differences between scanners and manual records.
The per-project update cycle requires the database to support data isolation by project dimension, to prevent interference between test data of different projects.
Storage of compliance documents such as test authorization letters must ensure data cannot be tampered with, while supporting hierarchical permission access to avoid sensitive information leakage.
High-risk error consequences require the database to have transaction guarantee and data backup mechanisms, to prevent legal disputes caused by lost vulnerability records or damaged authorization documents.

## How to Set Configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://pentest_user:secure_pass@db-host:27017/pentest_data?authSource=admin` | Stores mixed-format data including penetration test reports, vulnerability reproduction records, etc. Specifies a project-specific database and enables authentication to ensure security |
| `PG_URL` | `postgresql://ops_user:secure_ops_pass@db-host:5432/pentest_ops?sslmode=require` | Stores compliance documents such as test authorization letters and rectification suggestions that require strong consistency. Uses SSL encrypted transmission to avoid data leakage |
| `DB_MAX_LINK` | `20–30` | Adapts to connection requirements for parallel operation of multiple scanners under a single project and batch import of manual verification records, to avoid connection pool exhaustion |
| `REDIS_URL` | `redis://cache_user:secure_cache_pass@cache-host:6379/0?maxmemory-policy=allkeys-lru` | Caches temporary scanner results and vulnerability database incremental update data, to reduce high-frequency query pressure on the primary database |

## Three Common Misconfigurations
- Encounter `authentication failed` or `connection timed out` errors when connecting to the database. This occurs because the authentication username, password, and authentication source of the target database are not configured correctly according to the standard format of `MONGODB_URI`, or the Linux system firewall has not opened ports 27017 or 5432.
- Database write timeout occurs when batch importing vulnerability data for a single project. This is because `DB_MAX_LINK` is set too low, causing concurrent write tasks to fail to obtain sufficient database connections.
- Field parsing exceptions occur after importing vulnerability database data. This is because the compatibility between MongoDB 6 or 7 versions and FastGPT v4.17.0 was not confirmed, causing the database driver to fail to adapt to the storage protocol of the corresponding version.

## How to Confirm the Configuration Is Correct
- Run the official database connection test script to verify that `MONGODB_URI` and `PG_URL` can establish normal connections and complete read/write tests.
- Check Redis cache monitoring metrics to confirm that temporary scan results can be written to the cache normally and expire and clean up within the set period.
- Submit a test project authorization letter and simulated vulnerability report to verify that data can be stored correctly by project dimension and support query by project ID.
- Adjust the value of `DB_MAX_LINK` and observe changes in database connection count under concurrent tasks, to confirm that the value adapts to the concurrent scale of the current business.

The values given are common starting points and should be measured against the reader's own samples.
