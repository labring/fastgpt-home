# Release Notes and Operation Report Summary for Channel Attribution and Lead Distribution: HTTP Interfaces and External Systems

## What the data for this category looks like
This category's data mainly comes from advertising platforms, customer relationship management systems, attribution SDKs, and online form systems. Daily produced documents include attribution rule configuration tables, lead distribution tables, channel effect reports, and exception checklists. Data update cycles are usually daily or weekly. Core fields include channel identifiers, lead unique IDs, sales attribution identifiers, conversion times and amounts, and other fields. Field units vary by source system. Some fields require cross-system consistency checks.

## What constraints these characteristics impose on the HTTP Interfaces and External Systems link
Multi-source data access requires interfaces to adapt to authentication and data formats of different systems, to avoid cross-system field mapping deviations. Daily or weekly update cycles mean interface call frequencies should not be too high. Set reasonable request intervals to avoid rate limiting risks. Cross-system consistency checks for core fields require interfaces to support passing key parameters such as channel identifiers and lead IDs for verification. Interfaces must also return standardized exception identifiers for subsequent generation and troubleshooting of exception checklists. Additionally, exception checklist generation relies on detailed error information returned by interfaces, so interfaces must support returning structured error content.

## How to set configurations
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${custom authentication key}` | Adapts to the standard authentication format of most external advertising platforms and CRM systems, ensuring the legality of interface calls |
| `variables` | `{"channel_code": "${channel identifier variable}", "lead_id": "${lead ID variable}", "report_date": "${statistical date}"}` | Matches the core fields of attribution rules and channel reports in daily documents, binding interface parameters to business data |
| `responseData` | `Filter by statistical cycle, return daily/weekly data` | Matches the data update cycle, avoiding returning redundant data beyond business needs |
| Number of items per page for pagination | `100–200 items` | Adapts to the data volume of daily reports, avoiding timeouts caused by overly large single interface return data, and simplifying downstream data parsing logic |
| Request timeout | `600 seconds` | Adapts to the average response time of multi-system interfaces, avoiding call failures caused by network fluctuations |

## Three common mistakes
- Symptom: HTTP request returns empty fields, and downstream lead distribution links cannot obtain channel identifiers. Cause: The field names configured in the `variables` parameter do not match the field names returned by the external system, and cross-system field mapping is not completed.
- Symptom: Workflows cannot extract HTTP response content as downstream variables using jsonPath. Cause: The parsing rules for `responseData` are not configured correctly, or the jsonPath syntax does not match the returned nested data structure.
- Symptom: Interface calls frequently trigger rate limiting errors. Cause: Reasonable request intervals are not set based on the data update cycle, and call frequency exceeds the rate limiting threshold of the external system.

## How to confirm the configuration is complete
- Test channel identifiers, lead IDs, and statistical dates are manually passed. The interface is invoked, and returned data is checked against test data from the external system.
- After the `Authorization` parameter is configured, the authentication interface is invoked to verify that a 200 status code is returned.
- A complete daily report synchronization process is triggered, and generated data is checked to confirm whether expected exception checklist data is produced.
- The `responseData` returned by the interface is checked to confirm whether it includes preset core fields, such as channel ROI, lead count, and other fields.

The values provided are common starting points, and should be evaluated against local samples.
