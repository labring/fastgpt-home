# Release Notes and Operations Report Summary for Game Client Performance Optimization: Workflow Orchestration

## What Data for This Category Looks Like
Data for this category originates from Engine Profiler, crash platforms, real device testing tools, and frame rate collection systems. Four regular document outputs are produced: performance test reports, device compatibility lists, optimization records, and crash analysis reports.
Data updates occur daily or per version iteration. Included fields are device model, average frame rate, peak memory usage, crash rate, and package size. Common units are fps, MB, and occurrences per million users.
Core time-consuming processing steps are low-end device reproduction, resource usage analysis, and optimization effect regression. Data anomalies typically lead to client lag, crashes, or app store negative reviews.

## Constraints for Workflow Orchestration
Data sources for this category are scattered and have varied formats. Workflows must support connecting multiple data source nodes and adapting to different formats. Dedicated parsing nodes must be configured for each type of performance test report and crash analysis document.
Data follows a daily or per-version update schedule. Workflows must support scheduled triggering or triggering after a version release.
Core time-consuming steps focus on low-end device reproduction and optimization effect regression. Workflows must support concurrent execution of batch nodes to prevent single-node runs from blocking the entire process.
This category prioritizes frame rate, package size, and resource loading metrics. Dedicated metric validation nodes must be configured in workflows to filter irrelevant business data and improve analysis efficiency.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | Daily at 00:00 or 10 minutes after version release | Matches daily or per-version data update rhythm |
| `variables` scope | Only performance metrics for the current workflow node | Prevents irrelevant business data from mixing into the global context, focuses optimization analysis |
| Node Concurrency Count | 2–4 parallel nodes | Adapts batch processing for time-consuming steps like low-end device reproduction and resource analysis |
| Timeout Threshold | 600 seconds | Covers the longest expected duration for low-end device reproduction |
| Exception Retry Strategy | Up to 2 retries, 30-second interval | Addresses temporary faults like gateway forwarding errors |
| `nodeId` binding | Bind dedicated performance analysis nodes | Ensures the workflow only calls model services adapted for game client optimization |

## Three Common Configuration Mistakes
- Workflow node return results include irrelevant business data. This occurs when the `variables` scope is not restricted. The global context is called by default, mixing non-performance-related information.
- Large model node status displays as failed. Checking node logs reveals "500 Gateway forwarding error because service is disconnected". This occurs when the workflow’s bound model service is not running normally, or the network connection is interrupted.
- Batch performance test node runs take excessive time. This occurs when concurrent execution configuration is not enabled, or the concurrency count is set too low to support parallel processing of batch performance tests.

## How to Verify Correct Configuration
- Review the workflow’s trigger settings to confirm the trigger time matches the data update rhythm.
- Run a test of batch node execution, check execution logs to confirm the concurrent node count aligns with configuration requirements.
- Inspect the `variables` configuration to confirm only performance metric variables for the current node are included, with no irrelevant context.
- Execute a test node, check logs to confirm no gateway forwarding errors appear, and the service connection is normal.
- Confirm the workflow runtime environment is FastGPT v4.17.0, which supports the current configuration items.
