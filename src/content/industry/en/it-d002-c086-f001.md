# Publishing Instructions and Operational Report Summary for Game License and Publication Declaration: HTTP Interfaces and External Systems

## What data for this category looks like
The data for this category comes from the National Press and Publication Administration’s service platform, copyright registration system, game package files, and materials submitted by operating institutions. Daily processed documents include declaration request files, game application forms, copyright certificates, and review reports. Each data entry corresponds to the complete declaration process for a single game. Updates are triggered irregularly based on the declaration progress of individual games. Fields include declaration subject information, work identifiers, and audit status-related fields. There is no unified fixed batch update cycle.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Data sources are scattered across different official and institutional systems. HTTP interfaces must support pulling data from multiple sources and connecting to external services with different permission levels. Declaration progress for individual games triggers updates irregularly, so interfaces must support on-demand calls. Daily documents are structured declaration materials. Interface parameters must match fixed fields such as declaration subject, work identifier, and audit status. Approval processes have high requirements for material consistency. Interfaces must fully transfer original data fields to avoid information truncation or format errors.

## How to configure settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {API key generated by FastGPT deployment}` | External interface calls require identity authentication, complying with official interface call specifications |
| `variables` | `{"target_game_id": "${external_game_id}", "apply_stage": "first review"}` | Pass exclusive identifiers for individual games and declaration stage parameters, adapting to call requirements for irregular updates |
| `responseData` | `Return only material verification results and approval status` | Filter non-essential data to reduce interface transmission load, matching core data needs of the declaration process |
| Single call data volume limit | `800–1200 characters` | Adapt to the average size of single game declaration materials, avoiding transmission overload |
| Timeout threshold | `300–600 seconds` | Pulling declaration materials and querying approval status takes a long time. The reasonable interval is calibrated based on actual measurements |
| Retry count | `2 times` | Avoid call failures caused by temporary network fluctuations, ensuring continuity of the declaration process |

## Three common configuration mistakes
- Symptom: Empty approval status fields are returned after calling the interface. Cause: The unique identifier parameter for the target game was not configured in `variables`, causing the interface to fail to match the target declaration data.
- Symptom: Interface response time exceeds expected duration. Cause: No reasonable timeout threshold was set, and no retry mechanism was configured. After a call fails due to temporary network fluctuations, automatic recovery is not possible, extending overall process time.
- Symptom: External system cannot receive callback notifications. Cause: The correct external system callback address was not configured, or the `Authorization` authentication parameter format is incorrect, causing the interface request to be blocked.

## How to confirm configuration is complete
- Initiate a single call, check if the returned `responseData` only contains material verification results and approval status, with no redundant content.
- Simulate temporary network fluctuations to trigger a call failure, check if the system automatically executes the preset number of retry operations.
- View interface call logs, confirm that the `Authorization` parameter format is correct, and that the game identifier passed in `variables` matches the target declaration data.
- Check if the external system has received callback notifications, confirming that the callback address configuration is correct.

The values provided are common starting points and should be measured against the reader's own samples.
