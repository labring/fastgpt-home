# Release Notes and Operation Report Summary for Game Operation Activity Configuration: Context and Token

## What the data for this category looks like
The data for this category mainly comes from the game operation backend, player segmentation system, payment data platform, and activity log system. Daily produced documents include activity plans, reward configuration tables, launch checklists, and activity review reports. Fields include activity ID, time range, reward type and value, trigger conditions, player tier labels, and more. Update frequency is mostly weekly or concentrated adjustments before holiday activities. Data volume fluctuates with activity scale. Configuration documents and log data for a single activity are retained throughout the activity cycle. Core data covers the entire activity execution process, including reward distribution, player participation records, exception feedback, and other content.

## What constraints do these characteristics impose on the "context and token" link
Activity configuration documents and log data have complex structures, including multi-dimensional numerical and rule fields. Context needs to associate historical configurations and player interaction data within the activity cycle, so high precision is required for context recall. The characteristic of concentrated weekly or holiday updates requires the context cache to support dynamic adjustment according to the activity cycle, to avoid redundant data occupying token quota. At the same time, configuration fields vary greatly across different activities, with different reward types and trigger logic. The context must accurately match the exclusive fields of the current activity to prevent irrelevant data from mixing in and causing token waste. In addition, the timeliness requirement for exception compensation processing means the context must quickly recall historical exception records, which imposes clear constraints on token call efficiency.

## How to set the configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `maxContext` | First 3 same-type activity configuration documents + latest 2 rounds of configuration records for the current activity | Core reference data for activity configurations are recent same-type activities and core configurations of the current activity, to avoid excessive historical data occupying tokens |
| `quoteMaxToken` | 800–1200 token | The average length of activity configuration documents is 500-800 token, with reserved redundant space to cover complete reward configurations and rule descriptions |
| Context recall threshold | 0.75–0.85 | Activity data has high field similarity; setting a moderate threshold to recall accurately relevant historical data and avoid mixing irrelevant content |
| Context cache update trigger condition | When activity configuration is submitted | Matches the characteristic of concentrated weekly/holiday updates; only update the context cache when activity configurations are adjusted to reduce invalid token consumption |
| Exception log recall upper limit | First 10 exception records | Exception compensation processing only requires reference to recent exception cases; excessive records will increase token burden |

## Three common mistakes
- Phenomenon: Token limit exceeded error occurs during calls, with prompts related to insufficient token quota. Cause: Full historical activity data is used as context without considering the update frequency of activity configurations, and redundant data occupies excessive token quota.
- Phenomenon: In a multi-model orchestrated activity configuration workflow, context confusion occurs, and configuration data from different activities is incorrectly associated. Cause: Context cache is not isolated by activity ID, leading to interference between context data of different activities and deviations in token association logic.
- Phenomenon: Activity configuration context in multi-turn conversations cannot be recalled, and configuration content from historical conversations is not included in the context scope of the current call. Cause: The persistence configuration for multi-turn conversation context is not set correctly, or the activity ID filtering rule for context matching is not enabled.

## How to confirm the configuration is correct
- Call the FastGPT v4.17.0 test interface to check if the returned context data only includes the core configuration fields of the current activity, with no redundant irrelevant historical activity data.
- Simulate multi-turn activity configuration conversations to check if the context continuously associates the historical configurations of the current activity, with no cross-activity data confusion.
- Adjust the value of the `quoteMaxToken` parameter to verify whether the token consumption during calls matches the preset 800–1200 token range, with no limit exceeded errors.
- Submit an activity configuration adjustment operation to check if the context cache is automatically refreshed according to the configured update trigger condition, with no delays or failed updates.
