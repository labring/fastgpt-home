# Release Notes and Operation Report Summary for Game Operation Activity Configuration: Database and Operations

## What the data for this category looks like
Data for this category comes primarily from game operation backends, player segmentation systems, payment statistics modules, and activity logs. Daily associated documents include activity execution plans, reward configuration tables, pre-launch checklists, and activity post-mortem reports.
Data updates are typically triggered weekly or around holiday nodes. Individual data entries include fields such as activity ID, configuration effective time, reward tiers, trigger conditions, and player participation records. Units include person-times, item IDs, monetary amounts, and more. There is no fixed unified format, and adjustments must be made flexibly based on activity type.

## Constraints these characteristics impose on database and operations workflows
The data characteristics of this category impose multiple constraints on database and operations workflows. Multi-source data access requirements mean support must be provided for connecting to different data sources such as operation backends and player segmentation systems. Flexible configuration interfaces must be reserved.
Update frequencies fluctuate with activity cycles. Concurrent peaks occur during holidays or large-scale promotion periods. Elastic adaptation capabilities for database connection pools must be ensured.
Activity configurations are tightly bound to associated documents. Configuration changes require synchronized traceability. Databases must support version snapshot functions to enable rapid rollbacks.
Strict validation requirements apply to fields such as reward values and trigger conditions. Strong constraint rules must be configured to avoid format errors.
Exception compensation processing requires rapid data recovery. Operations workflows must support lightweight backup and recovery operations.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://admin:securepass@db-host:27017/activity_db?authSource=admin` | Adheres to database connection specifications for FastGPT v4.17.0, supports unstructured storage requirements for game activity logs and player participation data, and supports multi-document transactions |
| `PG_URL` | `postgresql://op_user:dbpass@pg-host:5432/game_operation?sslmode=require` | Stores structured reward configuration tables, activity time parameters, and operation report data, and supports complex aggregate queries |
| `DB_MAX_LINK` | `200–300 connections` | Matches concurrent access demands during holiday activity peak periods, and prevents database connection exhaustion |
| `REDIS_URL` | `redis://:redis-pass@redis-host:6379/1` | Caches frequently read activity configurations and player segmentation data to reduce query pressure on the primary database |
| Database backup cycle | Full daily backups, hourly incremental backups | Ensures rapid recovery of activity configuration and operation data, and addresses rollback requirements for exception compensation scenarios |

## Three common configuration mistakes
- Symptom: Database connection failure prompt on login page, with 503 status code returned. Cause: Incorrect authentication parameters, host address, or port were entered when modifying `MONGODB_URI` or `PG_URL` configurations, preventing establishment of a valid database connection.
- Symptom: System cannot be accessed normally after version upgrade, and a MongoDB authentication failure error pops up after service restart. Cause: The authentication source parameter in the MongoDB configuration file was modified during the upgrade process, and system connection configurations were not updated synchronously, leading to failed permission verification.
- Symptom: Abnormal activity reward distribution, with some players not receiving corresponding items. Cause: `DB_MAX_LINK` configuration value is too low, database connections are exhausted during peak periods, and reward configuration data fails to be written to the database.

## How to confirm configurations are set correctly
- Run a database connectivity test script to verify the correctness of `MONGODB_URI`, `PG_URL`, and `REDIS_URL` configurations, and confirm there are no authentication or address errors.
- Simulate peak concurrent requests, observe database connection pool usage, and confirm `DB_MAX_LINK` configuration covers actual concurrent demands.
- Trigger an activity configuration change operation, verify that data is synchronously written to the database, and that associated operation reports can be generated and exported normally.
- Manually trigger a database backup operation, confirm that backup files can be generated normally and stored to the specified storage location.
