# Release Notes and Operation Report Summary for Vulnerability Scanning Service: HTTP Interfaces and External Systems

## What the data for this category looks like
Operational data for vulnerability scanning services primarily originates from vulnerability scanners, asset inventories, CVE databases, and patch announcements. Update frequency is weekly or monthly.
Daily operation documents include scanning plans, vulnerability lists, rectification work orders, and rescan reports. Core fields include vulnerability CVE numbers, associated asset IP addresses, scan times, vulnerability severity levels, rectification statuses, and more.
Data is stored in structured text or JSON format. The number of fields in a single report is fixed, and covers all full-process operational requirements.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" workflow
Since data sources include multiple external systems, interfaces must adapt to authentication and format requirements of different data sources.
Weekly or monthly update frequency means high-frequency interface calls are unnecessary, but incremental synchronization must be supported to reduce duplicate data transmission.
The fixed field structure of daily operation documents requires interfaces to return standardized structured data, to prevent operational process interruptions from missing fields.
The severe impact of high-risk vulnerability exposures requires interfaces to include complete error retry and alert mechanisms, to ensure stable data synchronization.

## How to Configure the Integration
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {Vulnerability Scanning Service API Key}` | Complies with HTTP interface authentication standards, and matches the interface authentication requirements of the vulnerability scanning service |
| `variables` | `{"asset_scope": ["192.168.0.0/24"], "report_type": "full"}` | Adapts to the asset scope and report type parameters of the vulnerability scanning service, matching the configuration needs of daily scanning plans |
| `responseData` | `["cve_id", "asset_ip", "scan_time", "fix_status"]` | Only returns core fields required for daily operations, reducing data transfer volume and meeting traffic requirements for weekly or monthly updates |
| Request timeout | `600 seconds` | Vulnerability scanning tasks typically take a long time. This setting avoids interrupting the scanning process due to timeout |
| Retry count | `2 times` | Addresses temporary network fluctuations, and prevents data synchronization interruptions from a single failed request |

## Three Common Configuration Mistakes
- Symptom: Returns a 500 status code, with logs showing `do request failed: Post "https://xxx tls: failed to verify certificate`. Cause: Correct TLS certificate verification rules are not configured, or the target scanning service uses a self-signed certificate that has not been added to the trust list.
- Symptom: Synchronized vulnerability list fields are missing or have incorrect formats. Cause: The fields configured in `responseData` do not match the actual fields returned by the scanning service, and core fields required for daily operations are not covered.
- Symptom: No data is returned after a scheduled synchronization task is triggered. Cause: The asset range configuration in `variables` is incorrect, does not include the actual asset network segments that need to be scanned, or the update frequency setting does not match the weekly or monthly update rhythm of the scanning service.

## How to Verify Correct Configuration
- Call the configured HTTP interface, and check if the returned `responseData` fields include core operational fields such as vulnerability CVE numbers and asset IP addresses.
- Review interface authentication logs to confirm that the format of the `Authorization` parameter is correct, and no authentication failure errors are present.
- Compare synchronized local data with the vulnerability list from the scanning service, to confirm that fields match and data is complete.
- Simulate triggering a synchronization task, and check if data pulling completes within the preset time window, with no timeout errors.
