# Release and Release Notes Publishing Instructions and Operational Report Summary: Workflow Orchestration

## What Data for This Category Looks Like
The core data sources for this category are Git tags, merged commit records, CI build artifacts, and Issue milestones. The update cadence is once per version. Daily produced documents include release notes, change logs, version tags, and release checklists. Common data fields include version number, change type, associated merge request ID, artifact hash value, milestone association number. There are no fixed mandatory units; only version numbers, character counts, and similar information are labeled per industry-standard documentation conventions.

## Constraints Imposed on Workflow Orchestration by These Characteristics
Since data sources rely on code repositories and CI tools, the workflow must connect to the corresponding system’s APIs to pull data, and adapt to the once-per-version trigger cadence. Change categorization, breaking change descriptions, and release artifact verification are the most time-consuming steps, requiring the workflow to set classification nodes and verification nodes. There are no fixed mandatory units for data fields, so the orchestration must bind the format rules of the corresponding documents. Failures may cause user upgrade failures, version rollbacks, or community misunderstandings, so failure retry and notification nodes must be configured.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Bind Git repository version tags, merge records, and artifact hash variables | Matches the data sources and document fields of this category |
| `nodeId` | Set as the unique identifier of the change classification node | Accurately locates classification processing links in the workflow |
| Knowledge Base Selection Node | Bind the Release Notes knowledge base for the corresponding version | Adapts to the storage and calling logic of category documents |
| Change Type Classification Rules | Classify by breaking changes, feature updates, and bug fixes | Matches the categorization needs of daily change logs |
| Failure Retry Count | 2 times | Balances release efficiency and fault tolerance |
| Timeout Threshold | 300 seconds | Adapts to the typical time required for CI artifact pulling |

## Three Common Configuration Errors
- The symptom is the document parsing node returning "target file not found", caused by failing to bind the Git repository change log file path to the `variables` parameter.
- The symptom is no user-selectable knowledge base entry in the workflow, caused by failing to configure a preset knowledge base list variable in `variables`.
- The symptom is the SQL execution node returning "invalid parameter format" error, caused by failing to perform format verification and escape processing on SQL parameters passed via `variables`.

## How to Verify a Complete Configuration
- Trigger the test version workflow of FastGPT v4.17.0, confirm that the node logs successfully pull Git tags and merge record data.
- Manually trigger the knowledge base selection node, confirm that the preset Release Notes-related knowledge bases can be selected.
- Pass test SQL variables, confirm that the execution node shows no parameter error prompts.
- Simulate a node execution failure scenario, confirm that the workflow triggers the configured number of retries.
