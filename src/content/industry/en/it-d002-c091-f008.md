# Publishing Instructions and Operation Report Summary for Player Customer Service and Public Opinion Processing: Workflow Orchestration

## What the data for this category looks like
Core data for this category comes from customer service system tickets, community forum posts, app store reviews, and in-game behavior logs. Most updates occur on a daily basis or in real time. Daily processed documents include player feedback tickets, compensation application forms, daily public opinion summary tables, and standardized response script libraries.
Data fields typically include unique ID, player account information, feedback content, processing status, and associated game server information. Different data sources have varying formats, so adaptive parsing is required based on actual access sources.

## What constraints do these characteristics impose on the workflow orchestration link?
Multi-source heterogeneous data sources require workflows to support multi-channel data access nodes, adapting to input content in different formats. Real-time updated public opinion data requires workflow nodes to have low-latency execution capabilities, to avoid delaying the processing timing of negative feedback.
Diverse document structures require workflows to have built-in flexible field mapping nodes to achieve unified format conversion for different data sources. Time-consuming account verification and compensation judgment links need to embed independent verification nodes in the workflow to avoid invalid process execution. Failure branches must also be configured to prevent process interruptions caused by exceptions.

## Configuration guidelines
This configuration is formulated based on the FastGPT v4.17.0 workflow orchestration interface.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Question Classification Node AI Model | Use a preset model fine-tuned for customer service scenarios | Adapts to the semantic characteristics of colloquial player feedback, improving classification accuracy |
| `variables` global variable binding | Bind ticket ID, player account, game server identifier | Enables cross-node business context association, facilitating subsequent tracing and statistics |
| Text Extraction Node Output Format | Force JSON format | Meets parameter reading requirements of subsequent compensation judgment and public opinion statistics nodes |
| Global History Record Storage Count | Retain the first 20 interaction records | Covers the complete context of a single customer service session, avoiding information loss |
| Node Failure Retry Count | 3 times | Balances abnormal handling costs and task execution success rate |
| `nodeId` node identifier configuration | Configure a unique identifier for each business node | Facilitates log troubleshooting and precise control of process branches |

## Three common misconfigurations
1. When creating a new question classification node using an initialized AI model, an error occurs during running or saving. The issue resolves after switching the model. The cause is that the initialized model is not adapted to player customer service scenarios, and cannot accurately recognize specific semantics for ticket classification.
2. The workflow text extraction node returns an empty JSON result. The cause is that the forced JSON output configuration is not enabled, or the input text has no valid fields matching the extraction rules, resulting in no matching content for the extraction logic.
3. The specified reply component output does not appear in the global history record. The cause is that the output of this component is not bound to the `variables` global variable pool, or the history record storage threshold is set too low to cover the output content of this node.

## How to verify correct configuration
- Import a test player ticket, run the workflow, and check if the output of the question classification node matches the preset feedback type tags.
- View the execution log of the text extraction node, confirm that the returned content is a JSON structure that meets the format requirements, with no null values or abnormal characters.
- Open the global history record panel, confirm that the output of the specified reply component has been fully included, and contains the complete interaction context.
- Simulate a node trigger exception, check if the system automatically executes the preset retry or manual transfer branch process, verifying that the failure handling logic is active.
