# Release Notes and Operation Report Summary for On-Site Deployment: HTTP Interfaces and External Systems

## What the data for this category looks like
Data for this category primarily comes from customer on-site computer room environments, equipment lists, deployment software packages, and network topology diagrams. The update cadence follows each implementation order or phase delivery milestone. Daily produced documents include deployment manuals, installation records, configuration lists, and on-site check-in sheets. Data fields include equipment numbers, software versions, configuration parameters, implementation times, and customer on-site network segments. There are no uniform mandatory units, and some fields need adjustment based on actual on-site environment conditions.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Data sources are scattered and dependent on customer on-site environments. This requires interfaces to support cross-network segment access configurations to prevent call failures caused by customer network isolation. The update cadence changes with implementation orders, so interfaces must support dynamic adaptation to parameter formats for different projects, without requiring fixed templates. Document structures include multiple types of on-site records, so interfaces need to support batch submission of multiple fields and single-item queries, while also supporting data synchronization triggered by implementation phases. The non-standardized nature of on-site data requires interfaces to provide flexible field mapping configurations to adapt to the record formats of different customers. This page is written based on the interface specifications of FastGPT v4.17.0.

## Three Common Mistakes
- The callback interface’s returned `responseData` does not include fields for the large model’s thinking process. This occurs because the full response field switch was not enabled in the interface configuration, and only basic conversation results are returned.
- A 400 Bad Request status code is returned when calling the API to upload documents. This occurs because document metadata was submitted in a format that does not match the field rules defined in the deployment manual.
- A 404 Not Found status code is returned when calling the API to delete collection data. This occurs because the correct collection identification parameter was not included, or the collection was removed during a prior deployment.

## How to Confirm Proper Configuration
- Call the test interface and check if the returned `responseData` fields include deployment status and custom variables configured on-site
- Review interface authentication logs to confirm that the `Authorization` parameter format meets authentication requirements
- Simulate on-site data submission and verify that the returned results match the field rules in the deployment manual
- Trigger a batch synchronization test to confirm that the interface does not throw format errors when submitting multiple fields
