# Release Notes and Operations Report Summary for On-Site Deployment Implementation: Scheduled Tasks and Automation

## What the data for this category looks like
On-site deployment implementation business data primarily comes from raw materials collected on-site such as customer computer room environments, device lists, software packages, and network topologies. Daily associated documents include deployment manuals, installation records, configuration lists, and on-site check-in forms. Data updates trigger once per project or each implementation phase. Core fields include deployment node number, software version number, configuration parameter values, execution timestamp, on-site check-in person identifier, and others. No unified fixed cross-project fields exist, and adjustments must be made dynamically based on the customer’s on-site environment.

## What constraints these characteristics impose on the scheduled tasks and automation link
The data source for this category relies on customer on-site environments, so scheduled tasks must strictly isolate customer sensitive data to avoid unauthorized access. The data update frequency is once per project or phase, requiring task cycles to match the implementation rhythm, and excessively short trigger intervals should not be set. There are many types of daily associated documents and flexible fields, so automated processes must support dynamic mapping of document fields. The most time-consuming environment checks and software installation and configuration links account for a high proportion, requiring tasks to support step-by-step execution to avoid single-task timeouts. Errors can easily lead to system unavailability or project delay, so a complete failure alert and retry mechanism must be configured.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Task trigger cycle | Follow project phase intervals, such as `every 3 days` or after a single phase is completed | Match the update frequency per project or phase, avoid repeated collection of static customer on-site data |
| Single task execution timeout threshold | `1800 seconds` | Cover the maximum time required for environment checks and software configuration during on-site deployment, adapt to the task execution limit of FastGPT v4.17.0 |
| Task retry count | `2 times` | Address temporary on-site network fluctuations or device response delays, reduce return visit costs |
| Task output archive path | Exclusive directory named by customer project ID | Match the archiving specifications for deployment manuals and installation records, facilitate subsequent traceability |
| Alert trigger delay | Push within `10 minutes` after task failure | Match the business requirement of severe consequences for on-site deployment errors, enable timely response to anomalies |

## Three common mistakes
- Excessively long task execution timeout: The symptom is that the task status shows `execution timed out`, and the log returns `504 Gateway Timeout`. The cause is failing to split long on-site environment check and software installation tasks into sub-steps, and failing to set a reasonable timeout threshold.
- Scheduled task repeated execution: The symptom is multiple operation reports generated for the same deployment record, with duplicate execution timestamps in the fields. The cause is failing to configure a task deduplication identifier or setting overlapping trigger cycles, and failing to bind the project unique ID as the execution basis.
- Missing task output fields: The symptom is that the generated release notes lack device list content. The cause is failing to associate the data source of the customer's on-site device list, and failing to verify the mapping relationship between document fields and task outputs.

## How to confirm the configuration is correct
- Manually trigger a test task, verify that the output documents include the corresponding fields from deployment manuals and installation records, and confirm the archive path is correct.
- View the task execution log, confirm that the timeout threshold and retry count match the configured settings, and verify the delay time for triggering alerts after a failure.
- Simulate a matching project phase to trigger a task, confirm that the task only executes once with no repeated execution.
- Check the task trigger rules, confirm that the task only triggers during the specified project phase or interval cycle, and no false triggers have occurred.
