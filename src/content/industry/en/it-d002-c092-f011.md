# Release Notes and Operation Report Summary for On-Site Deployment Implementation: Database and Operations

## What Data for This Category Looks Like
Data for this category comes primarily from first-hand on-site deployment outputs and customer environment materials. Core daily documentation includes four types: deployment manuals, installation records, configuration lists, and on-site check-in forms. Data sources include customer computer room environment parameters, on-site device lists, deployment software packages, and on-site network topology diagrams. Updates follow per-order or per-deployment-phase cycles. Each completed segment triggers synchronized updates to matching documents and records. Fields include deployment environment identifiers, software version numbers, configuration parameter snapshots, and on-site issue logs. No fixed standardized units apply; values adjust based on customer environments and project requirements.

## What Constraints These Characteristics Impose on the Database and Operations Link
Scattered, dynamically updated data per project creates specific requirements. The database layer must support on-demand access to environment parameters and deployment records from different customers, and prevent cross-project data mixing. High-frequency updates per order or phase demand flexible database connection configuration adjustments. Core services do not require restarts to adapt to new deployment segments. Storage needs for multiple document and log types require the database to reserve sufficient field expansion space, to support custom configuration requirements across different customers. The time-intensive nature of on-site troubleshooting requires the operations layer to quickly identify issues such as database connection abnormalities and mismatched configuration parameters. This reduces the cost of on-site return visits.

## How to Configure Settings
This configuration guidance applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale for This Setting |
| ---- | ---- | ---- |
| `MONGODB_URI` | Full connection string containing the customer computer room network segment, port number, and authentication information | Adapts to the scattered customer computer room environments of this category, supports independent database connections across projects, and prevents data interference |
| `PG_URL` | Connection address pointing to a dedicated PostgreSQL instance for the deployment phase, with a dedicated database name configured | Stores structured documents such as deployment manuals and configuration lists, isolating them from unstructured deployment record data |
| `DB_MAX_LINK` | 10–15 | Matches the concurrent operation volume of single-project on-site deployments in this category, avoiding excessive connections occupying customer computer room database resources |
| `REDIS_URL` | Points to the in-container Redis instance for local deployments, and points to a dedicated cache node in the customer computer room for remote deployments | Caches on-site check-in records and temporary configuration snapshots, adapting to high-frequency updated data storage needs |

## Three Common Configuration Errors
- A database connection timeout error with 503 status code appears after container startup. The root cause is that `MONGODB_URI` is not set to a network address accessible from the customer computer room. This prevents the on-site deployment environment from connecting to the preset remote database.
- A field missing exception occurs during deployment record import. The root cause is that the table structure matching the configuration list was not pre-created in the database pointed to by `PG_URL`. This prevents structured documents from being written normally.
- Cache data expires too quickly, and temporary configuration snapshots are lost during on-site troubleshooting. The root cause is that the Redis cache duration was not adjusted to match the single-project deployment cycle. This causes snapshots to be cleared prematurely.

## How to Confirm Configurations Are Correct
- Run a database connection test script in the on-site deployment environment. Verify connectivity for `MONGODB_URI` and `PG_URL`, and confirm no authentication or network blocking issues exist.
- Import a standard deployment manual template, and check whether it writes successfully to the specified database. Confirm field mapping has no abnormalities.
- Review the Redis cache node connection logs, and confirm the instance configured via `REDIS_URL` accepts cache write requests normally.
- After adjusting the `DB_MAX_LINK` parameter, simulate concurrent deployment record write operations from multiple devices. Confirm no connection overflow errors occur.

The values provided here are common starting points, and should be evaluated against the reader’s own samples.
