# Release Notes and Operation Report Summary for Community Report Handling: Context and Token

## What the data for this category looks like
Core data for community report handling comes from report systems, content details, user historical records, and review rules. Update cycles fall into two categories: real-time and daily. Regularly produced documents include report tickets, processing records, appeal forms, and user notification templates. Each document contains fields such as ticket ID, report content, user identifier, processing status, and violation type. The smallest processing unit is a single ticket. There is no fixed format for unified aggregated statistics.

## What constraints these characteristics impose on the "context and token" link
Community report handling uses a single ticket as the core processing unit. Context must link historical report records, user behavior, and the latest review rules. Data volume changes in real time with the number of tickets. If the total context length exceeds the model limit, key report evidence or historical records will be truncated, harming judgment accuracy. The `maxContext` parameter must be properly configured to control total length. Real-time updated review rules require prompt loading. An unreasonable caching mechanism will cause context to reference outdated rules. For appeal forms, context must link the original report and processing records. Relevant content must be accurately recalled to avoid irrelevant data occupying excessive tokens and reducing response efficiency.

## How to configure settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `maxContext` | Total context associated with a single ticket does not exceed 6000 tokens | The context for community reports mostly consists of historical records and review rules linked to a single ticket. Controlling length prevents exceeding the model's context limit |
| `quoteMaxToken` | No more than 4 violation content fragments recalled per single retrieval | Core evidence for report handling is a single piece of violation content. Excessive references will occupy too many tokens and reduce response efficiency |
| Maximum response tokens | Output disposal suggestions do not exceed 1500 tokens | Content such as disposal result notifications and review opinions does not need to be lengthy. Limiting length ensures readability and interface response speed |
| Context recall scope | Only recall user historical records from the past 30 days | Community reports have strong timeliness. Older data has limited reference value for current processing. Narrowing the scope reduces token usage |
| Context filtering rules | Filter duplicate report records and invalid appeal content | Reduces token usage by redundant data and improves context accuracy |

## Three common configuration errors
- Phenomenon: The report processing context content returned by the API call is truncated, and some historical report records are not displayed. Cause: The `maxContext` parameter is not configured correctly. The total incoming context length exceeds the model's supported limit, and the system automatically truncates the excess part.
- Phenomenon: The image output address of violation content in the knowledge base is incomplete, with truncation at the end. Cause: The `quoteMaxToken` parameter is not configured correctly. It cannot accommodate the complete image address and associated violation content description.
- Phenomenon: The generated user notification template exceeds the character limit of the community platform. Cause: The maximum response tokens parameter is set too high, resulting in a longer-than-expected generated text length.

## How to confirm correct configuration
- Import a test report ticket. Check whether the context content loaded by the system includes all linked historical records and review rules, with no obvious truncation.
- Upload violation content containing a complete image address. Verify that the image address in the output result is complete and not truncated.
- Call the test API. Check whether the length of the returned disposal suggestion text meets expectations, with no excessively long or short content.
- After adjusting the `maxContext` parameter, observe whether context overflow error prompts appear in the system logs to confirm that the parameter takes effect.

The values provided here are common starting points and should be evaluated against the reader's own samples.
