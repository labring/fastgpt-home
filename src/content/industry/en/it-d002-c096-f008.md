# Release Notes and Operation Report Summary for Community Complaint Handling: Workflow Orchestration

## What the data for this category looks like
Core data for this category centers on complaint ticket generation. Daily documents include complaint tickets, processing records, appeal forms, and user notification templates. Complaint tickets contain fields such as complaint ID, reported content link, complaint type, and submitting user ID. Processing records are linked to ticket IDs, and record the reviewer, review result, and disposal measures for each ticket. Appeal forms are bound to corresponding ticket IDs, and include appeal reasons and supporting evidence. Data sources include the community complaint system, reported content details, user historical records, and review rules. Update frequency is real-time or daily summary. Fields and units are adjusted according to community operation rules. The core associated field is the unique ticket ID.

## What constraints these characteristics impose on the "workflow orchestration" link
Real-time updates for ticket-type data require workflows to trigger per individual ticket, to avoid parameter misalignment caused by batch processing. The document structure linked to ticket IDs requires workflows to pass the ticket ID in `variables` as a global parameter, to ensure consistent data binding across all nodes. Review rules come from external systems, so nodes must be configured to call rule interfaces, and a retry mechanism must be set for timeouts. The most time-consuming steps of complaint validity judgment and violation evidence extraction require sufficient execution time to be reserved, and an exception alert must be triggered on failure. Appeal rollback paths must be configured in the workflow to address error consequences, and avoid escalation of community conflicts.

## How to set the configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | `{"ticketId": "complaint ticket ID", "reportContent": "reported content link"}` | Binds the unique ticket identifier, complies with FastGPT v4.17.0 global parameter passing rules |
| Global variable assignment | Dynamically pull complaint details by ticket ID | Matches real-time updated complaint system data sources |
| Knowledge base retrieval | Top 5 matching results | Controls response duration, fits the concise nature of complaint content |
| `nodeId` | Review node ID | Marks core processing nodes to facilitate log tracing and exception alerts |
| Timeout setting | 600 seconds | Covers the time requirements for review and evidence extraction |
| Retry count | 3 times | Avoids frequent calls consuming system resources |

## Three common configuration mistakes
- Symptom: An error "no matching knowledge base found" is prompted when the workflow calls knowledge base search. Cause: The correct knowledge base associated parameter was not passed in `variables`, and the ticket ID was mistakenly passed as the knowledge base ID.
- Symptom: The AI chat module returns an empty result. Cause: The complaint content in `variables` was not configured as the user question, and the default generic query content was used directly.
- Symptom: Workflow execution times out and terminates. Cause: A reasonable timeout threshold was not set, or the timeout retry node was not configured.

## How to confirm the configuration is complete
- Trigger a test complaint ticket, check the workflow run logs, and confirm that the ticket ID and report content parameters in `variables` have been passed correctly.
- Call the knowledge base retrieval node, verify that the returned results match the current complaint type as expected.
- Simulate a timeout scenario, confirm that the workflow triggers an alert and enters the retry or exception handling branch.
- Check the daily operation report, confirm that the associated fields of processing records and appeal forms have been correctly written into the summary data.
