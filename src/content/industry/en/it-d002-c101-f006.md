# Release Notes and Operation Report Summary for Renewal Health Management: Scheduled Tasks and Automation

## What the data for this category looks like
Data for this category typically comes from CRM systems, product usage statistics, ticket ledgers, and contract management modules. Daily produced documents include customer health reports, renewal forecast sheets, high-risk customer lists, and cross-departmental communication minutes. Data updates follow a weekly or monthly cadence. Each document includes fields such as customer unique identifier, contract cycle milestones, current service consumption status, and renewal status tags. There is no fixed unified unit format. Settings must align with the statistical standards of the corresponding business module.

## Constraints on scheduled tasks and automation
Multi-source data access requires scheduled tasks to pull data across systems. Configure unified data format adaptation rules to avoid data loss from interface format differences. The weekly or monthly update cadence means task trigger cycles should not be too short. Short cycles will create redundant calculations. Different business documents have varying fields. Automated workflows must support custom field mapping rules to adapt to structures of health reports, risk lists, and other documents. The data interpretation and classification link takes significant time. Use automated rules to complete initial risk tag classification and reduce repetitive manual work. Alert actions must match the follow-up rhythm of customer success managers. Avoid sending excessive invalid notifications.

## How to set up the configuration
This configuration is designed for the scheduled task module in FastGPT v4.17.0. The specific parameters are as follows:
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Task trigger cycle | Once per week / Once per month | Matches the weekly or monthly cadence of business data updates to avoid redundant calculations |
| Data source pull range | Last 30 days of CRM and product usage data | Covers the complete renewal risk observation cycle to avoid data loss |
| Task timeout duration | 600 seconds | Avoids occupying system resources for long periods, and aligns with the response times of most business interfaces |
| Risk tag automatic classification rule | Match based on overdue status + usage threshold | Corresponds to the core judgment dimensions of customer health reports |
| Abnormal alert trigger threshold | Overdue amount ≥ 100 yuan / 3 consecutive weeks of declining usage | Based on industry general risk judgment standards, calibrated through actual testing |
| Task failure retry count | 2 times | Avoids task interruption caused by single interface fluctuations, balancing resource usage and success rate |

## Three common configuration errors
- Scheduled tasks only generate summary reports and do not trigger automatic balance control actions. Cause: No data linkage rules are configured. Only data pulling is completed, without binding subsequent automated operations. The logic to automatically stop services upon overdue payment cannot be implemented.
- Task execution times out and is interrupted without triggering the retry mechanism. Cause: No reasonable retry interval and count are set, or the data pull range is too large and exceeds the interface's carrying capacity.
- The workflow is interrupted due to incomplete user interaction and cannot recover automatically. Cause: No timeout automatic skip or rollback mechanism is configured. The workflow relies on manual user triggering of subsequent steps, leading to stagnation.

## How to confirm the configuration is complete
- Manually trigger a scheduled task. Check if the pulled data includes preset fields such as customer unique identifier and contract cycle milestones.
- Simulate an abnormal scenario, such as setting the overdue amount of a test customer to meet the threshold. Confirm if the corresponding risk tag and alert notification are generated.
- View task logs to confirm if the retry mechanism triggers as configured after a failure, with no abnormal error reports.
- Check if generated reports meet preset PDF and structured table format requirements, and can be shared and viewed normally.
