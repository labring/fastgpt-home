# Release Notes and Operations Report Summary for Renewal Health Management: Database and Operations

## What the data for this category looks like
Data is usually sourced from CRM systems, product usage data, ticket statistics ledgers, and contract archives. Update cycles run weekly or monthly. Daily produced documents include customer health reports, renewal forecast sheets, high-risk customer lists, and cross-departmental meeting minutes. Fields cover customer identifiers, contract cycle milestones, usage frequency, response times, renewal intent, and more. There are no fixed standard units. Values adjust based on document type and statistical dimension. Data volume fluctuates with customer scale. Flexible storage expansion and query optimization must be supported.

## What constraints do these characteristics impose on the database and operations link
Multi-source heterogeneous data access requires database configurations compatible with diverse data source formats. Use `MONGODB_URI` and `PG_URL` to connect non-relational and relational data storage respectively. Weekly or monthly batch data synchronization tasks require proper connection pool configuration. The value of `DB_MAX_LINK` must match concurrent processing capabilities. This avoids batch write timeouts or excessive database load. Structured and unstructured storage needs for multiple document types require table structure design that distinguishes data dimensions. This prevents field conflicts and storage chaos. High-priority high-risk customer list data requires separate read/write permission configuration. This prevents accidental modifications that impact renewal decisions. Periodic data updates must include automated validation mechanisms. This ensures data timeliness and accuracy.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---|---|--- |
| `MONGODB_URI` | `mongodb://[username]:[password]@[host]:[port]/[dbname]?authSource=admin` | Adapts to multi-source non-relational data storage requirements. Supports authentication and specified database instances. Compatible with the vector database and business data storage logic of FastGPT v4.17.0 |
| `PG_URL` | `postgresql://[username]:[password]@[host]:[port]/[dbname]` | Used to store structured customer contract, ticket, and other relational data. Complies with standard PostgreSQL connection formats. Meets the needs of associated queries for multi-dimensional data |
| `DB_MAX_LINK` | `20–50` | Matches the concurrent connection requirements of weekly or monthly batch data updates. Prevents excessive connection counts from causing high database load, or insufficient counts from causing synchronization task timeouts and interruptions |
| `REDIS_URL` | `redis://:[password]@[host]:[port]/0` | Used to cache frequently accessed customer health metrics. Reduces repeated database query pressure. Improves the speed of data reading and display |

## Three common configuration mistakes
- Symptom: `MongoDB connection failed`-type errors appear after startup. Customer business data cannot be loaded normally. Cause: Authentication parameters for `MONGODB_URI` are not configured correctly, or the access whitelist for the database instance does not allow the IP address of the deployment node.
- Symptom: Timeout errors occur during weekly batch CRM data synchronization. Synchronization tasks are interrupted. Cause: The `DB_MAX_LINK` configuration value is too low. It cannot support the concurrent connection requirements of batch data writes. This leads to exhaustion of the database connection pool.
- Symptom: Fields in the high-risk customer list are missing or formatted incorrectly. Renewal forecast sheets cannot be generated normally. Cause: Storage structures for relational and non-relational databases are not distinguished. Unstructured meeting minutes are written directly to PostgreSQL tables. This causes field mapping failures.

## How to confirm configurations are correct
- Run the built-in database connection test tool. Verify that `MONGODB_URI` and `PG_URL` configurations can establish normal connections. No authentication, address, or permission issues are present.
- Trigger a manual data synchronization task. Check the synchronization logs. Confirm that the `DB_MAX_LINK` configuration does not trigger connection count limit errors. The synchronization task can complete normally.
- Access the preview interface for customer health reports. Confirm that all configured fields load correctly. No missing data or format abnormalities are present.
- Check Redis cache access logs. Confirm that the `REDIS_URL` configuration can cache frequently accessed metric data normally. No connection timeouts or permission errors are present.

The values listed are common starting points. They should be assessed against individual deployment samples.
