# Release Notes and Operation Report Summary for Account Ban and Appeal Review: Workflow Orchestration

## What this category of data looks like
This category of data mainly comes from risk control systems, audit records, user behavior logs, and report evidence. Daily associated documents include account ban records, appeal submission materials, review opinion documents, and user notification content. The data update rhythm is divided into two categories: real-time and daily updates. Core fields include account unique identifier, violation type tag, appeal submission time, review conclusion, disposal status, and notification receipt number. There is no unified fixed unit, and it changes with the attributes of individual data entries.

## What constraints these characteristics impose on the "workflow orchestration" link
The scattered data sources require that workflow orchestration must configure cross-system data pull nodes. These nodes connect to risk control, audit, and log systems respectively to obtain original information, avoiding the problem that a single node cannot cover all data. The difference in update rhythms requires supporting two startup modes: event-triggered for real-time appeal data, and scheduled-triggered for daily operation summary data. This adapts to processing needs in different scenarios. The structural differences of multiple types of documents require adding format adaptation nodes in the workflow. These nodes parse appeal materials and audit records in different formats, ensuring the integrity of data extraction. At the same time, the consequences of errors such as false bans require adding a verification link. This link checks the matching degree between violation evidence and appeal materials, avoiding invalid process advancement and ensuring the accuracy of account disposal. This configuration is based on FastGPT v4.17.0.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | Real-time event trigger + daily 0:00 scheduled trigger | Adapt to the update rhythm of real-time appeals and daily operation reports |
| `variables` | Include account ID, violation type, appeal submission time, review result. The length of a single variable shall not exceed 800 characters | Unify the core data format for workflow circulation, avoiding processing exceptions caused by overly long fields |
| `nodeId` | Assign unique identifiers to the three data sources: risk control, audit, and log | Facilitate accurate calling of specified data sources in the process |
| Error Handling Timeout Threshold | 300 seconds | Address network delays during cross-system data pulling |
| Retry Count | 2 times | Avoid process interruption caused by a single failed call |
| Output Format | Structured JSON and exportable text format | Match the archiving and viewing needs of daily documents |

## Three common mistakes
- Unable to generate readable text when processing array-format search results in the workflow: No variable parsing node is added to the process, and `array<object>` format data is not converted to structured text.
- Unable to bind HTTP response input parameters when adding MCP services: The input parameter fields are not predefined in `variables`, causing workflow nodes to fail to recognize incoming parameter content.
- The workflow export function cannot be used normally: The storage path of the output node is not configured, or the export permission setting of the workflow is not enabled.

## How to confirm the configuration is complete
- Trigger test: Submit a real-time appeal, check whether the workflow starts automatically and pulls information from the corresponding data source.
- Variable verification: Check whether the fields in `variables` include core data such as account ID and violation type, with no missing or incorrect entries.
- Error handling test: Simulate cross-system call timeout, check whether the workflow triggers the retry mechanism and terminates after reaching the threshold.
- Export test: Manually trigger the workflow, confirm that downloadable operation reports and ban record summary files can be generated.
