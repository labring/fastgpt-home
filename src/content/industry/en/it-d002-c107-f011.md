# Release Notes and Operational Report Summary for Account Ban and Appeal Review: Database and Operations

## What this category of data looks like
Data for this category comes primarily from risk control systems, audit records, user behavior logs, and report evidence. Four types of documents are generated regularly: ban records, appeal materials, review opinions, and user notifications.
Ban records include fields such as account identifier, violation type, and disposal time.
Appeal materials include content such as appeal initiation time and supporting material ID.
Review opinions include information such as review result and reviewer identifier.
Data update rhythms fall into two categories: real-time and daily. Real-time updates correspond to appeal submissions and review operations. Daily updates correspond to aggregated statistics for operational reports.

## What constraints these characteristics impose on database and operations workflows
Data for this category has scattered sources and diverse structures. Multiple external systems must be connected to synchronize data, which places high requirements on database connection stability.
Real-time updates and daily aggregated updates run in parallel. This requires databases to support read-write separation to distribute load.
Storage requirements vary significantly across document types. Unstructured appeal materials and structured review opinions need to use different storage engines.
Data errors can lead to outcomes such as false bans and account reactivation. This requires databases to have transaction consistency guarantee capabilities to avoid data loss or inconsistency.

## How to Configure Settings

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://fastgpt:your_pass@10.0.0.1:27017/ban_db?authSource=admin` | Stores unstructured appeal materials and report evidence, supports flexible document structures |
| `PG_URL` | `postgresql://fastgpt:your_pass@10.0.0.2:5432/audit_db?sslmode=require` | Stores structured ban records, review opinions, and user notifications, guarantees transaction consistency |
| `DB_MAX_LINK` | `150–250` | Adapts to concurrent read-write demands from real-time appeal submissions and daily operational summaries, prevents connection exhaustion |
| `REDIS_URL` | `redis://:your_pass@10.0.0.3:6379/1` | Caches frequently queried account ban statuses, reduces repeated query pressure on databases |
| Database read timeout | `30 seconds` | Adapts to time demands for verifying violation evidence, prevents timeout interruptions to review workflows |
| Application layer concurrency limit | `First 5 requests` | Matches concurrency limit requirements of third-party interfaces, prevents triggering 429 errors |

## Three Common Misconfigurations
- Phenomenon: Unable to create databases after local deployment, with error prompts indicating invalid connection strings. Cause: `MONGODB_URI` or `PG_URL` is not configured properly, and correct database authentication information and access address are not specified.
- Phenomenon: Request latency increases significantly as concurrency rises, with slow return of results. Cause: `DB_MAX_LINK` is not set reasonably, insufficient connection pool capacity causes request queuing, or `REDIS_URL` is not used to cache frequently queried account ban statuses, increasing database load.
- Phenomenon: Direct return of 429 errors after exceeding third-party interface concurrency limits. Cause: Application layer concurrency limits are not configured, and rate limit counting via `REDIS_URL` is not implemented, leading to requests being forwarded directly to third-party interfaces and triggering rate limits.

## How to Verify Configurations Are Correct
- Run database connection test scripts to verify connectivity for `MONGODB_URI` and `PG_URL`, confirm that corresponding data collections and table structures can be created normally.
- Simulate batch appeal submission requests, check the database connection count monitoring dashboard, confirm that the configured value of `DB_MAX_LINK` is not exceeded.
- View the Redis cache monitoring dashboard, confirm that the cache instance configured via `REDIS_URL` normally stores account ban status data.
- After configuring application layer concurrency limits, simulate requests that exceed the limit, confirm that expected rate limit prompts are returned.
