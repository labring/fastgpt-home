# Release Notes and Operational Report Summary for Warranty Defect Response: Scheduled Tasks and Automation

## What Data Looks Like for This Category
Warranty defect response typically centers on defect warranty services after project delivery. Unlike on-site operation and maintenance outsourcing services, data for this category comes primarily from customer-submitted warranty work orders, system operation logs, project contract warranty clauses, and software version update records. Daily circulating documents include standardized warranty work orders, defect confirmation sheets, repair execution records, and customer final confirmation sheets.
Data updates do not follow a fixed unified schedule. Some updates are submitted with individual work orders, while others are aggregated from daily operation logs. Each individual data entry includes core fields such as work order number, defect description, responsibility determination result, repair duration, and customer confirmation status. There are no mandatory fixed field length requirements.

## Constraints Imposed on Scheduled Tasks and Automation
The scattered data sources and inconsistent update schedules for this category require scheduled tasks to support both order-based triggering and scheduled full verification modes. This prevents missed emergency work orders submitted manually.
Daily documents have no mandatory unified field formats. Mandatory field verification rules must be configured in automated workflows to prevent invalid data from entering the summary stage.
The requirement to link data to contract warranty clauses and version records means tasks must complete cross-data source association matching during execution. This increases the execution complexity of individual tasks.
Errors may trigger warranty disputes. Complete failure retry and alert mechanisms must be configured to enable rapid localization and repair when tasks encounter exceptions.

| --- | --- | --- |
| Task Trigger Timing | Order update triggering + daily midnight full verification | Matches data update frequency, covers all warranty work orders submitted manually and generated automatically |
| Task Execution Timeout Threshold | 1200 seconds | Covers execution duration of complex processes such as cross-data source association matching and responsibility boundary determination |
| Result Output Configuration | Only write to operational report storage table, do not return to conversation flow | Prevents execution results of automated tasks from interfering with business conversation scenarios |
| Exception Retry Count | 3 times | Balances computing resource consumption and task success rate, reduces task failures caused by temporary network fluctuations |
| Core Field Verification Rules | Verify work order number and customer confirmation status as mandatory fields | Ensures core information of summarized data is complete, prevents invalid records from entering operational reports |

## Three Common Configuration Mistakes
- Symptom: When a scheduled task calls a generic node, execution results are written to the conversation return flow and cannot be stored separately in the operational report table. Cause: The output target of the node was not configured correctly, and the conversation output channel was bound by default.
- Symptom: After a daily full verification task is executed, some warranty work orders have missing associated contract clause data, resulting in an incomplete summary report. Cause: Cross-data source association verification rules were not configured, and the contract warranty clause matching step was omitted.
- Symptom: Temporary indexes generated after task execution disappear after node restart, making it impossible to generate historical operational reports. Cause: Index persistent storage was not configured, and temporary indexes are only stored in node memory.

## How to Confirm Configuration Is Complete
- Manually submit a test warranty work order, wait for the order-based scheduled task to trigger, and check whether the corresponding record is generated in the operational report storage table.
- View task execution logs to confirm that the timeout threshold and retry count configurations have taken effect, and there are no parameter mismatch error messages.
- Simulate a field missing exception scenario by submitting a test work order without a customer confirmation status, and check whether the retry mechanism is triggered and an exception alert is generated.
- Wait for the next day’s midnight full verification task to complete, compare system logs and operational reports to confirm that all work order data updated on that day has been correctly summarized.
