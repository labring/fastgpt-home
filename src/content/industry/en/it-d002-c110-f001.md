# Release Notes and Operation Report Summary for On-site Outsourced Operations Services: HTTP Interfaces and External Systems

## What the Data for This Category Looks Like
Operational and release data for on-site outsourced operations services typically originates from customer ITSM systems, on-site monitoring platforms, asset inventory ledgers, and duty logs.
Documents generated daily include on-site daily reports, service desk ticket records, monthly inspection reports, and SLA summary monthly reports.
Common data fields include on-site staff identifiers, ticket numbers, completed inspection items, service response durations, and statistical business fields.
Update cycles are primarily daily and monthly.
Daily data comes from that day’s on-site tickets and duty logs.
Monthly data integrates full-cycle inspection, ticket, and response data.

## What Constraints These Characteristics Impose on HTTP Interfaces and External Systems
The data characteristics of this category create multiple constraints for HTTP interfaces and external systems.
First, data sources are dispersed. Connections must be made to multiple external systems including customer ITSM and monitoring platforms. Different systems use distinct authentication rules and return formats. Interface configurations must support pulling data from multiple sources and converting formats.
Second, update cycles are divided into daily and monthly. Interface call frequency must align with the data update cycle. This prevents excessive calls from triggering system rate limits. It also avoids missing incremental data due to too infrequent calls.
Third, daily documents include multiple structured and semi-structured contents. Interfaces must support precise extraction and mapping of specified fields. They must also accommodate abnormal field formats returned by some systems.
Fourth, data is linked to service contract fulfillment. The accuracy of interface returns directly impacts subsequent statistics and delivery. A complete exception handling mechanism must be configured.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${pre-configured customer service secret}` | Adapts to standard authentication rules for most customer ITSM and monitoring platforms. Ensures legitimacy of interface calls |
| `variables` | `{"doc_types": ["daily_report", "work_order", "inspection_report", "sla_monthly"], "update_cycle": ["daily", "monthly"]}` | Matches the multiple document types and periodic update characteristics of this category. Facilitates interface logic to distinguish different data types and pull schedules |
| `responseData` | Extract `work_order_id, duty_duration, inspection_count`, limit to returning the first 1000 entries | Accurately retrieves core business fields required for on-site services. Filters redundant data to improve interface efficiency |
| Single call timeout | 600 seconds | Accommodates potential network delays when pulling on-site data. Prevents data pull failures due to timeouts |
| Failed retry count | 3 times | Addresses temporary network fluctuations or short-term unavailability of external systems. Reduces missed data pulls |
| Incremental sync switch | Enabled | Matches the periodic update characteristics of this category. Only pulls newly added or modified data. Reduces interface call load |

## Three Common Configuration Mistakes
- Symptom: After calling an external system interface, the Set-Cookie field cannot be extracted from the returned HTTP response. This causes subsequent interface authentication failures. Cause: Cookie persistence is not enabled in the HTTP request configuration, or the Set-Cookie field is not specified for extraction via `responseData`.
- Symptom: Interface calls return 401 or 403 status codes. Normal data acquisition fails even after multiple retries. Cause: The `Authorization` parameter is not configured correctly. An expired or unauthorized secret is used. The authentication format for the target system is not adapted.
- Symptom: Daily inspection record content is missing from pulled on-site service data. Cause: The data source identifier for inspection reports is not configured in `variables`. This causes the interface to not pull document data of the corresponding type.

## How to Confirm Configuration is Complete
- On the interface debugging page of FastGPT v4.17.0, manually trigger an interface call. Check if the returned results include the configured core business fields.
- Check the configuration format of the `Authorization` parameter. Confirm it matches the authentication requirements of the target external system. A system-provided test interface can be used to verify authentication validity.
- Simulate a data update cycle. Check if the system only pulls newly added or modified data. Confirm the incremental sync switch configuration is active.
- Trigger an interface call failure scenario. Confirm the system automatically retries according to the configured failed retry count. Normal data returns after retries.
