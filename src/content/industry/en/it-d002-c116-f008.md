# Release Notes and Operational Report Summary for Project Document Handover Archiving: Workflow Orchestration

## What data for this category looks like
The data for this category primarily originates from project document libraries, configuration lists, meeting minutes, and test reports. The update cadence aligns with the end of each project phase or when the overall project is delivered. Daily produced documents include completion documents, configuration manuals, training records, and acceptance certificates. Common data fields include document version number, associated project identifier, signature status, handover date, and others. There is no unified mandatory format, and requirements must match the client’s archiving specifications.

## What constraints do these characteristics impose on the workflow orchestration link
This category of data is not updated in real time. The workflow must support execution triggered by project phase nodes or manually, to adapt to the phased delivery rhythm. Diverse document types with no unified format require the workflow to support parsing and verification logic for multiple file types. Fields require custom mapping, and support must be provided for configuring verification rules for custom fields such as associated project identifier and signature status. Additionally, as document integrity checks and version verification are core time-consuming steps, the workflow must embed automatic verification nodes to reduce repetitive manual operations.

## How to configure settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Condition | Trigger by project phase node, or manually trigger | Adapt to the rhythm of this category updating data at phase or project completion |
| `variables` | Configure associated project ID and document version number as global variables | Match the core associated fields of this category’s data, simplify cross-node data transfer |
| `nodeId` | Assign unique identifiers to file verification and version verification nodes | Facilitate locating execution status and exception logs for each link in the workflow |
| File Verification Rules | Verify the existence of required files such as completion documents and acceptance certificates; single file parsing timeout of 120 seconds | Cover the core types of daily documents for this category, ensure handover integrity |
| Loop Execution Logic | Cycle verification for document groups that fail verification, retry up to 3 times with a 60-second interval between each attempt | Adapt to the repeated adjustment needs of document verification, avoid process interruption caused by single verification failure |
| Exception Notification Configuration | Push verification failure notifications to the designated project team, retry failed verification tasks after a 600-second delay | Synchronize exception information in a timely manner, ensure process advancement efficiency |

## Three common misconfigurations
- Symptom: The link returned by the image upload node in the workflow uses an IP plus port format, and cannot use a custom domain name. Cause: No domain name replacement rule was configured in global variables, and the base URL of the upload path was not replaced with the custom domain name.
- Symptom: An error indicating that the `$schema` field is undefined appears after the workflow runs. Cause: No mapping relationship for this field was declared in the `variables` configuration, causing nodes to fail to recognize custom archiving fields.
- Symptom: The loop execution node cannot terminate the process based on verification results, leading to repeated execution beyond the preset number of times. Cause: No judgment condition for loop termination was configured, and the verification passed status was not used as the trigger identifier for loop end.

## How to confirm configuration is complete
- Manually trigger the workflow once. Verify that the process starts according to the preset project phase nodes, and confirm that the trigger logic takes effect.
- Upload a batch of test files including completion documents and acceptance certificates. Verify that the file verification rules correctly identify and verify required files, and confirm that the verification logic covers core document types.
- Simulate a verification failure scenario. Verify that the loop execution logic retries according to the preset rules, and confirm that exception notifications are correctly pushed to the designated recipients.
- View the workflow’s node logs. Confirm that the `variables` and `nodeId` parameters are transferred normally, with no missing fields or identifier conflict errors.
