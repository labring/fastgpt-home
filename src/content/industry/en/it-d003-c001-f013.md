# Security and Compliance Material Review for CDN and Edge Acceleration Configuration: Permissions and Data Isolation

## What this category of data looks like
This category of data primarily comes from CDN consoles, DNS resolution records, edge node access logs, and monitoring alert systems. Data syncs daily or immediately after configuration changes. Daily operation documents include domain name access approval forms, cache rule configuration tables, refresh and preload operation logs, and node fault troubleshooting reports. Data fields include domain names, cache rule versions, node IP ranges, traffic peaks (unit: Mbps), filing status, and more. Data scope is divided only by business scenario, with no fixed unified statistical caliber.

## What constraints these characteristics impose on the Permissions and Data Isolation link
Because data sources cover multiple systems including console configurations, DNS resolution, and access logs, isolate different source data by team identifiers to prevent cross-team access to sensitive configurations. Process data updates at high frequency, so enforce immediate effect for permission changes to block unauthorized members from modifying active cache rules. Restrict document viewing and modification permissions by role for daily operation documents involving core operations such as domain name filing and node troubleshooting, to prevent misoperations that cause domain name access failures or cache disorder. Additionally, CDN delivers public network content distribution, so store data including sensitive information such as node IPs and traffic details in encrypted form, and restrict access by unauthorized members. This configuration guide applies to FastGPT v4.17.0.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` binding configuration | Associate each CDN domain name and cache rule with the corresponding `teamId`, and only open access to members under that `teamId` | Matches the business logic of dividing CDN configurations by team ownership, preventing cross-team resource access |
| `tmbId` permission control | Assign a unique `tmbId` to each member, and restrict operation permissions by role (for example, only allow operation staff to modify cache rules) | Implements fine-grained member operation permission isolation, meeting the role division requirements of CDN operations |
| Refresh and preload concurrency limit | Set to `50–100 concurrency`, requests exceeding the threshold will be rate-limited | Avoids exceeding the processing capacity of CDN nodes, preventing node overload caused by configuration changes |
| Operation log retention period | Set the retention period to `30–90 days`, only allow `teamId` administrators to view full logs | Meets log retention requirements for compliance reviews, while restricting access to operation records by unauthorized members |
| Cache rule activation delay | Set to `10–30 seconds`, retain the original configuration during the delay period | Prevents business interruptions caused by configuration changes, reserving a rollback window for operation staff |

## Three Common Misconfigurations
- Symptom: Members across `teamId`s access another team’s CDN cache rules, receiving a `403 Forbidden` error, while some unauthorized members can still view configurations. Cause: Cache rules are not bound to the corresponding `teamId`, and the permission verification logic does not correctly associate team identifiers.
- Symptom: When an application calls CDN configuration-related APIs, it returns no matching content, and cross-team knowledge base data is returned incorrectly. Cause: Data scope is not filtered by `tmbId`, and cross-team data is not properly isolated.
- Symptom: After modifying the filing configuration of a CDN domain name, the configuration does not take effect and is overwritten by another team’s configuration. Cause: `teamId`-level configuration locking is not enabled, and non-team members are not restricted from modifying the configuration of the corresponding domain name.

## How to Verify Successful Configuration
- A non-team member account logs in, and access to the target team’s CDN domain name configuration list is confirmed to be unavailable.
- The CDN configuration query API is called with the specified `teamId` parameter, and only configuration data for that team is confirmed to be returned.
- A cache rule modification request is submitted using a non-team `tmbId`, and the request is confirmed to be blocked.
- Operation logs are viewed, and access to sensitive access logs and monitoring alert data is confirmed to be restricted to authorized members only.

The values provided are common starting points and should be measured against the reader's own samples.
