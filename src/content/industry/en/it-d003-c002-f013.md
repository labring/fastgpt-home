# Security and Compliance Material Review for IT Service Desk Ticket Processing: Permission and Data Isolation

## What the data for this use case looks like
This category of data includes four core document types: service request forms, incident tickets, processing records, and user satisfaction surveys. Data sources cover ITSM systems, phone or online chat logs, asset systems, and internal knowledge bases. Data updates occur daily or in real time. Core fields include unique ticket identifiers, requester identity identifiers, assignee information, problem classification tags, processing status, satisfaction scores, and more. The size of individual data records is tied to business scenarios, with no fixed standardized field unit requirements.

## What constraints do these characteristics impose on permission and data isolation
The data characteristics of this use case impose multiple constraints on permission and data isolation. Mixed multi-source data must cover access scopes for different data sources such as ITSM, chat logs, and asset systems, to prevent unauthorized personnel from viewing sensitive hardware information linked to asset systems. Real-time updated ticket data requires permission verification logic to take effect synchronously; batch offline verification alone cannot cover all real-time ticket scenarios. Tickets are bound to identity fields such as requester and assignee, so permission isolation must match multi-role access boundaries, allowing only corresponding roles to view tickets associated with them. User satisfaction surveys contain undisclosed employee evaluation information, so separate isolation rules must be set to prevent non-management roles from accessing data beyond their authority. Additionally, tickets from different teams must be isolated by the `teamId` dimension to prevent cross-team data leaks.

## How to configure
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Team permission isolation rules | Bind role permissions by `teamId` | Match the team-based ticket attribution of IT service desks to enable cross-team data isolation |
| Role access scope | Restrict to ticket data associated with the user | Implement precise permission control based on the requester and assignee fields of tickets |
| Sensitive data access toggle | Disable asset system data access for unauthorized roles | Prevent leakage of sensitive hardware information in asset systems |
| Real-time data verification cycle | 10–30 seconds | Adapt to the daily or real-time update rhythm of ticket data |
| Global variable isolation rules | Distinguish scopes by `tmbId` | Meet the requirement of isolating same-named global variables across different user IDs |
| Maximum single ticket data display count | Top 20 entries | Adapt to the conventional display requirements of IT service desk ticket lists |
| Single Sign-On (SSO) configuration | Only available to commercial edition authorized users | Comply with compliance requirements for internal enterprise identity authentication |

## Three common configuration errors
- Phenomenon: Non-commercial edition users configuring the SSO function see a prompt that the function is not available, and cannot save the configuration. Cause: The SSO function is only available to commercial edition authorized users; unauthorized editions cannot enable this configuration.
- Phenomenon: When different users call the same-named global variable, they return values that do not belong to them, resulting in data cross-talk. Cause: Global variable scope isolation rules were not configured by `tmbId`, causing different users to share variable storage space.
- Phenomenon: After switching teams, the team data obtained by calling the tokenLogin interface does not update, and the interface still displays the ticket list of the old team. Cause: The real-time storage update logic for team data was not configured, and cached team permission information was not refreshed synchronously.

## How to confirm the configuration is correct
- Submit a test ticket, log in with an unauthorized role account, and attempt to view ticket data not associated with the user. Confirm that access is denied.
- After configuring the global variable isolation rules, use two accounts with different user IDs to call the same-named global variable separately. Confirm that the returned values do not affect each other.
- After switching teams, call the tokenLogin interface. Confirm that the returned team data matches the currently logged-in team information.
- Attempt to configure the SSO function in a non-commercial edition environment. Confirm that the interface prompts that the function is not available, and the configuration cannot be saved.
