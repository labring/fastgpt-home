# Security and Compliance Material Review for IT Procurement and Supplier Management: Model Access and Configuration

## What data looks like for this category
Daily documents for this category include procurement requests, price comparison records, contracts, and acceptance documents. Data primarily comes from procurement systems, supplier quotation files, budget spreadsheets, and contract systems. Data updates follow individual procurement workflows: updates are completed when a single purchase order is finalized. Monthly summary data updates follow natural calendar cycles. Document structures include fields such as purchasing entity, amount range, supplier qualifications, and clause details. No uniform mandatory units exist. Some fields must be adapted based on internal enterprise procurement rules.

## What constraints these characteristics impose on model access and configuration
Differences in data formats across multiple sources require adapting parsing rules for different files during model access, to avoid losing critical compliance information due to format incompatibility. The update rhythm of single purchase orders means model context does not need to be overly long. Limiting the `maxContext` range improves call efficiency. Core fields such as compliance clauses and amount verification in documents require high consistency in model output. Parameters must be strictly controlled to reduce excessive randomness. Errors in the procurement process directly relate to enterprise compliance risks. Model configuration must prioritize output accuracy and compliance.

## How to set configurations
| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Matches the average length of procurement and contract documents, prevents truncation of critical compliance clauses |
| `maxTokens` | 2000–3000 token | Meets output length requirements for procurement approval and compliance review, prevents incomplete output |
| `temperature` | 0.2–0.4 | Reduces output randomness, ensures consistency for compliance clause verification and amount calculation |
| `toolChoice` | auto | Calls compliance verification tools as needed, adapts to procurement scenarios requiring cross-document verification |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, for example http://aiproxy:3000. Do not append /v1 or /chat/completions paths. Do not configure as single-model service addresses such as VLLM/Ollama/Xinference | Ensures normal model call connectivity, prevents connection failures |
| `AIPROXY_API_TOKEN` | AI Proxy administrator token, consistent with AI Proxy server configuration and not empty | Ensures model call permissions and data transmission security |

## Three common configuration mistakes
- Error "No language model configured" when entering the workspace edit page: The cause is that mandatory `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` environment variables are not configured on the App/Admin server, causing service startup verification to fail.
- Large discrepancy between online chat and API call return results: The cause is that the `temperature` parameter is not uniformly configured, and `maxContext` and `maxTokens` are not explicitly specified during API calls, leading to inconsistent context processing logic across different call chains.
- Doubao 1.6 model outputs thinking content but no main text: The cause is that `maxTokens` is set too low, resulting in truncation of main content, or `toolChoice` is configured to force tool calls, causing abnormal output flow.

## How to confirm successful configuration
- Verify that the App/Admin server has configured `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` environment variables, and that configuration values meet official requirements.
- After configuring `temperature`, `maxContext`, and `maxTokens` parameters, import a single procurement request document for testing, and verify that the output covers all critical compliance fields.
- Initiate online chat and API calls separately, compare their output formats and content completeness, and confirm that parameter configurations are uniform.
- Check system logs to confirm there are no records of model call failures or parameter parsing exceptions.

The values provided are common starting points and should be measured against the reader's own samples.
