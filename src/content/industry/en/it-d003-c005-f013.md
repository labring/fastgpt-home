# Security and Compliance Material Review for Issue Triage and Response: Permission and Data Isolation

## What This Category of Data Looks Like
The typical users of this category are open source maintainers, community operators, and core contributors. Daily processed documents include Issue templates, label rules, response records, and problem reproduction instructions. Data sources are primarily GitHub or Gitee issues, version logs, user environment information, and code repositories. Data update frequency is mostly daily or weekly. Core fields include Issue status, associated labels, creation time, reproduction steps, and responsibility module tags. Issue data associated with different applications is independent of each other, and must match the access permission scope of the corresponding repository.

## Constraints on Permission and Data Isolation
Data sources are bound to external repository permissions, requiring permission configuration to align with repository access permissions to prevent unauthorized users from obtaining cross-repository Issue data. Data includes user environment information and problem reproduction details, involving privacy and compliance requirements, so access to data from different users or teams must be isolated. Data update frequency is daily or weekly, so permission changes must be synchronized with configuration updates to ensure data access permissions match repository permissions. Issue data from different applications must be stored separately by application to avoid cross-application data leakage and ensure traceability for compliance reviews.

## How to Configure Settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---|---|--- |
| Team ID Binding | Bind the corresponding repository's `teamId` | Match the repository permission association of the data source to achieve cross-repository data isolation |
| Member Permission Group Configuration | Assign 1–5 level permissions via `tmbId` | Differentiate the operation scope of maintainers, operators, and visitors to meet team division of labor requirements |
| Non-login Link Limit | 10–100 per application | Match the default limits of subscription plans, support on-demand adjustments |
| Permission Check Timeout | 300 seconds | Ensure response speed of real-time permission checks and avoid long waits |
| Data Storage Isolation | Use independent storage directories divided by application | Prevent cross-application Issue data leakage |
| Operation Log Audit | Enable full operation log recording | Retain access and operation traces required for compliance reviews |

## Three Common Misconfigurations
- Symptom: A 403 error is returned when creating a non-login link, indicating the limit has been exceeded. Cause: The non-login link quantity limit was not adjusted according to the subscription plan; the default configuration only supports 10 links.
- Symptom: Unauthorized members can view Issue data from other teams. Cause: `teamId` and repository permissions were not bound, resulting in failed permission isolation and cross-team data leakage.
- Symptom: Exported conversation content includes Issue data from unrelated applications. Cause: Data storage directories were not divided by application, resulting in cross-storage of data from different applications.

## How to Verify Proper Configuration
- Attempt to access the Issue data of the specified application using an unauthorized member account, confirm that the corresponding content cannot be viewed.
- Create a non-login link, verify that the current limit matches the quantity configured for the subscription plan.
- View the operation log, confirm that all permission changes and data access operations have complete records.
- Export the conversation content of the specified application, confirm that it only includes Issue data associated with that application.

The values provided are common starting points and should be evaluated against the actual deployment’s own test samples.
