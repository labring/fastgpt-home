# Security and Compliance Material Review for Pull Request Reviews: Conversation Logs and Auditing

## What Data Looks Like for This Category
Typical users of this category are project maintainers, module owners, and contributors. Data originates primarily from code repositories, CI pipelines, Issue links, and contributor-submitted content. Daily associated documents include PR descriptions, code review comments, CI execution results, and merge records. Data updates occur daily or weekly on a regular basis. Each individual data entry includes fields such as PR number, submitter information, list of changed files, review interaction records, and merge status. No custom statistical units are used. Only standard code repository fields and timestamps serve as identification markers.

## Constraints for Conversation Logs and Auditing Workflows
Multiple data sources require conversation log auditing to link associated fields from code repositories, CI systems, and Issues. This ensures review interactions can be matched to change content and execution results. Daily or weekly update cycles require audit tasks to aggregate PR batches. This avoids scanning full datasets in a single pass. The binding between daily documents and review interactions requires logs to retain associated indexes for PR descriptions and review comments. This supports backtracking of change intent. Unlike Issue triaging and response, the core of PR review is handling mergeable code changes. Audit logs must therefore focus on change-related interactions. Only review conversations and operation records tied to code change review should be retained. This prevents irrelevant data from interfering with audit results.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind PR number as unique identifier | Ensures each review conversation is strongly linked to its corresponding PR, enabling quick log retrieval by PR dimension |
| `responseChatItemId` | Link to unique ID of review comments | Matches individual interaction records for code reviews, preventing log confusion across different review conversations |
| `detail` | Enable full field display | Includes associated information for changed files and CI results, meeting full-chain traceability requirements for compliance reviews |
| Conversation log retention period | 30–90 days | Matches average PR review processing cycle, balances compliance retention requirements and storage cost control |
| Bulk export limit | Top 100 PR logs | Adapts to daily or weekly update frequency, prevents system performance impact from overloaded single export data |
| Context association threshold | Calibrated via actual testing | Matches the change scope of PR reviews, ensuring accurate binding between logs and corresponding change content |

## Three Common Configuration Mistakes
- When viewing PR review conversation log details, the displayed content does not match actual interaction responses. This occurs when `chatId` is not bound to the PR number, leading to mixed matching of logs from different PRs.
- After configuring the `detail` parameter, logs do not display associated CI results or changed files. This happens when the synchronization switch for associated document indexing is not enabled, leaving logs with only conversation text and missing data required for compliance reviews.
- When attempting to pull full PR conversation logs, the returned result count is insufficient. This is caused by failure to adjust the bulk export limit configuration, which imposes a default restriction on the number of PRs exported per operation.

## How to Verify Successful Configuration
- Search for conversation logs using a specified PR number, confirm the `chatId` field exactly matches the PR number.
- Open the `detail` panel of a single log entry, verify that it includes associated changed files and CI result links.
- Run a bulk export operation, confirm the number of exported entries matches the configured bulk export limit.
- Check the log retention period, confirm that old PR logs older than 30 days have not been accidentally deleted.

The values provided above are common starting points, and should be evaluated against the reader's own samples.
