# Security and Compliance Material Review for SLA and Service Reports: Model Access and Configuration

## What data for this category looks like
This category of data is sourced from monitoring systems, ticket systems, service contracts, and customer communication records. The update frequency is monthly or quarterly. Daily generated documents include SLA clause text, monthly service reports, availability statistics reports, and customer review minutes. Core fields include service cycle duration, SLA compliance item values, abnormal event occurrence times, and customer contract identifiers. Field units include hours, occurrences, days, and others. Compliance review verifies consistency between service performance and contract terms using this data, ensuring content complies with established business rules.

## How these characteristics create constraints for model access and configuration
The dispersed, multi-source nature of this data requires model access configurations to support unified parsing of multi-format data, avoiding extraction errors caused by incompatible input formats. The fixed monthly or quarterly update rhythm requires configuring scheduled model invocation tasks to adapt to fluctuations in data volume within the cycle. Document structures vary significantly, from structured SLA clauses to unstructured review minutes, so context parameters adapted to different text volumes must be configured. At the same time, compliance review requires the model to accurately verify consistency between data and contracts, so semantic alignment accuracy must be maintained to avoid caliber deviations.

| `maxTokens` | 2000–3000 token | Outputs for SLA indicator calculation and abnormal attribution need to carry sufficient details to ensure complete review content |
| `toolChoice` | `auto` | Adapt to the parsing needs of multi-source data, allowing the model to independently choose whether to call data extraction tools |

## Three Common Mistakes
- Service startup verification fails, or model invocation failure errors appear when running workflows. Troubleshooting steps: Verify that `AIPROXY_API_ENDPOINT` or `AIPROXY_API_TOKEN` is not configured or configured incorrectly, or that the token does not match the AI Proxy server configuration.
- After configuring the same model across multiple channels, priority invocation does not trigger as expected. This occurs when channel priority rules are not clearly defined in the model access configuration, or the configuration does not take effect.
- The review result shows that relevant SLA clause information cannot be found, even though the knowledge base semantic retrieval matching rate meets standards. This happens because the `maxContext` configuration value is too small, causing retrieved text to not be fully included in the model context, making matching verification impossible.

## How to Confirm Configuration Is Complete
- Check the environment variable configuration on the App/Admin server, confirm that `AIPROXY_API_ENDPOINT` is the root address of the AI Proxy service, and `AIPROXY_API_TOKEN` is the administrator token consistent with the AI Proxy server configuration.
- Trigger a test task, review the model invocation return results in the workflow log, and confirm that SLA reports and contract text can be parsed normally.
- Adjust the configuration values of `maxContext` and `maxTokens`, and refine to an appropriate range based on context overflow prompts from test tasks.
- Simulate a multi-channel configuration scenario, and verify whether the model invocation selects the corresponding channel according to preset rules.

The values provided are common starting points and should be measured against the reader's own samples.
