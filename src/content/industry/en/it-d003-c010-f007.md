# Security and Compliance Material Review for Incident Response and Troubleshooting: Conversation Logs and Auditing

This document applies to FastGPT v4.17.0. The following content covers conversation logs and auditing configuration for incident response and troubleshooting scenarios.

## What this category of data looks like
Data sources for this category include monitoring alerts, log platforms, APM tools, and user feedback. Update frequency is real-time or after each incident is closed. Core documents include incident tickets, event timelines, emergency response plans, and incident notifications. Data fields include unique incident identifiers, occurrence times, affected service scopes, recovery statuses, operator information, and more. Field units are primarily event-level timestamps, service names, and operation counts. There are no fixed universal statistical units across operation and maintenance categories. All data is generated around a single fault or operation and maintenance event.

## What constraints do these characteristics impose on the conversation logs and auditing workflow?
Dispersed data sources lead to inconsistent log formats across different channels. Unified collection fields are required to ensure consistency of audit records. The real-time or incident-level update frequency requires the audit link to capture conversation interactions immediately to avoid missing key operations. The strong binding between core documents and incidents requires that conversation logs must be associated with the unique identifier of the corresponding incident to facilitate cross-document traceability. Compliance requirements for documents such as incident notifications require audit records to cover full-process operations, ensure every step can be traced, and match the field structure of incident tickets to facilitate subsequent review and verification.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` association rule | Automatically bind to the ticket ID of the current incident | Matches the one-to-one correspondence between incidents and conversations in incident response scenarios, facilitating quick location of corresponding audit records |
| `responseChatItemId` capture scope | Capture all conversation interaction items | Covers the operation trajectory of the entire fault handling process, meeting the complete traceability requirements of compliance audits |
| `detail` log field configuration | Include operation time, operator, execution result | Matches the field structure of incident tickets, facilitating cross-document association and verification |
| Log retention period | 60 days | Adapts to the review cycle of operation and maintenance incidents, meeting basic compliance audit requirements |
| Maximum single log size | 1000 KB | Adapts to the conventional content volume of operation and maintenance logs, avoiding storage overflow |
| Real-time audit trigger | Triggered on conversation submission | Matches the real-time processing rhythm of incident response, ensuring audit records are generated immediately |

## Three common misconfigurations
- Symptom: After deploying via Docker, FastGPT conversation audit logs cannot be viewed. Running the `docker logs` command only returns a small amount of startup information. Cause: Detailed log output configuration is not enabled, or the log storage directory is not correctly mounted to the host machine.
- Symptom: The `detail` field does not include key information such as operator and execution result, resulting in incomplete audit records. Cause: The full collection option for the `detail` field was not checked during configuration, or the field mapping rules were configured incorrectly.
- Symptom: Conversation logs cannot be associated with the corresponding incident ticket, making it impossible to quickly retrieve audit records via the ticket ID. Cause: The automatic binding rule between `chatId` and the ticket ID was not configured, or the ticket ID format does not match the `chatId` format.

## How to confirm the configuration is complete
- Check the association between `chatId` and ticket IDs, confirm that each conversation log is bound to the unique identifier of the corresponding incident, and the identifier format matches the ticket ID format.
- Randomly select a conversation log, confirm that the `detail` field includes preset fields such as operation time, operator, and execution result, and the field content is complete.
- Trigger a fault handling conversation interaction, confirm that the audit record is generated immediately after the interaction is submitted, with no noticeable delay.
- Check the usage of the log storage directory, confirm that the single log size meets the preset configuration requirements, and no storage overflow issues have occurred.
