# Security and Compliance Material Review for Cloud Host Provisioning and Resource Activation: Permissions and Data Isolation

## What the data for this category looks like
This category’s data primarily originates from cloud management platforms, order systems, IAM, and billing systems. Updates occur per individual order or in real time. Daily associated documents include resource activation forms, instance configuration sheets, account permission applications, and delivery confirmation forms. Fields include instance specifications (vCPU cores, memory in GB), deployment regions, IAM role identifiers, billing cycles, resource status, and more. The data structure uses individual resource provisioning workflows as units, with each entry tied to corresponding order, permission application, and delivery confirmation records.

## What constraints do these characteristics create for the permissions and data isolation process
Data from multiple systems requires permission checks to cover the full cloud management, order, IAM, and billing workflows. This prevents cross-module privilege escalation caused by permission vulnerabilities in a single system.
Real-time or per-order update characteristics require isolation configurations to take effect immediately when resources are created or permissions are changed. Offline batch checks cannot be used here.
Multiple types of associated documents correspond to different permission boundaries. Independent access permissions must be configured separately for resource activation forms, instance configuration sheets, and delivery confirmation forms. This prevents unauthorized personnel from modifying specifications or tampering with delivery records.
Cross-system data binding requires permission checks to sync with actual resource status. This avoids situations where expired permissions still allow access to allocated resources.

## How to set configurations
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `teamId` | Match cloud IAM team IDs exactly | Align FastGPT team permissions with cloud platform IAM permissions, preventing cross-team resource privilege escalation |
| `tmbId` | Bind to exclusive instance identifiers, value range 1000–9999 | Assign a unique isolation identifier to each cloud host instance, preventing cross-instance access |
| Resource Access Whitelist | Only include specified operation IP ranges, 192.168.1.0/24 to 192.168.255.0/24 | Restrict unauthorized terminal access to resource configuration pages, reducing external attack risks |
| API Call Permissions | Validate by order ID, timeout 30 seconds | Ensure API calls can only access resources tied to the corresponding order, preventing unauthorized calls |
| Permission Change Audit | Log all permission modification operations, retention period 180 days | Retain operation traceability records to meet compliance review requirements |
| Team Permission Groups | Divide by department, only grant operation permissions for the corresponding category, maximum 50 members per group | Avoid cross-department permission overlap, refining operation boundaries for different roles |

## Three common configuration mistakes
1.  Phenomenon: FastGPT API calls return a 403 permission denied error. Cause: `teamId` is not bound to cloud IAM team IDs, causing the permission check logic to fail.
2.  Phenomenon: Members from different departments can view each other’s resource activation forms. Cause: Independent permission groups are not configured for different `teamId` values, and cross-team permissions are not fully isolated.
3.  Phenomenon: Team management functions cannot be enabled after local deployment. Cause: The team permission module is not enabled in the configuration file, and the permission check rules corresponding to `teamId` are not bound.

## How to confirm configurations are correctly set
- Pass the `teamId` parameter when calling the FastGPT API, verify that the returned results only include cloud host resource lists for the corresponding team.
- Attempt to access the resource configuration page from an unauthorized IP, confirm that the page returns a permission insufficient prompt or fails to load content.
- After deleting a team member, check whether the member’s permissions in the cloud IAM system are removed synchronously, verify that the member can no longer access the corresponding cloud host resources.
- Enable team management configuration in the local deployment environment, verify that the `teamId` parameter can be bound normally after adding a new team.

The values provided here are common starting points, and should be evaluated against the reader’s own samples.
