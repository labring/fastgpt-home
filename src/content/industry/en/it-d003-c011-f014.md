# Security and Compliance Material Review for Cloud Host Provisioning and Resource Activation: Model Integration and Configuration

## What the data for this category looks like
Core data for this category comes from cloud management platforms, order systems, IAM permission systems, and billing systems. Updates are synced in real time per order. Daily processed documents include resource activation forms, instance configuration sheets, account permission application forms, and delivery confirmation forms. Data fields include instance specifications, permission scope, billing items, delivery status, and more. Native data formats vary across systems, so standardized business data must be obtained via interface integration.

## What constraints these characteristics impose on the "model integration and configuration" link
Multi-data source integration requirements demand model configurations that support multi-interface docking, with separate adaptation to each system’s authentication rules. Real-time update features require model calls to align with business process trigger timing, avoiding compliance risks from delayed processing. Fixed business document structures require model prompts to match the field definitions of each document, ensuring review results cover all necessary compliance items. Consequences of errors directly impact customer deployment and billing, so configurations must ensure stability and accuracy of verification logic, reducing the probability of resource misalignment or billing disputes.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, for example http://aiproxy:3000. Do not append /v1 or /chat/completions paths | Server environment variable required by AI Proxy, specifies the access address for the AI Proxy service |
| `AIPROXY_API_TOKEN` | Non-empty admin token matching the AI Proxy server configuration | Server environment variable required by AI Proxy, used for identity authentication with the AI Proxy service |
| `maxContext` | 8000–12000 token | Adapts to the total context length of multiple business documents included in a single order |
| `maxTokens` | 2000–3000 token | Ensures complete output of compliance review results, avoiding truncation of key verification information |
| `temperature` | 0.1–0.3 | Reduces random errors in model output, ensuring consistency of compliance verification results |
| `toolChoice` | "auto" | Automatically calls compliance verification tools and system APIs, adapting to multi-data-source integration scenarios |

## Three common configuration errors
- Issue: `chat:LLM_model_response_empty` error returned after calling. Troubleshooting steps: Confirm `AIPROXY_API_TOKEN` is a non-empty admin token matching the AI Proxy server configuration, and confirm `AIPROXY_API_ENDPOINT` is the root address of the AI Proxy service with no additional paths appended.
- Issue: Inconsistent results returned for the same compliance verification request. Cause: Context recall rules for RAG mode were not fixed, and unnecessary model fine-tuning parameters were misconfigured, leading to differences in matching logic across each call.
- Issue: Some fields are omitted from compliance review results. Cause: The value of `maxContext` is too small, failing to load the full content of resource activation forms and instance configuration sheets, preventing the model from covering all compliance verification items.

## How to confirm configurations are properly set
- Verify that `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are valid server environment variables, and confirm service startup verification passes.
- Submit a standard resource activation form test dataset, and check if compliance review results returned by the model cover core fields including instance specifications, permission scope, and billing items.
- Simulate multiple identical compliance verification requests, confirm returned results are consistent, and verify the configuration effect of the `temperature` parameter.
- Check system logs to confirm there are no error logs of the `chat:LLM_model_response_empty` type, indicating the interface call process operates normally.

The values provided are common starting points and should be measured against the reader's own samples.
