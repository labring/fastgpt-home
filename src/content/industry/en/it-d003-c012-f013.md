# Security and Compliance Material Review for Cloud Network and Load Balancer Configuration: Permissions and Data Isolation

## What this category’s data includes
Data for this category originates primarily from cloud platform consoles, network topologies, traffic monitoring tools, and customer architecture diagrams. Daily maintenance documents cover VPC planning, security group rules, load balancer configurations, and change tickets.
Data fields include network segment ranges, port protocols, health check thresholds, backend server group configurations, and more. Units include Class C network segments, second-level intervals, TCP/UDP protocols, and others.
Data updates occur per ticket or per change. Each configuration change corresponds to a separate document record.

## Constraints imposed on permissions and data isolation
Cloud network and load balancer configuration data is categorized by team and tenant ownership. Permission isolation must align with resource ownership identifiers to prevent unauthorized cross-team or cross-tenant access to configurations.
Data updates are frequent, and each change is independent. Permission checks must trigger synchronously with change tickets to avoid security risks from delayed permission configurations.
Fields include specific network segments and ports. Permission scopes must strictly match these fields; generalized authorization is not permitted, as it may lead to connectivity failures or service exposure risks.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Bind to the unique team identifier associated with the cloud network resource | Implement team-level permission isolation, matching the team ownership characteristic of cloud network resources |
| `tmbId` | Bind to the tenant identifier of the load balancer instance | Implement tenant-level data isolation, preventing cross-tenant access to configuration information |
| Team resource scope configuration | Limit access rules to those corresponding to VPC network segments | Match the network segment field characteristic of cloud network data, preventing unauthorized access to non-authorized network segments |
| Change permission check configuration | Trigger a permission check per change ticket | Match the update frequency of cloud network configurations, which is per ticket or per change |
| Log access permission configuration | Only allow operations roles to view traffic monitoring logs from the past 30 days | Prevent unauthorized personnel from accessing sensitive network traffic data |

## Three common configuration errors
- Symptom: Cross-team access to cloud network configurations persists after configuring `teamId`. Troubleshooting steps: Verify that `teamId` is bound and validated against the resource ownership identifier in the cloud platform console, and confirm that the identifiers match.
- Symptom: No input parameters are displayed when calling the cloud network configuration review plugin in a workflow, with no errors in logs. Troubleshooting steps: Verify that the plugin’s permission binding parameters are correctly configured, and confirm the trigger conditions for the parameter rendering logic.
- Symptom: Unauthorized access alerts appear in traffic monitoring logs. Troubleshooting steps: Verify that the role scope for log access is restricted, and confirm that non-operations roles do not have access permissions.

## How to confirm configurations are correctly applied
- Log in to the corresponding team instance of FastGPT v4.17.0, view the cloud network configuration list, and confirm that only VPC and load balancer resources belonging to the current team are displayed.
- Submit a cloud network change ticket to trigger the permission check workflow, and confirm that only authorized roles can pass the check.
- Attempt to access traffic monitoring logs using a non-operations role, and confirm that the content cannot be viewed.
- Check the server-side environment variables, confirm that `AIPROXY_API_ENDPOINT` (the root address of the AI Proxy service, for example http://aiproxy:3000; do not append /v1 or /chat/completions; this is not a single-model address for VLLM/Ollama/Xinference and similar tools) and `AIPROXY_API_TOKEN` (the AI Proxy administrator token, consistent with the AI Proxy server-side configuration and cannot be empty; this is not an application API key, model vendor key, token issued per application, or token count estimated per request) have been correctly configured, and that they are not configured in workflow global variables, application API request headers, or the standard model management page.
