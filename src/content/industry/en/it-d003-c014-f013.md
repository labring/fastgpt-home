# Security and Compliance Material Review for Cloud Resource Compliance Auditing: Permissions and Data Isolation

## What the data for this category looks like
This category of data primarily comes from cloud audit logs, IAM permission systems, CMDB resource inventory libraries, and security baseline scan results. Regularly produced documents include four types: compliance checklists, permission audit reports, cloud resource inventories, and rectification tracking forms.
The data update cycle is monthly or quarterly. Each document includes fields for resource unique identifier, permission binding relationship, audit timestamp, and rectification status. No additional statistical quantitative fields are included.
The entire data flow must rely on compliant permission controls to avoid sensitive information leaks.

## What constraints these characteristics impose on the permissions and data isolation link
Data for cloud resource compliance auditing is collected across multiple systems and includes sensitive permission information. This requires that permissions and data isolation rules cover the full link of cross-system data flow.
The monthly or quarterly update cycle means isolation configurations do not need frequent adjustments, but must ensure rule stability.
Compliance documents and resource inventories from different teams must be strictly isolated. This prevents audit data leaks or tampering caused by unauthorized access.
The resource unique identifier field requires isolation rules to accurately match resource dimensions. Combine this with team permission grouping to implement isolation, ensuring only authorized members can access corresponding data.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` binding rule | Bind to the tenant to which the cloud resource belongs | Matches the tenant identification logic of CMDB and IAM systems |
| `tmbId` permission verification | Enable the corresponding switch | Implements permission isolation for multiple teams under a single account |
| Team permission isolation threshold | Calibrated based on 10–50 team members | Adapts to the collaboration scope of small and medium-sized compliance teams |
| Data isolation scope | Only open to audit members of the corresponding team | Prevents leakage of sensitive compliance data across teams |
| Audit data retention period | 12 months | Meets conventional compliance document retention requirements |
| Cross-tenant data synchronization switch | Keep the default closed state | Prevents unauthorized cross-tenant data flow |

## Three common configuration errors
- Symptom: Team members have no permission to access compliance audit data after being invited. Cause: The `tmbId` was not correctly bound to the invited member's account configuration.
- Symptom: Non-team cloud resource entries appear in cross-team resource inventories. Cause: The data isolation scope configuration did not limit to the corresponding `teamId` dimension, and full data was broadly opened.
- Symptom: Account isolation fails after self-hosted deployment. Cause: The `tmbId`-based account permission verification logic was not enabled, and full audit data access was directly opened.

## How to confirm the configuration is complete
- Review the team member permission list to confirm that only resources under the corresponding `teamId` are visible.
- Initiate a cross-team resource query request to verify that non-authorized teams cannot obtain the target compliance documents.
- Check the configuration file of the FastGPT v4.17.0 deployment to confirm that the `tmbId` verification logic has been correctly enabled.
- Simulate the process of inviting new members to confirm that invited members can normally access audit data for their corresponding team.
