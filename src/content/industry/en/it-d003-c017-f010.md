# Security and Compliance Material Review for Code Review & Merge Management: Citation Sources and Traceability

## What this category of data looks like
This category of data primarily originates from Git repositories, CI pipelines, static scanning reports, and defect databases. Daily generated documents include merge requests, code review comments, commit records, and branch strategy descriptions. Data update frequency adjusts based on commit actions or the daily pipeline execution schedule. Core fields include commit hash, merge request ID, reviewer identifier, changed file path, and defect association number. The data structure primarily combines structured text and metadata, with some static scanning reports using semi-structured log formats. These characteristics typically align with standard cases for this category.

## Constraints on Citation Sources and Traceability
Commit records in Git repositories are updated per single commit. Traceability must bind to a unique commit hash to avoid confusion. Merge requests and review comments are produced through multi-person collaboration, so they must be associated with reviewer IDs and change scopes to clarify responsibility boundaries. Static scanning reports from CI pipelines are updated in real time, so traceability must match the latest report ID to ensure timeliness of compliance checks. The change impact assessment step takes extended time, so traceability needs to quickly locate associated review records and commit content. Therefore, the number and precision of returned results must be controlled. These constraints typically apply to standard business scenarios for this category.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum token count per citation | 8000–12000 token | Matches the typical text length of merge requests and review comments, avoids truncating critical change context |
| Returned data included fields | Commit hash, merge request ID, static scanning report ID | Binds core business identifiers for code review and merge management, supports precise traceability |
| Detail toggle | Enabled | Pulls complete review comments and changed file lists, ensures completeness of citation sources |
| Citation source matching threshold | 0.85–0.95 | Filters low-relevance review records, avoids invalid traceability interference |
| Context recall limit | Top 10 entries | Controls the number of traceability returned records, balances information completeness and response speed |

## Three Common Misconfigurations
- Issue: No associated code review records are returned after configuring citation sources. Cause: Response data is not bound to a format including commit hash or merge request ID, making matching of core business identifiers impossible.
- Issue: After setting the citation limit to 3000, large language models do not receive context content. Cause: The set maximum token count per citation exceeds the system's preset context carrying limit, resulting in content being truncated and discarded.
- Issue: Garbled characters appear after importing Git repository review records. Cause: File encoding format is not specified, causing text parsing failures for static scanning reports or commit records.

## How to Verify Successful Configuration
- Upload test files for merge requests and review records, check whether the returned citation list includes matching commit hashes and merge request IDs.
- Adjust the maximum token count per citation to a test value, verify that the context length received by large language models meets expectations.
- Enable the detail toggle, check whether citation sources include complete review comments and changed file lists.
- Simulate a change request submission, verify that traceability results are associated with the latest CI static scanning report.

The values given are common starting points and should be measured against the reader's own samples.
