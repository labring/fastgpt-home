# Secure and Compliance Material Review for Trusted Innovation Replacement Adaptation: Conversation Logs and Auditing

## What data for this category looks like
Data for this category comes from enterprise existing IT system inventories, official directories of domestic hardware and software, trusted innovation replacement migration test environments, and publicly available vendor materials.
Daily produced documents include adaptation inventories, compatibility test reports, migration plans, and issue ledgers.
Data updates follow the cycle of a single trusted innovation replacement project, or sync with domestic hardware and software directory updates on a quarterly basis.
Common data fields include hardware and software model, version number, compatibility conclusion, migration steps, and issue troubleshooting records. There is no unified mandatory format, and fields are adjusted based on project requirements.

## Constraints imposed on conversation logs and auditing
Dynamic existing system inventories require conversation logs to link to system identifiers for specific projects. This prevents cross-project data confusion.
Phased updates to adaptation inventories and test reports require audit logs to record version change nodes. This ensures traceability to corresponding test activities.
Non-standardized fields in issue ledgers require audit logs to support custom field storage. This adapts to troubleshooting record formats for different projects.
Update cycles per project or quarter require log retention periods to cover full project cycles. This prevents loss of critical audit data.
Sensitive or classified domestic replacement project data requires log access to be bound to project permissions. This prevents unauthorized viewing.

## Three common configuration mistakes
- Symptom: API calls do not return full conversation log fields | Cause: The `detail` parameter is not correctly configured to enabled status, only basic session information is returned, and full traceability requirements for auditing cannot be met
- Symptom: Audit logs cannot be written normally after internal network deployment | Cause: The log storage path is not bound to the data mount directory for trusted innovation replacement projects, logs are lost when containers are destroyed, matches common log error scenarios for internal network deployments
- Symptom: Log fields are incomplete when importing compatibility test reports | Cause: Custom log field mapping is not configured, cannot link hardware and software models and test results in the test report, preventing auditing from tracing specific test activities

## How to confirm configuration is complete
- Initiate an adaptation test conversation, check if the returned logs include the `chatId` and `responseChatItemId` fields, confirm the association between projects and test activities
- View the log storage directory, confirm that log files are generated along with the test process and retained in the specified path, verify that storage configurations are active
- Attempt to access logs using accounts with different roles, confirm that permission configurations restrict viewing by unauthorized users
- Export log files, check if full `detail` information is included, verify that full log recording is enabled
