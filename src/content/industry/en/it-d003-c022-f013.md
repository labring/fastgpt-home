# Secure and Compliance Material Review for Xinchuang Replacement Adaptation: Permission and Data Isolation

## What data for this category looks like
Data for this category is generated for Xinchuang software and hardware replacement adaptation scenarios. Four core document types are routinely produced: adaptation lists, compatibility test reports, migration plans, and issue ledgers. Data is primarily collected from existing IT system inventories, official directories of domestic software and hardware, project test environments, and publicly available vendor materials. Updates follow the cycle of individual Xinchuang replacement projects, or synchronize domestic software and hardware directories on a quarterly basis. Document structures typically include fields such as system identification, software and hardware version, adaptation status, and test conclusions. There are no uniform mandatory units; version, date, and other information are labeled only in accordance with project document specifications.

## What constraints these characteristics impose on the "permission and data isolation" link
Documents such as adaptation lists and compatibility test reports involve details of an enterprise’s existing IT architecture and procurement information for domestic software and hardware. These are sensitive compliance data that require strict permission isolation. When multiple projects run in parallel, documents from different domesticization project teams must be isolated by `teamId` to prevent cross-project data leaks. Domestic software and hardware directories updated quarterly must be synchronized to the knowledge base of the corresponding project. Only project team members are allowed to access directory versions associated with their own project. Issue ledgers record migration risks and fault information. Edit access must be restricted to core members of architects and integrators only, to prevent unauthorized personnel from modifying migration plans.

## Configuration settings
| Configuration Item | Recommended Practice | Rationale |

| Team permission isolation dimension | Bind corresponding project documents by `teamId` | Matches the team division logic of Xinchuang replacement projects to achieve cross-project data isolation |
| Knowledge base access scope | Only adaptation documents associated with the member’s own `teamId` are accessible | Complies with sensitive data control requirements for domesticization projects |
| Sensitive document edit permission | Only members with `teamId` assigned to the architect group may make modifications | Prevents unauthorized personnel from altering migration plans or test reports |
| Domestic directory synchronization frequency | Synchronize domestic software and hardware directories every 20–30 days | Aligns with the regular quarterly update rhythm of data |

## Three common configuration mistakes
- Phenomenon: After configuring write permissions for other team members, the members still cannot create adaptation list documents. Cause: The permission group for the corresponding project was not bound by `teamId`, resulting in permissions not being associated with the correct project document library.
- Phenomenon: After domestic software and hardware directories are updated, some project teams cannot access the latest version. Cause: Access scopes for directories were not divided by `teamId`, leading to cross-project directory permission conflicts.
- Phenomenon: Issue ledgers are modified by unauthorized members. Cause: Edit permissions were not restricted to members with `teamId` assigned to the architect group, resulting in overly broad permission ranges.

## How to confirm configuration is complete
- Switch test accounts from different teams to verify that only adaptation documents and test reports associated with their own `teamId` are accessible.
- Attempt to edit the issue ledger using an account not in the architect group, and confirm that modifications cannot be submitted.
- Manually trigger domestic directory synchronization, and verify that only accounts from the current project team can view the updated directory content.
- Log in to the FastGPT v4.17.0 backend, and confirm that permission configurations have been synchronized to the knowledge base settings for the corresponding `teamId`.
