# Security and Compliance Material Review for Duty Scheduling and Handover: Conversation Logs and Auditing

## What this category of data looks like
Data for this category mainly comes from scheduling systems, fault work orders, monitoring alerts, and organizational contact lists. Update frequency is daily or weekly. Core daily documents include duty rosters, handover records, escalation contact lists, and daily duty reports. Fields cover duty time periods, pending handover items, contact names and contact information, alert trigger nodes, and more. Data structure adjusts slightly based on team operation scale, with no additional custom statistical fields.

## What constraints these characteristics impose on the conversation logs and auditing workflow
Multi-source data access requires the auditing module to support cross-system log correlation, to avoid missing information from a single data source. The daily or weekly update rhythm means auditing tasks must match this cycle to trigger, preventing repeated collection or missed updated content. The presence of multiple document types requires auditing rules to cover different scenarios: duty schedule time matching, handover item tracing, contact information verification, and others. The personnel and time attributes of fields mean auditing filtering dimensions must focus on duty personnel responsibilities and response timeliness, ensuring audit results align with the business logic of duty scheduling and handover.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Log collection scope | Cover duty time period, handover records, and alert log three types of data sources | Match the category's core documents and data sources |
| Log retention period | 90 days | Meet the basic cycle requirements of general compliance auditing |
| `chatId` association rule | Bind duty personnel account and session ID | Achieve precise binding between session and duty responsibilities |
| `responseChatItemId` filter | Only collect duty response type session entries | Filter invalid logs from non-duty scenarios |
| `detail` log switch | Enable full field collection | Cover core audit fields such as pending items and contact information |
| Auditing batch processing size | 500 items per execution | Balance auditing efficiency and system load |
| Auditing trigger frequency | 2:00 AM daily | Match the daily data update rhythm |

## Three common configuration errors
- Phenomenon: Log calls show the session token is the fixed value `fastgpt`, and specific duty personnel cannot be associated. Cause: The binding rule between `chatId` and duty personnel account is not configured, resulting in inability to trace session responsibilities.
- Phenomenon: Audit results only show partial handover records, with fewer entries than expected. Cause: The `detail` full field collection switch is not enabled, missing log entries for cross-system correlation.
- Phenomenon: Audit tasks trigger outside duty hours, resulting in invalid session collection. Cause: Trigger frequency is not set to match the data update rhythm, and logs are not filtered by duty time periods.

## How to confirm the configuration is complete
- View the log collection configuration page of FastGPT v4.17.0, confirm that the three types of data sources (duty time period, handover records, alert logs) are selected.
- Randomly select an archived duty session, check whether `chatId` is bound to the corresponding duty personnel's account information.
- Export an audit log sample, check whether the complete content of `responseChatItemId` and `detail` fields is included.
- Simulate initiating a session outside duty hours, confirm that the session is not included in the same day's audit scope.
