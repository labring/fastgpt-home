# Security and Compliance Material Review for Duty Scheduling and Handover: Permission and Data Isolation

## What this category of data includes
This category of data originates from enterprise IT operations duty scenarios. Core documents include duty schedules, handover records, escalation contact lists, and daily duty reports. Data comes from internal enterprise scheduling systems, fault ticket platforms, monitoring alert tools, and organization contact directories. Most updates occur daily; some escalation contact lists sync weekly.
Duty schedules contain fields for duty time slots, duty personnel, and responsible business clusters. Handover records must log unresolved faults, pending follow-up items, and permission handover status. Escalation contact lists group contacts by business cluster, with fields for contact name, position, and contact information.

## How these characteristics create constraints for permission and data isolation
Duty schedules link to operation and maintenance permissions for specific business clusters. Handover records involve access permissions for sensitive data of unresolved faults. Escalation contact lists hold contact information for core operation and maintenance positions. All this data covers sensitive permissions and business secrets of enterprise IT infrastructure.
Data sources are scattered and updated frequently. Permission boundaries for different roles require strict differentiation. For example, frontline duty personnel can only view duty information for their assigned time slots. Operation and maintenance managers can view all data but only edit scheduling configurations.
If permission isolation is not properly implemented, unauthorized personnel may access unresolved fault details or core operation and maintenance contact information, leading to operation accidents or information leakage risks. Daily updated scheduling data needs real-time synchronization of permission configurations to avoid permissions lagging behind personnel changes.

## How to set up configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Data isolation dimension | Divide business clusters by `teamId` | Matches the business cluster grouping field in duty schedules, ensures operation and maintenance data for the same cluster is only accessible to the corresponding team, complies with FastGPT v4.17.0 permission isolation specifications |
| Role permission template | Preset three-level permission groups by position | Frontline duty personnel only view data for their assigned time slots, operation and maintenance managers edit full scheduling data, second-line support only view handover records, adapts to operation and maintenance responsibilities for different positions |
| Data access time limit | Bind `tmbId` to duty time slots | Only allow data access during the duty time slot and 15 minutes before and after, automatically block access outside the time slot, matches the duty cycle of personnel |
| Single data return limit | Top 20 entries | Avoid returning too much sensitive data in a single request, reduces leakage risks |
| Sensitive field encryption rule | Encrypt escalation contact information fields | Prevent unauthorized roles from accessing core operation and maintenance contact information, meets compliance review requirements |
| Permission synchronization frequency | Trigger permission refresh daily | Matches the daily update rhythm of scheduling data, ensures permissions are synchronized promptly after personnel changes |
| Abnormal access detection | Enable cross-cluster access alerts, alert delay no more than 60 seconds | Monitor unauthorized access to sensitive data, trigger operation and maintenance alerts in a timely manner |

## Three common misconfigurations
- Symptom: After restarting the permission synchronization service, some duty personnel cannot view the daily duty schedule. Cause: The permission synchronization task is not bound to `tmbId` and the personnel's duty time slot, resulting in delayed permission updates, which matches the scenario of configuration failure after service restart.
- Symptom: Attempting to access duty data for a business cluster not assigned to the accessing user returns a 403 Forbidden status code. Cause: The business cluster permission corresponding to `teamId` is not configured correctly, leading to failed cross-cluster permission verification.
- Symptom: The unresolved fault field in handover records shows as empty. Cause: Incorrect sensitive field encryption configuration leads to data decryption failure, preventing normal rendering of interface content.

## How to verify correct configuration
- Log in to the system with a frontline duty personnel account, verify that only the duty schedule for their assigned time slot is visible, and scheduling data for other business clusters cannot be accessed.
- Modify the `teamId` permission configuration for a specific business cluster, verify that accounts from the corresponding operation and maintenance team can normally access data for that cluster, while accounts from other teams cannot.
- Trigger the permission synchronization task, verify that accounts outside the duty time slot cannot access the daily duty data.
- View the escalation contact list, verify that unauthorized roles cannot view the plaintext content of sensitive contact information fields.
