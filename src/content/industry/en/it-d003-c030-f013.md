# Security and Compliance Material Review for Internal Network and WiFi Operations: Permissions and Data Isolation

## What data for this category looks like
This category’s data comes primarily from switch consoles, wireless controllers, office network monitoring systems, and user trouble ticket channels. The update frequency is daily or after each network change. Common daily documents include network topology diagrams, change tickets, fault logs, and wireless coverage inspection reports. Topology diagrams include fields such as port ID, VLAN number, and AP deployment location. Change tickets note change time and operation content. Inspection reports record information such as signal strength and number of connected devices.

## What constraints these characteristics impose on permissions and data isolation
Documents such as network topology diagrams and change tickets contain core network configuration information. Restrict access to these documents only to authorized operations staff and compliance reviewers. Data sources are scattered and update frequency is high. Sync permission changes to all associated data nodes. Isolate documents for different operation scenarios by business group. This prevents cross-departmental access to unauthorized network access details. User trouble ticket data involves employee office status. Set separate access permissions for this data to prevent leaks of sensitive office information.

## Three common configuration mistakes
- Phenomenon: The interface displays the prompt "No permission to operate this conversation record". Cause: The current user is not bound to the permission group of the corresponding `teamId`, or the team scope to which the conversation record belongs does not have access permissions enabled.
- Phenomenon: Unable to generate unauthenticated links after the default 10-link limit is exceeded. Cause: The unauthenticated link creation limit configuration for the team edition package has not been adjusted, or the configuration has not been synced to the permission pool of the corresponding `teamId`.
- Phenomenon: A permission error prompt appears when testing a locally deployed model. Cause: The model resource is not bound to the `tmbId` of the current team, or the oneAPI configuration is not associated with the correct team permission scope.

## How to confirm the configuration is complete
- Check the unauthenticated link creation limit configuration item, confirm the value meets business needs, and it is bound to the permission group of the corresponding `teamId`.
- View the member permission grouping list, confirm the correspondence between operation roles such as network administrators and desktop support and permission ranges matches job responsibilities and authorities.
- Initiate a cross-team document access test, confirm that unauthorized users cannot view sensitive data such as corresponding network topologies and fault logs.
- Invoke the locally deployed compliance review model, confirm that only the `teamId` and `tmbId` of the authorized team can normally access model resources.
