# Security and Compliance Material Review for Internal Network and WiFi Operations: Model Access and Configuration

## What this category's data includes
Data for this category primarily comes from switch consoles, wireless controllers, monitoring systems, and user trouble reporting channels. Daily produced documents include network topology diagrams, change orders, fault records, and wireless coverage inspection forms. Data is updated daily or synchronized immediately after network changes. Document fields include port numbers, VLAN identifiers, wireless signal strength parameters, inspection cycles, and fault troubleshooting steps. Some content is unstructured text records without a unified standard format.

## Constraints on model access and configuration
Unstructured fault records and inspection forms require models to support multi-format input. Context length must be limited to avoid redundancy. The data synchronization feature following network changes requires model access configurations to support dynamic data source updates. This prevents use of outdated network topology and fault information. Verification requirements for precise fields such as ports and VLANs require fixed parameter precision during model calls. Matching thresholds should not be relaxed. Locally deployed models must adapt to internal network environments and cannot rely on public network interfaces. Local access endpoints and token verification must be configured.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service accessible via the internal network, for example `http://internal-aiproxy:3000` | Required environment variable for the AI Proxy service. Specifies the service access root address. Do not add path suffixes such as `/v1`. This is not a single-model deployment address. |
| `AIPROXY_API_TOKEN` | Administrator token matching the AI Proxy server configuration | Required environment variable for the AI Proxy service. Used to verify access permissions for the AI Proxy service. This is not a model vendor key or application API Key. |
| `maxContext` | 8000–12000 token | Matches the total length requirements of multiple documents such as network topology diagrams and fault records. Prevents truncation of critical configuration information. |
| `temperature` | 0.1–0.3 | Ensures consistency of verification results for precise fields such as ports and VLANs. Reduces random errors. |
| `toolChoice` | auto | Allows the model to automatically call tools based on compliance review requirements. Adapts to dynamically changing network change scenarios. |
| `maxTokens` | 2000–3000 token | Limits the length of compliance review results generated per round. Prevents output of redundant information. |

## Three common configuration errors
- Using a public network address when configuring `AIPROXY_API_ENDPOINT`. This prevents the internal network from accessing the AI Proxy service, and a connection timeout error appears in the interface. The cause is failure to use the internal network-accessible AI Proxy service root address, which violates internal network access restrictions.
- Incorrectly configuring `AIPROXY_API_TOKEN`. The system reports a startup verification failure or prompts unauthorized access during runtime. The cause is missing configuration or use of an administrator token that does not match the AI Proxy server configuration. This is not a model-generated token.
- Triggering an error after adding a knowledge base. This only occurs when using locally deployed models. The cause is failure to adjust the `maxContext` parameter to match the total length of knowledge base documents. The request fails because the context upper limit supported by the model is exceeded.

## How to confirm configurations are valid
Verify configuration effectiveness using the following steps under FastGPT v4.17.0:
- Access the configured `AIPROXY_API_ENDPOINT` address. Confirm the internal network can normally access the AI Proxy service root address to verify network connectivity.
- Confirm the App/Admin service starts without reporting missing environment variables or verification failures. This verifies the `AIPROXY_API_TOKEN` configuration is valid.
- Upload a network fault record as a test knowledge base, then initiate a compliance review request. Confirm no timeouts or errors occur, and structured verification results are returned.
- Adjust the `temperature` parameter to 0.2, then submit two identical review requests. Confirm the results are consistent to verify the parameter configuration is effective.

The values provided are common starting points and should be measured against the reader's own samples.
