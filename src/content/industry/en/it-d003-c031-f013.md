# Security and Compliance Material Review for Creator Onboarding and Verification: Permissions and Data Isolation

## What this category of data looks like
Data in this category centers on creator admission and identity credibility. Daily documents include onboarding forms, identity qualification certificates, audit review records, cooperation agreements, and similar materials. Data sources include information submitted via the creator backend, enterprise credit public platform data, account historical behavior records, and archived content from contract systems. Data updates are mostly triggered by individual applications; some batch audit scenarios update data daily. Fields include applicant subject information, qualification numbers, audit status, cooperation periods, and similar details. There is no unified fixed single-data capacity unit, and values vary based on the size of submitted paper or electronic materials.

## What constraints these characteristics impose on the "permissions and data isolation" link
This configuration guide is based on FastGPT v4.17.0. Data in this category involves sensitive information such as identity qualifications and contract agreements, with scattered sources. Permission isolation must align with the application subject and audit role associated with the data. Temporary data triggered by individual applications and daily batch-updated data require separate isolation rules to prevent cross-application leakage of audit records. Different roles (such as creator operations, platform auditors, and institutional operations) must correspond to distinct data access scopes, to prevent unauthorized personnel from viewing uncompleted audit materials or cooperation agreement content. Sensitive fields including qualification numbers and contract clauses require separate access permission configuration, only allowing personnel in the corresponding audit stage to read the data.

## How to set the configurations
| Config Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Bind a unique `teamId` to the application subject, one application corresponds to one `teamId` | Match the independent data isolation requirement of a single application to avoid cross-application data confusion |
| `tmbId` | Allocate `teamId` scope according to audit roles, only allow `tmbId` corresponding to the `teamId` to access data | Implement role-level data access permission control, align with the responsibility division of the audit process |
| Sensitive data encryption | Enable end-to-end encryption for qualification materials and cooperation agreement fields, storage validity period is `30 days` (uncompleted audit) or `180 days` (completed verification) | Match compliance requirements for data update and retention, prevent sensitive information leakage |
| Access log retention | Retain all data access logs, retention duration is `90 days` | Meet compliance audit requirements, facilitate tracing of abnormal access behavior |
| Temporary data release | Uncompleted audit application data is automatically released if no operation occurs for `7 days` | Reduce exposure risk of idle sensitive data, align with temporary data lifecycle management |
| Permission audit cycle | Conduct permission configuration audit every `30 days` | Correct abnormal permission assignments in a timely manner, prevent unauthorized access |

## Three common mistakes
- Phenomenon: Auditors across application subjects can view qualification materials of other applications, leading to false verification risks. Cause: The application subject and access permissions are not bound according to `teamId`, resulting in unisolated permission scope.
- Phenomenon: In batch audit scenarios, old daily updated data is not cleaned up in time, leading to expired data leakage. Cause: Temporary data automatic release rules are not configured, idle sensitive data is retained for too long.
- Phenomenon: Operation personnel who are not in audit roles can export cooperation agreement texts, leading to cooperation dispute risks. Cause: The `tmbId` access scope is not allocated according to audit roles, resulting in unauthorized access to sensitive contract data.

## How to confirm the configuration is correct
- Submit a test onboarding application, use an account with a non-audit role to attempt to access the qualification materials of this application, confirm that viewing is not possible.
- Check the stored data of the corresponding application, confirm that enabled encrypted sensitive fields cannot be read directly.
- Check the system access logs, confirm that each data access records the corresponding `teamId` and `tmbId` information.
- Wait for the test application that has no operation for `7 days`, confirm that the system automatically released all associated data of this application.

The values provided are common starting points and should be measured against the reader's own samples.
