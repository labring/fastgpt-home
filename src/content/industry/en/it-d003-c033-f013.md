# Security and Compliance Material Review for Frontend Application Development: Permissions and Data Isolation

## What this category of data includes
Daily data generated during frontend application development includes four categories: interface documents, component specifications, debugging records, and release lists.
Interface documents record interface addresses, request parameters, and return fields.
Debugging records retain exception phenomena and repair steps from interface debugging.
Release lists mark version numbers, change content, and launch times.
Browser compatibility data includes test results for rendering performance across different terminals.
Data sources cover Git code repositories, interface management platforms, design tooling, and browser compatibility testing tools.
Update frequency follows daily commits or syncs before each version release.

## What constraints these characteristics impose on permissions and data isolation
Frontend application development data is tightly linked to terminal rendering and interface interactions, and includes sensitive information such as interface secrets and release configurations.
Project-stored code and documents require permission isolation that matches project ownership.
Daily code commits and debugging records require real-time permission synchronization to prevent data leaks caused by expired permissions.
Cross-team frontend projects need to isolate resources such as interface documents and release lists across different teams, to prevent unauthorized members from accessing sensitive configurations.
Browser compatibility data relates to end-user access scopes, so only project team members can view and modify it.

## How to configure the settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Bound to the team-exclusive ID of the code repository | Clarifies the resource ownership of frontend applications, ensuring team members only access data such as interface documents and debugging records for their own projects |
| `tmbId` | Assigned unique identifiers based on development, testing, and release roles | Differentiates permission levels, restricting the scope for viewing and modifying sensitive configurations |
| Data isolation scope | Divided by individual project, maximum isolated data volume per project does not exceed 1000 MB | Matches the update rhythm of frontend applications iterated by project, avoiding cross-project data confusion |
| Interface access whitelist | Only allows IP ranges of the team’s code repository to access | Meets the secure access requirements of interface documents, preventing unauthorized calls to interface data |
| Version release permission | Only bound to the `teamId` of the release list approver | Corresponds to the review process of release lists, ensuring permissions for online versions are controllable |

## Three common configuration errors
- Phenomenon: Clicking the team management entry has no response or fails to redirect. Cause: The frontend application permission binding corresponding to `teamId` is not configured, causing entry permission verification to fail.
- Phenomenon: Cross-team associated knowledge base queries return no relevant content. Cause: The data scope is not isolated by `teamId`, and the frontend application’s query request does not carry the affiliated team identifier, so it cannot match the permissions of the corresponding knowledge base.
- Phenomenon: Members cannot view debugging records or interface documents. Cause: The document access permission corresponding to `tmbId` is not assigned, and the member’s permission identifier is mistakenly set to another team’s `tmbId`.

## How to confirm the configuration is complete
- Log in to the FastGPT v4.17.0 backend, enter the configuration page of the corresponding frontend application, and check whether `teamId` matches the team ID bound to the code repository.
- Switch the `tmbId` of different roles, and verify that only the corresponding role can view sensitive configurations and release lists.
- Initiate a cross-team knowledge base query request, check whether the correct `teamId` parameter is carried, and confirm that the returned results comply with permission isolation rules.
- View the interface access whitelist configuration, and confirm that only the team’s IP ranges are allowed to initiate interface call requests.
