# Security and Compliance Material Review for Office System Process Configuration: Permission and Data Isolation

## What data does this category include
Data for this category primarily comes from enterprise OA systems, internal organization structure libraries, compliance policy documents, and frontline user feedback. Daily maintained documents include process configuration sheets, approval node tables, form field descriptions, and change records. Data updates trigger when business configurations change, typically at least once per month. Common fields include process identifiers, node permission scopes, associated form fields, and approver scopes. There are no standardized fixed units, and values adjust based on specific configuration scenarios. This guide applies to FastGPT v4.17.0.

## What constraints do these characteristics impose on permission and data isolation
The data sources, update rhythm, and document structure of this category create multiple constraints for the permission and data isolation link. First, data sources are scattered across multiple systems such as OA systems and organization structure libraries. Cross-system permission boundaries must be aligned to prevent cross-department permission overreach. Second, data updates trigger with business changes. Each configuration adjustment requires a corresponding update to isolation rules. Mismatches will occur between old rules and new data if updates are skipped. Multiple daily maintained document types require permission configurations to cover access ranges for different documents. They also require retaining audit permissions for change records to ensure compliance traceability. The binding relationship between approval nodes and form fields requires permission configurations to accurately match field and approver ranges. This prevents permission deviations.

## How to configure settings
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| Team permission scope | Bind `teamId` as the minimum permission unit | Aligns with the permission logic of existing enterprise team divisions |
| Approval node isolation | Divide permissions by approval role, limit the number of people covered by a single node's permissions to no more than 20 | Avoids excessive permission concentration, adapts to daily approval management |
| Form field permissions | Only grant access to fields associated with the current process | Prevents cross-process data leaks |
| Change record audit | Only administrators can view full logs, retain duration set based on actual testing | Ensures compliance traceability of configuration changes |
| Cross-system permission alignment | Sync updates with OA system `tmbId` permissions | Ensures consistent permission boundaries across systems |
| Configuration verification response threshold | 120 seconds | Adapts to response duration requirements for daily configuration testing |

## Three common configuration errors
- Phenomenon: Cross-team configured processes fail to trigger approval normally, logs show the `teamId` field is empty. Cause: The process configuration is not correctly bound to the permission identifier of the corresponding team, resulting in invalid permission isolation rules.
- Phenomenon: Regular members can view approval node configurations of other processes, and no permission intercept prompt appears in the interface. Cause: The minimum permission unit is not divided by `teamId`, and the permission range configuration covers non-associated processes.
- Phenomenon: After approval node configuration is submitted, some members cannot enter the approval process, and the page returns a permission error. Cause: Permissions are not synced with OA system `tmbId` permissions, and cross-system permission boundaries are not aligned.

## How to confirm the configuration is correct
- Log in to the FastGPT v4.17.0 team management backend, view the process configuration list bound to `teamId`, and confirm that only processes associated with the current team are visible.
- Submit a process configuration change, check the access permissions of the change log, and confirm that only the administrator group can view the full content.
- Simulate a regular member accessing the process configuration page, and confirm that approval node information of non-associated teams cannot be viewed.
- After syncing OA system `tmbId` permissions, verify whether cross-system process approval permissions take effect normally.
