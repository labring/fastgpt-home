# Security and Compliance Material Review for Unit and Component Testing: Document Parsing and Chunking

## What the data for this category looks like
Data for this category comes from code repositories, test framework reports, requirement specifications, and interface definitions. The update frequency is daily or after each code commit.
Commonly processed documents include test cases, coverage reports, Mock instructions, and defect tickets. Test cases contain fields for case identification, execution steps, expected results, and priority. Coverage reports contain module paths, coverage values, and statistical dimensions.
Most documents use structured entry formats. Some interface documents have mixed code snippets and comments.

## What constraints these characteristics bring to the document parsing and chunking process
Diverse data sources and frequent updates require the document parsing and chunking workflow to adapt to rapidly iterating test data. This avoids test logic lag caused by parsing delays.
Structured documents such as test cases and defect tickets must retain field association relationships. Chunking must not split the binding logic between execution steps and expected results.
For interface documents with mixed code snippets and comments, the boundary between code and comments must be accurately identified. This avoids splitting related content into different chunks.
High-frequency updated data also requires the parsing workflow to have lightweight validation capabilities. This supports incremental data processing for single commits.

## Configuration settings
This document is written for FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `chunkSize` | 800–1200 characters | Adapts to the structured entry length of test cases and coverage reports, avoids splitting the binding relationship between case execution steps and expected results |
| `chunkSplitter` | Switch based on document type | Use paragraph splitting for structured test documents, use code block + paragraph splitting for interface documents with mixed code |
| `customPdfParse` | Enabled | Adapts to PDF-format test reports and interface documents, retains original layout structure and content connections |
| `UPLOAD_FILE_MAX_SIZE` | 100 MB | Adapts to the file size of batch test reports and code snippet files submitted in a single batch, avoids interception due to oversized files |
| `PARSE_FILE_TIMEOUT_SECONDS` | 300–600 seconds | Adapts to the parsing time of long coverage reports and batch defect tickets, avoids interrupting the parsing process due to timeout |
| `chunkSettingMode` | Manual mode | Customize chunking rules for test scenarios, adapts to different types of test document formats |

## Three common mistakes
- Uploading a Java interface file with a modified file suffix results in empty parsing. The cause is failing to enable `customPdfParse` to adapt to parsing rules for non-standard file suffixes. The system only recognizes standard document suffixes by default.
- Some PDF files are parsed as empty. The cause is the PDF containing encrypted content or non-standard fonts, and the enhanced parsing mode not being enabled via the `customPdfParse` configuration.
- Using chunk mode to call the pushdata API for upload results in persistent "indexing" status. The cause is `PARSE_FILE_TIMEOUT_SECONDS` being set too short, as parsing of long documents is not completed before the indexing timeout wait is triggered.

## How to verify the configuration is correct
- Upload a single typical test document, check the parsed chunk content, confirm that the execution steps and expected results of the test case are not split into different chunks.
- Upload an interface document with a modified file suffix, verify that the parsed result includes code snippets and comment content, confirm that the `customPdfParse` configuration is effective.
- Submit a batch of test reports, check the execution logs of the parsing task, confirm that no timeout errors occur, and that the value of `PARSE_FILE_TIMEOUT_SECONDS` adapts to the parsing time of the current scenario.
- Call the pushdata API to upload test data, check the returned task status, confirm that the indexing process is completed within a reasonable time frame.

The values provided are common starting points and should be measured against the reader's own samples.
