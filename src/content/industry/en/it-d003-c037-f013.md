# Security and Compliance Material Review for Release Management and Version Acceptance: Permissions and Data Isolation

## What data for this category looks like
Data for this category primarily comes from CI pipelines, change management systems, test reports, and monitoring dashboards. Update frequency follows weekly or per-version release cycles. Daily generated documents include release plans, launch checklists, acceptance reports, and rollback plans. Data fields cover version identifiers, involved business modules, approval workflow nodes, rollback trigger thresholds, with units primarily being version numbers, timestamps, and percentages.

## What constraints these characteristics impose on the permissions and data isolation step
Data for this category is linked to the full R&D workflow and involves sensitive production release information. Access permissions for different roles such as release managers, operations staff, and product owners must strictly match their job boundaries. Data update frequency fluctuates with version cycles, so permission configurations must adapt to version iteration rhythms to avoid expired or unauthorized access. Sensitive documents like rollback plans and launch checklists may only be viewed by approval and execution personnel from the corresponding team. Cross-team release data must be isolated to prevent unauthorized personnel from accessing production change details.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Bound to the `teamId` of the current release project | Bind release data to the corresponding team to enable cross-team data isolation |
| `tmbId` | Associated with the exclusive `tmbId` of the current version | Distinguish release configurations for different versions to avoid permission confusion between versions |
| SSO configuration | Only enabled for commercial edition accounts on FastGPT v4.17.0 and above, bound to the enterprise organization's `teamId` | Implement enterprise-level unified team permission management to meet compliance requirements |
| Role permission scope | Only open document fields within the corresponding role's responsibilities. For example, approvers may only view approval node fields, with a single view limit of `50 items` | Follow the principle of least privilege to prevent unauthorized access to sensitive content |
| Sensitive data encryption | Enable encrypted storage for rollback plans and launch checklists, key validity period is `180 days`, storage capacity limit is `1000 MB` | Ensure storage security of sensitive production change information, rotate keys regularly |
| Permission validity period | Set to take effect within the version cycle, automatically recycle permissions after the version ends, cycle is `7–14 days` | Adapt to the weekly or per-version update rhythm of this category, avoid permission redundancy |

## Three common configuration errors
- Phenomenon: Non-commercial edition accounts attempt to configure SSO permissions and receive a prompt that the feature is not available. Cause: Failure to confirm that the current version only supports SSO configuration for commercial editions, leading to failed permission configuration.
- Phenomenon: Value conflicts occur in global variables across different users, making isolation by user ID impossible. Cause: Failure to configure variable scope binding based on `tmbId`, and the global variable scope is not limited to the corresponding release version or team.
- Phenomenon: After switching teams, release data from the old team remains visible. Cause: Failure to clear cached data associated with `teamId`, leaving old data access permissions after permission switching.

## How to confirm configuration is complete
- Log in with an account with no authorized role, attempt to access the rollback plan document for the corresponding release project, confirm that access cannot be completed or is blocked.
- Switch the `teamId` of different teams, verify that release data from different teams may only be accessed by corresponding team members.
- Submit a new version release, verify that permission configurations take effect automatically with version creation, no manual adjustment required.
- View the storage logs of sensitive documents, confirm that encryption configuration is enabled, and no plaintext leakage occurs during data transmission.
