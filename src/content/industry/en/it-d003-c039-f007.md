# Security and Compliance Material Review for Backend Service Development: Conversation Logs and Auditing

## What Data Looks Like for This Category
The data for this category primarily comes from code repositories, API gateway logs, databases, and configuration centers. Update frequency is daily archiving or synchronization with each version release. Associated daily documents include interface design documents, database change tickets, code review records, and release notes. Fields for conversation logs and audit data typically include `chatId`, `responseChatItemId`, call time, token consumption value, and operation context identifier. Data is organized by application or interface dimension, and follows the structured logging specifications for backend services.

## What Constraints Do These Characteristics Impose on Conversation Logs and Auditing Workflows
The characteristics of this category of data impose multiple constraints on the conversation logs and auditing workflow. Multi-source data collection must adapt to the log formats of different systems such as code repositories and API gateways, and unified structured parsing rules must be configured. The daily or per-version update frequency requires audit logs to support batch archiving and version association, ensuring logs are bound to corresponding releases or interface changes. Associated documents such as interface design documents require audit entries to carry corresponding interface identifiers, facilitating post-hoc tracing of contract matching. Backend services have high requirements for data consistency. Audit logs must avoid loss or tampering. Persistent storage and verification mechanisms must be configured.

## How to Configure Settings
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Mandatory collection enabled | Binds full logs for a single session, aligns with backend service session tracking specifications |
| `responseChatItemId` | Mandatory collection enabled | Locates call details for a single reply, facilitating interface contract matching |
| `detail` | Supplement with exception stacks and interface parameters | Provides additional troubleshooting information for backend services, matching the tracing requirements of code review records |
| Log retention period | 30–90 days | Aligns with the daily archiving update rhythm of backend services, meeting basic tracing requirements for compliance reviews |
| Log anomaly alert threshold | Trigger threshold set to 600 seconds | Meets backend service stability requirements, enabling timely detection of log synchronization interruptions |
| Application-level token statistics | Enabled | Meets backend service statistical requirements by application dimension, matching version association requirements in release notes |

## Three Common Configuration Errors
- Symptom: Unable to view historical call logs by knowledge base document dimension; logs only show summary records at the session dimension. Cause: Document association configuration for the `detail` field is not enabled, only basic session identifiers are collected, and specific document IDs for knowledge base calls are not bound.
- Symptom: Reply records from different Agents are visible to each other, leading to permission escalation issues. Cause: Ownership verification rules for `chatId` are not configured correctly, and sessions are not bound to Agent permission identifiers, resulting in cross-session access.
- Symptom: Conversation logs are lost, or log synchronization fails after Docker deployment. Cause: Log retention period and persistent storage path are not set in the configuration, and Docker volume mounting rules are not adapted, leading to log loss after container restart.

## How to Confirm Configuration is Complete
- Access the FastGPT log management panel, confirm that the `chatId`, `responseChatItemId`, and `detail` fields are properly collected and displayed in log entries.
- Initiate multiple sets of calls across different sessions and Agents, verify that token statistics data is aggregated by application dimension, matching the preset statistical logic.
- Simulate a container restart or version release process, check that logs are archived according to configured rules, with no abnormal loss.
- Attempt to access logs from other sessions across Agents, confirm that permission verification is active, and only records within the corresponding permission scope are accessible.
