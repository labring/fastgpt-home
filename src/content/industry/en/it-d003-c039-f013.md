# Security and Compliance Material Review for Backend Service Development: Permission and Data Isolation

## What data for this category looks like
Data for this category primarily comes from code repositories, API gateway logs, databases, and configuration centers. Update frequency follows a daily or per-release cycle. Daily produced documents include interface design documents, database change tickets, code review records, and release notes. Interface design documents contain request permission identifiers and interface parameter ranges. Database change tickets include operated table names and changed fields. Code review records contain permission check logic annotations. Release notes contain service permission configuration change items.

## Constraints imposed on permission and data isolation by these characteristics
Decentralized and frequently updated data sources require permission control to cover the full chain of code submission, interface calling, data reading and writing, and configuration changes. Diverse document structures linked to business logic require differentiated permission configuration for different document types. This prevents unauthorized personnel from accessing interface contracts or database change details. Data fields contain sensitive permission identifiers and operation instructions. Strict verification of the access subject's `teamId` and `tmbId` is required to prevent unauthorized reading or modification of core configurations. Service stability requirements dictate that permission changes must not cause interface timeouts or incorrect data writes. Rollback space must be reserved in isolation configurations.

## How to configure settings
This page applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` binding rules | Globally unique 32-64 characters, allocated per team | Matches FastGPT's team permission identifier specifications, ensuring precise isolation granularity |
| `tmbId` verification logic | Bound to user session context, valid for 24 hours | Limits permission validity of login-free links, preventing token abuse |
| Interface permission grouping | Divided by interface path, each group associated with the corresponding `teamId` | Matches backend service interface contract documents, enabling isolation by business module |
| Data access threshold | Read up to 1000 records per request | Prevents unauthorized leakage of bulk data, complies with backend service data isolation requirements |
| Configuration change verification | Requires approval to take effect, rollback window of 600 seconds | Prevents service exceptions caused by incorrect permission configurations, ensures release stability |

## Three common configuration errors
- The symptom is that login-free links do not verify `tmbId`, allowing any user to access sensitive data. The cause is that the `tmbId` verification logic is not bound to the session context, and authorization is granted directly via link parameters only.
- The symptom is that interfaces return a `403 Forbidden` status code but do not explain the insufficient permission reason. The cause is that no `teamId` permission matching logs are configured, making it impossible to quickly locate unauthorized requests.
- The symptom is that bulk database change operations are triggered by unauthorized personnel. The cause is that permissions are not configured by interface path grouping, and access permissions for core change interfaces are open to the entire team.

## How to verify successful configuration
- An interface testing tool can be used to send requests with different `teamId` values, verifying that unauthorized `teamId` cannot access corresponding interface resources.
- A login-free link can be generated, with the `tmbId` parameter in the link modified, verifying that the modified link cannot access content within the original permission scope.
- API gateway logs can be checked, confirming that all permission check requests record `teamId` and `tmbId` identifiers to facilitate subsequent troubleshooting.
- A permission configuration change can be triggered, verifying that rollback operations before the change takes effect can be completed within the preset window, and no service exceptions occur.
