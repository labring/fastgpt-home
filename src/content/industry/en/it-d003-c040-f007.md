# Security and Compliance Material Review for Pre-Sales Technical Solutions: Conversation Logs and Auditing
This document is written for FastGPT v4.17.0.

## Data Characteristics for This Category
Data for this category primarily comes from customer interview records, public bidding documents, vendor product materials, and historical project proposal documents. Core daily output documents include technical proposal books, customer requirement research forms, quotation lists, and demo scripts. Data updates follow a per-project cycle, with version iterations typically completed per project or once per week. Document fields cover technical route descriptions, implementation boundary definitions, quotation configuration items, demo process steps, and more. No unified mandatory format exists, and structures must be adjusted to match customer bidding document requirements.

## Constraints on Conversation Logs and Auditing
Since data for this category is updated per project, conversation logs must be split and archived by project to avoid cross-project data mixing. Document sources are scattered and formats are inconsistent. The auditing process must fully record the triggering subject, timestamp, and modified content for every proposal change to ensure traceability. As compliance materials related to bidding are involved, log retention must cover the full process from draft to final proposal version. It must also support retrieving operation records for corresponding nodes using `chatId` and `responseChatItemId` to meet compliance review traceability needs. Daily used tool chains must also be fully recorded to avoid auditing blind spots caused by unclear proposal boundary definitions.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Log archive binding key | `chatId` | Matches the per-project data management unit feature of this category, enabling quick retrieval of full-process proposals and call logs by project |
| Audit log detail switch | Enable `detail` field recording | Fully retains detailed content of tool calls and proposal modifications, meeting traceability requirements for bidding compliance reviews |
| Log retrieval index | Associate `responseChatItemId` | Facilitates locating specific nodes for single proposal modifications or tool calls, matching document traceability needs |
| Concurrent call rate limit threshold | 1–2 calls per second | Adapts to high-concurrency call abnormalities, avoiding empty results from tool responses |
| Log retention period | Add 60 days to the project cycle | Covers the full process from project initiation to acceptance, meeting compliance auditing requirements |

## Three Common Configuration Errors
- Phenomenon: Tool calls return empty results when concurrent call volume exceeds 2 calls per second. Cause: No reasonable concurrent rate limit threshold is configured, causing workflow node overload and triggering call exceptions.
- Phenomenon: The tool call module outputs redundant runtime records. Cause: Non-essential log detail switches are not disabled, causing irrelevant debug information to be mixed into audit logs and increasing review costs.
- Phenomenon: No connection can be established with the termination node after MCP tool calls. Cause: `responseChatItemId` is not bound in the log configuration, causing call links between nodes to not be fully tracked and preventing the termination node's verification logic from triggering.

## How to Confirm Correct Configuration
- Retrieve project logs for a specified `chatId`, confirm all proposal modification and tool call records are archived with no missing nodes.
- Simulate a high-concurrency call scenario, verify tool calls return normal results with no null values or abnormal errors.
- Check log fields, confirm the `detail` field fully records tool call input parameters, output parameters, and execution time to meet auditing requirements.
- Test the MCP tool call chain, confirm call records can be associated with the termination node with no broken links.

The values provided are common starting points and should be measured against the reader's own samples.
