# Security and Compliance Material Review for Image Annotation Projects: Conversation Logs and Auditing

## What data for this category looks like
Data for this category primarily comes from image samples, category dictionaries, spot check results, and rework lists produced by annotation platforms. Daily associated documents include annotation specifications, bounding box examples, quality inspection reports, and rework lists. Data updates follow a daily or single-batch annotation task schedule. Core fields include target bounding box coordinates, annotation categories, quality inspection markers, annotator IDs, and review statuses. Data only circulates based on actual business operations, with no additional statistical standards.

## Constraints for conversation logs and auditing workflows
Data for this category links to multi-dimensional business entities. Conversation logs must bind image sample IDs, annotation batches, and operator identities to ensure audits can trace back to specific annotation tasks. High-frequency daily or single-batch data requires logs to be split and stored by task batch, to prevent overly large single log volumes that reduce retrieval efficiency. Multi-field annotation records must support filtering logs by dimensions such as bounding box coordinates and quality inspection results. Conversation permissions for annotators, quality inspectors, and algorithm teams must also be differentiated, to prevent unauthorized access to sensitive annotation data.

## Configuration settings
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` generation rule | Bind annotation batch ID and operator ID | This category requires distinguishing conversation records of different operators and annotation tasks to avoid log confusion |
| Log detail storage switch | Enable full storage of the `detail` field | Annotation data includes sensitive information such as bounding box coordinates and quality inspection results; full storage meets complete audit traceability requirements |
| `responseChatItemId` association rule | Bind single image sample ID | Each round of conversation usually corresponds to a single annotated image; association allows quick location of audit records for specific samples |
| Log retrieval limit | Return the first 100 logs per request | Conversation records for single-batch annotation tasks are typically under 100, to avoid retrieval overload |
| Log retention period | 30 days after task completion (calibrated via actual testing) | Compliance review requires retaining necessary audit periods, to avoid invalid storage occupying resources |

## Three common configuration errors
- Symptom: Log retrieval returns conversation records not belonging to the current operator. Cause: `chatId` is not bound to the operator ID. Root cause: `chatId` is not split by annotation batch and operator ID, leading to logs from different users being grouped under the same session.
- Symptom: Database container fails to start normally after service launch, with logs showing database connection failure. Cause: Database permissions for conversation log storage are not configured, or the storage path does not adapt to the storage needs of batch annotation data.
- Symptom: Logs are not automatically cleaned after exceeding the preset limit. Cause: Automatic cleanup rules by task batch are not configured; using only global periodic cleanup leads to accidental deletion of logs for unfinished tasks.

## How to verify correct configuration
- Different annotator accounts are accessed, conversation logs are retrieved, and confirmation is made that only session records from the current user’s operations are visible.
- A single annotated image is uploaded, annotation communication is initiated, log details are viewed, and confirmation is made that the `detail` field contains complete bounding box coordinates and annotation category information.
- Multiple batch annotation tasks are initiated, logs for the corresponding batches are retrieved, and confirmation is made that `chatId` is bound to the correct batch ID and operator ID.
- The log cleanup rule is manually triggered, and confirmation is made that logs for completed tasks are archived or cleaned according to the preset period.

The values provided here are common starting points, and should be evaluated against the reader’s own samples.
