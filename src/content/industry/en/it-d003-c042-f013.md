# Security and Compliance Material Review for Backup Recovery and Disaster Recovery Drills: Permissions and Data Isolation

## What this category's data looks like
Data for this category is maintained daily by operations teams, database administrators, and business continuity leads. Core documents include backup policies, recovery drill reports, disaster recovery switchover plans, and data validation records. Data sources cover backup systems, database logs, object storage, and disaster recovery platforms. Update frequencies occur daily, monthly, and quarterly. In daily operations, confirming recovery points, executing drill scripts, and verifying data consistency are the most time-consuming steps. Operational errors may cause data loss, recovery timeouts, or business continuity failures. Unlike database operations categories, this category focuses on cross-system end-to-end recoverability, rather than single-node database maintenance scope. This configuration guide applies to FastGPT v4.17.0.

## What constraints do these characteristics impose on the Permissions and Data Isolation workflow
Data sources for this category are scattered, and responsibility boundaries are clearly defined. Permission configurations must match the access scope of different systems to avoid permission overlap across teams or roles. Core documents have widely varying update frequencies. Permission change workflows must align with document update rhythms to prevent unauthorized modifications to core configurations such as backup policies. The most time-consuming operational steps involve cross-system collaboration. Exclusive permissions must be bound to corresponding roles to prevent unauthorized personnel from executing drill scripts or modifying recovery points. Operational errors have severe consequences. Permission configurations must support fine-grained access control to ensure traceability and auditability for compliance material reviews.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Team permission groups | Divide dedicated permission groups by `teamId`, bind 1-3 preset roles to each group | Align with the team responsibility allocation of backup systems to prevent cross-team permission overlap |
| User role binding | Bind corresponding roles by `tmbId`, only allow operations roles to execute recovery drills | Correspond to the permission boundaries of business continuity leads to prevent unauthorized operations |
| Data resource isolation | Divide data access scope by storage path, only allow roles to access storage buckets of their corresponding disaster recovery platforms | Match the object storage permission rules of data sources to prevent unauthorized access to backup data |
| Audit log toggle | Enable full operation audit, retain logs for 30 days | Meet traceability requirements for compliance material reviews, facilitate tracking of permission changes and operation records |
| Permission change approval | Configure a two-level approval workflow, changes take effect within 24 hours after completion | Align with the update frequency of backup policies to prevent accidental modification of core configurations |

## Three common configuration errors
- Symptom: A call to the disaster recovery drill API returns a 403 permission denied error. Cause: The user role is not bound to the permission group for the corresponding `teamId`, so the API call does not match the valid resource scope.
- Symptom: Regular operations users can modify core backup policy documents. Cause: The data resource isolation configuration is not used to restrict document access scope, and global permissions are mistakenly assigned to regular roles.
- Symptom: Permission changes do not take effect, and recovery drills still cannot be executed. Cause: The required effective workflow specified in the permission change approval configuration is not triggered. Configurations are modified directly without going through the approval process.

## How to confirm configurations are properly set up
- Switch to an unauthorized role, attempt to access backup policy documents, and confirm that viewing or editing is not allowed.
- Call the disaster recovery drill API using a user token that is not bound to permissions, and confirm that a corresponding permission denied prompt is returned.
- Submit a permission change application, confirm that the approval workflow is triggered, and that configuration updates are synchronized to the permission system after completion.
- View audit logs, confirm that all permission-related operations are recorded and traceable.
