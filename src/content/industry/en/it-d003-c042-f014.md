# Security and Compliance Material Review for Backup Recovery and Disaster Recovery Drill: Model Access and Configuration

## What data for this category looks like
Data for this category originates from backup systems, database logs, object storage, and disaster recovery platforms. Four regular document types are produced: backup policies, recovery drill reports, disaster recovery switchover plans, and data verification records. Data update cycles are daily, monthly, or quarterly. Core workflows include recovery point confirmation, drill script execution, and data consistency verification. Errors in these workflows can lead to data loss, recovery timeouts, or business continuity failures.

## What constraints do these characteristics impose on model access and configuration
Multi-source heterogeneous data sources require model access to support integration with diverse data sources such as backup systems and database logs, and adapt to cross-system permission verification and data retrieval logic. Fixed-format daily documents require the model to recognize unified field rules, to prevent extraction deviations that compromise compliance review results. Data with different update cycles require configuration support for flexible context length adjustment, to accommodate real-time daily monitoring data and quarterly archived drill reports. The time-consuming nature of core workflows requires model configuration to prioritize scenarios like recovery point confirmation and data consistency verification, while strictly limiting output length to avoid timeouts and protect business continuity.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | Adapts to the context length of multiple documents such as backup policies and drill reports, covering processing needs for daily and quarterly updated data |
| `maxTokens` | `2000–3000 token` | Controls output length for data consistency verification and recovery point confirmation scenarios, preventing call timeouts |
| `quoteMaxToken` | `1500 token` | Retains original document reference fragments required for compliance review, meeting compliance requirements for traceability verification |
| `temperature` | `0.1–0.3` | Ensures consistency of compliance review results, avoiding random deviations that impact data verification accuracy |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, for example `http://aiproxy:3000`. Do not append `/v1` or `/chat/completions` paths, and use non-single-model service addresses | Required environment variable for the App/Admin server, specifies the root address of the AI Proxy service |
| `AIPROXY_API_TOKEN` | Administrator token consistent with the AI Proxy server configuration, and cannot be empty | Required environment variable for the App/Admin server, used for authentication with the AI Proxy service |

## Three common mistakes
- Symptom: After configuring `AIPROXY_API_ENDPOINT`, model calls show very low GPU resource usage, with 100% CPU single-core utilization. Verifiable troubleshooting items: Check if `AIPROXY_API_ENDPOINT` is the correct root address of the AI Proxy service, confirm `AIPROXY_API_TOKEN` matches the AI Proxy server configuration and is not empty, and verify that the App/Admin server startup check passed.
- Symptom: When creating a new model channel for testing, the error "cannot read properties of undefined (reading)" is returned. Verifiable troubleshooting items: Check if `AIPROXY_API_ENDPOINT` is configured correctly, confirm `AIPROXY_API_TOKEN` matches the AI Proxy server configuration and is not empty, and verify that the App/Admin server startup check passed.
- Symptom: The compliance review results output by the model do not include reference fragments from the original document. Cause: No reasonable value is set for `quoteMaxToken`, causing reference fragments to be truncated or not extracted.

## How to confirm configuration is complete
- Perform a field extraction test on a backup policy document, compare the fields output by the model with those in the original document, and adjust configuration items until they meet business verification rules.
- View model call logs, confirm that GPU resource usage is within a normal range, and CPU single-core utilization does not remain excessively high, to verify that acceleration configuration is effective.
- Check model output results, confirm that reference fragments from the original document are included, to verify that the traceability function configured via `quoteMaxToken` works properly.
- Test the compliance verification process for disaster recovery switchover plans, confirm that model response time meets business continuity requirements, and adjust the `maxTokens` configuration to fit the scenario.
