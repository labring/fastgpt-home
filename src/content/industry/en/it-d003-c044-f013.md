# Security and Compliance Material Review for Security Product Rule Operations: Permission and Data Isolation

## Data Overview for This Category
Data for this category primarily comes from WAF, IDS, firewalls, and threat intelligence platforms. Four core document types are produced regularly: rule change tickets, block logs, false positive analysis reports, and policy rollback records.
Data updates use either daily batch sync or real-time event-based push. Document structures include fields such as operator, change time, policy content, and associated block events.
Rule change tickets must record rule IDs before and after modification, plus effective scope. Block logs include standardized fields such as request source IP, block rule ID, and hit time. Some historical documents have missing fields due to version iterations.

## Constraints on Permission and Data Isolation
Scattered data sources and real-time updates for this category impose specific constraints on permission and data isolation. Access boundaries must be divided by protection product type and business team, to prevent cross-team policy configuration and block log leaks.
Core documents contain sensitive protection rules and business block details. Access must be restricted to authorized security operation engineers for their team’s corresponding documents.
Some historical documents have missing fields. Isolation logic must be compatible with older data structures to avoid permission check failures caused by missing fields.
Policy change operation logs must be bound to the operator and their affiliated team, to ensure changes are traceable and cannot be altered by unauthorized teams.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` permission binding | Bind to the protection product ID associated with the current team | Ensure only authorized team members can access rules and logs for the corresponding protection product |
| `tmbId` field compatibility | Allow empty values and automatically match the default team | Compensate for scenarios where historical documents lack the `tmbId` field, prevent old data from failing to load |
| Single team data storage threshold | 1000 MB upper limit | Prevent a single team from occupying too many cluster resources, ensure clear isolation boundaries |
| Access log retention period | 90 days | Meet security compliance requirements for operation traceability, while controlling storage costs |
| Cross-team access toggle | Only manually enabled by administrators | Prevent unauthorized cross-team data access, follow the principle of least privilege |
| Real-time sync interval | 5 minutes | Ensure real-time performance of block logs while reducing cluster load pressure |

## Three Common Configuration Mistakes
- Phenomenon: When loading older historical rule change tickets, the interface prompts missing fields, and the console reports `tmbId is not defined`. Cause: The `tmbId` field compatibility logic is not configured, and the field is forced to be required, causing old documents to fail permission checks.
- Phenomenon: In an on-premises deployment environment, the OneAPI service fails to start with a MySQL connection refused prompt, while the MySQL container logs show normal startup. Cause: No inter-container network isolation policy is configured, or the database port is not mapped correctly, causing the service to fail to access the database.
- Phenomenon: When adding a team member, entering their account shows the username as invalid. Cause: The mapping relationship between team accounts and `teamId` is not synchronized, so the system cannot identify the team associated with the entered account.

## How to Verify Correct Configuration
- Log in to the FastGPT v4.17.0 team management backend, check whether the binding relationship between `teamId` and the associated protection product matches the actual configuration.
- Upload a historical version of a rule change ticket, verify that it loads normally with no field errors, confirming that the `tmbId` compatibility logic is active.
- Attempt to access another team's block logs using an unauthorized team account, confirm that reading fails and a permission insufficient prompt appears.
- View the cluster data storage dashboard, confirm that single team data usage does not exceed the set 1000 MB threshold.
