# Security and Compliance Material Review for Security Baseline Checking: Permission and Data Isolation

## What the data for this category looks like
Core data for security baseline checking comes from server configurations, middleware configurations, security device policies, and content exported by baseline tools. Update frequency is monthly or quarterly. Daily produced documents include baseline checklists, configuration verification records, rectification suggestions, and exception approval forms. Data fields include baseline item identifiers, configuration parameter values, verification results, approver information, and update times. There are no unified fixed units. Formats are matched only according to configuration item types.

## What constraints these characteristics impose on the "permission and data isolation" link
Data sources are scattered and cover multiple types of technical assets. Baseline data from different business teams must be strictly isolated to prevent cross-team configuration information leaks. Update frequency is low, but the data involves compliance audits. Data versions must be bound to corresponding operating subjects to prevent unauthorized modifications. The responsibility boundaries of three typical roles are clearly defined: security operation and maintenance, consulting consultants, and internal control auditors. Different document access and editing permissions must be assigned according to roles. The circulation of exception approval forms must limit the scope of approval permissions. Otherwise, risks such as long-term retention of weak configurations or audit failure may occur.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Bound to business teams | Matches the team-level data isolation requirement of security baseline checking, ensuring that baseline asset data from different teams cannot access each other |
| `tmbId` | Assigned per single verification project | Corresponds to an independent security verification project space, avoiding confusion of baseline data across projects |
| Permission group configuration | Divided by operation and maintenance/consulting/audit roles | Matches the responsibility boundaries of the three typical roles, only opening document access and operation permissions required by the corresponding roles |
| Global variable scope | Bound to user ID | Adapts to the independent data needs of different users, avoiding data crossover caused by duplicate-named global variables |
| Operation timeout threshold | 1200 seconds | Adapts to the workflow timeout configuration logic of FastGPT v4.17.0, matches the duration of batch verification and approval processes for baseline checking, preventing mid-operation interruptions |

## Three common mistakes
- Phenomenon: Data crossover occurs after different users submit duplicate-named global variables. Cause: The scope isolation rules for global variables are not configured according to user IDs.
- Phenomenon: Unauthorized roles can view baseline checklists and configuration verification records of other business teams. Cause: Permission verification is not performed by binding `teamId`, and data spaces are not divided according to business teams.
- Phenomenon: Exception approval forms are modified by non-approval roles. Cause: Edit permissions for permission groups are not configured according to roles, and the responsibility boundaries between consulting consultants and internal control auditors are confused.

## How to confirm the configuration is complete
- Attempt to access the baseline checklist of another business team with an unauthorized role, confirm that the corresponding content cannot be viewed or edited.
- Submit duplicate-named global variables for two different user IDs for testing, confirm that their respective variable values do not interfere with each other, and there is no data crossover.
- Verify that team data bound to `teamId` is only visible to members of the corresponding team, and cross-team members cannot access it.
- Check whether the permission group configuration matches the responsibility scope of the three roles of operation and maintenance, consulting, and audit, confirm that only authorized roles can operate the corresponding documents.
