# Security and Compliance Material Review for Vulnerability Disclosure Handling: Permission and Data Isolation

## What this category's data looks like
Data for this category is generated across the full vulnerability lifecycle of a single open-source project. Daily documents include security advisories, vulnerability reports, fix patches, and CVE submission materials. Data sources include privately submitted vulnerability reports, project code repositories, public disclosure information from official CVE numbering authorities, and official project release channels. Data updates follow the cycle of a single vulnerability event. Each dataset corresponds to a unique vulnerability ID and processing workflow, with dedicated fields including vulnerability severity, impact scope, patch submission time, and disclosure plan. No universal bulk data structures are used.

## What constraints these characteristics impose on the permission and data isolation workflow
Privately submitted vulnerability reports may only be accessed by authorized members of the security response team. This prevents unauthorized parties from gaining early access to vulnerability details, which could lead to premature patch exploitation. Vulnerability data for different projects must be strictly isolated to prevent cross-project data leaks. Dedicated fields tied to a single event must be linked to its corresponding processing workflow to avoid data confusion. Data sources include information from external CVE authorities, so permission checks must be enforced when pulling external data to prevent unauthorized acquisition of official CVE data. Permission configurations must support adjustments at the event granularity to accommodate full workflow permission changes for a single vulnerability.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Team permission groups | Bind to the dedicated team for the corresponding project's security response group | Isolate vulnerability data across different open-source projects, prevent cross-project unauthorized access |
| Event permission ID | Assign a unique, independent identifier to a single vulnerability event | Tie to the exclusive permission scope of that event, ensure data is only visible to authorized members |
| Private data access scope | Only allow core team members to access private vulnerability reports | Prevent unauthorized parties from gaining early access to vulnerability details, avoid premature patch exploitation |
| Single access validity period | 1800–3600 seconds | Match the average cycle of vulnerability handling, prevent long-term permission leaks |
| Data storage quota | 2000 MB, calibrated based on actual testing | Adapt to the storage needs of documents related to vulnerabilities for a single project |
| FastGPT version | FastGPT v4.17.0 | Ensure compatibility and functional completeness of configuration items |

## Three common misconfigurations
- Symptom: After restarting the FastGPT container, private vulnerability reports fail to load normally, returning a 403 Forbidden status code. Cause: After the container restarts, the mounted permission configuration file fails to load correctly, resulting in invalid binding of team permission groups.
- Symptom: Cross-project vulnerability data is displayed crosswise, and core members can view vulnerability reports from other projects. Cause: No independent team permission group is assigned to each project, leading to failed permission isolation.
- Symptom: Timeout errors occur when pulling CVE data, returning a 504 Gateway Timeout status code. Cause: Data is not restricted to pulling only from the specified interface of the official CVE authority, leading to requests exceeding permission scope or occupying excessive bandwidth.

## How to confirm configurations are set correctly
- Access the FastGPT backend, review the team permission group list, and confirm that the security response group for the corresponding project is bound to the dedicated team.
- Use an unauthorized account to access private vulnerability reports, and confirm that the corresponding data cannot be viewed.
- Trigger a CVE data pull operation, and verify that the pulled data source is the specified official CVE authority interface.
- Restart the FastGPT container, and verify that the permission configuration has not undergone abnormal changes.
