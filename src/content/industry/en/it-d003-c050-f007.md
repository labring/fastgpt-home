# Security and Compliance Material Review for Customer Onboarding and Tenant Initialization: Conversation Logs and Auditing

## What Data for This Category Looks Like
This category’s data primarily originates from CRM systems, contract order databases, identity management systems, and the FastGPT product backend. Data updates run once per order or once per day. They trigger alongside customer onboarding workflows or sync with daily operations. Associated daily documents include customer onboarding application forms, tenant configuration sheets, administrator account lists, and delivery confirmation forms. Core fields include tenant unique identifier, customer subject identifier, onboarding time, permission configuration items, and administrator account list. Most field formats are strings, integers, or standard timestamps.

## Constraints Imposed on Conversation Logs and Auditing
Since this category’s data updates trigger with customer onboarding orders and link to multiple external systems, conversation logs must bind to the tenant unique identifier and customer onboarding process ID. This ensures logs can trace back to specific delivery orders. Differences in data update frequencies require audit logs to support filtering by onboarding time ranges, aligning with different customers’ delivery rhythms. Multi-field associations in daily documents require logs to simultaneously record operations like permission configuration and administrator account changes, preventing disconnects between configurations and logs. Failure consequences include customer login failures or delivery delays, so audit logs must cover the full workflow from tenant initialization to permission distribution and support quick location of abnormal steps.

## Configuration Guidelines
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `chatId` | Bound to tenant unique identifier and onboarding application form ID | Ensures logs link to specific customer onboarding processes, meeting this category’s data tracing requirements |
| `responseChatItemId` | Linked to administrator account operation records | Corresponds to this category’s administrator account list document, facilitating permission auditing |
| `detail` | Records full steps of permission configuration, account creation, and tenant initialization | Covers core operational links for this category, meeting compliance review requirements |
| Log retention period | 180 days | Meets general compliance audit retention requirements, aligns with this category’s delivery confirmation cycle |
| Log exception alarm trigger condition | Calibrated based on actual testing | Adapts to this category’s update rhythm of once per order or per day, avoiding invalid alarms |

## Three Common Misconfigurations
- Phenomenon: Conversation logs fail to generate when calling external applications or plugins in a workflow. Cause: The `detail` parameter for workflow-associated logging is not enabled in tenant initialization configurations, so non-core conversation operations go unrecorded.
- Phenomenon: When viewing historical records via an interface, the `source` field only displays API-related values. Cause: Log source binding rules for tenant initialization are not configured, and account source information from the identity management system is not synchronized, leading to missing extended field items.
- Phenomenon: MCP service operation logs during the tenant initialization phase cannot be located. Cause: `chatId` is not bound to the MCP service call identifier, so logs disconnect from specific tenant processes and cannot be filtered by tenant ID.

## How to Verify Proper Configuration
- Log in to the tenant management page of the FastGPT product backend, version 4.17.0 or higher. Select the target tenant, then view the conversation log list. Confirm that tenant initialization operation records are present.
- Call the historical record query interface, and verify that the `chatId` and `responseChatItemId` fields both include the tenant unique identifier and onboarding application form ID.
- Trigger a simulated tenant initialization operation, then check if log details include `detail` information such as permission configuration and account creation.
- View the system log module, and confirm that tenant initialization-related operation logs are stored per the configured retention period.
