# Security and Compliance Material Review for Client Data Import Migration: Permissions and Data Isolation

## What this category of data looks like
Data for this category primarily originates from customer legacy business systems, CSV or Excel standard templates, database export files, and FastGPT platform product import logs. Daily output documents include data templates, migration plans, field mapping tables, and migration verification reports. Update frequency follows per-project or irregular schedules. Data fields include business entity fields, mapping relationship identifiers, validation rules, and import status identifiers. No unified fixed units exist; configurations adjust based on the customer’s business scenario. Typical users include implementation consultants, data implementation engineers, and customer IT liaisons. Data flow centers on single client migration projects.

## Constraints on permissions and data isolation
The data sources for this category include sensitive business data exported from customer-owned systems, standard templates, and import logs. Update frequency varies irregularly per single migration project. This requires permissions and data isolation configurations to cover multi-dimensional boundaries: isolate import tasks across different customers to prevent cross-tenant data leaks; restrict access to sensitive documents such as migration plans and field mapping tables to only project participants; adapt to dynamically adjusted field structures based on customer scenarios to enable field-level permission verification; prevent risks of historical data loss or field misalignment caused by misoperations.

## Configuration settings
Precise permission and data isolation control can be implemented via the following configuration items in FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` binding configuration | Bind the exclusive `teamId` for the current migration project | Ensure import tasks only run within the specified tenant, isolating cross-tenant data |
| Field permission verification granularity | Field-level | Adapt to dynamically adjusted business field structures for the customer, enabling access and edit control for individual fields |
| Import log storage path | `./import_logs/${tmbId}/` | Divide storage directories by `tmbId` to isolate log data across different customers |
| Permission cache validity period | 300–600 seconds | Balance real-time performance of permission verification with system resource usage |
| Maximum number of access members per project | No more than 20 people | Limit access to sensitive migration documents and data, reducing leakage risks |
| Log retention duration | 7–14 days | Cover the full migration verification cycle, avoiding long-term storage of sensitive business data |

## Three common configuration errors
- SQL permission errors occur after restarting the Docker service, and import tasks cannot be started. The cause is that permission configurations are not retained after container restart, and the mounted directory permissions bound to `teamId` are reset, preventing FastGPT from reading migration configuration files.
- Field mapping options do not appear in the input parameters of import tasks in workflows. The cause is that the field-level permission switch is not enabled, causing the corresponding configuration item to be hidden, and the parameters fail to load because the current project’s `tmbId` is not associated.
- Multiple accounts cannot join the same migration project team. The cause is that the team is not created by binding `teamId` per project, and the default global team permissions do not open the access scope for migration tasks, preventing members from obtaining project permissions.

## How to confirm configurations are correct
- Check the tenant identifier of the import task, confirm it matches the current project’s `teamId`.
- Attempt to access migration plans and field mapping tables using a non-project member account, confirm that viewing or editing is not allowed.
- Check the storage path of import logs, confirm that directories are divided by `tmbId`, with no mixed cross-customer logs.
- Restart the Docker service, verify that import tasks can start normally with no permission errors.
