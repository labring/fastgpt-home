# Security and Compliance Review for Customer Data Import Migration: Model Access and Configuration

## What this category of data looks like
This type of data primarily originates from customers’ historical business systems, CSV/Excel templates, database export files, and product import logs. Daily supporting documents include data templates, migration plans, field mapping tables, and migration validation reports. Data update frequency is per order or irregular. Fields cover business dimensions such as customer ID, transaction records, and contact information. No fixed unified unit format exists, and some data may have missing values or disorganized formatting.

## What constraints do these characteristics impose on the model access and configuration link?
The diversity of data sources and formats requires model access configuration to adapt to multiple input types including structured tables and unstructured logs. Irregular update rhythms mean model call contexts must support dynamic adjustments, to avoid cached old data impacting validation results. Non-standard field requirements mean the model must have basic format conversion and validation capabilities, so reasoning parameters of the model need to be configured appropriately. The sensitivity of customer data also requires isolated configuration of multiple API keys, to prevent a single key leak from affecting full import tasks.

## How to set the configurations
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to context length requirements for tasks such as field mapping validation and dirty data cleaning for customer imported data |
| `maxTokens` | 2000–3000 token | Meets generation and validation output requirements for field descriptions and mapping rules for single-batch migrated data |
| `temperature` | 0.1–0.3 | Reduces output randomness, ensuring accurate and consistent results for field mapping and data compliance validation |
| `toolChoice` | auto | Allows the model to automatically choose whether to call tools for tasks such as data cleaning and format conversion |
| `AIPROXY_API_TOKEN` | Non-empty administrator token matching the AI Proxy server configuration | Required environment variable for the App/Admin server, used for authenticating access to the AI Proxy service. Must not be confused with application API keys or model vendor keys |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, for example http://aiproxy:3000 | Required environment variable for the App/Admin server. Must not have /v1 or model service subpaths appended, and must not be configured as a single model service address |

## Three Common Misconfigurations
- Format errors in docker-compose.yml when configuring multiple API keys. The symptom is model calls returning invalid key or 401 status codes. The cause is incorrect array formatting of environment variables or failure to escape special characters.
- Failure to adjust timeout parameters when deploying the model gateway. The symptom is import tasks timing out mid-process, with logs showing request timeouts. The cause is the default timeout threshold not adapting to validation time for bulk customer data.
- Incorrect configuration of AI Proxy-related environment variables in workflow global variables, application API request headers, or the model management page. The symptoms include service startup validation failures, model calls returning authentication errors or 404 errors. Troubleshooting step: Confirm that AI Proxy required environment variables are configured as system environment variables for the App/Admin server.

## How to Confirm the Configuration Is Correct
- Check the environment variable configuration of the App/Admin server, confirm that `AIPROXY_API_ENDPOINT` is the root address of the AI Proxy service, and `AIPROXY_API_TOKEN` is the non-empty administrator token matching the AI Proxy server.
- Upload a single test data sample, initiate a field mapping validation task, and check if the returned results match the preset field mapping rules.
- View the import logs, confirm that the response status code for model calls is 200, with no invalid key or timeout errors.
- Simulate multi-batch data import, verify that different API keys are rotated normally according to groups, to avoid exceeding limits for a single key.

The values provided here are common starting points, and should be evaluated against the reader’s own samples.
