# Security and Compliance Material Review for Customer Requirement Pool Management: Permissions and Data Isolation

## What this category's data looks like
This category of data primarily originates from ticketing systems, customer interview records, CRM systems, and product roadmap documents. Daily maintained documents include requirement pool lists, requirement evaluation forms, customer feedback records, and version planning descriptions. Data updates occur weekly or with each version iteration. Individual data entries contain fields such as requirement number, associated customer identifier, priority tag, submission time, evaluation status, and scheduling marker. There is no unified fixed unit; values adjust based on the specific document type.

## What constraints these characteristics impose on permissions and data isolation
This category’s data is sourced from multiple dispersed systems and includes associated customer identifiers. This requires permissions and data isolation to cover unified boundaries across cross-system entry points. Different document types have notably different sensitivity levels. Customer feedback records involve customer privacy, so separate isolation rules must be configured. Data update frequency adjusts with version iterations, so permission configurations must support bulk synchronous updates. Individual data entries are bound to associated customer and team identifiers, so precise verification must be performed based on customer and team dimensions. This prevents cross-customer or cross-team requirement information leaks, and avoids distortion of requirement commitments.

## How to configure settings
The following configurations are written for the permissions module of FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Bind to the exclusive ID of the current operations team | Match team-level requirement data isolation rules to enable cross-team permission isolation |
| `tmbId` | Bind to the team ID of the corresponding customer | Enable customer-level requirement data isolation to prevent cross-customer requirement information leaks |
| Sensitive document isolation rules | Set customer feedback records to be editable only by team leads | Align with the privacy attributes of customer feedback, limit editing permissions for sensitive data |
| Bulk configuration limit | Maximum 500 requirement data entries per operation | Adapt to daily bulk operation scales of the requirement pool, avoid system overload |
| Dynamic permission update cycle | Synchronize every 1–7 days | Match the weekly or per-version data update rhythm, ensure permissions align with data status |
| Permission verification matching fields | Customer and team identifiers in requirement data | Ensure permission verification logic aligns with data structure, avoid verification failures |

## Three common configuration mistakes
- Symptom: Team members attempt to create requirement pool entries and receive an insufficient permissions error, or cannot view requirement data from the target team. Cause: The `teamId` parameter is not correctly bound, or the configured team permission range does not cover the member’s role.
- Symptom: Non-associated team members can edit or delete customer feedback records. Cause: Isolation rules for sensitive documents are not separately configured, and customer feedback is assigned the same permissions as regular requirement pool data.
- Symptom: After permission configuration updates, old requirement data still retains incorrect permission settings. Cause: Permissions are not synchronized according to the data update rhythm, or bulk configuration does not cover all associated requirement data.

## How to confirm successful configuration
- Log in to an account from an unrelated team, attempt to access requirement pool data from the target team, confirm that viewing or editing operations are not allowed.
- Log in as a regular team member, attempt to edit customer feedback records, confirm that editing permissions are not granted, only public requirement pool information can be viewed.
- Trigger a bulk permission update, wait 1–7 days, confirm newly synchronized requirement data matches the latest configured permission rules.
- Randomly select 10 requirement data entries, check that all are bound to `teamId` or `tmbId` identifiers, with no empty fields or incorrect associations.
