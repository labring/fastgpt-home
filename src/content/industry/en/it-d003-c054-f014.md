# Security and Compliance Material Review for Container Platform Operations: Model Integration and Configuration

## What this category’s data looks like
Core data for this category comes from Kubernetes API, image registries, cluster monitoring systems, and CI pipelines. Daily operation and maintenance documents include cluster change tickets, namespace quota tables, deployment records, and failure reports. Data fields include change time, namespace identifiers, resource quota values, Pod running status, image versions, and more. Units are typically CPU cores, memory in MB, and timestamps. Data updates happen daily or whenever a cluster change occurs, with no fixed batch update cycle. Single data volume increases gradually as cluster scale expands.

## What constraints these characteristics impose on model integration and configuration
Structured data returned by the Kubernetes API requires models to support reading standardized fields, and avoids processing unstructured redundant content. Flexible data update frequencies mean the model context must adapt to dynamically changing cluster states, so context parameters should not be set too small. The fixed field structure of daily operation and maintenance documents requires compliance review results output by the model to match corresponding fields, reducing subsequent format conversion costs. Cluster change errors can cause business interruptions, so the stability and permission control of model calls must strictly match internal cluster access rules.

## How to set configurations
These configurations are based on FastGPT v4.17.0, and are adapted for security and compliance review scenarios for container platform operations:

| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | Container platform operation data mostly comes from K8s API and cluster logs, requiring sufficient context to cover single-cluster daily change records and quota configurations |
| `maxTokens` | `2000–3000 token` | Compliance review outputs are mostly structured reports, which do not require overly long content, to avoid exceeding model output limits |
| `temperature` | `0.1–0.3` | Compliance review requires accurate matching of cluster configuration rules, reducing randomness of generated content and minimizing deviations |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, for example http://aiproxy:3000 | Environment variable configured for the App/Admin server, used to specify the access address of the AI Proxy service. Do not append /v1 or model interface paths |
| `toolChoice` | `auto` | Allows the model to autonomously choose whether to call cluster data query tools to complete automatic review and verification of compliance materials |

## Three common misconfigurations
- Symptom: An exception or no response is returned when calling related services, and no call logs exist on the corresponding proxy platform. Troubleshooting steps: Check if the App/Admin server has a non-empty `AIPROXY_API_ENDPOINT` (AI Proxy service root address) and non-empty `AIPROXY_API_TOKEN` (AI Proxy admin Token), and confirm that the AI Proxy service is running normally.
- Symptom: The compliance review results generated by the model do not meet preset format requirements, and only rely on prompt word guidance for output. Troubleshooting steps: Check if the model prompt clearly specifies an output format that matches cluster document fields, and confirm that the model context parameter configuration is reasonable.
- Symptom: Model calls are rejected by the API, but direct use of curl to test the model interface returns normal results. Troubleshooting steps: Check if `maxContext` exceeds the maximum context limit supported by the currently used model, and confirm that no content review rules from the model provider have triggered interception.

## How to confirm configurations are correctly set
- Execute a curl command to test `AIPROXY_API_ENDPOINT`, confirming normal access to the AI Proxy service root address.
- Import a real cluster change ticket document, trigger the model’s compliance review, and verify that the output content matches the fields and units of the cluster document.
- Simulate a small-scale cluster change operation, trigger model compliance verification, and confirm that there are no timeouts or errors in the call.
- View the model call logs in the FastGPT backend, confirming that the actual call values of parameters such as `maxContext` and `maxTokens` match the preset configurations.
