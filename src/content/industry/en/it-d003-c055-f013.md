# Security and Compliance Material Review for Capacity Planning and Resource Scaling: Permissions and Data Isolation

## What data looks like for this category
This category's data primarily comes from cloud bills, monitoring systems, business forecast reports, and stress test results. Daily produced documents include capacity planning reports, scaling application forms, resource utilization reports, and budget calculation sheets. Data update cycles are usually weekly or monthly. For scenarios with frequent adjustments, updates can be completed quarterly. Document fields include resource type, peak load threshold, instance specification, budget limit, and more. Corresponding units include compute core count, memory capacity units, and currency units.

## Constraints imposed on permissions and data isolation workflows
Data sources are scattered and involve multiple types of sensitive business resource information. Resource data from different teams has clear ownership boundaries. Strict isolation is required to prevent unauthorized access. Differences in update frequencies require permission configurations to match the circulation cycles of different data. Monthly updated budget data needs stricter approval permissions. Documents contain sensitive budget and resource configuration information. Different roles can only access documents within their job responsibilities. Cross-team resource scaling applications must pass permission checks. This ensures only authorized personnel can initiate or approve operations.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| Team ID `teamId` | Bind to the unique `teamId` of the corresponding business team | Clearly isolate resource planning data across different teams to prevent cross-team unauthorized access |
| Scene Template ID `tmbId` | Configure a dedicated `tmbId` for capacity planning and resource scaling scenarios | Bind permission checks to specific business scenarios to prevent permission abuse by unrelated templates |
| Member Permission Scope | Divide by role: team leads can configure full rules, SREs can only view and adjust resource data for their own team | Match the role responsibility boundaries of this category to avoid high-severity outages or budget overruns caused by misoperations |
| Data Isolation Scope | Limit that resource data under `teamId` is only visible to authorized members | This category of data includes sensitive budget and resource configuration information, so access scope must be strictly controlled |
| Approval Permission Configuration | Set that scaling applications require approval from the team lead | Align with the error consequence control requirements of this category to strengthen compliance of change processes |

## Three common configuration errors
- The interface displays the prompt "No permission to operate this conversation record". The cause is that the current user is not bound to the corresponding `teamId`, so they cannot access capacity planning and resource scaling data for that team.
- The number of guest window links for team tier subscriptions cannot be adjusted to 100. The cause is that no custom limit is configured under the corresponding `teamId`, and the default limit is 10.
- After configuring a locally deployed model, the test returns a permission error. The cause is that model access permissions are not bound to the current `teamId`, leading to cross-team permission check failure.

## How to confirm configuration is complete
- Log in to the corresponding `teamId` on FastGPT v4.17.0, and check that the visible scope of capacity planning reports only includes authorized members.
- Initiate a scaling application, and verify that the approval process only grants operation permissions to team leads.
- Attempt to modify the number of guest window links, and confirm that custom values can be set.
- Call the locally deployed model for testing, and verify that only authorized users can access bound model resources.
