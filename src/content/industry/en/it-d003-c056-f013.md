# Security and Compliance Material Review for Object Storage and Backup Services: Permissions and Data Isolation

## What data does this category include
The data for this category typically originates from object storage consoles, backup systems, access logs, and customer policy tables. Daily maintenance documents include bucket configuration files, backup policy configurations, recovery operation records, and lifecycle rule configuration items.
Data updates occur either via daily synchronization or in real time when policies are changed. Fields include bucket permission identifiers, backup task status, access IP records, and policy application scope. There are no uniform fixed units, as values vary based on configuration item type.

## How do these characteristics create constraints for permissions and data isolation
Data in this category is multi-sourced and updates dynamically with policies. This requires permissions and data isolation configurations to adapt to the permission verification logic of multiple data sources.
Daily maintenance documents are mostly static configuration items, so strict isolation of operation scopes between different operations and maintenance personnel must be enforced to avoid accidental changes to core policies.
Access logs, as core evidence for compliance reviews, require non-tamperable storage configurations to ensure traceability during reviews.
Permission binding for backup tasks and recovery operations must match the application scope of buckets and backup policies, preventing unauthorized triggering of backup or recovery processes to avoid data leaks or task anomalies.

## How to configure settings
This configuration specification is based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Unique identifier bound to the corresponding bucket | Ensures permission verification corresponds one-to-one with bucket resources, preventing cross-team permission escalation |
| `tmbId` | Assigned by grouping backup tasks | Achieves permission isolation for different backup tasks, allowing only authorized members to view recovery records for corresponding tasks |
| Bucket access permission policy | Principle of least privilege, only open necessary operation scopes | Meets compliance review requirements, reduces unauthorized access risks |
| Recovery operation audit threshold | 2 times/day (calibrated based on actual testing) | Prevents permission abuse from batch recovery operations, balancing operational efficiency and security |
| Access log retention period | 180–365 days | Meets traceability requirements for compliance material reviews |
| Team member permission configuration | Divided by role (operations/audit/regular) | Matches daily operation and maintenance division scenarios, simplifies permission management workflows |

## Three common configuration mistakes
- Calling the FastGPT API returns a permission denied error, with a corresponding status code of 403. The cause is that the `teamId` parameter is not correctly bound, resulting in permission verification failing to match the authorized scope of the target bucket.
- A team member accidentally modifies the global backup policy, leading to cross-departmental backup data leaks. The cause is that permissions are not divided by role, and regular operations staff are granted policy editing permissions.
- After enabling team management features for local deployments, former team members cannot be deleted. The cause is that member removal was not completed on the console's team management page, and only the local account was deleted.

## How to confirm configurations are correct
- When calling the FastGPT API, check that the request parameters include the correct `teamId`, ensuring it matches the authorized identifier of the target bucket.
- View the team management page to confirm that member permissions and role divisions align with daily operations and maintenance divisions, with no over-permission configurations.
- Check the access log retention configuration to confirm the retention period meets compliance review requirements, and that logs cannot be tampered with.
- Initiate a test recovery operation to confirm only authorized members can trigger it, and unauthorized members cannot access the corresponding backup data.
