# Security and Compliance Material Review for Ticket Acceptance and Issue Tiering: Citation Sources and Traceability

## What this category of data looks like
Core data for ticket acceptance and issue tiering comes from ticketing systems, chat logs, product logs, and customer contract SLAs, with update frequencies of daily or real-time. Daily processing involves documents including customer tickets, issue tiering tables, processing records, and service reports. Fields include ticket ID, customer identifier, issue type, tiering level, processing time limit, associated SLA clauses, and more. The length of individual ticket content varies widely, ranging from short inquiries to complete troubleshooting records.

## What constraints do these characteristics impose on the citation sources and traceability process
Since data sources cover real-time interactions and structured business documents, the traceability process must bind specific business identifiers to ensure traceability back to the original ticket and processing node. Real-time updated ticket data requires that cited reference documents do not have outdated discrepancies, and must be synchronized with the latest processing records. The wide variation in ticket content length requires that traceability configurations adapt to business information of different lengths, avoiding truncation of core problem descriptions. At the same time, error consequences include response timeouts and SLA breaches, so the traceability process must not add additional processing time.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `quoteMaxToken` | `800–1200 token` | Ticket content includes structured fields and unstructured descriptions. This range covers the core information of a single ticket without exceeding the context limit, and adapts to the context restrictions of FastGPT v4.17.0 |
| `responseData` | Includes ticket ID, processing record ID | Ticket categories must bind specific business identifiers to ensure traceability can locate the original ticket and internal processing links, and avoid disconnecting citation sources from specific businesses |
| `detail` | Enabled | Issue tiering needs to associate fields from the original tiering table and processing records. When enabled, original document fragments that serve as the basis for tiering can be displayed, meeting compliance review requirements |
| Single traceability recall limit | Top 3 entries | Issue tiering for ticket acceptance usually relies on the 3 most relevant reference documents. Excessive entries will increase context load and extend processing time |
| Citation source display location | Ticket details page sidebar | Customer service teams need to quickly view traceability information while processing tickets. The sidebar layout does not interfere with the current operation interface, and aligns with daily usage habits |

## Three common misconfigurations
- Citation sources are only displayed at the bottom of the conversation, and are not bound to the corresponding ticket ID. Cause: The `responseData` parameter is not configured to bind business identifiers, and only the default knowledge base document name is displayed, which cannot be associated with the specific ticket being processed.
- In non-tool call mode, the large model output does not associate content from the ticket knowledge base, and only returns generic responses. Cause: The `detail` parameter is not enabled, or the `quoteMaxToken` value is too small, resulting in core ticket content being truncated and failing to trigger the recall logic.
- When tracing, only the document file name is displayed, and the uploaded original document fragments cannot be viewed. Cause: The `responseData` parameter is not configured to associate the original document storage path, and only the document name is displayed, which cannot locate the original ticket content uploaded by the customer.

## How to confirm the configuration is correct
- Submit a test ticket, and check whether the citation source area displays both the ticket ID and processing record ID at the same time.
- Adjust the value of `quoteMaxToken`, verify that the context length changes as expected, and confirm that core ticket content is not truncated.
- After enabling the `detail` parameter, check whether the tiering basis fragments and processing record details of the original ticket are displayed.
- After submitting the ticket, confirm that the citation source display position aligns with the team's daily operation interface layout.

The values provided are common starting points and should be evaluated against the reader's own samples.
