# Security and Compliance Material Review for Ticket Handling and Issue Tiering: Model Integration and Configuration

## What this category of data looks like
This category of data primarily comes from ticketing systems, chat logs, product logs, and customer contract SLA documents. Daily processed documents include ticket text submitted by customers, standardized issue tiering tables, historical processing records, and service reports. Data update cycles fall into two categories: real-time and daily. Real-time data includes newly submitted tickets and online chat content. Daily updated data consists of that day’s aggregated processing records and service reports. Data fields cover ticket identifiers, issue descriptions, tiering tags, associated SLA clauses, handler information, and more. This supports mixed semi-structured and unstructured input.

## What constraints do these characteristics impose on model integration and configuration
The data characteristics of this category impose multiple constraints on model integration and configuration. Real-time tickets and chat content require the call chain to support low-latency responses. This avoids timeouts that disrupt ticket processing timelines. Compliance data containing SLA clauses requires model outputs to strictly match the original text. This prevents deviations or tampering. Mixed semi-structured and unstructured input formats require models to have flexible text understanding capabilities. Both real-time and daily update cycles require models to support dynamic context loading. This also balances context length and token consumption. In addition, security and compliance reviews require retention of call logs and reference records. Configuration must balance traceability and call efficiency.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the context length of tickets and chat logs, avoids truncating critical SLA or customer information |
| `maxTokens` | 1500–2000 token | Meets output length requirements for single-round issue tiering and compliance reviews |
| `temperature` | 0.1–0.3 | Ensures output consistency for security and compliance reviews, reduces risk of subjective bias |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, for example http://aiproxy:3000 (do not append /v1 or /chat/completions, do not use single-model service addresses) | Configures the access address for the AI Proxy service. This is a required environment variable for the App/Admin server |
| `AIPROXY_API_TOKEN` | AI Proxy administrator Token. Must match the AI Proxy server configuration and not be empty | Configures the access authentication credential for the AI Proxy service. This is a required environment variable for the App/Admin server |
| `vision` | Enabled | Supports recognition of screenshot-based compliance materials in tickets, adapts to multimodal input requirements |

## Three common configuration mistakes
- Symptom: A connection error prompt appears after submitting a model call. Cause: The App/Admin server has not correctly configured `AIPROXY_API_ENDPOINT` (AI Proxy service root address), or `AIPROXY_API_TOKEN` (AI Proxy administrator Token) is configured incorrectly. This prevents connection to the AI Proxy service.
- Symptom: When adding a new channel on the model provider page, a prompt stating getModifierState is not a function appears. Cause: Front-end page rendering exception. Refresh the page or re-enter the model configuration module, then retry.
- Symptom: Model calls display an overdue balance, but the account corresponding to the API key has available remaining balance. Cause: The billing account for the API key is not correctly associated, or the configured call quota limit has been triggered.

## How to confirm the configuration is complete
- Check the environment variable configuration of the App/Admin server. Confirm that `AIPROXY_API_ENDPOINT` (AI Proxy service root address) and `AIPROXY_API_TOKEN` (AI Proxy administrator Token) are correctly configured and not empty.
- Upload a test ticket containing a standard issue description and SLA clauses. Initiate a model call. Verify that the returned issue tiering results follow preset rules, and no connection errors or parameter over-limit prompts appear.
- Upload a test ticket with a screenshot attachment. Confirm that the model can recognize the image content and include associated explanations in the returned results.
- View the model call logs. Confirm that the token consumption for each call falls within the range configured by `maxContext` and `maxTokens`, with no abnormal overflow.
