# Security and Compliance Material Review for Ad Account Opening Audit: Permission and Data Isolation

## What this category’s data looks like
Data for this category is generated across the full ad account opening process. Daily documents include account opening application forms, business license scans, corresponding industry access qualification documents, and account opening audit records.
Data sources include ad platform backend application data, main body verification data from the National Enterprise Credit Information Publicity System, paper or electronic materials submitted by customers, and the platform’s built-in industry access rule library.
Update frequency is triggered once per application or via daily batch sync. Each data entry is tied to a unique account opening application number, and includes fields such as main body name, unified social credit code, qualification validity period, and audit node status.

## What constraints do these characteristics impose on permission and data isolation
This category’s data includes customer-sensitive qualification materials and internal platform rules, and is tied to the owning main body via the account opening application form. As such, permission and data isolation must align with the business scope of different roles.
Agent operations teams can only access account opening application data they have undertaken, and must not view customer materials from other agents.
Audit specialists must limit their rule library access scope by the industry classification of the application, to avoid unauthorized calls to access rules for non-corresponding industries.
Sensitive materials submitted by customers must be encrypted for storage, and can only be decrypted and viewed at authorized nodes within the audit process, to prevent data leaks.
When data updates are triggered, permission ownership must be synchronized and verified, to avoid cross-application data confusion.

## Configuration settings
These configurations are adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` binding rule | Fully tied to the agent team ID associated with the account opening application | Matches the agent’s business ownership scope to prevent cross-team data access |
| Sensitive material encryption strategy | AES-256 encryption, with keys distributed per `teamId` dimension | Only audit nodes from the corresponding team can obtain decryption keys, preventing cross-team leaks |
| Permission check delay threshold | No more than 200 milliseconds | Ensures response speed of the audit process while avoiding business impact from permission check timeouts |
| Data sharding isolation rule | Divide data shards by `teamId`, with maximum storage per shard not exceeding 500 GB | Adapts to the agent’s business scale, avoiding overloading of single shards |
| Audit node access restriction | Only allow roles in the current audit link to access materials for corresponding applications | Limits access scope for sensitive materials, opening permissions only at necessary stages |

## Three common configuration mistakes
- Symptom: After restarting the Docker container, an `Access denied for user 'root'@'localhost'` error appears when executing audit data queries. Cause: Environment variables that tie database permission configurations to `teamId` were not persisted, so permission configurations are lost after restart.
- Symptom: After adding a custom audit plugin to the workflow, no input and output parameter configuration options are displayed. Cause: No permission mapping configured for `teamId`, so the plugin cannot obtain authorized data scope, leading to parameter loading failure.
- Symptom: After logging in with an agent account, the user can view account opening application data from other agents. Cause: The permission check logic does not filter the application list by `teamId`, and returns full data directly.

## How to confirm configurations are correct
- Use the FastGPT v4.17.0 test environment, switch test accounts with different `teamId`s, verify that only account opening application data associated with the corresponding ownership can be viewed.
- Upload sensitive qualification materials such as business licenses, verify that stored data is in AES-256 encrypted format, and unauthorized accounts cannot decrypt or view the data.
- Trigger an audit process for an account opening application, verify that the permission check delay does not exceed 200 milliseconds.
- Restart the Docker container, execute the audit data query again, verify that no permission error occurs.
