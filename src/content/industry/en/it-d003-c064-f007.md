# Security and Compliance Material Review for Tender Document Preparation: Conversation Logs and Auditing

## What this category of data looks like
This category of data is generated for a single tender project. Sources include tender announcements, tender documents, enterprise qualification libraries, and supplier quotation libraries. Daily processed documents include tender documents, qualification certificates, business deviation tables, and technical deviation tables. A single tender document is associated with multiple types of qualification and quotation materials. Data updates occur once per project, with new or adjusted content only added during the preparation period for that tender project. Document fields include tender clause numbers, response content, qualification file numbers, quotation details, and other fields. There are no universal fields that can be reused across multiple projects.

## What constraints these characteristics impose on conversation logs and auditing
The exclusive data attributes of a single project require conversation logs to be strictly bound to the `chatId` of the corresponding tender project, to avoid cross-project data confusion. The temporary data nature of each project requires audit logs to be archived by project, and context association rules from historical projects cannot be reused. The multi-field association requirement for documents requires logs to record interaction details for each clause response and qualification verification step, to ensure traceability of the response process for every tender requirement. The severe consequences of errors require audit logs to fully retain the entire interaction chain, including parameter adjustments and material reference processes, to facilitate traceability and troubleshooting after a bid rejection. The temporary nature of data updates requires log retention periods to be tied to the project cycle. After the project ends, logs can be archived or cleaned up as needed, to avoid invalid data occupying storage space. This configuration is implemented based on FastGPT v4.17.0.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique identifier of the current tender project, do not reuse historical project IDs | Avoid cross-project context confusion, aligns with the exclusive data characteristics of single projects |
| `responseChatItemId` | Record the interaction item ID for each qualification verification and clause response, ensure no duplicates within a single project | Accurately trace the response process for individual tender requirements, facilitate audit issue location |
| `detail` | Enable full log recording, including original questions, generated content, and referenced qualification file IDs | Meet the full-chain traceability requirements for tender project audits, cover all operational details |
| Single context item count | Keep the first 3 historical interactions, calibrated through actual testing | Tender project interactions revolve around current tender clauses; excessive historical content will interfere with current responses |
| Log export limit | 50,000 entries, calibrated through actual testing | Prevent export timeouts while covering all log data for a single tender project |
| Log archiving cycle | Tie to the project cycle, retain for 180 days after project completion | Meet the archiving requirements for compliance reviews, while avoiding long-term storage of invalid data |

## Three common configuration errors
- The symptom is that after setting the single context item count to 1 in the workflow, historical conversation records from a very old project are still associated. The cause is failure to strictly bind `chatId` to the unique identifier of the current tender project, and reuse of an old project ID. This causes cross-project context matching.
- The symptom is that an extra historical record appears when using the API to start a new tender project conversation. The cause is failure to correctly pass the `chatId` parameter in the API call. The system uses the global default context by default, resulting in an extra historical entry being generated.
- The symptom is an error `$lookup with 'pipeline' may not specify 'localField' or 'foreign'` when viewing audit logs, or log exports stop after retrieving 50,000 entries. The cause is that log query or export configurations are not adapted to the data volume of the tender project, or the aggregation syntax violates database rules.

## How to confirm the configuration is correct
- Review the workflow configuration, confirm that the `chatId` parameter is bound to the unique identifier of the current tender project, and no historical project IDs are reused.
- Generate a test qualification verification interaction, check that the log fully records all full content of the `detail` field, including original questions and referenced qualification file IDs.
- Call the API to start a new tender conversation, check that the returned result contains no extra historical records, and only includes interaction content from the current session.
- Attempt to export all audit logs, confirm that the number of exported entries matches the actual log volume of the project, with no mid-export stops.
