# Security and Compliance Material Review for Search Ad Keyword Management: Conversation Logs and Audits

## What the Data for This Category Looks Like
Daily documents for this category include keyword lists, negative keyword tables, bid records, and search term reports. Data typically comes from search ad backends, search term reports, ranking bid data, and landing page data. Update frequencies are mostly daily or weekly. Individual data entries usually include fields such as keyword text, matching mode, bid amount, search trigger count, and landing page jump path. Units include Chinese yuan, counts, characters, and more. This category centers on user-initiated search keywords, differing from feed advertising categories that focus on creative materials.

## Constraints These Characteristics Impose on Conversation Logs and Audits
Data sources are scattered and linked across multiple operational stages. Conversation logs must cover full-process interactions including keyword queries, negative keyword checks, and bid adjustments. Otherwise, compliance issues cannot be traced back. Daily or weekly update cycles require log retention periods to match data update cycles. This prevents missing critical nodes during audits. Structured data with multiple fields requires logs to record complete metadata. Otherwise, violations or inefficient operations cannot be located. Given the characteristics of user-initiated search terms, logs must distinguish between user-triggered search terms and system-recommended extended keywords. This ensures accurate tracing of compliance risk points during audits.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Log retention period | 7–30 days | Matches daily/weekly data update cycles, covers full audit periods |
| Log record fields | Includes `chatId`, `responseChatItemId`, `detail` | Covers complete metadata for keyword interactions and response results, meets compliance tracing requirements |
| Log storage capacity | 1000–2000 MB | Matches average daily keyword operation volume, prevents storage overflow |
| Log synchronization frequency | Every 5 minutes | Ensures real-time synchronization of audit data, avoids delays impacting problem troubleshooting |
| Audit trigger rules | Calibrated based on actual testing | Adapts to compliance verification and risk alert requirements for different brands |
| Log export format | JSON format | Compatible with data import and analysis tools for search ad backends |

## Three Common Configuration Mistakes
- Phenomenon: After executing a delete conversation record operation, the corresponding entry remains in the log list, and the POST request returns a non-200 status code. Cause: Cascading delete rules for associated logs are not configured. Only the main `chatId` index is deleted, and sub-log items corresponding to `responseChatItemId` are not cleaned up synchronously.
- Phenomenon: After offline deployment of FastGPT v4.17.0, calling the interface returns an error stating that the cl100k.tiktoken file cannot be loaded. Cause: The local token model file is not downloaded and configured in advance. The default reliance on external network resources causes the request to fail.
- Phenomenon: Only partial keyword text is displayed in audit logs, and matching rules and trigger results cannot be viewed in full. Cause: Full record configuration for the `detail` field is not enabled. The system automatically truncates overly long keyword and matching log content.

## How to Verify Proper Configuration
- Manually trigger a keyword adjustment or negative keyword check operation. Confirm whether the log list includes complete `chatId`, `responseChatItemId`, and `detail` field information.
- Review the available storage directory space. Confirm that the configured storage capacity matches the current average daily operation volume.
- Execute a delete conversation record operation. Verify that the corresponding log entries are fully cleaned up.
- Initiate an interface call after offline deployment. Confirm that no errors dependent on external network resources occur.
