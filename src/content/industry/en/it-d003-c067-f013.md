# Security and Compliance Material Review for Data Security Classification and Grading: Permissions and Data Isolation

## What this category of data looks like
This category of data primarily originates from data asset inventory results, database metadata, business system documentation, and public regulatory texts. Daily generated documents include four types: data catalogs, classification and grading rules, important data identification tables, and review minutes. Data updates are triggered quarterly or after a single business system change. Document fields include asset ID, data classification tags, grading level, responsible person information, and compliance review status. Some fields require population via association with external system metadata, and no unified fixed units exist.

## What constraints these characteristics impose on the permissions and data isolation workflow
Scattered data sources linked to external system metadata require permission isolation to support fine-grained access control for cross-system metadata. Multiple document types have uneven update frequencies, so a change-triggered permission synchronization mechanism must be configured to prevent old permissions from being paired with unupdated classification rules. Documents contain sensitive compliance review status and responsible person information, so permission configurations must distinguish three operational permission levels: review, view, and edit. This prevents unauthorized personnel from modifying classification rules or tampering with review results. In cross-team collaboration scenarios, different data governance teams must be restricted to accessing only classification and grading data for their corresponding business domains, to avoid cross-domain data leaks.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| Team Permission Binding | Bind `teamId` to business domain data catalogs | Restrict team access scope precisely based on the characteristic of scattered data sources requiring cross-domain isolation |
| Sensitive Document Permission Allocation | Divide view and edit permissions by role | Distinguish operational permission levels based on the characteristic that documents contain compliance review status |
| Metadata Synchronization Cycle | Synchronize every 8–12 hours | Balance timeliness and resource consumption based on the update rhythm triggered quarterly or after system changes |
| Permission Activation Delay | No more than 600 seconds | Adapt to real-time collaboration scenarios and avoid issues where permission changes do not take effect immediately |
| Cross-domain Isolation Switch | Enable `tmbId`-level fine-grained isolation | Prevent cross-business-domain data leaks based on multi-team collaboration requirements |
| Document Storage Quota | No more than 1000 MB per business domain | Avoid single-domain data overload based on the storage capacity characteristics of data catalogs |

## Three Common Misconfigurations
- Symptom: After configuring team write permissions, members still cannot create classification and grading rule documents. Cause: Member accounts are not associated with the corresponding `teamId`, so the permission scope does not cover the target business domain data.
- Symptom: After manually triggering metadata synchronization, classification and grading rules are not updated. Cause: Automatic synchronization trigger conditions associated with `tmbId` are not configured, and only fixed-cycle synchronization is used without associating system change events.
- Symptom: Unauthorized members can modify review minutes content. Cause: Edit and view permissions are not distinguished, and all team members are set to edit mode.

## How to Verify Proper Configuration
- Log in to the FastGPT v4.17.0 permission management page, and verify whether the target member is bound to the corresponding `teamId`.
- Attempt to access sensitive documents using an unauthorized member account, and confirm that review minutes and classification and grading rules cannot be viewed or edited.
- Trigger a single business system change, and verify that metadata is synchronized according to the set cycle.
- Check the permission change log, and confirm that the permission activation time meets the preset delay requirement.
