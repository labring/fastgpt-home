# Security and Compliance Material Review for Database Operations: Permissions and Data Isolation

## What the Data for This Category Looks Like
Core data for this category originates from database monitoring, audit logs, SQL execution plans, and ticketing systems. Associated daily documents include database change orders, slow SQL reports, backup records, and permission application forms. Data updates typically occur daily or in sync with individual database changes. Documents contain fields such as instance identifiers, operation times, permission application entries, and execution results. No fixed unified format exists for these documents, and materials must be archived according to operations ticketing workflows. The most time-consuming daily tasks include slow query troubleshooting, structural change review, and backup recovery verification. Operational errors may cause data corruption, query timeouts, or permission boundary violations.

## What Constraints These Characteristics Impose on Permissions and Data Isolation
Decentralized data sources require permission checks to cover multiple system entry points. Unified isolation rules are necessary to prevent cross-system permission boundary violations. Updates trigger alongside database changes, so systems must dynamically adapt to real-time permission change requirements to avoid permission configuration lagging behind database structural adjustments. Unstructured document fields mean the permission review process must support field parsing logic for multiple document types, to ensure accurate review of permission applications. The most time-consuming slow query and change review links require strict access range restrictions, to avoid query timeouts or data corruption caused by permission boundary violations. Permission application form workflows must bind to the instance access permissions of operations staff, to prevent unauthorized personnel from operating production databases.

## How to Configure Settings
Configuration options for FastGPT v4.17.0 can refer to the following settings:

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Permission Isolation Scope | Divide by database instance groups, bind `teamId` to the team that owns the instance | Matches instance ownership data from ticketing systems and database monitoring, ensuring consistent binding of permissions to teams |
| Instance Access Whitelist | Only allow operations staff `teamId` and designated DBA accounts to access | Prevents unauthorized personnel from accessing production database instances, reducing the risk of unauthorized operations |
| Audit Log Retention Period | 180 days | Meets security and compliance log retention requirements, and aligns with the time span of daily audit troubleshooting |
| Sensitive Data Desensitization Rule | Desensitize sensitive fields in permission application forms using `first 30% of characters` | Avoids leakage of sensitive business data during permission review |
| Permission Change Sync Frequency | Sync with each change | Aligns with the update rhythm of database changes, ensuring real-time synchronization of permission rules and actual changes |
| Container Permission Persistence Configuration | Enable local volume mounting to store permission configurations | Prevents loss of permission configurations after container restarts, and is compatible with Ubuntu deployment scenarios |

## Three Common Misconfigurations
- The symptom is an insufficient permissions error when executing SQL after restarting the Docker container. The cause is that the permission configuration bound to `teamId` was not persisted after the container restart, resulting in a reset of the operations account's access permissions.
- The symptom is that database instance access rules are not updated after a permission application form is reviewed. The cause is that the permission change sync frequency was set to daily sync, rather than triggering updates in real time with tickets.
- The symptom is that cross-instance sensitive data is returned during slow SQL queries. The cause is that the permission isolation scope does not cover the data source of the SQL execution plan, resulting in failed cross-instance permission checks.

## How to Verify Proper Configuration
- Log in using the operations account bound to `teamId`, and verify that only database instances within the specified range can be accessed.
- Submit a test permission application form, and check whether sensitive fields are processed according to the configured desensitization rules.
- Restart the database operations container, and verify that the permission configuration was not lost and the operations account can still normally access authorized instances.
- View the audit log archive records, and confirm that operation records have been stored according to the configured retention period.
