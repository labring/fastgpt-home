# Security and Compliance Material Review for Data Masking: Permissions and Data Isolation

## Data Characteristics of This Category
Data processed in this category originates primarily from enterprise databases, data dictionaries, self-developed masking tools, and access approval systems. It is updated per project batch or single task. Daily output documents include masking plans, field mapping tables, masking verification reports, and approval records. Data fields include sensitive information identifiers, original data content, masking rule configurations, verification results, and approval statuses. There are no fixed standard units, and configurations are adjusted flexibly based on the data types involved in the project.

## Constraints on Permissions and Data Isolation
Data sources for this category are scattered, covering databases, data dictionaries, masking tools, and access approval systems. Permissions and data isolation must cover access permission verification for all data access channels. Following the per-project batch update rhythm, permission configurations must support quick adjustment and revocation of permissions per project. Documents containing sensitive information identifiers, original data content, and approval records require strict layered setting of operation scopes for view, edit, and approval roles. Fields containing sensitive information and masking rules must ensure only authorized personnel can access original sensitive data and complete configuration items.

## Configuration Guidelines
This configuration rule applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` binding rule | Only associate data sources and documents from the current project | Match the per-project batch update data characteristics, isolate masking data across different projects |
| `teamId` permission check | Enable `teamId` verification for interface access | Ensure only authorized services can call masking processing interfaces |
| Member role configuration | Divided into three categories: data view, rule configuration, approval and verification | Match the layered operation requirements of documents, prevent unauthorized access |
| Sensitive data access logs | Retain for 30 days | Meet log retention requirements for compliance audits |
| `tmbId` call permission | Only bind the `tmbId` of the specified application | Limit the scope of callers for masked data, prevent unauthorized applications from accessing |

## Three Common Misconfigurations
- Symptom: Unable to open the team management page, or view team member operation records. Cause: Administrator role permissions for the corresponding `teamId` are not configured, no access authorization entry.
- Symptom: Cross-team application calls to the masking interface return a permission denied error. Cause: The caller has not bound a dedicated `tmbId`, or the `tmbId` does not match the `teamId` of the masked data. The system blocks unauthorized requests.
- Symptom: Masking rules for sensitive fields are modified by unauthorized personnel. Cause: Member role permissions are not set in layers, and regular members are assigned rule configuration permissions.

## How to Verify Successful Configuration
- Enter the team management interface, check whether the data sources bound to the current `teamId` match the data sources of the currently processed project.
- Initiate a masking interface call with a preset `tmbId` parameter, verify that the interface can complete the masking process normally and return results.
- View the member role configuration list, confirm that the operation permissions of each role match the preset layered rules.
- Export the sensitive data access logs, confirm that the log recording scope meets compliance audit requirements.
