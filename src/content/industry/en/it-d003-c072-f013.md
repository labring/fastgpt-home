# Security and Compliance Material Review for Data Collection Task Design: Permissions and Data Isolation

## What this category of data looks like
This category of data primarily comes from customer requirements, public data sources, collection tools, and internal sample libraries. Update cycles follow individual project cycles or weekly intervals. Four core document types are produced daily: collection plans, sample specifications, authorization statements, and task schedules. Fields include sample coverage scope, data field definitions, authorization compliance deadlines, and task execution nodes. Units are based on sample volume, time cycles, and compliance clause numbers, with no unified fixed unit system.

## Constraints for Permissions and Data Isolation
Sensitive compliance materials for this category are strongly bound to individual projects, leading to three core constraints.
First, collection plans and authorization statements for different projects must isolate permissions by project to prevent cross-project leakage of compliance documents.
Second, sample library data must distinguish access scopes between internal collection teams and customer algorithm teams to avoid unauthorized access to sensitive samples.
Third, weekly updated task schedules and field specifications must be synchronously bound to the permission configuration of the corresponding project, to ensure permission changes take effect alongside data updates.
Additionally, authorization documents used for collection legitimacy checks must be strictly associated with project identifiers to prevent unauthorized access.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Team Permission Binding `teamId` | Assign an independent `teamId` for each collection project | Matches the core requirement of single-project data isolation |
| Member Role Association `tmbId` | Assign independent `tmbId` for collection teams and customer algorithm teams | Distinguishes access scope and operation permissions for different entities |
| Sensitive File Encryption Configuration | Enable encrypted storage for authorization statements and sample specification files, bind key validity period to project cycle, with a maximum of 90 days | Prevents leakage of compliance materials during storage |
| Permission Check Trigger Rules | Trigger checks during data access, task editing, and authorization viewing, with single check duration not exceeding 5 seconds | Covers core operation scenarios and avoids permission check delays |
| Cross-Project Access Restriction | Disable cross-`teamId` data pulling and sharing permissions, set cross-project request timeout to 30 seconds | Prevents unauthorized projects from accessing sensitive collection data |

## Three Common Configuration Mistakes
- A UI prompt reading "No permission to operate this conversation record" appears when the current operating subject is not bound to the corresponding project's `teamId` or `tmbId`, causing permission verification to fail.
- An inability of team members to create shared programs occurs because project-level permission groups are not configured correctly, and operation permissions for the corresponding `tmbId` are not assigned to members.
- A permission error during local deployment model testing occurs because the model configuration is not bound to the current project's `teamId`, leading to cross-project permission verification failure.

## How to Verify Successful Configuration
- The permission verification function of FastGPT v4.17.0 can be used to attempt accessing documents of the corresponding collection project via a non-project member account. Confirmation that viewing or editing is not possible verifies that permission isolation is effective.
- Switching to the account bound to the project's `teamId` and attempting access to the authorization statement file, with confirmation of normal viewing, verifies that the permission configuration is correct.
- Submitting a cross-project data pulling request and confirmation that the system returns a permission insufficient prompt verifies that cross-project access restrictions are effective.
- Checking the storage status of sensitive files and confirmation that encryption configuration is enabled verifies data storage security.

The values provided here are common starting points and should be measured against samples relevant to the specific deployment.
