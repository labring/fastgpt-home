# Security and Compliance Material Review for Penetration Testing Services: Permission and Data Isolation

## What the data for this category looks like
Penetration testing service data includes four daily document types: test authorization letters, penetration test reports, vulnerability recurrence records, and rectification suggestions. Data sources include target systems, general vulnerability databases, automated scanner results, and manual verification records. Documents are organized by project, with each project corresponding to a separate dataset. Fields include authorized subject scope, vulnerability severity level, recurrence steps, impact scope, and more. Updates occur after each project is completed or when the target system undergoes a major version iteration.

## What constraints these characteristics impose on the "permission and data isolation" link
Penetration testing service data contains sensitive target system information and compliance authorization documents. The requirement for independent per-project updates means permissions must be divided by project granularity. Unlike vulnerability scanning services, this category includes manual attack path verification steps, so access permissions for manual verification records must be managed separately. Test data and authorization documents for different projects must be strictly isolated to prevent cross-project data leaks or compliance risks. Access to corresponding data must be restricted only to authorized red team engineers and security team members.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Assign a unique `teamId` to each penetration testing project | Matches project-based data isolation requirements to avoid cross-project data confusion |
| `tmbId` | Bind documents such as test authorization letters and vulnerability recurrence records to the corresponding project `teamId` | Ensures compliance documents are only visible to authorized project members |
| Team member invitation verification rules | Calibrated via actual testing | Resolves invalid username issues and adapts to internal enterprise identity systems |
| Operation log scope | Restricted to operations under the current `teamId` | Facilitates auditing testing process compliance |
| Timeout threshold | `600 seconds` | Adapts to the longer duration scenarios of manual verification steps |
| Document storage limit | `1000 MB` | Matches the conventional storage scale of single-project test documents |
| Single vulnerability database search limit | `Top 6 entries` | Meets conventional vulnerability query needs |

## Three common configuration mistakes
- An invalid username prompt appears after entering team member usernames. This occurs because the invitation operation is not restricted to the current project's `teamId` scope, leading to permission check mismatches.
- Application tool calls fail. This occurs because the application is not bound to the corresponding project's `tmbId`, and permissions are blocked during cross-project calls.
- Custom plugins fail to load properly. This occurs because the plugin configuration is not associated with the current `teamId`, leading to failed permission checks.

## How to confirm the configuration is complete
- In FastGPT v4.17.0, verify that each penetration testing project has a unique `teamId` and that corresponding documents are bound to it.
- After inviting test members, confirm that only authorized project users can access the corresponding test authorization letters and vulnerability reports.
- When testing custom plugins, confirm that only members under the current `teamId` can call the plugin.
- View the operation log to confirm that only test operation records within the current `teamId` scope are displayed.
