# Security and Compliance Material Review for Game Content Self-Check: Conversation Logs and Auditing

## What data for this category looks like
Data for this category comes primarily from story scripts, in-game text, and art assets during game development and iteration, plus publicly released regulatory compliance requirements. Daily associated documents include content self-check lists, sensitive content modification records, user agreements, and compliance review minutes.
Data updates align with game version iterations or event launch timelines, with one update per version or event.
Most document structures use structured fields: content type, review status, modification traces, and review opinions. Some art assets include metadata tags.

## Constraints imposed by these characteristics on conversation logs and auditing
Conversation logs and auditing for game content compliance self-check must adapt to the update rhythms of multiple data source types. High-frequency updates per version or event require log retention to cover the full cycle of review conversations.
Structured documents and metadata fields require audit logs to accurately link to unique identifiers of corresponding content, to avoid cross-version confusion. Regulatory traceability requirements mandate that logs include complete conversation chains: review requests, modification feedback, review opinions, and all related steps.
Mixed review scenarios for art assets and text require the audit module to distinguish log entries for different content types, to support subsequent compliance retrospective reviews. Modification traces and review opinions during the review process must be fully retained to address future compliance checks.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `chatId` | Bind to the unique version identifier of game content | Ensure each review conversation links to the corresponding version of game content, avoiding cross-version confusion |
| `responseChatItemId` | Link to the unique ID of the review node | Accurately locate the response content of a single review conversation, facilitating modification process retrospective |
| `detail` | Collect complete conversation context | Include all fields such as review requests, modification opinions, and feedback results, meeting the detail requirements for compliance reviews |
| Log retention duration | 365 days | Meet long-term traceability requirements for compliance audits |
| Log collection switch | Enable full-link collection | Cover the full process from content submission to review closure, ensuring no omissions |
| Log storage limit | 1000 MB / application | Adapt to the review data scale of a single game version, avoiding storage overflow |

## Three common misconfigurations
- After deploying FastGPT v4.17.0, marker logs show `ocr error`. This occurs when appropriate OCR collection parameters are not configured for text extraction from game art assets, leading to failure to properly identify sensitive art text.
- An error occurs after clicking the review submission button for compliance self-check. The error line references the regular expression matching step for chat records. This occurs when conversation log extraction rules are not correctly configured, or incoming chat record fields are not filled in the required format.
- A compliance review call is initiated, but no corresponding record appears in FastGPT's call logs. This occurs when the full-link log collection switch for the corresponding application is not enabled, or the collection scope does not cover the full process of the review conversation.

## How to confirm configuration is complete
- Run a compliance review process, and verify that FastGPT's call logs fully record the full-link conversation from content submission to review feedback.
- Verify that log fields include `chatId`, `responseChatItemId`, and `detail`, and that field values match the current review's game content version and node.
- Test by disabling the log collection switch, confirm no new logs are generated, then enable the switch and confirm log recording resumes, to verify the collection switch operates correctly.
- Simulate non-compliant format input, verify that corresponding error logs are generated, confirming the abnormal log capture mechanism operates normally.
