# Security and Compliance Material Review for Game Server Development and Operations: Permission and Data Isolation

## What This Category’s Data Looks Like
Daily documents for game server development and operations typically include server architecture descriptions, server launch plans, server merge plans, and incident reports. Data sources include game operation logs, online player count monitoring data, business databases, and player-submitted tickets.
Data update frequency is usually daily, or adjusted based on game event cycles. Documents related to server launches and merges are updated frequently only during active event cycles.
Document fields include server IP addresses, online player count thresholds, data validation rules, and more. Units include milliseconds, player counts, GB, and others. A single incident report can reach hundreds of MB in size.

## What Constraints Do These Characteristics Impose on Permission and Data Isolation?
Data related to game servers involves player privacy and business stability. Data sources include player tickets and real-time monitoring data. Permission isolation must cover the full access chain for sensitive data.
Frequently updated event cycle documents require dynamic adjustments alongside team permissions, to prevent unauthorized personnel from accessing capacity estimation parameters before server launches.
Server merge data validation involves cross-server data synchronization. Use `teamId` to separate cluster data managed by different operation and maintenance teams, to prevent data rollbacks or leaks.
Incident reports include details like login failures and data anomalies. Access must be restricted to core operation and maintenance and development teams only, to avoid harming player trust.

## How to Set Configurations
| Configuration Item | Recommended Approach | Rationale |
| ---|---|--- |
| Team ID Binding | Assign a unique `teamId` to each game server cluster, and bind cluster-related documents to the corresponding `teamId` | Ensure only authorized teams can access launch and merge documents for their cluster, compatible with FastGPT v4.17.0 team permission module |
| Temporary Access Token Binding | Bind `tmbId` to login-free links, set validity period to 15–30 minutes | Restrict the permission scope and validity period of temporary access, preventing unauthorized users from accessing sensitive data long-term |
| Team Role Permission Division | Divide access scope by team function: operation and maintenance teams can only view incident reports and server merge data, development teams can view architecture descriptions and server launch plans | Align with daily work boundaries for development and operation and maintenance teams, preventing unauthorized operations |
| Chat Content Export Permission | Restrict to team administrators only, export scope limited to server data belonging to the current team | Prevent unauthorized export of sensitive player tickets and incident data |
| Team Invitation Permission Configuration | Only team administrators can send team invitation links | Prevent unauthorized personnel from joining the team and accessing sensitive data |
| Permission Log Retention | Retain permission access logs for 7–14 days | Facilitate subsequent compliance reviews and abnormal issue troubleshooting |

## Three Common Misconfigurations
- Unauthorized team accounts can access server documents bound to a specified `teamId`. The symptom is a permission denied error message or empty data returned. The cause is failing to assign a unique `teamId` to each server cluster, with multiple clusters sharing the same `teamId` leading to permission confusion.
- Login-free links can be modified to use a different `tmbId` to access data from other teams. The symptom is the link jumping to display merge plans for a different team. The cause is failing to bind and validate `tmbId` against the current team’s `teamId`.
- Team members can export full game server data. The symptom is exported files containing unauthorized player ticket data. The cause is failing to limit the export scope to server data belonging to the current team, with full data export permissions left open directly.

## How to Verify Proper Configuration
- Use an unauthorized team account to attempt accessing the server architecture description document bound to a specified `teamId`, confirm the system returns a permission denied prompt.
- Generate a login-free link, replace the `tmbId` in the link with an invalid value, then attempt to access, confirm the link cannot load properly.
- Submit an export request as a team member, confirm the exported result only includes server-related data for the current team, with no information from other clusters.
- View permission access logs, confirm all access operations are associated with the corresponding `teamId` or `tmbId`, with no unbound abnormal access records.
