# Security and Compliance Material Review for Game Operation Activity Configuration: Permission and Data Isolation

## What the data for this category looks like
Core data for game operation activity configuration typically comes from operation backends, player segments, payment data, and activity logs. Daily produced documents include activity plans, reward configuration tables, launch checklists, and activity post-mortems. Activity plans note activity duration (days) and trigger conditions. Reward configuration tables include issuance quantity (units), effective time (YYYY-MM-DD HH:MM:SS). Activity logs record player IDs (strings) and trigger timestamps (millisecond precision). Data update frequency is mostly weekly or temporarily adjusted for holidays. Single configurations involve multi-dimensional fields, and there is no unified fixed batch update cycle.

## How These Characteristics Impact Permission and Data Isolation Requirements
Data sources cover multiple systems and include player private information. Permission isolation must cover the activity configuration scope of different operation teams to prevent cross-team access to sensitive data. The high-frequency update feature requires permission configurations to be synchronized quickly to adapt to weekly or temporary adjustment rhythms. Multi-dimensional field configuration content requires fine-grained permission control to distinguish access permissions for different fields such as reward values and activity times. Unlike game planning and value design, this category focuses on activity execution for already launched versions. Permission configuration must prioritize the timeliness and accuracy of activity execution. Applications and knowledge bases may belong to different teams. Clear isolation rules must be defined during cross-team calls to prevent unauthorized data leaks.

## How to Configure Settings
This configuration guide is based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Bind the unique identifier of the operation team to which the activity belongs | Match the ownership subject of the activity configuration to prevent cross-team data leaks |
| `tmbId` | Permission group identifier split by activity type | Adapt to the high-frequency update rhythm of weekly or holiday adjustments, quickly adjust permission scope |
| Permission synchronization interval | 300 seconds | Balance real-time performance and system load, adapt to daily update frequency |
| Data pull limit | Top 1000 entries | Match the single-batch data volume of activity logs, avoid system overload |
| Log storage limit | 2000 MB | Adapt to log generation volume during the activity cycle, control storage costs |
| Cross-team interface verification | Enable `teamId` verification | Correspond to scenarios where applications and knowledge bases belong to different teams, block unauthorized cross-team calls |

## Three Common Misconfigurations
- Phenomenon: An error indicating insufficient permissions or page failure appears when attempting to open the team management page. Cause: The current operation account is not bound to the `teamId` permission group of the activity.
- Phenomenon: The application calling the knowledge base interface returns no relevant content, and the application and knowledge base belong to different teams. Cause: The `teamId` verification rule for cross-team data isolation is not configured, leading to unauthorized cross-team data access.
- Phenomenon: Accounts associated with non-affiliated operation groups can modify the reward configuration table of the current activity. Cause: The `tmbId` permission group is not split by activity type, resulting in overly broad permission scope covering too many activity configurations.

## How to Confirm Successful Configuration
- Log in to an operation account associated with a team not affiliated with the activity, attempt to access the configuration page of the current activity, and confirm that the content cannot be viewed or modified.
- Call the cross-team interface, pass a `teamId` that does not match the current activity, and confirm that the interface returns a permission error prompt.
- Enter the team management page, confirm that the `tmbId` associated with the current account matches the ownership identifier of the activity configuration.
- Trigger an activity configuration update, wait 300 seconds, and confirm that the permission configuration takes effect after synchronization.
