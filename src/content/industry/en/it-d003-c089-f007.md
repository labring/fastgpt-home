# Security and Compliance Material Review for Vulnerability Scanning Services: Conversation Logs and Auditing

## What the data for this category looks like
Data for this category mainly comes from vulnerability scanners, asset inventories, CVE databases, and patch announcements. Update frequency is weekly or monthly. Daily generated documents include scanning plans, vulnerability lists, rectification work orders, and rescan reports. Each document’s fields correspond to scanning task scope, vulnerability IDs and severity levels, rectification progress, rescan results, and more. Data formats are mainly structured tables and plain text logs, with no additional custom statistical fields.

## What constraints these characteristics impose on conversation logs and auditing
Scattered data sources and fixed update cycles require conversation logs to be linked to the unique identifier of scanning tasks. This allows quick location of corresponding scanning plans and vulnerability data during audits. Document fields are relatively fixed. Audits must verify that logs include required fields such as vulnerability IDs and rectification status, to avoid missing critical information. Frequent asset scope confirmation and false positive elimination processes generate large volumes of temporary conversations. Log retention periods must be limited to meet compliance requirements. Logs for rescan result verification must retain complete interaction records for subsequent audit traceability. Unlike the tool-based closed loop of penetration testing services, logs must distinguish between automated scanning operations and manual intervention steps. This facilitates differentiation of audit traces for different operation types.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Conversation log retention duration | 30 days | Matches the retention period requirements of most compliance audits, while avoiding excessive storage resource usage |
| Log collection fields | `detail`, `chatId`, `responseChatItemId` | Covers interaction details, task identifiers, and response identifiers, meeting audit traceability and data association requirements |
| Log association with task identifiers | Automatically bind scanning plan ID | Ensures each log can be directly mapped to a specific scanning task, enabling quick retrieval and aggregation |
| Log output format | Structured JSON | Facilitates parsing and statistics by subsequent automated audit tools |
| Log anomaly alert threshold | 5 consecutive invalid scanning logs | Detects scanning task interruptions or log collection anomalies in a timely manner |

## Three common configuration errors
- Symptom: The frontend interface outputs incomplete scanning result fragments. Full content only displays after refreshing the page. No error logs are generated. Cause: Full log collection configuration is not enabled. Only partial temporary interaction fragments are cached, leading to missing frontend display data.
- Symptom: Logs do not record the parameter configuration content of scanning requests. It is impossible to retroactively review the execution conditions of scanning tasks. Cause: The `detail` field collection is not configured, resulting in missing interaction details related to scanning parameters.
- Symptom: It is impossible to count high-frequency question data by vulnerability type or scanning task. Cause: `chatId` is not bound to a specific scanning task identifier, making it impossible to filter and aggregate log data by task dimension.

## How to confirm successful configuration
- Navigate to the log management page in FastGPT v4.17.0, retrieve the scanning task logs for a specified `chatId`, and confirm that the complete content of the `detail` and `responseChatItemId` fields is included.
- Manually trigger a scanning task, check whether the logs automatically bind the identifier of the corresponding scanning plan, and verify that the association configuration is active.
- Adjust the log retention duration configuration, and check whether log storage resource usage matches the expected setting in the platform storage statistics.
- Simulate a scanning task interruption scenario, confirm whether the alert for 5 consecutive invalid logs is triggered, and verify that the alert configuration is active.
