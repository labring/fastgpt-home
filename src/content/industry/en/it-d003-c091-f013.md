# Security and Compliance Material Review for Player Customer Service and Public Opinion Processing: Permission and Data Isolation

## What data looks like for this category
Data for this category typically comes from customer service systems, community forums, app store reviews, and in-game logs. Daily processed documents include player support tickets, compensation requests, public opinion daily reports, and standardized response scripts. Data updates primarily involve real-time reception of player immediate feedback, with daily aggregation to generate public opinion daily reports and batch processing records. Common data fields include player account identifiers, original feedback content, processing progress status, and public opinion classification tags. No unified fixed custom statistical units are used.

## What constraints these characteristics impose on permission and data isolation
Data for this category includes sensitive content such as player privacy information and compensation requests. Customer service and public opinion data from different game projects must be strictly isolated to prevent player complaints caused by cross-project data leaks. Real-time updated player feedback and ticket data require permission configurations to take effect immediately, to avoid unauthorized access caused by delays. Different roles, such as frontline customer service, public opinion specialists, and compliance auditors, must correspond to different data access scopes, only allowing access to tickets and public opinion content for their assigned projects. At the same time, permissions for response scripts and daily report documents must be divided by business teams to prevent unauthorized personnel from obtaining standardized processing workflows, ensuring the accuracy of compliance reviews.

## How to configure settings
The following configurations are based on FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Divide by independent game projects, each project corresponds to a unique `teamId` | Implement isolation of customer service and public opinion data between different game projects, prevent cross-project unauthorized access |
| `tmbId` | Bind by role division: frontline customer service binds the `tmbId` for their assigned project, compliance specialists bind a read-only `tmbId` for all projects | Match the permission requirements of customer service, public opinion specialists, and compliance auditors, implement role-level data access control |
| Team data access scope | Restricted to player tickets, public opinion daily reports, and response scripts for the current assigned project, no more than 800 items returned per request | Prevent unauthorized personnel from accessing sensitive player information of other projects, control single data transmission volume |
| Sensitive data desensitization rules | Automatically hide player account and payment-related fields, only retain desensitized feedback content | Comply with privacy compliance requirements, avoid sensitive data leaks |
| Permission configuration update cycle | Automatically sync at 0:00 daily, manual trigger available for urgent changes | Match the permission requirements of daily-updated public opinion daily reports and real-time tickets |
| Cross-team collaboration permissions | Only allow specified teams to share desensitized public opinion summary data | Meet collaboration needs for cross-project public opinion analysis, while isolating core ticket data |

## Three common misconfigurations
- Symptom: Team members attempt to create or access a knowledge base for a specified project and receive a "no permission to access resource" prompt. Cause: The corresponding `teamId` is not bound to the member's role, and the permission configuration did not take effect correctly.
- Symptom: Frontline customer service accesses player ticket data from a game project they are not assigned to. Cause: `teamId` is not divided by game project, and cross-project permission isolation was not configured.
- Symptom: Public opinion daily reports contain unredacted player account or payment information. Cause: Sensitive data desensitization rules were not enabled, and raw data content was returned directly.

## How to verify successful configuration
- Log in to the FastGPT account for the assigned role, attempt to access the knowledge base for a non-assigned project, confirm that viewing or editing operations cannot be performed.
- Submit a test player support ticket, check whether the returned content has hidden sensitive fields such as player accounts.
- View the permission configuration logs, confirm that the binding relationship between `teamId` and `tmbId` has been correctly synchronized to the system.
- Modify the permission scope of a team member, wait for the configuration to take effect, then verify whether their access permissions have changed as expected.

The values provided are common starting points and should be measured against the reader's own samples.
