# Security and Compliance Material Review for On-Site Deployment Implementation: Conversation Logs and Auditing

## What the data for this category looks like
This category of data primarily originates from customer on-premises data center environments, equipment inventories, software packages, network topologies, as well as deployment manuals, installation records, configuration lists, and on-site check-in forms generated during implementation. Data is updated once per order or project phase. Documents are organized by individual project, with fields including equipment identifiers, software versions, configuration parameters, on-site operation times, implementer information, and more. There is no fixed standardized format, and it is adjusted based on the customer’s environment and project requirements.

## What constraints these characteristics impose on the conversation logs and auditing workflow
Since data comes from the customer’s private on-premises data center environment, conversation logs and auditing must strictly isolate project data to prevent cross-project leakage or confusion. The data update rhythm of once per project or phase requires that audit scope be adjusted synchronously with project phases, covering the full process of each installation configuration and environment check. Daily generated documents such as deployment manuals and equipment inventories must establish field associations with conversation logs to enable two-way tracing of operations and configurations. At the same time, the operation trails of on-site implementers must be fully recorded, ensuring audits can trace the specific content of each on-site adjustment to match the business process requirements of on-site deployment.

## How to configure the settings
This configuration guide applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` binding rule | Bind the unique identifier of a single project implementation session | Ensure each on-site deployment conversation log belongs to the corresponding project, avoiding cross-project data confusion |
| Log retention period | 30–90 days, calibrated based on actual testing | Match conventional audit cycle requirements after project delivery |
| Token consumption statistics configuration | Aggregate statistics by application dimension | Correspond to different software packages or service applications for on-site deployment, enabling accurate consumption accounting per link |
| `responseChatItemId` filtering rule | Only retain conversation response content related to on-site operations | Filter irrelevant conversations and focus on valid operation records for deployment implementation |
| `detail` log collection switch | Enable full operation detail collection | Cover complete operation trails for on-site links such as installation configuration and environment checks |
| Session history limit | Top 5 historical records, calibrated based on actual testing | Avoid excessive historical records interfering with context accuracy of on-site deployment conversations |

## Three common configuration errors
- Phenomenon: Data deviation occurs when counting Token consumption by application dimension, and actual consumption of each software package cannot be matched. Cause: The `chatId` is not bound to a single project session, causing Token data from different deployment projects to be aggregated and confused.
- Phenomenon: The session history limit is set to 1, but old historical records are still associated during conversations. Cause: The `chatId` is not correctly bound to the project phase, and the system incorrectly reads historical session data from other projects.
- Phenomenon: When starting an on-site deployment conversation via the API, an additional meaningless historical record is generated. Cause: Initialization requests are not properly filtered, causing the system to automatically add a redundant session history.

## How to verify the configuration is correct
- View the log list for a single project, confirm all conversation content is bound to the `chatId` identifier of the corresponding implementation project, with no cross-project logs mixed in.
- Trigger an on-site deployment operation, check the Token consumption statistics page, confirm data is correctly aggregated by application dimension, with no duplicates or omissions.
- After configuring the session history limit, initiate a test conversation, confirm only the specified number of historical records are loaded, and no expired or cross-project content is read.
- View the `detail` field of the audit log, confirm complete operation details for links such as installation configuration and environment checks have been collected, with no critical content omitted.
