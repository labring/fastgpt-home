# Security and Compliance Material Review for User Acceptance Testing Support: Permissions and Data Isolation

## What this category of data consists of
Data for this category is generated across the full user acceptance testing (UAT) workflow. Sources include requirement specifications, test environment configurations, customer business sample data, and defect tracking system records. Daily output documents include UAT test cases, acceptance issue tickets, acceptance reports, and signed confirmation forms. A single UAT test case includes test scenarios, operation steps, and expected result fields. Acceptance reports include defect lists and rectification status fields. Data is updated once per test phase or version iteration, with new content added and adjusted as testing progresses.

## What constraints these characteristics impose on permissions and data isolation
This category of data characteristics imposes multiple constraints on permissions and data isolation. First, data sources include sensitive business data such as customer business samples, so access by unauthorized personnel must be restricted. Second, UAT test cases are updated per phase, so permissions must be adjusted dynamically alongside test phases. Acceptance reports include legally binding documents such as signed confirmation forms, so modification permissions must be strictly controlled. Defect tracking system data is linked to specific customer projects, so data must be isolated per project. Additionally, participating roles include implementation consultants, test managers, and customer business representatives. Permission boundaries for different roles must be clearly defined to prevent cross-project data leaks or accidental operations.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Team permission binding | Bind each customer project to a unique `teamId` | Category data is generated per project, so data must be isolated per project |
| Member permission scope | Assign `tmbId` permission ranges by role | Multiple types of personnel participate as roles, so permission boundaries must be clearly defined |
| Sensitive data access duration | Only open during the test cycle, which ranges from 10–15 days, and adjust based on actual testing | Data is updated once per phase, so access must be controlled alongside testing progress |
| Document modification permissions | Only project managers can modify acceptance reports and signed confirmation forms | Acceptance-related documents are legally binding, so modifications must be strictly controlled |
| Cross-project data visibility | Disable cross-project data retrieval permissions | Defect tracking system data is linked to specific projects, so cross-project data leaks must be prevented |

## Three common configuration mistakes
- Symptom: Attempting to add a second team triggers an insufficient permissions prompt, and the creation operation cannot be completed. Cause: Cross-project binding rules for `teamId` are not configured correctly. The default setting only allows single-project team creation.
- Symptom: After restarting the Docker service on an Ubuntu system, UAT test case data fails to load normally, and an access denied prompt appears in the interface. Cause: `tmbId` is not bound to the user group of the server mount directory. Permission configurations become invalid after restarting the service.
- Symptom: After logging in, a customer business representative can view acceptance reports and defect data from other projects. Cause: Cross-project data retrieval permissions are not disabled, so data isolation configurations do not take effect.

## How to confirm configurations are correct
- Log in with test accounts for different roles, and verify that project data bound to `teamId` is only visible to corresponding team members.
- Check the sensitive data access duration configuration, and confirm that access is only open during the corresponding test phase.
- Attempt to edit an acceptance report as a non-project manager, and verify that modification operations cannot be performed.
- View system audit logs, and confirm that all permission change operations have complete records.
