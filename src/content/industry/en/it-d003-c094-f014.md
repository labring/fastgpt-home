# Security and Compliance Material Review for User Acceptance Testing Support: Model Integration and Configuration

## What this category of data includes
This category of data originates from requirement specifications, test environments, customer business examples, and defect tracking systems. It is maintained by implementation consultants, test managers, and customer business representatives. Daily generated documents include UAT test cases, acceptance issue tickets, acceptance reports, and signed confirmation forms. Document structures center on business scenarios, and include fields such as operation steps, expected results, problem descriptions, and rectification opinions. Data updates occur per phase or per version, with adjustments synchronized to acceptance progress.

## What constraints these characteristics impose on model integration and configuration
Data sources rely on test environments and customer business examples. This requires model integration to adapt to test environment deployment configurations, to avoid compliance risks from cross-environment calls. The business scenario-centered document structure requires model inputs to align with the field formats of UAT test cases. Pure technical parameter input cannot be used directly. The per-phase update frequency requires configurations to support rapid adjustments and version rollbacks, to match the iterative rhythm of acceptance progress. Errors directly lead to acceptance delays and delayed final payments. This requires model call stability and compliance to be included in configuration verification scope.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the bulk text length of UAT test cases and acceptance issue tickets, covering full business context for single-phase acceptance |
| `maxTokens` | 4096 token | Matches the single-page output length of acceptance reports, avoiding truncation of critical acceptance conclusions |
| `quoteMaxToken` | 1000 token | Limits the text length of referenced customer business examples, ensuring focus for compliance reviews |
| `temperature` | 0.2–0.4 | Maintains rigor in compliance reviews, preventing generation of content that does not meet acceptance standards |
| `AIPROXY_API_ENDPOINT` | Enter the root address of the AI Proxy service, for example http://aiproxy:3000. Do not append /v1 or /chat/completions. Do not use single-model addresses such as VLLM/Ollama/Xinference | Required environment variable for the App/Admin server, connects to the AI Proxy service in the test environment, and meets the test environment requirements for data sources |
| `AIPROXY_API_TOKEN` | Enter the administrator token consistent with the AI Proxy server configuration, and it cannot be empty. Do not use other keys such as application API Keys or model vendor secrets | Required environment variable for the App/Admin server, ensures permission compliance for model calls, and meets the control requirements of security and compliance reviews |

## Three common configuration errors
- A `401 Unauthorized` error occurs during model calls. Troubleshooting: Check if the `AIPROXY_API_TOKEN` environment variable on the App/Admin server matches the administrator token configured on the AI Proxy server, and that it is not empty.
- The model reranking function fails to return results matching UAT test cases as expected. This happens because the `toolChoice` parameter is not configured correctly, disabling the model’s corresponding tool capabilities.
- Model calls trigger automatically on the hour. This stems from leftover scheduled task configurations in the test environment that were not closed, causing unexpected model access and violating compliance review controllability requirements.

## How to verify correct configuration
- Confirm the App/Admin server has correctly configured the `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` environment variables, and that service startup verification passes.
- Import a single UAT test case text, call the model to generate a compliance review result, and check that the output does not trigger truncation errors for `maxContext` or `maxTokens`.
- Disable all non-essential scheduled tasks, and monitor for 24 hours to ensure no additional model call records appear, confirming configuration controllability.
- Submit multiple acceptance issue tickets, and verify that the referenced text length of model outputs stays within the preset `quoteMaxToken` range.

The values provided are common starting points and should be measured against the reader's own samples.
