# Security and Compliance Material Review for Monitoring Alert Configuration: Model Access and Configuration

## What Does the Data for This Category Look Like
This category’s data comes from Prometheus, Zabbix, cloud monitoring services, application logging systems, and CMDB platforms. Daily maintenance documents include monitoring metric lists, alert rule configurations, on-duty manuals, and alert change records. Data updates occur daily, or in real time after each alert rule change. Data fields include metric name, threshold range, alert level, trigger condition, and associated resource ID. Some fields include physical units, such as milliseconds for response duration, and percentage for request success rate.

## What Constraints Do These Characteristics Impose on Model Access and Configuration
Multi-source data sources require the model access layer to support parsing different formats of monitoring metrics, alert rules, and change records. It must be compatible with natively exported JSON, CSV, or text formats. Data updates occur at a high frequency. The model context window must adapt to dynamically changing alert configuration data, to avoid configuration parsing errors caused by context overflow. Alert configuration documents have large structural differences. Prompt templates must be used to unify parsing logic, ensuring correct field mapping across different sources. Alert configurations are directly linked to fault detection mechanisms. Model calls must guarantee low latency and high availability, to avoid disrupting operations workflows due to abnormal model responses.

## How to Set the Configuration
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, for example http://aiproxy:3000. Do not append /v1 or /chat/completions paths | Ensures model requests are correctly routed to the AI Proxy service |
| `AIPROXY_API_TOKEN` | AI Proxy admin Token, must match the AI Proxy server configuration and cannot be empty | Completes authentication with the AI Proxy service |
| `maxContext` | `8000–12000 token` | Adapts to batch parsing needs of multi-source monitoring data, avoids context overflow |
| `maxTokens` | `2000–3000 token` | Balances content length of alert configuration generation and response speed |
| `temperature` | `0.1–0.3` | Reduces randomness of configuration generation, ensures compliance of alert thresholds and rules |
| `quoteMaxToken` | `1000 token` | Limits the length of referenced original monitoring data, avoids redundant content interfering with configuration generation |

## Three Common Misconfigurations
- Phenomenon: Model calls fail after incorrect configuration of `AIPROXY_API_ENDPOINT` or `AIPROXY_API_TOKEN`. Cause: Variables are not configured correctly, or network policies restrict outbound connections between the service and the AI Proxy service.
- Phenomenon: After accessing models such as Kimi-k2, DeepSeek-r1, alert configurations generated with the same prompt have significant differences. Cause: The `temperature` parameter value is not adjusted for different models, leading to excessive randomness deviation in generation logic.
- Phenomenon: The Agent execution details page shows "completed reason: connection broken" in the model response. Cause: `AIPROXY_API_ENDPOINT` is configured incorrectly, or network policies restrict outbound connections between FastGPT and the AI Proxy service.

## How to Confirm Successful Configuration
- Check that `AIPROXY_API_TOKEN` and `AIPROXY_API_ENDPOINT` are correctly configured as server environment variables, and their values match the AI Proxy server settings. Connectivity can be verified by checking service startup verification logs or system logs.
- Run a small-batch alert rule parsing task, verify that the generated configuration content matches the field and threshold requirements of the original data, and confirm that the values of `maxContext` and `maxTokens` do not trigger context limits.
- Simulate an alert rule change, check whether the configuration generated by the model complies with the compliance requirements in the on-duty manual, and verify the control effect of the `temperature` parameter on generation randomness.
- Check the FastGPT v4.17.0 system logs to confirm there are no error records of model call timeouts or authentication failures.

The values provided are common starting points and should be measured against the reader's own samples.
