# Security and Compliance Material Review for Community Report Handling: Permission and Data Isolation

This content is written based on FastGPT v4.17.0.

## What the data for this category looks like

Daily documents for this category center on report tickets, processing records, appeal forms, and user notification templates, with ticket numbers as unique identifiers. Data sources include user report content submitted via the community reporting system, details of reported original content, user historical behavior records, and preset review rules. Data updates typically follow two patterns: newly submitted report tickets are synchronized in real time, while processing records and appeal form statuses are updated in daily batches. Fields include ticket status, violation type, associated content hash value, reporter and reported party identifiers, and other related fields. There is no unified batch data structure; all are structured field collections generated per individual ticket.

## What constraints these characteristics impose on permission and data isolation

Since data is linked to a specific community, reporter, and reported party for each ticket, permission and data isolation must strictly limit access scopes for different entities to prevent cross-community or cross-report-subject data leaks. The real-time update feature requires permission configurations to take effect immediately, ensuring newly submitted report tickets are assigned permissions based on their attribution right away. Data contains user privacy content and appeal details, so access paths for appellants, respondents, and unauthorized reviewers must be isolated to prevent sensitive information from spreading. Cross-team API calls also require permission verification to stop unauthorized teams from accessing report data from other communities, which aligns with business scenarios where cross-team calls lack required permissions.

## How to set configurations

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Team data isolation scope | Bind to the corresponding community's `teamId`, limit access only to members of that community's operations team | Matches the business characteristic that report tickets are attributed to specific communities, prevents cross-community data leaks |
| Reviewer permission binding | Assign ticket processing permissions for the corresponding community based on the reviewer's `tmbId` | Ensures only authorized reviewers can handle report tickets for their assigned communities |
| API call permission verification duration | 600 seconds | Matches the real-time processing update rhythm of report tickets, prevents expired calls from accessing data |
| Single ticket associated data return limit | Top 10 records | Limits the volume of sensitive data returned by a single API call, prevents bulk data leaks |
| Backend interface permission grouping | Enable visible permissions by community dimension | Only the operations backend for the corresponding community displays that community's report ticket list |
| Sensitive data storage configuration | 1000 MB encrypted storage pool | Matches the characteristic that report tickets contain user privacy content, ensures storage security |

## Three common misconfigurations

- Phenomenon: When a cross-community team calls the report ticket query API, an unauthorized error or empty ticket list is returned. Cause: The permission scope for API calls was not configured according to the corresponding community's `teamId`, causing teams from different communities to fail to access their own ticket data.
- Phenomenon: Regular reviewers can view report tickets from communities they are not assigned to. Cause: The reviewer's `tmbId` was not bound to the permission group for the corresponding community, causing permission isolation to fail.
- Phenomenon: Sensitive content in appeal forms is obtained by unauthorized third parties. Cause: Permission verification for the association between appeal forms and original report tickets was not configured, allowing unauthorized entities to access appeal content beyond their allowed permissions.

## How to confirm the configuration is correct

- Log in to the operations backend for the corresponding community, verify that only the report ticket list for that community is visible, and that ticket data from other communities cannot be accessed.
- Use an unauthorized reviewer's account to call the report ticket query API, confirm that an unauthorized error or empty result is returned.
- Attempt to access the corresponding appeal form using an account other than the appellant's, verify that the appeal content cannot be viewed.
- Check the data storage configuration, confirm that encrypted storage is enabled for sensitive report ticket data, meeting the preset storage requirements.
