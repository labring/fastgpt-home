# Security and Compliance Material Review for Renewal Health Management: Permissions and Data Isolation
This document is compatible with FastGPT v4.17.0.

## What this category of data looks like
Data related to renewal health management typically originates from CRM systems, product usage data, ticket statistics, and contract ledgers. Update cycles follow weekly or monthly intervals. Daily documents include customer health reports, renewal forecast sheets, high-risk customer lists, and cross-team meeting minutes. Data fields cover customer contract cycles, usage frequency, ticket response times, accounts receivable status, and more. No unified fixed statistical units exist; adjustments are made based on document type and business requirements.

## What constraints do these characteristics impose on the permissions and data isolation workflow
Data for this category comes from scattered sources and involves customer sensitive information. Different roles can only access customer data within their assigned scope. Therefore, permissions and data isolation must align with role responsibility boundaries. Data update frequency is low, so permission configurations do not need frequent adjustments, but immediate effect after changes must be ensured. Different document types have varying sensitivity levels: high-risk customer lists and contract ledgers require strict access restrictions, while meeting minutes must be limited to project team members to prevent unauthorized cross-departmental or cross-customer access. At the same time, knowledge bases storing this type of data must be synchronized with permission rules to ensure retrieval results only include content within the authorized scope.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Team permission groups | Divide by customer responsibility scope, each group corresponds to 1-3 customer success managers | Aligns with daily data responsibility boundaries, prevents cross-group access to unauthorized data |
| `teamId` binding scope | Limit to the customer ID range associated with the current team | Ensures only team members can access renewal health data under the corresponding `teamId` |
| `tmbId` data isolation | Enable single-member exclusive `tmbId` data filtering | Prevents members from accessing sensitive documents of non-assigned customers |
| Knowledge base permission association | Bind knowledge bases to corresponding team permission groups | Aligns with storage and access rules for renewal health documents |
| Access log retention period | 30-90 days, calibrated based on actual testing | Meets compliance review requirements while avoiding excessive storage resource usage |
| Member role permissions | Divided into three categories: renewal manager, sales operations, read-only view | Aligns with operational needs of different positions, prevents unauthorized data modification |

## Three common misconfigurations
- Symptom: API call returns permission denied error, status code 403 | Cause: The caller is not bound to the corresponding `teamId`, or team access permissions for the knowledge base are not configured
- Symptom: Team members cannot view specified customer health reports | Cause: The member is not added to the corresponding permission group, or the `tmbId` filtering rule is not correctly associated with the customer scope assigned to the member
- Symptom: Deleted team members can still access original data | Cause: Permission bindings for the knowledge base were not updated synchronously, or permission cache was not cleared in a timely manner

## How to confirm proper configuration
- Use a non-team member's API key to call the knowledge base interface associated with `teamId`, confirm that a permission denied result is returned
- Switch member accounts with different roles, verify that only customer health documents within the assigned responsibility scope are accessible
- Check team permission group configurations, confirm that each permission group is only bound to the customer ID range for its assigned responsibilities
- Review access logs, confirm that operation records match member permissions, with no unauthorized access traces
