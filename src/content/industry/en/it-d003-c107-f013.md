# Security and Compliance Material Review for Account Ban and Appeal Reconsideration: Permission and Data Isolation

## What data for this category looks like
Data for this category typically comes from risk control systems, audit records, user behavior logs, and report evidence. Four types of documents are regularly produced: ban records, appeal materials, reconsideration opinions, and user notifications.
Ban records include account identifiers, ban times, violation types, and disposition levels. Appeal materials include supporting content submitted by users, appeal times, and associated report IDs. Reconsideration opinions include auditor identifiers, reconsideration results, and adjusted disposition content.
Some historical appeal records do not include the `tmbId` field. Data update frequency is daily or real-time.

## What constraints these characteristics impose on permission and data isolation
Scattered data sources support real-time updates. Permission isolation must cover data sources accessed by multiple systems. This prevents cross-team unauthorized access to risk control and user behavior data.
Documents contain sensitive account violation information and user appeal content. Access scope for different roles must be strictly limited. For example, customer service staff can only view appeal records for accounts assigned to their team.
Some historical documents lack the `tmbId` field. This causes team identifier-based permission checks to fail. Additional processing is required for the association logic of old data.
Real-time data updates require isolation rules to support dynamic adaptation to newly accessed data sources and document types. This ensures permission policies do not lag behind data updates.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` binding rule | Bind one-to-one with the team that owns the account | Appeal and ban data for this category are divided by team for permission control. This prevents cross-team access to non-team business data |
| `tmbId` completion strategy | Fill in associated team identifiers for historical documents missing the `tmbId` field | Some historical appeal records do not include the `tmbId` field. Completion must be done via associated report IDs or original audit records to ensure permission checks work correctly |
| Role permission scope | Customer service staff can only access the first 100 unprocessed appeal records for their team | Customer service teams only handle appeal reconsideration for assigned accounts. This prevents unauthorized access to sensitive data from other teams |
| Data access time limit | Only retain real-time accessible data from the last 90 days | Compliance reviews typically only require recent business data. Older data can be archived to offline storage. This reduces pressure for online permission management |
| Appeal material size limit | Single upload must not exceed 10 MB | Compliance review materials typically do not exceed this size. This avoids excessive storage resource usage |
| Multi-system access verification | Configure layered permissions by data source type | Data comes from multiple systems including risk control and audit records. Access permissions for different systems must be managed separately |

## Three common misconfigurations
- Symptom: Permission check errors occur for some historical appeal records with the prompt `Missing tmbId field`. Cause: No completion operation was performed for historical documents missing the `tmbId` field. This causes team identifier-based permission rules to fail to match.
- Symptom: Cross-team members attempt to access appeal records not assigned to their team. The interface returns `403 Permission Denied`. Cause: The `teamId` binding rule was not configured correctly. This causes the association between accounts and teams to fail.
- Symptom: SSO authentication fails after local deployment. Logs show `Authentication parameter mismatch`. Cause: System permissions were not bound to the team identifiers returned by SSO. This causes the permission isolation logic to fail to recognize incoming authentication information.

## How to confirm configurations are correct
- Randomly select 3 appeal records assigned to the responsible team. Attempt to access them using an admin account from a different team. Confirm the interface returns a permission restricted prompt.
- Export bulk historical appeal record data. Confirm that documents missing the `tmbId` field have been filled with associated team identifiers.
- After completing SSO connection configuration, log in to FastGPT v4.17.0 using a test account. Confirm that only ban and appeal data for the assigned team is visible.
- View access logs for different data sources. Confirm that access permissions for risk control system and audit record data match the preset layered permission rules.
