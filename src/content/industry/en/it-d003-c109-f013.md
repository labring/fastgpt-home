# Security and Compliance Material Review for Identity, Account, and Permission Management: Permission and Data Isolation

## What data for this category looks like
This category targets internal employee account management for enterprises, with clear differences from customer-facing permission configuration. Data originates from enterprise IAM systems, HR systems, business system logs, and approval systems. Updates occur either daily or in real time alongside employee onboarding, offboarding, position changes, and transfers. Routinely associated documents include account application forms, permission matrices, offboarding account recovery forms, and compliance audit reports. Data fields include employee ID, account status, permission scope, approval nodes, change time, and similar attributes. No custom statistical units are used; data is stored exclusively in the native field format of the source systems.

## What constraints these characteristics impose on permission and data isolation
Multi-source data synchronization requires permission isolation rules to support cross-system account status changes, preventing permission failure from data desynchronization. The high-frequency update rhythm demands that isolation policies take effect in real time, covering permission recovery and changes after personnel adjustments. Different types of business documents map to distinct permission levels, so data access boundaries must be divided by document type. Audit data must retain tamper-proof access logs to enable traceability of permission operations during compliance reviews. Additionally, the permission scope of internal employee accounts must be strictly bound to their affiliated department and position, blocking cross-departmental unauthorized access.

## How to configure settings
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `teamId` | Bind to enterprise department hierarchy ID | Match enterprise organizational structure, divide data access boundaries by department |
| `tmbId` | Bind to employee ID and position permission group | Accurately correspond to the permission scope of individual employees, avoid permission generalization |
| Data isolation scope | Divide by business domain, allocate no more than 500 MB of storage space per domain | Comply with enterprise permission matrix field division rules, control single-domain data scale |
| Permission approval synchronization interval | 60 seconds | Ensure that permission changes following personnel adjustments take effect in a timely manner |
| Abnormal permission alert interval | 300 seconds | Intercept unauthorized access attempts in a timely manner |
| Log retention period | 180 days | Meet basic compliance audit retention requirements |

## Three common configuration errors
- When adding team members, entering a valid account results in an invalid username prompt. The root cause is that `tmbId` is not linked to valid employee data in the HR system, preventing identity verification.
- After generating a publicly accessible link, chat records of different users are not isolated. The root cause is that data storage directories are not divided by `teamId`, so all data writes to the same storage path.
- Database connections are rejected during internal deployment. The root cause is that no database access permission isolation rules are configured, and the deployment container's account is not included in the IAM system's allowlist.

## How to verify a successful configuration
- Log in to the IAM management interface of FastGPT v4.17.0, confirm that the department hierarchy bound to `teamId` matches the enterprise organizational structure.
- Submit a test account application form, verify that the permission approval process triggers as configured, and that abnormal alerts are issued within 300 seconds.
- Generate a publicly accessible link, use two accounts with different `teamId`s for testing, and confirm that chat records cannot be accessed across accounts.
- View the log retention page, confirm that all permission operation logs from the past 180 days can be queried normally.
