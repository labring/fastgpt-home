# Security and Compliance Material Review for Identity Account and Permission Management: Model Access and Configuration

## What data falls under this category
Data for this category originates from enterprise IAM systems, HR systems, business system logs, and approval systems. Daily processed documents include account application forms, permission matrices, separation recovery forms, and compliance audit reports.
Data updates occur either daily, or in real time when personnel undergo onboarding, separation, transfer, or role adjustments.
Included fields are account identifiers, permission binding scopes, approval node status, change times, and similar fields. No unnecessary custom statistical fields are included.

## What constraints do these characteristics impose on the model access and configuration link
Multi-source data sources require model access to support response formats from different interfaces. A unified field mapping rule must be configured.
Data updates have no fixed cycle. Model calls must support triggering when data changes, to adapt to temporary personnel change scenarios.
Daily documents with fixed structures require the model to preset field extraction templates, to avoid extraction deviations.
The strict nature of compliance audits requires the model to retain complete reasoning basis for outputs, to ensure audit results are traceable.
Flexibility in field order across different documents must be supported, to avoid extraction errors caused by format differences in permission documents.

## How to set configurations
These configurations are based on the FastGPT v4.17.0 model access interface. `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are App/Admin server environment variables, and must not be configured via the interface.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | Compliance documents for this category (permission matrices, audit reports, etc.) have large per-batch context volumes, and must carry complete content from multiple data sources |
| `maxTokens` | `2000–3000 token` | Identity permission review outputs must cover permission verification, anomaly tagging, and similar content, to avoid truncating critical compliance conclusions |
| `quoteMaxToken` | `500–800 token/entry` | Sufficient context must be allocated to each permission-related document fragment, to ensure the model can accurately match permission rules and document content |
| `toolChoice` | `auto` | The model must independently choose whether to call permission verification tools, to adapt to compliance review requirements across different scenarios |
| `temperature` | `0.1–0.3` | Compliance reviews must strictly align with preset rules, reducing reasoning randomness to ensure consistent audit results |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, for example `http://aiproxy:3000`. Do not append `/v1` or `/chat/completions` paths. Do not fill in single-model service addresses such as VLLM/Ollama/Xinference | This variable is an App/Admin server environment variable, used to specify the AI Proxy service access address |
| `AIPROXY_API_TOKEN` | Administrator token consistent with the AI Proxy server configuration, and cannot be empty | This variable is an App/Admin server environment variable, used for identity verification with the AI Proxy service. Do not use it for application API call authentication |

## Three common configuration mistakes
- Phenomenon: The model's permission anomaly list includes account information for former employees. Logs show the latest separation recovery form data was not synchronized. Cause: No data update trigger mechanism was configured. Model calls still use old permission matrix data, and do not synchronize latest changes from the HR system.
- Phenomenon: After configuring `maxTokens` as `10000 token`, model responses time out. The interface shows a context overflow prompt. Cause: Parameters were not adjusted based on the actual length of documents in this category, exceeding the maximum output limit supported by the model.
- Phenomenon: A large number of account IDs extracted by the model are missing, making it impossible to generate complete permission audit reports. Cause: Tool calling capabilities were not enabled. The model cannot call preset field matching templates, leading to incomplete extraction of core fields.

## How to confirm configurations are correct
- Import an archived account application form and permission matrix, run an audit task, and check if core fields extracted by the model match the original documents.
- Trigger a simulated personnel change operation, call the model to review related permission changes, and verify that latest business system logs and approval data are synchronized.
- Review the compliance verification results output by the model, confirm that reference content for corresponding document fragments is retained, to ensure audit basis is traceable.
- Adjust the parameter range, run the same audit task multiple times, and verify the stability and consistency of output results.

The values listed are common starting points, and should be evaluated against the reader's own samples.
