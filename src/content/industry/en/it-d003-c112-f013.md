# Security and Compliance Material Review for Incident Management and Root Cause Analysis: Permission and Data Isolation

## What the data for this category looks like
Data for this category centers on root cause analysis and incident closure after a failure. Daily documents include RCA reports, incident tickets, post-mortem minutes, and remediation tracking sheets. Data sources cover incident timelines, server logs, monitoring metrics, and code commit records. Update frequency is once after each major incident or once per month. Individual documents contain fields such as incident ID, occurrence time, root cause analysis conclusion, associated log path, remediation item number, and tracking status. Different documents are linked via incident ID to form a complete data chain.

## What constraints these characteristics impose on permission and data isolation
Data for this category includes multi-source heterogeneous incident details, code commit records, and internal remediation workflows. Permission and data isolation must align with the relationships in the data chain. Since data sources come from work outputs of different teams such as operations and development, access scope must be divided by team or role to avoid sensitive information leaks across teams. Documents generated during a single major incident may contain undisclosed incident details. Access must be restricted only to relevant leads and technical team members. Remediation tracking sheets involve internal process status. Different permission tiers must be established to prevent unauthorized members from viewing full remediation progress and associated details.

## Configuration settings
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setup | Rationale |
| --- | --- | --- |
| `teamId` grouping | Divide by development, operations, and quality teams | Aligns with the different team work outputs covered by the data sources for this category |
| `tmbId` permission configuration | Split into four tiers: administrator, core operations, regular member, intern | Matches the responsibility scope of different positions |
| Program data binding | Only bind exclusive incident data for the corresponding `teamId` | Ensures data access aligns with team responsibilities |
| Access timeout threshold | 600 seconds | Adapts to the multi-source data retrieval time required for root cause analysis |
| Team storage quota | 1000 MB per team | Matches the total volume of documents generated per month |
| Permission verification switch | Enabled | Prevents unauthorized access to sensitive incident data |

## Three common configuration errors
- Symptom: Permission errors occur when testing a locally deployed model, with a prompt indicating no access rights. Cause: The `teamId` binding for the program's access scope is not configured, or the current account is not assigned the permission tier corresponding to `tmbId`.
- Symptom: Intern accounts can view all RCA reports and remediation tracking sheets. Cause: The `tmbId` permission configuration is not set, and full data access permissions are enabled by default.
- Symptom: Team members cannot create exclusive root cause analysis programs. Cause: Team management configuration is not enabled, and only administrator accounts have program creation permissions.

## How to confirm correct configuration
- Use a non-authorized member account to access the RCA report directory for the corresponding team, and check if access is blocked with an insufficient permissions prompt.
- View the `teamId` list bound to the program, and confirm that only exclusive data sources for the corresponding team are included.
- Test access to remediation tracking sheets with accounts of different permission tiers, and confirm that only content matching the `tmbId` permission configuration can be viewed.
- Submit a simulated incident data set, and check if team members can normally view and edit associated documents.
