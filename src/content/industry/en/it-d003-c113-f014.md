# Security and Compliance Material Review for Integration and Interface Testing: Model Access and Configuration

## What data for this category looks like
Data for this category comes from interface management platforms, test environment logs, databases, and message queues. Update frequency is daily or per version. Daily produced documents include interface test cases, joint debugging issue tickets, environment descriptions, and test reports. Interface test cases contain interface addresses, request methods, parameter lists, and expected responses. Joint debugging issue tickets contain error codes, error messages, and call links. Test reports contain fields such as overall pass rate and exception statistics. The data structure is relatively fixed, and changes will occur with interface iterations or test version updates.

## What constraints do these characteristics impose on the "model access and configuration" workflow
Dispersed data sources and varying formats require model access configurations to support multi-format input parsing, and adapt to logs and test case documents from different sources. High update frequency requires configuration parameter verification logic to quickly adapt to new interface fields, preventing model parsing failures caused by field changes. Fixed daily document structure requires model prompt configurations to match fixed document fields, ensuring accurate information extraction from test cases and joint debugging issue tickets. Direct impact of errors on joint debugging progress requires adding timeout and retry mechanisms to configurations, reducing the risk of joint debugging delays caused by model call exceptions.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `AIPROXY_API_ENDPOINT` | Fill in the root address of the AI Proxy service, for example http://aiproxy:3000. Do not include extra spaces, do not append paths such as /v1 or /chat/completions. Do not use single-model addresses from VLLM/Ollama/Xinference, and do not fill this in workflow global variables, application API request headers, or the general model management page as a replacement for service deployment configurations | Used to specify the root address of the AI Proxy service, ensuring requests are correctly routed to the AI Proxy service |
| `AIPROXY_API_TOKEN` | Fill in the administrator token consistent with the AI Proxy server configuration. Cannot be empty. Do not use other types of credentials such as application API keys or model vendor keys, and do not fill this in workflow global variables, application API request headers, or the general model management page as a replacement for service deployment configurations | Used for identity verification with the AI Proxy service, ensuring request legitimacy |
| `maxContext` | 8000–12000 token | Adapts to the overall context length of interface test cases and joint debugging issue tickets, preventing incomplete parsing caused by content truncation |
| `maxTokens` | 2000–4000 token | Meets the output length requirements for interface parameter verification and link problem location |
| `temperature` | 0.1–0.3 | Reduces randomness in model generation results, ensuring the accuracy of interface parameter verification logic |
| `toolChoice` | auto | Allows the model to automatically choose whether to call the interface verification tool, adapting to different test scenarios |

## Three common configuration mistakes
- Symptom: New third-party models do not appear in the available list, and a "channel not found" prompt is displayed during calls. Troubleshooting steps: Check if the server `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` environment variables are configured correctly, and if the parameters contain extra line breaks or spaces. Missing required variables will cause startup verification to fail.
- Symptom: Custom models can be selected in the conversation module, but do not appear in the model list during text extraction. Troubleshooting steps: Check if the upstream model channel parameters are configured correctly, and if the server `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` environment variables are configured correctly.
- Symptom: The verification result returned by the model call does not match the actual interface parameters, and parameter misjudgment occurs. Troubleshooting steps: Check if the `temperature` parameter value is too high, and if the current value is outside the recommended range.

## How to confirm configuration is complete
- On the FastGPT v4.17.0 model management page, check if added models appear in the available model list.
- Upload a standard interface test case document, trigger a model call, and check if returned results contain content related to interface parameter verification and link problem location.
- Simulate input from a joint debugging issue ticket, and confirm the model can correctly extract key information such as error codes and interface addresses.
- Check test environment logs, and confirm model call request parameters match configured values for `maxContext`, `maxTokens`, and other parameters.
