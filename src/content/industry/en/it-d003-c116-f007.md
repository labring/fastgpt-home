# Security and Compliance Material Review for Project Document Handover and Archiving: Conversation Logs and Auditing

## What this category of data looks like
Data for this category primarily comes from project document libraries, configuration lists, meeting minutes, and test reports. Updates occur after each project phase delivery or when the overall project concludes. Daily covered documents include completion documents, configuration manuals, training records, and acceptance certificates. Core fields include project unique identifier, document version number, signature verification status, and handover and archiving time. Some documents include associated project execution process records. Data volume fluctuates based on project scale.

## Constraints on conversation logs and auditing workflows
This category of data is scattered across multiple types of project deliverables, and update schedules shift with project phases. The conversation logs and auditing workflow must associate document operation records from different sources. Documents include version number and signature verification status fields. Auditing must retain complete conversation interaction processes for version consistency checks and signature verification. Data updates do not follow a fixed high-frequency schedule, so auditing triggers must align with project handover nodes. The workflow must also cover full process logs for document integrity checks. This ensures the acceptance phase can trace operational basis.

## Configuration guidelines
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Log retention period | 180–365 days | Aligns with project warranty periods and compliance traceability requirements |
| Maximum storage per log entry | 2000–5000 characters | Matches the text length range of project documents |
| Auditing trigger binding | Bind to project number via `chatId` | Ensures logs are accurately tied to specific projects |
| Exception alert threshold | 3 consecutive verification failures | Intercepts non-compliant handover operations in a timely manner |
| Log export format | Structured CSV | Meets archiving and retrieval requirements for compliance reviews |
| Auditing query restriction | Only retrieve `responseChatItemId` for the current project | Narrows scope to improve retrieval efficiency |
| Auditing detail toggle | Enable `detail` mode | Retains complete conversation interaction details |

## Three common configuration mistakes
- Scenario: Audit logs only display operation results, and complete conversation interaction processes are not retained. Cause: `detail` mode is not enabled, and only minimal operation logs are recorded. This prevents backtracking and verification of details.
- Scenario: `chatId` binding errors occur during project handover, and logs indicate no associated project identifier exists. Cause: The association rule between logs and project numbers is not configured in settings. Auditing cannot match the corresponding project.
- Scenario: Question-and-answer pair extraction tasks get stuck during training, and no records appear in call logs. Cause: Node linkage for auditing triggers is not configured. Task execution logs are not synchronized to the auditing module. This makes troubleshooting stagnation causes via logs impossible.

## How to verify successful configuration
- Manually trigger a document integrity check conversation. Check if logs include complete interaction details to confirm `detail` mode is active.
- Enter a test project number, and retrieve audit logs for the corresponding `chatId` to confirm logs are accurately tied to the project.
- Trigger an exception verification operation to verify if the preset exception alert is triggered. Confirm the threshold configuration is correct.
- Attempt to export audit logs to confirm the export format is structured CSV and can be read normally.
