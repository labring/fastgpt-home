# Security and Compliance Material Review for Project Document Handover and Archiving: Permissions and Data Isolation

## What the data for this category looks like
Data for this category is maintained by project managers, implementation consultants, and customer archive administrators. It covers four core document types: completed project files, configuration manuals, training records, and acceptance certificates. Data sources include project document libraries, configuration lists, meeting minutes, and test reports. Updates align with project phase milestones or the project closing phase. Individual documents typically include fields such as project number, customer name, version number, and signature status. Documents are categorized and archived by type and storage path. The basic management unit is a single document or single-project archive package. No fixed unified statistical unit applies.

## What constraints these characteristics impose on permissions and data isolation
This category of data updates with project milestones and uses exclusive project identifiers. Permission configurations must adjust dynamically alongside project progress to prevent early leaks of internal documents not yet ready for delivery. Documents from different projects belong to independent customers or teams. This requires permission isolation granularity down to the single-project level to block cross-project data access. Core deliverables like acceptance certificates may only be viewed by authorized archive administrators and the corresponding customer. Internal meeting minutes are only accessible to project team members. Decentralized data sources also need unified permission rule mapping. This ensures documents imported from any channel match the correct permission group, avoiding missed configuration steps.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Exclusive unique string identifier for the project | Matches single-project permission isolation requirements, ensuring documents for the same project are only accessible to authorized teams |
| `tmbId` | Permission group ID bound to document type | Differentiates access permissions for different document types such as completed project files and acceptance certificates |
| Permission group configuration | Adjust dynamically based on project phase | Adapts to the rhythm of phase-based data updates, only granting access to documents required for the current phase |
| Tenant isolation switch | Enabled | Prevents unauthorized access to cross-tenant project documents |
| Access log retention | 30 days | Meets log tracing requirements for compliance reviews |
| Data export permission | Only configurable by archive administrators | Prevents unauthorized document export and leakage |

## Three common configuration mistakes
- Phenomenon: Non-authorized teams access cross-project documents. System logs show abnormal `teamId` matching. Cause: `teamId` is not assigned using project-exclusive identifiers, leading to mixed permissions for documents from different projects. This may result in subsequent acceptance failures or delayed final payments.
- Phenomenon: Ordinary project members download acceptance certificates. No permission intercept prompt appears in the interface. Cause: `tmbId` is not bound to the exclusive permission group for core deliverable documents, leading to missing permission configurations.
- Phenomenon: Configuration manuals from previous project phases cannot be accessed during the project closing phase. The system prompts insufficient permissions. Cause: Permission groups are not adjusted when rolling back project phases. Only access permissions for the current phase are retained, failing to cover full-cycle document access requirements.

## How to confirm configurations are correctly set
- Log in to the FastGPT v4.17.0 backend, view the `teamId` configuration list, and confirm that each project corresponds to a unique `teamId` identifier.
- Attempt to access the acceptance certificate for the corresponding project using an account from an unauthorized team, verify that a permission insufficient prompt appears.
- Attempt to export the project archive package, confirm that only the archive administrator account can perform this operation, and ordinary members have no export entry.
- View the permission group logs, confirm that the permission scope is adjusted synchronously when updated alongside project phases.
