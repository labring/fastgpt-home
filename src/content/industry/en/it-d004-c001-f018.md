# Customer Technical Support and Pre-sales Q&A for CDN and Edge Acceleration Configuration: Reranking and Hybrid Retrieval

## What data for this category looks like
Data for this category primarily comes from CDN consoles, DNS resolution records, user access logs, and node monitoring alerts. Regularly produced standardized documents include domain name access forms, cache rule configuration forms, refresh and preheating operation records, and troubleshooting analysis reports.
Data fields include domain names, cache rule parameters, node IPs, access peaks, alert trigger conditions, and more. Update frequency is daily, or real-time synchronization when configuration changes are made.

## What constraints do these characteristics impose on the reranking and hybrid retrieval link
Data for this category is scattered across multiple consoles and logs. Unlike cloud network and load balancing configurations, it is designed for public network content distribution and caching. Hybrid retrieval must integrate multi-source content such as domain name configurations, access logs, and alert information.
Data updates are synchronized in real time with configuration changes. This requires the retrieval link to have timeliness. The reranking model must prioritize matching the latest cache rules and access form content.
Daily document structures include standardized parameter fields. Reranking and hybrid retrieval must adapt to the field matching logic of different documents, and prioritize locating content related to time-consuming links such as domain name record verification and cache rule debugging.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| Hybrid retrieval recall upper limit | Top 10-15 entries | Adapt to the scattered nature of CDN multi-source data, avoid excessive redundant results interfering with the reranking stage |
| Reranking model recall threshold | 0.75-0.85 | Match the professional term similarity of CDN configuration documents, filter low-relevance logs or alert content |
| Retrieval context length | 800-1200 characters | Adapt to the field length of standardized documents such as cache rules and access forms, ensure complete retrieval content |
| Reranking model call timeout | 600 seconds | Adapt to latency scenarios of offline deployment or cross-node calls, avoid interrupting the retrieval process due to timeouts |
| Multi-source data merging rule | Group by document type | Differentiate access forms, cache rules, and log data to facilitate sorting by business priority during reranking |

## Three common errors
- Phenomenon: No retrieval results after enabling the reranking model on the application side, but results are normal during knowledge base testing. Cause: Cross-document association mapping for multi-source data is not configured, causing the application to fail to integrate CDN console data and knowledge base content during retrieval.
- Phenomenon: Offline deployed reranking model configuration fails after upgrading FastGPT, and the model test prompts a request error. Cause: The offline deployed model file was not synchronized to the dependency directory of the corresponding version, or the port mapping configuration does not adapt to the API path of the new version.
- Phenomenon: Reranking model call times out or returns empty results. Cause: The reranking model call timeout threshold is not adjusted, and the retrieval volume of CDN multi-source data is not adapted, causing excessive model load.
