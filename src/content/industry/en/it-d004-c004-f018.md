# Customer Technical Support and Pre-sales Q&A for IT Procurement and Supplier Management: Reranking and Hybrid Retrieval

## What data for this category looks like
Data for this category typically comes from internal enterprise procurement systems, supplier quotation documents, budget spreadsheets, and contract systems. Daily processed documents include purchase requisitions, price comparison records, formal contracts, and acceptance documents. Data updates follow individual procurement workflows. Updates occur per completed order or in monthly batches. Document fields include purchase order numbers, supplier qualification information, budget amounts, contract clause summaries, acceptance milestones, and more. Some data uses structured table formats, while others use free text. No unified standardized field alignment exists across datasets.

## Constraints imposed by these characteristics on reranking and hybrid retrieval workflows
Data for this category is scattered across multiple internal systems. It includes both structured table and free text formats. Hybrid retrieval must support recall logic for both data types. The update rhythm of individual procurement workflows means retrieval does not need high-frequency refreshes. It maintains timeliness and accuracy for each batch of data. Most document content centers on procurement requirements, supplier qualifications, budget amounts, and contract clauses. The reranking step prioritizes matching procurement scenario keywords from user queries. It filters out unrelated non-procurement documents. Additionally, data fields vary widely across different sources. Basic field alignment preprocessing is required before retrieval to avoid chaotic recall results.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Setting | Recommended Value | Rationale |
| --- | --- | --- |
| Rerank Toggle | Enabled | Data for this category is scattered and has diverse formats, reranking improves relevance matching accuracy |
| Similarity Threshold | 0.70–0.88 | Meets semantic matching requirements for procurement documents, filters low-relevance historical price comparison records |
| Single Recall Limit | Top 6–10 entries | Matches the number of core documents per procurement workflow, controls the processing scale of retrieval results |
| Retrieval Mode | Hybrid Retrieval | Adapts to mixed data sources of structured procurement documents and free text contracts, balances precise recall |
| Reranked Result Limit | Top 3–5 entries | Focuses on core procurement-related documents, avoids redundant results disrupting pre-sales and technical support workflows |

## Three Common Configuration Mistakes
- The "Result Rerank" toggle displays a cross mark after being enabled in the knowledge base. This occurs because connectivity verification for the reranking model has not been completed, or the model access key has not been properly configured.
- An error message pops up during reranking model testing, but the model runs normally during formal calls. This occurs because network restrictions or permission verification logic in the test environment differ from those in the production environment.
- Access tokens for the reranking model cannot be obtained. This occurs because the developer authorization process for the corresponding model service has not been completed, or valid access credentials have not been bound to the platform.

## How to Confirm Proper Configuration
- The knowledge base retrieval configuration page is accessed, and the "Result Rerank" toggle is confirmed to be enabled.
- A test query related to procurement requirements is submitted, and returned retrieval results are checked for sorting by relevance from highest to lowest.
- The number of retrieval results is verified to match the configured single recall limit.
- Reranking model operation logs are reviewed, and no connection errors or parameter anomaly prompts are confirmed.

The values provided are common starting points and should be measured against local sample datasets.
