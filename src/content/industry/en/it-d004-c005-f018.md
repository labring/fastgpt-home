# Customer Technical Support and Pre-sales Q&A for Issue Triage and Response: Re-ranking and Hybrid Retrieval

## What Data for This Category Looks Like
Data for this category primarily comes from GitHub or Gitee Issues, code repository version logs, user-submitted environment information, and code snippets. Daily maintained documents include Issue submission templates, tag rule libraries, historical response records, and problem reproduction documentation.
Data updates occur on a daily or weekly basis. Fields include problem titles, descriptions, tags, submission times, associated code paths, and more. The core content focuses on user-submitted technical problems and community response records. No additional custom statistical fields are configured.

## Constraints on Re-ranking and Hybrid Retrieval
Data sources are scattered across Issues, code repositories, and environment logs. Hybrid retrieval must support cross-source recall of associated content to avoid missing key historical responses or code-related information.
Daily or weekly data updates require retrieval indexes to support incremental synchronization, eliminating the extra time cost of full index reconstruction.
Structured tags and templates for Issue-related documents require the re-ranking link to prioritize matching preset tag rules and problem classification logic, which speeds up issue triage.
The most time-consuming steps for this category—problem classification and completion of reproduction information—require re-ranking output results to directly link to corresponding modules and historical responses, reducing repetitive manual triage work.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `usingReRank` | Enabled. Enable for scenarios where processing a single Issue takes over 30 seconds | This category requires quick location of associated historical responses. Re-ranking improves response efficiency for high-priority issues |
| `similarity` | 0.75–0.85 | Filter irrelevant content with overly low semantic matching, retain retrieval results related to the core requirements of user questions |
| `limit` | Top 8–12 entries | Control the number of results returned per retrieval, adapt to the manual review rhythm of Issue triage, avoid information overload |
| `searchMode` | Hybrid retrieval mode | Adapt to the scattered multi-source data sources of this category, balance matching effects between semantically similar content and structured tags |

## Three Common Configuration Errors
- Phenomenon: An abnormal status code is returned or the number of results is 0 after calling a custom re-ranking service. Cause: The interface address and request parameter format of the re-ranking service are not filled in correctly, and the field structure of Issue data is not adapted.
- Phenomenon: A large number of irrelevant historical response records are mixed in the hybrid retrieval results. Cause: Retrieval filter conditions are not configured based on Issue tag rules, resulting in the retrieval scope not being limited to the target problem set.
- Phenomenon: The number of results returned by a single retrieval exceeds the expected range. Cause: The value of the `limit` parameter is not set correctly, or the range of retrieval data sources is not restricted.

## How to Verify Successful Configuration
- Submit a test Issue, check whether the sorting of retrieval results prioritizes highly relevant historical responses.
- Switch retrieval modes, compare the result coverage of semantic retrieval and hybrid retrieval, confirm that hybrid retrieval can recall content matched by structured tags.
- Check the re-ranking service call logs, confirm that request parameters and return results conform to the expected format.
- Adjust the value of the `similarity` parameter, verify whether the effect of filtering low-similarity results meets expectations.
