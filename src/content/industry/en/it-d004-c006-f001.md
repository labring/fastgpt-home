# Pull Request Review Customer Technical Support and Pre-sales Q&A: HTTP Interfaces and External Systems

## What This Category of Data Looks Like
Pull Request review data typically originates from code repositories, CI pipelines, linked Issue links, and contributor-submitted content. Daily generated documents include PR descriptions, code review comments, CI execution results, and merge records. Data updates follow daily or weekly cycles, driven by code commits, CI triggers, or merge operations. Data fields include changed code blocks, review comments, test statuses, linked task identifiers, and more. There is no unified fixed format, and it adjusts based on repository configurations.

## Constraints for HTTP Interfaces and External Systems
Since PR review data is scattered across multiple source systems such as code repositories and CI pipelines, HTTP interfaces must support cross-system data pulling and permission verification, and adapt to authentication rules of different platforms. Data update cycles are tied to code commits and merge actions, so interface call frequency must match business rhythms to avoid excessive requests triggering rate limits. Data includes unstructured content such as code blocks and review comments, so interfaces must support large request bodies or chunked transfer. Additionally, statuses such as PR review merge conflicts and CI results must be synchronized via interfaces, so interfaces must return standardized status fields to support subsequent processing.

## Configuration Settings
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| File upload toggle | Enabled, set single file maximum size to 1000 MB | Supports uploading test reports and log files linked to PRs |
| History record optimization | Enabled, retain the first 3 rounds of dialogue | Resolves reference resolution issues, adapts to context-linked code change intent |
| Single request timeout | 60–120 seconds | Matches typical time required for code repository data pulling and CI result synchronization |
| Maximum context length | 8000–12000 characters | Accommodates long text content such as PR descriptions and code review comments |
| `responseData` field filtering | Retain code change and review status fields | Accurately extract core data required for PR reviews |
| `variables` global configuration | Bind repository access keys | Uniformly manage authentication information across interfaces |

## Three Common Misconfigurations
- When calling the dialogue interface, PR-linked files cannot be uploaded, only the front-end interface supports upload. Cause: The file upload toggle is not enabled in the HTTP interface configuration, or the correct file size limit is not set.
- Search results do not link to historical dialogue, and reference resolution issues cannot be resolved. Cause: History record optimization is not enabled, or the history record window is set too small.
- Interface requests return configuration error prompts indicating duplicate model-related parameters. Cause: Model-related parameters are added repeatedly in `config.json` and external system authentication configurations, causing parameter conflicts.

## How to Verify Successful Configuration
- Initiate a POST request containing a test file, check whether the `responseData` returned by the interface includes a file upload success identifier.
- Enter a question containing reference content, such as "View the previous change", check whether the returned result links to PR information in the historical dialogue.
- View interface logs, confirm that the `Authorization` authentication header is correctly carried, and there are no 401 or 403 permission errors.
- Wait 60 seconds then initiate a request, confirm that the interface does not trigger a timeout error and returns normal PR review data.

The values provided are common starting points and should be measured against the reader's own samples.
