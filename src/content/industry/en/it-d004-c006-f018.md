# Pull Request Review Customer Technical Support and Pre-sales Q&A: Reranking and Hybrid Retrieval

## What the data for this category looks like
This category's data primarily comes from code repositories, CI pipelines, Issue links, and contributor submission records. Daily documentation includes PR descriptions, code review comments, CI execution results, and merge history. Data update frequency is typically daily or weekly. Fields cover changed code scope, CI pass rate, merge conflict flags, contributor identifiers, and more. There is no unified fixed format; it adjusts dynamically based on project maintenance rules.

## What constraints these characteristics impose on the reranking and hybrid retrieval workflow
PR data from code repositories mixes code snippets and text descriptions. Hybrid retrieval must match both semantic and code structure characteristics. It requires balancing the fusion weights of text and code vectors. Daily or weekly updated data needs regular index refreshes to prevent retrieval results from lagging behind the latest changes. Data from multiple sources has significant format differences. The reranking stage must use unified field weight rules. Otherwise, irrelevant results may appear at the top. CI failure records and conflict flags, which are core to reviews, need adjusted weights to ensure core information is displayed first. This supports confirmation of change intent and test result review steps.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `usingReRank` | Enabled | Adapts to the multi-source mixed characteristics of PR data, improving retrieval result relevance |
| `similarity` | 0.75–0.85 | Filters low-match irrelevant PR content, avoiding redundant results interfering with reviews |
| `limit` | Top 10 entries | Matches the typical viewing scope for PR reviews, controlling the volume of retrieval results |
| `searchMode` | hybrid | Covers both text semantics and code structure characteristics, adapting to the mixed nature of PR data |
| Reranking model selection | Open-source reranking model on virtual machine | Adapts to semantic understanding needs for mixed PR code and text data, supports local deployment |

## Three common misconfigurations
- After enabling `usingReRank`, the reranking model checkbox cannot be toggled in the UI, and the order of retrieval results does not change. The cause is that reranking model parameters are not correctly configured in config.js, or the configured model deployment path is invalid, resulting in the reranking stage failing to load normally.
- After configuring multiple reranking models, retrieval results are not reranked as expected. The cause is that the default reranking model is not specified, or the model loading times out, resulting in the reranking logic not being executed.
- The number of retrieval results exceeds the preset `limit` range. The cause is that the `limit` parameter is not correctly set, or the recall logic during hybrid retrieval does not filter results beyond the threshold, resulting in redundant data being included.

## How to confirm the configuration is correct
- Check the backend configuration interface of FastGPT v4.17.0, confirm that the `usingReRank` switch is enabled, and the reranking model is correctly configured.
- Initiate a PR-related retrieval request, compare the order of results before and after enabling reranking, confirm that the sorting logic is effective.
- Check the number of retrieval results to confirm they match the `limit` parameter setting, with no redundant results beyond the range.
- Review system operation logs, confirm that the reranking model has loaded normally, with no error messages.
