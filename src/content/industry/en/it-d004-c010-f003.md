# Customer Technical Support and Pre-sales Q&A for Incident Response and Troubleshooting: Sharing and Embedding

## What data for this category looks like
Data for this category comes from monitoring alerts, log platforms, APM tools, and user feedback. Updates occur in real time or sync after each event trigger. Daily produced documents include fault tickets, event timelines, emergency plans, and fault notifications. Core fields include unique fault identifier, impact period, affected service scope, executed stop-loss operations, and notification recipients. Document size fluctuates with event complexity, with no unified fixed standard.

## Constraints imposed by these characteristics on sharing and embedding
Real-time updated data sources require embedded content to stay synchronized with platform data. Adjust content refresh logic based on actual data update frequency. Event-specific document structures require embedding configurations to use the sharing link for the corresponding event. This ensures shared content only applies to specific fault scenarios. Multi-source data aggregation requires external systems or corresponding knowledge base configurations to specify the data source scope. This prevents unrelated alerts or log content from being included. Fluctuating document sizes for single events require embedded context carrying capacity to adapt to fault information of different complexities. This prevents content truncation or loading timeouts.

## How to set the configurations
The following configurations apply to FastGPT v4.17.0:

| Configuration Item | Suggested Approach | Rationale |
| --- | --- | --- |
| Sharing entry `shareId` | Copy the full sharing link generated by the system; do not manually replace the identifier | Identifies the sharing entry; business records and data permissions for incident response and troubleshooting must still be handled by external systems |
| Sharing link validity period | Test starting point: 7 days; adjust based on actual testing of incident response and troubleshooting collaboration cycles and revocation requirements | Verify availability within the valid period and access behavior after expiration; this value is not an official default or industry statistic |
| QPM | Test starting point: 20 requests per user per minute; adjust based on actual load | Limits the access frequency of a single user; validation requires combining request logs and actual load |
| Identity verification | When identity permission requirements exist, first verify commercial edition capabilities and the uid returned by third-party identity services | Holding a sharing link does not equate to having business data permissions; third-party identity and data scope must be verified separately |
| Referenced content display | Select display configurations for referenced fragments, full text, and original text based on the sensitivity of incident response and troubleshooting materials | Check displayed content within authorized data ranges; hidden interfaces cannot replace data permission controls |
| Conversation record verification | Test example: Prepare 10 incident response and troubleshooting Q&A samples; check them in the same browser and another device respectively | Anonymous records rely on browser local identity; retention cannot be guaranteed across devices or after cache clearance |

## Three common mistakes
- Sharing entries related to incident response and troubleshooting fail to open. First verify the full system-generated link and its validity period, then check browser request statuses. Do not manually replace `shareId`.
- The visible scope of incident response and troubleshooting data does not match expectations. Verify third-party identity verification results, workflow request parameters, and external system data permissions separately. The sharing entry identifier itself does not provide business authorization.
- The same incident response and troubleshooting Q&A cannot be viewed on another device. For anonymous scenarios, first check device, browser, and local identity status. Record retention cannot be guaranteed across devices or after cache clearance. Do not use this phenomenon alone to judge service abnormalities.

## How to confirm the configuration is successful
- Open the embedded page, check if only work orders and timeline content related to the target fault are displayed, with no unrelated referenced information.
- Click the history record button, confirm that anonymous conversation records under the same device and browser can be viewed.
- Copy the embedded code and insert it into a test page; confirm no errors occur after loading and the expected layout size is displayed.
- Copy the login-free window sharing links corresponding to different events, confirm that the embedded content changes to exclusive information for the corresponding fault when the link changes.

The values provided are common starting points and should be evaluated against the reader’s own samples.
