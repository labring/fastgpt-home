# Customer Technical Support and Pre-sales Q&A for Cloud Host Provisioning and Resource Activation: HTTP Interfaces and External Systems

## What data for this category looks like
The data for this category primarily comes from cloud management platforms, order systems, IAM permission systems, and billing systems. Daily circulating documents include resource activation forms, instance configuration sheets, account permission forms, and delivery confirmation forms. Data is synced in real time per individual order. Each single data entry includes fields such as instance ID, compute specification, network security group configuration, permission binding scope, and delivery status. Common units are cores, GB, and second-level timestamps. No aggregated statistical bulk data is included.

## What constraints these characteristics impose on HTTP interfaces and external systems
Multiple data sources require HTTP interfaces to connect to multiple independent endpoints such as cloud management platforms and order systems. Compatibility with different systems' authentication formats must be supported. The real-time data sync rhythm requires interface timeout thresholds to match the creation cycle of individual resources, to prevent unfinished provisioning processes from being interrupted by timeouts. The variety of document fields requires request bodies to cover core parameters including compute specifications, security group configurations, and permission bindings. It also requires support for pulling data per individual order. This category only focuses on compute resource provisioning, so interfaces do not need to support extended configurations such as network load balancers.

## How to configure settings
The following configurations are written for FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `Authorization` | Authentication format with Bearer Token | Adapts to standard API authentication rules for cloud management platforms |
| Interface timeout duration | 600–900 seconds | Covers the average time required to create and deliver a single cloud host |
| Request batch size | 1–3 orders per request | Avoids excessive interface load caused by pulling too much order data in a single request |
| `variables` | Bind instance ID and order number as global variables | Enables associated transfer of cross-system data |
| `responseData` | Only return instance status and delivery time fields | Reduces invalid data transmission and adapts to the fast query needs of pre-sales Q&A |
| Proxy configuration | 1080–1088 ports, with username and password determined through actual testing | Adapts to network access requirements for internal deployment scenarios |

## Three common configuration mistakes
- Symptom: Interface requests return 403 authentication failure or cannot connect to external cloud systems. Cause: Only proxy IP and port are configured, and no username or password for proxy authentication is provided, so proxy authentication in the internal network environment cannot be passed.
- Symptom: `Data too long`-type errors are returned after calling the interface. Cause: The field length of the returned `responseData` is not limited, triggering database restrictions when writing overlong parameters to local storage.
- Symptom: Resource data associated with the interface fails to load when using login-free links across devices. Cause: The order number parameter in `variables` is not bound in the interface configuration, so requests from different devices cannot match the corresponding resource context.

## How to confirm your configuration is complete
- Initiate a simulated request for single cloud host resource activation, and verify whether the fields returned by `responseData` include the expected instance ID and delivery status.
- After configuring proxy parameters, call the external cloud management platform interface from the internal network environment, and confirm that connectivity is normal and data can be pulled.
- Adjust the interface timeout threshold, simulate a long-duration resource creation process, and confirm that the interface does not interrupt the request prematurely.
- Check the format of the `Authorization` authentication parameter, confirm that it complies with the authentication rules of the connected system, and has no format errors.

The values provided are common starting points and should be evaluated against your own samples.
