# Customer Technical Support and Pre-sales Q&A for Cloud Billing and Cost Accounting: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Data for this category typically comes from cloud billing systems, tag data, order systems, and resource monitoring tools. Update cycles fall into two categories: daily and monthly. Daily data covers temporary same-day billing items. Monthly data aggregates full-cycle costs. Daily output documents include billing details, cost allocation tables, resource utilization reports, and optimization suggestion sheets. Common data fields include billing item codes, unique resource identifiers, cost values, allocation rule identifiers, and resource runtime durations. Units include yuan, hours, and others. There are no unified fixed field naming or unit rules. These adjust based on cloud service providers and business scenarios.

## What Constraints These Characteristics Impose on Multi-turn Dialogue and Prompt Engineering
Decentralized data sources require continuous association of information from different systems during conversations. Multi-turn dialogue must retain `chatId` and `messages` context. This ensures that resources and cost items mentioned by users can be matched across turns. Differences in update cycles require prompts to distinguish real-time billing data from monthly summary reports. This avoids confusion between same-day temporary costs and monthly allocation results. Diverse document structures require prompts to clearly define field priorities for different documents such as billing details and cost allocation tables. Inconsistent fields and units require prompts to include field interpretation rules. This prevents misunderstandings caused by differences in billing item units or naming.

This document applies to FastGPT v4.17.0.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Generate a unique identifier per session | Ensures independent context for each conversation, prevents confusion between cost queries from different users |
| `messages` | Retain the most recent 10 turns of conversation content | Covers the span of multi-turn interactions from single cost queries to explanations of monthly cost allocations |
| `variables` | Bind to cloud service provider billing field mapping tables | Unifies field interpretations for data from different sources, resolves issues with unit and naming differences |
| Maximum context duration | 600 seconds | Matches the update interval of daily bills, avoids loading expired temporary billing data |
| Prompt template | Embed billing field descriptions | Adapts to different query scenarios for billing details and cost allocation tables, clarifies the correspondence between billing items and resource identifiers |

## Three Common Configuration Mistakes
- Phenomenon: Different users initiate conversations using the same application key, and cost data becomes mixed. Cause: No independent `chatId` is generated for each user session. This causes the `messages` context to be shared across users, failing to meet the user-independent query requirements of the cloud billing category.
- Phenomenon: After uploading a billing details or cost allocation table file, the system returns a format not supported prompt. Cause: No CSV and XLSX format whitelist, which are commonly used for cloud billing categories, is added to the configuration. The billing field types that need to be parsed in `variables` are not adapted.
- Phenomenon: After configuring the deepseek model for ollama, the conversation returns no streaming content. Cause: The streaming response trigger rule is not correctly configured in the `messages` parameter. The real-time data query logic of the cloud billing category is not matched, leading to response blocking.

## How to Confirm Successful Configuration
- Initiate a single-turn cost query. Check that `chatId` updates with each request. Ensure that context from different sessions does not overlap.
- Upload a test billing details file. Confirm that the system can recognize the billing items and cost values in the file. Verify that the field mapping bound to `variables` takes effect.
- Initiate consecutive multi-turn queries. Confirm that the conversation can associate previously mentioned resource identifiers and cost items. Verify that the `messages` context retention rule works correctly.
- Start a streaming response test. Confirm that conversation content is returned segment by segment. Verify that the streaming configuration matches the real-time data logic of the cloud billing category.
