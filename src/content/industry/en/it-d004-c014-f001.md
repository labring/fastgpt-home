# Customer Technical Support and Pre-Sales Q&A for Cloud Resource Compliance Auditing: HTTP Interfaces and External Systems

## What the data for this category looks like
This category’s data comes from cloud audit logs, IAM permission configurations, CMDB resource inventories, and security baseline scan results. Cloud security operations, internal audit, and customer compliance teams use this data daily. Core daily documents include compliance checklists, permission audit reports, resource inventory lists, and rectification tracking forms. Data updates occur monthly or quarterly. Data fields include resource unique identifiers, permission configuration status, scan execution time, rectification completion markers, and more. All data comes directly from cloud service native outputs, with no additional custom statistical fields.

## What constraints these characteristics impose on HTTP interfaces and external systems
All data for this category comes from cloud service native interfaces. HTTP interfaces must comply with cloud vendor authentication specifications and data formats.
Data updates occur monthly or quarterly. Keep interface call rates low to avoid triggering cloud service call rate limits.
The field structure of daily documents is fixed. Interface returned data must strictly match the core fields of these documents. Otherwise, the data cannot be directly imported into local compliance workflows.
Data association must be bound to local compliance entries. Interfaces must support parameterized passing of local document association IDs to ensure accurate data linkage.
Errors may lead to audit failure or unauthorized access. Interfaces must include failure retry and exception alert capabilities to ensure reliable data synchronization.

## How to configure settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {cloud vendor IAM access key}` | Follow standard Bearer token authentication specifications when connecting to cloud audit logs and IAM interfaces, to match cloud service authentication requirements |
| `responseData` | Return only resource ID, permission status, scan time | Match core fields of compliance checklists and permission audit reports, reduce invalid data transmission, and lower interface load |
| Data synchronization frequency | Once every 7 days | Aligns with the monthly/quarterly update rhythm of this category, avoids excessive cloud interface calls that incur additional costs |
| Maximum number of resources per single request | Top 100 entries | Matches the batch pull limit of CMDB resource inventories, prevents interface timeouts |
| `variables` | Bind local compliance check item ID, rectification tracking form ID | Associate interface returned data with corresponding entries in local compliance documents to enable data linkage |
| Interface timeout period | 600 seconds | Adapts to the average response duration of cloud service interfaces, avoids synchronization failures caused by network fluctuations |

## Three common mistakes
- An API call for a compliance audit workflow that includes a large model node returns a model API error, but in-app testing works normally. Cause: The interface request’s `variables` parameter does not correctly pass the key and endpoint required for large model calls, causing authentication failure with the external model service.
- When connecting to external document systems such as Feishu, only docx format uploads are supported. Cause: The interface’s configured file type whitelist only allows docx format, and no support for other compliance audit-required document formats has been added.
- Testing fails when connecting to a locally deployed DeepSeek model via Ollama. Cause: The interface’s `Authorization` parameter is not configured with the local model’s access key, or the endpoint address does not point to the locally deployed service address.

## How to confirm the configuration is complete
Call the test interface. Check whether the fields returned by `responseData` include core compliance data such as resource ID, permission status, and scan time.
View interface call logs. Confirm that `Authorization` authentication passes, and no 401 or 403 status codes appear.
Trigger a data synchronization task. Confirm that the number of returned resources does not exceed the preset maximum number of resources per single request limit.
Associate with local compliance checklist entries. Confirm that the data returned by the interface can be correctly mapped to the association ID of the corresponding entry.
