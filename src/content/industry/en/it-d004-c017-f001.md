# Customer Technical Support and Pre-sales Q&A for Code Review and Merge Management: HTTP Interfaces and External Systems

## What data for code review and merge management looks like
Typically, core data for code review and merge management comes from Git repositories, CI pipelines, static scanning reports, and defect databases. Daily business documents include merge requests, code review comments, commit records, and branch strategy descriptions. Common data fields include merge request unique identifiers, commit hashes, reviewer lists, changed file lists, CI build statuses, and detailed review comments. Data update frequency is daily or per commit, with real-time synchronization following code changes.

## Constraints imposed by these characteristics on HTTP interfaces and external systems
Because data sources rely on APIs from code hosting platforms such as Git, HTTP interfaces must comply with the authentication specifications of the corresponding platforms. Data update frequency is high and real-time requirements are strict, so interfaces must support real-time pulling or webhook-triggered synchronization methods. Business document structures are fixed and fields are clearly defined, so interfaces must accurately transmit business parameters related to merge reviews and avoid redundant data transmission. Interfaces must also adapt to branch strategy configurations of different development teams and support multi-dimensional business data queries.

## How to configure settings
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {Git repository personal access token}` | Standard authentication method for connecting to Git repository APIs, compliant with industry general specifications |
| `variables` | Bind merge request ID, commit hash | Accurately locate business data corresponding to code reviews and merges |
| `responseData` | Only return merge request status, review comment list, changed file list | Filter redundant content to reduce interface transmission load |
| API call timeout | 30–60 seconds | Adapt to average response duration of Git repository APIs, avoid frequent timeouts |
| Maximum changed files per pull request | 500 | Match the change scale of conventional merge requests, prevent excessively large interface return data |

## Three common configuration mistakes
- Anomalous billing occurs after calling the interface, with a 401 status code returned. The cause is incorrect configuration of the `Authorization` parameter, using an invalid or incorrect authentication token, resulting in the interface call being misclassified as an unauthorized billing request.
- The interface return data received by the external system contains a large amount of irrelevant CI build logs. The cause is that the filtering rules for `responseData` were not configured according to business requirements, pulling redundant content unrelated to reviews.
- The review process for a specified merge request cannot be triggered via the external system. The cause is that the unique identifier of the merge request was not bound in `variables`, causing the interface to fail to locate the corresponding business data.

## How to confirm successful configuration
- Call the interface and check if `responseData` includes core business fields such as merge request ID and review comments.
- View authentication logs to confirm that the format of the `Authorization` parameter complies with the authentication requirements of the Git repository.
- Simulate an external system trigger for an interface call, verify that changed records for the corresponding commit can be pulled.
- Adjust the business fields bound in `variables` to confirm that the interface can correctly respond to different query requests.

The values provided are common starting points and should be measured against the reader's own samples.
