# Customer Technical Support and Pre-sales Q&A for Code Review and Merge Management: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Data for this category primarily comes from Git repositories, CI pipelines, static scanning reports, and defect databases. Update frequency is daily or per commit. Daily documents include merge requests, code review comments, commit records, and branch strategy descriptions. Merge requests contain a list of changed files, associated branch names, and review status fields. Review comments include commenter, comment time, and modification suggestion fields.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
Data updates frequently and changes in real time with commits. Multi-turn dialogue contexts must support real-time retrieval of the latest Git commit records and merge request statuses. There are diverse document types, so prompts must adapt to retrieval logic for different documents such as merge requests and review comments to avoid confusion over field meanings. Change impact judgment relies on multi-dimensional information. Multi-turn dialogue must break down problems step by step according to commit order and branch associations, gradually guide acquisition of complete context, and ensure large models generate accurate judgments based on latest data.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---|---|--- |
| Single search limit | Top 8 entries | The number of changed files associated with a merge request typically falls between 5 and 10, avoiding retrieval of too many irrelevant review comments |
| Maximum context length | 8000–12000 characters | Fits the total content length of merge requests and multiple review comments, ensuring complete change information is covered |
| Multi-turn dialogue history retention | Last 20 conversation turns | Matches the number of review communication rounds for R&D personnel, avoiding context redundancy that impacts accuracy |
| `variables` variable configuration | Bind branch name and commit ID fields | Accurately filter relevant data for the corresponding merge request, narrowing the retrieval scope |
| Question optimization switch | Enabled | Converts colloquial review questions from R&D personnel into standardized retrieval instructions, improving retrieval precision |
| Version compatibility | FastGPT v4.17.0 | Ensures configuration items are compatible with current platform features |

## Three common configuration mistakes
-  Phenomenon: After setting the single search limit to 2000, the review suggestions generated by the large model do not reference any retrieved content. Cause: The retrieval threshold and context length do not match. Too many irrelevant retrieved entries dilute valid information, preventing the large model from locating core review basis.
-  Phenomenon: Image attachments in static scanning reports cannot be displayed in the dialogue interface. Cause: No image extraction rule was configured during document parsing. Only text content was extracted without loading associated image resources.
-  Phenomenon: Retrieved review records include non-business field IDs. Cause: Metadata fields were not excluded in the retrieval configuration, causing unrelated identifiers to be retrieved and sent to the large model alongside valid content.

## How to confirm configuration is correct
-  Initiate an inquiry that includes a specific branch name, verify that returned review comments only relate to changed content for that branch.
-  Test multi-turn dialogue by initiating 3 to 5 follow-up questions about review comments, confirm that context correctly associates with previous conversation content.
-  Review retrieval results, confirm that returned document paragraphs do not include non-business-related metadata fields.
-  Enable the streaming output switch, initiate an inquiry, confirm that the dialogue interface displays review suggestion content line by line as characters are processed.

The values provided are common starting points and should be measured against the reader's own samples.
