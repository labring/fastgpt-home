# Customer Technical Support and Pre-sales Q&A for Level Content Creation: Reranking and Hybrid Retrieval

## What Data Looks Like for This Category
Typical entities for this category are level design, scene editing, and content production teams. Daily output documents include level design drafts, resource requirement lists, test feedback sheets, and version submission records.
Data mainly comes from level editors, art resource libraries, player test data, and defect systems. Update frequency is weekly or per version cycle.
Core fields for individual documents include level ID, resource path, feedback severity, submission version number, and others. Data formats vary across sources. Some resource data includes binary path information. Test feedback mostly consists of text-based problem descriptions.

## What Constraints Do These Characteristics Impose on Reranking and Hybrid Retrieval
Data sources for this category are scattered and have diverse formats. They include text-based test feedback, binary resource paths, and other content types. Hybrid retrieval must support matching logic across data types.
The weekly or per-version update rhythm means retrieval must adapt to frequent data source refreshes. It must avoid returning outdated historical data.
Core business needs for a single level focus on current version resource configurations and test feedback. Retrieval results must prioritize entries from the current version. This reduces interference from non-current version data.
Errors in this category can lead to level blocks, reduced content quality, or delayed launches. The reranking step must accurately filter low-priority data. It must ensure reasonable sorting of core results.

## Three Common Misconfigurations
- Reranking does not change retrieval result order. The interface displays retrieval results identical to base retrieval results. It does not show priority differences from reranking. The cause is incorrect configuration of the reranking toggle, or a failed reranking model call causing the system to automatically revert to the base retrieval workflow.
- Retrieval takes too long. A single retrieval request exceeds 10 seconds. It fails to meet real-time business response requirements. The cause is setting too large a single search limit, and not limiting the number of entries processed by the reranking model. This leads to excessive data volume in a single request.
- Retrieval results include large volumes of non-current version data. Retrieval results contain resources and feedback from multiple historical versions. This interferes with matching core needs for the current level. The cause is setting the similarity threshold too low. It fails to effectively filter low-match historical data.

## How to Confirm Proper Configuration
- Navigate to the knowledge base configuration page for FastGPT v4.17.0. Check the reranking toggle status. Confirm the feature is enabled.
- Enter core keywords for the current level, such as "current version path design". Check if the order of retrieval results aligns with business priorities. Prioritize displaying current version test feedback and resource requirements.
- Measure the time taken for a single retrieval. Confirm it meets response requirements for the business scenario.
- Adjust the similarity threshold. Verify that the match quality of retrieval results changes reasonably with threshold adjustments.
