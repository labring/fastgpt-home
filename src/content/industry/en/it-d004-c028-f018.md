# Customer Technical Support and Pre-sales Q&A for Content Recommendation Operations: Reranking and Hybrid Retrieval

## What data does this category involve
The data for this category typically comes from content tag libraries, user behavior logs, experiment platforms, and recommendation backends. Daily produced documents include recommendation strategy records, content pool lists, experiment reports, and operational reviews. Data update frequency is mostly daily or weekly. Core fields include content tags, user interaction data, recommendation pipeline metrics, and more. The most time-consuming daily tasks are content pool filtering, experiment indicator interpretation, and abnormal traffic troubleshooting. Data anomalies may lead to low-quality content spreading, declines in core recommendation indicators, or user complaints.

## What constraints do these characteristics impose on the reranking and hybrid retrieval link
Content pools are updated dynamically daily or weekly. This means the recall pool for reranking and hybrid retrieval must adapt to real-time changes in content scale, avoiding a disconnect between the recall range and the currently available content pool. Multi-source data attributes require hybrid retrieval to support recall logic across different dimensions. The reranking stage must adjust sorting priority based on content tag weights and user interaction data. The reliance on experiment reports and operational review documents requires that reranking configurations retain traceable parameter records, to facilitate subsequent indicator interpretation and strategy optimization. The business positioning of regular distribution means that reranking logic must balance content diversity and user preferences, avoiding over-focus on a single type of content.

## How to set configurations
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `similarity` | 0.62–0.78 | Adapts to the content relevance threshold for multi-source recall, balancing content coverage and recommendation accuracy |
| `limit` | Top 15–25 entries | Matches the standard entry scale of daily updated content pools, controlling resource consumption for reranking calculations |
| `searchMode` | hybrid | Supports dual-dimensional recall of content tags and user behavior, meeting the business requirements of hybrid retrieval |
| `usingReRank` | Enabled | For regularly distributed content pools, corrects sorting bias in initial recall and optimizes recommendation effects |
| Rerank model call timeout | 8–12 seconds | Avoids delays affecting the overall timeliness of the recommendation pipeline, adapting to the real-time needs of operational reviews |

## Three common configuration mistakes
- Symptom: The rerank model option cannot be checked in the application configuration page, and the rerank model configured in config.js does not take effect. Cause: The global switch for the rerank model was not enabled in the FastGPT v4.17.0 system configuration, preventing the application layer from calling the configured model.
- Symptom: After adding a rerank model, the order of knowledge base retrieval results does not change as expected. Cause: The `usingReRank` parameter is not set to enabled, or the `limit` parameter value is too large, resulting in reranking only affecting a small number of results that are not easily noticed.
- Symptom: The rerank function is unresponsive, and the backend returns model call failure logs. Cause: The API key configuration for the rerank model is incorrect, or the model version is incompatible with FastGPT v4.17.0, causing the call chain to interrupt.

## How to verify a successful configuration
- Enter the application's retrieval configuration page, confirm that the `usingReRank` parameter is enabled, and the associated rerank model has been correctly bound.
- Initiate a test query, compare the initial recall results with the sorted order after reranking, and verify that the sorting logic takes effect.
- Check the application's running logs, confirm that the rerank model call request has been sent normally, with no timeout or error fields.
- Compare recall results under different `searchMode` configurations, confirm that the multi-dimensional recall logic of hybrid retrieval has loaded normally.
