# Customer Technical Support and Pre-sales Q&A for Creator Incentive Settlement: HTTP Interfaces and External Systems

## What Data for This Category Looks Like
Creator incentive settlement data is typically generated from four sources: content data, advertising revenue sharing systems, financial systems, and account backends. Daily supporting materials include four core documents: incentive rules, settlement details, appeal records, and payment lists. Data updates follow natural month or single activity cycles. Core data fields include creator ID, revenue amount, settlement status, and appeal number, with units including yuan, count, and natural day. Core work for this category focuses on revenue caliber verification, abnormal fraud detection, and payment material verification. This work differs from creator onboarding and certification processes by directly handling revenue calculation and payment-related steps.

## Constraints on HTTP Interfaces and External Systems
Multiple data sources require interfaces to comply with format specifications from different systems to avoid field mapping errors. Monthly or activity cycle update cycles require interfaces to support batch data retrieval on a fixed cycle, or to filter data by a specified time range. Structured requirements for core documents require the `responseData` field returned by the interface to fully match internal document field definitions, ensuring financial systems can directly import settlement data. Error consequences directly relate to creator rights and interests, so interfaces must include abnormal retry and data verification capabilities to prevent incorrect or missed payments. Requirements for troubleshooting core time-consuming links require interfaces to support quick data retrieval by creator ID and settlement cycle.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {FastGPT-generated interface token}` | Complies with HTTP interface standard authentication requirements for FastGPT v4.17.0, ensuring interface call permissions |
| `variables` | Pass the settlement cycle and the list of creator IDs for a single pull; the single list must not exceed 200 entries | Matches data update cycles and avoids interface overload that affects stability |
| `responseData` | Return structured settlement details, appeal status, and payment list fields | Aligns with internal document field formats and supports direct import by financial systems |
| Interface timeout threshold | 600 seconds | Covers the average time required to pull data from multiple systems and prevents normal requests from being misjudged as abnormal |
| Abnormal retry rules | Retry only for 500 status code and timeout scenarios, up to 3 times | Prevents duplicate triggering of settlement processes that lead to incorrect payments, while ensuring data completion in abnormal scenarios |
| Scheduled pull interval | Execute according to activity cycle or natural month | Matches data update frequency and reduces invalid call volume |

## Three Common Misconfigurations
- A 401 Unauthorized error is returned when calling the interface. Cause: The `Authorization` parameter is not configured correctly, or an expired interface token is used.
- The `responseData` field returned after a call is empty. Cause: Correct settlement cycle parameters are not passed in `variables`, so the interface cannot match the corresponding data range.
- A format incompatibility error occurs when connecting to external tools. Cause: The request body is not adjusted according to the base model API format, and non-standard request fields are incorrectly added.

## How to Confirm Successful Configuration
- Call the test interface, check that the `Authorization` parameter is correctly carried in the request header, and the returned status code is 200.
- Check that `responseData` includes expected fields such as settlement details and appeal records, and that the field formats match internal incentive rule documents.
- Simulate abnormal scenarios of timeout or 500 status code, check that the interface triggers the preset retry mechanism, and the number of retries meets the configured requirements.
- Pull settlement data for a single creator, and verify that the returned result matches the original data in the account backend.
