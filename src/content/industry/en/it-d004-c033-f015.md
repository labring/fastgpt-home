# Customer Technical Support and Pre-sales Q&A for Frontend Application Development: Knowledge Base Retrieval and Recall

## What this category of data looks like
Daily documents for this category typically fall into four types: interface documentation, component specifications, debugging records, and release lists. Data sources include code repositories, interface management platforms, design file assets, and browser compatibility databases. Updates follow a schedule of daily synchronization or updates upon each version release.
Interface documentation contains interface paths, request parameters, and return field structures. Component specifications mark props parameters, trigger events, and terminal compatibility ranges. Debugging records track debugging steps and error logs. Release lists record version numbers and change details. Fields often include string parameters, version numbers, compatible terminal types, and have no fixed monetary or time-based units.

## What constraints these characteristics impose on knowledge base retrieval and recall
Data sources for this category are scattered and updated frequently. Retrieval systems must support incremental synchronization across multiple data sources. This prevents full index rebuilds that consume excessive resources. Document structures vary significantly across types. Interface documentation must be split by individual interface. Component specifications must be grouped by props parameters. Flexible chunking rules are required to adapt to different document formats.
Technical fields often include specialized terminology and version numbers. Retrieval must prioritize exact keyword matches to avoid generalized recall of irrelevant content. Frontend technical support requires fast location of compatibility issues. Recall results must include browser compatibility data. Retrieval scope must cover the corresponding data sources.

## How to set configurations
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Matches precise terminology in frontend technical documents, filters low-relevance general technical content |
| `limit` | Top 8–12 results | Controls total token count of retrieval results, adapts to context length requirements in frontend scenarios |
| `usingReRank` | Enabled | Improves recall ranking accuracy for structured documents such as component specifications and interface documentation |
| `searchMode` | hybrid | Combines keyword matching and semantic retrieval, covers specialized term queries and vague question scenarios |
| `datasetSearchUsingExtensionQuery` | Enabled | Automatically expands vague questions in pre-sales consultations, matches simplified phrases such as "popup component" to corresponding documents |
| `collectionIds` | Fill in the frontend knowledge base dataset IDs associated with the current project | Limits retrieval scope, avoids recalling frontend-related documents not belonging to the current project |

## Three common misconfigurations
- When `usingReRank` is enabled and knowledge base indexing is complete, online recall test results do not show reordered changes. The cause is failure to configure passing reranked results during large model invocation, or the rerank model API key was not correctly bound to the current knowledge base.
- When `limit` is set to 3000 results, the large model does not receive context content. The cause is total token count of retrieval results exceeding the large model context window limit, leading to automatic truncation or discarding of context data.
- Retrieval results contain large amounts of duplicate content, or the number of recalled files does not match the configured expectation. The cause is incorrect configuration of the chunk duplicate rate threshold, or failure to adjust chunking rules per document type, leading to excessive duplicate segments.

## How to confirm configurations are correct
- The FastGPT knowledge base retrieval test page is accessed, a frontend-related question is entered, and the returned result ranking is checked to confirm alignment with expected outcomes. This verifies whether `usingReRank` is functioning correctly.
- The `limit` parameter is adjusted to different values, and the number of retrieved results is cross-checked against the configured setting.
- A question containing specialized terminology is entered, and retrieval results are checked to confirm prioritized matching of target documents such as interface documentation and component specifications. This verifies the configuration effect of the `similarity` parameter.
- The dataset association configuration is reviewed, and confirmation is obtained that only the frontend knowledge base associated with the current project is included in the retrieval scope. This verifies the correctness of the `collectionIds` configuration.

The values provided are common starting points and should be measured against the reader's own samples.
