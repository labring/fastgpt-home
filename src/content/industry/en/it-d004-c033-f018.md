# Customer Technical Support and Pre-sales Q&A for Frontend Application Development: Reranking and Hybrid Retrieval

## What this category’s data looks like
Daily documentation for frontend application development includes four core types of content: interface documentation, component specifications, joint debugging records, and release lists. Data sources cover code repositories, interface management platforms, design draft systems, and browser compatibility databases. Update frequency follows daily sync for code changes, or full updates completed with version iterations.

Interface documentation contains interface paths, request parameters, return fields, and status codes. Component specifications include props definitions, event parameters, and compatible browser lists. Joint debugging records contain debug time, issue symptoms, and fix solutions. Release lists contain version numbers, change content, and launch times. Most fields use a mixed format combining structured identifiers and natural language descriptions.

## What constraints these characteristics impose on reranking and hybrid retrieval
The multi-source and dispersed nature of frontend documentation requires retrieval systems to connect to multiple data sources such as code repositories and interface management platforms, to avoid limited retrieval scope. The high-frequency update characteristic requires retrieval indexes to support incremental synchronization, ensuring that latest content like joint debugging records and version changes can be quickly retrieved. The mixed format of documentation, which has both structured fields and natural language descriptions, requires retrieval to support both keyword matching and semantic matching. Relying solely on a single retrieval method easily leads to missed detections or redundant results. The terminal filtering requirement for browser compatibility data requires retrieval to support result filtering by field dimensions, adapting to query demands of different frontend scenarios.

## How to set up configurations
This document adapts to the configuration logic of FastGPT v4.17.0.

| Config Item | Recommended Value | Rationale |
| --- | --- | --- |
| Enable Reranking | Enabled | Frontend documentation includes mixed content types such as component specifications and joint debugging records. Reranking can correct initial ranking biases from vector retrieval |
| Similarity Threshold | 0.70–0.85 | Adapts to interface path matching and semantic descriptions of component attributes, balancing recall accuracy and coverage |
| Single Recall Limit | Top 8–12 results | Adapts to the average length of single frontend documents, controlling context window usage and avoiding exceeding model limits |
| Retrieval Mode | Hybrid Retrieval | Combines keyword retrieval and vector retrieval, adapting to mixed queries including structured keywords like interface paths and component names, and usage scenario descriptions |
| Reranker Model Address | Determined via actual testing | Supports locally deployed reranker models, adapting to deployment scenarios for frontend team-built models |

## Three common misconfigurations
- Empty or insufficient retrieval results displayed in the conversation details page: Data source synchronization is not configured correctly, and indexes for code repository and interface management platform frontend documentation have not been built.
- No corresponding option for the locally deployed reranker model in the platform: The correct model access address is not filled in the configuration items, or security credentials are configured incorrectly, causing the platform to fail to connect to the deployed model service.
- Low-relevance compatibility documents appear at the top of retrieval results: Reranking is not enabled, and only initial ranking from vector retrieval is used, which cannot correct biases from semantic matching.

## How to confirm the configuration is complete
- Access the FastGPT knowledge base configuration page, and confirm the Enable Reranking toggle is enabled.
- Submit a test query containing interface paths and component names, and verify whether the ranking of retrieval results meets expectations.
- Review model service logs, and confirm the platform has successfully connected to the deployed reranker model.
- Check knowledge base synchronization records, and confirm frontend documentation has completed full or incremental indexing.
