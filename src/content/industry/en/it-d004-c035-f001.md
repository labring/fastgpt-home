# Customer Technical Support and Pre-Sales Q&A for Unit and Component Testing: HTTP Interfaces and External Systems

## What this category of data looks like
This documentation applies to FastGPT v4.17.0. Data for this category primarily comes from code repositories, test framework reports, requirement specifications, and interface definitions. Daily deliverables include test cases, coverage reports, Mock instructions, and defect tickets.
Test cases contain fields for case identifier, preconditions, execution steps, and expected results. Mock instructions document interface addresses, request methods, and return parameter structures.
Data updates occur daily or per code commit, and iterate alongside development and testing workflows.

## What constraints these characteristics impose on HTTP interfaces and external systems
Data for this category updates frequently alongside code commits. HTTP interface configurations must align with real-time interface definitions to prevent test failures from parameter mismatches.
Test cases and Mock instructions include standardized request parameter structures. Interface configurations must support variable request bodies and return value validation to accommodate data construction needs for different test scenarios.
Test data construction accounts for a large share of total time spent. Configurations must simplify parameter mapping workflows to reduce manual splicing work.
Failed interface calls directly impact test result accuracy. Clear error capture and feedback mechanisms must be configured to lower the cost of defect troubleshooting.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Use the Bearer token from the test environment interface, formatted as `Bearer <token>` | Matches identity verification requirements for external interfaces, prevents request interception |
| `variables` | Bind parameter variables from test cases, use preset input values from test cases | Reuses standardized data from test cases, reduces manual splicing work |
| `responseData` | Validate that return fields match interface definitions, cover preset valid return value ranges | Ensures interface returns align with test expectations, speeds up logic defect troubleshooting |
| HTTP request timeout | 30–60 seconds | Accommodates the short execution cycle requirements of unit and component tests, prevents test build blocking |
| Request retry count | 2 | Balances interface call success rate and test execution efficiency |

## Three common configuration mistakes
- The `AIPROXY_API_ENDPOINT` missing error occurs when the `AIPROXY_API_ENDPOINT` environment variable for the App/Admin server is not correctly configured. This variable is the root address of the AI Proxy service, with an example format of http://aiproxy:3000. Do not append /v1 or model-related paths. Failure to configure this required environment variable causes startup verification failure.
- HTTP request body parameters in workflows cannot be automatically replaced with preset variables. This happens when the `variables` parameter is not used to bind input values from test cases.
- Interface calls return a 401 status code. This occurs when the `Authorization` parameter is not configured per Bearer token specifications.

## How to confirm configurations are correct
- Run local test cases, check interface request logs to confirm the `Authorization` parameter is correctly included.
- Trigger a test build, verify that HTTP request body parameters in workflows are automatically replaced with preset test variables.
- Simulate non-matching interface returns, confirm that `responseData` validation rules correctly catch exceptions.
- Review test coverage reports to confirm interface test cases cover target code logic.
