# Customer Technical Support and Pre-sales Q&A for Unit and Component Testing: Sharing and Embedding

## What data for this category looks like
Data for this category primarily comes from code repositories, test framework reports, requirement specifications, and interface definitions. Update frequency is daily or after each code commit. Daily documents include test cases, coverage reports, Mock instructions, and defect tickets.
Test cases contain case identifiers, preconditions, execution steps, and expected results. Mock instructions contain interface addresses, request parameters, and return examples. Defect tickets contain defect numbers, reproduction steps, and associated case identifiers. Coverage records the coverage status of each code unit, with no additional percentage-based statistical fields.

## What constraints this category’s characteristics impose on sharing and embedding
The data sources and update characteristics of this category impose multiple constraints on the sharing and embedding workflow. Data is updated frequently with code commits, so the corresponding test knowledge base must have real-time synchronization trigger rules configured by the external business system. This ensures that embedded chatbots always call the latest test cases, coverage reports, and other content.
Data granularity focuses on code units and testing processes. External embedding systems must limit recall scope to only associate test-related documents, to avoid mixing in non-test content. Document fields contain clear identifiers and associated information. External business systems must specify field filtering rules to ensure returned results only include test data relevant to the current technical support query.
Additionally, since data contains code and defect details, external embedding systems must configure access permission controls to prevent unauthorized access to sensitive research and development data. The `shareId` of the corresponding test knowledge base must be used to associate the knowledge base, limit recall scope, and avoid confusion with other business data.

## Three Common Misconfigurations
- Sharing entry for unit and component testing fails to open. First verify the complete system-generated link and its validity period, then check browser request status; do not manually replace `shareId`.
- Visibility of unit and component testing data does not match expectations. Verify third-party identity verification results, workflow request parameters, and external system data permissions separately; the sharing entry identifier itself does not provide business authorization.
- The same unit and component testing Q&A is not visible on another device. For anonymous scenarios, first check device, browser, and local identity status; record retention is not guaranteed across devices or after cache clearing, do not use this phenomenon alone to judge service anomalies.

## How to Confirm Successful Configuration
- Use the share link of the corresponding test knowledge base to initiate queries related to testing topics, verify that returned results only include test-specific documents such as test cases and coverage reports.
- View images in chatbot replies, confirm that clicking them opens in a new browser window or external pop-up, and can be freely scaled to adjust size.
- Check network request logs on the embedded page, confirm that no connection requests to local network segments are initiated.
- Submit a code modification, wait for synchronization to complete, then query for the updated test case information, confirm that returned results include the latest research and development test data.
