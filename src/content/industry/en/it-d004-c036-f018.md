# Customer Technical Support and Pre-sales Q&A for Prototyping and Interaction Design: Re-ranking and Hybrid Retrieval

## What the Data for This Category Looks Like
The typical stakeholders for this category are product designers, interaction designers, and front-end product teams. Daily deliverables include interactive prototypes, page flowcharts, component specifications, and review records. Data sources primarily include Figma or Axure files, internal team design systems, user feedback, and usability test logs. Data update frequency is typically weekly or with each version iteration. Document structures are organized around page operation paths, component attributes, and review comments. Core fields include page node ID, jump logic, component description text, and review modification records.

## What Constraints Do These Characteristics Impose on Re-ranking and Hybrid Retrieval
The core data for this category consists of hierarchical page nodes, operation paths, and review modification records. First, hybrid retrieval must recognize hierarchical associations within documents to avoid retrieving irrelevant isolated component descriptions. Second, since data updates occur weekly or with each version iteration, the retrieval workflow must support incremental update logic to ensure retrieved content always matches the current latest design version. Additionally, documents contain large volumes of operation path descriptions and review comments. The re-ranking step must prioritize content strongly relevant to technical support or pre-sales Q&A scenarios, while filtering outdated design content that has been rejected during reviews.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `usingReRank` | Enabled | This category’s data includes hierarchical page nodes and operation paths. Enabling re-ranking filters low-relevance isolated content and improves retrieval accuracy for technical support scenarios |
| `limit` | Top 8–12 results | Core content for interaction design documents is concentrated in a small number of key page nodes. Limiting the number of returned results avoids redundant information interfering with Q&A scenarios |
| `similarity` | 0.72–0.85 | Operation path descriptions in this category’s documents follow fixed sentence structures. This similarity range accurately matches jump logic or component descriptions from user queries |
| `searchMode` | Hybrid Retrieval | Adapts to the hierarchical document structure of this category, combining full-text retrieval and node association retrieval to cover both page flow and component specification data |

## Three Common Misconfigurations
- Phenomenon: Incompatible request errors returned by the re-ranking model deployed in Docker. Cause: Custom request address was not configured according to the model’s requirements, and input/output fields were not correctly matched to the model.
- Phenomenon: Retrieval results do not prioritize the latest design version content. Cause: Incremental update logic adapted to weekly or version-level updates was not configured, leading to retrieval of outdated review records or old prototype content.
- Phenomenon: The re-ranking model returns empty results or no valid sorting. Cause: The re-ranking model’s API key or request address was not correctly configured, preventing normal calls to the model service.

## How to Verify Successful Configuration
- Access the knowledge base configuration page in FastGPT v4.17.0, and confirm whether the `usingReRank` toggle is enabled.
- Submit a test query including specific operation paths, and cross-check the number of returned results against the setting of the `limit` parameter.
- Compare the order of retrieval results before and after enabling re-ranking, to confirm the re-ranking model has reordered the results.
- Verify the request address and API key for the custom re-ranking model for accuracy, and check that the model’s returned results match expected design document content.
