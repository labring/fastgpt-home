# Customer Technical Support and Pre-sales Q&A for Release Management and Version Acceptance: Knowledge Base Retrieval and Recall

## What this category of data looks like
Data for this category mainly comes from CI pipelines, change management systems, test reports, and monitoring dashboards. The update frequency is weekly or per version cycle. Daily produced documents include release plans, launch checklists, acceptance reports, and rollback plans. Data fields include semantic version numbers, release time windows, change content lists, rollback trigger conditions, and verification steps. Each entry is linked to a specific R&D iteration batch. The length of a single entry adjusts dynamically with release scale, with no unified fixed standard.

## What constraints do these characteristics impose on knowledge base retrieval and recall
The weekly or per-version update rhythm requires the knowledge base to support incremental synchronization. This prevents outdated invalid data from mixing into the current retrieval scope. Multiple types of linked document structures require filtering by version number and release time during retrieval. This ensures recall results match the current iteration batch. Field formats from multi-source automated systems have minor differences between batches. Retrieval must match linked fields to avoid cross-version confusion. Emergency rollback plan documents need prioritized recall. Content weight differentiation must be set to prevent these documents from being overwritten by regular change documents. The number of documents for a single batch release is limited. The single recall upper limit must adapt to this scale to avoid context window overload.

## Configuration Recommendations
| Configuration Item | Recommended Value | Basis for This Setting |
| --- | --- | --- |
| `similarity` | `0.75–0.85` | This category of documents is mostly structured technical content. A threshold that is too low will introduce irrelevant version data, while a threshold that is too high may miss matching change items. |
| `limit` | `Top 6–10 entries` | The number of linked documents for a single batch release is usually 5-8. Excessive recall will exceed the context window limit supported by FastGPT v4.17.0. |
| `searchMode` | `vector+keyword` | This category of data includes structured version numbers and free-text change descriptions. Hybrid retrieval balances exact matching and semantic relevance. |
| `usingReRank` | `Enabled` | Emergency documents such as rollback plans require prioritized sorting. Reranking adjusts result order based on content relevance, improving retrieval efficiency for emergency scenarios. |
| `datasetSearchUsingExtensionQuery` | `Enabled` | User pre-sales Q&A often mentions version compatibility issues. Extended queries can supplement associated test reports and change records to improve response content. |
| `collectionIds` | `Bind to release management exclusive dataset` | Avoid recalling irrelevant documents from other categories, ensuring the retrieval scope accurately matches the current release management scenario. |

## Three Common Misconfigurations
- Phenomenon: An API call for retrieval returns a 401 unauthorized error. Cause: The automatic Bearer token supplement function is enabled, causing the request header to carry a token format that does not meet the requirements of the target knowledge base system.
- Phenomenon: Retrieval results do not display emergency documents such as rollback plans first. Cause: The `usingReRank` function is not enabled, so result order cannot be adjusted based on content relevance, leading to regular change documents overwriting emergency content.
- Phenomenon: Test queries recall invalid cross-version documents. Cause: No version number filtering rules are configured, or `collectionIds` is bound to a non-exclusive dataset containing historical version data.

## How to Confirm Correct Configuration
- An operator accesses the FastGPT knowledge base management page. The operator checks whether `collectionIds` is only bound to the release management exclusive dataset.
- An operator initiates a test query. A question containing a specific version number is entered. The operator verifies that recall results only include documents such as release plans and launch checklists for the corresponding version.
- An operator reviews retrieval logs. The operator confirms that `searchMode` is set to vector+keyword hybrid mode, and the number of recalls falls within the range set by `limit`.
- An operator tests an API call. The automatic Bearer token supplement function is disabled. The operator verifies that the request can normally return matching retrieval results.

The values provided are common starting points and should be measured against the reader’s own samples.
