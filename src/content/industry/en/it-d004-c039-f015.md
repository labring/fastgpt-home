# Backend Service Development Customer Technical Support and Pre-sales Q&A: Knowledge Base Retrieval and Recall

## What this category of data looks like
Daily data for backend service development includes four core document types: interface design documents, database change tickets, code review records, and release notes. Data sources include code repositories, API gateway logs, databases, and configuration centers.
Interface design documents contain structured fields such as interface path, request parameters, and response format. Database change tickets record change time, table name, and operation type. Code review records include reviewer, modified content, and review comments. Release notes include version number, update content, and rollback steps.
Data updates occur daily or per version release, with no fixed batch update cycle.

## What constraints these characteristics impose on the knowledge base retrieval and recall link
Diverse data sources with both structured and unstructured content require retrieval to support both semantic matching and exact keyword matching, to avoid missing key structured information such as interface IDs and error codes.
High update frequency requires indexes to support incremental updates, to avoid performance loss caused by full index rebuilding.
Large differences in document structure exist: some documents require field filtering, such as filtering related change tickets by interface ID, while others require semantic recall, such as troubleshooting documents corresponding to exception logs.
The most time-consuming links are interface contract confirmation and exception log troubleshooting, so retrieval results prioritize core related content to reduce manual screening time costs.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Interface documents and log data for backend services need to balance exact matching and semantic coverage, to avoid filtering out valid historical change records that are similar but relevant |
| `limit` | Top 8–12 entries | Backend service exception logs and change tickets have large data volumes. Too many results increase troubleshooting time, while too few may miss related content |
| `searchMode` | vector+keyword hybrid mode | Data includes structured interface IDs, error codes and unstructured log text. Hybrid mode balances exact matching and semantic recall |
| `usingReRank` | Enabled | Technical issues for backend services often involve transaction boundaries and data consistency details. Reranking prioritizes returning the most relevant code review records or interface contract documents |
| `datasetSearchUsingExtensionQuery` | Enabled | Technical issues for backend services often involve parameter combinations and configuration item associations. Extended queries cover more relevant context |
| `collectionIds` | Split by backend service business modules, such as `["user-service", "order-service"]` | Backend services are usually split into datasets by business module, to facilitate filtering retrieval scope by service and avoid retrieving documents from unrelated businesses |

## Three Common Misconfigurations
- Phenomenon: After a knowledge base is created via API, parsing in progress, ready, and parsing failed status fields cannot be retrieved. Cause: The `datasetSearchUsingExtensionQuery` parameter is not enabled, so extended queries do not return parsing status related metadata.
- Phenomenon: Knowledge base retrieval returns far fewer results than expected. Cause: The `limit` parameter is set to an excessively small value, failing to cover multi-batch related data for backend service logs and change tickets.
- Phenomenon: Retrieval result similarity matching is overly strict, leading to missing related older version interface change records. Cause: The `similarity` parameter is set above 0.9, filtering historical documents that are semantically similar but have differing details.

## How to Confirm Configuration is Correct
- Call the FastGPT v4.17.0 knowledge base retrieval API, check if returned results include backend service specific document types such as interface design documents and code review records.
- Check the `similarity` field value of retrieval results, confirm it falls within the 0.75–0.85 range.
- Trigger a knowledge base parsing task, query parsing status via API, confirm returned status fields include ready, parsing in progress, and parsing failed.
- Simulate an exception log query, check if reranked results prioritize the most relevant exception troubleshooting documents.
