# Customer Technical Support and Pre-sales Q&A for Backend Service Development: Reranking and Hybrid Retrieval

## What data does this category include?
Daily documentation for backend service development includes interface design documents, database change tickets, code review records, and release notes. Data sources primarily include code repositories, API gateway logs, databases, and configuration centers. Data updates daily or when a version is released. Interface design documents contain fields such as interface paths, request parameters, and response formats. API gateway logs contain fields such as request time, status codes, and response latency. Database change tickets contain fields such as change time, affected table names, and operation types. The structure of each data type varies significantly, with distinct field types and business meanings.

## What constraints do these characteristics impose on the reranking and hybrid retrieval workflow?
Backend service development data is multi-source, heterogeneous, and has large structural differences. Hybrid retrieval must support both vector retrieval and keyword retrieval. This covers different data types such as code, logs, and configuration files. Data updates daily or per version. The reranking and hybrid retrieval workflow must support incremental data synchronization. This avoids retrieval results lagging behind the latest interface changes and log records. Field weights vary significantly across different documents. For example, the interface path field has a higher impact on technical support question relevance. Set differentiated reranking weights for different data sources. Retrieval result accuracy directly affects technical support troubleshooting efficiency. Strictly control the proportion of low-relevance results.

## Three common misconfigurations
- Symptom: The "Result Reranking" toggle in the knowledge base shows a red cross, and cannot be enabled normally. Cause: The access key for the reranking model is not configured correctly, or the deployed reranking model is not running normally, preventing the system from verifying reranking capabilities.
- Symptom: An error prompt pops up when testing the reranking function, but valid results can still be generated by running retrieval after ignoring the error. Cause: There is a discrepancy between the permission check logic in the test stage and the actual runtime logic, and temporary access permissions during testing are not loaded correctly.
- Symptom: The API configuration entry for the reranking model cannot be found, or available models cannot be pulled after configuration. Cause: The reranking model integration module has not been enabled in the system settings of FastGPT v4.17.0, or the model access address and key have not been configured correctly.

## How to confirm successful configuration
- Navigate to the target knowledge base settings page in FastGPT v4.17.0, confirm that the "Result Reranking" toggle is enabled, and no red error prompts are displayed.
- Submit a retrieval request related to interface exceptions or log troubleshooting, and check whether the returned results are sorted in line with business logic, with high-relevance interface documents and log entries ranked first.
- Call the reranking API interface, pass in test code snippets and log data, and confirm that the returned reranking scores match the expected relevance ranking.
- Check the system backend logs, confirm that there are no error messages about failed reranking model calls, and that the response time of retrieval requests falls within the preset reasonable range.
