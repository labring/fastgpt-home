# Customer Technical Support and Pre-sales Q&A for Image Annotation Projects: Sharing and Embedding

## What data for this category looks like
Typical users of this category are annotation teams, computer vision algorithm teams, and quality inspectors. Daily documents produced and used include annotation specifications, bounding box examples, quality inspection reports, and rework lists. Data mainly comes from image samples, project category dictionaries, spot check results, and annotators' rework records on the annotation platform, with an update frequency of daily or synchronized per annotation batch. The core data of this category revolves around the position and category of visual targets. Unlike text annotation projects, it requires handling visual interaction tasks such as bounding box delimitation and occluded sample judgment. Data anomalies will directly lead to recognition errors, increased rework rates, or even customer rejection. This document applies to FastGPT v4.17.0.

## What constraints do these characteristics impose on the "Sharing and Embedding" link
The data characteristics of image annotation projects directly restrict the configuration logic of the sharing and embedding link. First, data is updated daily or per batch, and includes sensitive content such as annotation specifications and rework lists. Therefore, sharing links must have validity period restrictions and access permission controls to prevent unauthorized personnel from accessing outdated or sensitive data. Second, core data relies on image samples and category dictionaries from the annotation platform. Shared content is generated by the knowledge base/workflow associated with the corresponding application, combined with current project data from the external annotation platform. FastGPT does not have built-in business data import or scheduled refresh capabilities, ensuring that the displayed bounding box examples and quality inspection reports after embedding fully match the current tasks. In addition, this category involves a large amount of visual content display. The embedded external system must support cross-origin resource loading and responsive layout to adapt to display requirements of different internal systems. Finally, the traceability requirement for annotation rework communication requires internal systems or external services to retain operation logs to avoid inability to trace deleted operations.

## Three common mistakes
- Sharing entries related to image annotation projects fail to open. First check the complete system-generated link and its validity period, then refer to the browser request status; do not manually replace `shareId`.
- The visible scope of image annotation project data does not match expectations. Check the third-party identity verification result, workflow request parameters, and data permissions of the external system separately; the sharing entry identifier itself does not provide business authorization.
- The same image annotation project question and answer cannot be seen on another device. For anonymous scenarios, first check the device, browser, and local identity status; records cannot be guaranteed to be retained after cross-device use or cache clearance, and service abnormalities cannot be judged solely based on this phenomenon.

## How to confirm the configuration is complete
- After generating the sharing link, use a browser outside the team's network segment to access it, and verify whether an access intercept prompt is triggered.
- Check the application configuration corresponding to the non-login sharing link, confirm that the associated project data matches the category dictionary of the current annotation project.
- After operating under the non-login link, check whether internal systems or external services retain operation traces.
- Deploy the embedding code to an internal test system, verify that the bounding box example images load normally and there are no cross-domain errors.

The values provided are common starting points and should be measured against the reader's own samples.
