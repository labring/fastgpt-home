# Customer Technical Support and Pre-Sales Q&A for Backup Recovery and Disaster Recovery Drills: Multi-turn Dialogue and Prompt Configuration

## Data Profile for This Category
Core data for this category originates from backup systems, database logs, object storage, and disaster recovery platforms. Four core document types are routinely generated: backup policies, recovery drill reports, disaster recovery switchover plans, and data validation records. Data update frequencies follow three tiers: daily, monthly, and quarterly. Recovery drill reports are updated per individual drill event, while data validation records are generated daily. The data is linked to cross-system resources, requiring verification of recovery points, drill script execution status, and data consistency validation results. Core stakeholders include operation and maintenance teams, database administrators, and business continuity leads, with a focus on validating cross-system recoverability.

## Constraints on Multi-turn Dialogue and Prompt Configuration
The data characteristics of this category impose clear constraints on multi-turn dialogue and prompt setup. Cross-system data sources require the dialogue to standardize terminology across platforms, to eliminate understanding gaps caused by differing terms between backup systems and disaster recovery platforms. Documents with varying update frequencies require differentiation of context timeliness, so context filtering rules must be configured to avoid calling outdated backup policies or older drill plans. Core processes involve multi-step validation, so the dialogue must support step-by-step retrospective confirmation, such as sequential guidance from recovery point confirmation to script execution and then to data validation. Error outcomes directly impact business continuity, so prompts must include pre-logic for data consistency validation, ensuring responses are based on newly generated validation records.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Maximum Context Length | 8000–12000 token | The longest single core document for this category is approximately 10,000 characters, which corresponds to approximately 8000-12000 tokens. Based on the token calculation rules of FastGPT v4.17.0, this avoids context overload |
| Context Retention Turns | First 20 valid conversation turns | Disaster recovery drill consultations often involve step retrospection; too many turns will interfere with logical judgment of current requests |
| Variable Binding | Bind environment variables for backup systems and disaster recovery platforms | Real-time data from corresponding systems must be called to ensure responses are based on the latest backup status and validation results. The `variables` parameter must be configured to associate with system interfaces |
| Input Length Validation | Within 15000 characters | A single customer consultation input typically does not exceed 12000 characters; setting a reasonable threshold blocks over-limit requests |
| Single Document Recall Limit | Top 6 entries | Associated entries for data validation records in this category typically do not exceed 6; excessive recall will interfere with dialogue logic |
| Multimodal Input Configuration | Enable jpg format support | Adapt to customer-uploaded inputs such as backup topology diagrams and screenshots of drill reports |
| Citation Identification Configuration | Enable document association identification | Facilitate customers to trace the backup policies or data validation records referenced in responses |

## Three Common Misconfigurations
- Dialogue request returns results without citation IDs. The symptom is that after calling the dialogue interface, the returned `messages` field does not include citation identifiers for associated documents, making it impossible to trace the referenced backup policies or validation records. The cause is that citation identification configuration is not enabled, and the `variables` variable is not bound to associate document metadata with dialogue response logic.
- Input exceeding the limit triggers unblocked error messages. The symptom is that the dialogue node returns a system error indicating input length over limit, without blocking over-limit requests as configured. The cause is that no input length validation rule is set, or the threshold is set unreasonably higher than the input limit of the AI model.
- Unable to access jpg files as dialogue input. The symptom is that after uploading a jpg-format backup topology diagram, the dialogue module cannot parse the image content, and the response does not include information related to the image. The cause is that multimodal input configuration is not enabled, and no jpg-format image-to-text preprocessing steps are configured.

## How to Verify Correct Configuration
- Initiate a dialogue containing "query the latest backup policy", check if the response includes citation identifiers for the corresponding document, to confirm that the citation configuration is effective.
- Construct input text exceeding 15000 characters, check if an input length blocking prompt is triggered, to confirm that the validation rule is effective.
- Upload a jpg-format disaster recovery drill topology diagram, initiate a dialogue containing "describe the content of this topology diagram", check if the response can correctly parse the image information.
- Initiate a new dialogue and end it, check if the conversation record corresponding to the `chatId` of that dialogue can be deleted normally, to confirm that the conversation management function is working properly.
