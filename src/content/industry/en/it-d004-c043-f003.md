# Customer Technical Support and Pre-sales Q&A for Security Incident Emergency Response: Sharing and Embedding

## What data for this category looks like
Data for this category comes from SIEM, EDR, firewall logs, and host images. Update frequency is real-time or triggered per single incident. Daily associated documents include emergency response reports, forensics records, disposal plans, and notification materials. Data fields include attack source IP, affected assets, disposal timestamp, evidence hash values, and more. There are no fixed unified units, and values adjust dynamically based on forensics and disposal content per incident.

## What constraints do these characteristics impose on the "sharing and embedding" workflow
The real-time update feature of this category's data requires that shared embedded sessions connect to external business systems to dynamically pull the latest security device logs. This avoids using expired forensics or disposal data.
Multi-source heterogeneous logs and report content require embedded pages to support mixed display of structured fields and unstructured text.
Since content such as attack paths and evidence chains is sensitive, permission control for sharing links must be implemented by the external business system. FastGPT's no-login window only provides a basic sharing entry. Permission binding needs to connect to the external business system.
For pre-sales Q&A scenarios, multi-language adaptation must be implemented by the external business system in the embedded code. FastGPT's no-login window only provides a basic display framework.
The volume of evidence data for a single incident may be large. Embedded pages need to limit the content size loaded at one time to prevent page freezes that affect usage.

## Three common misconfigurations
- Sharing entries related to security incident emergency response fail to open. First verify the complete system-generated link and its validity period, then check browser request status; do not manually replace `shareId`.
- The visible scope of security incident emergency response data does not match expectations. Verify third-party identity verification results, workflow request parameters, and external system data permissions respectively; the sharing entry identifier itself does not provide business authorization.
- The same security incident emergency response Q&A cannot be viewed on another device. For anonymous scenarios, first check device, browser, and local identity status; records cannot be guaranteed to be retained after cross-device use or cache clearing, do not judge service anomalies based solely on this phenomenon.

## How to confirm the configuration is complete
- Open the sharing link, check if the page display language matches the preset configuration, confirm that the target language can be used without manual switching.
- Enter a query related to the current security incident on the no-login page, confirm that the content returned by the external business system includes the latest logs or disposal records of the corresponding security device.
- Verify the external voice input function, confirm that the service can be called normally and the input content can be submitted and displayed properly (need to combine the actually deployed voice service).
- Copy the custom parameters preset by the external business system, add them to the embedded code, refresh the page, confirm that the content corresponding to the parameters is displayed normally.
