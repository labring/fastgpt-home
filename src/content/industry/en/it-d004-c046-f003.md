# Customer Technical Support and Pre-sales Q&A for Security Baseline Inspection: Sharing and Embedding

## What the data for this category looks like
This category's data primarily originates from server configurations, middleware configurations, security device policies, and export results from baseline tools. Daily associated documents include baseline checklists, configuration verification records, rectification suggestions, and exception approval forms. Fields cover configuration item numbers, compliance status, rectification requirements, approval status, and similar items. There are no unified fixed units; some fields must be aligned with the organization’s own security baseline definitions. The data update frequency is monthly or quarterly, and it is regularly maintained and verified by security operations staff, consultants, and internal audit personnel.

## Constraints Imposed on the Sharing and Embedding Workflow
The core data of security baseline inspection relies on internal organizational configuration and approval documents, and must match the organization’s exclusive security baseline. Unlike vulnerability scanning services, this category only focuses on whether configurations comply with the organization’s security baseline. Therefore, the sharing and embedding link must restrict data permission scope to avoid cross-organizational baseline data leaks. Since the data update frequency is monthly or quarterly, the access cache of shared links must be coordinated with the data update rhythm to prevent returning expired configuration verification results. Associated documents include sensitive fields such as approval status, so embedding scenarios must support identity authentication to only allow authorized users to access corresponding baseline data. Baseline fields vary across different organizations, and dynamic loading of field configurations must be implemented separately by external business systems. FastGPT only provides basic sharing and embedding display capabilities.

## Three Common Mistakes
- Security baseline inspection-related sharing links fail to open. First verify the complete system-generated link and its validity period, then check browser request status; do not manually replace `shareId`.
- The visible scope of security baseline inspection data does not match expectations. Verify third-party identity verification results, workflow request parameters, and external system data permissions separately; the sharing entry identifier itself does not provide business authorization.
- The same security baseline inspection Q&A cannot be viewed on another device. For anonymous scenarios, first check the device, browser, and local identity status; retention cannot be guaranteed across devices or after cache clearing, and this phenomenon alone cannot be used to judge service anomalies.

## How to Confirm Proper Configuration
- Copy the generated shared link, access the link without logging in, and confirm that identity authentication verification is triggered.
- Embed the iframe component into a test page, log in using a background authorized account and perform operations, and confirm that the login status does not experience abnormal loss.
- Switch to a mobile device to access the embedded page, and confirm that the layout of baseline verification content adapts normally.
- Verify that the `shareId` extracted from the shared link can correctly identify the corresponding sharing entry and associate with the baseline inspection scenario.

The values provided here are common starting points and should be evaluated against the samples of the respective organization.
