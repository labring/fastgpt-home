# Customer Technical Support and Pre-sales Q&A for Security Vulnerability Disclosure Handling: HTTP Interfaces and External Systems

## What the data for this category looks like
This category's data comes from private vulnerability reports, code repositories, CVE numbering authorities, and official release channels. Updates follow the rhythm of individual vulnerability events, with no fixed cycle. Daily documents include security advisories, vulnerability reports, patch packages, and CVE application materials. Data fields include vulnerability IDs, impact scopes, fixed versions, disclosure times, report sources, and more. Units are mostly event-level identifiers, version numbers, and timestamp formats. There are no universal bulk statistical fields.

## What constraints these characteristics impose on HTTP interfaces and external systems
The data characteristics of this category impose multiple constraints on HTTP interfaces and external systems. The sensitive nature of private vulnerability reports requires interfaces to be configured with strict identity verification to prevent unauthorized access to sensitive vulnerability information. The single-event update rhythm means there is no need to set a high-frequency polling strategy; interface calls can be triggered on demand. Documents include large-volume content such as binary patch packages, so interfaces must support large-volume data transmission or chunked responses. Cross-entity disclosure time coordination requirements require the transmission of standardized coordination parameters to achieve synchronization. Returned data must include key fields such as CVE IDs, and return structures must be standardized to ensure external systems can accurately extract information.

## How to configure settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale for This Value |
| --- | --- | --- |
| Authentication Verification Key | `Bearer {project-specific secret}` | This category of data contains sensitive vulnerability information. This configuration is used to verify the caller's identity to prevent unauthorized access |
| Synchronization Parameter Template | `{"cve_id": "", "disclose_time": "", "impact_scope": ""}` | Used to transmit core parameters for cross-system synchronization such as vulnerability IDs and disclosure times, adapted to single-event-level data transmission |
| Return Data Structure | `{"code": 200, "data": {"cve_no": "", "patch_version": ""}, "msg": "success"}` | Standardize returned fields to ensure external systems can accurately extract key information and avoid missing fields |
| Interface Timeout Period | 600 seconds | The evaluation and patch preparation process for individual vulnerability events takes a long time, so sufficient response duration must be reserved |
| Response Data Size Limit | 1000 MB | Must support transmission of large-volume documents such as binary patch packages to avoid transmission failures due to size restrictions |
| Parameter Verification Switch | Enabled | Prevent vulnerability information leaks or processing exceptions caused by invalid parameter input |

## Three common misconfigurations
- Phenomenon: A 401 Unauthorized error is returned when calling the interface, and vulnerability-related information cannot be obtained. Cause: The correct authentication verification key is not configured, or the key has been improperly shared, resulting in verification failure.
- Phenomenon: External systems cannot obtain real-time update information for disclosure time coordination, and can only retrieve old data. Cause: On-demand trigger calling logic is not configured, and fixed polling is still used, which cannot synchronize real-time changes.
- Phenomenon: The response data received by the external system is incomplete, and patch packages cannot be loaded or CVE IDs cannot be extracted. Cause: The response data size limit or return data structure is not properly set, resulting in missing key fields or truncated data.

## How to verify the configuration is complete
- Call the configured interface with the correct authentication verification key, and check that the returned status code is 200.
- Pass the preset synchronization parameter template, and check that the returned interface data contains the content corresponding to the parameters.
- Upload a test binary patch package, call the interface to obtain a response, and check that the size of the returned data meets the preset limit.
- Pass parameters in an invalid format, and check that the interface returns a clear error prompt to verify that the parameter verification switch is active.

The values given are common starting points and should be measured against the reader's own samples.
