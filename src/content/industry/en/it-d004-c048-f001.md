# Customer Technical Support and Pre-sales Q&A for Security Monitoring and SOC On-duty: HTTP Interfaces and External Systems

## What the data for this category looks like
Data sources for this category include SIEM, EDR, NDR, and various threat intelligence feeds. Update cycles fall into two categories: real-time and daily. Regularly produced documents include alarm disposal sheets, duty logs, threat intelligence reports, and daily and weekly reports. Fields cover alarm ID, disposal status, threat level, associated assets, and more. No unified fixed unit exists; values adjust based on different data sources and document types. Typical users include SOC analysts, security operation outsourcing teams, and enterprise security centers. These teams routinely use this data to complete alarm triage and escalation handling.

## What constraints these characteristics impose on HTTP interfaces and external systems
Real-time updated data sources require interfaces to support low-latency requests or callbacks, preventing alarm data lag that impacts triage efficiency.
Multi-source heterogeneous data formats require interfaces to support different parsing rules, adapting to the output formats of various security devices.
The flexibility of document fields requires interfaces to support custom field mapping, meeting the personalized needs of different teams.
Time-consuming alarm triage links require interfaces to support asynchronous task submission, avoiding alarm backlog caused by synchronous request timeouts.
The risk of false alarm backlog requires alarm data returned by interfaces to carry filterable label fields, facilitating quick screening of valid alarms.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Interface timeout period | 600 seconds | Adapt to real-time alarm triage response requirements, avoid alarm missed reports caused by timeouts |
| Single request data volume | No more than 500 entries | Match batch export scenarios for duty logs, reduce interface load |
| Field mapping rules | Map by alarm ID, asset IP, threat level | Match the field structure of alarm disposal sheets, facilitate data association by external systems |
| Authentication method | API key authentication | Adapt to SOC system security management requirements, avoid unauthorized access |
| Return data format | JSON format | Compatible with data parsing logic of mainstream SIEM and EDR systems |
| Retry mechanism | Retry 2 times after failure, 30 second interval | Respond to temporary network fluctuations, reduce alarm disposal interruptions |

## Three common misconfigurations
- Interfaces return duplicate alarm disposal sheet entries. This occurs when deduplication logic is not configured, leading to repeated pulling of alarm data from the same batch.
- Interface calls return a 401 status code. This occurs when authentication parameters are not correctly carried or tokens expire, failing to pass the external system's security verification.
- Alarm fields received by external systems are empty. This occurs when correct field mapping rules are not configured, leading to failure to correctly transfer core business fields.

## How to confirm proper configuration
- Send a test request, check that the returned JSON data includes preset core fields and has no redundant content.
- Simulate 10 consecutive requests, check that all interface return status codes are 200, with no frequent timeouts or authentication failures.
- Connect to an external SIEM system, verify that alarm data can be correctly synchronized to the system's alarm list.
- In FastGPT v4.17.0 interface logs, confirm that request authentication parameters are correctly carried with no format errors.
