# Customer Provisioning and Tenant Initialization Support and Pre-Sales Q&A: Multi-turn Dialogue and Prompt Engineering

This document applies to FastGPT v4.17.0.

## What This Category of Data Looks Like
Data sources for this category include CRM systems, contract order systems, identity management systems, and product backends. Daily maintained documents include provisioning application forms, tenant configuration sheets, administrator account lists, and delivery confirmation forms. Data update frequency is per order or daily. Core fields include tenant ID, administrator accounts, permission configuration items, delivery status, and more. In typical processing workflows, the most time-consuming steps are customer information verification, permission initialization, and provisioning result confirmation. The processing process must strictly match the exclusive configuration data of a single tenant. Unlike customer data import and migration, this category prioritizes establishing accounts and basic configuration before carrying out subsequent data association.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
The data characteristics of this category directly constrain the design logic of multi-turn dialogue and prompt engineering. First, data sources are scattered and bound to a single tenant. Prompts must clearly specify the retrieval scope to avoid cross-tenant data confusion. Second, the update frequency is per order or daily. Dialogue context must be limited to the application cycle of a single tenant to avoid calling expired data. Third, core steps take a long time. Multi-turn dialogue must include step-by-step confirmation logic to reduce manual verification costs. Finally, errors directly affect customer login and delivery acceptance. Prompts must include an exception verification step to identify configuration errors in advance.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `messages` | Sorted dialogue turns based on the tenant application workflow | Messages must be organized in the actual communication order to ensure the model understands the complete provisioning workflow |
| Multi-turn dialogue context window | Top 10 dialogue turns | Tenant initialization workflows typically include 3-8 steps, retaining the top 10 turns covers the complete application, configuration, and confirmation process |
| `variables` | Bound to exclusive configuration fields for the current tenant | Data sources come from single-tenant documents, using variables to limit the retrieval scope avoids cross-tenant data leakage |
| Maximum context length | 800–1200 characters | Calibrated through actual testing, avoids excessive length causing the model to confuse irrelevant information |
| Dialogue timeout threshold | 600 seconds | Covers the typical operation time required for customer information verification and permission initialization |
| `chatId` | Bound to the unique tenant ID as the session identifier | Must accurately match the configuration data of a single tenant; `chatId` can uniquely identify the dialogue session |

## Three Common Mistakes
- Symptom: Unable to specify only the current tenant's knowledge base during API calls. Cause: Tenant ID is not configured as a retrieval filter condition in `variables`, causing the model to retrieve full knowledge base content
- Symptom: Dialogue return results do not include the permission information configured for the tenant. Cause: The prompt does not explicitly bind the tenant-exclusive configuration fields in `variables`, causing the model to fail to retrieve the corresponding data
- Symptom: Automatic session termination is not triggered after timeout. Cause: No session timeout verification based on `chatId` is set, causing sessions that have not responded for a long time to occupy system resources

## How to Confirm Proper Configuration
- Initiate a simulated provisioning application dialogue, check whether the model can accurately retrieve the configuration fields for the current tenant
- Verify that the session bound to `chatId` only associates documents for the current tenant, with no cross-tenant data mixed in
- Test timeout scenarios, confirm that the session automatically terminates or triggers an alert after the set threshold
- Check whether the prompt template includes the complete steps of customer information verification, permission initialization, and result confirmation
