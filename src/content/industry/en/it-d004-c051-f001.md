# Customer Technical Support and Pre-sales Q&A for Customer Data Import and Migration: HTTP Interfaces and External Systems

## Data Structure for This Category
This category of data primarily originates from customers’ historical business systems, standard CSV or Excel templates, database export files, and the product’s built-in import logs. Daily supporting documents include data import templates, migration execution plans, field mapping comparison tables, and migration verification reports. Data updates occur per order or irregularly, with no fixed cycle. Data fields must align with the target system’s business rules, and include core items such as customer identifiers, business serial numbers, and content text. Units vary based on business scenarios, with no unified fixed unit.

## Constraints for HTTP Interfaces and External Systems
Data sources for this category are scattered and have diverse formats. HTTP interfaces must support multiple input formats including CSV, Excel, and database query results. They must also support field mapping configuration to match the target system’s business field rules. Single-batch data volume may be large. Interfaces must support segmented submission or paginated data pulling to avoid single-request timeouts. Data updates have no fixed cycle, and errors can lead to severe consequences. Interfaces must provide clear error return codes and detailed logs. They must also support a failure retry mechanism to prevent overall migration failure from dirty data or abnormal requests. Additionally, interfaces must support identity association verification. This ensures external system users match the FastGPT platform’s operation permissions, and prevents unauthorized access to migrated data.

## Configuration Settings
This configuration applies to FastGPT v4.17.0 and later versions.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {Application API Key}, minimum 32 characters` | Complies with FastGPT application API authentication specifications, and ensures the legitimacy of external requests |
| `variables` | Includes custom parameters such as customer ID, data batch number, and mapping rule ID. Parameter values are calibrated for the specific business scenario | Used to pass context information related to external systems and migration tasks, ensuring the accuracy of field mapping |
| `responseData` | Returns the number of successful imports, number of failed imports, and error detail list. Total response size does not exceed 1000 KB | Facilitates quick retrieval of migration results by external systems, and supports generation of migration verification reports |
| Single request data volume | 1000–2000 items per request | Balances request timeout risk and migration efficiency, avoiding timeouts caused by overly large single requests |
| Timeout duration | 600 seconds | Adapts to the processing time of large-batch data, preventing migration interruptions from request timeouts |

## Three Common Misconfigurations
- Phenomenon: The interface returns a 401 unauthorized error, or cannot recognize the user identity of the external system. Cause: The AI Proxy administrator Token is used as the application API Key when filling in the authentication parameter. Credential types for platform service authentication and application interface authentication are confused. Server-side AI Proxy environment variables are not correctly configured.
- Phenomenon: A maxLength error triggers during batch data import, or single-request processing times out. Cause: Single-submitted data volume and request timeout duration are not adjusted for the business scenario. This causes the request body to exceed limits or have insufficient processing time.
- Phenomenon: Field misalignment or data loss occurs after import. The migration verification report shows mismatched mappings. Cause: Correct field mapping parameters are not included in the interface request, or format consistency between source data and target fields is not verified in advance.

## How to Verify Proper Configuration
- Call the test interface, check if the returned authentication result shows legitimate passage, and confirm the `Authorization` parameter is configured correctly.
- Submit a small batch of test data, verify if the returned `responseData` includes correct counts of successful and failed imports and error details, and confirm the interface return format meets expectations.
- Check if the `variables` parameter carried in the interface request includes necessary context information for the current migration task, and confirm all parameters are fully passed.
- View the import logs on the FastGPT platform, confirm the migration task triggered by the external request has executed normally, with no abnormal errors.

The values provided here are common starting points, and should be evaluated against samples specific to the actual deployment scenario.
