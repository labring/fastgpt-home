# Customer Data Import and Migration Technical Support and Pre-sales Q&A: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Data for this category comes primarily from customers’ historical business systems, standardized CSV/Excel templates, database export files, and FastGPT platform import operation logs. Daily supporting documents include data import templates, migration execution plans, field mapping comparison tables, and migration effect verification reports. The data update rhythm adjusts irregularly based on project progress. Updates typically occur after each migration action or when receiving customer feedback. Core data fields fall into three categories: business entity identifiers, attribute values, and association relationships. Some scenarios require auxiliary fields such as data creation time and verification tags.

## Constraints on multi-turn dialogue and prompt engineering workflows
The data characteristics of this category create multiple constraints for multi-turn dialogue and prompt engineering workflows. First, data sources include multiple heterogeneous formats. Different customers use varying field naming and unit standards. Multi-turn dialogue must be used to gradually confirm field mapping rules, avoiding direct application of generic templates. Second, the number of supporting documents is large, and updates happen frequently. Prompt designs must guide users to upload corresponding documents per project phase. This ensures the dialogue context links only to the latest files for the current migration task. In addition, data update rhythms are irregular. Bind single-task dialogue chains using `chatId` to prevent context confusion across different projects. Limit dialogue context length to avoid lag caused by excessive historical data.

## Three common misconfigurations
- Phenomenon: Cannot upload data templates or field mapping tables when calling the dialogue API. Returns an error message of "unsupported file type". Cause: Fails to explicitly require users to submit content via the specified migration document submission entry in prompts. Incorrectly applies generic dialogue file upload logic.
- Phenomenon: Historical dialogue records for different customers are not isolated. Migration data from other projects can be viewed across projects. Cause: Fails to bind a unique `chatId` for each migration task. This leads to shared context, violating the business requirement to isolate data by project for this category.
- Phenomenon: Workflow nodes can only initiate a single question. Cannot adjust field mapping rules based on user feedback. Cause: Fails to configure multi-turn dialogue trigger logic. Only calls the single-turn question and answer interface. Does not enable multi-turn context management functionality.

## How to confirm proper configuration
- Initiate a test question containing keywords such as field mapping and dirty data cleaning. Observe if the system automatically starts a multi-turn confirmation process. Check that the dialogue context only links to content from the current test task.
- Generate two different migration task test dialogues. Confirm their respective dialogue records cannot access each other. Verify that data isolation configuration is active.
- Upload test CSV templates and field mapping tables. Check that the system correctly identifies and associates the files with the current dialogue task. No error messages should be returned.
- Wait longer than the preset response timeout duration. Observe if the system can normally handle subsequent questions. Verify that the timeout configuration is reasonable.
