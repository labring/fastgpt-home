# Customer Demand Pool Management for Customer Technical Support and Pre-sales Q&A: HTTP Interfaces and External Systems

## What the data for this category looks like
Daily data for this category comes from ticketing systems, customer interviews, CRM, and product roadmaps. The update frequency is typically weekly or when each product version is released. Daily documents include demand pool lists, demand assessment forms, customer feedback records, and version planning descriptions. Fields usually include demand source identifiers, customer tiers, demand descriptions, assessment scores, scheduling status, and other standard fields. There are no additional custom statistical fields, and the data structure aligns with the routine demand management processes of business teams.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Because data sources are scattered and the field structure is fixed, interfaces need to be compatible with the authentication formats of multiple external systems, while strictly matching the data update rhythm to avoid invalid calls. Since the data update cycle is long, the interface pull frequency should not be too high, otherwise it will exceed the call limits of external systems. In addition, the accuracy of demand data directly affects business scheduling. The return fields of the interface must strictly align with the structure of daily documents, to avoid errors in demand merging and assessment stages caused by missing fields.

## Configuration settings
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {external_token}`, calibrated based on actual testing with connected systems | Complies with industry general authentication specifications when connecting to external systems such as ticketing and CRM, ensuring interface call security |
| `variables` | Bind the token value of workflow global variables, in the format `{"token": "{workflow_token}"}` | Meets the requirement of passing authentication credentials across systems, and adapts to business scenarios |
| `responseData` | Only return the `demand_id, customer_level, priority, status` fields | Aligns with the field structure of daily demand pool documents, reducing transmission redundancy |
| Pull interval setting | `86400 seconds` (for weekly updates) or `2592000 seconds` (for version updates) | Matches the update cycle of data for this category, avoiding invalid calls that exceed external system limits |
| Retry strategy | Retry `2 times` after failure, with a `60 second` interval | Addresses temporary fluctuations in external systems, ensuring data synchronization stability |

## Three common configuration mistakes
- The `variables` field is empty when calling the interface, which prevents passing workflow global tokens. This occurs because global variables in the workflow are not correctly mapped to the variable parameters in the interface configuration, and the binding action is not completed.
- Calling the query interface returns an empty `responseData` array with no relevant customer demand content. This occurs because correct data source association rules are not configured, demand data from sources such as ticketing systems and CRM is not pulled, and the association permissions between the application and knowledge base are not matched.
- A large amount of duplicate data appears when pulling demands in batches. This occurs because deduplication rules are not configured, and duplicate merging is not performed based on demand IDs or customer feedback identifiers, leading to data redundancy that affects demand assessment.

## How to confirm the configuration is complete
- Manually trigger an interface call, and check if the returned `responseData` fields include expected fields such as demand ID and customer tier.
- View workflow logs to confirm that the `variables` field has correctly passed parameters such as global tokens.
- Call the interface three consecutive times at the configured pull interval, and confirm that the update status of the returned data aligns with the weekly or per-version update rhythm.
- Call the interface with an invalid `Authorization` token, and confirm that a 401 status code is returned to verify that the authentication logic is working.
