# Customer Technical Support and Pre-sales Q&A for Container Platform Operations: HTTP Interfaces and External Systems

This document is based on FastGPT v4.17.0.

## What data for this category looks like
Data for this category mainly comes from Kubernetes API, image registries, monitoring systems, and CI pipelines. Daily associated operation and maintenance documents include cluster change tickets, namespace quota tables, deployment records, and fault reports. Fields cover cluster node status, Pod runtime logs, resource quota thresholds, image version numbers, and more. Units are mostly seconds, entries, and GB. Data update frequency is daily or after each cluster change. Data is synchronized in real time or on a schedule alongside cluster adjustments, fault troubleshooting, and release workflows. Data volume fluctuates with cluster scale and change frequency.

## Constraints imposed by these characteristics on HTTP interfaces and external systems
Data sources are scattered and linked to the entire cluster operation and maintenance workflow. This requires HTTP interfaces to support permission verification for multi-source data pulling. The corresponding `Authorization` parameter must be configured with a cluster-specific service account token. Data update frequency is triggered by changes, so interface calls must align with change windows to avoid resource conflicts caused by frequent requests during cluster upgrade periods. Document fields include structured data such as quotas and logs. Interface responses must strictly match field formats, otherwise they cannot be directly imported into operation and maintenance document systems. Additionally, due to the high availability requirements of cluster operations, interface timeout thresholds must adapt to the fluctuating response delay range of cluster nodes.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | Read-only token for the cluster-specific service account | Matches Kubernetes API permission verification rules, ensuring secure access to cluster resources |
| `variables` | Fill in cluster node IPs, namespace quota thresholds, image registry addresses, and file paths | Simplifies parameter passing for cross-scenario calls, adapts to integration requirements for different operation and maintenance and external systems |
| `responseData` | Return only core fields such as Pod status, resource usage, and image version | Filters redundant data, adapts to structured import requirements for operation and maintenance documents and external systems |
| Request timeout | 30–60 seconds | Adapts to the conventional response delay range of the Kubernetes API, avoiding timeouts triggered by cluster load fluctuations |
| Retry count | 2 times | Responds to temporary cluster network fluctuations, reducing the probability of single call failure |

## Three common mistakes
- Phenomenon: Returns a 403 Forbidden error when calling the Kubernetes API. Cause: The `Authorization` parameter is not configured, or the used service account is not granted access permissions for the corresponding namespace.
- Phenomenon: A single interface runs normally during debugging, but results are abnormal when calling multiple external systems in sequence. Cause: Dynamic parameters are not passed via `variables`, and subsequent interfaces reuse residual configurations from the previous call.
- Phenomenon: Cannot pass file-format parameters when calling external systems. Cause: File paths and related permission parameters are not configured in `variables`, causing the interface to fail to recognize file-format requests.

## How to confirm configurations are correct
- Call the configured HTTP interface, check that no permission-related errors are returned, and confirm that the `Authorization` configuration is effective.
- Pass the preset `variables` parameters, verify that the interface correctly uses cluster node IPs and quota thresholds to initiate requests.
- View the returned content of `responseData`, confirm that only the preset core operation and maintenance fields are included, with no redundant information.
- Simulate a cluster change scenario, initiate 2 consecutive interface calls, confirm that the retry mechanism triggers normally and there are no duplicate request conflicts.

The values provided here are common starting points and should be evaluated against the reader's own samples.
