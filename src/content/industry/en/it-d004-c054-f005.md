# Customer Technical Support and Pre-Sales Q&A for Container Platform Operations: Multi-Turn Dialogues and Prompt Engineering

## What data for this category looks like
Usually, daily documents for container platform operations include cluster change tickets, namespace quota tables, deployment records, and fault reports. Data originates primarily from Kubernetes APIs, image registries, monitoring systems, and CI pipelines, with updates occurring daily or per cluster change. Data fields include cluster node identifiers, Pod running statuses, image version numbers, resource quota thresholds, etc. Units are mostly counts, seconds, MB, and namespace name identifiers. There is no fixed statistical aggregation format, and data must be pulled in real time per single dialogue request.

## What constraints these characteristics impose on multi-turn dialogues and prompt engineering
Since data sources are scattered and update frequencies are inconsistent, multi-turn dialogue context cannot be retained indefinitely, as this would introduce expired cluster configuration information. The structured fields of daily documents require prompts to explicitly specify the query field range, to avoid generalized queries that return irrelevant data. Errors in operation and maintenance scenarios directly affect business stability. Dialogue exception handling must strictly match the verification rules of cluster data, and attachment parsing can only be limited to currently uploaded content, to avoid loading redundant historical documents that interfere with troubleshooting.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| ---|---|--- |
| Maximum context dialogue turns | First 10 turns | Matches the single dialogue data volume for container platform operations, avoids context overload that affects response speed |
| Context auto-clear trigger rules | User sends "clear" or "reset" keywords, or auto-triggers every 24 hours | Adapts to the daily or on-demand update frequency of data, prevents old configurations from interfering with current dialogues |
| `variables` configuration | Fixed variables including cluster identifier and namespace name | Accurately matches exclusive data fields for cluster operations, avoids confusion from cross-cluster queries, complies with FastGPT v4.17.0 variable configuration specifications |
| Knowledge base reference switch | Default off, only enabled when explicitly requested by the user | Operation and maintenance scenarios mostly rely on native cluster API data, no additional knowledge base references are needed |
| Conversation link authentication configuration | Enable team-level authentication | Protects the internal sensitivity of cluster operation and maintenance data, prevents external visitors from accessing sensitive configurations |
| Attachment parsing scope control | Only parse currently uploaded attachments | Avoids parsing redundancy caused by loading historical documents, aligns with the single-troubleshooting needs of operation and maintenance scenarios |

## Three common misconfigurations
- Knowledge base references cannot be disabled in dialogues, with the symptom that every reply includes knowledge base reference content. The cause is failing to turn off the default knowledge base reference switch, or failing to configure the rule to only enable it when requested by the user.
- Dialogue context is not cleared per conditions, with the symptom that the `messages` field contains redundant historical dialogue records. The cause is failing to configure context auto-clear trigger rules, or failing to bind trigger conditions to cluster change events.
- Attachment parsing loads historical documents, with the symptom that document parsing results include files not currently uploaded. The cause is failing to configure attachment parsing scope control, with the default setting loading all historical documents, which does not match the user's requirement to only parse the current attachment.

## How to confirm configurations are correct
- Send a command including "clear context", check that the `messages` field only retains current dialogue content.
- Generate a conversation share link, attempt to access it using an unauthorized account, confirm that the conversation content cannot be viewed, verifying that the cluster permissions bound to `chatId` take effect.
- Upload a single attachment and initiate a parsing request, check that the parsing result only includes the currently uploaded attachment, with no historical documents included.
- Initiate a quota query request for a specified namespace, check that the returned result only matches the quota data for that namespace, verifying that the cluster identifier in the `variables` configuration takes effect.
