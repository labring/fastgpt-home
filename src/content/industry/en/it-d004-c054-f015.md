# Customer Technical Support and Pre-sales Q&A for Container Platform Operations: Knowledge Base Retrieval and Recall

## What this category’s data looks like
Data for this category comes primarily from Kubernetes APIs, image registries, monitoring systems, and CI pipelines. Daily generated documents include cluster change tickets, namespace quota tables, deployment records, and fault reports.
Data updates occur either via daily synchronization or in real time when cluster changes are made. Most document structures include resource identifiers, configuration parameters, operation steps, and exception details. Fields cover operation-specific identifiers such as cluster node IDs, quota values, Pod statuses, and image versions. No unified external packaging format is used for these documents.

## Constraints for knowledge base retrieval and recall
Data sources for this category are scattered and have varying formats, including Kubernetes native APIs and monitoring system outputs. Retrieval processes must support vector alignment for multi-source heterogeneous data.
Data update rhythms adjust flexibly based on cluster changes. Incremental recall must be supported to avoid full index rebuilding.
Document fields include operation-specific tagged values such as quota numbers, Pod statuses, and image versions. Retrieval processes must retain semantic associations between fields to improve matching accuracy.
High-frequency troubleshooting scenarios focus on resource quota adjustments and Pod exception troubleshooting. Results strongly related to operation and maintenance keywords must be prioritized for recall.

## Configuration recommendations
These recommendations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Threshold for semantic similarity matching of resource and exception keywords in container platform operation scenarios, balances recall coverage and result accuracy |
| `limit` | Top 10 entries | Adapts to single-round troubleshooting result counts, avoids excessive results that increase engineer filtering workload |
| `searchMode` | Semantic priority | Matches high-frequency operation scenarios such as Pod exceptions and quota adjustments, prioritizes results with high semantic relevance |
| `usingReRank` | Enabled | Corrects sorting bias in initial recall, adapts to complex association logic for cluster configurations and exception scenarios |
| `datasetSearchUsingExtensionQuery` | Enabled | Automatically expands operation-related synonyms, such as associating "Pod crash" with "Pod abnormal exit", improves recall coverage |
| `collectionIds` | Bound to cluster operation-specific datasets | Limits retrieval scope, avoids interference from unrelated documents, adapts to dedicated data scenarios for container platform operations |

## Three common configuration errors
- Knowledge base search response times out, with single retrieval taking over 30 seconds. Cause: Recall scope has not been optimized for multi-source container platform data, triggering full dataset retrieval.
- No change in result sorting after enabling `usingReRank`. Cause: Associated parameters for the re-ranking model have not been configured, or the re-ranking model does not adapt to semantic associations of Chinese operation and maintenance terminology.
- Retrieval result sorting does not match expectations, with high-frequency operation and maintenance keywords not appearing at the top. Cause: Initial recall `similarity` threshold is set too high, filtering out valid results with slightly lower scores but semantic relevance, or semantic priority mode for `searchMode` has not been enabled.

## How to verify successful configuration
- Retrieve keywords related to cluster change tickets, verify that returned results include configuration parameters and operation steps for the corresponding cluster.
- Review retrieval logs, confirm that only cluster operation-specific datasets have been bound, and no unrelated business documents have been retrieved.
- Trigger a retrieval for Pod exception troubleshooting, check that returned results include fault reports and troubleshooting guide documents.
- Adjust the `similarity` parameter, compare retrieval results, confirm that the number and relevance of recalled results change appropriately with parameter adjustments.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
