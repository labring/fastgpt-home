# Customer Technical Support and Pre-Sales Q&A for Ticket Handling and Issue Categorization: Knowledge Base Retrieval and Recall

## What data for this category looks like
The data for this category originates from ticketing systems, customer support chat logs, product operation logs, and customer contract SLA documents. Daily generated documents include customer tickets, issue categorization tables, issue handling records, and customer service reports. Data updates occur daily or in real-time sync. Document fields include ticket unique identifier, customer associated information, issue description text, pre-categorization label, impact scope, responsible team identifier, processing time limit requirements, and more. Most fields are text or enumeration types, with no complex nested structures.

## Constraints on Knowledge Base Retrieval and Recall From These Characteristics
Most data for this category consists of unstructured customer issue descriptions and historical handling records. Update frequencies include real-time sync. This requires knowledge base retrieval to support fast incremental updates and semantic matching. Data includes pre-categorization labels and responsible team identifiers. Retrieval must support filtering recall results by categorization labels and responsible team dimensions to prevent invalid cross-team matches. Text lengths of tickets and chat records vary significantly. Some short questions only contain core requests, so semantic recall accuracy for short text must be supported. Historical handling records include resolved issue solutions. Recall must link to valid solutions corresponding to the categorization, to avoid returning outdated or mismatched content.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` | `0.85–0.92` | Filters results with low semantic matching for this category of short-text issue requests, avoids invalid recall |
| `limit` | `Top 8–12 results` | Reduces customer support screening overhead by returning only enough results for fast ticket matching |
| `searchMode` | `Semantic Priority` | Prioritizes semantic matching over keyword matching, as this category data primarily uses natural language customer descriptions |
| `usingReRank` | `Enabled` | Further filters result relevance, adapts to multi-source historical ticket data |
| `datasetSearchUsingExtensionQuery` | `Enabled` | Automatically expands related synonyms based on user questions, covers similar ticket issues with different phrasing |
| `collectionIds` | `Bind knowledge base collections corresponding to ticket categories` | Precise retrieval scope limitation, avoids invalid recall of cross-category data |

## Three Common Configuration Mistakes
- Low matching content with semantic similarity below the preset threshold appears in retrieval results. This occurs when the threshold range for the `similarity` parameter is not configured correctly, or the threshold is set too low.
- The knowledge base does not sync data for the corresponding ticket category. This occurs when the correct `collectionIds` are not bound, or database connection configurations after deployment are not updated.
- Retrieval processes remain in a loading state. This occurs when the `limit` parameter sets too many recall results, or `usingReRank` is not enabled, causing retrieval calculation time to exceed business allowable limits.

## How to Verify Proper Configuration
- Submit a typical customer ticket question, check if the semantic similarity of retrieval returned results matches the preset `similarity` threshold range.
- Check the binding relationship of knowledge base collections, confirm that the `collectionIds` parameter is associated with the ticket and handling record dataset for this category.
- Simulate a single retrieval request, confirm that the number of returned results does not exceed the range set by the `limit` parameter.
- View the retrieval logs in FastGPT v4.17.0, confirm that the `usingReRank` and `datasetSearchUsingExtensionQuery` parameters are active.

The values provided here are common starting points, and should be measured against the user’s own samples.
