# Customer Technical Support and Pre-sales Q&A for Ticket Handling and Issue Tiering: Reranking and Hybrid Retrieval

## Data Profile for This Category
This category's data originates from ticketing systems, chat logs, product logs, and customer contract SLAs, with an update cadence of daily or real-time. Daily documents include customer tickets, issue tiering tables, processing records, and service reports. Data fields include ticket unique identifiers, customer-associated information, problem description text, tiering tags, processing status, and SLA constraint items. Each entry corresponds to the complete processing chain for a single customer feedback or inquiry.

## Constraints Imposed on Reranking and Hybrid Retrieval
Data for this category comes from structured ticketing fields, unstructured chat and product log text, with update cadences ranging from real-time to daily. This requires the reranking and hybrid retrieval pipeline to support both structured field matching and unstructured semantic retrieval. Data is linked to customer SLA constraints and historical processing records, so retrieval results must prioritize processing rules matching the corresponding service level. The pipeline must also support incremental synchronization and scheduled refresh update modes to avoid tiering deviations caused by delayed data.

## Configuration Guidelines
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `usingReRank` | Enabled | Ticket issues contain a large volume of content with similar semantics but different phrasing. Reranking optimizes the sorting priority for tiering matching. |
| `similarity` | 0.72–0.85 | This range balances recall precision and recall coverage, as low-relevance redundant historical ticket data must be filtered out. |
| `limit` | Top 10 entries | The volume of historical data returned per retrieval must align with customer service review efficiency to avoid information overload that slows issue tiering. |
| `searchMode` | Hybrid Retrieval | Both structured ticketing fields and unstructured problem descriptions must be matched to cover multi-dimensional retrieval needs. |
| Rerank model call timeout | 30 seconds | Ticket processing must comply with SLA constraints. Timeouts will cause response delays and negatively impact customer service experience. |

## Three Common Configuration Errors
- Symptom: The interface displays the `Invalid URL (POST /v1/rerank)` error. Cause: The rerank model API address is configured incorrectly, and does not correctly point to the deployed rerank service endpoint.
- Symptom: Tests return a `401 unauthorized` error. Cause: The rerank model access key is configured incorrectly, and it does not match the authorization verification rules of the deployed image.
- Symptom: The number of results returned by the rerank step does not match the configured `limit` value. Cause: The recall scope of hybrid retrieval is not aligned with the filtering logic of the rerank step, resulting in some data not participating in reranking.

## How to Verify Successful Configuration
Under FastGPT v4.17.0, configuration status can be verified using the following actions:
- Review retrieval pipeline logs to confirm that both structured ticketing fields and unstructured problem descriptions are matched, verifying that the hybrid retrieval configuration is active.
- Trigger a rerank test for a single ticket, check that the sorting priority of returned results aligns with historical tiering association rules, verifying that the rerank function is enabled.
- Cross-check the number of filtered results to confirm they fall within the reasonable range for business review, verifying that the similarity threshold and single retrieval limit configurations match.
- Test the rerank model call response to confirm it does not exceed the preset timeout threshold, verifying that the timeout configuration is reasonable.
