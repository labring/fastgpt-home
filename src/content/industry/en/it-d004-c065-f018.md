# Customer Technical Support and Pre-Sales Q&A for Interface Integration and Data Docking: Reranking and Hybrid Retrieval

## What data for this category looks like
The exclusive data for interface integration and data docking includes multiple types of structured and unstructured content. Data sources are primarily customer system interfaces, API documentation, test data, and integration logs. Update frequencies fall into two categories: daily updates and project phase updates. Daily documents include interface lists, integration records, field mapping tables, and issue tracking tables. The interface list contains structured fields such as interface addresses, request methods, parameter names, and return codes. Integration logs record unstructured content such as call chains, error codes, and troubleshooting processes. Field definitions and units must strictly match the customer system’s definitions. Common units include milliseconds, characters, bytes, and others.

## What constraints do these characteristics impose on the reranking and hybrid retrieval link
The data structure and update rhythm of this category impose multiple constraints on the reranking and hybrid retrieval link. First, structured interface lists and unstructured integration logs coexist. Hybrid retrieval must adapt to the recall logic of both types of data to avoid recalling only a single type of content. Second, data update frequencies are inconsistent. Daily updated test data and phase-updated integration records require adjustment of retrieval priority based on time weight to ensure the latest integration troubleshooting results are displayed first. Third, field definitions must strictly match the customer system’s definitions. Retrieval must first recall content directly related to interface parameters and error codes to avoid mismatching generic technical content unrelated to the current integration project. Finally, retrieval results in this link directly impact integration troubleshooting efficiency. The number of results and sorting logic must be controlled to reduce information screening costs.

## How to set configurations
| Configuration Option | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Similarity Threshold | 0.70–0.85 | Core threshold for matching interface field definitions and error information, filters out irrelevant generic technical content |
| Single Recall Limit | Top 8–12 entries | Controls the number of results for basic single-round recall, adapts to information display density for single-round integration troubleshooting |
| Retrieval Mode | Hybrid Retrieval | Recalls both structured interface lists and unstructured integration logs to cover all relevant associated data |
| Enable Reranking | Yes | Sorts recalled results by error correlation and field matching degree to prioritize the most relevant troubleshooting content |
| Number of Results Displayed After Reranking | Top 5–7 entries | Focuses on core troubleshooting clues to reduce information browsing burden |

## Three common mistakes
- Phenomenon: When configuring a reranking model, configurations for models with the same name are overwritten, and only the last added model is displayed in the interface. Cause: The system uses the model name as the unique identifier by default, and does not provide multi-instance management or renaming functions.
- Phenomenon: When calling a third-party reranking model, empty content is returned. The interface returns status code 200 but has no valid retrieval results. Cause: The model interface permissions are not enabled, or the request parameter format does not match the field structure required by the model.
- Phenomenon: An open-source model deployed locally cannot be connected to the retrieval process, and expected integration-related content cannot be returned. Cause: The model’s API access address and port are not configured correctly, or external access permissions for the corresponding port are not enabled.

## How to confirm that the configuration is complete
- Upload a mixed test set containing interface lists, integration logs, and test data, then verify if the coverage of recalled results meets expectations after running retrieval.
- Check the toggle status of the reranking feature, then confirm that the top N results from the retrieval match the preset field matching degree and error correlation.
- Call the test interface, then confirm that the number of returned retrieval results matches the configured single recall limit and number of results displayed after reranking.
- Verify that data from all relevant sources (such as API documentation, integration logs) is correctly recalled without missing associated content.
