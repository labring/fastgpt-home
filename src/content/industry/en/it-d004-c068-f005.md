# Customer Technical Support and Pre-sales Q&A for Database Cloud Service Operations: Multi-turn Dialogue and Prompt Engineering

## What data for this category looks like
The data for this category mainly comes from cloud database consoles, slow logs, monitoring metrics, and ticket systems. The update frequency is daily or after each instance change. Daily generated documents include instance change orders, backup and recovery records, performance diagnosis reports, and parameter adjustment records. Fields typically include instance unique identifiers, backup file size, slow SQL execution duration, and adjusted parameter values. Units include MB, seconds, entries, and similar units.

## What constraints these characteristics impose on the "multi-turn dialogue and prompt engineering" link
Scattered data sources require integrating multiple types of information such as consoles and slow logs during multi-turn dialogue. Prompts must clearly specify the call format for each data source. Real-time update frequency adjustments tied to instance changes require limiting the context length of `messages` to avoid loading outdated data. Fixed document structures require prompts to match the field order of instance change orders and performance diagnosis reports to prevent information confusion. Multi-tenant service boundary requirements mandate automatically filtering instance data that does not belong to the current tenant during dialogue, to ensure returned content complies with regulations.

## How to configure settings
These configurations are based on FastGPT v4.17.0.

| Config Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Max Context | Top 10 dialogue turns or 8000 characters | Matches the length of a typical daily performance diagnosis report, avoids loading excessive outdated data |
| `messages` | Only retain dialogue history for the current tenant | Complies with multi-tenant service boundary requirements, prevents cross-tenant information leakage |
| `variables` | Bind the current instance ID and tenant identifier | Obtains exclusive data for the corresponding instance from the cloud database console, ensures accurate queries |
| Question Optimization | Enabled | Automatically completes common questions about slow SQL positioning and backup recovery, improves dialogue coherence |
| Single Search Limit | Top 6 entries | Matches the standard number of returns for slow logs and monitoring metrics, avoids information overload |
| `chatId` | Bind the instance unique identifier | Differentiates dialogue sessions across tenants, ensures context isolation |

## Three common configuration mistakes
- Calling the dialogue guidance interface returns an `unAuthChat` error, and `apikey` has been configured. The cause is that the current tenant's instance permissions are not bound, or the tenant identifier parameter is not correctly passed in `variables`.
- Dialogue returned content contains line breaks, causing JSON request failure. The cause is that the prompt does not specify escaping line breaks to `\n`, and returning raw text directly destroys the request format.
- An error occurs after uploading a database backup file, but text dialogue works normally. The cause is that parsing rules for database backup files are not configured, or the target field for file parsing is not specified in `variables`.

## How to confirm correct configuration
- Initiate a test dialogue that includes an instance ID, verify that returned content only includes instance data for the current tenant.
- Send a test question containing line breaks, check that the JSON format of the returned result is complete with no errors.
- Upload a database backup file, verify that parsed fields match the structure of daily documents.
- Initiate multiple consecutive questions, confirm that the context length does not exceed the preset limit, and the dialogue process is not interrupted.
