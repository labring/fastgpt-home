# Database Operations Customer Technical Support and Pre-sales Q&A: Sharing and Embedding

## What the data for this category looks like
This category's data comes primarily from database monitoring, audit logs, SQL execution plans, and ticketing systems. Daily production includes documents such as database change orders, slow SQL reports, backup records, and permission application forms. Most fields include instance ID, execution time, impact scope, approval status, and similar items. Units include milliseconds, bytes, entries, and others. Data updates occur daily or in real time when database changes are made. Document structures vary slightly across different instances, requiring adaptation to multi-dimensional operation and maintenance scenarios.

## What constraints these characteristics impose on the sharing and embedding workflow
Since data sources involve monitoring and audit content related to operation and maintenance permissions, access permissions must be strictly controlled during sharing and embedding to prevent unauthorized users from accessing sensitive database information. Document structures are diverse. The embedded component displays only content configured in the FastGPT application. Custom field display requires separate implementation by external business systems. Data updates trigger when changes occur. Embedded content requires synchronous updates via external business systems to avoid displaying outdated data. Permissions for data associated with ticketing systems must be verified through the connected third-party identity verification system. Access control cannot rely solely on `shareId`.

## How to configure settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Sharing Entry `shareId` | Copy the full share link generated by the system, do not manually replace the identifier | Identifies the sharing entry; database operation business records and data permissions must still be handled by external systems |
| Share Link Validity Period | Test starting point: 7 days; adjust based on actual database operation and maintenance collaboration cycles and revocation requirements | Verify availability within the valid period and access behavior after expiration; this value is not an official default or industry statistic |
| QPM | Test starting point: 20 requests per user per minute; adjust based on actual load | Limits access frequency for a single user; requires verification combined with request logs and actual load |
| Identity Verification | When identity permission requirements exist, first verify commercial edition capabilities and the uid returned by the third-party identity service | Holding a share link does not equate to having business data permissions; third-party identity and data scope must be verified separately |
| Referenced Content Display | Select display configurations for referenced fragments, full text, and original text based on the sensitivity of database operation and maintenance materials | Check displayed content within authorized data ranges; hidden interfaces cannot replace data permission controls |
| Conversation Record Verification | Test example: Prepare 10 database operation and maintenance Q&A samples, check them in the same browser and another device respectively | Anonymous records rely on browser local identity; retention cannot be guaranteed across devices or after cache clearance |

## Three Common Mistakes
- Database operation and maintenance related sharing entries fail to open. First verify the full system-generated link and its validity period, then check browser request status. Do not manually replace `shareId`.
- The visible scope of database operation and maintenance data does not match expectations. Verify third-party identity verification results, workflow request parameters, and external system data permissions separately. The sharing entry identifier itself does not provide business authorization.
- The same database operation and maintenance Q&A cannot be viewed on another device. In anonymous scenarios, first check device, browser, and local identity status. Retention cannot be guaranteed across devices or after cache clearance; do not use this phenomenon alone to judge service abnormalities.

## How to Confirm Successful Configuration
- Copy the embedded code to a local test page, access it, and check if the Q&A interface for the corresponding database operation and maintenance knowledge base loads.
- Test embedding on sites with different domains, confirm that only configured whitelist domains can load shared content normally.
- Initiate a slow SQL query, wait for the external business system to complete data update, reload the embedded page, and confirm that the query record is displayed synchronously.
- Check if the `shareId` in the embedded code is a valid identifier generated by the FastGPT non-login window. Avoid using manually fabricated IDs.

The values provided are common starting points and should be evaluated against local test samples.
