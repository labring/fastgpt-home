# Customer Technical Support and Pre-sales Q&A for Logging Platforms and Observability: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Data for this category primarily comes from logging systems, Trace platforms, Metrics systems, and application SDKs. Daily supporting documentation includes logging collection specifications, link tracing instructions, metric dictionaries, and dashboard configuration records. Data update frequency is daily or tied to version iterations. Data fields include log levels, TraceID, timestamps, metric values and their corresponding units, etc. Field naming rules vary across different systems, and some custom fields lack unified standards.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompt Engineering
The data sources for this category are scattered, and field naming varies. This requires multi-turn dialogue to retain context to associate TraceIDs and log entries across different systems. Data update frequency is high, so prompts must regularly sync the latest collection specifications and dashboard configurations to avoid referencing outdated rules. Daily documentation is split across multiple independent entries, so prompts must clearly specify retrieval scopes to guide the model to prioritize matching documents from the corresponding category. Metric units differ across systems, so multi-turn dialogue must guide users to supplement system source information to ensure accurate parameter interpretation.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Single Search Limit | Top 5 entries | Logging and observability data have a large number of entries; too many entries will exceed the context window. The top 5 entries cover typical troubleshooting scenarios |
| Reranking | Enabled | Observability data contains a large number of similar logs; reranking can raise the priority of highly relevant entries and help quickly locate issues |
| Query Optimization | Enabled | User questions in pre-sales and technical support scenarios often have vague descriptions. After optimization, troubleshooting directions can be clarified, adapting to context association in multi-turn dialogue |
| Maximum Context | 8000–12000 characters | Logging and link tracing data have long contexts. This range covers at least 2 full troubleshooting conversations and avoids losing critical TraceIDs |
| `variables` | Preset logging system identifiers and metric unit rules | This helps the model unify field interpretation standards and reduce confusion across system data |
| `messages` | Retain the most recent 8–10 conversation turns | Excessively long history will occupy the context window. This number of turns covers typical step-by-step troubleshooting workflows and ensures coherent context |

## Three Common Misconfiguration Scenarios
- Symptom: When initiating a conversation via API, the generated response does not reference the configured knowledge base documents. Cause: The associated identifier of the knowledge base is not bound in `variables`, or the `messages` parameter does not carry the association marker for retrieval context.
- Symptom: When using FastGPT v4.17.0 and certain older versions, the knowledge base page or conversation page crashes. Cause: The knowledge base index format for the corresponding version is not matched; configuration parameters of older versions have compatibility differences with newer versions.
- Symptom: When deploying a model with Ollama, the preset pre-sales guiding prompts do not function. Cause: The `messages` parameter for the initial conversation does not correctly insert system prompt content, causing the model to not follow the rules of the guiding prompts when generating responses.

## How to Verify Successful Configuration
- Initiate a test question that includes known knowledge base content, and verify whether the response references fields or rules from the corresponding document.
- View the conversation history corresponding to `chatId`, and confirm whether the context of multi-turn dialogue is correctly retained and critical TraceIDs are not lost.
- Check whether the preset parameters in `variables` match the field rules of the currently used logging system to ensure accurate parameter interpretation.
- Trigger a complete multi-turn troubleshooting workflow, and confirm that the model will guide users to supplement necessary information such as system source or metric unit.
