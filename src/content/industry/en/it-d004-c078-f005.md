# Customer Technical Support and Pre-sales Q&A for Cabinet Rack Installation and Cabling: Multi-turn Dialogue and Prompt Engineering

## Data for This Category
Business data for cabinet rack installation and cabling scenarios primarily comes from DCIM systems, asset management systems, network topology diagrams, and customer work orders. Daily produced documents include rack installation application forms, cabinet cabling diagrams, port label lists, and construction records. Fields include cabinet number, U-position location, cable model, construction date, and acceptance status. Data updates are completed per order: each rack installation or cabling change triggers an update, with no fixed batch update schedule. Entities associated with this data include IDC operation and maintenance engineers, network engineers, and equipment implementation personnel, who rely on accurate physical asset information to complete business operations.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
Decentralized data sources and per-order updates require multi-turn dialogues to bind a unique identifier to lock the context of a single work order, preventing cross-order information interference. Diverse document structures and targeted fields require prompts to adapt to different document formats such as installation application forms and cabling diagrams, accurately extracting core business fields like cabinet numbers and port locations. No fixed batch update schedule for data means dialogue contexts must support real-time association with the latest asset system data; static knowledge bases alone cannot cover all scenarios. This category focuses on physical access for new or changed equipment, with clear differences from inspection scenarios. Dialogues must clearly distinguish the contextual boundaries between physical operations and status monitoring to avoid logical confusion.

## Configuration Settings
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` binding rule | Bind a unique identifier for a single work order | Lock the dialogue context for a single scenario, preventing cross-order information interference |
| Context window length | 1000–1500 characters | Adapt to the typical content length of a single installation application or cabling diagram, avoiding interference from redundant information |
| `variables` configuration | Extract cabinet number, port location, cable type | Match the core fields of business documents, quickly associating with real-time data from asset systems |
| `messages` storage rule | Archive by application + user dimension | Avoid overload of dialogue data under a single application, simplifying historical query and management |
| Timeout handling threshold | 600 seconds | Adapt to the loading and verification duration of construction records and network topology diagrams, preventing interruptions during long document processing |
| Prompt template binding | Associate with exclusive document sets for installation and cabling | Match the business document structure of this category, ensuring prompt output complies with physical operation requirements |

## Three Common Configuration Mistakes
- The client closes the SSE connection after a dialogue is initiated, and the `messages` field is not fully written to the database. This occurs because automatic persistence logic for session interruptions is not configured, resulting in lost or residual incomplete dialogue data.
- Calling the dialogue history interface returns full application data without filtering by application + user dimension. This occurs because the association rule between `chatId` and user identifiers is not correctly bound, and query parameters by application dimension are not enabled.
- The port verification result returned by the prompt does not match the actual assets. This occurs because the `variables` parameter is not correctly configured, and core fields such as cabinet number and port location are not extracted, leading to incorrect context matching.

## How to Verify Correct Configuration
- Initiate a test dialogue, manually close the SSE connection, and check whether complete `messages` records exist in the database.
- Call the dialogue history interface, pass the specified application and user identifiers, and confirm that the returned results only contain dialogue data for that user.
- Input `variables` parameters such as cabinet number and port location, and verify whether the prompt can associate with document content from the corresponding asset system.
- Set a 600-second timeout threshold, simulate the scenario of loading a long network topology diagram, and confirm that the dialogue does not interrupt unexpectedly.
