# Customer Technical Support and Pre-Sales Q&A for Penetration Testing Services: HTTP Interfaces and External Systems

## What this category of data looks like
Business data for penetration testing services primarily comes from target systems, public vulnerability databases, automated scanner results, and manual verification records. Update cycles follow individual test projects or major version changes, with no fixed batch update frequency. Daily documents include test authorization letters, penetration test reports, vulnerability reproduction records, and rectification suggestions. Core fields include vulnerability ID, risk level, reproduction steps, impact scope, and repair solutions. The field structure of each document is adjusted slightly based on project requirements.

## Constraints on HTTP interfaces and external systems
Data sources are scattered, requiring integration with multiple external systems such as scanners and vulnerability databases. HTTP interfaces must support parallel calls across multiple data sources and field aggregation. Data is isolated per project, so interface calls must bind project identifiers to avoid cross-project data confusion, and support pulling corresponding test documents per project. Business document structures are flexible, so interface responses must adapt to field differences across projects, requiring flexible response data extraction configuration. Some processes such as vulnerability verification take a long time, so interfaces must support long timeout configurations to cover normal response cycles.

## How to set configurations
These configurations are based on FastGPT v4.17.0’s HTTP module and external system integration logic.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${token}` | Complies with authentication standards for most penetration testing service interfaces |
| `variables` | `{"project_id": "{{projectId}}", "report_id": "{{reportId}}"}` | Binds test data per project to avoid cross-project data confusion |
| `responseData` | Extract the data array under the root node | Adapts to the response formats of most penetration testing interfaces, enabling quick access to core business data |
| Request timeout | 300-600 seconds | Covers normal response cycles for time-consuming processes such as vulnerability verification and report generation |
| Retry count | 2 times | Balances call success rate and resource consumption during network fluctuations |
| Response field validation | Validate that vulnerability_id and risk_level fields are included | Ensures returned data contains core required business information |

## Three common mistakes
- Symptom: The HTTP module call returns an empty result, but the request works normally in Postman. Cause: The `Authorization` parameter is not configured correctly, or the authentication format in the request header does not meet interface requirements.
- Symptom: Images in penetration test reports cannot be displayed normally. Cause: The file URL field is not extracted correctly via `responseData`, or the variable binding logic is not associated with the corresponding resource path.
- Symptom: Associated databases return garbled Chinese characters. Cause: The character set is not specified as utf8mb4 in the database connection configuration, or the interface encoding does not align with the database encoding.

## How to confirm configurations are correct
- Call the test interface and check if the returned `responseData` includes core business fields such as vulnerability ID and risk level.
- Configure `variables` to bind preset project variables, initiate a call, and check the request log to confirm that the project identifier and report identifier are correctly included in the incoming parameters.
- Simulate an authentication failure scenario and check if the corresponding error prompt is triggered, verifying that the authentication configuration takes effect.
- Initiate a long-duration test request and confirm that the call is not terminated early before the preset timeout period, verifying that the timeout configuration is reasonable.
