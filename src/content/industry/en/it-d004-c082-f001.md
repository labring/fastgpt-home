# Customer Technical Support and Pre-sales Q&A for Channel Attribution and Lead Distribution: HTTP Interfaces and External Systems

## What the data for this category looks like
Data for this category is typically synced from advertising platforms, CRM systems, attribution SDKs, and form systems. Associated daily documents include attribution rules, lead distribution tables, channel reports, and exception checklists. Data update cycles are mostly daily or weekly. Core fields include channel identifiers, lead IDs, conversion timestamps, sales owners, and others, with units typically being counts, currency amounts, and second-level timestamps. Primary processing roles include growth operations, sales operations, and data analysts. Core work focuses on channel parameter verification, duplicate lead deduplication, and sales ownership confirmation.

## Constraints Imposed by These Characteristics on HTTP Interfaces and External Systems
Data sources for this category are scattered, and their associated logic is complex. HTTP interfaces must support authentication adaptation for multiple external platforms, while also being compatible with field formats from different systems. Data update cycles are mostly daily or weekly, so interface call frequency must match this rhythm to avoid exceeding platform call limits. There are many core fields with strong associations, so interfaces must support pulling data by specified fields and configuring deduplication. Daily documents and interface fields must use consistent naming to lower configuration barriers for non-development personnel. Interface responses must include clear error identifiers and troubleshooting fields to quickly locate issues such as distorted channel ROI and sales ownership disputes.

## How to Configure Settings
The following configurations are based on FastGPT v4.17.0. This version retains the openAPI module capabilities, supports external system integration for channel attribution and lead distribution via HTTP interfaces, and adapts to functional differences across versions.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {custom secret}` | Complies with general HTTP interface authentication specifications, and adapts to authentication requirements of external systems such as advertising platforms and CRM |
| `variables` | `{"target_channels": ["Channel1","Channel2"], "deduplicate": true, "update_cycle": "Daily"}` | Matches daily attribution rules and channel report filtering logic, narrows data pull scope and enables duplicate lead deduplication |
| `responseData` | `["channel_id", "lead_id", "sales_owner", "convert_timestamp"]` | Only pulls core business fields to reduce data transfer volume, and aligns with the field structure of lead distribution tables |
| Interface call frequency | No more than 1200 times per day | Matches daily data update rhythm to avoid exceeding external platform call limits |
| Retry threshold | Pause for 180 seconds after 3 consecutive failures | Addresses temporary external system fluctuations, and reduces the probability of generating exception checklists |

## Three Common Configuration Errors
- Symptom: The `responseData` field in the interface response is empty. Cause: Core business fields are not specified in the configuration, so the interface only returns default full data and cannot match the field requirements of lead distribution tables.
- Symptom: The interface call triggers a 403 error. Cause: The `Authorization` parameter format is incorrect, and the Bearer token specification is not followed, so external system authentication fails.
- Symptom: Channel ROI data is distorted. Cause: The deduplication parameter in `variables` is not configured, so duplicate leads are counted multiple times in reports, triggering sales ownership disputes.

## How to Verify a Successful Configuration
- Call the test interface, and verify whether the returned `responseData` field includes the business fields specified in the configuration.
- Compare interface response data with local channel report field formats to confirm consistent naming and units.
- Simulate a single abnormal call, and verify whether the returned error code and prompt information are clear for troubleshooting.
- Review external system call logs to confirm interface frequency does not exceed preset limits.
