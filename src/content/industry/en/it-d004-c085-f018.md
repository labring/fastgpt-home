# Customer Technical Support and Pre-Sales Q&A for Game Server Development and Operations: Reranking and Hybrid Retrieval

## What This Category of Data Looks Like
Daily data for game server development and operations includes multi-source heterogeneous content, sourced from game operation logs, online player count monitoring data, player databases, and player support tickets. Daily maintenance documents include server architecture descriptions, server launch plans, server merging plans, and fault reports, updated daily or before and after major game events. Data fields include server IP addresses, process IDs, peak online users, server merging verification latency, and more. The dataset includes both structured monitoring metrics and unstructured log text and ticket descriptions.

## Constraints on Reranking and Hybrid Retrieval
Multi-source heterogeneous data requires hybrid retrieval to support vector mapping rules for both structured monitoring metrics and unstructured documents. This prevents key information from being missed by single-mode retrieval. Frequently updated real-time monitoring data requires controlled latency in the retrieval pipeline. The reranking step must quickly filter low-relevance content to maintain timeliness of pre-sales and operations Q&A. Variations across multiple scenario documents require adjusting retrieval weights based on business scenario. For example, pre-sales inquiries prioritize matching server launch and merging plans, while fault troubleshooting prioritizes associating fault reports. Non-standard ticket data formats require hybrid retrieval to support semantic matching across different fields. The reranking step must prioritize entries with high keyword relevance.

## Three Common Misconfigurations
- Reranking-related prompt fields fail to display correctly in conversation details. Cause: The reranking toggle is not enabled properly, or reranking parameters in the configuration file did not load successfully.
- Retrieval returns only a single entry with the highest similarity score. Cause: The single retrieval limit range was not adjusted. The default configuration restricts the number of returned entries, which does not fit recall requirements for multi-source data.
- Reranking models cannot be selected or switched. Cause: Multi-model switching functionality is not enabled in the configuration, or the optional reranking model list is not configured.

## How to Confirm Successful Configuration
- Access the FastGPT configuration panel to confirm the reranking toggle is enabled.
- Submit a simulated operations inquiry, such as a query about server launch capacity estimation, to verify the number of retrieval results matches the single retrieval limit configuration.
- Call the FastGPT retrieval log interface to confirm reranking model call records exist and return normal status codes.
- Test different inquiry scenarios, such as server merging data verification and fault troubleshooting, to confirm retrieval results prioritize documents matching the corresponding scenario.
