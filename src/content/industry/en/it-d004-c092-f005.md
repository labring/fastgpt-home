# Customer Technical Support and Pre-sales Q&A for On-site Deployment: Multi-turn Dialogue and Prompt Words

## What data looks like for this category
Business data for on-site deployment mainly originates from customer computer room environments, equipment lists, software packages, and network topologies. Update frequency is once per order or per stage. Daily supporting documents include deployment manuals, installation records, configuration lists, and on-site check-in forms. Data fields include equipment model, software version, network port, installation duration, and others. Common units are units, GB, and minutes. Data is only associated with the current on-site implementation work order, not reused across projects, and only serves the on-site installation, configuration, and troubleshooting work for that order.

## Constraints on Multi-turn Dialogue and Prompt Engineering
On-site deployment data is updated per order and only associated with the current work order. This requires multi-turn dialogue to bind `chatId` to the current work order ID to avoid cross-order context confusion. Document structures are fixed but fields change dynamically based on on-site environments. Prompt words must call `variables` to pass real-time data such as the current work order’s configuration list and installation records, and cannot use generic templates. On-site environments change dynamically, so `messages` must append current troubleshooting questions and responses by conversation turn, and must not truncate historical conversation content, otherwise key on-site troubleshooting details will be missed. Data update frequency is once per order or per stage, so dialogue context must update with the work order stage, and expired configuration information must not be retained.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Unique string identifier of the current on-site deployment work order | Binds single work order context to avoid cross-session data confusion |
| `messages` | Append the most recent 8-12 conversation turns and no more than 1000 characters of deployment document fragments for the current work order | Associates exclusive on-site deployment data to ensure responses match the current scenario |
| `variables` | Pass no more than 5 structured fields of equipment lists, network topologies, and installation records | Provides real-time on-site environment data for prompt words |
| Output format filtering | Disable Markdown syntax | Adapts to the concise communication needs of on-site deployment |
| Maximum context turns | First 10 conversation turns | Matches the typical communication cycle of on-site deployment orders to avoid context overload |

## Three Common Misconfigurations
- `Unexpected end of JSON input` error occurs. The cause is failure to splice the `messages` parameter by session, resulting in incomplete JSON formatting.
- Conversation results only pop up in the sidebar and are not displayed directly in the main dialog box. The cause is failure to bind `chatId` to the current implementation work order, so the system creates a new session by default.
- A new conversation is automatically started for each dialogue, and communication cannot be continued. The cause is failure to reuse `chatId`, with a new session ID generated for each request.

## How to Verify Correct Configuration
- Check that `chatId` matches the unique identifier of the current on-site deployment work order.
- Verify that the `messages` list includes deployment manual and installation record fragments for the current work order.
- Confirm that the same `chatId` is reused during the dialogue process, with no new session IDs generated.
- Ensure that the output content does not include Markdown syntax formatting.
