# Customer Technical Support and Pre-sales Q&A for User Growth & Retention Operations: Sharing and Embedding

## What the Data for This Category Looks Like
Daily documents for this category include growth experiment plans, user segmentation tables, outreach copy, and retention analysis reports. Data sources include user behavior logs, push systems, experiment platforms, and CRM systems. Update frequency is typically daily or weekly. Most data fields cover user segmentation tags, outreach conversion rates, and experiment attribution metrics. Units include person-times, percentages, cycle days, and similar units. The core focus is on operational data tied to in-site user lifecycles. The overall data structure is dynamically adjusted as operational experiments advance.

## What Constraints These Characteristics Impose on the "Sharing and Embedding" Link
Data sources for this category are scattered, and update cycles are fixed. Support is required for associating external systems with operational data updated on a daily or weekly basis. This association logic must be implemented separately by external business systems. Daily documents mostly include sensitive content such as segmentation tables and experiment plans. Embedding requires support for precise fragment selection to avoid full information leaks. Error consequences directly affect user retention and channel budgets, so sharing links must have access permissions configured. Operation audit must be implemented separately by external business systems. The core focus is on in-site user lifecycles, so embedded applications must adapt to in-site user identity association logic. This logic must be implemented by external business systems connecting to FastGPT's third-party identity verification capabilities.

## Configuration Settings
The following configurations are designed for FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Sharing entry `shareId` | Copy the full sharing link generated by the system; do not manually replace the identifier | Identifies the sharing entry; user growth and retention operation records and data permissions still need to be handled by external systems |
| Sharing link validity period | Test starting point: 7 days; adjust based on actual testing of user growth and retention operation collaboration cycles and revocation requirements | Verifies availability within the validity period and access behavior after expiration; this value is not an official default or industry statistic |
| QPM | Test starting point: 20 requests per user per minute; adjust based on actual load | Limits the access frequency of a single user; verification is performed combined with request logs and actual load |

| Conversation record verification | Test example: Prepare 10 user growth and retention operation Q&A samples, check them in the same browser and another device respectively | Anonymous records rely on browser local identity; retention cannot be guaranteed across devices or after cache clearing |

## Three Common Mistakes
- Sharing entries related to user growth and retention operations fail to open. The full system-generated link and its validity period are first verified, then browser request statuses are cross-checked. Manual replacement of `shareId` is not allowed.
- The visible scope of user growth and retention operation data does not match expectations. Third-party identity verification results, workflow request parameters, and external system data permissions are cross-checked respectively. Business authorization is not provided by the sharing entry identifier itself.
- The same user growth and retention operation Q&A is not visible on another device. For anonymous scenarios, device, browser, and local identity statuses are first checked. Record retention cannot be guaranteed across devices or after cache clearing; service abnormalities are not judged solely based on this phenomenon.

## How to Confirm Configuration is Complete
- A sharing link is generated, the system-generated `shareId` parameter is extracted, and the sharing target is confirmed to match the correct application configuration.
- After third-party identity verification integration is configured, the sharing link is accessed using different browsers or devices, whether the user identity is associated with the in-site unified identifier is checked, and configuration effectiveness is verified.
- After referenced fragment filtering rules are configured, the sharing link is accessed, and it is confirmed that only specified knowledge base fragments are displayed, with no full content leaks occurring.
- The sharing link is embedded into an in-site page, the width of the embedded container is adjusted, and content display is confirmed to have no misalignment or overflow.

The values provided are common starting points and should be measured against the reader's own samples.
