# Customer Technical Support and Pre-sales Q&A for User Acceptance Testing Support: HTTP Interfaces and External Systems

## What the data for this category looks like
Data for this category comes from requirement specification documents, test environment configurations, customer business sample data, and defect management systems. The update cycle is once per delivery phase or per version iteration. Daily produced documents include UAT test cases, acceptance issue tickets, acceptance reports, and signed confirmation forms. Document fields cover business scenarios, test steps, issue descriptions, reproduction conditions, and acceptance conclusions. There are no uniform mandatory units, and fields are flexibly adjusted based on the customer's actual business scenarios.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Decentralized data sources mean interfaces must support multi-source data pulling, adapting to format differences across different data sources such as requirement specifications and test environment configurations. Update frequency follows delivery phase iterations, so interfaces must support parameter adjustment logic for version changes. The transfer of multiple types of documents requires interfaces to support variable binding for custom fields, adapting to different document structures such as UAT test cases and acceptance issue tickets. Confirmation of acceptance conclusions involves customer permission verification, so interfaces must configure role permission rules via the `Authorization` parameter. Interface failures directly pose a risk of acceptance delays, so failure handling logic must be pre-configured.

## How to set the configuration
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Carry a Bearer Token for the customer role, set validity period to 7200 seconds | Adapt to permission verification requirements during the acceptance phase, avoid cross-phase permission leaks |
| `variables` | Bind fields from customer business samples, value range is 10–50 custom variables | Meet data replacement requirements for multi-scenario testing in UAT test cases |
| `responseData` | Only return core fields of acceptance issue tickets, limit return count to the first 20 entries | Reduce invalid data transmission, adapt to lightweight data synchronization needs during the acceptance phase |
| Timeout Threshold | Calibrated via actual testing, range is 300–600 seconds | Adapt to interface response durations for complex test scenarios, avoid interrupting the acceptance process due to timeouts |
| Retry Configuration | Retry 2 times after failure, interval of 120 seconds | Address occasional network fluctuations in test environments, ensure stability of acceptance data synchronization |

## Three common mistakes
- Calling the `/api/core/dataset/colle` interface to upload a CSV file returns garbled text, while the original file previews normally locally. The cause is failing to specify `Content-Type` as `text/csv; charset=utf-8` in the interface request header, leading to encoding parsing errors.
- The deployed LLM cannot trigger the function call function, and the interface returns undefined tool call parameters. The cause is failing to bind tool call trigger rules via the `variables` configuration, leading the interface to fail to recognize custom tool configurations.
- Interface calls time out, interrupting the acceptance process. The cause is failing to set a reasonable timeout threshold or configure a retry mechanism, leading to request failures due to occasional fluctuations in the test environment.

## How to confirm the configuration is complete
- Call the specified interface, check that the returned `responseData` only includes preset core fields with no redundant data.
- Simulate requests from different customer roles, verify that the permission verification rules for the `Authorization` parameter take effect, and roles without permissions cannot access acceptance data.
- Pass a custom `variables` parameter, check whether the interface can correctly bind business variables in test cases.
- Simulate network fluctuation scenarios, verify whether the interface retry mechanism triggers, and whether failed requests complete synchronization after retries.

The values given are common starting points and should be measured against the reader's own samples.
