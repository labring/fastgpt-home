# Customer Technical Support and Pre-Sales Q&A for User Acceptance Testing: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Data for this category originates from requirement specification documents, test environment configurations, customer business sample materials, and defect management systems. Update frequency follows each delivery phase or version iteration. Daily associated documents include UAT test cases, acceptance issue tickets, acceptance reports, and signed confirmation forms. Data fields include test case steps, problem reproduction paths, acceptance conclusions, and associated business scenarios. Common units are step numbers, timestamps, and business scenario names.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
The phase-based update of UAT test cases requires that multi-turn dialogue contexts adapt to phase-by-phase business scenario switches, and avoid interference from redundant cross-phase information. The structured fields of acceptance issue tickets require that prompts accurately match test case steps and defect fields, reducing extraction of non-associated information. The non-standardized nature of customer business sample materials requires that dialogue components support dynamic loading of `variables` to adapt to different customer scenarios. The signed confirmation link for acceptance conclusions requires that the dialogue process retains a complete `messages` chain to facilitate traceability of acceptance evidence. The high data update frequency requires that dialogue configurations support quick switching of current phase business data, avoiding retention of old data.

## How to set the configurations
The following configurations are based on FastGPT v4.17.0.
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `messages` | Retain the last 20 rounds of dialogue context, clear after each phase delivery | Adapt to the phase-based update characteristic of UAT test cases, avoid interference from redundant cross-phase information |
| `variables` | Bind the current phase's UAT test case ID and acceptance issue ticket number | Match structured document fields, accurately associate business scenario data |
| `chatId` | Generate a unique identifier per delivery phase | Distinguish acceptance sessions for different customers, avoid data confusion |
| Maximum context length | 8000–12000 characters | Cover the complete content of single-phase UAT test cases and acceptance issue tickets |
| Session archiving cycle | Archive per delivery project, retain for 30 days | Match the archiving requirements of acceptance reports, facilitate subsequent traceability |

## Three common misconfigurations
- When launching dialogue related to acceptance testing, uploaded UAT test case files cannot be retrieved. The cause is failure to bind the file storage identifier to the `variables` session variable, resulting in the dialogue context being unable to associate the corresponding storage resource.
- Uncaught exceptions are triggered when calling AI dialogue components in a private deployment environment. The cause is failure to correctly configure the session cache path for `chatId`, resulting in failure to read session data.
- When initiating a dialogue via code API calls, the returned results do not associate knowledge base matching content. The cause is failure to add customer business sample context associated with the knowledge base to `messages`, resulting in the prompt not triggering the retrieval logic.

## How to confirm configurations are set correctly
- Launch a dialogue to reproduce an acceptance issue, check whether the returned results associate the current phase's UAT test case fields.
- View the session log corresponding to `chatId`, confirm that the `messages` context only retains dialogue content from the current phase.
- Trigger the session cache in the private deployment environment, check whether the bound `variables` configuration data can be read normally.
- Upload a test UAT test case file, confirm that the file content can be retrieved during the dialogue process.

The values provided are common starting points and should be measured against the reader's own samples.
