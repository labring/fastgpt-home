# Customer Technical Support and Pre-sales Q&A for Monitoring Alert Configuration: Sharing and Embedding

## What the Data for This Category Looks Like
This category's data originates from Prometheus, Zabbix, cloud monitoring services, application logging systems, and CMDB platforms. Data update frequency is daily or after each alert rule change. Daily associated documents include monitoring metric lists, alert rule documentation, on-duty manuals, and alert change records. Data fields include metric names, threshold parameters, trigger delay duration, alert levels, notification link configurations, and more. Some metrics include standard units such as bps, %, and milliseconds.

## What Constraints These Characteristics Impose on the Sharing and Embedding Workflow
Multi-source data access requires external embedding carriers to explicitly specify the allowed data source range, to prevent cross-permission data leaks. The FastGPT sharing entrance does not have built-in data source permission control capabilities.
Differences in data update frequencies require external embedding carriers to configure cache durations to match alert rule change rhythms, to avoid displaying outdated threshold configurations. The FastGPT sharing entrance does not have built-in cache control capabilities.
The diversity of document structures requires external systems to bind shared content to specific alert rule IDs or metric list entries. The FastGPT sharing entrance does not support built-in business data association and binding capabilities.
Alert configurations contain sensitive notification links and on-duty arrangements. External embedding carriers must filter non-authorized visible fields to prevent internal information leaks. The FastGPT sharing entrance does not have built-in field filtering capabilities.

## How to Configure Settings
The following configuration items must be configured jointly with the FastGPT sharing entrance and external monitoring alert business systems:

| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| Sharing Entrance `shareId` | Copy the full sharing link generated by the system, do not manually replace the identifier | Identifies the sharing entrance; monitoring alert configuration business records and data permissions must still be handled by external systems |
| Sharing Link Validity Period | Test starting point: 7 days; adjust based on actual monitoring alert configuration collaboration cycles and revocation requirements | Verify availability within the valid period and access behavior after expiration; this value is not an official default or industry statistic |
| QPM | Test starting point: 20 requests per user per minute; adjust based on actual load | Limits the access frequency of a single user; must be verified combined with request logs and actual load |
| Identity Verification | When identity permission requirements exist, first verify commercial version capabilities and the uid returned by third-party identity services | Holding a sharing link does not equate to having business data permissions; third-party identity and data scope must be verified separately |
| Referenced Content Display | Select display configurations for referenced fragments, full text, and original text based on the sensitivity of monitoring alert configuration materials | Check displayed content within authorized data ranges; hidden interfaces cannot replace data permission controls |
| Conversation Record Verification | Test example: Prepare 10 monitoring alert configuration Q&A samples, check them in the same browser and another device respectively | Anonymous records rely on browser local identity; retention cannot be guaranteed across devices or after cache clearance |

## Three Common Misconfigurations
- The sharing entrance for monitoring alert configuration fails to open. First verify the full system-generated link and its validity period, then cross-check browser request statuses. Do not manually replace `shareId`.
- The visible scope of monitoring alert configuration data does not match expected values. Cross-check third-party identity verification results, workflow request parameters, and external system data permissions. The sharing entrance identifier itself does not provide business authorization.
- The same monitoring alert configuration Q&A cannot be viewed on another device. In anonymous scenarios, first verify device, browser, and local identity statuses. Record retention cannot be guaranteed across devices or after cache clearance. Do not use this phenomenon alone to judge service abnormalities.

## How to Verify Successful Configuration
- Open the embedded page, check if the displayed alert rule names and threshold parameters match the configurations from the external source.
- Manually modify the threshold of the source alert rule, wait for the cache duration of the external embedding carrier to expire, then refresh the embedded page. Confirm that the updated parameters are displayed.
- Check the network requests of the embedded page, confirm that the `shareId` parameter is correctly carried in the request, with no missing or incorrect values.
- Verify that unauthorized domains or unauthorized users cannot access the embedded page, confirm that access permission configurations have taken effect.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
