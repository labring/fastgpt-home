# Customer Technical Support and Pre-sales Q&A for Monitoring Alert Configuration: Knowledge Base Retrieval and Recall

## What the Data for This Category Looks Like
This category of data mainly comes from monitoring tools such as Prometheus, Zabbix, cloud monitoring platforms, application logs, and CMDB systems. Daily documents include monitoring indicator lists, alert rules, on-duty manuals, and alert change records. Fields cover indicator names, threshold ranges, alert levels, notification targets, trigger conditions, and more. Some fields have units such as percentage, millisecond, and trigger count. Data updates occur daily or in real time when alert rules are changed. The length of individual documents varies widely, from short single-line alert rule entries to complete dozens of pages of on-duty manual collections.

## Constraints Imposed on Knowledge Base Retrieval and Recall
The data sources for monitoring alert configurations are scattered, with significant format differences. The retrieval link must support field formats from multiple data sources. This prevents recall result deviations caused by field mismatches.
Document lengths vary widely, from single-line alert rules to full on-duty manuals. The system must adapt chunking and recall logic for different text lengths.
Data updates happen frequently. The retrieval link must support real-time or scheduled synchronization of the latest alert change records. This ensures returned content matches the currently active configuration.
Some fields have clear units. Retrieval must match query intentions related to these units. Semantic mismatches will occur otherwise.
Alert configuration association chains are complex. Recall results must include complete associated information such as notification targets and threshold parameters. This avoids returning fragmented content.

## How to Configure the Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value Range | Rationale |
| ---|---|--- |
| `similarity` | 0.75–0.85 | Matches the precision requirements for alert configurations. A threshold that is too low will introduce irrelevant alert rules. A threshold that is too high will miss valid configuration content. Adjust based on actual testing calibration |
| `limit` | Top 8–12 entries | The number of monitoring alert configuration entries is usually large. Too many single recalls will exceed the context window. Too few will fail to cover the complete alert chain configuration |
| `searchMode` | semantic | Addresses the semantic matching requirements for alert rules. Semantic retrieval can recognize associated intentions of keywords such as thresholds and indicator names. It performs better than pure keyword matching |
| `usingReRank` | Enabled | Alert configuration fields have strong correlations. Reranking filters semantically similar but irrelevant entries, improving result relevance |
| `datasetSearchUsingExtensionQuery` | Enabled | Extends user pre-sales or technical support queries. For example, it expands "how to set CPU alert thresholds" into retrieval terms matching corresponding indicators and threshold configurations |
| `collectionIds` | Bind the collection ID of the corresponding monitoring knowledge base | Restrict the retrieval scope to knowledge bases related to monitoring alert configurations. This prevents mixing documents from other categories |

## Three Common Configuration Mistakes
- Retrieval results do not match knowledge base content. This manifests as returned alert threshold configurations inconsistent with actual entered content. The cause is an unreasonable `similarity` threshold setting, where a too low value introduces irrelevant documents, or `usingReRank` is not enabled, causing semantically similar but irrelevant entries to be recalled first.
- The application queries the knowledge base and returns no relevant content. This manifests as empty results or prompts indicating no matching content. The cause is that `collectionIds` is not configured to limit the retrieval scope, leading the retrieval range to cover non-monitoring alert knowledge bases, or the `limit` setting is too low to recall valid entries.
- Long document chunking does not meet requirements. This manifests as alert rules being incorrectly split, causing semantic breaks. The cause is that the chunking logic is not adjusted for the document structure of monitoring alert configurations, and the association between alert entries and context is not matched.

## How to Verify a Successful Configuration
- Manually enter a known monitoring alert configuration keyword, check whether the retrieval result includes the core content of the corresponding document, such as indicator names and threshold parameters.
- Check the knowledge base synchronization logs, confirm that monitoring alert-related documents have completed the latest incremental or full synchronization, ensuring data timeliness.
- View the return parameters of the retrieval interface, confirm that the values of configuration items such as `similarity` and `limit` match the preset values.
- Simulate pre-sales or technical support scenario queries, verify whether the returned results include core configuration information such as alert thresholds and notification chains.

The values provided are common starting points and should be measured against the reader's own samples.
