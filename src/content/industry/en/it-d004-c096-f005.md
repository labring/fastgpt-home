# Customer Technical Support and Pre-sales Q&A for Community Report Handling: Multi-turn Dialogue and Prompts

## What data for this category looks like
Business data for community report handling comes from report systems, content details, user historical records, and review rules, with an update frequency of daily or real-time. Commonly used documents include report work orders, processing records, appeal forms, and user notification templates. Fields include report content ID, user identifier, violation type, disposal status, and more. Typical business entities are community operations teams, review teams, and customer service teams. Data is stored independently per individual report work order, with no default batch aggregation format.

## What constraints these characteristics impose on the "multi-turn dialogue and prompts" link
The independent storage of individual report work orders requires multi-turn dialogue to bind to a unique identifier, preventing cross-work-order context confusion. Real-time updated review rules and user historical records require pulling the latest data for each session call. Structured work order documents require prompts to clearly specify field extraction rules, ensuring processing results comply with business specifications. The single-order processing business model requires multi-turn dialogue to guide users to supplement complete report evidence and appeal content, covering full-process interaction.

## How to set up the configuration
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind the unique identifier of the current report work order | Ensure multi-turn dialogue only associates with a single report work order, avoiding cross-work-order context interference |
| `variables` | Pass report content ID and user historical appeal records | Allow prompts to access category-specific business data, improving the accuracy of report validity judgment |
| `messages` | Retain the last 10 session contents | Cover the full process of report handling interaction, including user appeal, review feedback, and other links |
| Maximum context length | 8000 token, calibrated via actual testing | Adapt to the total length of multi-segment text, screenshot descriptions, and other content included in report work orders |
| Question optimization switch | Enabled | Automatically convert vague user inquiries into standardized review rule queries, adapting to the community report business scenario |
| Single session timeout | 600 seconds | Match the conventional response cycle for review teams to handle individual report work orders, preventing premature session termination |

## Three common mistakes
- Phenomenon: File upload can be enabled in the front-end interface, but uploaded file parameters cannot be carried when the dialogue interface is called. Cause: No field mapping for file upload is configured in `variables`, causing the prompt to not recognize the file transfer logic on the interface side.
- Phenomenon: The output content of the front-end dialogue page mixes results from multiple modules, and a dedicated module cannot be specified to display report processing information. Cause: No output module filtering rules are specified in the configuration, causing the prompt to not split output content according to the business scenario.
- Phenomenon: The prompt cannot correctly distinguish the input of System and Human roles, leading to deviations in report validity judgment. Cause: No role input permissions are allocated according to the business scenario, and fixed review rules are mistakenly placed in the Human role module.

## How to confirm the configuration is correct
- A session simulating a report work order is initiated, and `chatId` is checked against the work order ID to ensure no cross-work-order context occurs.
- The interface is called with the report content ID passed, and the prompt is checked to correctly extract work order fields and associate with review rules.
- Multi-turn interaction is tested, and the session context is confirmed to retain the last 10 interactions with no redundant information.
- A test file is uploaded, and the interface is checked to correctly carry the file parameters and pass them to the prompt for processing.

The values provided are common starting points and should be measured against the reader's own samples.
