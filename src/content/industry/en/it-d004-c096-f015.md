# Customer Technical Support and Pre-sales Q&A for Community Report Handling: Knowledge Base Retrieval and Recall

## What the data for this category looks like
The core data for this category comes from community report systems, details pages of content awaiting review, users’ historical report records, and official audit rule bases. Daily generated documents include report tickets, report processing records, user appeal forms, and violation disposal notification templates. Data updates occur in real time or via daily batch jobs. Each data entry includes fields such as reporting user ID, reported content ID, report type, audit status, and disposal result. The basic processing unit is a single ticket, and there is no unified fixed unit.

## What constraints these characteristics impose on the knowledge base retrieval and recall link
The real-time requirements of community report handling require knowledge base retrieval to support low-latency recall, to avoid impacting ticket processing efficiency. Data sources are scattered, and the size of individual content entries varies widely. A retrieval mode adapted to multi-source data must be configured. Single report ticket processing requires accurate matching of audit rules and historical disposal cases. As such, retrieval results must strictly filter low-relevance content, and support calling dedicated knowledge base collections based on ticket scenarios. Real-time updated audit rules require the retrieval link to synchronize the latest rule data, to avoid using expired rules for judgment.

## How to set the configurations
These configurations are formulated based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Filter low-relevance audit rules and historical tickets to avoid invalid recall interfering with report judgment |
| `limit` | Top 10 entries | Control the number of single recall results, adapting to the fast review scenario of single report tickets |
| `searchMode` | Semantic Retrieval | Match the semantic association between report content and audit rules, covering scenarios that keyword matching cannot cover |
| `usingReRank` | Enabled | Perform secondary sorting on initial recall results, improving the display priority of highly relevant rules and cases |
| `datasetSearchUsingExtensionQuery` | Enabled | Automatically generate extended query terms based on user report content, covering more potentially relevant audit rules |
| `collectionIds` | Specify dedicated collection IDs by report type | Ensure retrieval only calls the knowledge base corresponding to the report scenario, avoiding interference from cross-type data |

## Three common mistakes
- An upload timeout is displayed on the interface, but the upload actually succeeds, and the corresponding knowledge base file cannot be retrieved later. This issue can be resolved by adjusting the upload timeout parameter in FastGPT v4.17.0. The cause is that the timeout parameter adapted to large document uploads is not configured, or the breakpoint resume upload logic is not enabled.
- The number of retrieval results does not meet expectations, with only a small number of low-relevance content returned. The cause is that the `similarity` threshold is set too high, filtering out relevant rules that meet business requirements, corresponding to the relevance restriction issue mentioned by community users.
- Cross-session retrieval does not switch the knowledge base collection, causing subsequent report tickets to call incorrect historical data. The cause is that dedicated `collectionIds` parameters are not configured for different report types, and the knowledge base is not dynamically switched based on ticket scenarios.

## How to confirm the configuration is correct
- Upload a single 100MB audit rule document, wait for the upload to complete, enter the report content keyword on the knowledge base retrieval test page, and verify that the corresponding rule entries can be recalled.
- Adjust the `similarity` threshold to 0.7, retrieve the test report ticket, and confirm that the number of returned results matches the preset `limit` value.
- Switch between different `collectionIds` collections, enter the report content of the corresponding type, and verify that only knowledge base entries within that collection are recalled.
- After enabling `usingReRank`, compare the order of initial recall results and rearranged results, and confirm that highly relevant content is displayed first.

The values provided are common starting points and should be measured against the reader's own samples.
