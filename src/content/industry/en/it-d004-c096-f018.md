# Customer Technical Support and Pre-sales Q&A for Community Report Handling: Reranking and Hybrid Retrieval

## What data for this category looks like
Data for this category primarily comes from community reporting systems, pending review content details, user historical reporting records, and official review rules. Data update frequencies include daily updates and real-time updates. Daily processing relies on documents including reporting tickets, disposal progress records, user appeal forms, and standardized user notification templates. Data fields include report ID, content link, report type, submitting user information, review status, and more. There is no unified fixed unit field. The core content revolves around the full-process information of individual report events.

## What constraints these characteristics impose on the reranking and hybrid retrieval link
Individual report events have small information volumes but strong relevance. They require quick matching of corresponding review rules and historical disposal cases. Therefore, the retrieval scope must be limited to the current community’s report-related dataset to avoid interference from irrelevant content. Real-time updated report data requires the retrieval pipeline to support low-latency responses. Multi-source recall in hybrid retrieval must adapt to the timeliness requirements of short-cycle data synchronization. Structured fields of reporting tickets must be accurately bound to retrieval parameters to ensure recalled content highly matches the current report’s type and scenario. Excessive recall of non-core information should be avoided to prevent lengthened processing time.

## How to set configurations
These configurations are based on FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Rerank toggle | Enabled | Community report handling requires precise matching of violation determination rules and historical disposal cases. Reranking filters low-correlation recall results to improve judgment efficiency |
| Similarity threshold | 0.72–0.85 | Filter historical tickets and review rules irrelevant to the current report scenario, ensuring the semantic matching degree of recalled content meets business requirements |
| Single recall limit | Top 10 entries | The volume of associated information for individual reports is limited. Excessive recall results lengthen processing time, adapting to the rapid response requirements of community operations |
| Retrieval mode | Hybrid retrieval | Need to recall both structured review rules and unstructured historical disposal records, covering all-dimensional reference bases for report handling |
| Retrieval timeout | 8–10 seconds | Adapt to the real-time requirements of community report handling, avoiding disrupting the processing rhythm of operation personnel due to excessive waiting time |
| Rerank result truncation | Top 5 entries | Focus on the most relevant disposal references, reducing the information screening cost for operation personnel |

## Three common mistakes
- Symptom: A `rerank error fastgpt | { message: { detail: '`-type error appears after enabling the rerank function. Cause: The API call path or permission for the rerank model is not configured correctly, or the locally deployed rerank model has not completed initialization loading.
- Symptom: The response time of hybrid retrieval exceeds 10 seconds, exceeding the reasonable time range for single report handling. Cause: A reasonable single recall limit and similarity threshold are not set, resulting in recall of excessive irrelevant content, or the timeout parameter for rerank model calls is configured too loosely.
- Symptom: GPU video memory usage quickly grows to 6–7G after rerank model calls, with simultaneous occupancy across multiple GPUs. Cause: The length of rerank text called per single request is not limited, or a load balancing strategy for multiple GPUs is not configured, leading to excessive resource occupation.

## How to confirm configurations are complete
- Check the running logs of the retrieval pipeline to confirm that the rerank model’s call requests and responses are normal, with no error messages.
- Simulate submitting a reporting ticket, and verify that the number and relevance of recalled results after hybrid retrieval and reranking meet business expectations.
- Test retrieval requests for different report types, confirming that response times meet the preset real-time requirements.
- Check the GPU resource monitoring panel to confirm that the video memory usage of the rerank model is within a reasonable range, with no abnormal spikes.

The values provided are common starting points and should be measured against the reader's own samples.
