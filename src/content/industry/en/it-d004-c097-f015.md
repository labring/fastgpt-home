# Customer Technical Support and Pre-sales Q&A for Community Events and Developer Relations: Knowledge Base Retrieval and Recall

## What This Category of Data Entails
The data for this category primarily comes from community forums, registration systems, social media, and project roadmaps. Four types of documents are regularly generated: event plans, speaking scripts, registration lists, and event post-mortems. Data updates follow monthly or single-event cycles. Document fields vary across different events. Event plans include fields for topics, speakers, and times. Registration lists include fields for user IDs and contact information. Event post-mortems include fields for feedback scores and participant counts. No unified mandatory format exists for the data. Adjustments must be made to fit the operational needs of individual events.

## Constraints Imposed on Knowledge Base Retrieval and Recall
The characteristics of this category of data impose multiple constraints on the knowledge base retrieval and recall process. Data sources are multi-source and heterogeneous, covering platforms such as community forums and registration systems. Adaptation is required for diverse formats including plain-text speaking scripts, structured registration lists, and forum posts with comments. Mixed-format recall logic must be supported. Update cycles are not fixed. Some event data is generated only once. Temporary knowledge base mounting and on-demand recall triggering must be supported. No unified standard exists for document fields. Key information for documents such as event plans and post-mortems is distributed across different fields. Targeted field weight configuration must be implemented. Event feedback data must be linked to original event documents. Cross-document associated retrieval must be supported to ensure complete information during Q&A.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Similarity threshold | Set `similarity` to 0.68–0.72 | Adapts to scenarios where colloquial questions from community forums mix with formal text from event documents, filters low-relevance redundant results |
| Single search upper limit | Set `limit` to the first 6–8 entries | Balances recalled information volume and large model context length limits, avoids content overload |
| Search mode | Set `searchMode` to hybrid | Combines keyword matching and semantic recall, adapts to multiple data types including event plans, registration lists, and event post-mortems |
| Rerank toggle | Set `usingReRank` to enabled | Performs secondary sorting on initial recall results, filters low-value content such as forum spam posts and invalid registration information |
| Extended query toggle | Set `datasetSearchUsingExtensionQuery` to enabled | Automatically supplements event-related keywords based on user questions, adapts to vague questions about event details during pre-sales Q&A |
| Restrict knowledge base collection | Fill `collectionIds` with the IDs of the corresponding event knowledge base | Limits the retrieval scope, avoids mixing redundant data from other events or projects |

## Three Common Misconfigurations
- Retrieval results return an empty list or only a small number of irrelevant entries. The cause is failure to correctly configure `collectionIds` to restrict the retrieval scope. The entire platform knowledge base is mistakenly included in retrieval, mixing non-event-related redundant data.
- Image links uploaded to the localFile knowledge base show as expired. The cause is failure to configure a permanent storage policy for the community event local file knowledge base. Only temporarily mounted documents are used, and the image expiration rule is not adjusted.
- Retrieval results exceed the preset large model context length limit. The cause is failure to set a reasonable `limit` parameter. Recalling too many documents causes the context length to exceed the large model processing limit, or the rerank toggle is not enabled, leading to low-relevance content occupying excessive context space.

## How to Verify Correct Configuration
- Input common community event-related questions, check if retrieval results include the corresponding event document content. Verify that the similarity threshold and search mode configurations are effective.
- Upload a test image to the localFile knowledge base, check if the image link remains valid long-term. Verify that the permanent storage policy is configured correctly.
- View the number of results returned by retrieval, confirm that it falls within the range set by the single search upper limit. Verify that the `limit` parameter configuration is effective.
- Input vague questions, check if the system automatically supplements relevant keywords. Verify that the extended query toggle is enabled.

The values provided here are common starting points. They should be evaluated against the reader’s own samples.
