# Customer Technical Support and Pre-sales Q&A for On-site Outsourced Operations Maintenance Services: HTTP Interfaces and External Systems

## What the data for this category looks like
Core data for on-site outsourced operations maintenance services typically comes from the customer’s ITSM system, on-site monitoring platform, enterprise asset inventory, and on-site staff duty records. Daily produced documents include on-site daily reports, service desk tickets, inspection reports, and SLA monthly reports. Data updates are mostly daily, with some monthly statistical documents updated monthly.
The core work links of this category include on-site ticket processing, inspection record organization, and SLA statistics and summary, which account for a relatively high proportion of total work time. Data fields mostly include ticket numbers, inspection items, service response duration, on-site staff scheduling information, and device status identifiers, among others.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
The data sources for this category are scattered and include multiple types of content such as tickets and inspection reports. Some documents also include device photos and inspection videos captured on-site. This requires HTTP interfaces to support multi-format data transmission and multi-tenant authentication isolation, to prevent confusion of service data between different customers.
The difference between daily and monthly data update rhythms affects interface call frequency settings. High-frequency calls need to adapt to low-latency responses. Low-frequency batch statistical interfaces require adjusted timeout thresholds.
In addition, single-batch data volume generated during on-site ticket processing and inspection record organization is relatively large. The interface must support batch request processing, and also need to handle relative link conversion to absolute links. This prevents external systems from failing to properly read files uploaded on-site, which would reduce the efficiency of customer technical support and pre-sales Q&A.

## How to set the configurations
The following configurations are formulated based on FastGPT v4.17.0.

| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `Authorization` | Generate a dedicated key per customer tenant; universal keys are prohibited | Data for this category involves sensitive systems such as customer ITSM, and universal keys increase the risk of data leaks |
| `variables` | Pass business identifiers such as on-site ticket numbers and inspection report IDs | Facilitate external systems to associate corresponding service records and match the document field structure of on-site outsourced operations maintenance services |
| `responseData` | Only return core fields such as ticket processing status and file upload results | Reduce invalid data transmission and adapt to the high-frequency call scenario requirements of this category |
| File upload size limit | 100–500 MB, calibrated based on actual testing | Files such as device photos and inspection videos uploaded on-site usually fall within this range |
| Interface timeout period | 600–1200 seconds | Batch SLA statistics and large ticket processing for this category may require a long execution time |
| Maximum number of tickets per single request | Top 200, calibrated based on actual testing | Adapt to the scale of daily batch ticket processing for this category |

## Three common misconfigurations
- Phenomenon: A 403 Forbidden error is returned when calling the knowledge base API, or the interface returns a "no permission to access data" message. Cause: A universal authentication key is used, and a dedicated key is not generated per customer tenant, which does not meet multi-customer data isolation requirements.
- Phenomenon: The external system cannot read uploaded image or video files, and returns "file does not exist" or "path error". Cause: The relative link automatic conversion function is not enabled, and relative links generated on-site cannot be properly parsed by external systems.
- Phenomenon: When processing batch tickets or inspection data, the interface returns a timeout error, and execution time exceeds 1200 seconds. Cause: The interface timeout threshold is set too short, and does not adapt to the time-consuming characteristics of batch data processing for this category.

## How to confirm the configuration is correct
- Initiate a single authentication request, check whether the returned status code is 200 OK, and confirm that the authentication key configuration meets the current tenant’s permission requirements.
- Upload a test photo taken on-site, check whether the external system can normally read the file content, and confirm that the relative link conversion function is active.
- Initiate a batch data request, monitor the interface execution duration, and adjust the timeout threshold to meet the current business’s time-consuming requirements.
- Call the interface to obtain the return result, check whether the returned fields include the core information required by the business, and confirm that the `responseData` configuration meets expectations.
