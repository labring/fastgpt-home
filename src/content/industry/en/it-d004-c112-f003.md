# Customer Technical Support and Pre-sales Q&A for Problem Management and Root Cause Analysis: Sharing and Embedding

This document applies to FastGPT v4.17.0.

## Data for This Use Case

Data for this use case originates from incident timelines, operation logs, monitoring metrics, and code commit records. Update frequency follows either each major incident or monthly. Daily deliverables include RCA reports, incident tickets, post-incident review minutes, and rectification tracking sheets. Document fields include incident occurrence time, root cause type, rectification measures, tracking status, and similar items. Common units include timestamps, event counts, and rectification item counts. This data is maintained by SREs, technical leads, or quality teams.

## Constraints for Sharing and Embedding Workflows

Incident-related data has low update frequency and large per-update content volume. This requires shared embedded data sources to support incremental synchronization or on-demand pulling, to avoid resource usage from repeatedly loading full historical data. Document structures include multiple types of structured and unstructured content. Sharing must preserve the original document hierarchy and field associations, to enable technical support staff to quickly locate root cause-related information. Data sources involve sensitive operation logs and code records. Sharing and embedding must include permission verification configurations to prevent unauthorized access. Rectification tracking sheet status must sync in real time, to avoid embedded content differing from actual operational status.

## Configuration Settings

| Configuration Item | Recommended Setup | Rationale |
| --- | --- | --- |
| Sharing entry `shareId` | Copy the full shared link generated by the system, do not replace the identifier manually | Identifies the sharing entry; business records and data permissions for problem management and root cause analysis must still be handled by external systems |
| Shared link validity period | Test starting point: 7 days; adjust based on actual testing of problem management and root cause analysis collaboration cycles and revocation requirements | Verifies availability within the valid period and access behavior after expiration; this value is not an official default or industry statistic |
| QPM | Test starting point: 20 requests per user per minute; adjust based on actual load | Limits access frequency for individual users; requires validation combined with request logs and actual load |
| Identity verification | When identity permission requirements exist, first verify commercial edition capabilities and the uid returned by third-party identity services | Holding a shared link does not equal having business data permissions; third-party identity and data scope must be verified separately |
| Referenced content display | Select display configurations for referenced fragments, full text, and original text based on the sensitivity of problem management and root cause analysis materials | Validate displayed content within authorized data scope; do not use hidden interfaces as a replacement for data permission controls |
| Conversation record verification | Test example: Prepare 10 question and answer samples for problem management and root cause analysis, and check them on the same browser and another device respectively | Anonymous records rely on browser local identity; retention cannot be guaranteed across devices or after cache clearing |

## Three Common Configuration Errors

- Sharing entries related to problem management and root cause analysis fail to open. First verify the full link generated by the system and its validity period, then check browser request statuses. Do not manually replace `shareId`.
- The visible scope of problem management and root cause analysis data does not match expectations. Verify third-party identity verification results, workflow request parameters, and external system data permissions separately. The sharing entry identifier itself does not grant business authorization.
- The same problem management and root cause analysis question and answer cannot be viewed on another device. For anonymous scenarios, first verify device, browser, and local identity statuses. Record retention cannot be guaranteed across devices or after cache clearing. Do not judge service anomalies solely based on this phenomenon.

## How to Verify Configurations

- Access the generated non-login shared link, verify that corresponding RCA reports, incident tickets, and other documents load correctly.
- Access the generated shared link, check that it matches preset validity period and permission settings.
- Adjust adaptation parameters for the embedded page, verify that the display effect fits the target technical support page.
- Restart the FastGPT service or container, check that sharing configurations are retained and no abnormal loss occurs.

The values provided are common starting points and should be measured against the reader's own samples.
