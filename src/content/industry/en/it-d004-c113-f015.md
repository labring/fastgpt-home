# Customer Technical Support and Pre-Sales Q&A for Integration Testing and Interface Testing: Knowledge Base Retrieval and Recall

## What the data for this category looks like
Core data for this category comes from interface management platforms, test environment logs, databases, and message queues. Update frequency is daily or when a version is released.

Daily produced documents include interface test cases, joint debugging issue tickets, test environment instructions, and test reports. Interface test cases include interface paths, request parameters, and expected response fields. Joint debugging issue tickets record link error messages and troubleshooting steps. Test environment instructions mark dependent service addresses and permission configurations.

Most data uses structured fields. Some log data is semi-structured text. Fields include interface identifiers, HTTP status codes, environment addresses, and other relevant fields.

## Constraints Imposed on Knowledge Base Retrieval and Recall
The data characteristics of this category impose multiple constraints on the retrieval and recall process.

Dispersed multi-source data requires associated recall. Cross-dataset retrieval logic must be configured to cover different data sources such as interface management platforms and test logs.

The high-frequency update feature requires an incremental synchronization mechanism. This ensures retrieval results match the current version of test environments and test cases.

The parameter fields of interface test cases and the error context of joint debugging issue tickets have high semantic relevance. Semantic matching accuracy for recall must be improved.

Precise information such as addresses and permissions requires strict matching. This avoids recalling irrelevant historical environment data.

Semi-structured log data requires pre-configured field extraction. This optimizes retrieval matching efficiency.

## Configuration Settings
These configurations are documented for FastGPT v4.17.0, as follows:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Matches the semantic relevance between interface test case parameters and user questions. The range covers common parameter verification and link troubleshooting scenarios. |
| `limit` | Top 6 entries | Single-round recall results for interface test scenarios must cover multiple version cases of a single interface and joint debugging issues. Six entries balance comprehensiveness and context length. |
| `searchMode` | hybrid | Combines keyword matching and semantic recall. Adapts to structured fields such as interface paths and parameter names, as well as semi-structured text from error logs. |
| `usingReRank` | Enabled | Reranks recall results. Prioritizes returning highly matching documents related to joint debugging issues and parameter verification. |
| `datasetSearchUsingExtensionQuery` | Enabled | Optimizes user questions through extension. Adapts to technical terms commonly used by test engineers. For example, expands "interface error" to "HTTP status code exception | link call failure". |
| `collectionIds` | Configured according to the IDs of corresponding test-type datasets | Only associates exclusive datasets such as interface test cases and joint debugging issue tickets. Avoids recalling irrelevant business documents. |

## Three Common Configuration Mistakes
- Phenomenon: When retrieving interface test parameters, case documents with missing fields are returned, or records without corresponding joint debugging issues are returned. Cause: Dataset synchronization is not configured according to the daily or per-version update frequency. This causes knowledge base data to not match the latest cases and logs of the current test environment.
- Phenomenon: When a query about a non-existent interface link problem is submitted, the system still returns references to irrelevant documents in the knowledge base. Cause: A reasonable `similarity` threshold is not set, or the recall dataset range is not limited. This causes low-matching content to be included in results.
- Phenomenon: After configuring a tool workflow, the AI only calls the interface debugging tool or only retrieves the knowledge base. It cannot perform both operations at the same time. Cause: The knowledge base retrieval node is not correctly associated in the tool workflow, or the extended query configuration of `datasetSearchUsingExtensionQuery` is not enabled. This causes the two types of logic to not collaborate.

## How to Verify a Successful Configuration
- Submit a test question for single interface parameter verification. Check whether the recall results include the interface test cases of the corresponding version. Confirm whether the dataset association range is correct.
- Submit a query about a non-existent interface. Check whether only a no-reference prompt is returned, or whether the proportion of low-matching documents meets the preset `similarity` threshold requirements.
- Simulate a query about a joint debugging link error. Confirm that the recall results include joint debugging issue tickets and corresponding log fragments. Verify that reranking and extended query are effective.
- View the dataset synchronization logs. Confirm that the daily or per-version update tasks have executed normally. No data missing or overwrite errors exist.

The values provided are common starting points. They should be evaluated against the samples used in the relevant deployment context.
