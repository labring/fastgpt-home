# Customer Technical Support and Pre-sales Q&A for Integration Testing and Interface Testing: Reranking and Hybrid Retrieval

## What data for this category looks like
Data for this category primarily comes from interface management platforms, test environment logs, databases, and message queues. Update frequency is daily or when a version is released. Daily documents include interface test cases, joint debugging issue tickets, environment descriptions, and test reports.
Interface test cases contain unique interface identifiers, request parameters, expected response formats, and execution statuses. Joint debugging issue tickets include issue symptoms, troubleshooting steps, associated interface IDs, and environment information. Test environment logs record request chains, response latency, error codes, and other related content.

## What Constraints These Characteristics Impose on Reranking and Hybrid Retrieval
This category’s data is multi-source and heterogeneous, including structured interface fields and unstructured logs and issue text. As a result, hybrid retrieval needs to meet the dual requirements of exact matching and semantic retrieval.
Data update frequency is high, so retrieval tasks must regularly sync the latest test cases and logs to avoid using expired data.
Daily documents have rich field dimensions. The reranking link needs to set appropriate weights for different data types, ensuring core interface parameters and issue symptoms are prioritized in recall.
Additionally, the most time-consuming link for this category is troubleshooting chain issues, which has strict requirements for retrieval efficiency. Reranking and hybrid retrieval configurations must balance recall count and response speed, avoiding excessive redundant results that slow down troubleshooting progress.

## How to Set Configurations
| Configuration Item | Suggested Value | Rationale |
| --- | --- | --- |
| `usingReRank` | Enabled | Adapts to multi-source heterogeneous interface testing and joint debugging data, improves the relevance of retrieval results |
| `similarity` | 0.72–0.85 | Filters low-relevance log entries and test cases for non-target interfaces, retaining core associated content |
| `limit` | Top 8–12 entries | Balances recall coverage for joint debugging issues and retrieval response speed, meeting the fast troubleshooting needs of test engineers |
| `searchMode` | hybrid | Balances exact matching for interface fields and semantic retrieval for logs and issue text, adapting to multiple data structures |

## Three Common Misconfigurations
- Configuring `usingReRank` triggers an error during testing. Forcefully ignoring the error allows the setup to run locally, but it fails during formal execution. The cause is failing to correctly obtain the ACCESS Token for the Reranker model, or the model deployment version does not match FastGPT v4.17.0.
- The Rerank model connects successfully, but the knowledge base enable result reranking switch remains disabled. The cause is failing to complete index construction for data sources such as interface management platforms and test environment logs, or the `similarity` threshold is set outside the reasonable range, filtering all results.
- Retrieval results include a large number of unrelated environment configuration documents that do not match the current interface testing scenario. The cause is not setting a reasonable `limit` parameter, resulting in too many recalled entries and failure to filter irrelevant content through reranking.

## How to Confirm the Configuration Is Complete
- Navigate to the retrieval configuration page of FastGPT v4.17.0, confirm that the `usingReRank` switch is enabled.
- Initiate a retrieval for the interface testing scenario, check the relevance scores of returned results to verify that the `similarity` threshold takes effect.
- Count the number of returned retrieval results, confirm that it matches the configured `limit` parameter.
- View the knowledge base data source list, confirm that target data such as interface test cases and joint debugging issue tickets have been correctly indexed.
