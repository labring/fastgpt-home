# Customer Technical Support and Pre-Sales Q&A for Project Implementation Plan Management: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Target users for this category are typically project managers, implementation managers, and PMOs. Data sources include contracts, work breakdown structures (WBS), client schedules, and internal enterprise project management systems. Daily maintained documents include project plans, milestone lists, weekly reports, and risk issue lists. Data updates occur weekly or per project milestone node. Document fields include task identifiers, responsible persons, deadlines, progress status, and risk levels. There is no unified mandatory format. Documents must align with internal enterprise project management specifications. Core focus areas are project progress, scope, and responsible persons.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
Data for this category is scattered and follows a fixed update rhythm. Multi-turn dialogue must integrate multi-source information such as contracts, WBS, and client schedules. Prompts must clearly define the range of data sources to call, to avoid introducing irrelevant non-project content. Document formats vary. Prompts must adapt to the field structures of different documents like project plans and risk lists, to accurately identify core business fields such as tasks, responsible persons, and deadlines. There is frequent demand for cross-party schedule coordination. This requires multi-turn dialogue to support step-by-step collection of schedule information from different participating parties. Context must regularly clear expired data based on update frequency, to prevent outdated schedule content from impacting decision-making.

## How to Set Configurations
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `chatId` | Bind the current project's unique identifier to the session | Ensure multi-turn dialogue context is associated with the corresponding project's plan and risk data, to avoid cross-project confusion |
| `messages` | Retain the last 3 rounds of user and assistant interaction content, filter expired schedule requests | Adapt to the weekly or milestone-level update frequency of project data, reduce redundant context usage |
| `variables` | Inject the current project's WBS hierarchy, responsible person list, and latest milestone node | Provide category-specific context data for prompts, to accurately match business requirements for project implementation plan management |
| Context window length | 8000–12000 tokens, calibrated via actual testing | Cover the total character count of a single project's weekly report and milestone list, avoid truncating core information |
| Knowledge base sync frequency | Trigger every 24 hours or per project milestone node | Match the update rhythm of category data, ensure the knowledge base content called by dialogue is the latest version |

## Three Common Misconfiguration Issues
- Symptom: When uploading documents in formats such as project plans and risk lists, the interface displays an upload failure prompt. Plain text input via dialogue works normally. Cause: No category-specific document parsing rules are configured. The hierarchical structure of WBS and milestone lists is not adapted, interrupting the file parsing process.
- Symptom: Multi-turn dialogue response times are long. Results for schedule coordination or risk tracking cannot be returned promptly. Cause: The context window length is not limited, or expired data is not cleared per the project's weekly or milestone update frequency. This causes each dialogue to load excessive redundant document content.
- Symptom: An `Unexpected end of JSON input` error occurs when calling the large language model. This error occurs more frequently when using the `chatglm2` model. Cause: The `messages` parameter for multi-turn dialogue is not formatted correctly, or missing fields exist in the passed project variable data. This causes the model request body to be abnormal.

- Check that the `chatId` parameter is bound to the current project's unique identifier. Ensure multi-turn dialogue context does not cross projects.
- Adjust the context window length. Verify dialogue content is not truncated and response speed meets business scenario requirements.
