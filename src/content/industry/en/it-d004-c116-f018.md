# Customer Technical Support and Pre-Sales Q&A for Project Document Handover and Archiving: Reranking and Hybrid Retrieval

## What this category of data includes
This category of data typically comes from project document libraries, configuration lists, meeting minutes, and test reports. Updates occur at the end of each project phase or after overall project delivery. Daily processed documents include as-built documents, configuration manuals, training records, and acceptance certificates. Documents usually contain fields such as project number, version identifier, stamp status, and delivery milestone. The length of a single document ranges from 500 to 5000 characters. Some documents include structured configuration parameters and acceptance items.

## What constraints these characteristics impose on reranking and hybrid retrieval
The update frequency of project document handover and archiving data is uneven. Batch new documents are added during phase deliveries, and centralized archiving occurs during overall project deliveries. Reranking and hybrid retrieval must support real-time recall of batch data. There are large differences in fields across different documents: as-built documents focus on delivery milestones and acceptance results, while configuration manuals focus on detailed parameters. Hybrid retrieval requires distinguishing the weight of different document types. Single documents have wide content spans. After chunking long documents, unified semantic alignment rules are needed to avoid irrelevant content in retrieval results. Most data is project-specific. Document libraries across different projects have no universal reusability, so retrieval must bind the data source scope of the corresponding project to prevent cross-project data confusion.

## How to configure settings
The following configurations are adapted for FastGPT v4.17.0, and can be adjusted based on the actual scale of the project document library.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Similarity threshold | `0.65–0.75` | Adapts to the density of technical terminology in project documents, filters low-relevance non-project content, and prevents irrelevant documents from appearing in retrieval results |
| Single retrieval limit | Top 10–15 results | Matches the typical number of documents in a single project document library, ensures retrieval results cover core delivery documents, and controls context length |
| Retrieval mode | Hybrid retrieval | Combines keyword matching and semantic retrieval, adapting to the characteristics of project documents that contain both structured fields (such as project number) and unstructured descriptions |
| Enable reranking | Yes | Performs secondary sorting on initial retrieval results, corrects deviations from semantic retrieval, and highlights acceptance certificates or configuration manuals that are strongly relevant to customer technical support questions |
| Rerank count | Top 5–8 results | Focuses on core delivery documents, avoiding excessive computational resource usage during the reranking stage |

## Three common misconfigurations
- The rerank switch is set to off but the function does not take effect. The symptom is that retrieval results are not sorted by relevance. The cause is that the rerank model call chain is not correctly bound, or the reranking stage is not triggered in the retrieval workflow.
- When multiple variables are output in an HTTP request, the corresponding knowledge base cannot be specified. The symptom is that retrieval results include documents from other projects. The cause is that variables are not bound to the data source scope of the corresponding project, and the data source is not limited via retrieval parameters.
- Rerank images cannot be used when deploying on arm architecture. The symptom is an architecture incompatibility error during the reranking stage. The cause is that the rerank model image adapted for arm architecture is not used, or the corresponding architecture image source is not specified during deployment.

## How to verify correct configuration
- Check the sorting order of retrieval results, confirm that highly relevant documents (such as acceptance certificates, configuration manuals) appear at the top, to verify that the rerank function is active.
- Enter project-specific keywords, confirm that retrieval results only include documents from the current project, to verify that the data source scope limitation is correct.
- Check system logs, confirm that there are no architecture incompatibility errors during the reranking stage, to verify that deployment configuration is correct.
- Adjust the similarity threshold parameter, observe changes in the number of retrieval results, to verify that the parameter configuration is active.

The values provided are common starting points and should be measured against the reader's own samples.
