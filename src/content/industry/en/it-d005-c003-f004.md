# Technical Documentation and API Q&A for IT Asset Inventory: Vector Models and Indexes
This document applies to FastGPT v4.17.0.

## What Data Looks Like for This Category
Data for this category primarily comes from asset management systems, procurement systems, financial fixed asset modules, and terminal management platforms. Daily processed documents include asset ledgers, inventory sheets, loan and return forms, and scrap requests.
Update cadence follows monthly, quarterly, or annual cycles, with single or bulk asset information updates per run. Most document structures include fields such as asset ID, device name, deployment location, responsible user, purchase date, and asset status. There is no unified fixed format, and some documents exported from systems will include bulk headers.

## What Constraints Do These Characteristics Impose on Vector Models and Indexing
Dispersed data sources lead to inconsistent field formats. Field standardization must be completed before indexing to avoid vector extraction bias.
Update frequency is low, but single bulk data volume may be large. Index construction must support incremental updates to reduce time spent on full rebuilds.
Diverse document types require differentiated chunking rules for different documents such as ledgers and request forms, to adapt to different text lengths.
Unlike configuration management and CMDB maintenance, indexes for this category must prioritize fields related to asset ownership, location, and user. This affects the priority settings for vector encoding.

## How to Configure
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Adapt to the single-block text length of asset ledgers and request forms, avoid overly fragmented or overly long chunks |
| Overlap Length | 50–100 characters | Retain contextual association between adjacent chunks, ensure cross-chunk information such as asset location and responsible user is not lost |
| `defaultToken` | 1024 | Match the input token limit of general-purpose vector models, adapt to encoding needs of most asset-related text |
| `maxToken` | 4096 | Limit the maximum token count for a single index entry, prevent indexing failures caused by overly long text |
| Single Search Limit | Top 10 entries | Balance recall efficiency and accuracy, meet result needs for core asset queries |
| Maximum Context | Calibrated via actual testing | Adapt to asset datasets of different sizes, avoid context overflow |

## Three Common Misconfigurations
- A 60-second timeout occurs when switching knowledge base indexes, with a request timeout prompt returned in the interface. The cause is that incremental indexing is not enabled for low-update-frequency asset data, and full rebuild execution exceeds system time limits.
- The knowledge base contains only a small amount of asset data but remains in training or rebuilding state for more than one day. The cause is that chunk length is set too small, generating a large number of redundant chunks and extending the indexing processing workflow.
- When adding indexes to a batch of asset sets, the request returns a parameter error and fails to complete indexing ingestion. The cause is that index mapping is not configured according to the field structure of asset documents, so the system cannot recognize core asset information fields.

## How to Verify Proper Configuration
- Submit an indexing test for a single asset document, check if the vector encoding result includes core fields such as asset ID and responsible user.
- Simulate a batch indexing submission, verify that the processing speed of the system task queue meets expectations, with no long-pending rebuild tasks.
- Initiate a test query for asset location, confirm that the number of recall results matches the configured single search limit.
- View the index collection mapping rules, confirm that all asset document chunks are uniformly mapped to the same index collection, and no single-document separate indexing is configured.
- View the indexing build logs, confirm that the values of `defaultToken` and `maxToken` do not trigger encoding over-limit error messages.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
