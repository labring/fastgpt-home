# Technical Documentation and API Q&A for Issue Triage and Response: Knowledge Base Retrieval and Recall

## What the data for this category looks like
This category's data mainly comes from GitHub or Gitee Issues, code repository version logs, user environment feedback, and code commit records. Daily maintained documents include Issue classification templates, tag rules, historical response records, and problem reproduction description documents. The data update frequency is daily or weekly. Fields include Issue number, problem description, reproduction steps, associated code modules, priority tags, etc., with no additional statistical quantitative fields.

## What constraints do these characteristics impose on the "knowledge base retrieval and recall" link
The core of this category's data is Issue-related problem descriptions, reproduction steps, and tag rules. Retrieval results must accurately match the problem keywords and reproduction scenarios submitted by users. The data is updated daily or weekly, so the knowledge base synchronization frequency must match the update rhythm to avoid using expired tag rules or historical responses. Since the data fields focus on problem classification and responsibility modules, retrieval must prioritize associating specific fields such as code modules and Issue numbers. At the same time, the number of recalled results must be controlled to avoid redundant information interfering with triage decisions.

## How to set the configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Matches the precision requirement for Issue problem descriptions, avoids recalling irrelevant issues |
| `limit` | Top 6–8 entries | Controls the information load for triage and response, avoids excessive content interfering with decision-making |
| `searchMode` | Keyword + semantic hybrid | Adapts to the structured descriptions and unstructured reproduction steps of Issues |
| `usingReRank` | Enabled | Optimizes the ranking of recalled results, prioritizes displaying high-match tag rules and templates |
| `datasetSearchUsingExtensionQuery` | Enabled | Supplements implicit keywords in Issue reproduction steps, improves recall coverage |
| `collectionIds` | Bind to Issue-related dataset IDs | Limits the retrieval scope, avoids interference from irrelevant knowledge base content |

## Three common mistakes
- Symptom: After deploying the application, retrieval results do not display document download links, but work normally in debug mode. Cause: The public access permission of the knowledge base is not configured in the production environment, or the document external link generation switch is not enabled.
- Symptom: After uploading a PDF, the vectorization task takes too long, and the interface shows a wait time exceeding 10 minutes. Cause: Large-volume PDFs are not preprocessed in chunks, or adapted vector model parameters are not used.
- Symptom: The number of knowledge base search results in the workflow is much lower than the configured upper limit on the application frontend. Cause: The `limit` parameter of the workflow node is bound to the system preset low upper limit by default, and is not manually adjusted to match business requirements.

## How to confirm the configuration is properly set
- Submit a simulated Issue, check after retrieval whether the recalled results include the corresponding tag rules and reproduction templates.
- View the knowledge base synchronization logs to confirm that the data update frequency meets the daily or weekly setting requirements.
- Test different types of Issue keywords to verify whether the retrieval results prioritize matching associated code modules and historical responses.
- Check that the configuration parameters are consistent with the FastGPT v4.17.0 interface options.

The values provided are common starting points and should be measured against the reader's own samples.
