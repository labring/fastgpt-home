# Technical Documentation and Interface Q&A for Pull Request Reviews: HTTP Interfaces and External Systems

## What Data for This Category Looks Like
Core data for Pull Request reviews comes from commit records of linked code repositories, CI pipeline execution results, linked Issue links, and contributor submission content.
Daily circulated documents include PR description documents, code review comments, CI test reports, and merge status records.
Data updates occur daily or weekly, on average.
Single PR data includes fields such as change scope, conflict markers, test pass rate, and submitter information.
There are no fixed statistical values. Updates follow actual submission rhythms only.
This category handles mergeable code changes, with clear differences in processing objects from categories such as Issue triage.

## Constraints Imposed on HTTP Interfaces and External Systems
Pull Request review data comes from multiple dispersed sources linked to external systems.
HTTP interfaces must be used to pull PR details, CI results, and other content from code repositories.
As a result, interface authentication must match the permission rules of each external system.
Data update rhythms are unstable.
Interface calls must support batch pulling and incremental synchronization logic to avoid duplicate requests or missed updates.
Single PR data fields have non-standardized structures.
The `responseData` returned by the interface must undergo field mapping to adapt to the parsing logic of review tools.
Additionally, the change intent confirmation step relies on context association.
Interface calls must carry associated context parameters to ensure returned content matches the specific change scope of the PR.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {external system authentication token}` | Complies with HTTP interface standard authentication specifications, adapts to interface permission checks for code repositories and CI tools |
| `variables` | Key-value pairs containing PR number, repository address, and CI task ID | Used to dynamically pass context parameters for PR reviews, replacing placeholder variables in prompt words |
| `responseData` | Mapped to the `{prId: string, ciStatus: string, hasConflict: boolean}` structure | Standardizes interface return formats, adapting to the field parsing logic of review tools |
| Interface timeout threshold | 30-60 seconds | Adapts to the average time required to pull CI results, preventing call failures due to delayed responses from external systems |
| Single pull quantity | First 10-20 pending review PRs | Matches daily review processing rhythms, avoiding excessive data volume in a single request |

## Three Common Misconfigurations
- Phenomenon: After calling the interface, returned content does not replace placeholder variables in the prompt words, and the result is unrelated to the PR scenario. Cause: Context parameters are not correctly passed via the `variables` parameter, or placeholder variable names do not match the passed key names.
- Phenomenon: Service startup verification fails when running FastGPT v4.17.0 or later, with a prompt that AI Proxy configuration is missing. Troubleshooting steps: Check if the `AIPROXY_API_ENDPOINT` (AI Proxy service root address) and `AIPROXY_API_TOKEN` (AI Proxy administrator Token) environment variables are configured in the App/Admin server, or if they were mistakenly entered into non-server deployment configuration locations such as workflow global variables, application API request headers, or the general model management page.
- Phenomenon: Returned data parsing fails after calling an external interface, with empty fields or format errors. Cause: No standardized field mapping is configured via `responseData`, and unstructured raw interface return data is used directly.

## How to Verify Successful Configuration
- Check the environment variables in the App/Admin server, confirm that `AIPROXY_API_ENDPOINT` (AI Proxy service root address) and `AIPROXY_API_TOKEN` (AI Proxy administrator Token) are correctly configured, and that `AIPROXY_API_ENDPOINT` does not have path suffixes such as `/v1` appended.
- Initiate a test interface call, pass test `variables` parameters, verify that placeholder variables are correctly replaced, and that returned content matches the PR review scenario.
- View interface call logs, confirm that the `Authorization` header is correctly carried, and that the returned `responseData` fields conform to the preset mapping structure.
- Start the FastGPT service, verify that the service starts without verification errors, and that external system interface calls return normal status codes.
