# Technical Documentation and Interface Q&A for Pull Request Reviews: Vector Models and Indexes

## What Data Looks Like for This Category
Data for this category primarily comes from hosted code repositories, associated CI pipelines, linked Issue links, and change submissions from contributors. Daily generated document structures include PR description text, code review comment details, CI execution result logs, and merge record metadata.
The data update rhythm is typically daily or weekly. Single data entry fields include change description, file change list, review score, test pass rate, and others. There is no fixed unified unit standard, and data is generated dynamically based on change content.

## Constraints for Vector Models and Indexes Workflows
Code repository change content includes a large number of code snippets and technical terms, which requires the vector model to adapt to tokenization requirements. CI result logs contain a large amount of structured text, so indexing needs to distinguish chunking rules for structured and unstructured data.
The daily or weekly data update rhythm requires incremental index update triggers to match change submission rhythms, avoiding resource consumption from full index rebuilds.
Associated PR review data has strong relational links. For example, the description and review comments of the same PR need to retain association identifiers in the index to ensure context integrity during retrieval.
Single data entry lengths vary widely, from short merge descriptions to hundreds of characters of review comments. A variable-length chunking strategy is required to adapt to these differences.

## Configuration Settings
The following configurations are written for the vector index module of FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Adapts to common lengths of PR descriptions and review comments, avoids overloading single chunks |
| Overlap Length | 100–200 characters | Retains context association between adjacent chunks, reduces information breakage during cross-chunk retrieval |
| maxToken | 4096 token | Matches input limits of most commercial vector models, supports embedding processing for long review comments |
| Similarity Threshold | 0.75–0.85 | Filters low-relevance code changes and review comments, improves retrieval accuracy |
| Single Search Limit | Top 10 entries | Controls the scale of retrieval results, adapts to the need for quick context confirmation during PR reviews |
| Incremental Update Trigger | By submission timestamp | Matches the daily or weekly data update rhythm, avoids resource waste from full index rebuilds |

## Common Misconfigurations
- Index creation shows success but page fails to load: The collection creation interface returns a success flag, but the frontend page always displays that the index is not ready. The cause is that the incremental update trigger logic does not match the actual submission timestamp of the PR, resulting in the index file not being correctly written to the storage path.
- Local run works normally but vector scores are identical after Docker image deployment: Retrieval results meet expectations in the local environment, but embedding scores for all texts are exactly the same after containerized deployment. The cause is that the cache directory of the vector model is not correctly mounted inside the container, causing the model parameters to be re-pulled for each embedding and resulting in feature loss.
- Hybrid retrieval takes longer than expected: Single retrieval takes more than 10 seconds, far exceeding the local runtime. The cause is that the number of returned entries from a single search is not limited, leading a large number of low-relevance results to participate in the reranking process and increasing computational overhead.
- Index build stalls at the final batch: The index build progress bar always stays at the last batch of data, with no error messages. The cause is that the chunk length is set too large, exceeding the processing limit of the vector model, causing the final batch of data to fail to complete embedding.

## How to Verify Proper Configuration
- Check the vector embedding logs to confirm that the number of chunks per data entry matches expectations, with no abnormal error messages.
- Run a simulated retrieval, input a PR description text, and check if the returned results include associated review comments and code change content.
- Compare the number of index entries before full index creation and after incremental update, confirming that the update rhythm matches the data submission rhythm.
- Test PR texts of different lengths, confirming that there is no obvious feature loss or truncation in the embedding results.

The values given are common starting points and should be measured against the reader's own samples.
