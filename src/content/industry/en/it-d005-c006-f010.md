# Technical Documentation and API Q&A for Pull Request Reviews: Source Citation and Traceability

## What this category of data looks like
Data originates from PR metadata in code repositories, CI pipeline execution logs, linked Issue URLs, and changed files submitted by contributors.
Update frequency is typically daily or weekly.
Daily documentation includes PR description text, code review comment entries, CI result reports, and merge status records.
Fields cover change content summaries, linked Issue numbers, CI pass rates, submitter identifiers, and more.
No unified fixed multi-field statistical format exists. Configurations are adjusted flexibly based on the corresponding repository.

## What constraints do these characteristics impose on source citation and traceability?
Data is scattered across multiple independent systems including code repositories and CI pipelines. Cross-source association rules must be configured to fully trace all basis for PR reviews.
Update frequency is not fixed. Index update frequency must be matched to ensure the timeliness of cited data.
Daily documentation includes structured review comments and unstructured change descriptions. Content splitting and retrieval must be adapted for different formats.
Linked Issues and CI results for PRs update dynamically as reviews progress. Traceability links must bind the latest change snapshots to avoid citing outdated review basis.

## How to configure
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `quoteMaxToken` | 800–1200 token | Adapts to the average length of PR review documentation, avoiding truncation of key review comments and CI result content |
| Reordering | Enabled | Adapts to mixed structured review entries and unstructured change descriptions in PR data, improving retrieval relevance |
| Single search limit | Top 6 entries | Matches the typical number of linked data associated with a single PR, avoiding introduction of redundant non-review-related content |
| `detail` | Enabled | Retains complete metadata of citation sources, facilitating traceability of linked CI results and Issue URLs |
| Similarity threshold | 0.75–0.85 | Filters low-relevance non-PR linked data, focusing on core content related to reviews |
| `responseData` | Return only linked PR and CI data | Limits the traceability scope, avoiding introduction of irrelevant knowledge base content |

## Three common configuration mistakes
- Phenomenon: Empty citation results appear after enabling reordering. Cause: The text length of CI results or Issue links linked to the PR is short, and the reordering threshold filters valid fragments that meet basic similarity requirements.
- Phenomenon: Retrieval requests time out without returning results. Cause: The `quoteMaxToken` parameter is not adjusted to adapt to long PR documents, causing excessive content loading during retrieval to trigger a timeout.
- Phenomenon: Citation sources are not linked to the corresponding PR's change records. Cause: The `detail` configuration is not enabled, and metadata association fields are not retained, making it impossible to bind the PR's merge status and submission information.

## How to confirm configuration correctness
- Simulated PR review technical Q&A requests are initiated, and returned results are examined for linked CI results and Issue URLs.
- The `quoteMaxToken` parameter is adjusted, and the token length of returned citations is verified against the preset range.
- The reordering function is disabled, and retrieval is performed again. Changes in result counts are compared to confirm reordering configuration effectiveness.
- Metadata fields of citation traceability are reviewed to confirm inclusion of submitter identifiers and merge status information.

The values provided are common starting points and should be evaluated against samples specific to the deployment context.
