# Technical Documentation and API Q&A for SLA and Service Reports: HTTP Interfaces and External Systems

## What the data for this category looks like
Data for this category comes from monitoring systems, ticketing systems, contract documents, and customer communication records. The update frequency is monthly or quarterly. Daily produced documents include four categories: SLA clause text, monthly service reports, availability statistics tables, and customer review minutes. Data fields include contractually agreed SLA thresholds, actual service event records, statistical cycle identifiers, customer association identifiers, and other fields. There are no fixed unified units, and general units such as time and count are adapted based on field types. The data is aggregated and organized according to the customer's contract cycle.

## What constraints these characteristics impose on HTTP interfaces and external systems
Multi-source heterogeneous data sources require HTTP interfaces to support flexible field mapping rules. Data format adaptation logic for different systems must be passed via parameters. Fixed monthly or quarterly update frequency means interfaces do not need high-frequency calls, and are suitable for periodic-triggered batch pull requests. Multiple document structures require interfaces to support filtering data by document type to avoid returning redundant content. Exclusive fields such as contract number and statistical cycle must be clearly included in requests to prevent data confusion. Complete event links require interfaces to return raw data fields to support subsequent SLA indicator calculation and abnormal attribution work.

## How to Configure Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${pre-configured service secret}` | Follows HTTP interface authentication specifications to ensure data access permissions are controllable, and adapts to the interface security requirements of FastGPT v4.17.0 |
| `variables` | `{"stat_cycle": "monthly", "data_sources": ["monitoring", "workorder"]}` | Adapts to multi-source data access and fixed-cycle statistical requirements, and matches the monthly/quarterly update rhythm of business data |
| `responseData` | `include ["contract_id", "actual_availability", "abnormal_events"]` | Only returns core business fields to reduce data transmission overhead and simplify subsequent SLA indicator calculation processes |
| Request timeout | `600 seconds` | Adapts to the time-consuming scenario of batch pulling monthly service reports, and avoids incomplete data caused by request interruption mid-process |
| Upload file format | `text/plain` | Matches the file processing logic of FastAPI, and supports direct transmission and return of txt-format service report files |

## Three Common Configuration Mistakes
- Symptom: A 401 Unauthorized error is returned when calling the HTTP interface. Cause: The `Authorization` parameter is not configured correctly, or an expired service secret is used, resulting in authentication failure.
- Symptom: Service report fields returned by the interface are missing or do not match business requirements. Cause: The correct data source and statistical cycle are not specified via the `variables` parameter, causing the interface to pull data that does not match the current contract cycle.
- Symptom: When using a curl command to transmit a txt file, the backend FastAPI cannot correctly parse the file content. Cause: The `Content-Type` request header is not set to `text/plain`, or the file parameters are not encapsulated as required, causing the backend to fail to recognize the uploaded txt file.

## How to Confirm Successful Configuration
- Call the configured HTTP interface and check if the returned `responseData` includes preset core business fields, such as contract number and actual availability data.
- Send a request carrying the `variables` parameter, and confirm that the interface only pulls data for the specified cycle and source, with no redundant content.
- Use a curl command to upload a test txt file, and verify that the interface can correctly receive and return the processed txt-format file.
- View the interface call logs to confirm that the `Authorization` parameter is correctly carried, and there are no authentication-related errors.
