# Technical Documentation and API Q&A for Cloud Resource Compliance Audit: HTTP Interfaces and External Systems

## What the data for this category looks like
This category of data mainly comes from cloud audit logs, IAM permission systems, CMDB resource inventory databases, and security baseline scan results. Daily produced documents include compliance checklists, permission audit reports, resource inventory lists, and rectification tracking forms. Each document field includes resource ID, permission configuration items, compliance status, rectification time limit, and other content, with no additional custom units. The data update frequency is monthly or quarterly. The update cycle of some real-time synchronized resource status data can be adjusted as needed.

## What constraints these characteristics impose on the HTTP Interfaces and External Systems link
The data sources for this category are scattered and the update frequency is low. HTTP interfaces must support pulling data by specified data sources to avoid meaningless high-frequency requests. Document fields include multi-dimensional compliance-related content, so interfaces must allow specifying return fields to adapt to document generation requirements for different scenarios. The accuracy of compliance data directly affects audit results. Interfaces must strictly verify calling identities, and support returning complete error information to facilitate problem troubleshooting.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `Authorization` | Bearer token, valid for 7200 seconds | Meets the high-security verification requirements for compliance-related data, prevents unauthorized access, and complies with the interface specifications of FastGPT v4.17.0 |
| `variables` | Pass data source and time range parameters | Matches the pull requirements for multiple data sources in this category, and adapts to monthly/quarterly batch data pull scenarios |
| `responseData` | Return only core compliance fields | Reduces redundant data transmission, and adapts to the lightweight generation requirements for compliance documents |
| Maximum number of items returned per single request | First 100 items | Prevents excessive data volume in a single request from causing timeouts, and adapts to batch pulls of monthly resource inventory lists |
| Request timeout setting | 600 seconds | Adapts to the time required for batch pulling compliance data, and prevents request interruptions caused by large data volumes |

## Three common mistakes
- Phenomenon: Slow response when calling external interfaces to pull compliance data, with longer-than-expected duration. Cause: The calling policy is not adjusted according to the low update frequency feature of this category, and high-frequency requests are set, causing interface resources to be occupied by invalid requests.
- Phenomenon: 401 authentication failure is returned when using HTTP requests to bind external systems. Cause: The `Authorization` parameter is not configured correctly, or the token validity period setting does not meet security verification requirements.
- Phenomenon: Prompt of authentication failure when synchronizing API knowledge base collections. Cause: Interface identity rules are not configured according to the high-security verification requirements of this category of data, causing cross-system data synchronization failures.

## How to confirm that the configuration is complete
- Call the test interface, check whether the fields returned by `responseData` include expected compliance-related content, and confirm that the field filtering configuration takes effect.
- Initiate a batch data pull request, check whether the number of returned items conforms to the preset maximum number of items returned per single request rule, and confirm that the pagination configuration is correct.
- Simulate an abnormal request, check whether the interface returns clear error information, and confirm that the identity verification and timeout configuration take effect.
- View the interface call log, confirm that the data source configuration in the request parameter `variables` is consistent with the actual data source of the pulled data, and confirm that the data source configuration is correct.
