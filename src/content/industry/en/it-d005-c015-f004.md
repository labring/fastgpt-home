# Technical Documentation and API Q&A for Product Usage Data Analysis: Vector Models and Indexes

## What this category of data looks like
Data sources for this category include tracking systems, data warehouses, CRM systems, and ticket systems. Daily produced documents include usage analysis reports, tracking plans, indicator caliber tables, and dashboard requirement sheets. Most data updates follow daily or weekly batch synchronization schedules. Data fields include customer identifiers, function modules, operation frequencies, indicator values, and reporting times. Units include counts, minutes, percentages, and others. Some documents contain semi-structured caliber explanations and cross-field relationships. Some fields have null or abnormal values, creating additional requirements for abnormal data troubleshooting.

## What constraints do these characteristics impose on vector models and indexes
This category’s data includes both structured fields and semi-structured explanatory documents, with fixed daily or weekly batch update schedules. Vector modeling must balance field semantics and complete context. Batch update requirements mean indexes must support incremental synchronization, to avoid resource consumption from full reindexing. Indicator caliber documents have high professional content, so complete term context must be preserved to prevent chunk splitting from breaking definition integrity. Cross-customer behavior data must support filtering and recall by customer or function module. Some abnormal data retrieval requires associating multi-source documents, so indexes must support multi-field combined recall to improve abnormal troubleshooting efficiency.

## How to set configurations
This document is written for FastGPT v4.17.0. The following configuration items are adapted to the business characteristics of this category:

| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to the text length of indicator caliber tables and tracking plans, avoids splitting that breaks indicator definition integrity |
| Overlap Length | 100–200 characters | Retains contextual association between adjacent chunks, ensures coherent explanation of indicator calibers |
| Similarity Threshold | 0.75–0.85 | Distinguishes similar indicator names and operation scenarios, reduces false recalls |
| Single Search Limit | Top 10 entries | Adapts to the information density of daily analysis, avoids overloading retrieval results |
| `defaultToken` | 8192 | Matches input length limits of local vector models |
| `maxToken` | 16384 | Covers complete contextual requirements for batch analysis reports |

## Three common configuration mistakes
- Symptom: Knowledge base capacity planning lacks a basis, leading to resource redundancy or shortage. Cause: Fails to estimate based on the category’s average daily data update volume and average single data length, and directly applies general calculation logic.
- Symptom: Vector model calls return 503 status codes. Cause: Fails to configure `defaultToken` to match model input limits, or concurrent requests exceed the vector database’s capacity threshold.
- Symptom: Recall results do not match indicator calibers. Cause: Chunk length is too short, splitting breaks the complete context of indicator definitions, leading to semantic recall deviation.

## How to confirm configurations are correct
- Upload a typical indicator caliber table, check if chunked text retains complete indicator definitions and explanations.
- Initiate queries containing specific indicator names, verify that corresponding tracking documents and analysis reports are included in recall results.
- View the vector database monitoring panel, confirm that concurrent requests do not trigger rate-limiting error reports.
- Test incremental update tasks, verify that newly uploaded weekly analysis reports can be recalled normally.
