# Technical Documentation and API Q&A for Code Review and Merge Management: HTTP Interfaces and External Systems

## What data for this category looks like
This category of data primarily comes from Git repositories, CI pipelines, static scanning reports, and defect databases. Daily produced documents include merge request details, code review comments, commit records, and branch strategy descriptions. Common data fields include merge request unique identifiers, commit hashes, review statuses, associated branch names, and more. Data updates are triggered daily or by each code commit, and are synchronized in real time alongside code changes.

## Constraints imposed by these characteristics on HTTP interfaces and external systems
Since data sources include code repositories and pipeline tools, HTTP interfaces must be compatible with permission verification logic across different platforms. The `Authorization` parameter must be configured correctly to ensure call legitimacy. Data updates trigger in real time alongside code commits. API call frequency must match the change rhythm to avoid exceeding system capacity limits. Multi-source business data must be passed via `variables`. Interfaces must support receiving structured parameters that include review statuses and branch information. Merge request status changes must be synchronized to external systems. Interfaces must ensure response timeliness, and timeout settings must align with business workflow cycles.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| ---|---|--- |
| `Authorization` | Fixed format as `Bearer {apiKey}`, where apiKey is the secret key generated by the platform | Used to verify API call identity, compliant with FastGPT v4.17.0 permission verification rules |
| `variables` | Pass a JSON object containing knowledge base IDs and workflow trigger parameters, with parameter values calibrated via actual testing | Used to pass business context related to code reviews, to accommodate multi-source data input requirements |
| `responseData` | Configured to return structured fields for merge request statuses and review comment details | Used to receive the core business data format required by external systems |
| Timeout period | 30–60 seconds | Aligns with the real-time workflow rhythm of code commits, to avoid process blocking from excessive waiting |
| Single call data volume | No more than 1000 MB | Matches the code change scale of a single Git repository commit, to avoid excessive interface load |

## Three common configuration errors
- Symptom: The API returns `400 Bad Request` with a prompt indicating a missing knowledge base ID parameter. Cause: The preset knowledge base global variable ID was not correctly passed via the `variables` parameter, causing the workflow to fail to associate with the corresponding knowledge base.
- Symptom: The results returned after API calls do not include review comments or merge request statuses. Cause: The return field mapping for `responseData` was not configured correctly, and core business data fields required by the business were not extracted.
- Symptom: API calls frequently trigger timeout errors. Cause: The timeout setting is shorter than the actual time required for business workflow processing, and the timeout parameter was not adjusted based on actual scenarios.

## How to confirm successful configuration
- Call the API, then check the returned `responseData` field to confirm that expected business fields such as merge request ID and review status are included.
- Verify that the knowledge base ID in the `variables` parameter matches the platform's global variable configuration, then trigger the workflow to confirm that the knowledge base association takes effect.
- Simulate a code commit to trigger an API call, then check whether the external system has received the updated review status information synchronously.
- View the FastGPT v4.17.0 API call logs to confirm that the `Authorization` parameter verification passed, and there are no permission-related errors.
