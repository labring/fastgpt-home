# Technical Documentation and API Q&A for Code Review and Merge Management: Vector Models and Indexes

## What this category of data looks like
This category of data comes from Git repositories, CI pipelines, static scan reports, and defect databases. Daily generated documents include merge requests, code review comments, commit records, and branch strategy descriptions. Data fields include merge request ID, changed file list, review comment content, associated commit hash, branch strategy rules, and more. Updates trigger daily or after each code commit. Most data consists of text fragments, with some including structured metadata. Overall update frequency is high and tightly bound to code commits.

## What constraints do these characteristics impose on vector models and indexing
Since data update frequency is tightly bound to code commits, indexes must support incremental updates to avoid time-consuming full rebuilds. Data includes large volumes of code snippets and review comments. When chunking, retain code context and review association relationships to avoid breaking semantic connections through splitting. Structured metadata such as merge request ID and branch information must be stored as index metadata to enable filtering recall results by change scope later. In high-concurrency commit scenarios, limit the number of submissions per batch of indexing tasks to prevent task backlog.

## How to set configurations
| Configuration Item | Recommended Values | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapt to semantic completeness of code snippets and review comments, avoid splitting to break change context |
| Overlap Length | 100–200 characters | Retain associated information between adjacent chunks, prevent disconnect between cross-chunk review comments and code changes |
| Similarity Threshold | 0.75–0.85 | Filter low-relevance recall results, focus on technical documentation and API content related to code reviews |
| Single Search Limit | Top 10 results | Control the number of results per recall round, adapt to information density requirements in review scenarios |
| `maxToken` | 16000 | Accommodate complete change content of merge requests and associated review comments, avoid truncating critical information |
| `defaultToken` | 2000 | Set default token length for a single vector, adapt to vectorization requirements for short-text review comments |

## Three common configuration errors
1.  Index error after upgrading version: The interface displays a configuration parameter incompatibility prompt or returns a 500 status code. The cause is that the new version updates verification rules for chunk parameters, and the value range of the old configuration exceeds the range allowed by the new version.
2.  Stuck incomplete index task: The index status remains in "processing" for an extended period with no progress updates. The cause is that incremental index trigger logic is not configured, and full index tasks continue to backlog under high-frequency commit data.
3.  Missing associated information in recall results: Q&A results cannot be linked to specific merge requests or review records. The cause is that metadata synchronization configuration is not enabled, and only plain text content is indexed without binding structured metadata from the Git repository.

## How to confirm the configuration is properly set
- Upload a test merge request document, verify that index generation completes within a reasonable time frame with no error prompts.
- Initiate a Q&A targeting code changes, check that recall results include associated review comments and commit records, and the quantity matches the single search limit setting.
- Adjust the chunk length parameter and re-index, validate that recall semantic integrity meets expectations across different lengths.
- Review FastGPT v4.17.0 system logs to confirm that the metadata binding field is correctly configured with no abnormal errors.
