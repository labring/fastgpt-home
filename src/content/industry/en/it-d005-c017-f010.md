# Technical Documentation and API Q&A for Code Review and Merge Management: Source Citation and Traceability

## What this category's data looks like
This category’s core data originates from Git repositories, CI pipelines, static scanning reports, and defect databases. Daily documents include merge requests, code review comments, commit records, and branch strategy descriptions. These documents contain fields such as merge request ID, list of changed files, reviewer identifiers, and commit hashes. Data updates run daily or with each code commit. Data from all sources uses synchronized update rhythms to ensure consistency of associated information. This supports development teams in judging change impacts and facilitating review communication.

## What constraints do these characteristics impose on the source citation and traceability link
The multi-source nature of this category’s data requires traceability links to bind unique identifiers such as Git commit hashes and reviewer identities. This prevents confusion between associated information of different merge requests. The high update frequency requires citations to match the data refresh rhythm for timeliness. Expired citations cannot reflect the latest status of current merge requests. Merge requests and review comments include code snippets and business descriptions. Traceability must cover full contextual information. This category also includes manual review business semantic judgments. Traceability links must distinguish between automatic scanning results and manual review content. This ensures citation credibility meets development scenario requirements.

## How to configure the settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | `800–1200 token` | The total length of core change content and review comments for merge requests typically falls within this range, and can fully carry key cited information |
| `responseData` | Includes commit hash, list of changed files, original review comments | Matches category data sources to enable precise traceability of Git commits, code changes, and manual reviews |
| `detail` | Enabled | Specific review details and code change context for citations must be displayed to support traceability verification by development personnel |
| Single search limit | Top 3–5 entries | Relevant citations for merge requests are mostly concentrated in a small number of associated commits and review records; too many entries will distract attention |
| Citation expiration threshold | 24 hours | Category data is updated daily or with each commit, and expired citations cannot reflect the latest status of current merge requests |

## Three common mistakes
- Phenomenon: Citations unrelated to the current merge request are displayed in conversations, and the corresponding content is not included in the local knowledge base. Cause: No source filtering rules for `responseData` are configured, and Git commit hashes are not bound as association criteria, resulting in matching unrelated static scanning reports.
- Phenomenon: The sorting priority of knowledge base citations does not meet expectations, and it is not possible to intuitively associate with recent code commits. Cause: Sorting weights are not adjusted for this category’s high-timeliness data, and the sorting logic of general documents is used instead.
- Phenomenon: Citations cannot display specific review comment details, only vague summaries. Cause: The `detail` parameter is not enabled, and only simplified citation information is returned, which cannot support traceability verification.

## How to confirm the configuration is complete
- Submit a test merge request. Check if returned citations include the corresponding Git commit hash and changed file paths.
- Adjust the `quoteMaxToken` value. Verify that cited content length meets expectations, with no truncation or overflow.
- Disable the `detail` parameter. Confirm that citations only display summaries. Re-enable the parameter to check if complete review comment content is restored.
- Check the background configuration logs of FastGPT v4.17.0. Confirm that `responseData` return fields include preset traceability information.
