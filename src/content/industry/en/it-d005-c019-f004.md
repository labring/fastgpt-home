# Technical Documentation and API Q&A for Crowdsourced Annotator Management: Vector Models and Indexes

## What This Category of Data Looks Like
Data for this category originates from crowdsourcing platforms, annotation quality records, training and exam logs, and financial systems. Daily processed documents include personnel access rules, annotation training materials, performance statistics tables, and settlement lists.
Data updates occur daily or monthly. Annotation quality data updates upon completion of daily annotation tasks. Settlement lists are generated during monthly account reconciliation.
Document fields include personnel ID, access qualifications, training assessment scores, annotation accuracy, settlement amount, and more. Some data comes from structured system-exported tables, some are unstructured training documents, and some lack unified standardized formatting.

## Constraints on Vector Models and Indexes
The data includes both structured performance and settlement fields, plus unstructured training documents. Vector models must support embedding for both data formats.
Daily updated annotation quality data requires indexes to support high-frequency incremental updates. This avoids time costs from full re-embedding.
Monthly generated settlement lists and access rule documents need reasonable chunk lengths. This preserves association logic between fields.
Differences in fields across multiple data sources require unified metadata identifiers during index construction. This prevents confusion between different personnel-related data types during retrieval.
Embedding numeric fields such as annotation accuracy and settlement amount requires the vector model to handle structured data. This ensures accurate matching of relevant personnel performance information during retrieval.

## Configuration Recommendations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to semantic integrity of unstructured documents such as personnel access rules and training materials, while avoiding embedding bias caused by overly long single chunks |
| Overlap Length | 100–200 characters | Retains contextual association between adjacent chunks, ensuring cross-chunk performance and settlement logic is not disrupted |
| Similarity Threshold | 0.75–0.85 | Filters low-match retrieval results, adapting to precise retrieval needs for personnel qualifications and performance data |
| Single Search Limit | Top 10 entries | Controls retrieval return volume, avoiding excessive irrelevant personnel data interfering with core retrieval goals |
| `defaultToken` | 2048 | Adapts to embedding length requirements of most annotation documents, avoiding truncation of critical settlement rules or performance descriptions |
| `maxToken` | 4096 | Supports complete embedding of long documents, covering longer structured table documents such as monthly settlement lists |

## Three Common Misconfigurations
- Issue: Multilingual recall rate does not meet standards after batch re-embedding of the knowledge base. Cause: Multilingual adaptation parameters for the embedding model were not adjusted for crowdsourced annotation multilingual training materials and access rules. Only the model was replaced, and chunking rules for the target language were not configured.
- Issue: Manually inserted personnel settlement list documents disappear automatically several hours after indexing. Cause: Persistent storage parameters for the index were not configured. Financial system exported document sources use automatic temporary path cleanup, causing synchronization failure after index-reliant source files are deleted.
- Issue: In FastGPT v4.17.0, uploaded files remain in the "Indexing" state for extended periods. Cause: The selected embedding model is incompatible with the current version’s vector processing logic. The model’s input format and output dimension were not verified in advance against the field length requirements of this category’s data.

## How to Confirm Proper Configuration
- Run a small-batch document embedding test, and verify that embedded vector dimensions match the standard output dimensions of the selected model.
- Search for keywords related to personnel performance, and check that the number of returned results matches the configured single search limit.
- Manually trigger an incremental update, and confirm that the updated index covers newly added daily annotation quality data.
- Check the index’s persistent storage path, and ensure source documents are not automatically cleaned up and index files are not deleted.

The values provided are common starting points and should be measured against relevant samples.
