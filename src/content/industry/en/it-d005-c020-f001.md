# Technical Documentation and API Q&A for Supplier and Equipment Delivery Management: HTTP APIs and External Systems

## What the data for this category looks like
Typically, data for this category is generated around equipment procurement and delivery workflows for integration projects. Daily documents include purchase orders, delivery acceptance slips, serial number lists, and invoice materials. Core fields include equipment model, serial number, purchase order number, acceptance status, and logistics tracking number. Data mainly comes from ERP systems, supplier shipping documents, logistics tracking information, and equipment manufacturer backends. Updates are carried out per order or weekly. Individual data entries are linked to delivery milestones for specific projects, and support the full equipment delivery workflow for integration projects.

## What constraints these characteristics impose on the HTTP APIs and External Systems link
Data for this category is linked to specific project delivery milestones. API calls must bind context at the project level to prevent cross-project data confusion. Data sources are dispersed, so APIs must support pulling data from multiple sources. They must adapt to return structures from different formats such as ERP and supplier systems. The per-order or weekly update rhythm requires APIs to support both on-demand triggering and scheduled synchronization modes. A single call must cover all fields for a single purchase order to prevent errors in model verification and serial number registration caused by truncated data. At the same time, due to the risks of equipment mismatching and discrepancies between book and actual inventory, API return fields must undergo strict verification to ensure consistency between acceptance slips and serial number list fields.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Configure as a Bearer token format with the docking key included | Complies with general authentication specifications for external system docking, ensuring data transmission security |
| `variables` | Pass purchase order number, project ID, and equipment serial number | Ensures API calls are linked to specific delivery processes, preventing cross-order data confusion |
| `responseData` | Verify that returned fields match local acceptance slip fields | Ensures accuracy of delivery acceptance data, preventing equipment mismatching |
| Timeout setting | 60 seconds | Adapts to standard response times for ERP and logistics systems, avoiding blocking of delivery workflows |
| Retry mechanism | Retry 2 times after failure, with a 10-second interval | Addresses scenarios such as temporary network fluctuations or temporary unavailability of supplier APIs |
| Field mapping rules | Map supplier shipping document fields to local acceptance slip fields | Unifies formats for multi-source data, simplifying model verification and configuration work |

## Three common mistakes
- Phenomenon: The API call returns a 403 Forbidden status code, or an authentication failure prompt is displayed. Cause: The `Authorization` header is not configured correctly, or the token format does not meet the requirements of the docking system.
- Phenomenon: The serial number field returned by the API call is empty, or the matching result does not match the actual delivered equipment. Cause: Correct project ID or purchase order number is not passed via `variables`, causing the API to not link to data for the corresponding project.
- Phenomenon: An error occurs when executing a query operation with variable parameters, but no error occurs when executing manually. Cause: Variable parameters are not processed for compliance, causing special characters to destroy the query syntax structure.

## How to confirm the configuration is complete
- Call the test API, check whether the fields returned in `responseData` match the core fields of the local purchase order.
- Pass test variable parameters, confirm that the API can correctly link to delivery data for the corresponding project, with no cross-order data confusion.
- Simulate temporary network fluctuations, verify whether the retry mechanism triggers according to preset rules, and confirm that valid data is returned normally after the API recovers.
- Check the `Authorization` header configuration, confirm that the key has not been leaked, and that it meets the authentication format requirements of the docking system.
