# Technical Documentation and Interface Q&A for Supply Chain Security and Open Source Dependency Governance: Citation Sourcing and Traceability

## What this category of data looks like
This category of data primarily comes from package managers, code repositories, public vulnerability databases, and license databases. Its update frequency is daily or upon each version release. Daily produced documents include SBOM lists, dependency risk reports, license lists, and repair work orders. Data fields include third-party component names, version numbers, vulnerability IDs, license types, risk levels, and no additional fabricated statistical figures.

## Constraints imposed on citation sourcing and traceability by these characteristics
Data sources for this category are scattered, and update rhythms are flexible. The citation traceability link must adapt to identification rules across multiple data sources. Daily document fields vary widely, so traceability requires matching corresponding fields for different document types such as SBOM lists and risk reports. Data updates occur frequently, so cited content must synchronize with the latest status of the corresponding data source to avoid citing expired dependency risk information. At the same time, the accuracy of traceability results directly affects dependency governance decisions. Incorrect citations may lead to high-risk dependencies being deployed or license violations.

## How to configure settings
The following configurations apply to FastGPT v4.17.0. The citation traceability logic can be adjusted using three core parameters: `quoteMaxToken`, `responseData`, and `detail`.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum citation token count | `800–1200 token` | Adapts to the field length of documents such as SBOM lists and dependency risk reports, avoiding truncation of critical citation information |
| Return data scope | Only associated document metadata | Focuses on dependency data related to supply chain security, reducing irrelevant output |
| Detail display level | Full | Retains core fields such as component names, version numbers, and vulnerability IDs, ensuring traceability information is verifiable |
| Citation source matching rule | Match by component version | Adapts to the data source identification rules of package managers and code repositories, avoiding matching errors |
| Citation mark format | Hide mark content | Avoids redundant citation mark text appearing in output |
| Citation update synchronization frequency | Synchronize daily | Adapts to the update rhythm of data in this category, ensuring cited content is up to date |

## Three common misconfigurations
- Phenomenon: Generated responses contain forged citation IDs with no corresponding source documents. Cause: Correct data source matching rules are not configured, so the system cannot associate real SBOM or risk report data.
- Phenomenon: Output content includes the phrase "Citation Mark: [1]". Cause: The citation mark display format is not adjusted, retaining the default redundant mark content.
- Phenomenon: Generated repair work order files retain unclosed citation information. Cause: No filtering rules for citation content are configured in the workflow, leading to redundant information being written to the output file.

## How to confirm correct configuration
- Initiate an interface Q&A that includes third-party dependency component names. Check if the returned results only associate real documents such as SBOM and risk reports.
- Review output content to confirm no undefined citation marks or forged citation IDs appear.
- Generate a repair work order file in the workflow. Check that the file contains no redundant citation mark information.
- Compare the latest update time of the data source. Confirm that the timestamp of cited content is synchronized with the data source.

The values provided are common starting points and should be measured against the reader's own samples.
