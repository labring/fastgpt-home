# Technical Documentation and API Q&A for Independent Innovation Replacement Adaptation: Knowledge Base Retrieval and Recall

## What data falls under this category
The data for this category primarily comes from existing system inventories, domestic software and hardware catalogs, test environments, and publicly available manufacturer materials. Daily produced documents include adaptation lists, compatibility test reports, migration plans, and issue logs. Data update frequency is once per project or once per quarter. Document structures include fields such as software and hardware model, version number, compatibility status, test date, and migration steps. There is no unified fixed format template: some documents are structured tables, while others are unstructured descriptive text.

## What constraints do these characteristics impose on knowledge base retrieval and recall
Since data is managed independently per project and has a long update cycle, retrieval scope must be strictly limited to avoid cross-project data confusion. The diversity of document structures requires retrieval methods to accommodate both structured field matching and unstructured text matching needs. Single-project data scale fluctuates greatly, so the number of recalled results must be flexibly adjusted to balance efficiency and coverage. Additionally, compatibility-related queries require precise matching of key information such as version numbers and models; basic vector retrieval cannot guarantee sorting accuracy.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `collectionIds` | Fill in the knowledge base ID bound to the current independent innovation replacement adaptation project | Limit retrieval scope to only cover adaptation documents for the current project, avoiding interference from irrelevant data in recall results |
| `searchMode` | "vector+keyword" hybrid mode | Accommodate mixed document types of structured tables and unstructured descriptions, matching both keywords and semantic vectors |
| `limit` | Top 10-15 entries | Balance single-project data scale and retrieval efficiency, avoiding increased latency caused by excessive recall |
| `usingReRank` | Enabled | Improve sorting accuracy for key information such as compatibility version numbers and hardware models, optimizing the display order of high-match results |
| `datasetSearchUsingExtensionQuery` | Enabled | Automatically expand synonym queries related to adaptation, covering similar expressions such as "domestic replacement" and "independent innovation migration" |
| `similarity` | 0.75-0.85 | Filter low-match irrelevant results, retaining documents highly relevant to the independent innovation replacement adaptation scenario |

## Three common mistakes
- Scenario: Instances deployed on Alibaba Cloud experience retrieval timeout. Cause: The `limit` parameter was not adjusted based on project data scale, and excessive recall exhausted computing resources
- Scenario: Specified row content from XLSX files in the knowledge base cannot be read. Cause: Corresponding file type content parsing rules were not configured, or the retrieval scope did not cover text extraction results from the files
- Scenario: Version numbers in compatibility test reports are sorted incorrectly. Cause: `usingReRank` was not enabled, and sorting relied only on semantic matching from basic vector retrieval

## How to confirm configurations are correctly set
- View the knowledge base binding configuration in the FastGPT v4.17.0 backend, confirm that `collectionIds` only includes document collections for the current independent innovation replacement adaptation project
- Submit a test query containing specific software and hardware models, check that the returned results include adaptation document content for the corresponding project
- Test retrieval response latency, confirm it meets the project's preset threshold of under 5 seconds
- Verify that after enabling `usingReRank`, high-match compatibility results appear at the top of the display list
