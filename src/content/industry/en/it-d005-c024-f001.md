# Technical Documentation and API Q&A for Information Feed Ad Creative Testing: HTTP APIs and External Systems

## What This Category's Data Looks Like
The core data for this category comes from advertising delivery platforms, internal asset libraries, user interaction and conversion data, with updates typically occurring daily or weekly. Daily produced documents include creative scripts, asset test sheets, delivery data reports, and iteration checklists. Fields include creative asset type, variable combinations, delivery time slots, conversion metrics, and more, with units mostly being counts, yuan, characters, and seconds. Data centers on test variables for image-text and video creative assets. Multi-source data must be synchronized to complete fatigue assessment and effect summarization. The overall data structure is dynamically adjusted with test iterations, and differs significantly from the keyword management data structure of search ads.

## Constraints Imposed on HTTP APIs and External Systems
Multi-source data requirements mean APIs must adapt to the authentication rules of different advertising platforms, to avoid data pull failures caused by incorrect authentication configurations. Daily or weekly update cycles require API call frequencies to match the data update period, preventing excessive calls from triggering platform rate limits. Diverse document structures require API parameters to pass different types of test variables, ensuring that creative scripts, test variables, and other information can be accurately identified. Risks of asset non-compliance require API response content to include compliance check fields, to quickly locate non-compliant assets.

## How to Configure Settings
This document is written based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `Authorization` | Use the `Bearer Token` format, carrying a valid token assigned by the advertising platform | Adapt to the authentication rules of multiple advertising platforms, ensuring APIs can normally pull delivery data |
| `variables` | Pass 10–50 creative variable combinations, including asset types, copy variants, and delivery targeting parameters | Match the quantity range of test variables within this category, ensuring APIs can handle batch test requirements |
| `responseData` | Specify return fields for click-through rate, conversion cost, and compliance status | Filter non-essential data, focusing on core metrics for creative testing |
| Call Frequency Limit | 100 requests per day | Match the daily data update cycle, avoiding triggering advertising platform rate limits |
| Timeout Setting | 60 seconds | Adapt to the average response time of advertising platform APIs, preventing test task interruptions |
| Batch Parameter Upper Limit | Do not pass more than 20 sets of test variables per request | Balance API load and test efficiency, avoiding request failures caused by overly long parameters |

## Three Common Configuration Mistakes
- Calling the audio asset upload API returns a 400 error, with the `responseData` field empty. The format and storage path parameters for audio assets were not specified in `variables`, causing the API to fail to recognize the upload request.
- After importing a workflow template, the interface shows success, but the workflow has no nodes. The authentication token for the corresponding advertising platform was not configured in `Authorization`, causing external resources relied on by the template to not be pulled correctly.
- After calling the API, no text embedding status query entry is returned. The status query field for embedding tasks was not specified in `responseData`, causing the corresponding information to not be included in the results.

## How to Confirm Configuration is Complete
- Call the authentication API, verify that the format and token content of the `Authorization` header are correct after a valid token is returned.
- Pass a set of test variable combinations to the API, check that the `variables` field format meets preset requirements.
- Initiate a test request, confirm that the `responseData` return fields include core delivery metrics and compliance check results.
- Simulate daily call frequencies, confirm that the API does not trigger rate limit prompts and that returned data is complete.
