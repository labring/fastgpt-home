# Technical Documentation and API Q&A for Shift Scheduling and Handover: Knowledge Base Retrieval and Recall

## What the data for this category looks like
Data for this category originates from scheduling systems, fault tickets, monitoring alerts, and organizational contact lists. Update frequency is daily or weekly. Daily documents include shift schedules, handover records, escalation contact lists, and daily shift reports. Fields include shift time periods, responsible person name and contact information, unresolved fault items, and escalation chain contacts. Each document links to a specific shift cycle and corresponding operations team, with no extra redundant statistical fields.

## Constraints on knowledge base retrieval and recall
This category’s data comes from multiple dispersed sources and has a high update frequency. Knowledge base retrieval must support field alignment matching across multiple data sources to avoid retrieving invalid information across cycles or teams. Different document types (shift schedules, handover records) have structural differences. Recall processes must filter results by document type to ensure returned shift time periods and contact information match the current query scenario. Unresolved items and escalation chains have strong timeliness. Retrieval must limit the update time range of returned data to prevent use of expired handover content.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Matches precise fields such as shift time periods and contact information, to avoid retrieving irrelevant historical shift records |
| `limit` | Top 6 entries | Covers core information for a single round of shift handover, to avoid excessive results interfering with judgment |
| `searchMode` | hybrid | Combines keyword and semantic matching, adapts to structured data exported from scheduling systems and free-form handover records |
| `usingReRank` | Enabled | Reorders retrieved results by relevance to the query, to ensure key information such as unresolved items and escalation chains appears at the top |
| `datasetSearchUsingExtensionQuery` | Enabled | Optimizes colloquial queries related to shifts, such as translating "who is on duty tonight" into structured retrieval terms |
| `collectionIds` | Bound to dedicated collections per operations team | Isolates shift data for different operations teams, to prevent cross-team information disclosure or incorrect retrieval |

## Three Common Mistakes
- After upgrading FastGPT v4.17.0, calling knowledge base Q&A returns a 404 error. Cause: The `collectionIds` parameter bound to the dataset was not updated. Collection IDs from older versions become invalid after the upgrade.
- Retrieving shift information returns empty results. Cause: `datasetSearchUsingExtensionQuery` was not enabled, so colloquial queries such as "who is on duty tomorrow" cannot be translated into structured retrieval terms.
- Retrieved results include expired historical shift records. Cause: No data update time filtering rules were configured, leading to retrieval of old shift data older than 7 days.

## How to Confirm the Configuration Is Correct
- Submit a query that includes specific shift time periods and responsible person names, and check whether the returned results include the core fields of the corresponding document.
- View retrieval logs to confirm that parameters such as `searchMode` and `usingReRank` take effect as configured.
- Submit a query for an expired time period, and confirm that documents beyond the update cycle are not retrieved.
- Submit the same query across multiple operations teams, and confirm that only shift data from the current operations team is returned.

The values provided are common starting points and should be measured against applicable deployment samples.
