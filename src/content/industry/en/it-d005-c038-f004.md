# Technical Documentation and API Q&A for Change Management and Release Windows: Vector Models and Indexes

## What Data for This Category Looks Like
This category’s data primarily comes from change management systems, CI pipelines, monitoring data, and business calendars. Daily documentation includes change requests, risk assessments, release window plans, rollback plans, and similar content. Update frequency is weekly or triggered by each individual change. Documents include structured metadata such as change ID, window time period, and risk level, plus unstructured text content. Field units include time measured in hours or days, level markers for low/medium/high risk, string IDs, and more. There is no fixed standard length for individual documents. Single document content ranges from hundreds to thousands of characters.

## Constraints on Vector Models and Indexes
Data for this category comes from scattered sources and has inconsistent update schedules. This requires vector indexes to support incremental updates and metadata-associated retrieval. Documents include structured time fields and risk level tags. Index configurations must balance semantic recall for unstructured text and precise filtering for structured fields. Semantic relevance for change-related content is strong, such as historical changes for a given window or rollback plans for similar risks. Index recall accuracy directly impacts subsequent risk rating and approval efficiency. Frequent change submissions also require incremental synchronization capabilities for index tasks. This avoids performance losses from full index rebuilding.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Aligns with the paragraph length of change documents, avoids semantic breaks within chunks, and ensures each chunk has complete semantic meaning |
| Overlap Length | 100–200 characters | Preserves contextual connections across chunks, ensures semantic integrity for cross-paragraph content such as change window time periods and risk association descriptions |
| Single Search Limit | Top 8 results | Matches the typical volume of change management data, balances retrieval efficiency and coverage of historical change data |
| Maximum Context | 6000 tokens | Meets retrieval and splicing requirements for long texts such as risk assessments and rollback plans, and satisfies context length requirements for Q&A scenarios |
| Similarity Threshold | 0.75–0.85 | Filters low-relevance historical change data, improves the accuracy of retrieval results, and avoids irrelevant content interfering with risk judgments |

## Three Common Misconfigurations
- Symptom: Index tasks remain in the "indexing" state and fail to become ready. Cause: Environment variables `AIPROXY_API_ENDPOINT` (root address of the AI Proxy service, do not append paths such as /v1 or /chat/completions) and `AIPROXY_API_TOKEN` (AI Proxy admin token, must match the AI Proxy server configuration and cannot be empty) for the App/Admin server are not correctly configured. This causes App/Admin service startup verification failures or abnormal vector model call links.
- Symptom: Knowledge base retrieval speed is much lower than expected. Cause: Chunk length is set too large or the single search limit is too high. This causes the computational load of vector retrieval to exceed a reasonable range, extending retrieval time.
- Symptom: Index entries in the dataset automatically increase repeatedly. Cause: No deduplication rules are configured for incremental indexing, causing duplicate-submitted change documents to generate multiple index entries.

## How to Verify Proper Configuration
- Check the App/Admin server environment variables for FastGPT v4.17.0. Confirm that `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are correctly configured and not empty.
- Upload a small change document as test data, initiate an index task, and check whether the index status changes to ready within a reasonable time frame.
- Submit a query about change windows or risk assessments, and verify that the relevance of returned retrieval results falls within the set similarity threshold range.
- Review vector model call logs, confirm there are no frequent timeouts or error messages, and verify that the model call link is working normally.

The values provided here are common starting points, and should be evaluated against the reader’s own samples.
