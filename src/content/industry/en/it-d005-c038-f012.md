# Technical Documentation and API Q&A for Change Management and Release Windows: Document Parsing and Chunking

## What Data for This Category Looks Like
This category's data primarily comes from change management systems, CI pipelines, monitoring data, and business calendars, with an update frequency of weekly or per change cycle. Commonly used documents include four types: change requests, risk assessments, launch window plans, and rollback plans. The document structure is fixed, with clear fields such as section titles, execution periods, risk levels, and approval statuses. Some documents include historical operation records and attachment content. Overall, the data is mostly structured or semi-structured.

## What Constraints Do These Characteristics Impose on the Document Parsing and Chunking Link?
The fixed hierarchical structure of change documents requires that the parsing and chunking process retain section association information, to avoid losing context after splitting which would lead to inaccurate retrieval. The high update frequency means the parsing process must have reasonable response speed to avoid delaying change workflow progress. Data from multiple sources includes common office formats such as PDF and DOCX, so parsing rules for different document types need to be adapted. Some documents include historical records and attachments, which imposes requirements on file upload and parsing capacity limits. These characteristics together determine that chunking rules must balance content completeness and retrieval accuracy, while adapting to the parsing needs of multi-format documents.

## How to Configure the Settings
| Configuration Item | Recommended Setting | Rationale |
| ---|---|--- |
| `chunkSize` | 800–1200 characters | The body length of a single section in change documents is moderate. This range can retain complete business context, avoiding overly fragmented or redundant chunks |
| `chunkSplitter` | Split by section title + paragraph | Change documents have clear section hierarchies. Splitting by this rule retains section association information, improving context accuracy during RAG retrieval |
| `customPdfParse` | Enabled | Most change documents are formal PDF files. Enabling this allows accurate extraction of text and layout structure, avoiding loss of key fields |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | Some change documents include historical records and attachments. This capacity covers file upload requirements in most business scenarios |
| `PARSE_FILE_TIMEOUT_SECONDS` | 300–600 seconds | Parsing large change documents takes a long time. This range avoids interrupting the parsing process due to timeout, ensuring complete processing of change documents |
| `chunkSettingMode` | Manual configuration | The structure of change documents is fixed. Manual configuration can accurately match the business's retrieval and chunking needs, adapting to usage habits in different scenarios |

## Three Common Mistakes
- Symptom: Uploading change documents in the local frontend environment parses normally, but when uploading in the server environment, the document parsing node returns a 404 error, and the file content cannot be read. Cause: The file upload path configuration in the server environment differs from the local configuration. The parsing node cannot locate the uploaded file storage directory.
- Symptom: When deploying Qwen3-14B with Vllm 0.10, response fields cannot be extracted from the parsing results of PDF change documents. Using Qwen2.5-14B allows normal extraction. Cause: Different large models have varying adaptability to parsed text formats. Some models cannot support specific layout and field structures present in change documents.
- Symptom: After uploading a DOCX-format change request document, RAG retrieval results only include the body content, without the corresponding section title information. Cause: The chunking rule for splitting by section title has not been configured. The parsing process did not retain the document's hierarchical structure.

## How to Confirm the Configuration Is Complete
- Log in to the FastGPT v4.17.0 console, upload a standard change request document, and view the parsed chunk results. Confirm that each chunk includes the corresponding section title and body content.
- Upload a change document larger than 500 MB, confirm that the parsing process does not trigger a timeout error, and that RAG retrieval can be initiated normally after parsing is complete.
- Test change documents in PDF and DOCX formats, confirm the text completeness and structural accuracy of the parsing results, with no obvious content loss.
- View the server's file storage directory, confirm that uploaded documents have been saved correctly, and that the parsing node can normally access files in this directory, with no permission or path errors.
