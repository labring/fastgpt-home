# Technical Documentation and API Q&A for Security Product Rule Operations: Citation Sources and Traceability

## What data looks like for this category
Data for this category primarily comes from WAF, IDS, firewalls, and threat intelligence platforms. Updates occur daily or when triggered by protection events. Daily produced documents include rule change tickets, block logs, false positive analysis reports, and policy rollback records. Each data entry includes fields such as rule identifier, block timestamp, associated business domain, and false positive trigger conditions. There are no unified fixed units, and field formats adjust based on the corresponding data source. Typical users include security operation engineers, WAF or IDS product administrators, and SOC teams. Core work revolves around protection policy maintenance and false block resolution.

## What constraints do these characteristics impose on the citation sources and traceability link?
Data sources are scattered across multiple types of security devices and intelligence platforms. The citation traceability link must associate unique identifiers across data sources to avoid rule confusion between different devices. The high-frequency update schedule requires traceability chains to support real-time or near-real-time version verification, matching rule changes triggered daily or by protection events. Diverse document types require traceability logic to adapt to different field structures. For example, extract rule IDs from block logs, and locate policy versions from change tickets. The high-risk nature of this category requires traceability results to accurately bind specific protection events and rule entries, supporting traceability for false positive review and policy rollback.

## How to configure settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | `800–1200 token` | Matches the single-entry content length of documents in this category (block logs, change tickets), avoids truncating critical rule IDs and event details |
| Single search citation limit | Top 3–5 entries | Core data in this category has few associated entries per item. Too many citations add context redundancy and reduce retrieval efficiency |
| `detail` | Enabled | Requires returning full fields of the data source, such as rule version, block time, to support traceability accuracy |
| Citation data merging and sorting rule | Sorted in descending order by event occurrence time | Work in this category requires prioritizing association with latest block events and rule changes, matching the priority of daily review |
| `responseData` | Return original data source identifier | Binds specific WAF/IDS device IDs and log entries, completing the closed-loop traceability chain |

## Three common configuration mistakes
- Setting `quoteMaxToken` to too small a value, such as `300 token`, causes returned block logs and rule change ticket content to be truncated. Only partial rule IDs display in the interface, preventing complete traceability. This occurs because the value does not match the single-entry content length of documents in this category, and the long-text requirements of false positive analysis reports are ignored.
- Not setting citation rules sorted by event time, leading to returned citation entries mixing old rule changes and latest block events. It becomes difficult to quickly locate the latest policy adjustments corresponding to current false positives. This occurs because generic similarity sorting is used incorrectly, without adapting to the business logic of prioritizing latest protection events in this category.
- In multi-class workflows, citation fields of different knowledge bases are not unified, leading to duplicate rule entries in merged traceability results that cannot be associated with specific device logs. This occurs because cross-knowledge base data source identifier mapping is not aligned, and the scattered multi-device data feature of this category is ignored.

## How to confirm configurations are properly set
- Initiate test Q&A that includes a specific rule ID, verify whether returned citation results include corresponding device identifiers and event timestamps, confirming the traceability chain is complete.
- Adjust the value of `quoteMaxToken`, verify whether long-text block logs are returned completely without truncation.
- Trigger a workflow that calls multiple knowledge base classifications, verify whether citation entries returned by different knowledge bases have unified data source identifiers, with no duplicate or unassociated entries.
- Inspect the citation module in the FastGPT v4.17.0 Q&A interface to confirm that original data sources can be located via citation entries, verifying traceability operability.
