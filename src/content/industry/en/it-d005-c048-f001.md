# Technical documentation and interface Q&A for security monitoring and SOC on-duty: HTTP interfaces and external systems

## What data for this category looks like
Data for this category comes from SIEM, EDR, NDR, and external threat intelligence sources, with an update frequency of real-time or daily. Daily processed documents include alarm disposal sheets, duty logs, threat intelligence notifications, daily and weekly reports. Single alarm entries include fields such as alarm time, source IP, target port, threat level, and disposal status. Duty logs include fields such as duty period, number of alarms, and disposal results. Weekly reports summarize total weekly alarms, escalation dispatch times, and other content.

## Constraints imposed by these characteristics on HTTP interfaces and external systems
Since this category's data comes from multiple types of security devices and intelligence sources, HTTP interfaces must support pulling multi-source data and be compatible with return formats of different devices. Real-time updated alarm data requires interface call delay to meet business response requirements. Daily batch-updated documents must support resumable transfers to avoid repeated pulling. Documents such as alarm disposal sheets and duty logs include structured fields, so interfaces must support filtering and pulling data within a specified range by fields such as alarm time and threat level. Because the consequences of errors include missed real attacks, interfaces must have retry mechanisms and exception reporting capabilities to ensure uninterrupted data synchronization.

## Configuration settings
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| Interface authentication configuration | Use the `Authorization` parameter to carry a Bearer Token | Adapts to the authentication requirements of most SIEM and EDR devices, and ensures the security of interface calls |
| Variable replacement rules | Bind the `variables` parameter according to document field names | Adapts to structured fields in alarm disposal sheets and duty logs, ensuring accurate variable replacement |
| Return data format | Specify `responseData` as structured JSON format | Facilitates parsing of fields such as alarm time and threat level by security operation systems, improving analysis efficiency |
| Call timeout period | 300–600 seconds | Adapts to the delay requirements of real-time alarm pulling, avoiding alarm misses caused by timeouts |
| Single pull limit | First 100 entries | Matches the single-batch processing volume of daily analysis for SOC on-duty work, avoiding data overload |
| Retry times | 3 times | Responds to temporary network fluctuations that cause interface call failures, ensuring the stability of data synchronization |

## Three common mistakes
- Phenomenon: Preset variables do not return correctly in the text splicing results of an API call workflow, while variables can be spliced correctly during debugging. Cause: Structured service fields are not passed through the `variables` parameter, or the parameter format does not meet interface requirements.
- Phenomenon: Clicking a knowledge base link returned by a call interface pops up an error "Only support .txt, .m". Cause: The returned `responseData` contains resource links in non-permitted formats, or invalid links are not filtered.
- Phenomenon: The scheduled synchronization interface for alarm data does not trigger, or synchronized data is incomplete. Cause: A reasonable call timeout period is not set, or the retry mechanism does not take effect, causing a failure to re-initiate after a single call fails.

## How to confirm configuration is complete
- Call the interface and pass a legitimate `variables` parameter, check whether the returned result contains expected variable replacement content.
- View the `responseData` format returned by the interface, confirm that all fields meet the parsing requirements of security operation systems.
- Simulate temporary network fluctuations, verify whether the interface retry mechanism triggers normally and completes data synchronization.
- Check whether the `Authorization` parameter is carried correctly, ensure that alarm data can be pulled normally after authentication is passed.
