# Technical Documentation and API Q&A for Customer Onboarding and Tenant Initialization: Vector Models and Indexes

## What Data for This Category Looks Like
Data for this category comes from CRM systems, contract orders, identity management systems, and product backends. The update frequency is per order or daily. Daily generated documents include onboarding application forms, tenant configuration sheets, administrator account lists, and delivery confirmation forms. Core fields include tenant unique identifiers, customer entity information, permission configuration scopes, administrator account information, configuration effective time, and similar fields. There are no fixed statistical numeric fields. All data is generated around the onboarding and initialization process for a single tenant.

## What Constraints These Characteristics Impose on Vector Models and Indexes
Scattered data sources and per-order updates require vector models to support unified mapping of cross-system fields. This avoids insertion failures caused by field format differences. The timeliness requirements of the tenant initialization process mean index rebuilding must balance efficiency and accuracy. Full scans cannot be triggered frequently. Data volume grows linearly with the number of tenants. Index sharding and recall logic must adapt to the configuration scale of a single tenant. This avoids overall process blocking caused by abnormal single-tenant data volume. Errors will directly affect customer login and delivery acceptance. The vector insertion verification link must cover all core configuration fields.

## How to Set Configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Matches the average length of single records in documents such as tenant configuration sheets and onboarding application forms, avoids information fragmentation within chunks |
| Similarity Threshold | 0.75–0.85 | Distinguishes valid permission configurations from irrelevant redundant fields, adapts to the field format characteristics of identity management systems |
| Single Recall Limit | Top 10 entries | Controls the volume of permission verification requests during tenant initialization, avoids process timeouts |
| `defaultToken` | 2000 token | Adapts to the text length of delivery confirmation forms, ensures context completeness |
| `maxToken` | 4000 token | Reserves processing space for full tenant initialization configuration |
| Reranking | Calibrated based on actual measurements | Performs sorting optimization for cross-system fields from scattered sources, improves matching accuracy |

## Three Common Mistakes
- A 60-second timeout occurs when switching knowledge base indexes. Incremental update logic was not used during index rebuilding, and full scans of scattered customer data were performed. This causes processing time to exceed the threshold.
- The knowledge base has a small content volume but stays in a training or rebuilding state for an extended period. The configured chunk length is too small, and the rule to trigger rebuilding based on incremental changes is not enabled. This causes the system to repeatedly run full rebuilding processes.
- Batch index addition request parameters do not match tenant configuration fields, and no unified index creation rules are specified. Parameters were not adjusted per the field mapping rules of onboarding application forms, and it was not clarified whether to generate independent vectors for each document or a unified index. This results in disorganized inserted data and failure to properly associate with the corresponding tenant.

## How to Confirm Configurations Are Set Correctly
- Submit a test tenant onboarding request. Check the vector insertion logs in FastGPT v4.17.0. Confirm that all fields from CRM and identity management systems have been properly chunked and vectorized.
- Trigger an index rebuilding operation. Check the system status page. Confirm that rebuilding time meets the preset threshold, and no persistent timeout alerts are present.
- Verify batch index request parameters. Ensure they fully match the field formats in tenant configuration sheets, with no missing or incorrectly mapped fields.
- Simulate a permission verification vector retrieval. Confirm that recall results match the configured permission scope, with no abnormal fields included.
