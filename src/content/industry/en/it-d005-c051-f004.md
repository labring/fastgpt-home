# Technical Documentation and API Q&A for Customer Data Import Migration: Vector Models and Indexes

## What Data for This Category Looks Like
The typical users of this category are implementation consultants, data implementation engineers, and customer IT liaisons. Data typically originates from customer legacy systems, CSV or Excel templates, database exports, and product import logs. Daily supporting documents include data templates, migration plans, field mapping tables, and migration verification reports. Data update frequency varies per order or is irregular. Single-batch data volume fluctuates based on customer business scale. Fields cover core customer business fields, import status, error codes, and some fields have clear units.

## Constraints Imposed on Vector Models and Indexes
Data sources for this category are diverse, including structured database exports, semi-structured tables, and unstructured business documents. Vector models must adapt to text vectorization for different formats. Data updates have no fixed cycle and are processed in single batches. Indexes must support incremental updates to avoid resource consumption from full reconstruction. Field mapping relationships change based on customer customization needs. Indexes must retain associated metadata of original fields to facilitate subsequent import verification and problem tracing. Single-batch data volume varies widely. Index sharding must have flexible adjustment capabilities to adapt to import tasks of different scales.

## How to Configure Settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Adapt to the business text length of customer imports, avoid single chunk tokens exceeding model input limits |
| Overlap Length | 100–200 characters | Retain contextual association between chunks, reduce impact of semantic fragmentation on retrieval accuracy |
| Similarity Threshold | 0.65–0.85 | Filter low-match retrieval results, adapt to field matching and sample verification requirements for imported data |
| `defaultToken` | 4096 | Adapt to standard input token limits of most open-source vector models, ensure complete vectorization of basic text |
| `maxToken` | 8192 | Support long-text import documents such as complete migration plans or field mapping tables, avoid truncation of key content |
| Single Search Limit | Top 10 entries | Control retrieval return volume, adapt to sample verification and problem troubleshooting requirements for imported data |

## Three Common Misconfigurations
- Search tests return errors, such as interface 500 status codes or "vector dimension mismatch" prompts. The cause is that the newly accessed embedding model does not match the vector dimension set in the index configuration, and the index dimension parameters are not updated synchronously.
- Only vector fields can be queried in the database, and the original document content corresponding to the vectorization cannot be found. The cause is that the index's original text associated storage configuration is not enabled, and only vector data is written.
- When using the bge-m3 model, semantic retrieval scores are generally high, such as scores exceeding 0.9. The cause is that basic cleaning is not performed on imported dirty data, or the chunk length is set too small, leading to excessive semantic fragments that amplify similarity calculation results.

## How to Verify Proper Configuration
- Import one test business data item, run the vector generation task, and check the task log to confirm token usage does not exceed the `maxToken` configuration.
- Run a retrieval test, and check whether returned results include both vector data and associated information of the original imported text.
- Adjust the similarity threshold, and observe whether the number of retrieval results changes according to expected matching logic.
- Import multiple batches of test data in different formats, and confirm that the index can complete incremental updates normally with no duplicate or missing data.

The values provided are common starting points and should be validated against local test samples.
