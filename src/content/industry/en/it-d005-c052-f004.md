# Technical Documentation and API Q&A for Customer Permissions and Organizational Structure Configuration: Vector Models and Indexes

## What data for this category looks like
This category's data comes from customer HR systems, identity directories, product backends, and audit logs. Four types of documents are generated regularly: permission matrices, organizational structure tables, role configuration records, and permission change tickets. Data updates occur per ticket or irregularly. Core fields include department hierarchy, role-permission mapping relationships, change times, and operators. The data structure changes dynamically with customer organizational adjustments, and there is no fixed batch update cycle.

## What constraints these characteristics impose on vector models and indexes
Multi-source heterogeneous data sources require indexes to support mixed encoding of structured fields and unstructured text. This adapts to the different formats of permission matrices and organizational structure tables. Irregular update rhythms require configuring incremental synchronization mechanisms. This avoids resource consumption and delays caused by full reconstruction. The strongly correlated characteristics of department hierarchy and permission mapping require vector models to prioritize learning semantic associations between hierarchy relationships and permission fields. This ensures that encoded data accurately captures permission boundaries. The traceability requirement of audit logs requires indexes to retain metadata fields for permission verification. At the same time, data volume fluctuates greatly. This requires configuring an adaptive index sharding strategy to balance retrieval performance and storage costs.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxToken` | 800–1200 token | The semantic length of a single permission mapping or hierarchy description in the core documents of this category falls within this range. This avoids truncating critical permission association information |
| Chunk overlap length | 50–80 characters | Adapts to the nested hierarchy structure of organizational structure tables. This retains department association semantics across chunks |
| Single recall limit | Top 10 entries | Matches the fine-grained characteristics of permission configurations. This avoids recalling irrelevant permission entries that interfere with matching accuracy |
| `defaultToken` | Calibrated via actual testing | Adapts to differences in permission matrix fields across different customers. This avoids semantic matching deviations caused by fixed thresholds |
| Embedding model selection | Select open-source embedding models that support structured field encoding, such as quantized versions of the Qwen3-Embedding series | This category's data includes structured semantics of hierarchy and permission mapping. Models in this series are adapted for encoding effects of long text and structured associated semantics |
| Index shard size | 1000 MB | Balances incremental synchronization efficiency and retrieval performance for the irregular updates of this category. This adapts to data volume fluctuations for individual customers |

## Three common configuration mistakes
- Phenomenon: Retrieval results include cross-customer permission entries, with no clear permission isolation prompt. Cause: Vector indexes are not isolated based on customer tenant dimensions, leading to mixed recall of permission data from different customers.
- Phenomenon: Token count results do not match the actual configuration, triggering a `maxToken` over-limit error. Cause: Token statistics are not performed separately for structured fields in permission matrices. Non-permission text is mistakenly included in the total length.
- Phenomenon: Permission mapping errors appear after incremental index updates. Cause: Hierarchy metadata from organizational structure tables is not retained. Vector encoding loses critical semantics of department affiliation relationships.

## How to confirm the configuration is complete
- Access the vector index management interface in FastGPT v4.17.0. Confirm that the index includes three metadata fields: customer tenant ID, department hierarchy, and permission role.
- Submit a permission configuration retrieval request for a single customer. Verify that the recall results only include permission matrix entries for that customer, with no cross-tenant data.
- Simulate an incremental synchronization for a permission change ticket. Confirm that the index only updates vector data for the changed portion, and no full reconstruction process is triggered.
- Test permission description text of varying lengths. Confirm that no truncation errors related to `defaultToken` or `maxToken` appear.
