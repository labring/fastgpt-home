# Technical Documentation and API Q&A for Customer Permission and Organizational Structure Configuration: Knowledge Base Retrieval and Recall

## What the Data for This Category Looks Like
This category of data primarily comes from customer HR systems, identity directories, product backends, and audit logs. Daily generated documents include permission matrices, organizational structure tables, role configuration records, and permission change orders. Data updates occur per order or irregularly, with no fixed cycle. Most documents use structured formats and include fields such as department ID, role name, permission scope, and effective time. No additional unstructured annotation content is present. Overall data has strong interconnections, and strict matching of permission boundaries is required.

## Constraints Imposed on Knowledge Base Retrieval and Recall by These Characteristics
Data sources are scattered, and updates have no fixed cycle. Retrieval must prioritize data timeliness to avoid recalling expired permission configurations. Structured document formats require retrieval modes to support both keyword and semantic matching. Without this, permission entry matching deviations may occur. Multi-field permission data increases single-retrieval processing complexity. The number of recalled results must be limited to control verification time. Permission data has sensitivity requirements, so recalled results must strictly match the target role and department to avoid unauthorized access risks.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Adapts to the structured characteristics of permission data, filters low-relevance permission entries |
| `limit` | Top 10 entries | Controls the number of documents recalled in a single retrieval, reduces time spent verifying organizational hierarchies |
| `searchMode` | vector + hybrid | Combines semantic and keyword matching, covers multiple document types such as permission matrices and change orders |
| `usingReRank` | Enabled | Sorts recalled results by relevance, corrects retrieval deviations for structured data |
| `datasetSearchUsingExtensionQuery` | Disabled | Permission data mostly consists of structured configurations, no additional extended queries are needed to reduce model calls |
| `collectionIds` | Bind exclusive permission knowledge base collections | Isolates permission configuration data from other business documents, avoids retrieval interference |
*FastGPT v4.17.0*

## Three Common Configuration Errors
- Phenomenon: Knowledge base retrieval takes too long, with obvious return result delays. Cause: The `limit` parameter value is not restricted, recalling too many permission-related documents increases time spent on organizational hierarchy verification.
- Phenomenon: Untriggered large model call error logs appear during workflow operation. Cause: `datasetSearchUsingExtensionQuery` is accidentally enabled, generating additional query requests that trigger unconfigured model calls.
- Phenomenon: The directory structure of knowledge base documents is automatically deleted. Cause: Exclusive `collectionIds` are not correctly bound, causing the system to mistakenly merge permission configuration documents with other types of documents for processing.

## How to Verify Successful Configuration
- View retrieval logs to confirm that the number of single recall results matches the configured `limit` value.
- Simulate a permission change scenario to verify that recalled results only include configuration documents related to the target department and role.
- Run the workflow to check for unexpected large model call error logs.
- Upload test permission configuration documents to confirm that the directory structure is not automatically modified.

The values provided are common starting points and should be measured against the user’s own samples.
