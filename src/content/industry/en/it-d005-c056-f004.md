# Technical Documentation and Interface Q&A for Object Storage and Backup Services: Vector Models and Indexes

## What data for this category looks like
Data for this category primarily comes from object storage consoles, backup systems, access logs, and customer policy tables. Daily generated documents include bucket configuration details, backup policy configurations, recovery operation records, and lifecycle rule documentation.
Data updates occur daily or in real time when policies change.
Fields include bucket permissions, backup task status, recovery duration, lifecycle trigger conditions, and more. Some fields use string, boolean, or timestamp formats, with no unified fixed unit standards.

## How data characteristics impact vector models and indexing
Decentralized data sources and inconsistent update rhythms require vector indexes to support incremental synchronization for multi-source data. This avoids performance losses from full index reconstruction.
Document structures vary significantly across types. Text length and format differ widely for items like bucket configurations and backup policies. Vector splitting must adapt to diverse text fragment lengths.
Recovery records and access logs contain sensitive permission fields. Vector processing must mitigate risks of sensitive information disclosure.
Daily or real-time update frequencies require indexes to support fast updates. This ensures the timeliness of retrieved data.

## How to configure settings
This configuration applies to FastGPT v4.17.0, and is compatible with all business document scenarios for object storage and backup services.

| Configuration Item | Recommended Range | Rationale |
| ---- | ---- | ---- |
| Similarity threshold | 0.75–0.85 | Matches semantic matching accuracy for texts such as bucket configurations and backup policies, filters low-relevance results |
| Chunk length | 800–1200 characters | Aligns with typical paragraph lengths of daily documents, reduces semantic breaks across chunks |
| Overlap length | 100–150 characters | Preserves semantic continuity between chunks, prevents critical configuration items from being split across different chunks |
| `defaultToken` | 8192 | Adapts to the input upper limit of most vector models, meets processing requirements for most backup policy documents |
| `maxToken` | 16384 | Covers the longest recovery records or lifecycle rule documents, avoids truncation of critical information |
| Single recall limit | Top 10 entries | Controls the volume of retrieval results, fits the quick query scenarios of operations personnel |

## Three common configuration errors
- Phenomenon: A large number of backup log fragments unrelated to the target document appear in retrieval results, with similarity scores generally exceeding the preset range. Cause: No reasonable similarity threshold is set, leading to low-relevance texts being misjudged as high-match results.
- Phenomenon: Auxiliary permission policy logs are not included in the index scope, and relevant configuration information cannot be obtained during retrieval. Cause: Auxiliary data sources are not added to the index synchronization list, only core bucket configuration documents are synchronized.
- Phenomenon: After uploading locally vectorized backup data to the server, no matching results are returned by retrieval. Cause: The vector model input formats used locally and on the server are inconsistent, resulting in vector embeddings that cannot match index rules.

## How to confirm configuration is valid
- Upload a single bucket configuration document, initiate a retrieval request, and verify whether the similarity scores of returned results fall within the preset threshold range.
- Simulate a backup policy change operation, check the index update status, and confirm that the incremental synchronization mechanism is working properly.
- Import a set of multi-source data, verify that vector splitting and embedding results for different document types meet expectations.
- Call the interface to test the retrieval function, confirm that the number of returned results matches the single recall limit configuration.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
