# Technical Documentation and Interface Q&A for Object Storage and Backup Services: Citation Sources and Traceability
This page applies to FastGPT v4.17.0.

## What the data for this category looks like
The core data for this category comes from object storage consoles, backup systems, access logs, and customer policy tables. Update frequency is daily or real-time alongside policy changes. Daily documentation includes bucket configurations, backup policies, recovery records, and lifecycle rules. Fields include bucket name, backup task ID, recovery time, lifecycle effective period, etc. Units include GB, count, days, etc., used to describe core information about storage resources and backup workflows.

## What constraints do these characteristics impose on the "citation sources and traceability" link?
Decentralized data sources require the traceability link to associate metadata from multiple systems to ensure the integrity of cited content. Irregular update frequencies require indexes to support near-real-time synchronization, avoiding the use of outdated backup policies or storage configurations in citations. The professional nature of documentation fields requires extracting specific fields such as bucket ID and backup task identifier during citation. The high time cost of permission policy verification requires the traceability link to quickly validate access permissions. Severe consequences of errors require traceability information to be accurate and complete.

## How to set configurations

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | `800–1200 token` | Matches the average length of single paragraphs in object storage documentation, avoiding truncation of key fields such as bucket configurations and backup policies |
| `responseData` | `Return full citation metadata` | Must include core identifiers such as bucket name, backup task ID, and recovery record ID to meet traceability requirements |
| `detail` | `Enabled` | Displays specific storage paths and last update times for cited content, facilitating verification by operations staff |
| Single search limit | `Top 5 entries` | Matches the typical number of associated entries for backup task monitoring, avoiding interference from redundant data |
| Citation refresh frequency | `Every 12 hours` | Matches the daily update frequency of object storage policies, ensuring timely synchronization of metadata indexes |

## Three common mistakes
- Symptom: After increasing the value of `quoteMaxToken`, the LLM response does not display any cited content, and only knowledge base content is recalled. Cause: The full metadata return configuration for `responseData` was not enabled synchronously, causing the system to fail to extract citation identifiers.
- Symptom: Citation traceability fields are empty in results returned by external API calls, but work normally during local testing. Cause: The whitelist for citation metadata that allows external access was not configured, and access log permission verification for object storage was not associated.
- Symptom: Traceability information cannot be matched when the knowledge base associated model and application configuration model are inconsistent. Cause: Field mapping rules for citation metadata were not unified, causing output identifiers from different models to fail to align.

## How to confirm configurations are set correctly
- View the `responseData` field returned by the interface to confirm that core metadata such as bucket name and backup task ID is included.
- Adjust the value of `quoteMaxToken` to verify that the truncation length of cited content matches the preset range.
- Initiate an external API call to check whether the returned results include complete citation traceability information.
- View system logs to confirm that the extraction and display logic for citation metadata is running normally.
