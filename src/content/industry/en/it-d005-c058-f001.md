# Technical Documentation and API Q&A for Advertising Compliance Record-Keeping: HTTP Interfaces and External Systems

## What the data for this category looks like
This category’s data centers on evidence retention across the full advertising compliance workflow. Daily documents include advertising review forms, qualification attachments, delivery records, and rectification notices. Data sources include advertising platform backends, customer qualification systems, contract management systems, and public regulatory rule repositories. Data updates are triggered per individual advertising campaign or monthly cycle. Core fields include compliance numbers, qualification validity periods, delivery times, rectification statuses, and more. Archiving and storage must be completed per campaign batch.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Category data is scattered across multiple internal systems and external regulatory platforms. HTTP interfaces must meet requirements for multi-source authentication and precise field extraction. Data update cycles vary flexibly per individual advertising campaign or monthly period. Interface call frequency must match campaign rhythms to avoid high-volume invalid requests. Core data fields include highly regulatory-related content such as compliance numbers and qualification validity periods. Interfaces must support precise field filtering to reduce invalid data transmission. Since errors may result in regulatory penalties and customer liability, interfaces must include failure retry, authentication verification, and exception log recording capabilities to ensure data transmission stability and traceability.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {oneapi_key}` | Matches the authentication format of oneapi, and adapts to permission verification for advertising compliance-related interfaces |
| `variables` | `{"target_docs": ["advertising review form", "qualification attachments", "delivery records"]}` | Limits the target document types for extraction, and focuses on core category compliance data |
| `responseData` | `Only return compliance number, delivery time, rectification status, qualification validity period` | Reduces invalid data transmission, and matches core archiving requirements for the category |
| Timeout setting | 30-60 seconds | Adapts to the single-processing scale of category data, and avoids timeouts caused by fluctuations in data volume |
| Maximum documents per request | Top 5 | Matches the single-processing volume of the qualification archiving link, and balances efficiency and data integrity |

## Three common mistakes
- Returns a 401 status code: Postman calls oneapi normally but FastGPT calls fail. Cause: The `Authorization` parameter is not configured correctly, or the passed key is not bound to the corresponding advertising compliance record-keeping interface permissions.
- The content extraction node cannot call the self-built model interface. Cause: `functionCall` and `toolChoice` configurations are not correctly enabled in config.json, or supported model types are not declared.
- A locally deployed chatglm2 model cannot be selected when creating a knowledge base. Cause: The model access path in oneapi is not correctly configured in FastGPT system settings, or the used FastGPT v4.17.0 version does not enable the access switch for the corresponding model.

## How to confirm configurations are correct
- Call the FastGPT test interface, check if the returned `responseData` includes core category fields such as advertising review form numbers and delivery record times.
- Replicate the FastGPT request headers and parameters, initiate a call using Postman, confirm that the returned status code is 200 and the data meets expectations.
- View the FastGPT system logs, confirm that the `variables` parameter has correctly passed the target document types, with no parameter parsing errors.
- Trigger a simulated compliance document archiving interface call, confirm that there are no timeout or authentication failure error reports, and that complete request and return data are recorded in the logs.

The values provided are common starting points and should be evaluated against individual deployment samples.
