# Technical Documentation and API Q&A for Ad Account Opening Audit: Document Parsing and Chunking

## What This Category's Data Looks Like
The core data for this category comes from the advertising platform backend, the National Enterprise Credit Information Public Disclosure System, customer-submitted account opening application materials, and industry access rules. Daily processed documents include account opening application forms, business license scans, industry qualification certificates, account opening audit records, etc. The document structure includes both structured fields (such as unified social credit code, application date) and unstructured text (such as audit opinions, qualification descriptions). The update frequency is daily or triggered by each account opening application. Data formats vary depending on the source.

## What Constraints Do These Characteristics Impose on Document Parsing and Chunking
The diverse document types and large format differences in this category require the parsing process to adapt to mixed input of structured forms and unstructured files. The high-frequency update feature requires the parsing process to have sufficient efficiency to avoid delays affecting the account opening audit progress. Key fields such as unified social credit code and industry qualification number must be fully retained. Chunking must not split associated information across fields, otherwise it will cause errors in subsequent qualification verification links and lead to account opening failure. Inconsistent data formats from multiple sources require targeted configuration of parsing rules to ensure valid information can be extracted from files of different formats.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chunkSize` | `800–1200 characters` | This category's documents contain short fields and paragraph text. This range balances field integrity and retrieval efficiency, and avoids splitting key qualification information |
| `customPdfParse` | `Enabled` | Most qualification documents in this category are PDFs with official seals. Enabling custom parsing preserves text and layout in the seal area, preventing loss of key information |
| `PARSE_FILE_TIMEOUT_SECONDS` | `300 seconds` | This category has a large volume of batch files submitted at one time. This duration covers the parsing process for most files, avoiding audit interruptions caused by timeouts. This configuration is compatible with FastGPT v4.17.0 timeout logic |
| `chunkSplitter` | `Split by paragraph + semantic chunking` | Audit records in this category are mostly coherent paragraph-style text. Semantic chunking preserves the integrity of audit logic and improves the accuracy of subsequent Q&A |
| `UPLOAD_FILE_MAX_SIZE` | `100 MB` | The upper limit for single-batch submission of batch qualification documents in this category usually does not exceed this value, preventing upload failures from affecting the account opening process |
| `chunkSettingMode` | `Manual configuration` | The document formats in this category vary greatly. Manual configuration adapts to parsing requirements for files from different sources, avoiding insufficient compatibility of default configurations |

## Three Common Mistakes
- Upgrading the version when uploading CSV files causes an error, returning `400 Bad Request`. The cause is that the default value of `chunkSettingMode` changed after the version upgrade, and the original chunking rule configuration was not adapted.
- Attempting to connect to minerU document parsing fails, with the symptom of empty text after parsing. The cause is that `customPdfParse` was not enabled and the corresponding parsing adapter was not configured, causing the system to use the default parsing process.
- Calling the create file collection API and specifying PDF parsing parameters has no effect. The symptom is that the API return result still uses the default parsing. The cause is that the enabled value of `customPdfParse` was not correctly passed in the request parameters, resulting in the configuration not taking effect.

## How to Confirm Configuration Correctness
Uploading a single qualification PDF with an official seal and verifying that the parsed text retains key information in the seal area confirms that the `customPdfParse` configuration is effective.
Submitting batch CSV-format account opening application forms and verifying that the parsing time falls within the `PARSE_FILE_TIMEOUT_SECONDS` range confirms that the timeout configuration is reasonable.
Calling the create file collection API and checking if the returned configuration parameters include the specified `chunkSize` and `chunkSplitter` values confirms that the API configuration was passed correctly.
Testing direct upload of the original file to the large model node and checking if the node input content is the binary stream of the original file confirms that the system's default parsing process was skipped.

The values provided are common starting points and should be measured against samples relevant to the specific deployment.
