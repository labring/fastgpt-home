# Technical Documentation and API Q&A for Performance Testing and Capacity Evaluation: Citation Sources and Traceability

This document follows the configuration logic of FastGPT v4.17.0, and explains the citation traceability process for this specific scenario.

## What Data for This Category Looks Like
This category’s data originates from stress testing platforms, APM monitoring tools, database slow logs, and production traffic baselines. It updates monthly or when major platform versions are released.
Daily produced documents include stress testing plans, capacity evaluation reports, stress testing data records, and optimization suggestion sheets.
Data fields include throughput rate, response delay, resource usage, and peak concurrent count. Corresponding units are transactions per second, milliseconds, cores or GB, and count respectively.
Each data entry includes a collection timestamp and source platform identifier.

## Constraints on Citation Sources and Traceability
This category’s data comes from scattered sources, most collected automatically by systems. When conducting citation traceability, accurately link each data entry to its collection platform and timestamp to avoid mixing data from different sources.
Data update schedules are inconsistent. When citing, synchronously mark the data collection time interval to align with the version range being evaluated.
Daily documents have clear hierarchical structures: stress testing plans include preconditions, capacity reports include conclusion basis. During traceability, distinguish citation levels for different document types to avoid mistakenly associating content from optimization suggestion sheets as original stress testing data.
Fields include dedicated units. Display the corresponding unit during traceability to prevent parameter ambiguity.
Data errors directly impact business resource allocation, so traceability accuracy directly affects the rationality of subsequent decision-making.

## How to Configure Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | Adapts to the typical length of stress testing plans and capacity evaluation reports, preventing truncation of critical traceability content |
| `responseData` | Enabled | Retains original source identifiers from stress testing platforms and APM monitoring tools, ensuring traceability can locate specific collection systems |
| `detail` | Display collection timestamp | Supplements the data collection time interval, matching the inconsistent update schedule of this category’s data |
| Single recall limit | Top 3 entries | Focuses on core stress testing data and reports, avoiding redundant information that interferes with traceability accuracy |
| Maximum context length | Calibrated via actual testing, typically no more than 3500 characters | Accommodates content from multiple associated documents, preventing context overflow from disrupting traceability logic |

## Three Common Configuration Mistakes
- Enabling `responseData` still fails to display original collection sources. The cause is that the original field synchronization switch for the corresponding data source was not enabled, only summary information was activated.
- Setting a minimum relevance threshold still outputs a large number of irrelevant citations. The cause is that the single recall limit was not restricted, leading to recall of redundant stress testing data and reports beyond business needs.
- Cited stress testing data has mismatched timestamps. The cause is that the `detail` parameter was not configured to display the collection time interval, only the document update time was used, resulting in traceability confusion.

## How to Confirm the Configuration is Correct
- Initiate an API Q&A test, check if the returned content includes the configured source identifiers and timestamps to confirm traceability information is complete.
- Adjust the value of a configuration item, verify that the length of the returned content matches expectations to confirm the `quoteMaxToken` restriction takes effect.
- Test recall results under different relevance thresholds, confirm that the single recall limit configuration constrains the number of results as expected.
- Check system logs to confirm there are no truncation errors caused by overly long contexts, verifying that the maximum context length configuration is reasonable.

The values provided are common starting points and should be evaluated against the reader's own samples.
