# Technical Documentation and API Q&A for Campaign Setup: HTTP Interfaces and External Systems

## What the data for this category looks like
The data for this category primarily comes from advertising platforms, user profile databases, budget scheduling sheets, and attribution tools. Daily produced documents include campaign plans, targeting setting rules, budget allocation plans, and conversion tracking configuration items. Data update frequencies are mostly daily or triggered by adjustments for individual campaign activities. Fields include targeted audience package identifiers, budget amounts, conversion event codes, and delivery time slot parameters. Units include yuan, person-times, hours, and others. Core fields must strictly align with the interface definitions of advertising platforms.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
The data sources for this category are scattered and have significant format differences. The interface return structures of different advertising platforms vary, so HTTP interfaces must adapt to multi-source data parsing logic. Data update frequency is high, so interfaces must support high-frequency calls and set reasonable timeout periods to avoid delaying campaign setup progress. Core fields such as targeted audience identifiers and budget parameters must strictly match document definitions. Incorrect input parameter formats will prevent delivery configurations from taking effect. Failed data validation can lead to budget waste or failed campaign launch, so interfaces must include complete return value validation steps.

## How to Set Configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Carry a platform authorization token prefixed with `Bearer ` | Complies with the identity verification standards of advertising platform interfaces to ensure request legitimacy |
| `variables` | Pass a structured object containing audience package ID, budget amount, and conversion event | Matches the field definitions in campaign plan documents to ensure correct input parameter format |
| `responseData` | Extract core configuration results under the `data` field | Adapts to the return structures of most advertising platforms to quickly obtain valid delivery configurations |
| Request timeout setting | 600 seconds | Covers the interface response duration for complex targeting configurations to avoid mid-request interruptions |
| Retry count | 2 times | Balances interface stability and request efficiency to reduce the impact of temporary network fluctuations |
| Return value validation rule | Verify whether the `code` field is a success identifier | Avoids receiving incorrect delivery configurations and prevents subsequent delivery anomalies |

## Three Common Mistakes
- Symptom: The HTTP request call succeeds but the return result is empty, or expected delivery configuration fields cannot be extracted. Cause: The specified fields are not extracted as required by `responseData`, outdated return value parsing rules are incorrectly employed, and the parsing logic of FastGPT v4.17.0 is not properly adapted.
- Symptom: The interface can be called normally using Postman, but calls fail in FastGPT, returning a timeout or 403 status code. Cause: The `Authorization` parameter is not configured correctly, the token format required by the advertising platform is not carried, or the timeout setting is too short to cover the interface response duration.
- Symptom: After passing variable input parameters, the targeting configuration of the delivery plan does not take effect. Cause: A structured input parameter object is not passed via the `variables` parameter, and the parameter format does not meet the field requirements of the advertising platform, causing the interface to fail to recognize the configuration content.

## How to Confirm Configurations Are Set Correctly
- Verify the format of the `Authorization` parameter, ensure that the identity identifier required by the advertising platform is carried, and confirm by calling a test interface that returns a 200 status code.
- Validate that the fields passed in the `variables` parameter match the definitions in the campaign plan documents, and confirm by printing input parameter logs to compare field completeness.
- Check the `responseData` parsing rules to ensure that the extracted fields match the structure returned by the advertising platform, and test the parsing results by simulating return data.
- After configuring timeout and retry rules, simulate high-frequency call scenarios to confirm that there are no consecutive failures in interface calls.
