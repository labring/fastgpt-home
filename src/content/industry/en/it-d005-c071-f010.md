# Technical Documentation and API Q&A for Data Masking: Citation Sources and Traceability

## What the data for this category looks like
This category of data primarily comes from databases, data dictionaries, masking tools, and access approval systems. Updates follow batch tasks or project cycles. Daily produced documents include masking plans, field mapping tables, masking verification reports, and approval records. Document structures typically center on field rules, execution steps, and verification results as core modules. Fields cover sensitive field identifiers, masking algorithm types, execution times, approval statuses, and more. There are no unified fixed units; values adjust based on the specific business requirements of individual projects.

## What constraints do these characteristics impose on the "citation sources and traceability" link?
Data sources are scattered and linked to multiple systems, so traceability requires associating metadata from multiple data sources to avoid broken traceability information. Documents are updated in batches per project, so citations must match the latest field mapping table for the current project to prevent use of expired masking rules. Documents include compliance-related content such as approval records, so traceability must retain the complete approval chain to meet compliance audit requirements. Fields have no fixed units, so traceability requires clarifying the business meaning corresponding to the field to avoid confusion between masking configurations from different projects.

## How to configure settings

| --- | --- | --- |
| `quoteMaxToken` | `800–1200 token` | Matches the single-block content length of masking documents, adapts to model input limits |
| `responseData` | `Only return masked fields and traceability ID` | Retains only compliant and usable data, prevents leakage of original sensitive information |
| `detail` | `Enable traceability details` | Correlates and displays the complete chain of masking verification reports and approval records |
| Single search limit | `Top 3 results` | Adapts to the typical number of masking documents per project, avoids redundant recall |
| Maximum context duration | `600 seconds` | Covers query time for cross-system traceability, prevents timeouts |

## Three common configuration mistakes
- Scenario: After calling the API, the returned result is empty, and only citation source links are displayed. Cause: When configuring `responseData`, masked field return is not enabled, only the original document path is retained, and no usable Q&A content is generated.
- Scenario: After referencing a plugin in a workflow, the code execution step reports an error with a 400 status code returned. Cause: The field mapping table for the current project is not matched, and expired masking rule configurations are called during traceability.
- Scenario: Approval record fields are missing from traceability results. Cause: The `detail` configuration is not enabled, and traceability data from the access approval system is not associated, resulting in a missing compliance chain.

## How to confirm that configurations are correctly set
- Review the citation module in Q&A results, confirm that it includes associated identifiers for masking plans and field mapping tables, and verify that they match the current project's documents.
- Call the API for testing, check that the returned `responseData` field only contains masked content and traceability IDs, with no original sensitive information.
- Review system logs, confirm that traceability queries cover all associated data sources including databases, data dictionaries, masking tools, and approval systems.
- After adjusting configuration item parameters, verify that traceability details in Q&A results fully display masking verification reports and approval records.
