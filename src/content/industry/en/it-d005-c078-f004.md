# Technical Documentation and Interface Q&A for Cabinet Installation and Cabling: Vector Models and Indexes

## What Data for This Category Looks Like
The typical users of this category are IDC operations engineers, network engineers, and equipment implementation specialists. Daily processed documents include rack installation applications, cabinet cabling diagrams, port label sheets, and construction records. Data sources include DCIM systems, asset management systems, network topology files, and customer service tickets. Update frequency is per order per day: data updates trigger each time a device is added or modified. Document fields include standardized rack unit numbers, port identifiers, cable lengths, construction timestamps, and other standard fields. Cabling diagrams include vector point location information. Port label sheets contain exact matching physical connection rules.

## Constraints on Vector Models and Indexes From These Characteristics
Mixed text and semi-structured data requires vector models to support both plain text fields and formatted point location information. High-frequency incremental updates require indexes to support lightweight incremental synchronization, avoiding performance loss from full reindexing. Exact physical connection rule requirements require retrieval processes to balance fuzzy semantic matching and precise field matching. The limited data volume per ticket and high timeliness requirements require index retrieval response speed to fit real-time verification scenarios. Additionally, data errors directly cause incorrect port connections, impaired heat dissipation, or delayed customer service activation. As a result, vector retrieval accuracy and completeness requirements are higher than general use cases.

## How to Configure Settings
| Configuration Item | Recommended Value Range | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Matches the average single-paragraph length of cabinet cabling documents, prevents chunk loss caused by overly large chunks |
| Overlap Length | 100–200 characters | Preserves cross-chunk rack unit numbers and port association information, prevents critical connection rules from being split |
| maxToken | 8192 | Matches the input limit of most open-source vector models supported by FastGPT v4.17.0, avoids truncation of core fields |
| Similarity Threshold | 0.75–0.85 | Filters low-match cable labels and rack information, reduces physical connection error risks |
| Single Search Limit | Top 10 results | Balances retrieval speed and result completeness, fits real-time ticket verification requirements |
| defaultToken | 1024 | Standardizes processing of unassigned-length scattered text chunks, reduces abnormal chunk generation probability |

## Three Common Misconfiguration Issues
- Knowledge base upload status remains stuck at "Indexing" with no progress: The root cause is missing incremental index trigger configuration. Full reindexing takes too long, and cannot adapt to daily updated ticket data.
- Chunk loss occurs when chunk length is set to 3000 characters: The root cause is a mismatch with the actual single-paragraph length of the document, exceeding the `maxToken` limit of the vector model. This leads the system to automatically discard overly long text chunks.
- Embedding rate limit error occurs during vectorization: The root cause is missing adjustment of concurrent processing parameters, and unstandardized single-chunk text length without `defaultToken` limits. This causes single-chunk processing time to exceed interface thresholds.

## How to Verify Successful Configuration
- Upload a test cabinet cabling diagram document. Confirm the index status completes within 10 minutes, with no abnormal error logs.
- Review the details of split text chunks. Confirm no empty fields or truncated critical rack unit numbers or port identifiers.
- Initiate a port label matching query. Verify returned results have matching scores within the preset threshold, and response time meets real-time verification requirements.
- Simulate an incremental upload of a new construction record. Confirm the index only synchronizes new data, without requiring full reindexing.
