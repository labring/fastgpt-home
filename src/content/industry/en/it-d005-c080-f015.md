# Technical documentation and interface Q&A for desktop terminal support: Knowledge base retrieval and recall

## What the data for this category looks like
This category of data comes primarily from terminal management platforms, asset systems, user trouble reporting channels, and software repositories. Daily documents fall into four types: terminal trouble tickets, installation lists, software installation records, and remote assistance records.
Most document structures use a combination of structured fields. For example, trouble tickets include terminal serial number, fault symptom, troubleshooting steps, and software version. Installation lists include hardware model, software package name, and deployment date. Field units include pieces, times, and GB.
Data updates occur daily or synchronize with individual requests, covering the latest installation, software deployment, and trouble reporting information.

## Constraints for knowledge base retrieval and recall
The structured nature of terminal-related data requires retrieval to balance semantic matching and exact field matching. This avoids missing key information such as hardware model and software version.
Data updates daily or in real time. Recall logic must sync the latest installation records and fault handling solutions to prevent returning outdated configuration steps.
Troubleshooting a single terminal relies on limited information. Too many recall results increase filtering time for engineers. Fault reproduction and troubleshooting take significant time, so retrieval results must accurately match the current issue. This prevents irrelevant content from disrupting the troubleshooting process.

## How to configure settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` | `0.75–0.85` | Desktop terminal data mostly consists of closely related fault and installation information. A threshold that is too low introduces irrelevant peripheral or software data, while a threshold that is too high misses matching accurate troubleshooting steps. This range suits daily troubleshooting scenarios. |
| `limit` | `Top 3–5 results` | Desktop operations engineers handle single-terminal issues one at a time. Too many results increase troubleshooting time. This quantity range covers core information such as fault reproduction and driver installation. |
| `searchMode` | Vector search + keyword hybrid | Terminal data includes both text descriptions of fault symptoms and exact matching requirements for hardware models and software versions. The hybrid mode balances semantic understanding and exact field matching. |
| `usingReRank` | Enabled | In terminal fault scenarios, descriptions of similar faults have minor differences. Reranking filters results that are semantically close but do not match the current terminal model or software version, improving accuracy. |
| `datasetSearchUsingExtensionQuery` | Enabled | Desktop operations engineers’ questions often use vague phrasing, such as "printer not working". Extended queries supplement relevant content such as driver installation and port configuration, covering more potentially valid information. |

## Three common configuration errors
-  Issue: A collection binding failure error returns when calling the knowledge base file upload interface. The root cause is failure to correctly specify the `collectionIds` parameter to associate the target knowledge base collection. This prevents the uploaded software installation record or trouble ticket from being mounted to the corresponding dataset.
-  Issue: Abnormal fluctuations appear in the number or similarity score of recall results after multi-turn conversations. Some accurate fault handling steps fail to return. The root cause is failure to disable the automatic truncation logic for conversation context. Redundant interfering information from multi-turn conversations is included during retrieval.
-  Issue: No matching recall results return from an imported knowledge base after switching the vector model. The root cause is failure to trigger the reindexing process for the existing knowledge base. Only the model configuration is updated, without regenerating vector embeddings. This creates a mismatch between the vector spaces of the old and new models.

## How to verify proper configuration
-  Submit a simulated terminal fault question. Check whether the `similarity` score of returned results falls within the preset 0.75–0.85 range.
-  Count the number of retrieval results. Confirm the quantity matches the 3–5 range set by the `limit` parameter.
-  Upload a test software installation record file. Verify through the interface that it successfully mounts to the specified `collectionIds` collection.
-  Initiate two consecutive fault troubleshooting conversations. Check whether recall results adjust with the conversation context, with no abnormal filtering or omission of core information.

The values provided are common starting points and should be evaluated against the reader's own samples.
