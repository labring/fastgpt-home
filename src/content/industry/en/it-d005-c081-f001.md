# Technical Documentation and Interface Q&A for Penetration Testing Services: HTTP Interfaces and External Systems

## What data for this category looks like
This category's data comes primarily from target test systems, public vulnerability databases, automated scanner results, and manual verification records from red team engineers. Daily produced documents include test authorization letters, penetration test reports, vulnerability reproduction records, and rectification suggestions. These materials are updated once per project or major version update.
Data fields include test scope, vulnerability IDs, risk levels, reproduction steps, and repair plans. Core identifiers are project cycles, CVSS scores, and the number of affected assets.

## What constraints these characteristics impose on HTTP interfaces and external systems
First, data sources are scattered and require strict authorization. Interfaces must carry valid temporary credentials to avoid legal disputes from unauthorized access.
Second, each project’s data is updated independently. Interfaces must support pulling or pushing data by project dimension, and should not reuse global configurations.
Vulnerability reproduction records and scanner results have significant format differences. Interfaces must support multi-format data parsing, and field completion for manual verification results.
Report risk ratings rely on manual judgment. Interface return results must retain editable risk level fields to support subsequent adjustments.
The consequences of errors are severe. Interfaces must add retry mechanisms and error log retention to prevent test process stagnation from data transmission interruptions.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Carry a project-specific Bearer token with a validity period not exceeding 7 days | Complies with the temporary authorization interface specification of FastGPT v4.17.0, and avoids the risk of long-term token leakage |
| `variables` | Bind project-specific test scope and vulnerability database version variables | Adapts to each project’s independent data sources and update rhythm, avoiding cross-project data confusion |
| `responseData` | Return core fields including vulnerability ID, risk level, and reproduction steps | Filters irrelevant data to reduce transmission and parsing overhead |
| Timeout period | 300–600 seconds | Adapts to the time required for manual vulnerability verification and scanner result return |
| Retry count | 2–3 times | Addresses interface call failures caused by network fluctuations, avoiding test process interruption |
| Data format verification | Enable JSON format verification | Compatible with multi-format data input from automated scanners and manual verification records |

## Three common configuration mistakes
- Symptom: The interface returns a 401 unauthorized error, indicating the token is invalid. Cause: The project-specific `Authorization` token was not used, or the token validity period exceeded the preset range, failing to follow temporary test authorization requirements.
- Symptom: Configured interface parameters are lost after service restart, and normal calls cannot be initiated. Cause: Bound `variables` project configuration was not stored in persistent storage, only saved in local temporary cache, leading to configuration failure after restart.
- Symptom: Vulnerability data returned by the interface does not match actual test results, with missing fields. Cause: The return field rules for `responseData` were not correctly configured, or project-specific test scope variables were not bound, resulting in scanning results from non-current projects being pulled.

## How to confirm the configuration is complete
- Initiate an interface call for the current test project, and check if the returned `responseData` includes the preset core vulnerability-related fields, with no redundant irrelevant content.
- Check if the interface’s `Authorization` parameter carries the current project’s specific token, and the token validity period meets temporary authorization requirements.
- Restart the service and initiate the interface call again, confirm that the configured `variables` project parameters are not lost, and data for the corresponding project can be pulled normally.
- Simulate a network fluctuation scenario to initiate an interface call, confirm that the preset retry mechanism is triggered, and the call does not return a failure directly.
