# Technical Documentation and Interface Q&A for Channel Attribution and Lead Distribution: HTTP Interfaces and External Systems

## What Data for This Category Looks Like
Data for this category primarily comes from advertising platforms, CRM systems, attribution SDKs, and form systems. Four types of documents are regularly generated: attribution rules, lead distribution tables, channel reports, and exception reconciliation sheets. Most data updates occur on a daily or weekly basis. Core fields include channel identifiers, lead IDs, conversion times, assigned sales IDs, and similar values. Units are mostly natural units such as counts or instances. Core processing steps include channel parameter verification, duplicate lead deduplication, and sales assignment confirmation. Business issues may easily arise from incorrect data associations. FastGPT v4.17.0 supports interface configuration requirements for this category, enabling standardized access to multi-source data.

## Constraints Imposed on HTTP Interfaces and External Systems by This Category's Characteristics
Multi-source scattered data, clear update cycles, and core processing steps relying on structured validation create multiple constraints for HTTP interfaces and external systems. Multi-source data access requires interfaces to support cross-system data pulling and format adaptation. Interfaces must accommodate differences in field naming across sources. Daily or weekly update cycles require interface calls to align with business rhythms. Avoid high-frequency calls that trigger rate limits. Core steps such as parameter verification, deduplication, and assignment confirmation require interfaces to return standardized structured responses. This supports automated validation and exception troubleshooting. Business losses may easily occur after errors, so interfaces must provide clear error status codes and detailed log fields. This aids rapid issue location.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| API Call Secret | Use the `Bearer ${secretKey}` format, store the secret in environment variables | Complies with interface authentication specifications, prevents plaintext secret exposure, and secures data access |
| Request Variables | Pass business parameters such as channel ID, lead time range, and attribution rule identifier | Adapts to attribution data pulling and validation needs across scenarios, flexibly covering different business logic |
| Response Data Format | Return structured JSON format including status code, data list, and error information fields | Facilitates automated processing and exception troubleshooting, meets core step requirements for parameter verification, deduplication, and assignment confirmation |
| Call Frequency Limit | No more than 60 calls per minute | Aligns with daily or weekly data update business rhythms, avoids triggering platform rate limit rules |
| Timeout Duration | 30 seconds | Adapts to average response times for multi-source data pulling, prevents long-term blocking of business processes |
| Log Configuration | Enable full request and response log recording | Facilitates subsequent troubleshooting of exceptions in channel parameter verification, lead deduplication, and other steps |

## Three Common Misconfigurations
- Symptom: When calling the `/api/v1/chat/completions` interface, an appId is configured but cannot be associated with content uploaded to the knowledge base. Cause: The knowledge base has not been bound to the corresponding appId, or the passed appId does not match the identifier bound to the knowledge base.
- Symptom: Calling the interface returns a 514 status code, and attribution data cannot be obtained normally. Cause: The request does not carry valid authentication information, or the authentication information has expired.
- Symptom: The number of lead data returned by the interface does not match actual business statistics, with duplicate leads or missing data. Cause: No deduplication parameter was included in the interface request, or channel parameter verification rules were not configured correctly, leading to duplicate pulling or incorrect filtering.

## How to Verify Proper Configuration
- Initiate a test interface call, check whether the returned response data includes expected channel, lead, and assignment information.
- View interface logs to confirm that all carried authentication information and business parameters are correct, with no format errors.
- Compare the number of leads returned by the interface with real-time data in the business system, confirm that the data range matches the configured time or channel conditions.
- Simulate a request carrying incorrect parameters, check whether the interface returns the corresponding error status code and prompt information.
