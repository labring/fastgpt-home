# Technical Documentation and API Q&A for Game Server Development and Operations: Knowledge Base Retrieval and Recall

## What this category of data looks like
Core data for game server development and operations includes server architecture descriptions, server launch plans, server merge plans, fault reports, and similar documents. Data sources cover game runtime logs, online player count monitoring data, business databases, and player support tickets. Most document structures include technical parameters, operation steps, and validation rules. Fields involve server IP addresses, concurrency limits, log timestamps, and similar items. Common units are concurrency per second, storage capacity in gigabytes, and millisecond-level timestamps. Update frequencies are mostly daily or synced with game events. Some core configuration documents have higher update frequencies.

## Constraints on Knowledge Base Retrieval and Recall
High data update frequencies require knowledge base retrieval to support incremental synchronization, ensuring the timeliness of recalled content. Documents contain large volumes of precise technical parameters, so retrieval must support field-level matching to avoid irrelevant content being recalled. Single documents are lengthy, and total data volume is large, so the number of recalled entries must be strictly controlled to fit within conversation context windows. Documents such as fault reports and server merge plans have strongly correlated operation steps. The most recent or most relevant entries must be prioritized for recall, so targeted adjustments to retrieval and reranking rules are needed.

## Configuration Settings
This applies to FastGPT v4.17.0. The following configurable items are available:

| Config Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Game server operation and maintenance documents contain large volumes of precise technical parameters. This range balances retrieval precision and coverage, preventing irrelevant documents from being included in results. |
| `limit` | Top 8–12 entries | Core server operation and maintenance information is concentrated in a small number of documents. Excessive recall will exceed conversation context windows, leading to truncation of critical information. |
| `searchMode` | `local` | Game server operation and maintenance data is mostly stored in internal private knowledge bases. No external search resources need to be called, reducing invalid retrieval overhead. |
| `usingReRank` | Enabled | Documents such as fault reports and server merge plans have complex structures. Reranking improves the recall priority of key operation steps and validation rules, optimizing retrieval result relevance. |
| `datasetSearchUsingExtensionQuery` | Enabled | Operation and maintenance queries often include industry abbreviations or custom terms such as server merge and server launch. Extended queries cover more relevant documents, improving recall completeness. |
| `collectionIds` | Bind exclusive game server development and operations knowledge base collection | Precisely limit the retrieval scope, preventing documents from other categories from being included and ensuring recalled results match the business scenario. |

## Three Common Configuration Errors
1. Phenomenon: When calling knowledge base chat, the <Reference> tag in the system prompt does not display recalled document content. Cause: The configuration switch for injecting knowledge base recall results into the system context is not enabled, so retrieved documents are not included in the conversation context.
2. Phenomenon: Unable to export the complete file name list of uploaded files in the knowledge base. Cause: Attempting to directly traverse the container storage directory to export the list fails due to permission restrictions or path mapping issues. The correct export method uses the official dataset management interface or API.
3. Phenomenon: The number of returned retrieval results does not match the configured `limit` parameter. Cause: When the reranking function is enabled, the system performs secondary filtering on initial recall results. The value range of `limit` is not adjusted synchronously to fit the number of results after reranking.

## How to Verify Correct Configuration
1. Upload a test server architecture document. Initiate a query containing key parameters from the document, such as specified port or concurrency limit. Check whether relevant fragments of the document are included in the returned results.
2. View the system prompt area of the conversation. Confirm that recalled document content is displayed within the <Reference> tag, verifying that the context injection configuration is active.
3. Adjust the `similarity` parameter to 0.7. Initiate a query containing vague operation and maintenance terms. Check whether the relevance of the recalled results meets expectations.
4. Access the dataset management interface. Attempt to export the file list. Confirm that complete names of all uploaded files can be obtained, verifying that file management configurations are working properly.
