# Technical Documentation and API Q&A for Version Releases and Release Notes: Document Parsing and Chunking

## What the data for this category looks like
The core data for this category consists of documents related to version releases and Release Notes. Commonly used documents include change logs, version tag descriptions, release checklists, and more. Data sources mainly include Git repository tags, merged commit records, artifact files generated by CI/CD workflows, and issue milestone tracking records. Data is updated once per version release. Each entry of data contains fields such as version number, change type, associated commits, and impact scope. Document structure usually uses the version number as the starting identifier, followed by multiple change entries categorized by type. Some files include pre-release check items and artifact download links.

## What constraints do these characteristics impose on document parsing and chunking
This category of data is updated on a per-version basis. Parsing and chunking must strictly match version boundaries to avoid mixing content across versions. Data sources include structured commit records and unstructured text logs. Parsing rules must support both formats. Classifying changes is the most time-consuming part of this category. Chunking must ensure each change entry falls entirely within a single chunk, to avoid splitting that would make classification difficult. Errors may lead to user upgrade failures or community misunderstandings. Therefore, chunking must accurately identify core content such as breaking changes and critical fixes, and must not omit or incorrectly merge content.

## How to configure settings
The following configurations are based on the feature logic of FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---|---|--- |
| `chunkSize` | `800–1200 characters` | Single change entries for this category are mostly hundreds of characters long. This setting ensures a single chunk contains complete change information, and avoids splitting across entries |
| `chunkSplitter` | `Split by version tag + line break` | Release Notes usually use the version number as the document starting identifier. This rule ensures each chunk corresponds to a complete set of changes for one version |
| `UPLOAD_FILE_MAX_SIZE` | `500 MB` | CI artifacts and log files related to this category usually do not exceed this size. This setting avoids invalid large file upload requests |
| `PARSE_FILE_TIMEOUT_SECONDS` | `600 seconds` | When processing multi-version Release Notes files in batches, sufficient time must be reserved for parsing and chunking, to avoid mid-process parsing interruptions |
| `customPdfParse` | `Enable version tag matching rules` | In PDF-format Release Notes, version numbers usually appear as headings or bolded text. Enabling custom parsing rules allows accurate identification of chunk starting points |
| `chunkSettingMode` | `Manual configuration` | The document structure for this category is fixed. Manually configuring chunking rules adapts to the specific format of version tags and change entries, without relying on generic chunking logic |

## Three common mistakes
- Chunks after parsing include change entries from multiple versions. The symptom is that change content from different versions is merged into the same chunk. The cause is failing to set `chunkSplitter` to split by version tags, using generic line-break chunking rules which causes cross-version content to merge.
- Parsing times out and returns a 504 status code. The symptom is that file parsing progress stalls beyond the preset time. The cause is that `PARSE_FILE_TIMEOUT_SECONDS` is set to a value less than the time required for actual batch parsing, or failing to adjust the timeout parameter for multi-version files.
- Multiple single-line entries from Excel-format change logs are merged into one chunk after import. The symptom is that a single chunk contains multiple change entries from rows in an Excel sheet. The cause is failing to enable line-break-based chunking rules, or failing to configure custom separators to match Excel row end markers, corresponding to a common community issue with import and chunking anomalies.

## How to confirm correct configuration
- A single-version Release Notes file may be uploaded. The parsed chunk list may be reviewed to confirm each chunk corresponds to one version or a set of related change entries.
- Release Notes files for 3 or more versions may be batch uploaded. Parsing time may be checked to confirm it stays within the range set by `PARSE_FILE_TIMEOUT_SECONDS`.
- Excel-format change logs may be imported. Each chunk may be checked to confirm it corresponds to a single row in the Excel sheet.
- Test queries may be initiated against change entries in chunks. Relevant change information may be confirmed to be accurately retrievable.
