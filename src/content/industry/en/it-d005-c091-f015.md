# Technical Documentation and API Q&A for Player Customer Service and Public Opinion Handling: Knowledge Base Retrieval and Recall

## What the Data for This Category Looks Like
The data for this category primarily comes from game customer service systems, community forums, app store reviews, and game logs. Daily processed documents include player tickets, compensation requests, public opinion daily reports, and standardized response scripts. Data update frequency is typically daily or real-time. Each data entry includes fields such as ticket number, player account identifier, feedback content, processing progress, and public opinion classification tags. Document structures vary across different scenarios. Some real-time feedback data has no fixed format.

## Constraints on Knowledge Base Retrieval and Recall
Multiple constraints apply to the knowledge base retrieval and recall link from this category’s data traits. Dispersed multi-source data and daily or real-time update cycles require the retrieval link to support rapid multi-source data synchronization and incremental updates. This prevents recalling outdated compensation rules or public opinion response scripts. Diverse document structures and inconsistent fields require retrieval to support fuzzy matching and field-specific retrieval. This accurately locates processing basis for player tickets. Real-time feedback with non-standard formats requires retrieval to include flexible query optimization capabilities. This adapts to colloquial player questions. The account verification and rule judgment stages take up a large share of processing time. This requires improving retrieval precision to reduce invalid results. Errors harm player experience. This requires the retrieval link to include fallback logic for scenarios with no retrieval results.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0, and are adapted for player customer service and public opinion handling scenarios.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Balances retrieval precision and coverage, adapts to semantic matching needs for colloquial player questions |
| `limit` | Top 8 entries | Controls the context length per retrieval round, adapts to the context processing limits of large models |
| `searchMode` | `keyword+vector` | Balances keyword matching and semantic recall, adapts to non-standard player feedback content |
| `usingReRank` | Enabled | Re-ranks initial retrieval results, raises the display priority of highly relevant results |
| `datasetSearchUsingExtensionQuery` | Enabled | Optimizes and expands player questions, adapts to colloquial expression habits in customer service scenarios |
| `collectionIds` | Pass an array of knowledge base IDs bound to the business, for example `["kb_789012"]` | Limits retrieval scope, avoids recalling irrelevant promotional activities or knowledge base data from other categories |

## Three Common Misconfigurations
- Symptom: Only selecting the `vector` mode when configuring `searchMode` prevents correct recall of compensation rules or ticket processing basis for some player questions using fixed terminology. Cause: Failing to include keyword matching means the system cannot cover question scenarios where players use standardized terminology.
- Symptom: Passing a knowledge base ID variable in the workflow knowledge base retrieval node triggers a parameter format error. Cause: The variable was not adjusted to the required array type. A single string-type knowledge base ID was passed directly.
- Symptom: In workflows using FastGPT v4.8.10 or later, the knowledge base retrieval node sometimes returns no results, and the preset fallback logic does not trigger. Cause: The empty retrieval branch configuration was not enabled, or the `similarity` threshold was set incorrectly, filtering out high-matching results.

## How to Verify Proper Configuration
- Submit a standardized player ticket query. Confirm whether retrieval results include the corresponding compensation rules or response scripts. Verify the validity of the `similarity` and `limit` configurations.
- Pass a preset knowledge base ID variable. Check if the workflow node triggers retrieval normally. Verify the correctness of the `collectionIds` parameter configuration.
- Simulate a public opinion query with no matching results. Check if the preset fallback logic triggers. Verify that the empty retrieval branch configuration works as expected.
- Adjust the `usingReRank` setting between enabled and disabled. Compare the sorting differences of retrieval results. Verify that the re-ranking function is active.

The values provided here are common starting points. They should be evaluated against samples from the target deployment.
