# Technical Documentation and Interface Q&A for User Growth and Retention Operations: HTTP Interfaces and External Systems

## What the data for this category looks like
Core data for this category typically comes from user behavior logs, push systems, experiment platforms, and CRM systems. Commonly produced documents include growth experiment plans, user segmentation tables, touch messaging templates, and retention analysis reports. Data updates occur most often on a daily or weekly basis. Document fields include user segment tags, touch channels, experiment variables, retention rate metrics, and similar items. Units are mostly person-times, natural days, and similar units. Structured data is required to complete segmentation and attribution analysis.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Data for this category relies on multi-source heterogeneous operation and business system interfaces. Daily or weekly batch data synchronization requires interfaces to support stable batch invocation. User segmentation and touch rhythm design frequently call external interfaces to verify tag validity. Interface response delay directly extends operation work cycles. Interface calls for touch messaging and experiment configuration must strictly follow permission verification rules. Incorrect calls may trigger user dissatisfaction or waste of channel budgets. Retention analysis reports require pulling full user behavior data via interfaces. Interface field compatibility must match the metric definitions in operation documents to avoid experimental attribution deviations caused by data format mismatches. This category mainly manages in-app user life cycles, so interface calls focus more on pulling and verifying in-app data.

## How to set configurations
This page’s configurations are based on FastGPT v4.17.0. The specific configuration items are listed below:

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Interface authentication method | Use the `Authorization` header to carry a Bearer token | Complies with industry general interface security specifications, and adapts to authentication requirements of multi-source external systems |
| Request timeout period | 30–60 seconds | Covers the conventional time required for batch pulling of user segmentation data, and avoids data synchronization interruptions caused by timeouts |
| Batch invocation batch size | Process 1000–2000 pieces of data per single operation | Matches the scale of daily batch synchronization, and balances interface load and synchronization efficiency |
| Return data format | Structured JSON format, matching the `responseData` field specification | Aligns with the field structures of retention analysis reports and user segmentation tables, enabling direct parsing and use |
| Error retry strategy | Retry 2–3 times after failure, with a 5-second interval | Addresses temporary network fluctuations or interface jitters, and reduces the failure rate of batch synchronization tasks |
| Callback notification configuration | Trigger callbacks based on task completion status | Adapts to the real-time verification requirements of experiment result attribution, and ensures that analysis is carried out only after data synchronization is completed |

## Three common misconfigurations
- Phenomenon: Authentication failure is returned when calling external model interfaces, with status code 401. Cause: The channel secret is not correctly configured in the `Authorization` header, or the secret format does not meet the requirements of the target interface.
- Phenomenon: The rerank interface call does not take effect after execution, and the number of returned results does not match expectations. Cause: The configuration parameters of the rerank model are not correctly specified in the interface request, or the input format does not match the interface requirements.
- Phenomenon: After actively interrupting the SSE connection, conversation records are not written to the database. Cause: The interface’s interrupt callback logic is not configured, so the data storage operation is not triggered when the request is not completed.

## How to confirm that configurations are complete
- Call the test interface to verify that the `Authorization` header is correctly carried, and that the returned `responseData` field matches the preset operation metric structure.
- Initiate a batch data synchronization task, observe whether the interface response time falls within the 30–60 second range, and confirm that no timeout errors occur.
- Simulate an interrupt of the SSE connection, check whether the corresponding conversation record is generated in the database, and confirm that the callback logic takes effect.
- After configuring the rerank interface parameters, initiate a test call to verify that the reranking order of the returned results meets expectations.
