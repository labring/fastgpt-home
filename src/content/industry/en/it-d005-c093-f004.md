# Technical Documentation and API Q&A for User Growth & Retention Operations: Vector Models and Indexes

## What data for this category looks like
The data for this category mainly comes from user behavior logs, push systems, experiment platforms, and CRM systems. Daily processed documents include growth experiment plans, user segmentation tables, outreach copy, and retention analysis reports. Data update frequency is usually daily or weekly. Each individual document contains fields such as user segmentation tags, timing parameters for outreach, experiment variables, and retention rate metrics. Most fields are numerical or text-based, with no unified fixed units. Some indicators require alignment with corresponding statistical specifications based on the business context.

## What constraints do these characteristics impose on the vector models and indexes link
Data sources for this category are scattered and have large format differences. There are both structured data such as user segmentation tables and experiment indicator data, as well as unstructured data such as outreach copy and analysis reports. Data update frequency is mostly daily or weekly. Incremental index updates must be supported to avoid resource consumption from full index rebuilding. Each individual document contains associated business fields. When splitting vectors, the business association between fields must be retained to avoid losing core information such as user segmentation and experiment variables after splitting. At the same time, data scale gradually expands as the user base grows. A balance must be struck between index recall accuracy and retrieval speed to avoid retrieval delays caused by excessive data volume.

## How to set configurations
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Balances semantic completeness of business documents and vector chunking accuracy, and adapts to the content length of most growth operation-related documents |
| Overlap Length | 100–200 characters | Prevents loss of contextual association after chunking, and ensures semantic coherence of content such as user segmentation and outreach copy |
| Similarity Threshold | 0.75–0.85 | Filters low-correlation user behavior data and experiment results, and improves business relevance of retrieval results |
| Single Search Limit | Top 10 entries | Controls context usage of retrieval results to avoid exceeding model input limits |
| `maxToken` | 8192 | Adapts to context length limits of mainstream embedding models, and balances retrieval information density and computing resource consumption |
| Reranking Switch | Enabled | Improves ranking accuracy of highly relevant outreach copy and analysis reports, and optimizes retrieval experience for user segmentation data |

## Three common misconfigurations
- Phenomenon: Significant delay occurs when retrieving user segmentation data, and the interface shows loading timeout. Cause: Incremental indexing is not configured for daily updated user behavior logs, and full index rebuilding occupies excessive computing resources.
- Phenomenon: A "no relevant content" error prompt pops up in the interface when using the knowledge base after configuring an embedding model. Cause: The embedding model access channel configuration is not bound to the knowledge base, or model call permissions are not correctly configured.
- Phenomenon: After connecting a local m3e embedding model, the knowledge base remains in the "indexing" state for a long time. Cause: No reasonable timeout threshold is set for the local model's API response, or chunk parameters do not match the model's input length.

## How to confirm the configuration is correct
- Upload a typical growth experiment plan document, and check whether the chunked text retains the association between experiment variables and metrics.
- Initiate a retrieval targeting user segmentation tags, and verify whether the similarity of returned results falls within the preset business threshold range.
- Run a daily incremental indexing task, and check whether the task execution time meets business expectations.
- Call the interface corresponding to `defaultToken` for testing, and confirm that the token usage of the retrieval context does not exceed the configured range.

The values provided are common starting points and should be measured against the reader's own samples.
