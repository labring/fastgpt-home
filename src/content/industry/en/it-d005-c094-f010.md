# Technical Documentation and API Q&A for User Acceptance Testing Support: Source Citation and Traceability

## What the data for this category looks like
The data sources for this category include requirement specification documents, test environment configurations, customer business sample data, and defect management system records. Daily produced documents cover UAT test cases, acceptance issue tickets, acceptance reports, and signed confirmation sheets. These documents are maintained and updated by implementation consultants, test managers, and customer business representatives. Updates occur once per test phase or software version iteration. Data fields include test case steps, expected results, issue reproduction paths, acceptance conclusions, and more. No unified fixed units apply; values adjust based on business scenarios.

## What Constraints These Characteristics Impose on Source Citation and Traceability
Data sources are scattered and tied to specific test phases. Traceability requires binding test environments and requirement documents from the corresponding version. This prevents cross-phase data confusion. Update frequency follows version iterations. Cited documents must match the current acceptance phase. General business document traceability logic cannot be reused directly. Daily produced documents such as signed confirmation sheets must clearly link to the corresponding acceptance phase. Traceability requires retaining traceable association identifiers. UAT test case step and expected result fields must match precisely. This ensures cited content aligns with the acceptance scenario. It safeguards the credibility of acceptance conclusions.

## How to Configure Settings
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| Maximum Context | 14000–16000 token | Adapts to the total length of multiple UAT test cases and acceptance documents, prevents truncation of traceability information |
| Single Search Limit | Top 3–5 entries | Controls the number of documents returned by retrieval, balances traceability accuracy and query efficiency |
| `quoteMaxToken` | 7000–11000 token | Limits the token length of a single cited document, adapts to the input constraints of large language models |
| Citation Source Filtering | Bind test phase ID | Ensures traceability information matches the current acceptance phase, prevents cross-phase data confusion |
| `responseData` | Include document type and creation time | Retains key metadata required for traceability, facilitates archive verification of acceptance reports |
| `detail` | Only retain associated fields | Streamlines cited content, focuses on UAT test case steps and defect reproduction paths |

## Three Common Configuration Mistakes
- Symptom: After calling the knowledge base tool in a workflow, the returned results do not display citation sources. Cause: The `responseData` parameter is not configured to enable source return, or the knowledge base permissions for the corresponding acceptance phase are not bound.
- Symptom: Knowledge base query takes too long, and single retrieval consumes more token than expected. Cause: `quoteMaxToken` is set to a too high range. This causes full document content to be loaded on each retrieval, exceeding actual business needs.
- Symptom: Cited documents do not match the current acceptance phase, and cross-version test cases appear. Cause: Citation source filtering rules are not configured, and the test phase ID is not bound. This causes documents from historical phases to be retrieved.

## How to Confirm Configuration is Complete
- Initiate a query related to UAT test cases. Confirm returned results include document source paths and creation time.
- Adjust the `quoteMaxToken` value. Confirm retrieved document lengths match the current acceptance phase's document scale.
- Test multi-knowledge base association scenarios. Confirm only current-phase documents are correctly cited.
- View tool call logs in FastGPT v4.17.0. Confirm returned `detail` fields include key UAT test case step information.

The values provided are common starting points, and should be evaluated against the target deployment’s own sample data.
