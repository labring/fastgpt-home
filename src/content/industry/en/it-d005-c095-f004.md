# Technical Documentation and API Q&A for Monitoring Alert Configuration: Vector Models and Indexes

## What the data for this category looks like
This category of data originates from daily operation and maintenance documents created by operation engineers and SRE teams, including monitoring metric lists, alert rules, on-duty manuals, and alert change records. Data sources cover Prometheus, Zabbix, cloud monitoring, application logs, CMDB, and other operation and maintenance tools. Updates occur daily or whenever alert rules are modified. Document structures include fields such as metric name, threshold, alert level, trigger condition, and on-duty contact. Some fields include units like percentage, millisecond, and trigger count.

## What constraints do these characteristics impose on vector models and indexes
The multi-source attribute of monitoring alert configuration data requires vector indexes to support unified embedding of cross-tool data, avoiding embedding deviations caused by differences in field formats across different tools. The high-frequency update feature requires indexes to support incremental updates, adapting to the refresh rhythm of daily updates or change-triggered refreshes. Documents contain strongly associated fields such as thresholds and levels, requiring context association to be retained during chunking, preventing splitting from destroying the complete logic of alert configurations. The feature that fields include units also requires vector models to recognize and retain semantic information related to units, improving matching accuracy.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Matches the single text length of alert rules and metric lists, avoids splitting that breaks associated fields such as thresholds and trigger conditions |
| Overlap Length | 100–200 characters | Retains context association between chunks, prevents splitting from breaking the configuration logic of alert links |
| Similarity Threshold | 0.75–0.85 | Filters noise matches in alert configurations, avoids accidentally triggering queries for similar but unrelated alert rules |
| `defaultToken` | 8000 | Adapts to the token usage of single records in alert documents, meeting basic query context requirements |
| `maxToken` | 16000 | Accommodates the total token volume after batch alert change records and multi-knowledge base splicing, adapting to complex query scenarios |
| Single Search Limit | Top 20 entries | Matches the number of alert configuration entries that operation teams typically review during troubleshooting, avoids returning excessive redundant data |

## Three common mistakes
- Phenomenon: A single alert configuration file remains stuck in indexing progress with no updates for a long time. Cause: The chunk length is set too small, resulting in too many chunks generated from a single file, and indexing tasks pile up without completion.
- Phenomenon: Knowledge base priority configuration does not take effect, and query results return content from two knowledge bases at the same time. Cause: Priority rules are not embedded in the recall sorting link of the vector index, and only adjust the order during the result display stage, without affecting the actual recall logic.
- Phenomenon: A 60-second timeout error is triggered when performing a knowledge base index switch. Cause: The `maxToken` parameter is not adjusted according to the update frequency of alert data, resulting in the total token volume exceeding the limit during batch indexing, triggering the platform's timeout threshold.

## How to verify successful configuration
- Upload a single alert configuration file, confirm that the indexing progress completes within a reasonable duration, with no persistent pile-up.
- Configure multiple knowledge base priority rules, initiate cross-knowledge base queries, and verify that the returned result priority matches the preset configuration.
- Execute an indexing task for batch alert change records, confirm that no 60-second timeout errors occur, and the task status shows completed.
- View the vector model call logs in FastGPT v4.17.0, confirm that the used model matches the preset configuration, with no failed call records.

The configuration values listed above are common starting points. Adjust them based on specific samples and use cases for each deployment.
