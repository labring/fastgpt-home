# Technical Documentation and API Q&A for Mobile Development: Knowledge Base Retrieval and Recall

## What data for this category looks like
This category of data typically comes from code repositories, app store backends, crash monitoring platforms, and device coverage datasets. Daily produced documents include device version release notes, device adaptation lists, crash analysis reports, and app store review materials. Data updates occur daily or per version release cycle. Document structures typically include fields such as device version, permission call rules, review status, and crash log tags. There is no unified standardized format, and structures are adjusted as projects iterate.

## Constraints on knowledge base retrieval and recall
Multi-source data sources require retrieval to support mixed recall across code snippets, backend documents, and monitoring data. Daily or per-version update frequency requires the knowledge base to support incremental synchronization and scheduled full updates, to avoid recalling outdated content. Ununified document formats require retrieval to adapt to unstructured text splitting and indexing. Exclusive content such as device adaptations and review materials requires retrieval to allow filtering by custom tags like device system and review status, differing from retrieval logic in general development scenarios. Additionally, mobile development requires handling app store reviews and device system differences, which requires recall results to prioritize matching exclusive documents for the current development device, avoiding interference from invalid cross-device information.

## Configuration Settings
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Adapts to the unstructured characteristics of mobile development documentation, filtering low-relevance retrieval results |
| `limit` | Top 8 entries | Adapts to mobile context window limits, avoiding excessive recalled content causing model output truncation |
| `searchMode` | Hybrid retrieval | Matches both code snippets and document text, covering multi-source data from code repositories and app store backends |
| `usingReRank` | Enabled | Rearranges initial recall results, prioritizing returning highly relevant content related to device adaptation and permission troubleshooting |
| `datasetSearchUsingExtensionQuery` | Enabled | Automatically optimizes retrieval queries, matching term variants in mobile development scenarios, such as expanding "iOS adaptation" to "iOS 17 system adaptation" |
| `collectionIds` | Fill in the knowledge base collection ID bound to the project | Restrict retrieval scope to only include mobile development-exclusive documents and code snippets |

## Three Common Mistakes
- Symptom: Unable to connect to the enterprise’s existing Confluence document library as a retrieval data source, or no retrieval results after synchronization. Cause: Failed to correctly configure the knowledge base’s external data source synchronization rules, or failed to map the mobile development-related directory in Confluence to the bound knowledge base collection.
- Symptom: Knowledge base response content is truncated, or unable to output complete device adaptation solutions. Cause: `limit` set too high causing context overflow, or failure to adjust the context window to adapt to long documents when using the qwen2.5-14b-int4 quantized model.
- Symptom: Retrieval results are not filtered by device system, returning invalid content that does not match the current development device. Cause: Custom tag filtering configuration not enabled, or failure to specify device dimension retrieval conditions during retrieval.

## How to Verify Correct Configuration
- Upload a latest iOS version release note to the bound knowledge base, initiate a query including "iOS 17 adaptation permissions", confirm that the retrieval results include this document.
- View the retrieval log, confirm that values of parameters such as `similarity` and `limit` meet the configuration requirements, with no abnormal parameter overrides.
- Test cross-data source retrieval, initiate a query including both "crash log analysis" and "app store review materials", confirm that retrieval results cover content from both code repositories and app store backends.
- Perform a knowledge base backup and restore operation, confirm that the bound knowledge base collection content is complete after restoration, and retrieval can be initiated normally.

The values provided are common starting points and should be measured against the reader's own samples.
