# Technical Documentation and API Q&A for Renewal Health Management: Knowledge Base Retrieval and Recall

## What Data for This Category Looks Like
Data for this category primarily comes from CRM systems, product usage backends, ticket statistics platforms, and contract ledgers. Daily generated documents include customer health reports, renewal forecast tables, high-risk customer lists, and customer communication notes. Data update frequency is typically weekly or monthly. Documents contain fields such as customer ID, contract cycle, health score, risk level, and follow-up records. There are no unified mandatory units, and field content changes dynamically based on individual customer circumstances.

## Constraints Imposed on Knowledge Base Retrieval and Recall
The data sources for this category are scattered and update slowly. This requires knowledge base retrieval to stably cover all historical data, avoiding missed cross-cycle customer-related information due to incremental updates. Daily documents include both structured tables and unstructured notes. Retrieval and recall must support both field matching and semantic fuzzy matching. Since the data relates to customer retention risk, retrieval results must have high confidence to avoid risk judgment errors caused by recall bias. A single retrieval must cover enough related entries to support multi-dimensional follow-up analysis for renewal actions.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` | 0.72–0.80 | Matches the semantic association strength of renewal health data, balances recall accuracy and coverage |
| `limit` | Top 8–12 entries | Supports multi-dimensional renewal risk analysis, prevents insufficient single results for decision-making |
| `searchMode` | Hybrid retrieval | Balances structured field matching and unstructured text semantic retrieval, adapts to multiple document types |
| `usingReRank` | Enabled | Optimizes sorting logic for long texts and multiple entry results, elevates the priority of content related to high-risk customers |
| `datasetSearchUsingExtensionQuery` | Disabled | This category has low data update frequency, no need for additional query semantic expansion, avoids introducing irrelevant information |
| `collectionIds` | Bound by customer groups | Accurately limits the retrieval scope, prevents interference from cross-customer data, improves retrieval targeting |

## Three Common Misconfigurations
- Phenomenon: Knowledge base retrieval response times out, and the interface displays 504 gateway timeout status code. Cause: Retrieval configuration not adjusted based on data volume, full cross-customer data retrieval causes excessive resource usage.
- Phenomenon: A single retrieval returns only 1 result, failing to cover multi-dimensional information related to renewal risk. Cause: `limit` is incorrectly set to 1, without adjusting the value to meet the multi-entry requirements of renewal health analysis.
- Phenomenon: Retrieval results include a large number of irrelevant cross-customer documents, failing to focus on the target customer's health data. Cause: `collectionIds` is not configured to bind the retrieval scope by customer groups, leading to an overly broad retrieval scope.

## How to Verify Proper Configuration
- Run a single retrieval test, verify that the number of returned results meets business analysis needs, and adjust the `limit` configuration to a value matching the scenario.
- Import a single customer health report, retrieve risk keywords for a specified customer, confirm that only documents related to that customer are returned, and verify the accuracy of the `collectionIds` configuration.
- Check the retrieval response duration, adjust the `similarity` and `usingReRank` configurations based on actual deployed resources to ensure response meets business timeliness requirements.
- Compare retrieval results with and without `datasetSearchUsingExtensionQuery` enabled, confirm whether irrelevant information is introduced, and adjust the configuration to match the data update frequency.

The values provided are common starting points and should be measured against the reader's own samples.
