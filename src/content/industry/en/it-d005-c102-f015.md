# Technical Documentation and API Q&A for Defect Management and Regression Testing: Knowledge Base Retrieval and Recall

## What This Category of Data Looks Like
This category of data primarily comes from defect management systems, test reports, code commit records, and user feedback. Daily produced documents include defect tickets, regression test checklists, repair verification records, and defect statistical reports.
Data updates occur daily or per version release cycle. Each data entry includes fields such as defect ID, priority, reproduction steps, associated version, and repair status. The structure follows the full lifecycle of a defect from discovery to closure.
Field formats vary across document types. Structured documents have clear, defined fields. Unstructured documents mostly consist of test steps and verification descriptions.

## Constraints on Knowledge Base Retrieval and Recall
This data follows the defect lifecycle, with closely linked fields and key attributes such as version and priority. Retrieval requires precise matching of associated dimensions to boost recall relevance.
Data updates occur daily or per version release cycle. Maintain stable synchronization links to avoid recalling outdated defect status information.
Document types include structured defect tickets and unstructured test reports. Adapt retrieval logic to parse and recall multiple formats.
Each data entry has many associated items. Control the number of recall results to avoid context overflow that harms answer accuracy.
Defect-related information has strict timeliness requirements. Prioritize recall results for current version defects and regression tasks.

## Configuration Settings
This configuration uses FastGPT v4.17.0 knowledge base features. Specific configuration items and recommended values are listed below:

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | `0.75–0.85` | Matches the precision requirement for defect reproduction steps and priority, avoids recalling irrelevant defect entries |
| `limit` | `Top 8 entries` | Balances context length and recall coverage, adapts to scenarios with multiple associated defect information |
| `searchMode` | `vector` | Addresses mixed retrieval needs for structured defect fields and unstructured test steps, balances precision and recall scope |
| `usingReRank` | `Enabled` | Improves recall ranking accuracy for high-priority defects and core regression test content, prioritizes display of critical information |
| `datasetSearchUsingExtensionQuery` | `Enabled` | Expands retrieval scope based on fields such as defect ID and version number, covers associated repair records and verification reports |
| `collectionIds` | `Specify the defect management and regression test dataset ID for the current project` | Isolates unrelated business datasets, ensures recall scope is precisely focused on the current R&D and testing scenario |

## Four Common Misconfiguration Issues
- Response content includes technical information outside the knowledge base. This occurs when strict knowledge base content restriction configuration is not enabled, causing the model to generate responses using external information.
- Retrieval results for docx format documents do not include chapter title information. This occurs when document extended retrieval configuration is not enabled, only plain main content is recalled without associating chapter structure.
- Passing the `metadata` field when calling the create file collection API produces no expected effect. This occurs when the official API documentation is not reviewed, and non-standard parameters are mistakenly passed to the interface.
- Responses automatically attach reference links for knowledge base content. This occurs when the retrieval result reference marker configuration is not disabled, causing links to be automatically included in the response.

## How to Verify Successful Configuration
- Upload a standard defect ticket document, perform a retrieval test, and check if the recall results include associated version and priority field information.
- Call the knowledge base retrieval interface with the `similarity` parameter, and verify that the similarity of returned results matches the preset range.
- Simulate updating defect data to trigger synchronization, and check if the knowledge base completes data updates within the preset cycle.
- Submit a question that does not include defect management-related content, and confirm that no relevant information outside the knowledge base is generated in the response.

The values provided are common starting points and should be measured against the reader's own samples.
