# Technical Documentation and API Q&A for License Compliance and Copyright Notices: Vector Models and Indexes

## What Data Looks Like for This Category
Data for this category primarily comes from LICENSE and NOTICE files in code repositories, license lists generated by third-party dependencies, official published standard license texts, and copyright ownership records from project contributors. Data updates are triggered by software version releases or third-party dependency changes, with no fixed schedule. Each individual data entry includes license clause text, original copyright notices, and associated dependency information. Most fields are text-based, and the original file formatting and semantics must be fully preserved.

## Constraints Imposed on Vector Models and Indexing
Data for this category comes from multiple original sources, with no fixed update cycle. This requires vector indexing to support incremental synchronization and multi-source data ingestion. Individual data entries have widely varying text lengths: short copyright notices of tens of characters, up to thousands of words of license compatibility clauses. This demands adaptation of chunking rules for different text lengths. Additionally, data must fully retain copyright notices and original clause semantics; vector modeling must not arbitrarily truncate critical information. Batch processing of dependency lists uses significant memory and computing resources, so indexing parallel processing parameters must be adjusted based on hardware configuration.

## How to Set Configurations
These configurations are based on the interface and parameter logic of FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Matches the average length of license texts and copyright notices for this category, avoiding semantic breaks in single chunks |
| Overlap Length | 100–200 characters | Preserves context for copyright notices and license clauses across chunks, preventing critical information from being split |
| `maxToken` | 8192 token | Aligns with the input limit of mainstream open-source embedding models, avoiding truncation of core compliance clauses in long license texts |
| Similarity Threshold | 0.75–0.85 | Differentiates between similar license clauses, enabling accurate matching of standard texts required for compliance checks |
| Single Search Limit | Top 10 results | Covers common query needs for license types and dependency associations, avoiding excessive redundant results |
| `defaultToken` | Calibrated via actual testing | Adapts to batch indexing tasks across different hardware environments, balancing memory usage and processing efficiency |

## Three Common Misconfigurations
- Phenomenon: Knowledge base search responses time out, or result return times exceed expectations. Cause: Failing to adjust chunking and indexing shard configurations for this category's multi-source license data, leading to traversal of too many redundant text blocks during vector retrieval.
- Phenomenon: Question answering splitting steps return empty results or incorrect license type classifications. Cause: Incorrectly using a vector model for question answering splitting tasks, without using a corresponding large language model to handle natural language splitting requirements.
- Phenomenon: Newly added custom indexes cannot sync the latest dependency license lists. Cause: Failing to configure incremental update trigger rules, only performing full index rebuilding, which cannot adapt to the high-frequency update rhythm of dependency changes for this category.

## How to Confirm Configurations Are Set Correctly
- Upload a single LICENSE file, run vector indexing, and check that chunked text blocks retain complete copyright notices and license clauses, with no critical content truncated.
- Initiate a compliance check query, verify that the matching degree between returned search results and input license keywords aligns with preset matching rules.
- Add a new third-party dependency license data entry, trigger index updates, and check that the index completes synchronization.
- View the hardware resource monitoring panel, confirm that resource usage for vector encoding and indexing tasks falls within a reasonable range, with no abnormal occupancy.

The values provided are common starting points and should be measured against the reader's own samples.
