# Technical Documentation and Interface Q&A for Integration Testing and Interface Testing: Knowledge Base Retrieval and Recall

## What Data for This Category Looks Like
Data for this category primarily originates from interface management platforms, test environment logs, databases, and message queues. Daily documents include interface test cases, joint debugging issue tickets, environment descriptions, and test reports.
Data updates follow a daily or per-version release cycle. Most document structures include interface paths, request parameters, response formats, test steps, and result fields. Some log data includes timestamps, call chains, and error code information. No unified mandatory format exists, but core test chain information must be included.

## Constraints for Knowledge Base Retrieval and Recall
Interface test-related data updates daily or per version. Knowledge base retrieval must support incremental recall mechanisms to prevent resource overuse from full scans.
Documents contain structured fields such as interface paths, call chains, and error codes. Retrieval must prioritize matching keywords linked to cross-module interactions to improve efficiency when troubleshooting chain issues.
Multi-source data is stored in a mixed configuration. Differentiated recall weights must be set for different sources, including interface management platform documents and test logs.
Test cases and joint debugging issue tickets have strong correlations. Binding recall for associated data in the same group must be supported to avoid isolated single pieces of information disrupting troubleshooting.

## Configuration Settings
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Matches precise parameters and chain keywords in interface test scenarios, avoiding recall of unrelated general test documents |
| `limit` | Top 10 entries | Covers associated use cases, logs, and issue tickets required for single-round test troubleshooting, avoiding excessive results that interfere with positioning |
| `searchMode` | hybrid | Combines keyword matching and semantic recall, adapting to mixed retrieval needs for structured fields such as interface paths and parameter names, as well as natural language questions |
| `usingReRank` | Enabled | Re-ranks initial recall results, prioritizing documents directly related to interface call chains and error troubleshooting |
| `datasetSearchUsingExtensionQuery` | Enabled | Expands retrieval terms based on user questions, covering scenarios such as synonyms and interface aliases, improving recall rates for cross-module interaction content |
| `collectionIds` | Specified by business scenario | Limits retrieval scope to exclusive collections such as interface test cases and joint debugging issue tickets, avoiding mixing documents from other categories |

## Three Common Misconfiguration Issues
- Phenomenon: After uploading grouped documents that include section titles, links, and summaries, retrieval splits individual grouped data into separate entries, failing to return complete grouped information. Cause: Incorrect configuration of binding parameters for associated recall, failure to associate grouped data to the same collection, or disabled grouped recall logic.
- Phenomenon: When calling the knowledge base interface to create a plain text collection or training order, the interface returns parameter errors or the feature does not take effect. Cause: No valid `trainingType` option specified, or use of an unsupported parameter configuration.
- Phenomenon: In high-concurrency scenarios, knowledge base retrieval requests related to interface tests experience timeouts or insufficient result counts. Cause: Failure to adjust retrieval parameters based on concurrency scale, or unreasonable `similarity` threshold settings leading to excessive retrieval latency.

## How to Verify Successful Configuration
- Upload a set of test data that includes section titles, links, and summaries. Confirm retrieval returns complete single-group information to verify associated recall configuration is active.
- Call the knowledge base interface to create a plain text collection. Pass different `trainingType` options. Confirm the interface returns normal results and functions as expected.
- Simulate high-concurrency requests. Observe retrieval response times and result completeness. Adjust `similarity` and `limit` configurations to thresholds meeting business requirements.
- Review retrieval logs. Confirm only documents within the specified `collectionIds` range are recalled, avoiding mixing unrelated data.

The values provided are common starting points and should be measured against the reader's own samples.
