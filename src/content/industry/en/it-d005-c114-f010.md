# Technical Documentation and API Q&A for Requirements Analysis and PRD Management: Citation Sources and Traceability

## What the Data for This Category Looks Like
Typical users of this category are internet product teams, business analysts, and product managers. Daily produced documents include requirement research notes, PRD documents, user story lists, and requirement change forms. Data sources mainly include customer interview records, internal ticketing systems, competitor public pages, and business tracking dashboards. Update frequency is usually once weekly or aligned with product version iterations. Document fields typically include business goal definitions, acceptance criteria descriptions, requirement boundary conditions, and change records. There are no uniform mandatory units. Some fields require linking to original interview or ticketing content as supporting evidence.

## What Constraints Do These Characteristics Impose on Citation Sources and Traceability
Data for this category comes from scattered sources, including both internal and public content. This requires citation traceability to support precise cross-data-source association, to avoid mixing requirement information from different sources. Document update frequency adjusts with version iterations or weekly. A regular knowledge base refresh mechanism must be configured to ensure cited content stays synchronized with the current version of requirement documents. Core fields such as business goals and acceptance criteria need to be bound to original supporting materials. This requires traceability to retain complete citation links, to facilitate verification of the authenticity of requirement bases. Requirement change forms have strong timeliness. Traceability linked by version number must be supported, to avoid development deviations caused by referencing outdated change records.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | `800–1200 token` | Single requirement supporting materials for this category are mostly business descriptions and acceptance conditions. This token range covers core content while avoiding redundancy |
| Number of single recall entries | Top 3–5 | Supporting materials for requirement analysis are usually concentrated in a small number of core interviews or tickets. Excessive recall will introduce irrelevant content |
| `responseData` | Return only linked source documents | Traceability for this category needs to clearly point to original supporting materials, to avoid returning redundant retrieval intermediate data |
| Knowledge base refresh interval | 7 days | Matches the weekly or version-aligned update frequency of documents in this category, ensures timeliness of traceability content, and complies with FastGPT v4.17.0 configuration specifications |
| `detail` | Full path | Documents in this category need to be linked to specific source types and update times. A full path can clearly define the traceability link |
| Traceability display toggle | Enabled | Acceptance criteria for requirement documents need to be bound to original evidence. Enabling this allows citation sources to be directly displayed in outputs |

## Three Common Misconfigurations
- Phenomenon: A red error prompt appears when specifying a knowledge base identifier using a global variable during knowledge base retrieval configuration. Cause: Variable reference permission is not enabled in the data source configuration of the retrieval node, or the variable scope does not cover the current workflow node.
- Phenomenon: In a workflow based on question classification, only the first round of questions can trigger knowledge base reference, and subsequent questions have no retrieval results. Cause: Context passing logic is not configured, causing subsequent questions to fail to associate with the loaded knowledge base retrieval configuration.
- Phenomenon: A global variable datasetid is set in the workflow knowledge base retrieval node but cannot be called normally. Cause: The global variable is not bound to the data source configuration item of the retrieval node, or the variable name does not match the parameter name of the node configuration item.

## How to Verify Successful Configuration
- Submit a query about requirement acceptance criteria, check whether the output displays clear citation source identifiers or document paths.
- Adjust the knowledge base refresh interval, verify whether retrieval results match the latest requirement change forms or interview records.
- Test multi-round query scenarios, confirm that each round of queries can correctly associate with the configured knowledge base data source.
- Check variable reference configuration, confirm that the global variable has been correctly bound to the corresponding configuration item of the retrieval node.
