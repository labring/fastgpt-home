# Test Cases and Defect Analysis for CDN and Edge Acceleration Configuration: Tool Calling and Plugins

## What this category of data looks like
This type of data typically originates from CDN consoles, DNS resolution records, public network access logs, and edge node monitoring alerts. Daily produced documents include domain name access forms, cache rule configuration forms, refresh and preheating operation records, and fault root cause analysis reports. The data update rhythm is usually daily synchronization or real-time updates tied to configuration changes. Fields include domain name access status, cache hit rate, edge node latency, error code distribution, and more. Records follow the console specifications of the corresponding CDN vendor, with no unified mandatory external field requirements.

## What constraints these characteristics impose on the tool calling and plugins workflow
The characteristics of this data category create multiple constraints for tool calling and plugin configuration. Multi-source data sources require plugins to support integration with multiple types of APIs including CDN consoles, DNS resolution, and access logs. Corresponding data source access permissions must be configured in advance. Differences in data update rhythms require setting differentiated polling intervals for different data types, to avoid excessive API calls or delayed retrieval of the latest status. The diverse structures of daily documents require plugins to adapt to input and output formats such as domain name access forms and cache rules, and preset field mapping rules. High-frequency operation requirements in operation and maintenance scenarios demand simplifying the parameter configuration process for tool calls, to reduce repeated input. Based on the FastGPT v4.17.0 tool calling framework, additional compatibility with vendor-specific API authentication methods is required.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | Automatically match the CDN-related tools needed for the current scenario, reducing manual selection operational costs |
| `functionCall` | `[{"name":"fetch_cdn_access_log","parameters":{"time_range":"24h"}}]` | Explicitly specify the call to the access log retrieval tool, to accurately pull log data for the target time range |
| Data polling interval | `300 seconds` to `86400 seconds` | Match the data update rhythm; use short intervals for real-time data monitoring, long intervals for daily report-type data |
| Document field mapping rules | Determined through actual testing | Adapt to differences in document fields across CDN vendors, avoiding parsing failures for documents such as domain name access forms and cache rules |
| Tool call timeout threshold | `15 seconds` | Edge node responses are typically fast, this threshold balances waiting time and call success rate |

## Three common error scenarios
- Phenomenon: Preset environment variable parameters cannot be read during the model selection step of tool calling. Cause: Environment variable calling permission is not enabled in the plugin configuration, preventing the tool from obtaining sensitive configurations such as CDN vendor API keys.
- Phenomenon: Format errors are returned when calling the CDN access log retrieval tool, including abnormal prompts for the `$schema` field. Cause: An unexpected `$schema` field was mistakenly added to the tool call parameters, which does not comply with FastGPT tool call format specifications.
- Phenomenon: CDN node data cannot be retrieved normally after MCP access is configured. Cause: MCP connection parameters were not configured correctly, or the CDN-related permission scope was not added for the MCP tool.

## How to confirm successful configuration
- Manually trigger a preset CDN tool call, and check if the returned result includes cache rules or access log information for the target domain name.
- Review plugin running logs to confirm there are no prompts for environment variable reading failures or format errors.
- Verify the MCP access connection status, confirm that edge node monitoring data can be retrieved normally.
- After adjusting the data polling interval, confirm that the tool's data retrieval time interval matches the expected data source update rhythm.
