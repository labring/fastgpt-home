# Test Case and Defect Analysis for IT Asset Inventory: Workflow Orchestration
This document is written based on FastGPT v4.17.0

## What this category of data looks like
Data for this category mainly comes from asset management systems, procurement systems, fixed asset modules in financial systems, and terminal management platforms. Four types of documents are generated daily: asset ledgers, inventory sheets, loan and return forms, and scrap application forms. Fields include asset ID, name, specification model, user, deployment location, usage status, etc. Units are mostly units, sets, and pieces.
Data update frequency is monthly, quarterly, or annually. Data changes are relatively stable during a single inventory cycle, with temporary increments only occurring during business links such as procurement, loan, and scrap.

## What constraints do these characteristics impose on the "workflow orchestration" link
Demand for multi-source data access requires workflows to configure multiple data source pull nodes, and adapt to interface formats and permission rules of different systems. Monthly or quarterly update frequency means workflows do not need high-frequency triggering. Timed trigger or event trigger rules can be configured.
Structural differences between the four daily document types require workflow nodes to support custom field mapping, to accurately match core business fields such as asset ID and user. Time-consuming steps such as account-physical verification and user confirmation require embedding manual approval nodes in the workflow, while configuring exception branches to handle risk scenarios like asset loss and account-physical mismatch.

## How to set the configuration
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| Variable mapping rules | Match fields of asset ledgers and inventory sheets one-to-one | Aligns with the fixed field structure of documents in this category |
| Multi-source data trigger timing | Timed trigger at 0:00 on the 1st of each month, or trigger on procurement, loan, or scrap events | Fits the monthly, quarterly, or annual data update frequency |
| Failure retry count | 2 times, 60-second interval | Addresses temporary interface fluctuations, avoids repeated data triggering |
| Node timeout threshold | 300 seconds | Adapts to the average time required for multi-source data pulling |
| `variables` configuration | Only bind core asset fields (ID, user, status) | Reduces invalid variable passing and lowers debugging complexity |
| `nodeId` identifier | Assign a unique identifier to each data source node | Facilitates workflow debugging and exception locating |

## Three common errors
- API call text splicing results have empty variable fields. The symptom is that returned results only contain fixed text, and variable placeholders are not replaced. The cause is that the mapping of the corresponding asset field is not configured in `variables`, or the variable scope does not cover the API call node.
- Workflow concurrent calls cause front-end interface unresponsiveness. The symptom is that the operation interface freezes, but container resources do not reach the threshold. The cause is that node concurrency limits are not configured, and multiple tasks pulling multi-source data simultaneously causes interface call overload.
- Unable to call external interfaces based on incoming identifiers in the workflow. The symptom is that external interfaces return permission errors. The cause is that the identifier is not passed to the workflow node as a `variables`, or the corresponding variable is not bound in the external interface call configuration.

## How to confirm the configuration is complete
- Manually trigger the workflow, check whether the returned results include core fields of the asset ledger, and whether variable replacement meets expectations.
- Call the test API to verify that the returned results are consistent with those of manual triggering, and no variable fields are missing.
- Configure the timed trigger rule, check whether the scheduled task starts according to the set cycle, and the data pull range meets the update frequency requirements.
- Simulate the data source interface timeout scenario, verify whether the workflow enters the preset failure handling branch.

The values given are common starting points and should be measured against the reader's own samples.
