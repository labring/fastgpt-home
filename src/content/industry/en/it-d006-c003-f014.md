# Test Case and Defect Analysis for IT Asset Inventory: Model Access and Configuration

## What data looks like for this category
Data for this category comes from asset management systems, procurement systems, financial fixed asset modules, and terminal management platforms. Four types of documents are routinely generated: asset ledgers, inventory sheets, loan and return forms, and scrap applications. Data update cycles are monthly, quarterly, or annual. Core fields include asset number, ownership entity, storage location, user, purchase date, status, and others. There are no unified mandatory units. Some assets require association with financial fields such as purchase amount and depreciation period. High-time-consuming links in business processes include account-physical verification, user confirmation, and scrap material organization. Data anomalies can lead to asset loss, financial account discrepancies, and audit issues.

## What constraints these characteristics impose on model access and configuration
Data sources for this category are scattered, covering multiple types of business systems, with wide variation in update cycles. This requires model access to adapt to format parsing of multi-source heterogeneous data, to prevent field missing that causes account-physical verification failure. Documents such as asset ledgers contain multi-field associated content, so models must support context-aware association matching to ensure accurate correspondence of core information such as ownership and user. Scrap application documents rely on historical asset status, so models must stably retain long context information to avoid truncation that causes process errors. Data anomalies can lead to serious business consequences, so error verification must be strengthened during configuration to intercept input that does not comply with business rules in advance.

## How to set configurations
The following configurations are formulated based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–16000 token` | This category of documents contains multi-field associated content, requiring sufficient context to match asset ownership and user information |
| `maxTokens` | `2000–3000 token` | Parsing of a single inventory sheet or ledger entry requires controlling output length to avoid resource waste |
| `quoteMaxToken` | `500 token` | Limit the length of referenced original document fragments to ensure the context is tidy and focused on core asset information |
| `vision` | Enabled | Some asset documents include physical photos or inventory labels, requiring support for visual information parsing |
| `temperature` | `0.2–0.4` | Defect analysis for asset inventory requires strict logical consistency, avoiding random deviations that affect account-physical verification results |
| `toolChoice` | `auto` | Allow the model to independently choose whether to call tools to process multi-source heterogeneous asset data |

## Three common misconfigurations
- Phenomenon: After enabling the `vision` configuration, when uploading an asset document with physical photos, the model return result does not include image parsing content, and fields are empty. Cause: The model endpoint supporting visual capabilities is not correctly configured, or the used model does not integrate visual decoding components.
- Phenomenon: A specific model is selected in application settings, but another model is called during test chat or analysis. Cause: The association configuration between the application and model channel is not correctly bound, or there is a default model override setting in the channel configuration.
- Phenomenon: A 401 unauthorized error is returned when calling the model interface, prompting that the key or authentication information is invalid. Cause: `AIPROXY_API_TOKEN` is configured incorrectly (inconsistent with the AI Proxy server configuration or empty), or `AIPROXY_API_ENDPOINT` is configured incorrectly (such as appending a /v1 path or using a single-model address).

## How to confirm configuration is complete
- View model call logs to confirm that the preset configuration item values are included in the request parameters, consistent with the recommended values in the table.
- Upload a test asset document containing both text and images to verify that the model can correctly parse fields and generate analysis results that comply with business logic.
- Check the status code returned by the interface to confirm there are no authentication-related errors, ensuring that the configured authentication information is valid.
- Adjust the `toolChoice` parameter to a specified value to verify whether the model call behavior matches the configured expectations.

The values provided are common starting points and should be measured against the reader's own samples.
