# Test Cases and Defect Analysis for Issue Triage and Response: Tool Calling and Plugins

## What Data Looks Like for This Use Case
Typical users for this use case are open source maintainers, community operators, and core contributors. Data sources primarily include GitHub or Gitee Issues, code repository version logs, user-submitted environment information, and problem reproduction descriptions. Daily maintained documentation includes Issue templates, label rules, and historical response records. Data update frequency is typically daily or weekly, triggered by new community-submitted issues and version iteration records. Data fields include problem title, description, labels, priority, associated code modules, user environment information, and other fields. There are no uniform fixed units, as values vary based on specific Issue content.

## Constraints Imposed on Tool Calling and Plugins
Data sources for this use case are scattered and have inconsistent structures. Tool calling and plugins must support pulling data from multiple sources, including GitHub Issue APIs and code repository commit records. Data update frequency is not fixed, so plugins must be configured with scheduled synchronization tasks to ensure data timeliness. Daily maintained Issue templates and label rules require tools to support automatic matching of preset labels and population of standard response templates. Since problem classification and completion of reproduction information are core time-consuming steps, tools must include built-in semantic parsing capabilities to automatically extract key problem information and reproduction steps.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | Set to `"auto"` | Adapts to multi-tool calling needs for Issue triaging, automatically selects appropriate plugins to handle problem classification and information extraction tasks |
| `functionCall` | Enable and bind preset label rules and Issue templates | Used to automatically match parsed Issue content to labels and populate standard response templates |
| Plugin timeout threshold | 600 seconds | Adapts to API response durations for most code hosting platforms, prevents task interruptions due to network fluctuations |
| Data synchronization frequency | 2:00 AM daily | Matches the daily/weekly update rhythm of this use case’s data, reduces unnecessary API calls |
| Label matching confidence threshold | 70%-85% | Balances automatic classification accuracy and recall rate, adapts to custom label rules for different communities |

This configuration applies to FastGPT v4.17.0.

## Three Common Misconfigurations
- The application name displayed during plugin calls does not match the preset value, only a generic identifier is shown. This occurs when a custom application name is not filled in the plugin configuration, or the configuration has not been synchronized to take effect.
- Custom secrets cannot trigger tool calls, and conversation logs show call failures without clear error messages. This occurs when the secret is not bound to the corresponding tool call permission, or the secret configuration fails format validation.
- Automatic classification results deviate significantly from actual Issue labels. This occurs when the label matching threshold is set too high or too low, and does not adapt to the current community’s Issue label distribution characteristics.

## How to Verify Proper Configuration
- A simulated Issue is submitted. Check whether the tool automatically triggers the label matching and template population process, and verify whether the trigger timing matches the preset configuration.
- Tool call logs are reviewed. Confirm that the custom secret has passed permission validation, and there are no failed call error records.
- The label matching threshold is adjusted. Compare classification results across different confidence levels to confirm the threshold setting aligns with the current community’s label rules.
- The data synchronization task is verified to execute on schedule. Check whether recently updated Issues have been automatically pulled into the system.

The values provided here are common starting points and should be measured against the reader's own samples.
