# Test Cases and Defect Analysis for Issue Triage and Response: Model Access and Configuration

## What this category’s data looks like
The core data of this category comes from GitHub or Gitee Issues, code repository version logs, user-reported environment information and problem reproduction instructions. Daily maintenance documents include Issue submission templates, tag rule libraries, historical response records, and similar content. Data update frequency is daily or weekly. Single data volume ranges from simple queries of tens of characters per entry to complete reproduction steps of hundreds of characters. Typical users include open source project maintainers, community operations staff, and core contributors. These users rely on this data to complete problem classification, priority marking, and response assignment.

## What constraints do these characteristics impose on the "model access and configuration" link
This category’s data is mostly unstructured natural language text with large format differences. This requires models to have flexible text understanding and classification capabilities. Data update frequency is tied to community activity levels. Call volume fluctuates during peak periods, so appropriate concurrency and timeout parameters must be configured. The data contains key information such as reproduction steps and tag fields. Models must accurately identify and map these to preset triage rules. At the same time, error handling must cover scenarios such as network connection exceptions and parameter format errors, to prevent overall process backlogs caused by failure to process a single Issue.

## How to set configurations
| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000-12000 token | Matches the full context of Issues including reproduction steps, tag descriptions, and historical responses, to avoid truncation of critical information |
| `maxTokens` | 2000-3000 token | Adapts to the output length requirements of triage responses, balancing the content volume of classification results and supplementary explanations |
| `temperature` | 0.3-0.5 | Maintains stability of classification results, reduces random fluctuations, and aligns with standardized rule requirements for Issue triage |
| `AIPROXY_API_ENDPOINT` | Fill in the root address of the AI Proxy service according to the deployment environment, for example http://aiproxy:3000 | Adapts to network configurations for Docker or local deployments, ensures normal AI Proxy service call links. Do not append /v1 or /chat/completions paths |
| `AIPROXY_API_TOKEN` | Fill in a non-empty admin token consistent with the AI Proxy server configuration | Completes identity verification for the AI Proxy service, ensuring legitimate call permissions |

## Three common mistakes
- Symptom: A connection timeout error is returned when calling the model, and the log shows the `ECONNREFUSED` status code. Troubleshooting steps: Check if `AIPROXY_API_ENDPOINT` is configured as the correct root address of the AI Proxy service, check if `AIPROXY_API_TOKEN` is correctly configured and non-empty, and verify if the deployment environment can access the AI Proxy service endpoint.
- Symptom: After adding the Volcengine DeepSeek-R1 model in a Docker deployment environment, the corresponding entry does not appear in the channel list. Cause: The model identifier and proxy endpoint were not correctly bound in the configuration file, or the service was not restarted after deployment to make the configuration take effect.
- Symptom: After updating FastGPT v4.17.0 for local deployment, the model does not respond after uploading test case attachments. Troubleshooting steps: Check if `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are correctly configured, check if the `maxContext` parameter meets the requirements, and verify if the deployment service has been restarted.

## How to confirm the configuration is complete
- Manually submit a simulated GitHub Issue containing reproduction steps and defect descriptions, and check if the classification tags returned by the model conform to the preset tag rules.
- Check if `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` in the server deployment configuration are correctly configured and formatted to meet the requirements of the AI Proxy service.
- View the system operation logs to confirm that there are no model call failure error records within 10 consecutive minutes.
- Upload a standard test case document to verify whether the model can correctly extract reproduction steps and defect fields and generate corresponding triage suggestions.
