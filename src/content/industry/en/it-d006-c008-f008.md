# Test Cases and Defect Analysis for Special Event Operations: Workflow Orchestration

## What Data for This Category Looks Like
Core data for special event operations comes from content libraries, event backends, traffic metrics, and user feedback. Update cycles follow a weekly schedule, with temporary adjustments before and after holidays. Daily deliverables include event plans, resource slot schedules, event page copy, and post-event review reports. Common data fields include event cycle, resource slot ID, user participation volume, and content review status. No unified fixed field format exists, and adjustments must align with the specific needs of each individual event.

## What Constraints These Characteristics Impose on Workflow Orchestration
Scattered data sources and inconsistent update cycles require workflows to support multi-source data pull nodes and flexible trigger rules. Diverse document types and inconsistent field requirements mean workflow `variables` configuration must support dynamic adaptation of field passing for different documents. Event errors can lead to low participation or resource waste, so explicit failure handling and alert links must be configured. Special events have clear cycles, so workflows must adjust execution node start/stop rules to match the event cycle.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | Trigger based on event node launch time, or scheduled weekly trigger | Matches the event cycle and update frequency of special event operations |
| Global Variable Configuration | `variables` supports string array assignment | Adapts field passing for multiple types of documents such as event copy and schedule |
| Maximum Number of Runs for Batch Execution Nodes | 1000 runs | Matches the platform's default batch execution limit to avoid resource overload |
| Batch Input Length Limit | 800–1200 characters | Adapts the typical single-item content length of event page copy and post-event review reports |
| Node Timeout Threshold | 600 seconds | Prevents workflow stalling due to delays in event backend interfaces |
| Failed Node Location | Mark failed nodes by `nodeId` | Compatible with FastGPT v4.17.0's node location feature to accurately identify error links |

## Three Common Misconfigurations
- Symptom: Workflow node connections appear normal, but execution always gets stuck at the current node, and the page shows a "Pending" status with no changes. Cause: No `variables` passing rules are configured between nodes, so downstream nodes fail to retrieve event data output by upstream nodes.
- Symptom: AI reply content generated by calling the FastGPT API has variable stacking, with results from previous runs appended to the current result. Cause: The `variables` context cache is not reset, so variable values from prior rounds remain.
- Symptom: Global variable string arrays cannot be assigned normally, and the workflow reports a "field format error" during execution. Cause: Parameters are not passed in array format, missing square bracket wrapping or comma separation requirements.

## How to Confirm Proper Configuration
- Manually trigger a small-scale test workflow, and use FastGPT v4.17.0's logging system to check whether each node's output logs match the actual data of event copy and resource slot schedules.
- Configure a batch execution node, input a small number of test cases, and confirm that the number of runs stays under the 1000-run limit.
- Simulate a node failure scenario to verify that the preset retry mechanism and alert notifications trigger correctly.
- Review global variable assignment logs to confirm that string array formats follow square bracket wrapping and comma separation rules.

The values listed above are common starting points, and should be evaluated against the reader's own samples.
