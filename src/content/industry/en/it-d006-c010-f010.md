# Test Cases and Defect Analysis for Incident Response and Troubleshooting: Citation Sources and Traceability

## What data looks like for this category
Data for this category comes from monitoring alerts, log platforms, APM tools, and user feedback. Updates occur in real time or immediately after a single event is triggered. Daily produced documents include fault tickets, event timelines, emergency response plans, and fault notifications. Data fields include event unique identifiers, alert trigger times, affected service scopes, stop-loss operation records, external notification recipients, and more. Fields are dynamically adjusted based on specific event scenarios, with no unified fixed units.

## What constraints these characteristics impose on citation sources and traceability
Data sources are scattered and updated in real time. Citation traceability must cover associated data from multiple systems. Cross-source correlation must be completed using event unique identifiers. The volume of documents for a single event increases with fault complexity. Traceability data scope must be limited to avoid context overload. Fault scenarios have high timeliness requirements. The traceability link must support quick location of associated documents by event timeline. Traceability results must be strongly bound to the current responding fault event, to avoid referencing irrelevant historical event data. Differences in fields between documents such as fault tickets and notifications require traceability configurations to support custom field matching rules. This ensures referenced content is directly relevant to the current fault handling scenario, reducing invalid traceability results.

## How to set the configuration
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | Matches the single-entry content length of fault tickets and event timelines, avoiding context overload |
| `responseData` | Return only associated source data | Ensures traceability results only include document content relevant to the current fault event, filtering irrelevant data |
| `detail` | Enable full field display | Facilitates matching core fields such as event unique identifiers and alert times to complete cross-source correlation |
| Single search limit | Top 3 results | Limits the number of traceability return results, avoiding redundant information interfering with fault judgment |
| Traceability matching threshold | 0.75–0.85 | Calibrated via actual testing, balancing recall accuracy and coverage |
| Context window size | 600 seconds | Matches the fault event processing cycle, ensuring traceability data covers the full period from event occurrence to the current time |

## Three common configuration errors
- Symptom: Returned fault handling recommendations are unrelated to associated traceability data. Referenced documents do not match the currently processed event ID. Cause: No field matching rule based on event unique identifiers is configured, causing irrelevant historical event documents to be recalled.
- Symptom: Traceability link times out. The interface returns a request failure status code. Cause: No reasonable context window size is set, causing the system to attempt loading excessive historical data beyond the response time limit.
- Symptom: After enabling the `detail` configuration, returned traceability data contains a large number of non-core fields, interfering with fault judgment. Cause: The `responseData` configuration that returns only associated source data is not enabled, causing redundant non-event-related fields to be recalled.

## How to confirm the configuration is correct
- Import a simulated fault ticket, trigger the traceability process, and verify returned reference data includes the ticket’s unique identifier.
- Adjust the value of `quoteMaxToken`, and verify the length of returned traceability content matches the set range.
- After configuring visibility rules, verify reference display in fault notification scenarios meets preset requirements.
- Simulate a timeout scenario, and verify the traceability link completes data recall within the set context window.

The values provided are common starting points and should be measured against the reader's own samples.
