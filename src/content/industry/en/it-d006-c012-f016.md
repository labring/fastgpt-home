# Test Cases and Defect Analysis for Cloud Networking and Load Balancing Configuration: Forms and Interactions

## What Data for This Category Looks Like
This category’s daily documents include four core file types: VPC planning, security group rules, load balancing configuration, and change orders. Data sources include cloud platform consoles, network topologies, traffic monitoring, and customer architecture diagrams. Update frequency is once per order or per change. Data fields include private network segments, listening ports, health check thresholds, backend server group IDs, and others. There is no unified fixed format template. Configurations must match the actual cloud resource configuration structure of the customer. Field priorities and required items vary across different customers.

## What Constraints These Characteristics Impose on the Forms and Interactions Link
Daily documents use a fixed change order field structure. Forms must preset core field items aligned with change orders to prevent users from missing required configurations. Data comes from real-time resource status in cloud consoles. Interactions must support connecting to external cloud platform APIs to pull existing configurations for port occupation and network segment conflict verification. Update frequency is once per order or per change. Forms must support incremental submission of single records, with real-time verification handled by external business systems or subsequent nodes. Data must match the customer’s cloud resource permissions. Interactions must connect to cloud platform APIs to limit selectable resource scope to available resources under the current account, preventing cross-account selection errors. | --- | --- | --- |
| Form input node `formInput` | Test example: Select 3 fields from cloud networking and load balancing configuration fields as required inputs; actual fields are determined by the task | This node collects user input; when required items are missing, interaction status must be checked to prevent subsequent nodes from obtaining incomplete input |
| User selection node `userSelect` | Test example: Set 2 business options, check corresponding branches one by one | This node handles user selection; querying and filtering records related to cloud networking and load balancing configuration must be implemented by subsequent APIs or external systems |

## Three Common Mistakes
- Workflow interruption occurs after form submission. The root cause is that required field validation for the `formInput` node is not configured, leading to incomplete collection of configuration information. This validation is handled by external business systems or subsequent nodes.
- A port conflict error appears after submitting load balancing configuration. The root cause is that the cloud platform port occupation verification API is not connected, and the list of ports already in use under the current cloud account is not pulled. This verification is handled by external business systems.
- No effective feedback is displayed after saving health check configuration. The root cause is that the cloud platform configuration status query API is not connected. Configuration submission status synchronization is handled by external business systems, and the effective status must be confirmed through the cloud platform console.

## How to Confirm Proper Configuration
- The form’s variable pool panel is accessed, and optional variables corresponding to preset fields such as network segments, ports, and backend server groups are confirmed to be included.
- A test configuration is submitted, and whether the external business system can pull backend server group options under the current cloud account is checked.
- An invalid network segment or port is entered, and whether the external business system or subsequent nodes display a format error prompt is confirmed.
- The configuration list in the cloud platform console is viewed after saving the configuration, and whether the newly added configuration items have been synchronized and updated is confirmed.
