# Test Cases and Defect Analysis for Cloud Resource Compliance Audit: Workflow Orchestration

## What data for this category looks like
Data for this category originates primarily from cloud audit logs, IAM permission systems, CMDB resource inventories, and security baseline scan results. Core regularly produced documents include compliance checklists, permission audit reports, resource inventory lists, and rectification tracking ledgers. The data update cycle is monthly or quarterly. Each document includes fields such as resource unique identifiers, permission configuration items, compliance check status, and associated rectification records. Check results are recorded only as text and enumeration values, with no fixed statistical unit.

## What constraints these characteristics bring to workflow orchestration
The data sources for this category are scattered and structurally complex. Workflows must support connecting multi-source data pull nodes, sequentially integrating with different data sources such as cloud audit logs and IAM permission systems. The monthly or quarterly data update cycle means workflows do not need to trigger frequently, but must support batch processing of full resource data for a single batch. Documents contain multiple non-standardized fields, so workflows need to include classification nodes to pre-classify resources and permission items, and check nodes to verify field integrity. This prevents compliance audit process interruptions caused by missing fields.

## How to configure settings
The following configurations are based on the workflow orchestration interface of FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Custom variable group including resource ID, compliance status, and rectification status | Must carry core compliance audit data passed across nodes, ensuring all process links can read unified business fields |
| `nodeId` | Assign a unique identifier to each data source pull node and classification node | Must precisely control the pull order and branch jump logic of multi-source data, to avoid node conflicts |
| Workflow trigger timing | 2:00 AM on the 1st of each month, or trigger according to the compliance check cycle | Matches the monthly/quarterly update frequency of data for this category, avoiding repeated processing of already verified historical data |
| Failure retry count | 2 times, with a 300-second interval | Addresses temporary fluctuations in cloud API calls, avoiding compliance audit process interruptions caused by a single failed call |
| Context window length | 8000–12000 token | Carries long text content of compliance reports, ensuring AI chat nodes can fully read audit-related data |
| Branch matching threshold | Top 3 highest-confidence classification results | Fits the multi-dimensional resource classification needs in compliance checks, avoiding process deviation caused by misclassification |

## Three common misconfigurations
- Phenomenon: The text classification extraction node returns no values, with no classification results. Cause: The `variables` binding for the compliance audit text field to be classified is not configured, or the node’s input text has not passed pre-checks, preventing the node from parsing normally.
- Phenomenon: After the workflow completes an AI chat, it cannot jump to the preset rectification tracking branch, and instead returns to the initial classification node. Cause: A correct `nodeId` jump rule is not configured after the AI chat node, or the branch matching conditions do not align with the identifiers of subsequent nodes.
- Phenomenon: After importing an old-version workflow, custom tool variables cannot be called normally. Cause: The `variables` definition format of the old version differs from that of FastGPT v4.17.0, and variable binding rules have not been updated to adapt to the new version.

## How to confirm the configuration is correct
- Manually trigger the workflow for a single resource, and verify that the fields passed in `variables` match the input resource data.
- View the running logs of the classification node, and confirm that the returned classification results match the preset branch rules.
- Simulate a cloud API call failure scenario, and confirm that the workflow triggers the failure retry mechanism and continues the process after retries.
- Export the workflow configuration file, and verify that `nodeId` values are unique and the jump logic matches the design plan.

The values listed here are common starting points, and should be evaluated against the reader's own samples.
