# Test Case and Defect Analysis for Code Security Audit: Workflow Orchestration

## What Data for This Category Looks Like
Data for this category primarily comes from project source code repositories, third-party dependency lists, static code scanning (SAST) tool outputs, and public vulnerability databases. Update frequency is adjusted based on project version iterations or special audit cycles, typically once per version or per project. Daily produced documents include code audit reports, vulnerability proof materials, repair recommendation documents, and retest records. Fields cover dangerous function location results, data flow tracking paths, vulnerability severity levels, repair status, and other details. Some content includes unstructured analysis of business logic attack paths.

## Constraints Imposed on Workflow Orchestration by These Characteristics
Data for this category is multi-source, scattered, and has significant format differences. Structured fields from static code scanning outputs and unstructured descriptions from vulnerability databases must be aligned and aggregated in the workflow. Unlike static code scanning categories, this category requires manual business logic review nodes in the workflow. The workflow must support flexible insertion of approval steps. The characteristic that data updates with project versions requires the workflow to support binding dynamic parameters such as project repository addresses and version numbers via `variables`. Daily documents include multiple types of associated files. The workflow must configure file transfer and association logic between nodes. The most time-consuming analysis links need to set node execution duration limits. Insertable approval nodes must be reserved for manual review links to avoid missing high-severity vulnerabilities due to automated process interruptions.

## Configuration Settings
| Configuration Item | Suggested Approach | Rationale |
| --- | --- | --- |
| Variable Binding | Reference project repository address and version number parameters in `variables` | Aligns with FastGPT v4.17.0 workflow variable binding rules, ensuring retrieval of the latest source code and vulnerability database data |
| Node Execution Timeout Limit | 1800 seconds | Covers the maximum time required for core analysis links such as dangerous function location and data flow tracking |
| Data Association Configuration | Associate audit reports and retest records by project ID | Matches the associated storage and retrieval logic of daily documents |
| Manual Review Node Insertion | Place after the repair solution review step | Reserves an operation entry for manual verification of repair solutions |
| Failure Alert Trigger | Bind failed nodes marked by `nodeId` | Accurately locates the specific execution link where the workflow interrupted |
| Form Input Component Configuration | Support variable input | Adapts to business requirements for dynamically adjusting audit scope |

## Three Common Misconfigurations
- No user interaction prompt when the workflow is accessed via API: The phenomenon is that no input guidance or parameter pop-up is returned after calling the interface. The cause is that the return parameter binding of the user input node is not configured in the workflow, causing the API call logic to not trigger interaction verification.
- Form input component reports an error after passing variables: The phenomenon is that an invalid parameter prompt is displayed when submitting the configuration. The cause is that the `variables` parameters are not correctly mapped to the binding fields of the form component, and the variable format does not meet the node receiving rules.
- Code running node fails to extract preset variable values: The phenomenon is that the target field is shown as empty in the logs. The cause is that the output mapping of the corresponding field is not configured in the preceding node, and the variable is not correctly written to the workflow context.

## How to Verify Correct Configuration
- Check if the `variables` parameters in the FastGPT v4.17.0 workflow editor are correctly bound to input nodes and form components. Use preview mode to input test parameters and verify whether values are normally passed.
- Manually trigger a node execution timeout, confirm that an alert notification is triggered for the failed node marked by `nodeId`, and verify that the failure alert logic works correctly.
- Import test project source code and vulnerability data, run the workflow, and check the association between the audit report and retest records to confirm that the data association logic is normal.
- Use the published API address to pass valid parameters, confirm that the corresponding workflow node is triggered and expected interaction prompts or analysis results are returned.

The values given are common starting points and should be measured against the reader's own samples.
