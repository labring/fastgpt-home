# Test Case and Defect Analysis for Code Security Auditing: Forms and Interactions

## What this category of data looks like
This category of data primarily originates from source code repositories, dependency lists, static application security testing (SAST) tools, and public vulnerability databases. Update frequency adjusts based on project version iterations or the timeline of individual audit tasks.
Daily generated documents include code audit reports, vulnerability proof documents, repair suggestion lists, and retest records. Common fields include unique vulnerability identifiers, dangerous function location information, data flow trace links, repair status, and risk level. There is no fixed unified unit, and values vary based on the specific content of each audit item.

## Constraints imposed by these characteristics on forms and interactions
Multiple data sources require external business systems or downstream nodes to support batch import of audit materials in various formats. It also requires configuring data deduplication and format verification rules to prevent duplicate entry of vulnerability information.
The update frequency tied to project iterations requires external business systems or downstream nodes to support incremental synchronization of uploaded audit data, eliminating the need to resubmit full files.
The diverse document structure requires external business systems or downstream nodes to split entry modules by audit phase, matching the field requirements of different documents such as code audit reports and vulnerability proofs.
The long duration of core time-consuming phases requires external business systems or downstream nodes to support temporary saving of entry progress, preventing duplicate work caused by operation interruptions.
The severe consequences of high-risk vulnerabilities being deployed require external business systems or downstream nodes to configure mandatory verification for key fields, ensuring complete core audit information.

## Three common mistakes
- Batch import of vulnerability lists causes continuous page refresh, making import progress unviewable. The cause is that external business systems or downstream nodes do not have progress feedback logic configured, preventing the frontend from synchronizing import status.
- Omitting the risk level field when entering repair suggestions, with no verification prompt triggered after submission. The cause is that external business systems or downstream nodes do not have mandatory verification logic configured for the corresponding field, leading to invalid data submission.
- Duplicate import of existing vulnerabilities during incremental synchronization of audit data. The cause is that external business systems or downstream nodes do not have multi-source data deduplication rules configured, only checking duplicates based on a single field.

## How to confirm correct configuration
- Upload batch vulnerability list files through external business systems or downstream nodes, verify that fields are automatically parsed and an import progress bar is displayed.
- Skip mandatory fields configured by external business systems or downstream nodes when submitting a form, confirm that a verification prompt for the corresponding field pops up.
- Interrupt the entry operation, then re-enter the form of the external business system or downstream node, confirm that the previously saved entry content is restored.
- Import existing vulnerability data, confirm that external business systems or downstream nodes automatically filter duplicate items and display prompt information.
