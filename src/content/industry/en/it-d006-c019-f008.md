# Test Cases and Defect Analysis for Crowdsourced Annotator Management: Workflow Orchestration

## What the data for this category looks like
Core data for crowdsourced annotator management draws from crowdsourcing platforms, annotation quality data, training and examination systems, and financial systems. Daily associated documents include personnel access rules, annotator training materials, monthly performance reports, and settlement statements. Data update cycles are split into daily and monthly updates: annotation quality data and performance reports update daily, while personnel access rules and settlement statements update monthly. Data fields include unique personnel identifiers, admission review status, training assessment scores, annotation accuracy, performance rankings, settlement amounts, and more. No unified fixed format exists, and adaptation is required per the field rules of different systems.

## What constraints do these characteristics impose on the "workflow orchestration" link
Multi-source data access requires workflows to pull fields of different formats across systems, avoiding data flow interruptions. Differences in update cycles require matching workflow node trigger cycles: daily update data needs daily trigger nodes, monthly update data needs monthly trigger nodes, otherwise data lag or repeated processing will occur. Document structure diversity requires workflows to support multi-variable configuration to adapt to field extraction needs for different documents, breaking the limitation of single-variable drop-down menus. Clear error consequences mean workflows must be configured with failure handling and alert mechanisms to prevent quality fluctuations, incorrect or missed payments, or project delays caused by incorrect personnel screening or settlement verification errors.

## How to set the configuration
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| Variable Group (`variables`) | Bind combined variables for personnel ID, training score, annotation accuracy, and settlement amount, support multi-field reference | Cover the field requirements of four core data sources, break the limitation of single-variable drop-down menus, and adapt to multiple document structures |
| Node ID (`nodeId`) | Associate node IDs of quality inspection, performance statistics, and settlement verification links | Enable automatic data flow across links, avoid errors caused by manual intervention |
| API Parameter Configuration | Use the fields bound by `variables` as input parameters for API requests, assign values according to the format required by the system | Adapt to API call requirements with global variables, meet the parameter assignment requirements of test cases |
| Knowledge Base Reference Validation | Add a large model node in the workflow, call the annotation quality data bound by `variables` to compare with knowledge base content, identify unreasonable references | Fulfill the core requirements of test cases and defect analysis, automatically check reference issues in annotation content |
| Trigger Timing | Trigger daily update data nodes at 2 AM daily, trigger monthly update data nodes on the 1st of each month | Match the daily update rhythm of annotation quality data and performance reports, and the monthly update rhythm of access rules and settlement statements |
| Failure Retry Count | Retry 2 times | Adapt to the verification delay of annotation quality data, avoid process interruption caused by single abnormal occurrence |

## Three common mistakes
- Phenomenon: Settlement statement fields are empty, causing the settlement process to get stuck. Reason: The financial system’s settlement data fields are not bound in the `variables` configuration, or the `variables` parameters are not correctly assigned for API calls, causing the workflow to fail to extract core information such as settlement amounts.
- Phenomenon: Quality inspection results are not synchronized to the performance report, leading to incorrect personnel quality rankings. Reason: The `nodeId` is not associated with the quality inspection node and performance statistics node, causing quality inspection data to fail to automatically flow to the performance statistics link, affecting the accuracy of defect analysis.
- Phenomenon: The workflow triggers personnel screening before training is completed, resulting in untrained annotators entering the project. Reason: The trigger timing is configured before training starts, violating the process order of personnel access rules, causing unqualified personnel to participate in annotation and triggering quality fluctuations.

## How to confirm the configuration is correct
- Check whether the `variables` configuration includes the four core fields of personnel ID, training score, annotation accuracy, and settlement amount, confirm that field binding from multiple data sources is complete and supports multi-variable reference.
- Verify whether the `nodeId` is associated with the nodes of quality inspection, performance statistics, and settlement verification links, confirm that the cross-link data flow path is correct and there are no manual intervention breakpoints.
- Simulate the scenario where personnel admission review is completed, confirm that the workflow automatically triggers the training material push node, and verify that the process trigger logic complies with personnel access rules.
- Simulate the scenario where annotation content has unreasonable references, confirm that the large model node automatically identifies and returns abnormal reference content, and verify that the knowledge base reference validation function is effective.
- Simulate the scenario where settlement data is abnormal, confirm that the workflow triggers an alert and pauses the subsequent settlement process, and verify that the failure handling mechanism is effective.
