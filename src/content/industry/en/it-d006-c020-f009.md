# Test Cases and Defect Analysis for Supplier and Equipment Delivery Management: Tool Invocation and Plugins

## What data for this category looks like
Data for this category typically comes from ERP systems, supplier shipping invoices, logistics tracking information, and equipment manufacturer backends. Daily processed documents include purchase orders, delivery acceptance slips, serial number lists, and invoice materials. Each order corresponds to an independent dataset. Data updates follow per-order cycles. Some bulk delivery scenarios use weekly update cycles. Data fields include purchase model, serial number, delivery quantity, acceptance status, and supplier information. No unified mandatory units apply. Some fields must match the exclusive coding rules of equipment manufacturers.

## Constraints imposed by these characteristics on tool invocation and plugins
Data for this category is scattered across multiple systems and documents. Tool invocation must adapt to format differences across data sources. This requires configuring plugin rules for multi-source data pulling. Data updates follow per-order or weekly cycles. Tool trigger timing must match business process nodes to avoid invalid calls that consume resources. Fields include exclusive device codes and serial numbers. Tool invocation parameters must clearly define field mapping rules to prevent data mismatches. Errors directly impact project delivery. Failure retry and data verification logic are required for tool invocation.

## Recommended configuration settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `functionCall` | Mandatory enabled | Adapts to standardized invocation processes for multi-source data pulling, and matches the per-order data processing logic of purchase orders |
| `toolChoice` | Set to auto | Lets the large language model automatically select appropriate tool invocations, and adapts to multi-source data pulling scenarios |
| Call timeout | 600 seconds | Addresses interface response delays from logistics information and equipment manufacturer backends |
| Field mapping rules | Purchase model → Device model, Serial number → Asset code | Matches the exclusive field naming of this category of data, prevents data mismatches |
| Retry count | 2–3 times | Addresses temporary interface fluctuations, reduces the probability of single invocation failure |
| Maximum number of invocations | Under 10 entries | Matches the typical data volume of a single order, avoids interface overload |

## Three common configuration mistakes
- Scenario: Invoking the HTTP interface for a multi-dimensional table tool returns a 403 permission error or empty fields. Root cause: No category-specific field mapping rules are configured. Generic fields are passed directly to the interface, which does not meet the column name requirements of the multi-dimensional table.
- Scenario: Invoking the interface for an equipment manufacturer backend returns no results or times out without a response. Root cause: No reasonable call timeout duration is set, and no retry mechanism is configured. This cannot address interface delays or temporary fluctuations.
- Scenario: After invoking a MySQL database using the `functionCall` tool, the large language model’s response does not reference raw database snippets. Root cause: Raw database snippets returned by tool invocations are not included in the large language model’s context, so the model cannot reference the corresponding content.

## How to verify correct configuration
- Manually trigger a tool invocation. Check if the returned results include category-specific fields such as purchase orders and serial numbers, and confirm that the field format matches business documents.
- Simulate a single delivery scenario’s invocation process. Check if the tool automatically pulls corresponding logistics information and equipment manufacturer data after triggering.
- After configuring the failure retry logic, simulate an interface timeout scenario. Confirm if the tool triggers retries according to preset rules.
- Verify the parameter statuses of `functionCall` and `toolChoice`. Confirm that the configuration meets the standard requirements of FastGPT v4.17.0.
