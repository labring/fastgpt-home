# Test Cases and Defect Analysis for Supply Chain Security and Open Source Dependency Governance: Tool Calling and Plugins

## What This Category of Data Looks Like
Data for this category typically originates from package managers, code repositories, public vulnerability databases, and license databases, with updates occurring daily or whenever a software version is released. Daily generated documents include SBOM lists, dependency risk reports, license compliance lists, and vulnerability repair tickets. Fields cover component names, version numbers, vulnerability CVE IDs, license types, risk levels, and additional relevant details. No custom statistical units are used, and the core focus is on asset and risk information for third-party open source components.

## What Constraints These Characteristics Place on the Tool Calling and Plugins Workflow
Since data sources are scattered and update frequencies are high, tool calling must support parallel multi-source pulling. It must also adapt to interface formats and authentication rules of different data sources. The standardization of fields in daily documents is limited, so plugin parameter passing must accurately match core identifiers such as component names and version numbers to avoid cross-component matching errors. The dependency asset identification and vulnerability matching steps take significant time. Tool calling must set a reasonable concurrency threshold to prevent overload during single calls. Format validation must also be performed on call results to prevent invalid data from entering subsequent risk assessment processes.

## How to Configure Settings
This configuration guide applies to the plugin system of FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Allows the system to automatically match plugins suitable for supply chain security scenarios, reducing manual configuration complexity |
| `functionCall` | `{"name":"pull_dependency_risk","parameters":{"scope":"all"}}` | Accurately triggers standardized calls for pulling dependency risks, meeting the core data acquisition needs of this category |
| Concurrent call limit | `10–15 times/second` | Avoids exceeding call rate limits of public vulnerability databases and package managers, adapting to daily business concurrency scenarios |
| Call timeout | `300–600 seconds` | Covers the longest time-consuming links of dependency asset identification and vulnerability version matching, preventing mid-process interruptions |
| Single call data limit | `500 MB` | Adapts to the maximum pull volume of a single batch of dependency assets, preventing data overload from single calls |
| Failure retry count | `2 times` | Addresses call failures caused by temporary network fluctuations or interface rate limiting, reducing the need for manual intervention |

## Three Common Misconfigurations
- Symptom: Tool calls return empty results when concurrent call volume reaches 2–3 times per second. Cause: No reasonable concurrent call limit is set, triggering rate limiting mechanisms from third-party data sources, resulting in some calls being dropped.
- Symptom: Multiple images cannot be passed correctly when passing parameters for plugins. Cause: No parameter passing format adapted for multimodal data is configured, and images are not converted to base64 or URL formats required by the plugin.
- Symptom: Plugin calls frequently fail after deployment, with prompts stating that the storage service requires public network access. Cause: The plugin storage path in the intranet environment is not configured correctly, public network access is incorrectly set as a mandatory requirement, and the storage link for intranet deployment is not adapted.

## How to Confirm Successful Configuration
- Review tool call logs to confirm that the parameters for each call match the configured items, with no missing or incorrect fields.
- Simulate daily business concurrency levels to verify that tool call return results are not empty and meet the format requirements of category documents.
- Check the plugin's storage configuration to confirm that dependency data can be read and written normally in the intranet environment, without requiring a public network access link.
- Trigger a complete dependency risk pulling process, and verify that the generated SBOM list matches the actual dependency assets.
