# Test Cases and Defect Analysis for Supply Chain Security and Open Source Dependency Governance: Forms and Interactions

## What data for this category includes
Data for this category primarily comes from package managers, code repositories, vulnerability databases, and license databases. Four core documents are routinely produced: SBOM lists, dependency risk reports, license lists, and repair tickets. Data updates follow two schedules: full daily updates and incremental updates triggered by version commits. Document fields include standardized entries such as dependency name, version number, license type, vulnerability severity, and repair status. The overall structure aligns with standard open source component governance workflows, so basic governance can be completed without additional custom extended fields.

## Constraints imposed on the "forms and interactions" workflow
Multiple data sources require configuring batch import and multi-data source linkage logic via external business systems or subsequent workflow nodes, to avoid repetitive manual entry operations and errors. Standardized document fields require configuring field mapping logic via external business systems or subsequent workflow nodes, to automatically match field names returned by different data sources and reduce manual configuration costs. High-frequency update schedules require configuring scheduled synchronization and event-triggered synchronization logic via external business systems or subsequent workflow nodes, to ensure data timeliness. Severe error consequences require implementing pre-validation logic via external business systems or subsequent workflow nodes, to pre-block high-risk dependencies, non-compliant licenses, and similar content, preventing risks from entering production environments.

## Three common configuration mistakes
- Phenomenon: Empty results are returned after configuring the vulnerability database data source. Cause: Permission scope was not correctly configured via external business systems or subsequent workflow nodes, resulting in no access to the target vulnerability database data source.
- Phenomenon: Dependency identification results lack fields after uploading an SBOM list. Cause: SBOM field mapping logic was not configured via external business systems or subsequent workflow nodes, resulting in failure to match fields returned by the data source.
- Phenomenon: Automatic dependency upgrade is not triggered after submitting a repair ticket. Cause: Synchronization trigger rules were not configured in the external code repository system, or the code repository synchronization interface was not associated via subsequent workflow nodes, resulting in governance rules failing to sync to the code repository.

## How to verify a complete configuration
- Upload a local test SBOM list, check whether external business systems or subsequent workflow nodes have completed matching of core fields such as dependency name and version number.
- Trigger a manual data sync, check whether the dependency asset identification results returned by external business systems or subsequent workflow nodes include the locally tested open source components.
- Simulate submitting a dependency version marked as high-risk, check whether external business systems or subsequent workflow nodes trigger preset blocking alerts.
- View the data update logs of external business systems or subsequent workflow nodes, confirm that full daily updates and incremental updates triggered by version commits are executing normally.
