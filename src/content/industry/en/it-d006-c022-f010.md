# Test Cases and Defect Analysis for Independent and Controllable IT Replacement: Citation Sources and Traceability

## What data for this category looks like
Data for this category primarily comes from existing system inventories, domestic hardware and software directories, test environment records, and publicly available vendor materials. Four types of documents are regularly produced: adaptation inventories, compatibility test reports, migration plans, and issue ledgers. Adaptation inventories include hardware and software models, version numbers, and compatibility verification statuses. Test reports are linked to test case IDs and defect severity levels. Data updates follow individual independent and controllable IT replacement project cycles, or synchronize with domestic hardware and software directory updates on a quarterly basis, with no fixed high-frequency update schedule.

## What constraints do these characteristics impose on the "citation sources and traceability" link?
The data characteristics of this category directly restrict the execution logic of the citation traceability link. Since data sources are scattered, including internal system inventories, external domestic hardware and software directories, and test environment records, it is necessary to accurately trace the original source of each cited fragment to avoid mixing adaptation data from different projects. Document structures vary significantly; field rules differ between adaptation inventories and issue ledgers, so the field formats of corresponding documents must be matched during traceability. Data updates follow project or quarterly cycles, so data update timestamps must be marked when citing to ensure the timeliness of adaptation verification. Additionally, defect data is linked to business system availability, so complete test environment and reproduction paths must be retained during traceability to ensure the credibility of citations.

## Three common misconfigurations
- Symptom: When `quoteMaxToken` is set too large, the returned results include redundant non-adaptation-related text, causing the large model's generated content to deviate from the test analysis theme. Cause: The token limit was not adjusted based on the actual length of IT adaptation documents, and blindly increasing the parameter led to context overload.
- Symptom: After batch uploading adaptation documents of 5kb in size, some documents show training exceptions, and automatic deduplication is not triggered when re-uploading, resulting in duplicate adaptation records in the knowledge base. Cause: Automatic deduplication configuration for the knowledge base was not enabled, or document hash identifiers were not matched during upload, so duplicate data was not cleaned up.
- Symptom: When citing test case data in the AI chat component, the correct citation ID cannot be obtained, leading to traceability failure. Cause: The knowledge base file collection ID was mistakenly used as the citation ID, instead of the single queried data entry ID as the traceability identifier.

## How to verify that configurations are correctly set up
- Run a query for independent and controllable IT adaptation defect analysis, and check whether returned results include complete citation metadata including fields such as file ID and test case ID.
- Review knowledge base citation logs to confirm each cited fragment is marked with the correct update time and source document.
- Upload duplicate adaptation documents, check if the knowledge base automatically cleans up duplicate entries, and verify deduplication configuration is effective.
- Adjust the `quoteMaxToken` parameter, then verify returned context length meets expectations with no key information truncated.

The values provided are common starting points and should be measured against the reader's own samples.
