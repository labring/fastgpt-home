# Test Cases and Defect Analysis for Duty Scheduling and Handover: Tool Calling and Plugins

## What the Data for This Category Looks Like
The data for the duty scheduling and handover scenario mainly comes from four sources: scheduling systems, fault work orders, monitoring alerts, and organizational contact directories. The update frequency is daily or weekly. The daily produced documents include four types: duty schedules, handover records, escalation contact lists, and daily duty reports. Duty schedules contain fields for duty time periods and responsible personnel. Handover records contain fields for unresolved items and follow-up progress. Escalation contact lists contain fields for job hierarchy and contact information. Daily duty reports contain fields for response events and processing results. The data structure adjusts with team size, but core fields all revolve around duty responsibilities, handover items, and escalation paths.

## What Constraints Do These Characteristics Impose on the "Tool Calling and Plugins" Link
The data sources for this scenario are scattered and cover all stages of the operation and maintenance workflow. This requires plugins to interface with multiple types of system interfaces simultaneously, to avoid missing information from a single data source. The data update rhythm is daily or weekly, so the trigger timing for tool calls must match this rhythm, to avoid frequently calling unchanged data or missing real-time updated scheduling information. The document structure includes multiple core fields, so plugin calls must accurately extract the corresponding fields; otherwise, core operations such as scheduling conflict verification and unresolved item follow-up cannot be completed. The consequences of errors in this scenario directly affect operation and maintenance response efficiency. Tool calls must have result verification capabilities to ensure the integrity and accuracy of returned data, to avoid duty responsibility confusion or handover omissions caused by missing fields.

## How to Configure the Settings
The following configurations are formulated based on the plugin system rules of FastGPT v4.17.0, as detailed below:

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `toolChoice` | auto, or limited to the three function types: scheduling coordination, handover record query, and escalation path verification | Matches the core tool requirements of the duty scheduling and handover scenario, and avoids calling irrelevant functions |
| `functionCall` | Split call groups by data source type | Interface with multiple data sources such as scheduling systems, fault work orders, and organizational contact directories, to avoid overloading parameters in a single call |
| Maximum number of single plugin calls | 3 times | Core operations within the scenario do not exceed 3 steps, to avoid timeouts delaying duty responses |
| Call trigger frequency | 1 time per day or 1 time per week, adjusted according to the scheduling update rhythm | Matches the data update frequency and reduces invalid calls |
| Call timeout threshold | 10 seconds | Scenario operations require timely response, to avoid duty response interruptions caused by timeouts |
| Data source whitelist | Only include interfaces from scheduling systems, fault work orders, and organizational contact directories | Filter irrelevant data sources to ensure call security and result accuracy |

## Three Common Mistakes
- Symptom: The plugin call returns the error "No available functions matched". Cause: The scenario-specific function list is not configured in the `toolChoice` parameter, and a general plugin list is used by mistake, which prevents core tools such as scheduling coordination from being triggered.
- Symptom: The handover record returned by the plugin lacks the unresolved items field. Cause: The fault work order data source is not included in the plugin call scope, and the core data source for unresolved items is missed, resulting in incomplete handover information.
- Symptom: Some models return an error when the `functionCall` parameter is used. Cause: The currently used model does not support the `functionCall` function, and an incompatible model is used by mistake, resulting in tool call failure.

## How to Confirm the Configuration Is Correct
- Manually trigger a plugin call, and check that only the three function types of scheduling coordination, handover record query, and escalation path verification are triggered in the call logs, which matches the `toolChoice` configuration requirements.
- View the plugin call trigger records, and confirm that the call frequency matches the current scheduling update rhythm, with no frequent calls or missed triggers.
- Verify that the plugin returned results include core fields such as duty personnel, unresolved items, and escalation contacts, which matches the document structure requirements of the scenario.
- Test accessing a non-whitelisted data source interface, and confirm that the plugin automatically filters this type of call and does not return irrelevant data.
