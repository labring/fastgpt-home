# Test Case and Defect Analysis for Level Content Creation: Tool Calling and Plugins

## What Data for This Category Looks Like
Data for this category comes from multiple sources: level design documents exported by the level editor, resource lists from the art resource library, player test feedback forms, version submission records, and error logs from the defect system.
Daily maintained documents include fine-grained fields such as level path node coordinates, resource placement positions, and task trigger rules. Update frequency is weekly or per version iteration.
Data centers on specific maps and task nodes. It does not include abstract numerical rules, and only records post-launch content status and feedback.

## Constraints for Tool Calling and Plugins Workflows
Since data centers on specific map nodes and resource placements, tool calling must precisely match fine-grained fields such as level coordinates and resource IDs. It cannot rely solely on fuzzy text retrieval.
Data has a high update frequency. Plugins must support real-time pulling of the latest version submission records and test feedback to avoid calling outdated level data.
Errors directly impact launch timelines. Tool calling return results must include clear defect location fields to enable quick association with corresponding level nodes.
Plugins must also adapt to standardized document formats exported by the level editor, to ensure they can parse unstructured design document content.

## Configuration Settings
This page is written for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` or specified as `["defect_analysis", "level_check"]` | Adapts to specialized level content creation scenarios, automatically selects the appropriate tool, or specifies the defect analysis and level check tools |
| `functionCall` | `enabled` | Enforces structured function calling to ensure return results include parsable fields such as level node IDs and defect locations |
| Knowledge Base Binding Rule | Bind an exclusive knowledge base for the current level version | Avoids retrieving level data from unrelated versions, narrowing the search scope |
| Single Tool Calling Timeout | `30–60 seconds` | Matches the time required for level data loading and test feedback analysis |
| Number of Tool Calling Results Returned | `Top 3–5 entries` | Focuses on high-priority level defects and path issues |

## Three Common Misconfigurations
- Symptom: Tool calling nodes return empty results or status code 500. Cause: The exclusive knowledge base corresponding to the current level version is not bound, leading the search scope to cover unrelated data.
- Symptom: Tool return results do not include level node ID or resource ID fields. Cause: The `functionCall` parameter is not enabled, resulting in unstructured text return results that cannot parse specific defect locations.
- Symptom: Tool calling times out. Cause: No reasonable timeout period is configured, preventing completion of large-scale level data loading and analysis.

## How to Verify Proper Configuration
- Initiate a tool call targeting the current level design document, and check if the return results include level node ID and defect location fields.
- Review tool calling logs to confirm that the current version's test feedback forms and resource lists have been pulled.
- Switch to another level version, and verify that tool calls only retrieve content from the bound knowledge base.
- Adjust the `toolChoice` parameter to `auto`, and confirm that the tool automatically selects the defect analysis and level check functions.

The values provided here are common starting points, and should be evaluated against the target deployment's own samples.
