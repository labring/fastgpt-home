# Test Cases and Defect Analysis for Internal Network and WiFi Operations: Workflow Orchestration

## What This Category's Data Looks Like
This category of data primarily serves network administrators, desktop support staff, and on-site outsourced personnel. Data sources include switch consoles, wireless controllers, operation and maintenance monitoring systems, and frontline user trouble reporting channels. Daily maintenance documents include network topology diagrams, change orders, fault records, and wireless coverage inspection forms. Fields cover device port numbers, VLAN configurations, signal strength values, trouble reporting times, and processing results. Units include dBm, seconds, port numbers, and others. Data updates occur during daily inspections or after each network change. Core fault records are updated in real time as troubleshooting progresses.

## Constraints on Workflow Orchestration
Data sources for this category are scattered, and update timelines shift with maintenance operations. Workflows must support connections to multiple heterogeneous data source nodes, while adapting to both scheduled triggering and event triggering modes. Core maintenance steps such as fault location, port and VLAN verification, and coverage blind spot troubleshooting take extended time. Workflows must include automated troubleshooting steps to cut down on repetitive manual operations. Since fault handling directly impacts office and meeting operations, and may even cause security isolation failures, workflows must have clearly defined failure branches and alert triggering logic to ensure abnormal states are detected promptly. Topology diagrams and change orders from maintenance documents must be passed as context parameters to workflow nodes, to ensure troubleshooting steps align with the current network configuration.

## Configuration Settings
Configurations on this page are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Bind switch/wireless controller API keys and device IP addresses | Complete identity verification and target device specification when connecting to heterogeneous data sources |
| `nodeId` | Bind corresponding nodes by inspection cycle and fault ticket type | Distinguish workflow nodes for different maintenance scenarios to avoid configuration confusion |
| Loop Count | 3–5 times | Match routine maintenance needs for repeated port and coverage blind spot troubleshooting |
| Failure Retry Count | 2 times, 60-second interval | Address temporary call failures caused by network fluctuations, reduce misjudgments |
| Export Scope | Full conversation context | Meet the needs of exporting and reviewing complete fault troubleshooting records |
| Debug Mode Trigger | Manual toggle switch | Distinguish between debug and formal runtime environment configurations, prevent formal environments from being disrupted by test operations |

## Three Common Misconfigurations
- Issue: After configuring a data analysis node in the workflow, the corresponding ticket cannot be bound to an operation. Cause: The `variables` parameter is not correctly mapped to the ticket ID field, so the node cannot read the associated network data of the target ticket.
- Issue: Tool calls work normally in debug mode, but errors are triggered during formal runtime. Cause: Data source permission configurations for debug and formal runtime are not distinguished, and the formal environment does not have authorization to access core switch console data.
- Issue: Only the last 6 entries are displayed when exporting workflow conversation records, and full content cannot be exported. Cause: The export scope is not configured to full context, and the default setting truncates the latest limited entries.

## How to Verify Successful Configuration
- Manually trigger the test workflow, check if the node can correctly pull port status data from the specified switch.
- Enable the loop node, verify that coverage blind spot troubleshooting steps are executed repeatedly as set 3–5 times.
- Run the full workflow, export the conversation record, confirm that logs for all steps are fully saved.
- Check if `nodeId` is correctly bound to the target maintenance scenario, trigger a simulated fault ticket process, confirm that the workflow executes as expected.
