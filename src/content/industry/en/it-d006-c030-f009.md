# Test Cases and Defect Analysis for Internal Network and WiFi Operations: Tool Calling and Plugins

## What the data for this category looks like
The data for this category primarily comes from switch consoles, wireless controllers, office network monitoring systems, and frontline user trouble reports. Daily generated documents include network topology diagrams, change orders, fault troubleshooting records, and wireless coverage inspection checklists. Fields include port numbers, VLAN identifiers, signal strength parameters, inspection cycles, fault location time, and additional relevant metrics. Data is updated daily or synchronized immediately following network changes.

## What constraints these characteristics impose on the tool calling and plugins workflow
Data sources for this category are scattered across multiple hardware consoles and systems. Tool calling must adapt to interface formats for different protocols. Access permissions for each data source must be configured in advance. Daily generated documents include network topology diagrams with mixed structures, inspection checklists, and fault records. Plugins must support parsing attachments in different formats. Data updates trigger immediately following network changes or are synchronized daily. Tool calling must support dynamic pulling of the latest configuration and inspection data to avoid using outdated information. Fault location relies on multi-dimensional data correlation. Plugins must support cross-data-source field matching logic to simplify manual verification workflows.

## How to configure settings

| Configuration Item | Recommended Setting | Rationale |

| `functionCall` | Force enable | Ensures the model only calls predefined operations tools, avoiding generation of unstructured analysis content that does not follow established processes |
| Multi-source data pull interval | 600–1800 seconds | Balances the timeliness of network data and system resource usage, adapting to the daily or change-based update rhythm of this category |
| `toolChoice` | Limited to port detection, inspection query, and fault location tools | Only opens tool permissions related to internal network operations, narrowing the calling scope |

## Three common configuration errors
- Symptom: Returns empty content when calling a local Ollama model. Cause: The local interface address and model name for Ollama are not correctly specified in plugin configurations, preventing the tool call from properly pulling model responses.
- Symptom: Calls to OpenAPI interfaces prompt a missing application ID parameter, and new applications cannot be created via existing interfaces. Cause: Pre-permissions for application creation are not configured in advance, or the identification parameter for the corresponding application is not bound during tool calling, resulting in interface authentication failure.
- Symptom: No parsing results are generated when processing HTTP file streams (such as images returned by text-to-image generation) in a workflow. Cause: The plugin’s file stream reception and conversion logic is not configured, and only structured text interface calls are supported, making it unable to process binary file content.

## How to confirm correct configuration
- Run a test call for the port detection tool, and verify whether the returned results match the actual port status displayed on the switch console.
- Simulate a network change operation, and check whether the plugin automatically pulls the latest inspection checklists and fault records to confirm that data updates follow the preset rhythm.
- Call the predefined model tools, and check whether the returned content strictly follows the preset tool calling format, with no freely generated irrelevant content.
- Test interface calls for binary file streams, and confirm that the plugin can correctly receive and convert file content to produce expected output.

The values provided are common starting points and should be measured against the reader's own samples.
