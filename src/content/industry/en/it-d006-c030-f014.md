# Test Cases and Defect Analysis for Internal Network and WiFi Operations: Model Access and Configuration

## What data for this category looks like
Daily data for this category comes primarily from switch consoles, wireless controllers, monitoring systems, and user trouble ticket channels. Update frequency is daily or after each network change. Typical documents include network topology diagrams, change orders, fault logs, and wireless coverage inspection checklists. Fields cover device port numbers, VLAN configurations, signal strength, fault occurrence time, and impact scope. There are no unified standardized statistical units; adjustments must be made based on specific operation and maintenance scenarios. Primary users are network administrators, desktop support staff, and on-site outsourced personnel. Core work focuses on office site network access and fault troubleshooting.

## What constraints these characteristics impose on model access and configuration
Because data sources are scattered and include image-based documents, model access must support parsing and integration with multiple data types. Daily updated fault logs and temporary change orders require the context window to accommodate non-fixed-length document inputs, preventing truncation of critical information. Operation and maintenance scenarios have strict requirements for result accuracy, so divergent model outputs must be limited. Support for calling internal operation and maintenance tools to complete time-consuming tasks such as port verification and coverage blind spot detection is also needed. Additionally, internal network security rules require strict binding of model access keys and interface addresses to block unauthorized access.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | Adapts to the total length of daily fault logs, inspection checklists, and similar documents, avoiding context truncation |
| `maxTokens` | 2000–3000 token | Matches the reasonable output length for test cases and defect analysis, preventing overly long or short results |
| `toolChoice` | auto | Enables the model to autonomously select and call internal operation and maintenance tools such as port verification and coverage detection, improving analysis efficiency |
| `vision` | Enabled | Used to parse image-containing documents including network topology diagrams and wireless coverage inspection checklists, extracting key configuration information |
| `temperature` | 0.3–0.5 | Controls the rigor of model output, reducing irrelevant divergence to meet the precise analysis needs of operation and maintenance scenarios |
| `AIPROXY_API_TOKEN` | Fill in a non-empty administrator token matching the AI Proxy server configuration | Used as an App/Admin server environment variable to authenticate access to the AI Proxy service |

## Three common configuration mistakes
- Calling the API after configuring `AIPROXY_API_TOKEN` fails, returning an invalid key error. Troubleshooting: Confirm the variable uses a non-empty administrator token consistent with the AI Proxy server configuration, and do not use application API keys, model vendor keys, or other non-administrator tokens.
- Locally deployed models cannot be called after being added, returning a connection timeout error. Troubleshooting: Confirm `AIPROXY_API_ENDPOINT` is the root address of the AI Proxy service (for example, http://aiproxy:3000; do not append /v1 or model interface paths), and that this address is accessible from the App/Admin server network. Confirm the deployment uses FastGPT v4.17.0 or later.
- Model output indicates the request is incomplete, and full test cases cannot be generated. This occurs because `maxContext` is set too small to accommodate complete fault logs and inspection checklist data, leading to context truncation.

## How to confirm the configuration is correct
- Check the App/Admin server startup logs to confirm no missing environment variables or verification failure prompts appear. Verify the AI Proxy service can respond to requests normally.
- Upload a standard-format network topology diagram, confirm the `vision` parameter is active, and that the model accurately identifies device ports and VLAN configuration information in the diagram.
- Review the token consumption data returned by the API, confirm the values of `maxTokens` and `maxContext` match expected settings, and that frequent context truncation or output length overrun does not occur.
- Trigger a tool call test, enter a query requiring port verification, and confirm the `toolChoice` parameter automatically initiates the corresponding internal operation and maintenance tool call.

The values provided are common starting points and should be measured against the reader's own samples.
