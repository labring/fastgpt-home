# Test Cases and Defect Analysis for Creator Onboarding and Verification: Workflow Orchestration

## What this category of data looks like
This category of data is generated across the full creator onboarding and verification workflow. Daily documents include onboarding application forms, identity qualification scan copies, audit logs for verification, and cooperation agreement texts. Data sources cover account information submitted via the creator backend, third-party enterprise credit query APIs, account historical behavior records, and archived records from enterprise contract systems. Data updates are triggered by the application workflow: each completed verification process updates the corresponding record. A single record includes applicant identity fields, qualification verification status fields, and audit node ID fields.

## Constraints on workflow orchestration
The process nodes of onboarding and verification must connect data from multiple sources. Workflow orchestration must support pulling data across systems, so clear global sharing rules for `variables` are required to avoid data silos between nodes. The audit node of a single record relies on the output results of preceding nodes, so `nodeId` must be used to bind the execution order of nodes, ensuring time-consuming steps such as qualification verification and risk assessment are triggered in sequence. Update frequencies vary per application, so the workflow must support on-demand triggering. Field validation rules must also be reserved to adapt to format requirements for different qualification materials, preventing workflow interruptions caused by abnormal data formats.

## Configuration settings
The following configurations are adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Global shared mode | The onboarding and verification workflow needs to share core data such as applicant identity and qualification ID across nodes. The global mode ensures all associated nodes read the same set of variables |
| `nodeId` | Bound according to audit node sequence | Qualification verification, risk assessment, and certification archiving must be executed in order. Binding node IDs via `nodeId` ensures the workflow triggers in the preset sequence |
| Data pull trigger condition | Triggered by application submission event | Data updates are triggered along with the application workflow. On-demand pulling avoids invalid scheduled pulls that consume resources |
| Timeout threshold | 600 seconds | Qualification verification requires calling third-party credit query APIs. Reserving a 10-minute timeout covers most API response durations |
| Single credit query limit | Top 5 entries | Core fields of enterprise credit information are concentrated in the first 5 query results, reducing invalid data loading |
| Context storage limit | 8000 characters | Audit records need to retain core text of application forms and qualification materials. 8000 characters covers the text length of most single applications |

## Three common configuration mistakes
- Symptom: The applicant identity field is empty after workflow execution, preventing the audit node from completing verification. Cause: The global sharing scope of `variables` was not configured correctly. Variables were only defined within a single node and not passed to subsequent audit nodes.
- Symptom: Token consumption exceeds expectations when multiple AI large model calls are made, leading to workflow interruption. Cause: Context isolation was not configured separately for each large model node, resulting in independent token count statistics not being maintained across nodes.
- Symptom: Enterprise credit information is not pulled after the workflow triggers, and the process gets stuck at the qualification verification stage. Cause: The data pull trigger condition was set to scheduled execution instead of application submission event triggering, failing to match the real-time application workflow.

## How to confirm correct configuration
- Manually submit a test onboarding application, check whether the global variables in the workflow logs include core fields such as applicant identity and qualification ID.
- Trigger the qualification verification, risk assessment, and archiving nodes in sequence, confirm that the workflow executes in the preset sequence via the node IDs bound by `nodeId`.
- Call the third-party credit query API, verify whether the workflow automatically pulls the corresponding data after application submission, with no timeouts or empty returns.
- Configure multiple large model nodes, check whether their respective token consumption statistics are independent, with no cross-node sharing occurring.

The values given are common starting points and should be measured against the reader's own samples.
