# Test Cases and Defect Analysis for Creator Onboarding and Authentication: Forms and Interactions

## What the Data for This Category Looks Like
The core data for this category comes from the creator backend, enterprise credit information query APIs, account history records, and contract systems. Daily circulating documents include onboarding application forms, scanned identity qualification documents, audit review ledgers, and cooperation agreement files. Data updates are triggered alongside application workflows; each individual application corresponds to one data update, and platform account statuses are synced daily on a routine basis. Fields include applicant subject information, qualification numbers, audit node statuses, protocol activation identifiers, and more. There are no unified fixed units; text, numeric, or enumeration types are adapted based on field properties.

## What Constraints These Characteristics Bring to the Forms and Interactions Link
Dispersed data sources linked to multiple systems require forms to support an interaction mode combining cross-source data pulling and manual completion. Update frequency is tied to application triggers, so forms must support temporary saving and field locking after submission. This function is implemented by external business systems to prevent modification of already reviewed content mid-process. Field types cover text, enumerations, and file uploads; multi-format upload adaptation is implemented by external business systems. Error outcomes directly relate to the platform’s trust system, so form validation must cover required fields, format validity, and cross-field logical validation to prevent submission of false information. Additionally, the audit interaction must display audit progress and rejection reasons synchronously; this function is implemented by external operation systems to allow operation staff to quickly locate issues.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |

| Form input node `formInput` | Test example: Select 3 required inputs from the creator onboarding and authentication fields; actual fields are determined per task | This node collects user input; missing required fields require checking interaction status to avoid subsequent nodes failing to receive complete input |
| User selection node `userSelect` | Test example: Set 2 business options, check corresponding branches one by one | This node handles user selection; querying and filtering records related to creator onboarding and authentication must be implemented by subsequent APIs or external systems |
| Field passing after submission | Test example: Prepare 10 creator onboarding and authentication input samples covering complete filling, missing required fields, and canceled operations | Compare inputs and node outputs to confirm whether subsequent nodes receive corresponding fields; result thresholds are determined per actual tasks |
| External implementation item: File upload configuration | Must be implemented separately by external systems; test example values: Maximum 1000MB, up to 10 files per application, support PDF, JPG, PNG formats | Meets the storage requirements of qualification materials for test samples |
| External implementation item: Form draft saving | Must be implemented separately by external systems; draft saving and manual saving functions are implemented by external business systems, and FastGPT workflows only support recording interaction status | Application workflows take a long time, preventing data loss from interrupted user operations |
| External implementation item: Cross-field logical validation | Must be implemented separately by external systems; matching validation between qualification numbers and enterprise credit information is implemented by external business systems, and external systems display prompts when mismatches occur | Avoids submission of false qualifications, aligns with core audit business requirements |

## Three Common Mistakes
- Phenomenon: Form input boxes cannot receive externally passed account history data, requiring manual repeated entry of applicant information. Cause: External business systems did not correctly pass account history data to the `formInput` node, and no data transfer link was configured.
- Phenomenon: The qualification material upload link cannot submit files larger than 1000 MB, or displays an upload failure prompt. Cause: External file upload size limit is set too low, not adapting to the actual storage requirements of test samples.
- Phenomenon: Corresponding audit knowledge base cannot be automatically switched based on industry information submitted by the applicant; only a single knowledge base can be called fixedly. Cause: No workflow branch logic was configured to match industry information, and no external knowledge base API was called.

## How to Confirm Proper Configuration
- A test application is submitted using FastGPT v4.17.0. Externally passed account history data from the business system is checked to confirm whether it is filled into the `formInput` node, verifying the data transfer link functions normally.
- Qualification materials in test sample formats and sizes are uploaded. The upload component is checked to confirm submission is allowed, verifying the file upload configuration meets test requirements.
- Applications are submitted by simulating applicants of different roles. The `userSelect` node is checked to confirm it correctly collects audit node options provided by external systems, verifying node interaction logic functions normally.
- Test data with mismatched qualification numbers and enterprise credit information is submitted. Cross-field validation prompts are checked to confirm they are displayed, verifying logical validation from the external business system takes effect.

Note: The configuration values provided here are common starting points, and should be evaluated against the samples relevant to the specific deployment.
