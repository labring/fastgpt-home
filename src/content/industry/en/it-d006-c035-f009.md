# Test Cases and Defect Analysis for Unit Testing and Component Testing: Tool Calling and Plugins

## What data for this category looks like
Data for this category mainly comes from code repositories, test framework reports, requirement specifications and interface definitions. Its update frequency is daily or after each code commit.
Daily produced documents include standardized test cases, code coverage reports, Mock interface description documents, and defect tracking tickets. Standardized test cases include input parameters, expected output, and execution step fields.
A single test case usually contains a test scenario description of tens to hundreds of characters. Defect tickets are associated with corresponding code commit records and test execution logs.
The data structure is strongly bound to the R&D process, with no redundant non-business fields.

## What constraints these characteristics impose on the tool calling and plugins workflow
This category’s data has a high update frequency and is strongly bound to code commits. Tool calling must support incremental pulling and real-time synchronization to avoid excessive resource usage from full pulling.
Test cases and defect tickets are associated with specific code commit records. Tool calling needs to accurately match commit hashes and defect IDs to ensure data association accuracy.
The data structure is fixed and bound to the R&D process. Plugins must adapt to fixed field formats, and cannot arbitrarily adjust input parameter structures.
In intranet deployment scenarios, the storage service relied on by plugins cannot be forced to be publicly accessible. Support for intranet storage path configuration is required.

## How to configure settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Plugin Call Timeout | 300 seconds | Test case and defect data pulling and analysis processes take a long time; reserve sufficient execution duration |
| Maximum Data per Plugin Call | Top 20 entries | Limit the number of test cases or defect tickets pulled in a single call, adapt to context window capacity |
| Variable Scope Setting | Single Session Isolation | Prevent variable results from different test tasks from overlapping, avoid duplicate output content |
| Plugin Storage Path | Intranet Local Storage Directory | Adapt to intranet deployment scenarios, no need to rely on publicly accessible storage services |
| `toolChoice` | `auto` | Automatically select tool calling logic suitable for test scenarios, cover multiple needs such as case generation and defect analysis |
| `functionCall` | `{"name":"fetch_test_cases","parameters":{"limit":20,"update_since":"last_commit"}}` | Match the rhythm of test data updates by commit, implement incremental synchronization |

## Three common configuration mistakes
- Phenomenon: The plugin call returns a timeout result, and the interface displays request timeout status code 504. Cause: The plugin call timeout duration is not adjusted based on test data pulling requirements, and the default timeout period is insufficient.
- Phenomenon: Test reports stored by the plugin cannot be read normally, and the interface displays a "file does not exist" error. Cause: The plugin storage path is configured as a publicly accessible storage service, which cannot be accessed normally in an intranet deployment scenario.
- Phenomenon: Defect analysis results output by the plugin include test case content from a previous session. Cause: The variable scope is not configured for single session isolation, causing old data to remain in the context.

## How to confirm correct configuration
- Run a test case synchronization plugin, check whether the plugin log displays a synchronization success identifier, and the number of pulled data entries does not exceed the configured single call limit.
- Check the permissions of the plugin storage directory, confirm that test framework reports can be written to the directory normally, and there are no permission errors.
- Initiate two consecutive test defect analysis tasks, check whether the output results of the two times are independent of each other, with no content overlap.
- In FastGPT v4.17.0, enter the plugin management page, confirm that the `toolChoice` and `functionCall` parameters are configured as required.

The values provided are common starting points and should be measured against the reader's own samples.
