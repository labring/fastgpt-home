# Test Case and Defect Analysis for Unit and Component Testing: Model Integration and Configuration

## What data looks like for this category
Data for this category comes from code repositories, test framework reports, requirement specifications, and interface definitions. Associated daily documents include test cases, coverage reports, Mock instructions, and defect tickets.
Test cases contain case identifiers, preconditions, input parameters, and expected output fields. Coverage reports include module coverage, line coverage, and branch coverage values. Defect tickets contain defect identifiers, reproduction steps, priorities, and associated code path fields.
Data exists as structured or semi-structured text, with an update frequency of daily or per code commit.

## What constraints these characteristics impose on model integration and configuration
Data sources cover multiple types of structured and semi-structured files. This requires model integration configurations to support multi-format text parsing and batch request processing, and to adapt to output formats from different test frameworks.
Update frequency is daily or per code commit. This requires configurations to adapt to high-frequency, low-latency call requirements, and to avoid blocking automated build workflows.
Daily documents cover multiple types of test-related content. This requires configurations to flexibly adjust context length and output length to adapt to different types of tasks.
The most time-consuming links of test data construction and boundary condition completion require configurations to enable tool calling capabilities, and to support models to independently call code parsing and data matching tools to complete tasks.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | The data volume of test cases and defect tickets for unit and component testing is moderate. An overly long context will increase model inference latency. |
| `maxTokens` | `2000–3000 token` | Requirements for parsing and generating single test cases or defect tickets, to avoid output truncation. |
| `temperature` | `0.3–0.6` | Test case generation requires consistent logic, to avoid excessive randomness. |
| `toolChoice` | `auto` | Requires the model to independently select and call code parsing and defect matching tools to complete test case completion and defect analysis. |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, with an example format of http://aiproxy:3000. Do not append /v1 or model service addresses | Required environment variable for the App/Admin server. Do not configure it in workflow global variables, application API request headers, or standard model management pages. Configure it via service deployment environment variables. |
| `AIPROXY_API_TOKEN` | AI Proxy administrator token, must match the server configuration and be non-empty | Required environment variable for the App/Admin server. Do not configure it in workflow global variables, application API request headers, or standard model management pages. Configure it via service deployment environment variables. |

## Three common configuration mistakes
- Symptom: Model returns the error "Only stdio processes are supported, MCP encapsulated with SSE protocol cannot be used". Cause: The model integration configuration did not correctly select the communication protocol type, and SSE was mistakenly set as the default call method.
- Symptom: Model node icons in the workflow do not display, and test case generation tasks fail. Cause: The `maxContext` configuration value exceeds the context window limit of the current model, preventing the model from loading input data.
- Symptom: Generated test cases deviate significantly from actual code logic. Cause: The `temperature` configuration value is too high, leading to excessive randomness in model output that does not meet the strictness requirements for test cases.

## How to confirm successful configuration
- Run a local curl command to call the configured `AIPROXY_API_ENDPOINT`, and verify that the interface returns a normal status code.
- In FastGPT v4.17.0, submit a code change to trigger automated testing, and check whether the model can normally generate supplementary boundary test cases.
- Upload a defect ticket to the test management module, and check whether the model can automatically associate existing test cases for the corresponding code module.
- View model call logs to confirm that no context overrun or output truncation error messages appear.

The values provided here are common starting points, and should be evaluated against the samples used in the specific deployment.
