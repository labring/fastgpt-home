# Test Cases and Defect Analysis for Prototype and Interaction Design: Source Citation and Traceability

## What Data for This Category Looks Like
The daily output of this category typically includes interactive prototypes, page flowcharts, component descriptions, and review records. Data mainly comes from Figma or Axure source files, team design systems, user feedback, and usability test records. Update frequency follows weekly or per-release cycles. A single document usually contains hierarchical page structures, component IDs, operation paths, and review comment fields. No unified standardized field format exists, and some content is stored as visual layers.

## Constraints Imposed on Source Citation and Traceability
Hierarchical document structures require traceability systems to link multi-level relationships between pages, components, and review records. This prevents retrieving only isolated prototype fragments.
Weekly or per-release update cycles require cited source data to be synchronized regularly. This ensures test cases reference the latest version of design content.
Visual layers and non-standardized fields require traceability systems to parse metadata from original design tools. Extracting only text content cannot cover all required information.
Design changes directly impact R&D implementation outcomes. The traceability link must retain complete change trails to help locate deviation sources.

## Configuration Guidelines
This configuration applies to FastGPT v4.17.0

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | `800–1200 token` | Matches the average content length of single-page interactive prototypes, to avoid truncating key operation path descriptions |
| `responseData` | Return only source file paths and version numbers | Focuses on core metadata required for traceability, reducing redundant information that occupies context space |
| `detail` | Enabled | Retains associated review records for prototype components, to trace specific reasons for design changes |
| Single search limit | Top 3 entries | Matches the number of associated test cases for a single-page prototype, to avoid information overload that affects retrieval efficiency |
| Context cache duration | `7 days` | Matches the weekly update frequency of prototype documents, to ensure cited source data remains up to date |

## Three Common Misconfigurations
- The phenomenon where prototype component variables referenced in test cases cannot be matched to source design files occurs when the component ID of the prototype file is not bound as a reference variable to the knowledge base retrieval configuration.
- The phenomenon where the number of retrieved test cases exceeds expectations occurs when the single search limit is set too high, exceeding the associated content volume of a single-page prototype.
- The phenomenon where version information for prototypes is not displayed in traceability results occurs when the `responseData` parameter is not configured to return the version number field.

## How to Confirm Successful Configuration
- Generate a test case targeting a specific prototype page, then confirm whether the corresponding source file path and version number appear in the results.
- Review the number of retrieved results, confirm alignment with the preset single search limit requirement.
- Trigger a version update for the prototype file, then confirm whether subsequent retrieval results display the latest version information synchronously.
- Verify that associated review records for the prototype component are included in retrieval results, confirming the `detail` parameter configuration is active.

The values provided are common starting points and should be measured against the reader's own samples.
