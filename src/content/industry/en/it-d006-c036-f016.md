# Test Cases and Defect Analysis for Prototyping and Interaction Design: Forms and Interactions

## What Data for This Category Looks Like
The core users of this category are product designers, interaction designers, and front-end product teams. Daily deliverables include interaction prototypes, page flowcharts, component specifications, and review records. Data mainly comes from Figma or Axure files, team design systems, user feedback, and usability test records. Update frequency is weekly or per version iteration. Core documents have clear component attributes, operation paths, and abnormal scenario descriptions. Fields mostly correspond to interface control states, trigger conditions, and display rules. There is no unified fixed unit system; it must match the current project’s design specifications.

## Constraints on Forms and Interactions
Since data comes from prototype files and component specifications in Figma or Axure, form and interaction configurations must strictly match control attributes and operation logic defined in prototypes, to avoid deviations between development implementation and design intent. Update frequency is weekly or per version, so configurations must support rapid iterative adjustments without complex historical version rollbacks. Review records in documents must be synchronized to configurations, to ensure test cases cover all abnormal scenarios approved in reviews. For the status flow and abnormal scenario completion of core time-consuming links, form configurations must cover all preset interaction states to avoid missing test points.

## How to Set Configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Form Input Node `formInput` | Test example: Select 3 fields from prototyping and interaction design documents as required inputs; actual fields are determined by the task | This node collects user input; missing required items require checking interaction states to prevent subsequent nodes from receiving incomplete input |
| User Selection Node `userSelect` | Test example: Set 2 business options, check corresponding branches one by one | This node handles user selection; queries and filtering of records related to prototyping and interaction design must be implemented by subsequent interfaces or external systems |
| Post-submission Field Passing | Test example: Prepare 10 prototyping and interaction design input samples, covering full completion, missing required items, and cancel operations | Compare input and node output to verify whether subsequent nodes receive corresponding fields; result thresholds are determined by actual tasks |
| External Implementation Item: Form Submission Timeout Threshold | Must be implemented separately by external systems; 10-15 seconds | Test example value range, used as an initial configuration reference |
| External Implementation Item: Abnormal Prompt Copy | Must be implemented separately by external systems; match unified wording in review records, include operation guidance | Unified specifications from team review records |
| External Implementation Item: Interaction Trigger Timing | Must be implemented separately by external systems; trigger form input node (`formInput`) verification on form blur, with verification logic implemented by external business systems | Aligns with daily user operation habits |

## Three Common Mistakes
- Referenced variables show no selectable values after selecting the corresponding data source node: The phenomenon is that the referenced variable dropdown menu for the corresponding configuration node is empty, and no data source fields can be selected. Verification step: Check whether the form data source defined in the corresponding interaction prototype file has been associated.
- User selection node options fail to load correctly: The phenomenon is that after configuration, opening the interaction page shows an empty option list for the user selection node or includes undefined roles. Verification step: Check whether role data provided by the external business system is synchronized normally, and verify whether the role range defined in the prototype matches the configuration.
- Form input fails to trigger verification normally: The phenomenon is that entered content does not trigger the preset form input node (`formInput`) verification rules, and no corresponding prompt pops up after submission. Verification step: Check whether the interaction trigger timing configuration is set to trigger verification on form blur, and check whether the verification logic of the external business system is properly connected.

## How to Confirm Configuration Is Complete
- The corresponding Figma or Axure prototype file is opened, and the verification rules of the form input node (`formInput`) are verified to fully match the component attributes.
- Test cases are submitted to verify that the abnormal prompt copy fully matches the wording in the review records.
- User operations are simulated to confirm that the option range of the user selection node (`userSelect`) matches the roles defined in the prototype.
- Referenced variables are confirmed to be correctly associated with data source fields via the external system or subsequent nodes.

The values provided are common starting points and should be measured against the reader's own samples.
