# Test Cases and Defect Analysis for Release Management and Version Acceptance: Tool Calling and Plugins

## What the Data for This Category Looks Like
Data for this category comes primarily from CI pipelines, change management systems, test reports, and monitoring dashboards. The update frequency is weekly or aligned with each version release cycle. Daily associated documents include release plans, launch checklists, acceptance reports, and rollback plans. Core fields include release version numbers, change item lists, test pass rates, rollback trigger conditions, launch window periods, and more. Each team adjusts the document field structure according to its own R&D process, and there is no unified mandatory format.

## What Constraints These Characteristics Impose on the Tool Calling and Plugins Workflow
Since data sources are scattered and update rhythms fluctuate with version releases, tool calling must support multi-source data aggregation. This avoids obtaining information from only a single system in a single call. Core document fields have no unified format, so plugins must support custom field extraction rules to adapt to the release document structures of different teams. Errors in the release phase have serious consequences. Tool calling must be configured with failure retry and exception alert mechanisms. At the same time, call frequency must be limited to match the time constraints of launch windows, to avoid interfering with official release processes.

## How to Configure Settings
In FastGPT v4.17.0, the following tool calling and plugin configuration can be completed via the plugin management page:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapt to business scenarios where AI freely identifies and calls tools, automatically select plugins matching release management data |
| `functionCall` | Enabled | Force the format of tool calls to ensure returned content meets the extraction requirements for release management data |
| Tool call timeout period | 300-600 seconds | Match the data return delay of CI pipelines and change management systems, avoid interrupting the release verification process due to timeout |
| Custom field extraction rules | Bind core fields of release plans and launch checklists | Adapt to the non-uniform format characteristics of documents in this category, accurately extract key information such as version numbers and change items |
| Number of failure retries | 2 times | Balance data acquisition success rate and time limits of launch windows, avoid retries occupying excessive release time |
| Exception alert trigger | Trigger when a call fails or required fields are missing | Match the business characteristic of serious consequences from errors in this category, promptly notify version managers to handle exceptions |

## Three Common Mistakes
- Phenomenon: Release verification content returned by tool calls is directly displayed to end users without being hidden as required. Cause: No output filtering rules for tool calls are configured, causing sensitive release data obtained from change management systems to be directly exposed in conversations.
- Phenomenon: The AI cannot automatically identify the tool to call, and only relies on the built-in knowledge base to answer questions related to release management. Cause: `toolChoice` is not set to `auto`, which limits the automatic selection capability of tool calls and fails to meet business requirements for freely identifying tools.
- Phenomenon: Scheduled tool calls frequently experience timeout errors, causing the release verification process to be interrupted. Cause: The tool call timeout period is set too short, failing to match the data return delay of CI pipelines and change management systems, exceeding the actual business response window.

## How to Confirm the Configuration Is Complete
- Log in to the FastGPT plugin management page, check the configuration status of `toolChoice` and `functionCall` to confirm they match the preset configuration.
- Manually trigger a tool call, check if the returned data includes core fields such as release version numbers and change item lists, to verify that the custom extraction rules are effective.
- Simulate a tool call failure scenario, confirm whether the exception alert is triggered as configured, to verify that the failure retry and alert logic are working properly.
- View the plugin call logs to confirm that the timeout period and number of retries match the preset values, and align with the time constraints of the launch window.

The values given are common starting points and should be measured against the reader's own samples.
