# Test Cases and Defect Analysis for Release Management and Version Acceptance: Model Integration and Configuration

## What this category of data looks like
This category of data typically comes from CI pipelines, change management systems, test reports, and monitoring dashboards. It updates on a weekly or per-release cycle. Associated daily documents include release plans, launch checklists, acceptance reports, and rollback plans. Core fields cover release version identifiers, change item details, test pass rate statistics, rollback trigger conditions, and more.
This data is maintained by version managers, R&D and operations teams, and product owners. It flows through the full lifecycle of a version from build to production release. Different documents have varying field structures. Some documents include structured lists and unstructured text content.

## How these characteristics impose constraints on model integration and configuration
Data from this category is scattered across multiple systems and updates with each release cycle. This requires model integration to support cross-source data pulling and lightweight context loading. It must avoid excessive resource usage that would impact tight launch windows.
Daily document formats vary widely. Models must adapt to text with different structures, including lists, reports, and plans. This ensures analysis results meet the standardized requirements of business scenarios.
Errors during the release phase directly impact online services. This requires model calls to include clear status feedback and failure retry mechanisms. Configured models can stably support version acceptance and defect analysis workflows, and prevent release delays caused by model anomalies.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `AIPROXY_API_ENDPOINT` | Enter the root address of the AI Proxy service, for example http://aiproxy:3000. Do not append paths like /v1 or /chat/completions. Do not use single-model service addresses | Specifies the root access address for the AI Proxy service, adapting to both local and cloud deployment scenarios |
| `AIPROXY_API_TOKEN` | Enter the admin token matching the AI Proxy server configuration. This value cannot be empty. Do not use application API keys, model vendor keys, or other types of secrets | This variable is the admin authentication credential for the AI Proxy service. It is used for identity verification when the App/Admin server calls AI Proxy. It cannot be used as an authentication key for application API calls |
| `maxContext` | 8000–12000 token | Adapts to the total length of multi-source documents in release management scenarios. Ensures core data such as release plans and test reports is fully loaded |
| `maxTokens` | 2000–3000 token | Controls the length of model-generated defect analysis and test case summaries. Meets the needs of rapid review of launch checklists |
| `temperature` | 0.3–0.5 | Reduces output randomness. Ensures test case and defect analysis results align with standardized acceptance process requirements |
| `toolChoice` | auto | Lets the model independently decide whether to call tools. Adapts to actual needs for cross-source data pulling and format organization |

## Three common misconfigurations
- Symptom: Model calls return a permission denied error. Troubleshooting steps: Check if a secret other than the AI Proxy admin token is used, or if a valid `AIPROXY_API_TOKEN` is not configured.
- Symptom: Local deployment instances cannot call vision models to process screenshots in test reports. Cause: The `vision` parameter is not enabled in the configuration, and the corresponding vision model plugin is not deployed.
- Symptom: Model-generated defect analysis results are redundant and poorly formatted. Cause: The `temperature` parameter is set to an overly high value, causing output to deviate from standardized acceptance report formats.

## How to confirm successful configuration
- Execute a test case and defect analysis call for the current version's release data. Confirm that returned results include core fields such as complete version identifiers and change item details.
- Review App/Admin service startup logs and runtime logs. Confirm that startup verification failures are not triggered by missing `AIPROXY_API_ENDPOINT` or `AIPROXY_API_TOKEN`, and that identity verification requests to the AI Proxy service return successful status codes.
- Validate configured `maxContext` and `maxTokens` parameter ranges. Ensure their value ranges adapt to the total length of documents associated with the current version and output requirements.
- Confirm that model-generated content conforms to the standardized format of release acceptance, with no obvious redundant content or non-compliant fields.
