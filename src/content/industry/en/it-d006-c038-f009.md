# Test Cases and Defect Analysis for Change Management and Release Windows: Tool Calling and Plugins

This content is based on FastGPT v4.17.0

## What the data for this category looks like
Core data for change management and release windows comes from change management systems, CI pipelines, monitoring data, and business calendars. Update frequency is weekly or triggered by a single change. Four regular document types are produced: change request forms, risk assessment forms, launch window plans, and rollback plans. Fields include unique change identifiers, request time, risk level, window time periods, rollback trigger conditions, and other details. Specific fields may vary slightly based on enterprise operation and maintenance specifications.

## What constraints these characteristics impose on the tool calling and plugins workflow
The above data characteristics define core constraints for the tool calling and plugins workflow. Multi-source heterogeneous data sources require plugins to support API interfaces for different systems, and adapt to non-standard document formats. Weekly or single-change update cycles require tool calls to be bound to change event triggers. Complex document fields require plugin input and output parameters to map one-to-one with change document fields, to avoid data misalignment. Time-consuming steps such as risk rating and approval coordination require tools to automatically pull historical data to generate preliminary analysis results, reducing manual intervention costs.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Matches the average length of single paragraphs in change request documents |
| Single Call Limit | First 10 change records | Aligns with reasonable data volumes for single-batch change analysis |
| Timeout Threshold | 600 seconds | Covers typical time spent pulling monitoring data across systems |
| `toolChoice` | auto | Allows the model to autonomously select tools suited for change analysis |
| `functionCall` | Mandatory parameter validation | Ensures plugin input and output align with change document fields |
| Loop Trigger Rule | Triggered by change events | Matches the weekly or single-change update cycle of change management |

## Three common mistakes
- Custom plugins added to workflows do not display input or output parameters. The cause is failure to map and bind plugin parameters to change document fields.
- External chat interface calls respond slowly. The cause is failure to limit the number of change records pulled per request, leading to context overload.
- Looped runs do not correctly iterate over change elements. The cause is using a generic array as the loop input source, without binding the change ID list as input.

## How to confirm proper configuration
- Trigger a simulated change event, and check whether the plugin correctly pulls corresponding document data such as change requests and risk assessments.
- View tool call logs, confirm that the `toolChoice` parameter takes effect, and the model calls the suited analysis tool.
- Verify the looped run workflow, confirm that each change ID is correctly iterated and an AI session is called.
- Simulate a cross-system data pulling scenario, confirm that no timeout error is triggered, and meets the configured timeout threshold requirements.
