# Test Cases and Defect Analysis for Change Management and Release Windows: Citation Sources and Traceability

## What the data for this category looks like
Core data for this category comes from change management systems, CI pipelines, monitoring data, and business calendars. Update frequency is weekly or triggered by a single change event.
Daily associated documents include change request forms, risk assessment forms, launch window plans, and rollback plans. Fields include change unique identifiers, risk levels, effective time periods, approval statuses, and rollback plans, among others.
The data structure updates dynamically with each change workflow, and is tightly linked to change actions in the production environment. No fictional statistical data is included.

## Constraints on Citation Sources and Traceability
Data comes from operations tools and business systems. Citation traceability requires precise matching of core fields such as change unique identifiers. This prevents mixing associated data from different changes.
Update frequency is weekly or triggered by a single change event. Context citations must be limited to a reasonable time range. This avoids including expired change plan content.
Document structures include fixed approval and risk fields. Extracted citations must cover these fields to support defect analysis. Total citation volume must be controlled to prevent context overflow from redundant data. Context overflow would reduce the accuracy of change risk judgments.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | `8000–12000 token` | Change management-related documents have long length. This setting covers core content of complete change requests and rollback plans |
| Single citation count limit | Top 3–5 entries | Change management data updates infrequently. Excessive redundant citations will cause context overload |
| `responseData` | Enabled | Original data fields from the change management system must be returned for traceability and defect analysis |
| Citation detail `detail` | Full fields | Core fields such as change ID, launch window time period, and approval status must be displayed. This supports test cases and defect localization |
| Context time range | Last 14–30 days | Change management data updates weekly or per single change. Data beyond this range has limited reference value |

## Three Common Misconfiguration Issues
- Phenomenon: Cited change management document information is not displayed on the official chat page, but displays normally on the debug page. Cause: The display configuration corresponding to `responseData` is not enabled. The logic for binding knowledge base citations to change management system documents is not linked.
- Phenomenon: Returned citation content exceeds the preset count limit, or only token quantity is limited but count is not. Cause: The configuration logic of `quoteMaxToken` and count limits is confused. A reasonable single citation upper limit tailored to change data characteristics is not set.
- Phenomenon: The text extraction component cannot extract fields such as change ID and launch window from knowledge base citations. Cause: `detail` is not configured to full field mode. The original data of knowledge base citations is not included in the extraction scope.

## How to Verify Proper Configuration
- In FastGPT v4.17.0, initiate a test case query containing change ID keywords. Check whether core fields such as change ID and launch window time period are included in the returned results.
- Adjust the value of `quoteMaxToken`. Verify that the length of returned citation content matches the expected range of 8000–12000 token.
- View the official chat interface. Confirm that source information of cited documents is displayed normally, with no missing fields.
- Trigger the program execution function and associate knowledge base citations. Verify that extracted change management fields can be used normally as background knowledge input to subsequent modules.
