# Test Cases and Defect Analysis for Change Management and Release Windows: Model Integration and Configuration

## What data looks like for this category
Data for this category is sourced from change management systems, CI pipelines, monitoring data, and business calendars. Daily associated documents include change requests, risk assessment forms, release window plans, and rollback plans. Data updates occur weekly or are triggered per individual change. Data fields include unique change identifiers, planned release windows, risk rating levels, approval statuses, rollback trigger conditions, and no additional custom statistical units. All fields are tightly bound to change workflows.

## Constraints on model integration and configuration
Scattered data sources across multiple systems require model integration to support pulling and parsing multi-format data sources. Configure unified input rules for structured change documents and unstructured monitoring data. Update frequency triggered per individual change requires model calls to support on-demand triggering, to avoid invalid computation from fixed-period calls. Many closely dependent associated fields require configuring the model to recognize inter-field logic, such as the matching relationship between release window periods and risk ratings. Additionally, the approval and rollback stages of the change workflow require the model to output traceable structured results, so fix the output format and fields.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | This category’s associated change documents, monitoring data and other content have large volume, so sufficient context must be retained to recognize inter-field relationships |
| `maxTokens` | 2000–3000 token | Structured results such as risk ratings and window adaptation suggestions must be output, to avoid exceeding return length limits |
| `temperature` | 0.3–0.5 | Rigorous risk assessments and change suggestions must be generated, to avoid overly divergent unexpected results |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, for example http://aiproxy:3000. Do not append paths such as /v1 or /chat/completions. Do not use single-model addresses such as VLLM/Ollama/Xinference | Entry point for App/Admin services to call the AI Proxy service, to ensure stable call links. This is an environment variable for the App/Admin service side, and must not be configured in workflow global variables, application API request headers, or the general model management page |
| `AIPROXY_API_TOKEN` | Administrator token consistent with the AI Proxy service side configuration, and cannot be empty. Do not use application API keys, model vendor keys, or tokens issued per application | Identity verification credential for communication between the App/Admin service and the AI Proxy service |

## Three common configuration errors
- Phenomenon: When calling the API to trigger batch execution nodes, only some loop tasks are completed, while the full process runs completely in the online debugging environment. Cause: In FastGPT v4.17.0, the default API call timeout duration does not adapt to the batch processing requirements of multiple change data in this category, and parameters are not adjusted to cover the full execution cycle of the loop.
- Phenomenon: When accessing a vision model, uploaded monitoring screenshots or change document images cannot be parsed normally. Cause: The `vision` parameter configuration is not enabled, and the input format requirements of the vision model are not adapted.
- Phenomenon: Token consumption statistics returned by model calls cannot be split by application dimension. Cause: The application identifier binding for model calls is not configured, and context-associated records of token consumption are not enabled.

## Verify correct configuration
- Initiate a test call for a single change, and check that the model return results include expected fields such as risk ratings and release window adaptation suggestions.
- Check server startup verification results and model call logs, confirm that `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are correctly configured as server-side environment variables, and there are no identity verification related errors.
- Adjust the `temperature` parameter, initiate two calls, and compare the rigor of the results to confirm that the parameter takes effect.
- Trigger an API call for batch execution nodes, check that all loop tasks are completed without mid-run interruptions.

The values listed here are common starting points, and should be assessed against local deployment samples.
