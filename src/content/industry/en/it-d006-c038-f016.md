# Test Cases and Defect Analysis for Change Management and Release Windows: Forms and Interactions

## What Data for This Category Looks Like
Data for this category originates from change management systems, CI pipelines, monitoring data, and business calendars. Data updates occur weekly or each time a change is executed. Daily associated documents include change request forms, risk assessment forms, launch window plans, and rollback plans. Data fields include change identifiers, application time periods, risk rating items, approval flow nodes, rollback trigger conditions, and more. Window time periods are measured in hours, the number of approval participants is measured in person-times, and rollback trigger thresholds are defined using business indicator thresholds. All data is updated in real time as the change process advances, with no fixed batch synchronization cycle. This document is based on FastGPT v4.17.0.

## Constraints Imposed by These Characteristics on Forms and Interactions
Multi-data source requirements require cross-system option pulling via subsequent workflow branches or external interfaces. Examples include pulling submitted change tickets from a change management system, or pulling current pipeline status from a CI pipeline. The weekly or single-change update frequency requirement requires matching the pull scope rhythm via external session storage or subsequent node logic, to avoid expired or redundant data. The multi-document structure requires splitting forms by module to reduce page visual complexity. The diversity of fields requires configuring forms with required field validation, and implementing linkage logic via external logic to avoid errors such as missing approvals or unconfirmed rollback conditions. Unlike release management and version acceptance, this category places greater emphasis on production environment risk control, so an additional time period validity check link must be configured via external logic. Window restrictions during business peak hours require pre-checking time period validity via external logic to avoid impacting business operations.

## Three Common Misconfigurations
- Symptom: The dropdown menu for change window time periods only displays partial historical data, and does not cover change requests from the past 7 days. Verification Action: Check the configuration parameters for the data source pull scope, and verify whether the interface returned change request records cover the required time range.
- Symptom: Submitting the form displays a prompt that the approver field is empty, even though the corresponding approval role is already selected in the interface. Verification Action: Check whether the selected approver value is passed to subsequent nodes before form submission, and verify whether the external session storage retains the selected state.
- Symptom: Previously filled fields such as change ID and window time period are lost after refreshing the page, requiring re-entry. Verification Action: Check the external session storage configuration, and verify whether user-entered form data is persisted.

## How to Verify Proper Configuration
- Enter the form editing page, check whether the dropdown options returned by the external interface cover change request records from the past 7 days, and verify that the data source pull scope configuration is effective.
- Attempt to submit the form without filling in required fields, confirm that the system pops up an error prompt for the corresponding fields, and verify that the required form field configuration is effective.
- Select an approver, then refresh the page, check whether the option remains selected, and verify that the external session storage logic configuration is effective.
- Fill in a window during a business peak period, confirm that the external logic pops up a risk prompt, and verify that the time period validity check configuration is effective.
