# Test Cases and Defect Analysis for Pre-Sales Technical Proposals: Workflow Orchestration

## What Data for This Category Looks Like
Data for this category comes primarily from customer interview records, public bidding documents, publicly available vendor product materials, and historical winning bid project proposals. Core daily output documents include technical proposal documents, customer requirement research forms, quotation lists, and demo scripts. Updates follow per-project cycles: updates trigger each time requirement clarification or proposal adjustments wrap up, with routine weekly syncs of the latest versions. Document fields include technical route descriptions, implementation boundary scopes, quotation details, demo scenario lists, and more. No unified standardized field format exists, and teams must adjust content flexibly based on project requirements.

## How These Characteristics Impact Workflow Orchestration
Data for this category is scattered and adjusted dynamically per project, so workflow orchestration must adapt to non-standardized document structures. Since data updates follow per-project timelines, workflows must support temporary node insertion and parameter adjustments to accommodate flexible project change needs. Core documents such as technical proposals see multiple revisions based on customer feedback, so workflows must associate `variables` to store temporarily adjusted requirement details, avoiding hardcoding. Pre-sales proposal outputs must cover multiple document types, so workflows must support generating corresponding document fragments per distinct nodes to meet multi-source data integration needs. The most time-consuming steps in this category are requirement clarification, proposal boundary design, and quotation configuration verification. ## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Global variable scope | Project-level | Adapt to the multi-document sharing requirements of pre-sales proposals, ensuring that the same set of requirement parameters can be reused across different links |
| `variables` storage field | Split storage by document type | Match the field differences across multiple document types in pre-sales proposals, avoiding data confusion |
| Workflow node trigger rule | Trigger based on node completion status | Adapt to the requirement of gradually confirming requirements in pre-sales proposal processes, preventing generation of unconfirmed content in advance |
| `nodeId` association rule | Bind unique identifiers of corresponding documents | Ensure each generated document fragment can be accurately linked to the original proposal node |
| Knowledge base reference limit | Top 3-5 matching results | Balance the accuracy of proposal content and generation efficiency, meeting the rigor requirements of pre-sales proposals |
| Timeout threshold | 600 seconds | Adapt to scenarios where multiple source materials must be retrieved during pre-sales proposal generation, preventing process interruptions due to prolonged material loading |

## Three Common Configuration Mistakes
- A parameter not found error occurs during workflow runtime, with the interface prompting that the `variables` field is empty. This happens because the global variable scope was not set to project-level; variables defined only within a single node cannot be called by other links, making it impossible to reuse requirement parameters across multi-document links in pre-sales proposals.
- Generated proposal document fragments do not match the original requirements, and the number of results does not meet expectations. This occurs because the `nodeId` association rule was not configured correctly, causing document fragments to not be bound to the corresponding proposal nodes and resulting in content misalignment.
- Workflows cannot reference multiple knowledge bases. This occurs because multi-knowledge base association configuration was not enabled in workflow nodes, with only a single knowledge base bound, making it impossible to retrieve multi-source vendor product materials or historical project data.

## How to Verify Proper Configuration
- Trigger the test node of the workflow, check whether global variables can be called normally across all associated nodes, and verify that the scope of the `variables` parameter is correct.
- Generate a single demo script document, check whether the generated content matches the bound `nodeId`, and confirm the association between document fragments and proposal nodes.
- Attempt to add two different knowledge base nodes in the workflow, verify that multi-source materials can be retrieved simultaneously, and confirm that the multi-knowledge base reference configuration is active.
- Run the complete workflow, check whether the execution duration is within the preset 600-second threshold, and confirm that the timeout configuration meets project requirements.
