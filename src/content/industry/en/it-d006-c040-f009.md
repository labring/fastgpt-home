# Test Cases and Defect Analysis for Pre-Sales Technical Proposals: Tool Calling and Plugins

## What Data for This Category Looks Like
The typical stakeholders for this category are system integrator pre-sales consultants, solution architects, and sales teams. Daily deliverables include technical proposal documents, customer requirement survey forms, quotation lists, and demo scripts. Data sources include customer interviews, bidding documents, vendor product materials, and historical project proposals. Updates occur per project or weekly. Core fields for a single document include technical roadmap, implementation boundaries, quotation details, and demo process nodes. There are no fixed, unified quantitative statistical fields, and content structure is adjusted solely based on customer requirements.

## Constraints Imposed on Tool Calling and Plugins Workflows
Documents in this category are updated per project, and core fields adjust dynamically based on customer needs. Tool calling must accurately match the field structure of the current single proposal to avoid redundant data from historical projects. Pre-sales proposal boundary design directly affects bidding outcomes. Tool calling results must be traceable and not exceed the preset scope of the proposal. Single document content falls within a standard length range. The tool calling context window must adapt to this length to avoid truncating critical implementation boundary information. Truncation could lead to proposal errors due to incomplete information.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapts to multi-tool calling scenarios for pre-sales proposals, automatically selects matching plugin types |
| `functionCall` | `enabled` | Supports structured output of proposal parameters to facilitate subsequent boundary verification and checking |
| Maximum context length | `8000–12000 characters` | Matches the standard length of single pre-sales technical proposal documents, avoids truncating critical information |
| Maximum single tool call count | `Top 3 entries` | Prevents excessive historical proposals from interfering with boundary design for the current proposal |
| Tool call timeout | `60 seconds` | Adapts to standard response cycles for bidding documents, avoids process blocking |
| Plugin response validation | `Enabled` | Ensures proposal parameters returned by plugins meet field requirements from customer requirement survey forms |

## Three Common Mistakes
- Phenomenon: No termination node is added at the end of the tool calling flow in process orchestration, resulting in cyclic tool calling or repeated concatenation of results. Cause: `toolChoice` is not configured as `none` or corresponding process termination settings are not configured, causing the system to continuously trigger tool calling logic.
- Phenomenon: AI conversation content cannot be hidden after plugin calling, resulting in redundant text output. Cause: The plugin's conversation content shielding configuration is not enabled, or AI reply generation is not turned off in the calling parameters.
- Phenomenon: Abnormal results returned by embedding model calling, with errors related to mismatched embedding dimensions. Cause: A compatible model with consistent embedding dimensions is not selected, or model calling parameters are not configured according to parameters calibrated through actual testing.

## How to Verify Configurations Are Correct
- The FastGPT v4.17.0 process orchestration page is accessed. Whether termination logic is configured at the end of the tool calling node is checked. A test flow is run to confirm cyclic tool calling is not triggered.
- The target plugin is called. Whether AI conversation text is hidden in the output results is checked. The custom card module display is confirmed to be normal and matching the preset proposal fields.
- The embedding model calling is configured. The embedding dimensions of the returned results are confirmed to match the target model parameters. Similarity filtering is verified to comply with preset screening rules.
- The tool calling configuration logs are exported. Values for parameters including `toolChoice` and `functionCall` are checked to exactly match the preset configurations.

The values provided are common starting points and should be measured against samples specific to the actual deployment scenario.
