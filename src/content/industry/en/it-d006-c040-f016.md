# Test Cases and Defect Analysis for Pre-Sales Technical Proposals: Forms and Interactions

## What Data for This Category Looks Like
Data for this category mainly comes from customer interviews, bidding documents, vendor product materials, and historical project plans. Daily output documents include technical proposal books, customer requirement survey forms, quotation lists, and demo scripts. Fields cover technical roadmap, implementation boundaries, budget amount, number of function points, with units typically days, ten thousand yuan, and count units. Update frequency is per order or weekly. Document content for a single pre-sales proposal is updated synchronously with customer requirement adjustments or bidding document updates.

## What Constraints These Characteristics Impose on Forms and Interactions
Since data sources are scattered and must match customer personalized requirements, the logic for dynamically binding multi-source fields must be implemented separately by an external business system. The `formInput` node only collects user input to avoid repetitive manual data entry. Data update frequency is high, so the logic for quickly copying preset templates and adapting to individual customer scenarios must be implemented separately by an external business system or subsequent workflows. Fields include numerical items with units such as amount and cycle. Format verification logic must be implemented separately by an external business system or subsequent workflow branches to avoid bid scoring losses caused by format errors. At the same time, the core content of pre-sales proposals must be strictly aligned with customer requirements, and the form interaction process must prioritize high-frequency links for requirement clarification and solution boundary design.

## Three Common Mistakes
- Phenomenon: After the `formInput` node is configured to reference global variables as default values, the field is empty when submitted. Cause: The global variable scope configuration logic must be handled by an external system or subsequent nodes. Incorrect configuration causes the variables to not be readable by the current form.
- Phenomenon: When submitting requirement items for pre-sales proposals in batches, an execution failure prompt is triggered. Cause: The batch submission limit that meets the requirements of the external system is not set, exceeding the single processing threshold.
- Phenomenon: The preset options of the `userSelect` node do not match customer requirements, and the submitted proposal is judged as inconsistent with the technical roadmap. Cause: The preset options are not updated based on the current customer's industry characteristics, resulting in a deviation between the selection and customer requirements.

## How to Confirm Proper Configuration
- Verify the field range collected by the `formInput` node, confirm that it matches the field requirements of the current customer's requirement survey form.
- Test the default value loading effect of the `formInput` node, confirm that the displayed content conforms to the solution boundary data of historical projects.
- Submit the test example number of requirement items, confirm that no batch submission failure prompt is triggered.
- Verify the preset option source of the `userSelect` node, confirm that it comes from an external business system and covers the common technical selection directions of the current customer.
- Compare the latest bidding documents, verify whether the form verification rules of the external business system or subsequent workflow cover all required fields.
