# Test Case and Defect Analysis for Backup Recovery and Disaster Recovery Drills: Quote Source and Traceability

## What data for this category looks like
Data for this category comes from backup systems, database logs, object storage, and disaster recovery platforms. Documents produced daily include backup policies, recovery drill reports, disaster recovery switchover plans, and data verification records. Data update frequencies fall into three categories: daily, monthly, and quarterly. Core fields include backup timestamp, recovery point objective duration, data verification hash value, and drill execution status. Units include seconds, GB, number of executions, and more. There is no unified fixed multi-dimensional aggregate statistics format.

## What constraints these characteristics impose on the quote source and traceability link
Mixed multi-source data access requires the traceability link to clearly bind unique identifiers for each data source. This prevents duplicate data interference from different backup systems. Documents with different update frequencies must match corresponding recall timeliness rules. Daily updated drill reports need to support real-time retrieval. Quarterly updated backup policies can use lower retrieval priority. Decentralized document structures require configuring field mapping rules. These rules bind core fields such as backup timestamp and recovery point objective duration to test case check items. Data consistency verification results must be directly linked to the hash value of original logs. This ensures tamper-proof traceability and supports accurate defect analysis.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | 8000–12000 token | Matches the single-document length of disaster recovery drill reports and data verification records, avoiding truncation of core verification fields |
| `responseData` | Only return data sources from backup systems and disaster recovery platforms | Filters irrelevant log data, focusing on core traceability sources for this category |
| `detail` | Enable full field display | Shows core fields such as backup timestamp and recovery point objective duration, supporting defect analysis for test cases |
| Maximum Context | 4000–6000 token | Adapts to the splicing length of multi-source data, meeting cross-document associated traceability needs |
| Single Search Limit | Top 6 entries | Covers recall volume for daily updated drill reports and quarterly updated backup policies, avoiding interference from redundant data |
| Data Source Timeout Threshold | 300 seconds | Adapts to interface response durations of disaster recovery platforms, preventing retrieval interruptions |

## Three common configuration errors
- Phenomenon: The generated traceability prompt includes unparsed `\n` escape characters, with no natural line break display. Cause: The text format parsing switch under the `detail` configuration is not enabled, and native escape content from original backup logs is returned directly.
- Phenomenon: The number of traceability data entries returned by retrieval is insufficient, failing to cover the complete content of a single recovery drill report. Cause: The single search limit is set too low, not matching average recall demands for daily updated documents in this category.
- Phenomenon: Traceability results do not link to the data verification hash value field, making verification of recovered data consistency impossible. Cause: No multi-source data field mapping rules are configured, and core fields from disaster recovery platform verification records are not bound.
