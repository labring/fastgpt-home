# Test Cases and Defect Analysis for Backup Recovery and Disaster Recovery Drills: Model Access and Configuration

## What data looks like for this category
Data sources for this category cover four core systems: backup systems, database logs, object storage, and disaster recovery platforms. Daily generated documents include backup policies, recovery drill reports, disaster recovery switchover plans, and data verification records. Document structures include fields such as operation steps, timestamps, verification results, and resource usage.

Data update frequencies fall into three categories: daily (backup logs, verification records), monthly (recovery drill reports), and quarterly (disaster recovery switchover plans). Core business links include recovery point confirmation, drill script execution, and data consistency verification. Errors in these links can lead to consequences such as data loss, recovery timeout, and business continuity interruption. The core difference from database operation and maintenance categories is the focus on cross-system overall recoverability.

## What constraints these characteristics impose on model access and configuration
This category’s data is multi-source, scattered, and has significantly different update rhythms. This requires model access configuration to support unified call permission management for multiple data sources.

Documents with different update frequencies need to adapt to different model call frequencies. High-frequency updated backup logs require shorter model response delays. The verification logic of core business links relies on large models to integrate and analyze cross-system data, so configuration must reserve sufficient context space.

At the same time, the consequences of errors are severe. Configuration must include a failure retry mechanism and observability settings for the call chain, to avoid full-link business interruption caused by a single link failure. FastGPT v4.17.0 configuration templates can meet the access requirements of this type of multi-source data.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Matches the average token size of single documents such as backup policies and recovery drill reports, to avoid missing verification logic due to context truncation |
| `maxTokens` | 2000 token | Meets the single-round response length requirement in disaster recovery drill scenarios, to ensure complete return of verification steps |
| `quoteMaxToken` | 1500 token | Limits the length of referenced backup logs and object storage metadata, to avoid redundant information interfering with model judgment |
| `toolChoice` | auto | Allows the model to independently choose whether to call built-in disaster recovery verification tools, adapting to the complex needs of different drill scenarios |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, for example http://aiproxy:3000 | Environment variable for the App/Admin backend; do not append /v1 or individual model service addresses |
| `temperature` | 0.2 | Reduces random output probability, ensuring accuracy and standardization of disaster recovery verification steps |

## Three common misconfigurations
- When configuring `AIPROXY_API_ENDPOINT`, only set a single model-specific endpoint (such as VLLM/Ollama/Xinference address) or append paths like /v1, instead of using the root address of the AI Proxy service. This causes model calls to stall with no response, and cannot be fixed by restarting the service.
- Directly pass unprocessed raw backup result strings to the large model without adding context prefixes or performing format verification. This causes the large model to fail to recognize valid questions, returning a `Question is empty` error, even if the original result contains valid content.
- Force `toolChoice` to `none` during configuration, disabling the model’s tool call capability. This prevents triggering the script execution verification logic for disaster recovery drills, and fails to detect abnormalities in drill links.

## How to confirm correct configuration
- Check the App/Admin backend startup verification logs to confirm there are no missing `AIPROXY_API_ENDPOINT` or `AIPROXY_API_TOKEN` error messages.
- View model call logs to confirm that the `maxContext` parameter value matches the total token size of the currently imported disaster recovery documents, and no context truncation prompts appear.
- Simulate a small-scale disaster recovery drill, and check whether the model call return results include verification suggestions for drill script execution.
- Verify that the `AIPROXY_API_TOKEN` configured on the App/Admin backend matches the value configured on the AI Proxy backend, and is not empty.

The values provided are common starting points and should be measured against the reader's own samples.
