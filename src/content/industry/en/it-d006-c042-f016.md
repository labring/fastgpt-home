# Test Cases and Defect Analysis for Backup Recovery and Disaster Recovery Drills: Forms and Interactions

## What data for this category looks like
Data for this category comes from backup systems, database logs, object storage, and disaster recovery platforms. Update frequencies are daily, monthly, or quarterly. Four types of documents are produced regularly: backup policies, recovery drill reports, disaster recovery switchover plans, and data verification records. Document fields include recovery point objective, recovery time objective, verification hash values, drill execution duration, and more. Units include seconds, bytes, entries, and others. Core content centers on verification records for cross-system recovery capabilities. This has clear differences from local data verification for single database operations.

## What constraints these characteristics impose on the "forms and interactions" link
Decentralized data sources require adaptation to multi-source data import capabilities of external business systems. Use external interaction logic or downstream nodes to handle export formats from different platforms. Prevent data entry failures caused by format incompatibility.
Differences in update frequencies require adaptation to custom submission cycle capabilities of external business systems. Match daily inspection records and quarterly overall drill reports. Meet archiving requirements for different operation and maintenance scenarios.
Numerous document fields with units require configuration of field verification rules via external business systems or downstream nodes. Prevent non-numeric content from being entered into duration or capacity fields. Ensure accuracy of data entry.
Cross-system recovery verification requirements require the `userSelect` node to collect disaster recovery node type selection information. Cover recovery verification for database, storage, application, and other scenarios.
The most time-consuming recovery point confirmation link requires configuration of pre-submission mandatory verification via external business systems or downstream nodes. Reduce repeated operations during execution and improve drill efficiency.

## Three common mistakes
- Empty recovery drill report displayed after form submission. Cause: External business systems or downstream nodes are not configured with mandatory field verification. Core fields such as hash values and recovery duration are not passed or entered.
- Timeout error with status code 504 occurs during disaster recovery drill execution. Cause: External business systems or downstream nodes are not set with reasonable timeout thresholds, and do not match response cycles of backup systems.
- Import of backup log files fails. The interface prompts unsupported format. Cause: External business systems or downstream nodes are only configured with CSV format import, and JSON format adaptation is not added. Cannot support log formats exported from object storage.

## How to confirm configuration is complete
- Import CSV format log files exported from backup systems. Confirm that external business systems or downstream nodes can normally process the format and pass fields to the `formInput` node.
- Select the quarterly submission cycle. Verify that external business systems or downstream nodes can generate archiving options for the corresponding cycle.
- Select the database node type. Confirm that the `userSelect` node can correctly pass node parameters to the downstream verification process.
- Fill in the duration field and add the second unit. Verify that the field verification rules of external business systems or downstream nodes can take effect normally.
