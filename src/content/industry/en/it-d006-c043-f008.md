# Test Cases and Defect Analysis for Security Incident Response: Workflow Orchestration

## What the data for this category looks like
Data for this category comes from Security Information and Event Management (SIEM), Endpoint Detection and Response (EDR), firewall logs, and host images. Updates occur in real time or per single event trigger. Daily output documents include incident response reports, forensics records, remediation plans, and notification materials. Core fields are unique incident identifier, attack source address, remediation timestamp, evidence hash value, and compliance check mark. No additional custom statistical units are used.

## What constraints these characteristics impose on workflow orchestration
Scattered data sources and real-time update rhythms require workflows to support parallel fetch nodes for multi-source logs. This avoids delays from single-source fetching that would impact response efficiency. Core document fields have fixed compliance check requirements. Workflows must include preset field check nodes to ensure full field completion for incident reports and forensics records. Evidence data volume varies widely across different incidents. Workflows must support dynamic adjustment of data cache thresholds to prevent memory overflow. Failures in the remediation stage directly affect business security. Workflows must be configured with tiered alert and rollback nodes to prevent risk escalation.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` scope configuration | Isolate by user ID | Different incident response engineers handle independent incidents, and need to isolate values of identical global variables |
| Context loading node configuration | Bind `nodeId` to associate historical conversations | Need to load global variables such as forensics records and remediation plans saved in previous incidents |
| Workflow trigger method | Trigger by SIEM alert events | Data updates occur in real time or per single event, requiring automatic workflow startup |
| Custom prompt binding | Associate remediation template `variables` | Need to generate customized prompts adapted to the current incident |
| Timeout threshold | 600 seconds | Incident response requires rapid remediation; timeouts will expand security risks |
| Failure handling node configuration | Associate tiered alert rules | Remediation failures directly impact business security, requiring triggering of corresponding level notifications |

## Three Common Configuration Mistakes
- Phenomenon: Preset context fails to load after calling the workflow API, and the workflow context configuration does not take effect. Troubleshooting: Verify whether the `nodeId` of historical conversations is bound to the context loading node, and confirm whether the workflow can associate previously saved global variables.
- Phenomenon: Variable values are mixed across workflow instances of different users, and identical global variables are overwritten. Troubleshooting: Verify whether the `variables` scope is configured to isolate by user ID, and confirm whether the global variable scope isolates different workflow instances.
- Phenomenon: Workflow execution timeout fails to trigger alerts, or generated prompts use default content. Troubleshooting: Verify whether a reasonable timeout threshold is set, or whether the custom prompt is bound to the corresponding `variables` template, and confirm whether content adapted to the current incident can be generated.

## How to Verify Proper Configuration
- Check the FastGPT v4.17.0 server environment variables. Confirm that `AIPROXY_API_ENDPOINT` (root address of the AI Proxy service, for example http://aiproxy:3000, do not append paths such as /v1) and non-empty `AIPROXY_API_TOKEN` (AI Proxy admin token, consistent with AI Proxy server configuration) are correctly configured, and that no duplicate configuration exists in workflow nodes.
- Trigger a test SIEM alert event, view the workflow execution log, and confirm that the context loading node successfully associates the historical conversation `nodeId` and loads the corresponding global variables.
- Simulate multiple users triggering workflows simultaneously, verify that values of identical global variables do not interfere with each other, and confirm that the `variables` scope configuration takes effect.
- View the generated prompts and alert notifications from the workflow, confirm that the prompts are bound to the remediation template variables of the current incident, and that corresponding alerts are triggered in timeout scenarios.
