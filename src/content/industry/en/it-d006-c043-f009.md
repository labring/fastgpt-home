# Test Cases and Defect Analysis for Security Incident Emergency Response: Tool Calling and Plugins

## What Data for This Category Looks Like
Data for this category primarily comes from SIEM, EDR, firewall logs, and host images. Data updates occur in real time or trigger per single incident. Daily produced documents include emergency response reports, forensics records, disposal plans, and notification materials. Data fields include incident unique identifiers, attack source addresses, timestamps, disposal action numbers, and evidence hashes. No additional fictional statistical values are included.

## What Constraints These Characteristics Impose on the Tool Calling and Plugins Link
Data sources are scattered and updated in real time. Tools must support pulling multi-source logs, and synchronize data per incident granularity to avoid cross-incident confusion. The `toolChoice` configuration adapts to scenario requirements for multi-source data correlation, ensuring flexibility in tool calling.

Document structures are fixed and require compliant retention. Plugins must support exporting standardized disposal results to adapt to report generation workflows.

Attack path restoration is time-consuming and relies on correlated data. Tools must support context-related queries, and limit the data range per call to reduce latency.

Disposal errors have serious consequences. Plugins must include failure retry and log retention capabilities to ensure traceability of the disposal process.

This configuration is based on FastGPT v4.17.0. The specific configuration items are as follows:

| Tool calling switch | Enabled | Adapt to tool calling requirements for real-time emergency response disposal |
| Single call data limit | Top 100 entries | Avoid overloading single log pulls, match the scale of SIEM single push |
| Timeout threshold | 600 seconds | Adapt to complex query time for attack path restoration, avoid interrupting the disposal process |

## Three Common Misconfigurations
- Phenomenon: After tool calling is triggered, both the native AI reply and tool results are displayed. Intermediate step content cannot be hidden separately. Cause: The result shielding configuration for tool calling is not enabled, and the requirement to output only final disposal results is not specified.
- Phenomenon: When orchestrating workflows, only a single model node can be bound. Multi-step distributed processing cannot be implemented. Cause: The multi-tool series configuration for workflows is not enabled, and the permission switch for step-by-step execution is not turned on.
- Phenomenon: When calling tools with a custom key, authentication failure is returned. Log data cannot be pulled normally. Cause: The access permission scope of the key is not configured, and the data source whitelist for the corresponding SIEM/EDR is not bound.

## How to Confirm Configuration Is Complete
- Initiate a simulated attack incident to trigger the tool calling process. Check if the interface only displays the final disposal result, with no intermediate step AI reply content.
- View tool calling logs to confirm that the number of data pulled per call matches the preset limit, and no overload-related error prompts appear.
- Verify the calling permissions of the custom key. Attempt to pull specified SIEM logs, and confirm that the returned data format matches the preset structured requirements.
- Check the workflow configuration page to confirm that multiple tool nodes can be connected in series. After step-by-step processing, only the final dialogue model result is output.
