# Test Cases and Defect Analysis for Security Incident Response: Citation Sources and Traceability

## What This Type of Data Looks Like
Data sources for this category include SIEM, EDR, firewall logs, and host images. Update frequency is real-time or triggered per single incident. Daily deliverables consist of incident response reports, forensic records, remediation plans, and notification materials. Fields include attack paths, remediation time, evidence hashes, affected asset IDs, and more. Users must bind a unique incident ID to enable traceability and association. Typical users include security operation centers, incident response engineers, and customer security leads.

## Constraints for Citation Sources and Traceability
Real-time multi-source log updates require traceability processes to bind a unique incident ID to prevent cross-incident citation confusion. Structural differences across document types require preset field matching rules by document type during retrieval, to ensure cited content is strongly correlated with attack paths and remediation actions. The high time cost of evidence chain organization requires traceability results to directly link to original log fragments, without requiring secondary verification. Errors may lead to serious consequences including expanded data leaks and business outages, so the credibility threshold for cited sources must be strictly limited.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Similarity Threshold | 0.75–0.85 | Match the precision of structured security logs, filter low-relevance alerts |
| Single Recall Limit | Top 8 entries | Match the typical number of log entries per incident, avoid context redundancy |
| `quoteMaxToken` | 800–1200 characters | Cover the core paragraph length of a single forensic record or remediation plan |
| `responseData` | Enabled | Retain associated fields of original logs to support evidence chain traceability |
| `detail` | Enabled | Display specific paths of citation sources, facilitating attack path verification |
| Context Window Size | 4000–6000 tokens | Adapt to the total retrieval length of multi-source logs |

This document applies to FastGPT v4.17.0

## Three Common Misconfigurations
- Phenomenon: Citation sources returned in conversations do not match the local knowledge base content of the current security incident. Cause: No incident ID is bound as a context filter condition, resulting in recall of log data from historical incidents.
- Phenomenon: Cited content exceeds expected length and cannot be truncated. Cause: The `quoteMaxToken` parameter value is not set appropriately, and does not match the typical length of a single document.
- Phenomenon: No relevant citations are returned after mixed retrieval. Cause: The similarity threshold is set too high, filtering some low-relevance but critical log fragments.

## How to Verify Proper Configuration
- Import logs and documents for a single security incident, submit a question related to attack path restoration, and verify that returned citation sources only associate with the current incident ID.
- View the citation display area, confirm that the length of cited content matches the preset value of `quoteMaxToken`, with no overlong or truncated anomalies.
- Switch to mixed retrieval mode, adjust the similarity threshold, and verify that the number of returned citations changes as expected with the threshold.
- Disable the `responseData` toggle and submit a question, confirm that associated fields of original logs are no longer displayed in the conversation.

The values listed are common starting points and should be evaluated against samples matching the actual deployment context.
