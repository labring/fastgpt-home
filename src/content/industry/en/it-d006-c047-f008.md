# Test Case and Defect Analysis for Vulnerability Disclosure Handling: Workflow Orchestration

## What the data for this category looks like
Data for this category comes from private vulnerability reports, code repositories, CVE numbering authorities, and publicly released channels.
Daily associated documents include security advisories, vulnerability reports, repair patches, and CVE application materials.
Data fields include unique vulnerability identifiers, affected component scopes, repair statuses, disclosure coordination records, and more.
There is no fixed unified format. Updates occur once per vulnerability event.
Data transfer must strictly follow sequential requirements for confidentiality and public release.

## What constraints these characteristics impose on workflow orchestration
Dispersed data sources and inconsistent formats require workflows to pull data from multiple channels across multiple nodes, and adapt to non-standardized document content.
Updates trigger per individual event, so workflows do not need cyclic scheduling. They only start when a vulnerability event occurs.
Data transfer involves sequential requirements for confidentiality and public release, so workflows must include permission verification and content desensitization steps.
Error consequences affect project reputation and user safety, so workflows must be configured with failure retry and alert nodes to ensure exceptions can be traced.

## Configuration Settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | Event-based trigger | Matches the one-update-per-event rhythm of the category, avoids invalid scheduling |
| Variable Configuration | Pass `variables` as the original vulnerability report content | Adapts to multi-source, non-standardized document data, and facilitates key information extraction in subsequent steps |
| Code Run Node Timeout | 600 seconds | Covers typical time for vulnerability impact assessment and patch verification, prevents mid-execution task interruption |
| Failure Retry Count | 2 times | Balances task success rate and overall time consumption, reduces resource waste from repeated execution |
| Core Node Tagging | Tag vulnerability assessment and disclosure coordination links by `nodeId` | Facilitates subsequent troubleshooting of execution exceptions, quickly locates problematic steps |
| Context Length Limit | 800–1200 characters | Adapts to input length requirements of security analysis models, prevents analysis failure from content truncation |
| Memory Limit | 1000 MB | Adapts to running resource requirements of security analysis models, prevents node crashes from insufficient memory |

## Three Common Misconfigurations
- The console.log logs from code run nodes cannot be viewed in the frontend inspection console. The reason is that workflow run logs are stored in the node execution log panel by default, and are not synchronized to the frontend inspection console.
- The AI model dropdown list for the problem classification node is empty. The reason is that the dedicated security analysis model has not been bound in the platform configuration area, resulting in no content in the optional list.
- The workflow API call returns a parameter error prompt. The reason is that the required fields of the `variables` parameter have not been passed correctly, causing the system to fail to recognize the vulnerability data to be processed.

## How to Confirm Proper Configuration
- Trigger a test vulnerability event, and check whether the workflow execution log includes complete data source content for each link.
- Enter the execution log panel of the code run node, and confirm that the console.log content has been output normally.
- Check the AI model dropdown list of the problem classification node, and confirm that the security analysis model options have been loaded.
- Call the test API for the corresponding workflow, and confirm that the returned result includes the core fields of vulnerability assessment.
