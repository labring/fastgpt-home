# Test Cases and Defect Analysis for Security Vulnerability Disclosure Handling: Forms and Interactions

## What the data for this category looks like
This category of data comes from private vulnerability reports, code repositories, CVE-numbered bodies, and official release channels. Daily produced documents include security advisories, vulnerability reports, repair patches, and CVE application materials. Individual vulnerability events trigger data updates, with no fixed cycle. Core fields include unique vulnerability identifiers, impact scope, disclosure coordination timelines, and patch submission status. These fields have no unified quantitative units, and some fields must strictly follow the format requirements of CVE-numbered bodies.

## What constraints these characteristics impose on forms and interactions
The data characteristics of this category impose multiple constraints on the forms and interactions workflow. Private vulnerability report privacy requirements require external business systems or subsequent nodes to configure role permission verification rules, so only authorized members can submit and view sensitive content. CVE-numbered body format specifications require external business systems or subsequent workflow nodes to implement field verification logic to block non-compliant submissions. The scenario where a single vulnerability event is associated with multiple types of documents requires forms to support multiple file uploads, and external business systems or subsequent nodes must implement field linkage logic. The timeliness requirement for disclosure time coordination requires external business systems or subsequent nodes to configure timeout reminder mechanisms to prevent delays in the disclosure schedule. External business systems or subsequent nodes must differentially configure operation permissions for different roles to avoid unauthorized modification of core vulnerability status.

## Three common error scenarios
- Symptom: A field format error is returned after submitting a vulnerability report. Verification step: The external business system or subsequent nodes are checked to confirm whether they have implemented field verification logic that complies with the format requirements of CVE-numbered bodies.
- Symptom: Only partial content is received when updating vulnerability status. Verification step: The external business system or subsequent nodes are checked to confirm whether they have correctly configured streaming response receiving rules.
- Symptom: Unauthorized members can submit vulnerability reports. Verification step: The external business system or subsequent nodes are checked to confirm whether they have configured role permission verification rules, and verify the submission permissions of unauthorized members.

## How to confirm the configuration is complete
- A test vulnerability report that complies with CVE format is submitted, and the external verification logic is checked to confirm whether it normally blocks non-compliant content.
- Accounts with different roles are switched, and the corresponding roles are checked to confirm whether they can access or modify the corresponding vulnerability form content.
- Multiple test documents are uploaded, and the number of uploads is checked to confirm whether it meets the preset upper limit.
- The preset timeout period is waited, and the external reminder mechanism is checked to confirm whether it is normally triggered.
