# Test Cases and Defect Analysis for Security Monitoring and SOC Duty: Tool Invocation and Plugins

## What Data Looks Like for This Category
Data for this category originates from SIEM, EDR, NDR, and third-party threat intelligence sources. Two update rhythms are used: real-time and daily update.
Common associated documents include alarm disposal sheets, duty records, threat intelligence notifications, and security operation daily and weekly reports. Each document’s fields include alarm ID, attack type, disposal status, response duration, and other details. Alarm disposal sheets must be linked to specific attack traceability fields. Duty records must record real-time threat analysis progress and dispatch status.

## Constraints Imposed on Tool Invocation and Plugins
Real-time updated alarm data requires tool invocation to support low-latency triggering, to avoid missing critical disposal windows due to response timeouts. Multi-source heterogeneous data sources require plugins to adapt to different API formats, and support batch pulling of alarm entries from SIEM/EDR.
Daily updated threat intelligence and weekly report data requires support for scheduled triggering of calls, to avoid repeated pulling of full data that consumes excess resources.
The high time-consuming nature of the alarm analysis and judgment process requires tool invocation to support context retention, linking historical duty records and disposal sheets to reduce repeated query operations for analysts.

## How to Configure Settings
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale for This Setting |
| ---- | ---- | ---- |
| `toolChoice` | auto mode, triggered by alarm priority | Adapts to the real-time alarm analysis needs of SOC duty, automatically selects matching security tools |
| Tool call timeout threshold | 300 seconds | Real-time alarm disposal requires rapid response; manual intervention processes must be triggered if the threshold is exceeded |
| Plugin batch call limit | First 10 alarms | Avoids overload from single calls, adapts to the conventional processing rhythm for SIEM batch alarms |
| `functionCall` | Force specify the security tool set | Ensures all called tools are compliant security tools for SOC scenarios, avoiding unauthorized calls |
| Scheduled trigger configuration | Pull daily updated threat intelligence every 1 hour | Adapts to the update frequency of daily updated intelligence, reducing unnecessary resource consumption |
| Context retention duration | 24 hours | Links that day’s duty records and alarm disposal sheets, ensuring continuity of analysis operations |

## Three Common Misconfiguration Issues
- Phenomenon: When tool invocation triggers two or more security tools simultaneously, field mismatches appear on alarm disposal sheets. Cause: No parameter verification rules for batch calls are configured, leading to conflicting data formats returned by different tools.
- Phenomenon: Calls to the current time plugin fail, returning status code 400. Cause: No time format requirements for the SOC scenario are bound in the plugin configuration, causing the returned value to fail to match the timestamp fields used in alarm analysis.
- Phenomenon: Low accuracy of tool invocation, with excessively long time spent on false positive elimination. Cause: No target data source range is limited for tool invocation, causing the plugin to pull irrelevant SIEM log entries.

## How to Confirm Configuration Is Complete
- Execute a single real-time alarm call, check whether the fields returned by the tool match the preset fields on the alarm disposal sheet.
- Trigger a batch call test, confirm that the number of returned alarm entries meets the configured limit requirement.
- Configure a scheduled task, check whether threat intelligence data is pulled at the set time interval.
- Simulate a call failure scenario, confirm that the preset manual escalation alert process is triggered.
