# Test Cases and Defect Analysis for Customer Onboarding and Tenant Initialization: Workflow Orchestration

## What data belongs to this category
This category of data primarily originates from CRM systems, contract orders, identity management systems, and product backends. Daily associated documents include customer onboarding application forms, tenant configuration sheets, administrator account lists, and delivery confirmation documents. Data updates follow a per-order cycle. Each individual onboarding process corresponds to a separate data set. Fields include customer entity information, tenant permission scope, initial configuration parameters, and more. The core focus is on tenant account creation and basic permission configuration, which differs from subsequent data migration operations.

## Constraints on workflow orchestration
Multi-source data access requires workflow configurations to include cross-system invocation nodes. Systems must connect to the identity management system to create accounts, and pull customer information from the CRM for verification. Clear rules for passing cross-system parameters via `variables` must be established. The independent data nature of single onboarding processes requires workflow nodes to support single-instance isolation of `variables`, preventing data mixing across different tenants. Core time-consuming steps require orchestration nodes to sequentially run information verification, permission initialization, and result confirmation. Error capture nodes must also be configured to handle exceptions in each link, avoiding delivery delays or customer login failures. FastGPT v4.17.0 workflow node configurations support basic adaptation to these constraints.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Cross-system parameter passing | Use `variables` to store customer ID, permission template ID | Complies with FastGPT workflow parameter transfer specifications, supports synchronization of tenant core identifiers across nodes, and prevents data misuse |
| Error capture trigger threshold | Configure the node timeout threshold bound to `nodeId` as 600 seconds | Covers the standard response duration of identity management system interfaces, avoids false error triggers due to network fluctuations, while retaining exception capture capabilities |
| Batch execution loop upper limit | Set the loop upper limit according to the number of entries in the administrator account list | Matches the number of administrator accounts for a single onboarding, prevents loop execution from exceeding expected scope and causing unnecessary resource consumption |
| Global variable append rule | Enable automatic appending of loop results to the `variables` array | Enables transfer of loop node results to external systems, meeting requirements for result aggregation and delivery confirmation after batch onboarding |
| Model node thinking control | Adjust the switch status according to the verification scenario | Disable thinking for information verification nodes to improve execution efficiency, enable thinking for permission verification nodes to optimize judgment logic |
| Multi-file upload capacity | Configure a single upload upper limit of 1000 MB | Matches the size range of conventional tenant initialization configuration documents, preventing process interruptions caused by upload failures |

## Three common configuration errors
- Missing node error capture: After an error occurs in a model request or system connection node, the workflow terminates directly without clear error copy. This occurs when no error capture branch bound to `nodeId` is configured, and no retry or jump logic is set for exceptions.
- Loop results cannot be passed externally: After the loop node completes execution, the global variable does not include the execution results of child items. This occurs when the configuration for automatically appending loop results to `variables` is not enabled, or the output path of the loop variable is not correctly bound.
- Model thinking control failure: The interface is set to disable model thinking, but thinking processes are still generated during actual execution. This occurs when the interface display switch is confused with the workflow node's execution control parameters, and no corresponding logic is adjusted in the node configuration.

## How to verify a correct configuration
- Trigger a single test onboarding process, check the execution logs of each node, confirm that cross-system parameter transfer is normal, and there are no uncaught errors.
- Execute a batch test scenario, check whether the global variable array includes the execution results of all loop child items, and verify that the result transfer logic meets expectations.
- Adjust the thinking control configuration of the model node, execute the corresponding verification task, and confirm that the execution result matches the configured thinking switch status.
- Upload multiple configuration files to the workflow node, confirm that the node can normally receive and parse all file contents, and there are no upload failure prompts.

The values provided are common starting points and should be measured against the reader's own samples.
