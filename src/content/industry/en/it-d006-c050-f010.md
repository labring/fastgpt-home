# Test Cases and Defect Analysis for Customer Onboarding and Tenant Initialization: Quote Source and Traceability

## What the Data for This Category Looks Like
Data for this category primarily originates from CRM, contract order systems, identity management systems, and product backends. Update frequency is per order or daily. Daily generated documents include onboarding application forms, tenant configuration sheets, administrator account lists, and delivery confirmation documents. Core fields include customer unique identifier, tenant ID, configuration item status, onboarding time, associated contract number, and additional relevant fields. There is no unified global data pool. Dispersed data across multiple systems must be associated using tenant IDs.

## Constraints Imposed by These Characteristics on the "Quote Source and Traceability" Workflow
Since data is scattered across multiple independent systems, quote traceability must accurately bind tenant IDs to enable cross-system data association. This prevents confusion between configuration records of different tenants. The per-order or daily update frequency requires that traceability query data sources stay synchronized in real time. This ensures returned configuration information matches the current tenant state. Fixed document structures require traceability to match specific document fields—such as the application number on an onboarding application form—to quickly locate corresponding delivery records. Errors in this workflow directly impact customer login and delivery acceptance. The traceability link must ensure returned information can be directly tied to specific onboarding operations and responsible parties.

## Configuration Guidelines
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | 900–1100 token | Adapts to the total length of all configuration fields for single-tenant onboarding. Fully retains key information required for traceability, such as document IDs and tenant identifiers |
| `responseData` | Return only associated system fields | Limits query scope to core onboarding data from CRM and identity management systems. Excludes redundant non-business fields |
| `detail` | Enable full field display | Fully records configuration operation time, operator, and status change details. Supports fast traceability and troubleshooting |
| Timeout Threshold | 60 seconds | Matches the average response time for multi-system data pulling. Prevents traceability requests from being interrupted due to timeout |
| Single Query Limit | Top 5 associated records | Calibrated based on actual testing | Controls the volume of data returned by traceability queries. Prevents interface loading lag |

## Three Common Configuration Mistakes
- Phenomenon: Markdown formatting in referenced tenant configuration descriptions is not rendered. Raw syntax is displayed directly. Cause: The format parsing switch was not enabled in the `responseData` configuration. This causes traceability-returned document content to be output as plain text.
- Phenomenon: Fields returned by traceability queries are empty. Corresponding onboarding application forms cannot be located. Cause: The mapping relationship between tenant ID and customer ID in the CRM system was not correctly bound. This causes data source matching to fail.
- Phenomenon: Traceability query delay exceeds 30 seconds after tenant initialization is complete. Cause: The `quoteMaxToken` value is too large. This causes the system to occupy excessive memory when pulling traceability data, extending response time.

## How to Verify Successful Configuration
- Manually trigger a simulated tenant initialization process. Check if traceability returned content includes complete document information such as onboarding application forms and administrator account lists.
- View log output for the `detail` parameter. Confirm that full field information such as configuration operation time and operator is recorded.
- Test traceability queries in a multi-tenant scenario. Verify that configuration data from different tenants is not returned mixed together.
- Verify that Markdown formatted configuration descriptions render correctly. Confirm that the format parsing switch has been correctly enabled.

The values provided are common starting points and should be measured against the reader's own samples.
