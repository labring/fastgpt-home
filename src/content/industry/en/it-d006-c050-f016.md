# Test Cases and Defect Analysis for Customer Onboarding and Tenant Initialization: Forms and Interactions

## Data Profile for This Category
This category of data typically originates from CRM, contract order systems, identity management systems, and product backends. Update frequency is per order or daily. Daily supporting documentation includes onboarding application forms, tenant configuration sheets, administrator account lists, and delivery confirmation forms. Core fields include customer unique identifiers, tenant codes, permission scopes, onboarding timelines, and administrator account lists. Data structures must align with cross-system synchronization rules. There is no unified fixed statistical standard.

## Constraints Imposed on Forms and Interactions
Data from multiple connected systems requires form fields to match the format rules of each system. Manually entered information will fail cross-system synchronization if this requirement is not met. Per-order or daily update frequency requires forms to support temporary modifications and operation logging. This prevents conflicts during data updates. The most time-consuming customer information verification step requires forms to reduce manual input steps. This lowers the probability of manual input errors. Severe error consequences require interaction flows to add confirmation steps. This notifies relevant parties of operation impacts in advance, and prevents issues such as customer login failures or delivery delays.

## Three Common Mistakes
- Symptom: After a customer submits an onboarding application, the system returns status code 400 and prompts "Tenant information verification failed". Verification action: Check whether the external system field format verification rules associated with the form input node match the contract number format entered by the customer
- Symptom: Some older browser versions cannot open the selection popup for tenant permission configuration. Clicking the control has no response. Verification action: Test whether the interaction controls of the user selection node can normally pop up and check permission options using different browser versions
- Symptom: After the onboarding process is completed, the administrator attempts to log in to the tenant backend and is prompted "Account does not exist". Verification action: Check whether the administrator accounts generated by the external system have been synchronized to the identity management system

## How to Verify Correct Configuration
- Submit one test onboarding application, and verify whether external verification logic blocks input content that does not match the format requirements of corresponding systems
- Open different browser versions, and test whether the interaction controls of the user selection node can normally pop up and check permission options
- Complete the initialization process for a test tenant, and verify that the number of administrator accounts generated by the external system matches the records in the administrator account list
- Check system logs to confirm that the time taken for data synchronization to CRM and identity management systems after submitting an onboarding application does not exceed the set 600 seconds (test example) threshold
