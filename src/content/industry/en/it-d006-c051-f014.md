# Test Cases and Defect Analysis for Customer Data Import Migration: Model Access and Configuration

## What this category of data looks like
This type of data primarily comes from customer legacy systems, CSV or Excel templates, database exports, and product import logs. Daily associated documents include standardized data templates, migration execution plans, field mapping comparison tables, and migration validation reports. Data update frequency follows project timelines, typically updated per order or on an irregular basis. Fields cover customer identifiers, business transactions, contact information, transaction amounts, and more. Units vary by specific business scenario, with no unified fixed format.

## What constraints these characteristics impose on the model access and configuration link
The diversity of data sources requires model access configurations to support multi-format input parsing, with preset adaptation rules for different data sources such as CSV and database exports. The uncertain update frequency means configurations must support dynamic adjustments that take effect without restarting services. The lack of unified field formats requires models to have semantic field mapping capabilities, with relevant parameters matching the semantic matching precision of the business scenario. The existence of import logs requires configurations to support anomaly troubleshooting, with parameter trace records retained. The variable proportion of dirty data requires configuring reasonable filtering thresholds to ensure the validity of imported data.

## How to set configurations
The following configurations are adjusted for the customer data import migration scenario based on FastGPT v4.17.0.

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the total length of customer imported data, covering the context requirements of field mapping and validation |
| `temperature` | 0.2–0.4 | Reduces random output, ensuring consistency in field mapping and rule matching |
| `toolChoice` | auto | Allows the model to independently determine whether to call tools to handle format verification and cleaning of imported data |
| `AIPROXY_API_ENDPOINT` | Fill in the root address of the AI Proxy service according to the deployment environment, for example http://aiproxy:3000. Do not append /v1 or /chat/completions; this is not a single-model address | Ensures correct routing of model requests and avoids connection errors |
| `AIPROXY_API_TOKEN` | Administrator Token consistent with the AI Proxy server configuration, and cannot be empty | Ensures identity legitimacy of interface calls and prevents unauthorized access. This variable is an environment variable for the App/Admin server, and must not be filled in workflow global variables, application API request headers, or the general model management page |

## Three common configuration mistakes
- A 404 status code (no body) is returned when accessing the model. The cause is incorrect configuration of `AIPROXY_API_ENDPOINT` (root address of the AI Proxy service) or `AIPROXY_API_TOKEN` (AI Proxy administrator Token), resulting in the request failing to reach the AI Proxy service; or a required variable is not configured, causing startup verification to fail.
- The large language model does not reference web search content in non-tool call mode. The cause is that `toolChoice` is not configured as auto or required, so the model cannot trigger the tool call process.
- The model does not automatically parse file content after uploading a file in simple mode. The cause is that the `maxContext` configuration value is too small to accommodate the context content after file parsing, causing the model to skip the parsing step.

## How to confirm the configuration is correctly set
- Access `AIPROXY_API_ENDPOINT` (root address of the AI Proxy service) to verify the connectivity of the AI Proxy service and confirm that a normal response is returned.
- Upload a test CSV template to trigger field mapping parsing, and check whether the mapping result output by the model matches the preset field mapping comparison table.
- Trigger a simulated import operation, and check whether the complete parameters and return results of the model call are recorded in the product import logs.
- Adjust the `temperature` parameter to different ranges, compare the consistency of field mapping, and confirm that the configuration takes effect.

The values provided are common starting points and should be measured against the reader's own samples.
