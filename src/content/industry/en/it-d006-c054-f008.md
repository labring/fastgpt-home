# Test Cases and Defect Analysis for Container Platform Operations: Workflow Orchestration

## What the data for this category looks like
Daily operations documents for this category include cluster change tickets, namespace quota tables, deployment records, and fault reports. Data sources are Kubernetes API, image registries, monitoring systems, and CI pipelines. Update frequency is daily or after each cluster change.
Cluster change tickets include change time, change content, and affected namespaces. Namespace quota tables list CPU core counts and memory quota units. Deployment records record Pod replica counts and image versions. Fault reports include error log snippets, trigger times, and affected scopes. Data fields and units are fixed according to operations document formats.

## What Constraints These Characteristics Impose on the Workflow Orchestration Link
Data sources depend on Kubernetes API and monitoring systems. Workflows must be configured with corresponding interface pull permissions to avoid unauthorized access to cluster data.
Update frequency is daily or change-triggered. Workflow trigger timing must match change events or scheduled execution to ensure data timeliness.
Daily document fields are fixed. Workflow `variables` must bind to corresponding document fields as input parameters. `nodeId` must match different operations nodes to prevent process connection errors.
Time-consuming steps such as resource quota adjustment and Pod troubleshooting must be connected into automated workflows. Failure alerts and rollback steps must be configured to avoid business interruption risks.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Timing | Triggered by cluster change events or every 24 hours | Matches the update frequency of daily updates or post-change updates |
| Variable Configuration | Bind `variables` to namespace quotas, Pod status, and change records | Corresponds to the fixed fields of daily operations documents |
| Node Timeout | 300 seconds | Matches the typical response duration of the Kubernetes API |
| Failure Retry Count | 2 times | Prevents resource conflicts caused by repeated cluster change operations |
| Workflow Export Permissions | Accessible only to team operations members | Cluster configuration is sensitive operations information |
| Context Association Scope | Associate the latest 3 change records | Fault troubleshooting requires historical change information to locate issues |

## Three Common Mistakes
- Symptom: The workflow export button is grayed out or unresponsive after clicking. Cause: Team-level workflow export permissions are not configured, and unauthorized roles cannot obtain export permissions.
- Symptom: When using a model that does not support function call, the workflow node reports an error "tool calls are not supported". Cause: No search node was added as an alternative process for function call, so the orchestration logic cannot be completed.
- Symptom: Workflow canvas node drag delay exceeds 5 seconds. Cause: FastGPT v4.17.0 has not been upgraded; older versions have insufficient rendering optimization for multi-node canvases.

## How to Confirm the Configuration Is Complete
- Manually trigger the workflow once. Check whether the namespace quota and Pod status data of the corresponding cluster can be correctly pulled, and verify that the `variables` binding takes effect.
- Disable the function call capability of the model, trigger the workflow, and verify that the search node is automatically called to supplement the execution logic.
- Switch to a non-operations role account, check whether the workflow export entry cannot be accessed, and confirm that the permission configuration takes effect.
- After upgrading to FastGPT v4.17.0, drag workflow nodes and check that the editing response has no significant delay.
