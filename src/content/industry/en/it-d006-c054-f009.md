# Test Cases and Defect Analysis for Container Platform Operations: Tool Calling and Plugins

## What data for this category looks like
Data for this category primarily comes from Kubernetes APIs, image registries, monitoring systems, and CI pipelines. Daily associated operation and maintenance documents include cluster change tickets, namespace quota tables, deployment records, and fault reports. Data updates occur daily or when cluster changes are triggered. Core fields include namespace identifiers, Pod status codes, resource quota thresholds, image version numbers, and fault troubleshooting logs. Field names and units vary based on data source type, with no unified fixed format.

## What constraints these characteristics impose on the tool calling and plugins workflow
Scattered data sources are updated in real time as clusters change. This requires tool calling to support parallel pulling from multiple data sources to avoid single-call timeouts. Daily operation and maintenance documents have widely varying structures. Plugins must support custom field mapping to adapt to quota tables and change ticket formats across different clusters. The most time-consuming links of Pod exception troubleshooting and cluster upgrade verification require tools to automatically associate multi-source data and aggregate context. Plugins must have structured data parsing capabilities. Errors directly impact business, so tool calls must trigger alerts and retain complete call chain logs when failures occur to facilitate subsequent defect tracing.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | Adapts to scenarios where multiple tools are called on demand for container platform operations, automatically matching tools for cluster data pulling, fault troubleshooting, and similar tasks |
| `functionCall` | Stitch together in structured format | Adapts to standardized data returned by Kubernetes APIs, facilitating field parsing in subsequent defect analysis workflows |
| Tool call timeout duration | 600 seconds | Covers single-call time consumption for large-scale cluster changes and multi-Pod exception troubleshooting, preventing call interruptions due to large data volumes |
| Number of data items returned per call | First 20 items | Controls returned data volume to avoid exceeding the context capacity limit of downstream models |
| Data cache validity period | 24 hours | Adapts to daily updated cluster data, preventing calls from pulling stale data due to cache expiration |
| Number of retries on call failure | 3 times | Addresses temporary network fluctuations in monitoring systems and image registries, reducing the impact of single-call failures |

## Three common misconfigurations
- Phenomenon: Tool calls return empty results with no clear error message. Cause: Parallel pulling from multiple data sources is not configured, and only a single monitoring system interface is called, making it impossible to obtain complete Pod exception troubleshooting data.
- Phenomenon: Raw cluster configuration data pulled by tools is directly output to end users. Cause: No content filtering rules are set, and unprocessed tool return content is returned directly, violating the information isolation requirements of test cases.
- Phenomenon: Scheduled tool calls frequently time out and interrupt. Cause: No reasonable timeout duration is set, and data pulling time for large-scale cluster changes on the container platform exceeds the preset threshold.

## How to confirm proper configuration
- Execute a test case simulating a cluster change, check whether the tool automatically pulls the quota table and deployment records for the corresponding namespace.
- Trigger a Pod exception troubleshooting test scenario, confirm that the structured data returned by the tool call can be correctly parsed into a defect analysis report.
- Manually trigger a tool call failure, check whether complete call chain logs are generated and alerts are triggered.
- Verify the content filtering rules, confirm that only processed defect analysis results are returned to downstream models.
