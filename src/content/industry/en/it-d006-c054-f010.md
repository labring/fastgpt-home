# Test Cases and Defect Analysis for Container Platform Operations: Citation Sources and Traceability

## What This Category of Data Looks Like
This category of data primarily originates from Kubernetes APIs, image registries, monitoring systems, and CI pipelines. Daily generated documents include cluster change tickets, namespace quota tables, deployment records, and fault reports. Data fields include cluster identifiers, namespace names, Pod running statuses, image versions, change execution times, resource quota thresholds, and more. Update frequency is daily or after each cluster change. Data structures are primarily structured tables and log entries; some monitoring metrics use time-series formats, and there is no unified cross-system metadata identifier.

## Constraints These Characteristics Impose on Citation Sources and Traceability
Data from this category is scattered across multiple heterogeneous systems. Cross-system metadata association must be completed during citation and traceability; otherwise, the correct knowledge base source cannot be matched. Data update frequency is flexibly adjusted alongside cluster changes, so the timestamp of cited content must be verified to avoid using expired cluster change tickets or deployment records. Fields in daily documents are mostly operation and maintenance-specific identifiers, and association can only be completed by matching the unique field formats of container platforms. At the same time, the accuracy of traceability results directly affects fault troubleshooting and change verification. Incorrect citations may lead to deviations in subsequent operation and maintenance decisions, and even cause business interruptions.

## Configuration Settings
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `quoteMaxToken` | 800–1200 token | Matches the single-block content length of container platform operation and maintenance documents, to avoid truncating key fields such as cluster IDs and Pod statuses |
| `responseData` | Enable metadata binding | Ensures returned content is associated with corresponding Kubernetes API logs or CI pipeline change records |
| `detail` | Full mode | Retains detailed troubleshooting steps and resource quota adjustment records in fault reports |
| Single recall source count | Top 5 entries | Matches the number of single change associated entries in daily operation and maintenance documents, to avoid excessive redundant information interfering with troubleshooting |
| Context window duration | 600 seconds | Matches the average execution cycle of cluster changes, ensuring cited change records align with the timeline of the current issue |

## Three Common Misconfigurations
- Phenomenon: Returned container platform fault troubleshooting answers have no association with the linked knowledge base citation content. Cause: Cross-system metadata mapping configuration was not completed, resulting in recalled source entries not matching the actual cluster change records.
- Phenomenon: When configuring workflow visibility, separate control of citation display for some content is not possible. Cause: The binding level of the `responseData` parameter was not distinguished, resulting in all citations being displayed or hidden uniformly.
- Phenomenon: Some deployment records fail to generate question-and-answer pairs after the knowledge base is split. Cause: The unique field format of container platform operation and maintenance documents was not matched, causing the splitting tool to fail to identify key information such as resource quotas and Pod statuses.

## How to Verify Successful Configuration
- Submit a query involving Pod exception troubleshooting or cluster change verification, and check whether the linked citation sources in the returned answer include the corresponding Kubernetes API logs and fault reports.
- Check the citation list below the answer to confirm that the fields of each source match the actual configuration of the current cluster.
- After adjusting the `quoteMaxToken` parameter, verify that the returned content does not truncate key cluster identifiers or quota values.
- Switch the `detail` parameter mode, and confirm that the fault troubleshooting steps displayed in full mode match the original document content.

The values provided are common starting points and should be evaluated against the reader's own samples.
