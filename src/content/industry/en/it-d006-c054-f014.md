# Test Cases and Defect Analysis for Container Platform Operations: Model Integration and Configuration

## What this type of data looks like
Core data for container platform operations comes from Kubernetes APIs, image registries, monitoring systems, and CI pipelines. Update frequency is daily or on each cluster change. Daily produced documents include cluster change tickets, namespace quota tables, deployment records, and fault reports. Data fields include cluster node status, Pod running status, image tags, CI build results, resource quota thresholds, and more. There is no fixed single data length. Single-batch data volume fluctuates with cluster scale.

## Constraints Imposed by These Characteristics on the "Model Integration and Configuration" Link
The data structure for container platform operations is mostly structured fields, and also includes unstructured logs and fault descriptions. Model integration configurations must support both structured field parsing and non-contextual content reference. Data update frequency is high. Model calls must adapt to real-time requirements, to avoid losing critical cluster status information due to context length limits. Tool call scenarios focus on Pod exception troubleshooting, resource quota adjustment, and similar operations. Automatic tool selection must be configured to adapt to different operation and maintenance scenarios. At the same time, the intranet security of the call link must be ensured, to match the RBAC permission system of the container platform.

## How to Set the Configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | The context for container platform operations includes complete cluster status snapshots, multiple fault reports, and change records. Sufficient historical data length is required to support comprehensive troubleshooting |
| `maxTokens` | `2000–3000 token` | Responses for test cases and defect analysis must include specific troubleshooting steps and quota adjustment suggestions. This value range balances output completeness and model performance |
| `quoteMaxToken` | `1500 token` | Original content from cluster change tickets and fault reports must be prioritized for reference. This ensures troubleshooting basis is traceable, and reduces generation of fictitious operation and maintenance suggestions |
| `toolChoice` | `auto` | Container platform operations frequently call Kubernetes APIs to query Pod status and quota information. Automatic tool selection adapts to call requirements for different troubleshooting scenarios |
| `temperature` | `0.2–0.4` | Defect analysis and test case generation require strict accuracy. A lower temperature value reduces the probability of generating fictitious content |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, for example http://aiproxy:3000 | This variable is a required environment variable for the App/Admin server. Configure it to the intranet-accessible root address of the AI Proxy service. Do not append /v1 or /chat/completions paths. Using an intranet endpoint ensures data transmission security and avoids external network attack risks |

## Three Common Misconfigurations
- Symptom: Model calls return the "Non-streaming calls are not supported" error with a 400 status code. Cause: The call mode of the target model is not adapted. FastGPT agent streaming request settings are incompatible with models that only support streaming calls such as Qwen3, leading to call failure.
- Symptom: The model response does not reference associated knowledge base content, and displays "No specific knowledge base content provided". Cause: The `maxContext` value is too small. Knowledge base fragments are truncated and cannot be read by the model, or the knowledge base source corresponding to cluster change tickets and fault reports is not correctly associated.
- Symptom: The cluster logs recalled by the model contain a large amount of irrelevant content, and filtering does not work as expected. Cause: The access level of the rerank model is not clearly defined. The filtering logic is not executed after recall, which affects troubleshooting efficiency.

## How to Confirm Configuration is Complete
- In the test workspace of FastGPT v4.17.0, send a simulated request for "query the abnormal status of Pods in a specified namespace". Check whether the returned result includes tool call records to confirm that the `toolChoice` configuration takes effect.
- View the reference markers in the model response. Confirm whether original fragments of cluster change tickets in the knowledge base are included, to verify that the `quoteMaxToken` configuration is reasonable.
- Send a simulated non-streaming call request. Check whether the "Non-streaming calls are not supported" error is returned, to confirm that the streaming settings for model integration are compatible with the target model.
- Check whether non-empty `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are configured in the environment variables deployed by the App/Admin server. Confirm that service startup verification passes. Verify the network connectivity of the AI Proxy service.

The values provided here are common starting points. They should be evaluated against the reader's own samples.
