# Test Cases and Defect Analysis for Object Storage and Backup Services: Tool Calling and Plugins

## What Data for This Category Looks Like
Data for this category primarily originates from object storage consoles, backup systems, access logs, and customer policy tables. Update frequency is daily, or real-time when storage policies or backup rules are modified. Daily operation and analysis documents include storage bucket configuration details, backup execution policies, recovery operation records, object lifecycle rules, and more. Fields cover storage bucket unique identifiers, backup task status, recovery time consumption, permission policy configuration items, and other standard storage-related fields. No additional statistical quantitative annotations are included.

## Constraints Imposed by These Characteristics on Tool Calling and Plugins
Data for this category is distributed across multiple systems. Tool calling requires configuring cross-system permission verification rules to prevent unauthorized access to storage or backup data. Data update rhythms are inconsistent, so plugins must support on-demand pulling of the latest policies and logs, without relying on fixed-cycle synchronization. Daily document fields are familiar to operations personnel as standard storage-related fields. Tool calling parameters must strictly match preset fields such as storage bucket ID and backup task status to avoid analysis failures caused by mapping errors. Data anomalies may lead to data leaks or backup failures, so tool call failure handling must include graded alarm logic for permission verification failures and abnormal task status.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` or specified as `["storage-backup"]` | Matches the exclusive tool set for object storage and backup services, avoiding calls to unrelated tools |
| `functionCall` | Enabled, with parameter verification threshold set to 90% | Ensures called function parameters strictly match storage bucket and backup task fields, reducing format error rates |
| Permission binding policy | Bind storage bucket-specific IAM roles | Complies with the requirement for strict permission control over data in this category, preventing unauthorized access to storage or backup data |
| Log pull duration | Last 24 hours | Matches the daily update frequency of data in this category, reducing invalid data pulls |
| Recovery task sampling interval | Every 7 days | Adapts to the execution cycle of conventional backup policies, covering full recovery sampling requirements |
| Plugin synchronization trigger condition | Triggered when storage policies change | Matches the real-time update characteristic of data in this category when policies change, ensuring data timeliness |

## Three Common Mistakes
- When calling a large model, using parameters consistent with the online API triggers an error. The cause is that the local large model has stricter format requirements for the `functionCall` parameter and does not adapt to the nested structure of object storage fields.
- When calling a plugin via API, file type variables cannot be passed. The cause is that the plugin's file upload permission is not configured, and the file upload interface fields of the object storage service are not matched.
- The number of tool call return results is abnormal. The cause is that no filtering rule is set for `toolChoice`, resulting in calls to backup or storage tools beyond the scope, returning irrelevant data.

## How to Verify Successful Configuration
- Execute a test call, check if return results include category-specific fields such as storage bucket configuration and backup task status, to confirm the tool call range is correct.
- Simulate a permission exception scenario, verify whether the tool call triggers a permission verification failure alarm, to confirm that the permission binding configuration takes effect.
- Modify a storage policy, check whether the plugin automatically pulls updated policy data, to confirm that the synchronization trigger logic is working properly.
- Upload a test file to the specified storage bucket, verify whether the plugin can correctly identify the file type and complete parameter transfer, to confirm that the file upload configuration takes effect.
