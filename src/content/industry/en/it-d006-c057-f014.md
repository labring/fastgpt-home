# Test Cases and Defect Analysis for Ticket Handling and Issue Tiering: Model Integration and Configuration

## What the Data for This Category Looks Like
Core data for this category originates from ticketing systems, chat logs, product logs, and customer contract SLAs. Update frequency is daily or real-time. Regularly maintained documents include customer tickets, issue tiering tables, processing records, and service reports. Ticket documents contain ticket ID, customer identifier, problem description, submission time, and associated product fields. Issue tiering tables contain tiering tags, response time limits, and responsible team mappings. Processing records contain flow nodes, processors, and time consumption data. All data exists as a mix of unstructured text and structured fields, with no unified fixed format template.

## How These Data Characteristics Impact Model Integration and Configuration
The data characteristics of this category create multiple constraints for model integration and configuration. First, real-time ticket and chat record updates require model interfaces to support low-latency responses. Total context and output token usage must be limited. Second, mixed multi-source data structures require models to accept combined input of unstructured problem descriptions and structured fields. The context length parameter must be configured appropriately. Third, accurate classification results are required for issue tiering and SLA compliance judgments. Adjust the model’s randomness parameter to ensure consistent output. Fourth, field matching for customer contract SLAs requires models to recognize structured field value rules. Fix the trigger logic for tool calls.

## How to Set Configurations
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the average context length of tickets and chat records, avoids overflow |
| `maxTokens` | 2000–3000 token | Covers the full output requirements for issue tiering and responsibility assignment |
| `temperature` | 0.2–0.4 | Ensures output stability for issue tiering and SLA judgments, reduces random fluctuations |
| `AIPROXY_API_ENDPOINT` | `http://localhost:8000` (local deployment scenario) | Root address of the AI Proxy service, do not add path suffixes such as `/v1` |
| `AIPROXY_API_TOKEN` | Non-empty administrator token consistent with the AI Proxy server configuration | Ensures the security of AI Proxy service calls |
| `toolChoice` | auto | Automatically determines whether to call tools for ticket flow or SLA verification |

## Three Common Configuration Mistakes
- Context overflow error returned by the interface, status code 413. Cause: The `maxContext` value is not adjusted based on the average context length of tickets and chat records, resulting in input tokens exceeding the model limit.
- Frequent jumping in the model selection dropdown box, abnormal model list refresh when adding a new channel. Troubleshooting: The `AIPROXY_API_ENDPOINT` or `AIPROXY_API_TOKEN` server environment variables are not configured correctly. This may cause service startup verification failure or inability to connect to the AI Proxy service, triggering interface status abnormalities.
- Unable to access local models via custom protocols, no custom option for protocol type when adding a new channel. Troubleshooting: The protocol and address of the upstream model are not correctly configured in the model channel settings. `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are App/Admin server environment variables and do not need to be filled in the channel configuration.

## How to Verify a Successful Configuration
- Submit a test ticket containing preset problem descriptions and structured fields. Check whether the issue tiering result output by the model matches the preset tiering table.
- View FastGPT interface call logs. Confirm that the actual call values of `maxContext` and `maxTokens` match the configured values.
- Verify that the App/Admin server has correctly configured the `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` environment variables. The service can normally obtain model responses through AI Proxy.
- Simulate a ticket scenario containing SLA time limits. Confirm that the model can correctly identify and associate the corresponding responsible team and processing requirements.

The values provided are common starting points and should be evaluated using samples from the relevant deployment context.
