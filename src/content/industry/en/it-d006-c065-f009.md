# Test Cases and Defect Analysis for Interface Integration and Data Docking: Tool Calling and Plugins

## What the data for this category looks like
Core data for this category typically comes from client system interfaces, API documentation, test data, and integration debug logs. Update frequency is usually daily or per phase delivery milestone. Daily maintained documents include interface lists, integration records, field mapping tables, and issue tracking tables. Interface lists contain request URLs, methods, parameter names, return fields, and business definitions. Field mapping tables must mark business meanings and data units. Integration logs record request parameters, response statuses, and latency for each call. The volume of data returned by interfaces usually does not exceed 1000 entries.

## What constraints these characteristics impose on the tool calling and plugins link
Because data sources are scattered and update frequency is high, tool calling must support dynamically pulling the latest interface documentation and field mapping rules to avoid parameter errors caused by expired configurations. The requirement for multi-field mapping means plugins must have flexible parameter binding capabilities, supporting custom parameter mapping rules. The retention of integration logs and issue tracking data requires that the tool calling chain fully records request and response details to facilitate subsequent defect troubleshooting. At the same time, interface call errors may trigger business interruptions, so strict parameter verification and exception capture logic must be configured.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `"auto"` | Adapts to dynamically changing interface parameters, automatically selecting matching tools |
| `functionCall` | `"strict"` | Enforces verification of interface parameter formats to avoid call failures caused by format errors |
| Timeout retry count | `2–3 times` | Balances call success rate and resource consumption, reducing invalid repeated requests |
| Single interface call timeout | `600 seconds` | Adapts to response durations of complex business interfaces, avoiding premature termination of valid calls |
| Single interface return data limit | `1000 entries` | Adapts to interface return limits of most client systems, avoiding data truncation |
| Interface parameter mapping rules | Bind one by one according to the field mapping table | Ensures consistency between business definitions and field units, eliminating mapping deviations |
| Log synchronization switch | Enabled | Fully retains call chain data to facilitate subsequent defect analysis and troubleshooting |

## Three common mistakes
- When calling a global variable application, return fields are empty. The symptom is that the target business field is missing in the interface response. The cause is that parameters are not bound according to the field mapping table, and hard-coded values are passed directly without matching the actual field naming rules of the client system.
- Tool calling fails when a team application is called as a plugin. The symptom is that the interface displays "no tool calling permission" or returns a 403 status code. The cause is that permissions related to tool calling are not enabled in the plugin configuration, adapting to the plugin permission change logic of FastGPT v4.17.0.
- The CSV file collection creation result does not match the data previewed in the interface. The symptom is that the number of file rows returned by the interface does not match the number of entries shown in the interface preview. The cause is that the correct file encoding parameter was not specified when calling the interface, leading to abnormal parsing of some special characters.

## How to confirm configurations are correctly set
- Initiate a simulated interface call, compare the response result with the field mapping table, and confirm that the values of all bound business fields are correct.
- View the tool calling log, check that the `functionCall` parameter format meets the requirements of the target interface, and there are no format verification errors.
- Trigger an exception scenario such as timeout or parameter error, and confirm that the exception capture logic triggers normally and complete logs are recorded.
- Cross-check the integration records and tool calling logs, and confirm that the request parameters, response statuses, and latency of each call are fully retained.
