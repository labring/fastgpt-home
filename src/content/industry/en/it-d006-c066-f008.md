# Test Cases and Defect Analysis for Search Ad Keyword Management: Workflow Orchestration

## What the data for this category looks like
Daily documents for this category include keyword lists, negative keyword tables, bid records, and search term reports. Keyword lists contain matching type, delivery bid, and regional restriction fields. Negative keyword tables include matching pattern and effective time period information.

Data is primarily sourced from search ad backends, search term reports, bidding ranking data, and landing page statistics tools. Data is pulled daily or weekly. Data fields are numerous and closely linked. Processing must be split by ad account to avoid mixing cross-account data.

## What constraints these characteristics impose on workflow orchestration
Dispersed data sources and the requirement to split processing by account mean workflows must support connecting multiple data source nodes and permission isolation.

Daily or weekly update rhythms require workflows to include scheduled trigger mechanisms, to avoid repeatedly pulling invalid data.

Keyword expansion and negative keyword screening are the most time-consuming steps. Workflows must support batch nodes and concurrent execution.

Data errors can cause issues including invalid clicks and brand term hijacking. Workflows must include failure retry and exception alert nodes.

Additionally, document fields are numerous and have fixed formats. Parameter passing must be used to transfer field values for different documents, to adapt to configuration differences across ad accounts.

## Configuration Recommendations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Scheduled trigger cycle | Daily 0:00 / Weekly Monday 2:00 | Matches the daily or weekly update rhythm of search ad data, avoids repeatedly pulling old data |
| Batch node concurrency count | 5–10 concurrent | Adapts to ad platform API call limits, avoids triggering API rate limiting |
| Context call scope | Bind the current node's `variables` | Isolates keyword data across different ad accounts, prevents context contamination |
| Node failure retry count | 2 retries, 60-second interval | Addresses temporary API fluctuations from ad platforms, reduces the probability of single task failure |
| Node timeout threshold | 300 seconds | Adapts to the time required for batch keyword processing, avoids premature task termination |
| Account node filtering | Bind the target account's `nodeId` | Accurately locates workflow tasks for the corresponding ad account, avoids cross-account interference |

## Three Common Configuration Mistakes
- Phenomenon: Large model nodes return a 500 Gateway forwarding error status code, with a prompt that the service is disconnected. Cause: No context isolation rules are configured. Mixing keyword data across ad accounts causes service exceptions.
- Phenomenon: Batch running nodes takes far longer than expected, and the task triggers a timeout alert. Cause: Concurrent execution configuration for batch nodes is not enabled. A large number of keyword tasks are processed in serial mode.
- Phenomenon: Workflow node icons do not display, and a network error prompt pops up when uploading a keyword list. Cause: Local storage permission configuration is not completed in FastGPT v4.17.0, or network proxy settings are abnormal.

## How to Verify Correct Configuration
- View the workflow trigger configuration panel, confirm that the scheduled trigger time matches the ad data update frequency.
- Run batch nodes, then check execution logs to confirm that nodes execute tasks in concurrent mode.
- Check node context configuration, confirm that only the current workflow node's `variables` parameter is bound.
- Upload a test keyword list, confirm that there are no network error prompts during file upload, and node icons display normally.
