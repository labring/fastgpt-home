# Test Case and Defect Analysis for Database Cloud Service Operations: Forms and Interactions

## What the data for this category looks like
Usually, core data for database cloud service operations comes from cloud database consoles, slow logs, monitoring metrics, and ticketing systems. Daily produced documents include instance change orders, backup and recovery records, performance diagnosis reports, and parameter adjustment records. Each document contains fields such as instance ID, change time, operator, risk level, and more. Units are mostly seconds, count, and MB. Data update frequency is usually daily synchronization or triggered by single operation and maintenance changes. The most time-consuming links such as slow SQL locating and backup and recovery drills rely on multi-source data aggregation.

## What constraints these characteristics impose on forms and interactions
Multi-source data sources require cross-console, log, and ticketing field linkage via external systems or subsequent workflows to avoid duplicate entry. The FastGPT form node only collects input information.
According to the update frequency triggered by changes, timestamps and instance status fields of forms need to be automatically synchronized with data sources via external systems or subsequent workflows, without manual filling. The FastGPT form node only collects input information.
Different types of operation and maintenance documents correspond to differentiated form fields. Form templates need to be switched on demand via external systems or subsequent workflows. The FastGPT form node only collects input information.
Multi-tenant service boundaries require data isolation by tenant via external systems or subsequent workflows, ensuring that different operation and maintenance teams can only access form and associated data for corresponding instances. The FastGPT form node only collects input information.
At the same time, time-consuming links such as slow SQL locating need to mount custom analysis tools via external systems or subsequent workflows to adapt to complex operation and maintenance logic. The FastGPT form node only collects input information.

## Three common configuration mistakes
- When dynamically specifying a knowledge base, the reference variable drop-down box is empty. Verification steps: Check whether the `formInput` node variable is correctly associated with the knowledge base configuration, and confirm that the external system has configured variable application permissions.
- There is no connection entry for the code running option in the tool call node. Verification steps: Check the external system code running tool permission configuration, and confirm whether it adapts to the cloud database operation and maintenance custom script scenario.
- Knowledge base query results are delayed, and the same question needs to be entered twice to return results. Verification steps: Check the external system cache verification rule configuration, and confirm whether the slow log data source synchronization frequency matches the query rhythm.

## How to verify a successful configuration
- Submit a test instance change order, and verify whether the external system synchronizes cloud console instance information and status to the input content collected by the `formInput` node.
- Trigger the external code running tool, and verify that it can read the slow log data source and generate expected analysis results.
- Check the dynamic knowledge base specification function, and confirm that the external system can display the knowledge base options corresponding to the instance associated with the `formInput` node.
- Switch different tenant accounts, verify that the external system only displays instance forms and associated data of the corresponding tenant, and the `formInput` node only collects input content allowed by the current tenant.
