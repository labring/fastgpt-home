# Test Case and Defect Analysis for Data Cleaning and Quality Inspection: Workflow Orchestration

## What this category of data looks like
Data sources for this category include raw datasets awaiting cleaning, ETL operation logs, annotation results produced by annotation platforms, and sampling results from the quality inspection stage. Data updates occur daily or per batch task cycle. Daily associated documents include cleaning rule configuration files, quality inspection sampling statistics tables, abnormal data lists, and final delivered quality reports. Data fields cover original data fields, cleaning tags, exception types, sampling verification results, and other related fields. There are no mandatory additional unit fields.

## What constraints these characteristics impose on the "workflow orchestration" link
Multiple data sources and inconsistent update cycles require the workflow to support dynamic configuration of multi-data source pull nodes, and adapt to daily update or batch processing trigger rhythms. Daily documents rely on multi-stage data flow, so the workflow must connect cleaning rule nodes, quality inspection sampling nodes, and abnormal data summary nodes to ensure traceability of documents across each stage. The generation of abnormal data lists and delivery reports depends on the output of preceding nodes, requiring unified data transfer formats between workflow nodes. Different subjects have different operation permissions, so the workflow must configure permission verification links for nodes to match the operation scopes of data engineers, quality inspectors, and project managers.

## How to set configurations
The following configurations are formulated based on the workflow orchestration interface of FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | Per batch processing cycle / Triggered by ETL log updates | Matches the daily update or per-batch update frequency of data |
| `variables` | Pass cleaning rule ID, sampling verification threshold | Transmits core business parameters for data cleaning and quality inspection |
| `nodeId` | Bind unique identifiers for each stage node | Ensures accurate and error-free data flow between workflow nodes |
| Single Processing Limit | 10000 entries | Adapts to the conventional scale of a single batch of raw datasets |
| Timeout Threshold | 600 seconds | References the average processing duration of ETL logs |
| Abnormal Data Storage Path | Calibrated based on actual testing | Adapts to the abnormal data storage requirements of different businesses |

## Three Common Misconfigurations
- Phenomenon: Delivered report fields are missing after the workflow runs. Cause: The statistical field mapping required for the report is not configured in `variables`, resulting in incomplete data transfer between nodes.
- Phenomenon: The agent node reports an error "associated node not found" during operation. Cause: `nodeId` is not correctly bound to the preceding cleaning rule node, resulting in the workflow being unable to trace the data source.
- Phenomenon: Abnormal data tags are not corrected after the problem optimization component is executed. Cause: The problem optimization component is placed before the data cleaning node, and raw data format standardization is not completed first.

## How to Confirm Proper Configuration
- Verify the workflow's trigger configuration to ensure it matches the data update frequency. Use test triggers to validate the execution rhythm.
- Check the configuration of `variables` and `nodeId` to confirm that all business parameters and node identifiers have been correctly bound.
- Run a single-batch test task and verify that the output data from each stage matches the format of daily documents.
- View the workflow operation logs to confirm there are no timeout or parameter missing errors, and that the abnormal data storage path is accessible normally.

The values provided here are common starting points and should be measured against the reader's own samples.
