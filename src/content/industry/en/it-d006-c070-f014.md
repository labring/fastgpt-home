# Test Cases and Defect Analysis for Data Cleaning and Quality Inspection: Model Integration and Configuration

## What data in this category looks like
Data processed in this category originates from raw datasets, ETL operation logs, annotation platform output results, and sampling quality inspection results. Data update frequency is daily or batch execution. Daily associated documents include cleaning rule configuration files, quality inspection sampling record forms, abnormal data lists, and delivery reports. Data fields include raw data content, ETL processing tags, annotation labels, sampling verification results, etc. There are no unified fixed units, and adjustments are made according to the format of the original business data.

## What constraints do these characteristics impose on model integration and configuration
The scale of raw datasets fluctuates greatly, so model context parameters that adapt to different data volumes must be configured. Data updated in batches or daily requires model integration to support scheduled triggering or batch task binding. The validity of server environment variables `AIPROXY_API_ENDPOINT` (AI Proxy service root address) and `AIPROXY_API_TOKEN` (AI Proxy administrator Token, must be consistent with the AI Proxy server configuration and non-empty) must be confirmed to adapt to batch requests. The abnormal data list includes unstructured text and numerical abnormal items, so `temperature` must be configured to adapt to different types of abnormal identification requirements. ETL logs include time-series operation records, so the model must support context-related analysis, and `maxTokens` must be limited to avoid request timeouts caused by overly long logs. At the same time, the structured fields in the quality inspection sampling form require the model to accurately match field mappings, and the field format of model input and output must be defined in advance.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapt to batch context association analysis requirements of ETL logs and raw datasets, avoid truncation of key business-related information |
| `maxTokens` | 4000 token | Limit the output length of single-batch abnormal data identification, adapt to the daily/batch task processing rhythm |
| `temperature` | 0.2–0.6 | Balance the accuracy and flexibility of abnormal value identification, adapt to the verification scenarios of cleaning rules and sampling results |
| `quoteMaxToken` | 2000 token | Limit the length of referenced cleaning rule documents, avoid exceeding the model input context limit |
| `AIPROXY_API_ENDPOINT` | Fill in the AI Proxy service root address, for example `http://aiproxy:3000`, do not append `/v1` or model-related path suffixes | Required environment variable for the App/Admin server, ensure correct model request routing and avoid connection failures |
| `toolChoice` | auto | Allow the model to automatically select appropriate tools to handle tasks such as duplicate data identification and abnormal value classification |

## Three common configuration errors
- Phenomenon: The configured and enabled model cannot be found in the workflow, and the interface returns 404 or 500 status codes. Cause: The server does not configure the required environment variables `AIPROXY_API_ENDPOINT` (AI Proxy service root address) or `AIPROXY_API_TOKEN` (AI Proxy administrator Token, must be consistent with the AI Proxy server configuration and non-empty), resulting in startup verification failure, or the channel configuration does not bind the mapping relationship of the corresponding model.
- Phenomenon: Request timeout errors occur during batch data processing. Cause: `maxContext` or `maxTokens` is set too large, exceeding the single request limit of the model interface.
- Phenomenon: The abnormal data identification result deviates greatly from the actual sampling verification result. Cause: `temperature` is set too high, causing the verification logic generated by the model to deviate from the preset cleaning rules.

## How to verify a correct configuration
- Check that the server environment variables `AIPROXY_API_ENDPOINT` (AI Proxy service root address) and `AIPROXY_API_TOKEN` (AI Proxy administrator Token, must be consistent with the AI Proxy server configuration and non-empty) match the deployment environment.
- Initiate a small-batch test request to confirm that the interface returns a 200 status code with no abnormal errors.
- Bind the configured model in the test case, run a single abnormal data verification task, and confirm that the output result aligns with the expected cleaning rule logic.
- Check the FastGPT v4.17.0 system logs to confirm that there are no authentication or routing errors in model access requests.

The values given are common starting points and should be measured against the reader's own samples.
