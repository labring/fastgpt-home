# Test Cases and Defect Analysis for Data Desensitization Processing: Tool Calling and Plugins

## What Data for This Category Looks Like
Data for this category originates primarily from business databases, system data dictionaries, self-developed desensitization tools, and access approval systems. Update frequency is adjusted per project batch or individual task. Core regularly produced documents include desensitization plans, sensitive field mapping tables, desensitization verification reports, and access approval records. Fields include sensitive type identifiers, desensitization rule codes, verification thresholds, and approval statuses. No fixed universal units exist; corresponding field definitions must be matched to project scenarios.

## What Constraints Do These Characteristics Impose on Tool Calling and Plugins
Data sources are scattered and updated dynamically per project. Tool calling must support multi-source data pull adaptation to avoid hard-coded fixed data sources. Document structure varies per project. Plugins must support dynamic parsing of field mapping tables and verification reports, and cannot rely on fixed templates. Sensitive field identification and verification take significant time. Tool calling must include built-in batch processing capabilities to shorten verification cycles. Access approval records must be verified synchronously with the desensitization process. Tool calling must interface with approval system status APIs to prevent unauthorized desensitized data from entering testing workflows.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapt to multiple types of desensitization tool calling scenarios, automatically match corresponding functions |
| `functionCall` | `[{"name":"batch_desensitize","parameters":{"count":"200 entries"}}]` | Match the processing rhythm of batch desensitization tasks, avoid performance loss from single-item calls |
| Tool call timeout threshold | 600 seconds | Cover multi-source data pull and desensitization verification time for complex projects |
| Sensitive field matching threshold | 0.75–0.85 | Based on semantic similarity of business fields, balance recognition accuracy and false positive rate |
| Approval status verification switch | Enabled | Interface with access approval systems, ensure only approved desensitization tasks are executed |

## Three Common Mistakes
- When calling desensitization tools, returned content fails to hide sensitive approval record fields as required. The cause is that output filtering rules are not configured in the `functionCall` parameter, resulting in sensitive approval information being returned.
- Tool calling times out and returns a 504 status code. The cause is that the tool call timeout threshold is not adjusted, and multi-source data pull time for complex projects exceeds the default limit.
- Desensitization verification results are not output as expected. The cause is that the sensitive field matching threshold is not customized, and using default configurations leads to misidentification or missed identification of high-risk sensitive fields.

## How to Verify Proper Configuration
- Initiate a single small-batch desensitization test, check if the `functionCall` result returned by tool calling includes correct desensitized fields.
- Interface with the access approval system API, verify that tool calling automatically checks approval status, and tasks that have not passed approval cannot trigger execution.
- Adjust the sensitive field matching threshold, compare recognition results across different thresholds, confirm that recognition accuracy matches business scenarios.
- Simulate a timeout scenario, verify that the tool call timeout threshold configuration takes effect, and whether corresponding processing logic is triggered after timeout.

The values listed above are common starting points and should be evaluated against the reader's own samples.
