# Test Cases and Defect Analysis for Data Collection Task Design: Tool Calling and Plugins

## What this category of data looks like
This data is generated across the full lifecycle of data collection projects. Sources include clear customer requirements, publicly available data sources, self-developed or third-party collection tools, and internally accumulated sample libraries. Daily deliverables include collection plans, sample specification descriptions, data authorization agreements, and task schedules. Fields cover sample scope, collection fields, compliance check items, execution nodes, and other relevant items. Data updates follow individual project cycles, or adjust collection rules via weekly syncs. Adjustments are made dynamically based on project implementation progress.

## What constraints these characteristics impose on the tool calling and plugins link
Tool calling for data collection task design must adapt to validation requirements for multi-source data. Customer requirements and public data sources from different origins have significant format differences, so plugins must support multi-format parsing. The high time cost of defining sample scope requires tool calling to perform batch validation of sample boundaries, to avoid exceeding compliance limits. The collection legitimacy check relies on real-time authorization status. Tools must connect to compliance databases to pull the latest authorization information. Data updates within a single project cycle require plugins to support dynamic adjustment of collection parameters, to adapt to weekly iterative task schedules. This category of data is directly tied to project rework risk. Tool calling stability directly affects raw data availability. Tool calling must strictly match collection field specifications to avoid missing fields or format errors.

## Configuration Settings
The following configurations are compatible with FastGPT v4.17.0 tool calling and plugin logic:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Compatible with FastGPT v4.17.0 tool calling workflows, adapts to dynamic tool calling requirements for multi-source data, and matches the varied validation and retrieval scenarios in collection tasks |
| `functionCall` | Enabled | Supports structured output of collection field validation results, to facilitate subsequent sample specification matching |
| Tool calling toggle | Configured per project | Enables tool linkage on demand to meet compliance validation requirements for individual collection tasks |
| Historical conversation retention rounds | 1–3 rounds | Adapts to field confirmation needs for single sessions in collection tasks, and avoids redundant context |
| Model call timeout | 300–600 seconds | Adapts to the time cost of multi-step validation in collection tasks, and prevents task interruption due to timeout |
| Thinking content output toggle | Enabled | Facilitates troubleshooting of intermediate tool calling logic, and locates deviations in sample scope definition |

## Three Common Configuration Mistakes
- Symptom: The thinking content output toggle is enabled for the tool calling component, but no thinking step output appears in execution logs. Cause: The context transfer link for tool calling is not correctly bound, so thinking content is not included in the output queue.
- Symptom: When configuring multiple model calling nodes, different nodes set different historical conversation retention rounds. Historical records are not reused as expected when accessing the same ID multiple times. Cause: Global session ID historical storage rules are not uniformly configured. Independent context maintenance by each node causes conflicts.
- Symptom: After enabling the tool calling toggle for a locally deployed open-source model, no tool calling action is triggered. Cause: The tool calling adaptation package for the local model is not loaded correctly, or the model itself has not completed local deployment adaptation for tool calling capabilities.

## How to Verify Correct Configuration
- Run a single collection task validation, check if the tool calling return results include sample scope and field specification validation information, to confirm that the tool calling logic is active.
- Check task execution logs. Confirm that intermediate reasoning step logs are generated normally after the thinking content output toggle is enabled.
- Simulate multiple accesses with the same ID, check if historical conversations are correctly loaded and reused according to the configured retention rounds.
- Trigger an exception scenario, such as a request exceeding the preset sample scope, confirm that the tool calling correctly triggers a compliance validation prompt.

The values provided are common starting points and should be evaluated against the reader's own samples.
