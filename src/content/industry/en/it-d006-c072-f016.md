# Test Cases and Defect Analysis for Data Collection Task Design: Forms and Interactions

## What Data for This Category Looks Like
Data for this category is generated across the full workflow of data collection tasks. Sources include clear client collection requirements, publicly compliant data sources, intermediate outputs from self-developed collection tools, and industry public sample libraries. Daily associated documents include collection plans, sample specification documents, data authorization agreements, and task execution schedules.
Data update rhythm follows individual project cycles or weekly units, and is updated alongside adjustments to collection scope and field requirement changes.
Core fields cover collection sample scope, field format requirements, validity check rules, and task execution node configuration. No unified fixed unit exists; match corresponding standards based on collection scenarios.

## Constraints Imposed on Forms and Interactions by These Characteristics
Form interactions for collection task design must adapt to multi-role collaboration needs. Data service project managers configure collection scope. Collection teams confirm field specifications. Client algorithm teams validate validity. External business systems implement role permission configuration. Form nodes only collect input information for corresponding roles.
Data sources are diverse. External business systems provide data source type selection entry, covering public data sources, local sample libraries, custom uploads, and other options.
High update frequency requires external business systems to support incremental editing and version rollback functions, avoiding repeated configuration.
Ambiguity often occurs during sample scope and field specification confirmation. External business systems add real-time check and compliance preview links to reduce ambiguity and lower later rework risks.

## Three Common Configuration Mistakes
- Phenomenon: When the front-end submits a collection task, the input content of the `formInput` field does not match the check result during workflow debugging. Verification action: Check the check trigger configuration of the external business system, confirm whether checks are only executed during submission, and front-end input is not synchronized to the workflow context.
- Phenomenon: When configuring data source selection, there are no selectable values for data source options. Verification action: Check the data source authorization and access permission configuration of the external business system, confirm whether the configuration of corresponding data sources is complete.
- Phenomenon: Subsequent nodes do not receive complete fields after a data collection task design form is submitted. Verification action: Compare required fields, actual submitted content, and node output mapping one by one, then check subsequent interface returns; existing symptoms cannot independently determine the root cause.

## How to Confirm Proper Configuration
- Verify the check rules of the `formInput` field, confirm they fully match the field specifications in the collection plan; check logic is implemented by the external business system.
- Test the `userSelect` user selection configuration, confirm the external business system has configured corresponding role permissions, and nodes only pass user selection results.
- Trigger validity checks, confirm the external business system has configured check trigger logic, and can pop corresponding compliance prompts within 10 seconds after field editing is completed.
- Test the version rollback function, confirm the external business system has configured the version rollback function, and can view configuration change records from the past 7 days.
