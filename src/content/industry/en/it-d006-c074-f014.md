# Test Cases and Defect Analysis for Text Annotation Projects: Model Access and Configuration

## What Data for This Category Looks Like
The data for text annotation projects primarily comes from corpora provided by clients, annotation results produced by in-house annotation platforms, industry-standard vocabularies, and quality inspection sampling results. Daily associated documents include annotation specifications, sample packages, quality inspection reports, and issue feedback forms. Data updates follow a daily or annotation batch schedule. Each batch of data includes text to be annotated, corresponding tag systems, annotation result fields, and quality inspection markers. Core fields focus on semantic entities, intent classification, and tag matching, with no additional complex unit requirements.

## Constraints Imposed on Model Access and Configuration
Decentralized data sources and frequent updates require model access to support batch adaptation for multi-source data, and configuration items must reserve data format validation rules. Most daily documents are unstructured text, so model configuration must optimize parameters for semantic boundary, entity recognition, and intent classification scenarios. Quality inspection sampling results serve as feedback basis, so model testing must support importing test cases by sampling batch, and configuration must associate field mapping logic for quality inspection reports. Single-batch data volume fluctuates with annotation progress, so dynamically adaptable context length parameters must be configured to avoid call failures or resource waste caused by data volume changes.

## How to Set Configurations
The following configurations are based on FastGPT v4.17.0, adapted for the test case and defect analysis scenario of text annotation projects:

| Configuration Item | Recommended Value Range | Rationale |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | Adapts to the batch sample package length of text annotation projects, avoiding call interruptions caused by context overflow |
| `maxTokens` | 2000–3000 token | Matches the semantic analysis requirements of a single annotation text, covering the output length for tag interpretation and entity recognition |
| `temperature` | 0.2–0.4 | Reduces random generation probability, ensures consistency of tag matching and semantic judgment, and meets the unified requirements of annotation specifications |
| `quoteMaxToken` | 1500 token | Limits the length of quoted quality inspection report content, avoiding redundant information interfering with test case analysis |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, for example http://aiproxy:3000. Do not append /v1 or /chat/completions paths; this is not a single-model address | This variable is a required environment variable for the App/Admin server. It must match the AI Proxy server configuration and cannot be empty |
| `toolChoice` | auto | Supports automatic tool calling to handle field mapping of quality inspection sampling results, improving test case generation efficiency |

## Three Common Misconfigurations
- A 404 error occurs when adding a model test. The log displays Api response error: /api/core/ai/model/test?model=xxx. Troubleshooting steps include: checking whether the model ID matches the identifier configured on the third-party platform, and whether it complies with the model naming rules of the corresponding provider.
- The model returns empty or incomplete results after being called. Troubleshooting steps include: checking whether the `maxTokens` value is too small to cover the complete output length required for tag interpretation and entity recognition, and whether results are forcibly truncated and discarded.
- The chat dialog box cannot switch between configured AI models. Troubleshooting steps include: checking whether multi-model availability permission is enabled in the model configuration, and whether the target model is added to the available model list.

## How to Confirm Configuration Completion
Access the FastGPT model provider page, select the configured target model, and run a test call. A successful call returns a 200 status code with no error messages.
Import a batch of annotation sample packages as test cases, run a model call to generate tag matching results, and verify that output fields match the requirements of annotation specifications.
Switch between multiple configured available models, confirm that the chat dialog box can normally load and switch the call results of different models.
View the model call logs, confirm that the actual values of configuration parameters such as `maxContext` and `maxTokens` match the preset values, with no abnormal overflow or tampering.

The values provided here are common starting points, and should be evaluated against samples corresponding to the actual deployment scenario.
