# Test Cases and Defect Analysis for Documentation Site Maintenance: Tool Calling and Plugins

## What data for this category looks like
Data for this category comes primarily from code repository commit records, documentation site build logs, end-user feedback, and version release records.
Daily maintenance documents include installation guides, API interface documents, version migration manuals, and frequently asked questions.
Data updates follow weekly or single version release cycles.
Individual document fields include dependency versions, interface paths, sample code, deprecation tags, and other fields.
There are no unified fixed unit constraints. Content structures vary based on document type.

## What constraints these characteristics impose on tool calling and plugins
Data characteristics of this category impose multi-dimensional constraints on tool calling and plugin configuration.
Data sources include code repositories and build logs.
Tool calling must pull code changes and parse build error messages.
This requires configuring access permissions for target code repositories and log parsing rules.
Document types vary widely.
Parsing logic differs across document types.
Tool calling must support switching processing workflows based on document type.
A specified parameter must trigger the corresponding processing logic.
Data update cycles are fixed.
Tool triggering must align with weekly or version release cycles to avoid excessive resource consumption from overuse.
Unstructured end-user feedback data requires plugins to complete defect classification and localization.
Corresponding model calling parameters must be configured.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | Adapts to tool calling requirements across different document types, allowing the model to independently select the plugin matching the current task |
| `functionCall` | Specify function identifiers by document type | Enforce calls to corresponding parsing plugins for different scenarios such as API documents and installation guides |
| Tool call timeout | 600 seconds | Aligns with the parsing cycle of documentation site build logs, preventing task interruptions caused by overly long log loading times |
| Plugin trigger threshold | Top 3 matching results | Filters low-relevance document data to focus on core maintenance content |
| Context window size | 8000 token | Matches the average length of individual documents, ensuring complete access to document content during parsing |
| FastGPT version | FastGPT v4.17.0 | This version fixes cross-domain and parameter passing issues for tool calling, and is compatible with current configuration requirements |

## Three common mistakes
- Symptom: An error stating the model does not support the specified parameter is returned during tool calling, with a status code of 400. Cause: A model suited for documentation site maintenance workflows is not selected. A model that only supports basic conversation is used incorrectly.
- Symptom: A cross-domain interception prompt is returned when a third party calls the tool API, and document data cannot be pulled normally. Cause: A cross-domain whitelist for corresponding third-party calls is not added in the FastGPT configuration. External calling requirements for documentation site maintenance are not addressed.
- Symptom: The workflow calls the document parsing plugin and returns an empty result, with no code repository change records obtained. Cause: Access permissions for the code repository are not configured. This prevents the plugin from pulling corresponding data, and does not align with the data source characteristics of this category.

## How to confirm correct configuration
- Trigger a tool call, check if the returned results include parsed content for the target document, and verify consistency with the actual document structure.
- Call the cross-domain test interface, confirm that third-party requests can access the tool API normally, with no interception prompts.
- View tool calling logs, confirm that the `toolChoice` or `functionCall` parameters are correctly passed, and that the model calls the matching plugin.
- Simulate the trigger process after a version release, confirm that the tool executes automatically according to the preset weekly or version cycle, with no abnormal interruptions.

The values provided are common starting points and should be measured against the reader's own samples.
