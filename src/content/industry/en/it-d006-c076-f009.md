# Test Case and Defect Analysis for Log Platform and Observability: Tool Calling and Plugins

## What the data for this category looks like
Data for this category primarily comes from logging systems, Trace platforms, Metrics systems, and application SDKs. Daily supporting documents include logging collection specifications, link tracing instructions, indicator dictionaries, and dashboard configuration records. Data is updated daily or as application versions are iterated. Data fields include timestamps, service identifiers, log levels, link IDs, indicator values and units, and more. Data formats and field naming differ across sources, so standardized processes are required to align them.

## What constraints these characteristics impose on the "tool calling and plugins" workflow
Dispersed data sources and inconsistent formats require `toolChoice` to support adaptive parsing for multiple data sources, and plugins to include built-in general field mapping rules.
Uncertain update frequencies require tool calling to support incremental pull configurations, to avoid excessive resource usage from full synchronization.
Dispersed supporting documents require plugins to link to official document entries for corresponding data sources, to facilitate reference to field definitions during calls.
Missing associated fields such as link IDs will cause troubleshooting to fail, so `functionCall` must enforce validation of the presence of associated fields.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | Auto mode | Adapt to dynamic parsing scenarios for multiple data sources |
| `functionCall` | Enforce link field validation | Ensure complete associated information required for troubleshooting |
| Plugin timeout threshold | 600 seconds | Cover the time required for full log pull and link association |
| Incremental sync interval | 1 day | Align with the daily update data synchronization rhythm |
| Single recall log count | Top 500 entries | Balance data loading speed and analysis accuracy |
| Single recall link count | Top 10 entries | Focus on core troubleshooting associated information |
| Data source mapping rules | Calibrated via actual testing | Adapt to differences in log field naming across environments |

## Three common configuration mistakes
- An error reporting empty fields occurs after configuring `functionCall`. The cause is failure to link field mapping rules for the corresponding data source, resulting in inability to extract key link IDs.
- An error occurs when adding a Doc2X plugin after deploying FastGPT v4.17.0. The cause is failure to fill in the correct API key and service address in the plugin configuration, or the dependent third-party service not starting normally.
- No response when clicking input after referencing a plugin in a workflow. The cause is failure to set a reasonable timeout threshold, resulting in plugin requests hanging for long periods without returning results.

## How to confirm successful configuration
- Trigger a plugin call, then check if the returned results include expected fields such as link IDs and service names, to verify that field parsing is working.
- Submit a test case, then check the plugin execution logs for error messages, to confirm that the timeout threshold and mapping rules are functioning normally.
- Compare the log data pulled by the plugin with log entries from the source system, to verify that the recall count and update frequency meet configuration requirements.
- Check if the document links associated with the plugin can properly jump to the official instructions for the corresponding data source, to confirm that the document linking configuration is correct.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
