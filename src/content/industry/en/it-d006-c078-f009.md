# Test Cases and Defect Analysis for Cabinet Rack Installation and Cabling: Tool Calling and Plugins

## Data Profile for This Category
Data for this category comes primarily from DCIM systems, asset management systems, network topology diagrams, and customer construction work orders. Daily produced documents include rack installation application forms, cabinet cabling diagrams, port label sheets, and construction records. Covered fields include rack unit number, cable specification, port identifier, construction time, and more.
Data updates occur per order or daily, synced in step with construction workflow progress. Incomplete rack installation and cabling task data remains in a pending update status. Completed task data is archived for retention.

## Constraints for Tool Calling and Plugins
Tool calling must support API response formats from different systems to accommodate multi-source data sources. For example, rack unit data returned by DCIM systems and device inventory formats from asset systems differ, so plugins must support custom field mapping.
Plugin triggers must be bound to construction task nodes to align with the per-order update rhythm, avoiding invalid data pulls.
Tools must support combined text parsing and image information extraction for scenarios mixing structured and visual documents, to meet cabling diagram rack verification needs.
Tool input parameters must strictly match fixed fields such as rack unit number and port identifier, as required by port label sheets. Failing to do so will cause calling failures.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | Auto | Adapts to multi-source heterogeneous data tool calling scenarios, no need to manually specify tool type |
| `functionCall` | Enabled | Supports converting structured data into analyzable text format, for field extraction from rack installation application forms and port label sheets |
| Single tool call timeout | 600–900 seconds | Matches the typical time range for cabinet rack installation and cabling construction, avoids mid-call interruptions |
| Tool return result limit | First 8 entries | Adapts to the volume of DCIM and asset system data associated with a single construction task, filters redundant information |
| Input parameter format validation | Enabled | Matches the fixed field rules of port label sheets, prevents calling failures caused by missing fields or format errors |
| Context window | 4000–8000 token | Accommodates parsed text from cabinet cabling diagrams, network topology diagrams, and construction records |

## Three Common Mistakes
- Phenomenon: Tool calling returns empty results, or the preset defect analysis logic fails to run multiple consecutive times. Cause: Plugin triggers are not bound to the construction task submission node, resulting in pulled data that does not match the current task.
- Phenomenon: Tool returned search results are in array<object> format and cannot be directly used for defect analysis. Cause: The `functionCall` configuration is not enabled, and structured data is not converted into a format that can be parsed into readable text.
- Phenomenon: When calling tool plugins, input parameters for port label sheets cannot be added, or returned cabling diagram information is incomplete. Cause: The input parameter format validation switch is not enabled, or fixed fields matching port identifiers and rack unit numbers are not specified, leading to incompatible input parameter formats.

## How to Verify Correct Configuration
- Submit a test construction task to trigger plugin calling, and verify if the tool returns DCIM and asset system data associated with the task.
- Input a test data set in array<object> format, and verify if the tool returns text content suitable for analysis.
- Add port numbers and rack unit numbers as input parameter variables, and confirm they can be saved and called normally.
- Review plugin calling logs, and confirm no timeout or format mismatch error messages are present.

The configuration values listed above are common starting points and should be evaluated against specific local samples.
