# Test Cases and Defect Analysis for Desktop Terminal Support: Tool Calling and Plugins

## Data for Desktop Terminal Support Scenarios
Data for desktop terminal support scenarios typically comes from terminal management platforms, asset systems, user trouble reporting channels, and software repositories. Daily generated documents include terminal trouble tickets, installation manifests, software installation records, and remote assistance records. Common fields include terminal serial number, fault type, processing duration, software version number, peripheral model, etc. Units include units, times, and days. Data update frequency is daily or per terminal request, with no fixed batch update cycle.

## Constraints Imposed on Tool Calling and Plugins Workflows
Dispersed data sources require plugins to support interfacing with APIs of multiple types of terminal management systems to pull data across sources. Flexible update frequencies require tool calling to support real-time or on-demand pulling of the latest terminal data, avoiding use of outdated installation or fault records. Diverse document structures require plugins to have configurable flexible field mapping rules to adapt to different formats of terminal trouble tickets and installation manifests. Unlike IT service desk ticket processing, desktop terminal support directly addresses computer and peripheral issues, so tool calling does not need to interface with ticket routing systems, and focuses directly on local terminal operations. Long fault troubleshooting durations require tool calling to set reasonable timeout and retry mechanisms to avoid interrupting the fault reproduction flow. Errors may lead to employee downtime or ticket backlogs, so tool calling stability and parameter validation logic must cover common exceptions in terminal scenarios. The FastGPT v4.17.0 tool calling framework has optimized parameter validation logic for desktop terminal scenarios.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` or `Specified Tool` | Adapt to scenarios where test cases dynamically select terminal troubleshooting tools, support automatically matching fault types to call corresponding plugins |
| `functionCall` | `Enabled` | Used to generate standardized tool calling requests, adapting to parameter transfer requirements for terminal fault troubleshooting |
| Single Tool Call Timeout | `600 seconds` | Terminal troubleshooting typically requires waiting for remote operations and driver detection to complete, avoiding timeout interruptions to the fault reproduction flow |
| Tool Call Result Cache | `Cache for 1 day per request validity period` | Terminal trouble tickets are updated daily or per request, caching for 1 day balances data timeliness and calling efficiency |
| Plugin Call Retry Count | `2 times` | Occasional network fluctuations during terminal troubleshooting can be resolved via retries, avoiding ticket backlogs caused by a single failed call |
| Plugin Parameter Mapping | `Automatically match fields by terminal serial number and fault type` | Daily documents include fixed fields such as terminal serial number and fault type, automatic mapping reduces configuration workload |

## Three Common Misconfigurations
- Issue: When creating a system plugin in Docker-deployed FastGPT, the `packages/plugins/register` file cannot be found, and a missing parameter error is returned when calling tools. Cause: The plugin directory was not mounted or the plugin registration script was not initialized according to specifications, so the system cannot recognize custom plugin configurations.
- Issue: In FastGPT v4.9.10, the tool calling configuration interface does not have a code running tool connection option, and code execution nodes cannot be bound. Cause: The code running plugin is not enabled by default for the desktop terminal support tool calling scenario, so the corresponding plugin switch must be manually enabled.
- Issue: When calling a large model to retrieve a knowledge base, the system prompts high memory usage, and users question whether 192GB DDR5 memory is sufficient. Cause: Knowledge bases for terminal support scenarios typically contain large amounts of terminal hardware parameters and fault history data. Context windows must be adjusted based on actual data volume, and calling parameters must be configured reasonably in combination with physical memory.

## How to Verify Proper Configuration
- Upload a simulated terminal trouble ticket to trigger the tool calling flow, check whether the corresponding troubleshooting plugin is automatically matched and scenario-compliant steps are returned.
- View the tool calling log to confirm that the `toolChoice` parameter automatically selects or specifies the corresponding tool according to the configuration, with no missing parameters or format errors.
- Simulate a 600-second delayed operation to verify that the single tool call timeout setting takes effect, and no forced interruption is triggered.
- Check the plugin parameter mapping results to confirm that fields such as terminal serial number and fault type are automatically matched successfully, with no field misalignment or omission.
