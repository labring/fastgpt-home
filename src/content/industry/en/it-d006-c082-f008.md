# Test Cases and Defect Analysis for Channel Attribution and Lead Distribution: Workflow Orchestration
This document is written based on FastGPT v4.17.0.

## What Typical Data for This Category Looks Like
Typical data for this category comes from advertising platforms, CRM systems, attribution SDKs, and form systems. Daily maintained documents include attribution rules, lead distribution tables, channel reports, and exception checklists. Data update frequency is usually daily or weekly. Core fields include channel identifier, lead ID, assigned sales account, conversion time, parameter validation flag, and more. Data field formats vary across different sources, so unified adaptation is required before processing.

## Constraints Imposed on Workflow Orchestration by These Characteristics
Multi-source data access requires workflows to configure multiple heterogeneous data source connector nodes, to avoid compatibility issues with single nodes. The low-frequency nature of data updates requires workflows to support both scheduled trigger and event trigger modes, to fit different business rhythms. The need to reuse core documents requires workflows to bind configurations such as attribution rules and lead distribution tables as global variables, to reduce duplicate configuration. The most time-consuming steps—channel parameter verification, duplicate lead deduplication, and sales assignment confirmation—must be completed via workflow automation. Anomaly detection nodes must also be set up to prevent issues such as distorted channel ROI, sales disputes, or budget misalignment caused by errors.

## How to Set Configurations
| Configuration Item | Suggested Setting | Rationale |
| --- | --- | --- |
| Trigger Timing | Scheduled daily / Triggered by new lead events | Data update frequency is daily or weekly, and leads are generated in real time |
| `variables` Binding | Bind attribution rules and lead distribution tables as global variables | Daily work documents include attribution rules and lead distribution tables, and configuration reuse in workflows is required |
| `nodeId` Assignment | Assign a unique `nodeId` to the duplicate lead deduplication node | Need to accurately locate execution logs and error messages for this step |
| Single Verification Entry Count | Set to `1000 entries` | Avoid timeouts caused by excessive data volume processed by a single node |
| Timeout Threshold | Set to `300 seconds` | The most time-consuming steps are channel parameter verification and duplicate lead deduplication; need to prevent workflow blocking |
| Output Format | Output standardized JSON containing channel ID and lead assignment | Daily generation of channel reports and exception checklists requires unified field structure |

## Three Common Mistakes
- The AI model option is empty in workflows, and no initialization model can be selected. The cause is that the corresponding AI service is not bound in the global configuration, so the list of callable models for the node fails to load.
- The workflow text content extraction node returns empty JSON results. The cause is that `variables` binding for the raw lead data field to be extracted is not configured correctly, so the node has no valid input content.
- Saving fails when using the initialization AI model for a new question classification node, and works normally after switching models. The cause is that permission configuration for the initialization model is not synchronized to workflow nodes; switching models overwrites the permission configuration.

## How to Confirm Correct Configuration
After the workflow is executed, verify whether the `variables`-bound attribution rules are read correctly. Loaded configuration content can be viewed in node logs.
A test case is triggered, multi-channel lead submissions are simulated, and whether the `nodeId` of the duplicate lead deduplication node is recorded correctly is verified. Relevant information can be viewed via node execution details.
Test data with abnormal channel parameters is simulated, and whether the timeout threshold takes effect is verified. Trigger logic can be confirmed by adjusting the processing duration of test data.
Workflow run results are exported, and whether output fields match the requirements of channel reports and exception checklists is verified.

The values provided here are common starting points and should be measured against the reader's own samples.
