# Test Cases and Defect Analysis for Game Content Compliance Self-Check: Workflow Orchestration

## What the data for this category looks like
This category of data mainly comes from game text, art resources, plot scripts, and public regulatory requirements. Updates follow each game version or event cycle. Daily produced documents include content self-check lists, sensitive content modification records, user agreements, and compliance review minutes. Fields include content snippets, compliance verification tags, modification status, review comments, and more. There is no fixed unified format, and it is adjusted based on the project.

## What constraints these characteristics impose on the "workflow orchestration" link
Multi-source data input requires workflows to support access to multiple node types such as text and files. This adapts to mixed verification scenarios for game text and art resources. The high-frequency update cycle requires workflows to bind trigger conditions like version updates or event launches, without repeated configuration. Non-standardized document structures require workflows to support dynamic `variables` parsing, compatible with self-check lists and review minutes in different formats. The long-link verification-modification-review process requires workflows to support state transfer between nodes and failure branch jumps, covering secondary verification for controversial content.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale for This Setting |
| ---- | ---- | ---- |
| Trigger Mode | Trigger by version node, or bind the version number parameter in `variables` | Matches the update rhythm of this category per version or event, to avoid missed triggers from manual operations |
| Input Node Types | Text node + file upload node | Covers multi-source data input requirements for game text, art resources, and more |
| Global Variable Storage Method | Store `variables` per session | Adapts to state transfer during a single compliance self-check process, retaining verification records for the current version |
| Failure Branch Configuration | Jump to manual review node, set timeout to 600 seconds | Covers scenarios where controversial content cannot be verified automatically, aligns with the manual review link of the compliance process |
| Node Parameter Binding | Associate context variables corresponding to `nodeId` | Ensures results from each verification node can be accurately passed to subsequent modification or review links |
| Debug Mode Configuration | Enable node input and output logs | Facilitates troubleshooting of abnormal parameter transfer, compatible with the debug function of FastGPT v4.17.0 |

## Three common configuration mistakes
- Phenomenon: When the workflow is used as a tool call, uploaded files cannot correctly pass file links to downstream nodes. Cause: No file link extraction logic is configured in the input node. Direct use of original upload parameters causes link breakage.
- Phenomenon: After setting global variables, downstream nodes show empty input during debugging. Cause: Variables in `variables` are not correctly bound to downstream node input parameters, or variable updates are not synchronized to the global context.
- Phenomenon: The workflow does not trigger as expected when a version is updated. Cause: Trigger mode is set to manual, and no event node for version updates is bound. This prevents the process from starting automatically.

## How to confirm the configuration is correct
- Upload a game plot script file, trigger the workflow to run, and check if the input node correctly reads the file content.
- Configure global variables in the workflow, call the `variables` parameter in downstream nodes, and verify if variable values are passed correctly.
- Simulate a verification failure scenario, and check if the workflow jumps to the manual review node.
- Check the workflow's trigger configuration, confirm that trigger conditions for version updates or event launches are bound.
