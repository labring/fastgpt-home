# Test Cases and Defect Analysis for Game Content Compliance Self-Check: Tool Calling and Plugins

## What this category of data looks like
This category of data comes from text, art assets, plot scripts during game development, and publicly released regulatory compliance requirements. Maintained documents include content self-check lists, sensitive content modification records, user agreements, and compliance review minutes. Updates are scheduled per version or before each event launch. Data fields include content type, self-check item number, modification traces, review conclusions, and have no unified fixed units. They adjust based on the requirements of specific self-check items.

## What constraints these characteristics impose on the tool calling and plugins workflow
Multi-source and multimodal data sources require plugins to support parsing formats for text and art metadata. Otherwise, full coverage of self-check content is not possible. The high-frequency update rhythm requires tool calling configurations to support quick adjustments, to avoid version update delays caused by redundant configurations. Diverse daily document structures require plugins to support custom field mapping, to adapt to the self-check list formats of different teams. Defect analysis needs to link modification records and review opinions, so tool calling must support context-related retrieval. Otherwise, the root cause of compliance issues cannot be quickly located.

## How to set configurations
The configurations on this page are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `"function"` | Explicitly specify calling compliance verification tools, avoid the model selecting irrelevant tools on its own |
| `functionCall` | Only call pre-defined functions related to compliance verification | Ensure tool calling focuses on compliance checks, and does not perform unrelated operations |
| Single tool call timeout | `600 seconds` | Compliance verification needs to process multiple game texts and art metadata, which takes a long time |
| Single tool call character processing limit | `800–1200 characters` | Adapt to the conventional length of single-segment self-check content in game scripts, avoid truncating key information |
| Failure retry interval | `60 seconds` | Allow sufficient time for temporary resource recovery, reduce the probability of retry failure |
| Number of failure retries | `3 times` | Compliance verification failures may come from temporary network or resource issues, retries can reduce misjudgment rates |

## Three common configuration mistakes
- The phenomenon is that the plugin returns an empty result after processing uploaded game text corpora. The cause is that parsing rules adapted to game script formats are not configured, so the corpora cannot be correctly recognized.
- The phenomenon is that the list of compliance documents associated with the knowledge base cannot be obtained after calling the API. The cause is that the context return configuration for tool calling is not enabled, and document association information is not included in the return fields.
- The phenomenon is that art resource metadata cannot be read normally after replacing the document parsing tool. The cause is that the format adaptation configuration item of the corresponding plugin is not modified, leading to incompatibility between the new tool and existing verification logic.

## How to confirm configurations are correctly set
- Upload a test game plot script, trigger tool calling, check whether compliance verification results are returned, confirm that the tool is called normally.
- Call the corresponding API, check whether the return result includes document association information, confirm that the context return configuration is effective.
- After replacing the document parsing tool, upload an art resource metadata file, check whether it can be parsed normally and included in compliance verification, confirm that the format adaptation configuration is effective.
- Simulate a tool call failure scenario, check whether the preset alarm and retry mechanism is triggered, confirm that the failure handling configuration is effective.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
