# Test Cases and Defect Analysis for Game Client Performance Optimization: Tool Calling and Plugins

## What This Category’s Data Looks Like
Data for this category primarily comes from engine Profiler tools, crash reporting platforms, real device performance test clusters, and frame rate capture devices. The update cadence is daily aggregation or synchronization before each version release. Daily output documents include performance test reports, device compatibility lists, optimization records, and crash analysis reports. Data fields include frame rate (fps), memory usage (MB), resource package size (MB), scene loading duration (seconds), and other relevant metrics. Units follow standard industry performance testing standards, with no custom special fields.

## What Constraints Do These Characteristics Impose on the "Tool Calling and Plugins" Link
Data sources for this category are scattered and have varying formats. The tool calling link must adapt to multi-source interface authentication rules and data format conversion logic. Unlike mobile development scenarios, this category focuses more on frame rate, package size, and resource loading related data, so plugins must prioritize mapping these fields. The high-frequency update cadence requires calling frequency to match the data synchronization cycle to avoid triggering interface rate limits. Fixed-structure business documents require plugins to preset field mapping rules to match raw performance data to standard fields in test reports. For scenarios relying on real device test data, plugins must support remote real device interface calls and adapt to parameter differences across device models.

## How to Configure Settings
| Configuration Item | Recommended Value | Rationale |
| ---|---|--- |
| `toolChoice` | `auto` | Adapts to multi-tool calling scenarios, automatically selects tools matching performance test data |
| `functionCall` | `enabled` | Supports structured output of performance test results to facilitate subsequent analysis and report generation |
| Single tool call timeout | `300 seconds` | Real device testing and cross-platform data pulling typically require a certain amount of time; prevents process interruption due to timeout |
| Tool call retry count | `2 times` | Addresses network fluctuations or temporary interface unavailability, reduces invalid calls |
| Maximum data returned per call | `Top 20 entries` | Performance test data usually includes multiple sets of samples; limiting returned entries avoids context overflow |
| Plugin data mapping rules | Determined based on actual measurements | Performance test report fields vary across projects, must match actual business document structure |

## Three Common Mistakes
- Phenomenon: Tool call returns empty results, and the page displays no matching data. Cause: `toolChoice` is not configured to the mode adapted for performance testing tools, so the corresponding plugin calling logic cannot be triggered.
- Phenomenon: Call logs are not displayed on the specified page, making interface issues impossible to troubleshoot. Cause: Plugin log reporting configuration is not enabled, so no traceable log records are generated during the calling process.
- Phenomenon: Tool call timeout error with status code 504. Cause: Single tool call timeout setting is too short, not matching the actual time required for real device testing or data pulling.

## How to Confirm Configuration Is Correct

- Check the plugin call log page to confirm that complete call chain records are generated, including interface requests and return parameters.
- Simulate a low-end device test scenario to verify that the plugin can correctly call the remote real device interface to obtain frame rate and memory usage data.
