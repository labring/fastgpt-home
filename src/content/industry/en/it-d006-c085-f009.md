# Test Case and Defect Analysis for Game Server R&D and Operations: Tool Calling and Plugins

## What the data for this category looks like
Data sources related to game server R&D and operations include game operation logs, real-time online player count monitoring, business databases, and player-submitted tickets. Data is updated either through daily aggregation or triggered by game events.
Daily maintenance documents include server architecture topology descriptions, server launch capacity planning plans, server merge data verification processes, and fault troubleshooting reports.
Data fields include server process ID, online player count, database connection latency, player feedback type, and log timestamp. Corresponding units are integer, person-times, milliseconds, classification tags, and ISO format timestamp.

## What constraints these characteristics impose on the "tool calling and plugins" workflow
Game server operation and maintenance data sources are scattered, including real-time monitoring, offline logs, business databases, and player tickets. Tool calling must support parallel pulling plugins for multi-source data.
Data update frequency fluctuates with events. Plugin triggering mechanisms must support flexibly configured scheduling cycles to adapt to daily inspection and event peak scenarios.
Daily maintenance document structures vary widely. Tool calling parsing parameters must support custom field mapping rules.
Fault outcomes affect player experience. Tool calling must configure failure retry and status reporting logic to avoid delayed defect analysis caused by calling exceptions.

## How to set the configurations
The following configurations are written for FastGPT v4.17.0.
| Configuration Item | Recommended Setting | Rationale for This Setting |
| ---|---|--- |
| Tool Trigger Timing | According to server log generation cycle / 1 hour before event start | Match data update rhythm to ensure timeliness of analysis data |
| Retry Count | 3 times | Balance call success rate and resource consumption |
| Timeout Threshold | 600 seconds | Adapt to long-duration scenarios of server log pulling |
| Field Mapping Rules | Match preset fields from operation and maintenance documents | Adapt to complex server operation and maintenance document structures |
| `toolChoice` | auto | Let the model autonomously select the appropriate tool to complete the call |
| `functionCall` | Configure according to log parsing requirements | Trigger the model to automatically call parsing functions to process returned data |

## Three common mistakes
- Phenomenon: When calling the MongoDB plugin, the visual tool can connect normally but FastGPT project startup reports an error. Cause: The server permission whitelist for the plugin is not configured, or the plugin connection parameters do not match the intranet access address in the operation and maintenance documents.
- Phenomenon: After calling the HTTP interface to obtain game logs, the knowledge base does not generate corresponding analysis results. Cause: The `functionCall` parameter is not configured correctly, causing the model to fail to automatically trigger the follow-up processing flow for log parsing.
- Phenomenon: The number of returned results from tool calling does not meet expectations, and cannot cover all requirements for server merge data verification. Cause: The return rules of the tool are not adjusted according to the field range in the server merge document, resulting in missing key verification data.

## How to confirm the configuration is complete
- Perform a manual tool call once, and check the consistency between the returned data and the fields in the server logs.
- Simulate a data update to trigger the plugin, and check whether analysis reports are generated according to the preset cycle.
- Configure abnormal alarm rules, and check whether corresponding notifications are sent when exceptions are triggered.
- Initiate a call request for the specified knowledge base, and confirm that the returned results include the preset server merge verification data.
