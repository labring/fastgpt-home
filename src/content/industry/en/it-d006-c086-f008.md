# Test Cases and Defect Analysis for Game Publication License and Publishing Declaration: Workflow Orchestration

## What This Category of Data Looks Like
This category of data is built around the publishing declaration process for a single game. Daily documents include declaration request files, game application forms, copyright certificates, and review reports. Data comes from the national press and publication administration office service platform, copyright registration archives, game package files, and operating institution filing materials. Data update timelines adjust irregularly based on the declaration progress of a single game. Core fields include declaration number, copyright identifier, package verification information, and preliminary review opinion number. There is no unified fixed batch update cycle.

## Constraints Imposed on Workflow Orchestration
The irregular data update timeline tied to single-game declaration progress means workflows cannot rely on fixed-cycle scheduling. Workflows must support triggering based on declaration status changes. Diverse daily document types, including text and package files, require workflow nodes to support multi-format input parsing. Core fields have unique identifiers, so workflow variable configuration must bind exclusive field mappings to avoid cross-category data confusion. The material verification link takes up a large share of total time, so workflow orchestration must automatically run consistency verification nodes to cut down on manual repetitive work. Errors will lead to approval failures, so workflows must include failure fallback nodes to trigger manual review processes.

## How to Configure Workflows

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Bind declaration number and copyright identifier fields | Match category-specific data fields to avoid cross-process data confusion |
| Node Trigger Condition | Trigger based on declaration status changes | Adapt to the irregular update rhythm of single-game declarations, no fixed scheduling required |
| Failure Handling Strategy | Trigger manual review node and push preliminary review opinions | Correspond to the error consequence of approval failure, quickly correct risks |
| Single Processing File Limit | Top 10 files | Match the document quantity scale of single-game declarations, avoid node overload |
| Context Length Limit | 800–1200 characters | Adapt to the conventional text length of review reports and application forms, ensure parsing completeness |
| `nodeId` | Bind the preliminary review opinion collection node ID | Accurately trigger subsequent correction processes, reduce invalid node calls |

## Three Common Configuration Mistakes
- Using `[{datasetId: xxx}]` format variable references in workflows returns no results. This occurs when category-specific `variables` configuration is not bound, and variable mapping rules do not match the exclusive fields of the declaration process.
- Data analysis operations cannot be fixed as permanent nodes in workflows. This occurs when the corresponding operation template is not selected in the workflow orchestration interface, and fixed node configuration is not associated via `nodeId`.
- Workflows cannot perform cyclic traversal of multiple declaration documents. This occurs when the workflow's cyclic trigger configuration is not enabled, and no traversal rule is set for multiple documents of a single game.

## How to Verify Successful Configuration
- Confirm that fields bound to `variables` match the core identifiers of declaration documents, and field names align with those used in daily declaration files.
- Trigger a single test declaration process to verify that nodes trigger based on declaration status changes.
- Simulate a failure scenario to confirm that the preset manual review node activates after a failure.
- Test the cyclic traversal function to verify that corresponding operations run automatically based on the quantity of declaration documents.
