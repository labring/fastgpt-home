# Test Cases and Defect Analysis for Game Design and Balance Tuning: Source Citation and Traceability

## Data Profile for This Category
Daily documents for this category include gameplay design documents, balance tuning sheets, version requirement lists, and balance test records. Data sources include player behavior logs, publicly available competitor materials, in-game battle records, and version iteration feedback. Update cycles follow a weekly or per-version schedule. Document fields include damage coefficients, growth curve parameters, trigger conditions, test pass rates, and more. Some numerical documents require precise unit matching, such as seconds, percentages, and damage multipliers.

## Constraints for Source Citation and Traceability
The multi-source data and high-frequency update characteristics of this category create multiple constraints for citation traceability. Teams must distinguish traceability logic between static documents (such as balance sheets and design documents) and real-time behavioral data (such as player logs). Mixing content from different versions must be avoided. Precise field and unit requirements mandate retaining original document field names and unit identifiers during traceability. This prevents gameplay imbalance caused by numerical deviations. The weekly or per-version update cycle requires the traceability chain to quickly locate the corresponding version of a document copy. This ensures cited content is not outdated. The severity of potential errors requires traceability information to link directly to test cases and defect records. This enables rapid identification of problem root causes.

## Configuration Settings
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | Matches the single-page content length of balance sheets and design documents, ensuring complete citation of rules and numerical information |
| `responseData` | Return only source document metadata and snippets | Retains fields, units, and version identifiers to enable quick location of original documents during traceability |
| `detail` | Enabled | Displays specific traceability paths, including document version, update time, and source type |
| Single search limit | Top 8 recalled results | Covers the typical recall volume of multi-source data, avoiding omission of key test records or balance sheet snippets |
| Knowledge base sync cycle | Weekly | Matches the version update cycle of this category, ensuring indexed content is synchronized with the latest design documents |

## Three Common Configuration Errors
- Symptom: No optional values appear when selecting a knowledge base for citation configuration. Cause: Target document fields have not been configured as citeable variables, or index fields for the corresponding knowledge base have not been bound.
- Symptom: "Cannot redefine property: toString" error appears in the production environment. Cause: A custom script repeatedly defines the toString method, which conflicts with FastGPT’s built-in citation traceability logic.
- Symptom: Cited numerical values in generated test cases lack unit identifiers. Cause: The `responseData` metadata return configuration has not been enabled, so original document unit fields are not extracted.

## How to Verify Proper Configuration
- Initiate a test query, enter "Current version character damage coefficient", and check if returned results include the source document’s version number and field names.
- Check the `quoteMaxToken` configuration value to confirm a single citation covers the core parameters of a single balance sheet.
- Trigger a knowledge base sync, then verify the index list includes the latest version requirement list and balance test records.
- Check FastGPT v4.17.0 system logs to confirm no prompts for failed source document location appear in the citation traceability chain.

The values provided are common starting points and should be evaluated against local deployment samples.
