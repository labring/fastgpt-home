# Test Cases and Defect Analysis for Game Operation Activity Configuration: Reference Source and Traceability

## What Data for This Category Looks Like
This category of data primarily originates from the game operation backend, player segmentation system, payment data platform, and activity log system. Daily produced documents include activity plans, reward configuration tables, launch checklists, and activity review materials. Document fields typically include activity ID, effective time period, reward type and value, trigger conditions, and similar items. Update frequency is mostly weekly or prior to holiday nodes. The data structure is adjusted based on activity scale: small-scale activities have simplified configuration fields, while large cross-server activities include multi-dimensional player segmentation rules and compensation parameters.

## What Constraints Do These Characteristics Impose on the "Reference Source and Traceability" Link
The strong timeliness of activity configuration data requires the traceability link to quickly associate the latest operation backend configurations and activity logs, avoiding reference to expired reward values or time period rules. Multi-source data requires clear marking of source types, distinguishing static configurations from the operation backend and dynamic data from real-time player segmentation, to prevent confusion between static and dynamic parameters. Differences in document structures require the traceability system to adapt to display logic for different fields: for example, the value fields of reward configuration tables need to be associated with corresponding launch checklist verification records, and activity review materials need to be bound to the approval nodes of the original activity plan. Additionally, the high-frequency update feature requires the traceability link to support quick retrieval of historical versions by activity ID, to avoid confusion between cross-activity data.

## How to Set Configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | 900–1100 token | Adapts to the average character count of game activity configuration documents, retaining complete reward values, effective time periods, and trigger rules |
| `responseData` | Return only document metadata and content fragments | Filters non-essential system logs, focusing on core business documents such as activity plans and reward configuration tables |
| `detail` | Enabled | Displays the complete hierarchical path of the document, for example "Operation Backend/2024 National Day Activity/Reward Configuration Table", to quickly locate the original configuration |
| Reference Upper Limit | Top 4 entries | Matches the number of core reference documents for a single activity, avoiding context overflow that affects test case validation |
| Source Display Switch | Enabled | Forces the system identifier and update time of the document source to be displayed in test results, meeting the traceability requirements of defect analysis |
| FastGPT v4.17.0 | Fixed use | Adapts to the traceability rendering logic of this version, ensuring that source markers are properly displayed in test reports |

## Three Common Misconfigurations
- Phenomenon: No source identifier of the referenced document is displayed in the test results, only content fragments are shown. Cause: The `detail` configuration item is not enabled, or the source display switch is not turned on, resulting in traceability information being filtered and unable to support defect location.
- Phenomenon: Referenced activity configuration data exceeds the context limit, causing test case execution to fail. Cause: `quoteMaxToken` is set too large, or the reference upper limit is set beyond a reasonable range, exceeding the context carrying capacity of FastGPT.
- Phenomenon: Real-time player segmentation data and static operation backend configuration are confused as reference sources. Cause: Data source types are not distinguished in the configuration, resulting in inability to mark the difference between static configurations and dynamic data during traceability, leading to defects such as incorrect reward distribution.

## How to Confirm Configuration Is Successfully Applied
- Execute the test case for a single activity configuration, check whether the complete hierarchical path of the document is displayed in the results, and confirm that the `detail` configuration is enabled.
- Adjust the value of `quoteMaxToken`, and verify whether the configuration adapts to the current activity document length through the token statistics tool of the test case.
- Submit a test request containing multiple activity configurations, and check whether the number of returned reference documents conforms to the preset reference upper limit rules.
- View the defect traceability module of the test report, and confirm that all referenced data are marked with the corresponding source system and update time.

The values given are common starting points and should be measured against the reader's own samples.
