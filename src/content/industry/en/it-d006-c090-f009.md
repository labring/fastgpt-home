# Test Cases and Defect Analysis for Version Releases and Release Notes: Tool Calling and Plugins

## What data in this category looks like
Data for this category originates from Git repository tags, merged commit records, artifact packages generated by CI pipelines, and linked Issue milestones. Daily output documents include release notes, change logs, version tag documentation, and pre-release checklists. Data updates follow the version release cycle, with one update per version. Core fields include version number, change category, associated Issue number, and artifact checksum. Only objective change and release-related content is recorded, with no additional statistical dimensions included.

## Constraints for tool calling and plugin configuration
In FastGPT v4.17.0, the data characteristics of this category create clear constraints for tool calling and plugin configuration. Batch retrieval of Git tags and merge records requires tools to filter accurately by version range. This prevents cross-version redundant data from consuming context. Integrity verification for CI artifacts requires tools to call hash verification interfaces. This ensures release packages match recorded data. Defects linked to Issue milestones must be archived per version. Tools must support filtering defect entries by milestone. Each version’s feature updates require tool call frequency to match the release cycle. This avoids frequent retrieval of invalid data. Manual change category classification can be automated via plugins. Plugins must adapt to different project classification rules, and custom mapping configuration must be available.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Supports automatic classification of batch changes, no manual tool specification required |
| Single change retrieval limit | Top 20 entries | Matches the typical number of merge records per version, prevents context overflow |
| Version range filtering | Current release Git tag range | Accurately retrieves merge records and Issues for the target version |
| Artifact verification timeout | 120 seconds | Matches typical download and verification durations for CI artifacts |
| `functionCall` | Enabled | Supports structured output for automatic change classification and defect linking |
| Context window limit | 8000 token | Supports processing of batch change text, avoids exceeding model limits |

## Three common misconfigurations
- Tool calls return empty results, and interface fields display no content. The cause is missing version range filtering. Retrieving cross-version invalid change data means no matching test cases or defect entries for the current release are found.
- Plugin execution times out with a 504 status code. The cause is an overly high single change retrieval limit, paired with an overly short artifact verification timeout. This prevents completion of bulk data retrieval and verification.
- Text extraction tools report format errors. The cause is the `functionCall` parameter not being enabled. Tools cannot extract defect information from change logs in structured format, leading to matching failures.

## How to verify correct configuration
- Run a tool call test, confirm that returned change entries only include content linked to the current release version’s Git tags.
- Trigger the artifact verification step, confirm that tools can correctly pull CI artifacts and complete verification without timeout errors.
- Check generated output for structured defect links and change categories that match preset classification rules.
- Verify that when `toolChoice` is set to `auto`, tools automatically select the appropriate classification model to complete change categorization.

The values listed here are common starting points, and should be evaluated against the relevant user’s own sample data.
