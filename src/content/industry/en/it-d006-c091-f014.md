# Test Cases and Defect Analysis for Player Customer Service and Public Opinion Processing: Model Integration and Configuration

## What Data for This Category Looks Like
Data for this category primarily comes from game customer service systems, community forums, app store reviews, and game runtime logs. Daily processed documents include player tickets, compensation requests, public opinion daily reports, and standardized response scripts.
Most updates are daily or real-time. Real-time public opinion and player tickets have higher update frequencies.
Each data entry typically includes fields such as feedback subject identifier, problem description, linked account information, release channel, and timestamp. Some public opinion data also includes interaction volume and user level tags.

## What Constraints These Characteristics Impose on Model Integration and Configuration
Data sources are scattered and have diverse formats, including structured player tickets, semi-structured public opinion text, and unstructured game logs. The model integration link must support unified parsing and adaptation for multi-source data.
Real-time updated public opinion and ticket data requires model call latency to match business response requirements. This avoids negative feedback escalation caused by processing lag.
Different types of business documents correspond to differentiated processing logic. Targeted configuration of model prompts and parameters is required. Single-input context length must be limited to prevent parsing failure from exceeding the model's token limit.
The data contains sensitive player account information. Corresponding data security verification rules must be enabled in the configuration.

## Configuration Settings
| Configuration Item | Recommended Value | Basis for This Value |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | This category needs to associate player historical tickets and real-time public opinion. Retaining sufficient context can accurately restore problem scenarios, while adapting to the context limits of most general large models |
| `maxTokens` | `1000–1500 token` | Single business processing results (such as script generation, public opinion classification) usually do not require overly long content. Limiting tokens can reduce call costs and improve response speed |
| `temperature` | `0.2–0.4` | Compensation rule judgment and negative feedback classification in this category need to maintain logical consistency. A lower temperature reduces random output and improves processing accuracy |
| `vision` | Enabled | Some player feedback includes game exception interface screenshots, so visual content parsing is required to complete account verification and problem location |
| `toolChoice` | `auto` | Some processing scenarios require calling account verification and rule query tools. Automatic mode allows the model to independently judge call requirements, improving processing flexibility |
| `AIPROXY_API_TOKEN` | Configure as a non-empty administrator token consistent with the AI Proxy server configuration. This must be set as an environment variable for the App/Admin server | Ensure valid identity verification between the App/Admin service and the AI Proxy service, avoid service startup verification failure or model integration abnormalities caused by invalid tokens |

## Three Common Mistakes
- Phenomenon: Service startup verification fails for FastGPT v4.17.0 and above, or identity verification/address errors are returned during model calls. Cause: The `AIPROXY_API_ENDPOINT` or `AIPROXY_API_TOKEN` environment variables are not configured on the App/Admin server, or the environment variable values are invalid.
- Phenomenon: When multiple models with the same name but different keys are configured, calls cannot distinguish different instances, resulting in incorrect request routing. Cause: No unique identifier field is added to the model configuration, or the unique identifier of the corresponding model is not specified in the workflow node.
- Phenomenon: When a workflow node processes player tickets, the returned result contains redundant information from the global context that is unrelated to the current ticket. Cause: The global context sharing switch is not turned off, or only the input context of the current node is limited in the node configuration.

## How to Confirm Proper Configuration
- Manually enter a typical player ticket text to trigger a model call, and check whether the returned result includes problem classification and processing suggestions that conform to business logic.
- Configure test cases and pass test data containing sensitive account information to confirm that the system automatically completes desensitization processing.
- View the model call log to check that the actual usage of `maxContext` and `maxTokens` does not exceed the configured limits, and that the call latency meets business requirements.
- Configure multiple models with the same name but different keys, call them separately in the workflow, and confirm that the returned results of each model conform to the model capabilities corresponding to the key.

The values provided are common starting points and should be measured against the reader's own samples.
