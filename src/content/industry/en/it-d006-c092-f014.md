# Test Cases and Defect Analysis for On-Site Deployment: Model Integration and Configuration

## What the data for this category looks like
Typical subjects are implementation engineers, systems engineers, and customer IT staff. Four types of documents are regularly produced: deployment manuals, installation records, configuration lists, and on-site check-in forms.
Data sources include customer computer room environments, equipment lists, software packages, and network topologies. Update frequency is per order or per project phase.
Document fields include deployment node IP addresses, software version numbers, configuration parameter values, and more. Units include units, hours, entries, and others. Data is updated in real time alongside on-site deployment progress.

## Constraints imposed on model integration and configuration
The data source and document structure of on-site deployment implementation mean model integration must adapt to heterogeneous networks and personalized configuration requirements at customer sites.
Configuration requirements updated per order must be dynamically adjusted alongside on-site progress. General templates cannot be directly reused.
Standardized processes in documents require model output to match on-site execution steps to avoid deviations.
The time-consuming nature of on-site problem troubleshooting requires configuration to simplify error points and reduce on-site debugging costs.
The risk of system unavailability requires parameter configuration to be rigorous, to avoid deployment interruptions caused by configuration errors.

## How to set configuration parameters
This document is written based on the configuration logic of FastGPT v4.17.0.

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the context carrying capacity of batch documents such as multi-node logs and configuration lists for on-site deployment |
| `maxTokens` | 2000–4000 token | Matches the content length of on-site deployment manuals and defect reports, avoiding truncation of key steps |
| `temperature` | 0.2–0.4 | Ensures the rigor of configuration steps and defect analysis output, reducing on-site execution deviations |
| `AIPROXY_API_ENDPOINT` | Fill in the root address of the AI Proxy service, for example http://aiproxy:3000. Do not append /v1 or /chat/completions paths | As an environment variable for the App/Admin server, configure the AI Proxy service address reachable from the customer's computer room network to ensure communication connectivity between the server and AI Proxy |
| `AIPROXY_API_TOKEN` | Fill in the administrator token consistent with the AI Proxy server configuration, and do not leave it blank | As an environment variable for the App/Admin server, serve as an identity credential for calling AI Proxy to ensure communication compliance |

## Three common misconfigurations
- Symptom: Embedding model call error prompts token limit exceeded, and knowledge base chunk content cannot generate vectors. Cause: The `maxContext` parameter was not adjusted for long on-site deployment documents, and the default general 1024 token configuration was used.
- Symptom: Model returns empty results or abnormal formats. Cause: `AIPROXY_API_ENDPOINT` was not configured as the root address of the AI Proxy service reachable from the customer's computer room network, causing the App/Admin server to fail to connect to AI Proxy.
- Symptom: Defect analysis steps output by the model do not match the on-site deployment manual. Cause: The `temperature` parameter was set too high, causing generated content to deviate from standard on-site execution processes.

## How to confirm configuration is complete
- Check that the environment variables `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` on the App/Admin server are configured correctly, and server startup verification passes.
- Import a single on-site deployment manual document, verify that the `maxContext` and `maxTokens` parameters can fully carry the document content without truncation errors.
- Generate one test case, confirm that the output content aligns with the logic of on-site configuration steps, with no obvious deviations.
- View system logs to confirm that model call token consumption falls within the range of configured parameters, with no abnormal over-limit prompts.

The values provided are common starting points and should be measured against the reader's own samples.
