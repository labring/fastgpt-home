# Test Cases and Defect Analysis for User Growth and Retention Operations: Workflow Orchestration

## What the Data for This Category Looks Like
The data for this category primarily originates from user behavior logs, push systems, experiment platforms, and CRM systems. Most updates occur on a daily or weekly basis. Daily produced documents include growth experiment plans, user segmentation tables, outreach copy, and retention analysis reports. Common data fields include user segmentation tags, outreach time ranges, experiment group identifiers, and retention cycle metrics. There is no unified fixed single data length, and workflows must support input and output in multiple formats.

## How These Characteristics Impact Workflow Orchestration
Data from multiple sources must be integrated via a unified variable transfer mechanism. Workflows must support `variables` configuration to pass data across systems. Business requirements with varying update frequencies require workflows to offer both scheduled trigger and manual trigger modes. Diverse document formats require workflow nodes to adapt to input content with different structures to prevent parsing failures. Long-time-consuming user segmentation steps are prone to execution timeouts. Nodes must be split or execution thresholds adjusted. Rapid alarms and retries must be triggered after errors to avoid impacts on user retention and channel budget allocation.

This configuration applies to FastGPT v4.17.0.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Single execution duration limit | 600–1200 seconds | Covers the average execution interval of typical long-time-consuming tasks such as user segmentation and outreach rhythm design |
| Variable transfer rules | Bind `variables` to pass cross-system data | Adapt to access requirements for business data from multiple sources, unify input formats |
| Form pre-submission validation | Validate the first 3 required fields | Ensure core operational information is completed before workflow triggering |
| File upload binding | Limit single file size to no more than 1000 MB | Match the general file storage limit of the platform, avoid excessive resource consumption |
| Workflow retry strategy | Retry 2 times after failure, 60-second interval | Address temporary system call fluctuations, reduce execution failure probability |
| Node ID association | Specify `nodeId` to bind core processing nodes | Precisely control the workflow execution link, avoid incorrect node order |

## Three Common Misconfigurations
- Symptom: Workflows are interrupted by the system after exceeding 1200 seconds of execution, with an execution timeout prompt displayed on the interface. Cause: No reasonable execution duration limit is set for long-time-consuming tasks such as user segmentation, and long tasks are not split into multiple child nodes.
- Symptom: A parameter missing error is returned when calling workflow APIs related to file upload. Cause: Uploaded files are not bound as workflow input variables via `variables` configuration, causing the API to fail to read file content.
- Symptom: Workflows are started without filling in required form fields. Cause: No form pre-submission validation rules are configured, and workflows are not restricted to trigger only after all required fields are filled.

## How to Verify Correct Configuration
- Run the workflow with a single piece of simulated user segmentation data, confirm the execution duration falls within the preset 600–1200 second interval.
- Call the workflow API after uploading a test file, confirm the `variables` parameters related to the file are correctly read in the logs.
- Attempt to start the workflow without filling in required form fields, confirm execution is blocked and cannot be triggered.
- View the workflow node link, confirm the core processing node specified by `nodeId` is in the correct execution order.

The values provided are common starting points and should be measured against the reader's own samples.
