# Test Case and Defect Analysis for User Acceptance Testing Support: Workflow Orchestration

## What data for this category looks like
Data sources for this category include requirement specifications, test environments, customer business examples, and defect systems. Update frequency is per phase or per version. Daily produced documents include UAT test cases, acceptance issue tickets, acceptance reports, and sign-off confirmation forms. UAT test cases contain fields for scenario, preconditions, operation steps, and expected results. Acceptance issue tickets include fields for issue number, reproduction steps, severity level, and affiliated module. All data must align with the customer’s actual business scenarios.

## What constraints these characteristics impose on the workflow orchestration link
Since data comes from customer business examples and test environments, the workflow must support access to multi-source heterogeneous test documents and defect data. Because update frequency occurs at the phase or version level, the workflow must support dynamic binding of global variables without reconfiguring nodes each time. Daily documents have a fixed field structure, so workflow nodes must adapt to field extraction rules. The workflow must also cover the three most time-consuming links: test case preparation, issue reproduction and classification, and acceptance conclusion confirmation. Failure branches must be set to address risks such as acceptance delays and payment delays.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `variables` | Bind UAT test case scenarios and defect reproduction steps as global variables | Data sources include customer business examples and requirement specifications, requiring dynamic adaptation to test data across different phases |
| `nodeId` | Assign fixed `nodeId` to document parsing nodes and defect synchronization nodes | Need to stably call data sources from test environments and defect systems, preventing workflow failure caused by node ID changes |
| Global variable assignment | Update variable value range of `200–500 characters` for case descriptions per phase | Scenario descriptions in UAT test case documents are typically this length, matching the input requirements of the document parsing node in FastGPT v4.17.0 |
| Failure branch trigger | Set to trigger failure branch on `600 seconds` timeout | Extraction of reproduction steps from acceptance issue tickets typically requires this duration; timeout triggers manual review processes |
| Knowledge base selection | Filter top 5 matching knowledge bases by test module | Need to focus on the business scenarios of the current UAT phase, avoiding interference from irrelevant knowledge base content |

## Three common configuration mistakes
- Symptom: The document parsing node returns a 404 error in the server environment and cannot read uploaded file content. Cause: The file storage path is not bound to the `variables` parameter. The local environment path does not match the server path, causing the node to fail to locate file resources.
- Symptom: The workflow does not return corresponding defect analysis results after execution, and the number of knowledge base matches is 0. Cause: The knowledge base is not filtered by test module, and the full knowledge base is called directly, causing the matching rules to fail to hit relevant business content.
- Symptom: Global variables do not update as expected, and the severity level field of the acceptance issue ticket is empty. Cause: The variable assignment trigger condition is not set in the node configuration. Variables are only initialized when the workflow starts, and real-time updated defect data is not synchronized.

## How to confirm the configuration is correct
- Upload the test file from the server environment, run the workflow, and check whether the document parsing node returns normal file content parsing results.
- Simulate a timeout scenario, run the workflow, and verify whether it automatically jumps to the failure branch and triggers the manual review process.
- Modify the value of the global variable, run the workflow, and check whether the node input is synchronously updated to the new variable content.
- Select the knowledge base for a specific test module, run the test case analysis node, and check whether the returned matching results only include relevant content for that module.
