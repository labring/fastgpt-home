# Test Cases and Defect Analysis for Monitoring Alert Configuration: Tool Calling and Plugins

## What the data for this category looks like
Core data for monitoring alert configuration originates from systems including Prometheus, Zabbix, cloud monitoring, application logs, CMDB and others. Update frequency is daily or after each alert rule change. Daily maintenance documents include monitoring metric lists, alert rules, on-duty manuals and alert change records. Data fields include metric name, threshold range, trigger condition, notification target, change time and more. Units include seconds, count, percentage and others. Field formats have minor variations across different data sources.

## What constraints these characteristics impose on tool calling and plugins
Data sources are diverse and their formats differ. Tool calling must adapt to API formats and authentication rules of different third-party monitoring systems. Data updates trigger on rule changes. Plugins must support dynamic pulling of the latest alert configurations and metric data. There are many types of daily documents. Plugins must support uploading and parsing configuration files in multiple formats. The most time-consuming threshold setting and noise cleanup steps require tool calling to batch process multiple sets of configuration data. It also requires accurate call results to avoid impacting fault detection. This page content is compatible with FastGPT v4.17.0.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `toolChoice` | Specify by data source type | Adapt to the call formats of different third-party monitoring tools such as Prometheus and Zabbix |
| `functionCall` | Enable batch mode, process up to 8 configurations per call | Match the reasonable single-processing volume of daily alert rule lists |
| Authentication key management | Bind to the platform's built-in key storage | Avoid plaintext leakage and uniformly manage authentication keys for multiple plugins |
| Default file format | All formats selectable | Adapt to uploads of monitoring metric lists and alert change records in different formats |
| Token verification | Validate by the 200 status code returned by the interface | Ensure the legality and security of the call chain |
| Global variable passing | Map by external call parameters | Support dynamically passing variables such as on-duty groups and time ranges for alert scenarios |

## Three common misconfigurations
- A 401 authentication failure status code returns when a plugin calls a third-party monitoring API. This happens because the platform's built-in key management module is not used, and plaintext keys are directly filled in the plugin configuration, leading to failed key verification.
- Global variables fail to correctly pass into a workflow when an external call is made to a published workflow. This occurs because mapping rules between external call parameters and global variables are not configured, so variables cannot be delivered to workflow steps.
- Only a small number of formats are supported for monitoring configuration documents during file upload, making it impossible to support all file types required by MCP. This happens because the default file format is not set to all selectable, so alert rule documents in some formats cannot be parsed normally.

## How to verify successful configuration
- Run a plugin call test, and check whether the returned alert configuration data matches the locally stored monitoring metric list.
- Initiate an external interface call, pass preset global variable parameters, and check whether variables within the workflow are correctly replaced.
- Upload monitoring configuration files in different formats, and confirm that all formats can be recognized and parsed normally.
- View the plugin call logs, and confirm that there are no traces of plaintext leakage during the authentication key call process.
