# Test Cases and Defect Analysis for Community Report Handling: Tool Calling and Plugins

## What does the data for this category look like?
The data for this category mainly comes from community report systems, involved content detail pages, report users’ historical behavior records, and platform audit rule bases.
Core documents processed daily include report tickets, report processing records, user appeal forms, and violation disposal notification templates.
Data is updated daily or synced in real time.
Each individual data entry contains fields such as report ID, involved content link, report reason, and review status.
There is no unified fixed statistical unit. Management is carried out only according to the workflow of individual report tickets.

## What constraints do these characteristics impose on the tool calling and plugin workflow?
Data for this category comes from multiple heterogeneous sources, with updates occurring daily or in real time.
This requires tool calling to support connections to multiple data source interfaces, and adapt to ticket and appeal form inputs in different formats.
Core documents have no fixed standardized fields, so plugins must support custom field extraction rules to match the ticket structures of different communities.
There are strict requirements for the processing timeliness of individual reports. Tool calling must limit the context length of single processing to avoid timeouts.
Errors may trigger user complaints or community conflicts. An exception capture and fallback mechanism must be configured to transfer abnormal tickets to manual review processes.

## How to set configurations
These configurations apply to FastGPT v4.17.0:

| Configuration Item | Recommended Value | Rationale |
| ---|---|--- |
| `toolChoice` | `auto` or specified as `["file_parse", "knowledge_retrieval"]` | Community report handling requires calling both content parsing and knowledge retrieval tools. Auto mode automatically matches required tools, while specified mode reduces invalid calls |
| Plugin call timeout | `30–60 seconds` | Report ticket processing has strict timeliness requirements; timeouts require transfer to manual review to avoid delays |
| `functionCall` | `strict: true` | Must strictly match the field extraction rules for report tickets to avoid returning irrelevant content |
| Document parsing tool configuration | Calibrated based on actual testing | Formats of involved content vary widely across communities, so parsing parameters must be adjusted based on actually uploaded corpus |
| Exception retry count | `First 3 retries` | A small number of retries covers temporary network fluctuations; excessive retries consume system resources |
| Return field filtering | Return only report ID, disposal suggestion, and associated file list | Streamline returned content to avoid context overflow affecting tool calling efficiency |

## Three Common Mistakes
- Symptom: After replacing the document parsing tool in configuration, no parsing results are returned when uploading involved report content. Cause: Only the global document parsing configuration was modified, and the parsing tool parameters bound to the plugin were not adjusted separately for the community report handling scenario.
- Symptom: After calling tools via API, the returned results do not include the report file list associated with the knowledge base. Cause: The field return configuration for tool calling was not enabled, or the association mapping rules between report tickets and knowledge base files were not correctly established.
- Symptom: Tool calling frequently triggers timeouts, leading to a large number of report tickets being transferred to manual review. Cause: The configured timeout period is too short, or the context length of single tool calling was not limited, resulting in processing time for complex report content exceeding the set threshold.

## How to Confirm Configurations Are Correctly Set
- Submit a test report ticket, call the bound plugin tool, and check if the involved content text can be parsed correctly.
- Call the API to trigger tool calling, view whether the returned results include the preset report associated fields, and confirm that field mapping is correct.
- Simulate a timeout scenario for single tool calling, check whether abnormal tickets are transferred to the manual review queue as configured.
- After modifying the document parsing tool configuration, upload involved content in different formats, and confirm that the parsing results meet expectations.

The values provided are common starting points and should be measured against the reader's own samples.
