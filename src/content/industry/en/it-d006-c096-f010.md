# Test Cases and Defect Analysis for Community Report Handling: Citation Sources and Traceability

## What the Data for This Category Looks Like
Core data for community report handling comes from report systems, reported content details, user historical behavior records, and audit rules. Daily processing documents include report tickets, disposal records, appeal forms, and user notification templates.
Report tickets contain fields such as report ID, reported content identifier, and report reason. Appeal forms contain appeal reasons and supporting materials.
Most data updates occur in real time. Report submissions and status changes are synced immediately. Bulk appeal forms update on a daily basis.
This category’s data centers on individual report events. There are no redundant fields for general content aggregation. All fields are tied to specific report workflows.

## Constraints Imposed on Citation Sources and Traceability
Since data is generated around individual report events, citation sources must be precisely tied to specific report IDs and associated documents. General content aggregation citation logic cannot be used.
Real-time updated report statuses require the traceability link to pull the latest disposal records and appeal statuses immediately. This avoids referencing expired data.
Single documents focus on fields tied to report workflows. Citation traceability must extract content directly relevant to judging report validity. It must not include irrelevant redundant user historical information.
Errors here can lead to user complaints or escalated community conflicts. The accuracy and timeliness of citation traceability directly affect processing efficiency and community order.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | `800–1200 token` | Single documents related to community reports, such as tickets and appeal forms, typically range from 200–800 characters in length. This parameter limits the total token count of cited content, preventing key information from being truncated due to exceeding the context window |
| `responseData` | Enabled | Community report handling requires association with specific metadata such as report ID and disposal time. When enabled, this setting synchronizes associated data from citation sources into replies and the front-end interface |
| `detail` | Full | Judging report validity requires complete details such as reported content and user historical records. Full mode returns all valid information from cited content, rather than only a simplified summary |
| Citation source refresh interval | `10–30 seconds` | Community report data updates in real time. This interval ensures cited disposal records and appeal statuses are always the latest versions |
| Maximum number of cited entries | `Top 3–6` | Valid evidence for community reports typically focuses on a small number of related tickets and records. Limiting the number of entries avoids redundant information interfering with audit judgments |

## Three Common Mistakes
- The cited report ticket ID or disposal record is not displayed on the official chat page. This occurs because the `responseData` configuration is not enabled, so metadata is not synchronized to the front-end rendering logic.
- Cited reported content is truncated, preventing full viewing of violation evidence. This occurs because the `quoteMaxToken` setting is too small, causing cited content to exceed limits and be automatically truncated.
- Extracted report text only contains partial content, making it impossible to fully match violation rules. This occurs because the `detail` configuration is not set to full mode. Only a content summary is retrieved, rather than the full original text.

## How to Verify Proper Configuration
- The FastGPT v4.17.0 debugging interface is accessed. A simulated report ticket is submitted. The reply is checked for associated metadata such as report ID and disposal time.
- The `quoteMaxToken` parameter is adjusted to a small value. A long-form report ticket is submitted. Cited content is checked for truncation. The recommended setting is restored, and verification confirms no truncation occurs.
- The `detail` configuration is enabled. Cited content is checked for inclusion of the full original reported content and relevant details of user historical behavior.
- Multiple associated report tickets are submitted. The reply is checked to confirm only the specified number of relevant cited documents are displayed, with no redundant content.

The values provided are common starting points and should be validated against the operator’s own samples.
