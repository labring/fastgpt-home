# Test Case and Defect Analysis for Mobile Development: Model Integration and Configuration

## What Data for This Category Includes
Data for this category primarily comes from code repositories, app store backends, crash monitoring platforms, and device coverage data. Update cadence follows daily or per-version release cycles. Daily associated documents include device version release notes, device adaptation lists, crash analysis reports, and app store review materials. Data fields include device version, permission call records, crash log IDs, app store submission status, and more. There is no unified fixed quantitative statistical unit; values vary based on the business attributes of individual data entries.

## Constraints on Model Integration and Configuration
Data sources for this category are scattered, with significant format differences. Field names and structures vary across different data sources. The model integration link must support format adaptation for multi-source data. Data update frequency is high, and the volume of content processed in a single batch fluctuates noticeably. Context window and token usage limits must be restricted to avoid timeouts. Business content focuses on defects related to device adaptation, permission troubleshooting, and review. Model parameters matching mobile development scenarios must be configured to ensure accurate recognition of professional terminology. Some data must be synchronized to app store backends. Model output content must comply with platform review format requirements to avoid disrupting subsequent processes due to format issues.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `maxContext` | `8000–12000 characters` | Adapts to the single-batch content length of mobile testing documents, avoids exceeding model context limits |
| `maxTokens` | `4000–6000 token` | Matches output requirements for mobile defect analysis, balances content completeness and response speed |
| `quoteMaxToken` | `1500–2000 token` | Limits the length of referenced test cases or crash logs, ensures context does not overflow |
| `toolChoice` | `auto` | Automatically selects tools suitable for defect analysis, adapts to multi-source data processing logic |
| `temperature` | `0.3–0.5` | Reduces random output, ensures accuracy and consistency of test cases and defect analysis |
| `AIPROXY_API_ENDPOINT` | Enter the root address of the AI Proxy service, for example `http://aiproxy:3000`. Do not append `/v1` or `/chat/completions` paths | Required environment variable for the App/Admin server, specifies the access root address of the AI Proxy service, complies with FastGPT v4.17.0 proxy access specifications, ensures correct request routing |
| `AIPROXY_API_TOKEN` | Enter the administrator token consistent with the AI Proxy server configuration, must not be empty | Required environment variable for the App/Admin server, used for identity verification with the AI Proxy service, ensures access permission security, avoids unauthorized access |

## Three Common Configuration Mistakes
- Incorrectly entering the root address when configuring `AIPROXY_API_ENDPOINT`, resulting in request timeouts or 404 status codes. Troubleshooting steps: check if the variable value is the root address of the AI Proxy service, no additional paths such as `/v1` are appended, and the address is not confused with a single-model service address.
- Setting `maxTokens` beyond the upper limit supported by the model, resulting in truncated output or model refusal to respond. Cause: failed to adjust parameters based on the actual content length of mobile testing documents, blindly used general configurations.
- Accidentally configuring an index model as a non-embedding model, resulting in empty recall results for test cases. Cause: confused configuration requirements for chat models and index models, failed to select the corresponding model type based on the scenario.

## How to Verify Successful Configuration
- Submit a mobile crash log analysis request, check if the returned result includes core fields such as device version and permission calls, confirm that context parameters are effective.
- View system logs, confirm that the proxy request status code is 200, no timeout or permission errors occur, verify that the access address and key configuration are correct.
- Submit a batch of test case data, check that the number of recall results matches the configured `maxContext` parameter, confirm that the context limit is effective.
- Adjust the `temperature` parameter and submit a request again, compare the differences between the two outputs, confirm that the parameter configuration is effective.
