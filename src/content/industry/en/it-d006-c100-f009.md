# Test Case and Defect Analysis for Cybersecurity Level Protection Assessment Consulting: Tool Calling and Plugins

## What this category of data looks like
Core data for cybersecurity level protection assessment consulting is generated around the full workflow of level protection assessments. Daily documents include four categories: level determination reports, gap analysis reports, rectification plans, and assessment reports.
Data mainly comes from assessment tool outputs, on-site interview records, asset system inventories, and security device operation logs.
Data updates follow individual assessment project cycles, with phased updates aligned to project progress, and are archived after the project concludes.
Document fields include control item number, gap description, rectification measures, evidence attachment number, and other fields. There are no unified fixed units, with adjustments made based on the asset scale and number of control items of the assessed object.

## What constraints these characteristics impose on the tool calling and plugins workflow
The document structure for level protection assessments is fixed and must strictly align with level protection standards. Tool calling must adapt input formats for different document types to ensure output content can be directly embedded into official assessment reports.
Data sources are scattered and require cross-tool integration, so multi-source data pulling plugins must be configured to enable unified calling of system inventories, logs, and interview records.
Update frequency follows the project cycle, so tool calling must support on-demand triggering to adapt to the phased update rhythm of the project.
The rectification evidence collection link requires verifying attachment authenticity, so tool calling must associate logs and system inventories for cross-checking.
Checking control item gaps involves a large number of standardized entries, so tool calling must limit output scope to align with assessment standards.

## How to configure
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapts to the mixed calling scenario of multiple documents and tools in level protection assessments, automatically matching corresponding tools to process different types of assessment data |
| `functionCall` | Enabled | Forces the model to generate structured output compliant with level protection standards, making it easy to directly write into level determination reports or gap analysis reports |
| Tool call timeout setting | 600 seconds | The log data volume of level protection assessments is large, so sufficient time must be reserved for cross-source data integration and verification |
| Single tool call limit | First 8 entries | Matches the number of gap checking entries for a single control item, avoiding redundant information interfering with assessment report generation |
| Plugin data filtering rule | Filter by assessment project archive tags | Ensures tool calling only calls system inventories, logs, and other data from the current project, avoiding interference from cross-project data |
| Maximum context length | 12000 characters | Adapts to the single-chapter content length of level protection assessment reports, ensuring the model can fully read document context for defect analysis |

## Three common misconfigurations
- Tool calling process is not hidden, and original interface requests and sensitive fields are exposed in the interface. Cause: FastGPT's tool call result folding configuration is not enabled, causing sensitive data such as system inventories and logs during the assessment process to be displayed directly.
- Interface call returns 413 error. Cause: The volume of security device log data uploaded in a single tool call exceeds the platform limit, and logs are not chunked in advance.
- When calling the Qwen3 model, the inference mode is not restricted, generating unstructured defect analysis content. Cause: The `functionCall` parameter is not configured to force structured output, causing the analysis result to fail to directly match the fixed format of the level protection assessment report.

## How to confirm the configuration is correct
- Initiate a test case generation call, check if the tool call result is automatically folded, and confirm that the hiding configuration takes effect.
- Upload a single test copy of security device log data, initiate a call, check if the interface returns a normal status code, and confirm that the timeout and chunking configurations are compatible.
- View the model output content, confirm that it is in a structured format compliant with level protection standards, and confirm that the `functionCall` and `toolChoice` configurations take effect.
- Switch to the dataset of a different assessment project, initiate a call, check if only the associated data of the current project is called, and confirm that the plugin filtering rule takes effect.
