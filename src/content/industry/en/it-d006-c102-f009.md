# Test Case and Defect Analysis for Defect Management and Regression Testing: Tool Calling and Plugins

## What data for this category looks like
Data for this category comes from defect management systems, test reports, code commit records, and user feedback. The update frequency is daily or per version release cycle. Daily produced documents include defect tickets, regression test checklists, repair verification records, and defect statistical reports. Data fields include unique defect identifiers, priority levels, reproduction steps, associated test case IDs, affected version numbers, repair status, and more. Most fields are structured, while some reproduction steps and verification records are unstructured text.

## What constraints these characteristics impose on the "tool calling and plugins" link
Since data sources are scattered and include both structured and unstructured content, tool calling must adapt to the interface formats of multiple data sources. It must also support structured field extraction and semantic parsing of unstructured reproduction steps. With an update frequency of daily or per version, the trigger logic for tool calling must be bound to version iteration nodes or scheduled tasks. This avoids pulling expired defect and test data. The strong association between defect data, test cases, and versions requires plugins to retain the transfer chain of associated fields. This ensures complete context during regression verification. For time-consuming links such as defect reproduction and priority determination, tool calling must prioritize processing associated historical defect and test case data.

## How to configure the settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `toolChoice` | auto | Allows the model to independently determine whether to call tools for tasks related to defect analysis and regression testing |
| `functionCall` | limited to the two scenarios of defect priority determination and regression verification | Focuses on core business links to avoid resource consumption from irrelevant tool calls |
| Tool call trigger timing | daily scheduled or 1 hour before each version release | Matches the daily or per-version update frequency of data, ensuring the called data is up to date |
| Single recall limit | top 10 entries | Controls the number of data source entries returned by the tool to avoid exceeding the context processing threshold |
| Similarity threshold | 0.75–0.85 | Filters associated data matching the current defect description and test cases |
| Knowledge base matching trigger condition | call when more than 3 relevant entries are matched | Reduces invalid tool calls and improves analysis efficiency |

## Three common misconfigurations
- The phenomenon is that GPU memory usage grows rapidly after calling the rearrangement model, and each GPU occupies relatively high resources. The cause is that the concurrency number and trigger frequency of tool calls are not restricted, causing the model to be called frequently and not releasing memory resources in time.
- The phenomenon is that the tool call returns empty results or results unrelated to the current defect. The cause is that reasonable similarity thresholds and recall limits are not set, resulting in recall of too many low-correlation historical defect data.
- The phenomenon is that the tool call trigger timing is not synchronized with data updates, causing analysis to use expired defect tickets or regression checklists. The cause is that the trigger timing is not bound to version release nodes or daily scheduled tasks.

## How to verify the configuration is correct
- View tool call logs to confirm that the trigger timing matches the data update rhythm, and verify that the version of the returned data is consistent with the current business version.
- Simulate call requests for different defect scenarios to confirm that the tool is only triggered within preset business links, and no unexpected calls occur.
- Adjust the values of configuration items, and check that the number and relevance of tool returned entries meet the configuration requirements.
- Monitor resource usage to confirm that the resource occupation of tool calls complies with preset allocation rules.

The values provided are common starting points and should be measured against the reader's own samples.
