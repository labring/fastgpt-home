# Test Cases and Defect Analysis for Landing Page Conversion Optimization: Tool Calling and Plugins

## Data Profile for This Category
The data for this category mainly comes from landing page access logs, heatmaps, form data, and ad source parameters. The update frequency is weekly or after a single campaign ends. Daily produced documents include landing page plans, buried point requirement lists, AB test reports, and form field configuration tables. Data fields include page dwell time, number of jump path nodes, number of form submissions, ad source identification values, and more. There is no unified standardized field format, and separate mapping is required based on campaign scenarios.

## Constraints Imposed by These Characteristics on the Tool Calling and Plugins Workflow
Multi-source data requires tool calling to support cross-data source parameter parsing and integration, preventing field mismatch issues.
Weekly or campaign-level update cycles require tool calling cache and pull cycles to match the campaign cycle, avoiding data lag or repeated pulls.
Non-standardized document and field formats require tool calling to bind configuration mapping rules for the corresponding campaign, ensuring parsed fields meet current landing page optimization scenario needs.
Errors can lead to lead loss, inability to attribute data, or increased ad costs. Tool calling must be configured with failure retry and log retention mechanisms.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `toolChoice` | Set to `auto` and bind the dedicated landing page conversion optimization toolset | Adapt to multi-data source calling requirements, automatically match analysis tools for the current campaign |
| `functionCall` | Enable field mapping mode | Ensure that business fields related to landing pages are correctly parsed during tool calling, matching configuration requirements in documents |
| Tool call timeout setting | 600 seconds | Match the long-cycle data pull requirements of landing page analysis, avoid calling failures caused by log pull delays |
| Local tool file upload limit | 1000 MB | Adapt to the conventional campaign data volume of landing page materials and log files, cover most scenario requirements |
| Workflow upload parameter binding | Associate with variable identifiers configured per campaign | Ensure that uploaded files can be linked to scenario parameters for the corresponding campaign, support dynamic file calling |

This document applies to FastGPT v4.17.0.

## Three Common Misconfigurations
- Calling an MCP tool returns an "insufficient tool permissions" error. The cause is that the calling scope of the corresponding tool is not configured in `toolChoice`, resulting in inability to access the data source interface required for landing page analysis.
- Calling times out after being published as an API interface. The cause is that the default timeout setting is not adjusted, and the long-cycle requirement for landing page data pulling exceeds the default threshold.
- Uploaded files in custom workflows cannot reference variables. Only static link uploads are supported, and files up to 2 MB are restricted by default. The cause is that the variable binding rules and file size threshold for workflow upload parameters are not configured.

## How to Verify Configurations Are Correct
- Call the test tool, check that the returned results include expected fields such as landing page access logs and form submission data, confirm that field mapping is effective.
- View tool call logs, confirm that the timeout setting is 600 seconds, and no frequent timeout errors occur, verify that the timeout configuration is effective.
- Test the workflow upload function, select a local file and bind the campaign variable, confirm that the file can be uploaded normally and linked to the corresponding scenario parameters.
- After starting the local MinerU container, view the container configuration parameters, confirm that the file upload limit has been adjusted to the target value, verify that the configuration is effective.

The values provided are common starting points and should be measured against the reader's own samples.
