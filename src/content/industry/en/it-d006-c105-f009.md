# Test Cases and Defect Analysis for License Compliance and Copyright Notices: Tool Calling and Plugins

## What Data Falls Under This Category
The core data for this category centers on documents related to code usage and distribution rights. Sources include project code repositories, third-party dependency lists, official license texts, and contributor submission records. Standardized documents produced regularly include the root directory LICENSE file, NOTICE statement file, dependency license list, and project copyright statement. Data updates are triggered by project version iterations or third-party dependency changes, with no fixed cycle. Updates must be synchronized alongside code and dependency changes to cover compliance document management needs across the full lifecycle of open source projects.

## Constraints Imposed on Tool Calling and Plugins
Because data sources are scattered and need to match multiple license text formats, tool calling must support multi-source data pulling and format validation to avoid field mismatch errors. Dependency list update frequency is not fixed, so plugins must support on-demand data synchronization to adapt to irregular dependency changes. Copyright ownership data comes from contribution records, so the tool must support associating commit hashes with contributor information to ensure accurate traceability. Field differences vary across different licenses, so tool calling must adapt to multiple document structures to avoid validation failures due to format incompatibility. The FastGPT v4.17.0 plugin framework supports the above flexible configuration requirements.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| ---|---|--- |
| `toolChoice` | `auto` | Adapts to automatic identification requirements for multiple types of compliance documents, no manual specification of tool type required, and aligns with the tool calling logic of FastGPT v4.17.0 |
| `functionCall` | `enabled` | Supports structured calling of tools such as license validation and dependency list generation, ensuring output formats meet standardized compliance document requirements |
| Single tool call timeout | `120–180 seconds` | Requires pulling data from multiple sources (code repositories, dependency lists); the timeout range covers conventional data pulling durations, calibrated based on actual testing |
| Tool call result cache duration | `24 hours` | Dependency list update frequency is not fixed; caching for 24 hours balances data timeliness and call overhead |
| Plugin input parameter validation rules | Match LICENSE and NOTICE file formats | Ensures input data aligns with the document structure of this category, avoiding invalid calls |

## Three Common Mistakes
- Symptom: The data link tool call returns an `SQL syntax incompatible` error. Cause: The SQL query statement was not written according to the field format of the dependency list, so compliance data cannot be pulled correctly.
- Symptom: The dependency license list is empty after plugin execution. Cause: On-demand data synchronization was not configured, and fixed polling caching was used instead; the latest third-party dependency change data was not pulled in a timely manner.
- Symptom: The JSON input box cannot select preset variables. Cause: Variables were not bound as optional parameters for plugin input; the input box was only configured as static JSON format, and the variable mapping function was not enabled.

## How to Confirm the Configuration Is Correct
- Trigger a tool call, check that the returned results include a complete dependency license list and copyright ownership information, with no missing fields.
- Simulate a third-party dependency change, trigger plugin execution, and confirm that the cached data updates automatically without manual refresh.
- View the plugin configuration logs, confirm that the `toolChoice` and `functionCall` parameters have taken effect as preset values, with no abnormal errors.
- Input test data in non-compliant document formats, confirm that the plugin triggers parameter validation errors and blocks invalid calls.

The values provided are common starting points and should be measured against the reader's own samples.
