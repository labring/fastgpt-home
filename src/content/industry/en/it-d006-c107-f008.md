# Test Cases and Defect Analysis for Account Ban and Appeal Review: Workflow Orchestration

## What Data for This Category Looks Like
Core data for this category originates from risk control systems, audit records, user behavior logs, and report evidence. Updates occur primarily in real time or on a daily basis. Daily produced documents include account ban records, appeal materials, review opinions, and user notifications. Typical fields include unique account identifier, violation type tag, appeal submission time, review result, and disposal level. No mandatory unified statistical units exist. Only violation and appeal data linked to a single account is recorded for each business scenario.

## What Constraints Do These Characteristics Impose on Workflow Orchestration
Real-time data requirements mean workflow triggers must align with the user’s appeal submission time window, to avoid excessive delays harming user experience. Multi-source data requires workflow configuration to include cross-system node aggregation, ensuring association and matching of ban records, appeal materials, and report evidence. Account-level business attributes require the workflow to bind a unique account identifier throughout, preventing cross-account process confusion. Error consequences such as false bans and returning of violating accounts require the workflow to add pre-check and review nodes, ensuring the accuracy of disposal logic.

## How to Set the Configuration
This page applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Workflow Trigger Timing | Within 10 seconds after a user submits an appeal | Matches real-time appeal data windows to avoid delayed processing |
| `variables` Bound Fields | Account ID, violation record ID, appeal material URL | Corresponds to core identifier fields in this category’s data, ensuring the process associates with correct business data |
| `nodeId` Specified Call Nodes | Pre-check node, evidence verification node | Splits the process by business links, avoiding excessive load on a single node |
| Timeout Threshold | 300 seconds | Meets reasonable user appeal waiting time, avoiding unresponsive processes |
| Batch Processing Limit | Top 20 pending review appeals | Matches daily single-batch appeal processing scale, avoiding node resource overload |
| Retry Count | 2 times | Handles temporary interface fluctuations, reducing invalid process interruptions |

## Three Common Mistakes
- When a non-24-digit hexadecimal character string is entered for the workflow ID, calling the workflow returns a 400 status code. The cause is that the system’s format check for the workflow identifier failed.
- An axioserror occurs when a code node sends an external request. The cause is that the correct API access key is not configured, or the target interface does not have the corresponding permissions enabled.
- In the locally deployed workflow configuration interface, text input lags when there are too many nodes. The cause is that the front end did not enable node list pagination loading, rendering too many DOM elements at one time.

## How to Verify Correct Configuration
- Submit a simulated appeal, check whether the workflow monitoring panel triggers execution within 10 seconds.
- Export the workflow run logs, check whether the `variables`-bound account ID and violation record ID fields are carried normally.
- Simulate a node timeout, verify whether the process automatically retries according to the configured retry count.
- In the locally deployed environment, drag the node list scroll bar, confirm that there is no obvious lag in the page input boxes.
