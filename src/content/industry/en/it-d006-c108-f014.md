# Warranty Defect Response Test Cases and Defect Analysis: Model Integration and Configuration

## What this category of data looks like
Data for this category typically comes from customer tickets, operation logs, contract warranty clauses, and system version records. Update frequency is daily or upon completion of each order task. Daily used documents include warranty work orders, defect confirmation sheets, repair records, and customer confirmation sheets. Typical users are after-sales engineers, project managers, and R&D support staff. Data fields usually include defect identification, responsible party determination, repair progress, customer feedback status, and require adaptation to multi-source heterogeneous document structures.

## What constraints do these characteristics impose on model integration and configuration
Multi-source, high-frequency update data requires model integration configuration to support flexible context stitching. This prevents analysis failure caused by missing fields or format mismatches. Fixed daily document structure requires configuration to match specific field extraction rules. This ensures the accuracy of responsibility boundary judgment and repair plan generation. Errors in this category directly affect warranty disputes and customer renewal. Therefore, configuration must include failure retry and log retention mechanisms to guarantee task closure. FastGPT v4.17.0’s model integration framework must adapt to docker compose-deployed vllm inference services. It must strictly match port and interface path configuration requirements to avoid deployment scenario incompatibility.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the context length requirements of multi-document stitching such as warranty work orders and defect confirmation sheets, preventing loss of key warranty clause information due to context overflow |
| `maxTokens` | 2000–3000 token | Meets the output length requirements for defect analysis and responsibility judgment, preventing generated content from being truncated |
| `temperature` | 0.3–0.5 | Reduces randomness, ensures consistency of responsibility boundary judgment and repair plan recommendations, and matches the rigor requirements of warranty services |
| `AIPROXY_API_ENDPOINT` | http://aiproxy:3000 | Root address of the AI Proxy service. Do not append /v1 or model interface paths. Must match the deployment address of the AI Proxy server |
| `AIPROXY_API_TOKEN` | Consistent with the administrator token configured on the AI Proxy server and non-empty | Acts as the identity verification credential for the AI Proxy service. Do not use model vendor keys or application API Keys as replacements |

## Three common mistakes
- Model calls return a 404 status code, and the interface displays model connection failed. Troubleshooting: Check if `AIPROXY_API_ENDPOINT` has /v1 or model interface paths appended, or if it is configured as a single model deployment address instead of the AI Proxy root address.
- Knowledge base retrieval takes too long, with a single defect analysis task waiting more than 60 seconds. Troubleshooting: Check if the `maxContext` configuration value is reasonable, and verify if context loading overhead is linked to the configuration value.
- Distilled deepseek access fails, returning a model format unsupported error during calls. Troubleshooting: Check if `AIPROXY_API_ENDPOINT` is configured as the AI Proxy service root address instead of a single model deployment address; check if the model channel configuration correctly matches the parameter format of distilled deepseek.

## How to confirm the configuration is complete and correct
- Check the environment variable configuration of the App/Admin server, confirm that `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are correctly configured and non-empty.
- Import a single warranty work order for retrieval testing, check if the number of returned related documents meets expectations, with no excessive redundant data.
- View system operation logs, confirm that the model call request address and token parameters match the configured values, with no missing or incorrect parameters.
- Simulate submitting a defect confirmation sheet, check if the generated repair plan recommendations meet the rigor requirements of warranty services, with no obvious logical deviations.
