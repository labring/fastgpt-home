# Test Case and Defect Analysis for Incident Management and Root Cause Analysis: Model Integration and Configuration

## What the data for this category looks like
Data for this category originates from incident timelines, system operation logs, monitoring metrics, and code commit records. Daily deliverables include root cause analysis (RCA) reports, incident tickets, review minutes, and rectification tracking forms. Each major incident triggers data updates, with monthly summary reviews. Document fields include incident occurrence time, root cause location description, associated test case ID, defect number, rectification measures, and closure status. Each field must align one-to-one with the original incident data.

## Constraints on Model Integration and Configuration From These Data Characteristics
Data for this category spans the full range from short incident tickets to complete RCA reports, with significant variation in individual data entry lengths. Data updates are unplanned; model calls must complete quickly when major incidents occur, placing high demands on interface response stability. Document fields include multiple types of associated information, so the model must accurately identify mapping logic between fields to avoid mixing up associations between test cases and defects. Monthly summary batch data processing requires configurations that support batch calls and context segment adaptation, preventing overload from single requests.

## How to Configure the Model
This document applies to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | This category of data contains multiple segments of associated logs and RCA reports, requiring sufficient context to associate full incident chain information and avoid truncation of critical associated content |
| `maxTokens` | `2000–3000 token` | Output for root cause analysis and test case matching must cover complete conclusions and associated items to avoid missing rectification suggestions due to truncated output |
| `temperature` | `0.2–0.4` | Root cause analysis requires maintaining conclusion rigor, avoiding randomly generated irrelevant assumptions, to match the rigorous business requirements of incident management |
| `quoteMaxToken` | `500–800 token` | Original logs or incident timeline fragments must be cited as root cause evidence, controlling the length of single citations to ensure context coherence |
| `toolChoice` | `auto` | Automatically select whether to call the associated test case retrieval tool based on input, adapting to different types of incident ticket scenarios |
| `AIPROXY_API_ENDPOINT` | `http://aiproxy:3000 (AI Proxy service root address, do not append paths such as /v1 or /chat/completions, do not point to a single model service address)` | Ensure correct model request routing, avoid request failures caused by routing exceptions |

## Three Common Configuration Errors
- Phenomenon: A 405 error is returned when calling an OpenAI-compatible interface or a model deployed via Xinference. Troubleshooting: Check if the server environment variable `AIPROXY_API_ENDPOINT` is configured as the root address of the AI Proxy service, without appended paths such as /v1 or /chat/completions, and not pointing to a single model service address.
- Phenomenon: The root cause analysis output from the model has low relevance to the original incident data. Troubleshooting: Check if the `maxContext` configuration value is too small, resulting in truncation of critical incident timelines or log fragments.
- Phenomenon: Request timeouts occur when processing monthly review data in batches. Troubleshooting: Check if the `maxTokens` or `maxContext` configuration values are adapted to the batch data length, ensuring the data volume carried by a single request does not exceed the model interface limits.

## How to Verify Successful Configuration
- Initiate a single incident ticket root cause analysis request, check the interface return status code, confirm a 200 status code and no routing or authentication errors.
- Check the model output content, confirm that matching results including associated test case IDs and defect numbers are present, with no obvious context truncation.
- Initiate a test call for batch monthly data, confirm that the interface has no continuous timeouts or request rejections.
- Verify that the server environment variables `AIPROXY_API_TOKEN` (AI Proxy administrator token, consistent with the AI Proxy server configuration and not empty) and `AIPROXY_API_ENDPOINT` (AI Proxy service root address, no paths appended) have configuration values consistent with the information provided by the deployment service provider.

The values provided are common starting points and should be measured against the reader’s own sample data.
