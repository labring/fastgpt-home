# Integration Testing and API Testing Test Case and Defect Analysis: Model Access and Configuration

## What data for this category looks like
Data sources include API management platforms, test environment logs, databases, and message queues. Update frequency is daily or during each version iteration. Daily output documents include API test cases, commissioning issue tickets, environment descriptions, and test reports. Data fields include API endpoints, request parameters, response status codes, defect association identifiers, and test environment identifiers. There are no additional statistical fields, and all data is generated around the verification process of cross-module interactions.

## What constraints these characteristics impose on the "model access and configuration" link
Multi-source heterogeneous data sources require configuring unified parsing and adaptation rules during access, to avoid model recognition deviations caused by logs and case formats from different sources. High update frequency requires configuring appropriate context length parameters to adapt to daily or version-level data increments. The fixed document field structure requires clearly specifying extraction rules when calling the model, to ensure that key information such as API endpoints and response status codes can be accurately associated during defect analysis. At the same time, the link attribute of test data requires configuring tool call-related parameters to support cross-module problem location.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to daily updated API test cases and commissioning logs, prevents loss of critical test data due to context overflow |
| `maxTokens` | 2000–3000 token | Meets the full output requirements for API response content and defect descriptions, prevents truncation of critical error information |
| `temperature` | 0.2–0.4 | Reduces random generation probability, ensures consistent and accurate output of information such as API parameters and status codes during defect analysis |
| `toolChoice` | auto | Supports automatic tool calls to locate API link issues, adapts to cross-module verification requirements for integration testing |
| `AIPROXY_API_ENDPOINT` | Fill in the root address of the AI Proxy service according to the deployment environment, for example http://aiproxy:3000. Do not append paths such as /v1 or /chat/completions | Ensures that the App/Admin server can correctly route the AI Proxy service |
| `AIPROXY_API_TOKEN` | Administrator Token consistent with the AI Proxy server configuration, and cannot be empty | Used for identity verification when the App/Admin server calls the AI Proxy service, prevents unauthorized access |

## Three common mistakes
- Symptom: Returns 404 page not found or connection failure when calling model-related APIs. Troubleshooting step: Check if `AIPROXY_API_ENDPOINT` is configured with the correct root address of the AI Proxy service, with no extra paths appended.
- Symptom: The model's classification results for issue categories have large deviations. The cause is that the `temperature` parameter is not configured or the value is too high, leading to unstable generated classification rules.
- Symptom: Key fields are empty after parsing API test cases. The cause is that the `maxContext` parameter is not set, leading to context being truncated due to excessive length, and core information such as API addresses and request parameters is lost.

## How to confirm the configuration is complete
- Submit a known API test case, check if the defect analysis result returned by the model includes expected fields such as API endpoints and response status codes.
- View the AI Proxy server logs, confirm that the call requests from the App/Admin server pass verification, and there are no errors related to unauthorized access.
- Trigger a model classification task for a commissioning issue ticket, check the field completeness and accuracy of the result.
- Adjust the `maxContext` parameter and submit large-volume test data, confirm that there are no errors related to context overflow.

The values provided are common starting points and should be measured against the reader's own samples.
