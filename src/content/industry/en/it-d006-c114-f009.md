# Test Case and Defect Analysis for Requirement Analysis and PRD Management: Tool Calling and Plugins

## Data Overview for This Category
This category of data primarily comes from requirement research notes, PRD documents, user story lists, and requirement change forms. Data sources include customer interview records, internal ticket systems, public competitor pages, and business burying point dashboards. The update frequency is typically synchronized weekly or during each version iteration. Document structures include fields such as business goal definition, acceptance criteria description, boundary condition sorting, and requirement change tracking. There is no unified mandatory format, but association with corresponding business modules and test-related items is required.

## Constraints Imposed on Tool Calling and Plugins
The multi-source data nature of this category requires tool calling to adapt to multiple document formats, to prevent data extraction failures caused by supporting only a single PRD template.
The high-frequency update rhythm requires plugins to support real-time synchronization of the latest requirement change records, otherwise test cases will become disconnected from actual requirements.
Non-standardized document fields require that tool calling parameters support custom field mapping, and cannot rely on fixed field extraction logic.
Additionally, association with test link data is necessary; plugins must connect the association chain between requirement documents and defect tickets to ensure test cases align with requirement acceptance criteria.

## Configuration Settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Adapt to multiple types of content in requirement documents, automatically trigger plugin calls |
| `functionCall` | Set based on actual testing | Adapt to non-standard fields in requirement documents, flexibly match business parameters |
| Number of plugin calls per single run | First 5 entries | Match the content length of single modules in requirement documents, avoid context overflow |
| Plugin timeout threshold | 60–90 seconds | Adapt to the extraction complexity of requirement data, balance response speed and completeness |
| Field mapping rules | Customize according to document templates | Adapt to differences in PRD formats across different teams, ensure accurate association of test data |
| Context synchronization frequency | Each version iteration | Match the update rhythm of requirements, avoid disconnect between test cases and requirements |

## Three Common Misconfigurations
- Workflow verification fails with the prompt "Missing configuration item": The cause is that the field mapping rule is not configured, causing the plugin to fail to recognize the acceptance criteria fields in the PRD.
- Tool calling response times out, with a duration exceeding 10 seconds: The cause is that the plugin timeout threshold is set too short, unable to complete batch extraction of multi-source requirement documents.
- Plugin call results do not match actual requirements: The cause is that `toolChoice` is fixed to `none`, so plugin calls are not triggered, and only generic content generated by the large model is used.

## How to Confirm Configuration Is Complete
- Upload a standard PRD document, trigger tool calling, and check whether business goal and acceptance criteria fields can be extracted.
- Simulate a requirement change operation, check whether the plugin can synchronize and update associated test case data.
- View the plugin call log, confirm that the `toolChoice` parameter trigger logic complies with the configuration requirements.
- Adjust the plugin timeout threshold, verify whether reasonable failure handling is triggered when the call duration exceeds the threshold.
