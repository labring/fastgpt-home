# Test Case and Defect Analysis for Requirements Analysis and PRD Management: Citation Sources and Traceability

## What this category’s data looks like
The typical users of this category are internet product teams, business analysts, and product managers. Daily produced documents include requirement research notes, PRDs, user story lists, and requirement change forms. Fields per document include business objectives, acceptance criteria, change records, and more. Data sources cover customer interview records, ticketing systems, public competitor pages, and analytics dashboards. Update frequency is usually weekly or per version iteration. The most time-consuming steps are organizing interview information, confirming boundary conditions, and synchronizing requirement changes. Incorrect traceability information may lead to development rework, schedule delays, or acceptance disputes. Unlike prototyping and interaction design categories, this category first defines business objectives and acceptance criteria before proceeding with subsequent steps.

## Constraints imposed by these characteristics on the citation sources and traceability process
The multi-source data and diverse document structures of this category require that the citation traceability process must accurately match the fields and formats of different documents to avoid confusion between different types of requirement documents. The weekly or per-version update rhythm requires that the traceability system regularly refreshes the latest versions of data sources to ensure that cited content aligns with current requirement statuses. The serious consequences of errors require that traceability information includes clear source identifiers and paths to enable quick problem location. Additionally, multi-source unstructured data such as interview records and analytics dashboards require that the traceability process supports cross-type data source association verification to prevent low-quality data from being included in cited content.

## Configuration settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | `800–1200 token` | Matches the average content length of requirement research notes and PRDs to avoid truncating critical acceptance criteria |
| `responseData` | Return only source metadata | Reduces response redundancy and focuses on traceability information for requirement documents |
| `detail` | Full source path | Supports locating specific requirement change forms or user story entries |
| Maximum traceability entries | `Top 3–5 entries` | Matches the field density of daily documents to avoid excessive sources interfering with test case writing |
| Document type filter | Include only requirement research notes, PRDs, and user story lists | Filters non-category-related data sources to improve traceability accuracy |
| Update trigger cycle | Trigger weekly | Aligns with the weekly or per-version update rhythm of the category to ensure timeliness of traceability data |

## Three common configuration errors
- Phenomenon: After configuring the minimum relevance threshold, a large number of non-matching cited content is still returned. Cause: Precise source filtering rules are not configured for the category’s document types, resulting in accidental recall of low-relevance public competitor pages or analytics data.
- Phenomenon: Traceability links cannot open Notion-format requirement documents normally. Cause: Corresponding data source adaptation rules are not configured, and permission verification and jump format support for Notion links are not enabled.
- Phenomenon: Cited requirement change forms do not sync the latest version content. Cause: The automatic refresh cycle for traceability data is not configured according to the weekly or per-version update rhythm of the category, resulting in lagging traceability information.
