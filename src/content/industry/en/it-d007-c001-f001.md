# Online Troubleshooting and Retrospective for CDN and Edge Acceleration Configuration: HTTP Interfaces and External Systems

## What the data for this category looks like
Data sources for this category typically include CDN consoles, DNS resolution records, user access logs, and monitoring alert information. Updates occur either daily or in real time when configuration changes are made. Daily generated documents include domain name access forms, cache rule configuration tables, refresh and preheating operation records, and fault analysis reports. Common fields include domain name, cache TTL, node IP, request status code, and cache hit rate. There is no unified mandatory format, and adjustments must align with the interface specifications of the specific CDN service provider.

## What constraints these characteristics impose on HTTP Interfaces and External Systems
Data sources are scattered and update cadences vary. HTTP interfaces must support integration with multiple data sources and adapt to different update frequencies. For example, interfaces must simultaneously support real-time pulling of monitoring alerts and batch querying of historical access logs. Differences in fields across daily documents require interface parameters to support custom filter conditions. This matches troubleshooting needs across different scenarios. The most time-consuming cache rule debugging phase requires interfaces to quickly query and modify cache configurations. This reduces manual operation time costs. Errors directly impact public network access experiences. Interfaces must have anomaly alert linkage capabilities to trigger troubleshooting workflows promptly.

## How to set configurations
This document is written based on the configuration logic of FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${CDN_API_TOKEN}` | Aligns with official CDN API authentication standards to prevent interface call failures caused by unauthorized access |
| `variables` | `{"domain": "your-cdn-domain.com", "logTimeRange": "last_24h"}` | Narrows the query scope to accurately locate fault-related data for the target domain, and matches common parameters used in CDN log queries |
| `responseData` | `["status_code", "hit_rate", "node_ip"]` | Returns only fields required for fault troubleshooting, reduces unnecessary data transmission, and improves troubleshooting efficiency |
| Interface timeout threshold | 30-60 seconds | Adapts to typical response durations of CDN interfaces, avoids long-term blocking of fault troubleshooting workflows |
| Cache rule synchronization interval | 5 minutes | Matches the typical update frequency of cache rules in CDN consoles, ensures that configuration information obtained via the interface remains consistent with the console |

## Three common mistakes
- Interface calls return a 401 unauthorized error. The cause is incorrect configuration of the `Authorization` parameter, using an expired API token or one without the required permissions.
- Cache refresh records are not synchronized after a Webhook is triggered. The cause is that the correct target domain is not configured in the `variables` parameter, so the interface cannot locate the corresponding CDN resources.
- CDN access logs cannot be pulled during local debugging. The cause is that local network access permissions for the CDN console API are not enabled in the external system configuration, and a reasonable log query time range is not specified.

## How to confirm that the configuration is complete
- Call the configured HTTP interface. Check whether the returned `responseData` fields include expected fault troubleshooting-related data, such as request status codes and node IPs.
- Manually trigger a cache refresh operation. Confirm that the interface can synchronously return the corresponding refresh and preheating records that match the operation records in the CDN console.
- Simulate an abnormal request. Confirm that the interface can trigger preset alert rules and synchronize alert information to the external system.
- Compare the cache hit rate data returned by the interface with real-time monitoring data in the CDN console. Confirm data consistency, and adjust filter parameters to match the actual business scenario.
