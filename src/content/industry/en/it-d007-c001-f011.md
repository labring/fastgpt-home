# Online Troubleshooting and Retrospective for CDN and Edge Acceleration Configuration: Database and Operations

## What Data for This Use Case Looks Like
CDN and edge acceleration configuration data primarily comes from CDN consoles, DNS resolution records, user access logs, and node monitoring alerts. Daily maintenance documents include domain name access tickets, cache rule configurations, refresh and preload records, and fault analysis reports. Data is updated daily or after each configuration change. Fields include domain names, cache TTL, edge node IP addresses, request response codes, traffic volume, and more. Content is generated based on actual business requirements, with no fixed statistical standard.

## What Constraints These Characteristics Impose on Database and Operations
Decentralized multi-source data requires databases to support structured storage and retrieval of multiple data types. High-frequency update and query demands require properly configured connection pools and timeout thresholds. Diverse document types require databases to support both structured and unstructured storage capabilities. The timeliness of anomaly troubleshooting requires controllable database query latency to avoid impacting fault localization efficiency. Additionally, frequent configuration changes require databases to support rapid configuration updates and rollback operations to adapt to daily cache rule debugging and domain name access processes.

## How to Configure Settings
This guide is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum database connection pool size | `150–250 connections` | Adapts to concurrent query demands of CDN workloads, avoids database connection exhaustion or excessive load |
| MongoDB connection address | Standard connection string containing cluster nodes and authentication details, such as `mongodb://admin:pass@cdn-db-1:27017,cdn-db-2:27017/cdn_logs?replicaSet=rs0` | Stores CDN access logs and cache rule data; cluster configuration ensures data availability during fault troubleshooting |
| PostgreSQL connection address | SSL-encrypted configuration connection string, such as `postgresql://cdn_user:secure_pass@cdn-config-db:5432/cdn_config?sslmode=require` | Stores structured documents including domain name access tickets and fault analysis reports; SSL encryption prevents sensitive configuration leaks |
| Redis cache address | Authenticated cluster connection string, such as `redis://cdn-redis:6379/1?password=secure_redis_pass` | Caches popular DNS resolution results and short-expiration cache rules, reducing high-frequency query pressure on databases |
| Query timeout threshold | `30 seconds` | Ensures real-time performance for anomaly node troubleshooting; timeouts will hinder rapid fault localization |
| Database backup cycle | Daily early morning | Ensures historical data is traceable during fault troubleshooting, preventing data loss from impacting retrospectives |

## Three Common Mistakes
- Symptom: Cannot select the Oracle type in the database connection module. Cause: The current version does not include the Oracle database driver, only database connections of specified types are supported for configuration.
- Symptom: Running `pnpm dev` during local development environment deployment shows MongoDB connection timeout. Cause: The local address for `MONGODB_URI` was not configured correctly, or firewall rules blocked traffic on the default MongoDB port 27017.
- Symptom: Database tool calls return a 400 status code with no response body. Cause: The database connection string parameter format is incorrect, or the maximum connection pool size was set too low, leading to connection exhaustion.

## How to Verify Successful Configuration
- Run the built-in database connectivity detection tool in FastGPT to verify that all configured database connections are working properly.
- View the real-time monitoring panel in the CDN console to confirm that database query QPS and connection counts fall within the configured connection pool range.
- Submit a test domain name access ticket to verify that the configured storage and retrieval workflows are functioning normally.
- Simulate a query for anomaly node troubleshooting to confirm that the returned result timeliness meets business requirements.

The values provided are common starting points and should be measured against the reader's own samples.
