# Online Troubleshooting and Retrospective for IT Service Desk Ticket Handling: Database and Operations

## What this category of data looks like
Data sources for this category include enterprise ITSM systems, phone or online chat logs, asset ledgers, and internal knowledge bases. Four types of documents are routinely generated: service requests, incident tickets, processing records, and user satisfaction surveys. Data fields include unique ticket identifiers, submitting user information, problem classification tags, processing progress, response time, satisfaction scores, and more. Data updates occur daily or in real time, and are synchronized alongside ticket flow and processing actions.

## What constraints do these characteristics impose on database and operations workflows
The data sources for this category are scattered, covering multiple heterogeneous systems, requiring database configurations that support multi-source data access interfaces. Real-time update rhythms require database connection pools to support high-concurrency read and write operations, avoiding write blocking during ticket flow. Associated query requirements for tickets and satisfaction surveys require database table structure designs that support cross-table associations and fast retrieval. At the same time, storage security of ticket data and user information must be ensured, and compliance with enterprise internal data management regulations must be met.

## How to set configurations
All following configurations are compatible with FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://admin:yourpass@localhost:27017/fastgpt_itsm?authSource=admin` | Adapts to unstructured storage requirements for ticket data, and supports multi-source data access |
| `PG_URL` | `postgresql://postgres:yourpass@localhost:5432/itsm_metadata?sslmode=require` | Used to store structured ticket fields and associated data, supporting cross-table queries |
| `DB_MAX_LINK` | `20–50` | Matches the daily or real-time update rhythm of this category, avoiding excessive database load caused by too many connections |
| `REDIS_URL` | `redis://:yourredispass@localhost:6379/0` | Used to cache frequently queried ticket classification rules and user-favorite knowledge base entries, reducing database pressure |

## Three common misconfigurations
- Symptom: Connection to the local FastGPT MongoDB database via MongoDB Compass fails, with a timeout or authentication failure prompt. Cause: The username, password, and authentication source parameters in `MONGODB_URI` are not configured correctly, or the local firewall blocks access to port 27017.
- Symptom: FastGPT fails to start normally after Docker deployment, with a database connection error prompt. Cause: The connection parameters for `MONGODB_URI` or `PG_URL` were not modified correctly in the deployment configuration, preventing the program from reading ticket and system data.
- Symptom: Ticket processing records fail to sync updates, and query results return empty. Cause: `DB_MAX_LINK` is set too low, depleting the database connection pool and preventing processing of real-time ticket update requests.

## How to confirm correct configuration
- Run a database connection test command to verify that the parameters for `MONGODB_URI` and `PG_URL` can successfully establish a connection.
- Submit a test ticket, check whether the corresponding ticket record is generated in the database, and confirm that data writes function normally.
- View Redis cache monitoring metrics to confirm that the cache service configured via `REDIS_URL` responds to requests normally.
- Check database connection pool runtime logs to confirm that the `DB_MAX_LINK` setting does not trigger connection exhaustion errors.

The values provided are common starting points and should be measured against the reader's own samples.
