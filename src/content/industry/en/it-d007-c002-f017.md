# Online Troubleshooting and Retrospective for IT Service Desk Ticket Handling: Deployment and Upgrade

## What the data for this category looks like
Data for this category comes from enterprise ITSM systems, phone or chat records, asset systems, and internal knowledge bases. Update frequency is daily or real-time, synchronized with ticket creation, routing, and completion. Daily documents include service requests, incident tickets, processing records, and user satisfaction forms. Core fields include ticket number, problem category, processing status, response time limit, dispatch records, and satisfaction scores. The data structure adjusts dynamically based on the ticket routing stage.

## What constraints these characteristics impose during deployment and upgrade
Dispersed data sources require connecting multiple system interfaces during deployment, with corresponding storage connection parameters configured separately. Real-time update frequency requires reserving sufficient concurrent processing resources during deployment to avoid ticket routing lag. Multiple types of document structures require retaining downward-compatible field mapping rules during upgrades to prevent unreadable old tickets. Fixed formats for core fields require configuring permission verification parameters during deployment to prevent sensitive ticket data leaks. As a unified enterprise technical support entry, load balancing-related parameters must be configured during deployment to ensure stability for multi-terminal access.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://it_user:it_pass@internal-db:27017/it_service_desk?authSource=admin` | Adapt to persistent storage of ITSM system ticket data, matching enterprise internal MongoDB instance configuration |
| `PG_URL` | `postgresql://asset_user:asset_pass@internal-pg:5432/it_assets` | Store structured data such as processing records and user satisfaction forms, compatible with PostgreSQL format of enterprise asset systems |
| `REDIS_URL` | `redis://:redis_pass@internal-redis:6379/0` | Cache real-time ticket routing status and dispatch queues. Connection timeout is recommended to be set to 300 seconds |
| `FE_DOMAIN` | `https://it-support.company.com` | Configure the access domain name for embedded web pages to resolve cross-domain permission verification issues |
| `FILE_TOKEN_KEY` | `Randomly generated 32-bit hexadecimal string` | Used for permission verification of ticket attachments and knowledge base documents, matching the permission logic of embedded sharing |
| `DB_MAX_LINK` | `20–50 connections` | Adapt to concurrent access requirements of average daily ticket volume, avoiding database connection exhaustion |

## Three common mistakes
- A `permission denied` error is prompted when the embedded web page calls the speech recognition function. The cause is that the `FE_DOMAIN` parameter is not correctly configured, and the domain name of the embedded web page is not added to the allowed access list.
- Uploaded files cannot be read during local deployment. The cause is that the `FE_DOMAIN` parameter is filled incorrectly, and does not match the local access domain name or port.
- The WSL2 container fails to start on Windows, with an error prompt related to `mkdir /run/destop/mnt/host/wsl/dock`. The cause is missing mount directory permission configuration, and no directory creation and permission assignment steps are added in the deployment script.

## How to confirm proper configuration
- Use the official FastGPT v4.17.0 image to run the `docker-compose ps` command, check the running status of all service containers, and confirm there are no abnormal exits.
- Access the domain name configured in `FE_DOMAIN`, try to create and submit a test ticket, and confirm that ticket data can be written to the corresponding database normally.
- Generate an embedded sharing link, embed it in a test web page and call the function, and confirm that no permission error prompts appear.
- Check the system log file, confirm that the number of database connections does not exceed the threshold configured in `DB_MAX_LINK`, and there are no connection timeout error reports.

The values provided are common starting points and should be measured against the reader's own samples.
