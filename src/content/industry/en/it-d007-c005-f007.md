# Online Fault Troubleshooting and Retrospective for Issue Triage and Response: Conversation Logs and Auditing

## What this category of data looks like
Data for this category primarily originates from GitHub or Gitee Issues, code repository version logs, environment information reported by users, and problem reproduction descriptions. Daily maintained documents include Issue submission templates, tag rule libraries, historical reply records, and problem reproduction process instructions.
Data is updated on a daily or weekly basis. Core fields include Issue number, problem classification tags, reproduction steps, and associated code submission records. Units are primarily entries, characters, and timestamps. This data supports daily triage and response work for open-source maintainers, community operations, and core contributors.

## What constraints do these characteristics impose on the "conversation logs and auditing" link
Data sources are scattered across multiple platforms and documents. Conversation log auditing must cover the full chain of Issue interactions and associated code submission records to avoid missing audit scope.
Daily or weekly update frequency means the auditing link must support incremental synchronization. This eliminates the need to pull full historical data, reducing resource consumption.
Differences across multiple document types and fields require auditing configurations to adapt to data formats from different sources. For example, distinguish parsing rules for Issue text and code repository submission information.
Additionally, auditing for time-consuming steps such as problem classification and completion of reproduction information must retain operation traces for backtracking. This ensures traceability of responsibility module tagging, and avoids risks of problem backlog or user churn.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Historical record retention count | Top 20 entries | Covers the full interaction cycle of most Issues, and adapts to the update frequency of category data |
| `chatId` binding rule | Bind to the corresponding Issue number | Ensures each conversation log is one-to-one with a business Issue, matching the granularity of the category's data sources |
| Audit log export scope | Filter by Issue dimension | Adapts to the category's document structure centered on Issues, making it easier for operations staff to backtrack the full processing flow of a single problem |
| `detail` field collection switch | Enabled | Retains environment information and reproduction steps reported by users, meeting core requirements for fault troubleshooting and retrospective |
| Timeout retry interval | 300 seconds | Adapts to GitHub API call frequency limits, avoiding frequent errors in the auditing link |
| `responseChatItemId` association rule | Bind to the unique identifier of reply records | Fully retains the operation trace of each triage response, facilitating responsibility tracing |

## Three common configuration errors
- Exported conversation logs lack associated Issue numbers. Cause: The binding rule between `chatId` and Issue numbers is not configured, causing logs to fail to match corresponding business entries.
- Global variable historical records cannot be modified as needed. Cause: The auditing configuration limits the number of historical records retained, and records beyond the range cannot be edited or adjusted.
- Fault troubleshooting responses with historical records have no effect. Cause: The `detail` field collection is not enabled, and environment information and reproduction steps reported by users are missing, leading to insufficient context and failure to trigger correct response logic.

## How to confirm configuration is complete
- Log in to the FastGPT v4.17.0 platform, create a test Issue, and check if the conversation log automatically binds to the corresponding Issue number after submission, confirming that the `chatId` configuration takes effect.
- Export audit logs for a specified time range, check if the complete content of the `detail` field is included, confirming that the collection switch is enabled.
- Modify the historical record retention count configuration, verify that old logs exceeding the retention limit are archived, confirming that the rule takes effect.
- Simulate a troubleshooting request with historical records, check if the response can associate the previous Issue context, confirming that the configuration takes effect.

The values listed above are common starting points. Adjust configurations based on your own specific samples and requirements.
