# Online Troubleshooting and Retrospective for Issue Triage and Response: Database and Operations

## What the Data for This Category Looks Like
Data for this category primarily comes from GitHub or Gitee Issues, release logs, user environment information, and code repositories. Update frequency is daily or weekly. Daily maintenance documents include Issue templates, tag rules, response records, and problem reproduction instructions. Data fields include Issue numbers, linked code branches, tags, priority levels, reproduction steps, user environment information, and more. Each entry must be linked to specific repository and version information to support subsequent troubleshooting and retrospective work.

## Constraints Imposed on Database and Operations Workflows
The multi-source nature of this category’s data requires databases to support hybrid storage. Structured tag rules, response records, and priority configurations can be stored in relational databases. Unstructured Issue content and user environment information can be stored in document databases. Daily or weekly update cycles require incremental sync tasks. This avoids performance losses caused by full data pulls. Diverse data fields require flexible index configuration. This enables fast retrieval of tags, priority levels, and linked repository information. This supports efficient problem classification and responsibility module tagging. Troubleshooting timeliness requires high database availability. This prevents connection interruptions from leading to problem backlogs and reduced community operational efficiency.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Enter a cluster connection string that includes authentication information, for example `mongodb://admin:pass@mongodb-01:27017,mongodb-02:27017/fastgpt_issues?replicaSet=rs0` | Unstructured Issue data and user environment information for this category are stored in MongoDB. Cluster configuration ensures high availability |
| `PG_URL` | Enter a PostgreSQL connection string, for example `postgresql://db_user:db_pass@pg-host:5432/fastgpt_config` | Structured tag rules, response records, and priority configurations require storage in a relational database to support complex queries |
| `DB_MAX_LINK` | Set to `80–120` connections | Daily incremental data volume for this category fluctuates with community activity. This connection pool size matches concurrent processing requirements |
| `REDIS_URL` | Configure a local cache node connection string, for example `redis://:redis_pass@localhost:6379/0` | Cache frequently accessed Issue tags and priority data to reduce repeated database queries |

## Three Common Misconfigurations
- Symptom: When calling a model to query MongoDB, the token consumption displayed in the interface does not match the token consumption returned by the actual API. Cause: The read-write separation parameter for `MONGODB_URI` is not configured correctly. This causes some queries to be routed to secondary nodes. Cached token statistics deviate from actual consumption on the primary node.
- Symptom: No Oracle type option appears in the dropdown menu of the FastGPT database connection module. Cause: The Issue triage and response logic for this category does not adapt to Oracle syntax specifications. The current version only supports connection configurations for MongoDB, PostgreSQL, and Redis.
- Symptom: When attempting to return JPG images via HTTP requests, the database returns empty results or no corresponding storage fields. Cause: No image storage field is added to the Issue storage template, and no Redis file cache path is configured. This prevents association between image data and Issue records.

## How to Verify Successful Configuration
- In FastGPT v4.17.0, run the MongoDB command `db.issues.countDocuments({})` to verify that the database corresponding to `MONGODB_URI` can read Issue data normally.
- Log in to the PostgreSQL database and run the query statement `SELECT * FROM issue_tags` to confirm that the database configured via `PG_URL` can read tag rule data normally.
- Check the Redis monitoring panel to confirm that the cache node configured via `REDIS_URL` has hit records and no connection timeout errors occur.
- Check the database connection pool monitoring metrics to confirm that the current number of connections does not exceed the value set for `DB_MAX_LINK`.

The values provided here are common starting points and should be evaluated against the reader's own samples.
