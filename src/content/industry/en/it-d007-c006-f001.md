# Pull Request Review Online Fault Troubleshooting and Retrospective: HTTP Interfaces and External Systems

## What data for this category includes
Data for this category originates from code repositories, CI pipelines, Issue links, and code change submissions from contributors. Daily generated documents include PR descriptions, code review comments, CI execution results, and merge records. Data updates occur daily or weekly. Fields include changed code snippets, review comment entries, CI status indicators, merge timestamps, and additional relevant fields. The core focus is the review and merge process for code changes, with no additional statistical fields.

## Constraints on HTTP Interfaces and External Systems
Data sources for this category are dispersed, requiring connections to HTTP interfaces from multiple external systems such as code repositories and CI pipelines. Multiple sets of authentication parameters must be configured. Data updates occur daily or weekly, so interface call frequency must align with this rhythm to avoid triggering external system rate limits. Daily documents include structured fields such as review comments and CI results. These fields must be extracted via interfaces and mapped to internal variables for context splicing during fault troubleshooting. Errors in code change review can impact main branch stability, so retry logic and exception alerts must be configured for interface call failure handling.

## Configuration Guidelines
This configuration reference is based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `Authorization` | Configure a Bearer token as required by the external system | Used for identity verification when connecting to external systems such as code repositories and CI pipelines, in line with project permission control requirements |
| `variables` | Map PR title, CI status, and Issue link fields from `responseData` | Matches daily document fields for PR reviews, used for context splicing during fault troubleshooting |
| `responseData` | Retrieve the top 20 core fields from interface responses | Covers key data required for PR reviews, avoiding redundant information that interferes with the review process |
| Interface timeout period | 30 seconds | Matches the average execution cycle of CI pipelines, avoiding process blocking caused by long waits |
| Call retry count | 2 times | Addresses temporary interface call failures caused by network fluctuations, balancing reliability and resource consumption |

## Three Common Misconfigurations
- Failing to include the `Authorization` parameter during interface calls, resulting in a 401 Unauthorized status code. This occurs when the external system’s authentication token is not configured correctly, leading to identity verification failure.
- Attempting to extract cookie fields from `responseData` with no returned results. This occurs when the external interface does not return cookie-related response headers, or when response header capture configuration is not enabled.
- Calling external APIs prematurely during the PR review process without binding `variables`. This occurs when interface return results are not mapped to context variables available for the review process, preventing subsequent troubleshooting from obtaining required information.

## How to Confirm Configuration is Complete
- Trigger a simulated PR change process, review external system interface call logs, and confirm the `Authorization` parameter is correctly included.
- Call the test interface, review the returned `responseData` fields, and confirm required PR and CI-related data has been correctly captured.
- Review the `variables` mapping configuration, and confirm fields extracted from `responseData` match those in daily review documents.
- Simulate an interface call failure scenario, and confirm the system triggers the preset retry logic and exception alerts.
