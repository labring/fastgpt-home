# Online Fault Troubleshooting and Retrospective for Pull Request Reviews: Conversation Logs and Auditing

## What the data for this category looks like
The data for this category primarily comes from code repositories, CI pipelines, Issue links, and change content submitted by contributors. Daily associated documents include PR descriptions, code review comments, CI execution results, and merge records. The data update frequency is typically daily or weekly. It covers key information across the full lifecycle of a single PR from submission to merge. Fields include PR number, changed file list, reviewer identifiers, review conversation content, CI status, merge flag, and more. All content centers on mergeable code changes, with clear differences from data of other sorting categories.

## What constraints these characteristics impose on conversation logs and auditing
Conversation logs and auditing for PR reviews must support association of multi-source data, and need to bind external data such as code repositories and CI results. Therefore, conversation context must include PR identifiers to link to corresponding change content. Since data updates occur daily or weekly, audit logs do not require high-frequency real-time storage, but must fully retain conversation fragments across the entire review process. Review conversations involve professional discussions about code changes, so original questions and response content must be retained without arbitrary truncation. These logs must also be associated with auxiliary information such as corresponding review comments and CI results. This ensures change intent and verification processes can be traced during fault troubleshooting. In scenarios where multiple contributors conduct parallel reviews, different sessions must be distinguished using `chatId` to avoid log confusion.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Session identifier binding | Bind PR number and `chatId` | Ensure each review session is associated with the corresponding code change, preventing cross-PR log confusion |
| Log storage granularity | Store complete conversation fragments and `detail` field | Cover questions, responses, and review comments across the entire review process to meet fault traceability requirements |
| Context length limit | Top 20 conversation history entries | Adapt to multi-round discussion scenarios for PR reviews, avoiding context overload that impacts response speed |
| Response timeout threshold | 600 seconds | Handle time-consuming operations such as CI result queries and code change analysis, preventing premature interruption of troubleshooting workflows |
| Response association configuration | Enable `responseChatItemId` association | Bind individual responses to corresponding review operations, enabling precise troubleshooting of delayed or abnormal responses |

## Three common configuration errors
- Symptom: In the same PR review session, response time increases significantly after multiple rounds of questions. Knowledge base retrieval takes longer than 600 seconds, and creating a new session restores normal performance. Cause: The `chatId` is not used to bind session context, resulting in full historical data being loaded for each retrieval without session-level context isolation.
- Symptom: Port 3000 is inaccessible after service startup, and logs show a database connection failure. Cause: No database connection log auditing parameters are configured, and database connectivity is not verified in advance, leading to configuration errors being exposed only after startup.
- Symptom: Workflow nodes cannot retain multi-round review conversation context, and only single operations can be executed. Cause: The `responseChatItemId` association configuration is not enabled, preventing the workflow from binding the context identifier of individual conversations and failing to pass historical information.

## How to verify correct configuration
- View session logs to confirm that each PR review conversation is associated with the corresponding PR number and `chatId` identifier.
- Simulate multi-round questions to check if response times remain stable without significant delays.
- View audit logs to confirm that each response is associated with `responseChatItemId`, enabling precise tracing of individual conversation content.
- In FastGPT v4.17.0, verify database connection configuration by performing a connectivity test before service startup to avoid post-startup connection failures.
