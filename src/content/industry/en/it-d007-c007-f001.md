# Online Troubleshooting and Retrospective for SLA and Service Reports: HTTP Interfaces and External Systems

## What the data for this category looks like
This category’s data comes from monitoring systems, ticketing systems, service contracts, and customer communication records, with an update frequency of monthly or quarterly. Daily documents include SLA clause text, monthly service summary reports, raw availability statistics tables, and customer retrospective meeting minutes. The data structure is organized according to the service period agreed in the contract, including event occurrence timelines, response and recovery duration records, and archived customer feedback content. Fields must match the service agreement items of the corresponding contract, and there is no fixed unified default format. This document is compatible with FastGPT v4.17.0.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
This category’s data comes from scattered sources and must match the personalized agreements of customer contracts, which brings multiple constraints to HTTP interface and external system integration. First, configure `Authorization` to adapt to the authentication rules of different source systems, ensuring the legality of pulling data from monitoring, ticketing, and other systems. Second, the data update frequency is monthly or quarterly, so interface calls must match this cycle rhythm to avoid frequent calls that exceed the access limits of external systems. At the same time, the daily document structure must match the service clauses of the customer contract, and `responseData` must support custom field mapping to ensure that aggregated data meets the format requirements of report output. In addition, data involves service compliance, so interface transmission must ensure security, and failure handling must adapt to the aggregation window within the cycle to avoid loss of key statistical data.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Authentication Configuration | Configure the `Authorization` field as the access credential for the corresponding system | Adapt to the authentication rules of different external monitoring and ticketing systems, ensuring legal permissions for data pulling |
| Request Parameter Configuration | Pass the `variables` field bound to `{"reportCycle": "monthly", "contractId": "corresponding contract number"}` | Match the monthly/quarterly update cycle, and associate service contract data for the corresponding customer |
| Response Data Mapping | Configure `responseData` to map to the structured fields required for reports | Adapt to the document structure of SLA reports, ensuring that statistical data meets the service indicators agreed in the contract |
| Interface Timeout Setting | 600 seconds | Adapt to the conventional response delay range of external systems, avoiding data collection being interrupted by single-call timeouts |
| Retry Policy Configuration | Retry 2 times after failure, with a 30-second interval | Adapt to the monthly aggregation time window, avoiding missing the data collection cycle due to a single call failure |

## Three common errors
- A `503 Service Unavailable` status code appears, and logs show that the default group configuration is abnormal. The cause is that the correct external system group identifier is not configured in `variables`, causing the interface call to fail to match available resources.
- Calling an external interface via a custom plugin returns empty fields, making it impossible to generate valid statistical data. The cause is that the `responseData` mapping rule is not configured, causing the pulled raw data to fail to be correctly parsed into the format required for reports.
- Interface calls fail due to protocol incompatibility, and the associated voice function cannot be triggered normally. The cause is that the API root address was not upgraded from HTTP to HTTPS, as the external system only supports encrypted transmission protocols.

## How to confirm the configuration is complete
- Call the configured HTTP interface, and check whether the `Authorization` field matches the authentication credential required by the external system.
- View the `responseData` field returned by the interface, and confirm whether it includes the structured data fields required for the report.
- Simulate a monthly aggregation cycle to call the interface, and check whether the retry policy is triggered after a timeout and does not exceed the time window.
- Verify that the transmission protocol of the API root address matches the security requirements of the external system, ensuring there are no protocol incompatibility errors.
