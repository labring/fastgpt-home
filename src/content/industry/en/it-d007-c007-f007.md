# Online Troubleshooting and Retrospective for SLA and Service Reports: Chat Logs and Auditing

## What data for this category looks like
Data sources include monitoring systems, ticketing systems, service contracts, and customer chat logs. Update cycles run monthly or quarterly. Daily output documents include SLA clauses, monthly service reports, availability statistics reports, and customer retrospective minutes. Core fields cover SLA compliance rates during the service cycle, abnormal event durations, chat interaction record identifiers, and contractually agreed service levels. Corresponding units are percentage, hour, calendar day, and chat ID identifier. Data must be aligned across multiple systems to ensure unified statistical standards for service performance. This supports customer service retrospectives and SLA-related validation.

## What constraints do these characteristics impose on chat logs and auditing workflows
Cross-system association of multi-source data requires chat logs to bind ticketing, contract, and monitoring data using unified identifiers. Without this, precise attribution of SLA metrics cannot be completed. Monthly or quarterly update cycles require log retention periods to match the statistical windows of service reports. This prevents data gaps during retrospective work. Core document generation depends on complete interaction chains. The auditing workflow must cover the full process from user question to response. This supports SLA compliance rate calculations and abnormal event tracing. Format differences across data sources require chat log field standards to align with SLA statistical standards. This reduces time spent aligning statistical standards.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` association binding | Bind with ticket ID and contract number | Ensure chat logs can directly link to corresponding service contracts and tickets, simplifying SLA metric attribution workflows |
| `responseChatItemId` log tracing | Generate unique identifiers for each single interaction | Facilitate locating full context of individual abnormal responses, matching event statistical needs of monthly service reports |
| Log retention period | 30–90 days | Match monthly or quarterly service report update cycles, covering the full time window required for customer retrospectives |
| Log detail `detail` collection | Enable full-field collection | Include user questions, response content, and response durations, supporting precise calculation of SLA compliance rates |
| Auditing trigger threshold | Calibrate based on actual testing | Adapt to differences in SLA clauses across different customers, avoiding false triggering of abnormal alerts |

## Three common configuration errors
- Configuring `chatId` without associating it with ticket IDs. This causes missing attribution of abnormal events in monthly service reports, leading to SLA metric calculation errors. The root cause is failure to establish a link between chat logs and ticketing system data, preventing cross-data source alignment.
- Setting log retention period to 7 days. This makes historical interaction data unavailable during quarterly retrospectives. The root cause is failure to match the monthly or quarterly update cycles of SLA and service reports, with insufficient retention duration.
- Not enabling `detail` field collection. This leads to missing response durations and user question content, making it impossible to verify response time commitments in SLA clauses. The root cause is only collecting basic chat identifiers, without covering core fields required for SLA calculations.

## How to confirm correct configuration
- In FastGPT v4.17.0, view the chat log list. Confirm that each log carries `chatId` and `responseChatItemId` identifiers, and can link to corresponding ticket or contract numbers.
- Retrieve historical chat records from 30 days prior. Confirm that logs have not been automatically cleaned, and the retention period matches the preset configuration.
- Export raw data from monthly service reports. Verify that the `detail` field includes user questions, response content, and response durations.
- Simulate an abnormal interaction to trigger auditing rules. Confirm that events meeting the threshold are correctly marked.
