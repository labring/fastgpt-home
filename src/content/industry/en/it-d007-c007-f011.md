# Online Troubleshooting and Retrospective for SLA and Service Reports: Database and Operations

This document applies to FastGPT v4.17.0, and targets database and operations engineers in the electronics, internet, and IT industries for online troubleshooting and retrospective scenarios.

## What This Category's Data Looks Like

Data for this category comes from monitoring systems, ticketing systems, contract documents, and customer communication records. The update frequency is monthly or quarterly. Daily produced documents include SLA clauses, monthly service reports, availability statistics ledgers, and customer retrospective meeting minutes. Data fields include service cycle identifiers, abnormal event association IDs, contract effective versions, customer communication archive times, and more. No fixed quantitative statistical caliber is preset. Service-related events and communication content are only aggregated according to contract cycles.

## How These Characteristics Create Constraints for Database and Operations Workflows

Multi-source data access requires the database to support cross-system data association and storage. Monthly and quarterly batch update rhythms do not require ultra-high concurrency, but need stable batch write and aggregation capabilities. Multi-document summarization logic requires the database to support complex associated queries to avoid data redundancy. Since data anomalies can trigger compensation disputes and customer complaints, data persistence and audit capabilities are required configurations. At the same time, high-time-consuming links such as SLA indicator calculation, abnormal event attribution, and report caliber alignment require the database configuration to balance query performance and resource usage, to avoid impacting business processes.

## How to Set Configurations

| Configuration Item | Recommended Value | Rationale for This Setting |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://[username:password@]host1:port1,host2:port2/dbname?replicaSet=rs0&maxPoolSize=40` | Stores multi-source ticketing and customer communication records. Replica sets ensure data high availability. Connection pools adapt to concurrent requirements of batch summarization tasks |
| `PG_URL` | `postgresql://user:pass@db-host:5432/sla_db?sslmode=require&statement_timeout=60000` | Stores SLA clauses and retrospective meeting minutes. SSL encryption protects sensitive data security. Timeout restrictions prevent long queries from blocking tasks |
| `DB_MAX_LINK` | `30–50` | Adapts to concurrent connection counts for monthly batch summarization tasks. Avoids service interruptions caused by exhausted database connections |
| `REDIS_URL` | `redis://:redis-pass@redis-host:6379/0?maxmemory-policy=allkeys-lru` | Caches intermediate results of SLA calculations to reduce repeated database queries. LRU strategy prevents cache memory overflow |

## Three Common Misconfigurations

- The symptom is the `getaddrinfo EAI_AGAIN mongo` error in logs. The cause is that the database address configured in `MONGODB_URI` cannot be resolved normally, or the connection pool has reached its upper limit, preventing new connections from being established.
- The symptom is long periods of unresponsiveness or even process exit during monthly service report generation. The cause is that the `DB_MAX_LINK` configuration value is too low. Batch aggregation tasks cannot acquire enough database connections, leading to task blocking.
- The symptom is that some SLA indicators are empty in exported service reports. The cause is that the `REDIS_URL` cache for intermediate calculation results is not configured, leading to timeouts when repeatedly querying historical data, or that abnormal event IDs from the ticketing system are not correctly associated, resulting in missing data.

## How to Confirm Configurations Are Correct

- Run database connection verification commands to test connectivity for `MONGODB_URI` and `PG_URL`, and check the current usage of the connection pool.
- Manually trigger a small-scale SLA indicator calculation task, and check that there are no connection timeout or aggregation failure errors in the task execution logs.
- View the cache service corresponding to `REDIS_URL`, and confirm that key-value pairs for caching SLA calculation intermediate data exist.
- Export a service report for a test cycle, and compare it with records from original data sources to confirm that data association relationships are correct.

The values provided are common starting points, and should be evaluated against the reader's own samples.
