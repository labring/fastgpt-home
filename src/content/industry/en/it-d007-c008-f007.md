# Online Troubleshooting and Retrospective for Special Event Operations: Conversation Logs and Auditing

## What Data for This Category Looks Like
This category of data typically originates from event backends, content libraries, traffic statistics tools, and user feedback. Daily deliverables include event plans, resource slot scheduling tables, event page copy, and retrospective reports. Common fields include event ID, cycle milestones, resource slot numbers, traffic metrics, and user feedback tags. Data updates follow a weekly schedule, with temporary adjustments around holidays based on event preparation progress. The data structure is organized around the full lifecycle of a single special event, linking records across all stages: launch, preheating, execution, and wrap-up.

## Constraints on Conversation Logs and Auditing Workflows
The full-lifecycle data characteristics of special event operations require the conversation logs and auditing workflow to use event ID as the core associated field. This ensures every log entry can be traced back to the corresponding special event. Data from multiple sources must be uniformly tagged with source types to prevent confusion between records from event backends, content libraries, and user feedback. Because event cycles are clearly defined and update cadences are flexible, the auditing function must support quick log filtering by event cycle and time range. Incomplete conversation request records must also be captured, to avoid missing critical links during troubleshooting caused by interruptions.

## Configuration Guidelines
This guide applies to FastGPT v4.17.0
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Unique identifier generated by concatenating the event ID and user customUid | Ensures conversation logs can be retrieved across both special event and participating user dimensions |
| `responseChatItemId` | Incremental sequence generated by interaction order within the event cycle | Matches the full-lifecycle record logic of special events, enabling retrospective analysis by interaction sequence |
| `detail` | Enable full log storage (includes request body and response body) | Covers complete interaction details required for event copy review and traffic anomaly troubleshooting |
| Log storage period | 30–90 days | Matches the standard retrospective cycle for special events |
| Batch retrieval limit | Top 1000 entries | Adapts to standard retrieval scale for event data |
| Abnormal log trigger rule | Calibrated based on actual testing | Adapts to traffic fluctuations across different events, avoiding false positive or missed fault alerts |

## Three Common Misconfigurations
- Symptom: Conversation logs are not saved to the database after the client interrupts an SSE connection. Cause: Log disk persistence logic for incomplete requests is not configured, and logs are only written to storage after a request completes normally.
- Symptom: After starting the FastGPT container, the service port is operational but login fails, with logs indicating a MongoDB connection failure. Cause: Correct MongoDB connection parameters are not specified in the conversation log configuration, or container network policies restrict database access.
- Symptom: When calling the API to retrieve conversation history, all application session records are returned, and filtering by customUid is not possible. Cause: `chatId` is not configured as a combined identifier of event ID and customUid, leading to missing retrieval dimensions.

## How to Verify Proper Configuration
- Initiate a conversation request with a customUid, check if the logs include the combined identifier of event ID and customUid, to confirm the `chatId` configuration is active.
- Interrupt an ongoing conversation request, check if incomplete conversation log entries are generated in the database, to confirm the full log storage configuration is active.
- Call the conversation history API, pass the specified event ID and customUid, check if the returned results only include records for the corresponding session, to confirm the retrieval dimension configuration is correct.
- View MongoDB connection logs, confirm the service can establish a normal database connection with no connection failure errors.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
