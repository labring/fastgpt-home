# Online Troubleshooting and Retrospective for Special Event Operations: Database and Operations

## What data looks like for this use case
The data for this use case primarily comes from activity backends, content libraries, traffic statistics tools, and user feedback channels. Daily produced documents include activity execution plans, resource slot schedules, activity page copy, and post-event retrospective reports.
Data update cycles are mostly weekly or adjusted to match activity cycles. Some core data, such as real-time traffic and user feedback, updates in real time as the activity progresses.
Individual data entries include fields like activity ID, cycle range, resource slot configuration, traffic peak value, and user feedback tags. There are no unified fixed units; values vary based on data type.

## Constraints for database and operations workflows
Data for special event operations has clear periodic peaks and real-time update requirements. This means database connection configurations must adapt to sudden high concurrency and dynamic traffic changes.
Multi-source data access requires operations workflows to support connection parameter configurations for different data sources.
Activity-related documents and data fields lack unified standards. This requires databases to support flexible field expansion to avoid hard-coded constraints.
Scenarios where weekly batch updates run alongside real-time traffic statistics require operations configurations to balance read/write performance and resource usage. This prevents service outages caused by resource exhaustion.

## Recommended configuration settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://admin:password@mongodb:27017/fastgpt?replicaSet=rs0` | Adapts to multi-node MongoDB deployments, supports high-availability storage for activity data, and supports unstructured data from activity backends and content libraries |
| `PG_URL` | `postgresql://postgres:password@postgres:5432/fastgpt` | Used to store structured data such as activity schedules and user feedback, supports complex queries and transaction operations |
| `DB_MAX_LINK` | `150–250 connections` | Adapts to sudden peak traffic for special events, prevents service unavailability caused by exhausted database connection pools |
| `REDIS_URL` | `redis://:password@redis:6379/0` | Caches static activity page resources and real-time traffic statistics data, reduces read/write pressure on the primary database |
| Database connection timeout | `600 seconds` | Adapts to batch data query scenarios during activity retrospectives, prevents long-running queries from being forcibly terminated |

## Three common configuration mistakes
- Symptom: FastGPT deployed via Docker fails to connect to MongoDB several hours after startup, with logs showing `connection timed out`. Cause: No reasonable value set for `DB_MAX_LINK`. Peak activity traffic exhausts the database connection pool, preventing subsequent requests from establishing new connections.
- Symptom: In FastGPT v4.17.0, an error occurs when saving or running operations using an initialized AI model while creating a new activity-related question classification node. The error is resolved after switching the AI model. Cause: Cache parameters for `REDIS_URL` are not configured correctly, causing node configuration data to fail to sync and store properly, triggering verification failures.
- Symptom: After upgrading from FastGPT v4.9.13 to v4.10.1, activity copy content in the knowledge base fails to display on the frontend. Cause: Database migration operations were not performed. The storage structure for activity metadata differs between old and new versions, and structured data fields were not synchronized.

## How to verify correct configuration
- Run database connection test commands to confirm that the addresses configured for `MONGODB_URI`, `PG_URL`, and `REDIS_URL` can connect normally, and that the parameters match the actual deployment environment.
- Review database connection pool monitoring metrics, adjust the value of `DB_MAX_LINK` to ensure connection usage stays within a reasonable range during peak traffic.
- Simulate a special event peak traffic scenario, send batch query requests, and verify that database read/write performance meets business requirements.
- Run the database migration script corresponding to the target FastGPT version, confirm that activity metadata and knowledge base content have been synchronized to the storage structure of the target version.

The values provided here are common starting points and should be evaluated against the reader's own samples.
