# Online Incident Troubleshooting and Retrospective for Incident Response and Fault Handling: HTTP Interfaces and External Systems

## What this category of data looks like
Data for this category is maintained daily by SREs, on-duty operations staff, and on-duty development leads. Sources include monitoring alerts, log platforms, APM tools, and user feedback. Data updates occur in real time or after each incident. Daily documents include incident work orders, event timelines, emergency response plans, and incident notifications. Fields cover unique incident identifiers, occurrence times, affected service scopes, stop-loss operation records, preliminary root cause judgments, notification recipients, and additional relevant fields. Field naming follows industry-wide operational specifications, with no custom units added.

## What constraints these characteristics impose on HTTP interfaces and external systems
Scattered data sources and real-time update requirements mean HTTP interfaces must support multi-format external system callbacks. Interfaces must quickly receive alert data from different monitoring and log platforms. Frequently updated associated incident documents require interfaces to support querying and appending content by incident ID. This avoids creating duplicate invalid records. High timeliness requirements for fault handling mean interface timeout settings must align with business stop-loss windows. Error responses must clearly point to the source of anomalies. This enables on-duty staff to quickly locate interface-level issues.

## How to configure settings
The following configurations apply to FastGPT v4.17.0

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Interface timeout duration | 600 seconds | Aligns with typical fault handling stop-loss windows, avoids blocking on-duty workflows for extended periods |
| Callback address whitelist | Only include internal operations system IP ranges | Prevents unauthorized external data pushes from interfering with fault incident records |
| `Authorization` | Combine fixed secret key and signature verification, with a 30-day key rotation cycle | Ensures the identity legitimacy of external systems calling the interface, prevents malicious data injection |
| `variables` | Bind event ID and affected service tags | Automatically populates core fields of incident work orders, reduces manual entry errors |
| `responseData` | Only return incident status and operation results | Simplifies receiving logic for external systems, focuses on core information for fault handling |
| Retry strategy | Retry 3 times at 30-second intervals after failure | Addresses interface call failures caused by network fluctuations, ensures data synchronization reliability |

## Three common misconfigurations
- Phenomenon: A cross-origin error is returned when calling the api/v1/chat/completions interface using fetch, including CORS-related prompts or status code 403. Cause: No allowed front-end domain whitelist is added in the interface configuration, causing external cross-origin requests to be blocked.
- Phenomenon: Long error codes, interface response timeouts, or abnormal parameter formats are returned when calling models via aiproxy. Cause: Proxy parameters in `variables` are not configured correctly, preventing requests from being properly forwarded to the target model service.
- Phenomenon: An invalid configuration prompt is returned when specifying the trainingType parameter with data-raw when creating a plain text collection via the knowledge base interface. Cause: The platform-supported trainingType options are not used, or the parameter format does not meet interface requirements.

## How to confirm the configuration is correct
- Call the interface to test authorization verification. An identity authentication failure prompt is returned when an invalid `Authorization` parameter is used. Normal responses are returned for valid parameters.
- After configuring the callback address, push test alert data from an external system. Confirm that an incident work order is automatically generated and fields match the preset rules.
- Check the `responseData` field of the interface response. Only incident status and operation results are included, with no redundant information.
- Simulate network fluctuations. Confirm that the interface automatically retries according to the configured retry strategy, and completes data synchronization in the end.
