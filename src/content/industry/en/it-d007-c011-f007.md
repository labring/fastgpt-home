# Online Troubleshooting and Retrospective for Cloud Host Provisioning and Resource Activation: Conversation Logs and Auditing

## What this category’s data looks like
Data for this category comes primarily from cloud management platforms, order systems, IAM permission systems, and billing systems. It is synced in real time per order. Common associated business documents include resource activation tickets, instance configuration sheets, account permission tickets, and delivery confirmation sheets.
Typical data fields include instance unique identifier, activation time, compute specifications, permission scope, and billing items. The instance identifier uses a string format. Compute specifications are measured in vCPU cores and memory in GB. Order numbers use numeric string formats.

## What constraints these characteristics impose on conversation logs and auditing
Multiple data sources require conversation logs to integrate business identifiers from cloud management platforms, order systems, IAM, and billing systems to avoid association gaps.
The real-time per-order update rhythm requires audit logs to save the interaction process for each order synchronously, without delayed bulk storage.
Diverse business document structures require logs to associate fields from corresponding tickets, to directly locate issues in specification verification, permission configuration, and other links.
Severe consequences of errors require logs to retain the complete interaction chain, to support full-process traceability after a fault occurs.
Unlike cloud network and load balancing configuration categories, this category only focuses on compute resource provisioning. Logs do not need to associate too many network configuration fields, further simplifying the audit scope.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| ---|---|--- |
| `chatId` | Bind to cloud host instance ID | Each cloud host provisioning order corresponds to a unique instance identifier. `chatId` can be used to associate interaction logs with business tickets, enabling precise traceability, and adapts to the workflow configuration rules of FastGPT v4.17.0. |
| `responseChatItemId` | Bind to the unique identifier of each LLM response | Facilitates locating occasional empty responses or timeout issues, and matches the multi-turn interaction chain characteristics of this category. |
| `detail` | Store full interaction content and associated ticket IDs | Covers the core business document fields of this category, meeting the complete recording requirements for auditing and fault retrospection. |
| Maximum number of chat records | First 20-30 records | Interactions for this category revolve around resource activation and configuration verification. 20-30 records cover the complete process, and align with actual business interaction lengths. |
| Log retention period | 180 days | Matches the conventional requirements for fault retrospection and compliance auditing, and aligns with the business update frequency of this category. |

## Three common misconfigurations
- Symptom: The "code execution" node in the workflow fails validation when input contains historical records, and cannot run. Cause: The binding rules between `chatId` and workflow variables are not configured correctly, causing the historical record parameter to not be properly recognized by the system.
- Symptom: LLM responses are empty, occasionally stuck for 10 seconds before throwing an error, with no corresponding logs in third-party call tools. Cause: Full log storage for the `detail` field is not enabled, making it impossible to locate occasional interface call timeouts or missing parameter issues.
- Symptom: By default, only the first 50 chat records are retained. After exceeding this limit, earlier specification verification records are truncated. Cause: The configuration is not adjusted based on the actual business interaction length of this category, leading to loss of critical pre-business information.

## How to confirm the configuration is correct
- View the interaction log list, confirm that each log is associated with a cloud host instance ID and corresponding order number, to verify that the `chatId` binding configuration is effective.
- Trigger a simulated resource activation process, check that each LLM response carries a unique identifier, to confirm that the `responseChatItemId` association configuration works properly.
- View the log storage details, confirm that the `detail` field stores complete interaction content and associated business ticket information, to verify that the full record configuration is correct.
- Adjust the chat record count configuration, verify that the modified retention rule takes effect normally based on the actual interaction length of this category.
