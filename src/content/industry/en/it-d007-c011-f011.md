# Online Troubleshooting and Retrospective for Cloud Host Provisioning and Resource Activation: Database and Operations

## Data structure for this category
Data for this category originates from cloud management platforms, order systems, IAM, and billing systems. It is synced in real time for each individual order.
Associated daily documents include resource activation tickets, instance configuration tables, account permission tickets, and delivery confirmation slips.
Core fields include instance ID, vCPU count, memory capacity, permission account group ID, order number, billing node, and others. Instance ID is a unique string identifier. Specification parameters use cores and GB as units. Permission scope is identified by account group ID.

## Constraints for database and operations workflows
Real-time updated data sources require databases to support high-concurrency writes and low-latency reads. This prevents resource configuration errors caused by delayed ticket data synchronization.
The multi-document, multi-field structure requires database table structures to align one-to-one with fields across all documents. Separate table spaces must be allocated for storing instance configurations, permission information, and order details. This avoids data mixing.
Research identifies the most time-consuming steps for this category as specification verification and network security group configuration. These steps frequently call cloud platform APIs. A caching mechanism reduces repeated requests. It is also necessary to verify that specification parameters stored in the database match real-time cloud platform data. This prevents resource mismatches or billing disputes.

## Configuration settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Connection address for cloud management platform instance metadata storage | Core database connection for storing instance configurations and order data, aligns with FastGPT data storage specifications |
| `PG_URL` | Read-only replica connection address bound to order systems and IAM systems | Separates read and write operations to reduce operational overhead, supports real-time pulling of permission and order data |
| `DB_MAX_LINK` | `100–150` | Adapts to concurrent ticket volume during cloud host provisioning, prevents connection pool overflow |
| `REDIS_URL` | Cache instance specification verification results with a validity period of `300 seconds` | Reduces latency from repeated cloud platform API calls, optimizes time spent on specification verification |
| Result rearrangement | When enabled, limits tool call concurrency to `1` | Prevents resource conflicts caused by concurrent tool selection, addresses reported concurrency exception issues from the community |
| Query optimization | When enabled, limits the context length of a single search to `800–1200 characters` | Reduces input token volume, lowers computational overhead during the retrieval phase |

## Three common configuration errors
- Enabling query optimization and result rearrangement causes message return timeouts. The symptom is a return duration exceeding 30 seconds. The root cause is failure to limit tool concurrency during the rearrangement phase, leading to overload of cloud platform API requests.
- Unable to create databases after local deployment. The symptom is a database connection failure error displayed in the interface. The root cause is incorrect configuration of `PG_URL` or `MONGODB_URI` pointing to uninitialized database instances.
- Billing anomalies occur after resource provisioning. The symptom is the billing system showing resource specifications that do not match actual allocations. The root cause is failure to update field data in the instance configuration table, leading to a mismatch between specifications stored in the database and actual cloud platform configurations.

## How to confirm successful configuration
- Run a database connectivity test script to confirm that `MONGODB_URI` and `PG_URL` can successfully pull test order data and permission information.
- Check the concurrent volume of current cloud host provisioning tickets. Confirm that the volume does not exceed the connection limit set by `DB_MAX_LINK`, and that there are no connection pool overflow logs.
- Submit identical instance specification verification requests repeatedly. Confirm that the first request calls the cloud platform API, and subsequent requests read data from the cache corresponding to `REDIS_URL`.
- Enable the result rearrangement feature and submit a test ticket. Review tool call logs to confirm that only one tool call is triggered, with no concurrent request records.

The values provided here are common starting points. They should be evaluated against specific samples and use cases.
