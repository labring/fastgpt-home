# Online Troubleshooting and Retrospective for Cloud Host Provisioning and Resource Activation: Deployment and Upgrade

## What the data for this category looks like
This category’s data typically originates from cloud management platforms, order systems, IAM permission systems, and billing systems, with updates synced in real time for each order. Daily supporting documents include resource activation forms, instance configuration sheets, account permission forms, and delivery confirmation forms. Core fields include instance specification parameters, network security group configurations, permission binding scopes, and billing association identifiers. All data flows through the full process of computing resource creation and delivery.

## What constraints do these characteristics impose on the deployment and upgrade phase
The data characteristics of this category impose multiple constraints on the deployment and upgrade phase. Real-time updated multi-system data sources require cross-system data consistency checks before deployment. This prevents issues like expired permissions and mismatched specifications. Differences in fields across multiple types of supporting documents require one-by-one verification of parameter alignment between the instance configuration sheet and delivery confirmation form before upgrade. Focused on the core positioning of computing resource creation, the deployment phase must prioritize the correctness of computing specifications and network configurations. This prevents confusion with cloud network configurations. Additionally, the risk of synchronization delays across multiple data sources requires temporarily disabling non-essential resource change operations during the upgrade process. This prevents data conflicts.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://username:password@host:port/fastgpt?authSource=admin` | Adapts to the database interaction logic of FastGPT v4.17.0, and conforms to the standard connection format for cloud host deployment |
| `REDIS_URL` | `redis://:your_password@host:port/0` | Meets storage requirements for cached sessions and vector indexes, and adapts to the memory resource limits of cloud hosts |
| `DB_MAX_LINK` | `80–150 connections` | Adapts to the database connection pool configuration of cloud hosts, and prevents deployment interruptions caused by exceeded connection limits |
| `STORAGE_S3_ENDPOINT` | `Fill in the access address provided by the cloud service provider's object storage console` | Ensures alignment between the storage service bound to the cloud host and deployment configurations, to guarantee normal file read and write operations after resource activation |
| `ROOT_KEY` | `32-character random encrypted string` | Ensures administrator authentication security, and conforms to permission control specifications for cloud host deployment |

## Three Common Mistakes
- A `MongoDB connection timeout` error occurs during deployment. This is caused by either not using MongoDB connection parameters matching FastGPT v4.17.0, or the cloud host security group not opening the default MongoDB port.
- Third-party API calls fail after upgrade. This is caused by not synchronously updating the keys and addresses in mobile third-party API configurations, leading to a mismatch between the configuration and the actual deployed cloud host resources.
- Instance specification verification fails after cross-version upgrade. This is caused by not verifying the instance configuration sheet and the specification fields in the upgrade script, leading to inconsistent core parameters for resource delivery.

## How to Confirm Configurations Are Correct
- Run the database connection test command, and verify that the configurations for `MONGODB_URI` and `REDIS_URL` match the database service addresses on the cloud host.
- View the cloud host's security group rules, and confirm that the open ports match the service ports declared in the configuration items.
- Verify the instance specifications on the delivery confirmation form and the parameters in the deployment script, to ensure they are fully aligned.
- Call the backend health check interface, and confirm that the connectivity of the storage service configuration `STORAGE_S3_ENDPOINT` is normal.

The values provided are common starting points and should be measured against the reader's own samples.
