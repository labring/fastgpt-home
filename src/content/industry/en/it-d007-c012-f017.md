# Online Troubleshooting and Retrospective for Cloud Network and Load Balancer Configuration: Deployment and Upgrade

## What data this category includes
Data for this category mainly comes from cloud platform consoles, network topology files, traffic monitoring reports, and customer architecture diagrams. Daily maintenance documents include VPC planning, security group rules, load balancer configuration lists, and change tickets. Data update frequency syncs with every configuration change, with no fixed cycle. Core fields include network segment ranges, port mapping rules, health check thresholds, and backend server group configurations. Some parameters must match the definitions of the corresponding cloud service provider, with no unified mandatory units.

## What constraints these characteristics impose on the deployment and upgrade phase
Based on the characteristics of scattered data sources and real-time updates tied to configuration changes, pull the latest console configurations and topology files before deployment or upgrade. Avoid using expired documents for verification. Align parameter definitions between the cloud service provider and internal documentation before making changes, as core fields have no unified units. Link change tickets to the historical versions of corresponding configuration items, to support tracing adjustment trails during fault retrospection. The network segment planning and rule verification step accounts for the largest share of time. Reserve dedicated verification time during the deployment phase to ensure the accuracy of configuration changes.

## How to Configure Settings
This configuration guide applies to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 100–200 connections | Matches the default connection limit of cloud databases, to avoid exhausting connection pool resources from concurrent requests |
| `MONGODB_URI` | Fill in the intranet connection string provided by the cloud service provider | Ensures network connectivity between the deployment environment and the database, reducing public network exposure risk |
| `REDIS_URL` | Configure as the address of a locally deployed instance, set the port to 6379 | Reduces cross-network latency, improving response speed for cache read and write operations |
| `STORAGE_S3_ENDPOINT` | Fill in the intranet endpoint from the cloud object storage console | Optimizes network paths for storage access, lowering cross-region traffic costs |
| `FE_DOMAIN` | Fill in the public access domain name of the deployment environment | Ensures correct loading of frontend page resources and callback requests |
| `FILE_TOKEN_KEY` | Use a 32-bit random string as the secret key | Ensures authentication security for file upload and download operations |

## Three Common Configuration Mistakes
- Symptom: Frontend page fails to load, and the console returns a `Failed to fetch` error. Cause: The `FE_DOMAIN` configuration does not match the actual access domain name, causing resource requests to fail to match the correct service address.
- Symptom: A network-related error is prompted when deleting an application. Cause: `STORAGE_S3_ENDPOINT` is not configured correctly, preventing the storage resources associated with the application from completing the release process normally.
- Symptom: Database connection timeout occurs, and the service experiences intermittent outages. Cause: The value of `DB_MAX_LINK` is too low, exhausting connection pool resources from concurrent requests and preventing new database connections from being established.

## How to Confirm Configurations Are Correct
- Log in to the corresponding cloud platform console, and verify that the load balancer port mapping rules match the configurations in the deployment documentation.
- Run a local network connectivity test to confirm that the services corresponding to `MONGODB_URI` and `REDIS_URL` are accessible normally.
- Send a frontend page access request, confirm that there are no errors in resource loading and interface calls, and that file upload and download functions can be triggered normally.
- Submit a small-scale configuration change, and verify that the configuration synchronization status between the change ticket and the cloud platform console is normal.

The values provided are common starting points, and should be evaluated against local deployment samples.
