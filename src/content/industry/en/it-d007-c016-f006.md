# Code Security Audit Online Fault Troubleshooting and Retrospective: Scheduled Tasks and Automation

## What Data for This Category Looks Like
Data for this category originates primarily from source code repositories, dependency manifests, Static Application Security Testing (SAST) tools, and public vulnerability databases. It is updated per project version or single audit task. Daily output documents include code audit reports, vulnerability proof documents, repair recommendation documents, and retest records. Fields include vulnerability severity, associated code lines, attack paths, repair verification status, and others. No unified fixed units exist; adjustments are made based on the scale and type of the audit target.

## Constraints Imposed by These Characteristics on Scheduled Tasks and Automation
Data sources for this category are scattered. Multi-source information must be regularly pulled from source code repositories, dependency manifests, SAST tools, and vulnerability databases. Scheduled tasks must therefore match code commit or version release rhythms to avoid incomplete pulls. Update frequency adjusts with project versions or single audit tasks; fixed cycles alone cannot cover all scenarios. A combined mode of scheduled polling and on-demand triggering must be supported. For documents such as multi-field audit reports and vulnerability proofs, automated processing requires field-based classification verification. For time-consuming links including dangerous function localization and data flow tracing, task sharding and priority scheduling must be configured to avoid task backlog and timeouts.

## Configuration Recommendations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Task Trigger Mode | Trigger on code commit events + full daily polling task at 00:00 | Matches the update rhythm of code audits, balances the timeliness of incremental scans and the completeness of full scans |
| Single Task Execution Duration Limit | 3600 seconds | Avoids occupying cluster resources of FastGPT v4.17.0 for extended periods, adapts to the complex data flow tracing links of code security audits |
| Task Failure Retry Count | 2-3 times | Addresses temporary network fluctuations or tool call exceptions, reduces resource usage from invalid retries |
| Failed Task Alert Threshold | Trigger alert after 2 consecutive failures | Notifies operations personnel of exceptions in a timely manner, prevents accumulated issues from leading to online vulnerabilities being deployed |
| Task Sharding Size | Calibrated via actual testing, single shard covers 100-200 code files | Balances task execution efficiency and resource usage, adapts to code repositories of different scales |
| Audit Result Sync Frequency | Sync after completing 1 shard | Prevents result backlog, facilitates real-time online fault troubleshooting and retrospective |

## Three Common Misconfigurations
- Phenomenon: After switching audit projects, mandatory global variable validation from the old project remains active, causing task execution errors. Cause: Associated context variable configurations are not cleared when switching tasks, resulting in residual historical configurations.
- Phenomenon: After a scheduled task triggers, the pulled source code files are empty, and task execution fails. Cause: No automatic renewal logic for repository access credentials is configured, causing expired credentials to fail to pull data sources.
- Phenomenon: After multiple consecutive audit tasks run, the counted number of vulnerabilities does not match the number actually discovered by the scan. Cause: No task deduplication rules are configured, resulting in repeated scanning of code segments that have already been audited.

## How to Verify Proper Configuration
- An incremental audit task is triggered manually. The number of pulled code files is verified against the number of files recently committed to the repository. Trigger rules are adjusted to match commit rhythms.
- A task failure scenario is simulated. Whether the preset alert notification is triggered is checked, and the alert threshold configuration is confirmed to be active.
- Task execution logs are reviewed. Shard size and execution duration are confirmed to match preset configurations, with no timeout errors.
- After switching audit projects, the task is verified to no longer validate mandatory variable configurations from the old project. The context cleanup logic is confirmed to be active.

The values provided are common starting points and should be measured against the reader's own samples.
