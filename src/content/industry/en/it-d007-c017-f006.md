# Online Troubleshooting and Retrospective for Code Review & Merge Management: Scheduled Tasks and Automation

## What this category of data looks like
This category of data primarily comes from Git repositories, CI pipelines, static scanning reports, and defect databases. Daily produced documents include merge requests, code review comments, commit records, and branch strategy descriptions. Unlike static code scanning categories, this category includes semantic judgments from manual reviews and maintenance boundary confirmation content. The data update rhythm is usually daily or triggered by code commits. Core fields include merge request number, submitter, reviewer list, changed file paths, branch name, review status, and defect association tags. There is no unified fixed unit, and it adapts to the native definitions of Git repositories and CI tools.

## What constraints these characteristics impose on the "scheduled tasks and automation" link
Data sources rely on the native interfaces of Git and CI tools, which are subject to interface call rate limits. Therefore, the scheduled task call interval must match the Git repository API quota. Data updates are triggered by code commits or daily, so automated tasks must adapt to both update rhythms and avoid repeatedly processing completed merge requests. The change impact judgment and conflict resolution links take a long time. Asynchronously executed scheduled tasks must set reasonable timeout thresholds to prevent task interruptions. If defect-associated review results are not synchronized in a timely manner, defects may flow into the main branch, cause build failures, or lead to online rollbacks. Therefore, tasks must include status verification and exception callback mechanisms.

## How to configure settings
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Task Trigger Timing | Trigger on code commit + full validation at 2:00 AM daily | Adapts to real-time review needs for code commits and daily batch scenarios for reviewing historical merge requests |
| Maximum Single Task Execution Duration | 1800 seconds | Matches the typical time range for change impact judgment and conflict resolution, preventing task timeout interruptions |
| Failure Retry Count | 3 times | Balances task success rate and resource consumption, addressing temporary interface fluctuations |
| Task Concurrency Limit | First 5 merge requests | Adapts to Git repository API call quotas, preventing rate limit triggers |
| Alert Trigger Threshold | 2 consecutive task failures | Notifies the R&D team in a timely manner to handle exceptions |
| Log Retention Period | 30 days | Meets log tracing needs for troubleshooting while controlling storage costs |

## Three common misconfigurations
- Duplicate merge request validation by scheduled tasks: This occurs when the trigger rule does not exclude completed merge request statuses, leading to repeated execution of the same task.
- Timeout interruptions for long-running review validation tasks: This happens when the single task execution duration is set too short, failing to cover the upper time limit for change impact judgment.
- Async API calls not associated with the corresponding merge request ID: This is caused by the task context not carrying a unique identifier, making it impossible to match execution results with the corresponding review task.

## How to confirm proper configuration
- Submit a test merge request, check whether the corresponding scheduled task is triggered after submission.
- Simulate a task timeout scenario to verify whether the preset alert notifications and retry mechanisms are triggered.
- View task logs to confirm that each merge request is processed only once, with no duplicate execution records.
- Check Git repository API call logs to confirm that task call rates do not exceed quota limits.

The values given are common starting points and should be measured against the reader's own samples.
