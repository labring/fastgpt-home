# Online Troubleshooting and Retrospective for Crowdsourced Annotator Management: HTTP Interfaces and External Systems

## What data for this category looks like
Crowdsourced annotator management daily documentation typically includes personnel access rules, training materials, performance reports, and settlement lists. Data sources mainly include the crowdsourcing platform’s own system, annotation quality feedback data, training exam records, and financial settlement systems. Data update frequencies are mostly daily or monthly. Core data fields cover personnel access qualifications, training assessment results, annotation quality scores, performance rankings, and settlement-related information. The overall workflow centers on human resource organization and performance settlement, differing from single-text annotation projects.

## What constraints these characteristics impose on HTTP interfaces and external systems
Because data sources involve multiple external entities such as crowdsourcing platforms, training systems, and financial systems, HTTP interfaces must adapt to multiple sets of authentication rules to ensure compliance with permission verification during docking. Data update frequencies cover daily and monthly cycles. Interfaces must support filtering data by time range to avoid returning excessive information in a single request. Core data fields include personnel qualifications, performance scores, and settlement information. The field format of `responseData` must strictly match business document definitions to prevent incorrect or missed payments caused by missing fields or format errors. Additionally, for time-consuming processes such as personnel screening and quality ranking, interfaces must support pagination and sorting parameters to improve data pulling efficiency.

## How to configure settings
This document is written based on FastGPT v4.17.0, and all configuration items adapt to the interface logic of this version.

| Configuration Item | Recommended Setting | Rationale |
| ---|---|--- |
| `Authorization` | Configure as a Bearer Token generated when docking with external systems, in the format `Bearer {actual token}` | Matches authentication specifications for most third-party APIs, ensures successful permission verification for interface calls |
| `variables` | Configure two types of variables: personnel ID and statistical cycle. Control the number of single request data at `800–1200` entries | Adapts to the batch pulling scale of crowdsourced annotator data, balances request efficiency and response stability |
| `responseData` | Map to fields for personnel access qualifications, performance scores, and settlement amounts | Strictly matches field definitions in business documents, avoids data parsing errors that cause quality or settlement issues |
| Timeout setting | 600 seconds | Adapts to the response duration of monthly batch data pulling, prevents interruptions caused by overly long request times |
| Retry count | 3 times | Addresses temporary call failures caused by network fluctuations, while avoiding duplicate settlement issues caused by repeated submissions |

## Three common configuration mistakes
- Phenomenon: The interface returns a `401 Unauthorized` status code, or the interface lacks permission to pull personnel data. Cause: The `Authorization` parameter configuration format is incorrect, or the token has expired and has not been updated.
- Phenomenon: When forwarding the interface through a middle service, page data remains fixed after streaming data reception is interrupted, and the latest annotator performance data cannot be obtained. Cause: No timeout reconnection mechanism is configured, and no breakpoint resume parameter is set, so data pulling cannot resume after an interruption.
- Phenomenon: Incorrect payments occur during settlement verification. The settlement amount field in the `responseData` returned by the interface is empty or does not match the required format. Cause: `responseData` fields are not mapped strictly according to business document definitions, leading to abnormal data parsing.

## How to confirm correct configuration
- Send a single personnel information pull request, confirm that `Authorization` authentication passes, and the fields returned in `responseData` fully match the personnel access rules document.
- Send a batch data request, verify that the number of returned data entries matches the scale set by the configured `variables` parameter, with no obvious timeouts.
- Simulate temporary network fluctuations, check whether the interface triggers the retry mechanism, and does not cause duplicate submission of performance or settlement data.
- Connect to a test financial system interface, confirm that the format of the settlement amount field matches the requirements specified in the business document.
