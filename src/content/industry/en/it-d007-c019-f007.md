# Online Troubleshooting and Retrospective for Crowdsourced Annotator Management: Conversation Logs and Auditing

## What this category of data looks like
This category of data primarily comes from crowdsourcing platform backends, annotation quality statistics systems, personnel training exam records, and financial settlement systems. Daily associated documents include personnel access rules, post training materials, monthly performance sheets, and settlement statements. Data updates occur on a daily and monthly basis, covering fields such as personnel qualifications, annotation quality, assessment results, and settlement details. Fields include personnel ID, annotation task volume, pass rate, settlement amount, and others, with no additional custom units.

## What constraints these characteristics impose on the conversation logs and auditing workflow
Since data sources are scattered and cover multiple types of information including personnel qualifications, annotation quality, and financial settlement, conversation logs must support multi-dimensional associated retrieval. Supported dimensions include personnel ID, task batch, settlement cycle, and others.
Data updates follow daily and monthly cycles. Logs must support filtering by precise time intervals to avoid mixing data across cycles.
Daily associated documents must be bound to corresponding personnel and tasks. During auditing, consistency between log content, access rules, and performance sheets must be verified. Complete conversation links and operation traces must be retained, and no truncation or tampering is allowed.
Error consequences include annotation quality fluctuations and settlement errors or omissions. Logs must retain sufficient details to locate the root cause of problems. Missing or incomplete log fields must be avoided.

## Configuration Setup
This applies to the configuration logic of FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Combined ID binding task batch and personnel ID | Used to associate all conversation logs of annotators in the same batch, enabling retrieval by task or personnel dimension |
| `responseChatItemId` | Retain complete session node ID | Used to trace the complete interaction link of a single annotation conversation, matching single-task results in annotation quality data |
| `detail` | Enable full log storage | Retain details such as personnel qualification queries and settlement checks in conversations, meeting audit traceability requirements |
| Single log storage limit | 1000 MB | Adapt to the storage needs of monthly settlement data and batch annotation logs, avoiding disk overflow |
| Log retrieval time range | Last 30 days / Last 180 days | Match daily and monthly data update cycles, facilitating cross-cycle problem troubleshooting |
| Audit log export format | CSV format | Facilitate batch verification and checking with settlement statements from financial systems |

## Three Common Misconfigurations
- Phenomenon: Irrelevant data across task batches appears when retrieving logs. Cause: `chatId` is not used to bind task batches and personnel IDs. Only general session IDs are used for retrieval, resulting in disordered data scope.
- Phenomenon: The complete conversation for settlement checks cannot be traced in audit logs. Cause: Full log storage via `detail` is not enabled. Only basic interaction content is retained, failing to cover operation details related to settlement.
- Phenomenon: Database connection failure is returned when calling logs, and the database service status is normal. Cause: Log storage database connection parameters are not configured correctly, or container network policies restrict communication between the log component and the database.

## How to Verify Successful Configuration
- Retrieve logs for a specified task batch. Verify that returned results only include conversation data of personnel from that batch, confirming the `chatId` configuration takes effect.
- View the log details of a single session. Confirm that the complete interaction link and `responseChatItemId` field are included, verifying that the node tracing function works properly.
- Export audit logs. Check whether key fields such as personnel ID, task batch, and settlement amount are included, confirming that the `detail` storage configuration is correct.
- Simulate a log write operation in an internal network environment. Verify that logs can be stored normally with no missing fields, confirming that storage parameter configuration is correct.

The values provided are common starting points and should be measured against the reader's own samples.
