# Online Troubleshooting and Retrospective for Supply Chain Security and Open Source Dependency Governance: Scheduled Tasks and Automation

## What this category of data looks like
Data for this category originates from package managers, code repositories, public vulnerability databases, and license databases. Updates occur via daily synchronization or when code versions are released. Daily generated documents include SBOM lists, dependency risk reports, license lists, and repair work orders. Core fields include dependency package name, version number, vulnerability CVE ID, license type, and risk impact level. No fixed statistical units exist. The number and type of fields adjust dynamically based on the asset scan scope.

## Constraints on scheduled tasks and automation
Data sources for this category are scattered and cover broad ranges. Full-volume scans take significant time to complete. Scheduled tasks must use appropriately divided execution windows to avoid occupying core business resources. The update rhythm supports both daily synchronization and version-triggered modes. Automated tasks must adapt to both trigger logics. Document fields are closely interconnected. Automated workflows must verify the completeness of fields such as dependency package names, vulnerability information, and license types to prevent missing critical risk items. Task execution failures can lead to high-risk dependencies being deployed or license violations. Automatic retries and manual alert links must be configured after task failures.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Task execution window | `22:00–06:00` | Avoids peak business hours, reduces resource usage on online services, and aligns with FastGPT v4.17.0 scheduling rules |
| Trigger timing | Daily fixed time + code version push trigger | Adapts to both daily synchronization and version update data update rhythms, covering full-volume and incremental scan scenarios |
| Scan concurrency | `2–4 threads` | Balances scan efficiency and server resource consumption, calibrated via actual testing |
| Failure retry count | `2 times` | Prevents task failure from temporary network fluctuations, reduces resource waste from invalid retries |
| Field verification scope | Dependency package name, version number, vulnerability level | Covers necessary fields for core risk identification, reduces false positive rates |
| Alert trigger threshold | High-risk vulnerability count ≥1 | Prioritizes responding to the most urgent supply chain security risks, aligns with online troubleshooting priority |

## Three common misconfigurations
- Symptom: Scheduled tasks return a `404: not found` error after execution, and logs show a failed dependency package index request. Cause: Automatic switching logic for package manager mirror sources is not configured, making the default source address inaccessible during cross-region scans.
- Symptom: Image links in automatically generated SBOM lists lack domain name prefixes, only retaining relative paths. Cause: The static resource domain name auto-completion function is not enabled in scan configurations, and this feature only takes effect in the manual import workflow.
- Symptom: Static page updates are not synchronized to the knowledge base dependency risk report. Cause: Incremental scan tasks triggered by version pushes are not configured, and only daily full-volume scans are relied on, which cannot respond to page content changes in a timely manner.

## How to confirm proper configuration
- Manually trigger a scheduled task, check the task execution log, and confirm that the configured verification fields are included in the scan scope.
- Simulate a code version push to verify whether the task executes according to the configured trigger logic.
- Construct a dependency combination containing high-risk items to verify whether the preset alert process is triggered after a task failure.
- View automatically generated documents to confirm that static resource links have been supplemented with relevant information as configured.

The values provided are common starting points and should be measured against the reader's own samples.
