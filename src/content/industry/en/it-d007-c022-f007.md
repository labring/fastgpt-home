# Online Troubleshooting and Retrospective for Trusted Innovation Replacement Adaptation: Conversation Logs and Auditing

## What this category’s data looks like
This data primarily comes from existing system inventories, domestic hardware and software directories, test environments, and publicly available vendor materials. Daily associated documents include adaptation lists, compatibility test reports, migration plans, and issue ledgers. Data is updated on a per-project cycle or quarterly basis. Fields cover hardware and software models, compatibility verification results, migration steps, and fault records. There is no unified mandatory format, and it must be organized to fit the actual project scenario.

## What constraints these characteristics impose on the "conversation logs and auditing" workflow
Since data sources cover multiple scattered resources such as existing system inventories and domestic hardware and software directories, conversation logs must support associating adaptation verification records and issue ledgers from different sources. Updates are made on a per-project or quarterly cycle, and high-frequency real-time archiving is not required, but complete audit trails of the full interaction chain must be retained for cross-cycle retrospective analysis. Fields have no unified mandatory format, so log collection must support custom fields, while also supplementing contextual information such as hardware and software models and migration steps. For compliance audits related to domestic adaptation, logs must retain complete call chains and parameter change records to avoid missing fields or content truncation.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `chatId` | Bind to the unique identifier of the project adaptation | Associate conversation logs with the adaptation list and migration plan of a single project, enabling auditing by project dimension |
| `responseChatItemId` | Associate with a single hardware or software verification request | Accurately track the interaction process of a single compatibility test and locate fault trigger nodes |
| `detail` | Store 800–1200 characters of contextual information | Adapt to scenarios where fields have no unified format, supplementing content such as hardware and software models and test environment parameters |
| Log retention period | 90 days | Match per-project cycle and quarterly update frequency, meeting cross-cycle retrospective requirements |
| Full log collection switch | Enabled | Fault troubleshooting requires complete interaction chains, avoiding missing abnormal calls during the adaptation process |
| Audit keyword configuration | Match against the adaptation fault keyword library | Quickly filter log entries containing compatibility errors or parameter mismatches |

## Three common configuration mistakes
- Symptom: The front-end interface outputs incomplete content, no error information appears in the logs, and refreshing the page displays the complete content. Cause: Complete contextual storage of the `detail` field is not enabled, resulting in log truncation, and the front end cannot load complete interaction data during rendering.
- Symptom: Unable to filter conversation logs during the adaptation process by project dimension. Cause: `chatId` is not bound to the project adaptation identifier, resulting in logs being unable to be associated with project documents, and the audit dimension is missing.
- Symptom: Unable to count high-frequency issues or token usage during the adaptation process. Cause: `responseChatItemId` is not configured to associate with single requests, and full log collection is not enabled, making it impossible to obtain complete interaction data for statistics.

## How to confirm the configuration is correct
- Confirm that the `chatId` field matches the project adaptation identifier to verify the association between logs and project documents.
- Randomly select one adaptation conversation log and verify that the `detail` field contains the required contextual information, confirming that the storage length meets the configuration requirements.
- Trigger a compatibility test request and confirm that the `responseChatItemId` field correctly associates with this request, enabling accurate positioning of the interaction node.
- Review the log retention period configuration and confirm that it meets the project cycle and audit requirements, with no early cleanup occurring.
