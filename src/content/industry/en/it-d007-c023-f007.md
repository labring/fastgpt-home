# Online Troubleshooting and Retrospective for IT Budget and Project Portfolio Management: Conversation Logs and Auditing

## What this category’s data looks like
Typical users of this category include CIO offices, PMOs, and financial business partners. Core data is sourced from financial systems, project management systems, contract ledgers, and business department requirements. Four core documents are routinely produced: annual budget sheets, project proposal documents, project portfolio dashboards, and investment retrospective reports.

Data fields include budget amount, project cycle, priority, revenue forecast, and more. Common units are ten thousand yuan and calendar days. Data update cycles follow monthly, quarterly, and annual schedules:
- Monthly budget allocation adjustments
- Quarterly project progress and portfolio dashboard updates
- Annual overall investment retrospective completion

## Constraints on Conversation Logs and Auditing
As core tools for CIO offices, PMOs, and financial business partners, conversation logs for this category must meet dual internal auditing and management retrospective requirements.

The category’s data is multi-source heterogeneous and has long update cycles. Conversation logs must link to unique project identifiers. This ensures traceability to specific budget and project information during audits.

Core documents contain sensitive budget amount and priority fields. Logs must filter non-essential content, only retaining fields relevant to the category.

Annual retrospective auditing requires log retention periods to cover full business cycles. Redundant storage of non-core multi-system data must be avoided.

Errors in this category directly impact management decisions. Logs must fully record every operation and associated data at each conversation node. This allows reproduction of decision links during troubleshooting.

## How to Configure
This configuration guide uses FastGPT v4.17.0. Specific configuration items are listed below:

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind to project ID to generate a globally unique identifier | Associate conversations with corresponding IT projects to facilitate audit traceability |
| `responseChatItemId` | Auto-generate per conversation node | Precisely locate the audit trail of a single reply, matching multi-node conversation scenarios |
| `detail` | Store core budget and project fields | Cover core dimensions of category data, reducing redundant storage |
| Conversation log retention period | 180 days | Match auditing cycle requirements for quarterly and annual retrospectives |
| Log storage threshold | 1000 MB | Adapt to monthly updated document volume, avoiding storage overflow |
| `detail` field filtering rules | Only retain core fields such as budget amount and project priority | Align with category data characteristics, controlling storage costs |

## Three Common Configuration Errors
- Phenomenon: MongoDB connection fails after Docker deployment, with logs indicating authentication errors. Cause: Fields from finance and project systems associated with the category are not written to the `detail` field, causing initialization verification to fail.
- Phenomenon: Logs repeatedly report slow operation timeouts during knowledge base parsing. Cause: Batch storage rules for the `detail` field are not configured, and the volume of multi-dimensional data for a single write to the category exceeds the system threshold.
- Phenomenon: Chat records are not saved to the database after closing the SSE connection. Cause: `chatId` is not bound to the project ID, and persistence verification is not triggered, resulting in incomplete data writing when the session is interrupted.

## How to Verify a Successful Configuration
- Initiate a conversation associated with a specific project ID, and check the logs for complete `chatId` and `responseChatItemId` fields.
- Log in to the MongoDB database, and verify whether the `detail` field contains core category data such as budget amount and project priority.
- Simulate an SSE connection interruption, and confirm that logs are automatically written to the database after the session ends with no data loss.
- Verify that the log retention period reaches the preset 180 days, and expired logs automatically trigger the cleanup process.
