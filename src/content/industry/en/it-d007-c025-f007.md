# Online Troubleshooting and Retrospective for Shift Scheduling and Handover: Conversation Logs and Auditing

## What the data for this category looks like
Data sources for this category include scheduling systems, fault tickets, monitoring alerts, and organizational contact directories. Update frequency is daily or weekly. Daily produced documents include shift schedules, handover records, escalation contact lists, and shift daily reports. Fields cover shift time periods, pending handover items, associated fault ticket numbers, escalation contact information and contact details, with no additional statistical values included.

## Constraints on Conversation Logs and Auditing
The data sources for this category are scattered and linked to multiple business systems. Conversation logs must be bound to the corresponding scheduling system ID, fault ticket number, and alert identifier to enable quick location of associated business nodes during audits. The update frequency is daily or weekly, so the audit cycle must match this rhythm to avoid overly short or long log retention periods. Daily documents include multiple types of structured content. Conversation logs must cover complete conversations for core links such as shift coordination, pending item handover, and escalation path confirmation. Communication records for escalation contacts must also be retained to ensure no gaps in the handover process.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Conversation log retention period | 7 days | Matches the weekly update rhythm of shift documents for this category, covering audit needs for complete shift cycles |
| `chatId` binding rule | Bind to the shift team ID of the corresponding scheduling system | Ensure logs can be associated with specific shift teams, enabling traceability of handover and troubleshooting records by team |
| `detail` field collection scope | Include pending items, escalation paths, and shift conflict coordination content | Covers the three most time-consuming core links of this category, meeting full traceability requirements for audits |
| `responseChatItemId` association rule | Bind to the unique number of the fault ticket | Enable precise association between conversations and specific faults, facilitating quick location of problem handling links during retrospectives |
| Single audit query limit | Top 20 entries | Matches the daily troubleshooting scale of shift teams, avoiding excessive occupation of query resources |
| Maximum size per log entry | 100 KB | Avoid excessive occupation of storage resources, adapting to the content length of daily conversations |
| Audit log trigger interval | 60 seconds | Matches the real-time push rhythm of monitoring alerts, ensuring fault conversations are saved promptly |
| Log export format | Markdown format | Can be directly imported into shift daily report documents, aligning with the usage habits of daily documents for this category, and compatible with FastGPT v4.17.0 export APIs |

## Three Common Configuration Errors
- Symptom: Conversation logs only display system instruction content, with no user original question records, and the `detail` field is empty. Cause: Full collection configuration for the `detail` field is not enabled, only system preset instructions are collected, and user original question content is omitted.
- Symptom: Conversations about shift conflict coordination are not captured by audit logs, and the number of audit results is 0. Cause: The scheduling system ID is not bound to `chatId`, causing logs to fail to associate with specific shift scenarios and be excluded by filtering rules.
- Symptom: Operation buttons remain unresponsive after submitting a fault troubleshooting conversation. Checking system logs shows upload succeeded but no subsequent logs are generated. Cause: The binding rule between `responseChatItemId` and fault tickets is not configured, causing the system to fail to complete the audit log submission verification and block the operation process.

## How to Verify Correct Configuration
- Randomly select a shift handover conversation from the current day, check if the `detail` field includes core content such as pending items and escalation paths, confirming the collection scope matches the configured requirements.
- Import a test scheduling system ID, verify that `chatId` is correctly bound to the corresponding shift team, ensuring logs can be filtered by team.
- Submit a conversation for a simulated fault ticket, check if `responseChatItemId` is associated with the ticket number, verifying the audit log trigger logic.
- View the log storage directory, confirm that audit log files for the configured retention period have been generated, matching the configured storage period requirements.
