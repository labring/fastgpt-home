# Troubleshooting and Post-Mortem for Online Incidents in Content Review Rule Operations: HTTP Interfaces and External Systems

## What the data for this category looks like
Data for this category primarily comes from content review backends, user reporting channels, public regulatory and policy documents, and industry review sample libraries.
Daily maintained documents include review rule details, violation disposal guidelines, user appeal records, and quarterly quality inspection reports.
Update cycles follow daily syncs for rule iterations from review backends, plus emergency updates triggered by policy adjustments.
Document structures primarily use structured fields. Review rules include trigger thresholds and matching keyword groups. Appeal records include user IDs, violation determination bases, and review results. The sample library stores annotated violation and compliance content snippets.

## What constraints these characteristics impose on the HTTP Interfaces and External Systems link
Data sources for this category are scattered, and update schedules are inconsistent. This requires HTTP interfaces to support real-time pulling of the latest review rules and appeal records, to avoid judgment deviations caused by expired configurations.
Field structures vary across multiple document types. Some fields, such as appeal review results and sample annotation tags, are dynamically changeable. This requires interfaces to support dynamic parsing of `responseData`.
Keyword groups in review rules have a wide length range. This requires support for receiving variable-length `variables` parameters.
Data involves compliant content. The `Authorization` field of the interface must carry a compliance verification identifier to prevent leakage of sensitive review data.
Sudden policy updates may trigger batch interface calls. This requires configuring reasonable timeout and retry strategies.

## How to Configure
This configuration logic applies to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Carry a compliance verification token, formatted as `Bearer {compliance verification string}` | Meet compliance transmission requirements for content review data, prevent unauthorized access to sensitive review rules and appeal data |
| `variables` | Pass review rule parameters with a length of `200–5000 characters` | Cover rule configuration lengths for most review scenarios, adapt to dynamically variable rule structures |
| `responseData` | Configure to automatically parse structured JSON responses | Adapt to dynamic field structures across multiple types of review documents, simplify post-ingestion data processing |
| Interface timeout period | Set to `30–60 seconds` | Match average response durations for review rule pulls and sample library queries |
| Retry strategy | Retry `3 times` after failure, with a single retry interval of `5 seconds` | Address temporary call failures caused by network fluctuations, reduce process interruptions |
| Data cache duration | Set to `1 day` | Match the daily update frequency of review rules, balance real-time performance and interface call pressure |

## Three Common Misconfigurations
- Phenomenon: Historical version documents returned after interface calls lack the `tmbId` field, making association with the review sample library impossible. Cause: No field completion logic was configured for old version data, leading to missing necessary association identifiers in pulled historical rule data.
- Phenomenon: Interfaces are accessible normally via local Docker Compose deployments, but trigger connection exceptions when called through a third-party forwarding service. Cause: No cross-domain whitelist was configured between the forwarding service and FastGPT, or `Authorization` verification information was not correctly passed in forwarding headers.
- Phenomenon: Password-free shared links cannot carry user database identification IDs, making it impossible to distinguish review data ownership in multi-tenant scenarios. Cause: No delivery rules for database identification were configured in shared link parameters, and the identification was not written into request parameters of the jump link.

## How to Verify Successful Configuration
- Call the interface to pull historical version documents, check whether returned results include the `tmbId` field to confirm the field completion logic is active.
- Configure forwarding rules, initiate a test call, and confirm the interface returns normal review rule data with no connection exception errors.
- Generate a password-free shared link, check whether link parameters or jump request headers include the user database identification ID.
- Initiate a batch rule pull request, confirm no timeout errors are triggered, to verify the timeout configuration matches business scenario requirements.

The values provided here are common starting points and should be evaluated against the reader's own samples.
