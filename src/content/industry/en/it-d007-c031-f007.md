# Online Troubleshooting and Retrospective for Creator Onboarding and Certification: Conversation Logs and Auditing

## What the Data for This Category Looks Like
Core data for this category originates from the creator backend, enterprise credit information query API, account history system, and contract management system. Data updates trigger per onboarding application, at nodes including application submission, qualification verification, certification completion, and contract signing. Daily processed documents include onboarding application forms, identity qualification scans, certification audit records, cooperation agreements, and more. Data fields include application unique identifier, creator account information, qualification file number, audit status, interaction conversation ID, and others. There are no unified fixed unit requirements, and values vary by document type.

## Constraints Imposed on Conversation Logs and Auditing by This Category’s Data Characteristics
Three core constraints apply to the conversation logs and auditing process from this category’s data characteristics:
1.  Data sources are scattered and linked to external systems. Logs must be bound to the application unique identifier and external system ID to avoid mixing logs across different applications.
2.  Updates trigger per individual application. Logs must be stored and retrieved per application dimension to prevent poor retrieval efficiency caused by global session aggregation.
3.  Core documents include qualification materials and audit records, and errors may lead to false certifications or benefit misalignment. Logs must retain full interaction details, and must not store only summary content.

Additionally, the two most time-consuming business links — qualification verification and risk judgment — require logs to be accurately associated with corresponding interaction nodes. This allows operation personnel to quickly locate faulty links.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind the creator application unique identifier as a prefix | Matches the category’s requirement to manage data per application dimension, enabling full conversation log retrieval per individual onboarding application |
| `responseChatItemId` | Associate interaction nodes from qualification verification and risk judgment links | Corresponds to the two most time-consuming business links in the category, enabling precise location of core audit conversation content |
| `detail` | Enable full field storage mode | Covers full interaction details for core category documents including onboarding applications, qualification materials, and audit records |
| Log storage path | Mount an independent 800–1200 MB disk partition | Adapts to the log volume generated per individual application, preventing system storage overflow |
| Log retention period | Set to 150–200 days after application completion | Covers the traceability window for cooperation disputes and qualification verification disputes, meeting compliance retention requirements |

## Three Common Misconfigurations
- Phenomenon: Conversation log detail page content does not match actual audit responses, and fixed content is displayed after multiple conversations. Cause: `responseChatItemId` is not correctly bound to the interaction node of the qualification verification link, leading to incorrect log association with conversation branches.
- Phenomenon: Full creator onboarding conversation records cannot be exported, only single fragments can be obtained. Cause: Batch retrieval interface permissions per `chatId` are not configured, and only single-node log queries are enabled.
- Phenomenon: The system prompts log storage failure, and runtime logs cannot be saved to the specified file. Cause: No disk partition meeting capacity requirements is mounted, or the storage path configuration does not match FastGPT v4.17.0 directory rules.

## How to Verify Successful Configuration
- Initiate a simulated conversation for creator onboarding qualification verification, retrieve logs via `chatId`, and confirm returned content includes complete application information and interaction steps.
- Check the log storage directory, confirm generated log file sizes fall within the preset partition capacity range, with no overflow errors.
- Trigger an abnormal interruption of an audit process, and confirm the `detail` field stores full abnormal interaction details and error messages.
- Verify the log retention period, confirm old logs exceeding the period are automatically archived or deleted in line with preset rules.

The values provided are common starting points and should be measured against the reader's own samples.
