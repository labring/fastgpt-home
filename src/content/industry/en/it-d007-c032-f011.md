# Online Troubleshooting and Retrospective for Creator Incentive Settlement: Database and Operations

## What the Data for This Category Looks Like
Daily documents for this category include incentive rules, settlement details, appeal records, and payment lists. Data sources include content data, advertising revenue sharing systems, financial systems, and creator account backends. Data update frequency is usually monthly or per single activity cycle. Core data fields include creator ID, earnings amount, appeal status, payment serial number, and others. Units include yuan for monetary amounts, timestamps, status codes, and more. In daily processing, earnings caliber verification, abnormal fraud detection, and payment material verification are the most time-consuming steps. Multiple systems are associated to generate data results, which requires high field consistency.

## What Constraints Do These Characteristics Impose on Database and Operations Workflows
Multi-source data access requires databases to support cross-system field mapping and batch writing. Concentrated updates during monthly or single activity cycles will cause sudden concurrent peaks. Sufficient connection and storage resources must be reserved. Complex earnings verification and fraud detection require frequent execution of multi-table join queries. Index structures must be designed appropriately to reduce query latency. Appeal records and payment lists require tamper-proof, high-availability storage to avoid data loss that could lead to settlement disputes. Additionally, the serious consequences of incorrect or missed payments require operations workflows to include data verification and rollback capabilities to ensure the accuracy of business data.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Bind to a dedicated replica set for settlement details and appeal records | Isolate core business data to avoid resource occupation by non-settlement traffic |
| `PG_URL` | Point to a read-only node for incentive rules and payment lists | Support complex aggregate queries for earnings caliber verification without affecting primary database write performance |
| `DB_MAX_LINK` | 120–180 | Match concurrent peaks during monthly settlement cycles to prevent connection pool exhaustion |
| `REDIS_URL` | Deploy as a local cache instance, set expiration time to 3600 seconds | Cache frequently accessed creator account information to reduce cross-system query latency, compatible with FastGPT v4.17.0 caching mechanism |

## Three Common Misconfigurations
- Symptom: `503 Service Unavailable` errors occur during settlement peak periods. Logs show database connection pool exhaustion. Cause: The `DB_MAX_LINK` parameter was not adjusted to match concurrent peaks during the settlement cycle. Connection count is insufficient to support bulk settlement requests.
- Symptom: Database tables for settlement details cannot be created after local deployment. A `relation not exists` error is thrown during startup. Cause: Table initialization statements related to incentive settlement were not added to the deployment script, or DDL operation permissions were not configured correctly.
- Symptom: As concurrency increases, query latency for creator appeal records exceeds expectations, and the number of returned results is abnormal. Cause: No composite index was created for the creator ID and appeal time fields, leading to excessively long full table scan latency.

## How to Confirm Configuration Is Complete
- Run concurrent stress tests during the monthly settlement cycle. Observe whether database connection counts fluctuate within the range set by `DB_MAX_LINK`, with no connection timeouts.
- Review cross-system data synchronization logs to confirm that fields from content data and advertising revenue sharing systems have been correctly mapped to corresponding fields in settlement details.
- Simulate creator appeal queries to verify that query latency falls within acceptable business ranges. Adjust index configurations based on actual business scenarios.
- Check the cache instance corresponding to `REDIS_URL` to confirm that frequently accessed account information has been successfully cached, with no cache breakdown events.

The values provided are common starting points and should be evaluated against local deployment samples.
