# Online Troubleshooting and Retrospective for Office System Process Configuration: Database and Operations

## What this category’s data looks like
The data for this category is generated around enterprise office process configuration scenarios. Daily documents include process configuration sheets, approval node tables, form field descriptions, and change records. Data mainly comes from OA systems, organization architecture databases, internal system documents, and frontline user feedback. Updates are triggered by process changes, with at least one batch update per month following centralized maintenance operations. Data fields include approval node permissions, form validation rules, circulation path configurations, etc., with no unified fixed units, changing dynamically based on configuration item attributes.

## What constraints these characteristics impose on the database and operations link
The non-standardized fields and low-frequency update characteristics of office process configuration data require the database to support flexible document-style storage structures, adapting to dynamic fields such as approval nodes and permission rules. The random update rhythm triggered by changes makes storage solutions with strong consistency and high-concurrency writes unsuitable, and a batch synchronization window after configuration changes must be reserved. Data is associated with organization architecture and user feedback, requiring the operations link to ensure the stability of cross-data-source associated queries, avoiding process approval interruptions caused by single-point failures. At the same time, change records must be fully retained, and the database must support the ability to query by change time for retrospective analysis to support process retrospection after failures.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://<db-user>:<db-pass>@<db-host>:27017/fastgpt_flow?authSource=admin` | Adapts to the document-style storage requirements of process configurations, specifies the business database name and authentication source to ensure data isolation and access security |
| `PG_URL` | `postgresql://<audit-user>:<audit-pass>@<db-host>:5432/fastgpt_audit?sslmode=require` | Used to store structured data such as change records, SSL mode ensures data security during transmission |
| `DB_MAX_LINK` | `20–30 connections` | Adapts to the low-frequency write and on-demand query scenarios of office process configurations, avoiding service interruptions caused by exhausted database connection pools |
| `REDIS_URL` | `redis://<redis-pass>@<redis-host>:6379/0` | Used to cache frequently accessed approval node rules, reducing repeated query pressure on the database |
| Approval node cache validity period | `300 seconds` | Balances configuration update timeliness and query performance, adapting to the monthly centralized change rhythm |

## Three common misconfigurations
- A "connection timeout" or "authentication failed" error occurs when the workflow calls database tools. The cause is that the database authentication account and password are not correctly filled in the `MONGODB_URI` configuration, or the network policy restricts outbound access to port 27017.
- Approval nodes become unresponsive after process configuration is saved. The cause is that `DB_MAX_LINK` is set too low, causing the database connection pool to be exhausted and unable to process new configuration query requests.
- Historical configuration modification content cannot be retroactively viewed via change records. The cause is that the structured storage library corresponding to `PG_URL` is not configured, or the database audit log write permission is not enabled.

## How to confirm the configuration is complete
- Log in to the FastGPT v4.17.0 system settings page, enter the database configuration module, and verify that the connectivity test results for `MONGODB_URI` and `PG_URL` show "Normal".
- Initiate an office process configuration change submission operation, wait 1–2 minutes, and check whether the corresponding change record entry is generated in the database.
- Call the database query tool in the workflow, enter the preset approval node query statement, and confirm that the returned result matches the configured content.
- View the Redis monitoring panel, confirm that the connection count of the cache instance corresponding to `REDIS_URL` is within the normal range, with no persistent alarms.

The values given are common starting points and should be measured against the reader's own samples.
