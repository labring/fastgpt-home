# Online Troubleshooting and Retrospective for Unit and Component Testing: Deployment and Upgrade

## What data for this category looks like
Data for this category primarily comes from code repository commit records, coverage reports generated by unit and component testing frameworks, requirement documents, and interface definition files. The data update schedule is daily synchronization or updates triggered by code commits. Daily produced documents include standardized test cases, coverage statistics reports, Mock interface instructions, and defect tracking sheets. Data fields include code unit identifiers, test case IDs, coverage ratios, Mock rules, and defect statuses. No additional custom units are used; only native numerical and status fields from the testing framework are retained.

## What constraints these characteristics impose on deployment and upgrade
Decentralized data sources that update frequently with commits require the deployment process to support concurrent configurations for pulling multi-source data. This avoids pulling timeouts caused by dense commit volumes. The high-frequency update characteristic requires that a fault-tolerant mechanism for incremental data synchronization is retained during upgrades. This prevents test data loss caused by full synchronization interruptions. The structured nature of documents such as test cases and defect sheets requires a data parsing format compatible with existing testing frameworks during deployment. This avoids test case loading failures caused by format mismatches. Additionally, usage scenarios for quality engineering teams require post-deployment services to isolate test data by commit branches. This prevents interference between test data from different branches.

## How to configure settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–200 connections` | Adapts to the concurrent request logic of the testing framework for FastGPT v4.17.0, to avoid exhausting the database connection pool |
| `REDIS_URL` | `redis://:[custom password]@[deployment host IP]:6379/0` | Stores temporary test case Mock rules and incremental coverage cache, to reduce resource consumption from repeated calculations |
| `STORAGE_S3_ENDPOINT` | `Set based on actual testing` | Adapts to the storage paths for test reports and defect sheet attachments, and must match the file upload configuration of the testing framework |
| `FE_DOMAIN` | `http://[local deployment domain]:3000` | Provides accessible jump links for test result pages, ensuring testers can directly view detailed test case execution logs |
| `ROOT_KEY` | `Randomly generated 32-character sequence` | Serves as the authentication key for internal test data management interfaces, to prevent unauthorized modification or deletion of test cases |
| `FILE_TOKEN_KEY` | `15 minutes` | Configures the access token validity period for test report attachments, to avoid unauthorized file access caused by token leakage |

## Three Common Misconfigurations
- Symptom: Unable to create a test administrator account after initial deployment, with the interface prompting "Invalid authentication key". Cause: `ROOT_KEY` or `FILE_TOKEN_KEY` was not configured correctly, leading to authentication failure for the internal user management interface.
- Symptom: Full coverage report generation times out, blocking the CI/CD build pipeline. Cause: `DB_MAX_LINK` is set too low, and the database connection pool cannot handle high-frequency test data pulling requests.
- Symptom: Mock rules for test cases do not take effect, and interface calls return empty data. Cause: The access path for `REDIS_URL` was not configured correctly, preventing the Redis cache from storing temporary Mock configurations.

## How to Verify Correct Configuration
- Execute the commit trigger script from the local testing framework. Confirm that test cases can be pulled normally and coverage reports can be generated. This verifies that database and Redis connection configurations are correct.
- Access the domain configured in `FE_DOMAIN`. Verify that the test result page loads normally. This confirms correct frontend domain binding.
- Call the internal test data management interface, using `ROOT_KEY` for authentication. Confirm that the interface responds normally. This verifies correct authentication configuration.
- Upload a test report attachment to the specified storage path. Verify that the storage service configured in `STORAGE_S3_ENDPOINT` can read and write files normally.

The values provided are common starting points and should be evaluated against the reader's own samples.
