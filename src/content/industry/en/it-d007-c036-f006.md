# Online Troubleshooting and Retrospective for Prototype and Interaction Design: Scheduled Tasks and Automation

## What data for this category looks like
Core data for this category typically comes from Figma, Axure files, internal team design systems, user feedback, and usability test records. Teams create daily deliverables including interactive prototypes, page flowcharts, component descriptions, and review records. These deliverables include fields such as page paths, interactive actions, component attributes, and review comments. Teams typically update data weekly or aligned with product version iterations. A single update adjusts the interactive logic of a single page or full module.

## Constraints imposed by these characteristics on scheduled tasks and automation
Most data for this category consists of static prototype files with irregular update cycles. Scheduled tasks must align with version iteration cycles to avoid excessive system resource usage. Prototype files contain large numbers of graphics and path descriptions. Automated tasks must support parsing logic for different formats. Scheduled synchronization of scattered review records ensures data integrity. Supplementing abnormal interactive logic scenarios relies on batch verification of historical data. Improper scheduled task trigger timing may lead to deviations in the understanding of interactive paths during the development phase.

## How to set configurations
| Configuration Item | Recommended Configuration | Rationale |
| --- | --- | --- |
| Scheduled task trigger cycle | `12 hours` or `per version iteration node` | Aligns with weekly or version-level data update frequency, avoids redundant execution |
| File parsing batch limit | First 20 files | Adapts to the single-batch size of Axure and Figma files, prevents single-task timeouts |
| Index recall limit | `recall_top_k = top 8 entries` | Core interactive paths for prototype pages typically do not exceed 8, covering core troubleshooting scenarios |
| Similarity verification threshold | `similarity_threshold = 0.75` | Distinguishes valid interactive action descriptions from irrelevant content, ensures verification accuracy |
| Text embedding model | `embedding_model = general text model` | Adapts to the characteristics of prototype files, which are primarily text and simple graphics |
| Global variable synchronization cycle | `600 seconds` | Aligns with the response rhythm of regular configuration updates, resolves issues where global variables do not update automatically |
| Failure alert threshold | 3 consecutive failures | Avoids alert triggers from single temporary exceptions, ensures alert effectiveness |

## Three common mistakes
- Phenomenon: In local deployment scenarios, the knowledge base does not automatically index image resources in prototype files. Cause: Scheduled file parsing tasks are not configured, and only manual triggers are used, resulting in non-text resources such as images not being synchronously parsed.
- Phenomenon: API calls return 404 - Resource Not Found. Cause: The configuration was not updated after the file path of the Figma/Axure file targeted by the scheduled task changed, causing the system to fail to locate the target resource.
- Phenomenon: Set global variable values do not update automatically. Cause: The scheduled synchronization cycle is set too long, and does not align with the update rhythm of version iterations, resulting in variable cache not being refreshed in a timely manner.

## How to confirm configurations are correctly set
- Check the scheduled task logs of FastGPT v4.17.0 to confirm that the most recent file parsing and indexing task executed successfully.
- Manually trigger an interactive path verification check to confirm whether the operation paths of core pages are correctly identified and marked.
- Modify a global variable, wait for the configured synchronization cycle, and verify that the variable takes effect during knowledge base retrieval.
- Simulate a prototype file path change, confirm that the scheduled task automatically triggers the reindexing process.

The values provided are common starting points. They should be evaluated against samples from the target deployment environment.
