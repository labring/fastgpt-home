# Online Troubleshooting and Retrospective for Prototyping and Interaction Design: Conversation Logs and Auditing

## What Data for This Category Looks Like
Typically, daily documentation for prototyping and interaction design includes interactive prototypes, page flowcharts, component specifications, and review records. Data sources are mostly Figma or Axure files, internal team design systems, user feedback, and usability test records. Update frequency is usually weekly or per version iteration. The core fields of the document structure are page path, component ID, operation steps, and version number. The number and complexity of fields vary greatly across different pages, and there is no unified fixed number of columns.

## Constraints Imposed on Conversation Logs and Auditing
Most data for prototyping and interaction design consists of structured page and component information, updated frequently alongside version releases. Conversation logs must accurately associate specific prototype versions and page nodes; otherwise, the design context corresponding to a fault cannot be located. Additionally, document fields are not fixed and exist in large numbers. The auditing process needs to collect sufficient supplementary information to restore the complete chain of design reviews and changes. If logs only capture basic conversation content, the root cause of R&D understanding deviations cannot be traced. The high-frequency update feature also requires accurate time stamp and version binding logic for logs, to prevent confusion between design data from different versions.

## Configuration Guidelines
This configuration guide is compatible with FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique identifier of the prototype project | Associate all conversation logs under the same prototype project, enabling quick fault tracing by project |
| `responseChatItemId` | Associate with prototype page node ID | Accurately match specific pages or components mentioned in conversations, aligning with the structural logic of prototype documents |
| `detail` | Include prototype version number and page path fields | Supplement the design change context required for auditing, facilitating association of review records and design documents during retrospectives |
| Log retention period | 30 days | Aligns with the weekly or per-version update rhythm of prototype versions, balancing storage costs and audit tracing needs |
| Maximum character count per log entry | 800–1200 characters | Adapts to the single-page description length of prototype documents, avoiding truncation of critical design information |
| Maximum number of logs retrieved per request | Top 10 entries | Adapts to the number of operation steps on a single page of prototype documents, avoiding overload of retrieval results |

## Three Common Misconfigurations
- Symptom: When uploading a prototype document knowledge base with multiple columns of fields, only two columns of data are recognized. Cause: Chunking rules are not configured per the field structure of the prototype document, and only the title and content columns are loaded by default, making other design fields unretrievable.
- Symptom: A `400 do request failed` error is returned, and the prototype version information in the `detail` field is missing from logs. Cause: Additional collection of the `detail` field is not enabled in the log configuration, preventing localization of the specific design version corresponding to the fault.
- Symptom: The output content of the specified reply component is not displayed in workflow history. Cause: `responseChatItemId` is not bound to the component's interaction node ID, causing logs to fail to match the operation path in the prototype.

## How to Verify Correct Configuration
- Initiate a test conversation that includes specific page paths and component names, then check if logs carry the association information between `chatId` and the prototype project ID.
- View the details of a single log entry, confirm that the `detail` field includes design-related fields such as prototype version number and page path.
- Upload a prototype document with multiple columns of fields, verify that all columns of content can be correctly recognized and retrieved.
- Trigger a test process that includes component interactions, then check if the interaction output of the corresponding component is displayed in the workflow history.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
