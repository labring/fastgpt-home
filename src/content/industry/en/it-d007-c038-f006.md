# Online Troubleshooting and Retrospective for Change Management and Release Windows: Scheduled Tasks and Automation

This page is compatible with FastGPT v4.17.0

## What the data for this category looks like

Data for this category originates from change management systems, CI pipelines, monitoring data, and business calendars. Four core document types are produced regularly: change requests, risk assessments, release window plans, and rollback plans.
Change requests include change window time and impact scope fields. Risk assessments include risk rating fields. Release window plans bind business time identifiers. Rollback plans clarify trigger conditions and execution steps.
Data updates occur once weekly, or upon completion of a single change. The core associated field is the change unique ID, which connects data across all systems.

## Constraints imposed on scheduled tasks and automation

Multi-source data access requires scheduled tasks to adapt to API call formats of different systems, to avoid data parsing errors.
Weekly or per-change update frequency means scheduled tasks should not use overly short trigger intervals, and must align with the rhythm of the change process.
Differentiated structures across multiple document types require automated tasks to configure field extraction rules for each file type, to accurately obtain core information such as change windows and risk ratings.
Core production environment risk control goals require scheduled tasks to strictly verify execution time periods, prohibit triggering change-related operations during business peak hours, and set clear alert and rollback mechanisms for abnormal execution results.

## How to set configurations

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| Change Window Verification Period | Use non-peak hours marked in the business calendar, or the effective window filled in the change request | Avoid triggering change tasks during business peaks, reduce production environment failure risks |
| Scheduled Task Trigger Interval | Set according to the change cycle, for example `7 days` or `triggered after a single change` | Match data update frequency, reduce redundant task executions |
| Long Task Execution Timeout Threshold | `1800 seconds` | Cover execution needs of ultra-long tasks exceeding 1200 seconds, prevent forced task termination |
| Duplicate Execution Deduplication Switch | Enable, deduplicate based on change ID | Avoid repeated triggering of the same change task, resolve scheduled task duplicate execution issues |
| Failure Retry Configuration | Retry `3 times`, retry interval `60 seconds` | Address temporary system call failures, reduce manual intervention costs |
| Low-Risk Change Automatic Approval | Enable, automatically pass only when the risk rating is low | Reduce approval coordination time, comply with risk control requirements for change management |

## Three common mistakes

- Phenomenon: Scheduled tasks execute repeatedly. The interface displays multiple execution records with the same change ID. Cause: Deduplication verification based on change ID is not configured. The task does not associate the unique change identifier when triggering on a fixed cycle.
- Phenomenon: Ultra-long task execution times out. An error shows that task execution exceeded the threshold. Cause: The timeout threshold is set lower than the actual task execution duration, and does not cover data analysis needs exceeding 1200 seconds.
- Phenomenon: Automated rollback plan does not trigger. Monitoring data shows anomalies but no corresponding execution logs. Cause: Monitoring abnormal indicators are not bound to change rollback conditions. Automated rules do not match the trigger scenario.

## How to verify correct configuration

- Review scheduled task execution logs. Confirm only one execution record exists for each change ID. This validates that deduplication configuration is active.
- Simulate ultra-long task execution. Observe whether the task runs continuously until completion. This validates that the timeout threshold setting is reasonable.
- Submit a low-risk change request. Confirm the automated approval process completes automatically, with no manual intervention required.
- Configure monitoring alert trigger rules. Verify automated rollback tasks start normally when matching change rollback conditions.
