# Online Troubleshooting and Retrospective for Pre-sales Technical Proposals: Deployment and Upgrade

## What data belongs to this category
Data for this category primarily comes from customer interviews, bidding documents, vendor product materials, and historical project plans. The update frequency is per order or weekly. Daily produced documents include technical proposal books, customer requirement survey forms, quotation lists, and demo scripts. Document structures typically center on core modules such as requirement matching, technical roadmap, implementation boundaries, and cost accounting. Fields mostly cover proposal boundary descriptions, implementation cycle planning, individual service quotes, demo scenario configuration, and have no unified fixed units. Adjustments must be made based on actual project needs.

## What constraints do these characteristics impose on the deployment and upgrade phase
Since the update frequency of data for this category is per order or weekly, the deployment phase must support rapid adaptation to individual project configurations, and avoid rebuilding basic environments repeatedly. Daily document structures are scattered, and fields have no unified standards. The deployment phase must provide configuration templates that can be imported by project, to reduce manual entry errors. Additionally, the core of pre-sales proposals is to clarify technical roadmap and implementation boundaries. The deployment phase must preset flexible adjustable boundary parameters, to ensure that proposal content matches deployment configurations, and prevent subsequent implementation from exceeding the scope promised in the proposal, which could affect project bidding or launch.

## How to set configurations
All configurations below are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `10–20 connections` | Adapts to the demand for parallel indexing of multiple proposal documents in pre-sales scenarios, and prevents database connection exhaustion caused by a large number of proposal documents in a single project |
| `MONGODB_URI` | Project-specific storage path configuration | Used to store demo scripts and requirement survey data for individual customers, ensuring data isolation between different projects |
| `REDIS_URL` | Local cache instance or dedicated cloud cache | Used to cache temporary configurations and demo scenario data for pre-sales proposals, reducing repeated loading time |
| `FE_DOMAIN` | `Project-specific secondary domain` | Ensures that customers accessing the demo environment are isolated from other projects, avoiding configuration confusion |
| `STORAGE_S3_ENDPOINT` | `Storage node adapted to project requirements, single node capacity no less than 1000 MB` | Used to store attachments and demo materials in pre-sales proposals, ensuring data can be migrated along with the project |
| `FILE_TOKEN_KEY` | `Randomly generated 32-character string` | Used to encrypt access links for attachments in proposal documents, ensuring data security |

## Three common mistakes
- The symptom is a 502 status code returned when accessing the page after Docker deployment. The cause is incorrect configuration of `MONGODB_URI` or `REDIS_URL`, preventing the service from connecting to required storage and cache services.
- The symptom is failure to automatically index images in proposal documents after local deployment. The cause is missing configuration of `STORAGE_S3_ENDPOINT` or insufficient storage path permissions, making image resources unreadable.
- The symptom is a version update prompt popping up every time a new conversation is opened. The cause is failure to disable the version reminder switch for non-administrator sessions, or incorrect permission configuration for `ROOT_KEY`, resulting in forced push of update prompts.

## How to confirm configurations are correct
- Run the built-in database connection test tool to verify that the `DB_MAX_LINK` configured connection count can support loading at least 5 pre-sales proposal documents simultaneously.
- Upload a demo script containing images, check whether images load and index normally, to confirm the `STORAGE_S3_ENDPOINT` configuration takes effect.
- Access the project-specific secondary domain, confirm no global version update prompt appears, to verify `FE_DOMAIN` and permission configurations are correct.
- Restart the service, check service logs for no error messages related to database or cache service connections.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
