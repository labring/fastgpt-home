# Online Troubleshooting and Retrospective for Backup Recovery and Disaster Recovery Drills: Deployment and Upgrade

## What Data Looks Like for This Category
Data for this category comes from backup systems, database logs, object storage, and disaster recovery platforms. Update frequencies are categorized as daily, monthly, or quarterly. Documents produced daily include backup policies, recovery drill reports, disaster recovery switchover plans, and data verification records. Document fields include recovery execution duration, verification pass rate, disaster recovery switchover time, and others. Units include seconds, percentage, count, and more. These documents are maintained by operation and maintenance teams, database administrators, and business continuity leads according to their respective responsibilities.

## What Constraints These Characteristics Impose on Deployment and Upgrade
Data sources for this category are scattered, covering backup systems, database logs, object storage, and disaster recovery platforms. During deployment, reserve independent configuration docking entrances for each type of data source to avoid cross-system call conflicts. Retain preset field mapping rules during upgrades to ensure documents such as backup policies and recovery drill reports can be parsed and stored normally, per the fixed structure of daily documents. Configure flexible scheduled synchronization tasks during deployment to adapt to the maintenance rhythms of different businesses, based on differences in update frequencies (daily, monthly, quarterly). Update permission configuration items synchronously during upgrades to ensure compliance of data access, per the permission division among different maintenance subjects. At the same time, configure fault tolerance mechanisms during deployment to prevent drill interruptions caused by single-point failures, as the consequences of errors in disaster recovery drills include data loss, recovery timeout, and business continuity failure.

## How to Configure Settings
These configurations apply to FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `100–200 concurrent connections` | Adapts to concurrent backup data pull and verification requests, avoids database connection exhaustion |
| `MONGODB_URI` | Cluster connection string with read-write separation flag | Disaster recovery drills require simultaneous reading of backup data and writing of verification records. Cluster connections ensure high availability |
| `REDIS_URL` | `600-second timeout cache connection configuration` | Caches temporary data for recovery point targets. The timeout setting matches the average execution cycle of daily drills |
| `STORAGE_S3_ENDPOINT` | Regional access endpoint corresponding to the object storage | Backup data and drill logs must be stored in the specified object storage to ensure data persistence and accessibility |
| `ROOT_KEY` | Random key string generated according to the deployment environment | Secures access permissions for disaster recovery configuration management interfaces, prevents unauthorized configuration modifications |

## Three Common Misconfigurations
- Phenomenon: Backup data pull fails after deployment, returning `503 Service Unavailable` status code. Cause: The `DB_MAX_LINK` configuration value is too low, and cannot support concurrent pull requests for batch backup data.
- Phenomenon: Disaster recovery drill reports cannot be written to storage normally, with specified fields empty. Cause: `STORAGE_S3_ENDPOINT` is not configured correctly, leading to failed object storage access and inability to write verification records.
- Phenomenon: Key verification fails when calling models after local deployment, and the corresponding model cannot be loaded. Cause: The `REDIS_URL` cache key is not configured correctly according to the deployment environment, leading to failure of temporary storage of API keys and timeout failure in the verification link.

## How to Confirm Configuration Is Successful
- Execute the database connection pool status query script, check whether the active connection count falls within the interval configured by `DB_MAX_LINK`, and confirm that the connection configuration takes effect.
- Submit a simulated recovery drill record, check whether it can be written to the specified object storage path normally, and verify the effectiveness of the `STORAGE_S3_ENDPOINT` configuration.
- Access the disaster recovery configuration management interface, use `ROOT_KEY` for permission verification, confirm that the interface can respond normally and there is no unauthorized access risk.
- Start a small-scale recovery drill, check whether the cached recovery point data is updated normally within the timeout period configured by `REDIS_URL`, and confirm that the cache configuration takes effect.
