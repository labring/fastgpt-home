# Online Troubleshooting and Retrospective for Security Training and Phishing Drills: HTTP Interfaces and External Systems

## What the data for this category looks like
The daily documents for this category include training slides, drill plans, phishing email templates, and drill result reports. Data sources cover employee contact lists, email gateways, training platforms, and click statistics. Update frequency is usually quarterly or annually. Core time-consuming steps focus on drill audience filtering, email template design, and result retrospection. Errors may lead to employee data leakage risks, audit gaps, or lack of valid evidence for rectification. Unlike the security baseline inspection category, this category focuses on training and drills for personnel security awareness and behavior.

## What constraints these characteristics impose on the HTTP Interfaces and External Systems link
Because data sources are scattered, multiple external systems must be connected, including employee contact lists, email gateways, and training platforms. Interfaces need to adapt to multi-source data pulling and verification logic. Daily documents are mostly static templates and reports. Interfaces must support batch pulling of templates and structured storage of result data. The high time-consuming nature of drill audience filtering and result retrospection requires interfaces to support paginated queries and batch result export. Low-frequency quarterly/annual updates mean interfaces do not need high-frequency refreshing, but must support parameter configurations for batch data processing.

## How to Configure Settings
| Configuration Item | Recommended Value | Rationale |
| ---|---|--- |
| `Authorization` | `Bearer {API key issued by the platform}` | Standard authentication method when connecting to external email gateways and training platforms, ensures legitimacy of interface calls |
| `variables` | `{"template_type": "phishing", "update_cycle": "quarterly"}` | Matches the quarterly updated drill templates and phishing email type parameters for this category, adapts to batch template calling logic |
| `responseData` | Only return the three core fields: click statistics, personnel grouping, and drill results | Filters non-essential data, reduces interface transmission load, and adapts to rapid data extraction during the retrospective stage |
| Batch call limit | First 200 entries | Adapts to batch pulling requirements for employee contact lists, avoids system performance impact from excessive data in a single call |
| Result data storage period | 365 days | Matches quarterly/annual audit retention requirements, meets basic compliance check conditions |
| Template pull length | 800–1200 characters | Adapts to the standard design length of phishing email templates, avoids content truncation that affects drill effectiveness |

## Three Common Configuration Mistakes
- Calling the template pull interface returns `400 Bad Request`, with an error message containing a parameter mismatch prompt. Cause: The `variables` parameter is not configured correctly, causing the passed template type to not match the external gateway's verification rules.
- Executing batch audience filtering returns a 504 Gateway Timeout status code. Cause: The batch call limit is set above 200 entries, and the volume of employee contact list data pulled in a single call exceeds the system response threshold.
- Exporting drill result reports shows empty click statistics fields. Cause: The return fields for `responseData` are not specified in the interface configuration. The default full data does not include core statistical fields.

## How to Confirm Configuration is Complete
- Call the `Authorization` authentication interface in the interface debugging tool of FastGPT v4.17.0. Return a 200 status code with no authentication failure prompt, confirming the authentication configuration is effective.
- Pass the preset `variables` parameter to call the template pull interface. The returned template type matches the preset value, confirming the parameter configuration is correct.
- Check the `responseData` field returned by the interface. It only includes the three core fields: click statistics, personnel grouping, and drill results, confirming the data filtering configuration is effective.
- Execute a test batch pull of employee contact lists. The returned data volume does not exceed 200 entries, confirming the batch call limit configuration is reasonable.
