# Online Troubleshooting and Retrospective for Security Training and Phishing Drills: Database and Operations

## What data for this category looks like
Typically, the primary stakeholders for this category are security operations teams, internal corporate training departments, or external security service providers. Daily produced documents fall into four categories: training courseware, phishing drill plans, phishing email templates, and drill result reports. Data sources typically include employee contact lists, corporate email gateways, internal training platforms, and user click statistics systems. Data update frequency is mostly quarterly or annual. The most time-consuming steps focus on drill audience filtering, email template design, and drill result retrospective. If configuration or process errors occur, risks such as employee data leaks, missing compliance audit items, and lack of valid evidence for rectification may arise. Unlike the security baseline inspection category, this category focuses on training and verification of personnel security awareness and behavior.

## What constraints do these characteristics impose on the database and operations link
Because data sources are scattered and include structured employee information, semi-structured email templates, and unstructured drill reports, unified mapping and storage of multi-source data must be implemented at the database layer. The low update frequency means high-frequency real-time writing is not required, but there are clear requirements for batch import and historical data retention. The high-frequency query demand for drill audience filtering requires the database layer to have efficient indexing and caching capabilities. At the same time, drill result reports must retain complete historical versions to prevent data tampering or loss, and ensure audit compliance. Differences in storage formats for different types of documents also require the database operations link to configure adapted storage strategies for different data types.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://localhost:27017/fastgpt_security_training` | Stores unstructured documents such as phishing email templates and drill result reports, adapting to the storage needs of multiple document types for this category |
| `PG_URL` | `postgresql://db_user:secure_pass@db-host:5432/security_training` | Stores structured relational data such as employee contact lists and click statistics, supporting complex audience filtering queries |
| `DB_MAX_LINK` | `20–30` | Addresses concurrent connection demands from quarterly batch imports, preventing service blocking caused by exhausted database connection pools |
| `REDIS_URL` | `redis://localhost:6379/1` | Caches temporary results from drill audience filtering, accelerating response speeds for high-frequency queries |

## Three common mistakes
- Symptom: No frontend response after calling the database connection interface, and Docker container resource usage does not reach the threshold. Cause: The `DB_MAX_LINK` configuration was not adjusted for the category's batch audience filtering scenario, leading to exhausted connection pools and blocked requests.
- Symptom: Format exceptions occur when reading content after importing phishing email templates. Cause: The category-specific unstructured data storage configuration was not used, resulting in a mismatch between the storage format of template documents and reading requirements.
- Symptom: Click statistics fields in drill result reports are empty. Cause: Association fields between employee contact lists and email gateways were not correctly mapped, leading to field mismatches during multi-source data synchronization.

## How to confirm configurations are properly set
- In FastGPT v4.17.0, run a test task for batch import of 1000 employee contact lists, check database connection pool monitoring metrics, and confirm that the actual connection count does not exceed the `DB_MAX_LINK` configuration value.
- Run a full drill audience filtering query, compare the cached results with the original data, and confirm that the `REDIS_URL` configuration takes effect and query latency meets expectations.
- Import a standard phishing email template, verify that the content read after storage matches the original template exactly, and confirm that the `MONGODB_URI` storage configuration is correct.
- Generate a simulated drill result report, verify that structured statistical data and unstructured report attachments can be associated and queried normally.

The values provided are common starting points and should be measured against the reader's own samples.
