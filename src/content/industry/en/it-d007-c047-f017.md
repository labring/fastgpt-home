# Online Troubleshooting and Post-Mortem for Security Vulnerability Disclosure Handling: Deployment and Upgrade

## What the data for this category looks like
This category’s data comes from private vulnerability reports, code repositories, CVE numbering bodies, and official release channels. Updates are triggered once per single vulnerability event. Core documents include security advisories, vulnerability reports, fix patches, and CVE application materials. Fields cover vulnerability IDs, impact scope, fixed versions, disclosure times, affected components, and more. There is no fixed batch update cycle. Updates only proceed alongside vulnerability discovery and remediation workflows.

## What constraints these characteristics impose on the Deployment and Upgrade workflow
Data for this category is generated per single vulnerability event, and contains mixed content from private vulnerability reports and public security documents. The deployment phase must isolate sensitive vulnerability information from publicly accessible resources to prevent unauthorized access. Since updates are only triggered by vulnerability remediation workflows, the upgrade process must ensure vulnerability response workflows are not interrupted. It must also be compatible with patch document parsing logic across different versions. Additionally, data sources involve multiple external institution interfaces. Deployment requires configuring stable external access permissions to avoid vulnerability information synchronization failures caused by interface instability.

## How to set the configurations
These configuration items apply to FastGPT v4.17.0. Follow official environment variable specifications strictly:

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://user:pass@host:27017/fastgpt?replicaSet=rs0` | This category stores structured data such as vulnerability reports and patch metadata. Replica set configuration ensures data persistence and high availability |
| `REDIS_URL` | `redis://:password@host:6379/0` | Used for caching vulnerability advisories and temporary session data. Single-database configuration meets lightweight caching requirements |
| `DB_MAX_LINK` | `200` | Data access for this category fluctuates with vulnerability events. 200 connections balances resource usage and concurrent response capacity |
| `STORAGE_S3_ENDPOINT` | Fill in the root address provided by the object storage service provider | Used for storing unstructured data such as patch files and vulnerability report attachments. Must match the access endpoint of the storage service |
| `ROOT_KEY` | `32-character random string` | Used to generate authentication tokens for sensitive operations, ensuring access security for the vulnerability remediation backend |
| AI Proxy Service Root Address | `http://aiproxy:3000` | Required by official specifications as the root address of the AI Proxy service. Do not add path suffixes to ensure normal service invocation |
| AI Proxy Admin Token | `32-character random string` | Must match the configuration on the AI Proxy server. Cannot be empty. Used for server-side authentication |

## Three common misconfigurations
- The symptom is a MongoDB startup verification failure, with an error indicating the replica set is not configured. The root cause is failing to add the replica set parameter to `MONGODB_URI` as required, which causes data storage verification to fail.
- The symptom is empty data processing after knowledge base training. The root cause is incorrect configuration of the `DB_MAX_LINK` connection count, which exhausts database connections and prevents writing training data.
- The symptom is abnormal vector index results after containerized deployment, with all scores identical. The root cause is incorrect configuration of the `REDIS_URL` connection parameters, which causes intermediate cache for vector retrieval to be incorrectly overwritten.

## How to confirm the configuration is correct
- Start the FastGPT server, check that the startup logs have no error prompts about missing required environment variables.
- Upload a test patch file to verify that the storage service can complete file writing and reading normally.
- Submit a simulated vulnerability report to confirm that data can be written to the database normally and can be queried.
- Check the service connection status to confirm that there are no timeout or rejection errors for Redis and MongoDB connections.

The values provided here are common starting points, and should be evaluated against local deployment samples.
