# Online Troubleshooting and Retrospective for Security Monitoring and SOC Duty: Scheduled Tasks and Automation

## What the data for this category looks like
Data sources for this category include SIEM, EDR, NDR, and external threat intelligence feeds. Update cycles cover real-time and daily updates. Daily associated documents include alarm disposal records, on-duty logs, threat intelligence bulletins, daily work reports, and weekly work reports. Data fields include alarm severity, attack type, disposal status, response duration, and no unified fixed units; they adjust according to the data source format. Service subjects include SOC analysts, security operation outsourcing teams, and enterprise security centers. Continuous follow-up of alarm judgment and escalation processes is required.

## Constraints Imposed on Scheduled Tasks and Automation by These Characteristics
Dispersed data sources and widely varying update cycles require scheduled tasks to support multi-cycle trigger configurations, adapting to minute-level pulling of real-time alarms and daily synchronization of threat intelligence. Associated processing of multiple document types requires scheduled tasks to bind the knowledge base ID corresponding to the data source, avoiding cross-source data confusion. Alarm judgment and false positive elimination account for the majority of daily workload. Automated processes must prioritize high-priority alarms after scheduled triggering to prevent response timeouts. A failure retry mechanism must also be configured for real-time data streams to avoid missing real attacks due to single task interruptions.

## How to Set Up Configurations
This document applies to FastGPT v4.17.0
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Task Trigger Cycle | Real-time alarms use `1–5 minutes`, threat intelligence synchronization uses `24 hours` | Adapt to data source update cycles; real-time alarms require rapid response, daily threat intelligence does not need frequent pulling |
| Knowledge Base Binding Rule | Bind the corresponding knowledge base ID by data source type | Avoid confusion of alarm data from different sources, ensuring judgment accuracy |
| Single Processing Alarm Limit | Top 20 high-priority alarms | Prevent single task overload leading to timeouts, prioritize high-risk events |
| Failure Retry Count | 3 times, interval `60 seconds` | Address temporary network fluctuations or brief data source unavailability, reduce missed alarm risk |
| Task Timeout Threshold | `300 seconds` | Match SOC duty response time requirements, avoid long task resource occupation |
| Alarm Filtering Rule | Exclude low-value alarms identified through testing | Reduce ineffective processing, focus on real threat events |

## Three Common Misconfiguration Scenarios
- Symptom: Calling the knowledge base interface in the workflow returns a null value or cannot find the corresponding resource. Cause: The correct knowledge base ID was not bound according to the data source type, causing the task's pulled knowledge base to not match the data source.
- Symptom: The scheduled task is forcibly terminated after exceeding 180 seconds of execution. Cause: The task timeout threshold was not adjusted. The default timeout limit cannot cover complex alarm judgment and batch processing workflows.
- Symptom: Low-value alarm accumulation prevents subsequent tasks from running normally. Cause: No alarm filtering rules were configured, and invalid alarms were not excluded in advance, leading to task processing volume exceeding the single limit.

## How to Confirm Successful Configuration
- Manually trigger a scheduled task. Check whether the task log correctly pulls alarm data from the corresponding data source, and verify that the knowledge base ID matches the configured value.
- Check the task execution duration to confirm it does not exceed the preset timeout threshold. Adjust the threshold to adapt to actual processing complexity.
- Review the alarm filtering results to confirm that preset low-value alarm types have been excluded, and remaining alarms meet priority requirements.
- Simulate a scenario where the data source is temporarily unavailable. Check whether the task triggers the failure retry mechanism, and confirm the retry count matches the configured requirements.
