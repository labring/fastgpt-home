# Online Troubleshooting and Retrospective for Security Monitoring and SOC On-Duty Operations: Conversation Logs and Auditing

## What this category of data looks like
Data for this category comes from SIEM, EDR, NDR, and threat intelligence feeds. Update frequency is real-time or daily. Daily associated documents include alert handling tickets, on-duty logs, threat intelligence briefings, and daily and weekly reports. Data fields include alert identifiers, handling entities, timestamps, threat correlation information, and more. Conversation logs must be bound to unique identifiers of corresponding alerts or handling processes for subsequent troubleshooting and auditing.

## What constraints do these characteristics impose on the conversation logs and auditing workflow
Multiple data sources require conversation logs to be linked to alert identifiers from different systems, enabling cross-system tracing. Real-time update characteristics require log collection to support real-time synchronization, preventing data loss. The diversity of daily documents requires audit logs to match the field structure of documents such as alert handling tickets, facilitating cross-document correlation. The most time-consuming alert triage and investigation phase requires logs to support fast retrieval and positioning, improving retrospective efficiency. The severity of potential error consequences requires logs to have an immutable retention mechanism, ensuring the credibility of audit results.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `chatId` | Generate a unique identifier by binding to the alert ID, in the format `alert-{alertId}_chat_{timestamp}` | Link SIEM, EDR alert data to enable one-click tracing between conversations and alerts |
| `responseChatItemId` | Number in the order of handling steps, generate a separate ID for each interaction round | Facilitate locating specific conversation segments for individual alert investigations during retrospectives |
| `detail` | Enable full log collection, including alert context and handling actions | Match the field structure of alert handling tickets to simplify audit archiving |
| Log retention period | 30 days | Match SOC on-duty cycles and standard audit requirements |
| Single log storage limit | 1000 MB | Adapt to storage requirements for multi-source data synchronization, prevent single log overflow |
| Retrieval and retrospective range | Previous 7 days of conversation logs | Match the retrospective timeliness requirements of daily alert investigations |

## Three Common Configuration Mistakes
- Phenomenon: No historical records are displayed on the frontend after refreshing the conversation page, but complete records are visible in the backend log list. Cause: The binding logic between `chatId` and frontend sessions was not configured correctly, resulting in a mismatch between the frontend session identifier and the `chatId` stored in the backend.
- Phenomenon: Exported audit logs lack content in the `detail` field. Cause: Full log collection was not enabled, only basic conversation metadata was synchronized.
- Phenomenon: The number of conversation log search results does not match the actual count. Cause: A reasonable retrieval and retrospective range was not set, exceeding the preset log retention period or retrieval limit.

## How to Confirm Correct Configuration
This verification process applies to FastGPT v4.17.0.
- Manually create a test alert conversation, check if the frontend page displays the `chatId` identifier bound to the alert ID.
- Export audit logs from a specified time period, verify that the `detail` field and alert correlation information are included.
- Simulate a page refresh operation, confirm that the frontend session can correctly load historical conversation records stored in the backend.
- Check log storage usage, confirm that single logs do not exceed the preset storage limit.

The values provided here are common starting points and should be evaluated against the reader’s own samples.
