# Online Troubleshooting and Retrospective for Customer Data Import Migration: Deployment and Upgrade

## What This Category of Data Looks Like
This page is written for FastGPT v4.17.0. Business data sources for customer data import migration typically include customer legacy systems, CSV or Excel templates, database export results, and product import logs. Daily supporting documents include data templates, migration plans, field mapping tables, and migration verification reports, with update frequencies varying per individual project. Typical responsible parties include implementation consultants, data implementation engineers, and customer IT liaisons. Core time-consuming steps focus on field mapping confirmation, dirty data cleaning, and post-import sampling verification. Failures may lead to historical data loss, misplaced fields, or customer rejection. This category differs from customer onboarding and tenant initialization in that it covers full-process verification and migration of existing business data into new systems.

## What Constraints Do These Characteristics Impose on the Deployment and Upgrade Link
Diversity of data sources requires that deployment links support connection configuration for multiple data types, to avoid migration failures caused by format incompatibility. Irregular update frequencies mean that upgrade processes must be compatible with historical data formats, and cannot rely on fixed version iteration rules. The existence of field mapping tables requires that deployments support custom field matching configuration items to adapt to business field differences across different customers. The characteristics of core time-consuming steps drive the deployment link to include built-in verification rules to reduce repetitive manual verification work. At the same time, the severity of failure consequences requires that deployment and upgrade links configure log retention and rollback mechanisms to ensure traceability of the migration process and fault recovery. For scenarios without network access, relevant parameters for local storage must be configured in advance to avoid relying on public network resources for deployment.

## How to Configure
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `10–20 connections` | Adapt to concurrent requests during multi-data-source import, avoid exhausting database connections |
| `PG_URL` | Fill in according to the customer's source PostgreSQL database connection string format | Support direct import of customer historical data exported from PostgreSQL |
| `REDIS_URL` | Local Redis service address or managed Redis connection string | Cache import task status and field mapping rules to avoid repeated calculations |
| `STORAGE_S3_ENDPOINT` | Set based on actual testing | Adapt to local storage or private object storage during offline deployment, address file storage needs in network-free environments |
| `FILE_TOKEN_KEY` | `32-bit random string` | Encrypt access tokens for imported files, prevent unauthorized access to migrated data |

## Three Common Mistakes
- Symptom: Unable to view runtime logs after Docker deployment; the container prompts that the log directory does not exist. Cause: The log storage path inside the container is not mounted to the host machine, resulting in failure to persist logs.
- Symptom: After passing the base64 value of `image_url`, the backend model prompts format incompatibility. Cause: The switch for parsing base64 format images is not enabled in the deployment configuration; the model only supports standard HTTP image URL formats.
- Symptom: Files cannot be read in the conversation scenario after local deployment, but the knowledge base file upload function works normally. Cause: The file storage path for the conversation scenario is not configured during deployment; only file read/write permissions for the knowledge base module are enabled.

## How to Confirm Proper Configuration
- Check if the `DB_MAX_LINK` configuration matches the maximum connection limit of the source database. View connection usage via database monitoring tools.
- Verify that the `REDIS_URL` configuration can connect normally. Confirm connectivity by executing the ping command via a Redis client.
- Upload a test CSV template, trigger an import task, and check if the product import log generates complete migration verification records.
- Confirm that the `STORAGE_S3_ENDPOINT` configuration adapts to the storage needs of the current deployment environment. Attempt to upload a test file and verify read permissions.

The values provided are common starting points and should be measured against the reader's own samples.
