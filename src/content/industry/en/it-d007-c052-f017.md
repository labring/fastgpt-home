# Online Troubleshooting and Retrospective for Customer Permission and Organizational Structure Configuration: Deployment and Upgrade

## What the Data for This Category Looks Like
The data for this category primarily comes from customer HR systems, identity directories, product backends, and operation audit logs. Daily maintained documents include permission matrices, organizational structure tables, role configuration records, and permission change orders. Data is updated per order or irregularly, triggered by customer permission adjustments and organizational structure changes. Data fields include department hierarchy, role identifiers, permission coverage ranges, change timestamps, and similar items. There are no unified fixed unit requirements; field formats are matched only according to configuration scenarios.

## What Constraints Do These Characteristics Impose on Deployment and Upgrade
The data characteristics of this category impose multiple constraints on the deployment and upgrade link. Data sources are scattered, so multiple system interfaces must be connected during deployment. Parameters such as `REDIS_URL` and `PG_URL` must be configured to achieve data synchronization and caching. The update rhythm is irregular, so a full data verification link must be reserved during upgrades to avoid conflicts in role permission mapping between old and new configurations. Daily documents are mostly semi-structured, so field alignment between the permission matrix and system configuration must be completed before deployment to prevent mapping mismatches. Audit logs require a separate storage path configuration to ensure complete traceability of permission change operations after upgrades.

## How to Set Configurations
| Configuration Item | Recommended Value | Rationale for This Value |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | 20–50 connections | Adapts to concurrent query requirements for permission and organizational structure data, avoiding connection exhaustion |
| `MONGODB_URI` | Cluster connection address with authentication parameters | Stores role configuration and permission change records, supports multi-node redundancy to ensure data reliability |
| `PG_URL` | Database address with read-write separation identifier | Stores structured data for organizational structure tables and permission matrices, adapting to complex query scenarios |
| `REDIS_URL` | Cache service address with password | Caches frequently accessed permission mapping data, reducing database query pressure |
| `ROOT_KEY` | Randomly generated 32-bit string | Configures the super administrator permission verification key to prevent unauthorized access to the configuration page |
| `STORAGE_S3_ENDPOINT` | Object storage endpoint matched to the deployment environment | Stores audit log files for permission changes, adapting to cross-node log access requirements |

## Three Common Misconfigurations
- Phenomenon: After upgrading to FastGPT v4.17.0, the original oneapi configuration file fails to take effect. Model interface exceptions are displayed on the permission configuration page. Cause: The new version migrates model configuration to the frontend page. The API address must be added to the docker compose file, with the /v1 path suffix appended.
- Phenomenon: When deploying with a PG database, the organizational structure synchronization task times out and does not respond. Cause: The `DB_MAX_LINK` parameter is not configured or the value is too low, causing the database connection pool to be exhausted and unable to process synchronization requests.
- Phenomenon: Unauthorized access occurs after permission changes, and no corresponding audit record exists in the system. Cause: The `STORAGE_S3_ENDPOINT` parameter is not configured, causing audit logs to fail to be stored, or the `ROOT_KEY` configuration is incorrect, causing the permission verification logic to fail.

## How to Confirm That Configurations Are Correct
- Execute the docker compose ps command to check whether the services corresponding to configurations such as `REDIS_URL` and `PG_URL` are running normally.
- Log in to the system backend, import the local permission matrix document, and check whether the system automatically completes field matching and permission mapping configuration.
- Initiate a department role adjustment operation, and check whether the corresponding audit log file is generated in the specified storage path.
- Call the permission verification interface using the preset `ROOT_KEY` key to verify whether the super administrator permission takes effect normally.

The values provided are common starting points and should be evaluated against local deployment samples.
