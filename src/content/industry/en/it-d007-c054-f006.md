# Online Troubleshooting and Retrospective for Container Platform Operations: Scheduled Tasks and Automation

## What this type of data looks like
Daily data for container platform operations comes from Kubernetes APIs, image registries, monitoring systems, and CI pipelines. Updates are triggered either via daily synchronization or after each cluster change. Common documents include cluster change tickets, namespace quota tables, deployment records, and fault reports. Fields include cluster node IDs, Pod status codes, image versions, resource quota thresholds, and more. Units include units, GB, counts, and others. The number of entries per document changes dynamically based on cluster scale.

## What constraints these characteristics impose on the "scheduled tasks and automation" workflow
Data sources are scattered and rely on external interfaces. Scheduled tasks must adapt to call rate limits of different systems to avoid interface blocking from frequent requests. Update cycles are not real-time, so scheduled tasks do not need overly short trigger intervals. They can run on a per-change or daily cadence to reduce resource consumption. Document formats and fields vary, so automated workflows must support parsing of structured tables and unstructured logs. The most time-consuming resource quota adjustment and Pod exception troubleshooting links require scheduled tasks to prioritize high-priority fault tickets. Errors directly relate to business interruptions, so complete failure retry and alert mechanisms must be configured.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale for This Setting |
| ---- | ---- | ---- |
| Scheduled task trigger interval | Every 300 seconds / 2:00 AM daily | Matches Kubernetes API log update frequency and cluster off-peak hours, avoiding frequent calls that exceed interface rate limits |
| Maximum number of Pods checked per single run | Top 20 entries | Controls resource usage per round of tasks, adapting to the concurrent processing capacity of cluster nodes |
| Fault alert threshold | 3 consecutive Pod restarts | Filters anomalies caused by temporary network jitter or scheduling fluctuations, reducing false alerts |
| Automated repair retry count | 2 times | Avoids repeated execution of operations that may cause resource conflicts, balancing repair success rate and resource consumption |
| Log pull timeout period | 60 seconds | Adapts to log return delays of monitoring systems, preventing long task blocking |
| Global variable update trigger condition | After cluster change is completed | Matches the update cadence of business documents, ensuring variables remain consistent with actual cluster configurations |

## Three common mistakes
- Symptom: API request returns 404 - Resource not found. Cause: The Kubernetes API path called by the scheduled task was not updated with the cluster version, or the configured namespace name was misspelled.
- Symptom: Set global variable values are not automatically updated. Cause: The scheduled task trigger condition is not bound to cluster change events, only runs on a fixed cycle, and does not sync the latest namespace quota table data.
- Symptom: Knowledge base images cannot be automatically indexed. Cause: The scheduled task is not configured with the image metadata pull link for the image registry, or does not specify scan rules for image storage paths.

## How to confirm configurations are correct
- Manually trigger a scheduled task, check the task execution logs in FastGPT v4.17.0, and confirm that Pod status data for the specified namespace can be pulled.
- Modify the configuration of one cluster change ticket, wait for the task to run, and verify that the global variable is synced to the latest value.
- Simulate an abnormal Pod restart, check whether the preset automated troubleshooting process is triggered and the corresponding fault report is generated.
- Manually block one API request, confirm that a preset alert notification is triggered after consecutive failures reach the threshold.

The values listed are common starting points and should be measured against the reader's own samples.
