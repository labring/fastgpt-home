# Online Troubleshooting and Retrospective for Container Platform Operations: Conversation Logs and Auditing

## What this category of data looks like
Data for this category primarily originates from Kubernetes APIs, image registries, monitoring systems, and CI pipelines. Update frequency is daily or after each cluster change. Daily associated documents include cluster change tickets, namespace quota tables, deployment records, and fault reports. Data fields include cluster node ID, Pod status, image version, CI build results, resource quota thresholds, and more. There are no uniform fixed unit requirements, and some fields adjust dynamically based on cluster configuration.

## Constraints on conversation logs and auditing workflows
Multi-source heterogeneous data sources require conversation logs to support association with multi-dimensional identifiers such as Kubernetes nodes, images, and monitoring metrics. This avoids siloed information during troubleshooting. Dynamic update frequency requires the auditing function to support flexible filtering of log ranges by change time and cluster event time. This adaptation supports daily or immediate change scenarios. Associated documents such as cluster change tickets and quota tables require log fields to reserve storage space for corresponding associated IDs. This facilitates subsequent tracing of operation links. The high-risk nature of fault troubleshooting requires audit logs to fully retain conversation context and operation parameters. This ensures troubleshooting processes can be reproduced during retrospective reviews.

## How to configure settings
All configurations below are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `chatId` filtering rule | Configure by grouping cluster namespaces | Adapt to the multi-tenant isolation operation scenario of container platforms, preventing cross-namespace log leakage |
| `responseChatItemId` association switch | Enable and bind Kubernetes resource IDs | Establish association between conversation logs and specific Pods or nodes, simplifying fault troubleshooting workflows |
| `detail` log storage granularity | Retain complete request and response bodies | Cover all operation parameters and return results, meeting full audit retrospective requirements |
| Concurrent thread limit | 10–30 threads | Adapt to resource quotas of container platforms, avoiding triggering system rate limits |
| Log retention period | 30–180 days | Adapt to the conventional audit cycle of container platform operations, adjustable based on actual testing |
| Single log export limit | Top 1000 entries | Prevent export operations from consuming excessive cluster resources and disrupting normal operations |

## Three common configuration mistakes
- Symptom: Different users can only view conversations they initiated after logging in, and cannot view operational conversations from other team members. Cause: The namespace grouping filter configuration for `chatId` is not enabled, resulting in failed permission isolation.
- Symptom: Conversations created via API have an empty Human field in the log preview interface. Cause: User identification information for the `detail` field is not correctly passed in request parameters, resulting in failure to collect user identities for logs.
- Symptom: Vectorization tasks report a rate limit exceeded error and cannot generate knowledge base vectors normally. Cause: Concurrent thread count is not limited, causing embedding requests to exceed cluster resource quotas and triggering system rate limits.

## How to verify correct configuration
- Log in with test accounts of different permissions, verify that only conversation logs under the corresponding namespace are visible.
- Initiate an API call with the complete `detail` parameter, check if the Human field in the log preview interface correctly displays the user identifier.
- Export audit logs, confirm that the format is JSON and contains complete request and response content.
- View the log retention period and single log export limit configuration, verify that export operations comply with resource usage requirements.
