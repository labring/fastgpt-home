# Online Troubleshooting and Retrospective for Container Platform Operations: Deployment and Upgrade

## What Data Looks Like for This Category
Core data for container platform operations comes from Kubernetes API, image registries, CI pipelines, and cluster monitoring systems. Daily maintenance documents include cluster change tickets, namespace quota tables, deployment records, and incident reports. Fields cover cluster node identifiers, Pod running status, image version numbers, change timestamps, and resource usage quotas.
Data updates daily or after each cluster change. Consistent fields across all documents must be maintained to ensure full traceability of changes and operational actions.

## Constraints Imposed by These Characteristics During Deployment and Upgrade
Since data relies on Kubernetes API and cluster monitoring, ensure service accounts have sufficient API access permissions during deployment. This avoids failed resource state collection due to insufficient permissions.
Data updates frequently. Validate image compatibility via CI pipelines before upgrading. Also adjust Pod resource requests and limits against the namespace quota table to prevent business interruptions from resource preemption.
Incident report fields must match troubleshooting logs. Associate a log collection tool during deployment to ensure complete capture and traceability of exception information.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–200 connections` | Matches the concurrent connection limit of container clusters, and aligns with Pod resource quota configurations |
| `MONGODB_URI` | `mongodb://<db-user>:<db-pass>@<mongo-svc>:27017/fastgpt?authSource=admin` | Follows official database connection format requirements, and adapts to service discovery address rules within containers |
| `REDIS_URL` | `redis://:<redis-pass>@<redis-svc>:6379/1` | Points to a containerized Redis service, uses database 1 to isolate business data, and matches cluster network policies |
| `FE_DOMAIN` | `https://your-fastgpt-domain.com` | Corresponds to the Ingress domain exposed externally by the container platform, ensuring correct frontend access paths |
| `FILE_TOKEN_KEY` | 32-bit random string determined via actual testing | Meets security requirements for file upload authentication, preventing unauthorized file access |

## Three Common Misconfigurations
- Symptom: After deploying via docker compose privately, interface errors occur when accessing the knowledge base. Cause: Failed to correctly configure the `AIPROXY_API_ENDPOINT` (root address of the AI Proxy service) and `AIPROXY_API_TOKEN` (AI Proxy admin token) environment variables in the App/Admin server, triggering startup validation failures introduced in FastGPT v4.17.0.
- Symptom: After upgrading to FastGPT v4.17.0, uncaught exceptions appear in simple applications. Cause: Failed to adjust Pod resource requests and limits against the namespace quota table, leading to insufficient container cluster resources.
- Symptom: No frontend output after the question-and-answer flow ends; messages can only be viewed via details. Cause: Confused `AIPROXY_API_ENDPOINT` (root address of the AI Proxy service), `AIPROXY_API_TOKEN` (AI Proxy admin token), and model vendor credentials. Upstream model parameters were not configured via the official model channel configuration page.

## How to Confirm Configuration Is Correct
- Check the App/Admin service’s container logs to confirm no environment variable missing validation errors occur during startup.
- Access the configured frontend domain to verify the knowledge base function loads normally and can initiate query requests.
- Log in to the FastGPT model channel configuration page to confirm upstream model channel addresses and vendor credentials are correctly configured.
- Run cluster resource check commands to confirm all service Pods are in running status, and resource usage aligns with configured requirements.
