# Online Troubleshooting and Retrospective for Capacity Planning and Resource Scaling: Database and Operations

## What the data for this category looks like
This category's data primarily comes from cloud billing, monitoring systems, business forecasts, and stress test reports, with an update cycle of weekly or monthly. Daily produced documents include capacity planning reports, expansion application forms, resource utilization reports, and budget calculation sheets. Common data fields include resource type, usage volume, peak threshold, procurement cycle, and budget quota. Units correspond to standard measurement methods for resources, such as core count, storage capacity, bandwidth rate, etc. All data must be collected and organized using a unified standard.

## What constraints these characteristics impose on the database and operations link
The weekly or monthly update cycle means database operations teams must regularly sync the latest resource usage and forecast data, and cannot rely on real-time incremental data for immediate adjustments. Data from multiple sources needs to be correlated and integrated in the database, requiring unified field mapping rules to avoid analysis deviations caused by inconsistent data standards. Documents for budget calculations and expansion applications rely on historical resource data stored in the database, so data traceability must be ensured, and fields must be reserved for recording approval status and change records. Peak prediction and bottleneck positioning rely on stress test reports and monitoring data, so database queries must support quick filtering by time range and resource type. Otherwise, the processing cycle of the most time-consuming links in this category will be extended.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `PG_URL` | Standard PostgreSQL connection string including `connect_timeout=10 seconds` | Used to connect to external database services; setting a reasonable timeout prevents invalid connections from occupying resources |
| `DB_MAX_LINK` | 100–200 connections | Matches the maximum connection limit of cloud database instances to prevent service failures caused by exhausted connections |
| `REDIS_URL` | Connection address bound to a 256 MB memory cache node | Used to cache resource utilization data from frequent queries, reducing read/write pressure on the primary database |
| `MONGODB_URI` | Connection address configured for replica set mode | Stores historical capacity planning reports and budget data to ensure high availability of data reads and writes |
| Database connection pool timeout | 300–600 seconds | Adapts to the query time of bulk resource data, avoiding interruptions to the data collection process due to timeout |

## Three common mistakes
- Symptom: Database connection errors indicating missing required parameters or abnormal text indexes. Cause: The complete information for `PG_URL` or `MONGODB_URI` was not filled in according to configuration requirements, omitting authentication information or path configurations.
- Symptom: Historical resource data is lost after upgrading FastGPT v4.17.0. Cause: Historical capacity planning data in the database connection pool was not backed up before upgrading or scaling, resulting in data loss after configuration reset.
- Symptom: Resource bottleneck positioning takes longer than expected. Cause: Reasonable indexes were not configured for resource data in the database, resulting in full table scans when filtering by time range or resource type, which extends the processing cycle.

## How to confirm configurations are correct
- Run a database connection test script to verify connectivity for `PG_URL`, `MONGODB_URI`, and `REDIS_URL`, confirming there are no timeout or permission errors.
- Check database connection pool monitoring data to confirm that the current active connection count does not exceed the configured limit of `DB_MAX_LINK`, and adjust the value based on actual business peak loads.
- Export a weekly resource utilization report and verify that the data stored in the database matches the raw data collected by the monitoring system.
- Simulate submitting an expansion application to confirm that the database can normally write the approval status of the application form and associated resource information.

The values provided are common starting points and should be measured against the reader's own samples.
