# Online Troubleshooting and Retrospective for Object Storage and Backup Services: Deployment and Upgrade

## What Data for This Category Looks Like
Daily operation and maintenance documents for this category include bucket configurations, backup policies, recovery records, and lifecycle rules.
Data sources include object storage consoles, backup systems, access logs, and customer policy tables.
Update frequency is daily or triggered by policy changes.
Data fields include bucket unique identifiers, backup task execution status, recovery duration, rule effective times, and similar items. Formats only match corresponding business scenarios, with no unified fixed statistical unit.

## Constraints Imposed on Deployment and Upgrade Workflows
The multi-source nature of daily operation and maintenance documents and data requires that permission docking and field mapping between multiple systems such as object storage consoles and backup systems be completed in advance during deployment.
The characteristic that data update frequency is triggered by policy changes requires that the upgrade process be compatible with policy configurations of different versions to avoid configuration incompatibility issues.
Data errors can lead to data leaks, backup failures, or unavailable recovery functions. This requires rollback plans and pre-permission verification logic to be configured during deployment and upgrade.
The most time-consuming permission policy verification step requires that permission associations between buckets and backup systems be sorted out in advance before deployment to shorten the deployment cycle.

## Configuration Guidelines
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–200 connections` | Matches the concurrent access limit of the object storage console to avoid connection exhaustion |
| `STORAGE_S3_ENDPOINT` | `Corresponding cloud service provider's S3-compatible endpoint` | Docks with the storage backend of the backup system to enable linkage between object storage and backup |
| `REDIS_URL` | `Local Redis service address, port 6379` | Caches access logs and policy configurations to improve operational data reading efficiency |
| `FE_DOMAIN` | `Filing-compliant frontend access domain name` | Matches the cross-domain configuration rules of the storage bucket to ensure normal loading of frontend pages |
| `PG_URL` | `Local PostgreSQL service address, port 5432` | Stores recovery records and lifecycle rule data to ensure persistent storage of operational data |

## Three Common Misconfigurations
- Symptom: Backup task status displays as empty after deployment. Cause: `STORAGE_S3_ENDPOINT` is not configured correctly, preventing connection to the storage backend to retrieve task data.
- Symptom: An unclickable mask appears on the login interface after upgrade. Cause: `FILE_TOKEN_KEY` is not updated, leading to frontend static resource verification failure and abnormal interface loading.
- Symptom: Service CPU single-core usage remains at 100%, while GPU resources stay idle. Cause: The `DB_MAX_LINK` parameter is not adjusted, causing database connection exhaustion, blocking IO processing threads, and preventing GPU resource scheduling.

## How to Confirm Successful Configuration
- Access the frontend address corresponding to the configured `FE_DOMAIN`, and confirm that the bucket configuration page loads normally with no cross-domain errors.
- Initiate a test backup task, wait for the task to complete, and check whether recovery record entries are generated in the corresponding database.
- Call the cache interface of `REDIS_URL` to confirm that policy configurations can be written to and read from the cache normally.
- Check the database connection monitoring panel to confirm that the current connection count is within a stable range, with no connection overflow.
