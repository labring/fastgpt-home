# Online Troubleshooting and Retrospective for Performance Testing and Capacity Assessment: Conversation Logs and Auditing

## What the data for this category looks like
Data for this category typically comes from stress testing platforms, APM monitoring tools, database slow logs, and production traffic baselines. Updates occur monthly or when major versions are released. Regularly produced documents include stress testing plans, capacity assessment reports, stress testing data records, and optimization suggestion sheets. Data fields include throughput (requests/second), latency (milliseconds), resource usage (%), peak concurrent connections, and more. Data from different sources uses varying units and formats. All data must be unified before being used for retrospectives.

## Constraints on conversation logs and auditing
Mixed use of multi-source data requires logs to be linked to unique identifiers. This allows quick location of corresponding stress testing sessions during troubleshooting.
The monthly or version-based update rhythm requires audit logs to be retained long enough to cover review and retrospective needs.
The strong link between documents and data requires logs to correspond to specific stress testing plan or assessment report nodes. This avoids confusion during traceability.
The diversity of field units requires the audit workflow to retain original unit information. This ensures indicator consistency during retrospectives.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Session ID Binding | Bind `chatId` and `responseChatItemId` | Match stress testing sessions to corresponding log entries, associate multi-source stress testing data |
| Log Detail Toggle | Enable `detail` field collection | Retain original units and values of stress testing indicators, enabling precise retrospectives |
| Audit Retention Period | 30–90 days | Align with monthly or major version update rhythms, meet review and retrospective requirements |
| Single Log Collection Limit | First 1000 records | Prevent log overflow from disrupting normal operation of stress testing platforms |
| Multi-source Data Association | Bind logs to stress testing plan ID | Match the structure of stress testing plan documents, enabling fast traceability |
| Field Validation Toggle | Enable unit validation | Meet category-specific requirements for units of throughput, latency, and other indicators |

## Three common configuration errors
- Tool call modules continuously output redundant runtime logs: No filtering rules configured for the `detail` field lead to collection of non-core intermediate runtime logs. This occupies audit storage space and interferes with retrospectives.
- MCP tool calls fail to establish connections with termination nodes: No binding of `responseChatItemId` to node call links means logs for broken links cannot be associated with corresponding sessions. This makes it impossible to locate connection failure causes.
- Stress testing data log fields have missing or inconsistent units: No unit validation configuration enabled, and no matching of category-specific unit requirements for throughput, latency, and other indicators. This results in invalid indicator comparisons during retrospectives.

## How to confirm configuration is complete
- Initiate a small-scale stress testing session, and check for the presence of `chatId` and `responseChatItemId` fields in the FastGPT v4.17.0 log panel.
- Check the `detail` field of a single log entry to confirm original unit information for stress testing indicators is retained.
- View the retention duration of audit logs to verify alignment with the configured 30–90 day period.
- Trigger a tool call, and confirm logs are associated with the corresponding stress testing plan ID, with complete and traceable links.

The values provided are common starting points and should be measured against the reader's own samples.
