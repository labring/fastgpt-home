# Online Troubleshooting and Retrospective Analysis for Delivery Effect Optimization: HTTP Interfaces and External Systems

## What the data for this category looks like
Daily data for delivery effect optimization primarily comes from advertising platforms, attribution systems, CRM lead data, and landing page data. Update frequencies are mostly daily or real-time.
Documents produced daily include daily reports, weekly reports, price adjustment records, material test sheets, and optimization retrospective documents.
Common data fields include impressions, clicks, cost per conversion, lead ID, and others. Units include yuan per action, count, cost per thousand impressions, and others.
Data structures returned by different external systems vary. Unified mapping is required to complete data integration.

## What constraints these characteristics impose on HTTP Interfaces and External Systems
Since data update frequencies include real-time and daily. HTTP interfaces must support both single real-time pull and batch synchronous pull capabilities.
Differences in data structures from multiple sources require interfaces to have unified field parsing capabilities. This avoids indicator anomalies caused by different external system formats.
The structured nature of daily documents requires interface return content to adapt to table data import and analysis.
Additionally, the high time cost of locating abnormal indicators requires interfaces to return clear error fields and detailed logs. This facilitates quick troubleshooting.
Furthermore, errors in delivery effect optimization directly impact customer acquisition costs and budget usage. Interfaces must have retry and alert mechanisms to reduce the impact of single call failures.

## How to Configure
FastGPT v4.17.0 configuration reference is as follows:

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` configuration | Use Bearer Token format, token validity period 3600 seconds | Complies with standard authentication specifications for external interfaces such as advertising platforms and attribution systems. Avoids frequent token acquisition that disrupts real-time data synchronization |
| Request timeout | 60-120 seconds | Covers typical response durations of most advertising-related external interfaces. Prevents single request timeouts from interrupting batch data pull tasks |
| `responseData` parsing rules | Extract core indicators such as impressions, clicks, conversions, and others from this field | Unifies return structures of different external systems. Simplifies the process of locating abnormal indicators |
| `variables` configuration | Pass parameters such as advertising account ID, statistical date range | Supports batch data pull across multiple accounts and periods. Adapts to daily retrospective needs for delivery effect optimization |
| Error log storage | Retain the last 7 days of interface call logs | Facilitates backtracking of request details and return results during online troubleshooting |
| Retry mechanism | Retry 2 times after failure, 10 second interval | Addresses temporary rate limiting or network jitter from advertising platform interfaces. Reduces the impact of single call failures |

## Three Common Misconfigurations
- Scenario: Interface returns 401 authentication failure error. Cause: `Authorization` parameter is not configured correctly, token format does not meet external system requirements, or token has expired.
- Scenario: Tool calls return incorrect delivery indicators. Cause: Unified mapping is not applied to `variables` parameters across multiple external systems, leading to passed account ID or date range that does not match actual requirements.
- Scenario: Pulled data fields are empty or do not match expected values. Cause: Return content is not parsed according to `responseData` rules, non-core fields are mistakenly used as the indicator extraction source.

## How to Confirm Configuration Is Complete
- Call the test interface, confirm that the `Authorization` parameter is correctly included in the request header, and verify that authentication passes.
- Initiate a batch data pull request, confirm that core indicators such as impressions and conversions can be correctly extracted from the `responseData` field.
- Pass test `variables` parameters, verify that the interface returns data for the corresponding advertising account and date range.
- Simulate an interface call failure scenario, confirm that the preset retry mechanism and error alert are triggered.
