# Online Troubleshooting and Retrospective for Campaign Performance Optimization: Scheduled Tasks and Automation

## What the Data for This Category Looks Like
Core data for campaign performance optimization comes from ad platform APIs, attribution systems, CRM leads, and landing page tracking data. Daily deliverables include daily reports, weekly reports, price adjustment records, material test sheets, and optimization retrospective documents. Fields include impressions, clicks, conversion cost, budget balance, and similar metrics. Units include yuan, counts, and others. Data update cycles fall into two categories: real-time and daily. Real-time data updates synchronously with ad delivery actions. Daily data is aggregated at a fixed time each day. This step takes place after ad delivery has launched, separate from the pre-configured phase of campaign planning.

## Constraints Imposed by These Characteristics on Scheduled Tasks and Automation
Dispersed data sources and inconsistent formatting require scheduled tasks to support multi-source data pulling logic and field mapping rules. Differences in update cycles require task trigger timing to match the corresponding data source’s update cycle, to avoid pulling incomplete partial data. The structured format of daily documents requires automated workflows to support automatic table field filling and format validation. The most time-consuming step of localizing abnormal indicators requires scheduled tasks to automatically pull full indicator datasets and compare against thresholds, reducing manual troubleshooting time costs. Failure to identify abnormal indicators in a timely manner can lead to increased customer acquisition costs and early budget exhaustion. As such, scheduled tasks must align with business monitoring requirements.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Task trigger frequency | Match data source update cycles: set to `300 seconds` for real-time data sources, `86400 seconds` for daily data sources | Aligns with actual update cycles of ad platforms and attribution systems, avoids pulling incomplete data |
| Single pull data limit | Top 1000 entries | Adapts to per-task memory usage limits, prevents data overload |
| Task retry count | 3 times | Addresses temporary network fluctuations or temporary ad API rate limiting |
| Log retention period | 30 days | Meets log tracing requirements for online troubleshooting |
| Task timeout period | 600 seconds | Matches average time required for multi-source data pulling |
| Abnormal indicator threshold | Calibrated via actual testing, e.g., conversion cost fluctuation exceeding ±15% | Aligns with core monitoring standards for campaign performance optimization |

## Three Common Mistakes
- Phenomenon: After a scheduled task runs, the configured ad account root permission is automatically reset to its initial value. Cause: The default permission reset switch for scheduled tasks was not disabled in FastGPT v4.17.0.
- Phenomenon: Model thinking time for MCP-assisted tasks exceeds 120 seconds. Cause: The upper limit for context token usage per single task was not restricted, causing the model to load excessive redundant data.
- Phenomenon: Workflow debug tasks respond faster than tasks running in production environments. Cause: Debug mode skips some log writing and permission verification steps. Production tasks must execute all processes in full.

## How to Verify Proper Configuration
- Review task scheduling logs to confirm trigger frequency matches the configured settings.
- Simulate an abnormal indicator that meets threshold criteria, then check whether the task triggers normally and generates corresponding alerts.
- Verify that data generated after task execution is correctly synchronized to the preset retrospective documents or data dashboards.
- Check permission configuration items to confirm no automatic reset has occurred.

The values provided are common starting points and should be measured against the reader's own samples.
