# Online Troubleshooting and Retrospective for Interface Integration and Data Docking: Conversation Logs and Auditing

## What Data for This Category Looks Like
This category of data primarily originates from customer system interfaces, API documentation, test data, and integration logs. Daily maintained documents include interface lists, integration records, field mapping tables, and issue tracking tables. Data is updated daily or per integration phase. Core fields include interface addresses, request parameters, return codes, data field names, synchronization times, and call statuses. Units include milliseconds, entries, characters, and others, used to record ongoing inter-system data exchange processes.

## Constraints Imposed by These Characteristics on Conversation Logs and Auditing
Since data comes from ongoing inter-system interface calls, conversation logs must be aggregated by session to fully display the full link of a single round of integration. The diversity of core fields requires the auditing workflow to support field-based filtering, retaining only key information related to integration. The phased nature of data updates means log retention periods must match integration cycles, to avoid premature cleanup of valid traceability data. Cross-system interface calls must also be linked to original API documentation and field mapping tables, to ensure consistency of interface specifications and field mappings can be verified during auditing.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Conversation log storage period | 7 days | Matches the issue traceability cycle of most integration phases |
| Log field filtering rules | Retain interface address, request parameters, return code, synchronization status | Corresponds to core fields in interface lists and integration records |
| Session aggregation association key | Bind `chatId` | Aggregates complete call links by single round of integration sessions |
| Single log detail display | Enable `detail` field | Fully displays original interface return data and exception details |
| Historical record loading limit | Top 20 entries | Prevents loading excessive redundant logs that cause interface lag |
| Exception log locating ID | Bind `responseChatItemId` | Accurately locates exception nodes for single interface calls |

## Three Common Configuration Errors
- Symptom: Exported conversation records are missing interface request parameters or return code fields. Cause: Log field filtering rules are not configured to retain the corresponding core integration fields.
- Symptom: Previous integration sessions cannot be traced even after enabling historical record association. Cause: `chatId` is not bound for session aggregation, causing logs from a single round of integration to be stored separately.
- Symptom: The number of returned audit log entries is far lower than expected when viewing logs. Cause: A reasonable historical record loading limit is not set, and the filtering logic incorrectly identifies valid data as redundant and discards it.

## How to Verify Correct Configuration
- Export logs for a specified `chatId`, and verify that core fields including interface address, request parameters, and return code are present.
- Send an integration request, then verify that the audit log list displays the complete call link aggregated by session.
- Enable historical record association, then call the interface again and confirm that previous integration records are loaded correctly.
- Log in to the FastGPT v4.17.0 backend, and check that the log storage period configuration meets the traceability requirements of the integration phase.

The configuration values provided here are common starting points, and should be evaluated against specific local samples and use cases.
