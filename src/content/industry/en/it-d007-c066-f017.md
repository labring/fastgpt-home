# Online Troubleshooting and Retrospective for Search Ad Keyword Management: Deployment and Upgrade

## What this category's data looks like
Data typically comes from search ad backends, search term reports, auction ranking data, and landing page data, with updates occurring daily or weekly. Daily produced documents include keyword lists, negative keyword lists, bid records, and search term reports. Fields cover keyword text, match mode, bid amount, triggered search volume, conversion data, and more. Units include yuan per click, clicks, characters, and others. The field order and format vary across different documents. Some historical documents may contain unstandardized redundant fields, which increases the complexity of bulk import.

## What constraints do these characteristics impose on the deployment and upgrade phase
This category has scattered data sources, requiring multi-platform API integration and multi-type document parsing. This page is compatible with the FastGPT v4.17.0 deployment process. During deployment, access permissions and field mapping rules for multiple data sources must be configured. The daily or weekly update rhythm requires that scheduled synchronization tasks are not interrupted during upgrades, and support for incremental updates and fast rollback mechanisms is needed. Diverse document structures and field types require deployment configurations to support custom field validation and format conversion to avoid parsing errors. Additionally, failures may lead to increased invalid clicks, brand term hijacking and other business impacts. Before upgrading, configure traffic isolation and gray release strategies to reduce the risk of fault spread.

## How to set configurations
| Configuration Item | Recommended Value/Method | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 800–1200 connections | Limits the number of database connections per operation, adapting to high-frequency queries and batch synchronization scenarios for search ad keyword management |
| `MONGODB_URI` | Exclusive connection string assembled per ad platform API documentation | Connects to the keyword data storage repository of the search ad backend, ensuring data read permissions |
| `REDIS_URL` | Cloud-hosted connection address using port 6379 | Caches search term report data for high-frequency queries, reducing the frequency of third-party API calls |
| `STORAGE_S3_ENDPOINT` | Endpoint address configured per cloud service provider region | Stores bulk documents such as search term reports and bid records, adapting to read and write requirements for large-volume data |
| `ROOT_KEY` | Randomly generated 32-character string | Configures a global permission verification key to prevent unauthorized access to sensitive keyword management data |
| `FILE_TOKEN_KEY` | Determined based on actual testing | Generates document access tokens, adapting to permission control for sensitive documents such as negative keyword lists |

## Three common misconfigurations
- Symptom: Empty results returned when querying the keyword list after deployment. Cause: `MONGODB_URI` is not configured correctly, making it impossible to connect to the keyword data storage repository.
- Symptom: Frequent timeout alerts triggered during scheduled synchronization of search term reports. Cause: `DB_MAX_LINK` is set too low, causing concurrent queries to exceed the database connection limit.
- Symptom: Extra zero-value fields appear in some keyword bid records after an upgrade. Cause: Format validation was not performed on imported historical documents, leading to redundant characters in the original data being retained.

## How to confirm configurations are correct
- The database connection test script can be executed to verify that the connection limit set by `DB_MAX_LINK` takes effect.
- A single search term report synchronization task can be triggered, and the task log can be checked for data source connection error messages.
- A test negative keyword list document can be uploaded to verify that the parsed fields match the preset mapping rules.
- The management page corresponding to the configured `FE_DOMAIN` can be accessed to confirm that the global permission verification function operates properly.

The values provided are common starting points and should be evaluated against the reader's own samples.
