# Online Troubleshooting and Retrospective for Database Cloud Service Operations: Deployment and Upgrade

## What data for this category looks like
Daily data for database cloud service operations typically comes from cloud database consoles, slow query logs, cluster monitoring metrics, and operation ticket systems. The update frequency is daily or after each instance change.
Core documents include instance change orders, backup and recovery records, performance diagnosis reports, and parameter adjustment records. Common fields include instance unique identifier, change time, slow SQL time-consuming threshold, backup file size, tenant ID, and others. There is no unified global standardized format, and data must be organized according to the field rules of the corresponding cloud service provider's console.

## What constraints these characteristics impose on the deployment and upgrade phase
Because data sources are scattered and there is no unified format, the deployment phase must connect to the API permissions of cloud database consoles, object storage, and other cloud services in advance to avoid configuration loading failures caused by insufficient permissions.
The high update frequency requires upgrade operations to use incremental change mode, avoiding full restarts that affect online services.
Multi-tenant document and data isolation requires separate configuration of tenant-level parameters during deployment, while also synchronously updating the change orders and diagnosis reports of each instance to ensure traceable operation processes.

## How to Set Configurations
This guide applies to the database cloud service operation deployment and upgrade scenarios for FastGPT v4.17.0. The following configuration items should be adjusted based on the actual rules of the cloud service provider:

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `2000–3000` | Adapts to the default connection limit of mainstream cloud databases, prevents connection pool exhaustion in high-concurrency scenarios |
| `MONGODB_URI` | Fill in the intranet connection address provided by the cloud service provider, with an account password with read-only permissions | Reduces cross-network access latency, complies with security isolation specifications for cloud service operations |
| `REDIS_URL` | `redis://:{custom strong password}@{intranet Redis address}:6379/0` | Caches session and configuration data, ensures session isolation in multi-tenant environments |
| `FE_DOMAIN` | Fill in the officially filed domain name bound to the cloud console | Unifies frontend access entry, complies with cloud service domain name management requirements |
| `STORAGE_S3_ENDPOINT` | Fill in the intranet endpoint address of the cloud object storage | Reduces network latency for backup and recovery operations, improves operation efficiency |

## Three Common Misconfigurations
- Symptom: The chat page crashes frequently after deployment, returning a 500 status code. Cause: `DB_MAX_LINK` is not configured, or its value is lower than the connection limit of the cloud database, leading to connection pool exhaustion in high-concurrency scenarios.
- Symptom: The knowledge base page fails to load after an upgrade, returning empty configuration fields. Cause: The cloud database instance pointed to by `PG_URL` was not updated synchronously, and the configuration table of the old instance did not complete data migration.
- Symptom: Permission boundary crossing occurs when multiple users log in, and other tenants' knowledge base data can be viewed. Cause: `ROOT_KEY` and tenant isolation rules were not configured correctly, leading to session cache not being isolated by tenant dimension.

## How to Confirm Configurations Are Correct
- Log in to the corresponding cloud database console, check that the `DB_MAX_LINK` configuration matches FastGPT's connection pool settings, and verify that there are no large numbers of connection timeout errors in the slow logs.
- Access the frontend address bound to `FE_DOMAIN`, confirm that the page loads normally, with no resource loading failures or cross-domain errors.
- Run a manual knowledge base backup task, check that the storage bucket corresponding to `STORAGE_S3_ENDPOINT` can normally write and read backup files.
- Use two accounts from different tenants to test login, verify that the session cache of `REDIS_URL` is isolated by tenant, with no cross-account session leakage.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
