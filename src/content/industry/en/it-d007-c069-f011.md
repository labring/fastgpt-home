# Online Troubleshooting and Post-Incident Review for Database Operations: Database and Operations Maintenance

## What data for this category looks like
Data for online troubleshooting and post-incident review in database operations typically comes from database monitoring systems, operation audit logs, SQL execution plan files, and internal ticketing systems. Daily generated documents include database change orders, slow SQL analysis reports, full/incremental backup records, and permission application approval forms. Data update frequency is usually daily synchronization or real-time updates alongside database changes. Document structures primarily use structured fields, including basic fields such as instance ID, execution time, rows affected, and permission level. No additional custom statistical units are used.

## What constraints these characteristics impose on the database and operations maintenance link
Multiple data sources require operations workflows to correlate logs and documents from different systems to fully locate the root cause of a fault. Daily or change-level update rhythms require fault troubleshooting processes to pull the latest monitoring data and change records promptly, avoiding reliance on outdated information. The diverse range of daily document types means operations configurations must support quick retrieval by document type, and require unified archive paths to facilitate subsequent post-incident review. The most time-consuming slow query localization step requires configurations to support quick filtering of SQL execution plans by execution time and rows affected, to shorten troubleshooting cycles.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://[username:password]@host:port/database?authSource=admin` | Complies with official MongoDB connection formatting, and meets FastGPT v4.17.0 database access requirements |
| `PG_URL` | `postgresql://username:password@host:port/database` | Follows PostgreSQL standard connection string specifications, and is compatible with mainstream cloud database instances |
| `DB_MAX_LINK` | `100–200 connections` | Balances database concurrent processing capacity and resource usage, to avoid service interruptions caused by exhausted connections |
| `REDIS_URL` | `redis://[password@]host:port` | Meets FastGPT's session caching and vector index caching needs, and ensures service state persistence |
| Slow query timeout threshold | `600 seconds` | Covers the normal execution duration of most business queries, to facilitate locating abnormal slow queries |
| Backup retention period | `7–30 days` | Meets general requirements for daily database archiving, to facilitate backtracking historical data after a fault occurs |

## Three common mistakes
- Issue: Unable to connect to external MongoDB instances via `MONGODB_URI`, returns connection timeout or authentication failure errors. Cause: Correct authentication source parameter is not added to the connection string, or network security policies restrict access to database ports.
- Issue: Local debugging environment requests to external database interfaces fail, returns 403 or connection refused status codes. Cause: Correct network whitelist or proxy rules are not configured, causing local requests to fail to penetrate to external database services.
- Issue: Database connection pool is exhausted, with Too many connections errors displayed. Cause: Configured `DB_MAX_LINK` parameter exceeds the maximum connection limit of the database instance, and the value is not adjusted based on instance resource conditions.

## How to confirm configurations are correct
- Run the FastGPT built-in database connection test tool to verify whether configuration items such as `MONGODB_URI` and `PG_URL` can establish normal connections. Set test thresholds according to the connection requirements of the database instance.
- Execute a slow query detection script to confirm that the slow query timeout threshold configuration takes effect. Set trigger conditions based on the average execution time of business queries.
- View the cache service monitoring dashboard to confirm that the `REDIS_URL` configuration is normal, and session status can be persisted normally.
- Check the backup task execution logs to confirm that the backup retention period configuration meets the preset archiving requirements.

The values provided are common starting points and should be measured against the reader's own samples.
