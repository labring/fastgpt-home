# Online Troubleshooting and Retrospective for Data Collection Task Design: Scheduled Tasks and Automation

## What the data for this category looks like
Data for this category is generated across the full lifecycle of collection tasks, sourced from customer requirements, public data sources, collection tools, and internal sample libraries. Four types of documents are routinely produced: collection plans, sample specifications, authorization statements, and task schedules. Core fields include sample scope, collection fields, compliance check items, and execution cycles. Data updates follow a per-project cycle, with task schedules and collection results typically synchronized weekly. The most time-consuming steps are sample scope definition, field specification confirmation, and collection legality verification. Errors in these steps can lead to unusable samples, compliance infringement risks, or project rework.

## What constraints these characteristics impose on scheduled tasks and automation
Dispersed data sources mean collection task trigger conditions must align with the update rhythms of multiple data sources. Weekly updates to task schedules require scheduled task execution cycles to flexibly adapt to project-level cycles. Frequent needs to confirm sample scope and field specifications mean automated workflows must support interface callbacks for temporary adjustments to collection parameters. The time-consuming nature of collection legality verification requires scheduled tasks to automatically check compliance status before execution, to avoid invalid collection. Additionally, the severity of error outcomes requires failure handling mechanisms to retain complete collection logs, to facilitate online troubleshooting and retrospective analysis.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Scheduled task execution cycle | Set according to project schedule, typically 1–7 days; short-cycle collection can be adjusted to 3–5 seconds | Aligns with the per-project update rhythm of category data, and adapts to requirements of different collection scenarios |
| Trigger check threshold | First 3 compliance check results | Covers the most time-consuming collection legality verification step, to avoid starting invalid collections |
| Failure retry count | 2–3 times | Addresses single failures caused by temporary fluctuations in collection tools, and reduces the risk of project rework |
| Log retention duration | 30 days | Meets log retrieval requirements for online troubleshooting and retrospective analysis |
| Webhook trigger switch | Enable as needed | Supports real-time receipt of external messages to trigger collection, adapting to short-cycle collection requirements |
| Interactive trigger configuration | Enable conversation invocation switch | Supports custom invocation of the interaction dialog box after triggering, to match custom workflow requirements |

## Three common mistakes
- Symptom: A 404 error is returned for POST /api/admin/initv4818 when running the FastGPT upgrade script. Cause: The scheduled task version check configuration does not match the current FastGPT version, resulting in an incorrect upgrade interface call path.
- Symptom: Scheduled tasks do not run at the set cycle, and the number of collected results does not match expectations. Cause: The sample scope definition is not correctly linked to the scheduled task trigger logic, resulting in a collection scope that does not meet task requirements.
- Symptom: Clicking the custom trigger button does not invoke the conversation dialog box, and the collection process cannot be triggered. Cause: The interactive trigger switch is not enabled in the automation configuration, causing the task to only run in the background without invoking the conversation interface.

## How to confirm the configuration is correct
- Access the scheduled task management interface of FastGPT v4.17.0, and verify that the execution cycle matches the project schedule.
- Trigger a test collection, and check that compliance check logs are fully retained.
- Simulate a collection failure scenario, and confirm that the system executes retries and log reporting according to the configuration.
- Enable the Webhook and interactive trigger switches, and test whether external message triggering and conversation invocation functions work properly.
