# Online Troubleshooting and Retrospective for Data Collection Task Design: Deployment and Upgrade

## What the data for this category looks like
This category of data primarily comes from customer requirements, public data sources, collection tools, and in-house sample libraries. Daily supporting documents include collection plans, sample specifications, authorization instructions, and task schedules. Data update rhythm adjusts based on project cycles or weekly cycles. Core fields include collection scope, target field type, authorization compliance requirements, and task schedule nodes. There are no unified fixed units; some fields use units such as items, characters, and calendar days for measurement.

## What constraints do these characteristics impose on the deployment and upgrade link
The data sources for collection task design are scattered and the update rhythm is flexible, requiring the deployment link to adapt to multiple types of data source connection configurations. When upgrading, seamless migration of existing data and configurations must be ensured. The structured storage requirements for supporting documents require configuring appropriate file storage and key management parameters. Sample scope definition, field specification confirmation, and collection legitimacy verification are core time-consuming links. Their verification logic must be updated synchronously with the deployment environment to avoid project rework caused by compliance verification failure after upgrade. Migration of knowledge bases and task configurations for existing projects must be completed via image pulling or data backup, and core configuration files must not be directly overwritten.

## How to set the configurations
| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| `MONGODB_URI` | Connection string pointing to the project-specific collection task database | Stores structured documents such as collection plans and sample specifications, and must be isolated from general business databases to ensure data separation |
| `REDIS_URL` | Configured as a cache connection with a 600-second expiration period | Caches frequently queried collection task schedules and authorization verification results to reduce database access pressure |
| `STORAGE_S3_ENDPOINT` | Bound to the object storage bucket exclusive to collection tasks | Stores temporary sample files and authorization instruction documents generated during collection, and uniformly manages unstructured data |
| `FILE_TOKEN_KEY` | Generate a 32-bit random key per project | Encrypts file access permissions for collection tasks to prevent unauthorized leakage of sample data |
| `PG_URL` | Connection address pointing to the collection compliance verification database | Stores historical records of collection legitimacy verification, supporting compliance retrospective per project |
| `ROOT_KEY` | Generated only during deployment initialization, not changed during upgrades | Manages global configuration permissions for collection tasks, preventing permission configuration chaos after upgrades |

## Three common mistakes
- Symptom: The content extraction module fails to execute normally after deployment, and the interface shows empty collection fields. Cause: `PG_URL` is not correctly configured to point to the compliance verification database, causing specification verification of collection fields to fail and blocking the extraction process.
- Symptom: After upgrading to FastGPT v4.17.0, the network connection function of existing collection tasks fails. Cause: Network configuration parameters from older versions were not migrated synchronously during image pulling, requiring manual update of the corresponding environment variables.
- Symptom: After deploying using the specified version combination, the rerank function returns no results. Cause: The data storage format designed for the collection task does not match the input requirements of the rerank model, resulting in data parsing failure.

## How to confirm configurations are correct
- Run the compliance verification script for collection tasks to check if the collection plan stored in the database corresponding to `MONGODB_URI` can be read normally.
- Upload a temporary sample file to verify that the access link generated by `FILE_TOKEN_KEY` can be downloaded normally without permission errors.
- Export existing collection task configurations before and after upgrading, and compare to confirm that core fields such as task schedules and sample specifications have not been lost or disrupted.
- Restart the service and check the connection logs for `REDIS_URL` to confirm that the cache service has no timeout or connection failure errors.

The values provided here are common starting points and should be measured against the reader's own samples.
