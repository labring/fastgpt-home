# Troubleshooting and Review of Online Faults for Dataset Delivery and Version Management: Deployment and Upgrade

## What this category of data looks like
Data for this category typically comes from object storage, data warehouses, annotation platforms, and customer acceptance feedback. The update rhythm follows each batch delivery or version release. Daily supporting documents include dataset descriptions, version records, delivery checklists, and acceptance reports. Common data fields include version number, source batch identifier, delivery verification code, sample difference description, etc. There are no mandatory additional units, only general identifier rules matching the delivery scenario need to be followed.

## What constraints these characteristics impose on the deployment and upgrade link
The data sources for this category are scattered. The deployment and upgrade links require configuring multi-source access storage and database parameters to avoid cross-source data confusion. The data update rhythm is flexibly adjusted with delivery batches. Upgrades must support incremental version synchronization to avoid excessive bandwidth occupation from full retransmissions. Daily documents are strongly bound to datasets. During deployment, the document storage path and dataset metadata must be associated to ensure consistency for version tracing. Delivery integrity verification relies on built-in verification logic. Corresponding configurations must be enabled during deployment to prevent data mixing or irreproducible training results.

The following configurations are formulated based on the deployment specifications of FastGPT v4.17.0.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://{user}:{pass}@{host}:27017/fastgpt_dataset?authSource=admin` | Stores dataset version metadata and delivery checklists, must match the storage address of the data source |
| `PG_URL` | `postgresql://{user}:{pass}@{host}:5432/fastgpt_version?sslmode=require` | Stores structured data for version records and acceptance reports, supports multi-version associated queries |
| `DB_MAX_LINK` | `80–120 connections` | Adapts to concurrent access of multiple dataset batches, avoids database connection exhaustion |
| `STORAGE_S3_ENDPOINT` | `Official access domain name of the corresponding object storage` | Connects to the object storage source for datasets, ensures legitimacy of file reading and delivery |
| `REDIS_URL` | `redis://:{pass}@{host}:6379/0` | Caches temporary status for delivery verification, timeout threshold is determined based on actual testing |
| `ROOT_KEY` | `Randomly generated 32-character string with no special characters` | Serves as the root permission key for dataset delivery, restricts unauthorized version access |

## Three common configuration mistakes
- The symptom is that accessing the dataset delivery interface returns a 403 Forbidden status code after deployment, with a prompt that the token does not have access permission. The cause is that the `FILE_TOKEN_KEY` configuration does not match the signature key of the object storage, resulting in failed token verification.
- The symptom is that some fields in version records are empty after an upgrade. The cause is that the database structure change corresponding to `PG_URL` was not synchronized during the upgrade, causing old version metadata to fail to match the new field rules.
- The symptom is data mixing during delivery of multiple batch datasets. The cause is that a reasonable connection number for `DB_MAX_LINK` was not configured, causing incorrect version data to be read during concurrent requests.

## How to confirm configurations are correctly set
- Run a connection test for the corresponding database to verify whether the configurations of `MONGODB_URI` and `PG_URL` take effect.
- Upload a single test dataset file, generate an access token through the delivery interface, and verify that the token legitimacy verification logic works normally.
- Initiate multi-batch dataset query requests to confirm that the configuration of `DB_MAX_LINK` does not cause database connection exceptions.
- Check the cache service status to confirm that the `REDIS_URL` configuration can normally store temporary verification data.

The values given are common starting points and should be measured against the reader's own samples.
