# Online Troubleshooting and Retrospective for Text Annotation Projects: HTTP Interfaces and External Systems

## What this project’s data looks like
Text annotation project data primarily comes from customer-provided corpora, annotation results produced by in-house annotation platforms, industry standard vocabularies, and quality inspection sampling results. Daily produced documents include annotation specifications, sample packages, quality inspection reports, and problem feedback forms. Data update cycles follow daily or single-batch annotation task schedules. Data fields mostly revolve around semantic entities, intent classification, and label boundary definitions, with no unified fixed unit standards. Adjustments must be made based on the label system of specific annotation tasks.

## What constraints these characteristics impose on HTTP interfaces and external systems
Text annotation project data relies on multi-source input and output. HTTP interfaces must simultaneously connect to sample push from the annotation platform, quality inspection result return, and vocabulary update requests. Therefore, interface call frequency must match the data update rhythm. The text length of single requests varies widely, covering short-text intent classification to long-document semantic annotation. Support for variable-length request payloads is required. Data correlation is high: annotation results must be bound to original corpora and quality inspection records. Interface transmissions must carry association identifiers to avoid data misalignment. Additionally, interruptions to annotation tasks directly impact delivery progress, and interface stability is directly tied to project delivery cycles.

## How to set configurations
This configuration is designed based on the interface functions of FastGPT v4.17.0.

| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `Authorization` | Fixed authentication key, rotated every 90 days | Ensures secure access to interfaces between external systems and the platform, complies with general authentication specifications |
| Timeout Period | 600 seconds | Matches the average processing duration of single-batch annotation tasks, prevents premature request termination |
| `responseData` | Includes original corpus ID, annotation results, quality inspection identifiers | Binds data association relationships, avoids misalignment between annotation results and original samples |
| Concurrent Request Limit | Top 20 entries | Matches the daily parallel task scale of annotation teams, prevents external system load saturation |
| `variables` | Carries the label rule ID of the current annotation batch | Dynamically adapts to the label systems of different annotation tasks, improves interface reusability |
| Retry Count | 3 times | Addresses temporary connection failures caused by network fluctuations, reduces interface call failure rates |

## Three common configuration mistakes
- `getaddrinfo EAI_AGAIN` error occurs, unable to resolve the target domain name. Cause: No reliable public DNS server is configured, or the domain name resolution cache of the external system has expired.
- Interface returns 429 status code, indicating upstream load is saturated. Cause: The concurrent request limit is configured too low, and does not match the parallel task scale of the annotation team, resulting in interface calls exceeding carrying capacity.
- The `responseData` field returned by the interface lacks association identifiers. Cause: The original corpus ID or batch information is not carried in the request parameters, resulting in annotation results being unable to bind to original samples.

## How to confirm configurations are set correctly
- Initiate a single annotation sample push request, check that the interface returns a 200 status code, and that `responseData` contains the expected association identifiers.
- Simulate multiple concurrent requests, observe the interface load status, adjust the concurrent limit to a value that matches the actual task scale, and confirm that no load saturation-related errors occur.
- Rotate the `Authorization` key regularly, verify that the new key can call the interface normally, and that the old key cannot access the interface, confirming that the authentication configuration takes effect.
- Test the domain name resolution function, initiate a request to the external system, confirm that no domain name resolution failure errors occur, and verify that the DNS configuration is normal.

The values provided here are common starting points and should be measured against the reader's own samples.
