# Online Troubleshooting and Retrospective for Documentation Site Maintenance: Conversation Logs and Auditing

## What the data for this use case looks like
Business data for documentation site maintenance comes primarily from code repositories, documentation site build logs, user feedback, and version release records. Update frequency is weekly or upon each version release.

Daily maintained documents include four categories: installation documentation, API documentation, migration guides, and FAQs. Common data fields include document version number, build timestamp, user question keywords, conversation request path, error status code, and version change entries. The overall data centers on document publishing, usage, and feedback, supporting document iteration and online troubleshooting.

## Constraints on conversation logs and auditing workflows
Data sources cover multi-dimensional documentation operation and maintenance and user interaction information. Conversation logs and auditing must associate multi-source data to complete effective troubleshooting. Do not store only single-dimensional conversation content.

The weekly or per-version update rhythm requires logs to be archived by version or cycle, to avoid redundant storage. The four categories of daily documents require logs to be classified and retrieved by document type, to help locate faults for specific documents.

Consequences of errors include users being unable to install, misusing interfaces, and similar issues. This requires audit logs to fully record request context and return results, to support accurate fault retrospection.

## How to configure settings
This configuration applies to FastGPT v4.17.0. Specific configuration items are listed below:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind a unique identifier to user sessions | Used to distinguish historical chat records of different users, matching multi-user session management requirements |
| `responseChatItemId` | Generate a unique identifier for each conversation response | Used to locate specific response content of a single faulty conversation, facilitating precise auditing |
| `detail` | Enable full log storage | Store user questions, document return content, and error information, covering multi-source business data |
| Log retention period | 7–30 days | Matches weekly or per-version update frequency, balancing storage costs and retrospection needs |
| Associated document version | Automatically bind the currently released document version | Aligns with version release records, simplifying version-based fault troubleshooting |
| Non-document request filtering | Only record conversation requests related to the documentation site | Focus on business data for this use case, filtering out irrelevant conversation interference |

## Three common configuration errors
- Phenomenon: Historical chat records of different users cannot be distinguished. Returned logs do not carry identifiable user session identifiers. Cause: The `chatId` parameter is not configured to bind a unique identifier for user sessions, resulting in logs being unable to distinguish conversation data of different users.
- Phenomenon: Audit logs are not associated with the current document release version, making version-based troubleshooting of faults caused by expired content impossible. Cause: The setting for automatically binding document versions is not configured, resulting in logs being disconnected from version release records.
- Phenomenon: Dependent services for starting the documentation site fail. Logs show database connection timeouts or high storage usage. Cause: A reasonable log retention period is not set, resulting in database storage resource exhaustion and startup exceptions.

## How to confirm configurations are correctly set
- Initiate test conversations for different users, check whether logs carry unique `chatId` identifiers, and confirm that historical records of different users can be distinguished.
- View the audit details of a single conversation, confirm that the `detail` parameter is enabled and saves complete user questions, document responses, and error information.
- Check the associated fields of audit logs, confirm that logs automatically bind the currently released document version.
- View database storage usage, confirm that the log retention period setting meets business retrospection needs, and that excessive storage issues do not occur.

The values given are common starting points and should be measured against the reader's own samples.
