# Online Troubleshooting and Retrospective for Log Platforms and Observability: Database and Operations

## What data for this category looks like
It typically comes from logging systems, distributed tracing (Trace) platforms, Metrics monitoring systems, and application-embedded SDKs. Daily supporting documents include logging collection specifications, tracing instructions, metric dictionaries, and dashboard configuration records. Data updates occur daily or alongside application version iterations. Fields include timestamps, request IDs, error codes, link latency, QPS, and others. Units include milliseconds, counts, bytes, and more. Data formats vary across sources. Log data is mostly semi-structured text. Trace data includes unique link identifiers. Metrics data primarily consists of time-series numerical values.

## What constraints these characteristics impose on database and operations workflows
Multi-source heterogeneous data access requires a unified storage format. Standardized mapping must be applied to fields from different sources, which increases the complexity of database table structure design. High update frequencies require databases with high write throughput. Connection pools and indexing strategies must be properly configured to ensure query performance during troubleshooting. The diversity of supporting documents requires operations teams to maintain metadata indexes for quick retrieval of historical configurations and troubleshooting records. The diversity of fields and units requires databases to retain original field information during storage, to avoid precision loss caused by unit conversion that could affect troubleshooting accuracy.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://[username]:[password]@[host address]:[port]/[database name]?authSource=admin` | Complies with official connection specifications for MongoDB and domestically compatible databases, supports domestic replacement scenarios |
| `PG_URL` | `postgresql://[username]:[password]@[host address]:[port]/[database name]?sslmode=prefer` | Adapts to standard connection formats for PostgreSQL and domestic PostgreSQL branches, ensures data transmission security |
| `DB_MAX_LINK` | `100–200 connections` | Balances database resource usage and concurrent processing capacity, prevents connection exhaustion |
| `REDIS_URL` | `redis://:[password]@[host address]:[port]/0` | Adapts to standard connection configurations for cache storage, used for persistent session context |
| Context cache expiration time | `300–900 seconds` | Matches the average duration of online troubleshooting, ensures context is not lost during the troubleshooting cycle |

## Three common mistakes
- Symptom: Database connection failure in domestic environments, with `Connection refused` or `unsupported authentication method` errors. Cause: Connection string format adapted for domestic databases is not used, and default configurations of open-source components are still applied.
- Symptom: Context is lost during consecutive multiple rounds of queries, returning results unrelated to the current question. Cause: Context cache expiration time is set too short, or `REDIS_URL` configuration is incorrect, preventing normal cache writes.
- Symptom: `Query timed out` errors occur during high-concurrency log queries, with excessively long query latency. Cause: Indexes are not created for key troubleshooting fields such as request ID and timestamp, leading to full table scans by the database.

## How to confirm configurations are correct
- Run the database connectivity test tool built into FastGPT v4.17.0 to verify that `MONGODB_URI`, `PG_URL`, and `REDIS_URL` configurations have no syntax errors and can connect normally.
- Check the database connection pool monitoring dashboard to confirm that current active connections fall within the range set by `DB_MAX_LINK`, with no connection overflow.
- Initiate more than 3 consecutive query requests to verify that the context cache updates normally, and subsequent queries can correctly associate historical session information.
- Execute a single log query to confirm that corresponding tracing data and metric information can be quickly located via the request ID, with no missing fields or format anomalies.

The values provided are common starting points, and should be evaluated against the reader's own samples.
