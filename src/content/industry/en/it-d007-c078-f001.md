# Online Troubleshooting and Retrospective for Cabinet Rack Installation and Cabling: HTTP Interfaces and External Systems

## What Data Looks Like for This Use Case
The typical users of this use case are IDC operations engineers, network engineers, and equipment implementation personnel. Daily used documents include rack installation applications, cabinet cabling diagrams, port label sheets, and construction records. Data sources are primarily DCIM systems, asset systems, network topologies, and customer work orders. Update frequency is per order or daily. Common data fields include rack position number, port number, cable type, construction date, and others. The format is fixed and strongly tied to physical device access.

## Constraints for HTTP Interfaces and External Systems
Data sources for this use case are scattered and strongly bound to physical device access. HTTP interfaces must connect to multiple external systems at the same time to pull full business data. Fixed-format field requirements mean interface request parameters must match standard fields from documents such as installation applications and cabling diagrams, to avoid data format incompatibility. The update frequency of per order or daily means interfaces must support both on-demand pulling and scheduled synchronization modes. This accommodates single installation tasks and daily asset update scenarios. Physical access errors can lead to severe business consequences. Interfaces must verify the completeness and correctness of returned data fields to prevent invalid data from entering subsequent processes.

## Configuration Guidelines
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `AIPROXY_API_ENDPOINT` | Root address of the AI Proxy service, for example http://aiproxy:3000. Do not append /v1 or /chat/completions, and do not use a single-model address instead. | Starting with FastGPT v4.17.0, the App/Admin server requires this environment variable to specify the access address for the AI Proxy service. |
| `variables` | `Collection of variables including rack position number, port label, cable type, and construction date` | Daily documents for this use case include fixed fields, which must be passed to HTTP interface requests and workflows via variables. |
| `responseData` | `Only retain return fields for port mapping, device rack position, and construction records` | Redundant data must be filtered out, leaving only core business fields required for cabinet rack installation and cabling. |
| Request timeout | `600 seconds` | Data docking for this use case involves multiple sources including DCIM and asset systems, so sufficient time is needed to complete cross-system data pulling. |
| Request retry threshold | `Terminate after the first 3 failures` | This avoids overloading external systems from repeated requests, while ensuring the success rate of core data pulling. |

## Three Common Configuration Mistakes
- Symptom: Workflow generation results are normal, but no content is received by the external push interface. Cause: The `AIPROXY_API_ENDPOINT` or `AIPROXY_API_TOKEN` environment variables are not configured correctly, or an application API Key is used instead of the AI Proxy administrator Token, resulting in authentication failure.
- Symptom: The HTTP interface returns full list data without filtering invalid ports or rack position information. Cause: Core business fields are not extracted via the `responseData` parameter, and raw interface data is returned directly.
- Symptom: Variables after an HTTP request in a workflow cannot be correctly bound to the specified step. Cause: Cabinet data fields are not explicitly mapped via the `variables` parameter, leading to chaotic variable passing.

## How to Verify Successful Configuration
- Check the environment variable configuration on the App/Admin server, confirm that `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are correctly set and not empty.
- Initiate a test request to verify the validity of AI Proxy service authentication, confirm that the returned status code is 200.
- Review workflow run logs, confirm that the `variables` and `responseData` parameters have correctly extracted and passed business fields.
- Trigger a simulated rack installation process to verify whether external systems have received return data that meets business requirements.

The values provided here are common starting points, and should be evaluated against samples specific to the actual deployment.
