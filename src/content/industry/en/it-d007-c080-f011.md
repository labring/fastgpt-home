# Online Troubleshooting and Retrospective for Desktop Terminal Support: Database and Operations

## What this category's data looks like
Data for this category primarily comes from terminal management platforms, enterprise asset systems, user reporting portals, and internal software repositories. Daily generated documents include terminal trouble tickets, installation manifests, software installation records, and remote assistance records. Fields cover terminal unique identifiers, fault categories, processing duration, software versions, and peripheral models, among others.
Data update frequency follows daily batch synchronization or real-time updates per single request. Single record size is small, but total batch data volume fluctuates with terminal scale.

## What constraints these characteristics impose on the database and operations link
Multiple data sources require databases to support cross-system data connection and associated queries, and adapt to field format differences across sources. Coexisting real-time update requests and daily batch sync tasks demand databases balance low-latency read/write operations and batch write performance.
Multiple document types such as terminal trouble tickets and installation manifests have varying field structures. Flexible data mapping rules must be configured to unify storage formats.
Additionally, data delays in fault troubleshooting directly lead to work order backlogs. High-availability deployment and rapid fault recovery mechanisms for databases are necessary configurations.

## How to set configurations
This configuration applies to FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `PG_URL` | PostgreSQL-standard connection format instance address, including authentication information and target database name | Adapts to internal enterprise or hosted PostgreSQL database instances, ensures normal storage and query of trouble ticket and asset data |
| `DB_MAX_LINK` | `10–20 connections` | Matches the concurrent request limit for a single node in desktop terminal scenarios, prevents exhaustion of database connection resources |
| `REDIS_URL` | Redis instance connection address including authentication information | Used to cache frequently accessed terminal trouble ticket and installation manifest data, reduces read/write pressure on the primary database |
| `MONGODB_URI` | MongoDB connection string including replica set configuration | Stores unstructured remote assistance logs and peripheral configuration data, supports flexible document-based queries |

## Three common mistakes
- Phenomenon: `text index required for $text query` error appears after service startup, and the knowledge base cannot load normally. Cause: No full-text index created for text fields in the PostgreSQL database, cannot support FastGPT's query matching logic.
- Phenomenon: Terminal fault data is lost after upgrading FastGPT. Cause: Did not back up stored data from the target database instance before upgrading, or did not retain the original database table structure and associated relationships.
- Phenomenon: Remote assistance records cannot be associated with corresponding terminal trouble tickets. Cause: Incorrect database field mapping configuration, no association index created between terminal ID and trouble ticket ID, resulting in failure to correctly associate data.

## How to confirm configurations are correct
- Run the official database connectivity test script to verify that the authentication and address configurations for `PG_URL`, `MONGODB_URI`, and `REDIS_URL` are correct.
- Submit a simulated terminal trouble ticket data record, confirm that the data can be written and read normally after querying, verify that the concurrent connection limit of `DB_MAX_LINK` is not triggered.
- View the database monitoring panel, confirm that the real-time connection count does not exceed the configured `DB_MAX_LINK` threshold, adjust the value based on actual terminal scale.
- Trigger a remote assistance log synchronization task, confirm that unstructured log data can be stored normally in the MongoDB instance.

The values provided are common starting points and should be evaluated against local deployment samples.
