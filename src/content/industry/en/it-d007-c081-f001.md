# Online Troubleshooting and Retrospective for Penetration Testing Services: HTTP Interfaces and External Systems

## What the data for this category looks like
Penetration testing service data comes from target systems, vulnerability databases, scanner results, and manual verification records. Updates are triggered per project or major version iteration. Daily produced documents include test authorization letters, penetration test reports, vulnerability reproduction records, and rectification suggestions. Core fields cover authorization scope, vulnerability severity, reproduction steps, affected interfaces, and risk ratings. There is no unified fixed standard for project data volume or field count.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Since data sources include both manual verification and tool scan results, HTTP interfaces must support parsing of both structured scan data and unstructured manual records. Because updates are triggered per project, interface calls must be triggered on demand to avoid ineffective high-frequency polling. In line with compliance requirements of test authorization letters, interfaces must verify access identities to prevent unauthorized test operations. Vulnerability ratings and report generation rely on standardized response data, so interfaces must filter redundant information to focus on core content. Errors may cause business interruptions or authorization disputes, so interfaces must be configured with appropriate failure handling and retry logic.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${project-specific authorization token}` | Matches the identity verification requirements of test authorization letters, ensures only interfaces within the authorized scope can be called, and adapts to the FastGPT v4.17.0 interface specification |
| `variables` | `{"targetSystem": "test domain", "maxResponseSize": "100 MB", "retryCount": 2, "timeout": 600 seconds}` | Adapts to target systems and data volume limits of penetration testing projects, calibrates retry and timeout parameters based on actual measurements to ensure interface call stability |
| `responseData` | `Only retain vulnerability-related fields` | Filters redundant scan data, focuses on core information required for vulnerability reproduction and rating, and simplifies subsequent report generation workflows |
| `variables` | `{"modelRedirect": {"gpt-4o-mini": "gpt-4o"}}` | Adapts to model call requirements in penetration testing scenarios, unifies model usage rules across different test phases |
| `responseData` | `Associate vulnerability database ID mapping` | Unifies vulnerability identifiers from different source scan results, facilitating cross-tool data integration and rating |

## Three common configuration errors
- Symptom: After configuring model redirection rules, the actual returned model type does not match the expected one. Cause: The redirection mapping parameter was not correctly configured in `variables`, causing the interface to not switch models according to the rules.
- Symptom: Interface calls frequently trigger quota limit errors. Cause: The token consumption threshold in `variables` was not set according to the authorized quota of the penetration testing project, exceeding the authorized token usage limit.
- Symptom: The number of vulnerability feature search results is abnormal, and matching accuracy is insufficient. Cause: An external interface that matches the embedding dimension of the target vector model was not used, resulting in non-compliant feature vector conversion.

## How to confirm the configuration is correct
- Call the test interface, check whether the correct `Authorization` parameter is carried in the request header, and confirm that the interface returns an identity verification passed result.
- View the `responseData` returned by the interface, confirm that only core fields such as vulnerability severity, reproduction steps, and affected interfaces are included, with no redundant information.
- Trigger multiple interface calls, check whether failure scenarios are handled according to the retry count and timeout period configured in `variables`.
- Compare the configured model redirection rules with the model identifier returned by the interface, confirm that the mapping relationship takes effect.

The values provided here are common starting points and should be measured against the reader's own samples.
