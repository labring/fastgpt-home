# Online Troubleshooting and Retrospective for Channel Attribution and Lead Distribution: Database and Operations

## What This Category of Data Looks Like
Data for channel attribution and lead distribution primarily comes from advertising platforms, CRM systems, attribution SDKs, and form submission systems. Update cycles follow daily or weekly schedules. Daily associated documents include attribution rule configuration tables, lead distribution tables, channel performance reports, and exception checklists. Common fields include channel identifiers, lead unique IDs, assigned sales accounts, conversion timestamps, budget association codes, and more. There is no unified mandatory format, and adjustments are made flexibly based on business configuration.

## What Constraints Do These Characteristics Impose on the Database and Operations Link
Multi-source heterogeneous data access requires the database layer to support multiple data source protocols, avoiding hard-coded adaptations for different business systems. Daily or weekly batch data updates create periodic write pressure, requiring proper configuration of database connection pools to handle peak loads. The flexible, non-mandatory format of daily documents requires the database to support flexible schemas, without pre-defining strict table structures. Frequent channel parameter verification and sales ownership confirmation operations require a caching layer to reduce database query latency. Temporary query needs for exception checks require operations teams to configure appropriate log retention periods and storage space.

## How to Set Configurations
The following configurations are compatible with FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://admin:xxx@host:27017/fastgpt_attr?authSource=admin` | Stores unstructured lead data from attribution SDKs and form systems, supports flexible schema adjustments |
| `PG_URL` | `postgresql://user:xxx@host:5432/attr_db?sslmode=require` | Stores structured data requiring transaction guarantees such as channel rules and budget associations, ensures data consistency |
| `DB_MAX_LINK` | `20–30` | Meets concurrent connection requirements for daily batch data synchronization and frequent lead verification, prevents resource exhaustion |
| `REDIS_URL` | `redis://:auth@host:6379/0?socket_timeout=60` | Caches frequently accessed channel mapping and ownership rule data, reduces database query latency |

## Three Common Misconfigurations
- Phenomenon: Channel attribution queries return a 504 status code, with single query latency exceeding 15 seconds. Cause: The caching service is not configured via `REDIS_URL`, and frequent queries directly access the database, failing to handle peak pressure from batch data synchronization.
- Phenomenon: Duplicate lead unique ID entries appear in lead distribution tables. Cause: The `DB_MAX_LINK` configuration value is improperly set. Connection pool exhaustion during concurrent writes causes partial write operations to execute repeatedly.
- Phenomenon: Some channel identifier fields in channel reports are empty, making it impossible to match attribution rules. Cause: The `PG_URL` configuration does not enable secure transmission options. Packet loss occurs during data transmission, leading to failure to properly load some configuration data.

## How to Verify Proper Configuration
- Run batch data synchronization scripts, monitor active connection counts for the database connection pool, and adjust the `DB_MAX_LINK` value to match current concurrent peak loads.
- Access the channel attribution query interface, check cache hit logs, and confirm that the caching service configured via `REDIS_URL` properly returns high-frequency rule data.
- Edit an attribution rule, check database write logs, and confirm that the `MONGODB_URI` and `PG_URL` configurations can properly read and write corresponding data.
- Run temporary query operations for exception checklists, verify that the database schema can adapt to flexible query conditions, with no mandatory format restrictions.

The values provided are common starting points, and should be evaluated against the reader's own samples.
