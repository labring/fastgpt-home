# Online Troubleshooting and Retrospective for Game Content Compliance Self-Check: Conversation Logs and Auditing

## What Data for This Category Looks Like
This category of data is generated daily by game release compliance officers, content reviewers, and game producers. Sources include game text, art assets, plot scripts, and public regulatory requirements. Data is updated per game version or operational campaign. Daily supporting documents include content self-check lists, sensitive content modification records, user agreements, and compliance review minutes. Data is created for a single compliance check task, containing reviewed content snippets, review actions, review opinions, and associated version or campaign identifiers. Its structure aligns with the full workflow of compliance self-checks.

## Constraints for Conversation Logs and Auditing
Unlike game edition number and publication declaration, this compliance self-check process occurs before declaration and during version updates. Logs do not need to cover the full publication workflow, and only need to focus on check nodes for a single version or campaign. The per-version or per-campaign data update pattern requires conversation logs to support batch retrieval and archiving by version or campaign. This allows efficient retrospective review of compliance check issues in batches. The structured format of daily supporting documents requires log fields to link to specific review nodes and task IDs. This ensures one-to-one correspondence with self-check lists and modification records. Data includes review records for multiple content resource types, so logs must distinguish content types and record corresponding verification parameters. This adapts to compliance check logic for different resources. Regulatory-related data attributes require log retention to meet compliance traceability rules, and logs must not be modified or deleted arbitrarily.

## Configuration Guidelines
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Conversation log retention period | 90–120 days | Matches the average cycle of game version updates, meets compliance traceability and retrospective needs |
| `chatId` parameter enable | Enabled | Associates individual conversations with specific review tasks, resolving the issue where call logs cannot locate corresponding review tasks |
| `detail` log switch | Enabled | Records complete reviewed content snippets and review opinions, meeting auditing requirements for compliance self-checks |
| `responseChatItemId` field collection | Enabled | Records the unique identifier of individual conversations, facilitating cross-system association of review tasks and logs |
| Log retrieval timeout threshold | 600 seconds | Prevents excessive system load from long-duration retrievals, adapting to batch compliance check scenarios |
| Automatic log cleanup rule | Clean up expired logs after archiving by version | Reduces redundant storage usage, adapting to the high-frequency version update rhythm |

## Three Common Misconfigurations
- Phenomenon: The `chatId` field does not appear in conversation logs after calling a compliance check interface. Cause: The log collection configuration for the `chatId` parameter is not enabled, leading to missing task association information.
- Phenomenon: Detailed failure logs for large model calls via OneAPI cannot be viewed. Cause: The `detail` log switch is not enabled. Only basic call status is collected, and detailed error content is not recorded.
- Phenomenon: Compliance self-check logs are automatically cleaned up due to high storage usage. Cause: The retention period is not configured according to version cycles, and the retention duration exceeds the system's preset storage threshold.

## How to Verify Configuration Success
- Initiate a compliance check call with the specified `chatId`, and confirm the field displays normally in the conversation log list.
- Trigger a large model call failure scenario, then view log details to confirm error information recorded via the `detail` field is present.
- Attempt to retrieve logs by version ID, and confirm that compliance check records for the corresponding batch can be located quickly.
- Check system storage monitoring to confirm the configured automatic cleanup rule regularly cleans up expired logs, preventing storage overflow.
