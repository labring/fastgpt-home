# Online Troubleshooting and Retrospective for Game Client Performance Optimization: Database and Operations

## What Data Looks Like for This Category
Data for this category comes from frame rate and CPU usage logs exported by engine Profiler, crash report data from crash platforms, resource loading time records from real device tests, and performance test reports, device compatibility lists, optimization records, and crash analysis reports that accompany version iterations.
Data is updated daily or when a version is released. Documents typically include fields such as device identifier, frame rate value, resource loading path, and crash stack information. Units include frames per second (fps), milliseconds (ms), megabytes (MB) for resource usage, and others.

## Constraints on Database and Operations Workflows
Data for this category originates from scattered sources with inconsistent update frequencies. Databases must support batch writing of multiple formats. Database connection pool configurations must be adapted for high-concurrency batch writing scenarios.
Multi-dimensional field structures require targeted database indexes to optimize query efficiency when filtering by device, version number, and other conditions.
Data errors can directly cause game lag, crashes, or store negative reviews. This means data writing reliability and low-latency queries must be ensured.
This category focuses heavily on frame rate and resource loading related data, which has high requirements for time series query performance.

## How to Configure Settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://perf_user:xxxx@db-host:27017/game_perf?authSource=admin` | Stores unstructured document data such as crash stacks and optimization records, supports flexible field expansion |
| `PG_URL` | `postgresql://perf_user:xxxx@db-host:5432/perf_metrics?sslmode=prefer` | Stores structured time series data such as frame rates and resource loading times, supports efficient range and conditional queries |
| `DB_MAX_LINK` | `20–30 connections` | Matches the batch write concurrency during daily version iterations, prevents database connection exhaustion |
| `REDIS_URL` | `redis://:xxxx@redis-host:6379/1` | Caches frequently accessed device compatibility lists and recent performance test report summaries, reduces database read load |
| Redis cache expiration time | `3600 seconds` | Caches device compatibility data with low update frequency, reduces repeated database query overhead |

## Three Common Errors
- Symptom: MongoDB connection status shows failure, console returns connection timeout or authentication failure errors. Cause: The username, password, or authentication source parameter in `MONGODB_URI` is not configured correctly, or database network policies restrict access.
- Symptom: No response occurs after concurrent requests reach a certain number, and local model server resources are not exhausted. Cause: The connection limit for `DB_MAX_LINK` was not adjusted, the database connection pool is exhausted, and cannot accept new requests.
- Symptom: Performance data query results are empty or missing recent records. Cause: No reasonable database write timeout was set during batch data writing, resulting in some log data failing to be stored in the database.

## How to Verify Correct Configuration
- Run a database connection test script to verify connectivity for `MONGODB_URI`, `PG_URL`, and `REDIS_URL`, confirm there are no authentication or network errors.
- Simulate the batch data writing scenario during daily version iterations, check the database connection pool usage, confirm the connection count does not exceed the `DB_MAX_LINK` configuration value.
- Query the device compatibility list data in the cache, confirm the data update frequency meets business requirements, verify the effectiveness of the Redis cache.
- Initiate multiple concurrent performance data query requests, observe database load, confirm query latency meets troubleshooting needs.
