# Online Troubleshooting and Retrospective for Game Design and Numerical Tuning: Scheduled Tasks and Automation

## What data for this category looks like
The data for this category primarily comes from player behavior logs, public competitive product materials, in-game battle records, and version feedback. Daily deliverable documents include gameplay design documents, numerical configuration tables, version requirement lists, and balance test records. Data updates follow weekly or single-version cycles. Numerical table fields include damage coefficients, skill cooldown durations, drop probabilities, and other metrics. Units include seconds, item quantities, and others. Document structures mostly consist of structured tables and rule description text.

## Constraints imposed by these characteristics on scheduled tasks and automation
This category’s data updates follow weekly or single-version cycles, so scheduled task trigger frequencies must align with update rhythms to avoid reprocessing unchanged historical data. Daily produced structured numerical tables and rule documents require automated workflows to adapt to table parsing and field matching logic, reducing exceptions caused by format errors. The volume of battle logs and player feedback data grows with version iterations, so the batch processing limit for scheduled tasks must adapt to data scale to prevent processing timeouts. Errors in numerical configuration directly cause gameplay imbalance, so automated workflows must add pre-check steps to ensure configuration compliance before execution.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| Scheduled task trigger cycle | `7 days` or 1 day before a single version launch | Aligns with weekly or single-version data update rhythms, avoids reprocessing historical data |
| Batch data processing limit | Top 2000 entries or calibrated via actual testing | Adapts to the scale of battle logs and version feedback data, and complies with FastGPT v4.17.0 task scheduling capabilities |
| Automated validation toggle | Enabled | Numerical configuration errors directly cause gameplay imbalance; pre-checks can intercept abnormal configurations early |
| Failure retry count | 3 times, with a `60 second` interval | Addresses task interruptions caused by temporary server fluctuations; reasonable retries reduce failure rates |
| Abnormal alert threshold | 2 consecutive task failures | Filters single temporary exceptions, and notifies relevant personnel promptly when failures occur consecutively |

## Three common mistakes
- Phenomenon: After a scheduled task runs, the associated knowledge base index status remains unready for an extended period, and no automatic retry is triggered. Cause: No automatic task rescheduling logic is configured after task failure, or the trigger cycle is set too long to allow timely retries.
- Phenomenon: The automated validation step incorrectly blocks valid numerical configurations, causing task termination. Cause: Validation rules do not adapt to the numerical field range for this category, such as not allowing decimal-precision probability configurations.
- Phenomenon: After a server restart, pre-configured scheduled tasks do not automatically resume execution and require manual triggering. Cause: No task persistence storage is configured, so scheduling information is lost after restart.

## How to verify a complete configuration
- View task scheduling logs to confirm the trigger cycle aligns with business update rhythms. Adjust the cycle via the corresponding configuration item if needed.
- Simulate a single temporary exception scenario to confirm the task triggers the automatic retry logic, and verify that retry counts and intervals match preset rules.
- Submit a valid numerical configuration sample to confirm the automated validation step passes normally, with no incorrect blocking.
- Manually trigger a server restart simulation to confirm scheduled tasks automatically resume execution without manual intervention.
