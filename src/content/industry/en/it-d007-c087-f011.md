# Online Fault Troubleshooting and Retrospective for Game Design and Numerical Balance Tuning: Database and Operations

## What Data Looks Like for This Category
The data for this category primarily comes from player behavior data, publicly available competitor materials, battle logs, and version feedback. Daily deliverable documents include gameplay design documents, numerical configuration tables, version requirement lists, and balance test records. Data update frequency is weekly or per version cycle. Most fields include parameters such as damage coefficients, drop probabilities, and growth curve parameters. There are no unified fixed units, so definitions must align with corresponding gameplay rules.

## Constraints Imposed on Database and Operations Workflows
This category has high data update frequency and relies on multi-source input. The database must support mixed storage of structured numerical tables and unstructured design documents. The lack of unified units across multiple fields requires operations teams to configure data validation rules to prevent numerical anomalies caused by unit mismatches. Severe gameplay imbalance consequences require the database to enable transactions to ensure atomicity of data updates. It must also support version snapshot functions to enable quick rollback to the last stable version during a fault. Multi-source data access requires configuring a unified data cleaning pipeline to block dirty data from entering the production database and disrupting subsequent numerical simulations and version validation.

## How to Set Configurations
These configurations are based on FastGPT v4.17.0:
| Configuration Parameter | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://gameDesign:pass@db-host:27017/game_data?authSource=admin&maxPoolSize=250` | Adapts to storage needs for unstructured gameplay design documents and battle logs, and supports flexible field expansion for different gameplay types |
| `PG_URL` | `postgresql://numericalConfiguration:pass@db-host:5432/numerical_db?sslmode=require` | Stores structured numerical configuration tables, ensures transactional consistency for bulk numerical updates, and prevents abnormalities in gameplay rules |
| `DB_MAX_LINK` | `200–300` | Matches concurrent demands for multi-source data writes, numerical queries, and log retrieval, and prevents service interruptions caused by exhausted connections |
| `REDIS_URL` | `redis://:cache-pass@cache-host:6379/0?maxIdle=50` | Caches frequently queried numerical configurations and player behavior statistics, reducing read/write pressure on the primary database |

## Three Common Misconfigurations
- Symptom: After a large-scale database version upgrade, the service fails to start with a database connection failure prompt. Cause: The database directory was migrated directly without synchronizing updates to the `MONGODB_URI` or `PG_URL` configuration parameters, causing the new deployment environment to fail to recognize the original database path.
- Symptom: A `getaddrinfo EAI_AGAIN mongo` error appears after restarting the service. Cause: The database host address in `MONGODB_URI` was not configured correctly, or network policies restrict communication links between the service and the database.
- Symptom: Knowledge base search responses are slow, and the number of query results does not meet expectations. Cause: The `DB_MAX_LINK` parameter was not set appropriately, causing the database connection pool to be exhausted and unable to handle concurrent numerical query and log retrieval requests.

## How to Verify Successful Configuration
- Run the official database connection test script to verify that the addresses, account credentials, and passwords configured for `MONGODB_URI` and `PG_URL` can establish normal connections.
- Check the database connection pool monitoring dashboard to confirm that the current active connection count does not exceed the threshold set by `DB_MAX_LINK`.
- Submit a structured numerical configuration table and an unstructured gameplay design document to verify that the data write and read processes work normally.
- Access the cache service monitoring interface to confirm that the cache service configured via `REDIS_URL` can respond normally, and that high-frequency query data can be cached and read normally.

The values provided are common starting points and should be measured against the reader's own samples.
