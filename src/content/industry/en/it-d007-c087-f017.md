# Online Troubleshooting and Retrospective for Game Design and Balance Design: Deployment and Upgrade

## What does the data for this category look like
The data for this category mainly comes from player behavior data, battle logs, version feedback, and publicly available competitor materials. The update frequency is weekly or per version cycle. Daily output documents include gameplay design documents, numerical tables, version requirement sheets, and balance test records. Numerical tables contain fields such as damage coefficients and growth curve parameters, with units mostly being relative ratios, fixed values, or time intervals. Gameplay design documents include rule descriptions and process nodes.

## What constraints do these characteristics impose on the deployment and upgrade phase
The data sources for this category are scattered and updated frequently. The deployment link must stably support access and storage of multi-source data, and avoid interruptions to numerical calculations caused by connection failures. Frequent version updates require the upgrade process to be compatible with the formats of old version numerical tables and gameplay documents, to reduce version rework costs. Diverse document structures and field units require deployment configurations to adapt to different types of parsing rules. This ensures accurate data reading for numerical simulations and balance tests, while also meeting storage and network adaptation requirements across different environments.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `20–30 connections` | This category frequently reads numerical table and battle log data. A reasonable connection count prevents database connection exhaustion and supports concurrent numerical calculation tasks |
| `MONGODB_URI` | Point to a dedicated replica set address | Used to store version feedback and player behavior data. A dedicated address isolates business traffic from other services and improves data security |
| `PG_URL` | Configure as a database address with a read-only replica | Used to store intermediate results of numerical calculations. Read-only replicas reduce read load and prevent overloading the primary database |
| `REDIS_URL` | `600-second expiration time` | Used to cache temporary balance test data. The expiration time aligns with the weekly update rhythm and prevents excessive cache resource usage |
| `FILE_TOKEN_KEY` | `32-bit random string` | Used to generate authentication tokens for file uploads, ensuring the security of design document uploads |
| `STORAGE_S3_ENDPOINT` | Fill in according to local storage or cloud service provider addresses | Used to store archived files of gameplay design documents and version requirement sheets, adapting to storage requirements across different deployment environments |

## Three Common Misconfigurations
- Symptom: The `docker build` command returns the error `ERROR: failed to solve: archive/tar: unknown file mod`. Cause: File permissions for numerical tables and design documents were not handled correctly during deployment, resulting in unrecognized file modes during the packaging process.
- Symptom: After upgrading to FastGPT v4.17.0, the numerical simulation API returns the error `API request failed: 404 - Resource not found`. Cause: The `FE_DOMAIN` configuration item was not updated during the upgrade, causing a mismatch between frontend and backend routing.
- Symptom: API requests frequently time out, and battle log data cannot be read. Cause: The `DB_MAX_LINK` configuration is too low, causing the database connection pool to be exhausted and unable to handle concurrent numerical calculation requests.

## How to Verify Proper Configuration
- Run the `docker ps` command, confirm that all FastGPT-related containers are in a running state, and check that there are no database connection failure errors in the container logs.
- Access the configured `FE_DOMAIN` address, verify that the frontend page loads the numerical configuration module normally, and there are no resource loading failure prompts.
- Submit a test numerical table to trigger a balance simulation task, confirm that the task runs normally and returns results, with no timeouts or format errors.
- Check the cache service corresponding to `REDIS_URL`, confirm that temporary test data can be written and read normally, and that the expiration time aligns with the update rhythm.

The values provided are common starting points and should be measured against the reader's own samples.
