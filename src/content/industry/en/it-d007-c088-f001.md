# Online Troubleshooting and Retrospective for Game Operation Activity Configuration: HTTP Interfaces and External Systems

## What this category of data looks like
This document is written based on FastGPT v4.17.0. Data for this category primarily comes from operation backends, player segment data, payment statistics data, and activity operation logs. Daily produced documents include activity plans, reward configuration tables, launch checklists, and activity retrospective reports. The data update rhythm is usually weekly or temporarily adjusted before holiday events. Data fields include activity unique identifiers, reward types, distribution quantities, effective time periods, etc. There are no unified mandatory units, and adjustments are made flexibly based on activity type.

## What constraints do these characteristics impose on the HTTP Interfaces and External Systems link
The data characteristics of this category impose multiple constraints on the HTTP interfaces and external systems link. Multi-source data docking requires interfaces to adapt to authentication rules of different external systems. The flexible update rhythm requires interfaces to support dynamic configuration loading, which takes effect without restarting services. The inconsistent document field requirements require interfaces to support flexible parameter passing to adapt to configuration needs of various activities. Since error consequences directly affect operation effects, interfaces must be configured with complete failure retry and exception reporting mechanisms.

## How to set configurations
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| Interface Authentication Configuration | Use the `Authorization` header to carry a Bearer token with a 12-hour validity period | Adapt to authentication requirements of multiple external systems, reduce the risk of token leakage |
| Activity Parameter Passing | Split the `variables` parameter by activity dimension, with no more than 20 parameters passed in a single request | Adapt to flexible activity configuration requirements, simplify calling logic |
| Return Data Format | Use `responseData` that includes three core fields: activity ID, execution status, and error code | Facilitate quick fault location and retrospective of activity execution results |
| Interface Timeout Setting | 600 seconds | Adapt to time consumption requirements for batch activity configuration processing |
| Failure Retry Configuration | Retry 3 times with a 30-second interval | Respond to short-term external system fluctuations, avoid misjudging faults |
| Intranet Deployment Adaptation | Disable public network interface verification, configure a local IP whitelist | Adapt to deployment scenarios without public network access |

## Three common mistakes
- Symptom: External system interface calls fail during intranet deployment, with logs showing connection timeout or service not responding. Cause: Local IP whitelist is not configured, or public network interface verification is not disabled, resulting in interface interception.
- Symptom: After passing activity configuration parameters, the returned result does not match the corresponding reward rules, and the expected reward distribution logic is not triggered. Cause: The `variables` parameter is not split by activity dimension, or the parameter key name does not match the interface requirements.
- Symptom: Interface authentication fails, returning a 401 status code. Cause: The `Authorization` header does not carry a correct Bearer token, or the token has expired.

## How to confirm the configuration is correct
- Call the test interface, check whether the `Authorization` header is correctly carried, and whether the returned `responseData` includes the expected core fields.
- Pass test `variables` parameters, verify whether the returned result matches the passed activity configuration.
- Simulate a scenario where the external system is temporarily unavailable, check whether the interface triggers the retry mechanism without abnormal errors.
- In the intranet deployment environment, call the internal interface to confirm that there is no interception caused by public network access restrictions.
