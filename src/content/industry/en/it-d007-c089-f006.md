# Online Troubleshooting and Retrospective for Vulnerability Scanning Services: Scheduled Tasks and Automation

## What the Data for This Category Looks Like
Core data for vulnerability scanning services comes from vulnerability scanners, enterprise asset inventories, public CVE databases, and patch bulletins. Four standardized documents are produced on a regular basis: scan plans, vulnerability lists, remediation tickets, and rescan reports. Document fields include asset IP addresses, vulnerability CVE IDs, repair statuses, and rescan results. Data updates run on a weekly or monthly cycle. The core workflow includes three time-consuming steps: asset scope confirmation, false positive elimination, and rescan result verification. Typical failure outcomes include high-severity vulnerability exposure and missed patches. This differs from penetration testing services, which focus on manual verification.

## Constraints Imposed on Scheduled Tasks and Automation
Multi-data source dependencies require scheduled tasks to support parallel pulling of scanner results, asset inventories, and CVE database data for associated verification, to avoid data disconnection. Weekly or monthly update frequencies require task scheduling to support custom cycle configuration, to prevent resource waste or data lag. The generation logic for the four core documents must be tied to task nodes, to ensure corresponding documents are automatically output after scanning completes. The time-consuming nature of asset scope confirmation and false positive elimination requires automated workflows to pre-configure asset filtering rules and false positive filtering thresholds, to reduce manual intervention. The risk of high-severity vulnerability exposure requires triggering an alert and retry mechanism after task failure, to ensure the timeliness and accuracy of security data. ## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Task scheduling cycle | Run weekly or monthly, single task duration no more than 120 minutes | Match the weekly/monthly data update frequency, avoid excessive resource occupation |
| Asset pull limit | Top 1000 asset records | Adapt to the conventional scale of enterprise asset inventories, reduce load pressure of single scan |
| False positive filtering configuration | Enable filtering, set threshold to 0.8 | Reduce manual workload in the false positive elimination step, improve scanning efficiency |
| Failure retry strategy | Retry 3 times, retry interval 60 seconds | Respond to temporary network fluctuations or data source interface jitter, ensure task execution stability |
| Rescan trigger condition | Automatically trigger 7 days after high-severity vulnerability is repaired | Match the verification cycle after remediation, ensure effective recheck of high-severity vulnerabilities |
| Task notification configuration | Bind to security operation ticket system and internal notification channels | Match daily operation and maintenance notification habits, synchronize task status in a timely manner |

## Three Common Configuration Mistakes
- Phenomenon: No rescan report is generated after a scheduled task triggers, and vulnerability fields are empty. Cause: The automatic generation node for rescan reports is not configured, and only basic scan task scheduling is completed.
- Phenomenon: Task execution times out, returning status code 504. Cause: Scan batches for large-scale assets are not split, the number of assets scanned in a single run exceeds the system load limit, and task timeout configuration is not adjusted.
- Phenomenon: The task cannot actively push scan results to a specified channel. Cause: Only passive trigger reply logic is configured, and no active push task node is added. This corresponds to the community’s common requirement scenario for active synchronization of scan results.

## How to Verify Correct Configuration
- View the task management interface, and confirm that the scheduling cycle and trigger node configuration match the business update rhythm.
- Run a single test task, and check that the four types of documents (scan plan, vulnerability list, remediation ticket, rescan report) are automatically generated with no missing fields.
- Simulate a scenario where a data source is temporarily unavailable, and confirm that the task retry and alert process operates normally.
- Mark a high-severity vulnerability as repaired, and verify that the preset rescan task is automatically triggered.
