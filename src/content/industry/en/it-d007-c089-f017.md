# Online Troubleshooting and Post-Mortem for Vulnerability Scanning Services: Deployment and Upgrade

## What the Data for This Category Looks Like
Core data for vulnerability scanning services comes from vulnerability scanners, enterprise asset inventories, public CVE databases, and official patch announcements. Daily produced documents include standardized scan plans, vulnerability detail lists, remediation workflow tickets, and re-scan validation reports. Each document contains fields such as asset IP/domain, CVE ID, risk level, repair status, and scan timestamp. Data update frequency follows a weekly or monthly cycle, adjusted synchronously with asset changes and CVE database updates.

## What Constraints These Characteristics Impose on Deployment and Upgrade
Vulnerability scanning service data sources involve multi-system integration. During deployment, multiple data source connection parameters must be configured to ensure connectivity between scanners, asset databases, and CVE databases. Daily document structures are standardized, so field mapping rules must be preset during deployment to avoid mismatches between scan results and ticket fields. Data update frequency is flexible, so upgrades must be compatible with both old and new versions of scan plan formats to prevent historical configuration failures. Asset scope confirmation relies on accurate asset import, so asset inventory format validity must be verified during deployment to avoid scan scope deviations. False positive exclusion and re-scan verification require retaining historical scan data, so upgrades must ensure complete data migration to prevent loss of historical vulnerability records.

## Configuration Settings
This configuration applies to FastGPT v4.17.0 vulnerability scanning service deployments.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 100–200 connections | Adapts to database connection requirements for concurrent scan tasks, avoids connection pool exhaustion |
| `MONGODB_URI` | Sharded cluster connection address with authentication information | Stores massive scan historical data and vulnerability lists, supports high-concurrency read/write operations |
| `PG_URL` | Relational database connection string with independent account and password | Stores structured business data such as scan plans and remediation tickets |
| `REDIS_URL` | Cache instance address with access password | Caches scan task status and temporary asset data, reduces database query pressure |
| `STORAGE_S3_ENDPOINT` | Official endpoint of enterprise-compliant storage services | Stores large files such as scan reports and log attachments, meets data retention requirements |
| `ROOT_KEY` | Randomly generated 32-bit string | Used as the system administrator's highest privilege verification key, ensures post-deployment access security |

## Three Common Misconfigurations
- Symptom: Scan task starts and returns `500 Internal Server Error`, logs show database connection timeout. Cause: `DB_MAX_LINK` parameter is not configured correctly, the connection pool upper limit is too low, causing concurrent tasks to exhaust connections.
- Symptom: Calling the vulnerability scanning tool in the workflow returns no output, database query results are empty. Cause: `PG_URL` or `MONGODB_URI` configuration is incorrect, missing correct database authentication information or network access permissions are restricted.
- Symptom: Re-scan report cannot be generated, upload fails. Cause: The storage service configured in `STORAGE_S3_ENDPOINT` has insufficient permissions to write scan-generated report files.

## How to Verify Successful Configuration
- Run the built-in database connectivity test tool to verify the configuration validity of `DB_MAX_LINK`, `MONGODB_URI`, `PG_URL`, and `REDIS_URL`, confirm that the connection pool has no exhaustion risk.
- Submit a test scan task with a small number of assets, wait for the task to complete, then check if the vulnerability list is generated and whether the fields match the preset document structure.
- Access the frontend access address configured in `FE_DOMAIN`, use `ROOT_KEY` to complete administrator privilege verification, confirm that system access control is working properly.
- Manually upload a test scan log file, confirm that the storage service configured in `STORAGE_S3_ENDPOINT` can normally write and read files.

The values provided are common starting points and should be evaluated against the reader's own samples.
