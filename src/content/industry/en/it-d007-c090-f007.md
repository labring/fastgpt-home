# Online Troubleshooting and Retrospective for Version Releases and Release Notes: Conversation Logging and Auditing

## What data for this category consists of
This category’s data primarily comes from Git repository tags, merged commit records, artifact packages produced by CI/CD pipelines, and associated Issue milestones. Daily maintained documents include officially released Release Notes, timeline-sorted change logs, version tag lists, and pre-release checklists. Data is updated once per official version release. Core fields include version number, change category, associated merge request ID, artifact checksum, release time, and responsible party information.

## Constraints on conversation logging and auditing workflows
Data for this category is generated in batches per version and comes from multiple dispersed sources. The conversation logging and auditing workflow must limit query scope to associated data for a specified version to avoid interference from cross-version information. Change entries require manual classification and sorting. During audits, change descriptions must be matched against actual CI artifact content to confirm consistency between change notes and actual outputs. Feature updates per version require audit logs to be bound to version numbers and associated milestones, enabling traceback of abnormal links for specific versions. The need to aggregate multi-source data requires audit processes to unify Git commits, CI logs, and Issue association information, preventing information silos.

## Configuration settings
These configuration rules apply to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind to session ID range for a specified version | This category’s data is aggregated by version. Limiting scope via `chatId` enables precise matching of conversation logs for the target version |
| `responseChatItemId` | Associate change entries with artifact IDs | Core fields for this category include change association information. This configuration binds logs to specific change content |
| `detail` | Enable full log collection | This category requires verification of change descriptions against actual artifacts. Full `detail` capture covers details such as CI commits and artifact checksums |
| Log retention period | 60 days | This category’s data is updated per version. A 60-day retention window covers at least two full version audit cycles |
| Single query limit | Top 20 entries | Aligns with typical range of change entries per version for this category, preventing query overload |
| Log timeout threshold | 30 seconds | Prevents long-running queries from blocking. Matches typical response times for multi-source data aggregation |

## Three common configuration mistakes
- Symptom: Workflow plugins do not display input and output parameters, and no corresponding error messages appear in logs. Cause: `chatId` is not bound to the current version’s session scope, causing audit logs to not be associated with plugin configuration changes for that version.
- Symptom: Database connection verification information is missing from returned logs. Cause: Full `detail` collection is not enabled, omitting log details for database connectivity checks in CI pipelines.
- Symptom: The page displays `bootstrap-legacy-autofill-overlay.js:6247 Uncaught TypeError` errors, and the copy button is unresponsive. Cause: Session scope is not limited, causing cross-version legacy script logs to interfere with current page log rendering.

## How to verify correct configuration
- Enter a specified version number, query associated change logs, confirm returned results only include commit and artifact information for that version.
- Trigger a version release workflow, check if audit logs include complete CI artifact verification, Git commit records, and Issue association information.
- Review the log retention period configuration, confirm older version logs older than 60 days have been archived or cleaned per rules.
- Simulate a plugin configuration change, check if audit logs are bound to the corresponding `responseChatItemId` and version marker.
