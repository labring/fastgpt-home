# On-site Deployment Implementation: Online Troubleshooting and Retrospective for HTTP Interfaces and External Systems

## What this category of data looks like
This category of data is primarily sourced from customer data center environments, equipment inventories, software packages, and network topologies. Its update cadence follows per order or per phase. Daily produced documents include deployment manuals, installation records, configuration checklists, and on-site sign-in sheets. Core fields include deployment environment version, external interface addresses, identity credentials, and configuration parameter items. On-site implementation personnel collect and organize data at the customer site, and refine it as the deployment process advances. Non-standardized fields vary based on differences in customer environments.

## What constraints these characteristics impose on HTTP interfaces and external systems
Data for this category is collected dispersedly from customer on-site environments. This means HTTP interface and external system configurations cannot use unified templates. Parameters must be adjusted for each customer’s network topology and equipment inventory. Data updates align with deployment phases, so interface configurations must support on-demand modification. Fixed parameters will block subsequent processes. Daily produced configuration checklists must correspond one-to-one with interface configuration items, to help on-site personnel verify details. Customer data center network restrictions may also require configuring parameters such as timeouts and proxies, to adapt to different outbound access rules.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| ---|---|--- |
| `Authorization` | Populate according to the API key format provided by the customer, in the format `Bearer {secret key}` | Complies with external system identity verification standards, avoids authentication failures, and adapts to FastGPT v4.17.0 interface call specifications |
| Interface request timeout | 60-120 seconds | Adapts to FastGPT v4.17.0 default timeout logic, balances request success rate and troubleshooting efficiency |
| `variables` field passing | Pass business-related parameters as needed | Enables parameter linkage between external systems and FastGPT, simplifies context localization during faults |
| `responseData` field extraction | Only retain core return content | Simplifies log analysis, quickly locates external system return exceptions |
| Interface retry count | 2-3 times | Responds to temporary network jitters, reduces on-site return troubleshooting needs |
| Proxy server configuration | Fill in according to customer data center network rules | Adapts to outbound access restrictions restricted by firewalls |

## Three common configuration errors
- The symptom is an interface returning a 401 Unauthorized status code. The cause is that the `Authorization` header format does not match external system requirements, such as missing the standard prefix or incorrect secret key entry.
- The symptom is a timeout after a long period of no request response. The cause is failure to adjust the timeout setting based on the customer’s on-site network topology, using a fixed short timeout value.
- The symptom is an empty `responseData` field in the return result. The cause is incorrect response parsing rule configuration, which fails to extract valid content from the external system.

## How to confirm configurations are properly set
- View FastGPT interface call logs, confirm the `Authorization` header is correctly carried and matches external system format requirements.
- Initiate a test request, check if the return result includes valid content for the `responseData` field.
- Compare the on-site configuration checklist with actual deployed interface parameters, confirm all configuration items match documented records.
- Simulate customer data center network restrictions, verify proxy configuration takes effect and requests complete normally.
