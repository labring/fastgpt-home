# Online Troubleshooting and Retrospective for On-Site Deployment Implementation: Deployment and Upgrade

## What this category of data looks like
Data for this category primarily comes from customer computer room environments, device lists, software packages, and network topologies. Daily retained documents include deployment manuals, installation records, configuration lists, and on-site check-in sheets. Data is updated once per order or per stage. Typical involved parties are on-site implementation engineers, system engineers, and customer IT staff. Core work takes the most time during environment checks, software installation and configuration, and on-site problem troubleshooting. Abnormal occurrences may lead to system unavailability, project delays, or additional return site costs. Unlike project implementation plan management categories, all work in this category is completed in the customer's on-site environment for installation and configuration.

## What constraints these characteristics impose on the Deployment and Upgrade link
The data characteristics of this category directly restrict the execution logic of deployment and upgrade workflows. Data comes from the exclusive on-site environment of the customer. Pre-deployment checks must be conducted one by one for the customer's computer room environment, device list, and network topology. General configuration templates cannot be directly reused. Daily retained deployment manuals, installation records, and configuration lists require every operation step to leave a trace. During upgrades, parameters must be adjusted against historical configurations to avoid configuration deviations. The order-by-order data update rhythm means each on-site task must be re-adapted to the customer's environment. Pre-environment check and software installation and configuration links account for a high proportion of total time. Pre-checks must be completed first to reduce later rework risk. Failure handling plans must be prepared in advance to address potential system unavailability issues.

## How to set the configurations
This configuration guide applies to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 100–300 connections | Adapts to the database concurrency carrying capacity of most customer computer rooms, avoids service interruptions caused by insufficient connections |
| `MONGODB_URI` | Assemble authentication strings using the intranet address of the MongoDB instance in the customer's computer room | Using intranet addresses reduces public network transmission latency and improves data access security |
| `REDIS_URL` | redis://:custom password@intranet IP:6379/0 | Uses dedicated database indexes and intranet access paths to avoid conflicts with Redis instances from other services |
| `STORAGE_S3_ENDPOINT` | Configure using the intranet endpoint of the customer's local storage cluster | Adapts to the customer's on-site storage environment, reduces cross-public network transmission costs and latency |
| `FE_DOMAIN` | Customer-specified frontend access domain name | Matches the service entry exposed externally by the customer, ensures users can normally access the deployed system |
| `ROOT_KEY` | 32-bit random string determined through actual testing | Ensures access permission security for the system backend, avoids malicious exploitation of default keys |

## Three common mistakes
- Symptom: Code execution nodes throw connection timeout errors during runtime, return status code 504. Cause: `STORAGE_S3_ENDPOINT` is not configured to the customer's intranet storage endpoint. Network restrictions cause timeout when accessing storage resources over the public network.
- Symptom: Service startup prompts database connection failure. Logs show `MONGODB_URI` format error. Cause: The connection string is not assembled using the actual address of the database in the customer's computer room, or the authentication password field is omitted.
- Symptom: AI agent interface calls return no response, with empty results. Cause: Authentication parameters for the proxy service are not correctly configured, leading to permission verification failure and inability to normally call AI capabilities.

## How to confirm the configuration is successful
- Log in to the database management tool, run a connection test. Confirm that the customer's computer room database instance can be accessed normally using the configured `MONGODB_URI` or `PG_URL`.
- Access the configured `FE_DOMAIN`. Check if the frontend page loads normally, and if static resource paths match the configured domain name.
- Run a code execution node test task. Confirm that storage resources and AI proxy services can be called normally, with no timeout or permission errors.
- View service runtime logs. Confirm that the configured `DB_MAX_LINK` value has taken effect, and database connection counts do not exceed the set threshold.

The values provided are common starting points and should be measured against the reader's own samples.
