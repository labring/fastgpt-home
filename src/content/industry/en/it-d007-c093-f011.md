# Online Troubleshooting and Retrospective for User Growth and Retention Operations: Database and Operations

## What the Data for This Category Looks Like

Daily documents for this category include growth experiment plans, user segmentation tables, outreach copy, and retention analysis reports. Data typically originates from user behavior logs, push systems, experiment platforms, and CRM systems. Most updates occur on a daily or weekly basis. User segmentation tables include fields such as user ID, segmentation tags, and outreach trigger conditions. Retention analysis reports include statistical dimensions such as retention rates and conversion paths. User behavior logs record details like access time, operation type, and device identifiers. The core business process centers on the in-app user lifecycle, involving association and analysis of multi-source data.

## Constraints Imposed on Database and Operations Workflows

Multi-source data sources create schema inconsistency issues, requiring a unified storage structure to support imports of varying data formats. Daily or weekly batch tasks generate peak loads, so database connection counts must be limited to prevent service interruptions. Core steps such as user segmentation and experiment result attribution involve complex join queries, so indexes and caches must be properly configured to optimize response speeds. Errors in in-app user lifecycle operations directly impact retention and budget, so complete backup and fault recovery mechanisms are required to ensure data security and service availability.

## How to Configure Settings

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://fastgpt:xxxx@db-host:27017/fastgpt_growth?authSource=admin` | Stores user segmentation data and outreach behavior logs. Requires account password and authentication source configuration to ensure data security, and adapts to the vector storage requirements of FastGPT v4.17.0. |
| `PG_URL` | `postgresql://fastgpt:xxxx@db-host:5432/fastgpt_growth?sslmode=require` | Stores structured data for growth experiment plans and retention analysis reports. Uses SSL encrypted transmission to prevent data leaks. |
| `DB_MAX_LINK` | `200–300` | Adapts to peak connection demands of daily batch tasks, avoiding service interruptions caused by exhausted connections. |
| `REDIS_URL` | `redis://:xxxx@cache-host:6379/0` | Caches intermediate calculation results for user segmentation, reducing repeated query overhead on relational databases. |
| Batch Task Concurrency | Calibrated based on actual testing | Controls the concurrency of outreach copy push tasks to avoid exceeding database connection limits. |

## Three Common Misconfigurations

- Phenomenon: `connection refused` error is returned when executing user segmentation queries. Cause: The `DB_MAX_LINK` parameter is not correctly configured, leading to exhausted database connection pools and inability to create new connections.
- Phenomenon: Batch outreach tasks time out, with `query timed out` displayed in logs. Cause: No indexes are created for join fields in user segmentation tables, and unoptimized complex queries lead to response timeouts.
- Phenomenon: Vector storage queries return empty results. Cause: Using the MongoDB 5.0.18 version with security vulnerabilities, and failing to update to a secure version causes abnormal data writes.

## How to Verify Proper Configuration

- Database connection test commands are executed to verify that `MONGODB_URI`, `PG_URL`, and `REDIS_URL` configurations can establish normal connections. Connection parameters are adjusted based on business peak loads.
- A single user segmentation batch task is run, database connection count changes are observed, and it is confirmed that connection counts do not exceed the `DB_MAX_LINK` configured value.
- Execution logs for outreach copy push tasks are reviewed, confirming that batch concurrency meets business expectations and does not exceed database carrying capacity.
- Generation logs for retention analysis reports are reviewed, confirming that structured data has been successfully written to the PostgreSQL database and vector data has been stored in MongoDB.
