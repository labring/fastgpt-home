# Online Troubleshooting and Retrospective for User Growth and Retention Operations: Deployment and Upgrade

## What the data for this use case looks like
Core data for this use case comes from user behavior logs, push systems, experiment platforms, and CRM systems. It supports user segmentation, outreach strategy formulation, and experiment effect analysis.
Documents produced regularly include growth experiment plans, user segmentation tables, outreach copy, and retention analysis reports.
Data update frequency is typically daily or weekly. Fields include user ID, outreach time, experiment group, retention days, outreach channel, and more. Units are mostly times, days, and user counts.
Data structure adjusts with experiment iterations and user segmentation logic, and must support multi-source data association query requirements.

## What constraints these characteristics impose on deployment and upgrade
Multi-source data access requirements mean the deployment phase must configure connection parameters for multiple external systems, and adapt to different interface formats and permission rules.
Daily or weekly batch data processing requires adjusting concurrent connection counts and caching strategies to avoid resource exhaustion during data synchronization.
Diverse document types and dynamically adjusted fields require storage configurations that support flexible Schema adaptation, while ensuring data write consistency.
Additionally, outages directly impact user retention and channel budgets. After deployment or upgrade, the validation phase must be completed quickly to reduce business impact duration.

## How to configure settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://[username]:[password]@host:port/growth_operation?authSource=admin` | Persistently stores core business data such as user segmentation tables and retention analysis reports |
| `REDIS_URL` | `redis://:[custom_password]@redis-host:6379/0` | Caches temporary calculation results of user behavior logs and experiment group tags to reduce database query pressure |
| `DB_MAX_LINK` | `20–50 connections` | Adapts to concurrent connection requirements for daily batch data synchronization, prevents connection pool exhaustion |
| `FE_DOMAIN` | `https://growth-operation-platform.com` | Configures the frontend access domain name for static resource loading of outreach copy and interface request forwarding |
| `FILE_TOKEN_KEY` | 32-character random string | Encrypts and stores attachments for outreach copy and exported files of user behavior logs to ensure data security |
| `ROOT_KEY` | Generated in accordance with FastGPT v4.17.0 official guidelines | Manages system permission verification and global access control for model configuration |

## Three common configuration mistakes
- The symptom is that the Docker container has an up status, but the frontend page on port 3000 cannot be logged into, and logs indicate a MongoDB connection failure. Manually connecting to MongoDB with the account and password also fails. The cause is that `MONGODB_URI` does not correctly specify the authentication database or has incorrect account password input.
- The symptom is that after starting the local development environment with pnpm, the oneAPI management interface cannot be accessed. The cause is that `FE_DOMAIN` is not correctly configured or the interface forwarding rules for the backend service are not associated, causing frontend requests to fail to match the backend address.
- The symptom is that after adding a model in FastGPT v4.17.0, a configuration error occurs, index model binding cannot be completed, or API Key configuration does not take effect. The cause is that `FILE_TOKEN_KEY` or `ROOT_KEY` is not correctly set, or the storage endpoint configuration does not match the cloud service provider's storage rules, causing model configuration files or permission verification to fail.

## How to confirm the configuration is correct
- Container runtime logs or local development terminal output are checked for no error messages about database connection failures or permission verification failures.
- The frontend address corresponding to the configured `FE_DOMAIN` is accessed, and after administrator login is completed, core modules such as user segmentation management and experiment configuration can be accessed normally.
- A daily data synchronization task is manually triggered, and user behavior logs and CRM data are confirmed to be successfully written to the specified storage, with no data loss or format errors.
- The environment variable configuration file is checked, and required parameters such as `DB_MAX_LINK` and `MONGODB_URI` are confirmed to be filled in and meet format requirements.

The values given are common starting points and should be measured against the reader's own samples.
