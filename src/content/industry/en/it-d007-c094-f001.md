# Online Troubleshooting and Retrospective for User Acceptance Testing Support: HTTP Interfaces and External Systems

## What data for this category includes
Data sources include requirement specification documents, test environment configurations, customer-provided business samples, and defect management systems.
Daily produced documents include UAT test cases, acceptance issue tickets, acceptance reports, and signed confirmation forms.
Data is updated once per project phase or version iteration.
Data fields include test case steps, expected results, issue reproduction paths, acceptance conclusions, and other relevant items.
Fields have no unified fixed units, and are adjusted based on the customer’s business scenario.

## Constraints for HTTP interfaces and external systems workflows
The data sources for this category are scattered and adjusted per customer scenarios. HTTP interfaces must support pulling data from multiple sources. This includes syncing acceptance issue tickets from defect systems, and retrieving interface response data from test environments.
Data updates occur once per phase or version. Interfaces must support triggering data sync per phase, to avoid high-frequency calls disrupting test processes.
Daily documents include structured content such as UAT test cases. Interfaces must support passing test case parameters in `variables` format, and support custom field mapping to adapt to different customers’ acceptance document structures.
Additionally, data fields have no fixed format. Interfaces must have flexible parsing capabilities, and cannot rely on unified field structures for data processing.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${token}, token must include model invocation and defect system access permissions` | Must invoke large models to analyze acceptance issues and pull defect system data, so permissions cover both types of operations |
| `variables` | Pass UAT test case steps and expected results, total characters per pass must not exceed 800–1200 | Structured content of UAT test cases must be passed via variables. Controlling length ensures interface processing stability |
| `responseData` | Extract defect status, issue reproduction path, and acceptance conclusion fields | Only retain core acceptance-related data to reduce invalid data transmission and processing overhead |
| Interface timeout setting | 600 seconds | Troubleshooting for this category requires waiting for full test environment responses. Too short a timeout will interrupt unfinished tasks |
| Field mapping rules | Adapt to field names from customer acceptance documents | Daily document structures are adjusted based on customer scenarios, so custom field mapping must be supported |

## Three common misconfigurations
- Symptom: Interface returns 403 status code, with a prompt that the token lacks permission to use the model. Cause: The token’s permissions only include a single type of access, and do not simultaneously configure model invocation and defect system access permissions.
- Symptom: Test case parameters in `variables` format are not parsed correctly, leading to missing test case steps in troubleshooting results. Cause: FastGPT v4.17.0 or later is not used. Older versions have compatibility issues with {{}} variables.
- Symptom: Configured models cannot be selected in the system. Cause: Model invocation permissions are not configured in the `Authorization` token, or the model is not correctly bound to the corresponding token.

## How to confirm configurations are properly set
- Call configured HTTP interfaces. Verify the `Authorization` header correctly carries the token by using an interface debugging tool to view request headers.
- Pass test `variables` parameters. Check if the interface correctly receives and parses test case-related content by viewing incoming variable values via logs.
- Check if the `responseData` return result includes the core fields specified in the configuration. Compare the configured mapping rules with the returned data structure for validation.
- Wait for the interface to complete the call. Confirm no timeout error is triggered, and adjust the timeout setting based on the test environment’s response speed if needed.

The values provided are common starting points, and should be evaluated against the reader’s own samples.
