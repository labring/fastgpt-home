# Online Fault Troubleshooting and Retrospective for Monitoring Alert Configuration: Database and Operations

## What Data for This Category Looks Like
Data sources for this category include Prometheus, Zabbix, cloud monitoring, application logs, and CMDB systems. Update frequency is either daily or after each alert rule change. Daily maintenance documents include a list of monitoring metrics, alert rules, on-duty manuals, and alert change records. Fields include metric names, threshold ranges, trigger conditions, notification links, and associated data sources. Common units include seconds, request counts, connection counts, and other operations-focused units.

## Constraints on Database and Operations Workflows
Multi-data source collection requires database connection configurations compatible with different instance types. Connections are established using parameters such as `PG_URL` and `MONGODB_URI`. High-frequency updated alert rules and change records require stable database storage to prevent data loss or synchronization delays. Metric threshold settings must match the actual carrying capacity of the database. For example, the connection pool size must align with the `DB_MAX_LINK` parameter to avoid alert noise or missed faults caused by unreasonable thresholds. Notification link verification relies on the cache service configured via `REDIS_URL` to ensure alert messages are forwarded correctly.

## How to Configure Settings
This document applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Database connection string | Fill in the complete connection information for the corresponding database instance, including username, password, and port | Adapt to the data source connection requirements of Prometheus or Zabbix |
| Maximum connection pool limit | 800–1200 | Match the concurrent carrying capacity of the database to avoid connection exhaustion |
| Alert notification cache address | Fill in the connection parameters for the Redis instance | Used to temporarily store alert notification queues and reduce pressure on the primary database |
| Multi-line query execution switch | Enabled | Support running multiple database statements at the same time, adapt to batch queries for complex monitoring metrics |
| Alert change record synchronization frequency | Synchronize once every 24 hours | Match the update frequency of alert change records to ensure data consistency |
| Test alert trigger threshold | Trigger when database connection failures exceed 10 times per minute | Aligns with threshold settings in daily monitoring metric lists to avoid false positives |

## Three Common Configuration Mistakes
- A syntax error occurs when executing multi-line database queries, with error messages containing "you have an error in your SQL syntax". This happens when the multi-line query execution switch is not enabled, so the database connection plugin only allows single statements to run.
- After backup and recovery, the knowledge base and agents do not display existing content. This occurs when the alert configuration backup data synchronization link is not associated with the database backup node storage path, so the correct dataset is not loaded during recovery.
- Alert notifications are not sent to the on-duty team as expected. This happens when the alert notification cache address is configured incorrectly, so the alert notification queue cannot be cached and forwarded normally.

## How to Verify Configuration Success
- Log in to the database configuration page in the FastGPT backend, check the connection status of the database connection string, and confirm that the connection is shown as normal.
- Manually trigger a test alert to verify that it is sent to the specified target via the configured notification channel.
- View the alert change record page to confirm that configuration changes have been synchronized to the database storage.
- Run a simulated multi-line database query to confirm that the returned results match expectations.
