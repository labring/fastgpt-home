# Online Troubleshooting and Retrospective for Community Report Handling: Conversation Logs and Auditing

## What the Data for This Category Looks Like
Typical community report handling data originates from report systems, content details, user historical records, and review rules. Update frequency is daily or real-time. Daily documents include report tickets, processing records, appeal forms, and user notification templates. Core fields include unique report identifier, involved content ID, processor account, processing time, and violation type. There is no fixed uniform per-record data volume; it varies with the complexity of the involved content.

## Constraints on the Conversation Logs and Auditing Link
Since data is aggregated per individual report ticket, conversation logs must be bound to a unique report identifier to enable end-to-end tracing. Real-time updated report data requires the auditing link to support immediate pulling and storage. Mixed collection of multiple document types requires clear field filtering rules to avoid irrelevant data interfering with auditing. The business logic of per-ticket processing requires log retention to cover the full process from report submission to processing completion, ensuring that issues can be quickly located when they occur.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind to report ticket ID | Match the full conversation chain of a single report, enabling single-ticket tracing of the processing workflow |
| `responseChatItemId` | Associate with review node ID | Locate the specific conversation segment where violation evidence is extracted, accurately linking to processing basis |
| `detail` | Enable full core field collection | Cover data required for auditing such as report content, processing opinions, and appeal information |
| Single log pull duration | 600 seconds | Adapt to the real-time update rhythm of report data pulling, avoiding timeout truncation of critical information |
| Log storage retention period | 30 days | Match the regular auditing tracing needs of community operations, balancing storage costs and compliance requirements |
| Context association range | Previous 5 historical conversations | Focus on historical interactions related to the current report, reducing interference from irrelevant data |

## Three Common Misconfigurations
- Symptom: After configuring a text content extraction node in the workflow and enabling chat record collection, multi-turn conversations fail to trigger normally, with no corresponding log output. Cause: The `chatId` parameter is not bound to the report ticket ID, so logs fail to associate with the current processing chain and valid audit records cannot be generated.
- Symptom: When the code running node input includes historical record fields, verification fails and the configuration cannot be saved. Cause: The collection scope of the `detail` parameter is not configured correctly, so fields with sensitive or invalid formats are included in the verification logic and trigger interception.
- Symptom: The specified service port cannot be accessed, and only partial startup information appears in logs. Cause: Failing to set a reasonable single log pull duration causes critical startup logs such as port binding and service initialization to be truncated due to timeout, making connection issues impossible to troubleshoot.

## How to Confirm the Configuration Is Correct
- Enter a test report ticket ID, retrieve conversation logs bound to `chatId`, and confirm that records for the full processing workflow can be pulled.
- Trigger a simulated report processing workflow, check that audit node logs associated with `responseChatItemId` fully display key operations.
- View the log storage directory, confirm that the `detail` field includes core audit data such as report content, processing opinions, and appeal information.
- Simulate input of a configuration containing invalid fields, verify that the verification rule can normally intercept incorrect configurations and ensure the auditing logic takes effect.
- Confirm that the current FastGPT version is v4.17.0, which meets compatibility requirements for all configuration items.
