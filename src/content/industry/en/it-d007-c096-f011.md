# Online Troubleshooting and Retrospective for Community Report Handling: Database and Operations

## What the data for this category looks like
The data for this category primarily comes from user reports submitted via the reporting system, details of reported community content, historical behavior records of involved users, and preset review rules. Daily retained documents include report tickets, processing progress records, user appeal forms, and standardized notification templates. Data updates are mostly real-time, with some archived tickets synced in daily batches. Each data entry contains fields such as unique ticket identifier, reported content snippet, report type, involved user account, disposal status, and number of appeals.

## What constraints do these characteristics impose on database and operations workflows
The data characteristics of this category impose multiple constraints on database and operations workflows. Real-time submission of individual report tickets requires the database to support high-concurrency writes and low-latency queries, to ensure the disposal process runs without lag. Multi-source data correlation needs—associating reported content, user historical records, and review rules—require the database to have flexible unstructured storage capabilities. Daily archived batch data sync requirements demand that operations workflows configure scheduled backup and cold storage migration policies. Each data entry contains sensitive content snippets, so additional data desensitization and fine-grained access permissions must be configured to prevent unauthorized data leaks. Multiple iterative updates to appeal forms require the database to support incremental updates or version tracking mechanisms.

## How to configure the settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://fastgpt:securepass@db-host:27017/fastgpt_reports?retryWrites=true` | Adapts to the unstructured storage needs of report tickets, enables retry writes to ensure tickets are not lost |
| `DB_MAX_LINK` | `200–300` | Matches high-concurrency ticket submission and query scenarios, prevents service interruptions caused by exhausted connections |
| `REDIS_URL` | `redis://:redispass@redis-host:6379/0?maxmemory-policy=allkeys-lru` | Caches frequently accessed review rules and user historical records, reduces query pressure on the primary database |
| `PG_URL` | `postgresql://fastgpt:pgpass@pg-host:5432/fastgpt_archive` | Stores daily archived historical tickets and appeal records, supports structured statistical queries |
| Database backup cycle | Daily full backup + real-time incremental backup, retained for 7 days | Matches the dual rhythm of daily archiving and real-time data updates, ensures rapid data recovery after a fault |

## Three Common Misconfigurations
- Phenomenon: A `Connection refused` or `Authentication failed` error is returned when the workflow calls the database, and report ticket data cannot be loaded. Cause: The authentication parameters for `MONGODB_URI` are not configured correctly, or the outbound access permissions for the database instance are not enabled.
- Phenomenon: Insufficient number of results are returned when querying archived tickets. Cause: Daily batch sync tasks are not configured, resulting in some historical tickets not being migrated to the archived database.
- Phenomenon: Updated appeal forms are not synced to the database. Cause: The connection pool upper limit for `DB_MAX_LINK` is not set appropriately, leading to exhausted connections that cannot write new appeal records.

## How to Confirm Configuration is Successful
- Run the database connectivity test tool in the FastGPT v4.17.0 system settings to verify the authentication and connection status of `MONGODB_URI` and `PG_URL`.
- Submit a test report ticket, confirm that the ticket data can be properly written to the database and full information can be queried in the backend management interface.
- Manually trigger a scheduled archiving task, check whether corresponding batches of historical ticket records are generated in the archived database.
- Simulate high-concurrency submission of multiple report tickets, observe system logs to confirm that no database connection exhaustion error messages appear.
