# Troubleshooting and Retrospective of Online Failures for Defect Management and Regression Testing: Scheduled Tasks and Automation

## What the data for this category looks like
Core data for this category comes from defect management systems, test reports, code commit records, and user feedback. Four types of documents are maintained daily: defect tickets, regression checklists, repair verification records, and defect statistical reports. Data updates follow a daily or per-version release cycle. Core fields include defect ID, priority, reproduction steps, verification status, and associated code commit records. The basic statistical units are individual defects, single regression tasks, and version cycles.

## What constraints these characteristics impose on scheduled tasks and automation workflows
Data sources are scattered, and update rhythms fluctuate with version releases or routine inspections. Scheduled tasks must support both daily bulk inspections and full validation within version cycles. Daily documents include defect tickets and regression checklists with multiple associated fields, so automated workflows must support cross-source data pulling from defect management systems and code commit records. The defect reproduction and regression verification steps account for a high proportion of total time spent, so automated tasks must cover repetitive verification actions to free up labor. There is a risk of high-priority defects being missed, so scheduled tasks must include priority filtering and exception alert triggering logic.

## Configuration settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Scheduled task trigger cycle | Daily inspection + full validation after each version release | Adapts to the daily and per-version update characteristics of data for this category |
| Defect priority filtering threshold | Top 3 high-priority defects | Focuses on high-priority defects to avoid business risks from missed issues |
| Regression verification concurrent task count | 2-4 concurrent tasks | Adapts to test environment resource limits to avoid resource overload |
| Regression verification timeout threshold | 30 minutes | Matches the typical time range for defect reproduction |
| Exception alert trigger conditions | Defect reproduction failure, regression verification timeout | Covers the most time-consuming defect reproduction and regression verification steps for this category |
| Data pull scope | Defect tickets and test reports associated with the current day or current version | Matches the data sources and update rhythms of this category |

## Three common configuration mistakes
- Symptom: Only partial defect tickets are pulled after a scheduled task triggers, and some fields are empty. Cause: Filter rules matching the data pull scope for this category are not configured, and only documents from the default scope are pulled.
- Symptom: Dialog boxes in workflows cannot trigger questions automatically, only manual triggering is supported. Cause: Trigger events tied to defect ticket status changes are not bound, and only manual trigger logic is configured.
- Symptom: Video memory is not released after knowledge base retrieval, causing subsequent task triggers to time out. Cause: Rules to automatically release idle model video memory after retrieval are not configured, and resource occupancy is not cleaned up in a timely manner.

## How to confirm correct configuration
- Review scheduled task run logs to confirm that the trigger cycle matches the configured trigger rules.
- Manually trigger a regression verification task to verify that the pulled document scope matches the configured data pull scope.
- Submit a test defect marked as high-priority to verify that alert notifications are triggered according to the configured priority threshold.
- Perform a knowledge base retrieval operation to confirm that idle model video memory is released according to the configured rules.
