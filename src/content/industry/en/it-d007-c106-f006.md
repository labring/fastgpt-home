# Online Troubleshooting and Retrospective for Speech Annotation and Transcription: Scheduled Tasks and Automation

## What the Data for This Category Looks Like
This category’s data comes primarily from uploaded audio files, annotation platform interaction logs, industry-specific term lists, and manual spot-check samples. Daily documents include transcription specifications, audio batch manifests, quality inspection result reports, and speaker annotation comparison tables. Data updates follow a daily or per-batch cycle. Each processed audio file generates structured transcription text, annotation logs, and quality inspection results. Unlike text annotation projects, speech annotation and transcription first convert audio to structured text before proceeding with subsequent annotation and quality inspection work.

## What Constraints These Characteristics Impose on Scheduled Tasks and Automation
This category has scattered data sources, and audio files must be linked to annotation records. Scheduled tasks must support multi-source data pulling and association verification. Data updates follow a daily or per-batch cycle, so scheduled task trigger cycles must match this rhythm to avoid reprocessing archived audio data. Core time-consuming steps such as noise segment judgment, speaker differentiation, and term proofreading have high computing resource requirements. Automated tasks must be configured with a breakpoint resume mechanism to prevent full rework caused by a single task timeout interruption. Transcription results must correspond one-to-one with the original audio and annotation tables, so tasks must retain complete associated fields to ensure traceability for subsequent quality inspection and retrospective work. Consequences of errors include recognition training bias, transcription rework, and delivery delays. Tasks must be configured with failure retry and alert mechanisms to reduce business impact from anomalies.

## How to Set Configurations
These configuration items apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| Task trigger cycle | Per batch completion time + 1 hour, or 2:00 AM daily | Matches the daily/per-batch data update rhythm, avoids reprocessing archived audio data |
| Maximum single task processing duration | 1200 seconds | Covers the average processing duration of core time-consuming steps, prevents tasks from being forcibly terminated |
| Number of failure retries | 3 | Addresses temporary resource call failures, reduces the need for manual intervention |
| Failure alert trigger threshold | 2 consecutive task failures | Notifies operations staff in a timely manner to troubleshoot anomalies |
| Breakpoint resume switch | Enabled | Adapts to long-duration speech transcription and annotation steps, avoids full re-runs after a single interruption |
| Multi-tool parallel trigger switch | Enabled as needed | Supports simultaneous calls to transcription, annotation, and quality inspection tools, improves task execution efficiency |

## Three Common Mistakes
- Phenomenon: The task status remains "pending" for an extended period, but the system task manager shows the process is running. Cause: Core time-consuming steps occupy a large amount of computing resources, causing task progress to not be synchronized to the status recording interface in a timely manner.
- Phenomenon: Scheduled transcription tasks cannot call multiple tools simultaneously to complete transcription and annotation. Cause: The multi-tool parallel trigger switch is not enabled in the task configuration, so only single-tool sequential calls are supported.
- Phenomenon: Transcription tasks cannot select a specified text understanding model, only displaying the default option. Cause: The model has not been batch imported and associated in the system configuration, so the task-available model list has not been updated.

## How to Confirm the Configuration Is Complete
- A test task is triggered manually, and the specified audio batch and term list files are confirmed to be pulled after the task starts
- Task logs are reviewed, and the failure retry mechanism is confirmed to trigger normally under simulated temporary errors
- Alert configurations are checked, and 2 consecutive task failures are simulated to confirm that alert notifications are pushed normally
- A running test task is interrupted, and the breakpoint resume function is confirmed to restore task progress

The values provided are common starting points and should be measured against the reader's own samples.
