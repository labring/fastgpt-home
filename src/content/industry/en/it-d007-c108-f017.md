# Online Troubleshooting and Retrospective for Warranty Defect Response: Deployment and Upgrade

## What this category's data looks like
Data for this category typically originates from customer-submitted warranty work orders, system operation logs, warranty clauses in project contracts, and version update records. Daily circulating documents include warranty work orders, defect confirmation sheets, repair records, and customer confirmation sheets. Core fields include work order number, defect type, associated version, repair status, and customer confirmation result. Data is updated daily or triggered per individual order. A clear phase division exists for the lifecycle of each data entry, spanning from defect reporting to closed-loop confirmation. This content is organized based on the deployment specifications for FastGPT v4.17.0.

## What constraints these characteristics impose on deployment and upgrade
Since data sources include customer work orders and system logs, deployment requires configuring relevant parameters for connecting to external log collection tools to ensure fault information can be synchronized to the system in real time. The per-order data update feature requires deployed services to have high concurrency processing capabilities to avoid blocking during order volume peaks. The standardization of document fields requires configuring corresponding data mapping rules during deployment to ensure information from different sources can be correctly entered into the system. Additionally, the core time-consuming link of this category involves responsibility boundary judgment, so clear work order routing paths must be configured during deployment to ensure information can be quickly transmitted to the corresponding responsible party. Furthermore, errors in this category directly relate to warranty disputes, so redundant storage and computing resources must be configured during deployment to reduce single point of failure risks.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–150 connections` | Matches the peak connection demand for daily processed work orders in this category, prevents database connection overflow |
| `MONGODB_URI` | Cluster address with read-write separation | Stores version records and repair logs, supports high-concurrency read and write operations |
| `REDIS_URL` | `600 second cache expiration` | Caches temporary defect confirmation sheets and customer confirmation information, reduces database query pressure |
| `STORAGE_S3_ENDPOINT` | Regionally nearest storage node | Quickly retrieves attachments from customer confirmation sheets, improves document loading speed during fault troubleshooting |
| `FILE_TOKEN_KEY` | Randomly generated 32-bit string | Encrypts file upload requests, prevents unauthorized access to defect images submitted by customers |
| `FE_DOMAIN` | Exposed official access address | Ensures the front-end interface loads normally, supports engineers accessing the system via a unified entry |

## Three common deployment mistakes
- Symptom: Logs show `ocr error` after deployment. Cause: Associated parameters between `FILE_TOKEN_KEY` and third-party OCR services are not correctly configured, preventing recognition of image-based defects.
- Symptom: No image understanding model option appears when creating a new knowledge base. Cause: Environment variable switches for the corresponding plugin were not enabled during deployment, so the model was not loaded into the system.
- Symptom: New deployment environment prompts database connection failure. Cause: Valid `MONGODB_URI` address was not correctly filled, so the system cannot connect to the core storage.

## How to verify configurations are correct
- Access the configured `FE_DOMAIN` address, confirm the front-end interface loads normally with no resource loading failure prompts.
- Submit a test warranty work order, check if the system generates a corresponding repair record entry with complete and accurate data fields.
- Upload a test image to the knowledge base, confirm the image understanding function operates normally with no error prompts.
- Check the cache monitoring logs for `REDIS_URL`, confirm the temporary data expiration time matches the configured value.
