# Online Troubleshooting and Retrospective for Configuration Management and CMDB Maintenance: Scheduled Tasks and Automation

## What this category of data looks like
This category of data originates from CMDB, cloud resource inventories, auto-discovery tools, and procurement ledgers. Four types of documents are routinely produced: configuration item lists, service component relationship topologies, change records, and asset inventory sheets. Data is updated daily or weekly. Core fields include asset unique identifiers, service dependency relationships, change timestamps, and inventory status. Only objective association information between assets and configurations is recorded, with no additional custom statistical values.

## How these data characteristics impose constraints on scheduled tasks and automation
The data characteristics of this category impose clear constraints on scheduled tasks and automation workflows. Decentralized multi-source data requires tasks to support cross-system pulling logic, to avoid overloading system resources with single large pulls. The differentiated update frequencies of daily and weekly updates require splitting scheduled tasks, to avoid high-frequency pulling of low-update-frequency data such as procurement ledgers. The strong association between configuration items and service dependencies requires automated updates to simultaneously verify association relationships, to prevent topology breaks. The fixed document structure requires task output formats to align with existing operations and maintenance documents, to reduce subsequent manual adaptation costs.

## How to Configure
The following configuration items are compatible with the FastGPT v4.17.0 automated task module.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Cross-source data pull interval | 300–900 seconds | Aligns with the average update cycle of multi-source data, avoids frequent requests that consume system resources |
| Task scheduling cycle | Daily/Weekly | Matches the update frequency of corresponding data sources, reduces invalid pull overhead |
| Association relationship verification threshold | Top 3 core dependency records | Ensures the dependency links of core services are complete, avoids missing critical associations |
| Exception alert trigger condition | 2 consecutive pull failures | Notifies operations and maintenance personnel in a timely manner to resolve data pull failures |
| Task output format | Aligned with existing CMDB documents | Reduces manual conversion costs, adapts to usage habits of daily operations and maintenance documents |

## Three Common Misconfigurations
- Phenomenon: After scheduled synchronization of CMDB data, some fields in the asset inventory sheet are empty. Cause: No cross-source data field mapping rules are configured, resulting in mismatched field names across different systems.
- Phenomenon: Scheduled tasks run continuously but do not generate updated configuration item lists. Cause: No distinction is made between data source update frequencies, and fixed daily scheduling is used to pull procurement ledgers that update weekly, resulting in tasks having no valid data to process.
- Phenomenon: Service dependency relationships do not match CMDB topologies during fault localization. Cause: Automated tasks do not simultaneously verify association relationships, only updating single configuration item information without synchronously updating association links.

## How to Confirm Configurations Are Correctly Set
- View task scheduling logs, confirm that the pull interval and scheduling cycle match the preset configurations, and check the number of requests and system resource usage in the logs.
- Manually trigger a task, compare the field consistency between the output configuration item list and the original CMDB data, and confirm that the mapping rules are effective.
- Simulate a data source pull failure, check whether the alert trigger logic activates normally, and confirm that the abnormal notification path is configured correctly.
- View the service dependency topology diagram, confirm that the updated association relationships match the actual deployment status, and verify that the association verification logic is effective.
