# Online Troubleshooting and Retrospective for Incident Management and Root Cause Analysis: HTTP Interfaces and External Systems

## What data for this category looks like
This category’s data originates from incident timelines, operational logs, monitoring metrics, and code commit records. The update cadence is either after each major incident or once per month. Daily deliverables include RCA reports, incident tickets, retrospective meeting minutes, and rectification tracking sheets. Document fields include incident occurrence time, root cause localization results, rectification measures, verification status, and more. Units are typically timestamps, event counts, and rectification item counts. There are no uniform fixed units; values vary based on the specific incident scenario. Data has strong association logic. Multi-source information must be linked via unique incident identifiers. Overall data volume fluctuates with incident complexity.

## What constraints these characteristics impose on HTTP interfaces and external systems
Data sources are scattered, and single-update volume is not fixed. HTTP interfaces must support multi-source data pulling and batch upload capabilities, and adapt to data sources in different formats such as operational logs, monitoring metrics, and code commit records. Update frequency is low but data association is strong. Interfaces must support associative query of historical data by incident ID, to avoid mixing data across incidents. Document structures are complex and fields are inconsistent. Interfaces must support custom parameter passing and response format adaptation, to align with field requirements for documents such as RCA reports and incident tickets. Root cause analysis requires repeated verification. Interfaces must support resumable uploads and result caching, to reduce overhead from repeated data pulling. Rectification tracking requires closed-loop recording. Interfaces must support status updates and historical version retention, to ensure rectification processes are traceable.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Carry a dedicated token for the incident scenario, valid for 7 days | Aligns with FastGPT v4.17.0 multi-tenant isolation specifications, prevents cross-incident data leaks |
| `variables` | Pass three types of variables: incident ID, log keywords, and monitoring metric ranges | Matches the field structure of documents such as RCA reports and retrospective meeting minutes, and the associative query logic of multi-source data |
| `responseData` | Return structured incident timelines, root cause localization results, and rectification tracking status | Aligns with standardized formats for retrospective documents, enabling direct generation of reusable retrospective materials |
| Timeout period | 600 seconds | Adapts to the long-duration data pulling requirements of root cause verification, prevents data acquisition from being interrupted by timeouts |
| Request format | Select the corresponding encoding based on the data source type, such as JSON, multipart/form-data | Adapts to data transmission requirements for different formats such as logs and file streams, ensures complete data parsing |

## Three common misconfiguration issues
- Issue: Calling the root cause analysis interface without the `Authorization` parameter returns a 401 Unauthorized status code. Cause: The dedicated token was not obtained via the application creation API, or the token was not correctly carried in the request. This prevents the interface from identifying the incident context associated with the request.
- Issue: Calling the file parsing interface with regular JSON format to pass file streams returns a successful call status but no returned results. Cause: The Content-Type of the HTTP request was not correctly configured as multipart/form-data. This prevents the interface from parsing file stream data and generating parsing results.
- Issue: After calling the model interface, the `responseData` field is empty, and logs show the message was truncated. Cause: A reasonable timeout period was not set. This causes the interface response to be disconnected before completion, returning incomplete response data.

## How to verify proper configuration
- Send a test request carrying the `Authorization` parameter, check if the returned status code is 200. Confirm that the token is valid and interface permissions are working correctly.
- Pass the `variables` parameter containing an incident ID, check if `responseData` includes relevant data such as the timeline and log snippets for the corresponding incident. Confirm that the associative query logic is working correctly.
- After sending the test request, wait for the configured timeout period, then check the response integrity. Confirm there are no truncations or empty returns.
- Review the interface call logs, confirm that all configuration item values have been correctly applied, with no missing or incorrect configurations.
