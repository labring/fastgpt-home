# Online Troubleshooting and Retrospective for Integration and Interface Testing: Conversation Logs and Auditing

## What the data for this category looks like
Data for this category comes from interface management platforms, test environment logs, databases, and message queues. Data updates occur daily or per version release cycle. Daily associated documents include interface test cases, commissioning issue tickets, environment descriptions, and test reports.
Data fields include interface request identifiers, response content, call chain information, session IDs, and detailed execution logs. Primary units are millisecond-level timestamps, request parameter lengths, and response status codes. No custom statistical fields are included.
This category differs from unit and component testing. Its core focus is verifying cross-module interface call logic. Data covers full service chain call details.

## Constraints Imposed on Conversation Logs and Auditing
The multi-source nature of the data requires unified cross-platform field mapping rules for conversation logs and auditing. This prevents traceability failures caused by format differences between logs from interface management platforms, test environments, and message queues.
The daily or per-version update frequency requires audit tasks to support batch parsing and storage of historical logs. This avoids delays from processing single log entries.
Associated documents such as test cases and commissioning issue tickets require audit chains to support linking corresponding test resource IDs. This enables two-way traceability between logs and test workflows.
The cross-module interactive business attributes require logs to fully record chain call nodes and dependent service response details. This supports cross-service fault location.

## How to Configure Settings

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the test case ID associated with the interface session | Enable direct association between logs and test cases, matching daily traceability needs |
| `responseChatItemId` | Generate from the unique request ID of the interface request | Ensure precise localization of logs for individual interface calls, avoid duplicate ID conflicts |
| `detail` | Retain the first 1000 characters of complete request parameters and response bodies | Cover common troubleshooting scenarios for parameter errors and response format exceptions, avoid excessive log size impacting storage |
| Log Storage Period | 30 days | Match the retrospective and traceability cycle of test teams, balance storage costs and usage requirements |
| Batch Audit Concurrency | Top 5 | Adapt to daily server resource usage of test teams, avoid impacting online test environments |
| Audit Trigger Rule | Trigger on interface call failure status | Focus on fault troubleshooting scenarios, reduce audit overhead for non-essential logs |

## Three Common Misconfiguration Issues
- Symptom: Interface test call records do not appear in call logs. Cause: `chatId` is not bound to the session identifier of the corresponding test case, causing logs to not be linked to the audit chain.
- Symptom: The `detail` field is empty in audit logs. Cause: Full log collection configuration is not enabled, only basic status code and timestamp information is collected.
- Symptom: Batch audit tasks time out. Cause: No reasonable batch audit concurrency value is set, leading to excessive server resource usage.

## How to Confirm Configuration Is Complete
- Initiate an interface test call known to trigger a failure. Check if the audit panel displays log entries for the corresponding session identifier.
- Export associated logs for a specified test case. Confirm that log fields include the preset collection content.
- Trigger a batch historical log audit task. Confirm that task execution duration matches the team's preset resource usage threshold.
- Verify that the audit chain can be linked to commissioning issue tickets and test reports, enabling cross-document traceability.
