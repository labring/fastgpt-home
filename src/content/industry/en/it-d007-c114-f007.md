# Online Troubleshooting and Retrospective for Requirements Analysis and PRD Management: Conversation Logs and Auditing

## What the data for this category looks like
This category’s daily documents include four core types: requirement research meeting minutes, PRD documents, user story lists, and requirement change forms.
Data sources typically include customer interview records, internal ticket systems, public competitor pages, and team tracking dashboards.
Documents update once per week or per version iteration.
Common fields include business objectives, acceptance criteria, boundary conditions, and change records.
Core data revolves around requirement definition and changes.
The most time-consuming tasks are interview information categorization, boundary condition confirmation, and requirement change synchronization.
The data is associated with internet product teams, business analysts, and product managers.

## What constraints these characteristics impose on conversation logs and auditing
The data characteristics of this category directly set core constraints for conversation logs and auditing.
First, multi-source data requires audit logs to cover interview conversations, ticket interactions, and document editing scenarios. Logs must associate session identifiers from different sources.
Second, weekly or per-version update frequency requires auditing to support periodic archiving and retrieval. This avoids data redundancy.
Third, requirement change-focused document structures require logs to bind unique identifiers of corresponding PRDs or change forms. This facilitates backtracking of conversation evidence before and after changes.
Fourth, conversation content related to acceptance criteria must be fully retained. This prevents acceptance disputes caused by missing logs.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Log Retention Period | 7 days / archive after each version iteration | Matches the document update frequency of this category, avoids storage redundancy |
| Associated Document Fields | Bind PRD numbers, change form IDs | Corresponds to unique identifiers of core documents in this category, facilitates backtracking requirement evidence |
| Session ID Collection Switch | Enable global collection | Covers all session scenarios, supports log retrieval by session dimension |
| Component Output Collection Switch | Enable workflow node output collection | Covers audit requirements for component outputs |
| Detailed Content Collection Scope | Include acceptance criteria, change discussion content | Covers audit scenarios for core data of this category |
| Single Retrieval Limit | Top 100 records | Prevents excessive retrieval results from affecting operational efficiency |

## Three common configuration errors
- Symptom: After workflow debugging, the output content of the specified reply component does not appear in the global variable history. Cause: The component output collection switch is not enabled, so logs corresponding to `responseChatItemId` are not included in audit records.
- Symptom: Debug history records generated by the workspace cannot be manually cleared and occupy excessive storage resources. Cause: Log retention period or automatic archiving rules are not configured, and only full session data is retained by default.
- Symptom: Update logs for system toolchain responses are not associated with corresponding PRD change forms. Cause: Associated document fields are not configured to bind document IDs, so logs cannot be linked to core documents of this category.

## How to confirm correct configuration
- Initiate a test conversation that includes PRD change discussions. Check whether the conversation log contains complete content of the `chatId`, `responseChatItemId`, and `detail` parameters.
- Enter the workspace history page. Attempt to filter the test session by session ID, and confirm that the filtering function works properly.
- Trigger a workflow node. View the global variable panel, and confirm that component output content has been recorded in the history log.
- Wait longer than the configured log retention period. Verify whether the corresponding session is automatically removed from the workspace or archived.
- This configuration applies to FastGPT v4.17.0.
