# CDN and Edge Acceleration Configuration Operations Duty and Internal Ticket Q&A: Permission and Data Isolation

## What this category of data looks like
The data for this category primarily comes from CDN consoles, DNS resolution records, user access logs, and cluster monitoring alerts. Daily associated documents include domain name access forms, cache rule configuration items, refresh and preheating operation records, and node failure analysis reports. Data updates typically occur via daily batch synchronization or real-time updates when configuration changes are made. A single data entry usually includes fields such as domain identifier, cache TTL value, node IP, alert level, and operator ID. There is no unified fixed length, and fields are adjusted based on configuration type differences.

## What constraints do these characteristics impose on permission and data isolation
This category of data covers public network distribution configurations and user access traces. Domain names and cache rules belonging to different teams are core business assets. Unauthorized access may trigger access exceptions. Multi-source data synchronization requires permission policies to cover multiple links including console operations, log queries, and alert reception, to prevent the spread of permission vulnerabilities from a single link. The ticket processing scope of different operations and maintenance personnel must be bound to their responsible domain name clusters. Typically, only tickets and configurations associated with their own team are allowed to be handled. This prevents cross-team modification of cache rules or access configurations, which could cause cache confusion or domain name access failures.

## How to set configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Team Isolation Scope | Divide by responsible domain name clusters, bind the domain group associated with `teamId` | Matches the business attribution logic of CDN configurations, prevents cross-cluster permission breaches |
| Member Permission Granularity | Split by job role: only view own team data, edit cache rules, submit tickets | Matches the division of labor in operations duty scenarios, prevents unauthorized modifications |
| Data Access Threshold | Only allow querying access logs and alert records from the past 30 days, return up to 1000 entries per request | Complies with conventional data retention requirements, reduces exposure scope of sensitive data |
| Ticket Association Binding | Bind `tmbId` with the domain ID of the corresponding ticket | Ensures internal ticket Q&A only associates configuration data of the current team |
| Permission Effective Timing | Synchronize to all CDN nodes within 10 minutes after change | Adapts to the real-time configuration requirements of CDNs, prevents permission delays |

## Three common misconfigurations
- Symptom: When attempting to add a second team, the system prompts no permission to create a team. Cause: Multi-team creation permission is not enabled in the `teamId` configuration; single-team management is allowed by default.
- Symptom: After restarting the Docker container, an SQL permission error appears in the internal ticket Q&A module. Cause: Permission configuration is not persisted across container restarts, and the database access permission bound to `tmbId` was not loaded correctly.
- Symptom: Cross-team members can view cache rules of other domains. Cause: The team isolation scope is not bound to a specific domain name cluster, and permission division by department leads to unauthorized access.

## How to confirm the configuration is complete
- Log in with different member accounts, verify that only domain configurations and ticket data associated with the current `teamId` can be viewed.
- Submit a test ticket, confirm that only members of the current team can view and reply to the associated configuration information of the ticket.
- After modifying the permission configuration, wait 10 minutes, verify that the new permission rules take effect in the CDN console and log query module.
- Restart the FastGPT service, confirm that the database permission bound to `tmbId` is not lost, and no permission errors appear.
