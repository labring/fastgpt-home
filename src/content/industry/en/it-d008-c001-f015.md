# CDN and Edge Acceleration Configuration Operations Duty and Internal Ticket Q&A: Knowledge Base Retrieval and Recall

## What this category of data looks like
Core data for this category typically comes from CDN consoles, DNS resolution records, user access logs, and cluster monitoring alerts. Daily generated documents include domain access forms, cache rule configuration tables, refresh and preheating operation records, and fault root cause analysis reports. Common data fields include domain names, cache rule IDs, edge node IP addresses, access traffic units, alarm trigger thresholds, and others. Update frequency is either daily sync or real-time updates when configurations are changed.

## What constraints do these characteristics impose on knowledge base retrieval and recall
These data characteristics impose multiple constraints on knowledge base retrieval and recall. Scattered data sources include static configuration documents and real-time access logs, which require retrieval to adapt to both structured fields and unstructured text. Flexible update frequencies require the knowledge base to support incremental synchronization, avoiding full rebuilds that occupy operation and maintenance resources. Technical documents with multiple fields require precise matching of specific parameters such as domain names and node IP addresses to reduce false recall rates. High-frequency scenarios such as record verification and cache rule debugging require controlling token consumption and response time per retrieval to ensure real-time response efficiency for operation duty shifts.

## How to set configurations
The following configurations are based on FastGPT v4.17.0, and are adapted for CDN and edge acceleration configuration operation scenarios:

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `similarity` | 0.75–0.85 | Matches the precision of technical parameters for CDN configurations, balances recall coverage and accuracy |
| `limit` | Top 6 entries | Number of recall results per retrieval, adapts to the concise query needs of operation tickets |
| `searchMode` | semantic | Semantic retrieval mode, covers unstructured documents such as cache rules and fault reports |
| `usingReRank` | Enabled | Reranks recall results, corrects deviations from semantic matching and improves the accuracy of root cause analysis |
| `datasetSearchUsingExtensionQuery` | Enabled | Optimizes query terms by supplementing CDN-related technical terminology, improving retrieval matching accuracy |
| `collectionIds` | Bind specified CDN configuration, log, and alert datasets | Limits retrieval scope, avoids interference from irrelevant data and improves retrieval efficiency |

## Three common configuration mistakes
- Phenomenon: Semantic retrieval recalls multiple matching results, but the model replies that no relevant answer is found. Cause: `usingReRank` reranking is not enabled, or the `similarity` threshold is set too high, causing valid matching results to be filtered out. Remaining low-correlation content cannot support the model in generating valid replies.
- Phenomenon: Knowledge base query response times out, or a single retrieval consumes too many tokens. Cause: The number of recall entries from the `limit` parameter is not restricted, or the query term length is not optimized. This causes the incoming context tokens during retrieval to exceed the platform threshold.
- Phenomenon: Markdown images embedded in the knowledge base cannot be retrieved and matched normally. Cause: Image external links are not configured for public access, or the knowledge base does not support vectorized parsing of image content. This causes image-related information to not be included in the retrieval index.

## How to confirm the configuration is correctly applied
- Initiate a query targeting specific domain name cache rules. Check whether the recall results include matching technical parameters, and adjust the `similarity` and `limit` parameters to levels that meet business requirements.
- View the token consumption records during retrieval. Confirm that the token usage per single retrieval meets the real-time requirements of operation response, and verify whether `datasetSearchUsingExtensionQuery` optimizes the query term length.
- Upload a fault analysis report in markdown format. Confirm that the retrieval results can match the cache exception descriptions in the report, and verify whether the retrieval adaptation configuration for images and text is working properly.
- Submit a temporary cache rule query that does not appear in the existing knowledge base. Confirm that newly synchronized data can be recalled normally, and verify whether the incremental update configuration is effective.

The values provided are common starting points and should be measured against the reader's own samples.
