# CDN and Edge Acceleration Configuration: Operations On-Duty, Internal Ticket Q&A, Deployment and Upgrade

## What this category of data looks like
Typically, data for this category comes from CDN consoles, DNS resolution records, access logs, and monitoring alerts. Daily supporting documents include domain access forms, cache rule configuration tables, refresh and preheating record ledgers, and fault analysis reports. Fields cover domain names, cache TTL, node IPs, access bandwidth, and more. Data updates occur daily or in real time when configuration changes are made. The most time-consuming operational steps include domain filing verification, cache rule debugging, and abnormal node troubleshooting. Errors may lead to slow public network access, incorrect cache states, or failed domain access.

## What constraints these characteristics impose during deployment and upgrade
Since data comes from multiple cloud service consoles and logs, access permissions for corresponding data sources must be configured in advance during deployment to prevent connection failures. Data updates happen frequently, so a gray release strategy must be used during upgrades. This allows verification of configuration synchronization timeliness in batches. The field structure of daily documents means search configurations must match dedicated fields such as domain names and cache rules. General search field mappings cannot be reused directly. The most time-consuming manual steps must be simplified with automated scripts during deployment to reduce operation and maintenance costs. Errors affect public network services, so full configuration backups and rollback tests must be completed before upgrades.

## How to set configurations
| Configuration Item | Suggested Approach | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | Fill in the cluster connection string for CDN node monitoring data | Connect to the monitoring data source of the CDN console to store alerts and access logs |
| `REDIS_URL` | Configure as the instance address for locally caching CDN cache rules | Speed up cache rule searches and adapt to the daily configuration update rhythm |
| Single retrieval limit | Top 6 entries | Match common search requirements in actual business, avoid exceeding the single-batch return volume of CDN logs |
| `STORAGE_S3_ENDPOINT` | Fill in the storage endpoint for CDN refresh and preheating records | Store archived data of historical refresh operations for ticket traceability |
| `DB_MAX_LINK` | 150-200 | Adapt to the high-concurrency query scenario of CDN access logs, avoid connection exhaustion |
| Browser version requirement | Chrome 90+, Firefox 88+ | Adapt to the front-end rendering logic of FastGPT v4.17.0, compatible with browser environments for public network access |

## Three common mistakes
- The reranker call via docker deployment returns false. The interface is connected but the returned result is empty. The cause is that the data source permission for CDN access logs is not configured, so search results cannot be correctly associated with cache rules.
- The number of custom retrievals cannot be adjusted above 6 after private deployment. The cause is that the value of `DB_MAX_LINK` is not modified. The default value limits the number of entries in a single batch query, which cannot match the batch return of CDN logs.
- After upgrading to the specified version, the plugin edit page prompts unsaved changes. The cause is that the `FE_DOMAIN` configuration is not updated synchronously. The domain verification between the front end and back end does not match, causing the save status to fail to sync.

## How to confirm that the configuration is correct
- Execute the reranker interface call, check if the returned results include matching content of CDN cache rules, confirm that the data source connection is normal.
- Try to adjust the number of retrievals to 7, check if it can be saved and take effect, confirm that the `DB_MAX_LINK` configuration is active.
- Modify the plugin configuration and click save, check if the prompt in the upper right corner of the page disappears, confirm that the `FE_DOMAIN` configuration is correct.
- View the monitoring alerts in the CDN console, confirm whether FastGPT can normally pull access log data, confirm that the data source permission configuration is correct.
