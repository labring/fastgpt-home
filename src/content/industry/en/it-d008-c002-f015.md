# IT Service Desk Ticket Handling: Operations On-Duty and Internal Ticket Q&A - Knowledge Base Retrieval and Recall

## What this category of data looks like
Data sources for IT service desk ticket handling include ITSM systems, phone or chat logs, asset systems, and internal knowledge bases. Data updates run daily or in real time, and sync with ticket creation and completion. Daily circulated documents include service request forms, incident tickets, processing records, and user satisfaction surveys. Data fields cover ticket identifiers, problem descriptions, processing workflows, feedback results, and more. Individual data entry lengths vary widely, from short device fault descriptions to complete multi-step processing records.

## What constraints these characteristics impose on knowledge base retrieval and recall
Structural differences between multi-source heterogeneous documents require the retrieval pipeline to adapt to text in different formats and associated metadata. Real-time updates require the retrieval module to support incremental synchronization and low-latency recall. Ticket problems include both colloquial expressions and standardized terminology, so the retrieval model must balance semantic understanding and exact matching. Individual data entry lengths range from tens of characters to thousands of characters. Chunking and recall logic must adapt to different text lengths to avoid semantic fragmentation or excessive context load.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` similarity threshold | 0.75–0.85 | Adapts to the mixed colloquial and standardized expressions in ticket problems, balancing recall precision and coverage |
| `limit` single search limit | Top 8–12 entries | IT service desk ticket problem types are relatively concentrated; too many recall results increase context window burden and affect subsequent generation efficiency |
| `usingReRank` reranking function | Enabled | Ticket problems have high semantic similarity; reranking improves the accuracy of Top 3 results and reduces manual screening costs |
| `datasetSearchUsingExtensionQuery` query expansion | Enabled | Ticket problems often include IT industry abbreviations or custom terminology; query expansion covers more relevant knowledge base content |
| `collectionIds` bound knowledge base collection | Bound to IT service desk exclusive knowledge base | Isolates business data to avoid interference from irrelevant administrative or financial content on ticket-related retrieval |

## Three common configuration errors
- Phenomenon: Long documents, such as complete multi-step processing records, develop semantic fragmentation after chunking, and relevant content cannot be accurately recalled. Cause: Only heading levels ( #, ##, etc.) are used as separators, and no chunking adjustments are made based on content semantics. Complete operation steps are split into different chunks as a result.
- Phenomenon: A 422 status code returns after submitting a ticket retrieval request, or graphical operation instructions cannot be output in conversations. Cause: The binding association between the knowledge base and graphical content is not configured, or the recall logic for graphical content is not enabled during retrieval. Document image information cannot be obtained as a result.
- Phenomenon: A large amount of irrelevant content appears in retrieval results, or recalled ticket processing records do not match the current problem. Cause: The `similarity` threshold is not adjusted to a reasonable range, or the `usingReRank` reranking function is not enabled. Low-matching content is recalled first as a result.

## How to confirm correct configuration
In FastGPT v4.17.0, verify configurations using these steps:
- Upload a single typical long document, such as a complete device fault processing record. Check the integrity of the chunked content, and confirm the chunking logic matches the structural characteristics of business documents.
- Submit 3–5 typical ticket problems. Check the matching degree of retrieval results, and adjust the `similarity` threshold to a range that meets business requirements.
- Upload a docx-format document. Check if the knowledge base retains image information from the original document, and verify the image extraction configuration is active.
- Trigger a retrieval task. Confirm the number of returned results matches the `limit` parameter setting, and confirm the retrieval scope only covers the bound exclusive knowledge base collection.

The values provided are common starting points and should be measured against the reader's own samples.
