# IT Service Desk Ticket Handling: Operations On-Call and Internal Ticket Q&A — Deployment and Upgrade

## What this category's data looks like
This category's data comes from enterprise ITSM systems, phone or internal chat records, asset ledger systems, and internal knowledge bases. Daily generated documents include service request tickets, incident tickets, processing process records, and user satisfaction feedback forms. Data update frequency is daily or real-time. Each data entry contains fields such as ticket number, submitter information, problem description, classification tags, processing status, dispatch records, and satisfaction scores. Multi-source heterogeneous data import and storage must be supported.

## Constraints during deployment and upgrade
Multi-source heterogeneous data sources require configuring multiple storage and integration parameters during deployment to adapt to data read/write requirements of different systems. Daily or real-time update frequency requires configuring appropriate caching strategies during deployment to ensure low-latency response for ticket handling. Ticket data contains sensitive information about employees and devices, so encryption and permission verification parameters must be configured during deployment to ensure internal data security. The unified acceptance and dispatch business model requires configuring a unified access entry during deployment to adapt to enterprise internal local area network access scenarios. During upgrades, the format of historical ticket data must be compatible to avoid loss of processing records and satisfaction data.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | Fill in the MongoDB cluster connection address integrated with the enterprise ITSM system | Adapt to persistent storage of ticket data and meet read/write requirements for daily or real-time updates |
| `PG_URL` | Fill in the PostgreSQL database connection address associated with the internal asset system | Store device ledger and ticket association data to ensure accurate data correlation |
| `REDIS_URL` | Configure as the connection address of the Redis service in the local area network, set the cache validity period to 300-600 seconds | Accelerate cached queries for ticket classification and dispatch, reduce real-time processing latency |
| `FE_DOMAIN` | Fill in the enterprise internal access domain name or local area network IP address, such as http://192.168.0.111:3000 | Ensure internal employees access the service desk through a unified entry, adapt to local area network access requirements |
| `FILE_TOKEN_KEY` | Use a randomly generated 32-bit string as the secret key | Encrypt transmission of ticket attachments and sensitive data, ensure internal data security |
| `ROOT_KEY` | Configure as a secret key known only to internal operations personnel, used for system background management permission verification | Restrict modification permissions for sensitive configurations to avoid business impact from misoperations |

## Three common mistakes
- The symptom is that after deployment, 127.0.0.1 is accessible but the local area network IP is not. The cause is that `FE_DOMAIN` was not correctly configured as the local area network IP or domain name, or the firewall permissions for the corresponding port were not opened.
- The symptom is that ticket classification results have large deviations and cannot match preset service types. The cause is that historical ticket data from the ITSM system was not integrated for model training, or caching parameter configuration was unreasonable leading to delayed data updates.
- The symptom is that the official QR code displayed at the bottom of the system cannot be removed. The cause is that the QR code display parameter in the front-end static configuration file was not modified, or the default promotion component was not disabled in the FastGPT v4.17.0 deployment package.

## How to confirm the configuration is correct
- Run the ping command to test the `FE_DOMAIN` address, confirm that devices in the local area network can connect to the corresponding address and port.
- Log in to the database corresponding to `PG_URL`, query whether associated data of test tickets has been written, verify that the data integration process is working properly.
- Submit a test service request ticket, check whether the system automatically generates ticket classification and dispatch records, verify that the core business process is available.
- Check the bottom of the system front-end page, confirm that the official QR code has been removed, verify that the front-end configuration modification has taken effect.
