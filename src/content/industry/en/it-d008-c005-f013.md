# Operational On-Duty and Internal Ticket Q&A for Issue Triage and Response: Permission and Data Isolation
FastGPT v4.17.0

## What this category of data looks like
This category of data mainly comes from GitHub or Gitee Issues, release notes, user environment information, and code repositories. Daily maintained documents include Issue templates, tag rules, response records, and problem reproduction instructions.
The data update frequency is daily or weekly. Each entry contains fields such as Issue number, status, associated repository path, reproduction steps, tags, and response content. No additional statistical percentage data is included.

## Constraints on permission and data isolation from these characteristics
Data sources are linked to different teams’ code repositories and Issue submitters. Team-based data isolation is required to prevent unauthorized cross-team access to Issue content.
Tag rules and response records in daily documents must match the maintenance permissions of the corresponding team, to prevent unauthorized modification of tag rules or tampering with response content.
User environment information contains sensitive content, which requires separate isolated desensitization to avoid sensitive data leakage.
The data update frequency is daily or weekly. Permission configurations must be synchronized to ensure newly submitted Issue data complies with isolation rules.

## How to set the configuration
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `teamId` binding | Bind the team ID of the corresponding code repository | Match the repository ownership team of the Issue data to implement basic data isolation |
| Member role permissions | Only team maintainers can edit Issue tags | Meet the maintenance permission requirements for tag rules to avoid accidental modifications |
| Data isolation scope | Isolate Issues and response records under different `teamId`s | Correspond to the business fact that data sources belong to different teams |
| Sensitive information desensitization | Hide secret key fields in environment information submitted by users | Avoid sensitive data leakage, comply with operational data security requirements |
| Synchronization frequency | Synchronize external repository Issue data daily | Match the business characteristic of daily/weekly data update frequency |

## Three common configuration mistakes
- An interface prompt displays "No permission to operate this conversation record". The cause is that the current user is not bound to the corresponding `teamId`, so they cannot access Issue data bound to that team ID.
- A permission error is prompted when testing a locally deployed model. The cause is that team access permissions for the corresponding model are not configured, leading to failed permission verification in the call chain.
- Team members cannot view other members’ Issue response records. The cause is that the data isolation scope was mistakenly set to visible only to the creator, so only the creator can access the corresponding records.

## How to confirm the configuration is correct
- Switch test accounts of different teams, verify that only Issue data for the corresponding team is visible.
- Submit a test Issue containing sensitive information, confirm that sensitive fields are automatically desensitized.
- Trigger external repository data synchronization, verify that synchronized Issue data is only visible to the bound team.
- Attempt to modify an Issue tag, verify that only accounts with maintainer permissions can perform the operation.

The values provided here are common starting points and should be measured against the reader's own samples.
