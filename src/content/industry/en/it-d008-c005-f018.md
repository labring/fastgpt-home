# Operations On-Duty and Internal Ticket Q&A for Issue Sorting and Response: Reranking and Hybrid Retrieval

## What Data Looks Like for This Category
This category of data primarily comes from GitHub or Gitee Issues, code repository version logs, user-submitted environment information, and problem reproduction descriptions. Daily maintained documents include Issue templates, tag rules, and historical response records. Data update frequency is daily or weekly, synchronized with newly submitted issues and version iterations. Data fields include problem titles, descriptions, tags, submission times, associated code snippets, user environment information, and more. There are no unified fixed units, with values changing dynamically based on specific Issue content.

## What Constraints Do These Characteristics Impose on the Reranking and Hybrid Retrieval Link
Data in this category is scattered across multiple formats including code snippets, environment descriptions, and plain-text problems. The hybrid retrieval link must support recall logic for multiple text types to avoid missing key code-related information with single-semantic retrieval. The data update frequency is daily or weekly, so a regular synchronization mechanism must be configured to ensure recalled tag rules and historical response records are up to date. Issue fields have no fixed structure, so the reranking link must support dynamic adjustment of weights for different fields to adapt to sorting needs for different problem types. Additionally, the number of issues fluctuates with project activity, so an upper limit for single-round recall entries must be set to avoid context overload that affects response speed.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Similarity threshold | 0.65–0.75 | Reasonable range for matching Issue semantic relevance, balances recall volume and precision, avoids incorrectly recalling unrelated issues |
| Single-round recall limit | Top 10 entries | Adapts to the fast response needs of on-duty operations, avoids excessive information interfering with sorting efficiency |
| Search mode | Hybrid retrieval | Must match semantics, tags, and associated code simultaneously, covers multi-dimensional recall needs and improves sorting accuracy |
| Reranking toggle | Enabled | Re-sorts recalled Issue results by relevance, prioritizes displaying high-priority issues |
| Reranking model adaptation | Calibrated based on actual testing | Adapts to ARM or AMD architecture deployment environments; FastGPT v4.17.0 provides mirror options for corresponding architectures |

## Three Common Mistakes
- Phenomenon: Semantic retrieval mode returns more accurate results than hybrid retrieval. Cause: Hybrid retrieval’s tag and code snippet recall rules are not configured, only relying on pure semantic matching without covering Issue tag association information.
- Phenomenon: When a workflow HTTP request outputs multiple variables, individual variables cannot be bound to a specified knowledge base. Cause: The mapping logic between variables and knowledge bases is not configured in the reranking and retrieval link, making precise matching of corresponding data sources impossible.
- Phenomenon: Reranking model images fail to load during ARM architecture deployment. Cause: An AMD architecture reranking model image is used, and the mirror version adapted to ARM architecture is not selected.

## How to Confirm Configurations Are Correctly Set
- Users may inspect the retrieval configuration page to confirm the search mode is set to hybrid retrieval and the reranking toggle is enabled.
- Users may submit a test Issue containing code snippets and tags, then verify that retrieval results preferentially return historical responses matching the tags and code.
- Users may check the deployment environment’s mirror version to confirm the reranking model mirror is adapted to the current system architecture.
- Users may review workflow logs to confirm the number of results returned by the retrieval link matches the single-round recall limit setting.

The values provided are common starting points and should be measured against the reader's own samples.
