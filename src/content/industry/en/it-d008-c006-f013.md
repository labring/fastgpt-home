# Pull Request Review Operations On-Call and Internal Ticket Q&A: Permission and Data Isolation

## What the data for this category looks like
Pull Request review data primarily comes from associated code repositories, CI pipelines, Issue links, and change submissions from contributors. Daily generated documents include PR descriptions, code review comments, CI execution results, merge records, and more. The data update rhythm is usually daily or weekly. Each data entry includes fields such as the submitter of the corresponding change, change scope, test status, etc. There is no unified fixed unit, and it is dynamically generated alongside change content.

## What constraints these characteristics impose on permission and data isolation
Pull Request review data involves multiple submitting and reviewing roles, with scattered sources. This requires permission configurations to match the operational scope of different roles. The data update rhythm fluctuates with the frequency of code changes, so incremental permission verification must be supported to adapt to real-time or scheduled synchronized change content. Code repositories and CI pipelines associated with different PRs belong to different project teams or departments, so cross-team data access must be strictly isolated to prevent unauthorized personnel from viewing unassociated review content and ticket information. Additionally, merge records and review comments are sensitive change information, so access to full content must be restricted to project maintainers and the Owners of corresponding modules only.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Team permission groups | Divide by project team, each group corresponds to a unique `teamId` | Match the requirement for isolating Pull Request review data by project team |
| Member role binding | Assign administrator roles to maintainers, general contributor roles to contributors | Differentiate operational and viewing permissions for different entities |
| Data scope isolation | Limit access to PR data under the corresponding `teamId` to only team members | Adapt to cross-team isolation constraints for scattered data sources |
| API call authentication | Bind `tmbId` to verify the caller's identity | Prevent unauthorized API calls from accessing PR review data |
| Permission synchronization cycle | Synchronize once every 24 hours | Adapt to the daily update rhythm of PR data |
| Session filtering configuration | Return corresponding data based on the `teamId` associated with the session | Ensure on-call operations staff only view tickets and PRs for their assigned projects |

## Three common configuration errors
- Symptom: API calls associated with PR review data return permission denied errors. Cause: The caller's access permissions are not bound to the corresponding `teamId` configuration.
- Symptom: Non-project members can view all PR review records. Cause: Data scope isolation configuration is not enabled, and access to data under the corresponding `teamId` is not limited to only team members.
- Symptom: Operations tickets and PR data from different departments are visible to each other. Cause: Team permission groups are not divided by project team, resulting in unisolated cross-team data.

## How to confirm the configuration is correct
- Log in to the FastGPT v4.17.0 backend, switch accounts with different roles, and verify that only the corresponding role can view PR review data associated with the `teamId`.
- Call the API associated with PR data, use a caller identity that is not bound to a `teamId`, and confirm that a permission denied prompt is returned.
- View the permission synchronization logs to confirm that team permissions and PR data scope are synchronized daily according to the configured cycle.
- Switch accounts from different project teams, and verify that only PR review and ticket information for the corresponding project team can be viewed.
