# Pull Request Review Operations On-Call and Internal Ticket Q&A: Deployment and Upgrade

## What This Category of Data Looks Like
PR review data primarily comes from PR files in code repositories, execution results of CI pipelines, linked Issue links, and change descriptions submitted by contributors. Data update frequency is typically daily or weekly. Single PR review records update in real time when the PR is merged or rejected. Daily documents include PR change content summaries, code review comment entries, CI test results, merge status records, and more. Data fields cover change content, review feedback, CI pass rate, linked Issue numbers, contributor identity information, and other items.

## What Constraints These Characteristics Impose on Deployment and Upgrade Workflows
PR review data relies on external integration with code repositories and CI pipelines. Valid access permissions must be configured during deployment to prevent synchronization tasks from being interrupted. Data update frequency is daily or weekly. A rolling update strategy must be used during upgrades to ensure incremental synchronization processes are not disrupted. Data includes code snippets and structured review records. Different document parsing rules must be adapted during deployment to avoid retrieval deviations. Single PR review results directly affect main branch stability. A health check mechanism must be configured after deployment to promptly detect configuration errors.

## How to Set Configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–200 connections` | Adapts to concurrent read and write requirements of PR review data, avoiding database connection exhaustion |
| `MONGODB_URI` | `mongodb://pr-review-user:secure-pass@db-host:27017/pr_db?authSource=admin` | Stores structured data such as PR review records and CI results |
| `REDIS_URL` | `redis://:redis-pass@cache-host:6379/0` | Caches PR change retrieval results to reduce database load |
| `STORAGE_S3_ENDPOINT` | `https://s3-cn-north-1.amazonaws.com` | Stores attachments and review documents uploaded for PRs |
| `FE_DOMAIN` | `https://pr-review-fastgpt.your-domain.com` | Configures the front-end access domain name for generating PR-related jump links |
| `FILE_TOKEN_KEY` | `Randomly generated 32-digit hexadecimal string` | Encrypts access tokens for PR attachments to prevent unauthorized access |

## Three Common Misconfigurations
- Phenomenon: A 504 timeout error occurs when searching for operational ticket content linked to PRs after deployment. Cause: The connection limit of `DB_MAX_LINK` was not adjusted, leading to the database connection pool being exhausted by concurrent requests for PR review.
- Phenomenon: After upgrading to FastGPT v4.17.0, a database connection failure error pops up when creating a new PR review application. Cause: Access permissions for `MONGODB_URI` were not configured correctly, making it impossible to write or read review-related metadata.
- Phenomenon: After enabling the thinking process configuration, the thinking content in PR review responses is always fully displayed and cannot be collapsed. Cause: The association logic between knowledge base retrieval configuration and the thinking switch was not correctly bound, resulting in the front-end rendering rules not taking effect.

## How to Confirm Configuration is Complete
- Run `curl https://pr-review-fastgpt.your-domain.com/api/health` and check that the returned status code is 200 to confirm the service started normally.
- Submit a test PR to the linked code repository, wait for synchronization to complete, then initiate a ticket Q&A for that PR in FastGPT, and check if the knowledge base can retrieve the corresponding PR description and review records.
- Initiate a ticket Q&A for a PR review, enable the thinking switch, then check if the thinking content in the response can be collapsed according to the configuration to confirm the front-end configuration took effect.
- View the database connection monitoring panel, confirm that the current active connection count does not exceed the value set for `DB_MAX_LINK`, to confirm the connection pool configuration is reasonable.

The values provided are common starting points and should be measured against the reader's own samples.
