# SLA and Service Reports: Operations On-Call and Internal Ticket Q&A, Permission and Data Isolation

## What this category of data looks like
This category of data is centered around customer contracts. Data sources include monitoring systems, ticket systems, contract documents, and customer communication logs. Daily produced documents include SLA clauses, monthly service reports, availability statistics, and customer review minutes. Update frequency is monthly or quarterly. Document fields vary by type, including indicator thresholds, service durations, incident attribution, review conclusions, and other content. There is no unified fixed unit.

## What constraints do these characteristics create for permission and data isolation
Because this category of data is aggregated by customer contract cycle, and different teams correspond to service management for different customers, permission isolation must strictly bind customers and teams to prevent cross-team access to SLA and report data for non-responsible customers. Data update frequency is low, so real-time permission verification is not required, but dimension filtering must be completed during report generation and data retrieval. Different job roles have different operating permissions for documents, so operating ranges must be divided by role. At the same time, access to raw data and archived reports by unauthorized roles must be restricted to prevent sensitive information leaks.

## How to configure settings
| Configuration Item | Suggested Approach | Rationale |
| --- | --- | --- |
| `teamId` association rule | Bind `teamId` to customer contract groups | SLA and service reports are managed by customer contract cycle. Different teams correspond to different contract groups to prevent cross-team data leaks |
| Role permission binding | Assign document operation permissions by `tmbId` | Customer success managers are bound to the `tmbId` that allows editing SLA clauses. Technical support supervisors are bound to the `tmbId` that only allows viewing |
| Data source filtering | Only retrieve monitoring and ticket data associated with the current `teamId` | Data sources include cross-customer system records, so retrieval scope must be isolated by team |
| Report access validity | Lock generated reports by contract cycle | Monthly/quarterly reports have low update frequency. Locking prevents unauthorized modification |
| Permission verification threshold | Complete cross-team data verification within `600 seconds` | Avoid long waits that impact operations on-call and ticket response efficiency |
| Referenced document isolation | Only allow documents associated with the current `teamId` to be used as reference sources | Prevent cross-customer documents from being incorrectly referenced in service reports |

## Three common configuration mistakes
- Phenomenon: Unauthorized team members attempt to create SLA reports, and the interface prompts "No permission to create document". Cause: The corresponding member's `tmbId` is not associated with the `teamId` group of the target customer contract.
- Phenomenon: When retrieving SLA indicator data, availability statistics records from other customers are returned. Cause: The rule to filter data sources by `teamId` is not configured, so cross-customer data is not isolated.
- Phenomenon: Generated service reports cannot reference specified SLA clause documents. Cause: Permission isolation restricts the access scope of referenced documents, only allowing documents associated with the current `teamId` to be called.

## How to confirm configuration is complete
- Switch test accounts with different `teamId` values, verify that only SLA and service report data for the corresponding customer contract group can be accessed.
- Attempt to modify SLA clauses with an unauthorized role, confirm that the operation is intercepted by the system and no edit permission is granted.
- Trigger monthly service report generation, verify that only members associated with the current `teamId` can view the generated results and raw data.
- Check the retrieval logs in FastGPT v4.17.0, confirm that only monitoring and ticket data associated with the current `teamId` is retrieved.
