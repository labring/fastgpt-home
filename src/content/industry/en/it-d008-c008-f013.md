# Operations on Duty and Internal Ticket Q&A for Special Event Campaigns: Permission and Data Isolation

## What the data for this category looks like
Special event campaign data typically originates from content libraries, campaign backends, traffic metrics, and user feedback. Four core document types are routinely generated: activity plans, resource slot schedules, event page copy, and post-campaign review reports. Data fields include activity cycle identifiers, resource slot numbers, copy version numbers, post-campaign statistical fields, and more. Update frequency follows a weekly cadence, with temporary adjustments to schedules and copy content around holidays.

## What constraints do these characteristics impose on permission and data isolation?
Core data for special event campaigns features clear activity cycle attributes. Documents and data from different campaigns must be strictly isolated to prevent cross-campaign resource slot conflicts or copy leaks. Dispersed data sources mean permission checks must cover multiple data entry points. Fluctuating update frequencies require permission configurations to adapt quickly to temporary adjustments. Errors in campaign data directly impact event participation and resource utilization, so permission isolation must be traceable to meet audit requirements for operations on duty.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Bind a fixed value to the event operations team | Differentiate activity data and permission scopes across teams |
| `tmbId` | Bind to a single special event campaign | Isolate page copy, schedules, and review data across different campaigns |
| Permission group configuration | Configure based on activity cycle, with validity covering the full activity lifecycle | Adapt to the clear cycle characteristics of special event campaigns, prevent permission expiration or unauthorized access |
| Storage quota | 1000 MB of storage per team | Control the upper storage limit for activity-related documents and data per team |
| SSO integration configuration | Configure authentication callback addresses for intranet environments | Adapt to on-premises intranet operation and maintenance scenarios |
| Operation log toggle | Enable full-link permission operation logs | Meet traceable audit requirements for operations on duty |

## Three common misconfigurations
- Failure to create multiple login accounts for the same team, or permission check failures caused by missing `tmbId` fields in historical version documents in MongoDB. The cause is failure to supplement the `tmbId` field during historical data migration, and failure to configure team-level account binding rules.
- SSO integration failure after intranet deployment, unable to redirect to the authentication page. The cause is failure to configure the authentication callback address whitelist for intranet environments, resulting in blocked authentication requests.
- Cross-campaign data leakage during operation and maintenance ticket queries. The cause is failure to bind the `teamId` parameter by activity cycle, and permission groups not covering the full activity lifecycle, resulting in old permission configurations remaining active.

## How to confirm configurations are correct
- Log in to test accounts from different teams, verify that only activity plans, resource slot schedules, and other documents belonging to the current team can be viewed, and that activity data from other teams is inaccessible.
- Check activity-related documents in MongoDB, confirm that all contain the `tmbId` and `teamId` fields, with field values matching the corresponding activity or team.
- Trigger the SSO authentication flow, verify that the system can normally redirect to the authentication page and complete login in the intranet environment, with the redirect path matching the configured callback address.
- View the FastGPT v4.17.0 operation logs, confirm that all permission changes and data access operations are fully recorded with no missing entries.
