# Operations Duty and Internal Ticket Q&A for Personal Information Protection Compliance: Reranking and Hybrid Retrieval

## What the data for this category looks like
This category’s data comes from business systems, App permission lists, privacy policies, and user request records. The update frequency is quarterly or whenever a product version changes. Daily generated documents include personal information inventories, processing rules, impact assessment reports, and user authorization texts. Document structures cover structured table types such as permission lists and unstructured text types such as privacy policies. Fields include compliance-related content such as information category, processing purpose, legal basis, and storage period.

## What constraints these characteristics impose on the reranking and hybrid retrieval link
Multi-source compliance data requires hybrid retrieval to integrate structured and unstructured content. This places requirements on the adaptability of retrieval modes. Document update frequencies are not fixed, and changes must take effect quickly. The reranking link must support adjusting priority based on update time. Document fields vary widely across different structures. The reranking model must adapt to field matching logic to avoid incorrectly recalling irrelevant content. Retrieval results in compliance scenarios directly affect subsequent processing workflows. The relevance and completeness of results must be strictly controlled to prevent missing key compliance rules.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `usingReRank` | Enabled | This scenario needs to filter compliance documents unrelated to operation tickets, and improve the targeting of retrieval results |
| `similarity` | 0.75–0.85 | Compliance documents require precise matching of compliance requirements in tickets, to avoid incorrectly recalling irrelevant rules |
| `limit` | Top 8 entries | Cover multiple core compliance documents such as personal information inventories and processing rules, while controlling context length |
| `searchMode` | Hybrid Retrieval | Integrate structured permission lists and unstructured privacy policy texts, to adapt to multi-format compliance data |

## Three common mistakes
- Phenomenon: After enabling the reranking function, the application interface cannot check the configured reranking model. The backend log returns a rerank error. Cause: The call address or permission parameters of the reranking model are not correctly configured in config.js, or multiple models are configured without specifying a default call item.
- Phenomenon: The number of compliance documents returned by hybrid retrieval does not match the set `limit` parameter. Results are redundant or too few. Cause: The number limits in the recall phase and reranking phase are not adjusted synchronously, leading to conflicting parameters between the two phases.
- Phenomenon: Retrieval results do not prioritize matching the latest compliance rules mentioned in the ticket. Cause: The document update time is not included in the weight calculation of reranking, or the reranking priority is not adjusted according to the update frequency of compliance documents.

## How to confirm the configuration is complete
- The application configuration page of FastGPT v4.17.0 is accessed. The `usingReRank` switch is confirmed to be in the enabled state, and the correct reranking model configuration is associated.
- A simulated operation ticket is submitted. The relevance of retrieval results is checked, and the `similarity` threshold is adjusted to a range that meets business requirements.
- The number of documents returned by retrieval is verified. The count matches the set `limit` parameter, with no abnormal missing or redundant entries.
- The sorted order of reranked results is reviewed. The priority of compliance documents is confirmed to meet the requirements of the business scenario.
