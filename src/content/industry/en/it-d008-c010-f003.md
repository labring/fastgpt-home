# Incident Response and Troubleshooting Operations On-Call and Internal Ticket Q&A: Sharing and Embedding

## What data for this category looks like
This category’s data comes from four sources: monitoring alerts, log platforms, APM, and user feedback. Updates are triggered in real time or synced after each incident is completed. Core business documents include four types: fault tickets, incident timelines, emergency response plans, and fault notifications. Document structure includes fields such as incident ID, trigger time, impact scope, execution steps, and notification records. Field units follow general operations industry standards: time uses standard time-series format, and impact scope is measured by service cluster or business module.

## What constraints do these characteristics impose on the Sharing and Embedding workflow
Data sources are scattered and updated in real time. Identity verification rules must be configured via the FastGPT commercial edition guest access window, or connected to the permission verification logic of internal operations systems, to prevent unauthorized access to sensitive operations data. Document structure includes multiple types of incident-related content. A specified document reference range must be configured in the FastGPT guest access window, to ensure returned content matches the operations fault handling business scenario. Data update frequency is high. Latest fault information must be synced via the knowledge base update mechanism of internal operations systems. The FastGPT guest access window will display the current content of the knowledge base. Fault handling has strict timeliness requirements. Shared link access response must match the response standards of the business scenario, to prevent delays in stop-loss operations.

| Shared link validity period | Test starting point: 7 days; adjust based on actual testing of incident response and fault handling collaboration cycles and revocation requirements | Verify availability within the validity period and access behavior after expiration. ## Three common misconfigurations
- Sharing entry for incident response and fault handling fails to open. First verify the full generated link and its validity period, then check browser request status. Do not manually replace `shareId`.
- Visibility range of incident response and fault handling data does not match expectations. Verify third-party identity verification results, workflow request parameters, and data permissions of external systems respectively. The sharing entry identifier itself does not provide business authorization.
- The same incident response and fault handling Q&A is not visible on another device. In anonymous scenarios, first verify device, browser, and local identity status. Retention cannot be guaranteed across devices or after cache clearing. Do not use this phenomenon alone to judge service anomalies.

## How to confirm configuration is complete
- Open the generated guest access shared link embedding code, embed it into your own system page in a test environment, and check if fault tickets and incident document content matching the specified incident range are loaded.
- Switch to different browsers or clear browser cache, then access the embedded page, and confirm that display of specified incident data is not affected by session state.
- Simulate deleting conversation content, check if logs of the external operations system retain records of this operation, and that records are not lost along with local session deletion.
- Check if the basic display framework of the embedded page matches the interface style of your own system, with no obtrusive default navigation elements.

Note: The configuration values provided here are common starting points. They should be evaluated against your own specific samples and use cases.
