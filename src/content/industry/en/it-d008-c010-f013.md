# Incident Response and Troubleshooting: Operations On-Call and Internal Ticket Q&A — Permission and Data Isolation

## What the data for this category looks like
SREs, operations on-call personnel, and research and development on-call leads maintain the core data for this category daily. This data includes four types of documents: fault tickets, event timelines, emergency response plans, and fault notifications.
Data sources include monitoring alerts, log platforms, APM tools, and user feedback channels. Updates happen in real time or each time an event triggers.
Fault tickets include the `teamId`, `tmbId`, incident severity, impact scope, and handler fields. Event timelines log trigger times and operation trails. Emergency response plans standardize fixed response procedures. All data binds to specific incidents and operations teams.

## What constraints these characteristics impose on permission and data isolation
Multi-source data access requires permission isolation to cover access scopes for external systems such as monitoring alerts and log platforms. This prevents unauthorized viewing of other teams’ monitoring data.
The real-time update feature requires permission verification and data access to take effect simultaneously. This stops newly triggered incidents from being accessed by unauthorized accounts.
Differing responsibilities for the four document types require permission division by role: operations on-call personnel can only view tickets and events belonging to their own team, SREs can edit response procedures, and research and development leads can generate fault notifications.
If historical incident documents lack the `tmbId` field, cross-team data confusion occurs. This increases the complexity of permission control.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Bind to the unique identifier of the business operations team | Match the owning team of the fault ticket, ensuring accounts in the same team share the same data scope |
| `tmbId` | Use a 32-bit random string, calibrated via actual testing | Distinguish all associated documents for a single incident, avoiding cross-incident data confusion |
| Team permission scope | Restrict to the team corresponding to the `teamId` bound to the current account | Align with the responsibility boundaries of operations teams, preventing unauthorized access to other teams’ fault data |
| Fault ticket query limit | Top 500 entries | Limit the number of tickets queried per account per session, avoiding overload of permission verification |
| Historical data completion rule | Automatically complete the associated `teamId` for documents missing `tmbId` | Resolve the issue of unisolated historical incident documents, complying with FastGPT v4.17.0 requirements |
| SSO authentication mapping | Map the team identifier returned by SSO to the `teamId` parameter | Implement unified permission management for multiple accounts under the same team, integrating with internal enterprise authentication systems |

## Three Common Misconfigurations
- Scenario: Multiple accounts under a single team cannot create fault tickets, and the interface prompts "No permission to access team data". The cause is that the account is not correctly bound to the preset `teamId` identifier, causing the system to fail to match the data scope.
- Scenario: Historical incident documents fail to load or are visible across teams, and the log prompts "Data matching failed". The cause is that the historical data completion rule is not configured, causing some old documents to lack the `tmbId` field and failing permission verification.
- Scenario: After logging in via SSO, users cannot access tickets for the preset team, with the error prompt "No valid team bound". The cause is that the team identifier returned by SSO is not correctly mapped to the `teamId` parameter, causing the system to fail to identify the account’s affiliated team.

## How to Verify Successful Configuration
- Two accounts from different teams access the platform. Only fault tickets and event data bound to the corresponding `teamId` are visible.
- A batch of historical incident documents without `tmbId` tags is imported. The system automatically completes the associated `teamId` field.
- After SSO authentication is configured, an enterprise account logs in. The account is automatically associated with the preset team permission scope.
- A test alert is triggered. Only accounts with corresponding permissions can view all associated data for the incident.
