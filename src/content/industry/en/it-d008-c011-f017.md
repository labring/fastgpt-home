# Operations on-call and internal ticket Q&A for cloud host provisioning and resource activation: Deployment and upgrade

## What this category’s data looks like
The data for this category typically comes from cloud management platforms, order systems, IAM, and billing systems. Updates occur per order or in real time. Associated daily documents include resource activation forms, instance configuration sheets, account permission forms, and delivery confirmation forms. Fields usually include items with clear units such as instance specifications, network configurations, permission scopes, and delivery statuses. Core data revolves around the creation and activation process of computing resources. This differs from adjacent categories focused on network or load balancer configuration.

## What constraints do these characteristics impose during deployment and upgrade
Data sources for this category are scattered, and update frequencies vary.
Complete multi-system integration configuration during deployment. This ensures the resource activation process synchronously pulls order, permission, and billing data.
Configure document association and parsing logic during the deployment phase, per the multiple associated daily documents. This logic matches validation rules for fields such as instance configurations and permission forms.
The most time-consuming steps focus on specification verification and configuration validation. Reserve parameter space for automated validation during deployment.
Maintain uninterrupted data synchronization during upgrades. Configuration changes may cause exceptions in the resource activation process, leading to customer deployment failures or billing disputes.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–200 connections` | Supports concurrent ticket queries and resource synchronization requests, avoiding connection pool exhaustion |
| `REDIS_URL` | `redis://localhost:6379/0` | Caches ticket status and permission verification results, reducing latency from cross-system calls |
| `MONGODB_URI` | Configured using the actual connection string of the local cloud management database instance | Stores structured business data such as resource activation forms and delivery confirmation forms |
| `STORAGE_S3_ENDPOINT` | Configured based on on-site measurement | Connects to cloud storage services to store instance configuration sheets and operation log files |
| `FE_DOMAIN` | `https://your-fastgpt-domain.com` | Configures the callback domain for the internal ticket system to ensure notification delivery is reachable |
| `ROOT_KEY` | `Randomly generated 32-character string` | Secures access to backend management interfaces, preventing unauthorized operations |

## Three common mistakes
- After upgrading FastGPT v4.17.0, rule traceability symbols appear at the end of model conversation response results. This occurs because the built-in rule display switch configuration is not disabled.
- Field empty errors occur during ticket synchronization. This is caused by incorrect configuration of the field mapping relationship between the cloud management platform and FastGPT, which prevents some required fields from being pulled.
- Resource activation processes time out. This is due to an excessively low `DB_MAX_LINK` configuration, which causes the database connection pool to fail to support concurrent resource verification requests.

## How to confirm configurations are correctly set
- Run a data source connection test, pull a real resource activation form, and verify successful synchronization to the FastGPT system.
- Initiate a simulated resource activation request, and check real-time updates of ticket status to the cloud management platform and billing system.
- Access the configured `FE_DOMAIN`, and verify the internal ticket system’s callback interface receives push notifications normally.
- Call the backend management interface, and use `ROOT_KEY` to confirm access permissions work correctly.

The values provided are common starting points and should be evaluated against local deployment samples.
