# Cloud Host Provisioning and Resource Activation: Operations On-Call and Internal Ticket Q&A — Reranking and Hybrid Retrieval

## What Data for This Category Looks Like
Usually, data for this category originates from cloud management platforms, order systems, IAM permission systems, and billing systems. Updates occur in real time for each individual order. Daily documents include resource activation tickets, instance configuration sheets, account permission tickets, and delivery confirmation sheets. Typical document fields cover instance specifications, network security group configurations, account permission scopes, billing nodes, and other details. Document formats and field order differ across exports from various systems. Core users of this data include cloud service operations staff, cloud platform operations staff, and customer support personnel. This data supports verification and confirmation across the full resource activation workflow.

## What Constraints Do These Characteristics Impose on Reranking and Hybrid Retrieval?
The need to integrate multi-source data means hybrid retrieval must cover four data source categories: cloud management, order, permission, and billing. This prevents missing key configuration information.
The real-time update feature requires the retrieval pipeline to pull latest data synchronously. This stops expired configuration matching results from being returned.
The variety of document fields and unique business attributes require the reranking model to prioritize matching high-value fields such as instance specifications and security group configurations. This ensures accuracy for core business verification.
The number of documents linked to a single ticket is limited, but field correlation is strong. It is necessary to balance the number of recalled entries and precision. This avoids irrelevant entries disrupting rapid verification by on-call operations staff.

## How to Configure Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Reranking Toggle | Enabled | This category has many document fields and strong business correlation. Enabling reranking filters low-relevance permission or billing entries, raising the display priority of core configurations |
| Maximum Single Search Results | Top 6-10 entries | The number of documents linked to a single ticket is limited. This range covers all relevant content without increasing the processing load of the reranking model |
| Similarity Threshold | 0.70-0.85 | Calibrated via field testing, this range balances recall rate and precision, avoiding missing key configurations or including irrelevant results |
| Retrieval Mode | Hybrid Retrieval | Data for this category comes from multiple systems. Hybrid retrieval integrates documents from different data sources, ensuring complete retrieval coverage |
| Reranked Display Count | Top 3-5 entries | Core configurations for this category are concentrated. Prioritizing the top 3-5 entries improves verification efficiency for on-call operations staff |

## Three Common Misconfigurations
- Symptom: No search results after enabling reranking in the application, but verification works normally in the knowledge base test page. Cause: The reranking model was only configured in the knowledge base test page, and not bound to the reranking model in the application's retrieval configuration. This means the reranking logic is not triggered when the application is called.
- Symptom: Result order is chaotic after reranking, and instance specification matching is lower than expected. Cause: Weighted rules were not set for exclusive fields of this category, such as instance specifications and security group configurations. A generic reranking model cannot recognize business priorities.
- Symptom: Reranking model call times out. Cause: The maximum single search result setting is too high, and the number of recalled documents exceeds the processing capacity of the reranking model, leading to call timeout.
