# Operations on-duty and internal ticket Q&A for cloud network and load balancing configuration: Deployment and upgrade

## What data this category includes
This category’s data primarily comes from VPC configurations exported from cloud platform consoles, local network topology diagrams, traffic monitoring reports, and customer architecture design diagrams. Daily maintenance documents include VPC network segment planning, security group rule lists, load balancing backend server group configurations, and change approval forms. Data updates are triggered every time a network change or ticket is submitted. Fields include network segment ranges, port mapping rules, health check intervals, backend server weights, and other items. There are no unified fixed units; configurations must match the specification standards of the corresponding cloud vendor.

## What constraints these characteristics impose during deployment and upgrade
Data for this category is stored across multiple cloud consoles and local change documents. During deployment, structured mapping of cross-source configurations must be completed to avoid configuration deviations caused by manual entry. Frequently updated change forms and real-time traffic data require that current running configurations be retained during the upgrade process to prevent service interruptions. The lack of unified units for fields requires automatic adaptation between cloud vendor configurations and platform parameters during the deployment phase, to avoid configuration failures caused by unit mismatches. Additionally, configuration rollback paths must be reserved during deployment and upgrades, to address access anomalies or traffic forwarding issues caused by incorrect network segment planning or health check configurations.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Point to the MongoDB replica set address deployed in the internal network, add database authentication parameters | Configuration and change records for this category are mostly stored in MongoDB instances. Internal network access permissions must be ensured to avoid external exposure risks |
| `REDIS_URL` | Configure as the internal network Redis cluster address, set connection timeout to `30 seconds` | Used to cache traffic monitoring and health check status data. A 30-second timeout balances query efficiency and connection stability |
| `DB_MAX_LINK` | `100–200` | Matches the concurrent request volume of frequent changes for this category, to avoid configuration synchronization failures caused by insufficient connection counts |
| `FE_DOMAIN` | Enter the access domain name of the internal network load balancer | Used to generate configuration jump links for internal tickets, matching the daily access path of operations staff |
| `STORAGE_S3_ENDPOINT` | Enter the endpoint address of the internal network object storage service | Used to store backups of change forms and network topology documents, adapting to the requirements of internal network deployments |
| `ROOT_KEY` | Configure as a random string with a length of no less than `32 characters` | Used for permission verification in the internal ticket system, to prevent unauthorized access to the configuration management page |

## Three common mistakes
- Symptom: After upgrading FastGPT v4.17.0, load balancing configuration synchronization fails, and the console shows database connection timeout. Cause: The `DB_MAX_LINK` configuration was not updated synchronously, leading to insufficient database connection counts and failure to pull the latest network segment and rule data.
- Symptom: Network topology diagrams or change form attachments cannot be loaded in internal ticket replies. Cause: `STORAGE_S3_ENDPOINT` was not configured, causing the platform to fail to properly read and return stored documents.
- Symptom: Health check configuration updates do not take effect, and traffic is still forwarded to abnormal backend nodes. Cause: The original `REDIS_URL` cache configuration was not retained during the upgrade, causing health check status data to not be synchronized to the load balancing system in real time.

## How to confirm configurations are set correctly
- Perform an internal network connectivity test to verify that services corresponding to `MONGODB_URI` and `REDIS_URL` can be connected normally.
- Submit a test change ticket to confirm that configuration jump links corresponding to `FE_DOMAIN` can be properly generated in ticket replies.
- Check database connection count monitoring to confirm that current active connection counts do not exceed the `DB_MAX_LINK` configuration threshold.
- Upload a test network topology document to verify that the storage service corresponding to `STORAGE_S3_ENDPOINT` can complete file storage and reading normally.
