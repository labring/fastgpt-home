# Cloud Billing and Cost Accounting Operations Duty and Internal Ticket Q&A: Deployment and Upgrade

This page is written based on FastGPT v4.17.0.

## What this category of data looks like
The data for this category mainly comes from cloud billing systems, tag data, order systems, and resource monitoring tools. Daily generated documents include billing details, cost allocation tables, resource utilization reports, and optimization suggestion sheets. Data update cycles are divided into daily and monthly levels. Fields include billing cycle identifiers, resource unique codes, cost accounting values, allocation ratio parameters, and more. Corresponding units include yuan, hourly resource consumption units, and others. Data must be associated with tag ownership and actual resource consumption for subsequent expense verification and cost optimization.

## What constraints these characteristics impose on the deployment and upgrade phase
The data for this category is scattered across multiple sources, has layered update cycles, and complex document structures. These factors create multiple constraints for the deployment and upgrade process. During deployment, configure permissions for connecting multiple systems, and adapt to the interface formats of different sources such as cloud billing and tag data. Distinguish between daily and monthly scheduled scheduling logic to match data update frequencies. During upgrade, maintain compatibility with field mapping rules for old versions of billing details and cost allocation tables to avoid data parsing errors. Support iterative updates of tag ownership verification logic to adapt to subsequent cost allocation optimization requirements. At the same time, synchronization of multi-source data must ensure consistency. During deployment, configure reasonable retry mechanisms and timeout parameters to avoid data synchronization interruptions.

## How to set the configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://username:password@host:27017/cost_db?authSource=admin` | Persistently stores unstructured data of billing details and resource utilization reports, supports multi-dimensional queries |
| `PG_URL` | `postgresql://user:pass@host:5432/cost_share?sslmode=require` | Stores structured data of cost allocation tables and optimization suggestion sheets, supports complex statistical operations |
| `REDIS_URL` | `redis://:auth_pass@host:6379/1` | Caches frequently queried tag data and billing summaries, reduces repeated calls to multi-source systems |
| `DB_MAX_LINK` | `15–25 connections` | Adapts to concurrent connection requirements for multi-source data synchronization, avoids exhausting database connection resources |
| `STORAGE_S3_ENDPOINT` | Fill in the exclusive endpoint provided by the cloud service provider | Stores historical billing files and optimization suggestion sheets, meets offline access and audit requirements |
| `ROOT_KEY` | Generate a random 32-character string | Configures the highest-privilege access key for the system backend, ensures management security after deployment |

## Three common mistakes
- The symptom is that variables in text concatenation during API calls do not return results. The cause is that the `FILE_TOKEN_KEY` parameter was not configured correctly during deployment, causing signature verification failure for variable parsing.
- The symptom is that Docker containers stay in a loading state for a long time after startup. The cause is that `REDIS_URL` or `MONGODB_URI` was not configured correctly, causing connection timeout to dependent services.
- The symptom is that the new account function cannot be enabled. The cause is that the permission switch corresponding to `ROOT_KEY` was not configured correctly during community version deployment, causing the account management interface to be blocked.

## How to confirm the configuration is correct
- Execute the container status check command to confirm that all associated databases, caches, and application containers are running normally.
- Initiate a simulated data synchronization request, pass preset billing field data, and verify that the stored field mapping matches the configuration.
- Access the frontend address corresponding to `FE_DOMAIN`, log in to the system backend, and check whether the configured data source connection status loads normally.
- Trigger a daily data synchronization task, check that there are no connection errors or data parsing exceptions in the system logs.

The values provided are common starting points and should be measured against the reader's own samples.
