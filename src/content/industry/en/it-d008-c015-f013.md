# Operations on Duty and Internal Ticket Q&A for Product Usage Data Analysis: Permission and Data Isolation

## What this category’s data looks like
This category’s data primarily comes from tracking systems, data warehouses, CRM, and internal ticket systems. Update cycles are typically daily or weekly. Regularly produced documents include usage analysis reports, tracking plans, indicator caliber tables, and dashboard requirement forms. Data fields include user identifiers, functional modules, operation duration, ticket circulation status, and more. Units are mostly times, minutes, and entries. Some indicators require unified conversion based on business calibers.

## What constraints do these characteristics impose on permission and data isolation?
Data sources cover multiple business systems and include user sensitive identifiers. Permission isolation must accurately match business ownership. Daily or weekly batch data updates require permission configurations to support batch verification. This prevents cross-permission data from being loaded in a single operation.
In operations on duty scenarios, usage data from different clusters must be isolated by business ownership. This stops non-responsible personnel from viewing core operation and maintenance indicators.
In internal ticket Q&A scenarios, only team members can access data analysis results associated with corresponding tickets. This prevents cross-departmental data leaks.
Unified indicator calibers require permission configurations to link to business groups. This ensures only authorized personnel can modify caliber configurations.

## How to configure settings
The following configurations are based on FastGPT v4.17.0. Specific parameters can be adjusted per actual business needs.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Team data isolation identifier | Bind `teamId` to the business cluster dimension | Match data analysis isolation requirements for different clusters in operations on duty scenarios, preventing cross-cluster data unauthorized access |
| Member access permission binding | Link `tmbId` to team roles | Enable only corresponding team members to access data analysis results associated with tickets in internal ticket Q&A scenarios |
| Unauthenticated link quantity limit | 10-100 | Adapt to internal usage scales of different teams, preventing data leaks caused by link abuse |
| Session expiration time | 1800-3600 seconds | Balance internal usage convenience and data security, preventing unauthenticated links from remaining valid for long periods |
| Data range verification threshold | Calibrate based on actual measurements | Adapt to indicator calibers and data volumes of different businesses, preventing misjudgment of permission ranges |

## Three common configuration errors
- Symptom: The interface prompts "No permission to operate this conversation record". Cause: The current user's `tmbId` is not bound to the team to which the conversation belongs, resulting in permission verification failure.
- Symptom: A quantity overlimit prompt triggers when creating an unauthenticated link. Cause: The unauthenticated link quantity limit configuration is not adjusted. The default value does not match the team's actual usage needs.
- Symptom: Cross-team members can view data analysis reports from non-affiliated clusters. Cause: Data isolation rules are not configured via `teamId`, resulting in overly broad permission coverage.

## How to confirm successful configuration
- Use an account from an unauthorized team to access the data analysis report of a specified cluster. Confirm normal viewing is not possible.
- Create unauthenticated links. Test creating links exceeding the configured quantity limit. Confirm the corresponding error prompt triggers.
- Check data analysis results associated with internal tickets. Confirm only members of the corresponding team can access the corresponding content.
- Wait beyond the set session expiration time. Attempt to use the old unauthenticated link. Confirm continued access is not possible.
