# Operational On-Call and Internal Ticket Q&A for Product Usage Data Analysis: Deployment and Upgrade

## What data for this category looks like
Typically, data for this category comes from four sources: tracking systems, data warehouses, CRM, and ticket systems. Updates follow a daily or weekly batch synchronization schedule. Daily associated documents include usage analysis reports, tracking plans, indicator caliber tables, and dashboard requirement forms. Data fields include function usage frequency, customer unique identifiers, operation duration, ticket circulation status, and more. Common units are times, days, minutes, entries, and others. The overall output provides cross-customer insights into functional usage behavior, focusing on global analysis of feature usage.

## Constraints on deployment and upgrade
Because data sources involve multiple heterogeneous systems, cross-source data connection parameters must be configured during deployment. This ensures permission and connectivity for each data source. Data is updated in daily or weekly batches, so scheduled synchronization rules must be configured during deployment. This avoids synchronization conflicts or delays. The indicator caliber table is a core configuration item. During upgrades, the original caliber mapping logic must be retained. This prevents incorrect indicator judgments. Data anomaly troubleshooting relies on original tracking and ticket data. Sufficient storage and computing resources must be reserved during deployment to support batch data verification.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Use the production environment exclusive replica set connection string, formatted as `mongodb://user:pass@host1:port1,host2:port2/dbname?replicaSet=rs0` | Ticket and tracking raw data for this category is stored in MongoDB collections; replica sets ensure high availability |
| `PG_URL` | Use the PostgreSQL read-only connection address associated with CRM and indicator caliber tables, with exclusive business account permissions | This category requires association with CRM data at the customer dimension and standardized indicator caliber configurations |
| `REDIS_URL` | Use an exclusive Redis instance on port 6379, with memory configuration no less than 2048 MB | Cache frequently queried indicator calibers and user session data to reduce multi-source query pressure |
| `DB_MAX_LINK` | Use `20–30` | Adapt to concurrent connection requirements for multiple data sources, avoid synchronization failures caused by connection pool exhaustion |
| `STORAGE_S3_ENDPOINT` | Use the access address of the enterprise’s self-built object storage, for example `https://s3.internal.example.com` | Store batch-exported usage analysis reports and archived raw tracking data |
| `ROOT_KEY` | Generate a random 32-bit string according to the FastGPT v4.17.0 deployment guide | Ensure access security for internal management APIs and prevent unauthorized operations |

## Three common misconfigurations
- Data insertion fails after deployment, with authentication failure or connection timeout errors returned in the interface. Cause: Write permissions for `PG_URL` or `MONGODB_URI` are not correctly configured, and a read-only account is used to attempt writing tracking and ticket data.
- Long text analysis returns irrelevant answers, with output results deviating from preset indicator calibers. Cause: The configuration logic of the indicator caliber table is not associated, and standardized mapping of indicator descriptions in long text is not performed, leading to model recognition errors.
- Data synchronization tasks fail after upgrade, with update delays exceeding preset cycles. Cause: The original `DB_MAX_LINK` configuration was not retained during upgrade, and the new environment’s connection pool threshold is too low to support concurrent requirements for multi-source data pulling.

## How to confirm proper configuration
- Run the FastGPT v4.17.0 built-in data source connectivity test tool to verify that the connection status of `MONGODB_URI` and `PG_URL` is normal, with no authentication failure or timeout errors.
- Trigger a manual data synchronization task to check that raw data for corresponding fields can be pulled from tracking systems and CRM, with no batch null values or format exceptions.
- View the mapping configuration of the indicator caliber table to confirm that it has been associated with the query logic of the analysis dashboard, and that standardized indicator results can be returned normally.
- Trigger a batch export task to verify that the `STORAGE_S3_ENDPOINT` configuration is valid, and that exported usage analysis reports can be successfully uploaded to the specified object storage path.
