# Operations on-call and internal ticket Q&A for code review and merge management: Deployment and upgrade

## What this category of data looks like
Data for this category originates primarily from Git repositories, CI pipelines, static scanning reports, and defect databases. Daily generated documents include merge requests, code review comments, commit records, and branch strategy descriptions. Each data entry includes fields such as changed code blocks, reviewer tags, commit hashes, and branch association information. Data updates occur daily or in real time alongside code commits. Core data centers on manual review and merge processes for code changes. This differs from automated rule checks in static code scanning, and includes records related to manual business semantic judgment.

## What constraints these characteristics impose during deployment and upgrade
Data sources for this category are scattered and updated in real time with code commits. During deployment, connection permissions and ports adapted for Git repository pulling and CI pipeline log parsing must be configured. During upgrades, the data synchronization link must remain uninterrupted to avoid blocking review processes. The field structure of merge requests and review records may shift as team branch strategies are adjusted. During deployment, configurable options for field mapping must be reserved to prevent process exceptions caused by missing fields. Data update frequency is high, so sufficient concurrent processing resources must be configured during deployment. Upgrades must use rolling update methods to prevent internal ticket backlogs caused by full restarts. Data anomalies will directly lead to severe consequences. During deployment, alarm linkage configuration for defect databases must be integrated. Before upgrades, full review and merge data must be backed up.

## How to configure settings
The following configuration instructions are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `80–150 connections` | Adapts to concurrent query demands from real-time code commits, prevents database connection pool exhaustion |
| `REDIS_URL` | `redis://:custom password@intranet Redis address:6379/1` | Stores temporary review caches, merge request statuses, and user sessions. Intranet deployment ensures data security |
| `STORAGE_S3_ENDPOINT` | `Intranet object storage service address` | Stores large files such as merge request attachments and review comment attachments, adapts to internal team storage rules |
| `ROOT_KEY` | `Randomly generated 32-bit string` | Configures the system's highest privilege access key, prevents security vulnerabilities caused by using default keys |
| `FE_DOMAIN` | `Intranet-deployed IP:port or custom domain name` | Generates review notification links and internal ticket jump addresses, adapts to intranet access scenarios |

## Three common configuration errors
- Issue: `EMFILE: too many open files` error occurs during Docker build. Cause: Maximum file open count limit for Docker containers is not configured, and system file handles are exhausted when processing code review data concurrently.
- Issue: Merge request attachments cannot be read normally after intranet deployment. Cause: `STORAGE_S3_ENDPOINT` is not correctly configured to point to the intranet object storage address, or permission configuration errors prevent access to storage resources.
- Issue: Code review data synchronization delay exceeds acceptable ranges. Cause: `DB_MAX_LINK` configuration value is too low, and the database connection pool cannot support concurrent query requests from real-time commits, leading to data synchronization blocking.

## How to verify successful configuration
- Run Docker image build and container startup commands, check that no error messages related to database connections or storage access appear in startup logs.
- Submit a test merge request, verify that the system can normally pull code changes from the Git repository, generate review tickets, and complete synchronization.
- Access the configured `FE_DOMAIN` address, confirm that the frontend page loads normally and internal ticket jump links are valid.
- Connect to the cache service corresponding to `REDIS_URL`, confirm that temporary review status data can be written and read normally.

The values provided are common starting points and should be measured against the reader's own samples.
