# Operations Duty and Internal Ticket Q&A for Crowdsourced Annotator Management: Reranking and Hybrid Retrieval

## What the data for this category looks like
Data for this category comes primarily from crowdsourcing platform backends, annotation quality statistical reports, annotator training exam records, and financial settlement systems. It serves roles including crowdsourcing platform operators, project supervisors, and quality inspection leads. Daily maintained documents include personnel access rules, standardized training materials, monthly performance reports, and settlement detail lists. Data updates follow daily and monthly schedules. Fields include unique personnel identifiers, annotation task types, pass rates, settlement amounts, training assessment scores, and more. Some data is structured as tables, while other content is stored as plain text documents.

## What constraints these characteristics impose on the reranking and hybrid retrieval link
Multi-source heterogeneous data sources require hybrid retrieval to integrate structured performance data, text-based training documents, and financial settlement data at the same time. It is necessary to balance semantic matching and keyword matching. Real-time daily updated annotation performance data requires the retrieval pipeline to support incremental synchronization. Monthly settlement data must adapt to batch processing needs. Different data formats require the reranking link to adjust weight allocation for structured fields and text fields. This ensures retrieval results for personnel screening and quality ranking align with business logic. It also avoids retrieval deviations caused by inconsistent data formats, and guarantees result accuracy during settlement verification to prevent risks such as incorrect payments, missed payments, and project delays.

## How to set the configuration
This configuration is based on standard parameters for FastGPT v4.17.0:

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `similarity` | 0.78–0.82 | Semantic similarity threshold for matching personnel access rules and performance data |
| `limit` | Top 8 entries | Controls the number of returned results, adapted for rapid response to operation and maintenance tickets |
| `searchMode` | hybrid | Hybrid mode combining vector retrieval and keyword retrieval, adapted for multi-source heterogeneous data |
| `usingReRank` | Enabled | Reranks recalled results to raise the priority of high-match results |
| Recall upper limit | 20 entries | Covers a sufficient set of candidate datasets to avoid missing critical personnel information |

## Three common configuration mistakes
- Issue: Only the single highest-similarity result is returned. Cause: The `limit` parameter was incorrectly set to 1, which truncates multi-source candidate data.
- Issue: Hybrid retrieval response time exceeds 12 seconds. Cause: The initial recall `limit` was not restricted and set too high, and no traffic control was implemented for multi-source data parallel retrieval.
- Issue: GPU memory usage stays steady at 6–7 GB after `usingReRank` is enabled. Cause: The number of candidate entries per rerank batch was not restricted, and bulk calls cause excessive memory usage.

## How to confirm the configuration is properly set
- Check that the `searchMode` parameter is set to hybrid, confirm that retrieval results include both keyword matching and semantic matching content.
- Verify that the `usingReRank` parameter is enabled, confirm that reranked results follow the weight priority of business fields such as personnel performance and qualifications.
- Test that retrieval response time is under 10 seconds, confirm that the hybrid retrieval configuration does not exceed hardware load limits.
- Confirm that the `similarity` parameter is set within the 0.75–0.85 range, confirm that the similarity threshold meets business matching accuracy requirements.

The values provided are common starting points and should be measured against the reader's own samples.
