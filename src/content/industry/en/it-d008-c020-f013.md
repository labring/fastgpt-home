# Vendor and Equipment Arrival Management: Operations On-Duty and Internal Ticket Q&A – Permission and Data Isolation

This page’s configuration is based on FastGPT v4.17.0.

## What This Category of Data Looks Like
Data for this category typically comes from ERP systems, vendor shipping documents, logistics tracking information, and device manufacturer backends. It is regularly associated with four types of documents: purchase orders, arrival acceptance documents, serial number lists, and invoice materials.
Data is updated per order or weekly. Each individual data entry includes fields such as purchaser ID, vendor information, device model, serial number, arrival date, and acceptance status. Some fields are linked to specific project dimensions. There are no unified fixed units, and values are adjusted based on device category and procurement requirements.

## How These Characteristics Impact Permission and Data Isolation
Data is linked by project and sourced from multiple systems. Data must be isolated by project dimension to prevent unauthorized access to cross-project procurement and device information.
The four document types contain content with varying sensitivity levels. For example, purchase orders include quotation information, and serial number lists contain unique device identifiers. Access to corresponding fields must be restricted to project-related personnel only.
Data update frequency varies per order or weekly. Permission configuration must support dynamic binding of permission scopes for single orders or weekly batch updates.
Roles have clearly defined differences in responsibilities. Field-level permissions must be subdivided to match the actual data access needs of positions such as procurement, business, and warehouse management.

## Configuration Recommendations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Bind the fixed `teamId` of the corresponding project | This category of data is linked by project, and `teamId` can accurately divide cross-project data boundaries |
| `tmbId` | Bind the `tmbId` of a single order or 7-day cycle | Data update frequency is per order or weekly, and using `tmbId` matches the permission scope of the corresponding update cycle |
| Field-level permission configuration | Subdivide visible fields by document type | Four document types contain fields with varying sensitivity levels, so role access ranges must be restricted |
| Role permission grouping | Divide into three-level permissions by procurement/business/warehouse | Typical roles have clear differences in responsibilities, so corresponding data access permissions must be matched |
| Permission cache duration | 1800 seconds | Balance data real-time performance and system performance, adapt to the update rhythm of per order/weekly |
| Dynamic permission synchronization | Trigger permission updates per order | Match the characteristics of per-order data updates, ensure permissions and data are synchronized consistently |

## Three Common Configuration Mistakes
- Phenomenon: Historical version data lacks the `tmbId` field, making it impossible to isolate corresponding equipment arrival management data by project. Cause: The `tmbId` field was not completed for existing historical data, and data structure update requirements were not synchronized.
- Phenomenon: Custom plugins in workflows do not display input and output parameters, making it impossible to bind fields related to equipment arrival management. Cause: `teamId` or `tmbId` was not associated in plugin configuration, causing parameters to not be loaded correctly by the system.
- Phenomenon: Multiple accounts cannot join the same team, making it impossible to share arrival data permissions for the same project. Cause: Team permission configuration was not bound to `teamId` by project dimension, causing accounts to fail to match the corresponding data range.

## How to Verify Successful Configuration
- Log in to accounts with different roles, verify that only purchase orders, arrival acceptance documents and other documents corresponding to the project can be viewed.
- Trigger permission verification for a single order, confirm that only accounts bound to the order's `teamId` can access the corresponding data.
- View historical version data, confirm that all documents have completed the `tmbId` field with no missing cases.
- Test workflow plugin calls, confirm that input and output parameters related to equipment arrival management can be displayed correctly.
