# Operations on-duty and internal ticket query for supply chain security and open source dependency governance: Sharing and embedding

## What this category of data looks like
This category of data typically comes from package managers, code repositories, vulnerability databases, and license databases. Update cadence is daily or per version release. Update interval ranges from 1 day to once per version update, as calibrated through actual testing. Daily generated documents include SBOM lists, dependency risk reports, license lists, and repair tickets. Each document contains fields such as dependency package name, version number, vulnerability CVE ID, license type, and repair priority. There are no unified fixed units; only actual attributes of dependent assets are used for labeling. Data volume fluctuates with code repository scale. Core time-consuming steps focus on dependent asset identification, vulnerability version matching, and upgrade impact assessment. This page is compatible with FastGPT v4.17.0. The `shareId` of a sharing link is generated by the system, used to identify the sharing entry, and cannot be bound to exclusive business data.

## What constraints do these characteristics impose on the sharing and embedding link
The core data of this category includes sensitive information such as high-risk vulnerabilities and license compliance requirements. The sharing and embedding link must strictly restrict access scope, and only allow internal operations and R&D teams to access. Data updates occur at a high frequency. The embedded query context must synchronize the latest dependency risk reports and repair ticket content updated by external systems. The field structure of documents such as SBOM lists is complex. Embedded components must support precise matching of specific fields such as dependency package names and version numbers to avoid generalized responses. Relevant capabilities are provided by the corresponding knowledge base or external system. Query responses for operations on-duty scenarios must be associated with real-time ticket status. Embedded scenarios must adapt to authorized identity verification logic. Identity verification integration with third-party systems is only supported in commercial editions. Sharing entries must be used in authorized scenarios. The `shareId` cannot be used as the sole authorization basis.

## Three Common Mistakes
- Sharing entries for supply chain security and open source dependency governance fail to open. First verify the complete system-generated link and its validity period, then cross-check browser request status. Do not manually replace `shareId`.
- The visible scope of supply chain security and open source dependency governance data does not match expectations. Cross-check third-party identity verification results, workflow request parameters, and external system data permissions respectively. The sharing entry identifier itself does not provide business authorization.
- The same supply chain security and open source dependency governance query is not visible on another device. For anonymous scenarios, first check device, browser, and local identity status. Retention is not guaranteed across devices or after cache clearing. Do not use this phenomenon alone to judge service anomalies.

## How to Confirm Successful Configuration
- Access the sharing link, verify whether internal identity verification is required, and confirm that permission control configurations are active.
- Initiate a query containing dependency package names and vulnerability IDs, verify that returned results include the latest SBOM lists and risk report content.
- Verify that conversation records comply with local identity storage rules, confirm that records cannot be retained across devices or after browser cache clearing, and verify that identity association configurations are working correctly.
- Attempt to embed components on an unauthorized domain name, verify that query content fails to load, and confirm that domain whitelist configurations are active.
