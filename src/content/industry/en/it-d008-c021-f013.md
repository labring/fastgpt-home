# Operations On-Duty and Internal Ticket Q&A for Supply Chain Security and Open Source Dependency Governance: Permission and Data Isolation

## What Data Looks Like for This Category
Data for this category primarily comes from package managers, code repositories, vulnerability databases, and license databases. Updates occur daily or when new versions are released. Daily generated documents include SBOM lists, dependency risk reports, license lists, and repair tickets. Core fields include dependency package names, version numbers, vulnerability CVE IDs, license types, repair priority levels, and impact scopes. Data is stored and grouped by project or business domain.

## Constraints Imposed on Permission and Data Isolation
Data grouped by project or business domain requires permission isolation tied to specific business scopes. This prevents cross-team data leaks.
Frequently updated dependency risk data needs permission checks embedded in all data reading and update workflows. This blocks access requests from expired permissions.
Documents containing high-risk vulnerability details and license compliance information require permission granularity refined to individual reports or single dependency categories. Coarse-grained team-based permissions do not meet protection requirements.
Repair tickets linked to R&D and security team tasks require permissions aligned with a role’s responsibilities. Only authorized personnel can handle corresponding tickets.

## Configuration Settings
Configurations below are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Team Data Isolation Identifier | `teamId` | Matches the data grouping by project or business domain feature, binds SBOM and risk reports for the corresponding business |
| Permission Check Timing | Before data reading, before ticket submission | Targets frequently updated dependency data, blocks unauthorized access in real time |
| Fine-Grained Permission Granularity | Individual dependency risk report, license list | Meets sensitive data protection requirements, prevents cross-team access |
| Global Variable Isolation | Isolate duplicate-named variables by `teamId` | Resolves conflicts between duplicate global variables across different teams |
| Team Data Storage Partitioning | Divide storage partitions by `teamId` | Optimizes data query efficiency while strengthening physical isolation |
| Permission Check Timeout Threshold | 30 seconds | Adapts to real-time response needs for operations on-duty, avoids workflow blocking |

## Three Common Misconfigurations
- Symptom: Non-commercial edition users cannot get SSO functionality to work after configuration. The interface displays an insufficient permissions prompt. Cause: The user did not confirm that SSO is only supported in the commercial edition, and incorrectly configured related parameters in the open-source edition.
- Symptom: After configuring `teamId` to bind permissions, some repair tickets cannot be viewed by corresponding team members. Cause: The `teamId` field of the ticket was not aligned with the configured isolation identifier, leading to mismatched permission checks.
- Symptom: Duplicate-named global variables across different teams overwrite each other’s values. Cause: The configuration to isolate global variables by `teamId` was not enabled, so global variable scopes were not divided by team.

## How to Verify Successful Configuration
- Log in to accounts corresponding to different `teamId` values. Confirm that only SBOM lists and dependency risk reports for the corresponding team are visible.
- Submit an internal repair ticket. Verify that only authorized roles can modify the ticket status and processing progress for the corresponding `teamId`.
- After configuring duplicate-named global variables, switch to accounts for different teams. Confirm that variable values do not interfere with each other.
- Simulate a high-frequency data reading scenario. Verify that permission checks complete within 30 seconds, with no workflow blocking.
