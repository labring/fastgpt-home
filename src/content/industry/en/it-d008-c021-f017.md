# Operations On-Duty and Internal Ticket Q&A for Supply Chain Security and Open Source Dependency Governance: Deployment and Upgrade

## What this category's data looks like
Core data for this category comes from package managers, code repositories, public vulnerability databases, and license databases. Updates occur daily or upon each version release.
Daily output documents include SBOM lists, dependency risk reports, license compliance lists, and repair tickets. Fields include component name, version number, vulnerability CVE ID, license type, risk level, and repair suggestions. There are no fixed statistical units; asset and risk information is only recorded per component.
Data association logic must match component versions and vulnerability impact scopes, which imposes high requirements for storage and query performance.

## What constraints do these characteristics impose on deployment and upgrade
Data for this category is pulled from multiple external interfaces. During deployment, stable database and cache connections must be configured to ensure uninterrupted pulling and parsing of daily incremental updates.
SBOM and risk report generation relies on component version matching logic. During upgrades, compatibility with original dependency identification rules must be maintained to avoid missing asset identification due to configuration changes.
Internal tickets are linked to repair workflows. Deployment must support lightweight integration with existing operational ticket systems, while reserving parameter adjustment space to adapt to dependency asset libraries of varying sizes.
High-risk dependency blocking logic must be solidified during deployment to prevent risk exposure or compliance issues caused by configuration oversights.

## How to configure settings
This document applies to FastGPT v4.17.0. Below are recommended values and supporting rationale for core configuration items:

| Configuration Item | Recommended Value | Basis for This Setting |
| --- | --- | --- |
| `MONGODB_URI` | Replica set connection string with authentication information | This category needs to store large amounts of SBOM and vulnerability association data. The replica set mode ensures high availability, and authentication information prevents unauthorized access |
| `REDIS_URL` | Connection string for a dedicated cache instance with 8 GB memory limit | Used to cache dependency version matching results and vulnerability query results. 8 GB can support cache hit requirements for millions of components daily |
| `DB_MAX_LINK` | 20–30 | Adapts to concurrent pull requests for daily incremental updates, avoiding task interruptions caused by exhausted database connections |
| `FE_DOMAIN` | Public or internal domain name of the deployment instance | Used to generate jump links for internal tickets, ensuring operations staff can directly access the corresponding dependency repair page |
| `FILE_TOKEN_KEY` | Randomly generated string of 32 or more characters with no special characters | Used to encrypt download links for dependency reports, preventing unauthorized access to sensitive compliance documents |
| `ROOT_KEY` | Only configured during initial deployment, adjusted via the permission management page in subsequent steps | Used to initialize the platform's super administrator permissions, avoiding security risks caused by long-term exposed configuration |

## Three common configuration errors
- Dependency asset identification tasks remain in the indexing state: The platform page shows the task as incomplete with no progress updates. This occurs when `REDIS_URL` is not configured, connection parameters are incorrect, or external data source access keys are not properly set up. This prevents the cache from storing intermediate identification results or pulling dependency data, halting task progress.
- Locally deployed rerank models do not appear on the platform: No new model entries are displayed on the model management page. This happens when interface authentication parameters are not correctly configured, and the required Bearer prefix is omitted, blocking requests and preventing model registration from completing.
- Login and sharing ports are not separated during offline deployment: The login-free sharing link can directly access the platform login page. This occurs when the port configuration corresponding to `FE_DOMAIN` is not modified, causing the sharing service and login service to bind to the same port and leading to permission leaks.

## How to confirm correct configuration
- Run a manual dependency asset identification task, and check task logs for errors related to database connection timeouts or cache read failures.
- Generate an internal dependency repair ticket, click the report download link in the ticket, and verify that a valid `FILE_TOKEN_KEY` parameter is required to access the document.
- Log in to the platform permission management page, and confirm that `ROOT_KEY` is only bound to the initialized administrator account, with no other public or temporary permissions.
- Restart the deployment service, and use the system monitoring panel to check that the `DB_MAX_LINK` configuration matches the set value.

The values provided are common starting points and should be evaluated against the reader's own samples.
