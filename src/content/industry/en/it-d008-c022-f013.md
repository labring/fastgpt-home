# Operations Duty and Internal Ticket Q&A for Independent Innovation Replacement Adaptation: Permission and Data Isolation

This document is written for FastGPT v4.17.0.

## What the data for this category looks like
This category’s data is generated for independent innovation software and hardware replacement adaptation scenarios. Daily produced documents include adaptation lists, compatibility test reports, migration plans, and issue ledgers. Data sources include existing inventory system lists, official directories of domestic software and hardware, test environment operation records, and publicly available vendor materials. Data updates follow individual independent innovation replacement project cycles, or synchronize the latest domestic software and hardware directories and adaptation verification results quarterly. Data fields include system model, adaptation version, compatibility score, migration risk level, and others. There are no unified fixed units; values adjust based on document type and project requirements.

## What constraints do these characteristics impose on permission and data isolation
Data in this category involves sensitive IT resources such as inventory systems and compatibility test reports. Adaptation data from different project teams must be strictly isolated to prevent cross-project configuration and plan leaks. Data updates occur at the project or quarterly level. Permission configurations must adapt to the lifecycle of a single project. No frequent adjustments are needed, but permissions must be accurately bound to the project’s ownership. Daily documents include highly confidential migration plans and risk assessment content. Access permissions for different roles, such as architects and testers, must be subdivided by job responsibilities. Only the data scope required for their respective workflows is exposed, to prevent unauthorized users from accessing sensitive information.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Bind to the exclusive team ID of a single independent innovation adaptation project | Strictly binds adaptation data and knowledge base resources to the corresponding project, preventing cross-project resource leaks |
| Knowledge base access scope | Restricted to the adaptation document collection for the corresponding project, no larger than 200 MB | Total size of documents such as adaptation lists and test reports varies with project scale; set based on the measured project data upper limit |
| API call permissions | Only open to the operation and maintenance duty account bound to the project, single call limit of 10 results, validity period set to 7–30 days aligned with project cycle | Meets the temporary call requirements of the operation and maintenance duty scenario, preventing abuse if API keys are leaked |
| Team member management | Only allow the project lead to add or remove members, maximum 5 members added at a time, revoke all resource permissions when removing | Ensures permissions are updated synchronously when team member changes occur, preventing permission loopholes left by resigned or transferred personnel |
| `tmbId` | One-to-one correspondence with `teamId`, cannot be reused across projects | Ensures each project’s knowledge base resources and team permissions are strictly bound, preventing cross-project data access |

## Three common mistakes
- Symptom: API call returns "No permission" error, with status code 403. Cause: API call permissions are not bound to the corresponding `teamId`, or the correct team identification parameter is not included in the call.
- Symptom: Cross-project members can view adaptation documents that do not belong to them. Cause: The knowledge base access scope is not divided by `teamId`, and documents from multiple projects are merged into the same knowledge base.
- Symptom: After a team member is removed, they can still access project knowledge base resources. Cause: Member permission configurations were not revoked synchronously, only the member information in the team list was deleted.

## How to confirm configurations are correct
- Log in to the FastGPT backend, enter the team management page for the corresponding `teamId`, check that member permission groups are divided by role, with no over-privileged configuration items.
- Call the test API using an account not bound to the project, confirm that a "No permission" error is returned.
- Import a single adaptation list document, check that only members of the corresponding permission group can view and edit the document, while users from other groups cannot access it.
- Check that relevant team isolation configuration settings in the locally deployed FastGPT configuration file are enabled. After removing a test team member, confirm that the member can no longer access any knowledge base resources within the team.
