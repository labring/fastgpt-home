# Operations on Duty and Internal Work Order Q&A for Independent and Controlled Software and Hardware Replacement: Deployment and Upgrade

## What Data for This Category Looks Like
The data for this category comes from enterprise existing IT system inventories, official directories of domestic software and hardware, project test environments, and publicly available manufacturer materials.
Daily produced documents include adaptation lists, compatibility test reports, migration plans, and problem ledgers.
Common fields include software and hardware model, adaptation status, compatible version, test result, and risk level.
Data update frequency is per project or per quarter.
It is dynamically adjusted with version iterations of domestic software and hardware, and results of stock system inventory.

## Constraints on Deployment and Upgrade Links
Data sources are scattered and require adaptation to multiple types of domestic software and hardware.
Configure multi-source data import rules in advance during the deployment phase to avoid errors from manual entry.
The data update rhythm adjusts with project progress.
Synchronously adapt to the latest domestic software and hardware versions during the upgrade phase.
Reserve a time window to conduct compatibility verification.
The stock system inventory process takes a long time.
Preload the adaptation list before deployment to reduce repeated verification.
Business interruption risk is high in independent and controlled software and hardware scenarios.
Use a gray release strategy during the upgrade phase to avoid service unavailability caused by full switching.

## How to Set Configurations
The following configurations are based on the deployment specifications of FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---|---|--- |
| `DB_MAX_LINK` | `20–30 connections` | The data volume of operation and maintenance work orders and adaptation documents fluctuates greatly in this adaptation scenario. This requires a reasonable upper limit for the database connection pool. |
| `REDIS_URL` | `Local Redis instance address, port 6379` | Internal work order Q&A requires caching session records and adaptation rules. Local deployment reduces intranet access latency. |
| `STORAGE_S3_ENDPOINT` | `Domestic object storage service address, such as 192.168.1.100:9000` | Independent and controlled software and hardware scenarios must avoid overseas storage dependencies. Adapt to domestic compliant object storage services. |
| `FE_DOMAIN` | `Enterprise internal domain, such as internal.oa.com` | Deployed on the enterprise intranet. Match the unified domain rules for internal access. |
| `FILE_TOKEN_KEY` | `32-bit random string calibrated through actual testing` | Ensure the security of upload, parsing, and storage permissions for adaptation documents. |
| `ROOT_KEY` | `One-time key only used for initial configuration, disabled after deployment` | Strictly control the highest system operation permissions in independent and controlled software and hardware scenarios. |

## Three Common Mistakes
- Phenomenon: Some tables in uploaded adaptation documents cannot be properly chunked. A parsing failure prompt appears on the interface. Cause: The document parsing rule for independent and controlled software and hardware adaptation is not enabled. The default parsing logic is not compatible with special table formats generated by domestic office software.
- Phenomenon: A maximum retry times error triggers when calling the knowledge base interface. The log shows `Reached the max retries`. Cause: The `DB_MAX_LINK` parameter is not adjusted according to intranet network fluctuations in the independent and controlled software and hardware scenario. Connection pool exhaustion causes retry limit to be exceeded.
- Phenomenon: After locally modifying the configuration and redeploying via Docker, the service cannot load adaptation rules. Cause: The locally modified configuration file is not mounted to the corresponding directory of the Docker container. The configuration does not take effect after deployment.

## How to Confirm Configuration is Successful
- Log in to the front-end interface. Access the internal domain configured in `FE_DOMAIN`. Confirm that the operations on duty and internal work order Q&A page loads normally.
- Perform a database connection test. Check that the number of connections does not exceed the value range configured in `DB_MAX_LINK`. No connection timeout or disconnection errors appear.
- Upload an adaptation document containing tables. Confirm that chunking is successful and no parsing errors occur. Knowledge base entries can be generated normally.
- Restart the service. Check that the cache instance configured in `REDIS_URL` can normally write session data. No cache write failure logs appear.
