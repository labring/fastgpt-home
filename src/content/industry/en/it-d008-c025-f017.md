# Duty Scheduling and Handover Scenario: Operations on Duty and Internal Work Order Q&A — Deployment and Upgrade

## What the Data for This Scenario Looks Like
This scenario’s data sources include enterprise scheduling systems, fault work order libraries, monitoring alert platforms, and organizational contact lists. Data updates run daily or weekly. Core documents include duty schedules, handover records, escalation contact lists, and daily duty reports.
Duty schedule fields include duty date, on-duty personnel, contact phone number, and duty time period. Handover records include pending items, follow-up status, and liaison personnel. Escalation contact lists include contact information and responsibility scope for all levels of operations and maintenance leads.

## Constraints During Deployment and Upgrade
Since data sources involve multiple internal systems including enterprise scheduling systems, fault work order libraries, monitoring alert platforms, and organizational contact lists, configure API permissions and interface addresses for connecting each system during deployment. This ensures data such as duty schedules and handover records can be synchronized to the knowledge base.
Data updates run daily or weekly. Configure the trigger cycle for scheduled synchronization tasks during deployment. Avoid excessive synchronization frequency that consumes system resources, or insufficient frequency that causes data lag.
The field structure of core documents is fixed. The knowledge base import template must strictly match the corresponding fields, otherwise data import will fail.
Errors in this scenario directly affect operations and maintenance response efficiency. Configure highly available service redundancy during deployment, to avoid single-point failures preventing on-duty response.

## Three Common Deployment Mistakes
- Symptom: When deploying locally with Docker, a "network unreachable" error appears after executing the pull command, and the image pull fails. Cause: The enterprise internal image acceleration address is not configured, or firewall rules restrict access to external image repositories.
- Symptom: When uploading PDF files such as duty schedules and handover records to the knowledge base, the upload progress reaches 90% and then an "offset out of range" error pops up. Cause: File shard verification fails due to incorrect configuration of `FILE_TOKEN_KEY`, or the storage node corresponding to `STORAGE_S3_ENDPOINT` has insufficient remaining space.
- Symptom: After private deployment is complete, internal work order Q&A cannot be bound to the duty scheduling function, and triggered Q&A has no response. Cause: The operations and maintenance work order database corresponding to `PG_URL` is not correctly associated in the deployment configuration, or the `ROOT_KEY` permission configuration is insufficient to call internal interfaces.

## How to Verify Successful Configuration
- Execute the local image pull test command, confirm that there are no network errors in the image pull process.
- Upload a test duty schedule PDF file, confirm that there are no abnormal errors after the upload progress completes.
- Submit a test duty work order, verify that the internal Q&A function can trigger normally and return results.
- Check the deployment node logs, confirm that the connection status of the database, storage, and cache services is normal, with no abnormal errors.
