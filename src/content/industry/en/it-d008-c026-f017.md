# Operations On-Duty and Internal Ticket Q&A for Level Content Creation: Deployment and Upgrade

## What data for this category looks like
Usually, data for level content creation teams comes from level editors, art resource libraries, player test data, and defect tracking systems. Daily produced documents include level design drafts, resource requirement lists, test feedback sheets, and version submission records. Document fields typically include level ID, resource path, test node, submission version number, and similar items. Update frequency is weekly or per version iteration. Data is generated around specific maps and mission rules, differing from other game development categories that focus on numerical values and rule frameworks.

## Constraints on Deployment and Upgrade Posed by These Characteristics
High-frequency version updates and multi-type document data for level content creation require the deployment process to support lightweight version rollback mechanisms. This prevents level data anomalies caused by version upgrades. Data sources are scattered across editors and resource libraries. Deployment must configure cross-source data access permissions. This ensures internal ticket Q&A can pull full-link documents. A single update involves a large number of level resources and test feedback. Post-deployment verification must cover scenarios like resource path matching and version number synchronization. This prevents launch delays or level blockages caused by configuration oversights. Additionally, the team’s need for multi-account collaboration requires configuring appropriate permission isolation and team management parameters during deployment. This ensures level data isolation between different planners.

## Configuration Settings
This page’s configurations are based on FastGPT v4.17.0. A server with at least 2 CPU cores and 4000 MB of memory is recommended.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–150 connections` | Adapts to concurrent access demands when multiple teams submit level data and test feedback, preventing database connection exhaustion |
| `MONGODB_URI` | Points to a dedicated MongoDB instance storing level design drafts and version submission records | Isolates game business data from general operations data, preventing document leaks caused by permission cross-over |
| `PG_URL` | Points to a local PostgreSQL instance for storing team permissions and ticket data | Ensures independent data storage for internal operations and ticket systems, avoiding confusion with business data |
| `REDIS_URL` | Configured as a local private Redis service with a memory quota of `2000 MB` | Caches frequently accessed level resource paths and test feedback data, reducing database query pressure |
| `FE_DOMAIN` | Enter the dedicated operations on-duty page domain for your team, such as https://fastgpt-game-dev.com | Ensures internal ticket Q&A redirect links point to the correct team deployment address |
| `ROOT_KEY` | Generate a random 32-character string | Acts as the backend highest-privilege verification key, limiting the scope of operations for internal operations staff |
| `FILE_TOKEN_KEY` | Generate a random 64-character string | Used to generate temporary tokens for level resource access, ensuring access security for the art resource library |
| `STORAGE_S3_ENDPOINT` | Points to the storage endpoint of your team’s self-built art resource library | Directly pulls art resource data required for level creation, reducing latency across storage services |

## Three Common Configuration Errors
- After deploying a new version, accessing `FE_DOMAIN` returns a 404 status code. This occurs when the `FE_DOMAIN` parameter is not correctly configured, causing front-end static resources to not bind to the correct domain path.
- Multiple accounts cannot be created, and no response occurs after adding data to a table. This is caused by incorrect configuration of `PG_URL` or `REDIS_URL`, leading to abnormal user permission and team data storage links.
- Ticket Q&A experiences timeouts when loading level data. This happens when the database connection count is not configured per the `DB_MAX_LINK` recommendation, or the memory quota of `REDIS_URL` is insufficient, leading to cache failure.

## How to Confirm Configuration Completion
The following verification steps are based on the FastGPT v4.17.0 deployment process:
- The configured `FE_DOMAIN` is accessed to confirm the operations on-duty page loads normally, with no 404 or 502 errors.
- The backend is logged into, and `ROOT_KEY` is used to verify permissions, confirming that highest-privilege operations can be executed normally.
- A test ticket is submitted, and an attempt is made to pull associated data from a local level design draft, confirming that storage service and database links function properly.
- Multi-account login is simulated, confirming that team permission isolation takes effect for different accounts, and those accounts cannot access level data from other teams.
