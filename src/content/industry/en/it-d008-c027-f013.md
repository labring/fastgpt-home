# On-Duty Operations and Internal Ticket Q&A for Content Review Rules: Permissions and Data Isolation

This document is written for FastGPT v4.17.0.

## What Data Does This Category Include
This category’s data comes from four main sources: content review backend, user reporting channels, public regulatory policy documents, and annotation sample libraries.
Core daily maintenance documents include review rule entries, violation handling guidelines, user appeal records, and quarterly quality inspection reports.
Data updates occur either daily or immediately when policies or regulations change. Review rules and annotation sample libraries are adjusted and updated alongside the platform’s content ecosystem.
Data fields include rule effective scope, violation judgment thresholds, appeal processing progress, and quality inspection scores. There are no uniform fixed units; values vary based on document type and business process.

## Constraints for Permissions and Data Isolation
Data in this category includes core content security rules, user privacy appeal records, and operational quality inspection results. Permissions and data isolation must align with the responsibility boundaries of different roles.
Review rule modification permissions must only be granted to the rule operations team. This prevents unauthorized personnel from adjusting violation judgment standards.
Appeal records and quality inspection reports contain sensitive user information. Cross-team unauthorized access to these records must be blocked.
Data updates occur daily or with policy changes. Permission configurations must sync with data range adjustments to prevent old permissions from overriding access restrictions for new data.
Documents for different business links must be tied to dedicated access groups. Permissions for rule explanations and sample judgments must be strictly separated from appeal review workflows. This stops cross-boundary operations.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Bind a dedicated ID per business team | Differentiate rule and data scopes for different content review teams to avoid cross-team data confusion |
| Member Permission Groups | Divide by role: rule operations group, appeal review group, quality inspection group | Align access boundaries with different role responsibilities to restrict unauthorized operations |
| Review Rule Sync Cycle | Sync upon policy changes or daily sync, with sync delay no more than 600 seconds | Ensure permission configurations take effect synchronously with data updates, matching data update frequency requirements |
| Global Variable Scope | Bind `teamId` and user ID | Ensure identically named global variables only take effect within the corresponding team and user scope, resolving cross-user variable leakage issues |
| SSO Login Configuration | Only available to commercial edition users, set session timeout to 3600 seconds | Match permission isolation requirements for commercial editions, addressing user questions about SSO feature usage |
| Team Switch Storage | Store current team context based on `tmbId`, cache validity period set to 1800 seconds | Ensure data isolation takes effect after switching teams, and business data for the corresponding team loads correctly |

## Three Common Configuration Errors
- Symptom: When logging in with accounts from different teams, the interface displays review rule entries that do not belong to the current team. Cause: `teamId` is not used as a data isolation identifier, resulting in unpartitioned storage of rule data across teams.
- Symptom: When logging in with different user accounts, values of identically named global variables leak across users. Cause: Global variable scope is not bound to `teamId` and user ID, and isolation configuration based on user ID is not implemented.
- Symptom: Non-operations role members can modify review rule entries after logging in. Cause: Member permission groups are not divided by role, and rule modification permissions are granted to personnel outside the operations role.

## How to Verify Correct Configuration
- Use accounts from different teams to log in. Confirm only review rule and sample library data bound to the corresponding `teamId` is visible.
- Test accounts for different roles. Confirm only members of the matching role permission group can access appeal records or modify review rules.
- Configure an identically named global variable. Use logins with different user IDs to verify variable values are isolated correctly per user.
- Perform team switches. Confirm the current team context updates correctly based on `tmbId`, with no cross-team data remaining.

The values provided here are common starting points, and should be evaluated against the reader’s own samples.
