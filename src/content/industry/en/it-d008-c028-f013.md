# Operations on Duty and Internal Ticket Q&A for Content Recommendation Operations: Permission and Data Isolation

## What this category’s data looks like
The core business data for content recommendation operations includes four types of documents: recommendation strategy records, content pool lists, experiment reports, and operation reviews. Data sources include content tag libraries, user behavior logs, experiment platforms, and recommendation backends. Most updates occur on a daily or weekly basis. Each document contains fields such as content pool ID, tag weight, experiment group, and core indicator values. Field units include counts, days, and others. Cross-document association dependencies exist across the dataset.

## What constraints do these characteristics impose on the permission and data isolation workflow
Sensitive business data from multiple sources requires fine-grained permission division to prevent cross-team strategy leaks or content pool misuse. Frequently updated data needs permission configurations to take effect in real time, to block expired permissions from accessing latest experiment data. Complex document structures and associated fields require layered authorization based on position and team, ensuring only authorized personnel can access content at the corresponding level. Cross-document dependency relationships require isolation scope to cover full-link data, to avoid chain risks triggered by single-point permission breaches.

## How to set the configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` binding rule | Associate with the team's unique system identifier, use the assigned ID of the current team | Divide data access scope by team to achieve cross-team data isolation |
| `tmbId` permission level | Bind to member roles, use three levels: operator, algorithm analyst, administrator | Match permission differences among content recommendation operation positions, control data access granularity |
| Global variable isolation configuration | Name variables by `teamId` + user ID prefix, use `{teamId}_{userId}_var` | Ensure that identical-named global variables take effect independently across different users and teams |
| Team cache expiration time | Use `teamId` as the cache key, use `1800 seconds` | Balance real-time performance of team data and interface call performance |
| Content pool retrieval filtering | Filter retrieval results by the `teamId` to which the content pool belongs, only return content visible to the current team | Prevent cross-team access to unauthorized content pool data |

## Three common configuration errors
- Symptom: Interfaces related to `teamId` return empty team data. Cause: Permission binding between the current user and `teamId` was not completed on the team management page.
- Symptom: Identical-named global variables are visible across users. Cause: The scope of variable isolation by `tmbId` was not configured.
- Symptom: Internal ticket Q&A returns cross-team recommendation strategy documents. Cause: The content pool retrieval filtering rule by `teamId` was not enabled.

## How to verify correct configuration
- Access FastGPT v4.17.0 using accounts linked to different teams, confirm that only recommendation strategy records and content pool lists associated with the corresponding team are visible.
- Call interfaces related to `teamId`, confirm that returned team data matches the team associated with the currently authenticated account.
- Test whether the values of identical-named global variables are independent when the same user assumes different `tmbId` roles.
- Submit an internal ticket to retrieve content pool data, confirm that only content pool information within the current team’s scope is returned.
