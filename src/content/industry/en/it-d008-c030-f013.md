# Operations On-Call and Internal Ticket Q&A for Internal Network and WiFi Maintenance: Permission and Data Isolation

## What Data for This Category Looks Like
The data for this category primarily comes from switch consoles, wireless controllers, office area monitoring systems, and employee user trouble reporting channels. Daily maintenance documents include network topology diagrams, network change orders, troubleshooting records, and wireless coverage inspection reports. Data is updated either via daily synchronization or immediately following network changes. Data fields include device port numbers, VLAN configurations, wireless signal strength, fault occurrence times, processing progress, and other relevant details. Some documents must be associated with specific office areas and device serial numbers.

## Constraints on Permission and Data Isolation
Documents such as network topology diagrams and change orders contain core configuration information for enterprise office networks. Access to this data must be restricted to authorized maintenance personnel only. Wireless coverage inspection data from different office areas must be isolated by region to prevent cross-department maintenance personnel from accessing network configuration data from unrelated areas. Verification data for device ports and VLANs relates to network security boundaries. Only maintenance personnel assigned to the corresponding area must be allowed to operate on this data. User trouble reporting data is associated with specific workstations, so it must be bound to the submitting user’s department to prevent unauthorized personnel from viewing trouble reporting information from other departments. Daily updated monitoring data must be stored divided by team permissions to prevent leakage of sensitive network configuration.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `teamId` | Unique identifier divided by maintenance teams, value range `10001–10005` | Matches the job role assignments of internal enterprise maintenance teams, enabling isolated data access permissions by team |
| `tmbId` | Device group ID bound to office areas, value range `50–200` segmented by region | Matches the maintenance responsibilities divided by office area for this category, preventing cross-region access to unrelated network data |
| Global variable isolation rules | Limit scope by `tmbId`; variables with the same name under different `tmbId`s do not share data | Resolves data conflicts when different maintenance teams use global variables with the same name |
| SSO permission toggle | Enabled for commercial editions, only users verified by binding `teamId` can access | Matches the permission requirements of commercial edition SSO functions, enabling binding verification of identity and permissions |
| Trouble record access permissions | Only allow users corresponding to `teamId` to view trouble records handled by their team | Matches the troubleshooting responsibility scope of this category, preventing unauthorized personnel from viewing sensitive trouble data |
| tokenLogin data storage | Store team data returned by the interface classified by `teamId` | Meets team data storage requirements, ensuring configuration data from different teams does not interfere with each other |

## Three Common Misconfiguration Issues
- Symptom: Cross-team data confusion occurs when different maintenance teams use global variables with the same name, and the viewed variable values do not match expectations. Cause: The global variable scope isolation rule is not configured according to `tmbId`, resulting in the variable scope not being bound to the team identifier.
- Symptom: Non-commercial edition users attempt to enable the SSO function, and the interface prompts insufficient permissions or the function is not available. Cause: The SSO permission configuration for basic and commercial editions is not distinguished, and the function is incorrectly enabled on the basic edition.
- Symptom: Cross-region maintenance personnel view wireless coverage inspection data from areas they are not responsible for, leading to leakage of sensitive configuration. Cause: The device group ID is not bound according to `tmbId`, and cross-region data access permissions are incorrectly opened.

## How to Verify Correct Configuration
- Log in to FastGPT v4.17.0, switch to accounts under different `teamId`s, and verify that only network device data assigned to the corresponding team can be viewed.
- Submit a test ticket, use accounts with different `tmbId`s, and confirm that the values of global variables with the same name do not interfere with each other.
- Call the tokenLogin interface, and verify that the returned team data only includes configuration information corresponding to the current `teamId`.
- Attempt to enable the SSO function in the basic edition environment, and confirm that the interface prompts that the function is not available, which meets the permission isolation requirements.
