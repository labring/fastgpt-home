# Internal Network and WiFi Maintenance: On-Call Operations and Internal Ticket Q&A — Deployment and Upgrade

## What the data for this category looks like
Data for this category typically comes from switch consoles, wireless controllers, office monitoring systems, and user trouble reporting channels.
Daily maintenance documents include network topology diagrams, change orders, fault records, and wireless coverage inspection forms.
Common fields include fault occurrence time, associated device MAC address, VLAN number, and trouble reporter's workstation information.
Data is updated daily or after each maintenance change is completed.
Core data focuses on network access status at office sites and fault troubleshooting results.

## What constraints these characteristics impose during deployment and upgrade
Data sources for this category are mostly enterprise internal private devices and internal trouble reporting channels.
During deployment, private storage or local databases must be adapted to avoid leakage of sensitive network data.
Data updates occur at a high frequency, so database connection parameters must be configured appropriately to prevent high-frequency read and write operations from exhausting server resources.
Daily maintenance documents follow a fixed field structure. Field mapping rules must be preset during deployment to reduce subsequent import configuration workload.
Office network outages directly affect daily work. A complete rollback path must be reserved during the upgrade phase, and cache optimization must be configured to improve system response speed during upgrades.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `15–25` | Matches the high-frequency daily maintenance ticket and fault query requests for this category, avoiding query timeouts caused by insufficient connection counts |
| `MONGODB_URI` | Intranet address pointing to a local private MongoDB instance | Adapts to the requirement that this category's data is stored within the enterprise internal network, ensuring sensitive maintenance data is not leaked |
| `REDIS_URL` | Intranet-deployed Redis instance address, with cache validity set to `300 seconds` | Caches frequently queried network topology and fault records to reduce database load, adapting to the high-frequency data update rhythm |
| `STORAGE_S3_ENDPOINT` | Intranet endpoint for enterprise internal object storage, with a single file maximum size set to `500 MB` | Stores maintenance documents such as inspection reports and fault logs, complying with internal data storage compliance requirements |
| `ROOT_KEY` | Randomly generated high-strength key | Secures access permissions for system backend configuration, preventing unauthorized modification of maintenance-related system settings |
| `FILE_TOKEN_KEY` | Encryption key matching the internal storage | Generates file access tokens to secure download permissions for maintenance documents |

*This configuration applies to FastGPT v4.17.0*

## Three common mistakes
- A database connection error occurs when running the source code local deployment script. The cause is failure to correctly configure `MONGODB_URI` to point to the enterprise intranet database instance, with a public network address used by mistake or access permissions not configured.
- A curl request timeout error is returned when running the upgrade command. The cause is failure to configure a reasonable value for `DB_MAX_LINK` as required. High-frequency maintenance requests exhaust database connections, preventing the upgrade script from making successful calls.
- Some fields fail to load normally after importing a wireless coverage inspection form. The cause is failure to preset field mapping rules. The system cannot recognize custom columns in the inspection form, resulting in data parsing failure.

## How to confirm configuration is complete
- Run a database connection test command to verify that the instance pointed to by `MONGODB_URI` can be accessed normally.
- Submit a simulated maintenance ticket query to check whether the cache response speed meets expectations, verifying that the `REDIS_URL` configuration is effective.
- Upload a test inspection form to check whether all fields load normally, verifying that the field mapping rules are configured correctly.
- Attempt to modify system backend configuration to verify that the `ROOT_KEY` permission check logic is working correctly, preventing unauthorized operations.

The values given are common starting points and should be measured against the reader's own samples.
