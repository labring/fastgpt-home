# Operations On-Call and Internal Ticket Q&A for Creator Onboarding and Verification: Permission and Data Isolation

## What This Category of Data Looks Like
This category of data includes onboarding application forms, scanned identity qualification documents, certification audit records, cooperation agreement files, and similar items. Data sources cover account information submitted via the creator backend, third-party corporate credit query interfaces, account historical operation logs, and archived files from the corporate contract system.
Data updates are mostly triggered by individual applications. Daily maintenance updates audit status and qualification validity periods each day. A single data entry contains fields such as applicant account ID, qualification file hash value, audit node status, and agreement signing time. There are no unified fixed quantitative statistical fields. Only application status and audit results serve as core identification markers.

## Constraints on Permission and Data Isolation
Data for this category is distributed across multiple internal systems and third-party interfaces, and includes sensitive details like identity qualifications and signed agreements. Permission configurations must align with the data source’s ownership scope and sensitivity level.
The data update process, triggered by individual applications, requires permissions to shift dynamically based on application status. Unsubmitted applications are only accessible to the dedicated operations team. Approved applications are made available to the relevant cooperation and docking teams.
Personnel at each audit node can only access data for their assigned tasks, and cannot view uncompleted audit records from other nodes. This prevents information leaks and permission mismatches. Additionally, data fields include account identifiers and agreement content, so permission identifiers must accurately bind data ownership to block unauthorized cross-team access.

## How to Configure
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `teamId` | Bind the unique identifier of the operations team to which the application belongs | Match the team ownership of application data, ensuring only members of the corresponding team can access this set of application data |
| `tmbId` | Bind the exclusive member ID of the current audit node | Restrict audit personnel to only access pending applications assigned to them, preventing cross-node unauthorized access |
| Team permission scope | Divide visible ranges by application status | Unsubmitted applications are only accessible to the operations group belonging to the submitter, while approved applications are accessible to the cooperation and docking group |
| Sensitive data encryption level | 128-bit AES encryption | Match the high sensitivity of qualification materials, preventing leakage of original files during transmission and storage |
| Dynamic permission update | Triggered by application audit node changes, update interval no more than 5 minutes | Adapt to the data update logic triggered by applications, ensuring permissions are automatically adjusted along with audit progress |
| Maximum cross-team access times | 1 time/application | Restrict cooperation teams to only view public information for corresponding applications, preventing unauthorized access to other application data |

## Three Common Misconfigurations
- Issue: An "insufficient permissions" error appears when calling the associated corporate credit information interface, with the prompt "No access permission". Cause: The `teamId` was not bound to the interface call permission configuration, triggering permission interception during cross-team external data source calls.
- Issue: Unauthorized accounts can view full qualification materials for all creator onboarding applications. Cause: No binding relationship was set between `teamId` and a member’s affiliated team, leaving full sensitive data access enabled by default.
- Issue: Audit personnel can view uncompleted application data from other nodes. Cause: No binding rule was configured between `tmbId` and audit nodes, so permissions were not isolated by audit stage.

## How to Verify Proper Configuration
- Access the FastGPT v4.17.0 team management backend, select the target operations team, and verify that only team members can view the associated onboarding application data.
- Submit a test onboarding application, switch to an account with an unbound `teamId`, and confirm that detailed application information is inaccessible.
- Trigger an audit node change for the application, and confirm that the assigned audit personnel’s account only displays pending applications for the current node.
- Review access logs for sensitive qualification files, verifying that only authorized personnel can view complete file content.
