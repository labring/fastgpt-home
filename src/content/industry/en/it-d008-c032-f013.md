# Operations On-Call and Internal Ticket Q&A for Creator Incentive Settlement: Permission and Data Isolation

## What this category's data looks like
Typically, daily documents for this category contain four core types of content: incentive rules, settlement details, appeal records, and payment lists. Data sources include content platform content data, revenue ledgers from advertising sharing systems, payment records from enterprise financial systems, and authorization information from creator account backends. Update cycles are generally monthly or tied to single event cycles. Fields include creator identifier, settlement cycle, amount in yuan, processing status, and some historical data lacks a team identifier field.

## Constraints on permission and data isolation
Data for this category involves creator privacy and financially sensitive information. Different operational roles must be assigned matching access scopes to prevent unauthorized access. In scenarios with multiple parallel operating teams, settlement data must be isolated by team to prevent cross-team viewing of sensitive payment lists and settlement details. Data originates from multiple systems with fixed update cycles. Permission configurations must align with data update cycles to avoid leakage risks from temporary permission changes. Some historical data lacks team association fields. Unaddressed, this will cause permission isolation to fail, leading to settlement data leakage or misalignment.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` binding rule | Automatically map team identifiers based on enterprise organizational structure | Matches the team-based operation scenario of this category, ensuring personnel from the same team can access corresponding settlement data |
| `tmbId` field validation | Enforce field existence check, return 400 status code if missing | Prevents permission isolation failure caused by historical data without `tmbId`, addresses compatibility issues with legacy data |
| Permission role division | Split into three roles: creator operations, financial operations, data operations | Matches daily operational divisions, limits accessible document scopes for different roles |
| Cross-team data isolation | Restrict single accounts to only view data bound to their `teamId` | Prevents cross-team viewing of sensitive financial and settlement information |
| SSO permission mapping | Map enterprise department IDs to `teamId`, with mapping delay no more than 600 seconds | Supports unified authentication integration, ensures team permissions take effect synchronously |
| Historical data completion | Batch complete missing `tmbId` fields, batch size 500–1000 records | Adapts to isolation requirements for legacy data, prevents unauthorized access to historical settlement data |

## Three common configuration errors
- Issue: After local deployment, multiple accounts cannot log in under the same team, and no permission to view settlement detail data after adding it. Cause: The `teamId` binding rule is not configured correctly, and multiple accounts are not mapped to the same team identifier.
- Issue: After SSO integration, team permissions cannot be synchronized, and settlement-related documents cannot be accessed. Cause: Enterprise organizational structure is not mapped to `teamId`, and permission mapping rules do not match the category's team isolation requirements.
- Issue: Cross-team viewing anomalies occur with historical settlement data, and some records lack permission identifiers. Cause: Legacy data lacks `tmbId` fields, no completion or validation blocking is performed, leading to failed permission isolation.

## How to confirm configurations are correct
The following verification steps are performed based on FastGPT v4.17.0.
- Log in to the system with different role accounts, and verify that only documents with matching permissions are accessible. For example, financial accounts can view payment lists, and creator operations personnel can only view appeal records.
- Submit new settlement detail data, and check that the system automatically associates the current account's `teamId` with no missing field errors.
- Import historical data, and verify that records missing `tmbId` are blocked or automatically completed, in compliance with team isolation rules.
- After integrating SSO, verify that enterprise department accounts are automatically mapped to the corresponding `teamId`, with permissions taking effect synchronously.
