# Operations On-Call and Internal Ticket Q&A for Creator Incentive Settlement: Knowledge Base Retrieval and Recall

## What the Data for This Category Looks Like
This category’s core stakeholders include creator operations, financial operations, and data operations roles. Daily maintained documents fall into four categories: incentive rules, settlement details, appeal records, and payment lists. Data sources include content data systems, advertising revenue sharing systems, financial systems, and creator account backends. Updates follow monthly settlement cycles or single event cycles. Document fields typically include creator unique identifiers, settlement cycle numbers, revenue calculation metrics, appeal status, payment amounts, and more. No unified fixed format exists, and field details are adjusted for each settlement activity.

## Constraints on Knowledge Base Retrieval and Recall
Multi-source data access requires retrieval to cover multiple independent datasets. Configure cross-dataset retrieval capability to meet this need. Non-fixed update frequencies mean retrieval must prioritize the most recently synced settlement data, and avoid expired caches. Non-standardized document fields require retrieval configuration to support custom field matching. This prevents generic retrieval from failing to accurately locate settlement-related content. Large individual settlement detail data volumes require controlling the length of retrieved document chunks per call. This avoids exceeding context window limits. Creator settlement questions often use abbreviations or colloquial expressions. Add query expansion support to cover more relevant documents.

## Configuration Recommendations
This configuration recommendation is based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | `0.72–0.80` | Settlement-related questions need high matching accuracy. This avoids interference from low-matching non-settlement content and prevents settlement verification errors |
| `limit` | `Top 8–12 entries` | Settlement details and appeal records typically have many entries. Limiting recalled entries compresses context length while covering core settlement information |
| `searchMode` | `Full-text search` | Meets keyword matching needs for rule-based documents and precise field matching for detailed data |
| `usingReRank` | `Enabled` | Settlement questions need precise sorting of relevant results. Reranking improves display priority for highly matched content |
| `datasetSearchUsingExtensionQuery` | `Enabled` | Creator settlement questions often use abbreviations or colloquial expressions. Query expansion covers more relevant documents |
| `collectionIds` | `Configured according to settlement-related dataset IDs` | Restrict retrieval scope to only target datasets like incentive rules and settlement details. Exclude irrelevant internal documents |

## Three Common Misconfigurations
- Retrieval response timeout: Operational ticket reply delays exceed preset thresholds. The cause is failure to limit retrieval dataset scope via `collectionIds`, while recalling large numbers of non-settlement historical documents. This leads to excessive retrieval load.
- Slower Q&A response after linking the knowledge base: Wait times after triggering Q&A are significantly longer than scenarios without an associated knowledge base. The cause is missing dataset filtering rules, recalling all internal datasets, and not limiting the number of recalled entries via the `limit` parameter. This increases computational load for retrieval and reranking.
- API call error: A 401 unauthorized status code is returned. The cause is the system automatically adding a Bearer token, which conflicts with user-configured authentication information. This causes authentication failure.

## How to Verify Proper Configuration
- Manually enter a settlement-related test question. Check if the matching degree of returned results meets the threshold requirements of the `similarity` parameter.
- View retrieval logs. Confirm only documents from datasets corresponding to the configured `collectionIds` are recalled, with no irrelevant internal content.
- Test API calls. Confirm no additional Bearer tokens are automatically added to request headers, matching the expected configuration.
- Adjust the value of the `limit` parameter. Check if the number of returned results matches the set range.

The values provided are common starting points and should be measured against the reader's own samples.
