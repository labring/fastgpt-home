# Operations On-Call and Internal Ticket Q&A for Creator Incentive Settlement: Deployment and Upgrade

## What the data for this category looks like
Business data for this category typically comes from content data, advertising revenue sharing systems, financial systems, and creator account backends.
Operations staff process daily documents including incentive rules, settlement details, appeal records, and payment lists.
Data updates follow monthly or single-event cycles.
Core data fields include creator ID, revenue metric, settlement amount, appeal status, and payment progress.
Operations staff verify revenue metrics, investigate abnormal fraudulent behavior, and validate payment materials.
The overall process requires cross-verification of data across multiple systems.
Document structure may shift to align with event rule adjustments.

## What constraints these characteristics impose on deployment and upgrade
Since data sources involve multiple business systems, configure multiple data source connection parameters during deployment.
This ensures accurate synchronization of settlement details and advertising revenue sharing data.
Data updates occur monthly or per event cycle.
Set appropriate scheduled task trigger intervals to avoid frequent synchronization consuming system resources.
Settlement documents include structured tables and rule text.
Adjust the adaptation mode of the file parsing module during deployment to improve field extraction accuracy.
Errors directly cause settlement disputes and creator attrition.
Retain a rollback mechanism during the upgrade process.
Configure monitoring alerts to detect data synchronization anomalies in a timely manner.
Internal tickets must link to creator ID and settlement cycle fields.
Configure association rules between tickets and business data during deployment.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `20–30 connections` | Adapts to batch query and synchronization requirements for settlement data, prevents database connection exhaustion |
| `REDIS_URL` | `redis://:custom password@deployment address:6379` | Caches frequently accessed settlement details and appeal records, reduces pressure on the core database |
| `STORAGE_S3_ENDPOINT` | `Fill in according to local storage or cloud storage service provider address` | Stores business files such as payment lists and settlement documents, adapts to storage requirements of different deployment environments, supports single file storage up to 1000 MB |
| Internal ticket association fields | Bind creator ID and settlement cycle fields | Matches the business data association logic of creator incentive settlement, enables quick location of settlement data corresponding to tickets |
| Scheduled task trigger interval | `24 hours` | Adapts to monthly or event-level data update cycles, regularly synchronizes data from advertising revenue sharing and financial systems |
| File parsing mode | Structured document parsing | Adapts to parsing requirements for structured documents such as settlement details and incentive rules, improves field extraction accuracy |

## Three Common Mistakes
- Symptom: After deployment, the file parsing module returns split-related error logs, or core fields are empty after parsing settlement detail documents. Cause: `FILE_TOKEN_KEY` is not configured correctly, causing the file parsing module to fail normal communication with the main service, and unable to complete document content splitting and field extraction.
- Symptom: After executing the upgrade command in a network-free environment, the service fails to start or dependencies are missing. Cause: FastGPT images and dependency packages of the corresponding version were not downloaded offline in advance, and attempts to pull resources online directly resulted in failure.
- Symptom: After upgrading to FastGPT v4.17.0, a prompt that the function is not available appears when attempting to parse settlement detail documents. Cause: The current version’s function configuration was not confirmed, the open-source version deployment logic was mistakenly mixed with commercial version functions, and the corresponding parsing permission was not enabled.

## How to Confirm Proper Configuration
- Execute the service log viewing command to confirm that the connection count configured for `DB_MAX_LINK` does not trigger connection exhaustion alerts, and database connection status is stable.
- Upload a test settlement detail document to check whether core fields such as creator ID, settlement amount, and settlement cycle are correctly extracted from the parsing result.
- Submit a test internal ticket, fill in the creator ID and settlement cycle, confirm that the system can automatically associate the corresponding creator’s historical settlement data.
- In a network-free test environment, import the pre-downloaded upgrade package, execute the upgrade command, then verify that the service starts normally and core functions operate correctly.
