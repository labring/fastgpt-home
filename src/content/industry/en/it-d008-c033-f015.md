# Operations on-duty and internal ticket Q&A for frontend application development: Knowledge base retrieval and recall

## What the data for this category looks like
Data for this category typically comes from code repositories, interface management platforms, design draft systems, and browser compatibility databases. Daily output includes interface documents, component usage guides, joint debugging records, and release lists. Data is updated daily or per version iteration.

Interface documents contain request paths, response status codes, and parameter explanations. Component usage guides include props definitions and version adaptation ranges. Joint debugging records note debug time, issue symptoms, and fix solutions. Release lists record version numbers, change content, and launch time.

## What constraints these characteristics impose on the knowledge base retrieval and recall link
Data is scattered across multiple platforms. This requires the retrieval link to support cross-dataset recall. It must avoid missing valid content from sources such as code repositories and interface management platforms.

Data is updated at high frequency. This requires the recall logic to support incremental synchronization configuration. Retrieval results must always match the latest interface definitions and component versions.

Document structures are diverse. This requires chunking strategies adapted to different content formats. The strategies must retain both structured information of interface parameters and full context of joint debugging records.

Browser compatibility data requires precise matching. This further constrains the retrieval similarity threshold and recall count.

## How to configure the settings
The following configurations are based on FastGPT v4.17.0 knowledge base retrieval logic. They are adapted to frontend application development business scenarios.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.72–0.80 | Adapt to the short text and structured field matching needs of frontend documents, avoid recalling irrelevant compatibility data or outdated version content |
| `limit` | Top 8 entries | Balance the richness of retrieval results and context window usage, adapt to the batch retrieval needs of frontend joint debugging records and interface documents |
| `searchMode` | hybrid | Combine keyword matching and semantic retrieval, cover keyword retrieval of interface paths and semantic matching scenarios of component descriptions |
| `usingReRank` | Enabled | Re-rank recall results from multiple frontend sources, prioritize displaying the latest version of component documents and joint debugging records |
| `datasetSearchUsingExtensionQuery` | Enabled | Automatically expand retrieval queries, supplement synonyms of interface parameters and associated keywords of component versions, improve recall coverage |
| `collectionIds` | Dataset IDs bound to the project | Accurately limit the retrieval scope, avoid recalling frontend document data from unrelated projects |

## Three common configuration errors
- Retrieval result count is far lower than expected, only returning 1-2 entries. The cause is incorrectly setting the `similarity` threshold too high, filtering out a large number of relevant joint debugging records and component descriptions.
- Retrieval results mix outdated component documents and obsolete interface definitions. The cause is not configuring incremental update rules for the dataset, and not enabling the `usingReRank` sorting logic, resulting in old data having higher weight than new data.
- Precise content related to browser compatibility cannot be recalled. The cause is not enabling `datasetSearchUsingExtensionQuery`, failing to automatically supplement associated search terms for device models and versions, resulting in insufficient matching degree.

## How to verify the configuration is correct
- A typical frontend development question, such as "How to call the user information interface", may be selected. Retrieval is executed, and the returned results are checked to confirm whether they include the corresponding interface path and parameter explanations.
- The `similarity` threshold may be manually adjusted. The change in the number of retrieval results is observed, and confirmation is made that the threshold setting meets the matching needs of the current scenario.
- The retrieval log is checked to confirm whether the expansion logic of `datasetSearchUsingExtensionQuery` is triggered, and whether relevant synonym search terms are supplemented.
- The cross-dataset retrieval configuration is verified to confirm that only the current project's `collectionIds` are bound, and no document content from unrelated projects is recalled.

The values given are common starting points and should be measured against samples relevant to the specific deployment scenario.
