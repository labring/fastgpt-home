# Operations On-Call and Internal Ticket Q&A for Frontend Application Development: Reranking and Hybrid Retrieval

## What this category of data looks like
This category of data primarily comes from code repositories, API management platforms, design draft systems, and browser compatibility databases. Daily produced documents include API documentation, component instructions, joint debugging records, and release checklists. Data fields cover API request paths, component parameter definitions, compatibility adaptation versions, and joint debugging issue records, among others. Data update frequency follows a daily or per-release cycle. The length of individual data entries varies significantly: API documentation snippets are typically hundreds of characters, while compatibility records are short entries.

## Constraints on Reranking and Hybrid Retrieval
Frontend development data sources are scattered and updated frequently. Hybrid retrieval must recall code snippets, API documents, and compatibility data simultaneously, and support vector alignment for multi-format data. The mixed structure of short entries and long fragments requires the reranking model to differentiate correlation weights across different data types. The daily update feature requires the retrieval pipeline to support incremental recall, avoiding delays caused by full re-scanning. Retrieval for operations on-call and ticket scenarios must prioritize content related to joint debugging issues and release anomalies. Reranking must adjust the priority of recall results to prevent irrelevant general component documents from interfering with troubleshooting.

## Configuration Guidelines
This configuration recommendation applies to FastGPT v4.17.0, as detailed in the table below.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| Reranking toggle | Enabled | Frontend multi-source heterogeneous data requires filtering low-relevance snippets; reranking improves the accuracy of operations troubleshooting |
| Similarity threshold | 0.70–0.85 | Adapts to the vector distribution range of API documents and code snippets, avoiding missing short entry data related to joint debugging |
| Single recall limit | Top 12 entries | Adapts to the context length of operations on-call scenarios, avoiding exceeding the input limits of general large models |
| Search mode | Hybrid retrieval | Covers both keyword matching and vector similarity, enabling matching of structured fields such as API paths and component names |
| Reranked recall count | Top 6 entries | Prioritizes displaying the most relevant joint debugging records and release checklists, reducing troubleshooting time |

## Three Common Configuration Mistakes
- No change to retrieval result order after enabling reranking toggle: Cause is failure to correctly configure the reranking model's API key or access address, or incompatibility between the reranking model and FastGPT version.
- Unable to select model options when configuring the reranking model: Cause is failure to pre-enter the reranking model's access information in system configuration, or failure to correctly declare the available reranking model list in the configuration file.
- Reranked results not sorted as expected: Cause is an overly high similarity threshold, which filters some potentially relevant short entry data, leading to insufficient reranking input samples.

## How to Verify Successful Configuration
- Navigate to the application configuration page, confirm the reranking toggle is enabled and the corresponding reranking model is selected.
- Initiate a test query containing joint debugging keywords, check whether the order of retrieval results matches expectations.
- View system logs, confirm that the reranking model's call request has been sent normally with no error returns.
- Adjust the similarity threshold, observe changes in the number of retrieved results, verify that the configuration takes effect.

The values provided are common starting points and should be measured against the reader's own samples.
