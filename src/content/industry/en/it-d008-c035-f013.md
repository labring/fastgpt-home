# Unit and Component Testing: Operations On-Call and Internal Ticket Q&A: Permission and Data Isolation

## What this category of data looks like
Data for this category is generated during unit and component testing activities in software development and testing workflows. Daily documents include structured test cases, code coverage reports, Mock interface descriptions, and defect tickets. Data sources include code repository commit records, reports generated by automated testing frameworks, requirement documents, and interface definition files.

Data updates occur daily or in real time alongside code commits. A single test case includes fields such as case ID, test scenario, expected result, and execution status. Coverage reports use percentages to mark code line coverage rates. Defect tickets are linked to corresponding test cases and code commit records.

## Constraints Imposed on Permission and Data Isolation
This category of data includes test cases linked to private code and real-time coverage reports, involving core team development assets and test results. Data update frequency is high, with some updates synchronized in real time alongside code commits. Without proper permission isolation, cross-team members can access unauthorized test data and defect tickets.

There are permission level differences for test documents: defect tickets are only accessible to development and testing teams, while coverage reports are only visible to quality engineering teams. It is necessary to bind data access scopes using team identifiers to prevent unauthorized members from accessing private test assets, while adapting to the high-frequency data synchronization rhythm to ensure isolation rules take effect in real time.

## How to Configure Settings
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Bind the unique team identifier for the current testing team | Matches the association between team members and their associated test assets, ensuring only team members can access corresponding data such as test cases and coverage reports |
| `tmbId` | Bind the exclusive space identifier for the current testing project | Isolates private data across different testing projects, preventing cross-project members from accessing unauthorized test resources |
| Team member addition validation | Only allow accounts with matching enterprise email suffixes to join; maximum 20 members added at one time | Prevents invalid accounts or external personnel from accessing team test data, and controls the scale of team collaboration |
| Public access link permissions | Disabled by default; enable only when needed and bind to the `teamId` scope; link validity period is 72 hours | Restricts unauthorized external access to internal test-related tickets and Q&A content, preventing leakage of sensitive test data |
| Chat record storage scope | Only store current team context; storage duration is 30 days | Isolates ticket and Q&A records across different testing teams, meeting the private access requirements for test data |
| Data access log retention | Retain for the team data archiving period; retention duration is 180 days | Meets audit and traceability requirements for testing activities, facilitating troubleshooting of permission access anomalies |

## Three Common Configuration Mistakes
- When attempting to add team members, the interface returns "Username invalid". The cause is that the enterprise email suffix validation rule is not configured, or the added account is not included in the member whitelist for the current testing team.
- After enabling a public access link, non-team members can view internal test-related Q&A records. The cause is that the public link is not bound to the `teamId` access scope, and access is not restricted to only team members.
- When running ticket Q&A linked to test cases, an error "Insufficient data permissions" is returned. The cause is that the binding relationship between `tmbId` and the testing project is not configured correctly, causing the system to fail to identify the data ownership scope.

## How to Verify Successful Configuration
- Attempt to add an account with a non-enterprise email suffix, confirm the system returns an invalid prompt, to verify that the team member addition validation configuration is effective.
- Generate a public access link, use a non-team member account to access it, confirm that internal test-related Q&A content cannot be viewed, to verify that the public link permission configuration is effective.
- Switch to another testing team account, confirm that test cases and coverage reports of the current team cannot be accessed, to verify that the `teamId` and `tmbId` binding configuration is effective.
- View the chat record storage directory, confirm that only Q&A records of the current team are retained, to verify that the storage scope configuration is effective.
