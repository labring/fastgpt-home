# Operations On-Call and Internal Ticket Q&A for Unit and Component Testing: Deployment and Upgrade

## What this category of test data looks like
The business data for unit and component testing primarily comes from code repositories, test framework reports, requirement specifications, and interface definitions. Daily produced documents include test cases, coverage reports, Mock instructions, and defect tickets. Data is updated daily or per commit. The most time-consuming tasks in this category are test data construction, boundary condition completion, and failed test case localization. After an error occurs, local logic defects may be missed during testing, regression costs may increase, or builds may be blocked. This category verifies the independent logic of small code units, which has core differences from integration testing.

## What constraints these characteristics impose on deployment and upgrade
Since data sources include code repositories and real-time test reports, the deployment link must interface with code repository permission configurations to ensure test data can be pulled and synchronized. The high-frequency update feature requires the upgrade process to support incremental deployment and rapid rollback, to avoid disrupting daily testing work. Storage requirements for documents such as test cases and coverage reports mean deployment configurations must support mounting dedicated storage services. At the same time, the consequences of errors in this category are relatively severe, so deployment and upgrade links must be configured with complete permission verification and status monitoring to ensure testing process stability.

This document applies to FastGPT v4.17.0.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale for This Setting |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–200 connections` | Test reports for unit and component testing are generated frequently, requiring sufficient database connections to support high-frequency read and write operations |
| `REDIS_URL` | `Local port 6379` or `Managed Redis instance address` | Used to cache test case execution status and temporary test data, reducing database pressure from high-frequency reads |
| `STORAGE_S3_ENDPOINT` | `Configure according to the standard endpoint provided by the storage service provider` | Used to store business documents such as test cases and coverage reports, supporting batch upload and download operations |
| `FILE_TOKEN_KEY` | `32-character random string` | Ensures permission security for test file upload and download, preventing unauthorized access to sensitive test documents |
| `FE_DOMAIN` | `Public or internal domain name of the deployed service` | Used to generate accessible test report links for on-call operations personnel and testing teams to view |
| `ROOT_KEY` | `Random key configured only during initialization` | Ensures the security of the initial management permissions of the deployed instance, preventing permission leaks caused by default keys |

## Three common misconfigurations
- Docker deployment results in container startup failure, with logs indicating database connection timeout. The cause is that the `MONGODB_URI` or `PG_URL` parameters are not configured correctly, and do not match the database address and port of the test environment.
- Local deployment results in failure to parse uploaded test case files, with logs indicating file permission errors. The cause is that the `FILE_TOKEN_KEY` parameter is not configured correctly, or the mounted storage directory has insufficient permissions to read the uploaded test documents.
- The cloud version only supports WeChat QR code login, and does not allow account and password login. The cause is that the account and password login mode is not enabled in the deployment configuration, or the initial administrator account has not been correctly configured with password credentials.

## How to confirm a successful configuration
- Run the `docker ps` command to confirm that all deployed containers are in a running state, with no abnormal exit records.
- Access the domain name configured in `FE_DOMAIN`, log in to the system, upload a test case file, and confirm that the file can be parsed normally and a preview link is generated.
- Execute the unit test script to generate a coverage report, confirm that the report can be normally uploaded to the configured storage service, and that the `STORAGE_S3_ENDPOINT` parameter takes effect.
- Check the database connection logs, confirm that the number of connections configured by the `DB_MAX_LINK` parameter has not been exhausted, and that database connections are normal with no timeout errors.

The values provided here are common starting points and should be measured against the reader's own samples.
