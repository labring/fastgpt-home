# Operations Duty and Internal Ticket Q&A for Prototyping and Interaction Design: Permission and Data Isolation

## What data for this category looks like
Data for this category typically comes from Figma or Axure files, internal design systems, user feedback, and usability test records. Daily outputs include interactive prototypes, page flowcharts, component descriptions, and review records. Data updates occur weekly or with each product version iteration, focusing primarily on page structure, operation paths, and interaction details. Common fields include prototype version numbers, component attributes, review comment IDs, and test scenario identifiers. Unlike requirements analysis categories, this work does not focus on sorting out business rules, only documenting the implementation of front-end interactions.

## What constraints these characteristics impose on permission and data isolation
Interactive prototypes and review records often include undisclosed page paths, internal component naming rules, and unfinalized adjustment suggestions. The weekly or product version update cycle requires isolation granularity to match the iteration rhythm, preventing unauthorized cross-team access. Design assets from different front-end teams have clear business domain differences, so data must be isolated by team to avoid mixing interaction documents across product lines. Additionally, review records contain internal feedback details, so access must be restricted only to project participants to prevent unauthorized personnel from accessing undisclosed design adjustments.

## How to set up the configuration
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Team isolation identifier | `teamId` bound to front-end team ID | Matches business domain ownership to avoid mixing cross-team design documents |
| Tenant isolation identifier | `tmbId` bound to deployment instance | Ensures locally deployed team data is stored independently, not shared with other tenants |
| Knowledge base access scope | Visible only to project participants | Aligns with the scope of review and design participation to prevent unauthorized access |
| Model call key | Exclusive key bound to each team | Facilitates separate accounting of model call costs for each team, meeting commercial edition requirements |
| Knowledge base storage quota | 1000 MB per team | Matches the output scale of design documents for each team, avoiding storage overflow |
| Session context length | 4000 token | Matches the average character length of design documents, controlling context costs |
| Session retention period | 7–14 days | Aligns with product version iteration cycles, preventing expired data from occupying storage |

## Three common configuration errors
- Symptom: All users can access all design documents after local deployment, and permissions cannot be divided by team. Cause: `teamId` is not correctly bound to the front-end team’s organizational structure, and tenant-level isolation configuration is not enabled.
- Symptom: Exported training text includes interactive prototype content from other product lines. Cause: Data storage tables are not divided by `teamId`, leading to design documents from different teams being mixed when imported into the knowledge base.
- Symptom: Non-project participants can view internal review records and unpublished page paths. Cause: Knowledge base project group visibility permissions are not configured, and private design documents are set to be publicly accessible across the platform.

## How to confirm the configuration is correct
- Log in to accounts from different teams, verify that only the design document knowledge base corresponding to the respective team can be accessed, and content from other teams cannot be viewed.
- When exporting training text, select the storage table for the specified `teamId`, confirm that only interactive prototypes and review records from the current team are included.
- When testing model calls, use the team’s exclusive key to initiate a request, verify that only accounts from that team can use the bound model.
- View the session list, confirm that only project participants can view session content related to the corresponding interactive design work.
