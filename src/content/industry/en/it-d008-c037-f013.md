# Operations On-Call and Internal Ticket Q&A for Release Management and Version Acceptance: Permission and Data Isolation

## What Data for This Category Looks Like
This documentation applies to FastGPT v4.17.0. Release managers, R&D and operations teams, and product owners maintain data in this category. This data regularly links to four core documents: release plans, launch checklists, acceptance reports, and rollback plans.
Data comes from CI pipelines, change management systems, test reports, and monitoring dashboards. Update frequency follows weekly or per release cycle.
Data fields include release version number, change content, test pass rate, rollback trigger conditions, and more. No fixed standard units exist; values adjust based on formatting requirements of corresponding documents.

## What Constraints Do These Characteristics Impose on Permission and Data Isolation
Data in this category comes from multiple systems and updates rapidly with each release. Different teams (such as R&D, operations, product) require access to documents and data with matching permissions.
Content such as release plans and rollback plans involves production environment changes, so access must be restricted for unauthorized personnel.
Acceptance reports and launch checklists for different versions must be isolated by team or project to prevent cross-project data confusion.
In operations on-call and internal ticket Q&A scenarios, it is necessary to ensure only corresponding team members can view release-related tickets and records for their project, to avoid leakage of sensitive change information.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Bind to a project-specific ID, use the project's unique identifier string | Isolate release management data across different projects, ensuring only authorized team members can access data for their project |
| `tmbId` | Assign by role, use team identifiers for roles such as operations, R&D, product | Differentiate operation permissions for different roles, restrict unauthorized roles from modifying sensitive content such as rollback plans |
| Number of password-free login links | 10-100 | Adapt to link requirements for multiple tickets and version acceptances in release management scenarios, avoid overuse of single links |
| Conversation record permission verification | Enable role-based verification | Prevent "No permission to operate this conversation record" errors, ensure only authorized personnel can view release-related tickets |
| Team member access scope | Limited to project-specific data | Ensure only project members can create and modify release plans and acceptance reports for their project |

## Three Common Misconfigurations
- Symptom: The interface displays "No permission to operate this conversation record". Cause: `teamId` or `tmbId` is not configured correctly, causing the current user's permission identifier to not match the permission identifier of the conversation's associated project.
- Symptom: No additional password-free login links can be created after reaching 10 created links. Cause: The password-free login link quantity configuration for the team plan is not adjusted, retaining the default 10-link limit.
- Symptom: Deployed applications cannot be used by other team members. Cause: Team member permissions are not configured by project, and corresponding members' `tmbId` is not bound to the target project's `teamId`.

## How to Confirm Configuration Is Correct
- Use an account not associated with the project to access release management tickets for the project, confirm the corresponding data cannot be viewed or modified.
- Create password-free login links, confirm the number of creatable links falls within the configured 10-100 range.
- Attempt to modify a rollback plan document, confirm only members with matching role permissions can complete the operation.
- Initiate a test conversation, confirm the "No permission to operate this conversation record" error does not appear.

The values provided here are common starting points and should be assessed against the target deployment's own sample data.
