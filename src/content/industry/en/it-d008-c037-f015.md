# Operations on-call and internal work order Q&A for release management and version acceptance: Knowledge base retrieval and recall

## What the data for this category looks like
Core data for this category comes from CI pipelines, change management systems, test reports, and monitoring dashboards. Daily produced documents include release plans, launch checklists, acceptance reports, and rollback plans. Most document structures include process steps, version identifiers, validation items, and emergency response plans. Key fields are version numbers, change IDs, execution times, and validation results. Data updates occur weekly or per version release cycle, and are synchronized with version iterations.

## What constraints this category imposes on knowledge base retrieval and recall
The document update rhythm for this category is weekly or per version. Knowledge base synchronization configuration must match this frequency to avoid resource waste from high-frequency synchronization. Documents contain precise identifier fields such as version numbers and change IDs. Retrieval must prioritize these fields to reduce irrelevant results. Rollback plans and launch coordination documents are emergency scenario content, so their recall priority must be maintained. Operations work orders typically include brief problem descriptions. Retrieval question matching accuracy must be optimized to prevent recall bias from vague expressions.

## How to configure the settings
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Release management document processes are clearly defined, so a high matching threshold is needed to filter irrelevant results and avoid interference from low-relevance content during on-call operations |
| `limit` | Top 5–8 results | Operations scenarios require quick location of key information; too many results increase information filtering costs, aligning with the efficiency needs of on-call work |
| `searchMode` | Semantic retrieval + keyword hybrid | Balances semantic matching for process text and precise keyword matching for fields such as version numbers and change IDs, covering different types of work order queries |
| `usingReRank` | Enabled | Release management documents have structured formats; re-ranking can further improve the ranking position of highly relevant results and optimize response speed for emergency scenarios |
| `datasetSearchUsingExtensionQuery` | Enabled | Operations work orders often contain abbreviated or colloquial descriptions; optimizing queries can improve recall accuracy for vague expressions |

## Three common configuration errors
- The symptom is semantic retrieval scores outside the 0–1 range, displaying thousands-level values. This occurs when the normalization logic for the `similarity` parameter is not correctly configured, or when embedding model outputs are not standardized.
- The symptom is failure to retrieve the source file list associated with the knowledge base via API. This happens when the source file metadata return switch for retrieval results is not enabled, or when the configuration to return source information is not specified during interface calls.
- The symptom is significant deviation in knowledge base capacity estimation. This occurs when original file size and total character count after chunking are confused, and storage requirements are not estimated based on actual post-chunk content.

## How to verify proper configuration
- Initiate a test retrieval that includes specific version numbers and rollback plan keywords, and confirm that the `similarity` scores of returned results fall within the 0–1 range.
- Call the FastGPT v4.17.0 knowledge base retrieval API, and check whether returned results include metadata such as source file names and paths.
- Initiate a retrieval simulating an operations work order scenario, and confirm that the number of returned results matches the range set by the `limit` parameter.
- Upload a new release plan document, trigger incremental synchronization, then retrieve core keywords of the document, and confirm that the result can be recalled normally.
