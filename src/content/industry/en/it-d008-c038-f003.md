# Operations on-call and internal ticket Q&A for change management and release windows: Sharing and embedding

## What this category of data looks like
Data sources for this category include change management systems, CI pipelines, monitoring data, and business calendars. Daily associated documents cover change requests, risk assessment forms, launch window plans, and rollback plans.
Data updates occur once weekly, or synchronize upon completion of each change operation. Fields include change number, risk level, approval status, window time period, and rollback trigger conditions.
All data ties directly to a single production change or weekly window planning. No additional custom statistical numeric fields exist. Content only revolves around risk control and execution processes for production changes.

## What constraints do these characteristics impose on sharing and embedding
This category of data ties to single changes or weekly windows, and sources from dedicated operations and maintenance systems. Embedded Q&A modules must obtain real-time data by connecting to change management system APIs. They cannot rely on FastGPT’s built-in general offline knowledge base.
Data synchronization logic must be configured by the connected external system.
Field structures for documents such as change requests and risk assessments are fixed. Extraction rules for corresponding fields must be configured through the connected external system to avoid missing fields in Q&A results.
Data update frequency ties to change actions. A data synchronization mechanism must be configured through the connected external system to ensure on-call personnel access the latest window plans and approval statuses.
Rollback plan data has sensitivity requirements. Embedded modules must restrict access permissions, only opening access to internal operations and maintenance roles. This prevents leakage of sensitive production information.

## Three common misconfigurations
- Sharing entry links for change management and release windows fail to open. First verify the complete link generated by the system and its validity period. Then check browser request statuses. Do not manually replace `shareId`.
- The visible scope of change management and release window data does not match expectations. Verify third-party identity verification results, workflow request parameters, and external system data permissions separately. The sharing entry identifier itself does not provide business authorization.
- The same change management and release window Q&A cannot be viewed on another device. For anonymous scenarios, first check device, browser, and local identity status. Record retention cannot be guaranteed across devices or after cache clearance. Do not use this phenomenon alone to judge service abnormalities.

## How to confirm successful configuration
- Open the share link or the preview page of the embedded component. Check whether the currently effective launch window time period and risk level are displayed. Verify that fields match the latest data in the change management system.
- Attempt to access the embedded page from an unauthorized IP. Confirm that loading or data acquisition fails to verify that the permission configuration takes effect.
- Manually trigger a simulated change operation. Check whether the Q&A results of the embedded component synchronize to the new change information in the change management system. Confirm that the external data synchronization mechanism operates normally.
- Submit a ticket question containing a change number to the embedded module. Confirm that returned content only includes document fields tied to this category, with no irrelevant redundant information.
