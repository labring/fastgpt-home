# Operations on-call and internal ticket Q&A for change management and release windows: Permission and data isolation

This page configuration applies to FastGPT v4.17.0.

## What this category of data looks like
This category of data mainly comes from change management systems, CI pipelines, monitoring data, and business calendars. Daily generated documents include change request forms, risk assessment reports, launch window plans, and rollback plans. The data update frequency is weekly or each time a change is triggered. The document structure includes core fields such as change subject, impact scope, execution steps, approval nodes, and rollback conditions. No additional fictional statistical values are included, and the data is only generated around the entire production environment change process.

## What constraints do these characteristics impose on the permission and data isolation link
Change-related data contains sensitive information related to production environment risks, and different permission subjects must be strictly isolated. Data updated according to the change cycle must match permission validity periods to avoid expired permissions accessing unarchived change records. After multi-source data integration, the data scope must be divided based on source and owning team to prevent cross-team unauthorized viewing of unauthorized change plans. Fields related to approval nodes must be bound to corresponding permission roles to ensure that only users with approval permissions can edit content of corresponding links, preventing unauthorized tampering of change processes.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Bound to the owning team ID of the change request form | Matches the team ownership of change data to enable sharing within the same team and isolation across teams |
| `tmbId` | Bound to the template ID of the change approval role | Restricts access to change approval link data only to corresponding approval roles |
| Maximum number of change records viewed per request | Top 20 entries | Aligns with the typical viewing volume of operations personnel to avoid data overload |
| Data retention period | 180 days | Meets the typical retention cycle for operations audits while controlling storage usage |
| Approval timeout period | 600 seconds | Matches the typical response duration for change approvals to avoid process blocking |
| Team invitation permission | Only team administrators can initiate | Restricts the scope of invitation permissions to prevent unauthorized personnel from joining the team |
| Change data storage quota | 1000 MB | Adapts to the change data storage needs of small and medium-sized teams |

## Three common mistakes
- Symptom: An insufficient permissions error is returned when attempting to call a team application as a tool. Cause: The `teamId` binding for the corresponding team's tool call permissions is not configured, resulting in missing cross-team call permissions.
- Symptom: Team members receive no notification prompt after accepting an invitation. Cause: The notification permission bound to `tmbId` is not correctly configured, resulting in invitation messages not being pushed to the corresponding member's permission domain.
- Symptom: A second team cannot be created or the team list only shows the initial team. Cause: Multi-team permission configuration is not enabled, resulting in permission domain restrictions that only retain the initial team.

## How to confirm the configuration is complete
- Submit a test change request, have different team accounts access the request, and confirm that only users from the owning team can view the request content.
- Initiate a team member invitation, and confirm that the invitation message appears in the notification bar of the corresponding member.
- Use an account without approval permissions to attempt editing a change approval node, and confirm that the operation is blocked by the system.
- Review the retention duration of change history, and confirm that it matches the preset retention period configuration.

The values provided here are common starting points and should be measured against the reader's own samples.
