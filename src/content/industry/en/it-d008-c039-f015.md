# Operations on-duty and internal work order Q&A for backend service development: Knowledge base retrieval and recall

## What the data for this category looks like
Daily documents for this category include interface design documents, database change tickets, code review records, and release notes. Data sources include code repositories, API gateway logs, databases, and configuration centers. Data updates daily or when a new version is released. Most document structures contain both structured fields and unstructured text. Some documents have clear hierarchical headings, interface parameters, change timestamps, and other identifiers. Fields often cover technical content such as service ports, call chains, and error codes.

## Constraints on knowledge base retrieval and recall workflows
Data sources for this category are scattered and update frequently. Retrieval workflows must support incremental sync configurations to avoid retrieving outdated code or change records. Documents include structured metadata and hierarchical headings. Retrieval must return associated metadata alongside text to enable quick location of relevant information by engineering teams. Time-consuming tasks such as interface contract confirmation and error log troubleshooting rely on precise matching of technical keywords. Retrieval workflows must limit result redundancy to prevent excessive irrelevant content from disrupting answer flows. Additionally, errors such as interface timeouts or incorrect data writes create high stakes for retrieval result confidence. Retrieval of erroneous change tickets or log fragments must be avoided.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Technical documents for backend service development have high keyword density. This range filters low-relevance logs or code fragments while retaining core matching results |
| `limit` | Top 10 entries | Too many retrieved results in scenarios like interface contract confirmation and error troubleshooting cause context overload. 10 entries balances retrieval coverage and answer fluency |
| `searchMode` | `vector` | Most data for this category consists of structured technical text. Vector retrieval accurately matches technical keywords such as interface parameters and error codes, outperforming pure keyword matching |
| `usingReRank` | Enabled | Re-ranking initial retrieval results further filters redundant content, aligning with engineering teams’ needs to quickly locate core changes or interface information |
| `datasetSearchUsingExtensionQuery` | Enabled | Generates extended query terms based on user questions to supplement matching of associated interface logic not directly present in code repositories, improving retrieval completeness |
| `collectionIds` | Bind dedicated knowledge base collections for backend services | Prevents retrieval of non-backend service documents, ensuring retrieved results only cover the current team’s technical materials |

## Three common configuration errors
- Symptom: Too many results returned in a single retrieval, causing AI answers to truncate mid-stream. Cause: The `limit` parameter is not configured, or its value is set too high, exceeding context window limits.
- Symptom: Retrieval results do not include associated metadata, making it impossible to match supplementary information for business scenarios. Cause: Metadata association retrieval configuration is not enabled. Only text fragments are returned without binding metadata such as change time and the service the interface belongs to.
- Symptom: Logical relationships between hierarchical headings and subordinate content are lost after markdown-format documents are uploaded. Cause: Document structure-based chunking configuration is not enabled. Direct paragraph splitting separates headings from their corresponding content, preventing associative matching during retrieval.

## How to verify correct configuration
- Upload one interface design document and one code change ticket, initiate a query containing interface parameter keywords, and check whether the number of returned results matches the `limit` parameter configuration.
- Review additional fields in retrieval results to confirm whether document metadata such as change time and affiliated service is included, verifying that the metadata association configuration is active.
- Upload a markdown document with hierarchical headings, initiate a query containing heading keywords, and check whether returned results associate with corresponding content under the headings, verifying that the structure chunking configuration works correctly.
- View knowledge base sync logs in the FastGPT v4.17.0 backend to confirm that data completes incremental updates daily or with each new version release, verifying that the data source sync configuration is correct.
