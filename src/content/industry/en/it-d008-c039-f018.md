# Operations Duty and Internal Ticket Q&A for Backend Service Development: Reranking and Hybrid Retrieval

## What this category of data looks like
Daily documents for backend service development include interface design documents, database change tickets, code review records, and release notes. Data sources primarily include code repositories, API gateway logs, databases, and configuration centers. Data update frequency follows a daily or per version release cycle.
Document fields typically include interface paths, change ticket numbers, review comments, version numbers, and other details. Log data includes timestamps, request parameters, error codes, and similar information. Overall data exhibits both structured and semi-structured characteristics.

## Constraints imposed by these characteristics on reranking and hybrid retrieval
Backend service development data has both structured and semi-structured characteristics, with an update frequency of daily or per version release cycle. This requires hybrid retrieval to cover both keyword matching and semantic matching scenarios.
Documents such as interface design documents and database change tickets have high technical detail density. The reranking stage must accurately match semantic associations to avoid retrieving irrelevant review records or log data. Multiple data sources lead to a large volume of documents retrieved in a single search. It is necessary to balance retrieval volume and reranking computation overhead to prevent response timeouts or excessive resource consumption.

## How to configure settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Aligns with the semantic similarity distribution of backend service documents, filters low-relevance search results |
| `limit` | Top 10–15 entries | Balances search retrieval volume and reranking computation overhead, meets the information needs of backend teams during daily troubleshooting |
| `usingReRank` | Enabled | Improves the accuracy of search results for backend service documents with high technical detail density |
| `searchMode` | hybrid | Combines vector retrieval and keyword retrieval to cover multiple query types such as interface paths and log keywords |

## Three common misconfigurations
- Search response timeout. Cause: Improperly setting the `limit` parameter leads to excessive document retrieval, causing overload in reranking computations.
- Continuous GPU memory usage increase during reranking that cannot be automatically released. Cause: Failure to configure a GPU memory recycling policy for the reranking model, with the number of documents processed in a single batch exceeding hardware carrying capacity.
- Unable to locate the reranking model configuration entry, with returned results not processed through reranking. Cause: Failure to correctly enable the `usingReRank` parameter in the retrieval workflow, and failure to mount the reranking component per documentation guidelines.

## How to confirm proper configuration
- Access the search configuration panel in FastGPT v4.17.0, confirm that `usingReRank` is enabled and `searchMode` is set to hybrid.
- Submit a query related to interface changes, verify that returned results are sorted according to technical detail matching degree.
- Observe the system monitoring panel, confirm that GPU memory usage during the reranking stage does not continuously exceed hardware thresholds.
- Adjust the `similarity` threshold range, verify that the number of retrieved search results meets expectations.
