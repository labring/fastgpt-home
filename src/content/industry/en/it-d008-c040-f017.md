# Operation and Maintenance Duty and Internal Work Order Q&A for Pre-sales Technical Proposals: Deployment and Upgrade

## What the data for this category looks like
This category uses customer interviews, bidding documents, vendor product materials, and historical project plans as data sources. Updates occur per order or weekly. Daily deliverables include technical proposal documents, customer requirement research forms, quotation lists, and demo scripts. Core fields cover proposal technical routes, implementation boundaries, quotation configuration items, customer requirement matching points, and more. Data centers on pre-sales requirements for a single customer project, and updates synchronize with requirement clarification and plan adjustments as the project progresses. All data must strictly match the customer’s bidding requirements and implementation boundaries.

## What constraints these characteristics impose on the deployment and upgrade link
Unique data characteristics of individual projects in this category require the deployment process to support configuring independent knowledge base association rules for each pre-sales project. This prevents mixing of plan document data across different projects. High-frequency update requirements mandate that the upgrade process support hot updates or zero-downtime switching. This stops upgrade interruptions to pre-sales demo progress. Requirements for structured processing of multiple document types require deployment configurations to support access to data sources in formats like technical proposal documents and demo scripts. Configurations must also strictly match mapping rules for proposal boundary fields. This prevents over-scope commitment of proposal content caused by configuration deviations, which can lead to bid scoring losses or project loss risks.

## Three common mistakes
- After upgrading to a new version, knowledge base queries run normally but the model produces no output. Knowledge base recall results appear normal, but the model returns empty content or no valid output. The root cause is that the `REDIS_URL` configuration resets after the upgrade, clearing the session context cache so the model cannot access the query context.
- After Docker deployment, the 3000 port page fails to load, while the 3001 port works correctly. The host’s 3000 port shows no response, but the 3001 port loads the frontend page normally. The issue stems from incorrect frontend service port mapping: the container’s internal 3000 port is not mapped to the corresponding port on the host machine.
- After Linux deployment, modifying the configuration file does not take effect. Corresponding functions do not change after configuration edits. The root cause is failure to restart the relevant service process, or the modified configuration item does not match the loading path in the startup script.

## How to confirm the configuration is complete
- Access the configured `FE_DOMAIN` to verify the frontend page loads normally, with no resource loading failure errors.
- Run a database connection test to confirm the instances configured via `MONGODB_URI` and `REDIS_URL` connect successfully.
- Log in to the backend management interface using `ROOT_KEY` to verify the permission control function operates correctly.
- Upload a pre-sales proposal document, trigger a knowledge base query, and confirm results output normally to the model and display correctly.
