# Operations on-duty and internal ticket Q&A for backup recovery and disaster recovery drill: Sharing and embedding

## What the data for this category looks like
The data for this category primarily comes from backup systems, database logs, object storage, and disaster recovery platforms. Four core document types are routinely produced: backup policies, recovery drill reports, disaster recovery switchover plans, and data verification records.

Data update frequencies cover daily, monthly, and quarterly cycles. Backup execution logs are updated daily. Quarterly disaster recovery drill reports are archived quarterly.

Document fields include backup path, recovery time threshold, verification hash value, and disaster recovery switchover timeline. Units include seconds, GB, count, and others. Some core fields require association with cross-system execution status identifiers.

## What constraints these characteristics impose on sharing and embedding
Cross-system data sources require associated external business systems to have API call permissions. Otherwise, complete backup and disaster recovery data cannot be retrieved.

Differences in update frequencies across documents require external systems to implement separate data synchronization logic. This avoids outdated or redundant embedded content.

Cross-system association of core fields requires associated external business systems to handle field association logic. Shared content only displays compliant associated data.

The size of large drill reports requires limiting the loading length of single context during embedding. This prevents page load timeouts or content truncation.

## Three common mistakes
- Sharing entry for backup recovery and disaster recovery drill services fails to open. First verify the full system-generated link and its validity period, then check browser request statuses. Do not manually replace `shareId`.
- Visibility of backup recovery and disaster recovery drill data does not match expectations. Verify third-party identity verification results, workflow request parameters, and external system data permissions separately. The sharing entry identifier itself does not provide business authorization.
- Original conversation is not visible on another device for the same backup recovery and disaster recovery drill Q&A. For anonymous scenarios, first check device, browser, and local identity status. Retention cannot be guaranteed across devices or after cache clearance; do not use this phenomenon alone to judge service anomalies.

## How to confirm configuration is complete
- Access the generated share link, attempt access via an unauthorized network, verify that access is blocked by permission configurations, and confirm that embedded page permissions are active.
- Embed a test page to call the bot, enter a query instruction related to backup verification, check that returned content matches the daily logs of the backup system, and confirm that data synchronization configuration is active.
- Adjust the window size of the embedded page, verify that the bot component loads normally across different sizes, and confirm that the context window configuration adapts to page layout.
- Trigger a simulated cross-system disaster recovery query, check FastGPT operation logs or receiving logs of external business systems, and confirm that call configuration is active.
