# Operational On-Call and Internal Ticket Q&A for Backup Recovery and Disaster Recovery Drills: Deployment and Upgrade

## What data for this category looks like
Data sources for this category include backup systems, database runtime logs, object storage, and disaster recovery management platforms. Daily operational documents include backup policies, recovery drill reports, disaster recovery switchover plans, and data validation records. Data update frequencies are divided into three categories: daily (backup logs), monthly (drill reports), and quarterly (switchover plans). Data fields include backup task ID, recovery point objective, validation pass status, and storage medium identifier. No additional statistical quantitative metrics are included.

## What constraints these characteristics impose during deployment and upgrade
Data sources for this category are scattered. Multi-system permission configuration and connectivity validation must be completed during deployment. Parameters such as `STORAGE_S3_ENDPOINT` and `MONGODB_URI` must match the actual connected storage and logging systems. Data update rhythms vary widely. Daily logs require scheduled pull tasks. Monthly and quarterly documents need regular synchronization paths to avoid data synchronization delays. Recovery-related processes take a long time. Connection thresholds must be adjusted during deployment to prevent connection interruptions during execution. Cross-system recoverable capability requirements must be met. During upgrade, validate the disaster recovery instruction transmission link between each service to ensure the switchover process can trigger normally.

## How to configure settings
The following configuration items are adapted for the backup recovery and disaster recovery drill module of FastGPT v4.17.0.

| Configuration Item | Recommended Value/Method | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 100–200 connections | Meets concurrent pull requirements for backup systems and database logs, avoids connection exhaustion |
| `MONGODB_URI` | Fill in with the actual connection string from the disaster recovery platform | Stores recovery drill reports and data validation records, must match authentication information for the disaster recovery platform |
| `STORAGE_S3_ENDPOINT` | Fill in with the actual endpoint from the object storage | Connects to storage media for backup data, ensures disaster recovery files can be read and written normally |
| `REDIS_URL` | Local or cluster address using port 6379 | Caches frequently accessed backup policy configurations and drill statuses, reduces repeated query overhead |
| `ROOT_KEY` | Random string generated per security specifications | Configures administrator permissions for internal tickets, prevents unauthorized access to operational configuration pages |
| `FE_DOMAIN` | Public or internal domain name of the deployment node | Configures callback addresses for internal tickets, ensures on-call notifications can be sent normally |

## Three common configuration errors
- Login errors appear after re-pulling the image, with an invalid authentication key prompt. The cause is that the `ROOT_KEY` configuration was not synchronized and updated after upgrade. The default key reset by the image does not match the encrypted information stored locally.
- Disaster recovery drill status cannot be synchronized during cluster deployment. The cause is that `REDIS_URL` was not configured as a cluster shared address. Using only a single-node cache causes inconsistent status across nodes.
- A 404 error is returned when accessing a custom model call chain. The cause is that the model storage path associated with `STORAGE_S3_ENDPOINT` was not configured correctly, causing model files to fail to load normally.

## How to confirm configuration is complete
- Run the specified connection test command to confirm that 100–200 backup log pull tasks can be started simultaneously, verifying that the `DB_MAX_LINK` configuration takes effect.
- Access the address configured in `FE_DOMAIN`, log in to the backend, and check whether test backup policy records exist in the database associated with `MONGODB_URI`.
- Upload a test backup file to the storage path specified by `STORAGE_S3_ENDPOINT`, confirm that the file can be read and downloaded normally.
- Check the cache monitoring for `REDIS_URL`, confirm that backup drill status data can be synchronized to all deployment nodes.

The values provided are common starting points and should be evaluated against the user's own samples.
