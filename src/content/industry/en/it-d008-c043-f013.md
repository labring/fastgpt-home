# Incident Response Operations On-Call and Internal Ticket Q&A: Permission and Data Isolation

## What This Category of Data Looks Like
This category of data covers the full security incident disposal workflow. Sources include SIEM, EDR, firewall logs, and host images. Updates occur in real time or are triggered per individual incident. Daily retained documents include incident response reports, forensic records, disposal plans, and notification materials. Each document’s fields include incident ID, attack source IP, disposal time, and evidence chain hash value. Units are typically timestamps, IP address strings, byte counts, and similar values. There are no unified aggregated statistical fields.

## Constraints Imposed by These Characteristics on Permission and Data Isolation
Data sources for this category are scattered and include sensitive forensic and disposal content. The real-time update feature requires permission rules to be dynamically adjusted alongside the incident lifecycle. Unlike security monitoring and SOC on-duty operations, this workflow performs disposal and forensic work only after an incident is confirmed. Permission isolation must cover the entire disposal process, from log retrieval to report generation. In operations on-call scenarios, security incidents across different regions must isolate the operation scope of corresponding on-call engineers. In internal ticket Q&A workflows, access to relevant documents must be restricted to only participating members of the corresponding incident. Data leaks or misoperations will directly expand attack impacts or cause regulatory delays. Therefore, permission isolation must strictly restrict unauthorized cross-team and cross-incident access.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Bind to the unique team identifier of the corresponding security operations center | Implement team-level data isolation, ensuring only authorized team members can access this team’s incident response data |
| `tmbId` | Use an integer between `100000–999999`, bound to individual emergency incidents | Implement single-incident data isolation, preventing unauthorized cross-incident access |
| Sensitive data masking rules | Mask the host image hash value in forensic records and the source IP in firewall logs. Keep the first 3 and last 2 characters, replace the rest with `*` | Reduce the risk of sensitive data leaks without disrupting troubleshooting |
| Session isolation timeout | `1800 seconds`, automatically destroy current session permissions after timeout | Match the average disposal duration of emergency incidents, avoiding long-term retention of session permissions |
| Role permission binding | Assign permissions based on two roles: security operations engineer and customer security lead. Engineers may only access disposal plans and logs. Leads may access all documents and notification materials | Align with the work content of different roles, implement the principle of least privilege |
| Team management entry | Path: `Settings > Team Management` | Quickly locate permission configuration entries, supporting rapid adjustment needs for operations on-call |

## Three Common Configuration Mistakes
- Symptom: The chat interface displays "No permission to operate this conversation record", and the ticket content of the corresponding incident cannot be viewed. Cause: The `teamId` of the current session is not bound to the incident’s owning team, causing permission verification to fail.
- Symptom: The team management page entry cannot be found, and permission rules cannot be configured. Cause: The "Team Management" entry was not correctly located in the system settings menu, or the current account does not have access permissions for system settings.
- Symptom: Team member model usage records cannot be viewed. Cause: The usage statistics view permission in role permission binding is not enabled, or the corresponding relationship between `tmbId` and team members has not been configured.

## How to Verify Successful Configuration
- Access the corresponding team’s account, attempt to view emergency incident tickets from other teams, confirm that viewing is blocked and a permission prompt pops up.
- Enter the Team Management page of FastGPT v4.17.0, verify that the configured `teamId` and `tmbId` binding rules can be edited and saved normally.
- Submit a test ticket, confirm that only authorized roles can view the forensic records and log content in the ticket.
- Wait `1800 seconds`, verify that the session permission automatically expires and further operations on the current ticket are no longer possible.

The values provided are common starting points and should be measured against the reader's own samples.
