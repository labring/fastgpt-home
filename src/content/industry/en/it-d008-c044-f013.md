# Operations On-Duty and Internal Ticket Q&A for Security Product Rule Management: Permission and Data Isolation

## What Data This Category Includes
This category’s data primarily originates from WAF, IDS, firewalls, and threat intelligence platforms, with updates occurring daily or when triggered by security incidents. Daily generated documents include rule change tickets, intercept logs, false positive analysis reports, and policy rollback records.
Rule change tickets include the following fields: rule ID, effective time, and changer.
Intercept logs include the following fields: source IP, target port, intercept rule number, and timestamp.
False positive analysis reports include the following fields: false positive sample characteristics, false positive cause, and adjustment suggestions.
Policy rollback records include the following fields: rollback time, pre-rollback rule version, and rollback executor.

## Constraints Imposed on Permission and Data Isolation
Decentralized data sources involving core protection configuration require permission isolation to cover access scopes across different data sources.
Rule change tickets and policy rollback records contain sensitive configuration information. Access to these records must be restricted to only on-duty operations staff and ticket approvers.
Intercept logs and false positive analysis data volume increases with incident volume. Data isolation boundaries must be divided by team or project to prevent cross-team data leaks.
Real-time data triggered by security incidents requires real-time permission validation to block unauthorized modification of protection rules.
Different SOC teams are responsible for distinct protection products. Data and permissions must be split by product dimension to avoid cross-team operational conflicts.

## Configuration Settings
The following configurations are adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Team permission binding | `teamId` associated with corresponding protection product permission groups | Different SOC teams are responsible for different WAF and IDS products, so protection configuration access scopes must be divided by team |
| Log data isolation | `tmbId` limits intercept log viewing scope | Intercept logs update in real time with security incidents, so data boundaries must be split by products managed by the team |
| Ticket approval permission | Only administrators of the team to which the rule change ticket belongs can perform operations | Rule change tickets involve core protection policies, so approval control must be implemented within the team |
| Data storage period | 90 days | Matches business analysis and compliance archiving requirements, can be adjusted based on actual testing |
| Team invitation validity period | 7 days | Prevents unauthorized access caused by long-term exposure of invitation links |
| Real-time permission validation delay | 600 milliseconds | Matches real-time processing requirements for security incidents, calibrated based on actual testing |
| Ticket review timeout threshold | 3600 seconds | Matches typical timelines for internal enterprise ticket approval |

## Three Common Misconfigurations
- Symptom: After a team member is invited, the recipient does not receive any permission notification. Cause: The invitation notification trigger rule corresponding to `teamId` was not configured correctly, so invitation information fails to be pushed to the target member account.
- Symptom: An account cannot be assigned operation permissions for multiple protection products. Cause: Permission groups were not split by `tmbId`, and only the permission scope of a single team was bound, which cannot cover multi-product management requirements.
- Symptom: Intercept log data not managed by the team is viewed across teams. Cause: Log data isolation by `tmbId` was not configured, so permission validation does not cover the log access scope for the corresponding protection product.

## How to Verify Successful Configuration
- A team member invitation is submitted, and the notification center of the invited member is checked to confirm receipt of the invitation information, verifying that the notification trigger configuration is effective.
- Permission accounts bound to different `teamId` values are switched, and verification is performed to confirm that only intercept logs and rule documents corresponding to the managed protection products are accessible.
- A rule change ticket is submitted, and verification is performed to confirm that only administrators of the owning team can view the ticket in the ticket list and perform approval operations.
- The data storage directory is checked to confirm that intercept logs older than 90 days have been automatically archived or deleted per configured settings.
