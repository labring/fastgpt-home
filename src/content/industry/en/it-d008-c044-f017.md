# Operational On-Call and Internal Ticket Q&A for Security Product Rule Operations: Deployment and Upgrade

## What this category of data looks like
This category of data primarily originates from WAF, IDS, firewalls, and threat intelligence platforms. Update frequency follows a daily schedule or is triggered by protection events. Daily associated documents include rule change tickets, intercept logs, false positive analysis reports, and policy rollback records. Document fields include rule unique identifiers, intercept matching conditions, false positive sample tags, rollback timestamps, and other items. No unified standardized format exists, so sorting must be completed according to the export rules of each protection product.

## What constraints do these characteristics impose on the deployment and upgrade phase
Data sources for this category are scattered and updates are frequent. The deployment environment must support multi-source log pulling and incremental synchronization to avoid excessive system resource usage from full pulls. Daily documents have no unified standardized format, so custom field parsing rules must be configured during deployment to adapt to the export structures of different protection products. The frequency of policy changes and rollbacks is high, so the upgrade process must ensure that original configurations are not lost, and support quick rollback to the last available version to prevent normal business or security protection effects from being impacted by rule change errors. Additionally, internal ticket Q&A must connect to the enterprise’s existing operation and maintenance system, so correct domain name and permission parameters must be configured during deployment to ensure compliance of access by the operation and maintenance team.

## How to set the configurations
The following configurations are explained based on FastGPT v4.17.0.

| --- | --- | --- |
| `DB_MAX_LINK` | `20–30 connections` | Adapt to high-frequency log queries triggered daily or by events, avoid connection pool exhaustion affecting service stability |
| `MONGODB_URI` | Address of a dedicated database instance storing protection logs | Store core data of this category with frequent read/write operations, such as intercept logs and false positive analysis reports |
| `REDIS_URL` | Address of a local cache instance | Cache rule change records and threat intelligence snapshots to reduce query pressure on the primary database |

| `FE_DOMAIN` | `https://your-ops-qa-domain.com` | Configure the access domain name of the internal ticket Q&A system to ensure compliance of access paths for the operation and maintenance team |
| `ROOT_KEY` | `Random key generated based on the deployment environment` | Ensure interface access permissions for internal ticket Q&A, prevent unauthorized operations |

## Three common mistakes
- The symptom is garbled characters when importing protection rule documents in the online environment, with no issues in local deployment. The cause is that the character encoding configuration of the online environment is inconsistent with the local environment, and a unified UTF-8 encoding parameter is not specified.
- The symptom is that the body content of the internal ticket HTTP module cannot be edited normally in a Docker-deployed instance. The cause is improper file permission configuration within the container, preventing the frontend from modifying mounted code files.
- The symptom is false positives where normal business is blocked after rule upgrade. The cause is that no gray release was performed during the upgrade process, and new rule policies were fully replaced directly, causing unvalidated rules to take effect.

## How to confirm configurations are correctly set
- Run a multi-source log pulling test script to confirm that latest intercept logs can be pulled from specified data sources such as WAF and IDS.
- Submit a test rule change ticket to confirm that ticket content can be stored normally and associated with the corresponding protection policy.
- Execute the version upgrade process to verify that the service has no errors after upgrade and original configurations have not been reset.
- Access the frontend page of the internal ticket Q&A system to confirm that it loads normally and the permission verification process takes effect.
