# Operations Duty and Internal Ticket Q&A for Security Baseline Checks: Permission and Data Isolation

## What the data for this category looks like
This category's data primarily comes from server configurations, middleware configurations, security device policies, and dedicated baseline tools. Daily produced documents include baseline checklists, configuration verification records, rectification suggestions, and exception approval forms. Each document contains fields such as baseline item number, verification time, rectification status, and approver identification. The data update frequency is monthly or quarterly, with a single update covering full verification results for current compliant configuration items. There is no real-time incremental synchronization requirement.

## What constraints these characteristics impose on the permission and data isolation link
The data sources for this category cover multiple types of IT infrastructure configurations, and are linked to work results from different roles. Permission isolation must cover three links: data access, operation approval, and result distribution. Baseline checklists and rectification suggestions contain undisclosed compliant configuration details. Cross-department access may trigger compliance risks. Monthly or quarterly batch verification data has a large volume, so storage ranges must be divided by team to prevent unauthorized teams from accessing full baseline data. Exception approval forms involve internal permission adjustments, and must be bound to the approver's exclusive permission identification to prevent unauthorized approval.

## Three common configuration mistakes
- Calling APIs related to baseline checks returns a 403 permission denied error. The cause is failure to bind an exclusive `teamId` key for the caller, so the system cannot identify the legitimate access subject.
- Viewing baseline checklists or verification records across teams shows empty content. The cause is failure to configure the knowledge base isolation scope to limit to the current `teamId`, resulting in data being incorrectly assigned to other team storage.
- After a team member is deleted, they can still access baseline data for their team. The cause is failure to synchronously update the permission identification bound to the deleted member's `tmbId`, so old permissions are not revoked.

## How to confirm configuration is complete
- The API interface bound to `teamId` is invoked, and returned results are confirmed to only include baseline check data for the current team.
- A non-current team member account is used to log in, and access to documents including current team baseline checklists and configuration verification records is confirmed to be restricted.
- A test team member is deleted, and access to all baseline-related content for the corresponding team by that member is confirmed to be revoked.
- For local deployment scenarios, the team management configuration page of FastGPT v4.17.0 is accessed, and the permission isolation function is confirmed to be properly enabled.
