# Operations on-duty and internal ticket Q&A for security baseline checks: Deployment and upgrade

This page is compatible with FastGPT v4.17.0

## What this category of data looks like

Security baseline check data originates from server configurations, middleware configurations, security device policies, and output content from baseline tools. Four core document types are regularly produced: baseline checklists, configuration verification records, rectification suggestions, and exception approval forms. Document fields include structured content such as configuration item name, compliance status, rectification suggestions, and exception approval opinions. The update cycle is monthly or quarterly. This category focuses on whether configurations match organizational security benchmarks, and differs from the vulnerability detection logic of vulnerability scanning services. Its core data revolves around configuration compliance.

## Constraints imposed by these characteristics during deployment and upgrade

Data sources are scattered and require connection to multiple configuration sources. During the deployment phase, configure import modules compatible with multiple configuration export formats, and support synchronizing configuration data from servers, middleware, and security devices. Since the update cycle is monthly or quarterly, ensure field compatibility between historical verification records and new baseline templates during upgrades to avoid invalidation of existing data. Since core documents include fixed fields, preset structured storage fields matching baseline checklist formats during deployment. Since compliance verification needs to be linked to exception approval workflows, integrate the internal ticket system's approval status synchronization interface during upgrades to ensure a complete data link.

## How to set configuration values

| Configuration Item | Recommended Value | Rationale |
| ---|---|--- |
| `DB_MAX_LINK` | `100–200` | Adapts to concurrent reading requirements of configuration data from multiple servers, avoids connection pool exhaustion |
| `MONGODB_URI` | `mongodb://[username]:[password]@host:port/database?authSource=admin` | Stores structured documents such as baseline verification records and exception approval forms, supports flexible field queries |
| `REDIS_URL` | `redis://:[password]@host:port` | Caches frequently accessed baseline templates and configuration comparison results, reduces database query pressure |
| `FE_DOMAIN` | `https://your-baseline-check-domain.com` | Configures the frontend access domain name, used to generate ticket jump links and access entrances for compliance reports |
| `FILE_TOKEN_KEY` | `Randomly generated 32-bit string` | Encrypts and stores uploaded baseline checklist attachments to prevent unauthorized access |
| `STORAGE_S3_ENDPOINT` | Set based on actual testing | Adapts to enterprise self-built object storage or cloud storage services, used to store baseline checklist attachments and rectification vouchers |

## Three common misconfigurations

- Phenomenon: Unable to load baseline configuration data after deployment in a Linux environment, the interface returns `502 Bad Gateway`. Cause: The connection count limit for `DB_MAX_LINK` was not configured correctly, causing the database connection pool to be exhausted and unable to handle concurrent configuration reading requests.
- Phenomenon: Network access errors occur when deploying with the Zilliz version, unable to synchronize security device policy data. Cause: Proxy parameters were not added to the configuration of `MONGODB_URI` or `STORAGE_S3_ENDPOINT`, causing cross-network segment access failures.
- Phenomenon: Deployment in the Alibaba Cloud DSW environment fails, Docker container fails to start, unable to load the baseline check service. Cause: Port permissions required by Docker were not opened, or the correct image pull address was not configured, causing dependent components to fail to download.

## How to verify successful configuration

- Run the database connection test script to verify whether the configurations of `MONGODB_URI` and `PG_URL` can normally read baseline verification records.
- Upload a test baseline checklist to verify whether the encryption logic of `FILE_TOKEN_KEY` works normally and whether attachments can be downloaded normally.
- Initiate an internal ticket to verify whether the ticket status can be synchronized to the baseline check system and whether the exception approval process is triggered normally.
- Access the frontend address corresponding to `FE_DOMAIN` to verify whether the baseline templates and compliance reports can be loaded normally on the interface.

The values provided are common starting points and should be evaluated against the reader's own samples.
