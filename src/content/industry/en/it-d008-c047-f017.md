# Operations On-Duty and Internal Ticket Q&A for Vulnerability Disclosure Handling: Deployment and Upgrade

## What this category of data looks like
This category of data comes from private vulnerability reports, code repositories, CVE numbering authorities, and official release channels. Daily documents include security advisories, vulnerability reports, fix patches, and CVE application materials. Data updates follow the rhythm of single vulnerability events, with no fixed cycle. Core fields include vulnerability ID, impact scope, fix status, disclosure time, and patch links. There are no unified fixed units, as they vary by document type.

## What constraints do these characteristics impose during deployment and upgrade
The non-public nature of private vulnerability reports requires isolated storage of sensitive data during deployment to prevent unauthorized access. Multi-source data access requires adaptation to different interface formats, and upgrade processes must maintain compatibility with existing data synchronization logic to avoid loss of historical vulnerability data. The event-driven update rhythm does not require fixed scheduled tasks, but must support manual triggering and event listening to adapt to the sudden nature of vulnerability disclosures. The varying field structure across documents requires configuration options that support custom field mapping, to avoid compatibility issues caused by hard-coded field names. The high-risk nature of vulnerability handling requires enabling full-link audit logs during deployment, to facilitate traceability of operations and troubleshooting.

## How to set configurations
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://username:password@host:27017/fastgpt_vuln` | Stores structured data such as vulnerability reports and patch records, requires a dedicated database instance |
| `REDIS_URL` | `redis://:password@host:6379/1` | Caches temporary vulnerability assessment results and ticket sessions. Uses the default port 6379, selects database 1 to isolate business data |
| `DB_MAX_LINK` | `20–30` | Adapts to concurrent connection counts for multi-source data synchronization, avoids exhausting database connections |
| `STORAGE_S3_ENDPOINT` | `http://192.168.1.100:9000` | Stores patch packages and vulnerability report attachments, must match the object storage service address of the deployment environment |
| `ROOT_KEY` | `Random 32-character string` | Configures platform super administrator permissions, avoids risks from default key leaks |
| `FE_DOMAIN` | `https://vuln-handle.your-domain.com` | Specifies the frontend access domain name, used to generate jump links for vulnerability disclosure notifications |

## Three common misconfigurations
- OneAPI connection errors occur after startup, with timeout or authentication failure prompts. The cause is incorrect authentication parameters for `REDIS_URL` or `MONGODB_URI`, preventing connection to dependent services.
- Vulnerability attachments fail to upload normally, with a file parsing failure message displayed on the frontend. The cause is incorrect configuration of `STORAGE_S3_ENDPOINT` or unopened permissions for the storage service, interrupting the file storage link.
- Ticket sessions fail to save normally, with data lost after refresh. The cause is an excessively low `DB_MAX_LINK` value, exhausting the database connection pool and preventing session data from being written.

## How to confirm successful configuration
- Access the configured frontend domain name, verify that the page loads normally, and check the browser console for error messages related to configuration items.
- Run the local data synchronization script, import test vulnerability report data, and verify that it can be successfully written to the specified database instance.
- Upload a test patch attachment, verify that it can be stored normally and generate an accessible link.
- Call the super administrator API, use the configured `ROOT_KEY` to verify permissions, and confirm that super administrator operation permissions can be obtained normally.

The values provided are common starting points and should be measured against the reader's own samples.
