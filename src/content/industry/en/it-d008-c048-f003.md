# Operations On-Duty and Internal Ticket Q&A for Security Monitoring and SOC Operations: Sharing and Embedding

## What Data for This Category Looks Like
Data for this category primarily comes from SIEM, EDR, NDR, and third-party threat intelligence sources, with update cadences of real-time or daily. Associated daily documents include alarm disposal tickets, on-duty records, threat intelligence briefings, and weekly or monthly security daily reports. Data fields include alarm unique identifiers, associated asset IPs, threat levels, disposal statuses, assignment times, and more. The data is constructed exclusively around the alarm circulation and disposal workflows for security operations, with no extra custom statistical fields.

## Constraints Imposed on Sharing and Embedding
Real-time updated alarm data requires that shared embedded chat windows can call external data sources to pull the latest information, avoiding returning outdated alarm details. Daily updated security briefings and daily reports require external knowledge base systems to support filtering associated documents by time range. FastGPT sharing and embedding only provides a basic display carrier. SOC analysts often work across multiple terminals, so embedded chat windows can be configured with adaptive display via the embedding code of FastGPT publishing channels, adapting to different browsers and terminal sizes. Alarm disposal tickets contain sensitive operation details, so identity authentication must be used to restrict unauthorized access and prevent sensitive information leaks. The high timeliness requirement for real-time alarm analysis requires that the response delay of the embedding function meets the response requirements of security operations.

## Three Common Misconfigurations
- Sharing entries related to security monitoring and SOC operations fail to open. First verify the full system-generated link and its validity period, then check browser request statuses; do not manually replace `shareId`.
- The visible scope of security monitoring and SOC operation data does not match expectations. Verify third-party identity verification results, workflow request parameters, and external system data permissions separately; the sharing entry identifier itself does not provide business authorization.
- The same security monitoring and SOC operation Q&A cannot be viewed on another device. For anonymous scenarios, first check device, browser, and local identity status; record retention cannot be guaranteed across devices or after clearing cache, so do not judge service abnormalities solely based on this phenomenon.

## How to Confirm Successful Configuration
- Open the share link, check whether login or team identity verification is required, and confirm that the authentication configuration takes effect.
- Initiate a query containing a known alarm ID, check whether the reply returns the latest alarm disposal status in real time, and confirm that the streaming output and external data source configuration take effect.
- Open the share link on different terminals and browser windows, check whether the chat window can adaptively display content, and confirm that the embedding adaptation configuration is correct.
- Copy the embedding code to a test page, initiate a query after loading, check whether the chat window can load normally and return associated alarm and document information, and confirm that the sharing configuration is correct.

The values provided are common starting points and should be validated against samples relevant to the specific use case.
