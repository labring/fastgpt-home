# Operations on-call and internal ticket Q&A for customer data import and migration: Deployment and upgrade

## What this category of data looks like
Data in this category typically comes from customer legacy systems, CSV or Excel templates, or database exports. Its update frequency is per order or irregular. Daily supporting documents include data templates, migration plans, field mapping tables, and migration verification reports. Core users are implementation consultants, data implementation engineers, and customer IT liaisons.
Data must go through three steps: field mapping confirmation, dirty data cleaning, and post-import sampling verification. Errors during this process may lead to loss of historical data, field misalignment, or customer rejection.

## What constraints do these characteristics impose on the deployment and upgrade phase
The diversity of data sources requires the deployment phase to support import adaptation configuration for multiple data formats. This prevents migration failures caused by format incompatibility.
The irregular update frequency means the system must be compatible with legacy import logs and field mapping rules after an upgrade. This ensures historical migration tasks can be reused normally.
The complexity of field mapping requires reserving extensible verification configurations during deployment. The dirty data cleaning link must also preset basic rules during deployment, to reduce subsequent manual processing time.
The linkage requirement between internal tickets and on-call operations requires configuring callback interfaces and status synchronization mechanisms during deployment. This ensures task progress can be synchronized to relevant on-call personnel in real time.

The following configuration applies to the customer data import and migration deployment scenario for FastGPT v4.17.0:
## How to set configurations

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–200 connections` | Adapt to database concurrency requirements during batch imports, avoid import interruptions caused by exhausted connections |
| `PG_URL` | `Fill in according to the actual deployed PostgreSQL vector database address` | Store import logs and field mapping configurations, must maintain connectivity with the vector database instance |
| `REDIS_URL` | `600-second timeout configuration` | Cache intermediate states of import tasks, avoid interruptions of long-duration batch import tasks due to connection timeouts |
| `FE_DOMAIN` | `Public network domain name of the deployment server or local IP:port` | Used to generate callback addresses for import tasks, ensure internal ticket systems can normally access the service |
| `ROOT_KEY` | `Strong security key calibrated through actual testing` | Protect the call permissions of the import API, prevent unauthorized bulk data operations |

## Three common mistakes
- The symptom is a batch import task timing out and failing, returning the `504 Gateway Timeout` status code. The cause is failure to adjust the `DB_MAX_LINK` configuration, leading to exhausted database connections during batch imports.
- The symptom is the web interface being unable to connect to internal services, with the import task showing "connection failed". The cause is using a fixed container IP as the service address, with connectivity interrupted after container restart due to IP changes.
- The symptom is field misalignment after import, with abnormal knowledge base data display. The cause is failure to pre-configure field mapping verification rules, and failure to enable field legality checks during the deployment phase.

## How to confirm configurations are correctly set
- Execute a small-scale single-batch import test task, check that there are no database connection errors in the import log, to confirm that the `PG_URL` and `REDIS_URL` configurations are valid.
- Restart the deployment service and associated containers, attempt to access the configured `FE_DOMAIN` address, to verify that the service can normally respond to requests.
- Upload a preset test CSV template, trigger the field mapping verification process, to confirm that the configured field rules can normally intercept invalid data.
- Trigger a callback interface call for the import task, check whether the internal ticket system receives synchronized task progress information, to verify that the API permission configuration is correct.
