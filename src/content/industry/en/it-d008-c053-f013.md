# Operations on-call and internal ticket Q&A for customer demand pool management: Permission and data isolation

## What the data for this category looks like
This category of data mainly originates from ticketing systems, customer interview records, CRM systems, and product roadmap documents. Data is updated weekly or upon each product version release. Daily maintained documents include demand pool lists, demand evaluation forms, customer feedback records, and version planning descriptions. Common data fields include demand number, associated customer identifier, demand content, priority score, scheduling status, etc. There is no unified industry standard field; the dataset only aligns with the business team’s filtering and sorting rules.

## What constraints do these characteristics impose on permission and data isolation
Since the data sources for this category are scattered and contain customer sensitive information, the access scope of different roles must be strictly differentiated. Operations on-call personnel can only view demand pool data associated with internal tickets. Customer success teams must only access customer feedback records for their assigned customers. Product managers can view all demand evaluation and planning documents. The weekly or per-version data update cycle requires that permission changes synchronize updated data access scopes to avoid information leaks or demand scheduling chaos caused by expired permissions. Mixed storage of multiple types of documents also requires setting differentiated isolation rules for different document templates to prevent unauthorized roles from accessing highly sensitive customer feedback or version planning content.

## How to configure the settings
The following configurations are adapted for FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Team data isolation configuration | Divide independent data spaces by `teamId` | Matches the storage logic of demand pool data grouped by customers or business teams |
| Role permission binding | Bind access permissions for corresponding roles to `teamId` and `tmbId` | Differentiates the different responsibility scopes of operations on-call, customer success, and product manager roles |
| Sensitive document isolation | Set customer feedback records to be accessible only by the corresponding team | Prevents unauthorized roles from accessing customer sensitive information |
| Permission synchronization latency | Synchronize permission rules within 12 hours after data update | Matches the weekly or per-version demand pool update frequency |
| Access log retention | Retain 90 days of permission operation and data access logs | Facilitates troubleshooting of issues such as distorted demand commitments or scheduling chaos |

## Three common configuration mistakes
- Scenario: After inviting a team member, the invited member does not receive a permission activation prompt and cannot access the specified demand pool data. Cause: The binding configuration between `teamId` and member roles was not fully synchronized, resulting in ineffective permissions.
- Scenario: Operations on-call personnel can view all customer feedback records, which exceeds their responsibility scope. Cause: An independent `teamId` isolation space was not set for the operations scenario, and full data permissions were mistakenly granted to the operations role.
- Scenario: A custom plugin bound to the demand pool returns empty results. Cause: The correct `teamId` parameter was not specified in the plugin configuration, so the corresponding data space cannot be matched.

## How to confirm configuration completion
- Test accounts with different roles can be used to verify that only demand pool documents and data within the corresponding responsibility scope are accessible.
- Team member invitations can be initiated to confirm that invited members receive system prompts related to permission configuration.
- Custom plugins bound to the demand pool can be called with the specified `teamId` parameter to verify that corresponding data results are returned.
- Permission operation logs can be reviewed to confirm that recent permission changes have taken effect in accordance with the configured synchronization latency.
