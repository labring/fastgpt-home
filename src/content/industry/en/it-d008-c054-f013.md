# Operational Duty Rounds and Internal Ticket Q&A for Container Platform Operations: Permission and Data Isolation

## What this category's data looks like
This category of data primarily originates from Kubernetes APIs, image registries, monitoring systems, and CI pipelines. Daily associated documents cover cluster change tickets, namespace quota tables, deployment records, and fault reports. Data updates occur either daily or in real time alongside cluster changes. Data fields include cluster node IDs, namespace quota values, Pod statuses, image version numbers, change approval statuses, and more. There is no unified fixed format, and the format adjusts based on cluster scale and operational workflows.

## Constraints imposed by these characteristics on permission and data isolation
Different operational roles require access to data within their respective scopes. Interns can only view data for the namespaces they manage. SREs need access to full cluster monitoring and change records. Cluster change tickets contain sensitive cluster expansion plans and permission configurations. Namespace quota tables cover resource allocation thresholds. Fault reports may include details of business interruptions. Administrators strictly bind API permissions from data sources to roles. CI pipeline logs are only accessible to change approvers. This prevents unauthorized users from accessing sensitive cluster configurations or fault traceability information. Knowledge base retrieved content must filter sensitive documents across namespaces to prevent unauthorized permission escalation.

## Configuration settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Configured per business team-bound namespace, such as dev-team-prod | Matches the team resource isolation rules of the container platform, binding knowledge base access permissions to the cluster resources managed by the team |
| `tmbId` | Configured per cluster node group, such as k8s-sre-group | Binds access permissions for the corresponding node group, restricting knowledge base calls from unauthorized operational nodes |
| Role permission grouping | Divide access scope by namespace | Aligns with the resource isolation logic of the container platform, matching the responsibility boundaries of different operational roles |
| Retrieved content filtering | Only retrieve documents that the current role has permission to access | Filters knowledge base content outside the permission scope to avoid sensitive configuration leaks |
| Session timeout setting | 1800 seconds | Prevents unused sessions from being misused by others, adapting to the operation duration of operational scenarios |
| Permission check trigger timing | Execute before each knowledge base call | Ensures that every Q&A request undergoes permission checks, preventing unauthorized access |

## Three common configuration errors
- Phenomenon: Knowledge base calls return empty results or prompt no permission to access. Cause: `teamId` is not bound to the namespace managed by the operational role, resulting in failed permission verification.
- Phenomenon: Team members cannot create knowledge base entries. Cause: Node group permissions associated with `tmbId` are not correctly configured, and the member's node is not included in the authorized scope.
- Phenomenon: Responses include cluster change ticket content from unauthorized namespaces. Cause: Retrieval filtering rules are not bound to namespace permissions, and full knowledge base documents are retrieved directly.

## How to confirm correct configuration
- Use a test role account to initiate a knowledge base call, and check that returned results only include documents related to the namespace managed by that role.
- View permission logs to confirm that each call carries the `teamId` or `tmbId` parameter, and that the parameter matches the role's permissions.
- Switch to an unauthorized role account to verify that documents such as cluster change tickets or fault reports from other namespaces cannot be accessed.
- In FastGPT v4.17.0, test the session timeout function to confirm that the session automatically expires and cannot continue calling the knowledge base after 1800 seconds of inactivity.
