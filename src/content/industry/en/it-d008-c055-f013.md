# Operational On-Call and Internal Ticket Q&A for Capacity Planning and Resource Scaling: Permission and Data Isolation

This document is based on FastGPT v4.17.0.

## What Data for This Category Looks Like
Organizations collect data for this category primarily from cloud bills, monitoring systems, business forecasting tools, and stress test reports. Four types of documents are routinely generated: capacity planning reports, expansion application tickets, resource utilization reports, and budget calculation sheets.

Data updates occur mostly on a weekly or monthly basis. Each individual data entry includes fields such as instance identifier, resource configuration parameters, usage duration, and predicted peak threshold. Corresponding units include cores, GB, hours, and times. Data links to the resource usage scope of specific business teams, and resource data from different teams does not overlap.

## How These Characteristics Impose Constraints on Permission and Data Isolation
This category’s data covers business resource information from multiple sources and links to the usage scope of specific business teams. Administrators must clarify access boundaries for resource data across different teams.

Data updates occur infrequently, so isolation configurations do not need frequent adjustments. These configurations must match the permission hierarchy of the expansion ticket approval process, to ensure only authorized personnel from the corresponding team can submit applications.

Each individual data entry contains sensitive resource configuration and budget information. Administrators must strictly restrict viewing and modification permissions for unauthorized users, to prevent resource data leaks or accidental operations. Additionally, stress test reports and forecasting data from different teams are internal business assets. Administrators must fully isolate these assets from datasets of other teams.

## How to Set Configurations
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| Team data isolation scope | Only display resource data linked to the team that the current user belongs to | Match the characteristic that data in this category is attributed to business teams, preventing cross-team resource leaks |
| Ticket permission binding rules | Bind ticket submission permissions by `teamId` and `tmbId` | Ensure expansion applications are only submitted by authorized personnel from the corresponding team, complying with the approval requirements of operational on-call work |
| Data synchronization cycle | Synchronize cloud bill and monitoring data once every 7 days | Match the weekly update frequency of data in this category, balancing data timeliness and system overhead |
| Sensitive data access control | Prohibit unauthorized users from viewing budget calculation sheets and stress test reports | Correspond to the sensitive nature of data in this category, preventing leakage of core business assets |
| Permission change approval | Take effect only after approval by the team leader | Adapt to the permission management specifications of operational scenarios, avoiding arbitrary adjustments to data isolation rules |
| Log retention configuration | Enable full permission operation logs, retain for 30 days | Meet the traceability requirements for operational activities, facilitating troubleshooting of permission violations |

## Three Common Misconfigurations
- Symptom: An error indicating no permission to access resource data of a specified team is displayed when submitting an expansion ticket, or the dataset for the second team cannot be switched. Cause: The binding relationship between `teamId` and the user account is not correctly configured, causing the system to fail to identify the business team scope that the user belongs to.
- Symptom: After deploying FastGPT and restarting the Docker container, an SQL permission error occurs when accessing capacity planning data. Cause: The permission mapping between `teamId` and database users was not resynchronized after the container restarted, causing database connection permissions to fail.
- Symptom: Cross-team operational personnel can view budget calculation sheets from other teams. Cause: The team data isolation scope configuration is not enabled, or the `teamId` scope for data access is not correctly limited during configuration.

## How to Confirm the Configuration Is Correct
- Administrators use an unauthorized user account to log in, check whether capacity planning reports from other teams can be viewed, and confirm that the data scope only includes resource data from the associated team.
- Administrators submit an expansion application ticket, check whether `teamId` binding is required, and confirm that only authorized users can submit applications for the corresponding team.
- Administrators restart the Docker container, test access to capacity planning data, and confirm that no SQL permission error occurs.
- Administrators view the permission operation logs, confirm that permission change operations have taken effect in accordance with the approval process, and confirm that logs are being retained normally.
