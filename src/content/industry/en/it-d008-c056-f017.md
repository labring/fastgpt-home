# Operations Duty and Internal Ticket Q&A for Object Storage and Backup Services: Deployment and Upgrade

## What the data for this category looks like
Typically, operational data for object storage and backup services comes from object storage consoles, backup systems, access logs, and customer policy tables. Daily operation documents include storage bucket configurations, backup policies, recovery records, and lifecycle rules. Data updates occur daily or when policies are modified.
The most time-consuming steps in operational work are permission policy verification, backup task monitoring, and recovery spot checks. Operational errors may lead to data leaks, backup failures, or recovery unavailability. This category focuses on file object and backup lifecycle management, and has clear differences from other cloud service categories.

## What constraints these characteristics impose on deployment and upgrade
Category data has multiple sources and updates frequently. During deployment, configuration items from multiple data sources such as object storage consoles and backup systems must be connected simultaneously to avoid missing key parameters.
Data field structures are complex. During the deployment phase, configuration fields related to storage buckets and backup policies must be checked one by one to prevent subsequent operational abnormalities caused by missing fields.
Since the consequences of operational errors are severe, a full backup of existing configurations must be performed before upgrading to avoid configuration loss during the upgrade process.
The high-frequency requirements for task monitoring and ticket queries also require reasonable configuration of connection pool parameters during deployment to ensure service stability in high-concurrency scenarios.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| ---|---|--- |
| `REDIS_URL` | `redis://:custom password@server address:6379/0` | Adapts to operational duty session caching and internal ticket data storage needs, prevents configuration loss |
| `MONGODB_URI` | `mongodb://username:password@server address:27017/fastgpt?authSource=admin` | Stores backup task logs, ticket records, and storage bucket configurations, matches the category data structure |
| `STORAGE_S3_ENDPOINT` | Official access address corresponding to the object storage service provider | Connects to the category's storage bucket configurations to enable persistent storage of backup data |
| `DB_MAX_LINK` | `20–30` | Adapts to the daily high-frequency backup task monitoring and ticket query request volume of the category |
| `FILE_TOKEN_KEY` | Randomly generated 32-bit string | Encrypts storage bucket access credentials to prevent unauthorized data access |
| `ROOT_KEY` | Custom high-complexity secret key | Manages the highest system permissions, matches the permission control requirements of operational duty |

## Three common mistakes
- Symptom: After deploying with docker-compose, workflow and knowledge base configuration items appear empty in the interface, but API calls work normally. Cause: `REDIS_URL` or `MONGODB_URI` is not configured correctly, resulting in configuration data failing to be persistently stored, and configurations being lost after container restart.
- Symptom: An OCI runtime create failed error is reported when starting the container. Cause: GPU dependency parameters are retained in the deployment configuration, and the deployment server is not equipped with GPU hardware, causing the container to fail to start.
- Symptom: The redis image fails to be pulled, and dependent services cannot be started. Cause: A redis image without a compatible tag specified is used. This version was added as a dependency in FastGPT v4.17.0, or the network environment cannot access the official image repository.

## How to confirm configurations are set correctly
- Run the `docker-compose ps` command to confirm that all dependent containers such as redis and mongodb are in a running state.
- Access the configured `FE_DOMAIN` address, log in to the system, and check whether storage bucket configuration lists and backup policy records load normally.
- Submit a test internal ticket to trigger a backup task monitoring query, and confirm that the number of records returned by the API is not empty.
- Modify `STORAGE_S3_ENDPOINT` to a test access address to verify that the storage connection can be established normally and return valid responses.

The values provided are common starting points and should be measured against the reader's own samples.
