# Operations Duty and Internal Ticket Q&A for Object Storage and Backup Services: Re-Ranking and Hybrid Retrieval

## What this category of data looks like
Object storage and backup service operations data originates from object storage consoles, backup systems, access logs, and customer policy tables. Daily operations documents include bucket configurations, backup policies, recovery records, and lifecycle rules. Fields cover bucket names, backup task IDs, recovery times, permission policy content, and additional relevant details. Units include GB, days, counts, and similar metrics. Data updates occur daily or in real time when policies change. Individual document lengths typically range from hundreds to thousands of characters.

## What constraints these characteristics impose on re-ranking and hybrid retrieval
This category of data includes both structured configuration items and semi-structured log content. Keywords are mostly operations-specific terminology. Field formats vary across different data sources. Hybrid retrieval must cover both configuration documents and log records, so it must adapt to multi-source data recall rules. The re-ranking step adjusts sorting logic based on operations scenario priorities, such as backup failure alerts taking priority over routine configurations. It also controls the total length of recalled data to avoid exceeding context window limits. The uncertainty of data updates requires retrieval logic to dynamically adapt to the latest policies.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Operations data mostly uses specialized terminology. A threshold that is too low will introduce irrelevant permission policy documents. A threshold that is too high will miss semantically related backup task records |
| `limit` | Top 5–10 entries | Valid information for operations tickets is usually concentrated in the most recent 5-10 associated records. Too many recalled entries will increase context processing load |
| `searchMode` | Hybrid retrieval mode | Needs to recall three types of data simultaneously: bucket configurations, backup policies, and access logs, to cover all information sources for operations scenarios |
| `usingReRank` | Enabled | There is a discrepancy between keyword matching accuracy and semantic relevance for operations data. Re-ranking can correct recall order, prioritizing content with higher relevance to ticket questions |
| Re-ranking recall cap | Top 3–5 entries | Key information for operations scenarios is usually concentrated in the 3-5 most relevant records. Too many entries will increase model inference time |

## Three Common Misconfigurations
- The symptom is a far lower-than-expected number of retrieval results. The root cause is a too-small `limit` parameter value, without adjusting the parameter upper limit to match the hybrid recall range of `searchMode`.
- The symptom is low result relevance even after re-ranking. The root cause is an overly high `similarity` threshold, which filters out some semantically related backup policy documents with average keyword matching accuracy.
- The symptom is a retrieval function error after service startup. The root cause is missing required environment variables for the App/Admin server: AIPROXY_API_ENDPOINT (root address of the AI Proxy service, do not append paths such as /v1, not a single-model address) and AIPROXY_API_TOKEN (AI Proxy administrator token, consistent with AI Proxy server configuration and non-empty). This is a startup verification failure issue that causes re-ranking model calls to fail.

## How to Verify Correct Configuration
- Review the App/Admin server environment variables. Confirm that AIPROXY_API_ENDPOINT and AIPROXY_API_TOKEN are correctly configured and non-empty, complying with FastGPT v4.17.0 deployment requirements. AIPROXY_API_ENDPOINT is the root address of the AI Proxy service, do not append paths such as /v1, and is not a single-model address. AIPROXY_API_TOKEN is the AI Proxy administrator token, consistent with the AI Proxy server configuration.
- Submit a test operations ticket. Confirm that the number of retrieved results matches the `limit` parameter setting, and verify that hybrid retrieval covers multiple data sources.
- Enable the re-ranking function, then compare result sorting before and after enabling. Confirm that the re-ranking logic adjusted the result order.
- Simulate a backup failure ticket. Verify that retrieval results prioritize backup task records and recovery logs.
