# Operations Duty and Internal Ticket Q&A for Performance Testing and Capacity Assessment: Permission and Data Isolation

## What This Category of Data Looks Like
Data for performance testing and capacity assessment primarily originates from stress testing platforms, APM monitoring tools, database slow logs, and production traffic baselines. Daily deliverable documents include stress testing plans, capacity assessment reports, stress testing data records, and optimization suggestion sheets. Common data fields include throughput (unit: TPS), average latency (unit: milliseconds), server resource utilization (percentage), capacity threshold (unit: GB), and others. Data update frequency is typically once per month, or synchronized following major version releases.

## What Constraints Do These Characteristics Impose on Permission and Data Isolation
Data for this category includes sensitive information such as production environment traffic baselines and stress testing resource configurations, and ties to the responsibility scopes of testing, operations, architecture, and other teams. Stress testing data for separate projects must be isolated by project group to prevent cross-project unauthorized access. If global variables are not isolated by user, identical-named configurations from different test engineers will interfere with one another, reducing the accuracy of stress testing models. Unmasked sensitive production traffic baseline data may expose production details during internal ticket Q&A. Additionally, data update frequency is relatively fixed. Permission configurations must be verified synchronously with data updates to avoid outdated permission rules applying to new sensitive data.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Bind to stress testing project group ID, range `1001–2000` | Match the project grouping rules of the stress testing platform, ensure only project group members can access corresponding stress testing data and documents |
| `tmbId` | Associate with stress testing task template ID, range `5001–6000` | Isolate stress testing configurations and historical results for different templates, avoid data confusion between templates |
| Permission role configuration | Divided into three levels: test engineer, architect, operations administrator | Match the responsibility division of the business scenario, restrict permissions for document viewing, ticket submission, and data modification for different roles |
| Sensitive data masking | Mask production traffic baseline fields, retain the first 20% of characters | Avoid direct exposure of sensitive production data during internal ticket Q&A |
| Session isolation policy | Isolate global variables by user ID | Ensure that identical-named global variables from different users do not interfere with one another |

## Three Common Misconfigurations
- Symptom: Identical-named global variables across different test engineers overwrite one another, resulting in abnormal stress testing model calculation results. Cause: Session isolation policy by user ID is not configured, so global variable scopes are not differentiated by user ID.
- Symptom: Non-project group members can directly access stress testing data records and capacity assessment reports. Cause: The `teamId` parameter is not bound, and data access scopes are not divided by project group, leading to cross-project unauthorized access.
- Symptom: Full production traffic baseline details are returned during internal ticket Q&A. Cause: Sensitive data masking configuration is not enabled, so sensitive production fields are directly returned during the Q&A process.

## How to Verify a Correct Configuration
- Use an account outside the target project group to access documents for the corresponding stress testing project. Confirm that access is denied or an insufficient permissions prompt is displayed.
- Switch between different user accounts, submit query requests for identical-named global variables. Confirm that each returned variable value matches the configuration content for that user.
- Submit a query that includes production traffic baseline fields. Confirm that sensitive fields in the returned results are masked, with only the specified percentage of visible content retained.
