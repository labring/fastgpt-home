# Database Cloud Service Operations: On-Duty Work and Internal Ticket Q&A – Permission and Data Isolation

## What This Type of Data Entails
Daily data for database cloud service operations originates from cloud database consoles, slow logs, monitoring metrics, and internal ticket systems. Daily generated documents include instance change orders, backup and recovery records, performance diagnosis reports, and parameter adjustment records. Fields include instance unique identifier, change time, backup file size (unit: MB), slow SQL execution duration (unit: seconds), pre- and post-adjustment parameter values, and other related fields. Data updates occur daily or after each instance change. Monitoring metrics are pushed in real time. Ticket records are updated synchronously as they move through internal workflows.

## Constraints for Permission and Data Isolation
Data for database cloud service operations comes from multiple sources and is tied to instance resources. This creates multiple constraints for permission and data isolation. Cross-system data from multiple sources requires unified validation rules to prevent permission vulnerabilities across systems. Data updates occur frequently and involve sensitive operations. Permission checks must trigger before each operation to prevent unauthorized modification or access. Internal tickets are tied to instance resources. Access scope must be divided by tenant and role to ensure only authorized personnel can view change, backup, and diagnosis data for their assigned instances. Multi-tenant boundaries for cloud services require permission configurations to match tenant identifiers from cloud consoles, preventing cross-tenant data leaks.

## Configuration Guidelines
This page’s configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Match the cloud console tenant ID | Aligns with resource ownership for cloud database multi-tenancy, preventing cross-tenant data access |
| `tmbId` | Bind to the first 5 permission groups for the corresponding role | Distinguishes different operational permissions for DBAs, on-duty operations staff, and customer support |
| Data Access Scope | Limit to all associated data for the current instance | Prevents access to sensitive data for other cloud database instances |
| Permission Check Trigger Timing | Validate before each operation | Adapts to scenarios with high data update frequency, avoiding unauthorized access caused by expired permissions |
| Single Data Pull Limit | Top 50 entries | Limits the volume of sensitive data returned in a single request, reducing the impact scope of unauthorized access |
| Audit Log Retention Period | 30 days | Meets conventional retention requirements for internal operations audits |

## Three Common Misconfigurations
- Phenomenon: An error indicating the username is invalid appears when adding team members. Cause: The member’s permission configuration is not bound to the cloud tenant scope corresponding to `teamId`, so the system cannot recognize cross-tenant member identifiers.
- Phenomenon: No permission block occurs when viewing slow logs or backup records across cloud database instances. Cause: Data access scope is not configured to limit to the current instance, and permission checks do not match resource ownership.
- Phenomenon: Failure occurs when calling an application as a tool, with an insufficient permissions prompt. Cause: Plugin permissions are not bound to the operations role group corresponding to `tmbId`, resulting in insufficient permissions to trigger tool calls.

## How to Verify Proper Configuration
- Attempt to add a member that does not belong to the current `teamId`, and confirm the system prompts insufficient permissions or an invalid username.
- Switch to the console for another cloud database instance, and confirm that change orders and backup records for the current instance cannot be viewed.
- Call a custom plugin, and confirm that only members of the role group bound to `teamId` are allowed to use it.
- View system audit logs, and confirm that all operations record associated information for `teamId` and `tmbId`.
