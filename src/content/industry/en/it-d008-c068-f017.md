# Operations On-Duty and Internal Ticket Query for Database Cloud Service Operations: Deployment and Upgrade

## What Data for This Category Looks Like
Normally, data sources for database cloud service operations include cloud database consoles, slow logs, monitoring metrics, and internal ticket systems. Daily generated documents include instance change tickets, backup and recovery records, performance diagnosis reports, and parameter adjustment records. Each document is associated with a unique instance ID and operation timestamp. Data update frequency is daily or after each instance change. Fields typically include instance identifier, operation type, time consumed, and result status. There is no unified mandatory format requirement.

## Constraints Imposed by These Characteristics on Deployment and Upgrade
Because data sources cover multiple types of cloud resources and internal systems, access permissions and connection parameters for multiple data sources must be configured during deployment. During upgrade, API format differences across cloud vendors must be accommodated. Data updates occur at high frequency, so the deployed query system must support incremental pulling to avoid excessive cloud resource usage. Daily documents are associated with fields such as instance ID, so field mapping rules for the knowledge base must be configured during deployment to ensure the query system can accurately associate corresponding operation and maintenance data.

## How to Configure Parameters
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Intranet connection string for the cloud-hosted MongoDB instance, including authentication information | Stores knowledge base vectors and operation and maintenance ticket data; uses intranet addresses to reduce network latency and public network traffic costs |
| `REDIS_URL` | Intranet connection address for the local Redis instance, default port `6379` | Caches slow log retrieval results and user sessions to reduce overhead from repeated pulling of cloud resources |
| `DB_MAX_LINK` | `150–250 connections` | Limits database connection count to avoid exceeding the default maximum connection limit for cloud database instances |
| `FE_DOMAIN` | Public or intranet domain for the deployed service | Configures jump and resource loading paths for the query interface, adapting to network access policies in cloud environments |
| `STORAGE_S3_ENDPOINT` | Intranet Endpoint for the cloud vendor's object storage | Stores attachments for backup and recovery records and performance diagnosis reports; uses intranet addresses to avoid public network traffic fees |
| `FILE_TOKEN_KEY` | `3600 seconds` | Configures the validity period of file upload tokens to reduce abuse risk after token leakage |

## Three Common Misconfiguration Issues
- Symptom: A network error is displayed when deleting a self-built application. Cause: `FE_DOMAIN` was not correctly configured during deployment. Frontend requests fail to point to the correct backend service address, leading to failed interface calls.
- Symptom: After upgrading to FastGPT v4.17.0, the existing shared link authentication function cannot be found. Cause: The deployment documentation for the corresponding version was not reviewed. The location of authentication configuration items was adjusted in the new version, and configuration parameters were not updated synchronously.
- Symptom: An empty result is returned when triggering slow SQL retrieval. Cause: `STORAGE_S3_ENDPOINT` was not correctly configured to point to the cloud vendor's slow log storage path, resulting in failure to pull slow log data for retrieval.

## How to Verify Successful Configuration
- Access the query interface corresponding to the configured `FE_DOMAIN`, verify that it loads normally and that queries can be initiated, with no resource loading failure prompts.
- Log in to the cloud database console, check that the configured `MONGODB_URI` and `REDIS_URL` can establish normal connections, with no authentication failure or timeout prompts.
- Upload an instance change ticket document to the knowledge base, verify that the query system can correctly extract instance ID and change content fields.
- Trigger a slow SQL retrieval request, check that expected log entries are returned, with no empty results or error messages.

The values given are common starting points and should be measured against the reader's own samples.
