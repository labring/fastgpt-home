# Database Operations & Maintenance On-Duty and Internal Ticket Q&A: Deployment and Upgrade

## What This Category of Data Looks Like
Data for this category is primarily collected from database monitoring, audit logs, SQL execution plans, and internal ticket systems. Daily associated documents include database change orders, slow SQL analysis reports, backup and recovery records, and permission application forms. Data update frequency is daily or triggered by individual database changes. Data fields include instance identifier, execution duration, permission scope, change content, and more. Units adjust flexibly based on specific monitoring items and document types.

## What Constraints Do These Characteristics Impose on Deployment and Upgrade
This category’s data characteristics impose multiple constraints on deployment and upgrade workflows.
Multi-source data sources require connecting internal ticket systems, database monitoring tools, and FastGPT permission channels during deployment to avoid cross-system data isolation.
Update frequencies triggered by changes require reserving independent change windows for upgrades to avoid conflicts with business database change cycles.
The lack of unified field units requires configuring multi-source data format conversion rules during deployment to prevent field parsing errors.
Processing permission-related data requires strict verification of access permission configurations during upgrades to prevent permission overreach.

## How to Configure
This configuration rule applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `100–200 connections` | Adapts to concurrent connection requirements in database operations scenarios, avoids connection exhaustion impacting business |
| `MONGODB_URI` | `Dedicated connection string for privately deployed clusters` | Meets persistent storage needs for tickets and monitoring data, ensures internal enterprise data security |
| `PG_URL` | `Built-in PostgreSQL instance connection address` | Stores system configuration and user permission data, complies with permission control requirements for database operations |
| `REDIS_URL` | `127.0.0.1:6379 (add authentication password parameter when required)` | Caches slow SQL queries and ticket status, reduces query pressure on core databases |
| `FE_DOMAIN` | `Internal operations platform secondary domain name` | Adapts to enterprise intranet integration requirements, ensures front-end pages are accessible in specified intranet environments |
| `ROOT_KEY` | `32-character random string` | Ensures security of system background access permissions, prevents unauthorized operations |

## Three Common Misconfigurations
- External service connection errors appear on port 3005, while the port 3000 service runs normally. The cause is that modified configurations were only synchronized to some container instances, and full deployment updates were not completed. This results in port binding configurations not taking effect.
- No embeddable front-end page can be found, and only API-based system access is available. The cause is that the front-end build step was not executed during deployment, or `FE_DOMAIN` was not correctly configured to point to the front-end service address.
- Database connection timeout errors occur during deployment. The cause is that the `DB_MAX_LINK` configuration value is too low, leading to concurrent connection exhaustion and inability to establish new database sessions.

## How to Confirm Configuration Is Correct
- Execute database connection test commands to verify the connection validity of `PG_URL` and `MONGODB_URI` configurations, confirm no timeout or permission denied errors.
- Access the configured `FE_DOMAIN` address, confirm the front-end page loads normally, and slow SQL reports and internal ticket lists can be queried.
- Submit a test database change ticket, verify the system can normally receive and generate corresponding processing records.
- View Redis service logs, confirm the cache service configured via `REDIS_URL` can normally read and write data, with no connection failure records.

The values provided are common starting points and should be measured against the reader's own samples.
