# Operations Duty and Internal Ticket Q&A for Data Cleaning and Quality Inspection: Permissions and Data Isolation

## What Data in This Category Looks Like
Core data for data cleaning and quality inspection scenarios includes four types of documents: cleaning rules, quality inspection sampling tables, abnormal data lists, and delivery reports. Data sources include original datasets, ETL operation logs, annotation platform outputs, and sampling quality inspection results. Data update frequency is daily or triggered per batch task. The volume of data per batch task varies with business scale. Document fields include task identifiers, data scope, processing rules, sampling ratio, anomaly markers, delivery status, and more. Some associated fields require binding to permission identifiers of corresponding business entities.

## What Constraints Do These Characteristics Impose on Permissions and Data Isolation
Data in this scenario is multi-source and contains business-sensitive content. Permission isolation must match the hierarchical differences of data sources. Set different access permissions for resources such as original datasets and ETL logs. Data is updated daily or per batch. Support dynamic adjustment of the effective permission scope based on task cycles, to avoid expired or untimely effective permissions. Documents include core business content such as cleaning rules and abnormal data lists. Restrict access to only engineers, quality inspectors, and project managers of the corresponding project. The business entity identifiers bound to fields serve as the core basis for permission verification, to prevent cross-project unauthorized data access.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| ---|---|--- |
| `teamId` | Bound to the unique identifier of the corresponding business project | Data cleaning and quality inspection tasks are divided by project. `teamId` can directly associate with the project permission scope to filter cross-project data |
| `tmbId` | Bound to the unique employee identifier of a single business member | Internal ticket and duty scenarios require filtering data by member permissions, to prevent unauthorized personnel from viewing sensitive business documents |
| SSO Authentication Integration | Configured to integrate with the enterprise's own SSO service, with timeout threshold set to 30–60 seconds | Operations duty scenarios are mostly deployed in internal networks. Unified identity authentication simplifies the login process and adapts to internal network environments |
| Historical Version Data Isolation | Enable `tmbId` field verification, historical versions with missing fields are visible only to project administrators by default | Adapts to scenarios where historical documents do not have the `tmbId` field, to prevent unauthorized access to old version data |
| Role Permission Division | Allocate permissions by position: data engineers can edit cleaning rules, quality inspectors can view sampling results, project managers can view full delivery reports | Matches the job division in data cleaning and quality inspection scenarios, restricting the operation and viewing scope of different roles |

## Three Common Misconfigurations
- When integrating SSO after internal network deployment, connection timeout or authentication failure may occur. The symptom is an authentication failure prompt popping up on the interface, and logs show the SSO service address cannot be accessed. The cause is failure to configure the SSO service whitelist for the internal network environment, or setting the timeout threshold too short.
- Permission verification failure may occur when viewing historical version data. The symptom is that some old version documents lack the `tmbId` field, so they cannot match current permission rules. The cause is failure to enable compatible verification logic for the `tmbId` field, or failure to set default permissions for historical data without this field.
- Database connection refused errors may occur during internal network deployment. The symptom is logs showing MySQL connection is refused, even though the MySQL service starts normally. The cause is failure to configure the internal network whitelist for database access, or failure to open the corresponding port for the database binding address.

## How to Confirm the Configuration Is Correct
- Test using the FastGPT v4.17.0 system. Log in to the account associated with the target project, and attempt to access cleaning rule documents that do not belong to the current project. Confirm that the documents cannot be viewed or prompt for no permission.
- View historical documents in the MongoAppVersion table. Confirm that versions missing the `tmbId` field are accessible only to project administrators.
- Test the SSO authentication process in the internal network environment. Confirm that users can log in directly using an enterprise account, without repeatedly entering account passwords.
- Attempt to add a team member. Enter the corresponding employee identifier, and confirm that the user name displays normally and permissions can be assigned.
