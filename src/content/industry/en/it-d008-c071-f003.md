# Operations on-call and internal ticket Q&A for data masking: Sharing and Embedding

## What the data for this category looks like
Data for this category comes from enterprise databases, data dictionaries, in-house masking tools, and access approval systems. Daily produced documents include masking plans, field mapping tables, masking validation reports, and approval records. Data update cycles follow individual projects or project phases, with one data update completed after each full masking workflow. Data fields include sensitive field identifiers, masking rule codes, validation results, approval status, and more. There are no uniform fixed units; field values adjust based on specific project scenarios.

## What constraints these characteristics impose on the sharing and embedding workflow
This category’s data contains sensitive fields and its sources involve internal systems. When sharing or embedding, access subjects must be strictly restricted via external business systems or commercial edition identity verification, and only internal operations and data security personnel are allowed access. Data updates follow individual project or batch cycles; connected knowledge bases or external business systems must support project-triggered data synchronization to avoid masking rule failures caused by cached expiration. Daily documents have diverse formats. The embedding link must rely on external business systems or knowledge bases to parse multiple document types, ensuring that masking plans, validation reports, and other content can be read normally. For internal ticket scenarios, external business systems must associate approval record fields. FastGPT’s sharing and embedding link only displays masked data. Permission control must be implemented via external business systems or commercial edition identity verification.

## Three common configuration mistakes
- Sharing entry for data masking processing fails to open. First verify the full system-generated link and its validity period, then check browser request status; do not manually replace `shareId`.
- Visibility range of data masking processing data does not match expectations. Verify third-party identity verification results, workflow request parameters, and external system data permissions separately; the sharing entry identifier itself does not provide business authorization.
- The same data masking processing Q&A is not visible on another device. For anonymous scenarios, first check device, browser, and local identity status; retention cannot be guaranteed across devices or after cache clearing, so do not judge service anomalies solely based on this phenomenon.

## How to confirm the configuration is complete
- Open the publish channel - no-login window page of the corresponding application, verify that the `shareId` in the share link matches the ID configured in the embedding module.
- Use the corresponding share link to access the embedding page, validate that the sensitive field filtering rules configured by the connected external business system take effect, and unauthorized access cannot obtain embedded content.
- Trigger the document synchronization operation of the external business system or knowledge base, verify that the embedding module can load the latest masking plans, validation reports, and other content.
- Open the embedding page in different modern browsers, combine with the style configuration of the embedding carrier page, verify that page rendering is normal with no typesetting errors.
