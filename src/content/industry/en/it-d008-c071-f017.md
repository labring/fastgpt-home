# Data Masking Processing Operations On-Duty and Internal Work Order Q&A: Deployment and Upgrade

## What data in this category looks like
The main body of data for this category is maintained by data security engineers, data service teams, and compliance personnel. Daily documents include masking plans, field mapping tables, masking verification reports, and approval records. Data sources cover business databases, data dictionaries, masking tools, and access approval systems. Update frequency follows each batch task or individual project cycle. Core processing steps include sensitive field identification, masking rule configuration, and availability verification. Data changes are directly linked to compliance audit results, and the risk of exposing sensitive information must be strictly controlled.

## What constraints these characteristics impose on the deployment and upgrade link
The data sources for this category are scattered, and update schedules are flexibly adjusted based on projects. The deployment link must adapt to connection configurations for multiple types of data sources, ensuring that masking rules can be synchronized to different storage nodes. Most data documents are structured configuration files and approval records. The upgrade process must retain compatibility with historical masking configurations to avoid invalidation of field mapping relationships due to version updates. Additionally, masking verification data under compliance requirements must be synchronized in real time. The deployment link must reserve sufficient cache and storage resources to ensure smooth sensitive field identification and rule verification. For FastGPT v4.17.0, additional adaptation of the permission framework configuration logic is required to avoid conflicts between configuration items and existing permission rules.

## How to set the configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 15–25 connections | Adapt to concurrent connection requirements for multiple data sources, avoid connection exhaustion when reading sensitive data |
| `MONGODB_URI` | Points to a dedicated database instance for storing masking rules | Isolate masking configurations from business data to prevent configuration leaks |
| `PG_URL` | Configure read-only access permissions for the field mapping table | Ensure safe reading of mapping data during sensitive field identification |
| `REDIS_URL` | Configure as a dedicated cache node, set timeout to 3600 seconds | Cache masked session context and verification results, reduce repeated identification overhead |
| `STORAGE_S3_ENDPOINT` | Point to a compliant storage bucket and enable version control | Store masking verification reports and approval records to meet audit traceability requirements |

## Three common mistakes
- Symptom: When using aiproxy to deploy a voice model, the curl test succeeds but returns code 500 Cannot read p. Cause: The `REDIS_URL` configuration does not sync masked session cache rules, resulting in missing fields when reading request context.
- Symptom: Third-party model test fails with 400 error. Cause: The sensitive field mapping table configured in `PG_URL` is not loaded correctly, leading to failed parameter verification during model invocation.
- Symptom: After uploading a file via the API, the agent backend cannot be accessed and the process hangs. Cause: The storage path configured in `STORAGE_S3_ENDPOINT` does not adapt to masked file metadata, resulting in failed file indexing and blocking subsequent requests.

## How to confirm the configuration is complete
- Check the connection logs for `DB_MAX_LINK` to confirm that the number of multiple data source connections does not exceed the configured threshold.
- After importing the field mapping table, run a sensitive field identification test to verify that the configured mapping relationship takes effect.
- Initiate a masking task to check whether the `REDIS_URL` cache node generates corresponding masking verification results.
- Access the storage bucket corresponding to `STORAGE_S3_ENDPOINT` to confirm that masking verification reports and approval records have been uploaded correctly.

The values provided are common starting points and should be measured against the reader's own samples.
