# Operations Duty and Internal Ticket Q&A for Data Masking Processing: Re-Ranking and Hybrid Retrieval

## What this category of data looks like
Data for this category primarily comes from enterprise internal databases, data dictionaries, data masking tool operation logs, and access approval systems. Primary service users include data security engineers, data service teams, and compliance personnel. Daily maintained documents cover data masking plans, field mapping tables, masking verification reports, and approval records. Data updates per project batch or single task, with no fixed cycle. Data fields include sensitive field identifiers, masking rule codes, verification results, approval status, and other fields. No unified mandatory units exist. Values adjust based on project configuration.

## What constraints do these characteristics impose on re-ranking and hybrid retrieval
Data for this category comes from scattered heterogeneous sources including databases, tool logs, and approval systems. Hybrid retrieval requires integrating valid data across different formats. Data updates per project batch. During retrieval, prioritize currently active project configuration data. This avoids calling expired masking rules. Daily document types are diverse, including plans, mapping tables, and verification reports. Re-ranking requires distinguishing information priority across different documents. Prioritize content directly related to sensitive field processing. Sensitive field identifier fields account for a high proportion. Retrieval must focus on keywords related to sensitive information processing. This avoids interference from irrelevant general operations and maintenance content.

## Three Common Mistakes
- Symptom: The interface displays `Invalid URL (POST /v1/rerank)`. The re-ranking model call fails. Cause: The re-ranking model API access address was not configured correctly, or the oneAPI re-ranking model forwarding path was not mapped properly.
- Symptom: Calling the re-ranking model returns a `401 unauthorized` error. Cause: The correct re-ranking model API key was not entered in FastGPT configuration, or the key has insufficient permissions.
- Symptom: Hybrid retrieval returns large amounts of non-sensitive content. Screening efficiency is low. Cause: The re-ranking function was not enabled, or the similarity threshold does not meet business needs. This results in recall of irrelevant results.

## How to Confirm Configuration Is Complete
- Access the scenario configuration page of FastGPT v4.17.0. Verify the `usingReRank` toggle is enabled.

- Adjust values of relevant configuration items based on actual operations and maintenance scenarios. Verify results meet business screening needs.
