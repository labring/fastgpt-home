# Operations On-Call and Internal Work Order Q&A for Data Collection Task Design: Knowledge Base Retrieval and Recall

## What This Category of Data Looks Like
This category of data is generated across the full lifecycle of collection tasks. Routine documents include collection plans, sample specifications, authorization instructions, and task schedules. Data sources cover customer requirements, public data sources, collection tool outputs, and internal sample libraries. Update frequency is per individual project or weekly. Data fields include sample scope, collection fields, authorization qualifications, schedule nodes, and more. Compliance and business alignment must be balanced. Core links focus on sample scope definition, field specification confirmation, and collection legality verification.

## What Constraints Do These Characteristics Impose on the "Knowledge Base Retrieval and Recall" Link
The data characteristics of this category impose multiple constraints on retrieval and recall. Data sources are scattered and include compliance documents. Accurately distinguish content from different sources such as customer requirements, public data sources, and collection tool documents to avoid retrieving irrelevant fragments. Update frequency is per individual project or weekly, so partition retrieval scope by project to prevent interference from cross-project data. Documents include dynamic content such as sample scope and field specifications. Adjust recall boundaries to fit task scenarios during retrieval, while prioritizing retrieval of authorization-related compliance documents to reduce risks of infringement and rework.

## How to Configure the Settings
Configuration settings are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | Matches compliance documents and field definitions for collection tasks. This range filters low-relevance general operations content, retaining sample specifications and authorization instructions highly relevant to collection tasks |
| `limit` | Top 8–12 entries | Documents for collection tasks are mostly structured plans and schedules, and a small number of highly relevant entries can cover task requirements, avoiding excessive redundant content that interferes with judgment |
| `searchMode` | Semantic retrieval | Documents in this category include non-standard task descriptions. Semantic retrieval better matches vague sample scope queries, with better matching results than hybrid retrieval mode |
| `usingReRank` | Enabled | For high-value documents related to collection compliance, reranking can further screen out high-priority content related to authorization instructions and legality verification |
| `datasetSearchUsingExtensionQuery` | Enabled | Automatically expand the query scope based on task keywords entered by users, matching implicit field specification requirements in collection plans |
| `collectionIds` | Bind specified collections by project | Distinguishes knowledge bases for collection tasks of different projects, avoids confusion of cross-project data, and aligns with the update frequency feature per project |

## Three Common Misconfigurations
- Phenomenon: After multiple rounds of questions in the same conversation window, knowledge base retrieval latency increases significantly, and in some scenarios exceeds 60 seconds. Cause: `collectionIds` are not bound by project, so the retrieval scope includes collection task documents from all historical projects, resulting in an overly large volume of retrieved data.
- Phenomenon: Semantic retrieval scores are high, but returned content is irrelevant to the current collection task. For example, authorization instructions from other projects are retrieved. Cause: The `similarity` threshold is not adjusted, or `usingReRank` is not enabled, failing to filter low-relevance but high-scoring general documents.
- Phenomenon: When using hybrid retrieval mode, field specification conflicts appear in returned collection plan content. Cause: Hybrid retrieval relies on both keywords and semantics. Keyword matching matches irrelevant historical schedule content, interfering with the accuracy of semantic matching.

## How to Verify Successful Configuration
- Initiate a keyword query targeting the current project's collection plan, and verify that returned results only cover collection documents for the current project, with no redundant content from other projects.
- Initiate more than 3 consecutive identical queries, and confirm that retrieval latency does not fluctuate significantly, and no timeout errors occur.
- Test returned results for different retrieval modes, and confirm that semantic retrieval results better fit the sample definition and compliance requirements of the collection task.
- Trigger retrieval with extended query, and confirm that returned content includes field specification-related information not directly mentioned in the user's input.

The values provided here are common starting points, and should be evaluated against samples from actual deployments.
