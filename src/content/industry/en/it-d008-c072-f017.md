# Operations on-duty and internal work order query for data collection task design: Deployment and upgrade

## What the data for this category looks like
Service subjects for this category include data service project managers, collection teams, and customer algorithm teams. Data comes primarily from customer requirements, public data sources, collection tools, and in-house sample libraries. Daily output documents fall into four categories: collection plans, sample specifications, authorization descriptions, and task schedules. Data updates occur once per project cycle or weekly. Core fields include collection scope tags, target data types, authorization compliance requirements, and task schedule nodes. Some fields must match the adaptation format of collection tools. Field attributes are defined only by business scenarios, with no fixed mandatory units.

## What constraints these characteristics impose on deployment and upgrades
The multi-source nature of data related to collection task design demands that deployments support multi-format data source access configuration, and upgrades retain compatible logic for historical collection plans. The per-project or weekly update feature demands that deployment environments support persistent storage for periodic task scheduling, to avoid configuration loss after restarts. The structured requirement for document data demands configuring adaptation rules for document parsing during deployment, and synchronously updating verification logic for document fields during upgrades. Compliance-related fields demand configuring intermediate storage for authorization verification during deployment, and synchronously updating rule versions for compliance verification during upgrades.

## How to set configurations
This configuration applies to FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–200 connections` | Adapts to concurrent requests from multiple data sources for collection task design, avoids connection pool exhaustion |
| `REDIS_URL` | Intranet-accessible persistent Redis instance address | Stores schedules and temporary status of periodic collection tasks, prevents data loss after restarts |
| `MONGODB_URI` | MongoDB instance address mounted with local persistent storage | Stores structured document data such as collection plans and sample specifications, supports project-level isolation |
| `FE_DOMAIN` | Intranet-deployed frontend access domain name | Configures callback addresses for collection tasks and document preview links, adapts to intranet access scenarios |
| `STORAGE_S3_ENDPOINT` | Intranet MinIO service address | Stores collected original sample data, replaces public cloud storage to fit intranet environments |
| `ROOT_KEY` | `Randomly generated 32-bit string` | Configures authentication keys for internal system interfaces, prevents unauthorized access to collection task configurations |
| `FILE_TOKEN_KEY` | `Randomly generated 64-bit character string` | Encrypts storage paths of collected samples, prevents unauthorized access to raw data |

## Three common misconfigurations
- Intranet deployments experience database connection timeout errors: The cause is failing to configure intranet-accessible `MONGODB_URI` or `REDIS_URL`, using public cloud addresses that cannot be connected.
- Collection configuration and sample data is lost after each Docker container restart: The cause is failing to mount MongoDB or Redis data directories to local persistent storage, so temporary storage data is cleared after container restarts.
- No docking notification is received after submitting internal work orders or commercial procurement forms: The cause is failing to correctly configure the callback address for `FE_DOMAIN`, so system notifications fail to reach the specified intranet address.

## How to confirm configuration is correct
- Log in to the frontend console, view the created collection task list and configuration items, confirm no configuration loss after container restarts, verify persistent storage is working.
- Initiate a test collection task, check that the data source connection status shows normal, verify that the `DB_MAX_LINK` database connection pool configuration matches actual requests.
- Modify the `FE_DOMAIN` configuration, access the preview link of the collection task, confirm the jump address matches the configuration, verify the frontend domain name configuration is effective.
- Call internal interfaces with `ROOT_KEY` for authentication, confirm an unauthorized error is returned when the key is not carried, verify the authentication configuration is correct.

The values provided here are common starting points, and should be evaluated against the user’s own samples.
