# Dataset Delivery and Version Management for Operations On-Call and Internal Ticket Q&A: Deployment and Upgrade

## What Data for This Category Entails
Data for this category is typically produced by data project managers, data engineers, and customer algorithm teams. Daily supporting documents include dataset descriptions, version records, delivery checklists, and acceptance reports.
Data sources include object storage, data warehouses, annotation platforms, and customer acceptance feedback. Update rhythm follows each batch delivery or version release.
Data fields include version numbers, sample difference descriptions, and delivery integrity check items. Common units are batch numbers, character counts, and check item quantities. The core focus is traceability management of delivery packages.

## Constraints Imposed on Deployment and Upgrade
These data characteristics impose multiple constraints on the deployment and upgrade process.
Scattered data sources require configuring interface permissions to connect multiple storage types and platforms during deployment. This prevents data synchronization failures caused by incomplete access.
The per-batch or per-version update rhythm requires the upgrade process to support incremental synchronization and version rollback mechanisms. This prevents data disorder caused by full overwrites.
Verification requirements for fields such as version numbers and sample difference descriptions require presetting verification rules during deployment. Field integrity must be verified after upgrade.
Customer acceptance feedback, as one of the data sources, requires configuring a receiving path for feedback data during deployment. This ensures subsequent iterations can be adjusted based on feedback.
The traceability requirement for delivery packages requires retaining version-associated logs during deployment. This facilitates troubleshooting ticket issues during operations on-call shifts.

## Configuration Settings
This document applies to the deployment and upgrade scenarios of FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://username:password@host:port/dbname?authSource=admin` | Used to store dataset version records, delivery checklists, and acceptance reports, adapting to storage requirements for multi-source data |
| `REDIS_URL` | `redis://:password@host:port/0` | Caches version verification rules and delivery package metadata, reducing database overhead from repeated queries |
| `STORAGE_S3_ENDPOINT` | `Access domain name of domestically compliant object storage services, calibrated via actual testing` | Connects to object storage to retrieve dataset source files, adapting to storage requirements for domestic business scenarios |
| `DB_MAX_LINK` | `100–200 connections/second` | Limits concurrent database connections, preventing system resource exhaustion during multi-version data synchronization |
| `FILE_TOKEN_KEY` | `Randomly generated 32-bit string` | Used to encrypt access tokens for delivery packages, ensuring access security for dataset deliveries |
| `ROOT_KEY` | `Administrator-exclusive key preset based on business scenarios` | Used to configure ticket permissions during operations on-call shifts, restricting unauthorized personnel from modifying version configurations |

## Three Common Configuration Mistakes
- Phenomenon: Embedding errors occur when uploading dataset documents after deployment. Logs show file pull failures. Cause: `STORAGE_S3_ENDPOINT` is not configured correctly, so source dataset files cannot be pulled from object storage, and the embedding preprocessing process cannot be completed.
- Phenomenon: Version records cannot be synchronized after upgrade. Internal tickets prompt delivery integrity check failures. Cause: The concurrent configuration of `DB_MAX_LINK` is not adjusted, leading to timeout when writing version data, and the verification process is not completed.
- Phenomenon: Internal ticket pages for delivery packages cannot be accessed during operations on-call shifts, prompting permission verification failures. Cause: `FILE_TOKEN_KEY` is not set correctly, leading to failed token verification and unauthorized access to dataset delivery resources.

## How to Verify Proper Configuration
- Run the version synchronization script for a test dataset, check if new version record entries are generated in the database corresponding to `MONGODB_URI`.
- Call the test interface of the object storage service, verify that the domain name configured in `STORAGE_S3_ENDPOINT` can normally pull test dataset files.
- Submit a test internal ticket, use the token generated by `FILE_TOKEN_KEY` to access the delivery package, confirm that the permission verification process works normally.
- Adjust the configuration value of `DB_MAX_LINK`, observe database connection count monitoring, confirm that concurrent connection counts fall within the preset business range.

The values provided are common starting points and should be measured against the reader's own samples.
