# Operations On-Duty and Internal Ticket Q&A for Documentation Site Maintenance: Permission and Data Isolation

## What the data for this category looks like
This category of data typically comes from code repositories, documentation site build logs, user feedback, and version release records. Daily produced documents include installation guides, API documentation, migration guides, and FAQs. Document structures are divided by functional modules, with fields such as version number, applicable environment, and operation steps. Data is updated synchronously weekly or when a version is released. Administrators must complete regular sample verification, version difference synchronization, and expired content cleanup.

## What constraints these characteristics impose on permission and data isolation
Data sources are scattered and linked to code and version information. Teams must isolate their own document resources to prevent cross-team misuse of API documentation or installation guides.
Update frequency fluctuates with versions. Administrators must synchronize permission configurations with version release schedules. This prevents unauthorized access to expired documents.
Documents contain sensitive environment parameters and interface information. Administrators must strictly control read and write permissions to avoid leakage or tampering.
Administrators must precisely divide access ranges for different entities such as internal operations staff and external developers. Only authorized personnel can modify document data related to version releases.

## How to set configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Bind to the unique identifier of the business team | Distinguish the ownership of document resources across different teams, prevent cross-team permission overreach |
| `tmbId` | Associate with the team identifier of the corresponding document knowledge base | Bind document site knowledge base data to team permissions, precisely control access scope |
| Team permission scope | Divide by document modules, such as installation documentation group, API documentation group | Match the functional classification of documents, refine the granularity of permission control |
| User role mapping | Set read-write permissions for operations on-duty staff, read-only permissions for external visitors | Adapt to daily operation scenarios for documentation site maintenance, distinguish between maintenance and public access needs |
| Expired document isolation | Retain 30 days of historical version permission archives | Meet compliance review requirements while preventing accidental access to expired resources |
| SSO integration configuration | Enable enterprise-level SSO login binding | Unify team identity verification processes, simplify permission management operations |

## Three common misconfigurations
- Symptom: Cross-team document access errors still occur after configuring `teamId`, with a 403 status code returned. Cause: The document site’s knowledge base resources are not bound to the corresponding `teamId`, and the permission verification logic does not match the team identifier.
- Symptom: Members cannot create new document entries after being assigned team write permissions. Cause: Read-write permission was not set for operations on-duty staff during user role mapping, and only read-only permission was configured.
- Symptom: Unauthorized expired document content appears in query results. Cause: No expired document isolation rules were configured, and resources beyond the retention period were not filtered.

## How to confirm configurations are correct
- Log in to an unauthorized team account, attempt to access the document module configured with `teamId`, and confirm that content cannot be viewed or edited.
- Assign corresponding permissions to operations on-duty staff, attempt to create a new document entry, and confirm that the operation can be completed normally.
- Trigger a documentation site build log query request, and confirm that only authorized team members can view build log data.
- Verify SSO login, and confirm that the account automatically matches the preset team permission scope without additional configuration.
