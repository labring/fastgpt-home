# Cabinet Installation and Cabling: Operation Duty and Internal Ticket Q&A, Deployment and Upgrade

## What the data for this category looks like
Typical users of this category are IDC operation and maintenance engineers, network engineers, and equipment implementation personnel. Daily involved documents include installation applications, cabinet cabling diagrams, port label tables, and construction records. Data is mainly sourced from DCIM systems, asset systems, network topologies, and customer tickets. Update frequency is per ticket or daily. Common fields include U position numbers, cable length (meters), port identifiers, construction time, and others. Document structures vary significantly. Structured tickets and unstructured drawings must be processed separately.

## What constraints do these characteristics impose during the deployment and upgrade phase
Because data sources are scattered and include heterogeneous systems, multiple data source connection parameters must be configured during deployment to ensure stable retrieval of core data such as cabinet positions and ports. Because document types are diverse, parsing and storage of structured tickets and unstructured drawings must be supported, so parameters related to file access and storage must be configured. Because update frequency is high, database connection pool size must be set appropriately to avoid connection exhaustion that disrupts ticket synchronization. Because errors may lead to incorrect port connections or delayed customer service activation, configuration verification logic must be enabled during upgrades to prevent business exceptions caused by incorrect parameters.

## How to configure these settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | 10–20 connections | Adapts to daily update volume of cabinet installation tickets, avoids database connection exhaustion |
| `MONGODB_URI` | Read-only connection address of the DCIM system | Used to retrieve cabinet topology and position data, read-only permission prevents accidental operations |
| `PG_URL` | Read-only address of the asset system's ticket database | Stores and synchronizes structured data such as installation applications and construction records |
| `REDIS_URL` | Locally deployed Redis instance address, uses default port 6379 | Caches port label tables and cabling diagram parsing results, reduces repeated retrieval overhead |
| `FILE_TOKEN_KEY` | 32-bit random string generated through actual testing | Used to sign access tokens for files such as cabinet cabling diagrams and port label tables, ensures secure file access |
| `STORAGE_S3_ENDPOINT` | VPC internal network access address of internal object storage | Enables secure storage and fast reading of cabinet-related documents |

## Three common misconfigurations
- Phenomenon: No return result when calling a locally deployed text parsing model, workflow node shows "run timeout". Cause: The `DB_MAX_LINK` parameter was not adjusted to match the concurrency limit of the local model, causing database connections to be exhausted by model calls.
- Phenomenon: Cabinet cabling diagram upload fails to parse normally, interface shows "invalid file token". Cause: `FILE_TOKEN_KEY` was not configured correctly, causing file access permission verification to fail.
- Phenomenon: After upgrading to FastGPT v4.17.0, port label table synchronization tasks cannot be triggered. Cause: Cache configuration associated with `REDIS_URL` was not updated, causing conflicts between old version cache logic and new version incremental synchronization rules.

## How to confirm configurations are correctly set
- Run the built-in data source connectivity verification tool to confirm that systems configured with `PG_URL` and `MONGODB_URI` can normally retrieve core data such as cabinet position numbers and port labels.
- Upload a test cabinet cabling diagram to confirm that the file loads normally, with no "invalid token" errors.
- Submit a simulated installation application ticket to confirm that the ticket is normally synchronized to the system, with no timeout or connection failure logs.
- Check the system monitoring panel to confirm that database connection count does not exceed the threshold set by `DB_MAX_LINK`, with no abnormal disconnections.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
