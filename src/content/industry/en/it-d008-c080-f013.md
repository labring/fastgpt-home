# Desktop Terminal Support for Operations On-Call and Internal Ticket Q&A: Permission and Data Isolation

This configuration applies to FastGPT v4.17.0

## What this category of data looks like
Data for this category primarily comes from terminal management platforms, asset systems, user reporting channels, and software repositories. Daily processed documents include terminal trouble tickets, installation lists, software installation records, and remote assistance records. Each document typically contains device ID, fault description, operation steps, and permission application fields, with fields linked to specific terminal hardware and software asset information. Data updates follow daily batch sync or single request triggers, with no fixed batch cycle. Updates occur in real time only when terminal status changes or a user submits a report.

## What constraints these characteristics impose on permission and data isolation
Terminal assets and user report data are linked to specific devices and employees. Permission isolation must prevent cross-department or cross-on-site team access to unauthorized terminal trouble tickets and installation records. Most data sources are internal systems, so integration with different permission systems is required to prevent unauthorized leakage of terminal management platform data. Each document links hardware and software assets, so isolation configuration must accurately match device ownership and team permission scope. Overly broad permissions must be avoided to prevent non-operation staff from viewing installation lists and remote assistance records. On-site team permissions must be strictly bound to terminal assets in their on-site area, to prevent cross-region operation staff from accessing non-on-site terminal data. Real-time update request data also requires restricted access scope, to prevent unauthorized users from triggering ticket processes related to terminal operations.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Team Permission Binding | Match corresponding operation and maintenance team by `teamId` | Accurately link ownership groups of terminal assets, isolate cross-group desktop terminal data |
| Member Account Verification | Verify enterprise domain accounts, return `Username invalid` prompt when invalid | Intercept unauthorized team member addition operations, resolve account invalid issues reported by the community |
| Data Isolation Granularity | Split data by single terminal device | Match management units supported by desktop terminal support, narrow permission coverage scope |
| Session Storage Duration | `7 days` | Comply with internal data retention requirements, limit retention period of chat records |
| Cross-Device Session Isolation | Bind terminal sessions by `tmbId` | Ensure sessions of the same terminal are only visible to authorized operation and maintenance personnel |
| Log Access Scope | Only open to operation and maintenance supervisor roles | Protect sensitive operations in remote assistance records and fault troubleshooting |

## Three Common Misconfigurations
- Phenomenon: When adding a team member, entering their account causes the interface to return `Username invalid` prompt. Cause: Account belonging to enterprise domain is not verified, or configured team permission scope does not allow cross-domain account access.
- Phenomenon: After generating a publicly accessible link, unauthorized users can view team terminal trouble tickets and chat records. Cause: Permission scope is not bound by `teamId`, public link is not associated with a dedicated team identifier.
- Phenomenon: Chat content in remote assistance records is accessed by unauthorized personnel. Cause: Data isolation granularity is set to department level, not refined to the ownership group of a single terminal, allowing cross-group operation staff to view records of unrelated terminals.

## How to Confirm Configuration is Successful
- Try adding a non-enterprise domain account, confirm the interface returns `Username invalid` prompt, verify member account verification rules are active.
- Switch accounts of different operation and maintenance teams, confirm only terminal trouble tickets and installation lists bound to the corresponding `teamId` can be viewed, verify team permission binding is active.
- View the session storage directory, confirm only authorized roles can access session data bound to the corresponding `tmbId`, verify cross-device session isolation is active.
- Generate a publicly accessible link, confirm unauthorized users cannot access team terminal support data, verify permission isolation configuration is active.

The values listed above are common starting points and should be evaluated against your own specific samples.
