# Desktop Terminal Support for Operations On-Call and Internal Work Order Q&A: Deployment and Upgrade

## What data for this category looks like
Data for this category primarily comes from terminal management platforms, enterprise asset systems, frontline employee trouble reporting channels, and internal software repositories. Daily generated documents include terminal trouble tickets, installation lists, software installation records, and remote assistance operation logs.
Data updates follow either daily batch synchronization or real-time updates tied to individual requests. Each individual data entry includes fields such as terminal serial number, fault type, processing node, and associated software version. There is no unified fixed format, and matching must align with the operations ledger structure of each individual enterprise.

## What constraints these characteristics impose during deployment and upgrade
Data sources for this category are scattered, and formats are inconsistent. During deployment, configure adaptation rules for multi-source data access to avoid field format conflicts across different systems.
Data update rhythms are flexible. Support switching configuration between scheduled batch synchronization and real-time pull for individual requests.
Daily documents have no fixed structure. Reserve a field mapping adjustment entry during deployment to adapt to the operations ledger formats of different enterprises.
Core data is associated with terminal assets. During the upgrade phase, ensure database connection stability to prevent core fields from being lost during version migration.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `10–15 connections` | The concurrent volume of work orders and terminal data supported for desktop terminals is moderate. This setting balances connection pool resource usage and concurrent response speed |
| `MONGODB_URI` | Fill in according to the enterprise’s internal MongoDB cluster address | Used to store unstructured operations data such as terminal trouble tickets and remote assistance operation logs |
| `PG_URL` | Fill in according to the enterprise’s internal PostgreSQL asset database address | Used to store structured asset data such as terminal serial numbers, software versions, and installation lists |
| `REDIS_URL` | `redis://:custom password@internal address:6379/0` | Used to cache frequently queried terminal online status and pending work order data to reduce database access pressure |
| `FILE_TOKEN_KEY` | `32-character randomly generated string` | Used to generate access tokens for terminal attachments to ensure permission security for attachment downloads |
| `ROOT_KEY` | `32-character randomly generated string` | Used for super administrator permission verification during system initialization to ensure access security during deployment |

## Three common misconfigurations
- Issue: After upgrading FastGPT v4.17.0, conversation records display as empty when refreshing the conversation page, only showing the new conversation entry. Cause: The permission configuration for the conversation storage collection corresponding to `MONGODB_URI` was not correctly migrated during the upgrade process, resulting in inability to read conversation data associated with existing work orders.
- Issue: Session conflicts or data disorder occur when multiple terminal operations staff log in to the system at the same time. Cause: Session storage parameters for `REDIS_URL` were not correctly configured during deployment, resulting in failure to synchronize user session information across nodes.
- Issue: When migrating old process orchestration logic to a new version, terminal work order data cannot be properly associated. Cause: The structure of the operations work order table associated with `PG_URL` was not updated synchronously during version migration, resulting in the old orchestration logic being unable to read new fields.

## How to confirm configurations are correct
- Run the database connection test script to verify that configurations for `DB_MAX_LINK`, `MONGODB_URI`, `PG_URL`, and `REDIS_URL` can establish normal connections, and the connection count does not exceed the preset value.
- Submit a simulated terminal trouble ticket and upload a test attachment to verify that the storage configuration for `STORAGE_S3_ENDPOINT` can write files normally, and attachments can be downloaded normally.
- Log in to the system with multiple different accounts and submit trouble reporting requests to verify that multi-user sessions can be properly isolated, and work order assignments have no conflicts.
- Import a legacy operations ledger data set to verify that the field mapping configuration can correctly match fields such as terminal serial number and fault type to the system’s preset fields.

The values provided here are common starting points and should be evaluated against the user’s own samples.
