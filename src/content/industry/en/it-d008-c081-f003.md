# Penetration Testing Services: Operations On-Call and Internal Ticket Q&A: Sharing and Embedding

This page configuration is based on FastGPT v4.17.0.

## What the data for this category looks like
Core data for penetration testing services comes from target systems, public vulnerability databases, automated scanner results, and manual validation records from red team engineers. Daily associated documents include test authorization letters, penetration test reports, vulnerability reproduction records, and rectification suggestions. Data updates follow individual project or major version iteration cycles. Data fields include vulnerability CVSS scores, attack path reproduction steps, authorized access scopes, and more. There is no fixed uniform single data length. Adjustments are made based on project complexity.

## What constraints do these data characteristics impose on the sharing and embedding process
Penetration testing service data characteristics impose multiple constraints on the sharing and embedding process. First, data is updated per individual project or major version. Unique identifiers must be used to distinguish knowledge base content across different projects, to avoid cross-project data confusion. Second, data includes sensitive authorized scope and undisclosed vulnerability details. Embedded calls must strictly restrict access permissions, to prevent legal or business risks from unauthorized access. Third, data includes complex attack path descriptions from manual validation. Embedded scenarios using FastGPT sharing links must support sufficiently long context transmission, to ensure complete coverage of business background during Q&A. Fourth, data retrieval involves multi-source scanner results and manual records. Sufficient processing time must be reserved, to avoid timeouts that impact response efficiency in operations on-call scenarios.

## Three common mistakes
- Sharing entries related to penetration testing services fail to open. First verify the full system-generated link and its validity period, then cross-check browser request statuses. Do not manually replace `shareId`.
- The visible scope of penetration testing service data does not match expectations. Cross-check third-party identity verification results, workflow request parameters, and external system data permissions separately. The sharing entry identifier itself does not provide business authorization.
- The same penetration testing service Q&A is not visible on another device. For anonymous scenarios, first verify device, browser, and local identity status. Retention cannot be guaranteed across devices or after cache clearance. Do not use this phenomenon alone to judge service abnormalities.

## How to confirm the configuration is complete
- Obtain the `shareId` corresponding to the project-specific sharing link generated from FastGPT Application Details - Release Channels - No-Login Window. Embed the FastGPT sharing link using this `shareId` into the internal operations ticket system (external business system). Enter keywords related to the test authorization letter, and check that the returned results include exclusive vulnerability information for the current project.
- Access the embedded FastGPT sharing link from an unauthorized domain name. Check whether a permission restricted prompt pops up or empty results are returned, to verify that the access restriction configuration is effective.
- Simulate high-frequency operations on-call scenarios by entering vulnerability-related questions. Check that the number of retrieval results matches the preset test example value: the top 3 entries, with no redundant irrelevant information in the content.
- Wait until the 7-day sharing link validity period from the test example ends. Access the embedded FastGPT sharing link again, and check whether a link expired prompt is displayed or content cannot be retrieved, to verify that the validity period configuration is effective.
