# Penetration Testing Services: Operations On-Call and Internal Ticket Q&A — Permission and Data Isolation

## What This Category of Data Looks Like
Data for this category originates from target business systems, public vulnerability databases, automated scanner output, and manual verification records from red team engineers. Daily associated documents include project test authorization letters, official penetration test reports, vulnerability reproduction step records, and rectification priority recommendation documents.
Data updates follow individual project cycles, or are synced in batches during major version iterations. Each data entry includes authorization scope, vulnerability details, exploit chain analysis, remediation solutions, and other fields. There are no fixed standardized unitized fields. Configurations are adjusted flexibly based on project scenarios.

## Constraints on Permission and Data Isolation
These data characteristics create three types of permission constraints.
First, the data includes legally valid test authorization letters. Unauthorized access or disclosure may trigger legal disputes. Permissions must be strictly bound to project authorization scopes.
Second, data updates follow individual project cycles. Penetration test data and reports from different projects must be strictly isolated to prevent cross-project permission leaks.
Third, the data includes manually verified exploit chain details and sensitive operation records. Role-based view and edit permissions must be differentiated. Unauthorized personnel are prohibited from modifying verification results or accessing unauthorized project data.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `teamId` binding | Associate with the exclusive `teamId` of a single penetration test project | Ensures only team members authorized for that project can access corresponding data, preventing cross-project permission leaks |
| `tmbId` binding | Create an exclusive `tmbId` for each internal ticket | Precisely isolate conversations and associated data for individual tickets, preventing unauthorized personnel from viewing other ticket content |
| Guest login link quantity limit | `10–100`, calibrated via actual testing | Matches the temporary collaboration needs of penetration test projects. Prevents data leaks from unrestricted links while supporting temporary access for multiple team members |
| Conversation record permission validation | Enable dual-field validation based on `teamId` and `tmbId` | Blocks unauthorized access to conversation records, preventing unauthorized operations |
| Role permission division | Divide permission levels by red team engineer, operations, and security manager | Aligns with daily collaboration workflows for penetration testing services, ensuring each role can only access data within their job scope |
| Project data storage isolation | Store data from different projects in independent directories, divided by `teamId` | Prevents cross-project data confusion, simplifying permission auditing and isolation management |

## Common Misconfiguration Issues
- Symptom: A prompt stating "No permission to operate this conversation record" appears, and target tickets or test data cannot be accessed. Cause: The `teamId` and `tmbId` associated with the conversation are not correctly bound, resulting in a mismatch in permission validation logic.
- Symptom: The guest login window only allows creation of 10 links, and the quantity cannot be adjusted higher. Cause: The value range for the guest login link limit has not been modified in team settings, and the default basic limit of the team plan is still in use.
- Symptom: External team members can access unauthorized penetration test project data. Cause: An exclusive `teamId` has not been configured per project, and a global team ID has been mistakenly bound to multiple projects, leading to failed permission isolation.

## How to Verify Successful Configuration
- Access the FastGPT v4.17.0 team management backend, view the binding configuration for `teamId` and `tmbId`, and confirm that the exclusive ID for each project has been correctly associated with corresponding data and tickets.
- Access the target conversation using an unauthorized member account, and verify that the prompt "No permission to operate this conversation record" appears, confirming that permission validation is active.
- Navigate to the guest login window configuration page, adjust the link quantity limit to `50`, confirm that the corresponding number of temporary links can be created after saving, verifying that the limit configuration is effective.
- Switch to a red team engineer role account, attempt to edit vulnerability reproduction records, then switch to an operations role account, verify that only viewing of records is allowed and editing is prohibited, confirming that role permission division is correct.
