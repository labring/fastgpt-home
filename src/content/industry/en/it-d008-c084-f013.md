# Operations on-duty and internal ticket Q&A for game client performance optimization: Permission and data isolation

## What data does this category include
Data for this category primarily comes from engine Profiler, crash platforms, real-device testing tools, and frame rate collection systems. The update cadence is daily or per version release cycle. Daily deliverables include performance test reports, device compatibility lists, optimization records, and crash analysis reports. Data fields include frame rate (unit: fps), package size (unit: MB), resource loading duration (unit: seconds), device model, crash log ID, and others. Fields vary across different test scenarios, and there is no unified standardized format.

## What constraints do these characteristics impose on permission and data isolation
Core data for this category includes undisclosed performance optimization plans and sensitive real-device test data, with a high update frequency. Engineers in different roles can only access documents and data within their job scope. In operations on-duty and ticket scenarios, permission boundaries for different team members must strictly align with their work scope to avoid cross-team access to unauthorized performance test reports or crash analysis data. Dispersed data sources mean permission control must cover multiple data types, ensure isolation rules correspond to data ownership, and prevent core optimization information from being leaked due to unauthorized access.

## How to set configurations
These configurations are formulated based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| Team permission grouping | Divided into three job roles: client, engine, performance testing | Matches the typical job division of this category |
| `teamId` binding rule | Bind to the performance optimization dataset of the corresponding project | Ensure only project members can access corresponding performance data |
| `tmbId` verification switch | Enable | Block unauthorized cross-team data access requests |
| Ticket data ownership | Associate with the submitter's affiliated `teamId` | Prevent non-associated teams from viewing ticket content |
| Log retention period | 30 days | Matches the version iteration and review cycle of this category |
| Cross-source data access | Only allow members under the same `teamId` to call | Cover permission isolation requirements for multiple data sources |

## Three common misconfigurations
- Username displays as invalid when entering a team member's username: `teamId` and member account binding is not configured correctly, so the system cannot identify legitimate members of the corresponding team.
- Insufficient permission error is returned when accessing performance test reports across teams: The `tmbId` verification switch is not enabled, or permission grouping does not match the job division rules of this category.
- Performance data associated with tickets fails to load normally: Data ownership is not bound to the `teamId` of the ticket submitter, so the system cannot match the corresponding permission scope.

## How to confirm the configuration is correct
- Attempt to access the team's performance test report using an account from a non-team member, and confirm the system returns an insufficient permission prompt.
- Submit an internal ticket, and confirm only team members can view it, while non-team members cannot search for the ticket.
- Check the dataset bound to `teamId`, and confirm only the corresponding project's performance data is associated with the group.
- View permission audit logs, and confirm cross-team data access requests are correctly blocked.
