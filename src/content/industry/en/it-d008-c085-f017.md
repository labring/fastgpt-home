# Game Server R&D and Operations On-Duty and Internal Ticket Q&A: Deployment and Upgrade

## What data this category uses
Data for this category comes primarily from game runtime logs, real-time online player count monitoring systems, business databases, and tickets submitted by players. Daily maintenance documents include server architecture descriptions, server launch plans, server merging plans, and fault reports. These documents are updated according to game event cycles or daily schedules. Data fields cover server node operational status, online player count, database interaction records, ticket processing progress, and other relevant dimensions. Only operations and business data aligned with business requirements are recorded for these dimensions.

## What constraints do these characteristics impose on deployment and upgrade
Game server business data is directly linked to player accounts and game state. The deployment phase must guarantee atomicity and stability of data reads and writes. This requires adapting to high-concurrency database connection configurations to avoid launch lag caused by insufficient connections. Updates conducted daily or for large-scale events require deployment workflows that support fast rollbacks, to prevent failed upgrades from harming online player experience. Server architecture documents and server merging plans require deployment tools compatible with multi-node cluster configurations. These tools must support synchronized batch upgrades of nodes and status verification. Correlated data from player tickets and fault reports requires post-deployment services to properly collect and store operations-related logs. This enables subsequent traceability and troubleshooting for server launch and merging issues.

## How to set configurations
All configurations below are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale for This Setting |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `120–180 connections` | Adapts to high-concurrency database access demands for game servers, avoids launch anomalies caused by exhausted connections |
| `MONGODB_URI` | Intranet-accessible game operations database address | Stores operations-related data including player tickets, fault reports, and server upgrade records |
| `REDIS_URL` | `Intranet cache address using port 6379` | Caches real-time online player count and temporary ticket status, reduces access pressure on core business databases |
| `STORAGE_S3_ENDPOINT` | Game operations-exclusive object storage node address | Stores large-volume operations files including server upgrade packages and fault log attachments |
| `ROOT_KEY` | Random string generated per operations team security standards | Configures administrator access permissions for the FastGPT internal ticket system, ensures operational security |

## Three common mistakes
- A container startup prompt shows database connection failure, and internal ticket data fails to load. This occurs when `MONGODB_URI` is not correctly configured to point to the game business intranet database, and a public network or invalid address is entered instead.
- After intranet deployment, access via public network mapping fails when calling the service. This occurs when `FE_DOMAIN` is not configured to the publicly accessible mapping address, causing the service callback link to fail to connect.
- When batch upgrading multiple game server nodes, some nodes fail to pull upgrade packages. This occurs when `FILE_TOKEN_KEY` is not correctly configured to generate valid file access credentials, causing insufficient node permissions to obtain upgrade files.

## How to confirm configurations are correct
- Access the FastGPT container shell, run a database connection test command to verify that the connection count set in `DB_MAX_LINK` can establish a normal connection with the database specified by `MONGODB_URI`.
- Submit a test internal ticket with content related to server upgrades, confirm that ticket data can be properly written to the database specified by `MONGODB_URI`.
- Upload a small-volume server upgrade package attachment, confirm that it can be successfully stored to the object storage node specified by `STORAGE_S3_ENDPOINT`.
- Check the FastGPT container runtime logs, confirm there are no error messages such as database connection timeouts or storage node access failures.
