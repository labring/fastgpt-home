# On-Call Operations and Internal Ticket Q&A for Game Design and Numerical Design: Permission and Data Isolation

## What Data Looks Like for This Category
The daily documents for this category include gameplay design documents, numerical tables, version requirement sheets, and balance test records. Data mainly comes from player behavior data, public competitor materials, battle logs, and version feedback. Document structures are mostly structured numerical tables and unstructured rule descriptions. Numerical table fields cover character growth parameters, damage coefficients, item drop rates, and similar items. Update frequency is mostly weekly or per version.

## Constraints on Permission and Data Isolation
Structured numerical tables and unstructured rule documents are stored together. The data is linked to sensitive business information such as player behavior and version feedback. Strict isolation of documents and data between different design teams is required. High-frequency weekly or per-version updates require permission configurations to support dynamic adjustments, to avoid delaying iteration efficiency due to permission changes. Numerical simulation results and balance test records from different design teams are internal core assets. Access must be restricted to only corresponding team members, to prevent leakage of core rules. In on-call operations and internal ticket scenarios, different operation permissions must be distinguished for on-call personnel, design team members, and administrators, to avoid accidental modification of core numerical data.

## Configuration Settings
The following configurations are adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Assign unique identifiers by business group | Accurately isolate core documents and data between different design teams, matching the group-based division of labor business model of game design teams |
| `tmbId` | Assign exclusive identifiers by document type | Distinguish between different types of business assets such as numerical tables and gameplay design documents, to avoid confusion of cross-type data permissions |
| Session context retention period | 72 hours | Matches the weekly update rhythm of version iterations, to avoid leaking core rules from old versions via expired chat records |
| Maximum sessions per user | First 15 entries | Limit the scope of batch sensitive data retrieval, to prevent unauthorized bulk export of numerical parameters |
| Permission check mandatory switch | Enabled | Block access requests not bound to the corresponding team, adapting to temporary permission allocation needs in on-call operations scenarios |

## Three Common Misconfigurations
- Public access links not bound to `teamId` permissions: The phenomenon is that clicking a generated public link directly accesses all team documents. The cause is that no `teamId` binding rule is configured, so the public link is not associated with the permission scope of the corresponding design team.
- Permission configuration not distinguishing `tmbId` types: The phenomenon is that numerical design team sessions can view level design documents. The cause is that exclusive template permissions are not assigned by `tmbId`, so cross-type document permissions are not isolated.
- Excessively long session context retention period: The phenomenon is that chat records for old version numerical tables can still be viewed via historical sessions. The cause is that the retention period exceeds the version iteration cycle, leading to risk of leaked expired sensitive data.

## How to Verify Successful Configuration
- Attempt to access design team documents with an account not bound to the corresponding `teamId`, confirm that access fails or a permission denied prompt is shown.
- Generate a public access link, verify that only documents bound to the specified `tmbId` can be accessed, and other types of documents fail to load.
- View the session list, confirm that historical chat records older than 72 hours have been automatically cleaned up.
- Test temporary permission allocation for on-call personnel, confirm that permissions can be quickly adjusted and take effect within a short time.

The values provided are common starting points and should be measured against local samples.
