# Operations on-duty and internal ticket Q&A for game planning and numerical design: Deployment and Upgrade

## What data looks like for this category
The core data for this category comes from player behavior data, publicly available competitor materials, battle logs, and version feedback. Daily produced documents include gameplay design plans, structured numerical tables, version requirement sheets, and balance test records. Document fields often include rule parameters, numerical ranges, version iteration milestones, and similar content. Units involve damage multipliers, update cycles, and other metrics. Data update frequency is mostly weekly or per version release cycle. Core documents must be revised synchronously with version iterations. Content involving numerical simulation and rule breakdown requires repeated verification.

## What constraints do these characteristics impose on deployment and upgrade
The data sources for this category are diverse and tightly bound to version iterations. Deployment must support multi-source data access and versioned storage, so stable database and caching services need to be configured. Documents include large-volume battle logs and structured numerical tables, so deployment must adapt to large-field storage requirements, and relevant storage configurations need to be adjusted to ensure data transmission stability. Version update frequency is relatively high. The upgrade process must retain historical conversations, configuration data, and version documents. Compatibility of cache and database connections must be confirmed to avoid data loss or parsing exceptions after upgrade. Additionally, numerical-related data verification logic is complex. A configuration verification link must be reserved during deployment to prevent disruption to normal rule and numerical calls after upgrade.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 20–30 connections | Adapts to concurrent access needs when multiple planners access documents such as numerical tables and version requirement sheets simultaneously |
| `MONGODB_URI` | Set based on actual measurements | Stores unstructured documents including gameplay design plans and balance test records, matching data storage volume and access frequency |
| `REDIS_URL` | 600-second cache expiration | Caches frequently accessed numerical simulation results and version configurations to avoid repeated calculations and improve response speed |
| `STORAGE_S3_ENDPOINT` | Private deployment exclusive node | Stores large-volume battle logs and version feedback data, ensuring stability of large file transmission and reading |
| `FE_DOMAIN` | Project-specific secondary domain | Distinguishes development, testing, and production environments to avoid configuration conflicts that disrupt version iteration workflows |
| `ROOT_KEY` | Randomly generated 32-character string | Ensures interface access security for internal ticket Q&A, preventing unauthorized configuration modifications and data access |

## Three common mistakes
- After upgrading to FastGPT v4.17.0, refreshing the conversation page shows new conversations but historical records are empty. The cause is that the cache configuration for `REDIS_URL` was not synchronized during the upgrade process, resulting in historical conversation data not being loaded correctly.
- A parameter incompatibility error occurs when migrating workflow orchestration functions. The cause is that the version compatibility of `MONGODB_URI` was not checked in advance, and there are differences in database connection protocols between the old and new versions.
- Private TTS model cannot be called normally after configuration. The cause is that the permission scope of `FILE_TOKEN_KEY` was not set correctly, causing the TTS service to fail to obtain a valid access token.

## How to confirm configurations are correct
- Access the frontend page corresponding to `FE_DOMAIN`, submit an internal ticket Q&A, and confirm that the interface returns normally without errors.
- Log in to the database console, check whether historical version numerical tables and test records exist in the storage corresponding to `MONGODB_URI` and `REDIS_URL`.
- Trigger a version upgrade process, confirm that historical configurations are not overwritten after upgrade, and existing tickets and conversation data can be queried normally.
- Upload a large-volume battle log file, confirm that the `STORAGE_S3_ENDPOINT` configuration can complete storage and reading normally.
