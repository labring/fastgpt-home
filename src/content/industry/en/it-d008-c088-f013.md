# Game Operation Activity Configuration: On-Call Operations and Internal Ticket Q&A - Permission and Data Isolation

## Data Profile for This Category
Data for this category originates from game operation backends, player segmentation systems, payment data reports, and activity logs. Regularly produced documents include activity plans, reward configuration tables, launch checklists, and activity post-event review materials. Data updates follow weekly cycles or temporary adjustments ahead of holiday events. Reward configuration tables include fields such as reward ID, issuance quantity, and trigger rules. Activity plans specify effective time periods and target user scopes. Units used include person-times, yuan, hours, and other business-specific metrics.

## Constraints on Permission and Data Isolation
The data traits of this category create multiple constraints for permission and data isolation. First, data includes sensitive information such as player segments and payment data. Access scopes for different operation roles must be strictly isolated to prevent unauthorized viewing or modification of sensitive business data. Activity configuration updates are flexible, with both weekly routine updates and temporary holiday adjustments. On-call staff must only modify activity configurations for their assigned time periods, to avoid accidental changes to activity content from other cycles. Document types are diverse, and field permissions for reward configuration tables and activity plans require fine-grained control. For example, only designated roles may modify reward values, and activity planners may configure target user scopes. Additionally, ticket Q&A must link to the context of the corresponding activity, to prevent mixing of ticket data across different activities and reduce on-call processing efficiency.

## Configuration Guidelines
These configuration rules are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Bind to the operation team owning the activity | Differentiate activities managed by different teams, prevent cross-team unauthorized access to activity configurations |
| `tmbId` | Bind session context to activity ID | Ensure ticket Q&A only links to configuration data for the corresponding activity, avoid mixing context across activities |
| Role permission groups | Divided into three categories: activity planner, value configuration, on-call operations | Match job roles within this category, restrict operation and viewing scopes for different roles |
| Sensitive data masking | Show first 3 digits of payment data, hide middle 4 digits of player ID | Comply with business data privacy requirements, prevent sensitive information leaks |
| Ticket context validity period | 72 hours | Align with weekly update or temporary activity processing cycles, avoid expired context interfering with on-call processing |
| Configuration approval threshold | Secondary approval required for reward value modifications exceeding 1000 yuan | Prevent accidental changes to large-value reward configurations, reduce potential error impacts |

## Three Common Misconfigurations
- Symptom: Members of different operation teams can view activity configuration tables from other teams, with no clear permission denial prompt. Cause: `teamId` is not bound to role permission rules, resulting in failed team-level isolation.
- Symptom: Global reward configuration variables called by different on-duty staff have data cross-use issues, with variables sharing the same name returning unexpected activity data. Cause: Variable scope is not bound by `tmbId`, resulting in global variables not being isolated by activity ID.
- Symptom: Full player IDs and payment amounts are returned directly in ticket Q&A, triggering internal compliance checks. Cause: Sensitive data masking rules are not configured, and sensitive business fields are not hidden.

## How to Verify Successful Configuration
- Switch test accounts for different operation teams, verify that only activity configuration data bound to the corresponding `teamId` can be viewed.
- Submit tickets for different activity IDs, verify that Q&A context only links to configuration information for the corresponding activity, with no cross-activity data exposure.
- Attempt to modify reward values, verify that a secondary approval process is triggered when the preset approval threshold is exceeded.
- View sensitive data display results, verify that payment data and player IDs have been masked according to configured rules.
