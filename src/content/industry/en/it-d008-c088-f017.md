# Game Operation Activity Configuration: Operations On-Call and Internal Ticket Q&A - Deployment and Upgrade

## What the data for this category looks like
The data for this category primarily comes from the game operation backend, player segmentation system, payment data platform, and activity logging system. Daily associated documents include activity plans, reward configuration tables, launch checklists, and activity review materials. Data fields include activity unique identifiers, reward types, issuance thresholds, effective and expiration times, target player group tags, and more. Data updates are mostly scheduled weekly, or conducted in concentrated batches before holiday events. A single update requires field alignment verification across multiple documents.

## What constraints these characteristics impose on the deployment and upgrade phase
Data sources for this category are scattered, and update schedules are volatile. During deployment, configure multi-data source connection parameters to ensure stable connectivity of data links such as the game operation backend and logging system. Field validation rules for activity configurations must fully match the fields in launch checklists and reward configuration tables. During upgrades, retain the field mapping logic from previous configuration versions to avoid configuration validation failures caused by parameter changes. Errors here can lead to player complaints and revenue fluctuations. Reserve configuration items for abnormal rollbacks in deployment and upgrade processes to enable rapid recovery when faults occur.

## How to set the configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `200–300 connections` | Game activity configurations involve concurrent requests from multiple data sources including the operation backend and logging system. This range accommodates traffic peaks during weekly concentrated updates |
| `PG_URL` | `postgresql://{user}:{pass}@{host}:5432/game_activity_config` | Structured data for game operation activities is typically stored in PostgreSQL. Using a dedicated business database isolates data interactions with other systems |
| `REDIS_URL` | `redis://:{password}@{host}:6379/1` | Temporarily cache validation results for activity configurations and player segmentation tags. Using database 1 avoids conflicts with cached data from other services |
| `FE_DOMAIN` | `https://game-act-config.internal-domain.com` | Use a dedicated internal domain for game operation activity configurations to help on-call operations staff and ticket handlers quickly locate the configuration page |
| `ROOT_KEY` | `32-character random string` | Secure access to the internal configuration backend. Only authorized operations and on-call staff can modify activity configuration parameters |

## Three common mistakes
- After upgrading to FastGPT v4.17.0, saved Qwen Plus model configurations automatically switch to GPT-4o during chat. Cause: Permission validation for `ROOT_KEY` is not configured correctly. This causes model configurations from the frontend page to fail synchronization to the backend service, or the original model binding configuration is overwritten during the upgrade.
- After Docker deployment, an error is prompted when entering the workflow stage, and activity configuration data cannot be loaded. Cause: The `PG_URL` or `REDIS_URL` parameters are not filled in correctly. This causes database or cache connection failures, preventing structured activity configuration data from being read.
- After deployment, the system prompts an incorrect username or password error, and the internal configuration backend cannot be logged into. Cause: `ROOT_KEY` is not generated or configured correctly. This causes the login validation logic to fail to match the preset administrator credentials, or the default credential configuration is reset during the upgrade.

## How to confirm configurations are set correctly
- Access the configured frontend domain `FE_DOMAIN` to verify that the activity configuration list loads normally, confirming connectivity between the frontend and backend.
- Run a database connection test to verify that the `PG_URL` and `REDIS_URL` parameters can successfully establish connections and read configuration data for test activities.
- Submit a test activity configuration change to trigger the validation process, confirming that configuration fields match the rules in the launch checklist without errors.
- Restart the service and verify that the model binding configuration is retained, confirming that configurations after the upgrade are not reset.
