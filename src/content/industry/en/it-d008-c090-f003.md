# Operations on Duty and Internal Ticket Q&A for Version Releases and Release Notes: Sharing and Embedding

This documentation applies to FastGPT v4.17.0 and later versions for relevant configurations.

## What the data for this category looks like
Data for this category primarily comes from Git version tags, merged PR records, CI build artifacts, and Issue milestones. Daily produced documents include official Release Notes, change logs, version tag descriptions, and release checklists. The data update cadence is once per official release. Core fields include version number, change category, breaking change description, associated artifact hash, and milestone number. No additional statistical quantitative indicators are included.

## What constraints these characteristics impose on sharing and embedding
The data update cadence is fixed at once per official release, and core content is tied to code repositories and release processes. Therefore, when sharing or embedding, ensure content is synchronized with the latest version to avoid information deviation caused by cached expiration. The permission boundaries of data sources are bound to internal ticket permissions of the operations team. Embedding scenarios must match corresponding access rules to prevent unauthorized access to unreleased release checklists or breaking change descriptions. Structured fields require shared content to retain core metadata such as version number and change category, and critical associated information must not be lost. Otherwise, the ticket processing efficiency of operations on duty personnel will be affected.

## Three common mistakes
- Sharing entries related to version releases and Release Notes fail to open. First verify the complete system-generated link and its validity period, then check browser request status; do not manually replace `shareId`.
- The visible scope of version release and Release Notes data does not match expectations. Verify third-party identity verification results, workflow request parameters, and external system data permissions separately; the sharing entry identifier itself does not provide business authorization.
- The same version release and Release Notes Q&A cannot be viewed on another device. For anonymous scenarios, first check device, browser, and local identity status; record retention cannot be guaranteed across devices or after cache clearance, and service anomalies cannot be judged solely based on this phenomenon.

## How to verify successful configuration
- Embed the share link in the test page of the internal operations system, verify that Release Notes content loads normally and no permission errors occur.
- Modify the test domain name of the embedded page, verify that permission interception is triggered, and confirm that the whitelist configuration takes effect.
- Confirm that the release document pointed to by the share link matches the latest version's Release Notes content.
- Wait beyond the configured session expiration time, verify that the session automatically expires, and confirm that the expiration time configuration takes effect.

The values provided are common starting points and should be evaluated against the reader's own samples.
