# Operations On-Call and Internal Ticket Q&A for Version Releases and Release Notes: Re-ranking and Hybrid Retrieval

## What data for this category looks like
This category of data primarily comes from Git repository tags, merge commit records, CI build artifacts, and Issue milestones. Daily output documents include release notes, change logs, version tag lists, and release checklists. Data updates per version cycle. Each document includes fields such as version number, change type, impact scope, associated Issue number, artifact check value, and other fields. There is no unified fixed format, and slight variations exist based on project maintenance habits.

## What constraints these characteristics impose on re-ranking and hybrid retrieval
This category of data updates per version cycle. The dataset for a single retrieval expands gradually with version iterations. Use recall limits to control retrieval efficiency. Document formats vary by project maintenance habits. Support structured metadata and unstructured change descriptions for hybrid retrieval. Change types include multiple categories, such as breaking changes and feature additions. Prioritize high-impact entries that operations on-call teams care about during re-ranking. Cover both text content and field information in hybrid retrieval for metadata such as associated Issues and artifact check values, to avoid missing key associated information.

## Configuration settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `searchMode` | Hybrid retrieval | Support multi-source heterogeneous change and metadata content for this category, covering both text and field information |
| `limit` | Top 20 entries | Control the scale of the retrieved dataset, matching the single-update volume of release-related data |
| `similarity` | 0.75–0.85 | Filter low-relevance change entries, focusing on high-match content that operations teams care about |
| `usingReRank` | Enabled | Prioritize high-impact breaking changes and core release items, aligning with the priority requirements of operations on-call work |
| Re-ranking recall limit | Top 10 entries | Balance re-ranking computation overhead and result accuracy, matching the number of change entries for a single version |
| Context window | Calibrated via actual testing | Adapt to the length of different version release documents, avoiding truncation of key information |

## Three common configuration mistakes
- Phenomenon: After configuring `usingReRank` as enabled, the returned results are still not sorted by priority, and the re-ranking switch status shows disabled. Cause: The enabled re-ranking setting was not saved in the retrieval configuration bound to the knowledge base, or the configuration was not synchronized to the retrieval engine.
- Phenomenon: The hybrid retrieval return results have little difference from semantic retrieval, and do not cover metadata entries such as associated Issues and artifacts. Cause: The hybrid retrieval metadata matching rules were not configured correctly, and only text semantic retrieval was enabled.
- Phenomenon: The number of retrieval results exceeds the expected limit, causing slow page loading. Cause: The `limit` configuration value is too large, not matching the average volume of change entries for a single version in this category.

## How to verify correct configuration
- Enter the knowledge base configuration page of FastGPT v4.17.0, and check whether the settings for `searchMode`, `limit`, `similarity`, and `usingReRank` match the configuration table.
- Initiate a test retrieval, enter a query that includes a version number and change type, and verify whether the returned results are sorted according to the priority of high-impact entries.
- View the retrieval log to confirm that the single recall count and re-ranking recall limit values meet the configuration requirements.
- Compare the return results of semantic retrieval and hybrid retrieval to confirm that hybrid retrieval covers metadata-associated entries.
