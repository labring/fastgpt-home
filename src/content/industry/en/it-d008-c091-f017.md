# Operations on-duty and internal ticket Q&A for player customer service and public opinion processing: Deployment and upgrade

## What this category’s data looks like
This category’s data primarily comes from customer service systems, community forums, app store reviews, and game logs. The update rhythm is mostly daily updates or real-time synchronization. Daily processed documents include player tickets, compensation requests, public opinion daily reports, and standardized response scripts. Common data fields include unique ticket identifiers, player account information, feedback content, processing status, public opinion keywords, and source channels. No additional mandatory statistical units are used.

## What constraints do these characteristics impose during deployment and upgrade?
The data sources for this category are scattered and updates are real-time. This requires configuring stable database and cache connections during deployment to avoid service interruptions caused by concurrent requests. The structure of daily documents varies widely, so storage configurations must be adapted to the read and write needs of different data types. The real-time nature of player feedback requires support for gray release during upgrades to avoid service unavailability caused by full switching. Data is also linked to player accounts and public opinion information, so permission parameters must be strictly configured during deployment to prevent sensitive information leaks. It is necessary to support format differences across various data sources to avoid format errors during import or synchronization.

## How to set the configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `20–30 connections` | Adapts to the concurrent read and write requirements of real-time updated player tickets and public opinion data, and prevents connection exhaustion |
| `MONGODB_URI` | Standard connection string pointing to an independent sharded cluster | Stores unstructured data such as player tickets and public opinion logs, and meets daily or real-time write requirements |
| `REDIS_URL` | Connection address configured for an in-memory cache instance | Caches frequently queried compensation rules and standardized response scripts, reducing database read pressure |
| `ROOT_KEY` | `Custom key string with a minimum length of 32 characters` | Restricts access to background management interfaces, protecting sensitive operational data |
| `STORAGE_S3_ENDPOINT` | Fill in according to the regional endpoints provided by the deployed cloud service provider | Stores large-capacity unstructured data such as public opinion daily reports and ticket attachments |

## Three common mistakes
- Symptom: Conversation logs are lost, and historical player feedback records cannot be queried through the interface. Cause: `REDIS_URL` is not configured to cache session data, or the read/write permissions of `MONGODB_URI` are insufficient, causing log write failures.
- Symptom: The background management interface cannot be accessed after the service starts, returning a 403 status code. Cause: `ROOT_KEY` is not set correctly, or the key string length does not meet the requirements, causing identity verification to fail.
- Symptom: Timeout errors occur when importing public opinion data in batches. Cause: The value of `DB_MAX_LINK` is too low, which cannot support concurrent write requests for batch data.

## How to confirm the configuration is correct
- Run the container status check command to confirm that the FastGPT container has not exited abnormally.
- Call the version query interface, which returns `FastGPT v4.17.0` version information, confirming that the deployed version is correct.
- Submit a test player ticket, and check whether a corresponding data entry is generated in the database corresponding to `MONGODB_URI`.
- After configuring `REDIS_URL`, query the frequently used script cache to confirm that cache hits occur without significant delays.

The values provided are common starting points and should be measured against the reader's own samples.
