# Operational On-Call and Internal Ticket Q&A for Player Customer Support and Public Opinion Management: Reranking and Hybrid Retrieval

## What Typical Data Looks Like for This Use Case
Typical data for this use case comes from game customer support systems, community forums, app store reviews, and game logs. Daily documents include player tickets, compensation requests, public opinion daily reports, and standard response scripts. Data update frequency is typically daily or real-time. Documents usually contain fields such as account identifiers, feedback type, submission time, and feedback content. The primary storage unit is natural text entries, with no fixed quantitative unit.

## Constraints for Reranking and Hybrid Retrieval
Multi-source heterogeneous data sources require hybrid retrieval to balance keyword matching and semantic recall, to avoid missing cross-platform player feedback. Real-time data updates require the retrieval pipeline to have low-latency reranking capabilities, to quickly filter outdated or irrelevant content. Document structures dominated by short text require reranking models to optimize ranking logic for short contexts, to prevent semantic matching errors caused by overly short text. Errors in this scenario directly impact player retention and community reputation. As such, the reranking stage must prioritize recalling content strongly related to account verification, compensation rules, and negative feedback categorization, to ensure retrieval result accuracy.

## How to Set Configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `usingReRank` | Enabled | Filters redundant content from multi-source public opinion and ticket data, improves retrieval relevance |
| `similarity` | 0.75–0.85 | Balances semantic recall precision and coverage, adapts to short-text customer support data |
| `limit` | Top 20 entries | Adapts to daily new ticket and public opinion data volume, prevents retrieval resource overload |
| `searchMode` | Hybrid retrieval | Balances keyword matching and vector semantic recall, covers cross-platform feedback content |
| Reranked result count | Top 5–8 entries | Adapts to the work scenario of customer support staff quickly reviewing and processing requests, reduces information redundancy |
| `AIPROXY_API_TOKEN` | Must be configured on the App/Admin server, value must match the administrator Token used by AI Proxy | This variable is a server-side environment variable required for AI Proxy authentication, and must not be entered in the application interface |

## Three Common Configuration Errors
- Knowledge base retrieval results do not change order. This occurs when `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are not configured on the App/Admin server, or when configuration values are invalid, preventing normal reranking service calls.
- Reranked results do not sort as expected, and the server returns a 401 status code. This occurs when the `AIPROXY_API_TOKEN` configured on the App/Admin server does not match the value set on the AI Proxy server, causing authentication failure.
- The reranking function cannot be called normally, and deployment logs indicate a missing required environment variable. This occurs when `AIPROXY_API_ENDPOINT` or `AIPROXY_API_TOKEN` are not configured on the App/Admin server, or when the `AIPROXY_API_ENDPOINT` value includes a `/v1` or `/chat/completions` suffix instead of using the service root address format.

## How to Verify Correct Configuration
- Check the environment variable configuration on the App/Admin server, confirm that both `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are correctly filled and not empty.
- Enable the reranking switch on the application configuration page, set a reasonable similarity threshold and single-pass recall limit, save the settings, and trigger a knowledge base retrieval.
- Compare the order of retrieval results before and after enabling reranking, confirm that the result order has adjusted as expected.
- Check the server runtime logs, confirm that there are no error messages about failed reranking service calls.

The values provided above are common starting points, and should be evaluated against samples appropriate for the specific deployment.
