# On-site Deployment Implementation for Operations Duty and Internal Ticket Q&A: Deployment and Upgrade

## What this category of data looks like
The data sources for this category include customer data center environments, device inventories, software packages, and network topologies. Daily associated documents include deployment manuals, installation records, configuration lists, and on-site check-in sheets. The data update frequency is per order or per phase, and it is maintained jointly by implementation engineers, system engineers, and customer IT staff. Data fields include device models, software versions, configuration parameters, on-site operation records, and more. There is no unified mandatory format, and it must match the actual record requirements of the customer’s on-site environment.

## What constraints do these characteristics impose on the "Deployment and Upgrade" workflow
Since the data relies on the exclusive environment and device inventory of the customer’s on-site location, pre-deployment checks must be conducted one by one for the network connectivity and resource quotas of the customer’s data center. Standardized general configurations cannot be directly reused. The per-order data update rhythm requires that each deployment and upgrade must rematch the customer’s current configuration list to avoid conflicts caused by leftover historical parameters. The non-mandatory format requirement for daily documents requires simultaneous updates to deployment manuals, installation records, and other files to ensure on-site operations are traceable. At the same time, on-site deployment relies on local software packages and the customer’s network. Available mirror resources must be prepared in advance to avoid pull failures caused by network restrictions.

## How to set the configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 100–200 connections | Adapts to the concurrent request volume of a single customer data center for on-site deployment, avoids database connection exhaustion, and complies with the database connection pool configuration requirements of FastGPT v4.17.0 |
| `MONGODB_URI` | MongoDB service address accessible via the customer data center intranet | Ensures local storage security of ticket data and knowledge base content, and complies with customer network isolation requirements |
| `REDIS_URL` | Redis instance address deployed on the customer’s on-site location, set connection timeout to 30 seconds | Supports real-time session caching for operations duty, avoids response speed impacts from cross-public network delays |
| `STORAGE_S3_ENDPOINT` | Intranet endpoint of a domestically available object storage service | Adapts to the on-site deployment network environment, reduces file transfer time consumption |
| `ROOT_KEY` | Random string generated according to on-site security policies | Ensures the security of background management permissions, avoids default key leaks |
| `FE_DOMAIN` | Access domain name or IP address assigned by the customer’s on-site location | Matches the customer’s network access rules, ensures normal access to the internal ticket system |

## Three common mistakes
- Using a public network address when configuring `MONGODB_URI`, resulting in database connection timeout errors. The cause is failure to follow on-site deployment network isolation requirements, and failure to use a service address accessible via the customer intranet.
- A significant increase in knowledge base retrieval time after upgrading the version, with no obvious errors in logs. The cause is failure to synchronize the `DB_MAX_LINK` configuration, leading to database connection pool exhaustion and queuing of retrieval requests.
- A plugin pull failure prompt during deployment, returning a 404 status code with no response body. The cause is failure to configure domestically available mirror resources, directly using the official address resulting in restricted network access.

## How to confirm the configurations are set correctly
- Run the database connection test command to verify the connectivity of configurations including `DB_MAX_LINK`, `MONGODB_URI`, and `REDIS_URL`, and confirm that the connection count meets the bearing requirements of the on-site environment.
- Access the address configured in `FE_DOMAIN` to verify that the internal ticket and operations duty interfaces load normally, with no access permission errors.
- Upload a test file to the storage service configured in `STORAGE_S3_ENDPOINT` to confirm that there are no delays or failures in file transfer.
- Generate a random `ROOT_KEY` and test the permission verification of the background management interface to confirm that the configuration takes effect and there is no risk of default key leakage.

The values provided are common starting points and should be measured against the reader's own samples.
