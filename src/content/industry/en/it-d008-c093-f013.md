# Operations On-Call and Internal Ticket Q&A for User Growth and Retention Operations: Permission and Data Isolation

## What the data for this category looks like
Data for this category comes primarily from user behavior logs, push systems, experiment platforms, and CRM systems. Most updates occur daily or weekly. Daily output documents include growth experiment plans, user segmentation tables, outreach copy, and retention analysis reports. Most data fields include user identifiers, behavior types, outreach channels, experiment groups, and conversion metrics. There are no unified fixed units, and some fields require format matching based on specific business scenarios.

## What constraints do these characteristics impose on permission and data isolation
Data for this category includes sensitive information such as user behavior and experiment groups, with sources scattered across multiple systems. Permission isolation must ensure unauthorized personnel cannot access experiment data or user segmentation tables from different operation groups. Daily document updates happen frequently, so permission configurations must adapt to rapidly iterating business needs. Overly strict permission checks must not block data queries or ticket processing. Sensitivity varies widely across documents: outreach copy and user segmentation tables require stricter isolation rules. Configurations must not slow internal operations on-call response times, and must prevent ticket circulation delays or data leaks caused by permission issues.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` binding | Assign exclusive IDs by business line | Isolate knowledge bases and internal ticket data for different growth operation teams |
| `tmbId` permission check | Enable fine-grained verification | Restrict permissions for temporary on-call ticket requests from individual operation staff |
| Sensitive data encryption | Enable | Protect sensitive business information in user segmentation tables and outreach copy |
| Log retention period | 7–30 days | Meet routine audit and troubleshooting needs for operations on-call |
| External call authentication | Bind application-specific API Key | Prevent permission leaks caused by misuse of AI Proxy admin Token |

## Three common misconfigurations
- Misuse of AI Proxy admin Token for external application API authentication, which allows unauthorized personnel to access full operation data. This happens when users confuse the usage scenarios of server environment variables and application API authentication keys.
- Failure to configure `teamId` isolation rules, which lets growth experiment data from different business lines be visible to each other. This leads to experiment result leaks or budget allocation confusion, and occurs when users ignore the business characteristic of grouping category data by business line.
- Failure to clarify the correspondence between knowledge base storage and tenant permissions, which makes it impossible to quickly export retention analysis reports for a specified team. This happens when users confuse general storage logic with the isolation needs of category-specific data.
