# Operations On-Call and Internal Ticket Q&A for User Growth and Retention Operations: Reranking and Hybrid Retrieval

## What the data for this category looks like
The core documents for this category include growth experiment plans, user segmentation tables, outreach copy, and retention analysis reports. Data sources include user behavior logs, push systems, experiment platforms, and CRM systems. Most updates run on a daily or weekly cadence. Document fields typically include user segmentation tags, outreach channels, experiment variables, retention metrics, and similar attributes. Individual document lengths vary widely, from hundreds of characters of outreach copy to tens of thousands of characters of analysis reports. All documents contain both structured tags and unstructured text content.

## What constraints do these characteristics impose on reranking and hybrid retrieval?
The data characteristics of this category create multiple constraints for the reranking and hybrid retrieval workflow:
First, most data comes from business system logs and reports with inconsistent formats. Hybrid retrieval must support both structured user segmentation fields and unstructured copy and analysis report content.
Second, updates occur on a daily or weekly basis. The retrieval dataset must be refreshed regularly. Reranking model call frequency must match the data update rhythm.
Third, document length varies widely, with both short texts and long documents present. The reranking model’s input length must adapt to different text types.
Finally, the scenario focuses on operations on-call and internal tickets. Retrieval results must prioritize alignment with operational workflows and rules, rather than relying solely on semantic similarity.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `usingReRank` | Enabled | This category of documents includes short-text outreach copy and long-form analysis reports. Reranking filters low-relevance results and improves retrieval accuracy |
| `similarity` | 0.75–0.85 | Balances recall coverage and result relevance. It adapts to matching requirements for structured fields such as user segmentation tags and experiment variables |
| `limit` | Top 10 entries | Valid information for internal tickets and operational documents typically concentrates in early recall results. Excessive entries increase reranking time overhead |
| `searchMode` | Hybrid retrieval | This category of data includes both structured tags and unstructured text. Hybrid retrieval matches both keyword and semantic features |
| Reranking model call timeout threshold | 600 seconds | Adapts to batch processing of long-form analysis reports. It aligns with the refresh rhythm of daily data updates |

## Three common misconfigurations
-  After deploying FastGPT v4.17.0 offline and configuring the reranking model, selecting model test triggers a request error. Incorrect configuration of the offline reranking model’s local path and environment dependencies causes this. Failure to complete offline import verification for the model files is another cause.
-  Retrieval speed drops significantly after reranking is enabled. Failing to limit the number of recall entries via the `limit` parameter causes this. Using overly long document segments also contributes. Per-round retrieval text volume exceeds the reranking model’s processing limit as a result.
-  A text understanding model is incorrectly configured as the reranking model. Confusion between the functional positioning of embedding models and reranking models causes this. Failure to distinguish their roles in the retrieval pipeline is another factor.

## How to confirm the configuration is complete
-  Access the knowledge base’s retrieval configuration page, confirm the `usingReRank` switch is enabled.
-  Submit a test query, check whether retrieval result sorting aligns with business priorities. For example, verify that results matching user segmentation tags are displayed first.
-  Review system logs to confirm that reranking model call requests have no timeouts or errors. Confirm that call frequency matches the data update rhythm.
-  Compare retrieval results with and without reranking enabled, confirm that retrieval result relevance and sorting logic meet expectations.
