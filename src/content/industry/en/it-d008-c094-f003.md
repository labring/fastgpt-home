# Operations on-duty and Internal Work Order Q&A for User Acceptance Testing Support: Sharing and Embedding

## What the data for this category looks like
This category’s data comes from requirement specification documents, test environment operation logs, customer business sample data, and defect management systems. Core daily output documents include UAT test cases, acceptance issue tickets, acceptance reports, and signed confirmation forms. Data is updated once per project phase or version iteration. Data fields include test case number, test scenario description, issue priority, acceptance status, associated business modules, etc. It is designed exclusively around the acceptance confirmation process, with no additional custom statistical fields.

## What constraints these characteristics impose on sharing and embedding
This category’s data sources are scattered and linked to customer business samples. Strict access permission control must be implemented during sharing and embedding to avoid leakage of customer sensitive business data. Data is updated per project phase or version iteration. Sharing links or embedded components must be implemented by external systems to synchronize content according to the update rhythm, to avoid displaying expired UAT test cases or acceptance issues. The core document structure is fixed, so embedded components must adapt to the unified field display logic, with no need for additional custom formatting. At the same time, data is linked to test environments and defect systems. When embedding, ensure that the data source permissions called match the sharing target, to avoid cross-project data confusion.

## Three common misconfigurations
- Sharing entries related to user acceptance testing support fail to open. First verify the full system-generated link and its validity period, then check browser request status; do not manually replace `shareId`.
- The visible scope of user acceptance testing support data does not match expectations. Verify third-party identity verification results, workflow request parameters, and external system data permissions separately; the sharing entry identifier itself does not provide business authorization.
- The same user acceptance testing support Q&A is not visible on another device. In anonymous scenarios, first check the device, browser, and local identity status; record retention is not guaranteed across devices or after cache clearance, so do not judge the service as abnormal based solely on this phenomenon.

## How to confirm the configuration is complete
- Open the sharing link, verify that only authorized internal users can access it, and unauthorized users cannot view the page content.
- Trigger an on-duty operations Q&A, confirm that the returned content is the latest UAT test cases and acceptance issue data for the current project.
- In the release channel - no-login window of the FastGPT application details, confirm that a sharing link containing a valid `shareId` has been generated.
- Adjust the sharing link validity period to 1 day, wait 1 day, then verify that the link cannot be accessed normally.

The values provided here are common starting points and should be measured against the reader's own samples.
