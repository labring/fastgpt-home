# Operations on-call and internal ticket Q&A for community report handling: Sharing and embedding

## What the data for this use case looks like
Daily documents for this use case typically include report tickets, processing records, appeal forms, and user notification templates. Core fields include report ID, associated content ID, reporter information, disposal result, processing timestamp, with units of count, times, hours. Data sources include community report systems, policy-violating content detail pages, user historical report records, and audit rule bases. Update rhythm is usually real-time or daily synchronization. During processing, associated information for individual reports must be frequently retrieved. Individual data volume is small but highly correlated, with no high-frequency demand for batch aggregation.

## Constraints imposed by these characteristics on sharing and embedding
The strong correlation of individual report data requires that shared embedded sessions carry corresponding business identifiers to avoid context confusion across report tickets. Real-time or daily updated data requires external systems to implement logic for real-time pulling of the latest audit rules and processing records. FastGPT’s built-in static cache cannot be relied on for this. For scenarios where individual information is frequently retrieved, the session context must retain sufficient historical processing records. The total context volume must also be limited to avoid performance loss. Incorrect configuration may lead to delayed disposal of policy-violating content, triggering escalation of community conflicts. Therefore, the stability of sharing and embedding, and the accuracy of business fields, have high requirements.

The following configurations are based on FastGPT v4.17.0, and are adapted to the community report handling business scenario:

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Sharing entry `shareId` | Copy the complete share link generated by the system; do not manually replace the identifier | Identifies the sharing entry; business records and data permissions for community report handling must still be processed by external systems |
| Share link validity period | Test starting point: 7 days; adjust based on actual testing of community report handling collaboration cycles and revocation requirements | Verify availability within the validity period and access behavior after expiration; this value is not an official default or industry statistic |
| QPM | Test starting point: 20 requests per user per minute; adjust based on actual load | Limits the access frequency of a single user; must be verified combined with request logs and actual load |

## Three common configuration errors
- Sharing entries related to community report handling fail to open. First verify the complete system-generated link and its validity period, then check browser request status; do not manually replace `shareId`.
- The visible scope of community report handling data does not match expectations. Verify third-party identity verification results, workflow request parameters, and external system data permissions respectively; the sharing entry identifier itself does not provide business authorization.
- The same community report handling Q&A is not visible on another device. For anonymous scenarios, first check device, browser, and local identity status; record retention cannot be guaranteed across devices or after cache clearance, and service abnormalities cannot be judged solely based on this phenomenon.

## How to verify successful configuration
- Open the shared embedded page, use the same device and browser to input test report content and submit, submit new content again, check if the session retains historical context, confirm that the session configuration and `shareId` configuration are effective.
- Check if the page display copy matches the preset language settings, confirm that the page language configuration is correct.
- Add a test report ID parameter to the share link, check if the page receives and displays the parameter, confirm that external business parameter transfer logic is normal.
- Long-press to trigger voice input, wait for the corresponding threshold duration before releasing, confirm that voice recognition and sending functions are normal, verify the voice timeout threshold configuration (recommended value: 5 seconds, pending actual testing).

The values provided are common starting points and should be measured against the reader's own samples.
