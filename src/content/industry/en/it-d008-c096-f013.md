# Operations on-call and internal ticket Q&A for community report handling: Permission and data isolation

## What this category of data looks like
This category of data primarily comes from community report systems, pending review content details, involved user historical records, and official review rules. Daily processed documents include report tickets, disposal records, appeal forms, and user notification templates. Data updates occur in real time or on a daily basis.
A single report ticket typically includes fields such as involved content link, reporting user ID, reported user ID, violation type tag, and submission time. Disposal records are associated with ticket IDs and auditor identifiers. The data structure is built around the full process flow of a single report event, and all documents are linked via ticket IDs.

## Constraints imposed on permission and data isolation
Since data flows around single report events and is associated with multiple sensitive entities, access scopes for different roles must be strictly restricted to prevent unauthorized viewing of unassigned report tickets. Real-time updated report data requires permission checks to take effect synchronously, to prevent access to old data after permission changes. Associated storage of multiple document types requires isolation mechanisms to support cross-document permission linkage. For example, only the assigned operations team can view their assigned appeal forms and notification templates.
Internal configuration of review rules must be restricted to only allow operations and maintenance personnel to make changes. This prevents unauthorized personnel from adjusting review standards and compromising the consistency of community governance.

## Configuration guidelines
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Divide by operations team, use the team's unique identifier string as the value | Used to bind report tickets to their assigned operations team, ensuring only corresponding team members can access the team's report data |
| `tmbId` | Divide by audit groups, use the group's unique identifier string as the value | Used to refine permissions within a team, only allowing specified audit groups to view assigned report tickets |
| Role permission grouping | Divided into three categories: operations administrator, auditor, and appeal specialist. Each category only grants corresponding permission scopes | Matches different job responsibilities in community report handling, to prevent unauthorized operations |
| Data isolation scope | Isolation granularity is set per single report ticket and associated document group | Matches the characteristic that this category of data flows around single events, to avoid bulk leakage of sensitive report information |
| Permission check timeout | `600 seconds` | Ensures permission checks do not block ticket processing efficiency |
| Sensitive data encryption | Enable end-to-end encryption for involved user IDs and content details, with storage granularity set to single ticket | Protects user privacy data involved in reports, complies with privacy requirements for community governance |

## Three common configuration errors
- Issue: After local deployment, the team-level permission function cannot be enabled, and report tickets cannot be assigned to different audit groups. Cause: The team version permission basic configuration of FastGPT v4.17.0 is not enabled, and the generation rule for `teamId` is not correctly set.
- Issue: When attempting to export associated knowledge base content of report tickets, the returned file contains ticket data from other operations teams. Cause: The data isolation scope is not configured to single-team, and permission checks do not filter cross-team associated data.
- Issue: After logging in, an auditor views an appeal form, and the associated report content details field is empty. Cause: The binding relationship between `tmbId` and the appeal form is not configured, and permission checks do not cover cross-document associated data.

## How to confirm correct configuration
- Access the system using an account from a non-assigned operations team, attempt to access the target report ticket, and verify that access is denied and a permission rejection prompt is returned.
- Use an account from an audit group not assigned the target ticket, attempt to view the specified report ticket, and verify that access to the corresponding data is denied.
- Export the current team's report ticket data, and verify that only tickets and documents associated with the current team are included, with no cross-team data mixed in.
- Modify the `teamId` parameter, revisit the original report ticket, and verify that permission checks take effect, and the original account can no longer access the ticket.
