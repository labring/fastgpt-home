# Operations on Duty and Internal Work Order Q&A for Community Complaint Handling: Deployment and Upgrade

## What the data for this category looks like
Community complaint handling scenarios use individual complaint work orders as the smallest management unit. Data sources include the community complaint system, detailed pages of reported content, historical behavior records of reporting users, and preset platform review rules. Update frequency is daily or real-time, depending on the daily traffic scale of the community. Core documents involved in daily operations include complaint work order ledgers, processing progress records, user appeal forms, and standardized user notification templates. Data fields include unique complaint identifiers, reported content links, complaint reasons, disposal status, associated review rule IDs, and more. There is no unified fixed unit; values change based on the content volume of individual work orders and the amount of associated data.

## What constraints these characteristics impose on deployment and upgrade
The per-order processing nature of this category requires that the processing link for individual work orders remain uninterrupted during deployment. Upgrades must use a gray release strategy to avoid interrupting community operation processes in bulk. The real-time or daily data update frequency requires database connection configurations to adapt to high-frequency read and write scenarios. The value of `DB_MAX_LINK` must be set appropriately. The requirement for multi-source data access requires configuring `STORAGE_S3_ENDPOINT` to set a unified attachment storage path, ensuring that evidence files for complaint work orders can be retrieved normally. At the same time, user notification templates associated with work orders must be bound to `FE_DOMAIN` to standardize jump links, preventing configuration inconsistencies from causing notification jump failures.

## How to configure the settings
These configuration items are compatible with FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 100–200 | Adapts to the high-frequency database read and write requirements of community complaint work orders, calibrated based on actual testing |
| `MONGODB_URI` | Cluster connection address containing authentication information | Stores unstructured business data such as complaint work orders and processing records |
| `REDIS_URL` | Independent cache instance address with password, cache validity period set to 3600 seconds | Caches real-time complaint queues and user session information to avoid repeated processing of the same work order |
| `FE_DOMAIN` | Official front-end domain name of the community | Generates jump links in complaint processing notifications, ensuring users can normally access the detailed page of reported content |
| `FILE_TOKEN_KEY` | Randomly generated 32-character string | Encrypts access tokens for storing complaint evidence files, preventing unauthorized downloads |
| `ROOT_KEY` | Complex random string, rotated every quarter | Configures the highest-privilege access credential for system administrators, ensuring the security of background configuration operations |

## Three common configuration mistakes
- Symptom: After restarting the server or container, the shared link for complaint work orders cannot be accessed normally, displaying a page not found prompt. Cause: The `FE_DOMAIN` parameter was not configured correctly, causing the generated jump link to be bound to a temporary local address, which becomes invalid after a restart.
- Symptom: Audit personnel cannot normally download complaint evidence files, receiving a 403 status code. Cause: The `FILE_TOKEN_KEY` was not set, or a duplicate token value was configured, causing access token verification to fail.
- Symptom: Database connection timeouts occur when the system processes complaint work orders, with background logs showing connection count exceeded. Cause: The value of `DB_MAX_LINK` is too low, failing to adapt to the high-frequency read and write requirements of community complaints.

## How to verify correct configuration
- Submit a test complaint work order, review the jump link in the generated user notification, and confirm the domain matches the preset `FE_DOMAIN`.
- Upload a complaint evidence file, attempt to download using the generated access link, confirm it can be opened normally with no permission errors.
- Check database connection pool monitoring metrics, confirm the current connection count does not exceed the set `DB_MAX_LINK` value.
- Attempt to log in to the system background using `ROOT_KEY`, confirm normal access to the administrator configuration page with no permission intercepts.

The values provided are common starting points and should be evaluated using sample data from the target deployment.
