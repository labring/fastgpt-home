# Operations Duty and Internal Ticket Q&A for Community Report Handling: Reranking and Hybrid Retrieval

## What data for this category looks like
This category’s data comes from community report systems, content details pending review, user historical report records, and built-in audit rule libraries.
Daily processed documents include report tickets, report processing records, user appeal forms, and violation notification templates.
Data updates run daily or sync in real time.
Individual data entries include report identifiers, associated content links, report types, submitting user information, and disposal status.
Each ticket is processed independently as it moves through the workflow.

## What constraints these characteristics impose on the reranking and hybrid retrieval link
This category’s data comes from multiple sources and updates in real time. Hybrid retrieval must cover report system tickets, historical audit records, audit rule libraries, and associated content details. This prevents missing critical reference data during retrieval.
Each ticket is processed independently. Retrieval results must be aggregated by report type and associated content dimensions. This helps duty staff quickly locate similar disposal cases.
Document structures vary widely across types. The reranking stage must distinguish matching weights for rule text, historical records, and content details. This ensures highly relevant results are displayed first.
Real-time updated data requires the retrieval pipeline to support incremental sync. This prevents disposal errors caused by outdated data.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `usingReRank` | Enabled | Community report handling needs to prioritize displaying highly relevant historical disposal records and audit rules. Reranking filters low-relevance recall results to improve retrieval accuracy |
| `similarity` | `0.72–0.85` | Content similarity for report tickets must cover typical matching rates for similar reports. The range is calibrated via testing to avoid missing similar report cases or misjudging unrelated content |
| `limit` | Top 10 entries | Reference information for a single ticket handled by duty staff should not be excessive. The top 10 entries cover most disposal experience for similar reports, while limiting retrieval time |
| `searchMode` | Hybrid retrieval | Must recall historical tickets, audit rules, and associated content details at the same time. Hybrid retrieval combines the strengths of vector recall and keyword recall to cover matching needs for different types |
| Rerank model batch processing count | `5–8 entries` | Processing a small number of entries per batch reduces computing resource usage. This fits the daily operations scenario for community report handling |

## Three common mistakes
- Symptom: After deploying FastGPT v4.17.0 offline, clicking model test when configuring a rerank model shows a request error, or offline model loading fails. Cause: The rerank model file was not placed in the specified local model directory, or the local model path was not filled correctly in the configuration file.
- Symptom: After enabling the rerank function, single retrieval takes more than 10 seconds. This affects response efficiency for operations duty. Cause: The `limit` parameter value is set too large, or the rerank model has insufficient inference resources. This increases processing time per data entry.
- Symptom: In hybrid retrieval results, the matching score for audit rules is lower than that for historical tickets. This causes retrieval results to fail to meet expected disposal reference needs. Cause: Different document type weights were not configured during the reranking stage. The matching weight for rule text was not adjusted appropriately higher.

## How to confirm configuration is complete
- Enter the FastGPT model test page, select the configured rerank model, and enter sample text for a report ticket. Check that normal similarity scores and sorted results are returned.
- Submit a test report ticket. Check that the number of retrieval results matches the `limit` parameter setting, and that sorted results follow the expectation of displaying highly relevant content first.
- Check system operation logs. Confirm that the rerank model call status is successful, with no timeout or error records.
- Adjust the `similarity` parameter value. Verify that the recall range of retrieval results adjusts appropriately as the parameter changes.

The values provided are common starting points. They should be evaluated against the reader’s own samples.
