# Operations on-call and internal ticket Q&A for community events and developer relations: Permission and data isolation

## What data for this category looks like
The data for this category mainly comes from community forums, registration systems, social media, and project roadmaps, with an update frequency of monthly or after each event. Daily produced documents include event plans, speaking scripts, registration lists, and event review files. Each document field has its own focus: event plans include fields for event theme, time, and venue; speaking scripts mark speaker, duration, and topics; registration lists record participant names, contact information, and affiliated institutions; event reviews include number of participants, feedback scores, and items to be optimized. Data is stored in a mixed format of structured tables and unstructured documents, with no unified cross-document field specification, and document formats vary widely across different events.

## What constraints these characteristics impose on permission and data isolation
Documents from different events involve sensitive information of different scopes. For example, registration lists contain personal contact information and should not be made public; speaking scripts and event plans are only accessible to the preparation team. Since the data update frequency is not fixed, permission configuration needs to support dynamic adjustment according to the event cycle to avoid retaining unnecessary permissions for long periods. Operations on-call for community events and developer relations needs to connect to multi-source data, and the permission boundaries of different source data must be clearly distinguished to prevent cross-event data leaks. At the same time, internal ticket Q&A needs to associate documents corresponding to the event, ensuring that ticket handlers can only access authorized data for the current event, preventing unrelated data from being retrieved or leaked.

## How to configure the setup
This document references configuration instructions for FastGPT v4.17.0. The specific configuration items are listed below:

| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| Team permission groups | Create independent permission groups for each single event | Matches the temporary usage attribute of event documents to avoid cross-event data access |
| `teamId` binding rules | Bind a dedicated `teamId` to each event document | Ensure internal ticket Q&A can only retrieve event-related documents bound to the current `teamId` |
| Data access range settings | Limit to no more than 20 documents associated with the current event | Narrow the retrieval scope to reduce the risk of sensitive data leaks |
| Role permission granularity | Intern roles only have access to public event documents, with no single document exceeding 1000 characters | Restrict accessible data types by job role to cover different permission requirements |
| Automatic permission expiration configuration | Automatically disable corresponding permissions 7 days after the event ends | Aligns with the event cycle to avoid retaining unnecessary access permissions for long periods |
| `tmbId` association | Associate operations on-call accounts to the corresponding event `tmbId` | Ensure on-call personnel can only handle internal tickets for the current event |

## Three common configuration errors
- Symptom: An "insufficient permissions" error is returned during internal ticket testing, and the event registration list document cannot be retrieved. Cause: The ticket handling account was not bound to the `teamId` of the corresponding event, so the system cannot identify the authorized scope.
- Symptom: Intern accounts can view review documents for all events. Cause: Independent permission groups were not created per event, and full access to all event data was granted by default.
- Symptom: After the knowledge base is published, speaking scripts for public events do not correctly match event-associated documents, and unauthorized content from other events is mixed in. Cause: No `teamId` binding rules were configured, so the retrieval scope was not limited to the current event.

## How to verify a correct configuration
- A non-authorized account attempts to access event documents bound to a `teamId`, confirming that the corresponding content cannot be retrieved.
- The intern role is activated, and verification confirms that only public event documents are accessible, while sensitive data such as registration lists cannot be accessed.
- Internal ticket Q&A is triggered, and returned results are confirmed to only include documents associated with the current event, with no cross-event data.
- 7 days after the event ends, verification confirms that the access permissions of the corresponding permission group automatically expire.

The values given here are common starting points and should be measured against the reader's own samples.
