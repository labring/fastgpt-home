# Operations on-call and internal ticket Q&A for community contributor governance: Deployment and upgrade

## What the data for this category looks like
Data sources for this category include code repository commit records, community forum interaction posts, contributor contribution statistics, and governance meeting minutes.
Daily maintained documents include contribution guides, code of conduct, maintainer lists, and governance meeting minutes.
Data is updated monthly or quarterly.
Core data is generated around personnel roles, governance rules, and decision-making processes.
Fields include contributor ID, permission level, rule version, meeting resolution number, and more.
There is no unified fixed unit, and it adjusts with document structure.

## What constraints these characteristics impose on deployment and upgrade
Data sources are scattered and update slowly.
Deployments must support multi-source data synchronization configuration.
Upgrades must retain historical data versions to avoid interrupting existing governance processes.
Daily documents include multiple types of structured and unstructured content.
Deployment links must support parsing and storage of governance documents in different formats.
Role permission confirmation steps are time-consuming and prone to errors.
Upgrades must retain permission inheritance logic to prevent permission confusion caused by configuration changes.
Governance rule changes require strict validation.
Deployment configurations must support rule version rollback to avoid governance disputes or contributor attrition.

## How to set configurations
This configuration guide applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `800–1200 connections`, calibrated via actual testing | Adapts to permission data query frequency in community contributor governance scenarios, prevents database connection exhaustion |
| `MONGODB_URI` | Local private network address | Stores unstructured content such as governance meeting minutes and contribution statistics, ensures data privacy |
| `PG_URL` | Independent instance address | Stores structured data such as role permissions and contributor IDs, supports multi-dimensional queries and permission verification |
| `REDIS_URL` | Local cache instance address | Caches governance rules and permission data, reduces database load from high-frequency queries |
| `FE_DOMAIN` | Community-exclusive domain name | Binds the frontend access address for internal ticket Q&A, ensures compliance of permission authentication scope |
| `FILE_TOKEN_KEY` | `Minimum 32 characters`, calibrated via actual testing | Used for identity verification of internal tickets, ensures authentication strength |
| `ROOT_KEY` | `Minimum 64 characters`, calibrated via actual testing | Used for highest-permission verification of the governance backend, prevents unauthorized access |
| `STORAGE_S3_ENDPOINT` | `Storage bucket capacity of at least 5000 MB`, calibrated via actual testing | Stores governance documents and contribution statistics, ensures sufficient storage capacity |

## Three common mistakes
- Phenomenon: After upgrading aiproxy, internal tickets cannot call AI capabilities, with an error prompt indicating the model is unauthorized. Cause: The AI proxy permission configuration for governance scenarios was not synchronized and updated, so the new proxy version is not included in the allowed call list.
- Phenomenon: After deployment, contributor permission fields are empty, and role confirmation cannot be completed. Cause: The database permission pointed to by `PG_URL` was not configured correctly, so structured role data cannot be read normally.
- Phenomenon: After upgrading, historical governance meeting minutes cannot be accessed normally, and links return a 404 error. Cause: The storage bucket access permission for `STORAGE_S3_ENDPOINT` was not updated, so old documents cannot be pulled normally.

## How to confirm the configuration is complete
- Run a database connection test, verify that the number of connections does not exceed the configured `DB_MAX_LINK` threshold.
- Access the internal ticket frontend page, verify that the identity verification logic can normally block unauthorized requests.
- Upload a governance meeting minute to the storage service, confirm that the document link can be obtained normally via the configured `STORAGE_S3_ENDPOINT`.
- Query contributor permission data, confirm that correct role information can be read from the database configured via `PG_URL`.

The values provided are common starting points and should be measured against the reader's own samples.
