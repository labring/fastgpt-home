# Operations On-Call and Internal Ticket Q&A for Community Contributor Governance: Reranking and Hybrid Retrieval

## What this category of data looks like
The data sources for this category include code repository commit records, community forum discussion threads, contribution statistics reports, governance meeting minutes, and official documentation. Daily maintained documents include contribution guides, code of conduct, maintainer lists, and quarterly governance meeting minutes. Data updates occur monthly or quarterly. Core fields include contributor ID, role permissions, contribution count, governance rule version, and meeting resolution content. The core processing objects are the identities, permissions, governance-related rules, and decision records of community contributors, which differ from static document data.

## Constraints Imposed on Reranking and Hybrid Retrieval
Data for this category is scattered across multiple sources, including structured maintainer lists and contribution statistics, as well as unstructured forum discussions and meeting minutes. Hybrid retrieval must therefore cover data sources in varying formats. Data update frequency is low, but changes must be synchronized promptly. The reranking phase must adapt to the low-frequency update rhythm of knowledge base indexing to avoid outdated retrieval results caused by indexing delays. Core content involves sensitive information such as permissions and roles. Retrieval result sorting must prioritize alignment with governance rule accuracy, with semantic similarity used only as a secondary reference. Additionally, retrieval must cover three high-frequency scenarios: role and permission confirmation, governance rule explanation, and contributor promotion evaluation. Reranking weights must be adjusted for different business scenarios, and irrelevant community casual chat content must be filtered out.

## Configuration Settings
The following configurations are written for FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Rerank Toggle | Enabled | Retrieval content for this category involves sensitive permissions and governance rules, so reranking is required to filter low-relevance redundant content |
| Similarity Threshold | 0.75–0.85 | Balances retrieval recall rate and semantic matching accuracy, adapting to retrieval requirements for sensitive content |
| Single Recall Limit | Top 10 entries | Controls the scale of returned results to avoid information overload in core scenarios such as role and permission confirmation |
| Retrieval Mode | Hybrid Retrieval | Covers multi-source heterogeneous data including code repository commit records, community forums, and contribution statistics |
| Rerank Model Call Timeout | 30 seconds | Adapts to the low-frequency data update rhythm of monthly/quarterly updates, avoiding timeouts during long-text retrieval |
| Rerank Model Type | Local Open-Source Model | Adapts to the localized deployment requirements of community governance data, reducing external call risks |

## Three Common Configuration Errors
- Symptom: After enabling the rerank toggle, no reranking results appear in online recall tests. Cause: The rerank configuration was not enabled during the knowledge base indexing process, or the rerank model call path was not correctly bound to the current retrieval workflow.
- Symptom: After deploying a local rerank model, the interface shows a request error. Cause: The listening port for the rerank model is not open, or the model address configured in FastGPT does not match the actual deployment address.
- Symptom: When using an ollama rerank model accessed via oneAPI, the interface returns Invalid URL (POST /v1/rerank). Cause: oneAPI was not properly configured with the rerank model interface path, or the ollama rerank model did not start the corresponding service port.

## How to Confirm Configuration Completion
- Navigate to the knowledge base retrieval test page, input a test question related to role permissions or governance rules, and check if the returned results include sorting markers from the reranking phase.
- Verify that the retrieval mode is set to Hybrid Retrieval, and confirm that the bound data sources include core category data such as contribution statistics and meeting minutes.
- Review the rerank model runtime logs to confirm there are no error reports for connection timeouts or parameter mistakes.
- Adjust the test range of the similarity threshold to validate whether retrieval result relevance aligns with business expectations.
