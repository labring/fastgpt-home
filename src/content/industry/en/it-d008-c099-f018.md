# Operations On-Duty and Internal Ticket Q&A for Mobile Development: Re-Ranking and Hybrid Retrieval

## What the data for this category looks like
Mobile development operations and ticket data typically comes from code repositories, app store backends, crash monitoring platforms, and device coverage data, with update frequencies of daily or per release cycle. Daily documents involved include device version release notes, device adaptation lists, crash analysis reports, and app store review materials. Data fields include device system version, crash log identifiers, package size, review progress, and more. The structure adjusts dynamically with version iterations and device coverage scope.

## What constraints do these characteristics impose on re-ranking and hybrid retrieval
The multi-source heterogeneous data characteristics of mobile development require hybrid retrieval to support recall results in different formats, such as code snippets, structured lists, and log text. Frequently updated version documents and real-time crash data require the re-ranking step to prioritize content with stronger timeliness. Device adaptation documents have highly specific fields, so re-ranking must adjust sorting weights based on device and system version keywords in the query. Permission troubleshooting and review issues involved in internal tickets need to be linked to permission call records in code repositories. Hybrid retrieval must connect associated fields across different data sources to avoid recalling irrelevant content.

## How to configure the settings
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `similarity` | 0.62–0.78 | In FastGPT v4.17.0, adapts to the highly specific fields of mobile development documents, filters low-relevance general operations and maintenance content, and avoids recalling results unrelated to devices and versions |
| `limit` | Top 8–12 entries | Covers common recall needs for multi-device adaptation and crash troubleshooting, prevents result overload that reduces rapid response efficiency during on-duty operations |
| `usingReRank` | Enabled | Adapts to the sorting needs of multi-source heterogeneous documents, corrects sorting bias from pure vector retrieval, and improves matching accuracy |
| `searchMode` | hybrid | Combines semantic matching from vector retrieval and precise matching from keyword retrieval, supports semantic queries for code snippets and keyword recall for structured documents |

## Three Common Configuration Mistakes
- Enabling `usingReRank` causes a model test prompt request error. The cause is that the local re-ranking model path was not configured in the offline deployment environment, or the model files were not mounted to the corresponding directory of the FastGPT container, resulting in model call failure.
- The number of hybrid retrieval return results does not match the `limit` configuration. The cause is that `searchMode` was set to pure vector retrieval mode, and hybrid mode was not enabled, so the recall source filtering rules did not take effect as configured.
- Retrieval latency is too long after re-ranking. The cause is that the `limit` value is too high, and the input length limit of the re-ranking model was not adjusted for short mobile development documents such as code snippets and single-line error logs, resulting in excessive model processing load.

## How to Confirm the Configuration Is Correct
- A user accesses the FastGPT model test page, selects the configured re-ranking model and retrieval parameters, inputs a mobile development-related query such as "iOS17 permission adaptation issue", and verifies that returned results include corresponding documents such as device adaptation lists and crash analysis reports.
- A user reviews retrieval logs to confirm that `searchMode` is set to hybrid, `usingReRank` is enabled, and the `similarity` threshold matches the configured value.
- A user simulates an internal ticket query, compares result sorting with and without re-ranking enabled, and confirms that highly relevant timeliness documents such as the same-day release version note appear at the top.
- A user checks the offline deployment container's mounted directory, confirms that the re-ranking model files exist and the path matches the configuration item, and verifies the validity of the offline configuration.
