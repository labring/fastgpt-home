# Operations On-Call and Internal Ticket Q&A for Renewal Health Management: Permissions and Data Isolation

## What the Data for This Category Looks Like
The core data for renewal health management typically comes from CRM systems, product usage data, internal ticket statistics, and contract ledgers. Update frequencies are mostly weekly or monthly. Daily produced documents include customer health reports, renewal forecast tables, high-risk customer lists, and customer communication records.

Data fields include customer ID, contract expiration date, 30-day usage frequency, renewal intention level, ticket response time, and others. Some fields are text enumeration values, while others are numerical statistical results. No unified fixed unit applies. The operations on-call and internal ticket Q&A scenarios require associating ownership permissions for these data.

## Constraints on Permissions and Data Isolation Posed by These Characteristics
Data sources span multiple internal systems, involving business permission boundaries across different roles. For example, customer success managers can only view data for assigned customers. Renewal managers must view the full team’s high-risk customer lists but cannot modify contract ledgers.

Data update cycles are not real-time. Permission checks must match team ownership within the current update cycle to prevent cross-team viewing of unauthorized data. Sensitivity levels vary across different documents. Communication records may only be viewed by members who participated in the conversation. Renewal forecast tables must be restricted to the sales operations team.

Internal ticket Q&A must associate permissions with the customer associated with the ticket, ensuring on-call personnel can only view relevant data for the corresponding customer. This aligns with permission control requirements for operations on-call.

## Configuration Settings
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` binding rule | Group by assigned customer teams, bind one `teamId` per group | High-risk customer lists for renewal health management are divided by team, which matches business ownership logic |
| `tmbId` permission scope | Only allow members to view customer-related data bound to `tmbId` | Customer success managers only need to view assigned customer health reports, which aligns with role permission requirements |
| Data isolation granularity | Configure per individual customer ownership, maximum 100 records per group | Prevent cross-team viewing of unauthorized renewal forecast tables and contract ledgers |
| Permission check trigger timing | Validate `teamId` before loading documents each time | Aligns with weekly/monthly data update cycles, ensuring permissions match the current data cycle |
| Forced permission prompt toggle | Disable the display of no-permission citations at the end of responses | Meets user experience requirements for internal ticket Q&A, avoids redundant prompts |

## Three Common Misconfigurations
- Phenomenon: Internal ticket Q&A initiated by different user IDs returns identical values for the same global variable. Cause: No binding of `tmbId` to isolate the scope of global variables, leading to global variables sharing the entire workflow context.
- Phenomenon: Team data returned by the tokenLogin interface fails to update synchronously after switching teams. Cause: Team data is not bound to `teamId` for storage in the session context, leading to permission checks using outdated team identifiers.
- Phenomenon: The prompt "No permission to operate this conversation record" is forcibly displayed at the end of knowledge base responses. Cause: The forced permission prompt toggle is not disabled, and the current user’s `teamId` is not validated against the team that owns the document.

## How to Verify Proper Configuration
- Log in to the system with accounts using different `teamId` values, view the high-risk customer list, and confirm that only customer data for the corresponding team is displayed.
- Call the tokenLogin interface, verify that the returned team data fully matches the current logged-in account’s `teamId`.
- Initiate an internal ticket Q&A, confirm that no forced no-permission operation prompt is displayed at the end of the response.
- Access the team management page, verify that it can be opened normally through the system-specified entry.
