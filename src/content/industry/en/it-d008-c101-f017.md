# Operation and Maintenance Duty and Internal Ticket Q&A for Renewal Health Management: Deployment and Upgrade

## What this category of data looks like
This category of data typically comes from CRM systems, product usage backends, internal ticket statistics ledgers, and contract management ledgers. Data update cycles are mostly weekly or monthly. Core documents include customer health reports, renewal forecast tables, high-risk customer lists, and cross-department communication minutes. Common data fields include customer unique identifiers, contract cycle nodes, product usage frequency, ticket response time, renewal trigger thresholds, and no unified mandatory units, with adjustments made per internal statistical rules.

## What constraints do these characteristics impose on deployment and upgrade
Data sources for this category are scattered and have fixed update rhythms. During deployment, multiple types of storage connections must be configured to connect to multi-source information such as CRM and product usage data, and weekly/monthly level data synchronization scheduling parameters must be matched. Since core document structures flexibly adjust per internal statistical rules, knowledge base indexes after deployment must support custom field mapping to avoid hard-coded restrictions on data access. As errors directly affect customer retention, the upgrade phase must retain rollback configurations, and `REDIS_URL` must be used to configure monitoring cache to quickly locate data link issues during exceptions. Additionally, for operation and maintenance duty scenarios, customer data associated with tickets must be quickly troubleshooted, so an association index between tickets and customer health data must be pre-configured during deployment to shorten fault troubleshooting time.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `20–30 connections` | Adapts to concurrent connection requirements for weekly/monthly batch data synchronization, avoids connection pool exhaustion |
| `MONGODB_URI` | Fill in the dedicated database connection address for customer health data and ticket ledgers | Isolates business data from general knowledge base data, reduces cross-scenario access risks |
| `PG_URL` | Fill in the structured data connection address synced from the CRM system | Supports structured query requirements for renewal forecast tables and high-risk customer lists |
| `REDIS_URL` | `127.0.0.1:6379` or dedicated cache cluster address | Caches frequently accessed customer health snapshots, reduces data read latency |
| `ROOT_KEY` | Generate a random string per internal operation and maintenance rules | Ensures backend management permission security after deployment, prevents unauthorized access |
| `FILE_TOKEN_KEY` | Set based on actual testing | Adapts to signature verification requirements for internal document uploads, prevents unauthorized file access |

## Three common mistakes
- After upgrading to FastGPT v4.17.0, knowledge base queries return results but cannot output to the model. The cause is that the association parameters between `FILE_TOKEN_KEY` and model invocation were not reconfigured after the upgrade, leading to document signature verification failure, so the model cannot read knowledge base content.
- After Docker deployment, the page on port 3000 cannot be opened, while port 3001 is accessible normally. The cause is that port mapping for `FE_DOMAIN` was not correctly bound during deployment, and the front-end service port configuration does not match the host port.
- Configuration parameters do not take effect after modifying the Linux deployment configuration file. The cause is that the corresponding service process was not restarted, or the modified configuration item was not loaded by the main process. For example, modifying `ROOT_KEY` requires a synchronous restart of the API service container.

## How to confirm the configuration is complete
- Run the data source connection test script to verify that the databases corresponding to `MONGODB_URI` and `PG_URL` can perform normal read and write operations, and check that the returned fields include customer health-related information.
- Access the address configured in `FE_DOMAIN`, confirm that the front-end page loads normally and can retrieve customer risk data returned by the back-end API interface.
- Call the model test interface, enter queries related to renewal health management, and confirm that the model can normally return answers based on the knowledge base.
- Check the cache monitoring indicators of `REDIS_URL`, confirm that frequently queried customer data has been cached, and there are no consecutive repeated database requests.
