# Operation Duty and Internal Ticket Q&A for Renewal Health Management: Reranking and Hybrid Retrieval

## What data for this specific category looks like
Data for this specific category typically comes from CRM systems, product usage data, internal ticket statistics, and contract ledgers. Regularly produced documents include customer health reports, renewal forecast sheets, high-risk customer lists, and communication minutes.
Data updates occur mostly weekly or monthly. Fields cover customer basic information, contract cycles, product usage frequency, ticket response status, and risk level tags.
Data formats are inconsistent: some are structured tables, some are unstructured text records.

## What constraints do these characteristics impose on the reranking and hybrid retrieval link
Multi-source heterogeneous data sources require hybrid retrieval to support both structured field recall and unstructured text retrieval. Recall rules adapted to multiple data types must be configured.
Weekly or monthly update frequency means reranking tasks do not need high-frequency triggering. Reranking can be run on a fixed cycle to reduce computing overhead.
Documents include content with clear priorities, such as high-risk customer lists. The reranking link must set weights based on business fields. High-risk customer data close to contract expiration dates or with a high number of tickets must be prioritized for recall. Low-priority information that distracts during operation duty must be avoided.
The internal ticket Q&A scenario requires concise and accurate retrieval results. The number and sorting logic of returned results must be controlled to match the usage habits of frontline operations and customer success staff.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `usingReRank` | Enabled | This scenario requires optimizing the sorting priority of high-risk customer data. Reranking improves the display position of critical information |
| `searchMode` | hybrid | Must recall both structured customer ledger fields and unstructured communication minutes content. Hybrid retrieval mode adapts to multi-source data types |
| `similarity` | 0.75–0.85 | Balances precise recall and coverage, adapts to the high-risk customer retrieval needs of renewal health management |
| `limit` | Top 10 entries | Controls the number of returned results to avoid information overload during operation duty, meets the conciseness requirements of internal ticket Q&A |
| Reranking model invocation method | Prioritize using open-source local models, call APIs as needed | Open-source models protect internal data privacy. API models adapt to higher computing power requirements, comply with enterprise internal security specifications |
| Reranking trigger timing | Trigger weekly | Matches the weekly or monthly update frequency of business data, avoids unnecessary reranking computing overhead |

## Three common misconfigurations
- Phenomenon: Unable to select the reranking model option when creating an application, the configuration item is grayed out. Cause: Failed to enable reranking in the `usingReRank` configuration item, or failed to load the reranking model file in system configuration.
- Phenomenon: After adding a reranking model, the order of knowledge base retrieval results does not change. Cause: Failed to set `searchMode` to hybrid mode, or the reranking model's invocation threshold is set too high, causing the reranking logic to not trigger.
- Phenomenon: Timeout error occurs when calling the reranking model. Cause: The `limit` parameter is not configured properly, too many returned results cause reranking computing timeout, or the deployed computing power of the open-source reranking model is insufficient.

## How to confirm the configuration is successful
- Enter the retrieval configuration page of FastGPT v4.17.0 application, confirm that the `usingReRank` switch is enabled.
- Submit a retrieval request targeting high-risk customers, check if the returned results prioritize displaying customer data close to contract expiration dates.
- Check the system backend logs, confirm that the reranking model has been successfully called with no error messages.
- Compare the order of retrieval results before and after enabling reranking, verify that the reranking logic is active.
