# Operations on-duty and internal work order Q&A for landing page conversion optimization: Deployment and Upgrade

## What the data for this category looks like
Typical participants in this category are growth product managers, front-end operations specialists, and ad optimization specialists. Data sources include landing page access logs, heatmaps, form data, and ad source parameters. Update frequency is weekly or within a single campaign cycle. Daily associated documents include landing page plans, tracking requirement documents, AB test reports, and form field lists. Data fields include page access paths, source channel identifiers, form field filling statuses, and page stay durations. Units include seconds, counts, and others. Adjust analysis dimensions alongside campaigns to ensure data aligns with business objectives.

## What constraints these characteristics impose on the "deployment and upgrade" link
Business data for landing page conversion optimization relies on multi-source logs and structured forms. During deployment, verify access permissions and format compatibility for all data sources to avoid data collection interruptions. The weekly or campaign-level update requirement means deployments must support rapid configuration adjustments after launch. This prevents disruptions to real-time data statistics and analysis. The structured nature of associated documents requires presetting field mapping rules during deployment. This ensures subsequent tracking and form configurations directly match the data storage structure. Additionally, fix the parsing logic for ad source parameters during deployment to ensure data attribution accuracy. This prevents attribution deviations after upgrades that could lead to lead loss or increased advertising costs. This link must balance configuration flexibility and data stability. Configuration errors can damage the business pipeline, so avoid them.

## How to set the configurations
All following configuration items apply to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `FE_DOMAIN` | The first-level domain name through which the landing page provides external services | Ensures paths for front-end resources and interface requests match, and complies with cross-domain access rules for landing pages |
| `REDIS_URL` | Address of a locally deployed Redis service, with port set to 6379 | Provides caching for landing page sessions and access logs, meeting real-time data reading requirements |
| `MONGODB_URI` | Connection string for an exclusive database | Stores form submission data and heatmap analysis results, adapting to the unstructured storage characteristics of category data |
| `DB_MAX_LINK` | 300–600 seconds | Limits the maximum idle duration of database connections, balancing resource usage and data access efficiency, and adapting to the weekly update business rhythm |
| `STORAGE_S3_ENDPOINT` | Configure according to the address of the landing page static resource hosting service provider | Hosts static file resources for the landing page, ensuring normal page loading |
| `ROOT_KEY` | A randomly generated 32-bit string | Serves as the system's internal root permission identifier, ensuring access security after deployment |

## Three common mistakes
- Phenomenon: A white screen appears when iOS devices access the externally exposed landing page chat interface, while macOS and Windows devices access normally. Cause: The `FE_DOMAIN` configuration does not include the cross-domain whitelist for iOS devices, resulting in blocked front-end resource loading.
- Phenomenon: Form data cannot be written to the database normally after deployment, and the backend returns a connection timeout error. Cause: The database permissions configured in `MONGODB_URI` are insufficient to perform write operations.
- Phenomenon: The update delay of landing page access logs exceeds expectations, and the backend displays a database connection exhaustion prompt. Cause: The value of `DB_MAX_LINK` is too high, causing the connection pool to fail to release idle connections in a timely manner.

## How to confirm the configuration is complete
- Access the landing page address corresponding to the configured `FE_DOMAIN`, verify front-end resources load normally, with no 404 or cross-domain errors.
- Submit a test form, verify corresponding records are generated in the bound database, confirming the data writing process is normal.
- Start the Redis service and use a connection tool for verification, confirm session caching is generated normally, verifying the `REDIS_URL` configuration is correct.
- View database connection logs, confirm the idle duration of the connection pool falls within the interval configured by `DB_MAX_LINK`, with no connection exhaustion situations.

The values provided are common starting points and should be measured against the reader's own samples.
