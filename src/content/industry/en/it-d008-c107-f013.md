# Operations on Duty and Internal Ticket Q&A for Account Ban and Appeal Review: Permission and Data Isolation

## What the data for this category looks like
This category of data typically includes four core document types: account ban records, appeal materials, review opinions, and user notifications. Data sources include risk control systems, audit records, user behavior logs, and report evidence. Update frequency is daily or real-time. Fields usually include account unique identifier, ban type, appeal status, associated evidence ID, disposal level, and others. There are no unified fixed units. Some fields require association with unique identifiers from external business systems. Typical user groups are platform governance, audit quality inspection, and customer service teams. Core workflows revolve around account-level punishment and review process circulation.

## Constraints Imposed on Permission and Data Isolation by This Category's Characteristics
The sensitive data nature of this category requires that permission and data isolation be tied to team and member dimensions. Real-time data from multiple sources requires synchronized permission update rhythm checks to prevent cross-team access to unauthorized appeal materials and report evidence. Disposal permissions for different audit teams must be clearly distinguished. This prevents unauthorized modification of other teams' review opinions or adjustment of disposal levels. Applications and knowledge bases from different teams cannot be associated. This avoids cross-team circulation of sensitive business data. Members must be restricted to accessing only their own team's ban and appeal data to ensure compliance of data usage.

## How to Set Configurations
All configurations below are based on FastGPT v4.17.0.

| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `teamId` | Bind to the unique identifier of the current business team, aligned with the team ID from the risk control system | Ensure consistency across system permission checks, prevent cross-team unauthorized access to ban data |
| `tmbId` | Bind to the team member ID of the current operating member, use the member identifier assigned by the platform | Prevent members from viewing sensitive appeal and ban data from other teams |
| Team permission scope | Restrict applications and knowledge bases within the same team to only associate with resources from the same team; cross-team association requires administrator approval | Match the team isolation requirements of this category of data, prevent applications from different teams from calling sensitive data |
| Member model usage permissions | Restrict members to only call model resources bound to their own team; the daily call limit per member is `1000 times` | Correspond to the permission management scenario for team members' model usage, clarify permission boundaries |
| Agent creation permissions | Only team administrators can configure global permissions for agents; regular members can only create agents for their own team | Match the management needs of platform governance teams, prevent unauthorized members from creating non-compliant agents |

## Three Common Misconfigurations
- Symptom: Clicking the team management page results in no response or failed redirection. Cause: `teamId` is not correctly aligned with the team ID of the current business system, leading to failed permission checks and inability to load the page.
- Symptom: Cross-team applications querying ban data from the knowledge base return no relevant content. Cause: Resources are not isolated by team dimension; cross-team applications and knowledge bases have no permission association configured, resulting in failure to return data normally.
- Symptom: Members cannot view appeal review records for their own team. Cause: `tmbId` is not bound to the current operating member; permission checks do not match the member's team, resulting in blocked data access.

## How to Verify Successful Configuration
- Log in to accounts from different teams, attempt to access the ban record page of another team, confirm that the corresponding data cannot be viewed.
- Configure association between applications and knowledge bases within the same team, attempt to call queries, confirm that returned results meet expectations.
- Enter the team management page, view member model usage statistics, confirm that only member call data from the own team is displayed.
- Attempt to create an agent as a regular member, confirm that only administrators can configure global permissions.
