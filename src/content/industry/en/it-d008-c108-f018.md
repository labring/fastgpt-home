# Operations On-Duty and Internal Work Order Q&A for Warranty Defect Response: Reranking and Hybrid Retrieval

## What this category of data looks like
This category of data comes primarily from customer-submitted warranty work orders, system operation logs, warranty clauses in project contracts, and software version update records. Core daily processing documents include warranty work orders, defect confirmation sheets, repair execution records, and customer confirmation sheets.
Data updates occur either daily or in real time with each new order. Each entry includes fields such as defect description, responsible party, repair status, and associated version. There are no unified fixed units, and field content is adjusted based on the specific details of each project.

## What Constraints Do These Characteristics Bring to Reranking and Hybrid Retrieval
Data for this category comes from scattered sources, including work order text, log snippets, clause text, and other formats. Hybrid retrieval must adapt to recall results of varying formats to avoid missing core information with a single matching logic.
Data updates happen per order or daily, so the retrieval pipeline must support near-real-time refreshing. This ensures the latest repair records and work order content can be recalled promptly.
Documents include strongly linked business fields such as responsible party and repair status. During reranking, priority must be given to matching content related to the current problem’s responsibility boundaries and repair solutions.
Additionally, there are no unified data units. This requires avoiding matching deviations caused by differences in field formats during retrieval, and filtering out irrelevant redundant contract clauses.

## Three Common Misconfigurations
- Symptom: A large number of irrelevant contract warranty clauses appear in hybrid retrieval results, and filtering performance is poor. Cause: No targeted similarity threshold is set for the document types in this category, leading low-match redundant content to be included in the recall range.
- Symptom: After enabling the reranking function, the number of returned results is always 0, and the interface displays the reranking status as not enabled. Cause: The reranking module is not correctly connected to the retrieval pipeline, or the configured reranking trigger conditions do not meet the current business scenario requirements.
- Symptom: Semantic retrieval mode returns results that better align with business needs than hybrid retrieval. Cause: The hybrid retrieval weight configuration is not adjusted for the multi-source data of this category, resulting in too low a matching weight for structured fields. This makes it impossible to effectively recall core information such as responsible party and repair status.

## How to Verify Correct Configuration
- View the initial recall results of the retrieval pipeline, confirm that core business documents such as warranty work orders and repair records are covered, and that no excessive irrelevant content is present.
- Check the configuration status of the reranking switch, confirm that the reranking function is enabled.
- Compare recall results across different search modes, adjust the similarity threshold and reranking priority to match the result sorting logic required by the business.
- Verify the context length of retrieval results, ensuring it meets the processing limits of the current workflow.
