# Operations Outsourced On-site Service: Operations On-duty and Internal Work Order Q&A: Deployment and Upgrade

## What the data for this category looks like
Data for this category primarily comes from customer ITSM systems, operations monitoring platforms, internal asset inventories, and on-duty records. Daily generated documents include on-site daily reports, service desk work orders, inspection reports, and SLA monthly reports. Document fields cover work order number, processing duration, inspection item status, SLA compliance rate, and other items. Operations staff typically update on-duty and work order records daily, and compile inspection and SLA data monthly. Data formats are usually a mix of structured tables and unstructured documents. Data volume changes dynamically with the scale of on-site services.

## Constraints imposed by these characteristics during deployment and upgrade
Data sources are scattered and involve the customer’s existing ITSM and monitoring platforms. During deployment, configure support for multi-source data access, and avoid conflicts with the customer’s existing system permission rules. Document structures are diverse and fields are inconsistent. During upgrade, support compatibility with different formats of on-site daily reports and work order data, and ensure data parsing logic can be adjusted flexibly. Differences in update frequencies require deployment to support flexible scheduled synchronization task configuration, to adapt to daily and monthly update rhythms. Additionally, on-site services involve customer-site deployment. The upgrade phase must support non-stop or low-downtime rolling updates, to avoid disrupting normal customer operations on-duty workflows. Simplify the configuration process to lower the operation threshold for on-site engineers.

| `ROOT_KEY` | Randomly generated 32-bit string | Used to configure interface call permissions for custom plugins, prevent unauthorized access |

## Three common configuration errors
- Phenomenon: Q&A results do not include the configured knowledge base content, only return generic responses. Cause: The vector model and knowledge base associated storage parameters are not configured correctly, resulting in failed document index generation.
- Phenomenon: After adding a custom plugin to the workflow, no input or output parameters are displayed, and no error logs are generated. Cause: The correct `ROOT_KEY` permission is not configured, resulting in insufficient plugin interface call permissions, and parameters cannot be loaded normally.
- Phenomenon: Continuous errors are returned when calling the embedding model. Cause: The self-built embedding model is not connected to the specified API channel, or the `STORAGE_S3_ENDPOINT` is not configured to adapt to the model’s storage path.

## How to verify successful configuration
- Access the intranet address corresponding to `FE_DOMAIN`, verify that the interface loads normally, with no resource loading failure or permission error prompts.
- Upload a standard-format on-site daily report document, verify that the document can be correctly parsed and indexed to the target knowledge base.
- Trigger a work order query workflow, verify that the custom plugin can load normally and display preset input and output parameters.
- Call the embedding model interface, verify that the returned result format meets expectations, with no connection timeout or permission exceptions.
