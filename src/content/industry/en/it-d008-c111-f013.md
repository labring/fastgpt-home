# Operations on-duty and internal ticket Q&A for configuration management and CMDB maintenance: Permission and data isolation

## What the data for this category looks like
This category of data mainly comes from enterprise CMDB systems, cloud resource inventories, automatic discovery tools and procurement ledgers. It includes four core documents: configuration item lists, service component dependency topologies, change records, and asset inventory tables. Data fields include configuration item unique identifiers, component dependency relationships, change times, asset owning departments, and more. The update frequency is daily or weekly. A single asset data entry contains basic attributes and association information for physical or virtual resources.

## What constraints these characteristics impose on permission and data isolation
This category of data covers assets and dependency relationships across multiple business departments. Different roles can only access configuration items within their respective scope of responsibility. Dependency topology data contains cross-component association information. Unauthorized access may expose undisclosed service links. Data is updated daily or weekly, so permission rules must be adjusted synchronously with asset changes. Data from multiple sources requires a unified permission verification entry to avoid inconsistent permissions across systems. Sensitive fields such as procurement ledgers must also be restricted to authorized administrators only.

## How to configure the settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| Team permission binding | Bind corresponding CMDB data groups by `teamId` | Match the asset scope managed by different operation and maintenance teams, prevent unauthorized cross-team access to configuration items |
| Role permission configuration | Assign the first 3 levels of operation permissions by `tmbId` | Differentiate access and editing permissions for roles such as administrators, on-duty engineers, and interns |
| Data isolation scope | Divide by asset owning department | Restrict different departments to only view their own department's configuration item lists and topologies |
| Sensitive field masking | Hide the procurement amount field in procurement ledgers | Prevent leakage of sensitive financial information, comply with operation and maintenance data permission requirements |
| Permission synchronization cycle | 2 AM daily (1-day cycle) | Match the daily data update frequency, ensure permission rules are synchronized with asset changes |
| Permission verification timeout | 600 seconds | Avoid page freezes caused by long verification delays, adapt to query delays of CMDB data |

## Three common configuration errors
- Scenario: A permission error prompt is returned in the interface when testing a call to a locally deployed model. Cause: The `teamId` of the current team was not added to the permission whitelist for model calls, resulting in interception of cross-team calls.
- Scenario: An intern account cannot access some knowledge base documents, but can view the full configuration item topology. Cause: Role permission scope was not configured by `tmbId`, only document access was restricted while viewing topology data was not limited.
- Scenario: Permission rules do not take effect synchronously after asset updates. Cause: The permission synchronization cycle was set to weekly, which did not match the daily data update frequency, leading to delayed permissions.

## How to confirm the configuration is complete
- Log in to the FastGPT v4.17.0 backend, enter the team management page, and verify whether the binding relationship between `teamId` and CMDB data groups is correct.
- Switch accounts with different roles, try to access configuration item lists and topologies within the corresponding scope of responsibility, and confirm that content without permission access is blocked.
- Manually trigger an asset update, check whether permission rules are updated within the set synchronization cycle.
- View the sensitive field masking configuration, confirm that sensitive data such as procurement ledgers has been correctly hidden.
