# Incident Management and Root Cause Analysis: Operations On-Call and Internal Ticket Q&A — Deployment and Upgrade

## What the data for this category looks like
Data sources for this category include incident timelines, system logs, monitoring metrics, and code commit records. These are maintained by SREs, technical leads, and quality teams. Daily produced documents include RCA reports, incident tickets, post-incident review minutes, and rectification tracking sheets. The core fields of the document structure are incident number, root cause type, and rectification measures. Data is updated after each major incident, or via regular monthly synchronization. The most time-consuming core steps are evidence collection, root cause hypothesis verification, and rectification item closure. Data volume fluctuates with incident frequency.

## What constraints these characteristics impose on the deployment and upgrade phase
Since data sources include structured logs and unstructured documents, storage and cache parameters compatible with multiple data types must be configured during deployment. Data update frequency is low, but single bulk import volume is large. Database connection pool limits must be adjusted to accommodate bulk tasks. Daily maintained documents are linked to full incident chain information. Storage services must be configured to persist attachments and historical records. During upgrades, association relationships of original configurations must be retained. This prevents historical RCA reports and ticket data from becoming unreadable due to configuration structure changes. FastGPT v4.17.0 version configuration requirements must be followed.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://username:password@host:port/fastgpt_prod` | Stores metadata for incident tickets, RCA reports, and associated incident timeline information |
| `REDIS_URL` | `redis://:your_redis_password@redis-host:6379/0` | Caches internal ticket sessions and intermediate calculation results of root cause analysis to reduce database access pressure |
| `DB_MAX_LINK` | `20–30 connections` | Adapts to monthly bulk import volumes of incident logs and code commit records, preventing connection limit exceedance |
| `STORAGE_S3_ENDPOINT` | `https://s3-cn-beijing.aliyuncs.com` (adjust based on actual service provider) | Persists unstructured data such as RCA report attachments and log fragments |
| `FE_DOMAIN` | `https://your-ops-platform-domain.com` | Configures jump links for internal tickets to ensure normal access to associated operations and maintenance pages |

## Three common mistakes
- Symptom: A 404 Not Found error occurs after Vercel automated deployment. Cause: The `FE_DOMAIN` parameter was not configured correctly, causing front-end static resource path matching to fail.
- Symptom: After upgrading to FastGPT v4.9.2 or later, `systemEnv` related configuration items documented in materials cannot be found in config.json. Cause: The configuration structure was adjusted during version iteration, and the configuration was not migrated to the new environment variable configuration file.
- Symptom: Root cause analysis functionality fails to start because MCP server related dependencies were not configured during deployment. Cause: Official documentation was not consulted, and the MCP server was mistakenly treated as a non-essential component.

## How to confirm configurations are correct
- Run a local deployment connectivity test script to verify that services configured via `MONGODB_URI` and `REDIS_URL` can establish normal connections.
- Upload a test RCA report attachment to confirm that the storage service configured via `STORAGE_S3_ENDPOINT` can normally write and read files.
- Submit a test internal ticket to check that the jump link configured via `FE_DOMAIN` points to the correct operations and maintenance on-call platform address.
- Check background running logs to confirm that no connection limit exceedance errors appear for the connection number configured via `DB_MAX_LINK`.

The values provided are common starting points and should be evaluated against the reader's own samples.
