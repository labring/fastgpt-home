# Operations on-call and internal ticket answering for integration and interface testing: knowledge base retrieval and recall

## What this category of data looks like
Data for this category comes from interface management platforms, test environment logs, databases and message queues. The update frequency is daily or when a version is released. Daily documents include structured interface test cases (with interface addresses, request parameters and expected return fields), joint debugging trouble tickets, environment documentation and test reports. Most documents contain fields such as interface identifiers, request headers, response status codes and link nodes. Some log data is unstructured text that must be parsed before being added to the knowledge base.

## What constraints do these characteristics impose on the knowledge base retrieval and recall process
The structuredness of interface test-related data varies widely. Unstructured logs and trouble tickets require more precise chunking strategies to avoid mixing unrelated link information during retrieval. Data updates occur frequently, so a synchronization mechanism adapted for high-frequency updates must be configured to prevent knowledge base content from lagging behind the current test environment state. Interface document fields are mostly precise technical terms, so retrieval must prioritize matching professional vocabulary, while controlling the context length of recall results to avoid exceeding model processing limits. Data formats from different sources differ significantly, so separate parsing rules must be configured for interface test cases and logs to ensure accurate field matching during retrieval.

## How to set the configurations
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale for this setting |
| ---- | ---- | ---- |
| `similarity` | `0.75–0.85` | Interface test-related content mostly uses professional technical terms. This similarity range balances recall precision and coverage, filtering low-relevance unrelated results |
| `limit` | `Top 8–12 results` | Interface test context usually includes multiple link nodes. An appropriate number of recall results covers complete problem scenarios and avoids missing key configurations and error messages |
| `searchMode` | `vector` | Most data in this category contains precise technical fields. Vector retrieval can match semantically similar interface parameters, link problems and error logs |
| `usingReRank` | `Enabled` | Semantic similarity between interface logs and trouble tickets is high. Reranking further filters redundant results and improves retrieval precision |
| `datasetSearchUsingExtensionQuery` | `Enabled` | Test questions often include abbreviations or variant terms. Query optimization expands the range of retrieved terms to match more relevant documents |
| `collectionIds` | `Specify knowledge base collection IDs related to interface testing and joint debugging` | Isolate knowledge base data from unrelated categories to avoid recalling irrelevant business documents or other test content |

## Three common misconfigurations
- Symptom: A large number of non-interface test related documents are included in retrieval results. Cause: `collectionIds` is not configured to limit the target knowledge base collection, resulting in recall of datasets from other categories.
- Symptom: Retrieval result ranking shows no obvious change after enabling `usingReRank`. Cause: The associated switch for the reranking function is not turned on in the platform interface, or the call quota for the reranking model is not configured.
- Symptom: Paragraph truncation occurs when the knowledge base parses long interface test cases. Cause: Misunderstanding of the maximum paragraph depth parameter for knowledge base parsing, failure to adjust parameters based on the nested structure of test cases, resulting in long paragraphs not being split correctly.

## How to confirm the configuration is correct
- Initiate a retrieval in the test environment, enter a typical interface test question, and check whether the recall results include documents within the specified knowledge base collection.
- Adjust the value of the `similarity` parameter, observe the change in the number of retrieval results, and confirm that the threshold takes effect.
- After enabling `usingReRank`, compare the ranking of retrieval results before and after enabling to confirm that the reranking function is operating normally.
- Trigger a knowledge base synchronization task, and check whether updated documents appear in retrieval results within the preset update cycle.

The values provided here are common starting points and should be measured against the reader's own samples.
