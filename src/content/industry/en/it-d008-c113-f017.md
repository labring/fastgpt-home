# Operations on-call and Internal Ticket Q&A for Integration and Interface Testing: Deployment and Upgrade

## What data for this category looks like
This category’s data comes from interface management platforms, test environment logs, databases, and message queues. Teams create daily documents including interface test cases, joint debugging issue tickets, environment descriptions, and test reports. These documents include fields such as interface addresses, request parameters, response status codes, test case identifiers, environment node information, and link call records. Data updates occur daily or with each version release, synchronized to test progress and version iterations. Logs and configuration data for different environments are stored independently per node.

## What constraints these characteristics impose on deployment and upgrade workflows
Data for this category is multi-source and updated alongside test progress and version iterations, creating multiple constraints for deployment and upgrade. First, data originates from interface management platforms, test logs, databases, and message queues. Connection parameters for each data source must be configured separately during deployment to avoid cross-environment data contamination. Second, data updates happen daily or with each version. Upgrade scripts must be compatible with the field structures of older versions of interface test cases and joint debugging issue tickets to avoid parsing errors. Additionally, daily documents include environment descriptions and node information. Deployment configurations must support identifier configuration for multi-environment nodes, to enable quick location of link nodes during operations on-call.

## How to set configurations
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 10–20 connections | Adapts to database connection requirements for concurrent interface calls in integration testing scenarios, preventing connection exhaustion |
| `REDIS_URL` | redis://:custom password@deployment server IP:6379/0 | Used to cache interface test cases and joint debugging issue tickets, reducing overhead from repeated database queries |
| `STORAGE_S3_ENDPOINT` | https://s3.custom region.amazonaws.com | Used to store category-specific data such as test logs and test reports, ensuring data persistence |
| `MONGODB_URI` | mongodb://username:custom password@deployment server IP:27017/fastgpt_test | Stores link logs and historical test results for interface tests, supporting data isolation per test environment |
| `FE_DOMAIN` | Public or internal domain name of the deployment server | Used to configure the frontend access address, ensuring normal interface access and calls during operations on-call |
| `ROOT_KEY` | Randomly generated 32-character string | Used to configure system administrator permissions, ensuring secure operational maintenance after deployment |

## Three common configuration mistakes
- Symptom: After uploading an interface test report or joint debugging issue ticket, the interface displays a request failure, and logs show a timeout error. Cause: File storage timeout duration was not configured to be long enough, causing interruptions during large model parsing of large test documents.
- Symptom: When calling the MCP service, the type field of interface parameters is forcibly set to string, preventing other parameter types from being passed. Cause: Parameter type validation rules for the MCP service were not configured correctly during deployment, causing all parameters to be uniformly converted to string format.
- Symptom: Link logs for integration tests cannot be stored to the database, making historical test link data unavailable during operations on-call. Cause: The configured `DB_MAX_LINK` value is too low, causing database connection exhaustion and preventing log data from being written.

## How to verify successful configuration
- Run the built-in database connectivity verification tool to validate the availability of configurations including `DB_MAX_LINK`, `MONGODB_URI`, and `REDIS_URL`, confirming that connection counts fit the business scenario.
- Upload a standard interface test document, check that the file can be uploaded normally and stored to the configured storage service, confirming that storage configurations are effective.
- Call the MCP service interface with preset test parameters, check that parameters are parsed correctly, confirming that there are no abnormal restrictions on parameter configurations.
- Access the configured `FE_DOMAIN` address, confirm that the frontend interface loads normally, and that functions related to operations on-call can be triggered normally.

The values provided are common starting points and should be measured against the reader's own samples.
