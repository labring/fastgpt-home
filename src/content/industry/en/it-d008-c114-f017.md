# Operations On-Duty and Internal Ticket Q&A for Requirements Analysis and PRD Management: Deployment and Upgrade

## What the data for this category looks like
The data for this category mainly comes from customer interview records, internal ticket systems, public competitor pages, and analytics dashboards. The update frequency is weekly or per release cycle. Daily processed documents include requirement research notes, PRD documents, user story lists, and requirement change forms. The core fields of document structure are business objectives, acceptance criteria, and change records. There are no uniform mandatory units. Field content is dynamically adjusted with requirement iterations.

## What constraints these characteristics impose on deployment and upgrade
This category has scattered data sources and a high update frequency. During deployment, multi-source document import configurations must be supported to ensure normal parsing of documents in different formats such as research notes and PRDs. There are no uniform mandatory fields for document structures. During the deployment phase, custom field mapping rules must be supported to adapt to document formats used by different teams. Since requirement changes directly affect business implementation, data backup and rapid rollback strategies must be configured during the upgrade phase. This prevents loss of historical documents or parsing errors caused by version updates. At the same time, permission control for multi-source data must adapt to the access levels of different documents. Permission configuration logic must be planned in advance during deployment.

## Configuration settings
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://username:password@host:port/dbname?authSource=admin` | Adapts to multi-source document storage requirements, ensures persistent access to data such as PRDs and change forms |
| `REDIS_URL` | `redis://:password@host:port/0` | Used to cache frequently accessed requirement document metadata, reduces database query pressure |
| `ROOT_KEY` | Custom key based on team permission rules | Controls platform super administrator permissions, limits the scope of core configuration modifications |
| `FILE_TOKEN_KEY` | Random 32-character string | Encrypts tokens for document upload and download, prevents unauthorized access to requirement documents |
| `STORAGE_S3_ENDPOINT` | Fill in according to internal object storage service address | Adapts to storage requirements for large PRD attachments, improves scalability compared to local storage |

## Three common mistakes
- Issue: After upgrading to FastGPT v4.17.0, the reference function returns content regardless of the switch state. Cause: After the version update, the default configuration of the reference logic is not bound to the interface switch, resulting in incorrect parameter synchronization.
- Issue: In older Docker-deployed applications, the tool call judgment logic has exceptions, and some models cannot trigger preset tools. Cause: The `REDIS_URL` parameter was not configured correctly during deployment, causing the tool call status cache to fail.
- Issue: When deploying and configuring models locally, startup fails due to empty required fields. Cause: The `MONGODB_URI` and `REDIS_URL` parameters were not filled out as required in the documentation, and core storage configurations were omitted.

## How to verify successful configuration
- Log in to the platform backend, check the connection status of the `MONGODB_URI` and `REDIS_URL` parameters, confirm that the storage services can be accessed normally.
- Upload a test PRD document, verify that the document parsing and metadata storage processes complete successfully.
- Trigger an internal ticket Q&A test, confirm that the tool call logic triggers according to the configured rules.
- View platform logs, confirm there are no error messages for core configuration items, verify that the permission key `ROOT_KEY` configuration takes effect.
