# Operations Duty and Internal Work Order Q&A for Project Implementation Plan Management: Permission and Data Isolation

## What this category of data looks like
Core data for project implementation plan management originates from contracts, work breakdown structures (WBS), client schedules, and project management systems. Data updates occur weekly or upon completion of individual milestone nodes. Daily generated documents include project plans, milestone lists, weekly reports, and risk issue lists. Data fields include task identifiers, responsible persons, node deadlines, budget amounts, and risk levels. Data only circulates within the associated project cycle, with no mandatory additional statistical standards.

## What constraints do these characteristics impose on permission and data isolation
Data sources are spread across multiple systems, so permission configurations must adapt to permission verification rules for multi-source data. Update frequency is not real-time, so permission configurations do not need frequent adjustments, but full verification is required before milestone nodes. Document types vary, with different permission scopes for each type. For example, risk issue lists are only accessible to core project members. The responsible person field is clearly defined, so fine-grained permission control based on responsible persons is needed to prevent cross-project data leaks.

## How to configure settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `teamId` | Bind a unique identifier per individual project | Matches the project-based isolation requirement of project implementation plan management, ensuring project members only access data for their assigned projects |
| `tmbId` | Bind and configure separately by document type, such as project plans and risk lists | Enables fine-grained permission control for different document categories, aligning with the document tiering characteristics of this category |
| Query range limit | Calibrate the first 5 project-related data entries based on actual testing | Adapts to the quick query needs of operations duty scenarios, avoiding returning excessive cross-project data |
| Permission verification cycle | 7 days | Matches the weekly data update rhythm, ensuring permissions for expired data automatically expire |
| External access control | Only allow IP segments of project management systems and work order systems | Aligns with the scope of data source systems, preventing unauthorized external access |

## Three common configuration errors
- Phenomenon: SQL permission errors appear after restarting the Docker container, and the interface returns "No permission to access data". Cause: The IP segment of the project management system was not added to the whitelist, and the container network configuration was reset after restart, causing the original permission rules to fail.
- Phenomenon: Cross-project members can view risk issue lists for non-associated projects. Cause: `teamId` was not bound per project dimension, and permission groups were only divided by department without linking to specific projects.
- Phenomenon: A large number of irrelevant historical data is returned when querying work orders. Cause: No query range limit was set, and permission verification did not filter data from non-current projects.

## How to confirm the configuration is correct
- Log in with an account that is not a project member, attempt to access documents for the target project, and confirm that viewing is not possible or a no permission prompt is returned.
- Restart the Docker container, then initiate a work order query again, and confirm that no permission errors appear.
- Switch to a member account for a different project, and confirm that only plans, weekly reports, and other documents for the corresponding project can be viewed.
- Check system logs, and confirm that only data query requests are initiated from the IP segments of the project management system and work order systems.
