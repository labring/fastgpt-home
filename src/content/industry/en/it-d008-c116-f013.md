# Operations on Duty and Internal Ticket Q&A for Project Document Handover and Archiving: Permission and Data Isolation

## What the data for this category looks like
This category of data primarily comes from project document libraries, configuration lists, meeting minutes, and test reports. Daily coverage includes completion documents, configuration manuals, training records, and acceptance certificates. Data updates occur at the end of each project phase or when a single project is completed. Each individual document includes fields such as project number, archiving batch number, version number, and signature status. The basic statistical unit is copy. Documents from different projects are categorized by their delivered clients, while different versions of documents for the same project are archived in chronological order.

## What constraints do these characteristics impose on permission and data isolation?
Data in this category is categorized by project and delivered client, and usage needs vary across different roles. Therefore, permission isolation must match both the ownership dimension and role permissions. Data updates happen in phases or when a project is completed, so permission configurations must be adjusted synchronously with archiving batches and version iterations to avoid failing to update permissions for older document versions. Each individual document includes sensitive fields such as signature and version number, so viewing and export operations by unauthorized roles must be restricted. Additionally, documents associated with internal tickets must be strictly bound to the permission scope of their corresponding project to prevent cross-project data leaks.

## How to configure settings
The following configurations are adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `teamId` | Assign a dedicated `teamId` for each archiving project, with a value range of 1000–9999 | Divide data ownership by project to prevent cross-project data leaks |
| `tmbId` | Assign dedicated `tmbId` permission groups for project managers, implementation consultants, and customer archive administrators | Match the document access permission needs of different roles |
| Document access filtering rules | Only display documents bound to the current `teamId`, with retrieval scope limited to the current archiving batch | Match the data characteristics of this category, which are categorized by project |
| Version isolation configuration | Only allow viewing documents from the current archiving batch, retain access permissions for the most recent 3 versions | Match the update rhythm of data iterated by version |
| Ticket association permission | Bind internal tickets to the `teamId` of their corresponding project, set the timeout period to 300 seconds | Ensure ticket handlers can only access documents from bound projects |

## Three common configuration errors
- Phenomenon: A 403 status code is returned when an internal ticket associates a document, or an error message stating "no permission to access the document" is displayed. Cause: The `teamId` of the project to which the ticket belongs is not bound to the accessing account, resulting in permission verification failure.
- Phenomenon: Archived documents from older versions can still be accessed by unauthorized roles. Cause: The `teamId` permission scope is not adjusted synchronously with data updates, and the permission configuration for older batch documents is not updated.
- Phenomenon: Documents from cross-projects are incorrectly displayed on the ticket interface of the current project. Cause: The document library's retrieval results are not filtered by `teamId`, leading to cross-project data leaks.

## How to confirm the configuration is correct
- Log in to the system with an implementation consultant account, attempt to access archived documents from non-managed projects, and confirm that viewing is not possible or a no permission prompt is displayed.
- Submit an internal ticket, associate it with the `teamId` of a test project, and confirm that the ticket interface only displays data such as completion documents and configuration manuals for that project.
- Modify the `teamId` of an archiving batch, verify whether the access permissions for the older batch documents are updated synchronously, and confirm that unauthorized roles cannot access them.
- Check the role permission group configuration, confirm that the `tmbId` permission scopes for project managers, implementation consultants, and customer archive administrators match their respective job responsibilities.
