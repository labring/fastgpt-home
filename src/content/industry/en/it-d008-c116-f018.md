# Operations On-Duty and Internal Work Order Question Answering for Project Document Handover Archiving: Reranking and Hybrid Retrieval

## What the data for this category looks like
Project document handover archive data typically originates from project document libraries, configuration lists, meeting minutes, and test reports. Updates are triggered at the end of a project phase or upon full delivery completion. Daily archived documents include completion documents, configuration manuals, training records, and acceptance certificates. Most fields include identifying information such as project number, document version, signature status, and delivery date. Individual document length varies widely. Some completion documents may contain multiple pages of structured charts and written explanations.

## What constraints do these characteristics impose on reranking and hybrid retrieval
Archived data has a low update frequency but a large number of associated documents per project. Reranking and hybrid retrieval must first filter out expired version documents to avoid retrieving invalid archived materials. Operations on-duty work orders are typically associated with specific projects. Retrieval must match both the project number and problem description in the work order, as well as the structured fields and full text content of documents. This requires cross-data source associated retrieval. Archived documents have high field complexity. The reranking link must prioritize matching document types directly related to work order issues, such as configuration manuals and acceptance certificates, to improve the targeting of retrieval results.

## How to configure it
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `usingReRank` | Enabled | Project documents contain multiple types of archived materials. Reranking filters content unrelated to operations work orders, improving result relevance |
| `similarity` | 0.72–0.85 | Must distinguish between different versions of documents under the same project. A threshold that is too low will retrieve expired versions, while a threshold that is too high will miss matching items |
| `limit` | Top 8–12 entries | Operations on-duty work orders usually focus on specific documents for a single project. Too many results increase the context processing burden |
| `searchMode` | Hybrid retrieval | Must match both the project number and problem description in the work order, as well as the structured fields and full text content of documents |

## Three common mistakes
- Phenomenon: An incompatible model error is returned when calling the reranking model, or no reranking results are returned after retrieval. This occurs when using models such as gte-rerank-v2 or Qwen3-Reranker-8B. Cause: The interface format of the reranking model supported by FastGPT is not used, or the custom request address does not point to the correct model service port.
- Phenomenon: Reranking results always return false, with no valid sorted output. Cause: The reranking function is not enabled correctly, or the input format of the reranking model does not meet requirements, and the correct query and document fragments are not passed.
- Phenomenon: Hybrid retrieval only retrieves documents from a single data source, and does not associate project document libraries with work order data. Cause: Cross-data source retrieval association rules are not configured, and the project number in the work order is not bound to the project field of the document library.

## How to confirm the configuration is complete
- Navigate to the knowledge base configuration page for FastGPT v4.17.0, check if the reranking function is enabled, and confirm that the `usingReRank` parameter is set to Enabled.

- View the service logs of the reranking model, confirm that FastGPT has successfully sent a reranking request, and that non-empty sorted results are returned.
- Adjust the similarity threshold, observe changes in the number of retrieved results, and confirm that the threshold configuration takes effect.
