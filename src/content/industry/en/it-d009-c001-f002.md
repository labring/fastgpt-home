# Requirements and Design Document Drafting for CDN and Edge Acceleration Configuration: Context and Token

## What Data Looks Like for This Category
Core data for CDN and edge acceleration configuration is sourced from CDN consoles, DNS resolution records, user access logs, and monitoring alert systems. Regularly produced documents include domain access forms, cache rule configuration tables, refresh and preheating operation records, and fault analysis reports.
Data updates occur daily or in real time when configurations are changed. Fields include domain name, cache policy type, refresh and preheating volume, edge node status, alert threshold, and more. Single document lengths vary widely.

## Constraints Imposed on Context and Token by These Characteristics
The high-frequency update nature of CDN data means contexts cannot include expired configurations or fault records. Doing so will mislead decisions for requirements and design document drafting.
The wide variation in single document lengths causes significant fluctuations in token consumption. Without a reference upper limit, a single request may carry an excessive number of tokens.
Document fields focus on specific content such as domain names and cache rules. Precise recall of relevant entries is required to avoid irrelevant data occupying token quotas, which protects drafting efficiency and accuracy.

## How to Set Configurations
| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `maxContext` | 1–3 days of business data volume | Matches the daily or change-level update frequency of CDN configurations, ensuring contexts include the latest domain access and cache rule data |
| `quoteMaxToken` | 8000–12000 tokens | Adapts to the average length of single CDN documents, avoids truncating key configuration parameters, and controls token consumption for a single request |
| Single recall count | Top 3–5 entries | Focuses on core domain access, cache rules, and fault records, reducing invalid token consumption |
| Context refresh interval | Every 24 hours | Aligns with the daily update frequency of CDN monitoring alerts, ensuring contexts always include the latest edge node status data |

## Three Common Misconfigurations
- Setting `quoteMaxToken` to 50000 tokens causes each request to carry an excessive number of tokens. This leads to large language model response delays or timeouts. The root cause is failing to set a reasonable threshold based on the actual length of single CDN documents, and blindly increasing the reference upper limit.
- Failing to pass the global variable token to the MCP tool in the workflow. The root cause is not enabling the global variable pass-through function in the context configuration, or not correctly binding the token parameter to the corresponding call node.
- Expired cache rules or invalid domain name data being mixed into the knowledge base recalled context. The root cause is not adjusting the context refresh cycle based on the update frequency of CDN configurations, resulting in contexts containing old data.

## How to Confirm Configurations Are Correctly Applied
- Check the large language model call logs in FastGPT v4.17.0. Confirm that the number of tokens carried in a single request does not exceed the preset threshold of `quoteMaxToken`.
- Manually modify one CDN cache rule. Retrieve the knowledge base and verify that the latest rule content can be recalled. This confirms the context refresh logic is effective.
- Check the MCP tool parameter bindings in the workflow. Confirm that the global variable token has been correctly passed to the tool call node, with no missing parameters.
- Cross-check the recalled knowledge base entries. Confirm that only configuration data related to the current target domain name or node is included, with no irrelevant entries mixed in.
