# Requirements and Design Document Drafting for IT Service Desk Ticket Processing: Context and Token

## What the data for this category looks like
The data for this category comes from enterprise ITSM systems, phone or online chat logs, asset systems, and internal knowledge bases. Daily generated documents include service request tickets, incident tickets, processing records, and user satisfaction forms. Data updates occur daily or in real time. Fields include ticket numbers, problem categories, processing progress, user feedback, and more. Only natively recorded business fields and associated identifiers are retained. No additional custom statistical values are included.

## What constraints these characteristics impose on context and token handling
Real-time ticket updates require context to synchronize and fetch the latest processing records. This prevents reliance on outdated information. Data structures vary widely across multiple sources. Unified field mapping rules for context are required to avoid wasted token consumption. Service request tickets and processing records have many associated fields. Context recall must accurately match associated IDs. This prevents irrelevant content from consuming quota. Knowledge bases update on a daily cycle. Regular synchronization of troubleshooting documents referenced by context is needed. This prevents calls to outdated content. Single ticket lengths vary significantly. `maxContext` and `quoteMaxToken` must be used to limit total token proportion. This avoids exceeding the model's single-round call limit.

## How to Configure the Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `maxContext` | First 8–12 entries | Matches the number of historical processing records for IT service desk tickets. Balances context completeness and token consumption |
| `quoteMaxToken` | 1800–2200 token | Adapts to typical lengths of service request tickets and processing records. Avoids single content exceeding model limits |
| Context synchronization frequency | Real time | Matches the daily or real-time update requirements of ticket data. Ensures calls use the latest processing records |
| Association matching accuracy | 85% | Accurately matches ticket numbers and associated IDs of processing records. Reduces irrelevant recall content |
| Redundant content filtering | Enabled | Excludes unrelated historical ticket records. Reduces invalid token usage |

## Three Common Misconfigurations
- Phenomenon: An insufficient quota error is returned during calls. This does not match the used quota shown in oneapi. Cause: Token statistics rules are not configured correctly. The calculation logic for input and output tokens does not match oneapi's billing rules.
- Phenomenon: The number of context entries is set to 0 in the workflow, but historical ticket content is still passed to the API. Cause: The system default context recall switch is not turned off. Or the associated knowledge base automatically synchronizes historical processing records.
- Phenomenon: The interface cannot separately display the input token count and output token count of AI conversations. Cause: The conversation token statistics configuration item is not enabled. Or the used FastGPT version is lower than v4.17.0.

## How to Verify the Configuration is Correctly Set
- View the context preview panel in the workflow. Confirm that the content passed to the API matches the configured number of context entries.
- Run a test ticket processing workflow. Check that the input and output token counts displayed on the interface match the actual calculated results.
- Review the oneapi billing logs. Confirm that token consumption aligns with the statistics results from FastGPT.
- Verify that when the number of context entries is set to 0, no redundant historical ticket content is included in the API request.

The values provided here are common starting points. They should be evaluated against the reader's own samples.
