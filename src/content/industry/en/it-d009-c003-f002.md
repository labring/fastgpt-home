# Drafting Requirements and Design Documents for IT Asset Inventory: Context and Token

## What Data for This Category Looks Like
IT asset inventory data originates from asset management systems, procurement systems, financial fixed asset modules, and terminal management platforms. Four standard document types are regularly produced: asset ledgers, inventory sheets, loan and return forms, and scrap applications. Document fields include asset number, name, user, storage location, ownership status, and additional relevant fields. Update frequencies are typically monthly, quarterly, or annually. Data processing responsibilities fall to IT asset administrators, financial asset staff, and desktop support teams, with a core focus on asset ownership, location, and user information.

## What Constraints Do These Characteristics Impose on Context and Token Configuration
The multi-source heterogeneous data sources, fixed update cycles, and strongly associated field traits of IT asset inventory data create clear constraints for context and token configuration.
Asset data updated monthly or quarterly does not need frequent context refreshes, but a single call must cover multiple documents such as ledgers and inventory sheets from the full inventory cycle, which can lead to excessive token consumption.
Strongly associated fields including asset number, user, and storage location require the context to retain relationships between fields. If complete field groups are not retained during segmented processing, context association breaks will occur.
Differences in field formats across documents from various sources will increase redundant token calculations. Field structures must be aligned in advance to optimize token usage efficiency.

## How to Set Configuration Parameters
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum Context Token Count | 8000–12000 token | Covers core fields of multiple documents including ledgers, loan forms, and scrap applications within a single inventory cycle, preventing insufficient tokens from truncating critical associated information |
| Context Chunk Length | 1000–1500 characters | Matches the total number of fields in a single asset document record, ensuring each chunk contains a complete set of asset information and avoiding field association breaks |
| Context Overlap Length | 100–200 characters | Retains key fields such as asset number and user between adjacent chunks, resolving issues where context cannot be linked after segmentation |
| `quoteMaxToken` | 500–800 token | Limits the maximum token count for a single quoted segment, preventing a single quote from using excessive context space |
| `maxContext` | Calibrated based on actual total document volume | Adapts to the scale of asset data updated monthly or quarterly, ensuring a single call can load the full set of inventory-related documents |

## Three Common Misconfigurations
- Phenomenon: System errors indicating token limit exceeded occur during calls, or returned results are truncated. Cause: The context token configuration is not adjusted based on the total volume of asset documents updated monthly or quarterly, and the set value is lower than the total token consumption of all associated documents within a single inventory cycle.
- Phenomenon: In asset information matching results, asset numbers cannot be paired with users or storage locations. Cause: The context chunk length is set too small, or the overlap length is insufficient, resulting in adjacent chunks not retaining complete asset associated field groups.
- Phenomenon: When multiple knowledge bases are called jointly, only asset records matching the current question are matched, and historical loan and scrap records are not associated, leading classification results to default to fallback categories. Cause: The historical context loading configuration is not enabled, and historical inventory documents are not included in the context scope of the current call.

## How to Verify Correct Configuration
- Upload a single asset ledger document, trigger a context call, and verify that the returned result includes complete asset number, user, and storage location fields.
- Upload multiple associated documents such as a ledger plus a loan and return form, and verify that the context call can cover the core information of all uploaded documents.
- Adjust the context chunk and overlap length parameters, test field association integrity under different configurations, and confirm that no field breaks occur.
- Use the system log viewing function of FastGPT v4.17.0 to check the token consumption of a single call, ensuring it does not exceed the preset upper limit.
