# Drafting Requirements and Design Documents for Issue Triage and Response: Document Parsing and Chunking

## What data looks like for this category
This category of data mainly comes from GitHub or Gitee issue tickets, code repository version logs, user-reported environment information and problem reproduction instructions. Daily processed documents include issue templates, tag rules, and historical reply records. The data update frequency is mostly daily or weekly. Core processing steps focus on problem classification, completion of reproduction information, and responsibility module tagging. Improper handling can lead to ticket backlogs, user churn, or delayed defect localization.

## Constraints Imposed by These Characteristics on the Document Parsing and Chunking Link
This category of data has diverse formats. It includes both structured issue ticket fields and unstructured problem reproduction instruction documents. This requires the parsing link to support multi-format input. The data update frequency is relatively high, so the parsing process must support incremental synchronization or scheduled refreshing to avoid processing outdated data. Core processing steps rely on accurate field extraction, such as issue tags and priority fields. When chunking, key metadata must be retained to ensure the accuracy of subsequent triage. At the same time, the stability of parsing and chunking directly affects operational efficiency. Parsing failures for large-volume documents will directly lead to ticket backlogs, so fault tolerance of the parsing link must be prioritized.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | Adapt to the upload requirements of hundreds-of-page PDF documents, avoid being blocked due to exceeding the file size limit |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600–900 seconds | Address the parsing time consumption of large-volume documents, prevent interruptions to the complete parsing process due to timeouts |
| `customPdfParse` | Enabled | Adapt to custom parsing rules for PDF documents related to issues, such as reproduction instructions and version logs, retain key metadata |
| `chunkSize` | 800–1200 characters | Balance information completeness and retrieval accuracy, adapt to the mixed scenario of short texts and long documents in issue tickets |
| `chunkSplitter` | Split by paragraph + title | Retain the hierarchical structure of issues, facilitate subsequent responsibility module tagging and priority triage |
| `chunkSettingMode` | Manual configuration | Adjust chunking rules for the specific document formats of this category, adapt to issue-related data from different sources |

## Three Common Misconfigurations
- Phenomenon: An error is triggered when calling the PDF parsing tool to process hundreds-of-page documents, while small-volume documents can be parsed normally. Cause: The `PARSE_FILE_TIMEOUT_SECONDS` parameter was not adjusted, and the parsing time of large files exceeded the default threshold, causing an interruption.
- Phenomenon: After the locally deployed document parsing component is started, a "Cannot read properties of undefined" error appears on the calling page. Cause: The component version does not match the compatibility requirements of FastGPT v4.17.0, and inconsistent dependency library versions cause runtime errors.
- Phenomenon: The retrieval results after chunking contain a large amount of duplicate content, or the number of recalled files does not meet expectations. Cause: The chunking parameters were not adjusted according to the reuse scenario of issue documents, or correct field matching rules were not configured.

## How to Verify Successful Configuration
- Upload a single test PDF document with 1000 pages, check whether the parsing progress is completed within the time set by the `PARSE_FILE_TIMEOUT_SECONDS` parameter, with no timeout errors.
- View the chunked document fragments, confirm that the title and paragraph structure are retained, and there is no obvious content truncation or repeated splicing.
- Simulate an issue ticket retrieval request, check whether the number of recalled files matches the preset rules.
- Check whether the uploaded file size complies with the limit set by the `UPLOAD_FILE_MAX_SIZE` parameter, with no file blocked prompts.

The values provided here are common starting points, and should be evaluated against the user's own samples.
