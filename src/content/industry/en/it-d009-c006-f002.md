# Drafting Requirements and Design Documents for Pull Request Reviews: Context and Token

## What the data for this use case looks like
This use case's data primarily comes from code repositories, CI pipelines, Issue links, and contributor submissions. Update frequencies are typically daily or weekly. Daily associated documents include PR descriptions, code review comments, CI results, and merge records. Involved parties include project maintainers, module owners, and contributors. Data fields include change scope, test pass status, associated Issue numbers, submitter information, and more. There is no unified fixed format, and it adjusts based on project collaboration rules.

## How these characteristics impose constraints on the context and token workflow
The scattered data sources require that context aggregation must cover multiple types of content including code changes, review comments, and CI results. This avoids missing key decision-making information. The daily or weekly update frequency means context synchronization does not need high-frequency triggering. Refresh cycles can be configured according to project iteration cycles, reducing redundant resource consumption. The inconsistent document structure requires chunk processing to adapt to text in different formats such as PR descriptions and review records. This prevents chunk breaks from disrupting content coherence. The diverse fields require context recall to prioritize matching core fields such as change intent and test status. This reduces irrelevant content occupying token quotas and improves context accuracy.

## How to configure the settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the total length of multi-source documents related to PR reviews, avoiding exceeding the model context limit |
| `quoteMaxToken` | 1500–2000 token | Limits the token usage of a single recalled entry, balancing the number of recalled entries and the information density of individual entries |
| Context synchronization cycle | 2:00 AM daily | Matches the daily update iteration rhythm of most projects, reducing unnecessary resource consumption |
| Recalled content priority | PR descriptions first, then review comments, then CI results | Aligns with the core decision-making logic of PR reviews, prioritizing recall of content related to change intent |
| Single recall upper limit | Top 8 entries | Controls total token consumption, avoiding context overload that affects model response efficiency |

## Three common misconfigurations
- An error with the message "context token exceeds model limit" appears, and logs show the total length of recalled content exceeds the configured value. This is caused by failing to correctly set the `maxContext` parameter, or failing to limit the token quota for single recalled entries.
- Search results cannot combine PR historical context, and returned content is unrelated to the current change intent. This is caused by failing to include core data such as PR descriptions and review records in the context recall scope, only using isolated search queries.
- After private deployment, the access path cannot match the preset context, causing the application to fail to load normally. This is caused by failing to correctly configure the application access context path in the deployment configuration, or failing to synchronously update reverse proxy rules.
