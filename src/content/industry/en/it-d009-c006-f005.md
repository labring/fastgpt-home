# Pull Request Review Requirement and Design Document Drafting: Multi-turn Dialogue and Prompt Engineering

## What this use case’s data looks like
This type of data typically comes from code repositories, CI pipelines, Issue links, and content submitted by contributors. Daily produced documents include PR descriptions, code review comments, CI results, and merge records. Data update frequency is mostly daily or weekly. Core fields include changed code snippets, review comment entries, CI pass rate, merge status, and more. The most time-consuming steps in the processing workflow are change intent confirmation, test result review, and merge conflict resolution. Errors may lead to regression defects, unstable main branches, or negatively impact contributor experience. Unlike the Issue triage use case, this use case focuses on mergable code change processing.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
Because data sources are scattered and include multiple types of content such as code snippets and review comments, multi-turn dialogue must support context integration across sources. Prompts must explicitly specify fields that need to be associated with code repositories, CI results, and Issue links. Data update frequency is mostly daily or weekly, so prompts and dialogue contexts must adapt to this rhythm to avoid introducing outdated data. The structured level of daily documents is limited, so multi-turn dialogue must guide the stepwise supplementation of key information such as change intent and test results to reduce manual repetitive operations in time-consuming steps. At the same time, since errors may affect main branch stability, prompts must include verification logic to ensure coverage of core steps such as merge conflict checks. Additionally, content submitted by contributors has diverse formats, so multi-turn dialogue must support standardized conversion of unstructured content to reduce subsequent review comprehension costs.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Maximum context length | 8000–12000 characters | Adapts to the total length of multi-source content such as PR descriptions, review comments, and CI results, preventing truncation of critical change information |
| Maximum conversation turns per session | First 8 turns | Covers the full review workflow including change intent confirmation, test result review, and merge conflict resolution |
| Context refresh frequency | Daily update | Matches the daily data update rhythm, ensuring that CI results and merge records used in dialogues are up to date |
| Prompt bound fields | Bind PR description, code review comment, and CI result fields | Extract core business fields from data sources to ensure multi-turn dialogue focuses on review-related content |
| Conversation ID association rule | Bind the unique identifier of the PR in the code repository | Associate full-process dialogue logs for a single PR to avoid cross-PR data confusion |
| FastGPT v4.17.0 | Enable context caching feature of this version | Optimizes context loading efficiency for multi-turn dialogue to meet the long context requirements of PR reviews |

## Three Common Misconfigurations
- Symptom: Running data in dialogue logs is empty after invoking the workflow. Cause: The dialogue identifier corresponding to the PR is not bound, or the context configuration is not associated with the PR identifier of the code repository, resulting in dialogue data not being correctly mounted to the corresponding PR workflow.
- Symptom: When passing arbitrary code block parameters to the prompt in the text content extraction module, the extraction result shows undefined. Cause: The prompt variable is not correctly bound to the code snippet field of the PR in the code repository, or the parameter passing does not match the content format of the corresponding data source.
- Symptom: Associated review logs disappear synchronously after a user deletes a dialogue. Cause: Dialogue logs and PR data are not stored with independent association; deleting the dialogue triggers cascading deletion of associated data, resulting in loss of review-related CI results and merge records.

## How to Verify Correct Configuration
- A simulated PR review dialogue is initiated, and the dialogue context is checked for preset bound fields such as PR descriptions and CI results.
- Dialogue logs are viewed to confirm that each dialogue is associated with the unique identifier of the corresponding PR, and no cross-PR data confusion occurs.
- The workflow is triggered, and running data is checked to confirm it is normally populated with no null or undefined fields.
- The dialogue deletion operation is tested, and review-related log data is confirmed to not be deleted synchronously.

The values provided are common starting points and should be evaluated against the reader’s own samples.
