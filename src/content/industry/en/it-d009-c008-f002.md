# Requirements and Design Document Drafting for Special Event Operations: Context and Token

## What data for this category looks like
Data for this category comes from several sources: scheduling data from event backends, event copy assets from content libraries, event exposure data from traffic platforms, and user event participation records. Daily deliverables include overall event plans, resource slot scheduling tables, event page promotional copy, and post-event review reports.
Data updates follow a weekly baseline schedule. Temporary changes to update frequency occur around major holidays.
Document structures typically include fields such as event objectives, execution milestones, resource allocation, and effect projections. No unified mandatory format exists. Adjustments to structure align with event scale.

## Constraints imposed on context and token workflows
Event-related documents have clear cycle-based attributes. Copy and scheduling data from pre-event phases must be integrated quickly. Context windows must cover all associated assets across the full event cycle to avoid interference from cross-cycle data.
Event copy lengths vary widely, ranging from short titles to lengthy post-event review reports. Token allocation must fit the length ranges of different document types.
Resource slot scheduling involves associated data coordinated across multiple teams. Context recall must prioritize matching resource information within the same event cycle to prevent confusion with cross-event resources.
Event data update frequencies fluctuate significantly. Context refresh mechanisms must adapt to temporarily adjusted traffic data to avoid using outdated event effect data.

## How to set configurations
The following configuration items can be adjusted directly in the application editing page for FastGPT v4.17.0:

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 4000-6000 token | Covers core plans, copy, and scheduling data for a single event, and fits the total length range of event documents |
| `quoteMaxToken` | 3000-5000 token | Fits the token requirements of event review reports and long-form copy assets, and prevents long documents from being truncated |
| Single search limit | Top 8-12 associated documents | Event documents are grouped by event cycle. Limiting recall volume prevents token overflow |
| Similarity threshold | 0.75-0.85 | Distinguishes event-related data within the same cycle from unrelated content, and prevents recall of redundant information |
| Reranking rule | Sort by event cycle | Prioritizes recalling data for currently active or upcoming events, which aligns with operational usage logic |

## Three common configuration mistakes
- Phenomenon: Context fails to send correctly to the large model when `quoteMaxToken` or the single search limit is set too high. Cause: The total token count of event documents exceeds the context capacity limit of the large model, leading the system to truncate or discard associated data.
- Phenomenon: External network request errors occur when calling an offline-deployed vector model. Logs show attempts to access cl100k.tiktoken. Cause: Local tokenizer dependencies are not configured correctly, and locally cached token rule files are not used.
- Phenomenon: Event copy generation or context recall experiences lag when configured concurrency and token processing rates exceed hardware capacity. Cause: Hardware resource allocation is not adjusted to match real-time event operation data volumes, leading to backlogs in the token processing queue.

## How to verify correct configuration
- Upload a complete event plan document, and check if the context preview includes associated data such as scheduling and copy from the same event cycle.
- Adjust the `maxContext` or `quoteMaxToken` parameters to different ranges, and test if recall and splicing of long documents work correctly with no obvious truncation.
- Simulate high-concurrency event data queries, and check if context recall speed and token processing meet expected standards.
- Review system logs to confirm there are no external network request errors related to tokenizers.

The values listed above are common starting points. They should be evaluated against the reader's own samples.
