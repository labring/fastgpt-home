# Drafting Requirements and Design Documents for Personal Information Protection Compliance: Multi-turn Dialogue and Prompt Words

## Data Profile for This Category
Data in this category comes primarily from business systems, App permission lists, privacy policies, and user request records. Update frequency follows quarterly cycles or each product change.
Daily produced documents include personal information inventories, processing rules, impact assessment reports, and user authorization texts. These documents are structured around the full processing workflow for information that can identify natural persons.
Core fields include information collection scope, processing purpose, legal basis, authorized retention period, and similar items. No unified fixed units exist. Values must be adjusted based on the specific document scenario.
Service targets include privacy compliance teams, security consulting agencies, and legal departments. Core work includes scenario sorting, legal basis confirmation, and collation of assessment materials.
This page is written for FastGPT v4.17.0.

## Constraints for Multi-turn Dialogue and Prompt Words
Data sources for this category are scattered and update dynamically with product changes. Multi-turn dialogue must link multi-source data such as business systems and App permission lists. Context scope must be limited to filter redundant information. Content generated beyond compliance document scope must be avoided.
Daily document fields cover detailed items such as information collection scope and legal basis. Prompt words must precisely match format requirements for different documents. Generated content must conform to structural specifications for compliance documents.
Update frequency varies widely. The system must support dynamic loading of the latest data. Conversation contexts must not contain expired compliance information.
Errors directly relate to administrative penalties or product removal. Content generated via multi-turn dialogue must strictly align with actual business data. Statements conflicting with processing rules for information that can identify natural persons are not permitted.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `messages` | Retain only the most recent 3–5 conversation context entries | Compliance document generation must focus on current core content. Overly long contexts may introduce redundant old data and reduce compliance accuracy |
| `variables` | Bind two core variables: personal information inventory and App permission list | Generated content must directly link to processing rules for information that can identify natural persons in actual business |
| `chatId` | Assign independent session IDs based on product modules | Compliance documents for different products must isolate contexts to avoid cross-product data mixing |
| Context refresh timing | Refresh on each product change, or calibrate based on actual testing | Data update frequency for this category follows quarterly cycles or product changes. Contexts must use the latest compliance data |
| Prompt word field validation | Enforce validation for two required fields: legal basis and information collection scope | Missing core fields in compliance documents directly creates compliance risks |

## Three Common Misconfigurations
- Phenomenon: Compliance documents generated via dialogue have field inconsistencies with content previewed in the workspace. For example, legal basis is labeled incorrectly. Cause: `chatId` is not divided by product module, leading to cross-module context data mixing.
- Phenomenon: Prompt words require generation using only compliance document data, but results still introduce unauthorized information. Cause: `variables` are not bound to limit core data sources, or non-compliant document content is not filtered from the context.
- Phenomenon: Impact assessment reports generated via multi-turn dialogue contain expired user authorization period data. Cause: Context refresh timing is not set, and old versions of user request record data are used.

## How to Verify Proper Configuration
- Review the `messages` configuration to confirm the number of retained conversation context entries meets the current product’s compliance document generation requirements. Adjustments can be made based on actual generation results.
- Check the data sources bound to `variables` to confirm they include core business data required for the current document generation, such as personal information inventories or App permission lists.
- Validate the `chatId` division rules to confirm session contexts for different product modules are isolated from each other, with no cross-module data mixed in.
- Trigger a compliance document generation run, and check that core fields are covered by prompt word validation rules with no missing entries.
