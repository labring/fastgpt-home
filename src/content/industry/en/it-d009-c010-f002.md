# Drafting Requirements and Design Documents for Incident Response and Troubleshooting: Context and Token

## What data for this category looks like
Data sources for this category include monitoring alerts, log platforms, APM tools, and user feedback. Updates occur in real time or each time an event is triggered. Daily produced documents include fault tickets, event timelines, emergency response plans, and fault notifications. Document fields include event ID, impact scope, stop-gap actions, notification recipients, and similar items. Units are primarily timestamps, event counts, and impacted service counts; no additional custom statistical units are used. The data volume for a single event fluctuates based on fault scale. Multi-source data formats vary, so filtering is required before context processing.

## What constraints these characteristics impose on the context and token link
Real-time data updates and fluctuating single-event data volume require the context window to adapt to sudden high-frequency input, preventing token consumption from exceeding model limits due to data overload. Large differences in multi-source data formats demand precise filtering of valid fragments. Without this, invalid content will be introduced, increasing unnecessary token consumption. Fault documents must quickly sync the latest status, so context update frequency must match incident response rhythm. Excessively long context increases model call latency and token costs. Additionally, internal operation and maintenance documents and external notification documents require separate contexts, avoiding model output deviations caused by mixing information from different links.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Maximum Context | `8000–12000 token` | In FastGPT v4.17.0, matches the valid data volume of a single fault event, avoiding exceeding the model's context capacity limit |
| Quoted Maximum Token | `2000–3000 token` | Limits the length of valid content extracted from fault tickets and event timelines, controlling overall token consumption |
| Context Refresh Interval | Updated on event trigger | Matches the real-time data update rhythm, ensuring the context always contains the latest fault status and alert information |
| Recall Result Limit | Top 6 entries | Filters the most relevant monitoring alerts and log data, reducing invalid content introduction and lowering token consumption |
| Context Cache Duration | `3600 seconds` | Covers the event processing duration of a single on-duty shift, avoiding latency caused by frequent data reloads |

## Three common misconfigurations
- Phenomenon: When calling the model to query fault ticket data, the token consumption displayed on the interface does not match API billing records. Cause: The `maxContext` and `quoteMaxToken` parameters are not configured correctly. The interface statistics cover preprocessed context content, while API billing includes additional tokens generated during model reply generation, leading to differences in their statistical scopes.
- Phenomenon: The context and reply content output by the AI conversation node are empty or incomplete. Cause: The set `maxContext` value is too small, failing to accommodate the complete fault timeline and monitoring alert data, resulting in early truncation of the context.
- Phenomenon: Model calls frequently time out or token consumption exceeds expectations. Cause: The recall result limit is not set, introducing a large number of irrelevant historical log data, causing the context length to exceed the model's capacity range and increasing token consumption and call latency.

## How to verify correct configuration
- Review the context content of a single fault event, confirm that it includes the latest monitoring alerts, event timelines, and ticket data, and verify that the context refresh logic aligns with the business rhythm.
- Compare the token consumption displayed on the interface with API billing records, confirm that their statistical logic matches, and verify the rationality of the parameter configuration.
- Simulate fault scenarios of different scales, test model call response speed and token consumption, and adjust parameters to meet business requirements.
- Check whether contexts for different links are separated, confirm that the contexts of fault tickets and external notifications are not mixed, and verify the scenario adaptability of the configuration.

The values provided are common starting points and should be measured against the reader's own samples.
