# Requirements and Design Document Drafting for Incident Response and Troubleshooting: Document Parsing and Chunking

## What data for this category looks like
Data for this category comes from monitoring alerts, log platforms, APM tools, and user feedback. Core documents include trouble tickets, event timelines, emergency response plans, and incident notifications. Data updates occur in real time or each time an event is triggered. A single document typically includes fields such as incident number, affected service scope, troubleshooting operation records, and notification recipients. Document formats are inconsistent. Some content includes tables, timestamps, and structured fields. The size of a single document varies widely based on event complexity.

## What constraints do these characteristics impose on the document parsing and chunking step
Because data sources are scattered and document formats are inconsistent, the parsing process must support multiple types of unstructured content and avoid missing key structured information. The real-time update feature requires the chunking process to have no additional preprocessing delay, to ensure the timeliness of incident response. Documents such as trouble tickets and event timelines include time-series fields and tables. Chunking must avoid breaking logical connections and structured layouts. The document size for a single event varies greatly. Chunking must adapt to input content of different lengths, while retaining the integrity of core fields to ensure that complete event context can be associated during retrieval.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `chunkSize` | 800–1200 characters | Matches the information density per chunk for trouble tickets and event timelines, avoids including too many associated fields in a single chunk |
| `chunkSplitter` | Split by paragraph + line break | Retains time-series and structured paragraphs within documents, avoids breaking the logical coherence of incident timelines |
| `customPdfParse` | Enabled | Compatibility with PDF format of emergency response plans, retains table and title hierarchy structure of original documents |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600 seconds | Matches the parsing duration of large-volume incident notifications and complete event timelines, avoids timeout interruptions |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | Matches the size of complete log export documents for a single event, avoids upload failures |
| `chunkSettingMode` | Manual configuration | Adjust chunking parameters for different event document types, meets the low-latency requirement for real-time updates |

## Three common mistakes
- Tables in trouble tickets do not display in search results: The `customPdfParse` configuration is not enabled. The parsing process does not retain structured table information, only extracts plain text content.
- Chunked content has inconsistent retrieval priority: The configuration logic for `chunkSettingMode` is not clearly defined, resulting in core fields and auxiliary data of chunks not being assigned weights according to business rules.
- Chunked documents uploaded across environments cannot be properly associated: Parameters `chunkSize` and `chunkSplitter` are not unified when using different vector models, resulting in a mismatch between chunk granularity and embedding vector dimensions.

## How to confirm the configuration is correct
- Upload a trouble ticket document that includes tables, check whether the row and column structure of the table is retained in the parsed text.
- Upload an event timeline document of approximately 1000 characters, check whether the chunked result falls within the preset `chunkSize` range.
- Upload a large-volume log export document, confirm that the parsing process does not trigger a timeout error.
- In FastGPT v4.17.0, switch between different vector models to test the same chunked document, confirm that the recall logic of search results is not affected by chunk granularity.

The values provided are common starting points and should be measured against the reader's own samples.
