# Requirements and Design Document Drafting for Cloud Network and Load Balancer Configuration: Context and Token

## What the data for this category looks like
Data for this category primarily comes from configurations exported from cloud platform consoles, network topology diagrams, traffic monitoring reports, and customer architecture design drawings. Daily produced documents typically include VPC planning plans, security group rule lists, load balancer configuration sheets, and change execution sheets. Data update frequency aligns with each configuration change or new order delivery. Document fields usually include network segment CIDR, port ranges, health check thresholds, and backend server group information. Units cover IP segment formats, port numbers, traffic rates, and similar metrics.

## What constraints these characteristics impose on the "context and token" link
Documents in this category are mostly structured configuration content, with dense fields that rely on precise parameter matching. Single-input tokens typically focus on key configuration items such as network segments and ports. Because configuration changes usually require tracing historical rules, context recall must cover the most recent change sheets and topology data to avoid missing associated configurations. Additionally, document update frequency follows change sheet progress. The context window must adapt to newly added configuration fields. Insufficient token quota will truncate critical network segment or health check parameters, leading to drafted documents that fail to fully match actual configuration requirements.

## How to set the configurations
| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the field density of load balancer configuration sheets, prevents truncation of critical network segment and port configurations |
| `quoteMaxToken` | 1500–2000 token | Matches the average length of a single security group rule document, ensures complete reference of historical configurations |
| Context recall count | Top 3–5 entries | Covers recent change sheets and topology data, meets requirements for network segment planning and rule verification |
| Single-match recall limit | Top 6 entries | Avoids recalling irrelevant historical configurations, narrows the valid context scope |
| Calibrate based on actual testing | Adjust according to the average length of actual change sheets | Adapts to cloud network configuration scenarios of different scales |

## Three common misconfigurations
- The `maxContext` parameter configuration entry cannot be located. This occurs because the configuration is not searched for in the Context and Token module of the FastGPT knowledge base configuration page. This parameter is hidden in advanced settings by default.
- A large token limit is set, but configuration content truncation still occurs. This happens because the conversion relationship between character count and token count is confused, and input content length is not adjusted according to actual token quota.
- An error is triggered when uploading a change sheet document, prompting context overflow. This occurs because the `maxContext` parameter is not adjusted according to the field density of the document, leading to insufficient token quota.

## How to confirm configurations are set correctly
- Import a typical load balancer configuration sheet, check that document content is fully displayed without truncation.
- Review recalled historical context configurations, confirm that the most recent 3 change sheets and topology data are included.
- Verify the `quoteMaxToken` parameter value, ensure that the length of a single referenced document does not exceed this quota.
- In FastGPT v4.17.0, submit a test change sheet, check that no content truncation or recall anomalies occur.
