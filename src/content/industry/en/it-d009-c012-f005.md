# Drafting Requirements and Design Documents for Cloud Networking and Load Balancing Configuration: Multi-turn Dialogue and Prompt Engineering

## Data and Document Types for This Category
Data for this category comes from cloud platform consoles, network topology diagrams, traffic monitoring reports, and customer architecture design diagrams. Daily deliverable documents include VPC planning plans, security group rule lists, load balancing configuration tables, and change tickets. Unlike cloud host delivery documents, documents in this category focus on network connectivity and traffic distribution configuration.
Data is updated synchronously each time a network change or ticket is completed. Document fields include CIDR blocks for network segments, port ranges, health check intervals, backend server group IDs, and more. Some fields use standard units: health check intervals use seconds, and traffic thresholds use Mbps.

## Constraints for Multi-turn Dialogue and Prompt Engineering
Data characteristics of this category create clear constraints for multi-turn dialogue and prompt configuration. First, data sources are dispersed and formats vary. Multi-turn dialogue must follow ticket workflows to guide users to provide different types of information such as VPC planning and security group rules, to avoid missing information.
Second, document fields have specific units. Prompts must explicitly require users to provide parameters with standard units, such as specifying seconds for health check intervals.
Third, data is updated synchronously with each change. Multi-turn dialogue must support temporary addition of the latest network topology or traffic monitoring data. It must also verify the accuracy of time-consuming steps such as network segment planning and access rule checks, to prevent issues such as inaccessible connections later in the process.
This document is written based on the configuration logic of FastGPT v4.17.0.

## Configuration Settings
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `chatId` | Generate a unique value for each new configuration ticket | Distinguish between different cloud networking configuration sessions to avoid context confusion |
| `messages` | Populate in the order of system prompt → user requirement → verification result | Align with standard cloud networking configuration workflows to guide multi-turn information verification |
| `variables` | Pre-set network segment ranges (10.0.0.0/8~192.168.0.0/16) and health check intervals (30 seconds) | Cover high-frequency required fields for this category to reduce manual user input |
| Multi-turn dialogue context retention duration | Retain the first 15 turns of dialogue content | Cover the full workflow of a single change ticket to avoid loss of critical information |
| Prompt template variable replacement | Auto-fill generic field placeholders for cloud platforms | Adapt to configuration format requirements of different cloud vendors |

## Three Common Mistakes
- Symptom: A 400 status code is returned when calling the api/v1/chat/completions interface, with a prompt indicating incorrect parameter format. Cause: The prompt template does not explicitly require users to provide parameters with units, causing the interface to fail to parse required fields.
- Symptom: The generated configuration document does not match the exclusive rules of the target cloud platform. Cause: The `variables` parameter is not used to bind the knowledge base corresponding to the cloud vendor, so the dialogue does not call exclusive configuration content.
- Symptom: The network segment planning generated by multi-turn dialogue has conflicts, leading to inaccessible connections in subsequent configuration. Cause: No network segment legitimacy verification step is added to `messages`, and overlapping conditions of CIDR network segments are not checked in a timely manner.

## How to Verify Correct Configuration
- Generate a test configuration ticket, call the api/v1/chat/completions interface, and check if the returned `chatId` matches the unique identifier of the test ticket.
- Enter a health check interval parameter without units, and check if the dialogue prompts for supplementary unit information to confirm that the prompt rules are active.
- Submit a request that includes a pre-set network segment range, and check if the dialogue automatically verifies the legitimacy of the CIDR format to confirm that variable replacement is active.
- View the workflow configuration to confirm that the multi-turn dialogue context retention duration does not exceed the preset threshold, to avoid token overflow risks.
