# Drafting Requirements and Design Documents for Product Usage Data Analysis: Context and Token

## What the data for this category looks like
The data sources for this category include four types: tracking systems, data warehouses, CRM systems, and ticket systems. Update frequencies are divided into daily and weekly. Daily output documents include usage analysis reports, tracking plans, indicator caliber tables, and dashboard requirement sheets. Usage analysis reports contain fields such as user behavior counts and session duration. Tracking plans include text fields such as event identifiers and trigger conditions. Indicator caliber tables contain unified indicator definition text. Data structures vary significantly by document type, with no unified standardized field format.

## What constraints do these characteristics impose on the "context and token" link
The need to integrate multi-source data requires context to be compatible with the field formats of different systems. Format mismatches cause invalid token usage, so this compatibility is critical. Daily and weekly update frequencies require context cache to synchronize with the data source. Using expired data causes token association errors, so synchronization prevents this. Diverse document types require differentiated token quotas for different documents. This ensures key content such as core indicator calibers and tracking rules is not truncated. The high-time-consuming link of unified indicator calibers requires context to retain complete caliber definition text. Token truncation causes caliber information loss, so this retention prevents that.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | 12000–18000 token | Matches the average total token count of daily documents for this category. It prevents truncation of key indicator calibers and tracking data |
| Maximum context cache duration | 24 hours | Matches scenarios where data is updated daily. It ensures cache synchronization with the data source |
| `quoteMaxToken` | 3000 token | Adapts to the content length of a single indicator caliber table or tracking plan. It ensures complete referenced content |
| Number of recalled context entries per request | First 6 entries | Controls total token usage. It covers core insights from multi-source data |
| Context matching threshold | 0.75–0.85 | Distinguishes valid tracking behavior data from noise. It avoids irrelevant content occupying token quotas |

## Three common configuration errors
- Phenomenon: After private deployment, the access path prompts 404. The application cannot be accessed via the /fastgpt context path. Cause: The access context path was not correctly bound in system configuration. Token verification fails to match the legal access route as a result.
- Phenomenon: When starting the OneApi associated service, a token encoder exception is displayed. Cause: The model token quota was not correctly configured. The system fails to parse the session token field in product usage data, leading to initialization failure.
- Phenomenon: Conflicting indicator calibers appear in generated analysis reports. Cause: The context token upper limit was not restricted. Content from multiple indicator caliber tables is mixed and truncated, so complete caliber definitions cannot be retained.

## How to confirm the configuration is correct
- Log in to the FastGPT v4.17.0 system configuration page. Check the context-related parameter items. Confirm that the values of parameters such as `maxContext` and `quoteMaxToken` match the preset configuration.
- Import a standard tracking plan document. Initiate a context recall test. Confirm that the length of the recalled context content does not exceed the preset value of `quoteMaxToken`.
- Initiate a simulated customer behavior data query. Confirm that the context matching threshold of the returned results falls within the preset range. No irrelevant content is recalled.
- Test the bound access context path. Confirm that there are no routing errors when accessing the application via the specified path. Token verification passes normally.
