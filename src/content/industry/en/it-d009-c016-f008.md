# Requirements and Design Document Drafting for Code Security Auditing: Workflow Orchestration

## What This Category of Data Looks Like
Data for this category primarily comes from project source code repositories, third-party dependency lists, static code scanning tools, and public vulnerability databases. It is updated per project version or individual audit tasks.
Daily produced documents include code audit reports, vulnerability verification certificates, repair solution suggestions, and retest records. Common document fields include vulnerability location information, attack path descriptions, risk level identifiers, and repair step guidelines.
The data update rhythm is tied to the project lifecycle, triggered by version iterations or the completion of individual audit tasks.

## Constraints Imposed on Workflow Orchestration by These Characteristics
Dispersed and diverse data sources require workflows to configure multiple nodes to connect separately to source code repositories, dependency list tools, and vulnerability databases. This avoids excessive load on a single node.
The per-project-version update feature requires workflows to bind project-level parameters. This ensures each audit task uses exclusive data for the corresponding project.
The need to output multiple document types requires workflows to split separate document generation nodes. It also requires configuring field mapping rules to match the format requirements of different documents.
Time-consuming steps such as dangerous function localization and data flow tracing require workflows to set serial node dependencies. It also requires configuring reasonable timeout thresholds and retry mechanisms for high-time-consuming nodes to ensure execution stability.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Bind project-exclusive code repository addresses and vulnerability database versions | Match the per-project data update feature, ensuring each audit task uses the corresponding project's data sources |
| `nodeId` | Assign a unique identifier to each data source node | Distinguish pull nodes from different sources to avoid data confusion |
| Node timeout threshold | 600–1200 seconds | Cover the execution duration of time-consuming steps such as dangerous function localization and data flow tracing |
| Retry count configuration | 2–3 times | Address temporary network exceptions during static code scanning tool calls and vulnerability database queries |
| Document type mapping | Classify and map output fields by vulnerability certificate and repair suggestion | Match the structure of multiple types of daily audit documents |
| Workflow trigger rule | Trigger on project version submission | Align with the per-version update business rhythm |

## Three Common Misconfigurations
- Phenomenon: The dropdown menu only displays a single variable option, and multiple associated data sources cannot be selected. Cause: The multi-variable binding rule for `variables` was not configured correctly, and only single-variable mode was enabled.
- Phenomenon: The current execution process cannot be terminated after the debug node starts. Cause: The forced termination parameter for the debug node was not configured, or the workflow did not set an exception interrupt trigger condition.
- Phenomenon: Audit data from intermediate steps is forcibly displayed, which does not meet the requirement of only outputting final results. Cause: The result display switch for intermediate nodes was not turned off, or the silent execution mode for intermediate nodes was not configured in the workflow.

## How to Confirm Proper Configuration
- View the `variables` item in the workflow configuration, confirm that it is associated with the corresponding project's source code repository address, dependency list path, and vulnerability database index.
- Verify the `nodeId` identifiers of each data source node, ensuring there are no duplicate or missing node configurations.
- Start a single test execution, confirm that only the final audit result node has output displayed, and there are no redundant pop-ups or log exposures in intermediate steps.
- Adjust the node timeout threshold and retry count to match the execution requirements of the current audit task. FastGPT v4.17.0 supports real-time verification of this configuration item.
