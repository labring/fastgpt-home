# Requirements and Design Document Drafting for Code Review and Merge Management: Workflow Orchestration

## What this category of data looks like
Data for this category primarily comes from Git repositories, CI pipelines, static scan reports, and defect databases. Core daily output documents include merge requests, code review comments, commit records, and branch strategy descriptions.
Data update frequency is triggered by commit actions. Full change and review records are aggregated daily.
Fields include changed file lists, reviewer comments, conflict markers, branch association relationships, and more. There is no unified mandatory format, and configurations adjust based on team development specifications.

## What constraints these characteristics impose on workflow orchestration
Data sources are scattered and updated in real time with commits. Workflow orchestration must support multi-source data pulling and incremental synchronization to avoid excessive resource usage from full pulls.
Document structures are inconsistent, so `variables` must be configured to adapt to different teams' review field mapping rules, ensuring unified process input formats.
Change trigger frequency is high, so workflows must support automatic startup based on commit events to ensure review processes execute promptly alongside code changes.
Review comments are closely linked to defect databases, so association verification steps must be embedded in the process to ensure review comments are synchronized to defect records.
Merge operations involve branch permissions, so workflows must be bound to Git repository permission configurations to prevent unauthorized submissions. `nodeId` must be used to bind associated nodes to enable data linkage.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Trigger timing | Trigger on Git commit events | Matches data update frequency to ensure review processes start in real time alongside code changes |
| `variables` field mapping | Associate merge request changed files and reviewer fields | Adapts to the field structure of documents in this category, unifying process input formats |
| Node timeout duration | 600 seconds | Covers the standard execution duration of Git pulls and static scans, preventing process interruptions |
| Review approval threshold | First 2 reviewers confirm | Aligns with standard development team review specifications, ensuring change quality |
| Variable reference format | Compatible with `{{}}` template syntax | Adapts to FastGPT v4.17.0 variable parsing rules, avoiding parameter errors |
| `nodeId` association configuration | Bind CI pipeline nodes and defect database nodes | Enables process linkage across multi-source data, synchronizing review and build results |

## Three common configuration mistakes
- Workflows end directly after reaching a large model node, with no subsequent steps. Logs show empty input fields for downstream nodes. This occurs because output bindings for `variables` are not configured, preventing downstream nodes from accessing review result data.
- Incorrect variable reference formats cause workflow errors, with interface prompts indicating parameter parsing failures. This occurs because non-standard template syntax is used, and variables are not referenced using the required `{{}}` format, leading to failed parameter recognition.
- Branch verification steps fail to trigger, with process status showing permission verification not passed. This occurs because Git repository branch permission configurations are not bound, preventing the workflow from verifying whether the submitter has merge permissions.

## How to confirm configurations are correct
- Submit a test merge request to verify whether the workflow starts automatically, with no manual intervention required to enter the process.
- Configure `variables` to map test fields, and check whether process nodes correctly obtain merge request information such as changed files and reviewers.
- Simulate a scenario where two reviewers approve the change, to verify whether the workflow correctly associates CI pipeline nodes and synchronizes build results.
- Adjust the node timeout duration to 300 seconds, simulate a long-running static scan task, and confirm that the process does not terminate early due to timeout.
