# Drafting Requirements and Design Documents for Crowdsourced Annotator Management: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
The data for this category primarily comes from crowdsourcing platform backends, annotation quality inspection records, annotator training exam results, and financial settlement systems. Daily produced documents include personnel access rules, standardized training materials, monthly performance ranking tables, and settlement verification checklists. Data update frequencies are mostly daily or monthly. Fields include unique personnel identifiers, access qualification types, training assessment scores, annotation accuracy, settlement cycles and amounts, among others. The field dimensions for different projects adjust based on the annotation task type.

## What constraints do these characteristics impose on the "multi-turn dialogue and prompt engineering" link?
The data sources for this category are scattered across different business systems. Multi-turn dialogue must support information integration across data sources. Prompt engineering must clearly distinguish field rules for different documents such as personnel access, quality inspection, and performance settlement. There are daily and monthly differences in data update frequencies, so dialogue context must dynamically distinguish between real-time synchronized annotation quality data and periodically updated settlement checklist content. The field dimensions of different documents vary significantly, so prompt engineering must adapt to the extraction logic of different fields such as personnel IDs, accuracy scores, and settlement amounts, to avoid confusing processing rules for different business documents. Additionally, core business time-consuming links are concentrated in personnel screening, quality ranking, and settlement verification. The context of multi-turn dialogue must focus on such business goals to avoid interference from redundant information.

## How to Configure the Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum context length | First 10,000 tokens | Adapts to the number of fields in personnel management documents and the historical length of multi-turn dialogue, avoids context overflow. FastGPT v4.17.0 supports this parameter configuration |
| Number of retained conversation history entries | First 5 entries | Focuses on core business rounds of current annotator management, filters non-core historical conversation content |
| `variables` parameter binding | Bind global variables such as personnel ID, project cycle, settlement cycle | Adapts to core business parameters passed across rounds in multi-turn dialogue, avoids repeated input of fixed business information |
| `messages` parameter filtering rule | Only retain user and assistant conversations from the current business round | Avoids interference from historical redundant content on the accuracy of current document drafting |
| Single conversation response timeout | 600 seconds | Adapts to the time required to pull annotation quality data and settlement data across systems, avoids business process interruption due to timeout |

## Three Common Misconfigurations
- Phenomenon: The final output of multi-turn dialogue contains redundant content from the previous round. Cause: No conversation history filtering rule is configured, causing the `messages` parameter to include all historical conversations, instead of only retaining the context required for the current business.
- Phenomenon: Timeout errors occur when pulling settlement data across systems. Cause: The single conversation response timeout setting is too short, failing to adapt to the time required for information integration across data sources.
- Phenomenon: Prompt engineering cannot correctly distinguish fields between performance tables and settlement checklists, extracting incorrect business data. Cause: Prompt engineering field recognition rules are not optimized for different document types, confusing the business logic of different documents.

## How to Verify Successful Configuration
- Trigger a test conversation, where the input is "Extract the personnel access rules for the current project", verify that the output only contains content related to access rules, with no redundant historical conversations.
- After binding the `variables` parameter, initiate two rounds of conversation, verify that the second round of conversation can call the personnel ID parameter passed in the first round to complete the corresponding business query.
- Adjust the single conversation response timeout setting to 300 seconds, simulate cross-system data pulling, confirm that no timeout errors occur.
- Upload different types of business documents, verify that the prompt engineering can correctly distinguish and extract corresponding fields, with no field confusion.

The values provided are common starting points and should be evaluated against the reader's own samples.
