# Requirements and Design Document Drafting for Supply Chain Security and Open Source Dependency Governance: Context and Token

## What This Category of Data Looks Like
Data for this category primarily comes from package managers, code repositories, vulnerability databases, and license databases. Daily produced documents include SBOM lists, dependency risk reports, license lists, and repair tickets. Fields cover component names, version numbers, vulnerability IDs, license types, repair status, and more. Units are mostly component counts, vulnerability severity levels, and license category identifiers. Data updates occur daily or when a version is released. The dependency asset identification and vulnerability version matching processes generate large amounts of incremental associated data.

## What Constraints These Characteristics Impose on the Context and Token Link
Documents and data for this category have multiple field associations and frequent incremental updates. This creates multiple constraints for context and token management. Component information in SBOM lists and risk reports must be fully associated. The context recalled in a single round must cover at least 3 associated fields to avoid information fragmentation. Frequently updated data will cause the context pool to expand rapidly. Use `maxContext` to limit the total token consumption of a single round of calls. Use `quoteMaxToken` to limit the text length of a single reference. This prevents exceeding the model's carrying limit. At the same time, the associated dependency information of repair tickets must be accurately matched. Excessively long context will cause excessive token consumption and affect response efficiency.

## How to Configure the Settings
The following configurations are formulated based on the logic of FastGPT v4.17.0.

| Configuration Item | Recommended Value Range | Rationale |
| ---- | ---- | ---- |
| `maxContext` (Maximum Context Token Count) | 8000–12000 token | Matches the total token volume of multiple documents such as SBOM and risk reports recalled in a single round for this category, avoiding exceeding the context carrying limit of general-purpose models |
| `quoteMaxToken` (Maximum Reference Token Count) | 1500–2000 characters | Limits the context reference length of a single dependency component, adapting to the conventional text length of vulnerability descriptions and license terms |
| Single-Round Context Recall Limit | Top 10 entries | Controls the total volume of dependency data for a single round of calls, preventing request interruptions caused by excessive token consumption |
| Context Synchronization Cycle | Every 6 hours | Adapts to the daily or per-version update frequency of this category’s data, balancing data timeliness and token management overhead |
| Context Cache Threshold | 200 MB | Limits the total volume of context data stored locally, avoiding storage resource overload in private deployment environments |

## Three Common Misconfigurations
- Symptom: Content is truncated with `[hide 38432 char]` during calls. Cause: Single context reference token count is not limited, causing automatic truncation after exceeding the model's carrying limit.
- Symptom: An exception `failed to get gpt-3.5-turbo token encoder` is thrown when starting the associated model service. Cause: Context token encoding matching rules are not configured correctly, causing dependency data text to fail proper parsing.
- Symptom: The number of dependency data entries recalled in a single round exceeds expectations. Cause: Single-round context recall limit is not set, causing batch fetching of full historical data to consume excessive tokens.

## How to Verify Proper Configuration
- Upload a standard SBOM list for testing. Confirm that the recalled context includes core fields such as component names, version numbers, and vulnerability IDs, with no obvious truncation.
- Check system operation logs. Confirm that the token consumption of a single round of calls does not exceed the configured `maxContext` value.
- Trigger a dependency risk report generation process. Verify that the context synchronization cycle matches the preset update frequency.
- Test associated model calls. Confirm that no token encoding-related exception logs are output.

The values given are common starting points and should be measured against the reader's own samples.
