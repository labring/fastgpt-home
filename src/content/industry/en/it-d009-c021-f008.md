# Drafting Requirements and Design Documents for Supply Chain Security and Open Source Dependency Governance: Workflow Orchestration

## What the data for this category looks like
Data for this category primarily comes from package managers, code repositories, public vulnerability databases, and license databases. Daily produced documents include SBOM lists, dependency risk reports, license lists, and repair tickets. Each document contains fields such as component name, version number, vulnerability severity, license type, and repair status. Data is updated daily or when a version is released, covering full third-party dependency asset information for the current project.

## What constraints these characteristics impose on the "workflow orchestration" link
Multi-source heterogeneous data sources require workflows to be configured with multiple nodes to connect to different data sources, with independent authentication rules configured for each data source. The flexibility of data update frequency requires workflows to support two scheduling trigger modes to adapt to daily batch updates and version-triggered scenarios. The non-standardized nature of document fields requires workflows to be configured with a field mapping node to uniformly align component information fields from different sources. The serious consequences of errors require workflows to be configured with a verification and interception node that directly blocks processes for high-risk vulnerability components and non-compliant licenses, preventing risks from flowing into subsequent links.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Scheduling trigger mode | Trigger on version update / Scheduled trigger at 00:00 daily | Matches the daily/per-version data update frequency, avoids repeated pulling of invalid data, and adapts to the scheduling logic of FastGPT v4.17.0 |
| Multi-source data source authentication | Configure API keys separately for package managers and vulnerability databases | Connects to dependency data from different sources, ensuring compliance with permissions for data pulling |
| `variables` | Preset platform time variables and SBOM version number variables | Used for dynamic fields such as document signatures and ticket numbers, meeting the format requirements of requirement documents |
| Field mapping rules | Uniformly map component names and version numbers to standard fields | Aligns field differences across different sources, ensuring accuracy of subsequent risk analysis |
| Exception interception threshold | Directly block processes for high-risk vulnerability components | Matches the risk level of error consequences, preventing high-risk dependencies from entering subsequent links |
| Log storage duration | Retain 90 days of workflow execution logs | Meets requirements for compliance audits and problem troubleshooting |

## Three common mistakes
- Symptom: The correct signature time does not appear in the post-workflow prompt. Cause: The platform time variable is not bound in the `variables` configuration, or the variable is not correctly referenced in the prompt.
- Symptom: Workflow node status shows an error, and detailed logs for the MCP service cannot be viewed. Cause: Node log collection configuration is not enabled, or the log retention duration is set too short, causing old logs to be automatically cleared.
- Symptom: The same task takes longer to execute in the workflow than in standalone debugging. Cause: The workflow is configured with multi-source data synchronization nodes, and the scheduling trigger mode is set to real-time trigger, causing repeated pulling of redundant data.

## How to confirm the configuration is complete
- Manually trigger the workflow once, check that the signature time in the generated document matches the current system time.
- Go to the workflow node details page, view the log information for the corresponding node, confirm that MCP service call records are complete and have not been cleared.
- Compare the execution time of standalone debugging and workflow runs, confirm that the scheduling trigger mode is not set to high-frequency repeated triggering.
- View the node configuration list, confirm that the `variables` parameter has been correctly bound to the platform time variable and other necessary fields.

The values provided are common starting points and should be measured against the reader's own samples.
