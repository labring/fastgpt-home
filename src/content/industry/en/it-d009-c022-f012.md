# Requirements and Design Document Drafting for Independent Innovation Replacement Adaptation: Document Parsing and Chunking

## What the Data for This Category Looks Like
Data for this category mainly comes from existing enterprise IT system inventories, official catalogs of domestic hardware and software, project test environment records, and public materials from hardware and software vendors. Core daily deliverables include adaptation inventories, compatibility test reports, migration plans, and issue ledgers. Data is updated on a per-individual-independent-innovation-replacement-project cycle, or quarterly to sync the latest versions of domestic hardware and software catalogs. Most document structures include fields such as hardware and software model, version number, compatibility conclusion, and migration steps. There is no unified mandatory format, and some documents include test screenshots and quantitative test results.

## Constraints Imposed by These Characteristics on the "Document Parsing and Chunking" Link
Since core document formats are inconsistent and include strongly related fields such as hardware and software model and version number, the document parsing link must avoid splitting that breaks the contextual association of key information. Multi-source data input requires parsing tools to be compatible with documents of different formats such as adaptation inventories and test reports, while also filtering redundant content from unstructured test screenshots. The data update cycle tied to individual projects requires that the chunking logic can be flexibly adjusted based on document length, to avoid excessively long single chunks that affect subsequent retrieval and matching. In addition, the association between compatibility conclusions and migration steps requires that semantic coherence of adjacent paragraphs is retained during chunking, to prevent loss of key decision-making basis after splitting.

## How to Configure Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `chunkSize` | 800–1200 characters | Ensures semantic completeness of single chunks for documents such as adaptation inventories and test reports, avoids splitting the association between key hardware and software models and compatibility conclusions |
| `chunkSplitter` | Split by paragraph + heading markers | Documents include structured sections such as adaptation inventory entries and test steps; using heading markers preserves module independence |
| `PARSE_FILE_TIMEOUT_SECONDS` | 300–600 seconds | Large compatibility test reports may contain multiple pages of test data; sufficient parsing time must be reserved to avoid timeout interruptions |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | Migration plans for some projects may include large numbers of historical test screenshots and attachments; this setting accommodates large file upload requirements |
| `customPdfParse` | Enabled | PDF documents of domestic hardware and software catalogs mostly include fixed-format model lists; custom parsing can extract structured fields |
| `chunkSettingMode` | Manual mode | Document structures vary widely across different projects; manual configuration allows flexible adjustment of chunking parameters to fit specific scenarios |

## Three Common Misconfigurations
- Symptom: File parsing returns no results or an error after enabling the feature, while normal chat functionality operates normally. Cause: The `customPdfParse` parameter is not configured correctly, or the `PARSE_FILE_TIMEOUT_SECONDS` value is set too short, causing parsing of large test reports to interrupt.
- Symptom: After deploying FastGPT v4.17.0 locally, the file parsing feature completely fails. Cause: Required document parsing plug-ins are not installed, or the `UPLOAD_FILE_MAX_SIZE` configuration is lower than the actual uploaded file size.
- Symptom: Parsing large PDF documents continues to time out while waiting for results. Cause: No task queuing mechanism is configured; single-file parsing occupies excessive resources, blocking subsequent tasks, and `PARSE_FILE_TIMEOUT_SECONDS` is not adjusted to a reasonable range.

## How to Confirm Configurations Are Correct
- Upload a single adaptation inventory document, check that the parsed text chunks retain key fields such as hardware and software model and version number, with no obvious content truncation.
- Upload a test file of the maximum allowed size, confirm that the upload and parsing processes have no timeout errors, and the completeness of parsing results meets expectations.
- Adjust the `chunkSize` parameter, compare retrieval and matching results across different chunk lengths, confirm that semantic coherence aligns with business requirements.
- Check backend logs, confirm that the execution time of file parsing tasks does not exceed the configured `PARSE_FILE_TIMEOUT_SECONDS` value, with no abnormal interruption records.

The values provided are common starting points and should be evaluated against samples specific to the actual deployment.
