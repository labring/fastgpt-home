# Drafting Requirements and Design Documents for Duty Scheduling and Handover: Multi-turn Dialogue and Prompt Engineering

## What data for this use case consists of
Data for this use case comes from scheduling systems, fault work orders, monitoring alerts, and organizational contact lists. Update frequency is daily or weekly. Daily produced documents include duty schedules, handover records, escalation contact lists, and daily duty reports. Fields cover duty time periods, unresolved handover items, escalation contact information, alert response levels, and more. The content structure of a single document is fixed, with no complex nested formatting. The length of a single record mostly falls within the hundreds of characters range.

## Constraints for multi-turn dialogue and prompt engineering
Disparate data sources and daily or weekly update frequencies require multi-turn dialogue to pull the latest scheduling and alert data in real time during each interaction, to avoid using outdated information.
Daily documents have fixed structures and clear fields. Prompts must precisely specify rules for extracting corresponding fields, to prevent generation of irrelevant content.
Duty schedules and handover records are strongly correlated. Multi-turn dialogue must retain historical interaction context, to ensure logical consistency for scheduling conflict coordination and handover item confirmation.
Data errors directly cause delays in operational response. The dialogue flow must include a verification step to confirm no scheduling conflicts and no unresolved handover items are missing.

## Configuration Settings
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Fixed session ID or dynamically generated | Ensures multi-turn dialogue context is bound to a unique session, avoiding cross-session data confusion |
| Chunk Length | 800–1200 characters | Matches the typical length of single duty schedule records, to avoid splitting complete duty time period entries |
| Overlap Length | 150–200 characters | Retains handover item association information across adjacent chunks, preventing unresolved items across chunks from being truncated |
| Single Search Limit | Top 5 entries | Matches the latest 5 alerts or scheduling change records that operational teams typically focus on, reducing irrelevant retrieved content |
| Maximum Context Window | 4000 token | Accommodates 3–5 rounds of scheduling coordination dialogue context, ensuring logical consistency of historical interactions |
| `variables` | Bind duty schedule and escalation contact list documents | Directly calls preset enterprise-level document data, eliminating the need for repeated uploads |
| `messages` | Retain historical interaction roles and content | Supports context linkage for multi-turn scheduling conflict coordination |

## Three Common Misconfigurations
- Symptom: The dialogue prompts that a file has not been uploaded, and the duty schedule document specified in the system prompt cannot be read. Cause: The target document is not bound to the `variables` parameter, or the prompt does not explicitly specify reading content from the documents in `variables`.
- Symptom: The workflow cannot switch knowledge bases in real time during dialogue. Cause: The context linkage logic for the `messages` parameter is not configured, and the knowledge base association rules are not dynamically updated during each dialogue.
- Symptom: Retrieved duty schedule content from the knowledge base is fragmented, and full weekly scheduling information cannot be read. Cause: Title levels such as # or ## are used as separators, and the time period line breaks or fixed entry separation rules of the duty schedule are not matched.

## How to Verify Correct Configuration
- Upload a test duty schedule document, bind it to the `variables` parameter, and initiate a multi-turn dialogue. Check that specified fields such as duty time periods and unresolved handover items are correctly extracted.
- Initiate a multi-turn scheduling coordination dialogue, modify the initial scheduling requirements, and check that the scheduling plan can be adjusted based on the context of historical interactions.
- Set the single search limit to top 5 entries, initiate a dialogue containing multiple alert records, and check that the number of retrieved content matches expectations.
- After deploying the private edition, modify the corresponding code of the front-end popup component, recompile and deploy, then check if the new dialogue popup is removed as expected.

The values provided here are common starting points, and should be evaluated against the user’s own samples.
