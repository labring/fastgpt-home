# Drafting Requirements and Design Documents for Level Content Creation: Workflow Orchestration

## What the data for this category looks like
Core data for level content creation comes from level editors, art resource libraries, player test data, and defect systems. Daily produced documents include level design drafts, resource requirement lists, test feedback sheets, and version submission records. Fields cover level coordinates, resource IDs, test feedback entries, version numbers, and more. There are no unified fixed units. Adjust based on the specific content of each individual document. Data updates occur weekly or during each version submission cycle. Updates typically sync with level iteration progress.

## What Constraints These Characteristics Impose on Workflow Orchestration
Level content creation workflows must support multi-source data association. For example, bind coordinate data exported from level editors to resource IDs in the art resource library. This requires support for cross-data source field mapping. Weekly or version-level update cycles require workflows to trigger on fixed schedules. This avoids frequent execution that wastes resources. Document fields have no unified units, so workflows need flexible field validation rules to adapt to personalized configurations for different levels. Errors may cause level blocks or launch delays. Workflows must include pre-check steps to reduce manual oversights. Unlike other game development categories, level content creation workflows focus on implementing rules for specific maps and tasks, and address personalized level configuration needs.

## How to Configure the Workflow
This configuration applies to FastGPT v4.17.0 and above.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` binding configuration | Bind level ID, resource version number, and test batch number as global variables | Match multi-source data association requirements for level content creation, ensure workflows across different links can share core identifiers |
| `nodeId` allocation rule | Assign fixed `nodeId` to form nodes and knowledge base call nodes | Support cross-branch node reuse, resolve issues where link jumps cannot recognize target nodes |
| Context length setting | 800–1200 characters | Match the average length of single paragraphs in level design documents, avoid overloading context information |
| Trigger timing configuration | Trigger per version submission cycle, 7-day interval | Match weekly or per-version update rhythms, reduce invalid executions |
| Field validation rules | Automatically validate required field completeness for resource requirement lists | Reduce manual document review oversights, align with core field requirements for daily documents |
| Timeout threshold setting | 600 seconds | Match the loading and processing duration of level data, avoid workflow interruptions caused by excessive data volume |

## Three Common Errors
- Phenomenon: When calling a form node across branches, the link cannot jump and the node does not trigger. Cause: Fixed `nodeId` is not configured for the target node, so the workflow cannot recognize the unique identifier of the reused node.
- Phenomenon: Calling the workflow API returns empty values, and no results are output in scenarios with nested knowledge base assistants. Cause: The level resource ID parameter associated with the knowledge base is not correctly bound in `variables`, causing context matching to fail.
- Phenomenon: A `quote type error` is thrown when referencing a variable. Cause: Variables are not formatted to the correct data type as required. For example, a string-type level version number is directly passed to a numeric field.

## How to Confirm the Configuration Is Complete
- Manually trigger the workflow once, select cross-branch form node calls, check if the node normally launches and executes, confirm that the `nodeId` configuration takes effect.
- Call the workflow API, verify that the returned results include expected level design document fragments, confirm that the global variables bound by `variables` work correctly.
- Submit a resource requirement list with complete required fields, check if the workflow automatically syncs corresponding fields to the generated document, confirm that the validation rules are configured correctly.
- Input a variable with an incorrect format, check if the workflow throws the corresponding error, confirm that the timeout threshold and validation rules are configured effectively.

The values listed above are common starting points. Adjust them based on your own specific samples and use cases.
