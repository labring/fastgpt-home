# Drafting Requirements and Design Documents for Internal Network and WiFi Operations: Multi-turn Dialogue and Prompt Engineering

## What Data This Category Contains
Data for this category primarily originates from switch consoles, wireless controllers, office area monitoring systems, and end-user trouble reporting channels. Daily produced documents include network topology diagrams, change orders, fault records, and wireless coverage inspection forms. Document fields mostly include device MAC addresses, SSID names, VLAN IDs, signal strength values, and similar details. Update frequency is daily or after each network change. Core processing steps focus on fault location identification, port and VLAN verification, and wireless coverage blind spot detection. Operational errors may cause office interruptions, meeting disruptions, or failed security isolation.

## Constraints Imposed by These Features on Multi-turn Dialogue and Prompt Engineering
Dispersed data sources, mostly device-native logs with inconsistent formats, require multi-turn dialogue to support parsing of different data formats, and prompts to clearly specify field extraction rules. Document update frequency is triggered by network changes, so dialogue context synchronizes the latest topology and inspection data in a timely manner. Fault troubleshooting requirements mostly involve cross-device association verification, so multi-turn dialogue retains device IDs and VLAN information from historical interactions to avoid repeated input. Signal strength values from inspection forms require precise extraction, so prompts limit value ranges to prevent incorrect fuzzy matching.

## Configuration Settings
The following configurations are based on the interface and parameter logic of FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Chunk Length | 1500–2000 characters | Matches the single-paragraph content length of operation and maintenance documents, prevents key fields such as VLAN IDs and MAC addresses from being split |
| Overlap Length | 200–300 characters | Ensures cross-segment network topology association information is not lost |
| Single Search Limit | Top 6 entries | Matches common requirements for cross-device association troubleshooting, filters redundant device log information |
| Question Optimization | Enabled, calibrated based on actual testing | Standardizes colloquial user trouble reports, improves prompt matching accuracy |
| Maximum Context | 8000–12000 characters | Fully loads the text content of core operation and maintenance documents, avoids information truncation |
| Knowledge Base Binding | Bind switch logs and wireless inspection forms as data sources | Matches the data source characteristics of this category, ensures dialogue can call dedicated operation and maintenance data |
| Session Context Retention Duration | Last 7 days | Matches the average processing cycle of operation and maintenance work orders, ensures session data is traceable |

## Three Common Misconfigurations
- Issue: After calling the API to upload a network topology diagram or inspection form, an error prompt "File parsing failed" is returned. Cause: No dedicated chunking rules configured for structured fields in operation and maintenance documents, leading to truncation of key information.
- Issue: After enabling the You May Also Ask feature, no associated operation and maintenance troubleshooting questions are returned when the conversation ends. Cause: No trigger conditions for generating associated questions specified in the prompt, or context length exceeds limits leading to logic interruption.
- Issue: When creating a dialogue application and calling the API, the preset operation and maintenance knowledge base is not loaded by default. Cause: No knowledge base sources corresponding to switch logs and inspection forms bound in the dialogue configuration, so the session cannot call dedicated data.

## How to Verify Proper Configuration
- Initiate a simulated office network fault trouble report dialogue, check if the dialogue context retains preset historical interaction records.
- Upload a test wireless coverage inspection form, verify that the system can correctly extract core fields such as signal strength and SSID names.
- Check if a unique session identifier is generated with each interaction, ensuring data from different operation and maintenance sessions is not mixed.
- Trigger the conversation end process, confirm that associated troubleshooting questions matching the operation and maintenance scenario are generated.
