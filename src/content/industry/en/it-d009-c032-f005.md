# Requirements and Design Document Drafting for Creator Incentive Settlement: Multi-turn Dialogue and Prompt Engineering

## Data Profile for This Category
The data for this category originates primarily from content platform content interaction and playback metrics, advertising revenue reconciliation systems, enterprise financial payment ledgers, and income application records in creator account backends. Daily deliverable documents include incentive rule details, monthly settlement detail ledgers, creator appeal records, and batch payment lists. Business nodes trigger data updates along monthly settlement cycles or single activity events. Document fields include creator unique identifiers, corresponding content IDs, revenue accounting standards, settlement amounts, appeal status, and additional relevant fields. Updates only occur per business nodes, with no unified fixed statistical standard.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
Disparate, highly correlated data sources require multi-turn dialogue to gradually bind data sources from different systems, preventing cross-system data confusion. Settlement detail fields are numerous and require strict correspondence, so prompts must fix field order and validation logic to avoid information misalignment. Update frequency fluctuates with business nodes, requiring support for dynamically triggered real-time data pull commands. Appeal records are strongly bound to the settlement process, so historical dialogue context must be retained to track full-process operations. Additionally, revenue standard verification and abnormal fraud investigation are core time-consuming steps. Multi-turn dialogue must break down complex validation steps to avoid model understanding errors caused by excessive input in a single turn.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique identifier of the monthly settlement cycle | Associate all full data for the corresponding cycle, including settlement details and appeal records, to avoid cross-cycle data confusion |
| `messages` | Retain the previous 8–12 turns of dialogue context | Cover the full process from incentive rule verification to abnormal investigation, matching the operation nodes of the settlement cycle |
| `variables` | Configure three binding variables: creator ID, settlement cycle, data source identifier | Dynamically pull settlement data from different systems, adapting to multi-source data call requirements |
| Maximum context length | 7000–9000 token | Carry multi-field content of settlement details and historical dialogue, avoiding context overflow |
| Prompt optimization | Calibrate based on actual testing | Optimize prompt logic for high-frequency scenarios of revenue standard verification and abnormal fraud investigation |

## Three Common Misconfiguration Issues
- Issue: API returns a parameter error when creating a workflow, with logs showing unrecognized workflow configuration fields. Cause: Failed to bind the data source identifier corresponding to `variables` as required by the document, causing the API to fail to match the exclusive data link for creator incentive settlement.
- Issue: The model returns "invalid token" after being called. Checking call logs shows the token field is the fixed string "fastgpt". Cause: Failed to correctly configure the data source key binding in `variables`, causing the carried request token to be incorrectly overwritten to the default value.
- Issue: When accessing multiple times with the same session identifier, the context turns from the first call are altered by subsequent requests. Cause: Failed to bind an independent settlement cycle identifier via `chatId`, causing dialogue contexts from different cycles to be confused and overwritten.

## How to Verify Proper Configuration
- Initiate a test dialogue, input the verification command for the corresponding settlement cycle, and check if the returned result automatically associates the settlement fields for that cycle.
- View API call logs to confirm that `chatId`, `messages`, and `variables` parameters are correctly passed according to the configuration, with no missing or altered values.
- Initiate 3 consecutive test requests for the same cycle, checking if the context retains the specified number of turns as configured, with no cross-cycle data confusion.
- Trigger an abnormal investigation command, checking if the prompt automatically calls the bound data source variables to pull abnormal data from the corresponding systems.

The values provided are common starting points and should be measured against the reader's own samples.
