# Requirements and Design Document Drafting for Creator Incentive Settlement: Forms and Interactions

## What the data for this category looks like
Data related to creator incentive settlement is typically generated by content data systems, advertising revenue systems, finance systems, and account backends. Daily associated documents include incentive rules, settlement details, appeal records, and payment lists.
Data update rhythm follows monthly or event cycles. Core fields include creator account ID, revenue amount, settlement cycle, and appeal status. Units include yuan, number of interactions, and calendar days.
The most time-consuming steps in the processing workflow are revenue caliber verification, abnormal fraud detection, and payment document verification. Operational errors can lead to settlement disputes, incorrect or missed payments, or creator attrition.

## What constraints these characteristics impose on the forms and interactions link
The dispersed nature of data sources requires external systems to pull multi-system data variables via APIs and pass them to forms, avoiding manual re-entry.
Field differences across different documents require external systems to support dynamic field loading. Forms only host interactive nodes for corresponding fields. For example, the settlement details page displays amount and cycle fields, while the appeal records page loads appeal reason and processing status fields.
The monthly or event cycle update rhythm requires external systems to implement preset default values per cycle. Forms only display preset default values to reduce repeated configuration operations.
The high time consumption of the revenue verification link requires configuring field validation rules for external business systems to automatically flag abnormal values or missing items.
The strict requirements for payment document verification require external systems to implement file upload components and connect to qualification verification interfaces from the account backend (handled by external systems or subsequent nodes). FastGPT forms only support hosting this component.

## Three Common Mistakes
- Phenomenon: Form input components fail to load revenue data from external systems. Cause: Revenue data is not passed to the form hosting page via external system APIs. The `formInput` node only supports collecting static data manually entered by users or passed in from external sources.
- Phenomenon: The payment document upload component prompts "Unable to upload file". Cause: The format and size limits of the file upload component are not configured, or the access permissions of the external storage service are not configured.
- Phenomenon: Form fields do not match the document structure of the current settlement cycle. Cause: The external system has not implemented dynamic field switching logic, and fixedly uses the monthly settlement field group to handle event cycle settlements.

## How to Verify Successful Configuration
- Open the form hosting page, test pulling revenue data via the external system API and passing it to the form, confirm that the `formInput` node can normally receive form data submitted by users.
- Upload test files of different formats, confirm that the component only allows uploading files that meet the preset format and size requirements.
- Trigger the settlement cycle switching logic of the external system, confirm that the form field group automatically updates to the configuration for the corresponding cycle.
- Enter abnormal revenue values, confirm that the external verification logic automatically flags abnormal entries.
