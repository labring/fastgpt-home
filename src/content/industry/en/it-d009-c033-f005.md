# Requirements and Design Document Drafting for Frontend Application Development: Multi-turn Dialogue and Prompt Words

## What the data for this category looks like
Data for this category is primarily sourced from code repositories, interface management platforms, design draft files, and browser compatibility datasets. Daily produced documents include interface documents, component descriptions, commissioning records, and release checklists. Data update frequency is typically daily or aligned with each release cycle. Fields commonly include interface paths, component properties, compatible browser versions, and commissioning issue records. There is no unified mandatory format, and adjustments are made based on team habits.

## What constraints these characteristics impose on multi-turn dialogue and prompt words
Frontend application development has scattered data sources and flexible formats. Multi-turn dialogue must adapt to mixed-format inputs including code snippets, interface metadata, and design draft annotations. Data update frequency is high. Dialogue context must prioritize recent commissioning records and version change information, to avoid reliance on outdated interface documents or component descriptions. Since daily documents have no unified mandatory format, prompt words must guide the generation of requirements and design documents that comply with general frontend team specifications, while accommodating different teams' document field habits. Additionally, frontend development focuses on interface state and terminal compatibility. Dialogue must clearly define the discussion scope, and avoid straying beyond the core links of page implementation and compatibility troubleshooting.

## Three common mistakes
- Attempting to use #, ## and other headings as long document separators leads to poor retrieval results. The reason is that frontend development interface documents and component descriptions often use custom separators, which do not match the semantic logic of general heading segmentation.
- A 422 status code appears when the agent replies with graphic operation instructions. The reason is that the `messages` parameter format of the dialogue request does not comply with context splicing rules for frontend development scenarios, and component properties or interface parameters are not correctly included.
- Attempting to hide the AI dialogue module has no effect. The reason is that the frontend page switch variable in the `variables` parameter is not correctly configured, or the modified code is not associated with the corresponding deployment branch.

## How to confirm the configuration is complete
- Initiate a requirement query that includes interface paths and compatible browser versions, check whether the preset `variables` parameter content is automatically included in the dialogue context.
- Switch the code repository branch, initiate a new dialogue, confirm that the context does not carry commissioning records and interface information from the old branch.
- Upload a frontend interface document that includes custom separators, confirm that the retrieval results cover interface parameters and component properties, and are not limited to heading tags.
- Trigger a reply request for graphic operation instructions, confirm that no 422 error is returned, and the content complies with the format requirements of frontend operation instructions.
