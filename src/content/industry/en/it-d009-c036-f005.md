# Requirements and Design Document Drafting for Prototyping and Interaction Design: Multi-turn Dialogue and Prompt Engineering

This configuration and usage scenario applies to FastGPT v4.17.0.

## What this category of data looks like
Data for this category primarily comes from daily deliverables of product designers, interaction designers, and front-end product teams. It includes interactive prototype files, page flowcharts, component specification documents, and design review records. Data sources are mostly Figma or Axure source files, internal team design systems, user feedback, and usability test records. Update frequency is once per week or per product version. The document structure centers on page nodes, operation paths, and state transitions as core fields, with no unified fixed units. Content scope must be adjusted according to prototype modules.

## What constraints these characteristics impose on the multi-turn dialogue and prompt engineering link
Since most data sources are unstructured design source files and scattered review records, multi-turn dialogue must support cross-file content association and retrieval. The periodic update requirement means the dialogue flow must adapt to batch processing during version iterations, avoiding redundant calls of expired content. Core fields focus on page structure and operation paths. Prompt engineering should prioritize high-time-consuming links such as state transition sorting and abnormal scenario completion, while ensuring output content only covers the exclusive scope of prototyping and interaction design. Additionally, the fragmented nature of design documents requires multi-turn dialogue to support segmented retrieval and context continuation, avoiding exceeding the content boundary of a single processing session.

## How to set the configuration
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `messages` | First 10 historical dialogues + current prototype context snippet | Design documents are mostly produced in segments, so context association of recent reviews and prototype nodes must be retained to ensure logical coherence of multi-turn dialogue |
| `variables` | Bind project ID of Figma files, current product version number | Adapt to weekly or per-version update frequency, accurately match design files of the current iteration, and avoid calling expired content |
| `chatId` | Generate unique ID per single prototype project | Differentiate dialogue history of different prototype projects, avoid cross-project context confusion, and ensure data isolation |
| Maximum character count per single call | 800–1200 characters | Single-module content length of design documents mostly falls within this range, preventing content truncation caused by exceeding model processing limits |
| Context retrieval count | First 3 latest review records | High-time-consuming state transition sorting only requires support from recent review data, reducing interference from redundant information |
| Automatic variable update rule | Triggered by prototype version submission | Adapt to daily update rhythm, ensuring that dialogue calls always use the latest design document content |

## Three common mistakes
- Phenomenon: The model selection panel for multi-turn dialogue only displays GPT series models, and third-party models such as GLM that have been connected cannot be selected. Cause: The model permission range is not configured in the dialogue node exclusive to prototyping design, and only the default model pool is open.
- Phenomenon: After the workflow is orchestrated, the results of intermediate processing steps are displayed on the frontend, which does not meet the requirement of only outputting the final dialogue result. Cause: The result display switch of intermediate nodes is not turned off, and the rule of only returning the output of the final dialogue node is not configured.
- Phenomenon: After the frontend enables the file upload function, the dialogue interface cannot correctly receive uploaded Axure or Figma files. Cause: The exclusive type whitelist for design files is not configured in the dialogue node, and the corresponding file parsing plugin is not bound.

## How to confirm the configuration is complete
- Open the model selection panel of the dialogue node, confirm that connected non-GPT models have been added to the optional list.
- Enter a query related to page structure or operation paths, confirm that the content returned by the dialogue only focuses on the exclusive scope of prototyping design.
- Upload design files in Axure or Figma format to the dialogue interface, confirm that the file content can be correctly parsed and included in the dialogue context.
- Trigger workflow operation, confirm that only the result of the final dialogue node is displayed on the frontend, with no additional output from intermediate steps.

The values provided here are common starting points and should be evaluated against the reader's own samples.
