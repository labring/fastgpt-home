# Drafting Requirements and Design Documents for Prototyping and Interaction Design: Forms and Interactions

## What the Data for This Category Looks Like
Core data for this category is produced by product designers, interaction designers, and front-end product teams. Daily documents include interactive prototypes, page flowcharts, component descriptions, and review records.
Data sources primarily include Figma or Axure files, team design systems, user feedback, and usability test records. Update frequency typically follows weekly or per-release cycles.
Document fields correspond to page component attributes, operation paths, and exception scenarios. There is no unified mandatory format, and configurations must align with team design specifications.
This page is written based on the configuration logic of FastGPT v4.17.0.

## What Constraints These Characteristics Impose on the "Forms and Interactions" Workflow
Since data sources rely on design tools and review records, form and interaction configurations must strictly match component definitions in prototype files to avoid field mismatches.
Update frequency requirements mean configurations must support rapid iterative adjustments without complex historical version rollback processes.
Documents cover exception handling for multiple scenarios, so form interactions need sufficient configuration items to cover exception scenarios such as empty states and error prompts.
The lack of unified format requirements for documents also means configurations must support flexible adjustments to adapt to different team design specifications.

## How to Set Configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Form Input Node `formInput` | Test approach: Select 3 fields from prototyping and interaction design fields as required inputs; actual fields are determined based on tasks | This node collects user input; missing required items require checking interaction status to prevent subsequent nodes from receiving incomplete input |
| User Selection Node `userSelect` | Test approach: Set 2 business options, check corresponding branches one by one | This node handles user selection; queries and filtering related to prototyping and interaction design records must be implemented by subsequent interfaces or external systems |
| Post-Submission Field Passing | Test approach: Prepare 10 prototyping and interaction design input samples covering full completion, missing required items, and cancel operations | Compare input and node output to verify whether subsequent nodes receive corresponding fields; result thresholds are determined based on actual tasks |
| External Implementation Item: Exception Prompt Copy Configuration | Must be implemented separately by external systems; use copy verified in usability test records from external systems or subsequent nodes, with single copy length of `20–30 characters` | Aligns with user usage habits and reduces repeated modifications in design reviews |
| External Implementation Item: Context Association Configuration | Must be implemented separately by external systems; associate current page flowchart context configuration via external systems or subsequent nodes | Synchronizes page flow logic to prevent interaction paths from deviating from prototype designs |
| External Implementation Item: Version Synchronization Configuration | Must be implemented separately by external systems; synchronize to team document libraries at weekly update frequency via external systems | Matches daily document update rhythm to ensure configurations align with the latest version of prototypes |

## Three Common Mistakes
- Phenomenon: When configuring the `formInput` node, only a single set of input fields is bound, failing to match the design of multiple sets of associated forms in prototypes, resulting in data mismatches. Cause: Did not reference the association logic of page flowcharts, only used conventional single-field binding configurations.
- Phenomenon: The custom input variable receiving rules of subsequent nodes do not match the input fields collected by the `formInput` node, resulting in empty interface receiving parameters. Cause: Did not align with variable definitions in interactive prototypes, leading to inconsistent configured fields and interface expectations.
- Phenomenon: No exception prompt copy is configured, users receive no feedback after incorrect operations, resulting in blocked operation paths. Cause: Ignored exception scenarios in usability test records and failed to complete exception handling logic.

## How to Verify Configurations Are Complete
- Open local Axure or Figma prototype files, verify that form fields fully match input fields configured in the `formInput` node.
- Simulate user-triggered exception operations, check that exception prompt copy matches review records in the design system.
- View configuration update logs to confirm that the most recent update time matches the current version's iteration cycle.
- Test the number of options displayed by the `userSelect` node, confirm it does not exceed the 8-option display limit configured by external systems or subsequent nodes.
