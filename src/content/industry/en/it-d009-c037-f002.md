# Requirements and Design Document Drafting for Release Management and Version Acceptance: Context and Token

## What the data for this category looks like
This document applies to release management and version acceptance scenarios for FastGPT v4.17.0. Core data for this category comes from daily work outputs of version managers, R&D and operations teams, and product owners. It includes four core document types: release plans, online checklists, acceptance reports, and rollback plans. Data sources cover CI pipelines, change systems, test reports, and monitoring dashboards. Update frequency is weekly or once per version. Core fields include version numbers, release item lists, online windows, rollback trigger conditions, acceptance criteria, and more. There is no unified standardized format. Data must be integrated and correlated across multiple systems.

## What constraints these characteristics impose on context and token configuration
The data characteristics of this category impose multiple constraints on context and token setup. First, heterogeneous data from multiple sources requires context to support integrated retrieval of cross-system documents. This avoids missing information from single data sources, which could compromise the completeness of release item verification. Second, the weekly or per-version update frequency requires context validity periods to match version cycles. This prevents redundant data from historical versions from interfering with current version decision-making. Third, core documents vary widely in length. Release plans and rollback plans are typically lengthy. Reasonable limits must be set for token usage per round of context to avoid errors caused by exceeding large model capacity limits. Finally, errors directly affect production environment stability. Context must accurately link to valid data for the current version. This prevents context contamination that could lead to incorrect release or rollback decisions.

## How to set the configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `maxContext` | Top 10–15 entries | Matches the number of core documents per version, covers core content such as release plans, online checklists, and acceptance reports |
| `quoteMaxToken` | 8000–12000 token | Adapts to the average length of single documents such as release plans and rollback plans, avoids token overflow errors |
| Context retrieval similarity threshold | 0.75–0.85 | Filters low-relevance historical version data, prevents context contamination |
| Context update frequency | Triggered once per version | Matches the weekly or per-version update rhythm of data, ensures context always links to current release items |
| Single context retrieval upper limit | Top 5 document sources | Limits the number of documents retrieved from multiple sources such as CI and change systems, avoids token overload |

## Three Common Misconfigurations
- Symptom: `maxContext` is set to 30 entries, but only 2 context entries appear in conversation details, and replies fail to link to historical release data. Cause: The single context retrieval upper limit is not configured correctly. Only the latest scattered change records are retrieved, and core documents for the current version are not fully pulled.
- Symptom: Online checklist content from old versions appears in release management context, leading the AI to recommend incorrect rollback plans. Cause: Rules for updating context based on version cycles are not configured. Redundant data from historical versions is retained, causing context contamination.
- Symptom: Token overflow errors occur during calls. Some scenarios are accompanied by Error response from daemon-related exceptions. Cause: The `quoteMaxToken` value is not limited, leading the total token count for a single round of context integration to exceed the large model’s allowed capacity.

## How to Confirm Configurations Are Correct
- Review context retrieval logs to confirm all retrieved documents fall within the scope of the currently processed version, with no redundant data from historical versions.
- Trigger a question-and-answer session for release item verification. Check that the AI reply has no format errors, and all linked content comes from the current version’s online checklist and acceptance reports.
- Simulate context input containing multiple release documents. Confirm no token overflow errors are triggered, and the `quoteMaxToken` configuration does not exceed the large model’s allowed limits.
- Verify the context update mechanism. After a new version is released, confirm that documents from old versions are no longer retrieved for the current context.

The values provided here are common starting points. Adjust them based on your own samples and measurements.
