# Requirements and Design Document Drafting for Change Management and Release Windows: Context and Token

## What the data for this category looks like
Core data for this category comes from four sources: change management systems, CI pipelines, monitoring data, and business calendars. Four types of documents are produced regularly: change requests, risk assessments, launch window plans, and rollback plans. Data updates occur weekly or when a single change is triggered. Document fields include change unique identifier, effective time window, affected business scope, risk level, approval status, rollback trigger conditions, and more. Time-related fields use hours or days as units, and the risk level field uses standardized graded labels.

## What constraints do these characteristics impose on the context and token workflow
Multi-source data requires context to integrate structured and unstructured content from different systems, which directly increases the required token consumption upper limit. The weekly or single-change update frequency requires context to refresh according to the change cycle, to avoid using expired monitoring or approval data. Multiple document structures require context recall to accurately match the currently drafted document type. For example, when drafting a rollback plan, priority must be given to recalling risk assessment content for the corresponding change. The diversity of fields requires context to focus on core decision-making fields, reducing token usage for non-critical information and preventing the model from being distracted by redundant content.

## How to configure the settings
| Configuration Item | Recommended Value Range | Rationale |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | Covers the core content of a complete single change process in change management scenarios |
| `quoteMaxToken` | 2000–3000 token | Covers the core content length range of a single change request or risk assessment document |
| Context refresh rule | Per change cycle | Matches the weekly or single-change data update frequency of this category |
| Recalled content priority | Prioritize effective time, risk level | Change management decision-making relies heavily on time window and risk rating information |
| Non-core field filtering | Enabled | Reduces token usage for non-critical content such as change IDs and operation logs |

## Three common configuration errors
- Phenomenon: Generated change risk ratings do not match actual monitoring data. Cause: Core field recall priority is not configured, so the model cannot obtain the latest monitoring data.
- Phenomenon: Token overflow errors occur even after `maxContext` is configured. Cause: Non-core field filtering is not enabled, and a large amount of non-decision-related log content is included in the context.
- Phenomenon: The effective time of the launch window plan is ignored by the model. Cause: The time field is not added to the priority recall list, so the context loses critical time information.

## How to verify correct configuration
In FastGPT v4.17.0, the configuration effect can be verified using the following actions:
- Import one complete change management document, test the context recall results, and confirm that core fields such as effective time and risk level are recalled first.
- Check the token consumption statistics, confirm that the proportion of non-core field usage meets expectations, with no excessive consumption.
- Simulate triggering a change process, confirm that the context refreshes according to the preset per-change cycle.
- Verify that the document content output by the model includes core information matching the current drafting scenario, such as rollback plans and approval status.

The values provided are common starting points and should be measured against the reader's own samples.
