# Drafting Requirements and Design Documents for Backup Recovery and Disaster Recovery Drills: Multi-turn Dialogue and Prompt Engineering

## What data looks like for this category
Data for this category originates primarily from backup systems, database logs, object storage, and disaster recovery platforms. Regularly produced documents include backup policies, recovery drill reports, disaster recovery switchover plans, and data verification records. Update frequencies range from daily, monthly, to quarterly. Each document typically includes fields such as recovery point objective (RPO), recovery time objective (RTO), verification rules, and execution steps. Common units are seconds, count, and GB. Some documents include structured drill script snippets and verification log snippets.

## What constraints do these characteristics impose on multi-turn dialogue and prompt engineering
Data sources for this category are dispersed, including structured logs from backup systems, backup file fragments from object storage, and drill records from disaster recovery platforms. This requires multi-turn dialogue to automatically associate fields across different sources. Document update frequencies vary widely. Daily updated verification records require dialogue to retain recent context. Quarterly updated disaster recovery plans require fixed context ranges to prevent interference from outdated data. Each document includes specialized fields like RPO and RTO. Prompt engineering must adapt to operation and maintenance terminology, while limiting context length to avoid redundant non-core drill steps disrupting generated results.

## How to configure settings
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Matches the typical length of a single backup verification record, avoids splitting specialized terms across paragraphs |
| Overlap Length | 100–150 characters | Retains contextual association for recovery steps, prevents loss of drill workflow continuity after splitting |
| Maximum Context | 6000 characters | Adapts to the document length of quarterly updated disaster recovery plans, while avoiding exceeding model processing limits |
| `variables` | Bind RPO and RTO fields | Automatically import specialized parameters for disaster recovery scenarios, reduces repeated prompt engineering work |
| `messages` | Store by document type | Separates dialogue context for backup policies and drill reports, avoids data mixing |
| `chatId` | Create independent sessions per drill task | Isolates dialogue data for different disaster recovery drills, ensures context only relates to the current task |

## Three common configuration mistakes
- Using #, ## and other heading-level separators to split long documents during chunking causes step breaks or lost verification fields. Specialized terms in disaster recovery drill documents rely on heading hierarchy for association. Using heading separators breaks the contextual continuity of recovery steps.
- When generating operation guidance via the dialogue module, a 422 status code is returned. This occurs when structured data fields from backup systems are not correctly bound. Missing required verification parameters in the prompt triggers format verification failure.
- Session records are lost after refreshing the dialogue window, but complete records can be queried in the backend. This happens when persistent storage for `chatId` is not configured. Sessions are only cached in frontend memory, so records cannot be restored after a refresh.

## How to confirm configuration is complete
- Import a complete disaster recovery switchover plan document, verify that split chunks retain full recovery steps and verification rules.
- Send a dialogue request that includes the RPO parameter, confirm that bound `variables` parameter values are automatically included in the returned results.
- Create a session for an independent drill task, refresh the page, check that session records are retained and match the backend data.
- Generate operation guidance content, confirm that no 422 status code is returned and results follow expected formatting.
