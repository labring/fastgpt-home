# Drafting Requirements and Design Documents for Security Incident Response: Context and Token

## What Data for This Category Looks Like
Typical users of this category include security operations center staff, incident response engineers, and customer security leads. Daily documents produced and used include incident response reports, forensics records, remediation plans, and notification materials. Data is primarily sourced from SIEM, EDR, firewall logs, and host images. Update frequency is real-time or per incident. Core time-consuming steps include attack path restoration, isolation remediation, and evidence chain organization. Improper handling may lead to expanded data leaks, business outages, delayed regulatory reports, and other consequences.

## How These Characteristics Impose Constraints on Context and Token Processing
Real-time or per-incident update rhythm requires context to quickly load the latest logs and forensics data, to avoid delayed remediation. Forensics records, SIEM logs and similar data are often lengthy, and can easily exceed the token limit of large models, requiring precise pruning of valid content. Evidence chain organization requires associating context information from multiple source logs. Insufficient context recall scope will lead to incomplete attack path restoration. Regulatory report timeliness requirements mean context data must accurately correspond to the incident cycle, otherwise it will affect report compliance.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `maxContext` | First 8–12 entries | Based on the number of log entries associated with a single security incident response event, avoid excessive redundant data consuming token quota |
| `quoteMaxToken` | 12000–15000 token | Based on the total length of forensics records and SIEM logs for a single event, adapt to the large model context window |
| Context recall count | First 6 entries | Based on the number of associated logs required for attack path restoration, ensure coverage of key evidence chains |
| Single context load duration | 60 seconds | Based on real-time data update delays, avoid timeout interruptions to the remediation process |
| Context filtering threshold | Calibrated via actual testing | Based on field relevance of security incident response documents, filter irrelevant log data |

## Three Common Misconfigurations
- Phenomenon: `maxContext` is set to 30 entries, but only 2 context entries are displayed in the conversation details, and historical remediation records cannot be associated. Cause: Context persistent storage is not enabled, or the configured context window is not bound to the exclusive session ID of the security incident response event.
- Phenomenon: The large model prompts that the context token count exceeds the limit, and response generation fails. Cause: The `quoteMaxToken` value is not restricted, and full SIEM logs are directly imported, leading to token overflow.
- Phenomenon: Ultra-long forensics analysis tasks time out. Cause: A reasonable context load timeout threshold is not set, and log data is not chunked and pruned.

## How to Verify Proper Configuration
- Import SIEM and EDR log samples for a single event in FastGPT v4.17.0, and check that the number of context entries displayed matches the configured `maxContext` value.
- Upload the longest forensics record document, and verify that the large model can parse it normally without triggering a token limit exceeded error.
- Simulate real-time log pushing, and verify that the context update frequency matches the real-time performance of event processing.
- View the token statistics data at the application level, and confirm that the token consumption for single event processing is within a reasonable range.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
