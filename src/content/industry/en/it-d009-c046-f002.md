# Requirements and Design Document Drafting for Security Baseline Checks: Context and Token

## What the data for this category looks like
Data for this category primarily comes from server configurations, middleware configurations, security device policies, and baseline tool exports. Four types of documents are generated daily: baseline checklists, configuration verification records, rectification suggestions, and exception approval forms. Update frequency is monthly or quarterly. Documents include fields such as configuration item name, current value, compliance status, and rectification requirements. No unified fixed units are used. Some fields exist in the form of configuration item numbers, status identifiers, etc. The core focus is compliance verification of security baselines.

## What constraints do these characteristics impose on the "context and token" link
Multi-source heterogeneous data sources cause large fluctuations in the text volume of a single input. Descriptive lengths of different configuration items vary significantly, easily exceeding the AI model's context limit. Monthly or quarterly update frequency means high-frequency context refreshes are unnecessary. However, when drafting requirements and design documents once, multiple historical verification records, rectification suggestions, and exception approval forms must be associated. The total text length easily exceeds conventional context thresholds. Differences in field structures across documents also increase token consumption during context integration. Targeted adjustments to context and token allocation strategies are required to avoid truncation of core compliance information.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | Must cover the integrated text of multiple baseline checklists, rectification suggestions, and exception approval forms to avoid truncation of core configuration information related to compliance judgments |
| `quoteMaxToken` | `2000–3000 token` | Limits the length of a single referenced baseline configuration item or historical verification record, preventing a single reference from occupying too much context space and compromising overall information integrity |
| Context chunk length | `1000–1500 characters` | Adapts to the descriptive length of single configuration items in security baseline documents, avoiding reduced recall accuracy from overly large chunks or increased token consumption from overly small chunks |
| Context recall count | `Top 6–8 entries` | Balances context information completeness and token consumption, covering key content of core configuration items, historical rectification records, and exception approval forms |
| Single processing timeout | `120 seconds` | Security baseline documents have large text volumes, so sufficient processing time must be reserved to avoid mid-interruption and ensure complete generation of requirements and design documents |

This configuration applies to FastGPT v4.17.0

## Three common mistakes
- Phenomenon: When generating requirements and design documents, ellipses appear at the end of the output text, and compliance descriptions of core configuration items are truncated. Cause: The `maxContext` parameter was not adjusted based on the actual integrated volume of security baseline documents, and the default value is insufficient to cover the total text length of multiple associated documents.
- Phenomenon: When starting an AI agent in an offline deployment environment, an error log prompting "get tiktoken dial tcp lookup" failure appears. Cause: Local tokenizer cache is not configured, or network policies restrict external access, preventing loading of dependent resources required for token counting.
- Phenomenon: The number of results returned in a single configuration verification session is insufficient to cover all preset baseline check items. Cause: The context recall count is set too low, or concurrent thread configuration is unreasonable, causing some historical records to fail to be recalled normally.

## How to confirm the configuration is complete
- Upload a typical security baseline checklist along with associated rectification suggestions and exception approval forms, test generation of requirements and design documents, and check for truncation prompts or ellipses in the output text.
- Review system operation logs to confirm that token counting-related errors have been resolved, verifying that context parameters are active.
- Compare result coverage across different context recall count settings, adjusting to align with core information requirements of security baseline check documents.
- Test the token loading process in the offline deployment environment, confirm that local dependent files are correctly configured, and verify absence of network access-related errors.

The values provided are common starting points and should be measured against the reader's own samples.
