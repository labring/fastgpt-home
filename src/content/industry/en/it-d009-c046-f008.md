# Requirements and Design Document Drafting for Security Baseline Checks: Workflow Orchestration

## What data for this category looks like
Data for this category comes from server configurations, middleware configurations, security device policies, and output results from baseline tools. Update frequency is monthly or quarterly. Daily produced documents include baseline checklists, configuration verification records, rectification suggestions, and exception approval forms.
Baseline checklists include fields for configuration item name, baseline value, and actual detected value. Configuration verification records include fields for detection time, detection node, and abnormal item list. Rectification suggestions include fields for abnormal item description and rectification measures. Exception approval forms include fields for exception reason and approval status.
The primary users of this data are security operations staff, security consultants, and internal control auditors. The core focus is whether configuration items comply with organizational security baselines, which differs from vulnerability scanning services. This page was written for FastGPT v4.17.0.

## What constraints do these characteristics impose on the workflow orchestration link
Dispersed data sources that rely on multiple system configurations require workflows to support pulling configuration data from different data sources across nodes.
Low update frequency but regular synchronization requirements mean workflows must be configured with timed trigger nodes to avoid resource waste from real-time triggers.
Fixed daily document fields and standardized output requirements mean workflows must preset variable mapping rules for corresponding fields to ensure unified generated document formats.
The most time-consuming steps are configuration verification, exception confirmation, and rectification review. Workflows must support bulk abnormal item marking and automatic association of exception approval form templates to reduce manual repetitive operations.
Errors affect security compliance. Workflows must add abnormal result verification nodes to block configurations that do not meet baselines from proceeding.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `nodeId` | Configure a unique `nodeId` for each data source node | When pulling data across nodes, `nodeId` is required to accurately locate the output content of the corresponding data source |
| `variables` | Preset four variables: configuration item name, baseline value, actual detected value, and abnormal tag, matching a 1000–1200 character document template | Ensure generated document fields are standardized and meet typesetting requirements for business scenarios |
| Trigger method | Trigger on a weekly schedule, or trigger when security device policies are updated | Data update frequency is monthly or quarterly; scheduled triggering balances resource consumption and data timeliness |
| Data source binding | Bind one server configuration node, one middleware configuration node, and one security device policy node each | Data for this category comes from three types of systems, and corresponding configuration information must be pulled separately |
| Abnormal verification threshold | Calibrate based on actual measurements, matching the deviation range of the organizational security baseline | Determine configuration abnormalities based on actual security baselines to avoid misjudgment or missed judgment |
| Retry strategy | Retry 2 times after failure, with a 600-second interval | Reduce the probability of workflow interruption caused by network fluctuations when pulling data across nodes |

## Three common mistakes
- Phenomenon: Configuration verification record fields generated by the workflow are empty. Cause: No mapping rules for corresponding fields were configured in `variables`, so node output data is not associated with required fields in the document template.
- Phenomenon: The workflow does not respond for a long time after triggering, and the status code shows timeout. Cause: No retry strategy was configured; when pulling multiple types of data sources in a single request, network fluctuations cause request timeout, and no timeout interception node was set.
- Phenomenon: Generated rectification suggestions do not match actual abnormal items. Cause: The abnormal item list node of the corresponding data source was not bound via `nodeId`, generic templates were incorrectly used to generate content, and actual detected configuration deviation data was not associated.

## How to confirm the configuration is correct
- Manually trigger the workflow once, check if the generated baseline checklist includes configuration item name, baseline value, and actual detected value fields, and if the field content matches the pulled data source.
- Simulate a scenario where a configuration item is abnormal, trigger the workflow, check if the abnormal verification node marks the corresponding abnormal item, and if corresponding rectification suggestion content is generated.
- View workflow logs to confirm that the timed trigger node runs according to the preset cycle, cross-data source pulling is successful, and there are no error messages.
- Export an exception approval form generated by the workflow once, check if it automatically associates the exception reason template for the corresponding abnormal item, and if the format meets business requirements.
