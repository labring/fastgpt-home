# Requirements and Design Document Drafting for Vulnerability Disclosure Handling: Workflow Orchestration

## What the data for this category looks like
Data for this category comes from private vulnerability reports, code repository commit records, public data from CVE-numbering authorities, and official project release channels. Updates are triggered once per individual vulnerability event. Daily produced documents include security advisories, vulnerability reports, repair patches, and CVE application materials. Fields cover unique vulnerability identifiers, impact scopes, patch-associated hashes, disclosure schedule times, impact assessment results, and more. The data structure adjusts dynamically based on vulnerability severity and the stage of the disclosure process.

## What constraints do these characteristics impose on the "workflow orchestration" link?
Each vulnerability event is updated independently. This requires workflows to bind to a unique event context to prevent mixing process data from different vulnerabilities. Sensitive attributes in private vulnerability reports require workflows to configure permission isolation nodes. Only project security team members can access these nodes. Public data from CVE-numbering authorities has strict timeliness requirements. This requires workflows to integrate scheduled verification nodes to ensure identifier accuracy before disclosure. The feature of multiple associated documents requires workflows to support cross-node variable passing to link document fields across different stages. The most time-consuming vulnerability impact assessment and disclosure coordination stages require workflows to configure customizable timeout and manual approval nodes to adapt to the processing cycles of different vulnerabilities.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | `{"cve_id": "", "impact_scope": "", "patch_hash": ""}` | Matches core fields of vulnerability documents to facilitate cross-node variable passing |
| `nodeId` | `event_{timestamp}` | Ensures each vulnerability event workflow instance has a unique identifier to avoid conflicts |
| Timeout Threshold | Vulnerability assessment stage: `12 hours`, disclosure coordination stage: `24 hours` | Adapts to the actual processing cycles of the two most time-consuming stages for this category |
| Variable Passing Scope | Only the current workflow instance | Prevents cross-contamination of variable data across different vulnerability events |
| Permission Verification | Only project security team members can trigger | Aligns with sensitive data access requirements for private vulnerability reports |
| Failure Retries | Up to 3 times, interval `5 minutes` | Addresses temporary network or data source fluctuations to avoid workflow interruptions |

## Three common misconfigurations
- Phenomenon: After updating `variables` via a code node in the workflow, subsequent AI chat nodes cannot access the updated variable content. Cause: The global variable real-time synchronization switch for FastGPT v4.17.0 workflows is not enabled. Variables are only loaded once when the workflow starts.
- Phenomenon: After importing a preset vulnerability disclosure workflow, the CVE data source node cannot pull valid data. Cause: API permissions for the corresponding CVE authority are not configured, or `nodeId` does not match the node identifier bound to the data source.
- Phenomenon: The manual approval node is not triggered during the vulnerability disclosure coordination stage. Cause: The timeout threshold is set too short, which does not match the actual processing cycle of the stage, causing the workflow to terminate early.

## How to confirm the configuration is complete
- Trigger a test workflow, check if the global variables panel displays preset fields such as the CVE ID and impact scope of the current test vulnerability event.
- Check the `nodeId` configuration of each node to confirm it matches the preset `event_{timestamp}` format.
- Simulate a timeout scenario to verify whether the workflow triggers an alert or manual intervention node after the set timeout threshold.
- Use an account that is not a project security team member to attempt to trigger the workflow, confirm that it cannot start normally.

The values provided are common starting points and should be measured against the reader's own samples.
