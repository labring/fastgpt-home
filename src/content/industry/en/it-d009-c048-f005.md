# Drafting Requirements and Design Documents for Security Monitoring and SOC Duty: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Data sources for this category include SIEM, EDR, NDR and various threat intelligence feeds. Update cycles fall into two categories: real-time and daily. Commonly produced and used documents include alarm disposal sheets, duty logs, threat intelligence reports, and daily and weekly reports. Fields cover alarm ID, disposal time, judgment conclusions, dispatch targets, and more. The information density of a single document varies with alarm volume. Typical users include SOC analysts, security operation outsourcing teams, and enterprise security centers.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompt Engineering
Multi-source real-time data requires dialogue contexts to pull the latest alarms and intelligence in real time. This avoids reliance on outdated information. Differentiated fields across multiple document types require prompts to clearly define format and field rules for specific documents like alarm disposal sheets and duty logs. High-frequency alarm judgment and false positive elimination scenarios require limiting the multi-turn dialogue context window to a reasonable range. This prevents redundant information from interfering with judgment logic. Errors directly impact security risks. Prompts must strengthen recognition constraints for real attack characteristics. This avoids false positive accumulation or missed alarms.

## Configuration Settings
These settings apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Prompt Template | Focus on three links: alarm judgment, false positive elimination, and dispatch escalation | Matches the most time-consuming core processes of SOC duty |
| Context Window Size | First 6-10 historical dialogues | Prevents redundant information from interfering with real-time judgment |
| `messages` Parameter | Associate historical disposal records by alarm ID | Ensures multi-turn dialogue context accurately links to the corresponding alarm |
| `chatId` Parameter | Bind sessions to a single duty team | Isolates alarm disposal contexts across different teams |
| `variables` Parameter | Inject daily SIEM alarm summary data | Supplement real-time updated data source information |
| Maximum Context Length | 3000-5000 tokens | Adapts to the information density of multi-source data, prevents session timeouts |

## Three Common Misconfigurations
- Incorrect configuration of the `messages` parameter when calling `/api/v1/chat/completions`. Returned content will be unrelated to the current alarm. This occurs when historical disposal records are not associated by alarm ID, and the context is not bound to the corresponding business scenario.
- Failure to set the `chatId` parameter. Dialogue contexts across different alarms will mix, leading to false positive accumulation. This occurs when context data across different duty sessions is not isolated.
- Use of a universal global key to initiate a conversation with a specific application. The interface returns an error of insufficient permissions or unassociated data source. This occurs when the session identifier for the corresponding application is not bound, causing permission and data source association to fail.

## How to Verify Successful Configuration
- Initiate a test dialogue. Enter a specific alarm ID. Check if returned content links to the alarm’s historical disposal records.
- Switch sessions across different duty teams. Confirm dialogue contexts are not shared across teams.
- Pass the `variables` parameter when calling the interface. Check if returned content includes preset daily threat intelligence data.
- Check session error logs. Confirm no context overflow or missing parameter errors appear.

The values provided here are common starting points, and should be measured against the user’s own samples.
