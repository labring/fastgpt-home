# Requirements and Design Document Drafting for Customer Onboarding and Tenant Initialization: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Data for this category typically comes from CRM systems, contract order databases, identity management systems, and product backends. Daily produced documents include onboarding application forms, tenant configuration tables, administrator account lists, and delivery confirmation sheets. Data updates occur per order or daily. Data fields include tenant unique identifiers, administrator account counts, basic permission configuration item statuses, and more. There is no unified mandatory format. Fields must match the internal identity management and contract process rules of the enterprise.

## What constraints do these characteristics impose on the multi-turn dialogue and prompt engineering link?
Data for this category is scattered across multiple systems. Multi-turn dialogue must pull CRM customer information, contract configuration items, and identity system account data in sequence. It must limit the context pull range for each dialogue to avoid redundant data interference. Data updates happen per order or daily. Prompts must explicitly only use the latest data from the current conversation cycle to prevent calling expired tenant configuration information. Additionally, daily documents contain fields in multiple formats. Multi-turn dialogue must match field extraction rules by document type to avoid confusing the field definitions of administrator account lists and tenant configuration tables. Furthermore, errors in this category directly affect customer login and contract acceptance. Multi-turn dialogue must add verification steps to ensure no extracted fields are missing.

## How to set the configuration
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Unique string bound to tenant ID | Ensures multi-turn dialogue binds context for the specified tenant, preventing cross-tenant data interference |
| `messages` | Retain the last 3 rounds of user and assistant dialogue, plus 2 system preset prompts | Requirements drafting for this category revolves around a single tenant's single onboarding process. Excessive historical messages increase context redundancy |
| `variables` | Inject 3 core fields: tenant ID, administrator account count, contract effective date | Matches core data items in daily documents for this category, improving prompt field extraction accuracy |
| Maximum context token count | 8000–12000 tokens | Documents for this category include multiple form contents. This range can accommodate complete text from at least 3 core documents |
| Dialogue timeout threshold | 600 seconds | This category requires pulling data across CRM and identity management systems. Sufficient interface call duration must be reserved |
| Single dialogue variable limit | Top 5 injected variables | Avoids excessive variables interfering with prompt context focus, aligning with the number of core fields for this category |

## Three common mistakes
- Symptom: Debug preview dialogue returns fixed short replies, and response tokens automatically drop below 200. Cause: Historical round limits for `messages` are not set. Excessive old dialogue uses all context tokens, causing subsequent replies to be truncated.
- Symptom: Onboarding configuration for some tenants does not take effect. Fields in delivery confirmation sheets appear empty. Cause: Tenant ID is not injected into `variables`. Prompts cannot match exclusive configuration data for the corresponding tenant.
- Symptom: Generic permission items are incorrectly written to administrator account lists during dialogue. Cause: Field extraction rules are not differentiated by document type. Field definitions of tenant configuration tables and administrator account lists are confused.

## How to confirm configuration is complete
- Initiate a simulated onboarding process dialogue. Check if the bound `chatId` matches the test tenant ID to confirm correct context binding.
- Call the variable injection link. Verify if `variables` include core fields for the current tenant to confirm complete data injection.
- Trigger a cross-system data pull scenario. Check if the dialogue returns results within the set timeout threshold to confirm the timeout configuration is active.
- View debug logs. Confirm that multi-turn dialogue context only retains messages from the specified rounds, with no redundant data interference.
