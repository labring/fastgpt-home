# Requirements and Design Document Drafting for Customer Data Import and Migration: Multi-turn Dialogue and Prompt Engineering

## What this type of data entails
Data sources for this category include customer legacy systems, CSV or Excel templates, database export results, and product import logs. Daily deliverables include data templates, migration plans, field mapping tables, and migration validation reports. Update frequency varies per individual project. Data fields cover core attributes of customer business entities, with no unified mandatory units. Matching must align with field definitions from the customer’s original system. Implementation consultants, data implementation engineers, and customer IT liaisons perform the work. Core tasks focus on field mapping confirmation, dirty data cleaning, and post-import verification. Errors may lead to historical data loss, field misalignment, or customer rejection.

## What constraints these characteristics impose on the multi-turn dialogue and prompt engineering workflow
Decentralized data sources require multi-turn dialogue to sequentially calibrate field formats exported from different systems, preventing mapping misalignment. Irregular single-batch updates require prompt engineering to dynamically adapt to field adjustments for individual migration tasks. Requirements to reference multiple associated documents limit the configuration scope of the context window. Predefined mapping rule parameters must be passed via `variables`. The risk of errors such as field misalignment and data loss requires adding pre-validation logic to the dialogue workflow. Field matching relationships must be confirmed incrementally across multi-turn interactions. Variations in single migration data volumes require prompt engineering to adapt to import validation steps of different scales. `chatId` must be used to isolate dialogue data across different batches, preventing confusion.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Context window size | 8000–12000 characters | Adapt to the needs of referencing multiple associated migration documents, avoid exceeding the built-in context limits of FastGPT |
| `variables` passing parameters | Include field mapping rules, data source identifiers | Used to pass predefined migration rules across multi-turn dialogue, reduce repeated input |
| `messages` queue length | Retain the first 20 historical messages | Focus on interaction content for the current migration batch, avoid redundant history interfering with prompt engineering logic |
| `chatId` binding rule | Bind a dedicated conversation ID for a single migration batch | Ensure isolation of interaction data for the same migration batch, prevent confusion across batches |
| No-interaction interruption threshold | Automatically reset the session after 600 seconds | Adapt to the time rhythm of single migration batches, avoid occupying dialogue resources for extended periods |

## Three common mistakes
- Issue: When calling the API to send consecutive questions, subsequent requests must wait for prior generation to complete. Cause: No dedicated conversation context is bound via `chatId`, leading to no concurrent isolation of the conversation queue.
- Issue: An error stating "No permission to operate this conversation record" appears during operations. Cause: `chatId` is not bound correctly, or session permission parameters are not passed via `variables`, leading to cross-session permission verification failure.
- Issue: After upgrading to FastGPT v4.17.0 and refreshing the page, conversation records appear as new conversations. Cause: `chatId` is not fixed in the configuration, the system generates a new conversation ID by default, leading to no association with historical data.

## How to confirm proper configuration
- Initiate a test conversation for a single migration batch, check if the `variables` parameter correctly passes field mapping rules covering all core fields for the current batch.
- Send two or more consecutive migration-related interaction requests, confirm that subsequent requests do not need to wait for prior generation to complete, verify that the concurrent isolation configuration for `chatId` takes effect.
- Review field matching results from import logs, confirm that the mapping rules generated in the conversation match the field definitions in the logs, with no misalignment.
- Wait 600 seconds without interaction, then refresh the page, confirm that the conversation record is not automatically reset, verify that the no-interaction interruption threshold configuration logic works correctly.
