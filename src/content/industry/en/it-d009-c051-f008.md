# Drafting Requirements and Design Documents for Customer Data Import and Migration: Workflow Orchestration

## What data for this category looks like
The data for this category primarily comes from customers’ legacy business systems, custom CSV or Excel templates, database export files, and log files generated by product import processes. Daily deliverables include data import templates, migration execution plans, field mapping comparison tables, and migration validation reports. Data update frequency is ad-hoc per order, with no fixed cycle. Data fields include customer business identifiers, business data content, relationship identifiers, and similar items. There are no unified fixed units, so matching must be done according to the customer’s business scenario.

## What constraints these characteristics impose on workflow orchestration
This page is written based on the workflow functionality of FastGPT v4.17.0. The multi-source data access feature requires the workflow to support node configuration adapted to different data sources, and must be compatible with multiple input formats such as CSV and database exports. Ad-hoc per-order data updates require the workflow to dynamically adjust parameters such as mapping rules and cleaning thresholds via `variables`. The complexity of field mapping requires the workflow to include a built-in field matching verification step to avoid field misalignment. The pre-requirement for dirty data cleaning requires adding a data verification branch during orchestration to intercept or flag abnormal data. The traceability requirement for import logs requires the workflow to retain execution record nodes for each step to facilitate subsequent verification. Additionally, the serious consequences of data errors require the workflow to be configured with failure retry and branch rollback mechanisms.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Variable configuration | Configure `variables` per order as data source path, field mapping rules, and dirty data cleaning thresholds | Adapt to ad-hoc per-order update requirements, support dynamic parameter adjustment |
| Loop body node | Configure a single loop to process 100-200 pieces of data, with the loop range covering the total number of rows in the imported data | Avoid excessive single processing volume causing timeouts, adapt to batch import scenarios |
| Field mapping node | Set matching rules to prioritize exact matching, set fuzzy matching threshold to 0.85 | Cover scenarios where field names differ, improve mapping accuracy |
| Failure retry configuration | Configure 3 retry attempts with a 60-second retry interval | Address temporary network fluctuations or temporary data source unavailability |
| Global variable binding | Bind `nodeId` as the unique identifier of the preceding data source node | Ensure the loop body can correctly reference the output data of the preceding node |

## Three Common Mistakes
- Loop body cannot reference external variables: The symptom is that the loop body node cannot read global parameters defined in `variables`, and the interface displays empty fields. The cause is failure to correctly bind `nodeId` to point to the external variable node, resulting in scope isolation.
- Code running node verification failure: The symptom is that when historical records are included in the input, the system returns a verification failure prompt, and the node cannot be saved or executed. The cause is failure to clean up unstructured historical record fields in the input content, triggering the input format verification rule.
- Field mapping matching deviation: The symptom is that the field corresponding results of imported data do not match the preset rules, and field misalignment occurs. The cause is failure to adjust the matching threshold for the customer’s data business fields, using the general default configuration.

## How to Confirm Proper Configuration
- Check variable configuration: Confirm that the parameters included in `variables` match the data source and mapping rules of the current import task. Parameter loading status can be reviewed via the preview node.
- Test loop body execution: Select a small volume of test data to run the workflow, confirm that the loop body can correctly traverse each data entry and reference externally defined parameters.
- Verify failure retry logic: Simulate a temporary data source unavailability scenario, confirm that the node triggers the retry mechanism and the number of retries aligns with the configured requirements.
- Verify field mapping results: Run a small-batch data import, check whether the field mapping results match the preset rules, and confirm no field misalignment occurs.
