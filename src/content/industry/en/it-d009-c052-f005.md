# Requirements and Design Document Drafting for Customer Permission and Organization Architecture Configuration: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
The data for this category mainly comes from customer HR systems, identity directories, product backends, and audit logs. Data is updated per order or irregularly. Daily produced documents include permission matrices, organization architecture tables, role configuration records, and permission change forms. Core fields include department hierarchy, role ID, permission scope, change time, and associated customer ID. The data structure adjusts based on the customer's organization size. Small customers’ organization architecture tables only include basic department and role mappings. Large customers add cross-department permission groups and temporary permission configuration items.

## What constraints do these characteristics impose on the "multi-turn dialogue and prompt engineering" link?
The data sources for this category are scattered, and updates have no fixed cycle. Multi-turn dialogue must support dynamically pulling the latest permission data from different systems, to avoid configuration deviations caused by static caching. The field structures of daily documents vary greatly. Prompts must clearly specify the parsing priority of different documents, and give priority to matching core permission rules in the permission matrix. Errors in permission configuration directly lead to unauthorized access or stuck business processes. Multi-turn dialogue must verify field integrity after each round of generation, to ensure no key configuration items are missed. This category details the relationship between roles and departments. Prompts must distinguish permission isolation rules within tenants, to avoid confusion with tenant initialization configurations of other categories.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `variables` | Includes department hierarchy, role ID, and permission scope fields | Matches the core business fields of category data, ensuring dialogue can accurately reference permission configuration data |
| `messages` context length | First 10 conversation turns | Avoids overload of permission configuration data, while retaining sufficient context to verify change impacts |
| `chatId` binding scope | Within a single customer tenant | Achieves isolation of permission configurations across different customers, aligning with the specialized scenario requirements of this category |
| Temperature parameter | 0.1–0.3 | Ensures rigor of permission configuration content, reducing randomness of generated results |
| Log synchronization threshold | Within 600 seconds | Matches the update frequency of audit logs, ensuring change records can be synchronized in a timely manner |

This configuration applies to FastGPT v4.17.0.

## Three common misconfigurations
- Phenomenon: After configuring variable references, the temperature setting button disappears, and generation parameters cannot be adjusted. Cause: The binding scope of the temperature parameter is not separately declared in the `variables` configuration, causing the dialogue context to automatically hide non-core configuration items.
- Phenomenon: After running the interface call workflow, the running data in the conversation log is empty. Cause: The `chatId` is not bound to the workflow's execution context, causing associated data of permission configurations to not be written to the log storage.
- Phenomenon: When entering the `any` parameter into the prompt code block of the text content extraction module, the returned result prompts that the code block is undefined. Cause: The parsing rules for code blocks are not specified in `messages`, causing fields of permission configurations to not be correctly identified and extracted.

## How to confirm configuration is complete
- Check whether the `variables` configuration includes core fields such as department hierarchy, role ID, and permission scope, and that the field names match those in documents exported from the customer's HR system.
- Initiate a test conversation, confirm that the temperature parameter setting option displays normally, and that the generated permission configuration content complies with preset permission matrix rules.
- Trigger the interface call workflow, check whether the conversation log includes the associated `chatId` and running data, confirming that log recording works properly.
- Simulate a permission change operation, confirm that the corresponding change record is generated in the audit log, and that all fields are complete.
