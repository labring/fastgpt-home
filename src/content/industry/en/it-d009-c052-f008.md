# Requirements and Design Document Drafting for Customer Permission and Organizational Structure Configuration: Workflow Orchestration

## What the data for this category looks like
Core data for this category typically comes from customer HR systems, identity directories, product backends, and audit logs. Four types of documents are regularly generated: permission matrices, organizational structure tables, role configuration records, and permission change forms. Data update cycles are per form or irregular. Core fields include department hierarchy, role permission scope, associated user list, and change approval records. Primary units are hierarchy serial numbers, permission codes, user IDs, and dates. Data verification must cover two core links: organizational hierarchy mapping and role permission matching. Failure to complete this verification may lead to subsequent process exceptions.

## What constraints these characteristics impose on the workflow orchestration link
Decentralized data sources require workflows to support pulling data from multiple systems. Temporary storage nodes must be configured to cache permission and organizational data obtained across systems. Irregular update frequencies require workflows to support on-demand triggering, to avoid invalid tasks consuming resources. Field differences in core documents require workflow nodes to verify the field matching degree of permission matrices and organizational structure tables, to ensure unified data formats. The high time cost of organizational hierarchy verification requires workflows to set segmented verification nodes, to avoid single-task timeouts. Audit log retention requirements mean workflows must automatically record every configuration change, for subsequent audit tracing.

The following configurations apply to FastGPT v4.17.0 workflow orchestration.

## How to set the configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Global variable `variables` | Cache permission and organizational data pulled across systems | Avoid repeated calls to external system interfaces, improve execution efficiency |
| Node timeout duration | 600 seconds | Cover the average time required for cross-system pulling and hierarchy verification |
| Branch trigger rule | Branch based on role permission mapping results | Adapt to the core permission allocation logic of this category |
| Change auto-recording | Enable audit log synchronization | Meet subsequent compliance tracing requirements |
| Verification trigger `nodeId` | Bind to the organizational hierarchy verification node | Ensure accurate execution of verification actions |
| Field verification matching degree | 80%-100%, calibrated based on actual testing | Ensure data consistency of core documents |

## Three common mistakes
- The workflow throws an error directly when running to a tool call node, and the interface returns empty fields. The cause is that cross-system pulled permission data is not configured via `variables`, resulting in missing necessary parameters when the node is called.
- The workflow branch does not reuse shared HTTP request nodes, leading to repeated interface calls and increased time consumption. The cause is that the shared HTTP request node is not set as a public branch node, and each permission branch has a separate request step configured.
- After modifying workflow configurations, published channels still execute old logic. The cause is that the updated workflow version is not synchronized to the published channel binding node, and version update verification is not triggered.

## How to confirm the configuration is complete
- Trigger a test workflow, verify whether the temporary data stored in `variables` matches the permission data exported from the source system.
- View the workflow run logs, confirm that the timeout duration does not trigger an alert, and node execution time is within the expected range.
- Submit a permission change form, verify whether the audit log automatically records the complete steps of the workflow execution.
- Switch between different role branches, confirm that the workflow executes the corresponding nodes according to the configured trigger rules.
