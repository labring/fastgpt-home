# Requirements and Design Document Drafting for Customer Requirement Pool Management: Context and Token

## What This Category’s Data Looks Like
The typical actors for this category are product operations, customer success teams, and product managers. Daily deliverables include requirement pool lists, requirement assessment forms, customer feedback records, and version planning descriptions. Data sources primarily include ticket systems, customer interview records, CRM systems, and product roadmaps. Update frequency is weekly or per version release cycle. The data structure includes fields such as customer identifier, requirement description, merge status, assessment score, and scheduling priority. There is no uniform fixed length for individual data entries. Length varies dynamically based on the volume of customer feedback and the complexity of requirements.

## What Constraints These Characteristics Impose on Context and Token Processing
Dispersed data sources and inconsistent update rhythms require precise filtering of expired data during context recall. This prevents redundant information from occupying token resources. Field differences across multi-source data require the context to adapt to the length characteristics of different documents. This prevents individual data entries from exceeding the model’s token limit. High-frequency duplicate requirement merging scenarios require retaining historical merge records as context references. At the same time, the maximum context length must be limited. This avoids excessive token consumption leading to call failures. The high data update frequency requires regular context refreshes. This ensures that associated requirement information remains synchronized with current version planning.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | `Retain customer requirement feedback and merge records from the last 7 days, approximately 8000–12000 token` | Matches the weekly or per-version data update frequency, covers the requirement iteration cycle of the current version, and avoids redundant old data occupying tokens |
| `quoteMaxToken` | `Single requirement document fragment must not exceed 1500 token` | Adapts to the single-field length of documents such as requirement pool lists and customer feedback records, preventing individual data entries from exceeding the model’s token limit |
| Context recall upper limit | `Top 6 matching requirements` | Balances information completeness for requirement merging and token consumption, covers typical scenarios of duplicate requirements across multiple customers |
| Context refresh cycle | `Reset every 7 days` | Matches the data update rhythm, ensuring the context always associates with the current version’s requirement scheduling |

## Three Common Misconfigurations
- Symptom: Repeated recall of duplicate historical requirement fragments during the requirement merging process, leading to consistently high token consumption. Cause: The recall scope for `maxContext` is not limited. Expired non-current version requirement data is retained, causing redundant information to occupy tokens.
- Symptom: The interface only displays total token consumption, and cannot separately view input and output token counts. Cause: Token split statistics configuration is not enabled, or the FastGPT version in use does not support this feature (FastGPT v4.17.0 or higher is required).
- Symptom: Model calls return network errors or `oneapi` fatal logs, and requirement documents cannot be generated. Cause: The `oneapi` proxy address and key are not configured correctly, leading to an interruption in the token call chain.

## How to Confirm Configuration Is Complete
- Review context recall logs to confirm only requirement data from the last 7 days is recalled, with no expired historical fragments.
- Access the model call records page to separately view the specific values of input tokens and output tokens.
- Test the requirement merging process to confirm that a context clear operation can be triggered after merging is completed.
- Verify the `oneapi` configuration by initiating a test call and confirming that normal requirement document content is returned.
