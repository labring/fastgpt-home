# Requirements and Design Document Drafting for Customer Demand Pool Management: Workflow Orchestration

## What the Data for This Category Looks Like
The data sources for this category are ticket systems, customer interview records, CRM systems, and product roadmaps. The update rhythm follows weekly or per-version release cycles. Daily produced documents include demand pool lists, demand assessment forms, customer feedback records, and version planning descriptions. Common fields include demand source, priority, associated customers, scheduled release dates, and resource usage. There is no unified mandatory format, and configurations must align with enterprise internal customer demand management specifications.

## What Constraints These Characteristics Impose on the "Workflow Orchestration" Link
Dispersed data sources and inconsistent formats require workflow orchestration to support flexible configuration of multi-source data pull nodes, avoiding hard-coded fixed data sources. Fluctuating update frequencies require configuring trigger conditions to adapt to weekly or on-demand triggered tasks, preventing repeated execution or missed updates. No unified standard for document fields requires defining extensible field mapping rules via `variables` to adapt to differences in demand pool fields across enterprises. Additionally, the demand merging and value assessment links account for a high proportion of total work time. Workflows must include standardized rule nodes to reduce manual repetitive operations.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0, as detailed below:

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Configure 10–15 extensible variables based on demand pool field definitions, including demand source and priority fields | Adapt to enterprise-customized demand pool field formats, avoiding hard-coded restrictions |
| `nodeId` | Assign unique `nodeId` values to multi-source data pull nodes, sorted in the order of ticket systems, then CRM systems | Ensure data pull order aligns with business logic for demand pool integration |
| Trigger Node Settings | Set to weekly scheduled triggering or triggering after customer feedback submission | Match the weekly or per-version update frequency of this category |
| Retry Count | 2 retries, with a 60-second interval | Address temporary access failures in multi-source systems, reducing task failure rates |
| Global Variable Persistence | Retain variable values after session ends | Support cross-session demand pool data synchronization and traceability |

## Three Common Configuration Mistakes
- Symptom: `variables` fields assigned via API links are empty. Cause: Corresponding field mapping rules for API returns are not declared in the `variables` configuration, resulting in failure to correctly bind data to demand pool fields.
- Symptom: Global variable values are lost after a session ends. Cause: Global variable persistence configuration is not enabled. The default behavior clears variable cache after session end, which does not meet cross-session demand pool data synchronization requirements for this category.
- Symptom: Demand merging results do not meet expectations after workflow execution, leading to disordered R&D scheduling. Cause: Execution order of `nodeId` is not configured based on demand source and priority, resulting in low-priority demands being processed first, which disrupts business logic.

## How to Verify Successful Configuration
- Check if the `variables` configuration covers the core fields of the current demand pool. This can be verified by exporting the demand pool list and comparing field matches.
- Verify that the execution order of `nodeId` aligns with business logic. This can be tested by manually triggering the workflow and reviewing the data pull sequence.
- Test the global variable persistence function. Modify variable values during one session, then end the session and re-enter to check if variables are retained.
- Trigger a scheduled task once to confirm the workflow executes at the configured update frequency, with no abnormal errors.

The values provided are common starting points and should be evaluated against local sample data.
