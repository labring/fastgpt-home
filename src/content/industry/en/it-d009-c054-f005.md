# Drafting Requirements and Design Documents for Container Platform Operations: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Container platform operations data primarily comes from Kubernetes API, image registries, monitoring systems, and CI pipelines. Update frequency is daily or upon each cluster change. Daily produced documents include cluster change tickets, namespace quota tables, deployment records, and fault reports. Fields cover namespace names, Pod replica counts, image versions, resource quota thresholds, monitoring metrics, and more. Units include cores, GB, entries, and times, among others. Most document structures are structured tables and standardized entries, which must match the current real-time configuration of the cluster.

## What constraints these characteristics impose on the multi-turn dialogue and prompt engineering link
Operations data has strict real-time requirements. The context length of multi-turn dialogue must be strictly controlled to avoid outdated cluster configuration interfering with current document drafting. Structured document formats require prompts to explicitly specify fields and output formats, reducing manual adjustment costs. Data update frequency is daily or per single cluster change, meaning variables bound in dialogues must be refreshed regularly to ensure document content aligns with cluster status. Additionally, sessions of different operations personnel must be independently isolated to prevent cross-viewing of others' document drafts.

## How to set configurations
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `messages` | Retain the most recent 10–12 dialogue context entries | Operations scenarios require tracing recent changes and troubleshooting records; excessive context will dilute core information |
| `variables` | Bind cluster data such as namespace quotas and Pod replica counts | Operations documents rely on real-time cluster configurations; injecting content via variables ensures accuracy |
| `chatId` | Bind session ID to isolate dialogues | Different operations personnel need independent usage to avoid cross-contamination of session data |
| Variable refresh interval | Refresh once every 120–180 seconds | Operations data updates daily or per cluster change; regular refreshing maintains variable timeliness |
| Prompt template | Preset structured output formats for cluster change tickets | Operations documents require standardized fields; templates reduce format errors |
| Context scope | Limit to cluster operations-related document fragments | Narrow the model's processing scope to improve the targeting of document drafting |

## Three common mistakes
- Symptom: Dialogue content from different operations personnel is visible to each other, with cross-contaminated session data. Cause: `chatId` binding for session isolation is not properly configured, and session permission verification is not enabled.
- Symptom: When calling the dialogue record list interface, the returned entries do not match the expected offset, and the number of results is abnormal. Cause: The role of the offset parameter is not properly understood, and the offset parameter is confused with the entry count parameter.
- Symptom: Global variables cannot be modified by the model in the same dialogue, only the initially passed values are retained. Cause: The editable permission for the variable is not configured, or the prompt does not explicitly allow variable updates.

## How to confirm the configuration is correct
This verification applies to FastGPT v4.17.0:
- Initiate a document drafting dialogue for cluster quota adjustment, and check that the dialogue is only visible to the current account.
- Call the dialogue record list interface, pass the offset parameter, and verify that the returned entries meet expectations.
- Submit a request to the model to modify a global variable, and verify that the variable value is correctly updated and takes effect in subsequent dialogues.
- Check that bound cluster data variables are automatically refreshed following cluster changes.

The values provided are common starting points and should be measured against the reader's own samples.
