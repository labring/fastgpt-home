# Requirements and Design Document Drafting for Container Platform Operations: Document Parsing and Chunking

## What this category of data looks like
Common document sources for container platform operations include Kubernetes APIs, image registries, monitoring systems, and CI pipelines. Daily produced documents include cluster change tickets, namespace quota tables, deployment records, and fault reports. These documents contain fields such as cluster ID, Pod replica count, resource quota thresholds, and fault occurrence time. Units include cores, GiB, and counts. Document update frequency is daily or per cluster change. Document formats include PDF, PPT, JSON, and plain text.

## What constraints do these characteristics impose on the document parsing and chunking link
Mixed document formats and automated sourcing require the parsing step to support PDF, PPT, and JSON formats. It must also avoid missing structured data output by CI pipelines. The daily or per-change update frequency requires the parsing step to support low-latency processing, to meet synchronization requirements for real-time operational scenarios. Documents contain strongly correlated fields such as cluster ID and resource quota thresholds. Chunking must retain context associations to avoid splitting critical parameters and causing information breaks. Operational documents often include operation steps and fault troubleshooting logic. Chunking rules must match the semantic structure of the content to adapt to the information density of operational scenarios.

## How to configure settings
These configuration notes are based on FastGPT v4.17.0
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chunkSize` | 800–1200 characters | Adapts to the information density of single segments in operational documents, avoids splitting critical parameters such as cluster quotas and Pod configurations |
| `chunkSplitter` | Semantic chunking | Matches the operation steps and fault troubleshooting logic in operational documents, retains context associations |
| `customPdfParse` | Enable OCR enhanced mode | Handles scanned cluster change reports and PPT-format deployment records |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | Accommodates large cluster upgrade documents and quarterly operational summary reports |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600 seconds | Meets parsing time requirements for large PDF and PPT files |
| `chunkSettingMode` | Manual configuration | Adjusts chunking rules for specific fields in operational documents, avoids accidental splitting of critical parameters |

## Three common mistakes
- Symptom: PPT or PDF document sync fails, interface displays sync error. Cause: `customPdfParse` configuration is not enabled. Basic parsing cannot support scanned documents or complexly formatted PPTs used in operational scenarios.
- Symptom: After deploying the v2 marker version, logs show an ocr error. Cause: OCR enhanced mode is not configured, or the resolution of the uploaded document is lower than the parsing requirements, resulting in text recognition failure.
- Symptom: After connecting the Claude 3.7 model, file parsing fails, while normal chat functions work normally. Cause: `chunkSettingMode` is set to automatic mode. Automatic splitting breaks the association between cluster ID and quota parameters in operational documents, causing the model to fail to recognize context.

## How to confirm the configuration is correct
- Upload a cluster change ticket PDF, check if the parsed text retains change time, cluster name and other key fields.
- Check the actual effective value of `PARSE_FILE_TIMEOUT_SECONDS`, confirm it matches the preset 600 seconds.
- Upload a PPT-format deployment record, verify that the parsed result contains complete slide content.
- Submit a cluster upgrade document larger than 500 MB, confirm the upload and parsing process does not trigger a timeout error.

The values listed here are common starting points, and should be evaluated against the reader's own samples.
