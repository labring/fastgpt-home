# Requirements and Design Document Drafting for Capacity Planning and Resource Scaling: Context and Token

## What does the data for this category look like?
Typical data for this category comes from cloud billing, monitoring systems, business forecast reports, and stress test results. Daily produced documents include capacity planning reports, expansion application forms, resource utilization reports, and budget calculation sheets. Most update frequencies are weekly or monthly. Document structures usually include current resource usage, peak load forecast data, expansion adjustment plans, and corresponding budget calculation content. Fields cover resource usage, peak load thresholds, applied resource specifications, procurement budget amounts, and more. There is no fixed unified format, and documents must match internal enterprise operation and maintenance documentation specifications.

## What constraints do these characteristics impose on the "context and token" link?
Data for this category comes from multiple dispersed sources with diverse fields. Integrating multi-source data generates significant token consumption, which places high requirements on context window capacity. Document update frequency is weekly or monthly, so frequent context refreshing is not needed, but stable storage of resource data and calculation results from historical cycles is required. The lack of unified document structure requires flexible adaptation to operation and maintenance documents in different formats, which increases the complexity of context extraction. At the same time, core content such as peak forecast and budget calculation must be retained first, so token quotas must be reasonably allocated to avoid truncation of key information.

## How to set the configurations?
These configurations are adapted for FastGPT v4.17.0, and adjusted for the operation and maintenance document scenario of this category:

| Configuration Item | Recommended Range | Rationale |
| ---- | ---- | ---- |
| Max context window | 8000–12000 token | Matches the integration requirements of weekly or monthly data for this category, and avoids truncation of core calculation content |
| Max reference token count | 3000–5000 token | Prioritizes retaining complete content of core data sources such as stress test reports and cloud billing |
| Context extraction threshold | 0.75–0.85 | Filters low-correlation historical resource data to reduce invalid token consumption |
| Historical data recall limit | Top 6 entries | Matches the update frequency of documents for this category, and avoids recalling excessive expired resource data |
| Chunk overlap length | 100–200 characters | Adapts to the paragraph structure of operation and maintenance documents, and reduces information loss during context splicing |
| Single search limit | Top 5 entries | Controls total context token consumption to avoid exceeding the single-round task limit of the platform |

## Three common configuration mistakes
- Issue: A "Reached the max retries" prompt appears during calls, and the number of context recall results is insufficient. Cause: The historical data recall limit is not set reasonably, leading to frequent retries to obtain data and exceeding the retry threshold.
- Issue: Budget calculation content is missing in the generated capacity planning report. Cause: A reasonable max reference token count is not set, leading to truncation of cloud billing and budget data.
- Issue: Token consumption exceeds expectations during multi-model orchestration. Cause: The max context window for single-round conversations is not limited, leading to repeated token resource occupation by each model.

## How to confirm configurations are correctly set
A typical capacity planning report document is imported, and core fields retained after context extraction are checked for completeness.
A multi-source data integration scenario is simulated, and total token consumption is checked against the preset max context window limit.
An expansion application form generation process is triggered, and the number of recalled historical data is confirmed to match the set recall limit.
The platform's token consumption statistics are viewed, and token usage of single-round tasks is confirmed to have no abnormal fluctuations.

Note: The configuration values listed are common starting points. Adjust them based on your own specific samples and scenarios.
