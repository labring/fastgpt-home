# Requirements and Design Document Drafting for Capacity Planning and Resource Scaling: Multi-turn Dialogue and Prompt Engineering
## What Data This Category Includes
The data for this category mainly comes from cloud service provider bills, infrastructure monitoring systems, business traffic forecast reports, and stress test results. Daily produced documents include capacity planning reports, scaling application forms, monthly resource utilization reports, and quarterly budget calculation sheets. Data update cycles are usually weekly or monthly. Core fields include resource type, current utilization, peak threshold, budget amount, and procurement cycle. Units are mostly cores, memory GB, storage TB, and currency units.

## What Constraints These Characteristics Impose on Multi-turn Dialogue and Prompt Engineering
Decentralized data sources and multiple field dimensions require multi-turn dialogue to sequentially guide collection of information from different data sources such as cloud bills, monitoring systems, and business forecasts. This avoids missing core parameters. Weekly or monthly update cycles mean dialogue must support calling previously generated document fragments as context, to reduce repeated data entry. Differences in units and types of core fields require prompt engineering to clearly specify standardized output formats, to adapt to statistical rules for different resource types. Errors directly affect production stability and budget control, so dialogue must add verification links to ensure parameters output in each round comply with business logic. FastGPT v4.17.0’s context management capability can adapt to multi-turn data call requirements for this scenario.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Context call scope | Previous 3 rounds of historical dialogue + current session documents | Focus on core context for current capacity planning, reduce interference from irrelevant information |
| `variables` | Predefined resource type, current utilization, peak threshold | Standardize business fields, reduce the number of multi-turn follow-up questions |
| Maximum context length | 8000–12000 token | Adapt to historical data and document fragments from multi-turn dialogue, avoid context overflow |
| Dialogue timeout duration | 600 seconds | Adapt to time spent on data query and document generation, avoid request timeout errors |
| Result verification switch | Enabled | Ensure output capacity parameters comply with business logic, reduce error probability |

## Three Common Misconfigurations
- Request timeout errors occur, with the interface displaying Request Time: The dialogue timeout duration is not set to match data query durations, causing the large model to time out while waiting for data returns when generating capacity planning documents.
- Historical context is lost during multi-turn dialogue: The `chatId`, `messages`, or `variables` parameters are not configured correctly, causing each dialogue to reset context and unable to continue previous discussions about capacity data.
- Output capacity parameters do not comply with business logic: The result verification switch is not enabled, causing generated scaling amounts to mismatch actual resource utilization, leading to subsequent resource waste or peak-hour failures.

## How to Confirm Configuration Is Complete
- Initiate an initial capacity planning query, such as “Please generate a current server resource utilization report based on cloud bill data”. Check if the dialogue can correctly accept subsequent supplementary questions and continue the previous discussion.
- Wait for the dialogue to complete, confirm no request timeout errors occur, verify that the timeout duration configuration is effective.
- Review the generated document, check if it includes core fields such as predefined resource types and utilization thresholds, verify that the variable configuration is correct.
- Manually modify the dialogue timeout duration to 30 seconds, initiate a test request, confirm that a timeout error is triggered, verify that the timeout configuration is effective.

The values provided here are common starting points, and should be validated against samples relevant to the specific deployment.
