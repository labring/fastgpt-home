# Requirements and Design Document Drafting for Ticket Acceptance and Issue Tiering: Context and Token

## What this category of data looks like
This category of data comes from ticketing systems, chat logs, product logs, and customer contract SLAs, with a daily or real-time update frequency. Documents generated daily include customer tickets, issue tiering tables, processing records, and service reports. Ticket fields include customer identifiers, problem descriptions, submission times, and priorities. Issue tiering tables include tiering rules and response time limit requirements. Processing records include assigned objects, processing progress, and results. This data focuses on customer feedback entry points, and does not involve regression verification links for product defects.

## What constraints these characteristics impose on the "context and token" link
Real-time ticket data updates require context to sync the latest customer feedback and processing progress. This avoids tiering errors caused by expired information.
Multi-source data including tickets, chat logs, and logs must be integrated into a unified context. Token consumption must be controlled to stay within model limits.
Issue tiering tables and SLA contracts are core reference materials. They must be included as fixed context fragments. Non-essential historical ticket token usage must also be restricted.
The real-time update feature requires context refresh frequency to match data update rhythm. A mismatch creates risk of response timeout or SLA violation.
Customer ticket field diversity may cause context length fluctuations. Token thresholds must be accurately configured to balance information completeness and call costs.

## How to set the configurations
| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| Maximum context length | 8000–12000 token | Matches the conventional token consumption after integrating tickets, chat logs, and tiering tables, avoids model truncation of core information, and adapts to the context processing logic of FastGPT v4.17.0 |
| Maximum reference token | 2000–3000 token | Limits the token usage of core reference documents such as issue tiering tables and SLA contracts, preventing coverage of real-time customer feedback content |
| Context refresh interval | 15–30 minutes | Matches the daily or real-time data update rhythm, balances synchronization costs and information timeliness |
| Historical ticket recall count | Top 3–5 entries | Only recalls historical processing records related to the current issue, controlling total context token consumption |
| Core document reference threshold | Calibrated via actual testing | Adapts to the document length of internal team issue tiering tables, ensuring core rules are fully loaded |
| Global context switch | Disabled | Avoids loading irrelevant historical session data when workflow nodes are called, aligning with the dedicated context requirements of ticket acceptance |

## Three common mistakes
- Unable to accurately count the model token consumption quantity for a single ticket acceptance process. The cause is that the context token statistics configuration is not enabled, resulting in the inability to obtain accurate consumption data.
- An error `AIPROXY_API_ENDPOINT or AIPROXY_API_TOKEN is not set` is prompted when starting context synchronization. The cause is that the environment variables `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` for the App/Admin server are not configured, causing startup verification to fail.
- Irrelevant global session context data is loaded when workflow nodes are called. The cause is that the global context synchronization switch is not disabled, resulting in historical information from non-current tickets being mixed in during node calls.

## How to confirm the configuration is complete
- View the context preview interface, confirm that the number of recalled historical tickets matches the preset top 3–5 entries.
- Test triggering the ticket acceptance process, check whether a token limit exceeded error occurs, and confirm that the context length meets the configuration requirements.
- Verify that core reference documents such as the issue tiering table are fully loaded into the context fragments and not truncated.
- Check the server environment variable configuration, confirm that `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are correctly configured with no empty values.

The values provided are common starting points and should be measured against the reader's own samples.
