# Requirements and Design Document Drafting for Ticket Acceptance and Issue Triage: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Data for this category originates from ticketing systems, chat logs, product logs, and customer contract SLAs, with updates occurring daily or in real time. Daily deliverables include customer tickets, issue triage tables, processing records, and service reports. Ticket fields include customer identifiers, request content, submission timestamps, and triage tags. Issue triage tables include priority, impact scope, and responsible team fields. Data is generated from customer feedback entry points, focusing on the full end-to-end process of request routing and service fulfillment.

## What constraints these characteristics impose on the multi-turn dialogue and prompt engineering link
Decentralized, real-time updated data sources require multi-turn dialogue to associate with historical dialogue and processing records for the corresponding ticket, to avoid loading irrelevant context. The fixed field structure of tickets and triage tables requires prompts to clearly define field extraction rules, preventing omission of key business information such as priority and impact scope. The high update frequency means dialogue context must be properly truncated to avoid response timeouts caused by loading excessive historical data. Additionally, the response time limit specified in the customer SLA must be aligned, limiting single-round dialogue processing duration to prevent response timeouts that trigger contract breaches. The design of starting from customer feedback entry points requires multi-turn dialogue to prioritize handling initial requests, without requiring navigation to other data source entry points.

The following configurations are based on FastGPT v4.17.0.

## How to set the configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` association rule | Bind the unique identifier of the current ticket | Must accurately load historical dialogue and processing records of the corresponding ticket to avoid context confusion |
| `variables` binding scope | Bind customer SLA level and impact scope field variables | Must automatically bring service agreements and current problem impact attributes into the prompt |
| `messages` context truncation rule | Retain the most recent 15 interaction records or the first 1200 tokens, calibrated based on actual testing | Balances historical reference value and response speed, adapting to real-time updated chat log data |
| Single-round response timeout threshold | 60 seconds | Aligns with the response time limit requirements of customer service SLAs to prevent contract breaches |
| Prompt field mapping rule | Extract ticket request content and triage tag fields | Matches the fixed field structure of documents in this category, ensuring extracted information complies with business specifications |

## Three Common Misconfigurations
- Multi-turn dialogue fails to load global variables saved in historical dialogue, with variable fields showing as empty in the interface. This occurs when the `chatId` binding for the unique ticket identifier is not correctly configured, preventing the system from matching variable storage for the corresponding context.
- Calling the MySQL tool returns a 400 status code with no response body. This happens when necessary database connection parameters are not configured in `variables`, or when parameter formats do not comply with system validation rules.
- Unable to switch AI models or add internet access functionality in multi-turn dialogue. This is caused by not enabling model switching and tool call permissions in the configuration, so the system cannot load context parameters for the intended functions.

## How to Confirm the Configuration is Correct
- Manually enter the unique identifier of a test ticket to confirm the system can load historical dialogue records and bound global variables for the corresponding ticket.
- Initiate a simulated customer request to verify that the prompt correctly extracts ticket triage tags and impact scope fields.
- After configuring tool call parameters, send a test request to confirm the returned response body has no abnormal status codes.
- Trigger the conversation end process to validate that the system clears dialogue context data associated with the current ticket.
