# Requirements and Design Document Drafting for Delivery Effect Optimization: Multi-turn Dialogue and Prompt Engineering

## What the Data for This Category Looks Like
The data for this category primarily comes from four sources: advertising platform backends, attribution systems, CRM lead databases, and landing page statistics tools.
Daily associated documents include daily delivery reports, weekly optimization reports, real-time price adjustment records, material A/B test ledgers, and effect review reports.
Data updates occur daily or in real time.
Fields include impressions, clicks, cost per conversion, remaining budget, and others.
Units include yuan, times, and cost per thousand impressions (CPM), among others.
The number of fields per document fluctuates based on delivery volume.

## What Constraints These Data Characteristics Impose on Multi-turn Dialogue and Prompt Engineering
Decentralized data sources and high real-time requirements require multi-turn dialogue to continuously synchronize the latest delivery data snapshots.
The `messages` context must limit the valid data window. This prevents old data from interfering with current analysis.
Daily document formats are inconsistent. Field differences exist between price adjustment records and test ledgers.
Prompts must predefine field mapping rules. This reduces the overhead of format correction during dialogue.
The real-time update feature requires `variables` to bind to real-time data interfaces. This avoids calls to outdated offline data.
Anomaly indicator localization in delivery scenarios needs rapid retrospective of historical queries.
`chatId` must bind to the complete conversation chain for a single delivery optimization. This supports subsequent effect reviews.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Context window length | Previous 8 turns of dialogue + most recent 24 hours of delivery data snapshots | Matches real-time analysis needs for delivery effect optimization, avoids response delays caused by overly long context |
| `variables` bound data source | Advertising platform API, attribution system real-time interface | Ensures data called during dialogue is synchronized with current delivery status |
| Prompt field mapping rules | Impressions → impression count, conversion cost → CPA | Unifies field descriptions in daily documents, reduces format ambiguity |
| `chatId` conversation binding rule | Binds to the unique identifier of a single delivery account | Facilitates retrospective of multi-turn adjustment records under the same scenario |
| Maximum response tokens per dialogue | 1500–2000 tokens | Covers core analysis content of a single daily delivery report, avoids truncation of key conclusions |
| Knowledge base recall limit | Top 6 historical optimization records | Matches the reference range for daily reviews, reduces interference from redundant information |

## Three Common Misconfigurations
- Uploading local delivery documents during dialogue cannot be read, but file uploads via the knowledge base work normally. The cause is that the file parsing permission for the dialogue scenario is not bound to the corresponding storage path, and only the knowledge base-exclusive file upload directory is open.
- Knowledge base retrieval returns empty results during dialogue, but works normally when tested in the knowledge base backend. The cause is that the real-time data interface bound to `variables` has not updated the retrieval data source range, causing the dialogue context to filter matching content.
- Dialogue request returns 404 Invalid URL (POST /api/chat/completions). The cause is that in FastGPT v4.17.0, the session routing rule for `chatId` is not configured correctly, causing the request to not point to the correct chat interface path.

## How to Verify Proper Configuration
- Initiate a dialogue containing a query for historical delivery data, verify that the `messages` context only includes valid turns of the current session and the latest data snapshots.
- Call the real-time interface bound to `variables`, confirm that the delivery data returned during dialogue matches the real-time values in the advertising platform backend.
- Upload a local price adjustment record document to the dialogue window, confirm that the document can be parsed normally and field information can be extracted.
- Check that `chatId` is bound to the unique identifier of the current delivery account, ensuring that multi-turn dialogue under the same scenario can be uniformly associated.

The values provided here are common starting points, and should be measured against the reader’s own samples.
