# Requirements and Design Document Drafting for Tender Document Preparation: Multi-turn Dialogue and Prompt Engineering

## What data looks like for this category
Data sources for this category include tender announcements, tender documents, enterprise qualification databases, and supplier quotations. The update frequency is per project. Daily output documents include tender documents, qualification certificates, commercial deviation tables, and technical deviation tables. Fields cover qualification requirements specified in tenders, commercial clause responses, and technical scheme matching items. No custom exclusive fields are used; only fields and units specified by the tenderer are retained. The size of a single dataset varies with the scale of the tender project.

## What constraints do these characteristics impose on the multi-turn dialogue and prompt engineering link
Since data sources are exclusive announcements and documents for a single tender, each project’s data is independent and its format changes dynamically based on the tenderer’s requirements. Multi-turn dialogue must strictly retain the exclusive context of the current tender to avoid confusion with past project data. Item-by-item responses for commercial and technical deviation tables require multi-turn prompts to gradually break down clauses, ensuring each item accurately matches tender requirements. Verification of enterprise qualification databases requires calling preset variables to associate corresponding qualification information, and confirming the validity of qualification items during multi-turn sessions to prevent bid invalidation caused by misplaced information. A single session must be limited to the scope of the current tender project to avoid introducing irrelevant data that interferes with response accuracy.

## How to set configurations
This configuration rule is compatible with FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique identifier of the current tender project | Isolate session data from different tender projects to avoid context reuse |
| `messages` | Retain complete session records, with a limit of 10 turns | Cover the clause response and qualification verification process for a single tender document, support retrospective corrections |
| `variables` | Inject tender document fragments and qualification database entries | Provide exclusive business data for prompts to ensure responses match tender requirements |
| Maximum context length | First 8000–12000 characters | Adapt to the full document length of a single tender project, prevent truncation of key response clauses |
| Timeout period | 600 seconds | Adapt to complex qualification verification and clause breakdown tasks, avoid session termination mid-process |
| Prompt triggering rule | Call item by item based on the current tender item | Ensure each round of prompts only processes a single clause, improving response accuracy |

## Three common mistakes
- Phenomenon: Session return results contain debug logs or irrelevant conversation content, and core response fields are empty. Cause: Filtering rules for the `messages` parameter were not configured correctly, including intermediate outputs from the debugging phase in the final response context.
- Phenomenon: Sessions time out and interrupt, returning a timeout status code. Cause: A reasonable timeout period was not set, or the `variables` parameter injected overly large tender document fragments, causing processing time to exceed the preset threshold.
- Phenomenon: Context reuse across tender projects, with qualification information or clauses from past projects appearing. Cause: The unique `chatId` for the current tender project was not bound, causing session data from different projects to be shared.

## How to confirm the configuration is correct
- Run a test session, input a response request for a single tender clause, and verify the returned result only contains compliant response content for the current clause, with no irrelevant logs or redundant information.
- Check the `chatId` parameter of the session, confirm it matches the unique identifier of the current test tender project, with no residual session data from cross-project use.
- Call the tender fragments injected via the `variables` parameter, verify the prompt template contains exclusive clauses for the current tender, with no redundant information from past projects.
- Set the timeout period to 600 seconds, run a test including multi-round clause verification, confirm the session does not interrupt mid-process, and complete the full process response.

Note: The values provided here are common starting points and should be evaluated against local samples.
