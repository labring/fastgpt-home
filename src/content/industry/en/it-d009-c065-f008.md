# Drafting Requirements and Design Documents for Interface Integration and Data Docking: Workflow Orchestration

## What the data for this category looks like
This category of data primarily originates from customer system interfaces, API documentation, test data, and integration logs. Its update frequency is daily or per project phase. Daily produced documents include interface inventory, integration records, field mapping tables, and issue tracking tables. The interface inventory marks interface addresses, request methods, and parameter rules. The field mapping tables clarify the correspondence between source fields and target fields. The integration logs record the timing and status of each call. The issue tracking tables retain full process records of exception troubleshooting and repair. This document is written based on FastGPT v4.17.0.

## What constraints these characteristics impose on the "workflow orchestration" link
Scattered data sources with inconsistent update cycles require workflows to adapt to different data pull timings, to avoid field caliber deviations caused by unsynced data. Multi-type document flow requires workflows to support sequential and parallel execution of different nodes. For example, pull the interface inventory first, then generate the field mapping table. Pre-validation is needed for the field caliber confirmation step, to prevent data mismatches in subsequent integration. The high impact of interface errors requires workflows to include built-in exception capture and retry mechanisms, to trigger automatic alerts when workflows are interrupted.

## How to set the configurations
| Configuration Item | Suggested Practice | Basis for This Setting |
| --- | --- | --- |
| Variable Configuration | Define interface addresses, authentication headers, and field mapping rules in `variables`, using official interface addresses and standard authentication formats provided by the customer | Ensure all interface nodes use unified parameter configurations, to avoid call failures caused by inconsistent parameters |
| Node Identification | Assign a unique `nodeId` to each interface node, using a 32-digit random string | Prevent execution conflicts from duplicate node IDs, ensure workflow nodes can be accurately identified and called |
| Trigger Timing | Trigger per integration phase, using "after requirements review is passed, 1 day before integration" | Match the actual project progress rhythm, avoid data redundancy from early or delayed execution |
| Exception Capture Strategy | Capture HTTP status code exceptions, using 4xx and 5xx status codes, automatically retry 3 times with a 60-second interval | Cover common interface call exceptions, the retry mechanism mitigates the impact of temporary network fluctuations |
| Log Synchronization Node | Define the parameter for the number of logs to retain in `variables`, retain the most recent 100 entries, synchronize to the knowledge base at a daily update frequency | Ensure integration data in the knowledge base is up-to-date and controllable, avoid redundant data occupying storage resources |

## Three Common Mistakes
- Workflow execution leads to out-of-sequence interface calls. The symptom is that the return order in integration logs does not match the actual call order. The cause is that node execution order is not configured according to call timing, leading to chaotic log recording.
- The workflow works normally in the knowledge base search step, but does not reference integration records in the AI chat step. The symptom is that the chat response results do not include interface field mapping content. The cause is that the knowledge base node for integration records is not correctly associated with the chat node.
- Workflow runs and returns empty fields. The symptom is that target fields are missing from the interface call return results. The cause is that field mapping rules are not configured in `variables`, causing the LLM to fail to recognize field correspondence.

## How to Verify Proper Configuration
- Review the `variables` configuration items, check that all interface parameters match the API documentation provided by the customer.
- Check the `nodeId` configuration, confirm that each node's identifier is unique and has no duplicates.
- Trigger a test run, verify that the exception capture node can correctly capture preset HTTP status code exceptions.
- Check the log synchronization node, confirm that the update frequency of integration logs matches the project phase.
