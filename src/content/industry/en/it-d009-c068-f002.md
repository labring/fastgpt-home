# Requirements and Design Document Drafting for Database Cloud Service Operations: Context and Token
This document is written based on FastGPT v4.17.0.

## What Data for This Category Looks Like
Data for this category primarily comes from cloud database consoles, slow query logs, performance monitoring metrics, and ticketing systems. Daily produced documents include instance change orders, backup and recovery records, performance diagnosis reports, and parameter adjustment records.
Data updates are triggered by changes or occur on a daily basis. Individual document lengths vary widely, ranging from hundreds of characters in parameter adjustment records to tens of thousands of characters in slow SQL troubleshooting reports.
Some fields are associated with multi-tenant instance identifiers. Strict separation of operational data boundaries across different customers is required.

## How These Data Characteristics Impact Context and Token Processing
These data characteristics impose multiple constraints on context and token handling.
First, document lengths vary widely, from hundreds to tens of thousands of characters. Direct concatenation will quickly exceed token limits.
Second, data such as slow query logs and performance diagnosis reports contain large amounts of structured and semi-structured content, with high token density. Effective content retrieved in a single pass will quickly consume available quotas.
Third, multi-tenant instance identifiers require contexts to be strictly bound to corresponding operational instances. Concatenating contexts across instances will cause data confusion and increase token usage.
Finally, frequently updated operational data requires contexts to pull the latest records in real time. A balance must be struck between retrieval efficiency and token consumption.

## Recommended Configuration Values
| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the average total length of cloud database operational documents, avoiding single context concatenation exceeding model limits |
| `quoteMaxToken` | 1500–2000 token | Matches the typical fragment length of individual operational documents, preventing single references from occupying excessive context quota |
| Single search reference upper limit | Top 6 entries | Corresponds to the average number of retrieved documents in daily operations, balancing information completeness and token consumption |
| Context instance binding switch | Enabled | Strictly isolates multi-tenant operational data, avoiding cross-instance token confusion |
| Real-time data retrieval interval | 10–30 minutes | Matches the update frequency of operational data, balancing real-time performance and system load |

## Three Common Configuration Mistakes
- Scenario: After setting `quoteMaxToken` to 2000, the total token count of system responses still exceeds 3000, and logs show that the total token count from context concatenation exceeds the limit. Cause: Cumulative token usage from multiple references is not accounted for, and the total quota for `maxContext` is not adjusted synchronously.
- Scenario: Operational context from the previous round cannot be retained in continuous conversations, and each response requires re-asking basic information. Cause: The instance binding switch is not enabled, or the quota for `maxContext` is set too small, causing the previous round's context to be automatically truncated.
- Scenario: After importing slow SQL logs, the system automatically splits the content, causing critical SQL statements to be truncated and preventing complete performance troubleshooting. Cause: Reasonable context truncation rules are not configured for long-text operational documents, and the default splitting logic does not retain complete SQL code blocks.

## How to Verify Proper Configuration
- Import a typical instance change order, trigger context retrieval, and check the system's returned token count to confirm that the total token count does not exceed the configured `maxContext` value.
- Initiate a continuous conversation, sequentially ask questions about parameter adjustments and backup recovery for the same instance, and check whether each response is associated with context information from the previous round.
- View the `quoteMaxToken` configuration, test the token count of a single reference fragment, and confirm that it does not exceed the set quota.
- Import operational data from two different tenants, initiate a cross-tenant query request, and check whether the system correctly isolates data and does not show cross-tenant context confusion.

The values provided are common starting points and should be measured against the reader's own samples.
