# Drafting Requirements and Design Documents for Database Cloud Service Operations: Workflow Orchestration

## What Data for This Category Looks Like
This category of data mainly comes from cloud database consoles, slow logs, monitoring metrics, and ticketing systems. Daily produced documents include instance change orders, backup and recovery records, performance diagnosis reports, and parameter adjustment records. Each document contains fields such as instance unique identifier, change time, operation type, and associated resource ID. Data is updated daily or each time a change operation is completed. Fields across different documents cover cloud product console permissions, tenant boundary information, and operation and maintenance details.

## Constraints Imposed on Workflow Orchestration by These Characteristics
Because data sources are scattered and include multiple heterogeneous sources such as cloud consoles and slow logs, workflow orchestration must support multiple nodes connecting to different data sources in sequence, and pass cross-node instance identification parameters via `variables`. Data updates do not have a fixed scheduled cycle, so workflow orchestration must be configured to start via event triggers. Documents contain tenant boundary and permission fields, so tenant permissions corresponding to `nodeId` must be verified during orchestration to avoid cross-tenant operations. Time-consuming steps such as slow SQL locating and backup recovery must execute tools serially, to prevent monitoring metric collection conflicts or data inconsistency caused by parallel calls.

## Configuration Specifications
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | Event trigger (instance change / slow log alert) | Matches the characteristic of non-fixed data update cycles, avoids invalid polling |
| Node Execution Order | Execute sequentially according to the configured node sequence | Ensures steps such as slow SQL locating and backup verification run serially, avoids resource conflicts |
| `variables` Parameter Configuration | Pass instance ID, tenant identifier | Unifies core identification parameters across nodes, ensures accurate data association |
| `nodeId` Permission Verification | Bind the current tenant's cloud console permissions | Meets multi-tenant boundary requirements for cloud service operations, prevents unauthorized operations |
| Timeout Threshold | 600 seconds | Covers the longest time-consuming scenarios such as backup recovery and performance diagnosis |
| Retry Count | 2 times | Addresses temporary cloud API call failures, avoids workflow termination from a single failure |
| Single Retry Interval | 30 seconds | Prevents frequent retries in a short period from occupying cloud service resources |
| Batch Processing Limit | Top 10 entries | Matches the conventional number of single-batch operation and maintenance operations |

## Three Common Misconfigurations
- Tools in the workflow are not executed in order, and some tools have no call records. This occurs because node execution order is not configured, or execution dependency parameters passed via `variables` are not correctly bound, leading to parallel tool calls.
- After deployment, the workflow and knowledge base configuration is blank, but the interface can be called normally. This occurs because locally stored configuration files are not correctly mounted, or persistent workflow orchestration data is not loaded after container restart.
- Variable references are invalid when selecting a knowledge base, returning empty results. This occurs because context passing for `variables` is not configured in workflow nodes, leading to variables not being correctly replaced with actual instance information.

## How to Verify Correct Configuration
- Manually trigger an instance change event, check whether workflow logs call all tool nodes in the configured order.
- View the permission verification log corresponding to `nodeId`, confirm that only instances from the current tenant can be associated with the workflow.
- Submit a slow SQL locating task, check whether the instance ID passed via `variables` matches the actual queried instance.
- Simulate a cloud API call failure scenario, confirm that the workflow triggers the retry mechanism and does not terminate execution directly.

The values provided are common starting points and should be measured against the reader's own samples.
