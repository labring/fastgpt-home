# Requirements and Design Document Drafting for Database Cloud Service Operations: Forms and Interactions

## What Data for This Category Consists Of
Daily documents for database cloud service operations include instance change tickets, backup and recovery records, performance diagnosis reports, and parameter adjustment records. Data sources are cloud database consoles, slow logs, monitoring metrics, and ticket systems. Update frequency is daily or after each change. Document fields include instance ID, slow SQL latency, backup file size, parameter names and corresponding values. Units include milliseconds, GB, days, and more. Required fields vary across different documents.

## Constraints on Forms and Interactions
Dispersed data sources require pulling pre-filled fields from multiple systems via external business systems to avoid duplicate data entry. Irregular update frequencies require dynamic adjustment of form field status via external business systems to accommodate ad-hoc change requests. Wide variation in document fields requires switching between multiple templates via external business systems to match different business scenarios. Multi-tenant attributes require distinguishing form permission scopes via external business systems, only displaying instance data accessible to the current tenant. Severe consequences of operational errors require implementing validation logic linkage via external business systems to reduce omission of core information.

## Three Common Mistakes
- Phenomenon: The system prompts unsupported format after file upload, and the file cannot be recognized. Cause: The allowed file format range is not configured in the external business system, and only limited formats are enabled, resulting in logs or screenshots required for operation and maintenance not being recognized.
- Phenomenon: An empty error is returned after submitting a ticket, and no specific missing field information is prompted. Cause: Required validation and format validation logic for fields related to the `formInput` node are not configured in the external business system or subsequent nodes, resulting in exceptions triggered after empty value submission.
- Phenomenon: Multi-layer branch interactions repeatedly ask the same question, and cannot correctly jump to subsequent business links. Cause: Accurate instance status trigger conditions are not configured in subsequent workflow branches, resulting in branch logic not correctly matching the business scenario entered by the user.

## How to Confirm Configuration Is Complete
- Check whether the input restrictions and required validation configurations of the `formInput` node in the external business system meet the requirements.
- Test the file upload function of the external business system, upload test files of different formats, and confirm that the supported format range matches the preset requirements.
- Simulate the multi-layer branch interaction process of subsequent workflows, select different instance running statuses, and confirm that the subsequent pop-up questions conform to business logic.
- Submit a test ticket, and verify whether the external business system can correctly obtain and validate the format and integrity of core fields such as uid and order number.
