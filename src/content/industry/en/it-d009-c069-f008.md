# Drafting Requirements and Design Documents for Database Operations: Workflow Orchestration
This document is compatible with FastGPT v4.17.0.

## What Data for This Category Looks Like
Data for this category primarily comes from database monitoring systems, operation audit logs, SQL execution plan files, and internal operation work order systems. Daily produced documents include database change tickets, slow SQL analysis reports, backup and recovery records, permission application forms, and more. Change tickets contain fields such as instance ID, change time, and executed SQL. Slow SQL reports record metrics including query latency, scanned rows, and resource usage. Data updates occur daily or whenever a database change operation takes place.

## What Constraints Do These Characteristics Impose on the "Workflow Orchestration" Link
Scattered data sources with inconsistent formats require workflow orchestration to support parallel pulling of operation and maintenance data from different sources. Data update frequency changes dynamically alongside change operations, so on-demand workflow trigger rules must be configured. Numerous document fields with strong business correlation require variable configuration to achieve precise transfer and reuse of fields. Errors may lead to data corruption or permission oversteps, so failure rollback and alert nodes must be added to workflows. Unlike backup and recovery scenarios, this category focuses on daily performance and permission management, so workflows must adapt to dedicated operation and maintenance links such as permission verification and slow query locating.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Map work order fields to instance ID, SQL statement, change time | Match core fields of database change tickets to enable precise data transfer between workflow nodes |
| `nodeId` | Bind IDs of slow SQL analysis nodes and permission verification nodes | Precisely control execution dependencies and order of workflow nodes to ensure processes advance in line with operation and maintenance logic |
| Question Optimization | Enabled, associated with historical context | Resolve coreference resolution issues in database operation and maintenance scenarios, simplify association matching for abbreviations such as instance IDs |
| Single Search Limit | Top 10 entries | Match the standard return volume of slow SQL reports to avoid workflow processing overload |
| Timeout Setting | 600 seconds | Adapt to the standard generation duration of SQL execution plans to prevent workflow interruptions due to excessive waiting |
| Global Variables | Bind default backup path of database instances | Reuse fixed configurations in operation and maintenance scenarios to reduce repetitive data entry operations |

## Three Common Mistakes
- Debug nodes cannot stop running: After clicking the stop debug button, the node status still shows running. This occurs because the `nodeId` parameter is not correctly bound to the target debug node, causing the system to fail to identify the process segment to terminate.
- Workflows only return single model results: Only the output of the last conversation node is displayed, and results from previous steps are not retained. This is because the `variables` configuration is not used to transfer processing results from preceding nodes, leading to intermediate data not being cached.
- Knowledge base search cannot resolve coreferences: Abbreviated database instance names in historical conversations cannot be correctly mapped to full IDs. This is because the Question Optimization configuration is not enabled, and historical context is not associated to optimize current search keywords.

## How to Confirm Proper Configuration
- Manually trigger a test workflow, check in the node logs whether the `variables` parameter carries core fields of the database change ticket correctly to verify normal data transfer.
- Enable workflow debug mode, locate the target debug node via `nodeId`, click the stop button to verify whether the debug termination function works.
- Submit a test case containing historical conversations, check whether knowledge base search results correctly associate previously mentioned database instances to verify whether the Question Optimization configuration takes effect.
- Review the workflow timeout setting, confirm that the 600-second threshold matches the current SQL execution plan generation duration to avoid unnecessary timeout interruptions.

The values provided here are common starting points and should be measured against the reader's own samples.
