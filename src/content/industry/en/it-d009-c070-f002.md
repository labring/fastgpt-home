# Requirements and Design Document Drafting for Data Cleaning and Quality Inspection: Context and Token

## What this category of data looks like
This category of data comes from raw datasets, ETL logs, annotation platforms, and sampling results. Update frequency is daily or per batch. Daily produced documents include cleaning rules, quality inspection sampling tables, abnormal data lists, and delivery reports. Fields cover data identifiers, anomaly types, processing status, sampling results, and similar items. There are no dedicated units. Data volume varies with business batches.

## Constraints on context and token handling from these characteristics
Raw dataset volume fluctuates with business batches. The context window must be sized to accommodate multi-batch data association information. High-frequency updates of ETL logs and sampling results require the context to load the latest verification records in real time. Documents such as cleaning rules and abnormal data lists have high field complexity, which increases the token consumption of a single context. The daily or per-batch update rhythm requires avoiding validation logic failure caused by expired context cache. The error consequences of unavailable data require reserving redundant space in token configuration to prevent loss of key quality inspection basis due to context truncation.

## Configuring context and token parameters
In FastGPT v4.17.0, adjust context and token related parameters via configuration items such as `maxContext` and `quoteMaxToken`. The specific recommended configurations are as follows:

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Data volume of this category fluctuates with business batches, so it is necessary to accommodate multi-batch association information and abnormal records, and reserve redundancy to avoid context truncation |
| `quoteMaxToken` | 1500–2000 token | Documents such as cleaning rules and abnormal data lists have high field complexity, so it is necessary to fully load key verification basis |
| Context cache validity period | 6–12 hours | The update frequency of data in this category is daily or per batch. The cache duration matches the update rhythm to avoid expiration and failure |
| Single batch data loading limit | Top 1000 entries | Core data for duplicate data identification and outlier processing is concentrated in the pre-sequenced samples of a single batch. Loading too much will increase token consumption |
| Abnormal data associated recall count | Calibrated through actual testing | The sampling quality inspection link needs to cover the associated information of abnormal samples to avoid missing key verification items |

## Three common configuration errors
- Phenomenon: An "context token limit exceeded" error pops up in the interface, or the output result is truncated. Cause: The `maxContext` configuration does not reserve a sufficient context window, leading to truncation of key abnormal records or cleaning rules.
- Phenomenon: Quality inspection results are inconsistent across runs, and the abnormal data list loads as empty. Cause: The context cache validity period is set too short, which does not match the daily or per-batch data update rhythm of this category, resulting in the latest verification records not being loaded.
- Phenomenon: Token consumption statistics do not match actual business conditions, with abnormal differences between input and output token counts. Cause: Associated data sources such as ETL logs and sampling results are not included in the context statistics scope, resulting in statistical values deviating from actual conditions.

## How to verify correct configuration
- Import a single batch of typical raw datasets, and verify that the fields loaded by the context cover the core content of cleaning rules and abnormal data lists.
- Simulate daily or per-batch data updates, and check whether the context cache automatically loads the latest sampling results and ETL logs.
- Run duplicate data identification and outlier processing tasks, and confirm that the output results include complete associated verification basis.
- View the token consumption statistics panel, and verify that the statistics scope includes all associated data sources of this category.

The values provided are common starting points and should be validated against samples relevant to the deployment use case.
