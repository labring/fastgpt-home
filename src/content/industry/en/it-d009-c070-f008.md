# Requirements and Design Document Drafting for Data Cleaning and Quality Inspection: Workflow Orchestration

## What this category of data looks like
The primary users of this category are data engineers, quality inspectors, and project managers. Data sources include raw datasets, ETL operation logs, annotation platform output results, and sampling quality inspection results. Update frequency is daily or per processing batch. Daily delivered documents include standardized cleaning rules, quality inspection sampling tables, abnormal data lists, and delivery reports. Fields cover data identifiers, anomaly types, processing status, sampling quantity, and processing dates. Units are mostly items, times, and date formats. Multiple rounds of intermediate results are generated during data processing, which must be saved per batch to support traceability and verification.

## What constraints do these characteristics impose on the workflow orchestration link
Decentralized data sources and batch-based updates require workflows to support multi-source data pulling and batch trigger configuration, and adapt to daily or per-processing-batch update rhythms. Daily delivered documents have fixed structures, so standardized document generation nodes must be embedded in workflows to automatically match fields such as cleaning rules and abnormal lists. Duplicate data identification and abnormal value processing are the most time-consuming links, so parallel processing nodes must be configured to optimize overall processing time. Data anomalies directly lead to delivery rejection, so workflows must include abnormal data verification and status rollback nodes to ensure that each step of processing results can be traced.

## How to set configurations
This document is written based on the workflow functions of FastGPT v4.17.0. Specific configuration items and their bases are as follows:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Workflow trigger mode | Batch trigger / Daily scheduled trigger | Matches the batch or daily update frequency of source data |
| Number of parallel processing nodes | 3 parallel nodes | Covers the core time-consuming links: duplicate data identification, abnormal value processing, and sampling quality inspection |
| Variable field binding | Bind cleaning rules and abnormal list fields in `variables` | Matches the fixed field structure of daily documents |
| Node ID binding | Bind target nodes corresponding to `nodeId` | Ensures accurate call identifiers for each link in the workflow |
| Anomaly verification trigger condition | Calibrated based on actual testing | Adapts to anomaly data tolerance levels for different business scenarios |
| Node timeout setting | 600 seconds | Adapts to the pulling and processing time of raw datasets and ETL logs |

## Three common mistakes
- Phenomenon: Retrieval results returned by HTTP requests in the workflow cannot be correctly passed to AI chat nodes. AI references data with empty fields displayed. Cause: No mapping field for retrieval results is configured in `variables`, so data transfer between nodes is not bound to corresponding parameters.
- Phenomenon: Workflow runs timeout, with status code 504 displayed. Cause: No reasonable node timeout time is set, and timeout configuration is not adjusted for time-consuming links such as ETL log pulling.
- Phenomenon: Generated delivery reports have missing fields and do not match the daily document structure. Cause: Corresponding fields in `variables` are not bound, and the document generation node does not match preset fields such as cleaning rules and abnormal lists.

## How to confirm the configuration is correct
- Trigger a test batch workflow, check the running logs of each node, confirm that the multi-source data pulling link can normally obtain raw datasets, ETL logs, and sampling results.
- View the output of the document generation node, confirm that the generated document includes preset fields such as cleaning rules and abnormal data lists, and matches the daily document structure.
- Simulate an abnormal data scenario, trigger the anomaly verification node, confirm that the rollback logic is normally triggered and meets the tolerance requirements of the business scenario.
- Check the node timeout settings, confirm that the timeout time for time-consuming links has been adjusted according to the business scenario.

The values provided are common starting points and should be measured against the reader's own samples.
