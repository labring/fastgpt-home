# Requirements and Design Document Drafting for Data Masking Processing: Context and Token

## What Data in This Category Looks Like
Data for this category originates from business databases, data dictionaries, in-house masking tools, and access approval systems. Four core document types are produced regularly: masking plans, field mapping tables, masking validation reports, and approval records.
Data updates are conducted on a per-project or per-batch basis, with no fixed schedule. Document fields include sensitive field identifiers, masking rule types, execution scope, validation results, and approval nodes. No unified fixed units are used; values are adjusted based on project scenarios.
Data processing requires linking metadata and approval flow information across multiple systems. Overall data volume fluctuates based on project complexity.

## Constraints Imposed on Context and Token Handling
Documents in this category are mostly structured compliance content. Single-batch data volume fluctuates significantly. Linking metadata across multiple systems makes it difficult to standardize the effective content share of context windows.
Sensitive field identification and masking rule configuration require repeated calls to field mapping tables and validation records from historical projects. If the context window is too small, associated historical configuration information cannot be retrieved, reducing rule configuration efficiency.
Data updates follow a project-based workflow. Each new task must reload the current project’s masking rules and approval nodes. If token quota is insufficient, the full configuration documents for the current project cannot be loaded, leading to masking task interruptions.
Compliance audit requirements mandate retaining complete context association records. If token limits cause partial historical validation reports to be lost, compliance audits cannot be completed successfully.

## Configuration Settings
FastGPT v4.17.0 supports the following adjustments to context and token configuration items:

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `maxContext` | First 3–8 historical project records | This category of data is updated per project. Each project has a limited number of associated historical records, so loading excessive irrelevant batch data is unnecessary |
| `maxContext` | Per-project dedicated context pool | Separates context data for different projects to prevent cross-project sensitive information leaks |
| `quoteMaxToken` | 800–1200 token | Single core documents such as masking plans and field mapping tables mostly fall within this length range, allowing full loading of key content |
| Context recall limit | Calibrated based on actual testing | Must be adjusted based on the total number of documents for a single project to avoid retrieving excessive non-associated historical approval records |
| Association matching threshold | 0.75 (adjusted per project scenario) | Used to filter historical field mapping records strongly associated with the current masking task, filtering out redundant data |

## Three Common Misconfigurations
- The `maxContext` setting for AI nodes is set to 30 records, but only 2 context entries appear in conversation details. Historical masking configuration cannot be associated. The cause is incorrect association matching threshold configuration. The system filters most non-associated historical masking documents, resulting in valid context being truncated.
- A task execution prompt indicates that context token count exceeds the limit, and complete masking plan documents cannot be loaded. The cause is an overly small `quoteMaxToken` setting, which does not cover the length of a single core masking plan document, leading to loading failure.
- Long-running masking tasks time out and show a failed status. The cause is failure to adjust the task timeout threshold. The default threshold cannot cover the associated context loading and validation process for multi-batch data.

## How to Verify Proper Configuration
- Review the masking plan documents for the current project to confirm that loaded content has the expected level of completeness, with no critical fields missing.
- Test calls to field mapping tables from historical projects to confirm that the system can retrieve records strongly associated with the current task.
- Submit a small-batch test task to observe whether task execution duration matches the preset timeout threshold, with no interruptions.
- Check context association logs to confirm that only historical records related to the current project are loaded, with no redundant data included.
