# Drafting Requirements and Design Documents for Data Masking: Workflow Orchestration

## What this category of data looks like
Data for this category is generated across the full data masking workflow, with main sources including enterprise databases, data dictionaries, commercial masking tools, and access approval systems. Standardized documents produced regularly include masking plans, field mapping tables, masking validation reports, and approval records, which are updated per batch project or single task. Data fields include sensitive field identifiers, masking rule types, validation pass rates, approval status, and more. There are no unified fixed units; values adjust based on project scenarios.

## What constraints do these characteristics impose on the workflow orchestration link
Since data is updated per project batch, the workflow must support dynamically binding data sources and document templates by project to avoid cross-project data confusion. Sensitive field recognition and masking rule configuration require pre-verification. The workflow must embed a field compliance check node to prevent unrecognized sensitive fields from entering the process. Masking validation reports and approval records must be mandatory retention nodes as workflow outputs to meet subsequent compliance audit requirements. Data from multiple sources must be unified in format within the workflow to adapt to document structures exported by different tools, avoiding data parsing failures.

## How to set configurations
This document is written based on FastGPT v4.17.0.

| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| Global variable `variables` | Preset sensitive field list and masking rule library per project | Adapt to dynamic data sources and masking requirements for each batch project |
| Node ID `nodeId` | Assign unique identifiers in sequence of process nodes | Ensure accurate calling and verification of each step in the workflow |
| Search filter reference upper limit | Top 30 entries | Match the single data call scale for masking documents, control token consumption |
| Session auto-trigger switch | Enabled | Meet the requirements for automatic verification without manual triggering in compliance processes |
| API parameter assignment rule | Pass project ID via incoming call requests | Adapt to multi-project parallel workflow invocation scenarios |
| Timeout threshold | 600 seconds | Match the average time required for masking document parsing and rule verification |

## Three common mistakes
- Symptom: The JSON file generated after clicking the workflow export button is empty or cannot be downloaded. Cause: The target path parameter for the export node is not configured in `variables`, causing the workflow to fail to generate a valid file.
- Symptom: A token limit exceeded error is returned in the session, even if a reference upper limit of 2000 is set. Cause: The reference upper limit is not adjusted based on the average length of a single masking document, and excessive splicing causes the total token amount to exceed the model limit.
- Symptom: No automatic reply content appears after the user opens the session window. Cause: The `nodeId` of the process start node is not correctly bound, or the configuration switch for session auto-trigger is not enabled, causing the workflow to fail to start automatically.

## How to confirm the configuration is complete
- Manually trigger the workflow, check if each node executes in the preset order, and if the sensitive field recognition node can correctly mark the preset sensitive fields.
- Call the API interface with a test project ID, confirm that the parameters in `variables` can be correctly passed to each node of the workflow.
- Click the export button, verify that a complete JSON format workflow file can be generated.
- Open a new session window, confirm that the system automatically triggers the workflow and returns compliant masking validation results.
