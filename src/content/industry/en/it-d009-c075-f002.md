# Requirements and Design Documentation for Documentation Site Maintenance: Context and Tokens

## What data looks like for this category
Typical stakeholders for this category include technical writers, documentation site maintainers, and developer relations teams. Daily deliverables include installation guides, API documentation, migration guides, and FAQs. Data typically comes from code repositories, documentation site build logs, user feedback, and version release records. Updates are synced weekly or when a new version is released. Most document structures include three core fields: version identifiers, operation steps, and parameter descriptions. The most time-consuming tasks are example validation, syncing version differences, and cleaning outdated content. After data updates, corresponding documentation content for the matching version must be synced.

## What constraints these characteristics impose on the "context and tokens" workflow
The multi-type document structure of documentation site maintenance requires context matching to cover core fields such as version identifiers and operation steps, to avoid missing critical information. The weekly or per-version release update rhythm requires the context window to adapt to rapidly iterating content changes, preventing reference to outdated documentation snippets. Data from multiple sources needs context-based filtering to distinguish technical details from code repositories and common issues from user feedback, avoiding model misunderstandings caused by mixed context. The long-term accessible nature of usage instructions requires token allocation to prioritize the recall priority of core documentation, reducing unnecessary content occupying context space.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| ---|---|--- |
| Maximum Context | No more than 128000 tokens per round | Adapts to the mainstream model context upper limit of FastGPT v4.17.0, covering the needs of batch recall for multiple documents |
| Maximum Knowledge Base References | Top 8 matching results | Matches the typical length of single-page documentation on documentation sites, balancing recall scope and context load |
| Maximum Response Tokens | 4000 to 8000 tokens | Covers the output length of common documentation content such as installation steps and API parameter descriptions |
| `maxContext` | 60000 to 115200 tokens based on total tokens for a single version of the documentation site | Adapts to content sync needs for weekly or version-level updates |
| `quoteMaxToken` | No more than 2000 tokens per referenced content segment | Prevents single documentation snippets from occupying excessive context space due to excessive length |

## Three common mistakes
-  Knowledge base image output addresses are truncated: The symptom is that image links in generated responses are incomplete, only retaining part of the path. The cause is that `quoteMaxToken` is set too small, causing the documentation snippet containing the image link to be truncated early without loading the full address.
-  Insufficient accuracy in model context understanding: The symptom is that responses contain outdated installation steps or incorrect API parameter descriptions. The cause is failing to adjust the recall scope of `maxContext` according to version update frequency, leading to outdated documentation snippets being recalled preferentially.
-  Response content exceeds expected length: The symptom is that responses are truncated early or exceed model output limits. The cause is that maximum response tokens are set too low, failing to cover the full documentation content output needs.

## How to confirm configurations are correctly set
-  Upload a single typical document such as an installation guide, trigger a question-and-answer test, and verify that the response includes complete documentation content and version identifiers.
-  View context logs to confirm that all recalled documentation snippets are valid content for the current version, with no outdated documents included.
-  After adjusting configuration items, compare response lengths and recall counts across different configurations to confirm alignment with business needs.
-  Test question-and-answer for documents containing image links, confirm that image addresses are displayed completely with no truncation.

The values provided are common starting points and should be measured against the reader's own samples.
