# Drafting Requirements and Design Documents for Log Platforms and Observability: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Data for this category primarily comes from logging systems, Trace platforms, Metrics systems, and application SDKs. Daily produced documents include logging collection specifications, link tracing instructions, metric dictionaries, and dashboard configuration records. Data updates occur daily or upon each version release. Data fields include timestamps, log levels, service sources, traceID, spanID, metric values, associated tags, and more. Some fields must comply with standardized format requirements.

## What Constraints These Characteristics Impose on Multi-turn Dialogue and Prompt Engineering
Mixed input from multiple data sources requires multi-turn dialogue to organize context by data source, to avoid mixing fields from different systems. For example, distinguish validation rules for log fields and link tracing fields. Frequently updated data and documents require the dialogue flow to support real-time synchronization of the latest version content. This prevents referencing outdated collection specifications or dashboard configurations and ensures the timeliness of requirement documents. Diverse document structures require prompt engineering to preset retrieval rules for different scenarios, adapting to drafting needs for tasks such as log field validation, link association troubleshooting, and dashboard configuration records. The requirement for standardized fields requires embedding format validation logic in dialogue. This ensures that output document fields comply with unified system specifications and avoids configuration errors in subsequent operations and maintenance.

## How to Configure Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind a dedicated conversation ID | Distinguish different observability requirement drafting tasks and avoid context confusion |
| `messages` | Retain the first 8 rounds of conversation content | Cover historical interactions for current requirement drafting and avoid context loss |
| `variables` | Bind log service addresses and metric dictionary IDs | Automatically replace business placeholders in prompt engineering and reduce manual input |
| Chunk Length | 800–1200 characters | Adapt to the typical length of a single log or link record |
| Single Recall Count | Top 5 entries | Match the common volume of evidence used in daily troubleshooting |
| Maximum Context Token Count | 7000–9000 tokens | Adapt to the context limits of mainstream large language models |

## Three Common Mistakes
- After uploading an observability-related document, an upload failure prompt appears, but plain text input in the conversation works normally. The cause is that the parsing rule for the corresponding document type is not configured, or the uploaded file format exceeds the range supported by the platform.
- An `Unexpected end of JSON input` error appears during the conversation, which occurs more frequently when using the ChatGLM2 model. The cause is that the context window is set too large, causing the content returned by the large language model to be truncated and preventing the generation of a complete JSON format response.
- The speed of generating requirement documents via multi-turn dialogue is slow. The cause is that too many documents are recalled in a single round, or the context window contains too many invalid historical conversations, increasing the inference load on the large language model.

## How to Confirm Configuration Is Complete
- On the FastGPT v4.17.0 platform, upload a log collection specification document, wait for parsing to complete, then initiate a conversation, and check whether the field requirements in the document can be correctly referenced.
- Initiate a test conversation with multiple rounds of interaction, check whether the `messages` configuration retains the most recent valid interaction content and is not overwritten by irrelevant history.
- Test uploading observability documents in different formats, confirm that no upload failures occur, and verify that the configured parsing rules are in effect.
- Adjust the token count of the context window, initiate a long conversation test, and confirm that no JSON truncation error appears.
