# Drafting Requirements and Design Documents for Log Platforms and Observability: Workflow Orchestration

## What Data Looks Like for This Category
Data for this category primarily originates from log systems, Trace platforms, Metrics systems, and application SDKs. Daily output documents include log collection specifications, link tracing guides, indicator dictionaries, and dashboard configuration records. Most updates occur daily or alongside version iterations. Most document structures include field definitions, collection rules, association logic, and maintenance instructions. Covered fields include log levels, Trace ID, indicator names, and threshold parameters. Common units are observability-specific ones such as milliseconds, bytes, and records.

## Constraints Imposed on Workflow Orchestration by These Characteristics
Dispersed data sources require that workflows include cross-source data pull nodes to connect multiple systems and retrieve log, link tracing, and indicator data. Frequent document updates require workflows to set up version verification steps to avoid using expired collection specifications or indicator dictionaries. Many fields and specialized units require workflows to include standardized processing steps to unify formats and units across different data sources. Additionally, the most time-consuming links in this category, such as collection field standardization and link association troubleshooting, require workflows to simplify repetitive operations, automatically synchronize the latest document configurations, and improve drafting efficiency.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `variables` | Bind to a `24 hour` refresh cycle based on document update frequency | Matches the regular update frequency of documents in this category, avoids using expired global configurations |
| `nodeId` | Assign a unique ID in the `001-999` range to each workflow node | Avoids node conflicts and facilitates subsequent workflow link troubleshooting |
| Global variable configuration | Set Redis connection information and log index prefix as global variables, with values calibrated in the `500 MB` to `2000 MB` range | Uniformly manages configuration parameters shared across nodes, facilitates batch adjustments |
| Version verification threshold | Set the document update interval to `1 day` | Intercepts expired document data such as collection specifications and indicator dictionaries |
| Field standardization rules | Unify log levels into the `INFO/WARN/ERROR` standard format | Unifies scattered log field formats in this category and simplifies subsequent link association |
| Subflow variable inheritance | Enable the switch for subflows to inherit parent process `variables` | Meets the requirement for shared global variables between outer workflows and nested subflows |

## Three Common Misconfigurations
- A `400 Bad Request` error is returned after workflow execution. The cause is that required fields of the `variables` parameter are not configured correctly, causing the system to fail to recognize global variables.
- Nested subflows cannot obtain shared variables from the outer workflow. The cause is that the configuration for subflows to inherit parent process `variables` is not enabled, causing variable scopes to be isolated.
- The format of log fields pulled by the workflow is chaotic, leading to increased time spent on subsequent link troubleshooting. The cause is that field standardization rules are not configured, and non-standard format data collected originally is used directly.

## How to Confirm Configuration Is Correct
The configuration rules on this page apply to FastGPT v4.17.0.
- Call the workflow creation API, check if the returned workflow ID matches the preset `nodeId` to confirm that basic configuration has taken effect.
- Manually trigger the workflow, view the global variable loading log to confirm that parameters such as Redis connection information have been correctly read.
- Submit test data with expired document identifiers to confirm that the workflow triggers version verification and interception, which meets the configured threshold requirements.
- Communicate workflow configuration-related experiences through the official technical community to obtain more scenario-based configuration references.
