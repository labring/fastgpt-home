# Drafting Requirements and Design Documents for Cabinet Rack Installation and Cabling: Context and Token

## What the Data for This Category Looks Like
This data supports IDC maintenance engineers, network engineers, and equipment implementation personnel. Teams process daily documents including rack installation applications, cabinet cabling diagrams, port label sheets, and construction records. Data is sourced from DCIM systems, enterprise asset systems, network topology diagrams, and customer service tickets, with an update frequency of once per order per day. Document fields include rack unit number, rack unit (U), cable type, port number, construction date, and other details. Some documents use structured table formatting, while others are topology-related graphics linked to text.

## Constraints on Context and Token
Since data sources include structured and semi-structured content from multiple systems, and update frequency is once per order per day, context recall must associate asset, topology, and ticket data simultaneously. This creates clear requirements for total token volume and single recall length. Core fields of cabinet-related documents, such as rack unit number and cable specification, must be retained first to avoid truncation due to token limits. The total content volume of documents linked to a single ticket fluctuates. Context configuration must adapt to recall data of different volumes, preventing content missing or context overflow issues.

## Configuration Settings
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| Maximum Context | `8000–12000 token` | Covers the total content volume of multiple documents linked to a single ticket, including installation applications, cabling diagrams, port label sheets, and similar materials |
| Maximum Token per Reference | `2000–3000 token` | Limits token usage for single recall content, prioritizing retention of core fields such as rack planning and cable type |
| Single Recall Limit | Top 5 entries | Matches the associated data volume of daily single tickets, preventing excessive historical data from occupying context tokens |
| Context Sync Frequency | By ticket submission time | Aligns with the once per order per day update rhythm, ensuring recall of the latest construction records and asset system data |

## Three Common Misconfigurations
- Context truncation errors still occur after setting `maxContext`, with a prompt indicating token limit exceeded. Cause: The value was not adjusted based on the actual total content volume of cabinet documents, and a small window configuration from general scenarios was mistakenly used.
- A `failed to get gpt-3.5-turbo token encoder` exception log appears during invocation. Cause: The local model's token configuration was not correctly associated, or the model version is incompatible with FastGPT v4.17.0.
- Port label information is missing from generated requirement documents. Cause: `quoteMaxToken` value is too small, leading to truncation of core field content such as port number and cable specification.

## How to Verify Correct Configuration
- Upload a cabinet rack installation application document, check if the recalled associated context data includes DCIM asset information and historical construction records.
- When testing requirement document generation, confirm the returned content includes complete core fields such as rack unit number and cable type, with no truncation.
- Check system logs to confirm there are no token limit exceeded or encoder exception errors.
- After adjusting configuration items, compare changes in recalled content volume before and after to verify configuration effectiveness.

The values provided are common starting points and should be measured against the reader's own samples.
