# Requirements and Design Document Drafting for Penetration Testing Services: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
The data for this category primarily comes from target systems, public vulnerability databases, automated scanner results, and manual verification records from red team engineers. Updates align with the completion of each penetration testing project or major system version update. Daily produced documents include test authorization letters, penetration test reports, vulnerability reproduction records, and rectification suggestions. Fields cover authorization scope, vulnerability severity ratings, reproduction steps, repair priorities, and more. There is no unified fixed standard format, and some documents are unstructured text.

## What constraints these characteristics impose on the multi-turn dialogue and prompt engineering workflow
The diversity of data sources requires multi-turn dialogue to gradually integrate structured scan results and unstructured manual verification records to avoid missing information. The project-based update feature requires each dialogue to be bound to the unique identifier of the corresponding project to prevent cross-project context confusion. The inconsistent document format status requires prompt engineering to clearly specify parsing rules for different types of documents, adapting to field extraction needs for documents such as test authorization letters and vulnerability reproduction records. The concentration of time-consuming links requires the dialogue flow to focus on authorization confirmation, vulnerability verification, and report rating to reduce interference from irrelevant information.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique identifier of the penetration testing project | Ensure each dialogue is associated with the corresponding project data, preventing cross-project context confusion |
| `messages` | Retain the first 20 rounds of conversation history, spliced by project conversations | Cover the complete process from authorization confirmation to report generation, avoiding context overflow |
| `variables` | Inject project number, authorization scope, vulnerability database version | Uniformly populate into prompt engineering to reduce repeated input and improve field extraction accuracy |
| Maximum context length | 8000–12000 token | Adapt to the processing needs of long penetration test documents, calibrated based on actual testing |
| Attachment upload limit | Support PDF and CSV formats, single file cap of 1000 MB | Compatible with standard document formats such as test authorization letters and scanner results |
| Dialogue timeout setting | 600 seconds | Matches the average time required for links such as vulnerability verification and report rating |

This configuration applies to FastGPT v4.17.0.

## Three common configuration errors
- Phenomenon: Exported conversation records do not include uploaded attachment content, and the test process cannot be fully restored. Cause: Attachment storage configuration for conversation context is not enabled, only text message content is saved.
- Phenomenon: After uploading a scanner result CSV file, the dialogue fails to recognize vulnerability fields and returns a parsing error. Cause: No field mapping rules are configured in `variables`, and the prompt engineering does not specify the field types to be extracted.
- Phenomenon: The dialogue interface cannot be called with a knowledge base tag specified, and the returned results include information from irrelevant vulnerability databases. Cause: No knowledge base tag filtering instruction is added to `messages`, and the tag parameter is not passed through `variables`.

## How to confirm the configuration is correct
- Initiate a dialogue for parsing a test authorization letter, check if the reply includes the preset project number and authorization scope fields to confirm that the `variables` configuration takes effect.
- Upload a scanner result file, initiate a dialogue for vulnerability reproduction verification, check if the reply is associated with the currently bound project data to confirm that the `chatId` configuration is correct.
- Call the `api/v1/chat/completions` interface, pass parameters specifying the knowledge base tag, check if the returned results only include vulnerability information corresponding to the tag.
- Wait 600 seconds and check the dialogue status to confirm that the timeout setting meets the time consumption requirements of business processing.

The values provided are common starting points and should be measured against the reader's own samples.
