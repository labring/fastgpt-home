# Requirements and Design Document Drafting for Penetration Testing Services: Workflow Orchestration

## What the data for this category looks like
Data for this category primarily comes from target systems, public vulnerability databases, output results from automated scanners, and manual verification records from red team engineers. Daily output documents include test authorization letters, penetration test reports, vulnerability reproduction records, and rectification suggestions. Data updates follow a cycle per individual project or major system version. Each project corresponds to a separate set of documents, with fields including authorization scope, vulnerability ID, reproduction steps, risk level, and others. There is no unified fixed unit field, and adjustments are made based on project scenarios.

## What constraints these characteristics impose on the "workflow orchestration" link
Dispersed data sources with heterogeneous formats require workflow configuration with multiple nodes to pull different data sources and unify formats. Update cycles vary per individual project, so support is needed for initializing dedicated variables and document templates per project instance. Diverse document structures and highly compliance-focused test authorization letters require adding pre-check nodes. The most time-consuming links — test authorization confirmation, vulnerability verification, and risk rating — need to be split into parallel or serial nodes to avoid single-node blocking, while adapting to mixed time consumption of manual operations and automated scans.

## How to set the configurations
These configurations are adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Bind project ID, authorization scope, vulnerability database type | Match unique identifiers and compliance requirements of penetration testing projects to avoid data confusion across projects |
| `nodeId` | Name in groups by scanner results, manual verification records, public vulnerability databases | Distinguish three types of data source nodes for quick troubleshooting |
| Multiple knowledge base references | Bind 2 associated knowledge bases | Cover public vulnerability data and internal enterprise private vulnerability data to improve vulnerability identification comprehensiveness |
| Keyword extraction rules | Extract vulnerability ID, risk level, authorization scope | Accurately extract core document fields for subsequent report generation and rating |
| Timeout threshold | 600 seconds | Adapt to manual operations in the vulnerability verification link and average time consumption of multi-data source pulling |
| Result verification node | Associate test authorization letter fields | Ensure data from all process nodes complies with authorization scope to avoid compliance risks |

## Three common misconfigurations
- Symptom: Calling `variables` global variables returns empty values or throws errors. Cause: Corresponding parameters were not bound during workflow initialization, or variable names do not match fields within the node.
- Symptom: Workflow runs with timeout errors, and model configuration is confirmed to be correct. Cause: No reasonable timeout threshold was set, and time consumption of multi-data source pulling or manual verification exceeds the preset duration.
- Symptom: Keyword extraction results miss target fields, such as failure to extract vulnerability ID or risk level. Cause: No entity extraction rules configured for penetration test documents, only general extraction logic was used.

## How to confirm the configuration is complete
- Manually trigger the workflow and verify that the project ID and authorization scope bound by `variables` load correctly.
- Call the keyword extraction node, input a snippet of test authorization letter or vulnerability reproduction record, and confirm that core fields are extracted correctly.
- Enable multiple knowledge base association configurations, run the node, and verify that vulnerability data from different sources is pulled simultaneously.
- Simulate a timeout scenario and confirm that the workflow completes data pulling and processing links within 600 seconds.

The values provided are common starting points and should be measured against the reader's own samples.
