# Drafting Requirements and Design Documents for Channel Attribution and Lead Distribution: Workflow Orchestration

## Data Profile for This Category
Core data for this category originates from advertising platforms, CRM systems, attribution SDKs, and form systems. Most updates occur on a daily or weekly basis. Daily output documents include attribution rules, lead distribution tables, channel reports, and exception checklists. Typical document fields include channel identifiers, conversion event IDs, lead attribution IDs, conversion amounts, and verification status. No unified fixed format exists, so matching must align with the field definitions of each connected business system. Data volume fluctuates based on business campaign scale, with the core focus on lead source tracking and attribution allocation.

## Constraints Imposed on Workflow Orchestration
Decentralized data sources require the workflow to connect to multiple API types, and configure data source pull logic across multiple nodes. Daily or weekly update frequencies require scheduled triggering to avoid exceeding API rate limits from frequent calls. Non-uniform document field formats require adding field mapping nodes in the workflow to accommodate differences in field naming across systems. Verification logic for core time-intensive steps must be embedded in workflow nodes to automatically complete channel parameter validation, duplicate lead deduplication, and attribution confirmation, reducing manual intervention. An alert mechanism must also be configured to prevent issues such as distorted channel ROI and sales disputes.

## Configuration Guidelines
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Data Source Connection | Configure multiple nodes by business system type, with each node corresponding to an advertising platform, CRM system, or attribution SDK | Decentralized data sources require separate extraction of exclusive data from each system |
| Scheduled Trigger Cycle | Daily (24:00) or Weekly (Monday 00:00) | Aligns with daily or weekly data update rhythms, and adapts to business report generation cycles |
| Field Mapping Rules | Preset 3-5 general mapping templates, with support for custom modifications | No unified standard exists for field naming across systems, enabling rapid adaptation to formats of different business documents |
| `variables` Configuration | Store fixed configurations such as channel whitelists and knowledge base IDs, with the size of a single `variables` group not exceeding 100 MB | Eliminates repeated configuration of fixed parameters, reducing workflow redundancy |
| Exception Alert Thresholds | Calibrate based on business scenarios | Timely intercepts issues such as abnormal channel parameters and overly high duplicate lead rates |
| `nodeId` Configuration | Assign a unique identifier to each business node | Facilitates subsequent workflow debugging and exception localization |

## Three Common Misconfigurations
- Symptom: After calling the workflow to upload a file, passing it to the knowledge base returns a parameter error prompt. Cause: Associated parameters for the target knowledge base are not configured in `variables`, or output fields from the file upload step are not correctly mapped.
- Symptom: The duplicate lead rate exceeds expectations after workflow execution. Cause: No duplicate lead deduplication verification node is embedded, or the lead’s unique identifier field is not associated during field mapping.
- Symptom: No advertising platform data is pulled after scheduled workflow triggering. Cause: No permission validation is configured for the data source node, or the scheduled cycle does not match the advertising platform’s data update rhythm.

## How to Verify Proper Configuration
- Run a single-node test to confirm whether the data source node can successfully pull test data from the specified system.
- Manually trigger the workflow to check if the field mapping node converts fields from all connected systems into a unified format.
- Configure a test alert rule, simulate an exception scenario, and confirm that the alert node can properly trigger notifications.
- Review the workflow’s `nodeId` configuration to confirm that each node has a unique identifier for future debugging.

The values provided are common starting points and should be measured against the reader's own samples.
