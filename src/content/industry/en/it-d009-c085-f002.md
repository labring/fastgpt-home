# Drafting Requirements and Design Documents for Game Server R&D and Operations: Context and Token

## What data for this category looks like
Daily deliverables for this category include server architecture descriptions, server launch plans, server merging plans, and incident reports. Data comes primarily from game runtime logs, online player count monitoring data, business databases, and player-submitted tickets. Updates occur on a daily basis or sync with game event cycles. Core document fields include server node configurations, online peak thresholds, server merging data validation rules, and more. Processed data covers real-time online status and historical player behavior records, requiring linking structured and semi-structured information from multiple sources.

## What constraints these characteristics impose on the context and token workflow
Contexts tied to game server documents include multi-dimensional operational data and configuration rules. Single core documents typically have high token lengths. Teams must limit the total token count of the full context to avoid exceeding model limits. Mixed data from multiple sources often creates context redundancy, so teams must precisely filter content matching the current requirement. High-frequency updated data during events can cause context expiration, so teams must regularly clean outdated tickets and log data. Documents for server launch and merging scenarios require linking cross-node configuration information. Context retrieval must cover multiple relevant document fragments, while preventing irrelevant incident history from interfering with the current task.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Single server launch or merging plans have high token lengths. When combined with associated architecture description documents, the full context must stay within this range to prevent model output truncation |
| `quoteMaxToken` | 1500 token | Individual retrieved document fragments must match the length of core configuration fields, to avoid unnecessary token usage |
| Context refresh cycle | Every 24 hours | Matches the daily update cadence of data for this category, ensuring the context uses the latest online monitoring and ticket data |
| Number of retrieved documents | Top 3–5 | Core requirements for this category typically relate to 3–4 associated documents. Retrieving too many increases token consumption and adds irrelevant content |
| Expired context cleanup | Within 7 days after an event ends | Matches the update cycle of game events, to clear outdated event-related data and historical tickets |

This configuration applies to FastGPT v4.17.0.

## Three common mistakes
- Symptom: Model output for server launch plans is truncated, showing only partial server node configurations. Cause: The `maxContext` setting is too low, failing to match the actual token length of documents for this category, resulting in high-token configuration content being truncated by the model.
- Symptom: Outdated event ticket data remains in the context, leading to deviations in new server launch capacity estimates. Cause: No expired context cleanup rule is configured, or the cleanup cycle is longer than the data update cadence, so outdated data is not removed in a timely manner.
- Symptom: Retrieved document fragments include large amounts of irrelevant historical incident reports, failing to accurately match current server merging validation requirements. Cause: The number of retrieved documents is set too high, introducing non-core associated content, increasing token consumption and interfering with model judgment.

## How to confirm the configuration is correct
- Upload a typical server launch plan and its associated architecture description document, test whether the model output fully covers core configuration parameters, and confirm no content truncation occurs.
- Manually import outdated event ticket data, check whether the system automatically clears this type of data per the configured cleanup rules.
- Submit a server merging data validation request, check whether the retrieved document fragments only include currently associated merging plans and database configuration content.
- Submit three consecutive related questions, check whether the context is managed according to the configured limit, with no meaningless redundant accumulation.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
