# Requirements and Design Document Drafting for Game Design and Numerical Design: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
The data sources for game design and numerical design work typically include player behavior logs, publicly available competitor development materials, internal battle test records, and version feedback. Daily deliverable documents include gameplay design documents, numerical configuration tables, version requirement lists, and balance test records. Data updates follow a weekly cadence or align with game version cycles. Document fields include damage coefficients, level cooldown durations, character growth curve parameters, and similar items, with corresponding units being numerical values, duration units, or universal in-game units.

## What constraints these characteristics impose on multi-turn dialogue and prompt engineering
Dispersed data sources and frequent updates require multi-turn dialogue to accurately associate context from different sources, and avoid mixing irrelevant information. Fields and units vary significantly across different types of documents, so prompts must be explicitly adapted to the format requirements of different documents such as gameplay design plans and numerical tables. Conversations must be updated alongside version cycles, and the scope of retained context must be limited to ensure dialogue always remains tied to the requirements of the current version. Numerical content has high validation needs; multi-turn dialogue must gradually verify the rationality of parameters to avoid imbalance issues.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` session binding rule | Bind to the current version's project ID | Aligns with the development rhythm of game version cycles, and complies with FastGPT v4.17.0 session management logic |
| `messages` context length limit | First 6–10 turns of dialogue | Adapts to the iterative communication logic of design documents, avoids mixing irrelevant information in overly long context |
| `variables` preset field variables | Damage coefficient, level cooldown duration, character growth parameters | Matches the standard field format of numerical design documents, ensures output content complies with business specifications |
| Conversation log retention duration | 14–30 days | Meets the basic needs of version review and revision, while controlling platform storage usage |
| Knowledge base permission scope | Only grant access to current version development materials | Prevents calling expired competitor data or older version content, ensures the timeliness of dialogue content |

## Three Common Misconfigurations
- Issue: Numerical parameters returned by dialogue lack clear units. Cause: The prompt does not preset unit constraints for the `variables` field, and does not explicitly require a specified output format.
- Issue: Dialogue context contains expired older version data. Cause: `chatId` is not bound to the current version's project ID, causing the session to associate with document content from historical versions.
- Issue: Irrelevant cross-project materials are returned when calling the knowledge base. Cause: Knowledge base permission scope is not configured, and access is not restricted to only current game version development materials.

## How to Verify Successful Configuration
- Initiate a test dialogue that includes numerical parameters, verify that the output contains the preset fields and units.
- View the session list bound to `chatId`, confirm that only current project dialogue records are displayed.
- Check the knowledge base permission configuration, confirm that only data sources allowed for the current version are accessible.
- Review the conversation log retention settings, confirm that the retention duration meets the current version's review needs.
