# Requirements and Design Document Drafting for Game Operation Activity Configuration: Context and Token

## What the data for this category looks like
Core data for game operation activity configuration comes from the operation backend, player segment system, payment data platform, and activity log system. Daily produced documents include activity plans, reward configuration tables, launch checklists, and activity post-mortems. Fields cover unique activity identifiers, reward types, issuance quantities, effective periods, player segment tags, and more. Units include yuan, pieces, days, and others. Update frequency is mostly weekly or before holiday events. A single update requires synchronized adjustments across multiple documents.

## What constraints these characteristics impose on the context and token link
Multiple data sources result in large content volume during single context integration. Strict control of the `maxContext` quota is required to avoid overflow. Weekly or holiday-level update frequency requires regular context refreshes. Otherwise, configuration data will lag behind. Field density varies significantly across different documents. Reward configuration tables have longer single entries, which consume more context tokens. Temporary activity features require context to support isolation and clearing per activity dimension. This prevents configuration data from different activities from being mixed.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Game operation activity documents integrate multi-source data, covering activity plans, reward configuration tables, and activity logs. This range prevents token overflow that causes recall failure |
| `quoteMaxToken` | 1000–1500 characters | Reward configuration tables have dense fields. Long single entries consume excessive context quota |
| Context refresh cycle | Every 3 days, or 1 day before holiday events | Activity updates occur weekly or before holidays. This ensures latest configuration data is synchronized in a timely manner |
| Context clearing trigger | Within 24 hours after activity ends | Activity post-mortem documents do not require long-term context retention. This prevents invalid token consumption |
| Context recall count | Top 6 entries | Activity launch checklists cover core configuration items. Too many recalled entries increase token consumption |
| Multi-prompt concurrency configuration | Calibrated via actual testing | Multiple prompts must be called simultaneously to process activity check items. This must align with system concurrency limits |

## Three common mistakes
- Phenomenon: Token overflow error occurs during calls, returning `context token limit exceeded`. Cause: The `maxContext` parameter was not adjusted for game operation activity's multi-source data. Integrated activity plan, reward table, and log data exceed the quota.
- Phenomenon: Results merge abnormally after multi-prompt concurrent processing. Output content is missing or duplicated. Cause: Reasonable concurrency quota was not configured, and merging logic did not group processing by activity ID, leading to context confusion.
- Phenomenon: Unable to clear context information for a specified activity. Cause: Activity ID was not bound as the unique identifier for context clearing. Global context clearing operations were performed incorrectly.

## How to confirm configuration is complete
- Upload a single complete activity plan and reward configuration table. Check the content length shown in the context preview to confirm it does not exceed the quota set by the `maxContext` parameter.
- Trigger a context refresh operation. Verify that updated documents include the latest activity logs and player segment data.
- Simulate a multi-prompt concurrent call. Check that system returned results are correctly merged according to activity configuration items, with no abnormal errors.
- Execute a context clearing operation. Verify that context information for the specified activity has been removed, with no residual data.

This verification process applies to FastGPT v4.17.0.
