# Requirements and Design Document Drafting for Vulnerability Scanning Services: Workflow Orchestration

## What the data for this category looks like
Core data for vulnerability scanning services comes from vulnerability scanners, asset inventories, CVE databases, and patch bulletins. Daily output documents include scan plans, vulnerability lists, remediation tickets, and rescan reports. Each document includes fields such as asset IP addresses, vulnerability IDs, repair status, and rescan results. Data updates run on a weekly or monthly cycle, adjusted in sync with asset changes and official CVE database updates. This maintains the timeliness of scan rules and asset scope.

## What constraints these characteristics impose on workflow orchestration
Asset scope confirmation takes significant time. Add an asset inventory validation node to workflows to prevent scan ranges from mismatching actual assets. False positive elimination requires manual intervention. Add branch nodes to workflows: send high-confidence vulnerabilities directly to the remediation process, and send low-confidence vulnerabilities to manual review. Rescan result verification must link to original scan plans and rescan reports. Bind the document ID field in workflows to enable data linkage. The weekly or monthly data update frequency requires workflow trigger cycles to match this rhythm, avoiding excessive execution or missed updates. High-severity vulnerabilities carry significant risk consequences. Configure an exception alert node in workflows to notify the security operations team promptly.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Defined by the asset scope of the scan plan and CVE database version | Used to uniformly pass scan targets and rule versions to all workflow nodes |
| Global variable sharing | Enabled and bound to the global scope | Supports shared use of asset inventory and scan cycle parameters between outer workflows and nested sub-workflows |
| Node timeout period | 1200–1800 seconds | Matches the average execution time of vulnerability scan data pulling and CVE database queries |
| Workflow trigger cycle | Weekly / Monthly | Matches the regular data update frequency of vulnerability scanning services |
| Alert trigger condition | High-severity vulnerabilities not linked to remediation tickets | Corresponds to risk prevention and control requirements for high-severity vulnerabilities |
| `nodeId` | Bound to scan plan ID and rescan report ID | Enables automatic linkage between original scan data and rescan results |

## Three common misconfigurations
- Nested sub-workflows cannot read asset scope parameters from outer workflows: Global variable binding is not enabled, or the `variables` scope is not configured correctly, preventing cross-process parameter transfer.
- Workflow nodes time out and return status code 504: The node timeout period is set shorter than the actual time required to pull vulnerability scan data, and does not match the execution cycle of the scanning tool.
- Rescan results are not automatically linked to the original scan plan: The `nodeId` linkage rule is not configured in the workflow, and the corresponding fields of scan plan ID and rescan report ID are not bound.

## How to confirm successful configuration
- Trigger a test workflow, check whether `variables` parameters are correctly passed to all child nodes, and verify parameter consistency.
- View workflow execution logs to confirm that the node timeout period matches actual execution time, with no timeout errors.
- Simulate a high-severity vulnerability scenario to verify that the alert trigger logic sends notifications correctly.
- Check variable reading in nested sub-workflows, confirm that the global variable sharing configuration is active.
