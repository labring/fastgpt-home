# Requirements and Design Document Drafting for Version Releases and Release Notes: Multi-turn Dialogue and Prompt Engineering

## What the Data for This Category Looks Like
Core users of this category include open source maintainers, release managers, and documentation maintainers. Daily maintained documents include Release Notes, change logs, version tags, and release checklists. Data sources typically come from Git repository tags, merged commit records, CI build artifacts, and Issue milestone entries. Update frequency aligns with software version release cycles. Document structures generally include fields such as version number, change classification entries, breaking change descriptions, and artifact verification information. No uniform mandatory units apply, and field content adjusts based on project scale and release specifications. Content is usually organized around sets of changes that have already been merged.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
Data for this category is scattered across multiple systems. Multi-turn dialogue requires pulling associated data across sources, so the `messages` context must include metadata identifiers from different sources to ensure logical coherence. Update frequency follows version releases, and dialogue must adapt to temporary version node triggers. Context windows must be limited to avoid interference from redundant content. Document fields have no unified specifications, so prompt engineering must support dynamic adaptation to different projects' change classification rules. For publicly released features, dialogue-generated content must avoid unmerged changes, so validation logic must be added to the prompt. Time-consuming steps such as change classification and breaking change descriptions require dialogue to support step-by-step task breakdown, to avoid exceeding processing limits for single requests.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `messages` | Concatenate merged records, Git tags, and CI artifacts within the version cycle, with a maximum length of 8000 characters | Adapts to the cross-source data concatenation logic for this category, and aligns with the context processing limit of FastGPT v4.17.0 |
| `variables` | Inject the current version number, project repository address, and the titles of the last 3 milestones | Supplementary metadata required for release documentation, reducing manual input steps |
| `chatId` | Bind a dedicated session ID for the current version release | Isolates dialogue contexts for different versions to avoid data confusion |
| Maximum context length | 6000–10000 characters | Adapts to the typical content length of version release-related documents, balancing processing efficiency and information completeness |
| Context filtering rules | Only retain merged commit records and tagged artifacts | Aligns with the core requirement of this category for publicly released changes that have already been merged |

## Three Common Configuration Mistakes
- Symptom: A dialogue error is returned after a call, with a prompt indicating abnormal context format. Cause: Multi-source data in `messages` was not concatenated in chronological order of the version cycle, leading to chaotic context logic.
- Symptom: Full version-related dialogue records cannot be retrieved. Cause: A dedicated `chatId` was not bound, causing the session context to be overwritten by requests from other versions.
- Symptom: Generated Release Notes include unmerged commit content. Cause: Context filtering rules were not enabled, and merged change records were not filtered.

## How to Verify Correct Configuration
- A dialogue may be manually triggered, and the generated content can be reviewed to confirm it only includes merged commit records and tagged artifacts.
- The session list can be viewed to confirm a dedicated `chatId` session entry bound to the current version exists.
- Test variables can be injected, and the generated document can be checked to confirm it automatically supplements metadata such as version number and repository address.
- Cross-version dialogue requests can be simulated, and confirmation can be made that dialogue contexts for different versions do not interfere with each other.

The values provided are common starting points and should be evaluated against local samples.
