# Drafting Requirements and Design Documents for Player Customer Service and Public Opinion Handling: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
The data for this category mainly comes from customer service systems, community forums, app store reviews, and game logs. Daily produced documents include player tickets, compensation requests, public opinion daily reports, and standard response scripts. Data updates occur daily or in real time. Core fields include feedback type, associated game server ID, player account information, feedback time, processing progress, and results. The data structure is organized around the problem type and appeal content of player feedback, covering all process nodes from when a user submits feedback to when the issue is closed.

## What constraints these characteristics impose on the "multi-turn dialogue and prompt engineering" link
Multi-source real-time data sources require multi-turn dialogue to support context association across data sources. The `messages` array must integrate player feedback from different channels in feedback time order. Differences in fields across document types require prompt engineering to preset field extraction rules for scenarios such as tickets, compensation requests, and public opinion daily reports. Real-time updated data requires `chatId` to bind session context, ensuring each round of dialogue can call the latest player feedback and historical processing records. The time-consuming steps of account verification and compensation rule judgment require prompt engineering to include standardized verification logic, reducing repeated checking steps. The complexity of negative feedback classification requires multi-turn dialogue to support prompt configuration for automatic classification by feedback sentiment.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind unique identifier for player sessions | Ensure multi-turn dialogue context is not mixed, match ticket and feedback records for different players |
| `messages` | Keep the first 20 conversation entries in time order | Cover complete context of player feedback, avoid loss of critical account verification information |
| `variables` | Preset data source tags for customer service systems and community forums | Distinguish feedback from different sources, adapt to processing rules for different document types |
| Maximum context length | 800–1200 characters | Match average length of player tickets and public opinion content, avoid context overflow |
| Single historical call limit | First 5 associated tickets | Quickly associate similar past issues for the player, reduce repeated query time |
| Timeout threshold | 60 seconds | Adapt to real-time feedback processing rhythm, avoid player churn from long wait times |

## Three common mistakes
- Symptom: Associated player ticket files cannot be uploaded when calling the dialogue interface, and returned fields are empty. Cause: Binding parameters for file upload are not configured in `variables`, and file identifiers are not passed in accordance with FastGPT v4.17.0 interface specifications.
- Symptom: Context is mixed in multi-turn dialogue, and ticket content from different players is confused. Cause: `chatId` is not correctly bound as the unique identifier for player sessions, leading to cross-session reuse of context.
- Symptom: Prompt engineering does not distinguish between System and Human roles, leading to disrupted processing logic. Cause: The boundary between preset customer service rules for the System role and player feedback passed via the Human role is not clearly defined, confusing the priority of preset rules and real-time input.

## How to confirm configurations are correct
- Call the dialogue interface, pass the test player's `chatId` and historical `messages`, check if the returned context only associates ticket data for that player.
- After configuring data source tags in `variables`, input feedback content from different channels, check if processing results are classified according to preset tags.
- Adjust the maximum context length parameter, input test text that exceeds the set length, check if the system truncates or retains core content in accordance with rules.
- Set the timeout threshold, simulate a delayed request, check if the system returns processing results within the set time.

The values provided are common starting points and should be measured against the reader's own samples.
