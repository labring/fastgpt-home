# Requirements and Design Document Drafting for On-Site Deployment: Multi-Turn Conversations and Prompts

## What This Category of Data Looks Like
On-site deployment core data comes from customer equipment rooms, device inventories, software packages, and network topologies. Updates occur once per order or per implementation phase. Daily documents include deployment manuals, installation records, configuration lists, and on-site check-in sheets. Covered fields include device model, software version, IP address, installation duration, and similar items. Units include units, GB, hours, and others. Data structure adjusts based on on-site environment differences. No unified fixed format exists. Core fields must be extracted based on the specific needs of a single implementation.

## What Constraints Do These Characteristics Impose on Multi-Turn Conversations and Prompts
Data for on-site deployment comes from scattered sources and updates dynamically with work orders. Multi-turn conversations must bind the exclusive identifier of the current work order. This prevents context confusion across work orders. Document fields have no unified format. Prompts must support dynamic adaptation to different on-site environments. They must accurately extract required fields. Single implementation cycles are limited. Conversation responses must match the timeliness of on-site operations. Excessively long context loading increases wait time. This reduces on-site implementation efficiency. Most on-site data consists of structured device and network information. Prompts must focus on this content. This avoids redundant information interfering with conversation logic.

## How to Configure Settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale for This Setting |
| --- | --- | --- |
| Historical message limit | Keep the first 15–20 messages | On-site deployment document data volume is limited. Excess history increases context loading time |
| `chatId` binding rule | Bind the unique identifier of the current deployment work order | Ensure conversation context only associates with the current on-site implementation task. Avoid cross-work-order data confusion |
| `variables` configuration | Bind structured fields of device inventories and network topologies | Quickly call on-site-specific standardized data. Reduce manual input steps |
| Context timeout period | 600 seconds | Match the average phase duration of on-site deployment orders. Avoid context failure mid-task |
| `messages` filtering rule | Only retain messages containing device, network, or software version information | Focus on core business data. Compress context volume and improve response speed |

## Three Common Configuration Mistakes
- When initiating the first conversation, the first-word response delay exceeds 3 seconds, but subsequent conversation speeds are normal. The cause is failure to limit the number of historical messages. Excess on-site heterogeneous data in context increases initialization time.
- After configuring the automatic question-asking function, the dialog box outputs no content when the deployment process starts. The cause is failure to bind the `variables` of the current work order. Prompts cannot obtain on-site environment data to generate valid question content.
- After calling the chart tool, the generated chart is empty or has no data. The cause is failure to bind device performance data from the configuration list to prompts. This results in no valid input parameters when the tool is called.

## How to Confirm Successful Configuration
- Initiate the first conversation. Check that the first-word response time matches the rhythm of on-site operations, with no obvious delay.
- View the conversation context panel. Confirm that only historical messages from the current work order are retained. No historical data from other unrelated work orders appears.
- Enter a query related to on-site devices. Confirm that the conversation automatically calls bound structured fields to generate corresponding reply content.
- Test the automatic question-asking trigger logic in the workflow. Confirm that the dialog box generates guidance content matching the current on-site environment when the deployment process starts.
