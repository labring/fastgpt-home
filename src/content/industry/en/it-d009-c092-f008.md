# Requirements and Design Document Drafting for On-Site Deployment Implementation: Workflow Orchestration
This document is written based on FastGPT v4.17.0.

## What data for this category looks like
Data for the on-site deployment implementation category typically comes from customer machine room environments, equipment lists, software packages, and network topologies. Teams update this data per order or deployment phase. Daily generated documents include deployment manuals, installation records, configuration lists, and on-site check-in sheets. Documents cover fields such as equipment model, IP address, software version number, network bandwidth, and check-in time. Units include units, pieces, seconds, MB, and others. The number of fields in a single document fluctuates based on the scale of the customer’s order.

## What constraints these characteristics impose on workflow orchestration
The data characteristics of on-site deployment implementation impose multi-dimensional constraints on workflow orchestration.
First, data comes from exclusive resources at the customer site. Workflows must support binding on-site collected data for a single order to prevent cross-order data confusion.
Second, data updates happen per order or per phase. Workflow configurations must be isolated per order, and general templates cannot be reused.
Third, daily document structures are fixed into four categories such as deployment manuals. Workflow nodes must correspond to document generation and validation for each stage.
Fourth, on-site stages have variable time costs and severe error consequences. Workflows must include timeout check and failure rollback mechanisms.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Import the equipment list and network topology fields for the current order | Data comes from exclusive resources collected on the customer site, must directly bind collected fields for a single order |
| Trigger timeout | 600–1200 seconds | On-site deployment steps include environment checks and software installation, with large time fluctuations; set a reasonable range based on actual measurements |
| `nodeId` | Bind node ID according to deployment phase | Data updates per order or phase, must isolate configurations by phase to avoid cross-order data confusion |
| Node retry count | 3 times | On-site problem troubleshooting has occasional exceptions; limited retries reduce the need for manual intervention |
| Knowledge base association scope | Bind deployment documents for the current order | Daily documents are exclusive deployment manuals for a single order, must limit the knowledge base to only associate data for the current order |
| Single execution limit | First 3 on-site records | On-site data volume fluctuates with order scale; limiting the number of records prevents workflow overload |

## Three common mistakes
- Workflow execution displays a "cannot connect to database" error. The cause is that network configuration fields for the customer machine room are not bound to the `variables` parameter, so the workflow cannot read on-site network permission configurations.
- Workflow cannot select the customer’s exclusive knowledge base in real time during conversations. The cause is that the `nodeId` isolation rule is not configured per order, so the workflow can only call the global knowledge base and cannot match the deployment documents for the current order.
- The content format of workflow output does not meet the requirements of deployment manuals. The cause is that node output fields are not limited to the fixed format of configuration lists and installation records, resulting in missing or redundant fields.

## How to confirm the configuration is correct
- Before executing the workflow, verify that the `variables` parameter has imported the equipment list and network topology files for the current order.
- After triggering the workflow, check that the `nodeId` of each node corresponds to the current deployment phase, with no cross-order data associations.
- Review the documents output by the workflow to confirm that they include the required fields for deployment manuals and installation records.
- Simulate an occasional on-site exception to trigger node retry, and confirm that the workflow executes according to the configured retry count.
