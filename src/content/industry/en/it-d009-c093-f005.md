# Requirements and Design Document Drafting for User Growth and Retention Operations: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Data for this category primarily comes from user behavior logs, push systems, experiment platforms, and CRM systems. Most updates run on a daily or weekly basis. Daily produced documents include growth experiment plans, user segmentation tables, outreach copy, and retention analysis reports. Document fields typically include user segment tags, outreach channels, experiment variables, and retention rate metrics. Common units include user visits, percentages, outreach counts, and similar units. Data update rhythms must be aligned with operational cycles.

## What Constraints These Characteristics Impose on the Multi-turn Dialogue and Prompt Engineering Link
Scattered data sources and inconsistent update rhythms require multi-turn dialogue to support context continuity across cross-system data pulls.
Diverse document types require prompts to adapt to field formats and business logic of different documents.
Time-consuming steps such as user segmentation and outreach design rely on multiple iterations. A stable context memory mechanism must be configured.
Experiment result attribution requires association with multi-dimensional data. Prompts must clearly define field extraction rules to avoid confusion between data metrics from different sources.

## How to Set Configurations
This document is compatible with FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `messages` context splicing rule | Arrange in the order of user segment tags, outreach channels, and experiment results. Retain the most recent 7 historical messages | Aligns with the structure of weekly updated operational documents, making it easier to extract core business fields |
| `variables` binding scope | Bind user ID and outreach count fields from user behavior logs and CRM systems | Covers the data sources for this category, enabling cross-system data association |
| `chatId` binding rule | Bind the session identifier for a single growth experiment | Isolates dialogue contexts across different experiments to avoid data confusion |
| Maximum context window | First 10 dialogue turns + historical data from the most recent 3 days | Calibrated through practical testing, meets the multi-turn iteration needs of user segmentation and outreach design |
| Prompt field restriction | Only extract user segment, retention rate, and outreach count fields | Matches the core fields of daily documents, reducing interference from irrelevant information |

## Three Common Mistakes
- The dialogue interface prompts that no knowledge base is selected, but the debug preview works normally. The cause is that the session did not correctly bind the data source configuration corresponding to `chatId`, leading to failure to match preset knowledge base association rules during runtime.
- Context confusion occurs after multi-turn dialogue, with user data from different experiments being mixed during extraction. The cause is failure to bind `chatId` by experiment dimension, resulting in no isolation of contexts across different sessions.
- Fields extracted by prompts do not match business documents, with irrelevant metrics appearing. The cause is failure to limit the field extraction scope of prompts, leading the model to capture non-core business data.

## How to Confirm Proper Configuration
Input fields from an existing user segmentation table. Verify whether the content returned by multi-turn dialogue includes these fields.
Switch different `chatId` values. Confirm that dialogue contexts across different experiments do not interfere with each other.
View debug preview and formal operation results. Confirm that the matching status of the knowledge base or data source is consistent.
Check whether the bound fields of variables match the core fields of business documents. Avoid extracting invalid data.
