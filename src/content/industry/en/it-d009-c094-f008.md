# Requirements and Design Document Drafting for User Acceptance Testing Support: Workflow Orchestration

## What Data for This Category Looks Like
Data for this category is generated around the full end-to-end user acceptance testing support workflow. Core documents include UAT test cases, acceptance issue tickets, acceptance reports, and signed confirmation forms. Data sources are requirement specification documents, test environment configurations, customer business sample data, and defect management systems. Data updates follow a project phase or version cycle. Each phase synchronizes updates to test case coverage, issue records, and acceptance conclusions. Document fields include test scenarios, expected results, defect severity levels, acceptance status, and additional relevant fields. All data takes effect only after confirmation from the customer’s business representative.

## Constraints Imposed on Workflow Orchestration
The data characteristics of this category impose multiple constraints on workflow orchestration.
First, data requires confirmation from the customer’s business representative. Workflows must include manual approval nodes. These nodes trigger a customer confirmation step after acceptance conclusions are generated.
Second, data sources include test environments and defect systems. Workflows must connect to multiple data source pull nodes to synchronize test results and defect records.
Third, data updates follow a phase-based cycle. Workflows must bind phase trigger rules to avoid cross-phase data confusion.
Fourth, document fields are fixed. Workflow output nodes must match the standard fields of UAT test cases and acceptance forms to prevent data format incompatibility.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale for This Setting |
| ---- | ---- | ---- |
| Data Source Association Configuration | Bind the three data sources: requirement specifications, test environments, and defect systems | Covers all data sources for this category, ensures synchronization of test case and issue data |
| Phase Trigger Rule | Trigger based on project iteration phases | Matches the phase-based data update rhythm, prevents cross-phase data confusion |
| Manual Approval Timeout | 72 hours | Ensures customers have sufficient time to confirm acceptance conclusions, automatically triggers an exception alert if the timeout is reached |
| `variables` Configuration | Bind standard UAT test case fields (test scenarios, expected results) | Ensures workflow output documents meet the fixed field requirements of this category |
| `nodeId` Configuration | Assign a unique identifier to each phase’s UAT test case node | Facilitates cross-phase tracing of data flow and change records |

## Three Common Mistakes
- After adding a custom UAT support plugin to a workflow, no input or output parameters appear, and no error logs are generated. Cause: The `variables` binding for standard UAT document fields was not configured correctly, so the plugin cannot recognize the parameter structure.
- An uncaught exception prompt pops up after the workflow triggers. Cause: In a private deployment scenario, the connection parameters for the data source node were not configured correctly, so the system cannot pull data from the defect system or test environment.
- When the workflow loops through a UAT test case array, the loop body cannot correctly read array elements. Cause: The loop node was not configured with association rules matching the `nodeId`, so the element mapping relationship is incorrect.

## How to Confirm Configuration Is Complete

- Verify that the data source node has been associated with the three types of data sources: requirement specifications, test environments, and defect systems, and confirm that the data pull path is correct.
- Check that the `variables` configuration binds the standard UAT test case fields, ensuring output document formats meet category requirements.
- Validate the manual approval node trigger logic, confirming that it automatically pushes to the customer confirmation step after acceptance conclusions are generated.
- Test the loop node’s parameter mapping, confirming that array elements can be correctly read by the loop body.
