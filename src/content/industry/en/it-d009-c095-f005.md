# Requirements and Design Document Drafting for Monitoring Alert Configuration: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Data sources for this category include Prometheus, Zabbix, cloud monitoring, application logs, and CMDB systems. Daily produced documents include monitoring metric lists, alert rules, on-duty manuals, and alert change records. Data update frequency is daily or after each configuration change. Document fields include metric name, threshold range, trigger condition, notification link, and alert level. Corresponding units include percentage, response milliseconds, trigger count, and more.

## What constraints these characteristics impose on the "multi-turn dialogue and prompt engineering" link
Since data sources cover multiple types of monitoring systems, metric naming and threshold units vary across systems. Multi-turn dialogue must first align with the field specifications of the data source to avoid generating configuration content that does not match the target system format. Data updates occur at a high frequency, so dialogue context length must be limited. Excessively long context may reference outdated alert rules or change records. Document structures include multiple segmented content types, so prompt engineering must clearly distinguish generation requirements for different document types such as monitoring metric lists and alert rules. Alert configuration involves multiple required fields, so multi-turn dialogue must confirm each field sequentially to prevent missing key configuration items.

## How to set the configuration
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `messages` | Retain the first 20 conversation records | Matches the update frequency of alert configurations to avoid referencing outdated data |
| `variables` | Bind the current session's monitoring metric list | Ensures generated content references the currently active business data source |
| `chatId` | Generate separately for each alert configuration project | Isolates dialogue contexts for different projects to prevent configuration confusion |
| Context clear trigger | Detect the keyword "update alert rules" | Aligns with data change scenarios, resets invalid historical dialogue |
| Question optimization | Enable field alignment mode | Adapts to field format differences across multiple monitoring systems |

## Three common mistakes
- Generated alert rules use outdated thresholds that do not match currently active configurations. This occurs because no context clear trigger rule is configured, retaining historical configuration data from old sessions.
- Generated alert configurations cannot be recognized by the target monitoring system, with mismatched field formats. This occurs because question optimization mode is not enabled, and field specifications across different data sources are not aligned.
- Generated documents include irrelevant historical alert records with excessive redundant information. This occurs because exclusive variables for the current session are not bound, referencing uncleaned historical document data.

## How to confirm the configuration is complete
- Initiate an alert rule generation request, check if the fields of the generated content match the format of the currently bound monitoring system.
- Simulate a conversation containing the keyword "update alert rules", check if the dialogue context is automatically cleared.
- Check if the session's `chatId` is isolated from sessions of other alert configuration projects to avoid context confusion.
- Verify that the variable binding only includes the current session's monitoring metric list, with no historical document data mixed in.
