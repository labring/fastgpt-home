# Requirements and Design Document Drafting for Monitoring Alert Configuration: Document Parsing and Chunking

## What the data for this category looks like
The typical users of this category are operations engineers, SRE teams, and platform engineering teams. Daily produced documents include four types: monitoring indicator lists, alert rules, on-duty manuals, and alert change records. Data sources cover Prometheus, Zabbix, cloud monitoring, application logs, and CMDB systems. Update frequency is daily updates or updates after each configuration change. Documents usually include fields such as indicator names, threshold ranges, alert levels, notification links, and trigger conditions. Some documents present the corresponding relationship between indicators and thresholds in table form. The degree of structuring varies depending on the source tool.

## What constraints do these characteristics impose on the "document parsing and chunking" link?
The heterogeneous sources and structural differences of monitoring alert configuration documents require parsing tools to adapt to multi-format tables and text structures, and avoid splitting that breaks the association between indicators and thresholds. The high-frequency update feature requires the chunking logic to support incremental parsing and incremental updates, reducing repeated processing of historical data. A large number of standardized fields exist in documents, such as alert levels and threshold units. Chunking must retain the context of these fields to ensure complete matching of query requirements during retrieval. At the same time, alert change records are sorted by timestamps, and chunking must retain the temporal association of adjacent records to avoid breaking the change chain.

## How to set the configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chunkSize` | 800–1200 characters | The length of a single alert rule in monitoring alert documents is usually 100-300 characters. This value can retain the complete configuration context of a single alert and avoid splitting breaks |
| `chunkSplitter` | Recursive splitting by headings | Monitoring documents are usually organized by alert type into chapters. Splitting by headings ensures that each chunk corresponds to a complete set of alert configurations |
| `customPdfParse` | Enabled | Monitoring documents often include tabular indicator lists. This configuration adapts to the pdf-marker parsing tool and retains column-aligned field associations in tables |
| `PARSE_FILE_TIMEOUT_SECONDS` | 300–600 seconds | Large quarterly alert change record PDFs may contain thousands of records. This value avoids task termination due to excessively long parsing time |
| `chunkSettingMode` | Manual mode | The degree of standardization of field structures in operations documents varies. Manually adjusting chunk boundaries can better match the paragraph logic of alert rules |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | Bulk imported quarterly alert change records may be large in size. This value avoids file truncation during upload |

## Three common mistakes
- The symptom is a Cannot read properties of undefined error after calling `customPdfParse`. The cause is that the locally deployed pdf-marker version is incompatible with FastGPT v4.17.0, and the dependency environment is not correctly configured.
- The symptom is excessively high repetition rate of retrieval results after chunking. Multiple results contain the same segment of alert rule text. The cause is that a reasonable chunk overlap parameter is not set, causing adjacent chunks to include too many repeated segments.
- The symptom is empty alert threshold fields identified during chunking, and the threshold configuration of monitoring indicators cannot be extracted. The cause is that `customPdfParse` is not enabled, and ordinary parsing tools cannot recognize tabular indicator configurations in monitoring documents.

## How to confirm that configurations are correctly set
- Upload a local Zabbix alert rule PDF, and check whether each parsed chunk corresponds to a complete alert rule, with no missing fields or splitting breaks.
- View the running logs of the parsing task, and confirm that no timeout error corresponding to `PARSE_FILE_TIMEOUT_SECONDS` is triggered.
- Initiate a retrieval query, enter keywords related to alert rules, and check whether the number of repeated retrieval results meets expectations.
- Upload an alert change record file with a size close to `UPLOAD_FILE_MAX_SIZE`, and confirm that the upload and parsing processes can complete normally.

The values provided are common starting points and should be measured against the reader's own samples.
