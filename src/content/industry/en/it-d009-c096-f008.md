# Drafting Requirements and Design Documents for Community Report Handling: Workflow Orchestration

## What the data for this category looks like
Core data for community report handling comes from report systems, involved content details, users' historical report records, and audit rules. Update frequencies cover two categories: real-time and daily. Standardized documents produced regularly include report tickets, processing records, appeal forms, and user notification templates. Core fields include unique report identifiers, involved content IDs, report classification tags, disposal results, appeal statuses, and notification receipts. Data is processed individually: each ticket corresponds to a dedicated processing pipeline, with no default batch aggregation logic.

## What constraints these characteristics impose on the "workflow orchestration" link
The real-time and daily update rhythm means workflow startup and execution must match data flow timeliness, to avoid delays that cause ticket backlogs. Individual processing requirements mean each workflow instance must bind to the unique identifier of a single ticket, to prevent data cross-interference between different tickets. Multiple types of documents and fields require stable transfer of core fields between workflow nodes, to ensure accuracy in classification, disposal, and other links. Errors can lead to user complaints and community conflicts, so failure retry and exception alert nodes must be configured to reduce the impact of disposal errors.

## How to set the configurations
| Configuration Item | Recommended Value | Basis for Selection |
| --- | --- | --- |
| Trigger Node | Triggered by report ticket creation event | Matches real-time data update rhythm, ensuring the workflow starts immediately after ticket generation |
| Classification Branch Node | Split execution branches by report type | Corresponds to the classification tag field of report tickets, enabling differentiated processing for different violation types |
| Context Call Limit | First 3 user historical report records | Based on the user historical record data source, avoids context overload that affects processing efficiency |
| Timeout Threshold | 600 seconds | Matches real-time processing update requirements, prevents workflows from stagnating for long periods due to node blocking |
| Report Content Truncation | 800-1200 characters | Matches the conventional audit length of community content, avoids node blocking caused by overly long content |
| Variable Binding | Bind ticket core fields to the `variables` field | Transmits key information such as report ID and involved content link, ensures accurate data flow between nodes |

## Three Common Mistakes
- The text classification extraction node returns a null value. The cause is failure to correctly bind the report content field to the node input parameters, resulting in the node having no valid processing data.
- The workflow repeatedly enters the classification node after execution. The cause is failure to configure branch jump termination logic after the AI chat return node, causing cyclic process triggering.
- Workflow import fails. The cause is failure to match the new version's `nodeId` parameter rules; node IDs from old configurations are incompatible with FastGPT v4.17.0.

## How to Confirm Configuration Completion
- Trigger a test report ticket, check whether the workflow starts automatically and enters the corresponding classification branch.
- Access the node log page, confirm that ticket core fields bound to the `variables` field have been correctly transmitted to downstream knowledge base call and AI chat nodes.
- Simulate inputs of different report types, verify that each classification branch executes the corresponding logic with no branch jump exceptions.
- Manually trigger a node timeout scenario, confirm that the failure handling node triggers normally and records abnormal ticket information.

The values provided are common starting points and should be measured against the reader's own samples.
