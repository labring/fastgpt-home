# Requirements and Design Document Drafting for Community Report Handling: Document Parsing and Chunking

## What this category of data looks like
Daily documents for community report handling include report tickets, processing records, appeal forms, and user notification templates. Data sources include report systems, content details, user historical records, and review rules. Update frequency is mostly daily or real-time. Most documents are structured tables or semi-structured text, containing fields such as report ID, involved content, user identifier, processing status, and disposal result. Field structures vary across different document types, and some tickets include multiple columns of associated data.

## Constraints on the document parsing and chunking link
The characteristics of multiple types of documents for community report handling create multiple constraints for the document parsing and chunking link. Structured multi-column table documents cause the default parser to hit recognition limits, resulting in only the first two columns of data being extracted, and failing to fully retain all associated fields of the ticket. Real-time updated report data requires the parsing process to have a high response speed, to avoid processing delays caused by parsing latency. Differences in fields across different document types require the chunking logic to retain core associated information, to avoid damaging the corresponding relationship between report tickets and processing records after splitting. Batch-processed report tickets generate a large parsing load, so the parsing duration of a single task must be reasonably controlled to prevent data loss caused by timeout interruptions.

## How to set configurations
The following configurations are written based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chunkSize` | 800–1200 characters | Matches the field length of a single report ticket entry, to avoid losing core associated information such as report ID and involved content after splitting |
| `chunkSplitter` | Split by paragraph + title | Adapts to the structured fields of report tickets, retains the paragraph logic of processing records, and avoids cross-field splitting |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600 seconds | Addresses the batch parsing time consumption of bulk report tickets, to avoid incomplete parsing of some tickets caused by timeout interruptions |
| `chunkSettingMode` | Manual configuration | Adapts to field differences across multiple types of report documents, to avoid damaging the structural integrity of tickets and appeal forms using the default automatic chunking logic |
| `customPdfParse` | Disabled | Most documents for community report handling are in Excel or CSV format, so custom PDF parsing rules do not need to be enabled |

## Three common mistakes
- After uploading a multi-column Excel file such as a network segment record table, only two columns of data are identified. The root cause is failure to adjust parsing rules for multi-column structured tables. The default parser only adapts to tables in standard question-and-answer format, and cannot extract content from all columns.
- The knowledge base automatically merges chunks into larger blocks after the specified chunk size is exceeded. The root cause is failure to set `chunkSettingMode` to manual configuration, using the default automatic chunking logic without limiting the maximum character count per chunk.
- Some fields appear empty in parsing results after batch uploading report tickets. The root cause is that `PARSE_FILE_TIMEOUT_SECONDS` is set too short. Batch ticket parsing is interrupted before completion, resulting in incomplete extraction of some fields.

## How to verify the configuration
- Upload a report ticket Excel file with more than 3 columns of fields, check if the parsed dataset.csv contains content from all columns.
- Upload a single report ticket document, view the parsed chunking results, and confirm that each chunk length falls within the preset `chunkSize` range.
- Batch upload 10 report tickets, wait for parsing to complete, check for timeout errors, and confirm that the parsing duration does not exceed the set value of `PARSE_FILE_TIMEOUT_SECONDS`.
- View the chunked knowledge base content, confirm that each chunk retains core associated fields such as report ID and involved content, and no field splitting breaks occur.

The values provided are common starting points and should be measured against the reader's own samples.
