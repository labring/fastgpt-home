# Drafting Requirements and Design Documents for Community Contributor Governance: Multi-turn Dialogue and Prompt Words

## What data for this category consists of
The primary data for this category comes from daily work outputs of community leaders, maintainer committees, and foundation project operations. Core daily documents include four types: contribution guidelines, code of conduct, maintainer lists, and governance meeting minutes. Data sources cover code repository commit records, community forum discussions, contributor contribution statistics, and offline governance meeting records. Data is updated monthly or quarterly. The most time-consuming processing steps include role permission confirmation, governance rule explanation, and contributor promotion evaluation. Errors may lead to governance disputes, permission abuse, or contributor attrition. The core difference from documentation site maintenance categories is that this category focuses on management of personnel roles, rules, and decision-making mechanisms. The content of this page is compatible with FastGPT v4.17.0.

## What constraints these characteristics impose on the "multi-turn dialogue and prompt words" link
Dispersed data sources covering multiple document types require multi-turn dialogue to split context by role and scenario, to avoid mixing rules from different sources. Update frequency is monthly or quarterly, so prompt words must reserve interfaces for regular adaptation to the latest documents, to prevent use of expired governance rules. The most time-consuming steps—role permission confirmation, governance rule explanation, and contributor promotion evaluation—must be broken down step by step. Multi-turn dialogue should proceed in the order of permission verification, rule matching, and result confirmation, to reduce information load per single dialogue. Errors have serious consequences, so verification steps must be added to the dialogue process, to ensure accurate matching of roles and rules at each step, and prevent permission abuse or governance disputes.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Maximum context window | First 8 dialogue history entries | Community governance documents are updated monthly/quarterly; overly long context may introduce expired rules |
| `variables` | Bind contributor contribution statistics fields | Rationale: Promotion evaluation requires linking code repository contribution data |
| `messages` | Splice governance document fragments grouped by role | Rationale: Community data sources are dispersed; rules must be categorized and organized by maintainer and contributor roles |
| Timeout threshold | 120 seconds | Governance rule explanation requires reading multiple documents; reserve sufficient processing time |
| Dialogue trigger logic | Match corresponding rules by contributor identity | Rationale: Community governance requires distinguishing permissions and document scopes for different roles |

## Three common misconfigurations
- A MySQL database tool call returns a 400 status code with no response body. The cause is failure to configure required database connection parameters in `variables`, leading to missing dependent data in the dialogue context.
- The workflow cannot add a model switching control in the AI dialogue interface. The cause is failure to split the display logic of `messages` by role permissions, and failure to link maintainer configuration permissions.
- Specified dialogue records cannot be cleared after Docker Compose deployment. The cause is failure to bind the unique identifier of the target session via `chatId`, leading to accidental operation of the global storage path.

## How to confirm proper configuration
- Initiate a simulated dialogue for contributor promotion evaluation, and check whether `variables` correctly associate contribution statistics fields.
- When testing multi-turn dialogue, confirm that the governance rules for `messages` displayed in role groups match local document content.
- Call tools, and check whether the returned results include permission confirmation content applicable to the current role.
- Simulate the operation of clearing specified dialogues, and confirm that the session context specified by `chatId` is correctly cleaned up.
