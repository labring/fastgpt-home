# Requirements and Design Document Drafting for Mobile Development: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Core data for mobile development comes from code repositories, app store backends, crash monitoring platforms, and device coverage data. Daily produced documents include device version release notes, device adaptation lists, crash analysis reports, and app store submission materials. Document fields include device identifiers, system version ranges, permission request items, submission review statuses, and more. Data is updated daily or per release cycle. Associated fields across different documents must be kept synchronized to avoid inconsistencies in version numbers or adapted devices.

## What constraints these characteristics impose on the multi-turn dialogue and prompt engineering link
Dispersed data sources and frequent updates require multi-turn dialogue to integrate real-time data from multiple platforms, avoiding reliance on outdated document content. Document structures include mobile-specific fields such as device adaptation and review rules, so prompts must clearly define the logic for identifying and generating these fields. Data formats vary across sources, so unified data parsing rules must be implemented in the dialogue flow to ensure field consistency across documents. Additionally, app store submission requirements for mobile development must be embedded in the dialogue context to ensure generated documents comply with platform standards.

## Three Common Mistakes
- When using a multimodal model to process mobile adaptation screenshots, incorrect return formats occur, with interface prompts indicating images cannot be parsed. This occurs because compliance format and resolution requirements for adaptation screenshots are not explicitly specified in the prompt.
- Online deployed dialogue services remain continuously unresponsive, with request timeouts shown in logs. This occurs because the historical context length of `messages` is not limited, leading to context overload that triggers timeouts.
- No session idle recycling policy is configured, and a large number of idle sessions embedded via iframes occupy service resources, leading to overall performance degradation. This occurs because no timeout recycling mechanism is set for `chatId`.

## How to Verify Proper Configuration
- Initiate a multi-turn dialogue, upload a screenshot of a mobile adaptation list, and check if the model's parsed results include core fields such as device type and system version.
- Simulate 10 consecutive dialogue turns, check if response times remain stable with no obvious timeout errors.
- Configure `variables` to bind preset release note fields, and verify if generated documents automatically populate bound field values.
- Test automatic recycling of idle sessions, check if sessions exceeding the set duration are automatically cleaned up, with no abnormal resource usage.
