# Requirements and Design Document Drafting for Mobile Development: Document Parsing and Chunking

This document is written based on FastGPT v4.17.0.

## What the data for this category looks like
The core users of this category are iOS engineers, Android engineers, and cross-platform development teams. Daily produced and used documents include version release notes, device adaptation lists, crash analysis reports, app store review materials, and others. Data mainly comes from code repositories, app store backends, crash monitoring platforms, and device coverage data platforms. Update frequency is daily or triggered by version iterations. The structure of different documents varies significantly. Version release notes include device compatibility ranges and permission configuration items. Adaptation lists mark system version adaptation requirements. Crash analysis reports include device models and error log snippets. App store materials are mostly structured review submission content.

## What constraints do these characteristics impose on the "document parsing and chunking" link
Mobile development documents come from diverse sources, including Markdown files from code repositories, exported tables from app store backends, plain text logs from crash monitoring, and more. Parsing logic must adapt to multiple formats and content structures. The update rhythms of different documents differ greatly. Some documents require daily batch processing, while others are updated with version iterations. This places requirements on the batch processing capability and time control of parsing. Additionally, the field structures of documents vary significantly. Some are structured submission content, while others are free-text logs. Chunking must retain contextual associations, avoiding splitting key adaptation information across fields. Otherwise, subsequent development links will fail to match device and permission configurations, leading to issues such as review rejection or increased crash rates.

## How to set the configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `chunkSize` | 800–1200 characters | Adapts to the characteristics of mobile documents, which are mostly structured short paragraphs and long log snippets. Avoids overly large chunks causing context breaks or overly small chunks increasing retrieval overhead |
| `chunkSplitter` | Split by paragraph + heading | Matches the heading hierarchy of version release notes and adaptation lists, retaining field association relationships |
| `customPdfParse` | Enable digital signature content extraction | Resolves the issue where PDFs with digital signatures cannot recognize content, adapting to the common PDF format of app store review materials |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | Adapts to the upload requirements of large-volume log files for crash analysis reports, avoiding interception due to oversized files |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600 seconds | Adapts to the parsing time of batch version release notes, avoiding task failure due to parsing timeout |
| `chunkSettingMode` | Manual configuration | Supports custom chunking rules for the differentiated structure of mobile documents, adapting to the parsing needs of different document types |

## Three common mistakes
- Doc2x tool calls return file read errors, with error messages containing "Only support .txt, .m" | The parameter allowing non-text format file parsing is not configured, or mobile document formats such as PDFs and Excel are not included in the supported range
- PDFs with digital signatures cannot recognize valid content after upload | The default PDF parsing logic skips blocks with digital signatures, and the `customPdfParse` signature content extraction configuration is not enabled
- File reading links generated by the API knowledge base throw errors after clicking | The uploaded file exceeds the `UPLOAD_FILE_MAX_SIZE` limit, and the link fails due to incomplete file upload

## How to confirm the configuration is correct
- Upload a single digitally signed PDF document under 1000 MB, check whether complete text content is extracted after parsing
- Submit batch mobile adaptation list files, check whether the parsed chunks retain the contextual association of device models and system versions
- Trigger the Doc2x tool to parse non-text format files, confirm that no format unsupported error messages are returned
- Wait for the parsing task to complete, check whether the time is within 600 seconds, with no timeout errors

The values provided are common starting points and should be measured against appropriate sample data.
