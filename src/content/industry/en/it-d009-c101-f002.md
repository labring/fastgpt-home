# Requirements and Design Document Drafting for Renewal Health Management: Context and Token

## What this category's data looks like
This category's data primarily comes from CRM systems, product usage data, ticket statistics ledgers, and contract archives. Daily deliverable documents include customer health reports, renewal forecast sheets, high-risk customer lists, and cross-department meeting minutes. Data updates follow a weekly or monthly cadence. Each document typically includes multi-dimensional customer metric fields, such as customer ID, health score, risk level, contract expiration date, and similar metrics. There is no fixed, uniform single-document length limit.

## How these characteristics impose constraints on context and token processing
Multi-source, heterogeneous data sources create differences in field formats. Context recall must match different types of customer data fields. The weekly or monthly update cadence reduces the need for real-time token refreshes. Incremental token update synchronization for historical data must be supported. Documents include two types of content: structured tables and unstructured meeting minutes. Long-text renewal forecast sheets and short-text risk labels require adapted token splitting rules. This prevents key indicators from being truncated or split incorrectly.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum context recall count | Top 6 customer-related records | Matches the single-batch data volume for renewal health management, avoids context overload |
| `quoteMaxToken` | 1200–1500 token | Matches the average text length of renewal forecast sheets, prevents key forecast data from being truncated |
| Chunk length | 800–1000 characters | Matches the typical paragraph length of meeting minutes and health reports, balances splitting accuracy and recall efficiency |
| `maxContext` | Calibrated based on actual testing | Matches the total token usage of multi-source data, avoids exceeding the model's context window limit |
| Mandatory reserved fields | Customer ID, contract expiration date | Ensures core business fields are not split or omitted, aligns with core renewal management business logic |

## Three common configuration mistakes
- Core business fields are split or truncated. This occurs when mandatory reserved field rules are not set for the structured content of renewal forecast sheets, leading to key indicators being split across different chunks.
- Setting `maxContext` to an overly large value causes context overflow errors. This happens when the parameter is not adjusted based on the total token volume of a single batch of recalled customer records, exceeding the model's supported context window.
- Using a single uniform chunk length parameter for all document types, leading to incorrect splitting of key dialogue in meeting minutes. This stems from failing to distinguish chunking adaptation rules for structured tables and unstructured text.

## How to confirm configurations are correct
- Upload a standard renewal forecast sheet on the FastGPT v4.17.0 platform. Check that the full-text token field fully retains core forecast indicators, with no truncation or incorrect splitting.
- Review the `maxContext` configuration value. Combine the number of customer records recalled per batch to confirm total token usage does not exceed the model's window limit.
- Test the mandatory reserved fields configuration. Verify that customer ID and risk level fields in high-risk customer lists are not split across different recall chunks.
- Adjust the chunk length parameter for meeting minutes. Upload a single meeting minute document to confirm that single-paragraph content is not forcibly split.
