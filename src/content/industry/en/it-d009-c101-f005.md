# Requirements and Design Document Drafting for Renewal Health Management: Multi-turn Dialogue and Prompt Engineering

All configurations below are explained based on FastGPT v4.17.0.

## Data Structure for This Category
Core data for renewal health management comes from CRM systems, product-side user behavior data, work order statistics ledgers, and contract filing information. Daily produced documents include customer health reports, renewal forecast tables, high-risk customer lists, and cross-cycle communication minutes. Data updates follow a weekly or monthly cycle. Document fields include customer ID, contract expiration date, recent cycle active duration, risk level tags, historical communication records, and other items. There are no unified fixed units; values adjust based on the business attributes of individual data entries.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
The multi-source data sources, periodic update rhythm, and multi-type document structure of renewal health management impose multiple constraints on multi-turn dialogue and prompt configuration. Differences in multi-source data formats require multi-turn dialogue to unify field mapping rules, to avoid cross-system data confusion. Weekly or monthly update rhythms limit prompts to adapt to periodic data refresh nodes, and real-time dynamic responses should not be required. Differentiated fields across multiple document types require dialogue to clearly identify the document type of the context, to prevent cross-document data misuse. Additionally, the high time-consuming nature of risk classification and data interpretation requires multi-turn dialogue to support step-by-step guided task breakdown, and fixed business parameter templates must be passed via `variables`. Session context persistence binding must also be ensured, to avoid loss of historical dialogue in multi-turn Q&A, and adapt to continuous consultation needs in actual workflows.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `chatId` | A string bound to the customer's unique identifier, such as `crm_{customerId}` | Ensures multi-turn dialogue contexts for the same customer are not shared across sessions, and meets the customer-specific data requirements of renewal health management |
| `messages` | Retain the most recent 15–20 rounds of dialogue content | Adapts to the weekly or monthly data update rhythm, avoids response delays caused by overly long contexts, and covers continuous risk analysis needs |
| `variables` | Preset three types of business variables: customer health status, risk level, and contract expiration date | Reduces repeated input via standardized parameter passing, and improves consistency of multi-turn dialogue |
| Maximum session context length | 8000–10000 token | Adapts to the total number of fields across multiple business documents, and avoids information loss caused by context overflow |
| Multi-turn Q&A trigger rule | Trigger sessions bound by `chatId` | Ensures continuous consultations for the same customer use the same context, which aligns with renewal health management scenario requirements |
| Prompt template update rhythm | Synchronize with the data update cycle | Adapts to weekly or monthly data refresh frequencies, and ensures prompts match current business document structures |

## Three Common Misconfigurations
- Symptom: Historical dialogue content is lost during multi-turn dialogue, and subsequent questions cannot reference previous customer risk level information. Cause: `chatId` is not correctly bound, resulting in a new session context being generated for each dialogue, and historical information cannot be reused.
- Symptom: Responses from multiple AI dialogue nodes in a workflow are all displayed in the final chat interface, leading to excessive redundant information. Cause: No context filtering rules are configured for node outputs, resulting in all intermediate node content being included in the `messages` context.
- Symptom: An error indicating empty fields occurs when prompts call `variables`. Cause: Default values for corresponding business fields are not pre-configured in `variables`, resulting in partial customer data not being synchronized to the session.

## How to Verify a Complete Configuration
- Launch a simulated customer consultation, ask two related questions in sequence, and check if the context retains the previous customer risk level information.
- Configure a test workflow with multiple AI dialogue nodes, launch a dialogue, then view the final chat interface to confirm only necessary output content is retained.
- Call `variables` to pass preset business parameters, and check if prompts can correctly read and use these parameters to generate content.
- View session logs to confirm that the `chatId` for each dialogue matches the customer's unique identifier, and no cross-session context misuse occurs.

The values provided are common starting points and should be measured against samples specific to the target deployment.
