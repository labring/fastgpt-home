# Requirements and Design Document Drafting for Defect Management and Regression Testing: Context and Token

## What this category of data looks like
Data for this category comes primarily from defect management systems, test reports, code commit records, and user feedback. Daily produced documents include defect tickets, regression checklists, repair verification records, and defect statistical reports. Defect tickets contain defect ID, priority, reproduction steps, associated code snippets, and error logs. Regression checklists sort test cases and associated defects by version. Data updates occur daily or per version release cycle. Most data fields are structured identifiers, paired with unstructured steps and log content. The length of individual entries varies widely.

## How these characteristics impose constraints on context and token handling
A high share of unstructured reproduction steps, error logs, and code snippets exists in this category of data. Token consumption for individual entries fluctuates greatly. Data updates happen frequently. The latest version of defect status and regression verification results must be retained in the context to avoid referencing outdated information. Strong associations exist between data entries. For example, a defect ticket links to corresponding test cases and repair code. Context recall must accurately match these associations, otherwise irrelevant content will be introduced. Single-round tasks may process multiple documents. Total token usage can easily exceed model limits. Strict control of the token upper limit for context and recalled content is required.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to multi-document context requirements for defect management and regression testing, balancing content completeness and model token limits |
| `quoteMaxToken` | 1500–2000 token | Matches the typical content length of individual defect tickets or test cases in this category, preventing single recalled content from exceeding token limits |
| Maximum context token count | Calibrated based on actual testing | Adapts to the model token upper limit of the deployment environment and the actual scale of business data |
| Single-recall content token upper limit | 1000–1500 token | Controls total token consumption of unstructured logs and steps during single-round recall |
| Context refresh interval | Daily | Matches the update frequency of this category of data, ensuring the context includes the latest defect and regression status |

## Three common misconfigurations
- Setting `quoteMaxToken` lower than the actual token length of a single defect document. This leads to retrieval of similar chunks but failure to fully reference them, resulting in truncated or discarded recalled content. The root cause is failing to match the actual content length of single documents in this category, and incorrectly using chunking parameters from generic knowledge bases.
- Incorrect configuration of `maxContext`. This causes the context to include too many historical defect records and regression verification logs, triggering model token overflow errors. The root cause is failing to adjust the context retention range based on the update frequency of this category of data.
- Failure to configure context association matching rules. This causes recalled test cases to have no association with the currently processed defect, resulting in invalid content occupying token limits. The root cause is failing to enable the association filtering mechanism between the context and the current task.

## How to verify correct configuration
- Check the environment variable configuration of the App/Admin server. Confirm that `AIPROXY_API_ENDPOINT` (the root address of the AI Proxy service, for example http://aiproxy:3000; do not append /v1 or /chat/completions, and do not use a single model address) and `AIPROXY_API_TOKEN` (the AI Proxy administrator token, consistent with the AI Proxy server configuration, cannot be empty, and cannot be an application API key or model vendor key) are correctly set. Ensure these variables are not configured in workflow global variables, application API request headers, or the general model management page, and comply with FastGPT v4.17.0 or later requirements.
- Trigger a defect document drafting task, and view the token usage statistics of the returned content. Confirm that the actual effective ranges of `maxContext` and `quoteMaxToken` match the configured values.
- Simulate retrieval of a defect ticket containing long logs. Verify that the token length of the recalled content does not exceed the `quoteMaxToken` setting.
- Wait for one update cycle, and confirm that the context has been updated with the latest defect status and regression verification results according to the configured refresh interval.

The values provided are common starting points and should be measured against the reader's own samples.
