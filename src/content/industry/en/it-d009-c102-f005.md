# Requirements and Design Document Drafting for Defect Management and Regression Testing: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
The data sources for this category include defect management systems, test reports, code commit records, and user feedback. Daily output documents include defect tickets, regression test checklists, repair verification records, and defect statistical reports. Data is updated daily or per version release cycle. Document fields include unique defect identifiers, reproduction steps, priority levels, associated version numbers, repair status, verification results, and additional relevant fields. Periodic report documents summarize defect distribution and repair status.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompt Engineering
Data sources are scattered and have inconsistent update cycles. Multi-turn dialogue must first align the context time range to avoid mixing expired defect records. There are numerous document fields with hierarchical relationships, so prompts must clearly specify the priority of extracted fields to prevent missing key information for high-priority defects. Format differences across documents are significant, so the dialogue flow must first guide users to specify the current document type to adapt to the distinct field requirements of defect tickets or regression checklists. A large volume of unstructured user feedback requires multi-turn dialogue to gradually guide users to supplement necessary information such as reproduction steps and associated versions, ensuring generated requirements and design documents are complete.

## How to Set Configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Unique string bound to the current defect management session | Ensures multi-turn dialogue context is not confused with other sessions, aligns with FastGPT v4.17.0 session management logic |
| `messages` | Concatenate the first 10 historical messages in the order of defect ticket → regression checklist → verification record | Prioritizes loading context for core documents of this category to avoid redundant information interfering with prompt understanding |
| `variables` | Preset "defect priority" and "associated version" as globally callable variables | Reduces repeated input and adapts to the fixed field requirements of defect management documents |
| Maximum context length | 8000–12000 characters | Covers the core defect data volume within a single version cycle, avoiding context truncation that loses critical information |
| Single dialogue response timeout | 60 seconds | Adapts to the time required for long-text generation of defect reproduction steps and field verification, preventing mid-process interruptions |
| Question classification model | Calibrated based on actual testing | Adapts to the terminology system of defect management scenarios, improving matching accuracy for question classification |

## Three Common Misconfigurations
- Symptom: The interface returns empty fields bound to the `variables` parameter, making it impossible to extract preset defect priority information. Cause: Global variables were not bound to the context corresponding to `chatId` during session initialization, causing variables to not persist across turns.
- Symptom: The generated requirements document omits reproduction steps, and the returned historical data includes defect records from non-current versions. Cause: The number of loaded `messages` was not restricted, resulting in expired historical data being mixed in and interfering with the prompt's field extraction logic.
- Symptom: A timeout error is triggered during the dialogue process, making it impossible to complete long-text reproduction step generation. Cause: No reasonable single dialogue response timeout duration was set, causing execution time to exceed the preset threshold.

## How to Confirm Configurations Are Correct
- Initiate a test dialogue, input "Extract the core fields of the current defect ticket", and verify whether the returned results include the fields corresponding to the preset global variables.
- Switch to a different `chatId` to initiate a new dialogue, confirm that the context is not confused with previous sessions and that historical data from other sessions is not loaded.
- Upload a test defect ticket document, confirm that the dialogue flow can correctly identify the document type and adapt to the corresponding field extraction rules.
- Wait longer than the preset response timeout duration without triggering an error, confirming that the timeout setting meets the time consumption requirements of the current scenario.
