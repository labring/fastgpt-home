# Drafting Requirements and Design Documents for Defect Management and Regression Testing: Forms and Interactions

## What Data Looks Like for This Category
Data for this category originates from defect management systems, test reports, code commit records, and user feedback. Update frequency follows daily or per version release cycles. Daily produced documents include defect tickets, regression test checklists, repair verification records, and defect statistical reports. Core fields cover defect ID, reproduction steps, priority, repair status, verification results, and more. Data flows through the full lifecycle of functional defects, focusing on defect discovery, judgment, repair, and verification stages.

## Constraints Imposed on Forms and Interactions
Data sources are scattered, and update rhythms align with version iterations. This requires forms to support quick associated entry of multi-source data, reducing repetitive filling work. Core document fields are numerous and must match defect lifecycle stages. Interaction design must display fields in stages according to process flow, avoiding single-page information overload that reduces filling efficiency. Defect reproduction and priority judgment take significant time, so external business systems must provide reproduction step templates and priority option values. FastGPT `formInput` and `userSelect` nodes handle collecting entry content and displaying optional lists, lowering manual entry costs. The risk of missing high-priority defects requires strict required field verification, and external business systems must support quick filtering of associated data by version and priority. FastGPT only collects input information for associated fields, ensuring core information is not missing. Repair verification records need to be associated with code commits and test reports, so external business systems must provide quick jump entrances for associated data sources. FastGPT only collects input information for associated fields, improving verification efficiency.

## Three Common Misconfigurations
- Manually submit an associated configuration form without mapping the defect ID field, resulting in a parameter mismatch prompt during submission. Verification action: Check whether the form fields and external business system field mapping configuration are complete.
- After submitting a defect management and regression test related form, subsequent nodes do not receive complete fields. Compare required items, actual submission content, and node output mapping one by one, then check subsequent interface returns; existing symptoms cannot independently determine the root cause.
- When creating a defect ticket, priority and iteration version fields have no default values, requiring manual repeated selection. Verification action: Check whether the field default value mapping configuration of subsequent nodes is completed.

## How to Confirm Configuration Is Complete
- Manually create a test defect ticket, check whether the form implemented by the external system displays fields split into four stages (discovery, judgment, repair, verification) according to the defect lifecycle; FastGPT `formInput` node is responsible for collecting input content of the corresponding stage.
- Click the priority drop-down box, confirm that the high/medium/low options provided by the external business system and the pass/fail/pending verification options for verification status load normally and can be selected normally; FastGPT `userSelect` node is only responsible for displaying the optional list.
- After configuring the external data source association, try to pull the associated test report data, confirm that the data can be displayed normally and associated with the current defect ticket; this logic is implemented by the external business system or subsequent nodes.
- Do not fill in the defect ID and priority fields when submitting the form, check whether a clear verification prompt is triggered, and confirm that the required field verification function is effective.
