# Drafting Requirements and Design Documents for Art Asset Production Management: Workflow Orchestration

## What this category of data looks like
Data for this category primarily comes from art asset libraries, project management systems, engine resource packages, and outsourced delivery packages. Daily produced documents include art requirement sheets, asset specification sheets, outsourced feedback sheets, and acceptance records. Fields covered include asset unique identifier, triangle count, pixel resolution, delivery deadline, acceptance status, and more. Units include pixels, triangle counts, MB, days, and others. Data update frequency is mostly daily or weekly, maintained synchronously by art teams, outsourcers, and project managers. Unlike level content creation, this category focuses on delivery management for character, scene, and special effect assets.

## What constraints these characteristics impose on workflow orchestration
Multiple data sources require workflows to support field extraction from multiple systems, to avoid manual entry errors. Fixed document structures and field requirements mean workflow `variables` configurations must precisely match required fields for each document. Otherwise, the workflow will fail to run. Daily or weekly update frequencies mean workflow trigger rules must support periodic or event-based triggering, to adapt to different synchronization rhythms. The most time-consuming specification confirmation and outsourced rework processes require workflows to include approval and loop nodes to reduce repeated communication. Consequences of errors such as resource mismatches or performance overrun require workflows to add specification verification steps to intercept abnormal data early.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `variables` | Associate fields from art requirement sheets and asset specification sheets, extract asset ID, triangle count, delivery deadline (default `30 days`) | Match the field structure of daily documents to ensure accurate data is available during workflow execution |
| `nodeId` | Bind to the acceptance record status change node, set to trigger when acceptance passes or fails | Adapt to event-based trigger logic for data updates, no manual workflow startup required |
| Loop trigger configuration | Trigger outsourced rework checks on a `7 day` cycle | Match the weekly data update frequency to timely follow up on unfinished rework tasks |
| Specification verification rules | Match engine resource triangle count threshold `10000 triangles` and file size threshold `500 MB` | Intercept non-compliant assets early to avoid subsequent performance issues |
| Knowledge base association configuration | Bind corresponding project categories in the art asset library | Quickly retrieve historical asset data to support drafting requirements and design documents |

## Three Common Mistakes
- Issue: Calling the workflow API returns a 404 error, and the workflow cannot be triggered. Cause: The trigger node corresponding to `nodeId` is not correctly configured, and the corresponding interface credential was not generated on the FastGPT v4.17.0 platform.
- Issue: The workflow cannot loop through the outsourced rework communication process, and it does not automatically terminate after multiple rework requests are submitted. Cause: Loop orchestration configuration is not enabled, and no clear loop termination condition is set, such as 3 consecutive acceptance passes.
- Issue: The art asset library selection in global variables cannot be dynamically assigned based on the project. Cause: The `variables` configuration is not associated with the project ID field from the project management system, so the variable cannot automatically match the asset library for the corresponding project.

## How to Confirm Configuration Correctness
- Check if the `variables` configuration covers all required fields from the art requirement sheet and asset specification sheet. The variable extraction results can be viewed via the preview node to confirm completeness.
- A test workflow can be triggered to verify that subsequent nodes run as expected after the acceptance status changes, confirming correct event trigger logic.
- The loop orchestration node can be tested, with up to 3 rework requests submitted, to verify that the loop automatically stops when the acceptance pass condition is met.
- The API documentation generated by the platform can be reviewed to confirm the trigger interface corresponding to `nodeId` has been created. A tool can be used to call the interface to verify normal return values.
