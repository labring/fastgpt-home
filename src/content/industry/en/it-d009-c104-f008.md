# Requirements and Design Document Drafting for Landing Page Conversion Optimization: Workflow Orchestration

## What the Data for This Category Looks Like
Core data for landing page conversion optimization comes from landing page access logs, heatmaps, form submission data, and ad source parameters. Regularly produced documents include landing page plans, tracking requirement documents, AB test reports, and form field lists. Data update frequency is weekly or after a single campaign ends. Fields include page path, dwell time, form submission status, ad channel identifiers, and more. Corresponding units must be matched based on specific data types, and there is no unified fixed format.

## Constraints Imposed on Workflow Orchestration
Data sources for landing page conversion optimization are scattered and have varied formats. Workflows must be configured with multiple data source connection nodes to support importing different types of content such as landing page access logs, heatmaps, and form data. Data update schedules are inconsistent. Workflows must support flexible configuration for on-demand triggering or weekly/campaign-level periodic triggering. Daily document structures vary widely. Workflows must have customizable variable mapping rules to support field parsing for different documents such as landing page plans and AB test reports. Process errors directly lead to lead loss or inability to attribute data. Complete timeout retry and exception alert mechanisms must be configured to ensure task execution stability.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Map core landing page fields to global variables, set the sharing scope to the parent workflow and all nested child workflows | Meet the requirement for shared core data such as ad sources and page paths between the parent workflow and child workflows, and avoid parameter transfer failures |
| `nodeId` | Configure unique and semantic identifiers for data source nodes, data parsing nodes, and result output nodes separately | Facilitate workflow debugging and parameter transfer between nodes, and avoid call exceptions caused by node ID conflicts |
| Trigger timing configuration | Trigger according to campaign cycles or buried point data updates, set the interval to 7 days or after a single campaign ends | Match the weekly/campaign-level update frequency of landing page conversion optimization, and reduce invalid execution times |
| Timeout retry configuration | Set single execution timeout to 600 seconds, set retry times to 2 | Adapt to the pull duration of data such as landing page logs and heatmaps, and avoid task failure caused by data pull timeout |
| Variable mapping rules | Automatically map fields from form field lists and AB test reports to workflow variables by name | Reduce manual configuration costs, and adapt to the document structure characteristics of landing page conversion optimization |

## Three Common Misconfigurations
- Symptom: Nested child workflows cannot read ad source parameters passed by the parent workflow after startup, and logs show that variable fields are empty. Cause: The cross-process sharing scope was not set in the `variables` configuration, and variables were only bound to the current node.
- Symptom: Deployment verification fails when starting the workflow, and the console returns an error that required environment variables are missing. Troubleshooting steps: Check whether `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` were not configured on the App/Admin server. `AIPROXY_API_ENDPOINT` is the root address of the AI Proxy service. `AIPROXY_API_TOKEN` is the administrator token consistent with the AI Proxy server configuration and cannot be empty. Or check whether the parameters were incorrectly filled in the application configuration page, workflow global variables, or other locations.
- Symptom: Calling the workflow API returns a 401 authentication failure. Troubleshooting steps: Check whether the AI Proxy administrator token was used as the authentication credential for application API calls. External calls to application APIs must not use the AI Proxy administrator token instead of the application API Key.

## How to Confirm the Configuration is Complete
- Check the environment variable configuration on the App/Admin server, confirm that `AIPROXY_API_ENDPOINT` (root address of the AI Proxy service) and `AIPROXY_API_TOKEN` (administrator token consistent with the AI Proxy server configuration) are correctly filled and not empty.
- Trigger a test workflow, and check the running logs to confirm that the global variables of the parent workflow have been successfully passed to the nested child workflows.
- Use the application API Key as the authentication credential when calling the workflow API, and confirm that a normal workflow execution ID is returned.
- Check the `nodeId` configuration of workflow nodes, confirm that all nodes have been configured with unique and semantic identifiers.
