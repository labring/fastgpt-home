# Drafting Requirements and Design Documents for Speech Annotation and Transcription: Multi-turn Dialogue and Prompt Engineering
## What Data for This Category Looks Like
Speech annotation and transcription scenario data primarily comes from audio files, annotation platforms, proprietary vocabularies, and spot-check samples. Daily associated documents include transcription specifications, audio delivery lists, quality inspection reports, and speaker annotation forms. Update frequency is adjusted on a daily basis or according to the rhythm of individual batch projects. Data processing covers links such as noise segment judgment, speaker differentiation, proprietary vocabulary proofreading, and more. The final output is structured transcribed text, which differs from project workflows focused on direct annotation text.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompt Engineering
The data sources for this scenario are scattered and updated in batches. This requires multi-turn dialogue to isolate context by project batch to avoid confusion across batch data. Structured transcription output requirements mean prompts must clearly specify fields and formats, while also covering rules for exclusive links such as noise judgment and speaker differentiation. Operation logic differs across roles including annotators and quality inspectors. This means multi-turn dialogue must bind corresponding role permissions and document scopes, while adapting to context expansion needs for batch data processing.

## How to Configure Settings
The following configurations are based on the functional logic of FastGPT v4.17.0:

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Generate a unique identifier per project/per user, using the project ID + user identity as the value | Isolate dialogue context across different users or batches to prevent data cross-talk |
| `messages` | Retain 800–1200 tokens of historical dialogue history, truncate excess content based on actual measurement | Adapt to the context length requirements of speech annotation documents, avoiding exceeding model context limits |
| `variables` | Bind the current project’s transcription specifications and proprietary vocabularies, using text fragments from the corresponding documents as values | Inject exclusive business rules into prompts to ensure consistent annotation logic |
| Historical Dialogue Recall Limit | Retain the first 5 dialogue records | Control total context length to avoid redundant data interfering with prompt effectiveness |
| Context Compression Trigger Threshold | Trigger compression when the length of `messages` exceeds 1000 tokens | Adapt to model context window limits to ensure smooth multi-turn dialogue |
| Variable Update Frequency | Update business rules in `variables` on a daily basis or per batch project | Match data update rhythm to ensure prompts use the latest business requirements |

## Three Common Misconfigurations
- When calling the API to retrieve dialogue records, the `Human` field returns null. The `messages` role identifier is not correctly configured in the request parameters, causing dialogue history to fail to be correctly identified and rendered.
- When multiple users share an application, different users can view each other’s dialogue content. A unique `chatId` is not generated for each user, causing context to be bound to a public session identifier and resulting in data cross-talk.
- When processing batch audio annotation tasks, multi-turn dialogue prompts fail to execute. Business rules in `variables` are not isolated by project batch, causing prompts to mix transcription specifications from unrelated batches and triggering logical errors.

## How to Confirm Configurations Are Correct
- Initiate a single test dialogue, verify that the `Human` field displays normally, and confirm that the role configuration for the `messages` parameter is correct.
- Generate independent `chatId` values for different test users, initiate a dialogue, and verify that only the current user can view the corresponding records, confirming that the session isolation configuration takes effect.
- Import a single batch of audio lists and vocabularies, check whether `variables` correctly bind the current project’s business rules, and confirm that the parameter injection logic works properly.
- Simulate multi-turn dialogue accumulating to the model context limit, check whether expected context compression or truncation is triggered, and confirm that the length control configuration takes effect.

The values provided here are common starting points and should be measured against the reader’s own samples.
