# Requirements and Design Document Drafting for Account Ban and Appeal Review: Multi-turn Dialogue and Prompt Engineering

## What the Data for This Category Looks Like
This category's data originates primarily from risk control systems, audit records, user behavior logs, and report evidence. Update frequency is daily or real-time.
Daily produced documents include ban records, appeal materials, review opinions, and user notifications. Core fields include account unique identifier, violation type tag, appeal submission time, and review disposition result.
Some documents include attachments such as user behavior screenshots and report links. Data association logic is strictly bound to the account dimension. There are no unified fixed statistical fields. Corresponding data sources are matched only based on business scenarios.

## Constraints on Multi-turn Dialogue and Prompt Engineering From These Characteristics
Real-time data updates require multi-turn dialogue to pull the latest risk control and audit data synchronously. Using expired cache may cause judgment bias.
Multiple data sources require clear association with the account unique identifier in the dialogue flow. This ensures only appeal and review data for the target account is processed.
The diversity of document structures requires prompt engineering to adapt to different data types such as ban records and appeal materials. It must accurately extract core fields.
Account-level disposition attributes require the dialogue link to strictly lock the account dimension. This prevents incorrect cross-account association. It also requires verification of information integrity for each round of interaction. This avoids missing appeal reasons or violation evidence.

## Configuration Setup
Based on the FastGPT v4.17.0 feature framework, the following configurations can meet the multi-turn dialogue and prompt engineering requirements for account ban and appeal review.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the target account's unique identifier | Ensures multi-turn dialogue only associates ban and appeal data for the corresponding account, avoiding cross-account confusion |
| `messages` | Concatenate historical interactions and latest evidence in appeal submission order | Aligns with the logical flow of user appeals, enabling the model to sort the correspondence between appeal reasons and violation evidence |
| `variables` | Pass three core variables: account ID, violation type, appeal time | Locks the account dimension of the dialogue, reduces irrelevant data interference, and improves judgment accuracy |
| Maximum context length | 800–1200 characters | Adapts to the typical data volume of a single-account appeal process, avoiding exceeding the model's processing limit |
| Timeout threshold | 600 seconds | Matches the typical time required for real-time data pulling and audit record queries, preventing dialogue interruption due to slow data loading |
| Single interaction return limit | Top 5 core records | Avoids excessive redundant data interfering with model judgment, focusing on key violation and appeal information |
| Attachment reading size limit | 100 MB | Adapts to the storage capacity of common appeal attachments, avoiding timeouts caused by loading overly large files |

## Three Common Implementation Mistakes
- Accidental output of the model's internal thought process during multi-turn dialogue. The cause is failure to explicitly require hiding reasoning steps in the prompt, leading to redundant information being included in the final reply, conflicting with the requirement to hide thought processes.
- Permission errors returned when calling external data interfaces. The cause is failure to bind the risk control system and audit record interface permissions for the target account in the configuration, preventing pulling exclusive data for the target account.
- Missing key evidence from appeal materials in dialogue results. The cause is failure to pass attachment association fields in `variables`, so the model cannot obtain complete appeal supporting information.

## How to Verify Correct Configuration
- Initiate a test dialogue that includes the target account ID. Check whether returned content only associates ban records and appeal materials for that account, with no data from unrelated accounts.
- Review dialogue output results. Confirm that no internal model reasoning steps are included, and only review or appeal judgment results are displayed.
- Simulate the interaction flow after appeal submission. Confirm that the tool can normally pull real-time audit data for the corresponding account, with no permission or timeout errors.
- Adjust context length and timeout threshold configurations. Verify processing stability under different values, and determine a reasonable range adapted to the business scenario.
