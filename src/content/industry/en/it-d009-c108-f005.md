# Requirements and Design Document Drafting for Warranty Period Defect Response: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Data for this category comes primarily from customer-submitted warranty work orders, system operation logs, project contract warranty clauses, and software version update records. Daily produced documents include warranty work orders, defect confirmation sheets, repair execution records, and customer acceptance confirmation sheets.
Data is updated per order. Each completed defect response process generates or updates the corresponding document. Fields include defect number, trigger time, responsibility boundary determination result, repair version, customer confirmation status, and other similar items. No additional statistical quantitative fields are included.

## Constraints Imposed on Multi-turn Dialogue and Prompt Engineering
Data sources for this category are scattered, covering multiple types of unstructured content such as work orders, logs, and contract clauses. Multi-turn dialogue must gradually integrate information from different sources, so complete contextual association must be maintained.
The per-order update feature requires that dialogue context is only bound to the corresponding warranty work order, to prevent cross-order data confusion. Most document fields are judgment-based content. Prompts must guide the model to focus on core fields such as responsibility boundaries and repair solutions, while adapting to format differences across data sources.
Data update frequency is high. The dialogue link must support real-time calls to the latest version records and contract clauses, to avoid using expired information.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` binding rule | Only associate the session ID of the current warranty work order | Isolate cross-work order dialogue data per the per-order update feature, avoid context confusion |
| `messages` context length | Retain the first 20 rounds of dialogue content | Provide sufficient context to integrate scattered data from multiple sources, avoid losing key interaction information |
| `variables` call scope | Bind the current work order number and contract clause ID | Accurately match category-specific document fields, improve content relevance |
| Timeout threshold | 600 seconds | Adapt to the time required for multi-turn integration of scattered data, prevent mid-process interruptions |
| Prompt template configuration | Embed responsibility boundary determination guiding prompts | Focus on core business links of the category, reduce invalid output |
| Version adaptation | Based on FastGPT v4.17.0 | Adapt to parameter calls and interface logic of the current version |

## Three Common Configuration Mistakes
- Symptom: After enabling image recognition functionality in the dialogue node, upload a real photo of a warranty defect, and the model returns a prompt stating "unable to provide image content". Cause: Multimodal model support is not enabled in the global configuration, or image encoding parameters are not correctly passed in the session.
- Symptom: A list of filenames for referenced documents such as warranty work orders and contract clauses is automatically appended to the end of each dialogue reply. Cause: The document source display switch for dialogue results is not turned off; this configuration item is enabled by default.
- Symptom: After multiple consecutive rounds of defect judgment dialogues, the model begins to mix information from different work orders. Cause: Session contexts of different warranty work orders are not isolated by `chatId`, leading to incorrect calls of cross-order data.

## How to Verify Correct Configuration
- Initiate a dialogue containing a test warranty work order number, check whether the model can correctly associate the work order fields bound in `variables`.
- Upload a simulated defect photo, verify that the model can correctly recognize the image content and generate a reply combined with the context.
- Initiate multiple consecutive rounds of dialogue, check whether contexts of different sessions do not interfere with each other, and only retain content related to the current work order.
- View dialogue results, confirm whether they meet preset document display requirements, and adjust relevant configuration switches as needed.
