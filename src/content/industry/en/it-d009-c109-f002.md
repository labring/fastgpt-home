# Requirements and Design Document Drafting for Identity Account and Permission Management: Context and Token

## What the data for this category looks like
Data for this category comes from IAM systems, HR systems, business system logs, and approval systems. Update frequency is daily or triggered by personnel changes. Daily produced documents include account application forms, permission matrices, offboarding recovery forms, and audit reports. Document fields include account ID, employee name, affiliated department, permission scope, effective and expiration time, and more. The number of entries per document varies widely. Most data is structured text, with some unformatted content from original business logs.

## What constraints do these characteristics impose on the context and token link
Differences in update rhythms across multiple data sources require context to match real-time synchronization nodes. For example, permission adjustments triggered by personnel changes must refresh context promptly to avoid using expired data. The diversity of document structures requires context recall to distinguish field priorities for different document types. For example, core fields of permission matrices must be recalled first. The sensitivity of data fields requires strict limits on token usage by context to prevent unauthorized information from being accidentally recalled. Additionally, unformatted characters in original logs may disrupt token splitting logic, requiring additional processing.

## How to set the configuration
This configuration is based on the interface and parameter logic of FastGPT v4.17.0.

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Matches the number of fields in IAM-class documents and the information carrying capacity of a single round of conversation, adapting to the splicing needs of multiple permission documents |
| `quoteMaxToken` | 1500–2000 token | Adapts to the core content length of single documents such as permission matrices and audit reports, avoiding single quotes exceeding token limits |
| Context refresh interval | Every 12 hours | Matches the daily data update or personnel change synchronization rhythm, ensuring conversations use the latest permission data |
| Number of recalled context entries per single request | Top 6 | Controls overall token usage, balancing information completeness and conversation performance |
| Illegal character filtering | Enabled | Processes special characters such as line breaks in original business logs, avoiding invalid content generated during token splitting |

## Three common misconfigurations
- An Invalid JSON error appears in the conversation, and logs show unescaped line breaks. Cause: Illegal character filtering is not enabled, causing content recalled from IAM original logs to disrupt the JSON structure for token splitting.
- Permission information returned after multiple rounds of conversation does not match the latest personnel changes. Cause: No context refresh interval is configured, retaining initially imported old data and failing to synchronize updates from the HR system.
- The conversation recalls permission data for former employees. Cause: The number of recalled context entries per single request is not limited, resulting in the recall of historical account data beyond the scope associated with the current conversation.

## How to confirm the configuration is properly set
- Import a document containing permissions for active and former employees, initiate a permission query associated with the department, and confirm that the recalled results only include valid permission entries for active employees.
- Simulate a personnel change operation, wait for the configured context refresh interval, then initiate a query, and confirm that the returned permission information has been updated to the latest state.
- Initiate a complex query involving multiple IAM documents, check that the conversation's token usage does not exceed the configured limit of `maxContext`.
- Review system error logs, confirm that no Invalid JSON errors caused by illegal characters appear.

The values provided are common starting points and should be measured against the reader's own samples.
