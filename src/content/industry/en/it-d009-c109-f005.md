# Requirements and Design Document Drafting for Identity, Account and Permission Management: Multi-turn Dialogue and Prompt Engineering

## What the data for this category looks like
Data for this category originates from enterprise IAM systems, HR systems, business system logs, and approval systems. Updates run on a daily schedule, or trigger when personnel changes occur. Daily output documents include account application forms, permission matrices, offboarding recovery forms, and audit reports. Document fields cover account ID, affiliated department, permission scope, effective and expiration times, approval status, and other basic identity and permission association information. No additional custom statistical values are included.

## Constraints imposed on multi-turn dialogue and prompt engineering
Data sources are scattered, and update triggers are inconsistent. Multi-turn dialogue requires stable association of account and approval node information from historical sessions to avoid cross-session data confusion. Document fields are fixed and tightly linked. Prompt engineering must clearly define the range of extracted fields to prevent irrelevant content generation. Fluctuating update frequencies cause changes in context length. A reasonable limit must be set on the effective number of session context entries to avoid loading expired or redundant data. For permission scopes targeting internal employees, multi-turn dialogue must distinguish between administrator and regular employee permission contexts. This ensures generated documents comply with internal management rules. Permission matrix data volume can be large during single sessions. A reasonable upper limit must be set for multi-turn dialogue context caching to prevent workflow exceptions caused by data overload.

This document applies to FastGPT v4.17.0.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Chat history entries | First 6 entries | Matches context length for single-round approval/change processes in daily IAM document handling, avoids loading redundant data |
| `messages` parameter | Full sequence including system prompt, user input, and historical interactions | Ensures complete context of permission applications and approval nodes is retained across multi-turn dialogue, aligns with IAM document drafting logic |
| `variables` variable | Bound to fixed fields such as account ID, department, permission scope | Automatically pulls corresponding variables from IAM and HR systems, prevents manual input errors |
| `chatId` binding | Bound to the session identifier of the current workflow | Ensures multi-turn dialogue context only associates with the current IAM document drafting task, prevents cross-session data confusion |
| Timeout duration | 300 seconds | Matches typical response times for IAM system interfaces, avoids workflow interruptions caused by data pull delays |
| Prompt field restriction | Only extract specified fields from account application forms and permission matrices | Aligns with the fixed structure of documents in this category, prevents generation of irrelevant content |

## Three Common Configuration Mistakes
- Symptom: A text extraction node is used in the workflow, and chat history is configured. Multi-turn dialogue interactions fail to trigger. Cause: The `chatId` parameter is not bound. The workflow cannot associate historical context for the current session, and can only process single-turn input.
- Symptom: When calling an IAM system interface to generate a permission matrix document, the returned format does not meet expectations. Fields are missing or garbled. Cause: The field range is not limited via the `variables` parameter. The prompt does not clearly specify the fixed structure of the document, leading to generated content that deviates from standard IAM document formats.
- Symptom: During multi-turn dialogue, the workflow continuously triggers knowledge base searches, and no response is returned. Cause: The context length of the `messages` parameter is not limited. Excessive redundant historical session data is loaded, causing workflow resource overload and failure to process the current request normally.

## How to Verify Successful Configuration
- Test a single account application form drafting process. Check that the generated document includes preset account ID, department, and permission scope fields. Confirm that `variables` binding is active.
- Simulate a multi-turn permission change dialogue. Check that the workflow correctly associates approval node information from historical interactions. Confirm that `chatId` binding works correctly.
- Adjust the chat history entries parameter. Verify that the context length loaded by the workflow matches the actual needs of IAM document handling. Confirm that no redundant data is loaded.
- Trigger an abnormal permission review scenario. Check that the prompt only extracts specified fields. Confirm that the field restriction in the prompt template is active.

The values provided are common starting points and should be measured against the reader's own samples.
