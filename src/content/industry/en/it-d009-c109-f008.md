# Requirements and Design Document Drafting for Identity Account and Permission Management: Workflow Orchestration

## What the data for this category looks like
This category’s data comes from enterprise IAM systems, HR systems, business system logs, and approval systems. Daily produced documents include account application forms, permission matrices, offboarding recovery forms, and audit reports. Data update frequency is daily updates or real-time triggers based on personnel changes.
Account application forms include employee ID, applied permission scope, and associated approval node ID. Permission matrices mark system names, roles, permission items, and effective time periods. Offboarding recovery forms record offboarding dates and associated account lists. Audit reports summarize abnormal permission entries and approval process durations.

## What constraints these characteristics impose on workflow orchestration
Data sources are scattered and have varying formats. Workflow orchestration must configure multi-system data source connection nodes, and handle field mapping differences across different systems.
Update frequencies include both scheduled and real-time triggers. Workflows must support both scheduled scheduling and event-triggered modes.
Daily document fields are closely linked. For example, offboarding recovery forms must link to the approval status of account application forms. Clear configuration of dependencies between nodes is required.
Incorrect permission operations can cause unauthorized access or failed audits. Workflows must add pre-check links to block non-compliant permission application and recovery processes.

## How to set configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | Scheduled trigger (2:00 AM daily) + personnel change event trigger | Adapts to the update frequencies of daily data updates and real-time personnel changes, covering full and incremental data synchronization scenarios |
| Data Source Mapping Rule | Map system field names to unified-format permission fields | Resolves format differences across multi-system data sources, ensuring field consistency for documents such as permission matrices |
| Node Dependency Configuration | Bind `nodeId` to associate approval node status | Ensures offboarding recovery forms are only triggered after the corresponding account application approval is completed, avoiding invalid processes |
| Check Threshold | Abnormal permission interception threshold calibrated through actual testing | Blocks non-compliant permission applications in advance, reducing the risk of audit failure |
| Variable Storage | Enable `variables` to store temporary permission data | Retains intermediate process states, facilitating backtracking and exception troubleshooting |
| Timeout Setting | Set single-node timeout to 300 seconds | Adapts to IAM system interface response durations, avoiding process blocking |

## Three Common Misconfigurations
- Incorrect workflow node connection point configuration: Mixing right-side and bottom-side connection points causes process interruptions. This occurs when the trigger logic of node connection points is not clearly defined. Right-side connection points are used for subsequent execution after branch judgment, while bottom-side connection points are used for direct jumps in serial processes.
- Failed backup data restoration: No corresponding permission documents appear after logging into the knowledge base. This occurs when IAM system account permission association data is not restored synchronously. Restoring only project files cannot cover the underlying dependencies of permission configurations.
- Missing cyclic trigger logic: Batch permission application processes only run once. This occurs when the trigger condition for cyclic triggering is not bound, so the system cannot iterate through permission application entries for multiple accounts.

## How to Verify Proper Configuration
- Trigger test: Manually trigger a personnel change event, check whether the workflow automatically synchronizes account application form data
- Mapping verification: View the generated permission matrix document, confirm that fields from multi-system data sources have been uniformly mapped
- Dependency validation: Submit an offboarding recovery application, check whether the process starts only after the corresponding account approval is completed
- Timeout troubleshooting: Simulate a long unresponsive single node, confirm that the workflow triggers a timeout alarm and terminates
