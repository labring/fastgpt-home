# Requirements and Design Document Drafting for Incident Management and Root Cause Analysis: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Teams source data for this category from incident timelines, system logs, monitoring metrics, and code commit records. Updates occur for each major incident or once monthly. Teams produce daily documents including RCA reports, incident tickets, review minutes, and rectification tracking sheets. Documents include fields such as incident occurrence time, impact scope, root cause hypothesis, verification steps, rectification items, and tracking status. Units used include timestamps, event counts, indicator threshold ranges, and similar values. SREs, technical leads, or quality teams maintain this data.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompt Engineering
This category’s data sources are scattered but highly correlated. Teams use multi-turn dialogue to gradually associate incident timelines, logs, and monitoring metric content. Prompts must clearly guide extraction of corresponding fields.
Updates trigger for major incidents or follow a fixed monthly schedule. Teams need rapid document generation in emergency scenarios, so prompts must adapt to large volumes of input data in a short time.
Document field formats are fixed and strict. Prompts must strictly match the field requirements of RCA reports and rectification tracking sheets.
Teams must isolate different users’ chat records to avoid cross-user data confusion. Teams must also filter out historical records containing plugin-specified reply content.

## Configuration Settings
This configuration is implemented based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Max Context Length | 8000–12000 characters | Adapts to the typical content length of RCA reports and review minutes, avoids truncating critical data |
| History Memory Filter Rule | Only retain business-related `messages` | Filters out plugin-specified reply content mixed into historical records to avoid interfering with root cause analysis |
| `chatId` Binding Rule | Bind to a single user's business session | Differentiates chat records of different users to avoid cross-user data confusion |
| Prompt Variable Configuration | Pass fields such as incident time and impact scope via `variables` | Fixes required fields for document generation, ensures output format matches business documents |
| Maximum Number of Turns per Dialogue | First 6 turns | Controls the scale of multi-turn dialogue context, avoids redundant data interfering with root cause hypothesis verification |

## Three Common Misconfiguration Scenarios
- Phenomenon: Generated RCA reports include irrelevant content from plugin-specified replies, such as repeated configuration prompts or non-business information. Cause: Teams do not configure history memory filter rules, and fail to filter non-business plugin historical content.
- Phenomenon: API calls fail to generate documents, returning status code 401 or empty fields. Cause: Teams do not configure AI keys correctly, or fail to pass required incident-related fields in `variables`.
- Phenomenon: Chat records of different users are visible to each other, mixing root cause analysis data. Cause: Teams do not bind sessions to a single user per `chatId`, and fail to isolate user data.

## How to Verify Proper Configuration
- Initiate a test session, input basic incident-related information, and verify that the output document contains required fields for RCA reports and rectification tracking sheets.
- Switch to a different `chatId` to initiate a session, and confirm that chat records are not shared across sessions.
- Initiate a test dialogue containing plugin replies, and confirm that the output content does not include irrelevant plugin-specified information.
- Configure `variables` to pass test fields, and verify that the generated document correctly matches the passed variable content.

The values provided are common starting points and should be measured against the reader's own samples.
