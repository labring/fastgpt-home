# Requirements and Design Document Drafting for Integration Testing and Interface Testing: Document Parsing and Chunking

## What this category of data looks like
This category of data comes from the daily work outputs of test engineers, test development teams, and interface platform maintenance personnel. It includes interface test cases, commissioning issue tickets, environment descriptions, and test reports. Interface test cases contain fields such as interface paths, request methods, parameters, and expected responses. Commissioning issue tickets include fields such as problem symptoms, link nodes, and error messages. Data sources include interface management platforms, test environment logs, databases, and message queues. The update frequency is daily or when each version is released.

## What constraints these characteristics impose on the "document parsing and chunking" link
Daily documents come in diverse formats, ranging from structured interface test cases to unstructured commissioning logs and issue tickets. This requires the parsing link to support multi-format adaptation. The data update frequency is high, so the parsing and chunking timeliness must match the business rhythm. Documents contain key technical information such as link dependencies and parameter verification. Chunking must not destroy logical coherence, otherwise it will affect subsequent retrieval and reuse of test cases. At the same time, individual documents may be large in size, so issues such as parsing timeouts or file upload failures must be avoided.

## How to set the configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chunkSize` | 800–1200 characters | The core information of interface test cases and commissioning issue tickets is mostly coherent paragraphs. This range balances retrieval accuracy and overhead |
| `chunkSplitter` | Semantic segmentation first | Preserve coherent technical information such as interface parameters and link nodes, avoiding logical fragmentation caused by fixed-character splitting |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600 seconds | Adapt to the parsing duration of large test reports and log files, avoiding timeout errors |
| `customPdfParse` | Enabled | Most interface test reports are exported PDF formats. Enabling this option preserves table and field structures, reducing information loss |
| `UPLOAD_FILE_MAX_SIZE` | 100 MB | Matches the common volume upper limit of single test logs or commissioning issue tickets |

## Three common mistakes
- Symptom: An error `timeout of 360000ms exceeded` is prompted when uploading test logs larger than 10 MB. Cause: The `PARSE_FILE_TIMEOUT_SECONDS` parameter was not adjusted, and the default duration is insufficient for parsing large documents.
- Symptom: Chunking results lose complete link information for interface parameters. Cause: Documents were split only by fixed character length, and semantic segmentation mode was not enabled, causing parameters to be truncated across two chunks.
- Symptom: Custom JS parsing methods do not take effect. Cause: The custom parsing switch was not enabled in the knowledge base configuration, or the method syntax does not comply with FastGPT execution specifications.

## How to confirm the configuration is correct
A single test log file under 100 MB can be uploaded, and the parsing progress can be checked to confirm it completes within 600 seconds with no timeout error prompts.
An interface test case PDF can be uploaded, and the parsed text can be checked to confirm it retains key fields such as interface paths and request parameters, with no structural confusion or garbled characters.
A custom JS parsing method can be configured, then a test case file can be uploaded, and the parsing result can be checked to confirm it applies the custom logical processing.
The `chunkSize` parameter can be adjusted, and the chunking results can be checked to confirm their length matches the set range, with no excessive splitting or overly long segments.

The values given are common starting points and should be measured against the reader's own samples.
