# Requirements and Design Document Drafting for Project Implementation Plan Management: Multi-turn Dialogue and Prompt Words

## What the data for this category looks like
The data for this category typically comes from project contracts, work breakdown structures (WBS), client-shared schedules, and enterprise project management systems. Daily deliverable documents include project plans, milestone lists, weekly reports, and risk issue lists. Fields cover task identifiers, responsible persons, duration nodes, risk levels, budget proportions, and more. The data update rhythm is weekly synchronization or triggered by individual milestone nodes, with no mandatory update requirements outside fixed cycles.

## What Constraints Do These Characteristics Impose on Multi-turn Dialogue and Prompt Words
Dispersed data sources that require cross-system alignment require multi-turn dialogue to guide the input of information from different data sources such as contracts, WBS, and client schedules in stages, to avoid information omission caused by a single prompt word carrying too much content. The flexible data update rhythm requires the dialogue context to retain the most recently updated project nodes and risk records, to prevent the generation of documents that do not match the current progress when calling old data. The document fields cover multi-dimensional content, so the prompt word must clearly specify required fields such as task identifiers, responsible persons, and duration, to ensure that the generated documents meet project management specification requirements.

## How to Configure Settings
This configuration is based on FastGPT v4.17.0.
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind the exclusive session ID for the current project | Ensure that the multi-turn dialogue context is bound to the corresponding project's plan and risk list, avoiding cross-project data confusion |
| `messages` | Organize historical messages in the order of task breakdown, schedule coordination, and risk tracking | Match the conventional workflow of project implementation plan management, allowing the model to sort context according to business logic |
| `variables` | Pass the current project's number of WBS nodes, number of milestones, and weekly report cycle | Provide fixed business parameters for the prompt word, reducing the workload of repeated input |
| Maximum context length | 8000–12000 characters | Adapt to the number of fields and content volume of project documents, avoiding loss of key project information due to insufficient context |
| Single dialogue output count | First 3 structured entries | Control the content granularity of a single round of output, making it easy to verify project plan content section by section |
| Session context retention period | 7 days | Match the weekly update cycle of project weekly reports, ensuring the context is synchronized with the latest project progress |

## Three Common Misconfigurations
- Phenomenon: Documents generated via multi-turn dialogue contain task information from other projects. Cause: The exclusive `chatId` is not bound, causing shared session context across different projects.
- Phenomenon: The generated requirements document does not include the specified fields for the risk issue list. Cause: Required parameters such as risk level and responsible person passed via `variables` are not clearly specified in the prompt word, leading the model to omit key content.
- Phenomenon: The dialogue workflow executes slower than local debugging. Cause: The number of historical messages in `messages` is not limited, resulting in overly long context that exceeds processing thresholds and increases the model's inference load.

## How to Verify Successful Configuration
- Initiate a test dialogue, input the current project's number of WBS nodes, and verify whether the generated document contains the corresponding number of task entries.
- View the session details page, confirm that `chatId` matches the unique identifier of the current project, with no residual historical messages from cross-project sessions.
- Adjust the order of historical messages in `messages`, and test whether the generated document unfolds according to the logic of task breakdown and schedule coordination.
- Check the format of the output reply, confirm that it meets the preset structured requirements, with no missing fields.
