# Supplier and Process Quality Audit for SMT Mounting and Electronic Assembly: Multi-turn Dialogue and Prompting

## What Data for This Category Looks Like
The business data for SMT mounting and electronic assembly comes from customer-provided BOMs, Gerber files, and coordinate files, as well as MES system data, solder paste and component batch ledgers, mounters, SPI/AOI testing equipment, and reflow oven temperature records. Daily documents include changeover sheets, stencil parameter sheets, first article confirmation reports, SPI/AOI defect reports, maintenance records, and traceability labels.
Data updates in real time per work order and each changeover. Fields include part numbers, reference designators, component batches, reflow temperature curve parameters, testing defect types, and more. Units include millimeters, degrees Celsius, batch numbers, and other standard units.

## Constraints Imposed by These Characteristics on Multi-turn Dialogue and Prompting
Data for this category is updated independently per work order and changeover batch, with numerous highly specialized fields. This requires multi-turn dialogue to strictly bind to the context of the corresponding work order, to avoid mixing data across work orders.
Prompts must explicitly specify extraction of specific fields from documents such as BOMs and SPI reports, to prevent the model from confusing batch and defect information across different documents.
Real-time updated testing data requires the dialogue system to quickly retrieve the latest temperature and defect records. This means the context window length must be limited, to avoid loading redundant historical data that slows response speed.
Multi-turn interactions must gradually clarify key information such as work order numbers and defect types, to ensure each call matches the correct business data.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `messages` | Retain the first 15 historical dialogue entries + BOMs and SPI reports associated with the current work order | Matches the per-work-order independent update feature, avoids cross-work-order context interference, and complies with the context management rules of FastGPT v4.17.0 |
| `variables` | Bind work order ID, component batch number, and reflow temperature curve ID | Automatically bring in corresponding business fields, reduce manual input errors, and adapt to the multi-dimensional data association requirements of SMT work orders |
| Maximum context window | 7000–11000 tokens | Covers complete audit data for a single changeover, avoids truncating critical SPI/AOI reports and reflow temperature curve content |
| Question optimization toggle | Enabled, specified for the SMT quality audit scenario | Optimizes queries for specialized terminology in this category, improving the accuracy of defect analysis and field extraction |
| `chatId` | Bind work order number as the unique identifier | Differentiates session contexts for different work orders, avoids session confusion, and ensures accuracy of log storage and calls |

## Three Common Configuration Errors
- Workflow dialogue displays a failure, but the model backend has response logs. The cause is failure to correctly bind the work order ID in `variables`, which prevents the system from retrieving BOMs, SPI reports, and other data for the corresponding SMT work order, and fails to complete context matching.
- Dialogue logs are empty. The cause is failure to set `chatId` to bind a unique work order identifier, so the system cannot store interaction records for the corresponding session, resulting in no logs being generated.
- Extracted part numbers in prompts do not match the actual BOM. The cause is failure to explicitly specify extracting part numbers and reference designator fields from the BOM in the prompt, leading the model to confuse batch numbers and component information from other documents.

## How to Verify Proper Configuration
- Under FastGPT v4.17.0, test retrieving the BOM and coordinate files for a single work order, and check if the reply automatically includes fields corresponding to the bound `variables` parameters.
- Initiate a multi-turn dialogue, gradually supplement information such as defect types and changeover times, and check if the system retains the context of previous interactions and associates it with the business data of the corresponding work order.
- View the session log, confirm that the work order number bound to `chatId` matches the currently operated work order, and that the log content fully includes interaction records and associated document information.
- Trigger a workflow call, check if the model backend receives correct `messages` context data, with no missing parameters or format errors.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
