# Supplier and Process Quality Audit for Basic Chemical Continuous Production: HTTP Interfaces and External Systems

## What the data for this category looks like
Typical entities in basic chemical continuous production include chlor-alkali, synthetic ammonia, methanol, soda ash and other enterprises. Daily documents cover operating procedures, process indicator cards, DCS trends, laboratory reports, interlock bypass records, special work permits, and shift reports. Data sources include DCS/SIS systems, online analyzers, LIMS systems, equipment condition monitoring, energy metering devices, and raw material tank sensors. Data update frequencies are divided into three categories: real-time, per-shift, and daily. Fields include process temperature, pressure, material concentration, laboratory indicators, and others, with corresponding engineering units attached.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
The multi-source heterogeneous data and differentiated update frequencies of this category require HTTP interfaces to support authentication formats and data structures from different systems. For DCS and online analyzer data with high real-time requirements, the interface must have low-latency synchronization capabilities. For shift reports and laboratory reports updated per-shift or daily, scheduled pull scheduling configuration must be supported. The presence of multiple fields with engineering units requires that interface requests and responses carry clear parameter metadata to avoid unit conversion errors. At the same time, the consequences of errors in this category are severe. The interface must include failure retry and abnormal alert capabilities to ensure the integrity of audit data.

## How to set the configuration
This configuration is formulated based on the interface and UI rules of FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| `Authorization` | `Bearer ${corresponding system API key}` | Matches the standard API authentication format of industrial systems such as DCS and LIMS, ensuring interface access security |
| `variables` | Fill in the process parameter range for the current audit batch, such as {"target_temp": 85, "pressure": "0.12-0.15MPa"} | Adapts to the field requirements of process indicator cards, accurately matching the process data to be audited |
| `responseData` | Extract valid laboratory records and interlock status, filter redundant data | Narrow the audit scope and improve interface processing efficiency |
| Interface timeout setting | 600 seconds | Matches the transmission delay requirements of real-time process data, avoiding call failures caused by network fluctuations |
| Retry strategy | Retry 3 times after failure, interval of 10 seconds | Copes with short-term fluctuations in industrial networks, ensuring the success rate of data synchronization |
| Session isolation configuration | Bind unique audit subject according to `Authorization` | Distinguish audit records of different suppliers, avoid data confusion |

## Three common mistakes
- Audit records of different suppliers are mixed in returned results. The cause is that the unique audit subject identifier is not bound through `Authorization`, causing the interface to fail to distinguish supplier data corresponding to the request.
- The amount of interface returned data exceeds the system's carrying capacity. The cause is that the number of extracted entries for `responseData` is not limited, and redundant DCS historical trend data is pulled.
- Real-time process data synchronization delay. The cause is that a reasonable interface timeout period is not set, causing long-delay requests to be forcibly terminated by the system.

## How to confirm the configuration is complete
- Call the test interface, pass in the `Authorization` key of the specified supplier, check that the returned results only include audit data corresponding to that supplier.
- Switch different `variables` parameters, verify that the process data returned by the interface matches the incoming parameter range.
- Simulate network interruption and recovery, check that the interface triggers the retry mechanism and does not lose valid data.
- View the system logs, confirm that the interface call timeout and retry configurations are executed according to preset rules.
