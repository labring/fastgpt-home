# Supplier and Process Quality Audits for Safety, Environmental Protection and Special Work Management: Tool Calling and Plugins

## What data for this category includes
This category covers end-to-end safety and environmental work management for manufacturing enterprise EHS departments and maintenance teams. Daily documents include risk identification checklists, work permits for hot work, confined space work, lifting operations and other work types, gas monitoring records, hazardous waste ledgers, emission monitoring reports, and accident and hidden danger rectification reports. Data sources include public regulatory standards, on-site workshop environmental monitoring equipment, portable gas detectors, operator qualification files, equipment isolation lists, and local regulatory platforms. Data updates trigger in real time upon completion of individual work, monitoring cycles, or regular inspections, with no fixed batch update schedule.

## Constraints for tool calling and plugins
Work data for this category mostly consists of one-off semi-structured documents, with real-time validation requirements for high-risk scenarios. Data sources are scattered across hardware devices, internal files, and external regulatory platforms. Plugins must call cross-system interfaces to retrieve real-time monitoring values and operator qualification statuses. Work permits and rectification reports must strictly align with fixed fields required by regulatory standards. Tool calling must ensure incoming parameters accurately correspond to document fields. Real-time monitoring data requires tool responses to match the time window for pre-work approval, and tool calling logs must be retained for subsequent compliance audits.

## Configuration Guidelines
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Workflow/API tool selection | `auto` | Fits scenarios where this category dynamically calls compliance validation and data retrieval tools |
| Workflow/API function-call configuration | Bind tool sets by work type | Ensures only authorized compliance validation tools are called for high-risk work |
| Plugin timeout setting | 30–60 seconds | Matches the time window requirements for pre-work approval |
| Parameter validation switch | Enabled | Prevents invalid parameters that do not match work permit fields from being passed |
| Single call result limit | Top 5–10 entries | Fits the volume of associated monitoring records and qualification data for a single work order |
| Log retention configuration | Retain all call records | Meets compliance traceability audit requirements |

## Three Common Configuration Errors
- Issue: Parameter validation fails during tool calling, and required fields for work permits are not passed correctly. Cause: The parameter validation switch is not enabled, so calls initiate without matching fixed fields from work documents, leading to invalid parameter passing.
- Issue: Plugin calls to local monitoring platforms fail in an intranet deployment environment, with a connection establishment failure prompt. Cause: Plugin network access permissions are not configured according to the FastGPT v4.17.0 intranet deployment specifications, and plugins are incorrectly set to only allow public network access.
- Issue: When `toolChoice` is set to `auto`, unauthorized tools are called frequently. Cause: Tool sets are not bound by work type, so the model mistakenly calls compliance validation tools unrelated to the current work.

## How to Verify Correct Configuration
- Initiate a single simulated work call, and verify that parameters passed in the tool calling log match work permit fields.
- Test the plugin's call to the local monitoring platform interface in the intranet environment, and confirm that the connection is normal with no timeouts.
- Check the plugin's log retention switch, and confirm that all tool call records have been properly saved.
- Adjust `toolChoice` to `auto`, and verify that the model only calls authorized tools bound to the current work type.

The values provided here are common starting points, and should be evaluated against the user's own samples.
