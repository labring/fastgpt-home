# Supplier and Process Quality Audit for Industrial Instrument Manufacturing and Calibration: HTTP Interfaces and External Systems

## What data for this category looks like
Data for this category mainly comes from design documents, standard instruments and environmental monitoring equipment, calibration software, laboratory information systems, and customer range requirements. Daily documents include assembly and commissioning sheets, calibration procedures, original calibration records, error curves, metrology certificates, and software version records, updated after each calibration of every device. Data fields include device number, calibration date, standard instrument parameters, ambient temperature and humidity, multi-point measurement values, error calculation results, and traceability chain number. Units include metrology-specific units such as pascals, degrees Celsius, milliamps, and others. Each calibration record is associated with a unique metrology certificate number.

## Constraints imposed on HTTP interfaces and external systems
Calibration records and metrology certificates are core deliverables for this category. These must be synchronized to external systems or supplier audit platforms via HTTP interfaces. Each calibration of a device generates independent data. The interface must support single-device or small-batch data submission. Data fields contain a large number of metrology-specific parameters. The interface must strictly match field formats and units. Audit links such as traceability chain and environmental conditions require the interface to support batch verification of data integrity. Incorrect submissions will directly lead to failed metrology audits. Calibration data is updated frequently. The interface must adapt to high-frequency small-batch submission scenarios to avoid data backlogs.

## Configuration settings
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Request header configuration | Fix the `Authorization` parameter to carry a Bearer token with a validity period of `7200 seconds` | Meet metrology data permission verification requirements and prevent unauthorized access |
| Variable mapping | Map calibration data fields to standardized key names in `variables` | Adapt to external system field receiving rules |
| Response data processing | Verify the integrity of the metrology certificate number field in `responseData` | Ensure returned submission results are traceable |
| Submission batch size | Submit calibration data for `1–3 devices` per request | Adapt to the independent data update rhythm of each device per calibration |
| Timeout period | Set to `60 seconds` | Prevent interface request timeouts caused by large volumes of calibration data |
| Retry strategy | Only retry when the status code is `500` or `502` | Avoid duplicate calibration data submissions caused by retries |

## Three common configuration errors
- Configuring `Authorization` with an expired Bearer token, returning status code `401 Unauthorized`, due to failure to update permission credentials regularly.
- Not setting the submission batch size according to the independent update rhythm of calibration data, submitting data for more than 3 devices in a single request, causing interface timeout and returning status code `504 Gateway Timeout`.
- Not correctly configuring the external system connection address, causing interface request failure and returning status code `500 Internal Server Error`, a common issue similar to incorrect external system connection configuration during community deployments.

## How to confirm configuration is complete
- Submit calibration data for a single device, check if the correct metrology certificate number is returned in `responseData`.
- View interface logs to confirm that the `Authorization` parameter is correctly carried in the request header.
- Simulate submitting abnormal data missing the metrology certificate number, confirm that the interface returns a clear error prompt.
- Submit calibration data for 3 devices in batch, confirm that no timeout errors occur in the interface.

The values provided are common starting points and should be evaluated against the reader's own samples.
