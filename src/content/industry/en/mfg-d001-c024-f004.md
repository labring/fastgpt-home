# Supplier and Process Quality Audit for Process Change and Engineering Change: Workflow Orchestration

## What Data for This Category Looks Like
Data for this category originates from PLM, ERP, and MES systems, supplier documentation, validation test records, and customer-specific requirement documents. Daily produced and circulated documents include ECN/ECR forms, change assessment reports, drawing and BOM version records, process validation reports, production switching plans, inventory disposal documents, and customer approval documents. Data updates have no fixed cycle; they are triggered by each process or engineering change, and involve collaborative circulation across R&D, process, quality, production, and procurement teams.

## What Constraints These Characteristics Impose on Workflow Orchestration
Multi-source heterogeneous data sources require the workflow to be configured with cross-system data pull nodes, adapting to the interface formats of different systems such as PLM, ERP, and MES. The lack of a fixed update cycle requires the workflow to use change triggers as startup conditions, without relying on scheduled scheduling rules. Multiple types of associated documents require the workflow to support multi-node parallel verification, ensuring that documents such as ECNs, process validation reports, and customer approval files circulate synchronously. Scenarios involving cross-team participation require the workflow to be configured with node permission groups, restricting the operation scope of different roles on change approval nodes.

## Configuration Recommendations
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Bind change order ID, BOM version number | Associate corresponding change data pulled from multiple systems, ensuring the workflow context accurately matches the current change request |
| `nodeId` | Assign in the order of change process steps | Ensure the workflow node execution sequence aligns with the actual change approval and verification process, avoiding execution misalignment |
| Timeout Threshold | 600 seconds | Adapt to the average response time of cross-system data pulls from PLM and ERP, preventing workflow interruptions caused by invalid waiting |
| Context Length | 800–1200 characters | Adapt to the content length after splicing multiple documents, avoiding exceeding the model's processing limit |
| Number of Parallel Processed Documents | First 3 items | Adapt to the scenario of synchronous verification of multiple documents, processing associated files such as process validation reports and switching plans simultaneously |
| Judgment Rule | Match the "customer approval document exists" field | Correspond to the mandatory requirement of customer approval for this category, ensuring the change process complies with compliance requirements |

## Three Common Misconfiguration Issues
- Phenomenon: The judge triggers the ELSE branch when matching "equals" or "starts with" rules, and triggers the IF branch when matching "contains" or "ends with" rules. Cause: The string matching logic of the judge is not configured correctly, causing the rule matching order to differ from expectations.
- Phenomenon: The workflow cannot obtain parameters passed by the system, and the corresponding fields do not exist in the global variables. Cause: System parameter mapping is not configured in the workflow startup node, causing parameters to not be correctly written to the `variables` storage area.
- Phenomenon: The workflow does not correctly process the returned content after calling an external interface, triggering a timeout error. Cause: A reasonable timeout threshold is not set, or the analysis node for the interface returned content is not configured, causing the workflow to fail to recognize valid responses.

## How to Verify Proper Configuration
- Submit a test change order, check whether the workflow starts the corresponding nodes in the preset order.
- View the `variables` storage area, confirm that parameters such as change order ID and BOM version number have been correctly bound.
- Simulate triggering different matching rules, verify whether the judge's branch logic meets expectations.
- Check the cross-system node call logs, confirm that data pulling has been completed normally.

The values provided are common starting points and should be measured against the reader's own samples.
