# Supplier and Process Quality Audits for Process and Engineering Changes: Deployment and Upgrade

## What data for this category looks like
Data for the supplier and process quality audit scenario for process and engineering changes originates from multiple heterogeneous systems and documents, including PLM, ERP, MES, supplier materials, validation tests, and customer-specific requirements. Daily generated documents include ECN/ECR, change assessment reports, drawings and BOM versions, process validation reports, transition plans, inventory disposal documents, and customer approval files. Data updates follow no fixed cycle, and are triggered by each process or engineering change. Data fields include change number, version number, effective date, involved materials and process items, and approval status. The version number uses a string format, the effective date uses a standard date format, and the material number uses a standardized number field.

## Constraints Imposed by These Characteristics on Deployment and Upgrade
This scenario’s data sources cover multiple heterogeneous systems. During deployment, configure multiple data source connection parameters to ensure data synchronization with systems such as PLM and ERP. Document types include both structured and unstructured content. Adapt a unified file storage configuration to ensure all types of change-related attachments can be stored and accessed normally. Data updates follow no fixed cycle. Reserve a data migration compatibility mechanism during upgrades to avoid loss of change history data. Changes involve collaborative participation from multiple departments including R&D, process, quality, production, and procurement. During deployment, configure permission control parameters to distinguish access permissions for different roles. Data errors can trigger production risks. Reserve a rollback mechanism during deployment and upgrades to ensure rapid service recovery in abnormal situations.

## How to Set Configuration Parameters
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://username:password@host:port/dbname` | This scenario needs to store structured change data such as ECN/ECR and BOM versions, so a persistent MongoDB instance connection is required |
| `PG_URL` | `postgresql://username:password@host:port/dbname` | This scenario includes change records associated with multiple systems, so a relational database is needed to manage cross-document association relationships |
| `REDIS_URL` | `redis://:your_password@localhost:6379/0` | Used to cache change approval status and user permission information to improve process response speed |
| `STORAGE_S3_ENDPOINT` | `http://localhost:9000` (local deployment) or cloud service provider endpoint | This scenario includes a large number of attachments such as drawings and process validation reports, so unified storage management is required |
| `FILE_TOKEN_KEY` | 32-bit random encrypted string | Used to encrypt attachment access tokens to ensure the security of access permissions for change-related files |
| `DB_MAX_LINK` | `100–200 concurrent connections` | Adapt to the needs of concurrent access to change data from multiple systems, set the connection upper limit based on actual measurements |

## Three Common Configuration Mistakes
- Symptom: After upgrading to FastGPT v4.17.0, custom models configured in simple applications do not take effect, and chats automatically switch to other preset models. Cause: `FE_DOMAIN` and model service association configuration were not updated correctly, causing front-end requests to point to incorrect model interfaces.
- Symptom: After Docker deployment of this scenario, a connection failure error with status code 500 pops up when entering the workflow editor. Cause: `REDIS_URL` or `PG_URL` was not configured correctly, causing the system to fail to connect to the cache or relational database and unable to load workflow configurations.
- Symptom: After local deployment, the system prompts incorrect username or password when logging in, and the background management interface cannot be accessed. Cause: The `ROOT_KEY` parameter was not initialized correctly, or the default administrator account password was not reset after initialization, causing permission verification failure.

## How to Verify Correct Configuration
- Run a database connection test command to verify that the instances configured with `MONGODB_URI` and `PG_URL` can establish normal connections.
- Upload a process validation report attachment to verify that the storage service configured with `STORAGE_S3_ENDPOINT` can store and download files normally.
- Initiate a simulated change application to verify that the cache service configured with `REDIS_URL` can synchronize approval status normally.
- Log in to the system with an administrator account to verify that the permission control configured with `ROOT_KEY` can normally restrict unauthorized users from accessing the change management module.
