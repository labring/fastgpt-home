# Supplier and Process Quality Audit for Non-Ferrous Metal Smelting and Electrolysis: HTTP Interfaces and External Systems

## What data looks like for this category
This category’s data originates from concentrate and auxiliary material analysis, DCS systems, cell voltage and current monitoring, laboratories, and energy and environmental monitoring equipment. Update frequency aligns with business nodes. Corresponding records generate for each raw material batch, each furnace, or each electrolytic cell. Key parameters synchronize in real time. Daily documents include batching lists, smelting records, electrolytic cell status records, test reports, anode and cathode quality records, and environmental protection ledgers. Fields cover raw material composition indicators, equipment operating parameters, test results, and environmental emission data. Units include mass units, current and voltage values, time units, and similar measurement units.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Multi-source data access increases the complexity of interface request parameters. Interfaces require adaptation to data field mapping rules from different sources including concentrate analysis, equipment monitoring, and test results. Different update frequencies require interfaces to support both on-demand triggering and scheduled polling modes. These modes match scenarios such as real-time cell status monitoring and batch raw material record synchronization. The diversity of document fields requires interface request bodies to bind business fields via dynamic variables. This avoids hard-coded adjustments for different data sources. Business errors have clear consequences, so interfaces require built-in parameter verification and failure retry mechanisms. These mechanisms ensure the accuracy and timeliness of data transmission.

## How to configure
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {custom API key}` | Ensures identity security for interface access, complies with compliance requirements for industrial data transmission, and adapts to the authentication logic of FastGPT v4.17.0 |
| `variables` | Bind business fields such as batching lists and electrolytic cell status | Adapts to field differences across multi-source documents, no need for hard-coded adjustments to request parameters |
| `responseData` | Extract the first 8 valid records under the `data` array | Focuses on core data required for audits, filters redundant content |
| Request timeout | 600 seconds | Adapts to processing duration for multi-source data aggregation, prevents request interruptions caused by large data volumes |
| Retry count | 3 times | Addresses scenarios such as temporary network fluctuations or temporary unavailability of third-party systems |
| Parameter verification switch | Enabled | Intercepts requests with missing fields or incorrect formats in advance, reduces the probability of business errors |

## Three common configuration errors
- Empty values return after calling the interface. The cause is failure to bind business fields such as batching lists and electrolytic cell status via the `variables` parameter. The request body lacks core data required for audits.
- HTTP return results are incomplete, only showing partial fields. The cause is incorrect configuration of the `responseData` extraction rule. The system fails to fully read the returned JSON data structure.
- Interface request triggering fails, returning a 401 status code. The cause is incorrect setup of the `Authorization` parameter. The system fails to complete identity verification with a valid API key.

## How to confirm configuration is complete
- Send a test request, check whether the `Authorization` parameter is correctly carried in the request header. Use interface logs to confirm whether the identity verification step passes.
- View the binding result of the `variables` parameter, confirm whether business fields are correctly mapped to the request body. Use debugging tools to view the original request data.
- Verify the extraction logic of `responseData`, confirm whether the returned valid data meets the field requirements for audits. Use return result previews to confirm this.
- Simulate abnormal scenarios such as disconnecting the network or delaying third-party system responses. Check whether the retry mechanism triggers normally, and confirm that the failure handling logic takes effect.
