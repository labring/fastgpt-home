# Supplier and Process Quality Audits for Incoming Material Inspection and Supplier Quality: HTTP Interfaces and External Systems

## What this category of data looks like
Data for this category comes from purchase orders, drawing specifications, supplier quality certificates, inspection equipment, historical quality data, and supplier portals.

Daily processed documents include inspection specifications, sampling plans, incoming material reports, supplier audit reports, exception contact sheets, 8D correction sheets, and concession acceptance approval forms.

Data updates follow these patterns: synchronized per incoming batch, supplier evaluations conducted monthly or quarterly, and ad-hoc special audits performed as needed.

Single quality data entries include fields such as batch identifier, supplier code, inspection item details, qualified judgment result, and rectification closed-loop status. Field units change dynamically based on inspection item type, with no unified fixed unit.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Data sources are scattered, and update frequencies vary. Interfaces must support batch retrieval of batch-level data from multiple sources. They must also adapt to ad-hoc triggered audit tasks.

Daily document formats vary. Interfaces must support text and attachment upload requests with different structures.

Data links supplier and batch information. Interface parameters must require two core identifiers: supplier code and incoming batch. This prevents mixing cross-batch data.

Some data comes from offline inspection equipment. Interfaces must support resumable uploads and abnormal reconnections. This prevents interruptions in bulk incoming material data transmission.

Rectification status must sync to external systems in real time. Interfaces must ensure call idempotency. This avoids repeated triggering of rectification processes.

## How to configure
This configuration guide applies to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Fixed prefix plus supplier-specific identifier | Verify external system call permissions, bind supplier identity to prevent unauthorized data access |
| `variables` | Preset incoming batch and supplier code fields | Match batch-based inspection business logic, accurately filter quality data for target batches |
| `responseData` | Only return qualified judgment, rectification status, and batch identifier | Simplify returned content, reduce data processing load on external systems |
| Timeout threshold | 600 seconds | Adapt to long-duration bulk data upload scenarios from offline inspection equipment, avoid task interruption |
| Retry limit | 3 times | Address call failures caused by network fluctuations, ensure completeness of data synchronization |
| Attachment encoding format | UTF-8 | Resolve garbled Chinese filenames, adapt to Chinese inspection report filenames uploaded by suppliers |

## Three common mistakes
- Duplicate requests occur when calling the interface. The `Authorization` field value for the second request is abnormal. No idempotency check is set for the interface. Repeated external system calls generate duplicate requests.
- The `unAuthChat` error is returned. The `Authorization` parameter is not configured correctly. The token prefix does not match the bound supplier identity.
- Garbled characters appear in uploaded inspection report filenames that use Chinese names. The attachment name is not transmitted with UTF-8 encoding. This causes parsing failure in the external system.

## How to confirm successful configuration
- Initiate a simulated call with correct supplier code and incoming batch parameters. Check that the `responseData` returned by the interface only includes three preset fields: qualified judgment, rectification status, and batch identifier.
- Submit an attachment upload request with a Chinese filename. Verify that the filename displays normally without garbled characters on the external receiving end.
- Simulate a network interruption, then retry the call. Confirm that the interface automatically runs the retry. Check that no duplicate data synchronization occurs.
- Initiate calls using supplier-specific identifiers for different suppliers. Verify that only quality data for the corresponding supplier is returned. Confirm there is no risk of cross-entity data leakage.

The values provided are common starting points and should be measured against the reader's own samples.
