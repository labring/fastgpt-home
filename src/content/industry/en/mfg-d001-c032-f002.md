# Supplier and Process Quality Audit for Complete Vehicle Final Assembly: Vector Models and Indexes

## What Data Looks Like for This Category
The data for this category comes primarily from ERP/MES systems, VIN and vehicle configuration systems, supplier batch management modules, tightening tool terminals, end-of-line (EOL) off-line inspection lines, and quality traceability systems. Daily documents include production orders, VIN lists, assembly work instructions, tightening torque data, off-line inspection reports, rework records, and consistency release documents.
Data updates happen in real time per vehicle, with batch synchronization per shift. Core fields include unique VIN codes, assembly torque values, supplier batch numbers, inspection qualification status, and more. Each data entry is linked to the full assembly, inspection, and rework information for its corresponding complete vehicle.

## Constraints Imposed on Vector Models and Indexing
This category uses VIN as the core thread to link full-process quality data for a single vehicle. Vector indexes must support precise filtering and recall using the VIN field, to prevent irrelevant complete vehicle data from interfering with recall results.
The high-frequency real-time update rhythm requires indexes to support incremental writing. Full index reconstruction is not needed for each update, to align with production beat requirements.
There are clear structural differences across document types. Assembly work instructions are long texts, while tightening data is short numeric text. A unified chunking logic must be used to adapt to input content of varying lengths and types.
Single-batch data volume increases with mixed-line production scale. Memory usage for single-batch indexes must be limited, to avoid service overload.

## Configuration Settings
The following configurations are based on the interface parameter settings of FastGPT v4.17.0.

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to single-station long text in assembly work instructions, while avoiding excessive chunk length that causes vector calculation overflow |
| Overlap Length | 100–200 characters | Retains contextual connection between adjacent chunks, ensuring VIN and assembly step information is not truncated during chunking |
| Similarity Threshold | 0.75–0.85 | Filters low-match recall results, meeting accuracy requirements for quality information in vehicle final assembly scenarios |
| Single Search Limit | Top 20 entries | Controls the number of recall results, preventing excessive irrelevant data from occupying the context window |
| `maxToken` | Set to the selected embedding model/service maximum supported input tokens | `maxToken` is the input-token maximum supported by the selected embedding model/service; verify it in that provider configuration. See the [v4.17.2 model-field reference](https://github.com/labring/FastGPT/blob/v4.17.2/document/content/self-host/config/model/intro.mdx). It is not retrieval/LLM context or a FastGPT-wide fixed cap. |
| `defaultToken` | 1500 tokens | Balances single-round question answering input length and model inference efficiency, adapting to the complexity of audit scenarios |

## Three Common Misconfigurations
- Symptom: Vector indexing tasks stay in a waiting state with no progress. Cause: Incremental indexing rules triggered by production beat are not configured. Full index reconstruction is used to adapt to real-time updated production data, leading to indexing task backlog.
- Symptom: Recall results are irrelevant to the query and do not link to quality information of the target VIN. Cause: Filtering configuration by VIN field is not enabled. The recall scope covers all complete vehicle data, resulting in irrelevant results being included.
- Symptom: Indexing tasks throw timeout errors. Cause: Values of `defaultToken` and `maxToken` are not adjusted. Excessively long single chunks cause vector calculation timeouts, or the single search limit is set too high, exceeding service carrying capacity.

## How to Confirm Configurations Are Correct
- Check indexing task logs to confirm incremental write trigger rules are configured according to production beat, with no repeated full index reconstruction tasks.
- Input an audit question containing a specific VIN, verify that recall results only return assembly, inspection, and rework data associated with that VIN.
- Test queries of varying lengths, confirm that context concatenation does not exceed the `maxToken` setting range, with no truncation errors.
- View knowledge base chunk statistics, confirm that single chunk lengths fall within the preset range, with no abnormal chunks.

The values provided are common starting points and should be measured against the reader's own samples.
