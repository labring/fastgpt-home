# Supplier and Process Quality Audit for Baking and Convenience Foods: Vector Models and Indexing

## What data looks like for this category
Factories producing bread, pastry, biscuits, instant noodles, and frozen pastries are the typical entities for this category. Daily documents include formulas and ingredient lists, production records, baking or steaming curves, metal detection records, cleaning and disinfection records, and factory inspection reports. Data sources cover raw and auxiliary material qualification certificates, ERP/MES systems, weighing systems, production equipment, laboratories, and food trace ledgers. Updates run per production batch, shift, or daily. Most document fields include batch numbers, raw material names, quantitative parameters, and test results. Some documents include time stamps and unit identifiers.

## Constraints on vector models and indexing
The data characteristics of this category create multiple constraints for the vector model and indexing workflow. Documents updated frequently per batch or shift require indexes to support incremental synchronization and rapid refreshing. This avoids excessive time spent on full index reconstruction. Multi-field document structures with quantitative parameters require embedding models to accurately associate text descriptions with numerical information. This ensures semantic capture accuracy. Professional documents related to allergens and foreign matter control require embedding models to adapt to specialized terminology in the food processing field. Frequent product line changes lead to variable document structures. Index chunking rules must be compatible with text types of different lengths.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Adapts to the average length of documents such as formulas and production records for this category, covering complete semantic units |
| Overlap Length | 50–100 characters | Avoids semantic breaks caused by chunking, ensuring continuity of information across chunks |
| `defaultToken` | 8192 token | Matches the context window limit of the qwen3-embedding-8b model, and adapts to the long document processing requirements of FastGPT v4.17.0 |
| `maxToken` | 1024 token | Controls the generation length of a single embedded vector, balancing semantic accuracy and indexing storage overhead |
| Similarity Threshold | 0.75–0.85 | Ensures relevance of recall results, adapting to the strict matching requirements of food quality audits |
| Single Index Limit | Top 200 entries | Controls the number of documents processed in a single batch, avoiding overload of deployment resources |

## Three common configuration errors
- Index tasks remain stuck in the "Indexing" state with no progress updates. Cause: The access address and permissions of the embedding model are not configured correctly, or the `maxToken` setting exceeds the supported range of the model, causing the embedding generation process to time out and interrupt.
- After adding a new embedding model configuration, the existing configuration with the same name is automatically overwritten. Cause: Unique identifiers are not used to distinguish different model instances, and only the model name is used as the configuration key, causing the system to overwrite duplicate writes.
- Key document fields such as batch numbers and test values are missing from recall results. Cause: The chunk length is set too small, splitting complete text containing associated fields into semantically broken fragments, causing vectors to fail to capture the association between fields.

## How to confirm configurations are set correctly
- The embedding model configuration page is reviewed to confirm that the target model has been added correctly and there are no duplicate configuration entries.
- A typical document of this category is uploaded to trigger a manual indexing task, and the update process of the task status is observed.
- Test queries related to food quality audits are entered, and the matching logic of recall results is verified against business requirements.
- Disk usage and memory usage of index storage are checked to confirm that configured indexing processing does not experience resource overload.

The values provided are common starting points and should be measured against the reader's own samples.
