# Supplier and Process Quality Audit for Production Planning and Shop Scheduling: HTTP Interfaces and External Systems

## What the data for this category looks like
Core data for production planning and shop scheduling comes from ERP orders and inventory, BOM and process routes, equipment capacity, staff shifts, work-in-progress, and supplier deliveries. Daily generated documents include sales orders, master production schedules, material requirements plans, weekly scheduling tables, work orders, material shortage lists, and delivery change notices.
Data update frequency is usually daily, weekly, or triggered by order changes or exceptions. Data fields include order number, material code, process number, planned capacity, actual output, delivery date, pass rate, and others. Units include pieces, hours, days, and percentage.

## What constraints these characteristics impose on HTTP interfaces and external systems
These characteristics impose the following constraints on HTTP interfaces and external systems.
First, multiple heterogeneous data sources require interfaces to support cross-system data pulling, and adapt to parameter formats of different external systems.
Second, uncertain update frequencies require interfaces to support both on-demand calling and scheduled triggering modes, balancing real-time performance and resource usage.
Third, complex document structures require interface parameters to support batch field mapping, and accurately return core data required for supplier and quality audits.
Fourth, diversity of fields and units requires interfaces to unify data formats, avoiding scheduling calculation errors caused by unit mismatches.
Finally, data volume grows with the number of work orders. Interfaces must support paginated returns to prevent overload from single requests.
FastGPT v4.17.0 provides corresponding configuration capabilities to address these constraints.

## How to configure the settings
Under FastGPT v4.17.0, configure HTTP interfaces and external systems according to the following rules:

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${JWT_TOKEN}, valid for 12 hours` | Production planning and quality audit data are internal sensitive information. Short-expiry tokens reduce the risk of data leaks. |
| `variables` | Pass up to 50 work order IDs, material codes, and pass rate thresholds | Matches core fields of category data, enabling accurate pulling of scheduling data related to suppliers and quality audits. |
| `responseData` | Return work order status, scheduling progress, material shortage list, and pass rate fields | Aligns with business requirements, filters irrelevant data, and improves interface call efficiency. |
| Interface timeout setting | 300-600 seconds | Scheduling data calculation takes a long time. This avoids early request termination leading to incomplete data. |
| Data synchronization trigger rule | Trigger real-time synchronization on order changes, perform full synchronization weekly | Adapts to the update frequency of category data, balancing real-time performance and system resource usage. |

## Three common configuration mistakes
- Symptom: Interface calls return the `401 Unauthorized` status code, and scheduling data cannot be obtained. Cause: The `Authorization` parameter does not carry a valid token, or the token has expired. This fails to comply with identity verification requirements for sensitive data.
- Symptom: Quality audit images uploaded via the interface are inaccessible after 1 minute. Cause: The interface does not have a persistent storage path configured. Temporary cached image resources are automatically cleaned up by the system. This matches a common issue of failed uploaded resources in actual use.
- Symptom: Custom external system calls fail, and returned fields are missing. Cause: Required core business fields are not specified in `variables` or `responseData`. The interface filters out data related to quality audits by default.

## How to confirm the configuration is correct
- Call the configured interface with a valid `Authorization` token. Confirm the returned status code is `200 OK` to verify that the identity verification configuration takes effect.
- Pass test work order IDs and material codes. Check if `responseData` includes preset core fields such as scheduling progress and material shortage list to verify that the field mapping configuration is correct.
- Simulate an order change event to trigger an interface call. Confirm that returned data is updated synchronously with the change content to verify that the trigger rule configuration is valid.
- Test the timeout scenario. Set the request duration to exceed 300 seconds. Confirm that the interface returns valid results within 600 seconds to verify that the timeout setting is reasonable.
