# Supplier and Process Quality Audit for Biologics and Aseptic Manufacturing: HTTP Interfaces and External Systems

## What the data for this category looks like
Typical data for this category comes from cell banks and seed lots, process analytics, cleanroom monitoring, MES, LIMS, and equipment integrity testing systems. Daily documents include cell bank or seed lot records, culture and purification records, aseptic filling records, environmental monitoring data, media fill simulation results, sterility test reports, and batch release documents. Data update rhythms fall into three categories: after each production batch completes, triggered by real-time monitoring, and executed per a fixed monitoring plan. Core fields include batch identifier, test item name, result value, and timestamp. Some test items have dedicated units, such as colony-forming units per cubic meter, degrees Celsius, hours, and others.

## What constraints these characteristics impose on HTTP interfaces and external systems
Data sources are scattered, requiring integration with HTTP interfaces from multiple external systems. This necessitates support for multiple endpoint configurations and differentiated authentication rules. Data update rhythms vary, so interfaces must support both scheduled pull and real-time trigger invocation modes to meet the needs of different data types. Document fields are tightly bound to business requirements, so precise specification of return fields is needed to avoid irrelevant data disrupting audit workflows. High data association requirements mean batch numbers and other parameters must be used to link seed lots, process records, and release documents. Interfaces must therefore support parameterized queries. Additionally, the severe consequences of errors require interfaces to have strict authentication and data validation rules to prevent incorrect data from entering audit processes.

## How to set configurations

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `Authorization` | Bearer Token format, bound to enterprise-specific authentication keys | Strictly restrict unauthorized access to protect sensitive production and quality data |
| `variables` | Pass business parameters such as batch numbers and test item types | Accurately pull quality audit-related data for the corresponding batch, avoiding redundant requests |
| `responseData` | Only return core business fields such as batch numbers, test results, and timestamps | Reduce invalid data transmission and adapt to the streamlined processing needs of production data |
| Scheduled pull interval | 15–60 seconds (real-time monitoring data), triggered after each production batch ends (batch record data) | Match data update frequency, balancing data timeliness and interface call costs |
| Failure retry count | 3 times, 10-second interval | Respond to temporary network fluctuations while avoiding data confusion caused by repeated submissions |
| Return data validation rules | Validate aseptic test results and environmental parameter ranges against business thresholds | Ensure accessed data meets production requirements and prevent incorrect data from entering the audit process |

## Three Common Mistakes
- Phenomenon: An empty result is returned after calling the interface, and batch release documents in LIMS cannot be pulled. Cause: The correct batch number parameter was not passed in the `variables` parameter, causing the interface to fail to match the corresponding business data.
- Phenomenon: The interface returns a `403 Forbidden` status code. Cause: The `Authorization` parameter was not configured as required, and an expired authentication key was used, causing access to be denied.
- Phenomenon: The `responseData` returned by the interface contains a large number of irrelevant device operation log fields. Cause: No return field filtering rules were configured, and non-audit-required data was pulled, increasing subsequent processing burden.

## How to verify configuration is effective
- Call the interface and pass a test batch number, check if the `responseData` contains the expected core business fields, and verify that the return field filtering configuration is effective.
- Initiate a request using valid enterprise-specific authentication information, confirm that no `401` or `403` status codes are returned, and verify that the `Authorization` configuration is correct.
- Simulate a temporary network interruption and retry the request, confirm that the interface automatically reconnects according to the configured retry count, and verify that the failure retry logic is effective.
- Configure a scheduled pull task with the corresponding update cycle, wait for the cycle to end, check if new batch data is successfully pulled, and verify that the scheduled trigger configuration is effective.
