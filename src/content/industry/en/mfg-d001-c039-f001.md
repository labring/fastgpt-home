# Supplier and Process Quality Audit for Electric Motor and Generator Manufacturing: HTTP Interfaces and External Systems

## What Data Looks Like for This Category
Data for this category comes from winding, insulation, final assembly, and testing departments of electric motor factories and power equipment enterprises. Daily documents include winding process cards, insulation treatment records, dynamic balance reports, voltage withstand insulation test data, and type and factory inspection reports.
Data sources cover electromagnetic design data, copper wire and insulation material batch information, winding equipment, balancing machines, electrical test benches, and ERP/MES systems. Updates are synchronized for each product, each material batch, or each type change.

## What Constraints Do These Characteristics Impose on HTTP Interfaces and External Systems?
The data characteristics of this category impose multiple constraints on the HTTP interfaces and external systems link.
Multiple data sources require interfaces to support integration with various external nodes such as ERP/MES, test equipment, and material management systems. Interfaces must be compatible with different system field formats.
The high-frequency update rhythm requires interface response delay to be controlled within a reasonable range. This prevents delayed data from disrupting audit workflows.
The rich document fields require interfaces to support precise field mapping. This ensures accurate transmission of core information such as winding turns, insulation parameters, and test data.
The severe consequences of errors require interfaces to have complete failure retry and data verification mechanisms. This prevents abnormal data from entering the audit link.

## Configuration Settings
These configuration items are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Application-specific key | When integrating with internal audit systems and test equipment interfaces, an application-specific key is required for authentication. This ensures controlled access to data. |
| API Request Timeout | 30–60 seconds | This category has frequent data updates and large core test data transfer volumes. A timeout that is too short may cause data pull failures. A timeout that is too long will block audit workflows. |
| `variables` | Bind winding batch numbers and test bench numbers | This enables precise pulling and association of data for individual units or batches of motors. It matches the batch processing logic of audit workflows. |
| `responseData` | Return only core fields such as winding turns, insulation thickness, and dynamic balance values | This filters redundant data, reduces interface transmission load, and improves audit efficiency. |
| Retry Count | 2–3 times | This addresses temporary interface call failures caused by network fluctuations. It reduces the need for manual intervention. |
| Data Verification Thresholds | Calibrate based on actual measurements | There are no universal standard thresholds for core parameters in this category. Adjustments must be made based on internal enterprise process standards.

## Three Common Configuration Errors
- Receiving an "Insufficient Permissions" error when calling the `api/v1/chat/completions` interface. Cause: Using a generic key for authentication instead of the application-specific key corresponding to the audit scenario. This causes a mismatch in interface permissions.
- Receiving empty fields when creating a knowledge base collection via `api/core/datas`. Cause: Not binding the required field mappings for winding process cards and test reports in `variables`. This causes the interface to fail to recognize valid data parameters.
- Audit results after importing MySQL data into the knowledge base do not match actual production batches. Cause: Not configuring the scheduled synchronization interface according to the per-unit or per-batch update frequency of this category's data. This causes imported data to lag behind production progress.

## How to Verify Proper Configuration
- Call the authentication interface to verify the `Authorization` configuration. Confirm that the returned status code is 200.
- Send a request to pull data for a single batch of motors. Check that the `responseData` returned fields match the preset core audit parameters.
- Simulate a network fluctuation scenario to verify that the interface retry mechanism triggers correctly.
- Adjust data verification thresholds based on internal enterprise process standards. Verify that the parameter verification logic takes effect.

The values provided are common starting points and should be measured against the reader's own samples.
