# Supplier and Process Quality Audit for Battery PACK and Energy Storage System Integration: Workflow Orchestration

## What Data Looks Like for This Category
Data sources for this category include cell capacity grading data, MES systems, welding equipment, torque tools, BMS software version records, and EOL test bench data.
Data is updated once per produced battery pack or energy storage cabinet, and synchronized whenever the BMS software version changes.
Daily documents include grouping rules, BOM lists, welding torque records, BMS flashing logs, insulation and voltage withstand reports, EOL test reports, and system configuration lists.
Fields cover cell capacity grading capacity, welding torque values, insulation resistance, BMS version numbers, and more, with corresponding units such as Ah, N·m, MΩ.

## Constraints on Workflow Orchestration
Multiple scattered data sources require workflow orchestration to integrate output nodes from different devices and systems. Configure parsing rules adapted to different log formats.
High-frequency, single-device-level data updates require workflows to support cyclic processing of full audit flows for individual battery packs or energy storage cabinets. This avoids missing individual anomalies during batch processing.
Document requirements for specific fields and units require workflow variable configurations to be strictly bound to corresponding business fields. This prevents audit failures caused by unit mismatches.
High-risk error consequences require workflows to set clear failure branches. Trigger verification interception and alert actions at abnormal nodes.

## How to Configure
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Loop node trigger condition | Triggered by audit data packets for a single device | Matches the single-device-level data update frequency of this category, avoids missing individual anomalies during batch processing |
| Global variable configuration | Only bind business fields within the current loop context | Prevents interference from global variables outside the loop body, complies with FastGPT v4.17.0 variable scope rules |
| Code execution node input | Only pass `variables` data from the current node | Avoids verification failures caused by conflicts between historical records and global variables |
| Failure retry configuration | Retry 2 times, with a 30-second interval | Addresses temporary communication exception scenarios with welding equipment and EOL test benches |
| Exception branch handling | Trigger an alert and terminate the current process | Matches the high-risk error consequences of this category, prevents unqualified products from entering subsequent links |
| Node identifier binding | Bind `nodeId` to the device's unique serial number | Accurately track the audit process for each battery pack or energy storage cabinet, facilitating problem traceability |

## Three Common Misconfigurations
- Loop nodes cannot access externally defined global variables. The symptom is empty fields when external variables are called inside the loop body. The cause is workflow variable scope restrictions: loop nodes can only access `variables` data bound to the current context.
- Code execution nodes trigger verification failures due to included historical records. The symptom is an error message "Input contains illegal historical records" when submitting configurations. The cause is failure to clear historical context data from node inputs, leaving only business fields required for the current audit.
- Variable reference format errors occur when writing to the audit body. The symptom is fields appearing as placeholders in generated audit reports. The cause is failure to bind corresponding fields from `variables` according to business document naming rules, leading to parsing failures.

## How to Verify Proper Configuration
- Traverse the audit process for a single device. Confirm the loop node only processes data packets for that device, and check that input data in node logs matches the device’s BOM and test records.
- Trigger the code execution node. Verify input parameters only include `variables` data from the current context, with no external global variables or historical records.
- Simulate an exception scenario, such as non-compliant welding torque. Check if the exception branch triggers an alert and terminates the process.
- Confirm the device serial number bound to `nodeId` matches the actual production device identifier, to ensure accurate process tracking.
