# Supplier and Process Quality Audit for Petroleum Refining: HTTP Interfaces and External Systems

## What data looks like for this category
Data sources for petroleum refining scenarios include DCS/APC, LIMS, tank farm metrology, crude oil evaluation, equipment management systems, and energy systems. Data update frequencies are divided into three categories: real-time, shift-based, and daily. It covers multiple types of documents including operating procedures, production plans, material balance, distillate export quality reports, interlock ledgers, shift handover records, and change management documents. Data fields include crude oil properties, unit load, product fractions, quality indicators, equipment status, and more. Some fields carry engineering units such as density, temperature, and flow rate.

## What constraints do these characteristics impose on the HTTP Interfaces and External Systems link
Multi-source industrial system data access requires interfaces to adapt to different authentication rules and data formats, and must comply with the docking specifications of various refining production systems. Requirements for different update frequencies require interfaces to support flexible polling and triggering mechanisms to avoid data lag or repeated pulling. Differences across multiple audit documents require interfaces to adapt to multiple request and response body formats to meet transmission requirements for different materials such as quality reports and scheduling logs. Data is linked to multiple units and logistics networks, so the stability of interface calls directly affects audit efficiency and production safety.

## How to Set Up the Configuration
This configuration is adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` authentication header | Carry a static token in Bearer format | Meet the API authentication requirements of most industrial systems, and ensure the transmission security of refining production data |
| `variables` binding field | Bind real-time flow data from DCS/APC and LIMS test result fields | Automatically synchronize dynamic production parameters and reduce manual entry errors |
| `responseData` filtering rules | Extract core fields of distillate export quality and material balance | Focus on key data required for audits and reduce interface transmission load |
| Request timeout threshold | 300–600 seconds | Adapt to the response duration of long-cycle businesses such as crude oil property coordination and multi-unit load adjustment |
| Retry trigger condition | Response status code 5xx or timeout | Respond to temporary fluctuations in industrial systems and improve interface call stability |

## Three Common Mistakes
- An interface call returns a 401 unauthorized error. Investigation reveals that the `Authorization` header does not correctly carry the token. The cause is failure to match the authentication rules of the refining system, or the static token has expired or has an incorrect format.
- When transmitting a TXT-format quality report file, the backend cannot parse the content. The cause is failure to configure the correct request header Content-Type as text/plain, resulting in failed file format parsing.
- The number of returned results after scheduled interface calls does not match expectations. The cause is failure to adjust the polling interval based on the update frequency of refining data, leading to repeated data pulling or missed data.

## How to Confirm the Configuration Is Correct
- Call the test interface and check whether the `Authorization` field is included in the request header to confirm that the authentication configuration takes effect.
- Trigger a test request for variable binding to verify whether the `variables` field automatically synchronizes the latest production data.
- Check the `responseData` content returned by the interface to confirm that only the core fields required for audits are included.
- Simulate a long-cycle business request to verify whether the timeout threshold configuration covers the normal response duration.

The values provided are common starting points and should be measured against the reader's own samples.
