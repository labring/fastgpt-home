# Supplier and Process Quality Audit for Equipment Inspection and Preventive Maintenance: HTTP Interfaces and External Systems

## What data for this category looks like
Data for this category comes from daily operations of manufacturing enterprise equipment departments, workshop maintenance teams, and public utility departments. It includes equipment ledgers, inspection checklists, maintenance plans, work orders, fault analysis, spare parts lists, and special equipment inspection records. Data sources include EAM/CMMS systems, equipment sensor collection data, operator inspection records, maintenance history archives, spare parts inventory data, and statutory inspection information. Update cycles cover shifts, daily, weekly, monthly periods, and emergency fault scenarios. Fields include equipment numbers, inspection items, measured values, spare part codes, inspection validity periods, and are dynamically adjusted based on business workflows.

## What constraints these characteristics impose on HTTP interfaces and external systems
Data sources for this category are scattered, including structured system data and unstructured inspection records. HTTP interfaces must support request bodies in multiple formats. Update frequencies range from real-time sensor data to monthly inspection reports. Interfaces must adapt to different request intervals, and support both batch and single-item data transmission. Equipment ledgers and spare parts lists must align with EAM/CMMS systems in real time. Interfaces must carry the `Authorization` parameter for identity verification. Emergency fault scenarios require fast data synchronization triggers. Interfaces must set reasonable timeout thresholds to avoid blocking production processes.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Authentication Header | Carry the `Authorization` header with a Bearer token value | Adapt to permission verification requirements for cross-domain calls between multiple systems, and protect the security of core equipment data |
| Request Timeout Threshold | 600 seconds | Cover processing durations for batch inspection data synchronization and large-scale equipment sensor data uploads |
| Batch Submission Limit | First 100 entries | Match the single submission scale of per-shift inspection checklists, avoiding interface overload that disrupts production processes |
| Response Data Parsing | Return structured results via the `responseData` field | Facilitate direct parsing of inspection qualification status and fault markers by workshop systems |
| Context Variable Binding | Bind the `variables` parameter to carry equipment numbers | Accurately match the inspection task context for individual equipment, avoiding data confusion |

## Three Common Configuration Mistakes
- Phenomenon: The interface returns a 401 Unauthorized status code, or inspection data cannot be synchronized with the EAM system. Cause: The `Authorization` parameter is not carried correctly, or the token has expired and not updated.
- Phenomenon: The interface reports an error when uploading equipment sensor images, and file content cannot be parsed. Cause: Multi-source file formats are not supported, or the file binary stream is not properly encapsulated in the request body.
- Phenomenon: The interface returns a timeout error when submitting a spare parts list in batches. Cause: A reasonable request timeout threshold is not set, or the number of batch submission entries exceeds the interface's carrying limit.

## How to confirm the configuration is complete
This verification process is compatible with FastGPT v4.17.0.
- Call the test interface with a valid `Authorization` token, and check that the return status code is 200 and includes the expected `responseData` field.
- Submit a single inspection record, and verify that the equipment number received by the external system matches the content carried in the `variables` parameter.
- Simulate batch submission of no more than 100 inspection data entries, confirm that the interface does not report overload errors and the external system receives all data completely.
- Simulate an emergency fault scenario, trigger data synchronization quickly, and confirm that the interface response time meets business requirements.
