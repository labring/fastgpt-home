# Supplier and Process Quality Audit for In-Process Quality and Finished Product Release: HTTP Interfaces and External Systems

## What this category of data covers
This category of data covers daily quality control scenarios for manufacturing enterprise IPQC, FQC, quality engineering, and laboratory teams. Daily documents include control plans, patrol inspection records, SPC reports, finished product inspection reports, nonconforming product reviews, release orders, and monthly quality reports. Data sources include MES systems, testing equipment, laboratory systems, process parameter libraries, customer standard libraries, and historical defect libraries. Data update rhythm supports batch-level or per-shift bulk synchronization, or continuous real-time collection triggered by testing equipment or process parameters. Data fields include batch identifiers, inspection item numbers, inspection thresholds, measured results, defect codes, inspector information, approval status, release conclusions, and other items; there is no unified fixed single-document format.

## What constraints do these characteristics impose on the HTTP Interfaces and External Systems link
Multi-source heterogeneous data sources require interfaces to support integration with different types of external systems, and need to adapt to and map the field format differences of each system. Differentiated update rhythms require interfaces to support both scheduled bulk pull and real-time push invocation modes, to match synchronization needs for batch-level, per-shift, and real-time collection. Diverse document structures require the `responseData` returned by the interface to support flexible field parsing rules, to avoid parsing failures caused by format differences across data sources. Severe error consequences require interfaces to configure failure retry and idempotent processing mechanisms, to prevent risks of spread of batch nonconforming issues or improper release of nonconforming products.

## Configuration Settings
The following configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Interface identity verification | `Bearer {third-party system API key}` | Complies with identity verification specifications for manufacturing external systems, and ensures legitimacy of interface invocations |
| Business variable passing | `{"batch number": "{{batch_id}}", "inspection time": "{{inspect_time}}"}` | Passes category-specific business parameters, and accurately matches data query conditions for in-process quality and finished product release |
| Return data processing | Map fields from patrol inspection records and finished product inspection reports to unified key names | Adapts to structural differences of multi-source heterogeneous data, and simplifies downstream data parsing and storage |
| Interface timeout period | 600 seconds | Adapts to time consumption requirements for bulk pulling per-shift patrol inspection data, and avoids request interruptions caused by excessive data volume |
| Failure retry count | 3 times | Addresses scenarios such as temporary disconnection of testing equipment and network fluctuations, and ensures success rate of data synchronization |

## Three common misconfigurations
- An interface invocation failure prompt is displayed, with status code 401 returned. The cause is that the interface identity verification parameter was not configured correctly, and no identity credential compliant with third-party system requirements was carried.
- Pulled inspection data fields are empty or incomplete. The cause is that category-specific business variables (such as batch number) were not passed, leading to the third-party system being unable to match quality data for the corresponding batch.
- Interface request times out and is interrupted. The cause is that the timeout period was not adjusted according to bulk data pulling requirements, and the default short timeout setting cannot complete pulling of large volumes of patrol inspection data.

## How to Confirm Successful Configuration
- Invoke the configured interface, pass test business parameters, and verify that returned data fields match the preset unified key names.
- View interface invocation logs, confirm that identity verification parameters were correctly passed, and no relevant error messages are present.
- Simulate a single bulk data pulling scenario, check whether the request completes response within the preset timeout period.
- Trigger an interface push for nonconforming product review, and confirm that the third-party system can normally receive and store the corresponding data.
