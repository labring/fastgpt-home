# Supplier and Process Quality Audit for General Mechanical Equipment Assembly: HTTP Interfaces and External Systems

## What data looks like for this category
Data for the general mechanical equipment assembly category is generated per single device or order. Core documents include assembly process cards, BOMs, torque records, gap adjustment records, commissioning reports, factory inspection sheets, and packing lists. Data sources cover PLM/ERP systems, part inspection data, assembly tool collection terminals, test benches, MES systems, and customer technical agreements.
Data is updated once per device or order. Fields include component numbers, torque values, gap parameters, test results, and others. Some fields have clear units, such as newton meters and millimeters.

## Constraints on HTTP Interfaces and External Systems
The update cadence per single device or order requires interfaces to support triggering data pulls by individual order or device ID, to avoid pulling redundant bulk data. Data from multiple sources must be aligned across systems via interfaces, such as synchronizing PLM BOM data with MES assembly progress data in real time.
Fields with units require interfaces to retain original field formats to avoid unit conversion errors. The complex document structure and numerous fields require interface requests to support specifying return field ranges, reducing transmission load. Additionally, real-time assembly process data such as torque records requires low-latency transmission, otherwise on-site audit timeliness will be compromised.

## How to configure settings
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Interface timeout setting | 300–600 seconds | Adapt to latency when pulling full assembly process data across systems to avoid request interruptions |
| `Authorization` header configuration | Carry a Bearer-type fixed token | Comply with external system security verification standards, ensure compliance of call permissions |
| Request parameter definition | Pass the `variables` field to bind the order ID | Accurately match full audit data for a single device, avoid pulling redundant content |
| `responseData` filtering rules | Only return specified fields such as assembly process cards and torque records | Reduce transmission load and improve interface response speed |
| Retry interval | 10 seconds | Avoid overloading external systems with frequent retries, balance retry efficiency and system pressure |
| Retry trigger conditions | Status code ≥500 or response timeout | Respond to temporary external system failures, ensure audit processes are not interrupted |

## Three common errors
- Interface calls return empty fields, preventing audit processes from proceeding. Cause: Required assembly record fields are not specified in `responseData`, resulting in default filtering of returned data.
- Multiple consecutive interface calls trigger rate limit blocking. Cause: Reasonable retry intervals and trigger conditions are not set, leading to a large number of duplicate requests in a short period.
- Large model calls prompt for payment arrears, but in-house API balance is sufficient. Cause: The `Authorization` header is not configured correctly, leading the request to be recognized as a platform built-in call and triggering the platform’s billing rules.

## How to confirm configurations are correctly set
- Initiate a manual interface call, verify whether returned data includes preset core fields such as torque values and gap parameters.
- Simulate a temporary outage of the external system, verify whether the interface triggers retries as configured and pulls data normally after system recovery.
- Review call logs to confirm the `Authorization` header is correctly carried, with no permission-related errors.
- Submit a test order ID, cross-check returned data against BOM information in the PLM system.
