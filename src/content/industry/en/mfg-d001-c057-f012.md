# Supplier and Process Quality Audit for Forging and Die Forging: Deployment and Upgrade

## What the data for this category looks like
Business data for forging and die forging originates from raw material quality certificates, furnace heating systems, press collection data, MES systems, non-destructive testing instruments, and customer forging drawings. Data updates occur per piece, per batch, or per furnace run. Covered documents include forging process specifications, cutting cards, furnace heating records, forging process cards, mold life records, heat treatment work orders, and ultrasonic testing reports. Data fields include forging ratio, fiber direction, furnace batch number, testing pressure, heating temperature, and additional metrics. Corresponding units include percentage, millimeters, degrees Celsius, megapascals, and others. Individual document sizes are typically large.

## Constraints imposed by these characteristics during deployment and upgrade
Because data updates happen at high frequency and are triggered per batch or furnace run, deployments must adapt to high-frequency, small-batch write requests to avoid connection pool exhaustion. Multiple heterogeneous data sources require deployments to support access to diverse data formats. Upgrades must add new field extraction rules to accommodate new forging part testing parameters. Individual document sizes are typically large, so deployments must provision sufficient storage resources. Upgrades must also maintain stability during the data validation step to prevent subsequent audit workflows from failing due to incorrect data formats. Errors in this category carry severe consequences. Upgrades must add pre-validation configurations to prevent unqualified data from entering the knowledge base.

## Recommended configuration settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–150 connections` | Forging data is written at high frequency per batch or furnace run. This value balances concurrent requests and resource usage to avoid connection pool exhaustion. |
| `MONGODB_URI` | `Cluster address with read-write separation flag` | Multiple data sources perform simultaneous writes and retrievals. Cluster deployment ensures system stability and supports storage requirements for large volumes of forging batch data. |
| `REDIS_URL` | `Single-instance address with persistence configuration` | Caches frequently accessed forging batch information to reduce database read/write pressure and support high-frequency query scenarios. |
| `STORAGE_S3_ENDPOINT` | `Endpoint address adapted to local or object storage` | Large individual documents such as ultrasonic testing reports and furnace heating records require distributed storage to ensure normal upload and reading. |
| `FILE_TOKEN_KEY` | `Random key calibrated via actual testing, minimum 32 characters in length` | Ensures access security for uploaded forging-related documents and prevents unauthorized access to sensitive quality data. |
| `ROOT_KEY` | `Fixed key only used for initialization` | Restricts unauthorized modification of system configurations and complies with permission control requirements for supplier quality audits. |

## Three common mistakes
- Phenomenon: Calling the `/v2/parse/file` API returns a 404 error or cannot find the corresponding code. Cause: Failed to properly pull the open-source code for pdf-marker v2, and the corresponding parsing module was not mounted during deployment.
- Phenomenon: Uploading knowledge base files fails, and logs indicate insufficient storage permissions. Cause: Did not configure storage permissions corresponding to `STORAGE_S3_ENDPOINT`, or did not open read/write permissions for the file upload directory during local deployment.
- Symptom: Plugin validation or loading fails with a MongoServerError. This error alone does not establish that MongoDB 4.4.29 is incompatible with FastGPT; inspect the complete logs, the database request issued by the plugin, and account permissions. The v4.17.2 deployment config defaults to MongoDB 5.0.32 and documents 4.4.29 as a fallback for CPUs without AVX (see [the official deployment configuration](https://github.com/labring/FastGPT/tree/v4.17.2/deploy/version/main)).

## How to confirm configurations are correct
- Run a database connection test to verify that the `MONGODB_URI` and `REDIS_URL` configurations can establish normal connections, with no timeout or permission errors.
- Upload an ultrasonic testing report with a size not exceeding 1000 MB to verify that the `STORAGE_S3_ENDPOINT` configuration can store files normally and return a valid access path.
- Initiate a vector generation request for forging batch data to verify that no connection pool overflow errors occur under the `DB_MAX_LINK` configuration.
- Check the `ROOT_KEY` configuration to confirm that only authorized administrators can access the system configuration page, with no risk of unauthorized modification.

The values provided are common starting points and should be measured against the reader's own samples.
