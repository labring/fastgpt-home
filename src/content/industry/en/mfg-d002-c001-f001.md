# PCB Manufacturing Process Document and Exception Report Drafting: HTTP Interfaces and External Systems

## What data for this category includes
PCB manufacturing category data comes from customer-provided Gerber files, drill files, and BOM lists, combined with factory CAM systems, lamination/drilling equipment parameters, bath solution test results, AOI inspection reports, electrical test reports, and laboratory slice reports. Data is updated by production batch and work shift. Some equipment data is collected continuously. Documents include engineering production instructions, drilling parameter tables, lamination temperature curves, chemical solution concentration records, and defect statistics sheets. Fields include layer number, drilling aperture (unit: mm or mil), lamination pressure (bar), defect location coordinates, and conduction resistance value (Ω).

## Constraints on HTTP Interfaces and External Systems
Data sources are scattered and have varying formats. HTTP interfaces must connect multiple types of external systems. The interfaces must support mixed transmission of binary files (Gerber), structured tables (parameter tables), and time-series data (bath solution tests). Following the update rhythm of production batches and continuous data collection, the interfaces must support batch requests and high-frequency small-data submissions. Single-batch data volume may increase as the number of PCB layers rises. Process documents and exception reports must associate multi-source data. The interfaces must carry business identification fields to match corresponding production batches and avoid data confusion. Exception report fields must align with device output formats. The interfaces must support custom field mapping to adapt to output structures of different devices.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Fixed factory-specific key with prefix, such as `Bearer sk-xxxxxx` | Complies with FastGPT v4.17.0 API authentication specifications, ensuring external system call permissions are controllable |
| Single request data limit | 1000 records | Adapts to typical data volume of a single production batch, avoiding interface timeouts |
| Response timeout threshold | 60 seconds | Covers the conventional time required for multi-source data splicing and format conversion |
| `responseData` field mapping | Map external system output field names to standard process document fields | Ensures external system data can be directly written to the FastGPT knowledge base |
| `variables` bound parameters | Production batch number and customer ID as required parameters | Associates multi-source data with corresponding production tasks, preventing data disorder |
| Interface retry count | 3 times | Addresses call failures caused by network fluctuations, ensuring data synchronization stability |

## Three Common Misconfigurations
- An interface call returns a 401 Unauthorized error. Investigation shows the `Authorization` parameter does not include the factory-specific key. The cause is failure to configure the key prefix according to FastGPT authentication rules, resulting in authentication failure.
- After pulling process data from an external system, the corresponding drilling parameter fields in the FastGPT knowledge base are empty. The cause is failure to configure `responseData` field mapping rules, and failure to map the corresponding fields from device output to standard fields in the FastGPT knowledge base.
- An interface call times out. A single request carries slice report data with more than 1000 records. The cause is failure to set a single request data limit, exceeding the interface's processing capacity and causing a timeout.

## How to Verify Proper Configuration
- Call the test interface, check that the response header includes correct authentication information, confirming the `Authorization` configuration is active.
- Import single-batch test data, verify that the process document fields generated in the FastGPT knowledge base match the external system output fields, confirming the `responseData` mapping configuration is correct.
- Initiate multiple high-frequency requests, observe interface call status, confirming timeout and retry configurations cover conventional network fluctuations.
- Initiate a request with bound `variables` parameters, check that the generated document is associated with the correct business identification, confirming the variable configuration is active.

All provided configuration values are common starting points, and should be evaluated against relevant samples.
