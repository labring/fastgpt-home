# SMT Chip Mounting and Electronic Assembly: Process Document and Exception Report Drafting via HTTP Interfaces and External Systems

## What data looks like for this category
SMT chip mounting and electronic assembly process and exception data originates from customer BOMs, Gerber files, coordinate files, MES systems, solder paste and component batch records, placement machines, SPI/AOI inspection equipment, and reflow oven temperature data. Daily documents include BOMs and coordinate files, line change lists, stencil records, furnace temperature curves, first article confirmation reports, SPI/AOI defect reports, maintenance records, and traceability labels. Data updates run in real time for each work order or line change. Some inspection data syncs at millisecond intervals. Data fields include part numbers, reference designators, component batch numbers, furnace temperature parameters, defect types, defect counts, and more. Coordinate units use millimeters. Furnace temperature units use degrees Celsius.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Data sources for this category are scattered and update frequency is high. Teams must connect to multiple internal systems including MES, placement machines, and inspection equipment. HTTP interfaces must support dynamic reception and format conversion for multi-source data. SPI/AOI defect data has strict real-time requirements, so interfaces must support high-frequency calls and deliver low-latency responses. Different document structures vary widely. For example, BOM files include multiple part number and reference designator pairs. SPI reports include defect classification statistics. So `variables` must support passing dynamic data for different scenarios. `responseData` must adapt to different return field parsing rules. Additionally, single work order data volumes are large. Interface request payloads must stay within reasonable limits to avoid timeouts or transmission failures. Interfaces must also comply with internal system identity verification requirements.

## Configuration settings for FastGPT v4.17.0
Configuration references are listed below:

| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| Request timeout | `30 seconds` | Meets low-latency response requirements for real-time inspection equipment, avoids blocking subsequent work order processes for extended periods |
| Request header configuration | `Content-Type: application/json` | Compatibility with HTTP interface formats of most MES and inspection equipment, ensures correct data transmission |
| `variables` | `{"workOrderId": "{{workorder_id}}", "bomList": "{{bom_data}}", "defectData": "{{spi_report}}"}` | Passes work order-specific process and exception data, adapts to parameter requirements for scenarios such as line changes and first article inspection |
| `responseData` | `{ defectType: $.data.defectList, totalCount: $.data.total }` | Extracts core defect fields from SPI/AOI reports, quickly generates core content for exception reports |
| `Authorization` | `Bearer {factory-specific API key}` | Verifies access permissions for external systems, prevents unauthorized interface calls |
| Request retry strategy | Retry 2 times after failure, interval of `5 seconds` | Addresses request failures caused by network fluctuations or temporary system lag, improves interface call success rate |

## Three common configuration errors
- Symptom: Interface returns "Host not allowed" error, status code 403. Cause: Internal system IP whitelist for allowed access is not configured, or the `Authorization` parameter does not carry a valid key.
- Symptom: HTTP request does not execute, no return data. Cause: Correct trigger conditions are not bound, and call logic tied to work order creation or line change events is not linked.
- Symptom: Fields are missing after parsing response data, making exception report generation impossible. Cause: Field path configuration for `responseData` is incorrect, and does not match the actual returned defect report data structure.

## How to verify correct configuration
- Send a test request with simulated work order data, check if the HTTP status code returned by the interface is 200, confirm that the request triggers normally.
- View the parsing result of `responseData`, confirm that core fields such as defect type and count are correctly extracted, verify that the data parsing logic works.
- Simulate an SPI/AOI inspection exception scenario, trigger an interface call, confirm that the system automatically generates a compliant exception report draft.
- Send a test request with an invalid API key, confirm that the corresponding error prompt is returned, verify that the `Authorization` authentication logic works.

The values listed here are common starting points. Always test against your own actual samples.
