# Process Document and Exception Report Drafting for Photovoltaic Cell Manufacturing: Workflow Orchestration

## What the Data for This Category Looks Like
The business data for photovoltaic cell manufacturing mainly comes from wafer incoming material records, workshop MES systems, operation logs of diffusion furnaces, coating equipment, and printing presses, outputs from EL and IV testing equipment, and laboratory test data. Data update cycles cover each production batch, single-wafer testing nodes, and daily summary links.

Daily produced documents include process cards, diffusion and coating parameter tables, printing and sintering records, EL defect detection images, IV performance data, and yield statistics documents. Fields include process temperature, coating thickness, printing screen specifications, defect coordinates, electrical performance values, etc., with corresponding units of degrees Celsius, micrometers, millimeters, pixels, watts, and others.

## What Constraints Do These Characteristics Impose on the "Workflow Orchestration" Link
The data characteristics of photovoltaic cell manufacturing impose multiple constraints on workflow orchestration.
Multi-source and heterogeneous data sources require workflows to adapt to device logs, test reports, and system records in different formats, to avoid data parsing deviations.
High-frequency updated node and batch-level data requires workflows to support event triggering and batch processing, to ensure data timeliness.
Diverse document types cover structured parameter tables and unstructured images, requiring workflows to be compatible with integration logic for different modal data.
Fine-grained single-wafer level data requires workflows to strictly associate parameters and test results corresponding to the batch, to prevent cross-batch data confusion that affects process traceability.
At the same time, the processes of this category are continuous and surface microstructures are sensitive, requiring workflow node sequences to strictly follow the process chain, to avoid missing pre-process parameters that affect abnormal judgment in subsequent links.

## How to Configure the Settings
The following configurations are adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Bind 10–15 fields including batch number, device serial number, and detection batch | Match the batch traceability and multi-source data association requirements of photovoltaic cell manufacturing |
| Context call configuration | Retain the global context of the previous 3 conversations | Support cross-node association of process parameters and exception records, avoid context redundancy |
| Node timeout threshold | 600 seconds | Adapt to the average time interval for device data reporting and parsing |
| Exception report trigger condition | Trigger when IV performance values deviate from the threshold interval calibrated by actual measurements | Match the electrical performance detection exception judgment logic of photovoltaic cells |
| `nodeId` | Specify the unique identifier of the EL detection image parsing node | Ensure that unstructured image data processing order is bound to the node, avoid parsing confusion |
| Global variable storage limit | 1000 MB | Meet the temporary storage requirements for multi-batch data |

## Three Common Misconfigurations
- Phenomenon: The database connection node returns the `Access denied for us` error. Cause: The account and key fields for database access are not configured in `variables`, leading to permission verification failure.
- Phenomenon: The workflow cannot reuse the configured context after calling an API. Cause: The context is not bound to global variables, leading to the context not being persistently retained during cross-node calls.
- Phenomenon: No customized guiding language is generated after the AI replies, only the system default "Guess you want to ask" content is displayed. Cause: No custom output node is added to the workflow to handle the guiding language generation logic, only relying on the system default configuration.

## How to Confirm the Configuration Is Complete
- Check whether the fields bound in `variables` cover the core traceability and parameter fields required by the business, confirm that the field configuration matches actual business requirements.
- Trigger a simulated device data reporting event, verify whether the workflow starts as expected and completes data parsing and integration.
- Simulate an exception detection result, verify whether the exception report is automatically triggered and generated, and includes the process parameters and detection data of the corresponding batch.
- View the workflow context logs, confirm whether the global context is correctly retained and reused during cross-node calls.
