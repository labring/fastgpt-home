# Drafting Process Documents and Exception Reports for Cosmetics Production: HTTP Interfaces and External Systems

## What Data for This Category Looks Like

Data related to cosmetics production process documents and exception reports comes from registered or filed formulas, raw material safety materials, weighing and emulsification equipment, MES/ERP systems, laboratory test data, and packaging material version information. Daily documents include formula process sheets, weighing and feeding records, emulsification or filling records, cleaning and site clearance records, semi-finished and finished product inspection reports, and label review documents.

Data updates trigger with each production batch or line change operation. Fields include raw material name, restricted substance content, emulsification temperature, homogenization time, batch number, packaging material version number, and more. Some fields use fixed units such as degrees Celsius, minutes, and grams.

## What Constraints These Characteristics Impose on HTTP Interfaces and External Systems

Data for this category is scattered across multiple external systems, and update frequency shifts dynamically with production batches. Interfaces must support pulling data by production batch, workshop, and other dimensions.

Formulas and labels must meet filing requirements. Interface returned data must include verifiable compliance fields to avoid inconsistencies with filed information.

Exception reports from production links must associate with specific batch equipment parameters and test data. Interfaces must support structured returns of relevant fields to support subsequent exception analysis and report drafting.

Data errors may lead to outcomes such as product removal from shelves and recalls. Interfaces must include basic permission verification and failure retry mechanisms.

## How to Configure Settings

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer {exclusive access key} | Connect to internal enterprise MES and ERP systems to secure interface access permissions |
| `variables` | Bind production batch number, workshop ID, packaging material version | Adapt to dynamic data pulling and verification requirements for each production batch |
| `responseData` | Only return raw material name, restricted substance content, production parameter fields | Simplify returned content to reduce data transmission overhead |
| Interface timeout duration | 30 seconds | Match typical production equipment data return latency |
| Retry count | 2 times | Address temporary network fluctuations or brief equipment offline status |
| Field verification rules | Match standard fields from filed formulas | Ensure returned data aligns with registered and filed information |

## Three Common Configuration Errors

- Scenario: A curl request returns an upgrade-related error with status code 400. The cause is using an interface path incompatible with FastGPT v4.17.0, or a request format that does not meet version requirements.
- Scenario: The interface returns an empty `responseData` field. The cause is failing to configure correct return filtering rules, resulting in accidental filtering of core business required fields.
- Scenario: The request times out with status code 504. The cause is setting an overly short interface timeout duration that does not match typical production equipment data return latency.

## How to Confirm Configuration Is Complete

- Send a test request, verify that the `Authorization` parameter format in the request header is correct, and that the returned status code is 200.
- Review the fields returned in `responseData`, confirm that only preset core content such as raw material name, restricted substance content, and production parameters is included.
- Simulate a production batch change, verify that dynamic parameters bound to `variables` take effect, and that production data for the corresponding batch is successfully pulled.
- Simulate temporary network fluctuations to trigger the retry mechanism, confirm that the request completes successfully after retries.

The values provided are common starting points and should be measured against the reader's own samples.
