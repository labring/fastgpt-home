# Drafting Process Documents and Exception Reports for Transformer and High-Voltage Electrical Equipment Manufacturing: Multi-Turn Dialogue and Prompt Engineering

## What This Category of Data Looks Like
Data for this category originates from design BOMs of power transmission and distribution equipment enterprises, switchgear and transformer factories, inventory data of silicon steel sheets and insulating materials, vacuum drying equipment logs, insulating oil test reports, and partial discharge and withstand voltage records from high-voltage test stations. Daily documents include winding and core assembly records, vacuum drying records, insulating oil reports, partial discharge withstand voltage test reports, and nameplate parameter tables. Data is updated per single product or per batch of materials, with fields including insulation distance parameters, moisture content test values, test voltage values, lead tap positions, and more. Units are mostly millimeters, percent, kilovolts, and megapascals.

## Constraints Imposed on Multi-Turn Dialogue and Prompt Engineering
Full life cycle traceability requirements for single products require that dialogue context be bound to the unique identifier of the corresponding equipment to avoid mixing data across batches. High-volume professional data from insulation and high-voltage tests must be called in real time during multi-turn dialogue, so context window size must be limited to filter redundant information. Most document fields are professional numerical values with units, so prompts must clearly specify formats and units to prevent ambiguous output. Exception reports must be associated with specific test data, and multi-turn dialogue must support filtering historical data by test time and batch to ensure drafted content matches actual test results.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum Context Window | First 10 turns of dialogue + 3 core test reports for the current device | Matches single product traceability requirements, adapts to FastGPT v4.17.0's dialogue context mechanism, and avoids interference from cross-batch data |
| Prompt Template Bound Variables | Associate device number and test batch fields in `chatId` and `variables` | Ensures dialogue context automatically matches exclusive data for the corresponding product, avoiding confusion between process and test information across batches |
| Single Dialogue Response Content Limit | 800–1200 characters | Adapts to segmented output requirements for professional process documents, avoiding content overload that harms readability |
| Markdown Rendering Settings | Enable native rendering | Ensures format tags set in prompts are displayed correctly, avoiding output of raw markdown code |
| Historical Dialogue Reference Switch | Enabled | Supports cross-turn calls of historical test data and process parameters, meeting traceability requirements for exception report drafting |
| Token Count Display | Enabled | Facilitates monitoring of input and output token consumption during professional document generation, aligning with platform v4.17.0's functional features |

## Three Common Misconfigurations
- Symptom: Fields are empty when calling historical dialogue data, making association of test records for the corresponding device impossible. Cause: The binding logic between `chatId` and device number is not configured, so context cannot match exclusive product data.
- Symptom: Redundant AI dialogue interaction text is included in tool call results. Cause: Dialogue content pass-through setting is not turned off, causing non-essential dialogue history to be carried during tool calls.
- Symptom: Generated process documents contain unrendered markdown symbols such as #, **, and others. Cause: Markdown native rendering function for dialogue results is not enabled, causing format tags to be output directly.

## How to Verify Proper Configuration
- Test device numbers and test batches are input to verify that dialogue context automatically associates corresponding data fields.
- Tool call requests are initiated, and returned results are checked to confirm they only include required process and test data, with no redundant dialogue text.
- Test process documents are generated, and markdown formats such as headings and lists are confirmed to be correctly rendered into typeset effects.
- The token count module in the dialogue interface is reviewed, and input and output tokens are confirmed to display specific numerical values respectively.

The values provided here are common starting points and should be evaluated against samples from the relevant deployment.
