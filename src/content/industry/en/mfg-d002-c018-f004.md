# Drafting Process Documents and Exception Reports for Basic Chemical Continuous Production: Workflow Orchestration

## What this category of data looks like
Data sources include DCS/SIS systems, online analyzers, LIMS laboratory management systems, equipment condition monitoring modules, energy metering systems, and raw material tank level monitoring modules. Daily documents cover operating procedures, process index cards, DCS trend charts, laboratory reports, interlock bypass records, special work permits, and shift logs. Data update frequencies fall into three categories: real-time, per shift, and daily. Fields include reactor temperature (℃), system pressure (MPa), material feed flow rate (m³/h), interlock number, work permit number, and others. Some documents require matching fixed-format units and validation rules.

## How These Characteristics Impact Workflow Orchestration
Real-time updated DCS and online analyzer data requires workflow node trigger frequencies to match data sampling intervals. This prevents delayed or redundant processing. Multiple document types with varying update frequencies require categorization and binding to workflow variables. This stops data confusion. Highly interlocked control systems require workflows to prioritize validation of critical alarms and bypass records. The workflow triggers an immediate interruption if an exception is detected. Continuous production steady-state maintenance requires workflows to support automatic cyclic execution without manual intervention. Automatic recovery mechanisms must be configured after failures.

## Recommended Configuration Settings
The following configurations are adapted for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Form input node trigger mode | Internal call only | Adapts to the no-on-site-popup operation scenario of basic chemical continuous production, and avoids interaction blocking when nesting workflows |
| `variables` binding rules | Bind DCS measurement points, process indicators, and work permit fields | Matches the structured fields of the category's data sources, ensuring the accuracy of data called by workflows |
| Workflow timeout period | 300 seconds | Covers the average time required for DCS data pulling and laboratory report queries, avoiding operation failures caused by data delays |
| Node retry count | 2 times | Responds to temporary system and network fluctuations, ensuring the execution success rate of critical validation nodes |
| `nodeId` specified node | Interlock validation node ID | Prioritizes processing exception validation related to strong interlocks, ensuring the execution priority of production safety-related links |
| Context call limit | Top 10 entries | Matches the single-processing scale of the category's daily documents, avoiding excessive data from occupying operation resources |

## Three Common Misconfigurations
- Running nested within a parent workflow causes the form input node to display a dialog box, and the parent workflow cannot advance automatically. The cause is that the form input node's trigger mode is set to "external call pop-up" by default, which does not adapt to the interaction-free operation scenario of nested workflows.
- Calling a custom Python code function returns an execution failure prompt, and expected process calculation results cannot be obtained. The cause is that the Python code node is not configured as a public node that can be called by external workflows, and real-time process parameters required by the function are not bound in `variables`.
- Attempting to call a workflow directly from the front end returns a permission error, and the workflow execution result cannot be obtained. The cause is that authentication is not performed using the workflow's unique `nodeId` or bound application key, and a workflow without public permission configuration is called directly.

## How to Verify Correct Configuration
- Trigger the nested workflow, confirm that no pop-up window appears for the form input node, and the workflow automatically completes all node executions and generates results.
- Call the custom Python code node, pass in the process parameters bound in `variables`, confirm that the code executes normally and returns required calculation results.
- View the workflow operation logs, confirm that all node executions are completed within the timeout period, and there are no timeout errors or critical node execution failure records.
- Check the `nodeId` configuration, confirm that the interlock validation node is correctly specified, and the retry rule for this node has taken effect.

The values provided here are common starting points and should be measured against the reader's own samples.
