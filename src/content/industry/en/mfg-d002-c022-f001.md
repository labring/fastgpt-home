# Craft Document and Exception Report Drafting for Household Appliance Complete Machine Manufacturing: HTTP Interfaces and External Systems

## What data looks like for this product category
This category covers scenarios including air conditioners, refrigerators, washing machines, and small household appliance complete machine manufacturing. Daily documents include configured BOMs, assembly work instructions, refrigerant charging records, electrical safety test reports, performance spot check reports, and rework records. Data sources include ERP/MES systems, component batch ledgers, tightening and charging equipment logs, safety compliance tester data, performance laboratory test results, and after-sales fault databases. Data update frequency follows individual product, team shift, or spot check schedule. Individual records include fields such as model identifier, process parameters, test results, batch information, and anomaly tags.

## What constraints do these characteristics impose on HTTP interfaces and external systems
The multi-source heterogeneous data and high-frequency update characteristics of this category require HTTP interfaces to support multi-format data reception and batch submission. Process and test data for individual products must be bound to a unique identifier. Interfaces must verify field integrity to prevent cross-line misassembly. Safety compliance and performance test data have strict timeliness requirements, so interfaces must support low-latency responses. Log formats vary across different devices, so interfaces must support standardized field mapping. Submission of batch rework records and recall-related data requires transactional processing to ensure data consistency.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Carry a Bearer token with a 12-hour validity period | Complies with FastGPT interface security specifications to prevent unauthorized access |
| Timeout period | 30–60 seconds | Adapts to the collection delay of safety compliance test data, preventing request failures due to slow device responses |
| Batch submission limit | First 50 records | Matches the daily data output scale of team shifts, avoiding excessive interface load |
| `variables` | Bind product model, batch number, and test station identifier | Used to associate corresponding data between process documents and exception reports, preventing cross-line misassembly |
| `responseData` | Return `success` status and record ID | Facilitates external systems to confirm data reception results and implement link tracing |
| Field validation rules | Enforce validation of model and test result fields | Prevents errors in process documents and exception reports caused by missing key information |

## Three common configuration mistakes
- Unable to specify PDF parsing parameters when calling the interface, and the request returns an unsupported parameter error. The cause is failure to pass parsing configuration parameters via `variables`, or failure to follow FastGPT interface parameter transfer rules.
- HTTP request timeout, with a timeout prompt displayed on the interface or a 504 status code returned. The cause is a timeout period set shorter than the response delay of the external system, or network link fluctuations.
- Node output variables cannot be stored in an external system via an HTTP request, and the interface returns a 400 or 401 error. The cause is incorrect configuration of the `Authorization` request header, or failure to match the field format requirements of the external system.

## How to confirm configuration is complete
- Send a single test data record with complete fields, check whether `responseData` returns a success status and record ID.
- Simulate submission of test data matching the batch limit, confirm that the interface completes the response within the 30–60 second timeout period.
- Construct a test request with missing key fields, confirm that the interface returns a field validation failure prompt.
- View FastGPT v4.17.0 interface logs, confirm that the `Authorization` token in the request is valid and not intercepted.
