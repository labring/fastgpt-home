# Drafting Process Documents and Exception Reports for Incoming Material Inspection and Supplier Quality: Model Access and Configuration

## What this category's data looks like
The core data for this category comes from incoming material inspection (IQC), supplier quality (SQE), procurement quality, and supplier engineering departments of manufacturing enterprises. Daily covered documents include inspection specifications, sampling plans, incoming material reports, supplier audit reports, exception contact sheets, 8D reports, concession acceptance approvals, and similar documents. Data sources include purchase orders, drawing specifications, supplier quality certificates, inspection equipment data, historical quality records, and supplier portal information. Update frequency is dynamically adjusted based on each batch of incoming materials, monthly/quarterly supplier evaluations, and irregular audits. Each batch of data is associated with corresponding purchase orders, inspection results, and supplier feedback information.

## What constraints these characteristics impose on the "model access and configuration" link
The data sources for this category are scattered and updated frequently, requiring model access configuration to support unified docking and high-frequency calls for multiple data sources. The structures of different types of documents vary greatly, requiring adaptation to structured fields of inspection specifications and multi-stage process content of 8D reports, which places clear requirements on the context processing capability of the model. At the same time, the data involves balancing supplier quality and production supply guarantee. Configuration needs to balance the rigor of generated content and call efficiency, avoiding misjudgments or timeouts caused by inappropriate parameters. In addition, some scenarios require docking with privately deployed large language models, so configuration needs to support custom API endpoints and authentication parameters to ensure data security.

## How to set the configurations
The following configurations are formulated based on FastGPT v4.17.0.

| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the total length of documents such as purchase orders and inspection reports associated with a single batch of incoming materials, avoiding truncation of core associated information |
| `maxTokens` | 2000–3000 token | Meets the complete drafting requirements for exception reports and 8D reports, covering all content such as root cause analysis and rectification suggestions |
| `temperature` | 0.3–0.5 | Maintains the rigor of process documents and quality reports, avoiding overly casual judgments or descriptive content in generated outputs |
| `AIPROXY_API_ENDPOINT` | Fill in the corresponding access address based on the deployment environment | Adapts to access requirements for privately deployed or third-party models, ensuring that requests can normally reach the model service |
| `AIPROXY_API_TOKEN` | Fill in the key provided by the model service provider | Ensures the validity of identity verification for model calls, preventing unauthorized access or request interception |
| `toolChoice` | auto | Automatically adapts to scenarios requiring calls to sampling plans and historical quality data during incoming material inspection, without manual tool specification |

## Three common configuration mistakes
- Phenomenon: The generated exception report contains forged reference IDs that cannot match the actually uploaded document content. Cause: The `maxContext` parameter is not configured correctly, resulting in the loss of reference association information of the original document after context truncation.
- Phenomenon: A privately deployed large language model cannot connect to the FastGPT instance, and the request returns a connection timeout error. Cause: The `AIPROXY_API_ENDPOINT` parameter is filled incorrectly, and does not match the intranet access address of the deployment environment.
- Phenomenon: Available AI models cannot be selected during workflow editing, but the published workflow can call the model normally. Cause: The `AIPROXY_API_TOKEN` parameter is not filled correctly in the system configuration, causing the model list to fail to load properly.

## How to confirm the configuration is complete
- Upload the inspection specifications and historical exception reports for a single batch of incoming materials, trigger the model to draft an exception report, and verify that the generated content includes correct document references and corresponding field information.
- Call the model interface, view the returned token consumption statistics, confirm that the values of `maxContext` and `maxTokens` parameters meet the actual document length requirements, with no abnormal truncation.
- Check the system operation logs, confirm that the model request address and key match the configured items, with no connection failure or identity verification error records.
- Publish a workflow containing model call nodes, verify that configured AI models can be normally selected and called during both the editing stage and after publication.

The values provided are common starting points and should be measured against the reader's own samples.
