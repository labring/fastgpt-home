# Process Document and Exception Report Drafting for Cement Clinker and Grinding: HTTP Interfaces and External Systems

## What the data for this category looks like
Data sources for this category include online composition analysis equipment, DCS control system, laboratory testing system, kiln and mill operation equipment, raw fuel ledger system, and energy metering system. Data update frequencies fall into three categories: real-time (such as kiln temperature, feed rate), per-shift (such as equipment inspection records), and daily (such as energy consumption reports). Daily documents include raw material batching plans, kiln operation records, laboratory reports, quality control notices, equipment inspection forms, and energy reports. Laboratory reports include sample number, test item, and test result fields. Energy reports include energy consumption value and statistical period. Some document fields use physical units: megapascals, kilowatt-hours, tons.

## What constraints these characteristics impose on HTTP interfaces and external systems
Scattered data sources and widely varying update frequencies for this category require HTTP interfaces to support flexible request interval configurations, to meet data pulling needs for real-time, per-shift, and daily data. Multiple document types correspond to different field structures. Interfaces must support diverse request body and response body formats to avoid adaptation issues caused by mandatory fixed fields. Serious failure outcomes such as clinker quality fluctuations and kiln system shutdowns require interfaces to include data verification logic, to intercept abnormal values in a timely manner. For intranet deployment scenarios, interfaces must support local calls without public network access, and must handle permission verification for cross-system data synchronization.

## How to set configurations
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Request timeout | 600 seconds | Adapt to fast response of real-time kiln temperature data, avoid system blocking caused by long waiting times |
| `Authorization` | Bearer {custom secret} | Comply with interface authentication specifications of external systems, ensure data transmission security |
| `variables` | Pass in by test item, equipment number | Adapt to variable replacement requirements for multiple types of documents, such as using the sample number in the laboratory report as a replacement variable |
| `responseData` | Return test results and energy consumption values in original format | Retain original data units and field structures, facilitate direct parsing by downstream systems |
| Retry count | 3 times | Respond to temporary network fluctuations causing interface call failures, ensure data synchronization stability |
| Batch pull limit | First 200 entries | Adapt to batch pulling requirements for per-shift inspection records, avoid excessive data volume in a single transmission |

## Three common misconfigurations
- Phenomenon: Interface calls return 401 Unauthorized status code, or authentication failure prompts. Cause: The `Authorization` parameter is not configured correctly, or the Bearer prefix is not added, causing external systems to fail to recognize authentication information.
- Phenomenon: Generated process documents or exception reports do not replace variables, and the returned content is unrelated to the preset documents. Cause: Corresponding variables are not passed via the `variables` parameter, or the variable name does not match the placeholder in the prompt. For example, the prompt uses {sample number} but the passed variable name is sample_id.
- Phenomenon: Interface calls time out, or the service restarts in intranet deployment scenarios. Cause: Network rules for intranet access are not configured, or the request timeout is set too short to adapt to delays in intranet data transmission.

## How to verify correct configuration
- Use the built-in interface debugging tool of FastGPT v4.17.0 to call the test interface, check that the fields returned in `responseData` match the document structure of the external system, and confirm that the data format meets expectations.
- Pass the preset `variables` parameter, verify that the placeholders in the prompt are correctly replaced, and the generated document contains the corresponding variable content.
- Simulate interface calls in an intranet environment, confirm that the service does not restart or throw timeout errors, and check that the authentication logic works properly.
- Adjust the request interval and batch pull quantity, verify that data with different update frequencies can be synchronized normally.
