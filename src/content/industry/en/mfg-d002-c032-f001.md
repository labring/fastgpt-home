# Process Document and Abnormal Report Drafting for Complete Vehicle Final Assembly: HTTP Interfaces and External Systems

## What data for this category looks like
Data for complete vehicle final assembly scenarios centers on Vehicle Identification Numbers (VIN). Data sources include ERP/MES systems, VIN and configuration systems, tightening tools, EOL inspection lines, and quality traceability systems. Daily documents cover production orders, VIN lists, assembly work instructions, tightening data, offline inspection reports, rework records, and consistency and release documents.
Data updates happen in real time for each vehicle and are synced in batches per shift. Single-vehicle data includes structured fields such as VIN, torque values (unit: newton meters), part batch numbers, and inspection results. It supports rapid matching of multiple configurations during mixed-line production.

## Constraints Imposed on HTTP Interfaces and External Systems
Since data uses VIN as the unique identifier and updates in real time, interfaces must support high-concurrency, short-cycle requests to match the beat of final assembly lines. Single-vehicle data includes multi-dimensional structured fields, so interfaces must support validation logic with multiple business parameters to prevent mismatches.
Under mixed-line production, requests must accurately match the configuration of the corresponding vehicle. VIN must be used as the core request parameter. Abnormal data processing requires rapid response, so interfaces must include timeout retry and exception capture mechanisms to prevent single request failures from disrupting assembly beats.

## How to Set Configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${Enterprise-specific API key}` | Complies with identity verification standards for industrial production systems, prevents unauthorized access to external interfaces |
| `variables` | Includes core business fields such as VIN, torque thresholds, and inspection item IDs | Accurately matches the assembly configuration and validation rules for individual vehicles, avoids data mismatches during mixed-line production |
| `responseData` | Returns only structured process parameters, abnormal judgment results, and associated document IDs. Limit each response to 800–1200 characters | Filters non-essential data, meets real-time response requirements for final assembly lines, and reduces parsing load on external systems |
| Request timeout setting | 10–30 seconds | Meets interface response requirements for real-time assembly beats, while reserving time for data validation and exception handling |
| Maximum number of documents per request | Top 5 entries | Matches the request load of a single workstation, prevents timeouts caused by excessive data volume in a single request |
| Retry count | 3 times | Addresses temporary network fluctuations or interface jitter, ensures continuity of assembly processes |

## Three Common Mistakes
- Symptom: HTTP interface returns 401 Unauthorized status code, or returns an empty response directly. Cause: `Authorization` parameter is not configured correctly, compliant identity verification token is not included, or the token has expired and is invalid.
- Symptom: Process documents returned by the interface do not match the configuration of the vehicle corresponding to the VIN. Part mismatches or parameter errors occur. Cause: VIN is not included in `variables` as a core matching parameter, so the interface cannot locate the exclusive assembly data for the target vehicle.
- Symptom: The interface response includes images that external systems cannot display properly. Cause: Full accessible URLs for image resources are not configured in `responseData`. Only relative paths or local file identifiers are returned, preventing external systems from parsing and loading the images.

## How to Verify Proper Configuration
- Use FastGPT v4.17.0 to send a test request with a valid VIN and business parameters for the current workstation. Confirm that the returned `Authorization` verification result is passed.
- Check the `variables` field in the request parameters. Confirm that core business fields for the current workstation are included, such as VIN and torque thresholds, with no omissions.
- After calling the interface, check that the `responseData` returned fields include the process parameters and abnormal judgment results required for the current workstation, with no redundant unrelated fields.
- Simulate a temporary network fluctuation scenario to trigger interface retries. Confirm that the interface returns compliant response data normally after retries.

All listed configuration values are common starting points. They should be evaluated against local operational samples and conditions.
