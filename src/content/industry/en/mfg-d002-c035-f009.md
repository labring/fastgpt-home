# Heat Treatment Process Document and Abnormal Report Drafting: Model Access and Configuration

## What Data Looks Like for This Category
Data for heat treatment scenarios originates from material grade archives, customer technical specifications, workshop temperature control instruments, furnace temperature uniformity test reports, test results from hardness testers and metallographic equipment, and production MES systems. Data updates occur per furnace charge and per batch. Daily generated documents include heat treatment process cards, charging diagrams, furnace temperature curves, hardness and metallographic reports, equipment inspection forms, and abnormal disposal forms. Fields cover material grades, heating temperatures, holding durations, cooling methods, hardness values, metallographic structure types, and similar items. Units include degrees Celsius, hours, HV, batch numbers, and other professional parameters.

## Constraints Imposed by These Characteristics on Model Access and Configuration
Per-furnace charge data updates frequently and mixes structured documents and unstructured charts. This requires the model’s context capacity to match the total data volume of a single furnace charge, to avoid truncating core process parameters. Data from multiple sources must be connected via a unified interface. Configured API endpoints must be compatible with the output formats of equipment and MES systems. The accuracy of abnormal reports and process documents directly impacts part service performance. Content generated by the model must strictly match industry parameter specifications, and professional fields cannot be adjusted arbitrarily. Additionally, the timeliness requirements of single-furnace charge tasks demand stable, reliable interface calls to avoid timeouts that disrupt production schedules.

## How to Set the Configuration
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `AIPROXY_API_ENDPOINT` | API gateway address corresponding to the workshop MES system, or official invocation path of the large model service | Ensures the model can normally connect to business data sources and large model services, covering the need to obtain full-process heat treatment data |
| `AIPROXY_API_TOKEN` | Valid identity credential obtained from the MES system or large model service provider | Completes identity verification for interface calls, preventing data unavailability or model invocation failures due to insufficient permissions |
| `maxContext` | `8000–12000 token` | The total token count of documents such as single-furnace charge process cards, furnace temperature curves, and test reports usually falls within this range, enabling complete loading of core business data |
| `maxTokens` | `1500–2000 token` | Meets the output length requirement for a single process document or abnormal report, balancing response speed and content completeness |
| `temperature` | `0.2–0.4` | Heat treatment process parameters must maintain rigor. A lower temperature value reduces randomness in generated content, ensuring parameters comply with industry specifications |
| Workflow/API tool selection | `none` | This scenario only requires generating text based on existing business documents, without needing to call external tools to obtain additional data |

## Three Common Misconfigurations
- Symptom: The platform model list is empty, and no available models appear after only configuring `AIPROXY_API_ENDPOINT`. Cause: `AIPROXY_API_TOKEN` is not configured synchronously, or the endpoint address does not include the correct API path prefix.
- Symptom: The specified model cannot be invoked after model mapping configuration, and generated content does not meet expectations. Cause: The platform has not bound the corresponding model and business data source permissions, preventing the model from accessing heat treatment-specific data.
- Symptom: Model tests return 401 errors or connection timeouts, occurring with both Alibaba Cloud Bailian and locally deployed Ollama models. Cause: `AIPROXY_API_TOKEN` has expired, or the locally deployed Ollama service has not opened external access ports.

## How to Verify Successful Configuration
- On the model debugging page of FastGPT v4.17.0, enter the core content of a single-furnace charge process card, initiate a test call, and confirm the return status code is 200 with no permission-related error messages.
- Upload the complete business document package for a single furnace charge, trigger the process document drafting task, and check that the output does not truncate core parameters such as heating temperature and holding duration.
- Trigger the drafting task with the same input multiple times, compare output differences, and confirm that variations fall within the range specified by the `temperature` configuration, with no obvious parameter deviations.
- View the task execution log, confirm no additional tool calls are triggered, only text-based output is generated, and verify the `toolChoice` configuration takes effect.

The values provided are common starting points and should be evaluated against the reader's own samples.
