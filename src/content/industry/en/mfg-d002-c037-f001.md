# Production Planning and Shop Scheduling: Crafting Process Documents and Exception Reports via HTTP Interfaces and External Systems

## What the Data for This Category Looks Like
Core data for this category comes from enterprise ERP systems: order and inventory records, BOM lists and process routes, equipment capacity ledgers, staff shift schedules, work-in-progress inventory, and supplier delivery records. Daily generated documents include sales orders, master production schedules, material requirements plans, weekly and daily scheduling tables, production work orders, material shortage lists, delivery change notices, and more. Data update frequencies vary by business scenario, including daily summary updates, weekly scheduling updates, and real-time updates triggered by order changes or exception occurrences. Data fields cover order numbers, material codes, process names, equipment numbers, capacity load, delivery deadlines, and other items, and must align with each enterprise’s production management specifications.

## Constraints for HTTP Interfaces and External Systems
Data for this category comes from multiple dispersed sources with inconsistent formats. This requires HTTP interfaces to support pulling data from multiple sources and adapting formats, without forcing downstream systems to unify their data structures. Non-periodic data updates require interfaces to support on-demand triggering, to meet real-time call needs when order changes or exceptions occur. The large number of fields in daily documents varies widely, so interface parameters must support flexible input of core business fields, while returning structured scheduling and exception results to enable direct parsing by downstream systems. Additionally, real-time requirements are high in exception scenarios, so interfaces must support low-latency responses to avoid delaying immediate shop floor scheduling decisions.

## Configuration Settings

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {Enterprise API Key}` | Complies with HTTP interface authentication standards, and aligns with authentication rules for internal enterprise ERP or production systems |
| `variables` | Pass core business fields such as work order ID, material code, and equipment number | Accurately matches the context data of production plans, ensuring the interface returns scheduling results for the corresponding process |
| Maximum data per single request | `5000 entries` | Matches the single-pull limit for shop scheduling data, preventing request timeouts caused by excessive data volume |
| `responseData` | Return structured fields for scheduling results and exception reports | Adapts to the parsing format of downstream systems, reducing the workload of secondary processing |
| Timeout period | `300 seconds` | A reasonable duration for handling complex scheduling calculations, preventing incomplete data due to interrupted requests mid-processing |
| Trigger timing | Triggered upon order changes or exception occurrences | Aligns with data update frequencies, reducing resource consumption from invalid requests |

## Three Common Mistakes
- Symptom: The interface call returns a 200 status code but no valid scheduling data. Cause: Core business fields are not passed in `variables`, so the interface cannot match the context of the corresponding production plan.
- Symptom: Timeouts or inconsistent results occur when multiple interfaces are called consecutively. Cause: The next request is not initiated after waiting for the `responseData` of the previous interface to return, and concurrent requests exceed the current limiting threshold of the enterprise system, leading to abnormal data processing.
- Symptom: A `403 Forbidden` error is received. Cause: The `Authorization` parameter is not configured correctly, an expired API key is used, or allowed calling IP whitelists are not added.

## How to Confirm Proper Configuration
The following verification steps are based on the interface configuration logic of FastGPT v4.17.0.
- A single test request is initiated with a known valid work order ID, and `responseData` is checked for scheduling information and exception markers for the corresponding process.
- An order change event is simulated to trigger an interface call, and the returned exception report is confirmed to include content corresponding to business scenarios such as material shortages or equipment failures.
- The format of the `Authorization` parameter is verified, the interface authentication test is passed, and a 200 status code is confirmed to be returned with no permission errors.
- Multiple consecutive requests are initiated, the consistency of returned results is observed, current limiting and retry configurations are confirmed to be effective, and no duplicate or missing data occurs.
