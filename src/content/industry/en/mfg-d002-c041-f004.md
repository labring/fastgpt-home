# Drafting Process Documents and Exception Reports for Electroplating and Chemical Surface Treatment: Workflow Orchestration

## What the data for this category looks like
Daily documents for this category include tank solution analysis records, process parameter cards, fixture records, film thickness and adhesion reports, hazardous waste ledgers, and wastewater monitoring records. Data sources include customer surface treatment specifications, tank solution test results, rectifier operation data, online water quality monitoring records, and hazardous waste management ledgers. Data update frequency is per tank batch, per shift, or per fixed monitoring cycle requirements. Fields for a single document include tank number, analysis time, metal ion concentration (unit: g/L), pH value, current density (unit: A/dm²), plating duration (unit: min), and others. Format and field definitions must strictly match on-site production specifications.

## What constraints do these characteristics impose on workflow orchestration
Pulling multi-source heterogeneous data requires configuring nodes for different data sources, and allocating permissions and pulling rules based on data type. High-frequency updated tank batch data requires workflows to support event triggering to avoid redundant computation caused by fixed polling. Exclusive units and fixed naming of fields require strict matching of field names and formats when extracting variables to prevent parameter misuse. Features with severe abnormal consequences require setting abnormal termination and alert nodes in the workflow to quickly interrupt the process when abnormalities such as coating defects or discharge overstandard are detected. At the same time, single-batch data volume is limited but updated frequently, so loop bodies and single processing volume need to be reasonably configured to avoid node overload.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Loop body termination condition | Terminate when the `variables.镀层缺陷` field is detected as non-empty | Matches plating abnormality judgment rules, quickly terminates invalid loops |
| Variable reference format | `{{variables.槽号}}` | Compatible with FastGPT v4.17.0 variable syntax, accurately extracts tank batch data |
| Data source trigger timing | Triggered per tank batch completion event | Corresponds to the per-tank-batch data update frequency, avoids redundant pulling |
| Single processing data volume | Top 10 entries | Matches the conventional number of single-batch tank solution analysis records, reduces node load |
| Timeout threshold | 300 seconds | Adapts to the time range for full data processing of a single tank batch |
| Context length | 8000 token | Covers the complete content length of process parameter cards and exception reports |

## Three common mistakes
- The loop body continues executing beyond the preset number of times, and the log shows the node status as running without termination. The cause is that the abnormal field in `variables` is not correctly bound as the judgment condition for loop termination.
- A 500 status code is returned when processing tank solution analysis PDFs after deploying Marker. The cause is that the correct path or permission for document parsing is not configured in environment variables.
- References to `{{槽号}}` in the LLM prompt do not take effect, and the output result does not include the corresponding tank batch data. The cause is that the FastGPT standard `{{variables.字段名}}` format is not used.

## How to confirm the configuration is complete
- Manually trigger a single tank batch data workflow, check whether the loop body terminates when the `variables.镀层缺陷` field is detected as non-empty.
- Input preset variable values in the test node, verify whether references in the `{{variables.槽号}}` format can correctly output the corresponding field content.
- View the trigger rules of the data source node, confirm that they match the data update frequency and trigger conditions.
- Simulate a timeout scenario, verify whether the node can trigger the exception handling logic after reaching the preset threshold.

The values given are common starting points and should be measured against the reader's own samples.
