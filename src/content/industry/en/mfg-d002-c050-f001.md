# General Mechanical Equipment Assembly: Process Document and Exception Report Drafting - HTTP Interfaces and External Systems

## What data looks like for this use case
Data for general mechanical equipment assembly scenarios primarily comes from PLM, ERP, parts inspection systems, assembly tool collection terminals, test benches, MES, and customer technical agreements.
Routine documents include assembly process cards, BOMs, torque records, gap adjustment records, commissioning reports, factory inspection sheets, and packing lists.
Data is updated per device or per order.
Document fields include equipment model, component number, torque value, gap parameters, test results, and more.
Units include newton meters, millimeters, pascals, and others.
Some fields must match custom requirements from customer technical agreements.

## Constraints for HTTP interfaces and external systems
The per-device or per-order update pattern for assembly data requires HTTP interfaces to carry full document data for a single order or device in one request. This prevents cross-order data confusion.
Heterogeneous data from multiple sources requires interfaces to support adaptation of different request and response body formats. Unified field mapping rules must be established in advance.
Custom fields from customer technical agreements require interfaces to reserve dynamic variable configuration space. This accommodates different customers’ field requirements.
Real-time assembly data such as torque and gap values needs low-latency synchronization. Interface timeout settings must match on-site collection rhythms. This prevents data loss or incompleteness.

## Configuration Settings
This guidance applies to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {API key assigned by the platform}` | Complies with HTTP interface authentication specifications. Ensures legitimacy of external system calls |
| `variables` | `{"orderId": "Extract from request path", "deviceModel": "Dynamic matching"}` | Adapts to dynamic data fetching for single orders or devices. Matches the business rhythm of order-based updates |
| `responseData` | `Only retain assembly process card, torque record, and gap adjustment fields` | Filters redundant data. Reduces interface transmission and parsing load |
| Interface timeout setting | `30–60 seconds` | Matches average data collection time on assembly sites. Prevents request interruptions from network latency |
| Request content type | `application/json` | Adapts to structured data output formats from PLM, MES, and other systems. Simplifies field mapping workflows |
| Single request data limit | `Within 1000 MB` | Fits the full document data scale for a single order or device. Prevents request overload |

## Three Common Configuration Errors
- An interface call returns a 401 Unauthorized error. This is caused by incorrect configuration of the `Authorization` parameter, or the key format not meeting interface authentication requirements.
- The `responseData` field returned by the interface is empty. This is caused by failure to specify required business fields, or request parameters not matching the document update cycle (such as omitting the correct order identifier when requesting single-order data).
- Forms cannot be synchronized to external platforms via API. This is caused by failure to enable `variables` dynamic parameter mapping in the interface configuration, which prevents delivery of custom form fields.

## How to Verify Correct Configuration
- Call a test interface. Check if the returned `responseData` includes preset core business fields, such as assembly process cards and torque records.
- Simulate a single-order request. Verify that the `variables` parameter correctly extracts dynamic identifiers. This avoids cross-order data mixing.
- Review interface authentication logs. Confirm that the `Authorization` parameter format meets requirements, with no authentication failure records.
- Simulate a data delay scenario. Verify that interface timeout settings match on-site collection rhythms, with no frequent timeout errors.

The values provided here are common starting points. They should be evaluated against the reader’s own samples.
