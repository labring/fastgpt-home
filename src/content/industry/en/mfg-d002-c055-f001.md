# Drafting Process Documents and Exception Reports for Foundry (Sand Casting, Precision Casting, Die Casting): HTTP Interfaces and External Systems
This document is compatible with FastGPT v4.17.0.

## What this category of data looks like
Data for this category originates from ERP material master data, melting furnace thermometers, spectrometers, MES heat records, mold management systems, and customer technical drawings. Updates occur per heat, per batch, or daily. Daily documentation includes foundry process cards, batching lists, heat records, mold histories, first-piece inspection records, material test reports, and nonconforming product review forms. Fields cover alloy batching parameters, pouring temperature, heat/mold identification numbers, defect types, and inspection results. Units include degrees Celsius, batches, heats, and more. Data is archived and stored per heat or batch.

## What constraints do these characteristics impose on HTTP interfaces and external systems?
Multiple heterogeneous data sources require interfaces to support pulling data from cross-system modules including materials, melting, and molds. The high-frequency update rhythm requires interfaces to use reasonable timeout thresholds to prevent process interruptions during urgent heat processing. Specific fields and units require interface parameters to strictly match the proprietary naming conventions used in foundry scenarios, such as heat number and pouring temperature unit formats. Exception reports must be linked to heat and mold numbers, so interfaces must support querying associated documents using unique identifiers. Binary data transmission must also be supported to accommodate the upload and forwarding of original detection files from spectrometers and thermometers.

## How to configure settings
| Config Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {team-specific token}` | Complies with standard authentication specifications to secure cross-system access |
| `variables` | `{"炉次ID": "${input.lotNumber}", "合金类型": "${input.alloyType}"}` | Passes core business identifiers for foundry scenarios to associate corresponding data for process documents and exception reports |
| `responseData` | `Return only document binary streams, heat verification results, and exception judgment fields` | Filters redundant data to meet the lightweight processing requirements of external systems |
| Timeout setting | `600 seconds` | Adapts to the standard processing cycle for melting heats to avoid process interruptions in high-frequency scenarios |
| Maximum attachment size | `1000 MB` | Adapts to the storage and transmission requirements of original detection files from spectrometers and thermometers |
| Number of records returned per request | `Top 5` | Prevents excessive returned data from overloading external system processing |

## Three common configuration errors
- Calling the process document query interface returns empty results. The cause is failure to pass heat number or mold number in `variables`, which prevents locating the corresponding foundry documents.
- Uploading original detection files does not return binary data. The cause is not configuring `responseData` to return binary stream format, only returning basic file metadata.
- Calling the authentication interface returns a permission error. The cause is using an incorrect team-specific token in the `Authorization` field, which blocks cross-system access.

## How to verify successful configuration
- Pass the `variables` parameter with a known heat ID, call the interface, then check if the returned `responseData` includes process card and exception report data for the corresponding heat.
- Upload a small test detection file, call the interface, then check if the returned result contains complete binary stream data.
- Fill the `Authorization` field with an incorrect token, call the interface, confirm that an authentication failure prompt is returned to verify the authentication logic functions correctly.
- Simulate high-frequency requests for a single heat, check that the interface response time does not exceed the preset 600-second threshold, with no abnormal interruptions.

The values provided are common starting points and should be measured against local deployment samples.
