# Forging and Die Forging Process Document and Abnormal Report Drafting: Deployment and Upgrade

## What the data for this category looks like
This category covers the entire forging workflow, with data sources including raw material quality certificates, furnace heating systems, press collection data, MES systems, and non-destructive testing instruments. Daily documents include forging process specifications, cutting lists, furnace heating records, forging process cards, mold life records, heat treatment work orders, and ultrasonic testing reports. Data update frequency is per forging, per furnace batch, or per production batch. Fields include forging ratio, fiber direction, furnace batch number, forging dimensions, heating temperature, pressure parameters, etc., with units including millimeters, degrees Celsius, tons, megapascals, and others. This category uses controlled plastic deformation to obtain shapes and continuous metal flow lines, with focus on forging ratio and fiber direction, distinguishing it from casting categories that focus on solidification defect control.

## What constraints these characteristics impose on deployment and upgrade
The data sources for this category are scattered, and update frequency is per part, per batch, or per furnace batch. During deployment, high-frequency data synchronization configuration must be adapted to avoid delays affecting the timeliness of process document drafting. Daily documents include multiple types of structured and unstructured files, so a parsing and storage chain adapted to multiple document formats must be configured during deployment. The steps of drafting deformation steps, heating intervals, and verifying furnace batches and forging batches take a long time. During upgrade, the knowledge base recall logic must be optimized to improve generation efficiency. Improper handling of forging defects can lead to scrap or service fracture, so a strict abnormal data verification mechanism must be configured during deployment to ensure the generated reports are accurate and reliable. This category focuses on verification of forging ratio and fiber direction, so corresponding field identification rules must be configured during deployment.

## How to configure the settings
The following configurations are based on FastGPT v4.17.0.
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://<user>:<pass>@<host>:<port>/forge_docs` | Stores metadata for structured documents such as forging process specifications and ultrasonic testing reports |
| `REDIS_URL` | `redis://:<password>@<host>:6379/1` | Caches frequently accessed furnace batch data and forging batch association information to reduce database pressure |
| `STORAGE_S3_ENDPOINT` | `http://<minio-host>:9000` | Stores large-volume files such as furnace heating records and original press collection data |
| `DB_MAX_LINK` | `60–100` | Adapts to concurrent document read requests from multiple data sources to avoid database connection exhaustion |
| `FE_DOMAIN` | `https://forge-fastgpt.example.com` | Configures the frontend access domain name to adapt to the access path of internal forging workshops |

## Three common configuration mistakes
- A 500 error is returned when importing large documents such as ultrasonic testing reports. The cause is that the `STORAGE_S3_ENDPOINT` is not correctly configured, causing the file upload chain to interrupt.
- The WeChat Work integration function cannot be triggered normally. The cause is that `ROOT_KEY` or `FILE_TOKEN_KEY` is not configured, causing identity verification to fail.
- The process document generation function times out. The cause is that `DB_MAX_LINK` is set too low, leading to database connection exhaustion and failure to read forging process card data in a timely manner.

## How to confirm successful configuration
- Use a database connection tool to test the connectivity of `MONGODB_URI` and verify that metadata of forging process documents can be read normally.
- Upload a typical furnace heating record file to verify that the storage chain of `STORAGE_S3_ENDPOINT` works normally.
- Initiate a test request for abnormal report drafting to confirm that the `REDIS_URL` cache service can respond normally.
- Access the configured `FE_DOMAIN` to verify that the frontend page can load normally and call backend interfaces.

The values provided are common starting points and should be measured against the reader's own samples.
