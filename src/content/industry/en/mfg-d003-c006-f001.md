# Q&A for Process Specifications and Technical Standards for Photovoltaic Module Encapsulation: HTTP Interfaces and External Systems

## What Data Looks Like for This Category
The core teams in the photovoltaic module encapsulation process are string welding, lamination, frame assembly, and testing. Daily generated documents include layout drawings, material batch records, lamination process records, EL images, IV test reports, insulation withstand voltage records, and packing lists.
Data sources cover wafer grading systems, glass adhesive film and backplane batch ledgers, MES systems, string welding and lamination equipment, and EL/IV testers.
Data is updated per module and per batch of materials. A single module is linked to multiple related records, with fields including wafer current gear, lamination process parameters, and test results. Data formats differ across sources.

## Constraints Imposed on HTTP Interfaces and External Systems
Data for this category is updated per module and per batch, with scattered sources and inconsistent formats. This creates multiple constraints for interface configuration.
High-frequency single-module data updates require interfaces to support small-batch, high-concurrency requests. This prevents overload from single large transmissions.
Format differences across multiple data sources require unified authentication and field mapping rules. This ensures data from different devices and systems can be read correctly.
Unstructured EL images and IV test reports require interfaces to support pulling binary or path data. Parameter binding must be used to accurately match the process documents for the corresponding module. This prevents Q&A results from being disconnected from actual production data.

## How to Configure Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {internal enterprise system unified API key}` | Connect to multiple external systems such as MES and test equipment to implement unified access authentication |
| `variables` | Bind component batch number and test timestamp variables | Accurately match the process specifications and test data of the corresponding module to avoid cross-batch confusion |
| `responseData` | Only return process parameters, test results, and associated batch fields | Reduce invalid data transmission and lower interface bandwidth consumption |
| Interface timeout period | 300 seconds | The time required to wait for test data returned by EL/IV testers is usually long, preventing premature request termination |
| Maximum entries per single request | Top 20 entries | The volume of historical data associated with a single module is limited, limiting the number of returned entries to improve query efficiency |
| Number of failure retries | 2 times | Avoid overloading external devices and systems with repeated requests, while covering temporary network fluctuations |

## Three Common Configuration Errors
- Symptom: The power field in the IV test report returned by the interface is empty. Cause: No field mapping including the power parameter was configured in `responseData`. This may cause process Q&A results to not match actual production parameters.
- Symptom: The request returns a 403 authentication failure status code. Cause: The `Authorization` parameter was not configured correctly, and an expired or unauthorized API key was used, making it impossible to access external production systems.
- Symptom: The Q&A result matches an incorrect lamination temperature parameter. Cause: No component batch number parameter was bound via `variables`, causing the system to call process records from other batches. This may lead to production issues such as lamination delamination and substandard power output.

## How to Verify Successful Configuration
- Call the test interface and check if the returned `responseData` includes preset process parameters and test result fields.
- Submit a known component batch number to verify that parameters bound via `variables` are correctly transmitted to the external system.
- After configuring the `Authorization` parameter, send a test request without valid permissions to confirm the authentication mechanism is active.
- Simulate a temporary network interruption to check if the failure retry mechanism triggers as configured.

All provided configuration values are common starting points. Adjust them based on your own specific samples and operational requirements.
