# Q&A for Cosmetics Production Process Specifications and Technical Standards: Deployment and Upgrade

## What this category's data looks like
Data for this category originates from daily production documents of skincare, haircare, makeup, and special cosmetics manufacturers. These documents include formula process sheets, weighing and feeding records, emulsification or filling records, cleaning and sanitization records, semi-finished and finished product inspection reports, and label review materials.
Data sources cover registered or filed formulas, raw material safety documents, production equipment data, ERP/MES systems, laboratory records, and packaging material version information. Updates occur per production batch or each line change.
Data fields include restricted substance information for raw materials, production parameters, batch numbers, packaging material claim content, and other details. All data must strictly align with filing and compliance requirements.

## Constraints on Deployment and Upgrade
This category’s data is updated frequently and sourced from multiple locations. During deployment, configure multi-data source synchronization adapters to ensure fast data access after each production batch or line change.
Data must match compliance filing requirements. Storage and retrieval processes must retain complete batch traceability information. During upgrades, avoid breaking relational links between historical data.
Multi-type document parsing demands preprocessing rules adapted to different document structures during deployment, to prevent parsing errors after upgrades.
Since retrieval focuses on production parameters and sensory inspection results, ensure the upgraded retrieval logic covers these specific fields.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `100–200 connections` | Adapts to concurrent access demands from production equipment, ERP, laboratory, and other data sources, and prevents connection exhaustion |
| `MONGODB_URI` | `Exclusive database address pointing to the filed formula and inspection record collection` | Cosmetics production data must strictly separate compliance filing data from daily production data to avoid confusion |
| `REDIS_URL` | `Configured as a local cache instance address, with a cache validity period set to 300 seconds` | Frequently retrieved production parameters can be accelerated via caching; 300 seconds matches the interval between production batches |
| `STORAGE_S3_ENDPOINT` | `Endpoint address pointing to the enterprise’s internal object storage service` | Stores large-volume documents such as cleaning records and packaging material versions, and adapts to the enterprise’s existing storage architecture |
| `ROOT_KEY` | `Generate an exclusive key in accordance with the enterprise’s internal permission management rules` | Controls access permissions for management interfaces, and prevents unauthorized personnel from modifying process specification-related configurations |

## Three Common Configuration Errors
- Running an upgrade command returns a `500 Internal Server Error`, and logs show database connection timeout. The cause is incorrect configuration of the `MONGODB_URI` or `PG_URL` parameters, which prevents reading or writing production data during the upgrade.
- After upgrading to FastGPT v4.17.0, third-party model calls fail, and the interface displays `model not found`. The cause is failure to synchronize updates to third-party model interface configurations after the upgrade, or the `FILE_TOKEN_KEY` parameter not matching the third-party platform’s verification rules.
- After an upgrade, newly produced batch data cannot be automatically synchronized to the Q&A system, and retrieval results only include historical data from before the upgrade. The cause is failure to configure a reasonable value for `DB_MAX_LINK`, which rejects connections from new data sources and interrupts incremental synchronization tasks.

## How to Confirm Correct Configuration
- Run a data source connection test to confirm that services referenced by parameters such as `MONGODB_URI` and `PG_URL` support normal read and write operations, with no connection errors.
- Submit a test batch of simulated production data to verify that the incremental synchronization task completes normally, and that the data can be queried in the retrieval interface.
- Call the management interface to confirm that the `ROOT_KEY` can complete normal authentication, with no permission denial prompts.
- Trigger a model call test to confirm that the third-party model connection configuration takes effect normally, with no call failure prompts.

## Final Note
The configuration values listed above are common starting points. They should be evaluated against the user’s own samples.
