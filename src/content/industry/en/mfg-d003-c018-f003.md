# Process Specification and Technical Standard Q&A for Basic Chemical Continuous Production: Multi-turn Dialogue and Prompt Engineering

## What Data Looks Like for This Category
Data sources for the basic chemical continuous production category include DCS/SIS systems, online analyzers, LIMS laboratory management system, equipment condition monitoring modules, energy metering devices, and raw material tank data. Data update frequencies are divided into three categories: real-time, per shift, and daily. Daily documents cover operating procedures, process index cards, DCS trend charts, laboratory reports, interlock bypass records, special work permits, and shift logs. Fields include process temperature (degrees Celsius), reaction pressure (megapascals), material flow rate (cubic meters per hour), interlock trigger thresholds, and other standardized parameters.

## What Constraints These Characteristics Impose on Multi-turn Dialogue and Prompt Engineering
Real-time updated DCS and online analysis data require conversation context to support high-frequency refreshes, avoiding calls to outdated steady-state parameters. Shift and daily shift logs and work permits require the dialogue to associate document fragments from specific periods, ensuring query results match current work shift requirements. Documents with multiple fields and units require prompts to explicitly specify parameter units, preventing confusion between values from different operating conditions. Documents with strong interlock controls require the dialogue to quickly locate interlock bypass records, while limiting context length to avoid interference from irrelevant data. The need to maintain steady state in continuous production requires multi-turn dialogue to break down problems step by step: first confirm the current operating condition, then gradually verify indicators.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| Maximum context length | 800–1200 characters | Matches the average length of single-process descriptions in basic chemical continuous production documents, avoiding information truncation caused by context overflow |
| Historical session binding | Bind the `chatId` parameter | Ensures multi-turn dialogue under the same operating condition reuses global variables from historical sessions, such as current tank liquid level and shift energy consumption data, avoiding repeated input of basic information |
| Global variable storage | Bind periodic data via the `variables` parameter | Associates shift-updated shift logs, interlock records, and energy metering data, ensuring the dialogue can call the latest in-cycle parameters |
| Dialogue message context | Bind the `messages` parameter | Ensures historical messages from multi-turn dialogue are correctly transmitted, supporting context continuity—for example, first confirm the current reactor temperature, then verify interlock status |
| Tool call timeout | 600 seconds | Matches the average time required for DCS data queries and laboratory report retrieval, avoiding interruptions to valid queries due to short timeouts |
| Number of single-recall documents | Top 6 | Covers the three core data types of process, equipment, and metrology that may be involved in a single round of dialogue, avoiding recall of too many irrelevant documents |

## Three Common Misconfigurations
- Issue: Returns a 400 status code (no body) when calling the MySQL database tool. Cause: Did not bind the authentication field for the database connection in the `variables` parameter, resulting in missing required parameters for the request.
- Issue: Fails to load globally saved variables from previous sessions during multi-turn dialogue. Cause: Did not bind the context storage for the corresponding session via the `chatId` parameter, resulting in no association of the session context.
- Issue: Process parameters from non-current operating conditions appear in dialogue results. Cause: Did not limit the maximum context length, resulting in recall of outdated shift logs or historical data from abnormal operating conditions.

## How to Verify Proper Configuration
- In FastGPT v4.17.0, initiate a query targeting current process indicators, confirming that the returned results include current operating condition parameters with units, such as temperature and pressure.
- Initiate a second query, supplementing with a request for the latest interlock bypass status, confirming that the dialogue context retains the operating condition information from the first round.
- Call the database tool to execute a data query, confirming that the returned results meet expectations and show no errors.
- Switch the session ID to initiate a new dialogue, confirming that the new session does not load global variables from the old session.
