# Process Change and Engineering Change Process Specification and Technical Standard Q&A: HTTP Interface and External Systems

## What this category of data looks like
Data for this category comes from PLM, ERP, MES, supplier materials, validation tests, and customer-specific requirements. Updates are triggered irregularly with each process or engineering change.
Daily documents include ECN/ECR forms, change assessment reports, drawings and BOM version records, process validation reports, production switch plans, inventory disposal documents, and customer approval files.
Data fields include change number, version number, effective date, associated process/material list, approval status, and validation results.
There is no unified fixed batch update rhythm. Each document is tied to a clear version switch node.

## What constraints do these characteristics impose on the HTTP Interface and External Systems link
Data sources cover multiple production management systems. Interfaces must support cross-system authentication and format adaptation. This prevents parsing failures caused by inconsistent data formats.
Irregular updates triggered by changes require interfaces to support event-driven synchronization or on-demand pulling of the latest version data.
Each document is tied to a clear version switch node. Interfaces must carry version identification parameters. This ensures that process specification content for the corresponding version is returned.
Data is linked to multi-department approval processes. Interfaces must synchronize approval status fields. This prevents returning unapproved change content.
The interconnected nature of multi-system data requires interfaces to support batch pulling of associated documents. This avoids returning excessive redundant data in a single request.

## How to configure settings
This configuration is written based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `Authorization` header configuration | Carry a Bearer-type token bound to the enterprise unified authentication key | Adapt to cross-domain authentication requirements across multiple production systems, avoid cross-domain errors |
| `variables` parameter | Pass three core variables: change number, version number, effective date | Ensure the interface returns process specifications and standard content for the corresponding version |
| `responseData` filtering | Extract approval status and associated process fields, discard redundant attachment information | Match the core query needs of change management teams |
| Timeout threshold | 30 seconds | Adapt to the average response duration of multi-system data pulling |
| Retry count | 2 times, 5 second interval | Respond to temporary cross-system network fluctuations |
| Single query quantity | Top 10 entries | Match the average number of documents associated with a single change |

## Three common configuration errors
- A CORS cross-domain error is returned during front-end interface calls, with a status code of 403 or 405. The cause is that the front-end domain name was not added to the allowed cross-domain list in the FastGPT configuration, or the authentication format of the `Authorization` header was not configured correctly.
- Valid authentication keys cannot be obtained after calling the interface, and database query-related errors are prompted. The cause is that the storage location and query rules of the key were not clearly defined, and the query logic for the corresponding database table was not associated.
- The external system is not called as expected after intercepting specified keywords. The cause is that the keyword trigger rule was not configured in the conversation flow, or the interface address and parameters of the external system were not bound correctly.

## How to confirm that the configuration is complete
- Use a front-end testing tool to send a request carrying the `Authorization` header. Check whether normal process specification content is returned, and no cross-domain errors occur.
- Pass different change number and version number parameters. Verify whether the returned document content matches the ECN/ECR form of the corresponding version.
- Trigger a change event. Check whether the external system receives the synchronized interface request carrying correct approval status and associated fields.
- Simulate a timeout scenario. Check whether the interface automatically retries according to the configured retry count, with no blocking behavior.

The values provided are common starting points and should be evaluated against the reader's own samples.
