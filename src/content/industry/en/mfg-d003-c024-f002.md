# Process Change and Engineering Change Process Procedure and Technical Standard Q&A: Vector Models and Indexes

## What this category of data looks like
Manufacturing enterprise change management teams generate documents daily. These include ECN/ECR, change assessment reports, drawings and BOM versions, process validation reports, transition plans, inventory disposal documents, and customer approval documents.
Data sources cover PLM, ERP, MES, supplier materials, validation test records, and customer special requirements. Updates occur irregularly, triggered once per process or engineering change.
Documents contain structured BOM fields and unstructured validation report text. No unified fixed fields exist, so unified processing adapted to multi-format data is required.

## Constraints on vector models and indexing from these data characteristics
Multi-source heterogeneous data sources require vector indexes to support unified preprocessing and incremental synchronization of cross-system data, to avoid embedding failures caused by data format differences.
Irregular update cycles require index configurations to adapt to non-periodically triggered incremental updates, to avoid excessive resource usage from full indexing.
Documents contain both structured and unstructured content, so chunking strategies must balance semantic integrity across different formats.
Changes involve multiple types of related documents, so indexes must retain version-related metadata to distinguish changed content between old and new versions during retrieval.

## Configuration settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Ensures semantic integrity for unstructured documents such as ECN and process validation reports, avoids semantic breaks within chunks |
| Overlap Length | 100–150 characters | Preserves cross-chunk process steps and change-related information, prevents change descriptions from being truncated |
| Similarity Threshold | 0.75–0.85, calibrated via actual testing | Distinguishes core and marginal associations for process changes, meets precise retrieval needs in change scenarios |
| Single Search Limit | Top 8 results | Covers related results across multiple document types involved in changes, including BOM, drawings, and validation reports |
| Maximum Context | 4000 tokens | Adapts to long-text integration needs for change assessment reports, matches the default context limit of FastGPT v4.17.0 |

## Three common configuration errors
- A 401 status code is returned when accessing a third-party vector model. Cause: The model's API access key is not configured correctly, or the key is not authorized to perform vector embedding operations.
- After custom document chunking, the knowledge base automatically deletes duplicate chunks, causing retrieval order to mismatch chunking results. Cause: The global duplicate chunk deduplication function of the knowledge base is enabled, and associated metadata for chunk order is not retained.
- Retrieval response times out after configuring the vector index. Cause: The incremental index trigger interval is not adjusted based on the update frequency of change documents, and frequent full index triggers cause excessive resource usage.

## How to confirm correct configuration
- Submit a vector model access test request, confirm that the returned embedding vector format meets platform requirements, and that no 401 or timeout errors occur.
- Upload a change document containing duplicate content, check if the knowledge base retains the chunked order, or adjust deduplication rules according to the configuration.
- Initiate a retrieval request related to process changes, confirm that the number of returned results matches the configured single search limit.
- View the index update log, confirm that incremental indexing triggers only after change documents are uploaded, and that no unnecessary full updates occur.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
