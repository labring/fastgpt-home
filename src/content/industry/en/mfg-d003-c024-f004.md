# Process Change and Engineering Change Process Specification and Technical Standard Q&A: Workflow Orchestration

## What this category of data looks like
This category corresponds to the process and engineering change scenarios of the manufacturing enterprise change management team. Daily data sources include PLM, ERP, MES, supplier materials, verification test records, and customer special requirement documents. Data updates are triggered irregularly with each change. Involved documents include ECN/ECR, change assessment forms, drawings and BOM version files, process verification reports, production switching plans, inventory disposal documents, and customer approval documents. Core fields include change number, version number, effective date, verification result, and material code. The version number uses string format, and the effective date is a date-type field.

## What constraints these characteristics impose on the "workflow orchestration" link
Multiple data sources require the workflow to be configured with cross-system docking nodes, ensuring that drawings in PLM, BOM data in ERP, and production records in MES can be retrieved. Diverse and closely related document types require recall rules to be configured by change scenario classification, to avoid irrelevant documents interfering with Q&A results. The chain impact of the change process requires the workflow to be verified in sequence according to approval nodes, ensuring that the design, material, process, and inspection links of the change have all completed verification. Irregular update rhythms require the workflow to support incremental synchronization triggers, to avoid resource waste caused by full data retrieval. Multi-team participation in the change process requires avoiding concurrent call conflicts, ensuring that only one core operation is executed for the same change process.

## How to set the configurations
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Variable Configuration | Bind `variables` to change number, version number, effective date | Match the core identification fields of business documents, enabling accurate retrieval of associated data for the corresponding change |
| Tool Call Node | Trigger by selecting one option based on change type | Differentiate the processing logic for process changes and engineering changes, avoiding concurrent call conflicts |
| Error Handling Branch | Capture the exception status returned by `nodeId`, and jump to the manual verification node | Address scenarios where tool calls fail or data retrieval is abnormal, ensuring process traceability |
| Context Call Limit | Top 10 matching documents | Control the retrieval scope, adapt to the single volume of change documents, and avoid context overload |
| Timeout Threshold | 600 seconds | Cover the time consumed by cross-system data retrieval, adapting to the acquisition cycle of multi-source data such as PLM and ERP |
| Retry Count | 2 times | Address temporary network fluctuations or system delays, reducing process termination caused by single exceptions |

## Three common mistakes
- A 400 status code is returned when the workflow calls a tool. The cause is that `variables` are not configured as the core identification fields of the corresponding change, causing the system to fail to accurately retrieve associated documents.
- The AI conversation node returns empty content or an error, and the process terminates directly. The cause is that no error handling branch is configured, and no fallback jump is set for abnormal results.
- Concurrent execution occurs during multiple tool calls, causing multiple processes for the same change to modify BOM data simultaneously. The cause is that the one-option trigger rule based on change type is not set.

## How to confirm the configuration is complete
- Simulate submitting a test change application, check whether the workflow triggers the corresponding tool node based on the change type.
- Manually trigger a tool call failure, check whether it jumps to the preset manual verification node.
- Check whether the variable configuration binds core business fields such as change number and version number.
- View the workflow running logs, confirm that there are no concurrent call records.

The values provided are common starting points and should be measured against the reader's own samples.
