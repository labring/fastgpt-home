# Process Change and Engineering Change Process Specification and Technical Standard Q&A: Deployment and Upgrade

## What the data for this category looks like
Data for this category is generated by manufacturing enterprise change management teams. It involves cross-role collaboration across research and development, process, quality, production, procurement and other teams.

Data sources include PLM, ERP, MES systems, supplier materials, process validation test records and customer special requirement documents. Data updates trigger irregularly for each process or engineering change. A single change generates multiple document types: ECN/ECR forms, change assessment reports, drawings and BOM version files, process validation reports, production switching plans, inventory disposal documents and customer approval documents.

Data fields include change number, version number, effective date, associated bill of materials, validation results and other items. Some documents contain unstructured content such as drawings and test data.

## Constraints on Deployment and Upgrade
The data characteristics of this category impose clear constraints on deployment and upgrade workflows.
First, data sources cover multiple heterogeneous systems. During deployment, cross-system data synchronization and docking parameters must be configured to ensure change documents are automatically synchronized from PLM, ERP and other systems to the knowledge base.
Second, data updates trigger irregularly alongside changes. During upgrades, the version mapping relationship of historical change data must be preserved to prevent mixing of old and new versions.
Third, documents include structured forms as well as unstructured drawings and test data. During deployment, storage services adapted to multiple file types must be configured to support storage and retrieval of large-volume attachments.
Finally, data generated through cross-role collaboration requires hierarchical permission parameters during deployment. This ensures personnel in different positions can only access change documents within their corresponding access permissions.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `MONGODB_URI` | `mongodb://fastgpt:yourpassword@mongodb-host:27017/fastgpt?authSource=admin` | Stores structured change metadata such as ECN/ECR forms, change assessment reports, and associated BOM version indexes |
| `STORAGE_S3_ENDPOINT` | `https://s3-cn-beijing.aliyuncs.com` | Stores large-volume non-text files such as drawings and process validation reports, and supports storage and retrieval needs for multiple types of attachments |
| `REDIS_URL` | `redis://:redispassword@redis-host:6379/0` | Caches context for change Q&A and similar document retrieval results, reducing latency from reading data across multiple systems |
| `DB_MAX_LINK` | `150–250 connections` | Adapts to concurrent query request volumes for change documents across multiple teams, preventing service interruptions caused by exhausted database connections |
| `FILE_TOKEN_KEY` | `32-character random string generated per enterprise’s own security rules` | Encrypts access tokens for process documents, preventing unauthorized roles from accessing sensitive change-related files |
| `FE_DOMAIN` | `https://your-fastgpt-domain.com` | Configures the frontend access domain name, ensuring that the frontend interface for change Q&A can properly load preview links for associated documents |

## Three Common Misconfigurations
- Issue: Pulling the official Docker image times out during deployment, even after configuring a domestic mirror source. Cause: The Docker image acceleration address is not correctly configured, or the acceleration source does not cover the full path of the FastGPT official image repository.
- Issue: Unable to update the application version online after Docker deployment. The container does not restart normally after executing the update command. Cause: Updating without stopping the existing container, or failing to back up the database configuration file leading to data loss.
- Issue: Some change documents cannot be retrieved after an upgrade, or returned version information is incorrect. Cause: Failing to retain the version index fields of the original database during upgrade, causing the association between old and new change data to break.

## How to Verify Correct Configuration
- Log in to the FastGPT v4.17.0 admin backend, access the database connection monitoring panel, and confirm the current connection count does not exceed the `DB_MAX_LINK` configuration threshold.
- Upload a process validation report to the system, and verify the file can be previewed and downloaded normally through the configured `STORAGE_S3_ENDPOINT` endpoint.
- Initiate a simulated process change Q&A query, and confirm returned results include the correct change number, version number and associated document links.
- Test access permissions for different role accounts, and confirm only authorized roles can view sensitive change documents including customer approval documents.

The values provided are common starting points and should be evaluated against local operational samples.
