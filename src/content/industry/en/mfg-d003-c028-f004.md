# Incoming Material Inspection and Supplier Quality Process Specification & Technical Standard Q&A: Workflow Orchestration

## What this category of data looks like
Data sources include purchase orders, drawing specifications, supplier quality certificates, inspection equipment data, historical quality records, and supplier portal information. Updates are triggered per incoming batch, supplier evaluations are completed monthly or quarterly, and audits are conducted irregularly. Daily documents include inspection specifications, sampling plans, incoming material reports, supplier audit reports, exception contact sheets, 8D reports, and concession acceptance approval forms. Document fields include batch identifiers, inspection project parameters, non-conformity judgment items, approval workflow nodes, and more. Units match corresponding inspection items and business document specifications.

## Constraints on workflow orchestration for this category
Data sources for this category are scattered, and update rhythms vary widely. Workflows must support flexible access and real-time synchronization of multiple data types, and adapt to document parsing for different formats such as purchase orders and supplier quality certificates. Daily documents have diverse structures, including complex content such as tables and approval nodes. Workflows must be configured with corresponding nodes to support field extraction and transfer for different business documents. Business fields carry specific meanings such as batch identifiers and inspection parameters. The `variables` binding for workflows must strictly match corresponding business fields to avoid inspection judgment errors caused by parameter confusion. Additionally, incoming material inspection requires real-time processing, so workflows must support execution triggered per batch. Supplier evaluation workflows must support automatic startup on a periodic basis.

| `variables` binding rules | Bind business fields such as incoming material batch number, supplier name, and inspection project | Accurately extract business data, avoiding inspection judgment errors caused by parameter confusion |

| Failure handling configuration | Retry 2 times, with 60 seconds between each retry | Avoid temporary network or system issues interrupting the inspection process |

## Three common configuration errors
- An error `Failed to connect to jyfkk:1433 - 38BBDDC3AF7F0000` occurs when configuring an MSSQL data source connection. The cause is incorrect configuration of the database server address and port mapping, or network policies restricting port access.
|
| Background knowledge for the question classification node is filled with disorganized content, leading to large deviations in classification results. The cause is failure to extract core exclusive document fragments such as inspection specifications and sampling plans, with filled content not matching the business scenario.
|
| No failure handling node is configured for the workflow, resulting in no alert after process execution interruption. The cause is ignoring the real-time requirements of the incoming material inspection process, and failing to set retry or alert mechanisms.

## How to confirm configuration is complete
- Trigger a simulated incoming material inspection process, and verify whether the workflow starts according to the preset trigger conditions.
- Check whether the business fields bound to `variables` match the purchase order and supplier information of the current simulated batch.
- View the return result of the question classification node, and confirm whether classification is completed based on the filled background knowledge.
- Simulate a data source connection failure, and verify whether the failure handling node triggers the retry or alert process.
- Verify that the workflow export function operates normally, ensuring that process configurations can be backed up and migrated.
