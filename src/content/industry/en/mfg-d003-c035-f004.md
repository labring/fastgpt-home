# Heat Treatment Process Specifications and Technical Standards Q&A: Workflow Orchestration

## What data for this category looks like
Heat treatment scenario data originates from material grade archives, customer technical requirements, temperature control instruments, furnace temperature uniformity testing equipment, hardness testers and metallographic equipment, and workshop MES systems. Data is updated per heat and per batch, and covers documents including heat treatment process cards, charging charts, furnace temperature curves, hardness and metallurgical reports, equipment inspection forms, exception handling sheets, and more. Core fields include material grade, heating temperature, holding duration, cooling rate, hardness value, furnace number, and others. Units include degrees Celsius, hours, HV hardness units, and similar.

## What constraints these characteristics impose on the "workflow orchestration" link
The per-heat update characteristic of heat treatment data requires workflows to bind to the trigger timing of a single heat, to avoid mixing cross-batch data.
The combination of multiple document types and data sources requires workflows to support inputs in different formats, including structured databases, time-series curve files, quality inspection reports, and more.
Links with long core process parameter verification times require workflows to split verification steps and set reasonable timeout nodes.
The characteristic of severe error consequences requires workflows to configure exception branch jumps and verification links, to prevent unqualified processes from entering subsequent stages.

## Configuration Settings
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale for This Value |
| ---- | ---- | ---- |
| Data source trigger timing | Trigger after each heat data sync is complete | Matches the update rhythm of heat treatment data updated per heat |
| Variable binding rules | Bind material grades and furnace temperature parameters defined in `variables` | Process specifications and technical standard Q&A rely on fixed core fields |
| Node timeout settings | 120–180 seconds | Adapts to the typical time required for furnace temperature data collection and parameter verification |
| Historical context limit | Previous 8 historical Q&A records | Matches the scenario boundary of single-heat Q&A |
| Exception branch jump | Bind the exception handling node with `nodeId` | Avoids batch unqualified risks caused by heat treatment process errors |
| Log output path | Workflow execution log directory | Facilitates troubleshooting of issues such as database connections and parameter verification |

## Three Common Configuration Mistakes
- Phenomenon: Database connection error Failed to connect to jyfkk:1433 - 38BBDDC3AF7F0000. Cause: Correct MSSQL instance address and port are not configured, or network policies restrict access to port 1433.
- Phenomenon: Console.log logs from the code running module cannot be viewed in the front-end console. Cause: The workflow detailed log switch is not enabled, or logs are not synchronized to the front-end display interface.
- Phenomenon: Workflow execution times out and terminates. Cause: A timeout time matching heat treatment process verification is not set, causing the key parameter verification link to be forcibly interrupted.

## How to Confirm the Configuration Is Complete
- Trigger a simulated heat data synchronization, check whether the workflow starts automatically at the configured timing.
- View workflow execution logs, confirm that the core fields bound to `variables` and the exception node associated with `nodeId` both function normally.
- Simulate input of parameters that do not meet process requirements, check whether the exception branch triggers a jump as configured.
- Verify the database connection configuration, confirm that corresponding data such as heat treatment process cards and furnace temperature curves can be pulled normally.

The values provided here are common starting points, and should be evaluated against the samples used in the specific deployment scenario.
