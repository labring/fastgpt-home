# Production Planning and Shop Scheduling Process Specifications & Technical Standards Q&A: HTTP Interfaces and External Systems

This document is written based on FastGPT v4.17.0.

## What data does this category include
Data for this category comes from enterprise ERP system order and inventory records, BOM lists, process routes, equipment capacity ledgers, staff shift schedules, work-in-progress ledgers, and supplier arrival records. Daily generated documents include sales orders, master production schedules, material requirements plans, weekly and daily scheduling sheets, production work orders, material shortage lists, and delivery change notices. Each document includes dedicated business fields. For example, work orders include process numbers, estimated working hours, material withdrawal quantities, and other fields. Data update frequencies vary by business scenario: daily summary updates, weekly scheduling updates, and real-time updates for order changes or exception events. Data fields have specific units corresponding to each document type. For example, working hours use hours as the unit, and material requirements use pieces or kilograms as the unit.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Since data sources cover multiple internal enterprise systems, interfaces must support cross-system parameter transfer and data splicing. This avoids parsing failures caused by inconsistent data source formats. Uncertain data update timelines require interfaces to support both on-demand real-time queries and scheduled batch pulls. This adapts to requirements of different scheduling scenarios. Complex document structures and dedicated field units require interfaces to have strict parameter validation logic. This ensures incoming query conditions and returned result formats match business rules. Additionally, the timeliness of scheduling adjustments requires interfaces to have low-latency response capabilities. Interfaces must also support failure retry mechanisms. This avoids interrupting production plan generation processes due to single call exceptions, which disrupts normal shop scheduling.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Interface authentication method | Use the `Authorization` header with a Bearer token | Complies with security standards for enterprise-level production systems, avoids plaintext transmission of secrets, and adapts to permission control requirements of shop scheduling systems |
| Request timeout period | 600 seconds | Adapts to time consumption requirements of cross-data-source joint queries, avoids interrupting scheduling processes due to cross-system call timeouts |
| Return data encapsulation | Encapsulate structured results in the `responseData` field | Allows shop scheduling systems to directly parse matching content from process specifications and technical standards |
| Query variable passing | Pass order numbers and device IDs via `variables` | Accurately locates process documents corresponding to production plans, narrows matching scope, and improves query efficiency |
| Concurrent request limit | First 20 concurrent requests | Matches daily processing capacity of shop scheduling systems, avoids system overload that disrupts production scheduling |

## Three common configuration errors
- Scenario: When no matching process specifications are found in the knowledge base, the HTTP interface returns an empty result and does not display online search content to users. Cause: No matching failure trigger logic is configured, so the online search for the latest process standard content is not invoked, failing to meet real-time query requirements for shop scheduling.
- Scenario: The interface returns status code 429 but automatic retry is not triggered. Cause: No reasonable concurrent limit is set, exceeding the carrying capacity of the shop scheduling system, resulting in request throttling.
- Scenario: The incoming `variables` parameter does not include an order number, causing the matched process specifications to not correspond to the current production plan. Cause: Required parameters are not validated, leading to overly broad query scope or inaccurate results from the interface, which affects scheduling accuracy.

## How to verify correct configuration
- Send a test request with a known order number and `variables` parameter, check if `responseData` returns matching content for the corresponding process specifications.
- Simulate a scenario where no matches exist in the knowledge base, confirm that the interface triggers online search and returns compliant results.
- Adjust the number of concurrent requests, observe that the system handles requests normally without authentication or timeout related errors.
- Check that the `Authorization` header is correctly carried, confirm that no authentication failure prompts appear.
