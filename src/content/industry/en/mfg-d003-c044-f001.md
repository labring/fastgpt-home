# Pulp and Paper Process Specifications and Technical Standards Q&A: HTTP Interfaces and External Systems

## What this category of data looks like
Process and standard data for the pulp and paper industry typically comes from daily documents and systems of preparation, pulping, paper making, quality and energy departments. Daily documents include pulp preparation sheets, beating records, paper machine operation logs, online quality curves, laboratory reports, sheet break and grade change records. Data sources include wood pulp and waste paper batches, DCS/QCS systems, paper machine online measurement equipment, laboratory testing systems, energy and water treatment systems. Data update frequencies cover real-time (such as online quality curves), per shift (such as beating records), and per roll (such as sheet break and grade change records). Data fields include stock consistency, beating degree, paper grammage, moisture content, and most use industry-standard physical units.

## What constraints these characteristics create for HTTP interfaces and external systems
Because data sources cover multiple production systems with varying update frequencies, HTTP interfaces must support on-demand pulling of process data for specific time ranges or production batches. Because data fields use industry-specific physical units, interface input parameters must clearly define mapping rules between fields and units. This prevents external systems from making incorrect process recommendations due to unit mismatches. Because process parameters are strongly bound to production batches, external systems must pass the current production context when calling interfaces. Thus, interfaces must support receiving and parsing global variables. Additionally, because production data relates to process safety, incorrect parameter passing may cause issues such as downgraded paper rolls, sheet breaks, or machine shutdowns. Therefore, interface authentication configurations must strictly control access permissions to prevent unauthorized calls from disrupting production workflows.

## How to set the configurations
The following configuration items apply to FastGPT v4.17.0:

| Configuration Item | Recommended Setup | Rationale |
| --- | --- | --- |
| `Authorization` | Set to Bearer Token, valid for 1200 seconds | Aligns with data access permission control requirements in pulp and paper production environments, prevents unauthorized calls |
| `variables` | Receive global variables passed from external systems, including production batches, current stock parameters, paper machine models, etc. | Meets real-time production context requirements for process specification Q&A |
| `responseData` | Only return the first 3 standard process solutions matching the current scenario | Reduces data parsing and processing burden for external systems |
| Timeout Settings | Calibrated to 60–120 seconds based on actual testing | Matches process response cycles for pulping and paper making links, avoids interrupting production workflows due to timeouts |
| Authentication Check | Enable request header authentication check | Prevents unauthorized external systems from calling interfaces to obtain sensitive process data |

## Three common mistakes
- Phenomenon: An external platform calls a published interface, and the returned process solution does not match the current production batch. Cause: Global production context variables are not passed via the `variables` parameter, so the Q&A service cannot match the process standards for the corresponding batch.
- Phenomenon: Configuration of a OneAPI interface fails during testing, with a prompt that the port is unreachable. Cause: Local container ports are not mapped to network addresses accessible to FastGPT, so FastGPT cannot connect to the model service.
- Phenomenon: The number of interface call return results exceeds expectations. Cause: The number of standard solutions returned by `responseData` is not properly limited, resulting in external systems receiving excessive redundant data.

## How to confirm the configuration is correct
- Pass test global variables to the interface, such as a specific stock batch or beating degree parameter, and check if the returned process solution matches the passed parameters.
- After configuring `Authorization` authentication, call the interface with an invalid token, and confirm that a 401 Unauthorized status code is returned.
- After calling the interface, check the fields returned in `responseData` to confirm that expected content such as process steps and parameter adjustment values is included.
- Simulate a long-running request, confirm that the interface returns valid results within the set timeout period, and no timeout errors occur.

The values provided here are common starting points and should be measured against the reader's own samples.
