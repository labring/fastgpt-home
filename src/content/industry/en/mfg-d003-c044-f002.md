# Pulp and Paper Process Specifications and Technical Standards Q&A: Vector Models and Indexing

## What this category of data looks like
Data for pulp and paper specific scenarios originates from preparation, pulping, paper making, quality, and energy departments. It covers documents including pulp mixing sheets, beating records, paper machine operation logs, online quality curves, laboratory reports, sheet break and product change records.
Data sources include wood pulp and waste paper batch ledgers, DCS/QCS systems, paper machine online measurement equipment, laboratory testing systems, and energy and water treatment systems.
Update cycles span three levels: real-time, per shift, and per roll. Individual documents contain fields with clear units such as pulp ratio, beating degree, grammage, and moisture content. Some online quality curves use time-series numerical formatting.

## Constraints for vector models and indexing
Since data update frequencies range from real-time to per-roll levels, indexing tasks must adapt to different scheduling strategies. This prevents real-time data processing from blocking batch tasks.
Time-series documents such as online quality curves and sheet break records have structures different from conventional text. When splitting chunks, the integrity of key parameters must be preserved to avoid broken retrieved information from cross-chunk splitting.
Cross-system data from multiple departments generates large numbers of duplicate or related entries. During indexing, unified document unique identification rules must be implemented to avoid duplicate retrieval results.
Single-roll production data has a large volume. Resource usage for single-batch indexing must be controlled to ensure retrieval response speeds meet the real-time requirements of process Q&A.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Matches the field length of single-page text such as pulp mixing sheets and beating records, avoids chunk splitting across key parameters like pulp ratio and beating degree |
| Overlap Length | 100–150 characters | Covers cross-chunk correlations of beating parameters and paper machine operation parameters, prevents breakage of key time-series information |
| Similarity Threshold | 0.72–0.85 | Matches the numerical matching accuracy of online quality curves, avoids incorrect recall of production data from unrelated batches |
| Single Search Limit | Top 8 entries | Matches the number of records per shift or per roll, ensures retrieval results cover associated information for complete production batches |
| defaultToken | 4096 | Adapts to the long text content of laboratory reports, meets the maximum token limit per chunk and avoids long document truncation |
| maxToken | Set to the selected embedding model/service maximum supported input tokens | `maxToken` is the input-token maximum supported by the selected embedding model/service; verify it in that provider configuration. See the [v4.17.2 model-field reference](https://github.com/labring/FastGPT/blob/v4.17.2/document/content/self-host/config/model/intro.mdx). It is not retrieval/LLM context or a FastGPT-wide fixed cap. |

## Three Common Misconfigurations
- Multiple indexes configured to associate the same document chunk lead to duplicate retrieval results. This happens when the duplicate result deduplication switch is not enabled, or deduplication processing using document unique identifiers is skipped during indexing.
- Indexing time for single-roll paper machine operation records exceeds 600 seconds. This occurs when chunk length is set too large, and the asynchronous indexing task queue is not enabled, causing real-time data processing to block batch indexing tasks.
- The open-source version of the `阿里-emb3` model is confused with the commercial version. This happens when annotation information from the model’s open-source repository is not verified, and unauthorized model parameters are used for configuration.

## How to Verify Correct Configuration
- Upload a single pulp mixing sheet document, and confirm that chunked text fully retains key fields such as pulp ratio and beating degree, with no truncation or cross-chunk breaks.
- Run a test query containing "current beating parameters", and check that returned result similarity scores fall within the preset range, with no unrelated sheet break or product change records.
- Simulate real-time upload of a new paper machine operation record, and confirm that the indexing status changes to completed within a reasonable time, with no long-term pending status.
- Open the model configuration panel in FastGPT v4.17.0, and confirm that the open-source version parameters of the `阿里-emb3` model are correctly loaded, with no missing model file references.

The values provided are common starting points and should be evaluated against the reader’s own samples.
