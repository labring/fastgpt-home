# Q&A for General Mechanical Equipment Assembly Process Specifications and Technical Standards: HTTP Interfaces and External Systems

## What data for this category looks like
Daily documents for general mechanical equipment assembly include assembly process cards, BOMs, torque records, gap adjustment records, commissioning reports, factory inspection sheets, and packing lists. Data sources cover PLM/ERP, part inspection data, assembly tool collection, test benches, MES, and customer technical agreements. The update frequency is once per device or per order. Document fields include process steps, material codes and quantities, torque values, gap parameters, commissioning temperature rise data, and more. Field structures vary across different documents, so precise extraction based on business scenarios is required.

## What constraints these characteristics impose on HTTP interfaces and external systems
Since data sources are scattered and data per device or order is independent, HTTP interfaces must support precise querying by device serial number or order number to avoid pulling redundant full datasets. Document fields have specific units and structural differences, so interface requests must pass clear business parameters to ensure returned data matches conversation needs. Additionally, errors in the assembly phase have severe consequences, so interface calls must include failure retry and status code verification mechanisms to guarantee the stability and accuracy of data acquisition. Furthermore, synchronized updates of multi-source data require interfaces to support real-time pulling of the latest assembly processes and inspection data, adapting to frequent order-level update cycles.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Request timeout setting | 30–60 seconds | Adapts to the single query volume of assembly data, avoids long-term blocking of conversation flows |
| Request header configuration | Carry the `Authorization` field, with a value of a custom interface key | Ensures security of external interface access, prevents unauthorized calls |
| Variable passing settings | Pass the `variables` parameter, which includes device serial number and order number | Accurately locates assembly process and standard data for a single device |
| Response data processing | Extract structured fields from `responseData` | Quickly matches process query needs in conversations, avoids interference from redundant data |
| Retry strategy | Retry 2 times after failure, with a 5-second interval | Addresses temporary network fluctuations, ensures the success rate of interface calls |

## Three common misconfigurations
- Phenomenon: When using fetch syntax or Promise to handle responses in the HTTP module, returned results cannot be parsed properly. Cause: Did not follow FastGPT's HTTP interface configuration rules when processing response data; directly using native JS syntax caused conflicts between parsing logic and the platform's response processing mechanism.
- Phenomenon: When calling a backend interface deployed on Alibaba Cloud or an intranet penetration domain name, connection timeout or 403 status code is returned. Cause: Did not configure the allowed domain name whitelist, or the intranet penetration domain name was not mapped to the correct port, preventing FastGPT from establishing a valid connection.
- Phenomenon: The process data queried in the conversation does not match the actual device, returning incorrect gap adjustment or torque standards. Cause: Did not pass the correct device serial number or order number via the `variables` parameter, so the interface returned assembly data for other devices.

## How to verify the configuration is correct
- Manually call the configured HTTP interface, pass the preset device serial number parameter, and check if the returned `responseData` includes core fields of the assembly process card, such as process steps, torque values, and more.
- Launch the FastGPT v4.17.0 conversation interface, initiate a process query containing a specific device serial number, and check if the returned results match the preset assembly standard data.
- Disconnect the local or server network connection, initiate the interface call request again, and check if the preset retry mechanism is triggered and a clear error prompt is returned.
- Check if the `Authorization` field is configured correctly, use an invalid key to initiate a request, and confirm that a 401 status code is returned to verify that the authentication logic is effective.
