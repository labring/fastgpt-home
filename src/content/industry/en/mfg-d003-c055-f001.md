# Process Specification and Technical Standard Q&A for Foundry (Sand Molding, Precision Casting, Die Casting): HTTP Interfaces and External Systems

## What the data for this category looks like
Business data for this category comes from process and quality departments at foundries and die casting workshops. Daily documentation includes casting process cards, batching lists, heat records, mold history records, first article inspection records, material test reports, and nonconforming product review forms.

Data sources cover ERP material master data, melting furnaces and thermometers, spectrometers, MES heat records, mold management systems, customer drawings, and technical requirements. Update frequency follows per heat, per batch, or daily schedules.

Data fields include professional industrial parameters such as alloy batching ratios, melting temperatures, pouring parameters, and defect types. No universal standardized field format exists for this data.

## What constraints do these characteristics impose on HTTP interfaces and external systems?
Dispersed data sources and uneven update frequencies require interfaces to support on-demand pulling of multi-source heterogeneous data. This avoids resource waste from fixed polling.

Non-standard formats for professional fields require interfaces to adapt to foundry industry-specific terminology and units during parameter verification and data parsing.

High-risk business attributes require interfaces to include complete failure retry and exception alert mechanisms. This prevents production quality issues caused by failed data pulls.

Businesses also have strict data timeliness requirements. Interface response delays must match the pace of industrial production.

## How to configure the system
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {Foundry System API Key}` | Complies with API authentication standards for industrial systems, ensuring secure interface calls |
| Question Optimization | Enabled, bound to historical context | Resolves coreference resolution issues, adapts to referential terms for heat numbers and mold runs in process Q&A |
| Single Search Limit | Top 8 entries | Covers process specifications and inspection data linked to a single heat, avoids redundant results |
| Timeout Duration | 30 seconds | Matches typical response delays for pulling industrial equipment data |
| `variables` | Bound to heat number, mold number | Accurately matches process parameters and equipment records for the corresponding batch |
| Context Window Length | 1200 characters | Adapts to the length of foundry professional terminology, prevents truncation of critical parameters |
| `responseData` | Return only process parameters, inspection result fields | Reduces invalid data transmission and improves interface response efficiency |

## Three common misconfigurations
- An interface call returns empty results. The cause is that question optimization is not enabled, and historical context is not bound. This prevents recognition of referential terms such as heat number and mold run.
- A model duplicate configuration error appears after startup. The cause is that model parameters are declared in both system basic configuration and interface configuration, violating the single configuration source principle.
- A curl call returns a 401 status code. The cause is an incorrect `Authorization` parameter format, missing the Bearer prefix or using an invalid key.

## How to verify a successful configuration
- Initiate a test call with historical context. Verify returned results are associated with process parameters and inspection records for the corresponding heat.
- Review interface call logs. Confirm the `Authorization` parameter is correctly carried and passes authentication checks.
- Trigger a simulated heat data pull. Confirm `responseData` only returns the preset target business fields.
- Check the system configuration page. Confirm model-related parameters are not repeatedly configured across multiple locations.

The values provided are common starting points and should be measured against local samples.
