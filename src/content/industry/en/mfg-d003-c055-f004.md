# Process Specification and Technical Standard Q&A for Foundry (Sand Casting, Precision Casting, Die Casting): Workflow Orchestration

## What This Category of Data Looks Like
This category of data covers daily documents for foundry technology and quality departments at foundries, die casting workshops, and equipment and parts suppliers. Documents include foundry process cards, alloy batching sheets, heat melt records, mold history logs, first article inspection records, and material test reports.
Data comes from ERP material master data, melting furnace temperature measuring equipment, spectral composition analyzers, MES production systems, mold management systems, and customer technical drawings. Update frequency covers per heat, per production batch, and daily archiving. Core fields include alloy batching ratio, melting temperature, pouring parameters, internal defect types, and corresponding heat and mold number information.

## Constraints Imposed by These Characteristics on Workflow Orchestration
This category of data has a high update frequency. A single heat generates new batching, melting, and defect records. This requires workflow retrieval nodes to connect to real-time synchronized structured datasets.
Core fields include high-precision ratio and temperature parameters. Retrieval configurations must prioritize field-level exact matching logic to avoid generic recall.
Multiple heterogeneous data sources create differences in field formats. Workflows must include basic field validation steps to ensure input parameters align with the fields of the retrieved dataset.
Defect tracing requires association with heat and mold number information. Workflows must fix the transfer logic for associated fields to prevent parameter loss.

## How to Set the Configuration
| Configuration Item | Recommended Value | Rationale |
|---|---|---|
| `variables` | `{ "datasetId": "Target foundry process knowledge base dataset ID", "batchId": "${input.batch_id}" }` | Bind global variables to reuse dynamic parameters such as heat and batch numbers, and comply with FastGPT v4.17.0 variable transfer rules |
| Single search limit | Top 8 entries | Core matching items for foundry process parameters are limited. Too many retrieved results will increase context redundancy |
| Maximum context | 800–1200 characters | Core content of single foundry process documents is concentrated in this range, to avoid exceeding model context limits |
| `nodeId` | Unique identifier of the retrieval node | Fix the node ID in multi-node workflows to ensure correct variable transfer paths |
| Timeout threshold | 300 seconds | Multi-source data retrieval requires waiting for device data synchronization, reserve sufficient response time |

## Three Common Misconfigurations
- Symptom: A variable unbound prompt appears during workflow runtime, or the retrieval node returns empty results, and the configured global datasetId variable cannot be referenced. Cause: The datasetId of the corresponding foundry knowledge base is not bound in the workflow's global variable configuration, or the variable transfer path does not cover the retrieval node.
- Symptom: Retrieved results include unrelated forging process documents, and the number of retrieved entries exceeds expectations. Cause: Field-level matching rules are not configured, only full-text retrieval logic is used, and the retrieval scope is not limited to the foundry process dataset.
- Symptom: Workflow execution times out, and the status code shows 504. Cause: The timeout threshold is set lower than the average time required for device data synchronization, and sufficient retrieval response time is not reserved.

## How to Verify the Configuration Is Correct
- Enter the workflow's variable configuration page, confirm that the datasetId bound in `variables` matches the ID of the target foundry process knowledge base.
- Trigger a test run, input the batch ID of a single heat, and check that all results returned by the retrieval node include core foundry fields such as alloy batching and melting temperature.
- Manually adjust the timeout threshold to 100 seconds, run the test to confirm that a timeout prompt is triggered, and verify that the threshold configuration takes effect.
- View the workflow's node link diagram, confirm that the retrieval node corresponding to `nodeId` has been correctly connected to the variable transfer link.
