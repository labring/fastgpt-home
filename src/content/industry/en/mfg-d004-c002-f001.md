# Cross-review of technical documentation for SMT chip mounting and electronic assembly: HTTP interfaces and external systems

## What the data for this category looks like
The data for this category comes from BOMs, Gerber files, component coordinates delivered by customers, as well as MES systems, chip mounters, SPI/AOI inspection equipment, reflow oven temperature collection devices, and solder paste/component batch ledgers. Daily documents include BOM lists, line change work sheets, stencil parameter records, furnace temperature curves, first article confirmation reports, SPI/AOI solder joint defect reports, maintenance records, and traceability labels. Data updates are triggered in real time along with production work orders and line change operations. Each document contains fields such as part number, reference designator, component specification, coordinate parameters, inspection results, and some documents include batch numbers and timestamp units.

## What constraints do these characteristics impose on the HTTP interfaces and external systems link
The real-time update and work order-level triggering characteristics of this category require that HTTP interface calls be bound to the session context of the corresponding production work order to avoid cross-work order data confusion. The multi-source and heterogeneous document types (BOMs, SPI reports, furnace temperature records, etc.) bring field differences, requiring interface requests to adapt to metadata transmission for different documents. Frequent line changes and real-time inspection calls require limiting the payload size and call frequency of single requests to prevent external system overload. Batch numbers and timestamp fields attached to traceability documents must be transmitted synchronously with interface requests to ensure the relevance and traceability of cross-review.

## How to configure the settings
This configuration guide is written based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {Enterprise-specific API key}` | Meets interface authentication requirements for electronic manufacturing scenarios, ensuring only authorized systems can access sensitive document data |
| `variables` | `Bind value ranges associated with the current work order ID and document type` | Ensures each API call is linked to the corresponding production work order, avoiding cross-work order session confusion |
| `responseData` | `Only return cross-review results matching the part number and reference designator` | Filters redundant data to adapt to the core verification needs of SMT documentation |
| Timeout duration | `600 seconds` | Adapts to cross-system query time for multi-source heterogeneous documents, preventing request interruptions mid-process |
| Request payload limit | `800–1200 characters` | Adapts to the number and length of fields in SMT documents, avoiding request overlimit errors |

## Three common mistakes
- Phenomenon: Multiple API calls are not linked to the same production work order, resulting in cross-work order data confusion. Cause: The current work order ID is not bound as a session identifier via `variables`, causing each interface call to generate an independent context.
- Phenomenon: The HTTP request component fails to pass preset numeric parameters, and the corresponding fields are empty in the request log. Cause: Parameters are not bound to the `variables` configuration item, or parameter naming does not adapt to the field rules of SMT documents.
- Phenomenon: The metadata parameter carried in the interface request does not take effect, or is rejected by the system. Cause: Metadata transmission support is not enabled in the interface configuration, or the metadata parameter is not included in the request body as required.

## How to confirm the configuration is correct
- Initiate a single API call carrying the current work order ID and the metadata of the corresponding document, and check whether the returned results only include document data matching the current work order.
- Initiate multiple consecutive API calls linked to the same work order, and confirm that the session context is not reset and the data association relationship remains consistent.
- Check the interface authentication configuration, initiate a call using an invalid key, and confirm that a corresponding authentication failure prompt is returned to verify that the configuration takes effect.
- Simulate a request exceeding the payload limit, and confirm that the system returns a reasonable overlimit prompt to verify that the request limit configuration takes effect.

The values provided here are common starting points and should be measured against the reader's own samples.
