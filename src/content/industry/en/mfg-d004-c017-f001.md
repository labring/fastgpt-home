# Cross-review of technical documentation for coating and painting: HTTP interfaces and external systems

## What the data for this category looks like
Core data for coating and painting scenarios covers multiple types of business documents and real-time collected data. Daily documents include coating process cards, paint batch sheets, paint mixing records, film thickness and color difference reports, oven curves, defect repair orders, and VOCs ledgers. Fields include film thickness (unit: μm), color difference ΔE, oven temperature (unit: ℃), paint batch numbers, VOCs concentration (unit: mg/m³), and other metrics.
Data sources include paint supplier TDS/SDS, real-time data from spray booths and ovens, colorimeters, film thickness gauges, environmental monitoring equipment, and MES systems. Static documents update per batch or per shift. Real-time data is collected continuously.

## What constraints these characteristics impose on HTTP interfaces and external systems
Data for this category comes from multiple sources and has significantly different update rhythms. Static documents trigger updates per batch. Real-time data requires continuous pulling. Interfaces must support connection to multiple data sources and mixed update modes.
Document fields include specific physical units. Interface requests must carry standardized parameters to match field validation rules. A single coating batch has a large number of associated documents. Interfaces must support bulk data queries to reduce call times.
Errors can lead to batch appearance repairs, unqualified adhesion or corrosion resistance, VOCs management violations, and other consequences. Interfaces must configure idempotency and failure retry mechanisms to avoid duplicate submissions or data loss.

This configuration is optimized for FastGPT v4.17.0.

## How to configure these settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer {system_token} | Complies with standard authentication specifications for external systems such as MES and testing equipment, and ensures secure interface calls |
| `variables` | Bind business parameters such as paint batch numbers, film thickness thresholds, and oven temperature ranges | Matches field validation for documents such as coating process cards and paint mixing records, and enables parameter linkage across documents |
| `responseData` | Extract core fields such as film thickness values, color difference ΔE values, oven curve nodes, and VOCs concentrations | Filters redundant data and focuses on key business information required for cross-review |
| Timeout threshold | 300 seconds | Matches the rhythm of continuous oven data collection, and avoids interrupting the review process due to real-time data pulling timeout |
| Retry count | 3 times | Addresses scenarios such as network fluctuations or temporary unavailability of external systems, and reduces the probability of single call failure |
| Request batch size | 20 items per request | Adapts to the average number of associated documents per coating batch, and balances interface load and call efficiency |

## Three common misconfigurations
- Interface disconnection and automatic reconnection failure occur after the MongoDB replica set primary node switches, returning a connection timeout status code. The root cause is that session persistence or automatic reconnection logic is not configured, causing the data stream dependent on MongoDB Change Streams to interrupt.
- Session context returned by each API call is inconsistent, and previously used coating process parameters cannot be reused. The root cause is that business variables are not bound to the global session, and the context is reinitialized for each request.
- The HTTP request component fails to pass configured numerical parameters, returning a `Request failed` error. The root cause is that variables are not correctly mapped to parameter positions in the request body or request header, causing the interface to fail to recognize and validate parameters.

## How to confirm correct configuration
- Send a simulated request, check that `responseData` correctly extracts core business fields such as film thickness and color difference, with no redundant or unrelated data.
- Simulate a primary node switch of an external system, verify that the interface can automatically reconnect and resume data pulling, with no persistent disconnection errors.
- Send 10 consecutive requests, check that session variables remain consistent, and ensure that business context can be reused for each call.
- Send a request that exceeds the configured batch size, check that the interface triggers reasonable splitting logic or current limiting prompts, with no abnormal errors.

The values given are common starting points and should be measured against the reader's own samples.
