# Cross-Review of Technical Documents for Safety, Environmental Protection and Special Operation Management: Workflow Orchestration
This document is written for FastGPT v4.17.0. It explains workflow orchestration for cross-review of technical documents in manufacturing scenarios focused on safety, environmental protection and special operation management.

## What Data Belongs to This Category
Core data for this category comes from regulatory standard libraries, online environmental monitoring systems, gas detectors, personnel qualification databases, equipment isolation lists and supervision platforms. Daily generated documents include risk identification forms, hot work/permit-to-work in confined spaces/hoisting operation permits, environmental monitoring records, hazardous waste ledgers, accident rectification reports and more. Data update frequencies cover new documents generated for each operation, real-time synchronization of monitoring data, and weekly or monthly updates of qualifications and regulatory content. Document fields include operation area, gas detection values (ppm/%LEL), hazardous waste generation volume (tons/kilograms), guardian qualification number and other specialized fields. Formats and units vary by document type.

## Constraints on Workflow Orchestration
Multi-source heterogeneous data sources require workflow configurations with multiple types of data source access nodes. These nodes adapt to interface formats of different systems. Differences in generation and update rhythms of operation documents require support for two modes: real-time review triggered by file uploads, and batch processing of regularly pulled monitoring data. Differences in formats and units of specialized fields require workflow configurations with targeted variable verification rules. These rules prevent invalid data from entering the review process. Cross-stage operation processes require strict node execution order. This ensures logical progression of steps such as risk identification, qualification verification and closed-loop confirmation. Additionally, errors in this category have severe consequences. Workflows must be configured with clear failure handling and alert mechanisms. These mechanisms prevent abnormal processes from entering production links.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Trigger Mode | File upload trigger, bound with `variables` verification | Match the operation type field in uploaded operation permits and monitoring records to automatically start the corresponding review process |
| Single Execution Timeout | 600–1200 seconds | Adapt to the average time required for single operation review, avoid timeout caused by fluctuations in data volume |
| Variable Verification Rules | Verify by specialized field format | Match format requirements for specialized fields such as gas detection ppm values and hazardous waste generation tonnage |
| Failure Retry Count | 2 times | Address temporary fluctuations in device interfaces, avoid single exceptions interrupting the process |
| Node Execution Order | Serial execution bound by `nodeId` | Ensure correct execution logic for risk identification, qualification verification and closed-loop confirmation |
| File Upload Limit | 100 MB | Adapt to the maximum storage specification for single operation documents |

## Three Common Misconfigurations
- Symptom: Workflow nodes return a premature close error. Cause: No `variables` verification rule is configured. Invalid format detection records or operation permits trigger abnormal node interruptions, or the timeout threshold is set too low, causing data pulling to terminate before completion.
- Symptom: Workflow API execution time exceeds 1200 seconds. Cause: Complex review processes are not split into multiple serial sub-nodes, and timeout configuration does not match actual time required for multi-source data integration.
- Symptom: Calling a workflow API with file upload returns an empty result. Cause: The `variables` parameter for uploaded files is not correctly mapped in the API request, causing the workflow to fail to read the uploaded operation permit documents.

## How to Verify Proper Configuration
- Upload a standard hot work operation permit document to trigger the workflow. Confirm whether the corresponding review process is automatically started based on the bound `variables`.
- Simulate the maximum data volume for a single operation review, run the workflow. Confirm whether execution time matches the preset timeout threshold.
- Call a workflow API with file upload, upload a test hazardous waste ledger file. Confirm whether the API returns normal execution status.
- Manually trigger a node error scenario. Confirm whether failure retry and log recording are executed as configured.

All provided configuration values are common starting points. Adjust settings based on your own specific samples and operational requirements.
