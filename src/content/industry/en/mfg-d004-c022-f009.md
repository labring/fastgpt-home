# Cross-Review of Technical Documentation for Complete Home Appliance Manufacturing: Model Access and Configuration

## What Data Looks Like for This Product Category
Core documents for this category include configured BOMs, assembly work instructions, refrigerant charging records, electrical safety test reports, performance sampling inspection reports, and rework records. Data sources cover ERP/MES systems, component batch ledgers, tightening and charging equipment logs, safety compliance tester data, performance laboratory test results, and after-sales fault archives.
Data updates are triggered by production milestones. Documents tied to a single product are updated once per unit. Shift-level documents are updated per shift. Sampling documents are updated per established sampling plans.

## What Constraints These Characteristics Impose During Model Access and Configuration
Data sources for this category are scattered, with significant differences in update frequencies. Model access must support real-time or batch data pulling from multiple sources, and adapt to varied formats of equipment logs and test reports.
Single-product documents have tightly linked relationships. Cross-review requires accurate matching of same-batch components to corresponding production and test records. This means configuration must include enhanced context association verification.
Consumer-facing product requirements mean review results must cover safety compliance, appearance, and function dimensions. Model configuration must balance field extraction accuracy across multiple document types, to avoid risks such as mixed-line misassembly and process out of control.

## How to Set Configurations
The following configurations are based on the parameter logic of FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | Covers full context of multiple assembly work instructions, safety compliance reports, and rework records, avoiding truncation of critical associated information |
| `maxTokens` | `2000–3000 token` | Adapts to the output length of a single review result, meeting text requirements for multi-dimensional anomaly judgment |
| `toolChoice` | `auto` | Allows the model to independently choose whether to call tools for cross-document data verification, adapting to multi-source data cross-check scenarios |
| `temperature` | `0.1–0.3` | Reduces random output probability, improving accuracy of compliance reviews for safety compliance and process parameters |
| `AIPROXY_API_ENDPOINT` | Fill in the actual access address based on the enterprise’s internal deployment instance | Adapts to enterprise intranet access restrictions, ensuring stability of model calls |
| `AIPROXY_API_TOKEN` | Configure a dedicated authentication key | Differentiates call permissions across production environments, preventing cross-environment data confusion |

## Three Common Configuration Mistakes
- Returns a 401 status code when called, but the key works in Postman tests. Cause: The configured `AIPROXY_API_TOKEN` is not bound to the access permissions of the corresponding production environment, or there are extra spaces in the key during configuration.
- Cannot trigger the specified tool push when the model calls a plugin. Cause: The authentication information of the plugin was not correctly associated in the configuration, or the trigger condition for tool calls does not match the review process node.
- Receives two requests when interpreting a file, and the second request has an incorrect Authorization field. Cause: The context reuse logic did not correctly pass authentication parameters, causing the second request to use an expired or incorrect key.

## How to Verify Valid Configuration
Based on the configuration logic of FastGPT v4.17.0, configuration effectiveness can be verified through the following actions:
- Call the test interface, check if the returned authentication status code is normal, and confirm that the `AIPROXY_API_TOKEN` configuration is correct.
- Import associated documents for a single home appliance, trigger a cross-review task, and verify that the context coverage of the model output matches expectations.
- Simulate multi-source data input, verify that tool calls can be triggered as configured, and confirm that the `toolChoice` setting takes effect.
- Review the anomaly judgment results output by the model, and verify that output stability matches the configuration expectations of the `temperature` parameter.

The values provided are common starting points and should be measured against the reader's own samples.
