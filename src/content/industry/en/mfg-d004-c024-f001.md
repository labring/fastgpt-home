# Cross-Review of Technical Documents for Process Changes and Engineering Changes: HTTP Interfaces and External Systems

## What Data for This Category Looks Like
Data for this category originates from PLM, ERP, MES, supplier materials, validation tests, and customer-specific requirements. Updates are triggered by each process or engineering change, with no fixed cycle. Daily processed documents include ECN/ECR, change assessment reports, drawings and BOM version files, process validation reports, transition plans, inventory disposal forms, and customer approval documents. Core fields include change number, version number, effective date, associated material code, and approval status. Version numbers use the Vx.y labeling format. Effective dates follow the YYYY-MM-DD format.

## Constraints for HTTP Interfaces and External Systems
Multiple data sources require interfaces to adapt to authentication rules of different external systems. Standardized authentication credentials must be passed through the `Authorization` parameter. There are many document types, and data volume per single change varies widely. Dynamic field mapping rules for different documents must be supported via `variables` configuration. Changes are triggered without a fixed cycle, so interfaces must support on-demand calls. Large drawings and BOM files must be transferred and parsed, so request durations must be configured appropriately. Change data accuracy directly impacts production operations. Core fields must be validated via `responseData` to prevent risks like mixed version usage.

## How to Configure the Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Fill in using the Bearer token format generated by the connected system | Adapt to unified authentication requirements of external systems such as PLM and ERP |
| Request timeout | 600 seconds | Longer processing cycles are needed to handle large BOM files, process validation reports, and other documents |
| `variables` | Preset field mapping rules based on change type | Adapt to differences in field structures across documents like ECN/ECR and transition plans |
| `responseData` | Extract and validate the version, effectiveDate, and approvalStatus fields | Ensure accurate version and approval status of returned change data |
| Number of associated documents per single request | Top 5 | Avoid overloading data volume in a single request to maintain interface stability |

## Three Common Configuration Mistakes
- Issue: The `responseData` returned by the interface includes an empty version field. Cause: No mapping rule for the version field was configured in `variables`, so version information from the external system was not correctly extracted.
- Issue: Mixed old and new version materials are found in batch production. Cause: Change effective dates were not validated via `responseData`, so the latest process document version was not synchronized to production systems in a timely manner.
- Issue: The interface call returns a 504 timeout status code. Cause: The request timeout configuration was not adjusted to an appropriate duration, so parsing and synchronization of large BOM files could not be completed.

## How to Verify a Complete Configuration
- Use the interface debugging tool included in FastGPT v4.17.0 to call the test interface. Verify that the `Authorization` parameter successfully passes external system authentication and returns valid data.
- Submit a change request containing a large BOM file. Confirm that the interface response duration does not exceed the preset 600-second threshold.
- Review the `responseData` returned results. Confirm that core fields including version and effectiveDate have been correctly extracted and validated.
- Trigger a change synchronization action. Confirm that the number of associated documents returned by the external system aligns with the preset top 5 limit.

The values listed above are common starting points and should be evaluated against the reader’s own samples.
