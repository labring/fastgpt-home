# Cross-Review of Technical Documents for Process Changes and Engineering Changes: Multi-Turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Data for this category comes from PLM, ERP, MES, supplier materials, validation test records, and customer special requirement documents. Updates occur irregularly each time a change is triggered. Core documents include ECN/ECR forms, change assessment reports, drawings and BOM version records, process validation reports, production switching plans, inventory disposal documents, and customer approval documents. Data fields include change number, version number, effective node, associated material code, inspection standard number, and others. The number of documents updated in a single batch has no fixed standard, and fluctuates with the complexity of the change.

## Constraints for Multi-Turn Dialogue and Prompt Engineering
Data for this category is scattered across multiple systems, has diverse types, and updates on an irregular schedule. This creates multiple constraints for multi-turn dialogue and prompt engineering configurations. First, multi-turn dialogue must pull associated documents across PLM, ERP, and other systems. Prompts must clearly specify retrieval priority and format for different data sources. Second, field logic varies significantly across different documents. Prompts must first identify the current document type under review, then match the corresponding validation rules. Third, dialogue context during the change cycle must be fully retained. `chatId` must be bound to the full-link dialogue of a single change batch to avoid context confusion across changes. Finally, validation results must clearly output identification of chain impacts on design, materials, processes, and inspections to prevent missing potential risks.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique identifier of the current change batch | Isolate dialogue contexts for different change batches to avoid information interference across changes |
| `messages` | Retain the most recent 12 turns of dialogue + core document metadata for the current change | Cover the full dialogue chain of the change review cycle, retain historical validation nodes and current document information |
| `variables` | Preset change type, associated system list, and validation rule templates | Quickly adapt review logic for different change scenarios, reduce repeated prompt engineering writing |
| Maximum single-dialogue wait time | 600 seconds | Pulling documents across multiple systems takes a long time, so sufficient response time must be reserved |
| Context window upper limit | 8000–12000 token | Accommodate the full content of multiple ECN, BOM version records, and validation reports; adjust the range based on actual measurements |

This configuration is based on the functional logic of FastGPT v4.17.0.

## Three Common Misconfigurations
- A call to an associated MySQL database tool returns a 400 status code with no response body. The cause is that required database connection parameters are not configured in `variables`, leading to missing necessary context information during tool calls.
- It is not possible to switch models within the current AI dialogue interface during a conversation. The cause is that model switching logic is not bound to the context management node of `messages`, so model change configuration cannot be triggered within the dialogue chain.
- It is not possible to clear dialogue records for a specified batch after local deployment. The cause is that the session chain of a single change batch is not bound via `chatId`, leading to batch clear operations accidentally deleting review data for other changes.

## How to Verify Proper Configuration
- Initiate a simulated change review dialogue, check that `chatId` remains consistent throughout the dialogue and does not automatically change with new change requests.
- Call the preset database tool, check that associated BOM version records can be pulled normally, and verify that tool call parameter configurations are effective.
- Attempt to switch models during the dialogue, check that model changes can be triggered within the context scope of `messages`, and that responses from the new model conform to preset validation rules.
- Execute a dialogue record clear operation, check that only the session bound to the current `chatId` is cleared, and that review records for other changes are not affected.

The values provided are common starting points and should be measured against the reader's own samples.
