# Cross-Review of Technical Documents for Process Change and Engineering Change: Tool Calling and Plugins

## What data for this category looks like
This data is generated and used by manufacturing enterprise change management teams. Daily documents include ECN/ECR forms, change assessment reports, drawings and BOM version records, process validation reports, production switch plans, inventory disposal documents, and customer approval files. Data is sourced from PLM, ERP, MES systems, supplier materials, validation test records, and customer-specific requirements. Updates are triggered irregularly with each change. Documents include fields such as version number, effective time, associated bill of materials, and validation conclusions. There is no unified fixed unit, and values adjust based on document type.

## Constraints imposed by these characteristics on tool calling and plugins
This category of data has scattered sources and close associations. Tool calling must support pulling data across multiple systems such as PLM, ERP, and MES. It must adapt to field format differences across different systems to avoid data parsing errors. Change triggers have no fixed cycle. Tools must support on-demand calling to adapt to temporary change requirements. Documents include key fields such as version number, effective time, and associated bill of materials. Tools must accurately match field names to correctly identify old and new versions. Errors directly impact production and compliance. Tool calling must add a pre-validation step to ensure returned data covers necessary content such as validation conclusions and customer approval files.

## How to set up configurations
This page is based on FastGPT v4.17.0 configuration guidelines.

| Configuration Item | Recommended Setting | Rationale for This Setting |
| --- | --- | --- |
| Workflow/API tool selection | `auto` | Adapts to dynamic tool calling needs in change scenarios, no manual tool specification required |
| Tool call timeout | `300–600 seconds` | Requires pulling data across multiple systems such as PLM and ERP, which takes a long time. Reasonable range determined by actual testing |
| Plugin input context length | `800–1200 characters` | Adapts to typical content length of change documents, avoids truncating key information such as version numbers and effective times |
| Number of plugin return results | `Top 3–5 entries` | Must cover multiple types of documents associated with changes such as drawings, processes, and materials, avoids redundant or missing content |
| Workflow/API function-call configuration | `enabled` | Allows tools to directly call external system interfaces to complete data pulling and validation |
| Plugin memory limit | `1024 MB` | Adapts to resource requirements for running Python plugins, avoids call failures due to insufficient memory |
| Plugin trigger condition | Match against change document keywords | Trigger tool calling only when keywords such as ECN/ECR and version number are detected, reduces invalid calls |

## Three common misconfigurations
- Symptom: After the application is called, viewing details shows only generalized results with no internal tool execution logs. Cause: The detailed logging switch for tool calling was not enabled, making it impossible to track specific steps of cross-system data pulling.
- Symptom: The chatId cannot be passed across sessions during API calls, resulting in lost tool calling context. Cause: The chatId field was not correctly included in API request parameters, and session persistence parameters were not configured.
- Symptom: A custom Python plugin fails to call after deployment, returning incorrect parameter formats. Cause: Input and output fields were not encapsulated according to plugin template specifications, and requirements for specific fields in change documents were not adapted.

## How to confirm the configuration is correct
- Submit a simulated change request, check if the tool automatically triggers the corresponding plugin call, and confirm that the `toolChoice` configuration takes effect.
- View tool calling logs, verify that returned data includes key fields such as ECN numbers and version numbers, and confirm that the input context length configuration is reasonable.
- Run a cross-system data pulling test, confirm that the number of plugin return results falls within the preset range, with no redundant or missing content.
- Test API calls with the chatId parameter included, confirm that session context is correctly retained, and that tool calling can continue the previous change workflow.

These values serve as common starting points, and should be validated against local deployment samples.
