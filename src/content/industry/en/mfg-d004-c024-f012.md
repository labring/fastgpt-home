# Cross-Review of Technical Documents for Process Changes and Engineering Changes: Deployment and Upgrade

## What Data for This Category Looks Like
Data for this category originates from PLM, ERP, MES, supplier materials, validation tests, and customer-specific requirements. Updates occur irregularly with each process or engineering change. Daily documents include ECN/ECR forms, change assessment reports, drawings and BOM version files, process validation reports, production switching plans, inventory disposal documents, and customer approval documents. Document fields include version number, effective time, associated material code, validation result, and customer approval status. No unified fixed units exist. Values adjust per the field rules of the corresponding business documents.

## Constraints Imposed by These Characteristics During Deployment and Upgrade
Data sources are scattered, and formats are inconsistent. During deployment, implement support for connecting to multiple heterogeneous system interfaces. Do not use hardcoding to adapt to a single data source. This reduces adaptation costs for subsequent system iterations. Change triggers follow no fixed cycle. During deployment, implement support for incremental synchronization instead of full data pulls. This reduces server resource usage. Documents include structured forms and unstructured drawings and reports. Implement adaptation for storage and parsing logic for multiple file types. After a change, synchronize file versions across multiple systems. During the upgrade phase, ensure the version consistency check mechanism remains operational. This avoids the risk of mixing old and new versions. Customer approval documents involve compliance requirements. During deployment, retain complete audit logs. During upgrades, do not lose historical approval records.

## Configuration Guidelines
This configuration rule applies to FastGPT v4.17.0. Specific configuration items and their rationales are listed below:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://admin:securepass@mongodb-host:27017/fastgpt_ecn?authSource=admin` | Stores structured change data such as ECN/ECR forms and BOM versions. Specifies an authentication source and dedicated database to isolate business data |
| `REDIS_URL` | `redis://:redispass@redis-host:6379/1` | Caches frequently accessed data such as change validation reports and customer approval status. Sets maximum connections to 120 to adapt to multi-system synchronization requests |
| `STORAGE_S3_ENDPOINT` | `https://s3-cn-beijing.aliyuncs.com` | Stores unstructured files such as drawings and process validation reports. Adapts to the access address of the enterprise’s existing object storage service |
| `ROOT_KEY` | Random 32-character string | Acts as the system’s core authentication key. Avoids hardcoding to prevent leaks, and ensures access security for change data |
| `DB_MAX_LINK` | `50` | Limits the number of concurrent database connections. Prevents database overload from multi-system synchronization requests |
| `FE_DOMAIN` | `https://your-company-fastgpt-domain.com` | Configures the frontend access domain name. Ensures correctness of change document previews and approval links |

## Three Common Configuration Errors
- Symptom: Knowledge base search results mix old BOM versions and new process documents. Cause: No version number filtering rule is configured. Valid documents are not filtered by change effective time during data synchronization.
- Symptom: The upgrade script returns a 401 status code. Cause: The `ROOT_KEY` environment variable is not replaced correctly. Authentication failure prevents the upgrade process from triggering.
- Symptom: Change document fields are empty after synchronization, making cross-review impossible. Cause: Custom field mapping for the PLM system is not adapted, leading to loss of key fields such as associated material code and customer approval status.

## How to Confirm Successful Configuration
Execute the preset upgrade script. Verify the return result contains no 401 or 500 status codes. Confirm the `ROOT_KEY` configuration meets requirements.
Manually trigger a change synchronization task from the PLM system. Check that the version numbers of new change documents in the knowledge base match the content returned by the source system.
Submit a technical document cross-review request. Confirm that search results only include currently effective versions of ECNs, process reports, and BOM files.
View the enterprise object storage console. Confirm that unstructured files such as drawings and validation reports have been stored per the configured path.
