# Cross-Review of Technical Documentation for Production Planning and Shop Scheduling: HTTP Interfaces and External Systems
This document applies to FastGPT v4.17.0.

## What this category of data looks like
Data for this category mainly comes from ERP orders and inventory, BOM, process routes, equipment capacity, staff shifts, work in progress, and supplier deliveries. Daily processed documents include sales orders, master production schedules, material requirements plans, weekly and daily scheduling sheets, work orders, material shortage lists, and delivery change notices. Data update rhythms are divided into daily, weekly, or triggered by orders or abnormal situations. The data structure revolves around order decomposition, resource constraints, and delivery commitments, and includes fields such as order number, material code, process duration, equipment load, and staff scheduling. Units include pieces, hours, sets, and others.

## What constraints do these characteristics impose on the "HTTP Interfaces and External Systems" link
Data sources for this category are scattered and update rhythms are inconsistent. This requires HTTP interfaces to support both on-demand pull and real-time push modes to adapt to sudden order and abnormal data updates. Diverse daily document types require interfaces to support multi-format parameter passing, and preset general field templates to adapt to different document structures. Data fields contain multi-dimensional production-related information, so clear parameter mapping rules are needed to ensure consistency of field units and meanings during cross-system transmission. Since errors in this category directly affect production rhythm, interfaces must have complete error capture, retry mechanisms, and status feedback capabilities to avoid scheduling interruptions or delivery delays caused by interface abnormalities. In addition, frequent order insertion and rescheduling scenarios require interfaces to have low-latency response capabilities to meet real-time scheduling adjustment needs.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {enterprise-specific API key}` | Complies with standard authentication formats, ensures interface access security, and adapts to authentication rules of most ERP systems |
| `variables` | `{"order_source": "ERP", "update_cycle": "daily"}` | Passes category-specific data source identification and update cycle parameters, enabling the interface to adapt to scheduling data processing logic |
| `responseData` | `Return only work order ID, scheduling priority, estimated completion time` | Filters redundant data, reduces interface transmission load, and adapts to core data requirements of shop scheduling systems |
| Timeout setting | `600 seconds` | This category of data processing involves multi-dimensional resource verification, requiring sufficient response time to avoid scheduling interruptions caused by timeouts |
| Retry strategy | `Retry 3 times after failure, 60-second interval` | Addresses network fluctuations or temporary unavailability of third-party systems, ensuring stability of data synchronization |

## Three Common Mistakes
- Symptom: The interface returns the `401 Unauthorized` status code. Cause: The `Authorization` parameter is not configured correctly, or an expired API key is used.
- Symptom: Scheduling data fields are missing after calling the interface. Cause: The category-specific data source identification is not passed through the `variables` parameter, causing the interface to fail to match the correct data mapping rules.
- Symptom: Unable to obtain the complete final result when receiving a stream response. Cause: The response parsing logic is not configured correctly, and the end marker of the stream is not monitored.

## How to Confirm Configuration is Complete
- Call the test interface, check if the `Authorization` parameter is correctly carried in the request header, and the returned status code is `200 OK`.
- View the `responseData` return result, confirm that it includes core data fields of this category, such as work order number, equipment load, estimated completion time.
- Simulate order changes to trigger data updates, check if the interface can pull the latest scheduling data according to the configured update cycle.
- Test stream calls, confirm that all returned fragments can be fully received and spliced to obtain the final result.
