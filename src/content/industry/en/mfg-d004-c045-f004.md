# Cross-review of Technical Documents for Spinning and Weaving: Workflow Orchestration

## What data for this category looks like
Data for this category mainly comes from raw fiber inspection reports, ERP production systems, real-time collected data from spinning and looms, and outputs from devices such as evenness testers and fabric inspectors. Daily documents include cotton blending or ingredient lists, process setup sheets, equipment operation records, yarn inspection sheets, gray fabric inspection sheets, and defect ledgers.
Data update rhythm adjusts synchronously with each batch of raw materials, each shift’s production, and each piece of fabric output. Document fields include fiber grade, yarn twist, loom speed, defect code, and more. Corresponding units include tex, revolutions per minute, grams per square meter, and more.

## What constraints these characteristics impose on the "workflow orchestration" link
Since data updates frequently with each batch, shift, and piece of fabric, workflows must support execution triggered by new document uploads or scheduled triggers. Category documents have many closely related fields, so `variables` must be used to extract key parameters for cross-checking.
Format differences exist between device-collected data and manually filled documents. Workflows must configure format conversion nodes to unify data structures.
A single production batch is associated with multiple document types. Tool calls must be orchestrated in production node order to avoid mixing data across batches.
Correlation checks between defect records and process parameters require fixed logic that cannot be covered by general rules.

## How to set the configuration
This page’s configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `nodeId` | Bind the unique document storage node ID for the category | Accurately trigger the verification process for spinning and weaving documents |
| `variables` | Preset field mappings for fiber, process, and inspection data by document type | Adapt to the fixed parameter structure of cotton blending sheets and process sheets |
| Tool call order | Execute in the order of ingredient preparation → setup → inspection | Align with the production logic of spinning and weaving |
| Timeout setting | 600 seconds | Accommodate the reading and verification duration of multiple documents |
| Retry mechanism | Retry 2 times after failure, with a 60-second interval | Address temporary transmission exceptions for device data |
| Single-match upper limit | Top 8 recall results | Cover the number of associated documents for a single production batch |
| Context window | Maximum 2000 tokens | Accommodate the associated content of multiple documents for a single batch |

## Three common errors
- Phenomenon: Multi-line text output configured in the workflow only displays single-line content. Cause: The multi-line text parsing setting for `variables` is not enabled, and line breaks are automatically filtered.
- Phenomenon: The problem classification node takes longer than expected. Cause: The single-match upper limit is set too high, and pre-screening is not performed for category documents, leading to a large number of irrelevant documents participating in matching.
- Phenomenon: Tools do not execute in the preset order, and some tools are not triggered. Cause: No pre-node dependencies are configured via `nodeId`, and no specification is made that the current tool must wait for the previous node to complete before starting.

## How to confirm the configuration is correct
- Upload a combined document of a cotton blending sheet and a process setup sheet, check whether the workflow automatically triggers execution.
- View the workflow run log, confirm that tools start in the order of ingredient preparation → setup → inspection.
- Extract the `variables` field, verify that the extracted fiber grade and yarn twist parameters match the original document.
- Simulate a tool call failure scenario, confirm that the workflow triggers the retry mechanism, and the retry interval matches the preset settings.

The values provided are common starting points and should be measured against the reader's own samples.
