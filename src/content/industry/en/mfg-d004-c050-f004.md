# Cross-Review of Technical Documentation for General Mechanical Equipment Assembly: Workflow Orchestration

## What the Data for This Category Looks Like
Technical documentation data for general mechanical equipment assembly comes from PLM/ERP systems, part inspection data, assembly tool collection records, test bench data, MES systems, and customer technical agreements. Data updates follow the cadence of single equipment or per order. Covered documents include assembly process cards, multi-level BOMs, torque records, clearance adjustment records, commissioning reports, factory inspection sheets, packing lists, and more. Document fields include material codes, assembly torque values (unit N·m), coaxiality clearance values (unit mm), operator numbers, assembly completion times, and others. Some documents require association with cross-system component traceability information.

## Constraints on Workflow Orchestration
The multi-order, single-unit customization nature of this category requires workflows to dynamically pull corresponding documents by order or equipment ID. This prevents data mixing across orders.
Multi-level BOMs and scattered assembly and inspection data sources require workflows to include cross-system data pulling nodes. These nodes integrate scattered torque, clearance records, and BOM lists.
The document update frequency for single equipment requires workflows to support real-time verification of document version consistency. This prevents use of expired assembly process or inspection data.
Differences in document field units (such as torque N·m and clearance mm) require workflows to include unified unit conversion nodes. This avoids numerical comparison errors during cross-review.

## Recommended Configuration Settings
This document uses the workflow orchestration function of FastGPT v4.17.0. The following are configuration references for this scenario:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `variables` | Bind equipment ID as the scope, retain for 7200 seconds after the session ends | Isolate exclusive document data for a single piece of equipment, avoid data mixing across sessions |
| `nodeId` | Assign a unique identifier to cross-system data pulling nodes, associate with the corresponding BOM data source | Ensure document pulling for different orders points to the correct system interface, avoid incorrect API calls |
| Global variable persistence rules | Only retain during the current session cycle, archive to specified storage as needed | Adapt to temporary verification needs for single equipment, prevent redundant data from consuming resources |
| Parameter completion trigger condition | Trigger one question-and-answer completion when missing verification fields are detected | Adapt to scattered field verification scenarios in technical document cross-review |
| Node timeout period | 600 seconds | Adapt to network latency when pulling PLM and MES data across systems, avoid task interruption |
| Context window size | First 8 historical interaction records | Adapt to multi-field verification scenarios for assembly documents, avoid context overload |

## Three Common Configuration Mistakes
- Loss of global variable values after session restart: The phenomenon is that previously set `variables` values such as equipment ID and BOM version appear empty when re-entering the session. The cause is that the scope binding rule for `variables` is not configured. The default retention period is only the current single session cycle.
- Failure to automatically complete multiple parameters: The phenomenon is that when the workflow calls cross-system tools, a prompt indicates that required fields such as torque value and clearance value are missing. Automatic supplementation via question and answer is not possible. The cause is that the parameter completion trigger condition is not configured, and verification rules for missing fields are not associated.
- Inconsistent results between debugging and actual testing: The phenomenon is that parameters work normally during local workflow debugging, but the number of returned documents does not match during front-end testing. The cause is that the equipment ID association rule for `nodeId` is not bound. The default data source used during debugging does not match the actual data source of online orders.

## How to Verify Correct Configuration
- Manually set the equipment ID for `variables`, restart the session, and check if the variables are retained. Confirm that the scope configuration takes effect.
- Intentionally delete a required field in the document, trigger the workflow's question-and-answer completion link, and confirm whether a parameter supplement prompt pops up.
- Copy the equipment ID of an online order, call the cross-system data pulling node, and compare the document return results from local debugging and online testing. Confirm that the data source associated with `nodeId` is correct.
- Wait 600 seconds and check the node task status. Confirm that no timeout error occurs, to verify that the node timeout period configuration is reasonable.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
