# Bid Document and Quotation Preparation for Warehousing, Lot Tracking, and In-Plant Logistics: Deployment and Upgrade

## What this category’s data looks like
Core data for this category comes from multiple sources: ERP/WMS systems, barcode or RFID collection devices, purchase work orders, warehouse location ledgers, AGV transport systems, and weighing equipment.
Common daily generated documents include receiving slips, putaway slips, material picking and return slips, warehouse transfer slips, monthly inventory counts, lot ledgers, and first-in-first-out (FIFO) and expiration date control records.
Common data fields include material codes, lot numbers, warehouse location numbers, inspection statuses, inventory quantities, and expiration dates.
Units include pieces, kilograms, cubic meters, and other standard units.
Data update frequencies fall into three categories: real-time (such as AGV scheduling data), daily (such as material picking and return statistics), and monthly inventory (such as inventory reconciliation).

## Constraints imposed by these characteristics during deployment and upgrade
For multi-source heterogeneous data sources, deployments must configure synchronization interfaces adapted to each system. This prevents data synchronization interruptions.
Mixed real-time and batch update rhythms require upgrades to adjust cache and database concurrent connection strategies. This stops service freezes during high-concurrency scenarios.
Documents and fields have strong lot correlations. Knowledge base indexes must accurately match core fields such as lot numbers and warehouse locations. Otherwise, material matching in bid documents will deviate.
Severe error risks require deployments and upgrades to include data verification and failure retry mechanisms. This avoids issues such as wrong materials or expired materials harming bid accuracy.
For container deployment scenarios, verify correct database connection and permission configurations. This addresses common deployment configuration issues.

## How to set the configurations
This configuration guide is designed for FastGPT v4.17.0, and targets bid document and quotation preparation scenarios for warehousing, lot tracking, and in-plant logistics.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `MONGODB_URI` | Connection string containing authentication information for the ERP/WMS database | Connect to core warehousing business data including lots, warehouse locations, and inventory, to ensure synchronization stability |
| `REDIS_URL` | Point to an internal enterprise cache node, set connection timeout to 300 seconds | Cache frequently queried lot ledgers and expiration date records, to reduce database concurrent pressure |
| `STORAGE_S3_ENDPOINT` | Bind to the node address of the internal enterprise object storage service | Store document attachments required for bids such as receiving slips and inventory counts, to enable unified management |
| `DB_MAX_LINK` | 10–15 | Adapt to concurrent connection requirements for multi-system synchronization, to avoid exhausting database resources |
| `FILE_TOKEN_KEY` | Match the key used by the internal enterprise proxy service | Adapt to the new version of the document access proxy, to avoid failure to download bid document attachments normally |
| `ROOT_KEY` | 32-bit key generated according to internal enterprise permission rules | Control the highest access permission for the knowledge base, to prevent leakage of sensitive bid data |

## Three Common Misconfigurations
-  Container startup fails to synchronize warehousing business data. Logs display connection timeout. This happens because `MONGODB_URI` is misconfigured, and the deployment node IP was not added to the ERP/WMS database’s allowed access whitelist.
-  Batch information cannot be matched when retrieving bid-related documents. Returned results are empty or irrelevant. This happens because core fields such as lot numbers and warehouse location numbers were not specified in the knowledge base index configuration, leading to insufficient retrieval accuracy.
-  Index construction tasks continue to fail after an upgrade. Status remains stuck in the pending execution queue. This happens because the `DB_MAX_LINK` parameter was not adjusted. Concurrent connection counts exceed the database limit, leading the database to reject new connection requests.

## How to Confirm Proper Configuration
-  Run the database connection test command. Verify that `MONGODB_URI` and `REDIS_URL` configurations establish normal connections, with no timeout or authentication failure prompts.
-  Upload a standard receiving slip document. Check that `STORAGE_S3_ENDPOINT` stores the attachment normally and returns an accessible link.
-  Simulate a retrieval request that includes a lot number. Confirm that returned results include correct fields such as material codes, expiration dates, and warehouse locations, with matching levels meeting business requirements.
-  View the system permission management panel. Confirm that the permission scope configured via `ROOT_KEY` is only open to business roles related to warehousing and bids, with no unauthorized access risks.
