# Tender Document and Quotation Preparation for Basic Chemical Continuous Production: HTTP Interfaces and External Systems

## Data Profile for This Category
This category covers basic chemical continuous production entities including chlor-alkali, synthetic ammonia, methanol, and soda ash. Daily documents include operating procedures, process index cards, DCS trends, laboratory reports, interlock bypass records, special work permits, and shift reports. Data is sourced from DCS/SIS systems, online analyzers, LIMS systems, equipment condition monitoring modules, energy metering devices, and raw material tank monitoring modules. Data update frequencies fall into three categories: real-time, per-shift, and daily. Document fields include process parameter values, interlock status, laboratory results, work approval status, and more. Units use industrial standard measurements such as pressure, temperature, flow, and material concentration.

## Constraints for HTTP Interfaces and External Systems
The multi-source nature and varied update frequencies of this category of data create multiple constraints for HTTP interfaces and external systems.
Real-time DCS trends and online analyzer data require interfaces to support scheduled polling or real-time triggering, to prevent data lag that compromises tender document accuracy.
Documents such as shift reports and special work permits, generated per shift, require interfaces to support batch data pulling to align with daily tender document preparation workflows.
Calls to multiple system data sources require unified field mapping rules to match fixed formats for fields like process parameters and interlock status, avoiding parsing errors.
Highly compliant interlock record data requires interfaces to include permission verification logic to secure data calls.

## Configuration Settings
This configuration guidance is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Carry a Bearer token with a 7-day validity period | Align with security verification requirements for multi-system access, avoid frequent token refreshes |
| `variables` | Configure process parameter mapping rules covering three core fields: pressure, temperature, and liquid level | Match the core field structure of this category of data, ensure accurate data parsing |
| `responseData` | Return only verified compliant fields, filter sensitive interlock records | Comply with data security standards, prevent leakage of sensitive production information in tender documents |
| Timeout Setting | 60–120 seconds | Accommodate response delays from DCS systems, prevent request failures from network fluctuations |
| Polling Frequency | Once per shift + real-time triggering | Match the update rhythm of shift reports and real-time process data, align with tender document preparation cycles |
| Concurrent Request Count | Parallel calls for the first 3 requests | Avoid overloading target systems from excessive simultaneous requests |

## Three Common Configuration Errors
- A 500 error with logs containing `tls: failed to verify` occurs when correct TLS certificate verification rules are not configured, preventing a secure encrypted connection to the target external system.
- Missing core parameters such as liquid level and pressure in interface-returned process data is caused by failure to map this category’s fixed data fields in the `variables` configuration, leading to incomplete parsing.
- Insufficient returned results during batch data pulling happens when an unreasonable concurrent request count is set, exceeding the interface call limit of the target system.

## How to Verify Successful Configuration
- Initiate a single test request, confirm that returned `responseData` includes preset process parameter fields to verify field mapping rules are active.
- Simulate a scheduled polling request, validate that interface response content across different update rhythms matches the generation cycle of shift reports and real-time data.
- Call the interface to retrieve interlock record data, check that sensitive content is filtered to confirm permission verification logic functions correctly.
- Simulate concurrent requests from multiple systems, observe interface response status to confirm no overload errors occur.
