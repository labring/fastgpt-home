# Bid Document and Quotation Preparation for Process Changes and Engineering Changes: HTTP Interfaces and External Systems

## What this type of data looks like
This type of data is generated by manufacturing enterprise change management teams. Core documents include ECN/ECR, change assessment forms, drawings and BOM versions, process verification reports, transition plans, inventory disposal documents, and customer approval documents. Data sources cover PLM, ERP, MES systems, supplier materials, verification test results, and customer special requirements. Updates are triggered irregularly with each process or engineering change, with no fixed cycle. Data fields include change number, version number, effective time, impact scope, approval status, etc. There are no unified fixed units, and they adjust with associated business documents.

## What constraints these characteristics impose on HTTP interfaces and external systems
Data sources are scattered and linked to multiple business systems. Interfaces must support pulling change-related documents in different formats across systems. Changes are triggered without a fixed cycle. Interfaces must support on-demand calls without relying on scheduled pulls. Documents include large files such as drawings and BOMs. Interfaces must support segmented transmission or large file uploads. Each change’s data is linked to multiple approval nodes. Interfaces must carry complete approval status and associated file IDs. Change data has clear version attributes. Interfaces must support filtering request parameters by version number.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Carry a fixed API key assigned by the external system | Complies with external interface authentication specifications and ensures secure data transmission |
| `variables` | Pass change number, version number, and effective time parameters | Accurately locate associated documents and business data for a single change |
| `responseData` | Extract ECN number, approval status, and associated file ID fields | Matches core verification requirements for bid document and quotation preparation |
| Timeout setting | 600 seconds | Adapts to large file pull delays from systems such as PLM and ERP |
| Retry count | First 3 attempts | Addresses interface call failures caused by temporary network fluctuations |
| Request header configuration | Declare `application/json` and `multipart/form-data` | Supports transmission of text data and binary files such as drawings |

## Three common misconfigurations
- An interface call returns a 401 Unauthorized error, and the interface displays authentication failure. The cause is that no authentication parameter for the `Authorization` header is configured in the request, and it does not match the external system’s interface verification rules.
- An interface call returns an empty `responseData` field, and no change-related data is obtained. The cause is that the change number or version number parameter in `variables` is not passed, so the external system cannot locate the target change document.
- An interface call times out, and the log shows that the request duration exceeds the threshold. The cause is that no reasonable timeout time is configured, and it does not adapt to the large file pull delay of the PLM system.

## How to confirm the configuration is complete
- On the interface debugging page of FastGPT v4.17.0, enter a test change number and initiate a call.
- Check whether the `responseData` field in the returned result includes core business fields such as ECN number and approval status.
- View the interface call log to confirm that the `Authorization` header correctly carries authentication information, and there are no 401 or 404 level errors.
- Test a request that includes drawing attachments, and confirm that there are no format errors or timeout prompts for file transmission.
