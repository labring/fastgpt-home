# Bid Document and Quotation Preparation for Process Change and Engineering Change: Model Integration and Configuration

## What This Category of Data Looks Like
This category of data is generated and maintained by manufacturing enterprise change management teams. Core documents include ECN/ECR forms, change assessment reports, drawings and BOM version records, process validation reports, production switching plans, inventory disposal documents, and customer approval documents. Data sources cover PLM, ERP, MES systems, supplier materials, validation test records, and customer-specific requirements. Updates are triggered irregularly with each change, with no fixed cycle. Document fields include change number, version number, impact scope, validation status, and other items. Some drawing-type documents include engineering unit fields such as dimensions and tolerances.

## Constraints Imposed on Model Integration and Configuration
This category’s data characteristics impose multiple constraints on model integration and configuration. Multi-source heterogeneous data sources require configuration of adaptive logic compatible with multi-system data pulling to avoid parsing format errors. Irregular update rhythms require support for dynamically triggered model calls to avoid using expired change data. Documents include engineering drawings, numerical fields, and version identifiers, so model capabilities supporting multi-modal parsing and accurate field extraction must be configured. Highly correlated change data requires limiting context length to prevent redundant information from interfering with key identification, while ensuring output can be bound to specific change numbers and version numbers for subsequent traceability and validation.

## How to Configure the System
The following configurations are formulated based on FastGPT v4.17.0.

| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | Adapts to the high volume and dense information of change-related documents, avoiding context overflow and loss of key change information |
| `maxTokens` | `2000–3000 token` | Controls single-round output length, ensuring bid documents and quotation content are complete and comply with engineering document format specifications |
| `quoteMaxToken` | `1500–2000 token` | Limits the length of referenced change document fragments, ensuring referenced information is precise and does not redundantly interfere with core content |
| `vision` | `enabled` | Supports parsing visual documents such as engineering drawings and BOM version diagrams, adapting to the multiple types of engineering files included in this category |
| `temperature` | `0.3–0.5` | Reduces output randomness, ensuring bid quotations and document content are rigorous and comply with engineering change specification requirements |
| `AIPROXY_API_TOKEN` | Fill in the enterprise-specific proxy key | Adapts to enterprise internal data isolation and permission control requirements, ensuring the security of model calls |

## Three Common Misconfigurations
- Phenomenon: Single-round model call times out, with response duration exceeding 10 seconds. Cause: The `maxContext` parameter is not set reasonably, and excessive redundant historical change data is introduced, leading to excessive model inference load.
- Phenomenon: Testing fails when accessing multi-modal embedding models, returning an Invalid error. Cause: The `vision` configuration item is not enabled, or the interface format of the multi-modal model is not correctly adapted, leading to failure in parsing drawing-type documents.
- Phenomenon: New and old versions of process documents are mixed in the output bid document. Cause: The reference document version range is not limited through configuration, or the change number and version number fields are not bound, leading to the model being unable to distinguish between new and old version data.

## How to Confirm Successful Configuration
- Initiate a test call containing ECN forms, engineering drawings, and BOM data, and verify whether the output content is associated with the corresponding change number. Verification rules must be determined in combination with the field specifications of the applicable change management system.
- View the model call log to confirm that the single-round response duration meets the requirements of the business scenario. The threshold must be calibrated according to internal process response standards.
- Upload engineering drawing-type documents to verify whether the model can correctly parse visual content. Verification logic must be determined in combination with the format requirements of the applicable documents.
- Check the validity of proxy-related configuration items, and confirm that identity verification and interface connectivity are normal through the return status of a single test call.

The values provided are common starting points and should be measured against deployment-specific samples.
