# Bid Documentation and Quotation Preparation for Process and Engineering Changes: Deployment and Upgrade

## What the data for this category looks like
The data for this category is generated by a change management team made up of R&D, process, quality, production, and procurement personnel from manufacturing enterprises. Daily documents include ECN/ECR forms, change assessment reports, drawings and BOM version files, process verification reports, old and new version switching plans, inventory disposal documents, and customer approval documents. Data sources include PLM, ERP, MES systems, supplier materials, verification test records, and customer special requirements. Update frequency is triggered irregularly for each process or engineering change. Data fields cover change number, version number, effective date, impact scope, approval status, and other items. Units include piece, batch, date, and others.

## What constraints these characteristics impose during deployment and upgrade
Since data sources involve multi-system integration, adaptation parameters for cross-system data synchronization must be configured during deployment to avoid data format incompatibility issues between different systems. Since change triggers occur without a fixed cycle, support for dynamically loading the latest change documents is required. During upgrades, incremental data synchronization must be maintained without interruption to prevent expired data from being used for bid documentation and quotation preparation. Documents include structured forms and unstructured drawings, so indexing and retrieval for multiple file types must be supported, and sufficient storage resources must be reserved during deployment. Change data involves complex chain impacts, so the accuracy of associated data must be ensured during retrieval. During upgrades, the stability of associated retrieval logic must be verified to avoid confusion between old and new versions.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | 20–30 entries | Adapts to the connection requirements of multi-system synchronized change data, prevents connection pool exhaustion from affecting retrieval |
| `REDIS_URL` | Local Redis instance or dedicated cache cluster | Used to cache frequently accessed change document metadata, improving retrieval speed during bid documentation generation |
| `STORAGE_S3_ENDPOINT` | Enterprise self-built object storage endpoint | Adapts to storage and fast reading of large-volume change documents such as drawings and BOM files |
| `FE_DOMAIN` | Enterprise intranet or public network access domain name | Used to configure the access path of the front-end interface, ensuring permission verification for change documents |
| Single search limit | Top 8 entries | Matches the associated retrieval scope of change documents, balances retrieval efficiency and the completeness of bid content generation |
| File storage quota | 1000 GB, calibrated via actual testing | Accommodates long-term accumulated change documents and verification reports, meeting storage requirements for multiple batches of changes |

## Three common errors
- Phenomenon: The reranker component calls the interface successfully but the retrieval result returns false. Cause: The `FILE_TOKEN_KEY` verification parameter is not configured, causing document permission verification to fail and returning invalid results.
- Phenomenon: After upgrading to FastGPT v4.17.0, the plugin editing interface always displays the "unsaved" status. Cause: The front-end cache and back-end configuration are not synchronized, and the browser cache is not cleared or the front-end configuration is not reset after the upgrade.
- Phenomenon: During private deployment, setting the custom retrieval quantity to 6 entries does not take effect. Cause: The `DB_MAX_LINK` configuration value is not adjusted, which limits the return upper limit of retrieval results.

## How to confirm the configuration is correctly set
- Perform a cross-system data synchronization test to verify that change documents from sources such as PLM and ERP can be properly loaded into the system.
- Upload an ECN document, confirm that the returned results include the associated BOM version and process verification report during retrieval, verifying that the associated retrieval logic is working properly.
- Adjust the single search limit parameter, verify that the number of returned results matches the configured value, confirming that the retrieval limit takes effect.
- Restart the service and check the connection status of `REDIS_URL`, confirming that the cache service is running normally and there is no delay in metadata retrieval.

The values provided are common starting points and should be evaluated against the reader’s own samples.
