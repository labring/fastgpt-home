# Incoming Material Inspection and Supplier Quality: Bid Documents and Quotation Preparation - HTTP Interfaces and External Systems

## What this category of data looks like
This category covers daily quality documents for IQC and SQE departments at manufacturing enterprises, including inspection specifications, sampling plans, incoming material reports, supplier audit reports, and more. Data sources include purchase orders, drawing specifications, supplier quality certificates, inspection equipment, historical quality data, and supplier portals. Updates are triggered by incoming material batches, or during monthly/quarterly supplier evaluations and irregular audits. Data fields include incoming material batch number, inspection date, number of defect items, sample size, rectification cycle, and more. There is no fixed unified format; core information must be extracted based on business scenarios.

## Constraints on HTTP interfaces and external systems from these characteristics
The data sources for this category are scattered and have inconsistent formats. This requires HTTP interfaces to support flexible pulling and format adaptation for multiple data sources. Update cycles are not fixed. The system must support on-demand trigger calls to avoid redundant data pulling. Data fields must align with the core needs of bid documents and quotations. Only content related to quality compliance and supplier capabilities should be extracted. Interface call failures may lead to bid delays or quality risks. Failure retry and authentication check mechanisms must be configured to ensure stable data acquisition.

The following configurations are developed based on FastGPT v4.17.0.
## How to set the configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {{variables.supplierApiToken}}` | Supplier portal interfaces generally use Bearer token authentication, which matches the authentication requirements of the category's data sources |
| Variable template | `{ "inspectBatch": "", "supplierCode": "" }` | Adapts to dynamic parameter requirements specific to the category, such as incoming material batch and supplier code |
| `responseData` | `Only retain the number of qualified inspections, list of non-conforming items, and rectification time limit` | Filter redundant data not required for bids, focus on core quality information for quotations and documents |
| Request timeout threshold | 30 seconds | Incoming material inspection data has a small volume; timeouts will delay the preparation of bid documents |
| Request retry count | 2 times | Offset the impact of temporary network fluctuations or brief interface unavailability |
| Data source protocol | RESTful API | Matches the common interface protocols of inspection equipment, supplier portals, and other systems |

## Three common mistakes
-  Interface returns empty fields, only returns database connection structure. Cause: `responseData` extraction rules are not configured correctly, and the connection metadata of the data source is mistakenly used as return content.
-  Automatic inclusion of extra Bearer tokens when calling the interface, resulting in 401 authentication failure. Cause: The platform's default automatic Bearer token supplement logic is not disabled, which conflicts with the custom authentication configuration.
-  Unable to pass different tokens to call external interfaces; all requests use a fixed token. Cause: Dynamic parameter templates are not configured via `variables`, so token values cannot be dynamically replaced.

## How to confirm the configuration is correct
-  Trigger an interface call, check if the returned results only include fields required for bids such as the number of qualified inspections and list of non-conforming items, to verify that the `responseData` configuration is effective.
-  Pass different supplier token values, call the interface to confirm authentication succeeds, to verify that the dynamic parameters configured via `variables` are effective.
-  Simulate network fluctuations, observe whether the interface automatically retries, to verify that the request retry count configuration is effective.
-  Check if the interface response time meets the preset threshold, to verify that the request timeout threshold configuration is effective.

The values provided are common starting points and should be measured against the reader's own samples.
