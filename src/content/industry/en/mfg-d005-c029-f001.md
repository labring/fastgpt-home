# Bid Document and Quotation Preparation for Mold Design and Manufacturing: HTTP Interfaces and External Systems

## What the data for this category looks like
Daily documents for this category include mold design task sheets, DFM reports, part drawings, processing technology cards, trial mold reports, mold modification notices, and mold records. Data sources include customer product models, mold flow or forming simulation results, CAD/CAM output files, machining and measurement data, and trial mold sample records. Data updates are triggered as individual mold projects progress. New records are generated after each trial mold or mold modification operation. Data fields include mold model, cavity count, machining tolerance, material grade, trial mold defect type, and more. Some data exists as structured parameters, while others are stored as unstructured documents.

## What constraints these characteristics impose on HTTP interfaces and external systems
Data sources for mold design and manufacturing scenarios are scattered across multiple independent tools such as CAD/CAM software, simulation tools, and trial mold management systems. HTTP interfaces must support pulling multi-format data across systems, including structured parameters and unstructured documents. Data updates are only triggered as individual mold projects progress, with no fixed cycle. Interfaces must support on-demand calls to adapt to project-driven update rhythms. Bid document and quotation preparation requires precise matching of exclusive parameters for mold projects. The fields returned by the interface must cover content required for quotations such as material costs, processing man-hours, and tolerance requirements. Otherwise, accurate bid documents cannot be generated. In addition, mold project documents have large volumes. Interfaces must support batch data transmission to avoid single request timeouts.

## How to configure the settings
| Configuration Item | Recommended Practice | Rationale |
| --- | --- | --- |
| `Authorization` | Use a project-specific key prefixed with Bearer, valid for 30 days | Complies with external system interface authentication specifications, prevents abuse if the key is leaked |
| `variables` | Bind three core fields: mold project ID, material grade, and machining tolerance | Adapts to the quotation preparation data requirements of mold design and manufacturing scenarios, ensuring accurate business parameters are passed during interface calls |
| `responseData` | Only return three types of fields: quotation details, bid document template placeholders, and trial mold risk prompts | Reduces invalid data transmission and improves interface response speed |
| Single request timeout | 600 seconds | Adapts to the time required for mold data parsing and simulation result pulling, prevents request interruptions due to large data volumes |
| Single return data limit | First 10 project data entries | Controls interface return volume, adapts to pagination requirements for batch generation of bid documents |
| Sorting rule | Sort by project priority in descending order | Prioritizes display of high-priority mold project data, improving bid document preparation efficiency |

## Three common mistakes
- Incorrect configuration of the `Authorization` parameter results in the interface returning a 401 Unauthorized status code. This occurs when a project-specific key is not used or the Bearer prefix is not added, causing authentication failure.
- The interface returns an empty `responseData` field after being called. This occurs when necessary business parameters are not bound in `variables`, preventing the system from matching data for the corresponding mold project.
- Failure to troubleshoot interface error logs for an extended period makes it impossible to quickly locate the link where data synchronization failed. This occurs when automatic retention of interface call logs is not enabled, preventing traceability of request details when exceptions occur.

## How to confirm the configuration is complete
- Call the configured interface and check if the `responseData` returned includes core business fields such as mold project ID and material grade.
- Simulate a bid document generation request to confirm that the fields returned by the interface can be directly filled into preset bid templates.
- Check the FastGPT v4.17.0 system runtime logs to confirm that interface call request parameters and return results are properly recorded.
- Call the interface three consecutive times to check the consistency of returned data, confirming there are no parameter binding errors.
