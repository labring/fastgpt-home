# Production Planning and Shop Scheduling: Bid Documents and Quotation Preparation - HTTP Interfaces and External Systems

## What This Category of Data Entails
Typical data is sourced from ERP orders and inventory, bills of materials (BOM) and process routes, equipment capacity, staff shifts, work in progress, and supplier deliveries. Daily documents include sales orders, master production plans, material requirement plans, weekly and daily scheduling tables, work orders, material shortage lists, and delivery change notices.

Data update frequencies are daily, weekly, or triggered for adjustment by orders or abnormal events. Fields include order numbers, process codes, capacity units, material codes, planned delivery dates, and additional relevant fields. There is no fixed unified single-document format, and configurations are dynamically adjusted based on business scenarios.

## Constraints for HTTP Interfaces and External Systems
Data sources are scattered and update rhythms are inconsistent, so interfaces must support high-frequency real-time pulling or on-demand callback requests.

Multiple types of business documents create complex field structures, requiring interfaces to support parameter verification and flexible field extraction rules.

Scheduling data is directly linked to delivery commitments, and interface request reliability directly impacts subsequent business operations. Retry and exception alert mechanisms must therefore be configured.

Differences in authentication and response formats across external systems require interfaces to adapt to multiple access specifications.

## Configuration Guidelines
The following configurations are based on the interface setup logic of FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${custom API_KEY}` | Complies with general HTTP interface authentication specifications, and adapts to the authentication requirements of most external production systems |
| `variables` | `{"targetOrders": ["SO2024001-SO2024010"], "planCycle": "2024-06"}` | Pass precise business filtering parameters to avoid pulling redundant scheduling data |
| `responseData` | `{"code": 200, "data": {"workOrderList": [], "capacityStats": {}}, "msg": ""}` | Unify the response format of external systems to facilitate quick extraction of valid scheduling and work order data |
| Request timeout | `30 seconds` | Scheduling data pulling involves multi-dimensional resource calculations, avoiding business interruptions caused by timeout interruptions |
| Retry count | `3 times` | Respond to network fluctuations or temporary external system failures, and ensure the success rate of data pulling |
| Cross-origin allowed domains | `Only allow exclusive domains of production ERP systems` | Restrict unauthorized third-party calls, and ensure access security of production data |

## Three Common Configuration Errors
- An API request returns 404 - Resource Not Found. This occurs when the external system's interface path is incorrectly configured, or the `variables` parameter includes order numbers that do not exist in the system.
- Cross-origin interception errors appear when a third-party browser calls the API. This happens when cross-origin allowed domains are not configured or are incorrectly configured, allowing external domains not belonging to production systems to access the interface.
- Scheduling data fields referenced in the knowledge base are empty. This is caused by failing to specify the correct response extraction path via the `responseData` parameter, resulting in failure to retrieve valid business fields from the external interface return content.

## How to Confirm Successful Configuration
- Initiate a simulated request with a valid `Authorization` parameter, and verify that the return status code is 200.
- Review the interface call log to confirm that the business filtering fields in the `variables` parameter are correctly parsed and applied.
- Initiate a cross-domain request from a production system domain allowed by the configuration, and confirm that no interception errors occur.
- Extract the interface return content, and verify that the `responseData` contains expected scheduling-related fields such as work orders and capacity statistics.

The values provided are common starting points and should be validated against sample data from the target deployment.
