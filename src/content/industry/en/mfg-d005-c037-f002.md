# Bid Document and Quotation Preparation for Production Planning and Shop Scheduling: Vector Models and Indexes

## What the data for this category looks like
Data for this category comes from manufacturing enterprise ERP systems, BOM lists, process routes, equipment capacity ledgers, staff scheduling sheets, work-in-progress inventory records, and supplier arrival information. Daily generated documents include sales orders, master production schedules, material requirements plans, weekly and daily scheduling sheets, production work orders, material shortage lists, and delivery change notices. Data update cycles are usually daily, weekly, or triggered in real time when sales orders are issued, production anomalies occur, or delivery schedules change. Data fields include order numbers, material codes, process names, equipment numbers, capacity values, shift time periods, work-in-progress quantities, and more. Each document has dedicated field and unit requirements; for example, capacity is measured in units per hour, and scheduling sheets use date and time periods as units.

## Constraints on Vector Models and Indexing
Data for this category comes from multiple systems with inconsistent update cycles, so vector indexes must support incremental synchronization of multi-source data and cross-document associated retrieval to avoid performance losses from full index rebuilding. There are diverse daily document types with significant field differences, so vector chunking must adapt to the structural logic of different documents to prevent semantic matching deviations caused by mixed cross-document fields. Bid and quotation preparation needs to associate multi-dimensional information such as orders, schedules, materials, and capacity, so vector recall must cover all relevant documents to ensure the coverage and accuracy of semantic matching. At the same time, real-time data updates triggered by production anomalies require indexes to quickly respond to incremental changes to ensure the timeliness of retrieval results.

## How to Set Configurations
| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to the average paragraph length of documents such as scheduling sheets and work orders, avoiding semantic fragmentation |
| Overlap Length | 100–150 characters | Retains cross-chunk process and material association information, preventing loss of critical context after chunking |
| Similarity Threshold | 0.72–0.85 | Balances retrieval accuracy and recall range, adapting to semantic matching of multi-field mixed production data |
| Maximum Recall Count Per Query | Top 8 entries | Controls the amount of retrieved information, avoiding information overload in bid scenarios |
| `defaultToken` | 2048 | Matches the average token length of most production documents, ensuring basic semantic encoding effects |
| `maxToken` | 4096 | Supports complete semantic encoding requirements for long documents such as master production schedules |

## Three Common Configuration Mistakes
- Phenomenon: A 503 status code is returned when calling the vector model, prompting that no available embedding model exists under the current default group. Cause: The access information for the corresponding embedding model is not configured on the platform, or the model group settings are incorrect, resulting in failure to normally call the model interface.
- Phenomenon: The knowledge base indexing task remains in a running state with no progress updates. Cause: Insufficient memory resources were configured when deploying via Docker, or the chunk length was set too large, causing the indexing process to block and fail to complete data chunking and encoding.
- Phenomenon: Irrelevant material or scheduling information appears in retrieval results, with insufficient semantic matching accuracy. Cause: The similarity threshold was set too low, recalling a large amount of semantically irrelevant production data, or critical associated fields such as processes and order numbers were not retained during chunking, leading to deviations in semantic matching.

## How to Confirm Configuration Validity
This document is written based on the configuration logic of FastGPT v4.17.0. Configuration validity can be verified through the following actions:
- Check the vector model access configuration, verify that the model call interface can normally return embedding vectors, and confirm that there are no 503 or connection timeout errors.
- Manually trigger an indexing task for a small batch of production documents, check whether the indexing progress is completed within a reasonable time frame, with no persistent hanging status.
- Enter query terms related to bids, check the quantity and relevance of the retrieved results, and adjust configurations such as the similarity threshold to match business requirements.
- View indexing logs to confirm that incremental update tasks can be automatically triggered when production data changes, without requiring full index rebuilding.
