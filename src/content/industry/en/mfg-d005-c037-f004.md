# Bid Document and Quotation Preparation for Production Planning and Shop Scheduling: Workflow Orchestration

## What Data for This Category Looks Like
Data for this category comes from ERP orders and inventory, BOMs, process routes, equipment capacity, staff shifts, work in progress, and supplier deliveries. Update frequency aligns with daily business changes, including daily and weekly updates, plus immediate updates when orders are generated or exceptions occur. Daily processed documents include sales orders, master production plans, material requirement plans, weekly production schedules, work orders, material shortage lists, and delivery change notices. Fields include order numbers, material codes, process man-hours, equipment load rates, work in progress quantities, and more. Units include pieces, hours, sets, and others. FastGPT v4.17.0 supports multi-node workflow orchestration for this category of data.

## Constraints Imposed on Workflow Orchestration
Data sources span multiple business systems. Workflow configurations must pull information from different data sources across multiple nodes to avoid excessive load on a single node. Update frequencies are not fixed. Dynamic triggering must be supported to prevent fixed-cycle data pulls from producing outdated information that reduces scheduling accuracy. Documents have strong interdependencies. For example, work orders must be bound to BOMs and process routes. Workflows must pass associated fields via variables to ensure data consistency. Additionally, scheduling must handle exceptions such as emergency order additions and material shortages. Workflows must support branch orchestration to adapt to processing logic for different business branches.

## Configuration Guidelines
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| Variable binding rule | Bind multiple fields such as order number, material code, process man-hour via `variables` | This category of data is associated with multiple documents. Variables must uniformly pass associated fields to avoid data gaps |
| Node trigger timing | Bind the completion signal of the previous node via `nodeId` | Scheduling data depends on preceding work orders and bills of materials. Execution must wait for the previous node to finish pulling data to ensure data completeness |
| Retry strategy | Retry 3 times, with a 60-second interval | ERP interface calls may occasionally time out. Retries reduce failure rates and meet the real-time requirements of production data |
| Single data pull limit | Top 5 entries | Aligns with the data volume returned by ERP interfaces in a single call to avoid overloading the interface |
| Result cache threshold | 800–1200 characters | Bid documents require integration of multi-process scheduling data. Cache length adapts to document splicing and display needs |
| Result output configuration | Only retain the final quotation and scheduling description nodes | Bid documents only need to display final results. Intermediate scheduling calculation processes do not need to be exposed externally |

## Three Common Mistakes
- Symptom: The workflow node dropdown menu only shows a single variable option, making it impossible to bind multiple document fields. Cause: The multi-field binding rule for `variables` was not configured correctly, and only a single associated field was selected.
- Symptom: The current debug mode cannot be stopped when debugging a node, and the interface becomes unresponsive. Cause: No node timeout parameter was set. Long-running resource occupation causes process blocking.
- Symptom: The workflow only calls a single large model to process full scheduling and quotation data, and cannot process intermediate results step by step. Cause: Workflow nodes were not split. Scheduling calculation and quotation generation were combined into a single node, and step-by-step execution logic was not configured.

## How to Confirm Proper Configuration
- Test pulling ERP order data, and check if the bound `variables` in the workflow include multiple fields such as order number and material code.
- Simulate an emergency order addition scenario to trigger the workflow, and confirm that nodes execute in sequence according to the previous signal bound via `nodeId`, with no early or delayed operation.
- Submit test scheduling data, and confirm that the final output node only displays quotation and bid document content, with intermediate process data not exposed externally.
- Simulate an ERP interface timeout scenario, and check if the workflow automatically retries according to the configured retry count, with no direct failure occurring.

The values provided are common starting points and should be measured against the reader's own samples.
