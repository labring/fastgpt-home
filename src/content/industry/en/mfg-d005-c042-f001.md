# Tender Document and Quotation Preparation for Petroleum Refining: HTTP Interfaces and External Systems

## What the data for this category looks like
Business data for petroleum refining scenarios comes from daily documents of production operation, process, scheduling, equipment and laboratory departments. These documents include operating procedures, production plans, material balances, distillate outlet quality reports, interlock ledgers, shift handover records, and change management files. Data sources cover DCS/APC, LIMS, tank farm metering, crude oil evaluation, equipment management systems, and energy systems. Update frequencies include real-time, per-shift, and daily. Operationally, multiple continuous units are coupled through logistics and hydrogen energy networks, and raw material properties fluctuate greatly. This differs from the multi-variety batch production mode of fine chemicals.

## What constraints do these characteristics impose on the HTTP Interfaces and External Systems link?
Multi-source heterogeneous data sources mean the interface must support compatible return formats across different systems. For example, quality inspection data from LIMS and process operation data from DCS have large differences in field structures, so targeted data extraction rules must be configured. Mixed update frequencies mean the interface must adapt to different pull cycles, avoiding excessive system resource usage or missed key data. Multi-unit coupling business logic means the interface must support linked pulling of load and material balance data for multiple units, ensuring accurate data relevance in tender documents. Large fluctuations in raw material properties mean the interface must dynamically adapt to parameter ranges for different crude oils, avoiding returned data that does not meet tender requirements.

## How to Set the Configurations
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {internal enterprise API key}` | Identity verification is required when connecting to heterogeneous systems within petroleum refining enterprises to ensure compliance with data access permissions |
| `variables` | `{crude oil evaluation data, unit load data, distillate outlet quality data, knowledge base query context}` | Includes core business data required for tendering and context information for knowledge base queries |
| `responseData` | Extract material balance, distillate outlet quality report, and file collection ID fields | Refine core data required for tendering and knowledge base queries, filter redundant information |
| Maximum single data pull count | Top 10 entries | Petroleum refining business data has many entries; limiting returned entries avoids interface overload |
| Interface timeout setting | 5-10 seconds | Adapts to actual response delays of systems such as DCS and LIMS, calibrated based on actual measurements |
| Knowledge base binding configuration | Bind two target business knowledge bases | Meets the requirement of querying two knowledge bases under the same account simultaneously |

## Three Common Misconfigurations
- The OneAPI test interface fails, returning a connection timeout or 403 status code. This occurs when the correct internal enterprise system address is not configured, or the `Authorization` parameter format does not meet system verification requirements.
- Repeated HTTP requests initiate in multi-branch workflows, with total execution time exceeding expectations. This occurs when the HTTP request node is not placed in advance, and request results are not reused through `variables`, resulting in separate interface calls for each question classification branch.
- Returned knowledge base query results do not include file collection IDs. This occurs when the `responseData` extraction rule is not configured, and the file collection ID field is not specified for extraction.

## How to Verify a Successful Configuration
The following verification actions are based on FastGPT v4.17.0.
1. Call the configured HTTP interface, check whether `Authorization` verification passes, and whether the returned `responseData` includes expected petroleum refining business fields.
2. Simulate data sources with different update frequencies (real-time, per-shift, daily) to verify whether the interface can stably pull data of the corresponding cycle.
3. Test the multi-branch question classification workflow, confirm that all branches can reuse initiated HTTP request results, and avoid repeated calls.
4. Trigger interface exception scenarios, check whether the retry mechanism triggers and takes effect as configured.

The values provided here are common starting points and should be measured against the reader's own samples.
