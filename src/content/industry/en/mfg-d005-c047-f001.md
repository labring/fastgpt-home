# Tender Document and Quotation Preparation for Measuring Instruments and Laboratory Management: HTTP Interfaces and External Systems

## What the data for this category looks like
This category of data comes from daily business documents of enterprise metrology rooms and CNAS system laboratories, including gauge ledgers, calibration plans, calibration certificates, periodic inspection records, original test records, reference material ledgers, and deviation handling documents. Data sources include internal metrology management systems, external calibration institution certificates, LIMS systems, and environmental monitoring equipment. The data update rhythm is not fixed, triggered by calibration cycles, single test results, or abnormal events. Data fields include professional metrology content such as instrument unique ID, calibration validity period, measured value, measurement uncertainty, traceability chain ID, etc.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
The multi-source nature of data for this category requires interfaces to support docking with multiple external data sources such as internal metrology systems and external calibration institutions. The non-fixed update rhythm requires interfaces to support on-demand calls, adapting to the need to temporarily retrieve the latest calibration data before bidding. The professional metrology fields require that the `responseData` returned by the interface accurately matches the required items of the tender document, avoiding interference from invalid data. The high compliance of data requires the interface to carry valid authentication information to ensure that the caller has data access permissions. The serious impact of data errors requires the interface to have idempotency and retry mechanisms to avoid tender document data errors caused by failed calls.

## How to set the configuration
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {external LIMS system API key}` | Used for identity authentication when connecting to the measuring instrument management system, in compliance with external interface security specifications |
| `variables` | `{"valid_status": "valid", "doc_type": "calibration certificate"}` | Filters valid metrology document data that can be used for bidding, excluding expired or invalid records |
| `responseData` | Return instrument ID, calibration date, measurement uncertainty, traceability chain ID | Matches the core data fields of the tender document, reducing invalid data transmission volume |
| Interface timeout setting | `600 seconds` | Adapts to the response delay of external calibration institution certificate interfaces, avoiding call failures caused by network fluctuations |
| Single call data limit | `Top 10 qualifying records` | Controls the data volume returned by a single interface, adapting to the context processing limit of FastGPT v4.17.0 |

## Three common mistakes
- After calling the interface, a 401 Unauthorized status code is returned. The cause is that the `Authorization` parameter is not configured correctly, and a valid external system API key is not carried, which is consistent with common authentication configuration error logic in the community.
- The pulled calibration data lacks the measurement uncertainty field. The cause is that the core metrology fields to be returned are not specified in the `variables` parameter, or access permissions for this field are not applied for from the external system.
- No retry is triggered after the interface call times out, causing the tender document preparation to be interrupted. The cause is that the interface retry policy is not configured, and the response delay fluctuation of external calibration institution interfaces is not considered.

## How to confirm the configuration is correct
- Call the configured HTTP interface, check whether the `responseData` returned contains core fields required by the tender document such as instrument ID, calibration date, measurement uncertainty, etc.
- Enter an incorrect API key, confirm that the interface returns a 401 status code, to verify that the authentication configuration takes effect.
- Simulate short-term network delay, temporarily adjust the interface timeout setting to 5 seconds, confirm that a timeout prompt is triggered when calling the external system interface, to verify that the timeout configuration takes effect.
- Pull a batch of records that have passed the calibration validity period, confirm that such data is not included in the returned results, to verify that the filtering logic of the `variables` parameter takes effect.

The values given are common starting points and should be measured against the reader's own samples.
