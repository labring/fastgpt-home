# Bid Document and Quotation Preparation for General Mechanical Equipment Assembly: HTTP Interfaces and External Systems

## What this category of data looks like
Core data for general mechanical equipment assembly scenarios comes from PLM, ERP, parts inspection systems, assembly tool collection terminals, test benches, MES, and customer technical agreements. Daily documents include multi-level BOMs, assembly process cards, torque records, gap adjustment records, commissioning reports, factory inspection sheets, and packing lists. Fields include part numbers, torque values (unit: newton meters), coaxiality parameters (unit: millimeters), test qualification marks, and more. Data updates follow a per-device or per-order cycle, triggered each time assembly is completed or an order is confirmed.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Multiple data sources require interfaces to support field formats and permission rules from different industrial systems, to avoid missing core assembly information in bid documents due to field mapping errors. The per-device or per-order update frequency requires interface calls to be bound to order-specific trigger logic, to avoid frequent pulling of redundant data. The structure of multi-level BOMs and multi-dimensional assembly parameters requires interfaces to support nested variable passing; simple key-value pairs cannot complete data interaction alone. At the same time, the accuracy of assembly data directly affects bid compliance, so interfaces must have basic field integrity verification capabilities.

## How to set configurations

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {external system assigned API key}` | Complies with identity verification specifications for most industrial PLM/ERP systems |
| `variables` | `Custom variable set containing up to 10 levels of BOM nodes, torque thresholds, and test qualification standards` | Adapts to multi-level data transfer requirements for general mechanical equipment assembly |
| `responseData` | `Return structured quotation details and document verification results of no more than 8000 characters` | Facilitates automatic generation of standardized bid documents |
| Interface trigger rules | Triggered after order creation, with a single call interval of no less than 300 seconds | Matches the update frequency of single orders, to avoid exceeding external system call limits |
| Field mapping rules | Map native PLM/ERP field names to bid document template variables | Adapts to exclusive document field formats for assembly scenarios |
| Timeout threshold | 120 seconds | Adapts to pull delays for complex assembly test data |

## Three common mistakes
- BOM level fields returned by the interface are empty, resulting in missing part lists in bid documents. The cause is failure to correctly map BOM nested fields from the PLM system, only pulling top-level part information.
- The interface returns a 401 unauthorized error, making it impossible to pull assembly data. The cause is that the `Authorization` parameter does not carry the correct external system API key, failing identity verification.
- Frequent interface call timeouts cause the quotation preparation process to interrupt. The cause is failure to set a reasonable timeout threshold and limit repeated call times for a single order, exceeding the data pull delay limit of the external test bench.

## How to confirm the configuration is correct
- Use the FastGPT v4.17.0 interface debugging tool to initiate a test call, and check that the returned `responseData` includes core assembly fields such as BOM and torque records for the current order.
- Verify that the `Authorization` parameter can pass identity verification from the external system, with no 401 unauthorized errors.
- After triggering the interface call, confirm that the bid document template automatically fills in parameters for the corresponding assembly scenario, with no blank or incorrectly mapped fields.
- Check the interface call logs, confirm that calls are only triggered after order creation, with no repeated call records for the same order.
