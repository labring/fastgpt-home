# Bid Document and Quotation Preparation for Precast Concrete Components: Vector Models and Indexes

## What This Category of Data Looks Like
Data for precast concrete components originates from BIM detailed design files, steel and concrete batch ledgers, mold table and curing kiln operation logs, laboratory test records, and product QR code traceability systems.
Daily documents include component detailed drawings, steel cutting lists, mold inspection reports, pouring and vibration records, curing cycle records, and demolding and factory inspection sheets.
Data is updated per single component, per batch of materials, and per curing batch in a kiln. Fields include component number, steel specification and model, concrete strength grade, curing duration, demolding strength value, and more. Units include millimeters, megapascals, hours, and other standard units.

## Constraints Imposed on Vector Models and Indexes
Precast concrete component data is scattered and updated per single component, per batch of materials, and per curing batch in a kiln. This requires indexes to support incremental updates and batch import of multi-source heterogeneous data.
Component data includes mixed content such as engineering drawing text, steel specifications, and strength parameters. When a vector model splits text, it must avoid damaging key information such as steel positions and component dimensions. This prevents split fragments from losing business-related association information.
Additionally, bid quotation preparation requires rapid matching of historical data for the same project and same type of components. Index recall must be limited to the component list of the corresponding bid project to avoid irrelevant data interfering with recall results. The system must also adapt to frequently updated ledger data to maintain index real-time performance.

## Configuration Settings
This configuration is based on the interface and parameter logic of FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Documents such as precast concrete component detailed drawings and cutting lists have long lengths. Chunking must retain key information such as steel positions and component numbers to avoid breaking business logic during splitting |
| `maxToken` | 4096 token | Adapts to the input upper limit of most mainstream vector models, ensuring complete embedding of component parameters and document fragments |
| Similarity Threshold | 0.72–0.85, calibrated via actual testing | Matches the similarity between component specification parameters and historical quotation data. Avoids overly low values causing irrelevant recall or overly high values missing valid matches |
| Single Search Limit | Top 10 results | Controls the number of recall results during bid quotation preparation, preventing excessive data from interfering with manual verification |
| `defaultToken` | 1536 dimensions | Adapts to the output dimensions of mainstream vector models, ensuring recall accuracy and storage efficiency of indexes |
| Maximum Context | 60000 characters | Covers the total length of the component list and historical quotation documents for a single bid project, ensuring completeness of recalled content |

## Three Common Misconfigurations
- Symptom: Index status shows not ready, and retrieval requests cannot be initiated. Cause: Incremental index trigger rules are not configured according to the update rhythm of single components and per-batch materials. Full index loading times out due to excessive data volume.
- Symptom: Retrieval results include a large number of irrelevant component data across projects, failing to match the current bid project requirements. Cause: The index scope is not limited to the component list of the current bid project. Full table data is directly imported as the index source, and no project-level filtering configuration is applied.
- Symptom: Retrieval results cannot match the specified vector model output, or a model incompatibility prompt appears. Cause: The selected vector model is not confirmed to support the current index embedding dimensions, and vector model parameters inconsistent with the `defaultToken` value are incorrectly configured.

## How to Verify Proper Configuration
- Check the status indicator in the index management interface, confirm the status is ready, and verify that the number of documents included in the index matches the number of imported component lists.
- Enter the steel specification and strength parameters of a single component as a retrieval term, check whether the recall results include historical component data of the same type, and adjust the similarity threshold to a range that meets business requirements.
- Test incremental import of log data for a single batch of curing kilns, confirm that the index updates automatically without data loss or format errors.
- Verify that the embedding dimension of the vector model matches the `defaultToken` value in the configuration items, ensuring that embedding results meet expectations.

The values provided are common starting points and should be measured against the reader's own samples.
