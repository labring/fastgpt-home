# Inspection and Process Record Audit for SMT Mounting and Electronic Assembly: Workflow Orchestration

## What this category of data looks like
Data sources for this category include BOMs, Gerber files, coordinate files provided by customers, as well as MES systems, solder paste and component batch ledgers, mounters, SPI/AOI inspection equipment, reflow oven temperature records, and more. Daily documents include changeover sheets, stencil archives, first article confirmation forms, SPI/AOI defect reports, maintenance records, and traceability labels.
Data is updated in real time per work order and each changeover. Core fields include component part numbers, reference designators, batch numbers, inspection parameters, furnace temperature curves, and defect types. There is no unified fixed format, and data must be stored associated with the corresponding work order dimension.

## What constraints do these characteristics impose on workflow orchestration
Data sources are scattered and real-time requirements are high. The workflow must support parallel pulling from multiple data sources to avoid process timeouts caused by single-node blocking.
Frequent updates triggered by work orders and changeovers require the workflow to support dynamic variable binding to adapt to parameter verification rules for different batches.
Unified document formatting requires configuring standardized cleaning nodes to extract core verification fields and match the corresponding work order dimension.
Verification of component part numbers and reference designators relies on precise field matching. The workflow must set clear mapping rules to avoid confusion of cross-work order data.
Full-link traceability requirements require the workflow to retain execution logs for each step and associate inspection and audit results.

## How to set the configuration
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| Trigger Mode | Trigger by work order ID + changeover batch | Matches the update rhythm per work order and each changeover to avoid invalid triggers |
| Input Data Source Configuration | Use dynamic parameters defined by `variables` | Adapts to scattered device and system data sources, enabling flexible pulling of real-time work order data |
| Field Verification Rules | Match BOM part numbers with reference designator fields from SPI inspection results | Corresponds to the constraints of the core verification link to ensure accurate data matching |
| Timeout Threshold | 600 seconds | Covers the pulling and processing duration of large files such as reflow oven temperature curves and AOI reports |
| Failure Handling Node | Bind the alert node specified by `nodeId` | Timely notify the audit status of abnormal work orders to avoid process blocking |
| Result Storage | Associate with work order traceability label fields | Meets the traceability requirements of full-link audits, binding the unique identifier of the corresponding work order |

## Three common mistakes
- Phenomenon: After importing configurations from an upstream workflow, intermediate verification results do not match the upstream output. Cause: The dedicated data source for the current work order was not rebound in `variables`, and parameters from the upstream test environment were reused.
- Phenomenon: After enabling knowledge base plugin question optimization, the optimization logic still takes effect even if the configuration is turned off in the final answer node. Cause: The global question optimization switch was not turned off in the workflow's global settings, and node-level configurations did not override the global settings.
- Phenomenon: After the workflow configuration is completed, it cannot be triggered in the chat window. Cause: The workflow's trigger permission binding was not configured, or the corresponding workflow `nodeId` was not associated in the chat component.

## How to confirm the configuration is correct
- Trigger a test work order, check whether the input data source has pulled the BOM, SPI report, and temperature record of the corresponding work order, and verify that field matching is correct.
- Simulate an abnormal scenario, such as a part number mismatch, check whether the failure handling node triggers an alert, and that complete exception information is retained in the logs.
- Verify the workflow's trigger permissions, confirm that the bound business system identity can normally call the workflow interface without permission errors.
- View the workflow's link logs, confirm that the execution status and output results of each node meet expectations, with no empty fields or timeout records.

The values provided are common starting points and should be measured against the reader's own samples.
