# SMT Mounting and Electronic Assembly Inspection and Process Record Review: Knowledge Base Retrieval and Recall

## What This Category’s Data Looks Like
The core data of this category comes from the full production flow of EMS factories, consumer electronics and industrial control automotive electronics factories. Daily documents include BOM and coordinate files, line change tables, stencil and reflow oven temperature records, first article confirmation reports, SPI/AOI inspection reports, maintenance records and traceability labels. Data sources include BOM, Gerber and coordinate files delivered by customers, plus MES systems, solder paste and component batch ledgers, mounters, SPI/AOI equipment, and reflow oven temperature data. Data updates trigger in real time when work orders are created or line changes are performed. The volume of data linked to a single work order shifts dynamically based on production scale.

## Constraints for Knowledge Base Retrieval and Recall
Data for this category is scattered and updated frequently. This requires the retrieval pipeline to support real-time incremental synchronization of multi-source data and adapt to rapid production workflow changes. Document types range from structured BOM part number fields, to semi-structured SPI/AOI inspection reports, to unstructured oven temperature and line change records. This means retrieval logic must support text parsing and precise field matching across all these formats. Core business processes rely on exact checks of part numbers and reference designators. Errors can cause batch mounting of incorrect components, full machine failure, and other serious issues. Recall results must prioritize the latest data linked to the current work order to avoid interference from outdated data. The number of results returned per retrieval round must also be controlled to maintain response efficiency.

## Configuration Settings
All configurations below are based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `similarity` | `0.75–0.85` | Matches core business fields such as part numbers and reference designators, requires high accuracy; this range filters out low-relevance results |
| `limit` | `Top 8 entries` | The volume of data linked to a single work order is limited; returning too many results increases context load; 8 entries covers core matching scenarios |
| `searchMode` | `mixedRecall` | Balances precise retrieval of structured fields (part numbers, reference designators) and semantic recall of unstructured text |
| `usingReRank` | `Enabled` | Multi-source recall results need to be reordered to prioritize data associated with the current work order |
| `datasetSearchUsingExtensionQuery` | `Enabled` | Automatically expands business-related queries, such as adding associated retrieval conditions like component batches and oven temperature ranges |
| `collectionIds` | `Specify dataset IDs associated with the work order` | Only retrieve knowledge base datasets bound to the current production work order to avoid interference from irrelevant data |

## Three Common Misconfigurations
- Symptom: Single retrieval takes more than 30 seconds, with obvious result delay. Cause: Failed to limit the `collectionIds` scope, retrieved full knowledge base data across work orders, and did not use the dataset bound to the current work order for filtering.
- Symptom: Two answers bound to knowledge bases are triggered for the same question, with no way to distinguish priority. Cause: Did not configure `usingReRank` or adjust recall order by business weight, and did not limit `collectionIds` to datasets associated with the current work order.
- Symptom: A large number of low-relevance expired line change records or old oven temperature data appear in retrieval results. Cause: Incremental synchronization is not enabled or data expiration filtering rules are not set, and historical data not associated with the current work order is recalled.

## How to Verify Correct Configuration
- Run retrieval tests related to a single work order, confirm that returned result latency meets business requirements, and adjust values of `similarity` and `limit` to match response speed needs.
- Trigger test queries across two bound knowledge bases, verify that results are sorted by business priority, and confirm that `usingReRank` and `collectionIds` configurations are active.
- Upload an expired line change table dataset, confirm that it is not returned in retrieval results, and verify that incremental synchronization and data filtering rules are functioning properly.
- Check the knowledge base update log to confirm that the delay of real-time work order data synchronization to the knowledge base aligns with production rhythm.

The values provided here are common starting points and should be measured against the reader's own samples.
