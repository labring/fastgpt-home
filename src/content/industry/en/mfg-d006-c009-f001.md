# Inspection and Process Record Audit for Pharmaceutical Preparations Manufacturing: HTTP Interfaces and External Systems

## What the data for this category looks like
This category's data originates from approved formulation processes, MES systems, electronic batch records, equipment and environmental monitoring data, LIMS, and quality management systems. Daily documents include master production files, batch production records, batch packaging records, cleaning records, inspection records, deviation/CAPA/change documents, and batch release audit forms. Data is updated per production batch, each key process step, and monitoring plan. Fields include material batch numbers, process parameter values, test results, deviation descriptions, and additional relevant details. Data must be stored synchronously with production operations.

## What constraints these characteristics impose on HTTP interfaces and external systems
The multi-source data requirement for this category means interfaces must support integration with multiple external systems such as MES, LIMS, and quality management systems, and must adapt to the authentication rules of different systems. Data is updated in real time according to production batches and key steps. Interface calls must match production pace to avoid data disconnection caused by delays. Under GMP compliance requirements, all fields transmitted via interfaces must fully correspond to batch record requirements. Missing parameters or format errors will directly affect the batch release audit process. Interfaces must strictly verify the completeness and format compliance of incoming and returned fields.

## How to set configurations
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Use an authenticated Bearer token with a 15-minute validity period | Adapt to the authentication rules of external quality management systems and avoid unauthorized access to data |
| `variables` | Pass core fields such as material batch numbers and process step IDs | Match the precise data range required for batch record audits |
| `responseData` | Only return three types of fields: batch production records, test results, and deviation records | Reduce invalid data transmission and comply with data storage requirements under GMP |
| Interface timeout period | 30–60 seconds | Adapt to the time required for multi-system data aggregation and avoid interrupting the audit process due to timeout |
| Retry strategy | Retry 2 times after failure, with a 5-second interval | Respond to temporary network fluctuations and ensure the stability of data acquisition |

## Three common mistakes
- A `400 InternalError.Algo.InvalidParameter` error occurs, prompting that the tool call parameters are invalid. The cause is failing to pass complete material batch numbers and process parameter fields in accordance with batch record requirements, which does not comply with interface verification rules.
- A MySQL connection error occurs, and test data from the LIMS system cannot be obtained. The cause is that the database connection parameters configured for the interface do not align with the port and permission settings of the external system.
- The interface call returns an empty result, and no production data for the corresponding batch is obtained. The cause is failing to pass the correct batch number parameter in `variables`, causing the interface to fail to match the corresponding data.

## How to confirm the configuration is complete
- Based on FastGPT v4.17.0, call the test interface, pass the `variables` parameter with a known valid batch number, and check if the returned `responseData` includes required fields such as batch production records and test results.
- View the interface authentication log to confirm that the `Authorization` token is carried correctly and has not expired.
- Simulate data upload for a single production step, and check if the external system normally receives and stores the corresponding data.
- Trigger an interface timeout scenario, and confirm that the system will automatically retry and restore the connection according to the configured retry strategy.
