# Inspection and Process Record Audit for Active Pharmaceutical Ingredient and Pharmaceutical Intermediate Manufacturing: HTTP Interfaces and External Systems

## What this category of data looks like
Data comes from registered process documents, raw material batch ledgers, DCS production control systems, weighing systems, LIMS laboratory information management systems, chromatography data systems, and QMS quality management systems. Updates occur per production batch and per process step. Core documents include batch production records, material balance sheets, reaction and purification logs, cleaning validation records, impurity profile reports, and deviation and change application documents. Data fields include batch numbers, process step serial numbers, reaction temperatures, yield ratios, impurity contents, solvent residue levels, change approval statuses, and other fields. Some fields must match preset parameter ranges from registered processes.

## What constraints these characteristics impose on HTTP interfaces and external systems
Data sources are scattered. Updates occur per production batch and per process step. Interface requests must carry precise business identifiers to avoid cross-batch data confusion. Core documents include structured fields and unstructured attachments. Interfaces must support transmission and extraction of mixed-type data. Multiple system integrations create authentication requirements. Access permissions for different external systems must be managed uniformly. Data updates happen frequently and require real-time synchronization. Interface configurations must adapt to time-consuming complex data aggregation tasks. Return fields must strictly align with preset parameters from registered processes to avoid compliance risks.

## How to configure settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Use Bearer token format with a 32-bit access key | Follow standard HTTP authentication specifications when integrating multiple external systems, and uniformly manage interface access permissions |
| Request timeout setting | 600–1200 seconds | Adapt to time-consuming requirements of multi-step production data aggregation and impurity profile report parsing, avoid mid-request interruptions |
| `responseData` | Return only business-required batch fields and structured report fragments | Reduce invalid data transmission, lower interface bandwidth usage, and match the precise extraction requirements for data fields in this category |
| `variables` | Bind batch numbers and process step serial numbers as fixed request variables | Ensure each request carries a unique business identifier, avoid cross-batch data confusion |
| Field mapping configuration | Align external system data with field names preset in registered processes | Ensure returned data matches parameter definitions in enterprise registered documents, avoid compliance risks |
| Return format configuration | Structured JSON + optional binary attachments | Adapt to transmission requirements for mixed-type data such as impurity profile reports and cleaning records |

## Three common configuration errors
- The impurity content field returned by the interface does not match the preset range of the registered process, triggering abnormal alerts in the audit workflow. Cause: No registered process field mapping rules are bound in the configuration. Original external system field names are used directly, which do not match parameter definitions required by business compliance rules.
- Requests are sent without carrying the batch number from `variables`. Cross-batch production data is returned, leading to incorrect material balance calculations. Cause: Batch numbers are not set as mandatory request variables. The interface does not verify the uniqueness of request parameters, resulting in data confusion.
- Interface timeout settings are lower than 300 seconds. Timeout errors trigger when aggregating impurity profile data from multiple chromatography data systems. Cause: The time-consuming requirements of multi-step data aggregation in this category are not considered. Generic interface timeout configurations are used, which do not adapt to complex data extraction scenarios.

## How to verify successful configuration
- Send test requests with specified batch numbers and process steps. Check whether returned fields match preset business document fields.
- Verify that the token format in the `Authorization` header conforms to standard Bearer specifications. Confirm that corresponding error status codes are returned when authentication fails.
- Simulate requests for multi-system data aggregation. Confirm the completeness and timeliness of returned interface data. Adjust timeout configurations to meet business time-consuming requirements.
