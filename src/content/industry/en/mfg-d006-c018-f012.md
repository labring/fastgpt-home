# Inspection and Process Record Audit for Continuous Basic Chemical Production: Deployment and Upgrade

## What the Data for This Category Looks Like
Typical data sources for continuous basic chemical production include DCS/SIS systems, online analyzers, LIMS laboratory management systems, equipment condition monitoring modules, energy metering devices, and raw material tank data terminals. Data update frequencies fall into three categories: real-time (process temperature, pressure parameters), shift-based (shift reports, special work tickets), and daily (laboratory reports, interlock bypass records). Routine documents include operating procedures, process indicator cards, DCS trend charts, laboratory reports, interlock bypass records, special work tickets, and more. Fields include process parameters (units: ℃, MPa, m³/h), laboratory concentration percentages, interlock trigger time, and reset status, among others.

## Constraints on Deployment and Upgrade
The multi-source real-time data, multi-type document structures, and strict security and compliance requirements of this category impose multiple constraints on deployment and upgrade workflows.
Concurrent requests from multiple data sources require matching connection pool capacity to avoid data reading delays. Multi-type documents need adapted parsing rules to ensure accurate extraction of structured fields. Real-time updated process data requires a reasonable cache strategy to reduce pressure on the underlying database. Additionally, records related to toxic and hazardous media must be strictly restricted to intranet access. Deployments must be bound to the enterprise intranet domain name, with no public network exposure. During the upgrade process, storage of core documents such as interlock records and special work tickets must not be interrupted, to avoid impacting production audit workflows.

## Configuration Settings
The following configuration instructions are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | 100–200 connections | Continuous basic chemical production data is updated in real time, with high concurrent requests from multiple data sources, requiring sufficient connection pool capacity to ensure stable operation |
| `MONGODB_URI` | Point to the enterprise internal MongoDB replica set address | Data of this category accumulates over the production cycle, and the replica set architecture ensures read/write availability and data fault tolerance |
| `PG_URL` | Point to the enterprise internal PostgreSQL database address | Stores user registration information and permission configurations, ensuring normal authentication links |
| `REDIS_URL` | Configure local cache expiration time to 300 seconds | Real-time process indicators require high-frequency queries, and caching effectively reduces access pressure on the underlying database |
| `FILE_TOKEN_KEY` | Configure as an enterprise internal custom secret string | Used to verify the legality of uploaded files, adapting to access requirements for custom PDF parsing services |
| `STORAGE_S3_ENDPOINT` | Bind to the enterprise internal object storage node address | Stores large-volume documents such as interlock bypass records and special work tickets, complying with enterprise internal storage specifications and security requirements |
| `FE_DOMAIN` | Configure as the intranet access domain name for the production area | Only allows access from the production area intranet, meeting security and compliance requirements for production data |

## Common Misconfigurations
- Symptom: PDF upload fails during conversation, returning "File parsing timed out" or "Verification failed". Cause: The `FILE_TOKEN_KEY` parameter is not configured correctly, blocking upload requests, or the cache expiration time set in `REDIS_URL` is too short, causing loss of intermediate states during the parsing process.
- Symptom: The system frequently displays the "too many connections" error, and cannot read process data. Cause: The value of `DB_MAX_LINK` is lower than the number of concurrent requests in the production scenario, failing to match the pressure of real-time data updates.
- Symptom: The registration page fails to load, and new users cannot complete the registration process. Cause: The configurations for `PG_URL` and `FE_DOMAIN` are not properly associated, breaking the user authentication link and preventing the generation of valid registration credentials.

## How to Verify Successful Configuration
- Run a connection pool test script to confirm no connection timeouts or errors occur when 150 concurrent database requests are sent.
- Upload a typical interlock bypass record PDF, and confirm that structured fields including trigger time, interlock number, and reset status can be extracted correctly after parsing.
- Access the intranet address configured for `FE_DOMAIN`, and confirm the registration page loads normally, allowing new users to complete the registration process.
- Check the storage node bound to `STORAGE_S3_ENDPOINT`, and confirm uploaded shift report documents have been stored correctly and can be read without issues.

The values provided are common starting points and should be evaluated against the reader's own samples.
