# Inspection and Process Record Audit for Complete Household Appliance Manufacturing: HTTP Interfaces and External Systems

## What the data for this category looks like
The data for this category comes from ERP/MES systems, component batch ledgers, tightening and filling equipment, safety compliance testers, performance laboratories, and after-sales fault databases. Daily documents include configured BOMs, assembly work instructions, refrigerant filling records, electrical safety test reports, performance spot check reports, and repair records. Data is updated per single product, per shift production batch, or per spot check plan. Each individual record includes component batch numbers, process parameter values, and test timestamps. Field units include kilograms, volts, decibels, and others, covering the entire assembly, testing, and after-sales process.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
The mixed-line assembly of multiple models for this category requires HTTP interfaces to support dynamic matching of configured BOM parameters, to avoid confusion of processes for different product models. High-frequency single-product or batch-level data updates require interfaces to support batch requests and low-latency responses, with single-request processing duration controlled within a reasonable range. Multiple heterogeneous data sources require interfaces to be compatible with reporting formats from different devices, adapting to the differentiated output structures of safety compliance testers and filling equipment. Consumer-facing product characteristics require that test data transmitted via interfaces be traceable, with fields including unique identifiers and traceability information. The non-fixed update rhythm of spot check and repair records requires interfaces to support on-demand data pulling, adapting to flexible invocation needs of business scenarios.

## How to configure the settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer token format, carrying access keys assigned by the platform | Complies with API authentication specifications of external ERP/MES systems, ensuring data transmission security |
| `variables` | Pass product model and batch number as dynamic input parameters | Adapts to the mixed-line assembly business scenario with multiple models, avoiding errors in process parameter matching |
| `responseData` | Extract test results, batch numbers, and timestamp fields | Filters redundant data, reduces transmission bandwidth usage, and adapts to high-frequency data synchronization requirements |
| Request timeout duration | 60–120 seconds | Covers the normal return duration of data from safety compliance tests and performance laboratories, avoiding request failures caused by device delays |
| Batch request limit | First 20 records | Matches the spot check sample size per shift production batch, balancing transmission efficiency and data integrity |
| Request body size limit | 2 MB | Adapts to the transmission size of single-batch inspection data, avoiding exceeding interface limits of external systems |

## Three common configuration mistakes
- Symptom: An empty value is returned when calling the workflow interface, and inspection data from external systems cannot be obtained. Cause: Dynamic input parameters are not configured in `variables`, causing the interface to fail to match BOM parameters for the corresponding model of household appliances, and unable to pull matching data.
- Symptom: After upgrading to FastGPT v4.17.0, extraction of HTTP interface return values fails, and previously parsable safety compliance test data cannot be read. Cause: FastGPT v4.17.0 adjusted the extraction logic of `responseData`, and parsing failures occur due to failure to synchronize updated field mapping rules.
- Symptom: Interface requests frequently time out, and failures occur when pulling repair records in batches. Cause: Request timeout duration is not set appropriately, and the timeout threshold is not adjusted for the delay characteristics of multi-source data, causing requests to be interrupted by external systems.

## How to confirm the configuration is correct
- Initiate an interface call for a single product, check whether `Authorization` authentication passes, and whether the returned `responseData` includes expected test fields.
- Pass dynamic parameters for different models of household appliances, verify that the interface can correctly match process parameters of the corresponding BOM and return inspection data for the corresponding batch.
- Adjust the request timeout duration, simulate device delay scenarios, and confirm that the interface will not trigger abnormal termination due to timeout.
- Initiate a batch request, check whether the number of returned records matches the expectations of the business scenario, with no redundant or missing fields.
