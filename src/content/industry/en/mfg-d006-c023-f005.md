# Inspection and Process Record Audit for Industrial Instrument Manufacturing and Calibration: Tool Calling and Plugins

## What This Category of Data Looks Like
Data for this category originates from design documents, standard instrument and environmental monitoring data, calibration software outputs, laboratory information systems, and customer range requirements. Daily associated documents include assembly and commissioning sheets, calibration procedures, original calibration records, error curves, metrology certificates, and software version records. The system updates calibration data for each device per calibration event. Fields include calibration date, standard instrument ID, tested device range, error value, and certificate number. Most units are metrology-related units such as Pa, ℃, mL/min, and others.

## Constraints on Tool Calling and Plugins Workflow
Calibration data for this category is updated per device per calibration event, and includes professional metrology fields and strict traceability requirements. These characteristics impose three constraints on the tool calling and plugins workflow:
1.  The system must accurately bind calibration documents to a single device to avoid cross-device data confusion.
2.  The system must support unit verification to ensure units for fields such as error values and ranges match calibration procedure requirements.
3.  The system must connect to the traceability interface of the laboratory information system to verify the compliance of calibration data sources. The system cannot use general document fragments directly to complete calibration record audits.

## Configuration Setup
This configuration is based on FastGPT v4.17.0, with specific parameters as follows:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Workflow/API tool selection | `{"type": "function", "function": {"name": "verify_calibration_record"}}` | Binds the exclusive calibration record audit tool for this category, and enforces calls to the specified function |
| Single call timeout | 300 seconds | Adapts to the time required for reading original calibration records and parsing error curves |
| Context window limit | 4000–6000 token | Covers the total length of calibration-related documents for a single device |
| Workflow/API function-call configuration | Strict verification mode | Ensures that fields in tool return results fully match calibration procedure requirements |
| Number of call retries | 2 | Addresses temporary fluctuations in the laboratory information system |

## Three Common Misconfigurations
- Cross-domain errors occur when the system calls the laboratory information system interface. This happens because no cross-domain allowed request headers are added in the FastGPT plugin configuration, or the backend interface has not configured a cross-domain allowlist.
- The error `chat: llm-model-response-empty` is returned after tool calling. This occurs because the verification mode for `functionCall` is not specified correctly, or the context window is too small to contain complete calibration document content.
- Non-compliant error values appear in audit results. This occurs because unit verification configuration is not enabled, or the unit parameter of the calibration procedure is not passed during tool calling.

## How to Verify Successful Configuration
- Trigger the calibration record audit workflow, verify that the tool calling successfully invokes the specified calibration audit function, and confirm that the `toolChoice` configuration is active.
- Simulate a single call to the laboratory information system interface, verify that the timeout setting matches actual time requirements, and no timeout errors occur.
- Import the complete calibration documents for a single device, check whether the context window is sufficient to carry the document content, and no truncation prompts appear.
- Trigger the tool call retry logic, simulate a temporary interface delay scenario, and confirm that the retry mechanism activates normally and completes the call.

The values provided are common starting points and should be measured against the user’s own samples.
