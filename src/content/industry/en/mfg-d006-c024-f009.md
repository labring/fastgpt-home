# Inspection and Process Record Review for Process Change and Engineering Change: Model Access and Configuration

## What the data for this category looks like
This category of data is generated by the change management team composed of R&D, process, quality, production and procurement departments of manufacturing enterprises. Sources cover PLM, ERP, MES, supplier materials, verification tests and customer special requirements. Daily documents include ECN/ECR forms, change assessment reports, drawings and BOM version files, process verification reports, switching plans, inventory disposal documents and customer approval documents. Data updates have no fixed cycle, and are synchronized each time a process or engineering change is triggered. Document fields include core information such as change number, version number, involved materials, verification results, etc. There is no unified standard unit, and corresponding field rules need to be matched according to the specific document type.

## What constraints do these characteristics impose on the "model access and configuration" link
Multi-source and heterogeneous data sources require model access to adapt to the interface formats of different systems, to avoid data synchronization exceptions or missing data. The irregular update rhythm requires the configuration to support dynamic loading of the latest change documents, to prevent using old version data for review and affecting the timeliness of changes. The diverse document types and large differences in length require reasonable control of the context length, to avoid audit interruptions caused by exceeding the model's processing limit. The core fields have no unified unit, which requires the model to perform field matching for a single document type, and cannot rely on general field rules to complete the review. At the same time, the rigor required for change review requires limiting the randomness of model output, to ensure that the results comply with the compliance standards of the manufacturing industry.

## How to set the configuration
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the total length of multiple documents such as ECN and BOM, avoiding audit interruptions caused by context overflow |
| `maxTokens` | 3000–5000 token | Controls the length of single-round output, ensuring that detailed feedback for change review meets the length requirements of process documents |
| `quoteMaxToken` | 1000–2000 token | Limits the content length of referenced source documents, ensuring that referenced content is complete and does not exceed the standard range of a single-page document |
| Workflow/API tool selection | auto | Allows the model to independently call tools to complete cross-system data queries, adapting to the linkage requirements of multiple data sources such as PLM and ERP |
| `temperature` | 0.2–0.4 | Reduces the randomness of generated content, ensuring the rigor of change review results and complying with the compliance requirements of the manufacturing industry |
| `AIPROXY_API_ENDPOINT` | Fill in the dedicated address according to the deployment environment | Adapts to locally or cloud-deployed model access, meeting the security requirements of data localization for manufacturing enterprises |

## Three common mistakes
- Phenomenon: <think> tags remain in the model output, or the reasoning_c marker cannot be correctly identified. Cause: The model output format is not configured according to the requirements of FastGPT v4.17.0, and the special reasoning marker rules of the locally deployed model are not adapted.
- Phenomenon: After configuring multiple data sources, the model cannot recall BOM version data in PLM. Cause: `AIPROXY_API_ENDPOINT` is not correctly set to point to the internal data source gateway, resulting in insufficient cross-system access permissions.
- Phenomenon: The change suggestions generated by the model do not match the actual document fields. Cause: The `temperature` value is too high, causing the generated content to deviate from the established change document specifications and affecting review accuracy.

## How to confirm that the configuration is complete
- Initiate a simulated change review request, check whether the output correctly references the number and version information of the corresponding ECN document.
- View the model call log to confirm that no context overflow error related to `maxContext` is triggered.
- Test the multi-data source access process, verify whether the model can correctly pull associated change data from PLM and ERP.
- Adjust the `temperature` parameter to different ranges, compare the rigor of the output content, and confirm that it meets the review requirements.

The values provided are common starting points and should be measured against the reader's own samples.
