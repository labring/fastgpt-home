# Inspection and Process Record Review for Tooling, Fixture and Gauge Manufacturing: Multi-turn Dialogue and Prompting
This document is written based on FastGPT v4.17.0

## What Data for This Category Looks Like
Data comes from product mathematical models and GD&T specifications, process route documents, coordinate measuring data, on-site trial feedback, and metrology system data. Updates are carried out per individual project, each product design change, and regular calibration cycles. Daily documents include tooling requirement documents, positioning datum scheme documents, fixture design drawings, gauge operation instructions, acceptance reports, calibration records, and change histories. Data fields include geometric dimensioning and tolerancing parameters, measurement deviation values, calibration validity periods, version identifiers, etc. Units include millimeters, newtons, days, and others.

## What Constraints Do These Characteristics Impose on the Multi-turn Dialogue and Prompting Link
Since data sources are scattered and updated per project, multi-turn dialogue must isolate context by project and user to avoid cross-project data confusion. Since document types are diverse and include professional technical parameters, prompts must be clearly adapted to GD&T specifications and units of measurement to ensure the professionalism of questions and responses. Since update frequencies are not fixed, dialogue must support dynamic loading of the latest calibration records and change histories to avoid using outdated data. Since individual documents have long lengths, the context window must reserve sufficient space to prevent truncation of critical information.

## How to Configure
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Generate a unique value using project number + user identifier | Isolate dialogue contexts for different projects and users to avoid cross-project data confusion |
| `messages` | Retain the most recent 15–20 turns of dialogue content | Adapt to the multi-step verification requirements of tooling inspection, and trace back earlier datum schemes and change records |
| `variables` | Bind project number and calibration validity period parameters | Automatically bring in exclusive documents and metrology data for the current project, reducing repeated data entry |
| Maximum context length | 8000–12000 characters | Adapt to the text and annotation lengths of tooling design drawings and calibration reports, avoiding truncation of critical information |
| Single dialogue timeout | 600 seconds | Adapt to the time required for loading and verifying tooling documents, avoiding dialogue interruptions due to large data volumes |
| Single recall limit | Top 6 matching documents | Cover core documents required for tooling inspection such as positioning datum schemes and acceptance reports, avoiding interference from redundant information |

## Three Common Mistakes
- Phenomenon: After initiating a dialogue via API, the `Human` field is empty in the response record preview. Cause: The user's question content for the `messages` parameter was not passed correctly, resulting in missing user input identifiers in the dialogue context.
- Phenomenon: Different users cannot view their respective historical dialogue records. Cause: The `chatId` parameter was not used to isolate contexts by user and project, resulting in all dialogue data being stored uniformly.
- Phenomenon: Large deviations in results when verifying tooling interference via multi-turn dialogue. Cause: The `variables` parameter was not bound to bring in product mathematical model parameters for the current project, resulting in the dialogue using outdated or incorrect datum data.

## How to Confirm Proper Configuration
- Initiate a test dialogue, enter the tooling inspection requirements for the specified project, and check whether the project information corresponding to the bound `variables` parameter is automatically included in the returned content.
- Switch to different user identifiers, initiate a dialogue with the same requirements, and check that each user's historical dialogue records only display content from their own conversations.
- Check whether the `Human` field in the response record preview contains the user's original question content, confirming that the `messages` parameter was passed correctly.
- Adjust the number of dialogue turns, check that the context retains earlier discussions of the datum scheme, and that no critical information has been truncated.

The values provided here are common starting points and should be measured against the reader's own samples.
