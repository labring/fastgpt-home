# Inspection and Process Record Audit for High-Volume Automotive Component Manufacturing: Knowledge Base Retrieval and Recall

## What this category of data looks like
The data for inspection and process record audit in high-volume automotive component manufacturing comes from customer drawings and special characteristic lists, ERP/MES systems, measurement tool collection data, equipment process parameters, and supplier quality certificates. Daily documents include control plans, process flowcharts, work instructions, first-piece and patrol inspection records, SPC reports, PPAP materials, and 8D reports. Each document’s fields include batch numbers, special characteristic IDs, test values, tolerance thresholds, abnormal records, and other items. Units match the test items, such as millimeters, newton meters, and CPK values. Data update frequency follows: first-piece patrol inspection records are updated per production batch, SPC reports are updated per shift, and equipment operating parameters are collected continuously.

## What constraints do these characteristics impose on knowledge base retrieval and recall
Data for this category comes from multiple dispersed sources and is updated frequently. Retrieval must cover multiple systems and document types, while supporting incremental synchronization to match the update rhythm of each batch and shift. This avoids audit deviations caused by delayed data. Document types cover quality system files and real-time test records. Retrieval must accurately match business semantics such as special characteristics and abnormal root causes, rather than relying only on keyword matching. Keyword-only matching can easily miss critical quality information. Restricted by vehicle customer quality systems, retrieval results must be strictly associated with the quality records of the corresponding batch, to avoid mixing in irrelevant business data. At the same time, retrieval speed must be guaranteed to support real-time audit requirements for high-volume production, to avoid impacting production line cycle time.

## How to set the configuration
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `searchMode` | Semantic Retrieval | This category requires matching quality content with semantic associations such as special characteristics and abnormal root causes. Semantic retrieval better aligns with business requirements |
| `limit` | Top 8 entries | High-volume manufacturing generates many inspection records. Limiting to the top 8 entries balances recall coverage and retrieval response speed |
| `usingReRank` | Enabled | Inspection and audit require accurate matching of abnormal details and root cause analysis content. Reranking improves the sorting priority of highly relevant results |
| `datasetSearchUsingExtensionQuery` | Enabled | Automatically expand keywords such as batch numbers and special characteristics to adapt to the associated retrieval requirements of multi-source data |
| `collectionIds` | Configured by business domain | Differentiate different document collections such as control plans, SPC reports, and 8D reports to avoid mixing irrelevant data into retrieval results |
| `similarity` | 0.75–0.85 | Calibrated through actual testing. Filters low-relevance non-quality documents and retains highly matched inspection and audit-related records |

## Three common misconfigurations
1.  Phenomenon: After consecutive queries in a single conversation window, retrieval time exceeds 60 seconds, and queries in a new window return to normal. Cause: The context window size is not limited. Accumulated historical conversations increase the vector database computing load, slowing down retrieval speed.
2.  Phenomenon: The number of retrieval results far exceeds the configured `limit` value, and a large number of documents unrelated to automotive component quality are mixed in. Cause: `collectionIds` are not configured to group by business domain. Cross-collection retrieval introduces irrelevant datasets.
3.  Phenomenon: Semantic retrieval scores are higher than 0.9, but result matching is poor. Changing the vector model does not improve the situation. Cause: `usingReRank` reranking is not enabled. Original semantic matching relies only on vector similarity, and does not filter content that is semantically similar but business irrelevant.

## How to confirm the configuration is correct
- Import a batch of control plans, SPC reports, and 8D reports, initiate a quality audit query for the corresponding batch, and verify that the retrieval results include documents from the target business domain.
- Initiate 10 related queries consecutively, check whether the single retrieval time remains within a reasonable range without a noticeable increasing trend.
- View the retrieval log to confirm that `searchMode` is set to semantic retrieval, `usingReRank` is enabled, and `collectionIds` only include datasets from the target business domain.
- Adjust the `similarity` threshold, and check whether the retrieval results show filtering effects that conform to business logic as the threshold changes.

The values provided here are common starting points, and should be evaluated against samples relevant to the specific use case.
