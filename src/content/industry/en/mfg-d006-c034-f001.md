# Inspection and Process Record Audit for Baking and Convenience Foods: HTTP Interfaces and External Systems

## Data profile for this category
Baking and convenience food inspection and process records cover bakeries, cookie, instant noodle, and frozen pastry factories. Daily processed documents include formula and feeding lists, production records, baking or steaming curves, metal detection records, cleaning and disinfection records, and factory inspection reports. Data sources include raw and auxiliary material qualification certificates, ERP/MES systems, weighing systems, ovens or frying lines, laboratory testing equipment, and food traceability ledgers. Data updates per batch, shift, or daily. Core time-consuming steps include reviewing formulas and allergen materials, controlling proofing or baking/frying windows, verifying foreign matter control results and package date/expiry dates. Since products are directly consumed and line changes are frequent, verification needs for allergens and cleaning switching are more prominent. Errors may lead to unqualified taste, incorrect allergen labeling, product recalls, and other issues.

## Constraints for HTTP interfaces and external systems
The multi-source data, high-frequency batch updates, and strict verification requirements of this category create multiple constraints for HTTP interface and external system integration. Frequent line changes require interfaces to support dynamic binding of batch-specific parameters, avoiding reuse of old batch configurations. Multi-system data synchronization requires interfaces to support compatible formats and return rhythms across different data sources, adapting to data upload delays from ovens, laboratory equipment, and other devices. High-priority allergen and cleaning verification requires interfaces to enforce mandatory checks for required fields, reducing unqualified data entering the audit process. The direct consumption product attribute requires interfaces to perform strict compliance checks on returned data, ensuring no non-compliant content is included.

## Configuration settings
The following configurations are adapted for FastGPT v4.17.0:

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {Factory-specific API key}` | Identity verification when integrating with external systems such as ERP and weighing systems |
| `variables` | Bind production order number, allergen list, baking window threshold | Adapt to dynamic batch parameter requirements for frequent line changes |
| `responseData` | Return only validation-passed fields and batch unique identifiers | Reduce invalid data transmission and lower system load |
| Interface timeout period | 30–60 seconds | Duration to wait for data returns from ovens and laboratory testing equipment |
| Required field validation | Mandatory inclusion of allergen list and package date 72+ hours before expiry | Match core verification requirements of this category |
| Interface retry count | 2 times | Address temporary interface call failures caused by network fluctuations |

## Three common configuration errors
- A call to an integrated MES system interface returns `408 Request Timeout`. Cause: No timeout duration matching production data return rhythm is set, and wait time for oven curve upload exceeds default limits.
- Some batches have missing allergen fields when submitting production records in bulk. Cause: Allergen list is not configured as a required parameter in `variables`, leading to missed key verification items during line changes.
- The number of results returned after calling the laboratory metal detection data interface does not match the actual batch count. Cause: Invalid data is not filtered via `responseData`, causing redundant historical detection records to be mixed into the current batch.

## How to confirm correct configuration
- Call the test production batch interface, check if the `Authorization` parameter is correctly carried, and confirm the identity verification result passes.
- Submit a set of test data including an allergen list, check if the `variables` parameter is correctly bound to the current batch’s audit logic.
- Trigger an interface call, check that the fields returned by `responseData` only include valid data for the current batch, with no redundant historical records.
- Simulate a temporary network interruption and retry the interface, confirm the retry mechanism triggers normally and no duplicate data is submitted.
