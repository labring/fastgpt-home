# Inspection and Process Record Audit for Baking and Convenience Foods: Vector Models and Indexes

## What Data Looks Like for This Category
Typical entities in this category are bread, pastry, biscuit, instant noodle, and frozen pastry factories. Documents generated daily include recipes and feeding lists, production records, baking or steaming curves, metal detection records, cleaning and disinfection records, and factory inspection reports. Data sources include raw and auxiliary material qualification certificates, ERP/MES systems, weighing systems, production equipment, laboratories, and food traceability ledgers. Documents are updated per batch, per shift, or daily. Most document fields include allergen labels, process parameters, shelf life, and batch information.

## Constraints on Vector Models and Indexing
This category’s high-frequency updates and multi-source heterogeneous document characteristics create constraints on vector index real-time performance and compatibility. Data updated per batch or shift requires indexes to support incremental synchronization, avoiding the time cost of full reindexing. Multiple document types — such as PDF files with parameter curves and structured CSV production records — need to adapt to different chunking logic, preserving key fields like allergens and process windows. Frequent product line changes require index retrieval logic to quickly switch associated document sets, avoiding interference from cross-batch data.

## Configuration Settings
This configuration is formulated based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| Chunk Length | 800–1200 characters | Adapts to the typical length of process parameters and batch records in this category’s documents, avoiding splitting critical information |
| Overlap Length | 100–200 characters | Preserves continuous information such as process curves and allergen labels across chunks |
| `defaultToken` | 1024 | Matches the average token proportion of most production documents, avoiding truncation of core content |
| `maxToken` | 4096 | Adapts to the total length of batch documents uploaded in bulk, preventing single-batch data from exceeding limits |
| Single Index Limit | 5000 items per batch | Adapts to batch uploads of 100,000-level data, avoiding overload from single-run loading |
| Similarity Threshold | 0.75–0.85 | Distinguishes between same-batch production records and cross-batch unrelated data, meeting the accuracy requirements for allergen review |

## Three Common Misconfigurations
- Excessively long vectorization time after uploading PDF documents to the knowledge base. Cause: Documents are not split and uploaded per batch, and chunk length is set too large, leading to excessive single-batch processing load.
- Total number of vectors after processing 100,000 CSV entries is reduced by thousands. Cause: Some rows contain unparseable special characters or empty fields, and automatic filtering of invalid rows is not enabled, resulting in skipped data.
- Collection creation succeeds but index cannot be built. Cause: Vector model dependency versions differ between local and container environments, and loading resources for the corresponding model are missing in the container, leading to index construction failure.

## How to Verify Correct Configuration
- Upload a single typical production record document, verify that chunked content fully retains key information such as allergens and process windows.
- After bulk uploading 100,000-level test data, verify the match between the final index item count and source data count, and adjust invalid row filtering rules.
- After starting containerized deployment, run a small-batch index build, check logs for model loading or parameter mismatch errors.
- For allergen review scenarios, search preset keywords, verify that the return result similarity threshold meets business filtering requirements.

The values provided are common starting points and should be measured against the reader's own samples.
