# Inspection and Process Record Audit for Electric Motor and Generator Manufacturing: Model Integration and Configuration

## What Data for This Category Looks Like
Data for this category comes from electromagnetic design databases, batch ledgers for copper wire and insulating materials, real-time collection data from winding machines, balancing machines, and electrical test benches, plus production work orders from ERP/MES systems. Data is updated per finished product or per workpiece batch, and synchronized whenever a product type modification occurs.

Daily documents include winding process cards, insulation treatment records, dynamic balance reports, dielectric strength test reports, and type and factory inspection reports. Fields include winding turns, insulation layer thickness, dynamic balance margin, test voltage value, plus equipment numbers, production batch numbers, and test dates.

## Constraints Imposed on Model Integration and Configuration
The multi-source heterogeneous data and high-frequency update nature of this category require the model integration link to support multi-format document parsing and field recognition. Strong validation fields such as winding turns and dielectric strength values have strict numerical ranges, so the model must accurately match document fields to business rules.

Each unit or batch has independent data characteristics, so the context window must support full loading of single-batch documents, while controlling resource usage per inference round to avoid GPU memory overflow from multi-source data accumulation. Additionally, the precision requirements for high-voltage test values require the model to have stable numerical extraction and validation capabilities, and adapt to deployment scenarios with different hardware resources.

## Configuration Settings
| Configuration Item | Recommended Range | Rationale |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | Adapts to the total text length of single-batch motor test reports and process cards, preventing truncation of core validation fields |
| `maxTokens` | 2000–3000 token | Controls the output length of single-round inference, meeting the result output needs of winding validation and anomaly analysis |
| `quoteMaxToken` | 1500–2000 characters | Limits the single-segment length of referenced documents, ensuring key data such as dielectric strength values and dynamic balance readings are fully readable by the model |
| `temperature` | 0.1–0.3 | Reduces random output probability, ensuring consistency of validation results for winding turns, insulation parameters, and other fields |
| `AIPROXY_API_ENDPOINT` | Fill in the actual access address of the deployment cluster | Adapts to API forwarding configurations for multi-GPU deployments, enabling reasonable allocation of GPU memory resources |
| `toolChoice` | auto | Allows the model to automatically select validation tools, adapting to field extraction and anomaly analysis needs for multiple document types |

## Three Common Misconfigurations
- Phenomenon: GPU memory usage continues to rise until overflow after the rerank model runs, with no automatic release of memory resources. Cause: No memory automatic recycling strategy is configured, and the number of concurrent calls to the rerank model is not limited.
- Phenomenon: No available models appear in the dropdown menu for the text extraction node in the workflow. Cause: The API key and access address of the corresponding text extraction model are not bound in the system configuration, or the model type does not match the node requirements.
- Phenomenon: Models mounted via Ollama produce outputs unrelated to knowledge base content, or the second GPU is not utilized in multi-GPU deployments. Cause: The context window parameters of the model are not configured correctly, leading to truncation of key document content, or the API forwarding logic for multi-GPU scheduling is not enabled.

## How to Verify Successful Configuration
- Log in to the FastGPT v4.17.0 backend, verify the API key and access address configuration for model integration, ensuring they match the deployment environment parameters.
- Upload a single motor dielectric strength test report to trigger the model validation process, check whether the output includes complete field extraction and validation conclusions.
- Start a parallel inference task for multiple batches of data, monitor GPU resource usage, confirm that memory usage stays within a reasonable range.
- Test the interaction flow for models mounted via Ollama, confirm that the output has logical correlation with the uploaded motor production documents.
