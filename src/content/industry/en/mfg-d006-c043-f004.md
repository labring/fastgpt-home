# Inspection and Process Record Audit for Batchwise Fine Chemical Synthesis: Workflow Orchestration

## What data for this category looks like
Data for this category comes from end-to-end production processes of paint, resin, additive, agrochemical intermediate, and specialty chemical enterprises. Daily documents include batch production instructions, raw material feeding verification slips, reaction process records, cleaning records, inspection reports, deviation and change orders. Data sources cover formula and process libraries, raw material batches, reactor DCS, weighing systems, LIMS, and warehouse systems, updated after each batch production or completion of each critical step. Data is bound to batch-specific multi-stage fields, including parameterized values such as feeding quantity, reaction temperature, and cleaning status. There are also compliance requirements for formula confidentiality and cross-batch cleaning residue verification.

## What constraints do these characteristics impose on workflow orchestration
The batchwise updates, multi-stage and multi-data-source nature, confidentiality requirements, and compliance needs of this category impose multiple constraints on workflow orchestration.
Bind batch ID as the core identifier in `variables`, and link to raw material, reaction, and inspection data for the corresponding batch.
Arrange nodes in the order of production steps, calling each system’s interface sequentially to pull corresponding data.
Configure permission-isolated `variables` parameters to limit access to formula-related data.
Set branch nodes to trigger different verification logic based on cleaning records and raw material feeding review results, to avoid cross-batch contamination or feeding errors.

## How to set configurations
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `variables` | Bind data source fields associated with `nodeId` per batch, set permission isolation scope | This category requires batchwise data management and has formula confidentiality requirements |
| Workflow trigger rule | Trigger after completion of the previous production stage | Data for this category is updated after critical steps, and must match production process order |
| Branch node condition | Match verification logic based on cleaning record and raw material feeding review slip fields | Must avoid cross-batch contamination and feeding errors, and meet business verification requirements |
| Timeout setting | 600 seconds | Covers average time for multi-system interface calls, adjust based on actual measurements |
| Node call order | Arrange in the order: raw material feeding review → reaction process → cleaning record → inspection report | Matches the production sequence logic of batchwise fine chemical synthesis |

## Three common mistakes
- Issue: Workflow calls return an identity verification failure prompt, requiring an application key instead of an account key. Cause: Failed to use the application key for interface calls, and mistakenly used an account key, resulting in identity verification failure.
- Issue: Workflow runtime exceeds expected duration, and the interface shows execution status unchanged for a long time. Cause: Did not set timeout parameters appropriately, and did not optimize parallel logic for multi-system calls, resulting in overall runtime exceeding system load limits.
- Issue: In FastGPT v4.17.0, only two global variables are displayed, and more custom variables cannot be added. Cause: Did not enable advanced variable editing mode in the global configuration menu of the workflow editing page, or configuration cache failed to sync after upgrade.

## How to confirm the configuration is correct
- Verify the `variables` configuration of the workflow, confirm that the corresponding batch’s data source fields are bound, and the permission scope meets confidentiality requirements.
- Trigger a test batch workflow, check the call logs for each node, confirm that the execution sequence and trigger logic match the production process.
- Adjust the timeout setting to match the average runtime of current system calls, to ensure the workflow does not stop unexpectedly.
- Verify the branch node’s verification logic, input abnormal cleaning record fields, and confirm that the corresponding verification prompt is triggered.

The values provided here are common starting points, and should be evaluated against the reader’s own samples.
