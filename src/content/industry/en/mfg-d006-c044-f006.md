# Pulp and Paper Inspection and Process Record Audit: Citation Source and Traceability

## What the Data for This Category Looks Like
Pulp and paper inspection and process record data mainly comes from wood pulp and waste paper batch ledgers, DCS/QCS control systems, paper machine online measurement devices, laboratory testing systems, and energy and water treatment systems.
Daily generated documents include pulp preparation sheets, beating records, paper machine operation records, online quality curves, laboratory test reports, and sheet break and product change records.
Data update frequencies include real-time (paper machine online measurement), shift-based (team summary records), and per roll (finished paper batch ledgers).
Single document fields include pulp ratio, beating degree, grammage, moisture content, and thickness. Common units are g/㎡, %, mm, and similar units.

## Constraints Imposed on Citation Source and Traceability Link
The high-speed continuous web production characteristics of pulp and paper require traceability to bind the complete production chain of a single paper roll. Citation sources must accurately match the corresponding relationships between batches, time, and equipment nodes. Multi-source heterogeneous data formats and update frequencies require traceability systems to support structured form records and unstructured curve data. Long shift summary documents require controlling total context length to avoid exceeding processing limits. Deviations in inspection and process records directly lead to paper roll downgrading or sheet breaks. The traceability link must ensure every citation can be traced back to the original data source, with no ambiguous associations.

## Configuration Setup
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 characters | Adapts to the single-segment data length of individual online quality curves and paper machine operation records, avoiding context overflow |
| `responseData` | Return only associated document metadata | Filters non-inspection data from energy and water treatment systems, focusing on core traceability documents such as pulp preparation sheets and laboratory reports |
| `detail` | Full traceability chain | Retains the source document ID, generation time, and associated production node information for every citation |
| Maximum context | First 6000 characters | Covers the total length of shift team summary records, meeting cross-document traceability requirements |
| Single search limit | Top 8 entries | Balances the recall volume of sheet break and product change records and online measurement data, avoiding redundant information interfering with audit results |

## Three Common Configuration Mistakes
- Redundant citations from energy systems appear in generated audit reports. Cause: The recall scope of `responseData` is not configured, causing searches to cover non-inspection documents.
- Citation source fields display empty values on the interface. Cause: The `detail` configuration is not enabled, and document metadata is not captured.
- Redundant knowledge base citation identifiers are included in generated pulp preparation sheet attachments. Cause: The option to disable citation output is not configured in workflow nodes, and traceability metadata is mistakenly written to attachments.

## How to Verify the Configuration
Inputting the batch number of a single finished paper roll allows checking if returned results include metadata for the corresponding batch’s pulp preparation sheets and beating records.
Reviewing the generated inspection audit report confirms that citation tags only link to inspection and process record documents, with no unrelated data sources.
Adjusting the `quoteMaxToken` parameter to 1500 characters enables observing if a context overflow error occurs, verifying the parameter takes effect.
Simulating a sheet break scenario by entering keywords allows checking if the number of recalled sheet break and product change records matches the single search limit configuration.

The values provided are common starting points and should be measured against the reader's own samples.
