# Inspection and Process Record Audit for Meat Products and Slaughter Processing: HTTP Interfaces and External Systems

## What the data for this category looks like
The main entities for this category are slaughterhouses, cooked meat and frozen prepared food enterprises. Daily generated documents include quarantine certificates, slaughter and cutting records, ingredient marinating records, thermal processing records, cold chain temperature records, and microbial test reports. Data sources include animal quarantine information, supplier batches, production traceability systems, temperature collection equipment, metal detection equipment, and laboratory test results. Data updates occur per production batch and per work shift. Cold chain temperature data is collected and updated continuously. Document fields include batch number, quarantine date, test item results, temperature value, operator identifier, and others. Cold chain temperature records use degrees Celsius as the unit. Batch numbers use a combination of letters and numbers.

## What constraints these characteristics impose on the HTTP Interfaces and External Systems link
This category has high-frequency data updates and strong association requirements. Continuous temperature control data requires real-time reporting, so the interface must support low-latency calls. Mixed transmission of multiple types of documents and fields requires the interface to handle both structured batch and temperature data and unstructured certificate documents. The strong association requirement between batches and quarantine information requires that the parameters passed by the interface include fields that uniquely identify production links. In addition, the consequences of errors are severe, so the interface must have verification and retry capabilities to prevent incorrect data from entering production links.

## How to set configurations
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| API Key Configuration | Bind a dedicated key for the business system, with the `Bearer ` prefix | Used to verify the permission of external system calls and avoid unauthorized access |
| Variable Transfer Settings | Transfer core fields such as batch number, quarantine number, and production shift | Used to associate inspection records with production batches to meet traceability requirements |
| Response Data Processing | Only return verified record IDs and status codes, filter redundant content of unstructured documents | Adapt to the lightweight data transmission requirements in meat product processing scenarios |
| Interface Timeout Setting | 30–60 seconds | Adapt to the real-time reporting delay requirements of continuous temperature control data |
| User Identification Configuration | Transfer according to the business system user ID | Used to distinguish audit records of different operators |
| Failure Retry Configuration | Retry 2 times after failure, with a 5-second interval | Respond to interface call failures caused by network fluctuations |

## Three Common Misconfigurations
- Phenomenon: The interface returns a `401 Unauthorized` error, or prompts that the key format is invalid. Cause: The `Authorization` parameter is not configured correctly, the `Bearer ` prefix is not added, or an expired service key is used.
- Phenomenon: Audit records of different operators are mixed, and ownership cannot be distinguished. Cause: The identification parameter is not transferred according to the business system user ID, and the variable transfer rule for user isolation is not configured.
- Phenomenon: The interface returns a large amount of redundant unstructured document content, causing parsing failures in the business system. Cause: The `responseData` filtering rule is not configured, and only the verified core fields are not returned.

## How to Confirm Proper Configuration
- Call the test interface, pass simulated batch numbers and quarantine numbers, check that the returned results only include core verification fields with no redundant content.
- Call the interface using different simulated user IDs, check that the returned audit records are correctly associated with the corresponding user identifiers.
- Simulate a network fluctuation scenario, trigger an interface call failure, check that retries are performed according to the configured retry rules.
- View the interface call logs, confirm that the `Authorization` parameter format is correct, and no key leaks or format errors occur.
