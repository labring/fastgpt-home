# Inspection and Process Record Audit for Meat Products and Slaughter Processing: Tool Calling and Plugins

## What data looks like for this category
Daily documents for this category include quarantine certificates, slaughter and cutting records, ingredient marinating records, thermal processing records, cold chain temperature records, and microbial test records. Data sources include animal quarantine information, supplier batches, production traceability systems, temperature collection devices, metal detection devices, and laboratory test results. Data is updated per production batch and per shift. Cold chain temperature data is collected and updated continuously. Document fields include standard business fields such as batch number, quarantine number, temperature value (℃), test result, and operation time. Different documents must strictly match the association relationships defined in the production workflow.

## What constraints these characteristics impose on tool calling and plugins
Data for this category is updated per production batch and per shift node, and includes continuously collected temperature control data. This requires tool calls to be strictly bound to associated data for the corresponding production batch to avoid cross-batch confusion. For quarantine certificates and test records related to biological risks, tool calls must support structured field verification to ensure extracted information meets compliance requirements. Differences in fields across multiple document types require tool call configurations to preset standard field mappings to avoid mismatches between extraction results and business documents. The real-time requirements of continuous temperature control data mean tool call response speeds must align with per-shift and per-batch business rhythms, with no excessive delays.

## How to configure settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `toolChoice` | `auto` | Automatically matches tool calling needs for quarantine, temperature testing, and other scenarios in the current context |
| Trigger timing | Triggered per production batch node | Aligns with the business data update rhythm of this category, which is updated per batch |
| Context window | 8000–12000 token | Covers multiple documents for a single production batch, including slaughter, quarantine, cold chain, and other related content |
| Timeout duration | 600 seconds | Adapts to the need to pull continuously collected cold chain temperature data |
| `functionCall` | Forced structured output | Requires tools to return results that conform to business fields to facilitate audit and verification |
| Maximum documents per call | Top 10 | Matches the typical number of documents for a single production batch |
| Call interval | 30 seconds | Prevents frequent triggering of interface rate limits |

## Three common misconfigurations
- Tool calling does not have the `functionCall` configuration enabled, returning unstructured natural language results that cannot extract standard fields such as batch number, quarantine number, or temperature value. This occurs because the forced structured output setting is not enabled.
- Tool calling in advanced orchestration fails to trigger normally, returning the prompt "trigger conditions do not match". This occurs because the trigger timing is incorrectly set, and the business logic tied to production batch nodes is not bound.
- Full tool call request body cannot be viewed. This occurs because debug logging configuration for FastGPT v4.17.0 is not enabled, so request details are not captured.

## How to verify correct configuration
- Simulate submission of production batch data to verify whether the tool automatically triggers the corresponding quarantine and temperature detection calling processes.
- Review tool call logs to confirm returned structured results include standard business fields such as batch number, quarantine number, and temperature value.
- Simulate a scenario for pulling continuous temperature control data to confirm that the tool completes responses within 600 seconds without triggering timeout errors.
- Switch the trigger timing to per-shift node to verify whether the tool can correctly pull all operation records and test data for the current shift.

The values provided here are common starting points and should be measured against the reader's own samples.
