# Inspection and Process Record Audit for Equipment Point Checking and Preventive Maintenance: HTTP Interfaces and External Systems

## What data for this category looks like
This category covers records related to the full lifecycle of manufacturing enterprise equipment. Data sources include EAM/CMMS systems, equipment sensor collection data, manual equipment point checking records from operators, maintenance history archives, spare parts inventory lists, and statutory inspection documents. Daily documents include equipment ledgers, graded point check lists, downtime maintenance plans, work orders, fault analysis reports, spare parts lists, and special equipment inspection records.
Data update frequencies cover shift-based point check submissions, daily/weekly/monthly maintenance plan distribution, and immediate updates when faults occur. Fields include equipment numbers, check locations, detection parameters and their corresponding units, maintenance execution times, spare part models, and more.

## What constraints these characteristics impose on HTTP interfaces and external systems
Data sources for this category are scattered and have large format differences. HTTP interfaces must support field mapping and format conversion for multi-source data, to adapt to output structures from different systems such as EAM/CMMS and sensor devices.
Data update frequencies range from immediate to periodic. Interfaces must support both scheduled batch calls and event-triggered immediate calls, to meet real-time synchronization needs for fault reports and shift-based point checks.
Fields include detection parameters with units and compliance records. Interface input parameters must clearly define field definitions and unit verification rules, to avoid data parsing errors.
Statutory inspection records have compliance requirements. Interfaces must include field integrity verification logic, to ensure no required fields are missing.

## How to configure settings
This configuration guide is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {pre-configured enterprise system API key}` | Identity verification requirements for connecting to permission-protected enterprise equipment management systems such as EAM/CMMS |
| `variables` | `{"deviceCode": "${input.deviceCode}", "checkDate": "${formatDate(now, 'yyyy-MM-dd')}" }` | Adapts to variable input parameters for shift point checks and fault reports, matches field definitions in equipment ledgers and point check lists |
| `responseData` | `Extract the first 8 entries from the data array under the root node` | Equipment point check data is usually returned grouped by equipment, and single-batch return data volume aligns with the record scale of team inspections |
| Request timeout | `30–60 seconds` | Balances real-time requirements for equipment sensor data and fault tolerance for workshop network fluctuations |
| Retry count | `2 times` | Addresses request failures caused by temporary network jitter, avoids repeated triggering of work order generation |
| Field verification rules | `Verify required field formats and units` | Meets compliance requirements for equipment point check lists and statutory inspection records, prevents invalid data from being stored |

## Three common configuration errors
- Symptom: Interface calls return status code 401 or a permission denied prompt, but calls via Postman succeed. Cause: The `Authorization` parameter is not configured correctly, or the key's permissions do not cover the interface access scope of the target equipment management system.
- Symptom: Returned point check data fields are empty or have abnormal formats. Cause: Returned content is not extracted correctly per the `responseData` rule, or field names in the input parameter `variables` do not match the target interface.
- Symptom: Scheduled calls do not sync the latest point check data. Cause: The correct trigger frequency is not set, or dynamic time parameters are not included in `variables` to match the target interface's query conditions.

## How to confirm correct configuration
- Call the test interface, verify that the returned `responseData` includes expected equipment point check fields and corresponding values.
- Submit test input parameters, confirm that dynamic parameters in `variables` are correctly replaced with test values.
- Check interface call logs, confirm that the `Authorization` parameter is correctly included, and no permission errors occur.
- Trigger a scheduled call, verify that the synchronized data update time matches the preset scheduling frequency.

The values provided here are common starting points, and should be evaluated against the organization’s own operational samples.
