# Inspection and Process Record Audit for Equipment Check and Preventive Maintenance: Workflow Orchestration

## What the data for this category looks like
Manufacturing enterprise equipment departments, workshop maintenance teams, and public utility departments provide core data for this category via daily operation and maintenance documents and system data.
Daily documents include equipment ledgers, checklists, maintenance plans, work orders, failure analysis, spare parts lists, and special equipment inspection records.
Fields cover equipment numbers, installation locations, check times, anomaly records, spare part codes, and more.
Data sources include EAM/CMMS systems, equipment sensor data, operator check records, maintenance history, spare parts inventory, and statutory inspection information.
Update frequencies include shift-based, daily, weekly, monthly, and real-time updates when failures occur.

## Constraints on workflow orchestration
Diverse data sources, uneven update rhythms, and rich document fields for this category require workflows to support flexible configuration of multi-data source nodes. This adapts to different access methods for EAM systems, sensor data, and manual check records.
Differences in update frequencies across documents require workflows to have configurable scheduled or event-triggered startup rules. This matches scenarios such as shift-based checks and monthly maintenance.
The complexity of core operation and maintenance links requires workflows to orchestrate branch logic such as hierarchical approval, failure troubleshooting, and spare parts verification. It also requires configuring failure alert nodes to avoid risks such as unplanned downtime.

## How to set configurations
| Configuration Item | Recommended Approach | Basis for This Approach |
| ---- | ---- | ---- |
| `variables` | Preset fields such as equipment number, check cycle, and spare part code according to the equipment ledger | Match the core field structure of daily operation and maintenance documents to enable automatic data mapping |
| Trigger Mode | Scheduled tasks or event triggers, calibrated based on actual measurements | Adapt to business scenarios with different update frequencies, such as shift-based checks and real-time failure reports |
| Node Branch Rules | Divide into 3-level processing logic according to anomaly level | Match the anomaly-level operation and maintenance process for equipment checks |
| Timeout Setting | `600 seconds` | Cover the average response time for equipment failure troubleshooting, to avoid unexpected workflow interruptions |
| Data Mapping Rules | One-to-one correspondence between EAM system fields and workflow variables | Enable unified calling and processing of multiple data sources |
| Alert Node | Push to the corresponding maintenance team group when triggered | Match the equipment operation and maintenance response process to notify anomalies in a timely manner |

## Three Common Mistakes
- Phenomenon: An invalid key error appears when calling an interface. Cause: External interface node configuration used an account key instead of an application key for credential setup.
- Phenomenon: The specified HTML output node has no content during workflow runtime, and the workflow proceeds directly to the next branch. Cause: Incorrect node trigger conditions caused the branch judgment logic to skip the output node execution.
- Phenomenon: The workflow interrupts after exceeding the preset duration. Cause: No reasonable timeout threshold was configured. The default timeout duration is not enough to cover the average time required for equipment failure troubleshooting.

## How to Confirm Proper Configuration
- Use the FastGPT v4.17.0 workflow editor. Check that the `variables` configuration includes core fields such as equipment number and check cycle, and that these match field names in the EAM system.
- Trigger a test workflow. Confirm there are no authorization errors when calling external interfaces. Verify that the key configuration is correct and that an account key was not used.
- Simulate anomaly scenarios of different levels. Check that branch nodes trigger corresponding processing steps according to preset logic.
- View workflow running logs. Confirm that timeout threshold settings meet business requirements, and that there are no abnormal interruption records.
- Configure a test HTML output node. Verify that content displays normally, and that no execution skips occur.
