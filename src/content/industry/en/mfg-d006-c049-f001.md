# Inspection and Process Record Review for In-Process Quality and Finished Product Release: HTTP Interfaces and External Systems

## What this category of data looks like
Data for this category comes from MES systems, online inspection equipment, laboratory test results, process parameter libraries, customer quality standards, and historical defect libraries. Data is updated continuously per production batch and per shift. Daily generated documents include control plans, patrol inspection records, SPC reports, finished product inspection reports, nonconforming product review forms, release forms, and quality monthly reports. Data fields include inspection batch numbers, inspection item parameters, qualified thresholds, defect types, release status, and more. There are no unified fixed units; values change dynamically based on the specific inspection item type.

## Constraints on HTTP Interfaces and External Systems
Multiple data sources require interfaces to adapt to the authentication rules and data formats of different external systems. The batch-based and continuous update rhythm requires interfaces to support both batch pull and real-time push invocation modes. Interfaces must also control invocation frequency to avoid exceeding external system current limit thresholds. Diverse business documents and dynamic field structures require interface request and response parameters to flexibly bind business variables. They must also support field filtering to reduce redundant data transmission. Consequences of errors such as incorrect nonconforming product release require interfaces to have retry mechanisms and exception capture capabilities. This ensures the reliability of data transmission.

## How to Configure Settings
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Carry access credentials in the format `Bearer {token}` | Adapt to the standard authentication requirements of external systems such as MES and inspection equipment |
| `variables` | Bind business variables such as inspection batch numbers, customer standard thresholds, and defect library IDs | Match the dynamic field requirements of in-process quality and finished product release data |
| `responseData` | Only return core fields including inspection results, release status, and defect records | Filter redundant data to meet the field extraction requirements of business documents |
| Request timeout | 600 seconds | Adapt to the full pull and processing duration of batch data per production batch |
| Batch pull limit | Top 500 entries | Match the single data volume scale collected per shift |
| Failed retry count | 3 times | Address scenarios where external systems are temporarily unavailable, ensuring data pull success rate |

## Three Common Configuration Mistakes
- An interface returns the `messages is empty` error. This occurs because required business parameters such as inspection batch numbers are not bound in `variables`, resulting in missing valid business identifiers in the request body.
- The interface returns an empty model stream response. This occurs because the `Authorization` authentication parameter is not configured correctly, causing the external system to refuse to return valid inspection data.
- The number of results returned during batch data pull does not match expectations. This occurs because a reasonable batch pull limit is not set, exceeding the maximum data volume limit for a single return from the external system.

## How to Verify Correct Configuration
- Send a test request and check if the fields returned in `responseData` include business-required content such as inspection items and release status.
- Verify that the `Authorization` parameter is formatted as `Bearer {token}` to confirm that the external system can receive and authenticate the request normally.
- Simulate a request for single-batch inspection data to confirm that the response duration of the interface does not exceed the preset timeout period.
- Compare the pulled data with actual records in the external system to confirm that field matching meets business requirements.
