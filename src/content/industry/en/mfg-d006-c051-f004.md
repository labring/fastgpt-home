# Inspection and Process Record Audit for Metal Cutting Machining: Workflow Orchestration

## What data for this category looks like
Data for this category covers full production process documents for entities including machining factories and precision parts factories. These documents include process routes, operation cards, tool lists, CNC programs, first-piece inspection records, patrol inspection forms, and measuring tool calibration records.
Data sources include product drawings and 3D models, CAPP/CAM systems, machine tool collected data, tool management systems, MES systems, and measuring and inspection tool data. Updates are triggered per work order, per workpiece, during sampling inspection, or when tools are changed.
This configuration is written based on the workflow features of FastGPT v4.17.0.

## What constraints do these characteristics impose on the workflow orchestration link?
Data for this category is multi-source and scattered, with diverse update trigger scenarios. Workflows must adapt to multi-system integration nodes, and bind real-time updated work order and tool wear data.
Processing logic differs significantly across different document types, including CNC programs, inspection records, and 3D models. Configured nodes must distinguish between file types.
Error consequences such as workpiece scrapping and machine tool downtime are severe. Workflows must include embedded verification and retry links.
Core links such as benchmark selection and CNC program verification rely on outputs from preceding nodes. Execution order between nodes must be strictly defined.

## How to set configurations
| Configuration Item | Recommended Approach | Basis for This Approach |
| --- | --- | --- |
| Variable Binding | Bind work order ID, tool number, inspection batch number in `variables` | Matches the data update rhythm triggered by work orders and tool changes for this category |
| File Type Differentiation | Classify and process files based on uploaded file MIME type and file extension | Adapts to the characteristics of this category including multiple document types such as CNC programs, inspection records, and 3D models |
| HTTP Request Wait Duration | 600 seconds | Matches the standard response cycle of machine tool collection and MES systems |
| Retry Mechanism | Retry 2 times after failure, with a 60-second interval | Addresses temporary connection fluctuations in machine tool collection and MES systems |
| Node Identification Configuration | Configure a unique `nodeId` for each core link node | Facilitates troubleshooting of workflow execution exceptions in multi-source data integration scenarios |
| Context Cache | Cache key data of the last 3 inspection records, with a cache duration of 1200 seconds | Meets the traceability requirements of sampling inspection links |

## Three common misconfigurations
- Phenomenon: Uploaded CNC programs in the workflow are mistakenly identified as image files, triggering image format verification failure. Cause: No dual verification rules for MIME type and file extension are configured, only a single condition is used to judge file type.
- Phenomenon: HTTP request body parameters cannot bind `variables` data such as work order ID and tool number, resulting in empty request body fields. Cause: Variables in `variables` are not correctly mapped to corresponding fields in the request body, and variable replacement configuration is not enabled.
- Phenomenon: The configured HTTP request node in the workflow does not execute and directly jumps to the AI chat link. Cause: No pre-trigger conditions are set, or the output of the preceding node is not correctly connected to the input port of the HTTP request node.

## How to confirm proper configuration
- Check variable binding configuration, confirm that fields such as work order and tool in `variables` have been correctly associated with corresponding nodes in the workflow.
- Verify file type differentiation rules: upload sample files such as CNC programs, inspection records, and images to confirm that node trigger logic meets expectations.
- Simulate node failure scenarios to confirm that the retry mechanism triggers according to preset rules, and the workflow exception handling link starts normally.
- Check node connection relationships, confirm that the trigger conditions of the HTTP request node match the output ports of the preceding node, and the execution order conforms to the business process.
