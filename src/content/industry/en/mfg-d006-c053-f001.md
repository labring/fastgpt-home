# Inspection and Process Record Audit for Iron and Steel Smelting and Continuous Casting: HTTP Interfaces and External Systems

## What the data for this category looks like
The inspection and process record audit for iron and steel smelting and continuous casting involves cross-department collaboration. Daily documents include heat plans, batching lists, converter smelting records, composition reports, continuous casting process records, and slab judgment sheets.
Data sources cover hot metal and scrap collection systems, L2 process control systems, laboratory testing systems, MES production management systems, energy medium systems, and equipment condition monitoring systems.
Data updates follow three rhythms: real-time process data for smelting and continuous casting is generated per heat, slab quality judgment results are aggregated per shift, and key indicators are synced in real time.
Data fields include heat number, hot metal weight, smelting duration, casting speed, composition indicators, and more. Units include tons, minutes, meters per minute, and degrees Celsius.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Multiple data sources require interfaces to support cross-system data pulling and pushing, and adapt to authentication and data formats of different systems.
Differentiated update rhythms require interfaces to have flexible triggering mechanisms. These mechanisms support real-time synchronization of L2 process data, and also support batch synchronization triggered per heat or per shift.
The tightly linked document structure requires interfaces to pass associated fields, so that documents across different systems can be matched via identifiers such as heat number.
The characteristics of high-temperature continuous production require interfaces to have high availability. This avoids interrupting production processes due to interface exceptions. It also requires data integrity verification to prevent incorrect data from causing heat downgrades or scrap.

## How to set the configurations
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer ${token}, valid for 1 hour` | Adapts to the authentication rules of steel plant L2 systems, prevents interface call failures caused by authentication expiration, and complies with FastGPT v4.17.0 authentication logic |
| `variables` | `Includes heat number, casting speed threshold, composition indicator range, calibrated based on actual measurements` | Passes business variables unique to this category, enabling associated matching of documents across different systems |
| `responseData` | `Only returns non-empty fields for valid heats, filters out abnormal data` | Reduces invalid data transmission, improves the efficiency and accuracy of the audit process |
| Retry Count | 3 times, 10-second interval | Addresses temporary network fluctuations or system delays, ensures data synchronization is not interrupted in high-temperature production scenarios |
| Trigger Timing | After each heat finishes smelting, before shift aggregation | Matches the update rhythm of this category, ensures audit data is synced to target systems in a timely manner |

## Three common mistakes
- The interface returns a `401 Unauthorized` status code. This occurs because the `Authorization` token is not updated per the L2 system's authentication cycle, leading to authentication failure.
- The synced slab judgment sheet has empty fields. This occurs because the heat number is not correctly passed as a `variables` parameter, so the corresponding heat's smelting record cannot be matched.
- The interface call times out. This occurs because no reasonable timeout threshold is set. The batch data response delay of steel plant L2 systems exceeds the default call duration, creating a risk of production process interruption.

## How to confirm the configuration is properly set
- Call the test interface, check if the fields returned in `responseData` include heat-specific content such as heat number and smelting duration. Adjust the field filtering rules to meet business requirements.
- Simulate an interface trigger after a heat finishes, verify that the validity period of the `Authorization` token matches system requirements. Adjust the refresh cycle to fit actual scenarios.
- Check the interface call logs, confirm that the retry count matches the preset configuration. Troubleshoot whether the automatic retry logic works during temporary network fluctuations.
- Compare heat records in the MES system with data synced via the interface, confirm that associated fields match correctly. Adjust the passing rules for `variables` parameters.
