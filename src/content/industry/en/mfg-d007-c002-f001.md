# Production Ledger Summary and Report Generation for SMT Mounting and Electronic Assembly: HTTP Interfaces and External Systems

## What the data for this category looks like
The production ledger for this category covers BOM and coordinate files, line change lists, stencil and furnace temperature records, first article confirmation reports, SPI/AOI inspection reports, maintenance records and traceability labels, and more. Data sources include BOM and Gerber files provided by customers, as well as real-time collected data from MES systems, solder paste and component batch ledgers, mounters, SPI/AOI equipment, and reflow ovens.
Data is updated in real time alongside work order execution and line change operations. Ledger data associated with a single work order includes fields such as part number, reference designator, component batch, furnace temperature parameters, defect type, and more. Some fields must strictly match the original BOM format provided by the customer.

## What constraints do these characteristics impose on the "HTTP Interfaces and External Systems" link
The scattered data sources and real-time update requirements of this category require HTTP interfaces to support high-frequency concurrent calls to match the real-time synchronization rhythm of work orders and line changes.
Field differences from multiple document types require the interface to support multi-field verification logic, to ensure core fields such as part number and reference designator match the customer’s BOM.
The real-time update feature requires the interface timeout setting to adapt to equipment collection delays. It also requires support for a failure retry mechanism to avoid missing ledger data caused by a single failed call.
In addition, errors in core data will trigger batch production issues. The interface must have idempotence to prevent exceptions caused by repeated submissions.

## How to Set Configuration Parameters
This configuration is explained based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer ${apiKey}, validity period determined via actual testing` | Complies with HTTP interface authentication standards, and adapts to internal interface permission control for EMS factories |
| Request Timeout | `30–60 seconds` | Adapts to collection delays from reflow ovens and SPI equipment, preventing call failures due to slow device responses |
| `variables` | Includes core fields such as work order ID, part number list, equipment ID, etc. | Matches the associated query requirements for production ledgers, ensuring the interface can accurately pull all data for the corresponding work order |
| `responseData` | Only return ledger fields that have passed verification, filter invalid data | Reduces data processing burden on external systems, and complies with structured storage requirements for SMT ledgers |
| Retry Count | `2–3 times` | Addresses temporary network fluctuations or short-term equipment offline scenarios, preventing a single failed call from interrupting production ledger summary |

## Three Common Misconfigurations
- A 404 status code is returned by the interface. The cause is that the interface URL does not match the actual deployment path of the internal MES system of the EMS factory, or the work order ID carried in the parameters does not match the format expected by the system.
- The `responseData` field returned by the interface is empty. The cause is that core associated fields were not passed in `variables`, causing the interface to fail to locate the corresponding production ledger data.
- A red numeric error appears after the call. The cause is that the `Authorization` parameter format is incorrect, a valid API key was not carried correctly, or the key has insufficient permissions to access the target data.

## How to Confirm the Configuration is Valid
- Call the test interface, pass in the `variables` parameter for a simulated work order, and check if the returned `responseData` includes the preset core ledger fields.
- Simulate a single failed call, check if the interface triggers the retry mechanism, and confirm that the number of retries meets the configured requirements.
- Compare the interface returned data with the original ledger exported from the MES system, and confirm that the field matching degree complies with the preset verification rules.
- Replace the invalid `Authorization` parameter, confirm that the interface returns a corresponding authentication failure prompt, and verify that the authentication configuration is effective.
