# Production Ledger Summary and Report Generation for Photovoltaic Module Encapsulation: Model Access and Configuration

## What the data for this category looks like
Data sources for the photovoltaic module encapsulation process include the cell grading system, glass adhesive film and backplane batch ledgers, the workshop MES system, data collected from string welding and lamination equipment, and output reports from EL/IV testers. Data updates follow a schedule where a unique ledger record is generated for each module, and batch information is updated synchronously for each batch of raw materials. Daily documents include layout drawings, material batch records, lamination process parameter records, EL defect images, IV test reports, insulation and voltage withstand test records, and finished product packing lists. Fields covered include module number, cell current grade, lamination temperature and duration, crack location grade, power value, voltage withstand value, and more.

## What constraints these characteristics impose on model access and configuration
This category has high data update frequency and small per-record size, so model access configuration must adapt to real-time small-batch data processing to avoid context overflow. Multiple types of documents coexist, including structured parameter records and image-based EL defect images, so model capabilities that support visual recognition must be configured. Professional fields such as cell current grade and lamination process parameters require the model to accurately identify and match them, so configuration must ensure the model’s understanding accuracy of electronic manufacturing terminology. Data sources are scattered and field standardization varies, so data mapping rules must be clearly defined during configuration to reduce subsequent summary errors.

## Three Common Configuration Mistakes
- Phenomenon: After deploying a rerank model, the corresponding model option does not appear in the FastGPT platform. Cause: The rerank model access configuration was not correctly added to the system configuration file, or the deployment address was not added to the allowed access whitelist.
- Phenomenon: After configuring the model as the v2 version, the actual call still uses the v1 version. Cause: The model name selected on the platform does not match the model name registered in the configuration file, or the configuration file was not correctly reloaded to take effect.
- Phenomenon: After deploying the model intranet, the service process restarts repeatedly. Cause: Correct network access permissions were not configured in the intranet environment, causing external resources relied on by the model to fail to load, or insufficient memory allocation in the startup parameters.

## How to Confirm Successful Configuration
- Enter the FastGPT model management page, view the list of connected models, and confirm that the target model is displayed normally.
- Initiate a simulated call, input test data containing EL image parameters and lamination records, and check whether the output result includes accurate summary of the corresponding fields.
- View the platform logs, confirm that the parameters of the model call request match the configured items, with no missing or incorrect parameters.
- Test model call connectivity in the intranet environment, confirm that the request can normally reach the deployment address and return valid results.
