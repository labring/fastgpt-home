# Cosmetics Production Ledger Summary and Report Generation: HTTP Interfaces and External Systems

## What this category's data looks like
Data for this category originates from registered or archived formulas, raw material safety documents, weighing and emulsification equipment, ERP/MES systems, laboratory test data, and packaging material version files.
Daily documents include formula process sheets, weighing and feeding records, emulsification or filling records, cleaning and site clearance records, semi-finished and finished product inspection records, and label review documents.
Data updates occur with each production batch or each line change.
Fields include raw material batch numbers, feeding quantities, production batch numbers, restricted substance content, test indicator values, packaging material version numbers, and other fields that must align with archived information.

## Constraints for HTTP Interfaces and External Systems
Data for this category updates per production batch or line change, and must strictly match archived information. This creates multiple constraints for HTTP interfaces.
Interfaces must use production batch numbers or line change times as triggers to pull data. This avoids repeated pulls of full historical data.
Transmitted fields must include restricted substance content, label claim content, and other fields aligned with archived information. This ensures data compliance.
Interfaces must integrate structured data from multiple sources. They must accept standardized data from equipment, ERP, laboratory, and other systems. They must validate consistency across fields from different sources to prevent data conflicts that reduce ledger accuracy.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| Authentication Method | Use `Authorization` header with Bearer token | Complies with FastGPT v4.17.0 interface call specifications, ensures secure data transmission |
| Trigger Parameters | Pass production batch numbers, line change times as `variables` | Accurately locates production ledger data for the target batch, avoids pulling irrelevant data |
| Response Data Format | Fixed JSON structured format | Enables quick parsing of multiple field types including formulas, inspection records, and feeding data |
| Response Field Filtering | Only return archived matching fields in `responseData` | Reduces invalid data transmission, improves interface call efficiency |
| Timeout Duration | Set based on actual measurements (recommended 60-120 seconds) | Accommodates time spent integrating data from multiple sources, prevents call failures from data pull delays |
| Request Retry Policy | Retry 2 times when 5xx status codes are received | Addresses temporary fluctuations in external systems, ensures stable data pulling |

## Three Common Mistakes
- Scenario: Each interface call returns independent results with no contextual connection between requests. Cause: No session identifier parameter is included in requests. Each call is treated as a new session, so historical ledger data cannot be reused.
- Scenario: The `responseData` field in the response contains formula fields that do not match archived information. This leads to failed ledger audits. Cause: No response field filtering rule is configured. Non-compliant data outside the archived range is returned.
- Scenario: Interface calls return a 402 status code with an insufficient quota prompt. Cause: No request frequency control is configured, and no enterprise-owned API quota monitoring is linked. Exceeded quota triggers deduction fees.

## How to Confirm Configuration Is Complete
- An interface request triggered by a production batch number is initiated. The request header is checked for `Authorization` authentication information to confirm authentication configuration is active.
- The `responseData` field in the response body is reviewed. Only archived matching ledger fields are confirmed to be included, validating that field filtering configuration is active.
- Two consecutive interface requests for the same batch are simulated. The second request is checked to confirm it reuses context data from the first request, validating that session configuration is active.
- Interface call logs are observed. Automatic retries are confirmed to occur when 5xx status codes are received, validating that exception handling configuration is active.
