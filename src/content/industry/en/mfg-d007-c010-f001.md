# Production Ledger Summary and Report Generation for Medical Device Assembly and Clean Production: HTTP Interfaces and External Systems

## What data for this category looks like
Core data for this category comes from design history files, device and material batches, MES systems, clean environment monitoring equipment, sterilization equipment, inspection and calibration systems. Daily generated documents include production process procedures, batch production records, clean area records, sterilization batch records, inspection reports, software version records, adverse event and traceability materials. Data update frequency is once per batch or per product unit. Clean area monitoring data is updated on a fixed schedule. Data fields include device unique identifiers, batch numbers, clean environment parameters, sterilization parameters, inspection results, and more. Some fields must match the fixed format required for medical device traceability requirements.

## What constraints these characteristics impose on HTTP interfaces and external systems
Data sources for this category are scattered and diverse in type. Interfaces must support multi-source data pulling and field mapping to avoid ledger summary errors caused by inconsistent data source formats. Data update frequency is strongly tied to production batches. Interfaces must support on-demand triggering or timestamp-filtered pulling methods to adapt to ledger generation requirements for single batches or single product units. Medical device traceability requirements mandate that core fields cannot be missing. Interfaces must have basic field verification capabilities to ensure complete return of traceability-related data. Different batches’ ledger data must be strictly differentiated to avoid cross-batch data confusion. Interfaces must support precise data filtering by batch identifiers. Associated data has a high risk level. Interface transmission must ensure authentication security to avoid leakage of sensitive production data.

## How to set up the configuration
This configuration applies to FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {Enterprise-specific API key}` | Complies with FastGPT interface authentication specifications to ensure secure transmission of production data |
| `variables` | `{"batchNo": "", "cleanAreaParams": [], "sterilizationBatch": ""}` | Matches the core retrieval and filtering fields of medical device ledgers, enabling precise pulling of production data for the corresponding batch |
| `responseData` | `Structured array containing batch production records, clean area parameters, sterilization parameters, and device unique identifiers` | Covers all ledger and report fields required for this category, meeting traceability requirements |
| Single request data limit | `Top 20 entries` | Matches the ledger data volume for a single batch or single product unit, avoiding interface overload |
| Request timeout threshold | `30–60 seconds` | Covers the data pulling time of sterilization equipment and clean monitoring systems, avoiding request interruptions |

## Three common mistakes
- The ledger data returned after calling the interface is missing the device unique identifier. The cause is that the mapping rules for traceability fields were not configured in `responseData`, resulting in core traceability data not being extracted.
- The interface callback result does not include thought process content. The cause is that the thought process return parameter was not enabled in the request configuration, and only the final conversation result was returned.
- The interface call returns a 401 authentication failure. The cause is an incorrect `Authorization` parameter format, where the Bearer prefix was not used to concatenate the enterprise-specific API key.

## How to confirm the configuration is complete
- Call the test interface with the correct `Authorization` parameter, confirm that the return status code is 200 and there are no authentication-related errors.
- Initiate a request with the `variables` parameter, verify that the returned `responseData` includes core fields such as batch production records and sterilization parameters for the specified batch.
- Simulate a production batch to trigger interface pulling, confirm that the returned data update time matches the production time of the corresponding batch.
- Check the content received by the callback interface, confirm that it includes the complete ledger report structure and required fields.

The values provided are common starting points and should be measured against the reader's own samples.
