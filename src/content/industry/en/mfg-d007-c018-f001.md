# Aggregation of Production Logs and Report Generation for Continuous Basic Chemical Production: HTTP Interfaces and External Systems

## What the data for this category looks like
Data logs for continuous basic chemical production originate from DCS/SIS systems, online analyzers, LIMS systems, equipment condition monitoring tools, energy metering devices, and raw material tank sensors.
Data update cadences fall into three categories: real-time (for process parameters), shift-based (for shift reports and interlock bypass records), and daily (for summary reports).
Daily documentation covers operating procedures, process indicator cards, DCS trend charts, laboratory reports, special work permits, interlock bypass records, and shift reports.
Data fields include real-time process parameter values, cumulative flow rates, equipment operating status, and laboratory indicator values. Most units use industrial standard measurements such as Nm³/h, MPa, and wt%.

## Constraints on HTTP Interfaces and External Systems
Multi-source heterogeneous data and varied update frequencies for this category require HTTP interfaces to support multi-endpoint calls and scheduled trigger logic.
Real-time process data requires high-frequency interface calls. Shift-based and daily summary documents require requests to be triggered on fixed cycles.
Multiple data sources create a need for multiple interface authentication and parameter adaptation workflows. Dimension variables such as equipment and shift must be bound.
Diverse document types require filtering of non-log data. Transmission accuracy for parameters related to strong interlocks must be maintained to prevent production risks caused by incorrect parameters.

## Configuration Settings
All configuration examples below are based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {Chemical System Exclusive API_KEY}` | Complies with authentication standards for industrial external systems, and ensures legitimacy of interface calls |
| `variables` | `{"device_id": "Chlor-Alkali Unit T01", "time_range": "8h"}` | Matches the device dimension and time window of basic chemical production logs, to accurately extract corresponding production data |
| `responseData` | `["dcs_trend", "lab_report", "shift_report"]` | Filters and extracts core log documents for this category, to reduce invalid data transmission |
| Retry policy | 3 attempts, 60 second interval | Addresses call failures caused by network fluctuations and MongoDB replica set primary node switches |
| Scheduled trigger cycle | 15 minutes (real-time data), 8 hours (shift reports), 24 hours (daily reports) | Matches the actual update frequency of data for this category, to avoid invalid calls |

## Three Common Configuration Errors
- Interface calls return the error `400 InternalError.Algo.InvalidParameter: Multimodal file size is`. This occurs when size restrictions are not set for large attachments such as DCS trend charts and laboratory reports, leading to exceeded parameter limits.
- Interface calls fail continuously. Logs show MongoDB connection timeouts. This occurs when a reconnection mechanism is not configured for MongoDB Change Streams, preventing automatic connection recovery after a primary node drift.
- Business numeric fields in the HTTP request body are empty. This occurs when log values such as equipment operating parameters and laboratory indicators are not correctly bound in `variables`, leading to failure to pass parameters into the request.

## How to Confirm Correct Configuration
- Initiate a single test call, and verify that the `Authorization` field in the request header follows the `Bearer {API_KEY}` format specification.
- Review the request body content, and confirm that the device ID and time range bound in `variables` match the production log dimensions.
- Verify that the content returned in `responseData` includes expected basic chemical production log documents such as DCS trends, laboratory reports, and shift reports.
- Simulate a MongoDB primary node switch scenario, and confirm that interface calls can automatically retry and restore normal connections.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
