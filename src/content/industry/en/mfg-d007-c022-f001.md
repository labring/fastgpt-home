# Production Ledger Summary and Report Generation for Complete Home Appliance Manufacturing: HTTP Interfaces and External Systems

## What this category’s data looks like
Production ledger data for complete home appliance manufacturing includes configuration BOMs, assembly work instructions, refrigerant charging records, electrical safety test reports, random performance inspection results, and repair records. Data sources cover ERP/MES systems, component batch ledgers, tightening and charging equipment, safety compliance testers, performance laboratory data, and after-sales fault records.

Data updates follow individual products, shift production batches, or random inspection plans. Charging and test records for single devices are generated in real time. Batch random inspection reports are summarized periodically. Repair records are updated synchronously with after-sales feedback.

Fields include product model, batch number, process parameters, test results, repair reasons, and more. Some process data requires specific units: refrigerant charging volume is measured in grams, and tightening torque is measured in newton meters.

## Constraints imposed on HTTP interfaces and external systems by these characteristics
Multi-source heterogeneous data sources for complete home appliance manufacturing require HTTP interfaces to support non-standard HTTP request formats from industrial equipment and standard interface protocols from ERP/MES systems.

Differentiated update cycles (per single product, per shift batch, per random inspection plan) require interfaces to support both incremental synchronization and batch pull modes. This adapts to transmission needs for different data volumes.

For sensitive process data such as refrigerant charging and electrical safety testing, interfaces must use the `Authorization` parameter for permission verification to ensure data transmission security.

Significant field differences exist across different business documents. For example, charging records require floating-point numeric fields, while repair records require text remark fields. Interfaces must support custom field mapping to prevent synchronization failures caused by format incompatibility.

## Configuration settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Carry a Bearer token, set validity period to 3600 seconds | Adapt to the permission verification cycle of industrial systems, avoid frequent token refreshes that impact synchronization efficiency |
| `responseData` | Return only core business fields, filter redundant metadata | Reduce interface transmission traffic, adapt to synchronization requirements for large-volume ledger data |
| Maximum number of data per single request | First 500 entries | Prevent excessive data volume in a single request from causing timeouts, comply with interface bandwidth limits of industrial equipment |
| Interface timeout period | 600 seconds | Adapt to time-consuming report pull scenarios such as safety compliance testing and performance laboratory work |
| `variables` | Bind product model and batch number as query variables | Accurately pull production ledger data for the corresponding model, avoid interference from mixed-line data |
| Field mapping rules | Match field names and types according to business document definitions | Adapt to field differences across different documents, ensure accurate data synchronization |

## Three common configuration errors
- Symptom: Interface calls return "Request failed with status code 400". Cause: The `Authorization` parameter is not configured correctly, or request fields do not match required items from business documents, such as missing the product batch number field.
- Symptom: Interface calls frequently stall or time out. Cause: A reasonable maximum number of data per single request is not configured, or the request retry mechanism is not enabled, making it unable to handle network fluctuations.
- Symptom: "getaddrinfo EAI_AGAIN" error appears in logs. Cause: A stable proxy node is not configured, or domain name resolution for the proxy node has failed, preventing normal connection to the target system.

## How to confirm correct configuration
- Initiate an interface request for a single data entry, verify that the returned `responseData` includes the core fields required by the business document, and that field types and units match.
- Call the batch pull interface, check that the transmitted data volume matches the configured maximum number of data per single request.
- Simulate network fluctuations, verify that the interface can complete the request within the configured timeout period, or trigger the preset retry mechanism.
- Check the validity of the `Authorization` parameter, confirm that no permission-related error messages are present.
