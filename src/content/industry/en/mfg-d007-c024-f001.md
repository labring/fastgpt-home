# Production Ledger Summary and Report Generation for Process Changes and Engineering Changes: HTTP Interfaces and External Systems

## What Data for This Category Looks Like
The data for this category comes from PLM, ERP, MES, supplier materials, validation test records, and customer special requirement documents. Daily produced documents include ECN/ECR forms, change assessment reports, drawings and BOM version records, process validation reports, production switching plans, inventory disposal documents, and customer approval documents. Data updates have no fixed cycle. They trigger every time a process or engineering change occurs. They are maintained by a cross-departmental change management team. Fields include change number, version number, impact scope, validation status, switching node, and others. There are no unified fixed units. Values adjust based on the associated document type.

## Constraints for HTTP Interfaces and External Systems
Multiple data sources require the interface to be compatible with return formats from different external systems. The interface must support parsing structured BOM data from PLM, inventory information from ERP, and production progress data from MES. Non-fixed update cycles require the interface to support on-demand pull requests. This adapts to temporary data synchronization needs triggered by changes. Diverse document types require the `responseData` returned by the interface to be compatible with multiple field structures. No unified field template is enforced. Additionally, the version correlation of change data requires the interface to carry version verification parameters. This ensures that synchronized ledger information uses the currently valid version, avoiding the risk of mixing old and new versions.

## How to Configure Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Maximum data volume per request | 1000–1500 entries | Adapts to the single-batch synchronization scale of ECN/ECR forms, avoiding request timeouts |
| Timeout threshold | 600 seconds | Adapts to the time requirements of cross-system multi-source data pulls, ensuring complete data retrieval |
| Maximum request body size | 1000 MB | Adapts to synchronization needs for large drawing attachments, avoiding request truncation |
| `Authorization` authentication configuration | `Bearer {API key generated by FastGPT v4.17.0}` | Complies with the HTTP interface authentication specifications of FastGPT v4.17.0, ensuring secure docking permissions |
| `responseData` field filtering rules | Only retain validated change ledger data | Filters invalid data, reducing storage and processing pressure on external systems |
| `variables` binding parameter configuration | Change number, version number, impact scope | Accurately matches core query dimensions for change ledgers, supporting targeted pulls of target change data |

## Three Common Configuration Errors
- Calling the interface returns a 503 status code, prompting that there are no available resources in the current group. Cause: The service group for corresponding change data pulls is not bound in the interface configuration, causing the request to fail to match available connected resources.
- The ledger data returned by the interface includes old version change records. Cause: No version filtering rules for `responseData` are configured, synchronizing old data that has not been switched to the valid version.
- After cross-system docking, the external system receives incomplete change documents. Cause: The maximum data volume per request is set too small, not adapting to the scale of ECN/ECR forms for batch synchronization, resulting in data truncation.

## How to Confirm the Configuration Is Correct
- Call the test interface, check that the `responseData` returned only includes validated change ledger data, and verify that the fields match the associated document structure.
- Simulate a data synchronization triggered by a change, confirm that the interface returns a 200 status code, with no permission or timeout errors.
- Verify that the `Authorization` configuration key matches the docking key generated by the FastGPT platform, confirming that permission verification is effective.
- Adjust the query dimension parameters bound to `variables`, confirm that target change ledger data can be accurately filtered.
