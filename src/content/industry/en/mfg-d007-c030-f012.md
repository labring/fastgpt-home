# Production Ledger Summary and Report Generation for Rubber Mixing and Product Vulcanization: Deployment and Upgrade

## What the data for this category looks like
Production data for this category comes from formula systems, raw material batch ledgers, internal mixers, Mooney rheometers, vulcanizing machines, and laboratory testing equipment. Daily generated documents include formula sheets, weighing records, mixing curves, rubber compound quick test reports, vulcanization process cards, mold usage records, and finished product performance reports. Data fields include raw material batch numbers, mixing temperatures, vulcanization durations, finished product tensile strength, and more. Units include degrees Celsius, minutes, MPa, and others. Data is updated for each batch of rubber, each batch of raw materials, and each molded product. Single data volume ranges from tens of KB to several MB, and overall data volume grows linearly with production scale.

## What constraints these characteristics impose during deployment and upgrade
High-frequency single-data updates require deploying storage connections configured to support high-concurrency read/write operations, to avoid data synchronization delays that affect ledger real-time performance. Multi-source heterogeneous data sources require preset data mapping rules, to ensure log formats from different devices are unified before connecting to the ledger system, reducing subsequent parsing and summary workload. Diverse document types require adapting to different file parsing formats, to avoid parsing failures caused by format differences between formula sheets, mixing curves, and other files. At the same time, errors in this category’s data can lead to product scrap or unqualified performance. Deployment requires configuring permission control mechanisms to prevent unauthorized modification of ledger content. Upgrades require retaining the immutability of historical data, to ensure the accuracy of production traceability.

## Three common mistakes
- A `400 Bad Request` error is returned after uploading a mixing curve PDF or formula sheet, indicating file parsing failure. The cause is that `FILE_TOKEN_KEY` is not configured, leading to failed file upload permission verification, preventing file synchronization to the storage service corresponding to `STORAGE_S3_ENDPOINT`.
- New users cannot complete registration after deployment, with the interface prompting "Registration interface not enabled". The cause is that the user registration-related configuration switch is not enabled during open-source deployment, and system permission-related parameters are not correctly configured.
- Knowledge base retrieval cannot match weighing records for a specified batch, with the number of retrieval results far fewer than the actual number of ledger entries. The cause is that `DB_MAX_LINK` is set too small, exhausting the database connection pool, leading to partial batch data not being synchronized to the knowledge base index.

## How to confirm configurations are correct
- Access the frontend address corresponding to `FE_DOMAIN`, confirm that the ledger summary page loads normally, with no loading failures or resource 404 errors.
- Upload a real mixing curve PDF file, confirm that mixing temperature, duration, and other fields are correctly extracted after parsing, with no empty or garbled data.
- Run a ledger generation task, confirm that the generated report includes corresponding fields from formula sheets, weighing records, and vulcanization process cards, with data consistent with source documents.
- Check the connection logs for `REDIS_URL`, confirm no continuous connection timeouts or authentication failure errors, with the caching service running normally.
- Check the database connection logs for `MONGODB_URI`, confirm no connection failures or authentication errors, with ledger data synchronization working normally.
