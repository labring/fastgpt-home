# Heat Treatment Production Ledger Summary and Report Generation: HTTP Interfaces and External Systems

## What data for this category looks like
Data for this category originates from material grades, customer technical specifications, temperature control instruments, furnace temperature uniformity testing equipment, hardness testers and metallographic equipment, and factory MES systems. Daily generated documents include heat treatment process cards, charging charts, furnace temperature curves, hardness and metallographic reports, equipment inspection forms, and exception handling sheets.
Data is updated per furnace charge and per batch. A single data entry includes fields such as process parameters, furnace temperature curve segments, hardness and metallographic test results, and exception handling records. Field units include degrees Celsius, megapascals, micrometers, and other standard units. Some fields require association with customer technical specifications for compliance verification.

## Constraints for HTTP Interfaces and External Systems
Data for this category is updated at high frequency per furnace charge and per batch. A single data entry includes multi-dimensional parameters and test results. HTTP interfaces must support both single furnace charge and batch call modes to avoid single request timeouts.
Data comes from multiple types of equipment and systems, so heterogeneous formats must be unified. Interfaces must carry verification fields in requests to filter invalid data.
Different types of heat treatment documents correspond to differentiated data structures. `responseData` must split fields by document type to allow downstream systems to directly parse and store the data.
Data association relationships are complex, so interfaces must support passing association parameters to ensure the accuracy of ledger summary.

## Configuration Settings
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {enterprise-specific API key}` | Complies with HTTP interface authentication specifications, and adapts to the external API call authentication configuration of FastGPT v4.17.0 |
| `variables` | `{"furnaceId": "string", "batchNo": "string", "testDate": "date"}` | Matches the core identification and time fields of heat treatment ledgers, facilitating downstream system association and classification |
| `responseData` | Split fields by process card, furnace temperature curve, and test report | Matches the document structure of this category, facilitating direct storage and display by downstream systems |
| Request timeout | 600 seconds | Covers the average time required for single furnace charge data collection, summary, and report generation |
| Batch request limit | First 20 entries | Balances interface load and data summary efficiency, calibrated based on actual measurements |
| Data verification switch | Enabled | Filters invalid furnace temperature curve and test result data to ensure ledger accuracy |

## Three Common Mistakes
- Phenomenon: The interface returns an empty `responseData` field. Cause: Returned fields are not split by document type such as process cards and furnace temperature curves for this category, so downstream systems cannot recognize valid data structures.
- Phenomenon: The interface returns a 401 Unauthorized status code. Cause: The `Authorization` parameter does not include the `Bearer ` prefix, or an expired API key is used.
- Phenomenon: Batch requests trigger timeout errors. Cause: The configured request timeout is shorter than the time required for collection and summary of batch furnace charge data, so complete ledger generation cannot be completed.

## How to Confirm Proper Configuration
- Initiate a single furnace charge test request, check whether `responseData` includes the three core fields of process card, furnace temperature curve, and test report.
- Verify the authentication effect of the `Authorization` parameter, confirm that the interface returns a 200 status code and no authentication-related errors.
- Adjust the batch request limit and timeout time, confirm that the interface responds stably within the range that matches the business load through multiple tests.
- Compare the consistency between the interface returned data and the local ledger fields, ensure that the values of the `variables` parameter correctly match the business identifiers.

The values provided are common starting points and should be measured against the reader's own samples.
