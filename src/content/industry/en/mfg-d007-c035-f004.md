# Heat Treatment Production Ledger Summary and Report Generation: Workflow Orchestration

## What This Category of Data Looks Like
This category of data comes from material grade archives, customer technical requirement documents, temperature control instrument collection data, furnace temperature uniformity test reports, output results from hardness testers and metallographic testing equipment, and workshop MES systems. Daily generated documents include heat treatment process cards, furnace loading layout drawings, real-time furnace temperature curves, hardness and metallographic test reports, equipment inspection records, and exception handling documents. Data is updated per furnace heat and per production batch. A single record includes fields such as process parameters, furnace heat number, test values, and exception situations. Units include degrees Celsius, HV hardness values, hours, and others.

## Constraints Imposed on Workflow Orchestration
This category of data is updated in batches per furnace heat and has diverse types. Workflows must support single-furnace-heat trigger execution to avoid mixing data across batches. Multiple types of documents are input together, so nodes must be split by document type to process structured and unstructured data separately. Data sources include manually entered process cards and automatically collected instrument data, so both data reading methods must be supported. Single-furnace-heat data is updated frequently but each record has a small volume, so workflows must be configured lightly to avoid excessive resource usage. Exception handling documents must be linked to the original furnace heat data, so furnace heat IDs must be retained as associated fields to ensure data traceability.

## Configuration Settings
The following configurations are based on the FastGPT v4.17.0 workflow editor.

| Configuration Item | Recommended Setting | Rationale for This Setting |
| --- | --- | --- |
| Variable Definition | Bind `variables` to furnace heat ID, process parameters (unit: degrees Celsius), test results (unit: HV) | Matches the unique identifier per furnace heat to ensure data from different furnace heats is not mixed up |
| Node Trigger Condition | Triggered by a single-furnace-heat submission event | Corresponds to the update frequency of data per furnace heat, avoids data disorder caused by batch processing |
| Data Association Rule | Bind `nodeId` to the furnace temperature curve reading node and hardness test node | Ensures temperature control data and test data from the same furnace heat are accurately associated |
| Timeout Setting | 1200–1500 seconds, calibrated based on actual measurements | Covers the longest time required for furnace temperature curve reading, equipment data pulling, and report generation |
| Result Output Format | Generate a PDF document containing furnace heat number, process parameters, and test report, with a single document no more than 20000 characters | Matches the delivery requirements of daily workshop ledgers and reports |

## Three Common Configuration Mistakes
- Text content extraction nodes return empty results. The symptom is that the heating temperature field in the process card is not extracted. The cause is that the associated `variables` parameter of the text extraction node is not configured, so the target extraction field is not specified.
- Subsequent nodes do not execute after calling a sub-workflow. The symptom is that after the user selection node of the sub-workflow is completed, the parent workflow has no subsequent processing logs. The cause is that the return parameter transfer of the sub-workflow is not configured, so the parent workflow cannot continue execution.
- Workflow execution is terminated due to timeout. The symptom is that the interface displays execution timeout status code 504. The cause is that the set timeout period is shorter than the total time required for furnace temperature data collection and report generation.

## How to Confirm the Configuration Is Correct
- Import test data for a single furnace heat, run the workflow, and check if the output report includes all preset fields.
- Trigger a sub-workflow call, confirm that the parent workflow continues to execute subsequent nodes after the sub-process is completed.
- Simulate abnormal data input, check if the workflow triggers the exception handling node as configured.
- View the workflow logs, confirm that both the `variables` and `nodeId` parameters are correctly bound to the corresponding data.

The values given are common starting points and should be measured against the reader's own samples.
