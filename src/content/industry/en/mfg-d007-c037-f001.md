# Production Ledger Summary and Report Generation for Production Planning and Shop Scheduling: HTTP Interfaces and External Systems

## What data falls under this category
This category covers daily production documents including sales orders, master production schedules, material requirements plans, daily and weekly scheduling sheets, work orders, material shortage lists, and delivery change notices. Data is sourced from ERP orders and inventory, BOMs and process routes, equipment capacity, staff shifts, work-in-progress, and supplier delivery information.
Data updates follow daily and weekly periodic cycles, plus real-time updates when orders are created or exceptions occur.
Fields include order numbers, material codes, capacity values, shift time periods, work-in-progress quantities, and more. Units include pieces, hours, sets, batches, and others. The field combination logic for different documents changes based on production process nodes.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Multi-source, heterogeneous data sources require HTTP interfaces to support parallel calls to multiple endpoints, adapting to the return formats of different ERP and equipment systems.
High-frequency or real-time updated data requires the interface to set reasonable timeout thresholds, preventing data lag that impacts scheduling decisions.
Differences in field combination logic across production documents require the `responseData` parameter to support dynamic field mapping, without hardcoding fixed field structures.
Update requests triggered by exceptions require the interface to support event-driven calls, adapting to on-demand synchronous needs.
The interface must return clear status codes and error messages to quickly locate issues such as data anomalies and insufficient permissions, reducing response delays for scheduling adjustments.

## How to configure settings
| Configuration Item | Recommended Setting | Rationale |
|---|---|---|
| `Authorization` | `Bearer {enterprise-specific API key}` | Follow HTTP interface authentication standards to ensure the legality of external system calls, and match internal enterprise permission control rules |
| `variables` | `{"start_date": "00:00 on the current day", "end_date": "24:00 on the current day"}` or set according to business cycles | Adapt to the requirement of summarizing production ledgers by time range. Dynamic variables such as scheduling cycles and work order numbers can be passed to enable flexible ledger generation |
| `responseData` | Only return fields including order number, work order status, capacity utilization rate, and delivery deviation rate | Filter redundant data, reduce interface transmission load, match the core field requirements of production ledger summary, and facilitate subsequent report generation |
| Interface timeout period | `30-60 seconds` | Adapt to the time consumption of multi-source data pulling, avoid overall interface timeout caused by single-node delay, and ensure the integrity of scheduling data |
| Authentication refresh rule | Calibrated based on actual testing | Adapt to the authentication system of existing enterprise external systems, ensure the security and compatibility of interface calls |

## Three common configuration mistakes
1. Phenomenon: The interface returns a `401 Unauthorized` status code, and production data cannot be obtained. Cause: The `Authorization` parameter is not configured correctly, an expired API key is used, or enterprise authentication rules are not followed.
2. Phenomenon: The generated production report does not include core document content such as material shortage lists and delivery change notices. Cause: Filter conditions for corresponding documents are not passed through the `variables` parameter, or the `responseData` parameter filters non-predefined fields, missing key business data.
3. Phenomenon: After calling database data via Function CALL, the large language model cannot return original database text fragments. Cause: The original data return setting is not enabled in the interface configuration, or the queried original data fields are not mapped to context variables, preventing the large language model from obtaining original fragments.

## How to confirm correct configuration
- Call the test interface, check the returned authentication status code, and confirm that the `Authorization` configuration takes effect.
- Pass preset time range variables, verify that the returned `responseData` fields include core data such as production plans and work orders, and confirm that the dynamic variable configuration is correct.
- Simulate an exception trigger scenario, such as passing a non-existent work order number, check whether the interface returns clear error information, and confirm that the exception handling configuration is valid.
- View the interface logs in FastGPT v4.17.0, confirm that the call duration meets the preset timeout threshold, and confirm that the timeout configuration takes effect.
