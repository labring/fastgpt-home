# Production Ledger Summary and Report Generation for Production Planning and Shop Scheduling: Workflow Orchestration

## What this category’s data looks like
Typical business data comes from ERP orders and inventory, BOM, process routes, equipment capacity, staff shifts, work in progress, and supplier arrivals. Daily documents include sales orders, master production schedules, material requirements plans, weekly and daily scheduling tables, work orders, material shortage lists, and delivery change notices.
Data update frequencies are daily, weekly, or triggered by orders or abnormal events. Fields include order number, process working hours, equipment number, material code, delivery date, and more. Units include pieces, hours, days, and more.

## What constraints these characteristics impose on workflow orchestration
The category’s data is multi-source, heterogeneous, and has flexible update rhythms. Workflows must support format validation and field mapping across multiple data sources to avoid data chaos.
There are many types of business documents with significant field differences. Unified variable configuration must be completed at the start of the workflow to adapt to subsequent summary and report generation nodes.
Abnormal event-triggered data updates, such as emergency order additions or material shortages, require workflows to use event-level triggering instead of fixed-cycle runs. Abnormal branch processing logic must be configured to ensure real-time consistency between scheduling and ledgers.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Configure field mapping for order number, process working hours, and equipment number | The category’s data includes multiple types of business documents. Unified variable format is required to adapt to subsequent nodes |
| Trigger Node Settings | Trigger on order changes and material shortage list updates | The category’s data update frequency changes with business events. Must match real-time triggering scenarios |
| Knowledge Base Recall Limit | Top 8 entries | The category’s business documents have many fields. Need to control field redundancy in recall results |
| Timeout Threshold | 600 seconds | Pulling data from multiple sources requires sufficient time for data synchronization |
| `nodeId` | Bind the unique identifier of the intermediate AI dialogue node | Intermediate dialogue results must be hidden to avoid mixing into the final report |
| Global Variable Injection Timing | Execute when the workflow starts | Core category data must be loaded uniformly at the start of the process to avoid repeated pulling |

## Three Common Mistakes
- Symptom: The final workflow output includes content from intermediate AI dialogue nodes, resulting in chaotic report formatting. Cause: The `nodeId` configuration is not used to specify skipping intermediate node result output. All node return values are collected by default.
- Symptom: The workflow cannot read preset global business variables, resulting in field empty errors. Cause: Field mapping for data sources such as ERP and scheduling tables is not completed in the `variables` configuration. The variable injection timing is not set correctly.
- Symptom: Content recalled from the knowledge base cannot be associated with historical scheduling records, resulting in ambiguous reference errors. Cause: Historical context association logic is not configured in the workflow. Historical session data is not loaded via `variables`.

## How to Confirm Proper Configuration
- Manually trigger the workflow once. Check if the final output only includes ledger summary and report content, with no redundant output from intermediate nodes.
- View the workflow’s variable configuration panel. Confirm that all business fields required for the category are mapped in `variables`, with no omissions.
- Simulate a business exception, such as a material shortage list update. Verify that the workflow can automatically trigger and pull the latest data.
- Check the trigger node configuration. Confirm that category-related event sources such as order changes and equipment failures are bound.
