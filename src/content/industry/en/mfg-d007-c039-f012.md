# Motor and Generator Manufacturing Production Ledger Summary and Report Generation: Deployment and Upgrade

## What data for this category looks like
Data for this category comes from electromagnetic design documents, copper wire and insulation material batch records, winding equipment operation logs, balancing machine test data, electrical test bench output reports, and ERP/MES production management systems. Daily generated business documents include winding process cards, insulation treatment records, dynamic balance reports, voltage withstand insulation test reports, and type and factory inspection reports. Data is updated once per motor or product batch. All linked data across the full workflow is synced whenever a product type change occurs. Data fields include winding turns, insulation material grade, test voltage value, temperature rise test results, and require association with equipment operation parameters and batch material traceability information.

## What constraints do these characteristics impose on the deployment and upgrade link
Multi-source data docking requirements, high-frequency update rhythm, and high-risk error characteristics of this category bring clear constraints to the deployment and upgrade link. Cross-source data docking between equipment logs, test reports, and ERP systems must be enabled. During deployment, configure storage and database connections compatible with multiple protocols. High-frequency updated batch data requires retaining incremental synchronization logic for historical ledgers during upgrades, to avoid overwriting or corrupting historical batch records. Diverse high-specification document types require configuring corresponding permission controls and storage encryption rules, to prevent leakage of sensitive test data. Summary requirements linked across multiple dimensions require verifying cross-data source field matching logic after upgrades, to ensure the accuracy of summary reports.

## How to set configurations
The following configurations are formulated based on FastGPT v4.17.0.
| Configuration Item | Recommended Value | Rationale |
| --- | --- | --- |
| `STORAGE_S3_ENDPOINT` | Intranet address adapted to the enterprise's internal object storage gateway | Documents such as motor manufacturing test reports and process cards must be stored in the enterprise's internal object storage; this configuration ensures stable upload and reading of multi-source documents |
| `REDIS_URL` | `redis://:custom password@intranet IP:6379/0` | High-frequency updated batch data and temporary sessions require caching; this configuration covers concurrent access requirements from multiple departments such as winding and testing |
| `DB_MAX_LINK` | `200 connections` | Multi-device data synchronization and ledger summary require a large number of database connections; this value meets resource requirements for concurrent requests from multiple departments |
| `PG_URL` | Address pointing to the PostgreSQL instance associated with the enterprise ERP | Material batches and production plan data for motor manufacturing are stored in ERP; this configuration is required to obtain material traceability information |
| `FILE_TOKEN_KEY` | Randomly generated 32-bit string | Ensures access permissions for sensitive documents such as uploaded test reports and process cards, preventing unauthorized downloads |

## Three common configuration mistakes
- After upgrading to FastGPT v4.17.0, an error `Failed to create post presigned url` occurs when uploading a voltage withstand test report via workflow. The cause is incorrect configuration of `STORAGE_S3_ENDPOINT` or unopened cross-domain permissions for the storage bucket, which prevents generation of upload signatures.
- Not configuring `REDIS_URL` during deployment leads to session expiration or data inconsistency when multiple departments concurrently access ledgers, because high-frequency updated batch data is not synchronized via caching.
- Not correctly generating and configuring `ROOT_KEY` during source code deployment leads to workflow permission verification failure, making it impossible to create custom workflow nodes for ledger summary, because the root key is not configured as required.

## How to confirm configurations are correctly set
- Run a workflow to upload a single dynamic balance report, check whether the upload completes normally and a corresponding ledger entry is generated, to confirm that storage configurations and permissions are effective.
- Batch import winding process card data for multiple batches, observe changes in database connection counts, to confirm that the `DB_MAX_LINK` configuration covers concurrent requests.
- Access the configured frontend address, log in and view the document list in the ledger module, download a test report and verify whether access permissions are protected by `FILE_TOKEN_KEY`.
- Run a summary task for historical batch data after upgrading, check whether material batch information in the summary report matches that in the ERP system, to confirm that data source docking via the `PG_URL` configuration is normal.

The values provided here are common starting points and should be measured against the reader's own samples.
