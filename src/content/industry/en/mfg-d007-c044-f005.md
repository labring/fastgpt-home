# Pulp and Paper Production Ledger Summary and Report Generation: Tool Calling and Plugins

## What the data for this category looks like
Production ledger data for the pulp and paper industry covers departments including material preparation, pulping, paper making, quality management, and energy management. Core documents include pulp mixing sheets, beating records, paper machine operation records, online quality curves, laboratory test reports, and sheet break and product change records.
Data sources include wood pulp and waste paper batch ledgers, DCS/QCS systems, paper machine online measurement equipment, laboratory test systems, and energy and water treatment systems.
Data update frequencies include real-time updates, shift summaries, and archiving after the end of a single paper roll production cycle, among other formats.
Fields include pulp ratio parameters, beating degree, paper basis weight, moisture content, sheet break duration, and energy consumption values, among others. Units include absolutely dry tons, square meters, grams per square meter, percentage, and seconds, among others.

## What constraints these characteristics impose on tool calling and plugin workflows
Production ledger data for pulp and paper is scattered across multiple heterogeneous systems. Tool calling must adapt to data source access with different protocols, such as connecting to DCS real-time data interfaces and laboratory system report export interfaces.
Multiple update frequencies require tools to support both scheduled and real-time triggering modes, which align with different ledger summary cycles.
Exclusive records for a single paper roll require tools to associate data by production batch, to avoid mixing cross-batch data.
Unstructured data such as online quality curves and sheet break records require tool calling plugins to complete format conversion and field extraction, to meet the structured requirements of summary reports.
Ledgers from multiple departments require tools to support cross-data source permission verification, ensuring data access complies with departmental responsibility scope.

## How to set up configurations
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Workflow/API tool selection | `auto` | Supports automatically matching tools adapted for pulp and paper scenarios, covering the calling needs of multiple types of ledger data |
| Tool call timeout setting | `600 seconds` | Real-time data collection and cross-system summary for pulp and paper usually require long interface response times. This setting avoids interrupting tasks midway |
| Workflow/API function-call configuration | `Specify three types of tool functions: pulp mixing sheet, beating record, and paper machine operation record` | Core production ledgers for this category are concentrated in these three document types. Limiting the calling scope improves the accuracy and efficiency of tool calls |
| Batch data binding rule | Associate corresponding data sources by single paper roll production ID | Production data for a single paper roll must be summarized independently to avoid mixing cross-batch data and affecting report accuracy |
| Unstructured data conversion configuration | Adjust based on actual calibration | The format of online quality curves and sheet break records varies greatly depending on the paper machine model. Conversion rules must be adjusted according to actual equipment parameters |

## Three common errors
- Symptom: Output interruption occurs during tool calling, and the interface displays a task timeout status. Cause: The tool call timeout setting is not adjusted for the pulp and paper scenario. The response time of real-time data collection and cross-system summary exceeds the default threshold, resulting in forced termination of tool calls.
- Symptom: When calling a workflow via API, execution details of MCP tool calls cannot be obtained, and the returned fields are empty. Cause: The tool call log collection switch is not enabled in the workflow configuration, so the API cannot pull corresponding execution data.
- Symptom: Two consecutive thought process outputs appear in the debug log of the tool call node. Cause: The calling function scope of `functionCall` is not correctly limited, causing the model to repeatedly trigger tool call requests and generate redundant thought steps.

## How to confirm the configuration is correct
- Manually trigger a tool call, check if the returned ledger data includes fields from the three core documents: pulp mixing sheets, beating records, and paper machine operation records, to confirm the configuration takes effect.
- Simulate a timeout scenario, verify whether the tool call completes response within the preset timeout period, to confirm the timeout setting meets scenario requirements.
- Call the workflow via API, check if the returned results include execution logs of tool calls, to confirm the log collection configuration is correct.
- Import a single paper roll production ID, verify whether the tool only associates data sources for the corresponding batch, to confirm the batch binding rule takes effect.

All provided configuration values are common starting points and should be evaluated against samples specific to the actual deployment.
