# Production Ledger Summary and Report Generation for Spinning and Weaving: HTTP Interfaces and External Systems

## What Data Looks Like for This Category
Data for this category primarily comes from original fiber inspection reports, ERP systems, real-time collected data from spinning and weaving machines, evenness tester results, fabric inspection machine records, and order specification documents. Daily ledgers include cotton blending lists, process setup sheets, equipment operation logs, yarn inspection sheets, grey fabric inspection records, and defect ledgers.
Data updates complete synchronously with each batch of raw materials, each shift’s production, and each piece of fabric output. Fields cover fiber indicators, spinning twist, weaving structure parameters, defect types and locations, and more. Units include count, meter, gram, times, and more.

## What Constraints Do These Characteristics Impose on the HTTP Interfaces and External Systems Link
Data sources for this category are scattered, covering multiple terminals such as inspection equipment, production systems, and ERP. Updates synchronize with each raw material batch, each shift’s production, and each fabric piece. This creates specific constraints for interface triggering logic.
Multi-source data has inconsistent formats and field units. Interfaces must pre-configure field mapping rules to ensure cross-system data compatibility. High-frequency update requirements mean interfaces must support a combination of on-demand pulling and scheduled synchronization. They must also accommodate different data formats, including structured ledgers and unstructured defect records.
Additionally, abnormal production data such as broken ends and defects must be pushed in real time. Interfaces must have low-latency response capabilities.

## How to Configure
This guidance is written for FastGPT v4.17.0.

| Configuration Item | Suggested Setting | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {Enterprise API Key}, set validity period to 7 days` | Adapts permission control for multi-system integration, complies with enterprise-level interface security specifications |
| Interface timeout setting | `300–600 seconds` | Adapts batch pulling duration for production data, avoids call failures due to device response delays |
| Data pulling trigger mode | Trigger by batch, shift, or fabric piece | Matches the data update rhythm of this category, ensures real-time ledger data |
| `variables` | Bind custom fields such as fiber indicators, twist, defect types | Adapts the exclusive field requirements of this category's ledgers, enables accurate data summary |
| `responseData` | Return structured JSON format containing verified ledger fields and exception markers | Facilitates direct parsing of production ledger data by external systems, simplifies subsequent report generation logic |
| Retry policy configuration | Retry 2 times after failure, 60-second interval | Addresses temporary offline scenarios for spinning and weaving equipment, reduces interface call failure rates |

## Three Common Misconfigurations
- Symptom: Unable to add custom input parameters when configuring HTTP interfaces, with a "field does not exist" prompt displayed. Cause: Failed to pre-bind exclusive custom fields for spinning and weaving such as yarn count and defect code in the `variables` configuration item, so the system cannot recognize non-preconfigured parameters.
- Symptom: Interface call returns 401 status code, unable to pull production data normally. Cause: The `Authorization` parameter is not configured with the correct Bearer prefix, or the key validity period has expired, and it does not match the permission verification rules of enterprise-level interfaces.
- Symptom: Defect records are missing from the summarized production report data. Cause: Failed to configure the return rule for defect fields in `responseData`, or the pulling trigger mode does not cover the update nodes of defect ledgers.

## How to Verify Successful Configuration
- Call the configured HTTP interface, pass test data for a single batch of raw materials, and check if the returned `responseData` contains the pre-configured production ledger fields.
- Simulate a temporary offline scenario for an external system, trigger an interface call, and confirm that the system executes the configured retry logic.
- Adjust the data pulling trigger node, verify that ledger data for the corresponding production link can be pulled according to the configured rules.
- Check the interface permission configuration, confirm that requests initiated using the `Authorization` parameter pass system verification.
