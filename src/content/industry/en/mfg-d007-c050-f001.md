# Production Ledger Summary and Report Generation for General Mechanical Equipment Assembly: HTTP Interfaces and External Systems

## What this category's data looks like
Data sources for general mechanical equipment assembly scenarios include PLM/ERP systems, part inspection collection data, real-time assembly tool records, test bench test data, MES production execution data, and customer technical agreement documents. Daily generated documents include assembly process cards, multi-level BOM lists, torque tightening records, gap adjustment records, no-load/load trial run reports, factory inspection sheets, and packing lists.

Data updates follow a per-equipment or per-order cadence. Each completed equipment assembly or delivered order triggers an update to the corresponding ledger data. Data fields include component model, tightening torque value, gap parameters, test results, inspection number, and more. Some parameters must match the technical specification units exclusive to the target equipment.

## What constraints these characteristics impose on HTTP interfaces and external systems
Multi-source heterogeneous data sources require HTTP interfaces to support integration with diverse system formats. This includes compatibility with structured BOM data from PLM, time-series torque records from assembly tools, binary test reports from test benches, and other formats.

The per-equipment or per-order update cadence requires interfaces to support low-frequency but high-concurrency batch requests, and avoid repeated pulling of redundant data. The time-consuming process of matching multi-level BOMs with physical parts requires ledger data returned by interfaces to include hierarchical component association information, and support fast retrieval by order number or equipment number.

Temporary adjustment records from the assembly process must be synchronized in real time. Interfaces must have response capabilities aligned with business needs, to avoid disrupting on-site assembly progress.

## How to configure settings
The following configurations are written based on FastGPT v4.17.0.

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {Enterprise-specific API Key}` | Completes identity verification when connecting to external systems, to prevent unauthorized access |
| `variables` | `{"order_no": "", "equipment_model": ""}` | Used to pass business identifiers such as order number and equipment model, enabling pulling of corresponding ledger data per individual equipment or per order |
| `responseData` | Only return assembly process card, torque record, and inspection sheet fields | Filters redundant data, reduces interface transmission volume, and improves response speed |
| Interface timeout duration | `300 seconds` | Assembly process test data may be large, so sufficient time must be reserved for transmission and processing to avoid timeout interruptions |
| Request retry count | `2 times` | Addresses request failures caused by network fluctuations, and avoids excessive system load from repeated large-volume data pulls |
| Data pull trigger rule | Triggered by order completion events | Aligns with the per-equipment or per-order data update cadence for this category, and avoids invalid data pulls |

## Three common configuration mistakes
- Symptom: Interface returns 502 Bad Gateway status code. Cause: External system network access permissions are not configured correctly, preventing the FastGPT container from connecting to PLM or MES systems.
- Symptom: The `responseData` field returned after calling the interface is empty. Cause: Correct order number or equipment model parameters are not passed in `variables`, so corresponding ledger data cannot be matched.
- Symptom: Request timeouts occur during concurrent calls. Cause: Reasonable interface timeout duration is not set, and the request retry mechanism is not configured, so network delays during multiple concurrent requests cannot be addressed.

## How to confirm configuration is complete
- Call the interface and pass valid `variables` parameters, then check if the returned results include expected business fields such as assembly process cards and torque records.
- Simulate a network fluctuation scenario, call the interface, and verify that the configured retry mechanism is triggered, and a normal result is returned in the end.
- Compare the `responseData` returned by the interface with the original ledger data exported from the PLM system, and confirm that the field matching degree meets business requirements.
- Initiate multiple consecutive concurrent calls, and check if the interface can return normal results stably.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
