# Production Ledger Summarization and Report Generation for Steel Rolling and Finishing: Multi-turn Dialogue and Prompt Engineering

## What Data for This Category Looks Like
Data for this category comes from slab or billet batches, heating furnaces, mill automatic control systems, online thickness and width measuring equipment, surface inspection devices, and manufacturing execution systems (MES). Data is submitted once per coil or individual steel product. Core production link data updates in real time. Daily documents include rolling plans, heating schedules, rolling specifications, shape and thickness records, surface quality reports, and quality certificates. Core fields include coil number, batch identifier, heating temperature, rolling speed, and thickness deviation. Corresponding units are ℃, m/s, mm, and others.

## Constraints for Multi-turn Dialogue and Prompt Engineering
Data for this category is split by coil or individual product and updates in real time. Multi-turn dialogue must accurately track the full ledger for a single steel product batch. It must avoid mixing fields from different coil numbers. Daily document types vary. Prompts must adapt to field formats for different documents such as rolling plans and surface quality reports, and extract information such as corresponding coil numbers, temperatures, and thickness deviations. The real-time update feature requires limiting the retention duration of historical messages in dialogue context, to prevent expired data from interfering with current summarization. The core requirement of coil-level traceability means multi-turn dialogue must repeatedly confirm batch identifiers to ensure accurate summarization scope. At the same time, abnormal data judgment must be embedded into prompt rules to match risk scenarios such as downgrades and strip breaks in business operations.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| Maximum context length | 1000–1500 preceding characters | Adapts to the total ledger data volume for a single steel coil, prevents parsing failures caused by context overflow |
| Number of retained historical messages | First 5 messages | Matches the real-time data update rhythm, reduces interference from expired batch data |
| Interaction timeout threshold | 300–600 seconds | Adapts to real-time data interaction response requirements, prevents dialogue interruptions caused by overly long data loading times |
| Prompt variable binding | Bind `variables` to the coil number field | Accurately locates ledger data for a single steel product batch, avoids cross-coil summarization errors |
| Session persistence configuration | Bind `chatId` | Enables cross-session retention of batch information, meets coil-level traceability business requirements |
| Result format validation | Enable JSON format validation | Adapts to structured report generation requirements for ledger summarization, ensures output complies with business standards |

## Three Common Misconfigurations
- Phenomenon: Dialogue node output content is directly mixed into global return results, making it impossible to separately extract ledger reports. Cause: No output mapping rule for the dialogue node is configured, and dialogue results are directly mounted to the default return field.
- Phenomenon: Multi-turn dialogue cannot retain batch information for a single steel coil across sessions, requiring re-entry of the coil number each time the dialogue restarts. Cause: Session `chatId` binding for context persistence is not configured, leading to unsaved session state.
- Phenomenon: Generated ledger reports do not comply with business standard JSON format, with missing fields or incorrect data types. Cause: No JSON Schema field requirements are specified in the prompt, and format validation configuration is not enabled.

## How to Verify Proper Configuration
- Use the dialogue node in FastGPT v4.17.0, input test data for a specified coil number, check whether the ledger data returned by the dialogue only includes fields related to that coil number.
- Restart the dialogue, verify that the previously entered coil number is automatically recognized without requiring repeated submission of the batch identifier.
- After generating the report, check whether the output format matches the preset JSON structure, and whether fields are complete and comply with business requirements.
- View the dialogue log, confirm that the `messages` parameter only retains necessary historical interaction content, with no redundant cross-batch data.

The configuration values listed above are common starting points. They should be evaluated against the user’s own samples.
