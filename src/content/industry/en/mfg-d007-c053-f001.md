# Production Ledger Summarization and Report Generation for Iron and Steel Smelting and Continuous Casting: HTTP Interfaces and External Systems

## What this category's data looks like
Data sources for this category include hot metal and scrap collection data, L2 process control data, laboratory composition test data, MES production data, energy medium system operation data, and equipment condition monitoring data. Data update frequencies cover per-heat, real-time, and shift cycles. Daily documents include heat plans, batching lists, converter smelting records, composition test reports, continuous casting process records, and slab quality judgment sheets. Data fields include heat number, smelting duration, molten steel temperature, casting speed, slab thickness, and others. Corresponding units are none (for numbering), minutes, degrees Celsius, meters per second, and millimeters.

## What constraints these characteristics impose on HTTP interfaces and external systems
Multi-source heterogeneous production data must be pulled in batches via HTTP interfaces. Update frequencies vary significantly across different data sources, so request scheduling strategies that adapt to multiple time granularities are required. Heats and casting sequences are closely coupled. Interface requests must bind a unique heat number as an identifier to avoid data confusion across heats. Data timeliness requirements are high in high-temperature continuous processes. Interface timeout thresholds must match the natural cycle of the smelting process to prevent disruption of production rhythm. Quality data such as slab judgment sheets must be synchronized completely. Missing fields will directly cause errors in subsequent report generation. Cross-system data must maintain consistency. Interfaces must support idempotency processing to avoid duplicate ledger data caused by repeated synchronization.

## How to configure the settings
This configuration follows the FastGPT v4.17.0 specification, with details as follows:

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer {exclusive API key} | Steel production system data has high sensitivity. Standard token authentication is used to ensure the security of interface access permissions |
| `variables` | Bind heat number and casting sequence number as global variables, with a value range of 10000-99999 | Bind unique production identifiers to avoid data confusion and misalignment across heats and casting sequences |
| `responseData` | Only return the `heat number`, `smelting duration`, `molten steel temperature`, and `slab thickness` fields | Filter redundant data, reduce interface transmission load, and meet the core field requirements for ledger summarization |
| Request timeout | 600 seconds | Match the natural cycle of the smelting process to avoid interrupting critical data pulling due to short timeouts |
| Synchronization trigger rule | Trigger real-time pulling per heat + full supplementary transmission per shift | Match the real-time update and batch archiving rhythm of data, covering all production data |

## Three common configuration mistakes
- Symptom: The interface returns status code 401, and no production data can be pulled. Cause: The `Authorization` parameter is not configured correctly, the token format is incorrect, or permissions are insufficient, so the authentication check of the steel production system fails.
- Symptom: Duplicate heat records appear in the summarized ledger. Cause: Interface idempotency processing is not configured, and repeated request triggers cause the same heat data to be written to the summarized ledger multiple times.
- Symptom: Slab thickness data is missing from the generated production report. Cause: The `responseData` configuration omits this field, or the upstream system does not push the corresponding data correctly, resulting in incomplete fields returned by the interface.

## How to confirm the configuration is successful
- Call the test interface to verify that the `Authorization` parameter passes authentication and returns non-empty valid production data.
- Bind the specified heat number to initiate a request, and check that the fields returned by `responseData` match the configured items.
- Simulate repeated request triggers to confirm that no duplicate heat records appear in the summarized ledger.
- Adjust the synchronization trigger rule to verify that both real-time heat data and shift supplementary transmission data can be normally synchronized to the ledger.
