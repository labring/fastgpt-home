# Production Ledger Summary and Report Generation for Lithium-ion Cell Manufacturing: Vector Models and Indexes

## What the data for this category looks like
Teams in electrode, assembly, formation, and quality departments at power, energy storage, and consumer battery companies provide the data for this category. Daily documents include batching records, coating and rolling parameters, winding/stacking records, liquid injection records, formation and grading data, OCV and safety test reports. Data sources cover raw material batches, MES systems, slurry and coating testing, dew point monitoring, formation and grading cabinets, and laboratory data. Update frequency follows per-batch and per-individual-cell levels. Some monitoring data updates in real time. Electrochemical systems have strict requirements for moisture, cleanliness, and batch consistency. The later formation and grading process takes a long time.

## What constraints these characteristics impose on vector models and indexes
High update frequency and fine data granularity require systems to support high-frequency incremental indexing and quick single-data updates. This avoids performance loss from full reconstruction. Multi-source heterogeneous data has large format differences. Systems must adapt unified vectorization processing for structured parameters and unstructured reports. Strong batch association requires indexes to retain batch attribution relationships between data. This prevents cross-batch data confusion. Electrochemical-related parameters have high precision requirements. Vector models must capture subtle parameter differences. Chunking should preserve relevant text while avoiding unnecessary long input; chunk length does not determine the embedding model's vector dimension. Index delay for real-time monitoring data must match production tempo. This ensures timeliness of ledger summary. Some scenarios require batch-to-batch association relationships. Teams must configure additional entity association index logic to meet associated summary requirements for ledgers.

## How to set the configuration
This configuration is based on FastGPT v4.17.2

| Configuration Item | Recommended Value | Rationale |
| ---- | ---- | ---- |
| Chunk Length | 800–1200 characters | Matches the average length of a single ledger record, avoids including cross-batch data in a single chunk |
| Overlap Length | 50–80 characters | Preserves continuity of batch association information, prevents data breakage between chunks |
| Similarity Threshold | 0.75–0.85 | Differentiates parameter differences between the same batch and cross-batch, avoids incorrect associations |
| Single Search Limit | Top 20 entries | Covers the core test data volume of a single batch, avoids redundant results interfering with summary |
| `defaultToken` | Calibrate with representative ledger documents | This is the default token count used for direct text splitting; inspect sample chunks. See the [v4.17.2 model-field reference](https://github.com/labring/FastGPT/blob/v4.17.2/document/content/self-host/config/model/intro.mdx) |
| `maxToken` | Set to the selected embedding model/service input limit | This is the configured embedding model's maximum token count, not retrieval or LLM context. Check the selected model or provider documentation. See the [v4.17.2 model-field reference](https://github.com/labring/FastGPT/blob/v4.17.2/document/content/self-host/config/model/intro.mdx) |
| Query Optimization | Calibrated via actual testing | Adapts to semantic understanding requirements for electrochemical parameters, optimizes matching accuracy between query vectors and document vectors |

## Three common mistakes
- Phenomenon: Attempting to mix multimodal vector models and text vector models, with an interface prompt indicating cross-model indexing is not supported. Cause: Multimodel mixed indexing configuration was not enabled, and compatibility settings for multimodal and text vectors on the platform were not confirmed.
- Phenomenon: Calling a vector model returns an error "Model does not support current call format", with status code 400. Cause: Call parameters were not adjusted for the multimodal vector model, and the call template for text vectors was used incorrectly.
- Phenomenon: Empty field errors occur during incremental indexing, and some ledger records cannot be indexed. Cause: Empty value fields in electrochemical test data were not adapted, and empty value skipping rules were not configured.

## How to confirm the configuration is properly set
- Upload a single batch ledger record and inspect the resulting text chunks. If an error reports a vector-dimension mismatch, compare the selected model's output with the index requirements; `defaultToken` is a text-splitting token count.
- Initiate a query for single-batch parameters, verify that the number of returned results matches the single search limit configuration.
- Import multi-source heterogeneous data, check if structured parameters and unstructured reports are correctly vectorized and indexed.
- Trigger an incremental indexing task, confirm that newly added real-time monitoring data can be quickly included in the index library.

The values provided are common starting points and should be evaluated against the reader's own samples.
