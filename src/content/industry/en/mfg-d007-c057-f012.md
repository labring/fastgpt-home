# Forging and Open-Die Forging Production Ledger Summary and Report Generation: Deployment and Upgrade

## What the data for this category looks like
Data covers the entire forging workflow. Sources include raw material quality certificates, heating furnace systems, press machine collected data, MES systems, non-destructive testing instruments, and customer forging drawings. Daily documents include forging process specifications, cutting lists, heating furnace records, forging process cards, mold life records, heat treatment work orders, and ultrasonic testing reports.
Data updates are triggered per piece, per batch, or per furnace heat. Single records include fields such as forging batch number, material heat number, heating temperature range, pressure parameters, mold wear value, and testing results. Units include degrees Celsius, megapascals, hours, millimeters, and others.

## What constraints these characteristics impose on the deployment and upgrade phase
Since data is updated frequently in small batches per furnace heat or per batch, the deployment phase must adapt to high-concurrency, small-batch data writes. Reserve sufficient database connection resources.
Daily document types are diverse with large field differences. The upgrade phase must support multi-format file parsing. Avoid parsing errors caused by new document types.
Data association requires matching forging batches and material heat numbers. Deployers must configure cross-system data association rules to ensure ledger association accuracy.
At the same time, errors may lead to forging scrap and service safety risks. Retain a complete data traceability link after deployment. Do not remove the storage logic for key fields during upgrades.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `15–25 connections` | Adapt to the concurrency requirements of high-frequency data writes per furnace heat or batch, avoid exhausting database connections |
| `MONGODB_URI` | Point to a MongoDB instance deployed on the factory intranet | Store high-frequency updated forging process data, ensure data read/write latency is below 500 milliseconds |
| `REDIS_URL` | Configure as a local cache instance, cache validity period `3600 seconds` | Cache commonly used forging process parameters and mold life data, reduce repeated query pressure |
| `STORAGE_S3_ENDPOINT` | Factory internal object storage service address | Store large documents such as ultrasonic testing reports and heat treatment work orders, uniformly manage file permissions |
| `ROOT_KEY` | Generate according to factory internal permission rules | Control the highest system permissions, prevent unauthorized users from modifying ledger configurations and data |

## Three Common Misconfigurations
- Symptom: Database connection timeout error, status code 504. Cause: Did not adjust the `DB_MAX_LINK` configuration for high-frequency writes per furnace heat, leading to connection pool exhaustion and inability to respond to new requests.
- Symptom: Forging batch and material heat number association fields are empty. Cause: Did not configure cross-system data association rules, directly read original collection data without batch matching.
- Symptom: Large-volume ultrasonic testing reports cannot be uploaded. Cause: Did not configure `STORAGE_S3_ENDPOINT` to point to internal object storage, used default temporary storage which caused file size limit violations.

## How to Confirm the Configuration Is Correct
- Run a batch write test for single furnace heat data, check the database connection number monitoring, confirm the connection number does not exceed the `DB_MAX_LINK` configuration value.
- Upload an ultrasonic testing report, verify that the file can be stored and read normally through the system file management module, confirm that the `STORAGE_S3_ENDPOINT` configuration takes effect.
- Randomly select a batch of forging data, verify that the association between forging batches and material heat numbers can be generated normally, confirm that the cross-system data association logic works correctly.
- Use the `ROOT_KEY` permission to test the system configuration modification function, confirm that unauthorized users cannot access this operation entry.

The values provided here are common starting points and should be evaluated against the reader's own samples.
