# Production Ledger Summarization and Report Generation for Precast Concrete Components: Model Access and Configuration

## What the data for this category looks like
Precast concrete component production data comes from BIM detailed design documents, steel bar cutting lists, mold inspection records, pouring and vibration logs, curing ledgers, and demolding and factory inspection reports.
Data is collected from BIM or detailed design systems, steel bar and concrete batch management systems, mold table and curing kiln equipment, laboratory test records, and two-dimensional code traceability systems.
Update frequency follows per component, per batch of materials, and per curing cycle of a kiln.
Data fields include component ID, strength grade, pouring time, curing duration, demolding strength, embedded part position, and more.
Units include MPa, cubic meters, hours, pieces, and others.
Single batch data covers multiple associated documents, and corresponds one-to-one with on-site lifting positions.

## What constraints these characteristics impose on model access and configuration
The multi-source, batch-updated data characteristics of precast concrete components require model access configuration to support multi-document context integration.
Single batch data includes multiple associated documents such as detailed drawings and cutting lists. Sufficient context window must be configured to avoid truncation of key ledger fields.
Data updates occur per piece or per batch. This matches real-time or near-real-time call requirements, so model call response duration must be limited.
Data fields include precise numerical values such as strength and duration. This requires ensuring accuracy of data extraction and summarization. Model-generated report content must comply with the precision requirements of engineering fields.

## How to set the configuration
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `AIPROXY_API_ENDPOINT` | Fill in the OneAPI transit address bound to a custom quantitative model | Enable large model access for precast concrete component ledger scenarios |
| `AIPROXY_API_TOKEN` | Fill in the access key generated by the corresponding platform | Complete identity verification for model access |
| `temperature` | 0.1–0.3 | Ensure accuracy of ledger data numerical extraction and summarization, adapt to processing of precise fields such as precast component strength and batch |
| `maxContext` | 8000–12000 token | Cover multi-document context such as detailed drawings, cutting lists, and curing records for a single batch of components |
| `maxTokens` | 2000–3000 token | Limit the generation length of a single ledger report, adapt to the conventional output scale of precast component ledgers |
| `quoteMaxToken` | 1500–2000 token | Limit the maximum token count of referenced original ledger documents, avoid context overload |

## Three Common Mistakes
- After replacing the model, an error for the original model still appears, and the interface shows model loading failed. The cause is that the `llmModels` array in the configuration file was not updated correctly. Only the first model’s configuration was retained, and all model entries were not replaced. This causes the system to still call the initial model.
- After deployment, the model in the configuration file fails to load, and the page shows no interface response. The cause is that `AIPROXY_API_ENDPOINT` was filled incorrectly and does not match the custom model’s interface address, or `AIPROXY_API_TOKEN` failed verification.
- The ledger report is truncated after generation, and the output content is incomplete. The cause is that `maxTokens` was set too small and does not cover the complete output length of the precast component ledger, or `maxContext` does not adapt to the total context of multi-source documents.

## How to Confirm Successful Configuration
- Access the model management page of FastGPT v4.17.0, view the configured model list, and confirm that the target model is displayed correctly.
- Initiate a test query for a single batch of precast concrete component ledgers, observe whether the model can correctly extract fields such as component ID and strength grade, with no error messages.
- Generate a complete ledger report, check whether the output length matches the preset threshold, with no truncation.
- Verify the OneAPI interface call logs, confirm that each query returns response data normally.
