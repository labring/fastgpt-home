# Production Ledger Summary and Report Generation for Beverage and Bottled Water: Tool Calling and Plugins

## What the Data for This Category Looks Like
This category covers data from carbonated drink, juice, tea, functional beverage, and packaged drinking water factories. Daily documents include formula sheets, water treatment records, blending records, sterilization or aseptic filling records, packaging material inspection reports, and finished product inspection reports.
Data is sourced from water source and raw material testing, formula systems, online sugar and acidity meters, filling equipment, visual inspection systems, and LIMS platforms. Data updates occur per batch, per shift, or continuously.
Fields include batch number, sugar content (°Brix), acidity (mg/100mL), filling liquid level (mm), sealing torque (N·m), and some fields sync in real time with production workflows.

## Constraints Imposed by These Characteristics on Tool Calling and Plugins
Multi-source heterogeneous data sources require tool calling to adapt to API formats and authentication rules of different systems. This prevents data pull failures caused by interface differences.
High-frequency update cycles require tool triggers to be tied to production batch or shift nodes. This avoids repeated pulls of redundant data or missed real-time collected production parameters.
Specific fields and units require plugins to include built-in field mapping rules. This ensures consistent units and accurate values during ledger summary.
High-speed filling production cycles require tool calling response delays to stay within a reasonable range. This adapts to the rhythm of real-time production workflows.
Frequent product switches require plugins to support dynamic adaptation to formulas and inspection fields for different product categories.

## Configuration Settings
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Workflow/API tool selection | Set to `auto`, and limit the tool list to multi-source data pull, ledger summary, and report generation | Allow the model to independently select tools matching production scenarios, while limiting scope to avoid unrelated calls |
| Workflow/API function-call configuration | Enable and configure parameter verification rules to match beverage production ledger fields | Ensure parameters passed during tool calling comply with category field requirements, and reduce format errors |
| Tool call timeout | Set to 600 seconds | Adapt to time requirements of multi-source data pull and complex ledger summary, and avoid call interruptions caused by large volumes of production data |
| Tool result caching strategy | Cache by batch, with a cache validity period of 8 hours | Production data for the same batch does not need to be pulled repeatedly, improving summary efficiency |
| Exception capture configuration | Enable full-link error capture | Quickly locate interface errors or data format issues during tool calling |

## Three Common Configuration Mistakes
- A tool call returns a 400 status code (no body). This occurs because authentication parameters for multi-source system APIs are not properly adapted, resulting in no valid return content for the request.
- Model function calling performs poorly. This occurs because parameter verification rules for `functionCall` are not configured. The model generates calling parameters that do not comply with category field requirements, and cannot match production ledger data.
- Tool call trigger timing is incorrect, leading to repeated pulls of production data for the same batch. This occurs because triggers are not tied to production shift or batch nodes, and pulls are only performed at fixed time intervals.

## How to Verify Successful Configuration
- On the FastGPT v4.17.0 tool configuration page, check that `toolChoice` is set to `auto` and bound to the tool list for the corresponding product category.
- Initiate a simulated production batch tool call, and verify that returned ledger data fields and units comply with standard beverage production formats.
- Trigger an exception scenario, such as simulating API authentication failure, and confirm that the system correctly captures and returns a corresponding error prompt.
- View tool call logs, and confirm that trigger timing is synchronized with production shifts or batches, with no repeated call records.
