# PCB Manufacturing Equipment Inspection and Maintenance Q&A: Workflow Orchestration

## What this category of data looks like
Data for this category comes from engineering, production, quality assurance, and laboratory departments of printed circuit board factories. It covers documents including engineering production instructions, Gerber analysis records, drilling and lamination parameters, chemical solution analysis, AOI reports, electrical test reports, and slice inspection reports. Data sources include customer Gerber files, drill tapes, BOM files, CAM systems, equipment parameters, bath solution test results, data collected from AOI and electrical test equipment, and laboratory test data. Update frequency is per production batch, per shift, or continuous collection. Different documents have dedicated fields: for example, drilling parameters include rotation speed and feed rate units, and Gerber files include layer identifiers and coordinate information.

## What constraints these characteristics impose on the "workflow orchestration" link
The multi-source, high-frequency update, and high-risk nature of this category of data imposes multiple constraints on workflow orchestration. Multi-source data requires configuring cross-system access nodes to adapt to parsing requirements for different formats such as Gerber and CAM files. High-frequency updates require workflows to support triggering execution per production batch or shift to avoid processing outdated data. Diverse document structures require splitting corresponding processing nodes to adapt to scenarios such as parameter reading and defect analysis. Errors may lead to full batch board scrap or high-value claims, so workflows must include error capture and rollback links to ensure process stability.

## How to configure the settings
This page is based on FastGPT v4.17.0 configuration.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Global variable `variables` | Create temporary variable groups per production batch, enable incremental write mode | Adapt to result aggregation requirements of batch execution nodes, avoid global variable conflicts |
| Error capture binding `nodeId` | Bind the unique identifier of the model call node, jump to the retry node after triggering | Capture 429 errors from model calls, execute retry logic per configuration |
| Number of single sub-items in batch execution nodes | 20–30 items, calibrated via actual testing | Match the single processing scale of PCB production batches, avoid triggering interface rate limits |
| Loop result transfer configuration | Enable global variable append mode, bind output fields within the loop | Achieve batch aggregation of sub-item results for subsequent node calls |
| Model call node timeout period | 600 seconds | Adapt to long-duration scenarios such as Gerber parsing and complex parameter analysis |
| Failure retry strategy | Retry 2 times, interval of 30 seconds | Mitigate 429 request rate limit errors, reduce process interruption probability |

## Three common mistakes
- Symptom: The called model returns a 429 Request rate increased too quickly error, with status code 429. Cause: No error capture and retry strategy configured for the model call node, causing the process to interrupt directly after request limits are exceeded.
- Symptom: After the batch execution node completes, sub-item results within the loop are not correctly transferred to nodes outside the loop, and global variable fields are empty. Cause: Incremental write mode for global variables is not enabled, and only single assignment is used to overwrite previous results.
- Symptom: Configured global variables cannot be obtained normally, and a variable undefined prompt is returned during node calls. Cause: Temporary variable groups for the corresponding production batch are not initialized before workflow startup, leading to mismatched variable scopes.

## How to confirm proper configuration
- Trigger a simulated production batch workflow, check the logs of the model call node, confirm that retry logic is triggered when a 429 error occurs.
- Run a batch execution task with 30 sub-items, check the content of the global variable `variables`, confirm that all sub-item results have been appended and written.
- Manually modify the bound `nodeId` of the error capture to a non-existent node identifier, trigger a test error, confirm that the process jumps to the preset exception handling node.
- View the system-configured global variable list, confirm that temporary variable groups for the corresponding production batch have been created, and fields match business documents.

The values provided are common starting points and should be measured against the reader's own samples.
