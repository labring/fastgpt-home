# Equipment Inspection and Maintenance Q&A for Medical Device Assembly and Cleanroom Production: Vector Models and Indexes

## What this category of data looks like
This category of data comes from production and compliance documents of disposable consumables, implantable and interventional devices, and diagnostic equipment manufacturers, including production process specifications, batch production records, clean zone records, sterilization batch records, test reports, and traceability materials. Data sources cover design history files, device batch ledgers, MES systems, clean environment monitoring equipment, sterilization equipment, and test and calibration systems. Update frequency follows production batches, each device, or environmental monitoring plans. Individual documents contain structured fields such as unique device identifiers, sterilization parameters, and software versions, as well as unstructured content like process steps and test results.

## Constraints Imposed by This Category’s Characteristics on Vector Models and Indexes
The mixed structured and unstructured nature of data in this category requires vector models to adapt to both structured field matching and non-semantic text retrieval. Frequently updated batch data requires indexes to support incremental synchronization, avoiding performance losses caused by full reconstruction. Multi-source heterogeneous data sources require index configurations to unify field formats, ensuring documents exported from different systems can be parsed correctly. Additionally, the strict traceability requirements for compliance documents require retrieval results to accurately match key information such as batch numbers and sterilization parameters, avoiding compliance risks caused by generalized matching.

## Configuration Settings
| Configuration Item | Recommended Value Range | Rationale |
| --- | --- | --- |
| Chunk length | 800–1200 characters | Adapts to the paragraph length of individual documents in this category, avoids splitting a single process description across multiple chunks, and preserves semantic integrity |
| Overlap length | 100–150 characters | Retains key information across chunks, such as unique device identifiers and sterilization batch numbers, preventing critical fields from being truncated |
| `maxToken` | 8192 token | Meets the loading requirements for long-text compliance records, avoids truncating core document content such as sterilization batch records and test reports |
| Similarity threshold | 0.75–0.85 | Differentiates device parameters across batches of the same category, reduces the probability of incorrect retrieval matches between devices of the same model but different serial numbers |
| Single search limit | Top 6 results | Covers associated inspection and maintenance records for a single device, avoids returning excessive redundant information that hinders troubleshooting efficiency |

## Three Common Mistakes
- Issue: When deploying a PG database via Docker, the knowledge base index build status always shows failed. Container logs show memory usage peaks close to 16 GB. Cause: The PG vector extension plugin is not enabled, or concurrency is not limited during batch vector generation, leading to exhaustion of the host’s 8-core 16-gigabyte memory resources.
- Issue: The embedding model connected via OneAPI continuously throws errors, and the interface returns a 503 status code, prompting that no available model channels are available under the default group. Cause: A dedicated index model group is not configured separately, and reusing the conversation model group leads to exhaustion of model quotas.
- Issue: After manually uploading a sterilization batch record, the retrieval results do not match the corresponding batch’s parameter information. Cause: The chunk length is set too small, causing the unique device identifier to be split across multiple chunks, leading to loss of critical matching fields during vector retrieval.
