# Equipment Inspection and Maintenance Q&A for Complete Home Appliance Manufacturing: HTTP Interfaces and External Systems

## Data Overview for This Category
Data for this category primarily comes from ERP and MES systems, tightening and filling equipment, safety compliance testers, performance laboratory equipment, and after-sales fault databases. Daily documents include configured BOMs, assembly work instructions, refrigerant filling records, electrical safety test reports, random performance inspection reports, and rework records.
Data updates follow per-unit product, shift-level operations, and random inspection plans. Data fields include component batch numbers, tightening torque values, refrigerant charge amounts, safety compliance test voltages, and other items, with dedicated unit requirements corresponding to different equipment and documents.

## Constraints Imposed on HTTP Interfaces and External Systems
The data for this category is multi-source, heterogeneous, and updated flexibly. HTTP interfaces are required to support on-demand trigger request modes and adapt to data formats from different sources such as equipment, ERP, and after-sales databases.
Single-unit product-level data association requirements mean interfaces must support precise parameter filtering by dimensions such as component batch and production time. Accuracy requirements for key process data such as refrigerant charge amounts and safety compliance test results require interfaces to configure parameter verification logic.
High-frequency, small-batch request scenarios from mixed-line batch assembly require interfaces to adapt to different data volume transmissions and avoid request timeouts. Historical query requirements for after-sales fault data require interfaces to support returning results by time range and fault type.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {pre-configured industrial system API key}` | Completes identity verification when connecting to ERP and equipment control systems, and complies with the industrial scenario security access specifications of FastGPT v4.17.0 |
| `variables` | `{"batch_no": "${input.batch_id}", "prod_type": "air_conditioner"}` | Adapts to the requirement of filtering data by component batch and product type for this category, and matches the business characteristics of single-unit product associated data |
| `responseData` | `Return specified fields: batch_number, torque_value, refrigerant_charge` | Reduces invalid data transmission, adapts to high-frequency small-batch request scenarios, and lowers the load on interfaces and external systems |
| Request timeout | 60 seconds | The data return cycle for this category's equipment is short, and timeouts will cause production process interruptions, which meets the real-time requirements of on-site operations |
| Failure retry count | 2 times | Responds to temporary network fluctuations, and ensures the stability of obtaining key process data such as tightening torque and refrigerant charge |
| Batch request limit | Top 100 entries | Adapts to the conventional range of single-batch product quantities for this category, and avoids timeouts caused by excessive data volume in a single request |

## Three Common Misconfigurations
- Symptom: Occasional 500 status code and empty return fields when calling database interfaces. Cause: Parameter verification is not configured for mixed-line batch scenarios, and SQL filter conditions for different batches are not verified for format, causing some invalid parameters to trigger execution failures.
- Symptom: Empty return results when calling multimodal parsing scripts via HTTP requests, with uploaded image content not recognized. Cause: No temporary storage path parameter for image upload is configured in `variables`, causing the script to fail to obtain the input image file.
- Symptom: Mismatch between the number of returned results and expected values when calling interfaces to obtain after-sales fault data, with records from non-target batches mixed in. Cause: Correct `variables` filtering parameters are not bound in the request, resulting in failure to filter data by component batch and cross-batch data mixing.

## How to Verify Correct Configuration
- A test request carrying the `Authorization` parameter is initiated. The returned status code is verified to match business expectations, and the returned `responseData` fields are checked to match the configured specified fields.
- Different `variables` filtering parameters are passed. The interface is verified to only return data for the corresponding batch and product type, with no redundant records.
- Temporary network fluctuations are simulated by initiating repeated requests. The interface is confirmed to return valid data normally after triggering the retry mechanism.
- A test safety compliance test report image is uploaded. The multimodal parsing interface is called, and parsing results for the corresponding image are confirmed to be returned.

The values provided are common starting points and should be measured against the reader's own samples.
