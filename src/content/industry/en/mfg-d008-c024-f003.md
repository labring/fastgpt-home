# Equipment Inspection and Maintenance Q&A for Process and Engineering Changes: Multi-turn Dialogue and Prompt Engineering

## What This Category of Data Looks Like
Data for this category comes from PLM, ERP, MES, supplier materials, validation tests, and customer-specific requirements. Updates occur irregularly, triggered each time a process or engineering change is initiated. Daily documents include ECN/ECR forms, change assessment reports, drawings and BOM version files, process validation reports, old and new version switching plans, inventory disposal documents, and customer approval files. Data fields include unique change identification numbers, version numbers, effective dates, lists of involved materials, processes, or equipment, validation results, and more. There are no unified fixed units; values adjust based on document type.

## Constraints on Multi-turn Dialogue and Prompt Engineering
This category of data has scattered sources but tight associations. Multi-turn dialogue must first retrieve cross-system linked data for the corresponding change order, so a unique identifier is required to bind conversation context. Document structures are complex and include multiple attachments, so prompt engineering must guide extraction of specific fields to avoid redundant information interfering with analysis. Updates follow no fixed schedule, so dialogue must support real-time queries of the latest version of change documents. For chain impact identification, multi-turn dialogue must break down change points step by step, gradually prompt users to supplement information, and support complete impact analysis.

## Configuration Settings
| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `chatId` | Bind to the unique identifier of the change order | Ensure conversation context only links to the current change order, avoiding cross-order data confusion |
| `messages` | Retain the first 20 historical conversation entries | Cover multi-role, multi-step interaction information throughout the change process, supporting chain impact analysis |
| `variables` | Preset variables for change number, current version number, and effective date | Quickly call change document data from corresponding PLM/ERP systems, reducing manual input |
| Timeout Duration | 600 seconds | Adapt to response times for internal system data calls, preventing timeouts during long-process conversations |
| Maximum Context Size | 8000–12000 token | Cover multiple documents related to the change, avoiding truncation of critical validation or approval information |
| Single Search Limit | Top 8 entries | Balance recall accuracy and conversation response speed, preventing excessive irrelevant data from interfering with analysis |

## Three Common Configuration Mistakes
- Phenomenon: The conversation returns a `connection error` message, and recovery fails after enabling a proxy. Cause: Access addresses for internal systems such as PLM and MES are not configured in FastGPT’s proxy rules, causing the conversation to fail when calling internal data.
- Phenomenon: After configuring multi-turn dialogue, output content from intermediate analysis steps cannot be hidden. Cause: Intermediate thinking content in the `messages` parameter is not filtered correctly, and non-displayable content is mistakenly included in the exportable list.
- Phenomenon: The conversation cannot automatically extract the version number field of the change order. Cause: Mapping rules for the corresponding field are not preset in `variables`, causing the prompt engineering to fail to obtain context variable information.

## How to Verify Proper Configuration
- Launch a conversation for the corresponding change order in FastGPT v4.17.0, check if the bound `chatId` matches the unique identifier of the change order, and confirm that context linking is correct.
- After triggering the conversation, check if the returned content includes the preset `variables` values, and verify that variable calls function normally.
- Simulate a multi-turn change analysis conversation, check if historical messages are retained in order, and confirm that the `messages` parameter configuration is effective.
- Call the internal system data interface, confirm that no `connection error` message appears, and verify that system connectivity configuration is correct.

The values provided here are common starting points, and should be evaluated against the user’s own samples.
