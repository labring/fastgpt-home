# Incoming Material Inspection and Supplier Quality Equipment Inspection and Maintenance Q&A: HTTP Interfaces and External Systems

## What this category's data looks like
This category’s data covers end-to-end documents and business information related to incoming material inspection and supplier quality for manufacturing enterprises. Daily documents include inspection specifications, sampling plans, incoming material reports, supplier audit reports, abnormality contact sheets, 8D reports, and concession acceptance approval forms. The data draws from purchase orders, product drawings and specifications, supplier quality certificates, online inspection equipment data, historical quality records, and supplier portal information. Updates trigger per batch of incoming materials, alongside monthly or quarterly supplier quality evaluations and ad-hoc supplier audit updates. Fields include batch number, inspection items, non-conformity types, supplier codes, concession approval status, and more. There is no unified fixed unit; adjustments are made based on specific business documents.

## Constraints for HTTP Interfaces and External Systems
The data sources for this category are scattered across multiple external systems, including procurement systems, supplier portals, and inspection equipment. This requires HTTP interfaces to support multi-source integration and flexible authentication. Data updates have both real-time and ad-hoc rhythms. Real-time updates trigger per batch of incoming materials, while other updates occur monthly, quarterly, or ad-hoc. Interfaces must support both on-demand calling and scheduled pulling modes. Document fields are flexible with no unified fixed structure. This requires `responseData` to support custom field mapping, to avoid hard-coded field matching logic. The risk of non-conforming materials entering production also requires interface calls to have idempotency and failure retry mechanisms. These mechanisms ensure the accuracy and stability of data synchronization.

## How to Configure Settings
These configurations apply to FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {Supplier Portal API Key}` | Supplier portal and inspection equipment interfaces typically use Bearer token authentication, which complies with industry general interface security specifications |
| `variables` | `{"batchNo": "{{batch_no}}", "supplierCode": "{{supplier_code}}"}` | Business parameters exclusive to this category such as incoming material batch number and supplier code need to be passed, to adapt to the inspection scenario for each batch of incoming materials |
| `responseData` | Custom field mapping rules | Category document fields are flexible without a unified structure, requiring custom matching of incoming material inspection fields from business systems |
| Interface call timeout | `30 seconds` | Incoming material inspection must adapt to production rhythms; excessive timeout will hinder production process progress |
| Failure retry count | `2 times` | Avoid duplicate data processing caused by repeated calls, while ensuring the success rate of interface calls |
| Scheduled pull interval | `Calibrated based on actual testing` | Adapt to the update rhythm of monthly/quarterly supplier quality evaluations, avoiding frequent calls that occupy system resources |

## Three Common Configuration Errors
- Phenomenon: Interface calls return exceptions such as `failed to get gpt-3.5-turbo token encoder`. Cause: The `Authorization` parameter is not configured correctly, or the key has insufficient permissions to access external model interfaces.
- Phenomenon: Every interface call returns fixed generic recommended questions. Cause: The category-exclusive `variables` parameter is not passed, and business context such as incoming material batch number and supplier code is not bound, leading to generalized question-and-answer matching.
- Phenomenon: Fields corresponding to `responseData` are empty after an interface call. Cause: Custom field mapping rules are not configured, so inspection data returned by external systems cannot be matched to business system fields, resulting in data parsing failure.

## How to Verify a Successful Configuration
- Call the test interface, and use a packet capture tool to check if the `Authorization` parameter is correctly carried in the request header.
- Pass simulated incoming material batch number and supplier code, then check if the `variables` parameter is correctly populated in the request body, and verify the completeness of business context transmission.
- Call the external system interface, view the returned data, and confirm that `responseData` can correctly map to the business system’s inspection fields.
- Simulate an interface call failure scenario, check if the preset retry mechanism is triggered, and confirm that the failure handling logic is effective.

The values provided are common starting points and should be measured against the reader's own samples.
