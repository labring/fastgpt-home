# Equipment Inspection and Maintenance Q&A for General Mechanical Equipment Assembly: Multi-turn Dialogue and Prompt Engineering

## What This Category of Data Looks Like
Daily data for general mechanical equipment assembly includes assembly process cards, BOMs, torque records, clearance adjustment records, commissioning reports, factory inspection sheets, and packing lists.
Data sources include PLM/ERP, part inspection data, assembly tool collection systems, test benches, MES, and customer technical agreements.
Update frequency is once per device or per order.
Fields include material codes, torque values, clearance values, assembly stations, and more. Corresponding units include newton meters, millimeters, pieces, and others.

## What Constraints These Characteristics Impose on Multi-turn Dialogue and Prompt Engineering
Data sources for this category are scattered and linked to a single device or order. Multi-turn dialogue must retrieve layered information from corresponding documents step by step. Avoid loading excessive redundant data at one time.
Since updates occur once per device or order, dialogue context must be strictly bound to a single device or order. Avoid mixing assembly data from different orders.
Multi-level BOMs and commissioning records require prompts to guide step-by-step disassembly and verification. Explicitly require returning parameter values with corresponding units to avoid data matching errors.

## Configuration Settings
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Maximum Context Length | First 1200–1800 characters | Matches the average total length of assembly documents for a single device, prevents context overflow |
| Context Binding Identifier | Isolate by `chatId` | Ensures dialogue history for a single device or order does not mix with data from other orders |
| Prompt Variable Population | Automatically bring in order numbers and station numbers from `variables` | Accurately match exclusive assembly data for the corresponding device |
| Dialogue Timeout Duration | 600 seconds | Matches the average response time requirement for a single round of dialogue |
| Historical Dialogue Truncation Threshold | Calibrated based on actual testing | Balances context completeness and response speed |
| Multi-turn Follow-up Trigger Rule | Automatically trigger when key parameters are missing from results | Supplement core data such as torque values and clearance values |

## Three Common Mistakes
- Symptom: Dialogue results only display plain text prompts, with no structured query data shown. Cause: `variables` are not configured to map query results to dialogue display variables, so data is not correctly brought into the dialogue context.
- Symptom: After multiple rounds of dialogue, the accuracy of answers to the same question decreases. Restarting a new dialogue restores normal accuracy. Cause: Dialogue history for different orders is not isolated by `chatId`, causing context to mix assembly data from unrelated devices.
- Symptom: Context clearing operations that meet specified conditions cannot be triggered. Cause: The `messages` parameter is not bound as a clearing trigger condition in the workflow, and the judgment logic is not correctly configured.

## How to Confirm Proper Configuration
- Initiate an inspection question for a single device, verify that exclusive data for the corresponding order number and station number is automatically included in the dialogue.
- Trigger the multi-round follow-up process, confirm that the system automatically initiates follow-up questions based on missing information in the current answer.
- Switch devices from different orders, confirm that dialogue history does not share data across orders.
- Test input with a long historical dialogue, confirm that the system automatically organizes or truncates the context.

The values provided here are common starting points, and should be evaluated against the reader's own samples.
