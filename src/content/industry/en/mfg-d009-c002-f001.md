# Quality Problem Traceability and Defect Analysis for SMT Mounting and Electronic Assembly: HTTP Interfaces and External Systems

## What this category of data looks like
Data for this category comes from BOM and Gerber coordinate files provided by customers, MES systems, and real-time collected data from placement machines, SPI/AOI testing equipment, and reflow oven temperature recorders. Daily generated documents include BOM and coordinate files, line change lists, stencil and furnace temperature records, first article confirmation reports, SPI/AOI testing reports, maintenance records, and traceability labels.
Data updates are triggered per work order and each line change. Key quality parameters are synced in real time. Fields include part number, reference designator, component batch number, furnace temperature parameters, defect coordinates, and more.

## What constraints do these characteristics impose on HTTP interfaces and external systems
Quality traceability data in SMT scenarios has three core characteristics: high real-time performance, updates per work order or line change cycle, and multi-source heterogeneity.
Real-time collected SPI/AOI defect data requires interfaces to have low-latency response capability to avoid disrupting production line beat. BOM and line change list data updated per work order requires interfaces to support dynamic passing of work order identification parameters, ensuring correct data association. Multi-source data from different devices and systems requires interfaces to use unified authentication and field mapping rules, preventing data format conflicts.
Additionally, association between traceability labels and maintenance records requires interfaces to support precise field matching, ensuring the accuracy of defect analysis.

## How to configure the settings
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Carry factory-specific API key | Distinguish work order data from different production entities and prevent cross-factory data leakage |
| `variables` | Pass work order ID, component batch number, line change list version | Match real-time data update requirements per work order and line change, achieve data isolation |
| `responseData` | Include defect coordinates, furnace temperature parameters, traceability label ID | Align with core quality traceability fields in SMT scenarios, support precise association for defect analysis |
| Interface timeout period | 30–60 seconds | Adapt to real-time upload and query delays of SPI/AOI reports, avoid production line wait timeouts |
| Maximum return entries | Top 20 entries | Control the volume of data returned per interface, reduce load pressure on downstream systems |
| Field mapping rules | Set based on actual measurements | Match field formats output by different devices, ensure correct data parsing |

## Three common configuration errors
1.  The interface returns `responseData` missing defect coordinates or component batch fields, with logs showing the specified fields are empty. This occurs because required return fields for SMT-specific quality data are not clearly defined in the configuration, making it impossible to associate defect locations and batch information from SPI/AOI reports.
2.  Quality data across multiple work orders is displayed combined, making it impossible to locate defective products from a single batch. This occurs because a unique work order ID is not passed via `variables`, leading to traceability data from different production tasks not being correctly distinguished.
3.  The interface returns a 504 timeout error, with the interface showing the request failed. This occurs because the timeout setting does not adapt to transmission delays of real-time SMT device data, leading to data upload or query timeouts that interrupt production line processes.

## How to confirm the configuration is correct
- Verify that `responseData` includes SMT-specific fields such as defect coordinates and furnace temperature parameters when the configured interface is invoked.
- Confirm that returned data only corresponds to quality records of the specified work order when `variables` parameters with different work order IDs are passed.
- Check that interface response time meets the preset timeout setting during simulated real-time data upload.
- Confirm that requests without the carried `Authorization` key are correctly intercepted by the system after the parameter is configured.

The values provided are common starting points and should be measured against the reader's own samples.
