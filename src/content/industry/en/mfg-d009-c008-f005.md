# Quality Problem Traceability and Defect Analysis for Cosmetics Production: Tool Calling and Plugins

## What this category of data looks like
Data related to quality traceability in cosmetics production comes from registered or filed formulas, raw material safety documents, weighing and emulsification equipment, ERP/MES systems, laboratory test records, and packaging material version information. Updates occur each time a production batch finishes or a line change takes place. Daily documents include formula process sheets, weighing and feeding records, emulsification or filling records, cleaning and site clearance records, semi-finished and finished product test reports, and label review documents. Core fields include restricted substance content, emulsification temperature, batch number, packaging material version number, test pass identification, and similar items.

## What constraints these characteristics impose on tool calling and plugins
Data sources for this category are scattered, and update frequency varies with production batches. This requires tool calling to accurately match the data sources and update nodes for each production batch. Fixed fields across multiple types of documents must be extracted strictly, to avoid mixing irrelevant content. Filed formulas and label data must fully align with official registered information, with no deviations allowed. The volume of data per batch changes with production scale, so tool calling must adapt to dynamically changing content lengths, to prevent incomplete traceability information caused by data truncation. Temporary data generated during line changes must trigger tool calling quickly, to ensure the timeliness of defect analysis.

## How to configure the settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Single call timeout | 600 seconds | Matches the generation and retrieval cycle of each production batch’s data, to avoid task interruptions caused by device response delays |
| `toolChoice` | auto | Adapts the automatic calling logic for multi-data-source plugins, covering multiple types of production documents including formulas, equipment, and test records |
| Result field extraction rule | Precise matching by preset field names | Strictly corresponds to fixed fields in formula process sheets and feeding records, to ensure extracted content is consistent with filed data |
| `functionCall` | Enabled | Forces plugin calls using preset parameters, to avoid returning unauthorized sensitive information or irrelevant content |
| Plugin trigger timing | Triggered by batch number | Matches the update frequency of each production batch, only calling tools after the corresponding batch’s data is generated |
| Maximum context length | 8000–12000 characters | Accommodates multiple types of document content for a single batch, to avoid truncation of critical traceability information |

## Three common mistakes
- Setting `stream` to `true` when calling the interface prevents correct reception of final results. The cause is either not configuring the result closing marker for the SSE protocol, or not processing returned content using line-by-line parsing.
- When deploying FastGPT v4.14.1 privately, importing a plugin prompts `internal server error`. The cause is either plugin dependency packages being incompatible with the current runtime environment version, or incorrect port mapping configuration.
- When using an SSE-wrapped MCP plugin, a prompt indicating only stdio processes are supported appears. The cause is either not configuring the plugin to run in stdio mode, or not completing local dependency installation and path binding.

## How to confirm the configuration is correct
- In FastGPT v4.17.0, initiate a tool calling request for a single production batch’s data, and check if the returned results include core fields such as the corresponding batch’s formula, feeding, and test information.
- After importing the plugin, check the system runtime logs to confirm there are no `internal server error` type error messages.
- Test calling the interface in `stream` mode, verify that all returned content can be fully received and spliced, with no missing final results.
- After configuring `functionCall`, initiate a call and check if the returned content only includes preset extracted fields, with no irrelevant information appearing.
