# Quality Problem Traceability and Defect Analysis for Active Pharmaceutical Ingredient and Pharmaceutical Intermediate Manufacturing: HTTP Interfaces and External Systems

## What the data for this category looks like
Data for this category originates from registered process documents, raw material batch ledgers, DCS production control systems, weighing systems, LIMS laboratory information management systems, chromatography data systems, and QMS quality management systems. Daily core documents include batch production records, material balance reports, reaction and purification process records, cleaning validation records, impurity profile reports, and deviation and change approval documents. Data updates are triggered once per production batch and each process step. Fields include batch number, reaction parameters, impurity content, solvent residue, operator, and approval nodes. Units mostly involve molar concentration, reaction duration, purity parameters, and other specialized chemical engineering parameters.

## What constraints these characteristics impose on the HTTP Interfaces and External Systems link
Multi-source heterogeneous data sources for this category require HTTP interfaces to support cross-system data format conversion and adapt to field naming rules of different systems. High-frequency batch-level updates require interface calls to align with production cycles to avoid exceeding system load. The complexity of specialized chemical fields requires interface parameters to accurately correspond to specific fields such as batch number, impurity content, and reaction parameters, to avoid insufficient adaptation of general fields. At the same time, the strict requirements of quality problem traceability require interfaces to support full-link data backtracking, and failed requests must have traceable log records to support deviation investigation and compliance audits.

## How to configure the settings
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Bearer token carrying an enterprise-specific secret key | Matches the identity verification requirements of external systems to prevent unauthorized access |
| `variables` | Pre-set business variables such as batch number, impurity type, and reaction step | Adapts to interface calls across multiple batches and scenarios, reducing repeated parameter configuration |
| `responseData` | Only return batch ID, impurity content, and reaction duration fields | Streamlines returned content, reduces data transmission overhead, and aligns with core quality traceability needs |
| Interface timeout period | 300–600 seconds | Adapts to the long-cycle data return requirements of chemical production processes |
| API call frequency limit | Triggered per production batch, no more than 10 calls per single trigger | Aligns with step-level data update rhythm per batch to avoid system overload |
| API key validity period | 90 days | Balances security requirements and daily operational convenience |

## Three common configuration mistakes
- Failing to obtain the target dataId after calling the interface, with empty return fields. The cause is that business-related parameters such as batch number and reaction step are not configured in `variables`, so the interface cannot match the traceability data of the corresponding production batch.
- Exceeding the expected number of data items returned by a single API call, causing parsing failure in downstream LIMS systems. The cause is that the `responseData` configuration is not used to only return necessary fields such as impurity content and batch number, and the interface returns full redundant system log data.
- Not setting a validity period and usage count limit for the API key, leading to the risk of abuse after the key is leaked. The cause is that the key's usage duration and call frequency threshold are not bound in the system settings, and the principle of least privilege for data security is not followed.

## How to confirm the configuration is correctly set
- Invoke the test interface to verify that the `Authorization` token can pass the identity verification of the external system, and return the correct response status code.
- After invoking the interface, check whether the fields returned by `responseData` only include the preset necessary business fields, with no redundant data.
- Simulate the key expiration scenario to verify that the interface returns an unauthorized error prompt, confirming that the validity period configuration takes effect.
- Adjust the batch parameter in `variables` to verify that the data returned by the interface updates with the parameter changes, matching the information of the current production batch.

The values given are common starting points and should be measured against the reader's own samples.
