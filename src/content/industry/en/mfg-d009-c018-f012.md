# Quality Problem Traceability and Defect Analysis for Continuous Basic Chemical Production: Deployment and Upgrade

## What the data for this category looks like
Data sources for quality traceability in continuous basic chemical production include DCS/SIS systems, online analyzers, LIMS systems, equipment condition monitoring tools, energy metering devices, and raw material tank sensors.
Data update frequencies fall into three categories: real-time, shift-based, and daily.
Real-time data covers process parameters such as reactor temperature and pipeline pressure.
Shift-based data includes shift reports and interlock bypass records.
Daily data includes laboratory reports and special work permits.
Document structures include standardized process indicator cards, long-term DCS trend charts, numbered work permits, and interlock records.
Fields include temperature and pressure units for process parameters, purity and impurity content markers for laboratory data, and approval status and execution time for work permits.

## Constraints on deployment and upgrade
This page applies to the deployment and upgrade workflow for FastGPT v4.17.0.
Multi-source real-time data access requires sufficient database connection pools and cache resources during deployment. This prevents connection overflow during concurrent collection.
Documents with different update frequencies need tailored vector library update strategies. Real-time data requires high-frequency synchronization. Static documents can be updated in batches as needed.
Parsing multiple document types requires preset distinct chunking rules. This adapts to the short fields of process indicator cards and the long text of DCS trend charts.
Basic chemical production involves hazardous media and strict interlock control. Deployments must configure internal network-isolated storage and access permissions to avoid leaking sensitive process data.
Large upgrade spans require verification of compatibility between the old version database structure and the new version. This prevents data migration failures.

## Configuration Settings
| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `DB_MAX_LINK` | `120–180` | Adapts to concurrent connection needs for multiple real-time data sources, covering collection requests from DCS, online analyzers, and other devices |
| `MONGODB_URI` | `Internal network MongoDB 4.4+ instance address, with read-write permission authentication parameters` | Supports offline deployments that cannot access the public network, ensuring storage performance for process data and traceability records |
| `REDIS_URL` | `Local Redis 6.2+ instance, with a 10 GB memory limit` | Caches real-time DCS trend data and process alarm information, reducing high-frequency read pressure on the database |
| `FE_DOMAIN` | `Enterprise internal network specified front-end access domain name` | Adapts to enterprise internal network deployment scenarios, avoiding public exposure of internal service addresses |
| `STORAGE_S3_ENDPOINT` | `Internal network MinIO service address` | Stores offline process documents, laboratory reports, and work permits, without relying on public network storage services |

## Three Common Misconfigurations
- When upgrading from v4.6.7 to v4.8.10 across versions, directly migrating the database directory causes service startup failure. Logs show a permission verification failure prompt. The root cause is failure to retain the `ROOT_KEY` configuration from the original instance, preventing the platform from verifying internal interface legitimacy.
- An error occurs during the initialization step for commercial edition deployments. The symptom is database connection timeout. This happens when a public network database address is entered for `MONGODB_URI`, without adapting to enterprise internal network access restrictions.
- Model context parameter configuration conflicts cause long-text process trend data to be truncated. This occurs when the global context upper limit set during deployment does not match the parameter configuration of a single model on the platform, triggering runtime truncation logic.

## How to Verify Successful Configuration
- Log in to the database monitoring panel. Confirm the database connection count stays within the `120–180` range to verify the `DB_MAX_LINK` configuration is active.
- Access the internal network address corresponding to `FE_DOMAIN`. Confirm the front-end page loads normally and displays the preset quality traceability module.
- Upload a DCS trend document. Check for the corresponding file in the storage service to verify the `STORAGE_S3_ENDPOINT` configuration is correct.
- Initiate a quality traceability query for a product batch. Confirm the returned results include process parameters and laboratory data for the corresponding time period, verifying the configuration matches business requirements.
