# Quality Problem Traceability and Defect Analysis for Industrial Instrument Manufacturing and Calibration: Workflow Orchestration

## What this category of data looks like
Data for this category comes from design documents, standard instrument and environmental monitoring data, calibration software, laboratory information systems, and customer range requirements. The update frequency is after each calibration of every individual device. Daily documents include assembly and commissioning sheets, calibration procedures, original calibration records, error curves, metrology certificates, and software version records. Core fields include tested part number, calibration parameters, error values, environmental conditions, metrology certificate number, and additional relevant fields. The core deliverables are traceable calibration records and metrology certificates.

## What constraints do these characteristics impose on workflow orchestration
Data for this category is updated per single device per calibration. The core deliverables are traceable calibration records and metrology certificates, so the workflow must bind a unique tested part identifier. There are diverse daily document types, so support for categorized retrieval of different documents is required. Core time-consuming steps are concentrated on standard instrument connection, error calculation, and traceability review. These steps must be split into separate nodes to enable step-by-step verification. The data has strong association logic, so a field validity check node must be added to the workflow to prevent invalid data flow. Branch workflows must also be supported to distinguish between normal and abnormal calibration results.

## Configuration Settings
This configuration is based on FastGPT v4.17.0.

| Configuration Item | Recommended Approach | Rationale |
| --- | --- | --- |
| `variables` | Bind tested part number and calibration date as custom variables | Matches the data characteristic of this category being updated per single device per calibration, enabling precise retrieval of historical documents for the corresponding device |
| Workflow branch trigger rules | Trigger based on the calibration error threshold in `variables` | Distinguishes between normal calibration and defective product workflows, adapting to quality traceability requirements |
| Single knowledge base retrieval limit | Top 8 results | The total volume of calibration-related documents for this category is controllable. Excessive results will increase node processing time |
| Historical context call limit | Top 3 chat records | Avoids interference from overly long historical records on the accuracy of current calibration analysis |
| Node timeout threshold | 600 seconds | Adapts to the time requirements of core steps such as error calculation and traceability review |
| `nodeId` | Assign a unique identifier to each calibration step node | Facilitates tracking of workflow execution links and quickly locating abnormal causes for incomplete nodes |

## Three Common Mistakes
- Phenomenon: The workflow is set with a historical context call limit of 1 record, but retrieval results still include chat records older than 1 day. Cause: The unique identifier of the current calibration session is not bound to `variables`, causing historical records from cross-sessions to be incorrectly matched.
- Phenomenon: When the same workflow is executed, it sometimes fails to complete all nodes without an error prompt. Cause: No field validation rules are configured for upstream nodes. When the tested part number in `variables` is empty, downstream nodes skip execution directly.
- Phenomenon: The knowledge base retrieval node cannot filter calibration-related documents by custom tags. Cause: The tag filtering function is not enabled in the retrieval configuration, or the calibration type tag is not passed to the parameters of the retrieval node.

## How to Confirm Proper Configuration
- Manually pass the tested part number and calibration date to `variables`, then verify that knowledge base retrieval results only return calibration documents for the corresponding device.
- Simulate a scenario where the upstream `variables` field is empty, then check whether the workflow triggers the field validation node and blocks subsequent execution.
- Set the historical context call limit to 1 record, launch two test sessions with an interval of more than 1 day, then verify that only chat records from the current session are returned.
- View the workflow execution log, confirm that each node is assigned a unique `nodeId`, then use `nodeId` to quickly locate abnormal nodes.

The values provided are common starting points and should be measured against the reader's own samples.
