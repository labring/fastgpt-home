# Quality Issue Traceability and Defect Analysis for Incoming Material Inspection and Supplier Quality: HTTP Interfaces and External Systems

## What data for this category includes
This category of data originates from purchase orders, drawing specifications, supplier quality certificates, inspection equipment-collected data, historical quality records, and supplier portals. Daily documents include inspection specifications, sampling plans, incoming material reports, supplier audit reports, abnormal contact sheets, 8D reports, and concession acceptance approval documents. New data records are created for each batch of incoming materials. Supplier quality evaluations are completed on a monthly or quarterly basis, and special audits are conducted irregularly. Data fields include batch number, supplier code, inspection items, qualified judgment results, abnormality types, and rectification statuses. Units cover batches, piece counts, inspection parameter standard values, and similar metrics.

## What constraints these characteristics impose on HTTP interfaces and external systems
Data for this category is dynamically generated with each batch of incoming materials, and is linked to a unique batch number and supplier code. HTTP interfaces must therefore support requests that carry dynamic parameters such as batch and supplier identifiers. Daily documents exist in diverse formats, so interfaces must support file transfer and query operations for multiple formats including inspection specifications and abnormal contact sheets. Data sources span internal inspection equipment and external supplier portals, so cross-system identity verification and data synchronization logic must be compatible. Additionally, defective materials entering production can cause batch-level failures. Interfaces must be configured with timeout retry and exception status capture mechanisms to ensure stable data transmission.

## How to configure settings
The following configurations are compatible with FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | `Bearer {preset API key}` | This category requires integration with external systems such as supplier portals. Standard Bearer tokens are used for cross-system identity verification to secure data access |
| `variables` | `{"batch_no": "dynamic batch number", "supplier_code": "supplier code"}` | Data for this category is tied to a unique batch and supplier. Dynamic business parameters must be injected to match corresponding inspection and quality records |
| `responseData` | Return only batch pass rate, abnormality type, and rectification status | This category only requires core quality-related fields. Filtering redundant data improves interface response speed |
| Request timeout setting | 300 seconds | This category involves batch incoming material data queries. Sufficient time must be allocated for cross-system data retrieval to prevent request interruptions due to timeout |

## Three common configuration mistakes
- An HTTP interface call returns empty content or a 401 status code. This occurs when the `Authorization` parameter is not configured correctly, or the `variables` parameter format is invalid, preventing matching of quality data for the corresponding supplier and batch.
- The interface response data includes a large number of non-quality-related fields. This occurs when the `responseData` filtering rules are not configured as required, and full raw data from the external system is returned, increasing data processing workload.
- The interface request times out and is interrupted. This occurs when the request timeout period is not set appropriately. Cross-system data retrieval for this category requires a longer response cycle, which exceeds the default timeout limit.

## How to verify a complete configuration
- Call the test interface with simulated incoming material batch numbers and supplier codes, and confirm that the returned fields cover the preset quality-related content.
- Review interface call logs to confirm that the `Authorization` parameter has been passed correctly, with no identity verification related errors.
- Simulate a timeout scenario to check whether the interface triggers the preset retry logic, with no request interruptions occurring.
- Compare the raw data returned by the external system with the interface response content to confirm that the data mapping relationship aligns with the configuration requirements.
