# Quality Issue Traceability and Defect Analysis for Incoming Material Inspection and Supplier Quality: Tool Calling and Plugins

## What this category's data looks like
Data for this category covers purchase orders, drawing specifications, supplier quality certificates, inspection device output data, historical quality ledgers, and supplier portal synchronized information. Daily associated documents include inspection specifications, sampling plans, incoming material inspection reports, supplier audit reports, exception liaison sheets, 8D correction reports, and concession acceptance approval forms.

Real-time records are created for each batch of incoming materials when data updates occur. Supplier quality rating updates are completed monthly or quarterly. Data adjustments are synchronized following irregular special audits.

Data fields include batch number, supplier code, inspection item parameters, defect type, correction status, and other items. Some documents include unit markings such as dimensional tolerance mm and inspection item rated values.

## What constraints these characteristics impose on the "tool calling and plugins" workflow
Data for this category is scattered across multiple channels including procurement systems, inspection equipment, and supplier portals. Update frequencies vary significantly across these sources. This requires tool calling and plugins to support multi-source data synchronization, and to configure calling rules adapted to different data sources.

Associated documents include inspection reports and correction sheets in multiple formats. Plugins must have general document parsing capabilities, and can adjust parsing logic for different document types.

Data fields include unique identifiers such as batch number and supplier code. Tool calling must carry these parameters to complete precise association, and avoid cross-batch data confusion.

Real-time incoming material data and periodic supplier rating data require tool calling to support a running mode that combines on-demand triggering and scheduled synchronization.

## Configuration guidelines
This configuration is written for FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| Workflow/API tool selection | `auto` | Adapts to the multi-data-source and multi-document-type tool calling requirements of this category, automatically matching corresponding parsing or synchronization plugins |
| Workflow/API function-call configuration | Carry batch number and supplier code parameters | Ensures tool calling accurately associates corresponding incoming material batches and supplier data, avoiding cross-batch confusion |
| HTTP plugin configuration | Set timeout to 600 seconds | Adapts to the response durations of supplier portal and inspection equipment interfaces, preventing call interruptions caused by batch data synchronization |
| Document parsing trigger rule | Trigger per incoming material batch | Matches the update rhythm of inspection record generation for each batch of incoming materials in this category, ensuring real-time data synchronization |
| Multi-data source synchronization frequency | 1 time per month to 1 time per quarter, calibrated based on actual testing | Adapts to the update cycle of supplier quality ratings for this category, avoiding resource occupation from frequent synchronization |
| API call return processing | Only use as context input | Aligns with the business requirement of using call results for large model analysis in this category |

## Three common configuration errors
- Symptom: After configuring `toolChoice`, the large model does not trigger tool calling and only returns general responses. Cause: The calling permission for the corresponding plugin is not enabled in the `toolChoice` parameter, and no trigger rule is configured to match the incoming material batch scenario of this category.
- Symptom: After importing the HTTP plugin, calling supplier data returns empty fields. Cause: Required fields such as batch number and supplier code are not carried in the plugin configuration, making precise association between incoming material and supplier data for this category impossible.
- Symptom: The application directly outputs inspection report content after an API call. Cause: No processing logic is configured for API return results, and the call result is returned directly without using it as context input for large model quality analysis.

## How to verify proper configuration
- Initiate a tool calling request simulating a single batch of incoming materials, confirm that the system triggers the corresponding plugin's synchronization and parsing process.
- View plugin call logs, confirm that required fields such as batch number and supplier code are carried in the request, and no null values are returned.
- Call the published application API, check that the returned result only contains structured context information, and does not directly output original inspection content.
- Upload supplier documents in different formats, confirm that the plugin can normally parse and extract corresponding fields.

The values provided here are common starting points and should be measured against the reader's own samples.
