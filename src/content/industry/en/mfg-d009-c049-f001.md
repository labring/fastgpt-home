# Quality Problem Traceability and Defect Analysis for Process Quality and Finished Product Release: HTTP Interfaces and External Systems

## What this category of data looks like
Data sources for this category include MES systems, online testing equipment, laboratory test records, process parameter libraries, customer quality standards, and historical defect libraries. Data is collected and updated continuously at per-shift frequency, organized by production batch. Daily associated documents include control plans, patrol inspection records, SPC reports, finished product inspection reports, nonconforming product review forms, release forms, and monthly quality reports. Data fields include production batch number, inspection item name, measured result, defect type, release judgment result. Some fields are associated with equipment numbers and process parameter numbers.

## What constraints these characteristics impose on the "HTTP Interfaces and External Systems" link
Multi-source heterogeneous data sources require interfaces to support cross-system data pulling. Configure the `Authorization` authentication parameter to adapt to the authentication rules of different external systems. High-frequency updated production data requires interfaces to support pulling by batch or time interval, to avoid excessive data volume in a single request. Diverse associated document types require interfaces to support specifying document parsing types, to accommodate uploads of quality reports in formats such as PDF. Standardized field mapping requires interface requests to pass the clear `variables` parameter, to align data fields with the internal quality system. Quality data errors can trigger the spread of batch defects. Interfaces must include a failure retry mechanism and `responseData` response verification logic to ensure data accuracy.

## Configuration Settings
The following configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| --- | --- | --- |
| `Authorization` | Configure Bearer Token or basic authentication based on external system type, with a value range of `32–64 characters` | Adapt to the authentication requirements of different external systems such as MES and testing equipment, and avoid authentication failures |
| `variables` | Set to `production batch number, inspection item type, release status`. The number of variables per single request must not exceed 10 | Match the core fields of this category of data, and ensure that interface requests accurately match target quality data |
| `responseData` | Configure to return fields `defect type, test result, release judgment`. Limit the number of returned entries to `top 20` | Focus on core data for quality traceability and defect analysis, and avoid redundant data occupying bandwidth |
| Request timeout | Set to `30–60 seconds` | Adapt to the time consumption requirements of multi-source data pulling, and avoid request failures triggered by network delays |
| PDF parsing parameters | Enable PDF parsing mode, specify the parsing page range as `1–50 pages` | Adapt to the parsing requirements of PDF format documents such as finished product inspection reports, and reduce invalid parsing content |

## Three Common Misconfigurations
- Phenomenon: The interface call returns `Api response error: undefined` with no specific error message. Cause: The `Authorization` parameter is not configured correctly, or the response format returned by the external system is not properly matched by `responseData`.
- Phenomenon: Unable to specify PDF parsing parameters when creating a file collection. Cause: No document type mapping rule is configured in the `variables` of the interface request, or the parsing switch for the corresponding format is not enabled.
- Phenomenon: The number of data entries returned after the interface call does not match the expected value. Cause: The number of entries returned by `responseData` is not limited, or request parameters are not filtered by production batch, resulting in the pulling of redundant data across batches.

## How to Verify a Correct Configuration
- Call the test interface, pass a known production batch number, and check whether the returned data includes the inspection records and defect information of that batch.
- View the interface logs, confirm that the `Authorization` parameter has been correctly carried, and there are no error records of authentication failure.
- Upload a finished product inspection report in PDF format, and check whether the interface can correctly parse the inspection items and result data.
- Simulate a batch data request, confirm that the interface response time meets the preset range, and there are no timeout errors.

The values provided here are common starting points and should be measured against the reader's own samples.
