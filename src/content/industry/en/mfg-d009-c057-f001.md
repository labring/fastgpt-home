# Quality Problem Traceability and Defect Analysis for Forging and Die Forging: HTTP Interfaces and External Systems

## What data looks like for this category
Data sources for forging and die forging scenarios include raw material quality certificates, heating furnace systems, press collection data, MES systems, non-destructive testing instruments, and customer forging drawings. Daily maintained documents cover forging process specifications, blanking cards, heating furnace records, forging process cards, mold life records, heat treatment entrustment slips, and ultrasonic testing reports.
Data is updated per piece, per batch, or per furnace run. Core fields include furnace batch number, forging batch number, forging ratio, fiber direction, ultrasonic testing defect type, and mold wear amount. Units include furnace runs, batches, millimeters, and other relevant units.

## What constraints do these characteristics impose on the "HTTP Interfaces and External Systems" link
Multi-source and scattered data sources require interfaces to support cross-system data pulling, and adapt to collection formats of different equipment such as heating furnaces, presses, and non-destructive testing instruments.
The high-frequency update rhythm per furnace run or batch requires flexible configuration of interface call frequency to avoid triggering external system current limiting.
Unique characteristics of core fields require interface requests and responses to accurately match forging scenario business parameters, rather than only using general business fields.
Defect analysis requires quick access to historical batch data, so interfaces must support precise queries by furnace batch number and forging batch number to reduce invalid data transmission.

## How to set configurations
These configurations are based on FastGPT v4.17.0.

| Configuration Item | Recommended Setting | Rationale |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {custom service key}` | Used for identity verification when connecting to external MES and non-destructive testing systems, to ensure data access security |
| `variables` | Bind furnace batch number, forging batch number, and detection time range as request parameters | Adapts to the feature of forging data being updated per furnace run or batch, to accurately pull historical data of the corresponding batch |
| `responseData` | Filter out fields including forging ID, ultrasonic testing defect type, and mold wear amount | Only extract core fields required for quality traceability and defect analysis, to reduce data transmission overhead |
| Interface call timeout | `600 seconds` | Forging data pulling involves splicing data from multiple systems, so sufficient response time must be reserved to avoid mid-process interruptions |
| Request retry count | `3 times` | Responds to temporary fluctuations in real-time data sources such as press collection data and heating furnace records, to ensure the success rate of data pulling |

## Three common configuration mistakes
- Symptom: Database connection error returns `Access denied for user`. Cause: The database access account for the forging scenario is not bound to query permissions for the corresponding furnace run or batch data, so specified batch forging data cannot be pulled.
- Symptom: Interface call returns 504 timeout status code. Cause: The timeout setting is too short without accounting for the time-consuming multi-source data splicing required for forging data, so integrated pulling of heating furnace records and press data cannot be completed.
- Symptom: Core analysis fields such as forging ratio and fiber direction are missing from response data. Cause: Forging-specific fields to extract are not specified in the `responseData` configuration, so only general business data is pulled.

## How to confirm the configuration is complete
- Initiate an interface request for query by furnace batch number, and verify that returned results include forging-specific data such as ultrasonic testing defect type and mold wear amount.
- Check interface logs to confirm the `Authorization` parameter is correctly carried, and no unauthorized access errors occur.
- Simulate batch requests using the actual daily furnace run volume, and verify that the interface call success rate meets the preset threshold.
- Confirm that the `variables` parameter is bound to the forging batch number, to ensure each request's query scope matches business requirements accurately.

These values are common starting points, and should be validated against local test samples.
