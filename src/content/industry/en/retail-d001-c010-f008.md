# JD POP seller operations: workflow routing for product questions

## What the documents look like

This page covers one task inside JD POP third-party store operations: answering product information and selection questions through workflow routing. The materials in play are the product information sheet, the dispatch time commitment, the dispute handling form, and the warranty period service record. Three industry facts shape the routing work. JD POP stores commonly handle matters around open platform dispute rules and warranty period service documents, so a question result can feed into dispute evidence or after-sales responsibility judgment, and the routing must keep the source and status of each material visible. The data sources are the JD merchant backend, the JD help center, the JD open platform rules, and logistics tracking; a question answer cannot step past these sources and produce its own conclusion. The consequences of error include a transaction dispute being upheld, expanded after-sales responsibility, and platform demerit points, so answers about address, time limits, and warranty scope must trace back to a specific document. Material update frequency is daily and per order. This page does not derive batch synchronization, full synchronization, real-time behavior, or transaction-triggered mechanisms from that frequency.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the workflow continues downward only after the user completes the interaction. It collects required information and, after submission, passes the collected values to later nodes. The User Selection node is also a user interaction node with the same interaction state and state recording; when the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. Routing must pass collected values explicitly to later retrieval, judgment, or interface nodes, and compare output against input item by item. Retrieval only returns materials; it does not perform authorization or entity isolation, and a relevance score is not a permission filter. Order writes, document backfill, and external status synchronization require a separate business interface or a later flow; a form submission by itself does not complete those actions.

Hypothetical drill sample. The source text reads: "The warranty period service record for item A in this store states: replacement service is provided within 12 months from the signing date; the applicable object is item A; the record status is accepted. The dispatch time commitment states: dispatch within 48 hours after payment. The dispute handling form states: the buyer claims item A failed on day 20 after signing; the handling status is pending evidence." The draft sentence to be judged is: "The warranty replacement request for item A has been approved and replacement can be arranged directly." The subject needed for judgment is item A, the period is within 12 months after signing, and the field is the warranty period service record status, which is accepted. The record does not state approval. The draft sentence writes pending evidence and accepted as approved, so it is unsupported.

## Configuration and implementation checks

| Configuration item | Use on this page | How to check |
| --- | --- | --- |
| Form Input node | Collect item A model, signing date, fault description | After submission, check whether values pass to later nodes |
| User Selection node | Let the user choose question type (information lookup or after-sales inquiry) | Check whether the selected branch executes its "yes" branch |
| Retrieval node | Retrieve materials from the product information sheet and warranty period service record | Check whether returned entries match the query subject |
| Judgment node | Compare the warranty period service record status field | Check same subject, same period, same field value |
| Interface node placeholder | Mark that replacement arrangement requires a separate business interface | Check whether it is declared as pending implementation, not written as executed |
| Output handoff | Pass form and retrieval results to the answer node | Compare input values against output references item by item |

This page assumes a trial starting value of 5 for the maximum number of retrieved entries. The reason for choosing it is to allow item-by-item checking of the small set of materials in this sample, and the comparison is between the actual number of returned entries and 5. This value is not an official default.

## Three common errors

1. Treating a retrieval hit as authorization. Symptom: because the warranty period service record was retrieved, the draft states the replacement request has been approved. Check: the input is the warranty period service record text above; compare the field "record status" value "accepted" against the draft sentence "has been approved"; the observed result is that the two do not match and the draft sentence does not hold.

2. Treating a user selection branch as business approval. Symptom: after the user selects "after-sales inquiry," the routing outputs that replacement has been arranged. Check: the input is the User Selection node record and the draft sentence; compare the selected branch action against the business action described in the draft sentence; the observed result is that the branch only executes a question-answer path and produces no approval or replacement arrangement.

3. Treating a form submission as completed external synchronization. Symptom: after the form collects the signing date, the draft states the system has synchronized to the order. Check: the input is the form submission value and the draft sentence; compare the Form Input node behavior against the external write action; the observed result is that the form only collects and passes values, external synchronization requires a separate interface, and the draft sentence lacks support.

## How to verify the setup

1. For the warranty period service record text and the draft sentence "The warranty replacement request for item A has been approved," the input is the record text; compare subject item A, period within 12 months after signing, and the record status field; the observed result is that the record status is accepted and does not state approval, so the draft sentence is unsupported and the evidence gap must be kept.

2. For the User Selection node, the input is the hypothetical choice "after-sales inquiry"; compare the selected branch against the downstream node connection; the observed result is that the corresponding "yes" branch is triggered and other branches are not executed. If the choice is not recorded, the case remains unverified.

3. For the Form Input node, the input is the hypothetical entry of item A, the signing date, and the fault description; compare the submitted values against the values received by the later retrieval node; the observed result is that the values are passed and match item by item. If retrieval returns an empty result, a paper input of [] can be used to check the downstream design, without claiming that a fictional rule search necessarily returns []. Libraries across different vector models cannot be associated together; check identifiers only, exclude those that do not match, and record the actual observation.
