# Franchise fee settlement: workflow routing for product questions

## What the documents look like

Franchise fee and deposit settlement centers on money received and paid plus breach deductions. It does not handle government filing. The working materials are franchise fee invoices, deposit ledgers, deduction notices, and contract payment schedules. Source systems include the finance system, franchise contracts, bank statements, and store violation records. Updates occur monthly and on each deduction.

For product information and selection questions, this means a single entry often carries the contract party, fee type, billing period, and deduction reason at the same time. A selection question has to land on one document type or one ledger row before any later reconciliation. The routing step decides which fields are collected and which branch runs, so the quality of that collection shapes every downstream comparison.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the workflow continues after the user completes the interaction. After the user fills required information and submits, the node collects the submitted form information and passes it to later nodes.

The User Selection node is also a user interaction node. It triggers the same interaction state and records workflow state. When the user makes a choice, the node evaluates that choice and executes the corresponding branch. Both nodes can be added repeatedly and trigger execution.

The constraint for selection questions: retrieval similarity does not determine fee attribution or authorization status. Fields collected through an interaction node carry the question forward to later judgment or interface nodes. Order writes, ledger backfill, and external status synchronization require a separate business interface or later process. The interaction nodes do not perform those business actions themselves.

Hypothetical paper exercise. A franchise contract payment schedule states: "Franchisee A, billing period March 2025, franchise fee 8,000, deposit 20,000, deduction reason is store violation record item 2, deduction notice has been issued." A proposed sentence reads: "The deduction has been completed and the deposit ledger has been reduced accordingly." That sentence lacks evidence of deduction execution and ledger update. It remains unsupported and cannot be judged complete.

## Configuration and implementation checks

| Configuration item | Relation to this page | Setting or check method |
| --- | --- | --- |
| Form Input node | Collects fields needed for selection questions | Enters interaction state on trigger; passes submitted information to later nodes |
| User Selection node | Branches on fee type or deduction reason | Executes the corresponding branch after user choice; verify each branch connection |
| Output handoff | Passes collected information to retrieval or judgment nodes | Compare output against input fields item by item |
| Retrieval library identifier | Confirms library and vector model identifiers | Libraries across different vector models cannot be associated together; check identifiers first and exclude non-matching ones |
| Empty result handoff | Checks downstream design | Use an explicit paper input of an empty list to check downstream handling; do not claim a fictional rule search always returns empty |
| External operation split | Ledger writes and status synchronization | Requires a separate business interface or later process; not completed inside interaction nodes |

Hypothetical starting point for this page: the Form Input node collects three fields, contract party, fee type, and billing period. This starting point is chosen because the party and period fields needed for judgment in the sample match those three. The comparison object is the field list actually received by the later node.

## Three common errors

1. Treating retrieval similarity as a permission or entity filter, so that high relevance is read as the record belonging to the current franchisee. Check: input the sample proposed sentence, compare the retrieval-returned record against the contract party field collected by the form, and observe whether both share the same party.
2. Treating a User Selection branch as business approval or completed execution. Check: input the "deduction notice has been issued" status from the sample, compare it against whether the ledger shows a corresponding reduction, and observe whether the ledger record matches the notice.
3. Treating the recorded interaction state as a global state switch or snapshot guarantee. Check: input the sample proposed sentence, compare the workflow state record against the business action record, and observe whether any business action evidence exists.

## How to verify the setup

1. Input the hypothetical sample text and the proposed sentence. Compare the contract party, fee type, and billing period collected by the Form Input node against the fields stated in the sample. When the three fields match and the proposed sentence lacks deduction execution evidence, judge it unsupported. This condition is met.
2. Input the "deduction notice has been issued" status from the sample. Compare the User Selection branch direction against the ledger record. When the branch direction is pending execution and the ledger shows no corresponding reduction, judge it pending verification. This condition is met.
3. Input a paper empty list as the retrieval result. Compare whether the downstream node handles it as an empty result. When the downstream produces no ledger write or status synchronization action, judge the handoff correct. This condition is met.
