# Brand livestream operations: workflow routing for product questions

## What the documents look like

Brand-operated livestream rooms carry their own scripting, inventory, and after-sales work. The difference from influencer-hosted sessions is the commission structure, which affects who owns and checks the material rather than what the workflow nodes themselves can do. For product information and selection questions, the inputs come from store operations dashboards, advertising tools, livestream comments, and transaction details. The everyday documents are the livestream script, the product explanation card, the shift schedule, and the livestream review.

Selection questions require the specifications, applicable scenarios, and stock status on the product explanation card to be organized into checkable inputs, then handed to workflow nodes. The material updates per session and per hour. This page does not derive batch synchronization or transaction-triggered mechanisms from that frequency. Retrieval results and form values serve only as inputs to later nodes. Retrieval and form submission do not constitute authorization, and they do not confirm an order, a stock level, or a qualification.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution waits until the user completes the interaction. The node collects required information and, after submission, passes the collected form information to later nodes. The user selection node is also a user interaction node. When the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. Both nodes record workflow state and continue downward after the user finishes interacting.

Order writing, document backfill, and external status synchronization require a separate business interface or a later process. This page does not assume automatic execution. Semantic recall and relevance scores do not handle permission or entity isolation. Libraries using different vector models cannot be associated together; identifiers must be checked first and non-matching items excluded.

Hypothetical paper exercise sample: A brand livestream team prepares a product explanation card before a June 2025 session. The source text reads: "Product A, specification 500 milliliters, suitable for oily skin, currently sellable stock 120 units, explanation card version revised June 1." A draft sentence to be judged reads: "Product A suits all skin types, and stock is sufficient for confident ordering." The subject, object, state, and validity scope needed for judgment are all inside that source text. The draft sentence changes "suitable for oily skin" into "all skin types," and changes "sellable stock 120 units" into "stock is sufficient." Both changes exceed what the source text states.

## Three common errors

1. Treating the product number collected by the form as a verified product identity. The input is the number the user filled in; the comparison object is the number in the source explanation card. The handoff condition is met only when the two match. When they differ, record the item as pending verification.
2. Treating the "yes" branch selected through the user selection node as business approval. The input is the user's selection action; the comparison object is whether the later node actually holds the conditions to execute. The selection action alone does not write an order or deduct stock.
3. Treating a retrieved product passage as authorization to release. The input is the fragment returned by retrieval; the comparison object is the applicable skin type and stock fields in the source explanation card. When the retrieved fragment and the source text differ, the fragment cannot serve as the basis for the draft.

## How to verify the setup

1. Check against the hypothetical source text and draft sentence above. The input is the explanation card source text and the draft sentence. Compare "suitable for oily skin" against "all skin types," and "sellable stock 120 units" against "stock is sufficient." When both places in the draft exceed the source range, judge the draft as unsupported and return it for revision.
2. Check with one handoff request. The input is "request to add Product A to this session's explanation order." Compare whether the request states the session, the product number, and the explanation card version. When any field is missing, record it as pending supplement and do not pass it to later nodes.
3. Check empty-result handoff. The input is an explicit paper empty result []. Compare whether the downstream node still processes it as having no product material. When the downstream node has no empty-value branch designed, record that as a gap. Do not claim that a fictional rule retrieval necessarily returns an empty result.

These verification steps describe expected conditions. They do not claim that any test, deployment, approval, or refund has actually occurred.
