# After-sales repairs and reships: workflow routing for product questions

## What the documents look like

After-sales repairs and reships aim to restore a product to use. A case closes when a repair is finished or a replacement part reaches the customer, which differs from a refund dispute path that closes on a refund decision. The working documents are repair applications, reship orders, inspection reports and parts outbound orders. These come from the after-sales system, the order system, repair sites and the parts warehouse WMS. Updates occur per order and daily. Brand after-sales teams, e-commerce service agents and the parts warehouse all take part. Judging whether a case needs repair or a reship, coordinating parts, and tracking customer confirmation consume most of the handling time.

Product-data and selection questions ask whether a part fits, which machine an inspection report belongs to, and which route a reship order should take. Answers rest on those documents. Workflow routing connects form-input nodes, user-selection nodes and later retrieval or interface nodes. A form-input node enters the interaction state when triggered, collects required information, and passes it to later nodes after submission. A user-selection node runs the matching yes branch once the user makes a choice. Recording that interaction state is behavior of the interaction node itself; no separate global state-recording switch is documented.

## Constraints at the workflow routing step

Routing must separate four kinds of action: behavior a node already has, fields that can actually be configured, manual comparison steps, and business actions that need a separate system implementation. Order writes, document backfill and external status synchronization require a separate business interface or a later process; the nodes do not perform them. Retrieval returns documents and does not grant authorization. A form collects values; business verification, approval, database writes and external synchronization each need their declared downstream implementation. A similarity setting does not exclude unrelated businesses or unauthorized records.

Hypothetical drill sample. The after-sales system holds "Reship order BS-2026-0417, subject a brand after-sales site, object a power adapter for model A, status pending review, submission date 17 April 2026, quantity 1." The parts warehouse WMS holds "Parts outbound order CK-2026-0418, object a model A adapter, status outbound, date 18 April 2026, quantity 1." The proposed sentence is "Reship order BS-2026-0417 has completed the reship." The handover request awaiting judgment is "Trigger the parts outbound synchronization directly from this reship order."

In this sample the reship order status is pending review and the outbound order status is outbound. The subjects, objects and fields differ: the reship order field is a review status, the outbound order field is an outbound status. Pending review does not mean the reship is complete, and it does not show that operating permission is missing. The proposed sentence states the reship order as complete without direct evidence of a completion status. The handover request treats a retrieval or form result as executable authorization; outbound synchronization needs a separate business interface, and the request itself is not execution.

## Three common errors

1. Treating a pending-review status as a completed reship. In the sample the reship order status is pending review and the outbound order status is outbound; the fields differ, and the proposed sentence "has completed the reship" lacks completion evidence on the same subject and field. Compare the reship order status field against a "completed" value; where the value is not stated, record it as unsupported.

2. Treating a retrieval or form result as authorized execution. The handover request asks to trigger parts outbound synchronization from the reship order. Retrieval and forms supply information and do not grant authorization; outbound synchronization needs a separate business interface. Compare the request description against the external action split; where no interface implementation is present, record it as pending verification.

3. Inferring permission isolation from a similarity setting. Retrieval returns documents, and relevance does not perform entity or permission filtering. Whether the reship order and outbound order can be retrieved depends on retrieval scope and access rights, not on the similarity value.

## How to verify the setup

1. Input the hypothetical reship order text and the proposed sentence. Compare "has completed the reship" against the reship order status field "pending review" and observe whether a completion value exists on the same subject and field. Expect unsupported, and record the evidence gap.

2. Input the handover request "Trigger the parts outbound synchronization directly from this reship order." Compare the request description against the external action split entry and observe whether a declared interface implementation exists. Expect pending verification, and do not write it as executed.

3. Use a paper input of an empty result to check the downstream handoff design. Compare the empty result against the later node design and observe whether the later node has an explicit handling description for an empty result. Expect a design-based check, without claiming that a fictional rule retrieval must return an empty result. Libraries across different vector models cannot be associated together; verify identifiers first and exclude those that do not match, record actual observations, and do not run cross-model retrieval to compare missed recall.
