# Supermarket supplier accounts: workflow routing for product questions

## What the documents look like

This page covers product information and selection questions in supermarket supplier entry settlement. The working documents are the purchase contract, the delivery acceptance note, the rebate agreement, and the reconciliation statement. Settlement in this category runs mainly as purchase-and-sale accounts or consignment accounts, and the supplier does not necessarily operate an on-site counter. Data arrives from ERP purchasing, the supplier portal, POS sales, and the finance system, and it updates weekly or monthly.

Three industry facts shape the workflow routing task. First, the documents are split across several systems, so a question about a product code may require values that live in different places. Second, the most time-consuming steps are checking accepted quantities, calculating rebate deductions, and handling return differences; each of these depends on values that a user must supply or confirm. Third, document differences feed directly into account disputes and supplier supply stoppage, so the routing step must keep collected values and branch choices traceable rather than treating them as settled business facts.

The workflow routing task here is narrow: fix the input, interaction, and output boundary for document lookup and selection questions, so that form values and user choices correspond in a checkable way to the nodes that follow.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the workflow continues after the user completes the interaction. After the user fills in the required information and submits, the node collects the submitted form information and passes it to later nodes.

The user selection node is also a user interaction node. It triggers the same interaction state and state recording. When the user makes a choice, the node evaluates that choice and executes the “yes” branch. Its basic use is to pose a question that requires a decision, then design different workflow paths from the user's response.

These two node behaviors set the constraints. Collection of document fields and branch direction are driven by interaction results. Retrieval or a form does not constitute authorized execution. Order writing, document backfill, and external status synchronization require a separate business interface or a later process. Semantic recall and relevance scores do not carry permission or entity isolation functions, and the same-vector-model requirement for a retrieval library does not extend to business registration sites or other external systems. Optional paths shown in a general workflow diagram do not mean every request executes all of them. Image retrieval requires a corresponding image input and model capability, and reranking requires a model and must be enabled according to settings.

## Three common errors

1. Treating form submission as business authorization. The form input node only collects submitted form information and passes it to later nodes; the submit action produces no approval, write, or synchronization effect. Check: input a submitted set of form values, compare whether later nodes show a write or synchronization record, and note that value passing alone matches the documented behavior.

2. Treating a user selection branch as a completed operation. The user selection node evaluates the choice and executes the “yes” branch when the user chooses; branch execution does not equal completion of an external business action. Check: input one choice result, compare the branch taken against the external system state, and note that an unchanged external state means the business action requires a separate interface.

3. Treating retrieval relevance as permission or entity filtering. Relevance is a ranking result; it does not exclude unrelated business or unauthorized records. Check: input a cross-supplier query, compare returned records against the access scope, and note that records outside the scope mean retrieval does not perform isolation.

## How to verify the setup

The verification below uses one hypothetical drill sample. Sample material text (hypothetical): the purchase contract states that supplier A supplies product code A to supermarket B in March 2025, with settlement as purchase-and-sale; the delivery acceptance note states that 120 units of product code A were accepted on 10 March 2025; the reconciliation statement states that the reconciliation period is March 2025 and that the amount payable for product code A is calculated from the accepted quantity. Draft sentence to be judged (hypothetical): “The settlement quantity for product code A for supplier A in March 2025 has been confirmed at 120 units.” The sentence does not state whether the reconciliation statement has been signed or approved, so it is unsupported.

1. Form value passing check. Input the three required values above and submit, then compare the values received by later nodes against the form entries. Three matching values with no additional write record satisfies the documented behavior of the form input node.

2. Branch execution check. Input the choice “enter settlement check,” then compare the branch actually executed against the branch corresponding to that choice. A matching branch with no change in external system state satisfies the documented behavior of the user selection node.

3. Output handoff check. Input a clearly stated paper empty result [], then compare how the downstream node is designed to handle that input. Downstream handling through an empty-result branch with no fabricated record makes the handoff design checkable; whether retrieval returns an empty result must rest on an actual observation record and is not guaranteed.
