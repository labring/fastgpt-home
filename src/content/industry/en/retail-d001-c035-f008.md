# Trade returns and claims: workflow routing for product questions

## What the documents look like

Trade returns and claims work handles reverse logistics and responsibility determination after goods have left the country. The difference from ordinary export declaration is that the goods are already abroad, and the document chain shifts from export declaration toward return reason, quality responsibility, and insurance claim. Everyday materials include the return agreement, the claim letter, the quality report, and the return customs declaration. These arrive from customer email, inspection reports, the customs system, and the insurer's claim system. Updates are irregular and progress case by case.

For workflow routing, the direct constraint is that materials arrive at different times. Different documents in the same case can sit at different stages. A quality report may be issued while the return agreement is still unsigned. A claim letter may have been sent while the insurer's claim system holds no acceptance record. Routing must preserve the state "a given material has not arrived" and let the flow stop at an interaction node to wait, then continue after a person supplies the missing item.

## Constraints at the workflow routing step

The Form Input node enters an interaction state when triggered, records the workflow state, and after the user completes required information and submits, passes the form information to later nodes. The User Selection node also enters an interaction state, and after the user makes a choice, executes the corresponding "yes" branch. These two nodes collect and route. They do not perform business verification.

The boundary that follows: retrieval results do not constitute authorization, and form submission does not constitute approval. Whether the return agreement has been signed, whether the claim has been accepted, and whether the customs declaration has been released are business facts. They require a separate business interface or a later process to confirm. The interaction node itself only passes values onward. The consistency requirement between a retrieval library and its vector model is limited to associations inside that library. It does not extend to an external business registration system or an insurer's system.

Hypothetical drill sample: the source material reads, "Return agreement (No. HYP-2024-001) signed by seller and buyer on the hypothetical date 10 March 2024, return reason is outer packaging damage, return quantity 200 pieces." The proposed handover request reads, "Please start preparing the return customs declaration based on the above material." This request lacks the return customs declaration itself and the customs release status. It is pending verification and cannot be treated as ready for execution.

## Configuration and implementation checks

| Configuration item | Setting or check relevant to this page | Basis and boundary |
|---|---|---|
| Form Input node | Collects case number, return reason, quantity | Documented to collect required information and pass it to later nodes |
| User Selection node | Used for the "materials complete" branch | Documented to execute the "yes" branch on the user's choice |
| Interaction state | Conversation enters interaction state and workflow state is recorded after trigger | Documented node behavior; no separate global switch is set |
| Output handoff | Form values passed to retrieval, judgment, or interface nodes | Compare each output against its input |
| External actions | Declaration preparation and claim acceptance connect to separate interfaces | Not documented as automatic; remains to be implemented |
| Retrieval association | Association requires the same library and same vector model | Documented that different models cannot be associated together |

This table contains no default values or limits. Numbers follow the hypothetical sample only.

## Three common errors

1. Treating the "yes" branch of the User Selection node as business approval. The input is the user clicking "materials complete." The comparison object is the return agreement signing status and the customs declaration release status. The observable result is that the branch fires while the business state is unchanged. Branch execution is not a completed signing or release.
2. Writing form submission values directly into the customs or claim system. The input is the quantity and reason in the form. The comparison object is whether a downstream interface exists. The observable result is that the form values remain in workflow variables only. Without an interface, no write occurs.
3. Using a retrieval hit in place of a permission decision. The input is the query "HYP-2024-001." The comparison object is the library scope the current account can access. The observable result is whether the hit record matches the authorized scope. A similarity score does not perform entity or permission isolation.

## How to verify the setup

1. Using the hypothetical sample source text as input, check whether the form node collected the three items: case number, return reason, and quantity. Compare the submitted variable values against the source fields. The result is satisfied when all three match and can be read by later nodes.
2. Using "materials complete" as the selection item, compare the connections of the "yes" and "no" branches. The result is satisfied when each branch points to a defined downstream node, and any unconnected point is recorded as a gap.
3. Using the proposed handover request as input, compare the materials the request needs against the materials already provided. The result is that the return customs declaration and release status are missing, recorded as pending verification, and not judged as executable or approved.
