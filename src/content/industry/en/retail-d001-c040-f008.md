# Customer-service knowledge: workflow routing for product questions

## What the documents look like

This page covers the product-data and selection-question task inside customer-service knowledge-base maintenance. The working materials for this category are FAQ entries, script templates, product parameter tables, and escalation tickets. The work is preparation of question-and-answer material ahead of customer contact; it does not approve refunds or returns directly. That separation matters for workflow routing, because a routing decision here decides which prepared answer or which follow-up path a question enters, not whether money moves.

Material updates arrive weekly or monthly. A routing design therefore has to carry parameter changes and script revisions that accumulate between cycles, and downstream nodes may need to reference the same batch of material more than once.

Inputs for product-data and selection questions typically contain a customer asking about a model, a specification, or a fit-for-use scenario. When customer-service supervisors, knowledge-base operators, and product operators hand work over, the handover has to state which materials are final and which are still pending. Fields not stated in the material stay unknown; the presence of a field in another category does not imply this category has it.

## Constraints at the workflow routing step

The Form Input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The User Selection node is also a user-interaction node. When it triggers, the conversation enters the interaction state, and when the user makes a choice the node evaluates that choice and executes the "yes" branch. Both nodes can be added repeatedly and both trigger execution.

The interaction state is behavior of the interaction nodes. No separate global state-recording switch is documented. Information collected at these nodes has to be passed explicitly to the downstream retrieval, decision, or interface node, and outputs must be compared against inputs item by item. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval and forms do not constitute authorization to execute.

Hypothetical walkthrough sample: the source material reads, "Type A water-purifier filter fits A1 and A2 models produced after January 2023; Type B filter fits A3 models, supplied from June 2023." The proposed handover request reads, "A customer asks which filter to choose for an A2 model; please confirm the answer." The subject of this request is a customer-service inquiry, the object is filter selection for an A2 model, the state is that the material states the fit relationship, and the valid scope is A2 models produced after January 2023. The material does not state when A2 production ended; that field remains unknown.

## Configuration and implementation checks

| Configuration item | Type | Description |
| --- | --- | --- |
| Form Input node | User-interaction node | Enters the interaction state on trigger; collects required information and passes it to later nodes |
| User Selection node | User-interaction node | Executes the "yes" branch after the user makes a choice; branch connections are verified one by one |
| Output hand-off check | Implementation check | Passes collected information explicitly to the later retrieval, decision, or interface node; compares outputs against inputs item by item |
| External-action separation | Implementation check | Order writes, document backfill, and external status synchronization require a separate business interface or later process |
| Interaction-state check | Implementation check | State recording is behavior of the interaction nodes; no separate global state-recording switch is documented |

The hypothetical starting point for this walkthrough is two interaction nodes. The reason for that choice is that the sample selection question needs one form collection and one branch decision; the comparison is against a flow with a single node, to observe whether branches are verified one by one. This starting point is a hypothetical value, not an official default.

## Three common errors

1. Treating a retrieval result as authorization to execute. In the sample, the proposed handover request asks only for confirmation of the answer. Finding the fit relationship does not mean the answer has been approved or that an external action has been performed. The check input is the source material and the proposed handover request; the comparison is against the authorization boundary stated in the request; the observable result is whether any action beyond "confirm the answer" appears.

2. Expanding interaction-state recording into a global state switch. The documents describe state recording as behavior of the interaction nodes. If a configuration shows a global switch that is not documented, that is an error. The check input is the node description text; the comparison is whether a global-switch description exists; the observable result is whether the configuration items stay limited to the interaction nodes' own behavior.

3. Reading an unstated field as a negative. The sample does not state when A2 production ended, so it cannot be concluded that the model is discontinued or unsuitable. The check input is the source material; the comparison is whether a discontinuation judgment appears; the observable result is whether the conclusion stops at "not stated."

## How to verify the setup

1. Using the sample source material and the proposed handover request, check whether the outputs of the Form Input node and the User Selection node are passed explicitly to later nodes. Compare the input information against the fields the downstream node receives, and observe whether any output is left unhandled. The expectation is item-by-item correspondence; no live test is claimed.

2. Using the sample question "which filter to choose for an A2 model," check whether the "yes" branch of the User Selection node is verified one by one. Compare the branch connections against the choice evaluation, and observe whether any branch is unverified. The expectation is that each branch has a corresponding connection; no live test is claimed.

3. Using the sample source material, check whether the reply goes beyond the authorization boundary of "confirm the answer." Compare the proposed handover request against the action descriptions in the draft sentence, and observe whether an order write or external synchronization appears. The expectation is that actions stay limited to confirming the answer; no live test is claimed.

An empty-result hand-off can be checked with an explicit paper input of `[]` against the downstream design. This does not claim that a fictional rule retrieval will return `[]`. Libraries using different vector models cannot be associated together; check the identifiers only, exclude the non-matching ones, and record what is actually observed.
