# Customer-service knowledge: document chunking for product questions

## What the documents look like

Knowledge-base maintenance for customer service sits upstream of after-sales handling. It organizes pre-sales and in-sales question material and does not approve refunds or returns. The material set for this task includes FAQ entries, reply templates, product parameter tables and escalation tickets. Sources include the customer-service system, product detail pages, after-sales question statistics and quality-check sampling. Updates follow a weekly or monthly rhythm, and synchronizing new-product parameters together with consolidating high-frequency questions consumes most of the working time. Failures surface as answers that miss the question, escalated complaints and failed agent training.

For product data and selection questions, the chunking task requires splitting parameter tables, applicability conditions and selection notes into units that are semantically complete. A retrieved fragment must be able to point back to its source passage and independently support a reply. A condition, its explanation and the content the condition constrains belong together. When they are separated, a selection answer loses its qualifying scope.

## Constraints at the document chunking step

One group of source data can map to several vector indexes. Retrieval recalls that source group when any one of its indexes is hit, and the vector score takes the highest value among them. The index and the source data live in different stores, so index update status needs a separate check. A successful upload does not mean retrieval has already been updated.

Semantic retrieval, full-text retrieval and hybrid retrieval each fit different situations. Precise queries for numbers and model codes rely more on full-text hits. RRF is a merge process inside the retrieval chain that combines results from multiple channels. The minimum relevance value is a filter threshold and takes effect only under semantic retrieval or result reranking; it does not perform permission or entity isolation. Reranking requires a rerank model and applies according to settings. Image retrieval requires an image input together with the relevant model capability.

Hypothetical paper exercise sample: a knowledge-base operator receives material for ingestion. The source text reads: "Type A charger supports 100 to 240 volt wide-voltage input and applies to the cross-border sales version. Type B charger supports 220 volt input only and applies to the mainland China sales version. The two chargers look similar, and the packaging label distinguishes them by the first letter of the model code." A draft sentence reads: "Type A charger and Type B charger both support wide-voltage input, so the same selection note can answer customers." This draft sentence is pending review, and no review conclusion exists.

## Configuration and implementation checks

| Configuration or check item | Value or action in this page's sample | Basis and explanation |
| --- | --- | --- |
| Segmentation completeness check | Keep the Type A and Type B voltage conditions inside their own passages | A condition and the content it constrains stay together |
| Multi-index association | One source group may carry several indexes; a hit on any one recalls it | Documented multi-vector mapping |
| Retrieval mode choice | Use full-text or hybrid retrieval first for model-code and voltage-value questions | Tuning guidance for precise code queries |
| Minimum relevance | This hypothetical trial starts at 0.5, compared against the displayed value before adjustment | The value applies only under semantic retrieval or reranking |
| Reference cap | Controlled by tokens; this hypothetical trial starts at 3000 tokens | Chunk lengths vary widely in mixed knowledge bases |
| Post-update recheck | After material changes, check actual training and index status | A successful upload is not the same as updated retrieval |

The 0.5 and 3000 values are starting points chosen for this paper exercise so that a comparison method exists. They are not official defaults. The comparison method is to read the value currently shown in the interface, record it, and then compare retrieval behavior before and after any change.

## Three common errors

1. Merging the Type A and Type B voltage conditions into one passage. After retrieval hits that passage, the applicable version can no longer be distinguished and the reply scope is wrongly widened. Check: enter the keywords from the draft sentence, compare whether the recalled fragment still contains each model code and its voltage limit, and observe whether the two conditions have become mixed.
2. Treating an uploaded material as an already-updated index and using it for replies without checking training status. Check: after a material change, search separately by model code and by voltage value, compare the returned content against the changed source text, and observe whether the old parameters still come back.
3. Inferring from a minimum relevance value that a certain model's material has been excluded or that a certain business category is inaccessible. Check: examine the correspondence between retrieval results and permission configuration, compare filtered content against unauthorized content, and observe whether a threshold is being treated as a permission decision.

## How to verify the setup

1. Input the hypothetical sample source text and the draft sentence. Compare whether the draft sentence agrees with the Type A and Type B voltage descriptions in the source. If the draft sentence merges the two conditions, the draft is unsupported and each model must be stated separately according to the source.
2. Input the model code keyword and the voltage value as separate searches. Compare whether the recalled fragments keep each model code and its full applicability limit. If a fragment is missing its condition, the segmentation is incomplete.
3. After a material change, search the same model code again. Compare the returned content against the changed source text. If the old parameters still return, record an index update gap and do not treat the upload action as updated retrieval.

An empty-result case can be checked on paper with an explicit empty input. Record what the downstream design returns and what remains unknown; do not assert that a rule will always produce an empty list. When libraries use different vector models, they cannot be associated together. Check the identifier first, exclude non-matching libraries, and record the actual observation instead of predicting recall behavior. Retrieval is not authorization. Forms collect values, and business verification, approval, database writes and external synchronization each need their own stated downstream implementation.
