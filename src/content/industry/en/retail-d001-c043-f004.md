# Multi-store management: vector indexes for product questions

## What the documents look like

Multi-store matrix operations for product information and selection questions work across four recurring materials: store authorization lists, price control tables, cross-territory complaint tickets, and monthly sales reports. These materials share three traits that matter at this step. They span stores and channels, so one product may carry different authorization states and price ranges per store. They update daily or monthly, so an index built from one snapshot may not reflect the current list. And the same product identifier can appear in several documents with different surrounding conditions.

For vector retrieval, the practical consequence is that each indexed passage must state its own subject, object, and validity scope. A natural-language question such as whether a model is sellable in a given channel is matched against the text of these documents, not against an authorization database. Where a document is missing, or where only evidence from a related stage exists, the retrieval result can only be recorded as pending verification. Retrieval returns cited content; business verification, approval, and any downstream synchronization require their own implementation.

## Constraints at the vector indexes step

Knowledge bases selected together for vector search must use the same vector model. Confirm the actual model identifier and the input types it supports before linking; a knowledge base on a different model cannot be jointly associated. This requirement applies to the retrieval knowledge bases and does not extend to external systems such as business registration sites.

One original data block may map to multiple indexes. The `indexes` field in `MongoDB` `dataset.datas` records the corresponding vector IDs as an array, so a single data block can carry several vectors. Index content and original content are checked separately. Index content works better when complete and focused; retrieval coverage and index length are weighed against the sample at hand. For image retrieval, whether an image can be found depends on whether an index was created at ingestion, not only on whether an image was supplied at query time.

Semantic recall and relevance scores do not perform permission or entity isolation. A similarity threshold is not a category, entity, or authorization filter, and retrieval is not authorization. After a model or index change, compare cited original text using the same set of questions; a vector score alone does not support a claim about outcome. The overall retrieval flow combines several paths, and not every path runs on every request: image retrieval requires image input and model capability, and `Rerank` requires a model and its configured activation.

## Configuration and implementation checks

Hypothetical paper exercise sample. A brand e-commerce lead holds a Store Authorization List whose text reads: "Store A is authorized to sell model X, authorization period 1 January 2025 to 31 December 2025; Store B is not listed in this list." A draft sentence is submitted for review: "Store B may sell model X." The materials do not state Store B's authorization status and do not state whether any supplementary authorization exists outside the list.

| Configuration item | Hypothetical starting point for this exercise | Comparison and reason |
| --- | --- | --- |
| Linked knowledge bases | One library containing only this brand's materials | Compare against the same-vector-model requirement; exclude libraries on other models |
| Vector model | Record the actual model identifier | Check against supported input types; no default value is assumed |
| Index content | Authorization list segmented by store and model | Compare against original completeness; avoid over-long index content |
| Image index | No image input in this sample | Check whether image description or image vector indexes were generated at ingestion |
| Search mode | Semantic search or hybrid search | Compare against question type; identifier-style queries can use full-text search |
| Citation limit and minimum relevance | Set and recorded for this exercise | Compare cited original text across the same question set |

## Three common errors

1. Reading "Store B is not listed in this list" as "Store B has no authorization." The list states only that Store B is absent from it; supplementary authorization is not stated, so the correct record is unsupported.
2. Treating a retrieval hit as authorization confirmation. Retrieval returns cited content only; business verification and authorization execution need a separate system implementation.
3. Jointly associating libraries on different vector models. Confirm the model identifier first and exclude non-matching libraries; do not run a cross-model retrieval to compare missed recalls.

## How to verify the setup

1. Input the hypothetical original text above together with the draft sentence "Store B may sell model X." Compare the draft against the original on subject, object, and validity scope. Where the original does not state Store B's authorization, the draft is judged unsupported. The materials do not state Store B's status, and this gap is preserved.
2. Input the same question twice and compare whether the cited original text is consistent, then check whether the cited length falls within the configured range. For an empty result, use the explicit paper input `[]` to check the downstream design; this does not assert that any particular query returns an empty array.
3. After changing index content, use the same question set to compare whether the cited original text still covers the authorization period and store scope, and record what is actually observed. First-position hits and complete recall are not guaranteed. Where an index change is made, the observation is recorded as an observation, not as a passed acceptance.

Across all three checks, an unsigned termination is not a completed termination, a pending request is not an approval, and an offered option is not an execution. Where a needed record is missing from the accessible retrieval scope, the gap is recorded rather than filled with an invented authorization or effective clause.
