# Seller ratings management: workflow routing for product questions

## What the documents look like

Seller ratings and experience-score maintenance in platform e-commerce operates on consumer feedback that arrives after fulfillment. The work does not set promotional prices, which separates it from campaign registration. The main data sources are Douyin Shop experience scores, Tmall service indicators, JD after-sales reviews, and customer service systems. Day-to-day documents include negative-review handling records, experience-score detail sheets, service diagnostic reports, and rectification ledgers. Typical roles are store operations staff, customer service supervisors, and quality inspection specialists. Data updates daily or weekly; this page's workflow routing does not depend on update cadence, so synchronization mechanics stay out of scope.

Product information and selection Q&A in this category carries two input types. One is the reference material for product attributes, specifications, and applicable scenarios. The other is the selection questions that must be confirmed with consumers or internal staff during ratings maintenance. Workflow routing organizes these materials and open questions into an interactive, inheritable, checkable node sequence, and it separates what a node already does from what needs a separate business interface.

Consider a hypothetical paper exercise. On 10 June 2025 a store operations staff member submits a negative-review handling record. The record states: "Order A was signed for on 3 June; the consumer reported that the product dimensions did not match the page description; customer service contacted the consumer to request supporting evidence; as of 10 June no evidence had been received; the rectification ledger status is pending supporting evidence." The proposed handoff request reads: "Based on this record, determine whether the negative-review handling process can be closed." The subject is Order A, the object is the dimension-mismatch negative review, the status is pending supporting evidence, and the effective scope runs through 10 June. The question to decide is whether the request meets closure conditions.

## Constraints at the workflow routing step

The Form Input node enters an interaction state when triggered, collects required information, and passes that information to later nodes after submission. The User Selection node executes the corresponding "yes" branch after the user makes a choice. Both nodes record workflow state and wait for the interaction to complete before continuing. The interaction state is node behavior; no separate global state-recording switch exists.

A retrieval relevance score does not carry permission or entity-isolation duties, and retrieval itself is not authorization. Libraries across different vector models cannot be associated together; check identifiers first and exclude non-matching ones rather than running cross-model retrieval to compare missed recalls. Optional paths shown in the overall workflow diagram do not all execute on every request: image retrieval requires a corresponding image input and model capability, and reranking requires a model and must be enabled in settings. An empty-result handoff can be checked with the explicit paper input [] against downstream design; no claim can be made that a fictional rule retrieval necessarily returns [].

Order writes, document backfill, and external status synchronization require separate business interfaces or later processes. Form-collected values, retrieved fragments, and user-selection branches are internal workflow data flows; they are not business approval, refund, or completed rectification.

## Configuration and implementation checks

| Configuration item | Purpose on this page | How to check |
| --- | --- | --- |
| Form Input node | Collect required information for selection Q&A, such as order number, feedback type, evidence status | After submission, check whether the information passes to later nodes |
| User Selection node | Provide a branch for questions such as "continue collecting supporting evidence" | Verify each "yes" branch connection matches the selection result |
| Interaction state check | Confirm the dialogue enters interaction state and records workflow state after triggering | Observe dialogue state after node trigger; no separate global switch is set |
| Output handoff check | Pass collected information explicitly to retrieval, judgment, or interface nodes | Compare output and input fields item by item |
| External action separation | Order writes, document backfill, external status synchronization connect to separate interfaces | Confirm no implicit write or synchronization inside the workflow |
| Retrieval scope check | Confirm the retrieval library identifier matches the vector model identifier | Exclude cross-model library association; record actual observation |

The table specifies no numbers, defaults, or global switches. This page claims no automatic approval, automatic closure, or automatic synchronization capability.

## Three common errors

1. Treating form submission as business authorization. In the exercise sample, customer service contacted the consumer but received no evidence. If the form collects a "contacted" field, submission means only that information collection finished; it does not mean the negative-review handling can be closed. The error is equating node output with an approval conclusion.
2. Treating the "yes" branch of User Selection as completed execution. The User Selection node executing the "yes" branch means only that the flow moves to that branch; it does not mean evidence was supplied or rectification finished. In the sample the rectification ledger status is pending supporting evidence, and branch selection does not change that status.
3. Treating retrieval relevance as an entity or permission filter. Retrieved fragments and scores do not exclude unrelated orders or unauthorized records. If the sample retrieves dimension feedback from another order, that cannot be used to judge Order A's handling conditions.

## How to verify the setup

1. Input the hypothetical exercise sample text and the proposed handoff request; compare whether the fields collected by the Form Input node include order number, feedback type, and evidence status. If later nodes receive these fields after submission, the form handoff meets the condition; if fields are missing, record the gap.
2. Input the proposed handoff request; compare the branch direction of the User Selection node for "continue collecting supporting evidence." If the selection result matches the "yes" branch connection, the branch configuration meets the condition; if the branch is unconnected or the selection does not trigger the corresponding branch, record it as pending verification.
3. Input the paper empty result []; compare whether downstream nodes handle it according to empty-result design. If downstream nodes have a defined handling path for [], the empty-result handoff meets the condition; if no corresponding design exists, record it as unsupported. None of the three verifications claims actual testing; each states expectations and observation methods only.
