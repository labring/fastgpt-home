# Marketplace category access: model connections for product questions

## What the documents look like

Category access work happens before a product is listed or a store is onboarded. The material set is made of subject credentials and authorization chains: a business license, a trademark registration certificate, a brand authorization chain, and any industry license. Platform recruitment pages, the national enterprise credit information disclosure system, trademark office data, and license systems are the usual sources. These documents are resubmitted at each onboarding attempt, and updates are irregular.

The model connection and configuration step takes those same documents into a knowledge base so that product material and selection questions can draw on them. A language model and an index model are the minimum system requirement. Without either one, question answering and retrieval cannot operate.

## Constraints at the model connections step

The material is made of licenses and authorization files, so questions turn on subject name, document number, authorization scope, and validity period. AI Proxy is a required dependency. Both the App and the Admin service must set `AIPROXY_API_ENDPOINT` and a non-empty `AIPROXY_API_TOKEN`; if either is missing, startup validation fails. Legacy OpenAI environment variables and a single-model custom request address cannot replace those two settings. `AIPROXY_API_ENDPOINT` holds the service root address and does not carry a `/v1` suffix. Model capability is checked against the input the application needs, with multimodal input, tool choice, and thinking configuration verified separately. Application parameters are set in the application or node configuration; there is no basis to assume that a same-named field on a compatible chat interface overrides orchestration. Retrieval and relevance scores do not carry permission or entity isolation duties. Retrieval is not authorization.

Hypothetical paper exercise. A subject submits a business license with unified social credit code 91330100MA2XXXXX0A, business scope "prepackaged food sales," registration status "active," valid until 31 December 2030. The same subject submits a brand authorization letter naming the authorized party "Hangzhou Example Trading Co., Ltd.," authorized category "grain, oil and seasoning," authorization period 1 January 2026 to 31 December 2026. A proposed sentence reads: "The store has obtained brand authorization for the grain, oil and seasoning category and may submit a category onboarding application." The handover request to be judged reads: "Please confirm from the above material whether the category onboarding submission may be executed."

## Configuration and implementation checks

The settings below come from the official environment variable and model configuration documents and are limited to material checking and question answering for this page.

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison object |
| --- | --- | --- |
| `AIPROXY_API_ENDPOINT` | `http://aiproxy:3000` | Documented example form; compare with the service root address and confirm no `/v1` is appended |
| `AIPROXY_API_TOKEN` | A non-empty administrator token assumed for this exercise | Compare with the AI Proxy server configuration and confirm it matches and is non-empty |
| Model types | At least one language model and one index model | Compare with the system minimum requirement and confirm both types are enabled |
| Index model `defaultToken` | 512 assumed for this exercise | Compare with the actual token count of the text split and confirm the split does not exceed it |
| `CHAT_MAX_QPM` | `5000` | Compare with the package limit; where the package states otherwise, the package limit governs |
| `FILE_URL_EXPIRED_DAYS` | `90` | Compare with the retention period the material short link needs and confirm it covers the checking cycle |

Model status probing applies only to system models that are currently enabled. The probe interval accepts an integer between 5 and 60 minutes. After a probe request fails, the system retries at most 3 times, so a single round makes at most 4 attempts; only when all 4 attempts fail is the result judged abnormal. A model that stays abnormal does not trigger repeated pushes. A fault alert fires when the status changes from non-red to red, and a recovery notice fires when it changes from red.

## Three common errors

1. Writing `AIPROXY_API_ENDPOINT` as a full request address with `/v1`. The input is the address string that was entered; the comparison object is the service root address form the document requires; the observable result is an address without `/v1` and a passing startup validation.
2. Treating a retrieval hit as a qualification authorization. The input is the authorization letter fragment returned by the knowledge base; the comparison object is the authorized party, category, and period stated in the original letter; the observable result is question answering output that matches the original text and contains no conclusion beyond the authorized scope.
3. Treating a pending review status as an approval. The input is a field marked "under review" in the material; the comparison object is a confirmable approval or rejection record; the observable result is that the item stays pending verification and no statement of completed onboarding is produced.

## How to verify the setup

1. Enter the business license text from the hypothetical exercise and the proposed sentence. Compare "may submit a category onboarding application" in the proposed sentence against the registration status and authorization period stated in the material. The observable result is that the proposed sentence is either supported or retains a gap; no definite onboarding conclusion appears.
2. Enter the brand authorization letter text from the hypothetical exercise and the handover request. Compare the authorized party, authorized category, and authorization period. The observable result is that all three match the original text; if the authorization period has already ended, the request remains unsupported.
3. Enter a material field explicitly marked "under review." Compare that field against an effective approval record. The observable result is a pending verification state; the item is not judged approved and not judged rejected.

These checks test the named primary task of model connection and configuration for product material and selection questions. They do not test identity certification, report analysis, or any other task. Where a document field is not provided, the value remains unknown.
