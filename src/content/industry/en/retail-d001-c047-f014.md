# Marketplace returns: model connections for product questions

## What the documents look like

Platform refund and return handling runs continuously per order and does not necessarily connect to a single live-stream promise. The after-sales backend keeps refund requests, return waybills, quality-inspection photos and refund approvals as separate records. Product-data and selection questions must answer what state a given order is in, which item it concerns and which rule applies. Those judgments depend on order number, item identifier, application time and approval result being present together. Records update per order and per day; a state change in one application does not automatically flow into conclusions about other orders.

## Constraints at the model connections step

Model connection determines whether question answering can reach product data; configuration determines the range it draws from. AI Proxy is a required dependency from V4.17.0. The App and any Admin service reusing App/Service configuration must set `AIPROXY_API_ENDPOINT` and a non-empty `AIPROXY_API_TOKEN`; missing either causes startup validation to fail. Legacy OpenAI environment variables or a single-model custom request address cannot replace these two settings. The system needs at least one language model and one index model to operate normally, and only one speech-recognition model takes effect.

Hypothetical paper exercise sample: on 10 March 2026 a platform after-sales specialist submits a refund request, order number A-20260310-017, item a particular insulated bottle model, reason written as "lid damaged on receipt." The same day the warehouse inspection photo note reads "crack along the lid edge, body intact," the refund approval field reads "pending review," and the return waybill shows "signed for." Draft sentence to check: "This order has completed its refund, and responsibility rests with the warehouse." This sentence carries subject, object and state, so it can be compared field by field.

## Configuration and implementation checks

Configuration is organized around checking that sample; database internals are not copied in as mandatory items. Numeric entries are starting points for this exercise only, with the reason for choosing them and the comparison object stated.

| Configuration item | Starting point for this exercise | Reason and comparison object |
| --- | --- | --- |
| AIPROXY_API_ENDPOINT | AI Proxy service root address | Per official requirement, no `/v1` or `/chat/completions` appended; compare against the documented format |
| AIPROXY_API_TOKEN | Non-empty administrator token | Official requirement is consistency with the server side; distinguish from an application API key |
| Language model and index model | One each enabled | Official requirement is at least one of each; compare against the enabled list |
| Model type | Checked against the input the question needs | Multimodal and tool-calling verified separately against model metadata fields |
| Quote content limit | Assumed set to 120000 | Exercise starting point only; compare against sample record length |
| Application parameters | Set in the application or node configuration | No assumption that same-named fields on a chat endpoint override orchestration; compare against node configuration |

## Three common errors

1. Filling `AIPROXY_API_TOKEN` with an application API key. Input is the token to be filled plus the official description of the administrator token; compare the two identities; observe whether startup validation passes.
2. Treating "pending review" as an approved refund. Input is the sample's refund approval field reading "pending review"; compare it against the draft sentence "has completed its refund"; observe whether the two states agree.
3. Treating a similarity score as a permission filter. Input is the similarity value returned by retrieval plus the sample order number; compare whether returned records belong to that order; observe whether records from unrelated orders appear.

## How to verify the setup

1. Take the sample text "the refund approval field reads pending review" and the draft sentence "This order has completed its refund, and responsibility rests with the warehouse." Compare the approval-state field. The sentence gains support only when the approval field shows approved and the responsibility field carries an explicit entry; at present it is pending verification.
2. Take the sample waybill "signed for" and the inspection photo note "crack along the lid edge, body intact." Compare the damaged part against the stated reason. The damage description agrees only when both point to the same part.
3. Take the retrieval result and order number A-20260310-017. Compare record ownership. The condition holds only when every returned record belongs to that order; if records from other orders appear, record the outcome as pending verification and do not judge permission or entity isolation from it. For an empty result, a paper input of `[]` can be used to check downstream design; no claim is made that a given rule's retrieval necessarily returns empty.
