# Parcel labels and handoffs: model connections for product questions

## What the documents look like

Parcel handoff happens at the point where a package leaves the warehouse, and the central fact is carrier scan responsibility. The working materials are electronic waybills, handoff lists, pickup scan records and exception item registrations. Updates arrive per batch and per day, so the same batch leaves separate records at printing, handoff and verification stages, and field definitions can differ between them.

Product data and selection questions must answer what state a specific waybill or handoff record occupies at a given time, and whether a proposed sentence can be supported by the available material. A scan record that shows 38 of 40 listed pieces does not describe a completed handoff. A registration still marked pending verification does not describe a final outcome. These distinctions matter because the consequence of error in this category includes false shipment, lost-item disputes and platform shipping timeout.

## Constraints at the model connections step

Model access runs through AI Proxy. Both App and Admin must set `AIPROXY_API_ENDPOINT` and a non-empty `AIPROXY_API_TOKEN`; missing either one causes startup validation failure. `AIPROXY_API_ENDPOINT` takes the service root address without an appended `/v1`. From V4.17.0, AI Proxy is a required dependency, and legacy OpenAI environment variables or single-model custom request addresses cannot replace these two settings.

Model channels, model IDs and model aliases are recorded separately. The model ID is the value of the `model` field in the request body and is globally unique. The model name is a display label that can be customized. A name appearing in a selection question must be matched against the identifiers in the configuration one by one. One model can be configured across different channels for load balancing, and channel priority ranges from 1 to 100, where a larger value is selected more readily.

Retrieval results supply text relevance only. They do not constitute an authorization judgment. Whether material belongs to a particular outlet or batch requires separate verification against identifiers.

Hypothetical paper exercise sample: a warehouse shipping group retains one paper record whose original text reads "Batch A-0312 dated 12 March 2026, handoff list states 40 pieces, pickup scan records show 38 pieces scanned, exception item registration records 2 pieces awaiting carrier confirmation, registration status pending verification." The proposed sentence to be assessed is "All 40 pieces in this batch have completed pickup handoff." The material does not state the final handling outcome for the 2 exception pieces, and it does not state signature or effective information.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting value | Reason and comparison object |
| --- | --- | --- |
| `AIPROXY_API_ENDPOINT` | Assume `http://aiproxy:3000` | Matches the documented example form; compare whether `/v1` was appended |
| `AIPROXY_API_TOKEN` | Assume a non-empty administrator token | Matches the documented required condition; compare whether it is empty |
| Model types | Assume one language model and one indexing model enabled | Matches the documented minimum requirement; compare whether either is absent |
| Model ID and alias | Assume filled per the model ID inside the channel | Matches channel configuration; compare names cited in questions |
| Probe interval | Assume 10 minutes | Documentation supports integers from 5 to 60; compare whether out of range |
| Retrieval scope | Assume limited to this batch's material | Matches handoff record identifiers; compare whether other batches appear |

## Three common errors

1. Treating "pickup scan records show 38 pieces scanned" as completion of all 40 pieces. Input is the sample original text and the proposed sentence; comparison is scanned piece count against listed piece count; the observable result is that the two are unequal and the exception item status is pending verification, so the proposed sentence is unsupported.

2. Treating a retrieval hit as authorization. Input is one retrieval request; comparison is returned text against material ownership identifiers; the observable result is that the hit text carries no outlet or batch permission field, so access cannot be concluded from it.

3. Treating a pending verification registration as a handling conclusion. Input is the exception item registration original text; comparison is the registration status field against the proposed conclusion; the observable result is that the status remains pending verification and a final handling record is absent.

## How to verify the setup

1. Input the hypothetical original text and the proposed sentence; compare the three fields of listed piece count, scanned piece count and exception item status. The proposed sentence is supported only when all three agree and the exception item status is handled. In this observation they do not agree.

2. Input one retrieval request limited to this batch; compare the batch identifiers of returned text against the request scope and observe whether all fall within A-0312. If text from another batch appears, record it as a scope mismatch.

3. Input an empty-result continuation scenario, assuming retrieval returns `[]`; compare whether downstream display handles it as an empty result and observe whether a conclusion without source appears. This behavior depends on downstream implementation and is not determined here.
