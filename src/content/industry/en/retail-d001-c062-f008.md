# E-commerce warehouse receiving: workflow routing for product questions

## What the documents look like

Receiving and putaway handles the first physical-and-record confirmation when goods enter a warehouse. The data sources named in the brief are the WMS, ERP purchasing, supplier delivery notes, and barcode scanning. The documents handled day to day are purchase arrival notes, receiving inspection sheets, putaway tasks, and discrepancy reports. The three most time-consuming steps are checking arrival quantities, printing barcodes, and assigning storage locations. Material updates occur per batch and daily. These facts shape which fields a workflow must collect: material, quantity, location, and discrepancy status, with interaction nodes passing submitted values to later nodes.

FastGPT v4.17.2 documents two interaction nodes relevant here. The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes required information and submits, the node collects the submitted form information and passes it to subsequent nodes. The user selection node is also a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and when the user makes a selection the node evaluates that selection and executes the "yes" branch. Both nodes can be added repeatedly and trigger execution.

## Constraints at the workflow routing step

Form collection and retrieval do not constitute authorization to execute. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. The same-vector-model requirement for knowledge-base association applies only to knowledge-base association; it does not extend to external systems. Empty-result handling can be checked against an explicit paper input for the downstream design.

Hypothetical drill sample: the source material reads "Supplier delivery note number H-01, material code M-100, arrival quantity 80 boxes, purchase arrival note PO-200 agreed quantity 80 boxes, receiving inspection sheet YS-300 records actual receipt 80 boxes, date 2025-03-10, receiver A." The draft sentence under review is "This batch's arrival quantity matches the purchase arrival note, so a putaway task can be generated and inventory can be written." That sentence involves a quantity-match judgment and a business write; the material does not state the authorized write scope.

## Configuration and implementation checks

| Configuration item | Setting or check for this page | Relation to the sample |
| --- | --- | --- |
| Form input node | Set material code, arrival quantity, and inspection quantity as required fields | Collects M-100 and 80 boxes |
| User selection node | Set "quantity matches / does not match" branches and verify each connection | Evaluates the draft sentence's quantity conclusion |
| Output handoff | Pass collected information explicitly to later retrieval, judgment, or interface nodes | Compare output against input |
| Interaction state check | Recorded state is interaction-node behavior; no separate global switch is asserted | Wait for submission before continuing |
| External operation split | Inventory writes and document backfill connect to a separate business interface | The draft sentence's write needs separate authorization |
| Retrieval association check | Check the vector model identifier first and exclude non-matching ones | No cross-model retrieval comparison is performed |

Hypothetical trial starting point: set the "quantity matches" judgment threshold at 0, on the reasoning that two values must be equal to be judged matching, compared against the draft sentence's "matches" wording.

## Three common errors

1. Treating form collection as authorized execution. Input is the draft sentence "a putaway task can be generated and inventory can be written"; compare whether the material states write authorization; if it does not, the write action remains unverified.
2. Treating retrieval similarity as an entity or permission filter. Input is an M-100 query; compare whether returned records are the same material; if other materials appear they must be excluded, and no permission inference is drawn.
3. Treating the user selection "yes" branch as already executed. Input is the user selection node branch; compare whether submission actually occurred; without submission the branch is not executed.

## How to verify the setup

1. Input the hypothetical source material and the draft sentence; compare the quantity fields 80 boxes and 80 boxes; if the two values are equal and in the same field, the quantity-match judgment holds; write authorization remains unverified.
2. Input a paper empty result []; compare whether the downstream design explicitly handles the empty value; if the downstream displays no records without error, empty-result handling holds.
3. Input the user selection node's "quantity matches" option; compare whether submission occurs; if after submission the "yes" branch is entered, the branch connection holds; without submission the record remains pending interaction.
