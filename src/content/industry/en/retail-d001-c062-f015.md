# E-commerce warehouse receiving: retrieval for product questions

## What the documents look like

Receiving and putaway is the first physical-and-ledger confirmation that goods have entered the warehouse. The working data comes from WMS, ERP purchasing, supplier delivery notes and barcode scanning. The documents handled each batch and each day are the purchase arrival note, the receiving inspection sheet, the putaway task and the discrepancy report.

Product reference and selection questions in this setting usually concern the item name, model, barcode, inspection status and location assignment recorded on those documents. These fields frequently appear as codes, model numbers and proper nouns. Full-text retrieval depends on keyword hits; semantic retrieval depends on vector similarity. The two paths suit different question shapes, and one does not replace the other.

The brief states that this material updates per batch and per day. That frequency is not used here to infer any batch synchronization, full synchronization, real-time trigger or transaction-driven mechanism.

A receiving inspection sheet may show a status such as pending quality inspection. It does not, by that fact alone, show that inspection finished, that putaway is authorized, or that the goods may be sold. A putaway task record shows an assigned location; it does not by itself show that the goods were moved. These are separate facts at separate stages.

## Constraints at the retrieval step

The knowledge base search node can link one or more knowledge bases that use the same vector model. Knowledge bases with different vector models cannot be linked together. The correct action is to check the model identifier of each candidate base, exclude those that do not match, and record what was excluded. Cross-model retrieval is not performed in order to compare missed recalls.

Quoted content is output as an array, and its length may be zero. The downstream chain still runs when nothing is found, so the downstream design must accept an empty array. A pending request is not an approval, and an offered option is not an execution.

The minimum relevance value is a filter threshold. It takes effect only under semantic retrieval or when result reranking is used. It is not a category filter, an entity filter or a permission filter. Retrieval is not authorization, and a similarity setting does not exclude unrelated businesses or unauthorized records.

Hybrid retrieval combines multiple result paths through RRF. RRF is the fusion process applied to those results; it is not a switch that is turned on. Image retrieval requires image input and the corresponding model capability. Reranking requires a rerank model and must be enabled according to configuration. The optional paths listed in the documented pipeline do not mean that every request executes all of them.

Hypothetical paper exercise. The material supplied for checking is a receiving inspection sheet reading: "Purchase arrival note PO-2026-0417, item name: stainless steel vacuum flask, model: SJ-500, arrived quantity 120 units, inspection status is pending quality inspection, location: Zone A temporary holding." The draft sentence to be judged is: "This model has completed inspection and can be put away for sale." The source shows only that inspection status is pending quality inspection. It does not state that inspection was completed or that putaway for sale is permitted. The draft sentence is not supported by the source and is marked as pending verification.

The quoted content limit is expressed in tokens, which is the documented unit. It is not a count of items. The starting values above are trial values chosen for this exercise and are not official defaults.

## Three common errors

1. Treating a pending inspection status as completed inspection. The sample source states only "inspection status is pending quality inspection," while the draft sentence states that inspection is complete and putaway for sale is permitted. The comparison must use the same subject, the same period and the same field. Where the field value is not stated, the claim is unsupported, not disproven.

2. Treating the minimum relevance value as a permission or entity filter. That value takes effect only under semantic retrieval or result reranking, and it filters low-relevance results. No conclusion follows from it about unrelated businesses or unauthorized records being excluded.

3. Linking knowledge bases that use different vector models. The node requires linked knowledge bases to share the same vector model. Where identifiers do not match, the base is excluded and the exclusion is recorded. No claim is made about missed recalls or redundant results after such a link, because that link is not performed.

## How to verify the setup

1. Input the sample source text and the draft sentence. Compare "inspection status is pending quality inspection" against "has completed inspection and can be put away for sale." The check is satisfied when the draft sentence is marked unsupported or pending verification, rather than accepted or treated as contradicted.

2. Input the sample question and the knowledge base that uses one vector model. Run semantic retrieval and full-text retrieval separately. Compare the content returned by the two paths and record what is observed. The check does not guarantee a first-position hit, complete recall, or an empty result for an irrelevant query.

3. Input a paper array of [] and check whether the downstream chain runs through and preserves the empty result. The check is satisfied when the downstream design accepts the empty array. It is not a claim that any retrieval rule always returns [].

Across all three checks, the same subject, the same period and the same field must be used. Only explicitly mutually exclusive values in one field constitute a contradiction. A status that is not stated, or evidence that shows only an earlier stage, is recorded as unsupported or pending verification. Missing evidence stays missing.
