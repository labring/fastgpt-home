# Creator sales campaigns: workflow routing for product questions

## What the documents look like

Creator sales campaigns depend on external creator performance and commission settlement rather than on internal brand scheduling. Brand business teams, MCN agencies, and creator managers handle four recurring document types around each live session: creator cooperation agreements, commission setting sheets, sample shipment forms, and live session reports. The product information and selection Q&A step draws verifiable fields from selected alliance listings, creator marketplace profiles, creator historical data, and store transaction details to judge whether a given creator fits the product mix of a specific session. These materials update per session or weekly; this page does not depend on real-time synchronization.

## Constraints at the workflow routing step

Workflow routing here handles information collection, conditional branching, and result handoff. The form input node enters an interaction state when triggered, records the workflow state, collects required fields, and passes submitted values to later nodes. The user selection node also enters an interaction state, and after the user makes a choice it executes the corresponding "yes" branch. Interaction state recording is behavior of the interaction nodes themselves; no global state recording switch is documented. Retrieval and form collection do not constitute authorization. Order writes, document backfill, and external status synchronization require a separate business interface or downstream process.

Hypothetical paper exercise: On 10 June 2025 a brand business team receives a draft creator cooperation agreement. The supplied text reads: "Party A commissions Party B to complete two live sessions between 1 July 2025 and 31 July 2025; commission is settled at fifteen percent of actual transaction value; the sample shipment form number is YP-2025-0610." On the same day a proposed routing sentence arrives for review: "The creator has completed agreement signing, so selection Q&A may proceed and sample shipment may be arranged." Comparison point: the draft shows no signing status, and the proposed sentence states signing as complete. The proposed sentence is unsupported.

## Configuration and implementation checks

| Configuration item | Type | Relation to this page's documents |
| --- | --- | --- |
| Form input node | Node | Enters interaction state when triggered, collects required fields, passes values to later nodes after submission |
| User selection node | Node | Executes the corresponding "yes" branch after the user makes a choice; verify each branch connection |
| Interaction state check | Check item | State recording is interaction-node behavior; no separate global state recording switch is documented |
| Output handoff check | Check item | Confirm collected values are explicitly passed to later retrieval, judgment, or interface nodes, comparing output against input item by item |
| External action separation | Check item | Order writes, document backfill, and external status synchronization require a separate business interface or downstream process |

Hypothetical starting point for this exercise: the form input node collects three required fields. This quantity is chosen because the sample agreement draft carries three items to verify: cooperation period, commission rate, and sample shipment form number. These are compared against the two branch conditions of the following user selection node.

## Three common errors

1. Treating a draft agreement status as signed. In the sample, the supplied text states only the commission period and commission rate, and does not state signing status. The proposed sentence reads "has completed agreement signing." Input is the draft text; the comparison is whether a signing field exists; the observable result is that the draft contains no signing record.
2. Treating a retrieval result as authorization to execute. In the sample, selection Q&A retrieval reaches creator historical data. Input is the returned retrieval records; the comparison is whether an authorization field is present; the observable result is that the retrieval records contain no authorization information.
3. Treating a user selection branch as an automatic judgment. In the sample, the user selection node requires a user choice before executing the "yes" branch. Input is the node configuration; the comparison is whether branch connections have been verified one by one; the observable result is that without verified branch connections the execution path cannot be confirmed.

## How to verify the setup

1. Input the sample agreement draft text and the proposed sentence. Compare whether the phrase "has completed agreement signing" in the proposed sentence matches any signing status stated in the draft text. The observable result: when the draft states no signing status, the proposed sentence is unsupported.
2. Input the three required fields collected by the form input node in the sample. Compare whether the submitted values reach the following user selection node. The observable result: when the later node can read the cooperation period, commission rate, and sample shipment form number, the output handoff holds.
3. Input the two branch conditions of the user selection node in the sample. Compare whether the corresponding "yes" branch executes after the user makes a choice. The observable result: after branch connections are verified one by one, the execution path matches the choice. Empty-result handoff can be checked on paper with an explicit input of `[]` against the downstream design, without claiming that a fictional rule retrieval necessarily returns `[]`.
