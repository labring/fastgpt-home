# Creator commission settlement: workflow routing for product questions

## What the documents look like

Creator commission settlement and deduction sits after a sale closes. The objects being reconciled are valid promotion orders, refund deduction details, settlement statements and invoices. Commission setting records, order after-sales data, finance systems and creator contracts form the main material sources, and updates move on a weekly or monthly rhythm. Product information and selection question answering has to organize these materials into content that can be questioned and handed over, while workflow routing collects information at key nodes and passes results to later steps.

When the Form Input node triggers, the conversation enters an interaction state, records the workflow state, and after the user fills required information and submits, the node passes that information to later nodes. When the User Selection node triggers, it likewise enters an interaction state, and when the user makes a choice the node evaluates the choice and executes the corresponding "yes" branch. Both nodes are user interaction nodes, can be added repeatedly, and trigger execution. Routing for product information and selection question answering has to make clear which fields the form collects, which branches the user selection decides, and which later node receives the collected values.

## Constraints at the workflow routing step

Commission settlement material involves alignment across three layers: subject, period and field. A contradiction exists only when the same field carries mutually exclusive values within the same period; an unstated item, or evidence covering only a related stage, counts as unsupported or pending verification. Signing, reaching cooperation and contract effectiveness are three distinct facts, and a quotation validity period does not indicate a supply period. Interaction nodes wait for user submission or selection, record state and hide the dialog box; the nodes themselves do not complete order writes, document backfill or external state synchronization, which require a separate business interface or a later process.

A retrieval relevance score does not carry permission or entity isolation. Libraries built on different vector models cannot be associated together; identifiers should be checked first and non-matching items excluded, without running cross-model retrieval to compare missed recalls. An empty-result handoff can use an explicit paper input to check downstream design. Optional paths listed in a document's overall flow diagram do not mean every request executes all of them; image retrieval requires a corresponding image input and model capability, and reranking requires a model and must be enabled according to settings.

## Configuration and implementation checks

Hypothetical exercise sample: the source material reads, "Party A and Party B signed the Creator Promotion Cooperation Contract on March 1, 2025, agreeing that March special-session commission is settled by valid orders; Party B's March settlement statement lists refund deduction details, and refunded order commission has been deducted from the payable amount; the signature page of this contract bears both parties' seals, and no effectiveness-condition clause is present." The proposed judgment sentence is, "This contract has taken effect, and the March refund deduction has completed financial posting." This sample is used to check field passing and branch judgment in routing, and does not indicate that any real business action has occurred.

| Configuration item | Setting or check item for this page | Relation to the sample |
| --- | --- | --- |
| Form Input node | Collects required information such as subject, period and field name, passing it to later nodes after submission | Collects contract subject and settlement period |
| User Selection node | Executes the corresponding "yes" branch after the user makes a choice | Decides whether refund deduction details enter the reconciliation branch |
| Interaction state check | Enters an interaction state on trigger and records the workflow state | Remains in interaction while awaiting submission or selection |
| Output handoff check | Passes collected information explicitly to later retrieval, judgment or interface nodes | Passes form values to the statement reconciliation branch |
| External action division | Order writes, document backfill and external state synchronization attach to a separate business interface or later process | Financial posting is not completed by the interaction node |
| Retrieval scope check | Checks identifiers and excludes items not matching across vector models, recording the actual observation | Contract and statement must sit in the same associable scope |

## Three common errors

1. Treating form submission as business authorization. In the sample the form collected contract subject and period; submission only completes information passing and does not constitute signing confirmation, effectiveness confirmation or payment authorization. When checking, input the sample source text and the proposed judgment sentence, compare whether "has taken effect" and "has completed posting" have corresponding evidence, and keep both pending verification when the effectiveness condition and posting record are absent.

2. Treating the user selection "yes" branch as automatic execution. The User Selection node evaluates the choice and executes the corresponding branch, and branch connections must be verified one by one. In the sample the refund deduction details enter the reconciliation branch, and the branch itself does not write to the finance system. When checking, compare whether a branch output and a downstream interface node exist; if no interface is attached, record it as pending implementation.

3. Treating a relevance score as permission or entity filtering. Similar results returned by retrieval do not exclude unrelated subjects or unauthorized records. In the sample, if the contract and statement come from libraries on different vector models, they cannot be associated together. When checking, verify identifiers first, exclude non-matching items, and record the actual observation without inferring missed recalls or redundant results.

## How to verify the setup

- Verification one: input the sample source text and the proposed judgment sentence "This contract has taken effect, and the March refund deduction has completed financial posting." Compare whether the source text states an effectiveness condition and whether a financial posting record exists. The source text has only signature-page seals, no effectiveness-condition clause and no posting voucher, so the expected result is that "has taken effect" is unsupported and "has completed posting" is unsupported, both remaining pending verification.

- Verification two: input the refund deduction details from the sample and the "yes" branch configuration of the User Selection node. Compare whether the branch output connects to a later interface node and whether that interface node declares a write to the finance system. The expected result is that the branch connection exists and the downstream write is not declared, recorded as pending implementation, without judging that posting is complete.

- Verification three: input the library identifiers of the sample contract and statement. Compare whether both use the same vector model, exclude non-matching items, and record the actual observation. The expected result is that matching identifiers allow entry into joint association checking, while non-matching identifiers are excluded and the gap recorded, without running cross-model retrieval to compare missed recalls.
