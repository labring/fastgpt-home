# Import and export permits: workflow routing for product questions

## What the documents look like

Permit handling happens before declaration and determines whether goods can be imported or exported lawfully. The materials come from commerce authority systems, customs commodity codes, supplier documents, and customer end-use statements. This page concerns automatic import licences, dual-use item licences, contracts, and product descriptions. Each shipment requires a fresh judgment about the regulatory certificate, preparation of the end-use statement, and follow-up on approval status. Updates are irregular and occur per shipment. Product data and selection questions therefore cannot rely on a one-time knowledge base. Collection of materials, branch decisions, and status follow-up need to be arranged as a workflow that can be checked item by item.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, the dialogue box is hidden, and execution continues after the user completes the interaction. The node collects required information the user fills in and, after submission, passes that information to later nodes. The user selection node also records workflow state and hides the dialogue box while waiting. When the user makes a selection, the node evaluates that selection and executes the "yes" branch. Both nodes are repeatable and trigger execution.

Retrieval and form collection supply input values only. They do not constitute authorization. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Libraries built on different vector models cannot be associated together; the model identifier must be checked and non-matching libraries excluded first. Empty-result handling can be checked against downstream design using an explicit paper input of an empty list. Retrieval does not guarantee a first-position hit or full recall.

Hypothetical drill sample: an enterprise submits materials for an automatic import licence application. The product description states "this equipment is used for general industrial inspection." The contract states "the seller delivers in March 2025." The end-use statement does not mention the final user. A drafted sentence reads "this goods item does not require a dual-use item licence." In review, the end-use description in the product description is compared with the fields needed for a dual-use determination. The end-use statement lacks final-user information. The drafted sentence is not supported and is recorded as pending verification.

## Configuration and implementation checks

| Configuration item | Type | Description |
| --- | --- | --- |
| Form input node | Documented | Triggers the interaction state, collects required information, and passes it to later nodes |
| User selection node | Documented | Executes the "yes" branch after the user makes a selection |
| Interaction state check | Implementation check | Check whether the node enters the interaction state and records state after triggering |
| Output handoff check | Implementation check | Compare collected information item by item with the inputs of later retrieval or judgment nodes |
| External action division | Implementation check | Order writes, document backfill, and external synchronization connect to a separate business interface |
| Retrieval library identifier check | Implementation check | Check the vector model identifier and exclude libraries from different models from being associated |

Hypothetical trial starting point: set the required fields of the form input node to product description, contract, and end-use statement. These three are chosen because they correspond to the materials needed for the judgment in this page's primary task. Compare with a configuration that collects only the product name, and observe whether later nodes receive complete input.

## Three common errors

1. Treating form submission as completed authorization. The input is the form value the user filled in. The comparison object is the approval status field. The observable result is that the approval status remains pending review. A licence cannot be treated as granted on this basis.

2. Treating a retrieval hit as a permission filter. The input is a similarity ranking result. The comparison object is the business ownership of the record. The observable result is that a high ranking does not mean the record belongs to the current entity. Unrelated records cannot be excluded on this basis.

3. Treating the user's selected branch as automatic execution. The input is the user selection value. The comparison object is the downstream node connection. The observable result is that the node the branch points to requires separate configuration. Later operations cannot be treated as already executed.

## How to verify the setup

1. Using the hypothetical sample above, input the three form values: product description, contract, and end-use statement. Compare the drafted sentence "this goods item does not require a dual-use item licence" with the final-user field in the end-use statement. The observable result is that the field is missing and the drafted sentence is not supported.

2. Using the same hypothetical sample, input the user selection value. Compare that selection with the connection to the "yes" branch. The observable result is that the branch node executes according to configuration, while unconnected operations remain unexecuted.

3. Using a paper input of an empty list, check empty-result handling. Compare the downstream node's design for handling empty input. The observable result is that the downstream node accepts the empty value according to configuration. Retrieval does not guarantee returning an empty result, and the actual observation must be recorded.
