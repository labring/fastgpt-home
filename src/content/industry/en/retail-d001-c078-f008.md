# Chain-store site selection: workflow routing for product questions

## What the documents look like

Site selection and store opening happen before a store begins trading. The work centres on leasing and engineering delivery rather than on supervising an operating store. The documents come from trade-area footfall studies, map POI data, POS records of historical store formats, and landlord materials. The recurring working documents are the site evaluation form, the lease letter of intent, the renovation budget, and the opening schedule. These materials are updated at irregular intervals, once per store.

The document forms differ substantially. A site evaluation form carries footfall estimates and a store-format matching conclusion. A lease letter of intent carries the lessor, the lessee, the subject premises, the lease term, the deposit, and the status of the terms. A renovation budget carries itemised amounts and a quotation validity period. An opening schedule carries milestones and responsible parties. Product data and selection questions require extracting selectable grounds from these documents and arranging the points where a person confirms them. A field the document does not state remains unknown and cannot be supplied from another document.

## Constraints at the workflow routing step

The form input node triggers user interaction. When it fires, the conversation enters an interaction state, the workflow state is recorded, and the conversation continues after the user completes the interaction. The node collects the required information the user submits and passes it to later nodes. The user selection node also triggers user interaction and records the workflow state. When the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch.

Several boundaries follow from this. The interaction state record is behaviour of these interaction nodes; there is no separate global state-recording switch. A retrieval library and a vector model identifier must match before they can be associated together; libraries on different models cannot be associated together, and the correct step is to check the identifiers and exclude those that do not match. Retrieval does not perform authorization judgement, and a similarity setting does not exclude unrelated business records or unauthorized records. Order writes, document backfill, and external status synchronisation require a separate business interface or a later process. This page does not construct such functions.

Hypothetical drill sample. A chain headquarters expansion staff member submits an excerpt from a site evaluation form. The source text reads: "Subject premises: ground-floor shop, No. 12 Yi Road, City A; lessor: Bing Real Estate; lessee: Ding Chain Headquarters; status: letter of intent awaiting lessor signature; deposit: two months' rent; lease term: five years; footfall estimate: approximately eight thousand visits on a working day." The same batch includes an excerpt from a renovation budget: "Quotation valid until 30 September of the current year." The proposed selection question to be submitted reads: "Please confirm that the lease for this site has taken effect, and on that basis generate the opening schedule and the renovation payment milestones."

## Configuration and implementation checks

| Configuration item | Value or checking method on this page | Basis and boundary |
| --- | --- | --- |
| Form input node | Collects subject premises, lessor, lessee, status, deposit, lease term, footfall estimate | Official description: triggers the interaction state, passes submitted information to later nodes |
| User selection node | Used for the "proceed to selection calculation" branch; verify the "yes" branch connection item by item | Official description: executes the corresponding "yes" branch after the user chooses |
| Interaction state check | Check that the conversation enters the interaction state and that the state is recorded | Official description: recording state is behaviour of this node |
| Output handover check | Compare each form output against the input of the downstream retrieval and judgement nodes | Official description: information is passed to later nodes |
| Retrieval library identifier check | Check whether the libraries taking part in retrieval and the vector model identifiers match | Official description: association together requires the same model |
| External action division | Order writes, document backfill, and external synchronisation connect to a separate business interface | Official description: such actions require a separate implementation |

Hypothetical trial starting point: treat "deposit: two months' rent" as the starting point for checking a required form field, because the sample source text gives this field an explicit value. The comparison method is a character-by-character comparison of the form output against the source text. This value is not described as an official default.

## Three common errors

1. Treating "letter of intent awaiting lessor signature" as an effective lease. The input is the status field in the sample source text, the comparison object is wording of the "signed and effective" kind, and the observable result is that the status field and the proposed sentence do not agree. The lease taking effect remains an evidence gap.
2. Treating the quotation validity period as a supply or renovation deadline. The input is "quotation valid until 30 September of the current year", the comparison object is the renovation payment milestone, and the observable result is that the two differ in field name and in meaning.
3. Using a similarity setting to exclude unauthorized records. The input is the retrieval return, the comparison object is the basis for an authorization judgement, and the observable result is that the retrieval results carry no authorization status.

## How to verify the setup

1. Enter the sample source text and the proposed sentence "please confirm that the lease for this site has taken effect" into the checking process together. Compare the status field "awaiting lessor signature" with "effective". If the two do not agree, the proposed sentence is not supported and the fact of the lease taking effect remains an evidence gap.
2. Place the renovation budget source text "quotation valid until 30 September of the current year" alongside the renovation payment milestone to be generated. Compare the field name and the validity scope. If they do not point to the same matter, no payment milestone may be generated on that basis.
3. Check the empty-result handover design with the paper input []. Observe whether the downstream node follows the empty-result branch. Do not assert that this input necessarily returns []; record only the output and the failure branch actually observed.
