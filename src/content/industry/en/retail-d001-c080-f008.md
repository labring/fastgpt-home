# Store price and display checks: workflow routing for product questions

## What the documents look like

Price and display auditing for chain stores happens during everyday operations. The focus is sustained execution of standards, which sets it apart from franchise training or opening support work. The main data sources are the supervision system, POS price lists, store cameras and the head office promotion calendar. The documents handled day to day are store visit photos, price tag lists, display standards and rectification notices. The typical roles are the chain operations department, regional supervisors and store managers. The supplied material gives weekly and monthly update frequencies. This page does not derive batch synchronization, full synchronization or real-time mechanisms from those frequencies.

For the product information and selection question task, workflow routing has to connect the fields in those documents with human confirmation actions. Store visit photos and price tag lists support price consistency comparison. Display standards support judging whether a shelf arrangement meets requirements. Rectification notices support tracking closure. These materials differ in authorization state: store visit photos are on-site evidence records, price tag lists are store execution records, and rectification notices are pending items. Information collected by the form input node must be passed explicitly to later retrieval, judgment or interface nodes. Retrieval and forms are not authorization execution.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The user selection node is also a user interaction node. After the user makes a choice, the corresponding "yes" branch runs. Interaction state checking belongs to the behavior of interaction nodes. No global state recording switch is set or claimed here. Output handover checking requires that collected information be passed explicitly to later retrieval, judgment or interface nodes, with output and input compared item by item. Order writing, document backfill and external state synchronization require a separate business interface or a later process.

The same vector model requirement for retrieval libraries is limited to vector retrieval association. It does not extend to business registration sites or other external systems needing the same model. Semantic recall and relevance scores do not carry permission or entity isolation. RRF is a hybrid result fusion process and is not written as an enable switch. Thinking budget is a reasoning budget and cannot be moved into a citation token limit. Image retrieval requires a corresponding image input and model capability. Reranking requires a model and is enabled according to settings.

## Configuration and implementation checks

Hypothetical drill sample: a chain brand operations department receives a store visit record. The source text reads: "On 12 March 2025, the price tag at Store A showed a certain product at 19.9 yuan, the POS price list recorded the same product at 19.9 yuan on the same day, and the store manager confirmed the price tag matched the system." A draft sentence awaiting judgment reads: "This store's price execution meets the standard and no rectification is needed." In this sample the subject is Store A, the object is a certain product, the date is 12 March 2025, the state is that the price tag and POS agree, and the authorization boundary is internal operations department checking, with no external publication or supplier notification.

| Configuration item | Relevant setting or check on this page | Relation to the sample |
| --- | --- | --- |
| Form input node | Enters interaction state on trigger, collects required information | Collects visit date, store, product and price fields |
| User selection node | Runs the "yes" branch after the user makes a choice | Confirms whether to enter the rectification process |
| Output handover | Passes collected information to later retrieval or judgment nodes | Passes the price tag and POS comparison result to the judgment node |
| Retrieval association | Only the same vector model can be associated together | Checks whether the price tag list and display standard share a library |
| External operation split | Order writing and document backfill need a separate interface | Rectification notice backfill needs a separate business interface |
| Interaction state | Recording state is behavior of interaction nodes | No separate global state recording switch is set |

This page provides no official default values. The items in the table are the starting points of this hypothetical trial. The reason for choosing them is that they map directly to the sample fields. The comparison method is checking item by item whether input and output agree.

## Three common errors

1. Treating retrieval or a form as authorization execution. The error appears when the form input node collects store confirmation and the rectification is then treated as complete. The input is the store manager confirmation sentence in the sample, the comparison object is the authorization boundary, and the observable result is that without a business interface the rectification state should not change.

2. Treating a relevance score as a permission or entity filter. The error appears when a similarity setting is assumed to exclude unrelated stores. The input is the Store A record in the sample, the comparison object is the retrieval scope, and the observable result is that relevance does not carry permission isolation and the store identifier must be checked separately.

3. Treating an unstated field as confirmed. The error appears when the draft sentence says "no rectification is needed" while the source text does not state the rectification status. The input is the sample source text, the comparison object is the rectification field, and the observable result is that an unstated field remains pending verification and cannot be judged as a denial or a conflict.

## How to verify the setup

- Check one: input the sample source text and the draft sentence, and compare whether "meets the standard" in the draft and "the price tag and POS agree" in the source share the same subject, the same period and the same field. The condition is met when the draft only restates content already stated in the source and adds no authorization or effective clause.

- Check two: input the Store A record in the sample and compare the vector model identifiers of the retrieval libraries. The condition is met when the price tag list and the display standard belong to the same vector model and can be associated together. If the identifiers differ, exclude the non-matching one and record the actual observation. Do not run cross-model retrieval to compare missed recall.

- Check three: input an explicit paper empty result `[]` and compare the design of the downstream judgment node. The condition is met when the downstream can accept an empty result and record the gap, without claiming that a fabricated rule retrieval necessarily returns `[]`. If the downstream has no defined empty-result branch, record it as pending addition.
