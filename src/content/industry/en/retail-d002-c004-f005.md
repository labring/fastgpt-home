# Temu semi-managed sellers: multi-turn prompts for after-sales questions

## What the documents look like

A Temu semi-managed seller maintains overseas inventory and arranges shipment directly, so order fulfilment depends on the platform fulfilment order, the overseas warehouse inventory sheet, and the logistics track together. Product declaration forms and price declarations record product attributes and declared prices. After-sales answers about fulfilment progress and return or exchange questions have to be grounded in these materials.

These materials update daily or per order. Inventory quantities and fulfilment status referenced in an answer change as the underlying documents change, so an answer must sit on a specific document and a specific date. A retrieval similarity score reflects textual closeness only. It does not distinguish store, order ownership, or permission scope, and it cannot be used to decide that a particular fulfilment order belongs to the current requester.

## Constraints at the multi-turn prompts step

Multi-turn dialogue sends history turns, knowledge-base retrieval results, and the new user question to the model together. History turns are bounded by the memory round setting; retrieval results are produced by the knowledge-base search node. Neither constitutes authorization to operate on an order or on inventory.

Hypothetical drill sample: the source text to be checked reads, "Platform fulfilment order PO-2025-0417-01, product declaration form number SP-0417-A, declared quantity 120 units, overseas warehouse inventory sheet shows 80 units available for this SKU, fulfilment order status pending shipment, date range 17 April 2025." The draft sentence to be judged reads, "This fulfilment order has been fully shipped, inventory is sufficient, reply to the buyer immediately that it has been dispatched." This sentence conflicts with the pending-shipment status and the 80 available units in the source text, and the source text records neither a shipment completion time nor a logistics tracking number, so the sentence is unsupported.

The prompt needs to state that the material scope is limited to the supplied declaration form, inventory sheet, price declaration, and fulfilment order, that the answer task is to describe fulfilment and after-sales status, and that when evidence is missing the answer should mark the item as pending verification and name the gap. Question optimization is used for reference resolution and question expansion, and is checked only when there is a knowledge-base continuous-dialogue need. Reply format is chosen according to downstream handling; when json_schema is selected, the corresponding format requirement is filled in and the returned structure is checked.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this trial | Reason and comparison method |
| --- | --- | --- |
| Memory rounds | Keep a small number of history turns | Reference value for customer-service and knowledge-base Q&A; compare with no history to see whether references resolve |
| Temperature | Lower | Fulfilment and after-sales are rule-bound scenarios; compare with a higher setting for answer stability |
| Reply cap | Limit length as needed | After-sales explanations need to be complete; compare with truncation to see whether status fields are dropped |
| Reply format | Default | No downstream need to read a fixed structure; compare with json_schema return structure |
| Multimodal recognition | Enable image recognition according to model capability | Screenshot-type evidence requires model support; compare with the disabled state to see whether images are read |
| Thinking configuration | Default | Complexity requirement is undetermined; compare with a higher thinking strength for answer completeness |

These values are hypothetical starting points for this trial, not official defaults. Knowledge bases across different vector models cannot be associated together; identifiers must be checked first and non-matching items excluded.

## Three common errors

1. Treating a relevance score as a permission filter. Input is a score and a fulfilment order record returned by one retrieval; compare the score level with the order ownership field, and observe whether a record with a high score but a non-matching ownership field is taken as an answerable basis.
2. Treating a form returned by an interactive node as already submitted. Input is the inputForm field returned by interactive; compare whether the form is submitted by a further conversation request, and observe whether an unsubmitted form is handled as filled in.
3. Writing a pending-shipment status as shipped. Input is the fulfilment order status field in the hypothetical sample; compare the draft sentence with the source status value, and observe whether a completion time or logistics tracking number not recorded in the source text is supplied.

## How to verify the setup

1. Input the hypothetical sample source text and the draft sentence; compare the shipment status and inventory quantity in the draft sentence with the values in the source text. If a clear inconsistency appears, or a field not recorded in the source text is supplied, the draft sentence is judged unsupported.
2. Input the quoteList and score returned by one retrieval; compare the datasetId in each record with the target scope identifier. If a record with a non-matching identifier enters the answer basis, the identifiers must be checked first and the record excluded.
3. Input the paper input [] for empty-result handling; compare whether the downstream node design produces a pending-verification output for an empty reference. If an unsupported business conclusion appears, the downstream handling needs correction.
