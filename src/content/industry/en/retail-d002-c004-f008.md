# Temu semi-managed sellers: workflow routing for after-sales questions

## What the documents look like

Temu semi-managed seller operations differ from fully managed supply in one decisive way: the seller maintains overseas inventory and arranges shipment rather than only supplying goods to the platform. Daily document work therefore centers on the product declaration form, the overseas inventory sheet, the price declaration, and the platform fulfillment order. In the order fulfillment and after-sales question task, the fulfillment order's order status, the inventory sheet's stock occupancy, and the buyer's after-sales request must be read against one another. A field mismatch between these materials can lead to a shipment timeout or a platform penalty. The materials update daily and per order, but workflow routing does not trigger itself from that update frequency; node behavior follows the interaction and branch design.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues downward after the user completes the required information and submits it. The collected form values then pass to subsequent nodes. The User Selection node is also a user interaction node: it enters the interaction state, records the workflow state, and after the user makes a choice it evaluates that choice and executes the corresponding "yes" branch. Both nodes can be added repeatedly and trigger execution. The documented purpose of the form node is to collect precisely the needed user information and then act on it; the documented purpose of the selection node is to pose a decision question and route the workflow according to the user's feedback.

The constraint is that these two nodes collect values and branch. Order writes, document backfill, and external status synchronization require a separate business interface or a downstream flow. A retrieval result or a submitted form is not authorization to execute. Semantic recall and relevance do not carry permission or entity isolation duties.

Hypothetical paper exercise sample: an operator handling after-sales questions receives a pending request. The source material reads: "Platform fulfillment order PO-2025-0417 status is awaiting shipment; overseas inventory sheet SKU-A available quantity 12; buyer after-sales request: change address." The draft sentence under review reads: "This order has entered the shipping process, and the address change request must be routed to manual review." This sample exists only for paper comparison. It does not represent a real record or an executed action.

## Configuration and implementation checks

| Configuration item | Setting or check on this page | Relation to the sample |
| --- | --- | --- |
| Form Input node | On trigger, enters the interaction state, collects required information, passes it downstream after submission | Collects supplementary fields for the address change request |
| User Selection node | After the user chooses, executes the corresponding "yes" branch; verify branch connections one by one | Separates the "route to manual" path from the "automatic reply" path |
| Interaction state check | Recording state is behavior of the interaction node; no separate global state-recording switch is documented | Checks whether the PO-2025-0417 interaction completed |
| Output handoff check | Pass collected information explicitly to later retrieval, judgment, or interface nodes; compare output against input item by item | Checks whether the address change field reached downstream |
| External action split | Order writes, document backfill, and external status synchronization require a separate business interface or downstream flow | Address change execution is not completed inside this workflow |
| Retrieval scope check | Verify identifiers and exclude non-matching ones; do not run cross-model retrieval to compare missed recalls | Checks whether the SKU-A inventory record is inside the accessible scope |

## Three common errors

1. Treating retrieval or form submission as authorized execution. Input: the draft sentence "This order has entered the shipping process." Comparison: the source material states only "status is awaiting shipment." Observation: awaiting shipment is not the same as shipped, so the draft sentence is unsupported.

2. Extending the interaction state record into a global state switch. Input: the Form Input node description. Comparison: the document states only that the workflow state is recorded. Observation: no global state-recording switch or snapshot guarantee may be asserted.

3. Jointly associating libraries on different vector models and then inventing a run result. Input: two library identifiers on different vector models. Comparison: the document does not describe joint association behavior. Observation: verify identifiers, exclude non-matching ones, and record what is actually observed; do not infer missed recalls or redundancy.

## How to verify the setup

- Check one: input the hypothetical sample text "Platform fulfillment order PO-2025-0417 status is awaiting shipment." Compare the draft sentence "This order has entered the shipping process." If the material does not state that the shipping action was completed, the draft sentence is unsupported and the evidence gap must be recorded.

- Check two: input the User Selection node configuration and compare the "yes" branch connection. If selecting the address change executes the "route to manual" branch and each branch connection passes verification, the condition is met. If the branch is unconnected or points to the automatic reply, the condition is not met.

- Check three: input an explicit paper empty result [] and check whether the downstream design accepts an empty result. If a downstream node has a defined handling path for [], the condition is met. If the downstream design assumes a return is always present, record the gap. Accepting an empty result does not mean that a fictional rule retrieval necessarily returns [].

This page addresses only Temu semi-managed seller operations, order fulfillment and after-sales questions, and workflow routing. At operator handover, which materials, actions, and requests sit at which authorization state must be kept distinct; retrieval and forms cannot be treated as authorized execution.
