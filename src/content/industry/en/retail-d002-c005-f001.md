# TikTok Shop US operations: HTTP integrations for after-sales questions

## What the documents look like

US TikTok Shop order fulfilment and after-sales answering is shaped by local return windows, return grading and overseas logistics constraints, which differ from shelf operations on Douyin Shop. The working materials centre on product listings, return and refund records, return grading evidence and settlement bills, updated daily and per order. Handling automatic returns, uploading photo evidence and reconciling settlement deductions consume the most time, and mistakes can lead to platform-initiated refunds, higher return fees or failed appeals. When these materials pass through an HTTP integration, the interface only transports and parses values. It does not replace the business judgement about what a record actually states.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a given address. Params, Body and Headers can each reference variables through `{{}}`, and the URL can reference variables as well. Variables come from global variables, system variables and upstream node outputs. The documented system variables include appId, chatId, responseChatItemId, variables, cTime and histories, where histories takes at most 10 entries by default and that length cannot be changed. Return values are extracted with JSON path syntax, and output formatting can convert the value at a chosen key into a JSON string. The chat interface authenticates with an API key; when calling `chat/completions` the recommended approach is to pass `body.appId` in the request body, and `Authorization: Bearer <apiKey>-<appId>` is also supported. Fields such as `model` and `temperature` have no effect because the orchestration decides them, and the actual consumed token value is not returned. An empty chatId means no context is used, while a non-empty chatId takes the last element of messages as the user question. The responseChatItemId must be unique within the current chatId. The interactive payload returned for an interaction node contains only type and params; internal runtime fields are not returned. A retrieval score is not a permission or entity filter, and retrieval does not grant authorization.

Hypothetical walkthrough sample: a US store after-sales specialist intends to hand a return ticket to an external system for registration. The material text reads: "Order US-0001; the buyer submitted a return request on 10 March 2025; the platform status shows Return received; the return grading evidence is three photos of the item's appearance; no refund amount has been generated." The handover request to be judged reads: "This order's return is complete; please register it in the external system as refunded." This request conflates the platform status with the fact of a refund and lacks any refund record to support it.

Hypothetical trial starting point for this page: use histories at the documented maximum of 10 entries, because the document states that length cannot be changed, and compare against the number of history entries actually passed. This is a hypothetical starting point, not a statement of an official default value.

## Three common errors

1. Writing the platform status Return received directly as a completed refund. The input is the material text together with the drafted sentence; the comparison is whether a refund amount and a refund record exist; the observable result is that the drafted sentence contains "complete" and "refunded" while the material states no refund amount.
2. Treating a similarity score as a permission or entity filter. The input is the score field returned by retrieval; the comparison is whether the interface performs an authorization check; the observable result is a record being released or blocked on the strength of the score alone.
3. Treating an empty chatId or responseChatItemId in test mode as a business fault. The input is a request made in test mode; the comparison is the documented statement that these do not exist in test mode; the observable result is an interface failure being declared on that basis.

## How to verify the setup

1. Against the sample material text and the drafted sentence, input the material text, the drafted sentence and the refund fields, then compare whether "Return received" and "refunded" are mutually exclusive values of the same field. If the material states no refund amount, judge the sentence unsupported and keep the evidence gap open.
2. Against a retrieval result, input a set of returned items and their scores, then compare whether the interface performs a separate authorization check. If release is decided by score alone, judge that the score has been treated as permission and record the actual observation.
3. Against empty-result handling, input an explicit paper empty array `[]`, then compare how the downstream design handles an empty value and observe whether the empty-result branch runs. Do not claim that a fictional rule retrieval must return empty.

This page addresses only TikTok Shop US operations, order fulfilment and after-sales answering, and HTTP integrations with external systems. At the point of operational handover, the authorization status of which materials, operations and requests are in play must be kept clear; retrieval and forms are not authorization to execute.
