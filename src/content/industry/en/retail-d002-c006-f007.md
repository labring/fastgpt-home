# General export declarations: conversation logs for after-sales questions

## What the documents look like

General trade export declaration work generates a declaration form, a commercial invoice, a packing list and a contract for every shipment. The working data comes from China International Trade Single Window, the customs code library, freight forwarder bills of lading and the company ERP. Compared with general trade import declaration, export declaration also affects the matching of export tax rebate vouchers. When a conversation log touches document fields, it therefore has to point back to a specific document and a specific session. The three most time-consuming steps are classifying commodity codes, filling in the declaration form, and checking freight and insurance. These same three topics recur in after-sales questions, so a log needs to keep the question, the answer and the cited source together to support later reconciliation.

The conversation interface identifies a session by chatId and a single exchange inside that session by dataId. When a non-empty chatId is passed, the system reads the session from the database and uses the last element of the messages array as the user question, ignoring the remaining messages. When chatId is not passed, the context is built entirely from messages. A responseChatItemId, when passed, is stored as the ID of the response message for that exchange and has to be unique under the current chatId. Running details are requested through detail according to the official contract: non-streaming results sit in responseData, and streaming responses are distinguished by event. The presence of a log does not by itself complete a compliance audit; reconciliation, retention and compliance requirements are handled by the wider business solution.

Hypothetical paper exercise sample: a documentation clerk at an export company submits a question in the session with chatId "exp-chat-0007". The source material reads: "Export declaration number EXP-2024-0001, commercial invoice amount USD 12,000, packing list quantity 80 pieces, contract signing date 12 March 2024." A proposed sentence reads: "This shipment has passed export tax rebate voucher matching." The request to be judged reads: "Please confirm that this shipment's declaration form has been released." The source material contains the subject, the object and a date scope. It does not contain a release status or a rebate matching result.

## Constraints at the conversation logs step

The chatId is the anchor for audit. Two exchanges with different chatIds have different context and history, so the identifier has to be checked before any comparison. The dataId identifies one exchange under a session, and the responseChatItemId stored for a response has to be unique under its chatId. When detail is set, the non-streaming response keeps intermediate module results in responseData, and the streaming response separates them by event. Retrieval returns citations; it does not authorize a release, a rebate match or any other business action. A form collects values; business verification, approval, database writes and external synchronization each need their own downstream implementation. A pending request is not an approval, an offered option is not an execution, and an unsigned termination is not a completed termination.

Knowledge-reference limits use the documented unit for the configured field, and the same-model retrieval association, empty-reference output and context limits keep their documented conditions. A relevance score is not a category, entity or permission filter, and a similarity setting does not exclude unrelated businesses or unauthorized records. Retrieval is not authorization. Where a document field is not provided, the value is unknown.

## Three common errors

1. Treating retrieval or a form as authorized execution. Retrieval returns citations only and does not authorize a release or a rebate match. The check is to compare the proposed sentence against the source material text and record whether the stated status appears there.
2. Mixing sessions that carry different chatIds. Different chatIds mean different context and history. The check is to read the chatId on each record first, exclude records whose chatId does not match the target session, and compare only the remaining records.
3. Assuming that a field absent from the response was retained. Business data that does not appear in responseData cannot be treated as fully retained. The check is to list the fields actually returned for the exchange and record the missing fields as an evidence gap rather than filling them in.

## How to verify the setup

1. Input the hypothetical source material text and the proposed sentence "This shipment has passed export tax rebate voucher matching." Compare the proposed sentence against the source material. The source material does not state a rebate matching result, so the sentence is unsupported. The expected observation is a recorded gap, not a finding of contradiction.
2. Input the request "Please confirm that this shipment's declaration form has been released." Compare the request against the source material for a release status. The source material does not state a release status, so the request remains to be verified. The expected observation is a pending-verification record with the missing field named.
3. Input two exchange records under the same chatId and compare their dataIds. If a duplicate appears, the responseChatItemId did not meet the uniqueness requirement under that chatId. Record the observed duplicate and do not infer a system error cause that the documentation does not state.
