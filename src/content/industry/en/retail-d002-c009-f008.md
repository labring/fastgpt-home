# Amazon FBM fulfillment: workflow routing for after-sales questions

## What the documents look like

Amazon FBM fulfillment means the seller handles delivery and sets the return address without relying on platform warehouse inspection. For order fulfillment and after-sales question handling, the main data sources named in the category brief are Amazon Seller Central, carrier systems, ERP orders and customer service email. The daily documents involved are order picking lists, shipment confirmation sheets, return address settings and logistics tracking sheets. Updates occur per order and per day. Within this page, workflow routing has to carry order information, logistics tracking and return address material at the same time, and the completeness and authorization status of each type of material can differ. The brief gives update frequency only at the per-order and per-day level; this page does not derive batch synchronization, full synchronization or real-time trigger mechanisms from that.

The official FastGPT v4.17.2 documents describe two interaction nodes. The form input node is a user interaction node: when it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The form input node collects required information the user fills in and passes it to later nodes. The user selection node is also a user interaction node with the same interaction-state behavior, and when the user makes a choice the node evaluates that choice and executes the corresponding "yes" branch. The interaction-state record is behavior of the interaction nodes; the documents do not describe a separate global state-recording switch. Information collected must be explicitly passed to later retrieval, judgment or interface nodes. Order writes, document backfill and external status synchronization require a separate business interface or a later process. Retrieval and forms do not by themselves constitute authorized execution.

## Constraints at the workflow routing step

A hypothetical paper exercise sample is used below. The material text supplied for checking is: "Picking list PO-2201, order number A-1007, item SKU-K3, quantity 2 pieces, shipping warehouse SZ-01, picking date 2025-03-11." "Shipment confirmation sheet SC-2201 corresponds to order number A-1007, carrier CN-08, tracking number TR-77812, shipment date 2025-03-12." "Return address setting RA-05 applies to store S-01, effective date 2025-03-01." The pending handoff request to be judged is: "Backfill this order's logistics tracking sheet status as delivered, and on that basis send the buyer a refund confirmation." This request involves external status synchronization and refund confirmation, which require a separate business interface or a later process; the form and retrieval do not constitute authorization.

The interaction nodes record workflow state and wait for user completion before continuing. The form input node collects required fields such as order number and tracking number and passes them downstream; it does not perform backfill. The user selection node executes the "yes" branch after the user makes a choice; it is used to confirm a return address or carrier branch, and each branch connection is verified item by item. Collected information must be explicitly handed to later retrieval, judgment or interface nodes. Comparing the picking list and the shipment confirmation sheet shows whether the order number values agree. The refund confirmation and status backfill in the pending request are not executed on this page. Retrieval is not authorization, and a relevance score does not act as a permission or entity filter.

## Three common errors

1. Treating a tracking number collected by the form input node as completed shipment confirmation. The input is tracking number TR-77812 from the material text; the comparison object is carrier CN-08 and shipment date 2025-03-12 on shipment confirmation sheet SC-2201; the observable result is whether the fields agree on the same subject, the same period and the same field. Where a field is not stated, or only related-stage evidence exists, the result is unsupported or pending verification.
2. Treating the "yes" branch result of the user selection node as refund authorization. The input is the refund confirmation in the pending request; the comparison object is whether the material text states refund authorization terms; the observable result is whether an authorization field exists for the same subject and the same period. Where it is missing, record the gap and do not invent an authorization or effective term.
3. Treating retrieval results as a basis for permission or entity isolation. The input is return address setting RA-05; the comparison object is effective date 2025-03-01 for store S-01; the observable result is whether the address falls within the valid range. Relevance does not carry permission or entity isolation, and retrieval does not constitute authorization.

## How to verify the setup

1. Input picking list PO-2201 and shipment confirmation sheet SC-2201 from the hypothetical text, compare order number A-1007, SKU-K3, quantity 2 pieces, carrier CN-08 and tracking number TR-77812, and observe whether the two materials agree on the order number field value. The expectation is agreement; no actual test is claimed.
2. Input the refund confirmation from the pending request, compare whether the material text states refund authorization, and observe that it is not stated. The expectation is unsupported or pending verification, with the evidence gap retained.
3. Input return address setting RA-05 and store S-01, compare effective date 2025-03-01 with order date 2025-03-11, and observe whether the address is within the valid range on the order date. The retrieval check records observations and failure branches; it does not guarantee a first hit or full recall.
