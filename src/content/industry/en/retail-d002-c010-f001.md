# JD POP seller operations: HTTP integrations for after-sales questions

## What the documents look like

JD POP third-party store operations centre on four recurring document types: the product information sheet, the shipping-time commitment, the dispute handling form, and the warranty-period service record. Compared with a Tmall flagship store, JD POP work commonly turns on open-platform dispute rules and warranty-period service documents. Failures in this area lead to an established transaction dispute, expanded after-sales liability, and platform penalty points. Source material comes from the JD merchant backend, the JD help centre, JD open-platform rules, and logistics tracking, with updates occurring daily and per order.

At the HTTP integration step, these documents determine which fields may be sent in a request and which must be checked by a person inside an authorization boundary. The HTTP module sends a request to a specified address. Params, Headers, Body, and the URL can each reference variables through `{{}}`. The Body is used mainly with POST and PUT requests, and its JSON structure and value types must be checked against the external contract. Responses are parsed by JSON path, and when the output type is set to string, the value at the corresponding key is converted to a JSON string. The variables available to the module come from global variables, system variables, and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories; chatId and responseChatItemId do not exist in test mode, and histories takes at most 10 entries by default and its length cannot be changed.

The chat completions API key and appId rules apply only to that API. They do not become mandatory fields for an external work-order interface. A retrieval result or a form value is not an authorization, and a pending review is not an approval.

## Constraints at the HTTP integrations step

The following hypothetical drill sample is the only evidence used on this page. It is clearly labelled as a paper exercise and does not describe any real customer, order, or system.

Material text supplied for checking, three sentences: "Order A-2024-0912, the buyer signed for receipt on 12 September. The shipping-time commitment states that an exchange may be applied for within 7 days of signing. The dispute handling form status is pending review, and no handling conclusion has been signed."

Draft sentence to be judged: "This order already satisfies the exchange conditions, please have the external system create the exchange work order directly."

In this sample the actor is a store after-sales supervisor, the object is order A-2024-0912, the status is pending review with no signed conclusion, and the effective scope is within 7 days of signing. The draft sentence treats the time-window condition "may apply for an exchange" as equivalent to "already satisfies the exchange conditions", and treats the pending-review status as an executable authorization. Both moves go beyond the supplied material. Whether a work order may be created depends on a creation permission and an applicable process that the material does not state, so that point remains unverified rather than denied.

The HTTP module can call external data sources and operate on databases. That capability describes what the module can reach, not what the store is authorized to do. A retrieval return or a form value does not supply a business approval.

## Three common errors

1. Treating pending-review material as authorization to create a work order. The supplied text states no creation permission and no applicable process, so whether the action may run stays unverified. The absence of a signed conclusion does not by itself show that creation is forbidden; the document status and the creation authorization must be checked separately.
2. Treating a time-window condition as a satisfied condition. The input is the signing date and the shipping-time commitment; the comparison is between the application window and the current date; the observable result is that the draft sentence reaches a conclusion without checking the signing date. The phrase "may apply for an exchange" does not supply any other exchange condition.
3. Treating retrieval or a form as authorized execution. The input is a retrieval return or a filled form value; the comparison is against the authorization boundary; the observable result is that the draft sentence substitutes retrieval or a form for an approval. The HTTP module can reach external data and databases, and that reach does not confer business authorization.

## How to verify the setup

1. Input the supplied material text together with the request to "create the exchange work order directly". Compare the material handling status, the creation permission, and the external contract. Only the pending-review status and the absence of a signed conclusion are given; the other two are missing, so the execution claim remains unverified.
2. Input the signing date and the 7-day application commitment, then compare against the actual application date or the drill check date. That date is not supplied, so the window match remains unverified. The phrase "may apply" cannot be extended into a conclusion that other exchange conditions are satisfied.
3. For the third item in the hypothetical sample, input a retrieval return or a form value, compare against the presence of an approval or authorization record, and observe that the material records no approval. This is recorded as an evidence gap to be filled, not as a denial or a conflict.

All three checks address the primary task on this page and use the hypothetical material and draft sentence already given, stating for each what is input, what is compared, and what would be observed. Items not stated, or supported only by a related stage, are recorded as unsupported or pending verification. The same-vector-model requirement for retrieval association applies only to knowledge-base retrieval association and does not extend to business-registration sites or other external systems. Empty-result handling can be checked with an explicit paper input of `[]` against the downstream design, without claiming that a fictional rule lookup returns `[]`.

A relevance score is not a category, entity, or permission filter, and retrieval is not authorization. Forms collect values; business verification, approval, database writes, and external synchronization require their stated downstream implementation.
