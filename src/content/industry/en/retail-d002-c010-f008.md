# JD POP seller operations: workflow routing for after-sales questions

## What the documents look like

JD POP third-party store operations for order fulfilment and after-sales answers draw on four recurring record types: the product information sheet, the delivery time agreement, the dispute handling form and the warranty-period service record. The public brief places this category around open-platform dispute rules and warranty service documents, which is a different emphasis from a Tmall flagship store. Workflow routing in this setting has to carry two lines at once: checking the agreed delivery time and assembling the evidence a dispute may require.

The fields that matter for routing are the ones the records actually contain. The product information sheet supplies the product identifier and the warranty position. The delivery time agreement supplies the agreed delivery time. The dispute handling form supplies the dispute status. The warranty-period service record supplies the service document status. A workflow can collect and pass these values forward. It does not decide authorization, and it does not confirm that a delivery happened or that a responsibility was accepted.

The brief gives the update frequency as daily and per order. That frequency is context for how often the records change. It does not establish a batch synchronization mechanism, a transaction trigger, or any automatic refresh inside the workflow.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The node collects the required form information the user submits and passes it to later nodes. The user selection node also enters the interaction state and records workflow state. When the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. The interaction state belongs to the interaction nodes; no separate global state-recording switch is documented.

Several limits follow. Order writes, document backfill and external status synchronization need a business interface or a later flow; they do not occur inside these nodes. Retrieval and relevance scores do not perform permission or entity isolation, so a similarity setting cannot be treated as a filter that excludes unrelated businesses or unauthorized records. Libraries built on different vector models cannot be associated together; the practical step is to check identifiers and exclude non-matching records, then record what was observed. An empty retrieval result can be used to check a downstream design with an explicit paper input. Optional paths shown in an overall flow diagram are not all executed on every request. Image retrieval needs an image input and a model with that capability. Reranking needs a model and must be enabled in settings. The thinking budget is a reasoning budget and is not a citation-token limit.

Hypothetical paper test case. The source records read: "The product information sheet states that product A has a warranty period of 12 months. The delivery time agreement states that order B has an agreed delivery time of 10 March 2025. The dispute handling form states that order B has a dispute status of awaiting evidence." The draft sentence to be judged is: "Order B was shipped at the agreed time, and warranty responsibility rests with the buyer." The subject and period match the records, but the records do not state a shipment proof field or a warranty-responsibility field. The draft is unsupported.

## Configuration and implementation checks

| Configuration item | Relevant setting or check on this page | Link to the sample |
| --- | --- | --- |
| Form input node | Enters the interaction state on trigger, collects required information, passes it to later nodes after submission | Collects the evidence fields for order B |
| User selection node | Executes the corresponding "yes" branch after the user chooses; verify each branch connection | Selects the dispute handling branch |
| Output hand-off check | Passes collected information explicitly to later retrieval, judgment or interface nodes; compare output against input item by item | Checks whether order B fields are complete |
| Interaction state check | State recording is interaction-node behavior; no separate global state switch is documented | Checks the interaction state record for order B |
| External action split | Order writes, document backfill and external status synchronization need a business interface or a later flow | Shipment write is not completed in this node |

The hypothetical starting point for this paper exercise sets the required fields for order B to product identifier, agreed delivery time and dispute status. The reason for choosing these three is that the sample source text states only these three. The comparison method is a field-by-field check against the source text.

## Three common errors

1. Treating a form input submission as proof that shipment occurred. In the sample, the dispute handling form states that order B is awaiting evidence. Submitting the form completes information collection only; it is not a shipment proof and does not assign responsibility.
2. Treating the user selection "yes" branch as an approval. In the sample, the user selects the dispute handling branch. Branch execution shows the direction of the flow; it does not show that the platform approved anything or that responsibility was determined.
3. Treating a retrieval relevance score as a permission or entity filter. In the sample, the retrieval result for order B is unrelated to the authorization scope, and relevance does not exclude unauthorized records.

## How to verify the setup

1. Input the three source fields and the draft sentence. Compare whether the draft contains a shipment proof field and a warranty-responsibility field. The observed result is that these fields are not stated, so the draft is unsupported. The condition is met when the draft does not write a definite conclusion.
2. Input the dispute status "awaiting evidence" for order B. Compare the output fields after the form input node submission. The observed result is that the output contains product identifier, agreed delivery time and dispute status. The condition is met when the output fields match the input and no authorization conclusion is added.
3. Input an explicit paper empty result. Compare whether the downstream node is designed to accept an empty result. The observed result is that the downstream node does not interpret the empty result as no dispute or no responsibility. The condition is met when missing evidence remains missing.
