# Warehouse picking and packing: multi-turn prompts for after-sales questions

## What the documents look like

Warehouse picking, checking, and packing handles outbound orders and does not handle supplier arrivals. The main data sources are the WMS, the order system, the electronic waybill platform, and weighing equipment. Daily documents include wave picking lists, checking records, waybills, and packaging material sheets. Multi-turn prompts therefore face outbound facts that advance order by order: whether a wave picking list has been checked, whether a parcel has been weighed, and whether a waybill has been generated are records that exist at separate stages and for separate objects. The consequences of wrong or missing shipments, damaged parcels, and after-sales compensation require answers to distinguish states such as scanned, checked, and handed over to the carrier. A record from an earlier stage cannot be treated as completion of a later stage.

Data updates per order and per hour, so one order can produce several status records within a short period. Each turn must make clear which document and which order it concerns. A conclusion reached in an earlier turn does not carry over to a new document automatically.

## Constraints at the multi-turn prompts step

The core task at this step is to answer order fulfillment and after-sales questions from wave picking lists, checking records, waybills, and packaging material sheets, and to keep evidence gaps open when the documents do not support a conclusion.

The range of history brought into a turn is controlled by the memory turns setting. A larger value makes it easier to reference earlier conversation, and it also brings in more content, which can increase consumption and affect response speed. Customer service and knowledge base question-answering applications usually keep a small number of history turns. In an outbound process that advances order by order, an earlier turn may concern a different picking list, and carrying its conclusion forward introduces unrelated facts.

Question optimization and reference resolution need to be checked when a knowledge base is used for continuous conversation. A short question does not automatically qualify. Reply format follows what downstream processing needs. When json_schema is selected, the corresponding format requirement must be filled in and the returned structure verified.

The following is a hypothetical drill sample used to explain the checking method.

Hypothetical drill sample: an excerpt from a warehouse checking record dated 10 March 2026 reads, "Order A1001, wave W-0310-07, picker has scanned 5 items, checker completed checking at 14:20, waybill not yet printed." A packaging material sheet for the same batch records, "A1001 used 1 medium carton." Draft sentence to be judged: "Order A1001 has completed packing and been handed over to the carrier, and can be dispatched today."

The draft sentence goes beyond the checking record. The record shows checking completed and the waybill not printed. It does not state that packing was completed, and it does not state handover to the carrier. A correct answer states that checking is complete, the waybill is not printed, and packing and handover status are unsupported.

## Three common errors

1. Treating "checking completed" in the checking record as "packing completed." The input is the hypothetical drill sample text above, and the comparison object is "has completed packing" in the draft sentence. The checking record does not state packing status, so the draft sentence goes beyond the evidence. Executable check: compare each status word in the draft sentence against the corresponding field present in the source text, and mark any status absent from the source as unsupported.

2. Treating a retrieval hit as authorization to act. The input is a checking record fragment returned by a knowledge base retrieval, and the comparison object is the business action "may be handed over to the carrier." Retrieval returns text content only and does not judge whether the order holds handover permission. Executable check: separate "what the record shows" from "what may be executed" in the answer, and note that the handover action requires a separate system implementation.

3. Carrying the order status discussed in the previous turn over to a new order. The input is the checking conclusion for order A1000 from an earlier turn, and the comparison object is order A1001 in the current question. The two subjects differ. Executable check: verify the order number and document number in each turn's question, and when the subject differs, obtain evidence again rather than reusing the earlier conclusion.

## How to verify the setup

1. Test with the hypothetical drill sample text and the draft sentence. The input is the checking record text and the draft sentence. Compare whether each status word in the draft sentence has a matching record with the same subject and the same field in the source text. "Packing completed" and "handed over to the carrier" do not appear in the source text. The expected answer keeps the gap open and states that the waybill is not printed.

2. Test downstream handling with an empty retrieval result. The input is a paper-constructed empty result `[]`, explicitly labeled as such. Compare the downstream node's output design when no quoted content is present. The expected output does not produce a specific order status conclusion and keeps the evidence gap open. This input is paper-constructed and does not represent actual retrieval behavior.

3. Check identifiers across knowledge bases with different vector models. The input is the vector model identifier of each of two bases. Compare whether the two identifiers match. When they do not match, exclude joint association and record the actual observation, without running a cross-model retrieval to compare recall results. The expected outcome is that only the identifier check is completed, and no inference is made about retrieval performance.
