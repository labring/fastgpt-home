# Omnichannel stock transfers: after-sales questions with HTTP integrations

## What the documents look like

For after-sales questions in Omnichannel stock transfers, this page examines FastGPT HTTP integrations. Location roles, the meaning of stock quantities and actual reception must remain distinct. The external response needs corresponding records before the service answer can establish a transfer’s execution stage. The examples are hypothetical.

## Constraints at the HTTP integrations step

A transfer-service inquiry can identify stages supported by demand, request, stock and transport material. Proposed input supplies a request and snapshot without receipt evidence. An application does not establish arrival. Inspect the actual external contract’s mapping of item and sending or receiving locations before method and conditions, without assuming synchronized ERP, WMS and channel records or combinable stock from matching item names.

## Configuration and implementation checks

| Service-reading check | Proposed material | Required evidence |
| --- | --- | --- |
| Role transfer | Location passages beside sent values | Request does not swap locations |
| Quantity meaning | Balance separate from movement record | Balance is not this event |
| Receipt stage | Transport present; store reception absent | Not rewritten as arrived |
| Source addition | Corresponding passage for this transfer | Retest cites actual added evidence |
| Business result | Separate creation, writing or reconciliation | Query is not channel synchronization |

### Documented conditions

| Documented item / implementation check | Condition |
| --- | --- |
| `Request address and method` | The request address and method follow the external contract. |
| `Params and Headers` | Inspect parameters, headers and authentication separately. |
| Body | Where a JSON body is used, validate its structure against the external contract. |
| `Variable references` | Variables can come from global, system or upstream outputs. |
| `Debug identity fields` | Test mode lacks chatId and responseChatItemId. |

## Three common errors

Location roles reversed in request: Transmitting the sending location as the receiving location requires comparison of the source role passage with the actual transmitted value. Snapshot balance mistaken for movement: A snapshot balance treated as this movement requires timing and corresponding event evidence. Logistics mistaken for store receipt: A logistics record described as store receipt needs this transfer’s reception source. These inspect location, quantity meaning and execution stage; a response does not establish missing business relationships.

## How to verify the setup

Retain item, location roles, source time, actual request and return. Repeat after corresponding material arrives and inspect what supports the answer. Check parameters, headers and any appropriate body under the real contract with private authentication. Transfer creation, stock writes, procurement changes or reconciliation require separate authority and receipts. Reading establishes neither movement, synchronization nor matched records and stock, and empty returns do not establish zero inventory.
