# Brand concession operations: HTTP integrations for after-sales questions

## What the documents look like

A brand concession counter inside a shopping mall differs from a brand-operated street store in one structural way: the mall collects payment centrally and settles with the brand under a concession deduction arrangement. The brand therefore receives sales data from the mall POS, while the brand ERP and the finance system each hold their own record. The daily and monthly documents in this setting are the concession deduction contract, mall activity letters, sales receipts, and the monthly reconciliation statement. Order fulfilment and after-sales answering draw on two external data streams: mall POS sales flow and brand ERP order status. The HTTP node in this workflow retrieves values returned by an external system so later nodes can reconcile them or route the case to a person.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a configured address. Params, Body, and Headers can each reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories; chatId and responseChatItemId do not exist in test mode. Return values are extracted with JSON path syntax, multiple return values can be added, and output can be formatted into a string. The chat interface authenticates with an APIKey, and when calling chat/completions the recommended practice is to pass body.appId in the request body. The appId priority order is body.appId, then `<apiKey>-<appId>`, then the appId associated with the apikey. Passed-in fields such as model and temperature have no effect because orchestration determines them. With detail=true the response includes intermediate values, and in stream mode these are distinguished by event.

Hypothetical paper exercise sample: an excerpt from a concession deduction contract states that "Party A, the mall, collects payment centrally; Party B, the brand, bears a deduction at the agreed proportion of sales; the monthly reconciliation statement follows the mall POS flow." A drafted handover request reads: "Have the HTTP node call the mall POS interface to retrieve this month's sales flow and automatically complete reconciliation." In this request the contract only states the basis for the deduction. It does not record authorization for the brand to call the mall POS interface directly, and it does not state that reconciliation is completed automatically by a system. This sample is used only for paper review and does not represent a real customer or an executed operation.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Reason and comparison method |
| --- | --- | --- |
| Request address and method | Fill in according to the mall POS interface document | The document does not provide a specific address; obtain it from mall operations |
| Headers authentication | Authorization: Bearer `{{token}}` | Credentials are injected through secure configuration and not written into public samples |
| Body structure | Check JSON fields against the external interface contract | Takes effect only under POST/PUT request types |
| Variable references | Check global variables and upstream node outputs item by item | Confirm that the actual passed-in values match expectations |
| Return value extraction | Configure keys using JSON path | Compare field by field against the interface response example |
| Debug identity fields | chatId and responseChatItemId do not exist in test mode | Do not treat a debug empty value as a business fault |

## Three common errors

1. Treating retrieval or form collection as authorized execution. In the hypothetical sample the contract states only the deduction basis, while the drafted request asks for automatic reconciliation. The input is the contract excerpt and the drafted sentence; the comparison is whether either records authorization for the brand to call the mall POS interface; the observable result is that the contract does not record that authorization, so the reconciliation action lacks a basis.

2. Treating a similarity score as a permission or entity filter. In the hypothetical sample the HTTP response returns sales flow covering multiple counters. If records are selected only by score, the input is the score field from the interface response; the comparison is whether score corresponds to a counter identifier; the observable result is that score does not carry a permission-filtering role, and the counter identifier must be checked separately.

3. Treating an empty chatId under test mode as a business fault. In the hypothetical sample the workflow is being debugged in test mode. The input is the empty chatId returned; the comparison is against the documented statement that it does not exist in test mode; the observable result is that the empty value is expected behaviour and does not constitute a session abnormality.

## How to verify the setup

1. Input the contract excerpt and the drafted request from the hypothetical sample. Compare whether the drafted sentence exceeds the authorization recorded in the contract. The observable result is that the drafted sentence asks for automatic reconciliation while the contract does not record that authorization, so the request is judged unsupported.

2. Input the sales flow returned by HTTP together with the counter identifier. Compare whether the score field corresponds to the counter identifier. The observable result is that score expresses similarity only, and the counter identifier must be checked separately before ownership can be confirmed.

3. Input the empty chatId returned under test mode. Compare it against the documented statement that chatId does not exist in test mode. The observable result is that the empty value is expected and is not judged a fault. All of the above are paper reviews and have not been executed.
