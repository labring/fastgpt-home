# Dealer ordering events: HTTP integrations for after-sales questions

## What the documents look like

Brand dealer ordering events center on offline dealer reservations and do not directly manage platform storefronts. The operating materials come from the ordering event system, historical sales, dealer inventory, and financial credit approval, with updates occurring by quarter or by year. The everyday documents are the ordering handbook, the ordering contract, the sample list, and the credit approval record. These materials determine which facts can be cited during order fulfillment and after-sales question answering. The ordering handbook states policy and delivery timing. The ordering contract records signing and effective status. The sample list ties physical items to identifiers. The credit approval record shows whether a limit has been approved. The HTTP integration step sends requests to external services and parses responses. It does not replace the business verification performed against those materials.

A retrieval result or a form entry is not an authorization. Retrieval and forms collect or pass values. Approval, database writes, and external synchronization require their own downstream implementation. A pending request is not an approval. An offered option is not an execution. An unsigned termination is not a completed termination.

## Constraints at the HTTP integrations step

The HTTP module sends a request to the corresponding address. Params are path request parameters and are used mostly with GET requests. Body is the request body and is used mostly with POST and PUT requests. Headers carry special information. All three can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and upstream node outputs. The system variables include appId, chatId, responseChatItemId, variables, cTime, and histories. The histories variable defaults to the most recent 10 records and its length cannot be modified. The chatId and responseChatItemId values do not exist in test mode.

Return values are extracted with JSON path syntax. When the output type is set to string, the value at the corresponding key is converted into a JSON string. The chat interface uses APIKey authentication. When calling chat/completions, passing body.appId in the request body is recommended. Authorization: Bearer <apiKey>-<appId> is also supported, and in that case body.appId is not required. The appId priority order is body.appId, then <apiKey>-<appId>, then the appId associated with the apikey for legacy compatibility. The model, temperature, and similar parameters passed in are invalid because the orchestration determines them. When detail=true, intermediate values are returned, and in stream mode they are distinguished through events. The interactive configuration returned to an external caller contains only type and params; internal runtime fields such as entryNodeIds, memoryEdges, nodeOutputs, and nodeResponseId are not returned. Continuing a form input requires keeping chatId consistent and serializing the object into a string as the messages content.

None of these capabilities constitutes authorization. Retrieval is not authorization. A relevance score is not a category, entity, or permission filter, and a similarity setting does not exclude unrelated businesses or unauthorized records.

Hypothetical paper exercise sample: the material text reads, "East China ordering event, 2026 spring session, dealer number HZ-041, ordering contract status pending review, credit approval opinion field empty, sample list number YP-2026-018, corresponding sample is the water purifier filter assembly." The sentence to be judged reads, "HZ-041 credit limit has been approved and this order can be shipped." The authorization boundary of this request is to check only the status already stated in the material and not to supply an approval conclusion.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Comparison method |
| --- | --- | --- |
| Request address and method | Fill in according to the external interface document; the address references an already provided variable | Compare path and method word by word against the interface document |
| Headers authentication | Authorization references a token injected through secure configuration | Check that credentials are not written into public samples |
| Body structure | Write JSON according to the interface contract; strings carry quotation marks | Compare field names and types against the interface document |
| Variable references | Check global variables, system variables, and upstream node outputs item by item | Compare against the values actually passed in |
| Return value extraction | Extract the required key with JSON path | Compare hierarchy against the response example |
| Debug identity fields | chatId and responseChatItemId do not exist in test mode | Distinguish debug empty values from business faults |

## Three common errors

1. Treating a pending review status as approved. In the sample, the ordering contract status is pending review and the credit approval opinion field is empty, while the sentence to be judged states that the credit limit has been approved. The input is the material text and the sentence to be judged. Comparing how the two describe the credit status, the observable result is that the sentence to be judged contains a conclusion not stated in the original text.

2. Treating retrieval or a form as authorized execution. In the sample, the material records only identifiers and status and states no approval action. The input is the handover request. Comparing whether it demands shipment execution, the observable result is that the request demands a business action the material does not authorize.

3. Treating an empty debug value as a business fault. The sample involves no real interface call. The input is the statement that chatId does not exist in test mode. Comparing it with a business fault, the observable result is that this empty value belongs to a documented debug condition.

## How to verify the setup

1. Input the sample material text and the sentence to be judged. Compare the credit conclusion in the sentence to be judged with the status stated in the original text. If the original text states only pending review and the approval opinion is empty, the sentence to be judged is unsupported and the evidence gap must be recorded.

2. Input the handover request. Compare the action the request demands with the authorization scope stated in the material. If the material states no approval or shipment authorization, the request remains pending verification and cannot be treated as executable.

3. Input the test mode statement. Compare the existence conditions of chatId and responseChatItemId. If test mode applies, the absence of both is a documented condition and must be distinguished from a real business fault.
