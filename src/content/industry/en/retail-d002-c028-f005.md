# Brand livestream operations: multi-turn prompts for after-sales questions

## What the documents look like

Brand-run livestream rooms carry their own scripts, stock, and after-sales work; commission from external hosts is not the main commercial structure. This shapes what the order-fulfillment and after-sales question-answering step has to read: livestream scripts, product explanation cards, shift schedules, and livestream reviews. The generic brief lists Douyin Shop Compass, Juliang Qianchuan, livestream comments, and transaction detail as data sources, with updates per session and per hour. Those rhythms describe the operating cadence; they do not by themselves create batch synchronization, full synchronization, real-time triggers, or transaction-triggered mechanisms.

For multi-turn prompts, the practical material is the set of checkable statements inside those four documents: which product, which price, which time window, which host, which quantity. The prompt has to name the document scope, the answering task, and how to behave when evidence is missing, so the model does not write business facts that the source material does not contain. A second concern is the actual context carried into a continued conversation, which must be distinguished from the input of a new session. A third is reference resolution and question expansion when a knowledge base is used for continuous dialogue; short questions are not assumed to work the same way in every case. Model choice and reply length must be checked against the supported context and reply settings, and long documents combined with follow-up questions need their own examination. Reply format follows the downstream consumer; when json_schema is selected, the corresponding format requirement is filled in and the returned structure is verified.

## Constraints at the multi-turn prompts step

The prompt itself is the first constraint. It states the document scope, the answering task, and the handling of missing evidence. Statements that go beyond the source material are recorded as unsupported rather than confirmed. History handling is the second: the number of turns actually carried into context is checked, and a new session is distinguished from a continued session. Question optimization is the third: reference resolution and question expansion are checked when a knowledge base is used for continuous dialogue, and short questions are not assumed to be universally applicable. Model and length form the fourth: the supported context and reply ceiling are checked, and long-document plus follow-up combinations are examined. Reply format is the fifth: it is chosen according to the downstream consumer, and json_schema requires the format requirement to be filled in and the returned structure verified. An interactive node collects form values; business verification, approval, database writes, and external synchronization require their own downstream implementation. A waiting state does not constitute authorization.

Hypothetical paper exercise sample. The source text available for checking is: "Product explanation card: Item A thermos cup, livestream price 89 yuan, valid this session from 20:00 to 22:00." "Shift schedule is On March 8, from 20:00 to 22:00, host Jia presents Item A." "Livestream review: On March 8, Item A closed 120 orders, of which 15 were submitted after 22:05." The draft sentence to be judged is: "Item A thermos cup still closed at 89 yuan after 22:05 on March 8." This sentence involves subject, object, time window, and price, and must be checked against the source text.

Hypothetical starting value for this page's exercise: the reply ceiling is set to a lower value, on the reasoning that after-sales answers are mostly short replies, and the comparison is whether replies are truncated relative to the default value. This starting point is a page hypothesis, not an official default.

## Three common errors

1. Treating retrieval or form submission as authorized execution. The input is the form value returned by an interactive node; the comparison object is the downstream approval or database-write record; the observable result is that only a value was collected while no approval record exists, which is an unexecuted state.
2. Treating a similarity score as a permission or entity filter. The input is a quoteList carrying score; the comparison object is the datasetId and authorization scope to which the record belongs; the observable result is that a high-scoring record may still fall outside the current authorization scope.
3. Treating a pending review as a lack of operating permission. The input is a request whose status is pending review; the comparison object is the three separate facts of signing, cooperation being reached, and contract taking effect; the observable result is that none of the three is confirmed.

## How to verify the setup

1. Input the three source passages from the hypothetical sample together with the draft sentence "Item A thermos cup still closed at 89 yuan after 22:05 on March 8." The comparison object is the explanation card's validity window of 20:00 to 22:00 and the 15 orders submitted after 22:05 in the review. The condition is met when the draft sentence is marked as beyond the material scope and pending verification, and is not written as confirmed transaction.
2. Input a follow-up question in a continued session. The comparison object is the number of history turns actually carried in versus the input of a new session. The condition is met when the two can be distinguished and reference resolution is not assumed for every short question.
3. Input an empty-result downstream scenario, using an explicit paper input of [] to check the downstream design. The comparison object is how the downstream node handles an empty reference. The condition is met when the downstream follows the empty-reference branch, without claiming that retrieval necessarily returns []. For libraries across different vector models, check the identifier first and exclude those that do not match; do not run cross-model retrieval to compare missed recall.
