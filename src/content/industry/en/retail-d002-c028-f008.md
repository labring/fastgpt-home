# Brand livestream operations: workflow routing for after-sales questions

## What the documents look like

Brand-operated livestream rooms carry their own scripts, inventory and after-sales handling; creator commissions do not form the main settlement relationship. For order fulfilment and after-sales answers, four working documents matter at the same time. The livestream script states what was promised on air, such as dispatch timing. The product explanation card carries specifications and time windows. The shift schedule names who is on duty. The transaction detail shows which orders actually occurred. Douyin Shop Compass, Juliang Qianchuan, livestream comments and transaction details are the main data sources, and the supplied material gives two update levels: per session and hourly.

At the routing step these materials serve as comparison references. Script and explanation card describe outward statements; transaction detail describes what happened; shift schedule describes who receives the request. Workflow routing connects these inputs to interaction nodes and to later processing. Interaction nodes collect and confirm values. Business actions such as order writes or status synchronisation need a separate interface or a later process.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the workflow continues after the user completes the interaction. The user fills required information and submits; the node then passes the collected form values to later nodes. The user selection node is also a user interaction node. When the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. Both nodes can be added repeatedly and trigger execution. The documented behaviour is entering the interaction state, recording state, and hiding the dialogue box. The documents do not describe a global state-recording switch, a submission-count limit, or an automatic judgement mechanism.

Retrieval and similarity scores do not perform authorisation. Libraries built on different vector models cannot be associated together; identifiers must be checked first and non-matching libraries excluded. Retrieval is not authorisation. A form collects values; business verification, approval, database writes and external synchronisation each need their own downstream implementation. The overall workflow diagram lists optional paths, and those paths do not all execute on every request. Image retrieval requires a corresponding image input and model capability. Reranking requires a model and must be enabled in settings. An empty result can be checked against downstream design using a clearly labelled paper input.

## Three common errors

1. Treating retrieval results as an authorisation basis. A similarity score is not an entity, category or permission filter, and retrieval does not produce authorisation. Check: enter one after-sales request that has not been approved, compare node output with downstream interface input, and confirm no write or synchronisation action appears.

2. Describing existing interaction-node behaviour as a configurable switch. The documents state that triggering enters the interaction state and records state; they do not state that a global state-recording switch or submission-count control exists. Check: compare configuration item names with the document text and record whether any switch or limit appears that the document does not contain.

3. Associating libraries across different vector models. Libraries built on different vector models cannot be associated together. Check: verify library identifiers and vector model identifiers, exclude non-matching ones, and record the actual observation. Do not infer missed recalls or redundant results from this.

## How to verify the setup

Hypothetical drill sample: the source material reads, "This session promises dispatch within 48 hours of order placement; after-sales issues are registered together by the on-duty floor controller after the livestream ends." The signature line is item 3 of a livestream script dated 1 June 2025 from a brand livestream team, valid for that session. The draft sentence to be judged is: "After-sales requests from this session's orders are authorised to be written directly into the fulfilment system."

- Verification one: input the script text above and the draft sentence, then compare the authorisation wording in the draft with what the source states. The source states only a promised time window and a registration method; it does not state authorisation to write into the fulfilment system. The draft sentence is unsupported and should be recorded as pending verification.

- Verification two: input the required form fields as order number, issue type and expected handling, then compare the values passed to later nodes after submission with the form definition. When all three values match the definition, the condition is met; when a field is missing, record the gap.

- Verification three: input the paper empty result [], then compare whether the downstream node design has an explicit handling path. When the downstream design handles empty input explicitly, the condition is met; when no handling exists, record it as a design gap. All three are paper checks and were not run.
