# After-sales repairs and reships: workflow routing for after-sales questions

## What the documents look like

After-sales repair and reship work aims to restore a product to use, and it does not close a case through a direct refund. The main data sources for this category are the after-sales system, the order system, repair sites and the parts warehouse WMS. Daily documents include repair requests, reship orders, inspection reports and parts outbound orders. Data updates per order and per day.

Workflow routing carries the objects, states and validity scope recorded in those documents into later nodes as inputs. The form input node and the user selection node are user interaction nodes. When either node is triggered, the conversation enters an interaction state, the workflow state is recorded, and the workflow continues after the user finishes the interaction. The form input node collects the required information the user submits and passes it to later nodes. The user selection node evaluates the user's choice and executes the corresponding yes branch. Both nodes can be added repeatedly and can trigger execution. Retrieval and form collection do not constitute authorized execution. During an operations handover, the authorization state of materials, actions and requests must be checked separately.

## Constraints at the workflow routing step

The form input node enters the interaction state when triggered and records the workflow state. After the user completes the required fields and submits, the node passes the collected information to later nodes. The user selection node executes the corresponding yes branch after the user makes a choice. The documentation describes the interaction state, the recording of workflow state and the hiding of the dialog box as behavior of these interaction nodes. It does not document a separate global state switch, a submission count limit, automatic judgment or a snapshot guarantee.

Order writes, document backfill and external status synchronization require a separate business interface or a later process. A form output field is a collected value, and it does not by itself complete a business verification, an approval, a database write or an external synchronization. A pending request is not an approval, an offered option is not execution, and an unsigned termination is not a completed termination. A relevance score is not a category, entity or permission filter, and retrieval is not authorization.

Hypothetical paper test case: the repair request in the after-sales system reads "Request number WX-2024-0417; the subject is a brand after-sales site; the object is the item under order A; the status is pending review; the validity scope is the repair request submitted on 17 April 2024." The proposed draft sentence is "This repair request has been approved and a reship can be arranged directly." The status field in the source text records only pending review and states no approval fact, so the proposed sentence is unsupported.

## Three common errors

1. Treating a pending-review status as approved. The input is the repair request source text, the comparison is between the status field and the proposed draft sentence, and if the source text records only pending review while the draft states approval, the draft is unsupported.
2. Omitting a branch connection on the user selection node. The input is the user selection node configuration, the comparison is between each branch and its downstream node connection, and if a branch has no downstream node, that path has no output handoff.
3. Treating information collected by the form as a completed order write. The input is the form output field, the comparison is whether a downstream interface node exists, and if only a form node exists without an interface node, the order write and external synchronization remain to be implemented separately.

## How to verify the setup

1. Take the hypothetical source text "Request number WX-2024-0417, status pending review" and compare it field by field with the proposed draft sentence "has been approved, a reship can be arranged directly." The expected observation is that the status field and the draft do not agree, so the draft is recorded as unsupported rather than as a denial or a conflict.
2. Take the branch configuration of the user selection node and check one by one whether each branch connects to a downstream node. The expected observation is that every branch has a clear downstream handoff; any branch without a connection is recorded as still to be completed.
3. Take the output field of the form input node and check whether it is passed to a later retrieval, judgment or interface node. The expected observation is that the output field is visible in a later node; if the downstream has only retrieval and no interface node, the order write and external synchronization remain to be implemented separately.

An empty retrieval result can be checked on paper by supplying an explicit empty input and confirming how the downstream design handles it. This page does not claim that any fictional rule returns an empty result. Where a document field is not provided, the value remains unknown.
