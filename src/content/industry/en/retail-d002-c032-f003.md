# Retail checkout and loyalty: shared access for after-sales questions

## What the documents look like

Retail checkout and loyalty promotion work centers on price and membership benefits. It does not handle short-shelf-life inventory. The main data sources are the POS system, the membership CRM, the payment platform, and the price tag system. Daily documents include promotional price tags, membership points rules, the checkout daily report, and exception refund slips. These records update by day and by shift.

In the order fulfillment and after-sales question stage, the material that gets shared or embedded is usually a checkout difference explanation, a points exception handling position, or a refund progress reply. The sharing entry point is a no-login window created from the publish channel. The system generates a localId for each user to identify that user and to pull conversation records from the cloud. This localId only holds within the same device and the same browser. Switching devices or clearing browser cache loses those records. For this reason, users can pull only the most recent 30 days and 20 records.

## Constraints at the shared access step

The no-login window is created under application details, publish channel, no-login window. After a name is filled in, the link is created; the name is used only for record display. Clicking to start opens the usage link, which can be copied. The link identifier is an access entry point. It cannot be treated as business authorization.

Anonymous users receive a system-generated localId. This identifier supports pulling conversation records only under the same device and same browser condition, within the 30-day and 20-record boundary. Cross-device records require a separately designed identity and session arrangement. Expiration time, QPM, points cap, and identity verification are checked against the actual version; some parameters are supported only in the commercial edition. Identity verification is a POST root address. Initialization, conversation start, and conversation finish each send a request to a specific endpoint under that address. The server returns only whether verification succeeded.

The unified response format contains success, message, msg, and data. FastGPT judges whether success is true to decide whether the user may continue. message and msg are equivalent; either may be returned. When success is not true, that error is shown. uid is the user's unique credential and must be returned. The uid format is a string that does not contain "|", "/", or "\", with a byte length of 255 or less. Otherwise the error Invalid UID is returned. uid is used to pull and save conversation records.

A hypothetical paper exercise sample: a store checkout supervisor submits a handover request dated 10 March 2026. The material text reads: "The 9 March A-shift checkout daily report shows one exception refund slip with status pending review; the corresponding membership points rule states that this refund involves a points deduction; the promotional price tag was valid on that day." The draft sentence to be judged reads: "This exception refund has been fully processed, the points have been deducted, and the member may be answered." The material only shows the refund slip in pending review status. The draft sentence goes beyond the source text.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Comparison method |
| --- | --- | --- |
| Share link | Use the full link generated by the system | Check the link identifier and the access entry scope |
| Expiration time | Set according to the date range marked in the handover material | Compare link availability period with material dates |
| QPM | Check against maximum visits per user per minute | Compare with the supported range of the actual version |
| Points cap | Check against the usage limit of the share entry | Compare cost attribution and cap description |
| Identity verification | Fill in the POST root address | Check the returned success and uid |
| Conversation record boundary | Check against same-device same-browser condition | Compare whether cross-device records are separately designed |

The hypothetical starting values above are chosen to match the material date range and the documented parameter meanings. They are not official defaults. Each is compared against the actual version support range or the material's own stated scope.

## Three common errors

1. Treating the share link identifier as business authorization. The link provides an access entry only. Authorization status must be checked separately against the identity verification return and the material original.

2. Writing a pending-review refund slip as fully processed. In the sample above, the refund slip status is pending review, while the draft sentence states it has been fully processed. The input and the comparison object do not match.

3. Treating retrieval or similarity settings as a permission filter. Retrieval does not exclude unrelated business records or unauthorized records. The basis is the identity verification return and the material scope.

## How to verify the setup

1. Input the hypothetical material text above and the draft sentence. Compare the refund slip status field: the original is pending review, the draft sentence is fully processed. A status mismatch means the condition is not met.

2. Input the identity verification interface return. Compare whether success is true and whether uid meets the character and length requirements. When success is false, the error is shown; the condition for allowing the user to continue is not met.

3. Input the share link and the material date range. Compare the link expiration time with the date marked in the material. When the link exceeds the material date range, the access entry and the material period do not match, and the item remains to be verified.

Points deduction, refund processing, and member replies are downstream business actions. They need their stated downstream implementation. The material above does not show them as completed. A pending request is not approval. An offered option is not execution. The evidence gap remains.
