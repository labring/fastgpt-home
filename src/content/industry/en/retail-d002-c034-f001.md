# Export tax rebate filings: HTTP integrations for after-sales questions

## What the documents look like

Export tax rebate filing happens after goods leave the country, and the work centers on matching tax vouchers to the export record. The main data sources are the electronic tax bureau, the export rebate filing system, customs electronic information, and the finance ledger. The documents handled day to day are the export tax exemption and rebate filing form, the export customs declaration, purchase invoices, and foreign exchange receipt vouchers. These materials carry fields that must move through HTTP integrations during order fulfillment and after-sales question handling. Values passed through an interface have to correspond item by item with the source material, and an interface call does not replace a business-level check of those materials.

The filing cycle runs monthly and per batch. That rhythm matters here because the interface passes values that later feed voucher matching, and a value carried forward from a prior batch does not describe the current batch. The documents also differ in what they actually state. A purchase invoice may name a corresponding customs declaration number without stating that the filing form was generated, and a foreign exchange receipt voucher may state an amount while leaving the filing status unstated. The integration layer should carry these distinctions rather than flatten them.

## Constraints at the HTTP integrations step

The HTTP module sends a request to the corresponding address. Params are path request parameters and are used more often in GET requests. Body is the request body and is used more often in POST and PUT requests. Headers are request headers and carry special information. All three can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and upstream node outputs.

System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. Histories defaults to at most 10 entries and its length cannot be modified. chatId and responseChatItemId do not exist in test mode. Return values are extracted with JSON path syntax, and when the output type is set to string, the value for the corresponding key is converted to a JSON string. In the chat interface, calling `chat/completions` recommends passing `body.appId` in the request body, and also supports `Authorization: Bearer <apiKey>-<appId>`. Passed fields such as model and temperature have no effect, because these are determined by the orchestration. When detail=true, intermediate values are stored in responseData. A plugin application does not need chatId or messages; inputs are passed through variables and outputs are read through pluginData.

An interface call, a retrieval result, and a completed form do not by themselves constitute authorization. Business verification, approval, database writes, and external synchronization each require their own downstream implementation. The HTTP module extends reach to databases, external data sources, web search, and email, and that reach is a capability, not a permission.

Assumed drill sample: a finance staff member at a foreign trade enterprise handles one export tax rebate filing during order fulfillment and after-sales question handling. The source materials are: "Export customs declaration: declaration number HYP-2024-0417, export date 17 April 2024, goods are cotton women's shirts, quantity 1200 pieces. Purchase invoice: invoice number FP-0417, issue date 20 April 2024, corresponding customs declaration number HYP-2024-0417. Foreign exchange receipt voucher: voucher number SH-0506, receipt date 6 May 2024, amount consistent with invoice FP-0417." The draft sentence to be judged is: "The purchase invoice and customs declaration for this export tax rebate filing are matched, the foreign exchange receipt voucher is complete, and the filing can be submitted." The draft sentence claims matching and completeness, but the materials only show that the invoice names a corresponding declaration number and that the receipt amount matches the invoice. They do not state that the filing form was generated, that doubts were resolved, or that authorization was issued, so the claim is unsupported.

## Configuration and implementation checks

| Configuration item | Assumed trial starting point for this sample | Check method and reason |
| --- | --- | --- |
| Request address and method | Selected per the external interface document, with the address referencing a provided variable | Check item by item whether the address, method, and interface contract agree |
| Headers authentication | Injected through secure configuration, not written into a public sample | Check whether the authentication credential is passed through secure configuration |
| Body structure | Used only under the corresponding request type | Check the JSON structure against the external interface contract |
| Variable references | References global variables, system variables, and upstream node outputs | Check the actual passed values item by item |
| Return value extraction | Key configured per JSON path | Check the extracted result against the interface response fields |
| Debug identity fields | chatId and responseChatItemId do not exist in test mode | Do not treat a debug empty value as a business fault |

## Three common errors

1. Treating an interface call as authorized execution. Input is the draft sentence above together with the source materials. Compare the draft's claim that the filing "can be submitted" against whether the materials state authorization or a generated filing form. The materials do not state either, so the claim is unsupported.
2. Treating a retrieval result or a completed form as business verification. Input is the invoice number and customs declaration number returned by the interface. Compare whether the two agree on the same entity, the same period, and the same field. When the filing form fields are not stated, the status remains to be verified.
3. Treating a test-mode empty value as a business fault. Input is the test-mode condition in which chatId and responseChatItemId do not exist. Compare whether the empty value is judged as a business exception. The document states these do not exist in test mode, so this does not constitute a business fault.

## How to verify the setup

1. Input the source materials above and the draft sentence. Compare whether the matching and completeness claimed in the draft have corresponding fields in the materials. The submit condition is met only when the materials state that the filing form was generated and that authorization was issued. The expected result is unsupported.
2. Input invoice number FP-0417 and customs declaration number HYP-2024-0417 as returned by the interface. Compare whether the two agree on the same entity, the same period, and the same field. Only an explicit mutually exclusive value counts as a contradiction; an unstated field remains to be verified.
3. Input the test-mode condition in which chatId and responseChatItemId do not exist. Compare whether the empty value is judged as a business fault. The document states these do not exist in test mode, so the expected result is that this does not constitute a business fault.
