# Trade returns and claims: HTTP integrations for after-sales questions

## What the documents look like

Trade return and claim work begins after export and handles reverse logistics and liability determination. The documents that circulate in this category include the return agreement, the claim letter, the quality report, and the return customs declaration. Sources include customer email, inspection reports, customs systems, and insurer claim systems. These materials arise case by case, update irregularly, and are handled once per case.

At the HTTP integrations step, document form shapes request form. The return agreement and claim letter are bilateral documents whose clause status needs human confirmation. The quality report and return customs declaration carry identifiers, dates, and quantities, which suit structured fields. Content returned by an external system is that system's output. This platform sends the request and parses the response; it does not perform business determination on the returned result.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a given address. Params carry path parameters, Body carries the request body, Headers carry request headers. All three positions and the URL can reference variables through `{{}}`. Variables come from global variables, system variables, and preceding node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. chatId and responseChatItemId do not exist in test mode, so reading an empty value during debugging is an environment difference.

Return values are extracted through JSON path. When the output type is set to string, the corresponding value is converted into a json string. For chat interface calls, passing body.appId in the request body is recommended; `Authorization: Bearer <apiKey>-<appId>` is also supported. Passed fields such as model and temperature have no effect and are decided by the orchestration. Retrieval or form collection only completes value capture. Business verification, approval, database writes, and external synchronization each need their own downstream implementation.

Hypothetical drill sample: an export after-sales staff member handles one return shipment. The material text reads "Return agreement number TR-2024-018, signing date 12 March 2024, return quantity 200 pieces, return reason recorded as surface scratches," together with "Claim letter number CL-2024-007, claim amount pending determination by the insurer claim system." The handover request to be judged is: "Write the return agreement number and return quantity into the external claim system, and confirm the claim has been accepted." In this request, the agreement number and quantity are directly capturable fields. Whether the claim has been accepted is an external system state not recorded in the material, and cannot be inferred from a request on this page.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this drill | Basis and comparison method |
| --- | --- | --- |
| Request address | Interface address provided by the external claim system | Fill in per the external interface document; the address can reference provided variables |
| Request method | POST | Choose per the external interface document; Body takes effect only under the corresponding request type |
| Headers | Authentication credential injected through secure configuration | Not written into public examples; check the actual injected value |
| Body fields | Return agreement number, return quantity | Reference preceding node outputs; check the actual passed values item by item |
| Return value extraction | Extract the acceptance status field by JSON path | When output type is string, it converts to a json string |
| Debug identity | chatId and responseChatItemId left empty | These two variables do not exist in test mode; not treated as a business fault |

## Three common errors

1. Treating a state not recorded in the material as confirmed. In the sample, the claim letter states only that the claim amount is pending determination by the insurer claim system. If "accepted" is written into the request body, the input is the material text, the comparison object is the state recorded in the claim letter, and the observable result is a state value in the request body that the text does not contain.

2. Treating retrieval or form value capture as authorized execution. The sample handover request asks to "confirm the claim has been accepted." The input is the agreement number collected by the form, the comparison object is the acceptance field returned by the external system, and the observable result is that this page's flow produces no acceptance conclusion.

3. Treating an empty chatId in test mode as an interface fault. The input is a request initiated in test mode, the comparison object is the system variable description stating chatId does not exist in test mode, and the observable result is that the request can still be sent and an empty chatId is an environment difference.

## How to verify the setup

1. Take the sample text "Return agreement number TR-2024-018, return quantity 200 pieces," pass that number and quantity as variables into Body, and compare the values that actually appear in the request body. The condition is met when both match the text; it is not met when a field value absent from the text appears.

2. Take the proposed sentence "Confirm the claim has been accepted" and compare it with the claim letter text "claim amount pending determination by the insurer claim system." The condition is met when the proposed sentence does not write the pending state as accepted; it is not met when the pending state is presented as accepted.

3. Take the test-mode request and compare the actual values of chatId and responseChatItemId. The condition is met when both are empty and the request is sent normally; it is not met when the empty values are recorded as a business fault. All three are paper reviews and were not actually executed.
