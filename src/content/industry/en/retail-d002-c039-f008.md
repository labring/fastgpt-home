# Tmall flagship operations: workflow routing for after-sales questions

## What the documents look like

Order fulfilment and after-sales answering for a Tmall flagship store draws on four document families: product listing pages, brand authorisation letters, dispatch commitment records, and after-sales tickets. The category differs from JD POP stores in its emphasis on brand authorisation, flagship-store identity, and Tmall points compensation rules. That difference shapes routing: the authorising party and the scope of authorisation have to be carried as separate fields rather than folded into a single "approved" flag.

Sources named for this category are the Tmall merchant backend, the Tmall rules centre, ERP order tables, and customer-service chat logs. Update frequency is daily and per order. Documented consequences of error include product delisting, delayed-dispatch compensation, and a falling store rating. None of those consequences is decided inside the workflow; the routing step compares material states and passes the request to the correct branch.

## Constraints at the workflow routing step

The Form Input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the interaction the workflow continues downward. When the user fills the required information and submits, the node collects the submitted form values and passes them to later nodes. The User Selection node is also a user-interaction node with the same interaction-state behaviour; when the user makes a choice, the node evaluates that choice and executes the "yes" branch. Both nodes can be added repeatedly and both trigger execution.

Forms collect values. Business verification, approval, database writes, and external synchronisation require a separately connected business interface or a later process. Retrieval and forms do not constitute authorisation to execute. Semantic recall and relevance scoring do not perform permission or entity isolation. Libraries built on different vector models cannot be associated together; the model identifier must be checked first and non-matching libraries excluded, with the actual observation recorded. A relevance score is not a category, entity, or permission filter, and it does not exclude unrelated businesses or unauthorised records.

Hypothetical paper exercise sample. The source text supplied for comparison consists of three sentences. "The brand authorisation letter for this store states that the authorising party is Brand Owner A, the authorised party is Flagship Store B, the authorisation is valid until 31 December 2026, and the authorised scope is the home appliance category." "The dispatch commitment record states that order A1001 was promised dispatch within 48 hours, with an order date of 1 March 2026." "The after-sales ticket states ticket T2001, in which the customer raised a delayed-dispatch enquiry about order A1001, and the current status is awaiting customer-service reply." The draft sentence to be assessed reads: "Order A1001 has been confirmed as delayed dispatch, compensation is paid to the customer under the Tmall points compensation rules, and after-sales ticket T2001 is synchronised to closed." The draft sentence converts an awaiting-reply status into closed, converts a commitment record into a confirmed delay, and attaches no source text for the compensation rule.

## Configuration and implementation checks

| Configuration item | Role | Point to check |
| --- | --- | --- |
| Form Input node | Collects required information | After submission, information passes to later nodes; compare each input against each output |
| User Selection node | Routes along the "yes" branch | Verify branch connections one by one; do not assume automatic evaluation |
| Interaction-state check | Records workflow state | Follow the documented behaviour; do not add a global state switch |
| Output hand-off check | Passes collected information to retrieval, evaluation, or interface nodes | Compare each output against its input |
| External action separation | Order writes, document backfill, external synchronisation | Requires a separately connected business interface or later process |
| Sample field mapping | Authorising party, authorised party, validity period, scope | Hypothetical starting point for this exercise; compare word by word against the source text |

## Three common errors

1. Treating form submission as completed business verification. Input is the submitted form value; the comparison object is the authorising party, authorised party, validity period, and scope in the brand authorisation letter source text; the observable result is whether the draft sentence states a definite conclusion while the authorisation source text is absent.
2. Writing an awaiting-reply status as closed. Input is the status field of after-sales ticket T2001; the comparison object is "awaiting customer-service reply"; the observable result is whether the draft sentence rewrites the awaiting state as closed.
3. Writing a commitment record as a confirmed delay. Input is the commitment and order date in dispatch commitment record A1001; the comparison object is whether independent evidence of an actual delay exists; the observable result is whether the draft sentence states "confirmed delayed dispatch" while that evidence is absent.

## How to verify the setup

1. Compare the three hypothetical source sentences against the draft sentence. Input is the authorisation letter, dispatch commitment record, and after-sales ticket source text; the comparison object is the party, counterparty, status, and scope named in the draft sentence; the condition is met when the draft sentence matches the source text word by word or explicitly marks the point as pending verification.
2. Check empty-result hand-off. Input is a clearly stated paper input of []; the comparison object is whether the downstream node design handles the empty result through its own branch; the condition is met when the downstream produces no fabricated record. No claim is made that a retrieval of an invented rule necessarily returns [].
3. Check cross-model identifiers. Input is the vector model identifier of each retrieval library; the comparison object is whether the identifiers match; the condition is met when only non-matching libraries are excluded and the actual observation is recorded. No cross-model retrieval is executed to compare missed recalls.

This page addresses only the workflow routing step for order fulfilment and after-sales answering in Tmall flagship daily operations. It does not decide which materials, actions, or requests are authorised at hand-over; a form or a retrieval result is not an authorisation to execute. Where the source text does not state a field, the value remains unknown, and any conclusion resting on it remains unsupported pending verification.
