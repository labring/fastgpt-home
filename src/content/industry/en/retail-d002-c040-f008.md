# Customer-service knowledge: workflow routing for after-sales questions

## What the documents look like

Knowledge-base maintenance for customer-service inquiries sits upstream of refund approval. Its outputs are FAQ entries, reply templates, product parameter tables and escalation tickets. These materials do not determine refund outcomes. The main data sources are the customer-service system, product detail pages, after-sales question statistics and quality-check sampling. Update frequency is weekly or monthly.

For the order-fulfilment and after-sales question-answering task, workflow routing must collect the user's order information, question type and expected request, then pass them to later retrieval or decision nodes. The Form Input node and the User Selection node are both user-interaction nodes. When either node triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The Form Input node collects required information and passes it to later nodes. The User Selection node evaluates the user's choice and executes the corresponding "yes" branch. Neither node writes orders, approves refunds or synchronizes external status. Those actions require a separate business interface or a later process.

## Constraints at the workflow routing step

Because knowledge-base maintenance produces question-and-answer material, workflow routing can only carry information collection and branch selection. A retrieval hit or a form submission does not constitute authorized execution. Retrieval performs relevance matching and does not enforce permission or entity isolation. A similarity setting does not exclude unrelated businesses or unauthorized records. Libraries built on different vector models cannot be associated together. Check the model identifier first and exclude non-matching libraries. Do not run cross-model retrieval to compare missed recalls.

The optional paths shown in an overall document flow diagram do not all execute on every request. Image retrieval requires a corresponding image input and model capability. Reranking requires a model and must be enabled according to configuration. For empty-result handling, a clearly stated paper input of `[]` can be used to check downstream design. Do not claim that a fictional rule-based retrieval necessarily returns `[]`. Interaction waiting, state recording and dialog hiding follow the documented behavior of interaction nodes. Do not introduce a global state-recording switch, submission-count limit, automatic judgment or snapshot guarantee. The thinking budget is a reasoning budget and cannot be reassigned as a citation token limit.

## Configuration and implementation checks

Hypothetical drill sample: a knowledge-base operator is preparing FAQ entries for order fulfilment and after-sales question answering in June 2025. The source material to be checked reads: "Ticket A-0612 was created by the customer-service supervisor on 10 June 2025, status pending review, concerning a delivery delay for order O-20250610-001; the requester asks to supplement the reply template." The proposed draft sentence reads: "Ticket A-0612 has passed review and can be used directly as a standard reply for order fulfilment and after-sales question answering." The draft sentence conflicts with the source material's pending-review status and cannot be used as an effective reply.

| Configuration item | Hypothetical starting point for this drill | Reason for the choice and comparison method |
|---|---|---|
| Required fields on the Form Input node | Order number, question type, expected request | Compare item by item against the inputs required by later retrieval or decision nodes |
| Branch on the User Selection node | A "yes" branch connected to the after-sales question-answering flow | Verify branch connections one by one and confirm the corresponding branch executes after selection |
| Interaction-state check | Entering the interaction state and recording workflow state after triggering | Check the documented interaction behavior; no additional switch is introduced |
| Output hand-off | Passing collected information to later retrieval, decision or interface nodes | Compare each output against its corresponding input |
| Division of external actions | Order writes, document backfill and external synchronization connect to a separate business interface | Check whether these actions are declared as implemented by a later process |
| Retrieval library identifier check | Check the vector model identifier first and exclude non-matching libraries | Cross-model association is not permitted; record the actual observation |

## Three common errors

1. Treating a pending-review ticket as having passed review. The input is the source material's "status pending review"; the comparison is the draft sentence's "has passed review"; the observable result is that the two status fields do not match and the draft sentence is unsupported.
2. Treating a retrieval hit or form submission as authorized execution. The input is the order number and question type collected by the form; the comparison is whether a later node declares a business interface; the observable result is that the Form Input node documentation describes collection and hand-off only, with no write or approval.
3. Associating retrieval libraries built on different vector models. The input is two libraries with different vector model identifiers; the comparison is whether the identifiers match; the observable result is that non-matching libraries are excluded and no cross-model retrieval is run to compare missed recalls.

## How to verify the setup

1. For the draft sentence "Ticket A-0612 has passed review," the input is the source material's "status pending review." Compare the same status field for the same ticket. The condition is met when pending review and passed review are found to be mutually exclusive, and the draft sentence is judged unsupported.
2. For the Form Input node configuration, the input is the required fields order number, question type and expected request. Compare whether later nodes receive these fields. The condition is met when outputs correspond to inputs item by item and no write or approval is declared.
3. For the two retrieval libraries, the input is each library's vector model identifier. Compare whether the identifiers match. The condition is met when non-matching libraries are excluded and the actual observation is recorded. Cross-model association is not permitted, and no inference is drawn about missed recalls or redundant results.
