# Product listing reviews: workflow routing for after-sales questions

## What the documents look like

Title and detail-page compliance for platform listings deals with the truthfulness of promotional wording and the display of supporting qualifications. It does not deal with parcel delivery, which belongs to platform shipping operations. Four document types carry the working material: the product title table, detail-page assets, the prohibited-terms list, and inspection reports. The title table records the correspondence between proposed wording and the physical parameters of the item. Detail-page assets carry images and accompanying text. The prohibited-terms list collects expressions that the platform rules centre and the advertising-law compliance checklist require writers to avoid. Inspection reports supply the parameter basis for claims.

These materials are updated weekly and on each new listing. Sources are the platform rules centre, the advertising-law compliance checklist, the brand asset library, and testing-agency reports. In the order-fulfilment and after-sales question context, operations staff hand these materials to a workflow, where interaction nodes collect the necessary information and later nodes act on it. The materials themselves do not determine authorisation status. Complete materials only mean the package can be submitted for checking.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The node then collects the form information the user submitted and passes it to subsequent nodes. The user selection node also enters an interaction state; when the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. The recorded interaction state is existing node behaviour. No separate global state-recording switch is documented, and none should be assumed.

Collected information must be passed explicitly to the later retrieval, judgement, or interface nodes, and outputs must be compared against inputs item by item. Order writes, document backfill, and external status synchronisation require a separate business interface or a later process. Retrieval or form submission does not by itself constitute authorised execution. Image retrieval requires a corresponding image input and model capability. Reranking requires a model and must be enabled according to its settings. Libraries built on different vector models cannot be associated together; check identifiers first and exclude those that do not match. Semantic recall and relevance scores do not perform permission or entity isolation.

Hypothetical paper exercise sample: the source material reads, "Product A title table proposed sentence: this item uses 304 stainless steel; inspection report number Q-2024-017 states the main body material is 304 stainless steel, report date March 2024, covering that batch; the prohibited-terms list does not include this expression." The sentence to be assessed is, "This item uses 304 stainless steel and has passed testing-agency inspection." The handover request reads, "Write the above proposed sentence together with the inspection conclusion into the detail page and synchronise the order note." In this request, writing to the detail page and synchronising the order note are external business actions that require a separate interface. Form submission does not produce that effect.

## Three common errors

1. Treating form submission as authorised execution. In the sample, the handover request asks for a detail-page write and an order-note synchronisation. Submission only collects information. Order writes and external status synchronisation require a separate business interface, and submission does not produce that effect.

2. Treating the "yes" branch of the user selection node as an automatic judgement. That node executes the corresponding branch after the user makes a choice. The judgement comes from user feedback, and the node does not itself determine that the proposed sentence is compliant.

3. Treating retrieval relevance as a permission or entity filter. In the sample, matching the proposed sentence against the report number is semantic recall. Relevance does not exclude unrelated businesses or unauthorised records, and retrieval does not carry the authorisation decision.

## How to verify the setup

1. Input the sample source material and the proposed sentence, then compare the proposed wording against the main body material, report number, date, and covered batch stated in the inspection report. Where the report does not state a passed-inspection conclusion, that conclusion remains pending verification and is not judged supported or contradictory.

2. Input the handover request, then compare whether the two actions in the request, writing to the detail page and synchronising the order note, are carried by separate interfaces in the flow. Where only the form input and user selection nodes exist, the two actions are not supported and are recorded as awaiting implementation.

3. Input the paper empty result [], then compare how downstream nodes are designed to handle empty input. Observe whether downstream follows the empty-input branch. Do not claim that a fictional rules retrieval necessarily returns [], and do not guarantee a first hit or full recall.

All three checks use the sample source text, the proposed sentence, and the request as inputs. The comparison objects are the fields stated in the materials and the behaviour of the workflow nodes. A condition is met when the observed fields match or the branch executes as described. Parts not observed remain unknown.
