# Seller ratings management: HTTP integrations for after-sales questions

## What the documents look like

Seller ratings maintenance tracks consumer feedback that arrives after fulfillment and after-sales service are complete. It does not set promotion prices. The typical data sources are platform experience scores, marketplace service indicators, after-sales review records, and customer service systems. The working documents are negative-review handling records, experience score breakdowns, service diagnostic reports, and rectification ledgers. These materials update daily or weekly, while the HTTP step is checked per request; nothing in the supplied documents supports inferring batch synchronization or real-time triggering from that cadence.

In the order fulfillment and after-sales question scenario, an HTTP call carries fields such as order number, after-sales status, and evidence link to an external system. These values come from upstream node outputs or global variables. The HTTP module itself does not decide whether an after-sales claim is valid, and it does not change order status.

A hypothetical drill sample is used below for illustration only. A store operator on 10 June 2025 reviews a negative-review handling record reading: "Order A was signed for on 3 June; the buyer submitted an after-sales request on 5 June; customer service added an evidence link on 6 June; the current after-sales status is pending review." A proposed handoff request reads: "Please use the HTTP interface to update this order's after-sales status to completed and synchronize it to the external system." This request involves a status change and external synchronization. The HTTP module documentation does not state that such business actions are performed automatically by the module.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a given address. Params, Headers, Body, and URL can all reference variables through `{{}}`. Variables come from global variables, system variables, and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. chatId and responseChatItemId do not exist in test mode. Return values are extracted through JSON path; when the output type is set to string, the value at the corresponding key is converted to a JSON string.

The chat interface uses APIKey authentication and recommends passing body.appId in the request body; it also supports `Authorization: Bearer <apiKey>-<appId>`. The model and temperature parameters passed in are ineffective because the orchestration decides them. With detail=true the interface returns intermediate values, and in stream mode these are distinguished through event. An interactive node returns interactive containing only type and params; internal runtime fields such as entryNodeIds, memoryEdges, nodeOutputs, and nodeResponseId are not returned.

For the drill sample, the record shows the after-sales status as pending review, while the proposed request asks to set it to completed and to synchronize externally. The supplied HTTP documentation describes sending a request and parsing a response. It does not describe a status-change rule, an approval step, or a downstream synchronization result.

## Three common errors

1. Treating a pending-review status as completed. In the sample, the after-sales status is pending review while the proposed handoff request asks to set it to completed. Compare the status field in the source text with the target value in the request; where the two do not match, the request lacks support.
2. Treating an evidence link as proof that the after-sales claim is established. In the sample, customer service added an evidence link on 6 June, and the source text does not state that the evidence passed review. Compare whether the source text records a review conclusion; where it does not, the link does not constitute evidence that the claim is established.
3. Treating the HTTP call as a completed external synchronization. The sample request asks to synchronize to an external system, while the interface documentation only describes sending a request and parsing the return value. Compare the requested action with the documented scope; the part beyond that scope remains unknown.

## How to verify the setup

1. Input the sample source text and the proposed handoff request, and compare the after-sales status field in the source with the target value in the request. When the source says pending review and the request says completed, record the result as unsupported and log the evidence gap.
2. Input the sample source text and compare whether it records a review conclusion for the evidence. When the source only says an evidence link was added and does not say review passed, record the result as pending verification, not as a negative finding.
3. Input the sample request and the interface documentation, and compare whether the requested action falls within the documented scope. When the documentation only describes sending a request and parsing a return value, external synchronization is a business action requiring a separate system implementation and is not treated as executed.

The items above are paper comparisons for the drill sample. No test, deployment, approval, status change, or synchronization is claimed to have occurred. Fields not provided in the source text, such as a review conclusion or a synchronization result, remain unknown.
