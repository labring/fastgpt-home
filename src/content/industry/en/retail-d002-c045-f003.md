# Seller ratings management: shared access for after-sales questions

## What the documents look like

Ratings maintenance draws on consumer feedback that arrives after after-sales fulfilment. It does not set campaign prices the way promotional registration does. Typical source material includes store experience score details, platform service indicators, after-sales review records, and customer service system records. These update on a daily or weekly rhythm. The working documents in this category are poor-review handling records, experience score breakdowns, service diagnostic reports, and rectification ledgers. A shared access step hands the entry point for these documents to a customer service supervisor or quality inspector. The entry point resolves an access path only. It does not establish whether a document has been verified or whether a rectification action has been authorized.

## Constraints at the shared access step

The no-login window is created under the publishing channel, and the system generates a complete link. The link identifier serves access and does not act as business authorization. Expiry time and QPM are set for the intended scope and checked against the actual edition; QPM is the maximum number of visits per user per minute. The points cap constrains usage and cost attribution for the shared entry, and some parameters are edition-limited. Identity verification is limited to the commercial edition and is judged by the official interface returning success and uid. The anonymous local identifier depends on the same device and same browser. Cloud retrieval allows only the most recent 30 days and 20 records. Cross-device records require separately designed identity and session management.

Hypothetical drill sample. Source text one: "Poor-review handling record: order A-2024-0312, after-sales stage is return received, customer service submitted supplementary evidence on 14 March, status is pending quality inspection review." Source text two: "Experience score breakdown: 12 March to 14 March, this store's service indicator is below its own weekly average, cause field is empty." Proposed handover request: "Please pass these two documents to the quality inspector through the share link, and after the pre-conversation verification interface passes, directly trigger a write to the rectification ledger." In this request the material status is pending review, and the ledger write is a downstream business action. The share link and the verification interface do not carry out that action.

## Three common errors

1. Treating the share link identifier as rectification authorization. The link provides access only. While the material status is pending quality inspection review, writing to the rectification ledger requires a separate system implementation; the link and the verification interface do not perform that action.

2. Treating the success returned by identity verification as business approval. Verification only decides whether the user may continue. In the sample, the pending-review status does not become approved because verification passed.

3. Treating the anonymous local identifier as a cross-device identity. If the sample handover moves to another device, the most recent 30 days and 20 records boundary applies, and cross-device identity and session management must be designed separately.

Corresponding checks. First, input the share link and the ledger write request, compare the link's permission scope with the write action, and observe whether the write is executed by a downstream system. Second, input the verification interface response and the material status field, compare success with pending review, and observe whether the status remains pending review. Third, input the local identifier and device information, compare the same-device same-browser condition, and observe whether records can be retrieved.

## How to verify the setup

- Check one. Input source text one and the proposed handover request. Compare the material status "pending quality inspection review" with the request's "directly trigger a write to the rectification ledger." The condition is met only when the write is carried by an explicit downstream implementation and the link and verification interface do not carry that action.

- Check two. Input the success and uid returned by the identity verification interface. Compare whether the uid format excludes vertical bar and slashes and stays within 255 bytes, and compare whether success is true. Only when both hold is the user allowed to continue, and the material status remains pending review.

- Check three. Input source text two and an empty-result handling design. Compare whether, when the cause field is empty, the downstream treats it as a recorded gap. The condition is met only when the downstream design explicitly records the gap and does not fabricate a cause. Retrieval checks observe the actual return and the failure branch only; they do not guarantee a first-hit result or that an unrelated query returns empty. Libraries across different vector models cannot be associated together; check the identifier first, exclude those that do not match, and record the actual observation.

This page covers only the shared access step for order fulfilment and after-sales question handling in seller ratings and experience score maintenance. When operations hands over material, the authorization state of each document, action, and request must be kept distinct. Retrieval and forms do not act as authorization.
