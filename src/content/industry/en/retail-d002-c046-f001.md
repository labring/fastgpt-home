# Marketplace category access: HTTP integrations for after-sales questions

## What the documents look like

Category access happens before listing and before store onboarding, so the review object is the entity qualification and the authorization chain itself. A business license identifies the operating entity, a trademark registration certificate identifies ownership of the right, a brand authorization chain identifies the step-by-step permission from the rights holder to the onboarding entity, and an industry license identifies the qualification to operate a specific category. These materials update irregularly and are collected again at each onboarding.

In order fulfillment and after-sales question handling, problems usually come from a mismatch between qualification status and records held in external systems. The admission requirements shown on a merchant recruitment page, the registration status in a public disclosure system, and the valid scope in a license system can sit at different stages. The HTTP module's role at this step is to retrieve query results from external systems for manual comparison. The retrieval action itself changes no qualification status.

## Constraints at the HTTP integrations step

The HTTP module sends a request. Params, Body, Headers and the URL can reference variables with `{{}}`, and those variables come from global variables, system variables, or outputs of preceding nodes. The response is extracted by JSON path syntax, and when the output type is set to string, the value at the corresponding key is converted to a JSON string. The documented system variables include appId, chatId, responseChatItemId, variables, cTime and histories; chatId and responseChatItemId do not exist in test mode. Fields of an external qualification interface follow that interface's own contract.

The documented rules of the FastGPT chat API, including how model and temperature parameters are ignored, how detail controls intermediate values, and how authProxy works, apply to that API. They do not become parameters of an external query interface. A retrieval relevance score reflects textual relatedness and does not replace verification of an entity or of a permission.

Hypothetical paper test case: an onboarding specialist needs to check one authorization document inside an order fulfillment and after-sales question flow. The supplied text of the authorization document reads: "Authorizing party: XX Brand Management Co., Ltd.; authorized party: XX Trading Co., Ltd.; authorized brand: XX; authorized category: household appliances; authorization period: January 1, 2024 to December 31, 2026; this authorization takes effect on the date both parties affix their seals." The supplied text of the business license reads: "Name: XX Trading Co., Ltd.; unified social credit code: omitted; registration status: in existence; business scope: sale of household appliances." The draft sentence to be assessed reads: "This store has obtained complete authorization for the household appliance category and can be listed directly." The information needed for the assessment includes whether the authorization chain is complete at every level, whether the authorized party name matches the business license entity, and whether the authorization period covers the planned listing period.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason for the choice and comparison object |
| --- | --- | --- |
| Request URL | External system query interface address, referenced through a variable | The address is set by the external interface document; the comparison object is the formal address given in that document |
| Request method | Selected according to the external interface document | Compared item by item against the method stated in the document; when the method does not match, the request result is unknown |
| Headers authentication | Credential injected through secure configuration | The credential is not written into a public sample; the comparison object is whether authentication takes effect |
| Body structure | JSON built according to the external interface contract | Field names and types compared item by item; string references require quotation marks |
| Return value parsing | Target field extracted by JSON path | The comparison object is the actual field path in the response |
| Output type | String | String is chosen when prompt text is assembled downstream; the comparison object is the input format of the downstream node |

## Three common errors

1. Treating retrieved material content as a conclusion that the qualification has been approved. The input is the field value returned by the HTTP module, the comparison object is the entity, object, status and valid scope in the source text, and the observable result is whether the draft sentence exceeds what the source text supports. In the sample the authorization period ends December 31, 2026; if the planned listing period extends beyond that date, the draft sentence lacks support.

2. Inferring a debug mode or a business fault from an external response that lacks chatId or responseChatItemId. The HTTP node's running mode and the system variables it can reference are checked directly, and the supplier response is checked separately against its own contract. Conversation variables are not fields that this interface must return.

3. Using a similarity score to infer qualification ownership. The input is the score field returned by retrieval, the comparison object is the authorized party name in the source text, and the observable result is whether a high or low score is taken as evidence of entity identity. The score reflects textual relatedness only; whether the entity matches still requires comparison against the source text.

## How to verify the setup

1. Take the two source texts and the draft sentence, and check the entity name, the authorization chain, the planned listing period, and the fact of both parties' seals. The names correspond in the sample, but the complete authorization chain, the listing period, the completion of sealing, and the platform listing basis are not given. The claims "complete authorization" and "can be listed directly" remain pending verification and are not released on the strength of the period and the name alone.

2. At actual runtime, record separately the node context, variable source and external response of test calls and production calls. Check against the documentation that the two identity variables do not exist in test mode. Whether an external response contains a field of the same name is decided by the interface contract and cannot confirm a running mode or a business result.

3. If the flow also connects to knowledge base retrieval, check its relevance score and the authorized party name in the source text separately, and do not substitute the score for the entity comparison. Whether an external qualification interface has a score field and what it means still requires the real contract and is not presupposed here.
