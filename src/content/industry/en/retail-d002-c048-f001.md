# Parcel labels and handoffs: HTTP integrations for after-sales questions

## What the documents look like

Parcel handoff happens at the point where a package leaves the warehouse, and responsibility turns on the carrier's scan record. The working materials for this category are the electronic waybill, the handoff list, the pickup scan record, and the exception parcel register. These materials update per batch and per day. After-sales answers must align them with the request records of external systems.

The handoff list records the handoff action. The pickup scan record reflects the carrier's responsibility node. These are different fields, and the handoff list alone does not carry scan status. When a customer asks whether a parcel was collected, the answer depends on the scan record for the same subject and the same batch, not on the handoff list count.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a specified address. Params carries path request parameters, Headers carries request headers, and Body carries the request body. The URL and all three data sections can reference variables through `{{}}`. Variables come from global variables, system variables, and upstream node outputs. Return values are extracted with JSON path syntax. When the output type is set to string, the value at the corresponding key is converted to a JSON string.

The chat completions interface uses APIKey authentication. When calling `chat/completions`, passing `body.appId` in the request body is recommended. The form `Authorization: Bearer <apiKey>-<appId>` is also supported, and in that case `body.appId` is not needed. When `chatId` is empty, the platform context is not used and the full messages array builds the context. When `chatId` is a non-empty string, the platform retrieves the session from its database and uses the last item in the messages array as the user question. `chatId` and `responseChatItemId` do not exist in test mode. The `model` and `temperature` parameters passed in do not take effect; these are determined by the orchestration. When `detail` is true, intermediate values are available in `responseData`.

Hypothetical paper exercise: on 11 March 2025, a warehouse shipping group hands off a batch of parcels. The handoff list states "12 parcels, carrier branch arrived on site." The pickup scan record shows "9 parcels scanned." The exception parcel register states "3 parcels pending investigation." The proposed sentence under review is: "All 12 parcels in this batch have been collected by the carrier." Judging this sentence requires scan records for the same subject and the same batch. The available materials support only 9 parcels scanned; 3 parcels remain pending verification.

## Configuration and implementation checks

| Configuration item | Purpose on this page | Verification method |
| --- | --- | --- |
| Request address and method | Query the carrier pickup interface | Select per the external interface document; the address can reference variables |
| Headers | Carry authentication credentials | Credentials injected through secure configuration, not written into public samples |
| Body | Submit batch query conditions | Effective only under the corresponding request type; check the JSON structure |
| Variable reference | Pass batch number and date | Check each actually passed value against the source |
| Return value extraction | Obtain scanned count and status | Configure the key per JSON path |
| Output type | Determine return value format | Selecting string converts the value to a JSON string |

The starting value for the batch query is the batch number recorded on the handoff list for 11 March 2025. This value is chosen because it is the only batch identifier present in the supplied materials, and it is compared against the batch identifier in the scan record and the exception register. No default value, limit, or unit is assigned beyond what the external interface document states.

## Three common errors

1. Treating the 12 parcels on the handoff list as the collected count. The handoff list records the handoff action only. The scan record reflects the carrier responsibility node, and the two carry different fields. The proposed sentence "all 12 parcels have been collected" is not supported by a scan record showing 12 scans.

2. Treating an empty `chatId` in test mode as a business failure. The field does not exist in test mode, which is documented behavior. An absent field in a test-mode request is not evidence of a fault in the business flow.

3. Treating a successful HTTP response as proof that the external system has written a business result. A returned response indicates the interface responded. Database writes and external synchronization require their own downstream implementation, and a response alone does not confirm them.

Corresponding checks:

- Compare the handoff list parcel count with the scan record parcel count. The statement of full collection is supported only when the two counts match for the same batch.
- Compare the running mode with whether the field exists. In test mode, an absent `chatId` matches the documented behavior and is not an anomaly.
- Compare the interface response with the business system record. When a response exists but the record is missing, the business result remains pending verification.

## How to verify the setup

- Verification one: input the handoff list and scan record from the hypothetical sample. Compare 12 parcels with 9 parcels. The proposed sentence "all collected" is not supported and must be revised to 9 parcels scanned with 3 parcels pending verification. The comparison is between the same batch identifier and the same parcel count field.

- Verification two: input a test-mode request. Compare whether `chatId` exists. The absent field matches the documented behavior, and the case is not judged a failure. The comparison is between the running mode and field presence, with the observable result being absence in test mode.

- Verification three: input the scanned parcel count returned by the interface and compare it with the handoff list parcel count. When the two are equal, the batch scan count is consistent. When the returned value is an empty array, the downstream design handles the empty result as an empty result, and no inference of full collection is made. The comparison is between the returned count and the handoff list count, and the observable result is either equality or an empty array.

These are paper checks. No actual request was executed, no carrier system return value was obtained, and no business write or synchronization occurred. The relevance score of a retrieval result is not a category, entity, or permission filter, and retrieval is not authorization. Forms collect values; business verification, approval, database writes, and external synchronization each require their stated downstream implementation.
