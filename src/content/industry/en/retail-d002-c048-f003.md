# Parcel labels and handoffs: shared access for after-sales questions

## What the documents look like

Handoff to the carrier happens at the point where parcels leave the warehouse, and responsibility turns on carrier scan events. The working documents are electronic waybills, handoff manifests, pickup scan records and exception-parcel logs. These update per batch and per day. In order fulfilment and after-sales answering, the practical question is which fields carry business authorization and which are only values collected by a link or a form. A share link's `shareId` and `authToken` are entry identifiers and identity credentials; they do not release a handoff or confirm a pickup. The status fields in pickup scan records and exception-parcel logs are the inputs used to check what actually happened.

## Constraints at the shared access step

The no-login window is created from the publishing channel and the system-generated full link is copied. The link identifier is not business authorization. Identity verification uses a `POST` root address; initialization, conversation start and conversation end each call the corresponding interface, and the response returns only `success` and `uid`. The `uid` is a string that excludes `|`, `/` and `\` and does not exceed 255 bytes. Conversation records depend on a localId tied to the same device and same browser, and the cloud allows pulling only the most recent 20 records within 30 days. Expiration time, QPM, points cap and identity verification are subject to version scope.

Hypothetical drill sample: a warehouse shipping group and a carrier outlet agree on batch A, 40 parcels, dated 10 March 2025. The handoff manifest reads: "Batch A, 40 parcels, handed to the outlet on 2025-03-10; scan status: 32 parcels picked up, 8 exception parcels, exception reason pending carrier confirmation." A drafted sentence reads: "Batch A has been fully picked up, so after-sales may answer customers as picked up." The material states 32 parcels picked up and 8 pending, so the "fully picked up" wording is not supported.

## Configuration and implementation checks

| Configuration item | Role on this page | How to check |
| --- | --- | --- |
| No-login window link | Share entry; `shareId` identifies the link | Copy the full link from the publishing channel |
| Expiration time | Limits the period the link is usable | Confirm against the actual version whether it can be set |
| QPM | Maximum visits per user per minute | Confirm against the actual version whether it can be set |
| Points cap | Cost ceiling generated by this link | Check which team bears the cost |
| Identity verification root address | Initialization, start and finish requests | Enter the root address only, without a path |
| `authToken` | Credential appended to the share link | Generated by the business system, then appended |

Hypothetical starting value for this drill: QPM set to 30, because the warehouse shipping group's routine enquiry concurrency sits below that figure; the comparison object is the observed number of requests per minute. This value is a hypothetical starting point for this drill, not an official default.

## Three common errors

1. Treating `shareId` or `authToken` as authorization to release a handoff. The input is the share link parameters; the comparison object is the scan status field in the handoff manifest; the observable result is that the link opens while the manifest still shows 8 exception parcels.
2. Treating the drafted sentence "fully picked up" as a verified fact. The input is the drafted sentence and the handoff manifest text; the comparison is "fully" against "32 parcels picked up, 8 pending"; the observable result is a quantity mismatch, so the sentence is not supported.
3. Treating identity verification `success` as completed business approval. The input is the authentication interface response; the comparison object is the authorization signature field in the handoff manifest; the observable result is successful authentication with no signature record in the manifest, so the authorization state remains unverified.

## How to verify the setup

1. Input the hypothetical handoff manifest text and the drafted sentence; compare "fully picked up" against "32 parcels picked up, 8 pending"; the observable result is that the drafted sentence does not match the manifest quantities, so it is judged unsupported.
2. Input the share link and `authToken`; compare the `uid` returned by the authentication interface against the authorized-party field in the handoff manifest; the observable result is that a `uid` exists while the manifest holds no corresponding authorization record, so authorization remains unverified.
3. Input an empty reference list `[]`; compare how the downstream design handles an empty result; the observable result is that downstream takes the empty-input branch, without asserting that retrieval necessarily returns `[]`.

The conversation-end reporting interface is optional; `responseData` contains `totalPoints` and `token`, and its business handling requires a separate system implementation. Retrieval and relevance scores do not carry permission or entity isolation. Libraries using different vector models cannot be associated together; check identifiers first, exclude those that do not match, and record the actual observation.
