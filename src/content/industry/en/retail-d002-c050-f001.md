# Complaints and official replies: HTTP integrations for after-sales questions

## What the documents look like

Complaints and official replies follow formal procedures run by a platform or a regulator. The working materials are complaint tickets, regulatory inquiry letters, order evidence, and rectification reports. Data arrives from the 12315 platform, platform complaint centers, customer service chat, and order systems. Compared with after-sales repair and reshipment work, this category must produce submittable formal evidence and rectification text, so the subject, object, time scope, and authorization status of each document need item-by-item checking. Records update per case; the update rhythm does not act as a trigger for the feature on this page.

A regulatory inquiry letter defines what must be answered, for which order, over which period, and by which deadline. An order system record defines the actual fulfillment state of that order. A rectification report states what the seller commits to change. These three document types carry different subjects and different evidentiary weight, and a draft handover sentence gains support only when it matches the document it claims to describe.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a specified address. Params, Headers, and Body carry path request parameters, request headers, and request body respectively, and all three can reference variables through `{{}}`. The URL can also reference variables. Variables come from global variables, system variables, and outputs of preceding nodes. Return values are extracted with JSON path syntax; when the output type is set to string, the value for the corresponding key is converted into a JSON string.

Among the system variables, chatId and responseChatItemId do not exist in test mode. A missing value during debugging is a documented test-mode condition. When calling `chat/completions`, the documented recommendation is to pass `body.appId` in the request body. To proxy a team member identity through `authProxy`, the team owner must enable `authProxy` when creating or editing that key, and the proxied identity still needs permission on the target app and conversation. Passed-in fields such as `model` and `temperature` have no effect; these are determined by the orchestration. Retrieval and similarity settings do not carry permission or entity filtering duties, and retrieval does not itself constitute authorization.

Hypothetical paper exercise: a shop customer service group receives a regulatory inquiry letter stating, "Please provide a written explanation and evidence materials regarding the refund handling of Order A on March 12, 2025, to be submitted before April 5, 2025," signed by a market supervision office. The order system record shows the refund request for that order was submitted on March 13, 2025, with status pending review. Customer service plans to submit a handover request to an internal ticket service through the HTTP module, with the draft sentence "Order A refund is complete and can be submitted for the regulatory reply." This draft sentence disagrees with both the letter and the order record: the letter asks for a written explanation and evidence, and the order record shows pending review. Neither supports "refund is complete."

## Three common errors

1. Writing the draft sentence into the handover request as fact. In the sample the draft says "refund is complete," while the order record status is pending review. The two take different values on the same field, which constitutes a contradiction. Pending review does not indicate approval, and it does not indicate a lack of operating permission.
2. Treating a retrieval or similarity result as an authorization basis. A retrieval returning a related record only describes the degree of match. It does not constitute permission on the target app or conversation, and it does not constitute authorization to submit regulatory materials.
3. Treating an empty value in test mode as a business fault. chatId and responseChatItemId do not exist in test mode, which is a documented condition, and no external system anomaly can be inferred from it.

## How to verify the setup

1. Input the sample letter text and the order record text, then compare whether "refund is complete" in the draft sentence and "pending review" in the order record take mutually exclusive values on the same order and the same field. If the two are mutually exclusive, the draft sentence is judged unsupported and must be rewritten to match the record.
2. Input a Headers configuration referencing `{{appId}}` and the authentication field declared in the interface document, then compare whether the field name and value format match. If the field name or format does not match, the authentication configuration is judged pending correction; if the document does not state it, record it as an evidence gap.
3. Input a request in test mode that does not contain chatId, and observe whether that field is absent from the return value. If absent, this matches the documented test-mode condition. If it is still absent in a formal call, record the actual observation and check the call parameters, without inferring a specific error cause.
