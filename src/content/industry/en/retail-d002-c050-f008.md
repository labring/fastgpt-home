# Complaints and official replies: workflow routing for after-sales questions

## What the documents look like

Complaints and official replies are addressed to a platform or a regulator, and they require formal evidence and remediation text. The main data sources are the 12315 platform, platform complaint centers, customer service chat, and the order system. The recurring documents are complaint tickets, regulatory inquiry letters, order evidence, and remediation reports. The most time-consuming steps are reconstructing the transaction, preparing the evidence package, and submitting the remediation reply. The supplied brief gives the update frequency as irregular and per case; this page does not derive batch synchronization or transaction-triggered mechanisms from that fact.

For workflow routing, these characteristics matter in a specific way. A form input node and a user selection node operate in an interaction state, where the conversation pauses and the workflow state is recorded until the user completes the interaction. Whatever the form collects is passed to later nodes; whatever the user selects drives a branch. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval and form collection do not constitute authorization to execute a business action.

## Constraints at the workflow routing step

When the form input node triggers, the conversation enters the interaction state and the workflow state is recorded. After the user fills the required information and submits, the node collects that information and passes it to subsequent nodes. When the user selection node triggers, the conversation also enters the interaction state. After the user makes a choice, the node evaluates the choice and executes the corresponding "yes" branch. Interaction waiting, state recording, and hiding the dialog follow the documented behavior; no separate global state-recording switch is assumed.

Information collected in a form must be explicitly passed to a later retrieval, decision, or interface node, and the output must be compared item by item against the input. Semantic recall and relevance scores do not perform permission or entity isolation. The requirement that a retrieval library use the same vector model cannot be extended to claim that a regulatory website or another external system must use the same model. Libraries built on different vector models cannot be associated together; check the identifiers first, exclude those that do not match, and record what is actually observed. The optional paths shown in the overall workflow diagram do not mean every request executes all of them. Image retrieval requires a corresponding image input and model capability, and reranking requires a model enabled according to its settings.

Hypothetical paper exercise sample: a shop customer service supervisor receives a ticket whose source text reads: "The complainant placed an order on 12 March 2025, order number H-2025-0312, product a vacuum flask, signed for on 15 March 2025; the complainant states the lid is cracked and requests a refund; the shop replied on 16 March 2025, 'logged, pending verification'." A proposed handover request is "mark this ticket as refunded and synchronize it to the regulatory reply ledger." The source text states the subject, object, status, and effective scope: the signing date, the complaint demand, and the shop reply status are all present. Whether the refund was completed is not stated.

## Three common errors

1. Treating form collection as authorized execution. Input: the ticket source text above. Comparison: the shop reply "logged, pending verification" against the proposed handover request "mark as refunded". Observable result: where evidence of a completed refund is absent, the handover request cannot be treated as executed.
2. Treating retrieval relevance as a permission or entity filter. Input: a retrieval request for ticket number H-2025-0312. Comparison: the retrieval output against the complainant identity field. Observable result: the retrieval result does not exclude unrelated business or unauthorized records because of a similarity setting.
3. Associating libraries across different vector models directly. Input: two library identifiers with different vector models. Comparison: the library identifiers and the model identifiers. Observable result: mismatched identifiers are excluded and recorded, and no cross-model retrieval is run to compare missed recall.

## How to verify the setup

1. For the hypothetical sample's proposed sentence "mark this ticket as refunded and synchronize it to the regulatory reply ledger", input the ticket source text and the proposed sentence. Compare whether "logged, pending verification" and "refunded" share the same subject, the same period, and the same field. Observable result: the refund status is not stated, so the determination is pending verification, and this does not constitute a denial or a conflict.
2. For empty-result handling, input the paper input []. Compare whether the downstream node design has an explicit path for an empty result. Observable result: the downstream design states how an empty result is handled; no claim is made that a fabricated-rule retrieval returns [].
3. For the user selection branch, input the "is the evidence complete" choice. Compare the choice result against the yes-branch connection. Observable result: after the choice, the corresponding yes branch executes, and the branch connections are checked one by one. All of the above are paper checks; no deployment or submission has taken place.
