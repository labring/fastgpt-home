# Douyin storefront operations: HTTP integrations for after-sales questions

## What the documents look like

Shelf operations for a Douyin storefront run on a small set of recurring materials: product qualification pages, experience score details, shipping violation appeals, and store announcements. These materials update daily or per order, and the order fulfilment and after-sales question task depends on moving fields such as shipping status, out-of-stock records, and appeal progress from those materials into external system requests. Compared with live-room operations, shelf operations do not depend on a single broadcast rhythm and pay closer attention to product cards and store experience scores. When field names, status values, or external interface contracts disagree, the request body parses into a result that differs from the material. Experience score details and shipping violation appeals are separate documents, so their field definitions require separate checks.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a corresponding address, and its operation is close to Postman and ApiFox. Params carry path request parameters and appear mostly in GET requests. Body carries the request body and appears mostly in POST and PUT requests. Headers carry special information. All three data types can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and upstream node outputs.

System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. The chatId and responseChatItemId values do not exist in test mode, and histories takes at most 10 entries by default with a length that cannot be modified. A return value configuration does not represent the interface return value; it represents how to parse the interface return value, using JSON path syntax to extract values from the response. When the output type is set to string, the value of the corresponding HTTP key is converted into a JSON string.

The chat interface uses APIKey authentication. When calling chat/completions, passing body.appId in the request body is recommended. The appId priority order is body.appId, then `<apiKey>-<appId>`, then the appId associated with the apikey. Passed fields such as model and temperature have no effect, because the orchestration decides them. With detail=true, intermediate values are returned, and in non-stream mode the result is stored in responseData.

Hypothetical paper sample: a Douyin storefront operator prepares an order fulfilment request for handover. The material text reads: "Order A-2024-0315-07, item is a summer short-sleeve shirt, order date 15 March 2024, current status is shipped, logistics tracking number not returned. The store announcement states that out-of-stock items require an appeal filed within 48 hours." The proposed handover request is: send a POST request to the external system, with Body containing `{"orderId":"A-2024-0315-07","status":"shipped"}` , and Headers carrying Authorization as Bearer plus a credential. The question to decide is whether the status value in the request matches the material text, and whether the missing logistics tracking number is a field the material does not state.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this trial | Reason for the choice and comparison method |
| --- | --- | --- |
| Request address | Filled per the external interface document, without referencing variables not provided | Compare the path and method word by word against the external interface contract |
| Params | This sample does not involve path parameters | Check whether the GET request needs them; record a gap when absent |
| Headers | Authorization uses Bearer plus a credential | The credential is injected through secure configuration and not written into a public sample |
| Body | `{"orderId":"A-2024-0315-07","status":"shipped"}`  | Compare field by field against the material text; the status value must match |
| Variable reference | No reference to global variables that were not provided | Check each actual passed value; keep the gap when a value is absent |
| Return value extraction | Configure the key by JSON path | Compare against the interface response structure without presuming a hit |

The hypothetical starting point for this trial only explains the checking method and does not represent an official default value. The reason for the numeric choice is to allow field-by-field comparison, and the comparison object is the material text against the external interface contract.

## Three common errors

1. Treating an empty chatId in debug mode as a business fault. Input is a test-mode request; the comparison object is the documented statement that chatId does not exist in test mode; the observable result is that an empty chatId field is expected behaviour.
2. Omitting quotation marks around a string variable in Body. Input is the two forms `"{{string}}"` and `{{string}}`; the comparison object is the documentation note that a string requires `""`; the observable result is whether the parsed type matches the expectation.
3. Treating the return value configuration as the interface return value itself. Input is a JSON path extraction configuration; the comparison object is the documentation statement that the return value represents how to parse the interface return value; the observable result is whether the extracted result corresponds to the response structure.

## How to verify the setup

1. Input the hypothetical sample material text and the proposed handover request, compare the status value against the material text "shipped" (English rendering), and observe that the field passes the check when the two match.
2. Input the case in the hypothetical sample where the logistics tracking number is missing, compare whether the material text states a logistics tracking number, and observe that when the material does not state it, the item is recorded as an evidence gap rather than judged as a fault.
3. Input the Body string field from the hypothetical sample, compare whether quotation marks are added as the documentation requires, and observe that the writing passes the check when the parsed type matches the expectation.

The checks above are paper-based reasoning and do not indicate that testing, deployment, or authorization has occurred. A pending review does not demonstrate a lack of operating permission, and fields not stated in the material remain unknown.
