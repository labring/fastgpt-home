# Pinduoduo seller campaigns: workflow routing for after-sales questions

## What the documents look like

Pinduoduo low-price campaign store operations revolve around campaign resource slots, campaign inventory, and refund-rate fluctuation. The working materials are the campaign registration form, the product cost calculation sheet, the after-sales refund form, and platform in-site messages. Supporting data comes from the merchant backend, campaign resource-slot data, ERP inventory, and logistics signed-receipt data. Campaigns run by session, and materials are refreshed daily or per campaign. The order fulfillment and after-sales question-answering task has to link the registration form, the cost sheet, the refund form, and the in-site messages so that a person can tell what state a given order or after-sales request is in, who handles it, and whether execution has been authorized. The refresh frequency does not change this page's function; it only affects which version of a material is used during checking.

## Constraints at the workflow routing step

In the Form Input node, triggering the node moves the conversation into an interaction state and records the workflow state. After the user fills in the required information and submits, the node collects the submitted form values and passes them to subsequent nodes. The User Selection node behaves the same way at trigger time; when the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. The interaction state and the state record are behaviors of the interaction nodes. No separate global state-recording switch is documented. Collected information must be explicitly passed to later retrieval, judgment, or interface nodes, and outputs must be compared item by item against inputs. Order writes, document backfill, and external state synchronization require a separate business interface or a later process. Retrieval and forms do not by themselves constitute authorized execution.

Hypothetical paper exercise. A campaign operator submits an after-sales handover request. The source material consists of three sentences. "The campaign registration form (hypothetical identifier HD-001) states that the campaign product is item A and the campaign period is the hypothetical 1 March to 3 March. The product cost calculation sheet (hypothetical identifier CB-001) states that the unit cost of item A is a hypothetical 12 yuan and the campaign price is a hypothetical 15 yuan. The after-sales refund form (hypothetical identifier TK-001) states that the buyer applied for a refund on an item A order, the refund reason is 'size mismatch', and the current status is 'awaiting merchant handling'." The draft sentence to be judged is: "TK-001 has been approved for refund, and the workflow can directly execute the refund and backfill the document." That sentence treats a pending status as an approval and has the workflow directly execute the refund and the backfill, exceeding the status in the material and the capability of the nodes.

## Configuration and implementation checks

| Configuration item | Value or check on this page | Basis and boundary |
| --- | --- | --- |
| Form Input node | Collect after-sales ticket number, order number, refund reason, buyer request | Official document: triggers into interaction state, passes submitted values to later nodes |
| User Selection node | Set "continue verification" and "route to human" options, check the "yes" branch connection | Official document: executes the corresponding "yes" branch after the user chooses |
| Interaction state check | Check that the conversation enters the interaction state and records the workflow state after trigger | Official document: interaction node behavior; no separate global state-recording switch |
| Output handoff check | Compare collected information item by item against the inputs of later retrieval, judgment, or interface nodes | Official document: information is passed to later nodes for use |
| External action split | Mark refund execution, document backfill, and external state synchronization as requiring a separate business interface | Official document: external actions require a separate interface or later process |
| Hypothetical trial starting value | Set "awaiting merchant handling" as the starting state for this hypothetical check, compared with "approved" | Hypothetical trial starting value on this page, not an official default |

## Three common errors

1. Reading the "awaiting merchant handling" status of TK-001 as "refund approved". The input is the TK-001 source text, the comparison field is the current refund status, and the observable result is that the draft sentence does not match the source status; the sentence is unsupported.
2. Having the workflow directly execute the refund and backfill the document. The input is the execution action in the draft sentence, the comparison is node capability against the external action split, and the observable result is that refund execution and document backfill lack a corresponding interface description and are business actions that require a separate system.
3. Using a retrieval or form result in place of an authorization judgment. The input is the after-sales information collected by the form, the comparison is against the source of authorization, and the observable result is that the form only collects values and produces no approval or execution authority; the authorization state remains to be verified.

## How to verify the setup

1. Take the TK-001 source text as input and compare the draft sentence "TK-001 has been approved for refund" against the source text "the current status is 'awaiting merchant handling'". If the two status fields do not match, the draft sentence is unsupported and the evidence gap is retained.
2. Take the draft sentence "the workflow can directly execute the refund and backfill the document" as input and compare node output handoff against the external action split. If refund execution and document backfill have no corresponding interface description, the action requires a separate system implementation and is not treated as executed.
3. Take the after-sales information collected by the Form Input node as input and compare it against the source of authorization. If the information contains only the ticket number, order number, refund reason, and request, the authorization state remains to be verified, and retrieval and forms do not constitute authorized execution.
