# Channel receivables: conversation logs for after-sales questions

## What the documents look like

Channel receivables collection happens after credit sales. The work centers on credit granting and cash recovery, and the everyday documents are the accounts receivable aging table, dunning letters, credit agreements, and shipment freeze notices. The typical roles are brand finance staff, sales back-office staff, and dealer owners. The data sources are the finance system, bank receipts, dealer orders, and sales contracts. Updates arrive mainly by week and by month; this page does not depend on that cadence for any functional decision.

For the conversation logs and audit step, the relevant records are the session records, run details, and feedback states produced during order fulfillment and after-sales question handling. The conversation interface documents how a session is identified, how run details are requested, and how feedback is recorded. This page covers only that logging and audit step for channel receivables. Reconciliation, retention, and compliance obligations belong to a complete business solution implemented elsewhere; the presence of a log does not mean a compliance audit is complete.

## Constraints at the conversation logs step

Use chatId to match a target conversation against a business record. Sessions created through different entry points should not be counted together. When run details are needed, follow the documented contract by setting detail and then inspect responseData. Compare the log against the fields the interface actually returns; business data that is not returned cannot be treated as fully retained. Identity fields in test mode may differ from those in a live call, so inputs, history, and returned content need separate checks.

Hypothetical paper exercise: a brand finance staff member performs an internal check of order fulfillment and after-sales question records for channel A. The supplied source text has three sentences. First, the credit agreement states that channel A has a credit limit of one batch, valid for the current quarter. Second, the shipment freeze notice states that shipments for this channel are suspended in an over-credit situation, that the notice has been issued, and it does not state a restoration condition. Third, the accounts receivable aging table states that one payment for this channel is in the overdue stage and does not state whether a repayment plan has been confirmed. One draft sentence to be judged reads: "Channel A has completed repayment plan confirmation and the shipment freeze can be lifted." The request is pending review and has not been authorized for execution.

## Configuration and implementation checks

| Configuration item | Relevant setting or check on this page | Relation to the exercise |
| --- | --- | --- |
| appId and chatId | Pass appId when calling the conversation interface; use chatId to locate the session | Match the exercise conversation to channel A |
| detail | Set detail to true when run details are needed | Inspect whether responseData contains the required node information |
| responseChatItemId | When passed, becomes the response message ID for this turn and must be unique under the same chatId | Mark the response tied to the exercise review request |
| variables | An object that replaces [key] in module input fields | Pass checking variables such as the channel identifier |
| source on the session list | source=api returns sessions created through the API | Separate API sessions from page sessions |
| loadCustomFeedbacks | Optional flag when reading the conversation list to load custom feedback | Check whether feedback tied to the exercise is retained |

For this hypothetical exercise, the starting value sets detail to true. The reason is that the exercise needs run details to check node returns. The comparison method is to compare the responseData actually returned by the interface against the required fields. This starting value is an assumption for the exercise, not an official default.

## Three common errors

1. Treating retrieval or a form as authorized execution. The draft sentence says the shipment freeze can be lifted, while the source text only states that the freeze notice has been issued and does not state a restoration condition. No authorization appears. The correct step is to check the authorization state and keep the conclusion pending verification.

2. Counting sessions from different entry points together. If API sessions and page sessions are not separated by chatId, the exercise conversation may be mixed with records for other channels. Check chatId before comparing.

3. Treating the existence of a log as a completed compliance audit. The source text does not state reconciliation or retention requirements. A log's presence does not mean an audit is complete. Record the evidence gap.

## How to verify the setup

1. Input the three source sentences and the draft sentence. Compare whether the claim "has completed repayment plan confirmation" matches the source on the same subject, the same period, and the same field. The source does not state repayment plan confirmation, so the observed result is unsupported and the item should be recorded as pending verification.

2. Input the exercise chatId with detail set to true. Compare whether the responseData returned by the interface contains the required node fields. If a field is missing, the observed result is that it was not returned; record the gap and do not assume the data was retained.

3. Input the exercise feedback check request. Compare the loadCustomFeedbacks result against the feedback state in the exercise. If the return is empty, the observed result is that nothing was read; keep the state unknown and do not claim the feedback does not exist.
