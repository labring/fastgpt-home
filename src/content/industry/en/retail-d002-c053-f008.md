# Channel receivables: workflow routing for after-sales questions

## What the documents look like

Channel receivables collection begins after credit sales. The work centers on credit limits and cash recovery, and the main data sources are the finance system, bank receipts, distributor orders and sales contracts. The documents handled day to day are the receivables aging table, dunning letters, credit agreements and shipping freeze notices. The supplied brief gives weekly and monthly update frequencies.

These features shape workflow routing in a specific way. Order fulfillment status, after-sales question handling and authorization boundaries need to be recorded separately. An aging table shows amounts and periods. A dunning letter shows a communication action. A credit agreement shows a limit and its conditions. A shipping freeze notice shows a restriction on the shipping step. The four document types do not share the same fields, so routing has to check subject, object and effective scope item by item. The status of one document type cannot be applied directly to another.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the workflow continues after the user completes the interaction. The node collects required information the user submits and passes that information to later nodes. The User Selection node is also a user interaction node. It enters the interaction state in the same way, and after the user makes a choice it evaluates that choice and executes the "yes" branch.

The interaction state is recorded by the interaction node itself. The supplied documents do not describe a separate global state-recording switch, so none is assumed. Collected information has to be passed explicitly to later retrieval, decision or interface nodes, and outputs are compared against inputs item by item. Order writes, document backfill and external status synchronization require a separate business interface or a later process. A form does not perform those business actions on its own. Retrieval or form submission does not constitute authorization to execute. During operations handover, the authorization state of each material, action and request has to be distinguished.

Hypothetical drill sample: the source material reads "The aging table for a distributor as of 31 March 2026 shows overdue amount of RMB 800,000; the credit agreement specifies a limit of RMB 1,000,000 and a payment term of 60 days; the shipping freeze notice states that shipping beyond the credit limit is suspended, and this notice has not yet been delivered to the distributor." The draft sentence to be assessed is "The distributor has been stopped from supply; execute the freeze immediately." This sample is used to compare the draft sentence with the source. The source states only that the notice has not been delivered. It does not state that the freeze has been executed, and it does not state that a supply stop has been completed.

## Configuration and implementation checks

| Configuration item | Type | Description |
| --- | --- | --- |
| Form Input node | Official node | Enters the interaction state on trigger, collects required information, passes it to later nodes after submission |
| User Selection node | Official node | Executes the "yes" branch after the user makes a choice; branch connections are verified one by one |
| Interaction state check | Implementation check | State recording is behavior of the interaction node; no separate global state-recording switch is assumed |
| Output handover check | Implementation check | Collected information is passed explicitly to later retrieval, decision or interface nodes, and outputs are compared with inputs item by item |
| External action division | Implementation check | Order writes, document backfill and external status synchronization connect to a separate business interface or later process |
| Hypothetical trial starting value | Hypothetical value | Overdue amount of RMB 800,000 in the aging table, chosen because the sample source states it; compared with the credit limit of RMB 1,000,000 to judge whether the limit is exceeded |

## Three common errors

1. Treating "not yet delivered" in a shipping freeze notice as "freeze executed." Input is the sample source and the draft sentence; comparison is the notice status field; the observable result is whether the draft sentence writes a pending delivery as an executed freeze.
2. Treating an amount collected by a form as the basis for an authorized deduction. Input is the submitted form value and the credit agreement; comparison is the field purpose; the observable result is whether the collected value is used for business execution.
3. Treating a retrieval result as a permission filter result. Input is the retrieval request and the returned records; comparison is the record subject against the request subject; the observable result is whether a similarity result is used to exclude unrelated business records.

## How to verify the setup

1. Input the sample source and the draft sentence. Compare the two expressions "not yet delivered" and "has been stopped from supply." If the draft sentence does not write a pending delivery as an executed freeze, the check condition is met. If it does, record it as unsupported.
2. Input the submitted form value and the credit agreement fields. Compare the amount with the limit and the payment term. If the form value is used only for a later decision node, the condition is met. If it is used directly for a deduction or a freeze execution, record it as use beyond authority.
3. Input the retrieval request and the returned records. Compare the record subject with the request subject. If all returned records fall within the request subject scope, the condition is met. If unrelated subjects appear, record them as requiring manual exclusion. Do not run a cross-model retrieval comparison for missed recall. An empty-result handover can be checked on paper with the explicit input [] against the downstream design, without claiming that a fictional rule retrieval necessarily returns [].
