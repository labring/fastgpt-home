# Franchise filing management: workflow routing for after-sales questions

## What the documents look like

Franchise filing management works on legal disclosure and the commerce department system. It does not handle individual storefront engineering. The documents in daily use are the franchise contract, the operations manual, filing materials, and the information disclosure file. Source records come from the commercial franchise information management system, enterprise licences, the store list, and the contract ledger.

At the order fulfilment and after-sales question stage, workflow routing operates on the check status of these materials and on handover requests. Material updates are irregular or annual. This page does not depend on update frequency, so no synchronization mechanism is described here.

Three facts shape the routing task. The franchise contract, the operations manual, and the disclosure file each carry a different status, and routing decisions depend on which status is current. Filing materials sit with the commerce department system rather than with the store list. Handover requests between headquarters and franchise applicants move through the same interaction nodes that collect form values and branch choices.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. After the user completes the required information and submits, the node collects the form values and passes them to later nodes. The user selection node is also a user interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. When the user makes a choice, the node evaluates the choice and executes the corresponding branch. Both nodes can be added repeatedly and trigger execution.

Retrieval or form collection does not constitute authorization. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Interaction waiting, state recording, and dialog hiding are explained in the documents as node behaviour. No global state switch is set here.

Hypothetical exercise sample: the source text reads, "Party A is a franchisor headquarters, Party B is a franchise applicant; the two parties signed a franchise contract in March 2024, the contract is pending review and has not been signed; the operations manual has been delivered, filing materials have been submitted to the commerce department system, and the information disclosure file has been served on Party B." The draft sentence to be assessed is, "This franchise contract is already effective, so order fulfilment can proceed and after-sales question records can be synchronized." The source text states only pending review and not yet signed. It does not state signing or effectiveness. The draft sentence is not supported.

## Configuration and implementation checks

| Configuration item | Value or check item on this page | Basis and limitation |
|---|---|---|
| Form input node | Collect the fulfilment order number, the after-sales question item, and the material list | Documents state that required information is collected and passed to later nodes |
| User selection node | Branch question is "are the materials complete" | Documents state that the corresponding branch executes according to the choice |
| Interaction state check | Confirm item by item that the interaction state is entered after triggering | Documents state that the workflow state is recorded |
| Output handover check | Pass the form information explicitly to a later retrieval or decision node | Documents state that information is passed to later nodes |
| Retrieval scope check | Confirm that the target library identifier and the vector model identifier match | Libraries across different vector models cannot be associated together |
| External operation division | Order writes, document backfill, and external synchronization connect to separate interfaces | Documents do not state automatic execution inside the node |

Hypothetical trial starting point: set the form required items to three, because the sample involves only three material types, the contract, the manual, and the disclosure file. Compare against the actual material count in the sample and adjust.

## Three common errors

1. Treating form submission as authorized execution. Input is the sample contract pending review. Compare the submission action with the authorization status. The observable result is that no signing or effectiveness record exists after submission.
2. Treating a user selection branch as an approval conclusion. Input is the "are the materials complete" choice. Compare the choice result with the filing acceptance status. The observable result is that the choice does not produce an acceptance fact.
3. Using a relevance score to exclude unrelated parties. Input is a returned retrieval record. Compare the score with the party identifier. The observable result is that the score does not change record ownership.

## How to verify the setup

1. Input the sample source text and the draft sentence. Compare "pending review, not yet signed" with "already effective." The observable result is that the draft sentence is not supported, and the evidence gap must be recorded.
2. Input a paper empty result []. Compare the downstream node handover design. The observable result is that the downstream node does not treat the empty result as already filed.
3. Input two libraries with different vector model identifiers. Compare the identifiers. The observable result is that no joint association is performed; record only the actual observation and exclude the non-matching one.

This page addresses only franchise filing management, order fulfilment and after-sales questions, and workflow routing. During operational handover, which materials, operations, and requests sit at which authorization status cannot be treated as authorized execution through retrieval or a form.
