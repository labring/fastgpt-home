# Producer export tax processes: HTTP integrations for after-sales questions

## What the documents look like

Producer export tax refunds combine domestic sales tax offsets with refund calculations, which means order fulfilment and after-sales question handling must trace back to four material types: the export tax refund declaration detail schedule, export contracts, the sales detail ledger, and export customs declarations. Processing runs on a monthly cycle, and within a single month the export quantity, free-on-board price, and customs declaration number need to stay consistent across certificates and accounts. The HTTP integration at this stage moves order status, customs declaration information, and after-sales question requests between systems. The integration itself does not perform tax calculation and does not replace the declaration.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a specified address. Params carry path request parameters, Body carries the request body for POST and PUT requests, and Headers carry request headers. URL, Body, and Headers can all reference variables through `{{}}`, drawing on global variables, system variables, or upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories; chatId and responseChatItemId do not exist in test mode. Return values are extracted through JSON path, and selecting string as the output type converts the value at the corresponding key into a JSON string. The chat completions interface uses APIKey authentication, with appId priority order of body.appId, the concatenated form in Authorization, then the appId associated with the apikey. Passed model and temperature fields have no effect. Token consumption requires setting detail=true and then manually calculating tokens from responseData. The interactive node returns an interactive object containing only type and params; entryNodeIds, memoryEdges, nodeOutputs, and nodeResponseId are not returned.

Hypothetical paper exercise sample: a producer enterprise holds export contract HT-2025-031 dated March 2025, covering one lot of self-produced goods, with export customs declaration number 202503120001. The sales detail ledger records current-month export sales of 1,200,000 yuan, and the corresponding line of the export tax refund declaration detail schedule has been filled in. The sentence under evaluation is: "This export lot has completed refund approval and the customer can be told the refund has arrived."

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison method |
| --- | --- | --- |
| Request address | URL provided by the external order system | Determined from the external interface document; compared character by character against the documented address |
| Request method | POST | Compared against the method declared in the interface contract; differences recorded |
| Headers authentication | Authorization injected through secure configuration | Compared against the authentication method required by the interface document; not written into public samples |
| Body fields | Order number and customs declaration number referenced from upstream node output | Compared field name by field name against the external interface contract |
| Return value extraction | Order status field extracted by JSON path | Compared against the actual response structure; output type set to string |
| Debug identity fields | chatId and responseChatItemId left empty | Neither exists in test mode; empty values are not recorded as business faults |

## Three common errors

1. Treating the interactive display configuration returned by an interactive node as a submittable form. That field contains only type and params; entryNodeIds, memoryEdges, nodeOutputs, and nodeResponseId are not returned, and the submission action requires separate implementation.
2. Using tokens from responseData returned under detail=true directly as actual consumption. The documentation states that actual consumed Token values are not returned and must be calculated manually.
3. Using a retrieval similarity score to judge whether a record belongs to this enterprise or has been authorized. Similarity does not perform entity isolation or permission filtering, and a retrieval result does not constitute an authorization basis.

Corresponding checks: inspect the returned field list of interactive and confirm whether fields excluded by the documentation appear; inspect the detail=true response and confirm whether tokens were manually calculated; inspect retrieval results against the permission scope and confirm whether similarity was treated as an authorization judgment.

## How to verify the setup

- Verification one: input contract HT-2025-031, customs declaration number 202503120001, the sales ledger export sales figure of 1,200,000 yuan, and the sentence under evaluation from the hypothetical sample. Compare whether the sentence matches the current state of the export tax refund declaration detail schedule. If the schedule does not record completed refund approval, the sentence is unsupported and cannot be treated as approved.

- Verification two: input the same customs declaration number from the hypothetical sample and compare whether the order number and customs declaration number referenced in the HTTP request Body match the field names in the external interface contract. If the field names differ, record the difference and do not assume the interface will accept the request.

- Verification three: input the debug request from the hypothetical sample with chatId left empty and compare whether the returned result reports the missing chatId as a business fault. The documentation states that chatId does not exist in test mode, so this condition does not constitute a fault.

All three verifications use the hypothetical sample as input and do not claim actual execution. Approval status, authorization scope, and interface responses not stated in the materials remain unknown.
