# Store cold-chain receiving: workflow routing for after-sales questions

## What the documents look like

Cold-chain receiving at a store operates batch by batch. The working materials are cold-chain vehicle temperature records, the WMS, the store receiving system, and quality inspection photographs. Compared with fruit procurement, this stage centers on transport temperature and arrival batch, and origin price inquiry falls outside the scope of the receiving step. The documents handled day to day are cold-chain temperature records, arrival acceptance forms, rejection forms, and supplier delivery notes.

These materials directly shape how order fulfillment and after-sales questions proceed. Temperature records and acceptance forms describe the state of the goods, while a rejection form marks the starting point of a dispute. Workflow routing has to connect material collection, user interaction, and downstream handling so that the judgment for each arrival batch has a traceable basis.

## Constraints at the workflow routing step

In FastGPT v4.17.2, the Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded; after the user fills required information and submits, the node collects the submitted form information and passes it to later nodes. The User Selection node is also a user interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded; when the user makes a choice, the node evaluates that choice and executes the "yes" branch. Both nodes can be added repeatedly and trigger execution.

In the store receiving setting, temperature measurement results, sampling quality conclusions, and rejection reasons require human confirmation. The workflow should collect this information through interaction nodes and hand it to later nodes. Retrieval or form collection only completes information gathering. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. The interaction state record is the node's own behavior; no separate global state-recording switch is documented.

Hypothetical paper exercise sample: a store receiving team handles one arrival batch on 12 April. The supplier delivery note states batch number B-0412, product name chilled pork, quantity 30 boxes. The cold-chain temperature record shows a transport temperature of 2°C to 5°C. The arrival acceptance form draft reads "appearance normal, temperature measurement pending confirmation." An inspector intends to submit a handover request: "This batch passes acceptance; please arrange inbound storage and synchronize with the supplier."

## Configuration and implementation checks

Configuration below follows the checking needs of this sample. It lists only documented settings or implementation checks relevant to workflow routing.

| Configuration item | Hypothetical starting point for this exercise | Checking method |
| --- | --- | --- |
| Form Input node | Collect batch number, temperature result, sampling conclusion | After submission, compare passed fields with later node inputs |
| User Selection node | Set two branches, "acceptance passed / rejection" | Verify each branch connection against its later node |
| Interaction state check | Conversation enters interaction state on trigger | Observe dialog hiding and state recording behavior |
| Output handover check | Pass collected information to retrieval or judgment node | Compare output against input item by item |
| External action division | Inbound storage and supplier sync use a separate interface | Confirm business actions are not performed by the interaction node |

The starting points in this table serve this page's hypothetical exercise. They were chosen to cover both the acceptance-passed and rejection paths, and the comparison object is the node's actual output against the downstream node's input.

## Three common errors

1. Treating form collection as acceptance authorization. The Form Input node collects required information and passes it on; business verification and approval require downstream implementation. In the sample, the inspector's handover request is a submission, and the submission itself does not constitute acceptance passed.
2. Treating execution of a User Selection branch as completed external synchronization. When the User Selection node executes a branch, order writes and supplier synchronization still require a separate interface. In the sample, "please arrange inbound storage and synchronize with the supplier" is a request awaiting execution.
3. Treating the interaction state record as a global state switch. The interaction state is node behavior; no separate global state-recording control is documented or claimed.

## How to verify the setup

1. Input batch number B-0412, the temperature result, and the sampling conclusion from the sample. Compare the fields passed after Form Input submission with the fields received by the later node. The condition is met when the two sets agree.
2. Input the "acceptance passed / rejection" choice from the sample. Compare the branch executed by the User Selection node with its later node connection. The condition is met when branch and connection correspond.
3. Input the handover request text from the sample. Compare the request content with records of completed business actions. When the request remains pending and no inbound storage or synchronization completion record exists, the external action division is correct.

All of the above is a paper check, and no actual test is claimed. Approval status, inbound storage results, and synchronization results not stated in the materials remain unknown.
