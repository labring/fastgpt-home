# Fresh-food weighing and sorting: HTTP integrations for after-sales questions

## What the documents look like

Weighing and sorting happen inside the warehouse fulfillment step, where the controlling facts are weight and specification rather than order aggregation. The working materials are the sorting task sheet, the weighing label, the short-weight compensation form, and the quality inspection record. These are produced per order and summarized on a daily basis. Their data comes from the WMS, electronic scales, the order system, and inspection photos.

For HTTP integration work, each material supplies a different part of the request. The sorting task sheet carries the order and specification identifiers. The weighing label carries the actual scale reading. The short-weight compensation form and the quality inspection record supply the factual basis for answering after-sales questions. Field names follow each system's actual contract; where a field is not provided, it remains unknown. The overall confidence level for this category description is approximate.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a configured address. Params carry path parameters and are common in GET requests. Body carries the request payload and is common in POST and PUT requests. Headers carry special information such as credentials. All three can reference variables with `{{}}`, and the URL can also reference variables. Available variables come from global variables, system variables, and upstream node outputs.

System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. The chatId and responseChatItemId values do not exist in test mode, so reading an empty value there matches the documented behavior of that mode. Histories default to a maximum of 10 entries and the length cannot be changed.

Return values are not the interface response itself. Each configured key defines how to extract a value from the response using JS object access rules or JSON path syntax. When the output type is set to string, the value at that key is converted to a JSON string. In the chat completions interface, authentication uses an APIKey, and passing `body.appId` in the request body is recommended. The alternative `Authorization: Bearer <apiKey>-<appId>` form is supported for OpenAI SDK compatibility. The model and temperature fields passed by the caller have no effect because the orchestration decides them. Actual token consumption is not returned; setting `detail=true` allows manual calculation from the tokens in `responseData`. Using `authProxy` to act on behalf of a team member requires the team owner to enable it when creating or editing the key, and the proxied identity still needs permission on the target app and conversation.

A hypothetical paper exercise illustrates the boundary. The sorting task sheet reads: "Task sheet T-0815, order O-2231, specification 500g±20g, sorter has labeled according to the electronic scale reading of 468g, short-weight compensation form awaiting confirmation by the quality inspection supervisor." A proposed handover request reads: "Please mark this short-weight compensation form as already compensated and synchronize it to the external after-sales system." The subject is the quality inspection supervisor, the object is the short-weight compensation form, the state is awaiting confirmation, and the authorization boundary is that confirmation has not been given. External synchronization is a business action that requires a separate system implementation.

## Three common errors

1. Treating an unconfirmed short-weight compensation form as already compensated. The input is the sample text stating "awaiting confirmation by the quality inspection supervisor," and the proposed handover request asks to mark it compensated and synchronize it externally. The comparison is between the recorded state and the claimed state of "already compensated." The observable result is that the text does not record any confirmation action, so the request exceeds the authorization boundary and is unsupported.

2. Treating an empty chatId under test mode as a business fault. The input is a request made in test mode, and the comparison is the documented statement that the field does not exist in test mode. The observable result is that the empty value matches the stated behavior and does not constitute a business exception.

3. Treating the return value extraction configuration as the interface response itself. The input is a configured key, and the comparison is the actual response structure. The observable result is that the extraction rule determines which field is read, while the response content is decided by the external service. The two cannot be conflated.

## How to verify the setup

1. Using the sample text, input the state description "awaiting confirmation by the quality inspection supervisor" together with the proposed handover request. Compare whether both refer to the same subject, the same object, and the same field. The expected observation is that the recorded state and "already compensated" are mutually exclusive values of the same field, and no confirmation action is recorded, so the request is unsupported and the evidence gap remains open.

2. Using a test mode request, input the case where chatId and responseChatItemId are empty. Compare against the documented test mode behavior. The expected observation is that both empty values match the description and are not judged as faults. If the same empty values appear outside test mode, record that as pending verification.

3. Using the return value extraction configuration, input the configured key and the response example structure. Compare the extraction result against the target field. The expected observation is that a key matching the structure returns the target value, while a structure without that path returns an empty extraction. Record the actual observation without inferring a cause in the external service.
