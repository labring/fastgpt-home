# Livestream after-sales service: HTTP integrations for after-sales questions

## What the documents look like

Livestream after-sales work concentrates around a single session's traffic. Refund requests, reshipment orders, order lists and script templates arrive together after a broadcast, and the host's on-air promises sit close to the stated refund reasons and reshipment demands. The material set draws on Douyin store after-sales records, customer service IM, warehouse WMS and logistics tracking. Customer service staff and warehouse exception roles align wording across the same batch of documents. This page covers only the HTTP integration and external system step inside order fulfillment and after-sales answering. Data updates per session and per day; that cadence does not by itself define any request trigger, batch sync or real-time behavior.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a target address. Params carry path parameters and appear mostly in GET requests. Body carries the request payload and appears mostly in POST and PUT requests, and it takes effect only under the matching request type. Headers carry special information. All three can reference variables through `{{}}`, and the URL can reference variables as well. Variables come from global variables, system variables and upstream node outputs. Return values are not the interface's raw response; each configured return value describes how to parse the response, using JSON path syntax to extract a value. After FastGPT v4.6.8, selecting string as the output type converts the value at the corresponding key into a JSON string. `chatId` and `responseChatItemId` do not exist in test mode, so a blank value there is an environment difference rather than a business fault. A retrieval score is not a category, entity or permission filter; similarity does not exclude unrelated businesses or unauthorized records. Whether an interface can write into an external system depends on that service's implementation and its authorization state.

Hypothetical paper exercise sample: after a livestream session on 8 March 2025, one refund request arrives. The source material reads: "Order A-20250308-017, item is a spring coat, buyer requests a refund, reason is wrong size; warehouse WMS shows the order has shipped, logistics tracking shows in transit." A separate handover draft under review reads: "Convert this refund request directly into a reshipment order and sync it to WMS." The draft treats the refund request as an approved basis for reshipment. The material contains no reshipment approval record, so the request remains pending verification.

## Configuration and implementation checks

| Configuration item | Starting point for this hypothetical exercise | How to check |
| --- | --- | --- |
| Request address and method | Fill per the external interface document; the address references a variable | Compare item by item against the interface document |
| Params and Headers | Auth credentials injected through secure configuration | Check the actual passed values |
| Body structure | Build JSON per the external interface contract | Compare against interface document fields |
| Variable references | Reference global variables, system variables, upstream node outputs | Check each source node one by one |
| Return value extraction | Configure the key per JSON path | Compare against the response example |
| Debug identity fields | `chatId` and `responseChatItemId` do not exist in test mode | Separate environment differences from business faults |

The starting point for this hypothetical exercise is chosen so that variable sources map one-to-one onto external interface fields; the comparison object is the field list declared in the interface document. This is not an official default.

## Three common errors

1. Treating a refund request as direct grounds for reshipment. Input is the source material above plus the draft sentence; compare whether the material contains a reshipment approval record; the observable result is that the material states no approval, so the request stays pending verification.
2. Treating a retrieval result or similarity score as a permission filter. Input is a quote list carrying `score`; compare whether it contains an authorization field; the observable result is that `score` does not express permission, so record usability cannot be judged from it.
3. Treating a blank `chatId` in test mode as a business fault. Input is a test-mode request; compare against the test-mode statement; the observable result is that the field does not exist in test mode, which is an environment difference.

## How to verify the setup

1. Against the source material "Order A-20250308-017, item is a spring coat, buyer requests a refund, reason is wrong size; warehouse WMS shows the order has shipped, logistics tracking shows in transit," check whether the draft sentence converts the refund request into a reshipment order. Compare whether a reshipment approval record exists in the material. The execution condition is met only when the material states such approval; at present it is not supported.
2. Against the same material, check whether the return value extraction key on the interface request matches the response structure. Compare the extracted result against the response example fields. The condition is met only when the field corresponds and the value can be parsed.
3. Against the same material, check whether the variable reference comes from an upstream node output. Compare the referenced value against the node output. The condition is met only when the source matches and the passed value can be checked. All three are paper checks; no actual request was executed.
