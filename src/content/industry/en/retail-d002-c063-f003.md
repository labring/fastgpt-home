# Livestream after-sales service: shared access for after-sales questions

## What the documents look like
Livestream after-sales work concentrates around individual broadcast sessions. Order lists, refund applications, reshipment orders and script templates appear in bursts after a session ends and are then summarized by day. Refund requests and reshipment needs frequently surface together once traffic stops, so support staff reconcile the host's on-air commitments, order status and warehouse handling results inside one working set of materials. The share-and-embed step carries a specific job: it hands a conversation entry point for order fulfillment and after-sales questions to livestream support staff or the after-sales supervisor, while keeping conversation records and cost attribution traceable. Data sources named in the brief are Douyin store after-sales, support IM, warehouse WMS and logistics tracking, updated after each session and daily.

The materials used at this step include the livestream order list, refund applications, reshipment orders and script templates. A shared conversation entry point does not replace the business records behind those documents. Refund approval status lives in the after-sales system; reshipment execution lives with the warehouse; the host's commitments live in session materials and support IM. The share link only determines whether a person can reach the conversation and whether an identity value is returned.

## Constraints at the shared access step
The no-login window is created from the application detail page under publishing channels, and the complete link generated by the system is copied for use. The link name is only for record display. The link itself does not act as business authorization and does not stand in for refund approval or reshipment execution. Expiration time, QPM and point cap are configurable parameters, and some parameters are supported only in the commercial edition. Identity verification is likewise limited to the commercial edition. After a root address is configured, initialization, conversation start and conversation end each send a request to the corresponding interface at that address. The server returns whether verification succeeded; when success is true the user may continue, and uid must be returned as a string that does not contain "|", "/" or "\" and does not exceed 255 bytes in length. The anonymous local identifier depends on the same device and the same browser; switching devices or clearing browser cache loses those records, and only the most recent 30 days and 20 records can be pulled.

These constraints define the boundary. The shared entry point solves conversation reachability and identity return. Order fulfillment status, refund approval and reshipment execution still require separate reconciliation in the after-sales system, support IM and warehouse WMS. A pending request is not an approval. An offered option is not execution. An unsigned termination is not a completed termination.

### Hypothetical paper exercise sample
The following is paper exercise material. It does not come from a real customer or a real order.

Material text one: "Session of 18 June 2025, order number A-0618-037, buyer applied for a refund, refund application status is pending review, warehouse WMS shows the order has not yet been shipped."

Material text two: "The after-sales supervisor stated in support IM: send the after-sales question share link for this session to the livestream support staff, and let support answer the buyer first."

Draft sentence to be judged: "The refund for this order has been approved and can be handled directly as a reshipment."

The subject required for judgment is order A-0618-037, the object is the refund application and reshipment arrangement, the status is pending review and not yet shipped, and the effective scope is the 18 June 2025 session. Pending review does not constitute refund approval. Not yet shipped does not constitute a reshipment arrangement. The draft sentence and the material text disagree on the same field.

An implementation check for the identity path compares the returned success field and the uid format. When success is true and uid meets the character and length requirements, the user may continue. When success is not true, the returned message is shown as an error. If the returned content is absent, record it as unsupported and do not infer a specific error code.

## Three common errors
1. Treating a refund application under pending review as approved. The erroneous input is "refund application status is pending review" from material text one. The comparison object is the draft sentence "the refund for this order has been approved." The observable result is that the draft sentence and the source take different values on the same field, so the draft should be revised to pending verification.
2. Treating a share link as business authorization. The erroneous input is the share link in material text two. The comparison object is refund approval and reshipment execution authority. The observable result is that the link provides a conversation entry point only and carries no approval or execution status, so no reshipment may be arranged on that basis.
3. Treating the anonymous local identifier as a cross-device identity. The erroneous input is the localId of the no-login window. The comparison object is record retrieval after switching devices or clearing browser cache. The observable result is that records may be lost, and identity and session management must be designed separately.

## How to verify the setup
1. Input material text one and the draft sentence, compare the refund application status field, and expect the draft sentence to be judged unsupported with a pending-verification record retained. This expectation is a paper judgment and was not actually executed.
2. Input the share link and the supervisor's request from material text two, compare the link's purpose against refund approval authority, and expect the check to identify that the link serves conversation reachability only and does not constitute refund or reshipment authorization.
3. Input the returned content of the identity verification interface, compare the success field and the uid format, and expect that success being true with a uid meeting the character and length requirements allows continuation, while success not being true shows the error message. If the returned content is missing, record it as unsupported and do not infer a specific error.
