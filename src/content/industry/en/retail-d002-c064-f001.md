# Livestream sample inspections: HTTP integrations for after-sales questions

## What the documents look like

Selection and sample quality checks happen before a livestream, and their purpose is to decide whether a product can be sold and whether it suits on-camera demonstration. The working materials are sample evaluation forms, quality inspection reports, supplier qualification files and prohibited-item lists. These draw on supplier submissions, testing-agency reports, platform negative catalogs and historical return rates. In the order fulfillment and after-sales question stage, the sample evaluation conclusion, inspection status and after-sales position are passed through an HTTP request to an external order or ticket system, and the fields returned by that interface determine the next manual action.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a corresponding address. Params carry path parameters and are used mostly with GET requests. Body carries the request body and is used mostly with POST and PUT requests. Headers carry special information. URL, Params, Body and Headers can all reference variables through `{{}}`, and those variables come from global variables, system variables and preceding node outputs.

System variables include appId, chatId, responseChatItemId, variables, cTime and histories. The histories variable takes at most the last 10 records by default and its length cannot be changed. Two of these variables, chatId and responseChatItemId, do not exist in test mode. Reading an empty value for either during debugging is an environment difference and does not by itself indicate a business fault.

Return values are extracted with JSON path syntax. After v4.6.8, output formatting converts a selected key into a JSON string when the output type is set to string. A configured key follows JavaScript object access rules, so a nested value such as data.user.name can be read directly.

Hypothetical drill sample. A sample evaluation form under review reads: "Supply entity: Supplier X; object: Batch A insulated cup; inspection status is pending re-review; validity scope: samples submitted from this batch." A draft handover request reads: "Mark Batch A insulated cup as inspection passed and sync to the fulfillment system." The request writes pending re-review as passed, and writes to-be-synced as already synced. The HTTP node can send a request and parse a response. Confirmation of business status, approval and database writes require downstream system implementation, and an interface call by itself does not produce authorization.

## Configuration and implementation checks

| Configuration item | Value or check content | Relation to this page's documents |
| --- | --- | --- |
| Request address and method | Chosen from the external interface documentation; the address can reference variables | The address and action must match the fulfillment system contract |
| Headers | Authentication credentials injected through secure configuration, not written into public samples | Used to carry identity information |
| Body | Used only under the corresponding request type; verify the JSON structure | Carries batch and inspection fields |
| Variable references | Reference global variables, system variables and preceding node outputs | Check the actual passed values item by item |
| Return value extraction | Specify a key with JSON path and select an output type | Determines the fields the downstream can read |
| Hypothetical trial starting value | This drill takes "pending re-review" as the starting status value | Chosen because the sample text says so; compared item by item against the inspection status field returned by the interface |

## Three common errors

1. Sending the hypothetical sample's "pending re-review" as already passed. The input is the sample text and the draft request; compare the status field in each; an observed mismatch between the request status and the source text is the error.
2. Treating an empty chatId or responseChatItemId in test mode as an interface failure. The input is the debug response; compare it against the documented test-mode condition; an observed test-mode context explains the empty value.
3. Treating a successfully parsed HTTP response as a completed business sync. The input is the response content; compare it against the actual record in the fulfillment system; an observed absence of the corresponding record shows the sync has not completed.

## How to verify the setup

1. Take the hypothetical sample text and the draft request, and compare supply entity, object, inspection status and validity scope word by word. A contradiction exists only when the same field holds mutually exclusive values. The source text saying "pending re-review" while the draft says "passed" is a conflict within one field.
2. After referencing variables with `{{}}`, check the actual passed values. The input is the node configuration and the runtime variables; compare the reference keys against the expected keys; the condition is met when the keys match and the values are non-empty. A missing key or an empty value is recorded as a gap.
3. Check the extraction key and output type for the return value. The input is the interface response example and the configured key; compare the extracted result against the value at the corresponding path in the response structure; the condition is met when the two match. When the path does not exist, keep the result unknown and do not infer a failure cause.

Retrieval and similarity scores do not carry authorization or entity isolation duties, and an interface call does not constitute authorization. The display configuration returned by an interactive node contains only type and params; internal runtime fields are not returned. A pending review does not show an absence of operating permission, pending re-review does not mean passed, and a sent request does not mean the business has synced.
