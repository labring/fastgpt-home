# Group-buy presale orders: shared access for after-sales questions

## What the documents look like

Group-buy presale collection takes orders first and then organizes procurement and fulfillment. That sequence differs from leader-relationship work. The everyday materials for this task are the presale product table, the collection result, the procurement plan, and the cut-off notice. Their sources are mini-program orders, supplier inventory, leader feedback, and warehouse-and-delivery routing. These materials determine what a shared entry point can display and what a user can submit.

A shared link solves access only. Whether an order is valid and whether an after-sales request can be accepted depend on the fulfillment materials and the authorization state. Access and business authorization cannot substitute for each other. The public brief marks this category background as roughly accurate, so the material list and update frequency remain conditional rather than fixed facts.

## Constraints at the shared access step

The no-login window is created under the publish channel, and the system generates the complete link that gets copied. The link identifier supports access only and cannot serve as business authorization. The system generates a localId for each user to identify that user and pull conversation records from the cloud. That method only holds on the same device and the same browser; switching devices or clearing browser cache loses the records. Only the most recent 30 days and 20 records can be pulled.

Identity verification is a POST root address. Initialization, conversation start, and conversation finish each send a request to a specific endpoint under that address. The server returns success and uid. The uid must be a string that excludes the characters "|", "/", and "\" and is no longer than 255 bytes; otherwise the system returns the error `Invalid UID`. This identity verification feature is provided only in the commercial edition. Parameters such as expiry time, QPM, points cap, and identity verification are partly restricted by edition.

Hypothetical paper exercise: a platform operator prepares a cut-off notice draft on 10 June 2025. The draft text reads: "This presale session cuts off at 20:00 on 11 June. After cut-off, procurement is placed according to the collection result. Out-of-stock orders are handled as refunds." The same batch contains a leader feedback note dated 9 June stating: "Some order demand was added after cut-off." The sentence to be judged is: "Added demand can be merged into this session's collection result after cut-off and enter the procurement plan." The subject is the platform operator, the objects are this session's collection result and procurement plan, the state is post-cut-off addition, and the authorization boundary is not written in the materials.

## Configuration and implementation checks

After the identity verification root address is configured, every use of the shared link sends a verification and reporting request. The table below is a hypothetical trial starting point for checking how configuration maps to the materials.

| Configuration item | Hypothetical trial starting point | Object compared and reason |
| --- | --- | --- |
| Link name | Cut-off notice Q&A entry | Used for record display only; unrelated to authorization |
| Expiry time | 20:00 on 12 June 2025 | Compared with the cut-off notice date; an expired link is unusable |
| QPM | 10 per user per minute | Set by usage scope; check the actual edition's support |
| Points cap | 5,000 points for this session | Check cost attribution and usage limit |
| Identity verification | POST root address entered | Check commercial-edition scope and endpoint response |
| authToken | Appended to the shared link | Compared with token in the initialization request body |

Conversation-record boundaries follow the documentation; cross-device records need separately designed identity and session management. A retrieval value or a form-collected value does not equal business authorization. Procurement, refunds, database writes, and external synchronization each need their own downstream implementation.

## Three common errors

1. Treating the link identifier as business authorization. Input: the shared link and the cut-off notice. Compare whether the link carries authToken and whether verification returns success. Observe whether operation can continue when verification does not pass.
2. Treating a pending added request as already merged into the collection result. Input: the 9 June leader feedback and the 10 June cut-off notice. Compare whether the added demand appears in the collection result material. Observe whether the procurement plan is still written when that material is missing.
3. Treating a similarity score or retrieval result as a permission filter. Input: one retrieval request and the returned quoteList. Compare whether returned records fall inside the target range the requester may access. Observe whether unrelated records are misused as operable objects.

## How to verify the setup

1. Input the cut-off notice text and the sentence to be judged from the hypothetical sample. Compare whether the judged sentence exceeds the cut-off and refund scope written in the source text. If the source text does not state that additions are merged, the judgment is unsupported and is recorded as pending verification.
2. Input the shared link and authToken. Compare the token in the initialization request body with the configured value. If verification returns success as true and data.uid meets the length and character requirements, operation may continue. If it returns `Invalid UID` or success is not true, record the error message.
3. Input one retrieval request. Compare whether sourceName and datasetId in the returned quoteList fall inside the target range the requester may access. If an empty list is returned, use an explicit paper input of [] to check the downstream design, without claiming that a fictional rule's retrieval always returns empty.

This page addresses only group-buy presale collection, order fulfillment and after-sales Q&A, and sharing and embedding. It does not treat retrieval or form collection as authorization execution.
