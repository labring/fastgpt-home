# Group-buy presale orders: workflow routing for after-sales questions

## What the documents look like

Presale group buying collects orders first and organizes procurement and fulfillment afterward. This differs from leader relationship management, which is a separate work focus. Everyday materials include the presale product table, the order-collection result, the procurement plan, and the cut-off notice. Data sources involve mini-program orders, supplier inventory, leader feedback, and warehouse-delivery routing. The order fulfillment and after-sales question stage needs to align post-cut-off product quantities, procurement arrangements, and user requests. Materials update daily or per session.

When these materials enter workflow routing, the Form Input node and the User Selection node carry information collection and branch decisions. The Form Input node enters an interaction state when triggered, records the workflow state, and after the user completes required information and submits, passes the form information to later nodes. The User Selection node also enters an interaction state, and after the user makes a choice, executes the corresponding branch. Neither node equals order writing, refund approval, or supplier synchronization. Those actions need a separate business interface or a later process.

## Constraints at the workflow routing step

Interaction nodes only collect and branch. A form submission yields values the user filled in, not a business verification result. A user selection yields an option, not authorized execution. If the order-collection result, procurement plan, and cut-off notice are to drive order status changes, the workflow must explicitly connect the corresponding business interface. The form node or selection node cannot substitute for it.

Retrieval finds related materials and does not carry permission or entity isolation. The knowledge-reference limit is calculated in the unit stated in the documentation, and only the same vector model can be associated together. Libraries across different vector models do not perform joint association; check identifiers and exclude non-matching items. An empty-result handoff can use a paper input to check the downstream design, without claiming that a given retrieval necessarily returns empty.

Hypothetical drill sample: the source text reads "Presale product table row A-17: product code SY-042, five-jin pack specification, cut-off time 2025-06-10 20:00, presale quantity cap 200 units. Order-collection result row B-03: product code SY-042, 187 orders received, status cut off. Procurement plan row C-09: product code SY-042, planned procurement 190 units, status pending review." The draft sentence to be judged is: "SY-042 is cut off, the 190-unit procurement plan has passed review, and the sorting wave can be arranged." The draft sentence writes pending review as passed review, which is an unsupported statement.

## Configuration and implementation checks

| Configuration item | Assumed starting point for this drill | Basis and comparison method |
| --- | --- | --- |
| Form Input node required fields | Product code, order number, request type | Collect required information per the documentation and pass it to later nodes after submission; compare item by item with the order-collection result |
| User Selection node branches | Reshipment and refund inquiry branches | Execute the corresponding branch after the user selects, per the documentation; verify branch connections one by one |
| Interaction state check | Enters interaction state after trigger | The documentation states the workflow state is recorded; check whether the conversation enters the interaction state |
| Output handoff | Form values passed to retrieval or decision nodes | Compare each node output against the next node input item by item |
| External action division | Order writing and refund approval connect to separate interfaces | Business actions need separate system implementation per the documentation and are not written into node configuration |
| Paper empty-result handoff | Input [] to check downstream design | Use an explicit paper input to check downstream branches; do not claim an actual retrieval result |

The assumed starting values are used only for this paper check and do not constitute official default values. These fields were chosen because, in the sample, product code and order number are unique corresponding identifiers, and request type determines the branch direction. The comparison object is the corresponding row in the sample source text.

## Three common errors

1. Treating a form submission as business verification. The input is the form-filled product code SY-042 and order number. The comparison object is the product code and status in order-collection result row B-03. If the form value directly triggers a refund or procurement write, the business interface handoff is missing, and this is an error.
2. Treating pending review as passed review. The input is the status "pending review" in procurement plan row C-09. The comparison object is "has passed review" in the draft sentence. The two take different values on the same field. If the sorting wave proceeds on the basis of passed review, this is an error.
3. Treating retrieval as authorization. The input is one knowledge-base retrieval request. The comparison object is the retrieval result and the identifier of the target material. If a retrieval hit is taken as authority to execute a refund or modify an order, this is an error.

## How to verify the setup

1. For the sample draft sentence, input the three source rows and the draft sentence, and compare "procurement plan row C-09 status is pending review" with the draft sentence "has passed review." The condition is met if the check conclusion is unsupported and the evidence gap is retained.
2. For the Form Input node, input the product code and order number from the sample, and compare whether the form output matches the next node input. The condition is met if the values received by the later node correspond item by item to the form-filled values.
3. For the User Selection node, input the request type from the sample, and compare the user selection result with the branch connections. The condition is met if selecting reshipment executes the reshipment branch and selecting refund inquiry executes the refund inquiry branch.

The above are paper check designs and were not actually run. A retrieval hit does not indicate authorization. Pending review does not indicate approval. A collected form value does not indicate completed business verification.
