# Cross-border product labels: workflow routing for after-sales questions

## What the documents look like

Cross-border product compliance and labelling work for order fulfilment and after-sales questions draws on four document families: product test reports, English-language labels, material safety data sheets (MSDS), and platform prohibited-item lists. These materials come from platform policy centres, testing laboratory reports, destination-country regulatory repositories, and supplier submissions. The category sits upstream of listing and import, where the core evidence concerns product safety and label content rather than transaction risk. Typical roles handling the documents are cross-border sellers, product managers, and compliance specialists. The consequence of getting the routing wrong is a platform delisting, customs hold, or consumer claim.

For workflow routing in order fulfilment and after-sales answering, the relevant point is that these documents are cited to answer fulfilment conditions, label consistency, and after-sales grounds. A workflow routes information collected through user interaction into later retrieval and judgement nodes. The documents update irregularly and on each new listing; that cadence does not by itself add a synchronisation mechanism to this page.

## Constraints at the workflow routing step

The Form Input node and the User Selection node are both user-interaction nodes. When either is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The Form Input node collects required information the user submits and passes it to later nodes. The User Selection node evaluates the user's choice and executes the corresponding "yes" branch. State recording is a behaviour of these interaction nodes; no separate global state-recording switch is documented.

Retrieval results do not constitute authorisation. Order writes, document backfill, and external status synchronisation require a separate business interface or a later process. A pending request is not an approval; an offered option is not an execution; an unsigned termination is not a completed termination.

Hypothetical paper exercise sample: a batch of children's drinking cups carries an English label reading "Suitable for ages 3+". The accompanying test report states "Ages 3 and above". The MSDS is not provided in this handover material. A proposed reply sentence reads: "The product label and test report agree on the age marking, so after-sales may answer on this basis." The handover request awaiting a decision reads: "Please confirm this batch of cups is label-compliant and agree to the after-sales reply." The material states no MSDS and no authorisation signing or effective clause. The request remains pending verification.

## Three common errors

1. Treating a retrieval result as an authorisation basis. A retrieval library returning a label document does not mean the after-sales reply is approved. For the check, input the proposed sentence and the source material text, compare whether subject, object, and status match on the same field, and observe whether an unstated authorisation clause exists.

2. Treating a pending review as approved. A handover request saying "please confirm" is in a pending-verification state. For the check, input the request text and the source material text, compare whether a signing, effective, or approval record appears, and observe whether an evidence gap remains.

3. Associating libraries of different vector models together. Cross-model association is not permitted. For the check, first verify the identifiers and exclude those that do not conform, then observe whether an actual observation result is recorded. Do not run a cross-model retrieval to compare missed recalls.

## How to verify the setup

- Verification one: input the hypothetical sample's label text "Suitable for ages 3+" and the test report text "Ages 3 and above". Compare the age-marking value on the same field and observe whether the two are clearly mutually exclusive. If the values agree, this supports only that field's agreement and does not constitute compliance approval.

- Verification two: input the proposed sentence "The product label and test report agree on the age marking, so after-sales may answer on this basis". Compare whether the material states an after-sales reply authorisation and observe whether an authorisation or effective clause appears. When none is stated, record it as unsupported, without judging it as a denial or a conflict.

- Verification three: input the handover request awaiting a decision, "Please confirm this batch of cups is label-compliant and agree to the after-sales reply". Compare whether a signing, cooperation-reached, or contract-effective record appears in the material and observe whether it remains pending verification. When the MSDS is missing, record the evidence gap and do not fabricate an authorisation clause.
