# Cross-border resale returns: multi-turn prompts for after-sales questions

## What the documents look like

Returns refurbishment handles reverse logistics and item condition, which is a different chain from first-leg replenishment. The working materials are return inspection sheets, refurbishment records, scrap sheets and relisting lists. Sources include overseas warehouse WMS, TikTok return centers, Amazon return reports and inspection photos. An after-sales supervisor answering fulfilment and after-sales questions needs multi-turn dialogue to stay anchored to these materials when stating a return grade, a refurbishment and repacking arrangement, or a scrap-versus-resale decision. Material updates arrive daily or per batch; this page does not depend on that cadence.

A hypothetical paper sample is used throughout. The return inspection sheet reads: "Batch R-0417, item is a folding storage box, inspection conclusion is outer carton damaged and inner contents intact, refurbishment method is replacement of the outer carton, refurbishment completion date 20 April, relisting list has been entered as pending review." One draft sentence under review reads: "This batch has completed refurbishment and has been relisted." The refurbishment completion date and the pending-review status of the relisting list are separate facts. The draft sentence states pending review as relisted, and no relisting execution evidence exists in the material. The material does not record the relisting authorizer, the relisting platform or the relisting time; those fields remain unknown.

## Constraints at the multi-turn prompts step

Multi-turn dialogue must check which history is actually carried in, and must distinguish a new session from a continued session. When chatId is supplied, the system reads the session from the database and uses the last item in the messages array as the user question; the remaining messages are ignored. When a knowledge base needs continuous dialogue, check pronoun resolution and question expansion rather than assuming every short question fits. Reply format follows the downstream consumer; when json_schema is selected, the format requirement must be filled in and the returned structure verified. Similarity and retrieval do not act as permission or entity isolation.

Prompt text should state the material scope, the answering task and how to behave when evidence is missing, so the model does not write business facts on its own. History handling should confirm the context actually carried in and separate new-session input from continued-session input. Model and length checks should confirm the supported context and reply settings against long documents combined with follow-up questions. Retrieval and relevance scores carry no subject or permission information and cannot be used to exclude unauthorized records.

## Three common errors

1. Writing a pending-review status as already executed. Input is the pending-review status of the relisting list in the sample; comparison object is the draft sentence "has been relisted"; observable result is that the two states do not match and the draft sentence is unsupported.

2. Treating similarity as a permission filter. Input is the score field returned by retrieval; comparison object is the business authorization scope; observable result is that score contains no subject or permission information and cannot be used to exclude unauthorized records.

3. Treating the display configuration returned by an interactive node as already submitted. Input is the type and params inside interactive; comparison object is the subsequent continue-run request; observable result is that the display configuration contains no submission result, so a separate request is needed and chatId must stay consistent.

## How to verify the setup

1. Input the sample source text and the draft sentence "This batch has completed refurbishment and has been relisted"; compare the refurbishment completion date with the relisting list status; observe whether the draft sentence states pending review as relisted. Expected outcome is that the state mismatch is identified, and the authorizer and time fields not recorded in the material are logged as gaps.

2. Input one continued-session request with chatId; compare the history actually carried in with the expected turn count; observe whether the returned historyPreview or contextTotalLen matches the setting. Expected outcome is that the carried turn count matches the configuration and that new-session input is distinguishable from continued-session input.

3. Input a question containing an image link; compare the model's multimodal capability with the returned content; observe whether the image is parsed. Expected outcome is that when the model supports it the image enters the request, when it does not support it the image is not sent, and link extraction is attempted only when the question is under 500 characters and at most 4 media links are handled at a time.
