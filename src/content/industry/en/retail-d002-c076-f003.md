# Creator commission settlement: shared access for after-sales questions

## What the documents look like

Creator commission settlement and deduction sits after promotion. The monthly workload concentrates on checking valid orders, deducting commission on refunds, and issuing invoices against payments. The Selected Alliance back office supplies commission setting records and settlement statements. The finance system carries refund deduction details and invoices. Creator contracts define the settlement cycle and the deduction basis. These four materials live in different systems, so order numbers, creator identifiers, settlement periods, and amount fields can misalign during cross-system comparison.

This page addresses one step only: sharing and embedding during order fulfilment and after-sales questions. It explains what authorization state the materials, operations, and requests occupy. Retrieval and forms collect values; they do not perform authorization or execute business actions. The update frequency stated in the brief is weekly and monthly. This page does not derive batch synchronization, full synchronization, or transaction-triggered mechanisms from that frequency.

## Constraints at the shared access step

A no-login window is created from the publish channel, and the system-generated full link is copied for use. The link identifier is an access entry point and does not function as business authorization. Expiry time and QPM are set according to the intended scope and checked against the actual version; QPM means the maximum number of visits per user per minute. The points cap is checked against the usage limit of the shared entry and the cost attribution, and some parameters are restricted by version. Identity verification is restricted to the commercial edition scope, and release is decided by the `success` status and `uid` returned by the official interface. The anonymous local identifier depends on the same device and same browser; cross-device records require separate design of identity and session management.

Hypothetical paper exercise: a settlement specialist intends to share a no-login link with an external creator business contact for querying a monthly statement. The material text supplied for checking is: "Commission setting record: Creator A, settlement period March 2025, commission rate 12%. Settlement statement: Creator A, March 2025, commission payable 4,800 yuan, status pending confirmation. Refund deduction detail: Creator A, March 2025, 3 refunded orders, commission deducted 260 yuan." The handover request to be judged is: "Please open the March statement query entry to Creator A through the share link; identity verification has been configured and the link can be used directly." The identity verification configuration state, the link authorization scope, and the statement confirmation state in this request each require separate verification.

## Configuration and implementation checks

The configuration below centers on the materials and request in the exercise. It lists only settings the official documents describe or implementation items to check. The values are starting points for this hypothetical trial, with the reason and the comparison object stated.

| Configuration item | Hypothetical trial starting point | Check method and reason |
| --- | --- | --- |
| Name | Enter "Creator A - March statement query" | The name is for record display only and is unrelated to authorization scope; check whether it matches the creator and period in the exercise |
| Expiry time | Set to one week after the statement query period ends | After this time the link cannot be used; compare with the settlement specialist's planned query window, not treated as an official default |
| QPM | Keep the existing value from link creation | QPM is the maximum visits per user per minute; compare with the creator contact's actual concurrent access before adjusting |
| Points cap | Set according to the estimated usage of this query | This is the maximum billing data the link generates; compare with single-query usage of the statement, and note cost attribution to the team owning the application |
| Identity verification | Enter the third-party verification root address | Only the root address is required, not the full path; release is judged by `success` and `uid` returned from the `POST` request |
| Conversation record boundary | Rely on same device and same browser | The anonymous local identifier loses records across devices; compare with the creator contact's multi-device usage needs |

## Three common errors

1. Treating the link identifier as an authorization credential. The input is the share link in the exercise and the request to be judged. Compare the link creation record with Creator A's authorization scope. If the request claims direct use while the authorization scope is not stated, the request remains unsupported.
2. Treating a pending statement as a confirmed statement. The input is "status pending confirmation" in the exercise material. Compare the confirmation field of the settlement statement with the open-query action in the request. The same field holds different values, which is a contradiction, and the confirmation state needs verification first.
3. Treating configured identity verification as already effective. The input is "identity verification has been configured" in the request. Compare the configuration record with the actual verification interface response. If a return record with `success` true and a `uid` is absent, the configuration remains pending verification.

## How to verify the setup

1. Check the link authorization scope. Input the request to be judged and the link creation record from the exercise. Compare the creator identifier, settlement period, and authorized party. If the record does not state a query authorization for Creator A, record the result as unsupported, not as a denial.
2. Check the statement confirmation state. Input "status pending confirmation" in the exercise material and the open-query action in the request. Compare the confirmation field of the same statement record. If the two values are mutually exclusive, record a contradiction and preserve the evidence gap.
3. Check the identity verification return. Input the `POST` request and response of the verification interface. Compare the `success` field and the `uid` format. If the response returns `success` true and a `uid` that is a string without special characters and no longer than 255 bytes, the release condition is met. If the response returns `success` false, handle it according to the `message` prompt and do not infer other system errors.
