# Import and export permits: HTTP integrations for after-sales questions

## What the documents look like

Permit handling takes place before customs declaration, and it determines whether a shipment may lawfully be imported or exported. For order fulfillment and after-sales answers, this timing difference shapes how an HTTP integration is designed: the interface may be asked to confirm a permit state that does not yet exist, or to pass along a draft sentence that treats a pending application as a completed one.

The working materials for this category are the automatic import license, the dual-use item license, the contract, and the product description. Sources include the commerce authority system, customs commodity codes, supplier materials, and the customer's statement of use. Updates are irregular and per shipment. An HTTP module can be called once per shipment against an external interface. The supplied brief does not describe batch synchronization, full synchronization, real-time updates, or transaction-triggered mechanisms, and none of those are inferred here.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a specified address. Params carry path request parameters and are used mostly with GET. Body carries the request body and is used mostly with POST and PUT. Headers carry special information. All three can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and preceding node outputs. The return-value configuration describes how to parse the interface response, extracting values through JSON path syntax. When the output type is set to string, the value of the corresponding key is converted into a JSON string.

The chat interface uses APIKey authentication. When calling chat/completions, passing `body.appId` in the request body is recommended. For OpenAI SDK compatibility, `Authorization: Bearer <apiKey>-<appId>` is also supported, and in that case `body.appId` is not required. The appId priority order is `body.appId`, then `<apiKey>-<appId>`, then the appId associated with the apikey under the older adaptation. Some SDKs need `v1` added to the BaseUrl and some do not; on a 404, the `v1` path can be added and retried.

`chatId` and `responseChatItemId` do not exist in test mode. An empty value during debugging is not a business fault. When `detail=true`, intermediate values are stored in `responseData`; when `stream=true`, they are distinguished through event. For an interactive node, the `interactive` returned to the external caller is a display configuration containing only `type` and `params`; internal runtime fields such as `entryNodeIds`, `memoryEdges`, `nodeOutputs`, and `nodeResponseId` are not returned. Forms and retrieval collect values. Business verification, approval, database writes, and external synchronization require their stated downstream implementation.

Assumed paper exercise sample: a foreign-trade compliance role receives an automatic import license application. The contract number is HT-2024-0517. The product description states the use as "assembly of industrial equipment components." The application date is 17 May 2024. The license has not yet been obtained. A draft handover request reads: "Please help confirm that this shipment's license has been completed and arrange dispatch." The draft treats an unobtained license as a completed fact. The subject, object, and state all require re-checking.

## Configuration and implementation checks

| Configuration item | Assumed starting point for this exercise | How to check |
| --- | --- | --- |
| Request address and HTTP method | Filled according to the external interface document | Compare against the interface document to confirm address and method |
| Params and Headers | Authentication credentials injected through secure configuration | Check the actual passed values item by item; the sample does not write public credentials |

| Return value extraction | Key configured according to JSON path | Compare against the response example to confirm the extraction path |
| detail and stream | Selected according to troubleshooting need | Check the responseData branch or the event branch |

The starting points in the table are assumed values for this paper exercise, used for paper checking, and are not defaults. Fields such as `maxToken`, `similarity`, and `limit` are used only with the meanings given in the documents. A similarity score is not a permission or entity filter.

## Three common errors

1. Treating the absence of `chatId` and `responseChatItemId` in test mode as an interface fault. Check whether the input is in test mode and whether these two fields were passed. Observe whether the corresponding fields are missing from the returned structure.
2. Mixing the appId in `body.appId` with the appId in `Authorization` without checking the priority order. Check whether the two values are consistent. Observe whether the appId that actually takes effect matches the expected one.
3. Writing the draft sentence "the license has been completed" into the handover as fact. Check the license status field in the source material. Observe whether the draft sentence matches the source. When they do not match, record it as pending verification.

## How to verify the setup

1. Input the assumed sample source material and the draft sentence. Compare "has been completed" in the draft against "has not yet been obtained" in the source. Observe whether the two are consistent. If they are not consistent, the draft sentence is not supported, and the evidence gap is preserved.
2. Input a request configuration containing `{{variable}}`. Compare the variable reference key against the name of the preceding node output. Observe whether the actual passed value matches the expected one. When it does not, record it as pending verification.
3. Input a request with `detail=true` and `stream=false`. Compare whether the returned structure's `responseData` contains the node response. Observe whether the extraction path hits. When it does not hit, record it as pending verification.

All of the above is paper reasoning. No call, approval, or dispatch has been executed.
