# Import and export permits: workflow routing for after-sales questions

## What the documents look like

Import and export permit handling happens before declaration and determines whether a shipment may lawfully cross a border. For order fulfilment and after-sales question handling, the working materials are the automatic import licence, the dual-use item licence, the contract, and the product description. Source material comes from the commerce authority system, customs commodity codes, supplier documents, and customer statements of use. Updates are irregular and each shipment is handled on its own.

Workflow routing in this task breaks order fulfilment and after-sales questions into checkable steps. A form input node enters an interaction state when triggered, records the workflow state, collects required information, and passes the submitted information to later nodes. A user selection node also enters an interaction state when triggered, and after the user makes a choice the node evaluates that choice and executes the corresponding branch. These interaction and state-recording behaviours belong to the two nodes as documented.

## Constraints at the workflow routing step

Permit materials change from shipment to shipment, so a workflow cannot rely on a fixed permit conclusion. Form and selection nodes collect information and route it; order writes, document backfill, and external status synchronisation require a separate business interface or a later process. Retrieval results do not constitute authorisation, and a similarity setting does not perform permission or entity isolation.

Hypothetical paper exercise sample, not a real business matter:

Source text one: "Party A entrusts Party B to apply for an automatic import licence for a specified model of equipment, contract number H-2026-014, with shipment expected in May 2026; Party B shall submit the application within five working days of receiving the complete product description."

Source text two: "Party B received the product description on 20 April 2026 and replied on 21 April 2026 that the application had been submitted, with approval status to be followed up."

Draft sentence to be assessed: "The automatic import licence for this shipment has been approved, and the order can ship as originally planned."

The draft sentence treats a submitted application as an approval. The source material shows only submission and a pending status, and contains no approval outcome. The workflow should keep this draft sentence in a pending-verification state and route it to a person to check the approval status before any release decision.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Reason and comparison method |
| --- | --- | --- |
| Form input node | Enabled, collecting contract number and product description | Compare with source text one to confirm the required fields cover the contract number |
| User selection node | Enabled, with branches "continue follow-up" and "route to person" | Compare with source text two; an undetermined approval status routes to a person |
| Interaction state recording | Recorded according to the documented node behaviour | Compare with the documentation; no separate global state switch is set |
| Output handover | Form information passed to a later retrieval or interface node | Compare each input field with the fields the downstream node receives |
| External operation split | Order writes and status synchronisation connected through a separate interface | Compare with the documentation; form submission is not treated as an order write |

These values are hypothetical trial starting points for this page and are not official defaults. The comparison method is to check each configuration item against the hypothetical source texts line by line and observe whether the configuration covers the fields and statuses that appear in those texts.

## Three common errors

1. Treating form submission as completed approval. The input is source text two, where the application has been submitted and the approval status is pending. The comparison object is the draft sentence stating approval. The observable result is that the two statuses do not match, so the draft sentence returns to pending verification.

2. Treating a user selection branch as authorised execution. The input is the interaction state triggered by the selection node. The comparison object is an order write or external synchronisation action. The observable result is that the selection node only executes a branch, while an order write requires a separate interface.

3. Treating retrieval similarity as a permission filter. The input is the records returned by retrieval. The comparison object is the party and contract number in source text one. The observable result is that similarity does not exclude unrelated parties, so the identifiers require manual checking.

## How to verify the setup

1. Check the form fields against source text one. Input contract number H-2026-014 and the product description, compare whether the required form fields cover both items, and observe whether the later node receives the same field values after submission.

2. Check the branch direction against source text two. Input the pending approval status, compare whether the user selection node takes the "route to person" branch, and observe whether branch execution triggers no order write.

3. Check the output handover against the draft sentence. Input the sentence stating that the automatic import licence has been approved, compare it with the approval status in source text two, and observe that the draft sentence lacks evidence of an approval outcome, so it should be marked pending verification and should not enter a release process.

All three verification steps are paper comparisons and were not actually run. A missing approval outcome remains missing, and a pending review status is not treated as approval.
