# Chain-store site selection: HTTP integrations for after-sales questions

## What the documents look like

Site selection and store opening happen before a store begins trading. The work centres on lease and construction delivery rather than on supervising operating franchise stores. The records generated at this stage include site evaluation forms, letters of intent to lease, renovation budgets and opening schedules. Each record is produced per store, and updates are irregular rather than scheduled.

Extension staff calculate the rent-to-sales ratio, negotiate lease terms and coordinate renovation milestones. A wrong date or amount reference in any of these steps can lead to a lost deposit or a delayed handover. The HTTP module treats the external system address, request parameters, headers and body as configuration items. The address and body fields can reference global variables, system variables or upstream node outputs, so one site-selection record is split into several variable values as it moves through the workflow.

## Constraints at the HTTP integrations step

The HTTP module sends a request to the configured address. Params are mostly used for GET requests, Body for POST and PUT, and Headers carry special information. Variables come from global variables, system variables and upstream node outputs. The `{{}}` reference works in all three data types, and the URL can also reference variables. Return values are extracted with JSON path syntax, and when the output type is set to string the corresponding value is converted into a JSON string.

In test mode, `chatId` and `responseChatItemId` do not exist, so an empty value during debugging is not a business fault. The chat completions interface uses APIKey authentication. Passing `body.appId` in the request body is recommended, and the `Authorization: Bearer` form is also supported. Fields such as `model` and `temperature` that are passed in have no effect, because these are decided by the orchestration.

Hypothetical paper test case: an extension department at a chain headquarters is processing a letter of intent to lease. The material text reads: "Letter of intent number YX-2024-031, tenant is the regional development group of a chain brand, subject is a ground-floor unit in a commercial district, intended lease term starts 1 June 2024, letter status is awaiting landlord confirmation, signature block is empty." A draft handover request is also under review: "This letter of intent is already effective; please schedule the renovation entry date according to the intended lease term and generate an opening schedule." The subject needed for the judgement is the tenant regional development group, the object is the above unit, the status is awaiting landlord confirmation with an empty signature block, and the valid scope is the start of the intended lease term.

For this page, a hypothetical starting value is a request method of GET with a Body declaration attached. This starting value is chosen because it directly exercises the documented condition that Body takes effect only under specific request types, and it is compared against the documented statement that Body is mostly used for POST and PUT.

## Three common errors

1. Treating the letter of intent status "awaiting landlord confirmation" as already effective, then scheduling the renovation entry date from the intended lease term. The input is the letter text above together with the draft handover request. The comparison is between the material status field and the effectiveness premise the draft relies on. The observable result is that the two do not match, and the effectiveness premise of the draft is not supported by the material.

2. Filling in a Body on a GET request, or omitting the outer quotation marks when referencing a string inside the Body. The input is the configured request method and Body declaration. The comparison is against the documented statements that Body takes effect only under specific request types and that a string reference needs `""`. The observable result is that the declaration does not match the actual request type or the reference syntax.

3. Recording a missing `chatId` or `responseChatItemId` in test mode as an interface fault. The input is the request and response in test mode. The comparison is against the documented statement that both are absent in test mode. The observable result is that the absence falls under a condition the document already describes.

## How to verify the setup

1. Take the letter of intent text above and the draft handover request. Check whether the material status field and the effectiveness premise the draft relies on are consistent. The expected observation is that the status is identified as awaiting landlord confirmation, the signature block is empty, and the effectiveness premise of the draft is not supported by the material, recorded as pending verification.

2. Take the configured request method and Body declaration. Compare them item by item against the documented Body effectiveness condition and the requirement that a string reference carries `""`. The expected observation is that any inconsistent items are found and listed; when none are found, record the actual observation.

3. Take the request and response in test mode. Check whether `chatId` and `responseChatItemId` are absent as documented. The expected observation is that the absence is classified under a condition the document already describes, and is not recorded as a business fault.

This page addresses only the HTTP integrations and external systems step of order fulfilment and after-sales questions in chain-store site selection. Retrieval and form collection do not constitute authorisation. Business verification, approval, database writes and external synchronisation require separate downstream implementation. Fields not stated in the material remain unknown.
