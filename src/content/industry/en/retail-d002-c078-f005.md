# Chain-store site selection: multi-turn prompts for after-sales questions

## What the documents look like

Site selection and store opening happen before a store starts trading. The work centers on lease negotiation and engineering handover rather than on supervising a store that is already operating. The daily materials are a site evaluation form, a lease letter of intent, a decoration budget, and an opening schedule. Status fields in these materials differ widely. A letter of intent may sit at drafted, pending signature, or signed. A schedule may sit at initial draft, pending confirmation, or confirmed. The task on this page is order fulfillment and after-sales question answering. Multi-turn prompts must carry these materials as context, answer progress and after-sales questions, and preserve gaps where the materials do not support an answer. Data updates are irregular and per store, so the same site can move between states without a fixed cadence.

## Constraints at the multi-turn prompts step

Multi-turn dialogue relies on the memory turns setting to bring earlier conversation into the answer. Customer service and knowledge-base question answering applications usually keep a small number of history turns. A value that is too small may fail to use earlier context. The model's maximum context determines how much content a single request can reference, so long documents combined with follow-up questions need a check against model capability. The reply format stays at default for ordinary question answering. Only when a downstream process needs to read a fixed structure does the format change to json_schema, and the corresponding format requirement must be filled in. Retrieval is not authorization. A retrieval result or a form value does not by itself permit a business action such as signing, payment, or engineering entry.

Hypothetical drill sample, clearly labelled as a paper exercise: a chain headquarters development staff member submits a lease letter of intent stating "Party A is a commercial management company, Party B is a chain headquarters, the subject is a third-floor unit in a shopping mall, the term is five years, the intent deposit has been paid, and the two parties have not yet signed a formal lease contract." A separate opening schedule states "decoration entry date is pending confirmation, opening date is pending confirmation." The draft sentence to be judged is: "The lease contract for this unit has taken effect and decoration has started." Comparing against the source text, deposit payment and contract effectiveness are two different facts, and both schedule items are pending confirmation. The draft sentence lacks evidence of contract effectiveness and entry, so it is unsupported.

## Configuration and implementation checks

| Configuration item | Relevant setting or check on this page | Relation to the sample |
| --- | --- | --- |
| AI model | Check maximum context and multimodal capability | Letter of intent and schedule text must fit within context length |
| Memory turns | Customer service keeps a small number of history turns | Multi-turn follow-up on the same unit references earlier text |
| Reply limit | Limit reply length as needed | Avoid truncating contract status explanation |
| Temperature | Lower values suit customer service and rule-based scenarios | Stable status determination |
| Reply format | Default; select json_schema when a fixed structure is needed | Fill format requirement if downstream reads status fields |
| Hide AI output | Intermediate result passed to a later node | Internal arrangement does not affect the final reply |

A hypothetical starting value for memory turns in this drill is 3, chosen because the follow-up concerns one unit and one schedule within a short exchange; it is compared against the number of prior turns actually needed to resolve the same unit. This is a drill starting point, not an official default. No default value, limit, unit, menu, or global switch is asserted beyond what the documents state.

## Three common errors

1. Treating intent deposit payment as contract effectiveness. Check whether the input contains a "formal lease contract signed" field, compare the letter-of-intent status against the contract status, and only a contract status of signed satisfies the effectiveness condition. The sample shows deposit paid with no signed contract, so the draft sentence is unsupported.
2. Treating a pending schedule as entered. Check the schedule field value, compare "pending confirmation" against "confirmed," and only a confirmed entry date supports an entry statement. In the sample both schedule items read pending confirmation.
3. Treating a retrieval result as authorized execution. Check whether the dialogue only returns material content, compare the answer against the authorization boundary, and only an explicit authorization field supports an execution action. The sample contains no authorization field, so no execution action is supported.

## How to verify the setup

1. Input the hypothetical sample source text above together with the draft sentence, compare the contract effectiveness and decoration entry claims in the draft against the source status fields, and only an "unsupported" notice satisfies the condition. The expected outcome is that the draft sentence is flagged as unsupported; this is a paper expectation, not a completed test.
2. Input consecutive follow-up questions under the same chatId, compare whether the second-round answer references the unit information from the first round, and only a consistent subject and object satisfies the condition. The expected outcome is that the same unit is carried forward; no live run is claimed.
3. Input a paper input of [] to represent an empty result, compare whether the downstream design handles an empty list, and only an explicit empty-result branch satisfies the condition. The expected outcome is that the empty branch is present; the empty result is a paper input, not a claim that a rule-based retrieval returns [].

Missing evidence remains missing. A pending request is not approval, an offered option is not execution, and an unsigned termination is not a completed termination. Where a document field is not provided, the value is unknown.
