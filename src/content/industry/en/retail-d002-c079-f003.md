# Central chain procurement: shared access for after-sales questions

## What the documents look like

Central chain procurement and distribution covers headquarters purchasing and outbound delivery, not store display checks. Order fulfilment and after-sales answering revolve around four document families: centralized procurement contracts, replenishment plans, delivery notes, and store requisition forms. Purchasing records come from ERP, warehouse and wave data from WMS, store sales from POS, and supplier delivery data is recorded separately. Daily and weekly updates coexist, and each store requisition form is generated per order. These materials determine what a shared access entry can reference and what it cannot. A share link solves the access entry point only; it does not change the authorization state of any purchasing, delivery, or claim party. A user who opens a share link has reached a conversation window, not an approved requisition, a dispatched delivery, or a settled supplier claim.

## Constraints at the shared access step

The no-login window is created from the application detail page under publish channels, and the system-generated full link is copied for use. The link name is recorded for display only. Expiry time, QPM, point cap, and identity verification are configurable items, and some parameters are supported only in the commercial edition. Identity verification accepts a POST request root address; initialization, conversation start, and conversation finish each send a request to the corresponding interface. The unified response returns success, and a true value allows the user to continue. The uid value must be returned as a string that excludes specific characters and does not exceed 255 bytes in length; otherwise an Invalid UID error appears. The authToken is appended to the share link as an extra query parameter, and FastGPT carries token=[authToken] in the authentication interface body. Conversation records depend on localId, so the same device and same browser can pull records from the last 30 days, limited to 20 entries, while switching devices or clearing browser cache loses them. These are conditions stated in the official documentation. Retrieval and link access do not constitute business authorization.

## Three common errors

1. Treating the creation of a share link as business authorization. A link can be copied and opened, which is a different fact from whether a requisition form is confirmed or a delivery note is dispatched. The input is the link and the material status; the comparison is between link availability and the document status fields; the observable result is that the two do not derive from each other.

2. Writing a pending status as completed. In the sample, the requisition form is marked "awaiting distribution center confirmation" and the delivery note is marked "awaiting dispatch," while the draft sentence says "confirmed and dispatched." The input is the status fields of the two materials; the comparison is between the draft sentence and the source text; the observable result is that the draft sentence exceeds the status recorded in the materials.

3. Treating retrieval relevance as a permission or entity filter. A similarity value reflects retrieval ranking only and does not distinguish stores, suppliers, or authorization scope. The input is the score returned by retrieval together with the record ownership identifier; the comparison is between the owning entity of the record and the identity of the visitor; the observable result is that a high or low score does not change whether the record may be used by that visitor.

## How to verify the setup

1. For the sample draft sentence, input the requisition form source text "awaiting distribution center confirmation," the delivery note source text "awaiting dispatch," and the draft sentence "confirmed and dispatched." Compare the status expressions of the three. The observable result is that the draft sentence is inconsistent with both source texts on the status field, and that sentence is not supported.

2. For identity verification, input the hypothetical authToken and the identity verification root address, and compare the success value and the uid format returned by the interface. The observable result is that when success is true and uid is a compliant string, the user is allowed to continue; when success is not true, the message is shown; when uid is missing or contains a disallowed character, Invalid UID appears.

3. For the conversation record boundary, input the two situations of the same device with the same browser and a switched device, and compare the record range that can be pulled. The observable result is that the first situation can pull records from the last 30 days, limited to 20 entries, while the second loses the records. This result does not change the authorization state of any document.
