# Returned-goods inspections: workflow routing for after-sales questions

## What the documents look like

Reverse returned-goods inspection handles returned parcels and the grade assigned to the goods. It does not handle outbound picking and packing for new orders. The main data sources are the WMS returns module, platform after-sales records, carrier returns, and the inspection bench. Day-to-day documents include the return putaway order, inspection photographs, the grade determination table, and the resale listing order. Records update per item and per day. Errors here can lead to defective goods being sold a second time, refund disputes, and inventory contamination.

Workflow routing in this setting strings the return putaway order, inspection photographs, grade determination table, and resale listing order into a sequence of nodes that can interact, branch, and pass values onward. The routing step also has to separate what a node already does from what requires a separate business interface or a later process. The form input node enters an interactive state when triggered, records the workflow state, and continues downward after the user completes the interaction. The user selection node also enters an interactive state, and after the user makes a choice the node evaluates that choice and runs the corresponding "yes" branch. Recording the interactive state and hiding the dialog box are existing node behaviors; a separate global state-recording switch is not part of this step. A form collects the information a user fills in. Passing that information to a later retrieval, decision, or interface node is an output handoff check. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval is the act of bringing material back; it does not constitute authorization. Similarity-related settings do not perform entity isolation or permission filtering.

Hypothetical drill sample. On 10 March 2026 a certain after-sales warehouse received return putaway order R-0310-07. The order states the returned item is a "portable juicer 300 ml, white," quantity 1, and the carrier return receipt status is "signed." Inspection photograph Q-0310-07 shows a crack in the cup body. Grade determination table D-0310-07 records the item status as "appearance damaged, pending determination." The draft sentence to be judged is: "This return has completed inspection, the grade is determined as resellable, and the refund can be executed." The question is whether this draft sentence is consistent with the material above.

## Constraints at the workflow routing step

The routing step has to keep three boundaries distinct. First, the interactive state, the dialog hiding, and the state record are documented behaviors of the interaction nodes. They are not controlled by an invented global switch. Second, the values a form collects are inputs. Whether those values later reach a retrieval node, a decision node, or an interface node is a handoff question to check item by item. Third, business actions such as writing an order, backfilling a document, or synchronizing an external status are not completed inside the node. They require a separate interface or a later process.

A user selection branch is a routing decision. When a user picks "scrap," the node evaluates the choice and runs the corresponding "yes" branch. That does not mean the scrap action has been written into the inventory system. The node decides the branch; the external status synchronization still needs its own interface. Similarly, a retrieval result is material brought back. Finding D-0310-07 means the record was retrieved, not that the return has been authorized for resale or refund. Relevance scores are not a category, entity, or permission filter, and a similarity setting does not exclude unrelated businesses or unauthorized records.

## Configuration and implementation checks

| Configuration item | Setting or check on this page | Relation to the sample |
| --- | --- | --- |
| Form input node | Enters the interactive state when triggered, collects required information, passes it to later nodes after submission | Collects the return order number and inspection photograph number fields |
| User selection node | Runs the corresponding "yes" branch after the user makes a choice | Used to branch between "resell" and "scrap" |
| Interactive state check | The state record is an interaction-node behavior; no separate global switch is set | Checks whether R-0310-07 is waiting in the interactive state |
| Output handoff check | Passes collected information explicitly to later retrieval, decision, or interface nodes | Checks whether form output reaches the grade determination branch |
| External action split | Order writes, document backfill, and external status synchronization use a separate interface or later process | Refund execution is not completed inside the node |

Hypothetical trial starting point. The required fields of the form input node are set to three items: return order number, inspection photograph number, and grade determination table number. The reason for this choice is that these three number fields appear in the sample material. The comparison method is to check whether a later node can read these three values after submission. This starting point is a hypothetical setting for this page and is not an official default value.

## Three common errors

1. Treating form submission as completed inspection or refund authorization. In the sample, grade determination table D-0310-07 records only "appearance damaged, pending determination." The draft sentence states "completed inspection, grade determined as resellable, refund executable." The material does not carry a resale conclusion or a refund execution basis, so the draft converts a collected value into a business conclusion.
2. Treating the "yes" path of a user selection branch as already executed. In the sample, if the user selects "scrap," that does not mean the scrap action has been written into the inventory system. The node evaluates the choice and runs the branch; external status synchronization needs its own interface.
3. Treating a retrieval result as a permission or entity filter. In the sample, retrieving D-0310-07 only shows the material was brought back. It does not show the return has been authorized for resale or refund.

## How to verify the setup

1. Input the draft sentence from the sample together with the original text of the three materials. Compare the draft's claims of "completed inspection, resellable, refund executable" against the "pending determination" record in the material. Observe whether the same field shows mutually exclusive values. If the material does not state a resale conclusion, record that as unsupported rather than as a denial.
2. Input the hypothetical form submission values. Compare the return order number, inspection photograph number, and grade determination table number read by the later node against the submitted values. Observe whether the output handoff is complete. If a field is missing, record the gap without inferring a cause.
3. Input the user selection result from the sample. Compare the chosen branch against the later process to see whether they connect. Observe whether the external action is carried by an interface or a later process. Refund and inventory write actions produce no execution result inside the node.
