# Store counts and loss control: HTTP integrations for after-sales questions

## What the documents look like

Store count and loss-control work centers on book-to-physical differences and shrinkage. It does not settle supplier payables, which separates this category from supplier entry and settlement work. The main data sources named in the brief are POS inventory, WMS, monitoring systems, and the SB/T count standard. Day-to-day documents include count sheets, difference analyses, shrinkage write-off approvals, and monitoring review records. The typical roles are the store loss-prevention department, store warehouse keepers, and financial auditors. Data updates monthly or quarterly.

The order fulfillment and after-sales question task passes count differences, write-off status, and review conclusions to external systems through HTTP. The interface itself carries no approval effect. A submitted request stays submitted until the responsible approver acts.

## Constraints at the HTTP integrations step

The HTTP module sends a request to the corresponding address. Params carry path request parameters and are used mostly with GET. Body carries the request body and is used mostly with POST and PUT. Headers carry special information. URL, Params, Headers, and Body can all reference variables through `{{}}`. Variables come from global variables, system variables, and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. chatId and responseChatItemId do not exist in test mode, so an empty value there is a feature of that mode.

Return values are extracted with JSON path syntax or JS object access rules. When the output type is set to string, the value at the corresponding key is converted to a JSON string. The chat endpoint authenticates with an APIKey. When calling chat/completions, passing body.appId in the request body is recommended. The appId priority order is body.appId, then `<apiKey>-<appId>`, then the appId associated with the apikey in the older adaptation. Passed fields such as model and temperature have no effect; the orchestration decides them.

Hypothetical drill sample: a store loss-prevention department on 10 March 2025 compiles the February closed-store count result. The source material reads: "Count sheet A-02 records SKU 1043 with a book quantity of 120 units and a physical count of 96 units, a difference of 24 units; the difference analysis draft is marked 'pending warehouse keeper review'; write-off approval form B-07 has the status 'submitted, pending loss-prevention supervisor approval'." A draft sentence proposes sending a handover request to an external system: "SKU 1043 difference of 24 units is confirmed shrinkage, the write-off approval has passed, please synchronize inventory in the external system as an approved write-off." The draft sentence conflicts with the the source material reads the difference analysis still awaits review, and the write-off approval sits at submitted and pending approval.

## Three common errors

1. Treating "pending loss-prevention supervisor approval" as approval passed and writing an approved write-off into Body. The input is the status text of write-off form B-07. The comparison is between "submitted, pending loss-prevention supervisor approval" and the draft sentence's "the write-off approval has passed." The observable result is that the two statuses do not match.
2. Treating the difference analysis draft's "pending warehouse keeper review" as confirmed shrinkage. The input is the annotation on the difference analysis draft. The comparison is between "pending warehouse keeper review" and the draft sentence's "confirmed shrinkage." The observable result is that the review step is not complete.
3. Treating a missing chatId or responseChatItemId in test mode as an interface fault. The input is a test-mode request. The comparison is between the documented "does not exist in test mode" and the actual return. The observable result is that the empty value belongs to the mode, and a business cause must be sought elsewhere.

## How to verify the setup

1. Input the source text of count sheet A-02 and the draft sentence. Compare the 24-unit difference for SKU 1043 with the 24 units in the draft sentence. Observe that the quantities match while the status descriptions do not.
2. Input the status text of write-off form B-07 and the draft sentence. Compare "submitted, pending loss-prevention supervisor approval" with "the write-off approval has passed." Observe that the draft sentence lacks evidence of completed approval, and the request remains pending verification.
3. Input the annotation on the difference analysis draft and the draft sentence. Compare "pending warehouse keeper review" with "confirmed shrinkage." Observe that the review is not complete, so the difference cannot be submitted to the external system as confirmed shrinkage.
