# Store counts and loss control: shared access for after-sales questions

## What the documents look like

Store counts and loss control work from book-to-physical variance and shrinkage. The main data comes from POS inventory, WMS, monitoring systems, and the SB/T counting specification. Day-to-day documents include count sheets, variance analyses, loss write-off approvals, and monitoring access records. This material updates monthly and quarterly. Unlike supplier entry settlement, this category does not handle supplier payables.

For order fulfillment and after-sales questions, sharing and embedding means handing count sheets and variance analyses to store inventory staff, the loss prevention department, or financial audit for checking. The share entry point solves how a document is reached. It does not settle whether the material is authorized for a given recipient or action.

## Constraints at the shared access step

The no-login window is created from the publishing channel, and the system-generated full link is copied for use. The link identifier is not a business authorization. The anonymous local identifier depends on the same device and the same browser. Records across devices need separate identity and session design. Identity verification is limited to the commercial edition scope, and it follows the official interface return of a success state and a uid.

Assume a paper exercise sample. A store loss prevention department prepares to hand a count variance document to an inventory keeper for checking. The source text of the material reads: "March 2024 closed-store count, Category A SKU 12 items, book quantity versus physical quantity variance on 3 items, the variance analysis sheet has been signed by the inventory keeper, and the loss write-off approval status is pending review." The proposed handoff request reads: "Please send the variance analysis sheet to the inventory keeper through the share link and allow direct modification of the loss write-off approval conclusion." The point to judge: the share link provides an access entry only, and modification of the loss write-off conclusion needs a separate system implementation. A pending review status does not indicate that authorization has been granted.

## Configuration and implementation checks

| Configuration item | Setting or check item for this page | How to check |
| --- | --- | --- |
| Name | Used for record display only, carries no business authorization | Check that the share link name matches the material purpose |
| Expiration time | Set by material use scope; after this time the link cannot be used | Check that the link validity covers the checking window |
| QPM | Maximum visits per user per minute; check against the actual edition | Check visit frequency against the number of users |
| Point cap | Maximum billable data produced by this link; cost belongs to the owning team | Check the usage limit and cost ownership |
| Identity verification | Commercial edition scope; follows the official interface return of success state and uid | Check the POST root address and the authToken concatenation |
| Conversation record boundary | The anonymous local identifier depends on the same device and same browser | Check whether cross-device records have separate identity and session design |

Assume a trial starting point. This exercise sets the expiration time to 7 days, because the checking window is arranged by week. Compare it against the count period marked on the material to confirm coverage of the checking window. This value is a hypothetical starting point, not an official default.

## Three common errors

1. Treating the share link identifier as business authorization. The input is the share link; the comparison object is the authorization state recorded in the material; the observable result is that the link provides an access entry only.
2. Treating a pending loss write-off approval as approved. The input is the loss write-off approval status field; the comparison object is the approval conclusion; the observable result is that pending review does not indicate authorization has been granted.
3. Treating retrieval or a form as authorization execution. The input is a retrieval request or a form submission; the comparison object is the downstream system implementation; the observable result is that business verification, approval, database writes, and external synchronization need separate implementation.

## How to verify the setup

1. For the proposed handoff request in the paper exercise sample, input the share link and the authToken, compare the interface return of success and uid, and observe that identity verification passes and the uid meets the format requirement. This does not indicate that the loss write-off approval has been authorized.
2. For the "loss write-off approval status is pending review" field in the source material, input that field and the proposed modification request, compare the approval conclusion against the authorization boundary, and observe that pending review does not constitute approval and that modifying the conclusion needs a separate system implementation.
3. For the anonymous local identifier boundary, input the same uid access request from a different device, compare the conversation record pull result, and observe that cross-device records need separate identity and session design. This does not claim that an actual test has been completed.
