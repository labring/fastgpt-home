# Store counts and loss control: workflow routing for after-sales questions

## What the documents look like

Store count and loss-control materials revolve around book-to-physical variance and shrinkage. Sources named in the category brief include POS inventory, WMS, and monitoring systems, with SB/T count specifications as a reference. The documents handled day to day are count sheets, variance analyses, damage write-off approvals, and monitoring access records. Update cadence is mainly monthly and quarterly. This differs from supplier entry settlement, which addresses supplier payables; store counting addresses book-to-physical differences and loss.

When order fulfillment and after-sales question answering lands in this category, workflow routing has to deal with fulfillment disputes arising from count variance, the status of write-off approvals, and the way monitoring access records are cited in after-sales answers. These materials share a common trait: many status fields, multiple parties, and multiple periods. Any routing decision has to confirm what authorization state a material is in before it is used. Retrieval and form collection do not themselves constitute authorized execution. Order writes, document backfill, and external status synchronization require a separately connected system implementation.

## Constraints at the workflow routing step

The Form Input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the required interaction the workflow continues downward. Once the user fills in the required information and submits, the node collects the submitted form information and passes it to later nodes. The User Selection node is also a user-interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. When the user makes a choice, the node evaluates that choice and executes the "yes" branch. These are documented node behaviors. Interactive waiting, state recording, and hiding of the dialog box follow the documentation; no separate global state-recording switch, submission-count control, automatic judgment, or snapshot guarantee is documented.

The routing step therefore has to keep two things distinct. The first is what the interaction nodes themselves do: trigger execution, enter interaction state, record workflow state, collect submitted values, and branch on a user choice. The second is what business actions must be implemented elsewhere: writing an order, backfilling a document, synchronizing an external status. A form collects values. Business verification, approval, database writes, and external synchronization need their stated downstream implementation. A pending request is not an approval, an offered option is not execution, and an unsigned termination is not a completed termination.

Hypothetical drill sample. The material text reads: "Store A conducted a count in March 2026. The count sheet records SKU-1001 with a book quantity of 20 units and a physical count of 18 units; the variance analysis marks the difference as pending verification. The damage write-off approval form records a write-off of 2 units for this SKU with status pending review. The monitoring access record states that the access period was after store closing on 31 March 2026, and the requesting person has not signed." The handover request to be judged reads: "Please route a workflow to answer Store A's after-sales question and execute a refund for the 2-unit write-off." This request treats pending review as approved, treats the pending-verification variance as confirmed shrinkage, and lacks a signature and an authorization boundary.

## Configuration and implementation checks

| Configuration item | Setting applicable to this page | Nature |
| --- | --- | --- |
| Form Input node | On trigger, enters interaction state, collects required information, passes it to later nodes after submission | Documented node behavior |
| User Selection node | After the user makes a choice, executes the "yes" branch; verify branch connections one by one | Documented node behavior |
| Interaction state check | Recorded state is interaction-node behavior; no separate global state-recording switch is set | Manual check action |
| Output handoff check | Pass collected information explicitly to later retrieval, judgment, or interface nodes; compare item by item | Manual check action |
| External operation division | Order writes, document backfill, and external status synchronization require a separately connected business interface | Requires separate system implementation |
| Hypothetical trial starting value | For this drill, set the pending-review write-off form to not enter the refund branch, compared against the approved state | Hypothetical trial starting value |

Reason for the hypothetical trial starting value: in the material text the write-off approval form status is pending review, which is mutually exclusive with the approved state on the approval field. The comparison baseline is therefore non-entry into the refund branch. This is a drill starting value chosen for this page, not an official default.

## Three common errors

1. Treating a pending-review write-off form as approved and executing a refund. Input: the write-off approval form in the hypothetical sample. Compare: the value of the approval status field. If the status is pending review, the refund branch should not be entered. Observable result: whether the observed branch path matches the status field value.
2. Treating a pending-verification variance analysis as confirmed shrinkage. Input: the variance analysis in the hypothetical sample. Compare: the variance field annotation. If it is pending verification, it cannot serve as a shrinkage confirmation. The evidence gap must remain open.
3. Treating an unsigned monitoring access record as completed access authorization. Input: the monitoring access record in the hypothetical sample. Compare: the signature field. An unsigned record is unsupported; access cannot be treated as valid on that basis.

## How to verify the setup

1. Input the hypothetical sample material text and the handover request. Compare the write-off approval form status field against the refund branch condition. If the status is pending review, the branch does not enter the refund. The condition is met when the observed branch path matches that condition. This is an expected outcome, not a completed test.
2. Input the hypothetical sample variance analysis and the shrinkage confirmation node. Compare the variance field annotation against the confirmation condition. If it is pending verification, the confirmation node output remains pending verification. The condition is met when the observed output matches the annotation.
3. Input the hypothetical sample monitoring access record and the authorization judgment node. Compare the signature field against the authorization condition. If unsigned, the authorization judgment remains unsupported. The condition is met when the observed judgment result matches the signature field.

For retrieval checks, write the observation and the failure branch. Do not guarantee a first hit, full recall, or an empty result for an unrelated query. An empty-result handoff can be checked with an explicit paper input of `[]` against the downstream design; this does not claim that a fictional rule retrieval necessarily returns `[]`. Libraries across different vector models cannot be jointly associated. Check identifiers first and exclude non-matching items; do not run cross-model retrieval to compare missed recall. The optional paths listed in the overall document flow diagram do not mean every request executes all of them: image retrieval requires a corresponding image input and model capability, and reranking requires a model and must be enabled per settings. A relevance score is not a category, entity, or permission filter, and a similarity setting does not exclude unrelated businesses or unauthorized records.
