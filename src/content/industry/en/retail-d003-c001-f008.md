# B2B marketplaces: workflow routing for copy drafting

## What the documents look like

B2B marketplace matching involves platform operations, suppliers and enterprise buyers. The working documents are enterprise certification materials, inquiry and quotation sheets, electronic contracts, and platform settlement statements. Compared with wholesale market stall transactions, this category has more online certification and electronic contracts, and transactions do not depend on a physical stall. That difference sets the starting point for copy drafting: the entity named in a draft sentence, the quotation target, the contract status and the settlement scope all need a corresponding field in the platform-side materials, and anything the materials do not cover stays unknown. The materials update daily and per order. This page does not infer batch synchronization or real-time triggering from that update frequency.

## Constraints at the workflow routing step

Workflow routing for copy drafting keeps interaction nodes separate from downstream processing nodes. When a form input node triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user fills the required information and submits, the node collects the form information and passes it to later nodes. A user selection node also enters an interaction state, and after the user makes a choice the node evaluates that choice and executes the corresponding "yes" branch. Both are user interaction nodes, both can be added repeatedly, and both trigger execution.

Three layers of constraint follow. The first layer is documented node behavior: the interaction state and the state record are documented behavior of interaction nodes, and no separate global state-recording switch is documented. The second layer is the fields that can actually be configured and the manual comparison actions: verify branch connections one by one, and compare each node output against its input. The third layer is business actions that need a separately connected system: order writes, document backfill and external status synchronization require a business interface or a later process, and the nodes themselves do not perform these actions. The relevance score of a retrieval result does not carry permission or entity-isolation duties, and retrieval does not constitute authorization.

Hypothetical paper exercise sample: the source material reads "Supplier A submitted an inquiry and quotation sheet for Type A packaging material to enterprise buyer B on 1 March 2025, with a quotation validity range through 31 March 2025; the corresponding electronic contract status is pending signature; the platform settlement statement covers the February 2025 accounting period." The draft sentence to be judged is "Supplier A and enterprise buyer B have reached a long-term stable cooperation on Type A packaging material." The comparison can confirm the entities, the material object, the quotation validity range and the contract status. The phrase "long-term stable cooperation" has no supporting field in the source material.

## Configuration and implementation checks

| Configuration item | Setting or check for this page | Relation to the sample |
| --- | --- | --- |
| Form input node | Enters an interaction state when triggered, collects required information, passes it to later nodes after submission | Collects the entity and material-object fields named in the draft sentence |
| User selection node | Executes the corresponding "yes" branch after the user makes a choice | Used to confirm whether the draft sentence proceeds to the next stage |
| Branch connection check | Verify branch connections one by one | Checks the downstream node that the "yes" branch points to |
| Output handoff check | Compare each node output against its input item by item | Compares draft-sentence fields with the source material |
| External action division | Order writes, document backfill and external status synchronization connect to a business interface | Settlement statements and contract status are not written by the nodes |
| Hypothetical trial starting point for this page | Mark the draft sentence as pending comparison and compare it field by field with the source material | The starting point is chosen because the material already gives the entities and the validity range |

The hypothetical trial starting point applies only to the sample on this page and is not an official default value.

## Three common errors

1. Treating the state record of an interaction node as a configurable global switch. Entering an interaction state and recording state in the form input and user selection nodes is documented behavior, and a configuration should not contain a state-recording switch that the documentation does not describe.
2. Treating retrieval relevance as a permission or entity-isolation mechanism. Similarity does not exclude unrelated businesses or unauthorized records, and retrieval results still need entity identifiers checked separately.
3. Treating an evaluative phrase in a draft sentence as an already verified fact. In the sample, "long-term stable cooperation" has no corresponding field in the source material and stays unknown.

## How to verify the setup

1. Input the sample source material and the draft sentence, then compare whether the entities, material object, quotation validity range and contract status in the draft sentence match the source. If the draft sentence contains an evaluative phrase the source does not cover, that phrase should be marked as lacking evidence.
2. Input the sample's "electronic contract status is pending signature" and the draft sentence's "cooperation reached," then check the signature status and the evidence of cooperation separately. The materials provide no supporting evidence that cooperation has been reached, so mark that statement as unsupported and pending verification. Keep the cooperation status undetermined from these materials; pending signature alone does not resolve it.
3. Input an empty-result handoff scenario, use the explicit paper input [] to check the downstream design, and observe whether the downstream node handles it through the no-match branch. Do not claim that a fictional rule retrieval necessarily returns an empty result.

Libraries using different vector models cannot be associated together. When checking, verify identifiers first and exclude those that do not match, then record the actual observation. Do not run cross-model retrieval to compare missed recalls.
