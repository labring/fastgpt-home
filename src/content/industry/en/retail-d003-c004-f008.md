# Temu semi-managed sellers: workflow routing for copy drafting

## What the documents look like

Temu semi-managed seller operations differ from fully managed supply in one structural way: the seller maintains overseas inventory and completes shipment rather than only supplying goods to the platform. The daily document spine therefore includes the product declaration form, the overseas inventory table, the price declaration, and the platform fulfillment order. These carry product attributes, inventory quantities, declared prices, and fulfillment status respectively. The brief lists Temu Seller Center, overseas warehouse WMS, logistics tracking, and procurement cost sheets as sources, with a stated update frequency of daily and per order. This page does not derive batch synchronization, full synchronization, real-time triggering, or transaction-triggered mechanisms from that frequency.

For product and marketing copy drafting, the working inputs normally come from declaration fields and inventory status inside those documents. Whether a draft sentence can stand depends on whether the material states the subject, the object, the status, and the valid scope. Fluency of the draft sentence carries no weight in that judgment.

## Constraints at the workflow routing step

In FastGPT v4.17.2, the Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the workflow continues after the user completes the interaction. The node collects the required form information the user submits and passes it to later nodes. The User Selection node is also a user interaction node with the same interaction-state behavior; when the user makes a choice, the node evaluates that choice and executes the "yes" branch. The documented behavior covers entering the interaction state, recording state, hiding the dialog box, and continuing after interaction. The documentation does not describe a global control switch, a submission count limit, or automatic judgment capability for either node.

Forms collect values. Order writes, document backfill, and external status synchronization require a separate business interface or a downstream flow. Semantic recall and relevance scores in retrieval do not carry permission or entity isolation duties, and a retrieval hit does not constitute authorization.

Hypothetical paper exercise sample: the material text reads, "The declared subject of this product is the on-sale batch in warehouse A; the declared price is 12.00 yuan; the declared valid scope is 1 June 2024 to 30 June 2024." The draft sentence to be assessed reads, "This product is supplied long term at a stable price." The comparison object is the declaration original against the draft sentence; the comparison item is the validity period and the price statement; the expected observation is that "long term" in the draft exceeds the 30 June 2024 boundary stated in the original and is therefore unsupported.

## Configuration and implementation checks

| Configuration item | Setting on this page | Verification method |
| --- | --- | --- |
| Form Input node | Collects product identifier, declaration period, and price field needed for drafting | After submission, compare each output item against the input item |
| User Selection node | Sets a "yes" branch for whether the draft sentence is adopted | Verify branch connections one by one against the selection result |
| Interaction state check | Enters the interaction state and records state on trigger | Observe dialog hiding and restoration; no additional switch is set |
| Output handoff | Passes collected values to a later retrieval or judgment node | Compare downstream input fields against upstream output fields |
| External action split | Order writes and external synchronization connect to separate interfaces | Confirm this workflow does not perform that action |
| Retrieval scope | Checks materials within the target scope that carries access rights | Record actual observations of hits and empty results |

## Three common errors

1. Treating "long term" in the draft sentence as already supported by the declaration form. The declaration states a validity period ending 30 June 2024, and the draft sentence exceeds that boundary, so the statement is unsupported and the evidence gap must be recorded.
2. Treating a retrieval hit as an authorization result. A relevance score is not a category, entity, or permission filter, and a hit record cannot show that the drafting subject has the right to use that material.
3. Treating the "yes" branch of the User Selection node as completed business approval. The selection only determines the flow direction; approval and writes require downstream implementation, and a pending review does not indicate approval has been granted.

## How to verify the setup

1. Input the declaration original and the draft sentence from the hypothetical sample above, compare the validity period field against the draft sentence wording, and observe whether "long term" exceeds the 30 June 2024 boundary. That observation satisfies the expected unsupported judgment.
2. Input the subject field from the hypothetical sample, compare it item by item against the subject of each retrieval hit, and where the subject does not match, exclude that hit and record it. Do not run cross-model retrieval comparison for missed recall.
3. Use a paper input of an empty result to check the downstream handoff design, and observe how the downstream branch handles empty input. Do not claim that retrieval necessarily returns an empty result.

All three checks address the primary task of whether the draft sentence is supported by the material. They do not extend into identity certification or report analysis.
