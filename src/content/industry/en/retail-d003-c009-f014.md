# Amazon FBM fulfillment: model connections for copy drafting

## What the documents look like

Amazon FBM fulfillment places fulfillment and the returns address under the seller rather than a platform warehouse, and the work does not depend on platform warehouse inspection. The working records for this category come from Amazon Seller Central, carrier systems, ERP orders, and customer service email. The daily documents named for this category are the order picking list, the shipment confirmation, the returns address setting, and the logistics tracking sheet. These records update per order and daily. This page addresses only model connections and configuration for product and marketing copy drafting, and it does not infer batch synchronization, full synchronization, or transaction-triggered behavior from that update frequency.

For copy drafting, the practical consequence is that a draft sentence can only be checked against the material actually on hand. The order picking list, the shipment confirmation, the returns address setting, and the logistics tracking sheet each carry a limited set of fields. A returns address setting records an address, not a returns policy. A shipment confirmation records a tracking number, not a delivery-time promise. When a draft sentence asserts a delivery speed or a returns condition, the comparison target is the material text, and material that does not state the claim leaves the claim unsupported.

## Constraints at the model connections step

From V4.17.0, AI Proxy is a required dependency. The App service and an Admin service that reuses App/Service configuration must both set `AIPROXY_API_ENDPOINT` and a non-empty `AIPROXY_API_TOKEN`; missing either item causes startup validation to fail. Older OpenAI environment variables and a single-model custom request address do not replace these two settings. `AIPROXY_API_ENDPOINT` holds the AI Proxy service root address, for example `http://aiproxy:3000`, without an appended `/v1`. The system needs at least one language model and one index model to work normally.

Model capability is checked against the input the application requires. Multimodal input, tool calling, and thinking configuration are verified separately. Application parameters are set in the application or node configuration, and it is not safe to assume that a same-named field on a compatible chat interface overrides orchestration.

Hypothetical paper exercise, not executed: Material text one reads, "Order picking list FBM-2026-0312, object is a self-fulfilled order, shipment date March 12, 2026, carrier is an overseas local carrier, tracking number is registered in the shipment confirmation." Material text two reads, "Returns address setting is a United States local returns address; the returns address is maintained on the returns address setting page." Proposed draft sentence under review: "This product supports nationwide next-day delivery, and returns require no reason." The comparison scope is limited to these two material sentences and the proposed sentence. The material does not state a delivery-time promise or a returns policy, so those two elements of the proposed sentence are unsupported.

## Three common errors

1. Treating "nationwide next-day delivery" in the draft sentence as a delivery-time promise supported by the material. The input is material text one and the draft sentence. The comparison is whether either text states a delivery-time promise. The material does not state one, so this element is unsupported and cannot be recorded as confirmed.
2. Treating "returns require no reason" as equivalent to the returns address setting. The input is material text two and the draft sentence. The comparison is whether either text states a returns policy. A returns address setting and a returns policy are different fields. The material does not state a returns policy, so this element is unsupported.
3. Using a same-named field on a compatible chat interface to override an application orchestration parameter. The input is the application or node configuration and the parameters the drafting task requires. The comparison is whether the parameter is set in the application or node configuration. When it is not set, a same-named field cannot be assumed to take effect.

## How to verify the setup

1. Input material text one, material text two, and the proposed sentence "This product supports nationwide next-day delivery, and returns require no reason." Compare whether the proposed sentence states a delivery-time promise and a returns policy. Neither material sentence states these two items. The expected result is that both elements of the proposed sentence are marked unsupported, with the evidence gap retained.
2. Input the configured value of `AIPROXY_API_ENDPOINT` and the documented example format. Compare whether `/v1` or `/chat/completions` has been appended. The expected result is that the configured value matches the documented format and that `AIPROXY_API_TOKEN` is non-empty and consistent with the server. When they do not match, record the item as configuration pending correction.
3. Input the enabled state of language models and index models in the system model list. Compare whether at least one of each is enabled. The expected result is that both records exist and are enabled. When either is missing, record that the documented usage condition is not met, without inferring a specific error message or an automatic business action.
