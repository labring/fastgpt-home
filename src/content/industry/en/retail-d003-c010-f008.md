# JD POP seller operations: workflow routing for copy drafting

## What the documents look like

JD POP third-party store operations work around open-platform dispute rules and warranty-period service records. The documents handled day to day include product information sheets, dispatch-time commitments, dispute handling forms and warranty-period service records. These materials are produced on a daily or per-order basis and form the evidence base that copy drafting can cite.

Copy drafting for products and marketing requires extracting the subject, object, status and valid scope from those documents before deciding which statements may enter a draft. The materials differ in what they can support. A product information sheet identifies a product and its warranty terms. A dispatch-time commitment identifies a payment condition and a time range. A dispute handling form records a dispute stage. A warranty-period service record records service within a warranty period. Merging fields from two different documents into one sentence produces a claim whose source cannot be traced to a single field.

Workflow routing in this setting connects scattered document fields and draft determinations into steps that can be reviewed. The form input node is a user interaction node: when triggered, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the interaction and submits, the node collects the required form information and passes it to subsequent nodes. The user selection node is also a user interaction node: when triggered, the conversation enters an interaction state, the workflow state is recorded, and when the user makes a choice, the node evaluates that choice and executes the corresponding branch. Both nodes can be added repeatedly and trigger execution.

## Constraints at the workflow routing step

Hypothetical paper exercise sample: a POP store operator needs to draft marketing copy for a batch of products. The source text available for checking is: "Product information sheet (number A-001) states that the warranty period for this product is twelve months, counted from the day after receipt." "Dispatch-time commitment (number B-002) states dispatch within forty-eight hours after payment." The draft sentence to be assessed is: "This product carries a twelve-month warranty and ships within forty-eight hours after payment." This sample only illustrates the checking method and does not refer to any real store or product.

The constraint is that every factual claim in the copy must trace back to a specific document field. The warranty subject is product information sheet A-001; the counting object is the day after receipt; the valid scope is twelve months. The dispatch subject is commitment B-002; the condition is after payment; the scope is forty-eight hours. The draft sentence combines fields from two different documents, so subject, object, period and field must be confirmed item by item. If a field is not stated in the materials, that field is unsupported in the draft, and a similar expression in another document does not substitute for it.

Interaction nodes record workflow state and continue after the user completes the interaction. Information collected by form input is passed to subsequent nodes, and user selection executes the branch based on the feedback. A copy drafting workflow can set the document number, field name and draft sentence as required form fields, and set "consistent" and "to be verified" as the two user selection branches. Order writing, document backfill and external status synchronization require a separate business interface or subsequent process; the nodes themselves do not perform those business actions.

| Form input required fields | Document number, field name, original draft sentence | Collects the minimum information set needed for checking |
| User selection branches | Two branches, "consistent" and "to be verified" | Executes the corresponding subsequent node based on the choice |

The configuration table centers on field checking for the hypothetical sample. The reason for choosing the hypothetical starting value is that the source text explicitly states twelve months, and the comparison method is a character-by-character comparison with "twelve months" in the draft sentence. This value is only the starting point for this hypothetical exercise and is not an official default.

## Three common errors

1. Treating fields from different documents as a single factual statement after merging. The draft sentence cites both the warranty period and the dispatch time; if A-001 and B-002 are not checked separately, fields belonging to two subjects may be mistaken for one source. The check is to list the document number and field name corresponding to each claim separately and observe whether any expression cannot be traced back.

2. Treating an unstated field as confirmed. The materials do not state extended-warranty conditions beyond the warranty start method; if the draft sentence contains an "extended warranty" expression, it is unsupported. The check is to search the source text for that field and observe whether an explicit value appears.

3. Treating the interaction node's state recording as a global state switch. The form input and user selection nodes recording workflow state is behavior of the node itself; no separate global state recording switch is set. The check is to review the node configuration for an item mistaken for a global switch and observe whether it is a node-level setting.

## How to verify the setup

- Verification one: input the hypothetical sample's source text and draft sentence, compare "twelve-month warranty" in the draft sentence with "warranty period is twelve months" stated in A-001, and observe whether subject, object, period and field match. If they match, that clause meets the checking condition; if the material does not state it, record it as to be verified.

- Verification two: input the draft sentence "ships within forty-eight hours after payment," compare it with "dispatch within forty-eight hours after payment" stated in B-002, and observe whether the condition and scope correspond. If the draft sentence is rewritten with another time limit, record it as unsupported.

- Verification three: input a handoff request asking that the checking result be passed to a subsequent node. Observe whether the fields collected by form input are passed downstream completely and whether the user selection branch executes according to "consistent" or "to be verified." If output and input fields do not match, record the gap. For empty-result handoff, a clearly stated paper input empty list can be used to check the downstream design; no claim is made that a fictional rule retrieval necessarily returns an empty list.

The above verifications are paper reasoning only, not actually executed, and do not constitute test conclusions about any real store, product or platform.
