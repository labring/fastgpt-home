# On-demand retail fulfillment: workflow routing for copy drafting

## What the documents look like

On-demand retail store fulfillment processes online orders on a per-minute, per-order cadence. This differs from periodic stocktaking, which runs on a scheduled inventory cycle. The documents handled on this page are the instant order, the picking list, the out-of-stock report, and the delivery exception form. Data sources named in the brief include Douyin instant retail, the Meituan or JD Daojia backend, store inventory, and rider tracking. Product and marketing copy drafting extracts checkable facts from these documents, such as the item name, specification, quantity, and substitution result actually picked for a given order in a given period.

Per-minute and per-order updates mean that the inventory state, substitution result, and delivery status cited by a draft may change after the drafting moment. Copy drafting may cite only fields already stated in the material. It may not infer real-time availability, a promised delivery time, or guaranteed stock from the update frequency. The out-of-stock report and the delivery exception form record exception facts. Copy must not rewrite a substitution or delay recorded on an exception form as normal fulfillment.

## Constraints at the workflow routing step

Within workflow routing, the Form Input node and the User Selection node are user interaction nodes. When either is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The Form Input node collects required information and, after submission, passes that information to subsequent nodes. The User Selection node, after the user makes a choice, executes the corresponding branch. The interaction state record is behavior of the interaction node; no separate global state-recording switch is documented.

Collected information must be explicitly passed to later retrieval, judgment, or interface nodes, and output must be compared item by item against input. Order writes, document backfill, and external status synchronization require a separate business interface or a downstream process. The interaction node itself does not perform these actions. The same-vector-model requirement for a retrieval library applies only to the association conditions of that library. It does not extend to requiring business-registration sites or other external systems to use the same model. Libraries using different vector models cannot be jointly associated; the correct step is to check identifiers and exclude non-matching ones, not to run cross-model retrieval to compare missed recalls. Optional paths shown in a document's overall flowchart do not mean every request executes all of them: image retrieval requires a corresponding image input and model capability, and reranking requires a model and must be enabled per settings. An empty-result handoff can be checked against an explicit paper input of [].

## Configuration and implementation checks

Hypothetical drill sample: the source material reads, "March 12, 2026, instant order A-0312; the customer ordered 2 bottles of a 500 ml brand soda water; the picking list records 2 bottles of the same specification actually picked; no out-of-stock report was generated." The draft sentence to be judged is, "This store has ample stock of this item; orders ship immediately." This sentence concerns stock status. The material records only the picked result of a single order and does not state store-wide inventory, so the sentence is unsupported. A second item is a handoff request: "Please synchronize the delivery status of order A-0312 to the external platform." The material states no synchronization interface or authorization, so the request lacks an executable basis.

| External action division | Order writes, backfill, and synchronization require a separate interface | Confirm whether a corresponding interface and authorization record exist |

## Three common errors

1. Writing a single order's picked result as the store's overall stock status. The material records only that order A-0312 picked 2 bottles. The draft sentence "ample stock; orders ship immediately" lacks inventory evidence. It is unsupported and cannot be judged as verified.

2. Treating the interaction node's state record as a global state switch. Form Input and User Selection enter an interaction state and record workflow state after triggering. The documentation does not describe a global state-recording switch, so configuration should not invent one.

3. Treating a handoff request as an executed action. The request asks to synchronize delivery status. The material states no interface, authorization, or execution record. The request remains pending and does not constitute completed synchronization.

## How to verify the setup

- Verification one: Input the hypothetical material text and the draft sentence "This store has ample stock of this item; orders ship immediately." Compare the evidence the draft sentence requires against the field scope stated in the material. The material contains only the order number, item, specification, picked quantity, and the fact that no out-of-stock report was generated. It contains no store inventory field, so the judgment is unsupported. Only if the material separately states an inventory field for the same store and the same period can further comparison proceed.

- Verification two: Input the hypothetical handoff request "Please synchronize the delivery status of order A-0312 to the external platform." Compare whether the interface and authorization record the request requires exist. The material states no interface identifier, authorization scope, or execution result, so the judgment is pending verification and is not treated as synchronized. If an interface and authorization record are later supplied, check the execution trace then.

- Verification three: Input a paper empty result of [] together with the downstream node design. Compare whether the downstream is designed to accept an empty input, and observe whether an unsupported default value or automatic completion appears downstream. An empty result does not mean a fictional rule retrieval will necessarily return []; it is used only to check how the downstream accepts empty input.
