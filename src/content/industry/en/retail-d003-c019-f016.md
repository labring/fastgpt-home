# On-demand retail fulfillment: interactive forms for copy drafting

## What the documents look like

On-demand retail fulfillment processes online orders by the minute rather than through periodic stock counts. The working documents are the immediate order, the picking list, the out-of-stock report, and the delivery exception sheet. Data arrives from the on-demand retail channel, the delivery platform back end, store inventory, and rider tracking, and it refreshes at minute level or per order. Copy drafting for products and marketing draws its material from these documents: product name, specification, stock status, and fulfillment conditions. When a drafted sentence cites material that disagrees with the picking list or the out-of-stock report, the advertised item and the deliverable item can diverge, and a customer refund can follow. Whether the fields collected during copy drafting are complete determines whether later nodes can continue from the same material.

## Constraints at the interactive forms step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution waits until the user completes the interaction. After the user fills the required information and submits, the node collects the submitted form values and passes them to later nodes. The node does not carry its own business database function. The user selection node also enters the interaction state and executes a branch according to the user's choice; it does not act as a personnel directory or a business data selector. Field validation, business approval, write-back, and bulk operations belong to external systems or later nodes as needed.

For copy drafting, the form can carry material submission and selection only. A similarity setting is not a permission or entity filter, and retrieval is not authorization.

Hypothetical paper exercise: on 10 June 2025 a picker at a supermarket home-delivery store submits an out-of-stock report. The material text reads: "Immediate order A, product name: a brand 500 ml mineral water, specification: 500 ml × 1 bottle, stock status: store out of stock, substitute: same brand 1 L pack." The picking list for the same batch states: "the order item is 500 ml mineral water, picking status: not picked." The sentence to be judged is: "This order's mineral water is guaranteed to arrive in the original 500 ml specification." The subject required for judgment is immediate order A, the object is 500 ml mineral water, the status is store out of stock, and the effective scope is that store on 10 June 2025. The drafted sentence shares the subject, period, and field with the out-of-stock report, and the value direction is opposite, so the sentence is unsupported.

## Configuration and implementation checks

| Configuration item | Setting relevant to this page | Basis and check method |
| --- | --- | --- |
| Form input node | Collect product name, specification, stock status, substitute, date range | Documented behavior: submitted values pass to later nodes |
| Required-field check | Record the gap when any field is missing; submit after completion | List the information this task cannot omit; test the missing case and the completed case separately |
| User selection node | Offer "may continue" or "pending verification" branches for the drafted sentence | Documented behavior: the node executes a branch according to the user's choice |
| Interaction state | On trigger, record workflow state and wait for interaction | Documented behavior: execution continues after the interaction completes |
| Downstream division of work | Field validation, business approval, write-back handled by external systems or later nodes | Documented behavior: the node does not carry its own business database function |
| Hypothetical trial starting point | The drafted sentence enters the pending verification branch when its value differs from the material on the same field | Starting point chosen for this exercise; compared against the material text value |

The starting point above is a hypothetical trial value, not an official default. It is chosen because the material text states store out of stock on the same field, and the comparison method is a field-by-field reading of subject, object, status, and date range.

## Three common errors

1. Treating a relevance score as a permission or entity filter, and using a similarity threshold to exclude unrelated businesses or unauthorized records. Retrieval is retrieval; authorization requires a downstream implementation.
2. Reading an out-of-stock report and producing "guaranteed to arrive in the original specification" without comparing the value direction on the same subject, period, and field, so an unsupported statement is written as supported.
3. Treating the user selection node as a personnel directory or business data selector, ignoring the documented statement that the node executes a branch according to the choice.

## How to verify the setup

1. Input the out-of-stock report text from the hypothetical exercise together with the drafted sentence "This order's mineral water is guaranteed to arrive in the original 500 ml specification." Compare whether subject, object, status, and date range correspond. When all four correspond and the value on the same field runs in the opposite direction, the pending verification branch is entered and the condition is met.
2. Input the picking list text for the same order and compare the picking status field with the deliverable state described in the drafted sentence. When picking status is not picked and the drafted sentence describes the item as deliverable, the judgment is unsupported and the condition is met.
3. Input a clearly labelled paper input of an empty result `[]` and check whether the downstream design keeps a gap record. When the downstream design does not treat the empty result as authorization or as a verified conclusion, the condition is met. When the downstream design releases the drafted sentence directly, record it as a failure branch.

These checks state expected behavior. No test has been run, and no deployment, approval, or refund is claimed.
