# After-sales repairs and reships: workflow routing for copy drafting

## What the documents look like

After-sales repairs and reships aim to restore a product to use. The case does not close through a direct refund, which differs from refund-only disputes. This difference shapes what copy drafting may draw on: draft copy can describe a repair or reship path, and cannot present a refund closure as the default outcome.

The main data comes from the after-sales system, the order system, repair sites, and the spare-parts warehouse WMS. Everyday documents include repair requests, reship orders, inspection reports, and spare-parts outbound orders. Statements about handling method, time limits, or parts source should map to fields in these documents. Content not stated in a document stays unknown and cannot be filled in by the copy.

Records update per order and daily. This page's routing function does not depend on update frequency, so batch synchronization and real-time mechanisms are out of scope. The most time-consuming steps are deciding between repair and reship, coordinating parts, and tracking customer confirmation. These are also the points where draft copy most easily introduces unsupported commitments.

## Constraints at the workflow routing step

At this step, workflow routing gathers the material that copy drafting needs and passes it to later nodes. The official documents state that a form input node triggers an interaction state, collects required information, and after submission passes the collected information to subsequent nodes. A user selection node, once the user makes a choice, executes the corresponding "yes" branch. The interaction state and the state record are behaviors of these nodes themselves. No separate global state-recording switch, submission count, automatic judgment, or snapshot guarantee is described.

Retrieval libraries can be associated together only when they use the same vector model. Libraries with different vector models cannot be associated together; the identifier is checked and non-matching libraries are excluded, without running cross-model retrieval to compare missed recalls. A relevance score does not carry permission or entity-isolation functions, and retrieval itself does not constitute authorization. Order writes, document backfill, and external status synchronization require a separate business interface or a later process; form nodes only collect values.

Hypothetical drill sample: the source material reads "Repair request WX-0417, product is a household water-purifier filter cartridge assembly, customer repair status is accepted, inspection conclusion is filter seal ring aging, handling recommendation is reship of the seal ring part, spare-parts outbound order CK-0417 shows 12 units of this part in stock, outbound status is pending outbound." The draft sentence to be judged is "This order has confirmed reship of the seal ring part, expected delivery within three working days." The subject needed for judgment is the order corresponding to WX-0417, the object is the seal ring part, the status field is outbound status, and the effective scope is that single order. The material states outbound status as pending outbound and does not state a delivery time limit, so the handling method in the first half of the draft sentence has a corresponding material field, while the time limit in the second half is unsupported.

## Three common errors

1. Treating pending outbound as completed outbound. The material says "outbound status is pending outbound." If the draft sentence states confirmed reship plus a delivery time limit, the input is the outbound status field, the comparison object is the material's stated value, and the observable result is that the draft sentence and the material value do not match.
2. Treating retrieval relevance as a permission filter. The input is one retrieval request, the comparison object is the returned records against the intended retrieval scope, and the observable result is that the relevance setting does not exclude out-of-scope records, so unauthorized records can still enter the results.
3. Treating form collection as business completion. The input is the submitted form values, the comparison object is the actual outbound status field on the outbound order, and the observable result is that the form was submitted while outbound status remains pending outbound, so the business action has not occurred.

## How to verify the setup

1. Input the sample material text and the draft sentence, then compare the handling method in the draft sentence against the material's handling recommendation field. If both point to the same object and the material supports that handling method, the handling-method portion meets the condition. The delivery time limit portion is recorded as unsupported because the material does not state it.
2. Input an explicit paper empty result []. Compare whether the downstream node design handles the empty result through its own branch. If the downstream design does not treat the empty result as containing records, the empty-result handoff design meets the condition.
3. Input the vector model identifiers of two libraries and compare whether the identifiers match. If they do not match, exclude joint association and record the actual observation. Only when they match can association checking proceed, and no recall effect is inferred from that match.

All three checks are paper-based reasoning, not actually executed, and do not constitute a conclusion that testing, deployment, or a business action has been completed.
