# Retail checkout and loyalty: interactive forms for copy drafting

## What the documents look like

Copy drafting for retail checkout and loyalty promotion draws its material from the point-of-sale system, the member CRM, the payment platform and the price-tag system. Promotion price tags set the usable range of price statements in draft copy. Member points rules set the boundary of benefit descriptions. The checkout daily report and the exception refund form supply facts about transaction status and the stage of refund handling. This category does not handle short-shelf-life inventory; the copy object is price and member benefit.

Daily and per-shift update frequency means a promotion price tag or a points rule can change while copy is still moving through drafting. The drafting step needs to check the material version so that a price or benefit condition from a previous shift is not written into current copy. Copy errors in this category produce price complaints, cash shortfalls and overages, and member benefit disputes. The checkout supervisor, CRM operations and financial audit each focus on price, benefits and cash respectively.

The four document types differ in what they can support. A promotion price tag states a price condition for a period. A member points rule states accumulation and redemption conditions. A checkout daily report states recorded transaction outcomes. An exception refund form states a refund handling stage. None of these documents by itself establishes that a draft sentence is approved, that a benefit condition is confirmed, or that a refund is complete.

## Constraints at the interactive forms step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues downward after the user completes the interaction. The node collects the information the user fills in and passes it to later nodes after submission. It does not carry its own business database function. The user selection node also triggers the interaction state and executes a branch according to the user's selection. It is not a personnel directory or a business data selector.

For copy drafting, the form needs to collect the draft sentence to be judged, the corresponding material source text, the material version and the applicable period. Field validation, business approval, write-back and batch operations are implemented as needed in external systems or later nodes. The interaction node itself does not carry out these business actions. The interaction state only means the node is waiting and recording workflow state. It does not indicate a submission count limit, automatic judgement or snapshot guarantee.

Hypothetical paper exercise sample. Material source text: "This store's member points rule (March 2025 version) states: a member who presents the member code at the checkout counter accumulates 1 point for every 1 yuan spent; points may be used in the next purchase at 100 points to offset 1 yuan." Draft sentence: "A member accumulates 1 point for every 1 yuan spent, and points can offset cash in the same purchase." The subject needed for judgement is the member, the object is point accumulation and offset, the state is the March 2025 version of the rule, and the applicable range is use in the next purchase. The draft sentence writes "use in the next purchase" as "offset in the same purchase," which does not match the applicable period in the material source text.

## Three common errors

1. Writing a benefit condition not stated in the material as confirmed. Suppose the material source text states only "points may be used in the next purchase at 100 points to offset 1 yuan," and the draft sentence reads "points can offset cash in the same purchase," treating same-purchase offset, which the material does not state, as supported content. Check: input the material source text and the draft sentence, compare the two applicable periods "in the next purchase" and "in the same purchase," and the draft sentence fails the condition when it contains a period the material does not state.

2. Treating a pending-review status as approved. Suppose the handover request reads "promotion price tag copy pending review by the store checkout supervisor," and the form records it as "review passed," writing a pending-review status as a completed approval. Check: input the handover request text, compare the two statuses "pending review" and "review passed," and the record fails the condition when the statuses do not match.

3. Treating the user selection node as a business data selector. Suppose the form uses the user selection node to let the writer choose a "points rule version," and the node is treated as a query against the member CRM rule library, which goes beyond the scope described in the node documentation. Check: input the node purpose description and the actual filled content, compare whether the node only executes branch judgement, and the setup fails the condition when business data query appears.

## How to verify the setup

1. Input the material source text, the draft sentence and the applicable period field from the hypothetical paper exercise sample. Compare "offset in the same purchase" in the draft sentence with "use in the next purchase" in the material source text. When the draft sentence contains an applicable period the material does not state, judge it as unsupported, and the form should keep that gap rather than record it as confirmed.

2. Input the handover request text "promotion price tag copy pending review by the store checkout supervisor." Compare the status recorded in the form with the status in the request text. When the form records "review passed," judge the status as inconsistent, keep "pending review" and wait for later handling.

3. Input the purpose description of the user selection node and the actual filled content. Compare whether the node only executes a branch according to the user's selection. When a member CRM rule library query or a business data write appears, judge it as beyond the node documentation and move it to a later node or an external system.

These checks describe expected observations. They do not report a completed test, an approval, a refund or any other business action. Where a material field is not provided, the field remains unknown, and the gap is kept rather than filled by assumption.
