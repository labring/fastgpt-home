# Trade and FX administration: interactive forms for copy drafting

## What the documents look like

Copy drafting for foreign-exchange receipt, settlement and trade directory work draws on a narrow set of materials: foreign-exchange receipt slips, trade contracts, invoices and foreign-exchange business registration records. The category centres on the authenticity of foreign-exchange funds and the underlying trade background, which distinguishes it from letter-of-credit document examination that reviews a full document set. Work proceeds transaction by transaction, with monthly aggregation. Any payer identity, amount, trade object or settlement status that appears in drafted copy is expected to stay consistent with those materials.

The interactive form and user-selection nodes sit at the input stage of this task. The form input node triggers an interaction state, records the workflow state, and continues only after the user completes the interaction. The user-selection node evaluates the user's choice and executes the corresponding branch. These nodes collect values and route branches. Field validation, business approval, database writes and external synchronisation require implementation in external systems or downstream nodes.

## Constraints at the interactive forms step

Inputs needed for copy drafting must be collected explicitly. Missing fields cannot be filled by inference. The collection subject, contract number, invoice number and registration status are required for checking promotional sentences in drafted copy. When these fields are absent, the interactive node cannot advance and downstream nodes receive no usable value.

Hypothetical paper exercise sample (constructed on paper, not a real customer):

Material text one: a foreign-exchange receipt slip for a hypothetical trading company names the payer as "HYPOTHETICAL OVERSEAS BUYER LTD" and the payee as "Hypothetical Export Enterprise", amount USD 12,000, date 2025-03-10, description "goods payment".

Material text two: a trade contract (number HT-2025-031) names the seller as "Hypothetical Export Enterprise", the buyer as "HYPOTHETICAL OVERSEAS BUYER LTD", the subject matter as "household textiles", total price USD 12,000, signing date 2025-02-28.

Material text three: foreign-exchange business registration records show the registration status for this transaction as "registered", and the registered entity matches the contract seller.

Draft sentence to be assessed: "The enterprise has completed trade directory registration with the State Administration of Foreign Exchange, the receipt funds have been credited, and it can undertake all types of export settlement business."

Assessment points: the materials support only that this transaction is registered and that the receipt slip payer matches the contract buyer. They do not state a directory classification result for the enterprise, and they do not state that funds have been credited. The phrase about undertaking all types of export settlement business exceeds the material scope. The draft sentence is unsupported and requires rewriting or additional evidence.

## Three common errors

1. Treating the form input node as a business database. The node collects entered values and passes them downstream. It does not perform approval, write-back or batch operations. In the sample, registration status must be checked manually; the node does not determine it automatically.

2. Describing the user-selection node as a personnel directory or business data selector. The node executes branches according to the user's choice, and the branch content must be implemented in downstream nodes.

3. Using a draft sentence to assert facts the materials do not state. The sample draft sentence includes "funds have been credited" and "can undertake all types of export settlement business", neither of which the materials state. Both are unsupported.

Corresponding executable checks:

- Check one: input the three sample materials and the draft sentence, and compare each assertion in the draft sentence against material fields. Observable result: any assertion not stated in the materials is marked unsupported.

- Check two: input a form submission missing the contract number and compare whether the interaction completes. Observable result: the interaction does not complete and downstream nodes receive no contract number value.

- Check three: input the sample material completeness state and compare the user-selection branch taken. Observable result: the complete branch is triggered and the pending branch is not.

## How to verify the setup

Verification must target the copy drafting primary task and use the complete sample given above.

- Verification one: input the three material texts and the draft sentence, and compare sentence by sentence. The clause "has completed trade directory registration with the State Administration of Foreign Exchange" is not the same field as "registered" in material three; the materials do not state a directory classification result, so this clause is unsupported. "The receipt funds have been credited" is not stated in the materials and is unsupported. "Can undertake all types of export settlement business" exceeds the material scope and is unsupported. Satisfied condition: all three are marked unsupported and a rewriting direction is given.

- Verification two: input a form submission missing the invoice number and compare the interaction state. Observable result: the interaction remains in a waiting state and does not proceed; after the invoice number is completed, the interaction completes and the value is passed to downstream nodes. Satisfied condition: both the missing-field and completed-field behaviours are observable.

- Verification three: input the sample material completeness state and compare the user-selection branch. Observable result: the complete branch is triggered and the pending branch is not. Satisfied condition: the branch taken matches the input state.

Fields not stated in the materials remain unknown. Do not supply authorisation or effectiveness clauses to obtain a definite answer. Retrieval and vector association do not carry permission or entity isolation duties. Libraries across different vector models cannot be associated together; check identifiers only, exclude non-matching items, and record actual observations.
