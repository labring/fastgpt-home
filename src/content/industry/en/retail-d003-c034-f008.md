# Export tax rebate filings: workflow routing for copy drafting

## What the documents look like

Export tax rebate filing work happens after goods leave the country and centers on matching tax vouchers. The main data comes from the electronic tax bureau, the export rebate filing system, customs electronic information, and financial ledgers. Documents handled day to day include the export tax exemption and rebate filing form, the export customs declaration, purchase invoices, and foreign exchange receipt vouchers. Typical roles are foreign trade enterprise finance staff, tax accountants, and documentation clerks.

These materials set the boundary for what product and marketing copy may state. A customs declaration records the exported goods name and quantity. A purchase invoice records the purchased item name and amount. A foreign exchange receipt voucher records the payment status. When drafting copy, the workflow compares each proposed sentence against the fields actually present in these documents and decides whether a claim is supported.

## Constraints at the workflow routing step

Workflow routing in this task does two things: it collects the materials to be checked and the draft sentence, and it passes the comparison result to later nodes. The Form Input node enters an interaction state when triggered, collects required information, and passes that information to later nodes after submission. The User Selection node evaluates the user's choice and executes the corresponding "yes" branch. Both nodes record workflow state, and the dialog box is hidden during interaction.

Hypothetical paper exercise sample: a documentation clerk at a foreign trade enterprise submits the following source text for checking — "The export customs declaration records the exported goods as stainless steel insulated cups, quantity 1,200 pieces, declaration date 15 March 2024"; "The purchase invoice records the item name as stainless steel insulated cups, quantity 1,200 pieces, invoice date 10 March 2024." The draft sentence to be judged is: "This product has been exported in a quantity of 1,200 pieces, with an export date of March 2024." The comparison targets are the exported goods name, quantity, and date fields. The authorization boundary is limited to this declaration and its corresponding purchase invoice; no foreign exchange receipt voucher is provided.

The constraints are these: the nodes only collect and pass information, and do not perform tax verification or rebate approval. Fields not recorded in the materials remain unknown. When the draft sentence refers to an "exported" status, the declaration date on the customs form is not the same as the actual export date and requires separate checking.

## Configuration and implementation checks

| Configuration item | Relevant setting or check on this page | Relationship to the sample |
| --- | --- | --- |
| Form Input node | Collect the source material text and the draft sentence, set as required | The declaration and invoice text plus the draft sentence serve as input |
| User Selection node | Set a "materials complete" branch, execute the "yes" branch | The sample lacks the receipt voucher, so the "no" branch records the gap |
| Interaction state check | Confirm the node enters the interaction state and records it | The dialog is in the interaction state before submission |
| Output handoff check | Pass collected information to later retrieval or judgment nodes | The draft sentence is compared field by field against the materials |
| External action separation | Rebate filing and voucher synchronization connect to separate business interfaces | This page does not write to the tax system |

Hypothetical trial starting point: set the material completeness threshold to "both the customs declaration and the purchase invoice are present." The reason for this choice is that the sample provides only these two material types, and the comparison object is whether the receipt voucher is missing. This starting point is a setting for this paper exercise and is not an official default value.

## Three common errors

1. Writing the customs declaration date into the copy as the export date. In the sample, the declaration records only the declaration date of 15 March 2024 and does not record the actual export date, so the draft sentence "export date of March 2024" lacks direct support.
2. Judging receipt status when no foreign exchange receipt voucher is provided. The authorization boundary of the sample does not include the receipt voucher, so any statement about receipt being complete or incomplete is unsupported.
3. Treating information collected by the Form Input node as completed tax verification. The node's behavior is limited to collection and handoff; rebate filing and voucher matching require a separate business interface.

## How to verify the setup

1. Input the sample source material text and the draft sentence, then compare the "1,200 pieces" in the draft sentence against the quantity fields recorded on the customs declaration and the purchase invoice. When all three agree, the quantity statement is supported by the materials. When the date field in the draft sentence does not match the declaration date on the customs form, record it as pending verification.
2. Input the missing receipt voucher state from the sample and compare the branch direction of the User Selection node's "materials complete" decision. Taking the "no" branch and recording the gap satisfies the condition. Entering the verification-passed branch directly does not satisfy it.
3. Input an empty result handoff scenario and check the downstream node design against a paper input of []. The downstream node should retain the empty result and record it, without fabricating retrieval return content. If the downstream node automatically fills in unprovided fields, the condition is not satisfied.
