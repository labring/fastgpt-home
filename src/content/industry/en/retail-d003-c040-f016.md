# Customer-service knowledge: interactive forms for copy drafting

## What the documents look like

This page covers knowledge-base maintenance for e-commerce customer service and after-sales work, at the copy-drafting stage for product and marketing text. The working materials are FAQ entries, reply templates, product parameter tables and escalation tickets. They arrive from the customer-service system, product detail pages, after-sales issue statistics and quality spot checks, and are handled by customer-service supervisors, knowledge-base operators and product operators. Knowledge-base maintenance is preparation of question-and-answer material in advance; it does not approve refunds. The drafting stage therefore checks whether the available material supports a proposed sentence.

Two features of this material shape the drafting step. First, the parameter table and the FAQ entry can describe the same product with different wording, so a draft sentence may rest on a term the source does not use. Second, escalation tickets and handover requests carry their own status, and a request that is still pending is not an approval. Update frequency for these materials is weekly or monthly; this page does not introduce batch synchronization or real-time triggers.

## Constraints at the interactive forms step

The Form Input node is a user-interaction node. When it is triggered, the conversation enters an interactive state, the workflow state is recorded, and execution waits until the user completes the interaction, then continues downward. After the user fills in the required information and submits, the node collects the submitted form information and passes it to later nodes.

The User Selection node is also a user-interaction node. It enters the interactive state on trigger, and when the user makes a choice the node judges that choice and executes the "yes" branch.

Neither node carries business-database functions. Field validation, business approval, write-back and bulk operations are implemented as needed in external systems or in later nodes. A relevance score or retrieval result is not an authorization or entity filter, and retrieval does not grant permission.

Hypothetical paper exercise sample. The source material reads: "This insulated cup has a capacity of 500 milliliters, the body is 304 stainless steel, and the applicable temperature range is minus 20 degrees Celsius to 100 degrees Celsius." The proposed draft sentence reads: "This insulated cup has a capacity of 500 milliliters, the body is 304 stainless steel, and it can withstand minus 20 degrees Celsius to 100 degrees Celsius." Compared with the source, the capacity and material fields agree. The temperature field differs in wording: the source says "applicable temperature range," the draft says "can withstand." Whether the two expressions are equivalent requires manual checking. The sample provides no basis for equivalence, so this point stays pending verification. The handover request reads: "Please confirm whether the above temperature wording can be used directly in the product copy." This request is a pending matter; it does not indicate that approval has been granted.

## Configuration and implementation checks

| Configuration item | What it covers on this page | How to check it |
| --- | --- | --- |
| Form Input node | Collects the fields needed to check the proposed sentence; passes them to later nodes after submission | After trigger, the conversation enters the interactive state; after submission, check whether the fields reach later nodes |
| Required information | Three items: source material text, proposed draft sentence, scope of the check | Test the missing-item and completed states separately; with a missing item the conversation should remain in the interactive state |

| Interactive state | Records workflow state on trigger and waits for interaction | After interaction completes, check whether execution continues downward |
| Downstream division of labour | Field validation, business approval and write-back are implemented as needed in external systems or later nodes | Check whether this node is being treated as a business database |
| Hypothetical starting point for this exercise | The temperature wording in the draft is treated as pending verification | Compare with the source phrase "applicable temperature range"; this is not a default value |

## Three common errors

1. Writing "applicable temperature range" into the draft as "can withstand temperature range." Input: the source material text and the proposed draft sentence. Comparison: the wording of the two temperature fields. Observable result: the wordings differ and the sample provides no basis for equivalence, so the point is recorded as pending verification.

2. Treating a pending handover request as an approval already granted. Input: the handover request text. Comparison: the request status against an approval status. Observable result: the request text contains no approval record, so the copy cannot be treated as passed on that basis.

3. Treating the Form Input node as a business database. Input: the fields submitted through the node. Comparison: the node's stated role against a database role. Observable result: the node only collects and passes information; business approval and write-back require external systems or later nodes.

## How to verify the setup

1. Input the source material text and the proposed draft sentence from the hypothetical sample. Compare the capacity, material and temperature fields. Observable result: capacity and material agree, the temperature wording differs. The condition is met when the temperature field is marked pending verification.

2. Input the missing-item and completed form states. Compare whether the conversation remains in the interactive state before and after submission. Observable result: with a missing item it remains in the interactive state; after the item is supplied and submitted, execution continues downward.

3. Input the two branch options of the User Selection node. Compare which branch the node executes. Observable result: choosing "yes" executes the "yes" branch; choosing the other option does not execute that branch.

All of the above is a paper-based check design. It has not been run, and no real submission, approval, refund or synchronization action has occurred.
