# Marketplace returns: workflow routing for copy drafting

## What the documents look like

Platform refund and return handling in this category centers on four document types named in the brief: refund applications, return shipping labels, quality inspection photos, and refund approvals. Ordinary platform refunds occur continuously per order and may not connect to a promise made in a single livestream session, which is the stated difference from concentrated livestream after-sales processing. The main data sources are the platform after-sales backend, customer service chat, WMS receiving records, and payment refund records. Typical practitioners are e-commerce customer service staff, after-sales specialists, and warehouse quality inspectors. Errors here can lead to platform intervention, consumer complaints, and loss of payment funds.

For copy drafting, the practical question is whether a proposed sentence about a product can be supported by the material at hand. That material records order identifiers, product names, return status, and approval opinions. Whether a promotional statement holds depends on whether the source text itself states the relevant subject, object, and effective scope. The materials do not automatically supply a cause of damage, a quality conclusion, or an authorization basis.

## Constraints at the workflow routing step

The Form Input node and the User Selection node are both user interaction nodes. When either is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The Form Input node collects required information and, after submission, passes the collected values to subsequent nodes. The User Selection node evaluates the user's choice and executes the corresponding branch. Recording state during interaction is behavior of the interaction node itself; the documents do not describe a separate global state recording switch.

Collected values must be explicitly passed to later retrieval, judgment, or interface nodes. Order writes, document backfill, and external status synchronization require a separately connected business interface or downstream process. Retrieval is not authorization, and a relevance score does not act as a permission or entity filter.

Hypothetical paper exercise sample: the source text reads "Refund application number A-17, product is a vacuum flask, return reason is a broken sealing ring on the lid, inspection photo shows the sealing ring is cracked, refund approval opinion is agree to refund." The draft sentence to be assessed is "This product was confirmed by platform inspection to have a sealing ring broken due to transport." The source text states the inspection photo and the broken condition but does not state the cause. The phrase "due to transport" has no corresponding field in the material, so it is unsupported and the evidence gap must be recorded rather than treated as established.

## Configuration and implementation checks

| Configuration item | Setting for this page | How to check |
| --- | --- | --- |
| Form Input node | Collect refund application number, product name, return reason | After submission, verify the output fields are passed to later nodes |
| User Selection node | Set a branch for "does the material support the draft sentence" | Verify the "yes" branch connection and execution one by one |
| Interaction state | Triggered and recorded by the interaction node | Check continued execution after entering the interaction state |
| Output handoff | Pass collected information to retrieval or judgment nodes | Compare each output against its input |
| External operation split | Order writes and document backfill connect to a business interface | Check whether a downstream implementation is declared |
| Retrieval scope | Target retrieval scope must contain the source text | Confirm access rights and that the material is in scope |

## Three common errors

1. Writing the broken condition from the inspection photo as damage caused by transport. The source text states only that the sealing ring is cracked and does not state the cause. The check input is the source text and the draft sentence; the comparison is whether the same field shows explicitly mutually exclusive values; the observable result is that the draft sentence contains content not stated in the material.

2. Treating the refund approval opinion "agree to refund" as a product quality conclusion. The approval opinion belongs to a refund handling field and is not the same field as the cause of damage. The check input is the approval opinion and the draft sentence; the comparison is the field each one points to; the observable result is that the two do not form a support relationship.

3. Treating a retrieval result as an authorization basis. Relevance does not carry permission or entity isolation. The check input is the retrieval return and the draft sentence; the comparison is whether the material sits within an accessible target scope; the observable result is that an access gap is recorded when access rights are missing.

## How to verify the setup

1. Input the source text and draft sentence from the hypothetical sample, compare whether the draft sentence contains a field not stated in the material, and record a gap when unsupported content appears rather than judging it established.

2. Input refund application number A-17 and the product name, compare whether the form output is passed to later nodes, and check the connection when a field is missing.

3. Input a paper empty result, compare whether the downstream design can accept an empty output, and record a pending item when the handoff is undefined.

Retrieval checks describe observation and failure branches only and do not guarantee a first hit or full recall. Libraries using different vector models cannot be associated together; verify identifiers first, exclude non-conforming ones, and record the actual observation.
