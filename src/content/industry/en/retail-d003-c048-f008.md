# Parcel labels and handoffs: workflow routing for copy drafting

## What the documents look like

Parcel handoff happens at the point where a package leaves the warehouse, and the central question is carrier scan responsibility. The documents for this category include electronic waybills, handoff manifests, pickup scan records and exception item registers. Sources include the courier system, WMS dispatch, the GB/T courier service standard and carrier billing. Data updates per batch and per day. For copy drafting, this means any statement about timeliness, pickup status or handoff responsibility can only be checked against the fields and statuses actually recorded in those documents. Fields the documents do not carry remain unknown.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the conversation continues only after the user completes the interaction. Once required fields are filled and submitted, the node collects the submitted values and passes them to downstream nodes. The User Selection node also enters an interaction state, records workflow state, and after the user makes a choice, evaluates that choice and executes the corresponding "yes" branch. The recorded interaction state is behavior of the interaction node itself. No separate global state-recording switch is documented. Information collected by a form must be explicitly passed to later retrieval, judgment or interface nodes. Order writing, document backfill and external status synchronization require a separate business interface or a later process. Retrieval checks describe observations and failure branches; they do not guarantee a first-item hit or full recall. Libraries built on different embedding models cannot be associated together; identifiers must be checked first and non-matching items excluded. Optional paths shown in the overall workflow diagram do not mean every path executes on every request.

Hypothetical paper exercise: A warehouse dispatch role retains a paper handoff manifest whose text reads: "This batch contains 40 parcels. The carrier completed pickup scanning on 10 March 2025. The scan record shows 38 parcels picked up and 2 parcels registered as exceptions." A draft sentence awaiting judgment reads: "All parcels in this batch completed pickup on that day." The comparison object is the manifest and scan record above; the scope is the 40 parcels of that batch on that date. The word "all" in the draft conflicts with the scan record of 38 picked up and 2 exceptions. The draft sentence is not supported by the material.

## Configuration and implementation checks

| Configuration item | Relevant setting or check on this page | Link to the sample |
|---|---|---|
| Form Input node | Enters interaction state on trigger; collects required fields and passes them downstream | Collects the batch and date fields of the copy to be checked |
| User Selection node | Executes the corresponding "yes" branch after the user chooses | Routes a "continue checking" choice to the matching branch |
| Interaction state check | Recorded state is behavior of the interaction node; no separate global switch | Confirms the interaction node itself records state |
| Output handoff check | Collected values must be explicitly passed to later retrieval or judgment nodes | Passes batch and date to the copy-check node |

## Three common errors

1. Treating the draft sentence "all parcels completed pickup on that day" as a verified conclusion. Check: input the manifest and scan record text above, compare the word "all" in the draft with the 38 picked up and 2 exceptions in the record, and observe that the two statuses do not agree.
2. Treating interaction state recording as a global switch that can be enabled separately. Check: input the Form Input and User Selection node documentation, compare whether any global state-recording switch is documented, and observe that the documents describe only the interaction node recording its own state.
3. Treating retrieval relevance as a permission or entity isolation mechanism. Check: input the retrieval node configuration and the access scope description, compare the relevance setting with permission fields, and observe that relevance carries no permission or entity filtering.

## How to verify the setup

1. Input the hypothetical sample's manifest and scan record text together with the draft sentence. Compare the draft word "all" with the record's 38 picked up and 2 exceptions. If the statuses disagree, the draft sentence is unsupported and the gap must be recorded.
2. Input the Form Input and User Selection node documentation. Compare whether any global state-recording switch is documented. If the documents describe only the interaction node recording its own state, no such switch should be claimed.
3. Input the retrieval node configuration and the access scope description. Compare the relevance setting with permission fields. If the relevance setting contains no permission or entity filtering, retrieval results do not represent granted authorization, and permission judgment needs a separate implementation.
