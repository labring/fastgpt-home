# Douyin storefront operations: workflow routing for copy drafting

## What the documents look like

Douyin storefront shelf operations differs from live-room operations in that it does not depend on the rhythm of a single live session. Attention sits on product cards and the store experience score. The main data sources are the Douyin store workbench, the Douyin e-commerce learning center, selected alliance data, and logistics interfaces. Day-to-day documents cluster around product qualification pages, experience score breakdowns, shipping violation appeals, and store announcements. The most time-consuming work involves maintaining the experience score, handling out-of-stock and missing-inventory cases, and supplementing product qualifications. These documents update daily or per order, so the qualification state that copy drafting relies on can shift with each order or each day of data.

For the product and marketing copy drafting task, workflow routing has to collect the subject, object, state, and validity scope from those documents as transferable information, then hand it to later nodes that judge whether a proposed sentence is supported by the material. The form input node and the user selection node are both user interaction nodes. When triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The form input node collects required information and passes it to later nodes. The user selection node judges the user's choice and executes the "yes" branch.

## Constraints at the workflow routing step

Copy drafting checks must use the same subject, the same period, and the same field. A statement that is not stated, or that has only related-stage evidence, counts as unsupported or pending verification. It cannot be recorded as a denial or a conflict. Pending review does not demonstrate a lack of operating authority. Signing, reaching cooperation, and contract effectiveness are three distinct facts. A quotation validity period does not indicate a supply period. Recording state is the interaction node's own behavior; no global state-recording switch is set or claimed.

Hypothetical drill sample: the material text supplied for checking reads, "This store obtained sales authorization for a brand's products on March 1, 2025; the authorization is valid until December 31, 2025; the authorized scope is series A products of that brand." The proposed sentence to be judged reads, "This store has obtained long-term authorization for the brand's full series of products." The source subject is "this store," the object is "series A products of that brand," the state is "sales authorization obtained," and the validity scope is "March 1, 2025 to December 31, 2025." The proposed sentence widens the object to "full series" and changes the term to "long-term," which does not match the source authorization scope. This difference is a simultaneous mismatch in the object and validity-scope fields and should be recorded as unsupported.

Order writes, document backfill, and external status synchronization require a separate business interface or a later process; the interaction node itself does not perform those business actions. The same-vector-model requirement for a retrieval library cannot be extended to mean that business registration sites or other external systems must use the same model. Libraries across different vector models cannot be associated together; check identifiers first and exclude those that do not conform. An empty-result handoff can use an explicit paper input of [] to check the downstream design; it cannot be claimed that a fictional rule retrieval necessarily returns [].

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point for this page | Reason and comparison method |
| --- | --- | --- |
| Form input node required fields | Subject, object, state, validity scope | These four fields correspond to all information needed for judgment in the sample; missing one prevents a same-field comparison |
| User selection node branch | The "yes" branch connects to the copy checking node | The document states that the "yes" branch executes after the user makes a choice; verify branch connections one by one against the checking node |
| Interaction state check | Enters interaction state after triggering | Check dialog hiding and state recording against the document explanation; no global state-recording switch is set |
| Output handoff check | Form information passed to later retrieval or judgment nodes | Compare output and input item by item; confirm collected information is clearly passed to later nodes |
| External action division | Order writes, document backfill, external sync marked as separately connected interfaces | The interaction node does not perform these business actions; a separate business interface or later process is required |

## Three common errors

1. Treating "full series" in the proposed sentence as a synonym for "series A products" in the source. The input is the sample source text and proposed sentence above; the comparison is the object field "series A products" against "full series"; the observable result is an inconsistent object scope, which should be recorded as unsupported.
2. Treating "long-term authorization" as a reasonable summary of the source validity period. The input is the source "valid until December 31, 2025" and the proposed sentence "long-term authorization"; the comparison is the validity-scope field; the observable result is an inconsistent term, which should be recorded as unsupported.
3. Treating information collected by the form input node as completed business verification. The input is the information handoff after form submission; the comparison is the node output against later business interfaces; the observable result is that the node only passes information, while order writes or external synchronization are not executed, which should be recorded as requiring separate system implementation.

## How to verify the setup

1. Using the hypothetical drill sample above, input the material source text and the proposed sentence, compare the object field "series A products" against "full series," and observe that the two do not match, judged as unsupported. The expected phenomenon is that the checking node outputs a record of object mismatch; no actual test is claimed.
2. Using the same sample, input the source validity "until December 31, 2025" and the proposed sentence "long-term authorization," compare the validity-scope field, and observe that the terms do not match, judged as unsupported. The expected phenomenon is that the checking node outputs a record of term mismatch.
3. Use a paper input of [] to check the empty-result handoff design and observe whether the downstream node handles it through the empty-result branch. The expected phenomenon is that the downstream design can accept empty input; no claim is made that a fictional rule retrieval necessarily returns []. Retrieval checks record only actual observations and failure branches, and do not guarantee a first-hit, full recall, or that unrelated queries must be empty.
