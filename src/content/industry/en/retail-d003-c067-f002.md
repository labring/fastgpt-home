# Group-buy leader operations: context limits for copy drafting

## What the documents look like

Group-buy leader operations revolve around community pickup nodes and commission settlement. The working materials for this category are leader agreements, commission tables, pickup lists, and community announcements. Copy drafting for products and marketing draws subject, audience, and validity scope from those materials, then produces publishable text. The materials refresh daily or per group, so a commission rate, pickup window, or announcement wording cited in a draft can change between batches; drafting must check the current version of the material.

Compared with cold-chain acceptance in fresh produce, leader operations manage community nodes and commissions, and do not perform cold-chain quality inspection directly. The main data sources are the community group-buy backend, leader chat groups, order details, and after-sales records. Typical participants are the group-buy platform, leader business developers, and fulfillment sites. Errors here lead to leader attrition, wrong or missing deliveries, and community complaints.

For copy drafting, the practical consequence is that a draft sentence must be traceable to a specific material version. A commission percentage, a pickup window, and an announcement date can each appear in several documents, and the drafting step needs to confirm which version is current before a sentence is treated as supported.

## Constraints at the context limits step

Context and tokens decide how much material a model can see in one request and how far retrieved content is trimmed. The reply limit controls output length and is a different concept from the model maximum context. The knowledge-base citation limit is counted in tokens, so a long single passage can lose its tail. Memory rounds change the input content, and the same question can produce different inputs with empty history and with history. A structured reply format requires complete fields and successful parsing; text length alone does not show that parsing succeeded.

Hypothetical paper exercise sample: the source material reads, "For this group, period 12, the commission rate for fresh produce is 8 percent; the pickup window is 18:00 to 20:00; the announcement publication date is 10 April." The draft sentence under review reads, "Fresh produce commission for this group is 8 percent; please complete pickup before 18:00." The item to decide is whether this draft sentence is consistent with the material.

The material states a pickup window of 18:00 to 20:00. The draft sentence narrows that to a deadline before 18:00. The material does not support that narrowing, so the correct judgement is "not supported by the supplied material," not "contradicted," because the material does not state an exclusive alternative value for the same field.

A second boundary applies to retrieval. A relevance score is a filtering threshold, not a category, entity, or permission filter. It does not exclude unrelated businesses or unauthorized records. Retrieval is not authorization. Forms collect values; business verification, approval, database writes, and external synchronization need their stated downstream implementation. No scheduled trigger or hidden control should be assumed.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison method |
| --- | --- | --- |
| Reply limit | No fixed value | Observe whether the draft sentence fully states subject, object, and time window; compare before and after truncation |
| Memory rounds | Keep a small amount of history | Compare the input content for the same question with empty history and with history |
| Citation limit | Counted in tokens, starting point covers the sample source text | Check whether the sample source text is cited in full; compare content before and after trimming |
| Minimum relevance | Keep the documented default | Takes effect only under semantic retrieval or result reranking; compare candidates before and after filtering |
| Reply format | Default text | Keep default when the draft sentence needs no fixed structure |
| Question optimization | Decide by observed effect | Compare retrieval input and elapsed time before and after enabling |

These rows are implementation checks for this page, not claims about official defaults. The starting points are chosen because the sample source text is short and the draft sentence is a single line; the comparison method is stated for each row so that a reviewer can repeat the observation on paper.

## Three common errors

1. Treating the reply limit as the full context window. The reply limit constrains output length; the model maximum context is the length of content a single request can reference. These are separate quantities, and a draft that fits the reply limit can still have lost source material to context trimming.

2. Treating minimum relevance as an entity or permission filter. The value is a filtering threshold. It does not exclude unrelated businesses or unauthorized records, and lowering or raising it does not grant or remove access to any record.

3. Treating RRF as a switch that can be turned on. RRF is the fusion step for mixed retrieval results, not an independent configuration item. It combines multiple retrieval paths after they return candidates.

## How to verify the setup

1. Input the hypothetical sample source text and the draft sentence, then compare the draft phrase "before 18:00" with the source phrase "18:00 to 20:00." If the draft narrows the pickup window and the material does not support that narrowing, the draft sentence is judged not supported by the supplied material. The expected observation is a mismatch between the stated window and the draft deadline; the material remains the reference.

2. Input the same question twice, once with empty history and once with history retained, then compare the two input contents. If memory rounds cause a difference in the input, record that difference and check whether it affects which material the draft sentence draws on. The expected observation is a recorded input difference, not a claim about which version is correct.

3. Use a clearly labelled paper input of an empty citation result, `[]`, to check the downstream design, and observe how the downstream node receives an empty result. Do not claim that a fictional rule retrieval necessarily returns an empty result. The expected observation is the downstream node's handling of the empty input, which remains unknown until that handling is documented or observed.

Across these checks, missing evidence stays missing. A pending request is not approval, an offered option is not execution, and an unsigned termination is not a completed termination. Where the material does not state a field, the field is unknown, and the draft sentence is recorded as unsupported or pending verification rather than as contradicted.
