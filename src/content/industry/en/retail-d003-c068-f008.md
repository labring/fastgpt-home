# Group-buy presale orders: workflow routing for copy drafting

## What the documents look like

Presale group-buy collection takes orders first and then organizes purchasing and fulfillment. This differs from leader relationship management, which centers on maintaining coordinator ties. The documents handled at this stage include the presale product table, the collection result, the purchasing plan and the cut-off notice. Typical operating roles are platform operations, purchasing planning and supply chain scheduling. Errors surface as stockout refunds, fulfillment delays and leader complaints. Data sources include mini-program orders, supplier inventory, leader feedback and warehouse routing. Update frequency is daily or per session.

For copy drafting, the material in those four documents is turned into checkable copy sentences and handoff requests. A product name, specification, price basis and cut-off time come from the presale product table. The collection result and purchasing plan set the quantity context. The cut-off notice fixes the time boundary. Copy that goes beyond these stated values creates a mismatch between what the customer reads and what the order and purchasing records support.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the required fields and submits, the node collects the submitted form information and passes it to subsequent nodes. The User Selection node is also a user interaction node. It enters the interaction state in the same way, and when the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch.

In copy drafting, Form Input can collect the product name, specification, price basis and cut-off time. User Selection can confirm whether to submit for manual review. Order writing, document backfill and external status synchronization require a separate business interface or a later flow. The interaction nodes themselves do not perform those actions.

Assume a paper exercise sample. The source material reads: "Presale product table: session of 10 June 2026, product name 'high-mountain baby cabbage', specification 500 g per portion, presale unit price 3.9 yuan, cut-off time 9 June 20:00; the supplier inventory table shows 1,200 portions available for this session; the purchasing plan states that purchasing follows the collection result and does not state a supply guarantee ceiling." The draft sentence to be judged is: "This session's baby cabbage has unlimited supply, and orders can still be added after cut-off." The subject, object, state and effective range needed for judgment are all present in the source: the subject is the platform's presale for this session, the object is baby cabbage, the state is 1,200 portions in inventory with no stated supply guarantee ceiling, and the effective range ends at the cut-off time.

## Configuration and implementation checks

| Configuration item | Assumed starting point for this page | Reason and comparison method |
| --- | --- | --- |
| Form Input fields | Product name, specification, presale unit price, cut-off time | Corresponds to presale product table fields; compare field by field against the source material |
| User Selection branch | Submit for manual review / return for missing material | The document states the "yes" branch executes after a choice; check the branch connection |
| Output receiving node | Pass form information to the copy check node | The document requires information to be passed to subsequent nodes; compare output against input |
| Inventory basis check | Use the supplier inventory table value of 1,200 portions as the comparison value | The assumed starting point comes from the sample source; compare against the draft phrase "unlimited" |
| Cut-off time check | 9 June 20:00 | Stated in the sample source; compare against "orders can still be added after cut-off" |
| External write division | Connect a separate business interface | Order writing and synchronization are not inside the interaction nodes; list as pending implementation |

## Three common errors

1. Treating a Form Input submission as an order already written. Submission only passes information to subsequent nodes; order writing requires a separate business interface. Check: input the sample form submission record, compare whether a downstream write node exists, and observe that the order status remains unknown when no write node is connected.

2. Treating a User Selection of "submit for manual review" as review approval. The choice only executes a branch and does not produce an approval conclusion. Check: input the branch selection record, compare whether an approval result field exists, and observe that the status remains pending review, not approved.

3. Writing the 1,200-portion inventory as "unlimited." The source states no supply guarantee ceiling and does not state unlimited supply. Check: input the supplier inventory table source text and the draft sentence, compare the quantity and wording, and observe that the draft sentence is not supported.

## How to verify the setup

- Verification one: input the assumed sample source material and the draft sentence "This session's baby cabbage has unlimited supply, and orders can still be added after cut-off." Compare the inventory table value of 1,200 portions and the cut-off time of 9 June 20:00 against the draft wording. The condition is met when the draft sentence is marked as unsupported and returned for missing material.

- Verification two: input the form submission record. Compare whether the downstream node receives the four items of product name, specification, unit price and cut-off time. The condition is met when all four items appear in the downstream input.

- Verification three: input the User Selection of "submit for manual review." Compare the branch direction against the approval field. The condition is met when the flow enters the review branch and the approval status remains pending review. All three verifications describe expected observations only and were not actually executed. If retrieval returns an empty result, a paper input of [] can be used to check the downstream receiving design, without claiming that a fictional rule necessarily returns empty.
