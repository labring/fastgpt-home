# Cross-border payment reviews: multi-turn prompts for copy drafting

## What the documents look like

Payment risk control for cross-border standalone stores centers on card network disputes and receiving accounts, not parcel status. Day-to-day materials include payment chargeback notices, fraudulent order lists, invoices, and carrier proof of delivery. Sources span the receiving account backend, standalone store orders, carrier delivery records, and customer service email. Copy drafting must cite the subject, amount, time, and status contained in these materials, and judge whether a proposed sentence has support.

Materials update daily or per order. That frequency affects citation timeliness and does not change the functional boundary of this page.

A chargeback notice may record an order identifier, a dispute amount, a reason code, and a date. A carrier record may record the same order identifier, a delivery date, and a recipient signature. A fraud order list may mark an order as high risk without stating any delivery outcome. These are different document types with different fields, and a sentence drafted from one type is not automatically supported by another.

## Constraints at the multi-turn prompts step

Multi-turn dialogue sends prior messages, knowledge base references, and the current question to the model together. The memory turns setting controls how many earlier rounds are referenced; a larger value carries more content and increases consumption. The prompt must state the material scope, the answering task, and how to handle missing evidence. The model must not write in business facts that were not provided.

When cited materials enter the context, the model may treat a high-similarity entry as grounds. A relevance score expresses retrieval similarity only and does not perform permission or entity isolation. Retrieval is not authorization. A retrieval library requires the same embedding model before entries can be associated together; libraries using different embedding models must first have their identifiers checked and be excluded, and cross-model retrieval is not executed to compare results.

Reply format follows downstream needs. Selecting json_schema requires filling in the corresponding format requirements and checking the returned structure. Thinking budget belongs to thinking configuration and is unrelated to the reference length limit.

Hypothetical paper exercise sample: the following material text and draft sentence are hypothetical for this page and do not come from real records.

Material text one: "On March 10, 2025, order A-1042 received a card network chargeback notice, dispute amount 120 USD, reason code goods not received."

Material text two: "On March 12, 2025, the carrier delivery record shows order A-1042 was signed for by the recipient on March 6."

Draft sentence: "All orders from this store are delivered within 48 hours, and a chargeback has never occurred."

## Configuration and implementation checks

| Configuration or check item | Hypothetical starting point for this page | Reason and comparison method |
| --- | --- | --- |
| Memory turns | Keep a small number of prior rounds | Customer service and knowledge base question scenarios usually keep few prior rounds; compare with a run that keeps no history to observe whether unrelated early rounds are referenced |
| Temperature | Take a lower value | Copy needs to cite materials stably, and a lower value reduces divergence; compare wording stability against a higher value output |
| Reply format | Keep default | This task has no fixed-structure downstream read requirement; switching to json_schema requires filling in format requirements and checking the returned structure |
| Prompt material scope | State that only materials provided in this session may be used | Prevents the model from writing delivery or chargeback facts that were not provided; compare against an output with no stated scope to observe statements outside the materials |
| Citation check | Manually compare the draft sentence against the material text | A relevance score does not judge whether material supports a promotional sentence; check subject, object, and status sentence by sentence |
| Multimodal recognition | Decide whether to enable based on model capability | Image recognition depends on model capability; when not enabled, image links are not converted into model input |

## Three common errors

1. Treating a relevance score as grounds for material support. Input is the draft sentence and the retrieval-returned entries; compare whether the entry text contains the subject, object, and status stated in the draft sentence, and observe whether promotional wording appears that the materials do not record.
2. Treating memory turns as a permission boundary. Input is a follow-up question across sessions; compare the range of history messages carried in, and observe whether records outside the current materials are referenced.
3. Treating thinking budget as the reference length limit. Input is the thinking configuration item; compare its field ownership against the reply limit, and observe whether thinking budget is used to cap reference tokens.

## How to verify the setup

1. Input hypothetical material text one, material text two, and the draft sentence. Compare whether "delivered within 48 hours" and "a chargeback has never occurred" in the draft sentence have corresponding records in the materials. The materials record only a delivery date and one chargeback notice; the draft sentence is unsupported and should be recorded as pending verification.
2. Input a continued session under the same chatId. Compare the history messages actually carried in against the memory turns setting, and observe whether the carried rounds match the setting. A new session that does not pass chatId does not use platform context.
3. Input an explicit paper empty result []. Compare the downstream node's design for handling empty references, and observe whether it follows the no-reference branch. Do not presuppose that retrieval necessarily returns an empty result.

Each check compares the input against a specific field or setting and records an observable outcome. When the material does not state a field, the result remains unknown rather than being read as a denial. A pending request is not approval, an offered option is not execution, and an unsigned termination is not a completed termination.
