# Cross-border payment reviews: workflow routing for copy drafting

## What the documents look like

Cross-border standalone-site payment risk control centers on card-network disputes and receiving accounts. The work does not track parcel status the way order fulfillment does; it follows chargeback notices, fraud order lists, invoices, and carrier proof of delivery. The typical operators are standalone-site merchants, risk specialists, and finance settlement staff. The main data sources are Stripe or PayPal backends, Shopify orders, carrier delivery confirmations, and customer service emails. The cost of error is dispute loss, account freezing, and interrupted ad delivery. Data updates daily and per order.

This page is limited to one task: drafting product and marketing copy. The workflow-routing feature takes material to be checked and a proposed sentence, sends them into interaction nodes, collects the information needed for a judgment, and passes it to downstream nodes. The daily and per-order update frequency does not change the interaction and collection behavior of these nodes, so it is not used here to infer batch synchronization, full synchronization, real-time behavior, or transaction-triggered mechanisms.

## Constraints at the workflow routing step

The Form Input node is a user-interaction node. When it is triggered, the conversation enters an interaction state and the workflow state is recorded. After the user fills in the required information and submits, the node collects the submitted form information and passes it to subsequent nodes. The User Selection node is also a user-interaction node. When it is triggered, the conversation enters an interaction state and the workflow state is recorded. When the user makes a selection, the node evaluates that selection and executes the corresponding branch. These two nodes carry collection and branching only. Retrieval, judgment, and interface writes must be handled by downstream nodes.

Hypothetical paper exercise sample. The source material reads: "This batch of orders corresponds to invoice number INV-2043. The invoicing entity is a standalone-site store. The invoice date is March 10, 2025. The carrier proof of delivery shows delivery on March 14, 2025. The payment chargeback notice states that the dispute stage is pending review." The proposed sentence to be judged reads: "All orders in this store have passed risk review and completed delivery." The proposed sentence covers an entity, period, and fields that go beyond what the source material records.

The comparison object is the source material text against the proposed sentence. The interaction nodes collect and branch; they do not decide whether the proposed sentence is supported.

## Configuration and implementation checks

| Configuration item | Value or check on this page | Basis and boundary |
| --- | --- | --- |
| Interaction node selection | Form Input collects material fields; User Selection judges whether the proposed sentence is usable | Both are user-interaction nodes that trigger execution |
| Required information | Source material text, proposed sentence, judgment conclusion | Form Input collects required information and passes it downstream |
| Branch design | User Selection continues along the "yes" branch | The User Selection node executes the corresponding branch |
| Output handoff | Pass collected information to a later retrieval or judgment node | Handoff must compare output against input item by item |
| External actions | Order writes, document backfill, external status synchronization | Require a separate business interface or later process |
| Hypothetical trial starting point | Proposed-sentence threshold set to "material covers all fields" | A starting point for this page, compared field by field against the source material |

## Three common errors

1. Treating the interaction node's state recording as a global state switch. Form Input and User Selection enter an interaction state and record workflow state when triggered. That behavior belongs to the node itself; the configuration does not add a separate global state-recording switch.

2. Treating retrieval relevance as a permission or entity filter. Relevance is a similarity measure and does not perform entity isolation. Retrieval is not authorization. Records outside the permitted scope must be excluded by downstream implementation.

3. Treating an unstated field as a negation. The material states only that the dispute stage is pending review. The proposed sentence claims all orders passed review and completed delivery. That claim is unsupported; it is not a negation and not a conflict.

## How to verify the setup

1. Enter the source material and the proposed sentence above. Compare whether the proposed sentence's fields share the same entity, the same period, and the same field as the material. The material covers only invoice number, invoicing entity, invoice date, delivery date, and dispute stage. The proposed sentence's "all orders" and "passed risk review" are unsupported. The expected result is a finding of unsupported, with the evidence gap preserved.

2. Enter the source material in which the dispute stage is pending review. Compare whether the proposed sentence presents pending review as completed review. Pending review does not constitute review approval. The expected result is that the proposed sentence cannot be used directly.

3. Check the downstream handoff design with a paper input of an empty result. Set the retrieval output to [] and check whether the later node handles it along an empty-result branch. This is an empty-result handoff check. It does not claim that a fictional rule retrieval necessarily returns [].
