# Cross-border resale returns: workflow routing for copy drafting

## What the documents look like

This page covers workflow routing for product and marketing copy drafting in cross-border return refurbishment and resale. The category handles reverse logistics and item condition rather than first-leg replenishment, so the working materials differ from overseas-warehouse restocking. Data comes from overseas-warehouse WMS records, TikTok return centers, Amazon return reports, and product inspection photos. The everyday documents are return inspection sheets, refurbishment records, scrap declarations, and resale listing lists. Copy drafting has to line up inspection conclusions, refurbishment records, and listing scope, then judge whether a proposed promotional sentence has material support.

The work here is limited to workflow routing for copy drafting. Whether a specific promotional sentence is supported by the materials stays a copy-checking question and does not become an enterprise identity certification exercise. A similarity setting cannot be used to infer permissions or entity isolation. The same-vector-model requirement applies to the retrieval library itself and does not extend to business-registration sites or other external systems.

Two interaction nodes matter. The form input node enters an interaction state when triggered, records the workflow state, collects required information, and passes the submitted values to later nodes. The user selection node enters the same interaction state, and after the user makes a choice it evaluates that choice and executes the corresponding "yes" branch. Waiting for interaction, recording state, and hiding the dialog box are documented node behaviors. No separate global state-recording switch, submission-count limit, automatic judgment, or snapshot guarantee is documented, and none is assumed here.

## Constraints at the workflow routing step

Return status, refurbishment actions, and listing scope are recorded in separate documents. Copy drafting first collects these fields, then hands them to later nodes. Collected values must be passed explicitly to later retrieval, judgment, or interface nodes, and outputs are compared item by item against inputs. Order writes, document backfill, and external status synchronization require a separate business interface or downstream process. This page does not claim those actions happen inside the nodes.

Hypothetical paper exercise sample: an overseas-warehouse inspection record states "Return number H-01, item is a portable juicer, inspection date 10 March 2025, visible scratches on the exterior, functional test passed." Refurbishment record R-07 states that the outer shell was replaced and the packaging is intact afterward. Resale listing list S-02 places this item in the sellable scope. A separate draft sentence awaits judgment: "This item is brand new and unused, with complete original factory packaging." The comparison object is the original text scope of those three materials, and the question is whether the draft sentence is supported.

## Configuration and implementation checks

| Configuration item | Value or check on this page | Relation to the documents |
| --- | --- | --- |
| Form input node | Collect return number, inspection date, refurbishment record number, listing list number | Matches field collection from inspection sheet, refurbishment record, and listing list |
| User selection node | Set a "yes" branch for "adopt this draft sentence" | Matches the draft sentence awaiting judgment |
| Output handoff | Pass collected fields to the copy-checking node | Compare outputs against inputs item by item |
| Hypothetical trial starting point | Mark the draft sentence as awaiting judgment | The materials do not state brand new and unused, so comparison with the original text is required |
| External action split | Listing and status synchronization connect to a separate business interface | Nodes do not perform writes or synchronization |
| Retrieval scope check | Verify the retrieval library identifier and vector model identifier | Libraries with different vector models are not jointly associated |

The hypothetical trial starting point is chosen because the draft sentence makes a condition claim that the three materials never state, so the only available comparison is against the original wording. This is a paper starting value for this exercise, not an official default.

## Three common errors

1. Treating a similarity score as a permission or entity filter, so that a low score is read as excluding unrelated businesses or unauthorized records. Retrieval is not authorization, and the score does not carry that role. Check by entering the same return number, comparing returned records against the target scope the operator is entitled to access, and observing whether records outside that scope appear.

2. Treating fields collected by the form as verified facts and writing them straight into copy. The form collects values only; business verification and writes need downstream implementation. Check by entering the hypothetical sample fields, comparing the draft sentence against the original text of the inspection sheet, refurbishment record, and listing list, and observing whether the original text supports the sentence.

3. Treating the "yes" branch of the user selection node as an approval or a completed execution. A pending review does not show that operation permission is missing, and the selection only determines branch direction. Check by entering the selection result, comparing the branch connection against the following nodes, and observing whether the branch executes according to the selection.

## How to verify the setup

- Verification one: enter the original text of the hypothetical sample inspection sheet, refurbishment record, and listing list, then compare the draft sentence "This item is brand new and unused, with complete original factory packaging" against that text. The original text states visible scratches and an intact package after shell replacement, and does not state brand new and unused. The draft sentence is unsupported, and the evidence gap is recorded.

- Verification two: enter return number H-01 and compare the retrieval-returned records against the target scope the operator is entitled to access. Observe whether returned records fall inside that scope. If records outside the scope appear, record a failure branch. First-hit ranking and full recall are not guaranteed.

- Verification three: enter the user selection result and compare the "yes" branch connection against the following nodes. Observe whether the branch executes according to the selection and whether the interaction state is recorded as documented. No claim is made that this was actually tested or that an approval was granted.

For an empty-result handoff, a paper input of `[]` may be used to check the downstream design. This does not assert that any fictional rule retrieval returns an empty list. Where libraries use different vector models, check identifiers first and exclude non-matching libraries rather than running a cross-model retrieval to compare missed recall.
