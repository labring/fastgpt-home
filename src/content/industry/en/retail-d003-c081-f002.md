# Chain-store closure accounts: context limits for copy drafting

## What the documents look like

Closure settlement handles exit and asset recovery, the reverse direction from head-office site selection and store opening. The main data comes from POS inventory, the fixed-asset system, lease contracts and the finance ledger. Typical documents include closure approvals, inventory clearance forms, lease termination agreements and asset count sheets. When drafting product and marketing copy, the context window has to hold store status, asset ownership, lease term and settlement basis at the same time. These fields sit in separate systems and vary widely in length. Data updates are irregular, once per store, so one batch of material may carry different dates, and any quantity, scope or time written into copy must be compared item by item against the corresponding material.

Three characteristics shape this step. First, closure material often contains long tables and contract clauses, so a low reference cap can trim key clauses and the copy then omits asset scope or settlement conditions. Second, the model context is checked against actual model capability, and the reply cap is not the full context window. Third, the knowledge-base reference cap is measured in tokens, so it must be checked against single-section length and question samples to confirm the content is complete. Historical input also affects retrieval: the same question may recall different content with empty history and with history, and both must be checked separately.

## Constraints at the context limits step

The model context is verified against actual model capability; the reply cap does not equal the full context window. Closure material commonly includes long tables and lease clauses. If the reference cap is set too low, key clauses may be trimmed, and the copy may omit the asset scope or settlement conditions. The knowledge-base reference cap is expressed in tokens and must be checked against single-section length and question samples to confirm the content is complete. Historical input affects retrieval results, so the same question under empty history and under history may recall different content and must be checked separately. When a fixed reply format is used, field completeness and successful parsing must be verified; checking text length alone is not sufficient.

Semantic recall and relevance scores do not perform permission or entity isolation. A requirement that libraries sharing a vector model be associated together does not extend to external systems needing the same model. RRF is a fusion process for mixed results, not a switch. The thinking budget belongs to the thinking configuration and cannot be repurposed as the reference token cap.

## Configuration and implementation checks

The settings below are built around a hypothetical drill sample. The values are starting points for this hypothetical exercise, not official defaults.

| Configuration item | Hypothetical starting point | Reason and comparison method |
| --- | --- | --- |
| AI model | Choose a model whose popup shows it supports the needed context length | Compare the model maximum context with total material length to confirm the material is not truncated |
| Reply cap | Turn on and set to a length covering the copy body and basis fields | Compare whether output is cut off early against the length needed to express the material fully |
| Reference cap | Set in tokens to cover a single section of material | Compare whether the referenced content includes subject, object, status and validity scope |
| Minimum relevance | Keep default; it applies only under semantic retrieval or rerank | Compare whether filtered results still contain the material needed for the judgment |
| Question optimization | Turn on for short questions or multi-turn follow-ups | Compare whether the retrieval terms before and after cover subject and object |
| Reply format | Keep default for ordinary copy | Switch to a structured format only when a downstream step must read fixed fields |

## Three common errors

1. Treating the reply cap as the full context window. The reply cap controls output length, while the model context is checked against actual model capability; the two play different roles. Raising only the reply cap still leaves input material open to truncation, and the copy may omit the asset scope. To check, input the complete material and compare whether the output contains the subject, object and status found in the material.
2. Mixing the reference cap with the thinking budget. The reference cap controls knowledge-base references in tokens, while the thinking budget belongs to the thinking configuration; the two are not interchangeable. To check, verify separately whether the referenced content is complete and whether the thinking strength matches question complexity.
3. Treating semantic recall as permission or entity isolation. A relevance score does not exclude unrelated business or unauthorized records, and retrieval is not authorization. To check, input the same question and compare whether the recalled results include material that does not belong to this store; record the actual observation and do not infer runtime results.

Hypothetical drill sample: the source material reads, "Store A submitted a closure approval on 1 March 2025, and the approval status is pending review. The store's lease termination agreement has not been signed. The inventory clearance form states 12 remaining shelf units and 3 cash registers." The draft sentence to be judged reads, "Store A has completed the closure approval, the lease has been terminated, and the remaining assets of 12 shelf units and 3 cash registers may be disposed of externally." When checking, compare the draft sentence with the material: the approval status is pending review, which does not amount to completed; the lease termination agreement is unsigned, which does not amount to terminated; the asset quantities match the material. The draft sentence is unsupported on approval status and lease status, and the evidence gap must be preserved.

## How to verify the setup

1. Input the hypothetical source material above together with the draft sentence, and compare whether the approval status, lease status and asset quantities in the draft sentence correspond item by item with the material. The condition is met only when approval status, lease status and asset quantities all match the material; pending review and unsigned must remain flagged as to be confirmed.
2. Input the same question under empty history and under history, and compare whether the recalled content in both runs contains the subject, object and status needed for the judgment. The condition is met only when both runs contain the complete fields; when fields are missing, record the gap and do not infer a cause.
3. Input a clearly labeled paper empty result `[]` and check whether the downstream design handles an empty reference. The condition is met only when the downstream has an explicit way of receiving an empty result; do not claim that a fictional rule retrieval necessarily returns `[]`. Libraries across different vector models cannot be associated together; first check the identifier and exclude those that do not match, then record the actual observation.
