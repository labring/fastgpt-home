# MCN operations: workflow routing for document comparison

## What the documents look like

An MCN manages long-term account compliance for multiple creators, and its work extends beyond any single brand session. The comparison materials come from the contract ledger, creator account data, platform violation notices, and training records. For the contract-and-transaction-material comparison task, the subject is the creator account, the object is the field relationship between the signed contract and the transaction materials, and the relevant states are three separate facts: signing, cooperation reached, and contract effectiveness.

Account scheduling and violation handling sheets update frequently, so material versions are easily misaligned. A comparison must lock the same creator, the same period, and the same field; only mutually exclusive values within one field form a contradiction. A missing field stays unknown, and a field supported only by evidence from a related stage is recorded as pending verification. Daily and weekly update frequencies affect how quickly versions drift, which is why the same-period lock matters here.

## Constraints at the workflow routing step

Workflow routing carries material collection, branch decisions, and result handoff. When the form input node triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the interaction the workflow continues downward; the node collects required information and passes it to later nodes. When the user-selection node triggers, the conversation also enters an interaction state, and after the user makes a choice the node evaluates that choice and executes the corresponding branch.

Hypothetical drill sample: the contract ledger reads, "Creator A, account A, 1 March 2025 to 31 August 2025, slot fee settlement, signature page bears both parties' seals, approval status pending review." A separate handover draft sentence reads, "Creator A's contract is effective; March scheduling can be arranged." The comparison requirement: the ledger states the signature page bears seals and the approval status is pending review, while the draft sentence says the contract is effective. Signing, cooperation reached, and contract effectiveness are three distinct facts. Pending review does not demonstrate a lack of operating authority, and it does not equal effectiveness. The draft sentence is unsupported against the ledger text on the same subject, same period, and same field, so it is pending verification and the evidence gap is retained.

The interaction nodes wait for the user to complete an action; there is no automatic judgment and no guarantee about submission counts. Order writing, document backfill, and external status synchronization require a separate business interface or a downstream process. Retrieval and forms do not constitute authorized execution.

## Configuration and implementation checks

| Configuration item | Assumed starting point for this page | Reason and comparison method |
| --- | --- | --- |
| Form input node | Enabled, collecting creator account, contract period, approval status | Corresponds field by field with later comparison fields; check whether the output is passed completely |
| User-selection node | Enabled, branches "continue comparison" and "mark pending verification" | Verify whether the corresponding branch executes after a choice |
| Interaction state recording | Workflow state recorded per node behavior | Compare with the node documentation; no separate global switch is set |
| Output handoff | Collected fields passed to the later comparison node | Compare input and output fields item by item for consistency |
| External operation split | Order writing and status synchronization connect to a separate interface | Check whether an independent business interface implementation exists |
| Retrieval scope | Limited to the contract ledger scope with access rights | Check whether the target scope and manual input cover the required materials |

## Three common errors

1. Treating pending review as already effective. In the sample the ledger states the approval status is pending review, while the draft sentence says the contract is effective; the two take mutually exclusive values in the same field, so the result is pending verification.
2. Using retrieval results in place of authorization. Retrieval returns materials only; business verification, approval, database writing, and external synchronization require downstream implementation. A hit record does not mean scheduling can be arranged.
3. Mixing evidence from different periods or different fields into a contradiction. The sample is limited to the same creator, same period, and same field; differences across periods or across fields do not form a contradiction.

## How to verify the setup

1. Input the sample source text and the draft sentence, and compare the approval status field. If the ledger shows pending review while the draft sentence says effective, the output should be pending verification with the evidence gap retained.
2. Input the fields collected by the form and compare them with the output passed to the later node. If creator account, contract period, and approval status match item by item, the handoff condition is met.
3. Input an explicit paper empty result [] and check whether the downstream design handles the empty-result branch, without inferring what a fictional rule retrieval would return.
