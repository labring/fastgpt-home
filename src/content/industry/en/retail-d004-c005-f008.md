# TikTok Shop US operations: workflow routing for document comparison

## What the documents look like

Contract and transaction material comparison for a TikTok Shop US store draws on four document types that arrive from different places and describe the same order from different angles: product listings, return and refund records, return grading evidence, and settlement bills. The public brief places the data sources at Seller Center, the order center, carrier tracking, and advertising reports, with updates stated as daily and per order. That frequency describes how material accumulates over time. It does not imply batch synchronization, full synchronization, real-time triggering, or transaction-driven triggering.

The comparison task itself is narrow. For one subject, one period, and one field, the values carried in separate documents are placed side by side and checked. A listing states a return commitment. A return record states what was actually handled. Return grading evidence states the basis for a judgment. A settlement bill states a deducted amount. These are different documents, and their field definitions may not line up. Workflow routing has to organize the material into a node order and make clear which steps collect input through interaction nodes and which steps require a separate business interface.

Compared with Douyin store shelf operations, a US TikTok Shop is more constrained by local return windows, return grading, and overseas logistics. One transaction can therefore produce listing commitments, return and refund records, return grading evidence, and settlement bills at the same time. The brief also notes the consequences of getting this wrong: automatic platform refunds, higher return fees, and failed appeals. Those consequences explain why the routing step matters, not what any node is guaranteed to do.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues downward only after the user completes the interaction. The node collects the required information the user fills in and passes it to later nodes. The user selection node is also a user interaction node. It enters the interaction state on trigger, records the workflow state, and when the user makes a selection, executes the corresponding "yes" branch. The basic use is to pose a question that requires a decision and route the workflow according to the feedback.

Neither node confirms material authenticity, authorization status, or a business outcome. They interact and branch. Retrieval and relevance scoring do not perform permission filtering or entity isolation. A retrieval library requires the same vector model for items to be associated together; that requirement belongs to the retrieval library and does not extend to business registration sites or other external systems. Libraries on different vector models cannot be associated together. Check the model identifier and exclude those that do not match rather than running a cross-model retrieval to compare recall.

Order writes, document backfill, and external status synchronization require a separate business interface or a later process. A form collects values. Business verification, approval, database writes, and external synchronization each need their own downstream implementation. Interaction waiting, state recording, and hiding the dialog box follow the documented behavior. No global state-recording switch is set here, and none is claimed.

## Configuration and implementation checks

The settings below concern the hypothetical drill sample on this page. They list only settings the official text describes or implementation checks tied to this page. The sample is constructed on paper and points to no real customer or real identifier.

Hypothetical drill sample: Material A is a US store listing text reading "return window 30 days; returns require unboxing photos." Material B is the return record for the same order reading "2025-03-10 delivered, 2025-03-25 return requested, status is pending review." Material C is return grading evidence reading "two photos, judgment: resellable." Material D is a settlement bill reading "2025-04-01 charge USD 12.00, item: return processing fee." The draft sentence to be judged is "the return for this order was completed within the window and refunded."

| Configuration item | Setting or check on this page | Relation to the sample |
| --- | --- | --- |
| Form input node | Collect order number, material type, field to compare | Carries field input from Materials A to D |
| User selection node | Set a "materials complete / materials missing" branch | Material B is pending review, so the missing branch applies |
| Retrieval scope | Limit to this store's order and return document library | Excludes unrelated store records |
| Vector model identifier | Check the model identifier is consistent within one library | Libraries on different models are not associated together |
| Output handoff | Pass collected values to the comparison judgment node | Compare same subject, same period, same field |
| External operations | Refunds, charges, status sync connect to separate interfaces | This page performs no write or sync |

In the sample, Material B carries the status "pending review." That status does not constitute a completed refund. Material D's charge date and Material B's request date differ; they are different fields and do not directly constitute a contradiction. The draft sentence claims "completed and refunded," which lacks evidence of refund completion and is unsupported.

## Three common errors

1. Treating pending review as completed. The input is Material B, "status is pending review." The comparison object is the draft sentence "completed and refunded." The observable result is that the status field and the draft sentence do not agree, so the draft sentence is unsupported.
2. Comparing different fields as if they were the same field. The input is Material B's request date, 2025-03-25, and Material D's charge date, 2025-04-01. The comparison object is the field definition for each date. The observable result is that the two dates belong to different business fields and do not form a same-field contradiction.
3. Treating retrieval or a form as authorized execution. The input is the order number and material type collected by the form. The comparison object is the refund, charge, and status synchronization actions. The observable result is that the form only collects values and triggers no business write.

## How to verify the setup

1. Input the original text of Materials A to D and the draft sentence. Compare the subject, period, and field in the draft sentence against the material values. The observable result is that the draft sentence "completed and refunded" lacks evidence of refund completion and is judged unsupported.
2. Input Material B's status "pending review" and the user selection node's "materials missing" branch. Compare the branch direction. The observable result is that the workflow enters the missing branch and does not enter the completion branch.
3. Input a paper empty result [] and the downstream handoff design. Compare whether the downstream handles the empty result as such. The observable result is that the downstream produces no fabricated record and the gap is recorded as pending verification.

All three verification items are paper expectations and were not actually run. The refund completion time, approval outcome, and external synchronization status are not stated in the material and remain unknown.
