# Amazon FBA preparation: workflow routing for document comparison

## What the documents look like

FBA preparation moves inventory into Amazon-operated warehouses before demand is confirmed, so the operating risk concentrates on inbound receiving and inventory age. The materials handled on this page come from FBA inbound plans, box labels, inventory reports and compensation claims, with daily and weekly update rhythms. The comparison task examines whether the purchasing order, freight forwarder documents and inbound plan agree on the same party, the same object, the same quantity and the same status.

This category differs from merchant-fulfilled operations because stock is positioned ahead of the sale. A receiving shortfall can produce a stockout and a ranking decline, while unsold units accrue storage fees. A compensation claim that never reaches a supported state produces a failed recovery. These consequences shape the routing work: the workflow must collect the fields needed to compare materials, then branch on whether the comparison result is consistent or inconsistent.

A form input node triggers, the conversation enters an interactive state, and the workflow state is recorded. After the user completes required fields and submits, the collected values pass to later nodes. A user selection node behaves the same way and, once the user makes a choice, executes the corresponding yes branch. That branch wiring must be verified one connection at a time. The interactive state record is a behavior of the interaction node; no separate global state-record switch is documented.

## Constraints at the workflow routing step

The form input node collects required information and passes it downstream after submission. Whatever is collected must be explicitly handed to the later retrieval, judgment or interface node, and the output must be compared field by field against the input. Order writing, document backfill and external status synchronization require a separate business interface or a later process. Retrieval and collected form values do not constitute authorization, and a pending review state does not indicate that an operation lacks permission.

Hypothetical paper exercise sample: the source materials supplied for checking read as follows. Purchasing order PO-2024-0517 states that supplier A will deliver 500 units of SKU-X before 10 June 2024. Freight forwarder document FB-2024-0601 states that 480 units of the same SKU arrived at the warehouse. FBA inbound plan RP-2024-0603 states that 500 units of the same SKU are planned for inbound. The draft sentence awaiting judgment reads: "This preparation batch is short by 20 units and the compensation claim has been accepted by the platform." The source text contains the party, object, quantity and date scope. It does not state the acceptance status of any compensation claim.

The routing constraint follows from that gap. A branch that treats the claim as accepted would route on a fact the source materials do not carry. The correct routing behavior is to send the draft sentence to a pending-verification outcome, because the acceptance status remains unprovided. Retrieval relevance does not filter by business entity or permission, so a retrieved record cannot be read as an approved operation.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason for the choice and comparison method |
| --- | --- | --- |
| Form input node | Required fields set to purchasing order number, SKU and quantity | Compare field by field against the source materials; missing entries remain in interactive waiting |
| User selection node | Two branches, consistent and inconsistent | Verify the yes branch connection one at a time and check the branch direction |
| Output handoff | Collected values passed to the comparison node | Compare comparison output against input fields and observe one-to-one correspondence |
| Retrieval scope | Limited to target materials with access rights | Check identifiers and exclude non-matching items, then record the actual observation |

## Three common errors

1. Treating a pending compensation claim as accepted. The sample source text does not state acceptance status, so the draft sentence "has been accepted by the platform" is unsupported and must be recorded as pending verification.
2. Treating a retrieval hit as authorization. Retrieval and relevance scores do not perform permission or entity isolation, so a matched record does not mean an operation has been approved.
3. Treating an interaction node's state record as a global switch. The interactive state record is a behavior of the node, and no separate global state-record switch is documented.

## How to verify the setup

1. Input the sample source text and the draft sentence. Compare whether the draft sentence exceeds the party, object, quantity and date scope stated in the source. Observe whether "has been accepted by the platform" has a corresponding statement in the source text. If no corresponding statement exists, record the sentence as unsupported.
2. Input the purchasing order number and SKU. Compare the form-collected values against the same fields in the source materials. Observe whether a missing required field enters interactive waiting, and whether submission passes the information to later nodes.
3. Input the paper empty result []. Compare whether the downstream node handles it according to the empty-result design. Observe whether an unsupported automatic business action appears, and record the actual observation rather than asserting that retrieval must return [].

Each check states what is compared and what result satisfies the condition. None of these checks has been executed, and no approval, refund or business action is claimed. Where the source materials leave a field unstated, that gap remains a gap.
