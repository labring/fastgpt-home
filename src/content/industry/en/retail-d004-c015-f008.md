# Letter-of-credit documents: workflow routing for document comparison

## What the documents look like

Letter-of-credit examination and presentation serves the paying conditions set by the issuing bank, so the comparison centers on document consistency rather than tax matching. The working materials named in the brief are the issuing bank notice, UCP600 clauses, the freight forwarder bill of lading, and bank presentation records. On a per-transaction basis these produce the letter of credit, commercial invoice, bill of lading, insurance policy, and draft. The update frequency given is per transaction.

These facts set the input boundary for workflow routing. The routing nodes receive text and form values submitted per transaction. Whether the underlying material is complete, and whether it agrees with the letter-of-credit terms, remains a matter for human comparison. The brief marks its own confidence as broadly indicative, so details not stated here stay conditional.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user submits the required information the node passes that information to later nodes. The user selection node is also a user-interaction node. When the user makes a selection, the node evaluates the choice and executes the "yes" branch. Both nodes can be added repeatedly and trigger execution. Routing collects and passes form values. It does not complete a document-consistency judgment, does not execute presentation, and does not write to a business system.

Hypothetical drill sample. Under a letter of credit, the drafted sentence is: "The commercial invoice amount agrees with the draft amount, and the bill of lading date is not later than the latest shipment date specified in the letter of credit." Two source sentences are supplied for comparison. First: "This letter of credit specifies the latest shipment date as 31 March 2025." Second: "Commercial invoice amount USD 50,000; draft amount USD 50,000." The request awaiting decision is: "Please confirm whether the drafted sentence can serve as a pre-presentation document-consistency conclusion." That request is pending review. It is not an authorization and not a completed consistency confirmation.

## Configuration and implementation checks

| Configuration item | Type | Description |
| --- | --- | --- |
| Form input node | Interaction node | Enters the interaction state on trigger, collects required information, passes it to later nodes |
| User selection node | Interaction node | Executes the "yes" branch after the user selects; verify each branch connection individually |
| Output handoff | Implementation check | Pass collected information explicitly to later retrieval, judgment, or interface nodes; compare input and output item by item |
| Interaction state check | Implementation check | State recording is behavior of the interaction node; no separate global state-recording switch is documented |
| External action separation | Implementation check | Order writing, document backfill, and external status synchronization require a separate business interface or later process |

Hypothetical trial starting point. Feed the drafted sentence and the two source sentences above as form values, and observe whether the output handoff node returns them item by item. This starting point is chosen because the sample carries a subject (the letter of credit), objects (invoice, draft, bill of lading), and a date range, which allows field-by-field comparison against the source text. The comparison objects are the field values in the two source sentences and the drafted sentence.

## Three common errors

1. Treating the drafted sentence collected by the form as a completed document-consistency conclusion. The input is the drafted sentence and the source text; the comparison objects are the invoice amount, draft amount, and latest shipment date fields; the observable result is the field values returned by the output handoff node. If the returned values remain pending review, no conclusion has been formed.

2. Treating the "yes" branch of the user selection node as business authorization. The input is the user's selection; the comparison objects are the branch connection and the request status; the observable result is whether the branch points to a later node. A pending request does not become approved because a branch executed.

3. Treating a retrieval result or form value as presentation execution. The input is the retrieval result or form value; the comparison object is whether an external interface call record exists; the observable result is whether the system shows an order write or document backfill action. Without an interface, no execution occurs.

## How to verify the setup

1. Input the two source sentences and the drafted sentence from the hypothetical sample. Compare the invoice amount, draft amount, and latest shipment date fields. Observe whether the output handoff node returns each field and preserves the pending-review status. The condition is met when field values can be compared and the status has not changed to approved.

2. Input the hypothetical request "Please confirm whether the drafted sentence can serve as a pre-presentation document-consistency conclusion." Compare the request status with the branch execution result. Observe whether the user selection node executes only the "yes" branch without producing an approval record. The condition is met when branch execution and business approval remain separate.

3. Input an empty-result handoff sample, using the explicit paper input [] to check the downstream design. Compare whether the downstream node receives the empty value and remains waiting. Observe whether any automatic write or external synchronization occurs. The condition is met when the empty value can be carried and no automatic business action appears.

These checks describe expected observations. They do not report an executed test, a deployment, an approval, or a refund. A relevance score is not a category, entity, or permission filter, and retrieval is not authorization. Forms collect values; business verification, approval, database writes, and external synchronization need their stated downstream implementation. Where a document field is not provided, it remains unknown.
