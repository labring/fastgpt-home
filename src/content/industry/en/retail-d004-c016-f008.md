# Franchisee onboarding: workflow routing for document comparison

## What the documents look like

Franchisee training and opening coaching is a transfer of operating capability. It differs from franchise filing administration, which is a legal disclosure process. This page covers the comparison of contracts and transaction materials for that onboarding work, and the documents involved are training sign-in sheets, opening checklists, SOP manuals, and assessment scores. Their sources are the training system, the supervisor app, store photographs, and the headquarters SOP library.

In this task the parties to be checked are the franchisee and the training department or regional supervisor. The objects are sign-in records, material status, SOP actions, and score records. The states include signed in, pending inspection, submitted, and pending verification. Materials update once per store per month, so a sign-in sheet for one month can belong to a different training batch than the sheet for the next month. Any comparison has to lock the same store, the same period, and the same field before it means anything. The supplied material does not state whether the system synchronizes automatically or processes in batches, so this page assumes no automatic trigger.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the workflow continues only after the user completes the interaction. The node collects the required form values and passes them to later nodes once the user submits. The User Selection node is also a user interaction node. It triggers the same interaction state and records the same workflow state, and when the user makes a choice the node evaluates that choice and executes the corresponding "yes" branch. Its basic use is to pose a question that requires a decision and to design different workflow paths from the user's feedback.

Retrieval output is not authorization. A relevance score does not carry entity or permission information, so it cannot be used to exclude unrelated businesses or unauthorized records. Libraries built on different vector models cannot be associated with each other; identifiers must be checked first and non-matching libraries excluded, and cross-model retrieval must not be run to compare missed recalls. An empty result can be handled by checking the downstream design against an explicit paper input of [], and no claim can be made that a fictional rule retrieval necessarily returns [].

Hypothetical paper exercise

The following paper materials are used for this exercise only. They do not come from a real customer or system record.

Material text one (training sign-in sheet excerpt): "March 2024, franchisee A attended cashier and inventory training, sign-in status signed in, confirmed by training department B."

Material text two (opening checklist excerpt): "March 2024, store A opening material inspection, recorded by supervisor C: cashier counter materials in place, inventory labels pending completion."

Draft sentence to be assessed: "Franchisee A has completed all March 2024 opening coaching requirements, with no gaps in training or materials."

Check point: the sign-in sheet records training attendance only, and the checklist records material status only. Neither states the full scope of "all opening coaching requirements." The draft sentence merges two different fields into "no gaps," which is an inference the source text does not support.

## Configuration and implementation checks

| Configuration item | Type | What this page checks |
| --- | --- | --- |
| Form Input node | Documented | Enters the interaction state on trigger, collects required values, passes them to later nodes on submission |
| User Selection node | Documented | Executes the "yes" branch after the user makes a choice; verify each branch connection |
| Interaction state check | Implementation check | State recording is behavior of the interaction node; no separate global state-recording switch is set or claimed |
| Output handoff check | Implementation check | Pass collected values explicitly to later retrieval, judgment, or interface nodes, and compare each output against its input |
| External action split | Implementation check | Order writes, document backfill, and external status synchronization require a separate business interface or downstream process |
| Hypothetical exercise starting point | Hypothetical | Use March 2024 as the comparison period and compare it against the month stated on the sign-in sheet and the checklist |

Reason for the hypothetical starting point: both material texts are labelled March 2024, so the same month serves as the comparison basis and keeps the fields within one period. This starting point is used for this paper check and is not an official default value.

## Three common errors

1. Merging "signed in" from the sign-in sheet with "pending completion" from the checklist into "no gaps." The input is the two material texts, the comparison is between the fields "signed in" and "pending completion," and the observable result is that the draft sentence's "no gaps" has no supporting basis in the source text.

2. Treating the "yes" branch of the User Selection node as executed authorization. The input is the claim "has completed" in the draft sentence, the comparison is between the node's branch connection and the source states, and the observable result is that the source text records only sign-in and material status and states no authorization execution.

3. Treating a retrieval result or relevance score as a permission filter. The input is the returned record, the comparison is between the record identifier and the target retrieval scope, and the observable result is that the relevance score carries no entity or permission information and cannot exclude unauthorized records.

## How to verify the setup

1. Input material text one and material text two from the hypothetical sample, compare the fields "signed in" and "pending completion," and expect the draft sentence's "no gaps" to be unsupported by the source text and recorded as pending verification. A contradiction can be recorded only if the same field carries mutually exclusive values in the source text.

2. Input the draft sentence to be assessed together with the branch connections of the User Selection node, compare the claimed "has completed" against the node's actual branch state, and expect the branch connection to represent a selection path only, not authorization or business completion. Where the source does not state a fact or shows only a related stage, record it as unsupported.

3. Input the returned retrieval record together with the target retrieval scope, compare the record identifier against the access scope, and expect the relevance score not to exclude unrelated businesses or unauthorized records. If the retrieval result is empty, check the downstream design against a paper input of [], and make no claim that a fictional rule retrieval necessarily returns [].
