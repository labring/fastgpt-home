# Franchise fee settlement: workflow routing for document comparison

## What the documents look like

Franchise fee and security deposit settlement centers on fund receipts and payments plus breach-related deductions. It sits apart from franchise filing administration, and this page does not carry any government filing duty. The materials for this category come from the finance system, franchise contracts, bank transaction records, and store violation records. Everyday documents include franchise fee invoices, security deposit ledgers, deduction notices, and contract payment schedules. The supplied brief gives an update frequency of monthly and per deduction; this page does not derive batch synchronization, real-time processing, or transaction-triggered mechanisms from that frequency. Reconciling contract payment terms, confirming deduction causes, and issuing invoices are the three time-consuming steps. Workflow routing has to separate material collection, human judgment, and downstream business actions.

For this task, three industry facts shape the routing design. Settlement materials mix a contractual layer (payment schedules, deduction clauses) with a transactional layer (bank records, ledgers), so a comparison step needs both sides present before it can conclude anything. Deduction causes depend on store violation records that arrive on their own schedule, so a routing step cannot treat a missing violation record as a zero deduction. Invoices follow confirmed amounts rather than leading them, so invoice issuance belongs downstream of confirmation, not inside the comparison itself.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes required fields and submits, the collected values pass to later nodes. The User Selection node is also a user interaction node; after the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. Both nodes can be added repeatedly and trigger execution. The interaction state record is existing node behavior; there is no separate global state-recording switch, and there is no guarantee of submission counts or automatic judgment.

Hypothetical paper exercise sample: a franchise contract payment schedule reads, "Party A shall pay the franchise fee of RMB 80,000 on or before 31 March 2025; the security deposit of RMB 50,000 shall be paid within ten days after contract signing." The security deposit ledger for the same period records that franchisee's deposit balance as RMB 50,000. One handover request awaiting determination reads: "Please convert the security deposit of RMB 50,000 into a franchise fee offset on 31 March 2025." The request names a subject, an object, a period, and an amount, but the contract text does not state that the deposit may be converted into a franchise fee, and the ledger records no such conversion.

Retrieval output is a candidate set only and does not constitute authorization. Semantic recall and relevance scores carry no permission or entity-isolation duty. The same-vector-model requirement is limited to libraries that are jointly associated; it does not extend to business registration sites or other external systems. Forms collect values; business verification, approval, database writes, and external synchronization require a separate business interface or downstream process. Order writes, document backfill, and external status synchronization are business actions that need their own system implementation.

## Configuration and implementation checks

| --- | --- | --- |
| Form Input node | Existing node behavior | Collect franchisee name, contract number, payment period, amount; pass to later nodes after submission |
| User Selection node | Existing node behavior | Set a branch for "route to manual verification"; verify the "yes" branch connection one by one |
| Interaction state record | Existing node behavior | Record workflow state and continue after the user completes interaction; no global switch |

Hypothetical trial starting point for this page: set the relevance threshold to 0.5. The reason for choosing this value is to make candidate returns easy to observe; the comparison object is the number of returned items for the same query at different thresholds. This value is not an official default.

## Three common errors

1. Treating retrieval candidates as authorization. Observable error: executing the RMB 50,000 deposit-to-fee offset directly from the ledger entry returned by retrieval. Input is the pending request and the ledger entry; the comparison object is whether the contract text states a conversion clause; the observable result is that the contract text does not state one, so the request is not supported.
2. Treating pending review as completed approval. Observable error: assuming the deduction is approved once the form is submitted. Input is the form submission record; the comparison object is whether an approval conclusion exists; the observable result is that only a submission record exists and the approval status remains unverified.
3. Jointly associating libraries across different models. Observable error: merging libraries with different vector model identifiers into one retrieval and judging a conflict from the result. Input is the model identifiers of the two libraries; the comparison object is whether the identifiers match; the observable result is that they do not match, so the non-matching library is excluded and the actual observation is recorded, without inferring missed recall or redundancy.

## How to verify the setup

1. Against the hypothetical sample contract text and the pending request, input "convert the security deposit of RMB 50,000 into a franchise fee offset on 31 March 2025," compare whether the contract payment schedule states a conversion clause, and observe that the text does not state one; the determination is not supported, and the evidence gap is retained.
2. Against the form output handoff, input the submitted franchisee name, contract number, payment period, and amount, compare whether the fields actually received by later nodes match the submitted fields, and record a gap when fields are missing or misaligned; no automatic judgment is claimed.
3. Against the retrieval library identifiers, input the names and vector model identifiers of the jointly associated libraries, compare whether the identifiers match, and exclude a library when they do not; cross-model retrieval is not performed to compare missed recall. For empty-result handoff, a paper input of [] can be used to check the downstream design, without claiming that a fictional rule retrieval necessarily returns [].
