# Omnichannel stock transfers: workflow routing for document comparison

## What the documents look like

Omnichannel stock transfer work moves goods between stores and warehouses. It does not handle marketing outreach. The main data sources are ERP inventory, store POS, e-commerce orders, and WMS. Updates arrive daily or weekly. The documents handled day to day are transfer requests, inventory snapshots, store shortage lists, and transfer logistics notes.

These materials sit at three stages: request, execution, and arrival. The same transfer number can carry different field values at different stages, so a comparison has to confirm the stage of each document first. Transfer number, item code, source and destination party, quantity, and date range are the shared fields used to decide whether two documents describe the same transaction.

For this page the task is contract and transaction material comparison, and the feature under discussion is workflow routing. Workflow routing collects values, passes them on, and takes branches. It does not grant authorization.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. The user fills in the required information and submits, and the node collects what was entered and passes it to later nodes. The user selection node is also a user interaction node. When the user makes a choice, the node evaluates that choice and runs the corresponding "yes" branch. Interaction state and state recording are existing node behaviors. There is no separate global state-recording switch to configure.

Materials collected through retrieval or through a form do not constitute authorization. Order writing, document backfill, and external status synchronization require a separate business interface or a later process.

Hypothetical drill sample. A transfer request reads: "Transfer DB-2024-031, source location Warehouse A, destination location Store B, item code SKU-7712, quantity 40 pieces, request date 2024-03-11, status is pending review." An inventory snapshot reads: "SKU-7712 available quantity at Warehouse A: 40 pieces, snapshot date 2024-03-11." The draft sentence to be judged is: "This transfer request has been approved and can proceed to outbound picking." In this sample, "pending review" means the request is at a pre-review stage and states no approval conclusion. The draft sentence treats an unsupported conclusion as an established fact. Pending review does not show that operating permission is absent, and it does not equal approval.

## Configuration and implementation checks

| Configuration item | Value or check on this page | Note |
| --- | --- | --- |
| Form input node | Collect transfer number, item code, quantity, date range | Enters interaction state on trigger; passes values on after submit |
| User selection node | Set two branches, "materials complete" and "materials missing" | Runs the corresponding "yes" branch after the user chooses |
| Interaction state check | Check item by item whether the node entered interaction state | Existing node behavior; no separate global switch |
| Output handoff check | Pass collected fields explicitly to the comparison or judgment node | Compare each output against its input |
| Retrieval scope check | Check the target library and vector model identifier | Libraries on different vector models cannot be associated together |
| External action split | Outbound picking, backfill, and synchronization connect to a business interface | Forms and retrieval do not carry authorization or execution |

## Three common errors

1. Treating pending review as approved. In the sample, "status is pending review" and the draft sentence "has been approved" address the same field of the same transfer number, and the values are mutually exclusive, which makes them contradictory. If a document states no approval conclusion, the correct record is unsupported or pending verification.
2. Treating a retrieval hit as permission. Retrieval and semantic relevance do not handle permission or entity isolation. A matched transfer record does not mean the party is entitled to perform outbound picking. Authorization has to be confirmed by a downstream business interface.
3. Treating an interaction node as automatic execution. The form input node and the user selection node continue the workflow after submit or selection. They do not complete approval, writing, or synchronization on their own. Those actions require a separate system implementation.

## How to verify the setup

1. Take "status is pending review" from the sample and the draft sentence "has been approved." Compare the values of the same field on the same transfer number. If the two values are mutually exclusive, record the contradiction and correct the approved wording in the draft sentence.
2. Take the transfer request and the inventory snapshot from the sample. Compare transfer number, item code, quantity, and date range. If they agree, the materials point to the same transaction. If they disagree, record the field difference and keep it pending verification.
3. Take a paper input of an empty result, written as []. Check whether the downstream node handles the empty input as designed. Do not claim that a fictional rule retrieval necessarily returns empty. Record only the return situation and failure branch actually observed.
