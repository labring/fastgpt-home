# Omnichannel stock transfers: document chunking for document comparison

## What the documents look like

Brand omnichannel stock transfer work follows goods moving between stores and warehouses. The recurring materials are transfer requests, inventory snapshots, store shortage lists and transfer logistics notes. These come from ERP inventory, store POS, e-commerce orders and WMS, with daily and weekly update rhythms. Contract and transaction material comparison requires placing the requested quantity, the store-to-warehouse correspondence and the logistics receipt status under the same subject, the same period and the same field before any conclusion is drawn.

Two features of this material shape the chunking step. First, the same document can arrive as a scan, a table or a body paragraph, so parsing must preserve a document identity and version that can point back to the source. Second, a condition and the content it constrains must stay in one segment. If a transfer request quantity condition and a logistics note receipt scope are split across different segments, a retrieved fragment can lose the subject or the effective range that the comparison needs. The update frequency of the underlying data does not change this page's chunking behaviour, so it is not treated as a driver here.

## Constraints at the document chunking step

Parsing output separates original data from retrieval indexes. One group of original data can map to more than one index, and a hit on any one index recalls that group. Segmentation completeness therefore directly affects comparison. Full-text retrieval suits numbers, models and proper nouns; semantic retrieval suits natural-language description; hybrid retrieval merges multiple result paths through RRF; reranking requires a model and must be enabled by configuration. The reference limit is counted in tokens. The minimum relevance value takes effect only under semantic retrieval or result reranking, and it is a filter threshold. It does not carry permission or entity isolation. Image retrieval requires a corresponding image input and model capability, and the optional paths in the overall retrieval flow diagram do not all execute on every request. Libraries built on different vector models cannot be associated together; the identifiers are checked first and non-matching libraries are excluded.

Hypothetical paper exercise sample. Material A is a transfer request whose source text reads: "Requesting party: a store in East China; receiving party: a warehouse in East China; item: a certain model; requested transfer quantity: 120 units; request date: 10 March 2024; approval status is pending review." Material B is a transfer logistics note whose source text reads: "Shipping party: the East China warehouse; receiving party: the East China store; item: the same model; actual shipped quantity: 120 units; receipt date: 12 March 2024; receipt status: signed for." The draft sentence to be assessed is: "This transfer request has been approved and completed inbound receipt." The fields needed for the judgement are approval status and inbound receipt status. Material A states only pending review. Material B states only signed for. Neither states approval or completed inbound receipt.

## Three common errors

1. Treating Material B's "signed for" as "approved and completed inbound receipt." The input is the source text of Material A and Material B. The compared fields are approval status and inbound receipt status. Material A states only pending review, Material B states only signed for, and the draft sentence exceeds what the source text states.

2. Treating a retrieval hit as authorised execution. The input is one retrieval request. The comparison is between the retrieval result and the approval status field. Retrieval returns reference content only. It does not change Material A's pending review status and does not produce an inbound action.

3. Associating libraries built on different vector models and then inferring a missed recall. The input is the model identifiers of two libraries. The comparison is whether the identifiers match. When identifiers do not match, exclude the non-matching library and record the actual observation. Do not infer a runtime result.

## How to verify the setup

1. Input the source text of Material A, the source text of Material B and the draft sentence. Compare "approved and completed inbound receipt" in the draft sentence against the pending review and signed-for states stated in the source. If the draft sentence still contains approval and completed inbound receipt that the source does not state, judge it unsupported and keep the evidence gap.

2. Input the retrieval terms "certain model transfer approval status." Compare whether the returned reference content contains the approval status field of Material A. If the reference content lacks that field, record it as a gap caused by segmentation or the reference limit. Do not conclude that the material itself lacks the field.

3. Input an explicit paper empty result, written as []. Compare how the downstream comparison flow is designed to handle the absence of reference content. If the downstream flow treats the empty result directly as approval, record it as a design defect. Do not claim that a fictional rule retrieval necessarily returns [].

These checks observe and record; they do not assert that a first hit is guaranteed, that all relevant content is recalled, or that an unrelated query returns nothing. An unsigned termination is not a completed termination, a pending request is not an approval, and an offered option is not execution.
