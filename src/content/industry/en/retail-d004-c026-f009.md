# Brand-owned store operations: tool calls for document comparison

## What the documents look like
Brand-owned stores are staffed and accounted for directly by the brand, and they are not managed through franchise contracts. In this category the materials that reach contract-and-transaction comparison are daily sales reports, shift schedules, display photographs, and inventory transfer orders. These materials come from the POS system, member CRM, ERP inventory, and store inspections, with daily or weekly update frequency. Transfers, scheduling, and sales targets inside a brand-owned store are decided through the brand's internal approval chain, so quantities, periods, and authorization status recorded in the materials are the fields that comparison has to examine.

Tool calls and plugins do not replace that approval chain. The tool call node receives material text, decides whether to invoke a tool based on the tool introduction and its parameters, and passes results to later nodes. Retrieval or form collection supplies values; business verification, approval, database writes, and external synchronization each need their own downstream implementation.

A hypothetical paper exercise is used throughout this page. The material text supplied for comparison reads: "Store A daily sales report for 1 June 2024 to 30 June 2024 totals 120 units; inventory transfer order number T-0601 records 30 units transferred into Store A with status pending review; the shift schedule covers 1 June to 30 June." The draft sentence to be judged reads: "Store A completed the transfer of 30 units in June 2024 and counted them in sales." The draft turns a pending-review status into a completed transfer, and treats transferred units and sold units as one field. Comparison has to proceed field by field.

## Constraints at the tool calls step
The tool call node decides whether to invoke a tool from the tool introduction, the parameter introduction, and whether a parameter is required. Where a required parameter has no suitable value in context, the model may not invoke the tool; prompting can guide the user to supply the value, and the actual request then has to be checked. In advanced orchestration, available tools are connected to the tool call module by joining the diamond on the tool header to the diamond at the bottom of the module; the official guidance is to avoid adding too many tools at once and to tune a small set first.

The tool call termination node ends the current call. When the workflow reaches it, no further tools are invoked and the AI is not asked to summarize tool results. Custom tool variables extend tool input so that nodes not treated as tool parameters can still be invoked. None of these node behaviours constitutes approval, a database write, or external synchronization.

For the paper exercise, the transfer order status field reads pending review, and the draft sentence asserts a completed transfer. The same-field values pending review and completed are mutually exclusive, so the draft sentence is not supported by the material text. The 30 transferred units and the 120 sold units sit in different fields and cannot be merged.

## Configuration and implementation checks
| Configuration item | Hypothetical starting point for this exercise | How to check |
| --- | --- | --- |
| Tool introduction | States that input is the original text of daily sales reports, shift schedules, display photographs, and inventory transfer orders | Inspect whether the introduction covers situations where the tool should not be invoked |
| Required parameter | Transfer order number set as a required parameter | Observe whether invocation occurs when the transfer order number is absent, and record the actual request |
| Tool connection | Only the material-reading tool and the field-comparison tool are connected | Confirm the connection points and diamond joins in advanced orchestration |
| Tool call termination | Termination node placed after comparison completes | Observe whether other tools and AI summarization are no longer invoked |
| Custom variable | A period description added for the shift schedule node | Check whether that node is invoked accordingly |
| Retrieval scope | Original material text taken within the accessible target scope | Record missing fields as evidence gaps |

The starting point uses a small number of tools. The reason is the official guidance against adding too many tools at once and the recommendation to tune a small set before extending it. The comparison object is the number of connected tools against the debugging result.

## Three common errors
1. Writing a pending-review transfer order as a completed transfer. Input is the transfer order text and the draft sentence; the comparison is the status field value; the observable result is that pending review and completed are mutually exclusive values in the same field, so the draft sentence is unsupported.
2. Counting transferred units directly as sold units. Input is the 30 units on the transfer order and the 120 units on the sales report; the comparison is the object and field; the observable result is that these are different fields and cannot be combined.
3. Treating tool call termination as completed approval. Input is the termination node behaviour and the handover request; the comparison is the node's existing behaviour against a business action; the observable result is that termination only ends the call, while approval requires a downstream implementation.

## How to verify the setup
1. Input the hypothetical material text and the draft sentence; compare whether pending review and completed are mutually exclusive values in the same field. If the draft sentence still states a completed transfer, the check does not pass.
2. Input a request with the transfer order number missing; compare the required-parameter setting against whether invocation occurs. If invocation occurs, record the actual request and check where the parameter value came from.
3. Input the flow after the termination node; compare whether other tools or AI summarization are still invoked. If invocation continues, the behaviour does not match the termination node.

Where a paper input produces an empty result, the downstream design has to be checked; it cannot be claimed that a fabricated rule search necessarily returns empty. Libraries using different vector models cannot be associated together; check the identifier first and exclude those that do not match.
