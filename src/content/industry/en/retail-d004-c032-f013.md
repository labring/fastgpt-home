# Retail checkout and loyalty: access controls for document comparison

## What the documents look like

This page addresses one task inside retail checkout and loyalty operations: comparing contract and transaction materials, with access control and data isolation as the governing feature. The materials in scope are promotional price tags, membership points rules, daily checkout reports, and exception refund slips. They originate from POS systems, membership CRM, payment platforms, and price tag systems. The people who handle them are store checkout supervisors, CRM operations staff, and financial auditors. Compared with convenience store fresh-food ordering, this category centers on price and membership entitlements and does not manage short-shelf-life inventory. Errors surface as price complaints, cash shortfalls or overages, and membership entitlement disputes. The brief gives daily or per-shift update frequency; this page does not derive batch synchronization, full synchronization, real-time processing, or transaction-triggered mechanisms from that frequency.

A hypothetical drill sample is used throughout this page. A store checkout supervisor submits a handover request with three quoted material sentences: "Promotional price tag A-0715 applies to store S-03, effective 2025-07-15 through 2025-07-20, member price 9.9 yuan." "Membership points rule R-22 provides that spending reaches 100 yuan during this period earns 20 points." "Daily checkout report D-0716 records exception refund slip X-003 for that day, amount 45 yuan, status pending audit." The draft sentence under review reads: "Please synchronize this batch of materials to the CRM operations group and the financial audit group, and authorize both groups to edit promotional price tags and points rules."

## Constraints at the access controls step

Permission determination first checks an individual member's permissions, then takes the union of department and group permissions; the final permission is the combination of those results. Resource permissions are defined separately for team, app, dataset, and file/folder (collection). File-level permission is a feature specific to the FastGPT commercial edition. When it is off by default, collection readability matches the knowledge base and the system queries no collection permission records. When it is on, each file or folder generates a permission snapshot, and lists, details, and retrieval recall all authenticate item by item against that snapshot. Knowledge base permission remains the threshold at all times; collection permission cannot bypass it.

Retrieval recall filters by the files the current member can read only when authentication runs under the current member identity. In scenarios where a workflow preselects a knowledge base and does not authenticate by member identity, file-level filtering does not apply and recall still follows knowledge base permission. A team administrator does not bypass file-level permission. System root and the team owner are treated as holding all permissions on all files.

For the sample, the draft sentence requests that two groups be authorized to edit promotional price tags and points rules. Editing corresponds to write permission on the collection. The request is a pending handover request; a pending request is not a completed authorization. Whether the two groups already exist as collaborators, whether the file-level permission switch is on, and whether the submitted collaborator list retains the current creator are all open questions that the sample alone does not answer.

## Configuration and implementation checks

| Configuration item | Documented setting or implementation check | Relation to the sample |
| --- | --- | --- |
| Team permission entry | Team permissions are set on a dedicated permission page; select member/organization/group before configuring | Check whether the checkout supervisor, CRM operations group, and financial audit group have been added as collaborators |
| Knowledge base file-level permission switch | Dataset details page → file list → target row menu → Permissions; enabling requires knowledge base "can manage" | If the sample materials are stored in a knowledge base, confirm the switch state first; when off, a write operation configuring a single file permission is rejected |
| Collection role assignment | Read permission, write permission, administrator, creator; the creator cannot be granted or modified through collaborator configuration | The draft sentence requests "edit," which corresponds to write permission; check whether both groups hold it |
| Collaborator full overwrite | The submitted collaborator list is the final result and must include the current creator | If the handover request overwrites the existing list, check whether the creator record is retained |
| Retrieval recall authentication condition | Applies only when authenticating under the current member identity; a preselected knowledge base without member-identity authentication does not filter at file level | Check whether the handover request follows the member-identity authentication path |
| Team administrator boundary | A team administrator does not bypass file-level permission | Check whether the CRM operations group or financial audit group is mistakenly treated as able to bypass |

Hypothetical trial starting point: the checked result of the file-level permission switch is recorded as "off," because this page provides no actual state for that knowledge base. The comparison method is to view whether the knowledge base information bar shows the enabled notice. This value is not an official default.

## Three common errors

1. Treating retrieval relevance or a similarity setting as a permission filter. Retrieval recall filters by readable files, and files beyond authorization are not recalled; a similarity score does not perform entity isolation or permission exclusion. Observable error: inferring from "retrieval can find it" that the CRM operations group has the right to edit promotional price tags.
2. Treating "authorize both groups to edit" in the draft sentence as already executed. Collaborator configuration uses full overwrite semantics, and the submitted list is the final result; a request in pending state does not constitute completed authorization. Observable error: concluding the handover is complete without checking whether the creator is retained.
3. Treating team administrator identity as grounds to bypass file-level permission. A team administrator does not bypass file-level permission, and team-level management permission covers only the team's own resources. Observable error: concluding that the financial audit group can read all exception refund slips because it holds team management permission.

## How to verify the setup

1. Input promotional price tag A-0715 from the hypothetical sample together with the draft sentence "authorize both groups to edit promotional price tags." Compare whether the roles of the CRM operations group and the financial audit group in the file-level permission dialog are write permission, and whether the submitted list includes the current creator. Observable result: the condition is met only when both groups show write permission and the creator record is retained; if the list lacks the creator, the submission is rejected and must be resubmitted with the creator restored.
2. Input daily checkout report D-0716 and exception refund slip X-003. Compare the files actually visible to the financial audit group account in retrieval recall against the item-by-item authentication result of the file-level permission snapshot. Observable result: that account recalls only files for which it holds read permission, and files beyond authorization do not appear in the results; if a file beyond authorization appears, record the actual observation and check whether the authentication path is member-identity authentication.
3. Input membership points rule R-22 and the "synchronize to" wording in the handover request. Compare whether the request remains in pending state and whether a corresponding collaborator configuration submission record exists. Observable result: when the request stays pending and no submission record exists, the authorization state is incomplete; the existence of the request does not support inferring that authorization has taken effect.
