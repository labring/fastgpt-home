# Trade and FX administration: workflow routing for document comparison

## What the documents look like

This page covers the comparison of contracts against transaction materials in foreign-exchange receipt and settlement work, together with the trade directory context that surrounds it. The documents in scope are receipt advices for incoming foreign exchange, trade contracts, invoices, and foreign-exchange business registration materials. Compared with letter-of-credit document examination, the focus here is the authenticity of the foreign-exchange funds and the underlying trade background; a full set of letter-of-credit documents is not examined.

The data sources named in the brief are State Administration of Foreign Exchange policy, bank online banking, enterprise financial ledgers, and customs export data. Typical practitioners are foreign-trade finance staff, bank relationship managers, and foreign-exchange specialists. Errors in this work can lead to bank rejection of documents, abnormal foreign-exchange classification, and funds that cannot be credited. The update frequency is per transaction and monthly, so each comparison takes a single foreign-exchange receipt together with its corresponding contract and invoice as one working unit.

Contract and transaction material comparison requires alignment across three things: the same entity, the same period, and the same field. The receipt party, the contract signing party, the invoice issuing party, and the enterprise name in the registration materials belong to the same field; mutually exclusive values in that field constitute a contradiction. Amount, currency, and goods description are fields that must be compared item by item. Where any field is not stated in the materials, the conclusion can only be unsupported or pending verification.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it is triggered, the conversation enters an interaction state and the workflow state is recorded; after the user completes the required information and submits, the node collects the form information the user filled in and passes it to subsequent nodes. The user selection node is also a user-interaction node. It enters the interaction state in the same way, and when the user makes a choice, the node judges that choice and executes the corresponding "yes" branch. The interaction state, the state recording, and the hiding of the dialog box are existing behavior of these nodes and are not controlled by an additional switch.

Retrieval and form collection do not produce authorization. Order writing, document backfilling, and external status synchronization require a separate business interface or a subsequent process. A similarity score is a recall-ranking result and cannot serve as a filter for enterprise entity, permission, or business attribution. Libraries that use different vector models cannot be associated together; identifiers must be checked first and non-matching items excluded.

Hypothetical drill sample. A trade contract states: "The seller is Company A, the buyer is Company B, the goods are valves, the amount is one hundred thousand US dollars, and the signing date is 5 March 2024." A receipt advice states: "The payee is Company A, the payer is Company B, the amount is one hundred thousand US dollars, and the credit date is 20 March 2024." An invoice states: "The issuing party is Company A, the purchaser is Company B, the amount is one hundred thousand US dollars, and the invoice date is 8 March 2024." A draft sentence to be judged reads: "The three materials above are consistent in entity and amount, and the contract has taken effect and settlement has been completed." The second half of that draft sentence goes beyond what the materials state. The materials show only signing, invoicing, and crediting; they do not state the conditions for effectiveness or the status of settlement processing.

## Configuration and implementation checks

| Configuration item | Setting or check on this page | Reason and comparison method |
| --- | --- | --- |
| Form input node | Collect three required items: contract number, receipt advice number, invoice number | The official description states that submitted required information is passed to subsequent nodes; this page uses the three numbers as the comparison entry point |
| User selection node | Set a "materials complete" branch; after the user chooses, the corresponding "yes" branch executes | The official description states that different workflow paths are designed from user feedback; this page uses it to route materials awaiting supplementation |
| Interaction state check | Check that triggering enters the interaction state and records state | The official description treats this as existing node behavior; no separate global state switch is set |
| Output handoff check | Pass the three numbers collected by the form explicitly to subsequent retrieval and judgment nodes | Compare output against input item by item to confirm the numbers are not lost |
| Hypothetical trial starting value | The amount field comparison uses one hundred thousand US dollars as the starting value for this exercise | Taken from the sample text above and compared item by item against the contract, invoice, and receipt advice amounts; not an official default value |
| External operation division | Settlement processing and registration material backfilling are marked as requiring a separate business interface | Forms and retrieval do not execute authorized actions; collection is not treated as execution |

## Three common errors

1. Treating "the contract has taken effect and settlement has been completed" in the draft sentence as a fact proven by the materials. The sample text states only the signing date, invoice date, and credit date. The conditions for effectiveness and the settlement status are not stated, so the correct conclusion is pending verification.
2. Using a similarity score to filter out "irrelevant enterprises." The score is a recall-ranking result and cannot carry entity or permission filtering. Entity consistency must be established by comparing name fields item by item.
3. Treating the "yes" branch of the user selection node as approval. That branch only indicates that the user made a choice; it does not indicate that any authorization or business action has been executed.

## How to verify the setup

1. Input the three sample texts above together with the draft sentence. Compare the second half of the draft sentence against the fields stated in the materials, and observe whether the unstated effectiveness and settlement status are written as established fact. The condition is satisfied when the output marks that part as pending verification and lists the missing fields.
2. Input the entity fields from the sample. Compare the contract signing party, the invoice issuing party, and the receipt advice payee. Observe whether mutually exclusive values appear in the same field. The condition is satisfied when matching names are marked as aligned and mismatches are marked as contradictions with the specific field identified.
3. Input the three numbers collected by the form. Compare what is passed to subsequent nodes after submission against what the user entered, and observe whether the numbers are passed completely. The condition is satisfied when the three numbers match item by item. If downstream retrieval returns an empty result, check the handoff design against an explicit paper input of an empty list; do not infer that a retrieval rule necessarily returns empty.
