# Seller ratings management: access controls for document comparison

## What the documents look like

Seller ratings work draws on marketplace experience scores, marketplace service metrics, after-sales review records, and customer service systems. The day-to-day documents in this category are negative review handling records, experience score breakdowns, service diagnostic reports, and remediation ledgers. These materials update daily or weekly, which affects version-date checking during comparison but does not change the access design on this page.

Contract and transaction material comparison requires placing negative review handling records, experience score breakdowns, and remediation ledgers into a knowledge base, then controlling visibility by member identity. Customer service supervisors and quality inspection specialists typically need to read the same batch of materials, while store operations may hold a broader permission scope. Material categories and retrieval relevance do not substitute for access authorization, and retrieval settings cannot isolate records belonging to different stores or different entities.

## Constraints at the access controls step

Knowledge base permission is always the threshold; file-level permission cannot bypass knowledge base permission. In the closed state, collection readability matches the knowledge base. In the open state, each file generates a permission snapshot, and lists, details, and retrieval recall are authorized item by item against that snapshot. Retrieval recall filters by the files the current member can read, and this takes effect only when authentication runs under the current member identity. A workflow that preselects a knowledge base without member-identity authentication does not perform file-level filtering. Team administrators do not bypass file-level permission; team owners and system root are treated as holding full permission on all files. Deleting a file is limited to the creator, and administrators or write-permission collaborators cannot delete it.

Hypothetical exercise sample: the knowledge base "Ratings Material Library" has file-level permission enabled. The file "March 2025 negative review handling record" has quality inspection specialist A as creator, and its collaborator list contains A (administrator) and customer service supervisor B (read permission). The separate file "March 2025 experience score breakdown" is visible only to creator A. Draft handover request under evaluation: "Please add B to the collaborators of the experience score breakdown with read permission, for the April service diagnostic report check." Two sentences of the source material reads "Negative review handling record: March 2025, order suffix A001, consumer reported delayed shipment, resolution was a coupon compensation, status closed." "Experience score breakdown: March 2025, service metric score range recorded, breakdown content visible only to creator." The subject in the request is B, the object is the experience score breakdown, the state is a proposed collaborator addition, and the effective scope is the April check. This request has not been submitted and does not constitute authorization.

## Configuration and implementation checks

| Configuration item | Value or check item on this page | Basis and explanation |
| --- | --- | --- |
| Knowledge base file-level permission switch | Enabled | Official description states that configuring a single file's collaborators requires this to be enabled first |
| Materialization before enabling | Completes synchronously; failure keeps it closed | Official description states the switch stays closed on mid-process failure and can be retried |
| Collaborator list semantics | Full overwrite | Official description states the submitted list is the final result |
| Creator retention | List must contain the current creator | Official description states a list missing the creator is rejected |
| Retrieval recall authorization | Filters by files the current member can read | Official description states this applies only under member-identity authentication |
| Team administrator | Does not bypass file-level permission | Official description states team-level management covers only the team's own resources |

Hypothetical trial starting point: before adding B as a collaborator of the experience score breakdown, first check whether B holds read permission on the Ratings Material Library. This starting point is chosen because knowledge base permission is the threshold, and the value must be compared against B's knowledge base permission.

## Three common errors

1. Treating retrieval relevance as permission isolation. Error symptom: assuming that adjusting retrieval settings can prevent B from seeing the experience score breakdown. Executable check: input B's member identity and the experience score breakdown file identifier, compare the retrieval recall result against the file's collaborator snapshot, and observe whether the file is recalled for B.

2. Treating a draft request as an executed authorization. Error symptom: concluding from the handover request that B has already obtained read permission on the experience score breakdown. Executable check: input the request text and the current value of the collaborator list, compare the request state against the actual list record, and observe whether the list already contains B.

3. Ignoring creator retention so that a full overwrite removes the creator. Error symptom: submitting the collaborator list while omitting creator A. Executable check: input the proposed submission list and the current creator field, compare whether the list contains A, and observe whether the submission is rejected.

## How to verify the setup

1. Input B's member identity and the experience score breakdown file identifier from the hypothetical sample, compare that file's collaborator snapshot against B's permission record, and if the snapshot does not contain B and retrieval recall does not return the file, the isolation expectation is met. The request has not been submitted, so the result remains to be verified.

2. Input the proposed collaborator list from the hypothetical sample (containing B, not containing A), compare the list against the creator field, and if the submission is rejected with a missing-creator notice, the creator-retention expectation is met. This is a paper check and no submission was actually made.

3. Input B's knowledge base read permission state and the file-level permission switch state from the hypothetical sample, compare the two, and if the knowledge base read permission is absent, file-level authorization cannot take effect. That state is not provided and is recorded as an evidence gap.

Knowledge bases using different vector models cannot be jointly associated; verify identifiers first, exclude those that do not match, and do not run cross-model retrieval to compare missed recalls.
