# Marketplace category access: document chunking for document comparison

## What the documents look like

Category access work happens before listing or onboarding. The material set is dominated by business licenses, trademark registration certificates, brand authorization chains, and industry permits. These documents carry entity names, certificate numbers, validity periods, and authorization scope. The same document may be submitted in different versions across onboarding batches, so retrieval and comparison need to keep the original text, the version, and the constrained object together. When a conditional clause is split from the main clause it limits, later verification loses its basis for judgment.

Authorization chains commonly appear as a continuous statement covering authorizing party, authorized party, authorized category, authorized region, and authorization period. If the period is cut into a separate chunk, the retrieved fragment cannot point back to what it constrains. In FastGPT, one data group can map to multiple vector indexes. Original data is stored in MongoDB `dataset.datas`, and vectors are stored in the PostgresSQL `vector` field. Retrieval recalls vectors first, then fetches original data by vector ID; entries corresponding to the same original data group are merged and the highest score is kept. Chunk quality therefore determines whether recalled fragments can support comparison. A similarity score expresses textual relatedness and does not perform entity isolation or permission judgment.

## Constraints at the document chunking step

Chunking should follow the structure of the material itself. The authorizing party, authorized party, category, region, and period in an authorization chain should stay in the same segment. A minimum relevance value is a 0–1 number that filters low-relevance results and takes effect only in semantic retrieval or when result reranking is used. The citation limit is counted in tokens per search, not in top-k items, because chunk lengths differ greatly in mixed knowledge bases. This page treats these as the settings relevant to keeping authorization statements whole.

Hypothetical exercise sample: the source text reads, "Party A, XX Trading Co., Ltd., authorizes Party B, XX Brand Management Co., Ltd., to sell Class 25 clothing goods in the East China region, with an authorization period from January 1, 2024 to December 31, 2025." The draft sentence to be assessed reads, "Party B's authorization to sell Class 25 clothing goods in South China is valid until December 31, 2025." Comparison checks the region field and the period field. The source region is East China; the draft region is South China. The two values are mutually exclusive for the same field, so the draft's region statement is not supported by the source. The period fields match.

## Configuration and implementation checks

| Check item | Setting or action relevant to this page | Observation and comparison method |
| --- | --- | --- |
| Chunk granularity | Keep authorizing party, authorized party, category, region, and period in one segment | Inspect whether the period remains in the same segment as the region after splitting |
| Multiple indexes | One original data group can carry multiple indexes; index content is kept concise | Compare hit differences between a concise index and the full segment in retrieval |
| Search mode | Semantic, full-text, or hybrid retrieval chosen as needed | Use full-text for numbers and codes; use semantic or hybrid for natural language |
| Citation limit | Citation limit counted in tokens | Hypothetical trial starting value of 3000 tokens, chosen because authorization-chain segments tend to be long; compare with a smaller value to observe truncation |
| Minimum relevance | 0–1 value, effective only in semantic retrieval or result reranking | Record the threshold and the relevance distribution of recalled fragments |
| Training state | After material changes, check actual training and index state | Record upload success and retrieval refresh separately |

## Three common errors

1. Splitting region, period, and category into different segments. Input is the hypothetical sample above. Compare whether each segment still contains the entity and its limiting conditions. The observable result is that a period segment detached from the region segment cannot show what it constrains.

2. Using a similarity score in place of entity verification. Input is the draft sentence and the recalled fragment. Compare the entity names and field values in both. The observable result is a high score alongside mutually exclusive region values, which still does not make the draft sentence supported.

3. Treating upload success as retrieval refresh. Input is a changed material version. Compare the training and index state records. The observable result is a version that has been uploaded while retrieval still returns the old fragment.

## How to verify the setup

1. Input the hypothetical sample source text and the draft sentence. Compare the region field values: the draft region is South China and the source region is East China, so the two are mutually exclusive and the draft's region statement is judged unsupported. The period fields match and can be judged consistent.

2. Input three query types—terminology, numbers, and natural language—and observe whether the returned fragments retain the entity and its limiting conditions. If a query type returns a fragment missing the period or region, record it as a chunking issue and do not conclude that retrieval has failed.

3. Input an explicit empty query set as a paper exercise and check how the downstream design handles empty results. The empty result is used only to check the handling logic; it does not imply that any invented rule necessarily returns an empty set. After material changes, rely on the actual training and index state. Unobserved errors or automatic actions remain unknown.

A pending request is not approval. An offered option is not execution. An unsigned termination is not a completed termination. Retrieval is not authorization. Forms collect values; business verification, approval, database writes, and external synchronization require their stated downstream implementation.
