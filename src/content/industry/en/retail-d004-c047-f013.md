# Marketplace returns: document comparison with access controls

## What the documents look like

For document comparison in Marketplace returns, this page examines FastGPT access controls. Compare the material received with the sources used in the answer. The examples are hypothetical.

## Constraints at the access controls step

A refund-approval attachment can support checking its approval wording, without establishing that funds were returned or that the current account may read every transaction source. List the application, approval and relevant order or contract resources separately before comparing terms, then test actual reading scope for each original. Customer service, after-sales and warehouse inspection describe business participants; their system rights require testing rather than inference from a title.

## Configuration and implementation checks

| Permission or implementation check | Refund-source object | Actual evidence |
| --- | --- | --- |
| Approval wording | Approval is separate from refund execution | No inferred return of funds |
| Independent resources | List application, approval, order and contract | Inspect reading scope of each original |
| Business stages | Requested and approved amounts may differ | Establish the matter and each entry’s meaning |
| External source | Payment and warehouse content need separate grants | Internal roles do not replace external authentication |
| Added sources | Test the same resource with authorized and denied accounts | Record reads, denials and remaining gaps |

### Documented conditions

| Documented item / implementation check | Condition |
| --- | --- |
| `Team roles` | Inspect roles for the actual member identity. |
| `Resource permissions` | Inspect reading, editing and management by resource. |
| `Document classification` | Classification and tags do not replace authorization. |
| `External-system permissions` | Verify external-interface authentication separately. |
| `Per-account validation` | Test the same source with authorized and unauthorized accounts. |

## Three common errors

- If application-only access validates refund terms, inspect availability and grants for order, contract and approval originals. One request cannot reconstruct another source.

- If a denied identity reads approval material, retain actual content, account and configuration. Generating a refund explanation does not validate resource access.

- If readable approval becomes returned funds or a completed process, inspect payment outcomes and external authentication. Approval differs from execution, and requested versus approved differences are not automatically errors.

## How to verify the setup

An application without the original order or contract remains insufficient for checking applicable refund terms. Establish whether those sources exist and whether the current identity may obtain them. Inspect external authentication separately for payment or warehouse content. After adding sources, access the same resource with authorized and unauthorized test accounts, checking the new content’s scope. Retain read and denial results with the remaining transaction-evidence gaps; an answer restating approval text does not establish completion of the refund process.
