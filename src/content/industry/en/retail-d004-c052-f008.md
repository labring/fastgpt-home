# Pinduoduo seller campaigns: workflow routing for document comparison

## What the documents look like

Pinduoduo low-price campaign operations revolve around campaign resource slots, campaign inventory and refund-rate fluctuation. The working materials are the campaign application form, the product cost calculation sheet, the after-sales refund form and platform internal messages. Updates arrive daily or per campaign. For this page the scope is narrow: workflow routing inside contract and transaction material comparison. The application form, cost sheet, refund form and internal messages are read for subject, object, status and validity scope, and those extracted fields are passed to later nodes for checking. Retrieval and form collection do not by themselves constitute authorized execution.

Two features of this category shape the routing work. First, campaign status moves through submission and platform review, so a material can exist in a pending state that is not an approved state. Second, the same supplier or campaign object appears across several documents, so a match on subject alone does not settle whether an action is permitted. A retrieval hit shows that a material exists; it does not show that the subject holds supply authorization. Authorization status has to be read back from the source text.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the required fields and submits, the node collects the submitted form information and passes it to later nodes. The user selection node is also a user interaction node. When it triggers, the conversation enters an interaction state and records the workflow state; when the user makes a selection, the node evaluates that selection and executes the corresponding branch. Interaction state, waiting and dialog hiding follow the documented behavior. No global state switch is added here.

Collected information must be explicitly passed to later retrieval, judgment or interface nodes, and outputs are compared item by item against inputs. Order writing, document backfill and external status synchronization require a separate business interface or a later process. Retrieval is used to find candidate materials; a relevance score does not carry permission or entity isolation duties. This page does not claim any system error code or automatic business action that the source text does not describe.

Hypothetical paper exercise sample. A campaign operator keeps a paper record of one campaign application form. The source text reads: "Applicant subject: a supplier in East China; Campaign object: Summer Cooling Special; Application status is submitted, awaiting platform review; Validity scope: 1 July 2025 to 15 July 2025." A draft sentence is awaiting judgment: "This supplier has passed platform review and may execute supply for this special." The check takes the application form source text and the draft sentence as input, compares the four fields of subject, object, status and validity scope, and finds that the pending-review status does not constitute review approval. The draft sentence is unsupported.

## Three common errors

1. Treating a pending-review status as review approval. The sample source text says "submitted, awaiting platform review" while the draft sentence says "has passed platform review." These are mutually exclusive values on the same field, so the draft sentence is unsupported.
2. Treating a retrieval hit as authorization. Finding the campaign application form shows only that the material exists. It does not show that the subject has been granted supply authorization; authorization status must be checked back against the source text.
3. Treating form submission as a business write. The form input node only collects and passes information. Order writing and external synchronization require a separate interface; the submission action itself does not complete a write.

## How to verify the setup

1. Input the sample application form source text and the draft sentence. Compare the four fields of subject, object, status and validity scope. The expected observation is an inconsistency on the status field between awaiting review and passed review, judged unsupported.
2. Input the sample source text and a handover request: "Please release supply based on this application form." Compare the status the request relies on against the status in the source text. The expected observation is that the request lacks a basis for review approval, recorded as pending verification.
3. Input a paper empty result [] and a downstream judgment node. Compare whether the downstream node gives explicit handling for empty input. The expected observation is that the downstream node accepts the empty result as designed and does not interpret the empty result as authorization.

These checks describe expected observations. They do not report a completed test, an approval, a deployment or any other business action. Where a document field is not provided, it remains unknown.
