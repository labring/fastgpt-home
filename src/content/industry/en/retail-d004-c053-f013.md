# Channel receivables: access controls for document comparison

## What the documents look like

Channel receivables collection happens after credit sales, and its core concerns are credit granting and cash recovery. The working materials are the accounts receivable aging table, the dunning letter, the credit agreement, and the shipment freeze notice. Data originates in the finance system, bank receipts, distributor orders, and sales contracts. These materials update weekly or monthly.

Contract and transaction material comparison means placing the credit limit and payment term in a sales contract alongside the corresponding order and payment records, item by item, and judging whether a given shipment or collection request falls inside an already authorized range. The materials sit in different systems, and the same distributor may be represented by fragments held separately by brand finance staff, sales back-office staff, and the distributor owner. Access control and data isolation determine who can see which files and who can initiate a comparison.

## Constraints at the access controls step

Knowledge base file-level permission is a commercial-edition feature. In the default closed state, a collection's readability matches the knowledge base itself, and the system queries no collection permission records. When it is opened, every file or folder generates a complete permission snapshot, and list views, detail views, and retrieval recall each authenticate against that snapshot item by item. Knowledge base permission remains the threshold throughout; collection permission cannot bypass it.

Collaborator configuration uses full-overwrite semantics, so the submitted list is the final result. The creator cannot be granted or modified through collaborator configuration, and a submitted list must contain the current creator or it will be rejected. Team administrators do not bypass file-level permission. Team owners and system root are treated as holding all permissions on all files. Retrieval recall filters by the files the current member can read, and this applies only when authentication runs by current member identity; a scenario that preselects a knowledge base without member-identity authentication performs no file-level filtering. A relevance score does not carry permission or entity-isolation duties, and a similarity setting cannot exclude unauthorized records.

Hypothetical paper exercise sample: a brand finance staff member checks one credit agreement against one order inside a knowledge base. The agreement text reads: "Party A grants Party B a credit-sale limit of RMB 800,000, with a payment term of sixty days from the shipment date. This agreement is valid until December 31, 2025." The order record shows a shipment date of November 10, 2025, for RMB 820,000. The draft sentence awaiting judgment reads: "This shipment is within the credit limit and can be released normally." The comparison requires the same distributor, the same period, and the same limit field. The shipment amount exceeds the agreement limit, so the draft sentence and the agreement text hold mutually exclusive values on the limit field. The agreement validity covers the shipment date. Payment term and limit are different fields, and an unexceeded payment term does not change the fact that the limit is exceeded.

## Configuration and implementation checks

| Configuration item | Setting or check content | Relation to this page's sample |
| --- | --- | --- |
| Knowledge base file-level permission switch | Knowledge base administrator confirms open or closed state | When closed, collection permission inherits the knowledge base and the sample file cannot be authorized separately |
| File collaborator list | Submitted as full overwrite, must contain the current creator | Determines which members can see the sample credit agreement and order files |
| Member identity and team role | Check actual member identity; role names do not replace resource access testing | Brand finance, sales back-office, and distributor owner each verify their visible range |
| Retrieval recall authentication condition | Confirm whether authentication runs by current member identity | Without member-identity authentication, the sample files receive no file-level filtering |
| Permission snapshot and inheritance state | Confirm whether the target file is in inherited or independent state | An independent file is not overwritten by parent changes, and the sample comparison scope follows from this |
| External system interface authentication | Verified separately from FastGPT resource permission | Checked on its own when bank receipt or finance system data is connected |

Hypothetical trial starting point: set the credit agreement file to independent state and grant read permission only to brand finance. This starting point is chosen because the sample comparison needs to be confined to the finance role, and it is compared against an all-member-readable inherited state to observe whether the sales back-office account can still see the file. This starting point is a hypothetical setting for this exercise, not an official default value.

## Three common errors

1. Treating retrieval relevance as a permission filter. Input the same query and compare the recall lists of an authorized account and an unauthorized account. If both return the sample file, file-level authentication did not take effect, and the relevance score does not carry the function of excluding unauthorized records.

2. Omitting the creator from the collaborator list. When the full overwrite list is submitted without the current creator, the system rejects that submission. Check whether the submitted list matches the creator record and observe whether a rejection notice appears.

3. Treating a pending state as granted authorization. The sample draft sentence sits in a pending-judgment state and has no signature or approval record behind it. Compare the draft sentence with the agreement text on the limit field: the shipment amount exceeds the limit, the draft sentence is not supported, and the evidence gap is retained.

## How to verify the setup

- Verification one: input the sample credit agreement text and the order record, and compare the shipment amount of RMB 820,000 against the agreement limit of RMB 800,000, for the same distributor, the same period, and the same limit field. If the two values are mutually exclusive, the draft sentence "this shipment is within the credit limit" is not supported; record it as pending verification rather than as granted authorization.

- Verification two: input the brand finance account and the sales back-office account, and search the sample credit agreement file from each. Compare the two recall results. If the sales back-office account does not return the file, file-level authentication took effect; if it does return the file, record the actual observation and re-check the collaborator list and the authentication condition.

- Verification three: input an empty-result paper material and check the downstream design against an explicit empty list. Compare whether the empty-result handling logic treats it as no match; do not claim that a fabricated rule search necessarily returns an empty list. If the downstream design treats an empty result as no permission, record that design difference, and leave missing evidence missing.
