# Franchise filing management: access controls for document comparison

## What the documents look like

Franchise filing management handles legal disclosure and the commerce department system, and it does not handle specific site engineering. The main data sources are the commercial franchise information management system, enterprise licenses, store lists, and contract ledgers. Daily documents include franchise contracts, operations manuals, filing materials, and information disclosure files. The most time-consuming steps are preparing filing materials, checking the two stores and one year condition, and updating franchise information. During comparison, the authorization state recorded in the contract ledger and the store list determines which records can be read. Retrieval relevance does not carry the isolation duty, and a similarity setting is not a category, entity, or permission filter.

## Constraints at the access controls step

Knowledge base permission is always a threshold, and collection permission cannot bypass knowledge base permission. When file-level permission is off, collection readability matches the knowledge base exactly, and the system queries no collection permission records. When it is on, each file or folder generates a permission snapshot, and the list, detail view, and retrieval recall are authorized item by item against that snapshot. A team administrator does not bypass file-level permission. The team owner and system root are treated as holding all permissions on all files. Retrieval recall filters by readable files only when authorization runs under the current member identity. A scenario that preselects a knowledge base in a workflow without member-identity authorization does not apply file-level filtering.

Hypothetical paper exercise sample: inside a franchisor headquarters knowledge base, a collection named Regional Franchise Contract Ledger contains three sentences: "Party A is a franchisor headquarters. Party B is a franchisee. The contract signing date is March 1, 2024. The filing status field reads: filing materials have been submitted to the commerce department." A separate handover request awaits a decision: "Grant write permission on this ledger collection to the commerce liaison so that the filing status can be updated." The request states no authorization validity period and no approver. This request is pending, and a pending request is not approval.

## Configuration and implementation checks

| Configuration item | Documented setting or implementation check | Relation to this sample |
| --- | --- | --- |
| Knowledge base file-level permission switch | Off by default; the entry to turn it on is in the file list of the knowledge base detail page, in the menu of the target row | Determines whether the ledger collection can carry its own collaborators |
| Collection collaborator roles | Read, write, administrator, creator; the submitted list is a full overwrite | The handover request must be checked for whether the current creator remains in the list |
| Inherited state and independent state | Inherited state follows parent changes; independent state is not overwritten by the parent | If the ledger collection is inherited, changing a parent collaborator raises a conflict prompt |
| Team administrator boundary | A team administrator does not bypass file-level permission | The commerce liaison's team role does not replace collection collaborator configuration |
| Retrieval recall authorization condition | Filters by readable files only when authorization runs under the current member identity | A preselected knowledge base without member-identity authorization applies no file-level filtering |

Hypothetical starting value for this exercise: grant write permission on the ledger collection to the commerce liaison. This starting point is chosen because the handover request explicitly asks to update the filing status. The comparison object is whether the current creator still remains in the collaborator list. The submitted list is a full overwrite, so removing the creator causes rejection. This value is a paper starting point, not an official default.

## Three common errors

1. Treating retrieval relevance as access authorization. The input is a retrieval query against the ledger collection. The comparison is between the retrieval results and the collection collaborator list. The observable result is whether records are visible to a member who holds no collaborator entry. If a similarity setting is used in place of permission configuration, isolation fails.

2. Treating the team administrator role as file-level permission. The input is the commerce liaison's team role. The comparison is between that role and the ledger collection collaborator configuration. The observable result is whether the member is assumed to bypass file-level permission. A team administrator still needs collection collaborator authorization to read or modify the ledger.

3. Treating a submitted filing status as a completed filing. The input is the ledger sentence "filing materials have been submitted to the commerce department." The comparison is between that sentence and the draft wording "filing completed." The observable result is whether the draft rewrites a submission action into a filing outcome. This comparison does not show that a filing was approved; it records an evidence gap.

## How to verify the setup

1. Input the three ledger sentences and the handover request. Compare the authorization subject named in the request with the collection collaborator list. The condition is met when the list contains the current creator and the write permission points explicitly to the commerce liaison. If the list omits the creator, the submission is rejected. The request remains pending until an approver and a validity period are supplied.

2. Input the commerce liaison's team role and the ledger collection collaborator configuration. Compare the team administrator permission description with the file-level permission requirement. The condition is met when the member still requires collection collaborator authorization to read or modify the ledger. A team role name does not substitute for a resource access test.

3. Input the ledger sentence "filing materials have been submitted to the commerce department" and the draft sentence "filing completed." Compare the filing status field values in the two sentences. The condition is met when the draft sentence is recorded as unsupported rather than as a contradiction, because the two values are not mutually exclusive in the same field. This comparison does not show that a filing was approved, and the evidence gap remains open.

For retrieval checks, the observation is which readable files are returned for the current member identity, and the failure branch is a returned file whose collection collaborator list does not include that member. An empty reference output can be checked against a clearly labelled paper input of an empty list when reviewing downstream design, without asserting that any particular query returns an empty result. When collections come from different vector models, verify the identifiers first and exclude non-matching collections; do not run a cross-model retrieval to compare missed recalls. Image retrieval requires a corresponding image input and model capability, and reranking requires a model enabled in settings; neither path runs on every request.
