# Fruit-store procurement: document comparison with workflow routing

## What the documents look like

For document comparison in Fruit-store procurement, this page examines FastGPT workflow routing. Fruit purchase terms, test reports and arrival acceptance cannot be combined by product name alone. Report batches and actual receiving subjects must travel with the workflow input. The examples are hypothetical.

## Constraints at the workflow routing step

A proposed purchase order asks for green fruit. An acceptance excerpt says appearance awaits review, while a test-report cover belongs to the preceding supply batch. Collect the item, requirement passage and each source’s batch description. A person may request this batch’s report or appearance confirmation. Supply no invented testing criteria or findings. An earlier report does not establish this batch’s conformity, and a purchase requirement must not become an observed quality claim downstream.

## Three common errors

Requirement promoted to condition: “Green fruit requested” rewritten as “green fruit received” needs the actual acceptance observation. Old report applied to a new batch requires the complete report subject and delivery relationship. Pending review promoted to completion: A recipient claiming passed acceptance needs comparison with submitted status and the actual conclusion. These inspect fact status, report coverage and transferred state.

## How to verify the setup

Compare original excerpts with received input and connect report collection separately from appearance confirmation. Added batch evidence changes only the judgments it covers. Keep missing appearance confirmation visible. Loss attribution, returns and procurement-system writes require other actual records. Continued execution establishes neither full product conformity nor any party’s responsibility for losses.
