# Livestream after-sales service: context limits for document comparison

## What the documents look like
Livestream after-sales work clusters after a single broadcast ends. Refund applications, reshipment orders and the livestream order list arrive in the same window, and support staff reconcile the host's on-air promises, the order record and the warehouse handling result against one another. Script templates are ready-made text used to explain those promises.

For contract and transaction material comparison, the job is narrower: deciding whether a proposed sentence is supported by the source wording of the materials. The materials sit in Douyin store after-sales, support IM, warehouse WMS and logistics tracking, refreshed after each broadcast and daily. Comparison requires locking the same order, the same field and the same time range. A retrieval hit is a candidate ordering result and does not establish authorization, approval or the truth of a status field.

## Constraints at the context limits step
The context window is checked against the actual model capability. The reply limit only caps output length and cannot be treated as the full context window. The knowledge base reference limit is measured in tokens, so a long single passage can be trimmed; the question sample is needed to confirm whether the supporting sentence entered the context intact. Earlier input changes retrieval and judgment for the same question, so empty history and history-bearing runs are observed separately. When a fixed reply format such as json_schema is used, field completeness and parse success are verified. Semantic recall and relevance scores only affect candidate ordering; they do not perform permission or entity isolation, and retrieval results do not replace an authorization decision.

Hypothetical paper exercise sample. Source material sentence one: "Order A-7301, placed on 12 April 2025, product is two summer short-sleeve items, refund application status is pending review." Source material sentence two: "The host stated during the 12 April livestream that this order may be reshipped once." Proposed sentence to be judged: "The refund application for order A-7301 has been approved, and the warehouse will reship on 13 April." The comparison objects are the refund application status field and the reshipment arrangement. The authorization boundary is review by the after-sales supervisor. No actual refund or reshipment execution is involved.

## Three common errors
1. Treating the reply limit as the full context window. Input is the sample material and question; comparison is between the reply limit and total material length; the observable result is whether the supporting sentence appears in the model input. If the sentence is absent, the material has been truncated and the judgment cannot rely on the full material.

2. Treating a retrieval hit as authorization or status confirmation. Input is the proposed sentence and the source material; comparison is between the two values of the same status field, "pending review" and "approved"; the observable result is whether mutually exclusive values appear for one field. A retrieval match does not establish that the status changed.

3. Associating libraries across different vector models, or describing RRF as a switch that can be turned on. Input is the library identifier and the vector model identifier; comparison is whether they match; the observable result is recorded as an actual observation only, without inferring runtime behavior. RRF is a fusion process for mixed results, not a configurable toggle.

## How to verify the setup
1. For the sample source material and the proposed sentence, input is "order A-7301, refund application status is pending review" and the proposed sentence "the refund application has been approved." Comparison is between the two values of the same field. The expected observation is that the proposed sentence is not supported by the material and must be marked as pending verification. This is an expected result, not a completed test.

2. For empty-history handling, input is the explicit paper input `[]`. Comparison is against the downstream node's output design when no reference content is present. The expected observation is that the downstream node handles the empty result as empty. Do not claim that a fictional rule retrieval necessarily returns `[]`.

3. For structured handling, input is a reply format using json_schema. Comparison is between the returned fields and the preset field list. The expected observation is that fields are complete and parsing succeeds, and text length is not the sole passing condition.

Operations handover must distinguish which materials, actions and requests are at which authorization state. Retrieval and forms collect values; business verification, approval, database writes and external synchronization require their stated downstream implementation. Where a document field is not provided, it remains unknown.
