# Short-video affiliate sales: workflow routing for document comparison

## What the documents look like

Short-video affiliate sales rely on long-term content exposure and product-link conversion, not on live explanation. This shapes the material set for contract and transaction comparison into four document types: short-video scripts, attached-product lists, commission plans, and violation feedback. Content operators, creator business development staff, and product distribution specialists hand these materials across daily and weekly cycles. The product reference in a script, the attached object in a list, and the ratio range in a commission plan need to stay checkable on the same field. The update rhythm describes when materials appear and does not imply batch synchronization or transaction-triggered mechanisms.

A hypothetical paper sample is used throughout this page. The material text reads: "Party A commissions Party B to publish an attached-product video on a designated short-video account. The attached product is thermal cup model A. The commission ratio is settled at fifteen percent of transaction amount. The cooperation period runs from March 1, 2025 to March 31, 2025." The draft handover request under judgment reads: "Please change the attached product to thermal cup model B per this material and proceed to settlement." The material states object model A, the request states object model B, the same field holds mutually exclusive values, and the request exceeds the material authorization boundary. The request is unsupported.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The user selection node is also a user-interaction node. After the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. Both node types can be added repeatedly and trigger execution. They collect information and pass it to subsequent nodes.

Order writing, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval and forms do not constitute authorized execution. The authorization status of a handover request must be checked separately. A pending request is not approval, an offered option is not execution, and an unsigned termination is not a completed termination.

At this routing step, the material identity, object, stage, date scope, and authorization boundary all need to be carried as context. The sample material identifies the parties, the object, the ratio, and the cooperation window. The draft request alters the object and asks to proceed to settlement. The comparison must stay on the same subject, the same period, and the same field. Only mutually exclusive values on the same field count as a contradiction. A field that is not stated, or evidence that covers only a related stage, is recorded as unsupported or pending verification.

## Configuration and implementation checks

| Configuration item | Role on this page | Setting or check method |
| --- | --- | --- |
| Form input node | Collects required information for the handover | Enters interaction state on trigger; passes submitted information to later nodes |
| User selection node | Branches on material version or object | Executes the corresponding "yes" branch after the user makes a choice |
| Interaction state check | Confirms the node recorded state and waits for interaction | Check per documented behavior; no separate global switch is set |
| Output handover check | Confirms collected information reaches later nodes | Compare each input field against the downstream receiving field |
| External action separation | Distinguishes node behavior from business actions | Order writing and external synchronization connect to a separate business interface |
| Hypothetical trial starting point | Sample commission ratio value | This trial uses fifteen percent, compared against the material text |

The hypothetical trial starting point of fifteen percent is chosen because the sample material text states that ratio. The comparison method is a field-by-field check of the ratio field in the plan document against the material text. This value belongs to this hypothetical trial and is not an official default.

## Three common errors

1. Treating an object substitution in the draft request as a completed change. The input is the request text; the comparison object is the object field in the material text; the observable result is that the two do not match. The sample material states model A, the request states model B.

2. Treating information collected by a form as an authorization credential. The input is the submitted form value; the comparison object is whether the material states an authorization scope; the observable result is that the material does not state that authorization.

3. Treating a retrieval hit as permission isolation. The input is the returned retrieval entry; the comparison object is the subject identifier on the entry against the requesting subject; the observable result is that the two identifiers do not match. A relevance score is not a category, entity, or permission filter.

## How to verify the setup

1. Use the sample material text and the draft request above. The input is the material text and the request text; the comparison object is the object field and the authorization scope field; if the request object does not match the material object and the material states no change authorization, the condition "unsupported" is satisfied.

2. Use the sample material to check the interaction node output. The input is the submitted form value and the user selection result; the comparison object is the downstream receiving field; if the submitted value reaches the downstream field completely and the branch executes per the selection, the handover condition is satisfied; if the downstream field receives no value, record a gap.

3. Use an explicit empty-reference paper input to check the downstream design. The input is a clearly stated empty array; the comparison object is the downstream node's handling design for empty values; if the downstream design declares no empty-value branch, record it as pending verification. Do not claim that retrieval necessarily returns an empty result.

Across libraries that use different vector models, joint association is not available. Check identifiers first, exclude entries that do not match, and record the actual observation. Do not run cross-model retrieval to compare missed recalls. The documented total-flow diagram lists optional paths that are not all executed on every request: image retrieval requires a corresponding image input and model capability, and reranking requires a model and must be enabled per settings.
