# Group-buy leader operations: context limits for document comparison

## What the documents look like

Group-buy leader operations manages community pickup nodes and commission relationships. The working materials are leader service agreements, commission tables, pickup manifests and community announcements, updated daily or per group. Contract and transaction material comparison has to read agreement clauses, commission bases and pickup quantities inside one context, so the content length a model can reference in a single request determines whether several materials fit together at once.

The reply cap controls output length and does not replace the model's maximum context. Treating the two as the same thing allows a long agreement to be truncated without anyone noticing. The knowledge base reference limit is measured in tokens, and together with individual material length and the question sample it decides whether referenced content is trimmed.

## Constraints at the context limits step

Hypothetical drill sample: a community group-buy platform signs a Leader Service Agreement with leader A. The agreement states in two sentences: "This agreement takes effect on the date both parties sign, for a term of six months." and "Commission is settled on the number of items actually signed for on the pickup manifest, at 2 yuan per item." A separate September Pickup Manifest records: "September 3, Community A self-pickup point, 120 items signed for." The draft sentence to be judged is: "Leader A's September commission is 240 yuan and the agreement has taken effect."

Checking requires confirming the agreement's signature status, the manifest's subject and period, and whether the commission unit price is the same field. Any item not stated remains pending verification. Semantic recall and relevance scores only affect content ordering and do not carry permission or subject isolation. The consistency requirement between the retrieval library and the vector model is limited to vector retrieval itself and does not extend into a claim that external systems must use the same model.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Reason and comparison method |
| --- | --- | --- |
| Maximum context | Use the value actually displayed for the selected model | Compare against the combined token count of agreement plus manifest to confirm both materials fit in one request |
| Reply cap | 800 tokens as the hypothetical starting point | Compare against the number of supporting fields the draft sentence needs, to confirm the basis and handling action can be expressed in full |
| Knowledge base reference limit | 2000 tokens as the hypothetical starting point | Compare against the length of a single agreement section to observe whether referenced content is trimmed |
| Minimum relevance | 0.5 as the hypothetical starting point | Compare against semantic retrieval or rerank scores; serves only as a filtering threshold, not a permission judgment |
| Memory turns | 2 turns as the hypothetical starting point | Compare retrieval results for the same question with empty history and with two turns of history, to rule out context differences |
| Reply format | json_schema selected for this hypothetical case | Compare against the draft sentence's field list to confirm fields are complete and parsing succeeds |

## Three common errors

1. Treating the reply cap as the full context window. Input is a long agreement plus manifest; the comparison object is the maximum context displayed for the model; the observable result is that material is truncated without being noticed.
2. Using a relevance score to exclude unrelated subjects. Input is a cross-leader query; the comparison object is the score threshold; the observable result is that low-scoring records are mistaken for records without permission.
3. Writing a pending-review state as already effective. Input is the draft sentence "the agreement has taken effect"; the comparison object is the signature and effectiveness wording in the agreement text; the observable result is a definite conclusion given while effectiveness evidence is not stated.

## How to verify the setup

1. Input the agreement text and manifest text from the hypothetical sample, then compare whether the subject, period and unit price fields in the draft sentence match the same fields in the source text. A contradiction is judged only when all three are stated and hold mutually exclusive values; when a field is not stated, record it as pending verification.
2. Input the same question under two conditions, empty history and two turns of history, and compare whether the returned referenced content differs because of the context difference. Observe whether the reference limit triggers trimming.
3. Input an explicit paper empty result `[]` and compare whether the downstream design handles it as an empty reference. Do not claim that a fabricated rule search must return an empty array. For cross-model libraries, check identifiers first and exclude non-matching ones; do not run cross-model retrieval to compare missed recalls.
