# Group-buy leader operations: workflow routing for document comparison

## What the documents look like

Group-buy leader operations centre on community pickup nodes and commission settlement. The work does not include cold-chain quality inspection, which belongs to fresh-produce receiving. The everyday materials are leader agreements, commission tables, pickup lists and community announcements. They come from the community group-buy backend, leader chat groups, order details and after-sales records. The supplied brief gives a daily and per-group update frequency; this page does not derive batch synchronisation, full synchronisation, real-time or transaction-triggered mechanisms from that frequency.

For contract and transaction material comparison, the difficulty is that these materials sit in different sources. A leader agreement states a commission rate and a settlement counterparty. A commission table records the amount payable for a given group and period. A pickup list records actually delivered quantities. Subject, period and field must be aligned one by one before any consistency judgement can be made. A field that is not stated in a document remains unknown; it cannot be treated as absent by inference from another category.

## Constraints at the workflow routing step

Workflow routing here has one job: connect material collection, comparison judgement and manual review into an executable sequence, and make clear which steps only collect information and which steps need a separate business interface.

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user submits the required information the node passes that information to later nodes. The user selection node is also a user interaction node. When it triggers, the conversation enters the interaction state, and after the user makes a choice the node evaluates that choice and executes the corresponding "yes" branch. Both nodes can be added repeatedly and trigger execution. The interaction state record is behaviour of the interaction nodes; no separate global state-recording switch is set here.

Collected information must be explicitly passed to later retrieval, judgement or interface nodes, and output compared against input item by item. Order writes, document backfill and external state synchronisation require a separate business interface or a later process. Routing itself does not perform those business actions. Retrieval is not authorization, and a relevance score is not a category, entity or permission filter.

Hypothetical paper exercise sample, clearly labelled as hypothetical. The leader agreement text supplied for checking reads: "Party A entrusts Party B to carry out group-buy promotion in Sunshine Lane community; commission is settled at eight percent of the order amount actually delivered in the current month; the settlement counterparty is the receiving account designated by Party B." The commission table text reads: "March 2025, Sunshine Lane community, commission payable 1,200 yuan, payee Li." The draft sentence to be assessed reads: "The March 2025 Sunshine Lane community commission has been settled in full under the agreement." Comparison points: the agreement states the settlement counterparty is the receiving account designated by Party B, and the commission table states the payee is Li. Neither material states the specific details of the receiving account designated by Party B, so counterparty consistency in "settled in full under the agreement" is not supported. Neither material states payment completion status, so the settlement fact remains to be verified.

## Configuration and implementation checks

| Configuration item | Type | Description |
| --- | --- | --- |
| Form input node | Documented official behaviour | Enters interaction state on trigger, collects required information, passes it to later nodes after submission |
| User selection node | Documented official behaviour | After the user makes a choice, executes the corresponding "yes" branch; verify each branch connection individually |
| Interaction state check | Implementation check | The state record is behaviour of the interaction nodes; no separate global state-recording switch is set or claimed |
| Output handover check | Implementation check | Collected information is explicitly passed to later retrieval, judgement or interface nodes, and output is compared against input item by item |
| External action separation | Implementation check | Order writes, document backfill and external state synchronisation require a separate business interface or later process |
| Sample comparison starting point | Hypothetical trial starting point | This exercise starts from the agreement commission rate and the commission table amount; the reason is that both materials carry a period and a community identifier; the comparison method is field-by-field checking within the same period and same community |

## Three common errors

1. Treating payee information collected by a form as settlement authorization. The form input node only collects and passes information the user fills in. Authorization status requires confirmation through a separate business interface; the collection act itself does not create authorization.
2. Treating the "yes" branch of a user selection node as approval. The user selection node executes the corresponding branch after the user makes a choice. A choice result is not a completed approval; approval needs its own implementation.
3. Treating retrieval results as a permission filter. Semantic recall and relevance do not perform permission or entity isolation. Materials returned by retrieval still need their subject, period and fields checked against the scope of this comparison.

## How to verify the setup

1. Input the agreement text and the commission table text from the hypothetical exercise sample above, and compare the settlement counterparty field of the two materials. The agreement states the settlement counterparty is the receiving account designated by Party B; the commission table states the payee is Li; neither material states the specific details of the receiving account designated by Party B. Expected observation: counterparty consistency in the draft sentence "settled in full under the agreement" is not supported, and the settlement status remains to be verified. If the flow judges the two materials to be consistent on settlement counterparty, the output handover check has not passed.
2. Input the draft sentence from the hypothetical sample and compare whether it goes beyond what the materials state. The draft sentence contains "settled in full under the agreement", and the materials do not state payment completion status. Expected observation: the flow marks the sentence as to be verified and preserves the evidence gap on payment status. If the flow directly outputs a settlement conclusion, the comparison judgement step has not passed.
3. Input an explicitly paper-based empty result from a manual input and check the downstream design. Carry the empty result into the downstream branch and observe whether the flow enters a manual review path. Expected observation: the empty result triggers the manual review path and does not automatically generate a settlement or authorization conclusion. An empty result does not mean that a retrieval of a fictional rule necessarily returns empty; it is used only to check the downstream handover design.
