# Cross-border product labels: workflow routing for document comparison

## What the documents look like

For cross-border product compliance and labelling, comparison materials cluster around four document types: product test reports, English-language labels, MSDS files, and platform prohibited-item lists. These materials are updated irregularly and are triggered by each new product listing, so a comparison workflow needs to be orchestrated per batch rather than per calendar period. The core action of contract and transaction material comparison is a field-by-field check of label text, report conclusions, and compliance statements agreed in the contract.

Compliance specialists and product managers hand materials over while those materials sit in different states: draft, pending review, or signed. Workflow routing needs to preserve those state differences rather than flattening them into a single "ready" assumption. The four document types also differ in what they can support. A test report carries a model scope and a signing state; a label carries a version; a prohibited-item list carries platform policy scope. Comparison that ignores these boundaries produces a conclusion the evidence does not carry.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues downward after the user completes the interaction. The User Selection node is also a user interaction node. When the user makes a selection, the node evaluates that selection and executes the corresponding "yes" branch. Both nodes can be added repeatedly and trigger execution. These are the documented node behaviours.

Hypothetical paper exercise sample: the source text of a batch product test report states "This report covers the label compliance items for Model A. Issue date: a given month and year. Report status: draft." The proposed handover request is "Please confirm label compliance based on this report and release for listing." The report this request relies on is in draft status and does not state a final issuance conclusion.

At routing time, keep four categories distinct. Node behaviours already documented: entering the interaction state, recording workflow state, executing a branch. Fields actually configurable: form required items, selection branch connections. Manual verification actions: field-by-field comparison of report against label. Business actions requiring a separate system implementation: order writes, document backfill, external status synchronisation. Retrieval or form collection does not constitute authorised execution. Semantic recall and relevance scores do not perform permission or entity isolation. Libraries built on different vector models cannot be associated together; check the identifier first and exclude non-matching libraries. For empty-result handling, a clearly labelled paper input of `[]` can be used to check downstream design; this does not claim that a fabricated rule retrieval necessarily returns empty.

## Configuration and implementation checks

| Configuration item | Setting or check for this page | Implementation boundary |
|---|---|---|
| Form Input node | Collect report number, label version, contract number | Passed to later nodes after submission |
| User Selection node | Set "continue comparison" and "return for supplement" branches | Execute the branch matching the selection |
| Interaction state check | Confirm the interaction state is entered after triggering | State recording is node behaviour |
| Output handoff check | Pass form information to the downstream comparison node | Compare output against input item by item |
| External action separation | Order writes and document backfill connect to separate interfaces | Not merged into interaction nodes |
| Retrieval scope check | Confirm target library identifier matches the vector model | Cross-model libraries are not associated |

This page assumes a trial starting point of three required form items (report number, label version, contract number). The reason for choosing three is that they correspond one-to-one with the three material types awaiting comparison in the sample. The comparison method is an item-by-item check of whether all three are passed completely to the downstream node after submission. This starting point is a hypothetical trial setting for this page, not an official default value.

## Three common errors

1. Treating a draft-status report as a compliance conclusion. Input: the sample wording "Report status: draft." Comparison object: the value "issued." Observable result: the draft is not treated as a final conclusion. A missing issuance conclusion counts as unsupported.

2. Treating form collection as authorised execution. Input: the proposed handover request "confirm label compliance and release for listing." Comparison object: the documented behaviour range of the node. Observable result: form submission does not trigger a listing action. Authorised execution requires a separate business interface.

3. Inferring retrieval results after associating libraries across different vector models. Input: two libraries with different vector model identifiers. Comparison object: consistency of the model identifiers. Observable result: non-matching identifiers are excluded and the actual observation is recorded. No inference is made about missed recall or redundant results.

## How to verify the setup

1. Input the sample wording "Report status: draft" and the proposed handover request. Compare the report status field against the value "issued." Observable result: the draft is not judged as a compliance conclusion and is recorded as pending verification.

2. Input the three required form values. Compare field completeness after submission into the downstream node. Observable result: all three values appear in the downstream node input; any missing item is recorded as a gap.

3. Input the paper empty result `[]`. Compare the downstream node's design for handling empty input. Observable result: the downstream node does not treat the empty result as a compliance pass and retains the unsupported status.

These checks describe expected observations under the stated hypothetical inputs. They do not claim that any test has been run, that a deployment exists, or that any approval or release action has occurred.
