# Cross-border product labels: access controls for document comparison

## What the documents look like

Contract and transaction material comparison in cross-border product compliance and labeling draws on product test reports, English labels, MSDS files, and platform prohibited-item lists. These materials appear before listing and import, and their purpose is product safety and label evidence. A single batch may be submitted by a compliance specialist, a product manager, and an external testing body, so the visible range of each file differs across team members.

When file-level permission is enabled, each file or folder generates a permission snapshot, and lists, details, and retrieval recall are each authenticated against that snapshot. Knowledge base permission remains the threshold; collection permission cannot bypass knowledge base permission. Materials update irregularly, and each new listing triggers a comparison round, so permission configuration needs to be checked in step with material versions.

## Constraints at the access controls step

Comparison conclusions depend on the range of readable files. When a member lacks file read permission, that file is invisible in lists and retrieval, and the comparison input is incomplete. Retrieval recall filters by the files the current member can read, and files beyond authorization are not recalled. A similarity score does not perform permission filtering, and retrieval relevance does not replace an authorization decision. A workflow that preselects a knowledge base without authenticating by member identity does not apply file-level filtering and still recalls by knowledge base permission. A team administrator does not bypass file-level permission; team-level management permission covers only the team's own resources.

Hypothetical paper exercise: a team knowledge base has file-level permission enabled. File A is "Product test report - batch 2601," created by member A, with a collaborator list containing member A and member B, where member B holds read permission. File B is "English label - batch 2601," created by member C, with a collaborator list containing only member C. Proposed sentence to be judged: "Member B can read File B and complete the label comparison on that basis." The request attaches no collaborator record for File B and states no authorization source for member B on File B.

## Configuration and implementation checks

| Check item | Documented setting or implementation check | Relation to the sample |
| --- | --- | --- |
| Knowledge base file-level permission switch | In the closed state no collection permission records are queried; in the open state each item is authenticated, and the switch is the only entry point that produces collection-level custom permission | The sample knowledge base is open, so File A and File B are both authenticated by snapshot |
| Collaborator full-overwrite semantics | The submitted collaborator list is the final result and must include the current creator | The File B list contains only creator C, and member B is absent |
| File read permission and knowledge base read permission | Viewing a list or detail requires knowledge base read permission plus that file's read permission | Member B has no file read permission record for File B |
| Retrieval recall authentication condition | Effective only when authenticating by current member identity; a preselected knowledge base without member-identity authentication applies no file-level filtering | The proposed sentence does not state whether the comparison entry authenticates by member identity |
| Team administrator boundary | A team administrator does not bypass file-level permission | The sample does not state whether member B holds a team administrator role |
| Hypothetical exercise starting point | This exercise starts from File A's collaborator list containing member B with read permission, for comparison with the File B list; this starting point is a paper setting, not an official default | Compare the two collaborator lists to judge member B's authorization state on File B |

## Three common errors

1. Treating retrieval relevance as permission filtering. Input: member B searches the knowledge base for "batch 2601 label." Compare the retrieval result with the File B collaborator list, and observe whether member B actually recalls File B. A relevance score does not perform authorization, and a file without authorization should not be recalled because of similarity.
2. Treating a pending review or pending handover as granted authorization. Input: the proposed sentence "Member B can read File B." Compare that sentence with the File B collaborator list, and observe whether the list contains member B. When the list does not contain member B, the sentence is unsupported and the authorization source remains to be verified.
3. Treating team administrator identity as grounds for bypassing file-level permission. Input: member B's team role record. Compare that record with the File B file-level permission requirement, and observe whether the document lists team administrator as an identity that bypasses file-level permission. The document states that a team administrator does not bypass file-level permission.

## How to verify the setup

1. Input the File A collaborator list and the File B collaborator list. Compare the member differences between the two lists, and observe whether member B appears in the File B list. Member B holds read permission on File A and has no record in the File B list, so the proposed sentence "Member B can read File B" is unsupported.
2. Input member B querying "batch 2601 label" at a retrieval entry that authenticates by member identity. Compare the recall result with the readable range of File B, and observe whether File B appears in the result. If File B does not appear, record this as an observation that permission filtering took effect; if it appears, record the actual observation and check the authentication condition. An empty result can be checked against downstream design using a paper input of an empty list, without claiming that a fictional-rule search necessarily returns empty.
3. Input the File B creator record and the collaborator list. Compare whether the creator is in the list, and observe whether the list satisfies full-overwrite semantics. The File B list contains creator C and satisfies the condition; if a submitted list omits the creator, that submission is rejected. The proposed sentence attaches no File B collaborator record, so the authorization state remains to be verified.
