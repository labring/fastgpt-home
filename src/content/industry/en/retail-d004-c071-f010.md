# Cross-border settlements: citation tracing for document comparison

## What the documents look like

This page covers one task inside cross-border platform settlement and foreign exchange: comparing contracts against transaction materials, with attention to citation sources and traceability. The materials involved are funds-collection records for orders that have already been completed. Fraud and chargeback handling sits outside this scope.

The working materials come from platform settlement centers, bank statements, payment provider back offices, and ERP order records. On a routine basis the documents to reconcile include platform settlement statements, exchange rate tables, service fee invoices, and receipt reconciliation sheets. These materials update weekly or monthly, and the people handling them are typically cross-border seller finance staff, tax accountants, and platform operations staff. Errors in this work affect profit calculation, tax filing accuracy, and cash flow planning.

For citation tracing, every conclusion needs to point back to specific source text. Materials may originate in different systems, and field names and period definitions do not always line up. Checking therefore requires confirming that the subject, the object, the period, and the validity scope are aligned before any statement is treated as supported.

## Constraints at the citation tracing step

Retrieval locates candidate content. It does not decide whether material falls inside an authorization boundary. The knowledge base search node can associate one or more knowledge bases that share the same vector model. Its output is an array of citations, and the array length may be zero. An empty array means the search path completed without matching content, and the downstream design must be able to carry that case.

The minimum relevance value is a filter threshold. It takes effect only under semantic retrieval or when result reranking is used. It does not perform permission filtering or entity isolation. Hybrid retrieval merges multiple result paths through RRF, and a rerank model reorders candidate text and returns a score between 0 and 1. The citation limit controls, in tokens, the maximum amount of content cited per search. These parameters affect relevance ordering of retrieved results. Whether material has been authorized or approved is a separate layer of fact.

A relevance score is not a category, entity, or permission filter. It does not exclude unrelated businesses or unauthorized records. Retrieval is not authorization. Forms collect values, and business verification, approval, database writes, and external synchronization each require their own stated downstream implementation. No scheduled trigger or hidden control is assumed here.

## Configuration and implementation checks

The configuration below is built around one hypothetical exercise sample. It illustrates a checking method. It does not represent any real record or any operation that has been carried out.

Hypothetical exercise sample: the material source text reads "Party A: Xinghai Supply Chain Co., Ltd.; Party B: Yuan'an Trading Co., Ltd.; settlement period: March 2025; platform settlement statement number: ST-2025-03-001; settlement amount: RMB 86,400; exchange rate table version: FX-2025-03; service fee invoice number: INV-2025-0312." The draft sentence to be assessed reads "Xinghai Supply Chain Co., Ltd. completed settlement payment to Yuan'an Trading Co., Ltd. in March 2025." The handover request to be assessed reads "Please confirm, based on the above materials, that this settlement has been fully executed and archive it."

## Three common errors

1. Treating a retrieval hit as authorization confirmation. Retrieval returns candidate content. Whether material falls inside an authorization boundary, and whether it has been approved, must be checked separately. In the hypothetical sample, the draft sentence states that settlement payment was completed, while the source text records only the settlement statement number and amount. The source text does not record a payment status field, so that conclusion is not supported.

2. Treating minimum relevance as an entity or permission filter. Minimum relevance only filters low-relevance results. It does not exclude unrelated businesses or unauthorized records. If the hypothetical search returned another company's settlement statement, a low relevance score would not mean that record had been excluded. The subject identifier still requires manual checking.

3. Treating a pending review state as executed. In the hypothetical sample, the handover request asks to confirm that the settlement has been fully executed and to archive it. The source text records neither a payment execution status nor an archive status. That request remains pending verification and cannot be judged complete from retrieval results.

## How to verify the setup

1. Input the hypothetical sample's source text and the draft sentence. Compare the phrase "completed settlement payment" in the draft sentence against the "settlement statement number" and "settlement amount" fields in the source text. The source text records no payment status field. The expected observation is that the draft sentence's conclusion is not supported, and the evidence gap is recorded.

2. Input the hypothetical sample's handover request. Compare "fully executed and archive it" in the request against the field scope in the source text. The source text records neither an execution status nor an archive status. The expected observation is that the request remains pending verification and cannot be judged complete.

3. Input an explicit paper-based empty result array `[]` and check whether the downstream handling design can carry a citation length of zero. The expected observation is that the downstream flow continues and records an empty citation, without producing an error assertion. This input is a paper exercise and does not represent any actual retrieval return.

All three items are paper-based checks. No retrieval, approval, or archiving operation was actually performed.
