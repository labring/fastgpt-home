# Cross-border payment reviews: context limits for document comparison

## What the documents look like

Payment risk control for independent storefronts centers on card-network disputes and the receiving account. The working materials are chargeback notices, fraudulent order lists, invoices and proof of delivery. They arrive from Stripe or PayPal back offices, Shopify orders, carrier delivery records and customer-service email, and they update daily or per order.

Contract and transaction material comparison places an invoice, an order and a delivery record into one context so that the subject, amount, time and status can be checked against each other. The same field can arrive from more than one system, so the source and version of each field need to be fixed before any comparison. A chargeback notice describes a dispute stage; it does not state that funds have been returned. An invoice states an amount owed; it does not state that payment was received.

## Constraints at the context limits step

The context window is set by the chosen model. The reply limit constrains output length only and cannot be treated as the full context capacity. The knowledge-base reference limit is controlled in tokens, so a long single item can be trimmed, and the key fields need to be confirmed as falling inside the referenced range before comparison. The number of memory rounds changes what is sent as input on a follow-up question; the same question under empty history and under retained history produces different input, and a comparison conclusion can shift accordingly. When a fixed reply format is used, field completeness and successful parsing require separate verification.

Hypothetical drill sample: an independent storefront merchant receives a chargeback notice and intends to check an invoice against a proof of delivery. The invoice text reads: "Invoice No. INV-2024-0871, issue date 12 March 2024, amount USD 428.00, buyer Company A, order No. SO-2024-0455." The proof of delivery text reads: "Carrier delivery record: order No. SO-2024-0455, delivery date 18 March 2024, signed by Company B warehouse." The draft sentence to be judged is: "The invoice and the proof of delivery point to the same order, and delivery has been completed." That sentence touches order-number agreement and the fact of signing, while the invoice buyer and the signing party differ, and whether delivery is complete is not supported.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this drill | Reason and comparison method |
| --- | --- | --- |
| Model context | Check against the maximum context shown for the selected model | Compare with the total tokens of the materials to confirm key fields are not truncated |
| Reply limit | Keep enough length to state the basis and the handling action | Compare with the number of fields the draft sentence needs; too short truncates the basis |
| Knowledge-base reference limit | Set in tokens to cover the key fields of a single item | Compare with the tokens of a single item and observe whether fields are trimmed |
| Memory rounds | Retain a small number of history rounds | Compare with the empty-history input to confirm whether a follow-up changes the comparison result |
| Reply format | Select json_schema when fixed fields are required | Check field completeness and successful parsing, not text length alone |
| Minimum relevance | Set when semantic retrieval or rerank is in effect | Compare with recalled results to filter low-relevance fragments |

The minimum relevance value is a filtering threshold, not a final ordering rule. It applies only under semantic retrieval or when result rerank is used, and it does not act as a permission or entity filter. Retrieval is not authorization. The reference limit is expressed in tokens; the thinking budget is a reasoning budget and is not a reference-token ceiling.

## Three common errors

1. Treating the reply limit as the full context window, so a long item is truncated and still compared as if complete. Check: send the same material, compare the referenced content before and after adjusting the reply limit, and observe whether the key fields remain.
2. Treating a retrieval hit as authorization or business confirmation, so a recalled invoice is read as proof that delivery is complete. Check: inspect whether the proof of delivery states a delivery status, and record it as pending verification when no status is stated.
3. Treating fields belonging to different subjects as a contradiction in one field, so a mismatch between the invoice buyer and the signing party is immediately judged a conflict. Check: confirm whether the two fields point to the same subject; when the subjects differ, record the point as unsupported.

## How to verify the setup

1. Enter the hypothetical sample above and compare the order number in the invoice with the order number in the proof of delivery. When the two agree, the order-number check condition is met. When the buyer and the signing party differ, the draft sentence "delivery has been completed" is unsupported and should be recorded as pending verification.
2. Enter the same question under empty history and under retained history, compare the input content, and confirm whether the memory-round setting changes the comparison conclusion. If the conclusions differ, the history input affects the check, and the version to be treated as authoritative must be stated.
3. When json_schema is used, enter the draft sentence and check whether the returned fields include the order number, amount and signing status. When a field is missing, parsing fails, and text length alone cannot show that the format is correct.

For the empty-result branch, a paper input of an empty list can be used to check the downstream design; this does not mean that a hypothetical rule necessarily returns an empty list. For cross-model association, first check the identifier and exclude items that do not match, then record the actual observation. The overall retrieval flow lists optional paths, and not every path runs on every request: image retrieval requires an image input and matching model capability, and rerank requires the model and its setting to be enabled.
