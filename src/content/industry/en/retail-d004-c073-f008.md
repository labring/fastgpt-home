# Cross-border payment reviews: workflow routing for document comparison

## What the documents look like

Cross-border independent-site payment risk control centres on card-network disputes and receiving accounts, which sit on a different track from parcel status. The working materials for this category are payment chargeback notices, fraudulent-order lists, invoices, and logistics proof of delivery. They arrive from Stripe or PayPal back offices, Shopify orders, carrier delivery records, and customer-service email. The comparison task requires matching invoice amounts, order numbers, transaction identifiers in chargeback notices, and delivery records so that the same transaction can be checked for consistent counterparty, amount, and status across materials. The brief gives a data update frequency of daily and per order; this page does not derive batch synchronisation, full synchronisation, real-time, or transaction-triggered mechanisms from that frequency.

For workflow routing, the practical consequence is that materials sit in separate back offices and must be collected first, compared second, and handed to later stages third. A form input node enters the interaction state when triggered, collects required information, and passes that information to subsequent nodes after submission. A user selection node evaluates the user's choice and executes the corresponding "yes" branch. The interaction state is recorded by node behaviour; no separate global state-recording switch is documented. Retrieval results supply material leads only. They do not constitute authorisation, and they do not isolate entities or permissions. Order writes, document backfill, and external status synchronisation require a separate business interface or downstream process.

## Constraints at the workflow routing step

A hypothetical paper exercise sample follows. An independent-site merchant's risk specialist processes one chargeback on 10 June 2025. Three source sentences are available for comparison.

Invoice text: "Invoice No. INV-0610-A, order No. SO-8841, amount USD 120.00, invoice date 1 June 2025, buyer an overseas individual consumer."

Chargeback notice text: "Dispute No. CB-0610-77, transaction identifier TX-5521, amount USD 120.00, dispute date 8 June 2025, reason code not stated."

Delivery proof text: "Waybill No. TR-3390, delivery date 5 June 2025, recipient signature visible, corresponding order-number field blank."

The draft sentence to be assessed: "The transaction underlying this chargeback has been confirmed as delivered by the delivery proof, and the materials are consistent."

This draft sentence treats the delivery proof as delivery confirmation, yet the delivery proof does not state an order number, so it cannot be matched to the invoice or the chargeback notice on the same field. The phrase "materials are consistent" lacks support. The authorisation boundary is: this page performs material comparison only. It does not execute refunds, does not submit chargeback rebuttals, and does not write to the order system.

## Configuration and implementation checks

| Configuration item | Type | Hypothetical trial starting point and reason |
| --- | --- | --- |
| Form input node | Officially documented node | Collects three required values: transaction identifier, order number, amount; passes them to later comparison nodes after submission |
| User selection node | Officially documented node | When materials are incomplete, lets the operator choose "continue checking" or "suspend", executing the corresponding "yes" branch |
| Interaction-state check | Implementation check | After triggering an interaction node, check whether the conversation enters the interaction state, confirming the state is recorded by the node |
| Output hand-off check | Implementation check | Compare each form output field against the input fields of the downstream retrieval and judgement nodes |
| External-action separation | Implementation check | Order writes, document backfill, and external status synchronisation are marked as requiring a separate interface and are not executed on this page |
| Comparison field list | Implementation check | Transaction identifier, order number, amount, and date are the hypothetical comparison fields for this exercise, because these fields appear in the sample materials |

## Three common errors

1. Treating delivery proof as delivery confirmation. In the sample, the delivery proof's order-number field is blank, so it cannot be matched on the same field to invoice order No. SO-8841. The draft sentence's claim of consistent materials is unsupported.

2. Treating a retrieval hit as authorisation. Retrieving a chargeback notice or an invoice shows only that the material exists. It does not mean a refund may be executed or a rebuttal submitted; authorisation requires manual checking and a downstream process.

3. Treating the interaction-state record as a submission-count control. The form input node records state and waits for the user to complete interaction. The documents do not describe a submission-count limit, so repeated submission or single submission cannot be inferred from that record.

## How to verify the setup

1. Input the three sample source sentences and the draft sentence. Compare the delivery proof's order-number field against invoice order No. SO-8841 for same-field correspondence. The observable result is a blank order-number field with no correspondence, so the draft sentence does not satisfy "materials are consistent".

2. Input the sample chargeback notice and invoice. Compare transaction identifier TX-5521 against order No. SO-8841 for a correspondence stated within the same material. The observable result is that each material states a different identifier and neither states a mapping to the other, so the judgement remains pending verification.

3. Input an explicit paper-based empty-result hand-off case: use the stated paper input [] to check the downstream node design, and observe whether the downstream handles it via an empty-result branch. Do not claim that a fictional rule retrieval necessarily returns []. At the same time, check the identifiers of libraries using different vector models, exclude those that do not match, and do not run cross-model retrieval to compare missed recalls.
