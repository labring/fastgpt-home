# Cross-border payment reviews: access controls for document comparison

## What the documents look like

Cross-border standalone-site payment risk control operates around card-network disputes and receiving accounts. The working materials are chargeback notices, fraudulent-order lists, invoices, and proof of delivery. They arrive from Stripe or PayPal back offices, Shopify orders, carrier delivery records, and customer-service email, and they update daily or per order. The comparison task places an invoice, an order, a delivery receipt, and a chargeback notice inside one authorized scope and checks them field by field. Because the materials sit in several systems, access control and data isolation determine which files a reviewer can see during comparison, and whether retrieval recall filters results by the current member identity.

## Constraints at the access controls step

Knowledge-base permission is the threshold; file-level permission cannot bypass it. After file-level permission is enabled, every file or folder generates a permission snapshot, and lists, details, and retrieval recall each authenticate against that snapshot. Retrieval recall applies only when authentication uses the current member identity; a workflow that preselects a knowledge base without member-identity authentication performs no file-level filtering. A team administrator does not bypass file-level permission, and knowledge bases and files still authenticate against their own collaborator settings. System root and the team owner are treated as holding all permissions on all files.

Hypothetical paper exercise sample: a standalone-site risk specialist intends to compare a chargeback notice against the corresponding invoice and delivery receipt before handing the case over. The source text reads: "Chargeback notice DP-2024-0317, subject order SO-88231, status pending review, amount 1200 USD, date 2024-03-17." "Invoice INV-88231, subject order SO-88231, status issued, amount 1200 USD, date 2024-03-10." The draft sentence is: "Order SO-88231 has been delivered, chargeback evidence is complete, ready to submit." The draft sentence attaches no delivery-receipt source text, and the delivery status is not stated.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Comparison and explanation |
| --- | --- | --- |
| Knowledge-base read permission | Held by the risk specialist | Check item by item against file-level read permission; both must be satisfied |
| File-level permission switch | Enabled | In the disabled state, collection permission matches the knowledge base and no collection permission records are queried |
| Collaborator list | Includes the current creator | Full-overwrite semantics: the submitted list is the final result, and a missing creator is rejected |
| Retrieval authentication mode | By current member identity | A preselected knowledge base without member-identity authentication performs no file-level filtering |
| External system authentication | Verified separately | External interface authentication and FastGPT resource permission are checked independently |

## Three common errors

1. Treating retrieval relevance as permission filtering. A similarity score does not exclude unrelated businesses or unauthorized records, and retrieval is not authorization. Check: enter the same query, search with an authorized and an unauthorized account, and compare whether the returned file list is filtered item by item per member.

2. Treating a team administrator as bypassing file-level permission. Team-level management permission covers only the team's own resources. Check: access an unauthorized file with a team administrator account and compare whether the list and details are filtered by collaborator configuration.

3. Treating a pending-review status as approved. Chargeback notice DP-2024-0317 has status pending review and does not constitute approval or execution. Check: compare the draft sentence against the source text field by field and confirm whether the delivery status has source support.

## How to verify the setup

- Verification one: input the chargeback notice and invoice source text from the hypothetical sample, and compare order number SO-88231, amount 1200 USD, and the dates. Matching order number and amount are consistent; differing dates are a normal stage difference. If the draft sentence claims delivery is complete, check whether the delivery-receipt source text states a delivery status; when it does not, record the claim as unsupported.

- Verification two: input the draft sentence "Order SO-88231 has been delivered, chargeback evidence is complete, ready to submit" and compare it against the source text. The source text does not state a delivery status, so the delivery assertion in that sentence is unsupported; the chargeback notice status is pending review and does not constitute approval. The assertion is satisfied only when the delivery-receipt source text explicitly states a delivery status corresponding to the order number.

- Verification three: search the same order number separately with an authorized account and an unauthorized account, and compare the returned results. The condition is satisfied when the authorized account can see the file, the unauthorized account cannot, and the list is filtered item by item per member. If both accounts return the same file, check whether retrieval authenticates by current member identity. An empty result can be checked against downstream design using a paper input of an empty list; do not claim that a fictional rule's retrieval necessarily returns an empty list.
