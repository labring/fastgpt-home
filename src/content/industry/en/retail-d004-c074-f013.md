# Cross-border resale returns: access controls for document comparison

## What the documents look like

Cross-border return refurbishment and resale work follows reverse logistics and item condition. It differs from inbound replenishment management, which covers forward stocking. The working materials are return inspection forms, refurbishment records, scrap declarations, and relisting checklists. Data arrives from overseas warehouse WMS, TikTok return centers, Amazon return reports, and item inspection photographs, with updates at a daily or per-batch cadence.

This page covers one task inside that material set: comparing contract and transaction materials, specifically return inspection forms, refurbishment records, scrap declarations, and relisting checklists. The question is which fields count as contract or transaction material, who may read them, who may modify them, and how comparison results are shown under permission isolation. Document classification, tags, and retrieval relevance are not access authorization. Retrieval settings cannot substitute for permission configuration.

## Constraints at the access controls step

The FastGPT permission system combines attribute-based and role-based models. Member permissions, department permissions, and group permissions are evaluated together, with member permissions taking priority. Resource types include team, app, dataset, and collection. Knowledge base file-level permission is a commercial-edition feature. In the closed state, collection readability matches the knowledge base. In the open state, each file or folder receives a permission snapshot, and list views, detail views, and retrieval recall are each authorized against that snapshot. Knowledge base permission remains the threshold; collection permission cannot bypass it.

Team administrators do not bypass file-level permission. System root and team owner are treated as holding all permissions on all files. Retrieval recall filters by the files the current member may read, and this applies only when authorization runs under the current member identity. A workflow that preselects a knowledge base without member-identity authorization does not apply file-level filtering. A similarity score does not perform permission filtering, and retrieval by itself is not authorization.

Hypothetical paper exercise sample: an overseas warehouse inspection group submits one return inspection form. The source text has three sentences: "Return order RT-2024-0871, item is a portable fan, return reason recorded as motor noise. Inspection conclusion is function normal, minor surface scratches, recommend refurbishment then relisting. Refurbishment record FR-0871 states the outer shell was replaced, scrap declaration BF-0871 states the original outer shell was scrapped." A draft sentence awaiting determination reads: "This returned item has been processed as scrap and will not enter the relisting checklist." The comparison objects are these three materials, the period is the same return batch, and the field is item disposition status. Authorization boundary: the after-sales supervisor holds read permission on the knowledge base and read permission on the file, the inspector holds write permission, and the inspector is the creator of the scrap declaration.

## Configuration and implementation checks

| Check item | Documented setting or implementation check | Relation to this page's sample |
| --- | --- | --- |
| Knowledge base threshold | Knowledge base read permission is the prerequisite for collection access | The after-sales supervisor must first hold knowledge base read permission |
| File-level permission switch | Open state authorizes per snapshot; closed state inherits knowledge base permission | The sample involves three materials, so switch state must be confirmed |
| Collaborator roles | Read permission, write permission, administrator, creator | The inspector is creator of the scrap declaration; the supervisor holds read permission |
| Full-overwrite semantics | The submitted collaborator list is the final result and must include the current creator | Editing scrap declaration collaborators must not remove the creator |
| Retrieval recall filtering | Filters by files the current member may read, effective only under member-identity authorization | Unauthorized files are not recalled during the supervisor's retrieval |
| Closure consequence | Deletes all file collaborator configuration and restores inheritance from the knowledge base | After closure the three materials return to knowledge base level |

Hypothetical starting value for this exercise: set the file-level permission switch to open, because the sample needs read permission and write permission distinguished per material. Comparison method: observe the same account's visibility and editability on the scrap declaration before and after opening.

## Three common errors

1. Treating retrieval relevance as permission filtering. Input: the after-sales supervisor account retrieves "scrap declaration." Comparison object: the similarity condition in retrieval settings and the file-level permission snapshot. Observable result: if only similarity is adjusted while file-level permission stays closed, unauthorized files may still be recalled. The correct step is to check the file-level permission switch and collaborator configuration.

2. Treating team administrator identity as a file-level permission bypass. Input: a team administrator account accesses the refurbishment record in the sample. Comparison object: team-level management permission and the file collaborator configuration. Observable result: team administrators do not bypass file-level permission and are still authorized by collaborator configuration.

3. Treating a pending draft state as an executed disposition. Input: the draft sentence "This returned item has been processed as scrap." Comparison object: the actual status field of scrap declaration BF-0871 and the relisting checklist. Observable result: existence of a scrap declaration does not mean scrap was executed; the scrap declaration status and the relisting checklist must be checked for consistency.

## How to verify the setup

1. Input: the after-sales supervisor account and the three sample materials. Compare the account's read permission on the knowledge base with its read permission on each file. Conditions met when: all three materials are viewable, and retrieval recall returns no other file for which the account lacks read permission.

2. Input: the inspector account and scrap declaration BF-0871. Compare the account's creator identity with the collaborator list. Conditions met when: the collaborator list includes the creator, and the creator record remains after collaborator modification.

3. Input: the draft sentence and the sample source text. Compare the disposition status stated in the draft with the field values in the scrap declaration and relisting checklist. Conditions met when: the draft sentence shares the same subject, same period, and same field as the source; if the source does not state that scrap was executed, record the item as pending verification rather than as a contradiction or denial.
