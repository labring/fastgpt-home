# Creator commission settlement: workflow routing for document comparison

## What the documents look like

Commission settlement and deduction for creators happens after a sale closes. The comparison work concentrates on valid promotion and post-sale deduction rather than on the terms agreed before a campaign begins. Materials come from the Selected Alliance backend, order after-sales data, the finance system and creator contracts. The documents handled day to day include commission setting records, settlement statements, refund deduction details and invoices, with a weekly or monthly update rhythm. The comparison between contract and transaction materials has to answer whether the commission rate, settlement cycle and deduction situations written into the contract can be corroborated against the same subject, the same period and the same field in the statement and refund details. This comparison relies on manual checking actions and on interactive nodes inside the workflow. Retrieval output does not by itself constitute authorization, and a value collected by a form does not equal business confirmation.

## Constraints at the workflow routing step

When the form input node triggers, the conversation enters an interactive state and the workflow state is recorded. After the user fills in the required information and submits, the node passes that information to subsequent nodes. The user selection node judges the user's choice and executes the corresponding "yes" branch. Both nodes are user interaction nodes, can be added repeatedly, and trigger execution. The constraint is that these interaction nodes collect values and choices entered by the user; order writing, document backfilling and external status synchronization require a separate business interface or a later process. The retrieval library and relevance settings do not carry permission or entity isolation duties. Libraries built on different vector models cannot be associated together; identifiers must be checked first and non-matching items excluded.

Hypothetical exercise sample: one creator contract text states "the commission rate is settled at fifteen percent of the transaction amount of valid orders, and refunded orders are deducted back in the following month's statement." The corresponding statement text states "valid order transaction amount for this period is one hundred thousand yuan, commission is fifteen thousand yuan, refunded order amount of twenty thousand yuan is not listed as a deduction item." A handover request awaiting judgment reads "please confirm that this period's statement has completed the refund deduction according to the contract." The subject, object, period and fields needed for the judgment are all present in those three sentences. The missing deduction item is unsupported, not a confirmed conflict.

## Configuration and implementation checks

| Configuration or check item | Assumed trial starting point for this page | What it is compared against |
| --- | --- | --- |
| Form input node required fields | Subject, period, commission rate, refund amount | Field-by-field against the contract text |
| User selection node branches | Two branches set as "materials consistent" and "materials pending verification" | Execute the corresponding "yes" branch by choice result |
| Interaction state check | Conversation enters interactive state after the node triggers | Against the documented interactive behavior |
| Output handover check | Pass form values to the subsequent judgment node | Item-by-item between output and input |
| External operation division | Order writing and status synchronization connect to a separate business interface | Check whether a downstream implementation exists |
| Retrieval scope check | Retrieve only within libraries the account may access | Check library identifier and vector model identifier |

The field names and branch names in this assumed trial starting point are set by the exercise. The reason for choosing them is to cover the minimum field set needed for the comparison, and the comparison method is a field-by-field reading against the contract text. This does not indicate that an official default value exists.

## Three common errors

1. Treating a retrieval hit as an authorization basis. A retrieval result shows only that text was recalled; it does not show that a subject is entitled to settle. Check: input the contract and statement texts above, compare the retrieval output with the contract text, and observe whether an authorization conclusion appears that goes beyond the source text.
2. Treating a form submission as business confirmation. The form input node collects required information and passes it on; business verification and approval require a downstream implementation. Check: input "please confirm that this period's statement has completed the refund deduction according to the contract," compare that request with the statement text, and observe whether a confirmed conclusion is produced while the deduction item is missing.
3. Writing a pending-verification item as a contradiction. A statement that does not list a deduction item is an unstated item; the contract and statement do not give mutually exclusive values in the same field. Check: input both source texts, compare values in the same field, and observe whether an unstated item is misjudged as a conflict.

## How to verify the setup

1. Input the contract text and the statement text above, compare the commission rate and the refund deduction fields, and accept the result only when each field's source value is listed and the unstated item is marked.
2. Input "please confirm that this period's statement has completed the refund deduction according to the contract," compare that request with the statement text, and accept the result only when the output marks the item as pending verification, explains that the deduction item is missing, and does not output a confirmed conclusion.
3. Input the paper input [] for an empty-result handover, compare whether the downstream design handles the empty value, and accept the result only when the empty-result branch is recorded and the follow-up action is described as requiring a separate implementation, without claiming that retrieval will necessarily return [].

All of the above is paper checking. No test was actually executed, and no approval, payment or status synchronization took place.
