# B2B marketplaces: workflow routing for procurement

## What the documents look like

In B2B marketplace matchmaking, online company certification and electronic contracts appear more frequently than in physical wholesale-stall trading. Enterprise certification materials, request-for-quotation and quotation sheets, electronic contracts, and platform settlement statements circulate in electronic form and do not depend on on-site verification. For the inventory procurement and supplier materials task, this means the workflow has to treat identity materials, quotation conditions, and contract text as structured inputs that can be passed between nodes. Typical parties are platform operations, suppliers, and enterprise buyers. Errors concentrate in transactions with false entities, contract disputes, and platform complaints.

Data sources named in the brief are the B2B platform, the National Enterprise Credit Information Publicity System, payment records, and logistics tracking. Update frequency is daily and per order. In inventory procurement, supplier materials, inventory quantity, quotation validity, and settlement basis need per-order comparison, and the pace of material updates affects how current the input is at later nodes.

## Constraints at the workflow routing step

The Form Input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the workflow continues downward after the user completes the interaction. The node collects the information the user fills in and passes it to later nodes. The User Selection node behaves the same way at trigger, and when the user makes a choice, the node evaluates that choice and executes the "yes" branch. Its basic use is to pose a question that requires a decision and route the workflow according to the user's feedback.

Both nodes record workflow state and resume after interaction completes. What they collect is user-entered information. Business verification, approval, database writes, and external synchronization require a separately connected business interface or a later process. Retrieval results do not constitute authorization. A form submission is not a certification pass, a quotation validity date is not a supply deadline, and a pending review is not evidence that an operating permission is missing. Signing, reaching cooperation, and contract effectiveness are three distinct facts.

Hypothetical paper exercise sample. The material text to be checked reads: "Supplier A, unified social credit code 91310000XXXXXXXX0A, business scope includes hardware wholesale; this quotation sheet number BJ-2024-0312, quotation valid until 30 June 2024; available inventory quantity 200 units, delivery location Shanghai." The proposed handover request reads: "Supplier A has passed certification and can proceed directly to contract signing and lock 200 units of inventory." The question is whether the source text supports that request. The source text contains no certification conclusion field, so the phrase "has passed certification" is unsupported. The source text states a quotation validity date only and no supply deadline, so the two cannot be inferred from each other.

## Configuration and implementation checks

| Configuration item | Type | Description |
| --- | --- | --- |
| Form Input node | User interaction | On trigger, enters the interaction state, collects required information, and passes it to later nodes after submission |
| User Selection node | User interaction | After the user makes a choice, executes the corresponding "yes" branch; verify each branch connection one by one |
| Interaction state check | Implementation check | State recording is the interaction node's own behavior; no separate global state-recording switch is set or claimed |
| Output handoff check | Implementation check | Pass collected information explicitly to later retrieval, judgment, or interface nodes, and compare each output against its input |
| External action separation | Implementation check | Order writes, document backfill, and external status synchronization require a separately connected business interface or later process |
| Hypothetical exercise starting point | Implementation check | This paper exercise uses quotation validity 30 June 2024 as the comparison starting point against a contract date field; this value is set for this sample only and is not an official default |

## Three common errors

1. Treating form submission as certification passed. The Form Input node collects user-entered information and passes it to later nodes; business verification and approval need a separately connected process. In the proposed handover request, "has passed certification" has no corresponding certification conclusion field in the source text, so it is unsupported.
2. Treating quotation validity as a supply deadline. The source text states only that the quotation is valid until 30 June 2024 and states no supply deadline. These are different fields and cannot be inferred from one another.
3. Treating a retrieval hit as authorization to execute. Retrieval is information acquisition and does not constitute permission or entity isolation. Inventory locking and contract signing require an independent business interface and authorization boundary.

## How to verify the setup

1. Input the hypothetical sample source text and the proposed handover request, then compare "has passed certification" against the source text's certification field. The source text states no certification conclusion. The expected observation is that this wording is unsupported, and the evidence gap should be recorded.
2. Input the quotation validity date of 30 June 2024 and a proposed contract date, then compare whether the two are the same field. They are different fields. The expected observation is that a supply deadline cannot be inferred from the quotation validity date.
3. Input an empty-result handoff scenario, using the paper input `[]` to check the downstream design. The expected observation is that the downstream node has a defined handling path for empty input. Do not claim that a fabricated-rule retrieval necessarily returns an empty array.

All three checks use the hypothetical sample as input, record the compared fields and the observed result, and do not claim that testing was performed. Situations that are unstated, or that have evidence only at a related stage, are recorded as pending verification.
