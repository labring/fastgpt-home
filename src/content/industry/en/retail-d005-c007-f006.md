# General import declarations: scheduled workflows for procurement

## What the documents look like

General trade import declaration work centres on customs dutiable value, freight and insurance, and duty payment. Data comes from the International Trade Single Window, customs tariff schedules, freight forwarder arrival notices, and foreign exchange payment documents. In the inventory procurement and supplier records step, the working materials are the import declaration form, commercial invoice, packing list, bill of lading, and contract. The stated update frequency is per shipment.

These materials carry different parties, amounts, statuses, and validity scopes. A scheduled job that reads them must check each shipment individually. A field value belonging to one shipment cannot be carried over to another. A contract number, invoice number, and bill of lading number identify different documents, and agreement between them is a per-shipment comparison rather than a shared attribute.

## Constraints at the scheduled workflows step

External data is read through an already configured interface. A scheduled trigger does not by itself establish a connection to a business system. The responsibility for triggering must be stated: whether the application scheduling capability or an external scheduler performs it, checked against the entry points available in the actual version. HTTP requests must be checked against the external interface documentation for method, headers, body, and variable inputs. Deduplication, idempotency, and business writes require explicit design in the interface or a later flow; they are not automatic properties of a scheduled task. Execution records must be compared against trigger time, actual input, returned result, and business status. The existence of a task does not substitute for successful execution.

Hypothetical paper exercise sample. A customs manager at an importer receives a freight forwarder arrival notice. The notice text reads: "Cargo under reference IMP-2024-001 is expected to arrive on 18 March; bill of lading number BILL-001; please submit declaration materials before arrival." The available commercial invoice text reads: "Invoice number INV-001, contract number CON-001, terms CIF, amount USD 120,000." A draft handover sentence awaiting assessment reads: "The system has automatically completed the declaration material submission for this shipment and the duties have been paid." This sample contains no authorization or execution record corresponding to the automatic submission or the duty payment claimed in the draft sentence.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | How to check |
| --- | --- | --- |
| Trigger method | External scheduling trigger | Check the entry points available in the actual version; distinguish from manual trigger |
| Request method | POST | Confirm against the external interface documentation |
| Request header Authorization | Bearer plus a variable | Check the token source against the interface documentation |
| Request body fields | Contract number, invoice number, bill of lading number | Compare item by item against the sample source text |
| Return value extraction | message and data.user.name by JSON path | Check the paths against the interface response example |
| Execution record | Record trigger time and returned result | Compare input, output, and business status |

The starting values above are chosen for this paper exercise so that each item has a stated comparison target. They are not official defaults. The request method and header follow the documented HTTP module behaviour, in which Params, Body, and Headers are configured and variables may be referenced with double braces. The return value extraction follows the documented JSON path syntax, where a configured key such as `message` or `data.user.name` retrieves a value from the converted response format. The execution record is an implementation check: the documented module description does not state that a scheduled task writes business status, so the record must be verified separately.

## Three common errors

1. Treating the existence of a scheduled task as successful business execution. In the sample, the draft sentence states that submission and duty payment were completed automatically, while no corresponding execution record exists. The check is to compare trigger time, actual input, and returned result. A task entry alone does not show that the business action occurred.

2. Treating retrieval or a form as authorized execution. In the sample, the handover request lists materials but states no authorization boundary. Listing materials does not establish that submission or duty payment was approved. The authorization subject, scope, and approval record must be present before any downstream action is treated as permitted.

3. Treating a similarity setting as a permission or entity filter. In the sample, invoice number INV-001 and bill of lading number BILL-001 belong to different materials. A relevance score does not separate unrelated records or enforce authorization. Retrieval is not authorization, and a similarity setting does not exclude records that fall outside a permitted scope.

## How to verify the setup

1. Input the sample notice text "Cargo under reference IMP-2024-001 is expected to arrive on 18 March; bill of lading number BILL-001" together with the draft sentence "The system has automatically completed the declaration material submission for this shipment and the duties have been paid." Compare the action claimed in the draft sentence against the material scope listed in the source text. The source text contains only the arrival notice and invoice information, with no submission or duty payment record. The draft sentence exceeds the source scope, so the condition is not satisfied.

2. Input the sample invoice text "Invoice number INV-001, contract number CON-001, terms CIF, amount USD 120,000" together with the contract number and invoice number cited in the request. Compare whether the two sets agree. If the cited contract number or invoice number does not match the source text, the input is mismatched and the materials must be rechecked before proceeding.

3. Input the sample handover request and compare whether it states an authorization status. The request does not state an authorization subject, authorization scope, or approval record. The authorization boundary is therefore missing, and the request must be completed before it can enter a downstream flow. This is a paper comparison; no submission, payment, or approval is asserted to have occurred.

Across all three checks, the observable result is a match, a mismatch, or a missing element in the stated comparison. Where the source text does not provide a field, the value remains unknown and must not be filled in by assumption. Where a request is pending, it is not an approval. Where an option is offered, it is not an execution. Where a termination is unsigned, it is not a completed termination.
