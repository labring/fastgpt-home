# Refund-only disputes: scheduled workflows for procurement

## What the documents look like

Refund-only disputes frequently proceed without any returned goods arriving at a warehouse, so the evidence that matters concerns dispatch, delivery signature and the value of the item. Procurement and supplier records carry two jobs in this category: showing that the disputed item was in fact supplied by a particular supplier and left the warehouse, and aligning supplier-side purchase records and outbound records with the platform after-sales order. The main data sources are the platform after-sales console, carrier tracking, customer service chat and warehouse outbound records. The documents handled day to day are refund-only applications, dispatch evidence, delivery signature proof and appeal materials. Scheduled tasks and automation are used here to organise reading, requesting and cross-checking these materials on a fixed rhythm, reducing manual searching order by order.

Update frequency for this category is per order and daily. That cadence matters for scheduling because each dispute moves on its own timeline, and the procurement record tied to a given after-sales order may be written at a different moment than the dispute itself.

## Constraints at the scheduled workflows step

The responsibility for triggering must be stated: whether the application's scheduled capability initiates the run or an external scheduler does, and which entry points are actually available in the version in use. External data is read through an already configured interface; a scheduled trigger by itself does not establish a connection to a business system. The HTTP request method, headers, body and variable inputs are checked against the external interface documentation. De-duplication, idempotency and business writes need to be explicitly designed in the interface or in a downstream flow. Execution records should be checked against trigger time, actual input, returned result and business status; the existence of a task does not mean the execution succeeded.

Hypothetical drill sample: a supplier record page states "supplier number S-1042, supplied item Type A insulated flask, outbound date 12 March 2024, outbound quantity 200 units, corresponding platform after-sales order number R-7781, outbound order status shipped." A separate refund-only application states "buyer claims goods not received, applies for refund only." The draft handover request to be assessed is "please have the scheduled task automatically push this supplier's purchase contract to the platform appeal." The purchase contract does not appear in the sample materials, and the authorisation status is not stated.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | How to check |
| --- | --- | --- |
| Trigger method | External scheduler, daily | Check against entry points available in the version in use and confirm who initiates |
| Request method | POST | Check method, headers and body against the external interface documentation |
| Body fields | Reference supplier number and after-sales order number | Check variable sources against the {{key}} reference rule |
| Return value extraction | Extract the outbound order status field | Check the extraction result against JSON path syntax |
| De-duplication and idempotency | Use the after-sales order number as the business key | Check in the interface or downstream flow whether this has been designed |
| Execution record | Record trigger time, input, returned result | Compare item by item with business status |

These values are hypothetical trial starting points. The reason for selecting them is that the sample already provides a supplier number and an after-sales order number, which can be compared against the return value extraction result.

## Three common errors

1. Treating the scheduled trigger as an established business system connection. In the sample the outbound order status is shipped; the task reads that field, and a successful read does not mean the purchase contract exists or that pushing it has been authorised.
2. Treating the draft handover request as already executed. The sample request mentions pushing a purchase contract, that contract does not appear in the materials, and the authorisation status is not stated, so the request remains pending verification.
3. Using the return value extraction result in place of a business judgement. Extracting the outbound order status field only shows that the interface returned that value; it does not show that the correspondence between the supplier and the after-sales order has been confirmed.

## How to verify the setup

1. Input supplier number S-1042 and after-sales order number R-7781 from the sample. Compare the body reference result with the sample record. The condition is met when they agree.
2. Input the outbound order status field from the sample. Compare the return value extraction result with the sample value "shipped". The condition is met when they are the same and the result is traceable.
3. Input the draft handover request. Compare the request content with the sample materials. If neither the purchase contract nor the authorisation status appears in the materials, record this as unsupported; it must not be judged as authorised or executed.

A pending request is not an approval, an offered option is not execution, and an unsigned termination is not a completed termination. Where the materials do not state a fact, that fact remains unknown.
