# Convenience fresh-food orders: HTTP integrations for procurement

## What the documents look like

Convenience-store fresh-food ordering runs at store level, with short shelf-life items ordered frequently. This differs from a hypermarket fresh counter operating on a joint-venture revenue-share basis. The working records are fresh-food order forms, damage write-off forms, near-expiry handling sheets, and cold-chain temperature records. Sources behind these records include POS sales, the head office ordering system, store inventory, and cold-chain temperature logs. The records update by day or by shift.

This page covers one step: inventory procurement and supplier records, connected to external systems through the HTTP module. Field values on order forms and write-off forms determine request body content. Supplier records determine which address a request goes to. If an interface writes an expired or near-expiry quantity incorrectly, later replenishment judgments drift.

The people handling this work are store managers, fresh-food buyers, and regional supervisors. Errors here lead to expired sales, stockout losses, and food-safety complaints. The most time-consuming steps are forecasting next-day sales, checking shelf life, and registering write-offs.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a specified address. Params carry path parameters and are common in GET requests. Body carries the request body and is common in POST and PUT requests. Headers carry request headers for special information. All three data locations can reference variables with `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and upstream node outputs.

Return-value configuration does not represent the interface's own return value. It represents how to parse the interface response, extracting values by JSON path syntax. When the output type is set to string, the value at the corresponding key is converted to a JSON string for output.

Among system variables, chatId and responseChatItemId do not exist in test mode. Reading an empty value during debugging is an environment difference, not a business fault. appId is the application ID. For the chat interface, passing body.appId in the request body is recommended, and APIKey handles authentication. The model and temperature parameters passed in do not take effect; orchestration decides these fields, and API parameters do not change them.

A hypothetical paper exercise sample follows. A convenience-store regional supervisor reviews a fresh-food order form on paper. The source text reads: "Store A, 10 March 2025, fresh-food order form number XD-0310, rice balls 120 units, sandwiches 80 units, status is pending review." The draft sentence to be judged reads: "This order form has passed review and can be submitted to the supplier system as a procurement request." The check compares the form's status field against the value "pending review," and confirms whether the order quantity in the HTTP request Body matches the source text. Pending review does not mean review passed. The submission action requires separate confirmation.

## Configuration and implementation checks

| Configuration item | How it is set | What to check |
| --- | --- | --- |
| Request address | Fill in per the external interface document; variables may be referenced | Matches the address the supplier system provides |
| Request method | Choose per the external interface document | Matches the method the interface contract requires |
| Headers | Fill in key-value pairs such as Authorization | Credentials injected through secure configuration |
| Body | Used only under the corresponding request type | JSON structure corresponds to order form fields |
| Return-value extraction | Configure key to extract by JSON path | Extracted field corresponds to the response structure |
| Variable reference | Reference global variables, system variables, or upstream node outputs | Verify each actual passed value item by item |

This exercise's starting value: the Body references the order-quantity variable with value 120. This value is chosen because the sample source text states rice balls 120 units, and it is used to compare against the quantity echoed in the response. This value is a paper-check starting point for this exercise, not an official default.

## Three common errors

1. Treating an empty chatId in test mode as a lost session. Input is a test-mode request. Compare the chatId value against the documented statement that it does not exist. The observed result is an empty field in test mode, which is an environment difference.
2. Treating pending-review status as review passed. Input is the sample source text status "pending review." Compare it against "has passed review" in the draft sentence. The observed result is that the two values differ, and the draft sentence is unsupported.
3. Treating return-value extraction configuration as the interface return value. Input is the configured key and JSON path. Compare the response structure against the extraction result. The observed result is that the extracted value comes from the response; the configuration itself does not produce an interface return value.

## How to verify the setup

1. Input the order quantity 120 from the sample source text and the variable value referenced in the Body. Compare whether the two match. The observed result is that matching values indicate correct referencing.
2. Input the sample source text status "pending review" and the draft sentence "has passed review." Compare the status values. The observed result is that differing values leave the draft sentence pending verification.
3. Input a test-mode request and a formal request. Compare whether the chatId field exists. The observed result is that it does not exist in test mode and exists in the formal request, which distinguishes an environment difference from a business fault.

All of the above is paper checking. No request was actually sent, and no submission, approval, or synchronization action was executed.
