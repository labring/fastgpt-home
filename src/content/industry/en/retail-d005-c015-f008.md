# Letter-of-credit documents: workflow routing for procurement

## What the documents look like

Letter-of-credit document examination and presentation serves bank payment conditions, and the central concern is consistency across documents rather than tax matching. The main data comes from issuing-bank notices, UCP600 clauses, freight-forwarder bills of lading, and bank presentation records. The documents handled per transaction include the letter of credit, commercial invoice, bill of lading, insurance policy, and draft. Each transaction updates the record set once.

When inventory procurement and supplier records enter this step, the material and the documents must correspond on the applicant or beneficiary, the goods, the quantity, and the current status. Workflow routing carries the task of connecting these records in node order. The Form Input node enters an interaction state when triggered, collects required information, and passes the submitted information to downstream nodes. The User Selection node evaluates the user's choice and executes the corresponding "yes" branch. Both nodes record workflow state, and the dialog box is hidden during interaction.

Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval and form submission do not constitute authorization to execute.

## Constraints at the workflow routing step

A clearly labelled hypothetical paper exercise sample is used below. It is not a real customer record and no test, submission, or payment has occurred.

The material text for comparison reads: "The issuing-bank notice lists the beneficiary as Company A, the goods as procurement batch inventory number A-01, and the presentation deadline as twenty-one days after the notice date; the supplier record sheet states that this batch is supplied by Supplier B, and the amount field of the draft invoice is left blank." A draft sentence awaiting judgment reads: "This transaction has completed presentation and obtained payment." The request is in a pending-review state, and no presentation or payment record is stated.

At this step, the Form Input node's documented behavior is to collect required information and pass it downstream after submission. The User Selection node's documented behavior is to execute the "yes" branch after a user choice. Neither node performs order writes, document backfill, or external synchronization. Those actions need a stated downstream implementation. A pending request is not an approval, and an offered option is not execution.

Retrieval is not authorization. A relevance score is not a category, entity, or permission filter, and a similarity setting does not exclude unrelated businesses or unauthorized records. Where records come from different vector models, they cannot be associated together; the correct action is to check identifiers and exclude non-matching records, then record the actual observation. An empty retrieval result can be handled by comparing a clearly labelled paper input of `[]` against the downstream design, without claiming that any rule-based retrieval must return `[]`.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison method |
| --- | --- | --- |
| Form Input node | Set required fields for beneficiary, goods batch, and presentation deadline | Compare field by field against the hypothetical source text; keep missing fields missing |
| User Selection node | Set the "yes" branch to point to record-backfill verification | Compare against the pending-review state of the hypothetical request; do not enter a presented branch |
| Output handoff | Pass form information to a later judgment node | Compare each output field against the corresponding input field for consistency |
| Retrieval scope | Limit to the document set with access rights | Compare against the subject scope in the hypothetical source text and exclude non-matching records |
| External action split | Order writes and status synchronization connect to a separate interface | Compare against the hypothetical request and confirm that no write or synchronization has occurred |

## Three common errors

1. Treating form submission as authorized execution and reading the pending-review state of the hypothetical request as completed presentation. The check takes the hypothetical source text and the draft sentence as input, compares the status field, and observes whether any presentation or payment record appears.

2. Treating retrieval results as a permission filter and using similarity to exclude unrelated subjects. The check takes the retrieval return list as input, compares the subject identifier of each record, and observes whether records for a subject other than Company A are mixed in.

3. Treating the "yes" branch as the default path without verifying branch connections one by one. The check takes the node connection configuration as input, compares the selection result against the branch target, and observes whether the "yes" branch is wrongly connected to an external synchronization action.

## How to verify the setup

1. Input the hypothetical source text and the draft sentence. Compare whether the draft sentence contains any presentation or payment fact not stated in the source text. The condition is met when the judgment result is unsupported by the source text.

2. Input the retrieval return list. Compare the subject identifier of each record against the beneficiary in the hypothetical source text. The condition is met when non-matching records are excluded and the actual observation is recorded.

3. Input the node connection configuration. Compare the User Selection result against the "yes" branch target. The condition is met when the branch is not connected to an external write or synchronization action.

For each check, the input, the comparison, and the observable result are stated. Missing evidence remains missing. No test, deployment, approval, refund, or other business action is claimed to have occurred.
