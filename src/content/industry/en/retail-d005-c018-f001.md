# Regional dealer stock: HTTP integrations for procurement

## What the documents look like

Regional dealer stock replenishment runs as a daily rolling order process. Dealer ERP records, the brand ordering system, warehouse stock, and sales collections together form the checking basis for replenishment applications, inventory turnover tables, outbound notes, and payment plans. These materials typically update by week or by month. An HTTP integration must map fields from external systems onto the primary task of this page: the checking and routing of procurement and supplier records. Brand channel managers, sales back-office staff, and dealer warehouses each hold data from different sources. An interface call can transmit only the variables it is given. It cannot replace human confirmation of supplier records, procurement quantities, or authorization boundaries.

## Constraints at the HTTP integrations step

The HTTP module sends requests to a specified address. Params, Headers, Body, and the URL support `{{}}` references to global variables, system variables, or upstream node outputs. appId identifies the FastGPT application; chatId and responseChatItemId are absent in test mode, and cTime is the current time. String references in the Body need double quotes, while numeric references retain a numeric type. JSON path extraction follows the actual response structure. The APIKey authentication and appId selection rules of the FastGPT chat API apply to that API. The supplier interface needs its own contract for credentials, identifiers, and permissions.

Hypothetical paper exercise sample: A sales back-office staff member at a regional dealer receives a paper Replenishment Application. The original text reads: "Applicant: East China regional dealer; Requested item: Brand A 500ml packaged product; Requested quantity: 200 cases; Application date: March 10, 2025; Authorization status is pending approval by the brand channel manager." At the same time, a handover request is drafted for submission through an HTTP interface, reading: "Please write this application directly into the supplier procurement system and generate an outbound note." The request carries no approval signature from the brand channel manager and provides no statement of write permission for the supplier system.

## Three common errors

1. Submitting a replenishment application that is pending approval as an already-authorized procurement request. In the sample, the authorization status is "pending approval by the brand channel manager" with no approval signature attached, and an interface call cannot replace the approval action. For the check, input the sample original text and the drafted request, compare the authorization status field with the request action, and observe whether the request is issued before approval is complete.
2. Treating retrieval or form completion as authorized execution. In the sample, the drafted request asks to write into the supplier system and generate an outbound note, but no write permission statement is provided. For the check, compare the action in the request with the authorization scope provided, and observe whether an unstated downstream business action is present.
3. Treating absent chatId or responseChatItemId system variables in test mode as a supplier business failure. Check the node mode and its available system variables. Their absence does not demonstrate a supplier response error. Check that response separately against the supplier contract.

## How to verify the setup

1. Input the replenishment application original text and the drafted request from the sample. Compare the authorization status "pending approval by the brand channel manager" with the request action "write directly into the supplier procurement system and generate an outbound note." Only when the approval signature is complete and write permission is explicit does the request meet the condition to continue; the current sample state is pending verification.
2. In the paper exercise, bind the upstream number 200 to the custom number variable, substitute it into the Body, and parse the JSON. Check that quantity is the number 200, with cases as the exercise unit, and that appId is a string identifying the source application. Check the token against its secure configuration source separately. No actual binding, authentication, or request result is available; the supplier field contract remains pending.
3. Input the application date "March 10, 2025" from the sample and the cTime system variable. Compare the date range with the request time. Only when the request time falls within the application validity range does the time field meet the checking condition; the sample does not state a validity period, so this item remains unsupported.
