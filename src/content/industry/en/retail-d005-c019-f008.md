# On-demand retail fulfillment: workflow routing for procurement

## What the documents look like

On-demand retail store fulfillment processes online orders by the minute. The working documents for this category include live orders, picking lists, out-of-stock reports, and delivery exception forms. The procurement and supplier records task places supplier profiles, purchase requests, and store stock status into one routing flow. Compared with periodic stocktaking, these records change with each order, and out-of-stock reports and substitution requests arise immediately.

Workflow routing decides which information the Form Input node collects, which decisions the User Selection node evaluates, and which writes and synchronization steps must be handed to an external business interface. A live order, a picking list line, an out-of-stock report, and a delivery exception form each carry different fields and different status meanings, so the routing design has to keep the document type visible rather than treating every input as a generic request.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the required fields and submits, the node passes the collected information to later nodes. The User Selection node is also a user interaction node. It triggers the same interaction state, and when the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. These two nodes collect values and branch on choices. They do not perform purchase approval, supplier onboarding, or stock writes. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval results and form values do not constitute authorization, and a retrieval hit cannot be treated as an approved supplier.

Hypothetical paper exercise sample: the source text of an out-of-stock report awaiting review reads, "Store A submitted an out-of-stock report for a brand of whole milk on 10 March 2025, reported quantity 12 cases, report status pending review, supplier a certain supplier, purchase request not yet submitted." A handover request awaiting judgment reads, "Please convert this report directly into a purchase order and notify the supplier to ship." The source text shows only that the report is pending review and the purchase request has not been submitted. There is no record that a purchase order was generated or that the supplier confirmed supply. The handover request exceeds what the report status supports.

## Configuration and implementation checks

| Configuration item | Type | Description |
| --- | --- | --- |
| Form Input node | Documented node | Triggers the interaction state, collects required fields, passes them to later nodes after submission |
| User Selection node | Documented node | Executes the corresponding "yes" branch after the user makes a choice; verify each branch connection |
| Interaction state check | Implementation check | Recording state is behavior of the interaction nodes; no separate global state-recording switch is set |
| Output handoff check | Implementation check | Pass collected information explicitly to later retrieval, judgment, or interface nodes; compare each output against its input |
| External action split | Implementation check | Order writes, document backfill, and external status synchronization require a separate business interface or later process |
| Retrieval scope check | Implementation check | Verify the target library identifier and vector model identifier, exclude non-matching ones, and record the actual observation |

Hypothetical starting point for this exercise: set the required fields of the out-of-stock report to reporting store, product, quantity, and status. The reason for this choice is that the sample source text happens to contain these four fields, which are compared item by item against the downstream purchase request fields. This starting point is a paper assumption, not an official default value.

## Three common errors

1. Treating a pending-review report as an approved purchase. The sample source text states that the report status is pending review and the purchase request has not been submitted. If the routing directly generates a purchase order and notifies the supplier, the input and the status field disagree, and the action advances beyond the supported stage.
2. Treating a retrieval hit as an approved supplier. Retrieval returns similar content and does not verify supplier onboarding status. If a similar result triggers a procurement write, the authorization basis is absent.
3. Treating the recorded state of an interaction node as a global switch. The Form Input and User Selection nodes entering the interaction state is node behavior. No global state-recording configuration or automatic submission count control can be claimed on that basis.

## How to verify the setup

1. Input the source text of the sample material and the handover request awaiting judgment, then compare the report status field against the requested action. The material shows pending review and a purchase request not yet submitted, while the request asks for direct conversion into a purchase order and supplier notification. The two disagree, so the request is judged unsupported and remains to be verified.
2. Input a paper out-of-stock report whose status field is approved and whose purchase request has been submitted, then compare that status against the downstream procurement write branch. Only when the status field is explicitly approved and the purchase request has been submitted is the write action handed to the external business interface; otherwise record the gap.
3. Input a clearly stated paper retrieval result of an empty array, and check whether the downstream design handles the empty-result branch. The empty array is used only to check the handoff logic; it does not claim that retrieval under a fictional rule necessarily returns an empty array. Libraries across different vector models cannot be associated together. Verify identifiers only, exclude non-matching ones, and record the actual observation.
