# Certificates of origin: HTTP integrations for procurement

## What the documents look like

Certificates of origin serve import-country tariff treatment and customs clearance, and they are not necessarily governed by a letter of credit. For the procurement and supplier records task, this means the material set must support two different activities at once: judging origin rules and completing the certificate application. The working documents are the certificate of origin application, the commercial invoice, the packing list, and production cost records. Data arrives from the China International Trade Single Window, chamber of commerce systems, enterprise production records, and customer clearance requirements. The update rhythm is per shipment or in batches.

At the HTTP integration step, the material that matters is narrower. Purchase origin, supplier identity, and goods description from those documents are passed to an external endpoint through request parameters, headers, a request body, or variable references, and the returned values are then parsed against the endpoint contract. The HTTP module sends a request to a configured address. Params carry path parameters and are common in GET requests. Body carries the request payload and is common in POST and PUT requests. Headers carry special information such as credentials. All three can reference variables using the double-brace form, and the URL can also reference variables. Variables come from global variables, system variables, and upstream node outputs. Returned values are extracted with JSON path syntax, and when the output type is set to string, the value at the configured key is converted to a JSON string.

Two system variables behave differently in test mode: chatId and responseChatItemId do not exist there. An empty value seen while debugging is a mode difference, not a business fault.

Assume a paper exercise sample. A supplier record reads: "Supplier A provided a batch of electronic components in March 2025, purchase contract number PO-2025-0312, country of origin Vietnam, corresponding commercial invoice number INV-2025-0456." A draft sentence is under review: "The country of origin of this batch of electronic components is Vietnam and it can be used directly for a certificate of origin application." The review materials are the supplier record text and the draft sentence. The origin country in the draft matches the supplier record. The claim that it can be used directly for a certificate application has no corresponding authorization or completed application record in the source text, so that part is unsupported.

## Constraints at the HTTP integrations step

The integration does not verify origin, grant authorization, or submit a certificate. It moves values between the workflow and an external endpoint. Several constraints follow.

Request address and method come from the external interface documentation, and the address may reference a variable. The header commonly carries an Authorization value using a Bearer token variable; the credential is injected through secure configuration and is not written into public samples. The request body is used only under the matching request type, and its JSON structure is checked against the external contract. Variable references may draw on global variables, system variables, and upstream node outputs, and each actual passed value is checked against the source material item by item. Return value parsing uses JSON path to extract the needed field, and the key and output type are checked against the interface response example.

A relevance score is not a category, entity, or permission filter, and retrieval is not authorization. The HTTP module's return parsing only extracts values from the response; it does not perform authorization judgment or business approval. An offered option is not execution, and a pending request is not approval. Whether the certificate application was authorized, submitted, or approved is a separate fact that must be evidenced elsewhere.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | How to check it |
| --- | --- | --- |
| Request address | The address given in the external interface documentation; may reference a variable | Compare address and method against the interface documentation |
| Request header | Authorization uses Bearer plus a credential variable | Confirm the credential is injected through secure configuration and kept out of public samples |
| Request body | JSON structure organized per the external interface contract | Use only under the matching request type; check each field against the sample material |
| Variable references | Reference supplier name and invoice number from upstream node output | Check item by item whether the passed value comes from the sample material |
| Return value parsing | Extract the needed field with JSON path | Compare key and output type against the interface response example |
| Debug identity fields | chatId and responseChatItemId do not exist in test mode | Do not treat a debug empty value as a business fault; record the actual observation |

The starting points above are stated for this exercise only. They are not official defaults, and no numeric limit, unit, or global switch is implied.

## Three common errors

1. Treating the country-of-origin field in the supplier record as evidence that the certificate of origin application is already authorized. The source text states only that the origin country is Vietnam. It does not state an application status or an authorization scope, so the draft conclusion is unsupported.

2. Seeing an empty chatId or responseChatItemId in test mode and concluding that the external interface call failed. The documentation states that these two system variables do not exist in test mode, so the empty value is a mode difference.

3. Writing a business authorization field as the HTTP module's return parsing key. Return parsing only extracts a value from the interface response; it does not carry authorization judgment or business approval.

## How to verify the setup

1. Input the sample supplier record text and the draft sentence. Compare the origin country field in the draft against the source text, and check whether "can be used directly for a certificate of origin application" has support in the source text. If the source text states only the origin country, that conclusion is unsupported and the evidence gap is recorded. The expected observation is a match on origin country and an unsupported conclusion on application eligibility.

2. Input the sample purchase contract number PO-2025-0312 and invoice number INV-2025-0456. Compare the variable values referenced in the HTTP request body against the sample material. If the request body variable values come from upstream node output and match the sample, the variable reference configuration meets the check condition. If a variable value is empty or does not match the sample, record it as pending verification. The expected observation is either a match or a recorded discrepancy; no outcome is guaranteed in advance.

3. Input a test request in which chatId is empty. Compare the actual chatId value in the response against the test-mode description. If chatId is empty and the request runs in test mode, this is the documented mode difference. If chatId is empty and the request runs outside test mode, record it as pending verification rather than declaring an interface fault. The expected observation is a documented mode difference in the test-mode case, and an open question otherwise.

These checks use the paper exercise sample only. No test, deployment, approval, or submission is claimed to have occurred.
