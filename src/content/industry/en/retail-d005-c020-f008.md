# Certificates of origin: workflow routing for procurement

## What the documents look like

Certificates of origin serve import-country tariff treatment and customs clearance. They are not necessarily governed by a letter of credit, so the workflow routing for this category organizes nodes around origin-rule determination and certificate completion rather than around document-examination sequences tied to banking terms.

The main data sources are the China International Trade Single Window, CCPIT systems, enterprise production records, and customer clearance requirements. Everyday documents include the certificate-of-origin application, commercial invoice, packing list, and production cost materials. For the inventory procurement and supplier materials task, purchase batches, supplier sources, and production inputs must be mapped to a specific certificate application. Materials update per shipment, and single-shipment and batch handling coexist.

These features shape the routing design. Data collection, rule determination, and certificate completion are distinct node groups. A form submission collects values; it does not confirm origin eligibility. A retrieval result is not an authorization. The relevance score does not act as an entity filter or a permission filter. A pending handover request is not an approved execution.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the required information and submits, the node passes the collected information to subsequent nodes.

The user selection node is also a user-interaction node. It triggers the same interaction state, and when the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch.

Both nodes collect values. Business verification, approval, database writes, and external synchronization require a separate business interface or a downstream process. Retrieval does not constitute authorization, and a relevance score does not perform entity or permission filtering.

Hypothetical paper exercise sample: An exporter intends to apply for a certificate of origin for a batch of inventory-procured goods. The supplier materials text reads: "The main raw materials used in this batch were delivered by Supplier A in March 2024; the purchase contract number and invoice number are in the attachment; this supplier declares the country of production of the raw materials to be Country X." The production cost materials text reads: "This batch of finished goods completed production in April 2024; the raw material input ratio is in the cost detail table." The handover request to be assessed reads: "Please enter the above supplier materials and cost materials into the corresponding fields of the certificate-of-origin application and advance to the certificate completion node." This request states no origin-rule determination conclusion and no certificate declaration authorization status. Both remain matters to be verified.

## Three common errors

1. Treating a form submission as a confirmed origin qualification. Input: the supplier materials and cost materials in the sample. Comparison object: the origin-rule determination conclusion. The sample states no conclusion. Observable result: the flow remains in the pending branch and does not advance to certificate completion.

2. Treating a pending handover request as authorized execution. Input: the request "please enter the above materials into the application and advance." Comparison object: the certificate declaration authorization status. The sample states no authorization. Observable result: only the request is recorded; no completion action is produced.

3. Using a relevance score to exclude unrelated supplier records. Input: supplier entries returned by retrieval. Comparison object: the supplier name and purchase contract number fields. Observable result: a high or low score does not change the entity attribution judgment; identifiers must be checked entry by entry.

## How to verify the setup

1. Input the supplier materials text and cost materials text from the sample. Compare whether the required form fields cover supplier name, purchase contract number, and invoice number. Observable result: all three appear in the collected result; a missing item is recorded as incomplete collection.

2. Input the pending handover request from the sample. Compare the direction of the two branches of the user selection node. Observable result: because the origin-rule conclusion is not stated, the flow enters the "materials pending" branch and does not execute certificate completion.

3. Input a paper empty result []. Compare the downstream node's design for accepting empty input. Observable result: the downstream records the gap and waits for supplementation; no claim is made that a hypothetical rule retrieval necessarily returns empty. For libraries with different vector models, check identifiers only and exclude non-matching ones; do not run cross-model retrieval to compare missed recalls.
