# Brand member operations: HTTP integrations for procurement

## What the documents look like

Brand member operations for a retail brand centres on customer data and repeat-purchase outreach rather than store scheduling. In the procurement and supplier records task, the working material comes from CRM systems, enterprise messaging, POS transaction records and mini-program behaviour data. The day-to-day documents are member tag tables, outreach plans, coupon rules and privacy authorization records. These materials update daily or weekly, and that cadence does not change how an HTTP module sends a request; it only affects which fields are selected when cross-checking.

The HTTP module sends a request to a corresponding address. Params, Headers and Body can each reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables and upstream node outputs. The system variables include appId, chatId, responseChatItemId, variables, cTime and histories, where histories defaults to at most 10 entries and its length cannot be modified. chatId and responseChatItemId do not exist in test mode, so reading an empty value during debugging is an expected behaviour of that mode and does not by itself indicate a business fault.

## Constraints at the HTTP integrations step

Procurement and supplier records involve a supplier entity, a procurement object, a document status and an authorization scope. Once these fields enter an external request, each actual passed value needs item-by-item checking. A similarity score or a retrieval result does not substitute for that check. Retrieval and relevance carry no permission or entity-isolation duty, and a recalled record does not mean the caller is entitled to read or write it.

The chat interface uses APIKey authentication. When calling chat/completions, passing body.appId in the request body is recommended, and the compatibility form Authorization: Bearer <apiKey>-<appId> is also supported. The appId priority order is body.appId, then <apiKey>-<appId>, then the appId associated with the apikey (legacy adaptation). Passed fields such as model and temperature have no effect and are determined by the orchestration. With detail=true, intermediate values can be inspected through responseData, and tokens must be calculated manually. When chatId is non-empty, the system retrieves the session from the database, uses the last item of the messages array as the user question and ignores the remaining messages, and chatId must be shorter than 250 characters.

Hypothetical drill sample: a brand member operations team sends a verification request to a supplier records interface. The source material supplied for verification reads: "Supplier entity: a packaging materials factory in East China; procurement object: outer cartons for a mid-autumn gift box; document status is pending review; authorization scope: limited to this enquiry only." The sentence to be judged reads: "This supplier has completed warehouse-entry authorization." The entity, object, status and authorization scope in that sentence must each be compared against the source material, and a pending-review status does not constitute evidence that authorization is complete.

The assumed trial starting points above are chosen to match the sample material, and each is compared against the external interface contract or the source text rather than against a platform default.

## Three common errors

1. Writing a pending-review status as completed authorization. The document status "pending review" describes the processing stage of that document; "warehouse-entry authorization completed" is a separate authorization fact. The material gives no basis for completed warehouse-entry authorization, so that statement should be marked unsupported and pending verification.
2. Treating a retrieval hit as a permission basis. Recalling a supplier record only shows semantic proximity; it does not show that the caller holds read or write permission on that record, and permission must be determined separately by a downstream implementation.
3. Treating an empty value in debug mode as an interface fault. chatId and responseChatItemId do not exist in test mode, so reading an empty value is an expected behaviour of that mode and must be distinguished from a real request.

## How to verify the setup

1. Input the sample source material and the sentence to be judged, then check the document review status and the basis for warehouse-entry authorization separately. The existing material gives only a pending-review document status and an authorization scope limited to this enquiry, with no record of completed warehouse-entry authorization, so the statement is marked unsupported and pending verification.
2. Input "authorization scope: limited to this enquiry only" from the sample and check the operation scope that this record supports. The record supports only this enquiry scope, and warehouse-entry authorization requires a separate basis; where none is provided, the item remains pending verification.
3. Input a request that contains no supplier entity, object, status or authorization scope, and compare whether the return value extraction configuration can still locate a field. When the extraction result is empty or cannot be located, record it as unsupported and do not infer a cause of interface error.

All of the above is a paper exercise. No test, deployment or approval has been executed, and the relevant business status follows the source material.
