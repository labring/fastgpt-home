# Brand outlet operations: HTTP integrations for procurement

## What the documents look like

Brand outlet discount operations exist to clear seasonal stock. The category does not maintain a full-price new-arrival image, so procurement and supplier records serve clearance decisions rather than new-product presentation. The data sources named for this category are ERP stock age, POS sales, outlet mall campaign records, and historical discount records, with weekly or monthly update frequency. The documents handled day to day include discount approvals, slow-moving stock lists, price tags, and gross-margin calculation sheets.

For the inventory procurement and supplier records task, those materials pass through an HTTP integration step where requests are sent and return values are parsed. The integration itself sends a request and extracts values from the response. It does not perform discount approval, gross-margin calculation, or supplier qualification recognition. Those remain separate business actions with their own authorization.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a configured address. Params carry path request parameters and appear mostly in GET requests. Body carries the request body and appears mostly in POST and PUT requests. Headers carry request headers for special information. All three data locations can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and upstream node outputs.

Return values are not the raw interface response. A key and JSON path extraction configure how the response is parsed. When the output type is set to string, the value at the corresponding key is converted into a json string. Among system variables, chatId and responseChatItemId do not exist in test mode. When the chat completions interface is called, fields such as model and temperature have no effect because the orchestration decides them. A non-empty chatId string means the conversation is taken from the database and the last item in the messages array is used as the user question. Setting detail=true returns intermediate values in responseData. An interactive node returns only type and params in interactive; internal runtime fields such as entryNodeIds are not returned. Form input requires serializing the object into a string as the messages content while keeping chatId consistent. Plugin calls need no chatId and no messages; inputs pass through variables and in a detailed non-stream response, outputs are read from the pluginOutput field of the moduleType=pluginOutput element in responseData.

Hypothetical drill sample: a brand outlet clearance team, on 10 March 2025, organizes a batch of seasonal stock. The supplier record page states: "Supplier code S-041, contact person changed, latest reconciliation period February 2025." The same page carries a draft sentence: "This supplier has passed this quarter's discount approval and can execute against the new price tag directly." The comparison material is those two passages. The object of judgment is the status description "has passed this quarter's discount approval."

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Check method |
| --- | --- | --- |
| Request address | External supplier record interface address | The address can reference a provided variable; select the method per the external interface documentation |
| Headers authentication | Authorization header | Credentials inject through secure configuration and are not written into public samples |
| Body structure | Supplier code and reconciliation period fields | Used only under the corresponding request type; check the JSON structure against the external contract |
| Variable reference | Supplier code from an upstream node output | Check the actual passed value item by item against the sample text |
| Return value extraction | Extract reconciliation period by JSON path | When output type is string, the value converts to a json string |
| Debug identity | chatId does not exist in test mode | Do not treat a debug empty value as a business fault |

The hypothetical trial starting point was chosen because the sample involves two fields, supplier code and reconciliation period, which need to pass through Body and be extracted from the return value. The comparison objects are "S-041" and "February 2025" in the sample text. A return value matching the sample text can proceed to manual review; a mismatch is recorded as a difference.

## Three common errors

1. Treating an interface return value as evidence that discount approval passed. The input is the reconciliation period returned by the supplier record interface. The comparison object is the status "has passed this quarter's discount approval" in the sample text. When the interface return value contains no approval status field, that status remains unsupported.
2. Judging a chatId empty value in test mode as a session fault. The input is a request in test mode. The comparison object is the documented statement that chatId does not exist in test mode. The observable result is that the request sends normally without session context, which is a documented condition.
3. Passing a form input object directly as messages content. The input is an unserialized object. The comparison object is the documented requirement to serialize the object into a string. The observable result is that the interface cannot parse it as expected, and the request needs resubmission in the documented format.

## How to verify the setup

1. Use the sample text "Supplier code S-041, latest reconciliation period February 2025" as input. Compare the corresponding fields in the interface return value. A return value matching the sample text passes; a missing or different value is recorded as a difference with the original text retained.
2. Use the draft sentence "This supplier has passed this quarter's discount approval" as the content to be judged. Compare whether the sample text contains an approval status field. When the original text does not state it, the judgment is unsupported, and a successful interface call does not make it an approved status.
3. Send a request with detail=true. Compare whether responseData contains the required intermediate value. When the result has no corresponding module status, record it as pending verification without inferring a failure cause. An empty result can be checked against the explicit paper input `[]` to review downstream design, without claiming that a fictional rule retrieval must return empty.

This page addresses only brand outlet discount operations, inventory procurement and supplier records, and HTTP integrations with external systems. Which materials, operations, and requests sit at which authorization state during handover cannot be converted into authorization execution by retrieval or forms. The integration sends requests and parses return values. Discount approval, gross-margin calculation, supplier qualification recognition, database writes, and external synchronization require their own stated downstream implementation.
