# Brand-owned store operations: HTTP integrations for procurement

## What the documents look like

Brand-owned stores are staffed and accounted for directly by the brand rather than managed through a franchise contract, and that difference shapes how inventory procurement and supplier records change hands. Daily documents center on daily sales reports, shift schedules, display photos, and inventory transfer orders. Data arrives from POS systems, member CRM, ERP inventory, and store inspections, with daily or weekly update rhythms.

For this task, the HTTP module carries the request to an external system and extracts the returned value. The daily or weekly rhythm describes how often the underlying material changes; it does not establish batch synchronization, full synchronization, real-time pushing, or transaction-triggered mechanisms.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a target address, and its behavior resembles direct-call tools such as Postman and ApiFox. Params carries path parameters and appears mostly in GET requests. Body carries the request payload and appears mostly in POST and PUT requests. Headers carries special information. URL, Body, and Headers can all reference variables through `{{}}`, and those variables come from global variables, system variables, and upstream node outputs.

Return values are extracted from the interface response by JSON path, and the configured key follows JavaScript object access rules. When the output type is set to string, the value at the corresponding key is converted into a JSON string. The system variables chatId and responseChatItemId do not exist in test mode, so an empty value during debugging is not by itself a business fault. Retrieval and forms collect and pass values; business verification, approval, database writes, and external synchronization each need their own downstream implementation.

Hypothetical paper exercise: a brand-owned store manager submits an inventory transfer order. The material text reads: "Transfer order DB-2025-0417-03; source store Brand-owned Store A; destination store Brand-owned Store B; item a summer short-sleeve style; quantity 24 pieces; application date April 17, 2025; status submitted by store; regional manager approval field empty." The proposed handoff request reads: "Push this transfer order to the ERP inventory system through the HTTP interface and synchronize the supplier contact in the supplier records." In this exercise, submitted by store records only that the submission action completed. The approval field is empty, the material provides no approval record, and the approval result remains to be verified. The push and the synchronization are business actions that require separately connected system implementations.

## Configuration and implementation checks

| Configuration item | Assumed trial starting point for this exercise | Reason and comparison object |
| --- | --- | --- |
| Request address | Reference the address variable given in the external interface document | Compare character by character against the address in the external interface contract |
| Request method | POST as the exercise candidate; the actual method remains to be verified | Confirm against the real ERP interface contract; do not substitute a node or verb name for the contract |
| Headers authentication | Inject credentials through security configuration; do not write them into public samples | Compare against the authentication field name required by the external interface document |
| Body structure | Declare transfer order fields according to the external interface contract | Compare field names and types item by item against the contract |
| Return value extraction | Extract the required key by JSON path | Compare against the hierarchy in the interface response example |
| Output type | String, for downstream text concatenation | Compare against the type the downstream node can accept |

These are assumed trial starting points for this exercise, not official defaults.

## Three common errors

1. Treating submitted by store as approval. The submission action and the approval result occupy different fields. The material gives a submitted status and an empty approval field, with no approval record, so the approval claim remains to be verified; the absence of a record does not establish that approval did not occur.
2. Treating the transfer quantity collected by a form as already written to ERP. A form collects values. Database writes and external synchronization each require their own downstream implementation.
3. Treating an empty chatId or responseChatItemId in test mode as an interface failure. The documentation states that these two fields do not exist in test mode.

## How to verify the setup

1. Input the transfer order and the proposed request, then check the address, method, field types, and authorization item by item once the ERP contract is obtained. Whether the request can be sent and what the approval result is are checked separately. With no contract and no approval record at hand, the push claim does not establish that approval has changed or will not change.
2. Input the sample material text and compare whether the phrase "synchronize the supplier contact in the supplier records" in the proposed handoff request has a corresponding downstream implementation description. The condition is met only when an explicit implementation description exists; otherwise record an evidence gap.
3. Input a request in test mode and compare whether chatId and responseChatItemId are empty. The condition is met only when this is confirmed as the test-mode behavior described in the documentation; do not judge a business fault from it.

These are paper review expectations and were not actually executed.
