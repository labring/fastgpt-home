# Dealer ordering events: workflow routing for procurement

## What the documents look like

Dealer ordering events serve offline dealer reservations and do not directly manage platform storefronts. For the inventory procurement and supplier records task, the main data sources are the ordering event system, historical sales, dealer inventory and financial credit. Day-to-day documents include the ordering handbook, the ordering contract, the sample list and credit approval. Update frequency is quarterly and annual. These characteristics mean workflow routing has to separate the fields collected by interaction nodes from downstream actions. The form input node enters an interaction state when triggered, collects required information, and passes that information to later nodes after submission. The user selection node executes the corresponding "yes" branch after the user makes a choice. Collected order quantities, sample list write-backs or credit approval requests are input values; business writes and external synchronization need a separate business interface or a later process.

## Constraints at the workflow routing step

Interaction nodes record workflow state and wait for the user to complete the interaction before execution continues. Form input and user selection are both user interaction nodes, can be added repeatedly, and trigger execution. During configuration, verify branch connections one by one and pass collected information explicitly to later retrieval, judgment or interface nodes, comparing output against input item by item. Retrieval or a form does not constitute authorized execution: whether credit approval passes, whether the ordering contract is signed, and whether an order is written all require downstream implementation or manual verification, and cannot be presumed from a retrieval result or form submission. Libraries under different vector models cannot be associated together; check identifiers first and exclude non-matching ones, and do not run cross-model retrieval to compare missed recalls. Optional paths shown in the overall document flow diagram do not mean every request executes all of them: image retrieval requires a corresponding image input and model capability, and reranking requires a model and must be enabled according to settings.

Hypothetical exercise sample: the source material reads, "Dealer A submits an ordering intent form, object is the autumn collection, quantity 1200 units, status pending review; the credit approval form shows a requested limit of 800,000 yuan, status pending review." The draft sentence to be judged is, "Dealer A has completed credit approval and is approved to order." According to the source, the credit approval form status is pending review, so the draft sentence's claim that credit approval is completed is not supported and should be recorded as pending verification.

## Three common errors

1. Treating form submission as completed authorization. In the sample the credit approval form status is pending review, and submitting an ordering intent form does not equal approval. When the downstream interface or manual verification has not run, "approved to order" cannot be output.
2. Treating a retrieval result as a permission or entity filter. A similarity score does not exclude unrelated dealers or unauthorized records; the same-vector-model requirement for retrieval libraries cannot be extended to require external systems to use the same model.
3. Treating optional paths as executed on every run. Image retrieval requires an image input and model capability, and reranking requires a model and must be enabled according to settings. When conditions are missing, record the actual observation and do not infer a run result.

## How to verify the setup

1. Input the sample source material and the draft sentence, compare the credit approval form status field "pending review" against the draft sentence's "has completed credit approval," and observe whether the output marks the draft sentence as unsupported or pending verification. If the output says "completed," the condition is not met.
2. Input the sample's order quantity of 1200 units and the hypothetical trial starting point of 0, compare whether the field collected by the form input node matches the field received by the later node, and observe whether the later node receives 1200 units. If the later node receives an empty value or 0, the condition is not met.
3. Input a credit approval request, compare the user selection node's "yes" branch connection against the downstream interface node, and observe whether the branch executes as documented and records state. If the branch is not connected or the downstream is not implemented, record the gap and do not judge the approval as passed.
