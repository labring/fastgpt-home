# Supermarket supplier accounts: HTTP integrations for procurement

## What the documents look like

This category covers supplier settlement for supermarket procurement, where accounts are typically purchase-and-sale or consignment payables and a resident counter operation does not necessarily exist. The core reconciliation chain runs through purchase contracts, delivery acceptance notes, rebate agreements and statements of account. Data originates from ERP procurement, supplier portals, POS sales and finance systems. Disputes over payables, supplier suspension of delivery and fair-trading requirements mean an interface call must be traceable to a specific document. Document updates occur weekly or monthly; this page does not infer batch synchronization, full synchronization or transaction-triggered mechanisms from that cadence.

A purchase contract may state that settlement follows the delivery acceptance note signed by the receiving party. A delivery acceptance note may record a signed quantity of 120 cartons on 8 April. A rebate agreement may state that rebates settle quarterly. These three sentences are the material scope for the checks below.

## Constraints at the HTTP integrations step

The HTTP module can be added repeatedly, configured manually and triggered to execute. It sends a request to a target address. Params are mostly used for GET requests, Body for POST/PUT requests, and Headers carry special information. All three data locations and the URL can reference variables through `{{}}`, drawing on global variables, system variables and upstream node outputs. Return values require extraction by JSON path.

The chat completions interface authenticates with an APIKey. Passing `body.appId` in the request body is recommended; `Authorization: Bearer <apiKey>-<appId>` is also supported, in which case `body.appId` is not needed. The appId priority order is `body.appId`, then `<apiKey>-<appId>`, then the appId associated with the apikey. Using `authProxy` to act on behalf of a team member requires the team owner to enable it when creating or editing the key, and the proxied identity still needs permission on the target application and conversation. This applies only to FastGPT versions at or above v4.15.0. Passed `model` and `temperature` fields have no effect; these are determined by the orchestration. `chatId` and `responseChatItemId` do not exist in test mode, so an empty value during debugging does not indicate a business fault. An interactive node returns `interactive` as a display configuration containing only `type` and `params`; internal runtime fields such as `entryNodeIds`, `memoryEdges`, `nodeOutputs` and `nodeResponseId` are not returned. Forms collect values; business verification, approval, database writes and external synchronization each need their own downstream implementation.

Hypothetical paper exercise sample: a supermarket buyer and a supplier sign a purchase-and-sale procurement contract stating that settlement follows the delivery acceptance note signed by the receiving party. The delivery acceptance note records a signed quantity of 120 cartons on 8 April. The rebate agreement states that rebates settle quarterly. The draft sentence to be assessed is: "The reconciliation quantity for this period follows the supplier's shipped quantity of 150 cartons." This sentence conflicts with the signed quantity of 120 cartons, and the contract designates the signed note as the basis.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison method |
| --- | --- | --- |
| Request address | The procurement order query address given in the external interface document | Address taken from the document; compare character by character against the path listed there |
| Request method | GET, per the document | Compare against the method marked in the document; record any mismatch |
| Headers authentication | Authorization references a credential injected by secure configuration | Compare against the document's authentication specification; credentials are not written into public samples |
| Body structure | Fields written to the document's JSON contract | Compare field names and levels item by item against the document |
| Return value extraction | Extract the signed quantity field by JSON path | Compare against the actual response structure |
| Variable reference | Reference the acceptance note number from an upstream node output | Compare against the actual node output value |

These values are hypothetical starting points for this exercise, not official defaults.

## Three common errors

1. Treating the supplier's shipped quantity as the reconciliation quantity. Input: shipped quantity 150 cartons. Comparison: signed quantity 120 cartons on the acceptance note. Observable result: the two values differ and the contract designates the signed note as the basis.
2. Treating an empty `chatId` or `responseChatItemId` in test mode as an interface fault. Input: a request in test mode. Comparison: the documented statement that these do not exist in test mode. Observable result: the missing field is expected.
3. Treating the interactive node's display configuration as containing internal runtime fields. Input: an interactive node response. Comparison: the documented return of only `type` and `params`. Observable result: fields such as `entryNodeIds` do not appear.

## How to verify the setup

1. Input the contract text, the acceptance note text and the draft sentence from the hypothetical sample. Compare the draft sentence quantity against the signed quantity on the acceptance note and the contractual basis. When the draft sentence matches the signed quantity and its basis points to the signed note, the check passes.
2. Input a request that references the acceptance note number from an upstream node. Compare the value actually passed against the node output value. When the two match character by character, the variable reference is correct; when they differ, record the difference without inferring a failure cause.
3. Input a request with `detail=true`. Compare whether `responseData` in the response contains module status and complete results. When the fields appear as documented, the parsing configuration is usable; when they are missing, record the gap without asserting an interface fault. Retrieval and similarity do not carry permission or entity isolation; fields not stated in the documents remain unknown.
