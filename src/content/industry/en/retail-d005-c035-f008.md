# Trade returns and claims: workflow routing for procurement

## What the documents look like

Trade returns and claims handle reverse logistics and liability determination after goods have been exported. The working documents for a case include the return agreement, the claim letter, the quality report, and the return customs declaration. Inputs arrive from customer email, inspection reports, customs systems, and insurer claim systems. A case is assembled irregularly, on a per-case basis rather than on a fixed schedule, so the workflow must accept material as it is submitted rather than assume a synchronized feed.

For the procurement and supplier records task, workflow routing has to break the three slowest steps — confirming the return reason, filing the return declaration, and submitting claim evidence — into interactive nodes. Those nodes collect what an operator enters or selects about material status, then pass that collected information to later retrieval or decision nodes. The routing step organizes and forwards what a person supplies; it does not decide liability, sign agreements, or move money.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues only after the user completes the interaction. Once required fields are filled and submitted, the node collects the submitted form information and passes it to later nodes. The user selection node behaves the same way at the interaction level: it triggers an interaction state, records workflow state, and continues after the user responds. When the user makes a choice, the node evaluates that choice and executes the "yes" branch.

Neither node writes orders, backfills documents, or synchronizes external status. Those actions require a separate business interface or a later process. Retrieval output is not authorization, and a similarity setting does not exclude unrelated business records or unauthorized records. A pending request is not an approval, an offered option is not execution, and an unsigned termination is not a completed termination.

Hypothetical drill sample: the source material reads, "Supplier A issued a quality report on 10 March 2025 stating that batch B-0310, 120 units, showed solder joint cracking, judged to be a production cause; the draft return agreement states the same 120 units of the same batch are to be returned, and the signature field is blank." The draft sentence awaiting judgment is: "The return reason for this batch has been confirmed by the supplier, and the return agreement has taken effect." The source supports only the quality report's production-cause judgment. The blank signature field means the agreement has not taken effect, so the draft sentence exceeds the evidence.

## Configuration and implementation checks

| Configuration item | Setting or check content | Relation to this page's sample |
|---|---|---|
| Form input node | Enters interaction state on trigger, collects required information, passes it on after submission | Collects batch number, quality report date, return quantity |
| User selection node | Executes the "yes" branch after the user makes a choice; verify each branch connection | Judges whether the return reason has been confirmed |
| Interaction state check | Recording state is behavior of the interaction node; no separate global state switch is set | Checks whether the sample material sits in an interaction wait |
| Output handoff check | Passes collected information explicitly to later retrieval, decision, or interface nodes | Compares batch number and quality report output for consistency |
| External action split | Order writes, document backfill, and external synchronization attach to a separate business interface | Signing and effect of the return agreement are not completed by the node |

## Three common errors

1. Treating the quality report's production-cause judgment as proof that the return agreement has taken effect. In the sample the signature field is blank, the agreement has not taken effect, and the draft sentence is unsupported.
2. Treating the "yes" branch of the user selection node as authorized execution. The choice only determines the workflow direction; it does not write orders or backfill documents.
3. Treating retrieval output as a permission filter. A similarity score does not exclude unauthorized records, and retrieval is not authorization.

## How to verify the setup

1. Input the sample source material and the draft sentence, then compare whether the draft sentence exceeds the evidence of the quality report and the draft agreement. If "the agreement has taken effect" appears while the signature field is blank, the sentence is unsupported.
2. Input batch number B-0310 and the quantity 120, then compare the form output with the values stated in the quality report. If the two agree and the branch connections are correct, the handoff condition is met.
3. Input an empty result [] and check the downstream design, observing whether the downstream keeps a record of the gap. If the downstream does not treat the empty result as a negative conclusion, the condition is met.
