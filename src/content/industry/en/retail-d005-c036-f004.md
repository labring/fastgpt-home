# Multi-warehouse inventory: vector indexes for procurement

## What the documents look like

Multi-warehouse allocation and inventory synchronization sit at the order-routing stage and decide which warehouse ships an order. For procurement and supplier records, the working documents are allocation rules, inventory synchronization tables, transfer orders and stockout alerts. They arrive from WMS, OMS, ERP inventory and platform inventory interfaces, and they update by day or by hour. Field definitions can differ between sources, so the same supplier or item may be described with different wording across documents.

At the vector model and index step, these documents become searchable libraries, collections and data records. The smallest search unit is the library: a search covers the whole library, while collections only classify data and do not affect search results. One original data record can map to several vectors, because a single `indexes` field in the `dataset.datas` table stores an array of vector IDs. Index content and original content are checked separately. A long text block can carry multiple index entries so that a match on any one entry recalls the whole record.

## Constraints at the vector indexes step

Knowledge bases linked for retrieval must use the same vector model. Confirm the actual model and its input type before linking; libraries built on different vector models cannot be linked together. Index content benefits from being complete and focused, and the trade-off between retrieval coverage and index length is weighed against real samples. Image retrieval depends on whether image descriptions or image vectors were generated at ingestion time, and query-side uploads alone do not decide whether an image can be found.

Semantic recall and relevance affect ordering and filtering. They do not isolate permissions or business entities. Retrieval is retrieval; authorization is authorization. A pending review does not show that an operation right is missing, and signing, reaching cooperation and contract effectiveness are three separate facts.

Hypothetical exercise sample: the source text reads "Supplier A submitted a quotation on 1 March 2025, valid until 30 April 2025; procurement handler B submitted a cooperation application on 5 March 2025, status pending review; the two parties have not signed a procurement contract." The draft sentence to be judged is "Supplier A and the purchasing party have reached cooperation, and the contract is effective." The judgement must use the same subject, the same period and the same field: a quotation validity period does not state a supply period, pending review is not approval, and an unsigned contract does not produce an effective fact. The draft sentence is unsupported.

## Configuration and implementation checks

The table below covers settings or implementation checks documented for this page's sample. Values are hypothetical starting points for this exercise, chosen for comparison against another value, and are not official defaults.

| Configuration item | Hypothetical starting point and reason | Comparison method and observation |
| --- | --- | --- |
| Linked knowledge bases | Select only libraries that share one vector model | Check the model identifier, exclude non-matching libraries, and do not run cross-model retrieval |
| Index content | Build focused indexes for allocation rules and inventory synchronization tables | Use one question set and compare whether returned references point to the corresponding source material |
| Reference limit | Control the amount of referenced content by tokens | Compare against a smaller or larger value and observe whether returned references are trimmed |
| Minimum relevance | Applies only under semantic retrieval or result reranking | Adjust the value and observe whether low-relevance results are filtered |
| Search mode | Use full-text or hybrid retrieval for number and model queries | Compare against semantic retrieval and observe differences in hits |
| Result reranking | Runs when a model is available and the setting is enabled | Compare rerank scores with vector scores and filter by score |

RRF is the fusion step for multiple result paths and is not an on/off switch. Question optimization adds one model call, and whether to enable it depends on observed results.

## Three common errors

1. Treating pending review as approval. In the sample, the cooperation application status is pending review. If the draft sentence says cooperation has been reached, the input is the status field, the comparison is between "pending review" and "reached cooperation", and the observable result is that the sentence is unsupported.
2. Treating the quotation validity period as a supply period. The sample records only that the quotation is valid until 30 April 2025 and states no supply period. A draft sentence that turns this into a supply commitment is an extrapolation beyond the field, and the result is recorded as unsupported.
3. Linking knowledge bases built on different vector models. If two libraries with different vector models are linked together, the correct action is to check the model identifier, exclude the non-matching library and record the actual observation, without inferring missed recalls or redundant results.

## How to verify the setup

1. Enter the sample source text and the draft sentence, compare "pending review" and "not signed" with "reached cooperation" and "effective", and observe whether the draft sentence is marked unsupported.
2. Enter one question set to search the allocation rules and the inventory synchronization table, compare whether returned references point to the corresponding source text, and observe whether the referenced content can be traced back.
3. Enter a number or model query, compare hits between full-text retrieval and semantic retrieval, and observe whether the precise query goes through full-text or hybrid retrieval. If a search returns an empty array, the downstream design handles a reference length of 0; no claim is made that a fictional rule must return an empty array.
