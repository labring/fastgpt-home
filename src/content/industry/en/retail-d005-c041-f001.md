# Marketplace promotions: procurement with HTTP integrations

## What the documents look like

For procurement in Marketplace promotions, this page examines FastGPT HTTP integrations. Promotion submission, approval and stock-lock arrangements need separate checks. Procurement requires the current item’s actual sources rather than a complete-looking activity document set. The examples are hypothetical.

## Constraints at the HTTP integrations step

Promotion-related procurement can read registration, approval scope and stock-lock wording without amounts or rates. Proposed sources lack current platform acceptance or actual reservation. The real contract must define item, activity and period conditions without presumed marketing-to-stock connectivity. Shared activity names do not establish universal applicability, and approval text supplies no inventory change or availability from complete titles.

## Configuration and implementation checks

| Procurement-reading check | Proposed material | Actual supporting evidence |
| --- | --- | --- |
| Registration stage | Submission without platform feedback | No direct approval conclusion |
| Approval scope | Item and period passage | Other applicability not borrowed |
| Stock execution | Lock arrangement separate from reservation | Obtain corresponding business record |
| Present reading | Activity identity and actual conditions | Return supports this item |
| Further action | Separate purchase, submission and writing | Reading is not campaign execution |

### Documented conditions

| Documented item / implementation check | Condition |
| --- | --- |
| `Request address and method` | The request address and method follow the external contract. |
| `Params and Headers` | Inspect parameters, headers and authentication separately. |
| Body | Where a JSON body is used, validate its structure against the external contract. |
| `Variable references` | Variables can come from global, system or upstream outputs. |
| `Debug identity fields` | Test mode lacks chatId and responseChatItemId. |

## Three common errors

Submission described as acceptance needs the current processing response. Approval for another item or period requires passage and query-condition checks. A lock plan described as reserved stock needs actual execution evidence. These concern platform stage, applicability and business execution rather than a successful request.

## How to verify the setup

Retain activity, item, version, sent values and return. Repeat with corresponding platform or stock sources and inspect actual traceability. Check headers, parameters and any appropriate body under the contract with private authentication. Ordering, activity submission, stock writes and publication need authority and real receipts. Reading establishes neither secured supply, platform acceptance nor executed campaigns.
