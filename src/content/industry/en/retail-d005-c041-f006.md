# Marketplace promotions: scheduled workflows for procurement

## What the documents look like

Promotion enrollment and price management revolve around price, inventory and campaign rhythm. Reviewing promotional wording belongs to a separate line of work. The daily materials are campaign enrollment forms, promotional price approval sheets, inventory lock sheets and campaign review sheets. Their data comes from platform marketing backends, ERP inventory and historical transaction prices. Calculating the lowest final price, locking campaign inventory and synchronizing prices across multiple platforms are the time-consuming steps. Errors here produce campaign losses, removal from resource slots or price complaints.

Inventory procurement and supplier records connect supplier quotations, purchase arrivals, inventory occupation and campaign enrollment. Scheduled workflows and automation can read external data on a fixed rhythm and issue HTTP requests. Reading results and business writes are separate stages.

## Constraints at the scheduled workflows step

In FastGPT, a scheduled workflow sends a request to a target address through the HTTP module. Params carry path request parameters and are used more often with GET requests. Body carries the request body and is used more often with POST and PUT requests. Headers carry special information. All three can reference variables with `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime and histories. Histories takes at most 10 records by default and the length cannot be changed. Return values require a configured key, extracted from the converted format according to JavaScript object access rules. When the output type is string, the value of the corresponding key is converted into a json string. The HTTP module can connect to public APIs for operating databases, calling external data sources, running web searches and sending email.

Triggering is handled by the application's scheduling capability or by an external scheduler, and the available entry point must be checked against the actual version. External data is read through an already configured interface. A scheduled trigger does not by itself establish a connection to a business system. Deduplication, idempotency and business writes need explicit design in the interface or in downstream steps. Execution records need to be checked against trigger time, actual input, returned result and business status.

Hypothetical exercise sample: on 3 June 2025, a marketplace store operations team organizes inventory procurement records for Supplier A. The source material reads: "Supplier A quotation number A-0603, quotation valid until 30 June 2025; the purchase arrival note shows 200 units arriving on 5 June; the inventory lock sheet records 150 units occupied for a campaign on 8 June." A handover request awaiting judgment reads: "Please have the scheduled workflow automatically write 150 units of inventory into the campaign enrollment form on 8 June and synchronize it to the marketplace campaign backend." In this request, "automatically write" and "synchronize" are business actions requiring separately connected system implementation. The material does not state authorization or an interface, so the request is marked as pending verification.

## Three common errors

1. Treating the scheduled trigger as automatically establishing a business system connection. The automated request for 8 June in the sample requires an interface and authorization. The material does not state them, so the item remains pending verification.
2. Writing the return value key as if it were the interface return value itself. A return value represents how to parse the interface response. It must be configured by JavaScript object access rules, and when the output type is string the value is converted into a json string.
3. Treating deduplication, idempotency and business writes as automatically present. These require explicit design in the interface or in downstream steps. The write and synchronization in the sample are business actions requiring separately connected system implementation.

## How to verify the setup

1. Enter the source material text and the handover request. Compare whether "automatically write" and "synchronize" in the request have corresponding interface and authorization descriptions. If the material does not state an interface and authorization, record the item as pending verification. Do not judge it as authorized or executed.
2. Enter the request method and Headers listed in the interface documentation. Compare whether the method, Authorization and other fields in the configuration match the documentation. If they differ, record the difference. Do not infer automatic correction.
3. Enter the interface response example and the configured return value key. Compare whether the extraction path hits the target field by JavaScript object access rules. If a change in the response structure causes the path to miss, record the actual observation. Do not guarantee a first-record hit or full recall.
