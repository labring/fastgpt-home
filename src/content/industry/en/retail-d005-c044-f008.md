# Marketplace advertising: workflow routing for procurement

## What the documents look like

Marketplace advertising adjusts bids against traffic and conversion in near real time, so delivery plans, keyword reports, audience package descriptions and conversion attribution tables move on a daily or hourly cadence. Procurement and supplier materials form a separate stream: purchase requests, supplier quotations, supply status and authorization boundaries. When both streams pass through one workflow, the routing design has to mark which fields originate on the advertising side and which on the procurement side, and record the state each document holds at handover. The brief states daily or per-order updates for the advertising materials; that fact describes material freshness only and does not justify assuming batch synchronization or transaction-triggered mechanisms.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues only after the user completes the interaction. Once required fields are submitted, the node collects the entered form information and passes it to downstream nodes. The User Selection node behaves the same way on trigger, and when the user makes a choice the node evaluates that choice and executes the corresponding "yes" branch. Interaction-state recording is behavior of these interaction nodes; no separate global state-recording switch is documented. Collected values must be passed explicitly to later retrieval, decision or interface nodes, and each output must be compared against its input item by item. Order writes, document backfill and external status synchronization require a separate business interface or downstream process. Retrieval and forms do not constitute authorized execution.

Hypothetical paper exercise sample: the source text reads "Supplier A submitted a quotation on 1 March 2025, valid until 31 March 2025; the buyer's internal approval record shows the quotation status as 'pending review'." The proposed sentence under review is "Supplier A's quotation has been approved and procurement may proceed." In this sample the subject is Supplier A, the object is the quotation, the status is pending review, and the effective range ends 31 March 2025. Pending review does not demonstrate the absence of operating authority, and quotation validity does not indicate a supply deadline. The proposed sentence records pending review as approved, which is a status misreading.

## Configuration and implementation checks

| Configuration item | Setting or check | Relation to this page's sample |
| --- | --- | --- |
| Form Input node | Collect required fields such as purchase request number, supplier name, quotation date | Supplier A and the quotation date serve as sample inputs |
| User Selection node | Define "continue verification" and "return for supplement" branches | Which branch a pending-review status takes requires human judgment |
| Interaction-state check | Confirm the node enters the interaction state and records it on trigger | The sample's submission remains traceable afterward |
| Output handover check | Pass form output to a later retrieval or decision node | The sample's quotation source text must reach the comparison step |
| External action separation | Connect order writes and status synchronization to a business interface | The sample's procurement does not complete through form submission |
| Hypothetical trial baseline | This exercise uses quotation validity 31 March 2025 as the comparison baseline, chosen because the sample source text states that date | Compared against the approval wording of the proposed sentence |

## Three common errors

1. Treating a pending-review status as approved. The sample source text states "pending review"; the proposed sentence states "has been approved". These are mutually exclusive values on the same field, which is a contradiction.
2. Treating quotation validity as a supply deadline. The sample states only validity until 31 March 2025 and states no supply deadline. Deriving executable procurement from it is unsupported.
3. Treating form submission as completed authorization. The Form Input node collects information and passes it onward. In the sample, procurement execution needs a separate business interface, and the submission action does not constitute approval.

## How to verify the setup

1. Input the sample source text and the proposed sentence, then compare whether "pending review" and "has been approved" are mutually exclusive on the same field. When mutually exclusive values appear, the proposed sentence does not hold.
2. Input the sample source text and check whether a supply deadline is stated. The source text carries only quotation validity; when no supply deadline is stated, record the evidence gap and do not conclude that procurement may proceed.
3. Input the sample source text and the form output, then check whether form submission triggers an external procurement interface. The sample does not describe that interface, so after submission only information transfer is complete and the procurement execution state remains unknown.
