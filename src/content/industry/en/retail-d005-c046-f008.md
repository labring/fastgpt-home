# Marketplace category access: workflow routing for procurement

## What the documents look like

Category access review happens before a listing is published or a store is onboarded. The review object is the operating entity's qualifications and the authorization chain, not post-listing performance. In the inventory procurement and supplier materials task, the documents that move through the workflow include the business license, trademark registration certificate, brand authorization chain, and industry license. These materials are typically submitted by marketplace recruitment operations, onboarding specialists, or brand-side channel managers, and they originate from separate places: the platform recruitment page, the national enterprise credit information publicity system, trademark office data, and license systems. Materials update irregularly, and each onboarding attempt can produce a new version, so the workflow needs to record the input and output of each interaction.

The practical consequence for routing is that a single submission may carry several documents whose values must stay distinguishable. An authorization chain can contain multiple levels of entities, and the form step has to collect entity names, the authorized object, and the valid scope. Those values then pass into later nodes, where the output is compared item by item against the input to confirm the transfer relationship holds. Order writes, document backfill, and external status synchronization require a separate business interface or a later process; the form itself only completes value collection.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues downward after the user completes the interaction. The node collects the required information the user fills in and, after submission, passes that information to subsequent nodes. The User Selection node is also a user interaction node with the same interaction-state behavior. When the user makes a selection, the node evaluates that selection and executes the corresponding "yes" branch. Its basic use is to pose a question requiring a decision and then route different workflow paths according to the user's response.

Both nodes record workflow state and wait for the interaction to finish before continuing. Neither node performs business approval, authorization validation, or external synchronization. In the inventory procurement and supplier materials task, that distinction matters because the authorization chain may be multi-level and the collected values must be compared against the source documents before any downstream conclusion is drawn.

Hypothetical paper exercise sample: a supplier submits a brand authorization letter whose text states "Authorizing party A, authorized party B, authorized sales category is household appliances, authorization valid until 31 December 2026." The supplier also submits a draft sentence: "B has obtained A's authorization for all categories and may list immediately." The pending request is to mark the authorization status corresponding to that draft sentence as "effective." The source text states only the household appliances category and does not state all categories. The validity date is in the future, and the text does not state a signing date or effectiveness conditions. The authorization boundary for that request does not hold.

## Configuration and implementation checks

| Configuration item | Type | Verification note for this page |
| --- | --- | --- |
| Form Input node | Interaction node | Triggers interaction state, collects required information, passes it to subsequent nodes after submission |
| User Selection node | Interaction node | Executes the corresponding "yes" branch after the user makes a selection; verify branch connections one by one |
| Interaction state check | Behavior check | State recording is behavior of the interaction nodes; no separate global state-recording switch is set or claimed |
| Output handoff check | Transfer check | Pass collected information explicitly to subsequent retrieval, judgment, or interface nodes; compare output against input item by item |
| External operation boundary | Boundary check | Order writes, document backfill, and external status synchronization require a separate business interface or later process |
| Hypothetical trial starting point | Paper check | This exercise starts from the category field in the authorization letter source text and compares it against the all-categories wording of the draft sentence, noting the difference |

## Three common errors

1. Treating the authorization category value collected by the Form Input node as an all-categories authorization. The input is the source category field "household appliances," the comparison object is the draft sentence "all categories," and the observable result is that the two do not agree, so the item is marked pending verification.

2. Treating the "yes" branch of the User Selection node as completed business approval. The input is the user's selection action, the comparison object is the approval status field, and the observable result is that branch execution does not equal the existence of an approval record.

3. Treating the recorded interaction state as proof that authorization is effective. The input is the state recorded by the node, the comparison object is the effectiveness conditions of the authorization letter, and the observable result is that a state record and effectiveness conditions are different facts.

## How to verify the setup

- Verification one: using the hypothetical sample source text above, input the authorization letter category field "household appliances" and compare it against the draft sentence "all categories," observing whether the two agree. The expected result is that they do not agree and the draft sentence is not supported.

- Verification two: using the pending request "mark the authorization status corresponding to that draft sentence as effective," input the request content and compare it against whether the authorization letter source text states a signing date and effectiveness conditions, observing whether the source text contains those fields. The expected result is that they are not stated and the request remains pending verification.

- Verification three: using the paper input `[]` to check the downstream design, input the empty result and compare it against whether the downstream node has empty-value handling logic, observing whether the downstream produces an undefined output. The expected result is that the downstream must define empty-value handling, without claiming that a fictional rule retrieval necessarily returns `[]`.
