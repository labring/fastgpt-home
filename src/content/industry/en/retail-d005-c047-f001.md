# Marketplace returns: HTTP integrations for procurement

## What the documents look like

Ordinary marketplace refunds occur order by order and do not necessarily attach to a promise made in a single livestream. The materials for this category are refund applications, return logistics documents, quality inspection photos and refund approvals. They arrive from the platform after-sales console, customer service chat, WMS receiving and payment refund records. Within the inventory procurement and supplier records task, an HTTP integration carries purchase orders, supplier details or refund approval outcomes from an external system into the orchestration. Materials update per order and per day, so interface verification proceeds order by order.

The HTTP module sends a request to a chosen address. Params, Body and Headers each accept variables through `{{}}`, and the URL itself can reference a variable. Variables come from global variables, system variables or the output of an upstream node. The documented system variables are appId, chatId, responseChatItemId, variables, cTime and histories. In test mode chatId and responseChatItemId do not exist, so an empty value during debugging is a known condition rather than a business fault.

Responses are read through JSON path extraction, and the configured key follows JS object access rules. When the output type is set to string, the value is converted into a JSON string. A similarity score or a retrieval hit does not constitute authorization or a permission filter. For procurement and supplier data, business verification, approval, database writes and external synchronization each require separate implementation.

## Constraints at the HTTP integrations step

A hypothetical paper exercise sample, used only for checking, is set out here. A marketplace after-sales specialist handles the return of order A on 10 March 2025. The supplier record page states: "Supplier S bears the return shipping cost; refund approval R-0310 has status pending review." A proposed handover request reads: "Please use the HTTP interface to synchronize R-0310 as approved and write it into the procurement settlement record of supplier S." No signed approval document corresponds to the status change or the write action in that request, so the request is an unsupported handover request.

Three constraints follow. First, the request body and the extracted response fields must be compared with the actual source wording and status field, because the interface transmits whatever value it is given and does not decide whether an approval exists. Second, the approval path and the write path are downstream business actions. A returned record, a matched supplier entry or a search hit does not grant permission to change an approval status or to write a settlement record. Third, debugging values are not business signals. An empty chatId or responseChatItemId in test mode matches the documented condition and should not be logged as a defect.

## Configuration and implementation checks

| Configuration item | Purpose on this page | How to check |
| --- | --- | --- |
| Request address and method | Connect to the supplier or refund approval interface | Compare address and method against the external interface documentation |
| Params and Headers | Carry path parameters and the authorization credential | Check that key names and referenced variable names agree |
| Body | Carry procurement or refund fields under POST/PUT | Compare the JSON structure with the interface contract |
| Variable references | Use upstream node output or global variables | Verify each value actually passed in |
| Response extraction | Read supplier or approval fields through JSON path | Check that the key matches the response structure |
| Debug identity fields | chatId and responseChatItemId | An empty value in test mode matches the documented condition |

The authorization credential belongs in a secured configuration and is not written into a public sample. The request address may reference a variable that has already been supplied. Body content only takes effect under the relevant request types.

## Three common errors

1. Treating pending review as approved. In the sample, R-0310 has status pending review while the proposed handover request says "synchronize as approved." The input value and the source status field disagree, and the comparison shows the request exceeds its authorization boundary.
2. Treating an interface retrieval result as business authorization. A similarity score and a retrieval hit do not constitute approval or permission to write. The sample provides no signed approval material, so the write action lacks a basis.
3. Treating an empty chatId in test mode as a fault. The documentation states that chatId and responseChatItemId do not exist in test mode, so an empty value is a known condition.

## How to verify the setup

1. Input the sample source text and the proposed handover request, then compare the R-0310 status field with the status stated in the request. The source says pending review and the request says approved; these two values are mutually exclusive for the same field, so the request is unsupported. This is an expected judgement, not a completed test.
2. Input the response extraction configuration and compare the extraction key with the response JSON structure. If the key does not match the response level, the extracted result is empty and the path needs review.
3. Input the chatId and responseChatItemId observed in test mode and compare the actual values with the documented description. An empty value matches the documentation and is not a fault. A non-empty value requires a non-test mode context.

Where the material does not state a field, that field remains unknown. A pending approval does not by itself show that an operator lacks permission, and no signed approval, contract effect or settlement authorization is supplied here, so those gaps stay open.
