# Marketplace returns: scheduled workflows for procurement

## What the documents look like

Ordinary platform refunds and returns occur continuously per order and are not necessarily linked to a promise made in a single livestream session. For inventory procurement and supplier records, a scheduled workflow therefore faces refund requests, return shipping labels, quality inspection photos, and refund approvals that accumulate order by order. Sources are spread across the platform after-sales console, customer service chat, WMS receiving, and payment refund records.

Scheduled tasks must read these materials according to an external interface document. A trigger does not automatically establish a connection to a business system. Procurement and supplier records sit on the other side of the process: a refund responsibility decision may affect replenishment or a claim against a supplier, but that linkage requires explicit design in an interface or a downstream process.

## Constraints at the scheduled workflows step

A scheduled trigger does not create authorization. A refund approval in pending review status does not demonstrate that operating permission is absent. A return shipping label marked as signed for does not mean a quality inspection conclusion exists.

The HTTP module sends a request using the configured method, headers, and body. Variables come from global variables, system variables, or upstream node output, and the URL can also reference variables through `{{}}`. Return values are extracted through JSON path, for example `data.user.name`. Trigger time, actual input, returned result, and business status must be checked separately. The existence of a task does not replace successful execution.

Hypothetical drill sample: a refund request record states "Order A-2201; the buyer applied for a return on March 4; return shipping label SF-7788 shows signed receipt on March 7; quality inspection photo Q-045 records outer packaging damage; refund approval R-0912 has status pending review." A proposed sentence reads "R-0912 has approved the refund, and the supplier can be notified to replenish." The object being judged in that proposed sentence is the approval status field, while the source only records pending review.

## Configuration and implementation checks

| Configuration item | Value or check on this page | Basis and boundary |
| --- | --- | --- |
| Trigger method | Check whether an application scheduling capability or an external scheduler triggers the run | Check the available entry point against the actual version |
| Request method | Check GET or POST against the external interface document | The method is specified by the interface document |
| Request headers | Set `Authorization` to Bearer `{{token}}` | The token comes from a global variable |
| Request body | Declare fields per the interface document; wrap strings in quotes | Reference variables with `{{key}}` |
| Return value extraction | Configure a key with JSON path, such as `data.user.name` | Output type can be set to string |
| Execution record | Check trigger time, input, return, and business status | A task existing does not equal successful execution |

This page assumes a trial starting point: set the return value key to `data.user.name`, because the sample response contains that field path, and compare it with the whole `data.user` value to confirm the extraction granularity.

## Three common errors

1. Treating pending review as approved. In the sample, R-0912 has status pending review, while the proposed sentence says "has approved the refund." The input is the approval status field; the comparison is between the source wording "pending review" and the draft wording "approved." Same subject, same field, mutually exclusive values, so the draft contradicts the source.
2. Treating signed receipt as completed inspection. The sample only records that SF-7788 was signed for on March 7 and does not record an inspection conclusion. A draft saying "inspection passed, refund allowed" is not supported by the source.
3. Treating a retrieval result as authorization. Retrieving a refund request does not mean refund execution permission has been granted. Authorization status must be checked separately.

## How to verify the setup

1. Input the sample source text and the proposed sentence "R-0912 has approved the refund," then compare the approval status field: the source says pending review, the draft says approved, and the two are mutually exclusive, so the draft is judged contradictory. If the source does not record a status, record the draft as unsupported.
2. Input the SF-7788 signed receipt record from the sample and compare whether a quality inspection conclusion field exists. The source does not record one, so the item is judged pending verification and is not written as a negative.
3. Input a paper empty result `[]` and check whether the downstream design distinguishes an empty result from "no refunds." Handling of an empty result must be explicitly designed downstream; no claim is made that a fictional rule retrieval necessarily returns empty.
