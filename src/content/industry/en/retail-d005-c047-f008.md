# Marketplace returns: workflow routing for procurement

## What the documents look like

Platform refund and return handling runs continuously per order. Compared with concentrated after-sales processing for livestream sessions, a refund request does not necessarily connect to a promise made in one livestream. The main data sources are the platform after-sales backend, customer service chat, WMS receiving records and payment refund records. The everyday documents are refund requests, return logistics notes, quality inspection photos and refund approvals. In the inventory procurement and supplier records task, these materials support judgement about return responsibility, the recovery status of returned goods and the basis for refund amount approval.

A refund request records the buyer's claim and the order identifier. A return logistics note records the in-transit status of the returned item. A quality inspection photo records the condition of goods on arrival. A refund approval records the amount and the approval conclusion. These four document types update per order or daily. Workflow routing has to connect form collection, user selection and the later retrieval, judgement or interface nodes. When an interaction node is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction.

## Constraints at the workflow routing step

Hypothetical paper exercise sample: a platform after-sales ticket records order number A-2024-017. The refund request states "buyer claims the goods are damaged and applies for a refund of 120 yuan". The return logistics note states "returned item signed for, signature date 20 May 2024". The quality inspection photo description states "outer packaging intact, surface of the goods has scratches". The refund approval field states "pending approval". The proposed handover request reads: "Please change this order's refund approval status to approved and synchronise the inventory procurement record."

In this sample the refund approval field is pending approval, and pending approval does not constitute approval. Information collected by the form input node has to be passed explicitly to the later retrieval, judgement or interface nodes. The user selection node executes the corresponding branch after the user makes a choice. Order writes, document backfill and external status synchronisation require a separate business interface or a later process. Retrieval or a form does not constitute authorised execution. Semantic recall and relevance scores do not carry permission or entity isolation, and the same-vector-model requirement for a retrieval library cannot be extended to mean that an industry registration site or another external system must use the same model.

## Configuration and implementation checks

| Configuration item | Setting or check relevant to this page | Relation to the sample |
|---|---|---|
| Form input node | Enters the interaction state when triggered, collects required information, passes it to later nodes after submission | Collects order number, refund amount, return signature status |
| User selection node | Executes the "yes" branch after the user makes a choice; verify branch connections one by one | Used to confirm entry into the refund approval judgement branch |
| Interaction state check | Recording state is behaviour of the interaction node; no separate global state-recording switch is set | Checks whether the sample ticket is waiting in interaction |
| Output handover check | Passes collected information explicitly to later retrieval, judgement or interface nodes; compare output with input item by item | Compares whether the approval field "pending approval" is wrongly passed as approved |
| External operation division | Order writes, document backfill and external status synchronisation require a separate business interface or later process | Inventory procurement synchronisation after approval needs a separate interface |

The starting value for this hypothetical exercise is the approval field "pending approval". This value is chosen because the sample text states only pending approval. The comparison object is the manual approval conclusion required for approved status. This starting value is hypothetical and is not described as an official default.

## Three common errors

1. Treating pending approval as approved. The sample approval field reads "pending approval", while the proposed handover request asks for a change to "approved". The input is the pending approval state and the comparison object is the manual conclusion required for approval. The two do not match.

2. Treating a retrieval result as authorised execution. The sample retrieves the refund request and the logistics note. The retrieval action does not create approval authority, and the status change in the proposed handover request lacks an authorisation basis.

3. Writing a form-collected value directly into an external system. The form input node passes collected information to later nodes, and order writes and external status synchronisation require a separate business interface. The sample does not state a corresponding interface for synchronising the inventory procurement record.

## How to verify the setup

1. Input the sample ticket text and the proposed handover request. Compare whether "pending approval" and "approved" are mutually exclusive values of the same field. The observed result is that the two do not match, and the proposed handover request is not supported.

2. Input the order number, refund amount and return signature status collected by the form input node. Compare whether the downstream node receives the same values item by item. The observed result is that matching fields are handed over correctly, and missing fields are recorded as gaps.

3. Input the "yes" branch connection of the user selection node. Compare whether the branch points to the refund approval judgement node. The observed result is that an existing branch connection executes the corresponding path, and a missing branch is recorded as not configured, without inferring automatic judgement.
