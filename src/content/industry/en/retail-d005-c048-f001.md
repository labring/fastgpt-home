# Parcel labels and handoffs: HTTP integrations for procurement

## What the documents look like

Parcel handoff occurs at the point where a package leaves the warehouse, and carrier scan records determine where responsibility sits. For inventory procurement and supplier records, this means the interface chain has to connect external courier systems with warehouse dispatch data in a way that can be reconciled. The daily documents are electronic waybills, handoff lists, pickup scan records, and exception item logs. The brief gives update frequency as per batch and daily.

The relevant question at the HTTP integration step is whether a request passes the correct waybill number, handoff batch, and supplier identifier to the external system, and whether the returned values are parsed back into the local system correctly. A handoff list that reads "awaiting pickup" is not a scan confirmation. An exception log entry for a blurred label is not a completed reprint. These are distinct states, and the interface layer does not merge them.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a configured address. Params carry path parameters, used mostly with GET requests. Body carries the request payload, used mostly with POST and PUT requests. Headers carry authentication and similar information. URL, Params, Headers, and Body can all reference variables through `{{}}`. Variables come from global variables, system variables, or upstream node outputs.

Return values are not the interface response itself. They are a configured key that extracts a value from the response using JSON path syntax. When the output type is set to string, the value at that key is converted to a JSON string. The documentation's extraction example shows keys such as `data.user.name` and `data.list[1]`.

Two identity fields behave differently in test mode. `chatId` and `responseChatItemId` do not exist in test mode. Their absence during debugging is a documented condition, not a business fault. The chat interface uses APIKey authentication, and the recommended practice is to pass `body.appId` in the request body. Fields such as `model` and `temperature` are determined by the orchestration and are not changed by API parameters.

A hypothetical paper exercise sample

Material text for comparison: A warehouse dispatch group generated a handoff list on 10 March 2025, batch number JC-20250310-01, containing 40 electronic waybills, corresponding to supplier number GYS-017, with the handoff status field filled as "awaiting pickup." The same batch's exception item log records one item with a blurred waybill print, handling status "awaiting reprint."

Draft sentence to be assessed: "This batch has completed pickup handoff, and all 40 parcels for supplier GYS-017 have been scan-confirmed by the carrier."

## Configuration and implementation checks

| Configuration item | Setting for this page | How to check |
| --- | --- | --- |
| Request address and method | Select according to the external courier system interface document; the address can reference variables | Compare against the interface document to confirm the path and HTTP method match |
| Params and Headers | Fill path parameters and request headers separately; inject credentials through secure configuration | Check the actual passed values and confirm credentials do not appear in public samples |
| Body | Used only under the corresponding request type; check the JSON structure against the external interface contract | Check field by field against the contract and confirm every `{{}}` reference has a defined variable |
| Variable references | May reference global variables, system variables, or upstream node outputs | Check each item against its source and confirm the name matches the upstream node output |
| Return value extraction | Configure a key and extract by JSON path; choose output type as needed | Compare the extracted result against the interface response sample and the expected field |
| Debug identity fields | `chatId` and `responseChatItemId` do not exist in test mode | Record an empty value in test mode as a known condition, not a fault |

Hypothetical starting point for this exercise: set the return value key to `data.list[0].status` with output type string. This path is chosen because the interface response sample shows `data.list` as an array, and the first element's status field is needed. Compare against the documented extraction example `$.data.list[0]` to confirm the syntax is consistent. This is a starting value for the exercise, not an official default.

## Three common errors

1. Treating an "awaiting pickup" handoff list as a completed pickup. The input is the handoff list status field and the exception item log. The comparison object is the completion wording in the draft sentence. The observable result is that the status field text and the draft sentence do not agree: the material says "awaiting pickup" and one item "awaiting reprint," while the draft says handoff is complete and all parcels are scan-confirmed.

2. Treating an empty `chatId` in test mode as an interface fault. The input is a test-mode request. The comparison object is the documented statement that this field does not exist in test mode. The observable result is that the empty field is a known condition, and it does not by itself indicate an external system problem.

3. Writing the return value extraction key as the raw interface field name. The input is the configured key. The comparison object is the documented statement that values are obtained from the FastGPT converted format. The observable result is that the key needs to follow the converted structure; writing the raw nested path directly may fail to retrieve a value.

## How to verify the setup

1. Use the hypothetical sample handoff list text to check the draft sentence. Input: batch JC-20250310-01 handoff list status "awaiting pickup" and one exception item "awaiting reprint." Compare: the draft sentence "has completed pickup handoff" and "all scan-confirmed by the carrier." Condition met: the draft sentence agrees with the material status, or it is explicitly marked as pending verification. Condition not met: the draft asserts completion while the material shows a pending state.

2. Use the hypothetical sample to check the HTTP request's variable references. Input: the waybill number, batch number, and supplier number variables referenced in the request. Compare: whether a variable with the same name is defined in global variables, system variables, or upstream node outputs. Condition met: every `{{}}` reference has a corresponding defined variable, and the actual passed value agrees with the handoff list. Condition not met: a reference has no defined variable, or the passed value differs from the handoff list.

3. Use the interface response sample to check return value extraction. Input: key configured as `data.list[0].status`, output type string. Compare: whether `data.list[0]` in the interface response contains a `status` field. Condition met: the extracted result agrees with that field's value in the response. Condition not met: the field does not exist; record this as an extraction failure and retain the raw response for review.

These checks describe what to compare and what would count as agreement. They do not claim that any test, deployment, or approval has occurred. Where the material does not state a field, the value remains unknown rather than assumed.
