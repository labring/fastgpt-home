# Parcel labels and handoffs: vector indexes for procurement

## What the documents look like

Parcel handoff occurs at the point where a package leaves the warehouse, and the carrier scan is the responsibility marker at that node. The materials handled on this page are electronic waybills, handoff manifests, pickup scan records and exception item registrations, under the main task of inventory procurement and supplier records. These materials carry precise fields such as waybill numbers, carrier names, handoff batches and scan times, alongside natural-language passages describing exception items. Full-text retrieval suits exact queries for waybill numbers, batch numbers and carrier names, while semantic retrieval suits similar expressions in exception descriptions and responsibility attribution. Candidates from both recall paths are fused through RRF and then reordered by ReRank. Data updates per batch and per day; this page does not derive batch synchronization or real-time mechanisms from that frequency.

## Constraints at the vector indexes step

Knowledge bases associated for retrieval must use the same vector model, so the actual model and input type are checked first. One source data block can be linked to multiple indexes, and the index and the source text content are checked separately. The MongoDB table dataset.datas records vector IDs in an indexes field as an array, while the PostgresSQL vector field stores vectors. During retrieval, vectors are recalled first, then the source data is looked up by vector ID; when entries correspond to the same source data group, they are merged and the highest vector score is taken. Index content is built from complete and focused information, and retrieval coverage against index length is weighed with samples. Image retrieval also depends on whether image descriptions or image vectors were generated at ingestion time, and cannot be judged from the query side alone. Minimum relevance is a filter threshold that takes effect only in semantic retrieval or with result reordering, and it does not perform permission or entity isolation. The reference cap controls the maximum tokens referenced per search and is not the same control method as top k.

### Hypothetical paper exercise sample

The following is a paper-based fictional sample and does not involve real customers, real companies or legitimate identity numbers. Source text one: an electronic waybill record states "waybill number SF-TEST-0001, carrier A, handoff batch B-2024-05-10, pickup scan time 2024-05-10 18:20, status scanned." Source text two: an exception item registration states "waybill number SF-TEST-0001, registration date 2024-05-11, exception type outer packaging damage, handling status pending carrier confirmation." Draft sentence to be assessed: "This waybill has completed pickup handoff, and the exception item has been fully handled." The assessment task is to compare the draft sentence against the two source texts, where the subject is the same waybill number SF-TEST-0001, the period is 2024-05-10 to 2024-05-11, and the fields are pickup status and exception handling status. The pickup status field holds the value "scanned," while the draft sentence says "completed pickup handoff." The exception handling status field holds the value "pending carrier confirmation," while the draft sentence says "fully handled." The same field carries mutually exclusive values, and the draft sentence is not supported by the materials.

## Configuration and implementation checks

The table below lists configuration check items for this hypothetical exercise. The values are starting points for this paper exercise only and are not official defaults.

| Configuration item | Hypothetical starting point for this exercise | Reason for the choice and comparison method |
| --- | --- | --- |
| Vector model | Same model identifier; only knowledge bases with the same vector model are associated | Check the model identifier and input type first, exclude bases whose identifiers do not match, and do not run cross-model retrieval comparisons |
| Index content | Separate indexes for waybill number, carrier, batch, scan time and exception type | Check against the exception description passage index separately and compare whether recall candidates cover the required fields |
| Search mode | Hybrid retrieval, with waybill-number queries also going through full-text recall | Compare candidate scope against semantic retrieval alone and observe whether the waybill number is hit by the full-text path |
| Minimum relevance | Starting point 0.3 for this exercise, effective only in semantic retrieval or reordering | Compare candidate counts against running without a threshold and observe whether low-relevance fragments are filtered |
| Reference cap | Starting point 800 tokens for this exercise | Compare against the average candidate chunk length and observe whether reference content is truncated |
| Result reordering | Enabled after a ReRank model is configured | Compare ordering against no reordering and observe the distribution of the 0-1 reordering score |

## Three common errors

1. Treating minimum relevance as a permission or entity isolation measure. The input is one semantic retrieval query, the comparison object is the candidate set before and after filtering, and the observable result is that low-relevance fragments are filtered while unrelated business or unauthorized records are not excluded on that basis. Retrieval itself does not complete authorization.
2. Associating knowledge bases that use different vector models. The input is two knowledge bases with different model identifiers, the comparison object is the model identifier field, and the observable result is that identifiers that do not match should not be associated together. Runtime behavior after cross-model association has no documented basis and remains unknown.
3. Writing a pending status as completed. The input is the exception registration source text "handling status pending carrier confirmation," the comparison object is the draft sentence "fully handled," and the observable result is mutually exclusive values in the same field. The draft sentence is not supported, and the pending verification status is retained.

## How to verify the setup

1. Against hypothetical sample source text one, enter the query "waybill number SF-TEST-0001 pickup scan time," compare whether the returned reference contains "2024-05-10 18:20" and "scanned," and observe whether the reference content matches the source text. If the returned content lacks that field, record it as a miss and retain the gap.
2. Against the hypothetical draft sentence, enter the draft sentence and the two source texts, compare the two fields of pickup status and exception handling status, and observe that pickup status can correspond to "scanned" while exception handling status shows mutually exclusive values, so the draft sentence is judged unsupported.
3. For empty-result continuation, enter the explicit paper input [] and compare whether the downstream design handles an array length of 0, observing that the output path runs through and generates no reference content. Do not claim that a fictional rule retrieval necessarily returns []. After model or index adjustments, compare reference source text with the same question set and do not promise outcomes from vector scores alone.
