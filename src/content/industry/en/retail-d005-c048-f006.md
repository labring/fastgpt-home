# Parcel labels and handoffs: scheduled workflows for procurement

## What the documents look like

Parcel handoff happens at the point where a parcel leaves the warehouse, and scanning responsibility sits with the carrier. That single fact shapes which records this page compares: electronic waybills, handoff manifests, pickup scan records, and exception parcel registrations. Shipment data arrives from the carrier system and from WMS dispatch, while carrier billing records serve later reconciliation. The four document types carry different fields, so a procurement and supplier record cannot be assembled by treating them as one uniform source.

For the inventory procurement and supplier records task, scheduled workflows consume waybill fields, handoff batch identifiers, and supplier fields from those documents, and produce records that can be checked against procurement and supplier files. Because the business consequences concentrate on false shipment declarations, lost-parcel disputes, and platform dispatch timeout, the status recorded in a field has to match the handoff stage it describes. A manifest that records a pickup status and a waybill register that records a print time are not the same evidence, even when both refer to the same batch.

## Constraints at the scheduled workflows step

Scheduled automation in FastGPT connects to external services through the HTTP module. The trigger responsibility has to be stated: whether the application scheduling capability or an external scheduler initiates the run, checked against the actual version in use. External data is read through a configured interface. A scheduled trigger does not by itself establish a connection to a business system, and no such connection should be assumed. Request method, headers, body, and variable inputs follow the external interface documentation. The URL and the body can reference variables through `{{}}`, drawing on global variables, system variables, or output from preceding nodes.

System variables available for reference include appId, chatId, responseChatItemId, variables, cTime, and histories. The histories variable takes at most 10 records by default and its length cannot be changed. Return values are extracted with JSON path syntax, and when the output type is set to string, the value at the configured key is converted into a json string. Deduplication, idempotency, and business writes need explicit design in the interface or in a later flow; they are not automatically present. Execution records are checked against trigger time, actual input, returned result, and business status. The existence of a task does not stand in for successful execution.

## Configuration and implementation checks

The table below covers documented settings and implementation checks tied to this page's documents and to the inventory procurement and supplier records task.

| Configuration item | Setting or check | Basis and note |
| --- | --- | --- |
| Trigger entry | Check whether the application scheduling capability or an external scheduler is the actual entry | Verify against the version in use; do not assume a connection is created |
| Request method | Check GET or POST against the external interface documentation | Method is determined by that documentation |
| URL variable | Reference a global variable or a preceding node output through `{{}}` | The URL can carry variable references |
| Body variable | Quote strings; leave number and boolean unquoted | Reference rules follow JS object value rules |

Hypothetical paper exercise: a warehouse dispatch group submits a handoff manifest dated 10 June 2025, with the text "Batch JL-20250610-03, carrier scan time 10 June 2025 at 18:00, waybill numbers SF-0001 through SF-0050, status picked up." The electronic waybill register for the same batch shows "waybill numbers SF-0001 through SF-0050, print time 10 June 2025 at 17:00." The draft sentence to be assessed is: "All waybills in this batch have completed pickup scanning and been synchronized to supplier records." This is a paper exercise and does not involve a real customer or a legal identity number.

## Three common errors

1. Treating a scheduled trigger as an established business system connection. Input the trigger configuration and the interface configuration, compare whether a configured external interface exists, and observe that when only a trigger entry is present without interface configuration, the connection state is unsupported.

2. Treating a retrieval result or a form submission as authorized execution. Input the draft sentence and the handoff manifest text, compare the claimed "all waybills completed pickup scanning" against the recorded scan time and status field, and observe that when the source records a picked-up status without item-by-item scan detail for every waybill, the claim remains unverified. A pending request is not an approval, and an offered option is not execution.

3. Treating task existence as successful execution. Input the execution record and the business status, compare trigger time, actual input, and returned result for consistency, and observe that when the returned result is absent from the record, execution success is unsupported.

## How to verify the setup

- Verification one: input the handoff manifest text and the draft sentence from the hypothetical sample, compare the draft claim "all waybills completed pickup scanning" against the source wording "waybill numbers SF-0001 through SF-0050, status picked up," and observe that when the source does not state item-by-item scan detail, the claim is unsupported. The expected outcome is a recorded evidence gap, not a determination of denial or conflict.

- Verification two: input the electronic waybill register text and the handoff manifest text, compare the waybill number range with the print time and the scan time, and observe that when the two waybill ranges match and the time order is coherent, no contradiction appears at the field level. The expected outcome is a comparison across the same subject, same period, and same field.

- Verification three: input the HTTP module return value extraction configuration and the interface response example, compare the extracted result for `data.user.name` against the `name` field in the response, and observe that when the output type is string, the corresponding json string is produced. The expected outcome follows JSON path syntax; no actual test is claimed.

Retrieval check: input an explicit paper input of `[]` to check the downstream design, observe how an empty result is carried forward, and do not claim that a fictional rule retrieval necessarily returns `[]`. Semantic recall and relevance scores do not handle permission or entity isolation. The same vector model requirement for a retrieval library does not extend to external systems. Libraries built on different vector models cannot be associated together; check the identifier first, exclude non-matching libraries, and record the actual observation. A relevance score is not a category, entity, or permission filter, and retrieval is not authorization.
