# Complaints and official replies: HTTP integrations for procurement

## What the documents look like

Complaint and regulatory reply work faces platforms or supervisory authorities and depends on formal evidence and remediation wording. Materials arrive from the 12315 platform, platform complaint centers, customer service chats, and order systems. The daily documents are complaint tickets, regulatory inquiry letters, order evidence, and remediation reports. This page covers the procurement and supplier records inside that work, handled through HTTP requests to external systems for record retrieval, evidence cross-checking, and reply drafting.

Data updates irregularly, once per case, so each request is triggered by an individual case rather than a batch or scheduled sync. Errors in these records can lead to administrative investigation, platform penalties, and brand exposure. Supplier names, purchase batches, stock quantities, and order numbers returned by an interface must correspond item by item with the ticket and the inquiry letter.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a specified address. Params carry path request parameters and are used mostly with GET requests. Body carries the request body and is used mostly with POST and PUT requests. Headers carry special information. All three can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories, where histories takes at most 10 entries by default and its length cannot be changed. chatId and responseChatItemId do not exist in test mode, so empty values during debugging are a known condition and not a business fault.

Return values are extracted through JSON path, and the key follows JS object access rules. When the output type is set to string, the value at that key is converted into a JSON string. The interface itself only sends the request and extracts values. Supplier qualification verification, procurement authorization confirmation, stock data writes, and external system synchronization each need their own downstream implementation. Retrieval and interface calls do not constitute authorization.

Hypothetical drill sample: a shop receives a platform-forwarded complaint ticket. The ticket text reads: "The complainant states that the goods in order A-2024-0517 do not match the page description and requests the purchase records and supplier qualification for that batch." The regulatory inquiry letter reads: "Within five working days of receiving this letter, provide the purchase contract, the supplier business license, and copies of the purchase invoice for that batch of goods." The proposed handoff request reads: "Call the supplier records interface, pass supplier number S-018, retrieve the business license and contract scans, and attach them directly to the remediation reply." Decision points: the ticket and the inquiry letter both point to order A-2024-0517, and whether supplier number S-018 matches the purchase record for that order has not yet been checked. The scans returned by the interface are a retrieval result. Before they are attached to the remediation reply, a person must compare the order, the batch, and the supplier for consistency. Submitting the reply is a business action that the interface does not perform.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point for this page | Reason and comparison method |
| --- | --- | --- |
| Request address | Points to the supplier records query service address, containing the `{{baseUrl}}` variable | The address comes from the external interface documentation and is fixed after comparison with the fields the ticket requires |
| Request method | POST | The query carries an order number and a supplier number, compared with GET, which only carries path parameters |
| Headers | Authorization takes Bearer `{{token}}`, with the token injected by security configuration | The credential is not written into public samples; compared with the interface documentation requirement |
| Body fields | Order number, supplier number, and document type | Compared with order A-2024-0517, S-018, and the required documents in the ticket text |
| Return value extraction | Three keys: business license, contract, invoice | Compared item by item with the three material types listed in the inquiry letter |
| Output type | String | Convenient for later text processing and concatenation; compared with the interface response structure |

## Three common errors

1. Treating the supplier number returned by the interface as confirmation that it matches the order. The input is supplier number S-018 returned by the interface. The comparison object is the supplier number registered in the purchase record for order A-2024-0517. The condition is met only when the two agree. In this sample the purchase record is not provided, so the match remains unsupported and the evidence gap must be recorded.

2. Treating an empty chatId in test mode as an interface failure. The input is a test-mode call. The comparison object is the documented statement that chatId does not exist in test mode. An empty chatId is a known condition, so the call must be retried in a formal environment with a real chatId before any judgment is made.

3. Attaching scans returned by the interface directly to the remediation reply. The input is the business license and contract returned by the interface. The comparison object is the material scope required by the inquiry letter and the result of manual verification. Only when the materials are complete and consistent with the order batch can reply drafting begin. The submission action requires separate confirmation of authorization status.

## How to verify the setup

1. Using the ticket text and inquiry letter from the hypothetical sample as input, call the interface with order A-2024-0517 and S-018, then compare whether the three returned keys for business license, contract, and invoice correspond to the three material types listed in the inquiry letter. The condition is met when all three can be extracted and their contents point to the same supplier. If any one is missing, record the gap.

2. Using the proposed handoff request as input, compare the supplier number returned by the interface with the number registered in the order purchase record. The condition is met when the two agree. When the purchase record is not provided, the match remains unsupported and is not judged as a contradiction.

3. Using a test-mode call as input, compare the values of chatId and responseChatItemId. When both are empty, classify this as the documented test-mode condition, then retry in a formal environment with a real chatId. The condition is met when return values can be extracted normally.
