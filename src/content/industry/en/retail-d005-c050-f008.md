# Complaints and official replies: workflow routing for procurement

## What the documents look like

Complaints and official replies are directed at platforms or regulatory authorities, so the material set needs formal evidence and corrective-response wording. In the procurement and supplier-data context, the recurring documents are purchase orders, supplier correspondence records, inbound and outbound warehouse vouchers, quality or compliance files, and the evidence bundle assembled around one transaction. Data sources include the 12315 platform, platform complaint centers, customer-service chat, and the order system. Material is updated irregularly and formed case by case, so the same supplier can carry an inconsistent document status across different cases.

That irregular, per-case formation has a direct effect on workflow routing. The Form Input node is a user-interaction node: when it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the interaction the workflow continues downward. The User Selection node behaves the same way at trigger, and when the user makes a choice the node evaluates that choice and executes the corresponding branch. Procurement material usually needs its ownership, period, and field confirmed first, before a decision is made about routing into a corrective-response branch or an evidence-supplement branch. A retrieval library carries semantic recall only. It does not carry permission or entity isolation, and it does not perform authorization judgments.

## Constraints at the workflow routing step

Routing has to separate four kinds of action: behavior a node already has, fields that are actually configurable, manual verification actions, and business actions that require a separate system implementation. Form Input and User Selection are user-interaction nodes. After triggering, the conversation enters an interaction state and the workflow state is recorded; after the user completes the interaction, execution continues downward. That interaction-state record is node behavior. No separate global state-recording switch is documented, and none should be assumed. Dialog hiding and submission counts follow the documented description; no corresponding control item should be invented.

Neither retrieval results nor values collected by a form constitute authorization. Order writes, document backfill, and external status synchronization require a separate business interface or a downstream process. Libraries built on different vector models cannot be associated together; the identifier must be checked first, non-matching items excluded, and the actual observation recorded. The optional paths shown in a general workflow diagram do not mean every request executes all of them. Image retrieval requires a corresponding image input and model capability, and reranking requires the model to be present and enabled according to its setting.

## Configuration and implementation checks

Hypothetical drill sample: a shop customer-service supervisor receives, on 10 March 2025, a regulatory inquiry letter. The letter names the object as "Supplier A," the period as 1 February 2025 to 28 February 2025, and the field as "procurement inbound quantity." Two sentences of existing source material read: "On 10 February 2025, Supplier A purchase order number PO-2025-0210; the inbound voucher shows a quantity of 120 units." "On 18 February 2025, Supplier A return order number RT-2025-0218; return quantity 20 units." One draft sentence awaiting determination reads: "Supplier A's procurement inbound quantity for February 2025 was 120 units." That draft sentence does not deduct the return, and it does not state whether the 120 units and the 20 units share the same field definition.

## Three common errors

1. Treating retrieval recall as authorization. Entering "Supplier A" and retrieving material shows semantic relevance only; it does not show that the material is authorized for use in a corrective response. The input to check is the retrieval term and the library identifier; compare the retrieval result against the authorized scope; observe whether use exceeds authority.

2. Treating a pending draft as approved. The draft sentence "Supplier A's procurement inbound quantity for February 2025 was 120 units" is in a pending state and is not supported. The input to check is the draft sentence and the source text; compare values for the same subject, same period, and same field; observe whether the 120 units and the 20-unit return form mutually exclusive values in one field.

3. Treating form submission as business completion. The Form Input node collects information and passes it to downstream nodes; it does not perform order writes or external synchronization. The input to check is the submitted value; compare whether downstream nodes connect to a separate interface; observe whether an undeclared automatic business action appears.

## How to verify the setup

- Verification one: input the two hypothetical source sentences and the draft sentence; compare the "procurement inbound quantity" value for the same period and same subject; observe whether the draft sentence deducts the return and states the field definition. The expectation is that the evidence gap is preserved and the 120 units are not determined to hold.

- Verification two: input the "supplement evidence" branch of the User Selection node; compare the selection outcome against the branch connection; observe whether the corresponding branch executes. The expectation is that the branch executes according to the selection, with no claim that this was actually tested.

- Verification three: input a paper empty result of []; compare whether the downstream node treats it as empty input; observe whether an assertion appears that a fabricated rule returns []. The expectation is that the gap is recorded, with no guarantee of a first hit or full recall.

All checks above stay within the hypothetical drill sample. No actual test, deployment, approval, or external synchronization is claimed.
