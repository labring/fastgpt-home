# Pinduoduo seller campaigns: workflow routing for procurement

## What the documents look like

Pinduoduo low-price campaign operations revolve around campaign resource slots, campaign inventory, and refund-rate swings. The working data comes from the merchant backend, campaign resource-slot data, ERP inventory, and logistics signed-receipt data. For the procurement and supplier-file task, four documents carry the values that matter. The campaign registration form states the campaign price and the registered quantity. The product cost worksheet states the procurement cost and the gross margin. The after-sales refund slip states the refund reason and quantity. The platform in-site message states the campaign rules and penalty notices. These documents update daily or once per campaign, but that cadence does not by itself create any synchronization, batch, or trigger behaviour on this page.

In workflow routing, these four documents decide what the Form Input node collects and what the User Selection node branches on. The Form Input node is a user-interaction node: when it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the required fields and submits, the node collects the submitted form values and passes them to later nodes. The User Selection node is also a user-interaction node: it triggers the same interaction state, and when the user makes a choice, the node evaluates that choice and executes the "yes" branch. Both nodes can be added repeatedly and trigger execution. The interaction state is node behaviour; this page does not assume a separate global state-recording switch.

## Constraints at the workflow routing step

A form collects values. Business verification, approval, database writes, and external synchronization require a separate business interface or a later flow. Retrieval is not authorization, and a relevance score is not a category, entity, or permission filter. The same-vector-model requirement applies to a given knowledge base itself and does not extend to external systems.

Hypothetical paper exercise. A campaign operator submits a handover request. The material text reads: "Campaign registration form: campaign price 9.9 yuan, registered quantity 500 units, campaign dates 1 June 2025 to 3 June 2025. Product cost worksheet: procurement cost 7.5 yuan per unit, gross margin 2.4 yuan per unit. After-sales refund slip: 3 units refunded on 20 May, reason size mismatch." The sentence to be judged is: "This supplier file has passed approval and can be used directly for procurement ordering in this workflow routing." The authorization boundary is: the campaign operator may submit materials; procurement ordering requires supply-chain procurement confirmation; there is currently no approval signature record.

## Configuration and implementation checks

| Configuration item | Setting or check on this page | Note |
| --- | --- | --- |
| Form Input node | Triggers the interaction state, collects required fields | Used to collect campaign registration form fields |
| User Selection node | Executes the "yes" branch after the user chooses | Used to confirm whether the supplier file is complete |
| Interaction state check | Recorded state is node behaviour | No separate global state switch is assumed |
| Output hand-off check | Collected values pass to later retrieval, judgement, or interface nodes | Compare each output against its input |
| External action split | Order writes, document backfill, external sync attach to interfaces | Forms do not perform authorized execution |
| Hypothetical starting value | Registered quantity 500 units is this paper exercise's starting point | Compared against the ERP inventory value; not an official default |

## Three common errors

1. Treating a supplier-file value collected by the Form Input node as approval. Input: the sentence to be judged from the hypothetical exercise. Comparison: the approval signature record. Observable result: that record is absent, so the status is pending verification.
2. Treating execution of the User Selection node's "yes" branch as a completed procurement order. Input: the node selection action. Comparison: a procurement order interface call record. Observable result: no such record exists, so the action is not executed.
3. Treating a retrieval similarity score as a supplier authorization filter. Input: the relevance value returned by retrieval. Comparison: the supplier authorization field value. Observable result: the two have no correspondence, so no authorization is constituted.

## How to verify the setup

1. Take the material text from the hypothetical exercise, feed it into the Form Input node, and compare the collected campaign price, registered quantity, and procurement cost fields against the source values. Item-by-item agreement satisfies the collection condition; a missing field is recorded as a gap.
2. Take the sentence "This supplier file has passed approval," feed it into the User Selection node, and compare the branch taken against the approval signature record. With no signature record, the status is pending verification and the procurement order branch is not executed.
3. Take the refund date and quantity from the hypothetical exercise's after-sales refund slip, feed them into a later judgement node, and compare the refund quantity against the campaign registered quantity. With 3 units refunded against 500 units, the result is recorded as within normal range and the out-of-stock penalty branch is not triggered; if the refund quantity field is empty, it is recorded as unsupported.
