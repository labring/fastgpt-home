# Channel receivables: HTTP integrations for procurement

## What the documents look like

Channel receivables collection happens after credit sales, and the work centres on credit limits and cash recovery. The procurement and supplier records task places dealer purchase orders, supplier delivery records and the receivables ageing table into one comparison set. The main data sources are the finance system, bank receipts, dealer orders and sales contracts. Day-to-day documents include the receivables ageing table, dunning letters, credit agreements and shipment freeze notices. The update rhythm is weekly or monthly. That rhythm supports batch reconciliation rather than a requirement for real-time triggering, and the HTTP module is repeatable, manually configured and triggered to execute.

The HTTP module sends a request to the corresponding address, and operation is close to tools such as Postman and ApiFox. Params are path request parameters, common in GET requests. Body is the request body, common in POST and PUT requests. Headers carry special information. All three can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables and preceding node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime and histories. The histories variable takes at most 10 records by default and its length cannot be modified. chatId and responseChatItemId do not exist in test mode.

## Constraints at the HTTP integrations step

Procurement and supplier record reconciliation needs calls to external data sources to obtain supplier delivery records or purchase order status. Return values are extracted with JSON path syntax. When the output type is set to string, the value of the corresponding key is converted to a JSON string. The HTTP module can be added repeatedly, configured manually and triggered to execute, and it is a core module.

Hypothetical paper exercise: a brand finance staff member assembles a paper set reading "Supplier A and Dealer B signed a credit agreement in March 2025, agreeing a credit limit of 500,000 and a payment term of 60 days. As of 30 June 2025, the receivables ageing table for Dealer B shows an overdue amount of 120,000 with an ageing of 45 days." The proposed determination sentence is "This dealer has triggered the shipment freeze condition." The credit agreement does not state a freeze trigger clause, and the ageing table does not state a freeze status. This determination is unsupported.

Retrieval and similarity do not perform permission or entity isolation, and a similarity setting cannot be treated as a means of excluding unauthorised records. An empty result can be checked against a downstream design using the explicit paper input `[]`; it cannot be claimed that retrieval necessarily returns an empty array. The interactive node response returns only type and params; internal runtime fields such as entryNodeIds are not returned.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Comparison method |
| --- | --- | --- |
| Request address | The address given in the external supplier interface document | Compare address and method against the document |
| Params | Path parameters filled per the external interface contract | Check each actual passed value item by item |
| Headers | Authorization injected through secure configuration | Do not write credentials into public samples |
| Body | Used only under POST or PUT | Check JSON structure against the contract |
| Variable reference | Reference a preceding node output or a global variable | Check the actual value of `{{key}}` |
| Return value extraction | Configure the key and extract by JSON path | Check output type and parsed result |

The hypothetical starting point uses the credit limit of 500,000 and the payment term of 60 days because the sample material explicitly states both values. The comparison objects are the overdue amount of 120,000 and the ageing of 45 days shown in the ageing table. This starting point is a value given in the sample, not an official default.

## Three common errors

1. Treating an empty chatId or responseChatItemId in test mode as a business fault. Input is a request in test mode; the comparison object is the documented statement that these do not exist in test mode; the observable result is that the empty value is expected behaviour.
2. Confusing the configured return value key with an interface response field. Input is the configured key; the comparison object is the JSON path extraction rule; the observable result is that the extracted value matches the corresponding field in the response example.
3. Treating "triggered shipment freeze" in the proposed determination sentence as executed. Input is the hypothetical sample material; the comparison object is the original text of the credit agreement and the ageing table; the observable result is that neither document states a freeze clause or freeze status, so the determination does not hold.

## How to verify the setup

1. Input the credit agreement text and the ageing table text from the hypothetical sample. Compare the proposed determination sentence "This dealer has triggered the shipment freeze condition" against whether the original text states a freeze trigger clause and a freeze status. The observable result is that neither document states either item, and the determination is unsupported.
2. Input a pending handover request: "Please confirm whether Supplier A's delivery records have been synchronised to the procurement ledger." Compare the subject, object and material scope in the request. The observable result is that the material does not provide the synchronisation status of the delivery records, and the request remains pending verification.
3. Input the hypothetical sample values "credit limit 500,000, payment term 60 days" and "overdue amount 120,000, ageing 45 days". Compare whether values in the same field are mutually exclusive. The observable result is that the two sets belong to different fields and do not conflict; the overdue fact holds while the freeze fact is unsupported.
