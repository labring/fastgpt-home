# Channel diversion reviews: workflow routing for procurement

## What the documents look like

Channel diversion review concerns regional and price order. It works on the direction of goods flow and the sales territory recorded for a shipment. It does not handle rebate amounts. The materials in this category include diversion complaint forms, anti-counterfeit code records, penalty notices and investigation photographs. Their sources cover anti-counterfeit code systems, e-commerce platform prices, distributor shipment records and market inspections. Typical operating roles are brand channel control, anti-counterfeit teams and regional managers. Updates arrive weekly or irregularly. Errors in this work can disrupt price systems, create distributor disputes and generate brand complaints.

This page addresses one task inside that category: inventory procurement and supplier records. Procurement documents, supplier qualification records and authorization status all enter the same routing arrangement. The update rhythm of the underlying materials affects how fresh a record is. It does not change how a node behaves.

A complaint form can carry a shipment date, a quantity and a code range. A supplier qualification table can carry an authorization letter, an authorized region, a validity period and a status value. These are the fields that later routing steps need to move without alteration.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the dialogue waits. After the user completes the required fields and submits, the node collects the submitted form values and passes them to subsequent nodes. The User Selection node is also a user interaction node. It triggers the same interaction state and state recording. When the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch.

State recording belongs to the interaction nodes themselves. No separate global state-recording switch is documented, and none should be assumed. Collected values must be explicitly passed to later retrieval, judgment or interface nodes, and the output of each downstream node must be compared field by field against its input. Order writing, document backfill and external status synchronization require a separate business interface or a later process. The interaction nodes do not perform those actions.

Hypothetical drill sample for review, not a real record: the material text reads, "Complaint form A-0715 states: distributor Jia shipped 240 cases to the East China region on 3 June 2025, anti-counterfeit code range 8801 to 9040. Supplier qualification table B-22 states: Jia holds a brand authorization letter, the authorized region is South China, the validity period is 1 January 2025 to 31 December 2025, and the authorization status is signed." The draft sentence to be assessed reads, "Distributor Jia is authorized to ship in East China, procurement and supplier records are complete, and a penalty may be executed." This request treats retrieval and form results as authorization to execute.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this drill | Verification method and reason |
| --- | --- | --- |
| Form Input node | Required fields set to complaint number, distributor name, shipment date, anti-counterfeit code range | Triggering enters the interaction state and collects required information; after submission the values pass to later nodes |
| User Selection node | Options set to "supplement materials" and "refer to human review" | After the user chooses, the corresponding "yes" branch executes; verify each branch connection one by one |
| Output handoff | Pass form values to a later retrieval or judgment node | Compare output against input item by item and confirm field correspondence |
| Authorization status field | Record the value as written in the supplier qualification table | Record only the stated status such as signed; do not infer authorization scope |
| External action split | Penalty execution and order writing connect to a separate business interface | Nodes do not perform external synchronization; a downstream implementation is required |

The starting values above are set for this hypothetical drill to observe field flow. They are not compared against any official default value.

## Three common errors

1. Treating a form submission as an effective authorization. In the sample, Jia's authorized region is South China, while the shipment goes to East China, yet the draft sentence states authorization. Input: the sample text and the draft sentence. Comparison: the authorized region against the shipment region. Observable result: the two do not match, so the draft claim is unsupported.

2. Treating a User Selection branch as penalty execution. Selecting "refer to human review" produces only a branch direction. Executing a penalty requires a separate business interface. Input: the selection result. Comparison: the branch connection against the actual execution record. Observable result: no downstream call exists, so execution is not established.

3. Treating retrieval output as a permission filter. Retrieval does not perform entity isolation. Retrieving Jia's records in the sample does not mean Jia may be penalized. Input: the retrieval output. Comparison: the output subject against the authorization status. Observable result: the two are mixed together, and the record remains unverified.

## How to verify the setup

1. Input the sample text and the draft sentence. Compare the authorized region "South China" against the shipment region "East China". When the draft sentence claims authorization, the condition is not met and the claim should be marked unsupported.

2. Input the authorization status "signed" from the sample. Compare the signing fact against the penalty execution fact. Observe whether an execution record exists. When it is absent, record the evidence gap rather than treating the signature as execution.

3. Input an empty-result handoff scenario. Use the paper input `[]` to check the downstream design and observe whether the downstream handles an empty value. Do not assert that a fictional retrieval rule always returns `[]`.
