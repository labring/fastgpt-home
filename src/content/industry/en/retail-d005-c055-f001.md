# Franchise filing management: HTTP integrations for procurement

## What the documents look like

Franchise filing management handles legal disclosure and the commerce department system. It does not handle individual site engineering. Within that scope, procurement and supplier records sit inside the operating-resource evidence portion of filing materials and information-disclosure documents. The usual sources are business licences, store lists, contract ledgers and supplier contracts. The responsible party is the franchisor headquarters; the objects are purchase batches, supplier qualifications and supply status. The brief gives an update frequency of irregular or annual, and this page does not derive batch synchronization or real-time triggers from that frequency.

The HTTP module sends a request to a configured address. Params carry path parameters and appear mostly in GET requests. Body carries the request payload and appears mostly in POST and PUT requests. Headers carry special information. All three can reference variables through `{{}}`, and variables come from global variables, system variables and upstream node outputs. The URL can also reference variables. Returned values are not the interface response itself; they describe how to parse that response, using JSON path syntax. When the output type is set to string, the value at the matching key is converted into a JSON string. In the system variables, chatId and responseChatItemId do not exist in test mode, so an empty value during debugging is not a business fault. In the chat completion interface, fields such as model and temperature have no effect because the orchestration decides them. Plugin calls do not need chatId or messages; inputs arrive through variables and outputs are read from pluginOutput.

The chat interface accepts an appId in the request body, or an `Authorization: Bearer <apiKey>-<appId>` header for OpenAI SDK compatibility, with body.appId taking priority. Some SDKs need a `v1` path segment in BaseUrl and some do not; a 404 can be retried with `v1` added. The `detail` flag controls whether intermediate module state is returned, and in stream mode results arrive as events. These are interface facts, and none of them grants permission to read, approve or write any supplier record.

## Constraints at the HTTP integrations step

The HTTP module is repeatable, manually configured and triggered by execution. It sends a request to an address and parses the response. The step carries several boundaries that matter for procurement and supplier material.

Retrieval and similarity are not authorization. A returned value from an external supplier system or a commerce department system is data, not approval. A relevance score is not a category, entity or permission filter, and it does not exclude unrelated businesses or unauthorized records. Reading a supplier contract through an interface does not verify the supplier, approve a purchase batch or write to any database. Those actions need their stated downstream implementation, and this page does not assume scheduled triggers or hidden controls.

Forms collect values. When a workflow reaches an interactive node, the interface returns a display configuration containing type and params. Internal runtime fields such as entryNodeIds, memoryEdges, nodeOutputs and nodeResponseId are not returned. A pending request is not approval, an offered option is not execution, and an unsigned termination is not a completed termination. The interface can present a user-select option or an input form, and it can accept a follow-up message that continues the workflow. It does not by itself complete any business verification, approval, database write or external synchronization.

The following hypothetical paper case is used throughout this page. It is a clearly labelled exercise, not a record from any real system. A franchisor headquarters filing specialist is organizing procurement material in March 2025. The supplier contract ledger states: "Supplier A, supply category is store consumables, contract valid until 31 December 2025, current status is signed." A draft sentence reads: "Supplier A's supply term covers the current filing period." The question to decide is whether the draft sentence is supported. Contract validity and supply term are different fields. The draft sentence treats validity as equivalent to supply term and lacks independent evidence of the supply term. This decision is the primary task of this page: checking whether material fields and external interface return values agree.

## Three common errors

1. Treating the contract validity field as the supply term. The error is that the two fields differ. The input is the contract ledger text in the sample, the comparison object is the draft sentence, and the observable result is that the draft sentence lacks independent evidence of the supply term.

2. Treating an absent chatId in test mode as a business fault. The error is that the test-mode statement says the field does not exist there. The input is a test-mode request, the comparison object is the system variable description, and the observable result is that the empty field is expected.

3. Treating the extraction key as the interface return value itself. The error is that the return value describes how to parse the response. The input is the JSON path configuration, the comparison object is the interface response example, and the observable result is that the key extracts a value from the converted format.

## How to verify the setup

1. Check the draft sentence against the sample text. The input is the contract ledger text and the draft sentence. The comparison object is the two distinct fields, contract validity and supply term. The observable result is that the draft sentence is not supported by supply-term evidence and is recorded as pending verification. This is an expected outcome, not a completed test.

2. Check the chatId field with a test-mode request. The input is a request made in test mode. The comparison object is the system variable description stating that chatId does not exist in test mode. The observable result is that an empty value there is an expected phenomenon rather than a business fault, and it is recorded as expected.

3. Check return value extraction against the interface response example. The input is the response example in the document and the configured key. The comparison object is the JSON path extraction result. The observable result is that the extracted value matches the example and is recorded as passing. For an empty downstream result, a paper input of `[]` can be used to check the downstream design; this page does not claim that a fictional rule search returns `[]`.

Missing evidence remains missing. Where the document does not state an error code or an observation, describe what to compare and leave the result unknown.
