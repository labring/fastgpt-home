# Near-expiry markdowns: scheduled workflows for procurement

## What the documents look like

Near-expiry markdown handling follows the shelf-life lifecycle of stock rather than the piece-by-piece weighing and sorting that defines other fresh-goods work. The records that matter here come from POS stock age, store inspections, ERP inventory, and quality-check records. On a daily or per-shift basis, staff work with near-expiry lists, markdown approvals, damage write-off forms, and promotional price tags. Store managers, loss-control administrators, and finance auditors are the typical roles involved.

These traits shape how scheduled tasks are designed. Near-expiry status changes as calendar dates advance, so a batch that qualifies for markdown on one day may not qualify on another. Approval of a markdown and the write-off form have a state order between them: a write-off should not proceed on the strength of an approval that has not been recorded. The effective scope of a promotional price tag needs to correspond to the approval result. Because the consequences of error include sale of expired goods, expanded loss, and food-safety complaints, any automation step must retain a manual verification point.

## Constraints at the scheduled workflows step

A scheduled task only triggers on time. It does not by itself establish a business connection to ERP, POS, or quality-check systems. External data must be read through a configured HTTP request, with method, headers, and body checked against the external interface documentation. Deduplication, idempotency, and business writes require explicit design in the interface or a later flow; they cannot be assumed to exist automatically. Execution records should be checked against trigger time, actual input, returned result, and business state. The presence of a task does not mean the task succeeded. A retrieval result or a collected form value does not constitute authorization, and markdown approval, damage write-off, and price-tag activation are three separate facts.

Hypothetical paper exercise: at a store during the shift of March 10, 2025, a fresh-goods store manager submits a near-expiry list. The source text reads: "Inspection on March 10 found 12 units of Batch A leafy greens remaining, shelf life to March 12, requesting a 30 percent markdown, pending loss-control administrator approval." On the same day a draft sentence reads: "Batch A leafy greens have completed markdown approval, and the promotional price tag is now in effect." The pending request is: "Please have the scheduled task automatically update Batch A status to marked-down at 08:00 on March 11." The source approval field only says "pending approval," and neither the draft sentence nor the request carries evidence of completed approval.

## Configuration and implementation checks

| Configuration item | Relevant setting or check on this page | How to verify |
| --- | --- | --- |
| Trigger entry | Confirm whether the application scheduling capability or an external scheduler triggers the task, and check the available entry against the actual version | Inspect the trigger-source identifier and trigger-time record |
| Data reading | External data is read through a configured HTTP request; method, Headers, and Body follow the interface documentation | Compare the request method against the interface documentation |
| Variable reference | URL, Params, Headers, and Body may reference global variables, system variables, or prior-node output through `{{}}` | Check that variable names match the referenced source |
| Return-value extraction | Configure a key using JSON path syntax to extract the interface response value; output type may be string | Use a sample response to check the extraction path |
| Execution record | Check trigger time, actual input, returned result, and business state | Compare the list source text against the returned content |
| Authorization boundary | Check approval, write-off, and price-tag activation separately; a form submission is not treated as completed authorization | Inspect the value of the approval-state field |

The trigger entry, data reading, and return-value extraction rows are documented settings. The execution-record and authorization-boundary rows are implementation checks rather than documented switches. No numeric default, limit, or unit is supplied by the documents, so none is asserted here.

## Three common errors

1. Treating a scheduled trigger as an established ERP or POS connection. The input is the scheduled-task configuration; the comparison object is whether a configured HTTP request and interface documentation exist; the observable result is that with no request configuration, data is not read.
2. Treating the "pending approval" draft sentence as completed approval. The input is the sample draft sentence; the comparison object is the approval-state field in the list source text; the observable result is that the source only says pending approval and the draft sentence lacks support.
3. Treating a retrieval result or form submission as authorized execution. The input is the handover request; the comparison object is the separate state records for approval, write-off, and price tag; the observable result is that when the approval state has not changed, later actions have no basis.

## How to verify the setup

1. Input the sample list source text and the draft sentence; compare the value of the approval-state field. The condition is met only when the source shows a completed approval record and the subject, batch, and date agree.
2. Input the scheduled-task configuration and the interface documentation; compare request method, Headers, Body, and variable references. The condition is met only when each item corresponds and the returned result can be extracted.
3. Input the handover request and the authorization-state records; compare the three states for approval, write-off, and price tag. The condition is met only when each has a completed record; where a record is missing, note the gap and do not conclude that the action was executed.

A missing record stays missing. A pending request is not approval, an offered option is not execution, and an unsigned termination is not a completed termination.
