# Near-expiry markdowns: workflow routing for procurement

## What the documents look like
Near-expiry markdown handling concerns the remaining shelf life of shelf inventory. This differs from order-by-order weighing and sorting, which processes individual order lines. The materials for this page's task, inventory procurement and supplier records, are the near-expiry list, the markdown approval, the damage report, and the promotional price tag. Data sources named in the brief are POS stock age, store inspection, ERP inventory, and quality inspection records. The brief gives update frequency as daily and per shift. This page does not derive batch synchronization, full synchronization, real-time behavior, or transaction-triggered behavior from that frequency.

These materials occupy different states in the process. A near-expiry list records batch and remaining shelf life. A markdown approval records an application and approval opinion. A damage report records disposal of unsellable goods. A promotional price tag records the outward-facing label. Any of the four may sit in draft, pending approval, approved, or executed state. Workflow routing must keep state transfer separate from the authorization boundary.

## Constraints at the workflow routing step
The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. After the user completes required fields and submits, the node collects the submitted form information and passes it to later nodes. The User Selection node is also a user interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. When the user makes a choice, the node evaluates that choice and executes the "yes" branch. Both nodes can be added repeatedly and trigger execution. Interaction-state recording is existing node behavior; this page does not add a global state-recording switch.

Hypothetical paper test case. A store loss-prevention administrator submits a near-expiry list with this text: "Batch A, leafy vegetables, remaining shelf life 1 day, quantity 12 units, stored in refrigerated cabinet No. 3; inspection time 2025-03-10 morning shift; markdown recommended, not yet submitted for approval." A second material is a draft promotional price tag sentence: "This leafy vegetable batch is marked down by half; execute after approval passes." The request to be judged is: "Please submit Batch A's markdown application for approval and synchronize the price tag."

This request touches two kinds of action: markdown approval and price tag execution. The Form Input node can collect application information. The User Selection node can let an approver make a choice and take the "yes" branch. Approval passing, price tag printing, ERP inventory writing, and external status synchronization require a separate business interface or a later process. Collected form values do not by themselves constitute approval or execution. Retrieval is used to find related material; retrieval results do not constitute authorization, and a relevance score does not perform permission or entity isolation. Libraries across different vector models cannot be associated together; check identifiers first and exclude those that do not match.

## Configuration and implementation checks

| Configuration item | Relevant setting or check on this page | Relation to the sample |
| --- | --- | --- |
| Form Input node | Enters interaction state on trigger, collects required information, passes it on after submission | Collects Batch A's markdown application fields |
| User Selection node | Executes the "yes" branch after the user chooses; verify branch connections one by one | Approver makes a choice on the application |
| Output handoff check | Pass collected information explicitly to later retrieval, judgment, or interface nodes and compare item by item | Check whether application fields reach the approval judgment |
| External action division | Order writing, document backfill, and external status synchronization require a separate business interface or later process | Price tag printing and inventory writing are not completed inside the node |
| Knowledge base association check | Associate libraries on the same vector model; check identifiers first and exclude non-matching ones | Check whether the supplier records library identifier matches |
| Empty-result handoff check | Use an explicit paper input of [] to check downstream design | Check the downstream branch when no matching material exists |

This page sets no numeric configuration and specifies no default value, limit, or global switch. If a hypothetical trial starting value were needed, its selection reason and comparison object would have to be stated; this page has no such starting value.

## Three common errors
1. Treating form submission as completed markdown approval. In the sample, the administrator submits an application; the node collects fields and passes them on, while the approval state remains pending. Submission and approval passing are different facts.
2. Treating a retrieval hit as an authorization basis. Retrieval returning material about Batch A does not mean the batch has been granted markdown permission, and does not mean the price tag may be executed. A relevance score does not exclude unrelated business or unauthorized records.
3. Treating the User Selection "yes" branch as completed external execution. After the approver chooses "yes", the workflow takes the corresponding branch, while price tag printing and inventory writing still require a separate interface. Branch execution does not produce an external business action.

## How to verify the setup
1. Input the sample text "Batch A, leafy vegetables, remaining shelf life 1 day, quantity 12 units" and check whether the Form Input node collects batch, category, and quantity fields, and whether those fields appear in later node inputs after submission. Missing fields or fields not passed on do not satisfy the condition.
2. Input the request to be judged, "Please submit Batch A's markdown application for approval and synchronize the price tag", and check whether the User Selection node takes the "yes" branch after the approver makes a choice, and whether branch connections are verified one by one. A branch not connected, or a choice not entering the corresponding branch, does not satisfy the condition.
3. Use a paper input of [] to check the downstream design when no matching material exists, and observe whether downstream nodes accept the empty result as designed. Do not claim that retrieval under a fictional rule necessarily returns []. If no downstream branch accepts it, record this as pending verification rather than as a conflict.

All three verification steps address this page's primary task and do not involve identity certification or report analysis. Whether approval passes, whether the price tag is printed, and whether inventory is written remain unsupported or pending verification; this page does not supply authorization or effective clauses for them.
