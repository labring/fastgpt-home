# Fresh-food supplier claims: HTTP integrations for procurement

## What the documents look like

Fresh-food supplier claims trace responsibility for quality problems that arrive with a delivery. The working materials are quality exception forms, photo evidence, deduction notices and claim reconciliation statements. These come from quality inspection systems, WMS acceptance, supplier contracts and finance reconciliation. The data rhythm runs on two parallel tracks: records per accepted batch, and monthly reconciliation. Compared with near-expiry markdown handling, a claim pursues the supplier's responsibility for delivered quality and does not address ordinary store-level shrinkage.

In this task, the HTTP integration sends requests from the inventory procurement and supplier records side to an external system and parses return values into usable fields. The integration does not complete a quality determination, a deduction confirmation or a supplier settlement. Those remain downstream business actions.

## Constraints at the HTTP integrations step

The HTTP module can be added more than once, is configured manually, and executes on trigger. Params are path request parameters, Body is the request body, and Headers are request headers. All three can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime and histories. chatId and responseChatItemId do not exist in test mode, so a missing value during debugging is a documented condition rather than a fault. Return values are extracted through JSON path syntax. When the output type is set to string, the value for the corresponding key is converted into a JSON string.

Retrieval and similarity affect content matching only. They do not constitute authorization, approval or entity isolation. Whether an external system writes or synchronizes depends on that system's contract; the HTTP module only sends the request and parses the response.

Hypothetical drill sample: a fresh-produce acceptance record reads, "On 12 March 2025, batch A-0312, accepted quantity 200 boxes, of which 18 boxes of leafy greens showed abnormal appearance; quality inspection has retained photographs." A separate handover request awaiting determination reads, "Please push this batch's quality exception form to the supplier claim reconciliation interface and complete the deduction confirmation." The materials support the delivery batch and the abnormal quantity. The deduction confirmation belongs to the finance reconciliation stage. The request carries no supplier confirmation and no deduction basis, so it can only be recorded as pending verification, not as authorized execution.

## Three common errors

1. Treating retrieval or similarity as authorization. Retrieval performs content matching; it does not judge supplier identity or deduction authority. Check: input the batch and abnormal quantity from the sample, compare whether the returned values contain only content fields, and observe whether identity or permission fields appear. If they do not, a deduction confirmation cannot be executed on that basis.

2. Treating a pending request as executed. The deduction confirmation request in the sample lacks supplier confirmation and a deduction basis, so it is pending verification. Check: input the request text, compare whether the materials state supplier confirmation and a deduction amount basis, and observe whether only the delivery batch and abnormal quantity are present. When only the latter appear, record the item as unsupported.

3. Treating an empty value in test mode as a business fault. chatId and responseChatItemId do not exist in test mode. Check: send a request in test mode, compare the values of these two fields, and observe whether they are empty. When empty, record it under the documented condition and do not infer an external system fault.

## How to verify the setup

1. Use the sample text to check return value extraction. Input "batch A-0312, accepted quantity 200 boxes, 18 boxes of leafy greens with abnormal appearance", configure the key using JSON path, compare the extracted result with the source numbers, and observe whether 200 and 18 land in their corresponding fields. If a field is empty or misaligned, the extraction path and the response structure do not match.

2. Use the pending request to check the authorization boundary. Input "Please push this batch's quality exception form to the supplier claim reconciliation interface and complete the deduction confirmation", compare whether the materials contain supplier confirmation and a deduction basis, and observe whether only the delivery batch and abnormal quantity appear. When only the latter appear, record the item as pending verification and do not mark it as authorized execution.

3. Use test mode to check the debug fields. Send a request in test mode, compare the values of chatId and responseChatItemId, and observe whether they are empty. When empty, record it under the documented condition and recheck under a session condition. Do not use this to conclude that an external system write or synchronization has completed.
