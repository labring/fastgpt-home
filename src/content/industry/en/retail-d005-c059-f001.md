# Store cold-chain receiving: HTTP integrations for procurement

## What the documents look like

Cold-chain receiving at a store produces a set of materials for each delivery batch: cold-chain temperature records, an arrival acceptance sheet, a rejection note, and the supplier delivery note. The data sources named in the brief are the cold-chain vehicle temperature control, the WMS, the store receiving system, and quality inspection photos. These materials update with each batch and daily, and their registered content covers transport temperature, arrival batch, sampled quality, and rejection reason.

This page addresses one task within that setting: inventory procurement and supplier records, specifically the HTTP interface and external system step. The question is how a request is organized when these materials are sent to an external service or retrieved from one, how variables are referenced, and how return values are parsed. The batch and daily update rhythm describes when materials appear. It does not establish batch synchronization, full synchronization, or a transaction-triggered mechanism.

The HTTP module sends an HTTP request to a given address. Params carry path request parameters and are common in GET requests. Body carries the request body and is common in POST and PUT requests. Headers carry special information. All three data sections and the URL can reference variables through `{{}}`. Variables come from global variables, system variables, and preceding node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. The chatId and responseChatItemId values do not exist in test mode, so a missing value during debugging is a condition of that mode rather than a business fault. Return value configuration describes how to parse the interface response, using JSON path syntax to extract values. When the output type is set to string, the value of the corresponding key is converted to a JSON string.

## Constraints at the HTTP integrations step

A hypothetical paper exercise sample is used here for illustration only. A store receiver submits one batch of cold-chain arrival materials. The source text available for checking reads: "Arrival acceptance sheet number A-001; the transport temperature record shows the batch stayed within the agreed range throughout; sampled quality is qualified; no rejection note was issued." The draft sentence to be judged reads: "The batch has passed acceptance and the supplier delivery note has been synchronized to the external system." According to the recorded content, the acceptance sheet and temperature record point to a qualified status. The phrase "has been synchronized to the external system" has no corresponding record in the source text. That part is unsupported and requires separate verification of whether a synchronization action occurred.

In the chat interface, the model and temperature fields passed in the request have no effect; these are determined by the orchestration and do not change with API parameters. When detail is true, intermediate values are returned, and in non-stream mode the result is stored in responseData. Automatic output formatting was added after v4.6.8, and when the output type is string, the value is output as a JSON string. These are existing node behaviors and configurable fields. Business-side acceptance decisions, approvals, and database writes require separate implementation.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason for the choice and comparison target |
| --- | --- | --- |
| Request URL | The address given in the external interface document, including the v1 path | Compare character by character with the document address; when a 404 appears, add v1 and retry |
| Request method | Chosen according to the external interface contract | Compare with the method declared in the external interface document |
| Headers authentication | Authorization references a token variable | Compare with the key usage specification; credentials are not written into public samples |
| Body structure | JSON organized by the external interface field names | Compare field by field with the external interface contract |
| Variable reference | References the acceptance sheet number from the preceding node output | Compare with the actual output value of the preceding node |
| Return value parsing | One key configured for each required field | Compare with the interface response structure; output type set to string |

The API key is used for authentication. When calling chat/completions, passing body.appId in the request body is recommended. For compatibility with the OpenAI SDK, Authorization: Bearer <apiKey>-<appId> is also supported, in which case body.appId is not required. Some SDKs need the v1 path added to BaseUrl and some do not; if a 404 appears, adding v1 and retrying is the documented step. The appId priority order is body.appId, then <apiKey>-<appId>, then the appId associated with the apikey under the older adaptation. This page treats these as documented configuration conditions, not as business verification or approval.

## Three common errors

1. Treating a missing chatId or responseChatItemId in test mode as an interface fault. The documentation states this is a test mode condition. The check compares the current running mode with the field value and observes whether the field is absent according to the mode, rather than concluding that the external system is abnormal.

2. Treating the phrase "has been synchronized to the external system" in the draft sentence as an occurred fact. The input is the sample source text and the draft sentence. The comparison target is whether the source text records a synchronization action. The observed result is that the source text supports only the qualified acceptance status, and the synchronization part should be recorded as pending verification.

3. Treating the extracted value of a return value key as the complete interface response. The input is the interface response and the configured key. The comparison target is the path corresponding to the key and the expected field. The observed result is that the extracted value may be only part of the response and should be checked against the interface contract before use.

## How to verify the setup

1. Input the sample source text and the draft sentence. Compare the status recorded in the source text with the scope of the assertion in the draft sentence. Observe whether the draft sentence exceeds the source text. If the draft sentence contains a synchronization action not recorded in the source text, judge it as unsupported and retain the evidence gap.

2. Input one request configuration. Compare the URL, method, and Headers with the external interface document. Observe whether a 404 appears. If it does, add the v1 path and retry according to the document, and record the actual observed result.

3. Input the interface response and the configured key. Compare the extracted value with the expected field. Observe whether a JSON string is produced when the output type is set to string. If the extracted value does not match the contract, check the key path. Do not infer a specific error cause.

These three checks use the hypothetical sample given above. They describe what to compare and what remains unknown. They do not claim that any test, deployment, approval, or synchronization actually happened. Where the source text does not record an action, the gap stays open.
