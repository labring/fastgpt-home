# Fruit-store procurement: HTTP integrations for procurement

## What the documents look like

Fresh-fruit procurement runs on wholesale-market price signals, supplier quotations, store sales, and residue test reports. Purchase orders, acceptance records, residue test reports, and shrinkage records change by day or by batch. Grade acceptance and price comparison drive spoilage losses and stockouts directly, so when these records are exchanged with an external system, field definitions and batch scope depend on the same-day market and the actual stall situation more than standard head-office meal ordering does.

The HTTP module sends a request to a target address. Params carry path parameters, Body carries the request body, and Headers carry request headers; all three can reference variables through `{{}}`, drawing on global variables, system variables, and upstream node outputs. Return values are extracted with JSON path syntax, and when the output type is set to string, the corresponding value is converted into a json string. The chat endpoint authenticates with an APIKey; when calling `chat/completions`, passing `body.appId` in the request body is recommended, and `Authorization: Bearer <apiKey>-<appId>` is also supported.

## Constraints at the HTTP integrations step

Purchase and acceptance data shift by day and by batch, so an interface integration has to check material, quantity, and status batch by batch. A single request result does not become a long-lived authorization or inventory conclusion. The HTTP module can operate a database, call an external data source, run a web search, or send email; these are extension directions, and the actual write, approval, and synchronization require their own downstream implementation. The module itself does not perform business authorization judgments.

Hypothetical paper exercise sample: the following is paper material for checking only and does not represent any real record.

Material text one: A store fresh-produce supervisor submits a purchase request on 10 March 2026. The material is Red Fuji apple, grade one, quantity 200 kilograms, supplying stall is a stall in Zone A of the Chengbei wholesale market, and the request status is "pending procurement supervisor review."

Material text two: The same stall provides a quotation on the same day stating "this quotation is valid until 12 March 2026." The quotation does not state a supply period or settlement terms.

Draft sentence to be judged: The purchase request has been approved and arrival can be arranged for 11 March.

Judgment point: The status in material one is "pending procurement supervisor review," and pending review does not constitute approval. The quotation validity period constrains the quotation itself; it does not indicate a supply period or contract effectiveness. The phrases "has been approved" and "arrival can be arranged" in the draft sentence are unsupported and remain to be verified.

## Three common errors

1. Reading "pending procurement supervisor review" in material one as already approved, treating a request whose review is unfinished as executable procurement. Check method: input the text of material one, compare the status field with "has been approved" in the draft sentence, and observe whether the two agree.

2. Extending "valid until 12 March 2026" on the quotation into a supply period or contract effectiveness. Check method: input the text of material two, compare the validity field with the arrival arrangement in the draft sentence, and observe whether the quotation states a supply period.

3. Treating an empty chatId in test mode as a business fault. Check method: input a test-mode request, compare the documented statement that the field "does not exist in test mode" with the returned result, and observe whether the missing field is expected behavior.

## How to verify the setup

1. For material one, input the purchase request text and the draft sentence, compare the request status with the wording "has been approved," and observe whether the draft sentence is supported by the source text. If the status remains pending review, record it as unsupported.

2. For material two, input the quotation text and the arrival arrangement, compare the validity field with the supply period, and observe whether the quotation states a supply period. When it does not, record an evidence gap.

3. For the interface request, input the configured address, method, and Body, compare the actual passed values against the interface contract, and observe whether return value extraction yields the expected field through JSON path. If the response is empty or a field is missing, record the actual observation and do not infer a deterministic failure cause.

Retrieval and similarity do not carry authorization or entity isolation functions, and retrieval results do not replace business authorization. Libraries across different vector models cannot be associated together; verify identifiers first and exclude those that do not match. The configuration returned by an interactive node contains only type and params, and internal runtime fields are not returned. Forms collect values, and business verification, approval, database writes, and external synchronization each require their own downstream implementation.
