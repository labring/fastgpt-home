# Livestream after-sales service: vector indexes for procurement

## What the documents look like

Livestream after-sales work clusters after a single live session, when refund requests and reshipment orders arrive in the same window. The outcome of each case is tied to what the host promised on air. For inventory procurement and supplier records, this means the livestream order list, refund requests, reshipment orders and script templates need to sit in one retrieval scope so that a supplier confirmation, a promised date and a quantity cap can be compared against a draft handover sentence. The brief lists update frequency as per session and daily; this page does not depend on that cadence and does not infer batch synchronization, full synchronization, real-time updates or transaction-triggered mechanisms from it.

The retrieval side only needs to check the current state of the documents. A supplier confirmation that names one model, one date and one quantity ceiling is a bounded statement. A draft sentence that widens the same supplier's obligation is a separate text that has to be judged against the source, not against a general impression of the supplier relationship.

## Constraints at the vector indexes step

Knowledge bases joined in one retrieval call must use the same vector model, so the actual model and its input type are checked before selection. One source data block can carry several indexes, and the index content is checked separately from the original text. Index content is most useful when it is complete and focused; retrieval coverage and index length are weighed together against the sample at hand. Image retrieval depends on whether image descriptions or image vectors were generated at ingestion time, so query-side capability alone does not decide the outcome. After a model or index change, the same group of questions is compared against the cited original text; a vector score on its own does not support a promise about results.

Hypothetical paper exercise sample: a livestream after-sales team keeps a paper record whose original text reads, "Supplier A confirmed on 1 March 2026 that model X reshipment parts can be dispatched by 10 March 2026, with a quantity ceiling of 200 units, and this confirmation applies only to the reshipment arrangement for this livestream order." A separate draft handover sentence reads, "Supplier A has committed to long-term supply and can cover all subsequent refund and reshipment cases." The question is whether the draft sentence matches the paper record.

The comparison is same-subject, same-period, same-field. The paper record states a single-session scope and a 200-unit ceiling for model X. The draft sentence states long-term supply covering all later cases. The draft sentence is unsupported by the record. The record does not contain a long-term supply clause, and no authorization or effective-date clause is invented to reach a definite answer. The evidence gap stays open.

## Configuration and implementation checks

| Configuration item | Setting or check for this page | Relation to the sample |
| --- | --- | --- |
| Linked knowledge bases | Select one or more knowledge bases that use the same vector model | The paper record and the draft sentence must be retrieved inside one library |
| Search mode | Semantic search, full-text search or hybrid search | Model X, the date and the quantity ceiling suit full-text or hybrid search |
| Citation ceiling | Maximum tokens cited per search | A hypothetical starting value for this exercise is set to cover every sentence of the paper record |
| Minimum relevance | A 0-1 value, effective only in semantic search or with result reranking | Filters low-relevance fragments; it is not an authorization or entity filter |
| Question optimization | Coreference resolution and question expansion before retrieval | A single clear question can leave this off |
| Result reranking | ReRank second-pass ordering, requires a model and is enabled per settings | Used to compare candidates against the original text when there are many |

The citation ceiling starting value for this exercise is the token amount that covers all sentences of the paper record. The reason is that the record has three sentences, and the subject, object, state and validity scope all have to be compared in full. When compared with a lower value, the observation is whether the draft sentence loses the phrase "only for this session" through truncation. This is a hypothetical starting value for the exercise, not an official default.

## Three common errors

1. Treating retrieval as authorization. In the sample, Supplier A's confirmation covers only reshipment for this livestream order. A retrieval hit on that record does not mean long-term supply has been authorized. The draft sentence's "long-term supply" is unsupported by the record.
2. Joining knowledge bases that use different vector models. The identifier is checked first and non-matching libraries are excluded. A cross-model retrieval is not run to compare missed recalls.
3. Treating RRF as an on/off switch. RRF is the fusion step for hybrid search results. Reranking requires a model and is enabled per settings. Image retrieval requires image input and the corresponding model capability.

## How to verify the setup

1. Input the original paper record text and the draft sentence. Compare "only for the reshipment arrangement for this livestream order" against "long-term supply". The observable result is that the draft sentence is judged unsupported and pending verification when it exceeds the record's validity scope.
2. Input model X and 10 March 2026. Compare whether the cited original text returned by full-text or hybrid search contains that date and the 200-unit ceiling. The observable result is that the check condition is met only when the cited original text shows those fields in full.
3. Input a text question with no image. Compare whether only the text path is used. The observable result is that no image description or image vector result appears when no vision model or image vector index is configured. Where an empty-result handoff needs to be checked, a clearly labelled paper input of [] can be used to check the downstream design; this does not claim that retrieval always returns an empty array.

These checks observe and describe failure branches. They do not guarantee a first-hit result, full recall, or that an unrelated query returns nothing. The same-vector-model requirement for linked knowledge bases does not extend to business registration sites or other external systems. No system error code or automatic business action is asserted beyond what the supplied documents describe.
