# Short-video affiliate sales: HTTP integrations for procurement

## What the documents look like

Short-video affiliate sales convert through long-running content exposure and product links, so the day-to-day materials are short-video scripts, linked-product lists, commission plans and violation feedback. Procurement and supplier records form a separate material set inside the same workflow: they record purchase batches, supplier entities and supply status. When these materials move through HTTP integrations and external systems, the surrounding data sources are the selected alliance, playback data, transaction data and platform rules, with daily or weekly update cycles. Those update cycles describe how often the materials themselves change; they do not establish batch synchronization, full synchronization or real-time triggering at the interface layer.

For this page the task is narrow: procurement and supplier records, handled at the HTTP integration step. The operational question is what the materials, actions and requests actually say about authorization state at handover, and whether a retrieval result or a form value has been treated as authorization. Retrieval and similarity do not carry permission or entity-isolation duties, so a returned record is not evidence that a party is authorized for the next action.

## Constraints at the HTTP integrations step

The HTTP module sends a request to the corresponding address, and the practical operation resembles Postman or ApiFox. Params are path request parameters, used mostly with GET requests. Body is the request body, used mostly with POST/PUT requests. Headers are request headers. All three data locations can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime and histories; chatId and responseChatItemId do not exist in test mode, so an empty value during debugging is not a business fault. Return-value configuration describes how to parse the interface response, extracted with JSON path, with the key following JS object access rules; when the output type is set to string, the corresponding value is converted to a json string. The chat interface uses APIKey authentication. When calling chat/completions, passing body.appId in the request body is recommended, and `Authorization: Bearer <apiKey>-<appId>` is also supported. The appId priority order is body.appId, then `<apiKey>-<appId>`, then the appId associated with the apikey. Passed fields such as model and temperature have no effect and are determined by the orchestration. Using authProxy to proxy a team member identity requires the team owner to enable it when creating or editing the key, and the proxied identity still needs permission on the target app and conversation.

Hypothetical paper exercise sample: the material text reads, "Supplier A submitted the linked-product list on 1 March 2025, batch number P-0301, containing Product A and Product B, supply status pending confirmation; commission plan number C-0301, applicable period 1 March 2025 to 31 March 2025." The draft sentence to be assessed reads, "Supplier A has completed supply confirmation for this batch and procurement warehousing can be arranged." The sentence concerns the subject Supplier A, the object batch P-0301, and the field supply status. The source text gives "pending confirmation"; the draft gives "completed". These are mutually exclusive values on the same field for the same subject and the same period, so the draft sentence is unsupported.

## Three common errors

1. Treating "pending confirmation" in the material as completed. Input: the Supplier A batch P-0301 material. Comparison field: supply status. The source text takes the value "pending confirmation" and the draft sentence takes the value "completed". Two mutually exclusive values on the same field for the same subject and period constitute a contradiction, and the draft is unsupported.
2. Treating retrieval or similarity as a permission filter. Input: a retrieval result carrying score and similarity. Comparison: whether the result carries an authorization field. When no authorization field is present, the result cannot be used to decide that the record is available for the next action.
3. Treating an empty chatId or responseChatItemId under test mode as a business fault. Input: a request made in test mode. Comparison: whether the system variable exists. The documentation states that both are absent in test mode, so the absence is expected.

## How to verify the setup

1. Input the hypothetical sample source text and the draft sentence, then compare subject, object, field and value. When the supply status field shows both "pending confirmation" and "completed" as mutually exclusive values for the same subject and period, the draft sentence is judged unsupported. This is a paper check; it has not been executed.
2. Input a request that references variables, then compare the variable sources with the actual passed values. When global variables, system variables and upstream node outputs each correspond item by item, the variable reference satisfies the condition. This is a paper check; it has not been executed.
3. Input a request with detail=true and stream=false, then compare the returned structure. When module status and complete results appear in responseData, the parsing configuration satisfies the condition. If the return is empty, record the empty result and check the downstream design; do not infer a specific failure cause. This is a paper check; it has not been executed.

The three checks above are paper-level comparisons. No deployment, approval, refund or other business action is claimed. Missing evidence remains missing, and a pending request is not an approval.
