# Group-buy presale orders: HTTP integrations for procurement

## What the documents look like

Group-buy presale collection takes orders first and organizes procurement and fulfillment afterward. This differs from leader relationship management, which is a separate line of work. The inventory procurement and supplier records step centers on four document types: the presale product table, the collection result, the procurement plan, and the cutoff notice. Data sources include mini-program orders, supplier inventory, leader feedback, and warehouse routing. Update frequency is daily or per session.

The costliest moments arrive after cutoff, when procurement is placed and picking waves are arranged. When an interface passes uncutoff data to an external system as though it were confirmed purchase quantity, the consequences are stockout refunds, fulfillment delays, and leader complaints. The HTTP module sends a request. Params carry path request parameters, Body carries the request body, Headers carry request headers, and all three positions can reference variables through `{{}}`. The URL can also reference variables.

## Constraints at the HTTP integrations step

Variables come from global variables, system variables, and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. chatId and responseChatItemId do not exist in test mode. When calling chat/completions, passing body.appId in the request body is recommended, and `Authorization: Bearer <apiKey>-<appId>` is also supported. The appId priority order is body.appId, then `<apiKey>-<appId>`, then the appId associated with the apikey. Whether BaseUrl needs a `v1` path depends on the SDK; if a 404 appears, adding `v1` and retrying is permitted. Passed fields such as model and temperature have no effect because the orchestration decides them. Proxying a team member identity through authProxy requires the team owner to enable it when creating or editing the key, and the proxied identity still needs permission on the target application and conversation.

Hypothetical paper exercise sample: A platform operator, after the cutoff on 10 March 2025, prepares a procurement plan draft from the presale product table and the collection result, intending to pass supplier code, product code, purchase quantity, and arrival date to an external procurement system through the HTTP module. Two source sentences: "The cutoff time is 20:00 on 10 March 2025; the collection result is 320 units of presale product A and 180 units of product B." "The procurement plan draft status is pending procurement supervisor review and has not been submitted to the external system." Draft sentence under review: "The procurement plan is confirmed and the order can be placed with the supplier." The request comes from the platform operator and involves the supplier and the products. The draft is pending review; no ordering authorization credential is provided. No inference is drawn that the person lacks operating permission.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Basis for checking and comparison method |
| --- | --- | --- |
| Request method | POST | Compare against the method declared in the external procurement system interface document |
| Request address | A procurement write path containing {{BaseUrl}} | Compare segment by segment against the interface document and confirm the variable resolves |
| Headers authentication | Authorization references an injected variable | Compare against the key usage rules; credentials do not appear in public samples |
| Body fields | Supplier code, product code, purchase quantity, arrival date | Compare field by field against the external interface contract and confirm matching types |
| Return value extraction | Extract procurement order number and status by JSON path | Compare against the hierarchy in the interface response example |
| Variable source | Collection result from an upstream node output | Compare against the global and system variable lists and confirm the source is legitimate |

POST and a write path are chosen as the starting point because this request carries procurement data and must match what the external interface document declares. This is not treated as an official default value. Return value extraction follows JS object access rules, and when the output type is string, the value at the corresponding key is converted to a JSON string.

## Three common errors

1. Passing a procurement plan draft that is pending review to the external system as confirmed purchase quantity. The input is a draft whose status is pending procurement supervisor review, the comparison object is the review status field in the source text, and the observable result is whether the request is sent before review completes.
2. Using a retrieval similarity or score to judge whether a supplier is authorized. The input is a relevance value returned by retrieval, the comparison object is the authorization status field, and the observable result is whether similarity is treated as a permission or entity filter.
3. Referencing chatId or responseChatItemId in test mode and treating it as a business fault. The input is a test-mode request, the comparison object is the system variable description, and the observable result is whether a field absent in test mode is treated as a production anomaly.

## How to verify the setup

1. For the draft sentence "The procurement plan is confirmed and the order can be placed with the supplier," the input is the two source sentences and the draft sentence, the comparison object is the status field "pending procurement supervisor review" in the source, and the observation is that the draft sentence and the same field's value are mutually exclusive. The result is recorded as unsupported, and the evidence gap is preserved.
2. For the procurement plan write request, the input is the four Body fields: supplier code, product code, purchase quantity, and arrival date. The comparison object is the fields and types declared in the external interface contract. If all four resolve and the types match, the check passes; if a field is missing or a type differs, it is recorded as pending verification.
3. For return value extraction, the input is the interface response example, the comparison object is the configured JSON path against the extraction example, and the observation is whether the extracted value matches the example hierarchy. If the response is empty or the path does not exist, the actual observation is recorded without inferring a deterministic failure cause.

Forms collect values. Business verification, approval, database writes, and external synchronization each need their own downstream implementation. Retrieval does not carry authorization responsibility, and a relevance score does not exclude unrelated businesses or unauthorized records. The above is a paper check and was not executed.
