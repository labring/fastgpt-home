# Dealer rebate calculation: HTTP integrations for procurement

## What the documents look like

Dealer rebate calculation happens after sales, and its core is policy interpretation and financial offset rather than replenishment. The working materials are rebate policies, sales attainment tables, reconciliation statements, and red-letter invoices. These come from ERP sales records, dealer remittances, contract ledgers, and the finance system, and they typically update monthly or quarterly. For the procurement and supplier materials task, three kinds of material need to sit under one consistent reading: purchase receipt quantities, supplier reconciliation balances, and the applicable period of the rebate policy. Rebate disputes and revenue recognition errors turn on whether these readings agree and whether the supporting documents are complete.

An HTTP integration step does not change those business facts. It carries values between systems. The FastGPT HTTP module sends a request to a given address, uses Params for path parameters (common with GET), Body for request bodies (common with POST and PUT), and Headers for special information. The URL and all three data areas can reference variables through `{{}}`, drawing on global variables, system variables, and outputs from earlier nodes. Return values are extracted with JSON path syntax, and the output type can be set to string. Among system variables, `chatId` and `responseChatItemId` do not exist in test mode, so an empty value during debugging is expected and does not indicate a business fault. When the chat completions interface is called, `model` and `temperature` are determined by the orchestration; passing them as API parameters does not change their values.

A hypothetical paper exercise sample is used below. The brand finance function supplies rebate policy text reading: "From July to September 2024, after Dealer A meets the quarterly procurement target, rebate is accrued at 2% of remittance amount; return amounts are deducted from the attainment basis." The reconciliation statement in the same batch shows one return in August, and the red-letter invoice has not been issued. The draft sentence to be judged is: "Dealer A's third-quarter rebate already meets the conditions for invoice offset." The source text does not state whether the target was met or what the return deduction produced, and it does not set out any condition for invoice offset, so the sentence is unsupported. The red-letter invoice status is recorded separately.

## Constraints at the HTTP integrations step

The integration carries the procurement and supplier values; it does not decide the rebate. Params, Headers, and Body each need to match the external interface contract, and variable references need to be checked item by item against the values actually passed. The request address may reference a variable, so the address in use is a runtime value rather than a fixed string. Authentication credentials belong in secure configuration and do not appear in public samples.

Return value extraction uses JSON path syntax, and the output type chosen for each key must suit the downstream use. Selecting a string output converts the corresponding HTTP key value into a JSON string. This matters where a downstream text step or AI dialogue step expects text rather than a structured object.

Two documented behaviours shape debugging. First, `chatId` and `responseChatItemId` are absent in test mode, so a blank value there is a documented condition, not evidence of a broken session. Second, `model` and `temperature` supplied to the chat completions interface are ineffective; the orchestration decides them. The API key rules also matter: `chat/completions` recommends passing `body.appId`, and the OpenAI-compatible form `Authorization: Bearer <apiKey>-<appId>` is also supported, in which case `body.appId` need not be sent. The appId priority order is `body.appId`, then `<apiKey>-<appId>`, then the appId associated with the apikey under the older adaptation. Where a `BaseUrl` needs a `v1` path depends on the SDK, and a 404 can be retried with `v1` added.

For this page's task, the integration boundary is narrow. The HTTP module can operate a database, call an external data source, run a web search, or send email. None of those actions constitutes business verification, approval, a database write, or external synchronisation on its own. Those require their stated downstream implementation. A retrieval result is not authorisation, and a form collects values rather than granting permission.

## Configuration and implementation checks

| Configuration item | Value source | Check method |
| --- | --- | --- |
| Request address and method | External interface document | Address may reference a variable; method chosen per contract |
| Params and Headers | External interface contract | Path parameters and headers checked separately; credentials injected from secure configuration |
| Body structure | External interface contract | Takes effect only under the corresponding request type; JSON structure matched to contract |
| Variable references | Global variables, system variables, earlier node outputs | Each reference compared with the value actually passed |
| Return value extraction | JSON path syntax | Output type matched to downstream use |
| Debug identity fields | `chatId`, `responseChatItemId` | Absent in test mode; a blank value is expected |

This check uses the July to September 2024 range from the source text and confirms that the August return falls inside that quarter. The contract ledger was not provided, so no cycle or attainment result is confirmed from it.

## Three common errors

1. Treating the quarterly range in the rebate policy text and the month on the reconciliation statement as directly equivalent, without checking the return deduction clause, so the attainment basis is overstated. Check: input the policy text and the reconciliation statement, compare whether the return amount has been deducted from the attainment basis, and observe whether both figures share the same period and the same field.

2. Writing the `model` field returned by the chat completions interface into the request body as a tunable parameter, on the assumption that API parameters change the orchestration result. Check: input a request body containing `model`, compare the model identifier actually used in the response, and observe whether it follows the orchestration.

3. Reading an empty `chatId` in test mode as a broken session path. Check: input a test-mode request, compare against the system variable description, and observe whether `chatId` and `responseChatItemId` are documented as absent.

## How to verify the setup

1. Input the rebate policy text and the reconciliation statement from the hypothetical sample. Compare whether the return amount is deducted from the attainment basis, and observe whether the two figures share the same entity, the same period, and the same field. The sample does not give the return amount or the deduction result, so record the gap and do not assume the deduction has occurred.

2. Input the draft sentence "Dealer A's third-quarter rebate already meets the conditions for invoice offset." Check it against target attainment, return deduction evidence, and any stated condition for invoice offset. The sample provides only the policy and the unissued status, so the evidence is insufficient and the sentence remains pending verification.

3. Input a request body containing `model` and `temperature`. Compare the model identifier in the response with the orchestration configuration, and observe whether the API parameters changed the actual value. Record the comparison between the actual model and the orchestration configuration. The basis for the parameter field being ineffective is the interface document; a single matching result does not independently establish that rule.

Retrieval and similarity scores do not carry permission or entity isolation. Libraries across different vector models cannot be associated together; identifiers must be checked first and non-matching ones excluded. An empty result can be checked against a clear paper input of `[]` for downstream design, without claiming that a fabricated rule search necessarily returns empty. Where the source is silent, the condition remains unknown rather than being resolved by assumption.
