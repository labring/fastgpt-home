# Cross-border settlements: HTTP integrations for procurement

## What the documents look like

In cross-border platform settlement and foreign exchange, procurement and supplier records serve as evidence before funds are collected. The platform settlement statement records order deductions and net amounts, the exchange rate table records the basis for conversion, the service fee invoice records cost, and the receipt reconciliation table records incoming detail. These materials update weekly or monthly, and the reconciliation target is the fund collection result of completed orders rather than fraud chargeback handling.

The HTTP integration step retrieves these materials from a procurement system or supplier system so that later reconciliation can use them. Retrieval moves data. It does not change the business status of the purchase order, invoice or reconciliation table itself.

## Constraints at the HTTP integrations step

The request URL and method follow the external interface document, and the URL can reference a variable. Params carry path parameters, Headers carry authentication and special information, and Body takes effect only under the corresponding request type. Variables come from global variables, system variables and preceding node outputs, and are referenced with `{{}}`. Return values are extracted through JSON path, and when the output type is string the corresponding value is converted into a json string.

Hypothetical drill sample. The source text available for checking: a supplier system interface document states that the interface returns purchase order number, supplier name, tax-inclusive amount, currency and document status; a procurement system export states "purchase order number PO-2024-0517, supplier name Xinghai Parts, tax-inclusive amount 12000.00, currency CNY, document status Submitted". One draft handover sentence awaiting judgment reads: "This purchase order has passed review and can be counted into the current period inventory cost."

chatId and responseChatItemId do not exist in test mode, so an empty value obtained during debugging is an environment phenomenon and cannot by itself be judged a business fault. The document status returned by the interface is "Submitted", which is a different fact from "passed review". The draft sentence writes a submitted status as a passed review, which goes beyond the source evidence.

## Three common errors

1. Writing the interface return value "Submitted" directly as "passed review" into the handover material. The input is the return field "document status = Submitted", the comparison object is the source wording, and the observable result is that the draft sentence contains "passed review" while the source text has no such statement.
2. Omitting the outer quotation marks when referencing a string variable in Body. The input is the two forms `"{{supplierName}}"` and `{{supplierName}}`, the comparison object is the Body declaration example given in the document, and the observable result is that the latter form cannot produce a quoted string value.
3. Judging a missing chatId or responseChatItemId in test mode as an interface anomaly. The input is the return from the debugging environment, the comparison object is the document statement that these do not exist in test mode, and the observable result is a false fault report while the request parameters are in fact normal.

## How to verify the setup

1. Take the hypothetical sample source text, input the actual return values of the five fields, and compare whether the "document status" field value matches "Submitted" in the source text. A match means extraction is correct. The phrase "passed review" in the draft sentence remains unsupported.
2. Take the hypothetical request Body declaration, input the quoted and unquoted forms, and compare whether the parsed result is a quoted string. The expected string appearing means the form is correct.
3. Take purchase order number PO-2024-0517 from the hypothetical sample, input the extraction result, and compare whether it matches the source text exactly. A match means the field mapping is correct. Supplier name, amount and currency are checked field by field in the same way, and any mismatch is recorded as pending verification rather than judged as a conflict.

These checks cover retrieval and field mapping only. Whether the purchase order has passed review and whether it can be counted into cost are facts that require separate confirmation from the business system, and this page does not decide them.
