# Cross-border settlements: vector indexes for procurement

## What the documents look like

Cross-border platform settlement and foreign exchange concerns the collection of funds from completed orders. It sits apart from fraud and chargeback handling, which addresses a different stage and a different set of records. The materials handled on this page are platform settlement statements, exchange rate tables, service fee invoices, and receiving reconciliation statements. The task falls under inventory procurement and supplier records, so the working subject is the supplier, the procurement batch, the settlement currency, the exchange rate, the service fee amount, and the receiving status.

These materials update weekly or monthly according to the supplied brief. The brief does not describe batch synchronization, full synchronization, real-time updates, or transaction-triggered updates, and none of those mechanisms are inferred here. For retrieval to connect one procurement batch's settlement content with its reconciliation content, the subject, the object, and the period must appear together. When any of those three is missing, the retrieval step can return a partial match, and the missing element remains an evidence gap rather than a settled fact.

The eight-dimension brief places this category apart from cross-border payment risk control because settlement and exchange work on funds already collected from completed transactions. The main data sources are the platform settlement center, bank statements, payment institution backends, and ERP orders. The typical practitioners are cross-border seller finance staff, tax accountants, and platform operations staff. Errors in this work affect profit calculation, tax filing accuracy, and cash availability.

## Constraints at the vector indexes step

The knowledge bases linked for retrieval must use the same vector model. The actual model and its input type are checked before any association is made. A single source data block can be associated with multiple indexes, and the index content is checked separately from the source text. Index content is built from complete and focused information, and the trade-off between retrieval coverage and index length is weighed against the sample at hand. Image retrieval depends on whether an image description or image vector index was generated at ingestion time, so it is not determined by the query side alone.

Semantic recall and relevance scores do not carry authorization or entity isolation. The same-model requirement for linked retrieval bases does not extend to external systems such as business registration sites, and it does not mean those external systems must use the same model. Retrieval is not authorization, and a similarity setting does not exclude unrelated businesses or unauthorized records. Forms collect values; business verification, approval, database writes, and external synchronization require their stated downstream implementation.

A hypothetical paper exercise sample: the source text reads, "Supplier A, procurement batch A-07, settlement currency US dollars, exchange rate executed per the value listed in the March 2024 reconciliation table, service fee invoice number SF-0312, receiving reconciliation statement status pending verification." The draft sentence under review reads, "Supplier A's procurement batch A-07 has completed settlement and collected the service fee." The draft sentence carries a subject, an object, and a status, but the source text states only "pending verification" and does not record completed settlement or completed service fee collection. The finding is that the draft sentence is unsupported, and the evidence gap is preserved.

The 2000-token figure is a starting point for this paper exercise, chosen so that it can be compared against the length of the sample reference text and adjusted from there. It is not an official default. RRF is a merge process for hybrid results, not a switch that is turned on. The documented reference limit uses the token unit, and the limit is not a guessed item count.

## Three common errors

1. Treating "pending verification" as completed settlement. The input is the source text above and the draft sentence. The comparison is between "pending verification" and "has completed settlement." The observable result is that the draft sentence is unsupported.
2. Treating a retrieval result as authorized execution. The input is a supplier record returned by retrieval. The comparison is between the retrieval action and the business authorization boundary. The observable result is that retrieval produces no approval and no write.
3. Linking knowledge bases that use different vector models. The input is the model identifiers of two knowledge bases. The comparison is whether the identifiers match. The observable result is that the non-matching base is excluded, and no cross-model retrieval comparison is run.

## How to verify the setup

1. Input the source text and the draft sentence given above. Compare "pending verification" with "has completed settlement and collected the service fee." The condition is met when the finding is that the draft sentence is unsupported.
2. Input the same supplier, the same batch, and the same period fields. Compare the values of the settlement status field. A contradiction is recorded only when the same field holds explicitly mutually exclusive values; when the value is not recorded, or only evidence from a related stage exists, the item is recorded as pending verification.
3. Input the vector model identifiers of two knowledge bases. Compare whether the identifiers match. The condition is met when the non-matching base is excluded and the actual observation is recorded. An empty result can be checked against a downstream design using the explicit paper input [], and no claim is made that a fictional rule search necessarily returns [].
