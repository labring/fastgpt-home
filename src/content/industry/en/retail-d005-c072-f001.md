# Overseas stock replenishment: HTTP integrations for procurement

## What the documents look like

Third-party overseas warehouses can serve multiple sales channels, and the seller allocates stock across those channels. Replenishment plans, inbound appointment requests, inventory age reports and final-mile delivery notes are spread across warehouse management systems, ERP sales forecasts, freight forwarder systems and carrier bills. Procurement and supplier records move between these sources. The HTTP module sends a request to an external address and parses the response, and its operation is close to tools such as Postman and ApiFox. Variables come from global variables, system variables and upstream node outputs, and the URL, Params, Headers and Body can each reference variables through double curly braces.

For this task, the material that matters is the supplier quotation, the replenishment plan it feeds, and the inbound appointment that follows. A quotation states a lead time and a validity window. Those are separate facts from whether a purchase contract was signed, whether cooperation was reached, and whether a contract took effect. The page treats quotation content as input to a replenishment plan, not as proof of a commercial commitment.

## Constraints at the HTTP integrations step

Params are path request parameters and are used mostly with GET requests. Body is the request body and is used mostly with POST and PUT requests. Headers carry special information. Body takes effect only under specific request types. Return-value configuration describes how to parse an interface response, extracting values through JSON path syntax, and the rule follows JavaScript object property access. When the output type is set to string, the value at the corresponding key is converted to a JSON string.

Among system variables, chatId and responseChatItemId do not exist in test mode. The chat interface uses APIKey authentication, and when calling chat/completions the recommendation is to pass body.appId in the request body. The appId priority order is body.appId, then apiKey-appId, then the appId associated with the apikey. Fields such as model and temperature that are passed in are determined by the orchestration and do not change with API parameters.

Hypothetical paper exercise sample: a cross-border seller intends to write a supplier lead time into a replenishment plan. The material to be checked reads: "The quotation submitted by Supplier A for the hypothetical date range 1 March 2025 to 31 March 2025 states a delivery lead time of 30 days and a quotation validity until 15 April 2025; the quotation does not state whether a purchase contract has been signed." The draft sentence to be judged is: "Supplier A has confirmed 30-day supply and it has taken effect." That sentence conflates quotation validity with supply lead time. Signing, reaching cooperation and contract effectiveness are three distinct facts. The material does not state the contract status, so the sentence is unsupported and remains to be verified.

## Three common errors

1. Treating quotation validity as the supply lead time. The input is the quotation text above; the comparison is between the field "quotation validity until 15 April 2025" and the field "delivery lead time 30 days". The two fields carry different meanings, and the draft sentence's assertion that supply is confirmed is unsupported by the material.
2. Treating an empty value in test mode as a business failure. The input is a request issued in test mode; the comparison is whether chatId and responseChatItemId are present. The documentation states that these two fields do not exist in test mode, so their absence does not establish an external system fault.
3. Treating return-value configuration as the interface return value itself. The input is a configured extraction key; the comparison is between the extracted result and the raw interface response. The configuration only describes how to parse, and choosing string as the output type changes the presentation form.

## How to verify the setup

1. Against the quotation text and the draft sentence, check whether the draft contains wording such as "has confirmed supply" or "has taken effect". Where the material does not state contract status, the observed result should be that the sentence remains to be verified; if that condition is not met, the sentence needs rewriting.
2. Against the test-mode request, check whether chatId and responseChatItemId are empty. The documentation states they do not exist, so an empty value is the expected observation; only an error report would require a separate investigation.
3. Against the return-value configuration, check whether the extraction key corresponds to the interface response structure, and observe whether the output is converted to a JSON string when the output type is string. A mismatch with the interface response example requires correction.

This page covers only overseas stock replenishment management, procurement and supplier records, and HTTP integrations with external systems. During an operational handover, the authorization state of materials, actions and requests must be kept clear. Retrieval and forms are not authorization to execute.
