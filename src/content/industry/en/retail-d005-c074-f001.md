# Cross-border resale returns: HTTP integrations for procurement

## What the documents look like

Cross-border return refurbishment and resale handles reverse logistics and item condition, which differs from first-leg replenishment at an overseas warehouse. Source data includes the overseas warehouse WMS, the TikTok return center, Amazon return reports, and inspection photographs. The working documents are the return inspection form, the refurbishment record, the scrap form, and the relisting checklist. The supplied brief gives the update frequency as daily and per batch. In the procurement and supplier records task, purchase orders, supplier profiles, and return inspection conclusions need to be exchanged with external systems. The HTTP module sends a request to the corresponding address and parses the returned values. Grading a return, arranging refurbishment packaging, and deciding between scrap and resale are the three most time-consuming steps, and the field definitions carried into the request determine whether those decisions reach the external system intact.

## Constraints at the HTTP integrations step

The HTTP module sends an `HTTP` request to the corresponding address. Params are path request parameters, Body is the request body, and Headers are request headers; all three can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and preceding node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories; chatId and responseChatItemId do not exist in test mode. The return value configuration describes how to parse the response, extracting values with JSON path. When the output type is set to string, the value for the corresponding key is converted into a json string. The chat interface uses APIKey authentication, recommends passing `body.appId` in the request body, and also supports the `Authorization: Bearer <apiKey>-<appId>` form; the appId priority order is `body.appId`, then `<apiKey>-<appId>`, then the appId associated with the apikey for legacy compatibility. Passed fields such as `model` and `temperature` have no effect because these are determined by the orchestration. Using `authProxy` to proxy a team member identity requires the team owner to enable `authProxy` when creating or editing the key, and the proxied identity still needs permission for the target app and conversation. A `detail=true` response returns intermediate values, and the documented note states that actual consumed Token values are not returned, so `responseData` tokens would need manual calculation.

Hypothetical paper exercise: a cross-border seller's after-sales supervisor is organizing a batch of returns on 10 March 2025. The material text reads: "Return inspection form number RT-0310-07, item is a folding storage box, inspection conclusion is minor surface scratches, status is pending refurbishment; scrap form number SC-0310-02, same item, status is pending review; relisting checklist not yet generated." A draft handover sentence awaiting judgment reads: "RT-0310-07 has completed refurbishment and can be relisted directly." The authorization boundary is that the after-sales supervisor submits the inspection conclusion only; refurbishment execution and the relisting decision belong to another role.

Hypothetical starting point for this exercise: pass the inspection conclusion field of RT-0310-07 into the Body as a variable. This starting point is chosen because that field is the direct input by which the external system judges the refurbishment grade; compare it against the field type declared in the external interface document, with no default value set.

## Three common errors

1. Treating a pending-refurbishment status as completed refurbishment. The inspection form states "status is pending refurbishment," and no refurbishment record appears, yet the draft sentence says "has completed refurbishment." These are mutually exclusive values for the same field, so the claim is unsupported.
2. Treating a scrap form pending review as approved scrap. Scrap form SC-0310-02 has the status "pending review." Pending review does not demonstrate a lack of operating permission and does not equal approval, so the matter remains to be verified.
3. Treating a relisting checklist that has not been generated as ready for relisting. The checklist has not been generated, yet the draft sentence says "can be relisted directly." The checklist subject and status evidence are missing, so this is an evidence gap.

## How to verify the setup

1. Input the RT-0310-07 inspection form text and the draft sentence. Compare the two values "pending refurbishment" and "has completed refurbishment." When mutually exclusive values appear for the same field, judge the claim unsupported.
2. Input the SC-0310-02 scrap form text. Compare "pending review" against any approval wording. When approval wording appears, judge the matter to be verified and keep the evidence gap open.
3. Input "relisting checklist not yet generated" together with the draft sentence. Compare whether the checklist exists. When the checklist is absent, judge the "can be relisted directly" claim in the draft sentence as an evidence gap, and do not supply authorization clauses to close it.

For the external request itself, the address, method, Params, Headers, and Body are checked against the external interface document rather than assumed. The return value configuration is verified by comparing the configured key and JSON path against the documented response example and confirming which value the extraction produces. The authorization boundary stays with the after-sales supervisor's submission of the inspection conclusion; refurbishment execution and the relisting decision remain with another role, and no interface call in this page moves that boundary.
