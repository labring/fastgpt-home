# Creator sales campaigns: HTTP integrations for procurement

## What the documents look like

Creator-hosted sales campaigns depend on external creator fulfillment, so inventory procurement and supplier records span brand commerce staff, MCN agencies, and creator managers. The working materials are creator cooperation agreements, commission setting sheets, sample shipment forms, and live-stream performance reports. These documents determine what an HTTP request sends to an external system and under whose identity it is sent. The category also draws on selected alliance data, creator marketing platforms, creator historical data, and store transaction details as its main data sources. Materials update per campaign and weekly; the interface design accepts that rhythm without implying batch or real-time synchronization mechanisms.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a corresponding address. Params carry path request parameters, Headers carry request headers, and Body carries the request body; all three can reference global variables, system variables, or upstream node outputs through `{{}}`, and the URL also supports variable references. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. The chatId and responseChatItemId values do not exist in test mode, so empty values during debugging are normal and are not business faults. Return values are extracted through JSON path; selecting string as the output type converts the value of the corresponding key into a JSON string. The chat interface authenticates with an APIKey, and calls to `chat/completions` are recommended to pass `body.appId` in the request body. The appId priority order is `body.appId`, then `<apiKey>-<appId>`, then the appId associated with the apikey. Proxying a team member identity through `authProxy` requires the team owner to enable it when creating or editing the key, and the proxied identity still needs permissions for the target application and session. Passed fields such as `model` and `temperature` have no effect because orchestration decides them. Setting `detail=true` returns intermediate values, and tokens must be calculated manually. Retrieval and similarity do not carry authorization or entity isolation duties, and an HTTP call by itself does not constitute authorization.

Hypothetical paper exercise sample: a brand commerce staff member and an MCN agency sign a creator cooperation agreement for a creator-hosted sales campaign. The agreement states the supplier is Supplier A, the sample shipment form number is YP-0312, the commission setting sheet specifies a commission rate of 15%, and the live-stream performance report is pending generation. The commerce staff member plans to submit an inventory procurement handover request to the supplier system through an HTTP interface. The request body contains supplierId, sampleId, commissionRate, and deliveryDate, and the Headers carry Authorization. The request is in a pending-review state and has not received supplier confirmation. The draft sentence under evaluation is: "The supplier has confirmed the inventory procurement quantity and delivery date for this campaign." The materials behind this sentence are only the agreement and the sample shipment form; no supplier confirmation record is present.

## Configuration and implementation checks

| Configuration item | Assumed trial starting point | Reason for choice and comparison method |
| --- | --- | --- |
| Request address | Supplier system interface address | Chosen according to the external interface document; the address can reference provided variables |
| Request method | POST | Consistent with the external interface contract; check whether Body takes effect |
| Headers authentication | Authorization: Bearer {{token}} | Credentials injected through secure configuration; not written into public samples |
| Body fields | supplierId, sampleId, commissionRate, deliveryDate | Check each item against the agreement, sample shipment form, and commission setting sheet |
| Variable source | Global variables and upstream node outputs | Check actual passed values; do not assume default values |
| Return value extraction | JSON path extraction of a specified key | When output type is string, the value converts to a JSON string |

## Three common errors

1. Treating a pending-review handover request as supplier-confirmed. Input is the draft sentence plus the agreement and sample shipment form; the comparison object is whether a supplier confirmation record exists; the observable result is that when the materials contain no confirmation field, the sentence is not supported.
2. Treating the absence of chatId and responseChatItemId in test mode as a business fault. Input is the test-mode return; the comparison object is the documented test-mode behavior; the observable result is that when the fields are missing but the flow runs normally, this is expected.
3. Treating a retrieval or similarity result as an authorization decision. Input is the similarity score returned by the interface; the comparison object is the authorization scope; the observable result is that a high or low score does not change access permission, and retrieval does not constitute authorization.

## How to verify the setup

1. Draft sentence verification: input is the draft sentence above together with the agreement and sample shipment form text; compare whether the draft sentence matches the materials in the same subject, same period, and same field; the observable result is that when the materials do not state supplier confirmation, the sentence is judged unsupported.
2. Request body field verification: input is supplierId, sampleId, commissionRate, and deliveryDate in the Body; compare each field against the corresponding values in the agreement, sample shipment form, and commission setting sheet; the observable result is a pass when fields match, and a recorded difference when they do not.
3. Return value extraction verification: input is the interface response and the configured JSON path; compare the extracted result against the actual response structure; the observable result is a pass when the extracted value matches the corresponding key in the response, and a recorded failure to extract when the path does not match.
