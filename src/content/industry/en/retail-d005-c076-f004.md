# Creator commission settlement: vector indexes for procurement

## What the documents look like

Creator commission settlement and deduction happen after a sale closes. The work centers on confirming valid promotion and on handling post-sale commission deductions. This page addresses one task inside that category: inventory procurement and supplier records. Four document types carry the relevant content: commission setting records, settlement statements, refund deduction details, and invoices. These materials update weekly or monthly, and both the settlement cycle and refund lookback can change the commission basis for the same group of orders at different times.

In the vector model and index step, one settlement statement may correspond to several supplier batches, and one refund deduction may touch several invoices. Data originates from the selected alliance backend, order after-sales data, the finance system, and creator contracts. Those sources do not align their fields by default, so before retrieval begins, the vector model and the input type must be confirmed. Retrieval is not authorization, and a relevance score is not a category, entity, or permission filter. A similarity setting does not exclude unrelated businesses or unauthorized records.

## Constraints at the vector indexes step

Knowledge bases joined in one retrieval must use the same vector model. The actual model and input type are checked first, and bases whose identifiers do not match are excluded. Cross-model retrieval is not run to compare missed recalls. One original data block can carry multiple indexes, and the index content is checked separately from the original text. Index content should be complete and focused; retrieval coverage and index length are weighed against the sample at hand. Image retrieval also depends on whether ingestion generated an image description or image vector, so the query side alone does not decide the outcome.

After a model or index change, the same group of questions is used to compare cited original text. A vector score alone does not support a claim about effect. Semantic recall and relevance do not enforce permission or entity isolation. The same-model requirement for retrieval bases does not extend to external systems such as business registration sites. RRF is a fusion process for mixed results; it is not written as a toggle. Optional paths in the overall flow are not executed on every request: image retrieval needs image input and model capability, and reranking needs a model and must be enabled in settings. The documented unit for the reference cap is tokens.

Hypothetical paper exercise: a settlement specialist needs to check whether one commission setting record and one refund deduction detail point to the same supplier batch. The supplied text for comparison is: "Supplier A, batch 2024-07, commission rate 8%, settlement period 1 July 2024 to 31 July 2024." and "Refund deduction detail: order number T-0912, refund date 3 August 2024, deduction amount 120, related batch 2024-07." One draft sentence to be judged is: "This refund deduction has been deducted from Supplier A's 2024-07 batch commission." This sample only illustrates the checking method and does not represent any real business record.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison method |
| --- | --- | --- |
| Vector model | A text vector model matching the existing base | Check the actual model identifier and input type first; exclude bases whose identifiers do not match |
| Index content | Keep subject, batch, and period for each record | Compare against the full original text to confirm no key field is lost from the index |
| Reference cap | Set a starting point in tokens for this exercise | Compare against cited original text length for the same question group and observe whether needed fields are covered |
| Minimum relevance | Set a starting point between 0 and 1 | Takes effect only in semantic retrieval or with reranking; compare against cited original text |
| Search mode | Hybrid retrieval | Batch and number queries depend on full-text recall; semantic queries depend on vector recall |
| Result reranking | Enable per settings when a model is available | Rerank score is 0 to 1 and is used to compare relevance against cited original text |

## Three common errors

1. Treating the commission rate in a settlement statement as the refund deduction rate. Input: the commission setting record and the refund deduction detail. Compare the batch identifier and period fields in both. Observe whether they point to the same batch and the same period. If the batch identifiers differ, the draft sentence is not supported.
2. Treating a refund deduction detail awaiting review as a completed deduction. Input: the current status of the refund deduction detail. Compare whether it states that the deduction was executed. Observe whether an execution record exists. A detail record alone does not make the deduction complete.
3. Treating a high-similarity record in retrieval results as authorized access. Input: the cited content returned by retrieval. Compare whether it falls within the current operator's accessible scope. Observe whether an out-of-scope record appears. A similarity score does not perform permission filtering.

## How to verify the setup

1. Take the commission setting record and the refund deduction detail from the hypothetical sample above and run retrieval. Compare whether the returned citations include both batch 2024-07 and order number T-0912. If only one appears, check whether the index content is complete.
2. Take the draft sentence "This refund deduction has been deducted from Supplier A's 2024-07 batch commission" and compare it against the status field in the original refund deduction detail. If the original does not state that the deduction was executed, the sentence remains unverified.
3. Take one record that clearly falls outside the current accessible scope and run retrieval. Compare whether the returned results exclude it. If the record is returned, check whether access control is implemented outside the retrieval chain. An empty result can be checked against an explicit paper input of [] for downstream design; a fabricated rule cannot be claimed to always return an empty array.
