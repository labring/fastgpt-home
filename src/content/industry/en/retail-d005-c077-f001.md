# Import and export permits: HTTP integrations for procurement

## What the documents look like

Permit handling takes place before customs declaration and determines whether a shipment may lawfully cross the border. In the inventory procurement and supplier data stage, the work therefore touches business authority systems, customs commodity codes, supplier records and customer end-use statements at the same time. Routine documents include automatic import licences, dual-use item licences, contracts and product descriptions. These materials update irregularly and per shipment. At this step, the HTTP module carries external responses such as licence status, commodity codes or supplier details into the orchestration flow.

The HTTP module sends a request to a configured address. Params carry path request parameters and are common in GET requests. Body carries the request payload and is common in POST and PUT requests. Headers carry request headers used for special information. All three, and the URL itself, may reference variables drawn from global variables, system variables and prior node outputs through the `{{}}` syntax. Return value configuration describes how to parse the interface response, using JSON path syntax to extract values; when the output type is set to string, the value for the corresponding key is converted into a JSON string. Among system variables, `chatId` and `responseChatItemId` do not exist in test mode, so empty values during debugging reflect that mode rather than a business fault. In the chat interface, fields such as `model` and `temperature` are determined by the orchestration and have no effect when passed in. Actual consumed token values are not returned; when needed, set `detail=true` and calculate the `tokens` values inside `responseData` manually. The `interactive` object returned to an external caller contains only `type` and `params`; internal runtime fields are not returned.

## Constraints at the HTTP integrations step

Because permit handling precedes declaration, a procurement flow that calls external systems must keep the distinction between a document that exists and a business action that has occurred. A quotation, an offer, a pending review and a signed contract are separate facts. The HTTP module can transport values between systems, but it does not by itself verify identity, grant permission, approve a request or write to a database. Those steps require their stated downstream implementation. Retrieval and relevance scores do not act as permission or entity filters, and a similarity setting does not exclude unrelated businesses or unauthorized records.

Assumed paper exercise sample: a paper record states that an export enterprise sent a procurement enquiry to a supplier on 10 March 2026 concerning a batch of CNC machine tool spare parts. The supplier replied the same day with a quotation, which states that its validity runs to 31 March 2026, and attaches a product description saying the spare parts are used for general industrial equipment maintenance. On the same day, a customs compliance staff member proposed a draft sentence for review: "The supplier has confirmed supply, so an automatic import licence application can be submitted on this basis." The differences between this sentence and the source wording must be checked item by item.

## Configuration and implementation checks

| Configuration item | Assumed starting value for this exercise | Verification method |
| --- | --- | --- |
| Request address | A variable referencing a prior node output that holds the external interface address | Compare character by character against the address given in the external interface document |
| Request method | Selected according to the external interface document | Compare the method stated in the document with the current configuration |
| Headers authentication | Credentials injected through secure configuration | Check that credentials are not written into public samples or page body text |
| Body structure | JSON organised according to the external interface contract | Compare key names and value types field by field |
| Return value extraction | Key configured per JSON path | Use a response sample to verify that the extracted result matches the expectation |
| Output type | String or original type | Check whether the converted result meets downstream concatenation needs |

These starting values are choices for this exercise, made to allow item-by-item comparison. They do not represent any official default value.

## Three common errors

1. Treating the quotation validity date as the supply period. In the sample, the quotation validity runs to 31 March 2026, while the material states no supply period. These are different fields and cannot substitute for each other.
2. Treating a supplier quotation reply as a supply confirmation. In the sample, the supplier replied with a quotation, and the material records no acceptance of the quotation and no signed contract. The phrase "has confirmed supply" in the draft sentence lacks support.
3. Treating an empty `chatId` in test mode as an interface failure. The documentation states that this field does not exist in test mode, so debugging environment behaviour must be distinguished from production environment behaviour.

## How to verify the setup

1. Input the source wording of the assumed sample and the draft sentence. Compare the phrase "has confirmed supply" in the draft sentence with the quotation reply recorded in the material. When the material contains no acceptance or signing statement, the sentence is unsupported, and the evidence gap should be recorded.
2. Input the quotation validity date of 31 March 2026 and the application submission wording in the draft sentence. Compare whether the two point to the same fact. The validity field does not constitute supply or application authorization, so the item is marked as pending verification.
3. Input a request address variable that references a prior node output. Compare the address actually sent with the address given in the external interface document. When the two match and the return value is extracted successfully using the configured key, that configuration item meets the condition. When extraction returns empty, record the actual observation without inferring a specific error cause.

This page addresses only import and export permit handling, inventory procurement and supplier data, and HTTP integrations with external systems. During operational handover, the authorization status of materials, operations and requests must be kept explicit; retrieval and forms are not authorization to execute.
