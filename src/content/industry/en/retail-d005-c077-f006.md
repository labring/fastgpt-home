# Import and export permits: scheduled workflows for procurement

## What the documents look like

Permit handling occurs before customs declaration, and it determines whether goods can be imported or exported lawfully. That front-loaded position shapes the procurement and supplier material used at this step. The main data comes from commerce authority systems, customs commodity codes, supplier material and customer end-use statements. The working documents are automatic import licences, dual-use item licences, contracts and product descriptions. The most time-consuming activities are judging which regulatory document applies, preparing the end-use statement and following the approval status. These records update irregularly, per shipment, so a scheduled job reads external data only through an interface that has been configured; a trigger does not by itself create a connection to a business system.

## Constraints at the scheduled workflows step

Trigger responsibility must be stated: whether the application scheduling capability fires the job or an external scheduler does, checked against the entry points available in the actual version. An HTTP request is checked against the external interface documentation for method, headers, body and variable inputs. URL, Params, Headers and Body can each reference variables through `{{}}`, drawing on global variables, system variables or upstream node output. Return values are parsed with JSON path syntax. Output formatting was added after v4.6.8; when the output type is set to string, the value at the corresponding key is converted to a JSON string.

Hypothetical paper exercise. On 10 March 2025 a foreign trade compliance role receives an automatic import licence application. The material reads: "Supplier A submitted on 8 March 2025 a product description within the dual-use export control list, contract number HT-2025-031; the customer end-use statement records use for testing equipment; the application status is recorded as materials accepted." The proposed handover request reads: "Have the scheduled job automatically write to the procurement inventory table and synchronise supplier material once the approval status becomes approved." That status change is a business action requiring downstream implementation; the scheduled job does not produce an approval outcome.

| Configuration item | Assumed starting point for this exercise | Reason and comparison method |
| --- | --- | --- |
| Trigger mode | External scheduler fires once after each shipment submission | Check the trigger entry against the interface documentation; compare whether the application scheduling capability provides it |
| Request method | POST | Check against the external interface documentation; distinguish from GET read scenarios |
| Headers | Authorization as Bearer `{{token}}` | Check the header against the interface documentation; compare whether the token source is a global variable |

| Output key | `data.user.name` | Check against JSON path rules; compare whether the output type is string |
| Execution record | Record trigger time, actual input, returned result and business status | Check the difference between a task existing and a task succeeding |

## Three common errors

1. Treating retrieval results as an authorization basis. The same-vector-model requirement for knowledge bases applies to association between those bases. It does not extend to requiring the same model for a commerce authority site or another external system, and a relevance score is not a permission or entity filter.
2. Treating a pending review status as missing operating permission. In the exercise the application status is materials accepted, with no approval recorded, so the item is unsupported or awaiting verification rather than negative or contradictory.
3. Treating a scheduled trigger as a completed business write. The exercise request asks for a write to the inventory table and a supplier material synchronisation after approval. Approval, writing and synchronisation are three distinct facts and need downstream interface implementation.

## How to verify the setup

1. Input the exercise source text and the proposed sentence. Compare whether the application status field records approved. The expected observation is an unsupported result; an output asserting approved does not meet the condition.
2. Input the exercise request. Compare whether the request contains an action to write automatically after approval. The expected observation is a note that downstream implementation is required; an output stating synchronisation is complete does not meet the condition.
3. Input a paper input of an empty result `[]`. Compare whether the downstream design accepts an empty result. The expected observation is a no-record notice; returning an empty result under a fabricated rule does not meet the condition.
