# Chain-store site selection: workflow routing for procurement

## What the documents look like

Site selection and store opening work happens before a store begins trading, and its core is lease negotiation and engineering delivery. The four document types that feed procurement and supplier records are the site evaluation form, the lease letter of intent, the decoration budget, and the opening schedule. The decoration budget determines the procurement categories and quantity ranges. The opening schedule determines supplier delivery milestones. The lease letter of intent and the site evaluation form constrain whether the opening proceeds at all. These materials are often in intermediate states such as drafted, awaiting signature, or awaiting review. Workflow routing has to carry those states forward honestly, and a pending item is not an approval.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the required fields and submits, the collected information is passed to subsequent nodes. The User Selection node is also a user interaction node. When it triggers, the conversation enters an interaction state, and after the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. Interaction nodes only collect values and evaluate branches. Order writing, document backfill, and external status synchronization require a separately connected business interface or a later process. Retrieval results supply candidate information and do not constitute authorization. A relevance score is not a category, entity, or permission filter, and retrieval is not authorization.

Hypothetical paper exercise sample. A chain headquarters expansion department submits a draft opening schedule with this text: "Store A opening schedule is decoration budget confirmed; lease letter of intent status is awaiting landlord signature; first batch of shelf procurement quantity awaiting confirmation by the engineering manager." The same submission contains a request to be judged: "Please start the shelf procurement order based on the signed lease letter of intent." When checking this request, the subject is the expansion department, the object is Store A shelf procurement, and the status field reads "awaiting landlord signature." That status has not reached signed, so the "signed" wording in the request does not match the source text. The procurement order must not be started on this basis. The item is recorded as an evidence gap and remains pending the signing event.

## Configuration and implementation checks

| Configuration item | Type | Description |
| --- | --- | --- |
| Form Input node | Official node | Enters the interaction state when triggered, collects required information, and passes it to subsequent nodes after submission |
| User Selection node | Official node | Executes the corresponding "yes" branch after the user makes a choice; verify each branch connection individually |
| Interaction state check | Implementation check | Confirm that the recorded state is the behavior of the interaction node; do not add or claim a separate global state-recording switch |
| Output handoff check | Implementation check | Confirm that collected information is explicitly passed to the subsequent retrieval, judgment, or interface node, comparing input and output item by item |
| Procurement order interface | Requires separate implementation | Order writing and external status synchronization need a separately connected business interface or a later process |
| Hypothetical trial starting value | Hypothetical starting value for this exercise | Use "awaiting landlord signature" as the initial check value for the schedule status field, compared word by word against the source text; this is not an official default |

## Three common errors

1. Treating a lease letter of intent that is awaiting landlord signature as signed, and starting the procurement order on that basis. The input is the draft schedule text; the comparison is between the status field "awaiting landlord signature" and the "signed" wording in the request; when the two do not match, the order must not be executed.
2. Treating a relevance score returned by retrieval as a permission filter, on the view that a high-scoring result is accessible. The input is the retrieval result list; the comparison is between the owning subject of the record and the subject of the current request; a score does not perform entity isolation.
3. Treating a procurement quantity collected by the Form Input node as a confirmed value and writing it directly into an order. The input is the submitted form value; the comparison is against the engineering manager's confirmation record; when the confirmation record is absent, the value remains unverified.

## How to verify the setup

1. Input the hypothetical sample source text and the request to be judged; compare the "signed" wording in the request against "awaiting landlord signature" in the source; observe whether the case is recorded as an evidence gap and the pending-signature status is retained. The condition is met when the procurement order is not started.
2. Input an explicitly empty retrieval result, written as `[]` on paper; compare whether the downstream node handles it through the empty-result branch; observe whether any unsupported procurement action appears. The condition is met when the downstream produces no order write.
3. Input the procurement quantity submitted through the form together with the missing engineering manager confirmation record; compare whether both are present at the same time; observe whether the order interface is called. The condition is met when the order interface is not called while the confirmation record is missing.

These checks describe expected behavior, not results that have been observed or tested. Where a document field is not provided, the value remains unknown.
