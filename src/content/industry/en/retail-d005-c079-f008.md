# Central chain procurement: workflow routing for procurement

## What the documents look like

Central chain procurement and distribution covers headquarters purchasing and outbound delivery to stores. It does not inspect store display or shelf execution, which separates this category from price and display auditing. The working materials are centralized procurement contracts, replenishment plans, distribution orders, and store requisitions. Source data arrives from ERP purchasing, WMS, store POS, and supplier delivery records. The people involved are the chain supply chain center, purchasing managers, and the distribution center. Errors here surface as store stockouts, excess inventory, or supplier claims.

Workflow routing in this step connects store requisitions, replenishment plans, and supplier delivery records into a sequence that can pause for user input, be compared, and be handed off. The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution waits until the user completes the interaction. After the user fills the required fields and submits, the node collects the submitted values and passes them to later nodes. The User Selection node is also a user interaction node. When it triggers, the same interaction state applies; when the user makes a choice, the node evaluates that choice and executes the corresponding branch.

## Constraints at the workflow routing step

Interaction nodes collect and pass information. They do not perform order writes, document backfill, or external status synchronization. Those business actions require a separate business interface or a downstream flow. Semantic recall and relevance scores in a retrieval library do not enforce permission or entity isolation, and a retrieval result is not a basis for authorized execution. Values collected by a form still need business verification, approval, or a downstream implementation before they can affect purchasing or distribution actions.

Hypothetical paper exercise. A chain supply chain center receives a store requisition reading: "Store A requests replenishment of item X, quantity 200 units, request date 10 March 2025, approval status pending review." A centralized procurement contract reads: "Supplier B signed a centralized procurement contract for item X with headquarters, contract valid until 31 December 2025, supply scope covers Store A." A handoff request awaiting judgment reads: "Based on Store A's requisition and the centralized procurement contract, generate the distribution order directly and notify Supplier B to ship." In this exercise the requisition approval status is pending review, and the contract states only the supply scope; it does not state that this replenishment has been approved. A pending status is not approval. A valid contract is not authorization for this specific delivery. Generating a distribution order and notifying a supplier are business actions and need a defined authorization boundary and a downstream implementation.

## Three common errors

1. Treating a pending-review status as approved. In the exercise, the requisition approval status is pending review. If a distribution order is generated directly, the input is the pending-review status, the comparison object is a completed approval status, and the observable result is a distribution order created while approval is incomplete.

2. Treating contract supply scope as authorization for this delivery. In the exercise, the centralized procurement contract states only that it covers Store A and does not state that this replenishment has been approved. If Supplier B is notified to ship directly, the input is the contract supply scope, the comparison object is the authorization record for this delivery, and the observable result is a notification sent while the authorization record is absent.

3. Treating retrieval or form collection as authorized execution. In the exercise, after the Form Input node collects the replenishment information, if an external interface is triggered directly to write an order, the input is the collected form value, the comparison object is the business approval or interface authorization status, and the observable result is an order write occurring while approval is missing.

## How to verify the setup

1. Against the exercise text "Store A requests replenishment of item X, quantity 200 units, request date 10 March 2025, approval status pending review," check whether the workflow places a manual review branch after the Form Input node. The input is the pending-review status, the comparison object is a completed approval status, and the condition is met when the workflow pauses in the interaction state and waits for the approval result before entering the distribution step.

2. Against the exercise text "Supplier B signed a centralized procurement contract for item X with headquarters, contract valid until 31 December 2025, supply scope covers Store A," check whether the output handoff compares contract information against requisition details item by item. The input is the contract supply scope and the requisition line items, the comparison object is the authorization record for this delivery, and the condition is met when a clear authorization basis exists before the distribution order is generated.

3. Against the exercise request "Based on Store A's requisition and the centralized procurement contract, generate the distribution order directly and notify Supplier B to ship," check whether the external action separation routes this request to a business interface or downstream flow. The input is the handoff request text, the comparison object is the external action nodes configured in the workflow, and the condition is met when generating the distribution order and notifying the supplier are carried by the downstream implementation and the interaction node does not execute these actions directly.
