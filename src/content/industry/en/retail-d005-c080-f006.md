# Store price and display checks: scheduled workflows for procurement

## What the documents look like

Price and display checks for chain stores take place during ordinary trading periods, where the operational focus is sustained execution of standards rather than one-off launch support. The material set for this category comes from supervision systems, POS price lists, in-store cameras and head office promotion calendars. Daily documents include store visit photographs, price tag lists, display standards and rectification notices.

For the procurement and supplier records task, price tags, display arrangements, purchase sources and supplier records are checked together to judge whether store execution matches the head office promotion calendar. Data updates on weekly and monthly cycles. This page does not derive batch synchronisation, full synchronisation, real-time or transaction-triggered mechanisms from that update frequency.

## Constraints at the scheduled workflows step

Scheduled workflows on this page mean that an application scheduling capability or an external scheduler triggers an HTTP module, which sends a request to a configured interface to read or submit procurement and supplier records. The HTTP module can be added repeatedly, configured manually and triggered to execute. Requests can carry Params, Headers and Body, and can reference global variables, system variables and upstream node outputs through `{{}}`. External data is read by a configured interface. A scheduled trigger by itself does not establish a connection to a business system. Deduplication, idempotency and business writes require explicit design in the interface or in downstream flows. Execution records should be checked against trigger time, actual input, returned result and business status.

Hypothetical paper exercise. A chain operations department plans a paper-based check of price tags and supplier records for 12 stores in the East China region on 10 March 2026. The supplied source wording is: "The price tag list for Store A shows a certain beverage priced at 6 yuan, and the head office promotion calendar states that this beverage runs at 5 yuan from 1 March to 15 March." A draft sentence awaiting judgement reads: "Store A has completed the price rectification according to the promotion calendar." That draft sentence carries no signed rectification notice and no supervisor confirmation, so it remains unverified.

## Configuration and implementation checks

| Configuration item | Purpose on this page | Basis or checking method |
| --- | --- | --- |
| Trigger entry | Determine whether the application scheduling capability or an external scheduler initiates the run | Check available entries against the actual version; do not assume an automatic business system connection |
| Request method | Match the external interface documentation | Check GET, POST, PUT and DELETE against the interface documentation |
| Headers | Carry Authorization, token and similar values | Variables can be referenced with `{{token}}`; complete fields per interface requirements |
| Body | Request body for POST/PUT, referencing upstream node output | Strings require `""`; arrays and objects follow the documented form |
| Return value extraction | Use `key` to take fields by JS object access rules | For example `data.user.name`; output type can be set to string |
| Execution record | Check trigger time, input, return and business status | Task existence does not replace successful execution; compare the actual return manually |

## Three common errors

1. Treating a scheduled trigger as an established business system connection. Input: the scheduled task configuration. Comparison: whether an interface is configured and returns successfully. Observable result: the return body contains the expected fields; where no interface is configured, the read result is empty and remains unsupported by evidence.
2. Treating retrieval or a form as authorised execution. Input: the handover request. Comparison: the authorisation boundary stated in the request against whether the rectification notice is signed. Observable result: a pending review does not demonstrate a lack of operating permission; signing, reaching cooperation and contract effectiveness are three distinct facts.
3. Treating a similarity or relevance score as a permission or entity filter. Input: the retrieval query. Comparison: whether the subject of each returned record matches the target store. Observable result: relevance does not perform permission or entity isolation; identifiers must be checked separately and non-matching records excluded.

## How to verify the setup

1. Use the hypothetical source wording above to check the draft sentence. Input: the two sentences "Store A price tag 6 yuan" and "calendar 5 yuan". Comparison: the same store, the same period, the same price field. Observable result: where two mutually exclusive values hold for that field at the same time, a difference requiring verification can be identified. The draft sentence "rectification completed" remains unsupported because no signed rectification notice and no supervisor confirmation are attached.
2. Use one paper input to check the downstream design. Input: an explicit empty result `[]`. Comparison: whether the downstream flow handles the empty-result branch. Observable result: empty-result handling can be checked with paper input; no claim is made that a fictional rule retrieval necessarily returns `[]`.
3. Check the execution record. Input: trigger time, request body and return body. Comparison: whether returned fields match the business status. Observable result: where the return body contains `message` or `data` fields, check them against the documented extraction rules; where no success status is observed, record the gap.

This page addresses only chain store price and display checks, procurement and supplier records, and scheduled workflows. During operations handover, the authorisation status of materials, operations and requests must be established; retrieval and forms do not constitute authorised execution.
