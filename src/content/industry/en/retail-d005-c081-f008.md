# Chain-store closure accounts: workflow routing for procurement

## What the documents look like

Chain-store closure settlement handles exit and asset recovery, the reverse direction from head-office site selection and store opening. The records relevant to this page come from POS inventory, the fixed-asset system, lease contracts and the finance ledger. The everyday documents are closure approvals, inventory clearance notes, lease termination agreements and asset count sheets. Updates are irregular, once per store.

For inventory procurement and supplier records in a closure setting, the material takes the form of quantities and purchase origins for goods awaiting clearance, unsettled amounts owed to suppliers, and requests for return or markdown handling. These records determine which fields the workflow must collect and who confirms them, and in which state.

A hypothetical drill sample is used throughout this page. The source text made available for checking reads: "Inventory clearance note number QD-001, store M-12, goods batch B-07, 120 units, supplier S-3, purchase unit price 18 yuan, submission date 10 March 2025; this batch has not been returned, and the unsettled amount awaits finance verification." A proposed handover request reads: "Please return the 120 units of batch B-07 to supplier S-3 under QD-001 and settle the amount." The request names a subject, an object, a quantity and a date scope. The source text does not state return authorization or settlement authorization, so the authorization boundary remains unknown.

## Constraints at the workflow routing step

The Form Input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the workflow continues downward after the user completes the interaction. Once the user fills in the required information and submits, the node collects the form values and passes them to later nodes. The User Selection node is also a user-interaction node. When the user makes a choice, the node evaluates that choice and executes the corresponding branch. Both nodes can be added repeatedly and trigger execution.

The constraint is that the interaction state only means waiting for a user action. It does not represent any business authorization. Values collected by a form must be explicitly passed to a later retrieval, judgment or interface node. Order writing, document backfill and external status synchronization require a separate business interface or a later process. Retrieval does not constitute authorization, and a similarity setting does not exclude unrelated business records or unauthorized records.

In the drill sample, QD-001 records batch B-07 and 120 units but no authorization. A submission that carries these values to a later node completes information collection only.

## Configuration and implementation checks

| Configuration item | Type | Use on this page and how to check it |
| --- | --- | --- |
| Form Input node | User interaction | Collect clearance note number, store, batch, quantity and supplier; pass values to later nodes after submission |
| User Selection node | User interaction | Offer return, markdown or hold as choices; execute the corresponding branch |
| Required-field setting | Node field | Set number, batch and quantity as required; an incomplete entry leaves the interaction unfinished |
| Downstream receiving node | Retrieval or interface | Pass form values to a retrieval or business interface; writing requires a separate implementation |
| Interaction-state check | Implementation check | Confirm the node enters the interaction state and records state after triggering; no global switch is set |

Hypothetical trial starting point: set the required fields to number, batch and quantity. The reason is that these three form the smallest set for checking the subject and the object. Compare against a control input that supplies only the number, and observe whether a missing item still proceeds to post-submission passing. This is a hypothetical starting point for this page, not an official default value.

## Three common errors

1. Treating form submission as return or settlement authorization. In the sample, QD-001 states the batch and the quantity only. No authorization is stated, and the submission action completes information collection alone.
2. Treating execution of a user-selection branch as a completed business action. Choosing the return branch only runs that branch. Return writing and external synchronization require a separate interface.
3. Treating a retrieval hit as permission to act. A relevance score is not a permission or entity filter. A hit on QD-001 does not mean settlement against S-3 may be carried out.

## How to verify the setup

1. Enter the sample source text and the proposed handover request. Compare whether the required form fields cover number, batch and quantity. Observe whether a missing item leaves the interaction at this node, and whether values are passed to later nodes after submission. The expected result is that a missing item leaves the interaction unfinished.
2. Enter the return branch of the User Selection node. Compare the branch connection with the downstream receiving node. Observe whether the choice executes only that branch without triggering a write. The expected result is that branch execution is not the same as business execution.
3. Enter a paper input of [] for the empty-result receiving case. Compare how the downstream design handles the empty value. Observe whether a record is fabricated. The expected result is that an empty input stays empty, and no claim is made that retrieval must return [].

All three checks address form collection and branch passing. They have not been run. Authorization, settlement and return status remain unverified, and the parts the source text does not state remain missing.
