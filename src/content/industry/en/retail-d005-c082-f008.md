# Returned-goods inspections: workflow routing for procurement

## What the documents look like

Returned-goods inspections at the warehouse handle reverse parcels and product grading. They do not handle outbound picking and packing for new orders. The main data sources are the WMS returns module, platform after-sales records, carrier return parcels, and the inspection bench. Daily materials include the returned-goods receipt, inspection photos, the grade determination table, and the resale listing form. These materials update per item and per day.

For the inventory procurement and supplier records task, workflow routing has to connect the supplier fields on the returned-goods receipt, the conclusion on the grade determination table, and the disposition result on the resale listing form, so that procurement and supplier records can be checked against them. The reverse flow means the supplier field carried on a return is the anchor for that check, while the grade conclusion determines whether a resale listing form exists at all. A routing design that treats the presence of a resale listing form as proof of receipt, or that treats a grade conclusion as an authorization to write inventory, crosses a boundary this category does not cross.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the dialog box is hidden. The user fills in the required information and submits, and the node collects the submitted form values and passes them to later nodes. The user selection node is also a user-interaction node. It triggers the same interaction state, and when the user makes a selection, the node evaluates that selection and executes the corresponding "yes" branch. Both behaviors are existing node behavior. No separate global state-recording switch is documented, and none should be described.

Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Form collection by itself is not an authorization. Retrieval is not authorization either.

Hypothetical paper exercise sample. A returned-goods receipt reads: "Return number R2024-0871, supplier code S-331, product batch B2405, inspection conclusion: resalable, resale listing form generated." A pending handoff request reads: "Please have the workflow mark this return as received into stock directly and synchronize the supplier records." The receipt does not state a received-into-stock status for this return. Synchronizing supplier records is an external operation. The workflow can collect and pass form values; it cannot write the receipt status or perform the external synchronization on the strength of the form submission.

## Configuration and implementation checks

| Configuration item | Material on this page | Setting or check method |
| --- | --- | --- |
| Form input node | Return number, supplier code, batch on the returned-goods receipt | Set these three as required fields; after submission, pass them to later nodes |
| User selection node | Inspection conclusion: resalable or not resalable | Connect the "yes" branch according to the conclusion; verify each branch connection item by item |
| Interaction state check | Conversation enters interaction state after trigger | Check this node behavior; no separate global state switch is documented |
| Output handoff check | Grade determination table conclusion and resale listing form | Compare the output against the input item by item |
| External operation split | Receipt write, supplier record synchronization | Mark as requiring a separate business interface; not executed by the form |
| Hypothetical trial starting point | Condition for generating the resale listing form | This exercise starts from an inspection conclusion of resalable, compared against a not-resalable conclusion |

## Three common errors

1. Treating a form submission as an authorization to receive stock. Input: the returned-goods receipt text, which states a resalable conclusion and a generated resale listing form. Comparison object: the "received into stock" field in the handoff request. The material does not state that field, so the result is recorded as unsupported.
2. Treating a user selection branch as execution of an external synchronization. Input: the handoff request. Comparison object: the supplier record synchronization action. The material does not state a synchronization interface or an authorization, so the result is recorded as requiring a separate business interface.
3. Treating the interaction state record as a global state switch. Input: the node behavior description. Comparison object: whether a global state switch exists. The documents do not describe such a switch, so the result is recorded as unknown.

## How to verify the setup

1. Check the form input node against the hypothetical receipt text. Input return number R2024-0871, supplier code S-331, and batch B2405. Compare whether the form sets all three as required and passes them to later nodes. The expectation is met when the later node receives these three values after submission.
2. Check the user selection node against the hypothetical inspection conclusion. Input a conclusion of resalable. Compare whether the "yes" branch connects to the node that receives the generated resale listing form. The expectation is met when the branch connection matches the conclusion.
3. Check the output handoff against the hypothetical handoff request. Input the request sentence asking the workflow to mark the return as received into stock and synchronize supplier records. Compare whether the material states a received-into-stock status and a synchronization interface. The material states neither, so record both as pending verification, without judging them completed or rejected.
