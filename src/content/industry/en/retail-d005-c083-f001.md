# Store counts and loss control: HTTP integrations for procurement

## What the documents look like

Store count and loss control work concerns book-to-physical variance and shrinkage. It does not settle supplier payables. The records that move through this work are count sheets, variance analyses, loss-report approvals and camera review logs. Upstream data arrives from POS inventory, WMS, camera systems and the SB/T count specification. The procurement and supplier records step takes purchase orders, supplier master data and count variance results and sends them over an HTTP interface to an external system so that loss prevention, store inventory staff and finance audit can compare them. The brief states monthly or quarterly update frequency. The supplied documents do not describe batch synchronization, full synchronization or real-time triggering, so those mechanisms remain unstated here.

The HTTP module sends a request to a corresponding address. Params carry path request parameters and appear mostly in GET requests. Body carries the request body and appears mostly in POST and PUT requests. Headers carry special information. URL, Params, Body and Headers can each reference variables with `{{}}`. Variables come from global variables, system variables and preceding node outputs. Return values are extracted by JSON path, and when the output type is set to string the value at the corresponding key is converted into a JSON string. Among system variables, chatId and responseChatItemId do not exist in test mode, so an empty debug value is not a business fault. In the chat interface, fields such as model and temperature are ineffective because the orchestration decides them. Retrieval and forms collect values; business verification, approval, database writes and external synchronization each need their own downstream implementation.

## Constraints at the HTTP integrations step

A hypothetical drill sample is used below. It is a paper case, not a real record, and no request in it has been executed.

The source text under review is a count variance analysis sheet with these lines: "Store number M-102, count period March 2024, variance SKU SKU-4471, book quantity 80, physical quantity 74, variance reason pending investigation, loss report approval status pending review." The draft handover request reads: "Push the variance quantity of 6 units for SKU-4471 to the external loss prevention system through the HTTP interface and complete the loss report." In this request the loss report approval remains pending review. Pending review does not constitute approval, and an interface push does not replace the approval action.

Several constraints follow. The request address and method must match the external interface document character by character, and the address may reference an already provided variable. Authentication credentials are injected through security configuration and are not written into public samples. Body structure must be compared field by field against the external interface contract. String variables referenced in Body must carry quotation marks, while numbers are inserted without them. A return value extraction path must exist in the actual response structure before the extracted value can be used. A similarity score is not a category, entity or permission filter, and retrieval is not authorization.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Reason and comparison method |
| --- | --- | --- |
| Request address | Address supplied by the external loss prevention system, including path parameters | Determined by the external interface document; compare character by character with that document |
| Request method | POST | Variance records are sent in the request body; compare with the method declared in the external contract |
| Header authentication | Authorization set to Bearer plus credential | Credential injected by security configuration; compare with the interface document requirement |
| Body structure | Fields for store number, count period, SKU and variance quantity | Compare each field name against the external interface contract |
| Variable reference | Variance quantity taken from the preceding node output | Check that the passed value matches the source text figure of 6 units |
| Return value extraction | Acceptance status field extracted by JSON path | Compare with the response example structure and confirm the path exists |

The values above are hypothetical trial starting points for this page. They are not official default values.

## Three common errors

1. Treating a pending loss report approval as approved and triggering the HTTP push. The check input is the source text line "loss report approval status pending review." The comparison object is the approval status field. The observable result is that the field still reads pending review, so the push action lacks an approval basis.
2. Referencing a string variable in Body without quotation marks, which breaks JSON parsing. The check input is a Body declaration that references variance reason text. The comparison object is the final parsed result. The observable result is a truncated string or an abnormal structure.
3. Reading an empty chatId in test mode as an interface fault. The check input is a request made in test mode. The comparison object is the chatId system variable value. The observable result is that this value does not exist in test mode, which the documents describe as normal.

## How to verify the setup

1. Input the hypothetical sample source text and the draft handover request. Compare the loss report approval status field against the condition for the push action. The condition is satisfied when that field is clearly approved before the push; otherwise record the evidence gap.
2. Input the Body declaration and the hypothetical variable values. Compare the final parsed result against the external interface contract fields. The condition is satisfied when strings carry quotation marks, numbers do not, and field names match.
3. Input the interface response example and the configured return value extraction path. Compare the extracted result against the response structure. The condition is satisfied when the extraction path exists in the response and the output type matches the expectation; when the path does not exist, record it as unsupported.
