# Store counts and loss control: scheduled workflows for procurement

## What the documents look like

This page covers stock procurement and supplier records in the store count and loss control category, with scheduled workflows applied to the handover and reconciliation of four document types: count sheets, variance analyses, loss report approvals, and monitoring access records. The category tracks book-to-physical differences and shrinkage. Supplier accounts payable sit outside this scope, so procurement records serve here as proof of receipt and as the reference for quantities arriving at the store.

Data comes from POS inventory, WMS, monitoring systems, and count standards. Update frequency is monthly or quarterly, and scheduled triggers can follow that rhythm without being designed per order or in real time. Typical roles are the loss prevention department, store warehouse keeper, and financial auditor. The consequences of error are inventory distortion, inflated gross margin, and employee fraud, which is why every trigger should retain reviewable input and return records.

A hypothetical paper exercise sample is used throughout. A supermarket loss prevention department prepares a "Count Variance Sheet" for a March 2025 closing count. The body states: "Store number A-017, count date 31 March 2025, SKU-8842 book quantity 120 units, physical count 113 units, variance 7 units, status pending verification." From the same batch, a "Loss Report Approval Form" states: "SKU-8842 loss report 7 units, approval status pending review, submitted by warehouse keeper Li." One draft sentence to be judged reads: "The 7-unit variance on SKU-8842 has been confirmed by the loss report approval and can be written to the inventory adjustment." Comparing that sentence against the source text: the approval form status is pending review and records no confirmation result, so the sentence is not supported.

## Constraints at the scheduled workflows step

Trigger responsibility must be explicit. Whether the application's own scheduled capability or an external scheduler initiates the run should be checked against the actual version's available entry points. The existence of a workflow does not mean it runs automatically. External data is read through an already configured interface; a scheduled trigger by itself does not establish a connection to a business system.

HTTP requests should be checked against the external interface documentation for method, headers, body, and variable input. Both the URL and the body can reference variables through `{{}}`, drawing on global variables, system variables, or upstream node outputs. Deduplication, idempotency, and business writes need explicit design in the interface or a downstream workflow and are not automatically present. Execution records should be checked for trigger time, actual input, return result, and business status. A task existing does not equal a successful execution.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason for the choice and comparison method |
| --- | --- | --- |
| Trigger time | 1 April 2025, 09:00 | The count is completed after the 31 March closing; used to check whether trigger time is later than the count date |
| Request method | POST | Check against the external interface documentation to confirm the method matches |
| Request body fields | Store number, count date, SKU, book quantity, physical count | Compare field by field against the count sheet source text; record missing items as gaps |
| Variable references | `{{appId}}`, `{{token}}` | Check against the documented system variable descriptions whether the references resolve |
| Return value extraction | `data.user.name` | Check the extraction key against the response structure using the JSON path rules |
| Execution record fields | Trigger time, return result | Check separately from business status; one does not substitute for the other |

The values in this table are starting points for this hypothetical exercise and are not official defaults.

## Three common errors

1. Treating "pending review" on the Loss Report Approval Form as a completed approval and writing the variance quantity directly into the inventory adjustment. The input is the approval form source text, the comparison is the approval status field, and the observable result is that the status remains pending review.

2. Treating a configured scheduled task as a connected external interface. The input is the task configuration, the comparison is the return result in the execution record, and the observable result is that the return result is empty or missing.

3. Mixing the return value extraction key with the interface response structure. The input is the extraction key `data.user.name`, the comparison is the response JSON path, and the observable result is that the extracted value does not correspond to the expected field.

## How to verify the setup

1. Compare the Count Variance Sheet source text in the hypothetical sample against the draft sentence. The input is the variance sheet and the loss report approval form source text. The comparison is between "pending verification" and "pending review" in the sources and "confirmed" in the draft sentence. The observable result is that the draft sentence is not supported, and the evidence gap must be retained.

2. Compare the trigger time against the count date. The input is the trigger time of 1 April 2025, 09:00 and the count date of 31 March 2025. The comparison is the order of the two dates. The observable result is that a trigger later than the count date satisfies this item.

3. Compare the return value extraction. The input is the extraction key `data.user.name` and the response example. The comparison is between the extracted result and the fields under `data.user`. The observable result is that the extracted value corresponds to the correct field. When the response is empty, record an empty result and do not infer a failure cause.
