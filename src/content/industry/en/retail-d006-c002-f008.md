# MCN operations: workflow routing for staff training

## What the documents look like

MCN operations manage long-term account compliance for multiple creators rather than serving a single brand session. The materials that reach a workflow routing step are creator signing contracts, training records, violation handling forms and account schedules, drawn from the MCN back office, platform violation notices, creator account data and the contract ledger. Daily and weekly updates coexist, so a routing design that assumes one refresh rhythm will misread the other.

For store service and internal training, the practical question is whether a given training session covers a given creator and whether a given contract is inside its stated period. Those answers live in the source materials. Workflow routing connects collection, human confirmation and downstream action; whether collected values are usable downstream depends on whether they are explicitly passed to a retrieval, judgement or interface node.

Two interaction nodes matter here. The form input node enters an interaction state when triggered, records the workflow state, and after the user completes required fields and submits, collects the submitted information and passes it to later nodes. The user selection node also enters an interaction state; when the user makes a choice, the node evaluates the choice and executes the corresponding "yes" branch. Both nodes collect information and route branches. Order writes, document backfill and external status synchronization require a separate business interface or later process.

## Constraints at the workflow routing step

Retrieval results do not constitute authorization. A similarity setting does not perform permission or entity isolation, and it does not exclude unrelated businesses or unauthorized records. Libraries built on different vector models cannot be associated together; check the identifiers first and exclude non-matching libraries rather than running a cross-model comparison to reason about missed recall.

Optional paths shown in an overall flow diagram do not mean every request executes all of them. Image retrieval requires an image input and model capability, and reranking requires a model and must be enabled according to its settings. An empty result can be handled by checking downstream design against an explicit paper input of an empty list; this does not assert that any retrieval must return an empty result.

The interaction state, state recording and hidden dialogue box are documented behaviours of these interaction nodes. No separate global state-recording switch, submission-count rule, automatic judgement or snapshot guarantee is documented, and none should be assumed. A pending request is not an approval, an offered option is not execution, and an unsigned termination is not a completed termination. Where a document field is not provided, the value is unknown.

## Configuration and implementation checks

The table below covers the main task of checking store training materials. Values are hypothetical starting points for this exercise, not official defaults.

| Configuration item | Hypothetical starting point | Reason and comparison method |
| --- | --- | --- |
| Required form input fields | Creator name, training session, contract number | Compare word by word against the training record; record a gap when a field is absent |
| User selection branch | Yes branch points to a training confirmation node | Inspect the branch connection and confirm the choice reaches the intended later node |
| Information passing target | Explicitly passed to a later judgement node | Compare each node output with the downstream input for consistency |
| Retrieval scope | Limited to target libraries with access rights | Check library identifiers and vector model identifiers, excluding non-matching ones |
| Empty result handling | Paper input of an empty list checked against downstream design | Observe whether downstream design handles empty input; do not claim an empty result must return |
| External operation split | Separate business interface | Check whether writes and synchronization have an independent implementation; do not assume automatic triggering |

## Three common errors

1. Treating form submission as completed authorization. The form input node collects required information and passes it to later nodes; the submission action produces no approval or execution effect. To check, supply one training record text and one pending request, compare whether the request contains an approved wording, and observe whether the material carries an approval field; when the field is absent, record it as pending verification.

2. Treating a user selection branch connection as business confirmation. The user selection node executes the "yes" branch, which indicates flow direction only, not contract effectiveness or a concluded partnership. To check, supply the selection result and the contract ledger text, compare the contract status field with the selection action, and observe whether separate evidence of signing or effectiveness exists; when absent, keep the evidence gap open.

3. Treating a retrieval hit as permission filtering. A similarity setting does not exclude unrelated businesses or unauthorized records. To check, supply one retrieval query and a library identifier, compare returned records with the target library scope, and observe whether any cross-model library association occurs; when it does, exclude it and record the actual observation.

## How to verify the setup

Hypothetical exercise sample: the source material reads "Creator A attended store service training in March 2025; the sign-in sheet records attendance and the assessment result is pass; contract number HT-001, contract period January 2025 to December 2025." The draft sentence to be judged reads "Creator A has completed training, the contract is valid, and the next store service session can be scheduled." The source contains the subject, object, period and assessment status.

- Verification one: input the source text above and the draft sentence, compare "the contract is valid" in the draft with the contract period field in the source, and observe whether the source records effectiveness or an approval record; when it does not, the sentence is unsupported and the gap remains.

- Verification two: input the source text above and a handover request reading "please schedule Creator A's next store service session directly," compare the execution action in the request with the training and contract fields in the material, and observe whether a scheduling authorization or approval record exists; when absent, record it as pending verification rather than as a negative finding.

- Verification three: input a paper empty result of an empty list and the downstream node design, compare whether downstream explicitly handles empty input, and observe whether the downstream design requires manual supplementary entry; the condition is met when a downstream path for empty input exists, without claiming that any retrieval must return an empty list.
