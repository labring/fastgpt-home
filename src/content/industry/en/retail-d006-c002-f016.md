# MCN operations: interactive forms for staff training

## What the documents look like

An MCN manages long-term account compliance for multiple creators. A single brand session is one part of that work, while the ongoing relationship covers many creators across many periods. Records arrive from the MCN back office, platform violation notices, creator account data, and the contract ledger. The documents handled at this stage include creator signing contracts, training records, violation handling forms, and account schedules. The store service and internal training step covers creator handover at the store, training sign-in, and collection of pre-review material for content review. Daily and weekly update rhythms mean form collection points need to align with handover batches. The form node itself only collects submitted information and passes it to later nodes; the update rhythm does not change that division of labour.

## Constraints at the interactive forms step

The form input node and the user selection node are both user interaction nodes. When either is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The form input node collects required information and passes it to later nodes after submission. It does not carry a business database function. The user selection node executes a branch based on the user's choice; it does not act as a staff directory or a business data selector. Field validation, business approval, write-back, and batch operations need to be implemented in an external system or in later nodes. Retrieval and forms do not constitute authorization. Which materials, operations, and requests sit at which authorization state during an operations handover needs to be checked separately.

Hypothetical drill sample: the material text available for checking reads "Creator A signing contract number HT-001, signing date 1 March 2024, contract status pending review; store training record number PX-001, sign-in date 5 March 2024, sign-in person Creator A; account schedule number PQ-001, schedule date 8 March 2024." The handover request to be judged reads "Please hand over Creator A's 8 March 2024 schedule to the store training lead and confirm that the contract has taken effect." The material only states that the contract is pending review. It does not state effective clauses or the scope of authorization, so the fact that the contract has taken effect is not supported, and the authorization premise in the handover request remains to be verified.

## Configuration and implementation checks

| Configuration item | Relevant setting or check on this page | Correspondence with the sample |
| --- | --- | --- |
| Form input node | List the required information; pass it to later nodes after submission | Collects Creator A's contract number, training sign-in, and schedule number |
| User selection node | Execute a branch based on the choice | Used to confirm the next direction of the handover request |
| Required information check | Test missing-item and completed-item behaviour separately | Records the gap when the contract status field is absent |
| Interaction state | Record workflow state after triggering and wait for interaction | Waits for the store training lead to complete the choice |
| Downstream division of labour | Field validation, approval, and write-back implemented in an external system | Contract effect and authorization are not completed inside the form node |
| Retrieval association check | Verify identifiers first and exclude non-matching records | Excludes records whose numbers differ from the sample |

This hypothetical trial starting point sets the required field count to three. The reason for this choice is that the sample lists one contract number, one training sign-in, and one schedule number. The comparison is against the field count actually listed in the sample, and it does not represent any official default value.

## Three common errors

1. Treating form submission as contract effect. In the sample the contract status is pending review. Submitting the form only completes information collection; contract effect needs separate checking. The input is the contract status field, the comparison object is "pending review" against "in effect", and the observable result is that the status field has not changed to in effect, so the matter remains to be verified.
2. Treating the branch result of user selection as authorized execution. In the sample the handover request contains an authorization premise. The input is the request text, the comparison object is whether the material states a scope of authorization, and the observable result is that the request stays at to be verified when the material does not state authorization.
3. Treating a retrieval hit as a permission filter. The input is the sample number, the comparison object is whether the returned record number matches the sample number, and the observable result is that records with non-matching numbers need to be excluded. Retrieval itself does not judge permissions.

## How to verify the setup

1. Input the sample material text and the request to be judged, compare the value of the contract status field, and observe that "pending review" is not rewritten as "in effect" and that the authorization premise in the request is marked as to be verified.
2. Input the schedule number PQ-001 from the sample, compare the returned record numbers, and observe that records with matching numbers are retained and records with non-matching numbers are excluded. For an empty result, check the downstream design against the paper input []. Do not claim that a fictitious rule retrieval necessarily returns empty.
3. Input the missing-item scenario, that is, remove the contract status field, compare the behaviour after form submission, and observe that the missing item is recorded as an evidence gap and that after completion the field is passed to later nodes. Do not infer automatic approval or automatic write-back.
