# Refund-only disputes: workflow routing for staff training

## What the documents look like

Refund-only dispute handling centers on four document types: the refund-only application, the shipment evidence, the signed-delivery proof, and the appeal materials. Compared with ordinary return-and-refund cases, a refund-only dispute frequently has no returned parcel entering the warehouse, so the evidentiary weight sits on dispatch, signed delivery, and the stated value of the goods. Source systems named in the brief are the platform after-sales backend, carrier tracking, customer-service chat, and warehouse outbound records. The brief gives an update frequency of per order and daily; where that cadence does not affect routing behavior on this page, it is left out.

For store service and internal training, the routing job is to collect these materials at defined nodes, move them along defined branches, and make clear to the operator which actions only collect and pass information and which actions require a separate connection to a business system. A form submission is a collected value. A branch choice is a routing decision. Neither one writes an order, returns a document, or synchronizes an external status.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interactive state and the workflow state is recorded; after the user completes the interaction, execution continues downward. Once the user fills the required information and submits, the node collects the submitted form information and passes it to later nodes. The user selection node is also a user-interaction node; when it triggers, the conversation enters an interactive state and the workflow state is recorded, and when the user makes a choice the node evaluates that choice and executes the "yes" branch. The interactive state and the state recording are behaviors of these interaction nodes. No separate global state-recording switch is documented.

Information collected at a form node must be explicitly passed to a later retrieval, judgment, or interface node, and the output must be compared item by item against the input. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval and forms do not constitute authorized execution. A pending request is not an approval, and an offered option is not an executed action.

Hypothetical drill sample. A store after-sales supervisor receives a refund-only application. The draft sentence under review reads: "The order has been signed for, the goods value is clear, agree to refund only." The source material supplied for comparison reads: "Carrier tracking shows signed for on 10 March 2025, signed by the recipient in person." "Warehouse outbound records show the order left the warehouse on 8 March 2025, goods being one insulated cup." The request awaiting determination is: submit the draft sentence to the platform appeal specialist for review. The material carries a subject, an object, a status, and a date range, but no appeal authorization clause is stated.

## Three common errors

1. Treating signed-delivery information collected at the form input node as authorized execution. The input is the source material text; the comparison object is the phrase "agree to refund only" in the draft sentence; the observable result is that the draft sentence lacks an authorization clause and must be recorded as awaiting verification.

2. Treating the "yes" branch of the user selection node as automatically completing an appeal submission. The input is the request awaiting determination; the comparison object is the branch behavior of the interaction node; the observable result is that the branch only decides the routing direction and produces no submission action.

3. Treating retrieval results as a basis for permission or entity isolation. The input is the sample material; the comparison object is the retrieval library identifier; the observable result is that retrieval does not exclude unauthorized records, so authorization status must be checked by hand.

## How to verify the setup

1. Enter the source material text and the draft sentence; compare whether the draft sentence contains an authorization clause. If it does not, record it as unsupported rather than as a denial or a conflict.

2. Enter the request awaiting determination; compare whether the interaction node's branch connections have been verified one by one. If a branch is not connected, record it as awaiting verification and do not claim the appeal was executed.

3. Enter the sample material; compare the retrieval library identifier against the same-vector-model requirement. If the identifier does not match, exclude that library and record the actual observation; do not run cross-model retrieval to compare missed recall.

An empty-result hand-off can be checked with a clearly labeled paper input of an empty list against the downstream design; this does not assert that any fictional rule retrieval returns an empty list. Relevance scores and semantic retrieval do not carry permission or entity isolation. The same-vector-model requirement for a retrieval library does not extend to business-registration sites or other external systems. Where a document field is not provided, it remains unknown.
