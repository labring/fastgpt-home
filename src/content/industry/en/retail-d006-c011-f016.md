# Refund-only disputes: interactive forms for staff training

## What the documents look like

Refund-only dispute handling differs from ordinary refund-and-return work in its evidence structure. There is usually no returned parcel entering a warehouse, so the material under review centres on dispatch and signed-delivery records together with the claimed value of the goods. In store service and internal training, the everyday documents are the refund-only application, the dispatch voucher, the signed-delivery proof, and the appeal materials. These materials are produced per order and summarised daily. The sources behind them include the platform after-sales backend, carrier tracking, customer-service chat, and warehouse outbound records.

The interactive forms step has one job: collect the fields this task needs and pass them to later nodes or external systems. The form input node enters an interaction state when triggered, records the workflow state, and continues downward once the user completes the interaction. It collects the information the user fills in and passes it to subsequent nodes; it does not itself act as a business database. The user selection node executes a branch according to the user's choice. It is an interaction node, and it does not serve as a staff directory or a business-data selector. Field validation, business approval, write-back, and bulk operations belong to external systems or later nodes.

## Constraints at the interactive forms step

The documented behaviour of the form input node is limited to triggering, entering the interaction state, recording the workflow state, waiting for completion, collecting the submitted values, and passing them onward. The documented behaviour of the user selection node is limited to presenting a choice and executing the "yes" branch according to the selection. Nothing in the supplied documents establishes a scheduled trigger, a hidden control, a submission-count limit, an automatic judgement, or a snapshot guarantee. No error code is documented, so a comparison can only record what is observed and what remains unknown.

Retrieval and form completion do not constitute authorisation to execute. A relevance score is not a category, entity, or permission filter, and it does not exclude unrelated businesses or unauthorised records. During operational handover, the authorisation state of materials, actions, and requests must be kept distinct. A pending request is not an approval, an offered option is not an execution, and an unsigned termination is not a completed termination.

Hypothetical paper exercise sample: a store after-sales specialist submits a refund-only dispute handover request. The material text reads: "Order A, dispatched 10 March 2025; carrier tracking shows signed delivery on 12 March 2025, signed for by Wang. The buyer applied for refund-only on 14 March 2025, on the ground of goods not received." The draft sentence to be assessed is: "Signed-delivery proof is in place; refund-only approved." The material does not state the value of the goods, the refund amount, or any approval opinion. The approval conclusion in the draft sentence lacks support in the material.

## Configuration and implementation checks

| Configuration item | Type | Description |
| --- | --- | --- |
| Form input node | Documented node | Enters the interaction state when triggered, collects fields, passes them to later nodes |
| Required-field checklist | Implementation check | Lists order number, dispatch date, and delivery-signature status as the minimum set for this task |
| User selection node | Documented node | Executes a branch according to the selection; does not act as a business-data selector |
| Interaction state record | Documented behaviour | Records the workflow state after triggering and waits for the interaction to complete |
| Downstream division of work | Implementation check | Field validation, approval, and write-back are implemented in external systems or later nodes |
| Starting point for this exercise | Hypothetical value | Required fields set to order number, dispatch date, and delivery-signature status; chosen as the minimum set for material review, compared against the appeal-material field list |

## Three common errors

1. Treating form submission as authorised execution. Input: the handover request above. Compare the submission action against the approval-status field. Observable result: after submission the approval field remains empty.
2. Treating the user selection node as a staff directory or business-data selector. Input: the selection-node configuration. Compare its branch logic against personnel-data fields. Observable result: the node executes a branch and returns no personnel records.
3. Treating a retrieval result or similarity score as a permission filter. Input: a retrieval output carrying a similarity score. Compare the score against the authorisation field. Observable result: the score carries no authorisation information.

## How to verify the setup

1. Input the hypothetical material text and draft sentence above. Compare the draft conclusion against the delivery-signature status and application ground stated in the material. Expected observation: the approval conclusion is unsupported by the material and must be recorded as pending verification.
2. Input the handover request above. Compare the approval field after form submission against the authorisation state in the request. Expected observation: the approval field does not change because of submission, and the authorisation state remains unsupported.
3. Input a retrieval output carrying a similarity score. Compare the score against the authorisation field. Expected observation: the score does not change the authorisation state, and unrelated records are not excluded by the score.

These checks describe comparisons and expected observations. They do not record a completed test, a deployment, an approval, a refund, or any other business action. Where the material does not state a field, that field remains unknown.
