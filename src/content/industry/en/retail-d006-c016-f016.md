# Franchisee onboarding: interactive forms for staff training

## What the documents look like

Opening coaching transfers operating capability to a franchise location. It differs from franchise filing administration, which is a legal disclosure process. The daily documents for this task are training sign-in sheets, opening checklists, SOP manuals and assessment scores. Data comes from the training system, the supervisor app, store photographs and the headquarters SOP library. Each document corresponds to a specific store, a specific stage and specific personnel, and the fields across documents need to keep the same subject and the same period.

The Form Input node collects information that users fill in and passes it to later nodes after submission. It does not include a business database function of its own. The User Selection node executes a branch according to the user's choice. Both nodes are interaction nodes: when triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. Field validation, business approval, write-back and batch operations are implemented in external systems or later nodes as needed.

## Constraints at the interactive forms step

The four document types carry different comparison objects. A sign-in sheet is checked against personnel and session. A checklist is checked against materials and store condition. An SOP manual is checked against action standards. Assessment scores are checked against personnel and subject. The Form Input node gathers these fields, and later nodes can then branch on field content. The User Selection node fits steps that require a decision, such as confirming whether a checklist passes; the branch outcome depends on the user's choice, and the node itself does not judge whether the material is authentic.

The interaction state means the workflow pauses and records state while waiting for the user to finish filling in or choosing. This waiting does not constitute approval. Submitting a form does not equal passing business verification. Information retrieved or collected through a form cannot be treated as authorization to execute; authorization requires separate implementation in an external system or a later node.

Hypothetical paper exercise sample: a chain brand training department receives a paper record of an Opening Checklist. The source text reads: "Store number HYP-0417, inspection date 12 March 2025, inspector Zhang Moumou, cashier counter materials item marked 'placed', inventory count item marked 'pending supplementary entry'." A draft sentence is to be assessed: "The opening inspection for this store has fully passed and can proceed to coaching closure." Comparison point: in the source text the inventory count item is "pending supplementary entry", and that item is not recorded as complete. The draft sentence presents "pending supplementary entry" as a full pass, which is unsupported.

## Three common errors

1. Treating form submission as completed business approval. The Form Input node collects information and passes it on; approval requires an external system or a later node. In the sample, the draft sentence turns "pending supplementary entry" into a full pass, which treats an incomplete state as complete.
2. Treating the branch outcome of the User Selection node as a personnel directory or a business data selector. That node executes a branch according to the user's choice and does not perform entity isolation or permission judgement.
3. Treating the interaction-state wait as automatic judgement or a snapshot guarantee. The node records state and waits for interaction; it does not automatically judge whether material is authentic, and it does not guarantee submission counts or snapshots.

## How to verify the setup

1. Enter the sample source text and the draft sentence, and compare the source line "inventory count item marked 'pending supplementary entry'" with the draft line "has fully passed". If the draft sentence is inconsistent with the source state, it should be judged unsupported and the evidence gap kept.
2. For the required-field check, enter one version with a missing item and one version with the item supplied, then compare whether the node still enters the interaction state when the item is missing and whether execution continues after the item is supplied. The expected observation is that it waits for the missing item and then passes the fields once supplied.
3. For the User Selection node, enter one decision question with two options, and compare whether the branch executed differs after choosing each option. The expected observation is that the branch changes with the choice, and the node does not judge the business truth of the option.

These checks describe expected observations only. No test, deployment, approval, refund or other business action is claimed to have occurred. Where the source text does not state a field, the field remains unknown.
