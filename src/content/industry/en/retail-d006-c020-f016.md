# Certificates of origin: interactive forms for staff training

## What the documents look like

Certificate-of-origin work for export trade turns on four recurring document groups: the certificate-of-origin application, the commercial invoice, the packing list, and production cost materials. These documents serve import-country tariff treatment and customs clearance, and they are not necessarily governed by a letter of credit. The main data sources are the China International Trade Single Window, CCPIT systems, enterprise production records, and the customer's clearance requirements. The typical people handling this work are foreign-trade documentation staff, CCPIT or customs declarants, and exporters. When something goes wrong, the consequences are clearance delays for the customer, loss of tariff preferences, and amendment fees.

In store-service and internal-training settings, the form-and-interaction layer performs information collection and branch decisions. The Form Input node triggers an interaction state, records the workflow state, and waits for the user to complete the interaction before continuing downstream. The User Selection node evaluates the user's choice and executes a branch. Both node types collect entered information and pass it to later nodes; neither carries its own business database function. Field validation, business approval, write-back, and batch operations require an external system or later nodes.

## Constraints at the interactive forms step

Certificate-of-origin handling updates per shipment or in batches, so store-service and internal-training work must collect material information accurately before handing it to downstream processing. The Form Input node only collects information the user enters and passes it to later nodes after submission; it does not act as a business database. The User Selection node executes a branch based on the user's choice; it is not a personnel directory or a business-data selector. The interaction state records the workflow state and waits for interaction, then continues downstream once interaction is complete.

Hypothetical drill sample: a store receives one set of certificate-of-origin application materials. The source text provided for comparison reads: "Exporter: a trading company in East China; Goods: men's cotton knitted shirts; Country of origin: China; Destination country: Germany; Commercial invoice number: INV-2024-0312; Packing list number: PL-2024-0312; Production cost materials: attached." One draft sentence awaiting judgment reads: "The certificate-of-origin application for this shipment has been submitted to the CCPIT system and approved." The subject, object, and status in that draft sentence all require comparison against the source text. The source text states only that the materials are attached; it does not record that an application was submitted or approved.

## Configuration and implementation checks

| Configuration item | Relationship to this document | Implementation check |
| --- | --- | --- |
| Form Input node | Collects certificate-of-origin application material information | After triggering, enters interaction state and waits for entry to complete |
| User Selection node | Executes a branch based on the choice | Evaluates the user's choice and executes the corresponding branch |
| Required-information check | Lists information this task cannot omit | Test missing-item and completed behavior separately |
| Interaction state | Records workflow state and waits for interaction | Continues downstream once interaction is complete |
| Downstream division of labor | Field validation, approval, and write-back implemented as needed | Implemented in an external system or later nodes |

Hypothetical trial starting point for this page: set "Commercial invoice number," "Packing list number," and "Destination country" as required, because these three affect clearance and tariff determination. The comparison method is to submit a form missing one item and a form with all three present, then observe whether the interaction state continues downstream.

## Three common errors

1. Treating information collected by the Form Input node as a completed business approval. The form collects entered information and passes it to later nodes; approval requires an external system or later nodes.
2. Treating the User Selection node as a personnel directory or business-data selector. The User Selection node executes a branch based on the user's choice and does not perform identity or permission judgment.
3. Treating the interaction state's recording of workflow state as an automatic snapshot or a guarantee of submission counts. The documentation states only that state is recorded and interaction is awaited; it does not describe snapshots or count control.

## How to verify the setup

1. Enter the hypothetical sample source text and the draft sentence, then compare the draft sentence "has been submitted to the CCPIT system and approved" against the source text "Production cost materials: attached." The source text does not record submission or approval status, so the draft sentence is unsupported.
2. Enter the hypothetical sample form with all three required items present, then compare whether the interaction state continues downstream after submission. The documentation states that execution continues downstream once interaction is complete, so the expected observation is continuation.
3. Enter the hypothetical sample form missing "Destination country," then compare whether the interaction state waits when an item is missing. The documentation states that the required-information check tests missing-item and completed behavior separately, so the expected observation when an item is missing is waiting for completion, without automatic continuation.

Retrieval and relevance scores do not perform permission or entity isolation. Libraries using different vector models cannot be associated together; check identifiers only and exclude non-matching records. For empty-result handling, a clearly labeled paper input `[]` can be used to check downstream design, without claiming that a fictional rule search necessarily returns `[]`.
