# Brand member operations: multi-turn prompts for staff training

## What the documents look like

Brand member private-domain operations work with customer data and repeat-purchase outreach rather than store scheduling. The recurring materials are member tag tables, outreach plans, coupon rules and privacy authorization records, drawn from CRM systems, enterprise messaging, POS purchase records and mini-program behavior data. In the store service and internal training setting, guides and enterprise messaging operators use multi-turn dialogue to look up materials, rehearse scripts and hand over explanations, and those conversations quote the materials directly.

Material updates follow a daily and weekly rhythm; this page's feature does not depend on batch synchronization or transaction triggers. Three properties shape the task. The materials themselves carry authorization status, and an outreach plan may sit in draft or pending-review state. Dialogue history carries earlier turns forward, so a prior turn's assumption can persist into a later turn. Once a reply format is read by a downstream node, a structural change interrupts the handoff.

## Constraints at the multi-turn prompts step

Prompts for multi-turn dialogue state the material scope, the answering task and the handling of missing evidence; the model does not write business facts on its own. History is checked against the context actually carried in, distinguishing a new session from a continued session. Question optimization, when used for continuous knowledge-base dialogue, is checked for reference resolution and question expansion, and short questions do not automatically qualify. Model and length are checked against the context and reply settings actually supported, and long documents combined with follow-up questions need separate testing. Reply format follows the downstream handoff; choosing json_schema requires filling in the corresponding format requirement and verifying the returned structure.

Retrieval and similarity affect recall ordering only and carry no permission or entity isolation. The interactive node returns a display configuration containing only type and params; internal runtime fields such as entryNodeIds, memoryEdges, nodeOutputs and nodeResponseId are not returned. Forms collect values, and business verification, approval, database writes and external synchronization each need their own downstream implementation.

Hypothetical rehearsal sample: an internal training material retained by a brand member operations team reads: "March 2025 East China store guide script rehearsal plan (draft), subject is in-store customers holding a valid member tag, authorization scope is limited to the outreach actions listed in this plan, plan status is pending review by the operations lead." A draft sentence to be assessed reads: "This plan has been approved, and guides may send coupons to all members according to the plan." The draft sentence is compared item by item against the source text on subject, object, status and effective scope.

## Three common errors

1. Reading a pending-review status as approved. The input is the training material source text above and the draft sentence; the comparison object is the plan status field. The source states "pending review by the operations lead" and the draft sentence states "has been approved," which are mutually exclusive values on the same field, so this is a contradiction. Executable check: compare the status wording character by character and observe whether "has been approved" appears.
2. Expanding the authorization scope to all members. The input is the source sentence "authorization scope is limited to the outreach actions listed in this plan"; the comparison object is the object scope. The draft sentence states "all members," which the source does not record, so this is unsupported. Executable check: verify whether the object description exceeds the scope listed in the source.
3. Treating retrieval similarity as a permission filter. The input is a retrieval return carrying similarity scores; the comparison object is the returned records against the current requester's accessible scope. A similarity score does not constitute a permission judgment. Executable check: verify whether returned record identifiers fall within the authorized scope, exclude those outside it and record the result.

## How to verify the setup

1. Take the training material source text and the draft sentence above; the input is both full texts, the comparison object is the plan status field. When the draft sentence shows "has been approved" while the source reads "pending review by the operations lead," the judgment is contradiction, and this phenomenon meets the error condition.
2. Take the source authorization-scope sentence and the draft sentence object description; the input is both full texts, the comparison object is the object scope. When the draft sentence shows "all members" while the source lists only this plan's outreach actions, the judgment is unsupported, and this phenomenon meets the error condition.
3. Take a paper input of `[]` as an empty retrieval result; the comparison object is the downstream node's design for accepting an empty result. Observe whether the downstream handles it through an empty-result branch; this check does not claim that a fictional rule retrieval necessarily returns an empty array.
