# Brand livestream operations: workflow routing for staff training

## What the documents look like

A brand-run livestream carries its own scripts, inventory and after-sales work; commission structures do not drive the operation. That difference shapes how store service and internal training handoffs are routed. Four document types matter here: livestream scripts, product explanation cards, shift schedules and livestream reviews. Supporting data comes from Douyin Shop Compass, Juliang Qianchuan, livestream comments and transaction details, with updates per session or per hour.

These materials arrive at the routing step in different states. A script may sit in draft, confirmed or awaiting revision. A shift schedule may be published or awaiting adjustment. An explanation card may be reviewed or awaiting review. Routing work checks each item's state and scope one by one; missing items stay open rather than being filled in by assumption.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When triggered, the conversation enters an interaction state, records the workflow state, and waits for the user to complete the interaction before continuing. It collects required information and passes submitted values to later nodes. The User Selection node is also a user interaction node, repeatable and trigger-executed; when the user makes a choice, it evaluates that choice and runs the corresponding "yes" branch. Both nodes share the same interaction behavior described in the official documentation. Verification here means checking the interaction state after triggering against the documented behavior and the actual run context, without deriving extra global settings from the description.

Typical handoff requests in store service and internal training include: whether a revised script from one session can be used for the next training; whether a shift adjustment for a host requires the explanation card review to run again; and whether a problem item from a review has been added to the training checklist. The authorization boundary is that forms collect values; business review, schedule publication and training activation require a separate business interface or a later process. Retrieval and form submission do not constitute authorization to execute.

## Configuration and implementation checks

Configuration centers on one hypothetical drill sample. The sample source text is: "10 March 2025, Brand A livestream room, session 12 script revised draft, submitted by floor manager Li, status awaiting review. Explanation card for the same session, number J-0310-07, status reviewed. Shift schedule version V3, status published. Review document R-0310, status draft." The sentence awaiting judgment is: "The explanation card for this session is reviewed and can be used directly for the next training." This sentence involves subject, object, state and validity scope, and each must be checked item by item.

| Configuration item | Relation to this page's documents | Check method |
| --- | --- | --- |
| Form Input required fields | Collects script revision submitter, session, state | After submission, compare field values against the sample source text |
| User Selection branch connection | Judges whether the explanation card can be used for training | Verify the downstream node connected to the "yes" branch one by one |
| Interaction state recording | Records workflow state after node trigger | Confirm the conversation state during interaction matches the documented description |
| Output handoff design | Passes collected information to later retrieval or judgment nodes | Compare output against input fields item by item |
| External action separation | Schedule publication and training activation need a separate interface | Confirm form submission is not treated as business activation |
| Retrieval library identifier check | Libraries on different vector models cannot be associated together | Check identifiers first and exclude non-matching ones |

Hypothetical drill starting point: set the Form Input node's required fields to three items (submitter, session, state). The reason for this choice is that the sample source text contains these three pieces of information, which makes item-by-item comparison possible. The comparison target is the field values actually present in the sample source text.

## Three common errors

1. Treating form submission as a passed business review. In the sample, the script revised draft is awaiting review; submitting the form completes information collection only, and the review conclusion requires a separate process.
2. Treating execution of the User Selection "yes" branch as training activation. Branch execution indicates only the flow direction; training activation requires business-side confirmation.
3. Treating a retrieval result as an authorization credential. A document matched in the retrieval library does not mean that document has been approved for training or external publication.

## How to verify the setup

1. Input the sample source text and the drafted sentence, then compare whether "reviewed" in the drafted sentence refers to the same subject, the same period and the same field as the explanation card state "reviewed" in the sample. The field showing this session's card as reviewed can be retained, but the source text gives no validity scope or authorization for the next training session, so the cross-session use claim remains unverified.
2. Input the sample source text and the handoff request "this session's script revised draft can be used for the next training," then compare "can be used" in the request against the script state "awaiting review" in the sample. Awaiting review does not support a usable conclusion, and the evidence gap must be recorded.
3. Input an empty-result handoff scenario and check the downstream design against the paper input []. Observe whether the downstream node handles empty input as such; do not claim that a fictional rule retrieval necessarily returns [].
