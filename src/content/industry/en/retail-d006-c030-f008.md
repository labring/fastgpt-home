# Supermarket supplier accounts: workflow routing for staff training

## What the documents look like

Supermarket supplier entry settlement usually involves purchase-and-sale or consignment payables. A supplier may have no resident staff at the store, which distinguishes this category from a hypermarket concession counter. The main data sources are ERP purchasing, the supplier portal, POS sales and the finance system. Documents handled day to day include purchase contracts, delivery acceptance notes, rebate agreements and statements of account. Data updates weekly or monthly; this page does not derive batch synchronization or real-time triggers from that cadence.

For store service and internal training, the practical work is to turn the parties, objects, periods and statuses recorded in those documents into a handover-ready input, then pass that input to workflow nodes. A form input node and a user selection node both belong to user interaction nodes. Each can be added repeatedly and triggers execution. When triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction.

## Constraints at the workflow routing step

The form input node collects required information that the user fills in and submits; the collected values are passed to later nodes. The user selection node judges the user's choice and executes the corresponding "yes" branch. These are the documented node behaviours. Constraints follow from that scope: the nodes collect values and route branches. Order writing, document backfill and external status synchronization require a separate business interface or a later process. A retrieval result or a submitted form does not constitute authorization to execute a business action. The interaction state record is the node's own behaviour; no separate global state switch is documented.

Hypothetical paper exercise sample: the source material reads, "Supplier A signed a purchase contract with Supermarket B, agreeing that the March 2025 settlement-period rebate is calculated on accepted quantity; the delivery acceptance note records 120 cartons arriving on 5 March; the statement of account shows a March settlement quantity of 118 cartons." The draft sentence to be assessed is, "The March rebate is calculated on 120 cartons and may be submitted for settlement." The parties, period and fields in that sentence fall inside the source material, but the accepted quantity and the settlement quantity do not agree. The difference requires manual verification of the cause; the sentence does not meet the submission condition on the evidence given.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison object |
| --- | --- | --- |
| Required form input fields | Supplier name, contract number, settlement period | Compared field by field with the statement of account header |
| User selection branch | The "yes" branch connects to a verification node | Compared with the documented branch execution behaviour |
| Interaction state check | Record node trigger and submission | Compared with the behaviour described for the node |
| Output handover | Form values passed to a later retrieval or judgement node | Compared with the later node's input fields |
| External action split | Settlement writing connects to a separate business interface | Compared with the documented division of node responsibilities |

These starting points are set for this hypothetical exercise only. They are not official defaults.

## Three common errors

1. Treating a supplier name collected by the form as a verified entity. The form collects values; business verification needs a downstream implementation. Check: input "Supplier A" from the sample, compare the party field in the contract against the party field in the statement of account, and observe whether the two agree.
2. Treating the user's "yes" branch as approval. The branch only determines the route the workflow takes. Check: input the draft sentence, compare whether any authorization record appears, and observe that branch execution and approval are separate facts.
3. Treating a retrieval result as a permission filter. A relevance score does not perform entity or permission isolation. Check: input the sample fields, compare the retrieval return against the authorized scope, and observe whether any unauthorized record appears.

## How to verify the setup

- Verification one: input the sample source material and the draft sentence, compare the accepted quantity of 120 cartons with the settlement quantity of 118 cartons. If the two do not agree, the draft sentence does not meet the submission condition; record the difference as pending verification.

- Verification two: input the required form fields, compare the values passed to the later node after submission. If the fields are passed completely, the output handover meets the condition; if any field is missing, record the gap.

- Verification three: input an explicit paper input of an empty result [], compare the downstream node design. If the downstream node can accept an empty value, the condition is met. This page does not claim that a fictional rule retrieval necessarily returns [].

All three are paper checks. No execution, approval, refund or other business action has taken place.
