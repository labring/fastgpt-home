# Retail checkout and loyalty: workflow routing for staff training

## What the documents look like

Retail checkout and loyalty work revolves around price and membership benefit. The materials involved are promotional price tags, membership point rules, daily checkout reports and exception refund slips. Store checkout supervisors, CRM operations staff and finance auditors handle these materials together. The category does not manage short-shelf-life inventory; that belongs to convenience-store fresh ordering. The sources behind the materials are the POS system, the membership CRM, the payment platform and the price tag system. In workflow routing, the nodes must carry the fields from these sources clearly, and displayed information must not be treated as an authorization basis. A price or benefit error can produce price complaints, cash shortfalls or overages, and membership benefit disputes.

## Constraints at the workflow routing step

The Form Input node and the User Selection node are both user interaction nodes. When either node is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The Form Input node collects required information and passes it to later nodes. The User Selection node evaluates the user's choice and executes the corresponding "yes" branch; branch connections need to be verified one by one. The recorded interaction state is behaviour of the interaction nodes. No separate global state-recording switch is documented. Collected information must be passed explicitly to later retrieval, decision or interface nodes, and outputs must be compared against inputs item by item. Order writes, document backfill and external status synchronization require a separate business interface or a later process; the nodes themselves do not perform those business actions. Retrieval and forms do not constitute authorized execution.

Hypothetical drill sample: a store checkout supervisor submits a handover request. The material text reads: "Promotional price tag A-07, applicable store M12, effective period 1 March 2025 to 31 March 2025, membership points calculated at double rate; the daily checkout report shows that on 12 March the refund slip R-33 amount at this store does not match the price tag; exception refund slip R-33 status is pending review." The draft sentence to be judged reads: "R-33 confirmed refund completed, points reissued at double rate." This sentence turns pending review into completed, and turns reissue into executed, while authorization and execution evidence are absent.

## Configuration and implementation checks

| Configuration item | Setting or check relevant to this page | Correspondence to the hypothetical sample |
| --- | --- | --- |
| Form Input node | Enters interaction state when triggered, collects required information, passes it to later nodes after submission | Collects store, price tag number, refund slip number |
| User Selection node | Executes the corresponding "yes" branch after the user makes a choice | Decides whether R-33 enters the reissue branch |
| Output carry-over check | Compares collected information against later node inputs item by item | Checks that A-07 and R-33 fields agree |
| External action division | Order writes, document backfill and external status synchronization connect to a separate business interface | Reissue and refund-completed status are not written by the node |
| Interaction state check | Recording state is behaviour of the interaction node | Interaction state is maintained while awaiting submission |
| Retrieval check starting point | For this hypothetical trial, the starting point is observing how the first result corresponds to input fields, compared field by field with the sample | First-hit and full recall are not guaranteed |

## Three common errors

1. Treating a pending-review refund slip as a completed refund. In the sample, R-33 status is pending review, while the draft sentence writes confirmed refund completed; execution evidence is absent.
2. Treating information collected by a form as authorization. The Form Input node collects required information and passes it on; business verification and approval require later implementation, and the collection action itself does not constitute authorization.
3. Treating the interaction state record as a global switch. The interaction state record is behaviour of the interaction nodes; no separate global state-recording switch is documented, and submission counts or automatic judgments must not be fabricated.

## How to verify the setup

1. Input the sample material text and the draft sentence, compare whether "pending review" and "confirmed refund completed" are mutually exclusive values of the same field, and observe whether the draft sentence is judged unsupported.
2. Input the A-07 price tag scope and refund slip R-33 from the sample, compare whether store, period and field refer to the same subject, the same period and the same field, and observe whether inconsistencies are recorded as pending verification.
3. Input an explicit paper empty result [] and check whether the downstream design carries an empty result, observing whether an assertion appears that a fictional rule retrieval returns []. Carrying an empty result must not claim that a fictional rule necessarily returns [].
