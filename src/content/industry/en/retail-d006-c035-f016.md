# Trade returns and claims: interactive forms for staff training

## What the documents look like

Trade returns and claims handle reverse logistics and liability determination after export. The main data sources are customer emails, quality inspection reports, customs systems and insurance claim systems. The documents handled day to day include return agreements, claim letters, quality reports and return customs declarations. In store service and internal training, these materials arrive at the counter as paper or scanned copies, and store staff check them before entering values into a workflow. Each case advances independently and updates on an irregular, per-case basis. This page does not derive batch synchronization or real-time triggers from that update pattern.

Two features of this category shape the interactive forms step. First, the return agreement and the claim letter carry different business stages: an agreement records a proposed arrangement between parties, while a claim letter is a demand supported by evidence. Second, the quality report and the return customs declaration come from different sources, so a store handover may receive one without the other. Staff training therefore has to separate what a document says from what a workflow node can do with it.

## Constraints at the interactive forms step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the dialog box is hidden, and the workflow state is recorded. After the user fills in the required information and submits, the node collects the submitted form information and passes it to subsequent nodes. The user selection node is also a user interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. When the user makes a choice, the node evaluates that choice and executes the corresponding branch. Neither node includes a business database function. Field validation, business approval, write-back and batch operations need to be implemented in an external system or in subsequent nodes.

A relevance score is not a category, entity or permission filter. Retrieval is not authorization. A form collects values; it does not verify a business fact, grant approval, write to a database or synchronize with an external system.

Hypothetical drill sample: a store receives a scanned return agreement. The text reads: "Party A agrees to accept the goods returned by Party B from the March 2024 batch. The reason for return is pending quality inspection confirmation. The agreement takes effect on the date both parties sign." Party A has signed; the Party B signature field is blank. The store also receives a handover request: "Enter this return agreement into the form and trigger the user selection node to confirm whether to start drafting the claim letter." The matters to be determined are whether this agreement is currently an effective document, and how the user selection branch in the handover request should be designed.

## Configuration and implementation checks

| Configuration item | Type | Description |
| --- | --- | --- |
| Form input node | Interaction node | Enters interaction state on trigger, collects required information, passes it to subsequent nodes after submission |
| Required field check | Manual check | List the information this task cannot proceed without, then test the missing-field and completed-field behaviors separately |
| User selection node | Interaction node | Executes a branch based on the user's choice; does not serve as a personnel directory or business data selector |
| Interaction state recording | Node behavior | Records workflow state and waits for interaction after trigger, then continues execution after completion |
| Downstream division of work | Implementation check | Field validation, business approval, write-back and batch operations are implemented in an external system or subsequent nodes as needed |
| Hypothetical trial starting point | This assumption | Set the agreement signature status as a required field; this field is chosen because the sample has a blank signature field, and it must be compared with a signed state |

## Three common errors

1. Treating the scanned return agreement as an effective document. In the sample, the Party B signature field is blank and the stated effective condition is not met. The form should not default this agreement to an effective state.
2. Treating the user selection node as a business approval tool. This node only executes a branch based on the user's choice and does not provide approval or authorization.
3. Treating form submission as completion of claim letter drafting. The form input node collects information and passes it to subsequent nodes; the drafting action needs to be implemented in a subsequent node or an external system.

## How to verify the setup

1. Enter the return agreement text and the handover request from the sample. Compare whether the form's required fields include signature status. Observe whether a missing value blocks submission and whether a completed value allows the information to pass onward. The expected result is that a blank signature status is treated as pending verification.
2. Enter the sample choice request "whether to start drafting the claim letter." Compare the branch design of the user selection node. Observe whether choosing "yes" executes the corresponding branch and whether choosing "no" executes the other branch. The expected result is that each choice follows its designed branch.
3. Enter the agreement state from the sample, in which the Party B signature field is blank. Compare the form record against the source text. Observe whether the form records the unsigned state as pending verification rather than as effective or terminated. The expected result is that the record preserves the gap instead of resolving it.

These checks describe what to compare and what to observe. They do not claim that a test has been run, that a deployment has occurred, or that any approval, refund or business action has taken place. Where the supplied documents do not state an error code or an observed result, the outcome remains unknown and is recorded as a gap.
