# Tmall flagship operations: shared access for staff training

## What the documents look like

Tmall flagship store operations centre on brand authorization, flagship store identity and Tmall points compensation rules. The day-to-day record set includes product publishing pages, brand authorization letters, delivery commitment records and after-sales tickets. Sharing and embedding for store service and internal training must make the handover of materials and the authorization state between customer service staff, the store manager and the agency operator explicit. Daily and per-order update frequencies affect the timing of a review; they do not change how sharing and embedding is implemented.

The no-login window is created from the application detail page under publishing channels. The system generates a complete link, and that link is only an access entry. It does not by itself represent a business authorization. Identity verification falls within the commercial edition scope. After a root address is configured, initialization, conversation start and conversation finish each send a request to a `POST` interface, and the interface must return `success` as `true` before the user may continue. The `uid` must be returned and must be a string that does not contain `|`, `/` or `\` and does not exceed 255 bytes. The anonymous localId only holds within the same device and the same browser; records across devices require separate identity and session design. The conversation result reporting interface has no specified return value and can be connected to downstream logic such as balance handling.

## Constraints at the shared access step

A hypothetical drill sample is used here for review purposes. In the internal training material of a Tmall flagship store agency team, a passage provided for checking reads: "The customer service share link is created by the store manager under publishing channels. The link name is 'Training Demo'. The expiry time is set for this drill to 7 days after creation. The identity verification root address is filled with the internal training server address. Trainees open the link by appending an authToken, and the authToken is issued per person by the training system." A handover request to be judged reads: "Send this link directly to an external partner for product consultation; there is no need to check the identity verification return result again."

In this request, whether the link may be used by an external partner and whether identity verification has been executed both need to be checked against the source passage and the documented conditions. The source passage names trainees as the users who append an authToken. It does not name an external partner. The request asks to skip checking the verification return result, while the documentation requires `success` to be `true` before the user may continue.

## Three common errors

1. Treating the system-generated share link as a business authorization credential. The link only indicates an access entry. Whether an external partner may use it must be judged from the `success` and `uid` returned by identity verification; the existence of the link does not show that authorization has been granted.
2. Treating the anonymous localId as a cross-device identity. The documentation states that this identifier only holds within the same device and the same browser; switching devices or clearing the browser cache loses the records, and cross-device records require separate design.
3. Treating a pending handover request as already executed. In the sample, "there is no need to check the identity verification return result again" is request content. Whether identity verification passed and whether external use was approved are not concluded in the source passage.

## How to verify the setup

1. Input the sample source passage and the proposed sentence, compare the subject scope of "external partner use" with the source passage's "trainees open the link by appending an authToken", and observe whether a subject mismatch appears. If the source passage does not record an external partner, record the conclusion as unsupported.
2. Input the identity verification root address and the three interface paths, compare whether the concatenated full address matches the documented `/shareAuth/init`, `/shareAuth/start` and `/shareAuth/finish`, and observe whether only the root address was filled.
3. Input the pending request from the sample, compare "there is no need to check the identity verification return result again" with the documented requirement that `success` must be `true` before the user may continue, and observe whether the request lacks evidence that verification was executed. Where evidence is missing, record it as pending confirmation.
