# Product listing reviews: workflow routing for staff training

## What the documents look like

Platform product title and detail compliance concerns the truthfulness of promotional claims and the display of supporting qualifications. It does not handle parcel delivery, which separates it from platform shipping operations. The working materials are platform rule-center entries, an advertising prohibited-terms list, a brand asset library, and inspection-agency reports. Day-to-day work centers on the product title table, detail-page assets, the prohibited-terms list, and inspection reports. The most time-consuming steps are checking absolute claims, comparing physical parameters, and replacing non-compliant assets. Errors can lead to product delisting, complaints, and administrative penalty risk. Material updates arrive weekly and with each new product launch; this page's feature does not depend on that cadence, so no synchronization mechanism is described here.

In the store-service and internal-training setting, workflow routing must keep material checking, human judgment, and external business actions separate. Interaction nodes collect values and branch choices. They do not grant authorization, record approvals, or write to databases. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval and similarity scores do not perform permission or entity isolation. Libraries built on different vector models cannot be associated together; identifiers must be checked first and non-matching items excluded, without running cross-model retrieval to compare missed recalls. Optional paths shown in an overall flow diagram do not mean every request executes all of them: image retrieval requires a corresponding image input and model capability, and reranking requires a model and must be enabled in settings.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. After the user completes the required information and submits, the node collects the submitted form information and passes it to subsequent nodes. The user selection node is also a user-interaction node. It likewise enters an interaction state, and when the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. Both nodes can be added repeatedly and trigger execution. The constraint is that what these nodes collect are values. A submitted form is not an approval, an authorization, or a database write. The recorded interaction state is a behavior of the interaction node; no separate global state-recording switch is documented.

Hypothetical paper exercise sample. The source text supplied for checking is: "Product title table, row A: 'pure natural, no additives'; advertising prohibited-terms list, item 7: 'pure natural' is a wording that must be replaced; inspection report number Q-2024-031, tested object batch B, conclusion field blank." The draft sentence to be judged is: "This product title has been verified by the inspection report and may retain 'pure natural, no additives'." The handover request is: "Submit row A of the title table to legal review, then publish directly." This sample is constructed only for this paper exercise. It uses no real customer, company, or legitimate identity number.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this page | Reason and comparison method |
| --- | --- | --- |
| Required fields of the form input node | Title table row number, prohibited-term item number, inspection report number | Compare against the three material identifiers in the sample; a missing item means the interaction is incomplete |
| Branches of the user selection node | "Materials complete" and "Materials pending" | The sample conclusion field is blank, so only the pending branch can be entered |
| Output handoff | Pass the collected form values to a later retrieval or judgment node | Compare each output value against its input value for consistency |
| Interaction state check | After triggering, check that the conversation enters the interaction state | Observe the hidden dialog box and the recorded state; no global switch is set |
| External action separation | Mark publish, backfill, and synchronization as requiring a separate interface | Record these separately from interaction-node behavior; do not embed them in the node |

The hypothetical starting points are set only for this paper exercise and are not official default values. The numeric comparison method is: match the three material identifiers in the sample against the three form fields one by one; a missing item is judged incomplete.

## Three common errors

1. Treating form submission as authorization. In the sample, legal review is in a pending-submission state. Collecting a row number through a form does not mean review passed, and the publish action requires a separate business interface.
2. Treating retrieval similarity as a permission filter. In the sample, the prohibited-terms entry and the title table row number can be compared within the same library, but similarity does not exclude unauthorized records.
3. Treating the existence of an inspection report number as a valid conclusion. The sample conclusion field is blank. The number's presence shows only that the report is referenced; it does not show that parameters passed.

Corresponding checks. First, input the sample draft sentence and the handover request, compare "pending legal review" against "publish directly," and if the request contains a publish action with no completed-review record, judge it as exceeding authority. Second, input the title table row number and the prohibited-term item number, compare whether both come from the same library and same model, and if the identifiers do not match, exclude them without running cross-model retrieval. Third, input the inspection report number and the conclusion field, compare whether the conclusion field holds a value, and if it is blank, judge the claim as unsupported, without judging it as a denial or a conflict.

## How to verify the setup

- Verification one: input the three source-text sentences and the draft sentence from the sample, compare the draft phrase "has been verified by the inspection report" against the blank conclusion field, and observe that a blank conclusion field satisfies the "unsupported" judgment. This does not claim an actual test was run.

- Verification two: input the handover request "submit to legal review, then publish directly," compare the review status against the publish action in the request, and observe that a publish request with review not completed satisfies the judgment "pending review does not demonstrate authorization." A pending request is not an approval.

- Verification three: input the paper empty result [] and the downstream node design, compare whether the downstream is designed to accept an empty value and record the gap, and observe that the downstream does not treat the empty value as a pass. All three verifications address this page's primary task: material checking and handover-request judgment. They do not drift into identity certification or report analysis. Missing evidence remains missing; pending review remains pending; unsigned remains unsigned.
