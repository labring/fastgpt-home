# Seller ratings management: shared access for staff training

## What the documents look like

Ratings maintenance for platform stores depends on consumer feedback that appears after fulfillment and after-sales service. The data sources named in the brief are Douyin Shop experience score, Tmall service indicators, JD after-sales reviews, and the customer service system. In a store service and internal training setting, the working materials are negative review handling records, experience score detail, service diagnostic reports, and rectification ledgers. These materials update daily and weekly. The sharing and embedding feature on this page does not depend on that update frequency, so the frequency itself is not treated here as a control.

Compared with platform promotion registration, ratings maintenance does not directly set activity prices. Errors in this category show up as lower search weight, restricted promotion registration, and lower store conversion. The sharing and embedding step hands a material or a conversation entry point to store staff. That makes it necessary to separate three things: the material itself, the access entry point, and the authorization state. A link that opens is an entry point. It is not a business authorization, and it does not by itself grant any approval or completion right.

## Constraints at the shared access step

The no-login window is created under application details, then publish channels, then no-login window. The system generates a complete link, and the name field is only used for record display. The link identifier opens the entry point and cannot be treated as business authorization. Expiration time and QPM are set according to the intended scope and checked against the actual edition. QPM means the maximum number of visits per user per minute. The points cap is used to check the usage limit and cost attribution of the shared entry point. Some parameters are restricted by edition.

Identity verification is limited to the commercial edition scope and is judged by the success status and uid returned by the official interface. The anonymous local identifier depends on the same device and the same browser; records across devices require separately designed identity and session management. A retrieval result or a value collected by a form does not constitute authorization or execution. Business verification, approval, database writes, and external synchronization each need their own downstream implementation.

Hypothetical drill sample: a store operator records one negative review handling record in the rectification ledger. The source text reads: "10 March 2025, store A customer service submitted a negative review handling record, status pending supervisor review, consumer not contacted, supporting evidence not supplemented." The proposed handover request reads: "Share the conversation entry point corresponding to this record with store A, and allow store A to directly mark the rectification as complete." The review status and the authorization boundary in that request need to be checked. Pending review does not constitute approval, and a shared entry point does not constitute a right to mark rectification complete.

## Configuration and implementation checks

| Name | Store service training entry | Used only for record display, unrelated to business authorization |
| Expiration time | Set to 7 days for this drill | After that time the link cannot be used; unrelated to material validity |
| QPM | Set to 10 for this drill | Maximum visits per user per minute; check against the actual edition |
| Points cap | Set to 1000 for this drill | Check the usage limit and cost attribution of the shared entry point |
| Identity verification | Fill in the commercial edition root address | Judge by the success status and uid returned by the interface |
| View quoted chunks | Enabled for this drill | Check the display scope against the system introduction |

The values above are hypothetical starting points for this drill, used for comparison against actual interface return values. They are not official default values.

## Three common errors

1. Treating a negative review handling record with status pending supervisor review as an approved rectification. Input is the sample source text above. Compare the status field "pending supervisor review" with "approved." When the two differ, the rectification completion mark cannot be executed.

2. Treating the share link identifier as business authorization for store A. Input is the generated complete link. Compare the link parameters with the authorization scope. The link opening does not mean store A has obtained the right to mark rectification complete.

3. Treating a retrieval result or a form-collected value as the basis for authorization. Input is the ledger entry returned by retrieval. Compare it with the approval record. When the approval record is missing, the request is not supported.

## How to verify the setup

1. Input the sample source text and the proposed handover request. Compare the status field with the authorization boundary. When the status is pending supervisor review and the request asks to mark rectification complete, the request is not supported, and the evidence gap remains open.

2. Input the generated share link and the actual device used. Compare record visibility on the same device and the same browser with visibility after switching devices. When records are not visible after switching, that matches the documented condition of the anonymous local identifier.

3. Input the success status and uid returned by the identity verification interface. Compare whether the uid format contains forbidden characters and whether it stays within 255 bytes. When it does not meet the format, record it as the Invalid UID condition and do not infer any other business outcome.
