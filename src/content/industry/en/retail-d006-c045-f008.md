# Seller ratings management: workflow routing for staff training

## What the documents look like

Seller ratings and experience score maintenance in platform e-commerce operates on consumer feedback generated after fulfillment and after-sales service. This separates the category from platform promotion enrollment, which centers on event pricing. The main data sources named in the brief are Douyin Shop experience scores, Tmall service indicators, JD after-sales reviews, and customer service systems. The routine documents are negative review handling records, experience score details, service diagnostic reports, and rectification ledgers. For store service and internal training, the work is to connect negative review attribution, supporting evidence collection, and rectification tracking into a handover-capable process. Workflow routing therefore handles three kinds of action: interaction-based collection, branch decisions, and information transfer to later nodes. The brief marks its category description as broadly indicative, so the specific document set and update rhythm of any single store remain conditional.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. Once the user fills in the required information and submits, the node collects the submitted form information and passes it to later nodes. The user selection node is also a user interaction node with the same interaction state and state recording, and when the user makes a choice, the node evaluates that choice and executes the "yes" branch. Both nodes can be added repeatedly and trigger execution. Retrieval and form collection supply information only; they do not constitute authorization. Order writes, document backfill, and external status synchronization require a separate business interface or a later process.

Hypothetical paper exercise sample: A store customer service supervisor submits a negative review handling record. The supplied text reads: "On 3 June 2025, the customer reported that the outer packaging was damaged. Customer service called the same day to apologize and sent a replacement. On 5 June the customer added a review expressing satisfaction." The accompanying experience score details for the same batch show that the service indicator for that order on 3 June is "pending verification." One proposed draft sentence reads: "This negative review has completed rectification and been closed." The material needed for the judgment is the record and the details above. The authorization boundary is internal store training verification only, and does not include submitting a platform appeal.

## Configuration and implementation checks

| Configuration item | Type | Relation to this page's sample |
| --- | --- | --- |
| Form input node | User interaction node | Collects required information for negative review attribution and passes it to later nodes after submission |
| User selection node | User interaction node | Presents the choice about whether the customer has been contacted and executes the "yes" branch |
| Interaction state check | Manual verification action | Confirms that triggering puts the conversation into interaction state and records workflow state |
| Output handover check | Manual verification action | Compares collected information item by item against the input of later nodes |
| External action separation | Requires a separate system implementation | Order writes and external status synchronization are not completed inside this process |
| Hypothetical trial starting value | Manually set value | Uses "pending verification" as the comparison starting point and compares it word by word against "satisfied" in the record |

The starting value is chosen because the experience score details supply "pending verification" for the same order and date, which gives a concrete counterpart to compare against the handling record. It is a hypothetical trial starting point for this paper exercise, not an official default.

## Three common errors

1. Treating form submission as completed authorization. Submission collects information and passes it to later nodes. Order writes and external synchronization need a separate interface, and the submission itself does not grant that authority.
2. Treating the "yes" branch of a user selection as an executed action. The selection determines which branch runs. Actually contacting the customer and closing the rectification require later process steps, and the branch decision alone does not accomplish them.
3. Treating retrieval results as a permission filter. A relevance score does not exclude unrelated businesses or unauthorized records, and retrieval does not perform authorization judgment.

## How to verify the setup

1. Input the negative review handling record and the experience score details from the hypothetical sample. Compare whether "satisfied" in the record and "pending verification" in the details belong to the same order and the same field. If the two values are explicitly mutually exclusive for that same field, mark the item as pending verification. If the details do not state that field, record the item as unsupported.
2. Input the proposed draft sentence "This negative review has completed rectification and been closed." Compare it against whether the source text contains an explicit statement that rectification was completed and that closure occurred. The source text contains only an apology, a replacement, and an added expression of satisfaction, and lacks a closure field. Judge the sentence as unsupported rather than as negated.
3. Input the interaction state after the form input node triggers. Compare whether the conversation enters the interaction state and whether the workflow state is recorded. If submitted information does not appear in the input of later nodes after submission, record an output handover gap. Do not infer that the node has failed.

These checks state expected observations. They do not claim that a test was run, that any deployment occurred, or that any business action was completed. Where the record and the details do not carry a field, the gap stays a gap. A pending request is not approval, an offered option is not execution, and an unsigned termination is not a completed termination.
