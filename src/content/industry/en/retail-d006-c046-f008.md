# Marketplace category access: workflow routing for staff training

## What the documents look like

Marketplace category access takes place before a listing is published or a store is onboarded. The review object is the operating entity's qualifications and the authorization chain, not post-listing performance. For the store service and internal training task, the working materials are the business license, trademark registration certificate, brand authorization chain, and industry license. These documents arrive irregularly, at each onboarding event, and this page does not derive batch synchronization or real-time triggers from that frequency.

Three facts shape the routing work. First, category access sits upstream of publishing, so a routing error blocks listing rather than correcting a live store. Second, the authorization chain is the slowest item to assemble, which means the workflow must carry an explicit authorization-validity field rather than assume completeness. Third, the material set spans several document types with different issuing sources, so a single form node cannot treat them as one interchangeable attachment.

Within the workflow routing step, the relevant FastGPT v4.17.2 nodes are Form Input and User Selection. Both are user-interaction nodes. When triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. Retrieval or form collection on its own does not constitute authorization execution. Order writes, document backfill, and external status synchronization require a separate business interface or a downstream process.

## Constraints at the workflow routing step

The Form Input node collects required information and, after submission, passes the collected values to later nodes. The User Selection node evaluates the user's choice and executes the "yes" branch. Neither node performs business verification, approval, or database writes. A branch being executed means the flow moved in that direction; it does not mean a business approval completed.

Hypothetical paper exercise sample, used only for desk checking and not representing any real entity or completed review outcome:

The store service team holds an authorization letter whose source text reads: "Party A authorizes Party B to sell Class 25 apparel goods on a given platform during the period from January 1, 2025 to December 31, 2025." A draft sentence reads: "Party B has obtained a long-term valid authorization from Party A and may sell goods in all categories." The pending request is to place the draft sentence into training material and, on that basis, make "authorization validity period" a required field in the Form Input node.

The constraint follows directly. The source text states a bounded period and a single class. The draft states an open-ended period and all categories. The form field can collect a validity period, but collecting it does not confirm that the authorization is in force. The User Selection "yes" branch can route a confirmation step, but routing does not approve the authorization chain.

These are implementation checks tied to this page's documents. They are not documented default values, and no numeric limit, unit, menu, or global switch is asserted.

## Three common errors

1. Treating "long-term valid authorization" in the draft as a verified fact. The sample source text states only January 1, 2025 to December 31, 2025. The draft's "long-term valid" conflicts with the source period field, so the statement is unsupported.

2. Treating a collected authorization validity period as proof that authorization is in effect. The Form Input node collects required information and passes it to later nodes. Whether the authorization is effective requires separate comparison against the authorization letter source text. Collection is not authorization confirmation.

3. Treating the User Selection "yes" branch as an approval. The node executes a branch according to the user's choice. Branch execution indicates flow direction, not completed business approval.

## How to verify the setup

1. Input the sample source text and the draft sentence; compare the "authorization validity period" field. The source period is January 1, 2025 to December 31, 2025, and the draft says "long-term valid." The two values are inconsistent, so the draft is judged unsupported by the source text.

2. Input the sample source text and the form required-field setting; compare the "authorized goods category" field. The source limits goods to Class 25 apparel. If the form has no category field, or the draft says "all categories," the scope is inconsistent with the source and should be recorded as pending verification.

3. Input the pending request and the User Selection branch configuration; compare what follows the "yes" branch. If the "yes" branch connects directly to order writing or document backfill, while the document states those actions require a separate business interface, the configuration is judged to lack external action separation and needs implementation added before re-checking.

For retrieval checks, record what is observed and which failure branch appears. A relevance score is not a category, entity, or permission filter, and retrieval is not authorization. An empty-reference handoff can be checked on paper with an explicit empty input against the downstream design; this does not assert that a fictional rule query returns an empty result. Libraries using different vector models cannot be jointly associated; verify identifiers first and exclude non-matching libraries rather than running a cross-model retrieval comparison. Where a field is not stated in the source, or only related-stage evidence exists, record it as unsupported or pending verification. Missing evidence remains missing.
