# Marketplace returns: shared access for staff training

## What the documents look like

Marketplace refund and return handling runs continuously per order, and it does not necessarily connect to a promise made in a single livestream session. In the store service and internal training task, the working materials come from the platform after-sales backend, customer service chat, WMS receiving, and payment refund records. The daily documents are refund applications, return logistics notes, quality inspection photos, and refund approvals. Store staff need to share handling wording and training material with frontline staff, and embed that material into an existing workflow.

Two facts shape this page. A share link identifier is used for access only, and it does not act as business authorization. An anonymous local identifier depends on the same device and the same browser, so cross-device records require a separate design for identity and session management. These facts mean the sharing and embedding step must separate material transfer from business approval. Retrieval and relevance scores do not carry permission or entity isolation duties.

## Constraints at the shared access step

A share link is created and copied from the publish channel. The link identifier cannot be treated as business authorization. Expiration time and QPM are set for the usage scope and checked against the actual edition; QPM means the maximum number of visits per user per minute. The points cap corresponds to the usage limit and cost attribution of the share entry, and some parameters are restricted by edition. Identity verification is restricted to the commercial edition scope, and it follows the official interface return of a success state and uid. For conversation record boundaries, the anonymous local identifier depends on the same device and the same browser, and cross-device records require a separate identity and session management design. Retrieval and relevance do not perform permission or entity isolation, and the same-vector-model requirement for a retrieval library cannot be extended to other external systems.

Hypothetical exercise sample. Material text for review: a store submits a refund application record stating "Order number A-2024-0312, return logistics note SF-7788, three quality inspection photos, requested refund amount 199 yuan, status pending approval." A separate internal training handover request states "Please share the above refund handling wording with newly onboarded customer service staff, and embed it into the store workflow." Draft sentence to be judged: "This refund application has been approved and can be refunded directly." The source text records only the status pending approval, and it does not record approval or refund execution. The draft sentence differs from the source text on the same subject, same period, and same field, so it is unsupported.

## Three common errors

1. Treating the share link identifier as business authorization. The input is the link identifier, the comparison object is the authorization boundary, and the observable result is that the link is accessible while the approval status remains pending approval.

2. Writing a pending approval status as approved. The input is the refund application source text, the comparison object is the status value in the same field, and the observable result is that the source text does not record approval, so the draft sentence is unsupported.

3. Treating retrieval relevance as a permission filter. The input is a retrieval request, the comparison object is the permission and entity isolation requirement, and the observable result is that relevance does not exclude unauthorized records, which requires a separate system implementation.

## How to verify the setup

1. For the draft sentence "This refund application has been approved and can be refunded directly," input the refund application source text and the draft sentence, and compare the status value in the same subject, same period, and same field. The source text is pending approval, and the draft sentence is approved. The two are inconsistent, so the judgment is unsupported.

2. For the handover request "Please share the above refund handling wording with newly onboarded customer service staff, and embed it into the store workflow," input the request text and the identity verification configuration, and compare whether the return contains success and uid. If success is true and uid meets the format, identity verification passes. If success is not true, an error is shown, and the gap is recorded.

3. For the conversation record boundary, input the same-device-same-browser scenario and the cross-device scenario, and compare the anonymous local identifier condition. The same device and same browser can pull the recent 30 days and 20 records. The cross-device case requires a separate identity and session management design. Record the actual observation without claiming that a live test was performed.
