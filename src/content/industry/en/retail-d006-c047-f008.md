# Marketplace returns: workflow routing for staff training

## What the documents look like

Marketplace refund and return handling occurs continuously per order, unlike concentrated after-sales processing tied to a single livestream session. Four document types form the main cross-checking materials for store service and internal training: refund applications, return logistics labels, quality inspection photos, and refund approvals. A refund application records the buyer's claim and the order identifier. A return logistics label records the in-transit status of the returned item. A quality inspection photo records the product's appearance at receiving. A refund approval records the amount and processing conclusion. These materials sit across the platform after-sales backend, customer service chat, WMS receiving, and payment refund records, updating per order and daily.

At the store service and internal training stage, material status and operational authority must be recorded separately. An in-transit label does not equal a signed-for return. The existence of a quality inspection photo does not equal a determined responsibility. The existence of an approval record does not equal an executed refund. Workflow routing at this step separates collection, judgment, and external writes into checkable steps, so that form collection or retrieval results are not treated directly as authorized execution.

## Constraints at the workflow routing step

The form input node enters an interaction state when triggered, records the workflow state, and after the user submits required information passes that information to subsequent nodes. The user selection node executes the corresponding "yes" branch after the user makes a choice. Both nodes are user interaction nodes, can be added repeatedly, and trigger execution. The interaction state is node behavior; no separate global state-recording switch is documented. Collected information must be explicitly passed to subsequent retrieval, judgment, or interface nodes, with outputs compared item by item against inputs. Order writes, document backfill, and external status synchronization require a separate business interface or subsequent process; the nodes themselves do not complete these actions.

Hypothetical drill sample: A store after-sales specialist receives a refund application. The application text reads: "Order A-2201, buyer claims outer packaging damage, requests refund of 86 yuan, return logistics label shows in transit." On the same day, a quality inspection photo records the product appearance as intact for this order, and the refund approval field is blank. The draft handover request reads: "Please directly approve this order's refund and synchronize with the payment system." This request treats a pending-review state as approved, treats an in-transit label as signed-for, treats the inspection photo as a responsibility determination, and asks the node to write directly to the payment system. Workflow routing needs to split this request into: form input collecting the order identifier and refund amount, user selection confirming responsibility attribution, and a subsequent interface node separately undertaking the payment write.

## Three common errors

1. Treating pending review as approved. In the sample, the refund approval field is blank, and the draft request says "please directly approve." The input is the blank approval field and the draft sentence. Compare the status field values; when the approval field is blank, record as pending verification, not as approved.

2. Treating in-transit logistics as signed-for return. The sample return logistics label shows in transit, and the draft request asks to synchronize with the payment system. The input is the logistics label status and the requested action. Compare the two values of in-transit and signed-for; when in transit, retain pending verification and do not undertake the payment write.

3. Treating a quality inspection photo as a responsibility determination. The sample quality inspection photo records the product appearance as intact, and the draft request approves the refund on this basis. The input is the photo record and the responsibility field. Compare the photo content with the responsibility conclusion; when the photo exists, record only appearance and do not substitute it for a responsibility determination.

## How to verify the setup

1. Input the sample text "Order A-2201, buyer claims outer packaging damage, requests refund of 86 yuan, return logistics label shows in transit" and the draft sentence "please directly approve this order's refund and synchronize with the payment system." Compare whether the form input node output contains the order identifier and amount, and whether the user selection node executes the "yes" branch. The condition is met when the output matches the original text in order and amount, and branch connections correspond item by item.

2. Input the blank refund approval record and the draft sentence. Compare the approval status field value; when blank, record as pending verification. The condition is met when downstream nodes receive the pending-verification marker and do not receive an approved marker. If downstream receives an approved marker, record this as a status handoff mismatch and preserve the evidence gap.

3. Input the return logistics label "in transit" and the draft request "synchronize with the payment system." Compare the logistics status with the external operation division; when in transit, the payment write requires a separate business interface. The condition is met when the payment write is not executed within this interaction node, and the separate interface is recorded as pending implementation. If the payment write is recorded as completed, record this as unauthorized execution and do not fabricate authorization terms.
