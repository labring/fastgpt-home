# Marketplace returns: interactive forms for staff training

## What the documents look like

Platform refunds and returns arise order by order, which differs from concentrated after-sales handling tied to a single livestream session. A refund request does not need to connect to a promise made during one broadcast. In store service and internal training, support agents and after-sales specialists work with four document types: the refund request, the return logistics waybill, inspection photos, and the refund approval. Warehouse inspection supplies receiving and quality information. These materials are produced per order, and the daily update rhythm follows each order as it is handled.

For interactive forms, the practical consequence is that material status moves with the order. What an interactive node collects, whether a filled value or a selected option, represents only that submission. It does not show that approval, refund, or receiving has been completed. The form input node collects the information a user fills in and passes it to later nodes after submission; it does not itself act as a business database. The user selection node executes a branch based on the user's choice and does not serve as a staff directory or a business data selector.

## Constraints at the interactive forms step

The form input node and the user selection node are both user interaction nodes. When triggered, the conversation enters an interaction state, the workflow state is recorded, and execution waits until the user completes the interaction, then continues downward. The recorded interaction state marks where the workflow is waiting. It does not confirm refund responsibility, amount, or authorization.

Hypothetical paper exercise sample: a store training record holds one paper document whose text reads: "Refund request A-07: order number 20240612-31, request date 12 June 2024, applicant claims outer packaging damage, requested refund amount 128 yuan; attached return logistics waybill number SF0000000001, two inspection photos, refund approval field empty." A second document states: "Return logistics waybill SF0000000001 was signed for by the warehouse on 14 June 2024; inspection conclusion pending entry." The draft sentence under review is: "This refund has completed approval and can be paid out." The subject, object, and status needed for judgment are readable from the above text. The empty approval field shows that approval is not complete, so the draft sentence does not match the source text.

## Three common errors

1. Treating form submission as completed approval. In the sample the refund approval field is empty; submitting a form only shows that a user filled in information, and approval status still requires separate checking.
2. Treating the selected branch as business authorization. The user selection node executes a branch based on the choice; the branch direction does not mean the refund was approved or the money was returned.
3. Treating the interaction state record as a snapshot guarantee. The document states that the node records workflow state and waits for interaction; it does not state a submission count limit or a data snapshot capability, so the material cannot be assumed to have been fixed.

Corresponding checks: the first check takes the sample source text and the draft sentence as input, compares the refund approval field value with the "completed approval" wording, and finds the draft sentence unsupported when the approval field is empty. The second check takes the selection branch name and the sample approval status as input, compares the branch direction with the approval field value, and records the case as pending verification when the branch is "approval passed" while the approval field is empty. The third check takes the interaction node trigger record as input, compares the record content with snapshot or count requirements, and keeps the item unknown when the document states no corresponding control.

## How to verify the setup

- Verification one: input the sample source text "refund approval field empty" and the draft sentence "this refund has completed approval and can be paid out"; compare the approval field value with the draft wording; when the two do not agree, the draft sentence does not meet the condition and is recorded as unsupported.

- Verification two: input the sample source text "inspection conclusion pending entry" and the draft sentence "inspection is complete"; compare the inspection conclusion field with the draft wording; when the field is pending entry, the draft sentence does not meet the condition and the evidence gap is retained.

- Verification three: input the paper input [] and the downstream node design; compare the empty-result handling logic with the retrieval scope marker and observe whether the downstream processes it on the empty-result branch. The same vector model requirement for a retrieval library is limited to that library itself and does not extend to external systems. When a cross-model marker does not match, exclude that source and record the actual observation; do not run a cross-model retrieval to compare missed recall.

All three verifications concern this page's draft sentences and sample source text, and judgment keeps the same subject, same period, and same field. Semantic recall and relevance do not carry permission or entity isolation duties, and retrieval results do not constitute authorization. A pending review status does not show a lack of operating permission, a quotation validity period does not indicate a supply period, and fields not stated remain unknown.
