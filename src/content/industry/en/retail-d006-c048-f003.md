# Parcel labels and handoffs: shared access for staff training

## What the documents look like

Parcel handoff happens at the point where a package leaves the warehouse, and the carrier scan is the event that carries responsibility. The daily document set for this category is the electronic waybill, the handoff list, the pickup scan record, and the exception parcel register. Updates arrive per batch and per day. In a store-service and internal-training setting, a training lead shares an operating entry point with outlet staff or logistics specialists. The share link is an access path, not a business authorization.

FastGPT v4.17.2 documents a no-login window that creates a temporary address any internet user can open. Costs are billed to the team that owns the application, so the sharing scope needs control. The system generates a localId per user for pulling conversation records from the cloud. This identifier only holds for the same device and same browser; switching devices or clearing browser cache loses those records. Only the most recent 30 days and 20 records can be pulled. Identity verification is scoped to the commercial edition. Once a root address is configured, initialization, conversation start, and conversation end each send a request to that address.

For this page the relevant facts are narrower than the full category. The share link carries a shareId and an authToken as access parameters. Those parameters do not function as authorization credentials. The electronic waybill, handoff list, pickup scan record, and exception register remain the operational documents, and none of them is produced by opening a share link.

## Constraints at the shared access step

The identity verification interface returns success as true together with a uid, and FastGPT then allows the user to continue. The uid is used to pull and save conversation records. The conversation result reporting interface is optional and has no specified return value. In store training, treating a share link as an operating permit confuses retrieval or form entry with authorized execution.

A hypothetical paper exercise sample is set out here. A store training lead plans to share an operating entry point with outlet staff. The material text supplied for comparison reads: "This no-login link has an identity verification root address configured. The initialization and pre-conversation checks both return success as true with uid user1. An expiry time is set and a points cap is filled in. This sharing is for internal training demonstration and is not used for actual pickup handoff authorization." One draft sentence to be judged reads: "Outlet staff who open this link can complete pickup scan confirmation on behalf of the store." That draft sentence equates opening an access link with pickup scan confirmation authorization. The material does not state any scan confirmation permission or handoff authorization. The draft sentence is judged unsupported, and the actual authorization boundary remains to be verified.

The same constraint applies to the reporting interface. A totalPoints or token field inside a reporting request describes what was reported. It does not show that a database write or a balance deduction occurred, because that interface has no specified return value and any deduction requires separate implementation. Likewise, a success response from the initialization interface shows a verification state. It does not contain a pickup handoff execution record.

## Configuration and implementation checks

| Configuration item | Relevant setting or check on this page | Check method |
| --- | --- | --- |
| Identity verification root address | After entry, initialization, conversation start, and conversation end send requests to this address | Compare the configured root address with the interface responses for success and uid |
| authToken concatenation | The share link gains an authToken parameter, and FastGPT carries token in the body | Compare the link parameter with the token value in the authentication interface body |
| Expiry time | After this time the link cannot be used | Compare the link validity period with the training usage period |
| Points cap | The maximum billing data produced by this link | Compare the team that owns the cost with the usage limit |
| Conversation record boundary | localId depends on the same device and browser, and only the most recent 30 days and 20 records are pulled | Check whether a cross-device scenario needs separate identity management |
| Result reporting interface | Optional, no specified return value, contains totalPoints and token | Check whether it is connected and what the data is used for |

The expiry time and points cap values are not documented defaults. If a hypothetical starting value is used in the paper exercise, its reason and the value it is compared against must be stated in the exercise itself. This page does not assign numeric values to those fields.

## Three common errors

1. Treating the shareId or authToken of a share link as pickup scan confirmation authorization. The input is the complete link containing authToken. The comparison is whether the material states a scan confirmation permission. The observable result is that the material does not state that permission, and the draft sentence is judged unsupported.

2. Treating a success response from the identity verification interface as a completed business operation. The input is an initialization interface response returning uid user1. The comparison is whether that response contains a pickup handoff execution record. The observable result is that the interface returns only a verification state and carries no business execution evidence.

3. Treating totalPoints or token in the conversation result reporting interface as an executed points deduction. The input is the totalPoints and token fields in a reporting request. The comparison is whether a database write or balance deduction record exists. The observable result is that the reporting interface has no specified return value, and any deduction requires separate implementation.

## How to verify the setup

1. Take the draft sentence from the hypothetical sample, "Outlet staff who open this link can complete pickup scan confirmation on behalf of the store," as input. Compare it with whether the material text states scan confirmation authorization. If the material states only identity verification and link parameters, the sentence is judged unsupported, and the authorization evidence gap is retained.

2. Take an initialization interface response returning success as true with uid user1 as input. Compare it with whether that response contains a business operation execution state. If it returns only verification success, pickup handoff is not judged complete, and the downstream implementation remains to be verified.

3. Take the authToken parameter in the share link and the token value in the authentication interface body as input. Compare whether the two match. If they match and success is true, identity verification is confirmed as passing. If they do not match or success is not true, record an identity error and do not infer any authorization state from it.

These checks describe expected observations for a paper exercise. They do not report that a test, deployment, approval, or refund took place. Where the material does not state a permission, an execution record, or a downstream write, that evidence remains missing.
