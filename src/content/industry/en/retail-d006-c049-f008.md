# Wholesale stall trading: workflow routing for staff training

## What the documents look like

Wholesale stall trading runs on small, scattered transactions. On-site bargaining, same-day consignment, and WeChat payment collection happen in parallel, and the main materials are purchase sheets, handwritten sales slips, stall lease contracts, and payment receipts. In store service and internal training, these materials are commonly split across workflow nodes: a form input node collects stall, buyer, goods, and payment details, then a user selection node confirms the following branch. The supplied brief gives an update frequency of daily and per order. Verification on this page proceeds document by document, and no batch synchronization or transaction-triggered mechanism is inferred from that frequency.

The two interaction nodes share a documented behavior. When a form input node triggers, the conversation enters an interaction state and the workflow state is recorded; after the user submits the required information, that information is passed to later nodes. When a user makes a selection at a user selection node, the node evaluates the choice and executes the "yes" branch. Both nodes only collect values and decide branches. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval results and similarity values do not carry permission or entity-isolation duties, and a matched material is not an authorization credential.

## Constraints at the workflow routing step

The routing step inherits the scattered shape of stall trading. Each slip, receipt, and consignment note is a separate small unit, so the form input node is the natural point to collect stall, buyer, goods, and payment values, and the user selection node is the natural point to ask about dispatch or collection branches. Neither node performs the business action itself.

Hypothetical paper exercise sample. Material text one: "Stall A issued a handwritten sales slip to Buyer B on 10 March, goods being 200 spring shirts, payment receipt number S-0310, consignment note number T-118, payment status recorded as partially collected." Material text two: "Stall lease contract number Z-022, lessee Stall A, lease term from January to December, signature block carries signatures from both parties." Draft sentence to be assessed: "Stall A has settled all payments from Buyer B and may arrange subsequent dispatch." The draft sentence and material text one take mutually exclusive values on the payment status field. The source text records only partial collection and does not record settlement. The draft sentence is therefore not supported.

The hypothetical starting value in the table is used only for this paper comparison. It is chosen because the field has an explicit value in the sample source text, which allows a word-for-word comparison against the draft sentence. It is not an official default and carries no numeric limit.

## Three common errors

1. Treating form submission as payment settlement or dispatch authorization. Input is material text one and the draft sentence; the comparison point is the payment status field; the observable result is that the source value "partially collected" and the draft value "settled" do not agree, so the draft sentence is not supported.
2. Treating a user selection branch as an already executed external action. Input is the branch connection and the external action division; the comparison point is whether the node only completes a decision; the observable result is that the node does not write an order and does not synchronize external status.
3. Treating a retrieval match or similarity value as a basis for permission or entity isolation. Input is the returned material and the access scope; the comparison point is whether the material falls inside the target scope the operator is entitled to access; the observable result is that a match does not change authorization status, and when the material is missing the gap is recorded.

## How to verify the setup

- Verification one: input material text one and the draft sentence; compare the payment status field; the source records partially collected while the draft records settled; the observable result is that the two values are mutually exclusive, so the draft sentence remains pending verification and is not judged as settled.

- Verification two: input material text two; compare the signature block against the contract effectiveness conditions; the source records only that both parties signed and does not record an effectiveness clause; the observable result is that the signing fact exists while the effective status is not supported, and the evidence gap is retained.

- Verification three: input an explicit paper empty result []; compare how the downstream node is designed to accept an empty input; the observable result is that the downstream handles it through the empty-input branch.
