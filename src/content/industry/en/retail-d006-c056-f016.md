# Producer export tax processes: interactive forms for staff training

## What the documents look like

Producer export tax processes combine the offset of domestic sales tax with the refund of export tax. This combination shapes what staff training and service-desk interactions must collect. A foreign-trade enterprise refund process works with export figures alone; a producer process needs fields for both the domestic offset side and the export refund side in the same form.

The main data sources are the electronic tax bureau, ERP sales records, customs electronic information, and the financial ledger. Monthly is the typical update rhythm. That rhythm does not change the interaction design on this page, so the configuration below does not depend on it.

The working documents are the producer export tax offset and refund declaration detail sheet, the export contract, the sales detail ledger, and the export customs declaration. The three most time-consuming steps are aggregating self-produced exports, calculating the offset and refund, and handling free-on-board price differences. These three steps determine which fields the form must collect and which materials service staff must reconcile.

## Constraints at the interactive forms step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The node collects the information the user fills in and passes it to later nodes. It does not include a business database function of its own.

The user selection node also triggers the interaction state and records the workflow state. It evaluates the user's choice and executes the corresponding branch. Field validation, business approval, write-back, and batch operations must be implemented in an external system or in later nodes. Retrieval or form submission by itself does not constitute authorized execution.

Hypothetical paper exercise sample: in August 2025, a tax accountant at a producer export enterprise holds an export contract (contract number HT-2025-08; seller, Producer Enterprise A; buyer, Overseas Company B; goods, self-produced Model A motor; trade term, FOB; amount, USD 120,000; signing date, 20 July 2025) and an export customs declaration (declaration number BG-2025-08-001; domestic consignor, Producer Enterprise A; FOB value, USD 120,000; export date, 5 August 2025). The proposed sentence for review is: "Producer Enterprise A's export business in this batch already meets the conditions for filing the offset and refund declaration and may be submitted." The question to decide is whether the two materials above support that proposed sentence.

## Configuration and implementation checks

| Configuration item | Type | Description |
| --- | --- | --- |
| Form input node | Existing node behavior | Enters the interaction state on trigger, collects filled-in information, and passes it to later nodes |
| User selection node | Existing node behavior | Enters the interaction state on trigger and executes a branch according to the choice |
| Required-field list | Implementation check item | Lists the subject, period, document number, amount, and trade term that this task cannot omit |
| Field validation logic | Requires a separate system implementation | The node does not include validation; it must be implemented in later nodes or an external system |
| Post-submission handling | Requires a separate system implementation | Business approval, database writes, and external synchronization are implemented as needed |
| Missing-item handling | Manual reconciliation action | When an item is missing, record the gap; do not automatically treat it as a denial or a conflict |

## Three common errors

1. Treating form submission as authorized execution. The form input node collects information and passes it to later nodes; it contains no approval or business authorization function. A successful submission means only that the interaction finished.
2. Treating the user selection node as a personnel directory or business-data selector. The node executes a branch according to the choice; it does not perform entity filtering or permission isolation.
3. Treating retrieval relevance as a permission or entity filter. A similarity setting does not exclude unrelated business or unauthorized records, and a retrieval result is not a basis for authorization.

## How to verify the setup

1. Enter the contract and customs declaration information from the hypothetical sample above, then compare whether the fields the form collects cover the subject, period, document number, amount, and trade term. If the fields are passed complete to later nodes, the collection scope meets the condition; if any item is missing, record the gap.
2. Enter the proposed sentence "Producer Enterprise A's export business in this batch already meets the conditions for filing the offset and refund declaration and may be submitted," then compare that sentence with what the two materials record. The materials record only the contract signing and the customs export facts; they do not record that the declaration conditions are met or that approval has been granted. The proposed sentence is unsupported, so record the evidence gap and do not judge it as a denial or a conflict.
3. Enter an empty form submission request, then compare the node behavior with the required-field list. If the node blocks submission and indicates the missing items, the required-field validation is in effect; if the node allows an empty submission and continues execution, the validation is not in effect and must be supplied in later nodes.
