# Livestream after-sales service: workflow routing for staff training

## What the documents look like

Livestream after-sales work arrives in bursts after a single broadcast session. Refund applications and reshipment orders cluster in the same window, and the handling outcome is closely tied to what the host promised on air. In the store service and internal training setting, the workflow routing step works with four document types: the livestream order list, refund applications, reshipment orders, and script templates. These materials come from the shop after-sales system, customer service IM, the warehouse WMS, and logistics tracking. They update after each session and daily.

The routing difficulty is that refund applications and reshipment orders require fields filled in by store staff or customer service, and the filled result then determines the branch taken. The Form Input node and the User Selection node are both user interaction nodes. When either is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. Form Input collects required information and passes it to later nodes. User Selection judges the user's choice and executes the corresponding branch. These nodes only collect information and direct the branch. Order writes, reshipment order generation, and external status synchronization require a separate business interface or a downstream process.

## Constraints at the workflow routing step

An interaction node enters a waiting state, so the routing design must preserve the filled content and the branch basis during that wait. The User Selection node verifies branch connections one by one; a branch that is not connected does not execute. Form output must be explicitly passed to the later retrieval, judgment, or interface node, and output must be compared item by item against input so that a field name mismatch does not cause the downstream node to read an empty value.

Retrieval and forms do not constitute authorization. A similarity or relevance setting does not exclude unrelated business records or unauthorized records, and a retrieval result cannot serve as a release basis. Libraries built on different vector models cannot be associated together; the identifier must be checked first and non-matching libraries excluded, and a cross-model retrieval must not be run to compare missed recall. An empty result can be handled by checking the downstream design against a paper input of []. A document's overall flowchart listing an optional path does not mean every request executes all paths: image retrieval requires a corresponding image input and model capability, and reranking requires a model and must be enabled according to its setting.

Hypothetical drill sample: the source material reads, "Store A submitted a refund application on March 12, order number H-2031, reason: livestream-promised gift not shipped, application status is pending review." The proposed handoff request to judge is, "Transfer this refund application directly to a reshipment order and notify the warehouse to ship." The comparison point: the application status is pending review, and pending review does not equal approved. Transferring to reshipment and notifying the warehouse to ship are business actions that require a corresponding interface and authorization. The current material records no approval and no shipping authorization, so this request is not supported.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Reason and comparison method |
| --- | --- | --- |
| Form Input node | Enabled, with fields for order number, reason, and application status | Collects fields needed for later branching; compare item by item against order list fields |
| User Selection node | Enabled, with "to reshipment" and "to refund" branches | Branches on the filled result; verify branch connections one by one |
| Interaction state recording | Records workflow state per node behavior | Compare against the documented interaction node behavior; no separate switch is set |
| Form output handoff | Explicitly passed to the later judgment or interface node | Compare output field names against downstream input field names |
| External action split | Order writes and status synchronization use a separate business interface | Check whether the interface actually exists; record the gap when it is missing |
| Retrieval association check | Check library identifier and vector model identifier | Only the same model may be associated; different models are excluded |

## Three common errors

1. Treating a refund application that is pending review as approved and transferring it to reshipment. In the sample, the application status is pending review. Pending review does not demonstrate approval, and the transfer to reshipment and the warehouse shipping notification lack an authorization basis.
2. Letting the form output field name differ from the downstream input field name, so the downstream node reads an empty value. In the sample, the form collects the order number and application status. If the downstream node reads under a different field name, the comparison does not match.
3. Using a relevance or similarity setting to exclude unrelated business records. Relevance is not a category, entity, or permission filter, and a retrieval result does not constitute a release basis.

## How to verify the setup

1. Input the sample source text and the proposed request, and compare the application status field value against the condition for the later action. If the status is pending review while the later action requires approval, the request is not supported. If an approval record appears and the authorization scope covers reshipment, check again.
2. Input the form filled result, and compare the output field names against the downstream node input field names. If each item matches and the downstream value is not empty, the handoff holds. If a field name differs or the downstream value is empty, record the gap.
3. Input the retrieval library identifier and the vector model identifier, and compare whether both use the same model. If the identifiers match, association is possible. If they do not match, exclude the non-matching library and record the actual observation; do not run a cross-model retrieval to compare missed recall.

This page addresses only livestream after-sales centralized handling, store service and internal training, and workflow routing. During operational handoff, the authorization status of materials, actions, and requests must be kept clear, and retrieval or form submission must not be treated as authorized execution.
