# Livestream violation appeals: shared access for staff training

## What the documents look like

Livestream violation appeals address penalties that have already been issued, so the working file is built around a violation notice, livestream recording, product qualification materials and a draft appeal statement. In the store-service and internal-training setting, these materials are handed to store staff for review, supplementation or cross-checking, and sharing and embedding is the mechanism that delivers an appeal-support application to the store side through a link. The materials update irregularly, once per violation event, and the validity scope of a shared link follows the current appeal task rather than a fixed schedule.

Two features of this category shape the sharing step. First, the appeal addresses an event that has already occurred, so the evidence chain must be reconstructed from the notice, the recording and the qualification file; the shared entry point only exposes an application, and it does not by itself establish who may act on the appeal. Second, the typical participants are store compliance staff, livestream operations staff and legal staff, whose access rights differ, so the identity returned by a verification interface is the operative signal for staff identity while the link identifier is not.

## Constraints at the shared access step

The no-login window is created from the application detail page under publish channels, and the system generates the full link. The link identifier controls access to the application; it does not grant business authority to store staff. Anonymous access relies on a local identifier generated on the same device and the same browser, records do not carry across devices, and this mode permits pulling only the most recent 30 days and 20 records. Identity verification is a POST request root address; initialization, conversation start and conversation end each send a request to the corresponding interface, and the server returns success as true to allow continuation. The uid must be returned as a string that excludes specific characters and does not exceed 255 bytes. Identity verification falls within the commercial edition scope.

Hypothetical drill sample: a store submits a draft appeal statement whose source text reads, "This store received a violation notice on 12 March 2026; the product concerned is a batch A prepackaged food item; the livestream recording period is 20:00 to 21:00 on that day; this store now requests review." The pending request reads, "Please submit this appeal statement to the platform through the shared link and complete the appeal." The materials contain a subject, an object and a time range, and they do not contain a platform acceptance status or a submission authorization.

## Three common errors

1. Treating the shared link identifier as business authorization for store staff. The link only controls the access entry point; identifying store identity requires the identity verification interface to return a uid, and the two cannot substitute for each other.

2. Treating a success return from the identity verification interface as the appeal having been submitted. The interface only decides whether the conversation may continue; submitting an appeal requires separate acceptance on the platform side.

3. Treating the anonymous local identifier as a store account usable across devices. That identifier is valid only on the same device and the same browser, and records do not carry over after switching devices.

Corresponding checks: confirm whether the identity verification address in the link configuration is filled in and returns a uid; confirm whether the draft sentence contains a submission authorization statement, and record it as pending verification when the source text does not state one; confirm whether the store's device and browser are consistent, and record a record gap when they are not.

## How to verify the setup

- Verification one: input the sample source text and the draft request, and compare whether the source text contains a platform acceptance status or a submission authorization. When the source text does not state either, record the result as pending verification, and do not record it as submitted.

- Verification two: input the content returned by the identity verification interface, and compare the success field with the uid field. When success is true and the uid format is compliant, the release condition is met; otherwise record the result as not passed.

- Verification three: input the store's device and browser information, and compare whether they match the first visit. When they match, the local identifier can continue; when they do not, record a record gap, and do not infer that the account has become invalid.
