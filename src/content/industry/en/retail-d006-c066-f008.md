# Short-video affiliate sales: workflow routing for staff training

## What the documents look like

Short-video affiliate sales rely on long-term content exposure and product-link conversion rather than live explanation. In store-service and internal-training settings, content operators, creator business-development staff and product distribution specialists work across four document types: short-video scripts, attached-product lists, commission plans and violation feedback. The correspondence between a script and its product list, the applicable status of a commission plan, and the handling stage of a violation feedback record together determine whether a handover request can move to the next step. The supplied brief gives daily and weekly update frequencies; this page does not derive batch synchronization or transaction-triggered mechanisms from that frequency.

In FastGPT v4.17.2, the Form Input node is a user-interaction node. When it is triggered, the conversation enters an interaction state, the workflow state is recorded, and after the user completes required fields and submits, the node collects the submitted form information and passes it to later nodes. The User Selection node is also a user-interaction node. When triggered, the conversation enters an interaction state; when the user makes a selection, the node evaluates that selection and executes the "yes" branch. Workflow routing for store service and internal training therefore keeps materials, operations, the authorization status of a request, and values collected by interaction nodes as separate concerns: retrieval and collected form values do not constitute authorized execution.

## Constraints at the workflow routing step

When the field definitions of scripts, product lists, commission plans and violation feedback differ, values collected by the Form Input node can only serve as input to later judgments. Business verification, approval, database writes and external synchronization require a separate business interface or a later process. The "yes" branch of the User Selection node must be verified connection by connection; it cannot be assumed that every branch points to a configured downstream node. The interaction state is behavior of the interaction nodes, and no separate global state-recording switch is documented.

Hypothetical paper exercise sample: the source material states, "Store A submitted short-video script S-01 and attached-product list G-01 on 1 March 2025; commission plan C-01 is marked pending review; violation feedback F-01 is recorded as submitted and unhandled." The handover request to be assessed is, "Move S-01, G-01, C-01 and F-01 together to the next step and treat them as authorized for execution." That request treats a pending-review status and a submitted-and-unhandled status as completed authorization. It lacks approval and handling evidence and is unsupported.

## Configuration and implementation checks

| Configuration item | Relevant setting or check on this page | Correspondence to the sample |

| Form Input node | Trigger enters the interaction state, collects required information, and passes it to later nodes after submission | Collects submitted information for S-01, G-01, C-01 and F-01 |
| User Selection node | Executes the "yes" branch after the user makes a selection; verify branch connections one by one | Assesses whether the handover request moves to the next step |
| Interaction-state check | Recorded state is behavior of the interaction nodes; no separate global switch is documented | Checks whether state is recorded before and after submission |
| Output handover check | Pass collected information explicitly to later retrieval, judgment or interface nodes | Compares output values with inputs such as S-01 |
| External-operation split | Order writes, document backfill and external status synchronization require a separate business interface or later process | C-01 approval and F-01 handling are not completed at these nodes |
| Hypothetical trial starting point | This exercise treats C-01 pending review as incomplete and compares it with the value "reviewed" | Reason: pending review does not equal completed approval |

## Three common errors

1. Treating submitted values collected by the Form Input node as authorized execution. In the sample, C-01 is marked pending review; the submission action only completes information collection, and approval must be implemented by a later process.
2. Treating the "yes" branch of the User Selection node as already executed. Branch connections must be verified one by one; in the sample, the handover request entering a branch does not mean the next step has received it.
3. Writing violation feedback F-01, recorded as submitted and unhandled, as completed handling. Submission and handling are two distinct facts; when handling evidence is absent, the status remains to be verified.
