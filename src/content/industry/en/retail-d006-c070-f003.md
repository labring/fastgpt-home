# Cross-border product labels: shared access for staff training

## What the documents look like

Cross-border product compliance and labelling work happens before listing and import. The core activity is assembling product safety and label evidence. The documents handled day to day include product test reports, English-language labels, MSDS files, and platform prohibited-item lists. These materials are updated irregularly, and each new product launch requires rechecking destination-country requirements.

In store service and internal training, sharing and embedding means handing compliance materials or training content to store staff as a link. The no-login window creates a temporary address that any internet user can open, and costs are billed to the team that owns the application, so the sharing scope needs control. The system generates a localId per user to pull conversation records. That identifier works only on the same device and the same browser; switching devices or clearing browser cache loses the records. The system allows pulling only the most recent 30 days and 20 records.

## Constraints at the shared access step

The readers of compliance documents are store staff and trainees. Once a link is forwarded, unauthorized people can open it. The no-login link identifier cannot be treated as business authorization; identity verification must be implemented by connecting a separate system. Identity verification is available only in the commercial edition. After a root address is configured, initialization, conversation start, and conversation end each send a POST request to that address. The server returns success as true to allow the user to continue. The uid must be returned and must be a string that excludes the characters "|", "/", and "\\" and is no longer than 255 bytes.

Conversation record boundaries need attention. The localId depends on the same device and same browser. Cross-device records require a separately designed identity and session management approach.

Hypothetical drill sample: A store training lead plans to share a compliance training link with 12 stores in the East China region. The material text to be checked reads: "Product test report number TR-2024-0317, applicable product is a portable power bank, destination country is Germany, report issue date is 17 March 2024, report conclusion is compliance with EN 62368-1." The draft sentence to be judged reads: "This test report already covers all power bank models on sale on the Germany site, and stores can cite it directly." The comparison object is whether the coverage scope of the report text and the draft sentence agree.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting value for this page | Reason for the choice and comparison method |
| --- | --- | --- |
| Link name | East China compliance training 2024Q2 | Used only for record display; corresponds to store region and training batch |
| Expiration time | 30 June 2024 | Set by the training cycle; compared with the training end date |
| QPM | 10 | Estimated from per-store visits per minute; compared with concurrent store headcount |
| Points cap | 5000 | Estimated from trainee count and per-conversation consumption; compared with historical usage |
| Identity verification root address | Store system authentication service address | Must return success and uid; compared with the interface response format |
| View quote snippets | Enabled | Lets store staff check the source of training content |

QPM means the maximum number of visits per user per minute. The points cap is the maximum billing data produced by the link. Some parameters are configurable only in the commercial edition.

## Three common errors

1. Treating the no-login link identifier as business authorization. The link can be forwarded, and anyone who obtains the address can open it. Check method: inspect whether the identity verification root address is configured, and compare whether a request without authToken is rejected.

2. Extending the applicable scope of a test report to untested models. In the hypothetical sample the report covers only a portable power bank, while the draft sentence claims coverage of all models on sale. Check method: compare the product scope in the report text with the claimed scope in the draft sentence, and observe whether the two agree.

3. Treating localId as a cross-device identity credential. localId is valid only on the same device and same browser. Check method: compare conversation records when the same link is opened on different devices, and observe whether the records continue.

## How to verify the setup

1. Input the report text and the draft sentence from the hypothetical sample, and compare the product scope in the report with the claimed scope in the draft sentence. If the claimed scope in the draft sentence exceeds the report text, the sentence is unsupported and must be revised to a scope consistent with the report.

2. Input a share link request without authToken, and compare the success value returned by the identity verification interface. If success is not true, the request is rejected, which matches the identity verification expectation.

3. Input an initialization request carrying authToken, and compare the format of the uid returned by the interface. If the uid contains the characters "|", "/", or "\\" or exceeds 255 bytes, an Invalid UID error is returned, and the uid format must be corrected before rechecking.
