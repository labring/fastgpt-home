# Cross-border settlements: workflow routing for staff training

## What the documents look like

Cross-border platform settlement and foreign-exchange work concerns the collection of funds from orders that have already been completed. It does not handle fraud chargebacks, which belong to payment risk control. The main data sources are the platform settlement center, bank statements, payment institution back office, and ERP orders. The documents handled day to day are platform settlement statements, exchange rate tables, service fee invoices, and receiving reconciliation sheets. Update frequency is weekly or monthly.

In store service and internal training, workflow routing has to connect the collection of these documents with staff actions into steps that can be reviewed. The authorization state of materials at handover determines whether a later action may run. The Form Input node and the User Selection node are user interaction nodes. When either is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The Form Input node collects the required information the user fills in and passes it to later nodes. The User Selection node judges the user's choice and executes the corresponding "yes" branch.

## Constraints at the workflow routing step

Interaction nodes collect form values and selection results. Retrieval or a submitted form does not constitute authorization. Order writes, document backfill, and external state synchronization require a separate business interface or a later process. The following is a hypothetical drill sample.

Hypothetical drill sample: the original text of an internal training handover sheet at a store reads: "Settlement statement period: March 2024; entity: Store A finance role; object: one platform settlement statement PDF; status is pending review by the store supervisor; authorization scope: internal reconciliation checking only, excluding outbound payment." The draft sentence to be judged reads: "The Store A finance role has completed the review of the March settlement statement and may execute foreign-exchange payment."

In this sample, pending review does not constitute completed review, and the authorization scope explicitly excludes outbound payment. The subject, status, and authorization boundary in the draft sentence all fail to match the original. Workflow routing needs to place this kind of judgment in the step that follows the interaction nodes, comparing input and output item by item. The interaction state and state recording are behaviors of the interaction nodes; no separate global state recording switch is documented.

## Configuration and implementation checks

| Configuration item | Type | Description |
| --- | --- | --- |
| Form Input node | User interaction | Enters the interaction state when triggered, collects required information, and passes it to later nodes after submission |
| User Selection node | User interaction | Executes the corresponding "yes" branch after the user makes a choice; verify branch connections one by one |
| Interaction state check | Implementation check | State recording is a behavior of the interaction node; do not set or claim a global state recording switch |
| Output handoff check | Implementation check | Pass collected information explicitly to later retrieval, judgment, or interface nodes; compare output against input item by item |
| External action division | Implementation check | Order writes, document backfill, and external state synchronization require a separate business interface or a later process |

The hypothetical trial starting point for this page is a Form Input node configured with two required fields: settlement statement period and entity name. This starting point is chosen because the sample original text contains two judgment elements, period and entity, which need to be compared item by item against later node output. The comparison object is the field values passed downstream after node submission. This starting value is a hypothetical trial starting point, not an official default.

## Three common errors

1. Treating pending review status as completed review. The sample original text states "pending review by the store supervisor," while the draft sentence says "has completed the review." The check is to take the sample original text and the draft sentence as input, compare the status field values, and observe that the original is pending review while the draft is completed. When the two do not match, the draft does not hold.
2. Extending internal reconciliation authorization to outbound payment. The sample original text states the authorization scope as "internal reconciliation checking only, excluding outbound payment," while the draft sentence says "may execute foreign-exchange payment." The check is to compare the authorization scope field and observe that the draft action exceeds the original scope. When it exceeds, the draft is beyond authority.
3. Treating a retrieval result as a basis for authorization. If a workflow triggers a payment branch directly after a retrieval node returns a settlement statement, the check is to compare the retrieval output against the authorization field. When the retrieval result does not contain an authorization clause, the payment branch lacks a condition for execution.

## How to verify the setup

1. Input the sample original text and the draft sentence, compare the three fields of subject, status, and authorization scope, and observe that the draft sentence disagrees with the original in at least two of the three fields. When this is observed, the draft does not hold.
2. Input the sample original text and the handover request "the Store A finance role submits the March settlement statement for supervisor review," compare the requested action against the original status, and observe that the requested action matches the pending review status. When this is observed, the request may enter the interaction node and wait for the supervisor's choice.
3. Input an empty-result handoff scenario, using the explicit paper input [] to check the downstream design, observe the branch direction of the downstream node when there is no retrieval result, and record the actual observation. Do not presuppose a fabricated rule that retrieval necessarily returns an empty value.
