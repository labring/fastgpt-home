# Cross-border payment reviews: workflow routing for staff training

## What the documents look like

Cross-border standalone-site payment risk control centres on card network disputes and receiving accounts, so the working materials are payment chargeback notices, fraudulent order lists, invoices and proof of delivery. These come from the payment service back office, the order system, the carrier and customer service email. The brief records an update rhythm of daily or per order. That rhythm describes how often the materials may change; it does not establish batch synchronisation, full synchronisation, real-time updates or transaction-triggered mechanisms.

For store service and internal training, a risk specialist and a finance settlement role hand these materials to frontline staff or trainees for checking before any next action is decided. The three most time-consuming steps named in the brief are identifying high-risk orders, preparing chargeback evidence and tracking frozen funds. Routing work at this stage therefore concerns which collected values and which branch decisions move forward, and what still requires a separate business interface.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it is triggered, the conversation enters an interaction state and the workflow state is recorded; after the user completes the interaction, execution continues downward. The node collects the required information the user fills in and passes that information to later nodes. The User Selection node is also a user interaction node with the same interaction state and state recording, and when the user makes a choice the node evaluates that choice and executes the "yes" branch. Both nodes can be added repeatedly and both trigger execution.

For this training scenario, a handover request splits into two kinds: field values collected by a form, and a branch direction fixed by a user selection. Retrieval and forms do not constitute authorisation. Order writes, document backfill and external status synchronisation require a separate business interface or a later process. The form collects values; business verification, approval, database writes and external synchronisation need their stated downstream implementation.

Hypothetical paper exercise sample. A chargeback notice reads: "Dispute number A-001, card network is Example Card Network, cardholder claims goods not received, merchant must submit proof of delivery after receiving this notice." A proof of delivery reads: "Waybill number B-002, delivery date is the example date, recipient field is blank." A draft sentence awaiting judgement reads: "The proof of delivery is complete and can be submitted directly as the dispute response." The source text carries a subject, an object and a status, while the recipient field is blank. Completeness and submittability both remain unsupported.

## Three common errors

1. Treating a field value collected by the form as authorisation. In the sample, the form can collect the dispute number and the waybill number and pass them to later nodes, while an order write still requires a separate business interface. The check input is the form output; the comparison object is whether the later node declares a business interface; the observable result is that the action remains unimplemented when the interface is absent.

2. Treating the "yes" branch of a user selection as already executed. In the sample, the user selection can fix a branch direction, while actually submitting a dispute response is an external operation. The check input is the branch connection; the comparison object is whether an external operation declaration appears; the observable result is that the submission state is unsupported when only the branch is present.

3. Treating a retrieval result as entity isolation. The same-vector-model requirement for retrieval libraries is limited to shared association and cannot be extended to a business registration site or another external system. The check input is the library identifier; the comparison object is the vector model identifier; the observable result is that the library is excluded when the identifiers do not match.

## How to verify the setup

- Verification one. Input the sample chargeback notice text and the draft sentence "The proof of delivery is complete and can be submitted directly as the dispute response." Compare whether the draft sentence is supported by the content of the recipient field. The recipient field is blank, so the sentence is unsupported and the evidence gap must be recorded.

- Verification two. Input the sample proof of delivery text and a handover request reading "Write waybill number B-002 into the order record." Compare whether that request declares a business interface. The workflow routing nodes themselves do not perform writes, so the request remains pending implementation.

- Verification three. Input two retrieval library identifiers and their respective vector model identifiers. Compare whether the identifiers match. When they do not match, exclude that library, do not run cross-model retrieval, and record the actual observation. A relevance score is not a category, entity or permission filter, and retrieval is not authorisation.
