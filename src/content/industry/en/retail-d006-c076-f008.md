# Creator commission settlement: workflow routing for staff training

## What the documents look like

Creator commission settlement and commission deduction happen after a sale closes. The central work is confirming valid promotion and handling after-sales commission deductions. The public brief lists four data sources for this category: the Selected Alliance backend, order after-sales data, the finance system, and creator contracts. The daily materials are commission setting records, settlement bills, refund commission deduction details, and invoices. In the store service and internal training setting, these materials move between operations, finance, and training staff through a workflow, and the information a node collects has to support the later reconciliation and handover steps.

The brief marks this category as different from creator special-session cooperation because commission settlement occurs after the transaction closes, with the emphasis on valid promotion and after-sales commission deduction. It also states the update frequency as weekly and monthly. That frequency does not change what the routing nodes in this page do, so it is not treated as a routing condition here. The three most time-consuming steps named in the brief are reconciling valid orders, deducting refunded commission, and invoicing and payment. Workflow routing sits before those steps and only carries the collected values forward.

## Constraints at the workflow routing step

The two documented interaction nodes in FastGPT v4.17.2 are Form Input and User Selection. Both are user interaction nodes, both can be added repeatedly, and both trigger execution. When either node is triggered, the conversation enters an interaction state and the workflow state is recorded; after the user completes the interaction, the workflow continues downward. The Form Input node collects the required information the user fills in and, after submission, passes that information to later nodes. The User Selection node judges the user's choice and executes the "yes" branch.

Neither node performs order writes, document backfill, or external status synchronization. Those actions require a separate business interface or a later process. A retrieval result is not authorization, and a similarity score does not exclude unrelated business records or unauthorized records. The public brief does not provide an error code, a default limit, or an automatic business action for this step, so none is asserted here.

Hypothetical paper exercise sample. The material text under review reads: "Creator A and Store B signed a commission agreement stating that the June 2025 special-session commission is confirmed against the settlement bill, and the commission for refunded orders is deducted in the following month's bill. The agreement is pending review and has not been signed." The draft sentence to be judged reads: "Creator A's June commission has completed commission deduction and entered payment." The subjects needed for the judgment are Creator A and Store B; the objects are the June settlement bill and the refund commission deduction details; the state is that the agreement is pending review. The material text does not state signing, completion of commission deduction, or payment, so the draft sentence goes beyond what the material supports.

## Configuration and implementation checks

| Check item | Hypothetical starting value for this exercise | Reason for the choice and comparison method |
| --- | --- | --- |
| Required fields on the Form Input node | Creator identifier, settlement period, bill number | Compare item by item against the subjects and objects in the material text; record a gap when an item is absent |
| Branch on the User Selection node | The "yes" branch carries the confirmation result | Compare against the state in the source text; a pending-review state must not run the confirmation-complete branch |
| Interaction state recording | The workflow state is recorded after the node is triggered | Check against the documented node behavior; no separate global state switch is set |
| Output handover target | Pass the collected information to a later reconciliation node | Compare each output field against the input fields for consistency |
| Division of external actions | Order writes and status synchronization connect to a separate interface | Compare against the documented statement that the node itself does not carry out this action |

These values are starting points for this paper exercise only. They are not official defaults, and no numeric limit, unit, menu, or global switch is taken from the documentation.

## Three common errors

1. Treating a pending-review agreement as signed. The material text states the agreement is pending review, while the draft sentence says commission deduction is complete and payment has started. The input is the pending-review state; the comparison object is the signing and payment facts; the observable result is that the source text lacks evidence for both.

2. Treating form submission as authorized execution. After a Form Input submission, the node only passes information forward. The input is the required information the node collected; the comparison object is the division of external actions; the observable result is that the node has not triggered any business interface.

3. Treating a retrieval hit as a permission confirmation. Retrieval results and similarity scores do not perform entity isolation. The input is the returned retrieval content; the comparison object is the authorization boundary; the observable result is that evidence of an authorization clause is absent.

## How to verify the setup

1. Use the hypothetical source text and draft sentence above. The input is the pending-review agreement together with the bill and deduction-detail materials. Compare "has completed commission deduction and entered payment" in the draft sentence against the state in the source text. The sentence is supported only when the source text shows signing, completed commission deduction, and a payment record. The current observation is that it is not supported.

2. Check the branch connection. The input is the pending-review state and the "yes" branch of the User Selection node. Compare whether the pending-review state triggers that branch. The branch connection holds only when the node judges the user's choice as documented and executes the corresponding branch. The current record is that this remains to be verified.

3. Check the output handover and the external action. The input is the creator identifier, period, and bill number collected by the form. Compare whether the later node receives these fields and whether order writing connects to a separate interface. The condition is met only when the fields match item by item and the external action is carried by an interface. The current observation is that a separate implementation is required.
