# Import and export permits: interactive forms for staff training

## What the documents look like

Import and export permit handling takes place before customs declaration and determines whether goods can legally cross the border. The documents in daily use include automatic import licences, dual-use item licences, contracts and product descriptions. In store service and internal training work, staff match the materials a client submits to the permit type being prepared, judge the regulatory document category, prepare the end-use statement and follow the approval status. Materials change at irregular intervals, once per shipment; this frequency only indicates that materials change with each shipment and does not imply batch synchronisation or a transaction-triggered mechanism. The form and interaction step is responsible for collecting the elements of these materials and passing them to later nodes. Business approval and write-back require a separate system implementation.

## Constraints at the interactive forms step

When the form input node is triggered, the conversation enters an interactive state, the workflow state is recorded, and execution continues after the user completes the interaction. The node collects the information filled in and passes it to later nodes; it does not include a business database function. The user selection node executes a branch according to the user's choice and is an interactive node, not a personnel directory or business data selector. Field validation, business approval, write-back and batch operations are implemented as needed in an external system or later nodes.

Hypothetical drill sample: the source material reads, "This unit is entrusted by an overseas buyer and intends to import in March 2025 a batch of ball screws for CNC machine tools, commodity code 8483.90, contract number HT-2025-031; the buyer's end-use statement records that they are for maintenance of the assembly line in its own factory." The handover request to be assessed is, "Please have the store receive the documents under the dual-use item licence process and forward them for approval." The source text states only the goods and the use; it does not state the regulatory document category corresponding to that code, nor does it state a conclusion on dual-use item licensing. The document category in that request is unsupported and remains to be verified; it cannot serve as a confirmed basis for receiving documents.

The values in the table are only the hypothetical starting point for this trial. This starting point was chosen so that both a missing-field input and a completed input have an observable object, and so that they can be compared with the interactive behaviour described in the documentation. Unstated default values, submission counts and automatic judgments are not set.

## Three common errors

1. Treating fields collected by the form as business authorisation. The input is the intake form for the sample above; compare the form values with the approval status. A submitted form does not mean the approval has passed.
2. Treating the branch result of the user selection as a document category determination. The input is the sample request; compare the selection result with the source end-use statement. When the source does not state a category, the selection result is not a basis for determination.
3. Treating a retrieval hit as permission or entity isolation. The input is a query within a restricted scope; compare the returned records with the access rights list. A similarity score does not exclude unrelated business or unauthorised records.

## How to verify the setup

1. Missing-field check: input the sample material with the commodity code removed, and observe whether the node remains in the interactive state; then complete the field and observe whether execution continues.
2. Branch check: input the sample request, select "dual-use item licence", and compare that selection with the source end-use statement. When the source does not state a category, record it as pending verification.
3. Empty-result handling: use the paper input [] to check the downstream design, and observe how later nodes handle a case with no return. Do not claim that a search of a fictional rule necessarily returns empty.

All three checks use the hypothetical sample as their object. The expected phenomenon is that the interactive state and the branch direction match the documentation. Approval, write-back and authorisation status remain unexecuted, and missing evidence remains recorded as missing.
