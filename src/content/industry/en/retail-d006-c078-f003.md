# Chain-store site selection: shared access for staff training

## What the documents look like

Site selection and store opening happen before a store trades. The work centres on lease negotiation and construction handover. Shopping-district footfall, map POI data, historical store-type POS records and landlord materials form the main inputs. The working documents are the site evaluation form, the letter of intent for lease, the fit-out budget and the opening schedule. These materials update per store on an irregular rhythm.

In the store service and internal training step, sharing and embedding act as the access channel that lets regional development staff, engineering managers and external collaborators view those materials. The materials carry a strong stage attribute: an unsigned letter of intent, an unaudited budget and an unconfirmed schedule are all process states. A share link only provides an access entry point. It does not change the state attribute of the material.

## Constraints at the shared access step

The no-login window is created from the publishing channel and the complete generated link is copied. The link identifier serves access only and cannot be treated as business authorization. Expiry time and QPM are set for the intended scope and checked against the actual version; QPM means the maximum number of visits per user per minute. The points cap constrains the billing data produced by the share entry, and some parameters are restricted by version. Identity verification connects the share link to a third-party system and is limited to the commercial edition; release is decided by the success and uid values returned by the interface. The anonymous local identifier depends on the same device and the same browser, so cross-device records need separate identity and session design.

Hypothetical paper exercise sample: a chain headquarters development department intends to share one Site Evaluation Form with an external engineering manager for viewing. The source material reads: "Object: street-front unit on XX Road; Stage: intent discussion; rent-to-sales ratio calculation: pending regional review; fit-out budget: not audited. This form is for internal evaluation only and does not constitute a lease commitment." The proposed sentence is: "The rent-to-sales ratio for this unit has passed review, the budget has been audited, and the unit can proceed directly to the signing schedule." The handover request to be judged is: ask the engineering manager to confirm the schedule using this link.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason for the choice and comparison method |
| --- | --- | --- |
| Share link name | Site Evaluation Form - intent stage | The name is used for record display only; matching it to the material stage is sufficient |
| Expiry time | Set to the expected end date of intent discussion | Compare against the validity range of the material stage; the link fails after that point |
| QPM | Estimated from the number of external collaborators | Compare against the per-user per-minute access demand |
| Points cap | Set from the estimated usage of this share | Compare against the billing data produced by the share entry |
| Identity verification | Enter the third-party root address | Check release against the success and uid values returned by the interface |
| Conversation records | Rely on the same device and same browser | Design identity and session management separately for cross-device scenarios |

## Three common errors

1. Treating the link identifier as business authorization. A reachable link does not mean the material has been reviewed or the budget audited. The check input is the proposed sentence and the source material; the comparison is between "has passed review" and "pending regional review"; the observable result is that the two states do not match.

2. Treating a pending review as a lack of operating permission. The material stage is intent discussion, which is a process state, and no conclusion about the engineering manager's viewing permission can be drawn from it. The check input is the material stage field; the comparison is between the stage description and the permission description; the observable result is that the material states no permission conclusion.

3. Treating retrieval or a form as authorized execution. A form collects values; business verification, approval, database writes and external synchronization each need their own downstream implementation. The check input is the handover request; the comparison is between the requested action and the state recorded in the material; the observable result is that the request goes beyond the scope of the material.

## How to verify the setup

1. Input the source material and the proposed sentence from the hypothetical sample. Compare "pending regional review" and "not audited" against "has passed review" and "has been audited", and observe whether the proposed sentence matches the source state. The expectation is that it does not match, and the proposed sentence must be returned for revision.

2. Input the handover request "ask the engineering manager to confirm the schedule using this link". Compare the requested action against the stage recorded in the material, and observe whether the request goes beyond the scope of the material. The expectation is that it does, and an authorization basis must be added or the request adjusted.

3. Input the response from the identity verification interface. Compare the success field and the uid format, and observe whether release occurs. The expectation is release when success is true and uid meets the format, and an error prompt otherwise. A retrieval check observes only the actual return; it does not guarantee a first-hit match or that an unrelated query returns empty. An empty result can be checked against the downstream design using the paper input [].
