# B2B marketplaces: HTTP integrations for operating reviews

## What the documents look like

B2B marketplace matching depends on online certification and electronic contracts, so the records behind operating reports and exception reviews are not stall-side notes. Corporate certification materials, quotation sheets, electronic contracts and platform settlement statements sit alongside payment flows and logistics traces, and they update daily and per order. A report or review that pushes these records into an external system through an HTTP module can only carry values that already exist in the source material. The request does not perform identity review, does not make a contract effective and does not confirm settlement.

Because certification and contracting happen online, the same supplier or buyer can appear in several records with different states. A certification record may still be pending while a quotation is already valid for a stated period. The operating review has to keep those states separate rather than collapsing them into one "active counterparty" label.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a configured address. Params, Headers and Body can each reference global variables, system variables and preceding node outputs through `{{}}`, and the URL can also reference variables. Returned values are extracted with JSON path syntax, and when the output type is set to string the corresponding value is formatted as a JSON string.

System variables include appId, chatId, responseChatItemId, variables, cTime and histories. The chatId and responseChatItemId values do not exist in test mode, so an empty value during debugging reflects that environment difference rather than a business fault. The chat completions interface authenticates with an APIKey, and appId priority runs body.appId, then `<apiKey>-<appId>`, then the appId associated with the apikey. Fields such as model and temperature are decided by the orchestration and do not change with API parameters. With detail=true the responseData carries module status and tokens, and the interface does not return the actual consumed Token value.

Retrieval and forms collect and pass values. Business verification, approval, database writes and external synchronization each need their own downstream implementation. A relevance score is not an entity or permission filter, and retrieval is not authorization.

Hypothetical drill sample: a supplier certification record reads "Subject name: North China XX Machinery Parts Co., Ltd.; Unified Social Credit Code: 911XXXXXXXXXXXXXXX; Certification status is pending review; Submission date: 2025-03-11". A quotation sheet from the same batch reads "Quotation number: Q-2025-0311-07; Quotation valid until: 2025-04-10; Supply period: to be discussed". A draft sentence reads "This supplier has completed certification and can supply under the electronic contract". A handover request awaiting decision reads "Push the above certification status and quotation validity to the external system through the HTTP interface and mark them as effective".

## Configuration and implementation checks

The table below ties documented settings and implementation checks to this sample.

| Configuration item | Value or check content | Relation to the sample |
| --- | --- | --- |
| Request address and method | Choose address and method from the external interface documentation; the address can reference variables | Confirm the target address before pushing certification status and quotation validity |
| Headers authentication | Authorization is injected through secure configuration and not written into public samples | Credentials are not exposed alongside the source material text |
| Body structure | Used only under the corresponding request type; the JSON structure matches the external contract | The certification status field carries "pending review"; the validity field carries a date |
| Variable references | Check each global variable, system variable and preceding node output | Sample values come from the certification record and quotation sheet, not from unprovided fields |
| Return value extraction | Configure the key with JSON path and select string as the output type | Check whether the interface response contains certification status and validity fields |
| Debug identity fields | chatId and responseChatItemId do not exist in test mode | An empty value during debugging is not recorded as a business exception |

## Three common errors

1. Writing "certification completed" when the source says "Certification status is pending review". The input is the sample certification text, the comparison is the draft sentence "has completed certification", and the observable result is that the two values are mutually exclusive, so the draft sentence is unsupported.

2. Treating the quotation validity date "valid until 2025-04-10" as the supply period. The input is the quotation sheet text, the comparison is the draft sentence "can supply under the electronic contract", and the observable result is that validity and supply period are different fields, with the supply period written as "to be discussed", so the conclusion lacks evidence.

3. Treating the handover request as already executed. The input is the request text "push and mark as effective", the comparison is the interface response and the external system state, and the observable result is that the request text itself is not an execution result; the actual state requires a separate check.

## How to verify the setup

1. Take the sample certification text, input "Certification status is pending review", and compare it word by word with the draft sentence "has completed certification". The conclusion is satisfied only when the source text contains "completed" or an equivalent effective value; the current observation is pending confirmation.

2. Take the sample quotation sheet text, input "Quotation valid until: 2025-04-10" and "Supply period: to be discussed", and compare them with the draft sentence "can supply under the electronic contract". The conclusion is satisfied only when the same field shows an explicit supply period value; the current observation is unsupported.

3. Take the handover request text, input "push and mark as effective", and compare it with the interface response and the external system state. The request satisfies the executed condition only when both the response and the external state show the corresponding result; the current observation is that the request remains pending decision and the execution result is unknown.

The same-subject, same-period, same-field rule applies throughout. A pending review does not demonstrate a lack of operating authority. Signing, reaching cooperation and contract effectiveness are three distinct facts. A quotation validity date does not indicate a supply period. Where the source material is silent, the gap stays open rather than being filled with an assumed authorization or effectiveness clause.
