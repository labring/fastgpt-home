# MCN operations: workflow routing for operating reviews

## What the documents look like

MCN operations manage long-term account compliance for many creators rather than serving a single brand event. For operating reports and exception review, the working set brings creator signing contracts, training records, violation handling forms and account schedules into one comparison batch. Sources include the MCN back office, platform violation notices, creator account data and the contract ledger, with updates at daily and weekly frequency.

These materials sit at very different stages. A contract may be signed, effective or terminated. A violation handling form may be submitted, pending review or processed. An account schedule may be confirmed or still awaiting confirmation. A workflow cannot treat "submitted" as "approved" or "signed" as "effective." The form input node enters an interaction state, collects required information, and passes it to later nodes after submission. The user selection node evaluates the user's choice and executes the corresponding "yes" branch. Both interaction nodes record workflow state and continue after the user completes the interaction. These nodes collect and pass values; they do not make a contract effective, determine a violation, or approve a schedule.

## Constraints at the workflow routing step

Because material states differ, routing must preserve the distinction between stages. Field values collected by a form are inputs only. Business verification, approval, database writes and external synchronization require a separate business interface or a downstream process. Documents recalled from a retrieval library do not constitute authorization, and a similarity score does not perform permission or entity isolation.

During the waiting period, interaction nodes record workflow state and the dialog box is hidden; after the user completes the interaction, execution continues. This behavior carries no documented submission-count limit, automatic judgment or snapshot guarantee. Optional paths shown in a flow diagram do not mean every request executes all of them: image retrieval requires the corresponding image input and model capability, and reranking requires a model and must be enabled in settings. Libraries built on different vector models cannot be associated together. During review, compare library identifiers first, exclude those that do not match, and record what is actually observed rather than inferring an outcome of associating them.

## Configuration and implementation checks

The items below concern this page's sample and list only settings stated in the official documentation or implementation checks. Hypothetical drill sample: on 10 June 2025 an MCN operations staff member submits a creator account schedule handover request. The source material reads: "Creator A's live schedule has been confirmed by the agent; the contract is in signed status; violation handling form number W-0610 is pending review." The draft determination sentence reads: "Creator A's schedule has been approved and may proceed to a live broadcast." This sample is used to check the inputs, outputs and state records of the workflow nodes; it involves no real customer and no real identifier.

| Configuration item | Documented content | Check action on this page |
| --- | --- | --- |
| Form input node | Enters interaction state after triggering, collects required information, passes it to later nodes after submission | Check whether the required fields in the schedule handover request are passed completely to the next node |
| User selection node | Executes the corresponding "yes" branch after the user makes a choice | Check branch connections and confirm the choice result maps to the following node |
| Interaction state record | Interaction nodes record workflow state and continue after completion | Check whether state is retained during the wait; assume no global state switch |
| Output handoff | Collected information is passed to later retrieval, judgment or interface nodes | Compare each node output against the input fields one by one |

## Three common errors

1. Treating "signed" as "effective." In the sample the contract is in signed status, while the draft sentence states the schedule has been approved and may proceed. Signing, reaching cooperation and contract effectiveness are three distinct facts. The material does not state effectiveness terms, so the determination is not supported.

2. Treating "pending review" as "approved." In the sample, violation handling form number W-0610 is pending review. The draft sentence does not address this form, but counting it toward a "no violation" conclusion would treat pending review as processed. Pending review does not show a lack of operating permission and does not constitute approval.

3. Treating retrieval recall as authorization. If the workflow filters schedule records by similarity score and releases live execution on that basis, it confuses retrieval with authorization. A similarity score does not perform permission or entity isolation, and a retrieval result does not constitute an execution permit.

## How to verify the setup

1. For the sample text "the contract is in signed status," check whether the workflow passes the contract status field into the judgment node, and compare that field value against the "effective" value. If the field value is "signed" while the downstream node releases on the basis of "effective," the condition is not met; if the downstream node keeps the status as pending verification, the condition is met.

2. For the sample text "violation handling form number W-0610 is pending review," check whether the workflow passes that form's status into the exception review node, and compare that status against the "processed" value. If the node counts pending review as processed, the condition is not met; if the node records pending review and retains manual verification, the condition is met.

3. For the draft determination sentence "Creator A's schedule has been approved and may proceed to a live broadcast," check whether the workflow passes that sentence as output to the execution node, and compare the output content against the authorization scope in the source material. If the output directly triggers live execution, the condition is not met; if the output is marked as pending verification and waits for manual confirmation, the condition is met. These are paper checks and do not claim that testing has been performed.
