# MCN operations: citation tracing for operating reviews

## What the documents look like

An MCN agency manages long-term account compliance for many creators at once, rather than serving a single brand campaign. Operating reports and exception reviews therefore have to connect four document families: creator signing contracts, training records, violation handling forms, and account schedules. Each conclusion in a report needs to point back to the specific material and version it came from.

Source data arrives from the MCN back office, platform violation notices, creator account data, and the contract ledger. Updates run on daily and weekly cycles. In this task, citation tracing decides whether an exception review conclusion can be tied to a concrete document, so that a platform notice or a verbal explanation is not treated as a contract term.

## Constraints at the citation tracing step

The knowledge base search node selects one or more knowledge bases that share the same vector model, and outputs a citation array whose length may be zero. When the array is empty, the output path still continues. Search results then pass to the answering step, where each answer sentence is checked against the cited source text. The minimum relevance value is a filter threshold that takes effect only under semantic retrieval or result reranking; it does not perform permission or entity isolation. A retrieval action is not an authorization, and a form collecting values does not mean that approval, a database write, or external synchronization has completed.

Hypothetical paper exercise sample: the source text reads "Creator A and Agency B signed the Livestream Content Compliance Training Confirmation on 1 March 2025; the confirmation states that Creator A completed the February 2025 training, the signature status is signed, and the contract number is B-2025-031." A separate "account schedule" records that Creator A took part in one livestream on 5 March 2025 from 20:00 to 22:00. The draft sentence under review is "Creator A has completed the February 2025 training and can be scheduled for the 5 March 2025 livestream." The items to check are whether the training confirmation covers February 2025, whether the signature status is signed, and whether the schedule sits under the same creator entity.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison method |
| --- | --- | --- |
| Linked knowledge bases | Select the contract ledger base and the training records base | Both bases must use the same vector model; check the vector model identifier first and exclude any that differ |
| Search mode | Hybrid retrieval | Contract numbers and dates need full-text recall; the semantic part supplements natural-language descriptions |
| Citation limit | 2000 tokens as a paper starting point | This value is only a paper starting point for the exercise; compare it against the sample source length before adjusting |
| Minimum relevance | 0.5 as a paper starting point | Compare against the rerank score; this value only filters low-relevance results and does not isolate creator entities |
| Result reranking | Enable ReRank | Rerank performs a second ordering of text when candidates are numerous; confirm the rerank model is configured |
| Citation output handoff | Pass the citation array to the answering step | Compare each answer sentence against the cited source text; when the array is empty, record the gap |

## Three common errors

1. Treating retrieval similarity as a permission filter. The incorrect practice is assuming that the minimum relevance value excludes other creators' contracts. Check method: input Creator A's contract number, compare whether the returned citations contain only the Creator A entity, and observe whether any other creator's fields appear.
2. Writing a pending-review status as already effective. The incorrect practice is treating a violation handling form marked "pending review" as fully handled. Check method: input the handling form text marked "pending review", compare whether the draft sentence claims it has been handled, and observe whether the draft keeps a to-be-verified wording.
3. Treating an empty citation array as a workflow failure. The incorrect practice is assuming the workflow has errored and stopped when the citation length is zero. Check method: use the paper input `[]` to check the downstream design, and observe whether the downstream can still accept it and record the gap.

## How to verify the setup

1. Use the training confirmation text from the hypothetical sample as input, compare the draft sentence "Creator A has completed the February 2025 training" against the training period and signature status in the source text, and observe whether the citation corresponds word for word to the same entity, the same period, and the same field.
2. Use the account schedule text as input, compare the livestream arrangement in the draft sentence against the date and time window in the schedule, and observe whether the citation comes from the same creator entity with a matching date.
3. Use the paper input `[]` as the retrieval output, compare it against the design of the downstream answering step, and observe whether the empty array is recorded as an evidence gap and whether wording such as "confirmed" or "approved" appears beyond the source text.
