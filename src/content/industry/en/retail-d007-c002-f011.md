# MCN operations: database operations for operating reviews

## What the documents look like

MCN management covers long-term account compliance for many creators, which differs from a single brand live-selling session. The working materials are creator signing contracts, training records, violation handling forms, and account schedules, drawn from the MCN back office, platform violation notices, creator account data, and the contract ledger. Operating reporting and anomaly review must align dates, parties, states, and authorization boundaries across these materials before deciding whether a record belongs in the review scope. Update frequency affects the reporting window, and this page does not derive batch synchronization or real-time triggers from it.

A hypothetical paper exercise sample: the source material reads "Creator A's signing contract number HT-2026-031 has contract status Signed, valid until 31 December 2026; violation handling form V-2026-018 records that Creator A received one platform warning during the live stream on 12 March 2026, with handling status Pending re-review." The draft sentence to be judged is: "Creator A's violation on 12 March 2026 has been fully handled and may be counted in this month's compliance report." The draft writes a pending re-review state as fully handled, which conflicts with the source text.

## Constraints at the database operations step

Database operations must separate business source-data storage from the vector retrieval backend and check connection settings against the actual deployment. Connection pool, cache, and vector store parameters do not map to a business category by name; configured values follow what the deployer actually entered. Retrieval stores require the same vector model to be associated together, and that condition applies only to vector retrieval. It does not extend to external business-registration systems or platform notices. A relevance score carries no permission or entity-isolation function, and retrieval results do not authorize any judgment about creator identity, contract validity, or violation handling state. Forms collect field values; business verification, approval, database writes, and external synchronization each need their own downstream implementation.

For this page's task, the operator must keep clear which materials, operations, and requests sit at which authorization state during handover. Retrieval is not authorization, and a form submission is not an execution of the business action it describes.

## Three common errors

1. Writing the violation handling form's Pending re-review state as fully handled. Input: the sample source text for V-2026-018. Comparison: the draft sentence's phrase "fully handled" against the source state Pending re-review. The two do not match.
2. Treating a relevance score as a permission filter. Input: a similarity value returned by one vector retrieval. Comparison: the value against Creator A's contract authorization scope. A high or low score does not change whether the record falls inside the readable range.
3. Extending the same-vector-model requirement for retrieval stores to platform violation notices or business-registration data. Input: two library identifiers using different vector models. Comparison: the identifiers against the joint-association condition. Different identifiers exclude joint association; no further inference about missed recalls or redundant results follows.

## How to verify the setup

1. Input: the sample source text "contract status Signed, valid until 31 December 2026" together with the draft sentence "may be counted in this month's compliance report." Compare the contract validity period against the report's month. The sentence is satisfied only when the report month falls inside the validity period and the violation state has been confirmed by re-review. The current violation state is Pending re-review, so the expected result is not satisfied.
2. Input: one vector retrieval request for Creator A. Compare the library identifier of each returned record against the library identifier of Creator A's contract. Joint association is permitted only when the identifiers match. When they do not match, exclude the record and record the actual observation. Do not run a cross-model retrieval to compare missed recalls.
3. Input: an empty-result query that returns an empty array []. Compare against whether the downstream report design has an explicit handling path for empty results. The expectation is that downstream treats it as empty input. Do not claim that a fabricated rule retrieval always returns an empty array.

After any change to database or service configuration, re-check the same business sample rather than relying only on process liveness. Backup generation and actual restoration are verified separately, with a checkable sample and record retained. Use the deployment's own load observations for connection, error, and latency behavior; untested concurrency thresholds are not transferable.
