# Shopify fulfillment: workflow routing for operating reviews

## What the documents look like

A Shopify standalone store configures its own payment, shipping and fulfillment services. The platform does not apply one unified automatic return process across all stores, unlike a marketplace-operated store such as a TikTok Shop US shop. This difference shapes the document set that operating reviews depend on. Order details sit in Shopify Admin, payment status sits in the payment gateway, shipping labels sit in the carrier system, and inventory location data sits in inventory records. Each order and each day can change these records, so any comparison must lock the same order number, the same date range and the same field before cross-system status descriptions become comparable.

Workflow routing for operating reports and exception review handles the state and hand-off relationships among these documents. It does not replace the business judgment made by the payment gateway, the carrier or the inventory system. The form input node and the user selection node are user interaction nodes. When triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. That behavior belongs to the node itself and does not authorize an order, a refund or a shipment.

## Constraints at the workflow routing step

Information collected by an interaction node must be passed explicitly to later retrieval, judgment or interface nodes, and the output must be compared item by item against the input. Order writes, document backfill and external status synchronization require a separate business interface or a later process. Workflow routing does not perform those actions. Retrieval locates relevant documents. A retrieval result does not establish permission and does not approve a specific order, refund or shipment request.

Configuring shipping rates, purchasing shipping labels and synchronizing fulfillment status are business operations. Their execution authority comes from the merchant's own system configuration and staff authorization, not from a single selection or a single form submission inside an interaction node. The user selection node executes the corresponding "yes" branch after the user makes a choice, and verifying branch connections one by one is part of routing review.

### Hypothetical paper exercise sample

The following is paper exercise material for this page. It does not refer to any real customer or real order.

Source text one (order detail excerpt): "Order number H-2041, order date March 4, 2025, item A quantity 2, payment status paid, fulfillment status awaiting shipment."

Source text two (refund record excerpt): "Order number H-2041, refund request date March 6, 2025, refund amount 0, request status pending review."

Draft sentence to be judged: "Order H-2041 has completed a refund."

Hand-off request to be judged: "Update the fulfillment status of order H-2041 to shipped and synchronize it to the carrier system."

In these materials, the refund record states a request status of pending review and does not state a review conclusion, a refund completion time or a refund arrival record. The order detail states a fulfillment status of awaiting shipment and does not state a shipment time or waybill number. The draft sentence and the source text disagree on the fact of refund completion. The hand-off request lacks evidence of shipment and lacks a statement of synchronization authority.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison method |
| --- | --- | --- |
| Interaction node type | Form input node | Order number and review scope must be collected; compared with the user selection node, which is used for branch decisions |
| Required form fields | Order number, review date range | Order number supports same-subject comparison, date range supports same-period comparison; compared item by item against the source text |
| Retrieval input | Order number H-2041 | Used to locate the order detail and refund record; observe whether returned documents contain that order number |
| Output receiving node | Judgment node | Passes the order number collected by the form to the judgment node; compare the passed value against the form value item by item |
| Manual review action | Compare refund request status with refund completion record | The source text states pending review only; when completion evidence is absent, record as pending verification |
| External synchronization | Separate business interface | Order writes and carrier synchronization are not completed inside routing; the interface and its authorization must be stated separately |

## Three common errors

1. Treating pending review as completed. Source text two states the refund request status is pending review and does not state approval or refund arrival. If the draft sentence reads "Order H-2041 has completed a refund," the input is the refund record text, the comparison is between "pending review" and "completed," and the observable result is that the two do not match, so the judgment does not hold.

2. Treating a selection in an interaction node as business authorization. The user selection node executes the "yes" branch, which is a workflow branch direction. If the hand-off request is treated as having obtained shipment and synchronization authority on that basis, the input is the branch direction, the comparison is between the branch direction and the source of authority, and the observable result is that the branch direction contains no authorizing subject and no authorization scope, so the request still lacks an authorization basis.

3. Treating a retrieval hit as permission or entity isolation. A retrieval returning a document containing the order number shows only that the document is relevant to the query. If the refund or shipment of that order is treated as confirmed on that basis, the input is the retrieval result, the comparison is between the retrieval result and the business status field, and the observable result is that the retrieval result contains no review conclusion, so the confirmation does not hold.

## How to verify the setup

1. Form input check. Enter source text one and source text two, and check whether the required form fields collect order number H-2041 and the review date range. Compare the form output value against the order number in the source text, observe whether the two match, and check whether that value is passed to the later judgment node.

2. Branch and output hand-off check. Enter the hand-off request to be judged, check the connection target of the "yes" branch of the user selection node, and compare the branch direction against the action type in the request. Observe whether the branch direction only indicates that the process continues and contains no shipment execution or carrier synchronization.

3. Empty result and missing evidence check. Use a paper input of an empty list to check the downstream design, observe how the downstream node receives the absence of retrieval results, and record the actual observation without presuming returned content. For the fact of refund completion, compare the status field in source text two against the draft sentence, and observe whether a review conclusion or an arrival record appears; when neither appears, record as pending verification and keep the evidence gap open.

This page addresses only Shopify standalone store order fulfillment, operating reports and exception review, and workflow routing. It concerns which materials, operations and requests at a hand-off stage are in what authorization state, and it does not treat retrieval or a form as authorized execution.
