# Shopify fulfillment: tool calls for operating reviews

## What the documents look like

On a Shopify standalone store, the merchant configures payment, shipping and fulfillment services. The platform does not run a single automatic return process across all sellers. Operating reports and exception reviews therefore work with material that sits in several places: Shopify Admin, payment gateways, carrier systems and inventory location data. The documents involved are order details, shipping rate templates, shipping labels and refund records. Updates arrive per order and per day, so a review has to align fields for the same order across sources rather than assume one consolidated record.

Tool calls and plugins matter here because the model decides from context whether to read these materials and which system module or plugin to invoke. A tool description tells the model what the tool is for. Tool parameters determine what is passed at call time. When a required parameter has no suitable value in context, the model may not call the tool at all. A report review cannot assume that every question triggers data retrieval.

## Constraints at the tool calls step

Retrieval and tool output do not constitute authorization. By default, the tool call node returns the tool result to the AI for summarization. The tool call termination node ends the current call: it does not invoke other tools and does not ask the AI to answer from the tool results. Custom tool variables extend variable input, so a node that is not treated as a tool parameter can still be called, along with the workflow that follows it.

Knowledge base search, HTTP modules and plugins are all tools. Similarity or relevance affects recall ordering only. It does not perform permission or entity isolation. Libraries built on different vector models cannot be associated together; the identifier must be checked first and non-matching items excluded, with actual observations recorded. Optional paths shown in the overall flow diagram do not all execute on every request. Image retrieval requires a corresponding image input and model capability. Reranking requires a model and must be enabled in settings.

Hypothetical paper exercise, not a real record. Source text one, order details: "Order number SY-1001, order date 2025-03-02, fulfillment status: shipped, shipping label purchased." Source text two, refund record: "Order number SY-1001, refund request date 2025-03-10, status is pending review." Proposed determination sentence: "Order SY-1001 has completed its refund." This sentence shares the same subject and the same field as source text two, and the values are mutually exclusive, so the sentence is unsupported. A separate handover request reads: "Call the plugin to synchronize the refund status of SY-1001 to the carrier system." That request concerns a business action. The materials do not state authorization or a downstream implementation, so it remains pending verification.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Comparison method and notes |
| --- | --- | --- |
| Tool description | State the purpose and the situations where the tool should not be called | Check against this page's materials whether the description covers order details and refund records |
| Tool parameters | System module parameters are fixed; plugin parameters are configurable | Review each parameter description and required flag; treat no description as a guarantee of execution |
| Required parameter | Order number treated as required | When absent the model may not call; after interactive completion, check the actual request |
| Tool connection | Connect a small number of tools first for debugging | In advanced orchestration, connect available tools to the tool call module and add gradually |
| Tool call termination | Place after the data retrieval tool | After termination, no other tool is called and the AI does not summarize the tool results |
| Custom tool variables | Fill in parameter descriptions for report nodes | This makes the node callable; check the workflow that follows it |

The starting values above are set only for this paper exercise and are not official defaults.

## Three common errors

1. Treating a retrieval hit as authorization. Input: "check the refund for SY-1001." Compare the retrieval result with the status field in the refund record. Observing a returned value of pending review while the draft states completed refund indicates an error.
2. Treating pending review as executed. Input: the proposed determination sentence. Compare it with the status value in the refund record. Observing that pending review and completed are mutually exclusive means the sentence is unsupported.
3. Treating a tool description as a guarantee of execution. Input: the tool description text. Compare it with the actual request parameters. Observing that a required parameter is missing and was not completed means the plugin cannot be treated as having run.

## How to verify the setup

1. For source text two and the proposed determination sentence: input the refund record status field, compare pending review with completed, and observe that the values are mutually exclusive, so the sentence is unsupported.
2. For the handover request: input the request, compare whether the materials state authorization and a downstream implementation, and observe that neither is stated, so the conclusion is pending verification and the action is not treated as executed.
3. For the empty result branch: input the paper input [], compare how the downstream design handles an empty reference, and observe that the downstream does not assume a result is always present. Record the gap without claiming that a fictional rule search necessarily returns [].
