# Temu semi-managed sellers: tool calls for operating reviews

## What the documents look like

Temu semi-managed sellers maintain overseas inventory and dispatch, which distinguishes this work from supplying goods under full platform management. Operating reports and exception reviews draw on four document types: product declaration forms, overseas inventory tables, price declarations, and platform fulfillment orders. These materials come from Temu Seller Center, overseas warehouse WMS, logistics tracking, and procurement cost sheets. The public brief gives an update frequency of daily or per order; that frequency does not change how the tool call node behaves, so it is noted here only as stated.

The role of tool calls and plug-ins at this step is to let the model decide, from context semantics, which module or plug-in to invoke in order to read a document, run a comparison, or trigger a downstream flow. A tool call needs a tool description and tool parameters. The description tells the model what the tool does. For plug-in parameters, two key values are the parameter description and whether the parameter is required. Where no required parameter exists, the model may fabricate one. Where a required parameter exists and no suitable value is present in context, the model may decline to call the tool. In advanced orchestration, connecting a tool to the tool call module separates tool input from ordinary input, and the description can be edited to sharpen call timing. The tool call termination node ends the current call, invokes no further tools, and stops the AI from summarizing tool results. Custom tool variables extend inputs for nodes not treated as tool parameters.

## Constraints at the tool calls step

A tool description that stays generic gives the model no boundary between callable and non-callable situations. Parameter descriptions describe inputs; they do not guarantee execution. A required parameter that is absent from context can lead the model to invent a value or to skip the tool. Connecting many tools at once makes call timing harder to tune, and the documentation advises starting with a small set and refining before adding more. Downstream business verification, approval, database writes, and external synchronization are not performed by retrieval or by a form; they need their own stated downstream implementation.

Hypothetical paper exercise sample. The source material reads: "Product declaration form number XS-2024-0715; declaring entity a semi-managed store; declared product a folding outdoor table; declaration date 15 July 2024; status pending review. The overseas inventory table shows 120 units available for this product in the overseas warehouse, updated 15 July 2024. The price declaration records a declared price of USD 19.99 for this product, effective 16 July 2024." The draft sentence to be judged reads: "This product has completed price declaration and holds overseas inventory, so it can be listed for sale immediately." The draft merges a pending-review status with a sellable status and does not check the dispatch time requirement in the platform fulfillment order.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Reason and comparison method |
| --- | --- | --- |
| Tool description text | State "read the status field of the product declaration form" | Compare against the status value in the source material to confirm the description covers the pending-review case |
| Parameter required flag | Set the declaration form number as a required parameter | Compare against sample number XS-2024-0715 to confirm the model does not call when the number is absent |
| Number of connected tools | Connect one tool first | Compare against the documented advice to tune a small set before adding more |
| Termination node position | Place it after the inventory query tool | Compare against the documented behavior that termination stops the AI summary |
| Custom tool variable | Add a variable description for the price declaration effective date | Compare against the sample effective date 16 July 2024 to confirm the variable is passed in |

## Three common errors

1. Writing a tool description as a general statement without input conditions or situations where the tool should not be called. Check: supply the pending-review status from the sample and observe whether the model still calls a listing tool.
2. Treating a parameter description as a guarantee of execution. In the sample the declaration form number is a required parameter; if the description does not stress that requirement, the model may fabricate a number. Check: remove the number and observe whether the model stops the call.
3. Expecting an AI summary after the tool call termination node. In the sample the inventory query is followed by the termination node. Check: observe whether any summary text is still returned.

## How to verify the setup

1. Input the product declaration form text from the hypothetical sample and compare the draft sentence "can be listed for sale immediately" against the source status "pending review." The expected observation is that the model does not output a listing conclusion, or outputs a prompt to verify further.
2. Input the overseas inventory table text and compare the available quantity of 120 units against "holds overseas inventory" in the draft sentence. The expected observation is that when the model cites the quantity it also marks the update time of 15 July 2024.
3. Input the price declaration text and compare the effective date of 16 July 2024 against "has completed price declaration" in the draft sentence. The expected observation is that the model distinguishes a declaration record from an effective status and does not treat the effective date as completed authorization.

These checks are paper comparisons. No test, deployment, approval, refund, or other business action is claimed to have occurred. Where a field is not provided in the source material, it remains unknown.
