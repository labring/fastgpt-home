# TikTok Shop US operations: workflow routing for operating reviews

## What the documents look like

TikTok Shop US operating data sits in Seller Center, the order center, carrier tracking, and advertising reports, with daily and per-order update cycles running side by side. Compared with Douyin Shop shelf operations, the US marketplace is shaped more strongly by local return windows, return grading, and overseas logistics constraints. Return and refund records, return grading evidence, settlement statements, and product listings form the main materials for exception review. These materials carry independent fields, statuses, and validity scopes, so workflow routing has to follow the status actually written on each document. A retrieval result or a value collected in a form does not become an authorization conclusion.

A return and refund record may state an order number, a submission date, a current status, and a return window deadline. A settlement statement may state a billing period and a deduction line. A product listing may state a listing identifier and a listing state. Each of these is a separate document with its own evidence boundary. When the workflow reaches an exception review, the routing decision depends on which document is being read and what that document actually records.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution waits until the user fills in the required information and submits. The collected information is then passed to subsequent nodes. The user selection node is also a user interaction node. It triggers the same interaction state, and once the user makes a choice, the node evaluates that choice and executes the corresponding yes branch. Both nodes can be added repeatedly and can trigger execution.

The documents describe the interaction state, the hidden dialog box, and the state record as existing node behavior. They do not describe a global state-recording switch, a submission count limit, or an automatic judgment mechanism. Collected values need an explicit connection to later retrieval, judgment, or interface nodes. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval and form-collected values do not constitute authorized execution, and a similarity score does not carry permission or entity filtering duties.

Hypothetical paper exercise sample: a return and refund record reads "Order number A-1001, buyer submitted a return request on 2025-03-10, status is pending review, return window closes 2025-03-20." A drafted sentence reads "This order has completed its refund, refund amount 39.99 USD." A pending request reads "Please mark this order as refunded and synchronize it to the settlement statement." The source text records only a pending review status. It does not record refund completion, a refund amount, or authorization to synchronize with the settlement statement.

## Three common errors

1. Treating a pending review status as a completed refund. The sample source text says "status is pending review," while the drafted sentence says "has completed its refund." These are mutually exclusive values for the same subject and the same field, so the drafted sentence is unsupported.
2. Treating a form-collected value as authorized execution. The sample request asks to mark the order refunded and synchronize the settlement statement. The source text does not record that authorization, and the form only collects values.
3. Treating a similarity score as an entity or permission filter. A retrieval result returning a related document does not mean the order has refund authorization. The identifier and the authorization boundary need separate verification.

Corresponding checks:

1. Input the sample source text and the drafted sentence, compare the status field values. If the source says pending review and the draft says completed refund, judge the draft unsupported.
2. Input the sample request and the source authorization scope, compare whether the requested action falls inside the recorded scope. If the source does not record marking and synchronization authorization, judge the request pending verification.
3. Input the retrieval result and the order identifier, compare whether the returned document subject matches the target order. If it does not match, exclude it. Do not run a cross-model retrieval comparison for missed recall.
