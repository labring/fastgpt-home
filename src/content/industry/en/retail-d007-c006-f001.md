# General export declarations: HTTP integrations for operating reviews

## What the documents look like

General trade export declaration work produces, for each declaration, an export declaration form, a commercial invoice, a packing list, and a contract. Data sources named in the brief are China International Trade Single Window, the customs code library, freight forwarder bills of lading, and the enterprise ERP. Compared with general trade import declaration, export declaration also affects the matching of export tax rebate vouchers, so operating reports and exception reviews must cover two verification lines at the same time: declaration errors and rebate voucher matching. Data updates per declaration, and report definitions need to correspond document by document to a single shipment. Exception review must be traceable to a specific declaration number, a specific field, and a specific document version. Commodity code classification, declaration form completion, and freight and insurance verification are the three most time-consuming steps, so report field design should first make these three areas verifiable.

For the HTTP integrations step, these characteristics mean that a request sent to an external system carries values drawn from the same per-declaration documents. The HTTP module sends a request to a given address. Params are path request parameters, used mostly in GET requests. Body is the request body, used mostly in POST and PUT requests. Headers carry special information. All three can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and preceding node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. The chatId and responseChatItemId system variables do not exist in test mode. Returned values are extracted through JSON path, and when the output type is set to string, the value at the corresponding key is converted to a JSON string. The chat interface uses APIKey authentication, recommends passing body.appId in the request body, and also supports `Authorization: Bearer <apiKey>-<appId>`. Passed model and temperature fields have no effect, because the orchestration decides them. With detail=true, intermediate values are returned; in stream mode they are distinguished by event, and in non-stream mode the result is stored in responseData. The interactive value returned by an interaction node contains only type and params, and internal runtime fields are not returned. Retrieval or form collection does not constitute authorization; business verification, approval, database writes, and external synchronization each need their own downstream implementation.

## Constraints at the HTTP integrations step

A hypothetical drill sample, clearly labelled as hypothetical, is used below. On 10 March 2026, a document clerk at a foreign trade company handles one export declaration, declaration number HYP-2026-0310-001, commercial invoice amount USD 48,000, packing list quantity 320 pieces, contract number CT-2026-008. The proposed draft sentence is "This export declaration has completed declaration and obtained the tax rebate voucher." The request awaiting determination is "Write this declaration's status into the external system through the HTTP module." The source material shows only that this declaration was entered into the enterprise ERP and a draft declaration form was generated. It does not show a declaration submission, a customs receipt, or a record of obtaining a tax rebate voucher.

The HTTP module can reference variables in Params, Body, Headers, and the URL. For this sample, a request that writes status would need the declaration number, the invoice amount, the packing list quantity, and the contract number to be passed as variables from preceding node outputs or global variables. The system variables available for identification are appId, chatId, responseChatItemId, variables, cTime, and histories. Because chatId and responseChatItemId do not exist in test mode, an empty value for either during a drill is a documented test-mode condition and is not by itself a business fault. The histories system variable takes at most 10 records by default and its length cannot be modified. The chat interface does not return actual consumed token values; if those are needed, detail=true can be set and the tokens value in responseData calculated manually. An interaction node returns only type and params to the external caller; entryNodeIds, memoryEdges, nodeOutputs, and nodeResponseId are internal runtime fields and are not returned.

## Three common errors

1. Treating a draft entry as a completed declaration. Input: the sample source material text. Comparison: "entered into the ERP and a draft declaration form generated" against "completed declaration and obtained the tax rebate voucher." Observable result: the material shows no declaration submission, no customs receipt, and no tax rebate voucher record, so the proposed draft sentence is not supported.

2. Treating retrieval or a form as authorized execution. Input: the request awaiting determination, "Write this declaration's status into the external system through the HTTP module." Comparison: form collection against business verification, approval, database writes, and external synchronization as downstream implementations. Observable result: when no authorization credential or approval record is provided, the write request remains pending verification.

3. Treating a test-mode empty value as a business fault. Input: chatId and responseChatItemId do not exist in test mode. Comparison: the documented test-mode condition. Observable result: the empty value is a documented condition and does not constitute a business exception.

## How to verify the setup

1. For the proposed draft sentence "This export declaration has completed declaration and obtained the tax rebate voucher," input the sample source material text, compare whether the three record types (declaration submission, customs receipt, tax rebate voucher) exist, and observe that when none of the three records appears, the sentence is not supported.

2. For the request awaiting determination "Write this declaration's status into the external system through the HTTP module," input the request content and the authorization boundary description, compare whether an approval record or authorization credential exists, and observe that when neither is provided, the request remains pending verification.

3. For empty-result handling, input an explicit paper input `[]`, compare how the downstream design handles an empty array, and observe that the condition is met when the downstream handles it through an empty-result branch. This does not claim that a fictional rule retrieval necessarily returns `[]`.
