# General export declarations: conversation logs for operating reviews

## What the documents look like

General trade export declaration work moves order by order. The document set centers on the export declaration form, the commercial invoice, the packing list and the contract, with data drawn from China International Trade Single Window, the customs code library, carrier bills of lading and the company ERP. The export stage also affects export tax rebate voucher matching, so a declaration error can trigger document return inspection, declaration discrepancy and blocked rebate processing. Operating reporting and exception review must align these documents and the conversation logs to the same transaction, checking the party, the object and the status before judging where a handover request sits in the authorization chain.

For the conversation logs and audit step, the chat interface separates sessions by chatId and separates individual exchanges within a session by dataId. When a non-empty chatId is passed, the system reads the session from the database and uses the last item in the messages array as the user question, ignoring the other messages. When chatId is not passed, the context feature is not used and context is built entirely from the submitted messages. If responseChatItemId is passed, it becomes the response message ID stored in the database and must be unique within the current chatId. Intermediate values require detail=true; in non-stream mode the result sits in responseData, and in stream mode it is distinguished by event. Actual consumed Token values are not returned; with detail=true the tokens inside responseData can be calculated manually. The session list can be limited with source=api to sessions created through the API, and clearing an application's sessions clears only sessions created by API Key, leaving sessions from online use, share links and other sources untouched. A stored log shows that a record exists; reconciliation, retention and compliance requirements are carried out by a complete business solution, and retrieval or similarity does not carry authorization or entity isolation.

## Constraints at the conversation logs step

The chat interface returns no actual consumed Token value, so any operating report that needs consumption figures must set detail=true and compute the tokens inside responseData rather than reading a returned total. The model, temperature and similar parameter fields passed in the request have no effect because they are determined by the orchestration. A non-empty chatId makes the system read the session from the database, so a report that merges sessions must keep chatId distinct; the caller must ensure chatId uniqueness and a length under 250. The responseChatItemId must be unique under the current chatId. The source=api filter returns only API-created sessions, and clearing sessions through the API Key path does not touch sessions from other sources. Retrieval relevance scores and similarity values describe retrieval association and do not act as category, entity or permission filters, so they cannot be used to exclude unrelated businesses or unauthorized records. Retrieval is not authorization, and a form collects values rather than performing business verification, approval, database writes or external synchronization.

Hypothetical paper exercise sample: a document clerk at an export company submits a handover request in the session with chatId ex-2024-0007: "Please hand over the declaration elements of this export declaration form to the review post." The material text supplied for checking reads: "Contract number HT-2024-0007, exporter is Company A, declaration form draft status is pending review, packing list quantity matches the invoice." The sentence to be judged is: "This handover request has obtained review authorization." Comparison checks the party, the object and the status: the material states only that the draft is pending review and does not state that the review post has confirmed or authorized it, so the request remains pending verification and cannot be judged as authorized.

## Configuration and implementation checks

| Configuration item | Use on this page | Basis or checking method |
| --- | --- | --- |
| appId | Locate the target application | Passed as body.appId in the request body, or carried with the key |
| chatId | Distinguish the target session | Non-empty reads the database session; the caller ensures uniqueness and a length under 250 |
| dataId | Locate a specific exchange in the session | Taken from the dataId returned by the exchange list |
| detail | Retrieve intermediate run details | Set to true, then inspect responseData |
| source | Limit the session source | source=api returns only API-created sessions |
| loadCustomFeedbacks | Read custom feedback | Optional when retrieving the exchange list |

These values are the starting point for this hypothetical exercise, used to check whether fields are returned as expected. They are not official default values.

## Three common errors

1. Treating a pending-review status as authorization. The material states that the declaration form draft status is pending review and does not state review-post confirmation, while the judged sentence claims authorization; the party and status do not match.
2. Merging sessions with different chatId values into one total. When the same transaction produces exchanges under more than one chatId, adding them directly mixes sessions from different entry points.
3. Treating log retention as completed compliance audit. The existence of a log record does not support the conclusion that reconciliation, retention and compliance requirements have been carried out.

## How to verify the setup

1. Enter the chatId ex-2024-0007 from the hypothetical sample together with the judged sentence, and compare the party, object and status in the material text. The authorized condition is met only when the material explicitly states review-post confirmation or authorization; the current material does not state this, so the result is recorded as pending verification.
2. Enter the exchange lists for two different chatId values and compare the list and total returned for each. The session isolation check is met only when each is counted separately without merging.
3. Enter a request with detail=true and compare whether the returned responseData contains module status and complete results. The run-detail check is met only when the fields appear as documented; business data that is not returned remains unknown.
