# General import declarations: conversation logs for operating reviews

## What the documents look like

General trade import declaration work centres on customs value, freight and insurance, and tax payment. Each declaration produces a customs declaration form, a commercial invoice, a packing list, a bill of lading, and a contract. These materials update on a per-declaration basis and draw on the International Trade Single Window, customs tariff schedules, freight forwarder arrival notices, and foreign exchange payment documents. For operating reports and exception review, the conversation log and audit step has to connect a chat's chatId and dataId to a specific declaration number and invoice number, so that a given question and answer can be attributed to one shipment. When the transaction terms, freight and insurance amounts, or tax basis are not retained in the conversation, the review cannot reconstruct them from the log alone and must mark them as unsupported.

The chat interface identifies a session and a single exchange through appId, chatId, and dataId. When chatId is passed, the system retrieves the session from the database and uses the last item of the messages array as the user question, ignoring the remaining messages. When chatId is not passed, context is built entirely from the supplied messages. Setting detail to true returns intermediate values; in non-stream mode the result is stored in responseData, and in stream mode it is distinguished by event. Fields for different modules inside responseData can vary by version, so business data that is not returned cannot be assumed to be fully retained. The presence of a log does not amount to a completed compliance audit; reconciliation, retention, and compliance requirements are handled separately by the full business solution.

## Constraints at the conversation logs step

A hypothetical drill sample: an importer's customs manager opens a conversation about one declaration. The material text reads: "Declaration number A-2024-0311, transaction terms CIF, freight RMB 1200, insurance RMB 300, commercial invoice number INV-7788, bill of lading number BILL-9901, contract number CT-2024-05; the above freight and insurance are borne by the seller and have been included in the customs value." The proposed handover request is: "Please confirm whether the freight and insurance for this declaration have been included in the customs value, and generate an exception review note." This request is pending determination. Whether the freight and insurance fields are retained in the conversation log still needs to be checked, and it cannot be treated as already verified or as authorized for execution.

Two further constraints follow. A relevance score from retrieval is not a category, entity, or permission filter; it cannot be used to decide that a record belongs to this declaration or that access is authorized. Retrieval is not authorization. A form collects values; business verification, approval, database writes, and external synchronization require their own stated downstream implementation. A pending review status does not show that operation permission is absent.

## Configuration and implementation checks

| Configuration item | Relevant value or check point on this page | Note and source |
| --- | --- | --- |
| appId | Passed in the request body as body.appId | Official chat interface description; this takes priority over other sources |
| chatId | Non-empty string, length under 250 | Used to retrieve the session from the database; uniqueness must be ensured |
| detail | true returns intermediate values | Non-stream results are stored in responseData; stream mode distinguishes by event |
| responseChatItemId | Unique under the current chatId | When passed, stored in the database as the response message ID |
| source | Set to api when retrieving the session list | Retrieves only sessions created through the API |
| loadCustomFeedbacks | Optional when reading the conversation list | Determines whether custom feedback is read |

For this hypothetical trial, the starting value for pageSize is 20. The reason is that this value can cover the multiple rounds of question and answer associated with one declaration. The comparison object is whether the total field in the response matches the number of records actually returned.

## Three common errors

1. Mixing calls that do not pass chatId with calls that do. The former builds context entirely from messages; the latter uses the last message as the question and retrieves the database session. The two correspond to different evidence scopes during review.
2. Judging business attribution from a retrieval similarity score. The score and similarity reflect retrieval relevance, not an entity or permission filter, and cannot be used to conclude that a record belongs to this declaration or that access is authorized.
3. Treating values collected by a form as a completed business check. inputForm only collects input; business verification, approval, database writes, and external synchronization need separate implementation, and a pending review status does not show that operation permission is absent.

## How to verify the setup

1. Enter the chatId and messages from the hypothetical sample, and compare the choices content in the response with the proposed handover request. If the response does not contain the freight and insurance fields, record that those fields are unsupported in the log, and do not judge them as included or not included.
2. Enter detail=true and stream=false, and compare the module fields in responseData with the fields listed in the official documentation. If a module does not return a business field, record the gap and do not assume full retention.
3. Call the session list with source=api, and compare the returned total with the actual number of records. If total exceeds the number returned, part of the pagination has not been retrieved; adjust offset and observe again, without assuming a single call retrieves everything.
