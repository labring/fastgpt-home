# General import declarations: workflow routing for operating reviews

## What the documents look like

General trade import declaration documents centre on customs dutiable value, freight and insurance, and tax payment. This differs from export declaration, where those elements carry less weight. Each declaration produces an import declaration form, a commercial invoice, a packing list, a bill of lading, and a contract. These materials support operating reports and exception reviews. They originate from the International Trade Single Window, customs tariff schedules, freight forwarder arrival notices, and foreign exchange payment slips. Data updates per declaration.

Two constraints follow for workflow routing. First, fields across documents correspond to one another: invoice amount, freight and insurance, and dutiable value jointly affect tax calculation, and exception review compares the same declaration number, the same period, and the same field. Second, document states vary. An arrival notice is a notice issued by a freight forwarder. A foreign exchange payment slip reflects a payment fact. Contract signing, cooperation reaching agreement, and contract taking effect are three distinct facts, and none substitutes for another.

## Constraints at the workflow routing step

Workflow routing in this task handles material collection, state recording, and result passing. After the form input node triggers, the conversation enters an interaction state, collects required information, and passes that information to later nodes once submitted. After the user makes a selection, the user selection node executes the corresponding "yes" branch. Both nodes record workflow state and wait for the user to complete interaction before execution continues.

Retrieval and forms do not constitute authorization. Semantic recall and relevance scores in a knowledge base do not carry permission or entity isolation, and a similarity setting cannot be read as excluding unrelated businesses or unauthorized records. Order writes, document backfill, and external status synchronization require a separate business interface or a later process; the nodes themselves do not perform these actions.

Hypothetical paper exercise: an importer holds one general trade import consignment. The source text reads: "Bill of lading HBL-2024-0317, consignee Hua Sample Import Co., Ltd., goods are industrial bearings, arrival date 17 March 2024." "Commercial invoice INV-0317 lists 500 bearings at USD 12 each, freight and insurance USD 400." "Foreign exchange payment slip shows USD 6,400 paid on 20 March 2024." The draft sentence to be assessed is: "This consignment has completed customs declaration and paid taxes." The draft sentence supplies no release record from the declaration form and no tax payment voucher, so it remains unsupported.

## Configuration and implementation checks

| Configuration item | Assumed trial starting point | Comparison method and reason |
| --- | --- | --- |
| Form input required fields | Declaration number, invoice number, bill of lading number | Compare item by item against the sample materials; record a gap when one is missing |
| User selection branch | "Yes" branch corresponds to complete materials | Verify branch connections one by one; do not assume automatic judgement |
| Interaction state recording | State recorded after the node triggers | Check against the documented explanation; no separate global switch is set |
| Information passing target | Later retrieval or judgement node | Compare whether output and input fields match |
| Retrieval scope | Library containing import declaration forms and invoices | Check the vector model identifier first and exclude non-matching ones |
| External action division | Order writes connect to a separate business interface | Forms and retrieval do not perform writes or synchronization |

## Three common errors

1. Treating "has completed customs declaration and paid taxes" in the draft sentence as an established fact. The sample provides only the bill of lading, invoice, and payment slip, with no release record and no tax payment voucher. The sentence remains unsupported and should be recorded as pending verification.
2. Treating retrieval results as a basis for authorization. A retrieved material shows only that content is related; it does not show that the record is authorized or usable for external handover. Permission requires separate checking.
3. Reading the "yes" branch of the user selection node as automatically completing approval. The node executes a branch; approval and writes require a separate business interface. A pending-review state does not demonstrate that an operating permission is absent.

## How to verify the setup

1. Input the three source sentences and the draft sentence from the sample, and compare whether the draft sentence has a release record and a tax payment voucher. The sentence meets the condition only when explicit vouchers appear and the subject, period, and field match; otherwise record it as unsupported.
2. Input the bill of lading number and invoice number from the sample, and compare whether the form required fields are complete. The condition is met when the fields are complete and passed to later nodes; when a field is missing, record the gap and keep it as pending verification.
3. Input the material list from the sample, and compare whether the retrieval scope contains the corresponding library and check the vector model identifier. When the identifier matches and retrieval results are observable, record the actual observation; when the result is empty, check downstream handling against an empty-result design, without asserting that a fabricated rule necessarily returns empty.
