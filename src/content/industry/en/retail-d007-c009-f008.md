# Amazon FBM fulfillment: workflow routing for operating reviews

## What the documents look like

Amazon FBM fulfillment leaves performance and returns-address setup with the seller, and platform warehouse inspection does not take part in the flow. The working papers for this category are the order picking list, the shipment confirmation sheet, the returns-address setting, and the logistics tracking sheet. Data comes from Amazon Seller Central, carrier systems, ERP orders, and customer-service email, with updates occurring per order and daily. In operating reports and exception reviews these papers act as evidence, so workflow routing has to place document status, handover requests, and authorization boundaries on separate nodes.

Two features of the category shape this page. First, the seller owns fulfillment and the returns address, so a shipment confirmation sheet can carry a pending status and an empty tracking-number field while the picking list already records a picked quantity. Second, the daily and per-order update rhythm means the papers used in a review may sit at different stages for the same order. A routing design that reads a collected form value as a completed business fact will misstate the stage.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the flow continues after the user completes the interaction. After the user fills the required information and submits, the node collects the submitted form values and passes them to later nodes. The user selection node is also a user-interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded; when the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. Both behaviors belong to the nodes themselves. The supplied documents do not describe a global state-recording switch, so none is assumed.

Collected values must be passed explicitly to later retrieval, judgment, or interface nodes. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval does not constitute authorization, and a collected form value does not equal a passed business verification.

Hypothetical drill sample. The source text for comparison reads: "Picking list P-0715 records order A-2201, picked quantity 12 units, status picked. Shipment confirmation sheet S-0715 records order A-2201, tracking-number field empty, shipment status pending confirmation. Returns-address setting R-0715 records returns address overseas warehouse H, effective scope this batch of orders." The draft sentence to be judged is: "Order A-2201 has completed shipment and the tracking number has been backfilled." The judgment must use the same subject, the same period, and the same field. The shipment confirmation sheet states a pending status and an empty tracking-number field, so the draft sentence's claim of completed shipment and backfilled tracking number is not supported by the source text.

## Three common errors

1. Treating a collected form value as passed business verification. The input is the submitted order number and shipment status; the comparison object is the status field on the shipment confirmation sheet; the observable result is that downstream execution proceeds as confirmed while the field values differ.
2. Treating a retrieval result as an authorization basis. The input is an order record returned by retrieval; the comparison object is the effective scope in the returns-address setting; the observable result is that a retrieval hit is used directly to release an order outside the authorized scope.
3. Writing a pending status as completed. The input is the draft sentence "Order A-2201 has completed shipment and the tracking number has been backfilled"; the comparison object is the pending status and the empty tracking-number field on the shipment confirmation sheet; the observable result is that the draft sentence and the source text hold mutually exclusive values in the same field.

## How to verify the setup

1. Input the picking list, shipment confirmation sheet, and returns-address setting text from the hypothetical sample above. Compare the required form fields against the document fields. The condition is met when the fields correspond item by item and each missing item is recorded as a gap.
2. Input the draft sentence "Order A-2201 has completed shipment and the tracking number has been backfilled." Compare it against the status field and the tracking-number field on the shipment confirmation sheet. The condition is met when the draft sentence is recorded as unsupported and the evidence gap is preserved.
3. Input the paper empty result []. Compare it against the downstream node design to see whether empty input is handled. The condition is met when the downstream design explicitly receives empty input; whether retrieval returns empty remains unknown.
