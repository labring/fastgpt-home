# Amazon FBM fulfillment: tool calls for operating reviews

## What the documents look like

Amazon FBM fulfillment generates four recurring materials: order pick sheets, shipment confirmation documents, return address settings, and logistics tracking sheets. These arrive from Amazon Seller Central, carrier systems, ERP orders, and customer service email. The brief describes them as updated per order and daily. In practice, an operating review matches materials to an order and a query time, then checks shipment confirmation fields, return address fields, and tracking fields separately.

FBM differs from FBA in one respect that shapes this page: the seller handles fulfillment and sets the return address without relying on platform warehouse inspection. That means the material states handled at the tool-call step are more dispersed. A pick sheet may already exist while a shipment confirmation document has not been filled in. A return address setting may sit at pending review. A logistics tracking sheet may contain only part of the carrier nodes. The tool call node decides whether to invoke a tool based on the tool introduction and parameter introductions. Retrieval or a form collecting a value does not constitute authorized execution.

Operating handover should check material state and operation authority separately. Reading a field does not mean shipment confirmation was executed, a return address was approved, or logistics was synchronized.

## Constraints at the tool calls step

A tool consists of a tool introduction and tool parameters. For system modules the parameters are fixed; for plugins the parameters are configurable. Two key values exist in parameters: the parameter introduction and whether the parameter is required. A tool with no parameters is invoked directly based on its introduction. A tool with parameters but no required parameters may still be invoked when no suitable parameter exists in context, and the model may fabricate a parameter. A tool with a required parameter and no suitable parameter available may not be invoked, and prompt wording can guide the user to supply the parameter. After the tool call node decides to invoke a tool, by default it returns the tool result to the AI for summarization. The tool call termination node ends the current invocation, calls no further tools, and does not call the AI to answer based on the tool result. Custom tool variables extend the variable input so that nodes not treated as tool parameters, or not callable as tools, can be invoked accordingly.

Hypothetical paper exercise sample: for one FBM order the pick sheet source text reads "Order number FBM-2026-0417-01, pick status: picked, shipment confirmation status: not confirmed, return address setting: pending review, logistics tracking sheet: carrier pickup node only." The proposed draft sentence reads "This order has completed shipment confirmation, the return address setting is effective, and the logistics tracking sheet has a complete track."

For checking, the tool call and plugin can only treat the source text above as input material. The phrase "has completed shipment confirmation" and the source value "shipment confirmation status: not confirmed" are mutually exclusive values for the same subject, same period, and same field, so the draft phrase is unsupported. "Pending review" provides no basis for the setting being effective, so this remains to be verified; no platform effectiveness rule may be inferred. "The logistics tracking sheet has a complete track" does not match the source value "carrier pickup node only," and no complete track is stated. A retrieval or plugin returning these field values does not indicate that shipment confirmation was executed, the return address was approved, or logistics was synchronized.

## Configuration and implementation checks

The following is a self-devised read-only plugin starting point. Parameters must be configured; these are not described as fixed parameters of a system module.

| Configuration item | Hypothetical starting point for this page | Check method |

| Tool introduction | State that it reads fields from FBM order pick sheets, shipment confirmation documents, return address settings, and logistics tracking sheets | Compare against the sample source text; confirm the introduction covers all four materials |
| Tool parameters | Order number, shipment confirmation status, return address status, tracking node | Compare each against the sample field names; record missing items as unknown |

## Three common errors

1. Writing the tool introduction as a general capability description without stating input conditions and situations where the tool should not be invoked. In the sample, "shipment confirmation status: not confirmed" is a situation where "has completed shipment confirmation" should not be output. When the introduction does not cover this, the model may generate a confirmation result that does not exist based on context.

2. Treating a parameter introduction as an execution assurance. In the sample, "return address setting: pending review" is only a field value. The parameter introduction explains what the field means; it does not indicate that review passed or that the setting became effective.

3. Treating the tool call termination node as a business termination. The termination node ends the current tool invocation and stops further tool calls and AI summarization. It does not change the business state of "shipment confirmation status: not confirmed" or "return address setting: pending review" in the sample.

## How to verify the setup

1. Input the order source text above together with the proposed draft sentence and compare item by item: "has completed shipment confirmation" conflicts with "not confirmed"; "return address is effective" lacks a basis; "carrier pickup node only" does not support a complete track. Record the conflict and the evidence gaps separately; do not treat all three as the same kind of error.

2. Input the same order number with "shipment confirmation status: not confirmed" and compare the value of the "shipment confirmation status" field in the tool parameters. Observable result: the field value remains "not confirmed" and does not become "confirmed" because of a tool call or retrieval return. If "confirmed" is returned, record it as contradicting the source text.

3. Using the read-only plugin flow diagram for the same order, check whether the termination node is attached at the end of the tool. When execution reaches that node, the current tool invocation should end, with no further tool calls or AI summarization. This control-flow check does not replace return address approval verification and does not ensure that business state is automatically rewritten. The paper input [] is used only to check the design for carrying an empty result; no actual test was performed.
