# JD POP seller operations: tool calls for operating reviews

## What the documents look like

JD POP third-party store operations centre on open-platform dispute rules and warranty-period service records. The daily materials are a product information table, a shipping-time commitment, a dispute handling form, and warranty-period service records. These materials update daily or per order. For operating reports and exception reviews, tool calls and plugins must pass the subject, object, status and validity scope recorded in these materials to the model for judgement.

Three industry facts shape this page. First, JD POP stores commonly handle disputes under open-platform rules and warranty-period service documents, so the dispute handling form and the warranty service record carry status fields that a report draft can easily overstate. Second, the main data sources are the merchant backend, the JD help centre, open-platform rules and logistics traces, so the tool inputs are field values from these materials rather than free narrative. Third, an error in this step can lead to an established transaction dispute, expanded after-sales liability, or platform demerit points, so the tool-call boundary must stay inside what the materials actually record.

A tool introduction tells the model what a tool does. A tool parameter carries a parameter introduction and a whether-required flag. The shipping-time commitment, the warranty start and end, and the evidence status on the dispute handling form are the context from which the model decides when to call a tool.

## Constraints at the tool calls step

The tool call node depends on three conditions: the tool introduction, the parameter introduction, and whether the parameter is required. A tool with no parameters is judged directly from its introduction, for example fetching the current time. For a tool with parameters and no required parameter, the model can call it even when the context holds no suitable parameter, and the model sometimes fabricates a parameter. For a tool with a required parameter, when no suitable parameter exists the model may not call the tool, and a prompt can guide the user to supply the parameter. System module parameters are fixed; plugin parameters are configurable.

In advanced orchestration, the available tool heads show a diamond once the tool call connection point is dragged, and that diamond connects to the diamond at the bottom of the tool call module. A connected tool automatically separates tool input from ordinary input, and its introduction can be edited so the call timing is more precise. The documentation advises adding few tools at a time and tuning before adding more.

The tool call termination node ends the current call. Placed after a tool, it forces the call to end when the workflow reaches it, calls no further tools, and does not call the AI to answer about the tool result. Custom variables extend tool input: a node not treated as a tool parameter, or one that cannot be tool-called, can receive a custom tool variable with a parameter description, so the tool call reaches that node and the workflow after it.

Retrieval results do not carry an authorization judgement, and a similarity score does not exclude unrelated business or unauthorized records.

Hypothetical drill sample

Material text one: "This store's product information table registers product A, warranty period twelve months from the day after signed receipt, shipping-time commitment forty-eight hours after payment."

Material text two: "Dispute handling form number J-01, buyer claims product A failed within the warranty period, current status awaiting merchant evidence, evidence deadline 10 June 2025."

Draft sentence to be judged: "J-01 has been decided in the buyer's favour, the merchant need not supplement evidence, and the case can be closed directly."

## Configuration and implementation checks

| Configuration item | Content on this page | Check method |
| --- | --- | --- |
| Tool introduction | Describes the tool that reads product information table or dispute handling form fields | Inspect whether the introduction states input conditions and situations where the tool should not be called |
| Tool parameters | Plugin parameters register product number, dispute form number, warranty start and end | Compare parameter introduction and whether-required flag, confirm the model does not call when a required parameter is missing |
| Tool connection | Connect the tool that reads the dispute handling form to the tool call module | In advanced orchestration confirm the diamond connection, debug with few tools first |
| Tool call termination | Placed after the dispute status output, ending the current call | Confirm no further tool call and no AI summary after termination |
| Custom variable | Adds a parameter description for a node not treated as a tool parameter | Compare the variable description with the corresponding node input |
| Hypothetical trial starting value | This sample sets "awaiting merchant evidence" as the current status value | Compare word by word with the status field in material text two and confirm agreement |

## Three common errors

1. Writing "awaiting merchant evidence" directly as "the claim has been decided in the buyer's favour". The input is the status field in material text two, the comparison object is the decision conclusion in the draft sentence, and the observable result is that the two disagree, so the draft sentence exceeds what the material records.

2. Treating the tool parameter introduction as a guarantee of execution. The input is the plugin parameter introduction text, the comparison object is the parameter value in the actual request, and the observable result is that when the introduction exists but the request lacks a required parameter, the model may not call the tool.

3. Treating retrieval similarity as an authorization filter. The input is the similarity score returned by knowledge base retrieval, the comparison object is the merchant authorization scope of the dispute handling form, and the observable result is that the score level does not change whether an unauthorized record appears; the authorization judgement needs a downstream implementation.

## How to verify the setup

- Verification one: input material text two and compare the draft sentence "J-01 has been decided in the buyer's favour" against the status "awaiting merchant evidence". The expected observation is disagreement, and the draft sentence needs to be changed to pending verification or to retain the evidence status.

- Verification two: input the warranty period "twelve months from the day after signed receipt" from material text one and compare whether the draft sentence cites that starting method. The draft sentence does not mention the day after signed receipt, so the expected observation is that the warranty start basis is missing and needs to be added.

- Verification three: input the evidence deadline "10 June 2025" from material text two and compare the current date with that date. Observe whether the date has passed; if it has not passed, the evidence obligation is still running and the draft sentence's "can be closed directly" lacks a basis. If the material does not state the current date, record this as unsupported and do not decide that closure holds.
