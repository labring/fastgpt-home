# Refund-only disputes: workflow routing for operating reviews

## What the documents look like

Refund-only dispute handling differs from ordinary refund-and-return work because there is usually no returned parcel entering the warehouse. The evidence emphasis falls on dispatch and signed receipt, together with the value of the goods. For operating reports and exception reviews this shapes the data scope directly: a report has to present the after-sales platform application record, the carrier trajectory, the customer service chat, and the warehouse outbound record side by side. When any one of those columns is missing, the evidence chain for a disputed order cannot close during review. The documented update frequency is per order and daily, and workflow routing advances on a single interaction rather than through batch synchronization or real-time triggering. The typical roles are the after-sales supervisor, the platform appeal specialist, and warehouse quality inspection. The handover materials between them include the refund-only application, the dispatch evidence, the signed receipt proof, and the appeal materials.

A practical consequence is that routing decisions rest on what the application record states at the moment of review, not on what a later business outcome might turn out to be. The application record, the dispatch evidence, and the signed receipt proof each carry their own subject, object, date, amount, and status fields, and those fields have to be compared on the same subject, the same period, and the same field before any conclusion is drawn.

## Constraints at the workflow routing step

The Form Input node and the User Selection node are both user interaction nodes. When either is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues downward after the user completes the interaction. The Form Input node collects required information and passes it to subsequent nodes after submission. The User Selection node evaluates the user's choice and executes the corresponding "yes" branch. The interaction state record is behavior of the interaction nodes; no separate global state-recording switch is set. Information that has been collected has to be explicitly passed to a later retrieval, judgment, or interface node. Order writes, document backfill, and external status synchronization require a separate business interface or a subsequent flow. Retrieval and form collection carry information transfer only and do not constitute authorized execution.

Hypothetical drill sample: the source material reads "Refund-only application A-01, applicant subject is a certain shop's after-sales account, object is order 2024-05-10-001, application status is pending review, application date 2024-05-11, application amount 199 yuan; the dispatch evidence shows outbound on 2024-05-09, and the carrier trajectory shows signed receipt on 2024-05-10." The draft sentence to be assessed reads "This order has completed the refund-only process, and the payment has been deducted from the shop account." That sentence writes a pending-review status as a completed refund, which does not agree with the application status in the source material.

## Three common errors

1. Treating a pending-review status as a completed refund. In the sample the application status is pending review, while the draft sentence states a completed refund and a deduction. This is a value mismatch under the same subject, the same period, and the same field. The check compares the application status field with the status description in the draft sentence; a mismatch means the draft sentence is unsupported.
2. Treating a retrieval hit as authorized execution. Retrieval and form collection transfer information only and do not perform permission or entity isolation. If a retrieval result directly triggers a deduction or a status synchronization, and there is no explicit record of a business interface or a subsequent flow, that is an overreach in inference.
3. Extending interaction node behavior into a global switch. The interaction state record is behavior of the interaction nodes. Claiming that a global state-recording switch or a submission-count control exists in the configuration adds a control item the source text does not describe.

## How to verify the setup

1. Input the sample source material and the draft sentence, and compare the application status field "pending review" with "completed refund-only" in the draft sentence. When the two values disagree, the draft sentence is judged unsupported; only when they agree does the next check proceed.
2. Input the sample application number A-01 and order number 2024-05-10-001, and compare the fields collected by the Form Input node with the source material. The condition is met when the fields are passed completely to the downstream judgment node; when a field is missing or rewritten, record it as a gap.
3. Input the deduction action described in the sample draft sentence, and compare whether a corresponding business interface or subsequent flow record exists. When no corresponding record exists, the action is judged not executed; when a record exists, check the record's subject and authorization boundary next.

These checks describe expected observations only. No test, deployment, approval, refund, or other business action has been performed. Where a field is not supplied in the source material, the value remains unknown.
