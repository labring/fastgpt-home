# Letter-of-credit documents: tool calls for operating reviews

## What the documents look like

Letter-of-credit document examination and presentation centres on the issuing bank notice, UCP600 clauses, the freight forwarder bill of lading, and bank presentation records. The operating goal is documentary consistency in service of the bank's payment conditions. Compared with export tax rebate filing, this stage reads the surface correspondence between documents and credit terms; tax matching sits outside this step. Each transaction updates its own records, so reports and exception reviews are grouped per single presentation. The document set typically includes the letter of credit, commercial invoice, bill of lading, insurance policy, and draft. Documentary clerks, bank international settlement staff, and the exporter carry different actions on the same presentation. A tool call can read or organise these materials; it cannot replace the bank's judgement of payment conditions.

## Constraints at the tool calls step

A tool introduction states the tool's purpose and should also state its input conditions and the situations in which it should not be called. The model decides whether to call a tool from the introduction, the parameter introductions, and whether each parameter is required. System module parameters are fixed; plugin parameters are configurable. A parameter introduction does not by itself guarantee execution. When a suitable required parameter is absent from context, the model may decline to call the tool; prompt wording can guide the user to supply it, and the actual request should then be checked for that parameter. In advanced orchestration, connect available tools to the diamond at the bottom of the tool call module, and begin with a small number of tools before tuning further. The tool call termination node ends the current call: no further tools are called and the AI is no longer asked to summarise tool results. Values collected through retrieval or a form enter the flow only; business verification, approval, database writes, and external synchronisation require separate implementation.

Hypothetical paper test case. The source text supplied for checking consists of three sentences. First: Issuing Bank A issued a letter-of-credit notice on 10 March 2025, beneficiary Exporter B, presentation period 21 days after the bill of lading date. Second: the bill of lading issued by Freight Forwarder C shows a loading date of 18 March 2025, consignee to order. Third: the commercial invoice was issued by Exporter B on 20 March 2025, amount consistent with the letter of credit. One draft sentence to be assessed reads: this presentation record shows that presentation was completed within the presentation period and that the bill of lading consignee information matches the letter-of-credit requirement. This draft sentence is checked in the report. The materials do not state the actual presentation date, nor the specific consignee requirement in the letter of credit, so the sentence is unsupported.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Comparison method |
| --- | --- | --- |
| Tool introduction | States input as materials for a single presentation; states non-call situation as missing materials | Compare against source text for presence of party, object, and status |
| Tool parameters | Plugin parameters configured per single presentation; system module parameters remain fixed | Check whether the actual request carries the parameters |
| Required parameter | Presentation date set as a required parameter | Observe whether the tool is called when that parameter is absent |
| Tool connection | Only the single-presentation checking tool is connected | Inspect whether inputs are separated after connection |
| Tool call termination | Placed after the single-presentation checking tool | Observe whether AI summarisation continues |
| Custom tool variable | Parameter description supplied for presentation date | Check whether the corresponding node is triggered |

The hypothetical starting point is scoped to a single presentation because this page's task groups by transaction, and the comparison object is the party, date, and object already stated in the source text.

## Three common errors

1. Treating a parameter introduction as an execution guarantee. Input: the plugin parameter introduction. Comparison: the parameter introduction against the source text. If the introduction mentions a presentation date but the source text does not state one, the actual request should not be treated as verified.
2. Treating a retrieved or form-collected value as authorised execution. Input: the presentation date field. Comparison: the collected value against the bank presentation record. If the record does not state it, only the gap is recorded; completed presentation cannot be determined.
3. Treating a pending-review status as an existing operating permission. Input: the presentation record named in the draft sentence. Comparison: the source text. If the source text contains only the notice and the bill of lading, with no actual presentation date stated, the sentence is unsupported.

## How to verify the setup

1. Input the three source sentences of the hypothetical sample together with the draft sentence. Compare the two claims in the draft sentence, completed presentation and matching consignee. The support condition is met only when the source text states the actual presentation date and the letter-of-credit consignee requirement. The current source text states neither, so record the item as pending verification.
2. Input a presentation-date request with the required parameter missing. Compare whether the actual request carries that parameter. If it is absent and the model does not call the tool, record the result as not called. If prompt wording supplies it and the tool is then called, check the parameter value in the request against the source text.
3. Input the tool call termination node placed after the single-presentation checking tool. Compare whether AI summarisation continues after termination. If it does not continue, record termination as effective. If it continues, record termination as not effective and inspect the connection position.
