# Franchisee onboarding: HTTP integrations for operating reviews

## What the documents look like

Franchisee onboarding transfers operating capability rather than filing legal disclosures. The working materials are training attendance sheets, opening checklists, SOP manuals and assessment results, drawn from training systems, supervisor apps, store photographs and the head office SOP library. These records refresh per store, per month, and errors land on failed openings, inconsistent customer experience and franchisee complaints.

For operating reporting and exception review, the central discipline is separating action status, signature status and authorization status inside those scattered materials, then using the HTTP module to extract external system return values into checkable fields. A checklist item marked complete, a training roster count and an assessment pass count each describe a different fact. None of them, on its own, states that a store is cleared to open.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a corresponding address. Params carries path request parameters, Body carries the request body, and Headers carries special information. All three data areas can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables and preceding node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime and histories. The chatId and responseChatItemId variables do not exist in test mode, so empty values during debugging are a known behavior of that mode.

Return values are extracted with JSON path syntax. Multiple keys can be configured, and when the output type is set to string, the corresponding value is converted into a JSON string. This mechanism retrieves data only. It does not determine whether materials are approved, whether a signature is complete, or whether a store meets opening conditions. Retrieval and similarity scores do not perform permission filtering, and an interface call by itself does not constitute authorization.

Hypothetical drill sample: a franchise project training department submits an onboarding exception review request dated 10 June 2025. The source text reads: "The training attendance sheet records that on 3 June 2025 the cashier and inventory course had 6 attendees on site and 6 sign-ins; the opening checklist records that on 5 June 2025 material counting was completed and store sign installation awaits supplier confirmation; the assessment results record 5 passes and 1 pending retake." The draft sentence under review is: "This store has completed all franchisee onboarding actions and can proceed to opening." The authorization boundary of this request is internal training department review; it does not include store opening approval or contract signing.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this drill | Reason and comparison method |
| --- | --- | --- |
| Request address and method | Fill in per the external interface document; reference an already provided variable for the address | Compare path and method word by word against the external interface document rather than a remembered value |
| Params and Headers | Inject the credential through secure configuration | Check that request header field names match the external document; keep credentials out of public samples |
| Body | Write the JSON structure according to the relevant request type | Compare field by field against the external interface contract and confirm the quoting rule for referenced variables |
| Variable references | List global variables, system variables and preceding node outputs item by item | Check that actual passed values correspond one-to-one with material fields; mark missing items unknown |
| Return value extraction | Configure key and output type per JSON path | Compare extraction results against the interface response example and confirm string conversion behaves as expected |
| Debug identity fields | chatId and responseChatItemId do not exist in test mode | Record the empty value for that mode and do not treat it as a business fault |

## Three common errors

1. Reading "material counting was completed and store sign installation awaits supplier confirmation" as full satisfaction of opening conditions. Check: input the source text above, compare the status field of each checklist item, and only when every item is complete with no pending confirmation is the condition satisfied; a pending confirmation is recorded as incomplete.
2. Treating "1 pending retake" as a pass. Check: input the assessment results source text, compare pass count against expected candidate count, and only when pass count equals expected candidate count is the condition satisfied; a pending retake is recorded as incomplete.
3. Treating submission of the review request as receipt of opening approval. Check: input the authorization boundary description of that request, compare its scope against opening approval authority, and when the request covers only internal training department review the approval condition is not satisfied and an authorization gap is recorded.

## How to verify the setup

1. Input the hypothetical sample's source text and draft sentence, then compare the draft sentence "has completed all franchisee onboarding actions and can proceed to opening" against the two records "store sign installation awaits supplier confirmation" and "1 pending retake." The presence of either incomplete item means the draft sentence is not supported.
2. Input the return value extraction entries configured in the HTTP module, then compare extraction results against the corresponding fields in the interface response example. A match between extracted value and response field satisfies the check; a mismatch is recorded as a difference between extraction configuration and the actual response.
3. Input the authorization boundary of that request together with the material list, then compare whether the request scope covers opening approval and contract signing. When the scope does not cover them, record a pending authorization gap and do not infer that approval has passed or that a contract has taken effect.
