# Franchise fee settlement: workflow routing for operating reviews

## What the documents look like

Franchise fee and deposit settlement centers on money movement and breach deductions. It does not handle government filing, which separates this category from franchise registration administration. The working documents are franchise fee invoices, deposit ledgers, deduction notices, and contractual payment schedules. Data arrives from finance systems, franchise contracts, bank statements, and store violation records. Updates occur monthly and on each deduction.

For operating reports and exception review, these traits mean the contract payment term, the deduction reason, and the invoice status need to sit on one reconciliation chain. Workflow routing collects those fields in sequence through interaction nodes and passes them to later judgment. The document set does not itself prove settlement, refund, or authorization; it only supplies values to compare.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution waits. After the user completes the required fields and submits, the node collects the submitted form information and passes it to later nodes. The User Selection node is also a user interaction node. It triggers the same interaction state and state recording. When the user makes a choice, the node evaluates that choice and executes the "yes" branch.

Interaction state recording is node behavior. No separate global state-recording switch is documented, and none should be assumed. Order writing, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval and form collection do not constitute authorized execution. A submitted form is a collected value; business verification, approval, database writes, and external synchronization need their stated downstream implementation.

Hypothetical drill sample: the source text reads, "Party A and Party B signed a franchise contract on March 1, 2025. The franchise fee due date is April 10, 2025. The deposit ledger shows a deposit of RMB 50,000 received on April 8, 2025. The deduction notice states that RMB 2,000 was deducted on May 6, 2025 due to a store violation." The draft sentence under review is, "The deposit has been fully refunded and there is no exception this period." Comparison point: the source text records only receipt of the deposit and occurrence of a deduction. It does not record a refund fact or a refund amount. The draft sentence lacks the refunding party, refund date, and refund amount, so it is unsupported. The source text also does not state that the period is exception-free.

## Configuration and implementation checks

| Configuration item | Type | Hypothetical trial starting point and comparison method |
| --- | --- | --- |
| Form Input node | Documented official behavior | On trigger, enters interaction state, collects required information, passes it to later nodes; compare each submitted field against the downstream node input |
| User Selection node | Documented official behavior | On user choice, executes the "yes" branch; verify branch connections one by one |
| Interaction state check | Implementation check item | Check whether the node records state; do not add or claim a global switch |
| Output handoff check | Implementation check item | Compare each form output against the input of the later retrieval, judgment, or interface node |
| External operation division | Implementation check item | Order writing, document backfill, and external synchronization require a separate interface or later process |

The table rows tie to this page's documents: invoices, deposit ledgers, deduction notices, and payment schedules supply the values that flow through Form Input and User Selection, and the handoff check confirms those values reach later nodes without being treated as execution.

## Three common errors

1. Treating form collection as authorized execution. Input: the deposit receipt record in the hypothetical sample above. Comparison: the draft sentence "The deposit has been fully refunded." Observable result: the draft sentence lacks a refund date and refund amount field, so it is judged unsupported.

2. Treating a user selection branch as automatic judgment. Input: the deduction notice and the User Selection node output. Comparison: whether the "yes" branch is actually connected and executed. Observable result: when the branch connection is absent, the later node receives no input.

3. Treating a retrieval hit as permission isolation. Input: a query containing a franchisee name. Comparison: the returned records against the access permission scope. Observable result: a returned record does not equal that user's right to view the record. A relevance score is not a category, entity, or permission filter, and retrieval is not authorization.

## How to verify the setup

- Verification one: input the hypothetical sample source text and the draft sentence. Compare whether the draft sentence contains the refunding party, refund date, and refund amount. Observable result: when all three are missing, the draft sentence is judged unsupported. This checks the named primary task of drafting review against supplied source wording and its limitations.

- Verification two: input the sample deduction notice. Compare the User Selection node's "yes" branch connection against the later node input. Observable result: when the branch is not connected, the later node has no input. The expected state is stated, not claimed as already tested.

- Verification three: input a retrieval request containing a franchisee name. Compare returned records against the access permission scope. Observable result: when returned records exceed the permission scope, record the gap. Do not claim retrieval is necessarily empty or necessarily matching. A paper input of an empty list can be used to check downstream design; it does not show that a fictional rule returns an empty list.

For cross-model retrieval, libraries using different vector models cannot be jointly associated. Check identifiers first and exclude non-matching items; do not run cross-model retrieval to compare missed recall. RRF is a hybrid result fusion process, not an on/off switch. Image retrieval requires a corresponding image input and model capability, and reranking requires a model enabled per settings.
