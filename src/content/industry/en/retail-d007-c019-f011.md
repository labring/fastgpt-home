# On-demand retail fulfillment: database operations for operating reviews

## What the documents look like

On-demand retail store fulfillment processes online orders by the minute. It does not work from periodic stock counts. The source data for this category comes from Douyin on-demand retail, Meituan or JD Daojia backends, store inventory, and rider tracking traces. The daily documents are instant orders, picking lists, out-of-stock reports, and delivery exception forms. Operating reports and exception reviews must reconstruct these minute-level documents into records that can be checked against one another.

The update frequency is minute-level, per order. This page does not derive batch synchronization, transaction triggers, or real-time mechanisms from that frequency. The database and operations layer determines whether those records can be written reliably, associated through the same identifier, and read back when needed. The material identities that matter here are the instant order number, the picking list, the out-of-stock report, and the delivery exception form. Each carries a status field, and the status field is what a review compares, not the mere presence of a record.

## Constraints at the database operations step

Business raw data and the vector retrieval backend have different responsibilities. They must be checked separately according to the actual deployment. Connection and load should be judged from observed connection counts, errors, and latency, not from untested concurrency thresholds copied from elsewhere. Backup generation and actual recovery are two separate things. They require separate verification and a checkable sample kept for each. After a database or service configuration change, the same business sample must be rechecked. A surviving process does not constitute a pass.

Hypothetical drill sample: the original text of an out-of-stock report reads "Store A, March 10, 2025, instant order number H-0310-07, item whole milk 250 ml out of stock, picker has submitted a substitution request, status is pending review." A draft sentence awaiting judgment reads "This order has completed the out-of-stock substitution and reported back to the platform." The original text shows only that the substitution request is pending review. It does not show approval, substitution execution, or status reporting back. The fact asserted by the draft sentence is not supported by the original text. It should be recorded as pending verification, and the approval result should be kept as an evidence gap.

A retrieval hit is not authorization. Finding a record by order number in the retrieval store only shows that the record exists. It does not show that the current operator is entitled to execute a substitution or report status back. The retrieval library and the authorization boundary are separate objects of comparison. A relevance score is not a category, entity, or permission filter. It does not exclude unrelated businesses or unauthorized records.

## Three common errors

1. Treating pending review as executed. In the sample, the substitution request status is pending review. If the draft sentence states that substitution is complete and reported back to the platform, the input is the original report text, the object of comparison is the value of the status field, and the observable result is that the draft sentence asserts more than the original text supports. It should be marked as unsupported.

2. Treating a retrieval result as authorization. Finding a record by order number in the retrieval store only shows the record exists. It does not show the current operator has the right to execute substitution or report status back. The input is the returned retrieval entry, the object of comparison is the authorization boundary, and the observable result is that retrieval hit and authorization state are separate. Authorization must be checked separately.

3. Using process survival in place of change recheck. After modifying a database connection configuration, the service still starts. The input is the changed configuration, the object of comparison is the read-back result for the same order number before and after the change, and the observable result is that when read-back is inconsistent, the change has not passed and must be rolled back or investigated further.

## How to verify the setup

1. Compare the sample report original text with the draft sentence, sentence by sentence. The input is the original text and the draft sentence above. The object of comparison is the status field value "pending review" against the draft sentence "completed substitution and reported back to the platform." The condition is met when the draft sentence is marked as pending verification and the approval result gap is recorded. The condition is not met when the draft sentence is written as a confirmed fact.

2. Perform one write and read-back for the order number. The input is the drill report record. The object of comparison is the written value against the read-back value. The condition is met when the fields match and the log database and business database are each readable. The condition is not met when read-back is missing or fields differ. In that case, record the difference and keep the sample.

3. Query the same order number once before and once after the change. The input is the same query before and after the change. The object of comparison is the two returned result sets. The condition is met when the results are consistent and no new errors appear. The condition is not met when the results are inconsistent. In that case, keep both returned results and the configuration difference as a record.

All of the above is a paper-based verification design. It has not been executed. A pending request is not approval. An offered option is not execution. An unsigned termination is not a completed termination. Where the original text does not state a system error or an automatic business action, no such error or action is asserted. Where evidence is missing, it remains missing.
