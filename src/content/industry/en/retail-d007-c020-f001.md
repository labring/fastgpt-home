# Certificates of origin: HTTP integrations for operating reviews

## What the documents look like

An origin certificate serves import-country tariff treatment and customs clearance. The application chain runs through the origin certificate application, the commercial invoice, the packing list, and production cost materials. Operating reports and exception reviews place the fields of these documents on the same timeline as the request records of external systems, so that a difference can be traced to a specific field or a specific request.

Data sources named for this category are the China International Trade Single Window, the CCPIT system, enterprise production records, and customer customs clearance requirements. Update frequency is per certificate or batch. The review value at this step lies in joining the declared fields of each certificate, the interface request, and the external response, then locating where a difference arises.

This category differs from letter-of-credit document examination because the origin certificate serves import-country tariff and clearance needs and is not necessarily bound by a letter of credit. Errors carry consequences such as blocked customer clearance, loss of tariff preference, and amendment costs.

## Constraints at the HTTP integrations step

The HTTP module sends a request to the corresponding address. Params carry path request parameters and are used mostly with GET requests. Body carries the request body and is used mostly with POST and PUT requests. Headers carry request headers for special information. All three data locations can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and the output of preceding nodes. Body takes effect only under specific request types.

Return values are not the interface return value itself. They represent how to parse the interface return value, and JSON path syntax extracts the needed value from the response. After FastGPT v4.6.8, output formatting mainly converts JSON into a string. When the output type is set to string, the value of the corresponding key is converted into a JSON string.

System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. The histories variable defaults to a maximum of 10 entries and its length cannot be modified. In test mode, chatId and responseChatItemId do not exist. An empty value observed during debugging belongs to an environment difference and does not by itself indicate a business fault.

For the chat interface, APIKey authentication is used, and passing `body.appId` in the request body is recommended when calling `chat/completions`. For OpenAI SDK compatibility, `Authorization: Bearer <apiKey>-<appId>` is also supported, and in that case `body.appId` is not required. The appId priority order is `body.appId`, then `<apiKey>-<appId>`, then the appId associated with the apikey under the older adaptation. Some SDKs require `v1` in the BaseUrl and some do not; if a 404 appears, adding `v1` and retrying is the documented step. The `model`, `temperature`, and similar parameter fields passed in are ineffective because these fields are determined by the orchestration. Actual Token consumption is not returned; if it is needed, `detail=true` can be set and the `tokens` value inside `responseData` calculated manually. When `detail=true`, `responseData` holds module status and the complete result, which supports reviewing node running time and token consumption.

If a workflow contains an interactive node, the same interface is called and `detail=true` must be set. With `stream=true`, the interactive node configuration is available from `data.interactive` in the `event=interactive` message. With `stream=false`, it is available from the element containing the `interactive` field in `choices[].message.content`. The `interactive` returned to an external caller is a display configuration containing only `type` and `params`; internal runtime fields such as `entryNodeIds`, `memoryEdges`, `nodeOutputs`, and `nodeResponseId` are not returned. When an internal children, loop, or tool wrapper interaction is hit, the interface returns the deepest user-facing interactive node. A pending request is not an approval, and an offered option is not an execution.

For plugin-type applications, the interface defaults to `detail` mode. No `chatId` is required because a plugin runs only one round, and no `messages` are required. Inputs are represented through `variables`, and outputs are obtained from `pluginData`.

Hypothetical drill sample: on 10 March 2025, a document clerk at an exporting enterprise submits one origin certificate application, accompanied by commercial invoice number INV-2025-0310, packing list number PL-2025-0310, and one set of production cost materials. The application status is "submitted, awaiting review." A draft handover sentence reads: "This application has passed review and certificate issuance is complete, and it can be used directly for customer customs clearance." Under the available materials, neither review nor issuance is recorded, so the draft sentence is unsupported.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Check method |
| --- | --- | --- |
| Request address | The address given in the external interface document | Compare word by word with the interface document; the address may reference variables |
| Request method | Selected according to the external interface contract | Compare with the action declared in the interface document |
| Headers authentication | Credentials injected through security configuration | Check that credentials are not written into public samples |
| Body structure | JSON fields per the interface contract | Check that field names and types match |
| Return value extraction | JSON path expression | Use a sample response to check the extracted result |
| Output type | String or object | Selected according to the needs of the downstream node |

The trial starting point for the request address is chosen because the external interface document is the only named source for the address, and it is compared against that document rather than against an internal default. The method and Body structure follow the external interface contract for the same reason. Headers authentication is injected through security configuration so that credentials do not appear in public samples. The output type is chosen by downstream need; the documented behavior is that selecting string converts the value of the corresponding key into a JSON string.

## Three common errors

1. Treating an empty value from a debugging environment as a business fault. In test mode, chatId and responseChatItemId do not exist. If a report counts sessions by these two fields, a debug record can be misjudged as a missing session. Check: input a test-mode request, compare whether these two fields appear in the return, and observe whether the result matches the test-mode statement.
2. Writing a pending-review status as issued. In the sample, the application status is "submitted, awaiting review," while the draft sentence states that review passed and issuance is complete. Check: input the sample source text and the draft sentence, compare the value of the status field, and observe whether the draft sentence goes beyond the scope of the source text.
3. Using a similarity score as a permission judgment. The `similarity` field in the return is retrieval relevance and does not perform entity or permission filtering. Check: input a return containing a similarity score, compare what the field means against permission-related fields, and observe whether the score is used as a basis for access control.

## How to verify the setup

1. Input the sample source text and the draft sentence. Compare "submitted, awaiting review" with "has passed review and certificate issuance is complete." When the draft sentence states review and issuance conclusions that the source text does not record, the draft sentence is unsupported. The expected observation is a mismatch between the recorded status value and the conclusion asserted in the draft; the gap remains a gap.
2. Input the request return from test mode. Compare whether chatId and responseChatItemId appear. When both are absent, record this as a test-mode difference and do not record it as a business fault.
3. Input a return containing `similarity`. Compare that field with permission-related fields. When `similarity` represents relevance only, confirm that it is not used as a basis for authorization or entity isolation.

These checks describe what to input, what to compare, and what observation satisfies the condition. No test, deployment, approval, issuance, or refund is claimed to have occurred. Where the source materials do not record review or issuance, the status remains unknown, and the draft sentence remains unsupported rather than disproved.
