# Certificates of origin: workflow routing for operating reviews

## What the documents look like

Certificates of origin serve import-country tariff treatment and customs clearance. Their governing basis differs from letter-of-credit document examination, which is not necessarily the constraint here. The working judgment rests on origin rules, production records, and the customer's clearance requirements. Data sources include China International Trade Single Window, CCPIT systems, enterprise production records, and customer clearance requirements. Everyday documents are the certificate-of-origin application, commercial invoice, packing list, and production cost materials. Update frequency is per shipment and batch.

Operating reporting and exception review collect these documents per shipment, then check the routing of process nodes. This page addresses workflow routing only: how interaction nodes collect information, how their output passes to later nodes, and which actions require a separate business interface. Retrieval and form collection do not constitute authorized execution. Order writes, document backfill, and external status synchronization require a separate business interface or a later process.

## Constraints at the workflow routing step

When the Form Input node triggers, the conversation enters an interaction state and the workflow state is recorded. After the user completes the required information and submits, the node passes the entered information to later nodes. The User Selection node also enters an interaction state; when the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. Both behaviors are documented. Interaction waiting, state recording, and dialog hiding follow the documentation. No global state-recording switch is assumed, and no submission count, automatic judgment, or snapshot guarantee is invented.

Hypothetical exercise sample: an export clerk submits one certificate-of-origin application. The source material reads: "Applicant: Exporter A; Object: Goods Model B; Status: certificate-of-origin application submitted, pending review; Valid scope: March 2026 batch." A second sentence reads: "The commercial invoice amount and the packing list piece count are consistent; the production cost materials state that the production completion date for this batch was 12 March 2026." The draft sentence to be judged is: "This batch of goods has completed certificate-of-origin processing and can be sent directly to the customer for customs clearance." The judgment requires the same subject, same period, and same field. An application submitted and pending review is an unsupported status and cannot yield completed processing. Sending to the customer for customs clearance is a later business action that the material does not state.

## Three common errors

1. Treating form collection as authorized execution. In the sample the application status is pending review. If the draft sentence states that processing is complete, the input is the pending-review status, the comparison object is the "completed" field, and the observed result is that the two do not match. The judgment should be unsupported.

2. Treating retrieval results as a permission or entity filter. The sample subject is Exporter A. If a downstream node includes records of other subjects in its output, the input is the subject identifier, the comparison object is Exporter A, and the observed result is a subject mismatch. Those records should be excluded.

3. Extending interaction node behavior into automatic business actions. The sample does not state sending for clearance. If the draft sentence directly states sending, the input is the source material, the comparison object is the sending field, and the observed result is that it is missing. The evidence gap should be recorded.

## How to verify the setup

1. Input the sample source text and the draft sentence. Compare "pending review" with "completed processing" and observe whether a field mismatch appears. The expectation is unsupported. No claim is made that this was actually tested.

2. Input the sample subject Exporter A and records of other subjects. Compare the subject identifiers and observe whether a subject mismatch appears. The expectation is to exclude non-matching records and record the actual observation.

3. Input a clearly defined paper-based empty result and compare the downstream handoff design. Observe whether it is handled as an empty result. No claim is made that a fictional rule retrieval necessarily returns empty.

Libraries using different vector models cannot be associated together. Check identifiers only, exclude non-matching records, and record the actual observation. Retrieval checks describe observations and failure branches; they do not guarantee a first hit, full recall, or that an unrelated query must return empty. Image retrieval requires a corresponding image input and model capability, and reranking requires a model and must be enabled by configuration.

The operational handoff must keep clear which materials, operations, and requests are at which authorization status. Retrieval and form collection are not authorized execution.
