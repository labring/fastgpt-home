# Brand member operations: HTTP integrations for operating reviews

## What the documents look like

Brand member private-domain operations centre on customer data and repeat-purchase outreach. The work does not cover store shift scheduling. The materials handled day to day are member tag tables, outreach plans, coupon rules and privacy authorization records. Operating reviews and anomaly retrospectives connect those materials to HTTP interfaces and external systems, checking the member identifier, outreach target, coupon rule status and authorization scope that an interface actually carries. Data updates follow a daily and weekly rhythm, and report checks compare the same period and the same field. The fact that an HTTP module can be triggered repeatedly does not imply an automatic batch synchronization.

## Constraints at the HTTP integrations step

The HTTP module can be added more than once, is configured manually and executes on trigger. It sends an HTTP request to a corresponding address, and in practice it works much like Postman or ApiFox. Params are path request parameters and are used mostly with GET requests. Body is the request body and is used mostly with POST and PUT requests. Headers carry special information. All three can reference variables through `{{}}`, and the URL can also reference a variable. Variables come from global variables, system variables and upstream node outputs.

System variables include appId, chatId, responseChatItemId, variables, cTime and histories. The histories variable takes at most the default 10 records, and that length cannot be changed. chatId and responseChatItemId do not exist in test mode, so an empty debug value is not a business fault. Return values are extracted by JSON path, and when the output type is set to string, the value of the corresponding key is converted into a JSON string.

When calling chat/completions, passing body.appId in the request body is recommended. For OpenAI SDK compatibility, Authorization: Bearer <apiKey>-<appId> is also supported, and body.appId is then not required. Some SDKs need `v1` added to BaseUrl and some do not; if a 404 appears, adding `v1` and retrying is the documented step. The appId priority order is body.appId, then <apiKey>-<appId>, then the appId associated with the apikey under the older adaptation. The model, temperature and similar parameter fields passed in are invalid; the orchestration decides them. Actual token consumption is not returned, so detail=true can be set and the tokens value inside responseData calculated manually. Proxying a team member identity through authProxy requires the team owner to enable authProxy when creating or editing that key, and the proxied identity still needs permission on the target application and conversation; this applies only to FastGPT >= v4.15.0.

A retrieval result or a collected form value does not constitute business authorization. Approval, database writes and external synchronization require their stated downstream implementation.

Hypothetical paper exercise: on 10 June 2025 a brand CRM team reviews an outreach plan material. The source text reads: "The member tag table records that member A belongs to the high-activity segment. The outreach plan intends to send a threshold discount coupon to member A on 12 June 2025. The coupon rule states that the coupon is valid until 30 June 2025. The privacy authorization record shows that member A's marketing outreach authorization status is authorized." The proposed handover request is: "Please submit member A's outreach execution to the external system through the HTTP interface." The object is member A, the period is June 2025, and the field is outreach execution status. The materials show only the plan and the authorization; they do not show that the external system accepted or executed anything. The request remains pending verification.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Comparison method and reason |
| --- | --- | --- |
| Request address and method | Fill in according to the external interface document; the address references a variable that has been provided | Compare against the external interface contract to confirm address and method; do not infer from page habits |
| Params and Headers | Check request parameters and request headers separately; inject the authorization credential through secure configuration | Compare each value actually passed; do not write sample credentials into public material |
| Body | Use a request body only under the corresponding request type | Check the JSON structure against the external interface contract; add quotes when referencing a string |
| Variable reference | Reference global variables, system variables and upstream node outputs | Compare each value actually passed and confirm the variable source |
| Return value extraction | Configure the key by JSON path and choose the output type as needed | Compare the extraction path and output format against the interface response example |
| Debug identity fields | chatId and responseChatItemId do not exist in test mode | Do not treat an empty debug value as a business fault; check separately on a formal call |

## Three common errors

1. Treating "intends to send on 12 June 2025" in the outreach plan material as already executed. The check takes the source text of that material as input, compares whether the field is a planned date or an execution status, and records the result as pending verification when the material does not state an execution outcome.
2. Extending "authorized" in the privacy authorization record to mean the external system has accepted the request. The check takes the source text of that record as input, compares whether the authorization object and the request object are both member A, and notes that an authorization status does not replace the external system's acceptance or execution status.
3. Treating the coupon rule validity of 30 June 2025 as a supply deadline or an outreach execution deadline. The check takes the coupon rule source text as input, compares whether the field is coupon validity, and preserves the evidence gap when the material does not state an outreach execution deadline.

## How to verify the setup

1. Input the outreach plan source text and the proposed handover request from the hypothetical exercise. Compare whether the request object member A and the material object member A are the same subject, in the same period of June 2025, on the same field of outreach execution status. The material shows only the plan and the authorization and does not show external system acceptance, so the expected result is pending verification, not a determination that execution occurred.
2. Input the privacy authorization record source text and the request. Compare the authorization status field with the authorization scope the request requires. If the record shows authorized and the request scope falls inside that authorization, the authorization condition is met; whether the external system accepts still requires downstream implementation confirmation, and an authorization record does not establish that the request is complete.
3. Input the coupon rule source text and the outreach plan. Compare the coupon validity field with the outreach plan date field. The coupon is valid until 30 June 2025 and the outreach plan date is 12 June 2025; these are different fields and neither is derived from the other. If confirmation of an outreach execution deadline is needed, the material does not state one, and that is recorded as an evidence gap.
