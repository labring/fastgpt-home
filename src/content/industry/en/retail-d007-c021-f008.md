# Brand member operations: workflow routing for operating reviews

## What the documents look like

Brand member operations in this category work from customer data and repeat-purchase outreach. Store scheduling sits outside this scope. The recurring records are member tag tables, outreach plans, coupon rules and privacy authorization records. Primary sources named for the category are the CRM system, enterprise WeChat, POS transaction records and mini-program behavior data. Typical consequences of getting this wrong are outreach harassment complaints, uncontrolled coupon cost and member churn.

This page addresses one task inside that setting: operating reports and exception review, implemented through workflow routing. The routing step collects the fields a review needs, branches on a user choice, and passes the collected values to later nodes. Update frequency for this category is daily and weekly. That frequency affects how reporting periods are chosen. It does not constrain how an interaction node is triggered, so this page does not derive batch synchronization or real-time mechanisms from it.

Two documented interaction nodes are relevant. The form input node belongs to the user interaction node type. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the dialog box is hidden. After the user completes the required information and submits, the node collects the submitted form values and passes them to subsequent nodes. The user selection node also belongs to the user interaction node type and behaves the same way on trigger. When the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. Both nodes can be added repeatedly and both trigger execution.

## Constraints at the workflow routing step

Because harassment complaints, coupon cost overruns and member churn are the named failure modes, a review workflow has to separate four things: behavior the nodes already perform, fields that can actually be configured, manual comparison actions, and business actions that require a separate system implementation.

Recording workflow state, hiding the dialog box and entering an interaction state are documented node behavior. There is no separate global state-recording switch to set, and no documented submission count or automatic judgment to configure. The form collects values. Business verification, approval, database writes and external synchronization require a separate business interface or a later process. Retrieval is not authorization. A similarity setting does not carry permission or entity-isolation duties.

Hypothetical paper exercise. The source material reads: "The member tag table states that member number M-0001 belonged to the 'dormant reactivation' tier from 1 March 2025 to 31 March 2025. The outreach plan states that the same member was scheduled for 2 outreach attempts in the same period. The coupon rule states that the coupon applies to that tier and is valid until 15 April 2025. The privacy authorization record states that the member's authorization status is 'signed'." The handover request to be judged reads: "Please configure the workflow so that the review form collects these four fields, and after the user selects 'enter exception review', passes the fields to subsequent nodes." That request stops at collection and branching. It contains no coupon redemption, no message send and no authorization change.

## Three common errors

1. Treating an interaction node as an authorization execution. In the exercise the privacy authorization record reads "signed". If a draft states that submitting the form completes an authorization change, the input is a form value and the comparison object is an authorization record field. These are not the same action. Executable check: compare whether the form field and the authorization record field share the same subject, the same period and the same field, then observe whether a separate record of authorization change exists.

2. Treating retrieval or similarity as a permission filter. The exercise reviews by member number and period. If a draft states that a similarity setting automatically excludes unrelated members, the input is a retrieval configuration and the comparison object is the record ownership field. Executable check: first verify the identifier and exclude non-matching records, record what is actually observed, and do not run cross-model retrieval to compare missed recalls.

3. Treating a pending or planned item as completed. In the exercise the outreach plan reads "scheduled for 2 outreach attempts". If a draft states that 2 outreach attempts were completed, the input is a plan field and the comparison object is the actual outreach record. Executable check: compare the same subject, the same period and the same field; where the record is absent or shows only a related stage, record the item as unsupported.

## How to verify the setup

1. Enter the four source statements and the handover request from the hypothetical exercise. Compare whether the form fields correspond item by item to the material, and observe whether all four fields are present and the required-field setting takes effect. When a field is missing the interaction does not submit; this is expected behavior and no live test is claimed.

2. Enter the user selection "enter exception review". Compare whether the branch connection points to the subsequent node, and observe the connection relationship for whether the "yes" branch is executed. Verify each branch connection individually. First-hit matching and full recall are not guaranteed.

3. Enter an explicit paper input of an empty result `[]`. Compare whether the downstream node design accepts an empty value, and observe whether the downstream handles empty input as designed. No claim is made that a fictional rule retrieval necessarily returns `[]`. Libraries built on different vector models cannot be associated together; verify identifiers only, exclude non-matching records, and record what is actually observed.

Across all three checks, the same subject, the same period and the same field are required. A contradiction exists only when the same field carries explicitly mutually exclusive values. Where a record is absent or shows only a related stage, the item remains unsupported or pending verification, not negated and not conflicting. A pending review does not demonstrate the absence of operating permission. Signing, reaching cooperation and contract effectiveness are three distinct facts. A quotation validity period does not indicate a supply period. Missing evidence stays missing, and no authorization or effective clause is invented to reach a definite answer.
