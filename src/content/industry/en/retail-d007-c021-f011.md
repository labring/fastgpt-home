# Brand member operations: database operations for operating reviews

## What the documents look like

Brand member private-domain operations draw on four record families: the member tag table, the outreach plan, the coupon rules and the privacy authorization record. Source systems named in the category brief are the CRM system, WeCom, POS consumption records and mini-program behavior data, with daily and weekly update cadences. Operating reviews and anomaly post-mortems require these records to be aligned on the same subject, the same period and the same field before any judgment is written. The database and operations layer carries connection, storage and auditability duties; it does not decide whether a business authorization exists.

Two features shape this page. First, business source data and the vector retrieval backend can sit in different services, so each deployment confirms its own connection settings and never infers a value from a variable name. Second, retrieval output is not an authorization or entity filter; a similarity setting does not exclude unauthorized records, and libraries built on different vector models cannot be associated together. Reviewers check the identifier first, exclude non-matching records, and record what remains unknown.

A hypothetical paper exercise sample is used throughout. A brand member operations team keeps a paper record whose text reads: "Member ID M-001; tag table registration status: tiered; outreach plan registration status is pending review; coupon rule registration status: not yet effective; privacy authorization record registration status: signed; coverage period 1 March 2024 to 31 March 2024." The candidate judgment sentence to be assessed is: "M-001 completed outreach in March 2024 and redeemed a coupon." The sentence touches two fields. The source text states only that the outreach plan is pending review and the coupon rule is not yet effective; it does not record outreach execution or a redemption event.

## Constraints at the database operations step

The review step inherits several limits from the documented environment. Connection settings for the main business store and the log store are confirmed separately, because the log URI may reuse the main store when it is not configured. Index creation and cleanup at startup are governed by a documented switch; when that switch is off, index maintenance becomes a manual duty. Cache connectivity is confirmed against the actual cache service address rather than assumed. None of these settings grants permission, and none of them substitutes for reading the privacy authorization record.

Retrieval behaves as retrieval. A similarity score is not a category, entity or permission filter, so it does not exclude unrelated businesses or unauthorized records. An empty result set is handled as a downstream design question: a paper input of an empty list can be used to check how the report layer treats an empty return, and no claim is made that a fictional rules lookup must return empty. Cross-model association is not performed; identifiers are checked and non-matching records are excluded, without running cross-model retrieval to compare missed recalls.

Backup creation and restore verification are separate activities. A backup that was generated is not a restore that was validated, and a running process is not evidence that a configuration change was reviewed. After any change to database or service configuration, the same business sample is re-checked against the same fields. Where the source text does not record a field, the field remains unknown; a pending review is not approval, an offered option is not execution, and an unsigned termination is not a completed termination.

## Three common errors

1. Treating the outreach plan status "pending review" as completed outreach. Input: the sample source text and the candidate judgment sentence. Comparison: the outreach plan field against the phrase "completed outreach." A pending-review status does not constitute execution evidence. Observable result: that clause is unsupported, and it is not recorded as a denial or a conflict.

2. Treating the coupon rule status "not yet effective" as a completed redemption. Input: the sample source text and the candidate judgment sentence. Comparison: the coupon rule field against the phrase "redeemed a coupon." A not-yet-effective rule does not constitute a redemption record. Observable result: that clause is unsupported, and it is not recorded as a denial or a conflict.

3. Treating a retrieval result as an authorization basis. Input: a set of member records returned by one retrieval. Comparison: the retrieval action against an authorization determination. Retrieval does not perform permission filtering. Observable result: the authorization state still has to be read from the privacy authorization record field, and the retrieval output does not settle it.

## How to verify the setup

1. Input the sample source text and the candidate judgment sentence. Compare the outreach plan registration status "pending review" against "completed outreach." If the source text does not record an outreach execution event, that clause is assessed as unsupported; it is not assessed as a denial or a conflict.

2. Input the sample source text and the candidate judgment sentence. Compare the coupon rule registration status "not yet effective" against "redeemed a coupon." If the source text does not record a redemption event, that clause is assessed as unsupported; it is not assessed as a denial or a conflict.

3. Input a paper input of an empty list together with the downstream report design. Compare the empty-result handling logic. If the downstream design does not define how an empty result is handled, record this as a gap to be supplied; do not claim that a fictional rules lookup must return an empty result.

Across all three checks, the same subject, the same period and the same field are required. Only mutually exclusive values within one field count as a contradiction. A field that is not recorded, or that carries only a related-stage status, is unsupported or pending verification. A pending review does not prove the absence of operating authority, and no authorization or effectiveness clause is invented to produce a definite answer.
