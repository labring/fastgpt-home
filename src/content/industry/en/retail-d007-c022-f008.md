# Omnichannel stock transfers: workflow routing for operating reviews

## What the documents look like

Omnichannel transfer work moves goods between stores and warehouses. It does not handle marketing outreach, which separates it from membership and private-domain operations. The data comes from ERP inventory, store POS, e-commerce orders and WMS. The day-to-day documents are transfer requests, inventory snapshots, store shortage lists and transfer logistics notes. Operating reporting and exception review must align these documents to the same entity, the same period and the same field before any comparison is meaningful. Data updates on a daily and weekly cadence. The three most time-consuming steps are locating transferable stock, approving the transfer path, and updating arrival and putaway. Reporting and review must be able to state the input and the receiving status of each of those steps.

For this task, three traits shape the work. First, the object under review is goods in motion, so a request, a snapshot and a logistics note describe the same movement from different angles and can disagree without either being wrong. Second, the source systems update on different rhythms, so a snapshot and a shortage list may cover different moments. Third, the workflow routing step decides what the review sees and in what order, which means routing choices become part of the evidence trail.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. It collects the required information the user fills in and passes that information to later nodes. The user selection node is also a user interaction node. When the user makes a choice, the node evaluates the choice and executes the "yes" branch. Interaction state is recorded by the interaction nodes themselves. No separate global state-recording switch is documented.

The values collected by a form are form values. Business verification, approval, database writes and external synchronization require a separate business interface or a later process. A retrieval step or a form submission does not constitute authorization to execute a business action.

Hypothetical drill sample. The material text reads: "Transfer request T-2024-0612, requesting entity East China regional store warehouse, source object Shanghai warehouse, destination object Hangzhou store, quantity 40 units, status pending review, request date 2024-06-12." The proposed handover request reads: "Update this request status to approved and synchronize to WMS." The deciding points: pending review is not approval. The status change and the external synchronization demanded by the proposed handover request are not shown as executed anywhere in the material, so the request is unsupported.

## Configuration and implementation checks

| Configuration item | Type | Assumed starting point and reason |
| --- | --- | --- |
| Form input node | Documented feature | Collects the transfer request number and status field; passes them to later nodes after submission |
| User selection node | Documented feature | Branches on whether to enter exception review; executes the "yes" branch after the choice |
| Output handoff | Implementation check | Compare each form output against the input of the later retrieval or decision node |
| Retrieval scope | Implementation check | Check the library identifier and the vector model identifier; exclude non-matching libraries |
| External synchronization | Implementation check | Status write-back and WMS synchronization require a separate business interface |
| Empty-result handling | Implementation check | Use a paper input of [] to check the downstream design; do not claim a rule retrieval must return empty |

## Three common errors

1. Treating pending review as approved. The input is the sample's "status pending review"; the comparison object is "approved" in the proposed handover request; the observable result is that the material records no approval action, so the item is logged as unsupported.

2. Treating a collected form value as authorization to execute. The input is the request number submitted through the form; the comparison object is the external action "synchronize to WMS"; the observable result is that the node only passes values, and external synchronization needs a separate interface.

3. Treating retrieval as a permission filter. The input is one library retrieval; the comparison object is "return only records the caller is permitted to see"; the observable result is that relevance does not carry permission or entity isolation, so the permission source must be checked separately.

## How to verify the setup

1. Take the sample text "Transfer request T-2024-0612 ... status pending review," enter the proposed handover request "update to approved and synchronize to WMS," compare the status field against the approval action, and record the item as unsupported when the material shows no executed approval.

2. Take the entity, source object, destination object and quantity from the sample text, enter them against the required form fields, compare the form output with the input of the later node item by item, and treat an exact match with a correctly connected branch as satisfying the condition.

3. Take a paper input of [] and compare it against the empty-result handling design, observe whether the downstream process treats it as an empty input, and do not claim that a hypothetical rule retrieval must return []. For libraries on different vector models, check the identifiers only and exclude non-matching libraries; do not run a cross-model retrieval to compare missed recalls.
