# Brand outlet operations: HTTP integrations for operating reviews

## What the documents look like

Brand outlet discount operations centre on clearing past-season stock. The main data sources are ERP stock age, POS sales, outlet mall campaigns and historical discounts. The working documents are discount approvals, slow-moving stock lists, price tags and gross-margin worksheets. The brief marks this background as broadly indicative, and the update frequency of weekly or monthly figures does not drive any automatic synchronisation mechanism on this page.

Operating reviews and exception reviews bring those documents together. A slow-moving stock list, the status recorded in a discount approval, and a gross-margin worksheet result are read side by side. An HTTP integration is the channel that fetches values from an external system and writes status back. The consistency between what the interface returns and what the internal documents record is the point of comparison.

Three industry facts shape this task. Past-season clearance aims at moving aged stock rather than maintaining a new-season full-price image, so a discount value and its approval state carry commercial weight. Stock age comes from ERP and sales come from POS, so an operating review often compares two systems rather than one. Discount approval is a staged process, which means a recorded state such as pending review describes a stage and does not describe an executed price change.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a target address. Params are path request parameters and appear mostly in GET requests. Body is the request body and appears mostly in POST and PUT requests. Headers carry special information. All three can reference variables through `{{}}`. Variables come from global variables, system variables and upstream node outputs. The URL can also reference variables.

System variables include appId, chatId, responseChatItemId, variables, cTime and histories. Histories default to a maximum of 10 entries and the length cannot be modified. chatId and responseChatItemId do not exist in test mode, so an empty value during debugging is not by itself a business fault.

Return values are extracted with JSON path syntax. When the output type is set to string, the value for the corresponding key is converted into a JSON string. The chat interface uses APIKey authentication. When calling chat/completions, passing body.appId in the request body is recommended. The appId priority order is body.appId, then `<apiKey>-<appId>`, then the appId associated with the apikey in the older adaptation. Some SDKs need a v1 path in BaseUrl and some do not; a 404 can be retried with v1 added.

The model, temperature and similar parameter fields passed in are ineffective because the orchestration decides them. Actual consumed Token values are not returned; detail=true allows manual calculation from the tokens values inside responseData. When an interactive node is reached, the returned interactive object contains only type and params. Internal runtime fields such as entryNodeIds, memoryEdges, nodeOutputs and nodeResponseId are not returned.

Hypothetical paper exercise sample. A brand outlet clearance group checks a slow-moving stock list against a discount approval record on paper. The stock list text reads: "SKU A, stock age 210 days, current discount 50 percent, belonging to the 2024 autumn batch." The approval record text reads: "SKU A, requested discount 40 percent, approval status is pending review." The draft sentence under review reads: "SKU A discount has been approved and can be executed at 40 percent." The comparison covers the same SKU, the same batch and the same discount field. A status of pending review does not constitute approval, and the draft sentence is not supported by the two source texts.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | How it is checked and why |
| --- | --- | --- |
| Request address | The address given in the external interface document; may reference a variable | Chosen from the interface document; when the address contains a variable, check the value actually passed |
| Request method | GET or POST as stated in the interface document | Compared against the interface contract, not assigned from habit |
| Headers authentication | Authorization injected through secure configuration | Credentials are not written into public examples; check that the credential is present |
| Body structure | Used only under the corresponding request type | Compared field by field against the external interface contract |
| Variable reference | References a global variable or an upstream node output | Each referenced value is checked against the value actually passed |
| Return value extraction | Key configured according to JSON path | Compared against the interface response structure to confirm the extraction path |

## Three common errors

1. Treating a pending review status as an approved discount. The input is the approval record text "approval status is pending review". The comparison object is the draft sentence "discount has been approved". The observable result is that the approval status field value and the claim in the draft sentence do not match, so the draft sentence is not supported.

2. Treating a missing chatId in test mode as a business fault. The input is a request made in test mode. The comparison object is the system variable description stating that chatId does not exist in test mode. The observable result is an empty value in the test environment, which matches the documented condition and does not constitute a fault.

3. Treating the display configuration returned by an interactive node as the complete runtime state. The input is the returned interactive content. The comparison object is the documented statement that only type and params are returned. The observable result is the absence of fields such as entryNodeIds, which matches the documentation and does not indicate a runtime anomaly.

## How to verify the setup

1. Enter the stock list text and the approval record text from the hypothetical exercise sample. Compare the values of the same SKU, the same batch and the same discount field. The observable result is that the approval status field reads pending review while the draft sentence claims approval; the two are inconsistent and the draft sentence is judged unsupported.

2. Enter a request with detail=true and stream=false. Compare whether the returned structure contains module status and complete results inside responseData. The observable result is that responseData is present and contains module information, while the tokens values in usage require manual calculation and are not treated as an actual consumption figure returned by the interface.

3. Enter a request made in test mode. Compare whether chatId and responseChatItemId appear. The observable result is that neither is present, which matches the documented condition and is not judged a business fault.

Across all three checks, the same subject, the same period and the same field must be compared. Only mutually exclusive values in the same field constitute a contradiction. Where a value is not stated, or where only evidence from a related stage exists, the result remains unsupported or pending verification. Pending review does not demonstrate the absence of operating authority. Missing evidence stays missing, and no approval, execution or downstream business action is claimed to have occurred.
