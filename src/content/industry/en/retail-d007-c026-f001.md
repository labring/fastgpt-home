# Brand-owned store operations: HTTP integrations for operating reviews

## What the documents look like

Brand-owned stores are staffed and accounted for directly by the brand rather than governed through a franchise contract. The working materials for operating reviews are the daily sales report, the shift schedule, display photographs, and the inventory transfer order. These are refreshed daily or weekly, and they are reconciled against external systems: POS sales data, member CRM, ERP inventory, and store inspection records. HTTP integrations carry the requests that push data to those external systems or pull data back, so the correctness of the request configuration determines whether the review rests on figures that match the store's actual state.

The primary task on this page is operating reporting and exception review. The HTTP request is the transport step; it does not itself approve a transfer, write to a database, or grant permission to act. A successful call means the request reached its destination and returned a response, nothing more.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a configured address. Params carry path request parameters and are used mostly with GET requests. Body carries the request body and is used mostly with POST and PUT requests. Headers carry request headers. All three can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and upstream node outputs.

System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. The chatId and responseChatItemId values do not exist in test mode. Reading an empty value for these two during debugging is a documented behavior of test mode, not a business fault.

Return values configure parsing rules rather than the interface's own response. A JSON path extracts the needed field from the response, and when the output type is set to string, the corresponding value is converted into a json string. A configured key that does not correspond to the actual response structure extracts nothing, and the mismatch has to be checked item by item.

Hypothetical drill sample. A regional manager for a brand-owned store receives a daily sales report. The material text reads: "Store number A-017, report date 10 March 2026, daily sales 48,200 yuan, customer visits 312, transfer order number DB-20260310-04, transfer status is pending regional approval." A draft sentence under review reads: "The sales exception at store A-017 on 10 March has been confirmed, and the transfer order has been approved for execution." The comparison points are these: the draft's "has been confirmed" does not match any confirmation conclusion in the material, and "has been approved for execution" does not match the material's stated status of pending regional approval. The material carries no approval record, so the draft sentence is unsupported and the evidence gap stays open.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this drill | Comparison method |
| --- | --- | --- |
| Request address | The address given in the external system's documentation, which may contain `{{}}` variables | Compare character by character against the external interface documentation |
| Request method | Selected according to the external interface documentation | Confirm the method matches the documentation |
| Headers authorization | Authorization injected through secure configuration | Check that credentials do not appear in public samples |
| Body structure | JSON constructed according to the external interface contract | Check field names and types |
| Variable references | References to global variables or upstream node outputs | Check each actual passed value item by item |
| Return value parsing | Fields extracted by JSON path | Check that keys correspond to the response structure |

The starting points above take the external interface documentation as their sole basis. Each item is compared against the address, method, field names, and response structure stated in that documentation. No default value is assumed for any row.

## Three common errors

1. Treating absent chatId and responseChatItemId in test mode as a business fault. Input: an HTTP request issued in test mode. Comparison: the availability of these system variables in test mode against their availability in normal mode. Observable result: both variables are empty in test mode, which is the documented behavior of that mode.

2. Treating a successful interface call as a completed business approval. Input: the drill sample, where the transfer order status is pending regional approval. Comparison: the draft sentence's "has been approved for execution" against the status stated in the material. Observable result: the two do not match; a pending status is not an approval.

3. Treating the return value parsing configuration as the interface's own return value. Input: the configured key and JSON path. Comparison: the actual response structure against the configured extraction path. Observable result: when the key does not correspond to the response structure, no value is extracted, and each item has to be checked.

## How to verify the setup

1. Input: the drill sample's material text and the draft sentence. Comparison: the draft's "has been confirmed" and "has been approved for execution" against the material's stated status of pending regional approval. Observable result: the draft sentence is unsupported by the material, and the evidence gap is retained rather than filled by assumption.

2. Input: an HTTP request issued in test mode. Comparison: the availability of chatId and responseChatItemId. Observable result: both are empty, which matches the documented behavior of test mode and is not treated as a fault.

3. Input: the configured return value key and JSON path. Comparison: the actual response structure against the configured path. Observable result: when the path corresponds to the response structure a value is extracted; when it does not, the extraction is empty and the configuration needs correction after checking.

These checks concern the request configuration and the review of draft language against source material. They do not confirm that any transfer was approved, that any database was written, or that any external system was synchronized. Those actions require their own downstream implementation and authorization, which this page does not supply.
