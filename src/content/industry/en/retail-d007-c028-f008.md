# Brand livestream operations: workflow routing for operating reviews

## What the documents look like

Brand self-operated livestream rooms differ from influencer-hosted sessions because the brand carries the script, inventory, and after-sales obligations, and does not rely mainly on influencer commission. The working documents for this category are the livestream script, the product explanation card, the shift schedule, and the livestream review. Operating reports and exception reviews need to link these materials into a traceable chain: which session, which product, who explained it during which time window, and what was promised at that moment.

The main data sources are the Douyin Shop Compass, Juliang Qianchuan, livestream comments, and transaction details. The stated update frequency is per session or hourly. That frequency is why review materials are archived by session, and why exception judgments are bounded by the same session, the same product, and the same field. A figure from one session does not settle a question about another session.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the required fields and submits, the node collects the submitted values and passes them to later nodes. The User Selection node is also a user interaction node. When the user makes a choice, the node evaluates that choice and executes the corresponding branch. The interaction state is the behavior of the interaction node itself; no separate global state-recording switch is documented. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval and form collection do not constitute authorization.

Hypothetical paper exercise sample. The source material reads: "On 10 May 2024, from 20:00 to 22:00, host A explained product A in the brand self-operated livestream room. The product explanation card states 'final price 199 yuan, stock 300 units.' The shift schedule records that during this window, floor controller B was responsible for inventory verification. The first draft of the livestream review states 'product A recorded 280 completed transactions this session.'" The draft sentence to be assessed is: "Inventory verification for product A this session is complete, and the remaining 20 units have been written back to the system." The judgment must use the same subject, the same period, and the same field. The shift schedule states only that floor controller B was responsible for verification; it does not state that verification was completed. The review draft states only 280 transactions; it does not state that any inventory was written back. The draft sentence is unsupported, and inventory write-back is a business action that requires a separate system connection.

## Configuration and implementation checks

| Configuration item | Setting or check on this page | Basis and boundary |
| --- | --- | --- |
| Form Input node | Collect session, product, time window, and promised wording | Submitted values pass to later nodes |
| User Selection node | Route exception items through the "yes" branch for further checking | The corresponding branch executes after the choice |
| Interaction state check | Confirm item by item that the node enters interaction and records state | Documented behavior of the interaction node itself |
| Output handoff check | Compare collected values against later node inputs | Values must be passed explicitly |
| External action split | Inventory write-back and order writes connect to separate interfaces | These do not complete automatically with the form |
| Hypothetical trial starting point | This sample compares 280 transactions against 300 units of stock | This figure is the starting point for this exercise, not an official default |

## Three common errors

1. Treating form submission as completed inventory verification. The form only collects values; verification completion requires human confirmation or a later process. The input is the draft sentence, the comparison object is the responsibility recorded in the shift schedule, and the observable result is that the draft claims completion while the materials do not record it, so the claim is unsupported.

2. Treating execution of a User Selection branch as approval. The choice only determines the flow direction. The input is the selection result, the comparison object is the authorization boundary, and the observable result is that no approval record is present, so the item remains pending verification.

3. Treating a retrieval hit as a permission filter. A similarity score does not exclude unrelated or unauthorized records. The input is the retrieval condition, the comparison object is the access scope, and the observable result is an inconsistent cross-model library identifier, so non-matching items are excluded first and the gap is recorded.

## How to verify the setup

1. Use the draft sentence above as input, compare the shift-schedule responsibility against the review-draft fields, and check whether neither material records verification completion or write-back. If both are absent, the claim is unsupported, and the condition is satisfied.

2. Use an empty-result paper input of [] to check the downstream design, and compare whether the downstream handles the empty value through an empty-value branch. If the downstream does not treat the empty value as confirmed, the condition is satisfied.

3. Compare the transaction count and the stock count for the same session, the same product, and the same field. A contradiction is found only when mutually exclusive values appear together; when only one side is recorded, the item is logged as pending verification, and the condition is satisfied.
