# Supermarket supplier accounts: database operations for operating reviews

## What the documents look like

Supermarket supplier settlement for entry usually involves purchase-and-sale or consignment payables, and a supplier does not necessarily maintain an on-site counter. Four source systems feed the review: ERP purchasing, the supplier portal, POS sales, and the finance system. These record the purchase contract, the delivery acceptance note, the rebate agreement, and the reconciliation statement. Updates arrive weekly or monthly, so documents for the same period are expected to corroborate one another.

For operating reports and exception review, the workable fields are the same across documents: subject, object, period, quantity or amount, and status. The database and operations step keeps business source data and the vector retrieval backend in separate roles. Each is checked against the actual deployment, and connection, error, and latency behavior is observed under the operator's own load. Within a retrieval store, data associated with the same vector model can be linked together; data across different vector models cannot be linked together. Identifiers are checked first, and non-matching records are excluded.

## Constraints at the database operations step

Business source data and the vector retrieval backend carry different responsibilities. `MONGODB_URI` points to the main business store. `PG_URL`, `OCEANBASE_URL`, `SEEKDB_URL`, `MILVUS_ADDRESS`, and `OPENGAUSS_URL` each correspond to an optional vector backend, and a configured value is not inferred from the variable name. `REDIS_URL` carries cache and streaming resume mirrors, and parameters such as `STREAM_RESUME_TTL_SECONDS` retain the conditions stated in the documentation. `DB_MAX_LINK` is automatically limited to the range 10 to 1000. Backup and recovery are verified separately: a successful backup generation does not mean a usable restore. A checkable sample and its record are kept. After a database or service configuration change, the same business sample is used for re-verification; process liveness alone is not sufficient.

Hypothetical drill sample: A supermarket and a supplier sign a purchase-and-sale procurement contract with a payment term of 30 days after acceptance. The delivery acceptance note states that on 5 March 2025, 200 units of item A were accepted at a unit price of 10. The March reconciliation statement shows a settled quantity of 180 units for item A, with the note "difference of 20 units pending return confirmation." A draft handover request reads: "The March difference for item A is 20 units; please have finance pay according to the reconciliation statement amount." Decision point: the acceptance quantity of 200 units and the reconciliation quantity of 180 units are mutually exclusive values of the same field, so a difference exists. The note "pending return confirmation" indicates that the return is not complete, and the payment request lacks the prior evidence of return confirmation. This sample is used only to check fields and status, and does not represent any real business action.

## Three common errors

1. Treating retrieval relevance as a permission or entity filter. A similarity setting does not exclude unrelated businesses or unauthorized records, and retrieval is not authorization. In the sample, the difference between the reconciliation statement and the acceptance note is checked field by field; a retrieval result does not directly determine payment.

2. Treating a pending review or pending return confirmation as completed. The sample note "difference of 20 units pending return confirmation" indicates the return is not complete, and the draft payment request lacks the prior evidence. It cannot be treated as authorized execution.

3. Checking only process liveness after a configuration change. After a database or service configuration change, the same business sample is used for re-verification. A running process does not demonstrate that data reads and writes and recovery are usable.

## How to verify the setup

- Verification one: Input the sample acceptance note text "on 5 March 2025, 200 units of item A were accepted at a unit price of 10" and the reconciliation statement text "settled quantity of 180 units for item A, note: difference of 20 units pending return confirmation." Compare the quantity in the same field: 200 and 180 are mutually exclusive values, so the difference holds; the note indicates the return is not complete. The condition is met when both fields share the same subject, the same period, the same field, and clearly mutually exclusive values.

- Verification two: Input the draft sentence "The March difference for item A is 20 units; please have finance pay according to the reconciliation statement amount." Compare this request with the sample status; the payment request does not attach return confirmation. The condition is met when the request is identified as pending verification and cannot be judged as authorized execution.

- Verification three: Input the paper input `[]` for empty-result handling and check whether the downstream design handles it as an empty result, without claiming that a fictional rule retrieval necessarily returns `[]`. Compare whether the downstream distinguishes empty input from input with results. The condition is met when the downstream has an explicit handling for empty input; actual observation is recorded within a retrieval scope to which access is held.

The verifications above are paper checks only, not actually executed, and do not constitute a basis for deployment, approval, or payment.
