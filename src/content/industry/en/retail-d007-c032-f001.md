# Retail checkout and loyalty: HTTP integrations for operating reviews

## What the documents look like

Operating review and exception review in retail checkout and loyalty work from four recurring records: promotional price tags, membership points rules, the daily checkout report, and exception refund slips. These records draw on the POS system, the membership CRM, the payment platform, and the price tag system. The brief gives a daily or per-shift update rhythm. This category centers on price and membership entitlement; it does not handle short-shelf-life stock, which distinguishes it from convenience-store fresh-food ordering. When something goes wrong, the consequences named in the brief are price complaints, cash shortfalls or overages, and membership entitlement disputes. For an HTTP integration page, that means the review object is three record types — price, points, and refund — and whether fields returned by an external system line up with those records item by item.

The HTTP module sends a request to a given address, in practice similar to Postman or ApiFox. Params carry path request parameters and are common in GET requests. Body is the request body and is common in POST/PUT requests. Headers carry special information. All three data areas, and the URL as well, can reference variables through `{{}}`. Variables come from global variables, system variables, and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories; chatId and responseChatItemId do not exist in test mode. Return value configuration describes how to parse the interface response, extracted through JSON path syntax; when the output type is set to string, the value is converted to a JSON string. The chat interface uses APIKey authentication, and when calling chat/completions it is recommended to pass body.appId in the request body; `Authorization: Bearer <apiKey>-<appId>` is also supported. Passed fields such as model and temperature have no effect and are determined by the orchestration. With detail=true, responseData is returned, containing module status and the complete result. The HTTP module can operate a database, call an external data source, run a web search, and send email.

## Constraints at the HTTP integrations step

The constraints that matter here are about what a request actually carries and what a returned value actually means, not about the general capability list. A review page must keep three record types separate, because a promotional price tag, a points rule, and a refund slip each have their own subject, object, stage, and date scope.

Hypothetical drill sample. The review material reads: "Promotional price tag P-0312 was submitted on 12 March 2025 at 09:00 by the CRM operator, status pending review; membership points rule M-0312 was submitted on 12 March 2025 at 09:10 by the CRM operator, status pending review; exception refund slip R-0312 was submitted on 12 March 2025 at 14:30 by the checkout supervisor, status pending review." The draft sentence awaiting judgment is: "The promotional price for P-0312 has been synchronized to the price tag system, and the refund for R-0312 has been reversed." The source text carries subject, object, and status. It does not state that review was completed, that synchronization ran, or that a reversal was executed. A pending request is not an approval, an offered option is not an execution, and an unsigned termination is not a completed termination.

A second constraint concerns identity fields during debugging. chatId and responseChatItemId do not exist in test mode, so their absence in a test run is expected behavior and must not be recorded as a business fault. A third constraint concerns authorization. Retrieval is not authorization. A relevance score is not a category, entity, or permission filter, and a similarity setting does not exclude unrelated businesses or unauthorized records. Forms collect values; business verification, approval, database writes, and external synchronization need their stated downstream implementation. Where the source document does not describe a downstream implementation, that field remains unknown.

A fourth constraint concerns returned fields. The return value configuration extracts values from the interface response through JSON path; it does not create values that the response does not contain. If a review needs a field such as an approval status or a synchronization timestamp, and the response does not carry it, the field is missing evidence, not a negative result.

## Three common errors

1. Treating a pending-review status as completed review. Input: the sample source text "status pending review." Comparison: the draft sentence "has been synchronized." Observable result: the status field and the draft sentence do not agree, so the draft sentence is unsupported. The source does not state that synchronization ran, and no document field supplies a synchronization timestamp.

2. Treating a retrieval result or a submitted form as authorized execution. Input: field values collected by a form. Comparison: the downstream implementation for business verification, approval, database write, and external synchronization. Observable result: the presence of form values does not show that authorization completed. The document does not describe those downstream steps for this sample, so the authorization state remains unknown.

3. Treating a similarity score as a permission or entity filter. Input: a score in the returned value. Comparison: the business permission boundary. Observable result: the score does not exclude unrelated businesses or unauthorized records. Retrieval is not authorization, and a relevance score is not a category, entity, or permission filter.

## How to verify the setup

1. Input: the sample source text "Promotional price tag P-0312 was submitted on 12 March 2025 at 09:00 by the CRM operator, status pending review." Compare: the draft sentence "The promotional price for P-0312 has been synchronized to the price tag system." Observable result: when the status field reads pending review, the draft sentence is unsupported. The expected observation is that the status field and the draft claim do not agree; this is a paper comparison, not a completed test.

2. Input: the sample source text "Exception refund slip R-0312 was submitted on 12 March 2025 at 14:30 by the checkout supervisor, status pending review." Compare: the draft sentence "the refund for R-0312 has been reversed." Observable result: when the status field reads pending review, the draft sentence is unsupported. The source does not state that a reversal was executed, and no document field supplies a reversal record.

3. Input: a pending request to "write the review results for P-0312 and R-0312 into the external system." Compare: the authorization status field against the write action. Observable result: when review is not complete, the write action lacks an authorization basis, and the evidence gap is recorded rather than resolved. This remains an unanswered case in the supplied material.

For the points rule M-0312, the same pattern applies: the source states a submission time and a pending-review status, and the material does not state that points were applied, adjusted, or synchronized. Any draft sentence asserting a completed points action is unsupported on the same comparison. Where the response example does not contain an approval or synchronization field, that field stays unknown; the correct action is to record the gap, not to infer a negative result.
