# Retail checkout and loyalty: workflow routing for operating reviews

## What the documents look like

Retail checkout and loyalty work in this category turns on four document families: promotional price tags, membership points rules, the daily checkout report, and the abnormal refund form. These materials describe prices and member benefits. They do not cover short-shelf-life inventory. The source systems named in the brief are the POS system, the membership CRM, the payment platform, and the price tag system. Updates arrive daily and per shift, so reconciliation and review naturally take a shift or a calendar day as their scope.

For workflow routing, the shape of the material decides how nodes divide the work. Promotional price tags and membership points rules read as rule text. Daily checkout reports and abnormal refund forms read as structured records. The form input node collects required fields for a reconciliation. The user selection node obtains a decision at a branch. Both are interaction nodes: triggering either one puts the conversation into an interaction state and records the workflow state, and execution continues after the user finishes interacting.

## Constraints at the workflow routing step

An interaction node enters the interaction state when triggered, collects required information, and passes it to later nodes. The user selection node runs the corresponding "yes" branch after the user makes a choice. Retrieval recall does not carry authorization judgment, and a similarity score is not a permission or entity filter. Libraries built on different vector models cannot be associated together; the identifiers must be checked first and non-matching libraries excluded. Cross-model retrieval is not run to compare missed recalls.

The following is a hypothetical drill sample used only to illustrate the reconciliation method. It does not point to any real entity or system record.

Material text one (hypothetical promotional price tag record): "Store A, shift of 10 March 2025, item X promotional price 9.9 yuan, effective range 10 March to 12 March."

Material text two (hypothetical daily checkout report record): "Store A, shift of 10 March 2025, item X settlement price 9.9 yuan, 12 transactions completed."

Draft sentence to be judged: "Store A applied the promotional price to item X during the shift of 10 March 2025, consistent with the price tag record."

The sample carries a subject (Store A), an object (item X), a period (the shift of 10 March 2025), and fields (settlement price and promotional price). A judgment requires the same subject, the same period, and the same field. The two materials agree on the settlement price and promotional price, so the draft sentence is supported. If the daily report is missing, or the price tag does not state an effective range, the result is unsupported or pending verification.

## Configuration and implementation checks

Configuration here follows the reconciliation chain in the sample. It lists only interaction behavior already described in the official material, or implementation checks.

## Three common errors

1. Treating a similarity score from a retrieval hit as a permission or entity filter. The input is a retrieval request for item X; the comparison object is the returned result against the authorized scope; the observable result is whether the returned content contains records of unauthorized stores. A similarity score reflects text relevance only and does not carry authorization judgment.

2. Treating values collected by a form as already verified business facts. The input is the store and shift fields submitted through the form; the comparison object is the submitted values against the daily report text; the observable result is whether the two share the same subject, period, and field. A form collects values only, and business verification requires a separate downstream implementation.

3. Extending an interaction node's state record into a guarantee of a global snapshot. The input is one trigger of the form input node; the comparison object is the behavior described in the node documentation against actual observation; the observable result is whether any automatic judgment or submission count limit appears that the documentation does not describe. The documentation states only that state is recorded and execution continues.

## How to verify the setup

- Check one: Input hypothetical material text one and material text two; compare the two materials on item X, the shift of 10 March 2025, and the settlement price and promotional price fields. The observable result is that the draft sentence is supported when the two agree. If the daily report is missing, record the result as unsupported.

- Check two: Input an explicit paper empty result []; compare whether the downstream node design accepts an empty result. The observable result is whether the downstream handles it in a way consistent with empty input. No claim is made that a fictional rule retrieval necessarily returns [].

- Check three: Input one cross-library association request; compare the vector model identifiers of each library. The observable result is that non-matching libraries are excluded and the actual observation is recorded when identifiers differ. Cross-model retrieval is not run to compare missed recalls.

These verification items are paper reconciliation designs. They were not executed and do not constitute a claim that deployment, approval, or any business action has occurred.
