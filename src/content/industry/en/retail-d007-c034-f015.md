# Export tax rebate filings: retrieval for operating reviews

## What the documents look like

Export tax rebate filing happens after goods leave the country, and the work is tax-voucher matching rather than customs declaration. The operating review for this category draws on the electronic tax bureau, the export tax rebate filing system, customs electronic messages and the financial ledger. The documents handled day to day are the export tax exemption and rebate filing form, the export customs declaration, purchase invoices and foreign exchange receipt vouchers. Materials update monthly and per batch, so a filing batch is the natural scope for retrieval.

For an operating review or an exception retrospective, the reviewer aligns the subject, the period and the field values of one filing batch, then retrieves prior treatment positions and handling records from the knowledge base. The retrieval step returns reference content; it does not confirm that a batch is eligible, that a voucher matches, or that a filing may proceed.

## Constraints at the retrieval step

The knowledge base search node can associate one or more knowledge bases that use the same vector model. Bases built on different vector models cannot be associated together. At this step the operator checks the model identifier, excludes bases that do not match, and records what was observed. A cross-model retrieval is not run in order to compare missed recalls.

Reference content is output as an array and its length can be 0. When nothing is retrieved, the output path still runs. Search modes are semantic retrieval, full-text retrieval and hybrid retrieval, and they suit different material types. The reference cap is measured in tokens. The minimum relevance value takes effect only under semantic retrieval or when result reranking is used. Question optimization performs coreference resolution and question expansion and adds an extra model call. RRF is the fusion step applied to hybrid retrieval results. Image retrieval requires image input and the corresponding model capability. Reranking requires the model and must be enabled according to configuration. Retrieval and similarity scores do not carry permission or entity isolation.

Hypothetical paper exercise sample: a finance staff member at a foreign trade enterprise is reviewing the second batch of March 2025 filings. The materials on hand are an export customs declaration (domestic consignor Company A, declaration date 2025-03-12, item number 2, commodity code 8544422900) and the corresponding purchase invoice (buyer Company A, invoice date 2025-03-10, goods name identical to the declaration). The draft sentence under review is: "Company A's item 2 on this batch's customs declaration has been matched to the purchase invoice and the rebate may be filed." The pending request is: "Retrieve the knowledge base for this batch's exception handling position." The sample does not state the status of the foreign exchange receipt voucher or the filing form; those two items are evidence gaps.

## Configuration and implementation checks

| Configuration or check item | Value or practice in this page's sample | Reason and comparison object |
| --- | --- | --- |
| Associated knowledge base | Associate only one rebate material base using the same vector model | Check the vector model identifier first and exclude bases on a different model |
| Search mode | Run one trial query with hybrid retrieval first | Compare with semantic and full-text results to see whether identifier-type queries hit |
| Reference cap | This hypothetical trial starting point is 2000 tokens | A trial starting point only; compare with smaller and larger values for content completeness |
| Minimum relevance | This hypothetical trial starting point is 0.3 | Label relevant and irrelevant samples first, then compare with adjacent values |
| Question optimization | Enable for short questions such as "this batch's exception handling position" | Compare the original and optimized question and check whether the subject was altered |
| Reference content check | Manually compare subject, period and field values item by item | Retrieval results do not carry authorization judgment and require manual checking |

## Three common errors

1. Forcibly associating bases on different vector models. The input is two bases whose model identifiers differ; the comparison object is the node requirement of the same vector model; the observable result is that a mismatched identifier means the base is excluded and no cross-model retrieval is run.
2. Treating minimum relevance as a permission or entity filter. The input is a candidate set containing unrelated enterprise names; the comparison object is the relevance threshold; the observable result is that the threshold affects relevance filtering only and does not exclude records of unrelated enterprises.
3. Treating a retrieval hit as filing authorization. The input is the draft sentence "the rebate may be filed"; the comparison object is the foreign exchange receipt voucher and filing form status that the sample does not state; the observable result is that the sentence is unsupported and remains pending verification.

## How to verify the setup

1. Input the declaration and purchase invoice text from the hypothetical sample, compare subject, period and commodity code, and observe that when all three agree, the "has been matched" part of the draft sentence is supported; the foreign exchange and filing form status remain gaps.
2. Input "this batch's exception handling position" with question optimization enabled, compare the original and optimized question, and observe that the optimized question retains the subject information of Company A and the second batch of March 2025 without altering the subject.
3. Input the explicit paper input [] and compare the downstream design; observe that the output path runs and the reference length is 0, without claiming that a retrieval for a fictional rule necessarily returns [].
