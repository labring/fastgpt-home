# Trade returns and claims: database operations for operating reviews

## What the documents look like

Trade returns and claims handle reverse logistics and liability determination after goods have been exported. This differs from ordinary export declaration work, which moves goods outward and closes at the border. Here the material set is assembled after the outbound stage: customer email, quality inspection reports, customs system records, and insurer claim systems. The documents that operations staff actually handle are the return agreement, the claim letter, the quality report, and the return customs declaration form. Each case updates on its own schedule, and the public brief does not describe batch synchronization or real-time triggers, so this page treats per-case handling as the working assumption and does not add a synchronization mechanism.

For operating reports and anomaly review, these documents matter through their retention state and retrieval reachability in the database. Three steps consume the most time: confirming the reason for return, filing the return declaration, and submitting claim evidence. Material status spans email, reports, and system records, so a report line can only reflect what was stored and what a query returned. The operational side therefore has to keep two responsibilities apart. Business source data lives in its own store, and vector retrieval runs against a separate backend. Which service is in use follows the actual deployment, not the name of a variable.

## Constraints at the database operations step

Retrieval results reflect text similarity. They do not carry permission isolation or entity isolation, and a relevance score is not a category filter, entity filter, or authorization filter. A similarity setting does not exclude unrelated businesses or unauthorized records. Retrieval is also not authorization: a returned document is evidence that a query matched, not evidence that a signature, submission, or approval occurred.

Libraries that use the same vector model can be associated together. Libraries using different vector models cannot be associated, and the correct step is to check the model identifier and exclude the non-matching library rather than running a cross-model retrieval to compare recall. Forms collect values. Business verification, approval, database writes, and external synchronization need their own downstream implementation, and this page does not assume scheduled triggers or hidden controls.

Hypothetical paper exercise sample. A customs clerk submits a draft return agreement on 10 March 2026, covering one batch of goods returned after export because of surface defects. The agreement status is awaiting signature by both parties, and its effective scope is limited to that batch. The source wording supplied for comparison reads: "Party A agrees to accept the returned goods; this takes effect upon signature." and "The claim letter and quality report are attached and submitted together with the return customs declaration form." The draft sentence to be judged reads: "The return agreement has been signed, the claim letter has been submitted at the same time, and this case is handled as a completed return." That sentence conflicts with the source status. It is unsupported, and the exercise does not claim any test was run.

## Three common errors

1. Treating a return agreement awaiting signature as signed. Input: the sample wording "this takes effect upon signature." Compare the agreement status field against "awaiting signature by both parties." The observable result is that the status is unchanged, and no signed conclusion follows.
2. Treating a retrieval hit as authorization or as business execution. Input: the sample draft sentence. Compare the retrieval return against the signature and submission actions. The observable result is that retrieval produces neither signature nor submission, and those business actions require a separate system implementation.
3. Associating libraries across different vector models. Input: two library identifiers with different vector models. Compare the model identifiers. The observable result is that the non-matching library is excluded, and no cross-model retrieval is run.

## How to verify the setup

1. Input the sample source wording and the draft sentence. Compare "awaiting signature by both parties" against "has been signed." Observe whether the draft sentence is judged unsupported. The expectation is unsupported; this is not a claim that a test was performed.
2. Input the attachment wording in the sample. Compare "submitted together with the return customs declaration form" against "has been submitted at the same time." Observe whether a planned attachment is treated as a completed submission. The expectation is pending verification; this is not a claim that a test was performed.
3. Input the model identifiers of the two libraries. Compare whether they use the same model. Observe whether the non-matching one is excluded and the gap recorded. The expectation is exclusion with a recorded gap; this is not a claim that a test was performed. An empty result can be checked against the downstream design using the paper input `[]`, without asserting that a fictional rule retrieval always returns `[]`.
