# Multi-warehouse inventory: HTTP integrations for operating reviews

## What the documents look like

Multi-warehouse allocation happens at the order routing stage and decides which warehouse ships an order. The working documents for operating reviews and exception replay are allocation rules, inventory synchronization sheets, transfer orders, and stockout alerts. These records come from WMS, OMS, ERP inventory, and platform inventory interfaces, and they update daily or hourly. A review compares allocation rules, synchronization sheets, transfer orders, and stockout alerts on one shared time basis.

The HTTP module sends a request to a configured address. Params carry path parameters, Body carries the request body, and Headers carry request headers. All three can reference variables through `{{}}`, and variables come from global variables, system variables, and upstream node outputs. System variables include appId, chatId, responseChatItemId, and variables. In test mode, chatId and responseChatItemId do not exist, so a debug run that cannot read them is a documented condition rather than a business fault.

## Constraints at the HTTP integrations step

A configured return value does not represent the interface response itself. It describes how to parse the response, using JSON path extraction. When the output type is set to string, the value at the corresponding key is converted into a JSON string. The chat completions interface uses APIKey authentication, and a request body carrying `body.appId` is recommended. The form `Authorization: Bearer <apiKey>-<appId>` is also supported. The appId priority order is `body.appId`, then `<apiKey>-<appId>`, then the appId associated with the API key under the older adaptation. A passed `model` or `temperature` field has no effect because the orchestration decides those values. With `detail=true`, intermediate values are returned, and in stream mode the event field distinguishes them. An interactive node returns only `type` and `params`; internal runtime fields such as `entryNodeIds`, `memoryEdges`, `nodeOutputs`, and `nodeResponseId` are not returned. Retrieval and similarity do not perform permission filtering, and a node run does not grant business authorization.

Hypothetical paper exercise: a supply planning group intends to use the HTTP module to push an A-warehouse stockout alert dated 10 March 2025 to an external ticket system. The material text supplied for checking reads: "Alert number W-0310-A, subject A warehouse, object SKU-1001, status pending review, available stock field value 0, statistical period 2025-03-10 00:00 to 2025-03-10 23:59." The proposed copy sentence under review reads: "A warehouse SKU-1001 is out of stock; replenish immediately." The request currently sits at pending review and has not received transfer execution authorization.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison method |
| --- | --- | --- |
| Request address | External ticket system interface address, referenced through a variable | Chosen from the external interface document; compare character by character against the address declared there |
| Request method | POST | Compare against the write method declared in the external interface contract |
| Headers | Authorization header injected by security configuration | Compare against the authentication specification; no credential is written into a public sample |
| Body structure | Contains alert number, subject, object, and status fields | Compare field by field against the material text and confirm nothing is added or removed |
| Return value key | JSON path configured against the response structure | Compare against the response example and confirm the extraction path exists |
| detail parameter | Set to true for this exercise | Used to obtain intermediate values; compare together with the stream setting |

## Three common errors

1. Treating a pending-review status as approved execution. The input is the status field from the material text, the comparison is between "pending review" and "approved," and when the two do not match, the proposed sentence is judged to exceed the authorization boundary.
2. Treating a missing chatId in test mode as a business fault. The input is a test-mode request, the comparison checks whether chatId is empty, and an empty value is recorded as a documented condition rather than entered into the exception review.
3. Treating the return value configuration as the interface response. The input is a configured JSON path, the comparison is between the actual response structure and the extraction result, and a path that does not exist is recorded as a parsing configuration issue without inferring an error in the external system data.

## How to verify the setup

1. Input the hypothetical material text and the proposed sentence, compare the status field "pending review" with the sentence "A warehouse SKU-1001 is out of stock; replenish immediately," and when the status field does not state approval, record the result as unauthorized and keep the evidence gap open.
2. Input the alert number, subject, and object fields from the request Body, compare them against the corresponding fields in the material text, and when they match field by field the checking condition is met; when a field is missing, record it as pending verification.
3. Input the returned response and the configured JSON path, compare the extraction result with the actual response structure, and when the path exists and the value can be extracted the condition is met; when the path does not exist, record the parsing configuration as needing adjustment.
