# Fresh-food concession counters: HTTP integrations for operating reviews

## What the documents look like

Fresh-food concession counters in hypermarkets are frequently staffed by suppliers who sell on site and share revenue with the store. That arrangement produces a specific document set: the concession contract, the daily sales report, the loss sheet, and the food purchase inspection record. POS weighed sales and supplier delivery notes sit in separate record systems, so reconciliation requires placing sales, deliveries, losses and inspection evidence side by side under the same operating entity, the same period and the same field. The daily sales report and loss sheet update daily or per batch.

The HTTP module performs the action of fetching data from or sending data to an external system at this step. The request address and method are chosen according to the external interface documentation, and the address can reference variables through `{{}}`.

## Constraints at the HTTP integrations step

The HTTP module can be added repeatedly, configured manually and triggered to execute. Params are path request parameters, used mostly in GET requests. Body is the request body, used mostly in POST/PUT requests. Headers carry special information. All three can reference variables with `{{key}}`, and the URL can do the same. Variables come from global variables, system variables and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime and histories, where histories takes at most 10 entries by default and its length cannot be modified. chatId and responseChatItemId do not exist in test mode; retrieving empty values during debugging is a test-mode characteristic and does not constitute a business fault. Return values are extracted with JSON path syntax, and when the output type is set to string the value of the corresponding key is converted into a json string.

Hypothetical paper exercise sample: the daily sales report text for a concession supplier counter reads "On 10 March 2025, supplier A sold 1200 yuan at the fresh-food concession counter of store B, with a loss of 30 yuan, and the purchase inspection record for the day has been registered." The proposed handover request reads "Push supplier A's sales of 1200 yuan and loss of 30 yuan for 10 March 2025 to the external reconciliation system." This request involves an entity, an object, a period and amounts, but it does not state push authorization, the target system's field contract or an effective confirmation, so it remains in a to-be-verified state.

## Configuration and implementation checks

| Configuration item | Assumed trial starting point for this page | Reason for the choice and comparison method |
| --- | --- | --- |
| Request address | The reconciliation interface address provided by the external reconciliation system | Chosen according to the external interface documentation, compared character by character with the path given in the documentation |
| Request method | POST | The request carries structured data, compared with the documentation statement that Body is used mostly in POST/PUT requests |
| Headers authentication | `Authorization: Bearer {{token}}` | Variable introduced according to the documentation example; check whether the credential is injected by security configuration |
| Body structure | `{"date":"{{date}}","supplier":"{{supplier}}","sales":{{sales}},"loss":{{loss}}}` | Compared with the documentation Body example: strings take quotation marks, numbers do not |
| Output extraction | `$.data.result` | Compared with the documentation JSON path extraction example for the return structure |
| Output type | String | According to the automatic formatting description, the extracted value is converted into a json string |

## Three common errors

1. Treating the absence of chatId and responseChatItemId in test mode as a business fault. Check: input a test-mode request, compare whether these two fields are missing from the return; their absence matches the documented test-mode characteristic.
2. Omitting quotation marks when referencing a string variable in the Body. Check: input a Body containing `{{supplier}}`, compare whether the parsed field remains a string; a missing pair of quotation marks produces a structural parsing anomaly.
3. Treating retrieval or form submission as authorized execution. Check: input the proposed handover request above, compare whether it carries push authorization and the target system field contract; when these are not stated, record the state as to be verified rather than as authorized.

## How to verify the setup

1. Input the daily sales report text from the hypothetical sample and the proposed request, then compare whether the four Body fields date, supplier, sales and loss match the values in the source text. Agreement satisfies the condition.
2. Input a test-mode request and compare whether chatId and responseChatItemId are missing from the return. Their absence matches the documentation and is not recorded as a fault.
3. Input a Body declaration containing a string variable and compare whether the parsed field keeps the string type. Keeping the string type satisfies the condition; when parsing is anomalous, record the actual observation without inferring a specific error code.
