# Customer-service knowledge: tool calls for operating reviews

## What the documents look like

Customer-service knowledge base maintenance works from FAQ entries, script templates, product parameter tables and escalation tickets. These materials are prepared ahead of customer conversations and do not approve refunds or returns. An operating review for this category asks whether, within a stated week or month, the tool-call step selected the intended tool when generating an answer, whether tool results were passed to the AI for summarization, and whether the termination node ended the call as designed. Source material comes from the customer-service system, product detail pages, after-sales issue statistics and quality-check sampling. When this goes wrong, answers miss the question, complaints escalate and agent training fails. Tool calling lets the model decide from context whether to invoke a tool, and the tool introduction, parameter introductions and required flags together shape that decision.

## Constraints at the tool calls step

A tool introduction tells the model what the tool does and needs to state the input conditions and the situations where the tool should not be called. System-module parameters are already fixed; plugin parameters are configurable. Two values matter inside a parameter: the parameter introduction and whether it is required. A tool with no parameters is judged from its introduction alone. A tool with parameters but no required ones can still be called when no suitable parameter appears in context, and the model sometimes fabricates a parameter. A tool with required parameters may not be called when no suitable value is present, and prompts can guide the user to supply one. In advanced orchestration, available tools are connected to the tool-call module; a connected tool separates its inputs from ordinary inputs and its introduction becomes editable. The documentation advises against adding many tools at once and recommends tuning a small set before expanding. The tool-call termination node forcibly ends the current call, so no further tools run and the AI does not answer from the tool result. Custom variables extend tool variable inputs so that nodes not treated as tool parameters, or nodes that cannot be tool-called, can be invoked with their downstream workflow.

Hypothetical exercise sample: the material to be checked reads: "In the week-2 customer-service knowledge base maintenance report for March 2025, the FAQ entry 'Return address entry' script template was submitted for update by the knowledge base operator, with status Pending review; in the escalation tickets, one inquiry dated 10 March is marked 'Transferred to product operations'." A draft sentence awaiting judgment reads: "The script template update has taken effect, and the tool call should select the return-address lookup plugin." A separate handover request reads: "Mark every ticket in that week's tool-call report that is 'Transferred to product operations' as resolved."

## Three common errors

1. Treating pending review as effective. The sample source says "status Pending review" and the draft says "has taken effect". Same subject, same period, same field, mutually exclusive values, so this is a contradiction. Record it as unverified and do not write it as a completed update.
2. Treating "Transferred to product operations" as resolved. The handover request asks that every such ticket for that week be marked resolved, while the source records only the transfer action and no resolution status. Transfer and resolution are different facts; keep the gap open when resolution evidence is absent.
3. Treating retrieval or a form as authorized execution. The documents say tool calling lets the model decide whether to invoke a tool; a retrieval result and a form value do not constitute authorization. The bulk marking in the handover request needs a separate system implementation and cannot be completed by a tool call or retrieval.

## How to verify the setup

1. Against the sample source text "status Pending review", enter the draft sentence "the script template update has taken effect". Compare the values of the same field: the source says Pending review, the draft says effective. If the two values are mutually exclusive, judge the draft a contradiction and do not use it as a conclusion that the update took effect.
2. Against the sample text "one inquiry dated 10 March is marked 'Transferred to product operations'", enter the handover request "mark every such ticket as resolved". Compare the source status field with the requested target status: the source has a transfer record only and no resolution record. When resolution evidence is missing, record it as unverified and do not perform the bulk marking.
3. Against the tool-call termination node, enter the hypothetical run result of the return-address lookup plugin. Compare whether that result still enters AI summarization: if the termination node is connected and the tool result does not enter AI summarization, the behavior matches the documented termination; if the node is not connected, record what is observed and do not infer whether other tools were called. All of the above are paper comparisons and do not claim that testing or deployment took place.
