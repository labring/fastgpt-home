# Marketplace promotions: workflow routing for operating reviews

## What the documents look like

Marketplace promotion enrollment and price management centers on price, inventory, and campaign rhythm. Reviewing advertising wording belongs to a separate task. The main data sources named in the brief are the Tmall marketing backend, the JD campaign backend, ERP inventory, and historical transaction prices. Typical roles include platform campaign operations staff, brand sales planning staff, and finance business partners. The daily documents are the campaign enrollment form, the promotional price approval sheet, the inventory lock sheet, and the campaign review sheet. Documented error consequences include campaign loss, removal of a resource slot, and price complaints. The brief gives an update frequency of weekly and per campaign. This page does not derive batch synchronization, full synchronization, real-time triggering, or transaction-triggered mechanisms from that frequency.

For this page the task is operating reports and anomaly review, and the feature is workflow routing. The materials that matter at this step are the enrollment form, the promotional price approval sheet, the inventory lock sheet, and the campaign review sheet. What the routing step decides is which collected values move to which downstream node, and what remains an open evidence gap. The behavior of the interaction nodes is documented; the business actions that follow are not part of those nodes.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it is triggered, the conversation enters an interaction state and the workflow state is recorded. After the user fills the required information and submits, the node collects the submitted form information and passes it to later nodes. The user selection node is also a user interaction node. When it is triggered, the conversation enters an interaction state and the workflow state is recorded. When the user makes a choice, the node evaluates that choice and executes the "yes" branch. Recording state is behavior of the interaction nodes. No separate global state recording switch is declared in the supplied documents.

Information that is collected must be explicitly passed to a later retrieval, judgement, or interface node. Order writing, document write-back, and external status synchronization require a separately connected business interface or a later process. Retrieval and form collection do not constitute authorized execution. A pending approval status does not show that an operation permission is absent.

Hypothetical paper exercise sample: the source material reads, "Promotional price approval sheet number SP-2041, subject is a brand sales planning group, object is a certain insulated bottle, campaign period is 1 June 2025 to 18 June 2025, status field reads 'pending finance business partner review', approval opinion field is blank." The sentence proposed for judgement reads, "This promotional price approval sheet has been approved by the finance business partner and the campaign inventory may be locked." Checking compares subject, object, status, and effective scope. The status field is pending review and the approval opinion field is blank, so the proposed sentence is not supported. Inventory locking is a business action implemented by another system and does not complete automatically because a form was submitted.

## Configuration and implementation checks

| Configuration item | Type | Description |
| --- | --- | --- |
| Form input node | Documented node behavior | Triggering enters the interaction state, collects required information, and passes it to later nodes after submission |
| User selection node | Documented node behavior | After the user makes a choice, the "yes" branch executes; check each branch connection |
| Interaction state check | Manual check action | Check whether the interaction node records state; no separate global state recording switch is declared |
| Output handoff check | Manual check action | Compare each collected value against the input of the later retrieval, judgement, or interface node |
| External operation split | Requires separately connected system implementation | Order writing, document write-back, and external status synchronization connect to a business interface or later process |
| Hypothetical exercise starting value | Hypothetical value | This paper check uses the approval sheet status field value "pending finance business partner review" as the comparison starting point, compared against the value "approved", because the sample status field is filled that way |

## Three common errors

1. Treating form submission as completed approval. In the sample above, the status field reads "pending finance business partner review" and the approval opinion field is blank. The submission action only collects information and does not support the conclusion that approval was granted.
2. Treating the "yes" branch of the user selection node as business authorization. Branch execution shows only that the choice result entered that path. Inventory locking and price taking effect still require a separately connected system implementation.
3. Treating a retrieval result as a permission filter. Retrieval does not perform entity isolation, and a similarity setting does not exclude unrelated businesses or unauthorized records. The check compares record identifiers and access scope, and records the gap when either is missing.

## How to verify the setup

1. Input the sample source text above together with the proposed judgement sentence, and compare the approval sheet subject, object, status, and effective scope. When the status field reads "pending finance business partner review" and the approval opinion field is blank, the expected conclusion is that the sentence is not supported. The condition is met when the conclusion matches the source status.
2. Input the handoff request from the sample, "Please lock the campaign inventory for this insulated bottle," and compare the request against the recorded status. When the status is pending review, the expected output is pending verification and no locking is executed. The condition is met when the flow produces no inventory write action.
3. Input the paper empty result [] and check the downstream design, comparing the empty-result handoff path. The expected output is to record the gap and wait for manual supplementation. No claim is made that a fictional rule retrieval necessarily returns []. The condition is met when the downstream does not treat the empty result as approved or as excluded.

These checks observe inputs, comparisons, and observable results. They do not assert that any test, deployment, approval, refund, or other business action has occurred. Where a document field is not provided, it remains unknown.
