# Product listing reviews: HTTP integrations for operating reviews

## What the documents look like

Platform product listing compliance covers the truthfulness of promotional copy and the display of qualification materials. It does not cover parcel delivery. The working materials for this category are the product title table, detail page assets, the advertising prohibited-word list, and quality inspection reports. Operating reports and anomaly reviews consolidate the field states in these materials into records that can be checked against one another.

In the HTTP integrations step, the HTTP module sends a request to a given address. Params are path request parameters, Body is the request body, and Headers are request headers. All three can reference variables through {{}}. Variables come from global variables, system variables, and upstream node outputs. Upstream node outputs are the values produced by earlier nodes in the same workflow. The three most time-consuming checks in this category are whether promotional wording falls into the prohibited-word list, whether physical parameters match the detail page, and whether non-compliant assets have been replaced. These three checks determine whether an operating report can locate an anomaly at all.

## Constraints at the HTTP integrations step

The HTTP module can be added repeatedly, configured manually, and triggered to execute. Its system variables include appId, chatId, responseChatItemId, variables, and cTime. The chatId and responseChatItemId values do not exist in test mode. When calling chat/completions, the recommended practice is to pass body.appId in the request body; the alternative is Authorization: Bearer <apiKey>-<appId>. The model and temperature fields passed in are invalid, because these are determined by the orchestration and do not change with API parameters. With detail=true, responseData intermediate values are returned, and tokens can be calculated manually. Variables replace the [key] content inside input boxes.

A hypothetical paper exercise sample: a compliance operator prepares a set of materials for review. The source text reads: "Product A's title contains 'lowest price on the entire internet.' The third screen of the detail page assets cites quality inspection report number Q-2024-018. The advertising prohibited-word list version is the 2024-06 weekly update. The listing date is 2024-06-11. Quality inspection report Q-2024-018 states that the tested item is fiber content, with an issue date of 2024-05-20." The proposed handover request reads: "Please synchronize Product A's title and detail page assets to the external compliance ledger, and flag anomalies against the prohibited-word list."

This request states an intention to synchronize. It does not state an authorization subject, an authorized object, or an effective scope. The request cannot be treated as approval for a ledger write.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason for the choice and comparison object |
| --- | --- | --- |
| Request address and method | External compliance ledger endpoint, POST | Chosen per the external interface document; the address can reference a variable |
| Headers authentication | Authorization references the configured token variable | Compared item by item against the request headers the interface document requires |
| Body structure | JSON containing product identifier, title text, asset links | Checked field by field against the external interface contract |
| Variable reference | Title text and asset links taken from upstream node outputs | Compared against the actual output values of the node |
| Return value extraction | Extract the ledger record identifier by JSON path | Compared against the interface response structure |
| Debug identity field | chatId does not exist in test mode | Compared against the session identifier used in a formal call |

The starting values above are hypothetical for this exercise only. They are not official defaults and were not tested.

## Three common errors

1. Treating a value collected by retrieval or a form as an already-authorized execution. In the sample, the proposed handover request expresses only an intention to synchronize and states no authorization subject or effective scope. A ledger write cannot be concluded to be approved on that basis.
2. Treating the absence of chatId in test mode as a business fault. That field does not exist in test mode by design, and it must be distinguished from the session identifier used in a formal call.
3. Treating a similarity score as a permission or entity filter. The score and similarity values reflect only the degree of retrieval relevance. They do not exclude unauthorized records or unrelated business.

## How to verify the setup

1. Input the sample source text and the proposed handover request. Compare whether the request body contains the product identifier, title text, and asset links, and whether Headers references the token variable. The expected observation is that the request body fields correspond item by item to the sample materials, and that the authentication credential is not written into a public example. If a field is missing, record it as a gap rather than a pass.
2. Input quality inspection report number Q-2024-018 and issue date 2024-05-20 from the sample. Compare the number cited on the third screen of the detail page assets against the number in the report source text. The expected observation is that the numbers match and the issue date falls within the range the asset cites, or that a mismatch in the number is recorded as a gap.
3. Input the proposed handover request. Compare whether it states an authorization subject, an object, and an effective scope. The expected observation is that when the request states no authorization boundary, the ledger write remains pending verification and no conclusion of execution is produced.

These are paper comparisons only. No test, deployment, approval, or ledger write is claimed to have occurred.
