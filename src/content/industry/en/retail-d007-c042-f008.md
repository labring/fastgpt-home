# Product listing reviews: workflow routing for operating reviews

## What the documents look like

Platform product title and detail compliance covers the truthfulness of promotional wording and the display of qualification material. It does not cover parcel delivery, so the material set differs from platform shipping operations. The working documents are the product title table, detail page assets, the advertising prohibited-terms list, and quality inspection reports. Sources include the platform rules centre, advertising law compliance checklists, the brand asset library, and inspection body reports.

Updates arrive weekly and with each new listing. The most time-consuming steps are checking absolute claims, comparing physical parameters, and replacing non-compliant assets. For operating reports and exception review, the workflow must connect the status, version, and handover request of these materials into a traceable chain. Workflow routing collects information at interaction nodes, evaluates branches, and passes results to later steps.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. After the user fills required information and submits, the node collects the submitted values and passes them to later nodes. The user selection node is also a user interaction node with the same interaction state behaviour. When the user makes a selection, the node evaluates that selection and executes the "yes" branch. Branch connections require item-by-item verification.

The interaction state is behaviour of the node itself. No separate global state-recording switch is documented, and none should be assumed. Collected information must be explicitly passed to later retrieval, evaluation, or interface nodes, and outputs must be compared item by item against inputs. Order writes, document backfill, and external status synchronisation require a separate business interface or later process. Retrieval and form collection do not constitute authorised execution.

Hypothetical paper exercise sample: a product operations specialist submits a handover request. The material text reads: "Title table draft: product name A, version dated 10 March 2025, containing the wording 'lowest price on the entire internet'; item 4 of the advertising prohibited-terms list states that 'lowest' is a prohibited expression; inspection report number Q-0310, conclusion compliant." The draft sentence to be assessed is: "This title table has passed compliance review and may be published." The subject under review is product name A, the object is the title table draft, the status is draft, and the date scope is the 10 March 2025 version. The request is pending review and does not constitute approval or publication authorisation.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Reason and comparison method |
| --- | --- | --- |
| Form input node required fields | Product name, title table version, handover request number | Check whether submitted information passes completely to later nodes; a missing field means the interaction is incomplete |
| User selection node branch | "Yes" branch connected to the compliance evaluation node | Verify branch connections item by item; after selection only the corresponding branch executes |
| Output receiving objects | Retrieval node and evaluation node | Compare collected information against downstream inputs item by item |
| Prohibited-terms comparison | Title table text against list entries | A contradiction is found only when the same field carries explicitly mutually exclusive values |
| External operation division | Order writes, document backfill, external synchronisation | Mark as requiring a separate business interface; interaction nodes do not execute these automatically |
| Retrieval library identifier check | Vector model identifier | Libraries across different vector models cannot be associated together; check identifiers first and exclude non-matching ones |

## Three common errors

1. Treating form submission as compliance approval. Input is the pending handover request; the comparison object is the review status field; if the status remains pending review, the result must not be recorded as approved.

2. Treating the "yes" branch of the user selection node as authorised execution. Input is the user selection result; the comparison object is the downstream interface call record; if no separate business interface is connected, external synchronisation has not occurred.

3. Treating retrieval results as a permission filter. Input is the returned retrieval entries; the comparison object is the access rights scope; a relevance score does not perform entity or permission isolation, and authorisation must be checked separately.

## How to verify the setup

1. Input the title table draft and item 4 of the prohibited-terms list from the hypothetical sample. Compare whether "lowest price on the entire internet" and "lowest" carry explicitly mutually exclusive values in the same field. A finding of violation requires a clear contradiction; where the text is absent or only shows related-stage evidence, record the item as pending verification.

2. Input the draft sentence under assessment, "This title table has passed compliance review and may be published," and compare it against the review status field. When the status is pending review, the output should be unsupported; it must not output approved.

3. Input a paper-based empty result [] and check the downstream design. Observe whether the empty-result receiving branch handles it as designed. Do not claim that a fictional rule retrieval necessarily returns []. For cross-model libraries, check identifiers first and exclude non-matching ones, then record the actual observation.
