# Product listing reviews: database operations for operating reviews

## What the documents look like

Title and detail-page compliance for platform listings concerns the truthfulness of promotional wording, the display of qualifications, and the compliance of creative assets. It does not concern parcel delivery. The material set for this category comes from the platform rule center, advertising-law prohibited-term lists, the brand asset library, and inspection-agency reports. The working documents are the product title table, detail-page assets, the prohibited-term list, and inspection reports. Updates occur weekly and at each new listing.

For operating reports and anomaly review, these four document types must sit inside one review scope so that the same product, the same field, and the same period can be checked for consistent meaning. Errors in this category lead to listing removal, complaints, and administrative penalty risk, so a review must be able to trace back to the specific source text and the basis for a judgment.

A product title table carries a product identifier, a field name, a field value, and an update date. A prohibited-term list carries a term entry, a status, and an applicable scope. An inspection report carries the tested object and the reported result. These are different sources, and their field names and value conventions may not agree. Retrieval returns text relevance only; it is not authorization, not a compliance conclusion, and not a basis for removal. The primary business data store and the vector search backend have different responsibilities and are checked separately against the actual deployment. After a configuration change, the same business sample must be re-checked; a running process is not evidence of business availability. Backup generation and actual restore are verified separately, and a checkable sample is retained.

## Constraints at the database operations step

Database and operations work here stores and retrieves the four document types, supports sample retrieval by product identifier, field name, and period, and supports review comparison. Because the material comes from different sources, retrieved records must be checked by hand for subject, object, status, and effective scope. A similarity score is not a category filter, an entity filter, or a permission filter; it does not exclude unrelated businesses or unauthorized records. Retrieval is not authorization.

The following hypothetical drill sample is paper material, not a real record.

Source text one (product title table): product identifier A-001, field "title", value "lightweight breathable running shoes", update date 2025-03-10.

Source text two (prohibited-term list): entry "ultimate lightweight", status "prohibited", applicable scope "title and detail page".

Draft sentence to be judged: the title of product A-001 is proposed to become "ultimate lightweight breathable running shoes".

Handover request: review whether this draft sentence conflicts with the prohibited-term list, and state the current authorization status.

The source text does not record an authorization status for this draft. A pending review is not approval, and an offered option is not execution. The draft sentence is not an executed title change.

## Three common errors

1. Treating retrieval similarity as a compliance judgment or an authorization basis. The input is the source text and the draft sentence; the comparison object is the status and applicable scope of the prohibited-term list entry "ultimate lightweight"; the observable result is that retrieval returns related text, while the compliance conclusion still requires a manual check against the list. Retrieval itself does not produce a prohibition judgment.

2. Comparing values from a different product or a different field. The input is the title field of product A-001 and the detail field of another product; the comparison object is the same product and the same field; the observable result is that the field name or product identifier does not match. A contradiction conclusion is not available in that case, and the result is recorded as an unsupported comparison pending verification.

3. Judging a configuration change as normal only from process liveness. The input is the database connection configuration before and after the change; the comparison object is the retrieval result for the same business sample A-001; the observable result is whether the sample can be retrieved under the same identifier. Process liveness is not evidence of business availability.

## How to verify the setup

1. Input source text one and source text two, plus the draft sentence "ultimate lightweight breathable running shoes". Compare the phrase "ultimate lightweight" in the draft sentence with the prohibited-term list entry "ultimate lightweight". The observable result is that the two are literally identical and the list status is prohibited with an applicable scope that includes the title. Record this as a conflict pending manual judgment. Do not execute a removal or a title change.

2. Input the title field value "lightweight breathable running shoes" for product A-001 and the update date 2025-03-10. Compare the value of the same field for the same product before and after a change. The observable result is that a value change can be judged only when the field name and product identifier match. When the identifier or field does not match, record the result as unsupported.

3. Input the handover request "review whether this draft sentence conflicts with the prohibited-term list, and state the current authorization status". Compare the authorization status described in the request with the status actually recorded in the material. The observable result is that when the material does not record an authorization status, the result is recorded as pending verification. A pending review is not treated as authorized, and no replacement or submission action is executed.

Backup and restore are verified separately: confirm that a backup is generated, then confirm that an actual restore produces a checkable sample. After any database or service configuration change, re-check the same business sample; do not rely on process liveness alone.
