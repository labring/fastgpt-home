# Multi-store management: HTTP integrations for operating reviews

## What the documents look like

Platform multi-store matrix management works across several platform merchant backends, ERP channel prices, brand anti-counterfeit systems and distributor reports. Compared with single-store advertising, this category pays more attention to cross-store authorization and price order than to traffic efficiency in one store. The daily documents are store authorization lists, price control tables, diversion complaint tickets and monthly sales reports. Data updates on a daily and monthly basis. In the operating review and exception review step, these materials are aligned to judge whether a record sits inside a valid authorization state.

A hypothetical drill sample is used throughout this page. The source text is: "Store authorization list row 12: entity A authorizes store S to sell brand B products, valid range 2025-01-01 to 2025-06-30; price control table row 8: store S lists brand B products at the channel price; diversion complaint ticket item 3: the complained party is store S, complaint date 2025-04-10, status pending verification." The sentence to be judged is: "Store S was within the valid authorization range for brand B on 2025-04-10." This sentence must be compared item by item against the valid range in the authorization list. The complaint ticket status of pending verification does not constitute a denial of the authorization state.

## Constraints at the HTTP integrations step

The HTTP module sends an HTTP request to the corresponding address. Params are path request parameters, mostly used in GET requests. Body is the request body, mostly used in POST and PUT requests. Headers carry special information. All three data groups can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables and upstream node outputs. Return values are extracted through JSON path syntax, and the output type can be set to string so the value is formatted into a JSON string. The chat interface uses APIKey authentication, and when calling `chat/completions` it is recommended to pass `body.appId` in the request body. `chatId` and `responseChatItemId` do not exist in test mode, so an empty debug value does not represent a business fault. Fields such as `model` and `temperature` are determined by the orchestration and do not change with API parameters. The appId priority order is `body.appId`, then `<apiKey>-<appId>`, then the appId associated with the apikey in the legacy adaptation.

For operating reviews, the HTTP module can call an external data source or operate a database, but retrieval and form entry are not authorization execution. A store authorization list, a price control table and a diversion complaint ticket each carry their own subject, object, state and period. The judgment must stay on the same subject, the same period and the same field.

## Configuration and implementation checks

| Check item | Setting for this page's sample | Comparison method |
| --- | --- | --- |
| Request address | Selected from the external interface document; the address may reference a provided variable | Compare character by character against the address listed in the external interface document |
| Params and Headers | Path parameters and request headers are filled separately; the authorization credential is injected through secure configuration | Compare key names against the external interface contract |
| Body | Used only under the corresponding request type; the JSON structure is checked | Compare field by field against the external interface contract |
| Variable reference | References a global variable, a system variable or an upstream node output | Compare the actual passed value item by item against the variable source list |
| Return value extraction | Extracts the needed field by JSON path and selects string as the output type | Compare against the response example structure of the interface |
| Debug identity fields | `chatId` and `responseChatItemId` do not exist in test mode | Compare against the formal call record to separate a debug empty value from a business fault |

The request address, Params, Headers and Body are implementation checks named here, not documented default values. No default numeric value, limit or global switch is assumed.

## Three common errors

1. Treating a retrieval result or a filled form as authorization execution. The input is the authorization list record for store S in the sample. The comparison object is the authorization valid range. The observable result is whether the draft sentence falls inside 2025-01-01 to 2025-06-30. Retrieval and forms only collect values; the authorization state needs a separate check.
2. Treating a pending-verification complaint ticket as a completed finding. The input is the status "pending verification" in diversion complaint ticket item 3. The comparison object is the valid range in the authorization list. The observable result is that the complaint ticket states no conclusion about the authorization state. Pending verification does not show that authorization is missing.
3. Treating an empty `chatId` in test mode as a business fault. The input is a test-mode call record. The comparison object is the `chatId` in a formal call record. The observable result is that the field does not exist in test mode. This phenomenon is a documented debug condition.

## How to verify the setup

1. Input the authorization list source text for store S and the draft sentence. Compare the start and end dates of the authorization valid range. Observe whether the draft sentence date falls inside the range. The expectation is that the draft sentence is supported when the date falls inside the range, and not supported otherwise.
2. Input the status field of diversion complaint ticket item 3. Compare its value with the authorization state field. Observe whether the two point to the same subject, the same period and the same field. The expectation is that different fields do not form a contradiction, and the record stays pending verification.
3. Input one test-mode call record. Compare whether `chatId` and `responseChatItemId` exist in it. Observe that neither field exists in test mode. The expectation is that both fields exist in a formal call record and do not exist in the test record, which separates a debug condition from a business fault.
