# Marketplace advertising: HTTP integrations for operating reviews

## What the documents look like

Marketplace advertising adjusts prices against traffic and conversion in real time, and platform campaign review is not the controlling gate. The working materials for this category are delivery plans, keyword reports, audience package descriptions and conversion attribution tables. Data sources include Juliang Qianchuan, JD Kuaiche, Alimama and store transaction data, with daily or hourly update frequency.

For operating reviews and anomaly retrospectives, these materials enter HTTP integrations as request addresses, methods, headers, bodies and extracted return values. The HTTP module sends a request to a corresponding address, and the practical operation resembles Postman and ApiFox. Params carry path request parameters and are used more often in GET requests. Body carries the request body and is used more often in POST and PUT requests. Headers carry request headers for special information. Params, Body, Headers and the URL can all reference variables through `{{}}`, drawing on global variables, system variables or upstream node outputs. An interface call is a data channel. It does not perform advertising authorization or budget approval.

## Constraints at the HTTP integrations step

Return values are not the interface return value itself. They define how to parse the interface return value, extracting values through JSON path syntax. After FastGPT v4.6.8, output formatting mainly converts json into a string. When the output type is set to string, the value at the corresponding HTTP key is converted into a json string for output, which can then pass into text processing and onward into an AI dialogue.

Several documented conditions shape field checking. The system variables available when referencing request parameters include appId, chatId, responseChatItemId, variables, cTime and histories, where histories defaults to a maximum of 10 entries and the length cannot be modified. chatId and responseChatItemId do not exist in test mode, so an empty value during debugging is not a business fault. With detail=true, intermediate values are retained in responseData, and in stream mode they are distinguished through event. Parameters such as model and temperature passed to the chat completions interface are invalid, because these fields are determined by the orchestration and do not change with API parameters. Token consumption is not returned directly; detail=true allows manual calculation from the tokens values inside responseData.

A hypothetical paper exercise sample is set out here for checking. The source material reads: "Delivery plan A runs from March 1, 2026 to March 31, 2026. Keyword report B records 1,200 clicks on March 5. Conversion attribution table C records 30 completed orders on the same day." The proposed determination sentence reads: "The ROI of this plan on March 5 is confirmed as meeting target." In this sample the subject is delivery plan A, the object is the March 5 click and order fields, the status is pending determination, and the effective range is March 1 to March 31. The proposed sentence lacks a spend field and a target threshold, so it remains unsupported.

## Three common errors

1. Treating an interface return value as a delivery target conclusion. In the sample, the proposed determination sentence lacks a spend field. Return value extraction only moves data; target judgment requires separate checking.

2. Treating an empty chatId or empty responseChatItemId in test mode as a business fault. The documents state that these two fields do not exist in test mode, so the check should record the absence without inferring an interface anomaly.

3. Treating a module's runningTime or tokens inside responseData under detail=true as a delivery performance indicator. These fields are runtime intermediate values and have no corresponding relationship with advertising spend or transaction attribution.

## How to verify the setup

1. Input the sample source text and the proposed determination sentence, then compare whether the fields required by the proposed sentence appear in the source. The source contains clicks and completed orders, and lacks a spend field and a target threshold, so the determination is unsupported.

2. Input a hypothetical request whose Body references `{{number}}` and `"{{string}}"`, then compare whether the final parse matches the documented example. If the string is not quoted or the array does not follow the documented form, the parsed result differs from the expectation.

3. Input a hypothetical response with detail=true and stream=false, then compare whether the moduleType inside responseData corresponds to the sample task. If the returned module is unrelated to the delivery report, record it as pending verification and do not judge delivery performance from it.

A pending request is not approval, an offered option is not execution, and an unsigned termination is not a completed termination. Retrieval is not authorization, and a relevance score is not a category, entity or permission filter. Where the documents do not state an error code or an automatic business action, the comparison records what was observed and leaves the remainder unknown.
