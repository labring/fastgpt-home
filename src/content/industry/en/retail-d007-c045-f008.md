# Seller ratings management: workflow routing for operating reviews

## What the documents look like

Ratings maintenance data comes from consumer feedback recorded after after-sales fulfilment is complete. It does not directly set promotion prices. The main sources named in the brief are Douyin Shop experience score, Tmall service indicators, JD after-sales reviews, and the customer service system. The documents handled day to day are negative-review handling records, experience score breakdowns, service diagnostic reports, and rectification ledgers. Typical roles are store operations staff, customer service supervisors, and quality inspection specialists. Errors in this area can reduce search weight, restrict promotion registration, and lower store conversion. These materials enter reporting and review on daily and weekly update cycles.

Workflow routing at this stage has to connect scattered negative-review attribution, supporting-evidence supplementation, and rectification tracking into a reusable flow. It also has to keep collection actions separate from authorization actions.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. After the user fills in the required information and submits, the node collects what was entered and passes it to later nodes. The user selection node is also a user interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. When the user makes a choice, the node evaluates that choice and executes the "yes" branch. Both node types can be added repeatedly and trigger execution.

Retrieval and authorization are separate matters. Semantic recall and relevance scores do not perform permission or entity isolation. A same-vector-model requirement for a retrieval library constrains only that library; it does not extend to business registration sites or other external systems. Order writes, document backfill, and external status synchronization require a separate business interface or a later flow. The nodes themselves do not perform those actions. Optional paths shown in an overall document flow diagram do not mean every request executes all of them: image retrieval requires a corresponding image input and model capability, and reranking requires a model and must be enabled according to settings.

Hypothetical paper exercise sample: Material text one reads, "The customer service supervisor submitted a negative-review handling record on 10 March 2025. The record object is the after-sales review for Order A. The status field states 'awaiting supporting evidence.' The effective range is 10 March to 17 March." Material text two reads, "The quality inspection specialist submitted a rectification ledger on the same day. For the same Order A, the same field 'handling status' states 'completed.'" The draft sentence to be assessed is: "The negative-review handling status for Order A is completed and can be closed directly."

A contradiction requires the same subject, the same period, and the same field with mutually exclusive values. Here the two materials have different subjects and mutually exclusive values in the same field. This is a pending-verification situation; it does not support a negative or conflicting conclusion. Awaiting supporting evidence does not equal missing operating permission, and it does not equal completed.

## Configuration and implementation checks

| Configuration or check item | Corresponding content on this page | How to check |

| Form input node | Collects required fields from the negative-review handling record | After submission, compare output fields against input fields one by one |
| User selection node | Makes a choice on "whether to supplement evidence" and follows the "yes" branch | Verify branch connections and the selection result one by one |
| Interaction state check | Triggering enters the interaction state and records the workflow state | Observe that the dialogue box hides and the state is recorded; no separate global switch is set |
| Output handoff check | Passes collected information to later retrieval, judgment, or interface nodes | Compare downstream inputs against upstream outputs one by one |
| External action division | Order writes, document backfill, external synchronization | Confirm a separate business interface is connected; the node does not carry out this action |

## Three common errors

1. Treating form input submission as authorized execution. Submission only collects required information and passes it to later nodes. Business verification, approval, database writes, and external synchronization must be implemented downstream.
2. Treating retrieval relevance as permission or entity filtering. A similarity setting does not exclude unrelated businesses or unauthorized records. Retrieval is not authorization.
3. Treating values from different subjects and different fields as a direct contradiction. A determination requires the same subject, the same period, and the same field, with clearly mutually exclusive values in that field.

## How to verify the setup

1. Enter the two hypothetical sample materials and the draft sentence above. Compare subject, object, status, and effective range. If the two materials have different subjects while the same field has mutually exclusive values, the observable result is "pending verification," and the condition for closing as "completed" is not met.
2. Enter a record containing only "awaiting supporting evidence." Compare whether "awaiting supporting evidence" and "completed" are mutually exclusive values in the same field. If they are in the same field and mutually exclusive, the observable result is that a source must be supplemented. If they are in different fields, the result remains unknown.
3. Enter an explicit paper empty result []. Compare whether the downstream node has a design for accepting an empty result. The observable result is that downstream handles it as empty input.
