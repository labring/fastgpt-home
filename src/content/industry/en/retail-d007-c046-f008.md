# Marketplace category access: workflow routing for operating reviews

## What the documents look like

Category access is decided before listing or onboarding. The evidence sits with the applying entity and the chain that connects it to the right holder. A business licence identifies the operating entity. A trademark registration certificate identifies ownership of the right. A brand authorization chain shows how the right passes from the holder to the applicant. An industry licence confirms the conditions for a specific category. These four material types form the spine of the access decision. When any one is absent, later routing has no verifiable input to carry forward.

Material updates are irregular and tied to each onboarding. This page does not derive batch synchronization or real-time triggering from that fact. The task here is operating reporting and exception review: recording the materials collected during one onboarding, the submission action, and the request status, so that a later review can identify which step stopped in which state. The public brief describes this category at a rough confidence level, so the descriptions below remain conditional where the brief itself is conditional.

## Constraints at the workflow routing step

Two interaction nodes are relevant. When the Form Input node triggers, the conversation enters an interaction state, the workflow state is recorded, and the node collects required information. After the user submits, the collected information is passed to later nodes. When the User Selection node triggers, the conversation likewise enters an interaction state and the workflow state is recorded. After the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. Both behaviours are documented node behaviour.

A form collects values. It does not perform business verification, approval, database writes, or external synchronization. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval and similarity scores do not carry permission or entity-isolation duties. Libraries built on different vector models cannot be associated together; identifiers must be checked first and non-matching libraries excluded. Retrieval is not authorization.

Hypothetical paper exercise: an applicant submits materials. The business licence states "unified social credit code segment A, entity name Example Trading Co., Ltd., registration status active." The trademark registration certificate states "registration number segment B, registrant Example Trading Co., Ltd., approved use class Class 25." The brand authorization chain document states "authorizing party Example Trading Co., Ltd., authorized party Example Trading Co., Ltd., authorization period 1 January 2024 to 31 December 2026." The proposed determination sentence is "the entity has obtained Class 25 operating authorization and may proceed to category publication." Review must compare whether the authorizing and authorized parties in the chain cover the applicant, whether the authorization period covers the intended onboarding period, and whether the class matches the target category. This sample is a paper exercise and was not submitted or approved.

## Configuration and implementation checks

| Configuration item | Value or check on this page | Basis and boundary |
| --- | --- | --- |
| Form Input node | Collect business licence, trademark certificate, authorization chain, licence fields | The node collects required information and passes it to later nodes |
| User Selection node | Branch question "are materials complete," execute the "yes" branch | The node executes the corresponding branch after the user chooses |
| Interaction state record | Observe that the conversation enters an interaction state after triggering | Documented node behaviour; no separate global switch is set |
| Output handoff | Compare each form output against later node inputs | Collected information must be explicitly passed to later nodes |
| External writes | Mark as requiring a separate business interface | The node does not perform database writes or external synchronization |
| Retrieval scope | Check library identifiers and vector model identifiers | Libraries on different models cannot be associated together |

## Three common errors

1. Treating form submission as completed authorization. The Form Input node only collects and passes information; the submission action does not produce approval or authorization effect. When checking, compare the proposed determination sentence against the source text. If the source only shows that materials were submitted, a sentence stating "authorization obtained" exceeds the source.

2. Treating the User Selection branch as a business conclusion. Executing the "yes" branch only indicates that the user made a choice; it does not indicate that materials passed verification. When checking, compare the branch direction against the source text. If the source records no review conclusion, the branch result cannot be written as a passed review.

3. Treating retrieval similarity as a permission filter. Similarity does not carry entity-isolation duties. When checking, compare the returned records against the authorization boundary. If a returned record belongs to another entity, check identifiers first and exclude it, and do not conclude that this entity obtained authorization on that basis.

## How to verify the setup

- Verification one: use the hypothetical sample above. Input is the three source passages from the business licence, trademark certificate, and authorization chain. Compare the proposed determination sentence "the entity has obtained Class 25 operating authorization" against the source text. Observe whether the authorization chain states that the authorizing and authorized parties cover the applicant. If the source does not state that coverage, the determination sentence is unsupported and is recorded as pending verification.

- Verification two: use the same hypothetical sample. Input is the four fields output by the form. Compare the form output against the later node inputs one by one. Observe whether the later node receives all fields. If a field does not appear in the later input, that field's handoff is incomplete.

- Verification three: use the same hypothetical sample. Input is the returned retrieval record and the authorization chain source text. Compare the entity identifier in the returned record against the authorizing party identifier in the chain. Observe whether the two match. If they do not match, exclude that record and record the actual observation, without inferring missed recall or redundant results.

All three verifications are paper checks and were not actually run. An empty-result handoff can be checked against a downstream design using an explicit paper input of an empty list, without claiming that a fictional rule retrieval necessarily returns an empty list.
