# Parcel labels and handoffs: HTTP integrations for operating reviews

## What the documents look like

Outbound parcel handoff sits at the point where a package leaves the warehouse, and the carrier scan carries the responsibility record. Operating reports and exception reviews for this category work from electronic waybills, handoff manifests, pickup scan records, and exception registrations. These materials update per batch and per day, so report periods are grouped by batch or by day. No other synchronization mechanism is introduced here.

The HTTP module sends a request to an external address, and its operation is close to tools such as Postman and ApiFox. Params are path request parameters and are used more often with GET requests. Body is the request body and is used more often with POST and PUT requests. Headers carry special information. Params, Body, Headers, and the URL can all reference variables through `{{}}`. Variables come from global variables, system variables, and upstream node outputs. The module can connect to external services; the documented example routes post, delete, put, and get actions to create, remove, update, and query records and returns an exception marker on failure. That example is not a commitment about any specific carrier system.

## Constraints at the HTTP integrations step

System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. chatId and responseChatItemId do not exist in test mode, so an empty value read during debugging is an environment difference and not a business fault. Return-value entries describe how to parse the interface response, extracted with JSON path syntax following JS object access rules; for example, a key of `data.user.name` retrieves the user name. When the output type is string, the value at the corresponding key is converted to a JSON string. Authorization is handled through the API key, and the documented priority for appId is `body.appId`, then `<apiKey>-<appId>`, then the appId associated with the API key. A pending request is not an approval, and a configured field is not an executed business action.

Hypothetical paper exercise sample, clearly labelled as hypothetical: the warehouse outbound team, on the day shift of 12 March 2025, uses the HTTP module to submit a handoff manifest to an external handoff service for batch 7, completed before 14:00 on 12 March 2025. The source texts to be checked read as follows. The handoff manifest states: "Batch 7, carrier branch A, 42 parcels, handoff time 2025-03-12 14:20." The pickup scan record states: "Batch 7, 40 parcels scanned, scan time 2025-03-12 15:05." The exception registration states: "Batch 7, 2 parcels with damaged outer packaging, awaiting branch confirmation, registered 2025-03-12 15:10." The draft sentence to be judged is: "All 42 parcels in batch 7 have been picked up by branch A." That draft sentence treats the 2 parcels still awaiting confirmation as completed pickup, which conflicts with the 40 parcels in the scan record, and is unsupported.

## Three common errors

1. Treating a count awaiting confirmation as a completed count. The input is the sample's 42-parcel manifest, 40-parcel scan, and 2 parcels awaiting confirmation; the comparison is between the manifest parcel count and the scanned parcel count; the observable result is that the draft sentence conflicts with the scan record and is judged unsupported.
2. Treating the missing chatId and responseChatItemId in a debug environment as an interface fault. The input is an empty chatId under test mode; the comparison is against the documented test-mode difference; the observable result is that the empty value is an environment difference and does not constitute evidence of a business fault.
3. Treating the return-value extraction configuration as the interface response itself. The input is the key and output-type settings; the comparison is between the actual response and the extracted result; the observable result is that the extracted value comes from the converted format, and a failed extraction does not support an inference that the interface returned no data.

## How to verify the setup

1. Check the draft sentence against the sample source texts. The input is the three source texts (handoff manifest, pickup scan record, exception registration) and the draft sentence; the comparison is the parcel count for the same batch and the same time scope; when the scanned count and the manifest count differ and an awaiting-confirmation registration exists, the draft sentence does not meet the condition and must be recorded as unsupported.
2. Check the variable passing with the sample request. The input is the batch and parcel count variables referencing upstream node outputs; the comparison is between the values actually passed in the request and the node output values; when the two agree and the request type matches the Body effective condition, the request configuration meets the condition.
3. Check the downstream design with an empty result. The input is a paper-agreed empty list `[]`; the comparison is the downstream node's handling design for an empty value; when the design explicitly accommodates an empty result and produces no business action, that branch meets the condition, and the actual return still needs observation and recording.

These checks verify only request construction and text judgement. They do not execute authorization, approval, database writes, or external system synchronization; those actions require their own implementations.
