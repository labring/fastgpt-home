# Parcel labels and handoffs: workflow routing for operating reviews

## What the documents look like

Parcel handoff happens at the point where a package leaves the warehouse, and responsibility is judged from carrier scan records. This page works with four document types: electronic waybills, handoff manifests, pickup scan records, and exception-item registers. Data sources named in the brief are the courier system, WMS shipment records, the GB/T express service standard, and carrier bills. These materials update per batch or per day.

For operating reports and exception reviews, the practical work is to place the handoff manifest and the pickup scan record for the same batch side by side. The review looks for parcels that have no scan, parcels whose scan time is later than the handoff time, and parcels whose waybill details disagree with the manifest. Workflow routing at this step moves the information needed for those comparisons along a fixed path and pauses for human confirmation when a decision is required.

The brief gives three time-consuming steps for this category: printing waybills, handing over parcels, and checking pickup scans. The consequence of error is a false shipment record, a lost-item dispute, or a platform shipping timeout. These are the business reasons the comparison matters, and they shape what the workflow must collect before any downstream action.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution waits until the user completes the interaction. The node collects required information and, after submission, passes that information to later nodes. The user selection node behaves the same way at the state level: it triggers, the conversation enters the interaction state, the workflow state is recorded, and execution continues after the user acts. When the user makes a choice, the node evaluates that choice and runs the corresponding "yes" branch.

Both behaviors belong to the nodes themselves. The documents do not describe a separate global switch for recording state, a guaranteed number of submissions, or automatic judgment. Interaction waiting, state recording, and hiding the dialog are node behavior, not configurable controls that this page can invent.

Hypothetical drill sample. A warehouse shipment batch A has a handoff manifest reading: "3 June 2024, parcels P001 to P010, 10 items total, handover person A, carrier B." The pickup scan record reads: "3 June 2024, P001 to P008 scanned, P009 and P010 have no record." A draft sentence reads: "All parcels in this batch have completed pickup." A pending request reads: "Please confirm whether P009 and P010 may be entered in the exception-item register."

Here the subject is the same batch A, the objects are P001 to P010, the period is 3 June 2024, and the field is pickup scan status. P009 and P010 have no record in the scan record. That is unsupported, not confirmed pickup and not confirmed loss. The draft sentence and the scan record take mutually exclusive values on the same field for the same batch and date, which makes the draft sentence contradictory. The pending request is a request, not an approval, and not an execution of any register write.

## Configuration and implementation checks

| Configuration item | Setting on this page | How to check it |
| --- | --- | --- |
| Form input node | Collect batch number, parcel range, handoff date | After submission, confirm the values pass to later nodes |
| User selection node | Ask whether P009 and P010 enter the exception-item register | After the choice, confirm the matching "yes" branch runs |
| Interaction state | Entered when the node triggers | Confirm the dialog hides and the state is recorded |
| Output handoff | Pass collected values to a later retrieval or judgment node | Compare each output item against the input item |
| External action split | Exception-item register writes require a separate business interface | Confirm no automatic write is claimed |
| Retrieval input | Paper input of an empty result [] | Check downstream design; do not claim a rule retrieval must return [] |

The table lists only documented node behavior and implementation checks tied to this page. The empty result [] is a paper input used to inspect downstream handling. It does not assert that any rule retrieval will return an empty array.

## Three common errors

1. Treating the draft sentence "All parcels in this batch have completed pickup" as a verified conclusion. The scan record shows no record for P009 and P010, and the two statements take mutually exclusive values on the same field. The correct finding is a contradiction, not a denial and not a loss.
2. Treating values collected by the form input node as business authorization. The node collects values and passes values. Order writes, document backfill, and external status synchronization require a separate business interface or a later process.
3. Treating retrieval as a permission or entity isolation mechanism. A relevance score does not perform category, entity, or permission filtering, and retrieval results do not replace an authorization decision. A similarity setting does not exclude unrelated businesses or unauthorized records.

## How to verify the setup

1. Input the handoff manifest text, the scan record text, and the draft sentence from the hypothetical sample. Compare the draft sentence against the scan record on the same batch, the same date, and the same field. If the scan record has no entry for P009 and P010, the draft sentence is unsupported and the contradiction condition is met. The expected observation is a mismatch on pickup scan status for those two parcels; the case does not establish loss.
2. Input the pending request "Please confirm whether P009 and P010 may be entered in the exception-item register." Compare the branch connections of the user selection node against the request content. The condition is met when the "yes" branch runs after that choice and the output handoff is explicit. If the branch is not connected, or the output does not reach the later node, the condition is not met. A branch running is not an approval and not a register write.
3. Input the paper empty result []. Compare the downstream node design for explicit handling of an empty input. The condition is met when the downstream design can handle the empty input and does not claim that a rule retrieval must return []. If the downstream depends on an undeclared automatic return, the condition is not met. The expected observation is documented downstream behavior, and the actual return value of any retrieval remains unknown.

Across these checks, keep missing evidence missing. A pending request is not approval. An offered option is not execution. An unsigned termination is not a completed termination. Where the documents do not state a field, an error code, a limit, or a scheduled trigger, the value remains unknown rather than assumed.
