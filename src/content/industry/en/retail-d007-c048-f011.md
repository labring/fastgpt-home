# Parcel labels and handoffs: database operations for operating reviews

## What the documents look like

Parcel handoff happens at the point where a parcel leaves the warehouse, and the carrier scan is what assigns responsibility. Operating reports and exception reviews for this category draw on four material types: electronic waybills, handoff manifests, pickup scan records, and exception item logs. These materials update per batch and per day, and their sources include the carrier system, WMS shipment records, and carrier bills. Compared with in-warehouse packing, the handoff step is decided by scan records, so a report has to place the waybill, the manifest, and the scan record under the same operating entity, the same period, and the same field before any comparison is meaningful. The database operations step makes those materials queryable, comparable, and traceable. Retrieval and forms do not themselves constitute authorization.

## Constraints at the database operations step

The business record store and the vector retrieval backend serve different roles and must be checked separately against the actual deployment. Connection pools, caching, and backup and recovery are observed against the load actually carried; thresholds that were not tested internally cannot be copied in. Retrieval locates materials. A relevance score does not perform permission or entity isolation. Libraries built on different vector models cannot be jointly associated; identifiers are checked first and non-matching libraries are excluded. Forms collect values, and business verification, approval, database writes, and external synchronization each need their own downstream implementation. After a database or service configuration change, the same business sample is re-checked; process liveness alone does not show that the change is correct.

Hypothetical drill sample. A warehouse shipped batch B-0610 on 2025-06-10. The handoff manifest states: "Handed to carrier branch A, 120 parcels, handoff person Zhang, date 2025-06-10." The pickup scan record states: "Branch A scanned 118 parcels, time 2025-06-10, 2 exception items logged, cause pending." A draft judgment sentence reads: "All 120 parcels in this batch completed pickup scanning." Comparing the same batch, the same date, and the same field: the manifest count is 120, the scan count is 118, the two do not agree, the draft sentence is not supported, and the exception cause remains pending.

## Configuration and implementation checks

| Configuration item | Hypothetical starting value for this drill | Reason and comparison method |
| --- | --- | --- |
| DB_MAX_LINK | 20 | Set against the concurrent query volume for this batch; compared with connection error rate and wait time and adjusted accordingly |
| SYNC_INDEX | true | Creates missing indexes at startup; when disabled, indexes are maintained manually, so the choice follows actual operations capacity |
| REDIS_URL | Points to the cache instance for this deployment | The connection string is checked against the deployment plan; usability is not inferred from the name |
| MONGODB_URI | Points to the main store for this deployment | Checked separately from the log store connection and filled in per the actual deployment |
| LOG_ENABLE_OTEL | false | Kept off when OTEL is not connected; once connected, checked against the reporting address |
| TRACK_BATCH_UPDATE_TIME | 10000 | Batch write interval for event counts, adjusted after observing write pressure |

These values are hypothetical starting points for this drill. They are compared with observed load values and are not official defaults.

## Three common errors

1. Treating a retrieval hit as authorization. Input: one request that retrieves by waybill number. Comparison: the records returned by retrieval against the batch scope granted to the current operator. Observable result: retrieval returns records, but the operator has not been granted that batch scope, so handoff confirmation must not be executed on that basis.
2. Treating a relevance score as an entity filter. Input: one query carrying a similarity threshold. Comparison: the entity identifier of each returned record against the target batch identifier. Observable result: a record scores high but its entity identifier does not match, so the record is excluded; the score does not perform isolation.
3. Treating form submission as business completion. Input: one submitted exception item log form. Comparison: the form status against downstream approval and write records. Observable result: the form is submitted but no approval record and no write record exist, so the exception item remains pending.

## How to verify the setup

1. Check count consistency with the hypothetical sample. Input: manifest 120 parcels, scan 118 parcels, draft judgment sentence "all parcels completed pickup scanning." Comparison: parcel counts in the same batch, same date, same field. Condition met: the draft sentence does not agree with the scan count, so it is judged unsupported and the exception cause is recorded as pending.
2. Check downstream design with an empty result. Input: a paper retrieval input of []. Comparison: the downstream path taken for an empty result. Condition met: the empty result does not trigger handoff confirmation and does not write a completed status; no claim is made that a fictional rule will always return [].
3. Re-check the sample after a change. Input: queries for the same batch B-0610 before and after the configuration change. Comparison: returned records and elapsed time for the same field. Condition met: after the change the same sample returns consistent records, and connection errors and elapsed time stay within the observed range; process liveness is not used as the pass criterion.

This page addresses only parcel labels and handoffs / operating reports and exception review / database operations. Which materials, actions, and requests sit in which authorization state during the operational handoff is a separate question, and neither retrieval nor a form may be treated as authorization to execute.
