# Wholesale stall trading: HTTP integrations for operating reviews

## What the documents look like

Wholesale market stall trading is fragmented. On-site bargaining sits alongside consignment shipping, and the materials that support an operating review arrive from several directions: market price quotations, stall inventory, payment records, and shipping waybills. The daily documents named in the brief are purchase notes, handwritten sales slips, stall lease contracts, and payment receipts. An operating review and exception replay has to align these materials to the same counterparty, the same period, and the same field before it can say whether a payment has been settled or a batch of goods has been dispatched.

The HTTP integration step sits at the edge of that work. An HTTP module sends a request to an address, and the returned fields are extracted by JSON path so a reviewer can compare them against the documents. The interface itself does not perform authorization, approval, or database writes. Those remain downstream implementation concerns.

## Constraints at the HTTP integrations step

The HTTP module can be added repeatedly, is configured manually, and executes on trigger. Params carry path request parameters and are used mostly with GET. Body carries the request body and is used mostly with POST and PUT. Headers carry special information. The URL, Params, Headers, and Body can all reference variables through `{{}}`, drawing on global variables, system variables, and upstream node outputs. The documented system variables are appId, chatId, responseChatItemId, variables, cTime, and histories. The histories variable defaults to the most recent 10 records and its length cannot be modified. chatId and responseChatItemId do not exist in test mode, so a missing value during debugging is expected and does not by itself indicate a business failure.

Return values are extracted with JSON path syntax, and the output formatting introduced after v4.6.8 mainly converts JSON into a string when the output type is set to string. The chat completions interface uses APIKey authentication. The documented appId priority is body.appId, then `<apiKey>-<appId>`, then the appId associated with the apikey. The model and temperature fields passed in the request have no effect because the orchestration decides them. When detail=true, responseData retains module status and the complete result.

Hypothetical paper exercise sample. The material text reads: "On 12 March 2025, stall A issued a shipping waybill to buyer B, waybill number T-0312. Payment receipt R-0312 records an amount of 8,600 yuan, and the status column reads 'received'. Stall lease contract Z-2025 sets the lease term to 31 December 2025." The draft sentence under review reads: "Buyer B's 8,600 yuan payment is settled and shipping is complete." That sentence merges the receipt status with a shipping completion claim, and no signed delivery field for the waybill is present in the material.

The relevance score returned by a retrieval step is not a category, entity, or permission filter. A similarity setting does not exclude unrelated businesses or unauthorized records, and retrieval is not authorization. The same-vector-model requirement for retrieval association applies only to knowledge base association; it does not extend to business registration sites or other external systems.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | How to check |
| --- | --- | --- |
| Request address | The address given in the external interface document | Compare character by character against the interface contract |
| Request method | Chosen according to the interface document | Check whether it matches the document |
| Headers authentication | Injected through secure configuration | Not written into public samples |
| Body structure | JSON fields per the interface contract | Check key names and types |
| Return value extraction | A JSON path expression | Verify the extracted value against a sample response |
| Output type | String | Check whether the value is converted to a JSON string |

The starting values above are chosen for this hypothetical exercise and are not official defaults. They are compared against the interface contract and a sample response.

## Three common errors

1. Treating an empty chatId or responseChatItemId in test mode as an interface failure. Check: send a request in test mode, compare the returned fields against the documented behavior, and observe that the empty value matches the documented condition rather than indicating a fault.
2. Treating the receipt status "received" as proof that shipping is complete. Check: take the sample material text and the draft sentence, compare the receipt field against the waybill delivery field, and observe that the delivery field is absent, which places the draft sentence beyond the evidence.
3. Treating a retrieval similarity score as a permission or entity filter. Check: submit an unrelated query, compare the returned items against the authorized scope, and observe that similarity does not exclude unrelated records, which confirms the setting does not carry a permission function.

## How to verify the setup

1. Take the sample material text and the draft sentence. Compare the assertions in the draft against the fields stated in the material. The receipt status "received" is supported; the claim "shipping is complete" is not supported. The result is pending verification.
2. Send a request in test mode. Compare the chatId and responseChatItemId values. An empty value with the remaining interface fields returning normally means the debugging empty value is not a fault.
3. Submit an unrelated query. Compare the returned items against the authorized scope. Similarity does not exclude unrelated records. Record the actual observation and do not draw a permission conclusion.

An empty reference result can be checked against a downstream design using an explicit paper input of `[]`; this does not assert that any fictional rule retrieval returns an empty array. Where a document field is not provided, the value remains unknown. A pending request is not an approval, an offered option is not an execution, and an unsigned termination is not a completed termination.
