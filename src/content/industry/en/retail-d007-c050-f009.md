# Complaints and official replies: tool calls for operating reviews

## What the documents look like

Complaint and regulatory reply work faces a platform or a regulator rather than an internal repair or reshipment queue. Formal evidence and rectification wording carry the case. The brief lists 12315 platform records, platform complaint centers, customer service chats and order systems as data sources, with complaint tickets, regulatory inquiry letters, order evidence and rectification reports as the daily documents. The stated update frequency is irregular, per case; this page does not convert that into batch synchronization or a real-time trigger.

For operating reviews and anomaly review, the practical consequence is that a tool call step must decide whether to run a module or plugin against material that may still be incomplete. A tool introduction tells the model what the tool does. System module parameters are already fixed; plugin parameters are configurable. Each parameter carries a parameter introduction and a whether-required value. When a required parameter has no suitable value in context, the model may decline to call that tool, and prompts can guide the user to supply the missing value.

## Constraints at the tool calls step

Tool calls let the model decide dynamically instead of following a fixed path, at the cost of token use. In advanced orchestration, available tools are connected to the tool call module; the connected tool separates tool input from ordinary input, and its introduction can be edited so the call timing is more precise. The official guidance recommends starting with a small number of tools and tuning before adding more. The tool call termination node ends the current call: no further tools run, and the AI does not summarize the tool results. Custom tool variables extend variable input for nodes that are not treated as tool parameters or cannot be tool-called, by supplying a parameter description.

Hypothetical paper exercise sample, used only for checking on this page. A shop receives a complaint ticket numbered X-001. The supplied material text reads: "The complainant placed an order on March 1, received it on March 5, claims the goods do not match the page description, and requests a refund." A draft sentence awaiting judgment reads: "This complaint has been verified as established, and the refund is approved." The comparison must check whether the order evidence for ticket X-001 states a verification conclusion and a refund approval status. The material states a claim and a refund request. It does not state that verification succeeded.

## Configuration and implementation checks

| Tool parameters | Check system module parameters and configurable plugin parameters separately | A parameter introduction is not a guarantee of execution |

## Three common errors

1. Treating retrieval or a form as authorization. Retrieval is recall, and a form collects values. Business verification, approval, database writes and external synchronization need their own downstream implementation. Check: input ticket X-001, compare the retrieval result with the approval record, and if retrieval returns the ticket while the approval field is empty, record the gap.
2. Treating a pending review as an approval. In the draft sentence "This complaint has been verified as established, and the refund is approved," verification and refund approval are different facts. Check: input the draft sentence and the order evidence, compare whether a verification conclusion and an approval status are stated, and mark the draft as unsupported when they are not stated.
3. Treating a relevance score as a permission filter. A relevance score does not exclude unrelated businesses or unauthorized records. Check: input an unrelated query, observe the returned content, and if an unauthorized record appears, record the actual observation without inferring a deterministic cause.

## How to verify the setup

- Verification one: input hypothetical ticket X-001 and the draft sentence "This complaint has been verified as established, and the refund is approved," then compare the draft sentence with the supplied material text. The material states only the claim and the refund request, and does not state that verification succeeded. The condition is satisfied when the draft sentence is marked as unsupported.

- Verification two: input an empty result `[]` and check whether the downstream design handles an empty result. The condition is satisfied when the downstream does not execute a refund action and only records the gap.

- Verification three: input library identifiers for two different vector models and check whether the identifiers match. The condition is satisfied when mismatched identifiers are excluded and the actual observation is recorded. Cross-model retrieval is not performed to compare missed recall.
