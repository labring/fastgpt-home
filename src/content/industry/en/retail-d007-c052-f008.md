# Pinduoduo seller campaigns: workflow routing for operating reviews

## What the documents look like

Pinduoduo low-price campaign operations revolve around low-price resource slots, campaign inventory and refund-rate swings, which sets the category apart from Tmall flagship store operations. The main data comes from the Pinduoduo merchant backend, campaign resource-slot data, ERP inventory and logistics delivery records. Day-to-day documents include campaign registration forms, product cost calculation sheets, after-sales refund slips and platform in-site messages. Data updates daily or per campaign.

In operating reporting and exception review, this material feeds into workflow routing. The form input node collects required information, the user selection node carries a manual decision, and both pass results to later nodes. Campaign inventory estimation, abnormal refund tracking and campaign-price gross-margin checking are the time-consuming steps. Material status and authorization status need separate records.

## Constraints at the workflow routing step

When the form input node triggers, the conversation enters an interactive state, the workflow state is recorded, and after the user fills the required information and submits, the node collects the submitted form information and passes it to later nodes. When the user selection node triggers, the conversation also enters an interactive state; when the user makes a choice, the node evaluates that choice and executes the "yes" branch. The interactive state is node behavior; no separate global state-recording switch is documented.

Collected information needs an explicit hand-off to later retrieval, judgment or interface nodes. Order writes, document backfill and external status synchronization require a separate business interface or a later flow. Retrieval does not carry authorization duties, and a similarity score does not constitute entity isolation or permission filtering. Optional paths listed in a document's overall flow diagram do not mean every request executes all of them. Image retrieval requires image input and model capability; reranking requires a model and must be enabled in settings. Libraries built on different vector models cannot be associated together; check identifiers first and exclude those that do not match.

Hypothetical paper exercise sample: a Pinduoduo campaign operator submits one set of material at the campaign review node. The source text reads: "Campaign registration form number HD-0715, product object summer cooling mat, campaign price 19.9 yuan, campaign inventory 800 units, registration status submitted and pending review; the product cost calculation sheet marks the single-unit cost of this product at 21.5 yuan; the after-sales refund slip shows 12 units refunded on July 15, all with the reason size mismatch; a platform in-site message notifies that the resource-slot campaign period is July 15 to July 17." The draft sentence to be judged is: "The campaign has passed platform review, so restocking can be arranged and ERP inventory synchronized." Checkpoints: the registration status is submitted and pending review, which does not constitute review approval; restocking and ERP synchronization are external business actions that require a separate interface or later flow; the refund slip's reason field and the inventory estimate share the same period and the same object and can serve as exception-review input.

## Configuration and implementation checks

| Configuration item | Purpose on this page | Check method |
| --- | --- | --- |
| Form input node | Collect required fields such as campaign registration form number, product object, campaign price and campaign inventory | After submission, compare the form output against the later node input item by item |
| User selection node | Carry the manual decision on whether an abnormal refund enters the review branch | After the user chooses, check whether the "yes" branch executes according to that choice |
| Interactive state recording | Record the workflow state at the interactive node | Confirm the interactive state arises from node behavior, with no separate global switch |
| Output hand-off | Pass form information to later retrieval, judgment or interface nodes | Compare upstream output against downstream input fields item by item |
| External action division | Order writes, document backfill, ERP synchronization | Confirm these are implemented by a business interface or later flow, not directly by retrieval or the form |
| Hypothetical trial starting point | This exercise uses campaign inventory 800 units and 12 refunded units as comparison starting points | These values are only the hypothetical trial starting points, used to compare against the cost calculation sheet and refund slip for the same period and same object; they are not official defaults |

## Three common errors

1. Treating "submitted and pending review" as review approval. Input is the registration status field "submitted and pending review"; the comparison object is the draft sentence "has passed platform review"; the observable result is that the two status values do not agree and the draft sentence is unsupported.
2. Treating form collection or retrieval results as authorized execution. Input is the campaign inventory and refund data submitted through the form; the comparison object is the restocking and ERP synchronization request; the observable result is that the form output only passes information and produces no order write or external synchronization action.
3. Treating a similarity score as entity or permission filtering. Input is the relevance score returned by retrieval; the comparison object is the material's owning entity and access scope; the observable result is that the score does not distinguish entities, so identifiers must be checked separately and non-matching items excluded.

## How to verify the setup

1. Use the hypothetical sample source text to check the draft sentence. Input is the registration status "submitted and pending review"; the comparison object is the draft sentence "has passed platform review"; the condition to satisfy is identifying that the status values disagree and recording that the sentence is unsupported. If the source text does not state a review result, record it as pending verification.
2. Use the hypothetical sample to check the output hand-off. Input is the registration form number, product object, campaign price and campaign inventory submitted at the form input node; the comparison object is the fields actually received by later nodes; the condition to satisfy is item-by-item field correspondence. When a field is missing, record the gap without inventing authorization or effective clauses.
3. Use the hypothetical sample to check the branch and external actions. Input is the user's choice at the user selection node; the comparison object is the "yes" branch execution record and the restocking and ERP synchronization requests; the condition to satisfy is that the branch executes according to the choice and the external actions are explicitly marked as requiring a separate business interface. If only a request exists without an execution record, record it as pending execution and do not treat it as completed.
