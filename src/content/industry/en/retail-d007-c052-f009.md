# Pinduoduo seller campaigns: tool calls for operating reviews

## What the documents look like

Pinduoduo low-price campaign store operations center on low-price resource slots, campaign inventory, and refund-rate fluctuation. The daily document set comprises campaign registration forms, product cost calculation sheets, after-sales refund slips, and platform in-site messages, with updates occurring daily or per campaign. For operating reports and anomaly reviews, this means the form fields, plugin parameters, and message statuses that tool calls must read change with each campaign. A field structure from one campaign cannot be reused as a fixed template.

In the tool calls and plugins step, the campaign registration form supplies product and campaign price information, the product cost calculation sheet supplies the cost basis, the after-sales refund slip supplies refund reasons and amounts, and the platform in-site message supplies platform notices and statuses. Whether these documents have complete fields and clear statuses directly determines whether a tool can obtain checkable parameters. Tool introductions and parameter introductions are defined by the documents, the LLM decides whether to call a tool based on contextual semantics, and whether a parameter is required affects call feasibility.

## Constraints at the tool calls step

After a tool call node connects available tools, it separates tool inputs from ordinary inputs and allows editing the introduction to refine call timing. When there are no required parameters, the model may call the tool even without suitable parameters, and may fabricate a parameter. When there are required parameters and no suitable value exists in context, the model may not call the tool. The tool call termination node ends the current call, does not call other tools, and does not call the AI to answer about tool results. Custom tool variables extend inputs for nodes not treated as tool parameters.

Hypothetical drill sample: a Pinduoduo campaign operator on 10 June 2025 prepares a campaign review packet. The source text reads: "The campaign registration form states that product A joined the low-price resource slot from 1 June to 5 June at a campaign price of 19.9 yuan; the product cost calculation sheet states that product A has a per-unit cost of 17.5 yuan; the after-sales refund slip states that on 3 June product A had 2 refunds, both for size mismatch; the platform in-site message states that on 4 June the platform notified that the resource slot inventory check did not pass." The draft sentence to be assessed is: "Product A's campaign price gross margin is positive, and both the refund reason and the inventory check result have been fully handled." This draft sentence concerns an operating report conclusion and an anomaly handling status. Fields to check include campaign price, cost, refund reason, and in-site message status. The authorization boundary is limited to this store's materials for this campaign.

## Three common errors

1. Writing the tool introduction as a generic description without stating situations where calling should not occur. In the sample, the in-site message status is "inventory check did not pass." If the introduction does not distinguish handled from unhandled statuses, the model may treat "did not pass" as "handled." Check action: read the tool introduction text, compare it with the in-site message source text, and observe whether the introduction contains a status distinction condition.

2. Treating the parameter introduction as an execution guarantee. In the sample, the campaign price of 19.9 yuan and the per-unit cost of 17.5 yuan are both required parameters. If the parameter introduction says "automatically obtained" while the materials provide no acquisition source, the model may fabricate values. Check action: compare the parameter introduction with actual material fields and observe whether value filling without a source occurs.

3. Treating the tool call termination node as automatic business handling. In the sample, the draft sentence states "both have been fully handled." The termination node only ends the current call; it does not execute refunds or inventory handling. Check action: inspect the workflow after the termination node and observe whether downstream system writes or external synchronization implementations exist.

## How to verify the setup

- Verification one: Input the four source sentences and the draft sentence from the sample, and compare "campaign price gross margin is positive" in the draft sentence with the same-field relationship between the campaign price of 19.9 yuan and the per-unit cost of 17.5 yuan in the materials. If the tool output does not calculate gross margin, or the output is inconsistent with the two fields, the condition is not met. The expectation is that the tool should read the two required parameters and retain the original values, without any claim of actual testing.

- Verification two: Input the in-site message "inventory check did not pass" from the sample and the draft sentence "the inventory check result has been fully handled," and compare the same in-site message status field. If the tool output marks "did not pass" as handled, or does not output the status field, the condition is not met. The expectation is that the tool should retain the original status and not automatically determine that handling is complete.

- Verification three: Input the refund slip "on 3 June product A had 2 refunds, both for size mismatch" from the sample and the draft sentence "the refund reason has been fully handled," and compare the refund slip reason field with the handling status in the draft sentence. If the tool output does not distinguish the reason record from the handling action, the condition is not met. The expectation is that the tool should present the refund record and the handling status separately, and not equate a record with completed handling.
