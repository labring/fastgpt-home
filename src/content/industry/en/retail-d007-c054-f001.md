# Channel diversion reviews: HTTP integrations for operating reviews

## What the documents look like

Channel diversion reviews address regional and price order. The materials handled are anti-counterfeit code records, e-commerce platform prices, distributor shipment records, and market inspection material. Rebate amount calculation sits outside this scope. Daily documents include diversion complaint forms, anti-counterfeit code records, penalty notices, and investigation photographs. Update frequency is weekly and irregular. Operating reports and exception reviews need to group these materials by complaint form, goods source code, store price, and penalty status. The HTTP interface carries the duty of sending requests to external anti-counterfeit code systems, price monitoring services, or internal penalty ledgers and of parsing returned values. Because materials sit across several external systems, the interface layer needs to state which complaint form, which goods source code range, and which inspection batch each request corresponds to.

## Constraints at the HTTP integrations step

The HTTP module sends a request to the corresponding address. Params serve as path request parameters, Body serves as the request body, and Headers carry special information. All three can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and preceding node outputs. Among system variables, chatId and responseChatItemId do not exist in test mode. An empty value obtained during debugging is a debug environment characteristic and does not by itself indicate an external system fault. Return value configuration defines parsing rules that extract needed values from the response through JSON path. When the output type is set to string, the value of the corresponding key is converted into a json string. The interface call itself does not constitute authorization, and it does not complete penalty execution or database writes.

Hypothetical drill sample: a brand channel control team receives a diversion complaint form whose original text reads "Complaint number TS-2024-0317, the complained distributor is East China distributor A, the anti-counterfeit code range involved is HZ-0001 to HZ-0200, the e-commerce store link provided by the complainant shows a price below the regional guidance price, the inspection photograph was taken on 15 March 2024, and the complaint form currently has the status pending verification." A separate handover request draft sentence awaiting judgment reads: "Ask the HTTP interface to call the anti-counterfeit code system to query the above range, write the returned result directly into a penalty notice, and synchronize it to the distributor ledger." This draft sentence merges query, penalty notice generation, and ledger synchronization into a single request. The penalty notice and the ledger write have no corresponding authorization basis and remain pending verification.

## Three common errors

1. Treating code segment records returned by the HTTP query as the penalty basis directly. The input is the sample complaint form and the query response. Compare the query result against the fields a penalty notice requires, and observe whether a penalty decision field exists. The query result reflects code segment information only. A penalty notice requires separate confirmation of authorization and process.
2. Treating an empty chatId under test mode as an external system fault. The input is a test mode request. Compare the available range of system variables and observe whether chatId and responseChatItemId are missing. The absence is a debug characteristic stated in the documentation.
3. Treating the ledger synchronization in the draft sentence as already executed. The input is the handover request draft sentence above. Compare the request content against the actual authorization status and observe whether an authorization record for the synchronization action exists. The draft sentence expresses request intent only and does not constitute an execution fact.

## How to verify the setup

1. Take the sample complaint form original text and the HTTP request configuration. Compare whether the request address, the anti-counterfeit code range in the Body, and the complaint number match the original text. Observe whether the request content contains only the fields needed for the query and does not contain penalty notice or ledger write fields.
2. Take the sample response structure and the return value parsing configuration. Compare whether the JSON path extraction results correspond to the query status and code segment records. Observe whether extracted values fall within HZ-0001 to HZ-0200. Results outside the range must be recorded as pending verification.
3. Take the handover request draft sentence above. Compare the actions described in the draft sentence against the confirmable authorization status. Observe whether penalty notice generation and ledger synchronization have corresponding authorization material. When no authorization material exists, record the item as unsupported and retain the evidence gap.
