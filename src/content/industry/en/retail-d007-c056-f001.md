# Producer export tax processes: HTTP integrations for operating reviews

## What the documents look like

Producer export tax processing combines domestic-sales offset with export refund in one calculation, so an operating review has to carry the same scope across four source documents at once: the exemption-offset-refund declaration detail sheet, the export contract, the sales detail ledger, and the customs export declaration. These four documents do not share a single authoritative figure by default. The contract states the agreed transaction amount and trade term, the customs declaration states the declared export amount and trade term, the sales ledger states the booked export revenue and its local-currency conversion, and the declaration detail sheet is the filing schedule that has to be filled from verified figures.

The monthly update rhythm matters for interface work. Data pulled through an HTTP request and manual reconciliation are expected to complete inside the same period, so a figure retrieved from an external system is a candidate value for comparison, not a replacement for the source document. Free-on-board price differences are the object most often located during exception review, because the contract amount and the declared amount can diverge on the same shipment.

The HTTP module sends a request to a configured address and behaves in practice like Postman or ApiFox. Params carry path request parameters and are used mostly with GET requests. Body carries the request body and is used mostly with POST or PUT requests. Headers carry request headers for special information. Custom variables can receive the output of preceding nodes as variables, and `{{}}` references variables inside Params, Headers, Body, and the URL itself. Variables come from global variables, system variables, and preceding node output. Returned values are not the interface response itself; they define how to parse the response, and JSON path syntax extracts the target value. From FastGPT v4.6.8, an output type of string converts the value at the corresponding key into a JSON string, which can then be passed to downstream nodes.

## Constraints at the HTTP integrations step

An interface returns fields under its own contract. Those fields do not automatically equal the filing basis for the declaration detail sheet. Authentication credentials are injected through secure configuration and are not written into public examples. Each variable reference has to be checked against the value actually passed in.

Two identity fields behave differently in test mode. `chatId` and `responseChatItemId` do not exist in test mode, so an empty value during debugging is a documented condition and not a business fault. `appId` is the application ID; `chatId` is the conversation ID within one application; `dataId` is a single exchange within one conversation. When `chatId` is a non-empty string, the conversation is taken from the FastGPT database and the last item of the messages array is used as the user question, with other messages ignored. When `chatId` is not passed, no FastGPT context is used and the context is built entirely from the supplied messages.

Retrieval and form collection do not constitute authorization. A relevance score is not a category, entity, or permission filter, and it does not exclude unrelated businesses or unauthorized records. Business verification, approval, database writes, and external synchronization each need their own downstream implementation. A form collects values; the values it collects are not verified filing data.

Hypothetical paper exercise. A producer-enterprise tax accountant reviews the February 2026 operating report in March 2026. The export contract text states: "Contract No. HT-2026-021, exporter is a domestic producer enterprise, goods are self-produced Type A fittings, trade term FOB, amount USD 120,000, signing date 10 February 2026." The customs export declaration text states: "Declaration No. 202602280001, export date 28 February 2026, trade term FOB, total price USD 118,000, domestic consignor is that producer enterprise." The sales detail ledger text states: "February 2026, Type A fittings export revenue USD 120,000, converted to CNY 864,000." The proposed sentence to be judged is: "February export revenue for this shipment is USD 120,000, consistent with the customs declaration, and the exemption-offset-refund declaration detail sheet may be filled at this amount." The contract and the ledger show USD 120,000; the customs declaration shows USD 118,000. These are different values in the same field. The word "consistent" in the proposed sentence is not supported, and the amount to be entered on the declaration detail sheet remains to be verified.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison object |
| --- | --- | --- |
| Request address | The address given in the external interface document | Compared character by character with the documented address |
| Request method | The method marked in the document | Compared with the documented method |
| Headers | Key-value pair containing Authorization | Compared with the authentication requirement |
| Body | JSON structure per the document | Compared with the interface contract fields |
| Variable reference | Reference to preceding node output | Compared with the value actually passed in |
| Return value extraction | Target field extracted by JSON path | Compared with the response structure |

These are hypothetical starting points for this exercise, not official default values.

The request address and method follow the external interface document, and the address can reference a supplied variable. Params and Headers are checked separately, with credentials injected through secure configuration. Body applies only under the corresponding request type, and its JSON structure is checked against the external interface contract. Variable references draw on global variables, system variables, and preceding node output, and each actual passed value is checked item by item. The debug identity fields are treated as documented conditions rather than faults.

## Three common errors

1. Treating the contract amount and the customs declaration amount as one value. Check by entering both source texts and comparing the trade term and total price fields. The coexistence of USD 120,000 and USD 118,000 shows that "consistent" in the proposed sentence is not supported.
2. Treating an empty `chatId` in test mode as an interface fault. Enter a test-mode request and compare whether `chatId` and `responseChatItemId` are present in the response. A missing value is a documented condition and does not constitute a business exception.
3. Treating an amount collected by a form as verified filing data. Enter the form return value and compare it with the customs declaration text. The two have different sources, and the form value does not constitute a filing basis.

## How to verify the setup

1. Enter the contract text and the customs declaration text given above, and compare the trade term and total price fields. When the two values differ, the "consistent" judgment in the proposed sentence is not supported, and the evidence gap is recorded.
2. Enter a test-mode request and compare whether `chatId` and `responseChatItemId` are present in the response. When absent, handle them as documented conditions and do not record a fault.
3. Enter an interface response containing a JSON structure, extract the target field by JSON path, and compare the extracted value with the response text. When they match, the extraction configuration holds. When the response is an empty array, downstream processing checks against an empty input and does not infer a retrieval result.
