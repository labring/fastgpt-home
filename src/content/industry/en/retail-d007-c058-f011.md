# Fresh-food supplier claims: database operations for operating reviews

## What the documents look like

Fresh-food supplier claims pursue responsibility for the quality of goods at arrival. They do not address ordinary in-store shrinkage. That boundary shapes what operating reports and exception reviews can be built from. Four source systems feed this work: quality inspection, WMS receiving, supplier contracts, and financial reconciliation. The recurring materials are quality exception forms, photographic evidence, deduction notices, and claim reconciliation statements. Two update rhythms coexist: per batch and per month.

At the database and operations step, the questions are narrow. Can these materials be read, compared, and retained consistently under the reporting basis? After a configuration change, does the same sample still produce the same result? Subjects, batches, statuses, and authorization boundaries originate in business systems. The database stores and retrieves; it does not replace business judgment.

## Constraints at the database operations step

Check database and cache connection settings against the chosen deployment plan. Do not infer a setting's purpose from its variable name. Keep the primary business data store and the vector retrieval backend as separate responsibilities, and verify each against the actual deployment. Judge connection and load behavior from observed connection counts, errors, and latency. Do not copy untested concurrency thresholds. Verify backup and recovery separately: a successful backup is not a usable restore. Retain a sample and a record that can be checked. After any database or service configuration change, re-check the same business sample. A running process does not constitute verification.

Hypothetical drill sample (paper materials, not real records): a quality exception form states "Subject: a supplier; Object: batch A received on 12 March 2024; Status: quality inspection judged non-conforming; Authorization scope: procurement may issue a deduction notice." A draft deduction notice for the same batch states "Proposed deduction amount calculated per contract terms, pending procurement review." A draft sentence awaiting judgment reads: "This batch's claim has been fully executed." That sentence conflicts with the source text. The deduction notice is pending review, no claim reconciliation statement appears, and no evidence supports an executed status.

## Three common errors

1. Treating a pending deduction notice as an executed claim. Input: the quality exception form and draft deduction notice above. Comparison: the draft sentence "has been fully executed." Observable result: the draft status and the draft sentence disagree, so the item is recorded as pending verification. The error is concluding without reading the status field.
2. Using retrieval similarity in place of authorization judgment. Input: a query for the same batch's quality exception form. Comparison: the retrieval results against the procurement authorization scope. Observable result: a high similarity score does not mean the user may issue a deduction. Retrieval does not perform permission filtering.
3. Confirming only that the process is alive after a configuration change. Input: the same batch sample before and after the change. Comparison: the batch, status, and amount fields read on both occasions. Observable result: only matching fields satisfy the re-check condition. A running process is not evidence.

## How to verify the setup

1. Check the draft sentence against the hypothetical sample. Input: the quality exception form, the draft deduction notice, and the draft sentence above. Comparison: "Status: quality inspection judged non-conforming" and "pending procurement review" against "has been fully executed." Observable result: the draft sentence has no support in the source text, so it is recorded as pending verification, not as a denial or a conflict.
2. Check downstream design with an empty result. Input: an explicit paper empty result. Comparison: whether the downstream report handles it as an empty set. Observable result: the downstream does not fabricate records, which satisfies the condition. No claim is made that any retrieval rule necessarily returns empty.
3. Check contradiction judgment using mutually exclusive values in the same field. Input: the status field for the same batch and the same period. Comparison: whether "non-conforming" and "conforming" appear together. Observable result: only mutually exclusive values in the same field constitute a contradiction. Evidence from a related stage alone is recorded as unsupported or pending verification.
