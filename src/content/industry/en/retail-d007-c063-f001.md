# Livestream after-sales service: HTTP integrations for operating reviews

## What the documents look like
Livestream after-sales work clusters after a single session's traffic, so refund requests and replacement orders stack up in a short window and stay closely tied to what the host promised on air. Operating reports and exception reviews draw on four document types: livestream order lists, refund requests, replacement orders, and script templates. Data sources include the shop's after-sales module, customer-service IM, warehouse WMS, and logistics tracking. The update rhythm is per session and daily, which means report reconciliation has to lock its scope by session or by day. At this step the HTTP module carries externally sourced records into the orchestration and then hands them to the reporting and review flow. Because those sources sit in separate systems, a request can only return the records it is authorized to reach, and a returned record does not by itself constitute business authorization.

## Constraints at the HTTP integrations step
The HTTP module sends a request to the corresponding address, and Params, Body, and Headers can each reference variables through `{{}}`. The URL can also reference variables. Variables come from global variables, system variables, and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories; histories takes at most 10 records by default and its length cannot be changed. chatId and responseChatItemId do not exist in test mode, so an empty value during debugging is a test-mode characteristic and does not indicate a business fault. Return values are extracted through JSON path, and when the output type is set to string, the value of the corresponding key is converted into a JSON string. The HTTP module can be added repeatedly, configured manually, and triggered to execute.

Hypothetical drill sample: a livestream room receives a burst of refund requests after its March 8 session, and the after-sales supervisor assembles materials on March 9. The source text reads: "For the March 8 session from 20:00 to 24:00, 46 refund requests were received, of which 12 were registered by customer service as replacement orders; the replacement orders are in the awaiting-warehouse-confirmation status, and the warehouse WMS has not yet returned any outbound result." The proposed judgment sentence is: "The 12 replacements for this session have been completed outbound by the warehouse." The handoff request awaiting judgment is: "Please sync this session's refund and replacement data to the reporting flow." That request is in a pending-confirmation state and does not constitute an authorized execution.

## Three common errors
1. Treating an empty chatId or responseChatItemId in test mode as a business fault. The input is a test-mode request; the object of comparison is the documented statement that these two fields do not exist in test mode; the observable result is that both fields are empty in the test-mode request while the caller supplies them in a formal request.
2. Treating refund or replacement records returned by the interface as an authorized execution. The input is the 12 replacement orders in the sample above; the object of comparison is the replacement-order status "awaiting warehouse confirmation" together with the warehouse WMS having returned no outbound result; the observable result is that the proposed judgment sentence "completed outbound" is not supported.
3. Treating a value extracted through JSON path as a confirmed business field meaning. The input is an extracted key value; the object of comparison is the external interface contract's definition of that field; the observable result is that when the field name matches but the meaning is not confirmed by the contract, only a pending-verification note can be recorded.

## How to verify the setup
1. For the source text in the hypothetical drill sample, the input is: "For the March 8 session from 20:00 to 24:00, 46 refund requests were received, of which 12 were registered by customer service as replacement orders; the replacement orders are in the awaiting-warehouse-confirmation status, and the warehouse WMS has not yet returned any outbound result." The object of comparison is the proposed judgment sentence: "The 12 replacements for this session have been completed outbound by the warehouse." The observable result is that neither the replacement-order status nor the warehouse return status shows completed outbound, so the judgment sentence is not supported and the evidence gap remains: the warehouse outbound result is unknown.
2. For the handoff request awaiting judgment, the input is: "Please sync this session's refund and replacement data to the reporting flow." The object of comparison is the authorization status of that request. The observable result is that the request is in a pending-confirmation state and does not constitute an authorized execution; whether the sync action occurs remains unknown.
3. For the HTTP module configuration, the input is the address, method, Params, Headers, Body, and return-value extraction filled in according to the external interface document. The object of comparison is the external interface contract and the documented variable sources. The observable result is that when a path exists the corresponding value is extracted, and when a path does not exist or the field meaning is not confirmed by the contract the item is recorded as unknown, without inferring the business meaning of the interface return value.
