# Livestream after-sales service: workflow routing for operating reviews

## What the documents look like

For livestream after-sales central processing, the working documents are the livestream order list, refund requests, reshipment orders and script templates. Data sources named in the brief are the platform after-sales system, customer service IM, warehouse WMS and logistics tracking. Compared with ordinary platform after-sales, livestream after-sales tends to break out in a concentrated way after a single session and is strongly tied to what the host promised. That shape matters for operating reports and exception reviews: refund requests can arrive together after one session ends, and the three most time-consuming steps are identifying refund surges, arranging reshipments for wrong or missing items, and giving one consistent explanation of what was promised. Update frequency is per session and daily.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user finishes interacting. Once the user fills the required information and submits, the node collects the submitted form information and passes it to later nodes. The user selection node is also a user interaction node. When the user makes a choice, the node evaluates that choice and executes the "yes" branch. Both nodes can be added repeatedly and trigger execution. Recording the interaction state is behavior of the interaction nodes; the documents do not describe a separate global state-recording switch.

Information collected at these nodes must be explicitly passed to later retrieval, decision or interface nodes. Order writes, document backfill and external status synchronization require a separate business interface or a later flow. Retrieval or form collection does not constitute authorized execution. Branch connections have to be checked one by one, because the node executes a branch according to the user's choice and the documents do not describe automatic branch validation.

## Configuration and implementation checks

The settings below apply to the hypothetical drill sample on this page. They contain only documented interaction-node behavior or implementation checks. Hypothetical drill sample: after the session of 20 June 2025 ends, a livestream customer service agent receives one refund request record whose source text reads: "Order number A-0620-017, buyer applied for a refund on 20 June at 22:15, reason 'host promised gift not sent', current status pending review." There is also one draft sentence awaiting judgment: "This refund request has passed review, and the reshipment order has been generated." The draft sentence has to be checked against the source text.

| Configuration item | Setting method | Check point |
| --- | --- | --- |
| Form input node | Enters interaction state on trigger, collects required information | Whether submitted information is passed to later nodes |
| User selection node | Executes the "yes" branch after the user makes a choice | Whether branch connections are verified one by one |
| Interaction state check | State recording is behavior of the interaction node | No separate global state-recording switch is set |
| Output handoff check | Pass collected information to later retrieval, decision or interface nodes | Compare output and input item by item |
| External action split | Order writes, document backfill and external status sync use a separate interface | Retrieval and forms are not treated as authorized execution |
| Hypothetical trial starting point | The hypothetical trial starting point is the status pending review | Compare with the source text "pending review" and confirm whether "has passed review" is satisfied |

Reason for choosing the hypothetical trial starting point: the source text states the current status is pending review, while the draft sentence claims review has passed. Both concern the same order and the same field with different values. Pending review is used as the comparison basis because it is the status value directly stated in the source text. The documents do not describe specific rules or default values for passing review or generating a reshipment order.

## Three common errors

1. Treating the pending-review status as already passed review. Input: the source text "current status pending review" and the draft sentence "this refund request has passed review". Compare the same status field of the same order. Observable result: the source text states pending review, the draft sentence claims review has passed, the two values differ, and the draft sentence is not supported by the source text. Pending review does not show a lack of operating permission, and it does not equal passed review.

2. Treating information collected by the form as an external action already executed. Input: refund request information collected by the form input node. Compare that information with external actions such as order writes and reshipment order generation. Observable result: the form node only collects and passes information, and the documents do not describe it automatically performing order writes or reshipment order generation. External actions require a separate business interface or a later flow.

3. Treating a retrieval result or similarity score as a permission or entity filter. Input: a refund request record returned by retrieval. Compare that record with the current operator's authorization scope. Observable result: retrieval returns relevant text and does not decide whether the record falls within the business scope the current operator is authorized to handle. A similarity score is not a permission filter, and retrieval does not constitute authorization.

## How to verify the setup

1. Input the hypothetical drill sample source text "Order number A-0620-017, buyer applied for a refund on 20 June at 22:15, reason 'host promised gift not sent', current status pending review" together with the draft sentence "This refund request has passed review, and the reshipment order has been generated." Compare the status description in the draft sentence with the status field stated in the source text. Observable result: the source status is pending review, the draft sentence claims review has passed, the two do not agree, and the draft sentence is not supported by the source text. The expected condition is that the draft sentence agrees with the source status; the current source text does not support this draft sentence.

2. Input the refund request information collected by the form input node. Compare whether that information is explicitly passed to later retrieval, decision or interface nodes. Observable result: if the information stays at the form node and is not passed to later nodes, the output handoff is incomplete. The expected condition is that the collected information explicitly appears in the input of later nodes. The documents do not describe an automatic passing mechanism, so node connections have to be checked manually.

3. Input a refund request record returned by retrieval. Compare that record with the current operator's authorization scope. Observable result: if the record returned by retrieval falls outside the business scope the operator is authorized to handle, the retrieval result does not serve as a basis for authorization. The expected condition is that the operator handles only records within the authorized scope. The authorization scope has to be provided by the business system, and the documents do not describe a permission filtering function in the retrieval node.
