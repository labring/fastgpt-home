# Livestream violation appeals: tool calls for operating reviews

## What the documents look like

Livestream violation appeals deal with penalties that have already been issued. The working materials are the violation notice, the livestream recording, the product qualification files and the appeal statement. A new round of document assembly starts each time a violation occurs, and the update cycle is irregular rather than scheduled. For operating reports and exception review, the task is to line up the violation timestamp, the product involved, the penalty type and the appeal evidence chain so that store compliance, livestream operations and legal staff can hand the file over and check it against one another.

Tool calls and plugins sit inside this step. Their role is to let the model decide, from the content of the materials, whether to invoke a module or a plugin, for example reading a recording note or comparing a qualification record, and then pass the result to later nodes. The tool description tells the model what the tool is for, and the model uses that description to judge when a call is appropriate. Tool parameters divide into fixed parameters for system modules and configurable parameters for plugins. The parameter description and the required flag together affect whether the model issues a call. Retrieval is not authorization, and a form that collects values does not by itself perform business verification, approval, database writes or external synchronization.

## Constraints at the tool calls step

Appeal materials arrive in very different states. A violation notice may be at the pending-appeal stage, the appeal-submitted stage or the penalty-issued stage. A recording may cover only a fragment. A qualification file may be past its validity date. A tool call must not treat "a material was retrieved" as "that material has been accepted as appeal evidence." When a suitable required parameter is missing, the model may choose not to call the tool; the parameter then has to be completed through interaction, and the actual request content has to be checked. A tool call termination node attached after a tool forces this tool call to end, so no further tools are called and the AI is no longer asked to summarize the tool result. Custom tool variables can bring in nodes that are not treated as tool parameters or cannot be called as tools, and the corresponding parameter description has to be filled in.

Hypothetical drill sample: the source text to be checked has three sentences. Sentence one: "Violation notice number V-2024-0317, subject is a store, violation object is the livestream explanation segment for product A, penalty status is pending appeal, notice date 17 March 2024." Sentence two: "Livestream recording file is marked with the period 15 March 2024, 20:10 to 20:22, and the frame contains the price display for product A." Sentence three: "The qualification certificate for product A is valid until 28 February 2024." One draft sentence to be judged: "The qualification for product A was valid on the date of the violation and can be submitted as appeal evidence." In this sample the qualification expiry date falls before the violation date, so the draft sentence and sentence three take mutually exclusive values on the same field, and the draft sentence is unsupported.

## Three common errors

1. Treating a retrieved qualification file as evidence already in effect. The input is sentence three, "valid until 28 February 2024." The comparison object is the violation date of 15 March 2024. The observable result is that the expiry date falls before that date, so the draft sentence "the qualification was valid on the date of the violation" is unsupported.

2. Treating a pending-appeal status as a completed appeal. The input is sentence one, "penalty status is pending appeal." The comparison object is a completed state such as appeal submitted or penalty issued. The observable result is that the status field holds a different value, so it cannot be concluded that an appeal has been submitted or completed.

3. Reading tool call termination as automatic generation of a conclusion. The input is a termination node attached after the violation notice reading tool. The comparison object is the documented behavior of no longer calling the AI summary. The observable result is that the later summary node is not executed, and this does not mean an appeal reason has been written automatically.

## How to verify the setup

- Check one: input sentence one together with the draft sentence "The qualification for product A was valid on the date of the violation and can be submitted as appeal evidence." Compare the qualification validity field of 28 February 2024 with the violation date of 15 March 2024. The expected observation is that the expiry date falls before the violation date and the draft sentence is unsupported, while the evidence gap remains open as to whether the qualification covered the violation period.

- Check two: input sentence one, "penalty status is pending appeal." Compare the status field against the values appeal submitted and penalty issued. The expected observation is that the values differ, so it cannot be concluded that an appeal has been submitted or completed; a pending review does not demonstrate a lack of operating permission.

- Check three: input the tool connection setting "connect only the violation notice reading tool" together with the termination node position. Compare whether the actual request calls only that tool and whether no AI summary follows termination. The expected observation is that the request carries V-2024-0317 and that no summary output follows termination. If a required parameter is missing, record that the model did not call the tool, complete the parameter through interaction, and then check the actual request again. Retrieval and similarity scores do not carry permission or entity isolation, libraries built on different vector models cannot be associated together, and the check is limited to confirming identifiers and excluding non-matching records.
