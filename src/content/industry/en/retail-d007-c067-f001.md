# Group-buy leader operations: HTTP integrations for operating reviews

## What the documents look like

Group-buy leader operations manage community nodes and commission rather than cold-chain inspection. The working materials are leader agreements, commission tables, pickup lists and community announcements, drawn from the group-buy backend, leader chat groups, order details and after-sales records. Updates arrive daily or per group. For operating reviews and exception replay, the task is to line up order, commission, pickup and after-sales states from those materials against the requests and responses of an external interface. Community complaints and leader churn tend to follow mis-shipments, missed shipments and commission reconciliation gaps, so the review must keep each document's own status field intact instead of reading a later stage into it.

A paper exercise sample is used throughout this page. It is hypothetical and was not run against any live system. The leader agreement text states: "This agreement takes effect on the date both parties sign. Commission is settled by calendar month, and the basis for settlement is the order details in the platform backend." A March commission table lists leader A with 120 orders and a commission of 600 yuan, and its status column reads "pending review." A pickup list dated 5 March lists 30 items, and its signature column is blank. A draft sentence reads: "Leader A's March commission is confirmed and payment can be initiated." A pending request reads: "Please update leader A's March commission status to settled through the external interface."

## Constraints at the HTTP integrations step

The HTTP module sends a request to a given address. Params carry path request parameters, Body carries the request body, and Headers carry request headers. All three can reference variables with `{{}}`, and the URL can also reference variables. Available variables come from global variables, system variables and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime and histories; chatId and responseChatItemId do not exist in test mode, so an empty value there is a debug condition rather than a business fault. Response values are extracted with JSON path syntax, and when the output type is set to string the value is converted to a json string.

The chat endpoint authenticates with an APIKey. When calling chat/completions, passing body.appId in the request body is recommended, and `Authorization: Bearer <apiKey>-<appId>` is also supported. The appId priority order is body.appId, then `<apiKey>-<appId>`, then the appId associated with the apikey under the older adaptation. Fields such as model and temperature passed in the request have no effect because the orchestration decides them. With detail=true, non-stream results are held in responseData and stream results are distinguished by event. An interactive node returns interactive containing only type and params; entryNodeIds, memoryEdges, nodeOutputs and nodeResponseId are not returned. Retrieval and forms that collect values do not constitute authorization. Business verification, approval, database writes and external synchronization each need their own downstream implementation.

For this page's task, the commission table's "pending review" status is a stage marker, not proof that an operator lacks permission to act. The blank signature column on the pickup list is a missing-evidence gap, not a finding of mis-shipment. The pending request asks for a status update, and no authorization boundary statement accompanies it, so the request stays pending.

## Three common errors

1. Treating pending review as confirmed. The commission table's status column reads "pending review" while the draft sentence says "confirmed and payment can be initiated." Both statements take values on the same field, and those values are mutually exclusive, so the pair is contradictory.
2. Treating a blank signature as signed. The pickup list's signature column is blank, so signed receipt evidence is absent and neither mis-shipment nor completed pickup can be concluded from it.
3. Treating retrieval or a form as authorized execution. The pending request asks for a commission status update. A form collects values only; updating status needs a downstream implementation, and the request on its own does not carry authorization.

The corresponding checks are as follows. First, take the commission table text and the draft sentence as input, compare the value of the status field, and mark a contradiction when "pending review" and "confirmed" appear together. Second, take the pickup list text as input, compare whether the signature column holds a value, and when it is empty record an evidence gap without concluding mis-shipment. Third, take the pending request and the authorization materials as input, compare whether an authorization boundary statement exists, and when it is absent record the item as pending verification and do not execute the status update.

## How to verify the setup

- Verification one: take the leader agreement text and the draft sentence as input, compare the agreement's effective condition against the draft sentence's "confirmed" wording, and when the agreement states only that it takes effect on signing and does not describe a commission confirmation process, judge the sentence unsupported.

- Verification two: take the March commission table text as input, compare the order count against the commission amount, and when the two cannot be derived from the text, record the item as pending verification without supplying a calculation rule.

- Verification three: take the pending request and the pickup list as input, compare the requested status update against the list's signature state, and when the signature column is blank judge the evidence insufficient and do not execute the update.

All three verifications use the hypothetical sample above as input, and the expected results are a contradiction finding, an evidence gap, or an unsupported judgment; no live test is claimed. An empty result can be checked against downstream design using the paper input []. Retrieval and relevance scores do not perform permission or entity isolation, and libraries built on different vector models cannot be associated together; only identifiers are checked and non-matching items are excluded. Where the source documents do not state a system error or an automatic business action, that behavior remains unknown.
