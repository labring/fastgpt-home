# Group-buy presale orders: HTTP integrations for operating reviews

## What the documents look like

Presale group buying collects orders first and organizes procurement and fulfillment afterward. The operating review for this category therefore has to read four documents together: the presale product table, the group-order result, the procurement plan, and the cut-off notice. Data arrives from mini-program orders, supplier inventory, group-leader feedback, and warehouse routing. The review step described here sits at the HTTP integration layer, so the values under examination come from an external response, and the objects to compare are the request that was sent and the response that came back. A field that the source material does not state stays unknown.

The material identities matter because each document carries a different field. The group-order result carries an order count and a shortage count. The procurement plan carries a purchase quantity and an arrival date. The cut-off notice carries a cut-off time. A statement about refund completion is a different field from a shortage count, and it stays unsupported unless the material states it.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a configured address. Params hold path request parameters and are common in GET requests. Body holds the request body and is common in POST and PUT requests. Headers carry special information. All three can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and outputs of preceding nodes.

System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. In test mode, chatId and responseChatItemId do not exist. A returned value is extracted through JSON path syntax, and when the output type is set to string, the value is converted to a json string. The chat completion interface uses APIKey authentication, and when calling chat/completions the recommended approach is to pass body.appId in the request body. It also supports `Authorization: Bearer <apiKey>-<appId>`, in which case body.appId is not required. Some SDKs need a `v1` path on BaseUrl and some do not; a 404 can be retried with `v1` added.

Parameters such as model and temperature passed to the chat interface have no effect, because the orchestration decides them. When detail is true, non-stream results are stored in responseData, and in stream mode the results are separated by event. The HTTP module can reach external APIs, operate a database, call an external data source, run a web search, or send email. These are business actions that need their own downstream implementation; the module itself does not perform them.

Hypothetical drill sample: a platform operator reviews a presale on 10 June 2025 for a session held on 9 June 2025. The source material reads: "Cut-off notice: cut-off at 20:00 on 9 June, group-order result totals 1,200 orders, of which 30 are short." "Procurement plan: purchase against 1,200 orders, arriving at the warehouse on 10 June." The draft sentence to be judged is: "The 30 shortage refunds for this session are complete." That sentence shares only the shortage quantity field with the group-order result. The refund completion status is not stated in the material, so the sentence is unsupported.

## Three common errors

1. Writing "the 30 shortage refunds are complete" from the material phrase "30 are short." The input is the shortage count in the group-order result; the comparison object is the refund completion status; the two are different fields; the material does not state the refund status, so the draft sentence is unsupported.

2. Treating an empty chatId in test mode as a lost session. The input is a test-mode request; the comparison object is whether chatId exists; the document states that chatId does not exist in test mode; an empty value is expected behavior.

3. Omitting quotation marks when referencing a string variable in Body. The input is `{{string}}`; the comparison object is the final parsed result; the document requires `""` around a string reference; omitting them produces a structure that does not match the contract.

## How to verify the setup

1. Take the hypothetical sample material and the draft sentence "The 30 shortage refunds for this session are complete." Compare the shortage quantity field with the refund status field. The sentence is supported only when the material also states the refund completion status. The current observation is unsupported.

2. Send one test-mode request and compare the chatId value. The document states that chatId does not exist in test mode. An empty chatId matches the expectation and is not recorded as a business fault.

3. Take a Body declaration that references a string variable and compare the final parsed result. The document requires `""` around a string reference. A parsed result with the correct string type satisfies the condition; a type mismatch is recorded as pending verification.
