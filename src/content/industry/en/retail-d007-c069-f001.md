# Dealer rebate calculation: HTTP integrations for operating reviews

## What the documents look like

Dealer rebate calculation happens after sales close. The work centers on policy interpretation and financial treatment rather than on replenishment planning. The source records are ERP sales entries, dealer remittances, contract ledgers, and the finance system. The documents handled day to day are rebate policies, volume achievement tables, reconciliation statements, and red-letter invoices. Update frequency is monthly or quarterly, and that cadence shapes the review window rather than the interface behavior itself.

For the HTTP integrations step, these characteristics fix what must be reconciled. The achievement quantity, the returned-goods deduction, and the invoicing offset status that arrive through an interface must correspond item by item with the policy text, the reconciliation statement, and the finance records. The interface transmits and extracts values. Rebate amount calculation, approval, and ledger writes are implemented by downstream business systems.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a given address. Params carry path parameters, used mostly with GET requests. Body carries the request payload, used mostly with POST and PUT requests. Headers carry special information. All three can reference variables through double curly braces, and the URL can reference variables as well. Variables come from global variables, system variables, and outputs of preceding nodes. Return values are extracted with JSON path syntax, and when the output type is set to string, the value for the corresponding key is converted into a JSON string.

chatId and responseChatItemId do not exist in test mode. Reading an empty value during debugging matches documented behavior and does not constitute a business failure. For the chat completions interface, fields such as model and temperature that are passed in have no effect, because the orchestration decides them. When detail=true, intermediate values are kept in responseData, distinguished by field in non-stream mode and by event in stream mode. A relevance score is not a category, entity, or permission filter, and retrieval is not authorization.

Hypothetical drill sample: a brand finance reviewer holds a reconciliation statement during a quarterly rebate review. The statement text reads: "For the third quarter of 2024, dealer A's rebate policy is calculated at 2% of remittance amount, and returned-goods amounts are deducted from the achievement amount; as of 30 September 2024, the reconciliation statement lists remittances of 5,000,000 and returns of 200,000, with the rebate amount pending finance review before confirmation." The proposed handoff request is: "Please use the reconciliation interface to write this quarter's rebate amount into the finance system and mark it approved." That request involves approval and a write. The interface itself does not perform approval, and the authorization status and downstream implementation must be checked.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this drill | How to check |
| --- | --- | --- |
| Request address and method | Fill according to the external reconciliation interface document; the address references a global variable | Compare against the path and method in the interface document |
| Headers authentication | Inject credentials through secure configuration; do not place them in the public sample | Check the credential source and the target application permission |
| Body structure | Build JSON according to the reconciliation interface contract, referencing preceding node output | Compare each field name against the interface document |
| Variable references | Reference global variables and preceding node output | Check actual passed values against the reconciliation statement text |
| Return value extraction | Extract rebate amount and status fields by JSON path | Compare the response structure with the extraction key |
| Output type | String, for downstream text processing | Check the converted content against the original value |

These starting points are fill positions for this hypothetical drill. They are not official default values. The reason for choosing them is that the quarterly reconciliation statement contains explicit fields that can be referenced.

## Three common errors

1. Treating "mark it approved" in the proposed handoff request as an action the interface can complete. The interface sends a request and extracts a response; approval and the write require downstream system implementation. Check: input the proposed sentence, compare the action in the sentence with the interface document's capabilities, and if the interface document does not describe an approval field, record it as pending verification.
2. Treating an empty chatId in test mode as a lost-session failure. Check: input a test-mode request, compare against the document statement that the field does not exist in test mode, and if the value is empty and the document already states this, record it as matching documented behavior.
3. Treating a string output from return value extraction as a confirmed rebate amount. Check: input the response sample, compare the extraction key with the reconciliation statement fields, and if the extracted value is only a number returned by the interface, record it as pending finance review.

## How to verify the setup

1. Input the hypothetical reconciliation statement text and the proposed handoff request. Compare "write into the finance system and mark it approved" in the request with the interface document description. The observed result is that the interface document does not describe an approval action. Judge it as pending verification, and preserve the evidence gap.
2. Input a test-mode request. Compare chatId and responseChatItemId against the document description. The observed result is that the fields do not exist. Judge it as matching documented behavior, and do not record it as a business failure.
3. Input the response sample and the extraction configuration. Compare the JSON path extracted value with the remittance and returns fields in the reconciliation statement text. The observed result is that the extracted value can correspond to the source numbers, while the rebate amount still requires finance review. Judge it as interface transmission complete and business confirmation incomplete.
