# Cross-border product labels: retrieval for operating reviews

## What the documents look like

Cross-border product compliance and labelling draws on four document families: product test reports, English-language labels, MSDS files, and platform prohibited-item lists. These materials take shape before listing and import. The recurring work is judging destination-country requirements, arranging additional testing, and revising packaging labels. Updates arrive irregularly, and each new product launch starts a fresh round of material changes. Operating reviews and exception retrospectives compare the evidence version returned by retrieval against the current batch.

The knowledge base search node can associate one or more knowledge bases that use the same vector model. The smallest search unit is the library; a collection only classifies data and does not affect search results. One data group can map to multiple vectors, and a hit on any one vector recalls that group, with the vector score taken as the highest score. Quoted content is output as an array, and its length can be zero, so the output path still completes when nothing is found.

## Constraints at the retrieval step

Hypothetical drill sample: a batch of portable power banks is intended for export to the European Union. The source material reads: "Supplier A provided the UN38.3 test report on 12 March 2025, report number TEST-2025-0312, covering model PB-10000, with a pass conclusion." The English label draft for that model states a rated capacity of 10000mAh, is written in English, and carries no official-language version for the destination country. The April 2025 platform prohibited-item list places lithium-battery products in a category requiring additional review, and the review status is pending platform confirmation. The draft sentence under judgment is: "This batch holds all compliance documents required for EU listing, and both label and prohibited-item review have passed."

Retrieval must compare whether the model covered by the test report matches the batch model named in the draft; whether the label draft language matches the destination-country official-language requirement; and whether the prohibited-item review status of pending platform confirmation matches the claim that review has passed. Retrieval results do not carry authorization. Recalling a related material does not mean a business review is complete. Knowledge bases using different vector models cannot be associated together; their identifiers must be checked first and non-matching ones excluded. Image retrieval requires an image input and the corresponding model capability, and reranking requires a model enabled under the settings. Optional paths shown in the document flow diagram do not mean every request executes all of them.

## Three common errors

1. Treating recalled material as business authorization. In the sample, the prohibited-item review status is pending platform confirmation. Retrieving that list only shows the material exists, while the draft sentence "both review have passed" lacks a passing record in the same field. Check: input the draft sentence and the list source text, compare the review status field, and observe whether a value mutually exclusive with "passed" appears, such as pending platform confirmation.
2. Associating knowledge bases across vector models. Check: examine each library's vector model identifier, compare the association list against those identifiers, exclude non-matching ones, and record what is actually observed. Do not run a cross-model search to compare missed recalls.
3. Confusing test report coverage with batch scope. In the sample, the report covers model PB-10000 while the draft sentence claims the batch. Check: input the report source text and the batch model, compare the coverage model field, and observe whether the same subject and the same field are involved.

## How to verify the setup

1. Input the test report source text and the draft sentence from the hypothetical sample, compare the report coverage model against the batch model named in the draft, and observe whether the two model values agree. When they agree, the sentence is supported; when they differ or the field is absent, record it as pending verification.
2. Input the English label draft and the destination-country official-language requirement, compare the label language field, and observe whether an official-language version exists. When it is absent, record the evidence gap without supplying authorization or effective clauses.
3. Input the prohibited-item list source text and the draft sentence "both review have passed", compare the review status field, and observe whether the value is pending platform confirmation. When it is pending, the sentence is not supported and the gap is retained. For empty-result handling, a clearly written paper input of [] can be used to check downstream design; do not claim that a fabricated rule search necessarily returns [].

The checks above compare specific proposed sentences against supplied source wording and its stated limitations. They do not test identity certification, report analysis, or any other task. Where a field is not provided, it remains unknown. A pending request is not approval, an offered option is not execution, and an unsigned termination is not a completed termination.
