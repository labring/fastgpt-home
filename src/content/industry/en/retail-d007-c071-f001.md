# Cross-border settlements: HTTP integrations for operating reviews

## What the documents look like

Cross-border platform settlement and foreign exchange work concerns the collection of funds from completed orders. The materials are platform settlement statements, bank transaction records, payment institution back-office exports, and ERP order data. The settlement statement states the settlement period, the store entity, the currency, and the platform service fee total. The receipt reconciliation table states the same store entity, the same period, and the amount received. A rate table and a service fee invoice supply the conversion basis and the fee document number.

The operating review task compares these materials for the same entity, the same period, and the same field. The HTTP integration carries the fetch and write-back channel. It does not decide fraud or chargeback questions, which belong to a different category. Data updates weekly or monthly, so a review cycle follows that rhythm rather than a per-transaction trigger.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a configured address. Params carry path parameters, Body carries the request body, and Headers carry request headers. All three can reference variables through `{{}}`, and the URL can also reference variables. Variables come from global variables, system variables, and preceding node outputs. Return values are extracted with JSON path syntax; when the output type is set to string, the value at the corresponding key is converted to a JSON string.

Among the system variables, chatId and responseChatItemId do not exist in test mode. An empty value for these fields during debugging is an environment difference, not a business fault. In the chat interface, a non-empty chatId string causes the system to read the session from the database and treat the last item in the messages array as the user question; the remaining messages are ignored. With detail=true and stream=false, the intermediate results are stored in responseData. Authentication uses an APIKey. The appId priority order is body.appId, then `<apiKey>-<appId>`, then the appId associated with the apikey. Retrieval and similarity scores do not constitute authorization. Forms collect values only; business verification, approval, database writes, and external synchronization each require their own downstream implementation.

Hypothetical paper test case. A cross-border seller's finance staff member prepares a March 2025 monthly review. The available materials are: a platform settlement statement stating a settlement period from 1 March 2025 to 31 March 2025, a settlement entity of Store A, a currency of US dollars, and a platform service fee total of 1,200.00 US dollars; and a receipt reconciliation table stating the same Store A, the same period, and a received amount of 8,800.00 US dollars. The draft sentence under review is: "The platform service fee for this period has been verified and can be carried into profit calculation." This sentence does not state the rate table version or the service fee invoice number, and the materials contain no authorization signature or approval record. The draft sentence therefore remains pending verification.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Reason and comparison method |
| --- | --- | --- |
| Request address | The settlement statement query address provided by the external settlement system | The address comes from the external interface document; this starting point follows that document and is compared character by character against the declared path |
| Request method | POST | Filled according to the method declared in the external interface document; compared against the declared method |
| Headers authentication | Authorization references a configured token variable | The credential is injected through secure configuration; compared against the actual variable value passed in, and not written into a public sample |
| Body structure | JSON containing settlement period and store identifier fields | Field names and types are checked against the external interface contract, item by item against the counterparty document |
| Return value extraction | A key configured for the service fee total, output type string | Extracted by JSON path; compared against the value in the settlement statement text |
| Variable reference scope | Global variables, system variables, preceding node outputs | Each item is checked against the actual value passed in and compared against the node output record |

These values and structures are the hypothetical trial starting point for this exercise. They are not official defaults and have not been executed.

## Three common errors

1. Treating an empty chatId or responseChatItemId in test mode as a business failure. Check: send a test-mode request, compare whether these two fields are present in the response, and observe whether the empty value matches the documented statement.

2. Treating a similarity score or retrieval result as an authorization or entity-isolation basis. Check: submit a query containing Store A, compare the entity identifiers in the returned records, and observe whether records outside Store A appear.

3. Treating a value collected by a form as already verified or approved. Check: input the draft sentence from the hypothetical sample, compare whether an approval or signature record exists in the materials, and observe whether the sentence remains pending verification.

## How to verify the setup

1. Input the settlement statement text and the draft sentence from the hypothetical sample. Compare whether the draft sentence states the rate table version and the service fee invoice number. Observe whether the missing fields in the materials remain marked as unknown.

2. Input the receipt reconciliation table from the hypothetical sample. Compare whether the received amount and the settlement statement service fee belong to the same entity, the same period, and the same field. Observe whether the two can be subtracted directly; if the field definitions differ, record the item as pending verification.

3. Input a paper response containing an empty result `[]`. Compare whether the downstream node handles it as an empty array. Observe whether a definite business conclusion is drawn from the empty result. Whether retrieval matches and whether an unrelated query returns empty are matters for actual observation and carry no guarantee.

This page addresses only the cross-border platform settlement and foreign exchange category, the operating review and exception review task, and the HTTP integration feature. During operational handover, the authorization status of materials, operations, and requests must be stated explicitly. Retrieval results and form values do not constitute authorization to execute.
