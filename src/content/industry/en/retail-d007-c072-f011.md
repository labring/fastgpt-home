# Overseas stock replenishment: database operations for operating reviews

## What the documents look like

Third-party overseas warehouses can serve several sales channels at once, and the seller allocates stock across those channels. This is the main difference from first-party marketplace stocking, where the platform holds and assigns inventory. Because allocation sits with the seller, replenishment planning, inbound appointment, inventory age, and last-mile delivery documents all enter the operating review together. Weekly and daily update rhythms are documented for this category, so the same batch of stock can appear at different timestamps across documents. Before any comparison, confirm that the records belong to the same entity, the same period, and the same field.

The four recurring documents are the replenishment plan, the inbound appointment, the inventory age table, and the last-mile delivery order. Data sources named in the category brief are the overseas warehouse WMS, ERP sales forecasts, freight forwarder systems, and carrier bills. The database and operations layer stores, retrieves, and compares these materials. It does not replace business authorization, and it does not decide whether a plan is approved or an appointment is confirmed.

## Constraints at the database operations step

Retrieval association depends on the same vector model identifier. Libraries built on different vector models cannot be associated together. A relevance score is not a category, entity, or permission filter; a high score does not mean the record is authorized for a given operator, and it does not mean an inbound appointment is approved or a replenishment plan has taken effect. Retrieval is not authorization. Connection configuration, backup and recovery, and post-change review each need item-by-item checks against the actual deployment plan. A configuration value cannot be inferred from a variable name.

A paper exercise sample is used below. It is hypothetical and does not describe a real customer, warehouse, or authorization.

Material text, hypothetical: "Entity: Warehouse A operations group; Object: SKU-001; Period: 2026-03-01 to 2026-03-31; Status is pending review; Effective scope: Channel B only."

Draft sentence to be judged: "The Warehouse A operations group received approval for SKU-001 replenishment in March 2026."

The material states a pending review status. The draft sentence states approval. The two statements are not the same field value, and the material does not support the draft sentence. This remains an evidence gap rather than a confirmed conflict, because the material does not record any later approval event.

The DB_MAX_LINK value of 10 is chosen only because the official document states that the connection pool maximum is automatically limited to the range 10 to 1000. The value 10 is the lower bound of that documented range, used here as a paper starting point, and it must be compared with the connection count observed under the deployment's own load. It is not an official default and it is not a tested threshold.

## Three common errors

1. Writing a pending review status as approved. Input: the hypothetical material text above. Comparison: the status field. The material records pending review, the draft sentence records approval, and the observable result is that the status field values differ.
2. Treating a retrieval relevance score as a permission filter. Input: one retrieval request. Comparison: the retrieval return against the authorization scope. If score level is treated as a right of access, the observable result is that an out-of-scope access risk is not identified.
3. Inferring a connection value from a variable name. Input: the connection address recorded in the deployment plan. Comparison: the configured value against the plan record. If the value is filled from the name alone, the observable result is that the connection address does not match the plan.

## How to verify the setup

1. Take the hypothetical material text above. Input the draft sentence "The Warehouse A operations group received approval for SKU-001 replenishment in March 2026." Compare the status field value "pending review" with "approved." The condition is satisfied only when the two agree. The expected result for this review is disagreement, which counts as unsupported by the material.
2. Take the same material text. Input the handover request "Please execute replenishment as approved." Compare the material status with the premise of the request. The condition is satisfied only when the material records approval. The expected result for this review is pending verification, because the authorization boundary is not closed.
3. Take the configuration table above. Input the hypothetical MONGODB_URI value and the deployment plan record. Compare whether the two match character by character. The condition is satisfied only when they match. The expected result for this review is that the value must be checked against the actual deployment, and where the record is missing, the gap remains open.

For retrieval checks, describe what is observed and what failure branch applies. Do not assert that the first result always matches, that all relevant records are always recalled, or that an unrelated query always returns empty. An empty result can be checked against a clearly stated paper input of an empty list for downstream design, without claiming that a fictional rule always returns an empty list. Where libraries use different vector models, first check the model identifier and exclude the non-matching library; do not run a cross-model retrieval to compare missed recalls. The optional paths in the overall document flow do not all execute on every request: image retrieval requires a corresponding image input and model capability, and reranking requires a model and must be enabled by configuration.
