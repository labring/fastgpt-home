# Creator sales campaigns: HTTP integrations for operating reviews

## What the documents look like

Creator sales campaigns run on external creator fulfillment and commission settlement rather than internal brand scheduling. Brand business teams, MCN agencies, and creator managers all take part. Operating reviews and exception reviews have to align four external data sources (selected alliance, Juliang Xingtu, creator history, and store transaction details) with four internal documents (creator cooperation agreements, commission setting sheets, sample shipment sheets, and livestream battle reports) on a per-session basis. Each livestream session produces a batch of settlement records awaiting reconciliation, and weekly rollups frequently show differences in how figures are defined. The HTTP integration step brings external system return values into the workflow so reports and reviews can compare them; the interface itself does not change any settlement status.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a target address. Params carry path request parameters and are used mostly with GET. Body carries the request body and is used mostly with POST/PUT. Headers carry special information. The URL and all three data types can reference variables through `{{}}`, drawing on global variables, system variables, and preceding node outputs. Return values are extracted through JSON path syntax or JS object access rules; when the output type is set to string, the value at the corresponding key is converted to a JSON string. Among system variables, chatId and responseChatItemId do not exist in test mode. For the chat API, fields such as model and temperature are determined by the orchestration and do not change with API parameters.

Hypothetical exercise sample: A brand business team retains the original text of a creator cooperation agreement, which states "This agreement takes effect on the date both parties sign it, and commission is calculated according to the settlement basis confirmed in the livestream battle report." In the same batch, a commission setting sheet records "The commission rate for this session is pending operations review before confirmation," and a sample shipment sheet records "The sample has been sent; the receipt status has not been returned." A draft handover request awaiting judgment reads: "The cooperation agreement is in effect, the commission rate is confirmed, and settlement can proceed directly per the battle report." Judgment requires comparing the same subject, the same period, and the same field: agreement effectiveness and commission rate confirmation belong to different fields. The pending-review status shown on the commission setting sheet and the "confirmed" claim in the draft sentence point to the same field with mutually exclusive values, so that clause in the draft is not supported. The sample receipt status has not been returned, which is an evidence gap and remains unknown.

## Configuration and implementation checks

The table below lists documented settings or implementation check items tied to this sample. Numeric values are hypothetical starting points for this exercise only.

| Request address and method | Chosen per the external interface document; the address references a variable through `{{}}` | Compare character by character against the path stated in the interface document |

## Three common errors

1. Treating agreement effectiveness as equivalent to a confirmed commission rate. The input is the agreement text and the commission setting sheet; the comparison is between the "effective" field and the "pending review" field; the observable result is that the "confirmed" claim in the draft sentence has no corresponding evidence.
2. Treating successful HTTP return value extraction as completed business authorization. The input is the interface response and the extraction configuration; the comparison is between data reading and approval status; the observable result is that a returned value does not mean settlement has been approved.
3. Treating a missing chatId in test mode as an interface fault. The input is a test-mode request; the comparison is against the system variable documentation; the observable result is that this variable does not exist in test mode by design.

## How to verify the setup

1. Take the agreement text and the draft sentence from the sample. Compare the "effective" field with the "confirmed" field. If the two point to different fields and the setting sheet shows pending review, the draft sentence is not supported, which is the expected outcome.
2. Take the interface response example and the extraction configuration. Compare the key and the output type. If the extracted value matches the response example, the extraction configuration is correct. If an empty array [] is returned, check the downstream design for handling it, and do not infer that a retrieval rule must return empty.
3. Take the test-mode request and the system variable documentation. Compare whether chatId exists. If the value does not exist in test mode, record it as a documented phenomenon and exclude it from business exceptions.

All three items are paper checks and were not actually executed.
