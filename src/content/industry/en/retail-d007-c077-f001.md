# Import and export permits: HTTP integrations for operating reviews

## What the documents look like

Import and export permit handling happens before customs declaration and determines whether a shipment may lawfully cross the border. Working materials include automatic import licences, dual-use item licences, contracts and product descriptions. They come from commerce authority systems, customs commodity codes, supplier materials and customer end-use statements. Each shipment requires a fresh judgement about which regulatory certificate applies, and the material updates irregularly, once per shipment rather than on a fixed cycle.

For operating reports and exception reviews, the practical question is where a given permit case is sitting, who is following it, and what status it currently holds. At the HTTP integrations step these materials enter and leave as request parameters, request bodies and extracted return values. The review task is to compare what was actually passed against the external interface contract, and to keep the reported status tied to the source material.

## Constraints at the HTTP integrations step

The HTTP module sends a request to a configured address. Params carry path request parameters and are common in GET requests. Body carries the request body and is common in POST and PUT requests. Headers carry special information. All three data positions, and the URL itself, can reference variables through `{{}}`. Variables come from global variables, system variables and upstream node outputs. System variables include appId, chatId, responseChatItemId, variables, cTime and histories; histories defaults to at most 10 entries and its length cannot be changed. chatId and responseChatItemId do not exist in test mode.

Return values configured in the module do not represent the interface return value itself. They configure how the interface response is parsed, using JSON path syntax to extract values. From FastGPT v4.6.8, output formatting mainly converts json to string: when the output type is string, the value at the corresponding key is converted to a json string. In the chat interface, a passed model or temperature field has no effect, because orchestration decides those. Actual token consumption is not returned; setting detail=true allows manual calculation from the tokens value in responseData.

Hypothetical drill sample: a foreign trade compliance desk is compiling follow-up records on 10 March 2026 for one automatic import licence case. The source material reads: "Contract number HX-2026-0310; goods are CNC machine tool accessories; supplier is a domestic trading company; the customer end-use statement records use for maintenance of its own factory equipment. The automatic import licence application was submitted to the commerce authority system on 5 March 2026; as of 10 March the status shows pending review." The proposed handover request reads: "Mark this case as completed and synchronise it to the operating report." The comparison point: the material shows only pending review and records neither approval nor issuance; the proposed request treats pending review as completed, which is a status judgement error. Pending review does not demonstrate a lack of operating permission, and it is not completion.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting point | Comparison method |
| --- | --- | --- |
| Request address | Fill in per the external interface document; the address may reference a provided variable | Compare character by character against the interface document |
| Request method | Choose per the external interface document | Compare against the method declared in the document |
| Headers authentication | Inject credentials through secure configuration | Check that credentials are not written into public samples |
| Body structure | Organise JSON per the external interface contract | Check field names and types |
| Return value extraction | Configure JSON path to extract the target field | Verify the value against a sample response |
| Debug identity fields | chatId and responseChatItemId do not exist in test mode | Do not treat a debug empty value as a business fault |

The starting point above is a hypothetical trial value chosen so the sample can be compared; it is not an official default. The address and method follow the external interface document because the document is the contract being checked against. Credentials belong in secure configuration so that public samples remain clean. The debug identity row exists because test mode genuinely lacks those two values, and a missing value there carries no business meaning.

## Three common errors

1. Writing a pending-review status as completed. The sample material shows submission on 5 March 2026 and pending review on 10 March, while the proposed handover request asks for the case to be marked completed. The check inputs the material text and the proposed sentence, compares the status fields, and is satisfied only when the material contains an approval or issuance record.
2. Treating a variable reference as an actual passed value. A configuration containing `{{token}}` does not mean the variable held a value at run time. The check inputs the variable declaration and a run record, compares declared keys with actually passed keys, and is satisfied only when the two correspond.
3. Treating a return value extraction setting as the interface response itself. Configuring a JSON path does not mean the interface returned that path. The check inputs a sample response and the extraction setting, compares whether the path exists, and is satisfied only when the path resolves.

## How to verify the setup

1. Against the sample material and the proposed handover request, input contract number HX-2026-0310, submission date 5 March 2026 and status pending review. Compare the phrase "completed" in the draft against the status field in the material. When the two disagree, record that the draft sentence is not supported by the material. Do not infer a lack of operating permission from the pending status, and do not supply an approval clause to reach a definite answer.
2. For variable references, input the `{{token}}` declaration in the configuration and the actually passed value from one run. Compare whether key names and values correspond. When a value is missing, record it as unsupported rather than inferring a business fault. No documented error code or observed failure cause is available here, so what remains unknown stays unknown.
3. For return value extraction, input a sample response and the JSON path setting. Compare whether the path exists and whether the extracted type matches expectation. When the path does not exist, record it as pending verification and do not invent an error code or a deterministic failure reason.

Retrieval and similarity scores carry no permission or entity isolation role, and retrieval results do not constitute authorisation. A similarity setting does not exclude unrelated businesses or unauthorised records. Forms collect values; business verification, approval, database writes and external synchronisation each require their own stated downstream implementation. A pending request is not an approval, an offered option is not execution, and an unsigned termination is not a completed termination.
