# Import and export permits: database operations for operating reviews

## What the documents look like

Permit handling takes place before customs declaration and determines whether a shipment may lawfully cross a border. For the operating review task, the working materials are the automatic import licence, the dual-use item licence, the contract, and the product description. These four documents are checked as a set: the applicant or holder, the object being licensed, the current status, and the validity scope each have to be present before a review conclusion can be recorded. Source data arrives from the commerce authority system, customs commodity codes, supplier materials, and customer end-use statements. Updates are irregular and occur per shipment, so reports are organised by shipment rather than by a fixed calendar, and any exception review has to return to the original wording of the specific shipment file.

Three steps consume most of the working time: deciding which regulatory document applies, preparing the end-use statement, and following the approval status. Report fields should therefore be able to locate the material state at each of those three points. A status value copied from an earlier shipment, or a validity column left blank, cannot stand in for the current file.

## Constraints at the database operations step

Database and operations work carries two responsibilities here: storing the business source records, and serving as the retrieval backend. The two are checked against the actual deployment separately, and configuration values are not inferred from variable names. Retrieval returns text; it does not decide authorisation. Forms collect values; business verification, approval, database writes, and external synchronisation each need their own downstream implementation. Connection and load behaviour is observed against the system's own traffic, covering connection counts, errors, and latency; concurrency thresholds tested elsewhere are not transferred. Backup and recovery are verified as two separate facts: that a backup was produced, and that a restore actually completed, with a comparable sample and record retained. After any database or service configuration change, the same business sample is checked again; a running process is not evidence of a correct result.

Hypothetical drill sample: the source text reads, "A company submitted an automatic import licence application on 1 March of a given year, for a specified equipment model, status pending review, validity column not stated." The proposed determination sentence reads, "This shipment has obtained the licence and shipment may be arranged." The source shows only pending review and no issuance, so the proposed sentence is not supported. Pending review does not demonstrate a lack of operating permission, and it is not the same as approval.

## Three common errors

1. Treating pending review as issued. The sample source states pending review; the proposed sentence states that the licence has been obtained. Same subject, same object, same period, and mutually exclusive values in the status field would be a contradiction. Here the proposed sentence is not supported, and the evidence gap is recorded instead.

2. Treating a retrieval result as authorisation. Retrieval returns text and does not judge whether a licence is valid. A form collects values and does not perform approval. Business verification and writes require a separate downstream implementation.

3. Confirming only that the process is alive after a configuration change. After a database or service configuration change, the same business sample has to be re-checked against the report and the exception record, comparing whether fields and status agree.

## How to verify the setup

1. Enter the sample source text and the proposed determination sentence, and compare four fields: subject, object, status, and validity scope. The source status is pending review and the validity column is not stated, while the proposed sentence states that the licence has been obtained. The observable result is that the status field is not supported, and the item is recorded as pending confirmation.

2. Enter a retrieval request and observe both the returned results and the failure branch. Retrieval does not guarantee a first-position hit, full recall, or an empty result for an unrelated query. An empty result can be checked against a clearly labelled paper input of an empty list to review the downstream design; no claim is made that a fabricated rule search returns an empty list.

3. After a configuration change, enter the same business sample and compare the report fields and exception record before and after the change. The observable result is that the same sample produces consistent fields, which is the condition for the re-check to be satisfied. A running process is not a basis for passing.
