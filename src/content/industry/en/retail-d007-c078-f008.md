# Chain-store site selection: workflow routing for operating reviews

## What the documents look like

Site selection and store opening work happens before a store trades. The center of gravity is lease negotiation and engineering handover, not in-store supervision. The material set for an operating review at this stage includes the site evaluation form, the letter of intent for the lease, the renovation budget, and the opening schedule. These documents are maintained by different roles: headquarters expansion, regional development, and engineering management. Updates are irregular and occur once per store, so a review packet is assembled per site rather than drawn from a rolling feed.

Because the documents are produced by separate teams, the subject store, the stage, and the individual fields are often scattered across different files. A reviewer must first confirm that the materials belong to the same store and the same stage before any figure can be compared. A rent-to-sales ratio computed at the pre-signing stage and a renovation budget prepared after signing describe different decision points and cannot be merged into one status.

## Constraints at the workflow routing step

Workflow routing in this task passes document information along a node sequence, collects input, and evaluates a choice. The Form Input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the flow waits. After the user completes the required fields and submits, the node collects the submitted values and passes them to later nodes. The User Selection node is also a user-interaction node. When the user makes a selection, the node evaluates that selection and executes the corresponding yes branch. Branch connections are verified one by one.

The interaction state is a behavior of the interaction nodes. No separate global state-recording switch is documented, and none should be assumed. Output handoff means the collected information is explicitly passed to a later retrieval, evaluation, or interface node, with output compared field by field against input. Order writing, document write-back, and external status synchronization require a separate business interface or a later flow. The Form Input and User Selection nodes collect values and route branches; they do not perform business execution.

Hypothetical paper exercise. A chain headquarters expansion department plans an operating anomaly review for the pre-opening stage of a store referred to as Store XX Road. The source text supplied for checking reads as follows. The site evaluation form, number A-017, states that the subject is Store XX Road, the evaluation stage is pre-signing, and the calculated rent-to-sales ratio is 18 percent. The lease letter of intent, number B-023, states that the subject is Store XX Road, the status is intent pending confirmation, and no signing date is recorded. The renovation budget, number C-009, states that the subject is Store XX Road, the total budget is 1.2 million, and the preparation stage is post-signing. One draft sentence is to be judged: "The lease letter of intent for Store XX Road has been signed and can proceed to the renovation schedule." The draft sentence concerns Store XX Road, the object is the lease letter of intent, the recorded status is pending confirmation, and the draft asserts that it has been signed.

## Configuration and implementation checks

| Configuration item | Setting or check for this page | Note |
| --- | --- | --- |
| Form Input node | Collect site evaluation form number, subject store, evaluation stage, rent-to-sales ratio | Enters the interaction state on trigger; passes values to later nodes after submission |
| User Selection node | Set a yes branch for whether the letter of intent status is confirmed | Executes the corresponding branch after the user selects; verify each connection |
| Output handoff | Pass the collected store, document number, and status fields to the evaluation node | Compare output against input field by field to confirm correspondence |
| Interaction state check | Confirm the interaction node records state; no separate global state switch | Follow the documented explanation of interaction waiting and state recording |
| External action split | Order writing, document write-back, and external status synchronization connect to a separate business interface | Form and selection nodes do not carry business execution |
| Hypothetical starting value | Use the rent-to-sales ratio of 18 percent as the paper comparison starting point | Chosen because the source text records it; compared against the same store and the same field |

## Three common errors

1. Treating intent pending confirmation as signed. The source text records the lease letter of intent status as intent pending confirmation and records no signing date. The draft sentence states that it has been signed. The input is the letter of intent status field; the comparison is between pending confirmation and signed; these are mutually exclusive values of the same field for the same document number and the same store, so the draft is unsupported.

2. Treating form submission as authorized execution. The Form Input node collects required information and passes it to later nodes; this is an information-collection action. Order writing, document write-back, and external status synchronization require a separate business interface. The input is the submission action; the comparison is between collection and execution; the observable result is whether a later node received the values, and no business write occurs.

3. Treating retrieval results as a permission or entity filter. Retrieval and semantic recall do not perform permission or entity isolation. The input is a retrieval request; the comparison is between returned records and the target store identifier; the observable result is whether a record for a store other than Store XX Road appears. When one appears, record the actual observation and do not infer a permission filter.

## How to verify the setup

1. Check the draft sentence against the hypothetical source text. The input is the source text of the three documents, site evaluation form A-017, lease letter of intent B-023, and renovation budget C-009, together with the draft sentence about the letter of intent being signed and proceeding to the renovation schedule. The comparison is between the source status field intent pending confirmation and the draft assertion signed. The condition is met when, for the same store, the same document number, and the same status field, the draft does not match the source; the result is recorded as unsupported with the evidence gap noted.

2. Check the form output handoff against the hypothetical sample. The input is the store Store XX Road, document number B-023, and status intent pending confirmation collected by the Form Input node. The comparison is against the field values received by the later evaluation node. The condition is met when the received fields match the submitted values item by item and no order writing, document write-back, or external status synchronization action occurs.

3. Check the downstream design for empty results. The input is the paper input of an empty list. The comparison is against the downstream branch design for an empty result. The condition is met when the downstream design states an explicit handling path for the empty result and does not claim that a hypothetical rule-based retrieval necessarily returns an empty list. Libraries built on different vector models cannot be associated together; check the identifier first and exclude those that do not match, and do not run a cross-model retrieval to compare missed recalls.
