# Store price and display checks: workflow routing for operating reviews

## What the documents look like

Price and display audits for chain stores take place during day-to-day operations, a different stage from franchise training or opening coaching. The focus falls on whether standards continue to be executed after opening. The main data sources are the supervision system, POS price lists, store cameras and head office promotion calendars. Weekly and monthly update frequencies mean that reports and exception reviews handle patrol photos, price tag lists, display standards and rectification notices accumulated across weeks. These materials record store floor conditions, price execution and standard requirements respectively. Checking price tags, photographing evidence and tracking rectification closure are the time-consuming steps.

Workflow routing in this category connects form collection, user selection and downstream retrieval, judgement or interface nodes into a checkable chain. The authorization state of a material and the business execution state of a request stay distinct from the state of a workflow node. A form collects values. Whether a rectification notice has been filled in, whether a price has been adjusted, and whether an external system has been synchronized are separate business facts that require their own downstream implementation.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. After the user fills in the required information and submits, the node collects the submitted form information and passes it to subsequent nodes. The user selection node is also a user interaction node. When the user makes a selection, the node evaluates that selection and executes the corresponding "yes" branch. Verifying branch connections one by one is a checking action.

The recorded interaction state is behaviour of the interaction node. No separate global state-recording switch is documented. Output handover requires that collected information is explicitly passed to subsequent retrieval, judgement or interface nodes, and that output and input are compared item by item. Order writing, document backfill and external state synchronization require a separate business interface or a later process. Retrieval and forms do not themselves constitute authorized execution.

Optional paths shown in a general flow diagram do not mean every request executes all of them. Image retrieval requires a corresponding image input and model capability. Reranking requires a model and must be enabled according to settings. Libraries using different vector models cannot be associated together; identifiers are checked first and non-matching libraries are excluded. An empty result can be checked against an explicit paper input of `[]` to inspect downstream design; no claim is made that a fictional rule retrieval will return `[]`.

## Three common errors

1. Treating form submission as completed rectification. In the hypothetical trial sample, after the supervisor submits patrol photos and the price tag list, the form input node only collects information and passes it to subsequent nodes. Whether the rectification notice has been backfilled and whether a price has been adjusted belong to a separate business interface or later process. The submission action does not constitute business execution.

2. Treating the "yes" branch of user selection as authorization or approval. The user selection node executes the corresponding branch after the user makes a selection. The selection result only determines the flow direction. A pending-review state does not show that operating permission is absent, and a quotation validity period does not indicate a supply period.

3. Treating retrieval results as a permission or entity isolation mechanism. Semantic recall and relevance do not handle permission or entity isolation. The same-vector-model requirement for a retrieval library cannot be extended to require other external systems to use the same model. Libraries using different vector models cannot be associated together; identifiers are checked and non-matching libraries are excluded.

## How to verify the setup

Hypothetical trial sample: a regional supervisor in a chain operations department submits a patrol record in the second week of June 2025. The source text reads: "Store A was patrolled on 10 June 2025; the price tag list shows 3 promotional prices consistent with the head office promotion calendar; 2 display standard photos have been uploaded; rectification notice number A-0610 is in pending-backfill state." The draft sentence to be assessed is: "Store A rectification notice A-0610 has completed backfill, and price execution shows no abnormality." The three checks below use this sample item by item.

1. Input is the source text above and the draft sentence. Compare "has completed backfill" in the draft sentence against "pending-backfill state" in the source text. Observable result: the source text records only pending backfill and does not record completed backfill. That wording in the draft sentence is unsupported and should be recorded as pending verification.

2. Input is the patrol record fields collected by the form input node and the fields actually received by subsequent nodes. Compare field names, counts and values. Observable result: if the fields received by subsequent nodes match the required form fields, the output handover holds; if fields are missing or values changed, record the location of the difference without inferring a cause.

3. Input is the "yes" branch connection of the user selection node and the rectification notice backfill request. Compare the branch execution condition against the request state. Observable result: if the request is only pending review or submitted, branch execution does not constitute approval or completion. Record the current request state and preserve the evidence gap.
