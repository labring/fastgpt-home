# Store price and display checks: tool calls for operating reviews

## What the documents look like

Price and display audits take place during ordinary trading periods, and the central question is whether standards continue to be executed after launch. The materials involved come from supervision systems, POS price tables, store cameras and head office promotion calendars. Day-to-day handling covers store visit photographs, price tag lists, display standards and rectification notices. Operating reports and exception reviews use these materials to assess price execution and display deviations.

Tool calls and plugins matter here because the model decides from context whether to invoke a connected tool, then reads the tool result to form output. The supplied brief gives weekly and monthly update frequencies. This page does not derive batch synchronisation, full synchronisation or real-time trigger mechanisms from those frequencies.

## Constraints at the tool calls step

A tool consists of a tool introduction and tool parameters. System module parameters are fixed; plugin parameters are configurable. The model decides whether to call a tool by combining the tool introduction, each parameter introduction and whether each parameter is required. Where no parameter is required, the tool may be called even when the context holds no suitable parameter, and the model sometimes fabricates one. Where a required parameter is absent and no suitable value exists, the model may decline to call the tool, and prompts can guide the user to supply the value. In advanced orchestration, available tools are connected to the tool call module, and the guidance is to start with a small number of tools and tune before adding more. The tool call termination node ends the current call, so no further tools are called and the AI is not asked to summarise the tool result. Custom tool variables extend variable input for nodes that are not treated as tool parameters.

Retrieval and similarity scores do not constitute authorisation. A form collecting a value does not mean that business verification, approval, a database write or external synchronisation has occurred.

Hypothetical paper exercise sample: a chain operations supervisor submits a paper review pack for week 2 of March 2026. The source text reads: "Store A, 10 March 2026, display standard execution status is awaiting regional supervisor review; the price tag list for the same period records that the promotional price tag at this store has been replaced." The draft sentence to be assessed reads: "Store A display standard execution has passed review, so this exception review can be closed." The request concerns subject Store A, object display standard execution status, period week 2 of March 2026, and status awaiting review. Awaiting review is not the same as passed review, and the draft sentence records an unfinished state as a completed conclusion.

## Configuration and implementation checks

## Three common errors

1. Recording an awaiting-review state as passed. In the sample source text the status is "awaiting regional supervisor review", while the draft sentence says "has passed review". Comparing the status value for the same subject, the same period and the same field shows the two do not agree.

2. Treating a tool introduction as a guarantee of execution. The introduction only states the purpose. Whether the model calls the tool also depends on the parameter introductions and the required flags. Where a required parameter is absent the model may decline to call, so the actual request must be inspected.

3. Treating a retrieval result as authorisation. Retrieval and similarity scores do not carry permission or entity separation, and a form value does not produce an approval or a write. The review status in the sample still requires human confirmation or a downstream system.

## How to verify the setup

1. Enter the sample source text and the draft sentence, then compare "awaiting regional supervisor review" with "has passed review" for the same subject, the same period and the same field. Where the status values disagree, the draft sentence is not supported and the evidence gap remains open.

2. Enter the tool introduction and the parameter configuration, then compare whether the parameter introductions and required flags cover the fields the sample needs. Where a required parameter is absent, observe whether the model declines to call and record the actual request, without assuming a particular failure.

3. Enter the position of the tool call termination node, then compare whether other tools or AI summarisation still run after termination. Where the termination node is attached after the specified tool, the current call should end and neither other tools nor AI summarisation should execute. All three checks are paper expectations and have not been tested.
