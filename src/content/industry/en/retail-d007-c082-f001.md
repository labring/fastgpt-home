# Returned-goods inspections: HTTP integrations for operating reviews

## What the documents look like

Returned-goods inspection handles reverse parcels and item grades. It does not handle outbound picking and packing for new orders. The records behind an operating review come from the WMS returns module, platform after-sales, carrier returns, and the inspection bench. The working documents are the return inbound note, inspection photos, the grade decision table, and the resale listing note. Each returned item is recorded individually, and the data updates per item and per day.

An operating review and exception review for this category asks how a batch of returned items is distributed across inspection decisions, resale, or scrapping, and where the recorded values deviate from the source documents. A second question is whether those records can be sent to and received from external systems through HTTP integrations in a stable way. The HTTP module sends a request to a configured address. Params carry path parameters and are common in GET requests. Body carries the request body and is common in POST and PUT requests. Headers carry special information. URL, Params, Body, and Headers can all reference variables through `{{}}`. The available variables come from global variables, system variables, and the outputs of preceding nodes. System variables include appId, chatId, responseChatItemId, variables, cTime, and histories. The chatId and responseChatItemId values do not exist in test mode. Returned values are parsed through JSON path syntax or JavaScript object access rules. When the output type is set to string, the value of the corresponding key is converted into a JSON string.

The HTTP module can operate a database, call an external data source, run a web search, or send email. These are business actions that require a separately connected system to implement. The module itself does not complete authorization, approval, or a database write. Retrieval is not authorization. A form collects values; business verification, approval, database writes, and external synchronization each need their stated downstream implementation.

## Constraints at the HTTP integrations step

The HTTP module is a triggered node that can be added more than once and is configured manually. It does not run on a schedule, and no hidden trigger should be assumed. A relevance score is not a category, entity, or permission filter, and a similarity setting does not exclude unrelated businesses or unauthorized records. Knowledge-reference limits use the documented unit. Same-model retrieval association, empty-reference output, and context limits keep their documented conditions. Cross-model libraries cannot be associated together; check the identifiers first and exclude those that do not match.

For an operating review, the constraint that matters is that an HTTP response is evidence of an interface response only. It is not evidence of authorization, approval, or a completed write. A pending request is not approval. An offered option is not execution. An unsigned termination is not a completed termination. Where the documents do not state an error code or an observed result, the review records what to compare and leaves the outcome unknown.

Hypothetical drill sample, clearly labelled as hypothetical: on 12 March 2025, a returns warehouse records return inbound note RB-20250312-017. The object is one returned item. The inspection photo shows outer packaging damage and no visible damage to the item itself. The grade decision table records the status "pending recheck". The resale listing note has not been generated. The sentence to be checked is: "This returned item has completed inspection and can be listed for resale directly." The source wording for comparison is: "Grade decision table status is pending recheck; resale listing note: not generated." In this sample the subject is the returns warehouse inspector, the object is that returned item, the status is pending recheck, and the valid scope is limited to that note on that day.

## Configuration and implementation checks

| Configuration item | Assumed starting point on this page | How to check |
| --- | --- | --- |
| URL | The address given by the external interface document | Confirm the address matches the external interface contract |
| Params | Path parameters completed from the external interface document | Compare each item against the interface document |
| Headers | Authorization uses Bearer plus a credential | The credential is injected through secure configuration and is not written into the sample |
| Body | Used only under POST or PUT; check the JSON structure | Compare field by field against the external interface contract |
| Variable reference | References a global variable or a preceding node output | Check whether the actual passed value matches the source material |
| Debug identity fields | chatId and responseChatItemId do not exist in test mode | Do not treat a debug empty value as a business fault |

The assumed test starting point on this page uses "pending recheck" as the grade decision table status, because the source wording records that status explicitly. The comparison object is whether the resale listing note has been generated. This starting point is an assumed value for this drill and is not an official default.

## Three common errors

1. Treating "pending recheck" as completed inspection. The grade decision table status is pending recheck and the resale listing note has not been generated, so the draft sentence "has completed inspection and can be listed for resale directly" does not match the source wording. Check: input the source wording and the draft sentence, compare the status field and the listing note field, and observe whether the draft sentence conflicts with the source. The expected result is a conflict; this is not claimed to have been tested.

2. Treating a missing chatId in test mode as an interface fault. The documents state that chatId and responseChatItemId do not exist in test mode. Check: input a test-mode request, compare whether chatId and responseChatItemId are present in the request, and observe whether an empty value is misread as a business exception. The expected result is absence, which is normal for test mode; this is not claimed to have been tested.

3. Treating an HTTP module call to an external data source as a completed database write or as authorization. The documents state that the module can operate a database and call an external data source, while authorization, approval, and writing are business actions that require a separately connected system. Check: input a request that calls an external interface, compare the returned value with the business status field, and observe whether an interface response is treated as authorization or as a completed write. The expected result is pending verification; this is not claimed to have been tested.

## How to verify the setup

1. For hypothetical sample RB-20250312-017, input the source wording "Grade decision table status is pending recheck; resale listing note: not generated" together with the draft sentence "This returned item has completed inspection and can be listed for resale directly." Compare the status field and the listing note field. If the draft sentence conflicts with the source wording, record the draft as unsupported. The expected result is a conflict; this is not claimed to have been tested.

2. For the same hypothetical sample, input one test-mode request. Compare whether chatId and responseChatItemId are present in the request. If they are absent, record this as normal behaviour in test mode and do not judge it as a business fault. The expected result is absence; this is not claimed to have been tested.

3. For the same hypothetical sample, input one request that calls an external interface. Compare the interface return value with the business status field. If the return value indicates only an interface response without carrying an authorization or write-completion marker, record the item as pending verification and do not judge it as authorization or as a completed write. The expected result is pending verification; this is not claimed to have been tested.
