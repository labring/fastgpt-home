# Returned-goods inspections: tool calls for operating reviews

## What the documents look like

Returned-goods inspection handles reverse parcels and item grades. It does not handle outbound picking for new orders. Every returned item is scanned, its condition is judged, and a decision is made to resell or scrap it. The records come from the WMS returns module, platform after-sales, carrier return parcels, and the inspection bench. Operating reports and exception reviews draw fields from the return warehouse receipt, inspection photos, the grade decision table, and the resale listing form.

For the tool-call step, the model decides from context whether to invoke a module or plugin. The tool introduction states the purpose and the situations in which the tool should not be called, and the model uses that introduction to judge timing. Tool parameters separate fixed parameters of a system module from configurable parameters of a plugin. The parameter description and the required flag together affect the call decision. A grade decision on a returned item, a resale listing status, and a photo reference are separate facts recorded in separate documents; a report line that treats one as another is not supported by the source records.

## Constraints at the tool calls step

Tool calling depends on three pieces of information: the tool introduction, the parameter description, and whether a parameter is required. The model decides from context semantics whether to execute. A tool with no parameters is judged directly from its introduction. A tool with required parameters and no suitable value in context may not be called, and prompts can guide the user to supply the missing value. A model that supports function calling can call multiple tools in one turn. In advanced orchestration, available tools are connected to the tool-call module, and the guidance is to tune a small number of tools first.

The tool-call termination node can be placed after a tool. When the workflow reaches it, the current tool call ends, no further tools are called, and the AI does not summarize the tool result. Custom tool variables extend the variable inputs of nodes that are not treated as tool parameters, so the tool call can invoke such a node and the workflow after it. The same-vector-model requirement for a retrieval library is limited to that library and does not extend to external systems. A relevance score does not perform permission or entity isolation, and retrieval does not grant authorization.

Hypothetical drill sample: a return warehouse receipt reads "Return ID RT-2024-0412, item is a Bluetooth earphone, inspection bench graded appearance as B, inspection photo IDs P-0412-01 through P-0412-03, resale listing form status is pending review." A draft sentence reads "This return has completed resale listing." Checking compares the resale listing status field with the draft sentence. A pending-review status does not mean listing is complete.

## Three common errors

1. Treating a tool parameter description as a guarantee of execution. The description explains what the parameter means; it does not mean the model will pass that parameter. The check compares the parameter value in the actual request with the parameter description. An observable result is a request in which the described parameter is absent while the description implies it is needed.

2. Treating a pending-review status as completed listing. In the hypothetical sample, the resale listing form status is pending review and the draft sentence says listing is complete. These are mutually exclusive values on the same field. The check compares the status field value with the draft sentence. The observable result is that the draft sentence is unsupported while the status remains pending review.

3. Treating a relevance score as permission filtering. A relevance score does not carry entity or permission isolation, and a retrieval result does not mean authorization was granted. The check compares the retrieved records with the access scope and confirms whether they fall inside the target range to which access is held. The observable result is a retrieved record outside the access scope, which the score does not exclude.

## How to verify the setup

1. Input the return warehouse receipt text from the hypothetical sample and the draft sentence "This return has completed resale listing." Compare the resale listing status field value with the draft sentence. When the pending-review status appears, the draft sentence is unsupported and the evidence gap is recorded. This is a paper check; no listing action is claimed to have occurred.

2. Input the tool introduction from the hypothetical sample and one tool-call request. Compare whether the introduction states situations where the tool should not be called and whether the actual request is made when the introduction's conditions are met. When a situation not covered by the introduction appears, the call timing cannot be determined.

3. Input the inspection photo IDs P-0412-01 through P-0412-03 and the grade decision table from the hypothetical sample. Compare whether the photo IDs are referenced in the grade decision table and whether the grade B decision has corresponding photo evidence. When a photo ID does not appear in the decision table, that grade decision remains unverified.

These checks describe what to compare and what remains unknown. They do not claim that a test, deployment, approval, or business action took place. Where a document field is not provided, the value is unknown. Where only evidence of a related stage exists, the conclusion is unsupported or pending verification rather than contradicted.
