# Store counts and loss control: workflow routing for operating reviews

## What the documents look like

Store counts and loss control examine book-to-physical variance and shrinkage. They do not settle supplier payables, which separates this category from supplier inbound settlement work. The working material comes from POS inventory, WMS, monitoring systems, and the SB/T count specification. The people handling it sit in loss prevention, store inventory control, and financial audit. The documents in daily use are count sheets, variance analyses, damage write-off approvals, and monitoring access records. Monthly or quarterly update cycles shape how operating reports and exception reviews treat each record as a period-scoped artifact rather than a live feed.

For workflow routing, this means the objects being routed are the flow states of variance items and write-off matters. A report or review has to link variance SKUs, write-off requests, and monitoring access records into a chain that can be checked item by item. Routing a request is not the same as confirming a variance, approving a write-off, or authorizing monitoring access.

## Constraints at the workflow routing step

The Form Input node and the User Selection node are both user-interaction nodes. When either is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. Form Input collects required information and passes it to later nodes. User Selection evaluates the user's choice and executes the corresponding "yes" branch. These are the documented behaviors. The documents do not describe a global state-recording switch, a submission-count control, automatic judgment, or snapshot guarantees, so none of those should be assumed.

Retrieval and form collection supply information. They do not constitute authorization, approval, or business execution. Damage write-off approval, count variance confirmation, and monitoring access authorization each require a separate business interface or a downstream process. The nodes themselves do not complete those actions. A pending request is not an approval; an offered option is not execution; an unsigned termination is not a completed termination.

Assumed drill sample: a store's March 2025 monthly count sheet records "count date 2025-03-31, count scope: all store storage locations, variance SKU: A-1023, book quantity 40, physical quantity 31, variance quantity -9, variance cause pending investigation." A draft variance-analysis sentence reads "the A-1023 variance has been confirmed as caused by employee fraud, the damage write-off approval passed, and write-off is agreed." The request to be judged is "based on the above count sheet and variance analysis, route the damage write-off approval workflow and execute the write-off."

## Configuration and implementation checks

| Configuration item | Setting or check relevant to this page | Relation to the sample |
| --- | --- | --- |
| Form Input node | Enters interaction state when triggered, collects required information, passes it to later nodes after submission | Collect variance SKU, book quantity, physical quantity, variance cause |
| User Selection node | Executes the corresponding "yes" branch after the user chooses; verify each branch connection individually | Branch on "is the variance cause verified," separating verified from pending investigation |
| Interaction state check | Recording state is a behavior of interaction nodes; no separate global state-recording switch is documented | Check whether the sample request enters interaction state and waits for input after triggering |
| Output handoff check | Pass collected information explicitly to later retrieval, judgment, or interface nodes; compare output against input item by item | Check whether the A-1023 variance information is passed intact to later nodes |
| External action separation | Order writes, document backfill, and external state synchronization require a separate business interface or downstream process | Write-off execution and approval passage require a separate business interface; nodes do not complete them |
| Assumed trial starting point | This assumed trial treats variance cause verification as required, because that field determines the branch direction; compare against the "pending investigation" value | The sample's variance cause is "pending investigation," used to check whether the branch enters the pending-verification path |

## Three common errors

1. Treating variance information collected by the form as a passed damage write-off approval. In the sample, the draft variance-analysis sentence states "the damage write-off approval passed, and write-off is agreed," while the count sheet original records only the variance quantity and "pending investigation." It does not state an approval subject, approval time, or approval conclusion. Form Input only collects information; approval status requires a separate business interface, and the draft sentence's "approval passed" is unsupported.

2. Treating the User Selection "yes" branch as business authorization execution. The User Selection node executes the "yes" branch after the user chooses; that branch indicates only the process direction, not that write-off, damage reporting, or access has been authorized. The sample request asks to "execute the write-off," and the write-off action requires a separate business interface; the node does not complete the write-off.

3. Treating a retrieval result as a permission or entity filter. Retrieval and similarity scores do not perform permission or entity isolation. A retrieval hit on A-1023 does not mean that SKU's write-off has been authorized. In the sample, the A-1023 variance cause remains "pending investigation," and the authorization state is unknown.

## How to verify the setup

1. Input the sample count sheet original and the draft variance-analysis sentence, then compare the variance cause field value "pending investigation" against the draft sentence's "confirmed as caused by employee fraud" for the same subject, same period, and same field. If the count sheet does not state a fraud conclusion, the draft sentence's "confirmed" is unsupported and should be recorded as pending verification, not judged as a contradiction or a denial.

2. Input the sample request "route the damage write-off approval workflow and execute the write-off," then compare the User Selection node's "yes" branch output against the execution conditions for the write-off action. If the branch indicates only process direction and no business interface is connected, the write-off is not executed and should be recorded as pending verification, without claiming the write-off occurred.

3. Input a paper input of `[]` for an empty result handoff and check whether the downstream design has explicit handling for an empty result. If retrieval returns empty, the downstream should record the gap. Do not claim that a fictional rule retrieval necessarily returns `[]`, and do not claim that an unrelated query is necessarily empty. Libraries across different vector models cannot be associated together; verify identifiers first, exclude non-matching ones, and record the actual observation.
