# MCN operations: workflow routing for multilingual work

## What the documents look like

An MCN organisation manages long-term account compliance for many creators rather than serving a single brand event. The material set for this page includes creator signing contracts, training records, violation handling forms and account scheduling sheets. These documents arrive from the MCN back office, platform violation notices, creator account data and the contract ledger. In cross-border work the same material may exist in several languages and several signing states, and update frequency is daily or weekly.

For workflow routing, the practical consequence is that a retrieved document is only a document. Retrieval and similarity scoring show what text exists and how close it is to a query. They do not decide whether the operator is allowed to act on that creator, whether a contract has taken effect, or whether a violation has been resolved. Routing decisions therefore depend on collected values, explicit user choices and downstream checks rather than on the retrieval result alone.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution waits. After the user completes the required fields and submits, the node collects the submitted form information and passes it to later nodes. The User Selection node is also a user interaction node with the same interaction behaviour. When the user makes a choice, the node evaluates that choice and runs the corresponding branch.

Both nodes collect values or select a branch. Order writing, document backfill and external status synchronisation require a separate business interface or a later process. A similarity score is not a category, entity or permission filter, and retrieval is not authorisation.

Hypothetical paper exercise sample. A creator signing contract is being checked inside a cross-border document retrieval workflow. The paper original reads: "Party A is an MCN organisation; Party B is creator Lin; the contract signing date is 10 March 2025; the agreed cooperation period runs from 1 April 2025 to 31 March 2026; the contract status field is marked 'awaiting seals from both parties'." A drafted sentence reads: "This contract is in effect, so the creator can be scheduled for the April special event." The original shows a signing date and an awaiting-seals status. It does not state an effectiveness clause. Signing, reaching cooperation and contract effectiveness are three distinct facts, and the drafted sentence is not supported by the original.

## Configuration and implementation checks

| Configuration item | Type | Relation to this page's sample |
| --- | --- | --- |
| Form Input node | Documented in official material | Collects required values such as creator name, contract number and retrieval language, then passes them to later nodes after submission |
| User Selection node | Documented in official material | Presents a choice between continuing retrieval and routing to manual verification, then runs the corresponding branch |
| Interaction state check | Implementation check | Confirm the interaction state is entered and workflow state is recorded on trigger; no separate global state switch is assumed |
| Output handover check | Implementation check | Confirm the collected contract number and language are explicitly passed to the later retrieval or evaluation node, and compare inputs against outputs item by item |
| External action boundary | Implementation check | Contract status backfill and seal status synchronisation require a separate business interface; form submission does not produce that effect |
| Retrieval scope check | Implementation check | Confirm the target retrieval library and the query use the same vector model identifier, and exclude records whose identifier does not match |

## Three common errors

1. Treating form submission as contract effectiveness. The input is the sample original marked "awaiting seals from both parties" together with the drafted sentence. The comparison is whether the original states an effectiveness clause. The observable result is that the original does not state effectiveness, so the drafted sentence remains unsupported and cannot be recorded as effective.

2. Treating a retrieval similarity score as a permission filter. The input is one cross-language contract retrieval request. The comparison is whether the returned records include creator records the operator is not authorised to use. The observable result is that the similarity score reflects textual closeness only and does not exclude unrelated or unauthorised records, so the permission boundary must be checked separately.

3. Treating a User Selection branch as completed business execution. The input is the action of choosing to continue retrieval. The comparison is whether contract status backfill occurs afterwards. The observable result is that the branch only determines the route; backfill requires a separate interface, and without that interface the action remains unexecuted.

## How to verify the setup

1. Using the sample original and the drafted sentence, inspect whether the workflow output presents "awaiting seals from both parties" as a pending state and does not output an "in effect" conclusion. The condition is met when the output keeps the original status wording and does not add an effectiveness clause.

2. Using the paper input `[]`, check the empty-result handover design and observe whether downstream nodes follow the empty-result branch and prompt for manual verification. The condition is met when downstream nodes do not fabricate records and do not automatically write contract status.

3. Using the sample contract number, run one retrieval and compare returned records against the input number, language and vector model identifier, excluding records whose identifier does not match. The condition is met when only records with a matching identifier are presented; records with a mismatched or missing identifier are recorded as unsupported, and no cross-model comparison is performed.
