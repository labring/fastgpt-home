# MCN operations: citation tracing for multilingual work

## What the documents look like

MCN management covers long-term account compliance for many creators, and a single brand campaign is only one part of that work. The daily document set includes creator signing contracts, training records, violation handling forms and account schedules. Sources include the MCN back office, platform violation notices, creator account data and the contract ledger. In cross-border and multilingual retrieval, one contract may exist in a Chinese version, an English version or other language versions. A retrieval hit has to be traced to a specific version, a specific clause and a specific status.

A creator contract, a training record and a violation handling form do not share one status vocabulary. A signature date, a cooperation start, a contract effective date and a violation closure are separate facts. Retrieval returns text; it does not return the business status of that text.

## Constraints at the citation tracing step

The knowledge base search node outputs cited content as an array, and the array length can be zero. The output path still runs when nothing is found. When knowledge bases are associated, only knowledge bases that use the same vector model can be selected together. Whether a retrieved result is adopted still depends on review of the valid version. Retrieval on its own is not authorization.

Hypothetical paper exercise sample: an MCN organization and creator A signed a Chinese version of a creator signing contract, contract number HT-2024-031, signature date 1 March 2024, with a cooperation term running to 28 February 2025. A separate English translation exists and carries no marked signature status. Creator A's training record shows completion of platform rules training in April 2024. A draft sentence reads: "Creator A's contract was signed and took effect on 1 March 2024, with a cooperation term to 28 February 2025." The question is whether this draft sentence matches the retrieved contract original.

The contract original, as a paper input for this exercise, contains two lines: "Contract number: HT-2024-031; signing date: 1 March 2024" (English rendering) and "Cooperation term: from 1 March 2024 to 28 February 2025" (English rendering). The English translation carries no signature status line. No clause in either version states a contract effective date.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison method |
| --- | --- | --- |
| Associated knowledge bases | Creator contract library and training record library, same vector model | Check the vector model identifier first; exclude any library whose identifier differs, and do not run cross-model retrieval |
| Search mode | Hybrid retrieval | The contract number is an exact query, while semantic retrieval covers multilingual wording; both result sets are merged through RRF |
| Citation limit | Set to 2000 tokens as a hypothetical starting point for this exercise | Contract clauses are short; compare against the training record entries and observe whether a key clause is cut off |
| Minimum relevance | Set to 0.5 as a hypothetical starting point for this exercise | Compare against the contract original fragment and observe whether low-relevance fragments are filtered |
| Result reranking | ReRank enabled | When candidates are numerous, apply a second ordering and filter by the rerank score |
| Citation output | Carried forward as an array | Check whether the output is passed to the answering step, then compare each answer item against the cited original text |

The token value here is a citation limit for retrieved content. It is not a thinking budget and does not control model reasoning.

## Three common errors

1. Treating a retrieval hit as an authorization basis. Input: the retrieval result for creator A's contract. Compare: the retrieval output against the signature status field in the contract ledger. Observe: retrieving contract text does not mean the contract took effect. Signature, cooperation start and contract effectiveness are three different facts, and the paper contract original states a signature date and a cooperation term only.
2. Treating an empty citation array as a system error. Input: a retrieval run that returns an empty array. Compare: whether the output path continues to execute. Observe: citation length can be zero, and an empty array does not mean the workflow terminated with an error.
3. Forcing association of libraries with different vector models. Input: two knowledge bases with different vector model identifiers. Compare: whether the vector model identifiers match. Observe: when they differ, they cannot be associated together. Check the identifier and exclude the non-matching library; do not run the cross-model retrieval to compare recall.

## How to verify the setup

1. Input the contract original and the draft sentence from the hypothetical sample. Compare the signature date, contract number and cooperation term in the draft sentence against the original line by line. The draft sentence is supported when all three fields match exactly. When any field differs, or the original does not state the field, record it as pending verification. The paper original does not state a contract effective date, so the "took effect" wording in the draft sentence remains unsupported and the evidence gap stays open.
2. Input the English translation from the hypothetical sample. Compare whether the translation carries a marked signature status. When no signature status is marked, the English version cannot be judged effective, and the evidence gap remains.
3. Input a paper record whose citation content is an empty array. Compare whether the downstream answering step handles it as an empty array. The empty-citation handoff design holds when the output path runs and the downstream step reports no error. When the downstream step behaves abnormally, record the actual observation and do not infer a specific error cause.

A pending review does not show a lack of operating authority. A retrieval result that is relevant to the question is not a category or permission filter, and relevance does not exclude unrelated business records or unauthorized records. The same-vector-model requirement applies to associated knowledge bases in this node; it does not extend to business registration sites or other external systems.
