# Temu semi-managed sellers: workflow routing for multilingual work

## What the documents look like

Semi-managed Temu sellers differ from fully managed suppliers because they maintain overseas inventory and handle dispatch themselves. The work therefore spans records held in an overseas warehouse WMS and logistics tracking, with supplying goods to the platform forming one part of the operation. The documents handled day to day fall into four groups: product declaration forms, overseas inventory sheets, price declarations, and platform fulfilment orders. Sources include the Temu Seller Center, the overseas warehouse WMS, logistics tracking, and purchase cost sheets. The brief describes these materials as updated daily and per order. Product declarations and price declarations can change field values from order to order, while overseas inventory sheets and platform fulfilment orders are checked line by line. In the cross-border documentation and multilingual retrieval task, workflow routing concerns how these documents move between retrieval and interaction nodes. A retrieval result locates material; it does not confirm inventory, price, or fulfilment status.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the required information and submits, the node collects the submitted values and passes them to later nodes. The user selection node is also a user interaction node: it enters the interaction state, records the workflow state, and when the user makes a choice the node evaluates that choice and executes the corresponding "yes" branch. The interaction state is recorded by the interaction node itself; no separate global state-recording switch is documented. Collected information must be passed explicitly to later retrieval, judgement, or interface nodes, and outputs are compared item by item against inputs. Order writing, document backfill, and external status synchronisation are business actions that require a separate business interface or downstream process. Retrieval and form nodes do not carry authorisation duties.

Hypothetical drill sample. A semi-managed seller operations staff member holds a product declaration draft reading: "Declaring entity: a cross-border supplier in East China; declared object: Model A storage box; declaration status is pending review; validity period: 1 March 2025 to 31 March 2025." The same person holds a price declaration draft reading: "Quoting entity: a cross-border supplier in East China; quoted object: Model A storage box; quote status is submitted; quote validity period: 1 March 2025 to 15 March 2025." The draft sentence to be assessed is: "This supplier's Model A storage box declaration has passed review and can be supplied under the quote validity period until 31 March." The material needed for assessment is the text of the two drafts above, both inside an accessible target retrieval scope.

## Configuration and implementation checks

| Configuration item | Setting or check relevant to this page | Correspondence with the sample |
| --- | --- | --- |
| Form input node | Enters the interaction state on trigger, collects required information, passes it to later nodes after submission | Collects declaring entity, declared object, declaration status, validity period |
| User selection node | Executes the corresponding "yes" branch after the user chooses; verify branch connections one by one | Choose the "publishable" or "to be verified" branch for the draft sentence |
| Interaction state check | The interaction node records state; no separate global state-recording switch is documented | Check the submission state of the two drafts |
| Output handover check | Collected information is passed explicitly to later retrieval, judgement, or interface nodes; compare output against input item by item | Compare the draft sentence against field values in the two source texts |
| External action separation | Order writing, document backfill, and external status synchronisation require a separate business interface or downstream process | Declaration approval status and supply period are not confirmed on this page |
| Retrieval scope check | Material needed for assessment must sit in an accessible target retrieval scope or explicit manual input | Whether the two draft texts fall inside accessible scope |

## Three common errors

1. Treating "pending review" as "passed review". In the sample the declaration status field reads "pending review", while the draft sentence says "has passed review". Same entity, same object, same field, mutually exclusive values: an unsupported judgement. The check takes the declaration source text and the draft sentence as input, compares the declaration status field, and observes whether the two agree.
2. Treating the quote validity period as the supply period. In the sample the quote validity period ends on 15 March 2025, while the draft sentence says supply is possible under the quote validity period until 31 March. Quote validity and supply period are different facts; a quote validity period does not express a supply period. The check takes the price declaration source text and the draft sentence as input, compares the date field and the described object, and observes whether the draft sentence substitutes the quote validity period for the supply period.
3. Treating a retrieval hit as authorised execution. A retrieval node returning the declaration draft only shows the material was located; it does not show the declaration passed or is publishable. The check takes the retrieval request and the returned material as input, compares the retrieval action against the business action, and observes whether any step treats the retrieval result directly as grounds for publishing, writing, or synchronising.

## How to verify the setup

1. For the draft sentence "This supplier's Model A storage box declaration has passed review and can be supplied under the quote validity period until 31 March", input the declaration source text "declaration status is pending review" and the price declaration source text "quote validity period: 1 March 2025 to 15 March 2025". Compare values for the same entity, same object, and same field. Observe whether the declaration status agrees with "has passed review" and whether the quote validity period covers 31 March. The expected phenomenon is that neither agrees; the draft sentence is judged unsupported and the evidence gap is retained.
2. For the user selection node, input the sample draft sentence as the object to be assessed, set the two branches "publishable" and "to be verified", compare the user's choice against the branch connections, and observe whether the "to be verified" branch is entered. The expected phenomenon is that the choice determines the branch taken, branch connections are verified one by one, and no automatic judgement or automatic publishing occurs.
3. For retrieval scope, input the explicit manual input "[]" as an empty-result handover sample, compare whether the downstream node design handles empty-reference output, and observe whether the empty result is treated as a conclusion of "no relevant record" or "no permission". The expected phenomenon is that downstream only accepts the empty result and records the gap, without inferring business status and without claiming that a fictional rule retrieval necessarily returns an empty array.
