# Refund-only disputes: workflow routing for multilingual work

## What the documents look like

Refund-only disputes differ from ordinary return-and-refund cases in one structural way: there is often no returned parcel entering the warehouse. The evidentiary center of gravity therefore sits on dispatch and signed receipt, together with the declared value of the goods. Materials arrive from the platform after-sales backend, carrier tracking, customer-service chat, and warehouse outbound records. The working documents for a single case are the refund-only application, the dispatch proof, the signed-receipt proof, and the appeal materials. Data updates per order and daily. This page does not derive any batch synchronization, full synchronization, real-time, or transaction-triggered mechanism from that update frequency.

The task here is cross-border materials and multilingual retrieval as it appears at the workflow routing step. The routing step has to place form input, user selection, and retrieval hand-off in a clear order, and it has to keep three things apart: behavior a node already performs, fields that can actually be configured, and business actions that require a separate system connection. Retrieval and form submission do not constitute authorization. Order writes, document backfill, and external status synchronization require a separate business interface or a downstream process.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the workflow continues downward only after the user completes the interaction. Once the user fills the required information and submits, the node collects the submitted form information and passes it to later nodes. The user selection node is also a user-interaction node with the same interaction-state behavior; when the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. The documented behavior covers waiting, state recording, and branch execution. It does not document a control switch for the interaction wait, a submission-count limit, an automatic judgment, or a snapshot guarantee, and none is assumed here.

Retrieval carries its own limits. Libraries built on different vector models cannot be associated together; the identifier is checked first and non-matching libraries are excluded, without running cross-model retrieval to compare missed recalls. A similarity score is not a category, entity, or permission filter, and retrieval does not perform permission or entity isolation. Whether a relevant document is reachable depends on the target retrieval scope being accessible or on an explicit manual input; when it is missing, the gap is recorded as a gap.

Hypothetical paper exercise sample. The material text reads: "Application A-01 states that order D-01 was signed for on 2 March 2026, requests refund only, amount USD 120; carrier tracking shows signed receipt on the same day; the outbound record shows two items dispatched on 1 March." The proposed hand-off request reads: "Based on the above materials, route A-01 into the appeal-material collection node and confirm whether return of goods is required." In this sample the signed receipt and the outbound record are same-subject, same-period records. Whether return of goods is required has no supporting field and remains to be verified.

## Configuration and implementation checks

| Configuration or check item | Use on this page | Basis and boundary |
| --- | --- | --- |
| Form input node | Collect required refund-only application information | Documented: submitted information passes to later nodes |
| User selection node | Take the user choice on whether return of goods is required | Documented: the "yes" branch is executed |
| Interaction-state check | Confirm the interaction state is entered on trigger | State recording is interaction-node behavior |
| Output hand-off check | Compare collected information against downstream inputs item by item | Must be explicitly passed to a retrieval or judgment node |
| Retrieval library identifier check | Exclude libraries on different vector models from joint association | Identifier check only; no missed-recall comparison |
| External action split | Order writes and status synchronization connect to a separate interface | Form and retrieval do not constitute authorization |

## Three common errors

1. Treating form submission as authorized execution. Input: the proposed hand-off request for A-01. Comparison: "submitted" against "authorized." Observable result: the record is written although no authorization field is present.
2. Treating a similarity score as a permission or entity filter. Input: a score returned by retrieval. Comparison: the score against access rights. Observable result: an unrelated business record is treated as readable.
3. Associating libraries across vector models. Input: two library identifiers. Comparison: whether the model identifiers match. Observable result: identifiers that differ are still merged into one retrieval.

## How to verify the setup

- Verification one: take the sample material text as input and compare the signed-receipt date against the outbound date for mutual exclusivity within the same field. The two values sit in different fields, so the condition is met when the record is marked as pending verification rather than as a contradiction.
- Verification two: take the proposed hand-off request as input and compare "route into the appeal-material collection node" against the existing authorization fields. With no authorization field present, the condition is met when the case stays at pending review and no write is executed.
- Verification three: use the paper input `[]` to check the downstream design and compare whether the empty-result hand-off branch is explicit. The condition is met when the downstream shows a defined empty-result handling path, without claiming that a fictional rule retrieval necessarily returns `[]`.

These checks describe expected behavior. They do not report a test that was run, an approval that was granted, or a deployment that occurred.
