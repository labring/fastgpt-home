# Franchisee onboarding: workflow routing for multilingual work

## What the documents look like

Opening coaching transfers operating capability rather than filing a legal disclosure, so the material set differs from franchise registration work. The documents in scope are training sign-in sheets, opening checklists, SOP manuals and assessment scores. Sources include the training system, the supervisor app, store photographs and the headquarters SOP library. In a cross-border setting the same SOP manual may exist in a headquarters-language version and a store-locale version, while sign-in sheets and checklists may carry region-specific field names, date formats and signature blocks. Those differences decide whether a retrieval result can be used at all: a multilingual search must first establish which language version, which store and which period the request points to before any material is passed to a later node. The brief gives a per-store, monthly update rhythm. This page does not derive batch synchronisation, full synchronisation or real-time triggering from that rhythm.

Three industry facts shape this page. First, the deliverable is a capability handover, so a checklist signature and a training record are operational evidence, not legal filings. Second, the material set is multilingual by default, so language identity travels with every record. Third, the same document type can differ in field names and date format across regions, so a query that matches semantically may still point at the wrong version.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The node collects the required values the user submits and passes them to later nodes. The user selection node behaves the same way at the state level: it triggers an interaction state, records workflow state, and after the user makes a choice it evaluates that choice and executes the "yes" branch. Documented behaviour covers state recording, waiting for completion, and continuation. The documentation does not describe a global state-recording switch, a submission-count control, an automatic judgement step or a snapshot guarantee, and this page does not assert any of them.

Retrieval at this step performs semantic association between a query and knowledge-base content. It does not perform permission judgement or entity isolation. A relevance score reflects semantic closeness; it does not distinguish store ownership and does not decide whether a given franchisee may view a given SOP. Forms collect values. Business verification, approval, database writes and external synchronisation require a separate business interface or a downstream process.

Hypothetical paper exercise. A chain brand training department receives a request to be filed, worded as: "The Chinese version of the Opening Checklist submitted by franchisee Chen in March 2025, for April opening-coaching review." The material supplied for comparison reads: "Opening Checklist, Chinese version, store number A-102, submission date 18 March 2025, signature block completed with the name of regional supervisor Li." The draft sentence to be judged is: "This checklist has been signed and can be used for opening-coaching review." The material shows only that a supervisor name appears in the signature block. It does not state a signing completion time and does not state the scope of review authorisation. The phrase "has been signed" is therefore unsupported by the supplied material, and the authorisation boundary for "can be used for review" is likewise missing. Both are recorded as pending verification. A pending request is not an approval, and an offered option is not an execution.

## Three common errors

1. Treating a retrieval relevance score as a store-ownership or permission filter. The score reflects semantic proximity only. It does not separate records for store A-102 from records for other stores, and it does not decide whether a franchisee may view a document. Executable check: submit one query and compare the store-number field of each returned record against the requested store number; observe whether records from other stores appear.
2. Treating form submission as completed business verification. The form input node collects and passes values. Whether a signature is complete and whether a review is approved are separate facts. Executable check: take the sample above and compare the signature block in the material text against the draft phrase "has been signed"; observe whether the material states a signing completion time. If it does not, record the phrase as unsupported.
3. Treating interaction-state recording as a global switch or a snapshot guarantee. The documentation states that an interaction node records workflow state and continues after the interaction. It does not state that a global state-recording switch or a submission-count control exists. Executable check: trigger the form input node once and compare the conversation state before and after the node against the parameters received by the following node; observe whether those parameters come from this submission.

## How to verify the setup

1. For the sample draft sentence "This checklist has been signed and can be used for opening-coaching review", input the material text and the draft sentence, then compare the signing-completion field. The material signature block contains only a supervisor name and no signing completion time, so the expected finding is unsupported; the authorisation-scope part is recorded as an evidence gap.
2. For the retrieval step, input the query "store A-102 opening checklist Chinese version" and compare the store-number and language identifiers of returned records. The expected observation is that only records with matching identifiers are returned. If another store number appears, or a record carries no language version, record it as pending verification. This page does not claim that an unrelated query must return an empty result.
3. For empty-result receiving, pass the paper input `[]` to the downstream node and compare whether the downstream design provides an explicit branch for an empty array. The expected observation is that the empty result is handled as a separate case. This page does not claim that a fictional rule-based retrieval necessarily returns `[]`.

All three checks are paper comparisons. No deployment, approval submission, signing or review action has taken place. Where a document field was not supplied, it remains unknown.
