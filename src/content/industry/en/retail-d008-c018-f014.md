# Regional dealer stock: model connections for multilingual work

## What the documents look like

Regional dealer stock replenishment runs as a daily rolling order flow, which differs in rhythm from seasonal centralized ordering. The working data comes from dealer ERP, the brand ordering system, warehouse stock, and sales collections. The documents handled at this step are replenishment applications, inventory turnover sheets, outbound delivery notes, and collection plans. Cross-border and multilingual retrieval has to work across Chinese, English, and other languages mixed inside the same replenishment application or turnover sheet. Retrieval output supports manual checking and does not carry authorization or approval authority. Material updates on a weekly or monthly cadence; this page does not derive real-time synchronization or transaction-triggered behavior from that cadence.

## Constraints at the model connections step

Model access depends on AI Proxy. App and Admin must set `AIPROXY_API_ENDPOINT` to the AI Proxy service root address without appending `/v1`, and must set a non-empty `AIPROXY_API_TOKEN`. A missing value in either place causes startup validation to fail. The system requires at least one language model and one index model. The index model builds indexes over text chunks; the language model produces answers or assists judgment. Multilingual replenishment material requires an index model with the corresponding language capability, and that capability must be checked inside model configuration rather than inferred from retrieval behavior.

Retrieval association requires the same vector model as a precondition. Libraries built on different vector models cannot be jointly associated; the model identifier must be checked first and non-matching libraries excluded. Semantic recall and relevance scores do not perform permission or entity isolation, and the retrieval library does not decide whether a replenishment record falls inside the range the current operator may view. RRF is a hybrid result fusion process, not a switch that can be turned on. Empty-result handling can be checked against the explicit paper input `[]` for downstream design.

Hypothetical paper exercise sample, not a real record: a regional dealer submits a replenishment application reading: "This application covers March 2026 replenishment for the East China warehouse, requested quantity 1200 units, based on row 4 of the February inventory turnover sheet; the applicant signature field is blank. Attached outbound delivery note number CK-2026-0312, status 'shipped'." Proposed judgment sentence: "This replenishment application has been approved." The checking material also contains a collection plan stating "60% collection planned before April 15." Authorization boundary: the material above is used for paper checking only and does not constitute any actual approval, shipment, or collection action.

## Three common errors

1. Treating retrieval output as authorization evidence. Input: the replenishment application and proposed judgment sentence in the sample. Error: concluding the approval is complete because the application was retrieved. Check: compare the signature field state in the application text against the evidence required for "approved"; with the signature field blank, the judgment sentence is not supported.

2. Jointly associating knowledge bases built on different vector models. Input: two replenishment libraries whose index model identifiers differ. Error: running a combined retrieval over both libraries and judging missed recall from that result. Check: verify the model identifier of each library first; when identifiers differ, exclude joint association and record only the separate retrieval observations.

3. Reading a pending status as a completed fact. Input: the outbound delivery note marked "shipped" and the collection plan stating "60% collection planned before April 15." Error: treating the collection plan's planned status as completed collection or effective authorization. Check: compare the collection plan fields against the evidence required for completed collection; a planned status does not constitute a completed fact.

## How to verify the setup

1. Check startup validation. Input: the configured values of `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN`. Compare: whether both are non-empty and the endpoint carries no `/v1`. Observation: when either value is missing, startup validation fails; when both are correct, the service starts normally.

2. Check the minimum model requirement. Input: the list of enabled models in the system. Compare: whether at least one language model and one index model are present. Observation: when either category is missing, the system does not meet the minimum requirement; when both exist, it does.

3. Check the judgment boundary of the hypothetical sample. Input: the sample source text and the proposed judgment sentence "This replenishment application has been approved." Compare: the application's signature field is blank, while the judgment sentence requires completed approval. Observation: with the signature field blank, the judgment sentence is not supported; record the evidence gap and keep the item pending verification.
