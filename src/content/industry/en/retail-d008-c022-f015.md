# Omnichannel stock transfers: retrieval for multilingual work

## What the documents look like

Omnichannel stock transfers move goods between stores and warehouses. The work does not involve marketing outreach to customers; it tracks physical inventory as it changes location. The main data sources are ERP inventory, store POS, e-commerce orders and WMS. The documents handled day to day include transfer requests, inventory snapshots, store shortage lists and transfer logistics notes. In a cross-border and multilingual setting, one transfer batch may carry Chinese, English or other language versions of the same transfer request and logistics note, and retrieval has to reach the same business object across languages.

Data updates on a daily or weekly cycle. A retrieval result reflects the state of the material when it was indexed; it does not perform real-time inventory reconciliation. The consequences of getting this wrong are overselling, store stockouts and book-to-physical mismatches, which is why the retrieval step has to be checked against the material it is meant to serve.

## Constraints at the retrieval step

The knowledge base search node can associate one or more knowledge bases that use the same vector model. Knowledge bases built on different vector models cannot be associated together. The vector model identifier has to be checked first, non-matching bases excluded, and the actual observation recorded; a cross-model search is not run to compare missed recalls.

Retrieval output is an array of references, and its length can be zero. When nothing is found, the output path still runs through. Semantic search can match across languages, so a Chinese question can reach an English knowledge point, with the result depending on how the vector model was trained. The minimum relevance value is a filter threshold and takes effect only in semantic search or when result reranking is used; it does not perform permission or entity isolation. Hybrid search merges multiple result paths through RRF, which is a fusion process rather than a separate switch that can be turned on.

Image retrieval requires an image input and model capability. Reranking requires a rerank model and is enabled according to configuration. The optional paths drawn in the overall retrieval flow diagram do not mean every request executes all of them. A document field that is not provided remains unknown.

## Configuration and implementation checks

The following items are checked against a hypothetical drill sample. Hypothetical drill sample: a brand supply chain specialist submits a transfer request on 10 March 2026, asking to transfer 200 units of style A coats from the East China warehouse to a Shanghai store. The request states "transfer status is pending review." The logistics note states "estimated arrival: 15 March 2026." The draft sentence to be judged is "This transfer request has been approved and can be scheduled for shipment." No approval record appears in the sample material, and a pending-review status does not show that approval is complete.

| Configuration item | Starting point for this hypothetical trial | Reason and comparison method |
| --- | --- | --- |
| Associated knowledge bases | Associate only transfer material bases that use the same vector model | Check the vector model identifier of each base and exclude those that do not match |
| Search mode | Hybrid search | The sample contains coded fields and natural-language description; compare against pure semantic and pure full-text results |
| Reference limit | Hypothetical starting value of 2000 tokens | Test with transfer requests and logistics notes of different lengths for content completeness, compared with 1000 and 3000 |
| Minimum relevance | Hypothetical starting value of 0.4 | Label relevant and irrelevant passages in the sample first, then compare filtering against 0.3 and 0.5 |
| Question optimization | Enabled | Compare the original question and the optimized question across multi-turn follow-ups, checking whether the subject was changed incorrectly |
| Result reranking | Enabled according to configuration | Check whether a rerank model is configured, and compare ordering before and after reranking |

## Three common errors

1. Treating a retrieval hit as approval authorization. Input is the sample transfer request; compare the "pending review" status against an approval record. When the material contains no approval field, the draft sentence "has been approved" is not supported.
2. Treating minimum relevance as a permission filter. Input is the sample transfer request; compare the retrieved content against the access permission list. If the returned content includes material from other stores that the requester may not view, the relevance threshold does not perform permission isolation.
3. Forcing association of knowledge bases with different vector models. Input is two knowledge bases whose vector model identifiers differ; compare the identifier fields. When the identifiers do not match, they cannot be associated together; record that observation and do not infer a runtime result.

## How to verify the setup

1. Input the sample transfer request text and the draft sentence "This transfer request has been approved and can be scheduled for shipment." Compare "transfer status is pending review" in the source with "has been approved" in the draft. When the source has no approval record, the draft sentence is not supported and is marked as pending verification.
2. Input the sample logistics note text "estimated arrival: 15 March 2026" and the draft sentence "The goods arrived on 15 March." Compare the "estimated arrival" field with the "arrived" field. When the source states only an estimated date, the arrival fact is not supported.
3. Input an empty reference array [] and the downstream node. Compare whether the downstream node accepts the empty result normally. When the downstream path runs through without error, empty-result handling matches the documented behavior; this check does not claim that a fictional rule search always returns [].
