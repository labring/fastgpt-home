# Retail checkout and loyalty: document chunking for multilingual work

## What the documents look like

Retail checkout and loyalty documents revolve around prices and membership entitlements. The main sources are the POS system, the member CRM, payment platforms and the price-tag system. Day-to-day documents include promotional price tags, member points rules, checkout daily reports and exception refund slips. Compared with convenience-store fresh-food ordering, this category does not handle short-shelf-life inventory; the focus sits on consistency of price and entitlement wording. Materials update daily or per shift, so parsing and chunking must let the same price tag or points rule keep a document identity and version that can be traced back across repeated retrievals. In cross-border and multilingual settings, one promotion rule may appear in several languages. Semantic retrieval offers cross-language understanding, but if chunking separates a condition from the amount it constrains, a retrieval hit still cannot reconstruct which object the condition applies to.

## Constraints at the document chunking step

Chunking follows the structure of the specific material, so conditions, notes and the content they constrain are not split apart. Original data and retrieval indexes are distinct: one group of data can map to multiple vectors, and the vector score takes the highest score. Full-text retrieval suits numbers, models and proper nouns; semantic retrieval suits natural-language phrasing; hybrid retrieval combines the two paths through RRF; a rerank model can reorder candidate text and produce a 0-1 score. The reference cap controls, in tokens, the maximum content quoted per search. The minimum relevance score takes effect only in semantic retrieval or when result reranking is used; it is a filter threshold and does not perform permission or entity isolation. Retrieval is a recall action, and business authorization, approval and database writes each need their own downstream implementation.

Hypothetical paper exercise sample: a store price-tag system exports a piece of material to be checked. The source text reads: "This store's member-day promotion takes effect from March 1. Members buying marked items receive a 10% discount; non-members settle at the original price. This rule applies to this store's checkout counter and remains valid through March 31." A handover request to be judged reads: "Please confirm that this promotion rule also gives a 10% discount to non-members visiting the store on April 5." The check compares the request date against the source validity period and the request subject against the source applicable subject. The source does not state applicability for April 5, so the request remains unsupported.

| Index creation | Confirm the text index exists at ingestion | Image retrieval additionally depends on a vision model or a vector model that supports images |
| Post-update review | Check actual training and index status after material changes | A successful upload does not mean retrieval has updated |

## Three common errors

1. Treating the minimum relevance score as a permission or entity filter. The minimum relevance score is a 0-1 filter threshold that only affects which low-relevance results are kept or dropped; a similarity setting does not exclude unrelated businesses or unauthorized records. To check, submit the same query under different thresholds and observe whether returned content changes only by relevance, while permission decisions follow a separate business check.
2. Treating a successful upload as updated retrieval. After a material change, actual training and index status need a separate check. To check, retrieve the same term before and after the update and compare whether returned content reflects the new version; if it does not, record it as pending verification.
3. Describing RRF as a switch that can be turned on. RRF is the process that fuses multiple result paths in hybrid retrieval, and the documentation provides no corresponding switch. To check, confirm whether such a field exists in the configuration interface; if it does not, record it as not described in the documentation.

## How to verify the setup

1. Enter the hypothetical sample source text and the request "Please confirm that this promotion rule also gives a 10% discount to non-members visiting the store on April 5," then compare the request date against the source validity period and the request subject against the source applicable subject. The source states only validity through March 31 and a member subject, so the satisfying result is a judgment of unsupported, with the evidence gap preserved.
2. Enter one term, one number and one natural-language question, then compare whether chunking keeps each condition together with the amount it constrains. The satisfying result is that hit content can be traced back to the same source paragraph, with condition and amount not split apart.
3. Enter the hypothetical paper empty-result set [] and check how the downstream design handles an empty reference. This input checks whether the downstream continues with no reference; it does not mean any rule retrieval necessarily returns an empty result.

Libraries across different vector models cannot be associated together. During checks, inspect identifiers only and exclude non-matching ones, record actual observations, and do not run cross-model retrieval to compare missed recalls. Image retrieval and reranking are optional paths and require the corresponding image input and model capability, enabled according to settings; they do not mean every request executes all paths.
