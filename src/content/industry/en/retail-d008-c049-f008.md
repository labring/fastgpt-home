# Wholesale stall trading: workflow routing for multilingual work

## What the documents look like

Wholesale market stall trading is more fragmented than regional dealer replenishment and depends on on-site bargaining and consignment shipping. The records are less standardized. Purchase notes, handwritten sales slips, stall lease contracts and payment receipts form the main material for cross-border document checking. On a handwritten sales slip, the handwriting, the amount and the link to a consignment waybill require manual confirmation. Material is updated daily and per transaction, so retrieval must draw data within a single transaction scope. Combining all documents of one day into one request does not match how the records are kept.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it is triggered, the conversation enters an interaction state, the workflow state is recorded, and the dialog box is hidden. The user fills in required information and submits it; the node then collects the submitted form information and passes it to later nodes. The user selection node is also a user interaction node with the same interaction state, recorded workflow state and hidden dialog box. After the user makes a choice, the node evaluates that choice and executes the "yes" branch. Retrieval at this step can only accept fields that an upstream node has explicitly passed out. Retrieval itself does not constitute authorization for a transaction, a payment or stall rights.

Hypothetical paper exercise sample. The material text reads: "Stall A issued a handwritten sales slip to Buyer B on 10 March 2025, stating three boxes of goods and an amount of four thousand yuan, consignment waybill number T-0310; no payment receipt is attached." The draft sentence to be judged is: "This transaction has completed payment settlement." The parties needed for the judgment are Stall A and Buyer B, the period is 10 March 2025, and the field is payment status. The source text states only the sales slip and the waybill number. It does not state a payment receipt, so payment status remains unsupported and the evidence gap must be kept open.

## Configuration and implementation checks

| Configuration item | Documented basis | Implementation check |
|---|---|---|
| Form input node | Enters interaction state when triggered; collects required information | Check whether required fields cover the party, the object and the document number |
| User selection node | Executes the "yes" branch after the user makes a choice | Verify each branch connection against its downstream node |
| Interaction state check | Recording state is behavior of the interaction node | Do not add or claim a separate global state recording switch |
| Output handoff check | Information is passed to later nodes | Compare each passed field with the retrieval input |
| External action split | Order writes and external synchronization require a separate interface | Confirm retrieval is not treated as authorized execution |

The hypothetical trial starting point for this page is a single-transaction scope. The reason is that this category updates per transaction, and comparing it with a whole-day document scope makes the difference in retrieval input observable. This starting point is a hypothetical setting for this exercise, not an official default value.

## Three common errors

1. Treating a retrieval hit as evidence that payment is settled. In the sample, the sales slip and the waybill number are retrieved, but the payment receipt is absent, so payment status remains unsupported.
2. Treating the "yes" branch of the user selection node as an approval. The branch only shows that the user made a choice. It does not show authorization or business execution.
3. Associating libraries that use different vector models. First check the identifiers and exclude those that do not match, then record what is actually observed. Do not infer missed recall or redundant results.

## How to verify the setup

1. Input the sample source text and the draft sentence, then compare whether the party, the period and the field come from the same source. The draft sentence is supported only when the source states a payment receipt and the status agrees. The current sample shows it is unsupported.
2. Use an explicit paper input of [] to check the downstream design for an empty result, and observe whether the downstream node handles the empty input as designed. Do not claim that a fictional rule retrieval necessarily returns [].
3. Check the fields passed out by the form input node and the user selection node, then compare whether the retrieval input corresponds item by item with the node output. The condition is met when the fields agree and the branch connections are correct. When it is not met, record the gap and do not supply an authorization clause.
