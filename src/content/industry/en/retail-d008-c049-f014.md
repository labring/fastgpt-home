# Wholesale stall trading: model connections for multilingual work

## What the documents look like

Wholesale stall trading produces documents in a scattered pattern. On the same day, a stall may generate a purchase receipt, a handwritten sales slip, a stall lease contract, and a payment receipt, each with a different format and no shared numbering. Cross-border material handling and multilingual retrieval must translate and locate these items, and the data updates daily and per order.

For model connection and configuration, this pattern means two things. First, the system needs at least one language model and one index model before retrieval can work at all. Second, because a handwritten sales slip and a lease contract may describe the same parties and dates in different wording, the model mapping and model ID must be checked before any retrieval is trusted. The model ID is the value of the `model` field in the request body, and it is globally unique. Model mapping takes the model FastGPT requests and maps it to the upstream model that actually serves the call. A retrieval library's vector model requirement is a retrieval-side condition; it does not extend to external business registration sites or other systems. Semantic recall and relevance scores do not perform permission or entity isolation.

## Constraints at the model connections step

AI Proxy is a required dependency. Both the App and any Admin service that reuses App/Service configuration must set `AIPROXY_API_ENDPOINT` and a non-empty `AIPROXY_API_TOKEN`. Missing either one causes startup validation to fail. The endpoint is the AI Proxy service root address and does not carry `/v1`. The token is the AI Proxy administrator token and must match the server configuration; an application API key does not substitute for it.

The system needs at least one language model and one index model to function. Model types include language, index, rerank, speech synthesis, and speech recognition. A model can be configured across multiple channels for load balancing, and channel priority ranges from 1 to 100, with higher values selected more readily.

Model status probing applies only to currently enabled system models. Disabled models do not participate and produce no history. A probe request that fails is retried up to 3 times, so a single round makes at most 4 attempts; one success marks the round valid, and only 4 failures mark it abnormal. Health states are normal (green, latency at or below 30s), high latency (yellow, success above 30s), and abnormal (red, 4 consecutive errors). Webhook alerts fire on edge changes only, with event types `model_status_error` and `model_status_recovered`, one notification per model, not merged.

Hypothetical drill sample. A handwritten sales slip reads: "March 12, 2026, stall A sold 40 boxes of dried chili to buyer B; unit price and total price to be negotiated separately; shipping arranged by the buyer; balance unpaid." A stall lease contract reads: "Lessor C and lessee D agree the lease starts April 1, 2026; monthly rent to be negotiated separately; deposit not stated." A draft sentence awaiting review reads: "Both the sales slip and the lease contract have been settled and shipping has been completed." The materials do not state settlement, completed shipping, or deposit status.

## Three common errors

1. Treating model mapping as authorization. Mapping changes only the upstream `model` field; it does not change whether materials are settled or shipping is complete. Check input: the mapping configuration and the sales slip text. Compare the `model` value before and after mapping. Observable result: mapping takes effect while the settlement state remains unstated.

2. Treating relevance score as an entity filter. A relevance score does not exclude unrelated businesses or unauthorized records. Check input: a retrieval request and the lease contract text. Compare returned entries against the contract parties. Observable result: returned content does not change authorization state based on score.

3. Treating a pending review as an approval. A pending review does not show that an operation lacks permission, and it does not equal completed execution. Check input: the draft sentence and the two materials. Compare "settled and shipping completed" against the source text. Observable result: the source does not state that status, so the claim is unsupported.

## How to verify the setup

1. Input: the sales slip text above and the draft sentence "Both the sales slip and the lease contract have been settled and shipping has been completed." Compare the settlement and shipping completion in the draft against the source record. The source states only the sale, that shipping is arranged by the buyer, and that the balance is unpaid. It does not state settlement or completed shipping. Result: unsupported.

2. Input: the lease contract text above and the same draft sentence. Compare the start date, rent, and deposit fields in the contract. The contract does not state the deposit or settlement status. Result: pending verification, with the evidence gap preserved.

3. Input: an explicit paper empty result `[]` and the downstream design. Compare the empty-result handling logic against the documented empty-reference output condition, and observe whether the downstream processes it as empty input. Do not claim that a fictional rule retrieval necessarily returns `[]`; missing evidence remains missing.
