# E-commerce warehouse receiving: model connections for multilingual work

## What the documents look like

Inbound putaway handles the first book-to-physical confirmation when goods enter a warehouse. The main data sources are the WMS, ERP purchasing, supplier delivery notes and barcode scanning, and the daily documents include purchase arrival notes, inbound acceptance sheets, putaway tasks and discrepancy reports. Cross-border scenarios frequently add multilingual fields to these documents, so receiving clerks rely on retrieval to confirm product names, specifications and batch information. Model connections and configuration determine whether retrieval returns usable text as expected, and a configuration error directly affects two of the most time-consuming steps: checking arrived quantities and assigning storage locations.

## Constraints at the model connections step

Multilingual material contains text blocks in different languages. The index model handles vectorization and the language model handles generation, and the system needs at least one language model and one index model before it works normally. The model ID is globally unique and is the value of the `model` field in the request body; retrieval association follows that identifier. AI Proxy is a required dependency. `AIPROXY_API_ENDPOINT` holds the service root address without `/v1` appended, and `AIPROXY_API_TOKEN` must match the server side and be non-empty. Model capabilities are checked against the inputs the application needs, with multimodal input, tool calling and thinking configuration verified separately. Retrieval itself carries no permission or entity isolation, and a similarity setting does not exclude unrelated business records or unauthorized records.

Hypothetical paper exercise: a warehouse receives a supplier delivery note whose two source passages read "PO-2026-0417, product name Stainless Steel Bottle 500ml, quantity 1200 pcs, batch B2409" and "arrival date 2026-04-17, receiving warehouse WH-SH-02, supplier signature field blank." The draft sentence to be judged is "This batch of 1200 pcs has completed acceptance and has been assigned location A-03." Checkpoints: the delivery note states quantity and batch; the blank signature field means the supplier's signing status is not stated; acceptance and location assignment are downstream business actions. The draft sentence turns an unstated status into a completed fact.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting value | Reason and comparison object |
| --- | --- | --- |
| AIPROXY_API_ENDPOINT | Assume `http://aiproxy:3000` | Documentation requires the root address without `/v1`; compare against a writing that appends a path |
| AIPROXY_API_TOKEN | Assume a non-empty value matching the server side | Documentation requires a matching non-empty administrator token; distinguish from an application API key |
| Index model | Assume one embedding model that has passed a channel test is enabled | Documentation requires at least one index model; compare against an unenabled state |
| Language model | Assume one llm model that has passed a channel test is enabled | Documentation requires at least one language model; compare against index model only |
| Model ID | Assume the value of the model field in the channel is reused | Documentation states it is globally unique; compare against a self-rewritten alias |
| Model capability check | Assume each item is verified against multilingual text input | Documentation requires checking against needed input; compare against enabling without verification |

This table records implementation checks tied to the documents on this page. The starting values are hypothetical trial points for this exercise, not documented defaults.

## Three common errors

1. Treating "has completed acceptance and has been assigned location" in the draft sentence as a fact already stated on the delivery note. The signature field is blank, acceptance and location assignment are downstream actions, and the input contains no corresponding record, so the draft is unsupported.
2. Filling `AIPROXY_API_TOKEN` with an application-side API key. Documentation requires the administrator token to match the server side; the two have different sources, and mixing them causes startup validation failure or rejected calls.
3. Using a similarity setting to infer that retrieval has excluded unauthorized records. A relevance score carries no permission or entity isolation, and retrieval results still need manual checking of subject and scope.

## How to verify the setup

1. Input the hypothetical delivery note passages and the draft sentence, then compare whether the draft writes the blank signature field as signed and the unstated acceptance and location as completed. Expected observation: the draft does not match the source status and is marked unsupported.
2. Input the hypothetical `AIPROXY_API_ENDPOINT` value and compare whether it appends `/v1` or `/chat/completions`. Expected observation: a writing with an appended path does not match the documented requirement and needs to be changed to the root address.
3. Input retrieval requests carrying two different model IDs and compare whether returned records are all labelled with the same model identifier. Expected observation: records cannot be associated across models; keep only those with a matching identifier, exclude the rest, and record the actual observation and the remaining gap.

Missing evidence stays missing. A pending request is not approval, an offered option is not execution, and an unsigned termination is not a completed termination.
