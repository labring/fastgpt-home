# Short-video affiliate sales: workflow routing for multilingual work

## What the documents look like

Short-video affiliate sales rely on long-term content exposure and product-link conversion. They do not depend on live explanation, so the cross-border materials and multilingual retrieval inputs for this category are typically short-video scripts, attached-product lists, commission plans and violation feedback. These materials are updated daily or weekly. During handover, operations staff distinguish whether a material sits in draft, pending review, submitted or effective status. Retrieval only locates relevant documents. It does not replace an authorization decision.

## Constraints at the workflow routing step

The Form Input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. It collects required information and passes that information to later nodes. The User Selection node also enters an interaction state and records workflow state. When the user makes a choice, the node evaluates that choice and executes the "yes" branch. Branch connections need to be verified one by one. The interaction state is recorded by the node itself. No separate global state-recording switch is documented. Collected information must be explicitly passed to later retrieval, judgment or interface nodes, and outputs are compared against inputs item by item. Order writes, document backfill and external status synchronization require a separate business interface or later process.

Hypothetical paper exercise sample: the material text reads, "A short-video script was submitted on March 1, 2025, the attached product is item A, the commission plan status is pending review, and the violation feedback field is empty." The proposed copy sentence reads, "This script has passed review and can be used for affiliate distribution." The check compares the script status field with the description in the proposed sentence. Pending review does not equal passed. The proposed sentence is unsupported. A separate paper input of [] checks downstream handling of an empty result. No claim is made that a fictional rule search necessarily returns [].

The hypothetical starting value for this exercise is the status "pending review." This value is chosen because the material text states it explicitly. The comparison object is the proposed sentence "has passed review."

## Configuration and implementation checks

| Configuration item | Relevant setting or check on this page | Relation to the sample |
| --- | --- | --- |
| Form Input node | Enters interaction state on trigger, collects required information, passes it to later nodes | Collects script ID, product and status fields |
| User Selection node | Executes the "yes" branch after the user makes a choice; verify branch connections one by one | Branch decides whether the proposed sentence can be submitted |
| Output handoff check | Explicitly passes collected information to later retrieval, judgment or interface nodes | Compares script status with the proposed sentence |
| Retrieval scope check | Confirms materials sit within an accessible target retrieval scope | Script and commission plan must be in scope |
| Empty-result handoff | Uses paper input [] to check downstream design | Handling when violation feedback is empty |
| External action split | Order writes, document backfill and external status synchronization connect to a separate business interface | Passed review requires a separate system implementation |

## Three common errors

1. Treating pending review as passed. The input is the material text "the commission plan status is pending review," compared with the proposed sentence "this script has passed review." Directly outputting passed is an error.
2. Treating a retrieval hit as authorization. The input is a retrieved script record, compared with its authorization status field. Executing the attached-product action without checking that status is an error.
3. Treating form collection as a database write. The input is the script ID collected by the form, compared with whether a later node connects to a separate business interface. Assuming an automatic write is an error.

## How to verify the setup

1. Input the material text "A short-video script was submitted on March 1, 2025, the attached product is item A, the commission plan status is pending review, and the violation feedback field is empty." Compare the proposed sentence "This script has passed review and can be used for affiliate distribution." The condition is met when the output marks the proposed sentence as unsupported.
2. Input the paper input []. Compare whether the downstream design handles an empty result. The condition is met when no claim is made that a fictional rule search necessarily returns [].
3. Input the script ID collected by the form. Compare whether a later node explicitly passes it to a retrieval or interface node. The condition is met when no automatic write is assumed.
