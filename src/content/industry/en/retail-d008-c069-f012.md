# Dealer rebate calculation: document chunking for multilingual work

## What the documents look like

Rebate calculation happens after sales. The decisive material is the policy wording and the financial treatment, not the movement of goods. In cross-border work, four document families carry that material: rebate policies, sales achievement tables, reconciliation statements, and red-letter invoices. These may sit in different languages and different systems, and the same item may exist in more than one version.

Documents update monthly or quarterly. Parsing and chunking must therefore preserve a document identity and version that can point back to the source text, so a later check can locate the specific clause that was applied. Multilingual retrieval through semantic recall relies on the documented characteristics of vector search: it handles close meaning and cross-language matching, and its precision depends on model training quality and on how complete the sentences are. Whether a segment is complete therefore determines whether retrieval can reach both a condition and the content that condition constrains.

## Constraints at the document chunking step

Chunking must follow the structure of each document. A condition, its explanation, and the object it constrains should not be separated. Original data and retrieval indexes are two layers. One set of original data can map to several indexes, and a shorter, more precise index content raises precision while narrowing retrieval range.

The retrieval step does not perform authorization. The minimum relevance value is a filter threshold, not a permission or entity-isolation mechanism. Retrieving a document does not mean the current operator may act on it to execute a rebate, issue an invoice, or offset an amount. Hybrid retrieval merges multiple result paths through RRF, which is a result-combination process. Image retrieval requires corresponding image input and model capability, and reranking requires an available model enabled by configuration. These paths do not all run on every request.

Hypothetical paper exercise sample: A brand finance user, during a quarterly rebate reconciliation, receives a dealer reconciliation statement. The source text contains three sentences: "Returns for this period have been deducted from achieved sales volume. The rebate rate follows Appendix 2 of the contract. This reconciliation statement may serve as the basis for invoicing only after both parties confirm it." A handover request draft also arrives: "This dealer's rebate for the quarter has been reconciled and can be invoiced and offset directly." The question to judge is whether the draft's claim of completed reconciliation and direct invoicing authority is supported by the source text above. The source text states only the deduction basis, the source of the rate, and a confirmation precondition. It does not state that confirmation is complete, and it does not state that invoicing is authorized. The draft is therefore unsupported.

## Three common errors

1. Treating a retrieval hit as authorization. Incorrect behavior: because a reconciliation clause was retrieved, the user assumes invoicing and offset have been approved. Check: input the reconciliation source text above and the handover request draft, compare the state described in the draft with the state stated in the source text, and when the source text does not state that confirmation is complete, judge the draft as unsupported.

2. Treating the similarity threshold as an entity or permission filter. Incorrect behavior: assuming that raising the minimum relevance value excludes unrelated dealers or unauthorized records. Check: input the same question with different relevance values, compare whether returned content changes, and check whether returned content may still include material the operator is not entitled to use, confirming that the filter threshold does not change the authorization boundary.

3. Treating a successful upload as an updated index. Incorrect behavior: after a document is replaced, retrieving directly under the new wording. Check: input the same term before and after the change, compare the document version corresponding to the returned fragment, and observe whether the old version is still hit; when the training and index state has not been checked, the conclusion remains unknown.

## How to verify the setup

- Verification one: Input the three source sentences of the hypothetical reconciliation statement and the draft sentence "This dealer's rebate for the quarter has been reconciled and can be invoiced and offset directly," then compare whether the draft is supported by the source text. The source text states only the deduction basis, the source of the rate, and a confirmation precondition. It does not state that confirmation is complete or that invoicing is authorized. The expected judgment is unsupported, and the evidence gap remains open for further verification.

- Verification two: Input one query containing an identifier and one natural-language query, then compare whether the returned fragments under the two modes cover both the conditional sentence and the content it constrains. When chunking is complete, the condition and the constrained content are expected to appear in the same segment. If the conditional sentence is separated, record it as a chunking problem and do not conclude from that alone that retrieval must fail.

- Verification three: Input an explicit paper input [] and check the downstream design, comparing whether the downstream process handles an empty result as designed; do not claim that a search for a fictional rule necessarily returns [].
