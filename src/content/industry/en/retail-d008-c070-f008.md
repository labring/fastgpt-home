# Cross-border product labels: workflow routing for multilingual work

## What the documents look like

Cross-border product compliance happens before listing and before import, and its core evidence is product safety and label material. The documents handled day to day include product test reports, English labels, MSDS files and platform prohibited-item lists. Sources span platform policy centers, testing laboratory reports, destination-country regulation libraries and supplier material. Updates are irregular, and each new listing can bring a new report version and new label text.

When this material enters retrieval it shows multilingual, multi-version and multi-source characteristics. One product may have a Chinese test report and an English label at the same time, and the two do not use the same field names or the same wording for conclusions. Retrieval needs cross-language alignment while keeping the source and version of each item so a person can check it later.

## Constraints at the workflow routing step

Workflow routing does two things in this task: it collects the information needed for checking, and it passes retrieval results to downstream judgement. When the form input node is triggered, the conversation enters an interaction state and the workflow state is recorded. After the user fills the required information and submits, the node passes that information to later nodes. The user selection node judges the user's choice and executes the corresponding "yes" branch. Both nodes are user interaction nodes, can be added repeatedly, and trigger execution.

Retrieval itself is not authorization. A form collects values; business verification, approval, database writes and external synchronization each need their own downstream implementation. Interaction nodes record state. The documents do not describe a global state-recording switch, a submission-count limit or an automatic judgement mechanism. The requirement that a retrieval library and a vector model be associated applies to the retrieval library itself and does not extend to external systems. Hybrid result fusion is a process inside retrieval, and no corresponding switch is described.

Hypothetical paper exercise sample

Source text one: "This report covers model A-100 children's water cup and was completed using the sample provided by the commissioning party for migration testing. Report number TR-2405, issue date 10 May 2024. The report conclusion covers only the submitted sample."

Source text two: "The English label draft states the applicable age as 3 years and above and the material as polypropylene. It does not state the manufacturer address or the batch number."

Draft sentence to be judged: "This model of children's water cup has completed destination-country compliance testing, the label information is complete, and it can be listed directly."

Handover request: "Please confirm whether the test report and English label for A-100 meet listing conditions, and arrange the follow-up actions."

The sample above is a paper exercise used to explain the checking method. It was not actually executed.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason for the choice and comparison method |
| --- | --- | --- |
| Form input node fields | Product model, report number, label language | Corresponds to model A-100, report number TR-2405 and the English label in the sample; compare each entered value against the source text |
| User selection node branches | Two branches: "material complete" and "material pending" | Corresponds to the judgement need in the handover request; check whether the selection result enters the matching branch |
| Retrieval input | Model A-100 and report number TR-2405 | Uses the sample identifiers as retrieval conditions; observe whether returned material carries the same identifiers |
| Output handover | Pass retrieval results to a manual checking step | Compare node output against form input item by item and confirm the information is passed completely |
| Empty-result handling | Check the downstream design against the paper input [] | Observe how the downstream node receives a result set with no items; do not assume a real retrieval necessarily returns empty |

These starting points are settings for this hypothetical exercise and do not represent official default values.

## Three common errors

1. Treating form submission as completed compliance approval. The form input node collects required information and passes it to later nodes; approval needs a separate implementation. Check: enter the handover request from the sample, compare the node output against approval records, and when no approval record is observed, mark the matter as pending verification.

2. Treating a retrieval result as an authorization basis. A retrieval returning material that contains TR-2405 does not mean that material has been approved. Check: enter model A-100, compare the report number in the returned material against the value entered in the form, and when the identifier matches but no authorization field is present, keep the gap open.

3. Expanding the coverage stated in the source text. The sample report conclusion covers only the submitted sample, while the draft sentence says destination-country compliance testing has been completed. Check: enter the draft sentence and the report source text, compare the subject, the object and the effective scope, and when the scopes do not match, mark the statement as unsupported.

## How to verify the setup

1. Form collection check. Enter model A-100, report number TR-2405 and the label language from the sample, compare the form fields against the source text, and confirm the condition is met when the field values match the source text and the submitted information appears in the input of a later node.

2. Branch execution check. Enter the handover request, select the "material pending" branch, compare the node output against the selected branch, and confirm the condition is met when the executed path matches the selection. Run the same path check when "material complete" is selected.

3. Retrieval identifier check. Enter model A-100, compare the report number in returned material against the form value, and record what is observed when material with a matching identifier is kept and material with a non-matching identifier is excluded. For an empty result, check the downstream receiving design against the paper input []; do not claim that a retrieval under invented rules necessarily returns [].

Situations that are not stated, or that have evidence only at a related stage, are recorded as unsupported or pending verification. A pending review does not mean operating permission is absent, and a quotation validity period does not mean a supply period. Evidence gaps stay as gaps.
