# Cross-border resale returns: document chunking for multilingual work

## What the documents look like

Cross-border return refurbishment handles reverse logistics and item condition. It sits on a different chain from first-leg replenishment, where goods move forward into overseas warehouses. The records here come from overseas warehouse WMS, TikTok return centers, Amazon return reports, and item inspection photos. They form four document types: return inspection sheets, refurbishment records, scrap or disposal forms, and relisting lists. These materials are produced daily or per batch, and for one item the inspection conclusion, refurbishment action, and relisting decision are spread across separate documents.

Two features of this material shape chunking work. First, condition and conclusion travel together. An inspection sheet carries a grade decision, a refurbishment record carries packaging and process steps, a disposal form carries a final disposition, and a relisting list carries the sellable scope. If a chunk splits a condition clause from the conclusion it governs, a retrieved fragment arrives without the basis for its judgment. Second, the same item is described in Chinese terms, identifiers, and status wording that multilingual retrieval must keep intact inside one data block. The source data sits in the MongoDB `dataset.datas` table, where an `indexes` field records the corresponding vector IDs; one set of data can map to multiple vectors. Vectors live in the `vector` field in PostgresSQL. Retrieval recalls vectors first, then uses the vector ID to fetch the original data from MongoDB, and when records resolve to the same original data they are merged with the highest vector score retained. Chunk quality therefore affects how readable the merged recall result is.

## Constraints at the document chunking step

The parsing and chunking step must keep the subject, item object, status, and validity scope inside the same data block so later retrieval can cite them. A return inspection sheet states a grade; a refurbishment record states packaging and process; a disposal form states an outcome; a relisting list states a sellable range. Splitting these apart weakens every downstream citation.

A hypothetical paper exercise clarifies the boundary. The source text under review reads: "Item A-100, return batch R-2024-05, inspection date 2024-05-10, surface scratches, function normal, grade B assigned, eligible for relisting after refurbishment, refurbishment completed 2024-05-12, packaging replaced, relisting list number S-2024-05-18." A draft sentence awaiting judgment reads: "Item A-100 has completed refurbishment and been approved for relisting." Checking the draft requires comparing the word "approved" against whether the source contains an approving party and an approval record. The source states only a refurbishment completion date and a list number; it names no approving party and no approval action. The draft wording is unsupported, and the evidence gap stays open.

Retrieval is not authorization. Recalling a relisting list number does not mean the item has been cleared for sale; approval and execution require their own downstream implementation. A pending request is not approval, an offered option is not execution, and an unsigned termination is not a completed termination.

## Configuration and implementation checks

| Configuration item | Value or check relevant to this page | Note |
| --- | --- | --- |
| Search mode | Semantic, full-text, or hybrid | Identifier and model-number queries suit full-text or hybrid |
| Reference limit | Measured in tokens; hypothetical trial starting value 2000 | Chosen above the single-chunk average to observe whether long chunks are truncated |
| Minimum relevance | A 0-1 value, effective only in semantic retrieval or with rerank | A filter threshold, not a final ordering rule |
| Question optimization | Can be enabled for multi-turn follow-ups or short questions | Adds one model call before retrieval and increases elapsed time |
| Rerank | Effective when a ReRank model exists and is enabled by configuration | Outputs a 0-1 score usable with minimum relevance for filtering |
| Chunk check | Inspect whether condition, conclusion, and validity scope share a block | A manual review item, not an automatic switch |

The 2000-token starting value is a hypothetical trial figure for this exercise, not an official default. It is compared against the observed average chunk length to see whether long blocks are cut. Minimum relevance is a filter threshold; a relevance score is not a category, entity, or permission filter, and a similarity setting does not exclude unrelated businesses or unauthorized records. RRF is a fusion process for mixed results, not an enable switch. Image retrieval requires an image input and matching model capability; rerank requires a model enabled by configuration. Optional paths in the overall retrieval flow are not executed on every request.

## Three common errors

1. Treating "approved" in the draft sentence as a fact already stated in the source. The source carries only a refurbishment completion date and a list number, with no approving party and no approval record, so the wording is unsupported.
2. Treating a successful upload as proof that retrieval has updated. After a material change, the actual training and index state must be checked; an upload action does not show the index was rebuilt.
3. Treating a retrieval result as authorized execution. Recalling a relisting list number does not mean the item has been cleared for sale; approval and execution need a separate downstream implementation.

## How to verify the setup

1. Input the hypothetical source text and the draft sentence above, then compare whether the word "approved" has a corresponding approval record. The source names no approving party, so the draft wording is unsupported and the evidence gap should be recorded.
2. Input item number A-100 and batch R-2024-05, run full-text retrieval and semantic retrieval separately, and observe whether returned fragments contain the inspection grade, refurbishment completion date, and list number. If a fragment lacks a status field, check whether chunking separated the conclusion.
3. Input a paper-based empty result `[]` to check the downstream design. When retrieval returns an empty result, observe whether the system handles it as empty-reference output; do not claim a fictional rule necessarily returns `[]`. Libraries across different vector models cannot be associated together; verify the identifier first and exclude those that do not match, without running cross-model retrieval to compare missed recalls.

For each check, state the input, the comparison, and the observable result. A missing field remains missing. An unprovided document field is unknown, and no test, deployment, approval, or refund is claimed here.
