# Import and export permits: model connections for multilingual work

## What the documents look like

Permit handling happens before customs declaration, and that timing decides whether a shipment may legally cross a border. The everyday materials are automatic import licences, dual-use item licences, contracts and product descriptions. They arrive from commerce authority systems, customs commodity codes, supplier files and customer end-use statements. Updates are irregular and handled per shipment, so the same commodity can carry different documents and different end-use wording from one shipment to the next.

Cross-border material work with multilingual retrieval covers field extraction and cross-language comparison across those documents. Model connection and configuration makes a language model and an index model usable for that work. It does not verify whether a licence is genuine and does not confirm approval status. Because the licence decision precedes declaration, a retrieval hit on a licence text is a document finding, not a permission to declare.

## Constraints at the model connections step

Model access depends on the AI Proxy service. In the App and Admin shared variables, `AIPROXY_API_ENDPOINT` and `AIPROXY_API_TOKEN` are required, and a missing value in either one fails startup validation. `AIPROXY_API_ENDPOINT` takes the service root address without a `/v1` suffix. The proxy address inside a model channel takes a `BaseUrl`, not a full request address. Model mapping links the system model identifier to the upstream model that actually receives the request. The system needs at least one language model and one index model to work.

Retrieval relevance does not act as a permission or entity filter. A similarity score does not exclude unrelated businesses or unauthorized records, and retrieval is not authorization. The same-vector-model requirement applies within one retrieval library; it does not extend to commerce authority systems or any other external system.

Hypothetical paper exercise sample: the source material reads, "Automatic import licence. Applicant: a machinery trading company in East China. Commodity: CNC lathe. Licence valid until 31 December 2026. End use: production equipment for own use." The handover request reads, "Based on the material above, confirm that this shipment may be declared for import under this licence." The sample is for paper checking only and involves no real entity or number.

## Configuration and implementation checks

The table below covers the sample's retrieval and comparison needs. The values are hypothetical starting points for this exercise, used for manual checking; they are not official defaults.

| Configuration item | Hypothetical starting point | Reason and comparison object |
| --- | --- | --- |
| `AIPROXY_API_ENDPOINT` | AI Proxy root address | Compare with the deployed service address; confirm no `/v1` suffix |
| `AIPROXY_API_TOKEN` | Non-empty administrator token | Compare with the server-side configuration; confirm consistent and non-empty |
| Language model | One enabled | Pair with the index model to meet the system minimum |
| Index model | One enabled | Pair with the language model for text block retrieval |
| Model mapping | System identifier mapped to upstream model | Compare with the actual model name in the channel; confirm it resolves |
| Model test | Run against the configured channel | Compare with the returned model list; confirm each model returns a result |

## Three common errors

1. Writing `AIPROXY_API_ENDPOINT` as a full request address that includes `/v1`. The input is an address carrying a path; the comparison object is the documented root address; the observable result is an address-related error at startup validation or at the channel request.
2. Using an application API key as `AIPROXY_API_TOKEN`. The input is an application-side credential; the comparison object is the server administrator token; the observable result is an authentication failure returned by the channel call.
3. Treating a retrieved material as an already-authorized basis for handling. The input is retrieved licence text; the comparison object is the authorization status field; the observable result is that the material exists while the authorization status field is not stated.

## How to verify the setup

1. Input the sample source text and the handover request. Compare against whether the source states the authorizing subject, the validity period and the end use. The observable result is that the source states only the applicant and the validity period, the authorization status field is absent, and the item is recorded as pending verification.
2. Input a model channel test request. Compare the returned results for each model and the request duration. The observable result is that both the language model and the index model return results, which supports the conclusion that the connection is usable. If a model returns nothing, record that model identifier and the error information.
3. Input a retrieval request with a target retrieval library identifier. Compare the vector model identifier used by that library against the model identifier in the request. When the identifiers match, run the retrieval and record the returned entries. When they do not match, exclude that library and record that retrieval was not executed. For an empty result, check the downstream display against an explicit paper input of an empty list, without inferring that the retrieval rule must return an empty list.
