# Store price and display checks: workflow routing for multilingual work

## What the documents look like

Price and display auditing for chain stores happens during ordinary trading periods. The work centres on whether published standards continue to be followed after opening, not on onboarding or training. The materials involved are supervision-system visit records, POS price lists, store camera footage, head-office promotion calendars, visit photographs, price-tag lists, display standards and rectification notices. In cross-border operations these materials frequently exist in several language versions at once. A single rectification notice may contain a Chinese passage and a local-language passage side by side.

The comparison target is the on-site state of an already trading store. Price tags and display photographs carry most of the evidential weight, and rectification notices carry the follow-up loop. Multilingual retrieval has to establish how the same store, the same promotion period and the same field correspond across materials written in different languages. Update frequency for these materials is weekly or monthly; where that frequency does not affect routing, it can be left out of the design.

## Constraints at the workflow routing step

The Form Input node is a user-interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. After the user completes the required information and submits, the node collects what was entered and passes it to later nodes. The User Selection node is also a user-interaction node. It enters the same interaction state, and when the user makes a choice the node evaluates that choice and executes the corresponding "yes" branch. Both nodes can be added repeatedly and both trigger execution.

The routing constraint follows from this. The interaction state is recorded by the node itself; there is no separate global state-recording switch described in the documentation. When a retrieval node receives the output of a form or selection node, the output and the input have to be compared item by item. Order writing, document backfill and external status synchronisation are business actions. They require a separate business interface or a later process. Retrieval and form collection do not by themselves constitute authorised execution. A vector retrieval library requires the same vector model for records to be associated together; that requirement is internal to the retrieval library and does not extend to external systems.

Hypothetical paper exercise. A chain operations department receives a bilingual visit bundle. The source text reads: "Week 2 of March 2025, Area A store price-tag spot-check record: shelf tags and POS price tags are consistent; display photograph P-07 shows an empty end-cap." A second passage in the local language carries the same store and the same week. The handover request to be assessed reads: "Please retrieve all rectification notices for this store this month and synchronise them to the supervision system." The phrase "synchronise to the supervision system" is an external business action. The materials do not state an authorisation scope or an interface implementation for it.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison method |
| --- | --- | --- |
| Required form fields | Store number, promotion week, material language | Compare item by item with "Area A store" and "Week 2 of March 2025" in the sample |
| User selection branch | Yes branch points to the retrieval node | Check whether the selection result matches the branch connection |
| Retrieval library vector model identifier | Recorded as model A | Compare with the other library's identifier; exclude joint association when they differ |
| Empty-result downstream input | Paper input `[]` | Check how the downstream node is designed to accept an empty array |
| Output handover field | Retrieval result passed to the judgement node | Compare input fields with output fields item by item |
| External synchronisation action | Marked as requiring a separate interface | Check whether the materials state an authorisation and an interface implementation |

The values in the table are hypothetical starting points for this exercise, not official defaults. Model A is used only for identifier comparison and no statement is made about its runtime behaviour.

## Three common errors

1. Treating retrieval or form submission as authorised execution. In the sample, "synchronise to the supervision system" is a business action. The materials do not state an authorisation boundary. A form collecting values does not mean an authorisation has taken effect.
2. Associating records across libraries with different vector models. When two libraries carry different model identifiers, the correct step is to check the identifiers and exclude the ones that do not match, then record what was actually observed. No inference is drawn about missed recall or redundant results.
3. Treating a pending-review state as a missing permission. The sample material is at a to-be-verified stage. That does not establish that the store lacks an operating permission, and no authorisation clause may be supplied to force a definite answer.

## How to verify the setup

1. Input the sample source text "Week 2 of March 2025, Area A store price-tag spot-check record: shelf tags and POS price tags are consistent". Compare whether the required form fields include the store number and the promotion week. The condition is satisfied when all three fields are present and match the source text.
2. Input the handover request "Please retrieve all rectification notices for this store this month and synchronise them to the supervision system". Compare whether the retrieval node output corresponds item by item with the judgement node input, and check whether the "synchronise" action is marked as requiring a separate interface. The condition is satisfied when that marking is present and the retrieval output is handed over completely.
3. Input the paper empty result `[]`. Compare whether the downstream node is designed to accept an empty array, and observe whether an undefined handling path appears. The condition is satisfied when the downstream node explicitly accepts an empty input. All of the above are paper checks; no deployment or testing has taken place.
