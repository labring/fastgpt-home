# Store counts and loss control: workflow routing for multilingual work

## What the documents look like

Store counts and loss control centre on book-to-physical variance and shrinkage. The work does not settle supplier payables. The main data comes from POS inventory, WMS, monitoring systems and the SB/T count specification. Day-to-day documents are count sheets, variance analyses, loss-report approvals and monitoring access records. Typical roles are the loss-prevention department, store inventory keeper and finance audit. In cross-border material and multilingual retrieval, one set of count materials may sit in several repositories in different languages and versions. The retrieval step finds materials. Authorization status and business conclusions belong to later human or interface steps. Material updates run monthly and quarterly; this page does not derive any batch, full, real-time or transaction-triggered synchronization from that cadence.

## Constraints at the workflow routing step

In FastGPT v4.17.2, the form input node is a user-interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. After the user fills required information and submits, the node collects the submitted form information and passes it to later nodes. The user selection node is also a user-interaction node. It enters the same interaction state, and when the user makes a choice the node judges that choice and executes the corresponding "yes" branch. For both nodes, the interaction state and state recording are the node's own behaviour. The documentation does not describe a global state-recording switch. Collected information must be passed explicitly to later retrieval, judgement or interface nodes, and output must be compared item by item against input. Order writing, document backfill and external status synchronization require a separate business interface or later process. Retrieval or a form does not constitute authorized execution.

Hypothetical drill sample: a store loss-prevention department submits a paper "Count Variance Statement" in March 2025. Two sentences of the original read: "This store conducted a closed-door count on 28 February 2025. SKU-A book quantity 120 units, physical count 108 units, variance 12 units, preliminarily judged as loss not registered. This statement takes effect after review by the regional loss-prevention manager." A Chinese "Loss Report Approval Form" accompanies the same batch, with status field "pending review". The proposed draft sentence is: "The variance has been confirmed and the loss report approval has passed." The request to be judged is: "Please retrieve this store's February 2025 count variance materials and summarize them."

## Configuration and implementation checks

| Configuration item | Relevant setting or implementation check on this page | Relation to the sample |
| --- | --- | --- |
| Form input node | Enters interaction state on trigger, collects required fields, passes values on submit | Used to collect count period, store and SKU retrieval conditions |
| User selection node | Executes the "yes" branch after the user chooses; verify each branch connection | Used to confirm whether retrieval continues or goes to human review |
| Output handover | Pass collected information explicitly to later retrieval or judgement nodes; compare item by item | Checks whether the request to be judged enters retrieval intact |
| Retrieval scope | Verify that the target library identifier and the vector model identifier match | For multilingual material split across libraries, check identifiers first and exclude non-matching ones |
| Empty-result handover | Use an explicit paper input [] to check downstream design | When retrieval returns no hit, observe whether downstream distinguishes empty result from failure |
| External operation split | Order writing, document backfill and status synchronization connect to separate interfaces | The loss report approval status is not rewritten by the retrieval node |

## Three common errors

1. Treating a retrieval hit as an authorization conclusion. In the sample the Loss Report Approval Form status is "pending review". Retrieving that form does not mean approval has passed. The draft sentence "the loss report approval has passed" is unsupported.
2. Treating interaction-state recording as a global switch. The documentation states that interaction nodes record workflow state. It does not describe a configurable global state-recording switch, so configuration should not invent one.
3. Jointly associating libraries across vector models. Libraries on different vector models cannot be jointly associated. Verify library identifiers and model identifiers first, exclude non-matching ones, and do not run cross-model retrieval to compare missed recall.

## How to verify the setup

1. Input the request to be judged and the draft sentence from the sample. Compare the draft sentence "the variance has been confirmed and the loss report approval has passed" with the original Count Variance Statement wording "takes effect after review by the regional loss-prevention manager" and the Loss Report Approval Form status "pending review". Satisfied when the judgement states that "confirmed" and "passed" are unsupported and that the variance statement remains pending review.
2. Input the store, period and SKU fields from the sample. Compare whether the retrieval output shares the same subject, the same period and the same field as the request. Satisfied when the output covers February 2025, that store and SKU-A, and does not mix in records from another period or another store.
3. Input the explicit paper empty result []. Compare whether the downstream node design distinguishes an empty result from a retrieval failure. Satisfied when downstream has a clear handover path for [] and does not describe the empty result as no permission or record not existing. All three items rest on paper comparison; no live test is claimed.
