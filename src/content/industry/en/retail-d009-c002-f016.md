# MCN operations: interactive forms for operations handover

## What the documents look like

MCN creator management handles long-term account compliance for multiple creators rather than a single brand campaign. The working records include creator signing contracts, training records, violation handling forms and account schedules. These arrive from the MCN back office, platform violation notices, creator account data and the contract ledger. Operations permission and handover work turns on one question: what authorization state does a given material, action or request currently hold.

The interactive nodes in FastGPT v4.17.2 do not answer that question on their own. The form input node collects values the user fills in and passes them to later nodes. The user selection node judges the user's choice and executes the matching branch. Both are user interaction nodes: when triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues only after the user completes the interaction. Neither node carries a business database, and neither constitutes an authorization action. Field validation, business approval, write-back and batch operations belong to an external system or to later nodes.

## Constraints at the interactive forms step

A hypothetical drill sample is used here. The source material reads: "Creator A's signing contract takes effect on 1 March 2025; the account schedule shows the live session on 10 April 2025 as confirmed; violation handling form number V-2025-0412 records that the live content review on 12 April 2025 did not pass, with handling status pending review." The draft sentence to be judged reads: "Creator A's operations permission has been handed over to agent B, effective 15 April 2025."

The draft sentence lacks a stated authorization boundary. The contract ledger and the violation handling form contain no handover approval record. The form input node, once triggered, puts the conversation into the interaction state, records the workflow state and waits; after the user fills the required information and submits, the node collects the values and passes them to later nodes. The user selection node executes a branch based on the user's choice. Until the interaction completes, the handover described in the draft sentence cannot be treated as executed. Retrieval and similarity settings do not perform permission or entity isolation, and retrieval is not authorization.

## Configuration and implementation checks

| Configuration item | Assumed trial starting point | Checking method |
| --- | --- | --- |
| Required fields on the form input node | Handover counterparty, handover effective date, authorization scope | Submit with one item missing and observe whether the interaction state continues |
| Branches on the user selection node | Yes and no branches | Choose yes and observe whether the matching branch executes |
| Interaction state recording | Workflow state recorded after triggering | Check whether the conversation sits in the interaction state before submission |
| Form value passing | Values passed to later nodes after submission | Check whether later nodes receive the submitted values |
| Handover authorization check | Manual comparison of contract ledger and violation handling form | Check whether a handover approval record exists |
| Retrieval library identifier | Same vector model | Check the identifier and exclude non-matching entries |

The assumed trial starting point selects handover counterparty, handover effective date and authorization scope because the sample draft sentence involves a subject, a date and a permission boundary, and these can be judged only after comparison with the contract ledger. This starting point is a hypothetical value, not an official default.

## Three common errors

1. Treating form submission as completed authorization. The form input node only collects information and passes it to later nodes; business approval requires an external system. In the sample, submitting the handover form does not change the authorization state in the contract ledger.
2. Treating a user selection branch as a personnel directory or business data selector. The user selection node executes a branch based on the choice; it provides no entity isolation and no permission filtering.
3. Treating retrieval results as a permission basis. Similarity settings do not exclude unauthorized records, and retrieval is not authorization. In the sample, retrieving the contract text does not mean the handover has been approved.

## How to verify the setup

1. Input the sample draft sentence and the contract ledger text. Compare the handover effective date stated in the draft sentence with the authorization scope recorded in the contract ledger, and observe whether a handover approval record exists. Expected: when the approval record is missing, the draft sentence cannot be judged as executed.
2. Input the sample violation handling form number V-2025-0412 and its handling status "pending review". Compare that status with the authorization boundary of the handover request, and observe whether the pending review status is treated as approval. Expected: pending review does not equal approval.
3. Input a scenario where a required form field is missing. Compare the interaction state before and after submission, and observe whether the conversation continues. Expected: when a required field is missing, the interaction state does not proceed to later nodes.

These are paper checks and were not actually run.
