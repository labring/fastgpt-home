# Shopify fulfillment: interactive forms for operations handover

## What the documents look like

On a Shopify standalone store, the merchant configures payment, shipping and fulfillment services directly, and the platform does not run a single automatic return process. That difference shapes how operations handover works. The materials that change hands are merchant-owned: order details, shipping-rate templates, shipping labels and refund records. They update per order or daily. A handover therefore turns on the state of those materials at a point in time. The previous operator's shipping-rate template version, the status of shipping labels, and the processing progress of refund records all need item-by-item checking inside a form.

The form itself is a collection surface. In FastGPT v4.17.2, the form input node gathers the information a user fills in and passes it to later nodes. It does not carry a business database function. Fields, business approval, write-back and bulk operations are implemented in an external system or in downstream nodes. Retrieval and form submission do not create authorization. The approval status of a handover request is read from external system records.

## Constraints at the interactive forms step

When the form input node triggers, the conversation enters an interactive state, the workflow state is recorded, and execution continues after the user completes the interaction. The user selection node behaves the same way at trigger, then evaluates the user's choice and runs the "yes" branch. Neither node includes a business database. Field validation, business approval, write-back and batch operations require an external system or later nodes. Retrieval is not authorization, and a relevance score is not a category, entity or permission filter. Same-model retrieval association applies inside one vector model library; libraries built on different vector models cannot be associated together, so identifiers are checked first and non-matching items are excluded.

Hypothetical paper exercise sample: the source text reads, "Handover number J-2024-0312, transferring operator A, receiving operator B, handover object is the shipping-rate template and shipping-label status for orders #1001 to #1050 dated 12 March, handover scope is limited to viewing and continued processing, refund approval authority does not transfer with this handover." The sentence to be judged reads, "Receiving operator B has obtained refund approval authority and can execute refunds." Comparison result: the source text states that refund approval authority does not transfer with this handover, so the drafted sentence does not match the source and cannot serve as evidence that handover is complete.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting value | Reason and comparison method |
|---|---|---|
| Form input node | Enabled, collecting handover number, transferring operator, receiving operator | The node documentation states it collects filled-in information and passes it to later nodes |
| Required fields | Handover number, order scope, authority boundary | Missing any one prevents judging authorization state; test each missing item and the completed set |
| User selection node | Enabled, options "continue processing" and "view only" | The node runs a branch from the user's choice; compare against the authority scope in the source text |
| Interactive state wait | Workflow state recorded, execution continues after submission | Documentation states the node enters an interactive state on trigger; no submission-count assumption is set |
| Downstream approval | Implemented in an external system, the form does not write approval results | The node has no business database, so approval requires a separate system |
| Retrieval association | Associated within one vector model library | Libraries on different vector models cannot be associated; check identifiers first and exclude non-matching items |

## Three common errors

1. Treating form submission as completed refund approval. The form node collects filled-in information and passes it on; approval status is checked against external system records, and the submission action itself does not change authority.
2. Treating a user selection branch result as a grant of authority. The user selection node runs a branch from the choice; branch execution does not mean authority transfer and must be compared item by item with the authority boundary in the source text.
3. Treating a retrieval hit as confirmation of the handover object. Retrieval results do not constitute entity or permission isolation; identifiers are checked, non-matching items are excluded, and the actual observation is read from external records.

## How to verify the setup

1. Input the hypothetical sample source text and the drafted sentence, then compare "has obtained refund approval authority" in the draft against "refund approval authority does not transfer with this handover" in the source. If the two disagree, the drafted sentence does not meet the condition and is marked as not matching the source.
2. Input the three required items — handover number, order scope, authority boundary — and test the node behavior with each item missing and with all items completed. If the node does not stop continuation when an item is missing, the required-field configuration does not meet the condition.
3. Input the user selection branch "view only" and compare whether downstream nodes execute under "view only." If a downstream node executes a refund-approval type action, that branch configuration does not meet the condition, and the authority boundary source text is checked again.

These checks describe expected behavior on paper. They do not record a completed test, an approval, or a deployment. Where the documentation does not state an error code or an automatic business action, the comparison is left open and the missing evidence stays missing.
