# Shopify fulfillment: upgrades for operations handover

## What the documents look like

For a Shopify standalone store, payment, shipping and fulfillment services are configured by the merchant rather than unified by a platform, and returns are not automatically processed on the merchant's behalf. This differs from a TikTok Shop US store, where the platform governs more of the order lifecycle. The materials that matter at handover are order details, shipping templates, shipping labels and refund records. Refund records involve a money movement, and shipping labels involve a carrier action, so both are easy to mistake for completed execution during a handover.

The operational permission and handover task requires distinguishing the state each material is actually in. A form that has been filled in is not a business approval. A refund request that has been submitted is not a refund that has been executed. Data updates per order and per day, but that cadence does not by itself establish any batch, full-sync, real-time or transaction-triggered mechanism.

## Constraints at the upgrades step

During deployment and upgrade, an old instance and a new instance may exist at the same time, so permission ownership and action states in the handover materials need to be checked item by item. The following is a hypothetical drill sample.

Hypothetical drill sample: an independent-store operations team prepares handover materials before an upgrade window. Material text one (order detail page note): "Order #A-1042, customer has submitted a refund request, refund amount USD 120.00, status is pending review." Material text two (shipping template change record): "Template 'North America Standard' was modified one day before the upgrade, effective time not filled in." Proposed handover request: "Please have the incoming operator execute this refund directly after the upgrade completes, and reissue the shipping label under the new template."

Draft sentence to be judged: "The refund request has been submitted, so the incoming operator can execute the refund directly after the upgrade."

In this sample, the refund request is pending review and has not been approved; the shipping template change does not state an effective time; the proposed handover request treats a pending-review item as executable and treats an uneffective template as effective.

Before upgrading, check the current version, the target version and the corresponding upgrade notes rather than inferring current behavior from old configuration names. The V4.17.2 upgrade notes list two manually triggered scripts: the historical chunk training task migration and the knowledge base rebuild status migration. The second depends on the first having completed. Neither blocks service startup, and both are to be run after confirming that all old-version FastGPT App and Pro instances have fully stopped and old task leases have expired.

## Three common errors

1. Treating a pending-review refund request as an approved refund and executing it. The input is the order detail page note "status is pending review"; the comparison object is a value of "approved" or "executed". If the materials contain no approval record, the refund has no basis for execution.

2. Treating a shipping template with no stated effective time as an effective template. The input is the template change record "effective time not filled in"; the comparison object is an explicit effective time. If it is absent, whether the new template applies to post-upgrade orders cannot be determined.

3. Treating "execute directly" in the proposed handover request as an authorized instruction. The input is the proposed handover request text; the comparison object is an approval record or authorization record. If the materials contain only the request and no approval, the execution permission is not supported.

## How to verify the setup

The three checks below use the hypothetical drill sample text and draft sentence above. They state expectations only and do not claim that any test was run.

1. Verify the refund status determination. Input: the order detail page note text "status is pending review". Compare: whether that field value is consistent with "approved" or "executed". The condition is met when the field explicitly states an approval or execution status that is mutually exclusive with pending review; if it states only pending review, the basis for executing the refund is not supported.

2. Verify the shipping template effectiveness determination. Input: the template change record text "effective time not filled in". Compare: whether that field states a specific effective time. The condition is met when the field states an effective time earlier than the creation time of post-upgrade orders; if it does not, the applicability of the template remains to be verified.

3. Verify the handover request authorization determination. Input: the proposed handover request text "please have the incoming operator execute this refund directly after the upgrade completes". Compare: whether that request corresponds to an approval record or authorization record. The condition is met when an explicit approval record exists and the approved object is the same refund; if only the request exists, the execution permission is not supported and the evidence gap should be recorded.

After the upgrade, use the same sample to recheck import, retrieval and application invocation, and do not state a completed step sequence as a zero-interruption guarantee. Retrieval results do not carry permission or entity-isolation duties, and libraries using different vector models cannot be associated together; check the identifier first, exclude those that do not match, and record the actual observation.
