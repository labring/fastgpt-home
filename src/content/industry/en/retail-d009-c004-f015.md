# Temu semi-managed sellers: retrieval for operations handover

## What the documents look like

Semi-managed sellers on Temu maintain overseas inventory and ship orders themselves, rather than supplying goods to the platform for the platform to fulfill. Day-to-day materials concentrate on product declaration forms, overseas inventory tables, price declarations, and platform fulfillment orders, with updates occurring daily and per order. During operations handover, retrieval results over these materials reflect text similarity only. A retrieved price declaration does not mean that declaration has been approved. A retrieved fulfillment order does not mean the incoming operator already holds handling authority. The stated update rhythm only indicates that material versions may change daily; when checking, the same date and the same document number must be used as the comparison basis.

## Constraints at the retrieval step

The knowledge base search node can associate one or more knowledge bases that use the same vector model. Knowledge bases using different vector models cannot be associated together. Before running a query, the vector model identifier should be checked and non-matching bases excluded; a cross-model retrieval should not be executed to compare missed recalls. Reference content is output as an array and its length may be 0, so the downstream chain still proceeds even when nothing is retrieved. The minimum relevance value takes effect only under semantic retrieval or when result reranking is used. It is a filtering threshold and does not perform permission or entity isolation; a similarity score does not exclude unrelated business records or unauthorized records. Hybrid retrieval fuses multiple result paths through RRF, reranking requires a model and must be enabled according to settings, and image retrieval requires image input plus the corresponding model capability. The retrieval step does not constitute authorization; approval, database writes, and external synchronization require separate downstream implementation.

Hypothetical paper exercise sample: on 10 June 2025, a semi-managed seller operations team prepares handover materials. The source text contains two sentences: "Price declaration PJ-20250610-A: Product A, declared price USD 12.50, status is pending review." and "Platform fulfillment order LY-20250610-07: Product A, overseas warehouse shipment, status: shipped, handover handler: not designated." A draft handover sentence reads: "Price declaration PJ-20250610-A has been approved, and the handover person may execute shipment at this price directly." A pending request reads: "Please transfer handling authority for fulfillment order LY-20250610-07 to the next shift." The source text states only pending review and not designated; approval and authority transfer are not supported by it.

## Configuration and implementation checks

| Configuration or check item | Setting on this page | Basis and comparison method |
| --- | --- | --- |
| Associated knowledge bases | Associate only knowledge bases with a matching vector model identifier | The node requires the same vector model; check identifiers and exclude non-matching ones |
| Search mode | Run the sample question separately under semantic retrieval and full-text retrieval | Compare the three modes against the test question; do not presume one mode suits all materials |
| Reference cap | Hypothetical starting value for this exercise: 3000 tokens | This value is a starting point for this exercise because the sample contains document numbers and status fields; compare content completeness against 1500 and 6000 |
| Minimum relevance | Hypothetical starting value for this exercise: 0.30 | First label relevant and irrelevant sentences in the sample, then compare filtering against 0.20 and 0.40 |
| Question optimization | Enable for follow-up questions containing references; disable for explicit questions | Compare the original question with the optimized question and check whether the subject was altered incorrectly |
| Empty-result handling | Use a paper input of [] to check downstream design | Reference length may be 0 and the chain still proceeds; do not claim a fictional rule must return [] |

## Three common errors

1. Treating a retrieval hit as authorization. In the sample, the price declaration status is "pending review." Drafting "has been approved" from that hit treats pending review as approval. Compare the source status field with the status wording in the draft sentence.
2. Treating "not designated" as default authority. The fulfillment order handler field reads "not designated." Transferring handling authority on that basis fabricates authorization. Compare the source subject field with the authority subject in the request.
3. Using similarity filtering in place of permission isolation. Raising the minimum relevance and assuming unauthorized records are excluded misuses the threshold. Compare returned content before and after filtering to confirm the setting affects relevance ordering only.

## How to verify the setup

1. Enter the two hypothetical source sentences and the draft sentence, then compare whether "has been approved" in the draft and "pending review" in the source share the same subject, the same period, and the same field. Only an explicit approval value in the source satisfies this; the current evidence does not support it.
2. Enter the pending request and the fulfillment order source text, then compare the authority transfer in the request with "handler: not designated" in the source. Only a stated authorization subject and scope in the source satisfies this; the current state is an evidence gap and must be recorded as pending verification.
3. Enter the same question under semantic retrieval and full-text retrieval, then compare whether the returned array contains that document number. Observe whether a number hit or an empty array appears; do not assume a first-position hit or full recall. Check the empty result against [] for downstream design.
