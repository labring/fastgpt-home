# JD POP seller operations: upgrades for operations handover

## What the documents look like

JD POP third-party store operations work around open-platform dispute rules and warranty-period service document handling. The daily materials are a product information table, a shipping-time agreement, a dispute handling form, and warranty-period service records. These materials update daily and per order. During handover, store operations staff and after-sales supervisors need to establish which materials are readable, editable, or awaiting authorization. A retrieval result or a completed form does not mean that an authorization has taken effect. At the deployment and upgrade step, the current version and the target version with the corresponding upgrade notes are checked first. Current behavior is not inferred from an old configuration name.

## Constraints at the upgrades step

Assume a paper exercise sample. A POP store operations staff member A submits a handover request to recipient B. The source material has three sentences. Sentence one: "Product information table V3, containing 120 on-sale SKUs, last updated 8 October 2026, edit permission currently held by the operations supervisor." Sentence two: "Dispute handling form D-20261008-017, status awaiting evidence, evidence deadline 10 October 2026, no submission record at present." Sentence three: "Warranty-period service record S-20260930-044, warranty period to 31 December 2026, service form status accepted and not completed." The draft sentence to be assessed is: "B has obtained edit permission for product information table V3 and has submitted the evidence materials for dispute handling form D-20261008-017." Against the source, sentence one states only that edit permission is held by the operations supervisor; it does not state that B has obtained that permission. Sentence two gives a status of awaiting evidence with no submission record; it does not state that a submission occurred. Compared on the same subject, the same period, and the same field, the draft sentence is unsupported and the evidence gap is recorded.

For deployment and upgrade, AIPROXY_API_ENDPOINT and AIPROXY_API_TOKEN are required for App and Admin. Missing either one causes startup validation to fail. This configuration does not replace the granting of operations permissions in the store backend. The upgrade notes for V4.17.2 list two manually triggered upgrade scripts that do not block service startup: the historical chunk training task migration, and the knowledge base rebuild status migration, which depends on the first migration being complete. The notes state that the first script is executed after all old-version FastGPT App and Pro instances in the cluster have fully stopped and old task leases have expired. The notes also describe knowledge base and file list search being limited to the current directory and its subtree when a search is run inside a specified directory, with root-directory search retaining full-scope behavior.

## Three common errors

1. Treating a retrieval hit as a granted permission. The input is the draft sentence "B has obtained edit permission" in the handover request. The comparison object is the source line "edit permission currently held by the operations supervisor." The observable result is that the draft sentence and the source differ in the value of the same field, so the draft sentence is unsupported.
2. Treating an awaiting-evidence status as a completed submission. The input is "has submitted the evidence materials" in the draft sentence. The comparison object is the source line "status awaiting evidence, no submission record at present." The observable result is that the source does not record a submission action, so the draft sentence lacks evidence.
3. Treating a filled configuration item as a completed business authorization. The input is that AIPROXY_API_ENDPOINT and AIPROXY_API_TOKEN are filled in. The comparison object is the permission-holder field in the store backend. The observable result is that the configuration items and the operations permission belong to different layers, and the former does not change the value of the latter.

## How to verify the setup

1. Check the draft sentence "B has obtained edit permission for product information table V3." The input is sentence one of the source. Compare the subject of "edit permission currently held by the operations supervisor" with the subject of the draft sentence. The observable result is that when the two subjects differ, the draft sentence is judged unsupported.
2. Check the draft sentence "has submitted the evidence materials for dispute handling form D-20261008-017." The input is sentence two of the source. Compare "awaiting evidence, no submission record" with "has submitted." The observable result is that when no submission record appears in the source, the draft sentence is judged pending verification.
3. Check the deployment configuration. The input is the two items AIPROXY_API_ENDPOINT and AIPROXY_API_TOKEN. Compare whether both are non-empty and match the documented format. The observable result is that if either is missing, startup validation fails; if both match, the next check step is entered, and completing the configuration is not treated as completing the operations permission handover.
