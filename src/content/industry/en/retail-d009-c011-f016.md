# Refund-only disputes: interactive forms for operations handover

## What the documents look like

Refund-only disputes differ from ordinary return-and-refund cases in one respect that shapes the whole handover step: there is usually no returned-goods warehouse receipt. The evidence therefore centres on dispatch and signed receipt, together with the value of the goods. The working materials for this category come from the platform after-sales backend, carrier tracking, customer-service chat, and warehouse outbound records, and they update per order. During an operations handover, four document types carry the state that a permission judgement depends on: the refund-only application, the dispatch proof, the signed-receipt proof, and the appeal material.

Because the goods are not recovered, the handover conversation has to keep material state and authorization state apart. Whether a signed-receipt proof has been uploaded is a statement about evidence. Whether appeal permission for that order has been transferred is a statement about authority. A handover request can legitimately contain both facts, and the two still need separate records.

## Constraints at the interactive forms step

The form input node is a user-interaction node. When it is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution waits until the user completes the interaction. After submission, the node collects the information the user filled in and passes it to later nodes. The node does not carry its own business database function. Field validation, business approval, write-back, and bulk operations need to be implemented in an external system or in later nodes.

The user selection node is also a user-interaction node. It triggers the interaction state, and when the user makes a choice the node evaluates that choice and executes the corresponding branch. It is not a personnel directory and not a business-data selector. Retrieval and forms do not perform authorization.

Hypothetical drill sample for paper review: an after-sales supervisor submits a handover request reading, "Refund-only application number A-001, goods signed for, signed-receipt proof uploaded; request to hand over appeal permission for this order to specialist B." The subject is the after-sales supervisor, the object is application A-001, the recorded state is that the signed-receipt proof is uploaded and the permission handover is pending confirmation, and the effective scope is appeal permission. The draft conclusion to be assessed reads, "The signed-receipt proof is uploaded, therefore appeal permission for this order has been handed over." This sentence treats an evidence-upload state as a completed permission transfer, and it remains pending verification.

## Configuration and implementation checks

| Configuration item | Documented behaviour or implementation check | Relation to the sample |
| --- | --- | --- |
| Form input node | Enters the interaction state when triggered, records workflow state, waits for the user to complete the interaction | Collects order number, material state, and permission scope from the handover request |
| Required-field check | List the information this task cannot omit, then test the missing-item case and the completed case separately | Checks whether subject, object, state, authorization scope, and material list are all present |
| User selection node | Executes a branch according to the user's choice; not a personnel directory | Branch condition is whether the handover request satisfies field completeness |
| Interaction state | Continues downward after the interaction completes | After submission the information passes to later nodes; approval is not completed automatically |
| Downstream division of work | Field validation, business approval, write-back, and bulk operations are implemented as needed in an external system or later nodes | Completion of permission handover needs external confirmation; the form does not carry that function |

Hypothetical starting point for this exercise: set five required fields, chosen to cover subject, object, state, authorization scope, and material list. The comparison method is to delete one field at a time and observe whether the interaction state can still be submitted. This starting point is for paper review and is not an official default value.

## Three common errors

1. Treating an uploaded signed-receipt proof as a completed appeal-permission handover. The input is the sample text; the comparison is between the material-state field and the authorization-state field; the observable result is whether the two are handled as one fact. Executable check: define material state and authorization state as two separate fields in the form, then after submission inspect whether later nodes read them separately.
2. Treating the branch outcome of the user selection node as a personnel directory or a permission assignment. The input is the branch-selection action; the comparison is between the selection result and the authorization record; the observable result is whether the selection is handled as authorization. Executable check: inspect whether the branch output carries only the selected value, and whether authorization confirmation is recorded separately by an external system.
3. Treating retrieval or form submission as authorization execution. The input is the submission action of the handover request; the comparison is between submission state and approval state; the observable result is whether pending review is handled as approved. Executable check: inspect whether submission produces a pending-review marker and whether approval completion has an independent record.

## How to verify the setup

- Verification one: input the sample text "Refund-only application number A-001, goods signed for, signed-receipt proof uploaded; request to hand over appeal permission for this order to specialist B." Compare the values of the material-state field and the authorization-state field. The condition is satisfied when the two fields are stored independently and neither overwrites the other, and the draft conclusion "The signed-receipt proof is uploaded, therefore appeal permission for this order has been handed over" is marked pending verification.

- Verification two: input the draft conclusion sentence and compare its claim against the state recorded in the sample text. The condition is satisfied when the sentence is not treated as established and the permission-handover state remains pending confirmation.

- Verification three: input a handover request that omits the authorization scope, and compare the required-field check result. The condition is satisfied when the interaction state does not reach submission completion and the missing item is explicitly recorded. All three are paper expectations and were not actually executed.

The scope of this page is refund-only dispute handling, operations permission and handover management, and forms and interaction. Which materials, actions, and requests sit in which authorization state during a handover is a matter for separate records; retrieval and form submission are not authorization execution.
