# Franchise store supervision: conversation logs for operations handover

## What the documents look like

Franchise supervision differs from direct-operated convenience store fresh-food ordering. The headquarters supervises how franchisees carry out standards, and the daily materials reflect that relationship rather than a single company's internal ordering flow. The main data sources are the supervision app, POS sales, the franchise system, and store photographs. The recurring documents are store visit forms, franchise contracts, rectification notices, and display standards. These materials update weekly or monthly. Each one records a different kind of fact: a store visit form records an inspection result, a franchise contract records an authorization relationship, a rectification notice records a pending task, and a display standard records an execution requirement. Their fields do not match each other.

Conversation logs and audit work must connect one conversation to one store, one store visit record, and one authorization scope. The check is made against the original wording of the material. Records from different sources are not combined into a single total, and a value that one document does not state stays unknown. The material itself decides what can be compared; the log does not supply a business fact that the source document omits.

## Constraints at the conversation logs step

Conversation identity is separated by chatId. When a non-empty chatId is passed, the interface takes the conversation from the database and uses the last item in the messages array as the user question; the remaining messages are ignored. When responseChatItemId is passed, that value becomes the ID of the response message for this turn and is stored in the database, and it must be unique under the current chatId. When detail is true, intermediate values are returned, and in non-stream mode the result is held in responseData. Log review judges only by the fields actually returned. Business data that is not returned cannot be treated as fully retained.

Retrieval and similarity do not perform authorization or entity isolation. A similarity value reflects how close two texts are; it does not exclude unrelated stores or unauthorized records. Authorization must be checked against the franchise contract and the permission settings, which are separate from the retrieval result.

Hypothetical paper exercise sample. A supervisor starts one conversation for Store A in the franchise system. The chatId is "jd-A-2024-10". The last message is "Please confirm whether Store A's display rectification is complete this week." The store visit form contains two sentences: "Store A, 2024-10-08, display rectification notice delivered. Rectification completion status is awaiting franchisee confirmation." A proposed statement reads: "Store A rectification is complete." In the material the rectification status is awaiting confirmation. The proposed statement records awaiting confirmation as complete. Both refer to the same subject, the same period, and the same field, and their values are mutually exclusive, so the pair is a contradiction.

## Configuration and implementation checks

Configuration is built around this sample and lists only settings the official document describes, together with implementation check items.

| Item | Value or action | Relation to the sample |
| --- | --- | --- |
| chatId | Hypothetical starting value "jd-A-2024-10", chosen because the conversation must be uniquely separated from Store B; compared against the Store B conversation value | Keeps the target conversation from being merged with another |
| responseChatItemId | Hypothetical starting value "resp-A-1008-1", chosen because it must be unique under this chatId; compared against stored values | Locates a single response |
| detail | Set to true because the intermediate values in responseData need to be inspected | Checks the run detail |
| source | Set to "api" because only conversations created through the API are wanted | Separates API conversations from page conversations |
| authProxy | Enabled by the team owner when creating or editing the key; the proxy identity still needs permission on the target app and conversation | Checks the proxy identity |
| Authorization status | Manually checked against the original store visit form and franchise contract | Awaiting confirmation is not complete |

## Three common errors

1. Treating an awaiting-confirmation status as complete. In the sample the store visit form says "awaiting franchisee confirmation". If a log or a drafted sentence records "complete", the same field holds two mutually exclusive values, and the drafted sentence is recorded as unsupported.

2. Treating retrieval or similarity as an authorization filter. A similarity value only reflects textual closeness. It does not exclude unrelated stores or unauthorized records. Authorization is checked separately against the franchise contract and the permission settings.

3. Treating a field that detail did not return as retained. Business data the interface did not return is unknown. It cannot be written as fully retained or as having passed an audit.

## How to verify the setup

1. Input the sample chatId "jd-A-2024-10" and the proposed statement "Store A rectification is complete". Compare the store visit form wording "Rectification completion status is awaiting franchisee confirmation" with the proposed statement. Observe the result: the two hold mutually exclusive values in the same field, so the pair is a contradiction and the proposed statement is unsupported. If the store visit form instead read "Rectification completion status: complete", the proposed statement would agree with it.

2. Input a request with detail=true and inspect whether responseData contains fields such as moduleName, tokens, and runningTime. Compare the fields actually returned with the check list. Observe the result: returned fields can be checked; business fields that do not appear are recorded as unknown, and no conclusion of retention is drawn.

3. Input the chatId and the responseChatItemId, and compare whether that responseChatItemId is unique under the current chatId. Observe the result: if it is unique, the location holds; if it repeats, record a conflict and assign a new value. This check does not involve cross-vector-model association, and it does not guarantee a first-hit match or full recall.

The items above concern conversation identity, run detail, field meaning, and the separation between log existence and a completed compliance audit. Reconciliation, retention, and compliance obligations are carried out by a complete business plan; the presence of a log does not by itself complete a compliance audit.
