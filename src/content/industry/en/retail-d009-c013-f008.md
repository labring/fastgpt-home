# Franchise store supervision: workflow routing for operations handover

## What the documents look like

Franchise supervision for convenience stores rests on four recurring document types: store visit forms, franchise contracts, rectification notices, and display standards. The data reaches the supervisor through a supervision app, POS sales records, the franchise system, and store photographs. Weekly and monthly update rhythms are the documented pattern, and this page does not derive batch synchronization, real-time triggering, or full refresh behavior from that rhythm.

The distinguishing feature of this category, compared with directly operated fresh-food ordering, is that headquarters supervises how franchisees carry out standards. A single store visit form therefore often carries three kinds of records at once: display checks, headquarters order reconciliation, and rectification tracking. These records describe different facts, and a form entry about one of them does not settle the state of another.

## Constraints at the workflow routing step

Workflow routing here determines which materials, operations, and requests sit in which authorization state across store visits, rectification, and handover. The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and the dialogue waits until the user completes the interaction. After the user fills the required information and submits, the node collects the submitted values and passes them to subsequent nodes. The User Selection node is also a user interaction node. When the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. The interaction state is recorded by the interaction node itself; the documentation does not describe a separate global state-recording switch, and this page does not add one.

Retrieval and form collection do not constitute authorization. Order writes, document backfill, and external status synchronization require a separate business interface or a downstream flow. A pending request is not an approval, an offered option is not an execution, and an unsigned termination is not a completed termination.

Hypothetical paper exercise sample. A franchise contract annex states: "The Party A regional supervisor has the right to enter the store during business hours to check displays, and rectification notices are issued by the supervisor and delivered to the franchisee." A store visit form records: "May 2024 display check, object is the cold cabinet end shelf, status is pending rectification." The draft sentence to be judged is: "The supervisor has approved the store's resumption of end-shelf display." The comparison must hold the same subject, the same period, and the same field. The contract annex supplies a right of entry for checking and a right to issue rectification notices. The store visit form supplies a pending-rectification status. Neither contains a record approving resumption of display, so the draft sentence is not supported.

## Three common errors

1. Treating "pending rectification" on a store visit form as completed rectification. The input is the sample store visit form record; the comparison object is the supervisor authority in the contract annex; the observable result is that neither document records completed rectification, so the claim is not supported.

2. Treating a form submission as an authorization approval. The input is the draft sentence "The supervisor has approved resumption of display"; the comparison object is the contract and store visit form wording; the observable result is that neither document contains an approval field, so the matter remains pending verification.

3. Treating the branch direction of a User Selection node as a business status change. The input is the node's branch connection; the comparison object is the interface implementation required for external synchronization; the observable result is that the node itself does not write orders or backfill documents, so a separate implementation is required.

## How to verify the setup

1. Input the sample store visit form wording and the draft sentence, compare the subject, object, and status fields, and if the draft sentence contains an approval statement absent from the source wording, mark it not supported and record the evidence gap.

2. Input an explicit paper empty result `[]` and check whether downstream nodes are designed to accept an empty input. Do not claim that a search of invented rules necessarily returns an empty result.

3. Check the retrieval library identifier and the vector model identifier, and exclude libraries that associate different vector models together. Record only what is observed, and do not infer missed recall or redundant results from cross-model retrieval. A relevance score is not a category, entity, or permission filter, and retrieval is not authorization.
