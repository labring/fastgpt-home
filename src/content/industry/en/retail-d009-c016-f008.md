# Franchisee onboarding: workflow routing for operations handover

## What the documents look like

Franchisee training and store-opening coaching is a transfer of operating capability, distinct from franchise filing management, which is a legal disclosure process. The materials for this category come from training systems, supervisor apps, store photographs and the head office SOP library. The routine documents are training attendance sheets, store-opening checklists, SOP manuals and assessment results, with a per-store, monthly update rhythm. In operations permission and handover management these materials record who completed which actions at which stage, and which requests remain pending. An attendance sheet shows that people were present; a store-opening checklist records the result of a materials check; assessment results reflect training completion; the SOP manual supplies the action standard. The shared trait is that these materials sit in several systems, so workflow routing has to connect form collection with user selection and give each handover request a clear authorization boundary.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues only after the user finishes the interaction. The user selection node behaves the same way at trigger, and when the user makes a choice the node evaluates that choice and runs the corresponding "yes" branch. Information collected by these nodes has to be passed explicitly to later retrieval, judgment or interface nodes. Order writing, document backfill and external status synchronization require a separate business interface or a later process; the form itself does not perform those actions.

Retrieval and form submission do not constitute authorization to execute. The authorization state of materials in an operations handover has to be checked separately. The same-vector-model requirement for a retrieval library is limited to the scope the documentation states; it does not extend to other external systems. Libraries built on different vector models cannot be associated together. The correct step is to check identifiers first, exclude those that do not match, and record what was actually observed. A relevance score does not act as a category, entity or permission filter.

For this page the working case is a clearly labelled hypothetical paper exercise. The material text to be checked reads: "Franchisee A submitted a store-opening checklist in March 2025, requesting that regional supervisor B confirm acceptance; the request number is H-001 and the current status is pending review." The sentence under review reads: "Supervisor B has confirmed acceptance of this request." The original text states a pending-review status only. It does not state that acceptance was confirmed.

## Configuration and implementation checks

| Configuration item | Setting or check for this page | Relation to the sample |
|---|---|---|
| Form input node | Enters the interaction state on trigger and collects required information | Collects the submitter, store and request type of the handover request |
| User selection node | Runs the corresponding "yes" branch after the user makes a choice | Used to judge whether the supervisor confirms acceptance of the request |
| Output handover | Passes collected information explicitly to later nodes | Checks whether form output reaches the judgment or interface node |
| Interaction state check | State recording is behavior of the interaction node | Checks whether the conversation waits after entering the interaction state |
| External action split | Order writing, document backfill and external status synchronization connect to a separate interface | Approval and execution of the handover request are not completed inside the form |
| Hypothetical exercise starting point | In this paper exercise the user selection branch is set to "yes" to continue and "no" to return | This starting point is for paper checking and is compared with the branch behavior the documentation states |

## Three common errors

1. Treating form submission as completed authorization. In the hypothetical exercise, the franchisee submits the store-opening checklist, and the form input node collects the required information and passes it on. Treating that submission as supervisor confirmation of acceptance confuses collection with authorization. The check compares the submission record with the branch result of the user selection node; the handover confirmation condition is met only when both appear.

2. Treating retrieval output as a permission filter. In the hypothetical exercise, the regional supervisor enters a store number in the retrieval scope and expects only that store's materials. The same-vector-model requirement for the retrieval library is limited to the documented scope, and a relevance score does not carry permission or entity isolation. The check compares retrieval output with the explicit manual input scope; if the output contains a store outside that scope, record it as unverified.

3. Treating a pending-review request as a completed handover. In the hypothetical exercise, the franchisee's store-opening coaching request is in pending-review status and no "yes" branch result from the user selection node appears. The check compares the request status field with the branch execution record; if either is missing, the item stays unverified and is not written as a completed handover.

## How to verify the setup

- Verification one: using the hypothetical exercise text "Franchisee A submitted a store-opening checklist in March 2025, requesting that regional supervisor B confirm acceptance; the request number is H-001 and the current status is pending review," with the draft sentence "Supervisor B has confirmed acceptance of this request." The input is the original text and the draft sentence. Compare the confirmation action in the draft sentence with the status field in the original. The original states pending review only and does not state confirmed acceptance, so the draft sentence is not supported and should be recorded as unverified.

- Verification two: using the same hypothetical sample, the input is the form input node output and the user selection node branch record. Compare whether the output information reaches the "yes" branch. If the form output contains request number H-001 and the user selection node runs the "yes" branch, the output handover condition is met. If only the form output exists and the branch record is missing, record it as partially complete.

- Verification three: using the retrieval scope input "store number A" from the hypothetical sample, compare whether retrieval output contains only that store's materials. If another store number appears in the output, record it as an out-of-scope result. If the output is empty, check the downstream design against the explicit paper input [] and do not claim that a fictional rule necessarily returns an empty result.

These three verifications address the named primary task of workflow routing for operations handover. They do not test identity certification or report analysis. Each expected result is stated for paper comparison; no test, deployment, approval or handover execution is claimed to have occurred. Where the documentation does not state an error code, a default value or an automatic business action, the item remains unknown and is recorded as an evidence gap.
