# Brand member operations: conversation logs for operations handover

## What the documents look like

Brand member private-domain operations center on customer data and repeat-purchase outreach. The working material comes from CRM systems, enterprise messaging, POS purchase records, and mini-program behavior data. The documents handled day to day include member tag tables, outreach plans, coupon rules, and privacy authorization records. In the conversation logs and audit step, a session is identified by chatId within one application, and a single exchange within that session is identified by dataId. Log retention and business reconciliation are two separate matters. During an operations handover, the team needs to separate material that was merely retrieved, requests still awaiting review, and actions already completed. A retrieval hit on a historical conversation shows only that the text exists within an accessible retrieval scope. It does not show that a handover has been authorized.

Two features of this category shape the audit step. Member data moves on a daily and weekly cadence, so a handover packet can lag behind the state of a tag change or an outreach plan, and the packet must state the date range it covers. Outreach touches customers directly, so an unauthorized continuation of messaging carries complaint and cost consequences. The conversation interface returns fields that determine what a log can actually be checked against. When detail is false, the response carries choices and usage. When detail is true, the response additionally carries responseData, which includes module names, model, tokens, similarity, limit, quoteList, and completeMessages. Field meanings must be checked against what the interface actually returns. Business data that is not returned cannot be assumed to be fully retained. The authProxy setting proxies a team member identity, and a team owner must enable it when creating or editing the key; the proxied identity still needs permission on the target application and session. Retrieval and similarity scores do not perform permission or entity isolation.

## Constraints at the conversation logs step

The conversation interface fixes what an operations handover can verify. A chatId is required to be unique and shorter than 250 characters, and the caller is responsible for that uniqueness. A responseChatItemId, when supplied, must be unique within the current chatId. The session list accepts a source parameter, and source=api returns sessions created through the API rather than sessions created on the page. Clearing an application's sessions removes only those created through an API key, not sessions from online use or shared links. The detail parameter controls whether intermediate values are returned, and in stream mode those values arrive through distinct events while in non-stream mode they sit in responseData. None of these fields grant authorization. They describe what the log contains.

A hypothetical paper exercise sample: a brand member private-domain operations team prepares a handover packet. The source text reads, "Between March 1 and March 31, 2025, guide A sent coupon reminders from the outreach plan to member B through an enterprise messaging session. This batch of sessions was created through an API key, with chatId api-202503-017 and dataId rec-0007. The member tag table change request submitted on March 20 is in a pending-review state, and no approval record has been obtained." The sentence to be judged reads, "Guide A completed the outreach authorization handover for member B in March and may continue using this API key to start new sessions." In this sample, pending review is not approval, and creating a session through an API key is a different fact from outreach authorization.

## Three common errors

1. Treating a retrieval hit as a grant of permission. In the sample, retrieving the historical conversation with chatId api-202503-017 shows only that the text sits within an accessible retrieval scope. It does not establish that guide A received outreach authorization.
2. Treating pending review as approval. The sample states that the member tag table change request submitted on March 20 is pending review with no approval record. The handover material cannot describe the change as completed.
3. Treating an API-key-created session as business authorization. The sample states that the batch of sessions was created through an API key, which shows only that the session source is api. Whether guide A holds outreach authorization is a separate fact.

## How to verify the setup

1. Take the sample text "chatId api-202503-017, dataId rec-0007" and compare it character by character against the chatId and dataId actually returned by the interface. If both match and the responseChatItemId is unique within the current chatId, the check condition is satisfied. If a duplicate or a missing value appears, record it as pending verification.
2. Take the sample text "the member tag table change request submitted on March 20 is in a pending-review state, and no approval record has been obtained" and compare it against the wording about that request in the handover material. If the material says pending review, it matches the source. If the material says completed or approved, the wording is unsupported.
3. Take the sample text "this batch of sessions was created through an API key" and compare it against the session list returned with source=api. If the returned list contains that chatId, the source check is consistent. If the list is empty or the chatId is absent, record the observed result without inferring an unstated failure cause.

Retrieval scope and similarity scores do not carry permission or entity isolation, so a matched conversation is not an authorized handover. Where the material needed for a check is absent from the accessible retrieval scope or from a clearly identified manual input, record the gap rather than supplying a value.
