# Brand member operations: citation tracing for operations handover

## What the documents look like

Brand member private-domain operations centre on customer data and repeat-purchase outreach. The working material comes from a CRM system, enterprise WeChat, POS consumption records and mini-program behaviour data. The documents handled day to day are member tag tables, outreach plans, coupon rules and privacy authorisation records. Updates arrive daily or weekly.

The category differs from direct-store operations in that it does not handle store shift scheduling. Errors here produce outreach harassment complaints, uncontrolled coupon cost and member churn. For operations permissions and handover management, citation tracing has to answer a narrow question: during handover, what authorisation state does a given piece of material, a given operation or a given request actually hold. A retrieval result and a form entry are both records of what was written. Neither one is the authorisation having been executed.

The four handover documents carry different authorisation boundaries. A member tag table, an outreach plan, a coupon rule and a privacy authorisation record each need their source version and current effective scope checked item by item. A tag table may describe a member without granting any contact right. An outreach plan may name an intended action without that action being approved. A coupon rule may state a discount value without stating who may issue it. A privacy authorisation record may show a signature without that signature covering the specific operation being handed over. The tracing step keeps these apart.

## Constraints at the citation tracing step

The knowledge base search node outputs citations as an array, and that array may have a length of zero. Even when nothing is found, the output path still runs. An empty array does not mean the workflow has raised an error and stopped. This directly constrains handover checking: a retrieved citation shows that text was found, and it does not show that the operation described in that text has been authorised.

The knowledge base search node can associate one or more knowledge bases that share the same vector model. Bases built on different vector models cannot be associated together. During checking, confirm the identifiers first and exclude the ones that do not match; do not run a cross-model search to compare missed recall. The minimum relevance value is a filter threshold that takes effect only in semantic retrieval or when result re-ranking is used. It does not perform permission filtering or entity isolation. The same-vector-model requirement for associated bases does not extend to business-registration sites or other external systems.

The optional paths shown in the overall retrieval diagram do not all execute on every request. Image retrieval requires corresponding image input and model capability. Result re-ranking requires a model and must be enabled by the setting. RRF is the result-fusion step of hybrid retrieval and is not described as a standalone switch. A thinking budget is a reasoning budget and is unrelated to the token control of the citation limit.

Hypothetical drill sample: in a brand member operations handover packet, one privacy authorisation record reads in full, "Member ID M-0001, authorisation scope: enterprise WeChat outreach, authorisation date 1 March 2025, status: signed." A draft sentence in the same batch of outreach plan material reads, "Issue the April coupon to M-0001." The authorisation state of this request is undetermined.

## Configuration and implementation checks

| Configuration or check item | Hypothetical trial starting point and reason | Comparison method |
| --- | --- | --- |
| Associated knowledge base | Select the member material base that shares the vector model of the handover material; start with one base | Check the selected base identifier against the vector model identifier, and exclude non-matching bases |
| Search mode | Semantic retrieval, used for natural-language question checking | Compare against full-text retrieval; switch identifier-type queries to full-text or hybrid |
| Citation limit | Start at 2000 tokens, because the sample material is short and truncation is easy to observe | Compare against the sample source length and confirm whether the citation was cut |
| Minimum relevance | Start at 0.5, to observe whether low-relevance results are filtered | Compare against the re-ranking score and confirm the threshold does not perform permission filtering |
| Citation content output | Observe whether the output array length can be zero | Use a paper input of an empty array to check the downstream receiving design |
| Material currency check | Test the current and historical versions of the privacy authorisation record separately | Compare the cited text against the effective version and record which version was used |

## Three common errors

1. Treating a retrieved citation as an executed authorisation. Input the sample privacy authorisation record and the draft sentence; compare the retrieval output against the authorisation status field. The observable result is that the citation array contains the record, while the authorisation scope states enterprise WeChat outreach only and does not cover coupon issuance. Whether authorisation holds remains to be verified.

2. Treating minimum relevance as a permission or entity filter. Input the sample member ID with an unrelated query; compare the returned results against the authorisation scope. The observable result is that the relevance threshold affects ordering only and does not exclude unauthorised records. Retrieval does not perform authorisation judgement.

3. Merging pending review and signed into one fact. Input the status field of the sample authorisation record; compare the three separate statements of signed, cooperation reached and contract effective. The observable result is that the record states signed only, does not state coupon-issuance authorisation, and the request is unsupported. It cannot be recorded as a denial or a conflict.

## How to verify the setup

1. Input the sample privacy authorisation record text and the draft sentence; compare the authorisation scope field in the cited text against the operation requested by the draft sentence. The observable result is that the cited text covers enterprise WeChat outreach only, coupon issuance is outside the authorised scope, and the finding is unsupported.

2. Input the sample member ID M-0001 with an unrelated query; compare the returned citation array against the authorisation record. The observable result is that the array length may be zero or may contain unrelated text, the minimum relevance value does not exclude unauthorised records, and retrieval does not constitute authorisation.

3. Input the current and historical versions of the privacy authorisation record; compare the authorisation scope and date fields across the two versions. The observable result is that mutually exclusive values in the same field are recorded as a conflict, a value present in only one version is recorded as pending verification, and missing evidence stays missing.
