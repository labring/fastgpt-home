# Brand member operations: retrieval for operations handover

## What the documents look like

Brand member operations work with customer data and repeat-purchase outreach. The main sources are the CRM system, enterprise messaging, POS purchase records, and mini-program behavior data. The documents handled day to day are member tag tables, outreach plans, coupon rules, and privacy authorization records. These materials update daily or weekly, so a handover can encounter tags, coupon states, and authorization records that come from different update batches. The consequences of error are outreach complaints, uncontrolled coupon cost, and member loss, which makes the question of whether retrieved content can support a permission judgment more important than retrieval speed.

## Constraints at the retrieval step

The knowledge base search node can associate one or more knowledge bases that use the same vector model. The smallest search unit is the knowledge base; collections serve only to classify and manage data and do not affect search results. Quoted content is output as an array and its length can be 0, which means the downstream path still runs even when nothing is retrieved. Retrieval is not authorization: semantic recall and relevance scores do not judge operating permission or entity ownership. Hybrid retrieval merges multiple result paths through RRF, reranking requires a model and must be enabled by configuration, and image retrieval requires image input together with model capability. These optional paths do not all execute on every request.

Hypothetical paper exercise sample. The source material reads: "Member ID M-2041 held discount coupon C-88 from 1 March 2025 to 31 March 2025, status redeemed; this member's April 2025 outreach plan is marked pending store confirmation." The draft handover request reads: "Coupon C-88 for M-2041 is redeemed; please hand over the April outreach permission." Checking must compare subject, period, and field: the coupon status is redeemed, while the outreach plan is pending store confirmation. These are different fields. The draft sentence presents the outreach permission as directly transferable and lacks evidence that store confirmation was completed.

## Three common errors

1. Treating a retrieval hit as confirmed permission. The input is a retrieved member tag or coupon rule fragment. Compare whether that fragment states the authorized operating subject and scope. The observable result is that the fragment describes only a status and carries no authorization field, so the handover action must not be executed.
2. Writing a pending-review state as already effective. The input is the outreach plan marked pending store confirmation in the hypothetical sample. Compare whether the same field holds a mutually exclusive value in the same period. The observable result is a single pending value, so the request is unsupported and the evidence gap must be recorded.
3. Associating bases with different vector models and then inferring runtime results. The input is two base identifiers. Compare whether their vector model identifiers match. The observable result is that the identifiers differ, so the non-conforming base is excluded and the actual observation is recorded, without inferring missed recall or redundancy.

## How to verify the setup

1. For the hypothetical sample, input the draft handover request sentence and compare whether the retrieved content contains member ID M-2041, coupon C-88, the March 2025 period, and the redeemed status. The observable result is that the quoted content covers those fields and contains no statement that authorization is complete; the retrieval-side check then passes, while whether the authorization can be handed over remains unverified.
2. For empty-result handling, input the paper value [] and compare whether the downstream design follows the path for a quote length of 0. The observable result is that the downstream does not break on the empty array, so the empty-result handling check passes. No claim is made that a fictional rule search necessarily returns [].
3. For cross-model association, input two base identifiers and compare whether the vector model identifiers are the same. The observable result is that differing identifiers lead to exclusion, and no cross-model retrieval is executed to compare missed recall.
