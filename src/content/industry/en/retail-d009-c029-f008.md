# After-sales repairs and reships: workflow routing for operations handover

## What the documents look like

After-sales repairs and reships aim to restore a product to working use, and the closing state differs from a refund-only dispute. The daily materials are a repair request, a reship order, an inspection report and a parts outbound record. These come from the after-sales system, the order system, repair outlets and the parts warehouse WMS. Materials update per ticket and per day. At handover, one work order can carry request, inspection and outbound records at the same time. Workflow routing has to map these materials to specific nodes so the collected information reaches later decision or interface nodes.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interactive state, the workflow state is recorded, and after the user submits the required information the node passes that information to later nodes. The user selection node is also a user interaction node. When it triggers, the conversation enters an interactive state, and when the user makes a choice the node evaluates the choice and executes the corresponding "yes" branch. Both nodes can be added repeatedly and trigger execution. Retrieval and form collection only gather information. Order writes, document backfill and external status synchronization require a separate business interface or a later process. Interactive waiting, state recording and hiding the dialog are existing node behaviors. No global state-recording switch is set here, and no submission count or automatic judgment is assumed.

Hypothetical paper exercise sample: the source material reads "Repair request WX-0417, subject is a brand after-sales outlet, object is one signed-for complete unit, application date 2025-04-17, status pending inspection; inspection report JC-0417 records the fault as damaged parts, conclusion repairable; parts outbound record PJ-0417 states the part has been issued, quantity one, outbound date 2025-04-18." The draft sentence to be judged is "This work order has completed the reship and the customer has confirmed receipt." The comparison checks the subject, object, status and date range of the draft against the three materials. The materials do not state a reship order or a customer confirmation record, so the sentence is unsupported.

## Configuration and implementation checks

| Configuration item | Value or check on this page | Note |
| --- | --- | --- |
| Form input node | Collect repair request number, inspection conclusion, parts outbound status | Submitted information passes to later nodes |
| User selection node | Set repair and reship branch options | After the user chooses, the "yes" branch executes |
| Interactive state check | After triggering, confirm the conversation enters the interactive state | State recording is node behavior |
| Output handover | Pass collected information to later retrieval or interface nodes | Compare each output against its input |
| External action split | Order writes and status synchronization use a separate business interface | The form does not carry authorization execution |
| Hypothetical trial starting point | Reship order number field left blank, compared with source material | This starting point is used for the present paper check |

## Three common errors

1. Treating form submission as reship authorization. Input is the draft sentence and the source material. Compare whether the material states a reship order and an authorization record. When the material does not state them, the sentence is unsupported.
2. Treating execution of a user selection branch as a completed business action. Input is the user selection node configuration and the draft sentence. Compare whether an order write or status synchronization interface exists. When the interface is absent, the action has not executed.
3. Treating retrieval results as a permission filter. Input is the returned records and the handover request. Compare whether the record subject matches the request subject. When the subjects differ, the record does not enter the handover.

## How to verify the setup

1. Input the draft sentence and the three source materials from the hypothetical sample. Compare subject, object, status and date fields. When the reship completion described in the draft has no corresponding record in the materials, mark it unsupported.
2. Input the user selection node branch configuration and the interactive state record. Compare whether the corresponding "yes" branch executes after the user makes a choice. When the branch is not connected, that path does not hold.
3. Input the paper empty result [] and the downstream node design. Compare whether the downstream has a handover statement for the empty result. When it is absent, record it as pending addition, and do not claim that a fictional rule retrieval necessarily returns an empty result.
