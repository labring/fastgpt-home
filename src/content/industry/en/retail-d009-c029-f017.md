# After-sales repairs and reships: upgrades for operations handover

## What the documents look like

After-sales repair and reship work aims to restore a product to use, so cases close through repair completion or replacement delivery rather than through a direct refund decision. The working documents are repair requests, reship orders, inspection reports and accessory outbound notes. These come from the after-sales system, the order system, repair outlets and the accessory warehouse WMS, and they update per order and daily. Each document records a different fact: a request records submission, a reship order records a dispatch or delivery state, an inspection report records a conclusion about the fault, and an accessory outbound note records that stock left the warehouse. None of these substitutes for another, and a retrieval hit or a completed form field only shows that information is readable. It does not show that an authorization step has occurred.

## Constraints at the upgrades step

Across an upgrade, field meanings in repair requests and reship orders, the wording of inspection conclusions, and the issuing party on accessory outbound notes can all change with the version. Operations permission and handover management therefore requires confirming, at deployment and upgrade time, which accounts may submit, which accounts may approve, and which actions count as execution. Retrieval association within the same vector model addresses recall only; it does not carry permission or entity isolation, and a similarity score is not an authorization credential. Empty-reference output follows its documented conditions and cannot be treated as proof that a business record does not exist. Libraries on different vector models cannot be associated together, so identifiers should be checked first and non-matching libraries excluded.

Hypothetical paper exercise sample. A brand after-sales team prepares handover material before an upgrade. The source text has three sentences. Sentence one: "Repair request WX-A, subject the after-sales service group, object the faulty item on order A, status awaiting inspection, valid scope limited to that order." Sentence two: "Reship order BJ-B, subject the accessory warehouse, object the replacement part for order A, status dispatched, issue date the day before the upgrade." Sentence three: "Inspection report JC-C, subject the repair outlet, object the faulty item on order A, conclusion repairable, not yet entered into the reship process." The handover request to be assessed: "Mark reship order BJ-B for order A as completed, and update repair request WX-A to closed." This request covers two actions, a reship status change and a repair case closure, and the material states no approver or execution authorization.

## Three common errors

1. Treating a retrieval hit as authorization. Input: the handover request sentence and the retrieval result. Comparison: the approval field in the material. If the material states no approver, the authorization state is unsupported and the order cannot be marked completed.
2. Treating an awaiting-inspection status as grounds for a reship. Input: repair request WX-A status "awaiting inspection" and inspection report JC-C conclusion "repairable". Comparison: the two conclusions. The dispatched state of reship order BJ-B and a repair closure are different facts and cannot be derived from each other.
3. Treating a configuration default as a business rule. Input: the value of DEFAULT_TEAM_BASIC_PERMISSIONS_ENABLED. Comparison: the permission difference between new and existing teams. This variable does not affect existing teams, so it cannot support an inference about the handover authorization scope.

## How to verify the setup

1. Input the three hypothetical source sentences and the handover request sentence. Compare "mark as completed" in the request against the "dispatched" state of reship order BJ-B in the material. If the material states no completion approval, the result is unsupported and the evidence gap must be recorded.
2. Input the "awaiting inspection" status of repair request WX-A and the "repairable" conclusion of inspection report JC-C. Compare the same field on the same order A. The two do not conflict, but the reship process has not started, so the repair request cannot be closed.
3. Input the hypothetical value of AIPROXY_API_ENDPOINT and the documented root-address format. Compare whether `/v1` is appended. If it is, the value does not match the documented requirement and must be corrected before re-checking. All of the above is paper review, and no test, deployment, approval or business action is claimed to have occurred.
