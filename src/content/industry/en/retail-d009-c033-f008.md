# Trade and FX administration: workflow routing for operations handover

## What the documents look like

Foreign-exchange receipt and settlement work, together with trade directory records, relies on a small set of recurring materials: foreign-exchange receipt slips, trade contracts, invoices, and foreign-exchange business registration records. The paying entity, amount, contract number, and registration status sit across bank online portals, enterprise financial ledgers, and customs export data. Confirming the receiving entity, completing settlement, and explaining the underlying trade background are the most time-consuming steps. Records update at two rhythms, per transaction and monthly, and the same transaction can show different field values at different stages across these materials. Workflow routing must accept that state.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. After the user completes required fields and submits, the node collects the submitted form values and passes them to later nodes. The user selection node is also a user-interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. When the user makes a choice, the node evaluates that choice and executes the "yes" branch. Both nodes can be added repeatedly and trigger execution. Retrieved results and collected form values do not constitute authorization. Order writing, document backfill, and external status synchronization require a separate business interface or a later process.

Hypothetical paper test case. Material text one: "The foreign-exchange receipt slip shows the payer as Company A, amount USD 12,000, contract number HY-001, receipt date 5 March 2024." Material text two: "Trade contract HY-001 has Company A as signing party, invoice number FP-001, amount USD 12,000." Handover request to be assessed: "Transfer the settlement operation permission for this receipt to Post B, and treat settlement as completed." In this sample the entity is Company A, the object is the receipt under contract HY-001, the state is received but not settled, and the authorization boundary is operations permission and handover management. The request merges permission transfer and settlement completion into one fact and lacks evidence of settlement execution.

## Configuration and implementation checks

| Configuration item | Setting on this page | How to check |
| --- | --- | --- |
| Form input node required fields | Receiving entity, contract number, amount | After submission, compare each item against later node inputs |
| User selection node branch | "Yes" branch carries the settlement permission handover confirmation | Check branch connection and the selection result |
| Interaction state recording | Workflow state is recorded when an interaction node triggers | Inspect continued execution after entering the interaction state |
| Output handoff | Collected values pass to later retrieval or decision nodes | Compare output against input fields for consistency |
| External operation split | Settlement execution and status synchronization connect to a separate business interface | Check whether a corresponding downstream implementation exists |
| Hypothetical test starting value | Permission handover confirmation set to "pending confirmation" | Compare against the material text state; this is not an official default |

## Three common errors

1. Treating a retrieval hit as a permission grant. Library similarity does not perform permission or entity isolation. A hit on Company A material does not mean Post B holds settlement operation permission. Check the input as the retrieval result, compare against the authorization status field, and observe whether an explicit authorization record appears.

2. Treating a collected form value as an executed business action. Form submission only passes information. Settlement completion requires downstream interface or process evidence. Check the input as the submitted form value, compare against the settlement status, and observe whether an execution record exists.

3. Treating a pending-review state as absent operation permission. Pending review and permission presence are different fields. Check the input as the original state field text, compare against the permission field, and observe whether the two are mutually exclusive on the same entity, same period, and same field.

## How to verify the setup

- Verification one: input the hypothetical material texts one and two, compare the receiving entity, contract number, and amount fields. When all three match and the state is received but not settled, the materials can carry the handover. This is a paper comparison only and was not executed.

- Verification two: input the handover request to be assessed, compare the phrase "treat settlement as completed" against the material state field. When the materials do not record settlement execution evidence, the request is unsupported and the evidence gap is recorded. This is a paper comparison only and was not executed.

- Verification three: input an empty result [] to check the downstream handoff design, and observe whether the downstream handles an empty input as designed. Do not claim that a fictional rule retrieval necessarily returns []. This is a paper comparison only and was not executed.
