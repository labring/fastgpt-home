# Trade and FX administration: access controls for operations handover

## What the documents look like

Trade and FX administration for foreign exchange collection, settlement and trade directory work runs on a document set that includes foreign exchange receipt vouchers, trade contracts, invoices and foreign exchange business registration materials. These records update per transaction and per month. The main verification burden falls on matching the receiving entity: which contract, which invoice and which registered entity correspond to a given inbound payment. During a handover, the visibility of these materials and the operational rights over them need separate confirmation. Content organization, such as file classification and retrieval relevance, is not access authorization. A retrieval hit does not grant permission to open or edit a record.

## Constraints at the access controls step

Team permissions are decided across three dimensions: member, department and group. The system checks individual member permissions first, then takes the union of department and group permissions, and the final permission is the combination of those results. Individual member permissions carry the highest priority and can override an all-member group permission. A knowledge base is always the threshold: collection (file/folder) permissions cannot bypass knowledge base permissions. File-level permission is a commercial-edition feature and is off by default. In the off state, collection readability matches the knowledge base and the system queries no collection permission records. In the on state, each file or folder generates a full permission snapshot, and list, detail and retrieval recall are authorized item by item against that snapshot. Enabling and disabling both require knowledge base administrator rights. Disabling deletes all collaborator configurations for every file and folder under that knowledge base and cannot be reverted. Deleting a file is limited to the creator; an administrator or write-permission collaborator cannot delete it. Retrieval recall filters by the current member's readable files, and this applies only when authorization runs by current member identity. A workflow that preselects a knowledge base without member-identity authorization does not apply file-level filtering. A team administrator does not bypass file-level permissions.

Hypothetical paper exercise sample: a trade finance staff member submits a handover request to transfer access and edit rights over a foreign exchange receipt voucher, a trade contract, an invoice and foreign exchange business registration materials to a successor colleague. The source text for verification reads: "Foreign exchange receipt voucher number SW-2024-031, receiving entity Company A, amount consistent with contract HT-2024-018; trade contract HT-2024-018 signed between Company A and Company B; foreign exchange business registration materials registered to Company A." The draft handover request sentence reads: "Grant the successor colleague file-level permission over the four materials in the knowledge base and allow modification of file content." This request involves knowledge base read permission and file write permission, and it must first be confirmed whether the knowledge base has file-level permission enabled.

## Configuration and implementation checks

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison method |
| --- | --- | --- |
| Knowledge base read permission | Successor colleague holds read permission on the knowledge base | File-level permission cannot bypass the knowledge base threshold; check the knowledge base collaborator list before comparing file visibility |
| File-level permission switch | Assume the knowledge base is not yet enabled | While off, any single-file permission write is rejected; enable first, then configure |
| File write permission | Intend to grant the successor colleague write permission | Write permission allows modifying content, updating, syncing and adjusting training parameters; compare against a read-only request |
| Creator record | The submitted collaborator list includes the current creator | Under full-overwrite semantics, omitting the creator causes rejection; compare list members item by item |
| Retrieval recall scope | Authorize by current member identity | A workflow that preselects a knowledge base without member-identity authorization does not apply file-level filtering; check the call method |
| Permission subject | One of member, member group or organization | Team permissions require selecting member/organization/group before configuration; verify each subject identifier |

## Three common errors

1. Treating retrieval relevance as access authorization. Retrieval recall filters by the current member's readable files, and a similarity score does not perform permission or entity isolation. The check input is the retrieval query and the current member identity; compare the recall results against the file collaborator list and observe whether an unauthorized file appears in the results.
2. Submitting a single-file permission configuration while the knowledge base has file-level permission disabled. The system rejects the write and prompts to enable first. The check input is the configuration dialog submission action; compare the switch state before and after submission and observe whether an enable prompt appears.
3. Omitting the current creator from the collaborator list in a handover request. Collaborator configuration uses full-overwrite semantics, and the submitted list is the final result. The check input is the proposed collaborator roster; compare the roster against the current creator record and observe whether submission is rejected.

## How to verify the setup

1. Use the hypothetical sample source text and the draft handover request sentence, with the successor colleague account and the knowledge base holding the four materials as input. Compare that account's knowledge base collaborator configuration against the file collaborator configuration, and observe whether the file list filters by readable files with unreadable files not occupying a slot. The expectation is visibility only when both knowledge base read permission and file read permission are present; missing either one means no visibility.
2. The input is the write-permission grant action in the draft handover request sentence. Compare the submitted collaborator list against the current creator record. Observe whether the submission includes the creator, and whether omission causes rejection. The expectation is that submission passes when the list includes the creator and a rejection prompt appears when it does not; the prompt content follows the actual interface.
3. The input is the retrieval query and the successor colleague identity. Compare the recall results against the file readable scope. Observe whether an unauthorized file is recalled. The expectation is that unauthorized files are not recalled when authorization runs by current member identity; if a workflow preselects a knowledge base without member-identity authorization, file-level filtering does not take effect, and in that case record the actual observation without inferring permission configuration success or failure.
