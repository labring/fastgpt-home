# Trade returns and claims: workflow routing for operations handover

## What the documents look like

Trade returns and claims concern reverse logistics and liability determination after goods have been exported. The direction of work runs opposite to ordinary export customs declaration. The main data sources are customer email, quality inspection reports, customs systems and insurer claim systems. The documents handled in day-to-day work include return agreements, claim letters, quality reports and return customs declarations. The supplied brief describes the update frequency as irregular, on a per-case basis.

These features shape what workflow routing must support. Return-reason confirmation, return declaration filing and claim-evidence submission are the three most time-consuming stages, and each one depends on a person submitting material or making a choice. The form input node and the user selection node are both user-interaction nodes. When either is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The form input node collects required information and passes it to later nodes. The user selection node evaluates the user's choice and executes the corresponding branch. Retrieval and form collection do not by themselves constitute authorization, so operations handover must distinguish which authorization state each document, action or request is in.

## Constraints at the workflow routing step

The waiting behaviour and state recording of interaction nodes come from the nodes themselves. The supplied documents do not describe a global state-recording switch, a submission-count limit or an automatic judgment mechanism. Values collected by a form must be explicitly passed to later retrieval, judgment or interface nodes, and outputs must be compared item by item against inputs. Order writes, document backfill and external status synchronization require a separate business interface or a later process; a form submission does not perform them automatically.

A knowledge-base relevance score does not perform permission or entity isolation, and a retrieval result is not authorization. Only knowledge bases using the same vector model can be associated together; cross-model association is not possible, so identifiers must be checked first and non-matching items excluded. Hybrid result fusion is a process, not a switch that can be turned on. Image retrieval requires corresponding image input and model capability, and reranking requires a model and must be enabled in settings. These optional paths do not mean every request executes all of them. Empty-result handling can be checked against downstream design using an explicit paper input; no claim is made that a fictional rule search necessarily returns an empty array.

Hypothetical paper exercise sample: the source material reads, "Party A received the goods returned by Party B on 10 March 2025, quantity 120 pieces. Quality inspection report number QC-2025-0310 determined that 30 of these pieces have welding defects. The two parties signed a return agreement on 15 March 2025, agreeing that those 30 pieces are to be filed for return declaration." A pending handover request reads, "Please process all 120 pieces in this batch as a return declaration and synchronize the insurer claim status." This request exceeds the 30-piece scope agreed in the return agreement, and claim status synchronization requires a separate connection to the insurer claim system.

## Configuration and implementation checks

| Configuration item | Starting point for this hypothetical exercise | How to check |
| --- | --- | --- |
| Required fields on the form input node | Return agreement number, quality report number, return quantity | After submission, compare the field values passed to later nodes |
| Branches on the user selection node | Two options: "confirm return reason" and "supplement evidence" | Verify each branch connection and the selection result |
| Interaction state recording | Recorded when an interaction node is triggered | Observe whether the conversation enters the interaction state and resumes execution |
| Output receiving node | Pass form values to a later judgment node | Compare outputs against inputs item by item |
| External action division | Order writes and claim synchronization connect to separate interfaces | Check which interfaces and business actions are connected |

The return quantity field is chosen as the starting point for this hypothetical exercise because the sample agreement covers only 30 pieces, which creates a comparable difference against the 120 pieces in the request. The comparison method is to check the form-collected value against the agreement text word by word. This starting point is a hypothetical setting for this page and is not an official default value.

## Three common errors

1. Treating form submission as authorized execution. In the sample, submitting the form collects only the return agreement number and quantity; it does not produce authorization for a return declaration or claim synchronization.
2. Treating a retrieval result as a permission filter. A relevance score does not exclude unrelated business or unauthorized records, and retrieving material does not mean that material can be used in the current handover.
3. Treating a pending-review state as missing operating permission. In the sample the return agreement has been signed, but claim status synchronization still requires the insurer claim system to implement it; signing and system synchronization are two different facts.

## How to verify the setup

1. Enter the sample source material and the pending request, compare the 120 pieces in the request against the 30 pieces agreed in the agreement, and observe whether the system passes the out-of-scope quantity to later nodes. If the form collects only the agreement number and quantity without performing a scope check, the scope comparison is not supported and the evidence gap must be recorded.
2. Enter the "confirm return reason" option from the sample, compare the user's selection result against the branch connection, and observe whether the corresponding branch executes. If the branch is not connected or the selection result is not passed, this is a configuration gap.
3. Enter a paper empty array to check the downstream receiving design, compare how later nodes handle an empty result against the design, and observe whether undefined behaviour appears. This check does not claim that a fictional rule search necessarily returns an empty array; it verifies only how downstream handles empty input.
