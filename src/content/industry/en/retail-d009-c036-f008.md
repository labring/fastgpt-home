# Multi-warehouse inventory: workflow routing for operations handover

## What the documents look like

Multi-warehouse allocation happens at the order routing stage and determines which warehouse fulfils a shipment. This placement differs from courier handover, which occurs later in fulfilment. The main data sources for this category are the WMS, the OMS, ERP inventory records and platform inventory interfaces, with update frequencies given as daily or hourly. The daily documents are allocation rules, inventory synchronization tables, transfer orders and shortage alerts.

Within operations permission and handover management, these materials act as state records. Allocation rules state the priority of each fulfilment warehouse. Inventory synchronization tables reflect sellable stock. Transfer orders record movement between warehouses. Shortage alerts flag overselling risk. Workflow orchestration has to turn the fields, states and validity ranges in these documents into checkable inputs, pass them to interaction nodes for collection or confirmation, and then hand them to downstream nodes.

A practical consequence is that routing decisions depend on several documents at once, and those documents can disagree. An allocation rule can name a priority while the synchronization table shows no sellable stock at that warehouse. A transfer order can be raised to correct the imbalance while still awaiting review. The orchestration layer does not resolve these disagreements by itself; it carries the collected values forward and leaves the business decision to the connected systems.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The node collects the required information the user submits and passes it to subsequent nodes. The user selection node is also a user interaction node. When the user makes a choice, the node evaluates that choice and executes the corresponding “yes” branch. The interaction state is recorded by the interaction node; no separate global state-recording switch is documented.

Information collected at these nodes has to be passed explicitly to later retrieval, judgement or interface nodes, and output compared against input item by item. Order writing, document backfill and external status synchronization require a separate business interface or a later process. The nodes themselves do not perform those business actions.

Hypothetical paper exercise sample. The source text reads: “The allocation rules table states: East China warehouse priority 1, South China warehouse priority 2, applicable from 1 March 2025 to 31 March 2025. The inventory synchronization table states: East China warehouse SKU-A sellable stock 0, South China warehouse SKU-A sellable stock 120. Transfer order TR-0315 states: 50 units of SKU-A transferred from East China warehouse to South China warehouse, status pending review.” The draft sentence to be assessed is: “East China warehouse sellable stock is insufficient, and the system should automatically route the order to South China warehouse for dispatch.” This sentence concerns routing execution, which requires a separate business interface or later process; the node itself does not complete routing.

## Three common errors

1. Treating information submitted at the form input node as completed routing execution. Input: the sample values “East China warehouse sellable stock 0, South China warehouse sellable stock 120”. Comparison: whether the node output contains a routing action. Observable result: the node passes information only and does not execute routing.
2. Treating the “yes” branch of the user selection node as authorization approval. Input: the sample transfer order status “pending review”. Comparison: the field values “pending review” and “reviewed”. Observable result: the two values differ, and pending review does not demonstrate that authorization has been granted.
3. Treating retrieval or form collection as a permission isolation mechanism. Input: the date range in the sample allocation rules table. Comparison: whether retrieval results are filtered by warehouse or by permission. Observable result: retrieval does not carry permission or entity isolation functions.

## How to verify the setup

1. Take the sample source text “The allocation rules table states: East China warehouse priority 1, South China warehouse priority 2, applicable from 1 March 2025 to 31 March 2025” and enter it at the form input node. Compare whether the output contains the priority and applicability date fields. The condition is satisfied when the output fields match the input.
2. Take the sample draft sentence “East China warehouse sellable stock is insufficient, and the system should automatically route the order to South China warehouse for dispatch” and enter it at the user selection node. Compare whether the downstream node connected to the “yes” branch contains a routing interface. The condition is satisfied when the downstream node is explicitly marked as requiring a separate business interface.
3. Take the sample transfer order status “pending review” and enter it at the output handover check. Compare whether a later node records “pending review” as a completed handover. The condition is satisfied when the later node retains the “pending review” status and records the evidence gap.
