# Peak-sale fulfillment: workflow routing for operations handover

## What the documents look like

Peak-sale warehouse and delivery scheduling centers on short-term peak capacity and the arrangement of people, vehicles and dock space. This differs from multi-warehouse inventory synchronization, which pursues continuous balance. The main data sources are historical peak-sale orders, platform campaign registrations, WMS capacity and courier pickup capability. New data appears per campaign and daily. The documents handled day to day are the peak-sale forecast table, staff scheduling, the courier support plan and the exception daily report. In operations permission and handover management, these materials form the input basis for workflow routing.

In this task, workflow routing uses the Form Input node to collect the required information a handover needs, and the User Selection node to obtain the handover decision. The information collected then drives subsequent retrieval, judgment or interface nodes. When the Form Input node triggers, the conversation enters an interaction state and the workflow state is recorded; after the user completes the interaction, execution continues. The User Selection node executes the corresponding branch after the user makes a choice. Both nodes are user interaction nodes, and triggering either one enters the interaction state and records the workflow state. That state record is node behavior; no separate global state-recording switch exists.

## Constraints at the workflow routing step

The daily update frequency of peak-sale scheduling documents means handover materials may change each day. Each workflow run needs to collect current information again and cannot rely on cached values from a previous interaction. Collected information must be explicitly passed to subsequent nodes, and output and input are compared item by item.

Order writes, document backfill and external status synchronization require a separate business interface or a later process. Retrieval results do not constitute authorization, and form-collected values do not constitute approval. Which materials, operations and requests in an operations handover sit at which authorization state is determined by later business nodes; workflow routing itself does not perform authorization actions.

Hypothetical drill sample

Material text for checking:

"The peak-sale forecast table (June 2026 campaign) shows: the East China warehouse peak capacity is 80,000 orders per day, and courier pickup capability is 75,000 orders per day. The staff scheduling table (June 1 to June 18) notes that temporary staff arrive on June 1, with 120 people on duty. The courier support plan (June edition) states that pickup vehicles reach the warehouse dock before 18:00 each day."

Handover request to be assessed:

"Please hand over the East China warehouse June peak-sale scheduling plan to the next shift. The handover scope includes the forecast table, scheduling table and support plan, authorizing the next shift to execute scheduling adjustments from June 1 to June 18."

In this request, the material subject is the East China warehouse, the object is the next shift, the time range is June 1 to June 18, and the authorization boundary is executing scheduling adjustments. The source text does not state whether the next shift holds scheduling adjustment permission, nor does it state an authorization approval record. This request remains pending verification.

## Three common errors

1. Treating the handover request collected by the Form Input node as authorization to execute. The Form Input node collects required information and passes it to subsequent nodes; authorization judgment requires a later business node. In the sample, the phrase "authorizing the next shift to execute scheduling adjustments" has no corresponding approval record in the source text, so that authorization remains pending verification.

2. Treating branch execution by the User Selection node as completion of business approval. The User Selection node executes the corresponding branch after the user makes a choice, and the branch points to subsequent nodes. In the sample, if the user selects "agree to hand over," that choice only triggers branch execution and does not constitute a grant of scheduling adjustment permission.

3. Treating retrieval results or similarity scores as permission filtering. Retrieval does not perform authorization judgment, and a similarity score does not exclude unrelated business or unauthorized records. In the sample, if the East China warehouse scheduling plan is retrieved, that result only indicates a match and does not indicate that the next shift has the right to execute adjustments.

## How to verify the setup

1. Enter the sample material text and handover request, then check whether the Form Input node collects the three items of time range, warehouse subject and material list, and whether the output is passed to subsequent nodes. Expected observation: the three items appear in the input of subsequent nodes. If an item is missing, record the missing item.

2. Enter the sample handover request, then check whether the User Selection node presents choices on whether to hand over or on handover scope, and whether the corresponding branch executes after the user makes a choice. Expected observation: after the choice, the workflow continues along the corresponding branch. If the branch does not execute, record the actual observation.

3. Enter the sample material text, then check whether subsequent nodes compare "authorizing the next shift to execute scheduling adjustments" against the approval records in the source text. Expected observation: when the source text states no approval record, that authorization judgment remains pending verification. If a subsequent node outputs a definite authorization conclusion, record the difference between that output and the source text.
