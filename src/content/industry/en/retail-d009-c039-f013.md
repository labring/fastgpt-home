# Tmall flagship operations: access controls for operations handover

## What the documents look like

Daily Tmall flagship store operations revolve around four recurring materials: product publishing pages, brand authorization letters, delivery commitment records, and after-sales tickets. These are drawn from the Tmall merchant backend, the Tmall rules center, ERP order tables, and customer service chat logs. Brand authorization and flagship store identity form the platform-side threshold, and delivery commitments together with delayed-shipment compensation rules directly affect store ratings. The materials update daily or per order; that update frequency does not change how access control decisions are made, and this page does not derive any automatic synchronization mechanism from it.

For operations handover, the practical difficulty is that materials, actions, and requests each sit at a different authorization state. A product publishing page may be readable while the underlying brand authorization letter has an authorization window that does not cover the handover period. A delivery commitment record may be editable by one role and only readable by another. An after-sales ticket may be pending review rather than approved. Separating these states is the core of the access controls step.

## Constraints at the access controls step

FastGPT evaluates permissions across three dimensions: members, departments, and groups. Member permissions have the highest priority. Department and group permissions are combined as a union and sit below member permissions. Knowledge base permission is always a threshold; collection-level permission cannot bypass knowledge base permission. Collection-level permission is a commercial-edition feature. In the closed state, collection readability matches the knowledge base and the system does not query any collection permission records. In the open state, each file or folder generates a complete permission snapshot, and list, detail, and retrieval recall are each authorized against that snapshot. Retrieval recall filters by the files readable by the current member, and this applies only when authorization is performed by current member identity; in workflows where a knowledge base is preselected and authorization is not by member identity, collection-level filtering does not apply. Relevance scores and vector models do not carry permission or entity isolation duties. Knowledge bases across different vector models cannot be jointly associated; identifiers must be checked first and non-matching entries excluded.

Hypothetical paper exercise sample: in a Tmall flagship store operations handover scenario, the material text to be checked reads: "Brand authorization letter A-2024-07, authorizing party is Brand Owner A, authorized party is E-commerce Company B, authorization scope is daily operations of the Tmall flagship store, authorization valid until June 30, 2025." A handover request to be judged reads: "Grant write permission on brand authorization letter A-2024-07 to a member of Agency C, for product publishing in July 2025." In this sample the stated authorization window ends June 30, 2025, the request concerns July 2025, and the material does not state whether authorization continues into that period.

## Configuration and implementation checks

The following configuration items relate to the sample above and list documented settings or implementation checks relevant to this feature. The hypothetical starting values are for this paper comparison only; the reason for each choice and the comparison target are stated, and no official default is implied.

| Configuration item | Hypothetical starting value for this exercise | Comparison target and reason |
| --- | --- | --- |
| Knowledge base collection-level permission switch | Closed state | Compared with open state; in closed state the system does not query collection permission records, in open state each snapshot is authorized item by item |
| Collaborator role | Write permission | Compared with read permission and administrator; write permission corresponds to modifying content, updating, syncing, and adjusting training parameters |
| Authorization validity check | June 30, 2025 | Compared with the requested period of July 2025; the material states the window ends on that date |
| Retrieval authorization mode | Authorized by current member identity | Compared with preselected knowledge base without member-identity authorization; the latter does not apply collection-level filtering |
| Vector model identifier | Matches the target knowledge base | Compared with a non-matching identifier; knowledge bases across different vector models cannot be jointly associated |
| Collaborator list submission mode | Full overwrite | Compared with incremental submission; the submitted list is the final result and must contain the current creator |

## Three common errors

1. Treating the authorization window of the brand authorization letter as covering the handover request period. In the sample the stated window ends June 30, 2025, the request concerns July 2025, and the material does not state whether authorization continues into that period. The request cannot be treated as authorized on the existing material.

2. Treating retrieval relevance or vector model consistency as a permission isolation measure. Relevance does not carry permission or entity isolation duties, and knowledge bases across different vector models cannot be jointly associated. Identifiers must be checked and non-matching entries excluded.

3. Treating a pending handover request as a completed permission grant. The request is in a to-be-judged state, has not been approved, and has not been executed, so the Agency C member cannot be treated as having obtained write permission on that basis.

## How to verify the setup

1. Input the sample material text and the handover request, and compare the stated authorization end date of June 30, 2025 with the requested period of July 2025. If the material does not state that authorization continues into July 2025, the authorization state for the requested period is unsupported and the evidence gap is recorded.

2. Input the write-permission grant target from the sample request and compare against the knowledge base collection-level permission switch state. If the switch is in the closed state, any write operation configuring a single file permission is rejected with a prompt to enable it first. If the switch is in the open state, check whether the collaborator list contains the current creator; a full-overwrite submission that omits the creator is rejected.

3. Input a retrieval condition authorized by current member identity and a retrieval condition with a preselected knowledge base without member-identity authorization, and compare the recall scope. The former filters by files readable by the current member; the latter does not apply collection-level filtering. Record the observed result without presupposing a first hit or full recall.
