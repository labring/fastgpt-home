# Customer-service knowledge: access controls for operations handover

## What the documents look like

Customer-service knowledge base maintenance works across FAQ entries, reply templates, product parameter tables and escalation tickets, with material refreshed weekly or monthly. This category sits ahead of refund and return handling: the work organizes question-and-answer material and does not directly approve refunds. Material refresh cadence and permission configuration are independent of each other. Permission changes follow staff handover or responsibility adjustments, not the document refresh cycle.

The type of material affects permission granularity. FAQ entries and reply templates are commonly shared across a whole knowledge base, while product parameter tables may be split into folders by category. Escalation tickets involve specific orders and customer information and need a tighter access scope. The official documentation states that files and folders inside a knowledge base share the knowledge base's own permissions by default; after file-level permission is enabled, collaborators can be configured separately for a single file or folder.

## Constraints at the access controls step

Permission determination first checks the individual member permission, then takes the union of department and group permissions, and the final permission is the combination of those results. Individual member permission has higher priority than department and group permission. Knowledge base permission is always the threshold; collection permission cannot bypass knowledge base permission.

After file-level permission is enabled, lists, details and retrieval recall are each authorized against the snapshot. Retrieval recall is filtered by the files the current member can read, and this takes effect only when authorization is performed by current member identity; scenarios where a workflow preselects a knowledge base and does not authorize by member identity do not apply file-level filtering. The system root and the team owner are treated as having all permissions on all files; the team administrator does not bypass file-level permission.

Hypothetical exercise sample: the knowledge base "After-sales FAQ Library" has file-level permission enabled. Member A has knowledge base manage permission, and Member B has knowledge base use permission. The file "July 2024 return script" has Member A as creator, and its collaborator list is Member A (administrator) and Member B (read permission). Member C is a team administrator and is not on that file's collaborator list. Pending request: Member C applies to delete the file "July 2024 return script". Per the documentation, deletion is limited to the creator, and the team administrator does not bypass file-level permission, so this request does not satisfy the deletion condition at the permission layer.

## Configuration and implementation checks

| Configuration item | Hypothetical trial starting value | Verification method |
| --- | --- | --- |
| Knowledge base file-level permission switch | Enabled | Confirm the enabled notice and the close entry on the knowledge base detail page |
| File collaborator list | Member A administrator, Member B read permission | Compare the submitted list against whether the creator is included, item by item, in the permission dialog |
| Member C team role | Team administrator | Check the actual role on the team permission page |
| File creator | Member A | Confirm the creator field in the file list or detail |
| Retrieval authorization entry | Authorized by current member identity | Check whether the workflow knowledge base search node authorizes by member identity |

Reason for the starting value: the sample needs to cover four conditions at once — the knowledge base threshold, file-level permission, the creator-only deletion restriction, and the team administrator not bypassing. Enabling the switch and keeping a minimal collaborator list serves that purpose. What to compare against: compare Member C's actual role with the file collaborator list, confirm Member C is not on the list, and confirm the team administrator does not bypass file-level permission.

## Three common errors

1. Treating retrieval relevance or file classification as access authorization. Retrieval settings do not carry permission isolation, and file classification and tags do not equal access authorization. The check input is Member C's account and a search term; compare whether the retrieval result includes that file, and observe whether an unauthorized recall appears.

2. Treating the team administrator role as able to bypass file-level permission. The documentation states clearly that the team administrator does not bypass file-level permission. The check input is Member C's team role and the file collaborator list; compare whether the delete operation is allowed, and observe whether a non-creator deletion succeeds.

3. Treating closing the switch as a reversible operation. Closing deletes all collaborator configurations for all files and folders under that knowledge base and cannot be rolled back. The check input is the close operation and the second confirmation; compare the collaborator list before and after closing, and observe whether the configuration is cleared.

## How to verify the setup

- Verification one: using the sample text, Member C applies to delete "July 2024 return script". The input is Member C's account, the team administrator role, and a file collaborator list that does not include Member C. Compare the deletion permission requirement with the creator field. The condition is met when the delete operation is rejected or not executable and the file creator remains Member A.

- Verification two: using the sample text, Member B views the file with read permission. The input is Member B's account, file read permission, and knowledge base use permission. Compare list and detail visibility. The condition is met when Member B can view the file content and the modify-file-information operation is not executable.

- Verification three: using the sample text, Member A transfers ownership of the file to Member B. The input is Member A's creator identity and Member B's same-team identity. Compare the transfer permission with the creator field after transfer. The condition is met when the transfer operation is executable, the creator becomes Member B after transfer, and Member A no longer holds creator identity for that file. All of the above are paper checks of expectations and were not actually executed.
