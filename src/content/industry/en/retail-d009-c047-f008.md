# Marketplace returns: workflow routing for operations handover

## What the documents look like

Marketplace refund and return handling runs continuously per order. This differs from after-sales work concentrated around a single livestream, where a refund request may connect to one broadcast commitment. In this category a refund request does not necessarily attach to a single livestream promise, so routing decisions cannot rely on a broadcast record as the default anchor.

Daily materials include refund applications, return logistics waybills, quality inspection photos, and refund approvals. These arrive from the platform after-sales backend, customer service chat, WMS receiving, and payment refund records. Data updates per order and per day. Three consequences shape workflow routing. First, materials sit in several systems, so routing must state which node collects or receives each material type. Second, refund amount approval and responsibility judgment are business decisions, and neither retrieval nor form collection replaces them. Third, handover occurs among customer service, after-sales specialists, and warehouse inspection staff, so authorization status has to travel together with the materials.

## Constraints at the workflow routing step

A Form Input node belongs to the user interaction nodes. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and after the user completes the interaction the workflow continues downward. The node collects required form information and passes it to later nodes. A User Selection node also belongs to the user interaction nodes, enters the interaction state when triggered, records workflow state, and after the user makes a choice executes the corresponding "yes" branch. Branch connections require verification one by one. The interaction state is recorded by the interaction nodes; no separate global state-recording switch applies.

Collected information must be explicitly passed to subsequent retrieval, judgment, or interface nodes, and outputs are compared against inputs item by item. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval can return candidate materials. Retrieval itself does not constitute authorization, and a similarity score does not carry permission or entity filtering. Libraries using different vector models cannot be associated together; identifiers are checked first, non-matching items are excluded, and actual observations are recorded.

Hypothetical paper exercise sample. Material text: "Refund application A-01, order number H-2024-0701, applicant Zhang, application date 1 July 2024, refund amount 199, return waybill number SF-0001, three quality inspection photos, status is pending review." Proposed handover request: "Change the refund approval status of A-01 to approved and synchronize it to the payment refund records." This request involves approval and external synchronization. The material shows only pending review, and the authorization boundary is not stated.

## Configuration and implementation checks

| Configuration item | Use on this page | Basis or verification method |
| --- | --- | --- |
| Form Input node | Collect required refund application fields | Enters interaction state when triggered; passes information to later nodes after submission |
| User Selection node | Offer a choice on responsibility judgment or approval branching | Executes the "yes" branch after a choice; verify connections one by one |
| Interaction state check | Confirm the conversation enters the interaction state and is recorded | Behavior of interaction nodes; no separate global switch |
| Output receiving check | Pass form information to retrieval or judgment nodes | Compare outputs against inputs item by item |
| External action division | Order writes and status synchronization | Requires a separate business interface or later process |
| Retrieval scope check | Confirm materials sit in an accessible target scope | Check identifiers, exclude non-matching items, record observations |

The hypothetical trial starting point for this page is three candidate materials returned by retrieval, compared against a manually checked material list. This value is a hypothetical exercise starting point for this page, not an official default.

## Three common errors

1. Treating a pending review status as approved. In the sample, A-01 has status pending review. If a draft sentence states "approved," the input and the material status do not agree, and the statement is unsupported.
2. Treating a retrieval hit as authorized execution. Retrieval returning candidate material A-01 shows only that the material can be found within the target scope. It does not support writing to the payment refund records.
3. Treating form collection as business approval. The Form Input node collects required information and passes it to later nodes. Approval and synchronization still require downstream implementation.

Corresponding checks:

1. Input the sample material text and the draft sentence, compare the status field values, and treat the condition as met only when the two agree.
2. Input the retrieval result and the authorization scope list, compare whether the material falls within the authorized scope, and treat the condition as met only when authorization is explicitly stated.
3. Input the form output and the downstream node input, compare whether fields correspond item by item, and treat the condition as met only when downstream implementation exists.

## How to verify the setup

- Verification one. Input the material text "status is pending review" and the draft sentence "change to approved." Compare the status field. The condition is met only when the material states approved; otherwise record the result as unsupported.

- Verification two. Input the A-01 candidate material returned by retrieval and the authorization scope. Compare whether approval authority is stated. The condition is met only when it is stated; otherwise record an evidence gap.

- Verification three. Input the output after form submission and the input of the later judgment node. Compare whether fields correspond item by item. The condition is met only when the correspondence is explicit.

An empty-result handoff can be checked against an explicit paper input of [] to review downstream design. This page does not claim that a fictional rule retrieval necessarily returns []. Libraries using different vector models cannot be associated together; check identifiers first, exclude non-matching items, and do not run cross-model retrieval to compare missed recall.
