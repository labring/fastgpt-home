# Marketplace returns: interactive forms for operations handover

## What the documents look like

Platform refunds and returns arise order by order, and most cases do not attach to a promise made in a single livestream session. Each refund request, return waybill, quality-inspection photo and refund approval forms an independent material chain. The platform after-sales backend, customer-service chat, WMS receiving records and payment refund records supply different fields, and the materials are aligned through the order number and the return-item number. Updates occur per order or per day. This page does not derive batch synchronization, full synchronization, real-time or transaction-triggered mechanisms from that frequency.

The Form Input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution waits until the user completes the interaction. After the user submits the required information, the node collects the entered values and passes them to later nodes. The User Selection node also enters an interaction state when triggered and executes a branch according to the user's choice. Neither node carries a business database function, and neither performs permission determination.

## Constraints at the interactive forms step

A form collects values. It does not grant authorization. When fields such as refund amount, responsibility determination and return-item status are filled in, that only means someone submitted those values. Business approval, database writes and external-system synchronization require later nodes or external systems. During an operations handover, the authorization state of the materials must be verified separately. A retrieval hit or a form submission does not constitute an executed authorization.

Hypothetical paper exercise. Material text: the refund request record for platform order A-0001 states "refund request submitted, pending review"; the return waybill for the same order states "returned item signed for, signature date 10 March 2024"; the quality-inspection photo note reads "appearance intact, function pending inspection." Proposed handover request: "Mark the refund approval status of order A-0001 as approved, and notify the warehouse to release the goods."

In this sample, the refund request is pending review, the return waybill only shows signature, and the quality-inspection photo gives no functional conclusion. None of the three states that approval was granted. The phrase "mark as approved" conflicts with the material state, and "notify the warehouse to release the goods" is an external-system action whose executability this page does not judge.

## Configuration and implementation checks

| Configuration item | Relevant setting or check on this page | Relation to the sample |
| --- | --- | --- |
| Form Input node | List the fields indispensable to this task and mark them required | Order number, return-item number, refund amount, responsibility determination |
| User Selection node | Configure the choices and branch directions | Used for the "enter manual review" branch |
| Interaction state | After triggering, the workflow state is recorded and execution waits | No downward execution before submission |
| Required-field gap check | Test the missing-field behavior and the completed behavior separately | Observe whether execution continues when refund amount is absent |
| Downstream division of work | Field validation, approval and write-back are implemented by external systems or later nodes | In the sample, approval status is not decided by the form node |
| Hypothetical starting point for this exercise | Set "refund amount" as required, because this field determines the approval branch; compare against a non-required setting and observe the behavioral difference | Paper hypothesis only, not an official default value |

## Three common errors

1. Treating form submission as completed authorization. In the sample the refund request is pending review. If the submission action is mapped directly to "approval granted," the input and the state do not match. The comparison is between the material text and the proposed marked value, and the observable result is that the two disagree.
2. Treating the User Selection node as a personnel directory or business-data selector. This node only executes a branch according to the user's choice. The "enter manual review" branch in the sample queries no personnel or permission data.
3. Treating a retrieval hit as permission or entity isolation. Semantic recall and relevance scores do not perform permission filtering. Retrieving the materials of order A-0001 in the sample does not mean the current operator is authorized to approve that order.

## How to verify the setup

1. Input the three material texts and the proposed handover request from the sample, and compare "refund request submitted, pending review" with "mark as approved." If the two take mutually exclusive values on the same field, judge the request unsupported and preserve the evidence gap.
2. Input the required-field set for order A-0001 and remove the refund amount one field at a time. Observe whether the form stays in the interaction state and does not execute downward; after the field is completed, observe whether execution continues. The condition is satisfied when a missing field prevents submission and a completed field permits submission.
3. Input an explicit paper empty result [] and check whether the downstream branch design distinguishes an empty result from a non-empty result. Do not claim that a fictional rule retrieval necessarily returns []. Record only the branch direction actually observed.
