# Complaints and official replies: workflow routing for operations handover

## What the documents look like

Complaints and official replies are directed at a platform or a regulatory authority. The material therefore has to carry formal evidence and remediation wording rather than the lighter records used in repair or reshipment after-sales work. The main sources are the 12315 platform, platform complaint centers, customer service chat, and the order system. The documents handled day to day are complaint tickets, regulatory inquiry letters, order evidence, and remediation reports. Updates are irregular and case by case; this page does not derive batch synchronization or transaction-triggered mechanisms from that frequency.

For operations handover, the important consequence is that the authorization state of a material or an action matters more than the speed of the flow. A complaint ticket, an inquiry letter, order evidence, and a remediation report can each be at a different stage: drafted, pending review, submitted, or answered. A handover request that collapses these stages into one status label loses the distinction the receiving operator needs.

## Constraints at the workflow routing step

The Form Input node is a user interaction node. When it is triggered, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. Once the user fills the required information and submits, the node collects the submitted form information and passes it to subsequent nodes. The User Selection node is also a user interaction node. When triggered, the conversation enters an interaction state and the workflow state is recorded; when the user makes a selection, the node evaluates that selection and executes the "yes" branch.

Both node types perform information collection and branch judgment only. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval and semantic recall do not constitute authorization, and a similarity setting does not exclude unrelated businesses or unauthorized records. The interaction state is produced by node behavior; there is no separate global state-recording switch.

Hypothetical paper exercise: a shop receives a regulatory inquiry letter. The supplied text reads: "Within five working days of receipt of this letter, submit a written explanation and evidentiary materials concerning the return and exchange handling of order A-2024-0317." It is signed by a market supervision office and dated 20 March 2024. A customer service supervisor drafts a handover request: "Mark this ticket as answered and backfill the remediation report into the order evidence directory." The item to be judged is whether the "answered" status in that request is supported by submitted evidence, and whether the backfill action is an operation this workflow can carry out directly.

## Configuration and implementation checks

| Configuration or check item | Hypothetical starting point for this exercise | How to check |
| --- | --- | --- |
| Form Input required fields | Ticket number, issuing authority, reply deadline | Compare each field value against the inquiry letter text item by item |
| User Selection branch | The "yes" branch points to manual review | Verify the branch connection and the following node one by one |
| Interaction state check | The node enters an interaction state after triggering | Observe the hidden dialog box and the recorded state; no separate switch is set |
| Output handover check | Collected information passes to a later judgment node | Compare output fields against input fields item by item |
| External operation division | Order writes, document backfill, external synchronization | Confirm whether a separate business interface or later process exists |
| Retrieval scope check | Target retrieval scope with access rights | When missing, record the evidence gap; do not run cross-model retrieval |

The values in the table are starting points for this hypothetical exercise, used for comparison against the inquiry letter text and actual node output. They are not official defaults.

## Three common errors

1. Treating form submission as completed authorization. In the exercise, the drafted sentence marks the ticket as answered, while the inquiry letter only requires a written explanation to be submitted. The submission has not occurred, so the mark lacks supporting evidence.
2. Treating a retrieval hit as a permission filter. A similarity score does not carry entity or permission isolation. Retrieving order evidence does not mean that record has been authorized for handover.
3. Treating the interaction state as a global snapshot guarantee. The recorded state is behavior of the interaction node. It does not guarantee a submission count or automatic judgment, and backfill still requires downstream implementation.

Corresponding checks: first, input the drafted sentence and the inquiry letter text, compare whether "answered" has a submission record, and treat the status as not established when no submission exists. Second, input the retrieval result and the authorization list, compare whether the record identifier falls within the authorized scope, and exclude records outside it. Third, input the node output and the following node input, compare whether fields are carried over item by item, and record a gap when a field is missing.

## How to verify the setup

- Verification one: input the inquiry letter text and the drafted sentence, compare the reply deadline field against the "answered" status. The mark is satisfied only when submission evidence exists and the deadline has not passed; otherwise it remains pending verification.

- Verification two: input the User Selection branch configuration, compare the connection target of the "yes" branch. The branch counts as configured only when it connects to the manual review node and each item passes verification.

- Verification three: input a paper empty result [] and the downstream design, compare whether the downstream has a path for accepting an empty result. When that path is undefined, record it as unsupported; do not claim retrieval necessarily returns empty. All of the above are paper checks; no actual submission or backfill was executed.
