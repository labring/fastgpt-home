# Complaints and official replies: access controls for operations handover

## What the documents look like

Complaint and regulatory-reply work faces a platform or a regulator, so the materials carry formal external weight. The main sources are the 12315 platform, platform complaint centers, customer-service chat, and the order system. Day-to-day documents include complaint tickets, regulatory inquiry letters, order evidence, and rectification reports. The people involved are customer-service supervisors, legal and compliance staff, and store owners. Errors can lead to administrative investigation, platform penalties, and brand exposure. Updates are irregular and handled case by case.

For operations handover, the question is which materials, actions, and requests sit at which authorization state. A ticket records the complainant's demand and a deadline. An inquiry letter records what the regulator requires and the reply deadline. A rectification report records the corrective measures and submission status. Retrieval or a form that collects values does not perform authorization. A pending request is not an approval, and an offered option is not execution.

## Constraints at the access controls step

FastGPT permissions combine member permissions with department and group permissions. Member permissions have the highest priority; department and group permissions are taken as a union and rank below member permissions. Resources include the team, applications, knowledge bases, and files or folders (collections). A knowledge base has three levels: usable, editable, and manageable. A collection has read permission, write permission, and administrator; deletion is limited to the creator. File-level permission is a commercial-edition feature. In the closed state, collection readability matches the knowledge base. In the open state, each file or folder generates a permission snapshot, and lists, details, and retrieval recall are each authenticated against that snapshot. Knowledge base permission always remains the threshold; collection permission cannot bypass it.

Retrieval recall filters by the files the current member can read, and this applies only when authentication is performed by the current member identity. A workflow that preselects a knowledge base without member-identity authentication does not apply file-level filtering. A relevance score does not carry permission or entity-isolation duties, and a retrieval setting does not replace authorization. A team administrator does not bypass file-level permission; system root and the team owner are treated as holding full permission over all files.

Hypothetical drill sample: a store customer-service supervisor plans to hand over edit permission for a draft reply to a regulatory inquiry letter to a legal and compliance colleague. The material text reads: "Inquiry letter number JB-2024-0417 requires submission of a rectification report by 10 May 2024. The current draft is stored in the knowledge base 'Regulatory Replies' under the file '0417 rectification report draft'. The creator is customer-service supervisor A. The knowledge base has file-level permission enabled, and A holds administrator permission on this file." Draft sentence to be judged: "Legal and compliance colleague B can edit the draft and submit the rectification report." Check points: whether B holds write permission on this file in the collaborator list; submission of a rectification report is an external business action that needs separate confirmation of authorization and an executing system, and edit permission does not include submission.

## Configuration and implementation checks

| Configuration or check item | Setting applicable to this page | Explanation and boundary |
| --- | --- | --- |
| Knowledge base file-level permission switch | Open state or closed state | When open, collections are authenticated item by item against snapshots; when closed, collections inherit knowledge base permission |
| File collaborator role | Read permission, write permission, administrator | The creator cannot be granted or modified through collaborator configuration, and the submitted list must include the current creator |
| Collaborator configuration semantics | Full overwrite | The submitted list is the final result, and one overwrite can remove the creator record |
| Retrieval recall authentication condition | Authenticated by current member identity | A preselected knowledge base without member-identity authentication does not apply file-level filtering |
| Handover check scope | Target file and knowledge base read permission | Collection permission cannot bypass knowledge base permission, so both must be checked |
| External submission action | Requires a separate system implementation | Edit permission does not produce submission, approval, or synchronization effects |

Hypothetical test starting value for this page: treat "B holds write permission" as the value to be checked, compared against the actual record in the collaborator list. This starting value is chosen because the draft sentence in the sample claims B can edit, and the list record is what decides it; it is not an official default.

## Three common errors

1. Treating retrieval relevance as permission filtering. The input is a knowledge base search test, the comparison is between the recalled results and the list of files the current member can read, and the observable result is whether a file beyond the member's permission appears. A relevance score does not carry permission or entity-isolation duties.
2. Treating edit permission as equivalent to external submission. The input is the draft sentence "B can edit the draft and submit the rectification report", the comparison is between file write permission and the authorization required for the submission action, and the observable result is whether submission has independent authorization and an executing system. Edit permission does not include submission.
3. Omitting the creator when submitting a collaborator list by full overwrite. The input is a collaborator list that does not contain creator A, the comparison is between the list and the current creator record, and the observable result is whether the submission is rejected. The creator cannot be granted or modified through collaborator configuration.

## How to verify the setup

1. Input the sample material text and the draft sentence, compare B's actual role in the collaborator list against the claim in the draft sentence, and observe whether the list states that B holds write permission. If the list does not state it, the claim is not supported and the evidence gap must be recorded.
2. Input the two records of knowledge base read permission and file write permission, compare whether B holds both at the same time, and observe whether the condition of "knowledge base threshold plus file permission" is met. If either is missing, the access condition is not met.
3. Input the phrase "submit the rectification report" from the draft sentence, compare that action against the authorization scope of file edit permission, and observe whether an independent authorization and executing-system record exists. If it is not stated, the submission action remains to be verified and cannot be inferred from edit permission.

An empty-result continuation can use the explicit paper input [] to check the downstream design; it cannot claim that a fictional rule search necessarily returns []. Knowledge bases across different vector models cannot be associated together; first check identifiers and exclude those that do not match, record the actual observation, and do not run a cross-model retrieval to compare missed recall.
