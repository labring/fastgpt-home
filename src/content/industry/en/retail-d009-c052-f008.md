# Pinduoduo seller campaigns: workflow routing for operations handover

## What the documents look like

Pinduoduo low-price campaign store operations revolve around low-price resource slots, campaign inventory, and refund-rate fluctuation. The working materials are campaign registration forms, product cost calculation sheets, after-sales refund documents, and platform in-site messages. Campaigns proceed by session, and the materials update daily and per campaign. Workflow routing for operations handover deals with these materials across campaign operators, supply-chain procurement, and the merchant: who submitted, who confirmed, and which material still sits at a review-pending state must be traceable at the node level.

Handover materials carry different states at different moments. A registration form may be submitted and awaiting review while a cost calculation sheet for the same campaign session already shows a completed margin estimate. The routing layer must reflect those states as they are recorded, not as an operator expects them to become.

## Constraints at the workflow routing step

The form input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution waits until the user completes the interaction. The node collects required information and, after submission, passes the collected values to downstream nodes. The user selection node is also a user-interaction node. When the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. Branch connections must be verified one by one. Recording state is behavior of the interaction nodes; no separate global state-recording switch is documented.

Retrieval and similarity scores do not perform authorization or entity isolation. Libraries built on different vector models cannot be associated together; the identifier must be checked first and non-matching libraries excluded, without running cross-model retrieval to compare missed recalls. An empty-reference output can be checked against downstream design using an explicit paper input. Optional paths shown in an overall document flow diagram do not mean every request executes all paths: image retrieval requires a corresponding image input and model capability, and reranking requires a model and must be enabled by its setting. Order writes, document backfill, and external status synchronization require a separate business interface or a later flow; the form itself only collects values.

Hypothetical paper exercise sample: the source material reads, "Campaign registration form A-0715, subject is a campaign operations group, object is the July 15 low-price resource slot, status is submitted and pending review; product cost calculation sheet C-0715 records that the campaign-price margin estimate for this session is complete, date range July 15 to July 17." The draft sentence to be judged is, "A-0715 has been approved and inventory handover may proceed." The source shows only pending review and states no approval record, so the draft sentence is not supported.

## Configuration and implementation checks

| Configuration item | Documented setting or implementation check | Relation to this page's sample |
| --- | --- | --- |
| Form input node | Triggers into interaction state, collects required information, passes it to downstream nodes after submission | Carries the submitted values of A-0715 |
| User selection node | Executes the "yes" branch after the user's choice; verify branch connections one by one | Checks the approval and rejection branch connections |
| Interaction state check | Recording state is behavior of the interaction nodes; no separate global state-recording switch | Checks whether A-0715 is in interaction or submitted |
| Output handoff check | Pass collected information explicitly to downstream retrieval, judgment, or interface nodes; compare each output against its input | Compares submitted values with values received downstream |
| External operation separation | Order writes, document backfill, and external status synchronization require a separate business interface or later flow | Inventory handover does not sit inside the form node |
| Numeric starting point | This hypothetical exercise takes 3 working days as the review observation starting point, chosen as a pre-campaign check window, compared against the date range stated in the material | Serves only as this exercise's comparison baseline |

## Three common errors

1. Treating pending review as approval. The A-0715 source states status is submitted and pending review, while the draft sentence says "has been approved." The input is the registration form status field, the comparison object is an approval record, and the observable result is that no approval record is found, so the draft sentence is not supported.
2. Treating a retrieval hit as authorization. A similarity score does not constitute a permission or entity filter. The input is the returned retrieval list, the comparison object is an authorization record, and the observable result is that the list contains no authorization field, so retrieval cannot substitute for authorization.
3. Treating form collection as business execution. Form input only collects and passes values. The input is the submitted form value, the comparison object is a completed inventory handover record, and the observable result is that no business interface is connected, so handover has not executed.

## How to verify the setup

1. Take the sample source "A-0715 status is submitted and pending review" as input, compare the draft sentence "has been approved," and observe that the two status fields do not match. When this condition holds, record that the draft sentence is not supported and note the approval evidence gap.
2. Take the sample source "C-0715 date range July 15 to July 17" as input, compare the 3-working-day review observation starting point, and observe that the start and end dates fall inside the stated range. When this condition holds, record that the range is valid, without inferring a supply deadline.
3. Take an explicit paper input of an empty list as input, compare the downstream node handoff design, and observe that the downstream has a defined handling path for empty input. When this condition holds, record that empty-reference handling is in place, without claiming that a fictional rule retrieval necessarily returns an empty list.
