# Pinduoduo seller campaigns: interactive forms for operations handover

## What the documents look like

Low-price campaign operations on Pinduoduo revolve around low-price resource slots, campaign inventory, and refund-rate fluctuation. The working documents for this category include campaign registration forms, product cost calculation sheets, after-sales refund orders, and platform in-site messages. These materials update daily or per campaign.

For handover work, each document carries a state that matters more than its existence. A registration form may sit in draft or submitted state. A refund order may sit in pending review or refunded state. An in-site message may be a notification only. The form input node collects the values a user fills in and passes them to later nodes after submission; it does not carry its own business database function. The user selection node executes a branch according to the user's choice. An interaction state records the workflow state and waits for the interaction to complete before execution continues downward. Retrieval or form submission does not by itself constitute authorization. Business approval, write-back, and bulk operations require an external system or later nodes.

## Constraints at the interactive forms step

In a handover scenario, pending review does not demonstrate the absence of operating permission. Signing, reaching cooperation, and contract effectiveness are three distinct facts. The form input node only collects field values; field validation, business approval, and write-back are implemented as needed in an external system or later nodes. The user selection node is not written as a personnel directory or a business data selector. Interaction waiting, state recording, and dialog hiding are interpreted per the documents, without inventing corresponding control switches, submission counts, automatic judgment, or snapshot guarantees. Semantic recall and relevance do not handle permission or entity isolation; retrieval is not authorization. Libraries across different vector models cannot be associated together. Only verify identifiers, exclude non-matching items, and record actual observations. The optional paths listed in the overall workflow diagram do not mean every request executes all of them.

Hypothetical paper exercise sample. The material text is: "Campaign registration form (number A-0715), submission date 2025-07-15, product summer short-sleeve shirt, campaign price 19.9 yuan, inventory 500 units, status: draft"; "Platform in-site message (2025-07-16) notifies that this product's campaign registration is pending review, and does not state a review result"; "After-sales refund order (number R-0720) submitted 2025-07-20, status is pending review." The handover request to be judged is: "Transfer the operating permission of A-0715 to the procurement group, because the registration form has been submitted and the in-site message notifies pending review." The comparison points are: the registration form's status field is draft, which conflicts with "submitted"; the in-site message only states pending review and does not state approval; the refund order's pending review does not demonstrate the absence of operating permission. This request is not supported, and permission transfer needs a separate system implementation.

The hypothetical starting point for this exercise is to treat the registration form's status field as a required check item. The reason for this choice is that the sample status is draft while the request claims submitted, and the comparison object is the pending-review state stated in the in-site message. This starting point is a paper hypothesis, not an official default value.

## Three common errors

1. Treating pending review as approval. The sample in-site message only states pending review and does not state a review result. If permission transfer is judged possible on this basis, the input is the in-site message text, the comparison point is "pending review" against "approval" as two distinct facts, and the observable result is that the request is not supported.

2. Treating draft as submitted. The sample registration form's status field is draft while the request claims submitted. The input is the registration form text, the comparison point is the value of the status field, and the observable result is that the same field holds mutually exclusive values, forming a conflict.

3. Treating retrieval or form submission as authorization. In the sample the form only collects field values and does not execute approval. The input is the form submission action, the comparison point is whether an external approval record exists, and the observable result is that the authorization state is unknown.

## How to verify the setup

1. Against the sample registration form text, input the status field value "draft" and the request sentence "submitted," and compare the values of the same field. The condition is met only when the two agree; currently they conflict, so the gap must be recorded.

2. Against the sample in-site message text, input "pending review" and the request sentence "permission transfer," and compare whether a review result and effective scope are stated. The condition is met only when approval and an effective scope are stated; currently the request is not supported.

3. Against the sample refund order text, input "pending review" and the inference "lacks operating permission," and compare whether a permission state is stated. The condition is met only when a permission field is stated; currently this is pending verification, and it is not called a negation or a conflict.

If a downstream design needs to accept an empty result, a clearly stated paper input empty list can be used to check the downstream design. Do not claim that a fictional rule retrieval necessarily returns an empty list. Retrieval checks should state observations and failure branches, without guaranteeing a first hit, full recall, or that an unrelated query must be empty.
