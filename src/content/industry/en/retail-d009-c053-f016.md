# Channel receivables: interactive forms for operations handover

## What the documents look like

Channel receivables collection happens after credit sales, so the working data centres on credit limits and cash recovery. The main sources are the finance system, bank receipts, distributor orders and sales contracts. The documents handled day to day are the receivables ageing table, the demand letter, the credit agreement and the shipping freeze notice. Brand finance staff, sales back-office staff and distributor owners work on these materials together. Errors in this area produce bad debt, channel supply interruption and damage to sales targets.

This page covers only one slice of that work: interactive forms inside operations permission and handover management. The question is which materials, actions and requests sit in which authorization state at the moment of handover. A form collects values. Business authorization is a separate fact. A retrieval result and a form submission do not by themselves authorize execution.

## Constraints at the interactive forms step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution waits for the user to complete the interaction. After the user fills the required information and submits, the node collects the submitted form information and passes it to later nodes. The node collects information; it does not carry business database functions of its own.

The User Selection node is also a user interaction node. It enters the interaction state, records the workflow state and waits. When the user makes a choice, the node evaluates that choice and executes the branch. It is not a personnel directory and not a business data selector. Field validation, business approval, write-back and batch operations are implemented as needed in external systems or later nodes.

In a handover setting, whether a material is valid, whether an action is authorized and whether a request has been approved must each be checked outside the form. Completing the interaction only shows that the filling action ended.

Hypothetical paper exercise sample. The material text reads: "Credit agreement number HX-2024-031, subject is East China distributor A, credit limit valid until 30 June 2024; the ageing table shows this distributor is 45 days overdue, amount 820,000 yuan; the shipping freeze notice draft is marked 'pending review by the finance lead' and has no signature date." The proposed handover request reads: "Please move distributor A's overdue orders into the shipping freeze process and notify sales back-office to stop taking orders." The point to decide: whether this request can be treated as an authorized freeze execution.

## Configuration and implementation checks

The values below are starting points for this paper exercise. Each is chosen for a stated reason and compared against a named counterpart. None is an official default.

| Configuration item | Hypothetical starting point or check method | Reason and comparison method |
| --- | --- | --- |
| Form Input node | Collect the handover request text and material number | Submitted values pass to later nodes; no write to the business database |
| Required-field check | Material number, subject, status field | Test whether a missing item blocks submission, compared with the completed case |
| User Selection node | Branches: "continue handover" / "return for supplement" | The node executes the branch; it does not read a personnel directory |
| Interaction state wait | State recorded and waiting after trigger | Execution continues after interaction completes; no submission-count cap is set |
| Authorization state check | Compare against the freeze notice signature state | A draft marked "pending review" is not approved execution |
| Downstream division of work | Approval and write-back implemented in external systems | The node does not carry business approval or database writes |

## Three common errors

1. Treating form submission as completed authorization. In the sample, the freeze notice is a draft marked "pending review by the finance lead." Submitting the handover request completes the filling action only. No signature authorization exists, so the freeze cannot be executed on this basis.

2. Treating a User Selection branch as a personnel or permission directory. Choosing "continue handover" decides the workflow direction only. It does not show that the operator holds freeze permission.

3. Treating a retrieval result as authorization or as an entity-isolation basis. A relevance score does not carry permission filtering. Retrieving a record for a distributor does not mean that record has been cleared for operation.

Corresponding checks. First, input the sample material text and the proposed handover request, compare the freeze notice status field "pending review" against "signed," and observe whether the item still shows as pending verification. Second, input the selection branch "continue handover," compare the node output branch against the external approval record, and observe whether signature evidence is absent. Third, input a retrieval query containing distributor A, compare the returned records against the authorized-scope list, and observe whether any unauthorized record has been included.

## How to verify the setup

- Verification one: input the sample material text and the proposed handover request, compare the freeze notice status "pending review by the finance lead" against the signature condition required to execute a freeze. The authorization condition is met only when an explicit signature record is present. Otherwise record the evidence gap.

- Verification two: input a submission in which the required field "material number" is missing, compare the missing-field behaviour against the completed case, and observe whether the missing item blocks submission and whether the completed case continues to later nodes. Do not presuppose a submission count or an automatic judgement.

- Verification three: input an empty-result continuation scenario, using the paper input [] to check the downstream design, and observe whether the downstream handles it as an empty set. Do not claim that a retrieval rule necessarily returns empty.

All of the above are paper checks. No deployment or live test has taken place. Retrieval and relevance do not carry permission or entity isolation. Libraries across different vector models cannot be associated together; check the identifier and exclude those that do not match.
