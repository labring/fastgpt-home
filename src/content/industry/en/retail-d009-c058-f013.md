# Fresh-food supplier claims: access controls for operations handover

## What the documents look like

Fresh-food supplier claims pursue quality responsibility for goods on arrival. They do not handle natural in-store shrinkage. The working materials come from quality inspection systems, WMS acceptance, supplier contracts and financial reconciliation. Day-to-day documents include quality exception forms, photo evidence, deduction notices and claim reconciliation statements. These materials update per batch and per month.

For operations handover, the practical difficulty is that one arrival batch carries its inspection conclusion, deduction amount and reconciliation status across separate documents. A handover request that relies only on retrieval output or on values typed into a form can mistake "can view" for "can execute a deduction" or "can send a claim notice externally." Knowledge-base file-level permissions and team resource permissions constrain different things: the first governs material visibility, the second governs the scope of operations. Neither substitutes for the other.

## Constraints at the access controls step

Knowledge-base permission is always the threshold. Collection permission cannot bypass knowledge-base permission. When file-level permission is enabled, lists, details and retrieval recall are all authorized item by item against a snapshot. When it is not enabled, collection readability matches the knowledge base exactly and the system queries no collection permission records. A team administrator does not bypass file-level permission. The team owner and system root are treated as holding all file permissions. File-level filtering in retrieval recall applies only when authorization runs against the current member identity; a scenario that preselects a knowledge base without member-identity authorization performs no file-level filtering. A relevance score does not perform permission or entity filtering, and retrieval behavior on its own does not constitute authorization.

Hypothetical drill sample: a fresh-food procurement team's knowledge base has file-level permission enabled. The source text reads: "Quality exception form QA-0417 records: batch B-0417 arrived 17 April 2026; inspection judged the leaf-wilting ratio as exceeding the standard; this batch's payment is temporarily withheld pending supplier confirmation. Deduction notice DK-0417 status is pending review. Claim reconciliation statement SC-0417 status: not generated." The handover request to be judged is: "Transfer QA-0417 and DK-0417 together to the supplier business group, and authorize that group to send the deduction notice directly." In this request, DK-0417 is in pending-review status. Pending review does not demonstrate that operational permission is absent, and it does not equal approved execution. Sending a deduction notice is an external business action that needs a separately connected system implementation; it cannot be replaced by file collaborator configuration or by retrieval visibility.

## Configuration and implementation checks

The following items center on the sample above and list only documented settings or implementation checks. Where a value is needed, it is stated as a starting point for this hypothetical trial.

| Configuration or check item | Hypothetical starting point | Reason and comparison method |
| --- | --- | --- |
| Knowledge-base file-level permission switch | Enabled | The sample requires per-file authorization; compared with the disabled state, where collection permission records are not queried |
| QA-0417 collaborator scope | Quality inspection group read permission, procurement group read permission | Handover requires both groups to view; compare visibility against an account with no read permission |
| DK-0417 collaborator scope | Procurement group read permission, excluding the supplier business group | A pending-review document should not gain scope automatically from a handover request; compare operation results against an authorized account |
| Creator retention | Submitted collaborator list includes the current creator | Under full-overwrite semantics, omitting the creator is rejected; compare the submission result against a list that includes the creator |
| Retrieval authorization mode | Authorized against current member identity | File-level filtering applies only under this condition; compare recall scope against a scenario that preselects a knowledge base without identity authorization |
| External send action | Marked as requiring separate system implementation | Sending a deduction notice is not executable through FastGPT resource permission; compared with configuring collaborators alone, the latter produces no send behavior |

## Three common errors

1. Treating retrieval visibility as deduction execution authority. The input is a procurement-group account retrieving QA-0417 and seeing its content; the comparison object is the pending-review status of DK-0417. Concluding from this that the deduction notice can be sent directly confuses read permission with an external business action. The observable result: retrieval returns content, while the send action has no corresponding implementation record.

2. Treating pending review as approved within a handover request. The input is DK-0417 with status "pending review"; the comparison object is an explicit value such as "reviewed" or "approved." Judging pending review as executable is a status misreading. The observable result: the status field remains pending review, with no approval record.

3. Assuming configuration survives after the file-level permission switch is turned off. The input is the configured QA-0417 collaborator list; the comparison object is the permission state after the switch is turned off. Turning it off deletes all file collaborator configurations for that knowledge base and restores inheritance, with no rollback. The observable result: the former collaborator list no longer takes effect.

## How to verify the setup

1. Use the hypothetical sample text to check visibility. The input is a procurement-group account and an account without permission each retrieving QA-0417; compare the returned content of the two. The condition is met when the procurement group can see it and the unauthorized account cannot. Retrieval results do not guarantee a first-hit match or full recall; an empty result can be checked against the downstream design using the paper input [].

2. Use the handover request to check status and authorization boundary. The input is "Transfer QA-0417 and DK-0417 together to the supplier business group, and authorize that group to send the deduction notice directly." Compare the "pending review" field of DK-0417 against an "approved" field. The condition is met when the check identifies that pending review does not constitute approval and that the send action requires a separate system implementation. Where no approval record is stated, the conclusion is pending verification.

3. Use collaborator submission to check creator retention. The input is a collaborator list containing the current creator and a list omitting the creator; compare the two submission results. The condition is met when the list containing the creator submits successfully and the list omitting the creator is rejected. This expectation is a paper check and does not claim to have been tested. Knowledge bases on different vector models cannot be associated together; verify identifiers first and exclude non-matching ones rather than running a cross-model retrieval to compare missed recall.
