# Livestream after-sales service: interactive forms for operations handover

## What the documents look like

Livestream after-sales work tends to arrive in a surge after a single broadcast session, and refund requests and reshipment orders arrive together in the same window. The working materials are the livestream order list, refund applications, reshipment orders and script templates. These are recorded across Douyin Shop after-sales, customer service IM, warehouse WMS and logistics tracking, and each system holds its own status values. For an after-sales supervisor handing work to the next shift, the practical difficulty is not locating the materials but stating which authorization state each material, action or request is currently in. Documents update after each session and daily, which means the materials change; the form nodes described here do not perform bulk synchronization or trigger transactions.

## Constraints at the interactive forms step

The Form Input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues downstream only after the user completes the interaction. Once the user fills the required information and submits, the node collects what was entered and passes it to later nodes. The node itself does not include business database functions. The User Selection node is also a user interaction node: it triggers the same interaction state, records workflow state, waits for the user to finish, and then evaluates the user's selection to run the "yes" branch. It does not act as a personnel directory or a business data selector. Field validation, business approval, write-back and bulk operations need to be implemented in an external system or in later nodes. Retrieval and forms do not constitute authorization execution. Whether a handover request is approved is a business fact and cannot be replaced by node interaction.

Hypothetical paper exercise sample. The source material reads: "Refund application A-0312-07 for the 12 March 2025 session, applicant Lin, order number not stated, reason is missed or incorrect reshipment, current status pending review; reshipment order B-0312-11 for the same session, registered by the warehouse exception role, status submitted and awaiting warehouse confirmation; script template T-03 version date 10 March 2025." The draft sentence to be judged reads: "A-0312-07 has been approved by the after-sales supervisor and reshipment may proceed." The source shows only pending review; approval and permission to proceed are not stated, so the draft sentence is not supported and should be recorded as pending verification.

## Configuration and implementation checks

| Configuration item | Type | What this page checks |
| --- | --- | --- |
| Form Input node | Documented node behaviour | Enters interaction state and records workflow state on trigger; passes submitted information to later nodes |
| Required information check | Implementation check | List the subject, object and status fields the handover needs; check each missing item and the downstream result after it is supplied |
| User Selection node | Documented node behaviour | Runs a branch according to the user's selection; does not read a personnel directory or business data |
| Downstream handling split | Implementation check | Field validation, approval, write-back and bulk operations are implemented in an external system or later nodes |
| Retrieval scope check | Manual check action | Check whether the target library is within accessible scope; record the evidence gap when it is not |
| Interaction wait observation | Implementation check | Observe the hidden dialogue box and interaction state; do not assume submission counts or automatic judgement |

The table sets no numeric default values. If a paper exercise needs a starting value, it may state: "the starting value for this hypothetical exercise is three handover fields," because the sample contains subject, object and status categories, and this is compared with the downstream result after the missing-item test.

## Three common errors

1. Treating pending review as approval. In the sample, A-0312-07 has status pending review, while the draft sentence writes that approval has been granted. The input and the comparison object are misaligned, and the observable result is that the status field and the draft sentence do not agree.
2. Treating the User Selection node as a personnel directory. The sample handover request needs a receiving role to be named, but the node only runs a branch according to the selection and provides no personnel data. The observable result is that the node output contains no personnel field.
3. Treating a retrieval result as authorization. In the sample, a refund application is retrieved, but the retrieval action does not change the pending review status. The observable result is that the authorization field remains empty.

## How to verify the setup

1. Input the sample source text and the draft sentence "A-0312-07 has been approved by the after-sales supervisor and reshipment may proceed." Compare the status field "pending review" with "approved." The condition is satisfied only if the source states approval; at present it should be recorded as unsupported.
2. Input the sample's reshipment order B-0312-11 status "submitted and awaiting warehouse confirmation." Compare "submitted" with "confirmation completed." The condition is satisfied only if a warehouse confirmation record appears; at present it is pending verification.
3. Input the paper empty result []. Check whether the downstream design distinguishes an empty result from "no record." The condition is satisfied only if the downstream explicitly handles the empty value and does not generate an authorization conclusion. No claim is made that a fictional rule retrieval necessarily returns [].
