# Livestream violation appeals: access controls for operations handover

## What the documents look like

Livestream violation appeals address a penalty that has already taken effect. The working materials come from the platform violation center, livestream recordings, customer service records, and the product qualification library. Day-to-day handling covers four document types: violation notices, livestream screen recordings, product qualifications, and appeal statements. This category differs from influencer management because the material points to a completed penalty and requires reconstructing the evidence chain and stating appeal grounds. New documents appear irregularly, one batch per violation, so access control and handover focus on material ownership and operation boundaries within a single incident.

FastGPT's permission system combines member permissions with department and group permissions. Member permissions carry the highest priority; department and group permissions are combined as a union. Knowledge base permission is always the threshold, and collection-level permission cannot bypass it. Collection-level permission is a commercial-edition feature and is off by default. In the off state, collection readability matches the knowledge base. When enabled, each file or folder generates a permission snapshot and is checked item by item. Retrieval recall filters by the files the current member can read, and this applies only when authentication runs as the current member identity. Retrieval relevance does not perform permission or entity isolation, and a similarity setting cannot replace collaborator configuration.

A hypothetical paper case is used below for comparison. A store compliance account receives a violation notice whose text reads: "This notice concerns the session on 12 March 2025 from 20:00 to 22:00, the penalized object is product link A, the penalty type is product ban, and the appeal deadline is 19 March 2025." The same batch contains a scan labelled "product qualification file, valid until 30 June 2025" and a recording labelled "session replay of 12 March 2025". The proposed handover request reads: "Move the above three materials into the appeal knowledge base and grant the livestream operations account edit permission on that knowledge base." The authorization scope, material ownership, and operation permissions in this request all remain to be checked. The dates, subjects, and states in the sample serve paper comparison only and do not represent any real penalty or actual authorization.

## Constraints at the access controls step

Violation notices, livestream recordings, product qualifications, and appeal statements typically sit with store compliance, livestream operations, and legal, so materials move across roles. Under the permission system, the final permission is the combination of the member permission check and the union of department and group permissions. A knowledge base administrator can manage collaborators. Collection-level permission requires the knowledge base to be enabled first; while it is off, any write operation configuring a single file's permission is rejected and prompts to enable it first. Enabling materializes permission snapshots for all files and folders synchronously within the request, and the switch is set only after materialization succeeds. Closing the switch deletes all collaborator configurations under that knowledge base and restores inheritance, and this operation cannot be rolled back. Collaborator configuration uses full-overwrite semantics, so the submitted list is the final result, and the submitted list must contain the current creator or it is rejected. The creator cannot be granted or modified through collaborator configuration. A team administrator does not bypass collection-level permission; team-level management permission covers only the team's own resources such as member groups and organizations, while knowledge bases and files are still authenticated by their own collaborator configuration. Team owners and system root are treated as having all permissions on all files.

## Three common errors

1. Treating retrieval relevance as permission filtering. In the hypothetical case, when the livestream operations account searches for "product qualification", the file may be highly relevant to the query. If that account is not listed as a collaborator on the file and collection-level permission is off, retrieval still returns results under knowledge base permission, and similarity cannot be used to infer readability.

2. Treating a pending collaborator request as already authorized. In the hypothetical case, "grant the livestream operations account edit permission" is only a proposed handover request. Before it is submitted and takes effect, that account's actual permission on the appeal knowledge base is still judged by the existing collaborator configuration, and the request content cannot be used to conclude that edit permission is already held.

3. Treating team administrator identity as a collection-level exemption. In the hypothetical case, if an account is a team administrator, the official text states it does not bypass collection-level permission. The account still needs item-by-item checking against the knowledge base and file collaborator configuration, and team-level management identity cannot be used to conclude that all appeal materials are readable.

## How to verify the setup

1. Input the violation notice text from the hypothetical sample and the livestream operations account. Compare the account's actual collaborator role in the appeal knowledge base against the proposed edit permission, and observe whether the account can enter the collaborator configuration entry. If the entry is not visible, the account has not obtained file administrator permission, and the authorization request has not taken effect.

2. Input the product qualification file from the hypothetical sample and the livestream operations account. Compare the collection-level permission switch state against that file's collaborator list, and observe whether the account can see the file in the file list. If the list does not show the file, the account lacks read permission on that file, and retrieval recall will not return that file either.

3. Input the handover request from the hypothetical sample and the store compliance account. Compare the material scope listed in the request against the current file list of the knowledge base, and observe whether the creator remains in the collaborator list after submission. If the submitted list does not contain the creator, the system rejects that configuration, and the original list must be kept while the gap is recorded.

These checks describe what to compare and what to observe. They do not claim that any test, deployment, approval, or authorization has actually occurred, and any field not provided in the documents remains unknown.
