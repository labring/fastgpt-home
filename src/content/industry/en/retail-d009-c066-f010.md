# Short-video affiliate sales: citation tracing for operations handover

## What the documents look like

Short-video affiliate sales distribute products through content that keeps generating impressions and link conversions after publication, without depending on live explanation. The working materials for this category are short-video scripts, attached-product lists, commission plans and violation feedback, updated daily and weekly. Handover management has to keep script versions, product-list entries, commission-plan states and violation-feedback progress aligned with each other.

Four document types carry the evidence this page traces. A script holds a version identifier, a submission state and an attached product. A product list holds the product entry that a script points to. A commission plan holds its own approval state. A violation feedback record holds a processing state. Citation tracing means checking whether a retrieval result or a drafted handover sentence actually matches the state recorded in these documents, rather than treating the retrieval output as an authorization decision.

## Constraints at the citation tracing step

The knowledge-base search node can associate one or more knowledge bases that share the same vector model, and it outputs a citation array whose length can be 0. When nothing is retrieved, the output path still runs through. The citation cap is controlled in tokens, and the minimum relevance setting takes effect only under semantic retrieval or result re-ranking. Retrieval returns candidate content. Authorization decisions, commission-plan activation and product listing states are confirmed by the corresponding business systems, not by the search node.

A relevance score is a similarity measure. It does not act as a category, entity or permission filter, and it does not exclude unrelated businesses or unauthorized records. Retrieval is not authorization. The same-vector-model requirement for associating knowledge bases applies to those knowledge bases; it does not extend to business-registration sites or other external systems.

Hypothetical paper exercise sample. The source text reads: "Creator A's short-video script V3 was submitted for review on 10 March 2025, its attached product is product P, commission plan C was in pending-review state on 12 March 2025, and violation feedback F records a title containing a prohibited term with processing state pending re-check." The draft sentence to be judged reads: "Creator A's short-video script V3 has been authorized to attach product P and settles under commission plan C." Comparing the draft with the source: the script is submitted for review, the commission plan is pending review, and the violation feedback is pending re-check. All three are pending states.

## Configuration and implementation checks

| Configuration or check item | Hypothetical starting point for this exercise | Reason for the choice and comparison object |
| --- | --- | --- |
| Associated knowledge bases | Select the script library and the product-list library whose vector-model identifiers match | Compare against the vector-model identifier of each already-selected knowledge base and exclude non-matching ones |
| Citation cap | Set to a token amount covering one script passage and one list entry | Compare against the actual length of a single script passage and a single list entry |
| Minimum relevance | Keep the default value, unchanged for handover checking | Compare against whether semantic retrieval or re-ranking is enabled; it does not take effect when neither is active |
| Citation content output | Record the array length, which may be 0 | Compare against whether the downstream answer step accepts an empty array |
| Document-version check | Take current script V3 and historical script V2 | Compare against the version identifiers listed in the handover checklist |
| Authorization-state check | Record review, pending-review and pending-re-check states item by item | Compare against the authorized and settled wording in the draft sentence |

## Three common errors

1. Treating retrieval output as an authorization conclusion. The input is the retrieved citation for script V3 and product P; the comparison is between the review state stated in the cited source and the authorized wording in the draft sentence; the observable result is that an authorized conclusion is written even when the two do not match.

2. Treating a pending-review commission plan as already effective. The input is the state field of commission plan C; the comparison is between the pending-review value and the settled value; the observable result is that settlement under plan C is written while the field value has not changed to settled.

3. Treating pending-re-check violation feedback as fully resolved. The input is the processing state of violation feedback F; the comparison is between pending re-check and completed; the observable result is that the violation is written as cleared while the state remains pending re-check.

## How to verify the setup

1. Input the source text for script V3, product P, commission plan C and violation feedback F from the hypothetical sample. Compare the draft sentence against the three state fields. The condition is met when all three states are pending and the draft sentence does not hold. This is a paper check of the comparison, not a record of a completed test.

2. Input the retrieval citation array. Compare the array length against the downstream answer step's design for accepting it. The condition is met when a length of 0 is still handled downstream as an empty citation, and that branch is recorded. A paper input of an empty array `[]` can be used to check the downstream design; this does not assert that a rule-based search will return an empty array.

3. Input script V3 and script V2 as two versions. Compare the version identifier listed in the handover checklist against the version identifier matched in retrieval. The condition is met when the matched identifier agrees with the checklist and the source is traceable, and when a mismatch is recorded as a gap to be confirmed rather than as a resolved fact.

Across these checks, a pending request is not approval, an offered option is not execution, and an unsigned termination is not a completed termination. Where the source document does not state a field, that field remains unknown.
