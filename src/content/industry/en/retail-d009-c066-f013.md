# Short-video affiliate sales: access controls for operations handover

## What the documents look like

Short-video affiliate sales centers on long-term content exposure and product-link conversion, so the work does not depend on live explanation. The main data comes from the selected affiliate alliance, short-video playback data, product transaction data, and platform rules. Daily documents include short-video scripts, product lists for linked carts, commission plans, and violation feedback. During handover these materials are often scattered across different members: content operators maintain scripts, product distribution specialists maintain product lists, and creator business development staff maintain commission plans. Update frequency is daily and weekly.

These characteristics matter for access controls because a handover request can reference a document that is still pending confirmation, while the receiving member's underlying knowledge-base read permission remains unstated. Retrieval visibility does not establish access authorization, and document freshness does not establish operational permission.

## Constraints at the access controls step

FastGPT permissions combine member permissions, department permissions, and group permissions. Member permissions have the highest priority; department and group permissions are combined as a union. Resource permissions exist for teams, applications, knowledge bases, and files/folders (collections).

Knowledge-base file-level permission is a commercial-edition feature. By default the switch is off, and collection readability matches the knowledge base. When the switch is on, each file or folder generates a permission snapshot, and lists, details, and retrieval recall are authenticated item by item against that snapshot. Knowledge-base permission remains the threshold; collection permission cannot bypass it. A team administrator does not bypass file-level permission. System root and the team owner are treated as having full permission over all files. Retrieval recall filters by the current member's readable files only when authentication is performed by the current member identity; a workflow that preselects a knowledge base without member-identity authentication does not apply file-level filtering. Retrieval relevance is not access authorization.

### Hypothetical paper exercise

The following is a hypothetical paper exercise for checking the authorization state of a handover request. It does not refer to any real customer, company, or identity number.

Source text (hypothetical):
"Linked-cart product list V3, maintainer: content operator A, status is pending creator business development confirmation. Commission plan P-0715, applicable product: item A, commission ratio: as displayed in the selected affiliate alliance backend on the day. Violation feedback R-0820, handling status is pending product distribution specialist review."

Proposed handover request (hypothetical):
"Please transfer edit permission for linked-cart product list V3 to product distribution specialist B, and allow B to view commission plan P-0715."

Subjects, objects, and states to check: content operator A is the list maintainer, creator business development staff are the confirming party, and product distribution specialist B is the receiving party. The objects are linked-cart product list V3 and commission plan P-0715. The states are pending confirmation and pending review. Authorization boundary: transferring list edit permission requires the list administrator or creator; viewing the commission plan requires the corresponding knowledge-base or file read permission. The source text does not state whether B currently has knowledge-base read permission, so that field is unknown.

## Configuration and implementation checks

The following table lists only official documented settings or implementation checks relevant to this feature and this task. The values are hypothetical starting points for this exercise, not official defaults.

| Configuration item | Hypothetical starting point for this exercise | Reason and comparison method |
| --- | --- | --- |
| Knowledge-base file-level permission switch | On | The exercise involves permission for an individual file; in the off state collection collaborators cannot be configured. Compare with off-state behavior. |
| List file collaborators | Content operator A is creator; product distribution specialist B to be added | The creator cannot be granted or modified through collaborator configuration; the submitted list must include the current creator. |
| Read permission for the knowledge base containing the commission plan | Whether B has it, to be verified | Knowledge-base permission is the threshold and collection permission cannot bypass it. Compare with an account without read permission. |
| Retrieval identity authentication method | Authenticate by current member identity | Only this method triggers file-level filtering. Compare with a preselected knowledge base without identity authentication. |
| Collaborator submission semantics | Full overwrite | The submitted list is the final result; omitting the creator causes rejection. |
| Handover request state | Pending approval | Pending review does not establish absence of operational permission; distinguish from an approved state. |

## Three common errors

1. Treating a pending-confirmation state as already authorized. In the exercise, linked-cart product list V3 has status "pending creator business development confirmation," and commission plan P-0715 does not state B's read permission. If edit permission transfer is executed directly, the input is a pending-confirmation list and an unknown read permission, the comparison object is an approved handover request, and the observable result is that the authorization boundary is not satisfied.

2. Substituting retrieval visibility for access authorization. In the exercise, violation feedback R-0820 is pending review, and retrieval relevance does not perform permission isolation. The input is a retrieval result, the comparison object is the member's actual readable file list, and the observable result is that when the two are inconsistent, a retrieval hit must not be used to infer readability.

3. Confusing team administrator with file-level permission. In the exercise, if product distribution specialist B is only a team administrator, team-level management permission covers only the team's own resources, and knowledge bases and files are still authenticated according to collaborator configuration. The input is B's team role, the comparison object is the list file collaborator list, and the observable result is that team administrator does not automatically obtain file management permission.

## How to verify the setup

1. Input the hypothetical source text and the proposed handover request, and compare the creator field of linked-cart product list V3 with the submitted collaborator list. If the submitted list includes the current creator and B is added as administrator, and knowledge-base read permission has been verified, the condition is satisfied. If the creator is missing or read permission is not stated, record it as a gap.

2. Input the view request for commission plan P-0715, and compare B's knowledge-base read permission with the file-level permission snapshot. If knowledge-base read permission exists and the snapshot permits reading, the condition is satisfied. If knowledge-base read permission is unknown, keep it as pending verification and do not substitute a retrieval hit.

3. Input the review request for violation feedback R-0820, and compare the handling status "pending review" with an approved state. If the status remains pending review, the handover request must not be executed; the observation record should state the status field and the operation result, without inferring automatic approval or a system error.
