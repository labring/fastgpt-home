# Group-buy presale orders: interactive forms for operations handover

## What the documents look like

Presale group-buy collection takes orders first and organizes procurement and fulfillment afterward, so the working materials are the presale product table, collection results, purchase plan, and cut-off notice. Orders arrive from the mini-program, supplier stock and leader feedback feed the same cycle, and warehouse routing depends on the wave schedule. Updates run daily or per session; after cut-off, procurement is placed and picking waves are arranged as quickly as possible. The consequence of getting this wrong is a stockout refund, a delayed fulfillment, or a leader complaint.

For operations handover, the practical difficulty is that authorization state has to be read off these documents rather than assumed from activity. A cut-off notice, a collection result, and a purchase plan each carry a status, and a form submission or a retrieval result is not an authorization to act. The handover task is to establish which materials, actions, and requests are in which authorization state before any downstream step is treated as cleared.

## Constraints at the interactive forms step

The Form Input node is a user-interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues downward only after the user completes the interaction. After submission, the collected form values are passed to later nodes. The User Selection node is also a user-interaction node: it enters the same interaction state, records workflow state, waits for the user to finish, and then evaluates the user's choice and executes the "yes" branch. Neither node carries a business database. Field validation, business approval, write-back, and batch operations need an external system or a later node.

Hypothetical drill sample. An operations staff member plans to hand over one presale collection session. The material text supplied for checking consists of three sentences: "The presale product table lists the cut-off time as 10 March 18:00. The collection result status is pending review. The purchase plan has not yet been generated." The proposed handover request is: "Mark this session's collection result as approved and generate the purchase plan on that basis." The source text records only the pending-review status; it records no approval entry and no approval authority, and the purchase plan is not yet generated. The authorization boundary of that request cannot be confirmed from the material and remains to be verified.

## Three common errors

1. Treating a form submission as completed approval. In the sample, the collection result status is pending review, and the Form Input node passes collected values to later nodes; the submit action itself produces no approval record. Check input: the three source sentences and the proposed handover request. Compare: whether "pending review" and "approved" are mutually exclusive values of the same field for the same subject and the same period. Observable result: the source text records no approval, so the item is recorded as pending verification.

2. Treating a retrieval result as the basis of authority. Retrieval and forms do not grant authorization, and a relevance score does not act as an entity or permission filter. Check input: the sample source text and the proposed handover request. Compare: whether the authorizing subject named in the request appears in the source text. Observable result: the source text names no authorizing subject, so the purchase plan cannot be generated on that basis.

3. Treating a User Selection branch as a business approval flow. The User Selection node executes a branch from the user's choice and does not constitute approval execution. Check input: the sample source text and the proposed handover request. Compare: the branch outcome against the approval status field. Observable result: the branch does not change the pending-review status, and approval still requires an external implementation.

## How to verify the setup

1. Use the sample source text and the proposed handover request as input. Compare whether the source "pending review" and the request "approved" refer to the same subject, the same period, and the same field. Observe whether the same field carries mutually exclusive values. When the value is not recorded, log it as pending verification rather than as a negation or a conflict.

2. Use the sample source text as input. Compare the authorizing subject and object named in the request against the scope recorded in the source text. Observe whether the source records that authorization. When it is absent, keep the evidence gap open and do not substitute a constructed case for the actual sample.
