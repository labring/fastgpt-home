# Cross-border settlements: workflow routing for operations handover

## What the documents look like

Cross-border platform settlement and foreign exchange work concerns the collection of funds from completed orders. It does not handle fraud chargebacks, which belong to a different risk-control category. The primary materials come from the platform settlement center, bank statements, payment institution backends, and ERP orders. Day-to-day documents include platform settlement statements, exchange rate tables, service fee invoices, and receipt reconciliation tables. Update frequency is weekly or monthly, and that rhythm affects how material timeliness is judged during handover. It does not change the node behavior of the workflow routing described on this page.

Operations permission and handover management asks what authorization state a material, an operation, or a request is in. Workflow routing organizes interaction, judgment, and output into a checkable sequence. In this category, the relevant question is whether a settlement statement, a fee invoice, or a reconciliation entry has reached a state that supports moving an operation right to another person. A pending state, an issued invoice, and an unreceived payment are three separate facts. A handover request that does not state its authorization boundary remains a request, not an approval and not an execution.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The node collects the form information the user fills in and passes it to later nodes. The user selection node is also a user interaction node. When it triggers, the conversation enters an interaction state and the workflow state is recorded. When the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. Recording the interaction state is a behavior of these nodes. No separate global state-recording switch is documented, and none should be assumed.

Information collected by a form must be explicitly passed to a later retrieval, judgment, or interface node, and the output must be compared item by item against the input. Order writes, document backfill, and external status synchronization require a separate business interface or a later process. Retrieval and form collection do not by themselves constitute authorized execution. A pending review does not demonstrate that an operation right is absent.

Hypothetical paper exercise sample: the source material reads, "March 2025 platform settlement statement, subject is a cross-border seller, currency USD, settlement amount 12000.00, status is pending review; service fee invoice number SF-0301, amount 300.00, status: issued; the receipt reconciliation table marks this payment as 'not received'." The draft handover request to be judged is, "Transfer the collection operation right for the March 2025 settlement statement to the tax accountant." Judgment points: the pending review status does not constitute a completed settlement; an unreceived payment together with an issued invoice does not establish that funds have been collected; the handover request does not state its authorization boundary, so it is recorded as pending verification.

## Three common errors

1. Treating form submission as completed authorization. Input is the "pending review" settlement statement and the handover request from the sample. The comparison item is whether the authorization boundary is stated. The observable result is that when the request lacks an authorization statement, it is recorded as pending verification.
2. Treating the user selection "yes" branch as business execution. Input is the branch connection of the selection node. The comparison item is whether a downstream business interface exists. The observable result is that when only a branch exists without an interface, collection completion must not be declared.
3. Treating retrieval similarity as a permission filter. Input is the retrieval return result. The comparison item is the record subject and permission fields. The observable result is that similarity does not exclude unrelated or unauthorized records, and a separate check is required.

## How to verify the setup

1. Input the sample source material and the draft request to be judged. Compare the settlement statement status field against the authorization boundary statement. Observe whether mutually exclusive values appear for the same subject, same period, and same field. When the boundary is not stated, record the request as unsupported.
2. Input the required fields and submission output of the form input node. Compare the values actually received by the later judgment node. Observe whether output and input match item by item. When they do not match, record the gap.
3. Input an explicit paper empty result []. Compare whether the downstream node design accepts an empty value. Observe whether an unsupported default pass appears. Do not claim that a fictional rule retrieval necessarily returns empty.

Retrieval checks record observations and failure branches. They do not guarantee a first hit or full recall. Libraries on different vector models cannot be associated together; check identifiers only, exclude non-matching ones, and record actual observations. Signing, reaching cooperation, and contract effectiveness are three distinct facts. A quotation validity period does not indicate a supply period.
