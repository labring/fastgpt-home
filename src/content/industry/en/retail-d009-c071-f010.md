# Cross-border settlements: citation tracing for operations handover

## What the documents look like

Cross-border platform settlement and foreign exchange work concerns the collection of funds from completed orders, which places it in a different operational stage from fraud and chargeback risk control. The materials come from platform settlement centers, bank statements, payment institution back ends and ERP orders. The documents handled day to day include platform settlement statements, exchange rate tables, service fee invoices and receipt reconciliation sheets. The typical roles involved are cross-border seller finance staff, tax accountants and platform operations staff. Errors in this work produce incorrect profit calculations, deviations in tax filing and cash shortfalls. The supplied brief gives a weekly or monthly update frequency. This page addresses citation tracing during operations handover, and no batch synchronization or transaction-triggered mechanism is documented for that step, so none is described.

For citation tracing, each conclusion in an answer must be traceable to a specific passage of source material, and the version and validity scope of that material must be checked. The knowledge base search node can associate one or more knowledge bases that share the same vector model, and it outputs citations as an array whose length may be zero. Even when no content is found, that output path still runs. The retrieval output then needs to be passed to the answering step, where the answer is checked line by line against the cited source text. Semantic recall and relevance scores do not carry permission or entity isolation duties, and retrieval by itself does not constitute authorization.

## Constraints at the citation tracing step

The knowledge base search node accepts one or more knowledge bases that use the same vector model. Its citation output is an array, and a zero-length array is a valid result rather than a workflow error. Retrieval results must be handed to a downstream answering node for line-by-line comparison against the source text.

Hypothetical drill sample, clearly labelled as an invented paper case: the source passage is "Platform settlement statement for March 2025 (sample number JS-2025-03-A) states: amount due this period USD 12,000, total deductions USD 480, actual received USD 11,520, settlement period 2025-03-01 to 2025-03-31." The draft sentence to be judged is "Actual received in March 2025 was USD 11,520, deductions USD 480." The handover request is "Transfer the citation tracing check result for this settlement statement to the next operations holder." The source contains subject, object, period and amount fields. The draft sentence shares the subject, period and fields with the source, so the fields can be compared one by one.

The following constraints apply at this step. A retrieval hit does not mean the handover has been approved. A pending review does not show that operating permission is absent. The relevance score is a filtering threshold, not a permission or entity filter, and it does not exclude unrelated businesses or unauthorized records. Knowledge bases with different vector models cannot be associated together; the identifiers must be checked first and non-matching ones excluded, without running a cross-model retrieval to compare missed recalls. The citation limit uses the documented token unit. The thinking budget belongs to the thinking configuration and is a separate parameter from the citation token limit.

## Three common errors

1. Treating a retrieval hit as authorized execution. The input is the citation array returned by retrieval, the comparison object is the authorization state of the handover request, and the observable result is whether a citation exists. A retrieval hit does not mean the handover has been approved, and a pending review does not show that operating permission is absent.
2. Associating knowledge bases that use different vector models. The input is the candidate knowledge base identifiers, the comparison object is the vector model identifier, and the observable result is whether the identifiers match. Non-matching ones should be excluded and recorded, without running a cross-model retrieval to compare missed recalls.
3. Moving the thinking budget into the citation token limit. The input is the thinking configuration level, the comparison object is the citation limit field, and the observable result is whether the two fields have been mixed. The thinking budget and the citation limit are separate parameters and must not be exchanged.

## How to verify the setup

1. Input the sample source passage and the draft sentence above, compare the amount and period in the draft sentence against the corresponding fields in the source, and observe the result: when the subject, period and field values match, the draft is judged supported; when the source does not state a field, the draft is judged unsupported or pending verification.
2. Input a paper empty citation array `[]`, compare it against the downstream answering node design, and observe the result: when the downstream continues with a zero-length citation without error, the handling is judged correct; when the downstream treats the empty array as an error termination, the design is judged to need correction.
3. Input the handover request and the material version identifier, compare the request's current state against the material's validity scope, and observe the result: when the request is pending review, record it as pending verification and do not judge it approved; when the material version falls outside its validity scope, record the gap and do not supply authorization or effective clauses.

The verification steps above test the named primary task of citation tracing against the supplied source wording and its limitations. They do not test identity certification, report analysis or any other task. Where the source does not state a field, the evidence remains missing.
