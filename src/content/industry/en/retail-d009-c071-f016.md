# Cross-border settlements: interactive forms for operations handover

## What the documents look like

Cross-border platform settlement and foreign-exchange work concerns the collection of funds from orders that have already been completed. It does not handle fraud chargebacks, which belong to a different control area. The main data comes from the platform settlement center, bank statements, payment-provider back offices, and ERP orders. The documents handled day to day include platform settlement statements, exchange-rate tables, service-fee invoices, and receipt reconciliation tables. These records update weekly or monthly.

For an operations handover, this document set has a direct consequence. A form used during handover has to collect values that map to a specific settlement statement, a specific exchange-rate version, and a specific reconciliation row. Without that mapping, the receiving operator cannot tell which processing stage a given pool of collected funds has reached. A settlement statement number, a reconciliation row range, an invoice status, and a rate-table version are the kinds of values that make the stage visible.

## Constraints at the interactive forms step

The form input node is a user-interaction node. When it is triggered, the conversation enters an interactive state, the workflow state is recorded, and execution waits for the user to complete the interaction. After the user submits the required information, the node collects what was filled in and passes it to later nodes. The node collects submitted content. It does not carry its own business-database function. Field validation, business approval, write-back, and bulk operations need to be implemented in an external system or in later nodes.

The user-selection node is also a user-interaction node. On trigger, the conversation enters an interactive state, the workflow state is recorded, and execution waits. When the user makes a choice, the node evaluates that choice and executes the corresponding branch. This node is not a personnel directory and not a business-data selector. Retrieval and forms do not constitute authorization. A relevance score does not carry entity-isolation or permission-filtering duties, and a retrieval result is not an authorization decision.

Hypothetical paper exercise sample. Source text: a cross-border seller's finance operator wrote in a handover record, "Settlement statement S-0715 corresponds to the platform settlement center summary for July 1 to July 15; receipt reconciliation table R-0715 has been filled by the previous operator through row 3; the service-fee invoice has not yet been received; the exchange-rate table version is the one released on July 1." Draft sentence to be judged: "R-0715 is fully complete, the service-fee invoice has been archived, and the exchange-rate table has been updated to the July 15 version." A contradiction requires mutually exclusive values in the same field. Here the source text supports only that some rows are filled, the invoice has not been received, and the version is the July 1 release. The draft sentence's "fully complete," "has been archived," and "July 15 version" are not supported.

## Configuration and implementation checks

Configuration below stays with this page's sample and lists only interaction-node settings that the official documents describe, plus implementation checks. The numeric starting points are marked as hypothetical trial starting points for this exercise, with the comparison object stated.

| Configuration item | Hypothetical trial starting point | Check method and comparison object |
|---|---|---|
| Form input node fields | Settlement statement number, reconciliation row range, invoice status, rate-table version | Compare field by field against the source text; route missing items to a completion process |
| Required-field setting | All four fields above set as required | Test node behavior with one field missing, then after completion |
| User-selection node branches | Handover confirmed, returned for supplement | Check which branch executes for the choice made; do not treat it as approval |
| Interactive-state handling | Wait for submission before continuing | Observe whether the conversation enters an interactive state and records workflow state |
| Downstream division of work | Validation, approval, write-back handled by an external system | Check whether the node only passes submitted information |

The four fields were chosen because each one corresponds to a distinct item in the sample source text, so a missing field is directly observable. The two branches were chosen because the sample record describes a handover that is either confirmed or returned for supplement, and the node's documented behavior is to execute a branch based on the choice.

## Three common errors

1. Treating a form submission as completed authorization. The form input node collects submitted content. Approval and write-back require a separate system implementation. The submission action itself does not produce an authorization effect.
2. Treating a retrieval result as a permission filter. A relevance score does not carry entity-isolation duties, and retrieval does not constitute authorization. A settlement record cannot be judged operable by the current operator on the basis of a retrieval result.
3. Writing a pending-review state as already effective. When a handover request is pending review, that fact does not show that operating permission is absent, and it does not equal approval. Signing, reaching cooperation, and contract effectiveness are three distinct facts.

## How to verify the setup

1. Input the source text and the draft sentence above. Compare "fully complete," "has been archived," and "July 15 version" against the source's "filled through row 3," "not yet received," and "released on July 1." The condition is satisfied only when the draft sentence and the source share the same subject, the same period, the same field, and a consistent value. The current finding is not supported, and the item is returned for supplement.
2. Input a submission that omits the invoice-status field. Compare whether the node blocks submission under the required-field setting. Then complete that field and submit again, and observe whether execution continues to later nodes. The expected behavior is non-passage when the field is missing and information passing after completion. This is not claimed to have been tested.
3. Input an explicit paper-form empty result and check whether that empty result stays empty when passed downstream, recording the actual observation. Do not claim that a fictional rule retrieval necessarily returns an empty result. Libraries built on different vector models cannot be associated together; check the identifier and exclude non-matching libraries rather than running a cross-model retrieval to compare missed recalls.
