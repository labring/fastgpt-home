# Overseas stock replenishment: access controls for operations handover

## What the documents look like

Overseas warehouse replenishment for cross-border sellers usually spans several sales channels at once. A third-party overseas warehouse can serve multiple channels, and the seller decides how stock is allocated among them. The working materials for this category are replenishment plans, inbound appointment requests, inventory age reports, and last-mile delivery orders. These draw on warehouse management systems, ERP sales forecasts, freight forwarder systems, and carrier statements. Weekly and daily update rhythms coexist, and the same material frequently moves between members and departments during a handover.

For operations handover, the question is not only who can open a file. It is which materials a person can read, which actions that person can perform, and which requests are still pending. FastGPT organises permissions across members, departments, and groups. Member permission has the highest priority; department and group permissions are combined as a union. Resource types include team, app, dataset, and collection, where a collection is a file or folder inside a dataset. Dataset file-level permission is off by default, and while it is off, collection readability matches the dataset. Once it is on, each file or folder carries a full permission snapshot, and list views, detail views, and retrieval recall are checked item by item against that snapshot. Dataset permission remains a threshold: a collection permission cannot bypass it. Recall filters by readable files only when authentication runs as the current member identity; a workflow that preselects a dataset without member-identity authentication does not apply file-level filtering. Team administrators do not bypass file-level permission. The team owner and system root are treated as holding full permission on all files.

## Constraints at the access controls step

A hypothetical drill sample makes the boundary concrete. A cross-border seller team keeps one dataset in FastGPT for overseas warehouse replenishment materials. File-level permission is on for that dataset. Member A holds read permission on the dataset and read permission on the file "March 2025 replenishment plan." Member B holds read permission on the dataset and only inherited-state permission on that file. A draft handover request reads: "Please change Member B's permission on the March 2025 replenishment plan to write permission so that Member B can update the sales forecast." That request has not been submitted and has not received any approval.

Two constraints follow from the documents. First, configuring a collaborator or restoring inheritance requires the file administrator role and requires that file-level permission is already on. Second, collaborator configuration uses full-overwrite semantics: the submitted list is the final result, and it must contain the current creator or the submission is rejected. A single overwrite can remove the creator record. Inherited state means the file or folder permission is derived from its parent and follows parent changes; independent state means later parent changes no longer overwrite it, and its subtree stops propagating from that node. When a parent-derived collaborator is modified or deleted while the node is inherited, the system reports a conflict, and after confirmation the node becomes independent rather than silently rewriting the parent.

## Configuration and implementation checks

| Configuration item | Hypothetical starting value for this drill | Reason and comparison method |
| --- | --- | --- |
| Dataset file-level permission switch | On | The sample needs per-file distinction between members; while off, collection permission matches the dataset and no distinction is possible |
| Member A permission on the target file | Read | Compare with Member B's target permission in the draft request to see whether one file has different subjects |
| Member B permission on the target file | Inherited state | Compare with independent state after file-level permission is on, to confirm whether the node follows parent changes |
| Authorization status of the draft request | Not submitted, not approved | Compare with submitted and approved states to confirm the request does not constitute executed authorization |
| Dataset collaborator configuration semantics | Full overwrite | The submitted collaborator list is the final result and must contain the current creator, or the submission is rejected |
| Recall authentication condition | Authentication as the current member identity | Compare with a workflow that preselects a dataset without member-identity authentication, where file-level filtering does not apply |

## Three common errors

1. Treating the draft handover request as effective authorization. The input is the draft sentence about changing Member B to write permission. The comparison is the authorization status field of that sentence. The observable result is whether the request sits in an approved state. It has not been submitted and has not been approved, so write permission is not established.

2. Treating retrieval relevance as a permission filter. Recall filters by files readable to the current member; a relevance score does not perform permission or entity isolation. The input is a retrieval query by Member B. The comparison is whether the recall result contains a file Member B cannot read. The observable result is whether an over-permission file appears in the recall list.

3. Treating team administrator identity as a bypass for file-level permission. A team administrator does not bypass file-level permission, and team-level management permission covers only the team's own resources. The input is a team administrator account. The comparison is that account's collaborator configuration on the target file. The observable result is whether the account can configure collaborators without holding file administrator permission.

## How to verify the setup

1. Check permission status against the sample text. The input is the current collaborator list for the March 2025 replenishment plan file together with Member B's permission record. The comparison is the target state in the draft request, "change to write permission." The observable result is whether Member B's current permission is still inherited state and whether the request is still unsubmitted. If the request is unsubmitted, write permission cannot be treated as in effect.

2. Check the recall scope against the sample text. The input is a retrieval query Member B issues under authentication as the current member identity. The comparison is whether the recall result contains a file Member B cannot read. The observable result is whether the over-permission file is filtered out. If a workflow preselects a dataset without member-identity authentication, file-level filtering does not apply, and that scenario needs separate recording.

3. Check full-overwrite semantics for collaborator configuration against the sample text. The input is the collaborator list about to be submitted. The comparison is whether that list contains the current creator. The observable result is whether the submission is rejected. If the list does not contain the creator, the submission is rejected and needs to be completed before resubmission. This action has not been executed; it is described only as a checking step.
