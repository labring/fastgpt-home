# Creator commission settlement: interactive forms for operations handover

## What the documents look like

Creator commission settlement and commission deduction happen after a sale closes. The work centers on confirming valid promotion and handling post-sale commission deductions. The main data comes from the Selected Alliance backend, order after-sales data, the finance system, and creator contracts. Everyday documents include commission setting records, settlement bills, refund deduction details, and invoices. The typical roles involved are finance settlement staff, Selected Alliance operations staff, and creator business staff. These materials update weekly or monthly, and a single handover needs to reconcile valid orders and deduction rules for a specific period.

At the interactive forms stage, the question is which materials, operations, and requests sit at which authorization state during handover. The interactive nodes only collect filled-in information and branch choices. They do not carry business database, approval, or write-back functions. Retrieval or form collection counts as information input and does not constitute authorized execution.

## Constraints at the interactive forms step

When a form input node triggers, the conversation enters an interactive state, records the workflow state, and waits for the user to complete the fields. After submission, the node passes the collected information to later nodes. A user selection node judges the user's choice and executes the corresponding branch. Neither node includes a business database. Field validation, business approval, write-back, and batch operations are implemented in external systems or later nodes as needed.

This means authorization confirmation, deduction rule reconciliation, and payment status judgment in a commission settlement handover cannot rely on the interactive nodes themselves. A relevance score from retrieval does not change an authorization status field, and a branch selection does not write an approval status.

Hypothetical paper exercise. The source text for reconciliation reads: "The June 2025 settlement bill (number JS-202506) shows creator A's valid order commission totaling RMB 8,000. The refund deduction details (number TK-202506) show RMB 1,200 in commission to be deducted for refunds in the same period. The bill remarks column states 'submitted to finance for review, pending confirmation.'" The handover request to be judged reads: "Please pay creator A's June commission at RMB 8,000, and handle the deduction part later." This request involves subject creator A, objects being the June settlement bill and refund deduction details, status being submitted to finance for review and pending confirmation, and effective scope being June 2025. The source text does not state that finance review passed, does not state that the deduction is complete, and does not state payment authorization.

## Configuration and implementation checks

The table below lists implementation check items relevant to this page's primary task, built around the exercise above. The values are starting points for this hypothetical trial only, used to explain the comparison method. They are not official defaults.

| Check item | Hypothetical trial starting point | Comparison method and reason |
| --- | --- | --- |
| Required settlement bill fields | Bill number, creator identifier, period, commission total | When any field is missing, the interactive node cannot pass complete information; compare against JS-202506 |
| Refund deduction detail link fields | Detail number, linked bill number, deduction amount | Check whether TK-202506 shares the same period and subject as JS-202506 |
| Authorization status fields | Review status, payment authorization status | The sample remark is pending confirmation; compare against an authorized value |
| User selection branch condition | Select "continue reconciliation" or "hold" by review status | The branch depends on a field value, not on retrieval relevance |
| Interactive state record scope | Record the current workflow state | Wait for interaction to finish before continuing; do not infer automatic approval |
| Downstream processing ownership | Field validation, approval, and write-back are implemented by external systems | Interactive nodes do not perform database writes or synchronization |

## Three common errors

1. Treating "submitted to finance for review, pending confirmation" as review passed or payment authorized. The input is the sample remark text. The comparison object is the field value "pending confirmation" against "authorized." The observable result is that the two values are not equal, and the authorization state remains unsupported.
2. Using retrieval relevance or form collection results in place of a permission judgment. The input is retrieved content or a filled-in form value. The comparison object is the business authorization field. The observable result is that a relevance score does not change the authorization status field, and payment cannot be executed on that basis.
3. Equating the execution result of a user selection branch with completed business approval. The input is the branch selection action. The comparison object is the approval status field. The observable result is that branch execution does not write an approval status, and whether approval is complete still requires an external system record.

## How to verify the setup

1. Use the sample source text to check settlement bill field completeness. The input is the field list of JS-202506. The comparison object is the required field list. If bill number, creator identifier, period, and commission total are all present, the fields are complete. If any field is missing, record the gap and keep the item unsupported.
2. Use the sample source text to check authorization status. The input is the remark column "submitted to finance for review, pending confirmation." The comparison object is the value "authorized." If the two do not match, the payment request does not meet execution conditions. If the material is later supplemented to state that review passed and payment is authorized, compare again.
3. Use the sample request to check the deduction handling boundary. The input is "handle the deduction part later." The comparison object is the RMB 1,200 deduction amount in TK-202506 against the RMB 8,000 bill commission. If the request does not state whether the deduction has already been subtracted from the payable amount, the deduction status remains to be verified, and completed deduction is not presumed.
