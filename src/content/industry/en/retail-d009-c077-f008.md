# Import and export permits: workflow routing for operations handover

## What the documents look like

Permit handling for import and export takes place before customs declaration, and its outcome decides whether goods can lawfully cross the border. The materials handled day to day include automatic import licences, dual-use item licences, contracts and product descriptions. They originate from commerce authority systems, customs commodity codes, supplier materials and customer end-use statements. These materials update irregularly and on a per-shipment basis, and within one shipment the statuses of different materials do not move together. A licence may sit at pending review, a contract may already be signed, and a product description may still be a draft.

For operations handover, the practical question is which material, operation request or handover request currently holds which authorization state. Workflow routing can record and pass those states between nodes. It does not perform approval or grant authorization. A retrieval hit shows that a document exists in the accessible target scope; it does not show that approval completed or that customs handover is permitted. Retrieval does not carry out permission filtering or entity isolation, and a relevance score is not a category, entity or permission filter. A requirement that a knowledge base and its embedding model match cannot be extended to mean that an external commerce authority system or any other outside system must use the same model. Libraries built on different embedding models cannot be associated together; identifiers are checked first and non-matching libraries are excluded, without running a cross-model retrieval to compare missed recalls.

## Constraints at the workflow routing step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution continues after the user completes the interaction. The node collects required information and, after submission, passes the collected form values to later nodes. The user selection node is also a user interaction node. When the user makes a choice, the node evaluates that choice and executes the corresponding "yes" branch. The documented behavior covers waiting, recording state and hiding the dialog box during interaction; no global state-recording switch, submission-count control, automatic judgement or snapshot guarantee is documented, and none is asserted here.

Collected values must be passed explicitly to later retrieval, judgement or interface nodes, and output is compared against input field by field. Order writing, document backfill and external status synchronization require a separate business interface or a later process; the nodes themselves do not complete those business actions. A pending request is not an approval, an offered option is not execution, and an unsigned termination is not a completed termination. Where the documents do not state an error code or an observed result, the comparison method and the remaining unknown are recorded rather than a deterministic failure cause.

Hypothetical paper exercise sample. The source material text for one shipment reads: "Automatic import licence application number A-001, applicant Alpha Company, status pending review; dual-use item licence application number B-002, applicant Alpha Company, status accepted for processing; contract number C-003, signed by Alpha Company and Beta Company, signing date 1 March, no effective conditions stated." A handover request awaiting judgement reads: "Please confirm that Alpha Company has obtained all permit documents for this shipment and that customs handover can be arranged." The request treats pending review and accepted for processing as obtained, which does not match the source material text, so the request is unsupported.

## Configuration and implementation checks

| Configuration item | Setting for this page | Verification method |
| --- | --- | --- |
| Form input node | Collect permit type, application number, applicant name, current status | After submission, check whether the values were passed to later nodes |
| User selection node | Set the "yes" branch for "materials complete" | Verify branch connections item by item against the selection result |
| Interaction state check | Confirm the interaction node records state and waits for completion | Observe whether the conversation enters the interaction state |
| Output handover check | Pass collected values to retrieval or judgement nodes | Compare output and input fields item by item |
| External action split | Route customs handover and document backfill to a separate business interface | Confirm the node does not itself complete the business action |
| Hypothetical exercise starting value | Use "pending review" as the status comparison starting point | Compare field by field against the status stated in the source material text |

The hypothetical exercise starting value in the table applies only to this paper check. "Pending review" is chosen because the sample source text states that status explicitly, and the comparison target is the status field recorded in the source material text. It is not an official default value.

## Three common errors

1. Treating "accepted for processing" as "obtained". In the sample, B-002 has the status accepted for processing, while the draft sentence says all permit documents have been obtained. The applicant is the same and the field is the same, and the two values are mutually exclusive, so the draft is unsupported.
2. Treating a retrieval hit as authorization. Retrieving a licence document shows only that the material exists. It does not show that approval completed or that customs handover is permitted, and retrieval does not perform permission filtering.
3. Treating pending review as missing operating permission. In the sample, A-001 is at pending review, which shows only that approval is not complete. It does not support a conclusion that the applicant lacks permission to submit or modify.

## How to verify the setup

1. Input the sample source text "Automatic import licence application number A-001, status pending review" and compare it with the draft sentence "has obtained all permit documents". Observe whether the check identifies pending review and obtained as mutually exclusive. The condition is met when the draft is identified as unsupported.
2. Input the sample source text "dual-use item licence application number B-002, status accepted for processing" and compare it with the handover request "customs handover can be arranged". Observe whether the check states that accepted for processing does not equal completed approval. The condition is met when the evidence gap is identified.
3. Input an explicit paper empty result [] and check whether the shipment is still judged to have complete materials. If the downstream design still outputs a complete conclusion on an empty result, record it as a handover design item to correct. Do not claim that a fictional rule retrieval necessarily returns [].

All of the above is paper checking. No test was actually executed, and no customs declaration, approval or handover action took place.
