# Import and export permits: interactive forms for operations handover

## What the documents look like

Import and export permit handling happens before customs declaration, and it determines whether a shipment may lawfully cross the border. The working data come from the commerce authority system, customs commodity codes, supplier materials and customer statements of use. The documents handled day to day include automatic import licences, dual-use item licences, contracts and product descriptions. The authorisation status, valid scope and handover responsibility attached to these materials decide whether a later declaration can proceed. Materials update irregularly and each shipment is handled on its own, so permission and handover management has to be checked shipment by shipment rather than through batch synchronisation or transaction-triggered mechanisms.

For this page the relevant industry facts are three. Permit handling sits upstream of declaration, so a status recorded in a form is not the same thing as a permission granted by an authority. The evidence a handover reviewer works from is a document excerpt plus a status field, and those two may disagree. Each shipment carries its own contract number, licence type and current status, so a value collected for one shipment cannot be reused for another.

## Constraints at the interactive forms step

The form input node is a user interaction node. When it triggers, the conversation enters an interaction state, the workflow state is recorded, and execution waits until the user completes the interaction. After the user submits, the node collects the values entered and passes them to later nodes. The user selection node is also a user interaction node. It triggers the same interaction state and state recording, and when the user makes a choice the node evaluates that choice and executes the branch. Neither node carries business database functions of its own. Field validation, business approval, write-back and batch operations need to be implemented in an external system or in later nodes. Interaction waiting, state recording and dialogue hiding follow the documented description; no submission count, automatic judgement or snapshot guarantee is documented.

Retrieval or form collection does not constitute authorisation to act. A relevance score is not a category, entity or permission filter, and a similarity setting does not exclude unrelated businesses or unauthorised records.

Hypothetical paper exercise sample. The material excerpt reads: "This shipment's automatic import licence application has been submitted to the commerce authority system, and the current status is pending review; the attached contract number is HYP-2024-017, the buyer is an overseas company, and the goods are products listed in the dual-use items schedule." The draft sentence to be assessed reads: "This licence has been approved and customs declaration can be arranged." The check point: the material shows only pending review and states no approval; the draft sentence presents pending review as approval, and it does not distinguish among signature, agreement reached and contract effectiveness as three separate facts. The authorisation boundary is operations handover checking, and it does not involve an actual declaration or approval action.

## Configuration and implementation checks

| Configuration item | Hypothetical starting value for this exercise | How to check |
| --- | --- | --- |
| Required form input fields | Licence type, contract number, current status | Submit empty values and completed values separately, then observe what is passed on |
| User selection branch conditions | Pending review, approved, returned | Select according to the status wording in the material and record which branch runs |
| Interaction state waiting scope | Continue after a single interaction completes | Observe whether the conversation records state and continues downward |
| Location of later field validation | External system or later nodes | Check whether the form node only collects values |
| Handover material reference scope | Automatic import licence, contract, product description | Check shipment by shipment the correspondence between materials and fields |

The values above are starting points for this paper exercise, not official defaults. The reason for choosing the three required fields is that the sample material supplies exactly those three identifiers and no others. The comparison method is to submit the form with one field left empty and then with all three completed, and to compare what the later node receives in each case. The form input node can be added repeatedly and triggers execution; the user selection node has the same properties.

## Three common errors

1. Writing a pending review status as approved. The input is the material wording "the current status is pending review"; the comparison is the draft sentence "has been approved"; the observable result is that the two do not agree and the draft sentence is not supported by the material. The evidence gap remains: no approval wording appears in the excerpt.

2. Treating form collection as authorised execution. The input is the licence type and contract number submitted through the form; the comparison is whether a later node directly triggers a declaration action; the observable result is that the form node only passes values and performs no approval. Whether an approval step exists downstream is unknown from the supplied documents.

3. Treating a similarity setting as a permission filter. The input is a retrieval query and the records returned; the comparison is whether the returned records include unauthorised parties; the observable result is that similarity does not carry entity or permission isolation. What the retrieval returns for any particular query remains an observation, not a guarantee.

## How to verify the setup

- Verification one. Input the material wording "the current status is pending review" together with the draft sentence "This licence has been approved and customs declaration can be arranged." Compare the value of the status field. If the draft sentence does not agree with the material wording, the draft sentence is judged unsupported and the item is retained as pending confirmation. A pending request is not an approval.

- Verification two. Input the form with the required fields left empty, submit, and observe whether the later node receives complete values. Then input the completed fields and observe what is passed on. If the later node does not receive complete values after an empty submission, the required-field check is working as intended. This is a paper expectation, not a recorded test result.

- Verification three. Input the user selection branch condition "pending review" and observe whether the branch taken is the pending review path; then input "approved" and observe whether a different branch runs. If the branch taken matches the selection, the branch configuration can be checked. A paper input of [] can be used to check downstream design, and no claim is made that a fictional rule retrieval necessarily returns an empty result. Different vector models cannot be associated together; check the identifier first and exclude those that do not match.
