# Chain-store closure accounts: access controls for operations handover

## What the documents look like

Closure settlement runs in the opposite direction from site selection and store opening. It handles exit and asset recovery rather than expansion. The working materials come from POS inventory, the fixed-asset system, lease contracts and the finance ledger. The everyday documents are closure approvals, inventory clearance sheets, lease termination agreements and asset count sheets. The people involved are chain operations staff, finance staff, legal staff and the landlord contact person. Records are updated per store on an irregular basis.

A closure handover crosses several document types at once, and each type carries its own state. An approval can be pending review. A clearance sheet can carry signatures and a date. A termination agreement can be unsigned while a draft has been received. An asset count sheet can be ready for transfer while the receiving member still lacks the file permission needed to open it. These states belong to different fields, and a single handover request can mix them. The permission layer has to be read against the specific store, the specific document and the specific operation. The pace at which store records are updated does not change the permission rules.

## Constraints at the access controls step

Team permission is decided by checking the individual member permission first, then taking the union of the permissions of the departments and groups the member belongs to. Resource permissions differ across team, application, dataset and file or folder (collection). File-level permission for a dataset is a commercial-edition feature. While it stays off, collection readability follows the dataset itself and no collection permission record is queried. Once it is on, every file or folder gets a permission snapshot, and list views, detail views and retrieval recall are each checked against that snapshot. Dataset permission remains the threshold; collection permission cannot bypass it. Collaborator configuration uses full overwrite semantics, so the submitted list is the final result. The creator cannot be granted or changed through collaborator configuration. A team administrator does not bypass file-level permission. Retrieval filters unauthorized files only when it authenticates as the current member; a workflow that preselects a dataset without member-identity authentication does not apply file-level filtering. Retrieval recall and relevance do not constitute authorization.

Hypothetical exercise sample. A chain operations staff member submits a closure handover request to move the asset count sheet and the lease termination agreement for "XX Road Store" to finance for review. The source text supplied for checking reads: "The closure approval for store number A-017 has been submitted by regional operations and its status is pending review by the regional manager. Inventory clearance sheet QC-2024-088 has been signed by the store manager and the finance specialist, dated 30 June 2024. The lease termination agreement has not been signed by either party; the landlord contact person has confirmed receipt of the draft." The draft sentence to be judged reads: "The store closure approval has passed, the lease termination agreement has taken effect, and the asset count sheet can be handed to finance for archiving." The points to judge: a pending review status does not constitute approval; an unsigned agreement does not constitute effect; the transfer of the count sheet requires checking whether the target member holds the corresponding file permission. For this exercise the handover checklist is set to 5 items as a starting value. The reason is that the sample names five material types: approval, clearance sheet, agreement, count sheet and employee settlement. The comparison object is the set of material entries actually listed in the sample text.

## Configuration and implementation checks

| Configuration or check item | Setting relevant to this page | Implementation note |
| --- | --- | --- |
| Team and member permission | Member permission takes priority; department and group permissions are combined as a union | Check the actual member identity and team role of each closure handover participant |
| Dataset resource permission | Can use, can edit, can manage | Check item by item against the scope finance, legal and operations each require |
| File-level permission switch | Off by default; turning it on requires dataset administrator | Once on, collections are checked against snapshots; turning it off clears all collection collaborator configuration |
| Collection collaborator roles | Read, write, administrator, creator | Submitted as full overwrite; the creator cannot be changed through collaborator configuration |
| Retrieval authentication condition | Filtering applies when authenticating as the current member | A preselected dataset without member-identity authentication does not apply file-level filtering |
| External system permission | External interface authentication and resource permission are verified separately | When connecting a business system, check both; neither substitutes for the other |

## Three common errors

1. Treating a pending review status as passed. In the sample the closure approval status is pending review by the regional manager, while the draft sentence says it has passed. The input is the approval status field, the comparison is between the values "pending review" and "passed", and the observed result is that the two do not match.

2. Treating an unsigned agreement as effective. In the sample the lease termination agreement has not been signed by either party, while the draft sentence says it has taken effect. The input is the signature status, the comparison is between "unsigned" and "effective", and the observed result is an evidence gap that does not support a finding of effect.

3. Using retrieval relevance in place of file permission. The input is a member's retrieval result against the asset count sheet, the comparison is that member's collaborator role on the collection, and the observed result is that a retrieval hit does not constitute read permission; the authorization record must be checked separately.

## How to verify the setup

1. For the sample draft sentence "the store closure approval has passed", the input is the source sentence "its status is pending review by the regional manager". The comparison object is the value of the approval status field. The condition is met when the draft sentence agrees with the source status. The current observation is that they do not agree, so the sentence should read pending review.

2. For the sample draft sentence "the lease termination agreement has taken effect", the input is the source sentence "has not been signed by either party". The comparison object is the signature status. The condition is met when a record exists showing both parties have completed signing. The current observation is that no such record is supported, so the evidence gap remains.

3. For the asset count sheet transfer request, the input is the receiving member account and the target file. The comparison object is that member's read or write permission record on the collection. The condition is met when the member holds the corresponding permission and file-level permission is on for the dataset. The current observation is that this must be checked account by account, and retrieval relevance is not a basis for authorization. If retrieval returns an empty result, a paper input of [] can be used to check the downstream design; no rule should be inferred that a fictional rule necessarily returns an empty set.
