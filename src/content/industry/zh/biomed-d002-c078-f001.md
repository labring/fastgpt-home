# 监护设备产品的HTTP 接口与外部系统

## 这个品类的数据长什么样
监护设备产品的数据主要来源于设备内置传感器、外部连接模块或医院信息系统（HIS/CIS）。数据更新频率高，多为实时或准实时传输，例如心电、血压、血氧饱和度、体温等生理参数，通常以秒级或毫秒级间隔进行数据流推送。文档结构上，数据常采用HL7、DICOM或私有协议进行封装，转换为HTTP接口时，多表现为JSON或XML格式。字段命名规范性强，但不同厂商的设备可能存在细微差异，例如血压数据可能分为`systolic_pressure`、`diastolic_pressure`，也可能统一为`bp_systolic`、`bp_diastolic`。单位通常遵循国际标准，如mmHg、bpm、%SpO2，并明确标注在字段定义中。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
监护设备数据的高更新频率要求HTTP接口具备高吞吐量和低延迟处理能力，以避免数据积压和延迟感知。实时性需求意味着接口调用不宜采用长轮询，更适合基于Webhook或流式API的推送机制。数据格式的标准化倾向于JSON，便于解析和处理，但也需兼容部分遗留系统可能采用的XML格式。字段命名和单位的差异性，要求外部系统在集成时具备灵活的字段映射和单位转换机制，以确保数据一致性。面对大量的生理参数，API设计需要考虑如何高效地批量传输和更新数据，减少不必要的请求开销。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| :----- | :------- | :----------- |
| `API_ENDPOINT` | `https://api.example.com/monitor/v1/data` | 指向设备数据聚合服务的标准接口地址 |
| `HTTP_METHOD` | `POST` | 适合实时数据流推送，承载结构化数据 |
| `REQUEST_TIMEOUT` | `5 秒` | 应对实时性要求，避免过长等待导致数据堆积 |
| `MAX_RETRIES` | `3 次` | 应对瞬时网络波动或服务暂时不可用，提高数据传输稳定性 |
| `RATE_LIMIT` | `100 次/秒` | 适配设备数据更新频率，防止接口过载 |
| `DATA_FORMAT` | `JSON` | 行业主流格式，解析效率高，便于集成 |

## 容易做错的三处
*   HTTP 接口调用时常出现 `429 Too Many Requests` 错误，这是因为未正确配置请求限流或设备数据推送频率超出接口处理能力。
*   接收到的数据中关键生理参数字段为空或类型不匹配，通常是由于不同设备厂商的字段命名差异未在外部系统进行适配性映射。
*   数据更新延迟显著，例如心率数据长时间未更新，可能是因为外部系统未采用实时推送机制，而是周期性拉取，导致数据获取滞后。

## 怎么确认配好了
*   检查外部系统日志，确认 HTTP 接口调用返回状态码为 `200 OK`，且无 `4xx` 或 `5xx` 错误。
*   对比监护设备显示数据与外部系统接收到的数据，验证关键生理参数（如`heart_rate`、`spo2`）的数值和单位是否一致，并确认数据更新频率符合预期。
*   模拟设备故障或网络中断场景，观察外部系统是否能通过重试机制或错误处理流程，在网络恢复后继续接收数据，并无数据丢失。
*   检查外部系统数据存储，确认不同时间点的设备数据记录完整，且字段无缺失或异常值。
