# 监护设备产品的表单与交互

## 这个品类的数据长什么样
监护设备的数据主要来源于设备自身的传感器实时采集，以及与医院信息系统（HIS）、电子病历系统（EMR）的集成。数据更新频率高，通常以秒级或毫秒级进行。文档结构方面，技术文档和说明书是主要载体，包含设备型号、序列号、测量参数（如心率、血压、血氧饱和度、体温等）、测量范围、精度、校准方法、报警阈值设置、故障代码及处理流程。字段通常包含数值型（带单位）、布尔型、枚举型和文本型。例如，血压数据可能表示为“120/80 mmHg”，血氧饱和度为“SpO2: 98%”。设备日志、报警记录等也是重要数据来源，其结构化程度相对较低，常以非结构化文本形式存在。

## 这些特征在「表单与交互」这一环带来什么约束
监护设备的实时性数据特征，要求表单与交互设计在数据获取、展示和校验上需支持高频更新与快速响应。设备参数的复杂性和多样性，使得表单需要具备灵活的字段定义和条件逻辑，以适应不同型号设备的特定参数。例如，某些设备可能特有呼吸末二氧化碳（EtCO2）测量，而其他设备则无此功能。单位的规范性与一致性是关键，例如血压单位 `mmHg`，血氧单位 `%`。由于数据可能来自设备直接上报，也可能通过第三方系统同步，因此在交互中需考虑数据源的切换和冲突解决机制。设备故障代码和报警信息需要快速检索和解释，这就要求表单能直接关联到故障排除指南，并支持模糊匹配查询。文档结构决定了知识库的切分策略，例如，将设备参数、故障排除和使用说明作为独立的知识块。

## 配置怎么定
| 配置项           | 建议取法                                        | 这样取的依据                                                 |
| :--------------- | :---------------------------------------------- | :----------------------------------------------------------- |
| `分段长度`       | `500–800 字符`                                  | 监护设备说明书和技术文档的段落长度适中，避免过长导致语义分散。 |
| `召回条数`       | `前 8 条`                                       | 确保能覆盖常见设备参数、故障代码及相关解释，同时控制查询效率。 |
| `相似度阈值`     | `0.75`                                          | 过滤掉不相关的召回结果，提升精准度，避免误导性信息。         |
| `重排返回条数`   | `前 3 条`                                       | 在召回结果中精选最相关的条目，优先展示设备型号、报警处理等关键信息。 |
| `maxContext`     | `4096 tokens`                                   | 适应监护设备查询中可能包含的多个参数、故障描述或操作步骤。   |
| `UPLOAD_FILE_MAX_SIZE` | `100 MB`                                        | 支持上传大型设备说明书或固件更新日志等技术文档。             |

## 容易做错的三处
*   聊天对话时，显示未选择知识库，但在调试预览时正常：原因常是应用部署后，对应的知识库ID未正确绑定到生产环境的对话流或API调用中，导致运行时无法加载。
*   工作流中，AI模型下拉列表为空：通常是后端服务未能正确加载或认证AI模型提供商的API密钥，导致模型列表无法从远程API获取。
*   返回引用内容不符合预期：可能由于文档切分策略不当，例如将不同设备型号的参数混淆在一个知识块中，或知识块过大导致召回时包含冗余信息。

## 怎么确认配好了
*   针对某款具体监护设备型号，提问其核心测量参数及正常范围，核对返回结果与设备说明书中的参数表是否一致。
*   模拟一个常见的监护设备报警代码，查询其原因及处理步骤，验证返回信息是否准确且包含关键操作指引。
*   上传一份新的监护设备技术手册，等待知识库处理完成后，尝试查询其中独特的功能或校准方法，检查是否能被正确检索。
