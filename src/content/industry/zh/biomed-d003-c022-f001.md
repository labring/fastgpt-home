# 值班转接企微群自动化管理的HTTP 接口与外部系统

## 这个品类的数据长什么样
值班转接场景的数据主要包括值班表信息、企业微信群成员列表、外部系统事件通知和转接记录。值班表通常以结构化数据形式存在，如 JSON 或 CSV，包含值班人员姓名、ID、值班时段和联系方式。更新频率根据排班周期而定，可能是每周或每日更新。企业微信群成员数据通常通过 API 获取，包含成员 ID 和昵称。外部系统事件通知通常是实时的，以 JSON 或 XML 格式推送，包含事件类型、发生时间、相关实体 ID 和紧急程度。转接记录则包含转接发起人、被转接人、转接时间、转接原因和处理状态。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
值班表数据的周期性更新要求外部系统能够定时拉取或接收推送，确保值班信息始终为最新。如果值班表是手动维护的 CSV 文件，则需要考虑文件上传与解析机制。企业微信群成员列表的动态性，要求在转接操作前实时查询，以确保目标群组或成员的有效性。外部系统事件通知的实时性，要求 HTTP 接口具备高可用性和快速响应能力，以避免事件处理延迟。事件通知中的紧急程度字段，可能需要映射到 FastGPT 内部的优先级策略，影响消息发送频率或转接流程。转接记录的存储与查询，则需要外部数据库支持，并通过 HTTP 接口进行数据同步。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| `externalApiUrl` | `https://api.example.com/oncall/schedule` | 值班表数据源的实际 API 地址，确保可访问性。 |
| `updateIntervalSeconds` | `3600` 秒 | 值班表通常按小时或更长周期更新，减少不必要的请求。 |
| `timeoutMilliseconds` | `5000` 毫秒 | 外部接口响应时间预期，防止长时间等待导致任务堆积。 |
| `requestHeaders` | `Authorization: Bearer <TOKEN>` | 外部 API 认证要求，确保数据请求的安全性。 |
| `responseBodyPath` | `$.data.oncall_list` | 解析 JSON 响应体，获取值班人员列表的核心数据路径。 |
| `maxRetries` | `3` 次 | 临时网络波动或服务不可用时的重试机制，提高稳定性。 |

## 容易做错的三处
*   外部系统事件通知无法触发转接流程：原因在于 HTTP 接口配置的监听路径与外部系统推送的路径不匹配，导致事件未能正确接收。
*   值班人员转接错误或失败：原因在于获取的值班表数据过期，或者企业微信群成员 ID 与值班表中的人员 ID 映射关系不正确。
*   重启 Docker 容器后数据丢失：原因在于 Docker 容器未正确配置数据卷（`volumes`），导致容器内部的数据未持久化到宿主机。

## 怎么确认配好了
*   通过 FastGPT 的日志系统检查 HTTP 请求是否成功发送到外部系统，并观察响应状态码是否为 200。
*   手动触发一个模拟的外部系统事件，观察企业微信群中是否按预期发送了转接通知，并检查通知内容是否包含正确的值班信息。
*   对比 FastGPT 内部存储的值班人员列表与外部系统最新值班表数据，确认数据同步的准确性和时效性。
*   模拟一次网络中断或外部系统短暂不可用的情况，观察 FastGPT 的错误处理机制是否按配置进行重试。
