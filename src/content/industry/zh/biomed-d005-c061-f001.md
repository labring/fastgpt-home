# 手术机器人制度的HTTP 接口与外部系统

## 这个品类的数据长什么样
手术机器人制度的数据源主要包括医疗机构内部的质量管理系统、设备维护记录、以及相关法规更新文档。这些数据通常以结构化文档（如 PDF、Word）和半结构化数据（如 XML、JSON 格式的设备日志）形式存在。法规更新频率通常是季度或年度，而设备维护与操作记录则实时生成。文档内容涵盖操作规程、故障排查手册、合规性要求、软件版本更新说明等。关键字段包括 `device_id`、`software_version`、`procedure_code`、`compliance_status`、`update_date`，单位多为文本描述、日期时间戳、布尔值。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
手术机器人制度数据的多源性和复杂性，对 HTTP 接口的数据同步和解析提出了特定要求。法规文档的低频更新意味着不适合高频全量拉取，需要支持增量更新或事件驱动机制。设备日志的实时性要求接口具备高吞吐量和低延迟，并能处理大量的结构化小文件或数据流。文档的半结构化特性决定了需要强大的文本解析能力，以准确提取 `procedure_code` 等关键信息，避免因格式差异导致的数据丢失。此外，合规性数据对数据完整性和准确性有严格要求，任何接口传输错误或解析失败都可能影响制度问答的可靠性。

## 配置怎么定

| 配置项                       | 建议取法                               | 这样取的依据                                                              |
| :--------------------------- | :------------------------------------- | :------------------------------------------------------------------------ |
| `max_document_size_mb`       | `50 MB`                                | 应对大型法规文件和详细操作手册，确保上传完整性。                          |
| `fetch_interval_hours`       | `24 小时`                              | 适用于法规更新频率较低的场景，兼顾时效性与系统负载。                      |
| `timeout_seconds`            | `120 秒`                               | 考虑外部系统响应延迟及大型文档处理时间，防止连接中断。                    |
| `chunk_size_characters`      | `1000 字符`                            | 平衡语义完整性与分段处理效率，提高问答召回准确率。                        |
| `max_retries`                | `3 次`                                 | 应对外部系统瞬时故障或网络波动，提高数据同步成功率。                      |
| `error_notification_webhook` | `https://your.alert.system/webhook`    | 及时通知集成方处理接口调用失败，保障数据同步的健壮性。                    |

## 容易做错的三处
*   现象：HTTP 接口返回 `403 Forbidden` 或 `401 Unauthorized` 错误码。原因：API 密钥或认证令牌过期、权限不足，或者 `Authorization` 请求头未正确设置。
*   现象：从外部系统同步的文档内容缺失，例如缺少 `software_version` 字段。原因：文档解析器配置不当，未能正确识别或提取特定格式的字段，或者外部系统返回的数据结构与预期不符。
*   现象：设备日志数据同步后，问答系统无法回答最新的故障排查问题。原因：数据同步频率过低，未能及时获取到最新的实时日志数据，或者 `chunk_size_characters` 过大导致日志细节被截断。

## 怎么确认配好了
*   执行一次完整的数据同步流程，检查日志中是否存在 `200 OK` 响应码，并核对 `data_sync_count` 字段是否与源系统数据量匹配。
*   随机选取 5 份同步完成的制度文档，在问答系统中提问相关操作规程和合规性问题，验证回答是否准确且包含文档中的关键 `procedure_code`。
*   模拟一次外部系统的数据更新（例如更新一份法规文档），观察系统是否能在 `fetch_interval_hours` 设定的时间内自动同步并更新问答内容。
*   通过 `GET /api/v1/sync_status` 接口，检查 `last_sync_timestamp` 是否为最新，以及 `error_count` 是否为零。
