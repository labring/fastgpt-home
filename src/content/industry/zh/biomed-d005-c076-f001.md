# 病历质控制度的HTTP 接口与外部系统

## 这个品类的数据长什么样
病历质控制度数据主要来源于医疗机构内部的管理系统、规章制度文档、操作手册以及国家或地方的医疗法规。这些数据通常以非结构化文本（如 PDF、Word 文档）、半结构化数据（如 XML 格式的制度文件）和结构化数据（如数据库中的质控标准条目）的形式存在。制度文档更新频率相对较低，通常按年度或政策调整周期进行修订。文档结构复杂，包含章节、条款、附件等，且常引用其他制度或法律文件。字段与单位方面，制度内容涉及具体的医疗行为规范、质量指标、考核标准等，例如“病历书写时限”可能以“小时”或“天”为单位，“质控检查项”则为布尔值或枚举值。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
病历质控制度数据的多样性与复杂结构，决定了 HTTP 接口需要支持多种数据源的接入，以及对非结构化文本的有效解析。文档更新频率低，意味着初期数据同步可以采用全量同步，后续则需设计增量更新机制，减少不必要的资源消耗。制度文档的引用关系和嵌套结构，要求外部系统在处理时能够识别并建立知识图谱，以便在问答时进行多文档关联。字段与单位的规范性，使得在将制度内容转化为可查询知识时，需要进行严格的实体识别和标准化处理，确保数值型指标的准确性对比。此外，制度的权威性要求数据传输和处理过程具备高可靠性和安全性，例如使用 HTTPS 协议，并对敏感信息进行加密。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| `chunk_size` | `800–1200 字符` | 平衡文本语义完整性与召回效率，避免长文本切分后语义丢失。 |
| `overlap_size` | `100 字符` | 确保切片之间有足够的上下文重叠，提高边缘信息召回率。 |
| `parser_timeout` | `600 秒` | 制度文档通常较大，解析时间较长，防止因超时导致解析失败。 |
| `max_connections` | `50` | 考虑到制度文件数量与并发解析需求，提供足够的连接数支持。 |
| `api_key_header` | `X-API-Key` | 遵循常见的 HTTP API 认证实践，提高安全性与可识别性。 |
| `max_retries` | `3` | 应对外部系统暂时性网络波动或服务不可用，增加请求的健壮性。 |

## 容易做错的三处
1. HTTP 请求返回的链接缺少 `http://` 或 `https://` 前缀，导致外部系统无法直接访问。原因可能是外部系统在生成链接时未包含协议头，或者接口设计时未强制返回完整的 URL 格式。
2. 通过 API 调用时，工作流中配置的变量在调试阶段能正确拼接，但实际调用时变量部分为空。原因通常是 API 请求参数与工作流内部变量名不匹配，或变量作用域配置不当，导致外部系统未能正确传递或解析变量。
3. 文档解析或数据同步过程中出现超时错误。原因在于制度文档通常体积较大且结构复杂，默认的连接或解析超时时间不足以完成处理。

## 怎么确认配好了
1. 选取多份不同格式和大小的病历质控制度文档，通过 HTTP 接口上传，检查接口返回状态码是否为 `200`，并确认文件内容是否被正确解析并入库，观察知识库中是否生成了对应的知识条目。
2. 调用外部系统提供的质控问答接口，使用包含专业术语和引用关系的复杂问题进行测试，核对返回结果是否准确引用了制度原文的条款，并检查答案的完整性和一致性。
3. 模拟并发请求，观察 HTTP 接口的响应时间和稳定性，通过监控系统检查是否有异常的错误率或超时情况，确保系统在高负载下仍能正常工作。
4. 检查外部系统日志，确认数据同步任务是否按预期周期运行，并记录了所有制度文档的更新或增量变化，没有出现数据丢失或同步失败的错误提示。
