# 血糖数据解读智能客服的工具调用与插件

## 这个品类的数据长什么样

血糖数据主要来源于智能血糖仪、连续血糖监测（CGM）设备、以及用户手动录入。数据更新频率高，CGM 设备每 5-15 分钟即可生成一条数据，而指尖血检测则按需记录。数据文档结构通常包含时间戳 `timestamp`、血糖值 `glucose_value`、单位 `unit`（如 `mmol/L` 或 `mg/dL`）、事件标签 `event_tag`（如餐前、餐后、运动后）等字段。部分设备还会提供趋势图、波动范围等衍生数据。单位转换是常见操作，尤其在不同设备或地域标准下，`mmol/L` 与 `mg/dL` 之间的换算需精确处理。

## 这些特征在「工具调用与插件」这一环带来什么约束

高频更新的血糖数据要求工具调用具备高效的数据拉取与处理能力，以确保智能客服能基于最新数据提供咨询。数据源的多样性（不同品牌设备）意味着需要适配多种数据接口或数据格式转换工具。单位不一致的问题，如 `mmol/L` 与 `mg/dL`，强制要求插件在数据处理环节内置单位校验与转换逻辑，避免因单位混淆导致解读错误。事件标签的存在，促使工具调用需要能够根据特定事件（如餐后两小时）筛选和分析数据，从而提供更具上下文的咨询服务。此外，历史数据的积累量大，对工具调用的数据查询效率和结果聚合能力提出了要求。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| `tool_timeout_seconds` | `30 秒` | 确保在数据拉取或复杂计算时避免长时间等待，兼顾响应速度与处理耗时。 |
| `max_tokens_output` | `2048` | 允许工具返回足够长的分析报告或图表数据，避免信息截断。 |
| `data_source_api_endpoint` | 按实测标定 | 对应不同血糖设备厂商的 API 地址，确保数据来源准确性。 |
| `unit_conversion_factor` | `18.01559` 或 `0.0555` | `mg/dL` 到 `mmol/L` 或 `mmol/L` 到 `mg/dL` 的转换因子，确保数值解读一致。 |
| `query_time_range_days` | `7 天` | 提供近一周的血糖趋势分析，平衡历史数据量与即时性。 |
| `max_retries_on_failure` | `3 次` | 应对网络波动或外部 API 临时故障，提高工具调用的鲁棒性。 |

## 容易做错的三处

*   现象：智能客服无法获取最新血糖数据，返回“数据查询失败”或旧数据。原因：`tool_timeout_seconds` 设置过短，外部数据接口在高并发或复杂查询时响应超时。
*   现象：血糖值解读结果出现数量级错误，如 `10 mmol/L` 被误读为 `10 mg/dL`。原因：插件在处理来自不同数据源的血糖值时，未进行单位 `unit` 的校验与标准化转换。
*   现象：高级编排中工具调用返回状态码 `400 Bad Request`。原因：`data_source_api_endpoint` 或其所需的 `authentication_token` 配置有误，导致请求参数不符合外部 API 规范。

## 怎么确认配好了

*   进行端到端测试，模拟用户咨询“我最近的血糖怎么样”，检查返回的血糖值和趋势是否与实际设备数据一致，并核对单位是否正确。
*   在 FastGPT 平台查看工具调用日志，确认 `tool_timeout_seconds` 范围内工具是否成功执行，并且 `response_body` 包含预期的血糖数据字段。
*   针对不同单位的输入（如 `5.5 mmol/L` 和 `99 mg/dL`），测试智能客服的解读结果是否一致且准确，验证单位转换逻辑的有效性。
*   模拟外部数据源接口故障或延迟，观察 `max_retries_on_failure` 配置是否生效，并最终给出合理的失败提示。
