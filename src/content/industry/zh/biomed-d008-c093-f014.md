# 血糖数据解读智能客服的表单与交互

## 这个品类的数据长什么样

血糖数据主要来源于个人血糖仪、连续血糖监测（CGM）设备、以及部分智能穿戴设备。这些数据更新频率较高，尤其CGM设备可实现分钟级甚至秒级的数据采集，形成连续的时间序列。数据文档结构通常包含时间戳、血糖值（mg/dL 或 mmol/L）、事件标记（如餐前、餐后、运动、用药）。部分设备还会记录胰岛素剂量、饮食摄入、运动时长等伴随信息。字段名称和单位存在标准化的趋势，例如 `glucose_level`、`timestamp`，但不同厂商的设备输出格式和字段命名仍有差异，可能涉及 CSV、JSON 或专有二进制格式。

## 这些特征在「表单与交互」这一环带来什么约束

高频更新和时间序列特性要求表单设计能高效处理批量数据上传与实时数据流接入。由于数据格式多样，表单需提供灵活的数据导入选项，例如文件上传、API 对接凭证输入。同时，对事件标记和伴随信息的捕获，意味着表单需要包含结构化的输入字段，辅助用户补充上下文信息，以提高解读的准确性。血糖单位的国际差异（mg/dL 与 mmol/L）要求在交互中提供明确的单位选择或自动识别机制，避免因单位混淆导致误判。此外，数据隐私和敏感性决定了在表单提交与数据处理过程中，必须严格遵循数据安全和合规性要求。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| `UPLOAD_FILE_MAX_SIZE` | `10 MB` | 考虑单个用户上传的血糖数据文件大小，避免过大文件导致上传失败或内存溢出。 |
| `maxContext` | `3000 Tokens` | 确保能够容纳用户上传的近期血糖数据和必要的上下文信息，进行一次完整的解读。 |
| `PARSE_FILE_TIMEOUT_SECONDS` | `60 秒` | 预留充足时间解析各种格式的血糖数据文件，防止因文件复杂或网络延迟导致解析超时。 |
| `similarityThreshold` | `0.75` | 用于匹配用户输入的特定血糖事件或疑问与知识库中的相关解读规则。 |
| `segmentLength` | `800 字符` | 将较长的血糖趋势分析报告或健康建议进行分段，便于模型处理和用户阅读。 |
| `modelTemperature` | `0.3` | 确保血糖解读结果的严谨性和一致性，避免过度发散或产生不准确的建议。 |

## 容易做错的三处

*   上传数据后，智能客服返回“数据格式错误”或“无法识别字段”。原因在于未充分覆盖不同血糖设备导出的数据格式和字段命名，导致解析器无法正确提取关键信息。
*   用户提交了连续血糖数据，但系统仅解读了部分时间段或单一数值。原因在于 `maxContext` 参数设置过小，无法承载完整的历史数据，导致截断或只处理了最新数据。
*   用户输入“胰岛素用量”等信息后，系统未能将其关联到血糖解读。原因在于表单设计未能提供相应的结构化字段或提示，导致用户以自由文本形式输入，模型难以准确捕获并作为上下文。

## 怎么确认配好了

*   上传来自不同品牌血糖仪和CGM设备的真实数据文件，检查系统是否能正确解析并提取所有关键字段和数值。
*   提交包含高频、长周期血糖数据的表单，验证智能客服能否基于完整数据给出连贯的趋势分析和解读。
*   在表单中刻意输入不同单位的血糖值（如 `120 mg/dL` 和 `6.7 mmol/L`），确认系统能否正确识别并转换或提示用户选择单位。
*   模拟用户提出关于餐后血糖、运动后血糖等特定场景的问题，并提供相关伴随信息，检查智能客服是否能结合这些信息进行个性化解读。
