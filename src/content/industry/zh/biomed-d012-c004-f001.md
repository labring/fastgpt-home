# CRO药物警戒的HTTP 接口与外部系统

## 这个品类的数据长什么样

CRO（合同研究组织）在药物警戒领域的数据，主要来源于临床试验、上市后监测、文献回顾以及患者报告等多个渠道。这些数据以结构化和非结构化形式并存，包括患者基本信息、用药史、不良事件描述、严重程度、结局、相关性评估、实验室检查结果以及影像学报告。数据更新频率高，尤其是在临床试验阶段，可能每日或每周都有新的不良事件报告产生。文档结构复杂，涉及 ICH E2B R3 国际标准报告格式、MedDRA 编码术语、WHO-ART 药物字典等。字段众多且专业性强，例如 `AE_TERM`（不良事件术语）、`DRUG_PRODUCT_NAME`（药品名称）、`SERIOUSNESS_CRITERIA`（严重性标准），单位通常是国际标准单位或医学常用单位，例如 `mg`、`ml`、`μg/dL`。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

CRO药物警戒数据的高更新频率和复杂结构，对 HTTP 接口的实时性和数据解析能力提出了较高要求。多种数据来源导致数据格式多样，需要接口支持多种数据类型（例如 JSON、XML，甚至二进制文件）。ICH E2B R3 等国际标准的存在，意味着接口在数据传输和接收时需严格遵循特定 Schema 规范，确保数据完整性和合规性。专业性强的字段和特定的编码体系，要求外部系统在处理这些数据时能够准确映射和解析，避免语义丢失或错误。此外，大量非结构化文本数据，如不良事件描述，需要接口能够高效传输并支持后续的自然语言处理，以提取关键信息。对失败处理机制的要求也更高，确保数据传输中断或解析错误时能够及时重试或告警，防止关键药物警戒信息遗漏。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| `REQUEST_TIMEOUT_SECONDS` | `300 秒` | 应对复杂数据包传输及外部系统处理可能耗时较长的情况。 |
| `MAX_PAYLOAD_SIZE_MB` | `100 MB` | 考虑单个不良事件报告（尤其是包含附件）可能较大，避免因数据包过大导致传输失败。 |
| `CONTENT_TYPE` | `application/json; charset=utf-8` 或 `application/xml` | 适应 ICH E2B R3 标准的 XML 传输，以及其他系统常用的 JSON 格式。 |
| `RETRY_ATTEMPTS` | `3-5 次` | 应对网络瞬时抖动或外部系统短暂不可用，提高数据传输成功率。 |
| `PARSE_SCHEMA_VALIDATION` | 开启 | 强制校验传入数据的结构与 ICH E2B R3 或自定义 Schema 是否一致，确保数据质量。 |
| `ERROR_CALLBACK_URL` | 按实测标定 | 数据传输或解析失败时，及时通知监控系统或人工介入处理。 |

## 容易做错的三处

*   HTTP 请求发送后外部系统长时间无响应，导致连接超时或数据丢失。原因在于未充分考虑外部系统处理复杂数据或网络延迟可能带来的耗时。
*   外部系统返回的状态码是 200，但实际业务数据字段为空或格式错误。原因在于只检查了 HTTP 状态码，未对返回的业务响应体内容进行结构和值的校验。
*   上传文档后，系统长时间显示“索引中”状态，无法正常检索。原因在于上传的文档格式未被正确识别或解析，或者文件内容过大导致处理队列拥堵。

## 怎么确认配好了

*   通过实际发送包含 ICH E2B R3 格式 XML 或复杂 JSON 的请求，检查外部系统是否能正确接收并解析所有关键字段，确认数据完整性。
*   监控 HTTP 接口的响应时间，确保在预期时间内完成数据传输和初步处理，其阈值应根据数据包大小和外部系统处理能力进行设定。
*   在外部系统或日志中，核对传入数据的 `AE_TERM`、`DRUG_PRODUCT_NAME` 等核心字段的值与原始数据是否一致，确保编码和映射无误。
