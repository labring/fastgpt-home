# DTP 药房药物警戒的HTTP 接口与外部系统

## 这个品类的数据长什么样
DTP 药房在药物警戒领域的数据主要来源于患者报告、医生诊断、药师记录以及药品销售与流向数据。患者报告通常通过电话、在线表格或现场反馈，内容包含症状描述、用药情况和个人基本信息。医生和药师的记录则更为结构化，包含诊断编码、药品批次号、用药剂量、不良反应事件（AE）分类和严重程度。药品销售与流向数据则提供药品的流通路径和销售数量，通常以 CSV 或 JSON 格式批量传输。这些数据更新频率较高，不良反应事件可能实时发生并上报，销售数据则通常按日或按周汇总。文档结构方面，患者报告多为非结构化文本，而药师和医生记录则倾向于使用标准化的医学术语和编码，例如 MedDRA 词典进行不良反应事件编码。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
DTP 药房药物警戒的数据特性对 HTTP 接口与外部系统提出了具体约束。非结构化患者报告需要接口支持大文本传输，并要求后端具备自然语言处理能力进行初步解析。实时性要求较高，例如严重不良反应事件报告，意味着接口需要支持高并发、低延迟的数据提交，并可能需要异步处理机制。标准化医学编码的使用，如 MedDRA，要求接口在数据校验时能与外部编码系统进行集成，确保数据准确性和一致性。药品批次号和销售数据涉及大量结构化信息，要求接口支持批处理或流式数据传输，并且字段定义需严格匹配药房管理系统中的库存、销售与追溯数据结构，例如`product_batch_id`、`sale_quantity`等字段。此外，由于涉及患者隐私和敏感医疗信息，接口必须强制使用 HTTPS，并实施严格的身份验证与授权机制，确保数据传输的安全性。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| `HTTP_TIMEOUT_SECONDS` | `60 秒` | 多数不良反应事件上报包含附件或复杂文本，确保数据传输完整性。 |
| `MAX_PAYLOAD_SIZE_MB` | `5 MB` | 考虑患者报告可能包含图片或详细的医生诊断书，避免因体量过大导致接口拒绝。 |
| `CONCURRENT_REQUEST_LIMIT` | `200` | 应对高峰期患者或药师实时上报，确保系统响应能力。 |
| `ERROR_RETRY_COUNT` | `3` | 网络波动或外部系统临时故障时，自动重试以提高数据提交成功率。 |
| `DATA_SCHEMA_VERSION` | `v2.1` | 明确接口数据结构版本，确保与外部系统的数据兼容性，例如 MedDRA 编码版本。 |
| `AUTH_HEADER_TYPE` | `Bearer Token` | 提供基于令牌的认证机制，增强接口安全性，方便权限管理。 |

## 容易做错的三处
*   接口返回 `HTTP 400 Bad Request`，日志显示 `Invalid MedDRA Code`，原因是上报数据中不良反应事件编码与外部字典版本不匹配。
*   大量患者反馈提交失败，系统日志中出现 `HTTP 504 Gateway Timeout`，这通常是由于接口处理时间过长，未能及时响应客户端请求。
*   部分药品销售数据未能在药物警戒平台中更新，检查发现外部系统批量传输时 `product_batch_id` 字段为空，导致数据无法关联。

## 怎么确认配好了
*   模拟提交包含多种数据类型（文本、图片）的不良反应事件报告，检查接口返回 `HTTP 200 OK`，并在平台中确认数据内容完整且字段解析正确。
*   通过压力测试工具模拟高并发请求，观察接口响应时间，确保在预期并发量下响应时间稳定在 `2 秒`以内。
*   定期从外部系统导入一批包含`product_batch_id`、`sale_quantity`等字段的药品销售数据，核对数据在药物警戒平台中的关联性与准确性。
*   检查日志系统，确认在异常情况下（如网络中断或数据校验失败）能够记录 `HTTP 4xx` 或 `HTTP 5xx` 错误码，并触发相应的告警通知。
