# I 期临床药物警戒的HTTP 接口与外部系统

## 这个品类的数据长什么样
I 期临床试验的药物警戒数据主要来源于受试者病例报告表（CRF）、实验室检查结果、影像学报告及随访记录。这些数据通常以结构化或半结构化的形式存在，例如 CSV、JSON 或 XML 文件，也可能存储在临床数据管理系统（CDMS）或电子病历（EHR）中。数据更新频率在试验进行期间较高，可能每日或每周更新，尤其是在出现不良事件（AE）或严重不良事件（SAE）时。关键字段包括受试者 ID、不良事件描述、不良事件发生/结束日期、严重程度、与试验药物的关系、采取的措施、结局等。单位通常为国际标准单位，如实验室指标的 mol/L 或 mg/dL，时间单位为天或小时。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
I 期临床数据来源多样且更新频繁，对 HTTP 接口的实时性与稳定性要求较高。由于不良事件的紧急性，接口需支持高并发数据写入，并能处理大量结构化与半结构化数据。数据文档通常包含详细的元数据定义和字段说明，这要求外部系统在解析时能准确映射和验证数据类型、格式及约束。例如，不良事件的严重程度字段可能采用枚举值，与试验药物关系字段可能为布尔值或分类值。数据量可能在数 GB 到数十 GB 之间，对接口的传输效率和外部存储系统的容量构成挑战。错误处理机制需要细致，因为任何数据丢失或错误都可能对受试者安全和试验结果产生影响。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| `batchSize` | `100–500` 条记录 | 兼顾单次请求负载与处理效率，避免过大请求导致超时 |
| `requestTimeout` | `600` 秒 | 应对数据量较大或网络不稳定的情况，防止请求中断 |
| `maxConnections` | `50` | 保证高并发场景下外部系统能够及时响应，避免连接耗尽 |
| `retryAttempts` | `3` 次 | 应对瞬时网络抖动或外部系统短暂不可用，提高数据传输成功率 |
| `dataEncoding` | `UTF-8` | 确保多语言描述不良事件时字符集兼容性，避免乱码 |
| `parseMode` | `JSON_STRICT` | I 期临床数据结构通常严格，确保数据解析的准确性 |

## 容易做错的三处
*   调用 API 时返回 `400 Bad Request` 错误，常见原因是没有正确处理外部系统要求的特定字段类型或格式，例如日期格式不符合 ISO 8601 标准。
*   数据导入后部分字段为空，原因可能是外部系统接口返回的数据结构与预期的不一致，导致解析器未能正确提取对应字段。
*   API 调用频繁出现 `504 Gateway Timeout`，原因通常是外部系统处理单个请求的时间过长，未能及时响应，或者网络链路存在瓶颈。

## 怎么确认配好了
*   执行一次包含少量不良事件数据的端到端导入测试，检查所有关键字段是否均能正确映射并存储。
*   模拟高并发场景，使用 `batchSize` 和 `maxConnections` 配置下的最大负载进行数据写入，观察是否有 `5xx` 错误或数据丢失。
*   检查外部系统日志，确认数据传输过程中没有出现解析错误或数据验证失败的警告信息。
*   随机抽取导入后的不良事件记录，与原始数据源进行比对，核实数据完整性与准确性，特别关注不良事件描述、严重程度等敏感字段。
