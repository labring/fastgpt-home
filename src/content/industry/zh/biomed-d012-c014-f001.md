# siRNA 核酸药药物警戒的HTTP 接口与外部系统

## 这个品类的数据长什么样

siRNA 核酸药的药物警戒数据主要来自临床试验、真实世界研究、上市后监测报告，以及相关文献数据库。这些数据通常以结构化或半结构化形式存在，包含患者基本信息、用药史、不良事件描述（MedDRA 编码为主）、事件发生时间、严重程度、结局、相关实验室检查结果等。数据更新频率较高，尤其在上市初期和关键临床研究阶段，可能每日或每周都有新数据产生。文档结构上，通常遵循 ICH E2B R3 或 FDA Adverse Event Reporting System (FAERS) 等标准，字段明确且存在大量医学术语。剂量单位常涉及 `mg/kg` 或 `μg/kg`，时间单位精细到 `日`、`小时`，不良反应描述则依赖于统一的医学词典编码。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

siRNA 核酸药数据的高更新频率要求 HTTP 接口具备高效的数据拉取机制，避免因数据陈旧导致预警不及时。其结构化和半结构化并存的特性，意味着接口需要支持多种数据格式，例如 JSON 或 XML，并能有效处理嵌套结构。医学术语的专业性与编码标准（如 MedDRA `26.0` 版本）要求接口在数据传输前进行预处理或在接收端进行严格的校验，以确保数据一致性与准确性。特别的剂量单位与时间精度，对字段的数据类型和长度有严格要求，例如 `dosageValue` 字段需支持浮点数，`eventTimestamp` 字段需包含精确到秒的时间戳。此外，由于数据敏感性，接口的安全认证与授权机制至关重要，常采用 OAuth 2.0 或 API Key 认证，并要求传输加密。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| `requestTimeoutSeconds` | `60 秒` | 处理大数据量或复杂查询时，避免因网络延迟或后端处理时间过长导致请求失败。 |
| `maxConnections` | `10` | 兼顾数据拉取效率与外部系统并发处理能力，避免过载。 |
| `retryAttempts` | `3 次` | 在网络瞬时波动或外部系统短暂不可用时，提高数据获取的成功率。 |
| `pollingIntervalMinutes` | `15 分钟` | 平衡数据实时性需求与外部系统负载，应对较高的数据更新频率。 |
| `responseBodyMaxSizeMB` | `100 MB` | 预留足够的空间处理包含详细医学报告或多条不良事件记录的响应体。 |
| `authHeaderName` | `Authorization` | 遵循业界通用的 HTTP 认证头规范，易于集成和维护。 |

## 容易做错的三处

*   获取数据时 `pageNum` 始终返回相同内容，实际原因是外部接口的缓存机制或参数未正确传递，导致分页逻辑失效。
*   接口调用频繁后出现 `429 Too Many Requests` 错误，原因是没有配置合理的请求间隔或未处理限流响应。
*   接收到的不良事件描述字段为空或乱码，原因是没有正确处理外部接口返回的字符编码或医学编码版本不匹配。

## 怎么确认配好了

*   通过 FastGPT 的接口测试功能，使用测试数据模拟一次完整的 HTTP 请求，检查返回状态码是否为 `200 OK`，并验证关键字段（如 `adverseEventId`、`meddraCode`）是否包含有效数据。
*   在实际运行环境中观察日志输出，核对是否有因 `requestTimeoutSeconds` 或 `retryAttempts` 触发的错误信息，并确认重试机制是否按预期工作。
*   定期比对 FastGPT 中导入的 siRNA 核酸药不良事件数据与外部系统源数据，检查数据完整性、字段映射准确性以及更新频率是否符合预期，例如核对最新事件的 `eventTimestamp`。
*   检查外部系统提供的 API 文档，确认 FastGPT 中配置的 `authHeaderName` 和认证凭据与文档要求一致，确保接口权限正确。
