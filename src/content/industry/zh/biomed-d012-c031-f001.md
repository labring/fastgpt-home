# 医保准入药物警戒的HTTP 接口与外部系统

## 这个品类的数据长什么样

医保准入相关的药物警戒数据主要来源于国家医保局、省级医保中心发布的官方文件、药品目录更新公告，以及药企提交的医保谈判材料。这些数据通常以结构化（如 XML、JSON）或半结构化（如 PDF 表格、Excel）的形式发布。更新频率受政策调整和谈判周期影响，通常为每年一次大范围更新，季度或月度会有局部调整和增补。文档结构复杂，包含药品名称、通用名、剂型、规格、医保支付标准、支付范围、限制条件、以及不良反应监测要求等字段。单位涉及金额（元）、剂量（mg、μg）、频次（次/日）、时长（月、年）等，且不同来源可能存在单位不统一的情况，例如支付标准可能以“元/单位”或“元/疗程”表示。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

医保准入数据的复杂性和多源性，对 HTTP 接口与外部系统集成提出了特定要求。首先，数据来源多样决定了需要配置多个外部系统连接器，以适配不同的数据格式和认证机制。例如，获取官方公告可能需要解析网页内容或下载文件，而对接药企系统则可能涉及特定的 API 密钥认证。其次，年度或季度更新频率意味着系统需支持定时任务或事件触发机制，以确保数据同步的及时性，避免使用过时医保政策进行判断。再次，文档结构复杂且单位不统一，要求接口返回的数据在进入工作流前进行严格的标准化和清洗。例如，对于支付标准，需要统一转换为“元/单位”进行计算，才能在后续的药物警戒规则中进行比对。字段名可能存在差异，例如“药品名称”与“通用名”可能在不同来源中互换使用，需要映射处理。

## 配置怎么定

| 配置项                   | 建议取法                               | 这样取的依据                                                                                             |
| :----------------------- | :------------------------------------- | :------------------------------------------------------------------------------------------------------- |
| `requestTimeout`         | `60000 毫秒`                           | 应对医保系统可能存在的响应延迟，确保数据完整获取。                                                       |
| `maxRetries`             | `3`                                    | 应对网络波动或外部系统临时故障，提高数据获取成功率。                                                     |
| `responseSchema`         | 严格定义 JSON Schema 或 XML Schema     | 确保返回数据结构符合预期，便于后续解析和标准化处理。                                                     |
| `dataNormalizationScript`| 按实测标定                             | 统一不同来源的单位和字段命名，例如将“元/疗程”转换为“元/单位”。                                         |
| `authenticationMethod`   | `API Key` 或 `OAuth 2.0`               | 适配医保数据提供方要求的安全认证机制，保障数据访问权限。                                                 |
| `updateTrigger`          | `cron: "0 0 1 * *"` (每月1日0点触发)   | 满足医保政策通常的月度或季度更新周期，确保数据及时性。                                                   |

## 容易做错的三处

*   HTTP 请求返回 403 状态码，或返回内容提示“权限不足”。这通常是由于 `authenticationMethod` 配置错误，或 `API Key` 过期、未正确传递导致。
*   工作流中解析到的医保支付标准为空，或数值异常。这往往是 `responseSchema` 未能准确匹配返回数据结构，或 `dataNormalizationScript` 未能正确处理不同单位和字段名导致的。
*   定时任务触发后，数据长时间未更新，或更新的数据量远小于预期。这可能是 `requestTimeout` 设置过短，导致大文件下载或复杂查询未能在规定时间内完成，也可能是外部系统接口返回了分页数据，但未实现完整的分页循环获取。

## 怎么确认配好了

*   手动触发一次 HTTP 请求，核对返回的原始数据与预期官方文档内容一致，特别是关键字段如 `支付标准` 和 `限制条件`。
*   在工作流中运行一个包含该 HTTP 接口的测试流程，检查 `dataNormalizationScript` 处理后的输出，确认所有单位和字段已按规则统一。
*   配置一个计划任务（例如 `cron` 表达式 `0 0 1 * *`），待其首次执行后，比对外部系统数据与 FastGPT 知识库中的数据，确保数据同步无误且完整。
