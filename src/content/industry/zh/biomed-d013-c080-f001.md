# 眼科质量文档的HTTP 接口与外部系统

## 这个品类的数据长什么样

眼科质量文档主要包括临床试验方案、研究者手册、知情同意书、不良事件报告、SOP（标准操作规程）以及各种法规符合性文件。这些文档通常以 PDF、Word 或结构化 XML 格式存在，由医院信息系统（HIS）、临床试验管理系统（CTMS）或电子数据采集系统（EDC）生成。更新频率取决于临床试验阶段或法规变更，可能从每周数次到每季度一次不等。文档内容高度专业化，包含大量医学术语、剂量单位（如 `mg/kg`、`IU`）、时间点（如 `D1`、`W4`）、检查结果（如 `视力 0.8`、`眼压 15 mmHg`）及图表数据。字段通常包括患者 ID、试验编号、药物名称、诊断代码、不良事件描述等，格式严格遵循 ICH-GCP 等国际规范。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

眼科质量文档的专业性和结构化要求，对 HTTP 接口的数据传输格式和校验提出了高标准。由于文档包含敏感患者信息，接口必须支持 HTTPS 加密，并可能需要 OAuth 2.0 或 API Key 进行认证授权。其更新频率和文件大小（单个 PDF 可能达数十 MB）要求接口具备高效的文件上传和下载能力，并能处理大文件分片传输。文档中的专业医学术语和单位，意味着外部系统在解析和处理数据时，需要精确的正则表达式或特定解析库来提取关键信息，避免因单位混淆（如 `mg` 和 `µg`）导致的数据错误。此外，为了确保合规性，接口调用日志必须详细记录请求来源、时间戳和操作类型，以便追溯。长文本内容的准确分段与向量化，也对外部系统的数据预处理能力形成挑战。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| `UPLOAD_FILE_MAX_SIZE` | `100 MB` | 考虑单个眼科临床试验方案或研究者手册可能较大，预留充足上传空间。 |
| `maxContext` | `3000 tokens` | 确保能够完整捕获眼科文档中一段关键描述的上下文信息，避免语义丢失。 |
| `PARSE_FILE_TIMEOUT_SECONDS` | `600 秒` | 处理复杂 PDF 文档的 OCR 和内容解析可能耗时较长，防止因超时导致失败。 |
| `分段长度` | `500 字符` | 眼科文档专业术语多，保证每个分段包含足够语境，同时避免过长影响检索效率。 |
| `召回条数` | `前 8 条` | 提升检索相关性，覆盖更多潜在相关的眼科临床细节或法规条款。 |
| `相似度阈值` | `0.75` | 平衡召回率与准确率，确保检索结果与查询的眼科问题高度相关。 |

## 容易做错的三处

*   现象：HTTP 接口返回 `401 Unauthorized` 或 `403 Forbidden`。
    原因：外部系统调用时未提供正确的 `Authorization` 头或 API Key，或者 IP 地址不在白名单范围内。
*   现象：上传 PDF 文件后，知识库中部分关键信息缺失或乱码。
    原因：文件解析器对特定格式的眼科文档（如扫描件或包含复杂表格的 PDF）识别能力不足，导致 OCR 错误或结构化信息提取失败。
*   现象：对话中引用的眼科术语或剂量单位与原文不符。
    原因：外部系统在处理文本时，对专业医学词汇和数值单位的标准化或实体识别不够精确，导致信息转换错误。

## 怎么确认配好了

*   上传一份典型的眼科临床试验方案 PDF 文件，检查知识库中是否完整且准确地提取了所有章节标题、关键数据（如 `患者入组标准`、`主要终点指标`）和表格内容。
*   使用包含特定眼科疾病名称、药物剂量或检查结果的查询语句，测试知识库的召回能力，并验证返回的文档片段是否准确、相关。
*   模拟外部系统通过 HTTP 接口上传一个大型眼科文档（例如 50 MB），检查接口响应时间是否在可接受范围内，以及上传进度和状态码是否正确。
*   检查系统日志，确保所有外部接口调用都有详细的请求信息、响应状态码和处理时间记录，以便于审计和问题追溯。
