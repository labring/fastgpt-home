# 眼科质量文档的工具调用与插件

## 这个品类的数据长什么样
眼科质量文档的数据主要来源于临床试验记录、药品生产批记录、器械验证报告及上市后不良事件监测报告。其更新频率受研发进展、法规要求和产品生命周期影响，通常为季度或年度更新，但临床试验数据可能日更或周更。文档结构规范，多采用 ICH 指导原则或 FDA 指引的模板，包含标题、版本号、修订历史、目的、范围、责任人、操作步骤、结果记录、偏差处理等固定章节。字段方面，常涉及患者 ID、试验药物批次号、检测指标（如眼压、视力）、计量单位（mmHg、LogMAR、IU）、统计学参数、以及符合性判断。

## 这些特征在「工具调用与插件」这一环带来什么约束
眼科质量文档的规范性和结构化特征，对工具调用与插件提出了明确要求。文档中大量的专业术语和计量单位，要求插件具备精准的语义理解能力，避免误读或混淆。例如，`LogMAR` 视力与普通小数视力的转换，需要特定插件处理。批次号、患者 ID 等敏感信息的处理，则要求插件在数据脱敏和权限控制上具备高安全性。更新频率的不一致性，意味着工具调用需要支持多源数据的同步与合并，并能处理版本冲突。此外，法规遵循的严格性，要求工具调用与插件能追溯数据来源和处理过程，确保合规性。文档间的逻辑关联性，例如临床批记录与对应的生产批记录，需要插件能够进行跨文档的关联查询和验证。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| `toolCallTimeout` | `60 秒` | 眼科领域工具调用可能涉及复杂计算或数据库查询，需预留足够时间，避免因超时中断。 |
| `maxToolOutputTokens` | `2000 词元` | 质量文档的查询结果可能包含详细的报告摘要或数据表格，需支持较长的输出以保持完整性。 |
| `pluginSchemaVersion` | `v1.2` 或更高 | 确保支持最新的安全特性和数据类型定义，以应对眼科数据复杂性。 |
| `retrievalTopK` | `5` | 针对特定质量文档的检索，通常需要精准匹配少量高相关性结果，避免无关信息干扰。 |
| `contextWindow` | `8000 词元` | 眼科质量文档上下文关联性强，需要更大的上下文窗口以理解文档间的逻辑关系和背景信息。 |
| `enableSQLInjectionProtection` | `true` | 数据库查询插件必须开启，防止恶意 SQL 注入，保护敏感的临床与生产数据。 |

## 容易做错的三处
*   工具调用返回 `500 Internal Server Error`，日志显示数据库连接超时。这通常是由于 SQL 语句中包含复杂的联表查询或大数据量统计，导致数据库执行时间过长，超出了工具调用设定的 `toolCallTimeout` 限制。
*   大模型在生成回复时未引用网络搜索插件的结果，即使网络搜索插件已成功返回内容。这可能由于网络搜索插件返回的 `relevanceScore` 过低，未达到大模型判断为可引用内容的阈值，或者返回结果的 `format` 不符合大模型预期。
*   插件开发时，JSON 输入框中无法正确引用变量，导致测试时参数传递失败。这是因为 JSON 输入框的设计主要用于固定结构的数据输入，不支持动态变量的直接嵌入，需要通过预处理或模板渲染机制来构建完整的 JSON 结构。

## 怎么确认配好了
*   执行针对不同批次号的查询，检查返回结果中批次信息与原始文档是否一致，并核对关键指标的单位是否正确。
*   模拟一次包含敏感信息的查询，确认工具调用返回结果中敏感数据是否已按预期进行脱敏处理。
*   测试插件在处理异常输入（如不合规的日期格式、超出范围的数值）时的表现，确认其错误处理机制是否能给出清晰的提示或报错信息。
*   针对一份包含多版本修订的文档，验证工具调用能否正确识别并引用最新版本的内容，同时也能查询到历史版本的数据。
