# 远程医疗质量文档的HTTP 接口与外部系统

## 这个品类的数据长什么样
远程医疗的质量文档主要包括电子病历、诊断报告、治疗方案、远程会诊记录、患者反馈以及医疗设备操作规程等。这些数据往往分散在不同的医疗信息系统（如 HIS、EMR、PACS）中。数据更新频率相对较高，尤其是患者诊疗记录，可能实时产生。文档结构上，既有结构化的数据字段（如诊断代码 ICD-10、药品编码），也有大量的非结构化文本（如医生手写病程记录、会诊意见）。字段单位涉及医学计量单位，如 `mg`、`ml`、`mmHg`，以及时间戳格式 `YYYY-MM-DD HH:MM:SS`。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
远程医疗质量文档的数据源多样性，要求 HTTP 接口具备灵活的数据源集成能力，能够对接不同医疗系统提供的 API。实时性需求意味着接口调用频率可能较高，需要考虑并发处理和响应速度。非结构化文本的存在，增加了数据预处理的复杂性，可能需要在接口调用后进行额外的文本清洗和结构化提取。医学专业字段和单位的特殊性，要求接口在数据传输和解析时，能正确识别和处理这些信息，避免因单位转换或字段误解导致的数据错误。此外，患者隐私保护和数据安全是核心考量，接口设计必须符合 HIPAA 或 GDPR 等法规要求，确保数据传输的加密和访问控制。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| `apiBaseUrl` | 医疗系统实际 API 网关地址 | 确保请求发送到正确的后端服务 |
| `requestTimeout` | `60 秒` | 远程医疗数据量可能较大，避免因网络延迟或处理时间过长导致超时 |
| `maxRetries` | `3` | 应对临时网络抖动或后端服务短暂不可用，提高接口调用成功率 |
| `headers` | `Authorization: Bearer <token>` | 医疗系统通常采用 OAuth2 或 JWT 进行身份验证，保障数据安全 |
| `responseSchema` | JSON Schema 定义 | 确保接收到的数据结构符合预期，便于后续解析和处理 |
| `dataPollingInterval` | `300 秒` 或按实测标定 | 根据远程医疗数据更新频率和业务需求，平衡数据实时性与系统负载 |

## 容易做错的三处
*   调用 API 后返回 `401 Unauthorized` 或 `403 Forbidden`：通常是由于 `Authorization` 头中携带的 `token` 过期、无效，或请求的账户没有足够的权限访问目标资源。
*   接口调用成功但返回数据字段为空或格式错误：原因可能是 `responseSchema` 未正确定义，导致解析器无法匹配返回的 JSON 结构，或者后端服务返回的数据与约定不符。
*   请求频繁被拒绝或出现 `429 Too Many Requests`：医疗系统 API 可能有调用频率限制，未进行适当的请求间隔控制或限流处理导致。

## 怎么确认配好了
*   使用 Postman 或 curl 工具，携带配置的 `apiBaseUrl`、`headers` 和 `payload`，手动调用一次接口，确认能够成功获取到预期格式的数据。
*   在 FastGPT 内部配置完成后，执行一次数据同步或调用测试，检查日志输出，确认没有出现 `HTTP 5xx` 错误码或连接超时信息。
*   检查知识库中导入的文档内容，验证从外部系统获取的关键字段（如患者 ID、诊断结果、治疗日期）是否正确解析并存储，且单位无误。
*   模拟高并发场景，观察接口调用成功率和响应时间，确保在预期负载下系统稳定运行，响应时间在可接受的阈值内。
