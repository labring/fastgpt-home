# 学位授予与证书信息报送的问答受理与缺项补问：HTTP 接口

## 这个品类的数据长什么样

本页围绕学位授予与证书信息报送的问答受理与缺项补问，材料来源为培养单位提交的学位申请表、论文评阅书、答辩决议，以及随附的回执与签字页。更新节奏按批次报送推进，每轮受理后先做缺项识别，再生成补齐的问项。三类材料各自角色不同：学位申请表提供申请人身份、学科与拟授学位字段；论文评阅书提供评阅结论、评阅人与评阅日期；答辩决议提供答辩结论、表决结果、主席签字与决议日期。字段特征集中在名称、数量、日期与签字四类，同一记录在三份材料中需保持指向一致。材料进入该功能时，先由工作流里的 HTTP 节点把已抽取字段发往外部系统做校验，返回的缺项清单再转成追问内容，受理记录与补齐的问项由后续节点解析响应，或外部系统按约定处理接着完成。

## 配置怎么定

这一环由工作流里的 HTTP 节点执行，输出响应体、状态码与返回字段。受理记录与补齐的问项由后续节点解析响应，或外部系统按约定处理接着完成。路径参数、请求体与请求头三处都能用变量占位，变量来自全局变量、系统变量或前方节点输出。

| 对象 | 判断 | 核验动作 |
| --- | --- | --- |
| 学位申请表 | 身份、学科、拟授学位字段是否齐全，日期与签字是否到位 | 核字段名与取值来源，比对签字页与回执是否随附 |
| 论文评阅书 | 评阅结论、评阅人、评阅日期是否与申请表指向同一记录 | 核名称、数量、日期三处是否对得上，检查版本是否同步 |
| 答辩决议 | 答辩结论、表决结果、主席签字与决议日期是否完整 | 核决议日期与评阅日期先后关系，检查缺签字或回执情形 |
| HTTP 请求 | 占位变量能解析成实际值，鉴权信息按外部系统要求传入 | 在请求预览里看渲染后的完整地址，核对请求头名称与取值来源 |

## 容易做错的三处

- 现象：同一申请人的名称在学位申请表与论文评阅书中写法不一致。原因：两份材料由不同环节录入，未做名称归一与交叉比对。
- 现象：答辩决议的日期早于论文评阅书日期，或版本未同步。原因：材料分批上传，旧版本覆盖新版本，日期字段未做先后校验。
- 现象：外部系统收到空字段，或缺签字与回执仍进入受理。原因：请求体字段与外部接口约定不一致，签字页未纳入必填校验。

## 怎么确认配好了

本功能验收：预览渲染后的请求，核状态码与返回字段，再对一条样例比对结果；用 `variables` 核每个占位的来源，用 `responseData` 核返回字段结构，用 `Authorization` 核鉴权信息是否按外部系统要求传入。

业务测试：提一个缺关键信息的问句，看是否先追问再作答。

- 在变量面板核对每个占位的来源，确认路径参数、请求体与请求头三处变量都能追到全局变量、系统变量或前方节点输出。
- 用一条样例请求比对返回，核请求体字段与外部接口约定一致，并记录引用文本的 tokens 与数组条数。
