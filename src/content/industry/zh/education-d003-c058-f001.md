# 科研项目任务书签订的问答受理与缺项补问：HTTP 接口

## 这个品类的数据长什么样

科研项目任务书签订场景下，进入本功能的材料包括项目任务书、课题任务分解表、预算书。项目任务书通常由牵头单位在立项批复后起草，字段含项目名称、编号、承担单位、起止日期、签字栏；课题任务分解表由各课题负责人填报，字段含课题名称、负责人、参与人、任务节点；预算书由财务或预算编制人汇总，字段含科目名称、金额、来源、年度。三类材料更新节奏不同：任务书随签订流程流转，分解表随课题调整，预算书随经费下达或调整。材料进入问答受理与缺项补问功能时，任务书作为主记录，分解表与预算书作为交叉核对依据，用于识别同一记录在两份材料里的名称、数量、日期是否对得上，以及版本、签字与回执是否齐全。

## 配置怎么定

这一环由工作流里的 HTTP 节点执行，输出响应体、状态码与返回字段。受理记录与补齐的问项由后续节点解析响应，或外部系统按约定处理接着完成。HTTP 节点只向目标地址发请求，不代替外部系统写库或审批。

| 对象 | 判断 | 核验动作 |
| --- | --- | --- |
| 项目任务书 | 项目名称、编号、承担单位、起止日期、签字栏是否齐全且与立项批复一致 | 核对任务书字段与日期，检查签字与回执；在变量面板追溯每个占位的来源 |
| 课题任务分解表 | 课题名称、负责人、任务节点与任务书主记录是否对得上 | 比对分解表与任务书中的名称、数量、日期；核对 `variables` 占位是否解析成实际值 |
| 预算书 | 科目名称、金额、来源、年度与任务书、分解表是否一致 | 比对预算书与另两份材料的名称、数量、日期；在请求预览里看渲染后的完整地址 |
| HTTP 请求 | 请求头鉴权信息、请求体字段与外部接口约定一致 | 核对 `Authorization` 请求头名称与取值来源，用一条样例请求比对 `responseData` 返回字段 |

## 容易做错的三处

- 现象：同一记录在任务书与分解表里的名称、数量、日期对不上。原因：两份材料分别填报，未做交叉核对。
- 现象：预算书版本未同步，金额与科目仍为旧版。原因：经费调整后只更新一处，未回写另一处。
- 现象：任务书缺签字或回执，流程仍继续。原因：缺项识别未覆盖签字栏与回执字段。

## 怎么确认配好了

本功能验收：预览渲染后的请求，核状态码与返回字段，再对一条样例比对结果；检查 `Authorization`、`variables`、`responseData` 是否按约定出现。

业务测试：提一个缺关键信息的问句，看是否先追问再作答。

- 在变量面板核对每个占位的来源，确认来自全局变量、系统变量或前方节点输出。
- 用一条样例请求比对返回字段，确认请求体字段与外部接口约定一致。
