# 研究生招生复试录取的资料版本与变更维护：HTTP 接口

## 这个品类的数据长什么样

本页聚焦研究生招生复试录取品类下的资料版本与变更维护，涉及复试方案、考生成绩表、调剂名单三类材料。复试方案通常由招生单位按年度发布，含流程、时间节点与评分规则；考生成绩表来自初试与复试评分记录，字段含考生编号、科目、成绩、日期；调剂名单由调剂系统导出，含考生编号、原报考单位、拟录取专业、签字栏。这些材料在 HTTP 接口与外部系统功能中，复试方案作为规则基准进入请求体供外部系统校验，考生成绩表与调剂名单作为数据载荷通过路径参数与请求头传递。更新节奏随招生批次推进，字段特征为日期、数量、名称、签字与回执需跨材料一致。

## 配置怎么定

这一环由工作流里的 HTTP 节点执行，输出响应体、状态码与返回字段。版本台账与变更记录由后续节点解析响应，或外部系统按约定处理接着完成。

| 对象 | 判断 | 核验动作 |
| --- | --- | --- |
| 复试方案 | 方案中的日期、流程节点与签字要求需与当年招生批次一致 | 在请求预览里核对渲染后的完整地址与请求体字段，确认方案版本号与引用出处 |
| 考生成绩表 | 同一考生编号在成绩表与调剂名单中的姓名、数量、日期需对得上 | 用一条样例请求比对返回，核对 `variables` 中每个占位的来源与取值 |
| 调剂名单 | 名单中的拟录取专业、原报考单位与签字回执需与方案约定一致 | 核对请求头名称与取值来源，确认 `Authorization` 按外部系统要求传入 |
| 版本台账 | 现行版本唯一，旧版可追，引用同步更新 | 改一处内容后，在变量面板核对 `responseData` 返回字段与引用是否同步 |

## 容易做错的三处

- 现象：同一考生在成绩表与调剂名单里的姓名、数量或日期对不上。原因：两份材料各自维护，未以现行版本为唯一基准做交叉核对。
- 现象：复试方案更新后，外部系统仍按旧版字段处理。原因：版本未同步，请求体与请求头未随现行版本调整。
- 现象：调剂名单缺少签字或回执，外部系统仍返回成功。原因：请求体未包含签字字段，后续节点未解析响应中的缺失标记。

## 怎么确认配好了

本功能验收：预览渲染后的请求，核状态码与返回字段，再对一条样例比对结果；确认 `Authorization`、`variables`、`responseData` 三处占位可追。

业务测试：改一处内容，看版本号与引用是否同步更新。

- 在变量面板核对每个占位的来源，确认请求地址、请求头与请求体中的变量均能解析成实际值。
- 用一条样例请求比对返回，核对字段与外部接口约定一致，并记录数组条数与引用文本的 tokens 预算。
