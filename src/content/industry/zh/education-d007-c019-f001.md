# 选课排课与教室资源调度的异常追溯与人工复核：HTTP 接口

## 这个品类的数据长什么样

选课排课与教室资源调度场景中，材料分为开课计划、排课表、选课规则三类。开课计划由教务端生成，含课程名称、课程代码、开课学期、计划人数与审批签字；排课表由排课端产出，含课程名称、上课时间、教室编号、周次与调停课回执；选课规则由选课端维护，含选课轮次、容量上限、优先级字段与生效日期。三类材料按学期批次更新，调停课与补退选阶段会追加版本。材料进入 HTTP 接口与外部系统对接时，开课计划充当基准源，排课表充当执行记录，选课规则充当约束条件，三者字段需在名称、数量、日期与签字上互相印证，异常追溯时按记录标识回查原始材料。

## 配置怎么定

这一环由工作流里的 HTTP 节点执行，输出响应体、状态码与返回字段。「异常清单与复核结论」由后续节点解析响应，或外部系统按约定处理接着完成。

| 对象 | 判断 | 核验动作 |
| --- | --- | --- |
| 开课计划 | 课程名称、课程代码、计划人数、开课学期与审批签字是否与排课表逐项对应 | 取一条开课计划记录，比对排课表里的课程名称、人数与日期，核对签字栏 |
| 排课表 | 上课时间、教室编号、周次与调停课回执是否与选课规则日期一致 | 抽取同一课程在两份材料里的日期与教室字段，核对回执编号 |
| 选课规则 | 选课轮次、容量上限、优先级字段与生效日期是否版本同步 | 比对规则版本号与生效日期，确认无旧版本残留 |
| 请求地址与路径参数 | 占位变量能解析成实际值 | 在请求预览里看渲染后的完整地址 |

## 容易做错的三处

- 现象：同一课程在开课计划与排课表里的名称或人数对不上。原因：两份材料由不同节点写入，未按同一记录标识回查。
- 现象：选课规则已更新，排课表仍引用旧版本日期。原因：版本未同步，HTTP 请求体字段取自过期变量。
- 现象：调停课记录缺签字或回执。原因：外部系统未按约定回传确认字段，后续节点无法解析。

## 怎么确认配好了

本功能验收：预览渲染后的请求，核状态码与返回字段，再对一条样例比对结果；检查 `Authorization` 请求头、`variables` 变量来源与 `responseData` 返回字段是否一致。

业务测试：造一条异常记录，看能否追到源头材料

- 在变量面板核对每个占位来源，确认 `variables` 能追到全局变量、系统变量或前方节点输出
- 用一条样例请求比对返回体，核对 `responseData` 字段与外部接口约定是否一致
