# 多应用路由一体化 AI 平台的数据库与运维

## 这个品类的数据长什么样
多应用路由的数据主要来源于两类：一是管理后台配置的路由规则条目，二是调用过程中生成的运行日志。数据更新节奏分为两类：路由规则在用户手动修改或定时同步时更新，运行日志在每次调用完成后实时写入。单条路由数据的文档结构包含唯一标识字段`route_id`、来源应用标识`source_app_id`、目标应用ID列表`target_app_list`、负载均衡类型`load_balance_type`、权重配置`weight_map`、更新时间戳`update_time`。其中`target_app_list`为数组类型，元素单位为应用ID字符串，`update_time`的单位为毫秒。

## 这些特征在「数据库与运维」这一环带来什么约束
路由规则的实时更新要求数据库支持原子性修改操作，避免多用户同时修改同一条规则时出现数据冲突。运行日志的实时写入需要数据库具备高并发写入能力，防止调用高峰期出现日志丢失。数组类型的`target_app_list`字段要求数据库支持嵌套数据结构查询，否则无法高效筛选符合条件的路由规则。同时，金融场景下的日志留存需匹配合规周期，因此需要配置合理的日志归档与清理策略，避免数据库存储空间溢出。此外，路由数据的查询频率较高，需配置缓存机制降低数据库的直接查询压力。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `ROUTE_RULE_CACHE_EXPIRE` | `180–300 秒` | 路由规则变更频率较低，缓存可降低数据库查询开销，同时保证规则更新后在合理时间内生效 |
| `LOG_RETENTION_DAYS` | `90 天` | 匹配金融行业合规性日志留存要求，避免数据存储过载 |
| `MAX_ROUTE_PARALLEL` | `8–12 并发` | 适配单路由关联目标应用的并发承载上限，防止数据库连接池耗尽 |
| `DB_CONNECTION_POOL_SIZE` | `20–30 个` | 平衡数据库读写性能与资源占用，适配多应用路由的并发调用需求 |
| `ROUTE_INDEX_FIELD` | `source_app_id, load_balance_type` | 为高频查询字段创建索引，提升路由规则筛选效率 |

> 本页给出的参数取值均为常规建议，用于确定配置的起点。实际取值受材料形态、数据量与业务规则影响，具体问题需具体分析，建议在自有样本上实测后再定。

## 容易做错的三处
- 现象：本地部署后登录异常，日志显示`Connection refused`错误。原因：未正确配置多应用路由关联的数据库连接参数，未验证数据库服务的网络连通性。
- 现象：调用路由时无法获取sourceid关联的匹配数据，返回`null`结果。原因：未为`source_app_id`字段创建数据库索引，导致查询无法快速匹配目标路由规则。
- 现象：手动修改路由规则后，新规则未立即生效。原因：未合理设置`ROUTE_RULE_CACHE_EXPIRE`参数，缓存过期时间过长，导致旧规则仍被读取。

## 怎么确认配好了
- 登录管理后台，查看路由配置列表，确认每条规则的`route_id`、`source_app_id`、`target_app_list`等字段均已正确填写并保存。
- 执行一次测试调用，查看数据库日志或监控面板，确认`route_log`集合中生成了包含完整字段的调用记录。
- 模拟10次并发调用，查看数据库连接数监控，确认未超出`DB_CONNECTION_POOL_SIZE`的设置值。
- 手动修改一条路由规则的`weight_map`字段，等待缓存过期后再次调用，确认新的权重配置已生效。
