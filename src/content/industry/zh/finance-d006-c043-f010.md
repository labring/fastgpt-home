# 商业地产投研知识库建设的数据库与运维

## 这个品类的数据长什么样
商业地产投研数据来源包括各地住建部门公开的不动产登记数据、商业运营商内部运营系统、第三方市场调研机构报告、土地交易平台出让信息。更新节奏分层：基础项目信息更新周期较长，租赁、租金等运营数据按月度更新，竞品动态按季度更新，突发招商调整、政策变动实时更新。数据包含结构化运营台账、半结构化可研报告、非结构化区位图与招商手册，单份结构化文档行数可达数千行，非结构化文档单篇最长可达数十万字，字段涵盖总可租赁面积、月均租金单价、项目开业时间等，单位包含平方米、元/平方米/月、日期等。

## 这些特征在「数据库与运维」这一环带来什么约束
多类型数据并存，需同时支持关系型结构化查询与向量检索，数据库选型需兼顾结构化存储与向量索引能力。数据更新节奏分层，需配置冷热数据分离策略，避免热数据查询被冷数据写入占用资源。单文档体量差异大，需配置合理的分块与分页规则，防止单次查询返回数据过载。专业字段与单位较多，需在数据库层面配置字段校验规则，确保数据录入一致性。实时更新的招商数据需低延迟写入接口，避免影响常规投研查询的性能。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `db_connection_pool_size` | `20–30` | 商业地产投研工作流常需同时发起多组关联查询，该参数控制数据库连接池上限，避免连接耗尽影响并发 |
| `POSTGRES_MAX_CONNECTIONS` | `150–200` | PostgreSQL用于存储结构化的租金、招商台账数据，多工作流并发时需足够连接数支撑批量查询 |
| `mongo_vector_index_dim` | `1536` | 商业地产的区位、报告文本多采用通用嵌入模型，1536维向量可兼顾检索精度与存储成本 |
| `PARSE_FILE_CHUNK_SIZE` | `800–1200 字符` | 商业地产可研报告单段内容较长，该参数控制分块长度，避免分块过碎导致语义断裂或过粗导致检索精度下降 |
| `db_query_timeout` | `600 秒` | 批量查询大型招商台账时，需足够超时时间避免中途中断，适配商业地产数据体量较大的特征 |
| `cold_data_retention_days` | `365 天` | 基础项目信息属于冷数据，超过一年的历史数据可迁移至归档存储，降低主库负载 |

> 本页给出的参数取值均为常规建议，用于确定配置的起点。实际取值受材料形态、数据量与业务规则影响，具体问题需具体分析，建议在自有样本上实测后再定。

## 容易做错的三处
- 现象：批量执行数据库查询组件时，上一步输出为列表格式，但执行后无返回结果。原因：未配置`db_batch_process_threshold`参数，当列表元素数量超过数据库单次查询上限时，任务被静默截断或阻塞。
- 现象：数据库连接调试时返回`Access denied for user`报错。原因：未正确配置数据库访问白名单，或未为FastGPT服务账号授予对应数据库的读写权限。
- 现象：多轮投研查询出现明显延迟，数据库性能监控显示CPU或IO占用过高。原因：未配置冷热数据分离策略，冷数据与热数据混合存储导致查询资源竞争。

## 怎么确认配好了
- 发起一次包含多组关联查询的测试工作流，观察数据库连接池的占用情况，确认连接数未达到配置上限。
- 导入一份商业地产可研报告，检查分块后的文档片段语义完整性，确认分块长度符合业务需求。
- 查看数据库性能监控面板，确认热数据查询的响应时间符合预设标准，冷数据迁移任务按时执行。
- 调试数据库连接组件，使用测试账号发起读写操作，确认权限配置正确，无访问报错。
