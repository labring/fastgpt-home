# 酒店餐饮投研知识库建设的数据库与运维

## 这个品类的数据长什么样
酒店餐饮投研的数据来源包含多类渠道：行业协会发布的区域客流、坪效统计报告，第三方点评平台的门店客评与评分数据，食材供应商的每日报价单，品牌公开的季度财报片段，以及门店上传的菜单、营业日报等内部运营数据。数据更新节奏差异明显：食材报价每日更新，客流统计按周更新，财报按季度更新，客评与营业日报实时更新。数据结构包含结构化表格（如单店营收明细，含门店ID、城市、坪效、客单价等字段）、非结构化文本（客评汇总）与图片（门店实景、菜单图片），字段单位多为元、平方米、人等通用计量标准。

## 这些特征在「数据库与运维」这一环带来什么约束
多源且更新频率不一的数据，要求数据库运维支持增量同步与多源适配，避免全量同步占用过多资源。结构化与非结构化混合的数据类型，要求数据库同时支持文档存储与二进制文件存储，需单独配置图片等二进制数据的存储路径。数据的实时性与历史查询需求，要求运维策略保留至少90天的全量数据快照，同时优化索引以加速历史投研查询。门店数量增长带来的数据量扩张，要求数据库配置分片集群以应对持续增长的存储与查询压力，避免单节点过载。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `MONGODB_CONNECT_TIMEOUT_MS` | 30000–60000 毫秒 | 适配多源数据同步的延迟波动，避免频繁超时中断同步任务 |
| `DATA_SYNC_INTERVAL` | 15 分钟–1 小时 | 覆盖食材报价日更、客流周更的不同更新节奏，平衡实时性与资源占用 |
| `UPLOAD_ALLOWED_MIME_TYPES` | `image/jpeg,image/png,text/plain,application/json` | 适配菜单图片、营业报表、结构化营收数据的上传需求 |
| `PARSE_DOCUMENT_MAX_LENGTH` | 50000 字符 | 处理长文本的行业财报或多门店客评汇总数据 |
| `DB_BACKUP_RETENTION_DAYS` | 90 天 | 满足投研的历史数据查询与合规留存需求 |
| `ENABLE_INCREMENTAL_SYNC` | 开启 | 减少全量同步的资源消耗，适配多源数据的增量更新特征 |

> 本页给出的参数取值均为常规建议，用于确定配置的起点。实际取值受材料形态、数据量与业务规则影响，具体问题需具体分析，建议在自有样本上实测后再定。

## 容易做错的三处
- 现象：本地开发环境执行`pnpm dev`时提示MongoDB连接超时，控制台返回`ETIMEDOUT`状态码。原因：未调整`MONGODB_CONNECT_TIMEOUT_MS`参数，默认值过短无法适配多源数据同步的延迟。
- 现象：调用模型查询数据库时，平台显示的token消耗与API后台统计数值不一致，差值集中在图片查询场景。原因：未配置`INCLUDE_IMAGE_TOKEN`参数，未将图片的base64编码开销计入token统计范围。
- 现象：尝试通过数据库查询返回jpg图片时，模型输出仅显示文本链接，无法直接渲染图片内容。原因：未开启`DB_IMAGE_RESPONSE_ENABLE`参数，未配置图片的base64编码转换逻辑。

## 怎么确认配好了
- 执行本地开发环境启动命令，查看控制台日志，确认无`ETIMEDOUT`或`ECONNREFUSED`类的连接错误。
- 上传一张jpg格式的菜单图片至知识库，检查是否能正常预览图片内容。
- 发起一次包含图片的投研查询，对比平台显示的token消耗与API后台的统计数值。
- 查看数据库连接模块的数据源列表，确认已配置的数据源状态均为正常连接。
