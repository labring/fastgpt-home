# 专业服务收益率的部署与升级

## 这个品类的数据长什么样
专业服务的收益率与行情日报数据，来源为持牌金融行情接口、监管公开报送数据及机构自研核算系统。更新节奏为每日固定时段完成前一交易日的全量数据更新。文档采用结构化JSON或CSV格式，每条记录包含产品唯一标识、统计周期、收益核算值、关联标的代码、数据来源标识。字段遵循金融行业标准化编码规则，统计周期采用ISO 8601日期格式，收益核算值采用通用金融计量单位，关联标的代码匹配交易所标准编码。

## 这些特征在「部署与升级」这一环带来什么约束
该品类的数据合规性要求高、更新节奏固定且结构化特征明确，为部署与升级带来三点约束。第一，多源数据接入需配置合规校验规则，确保仅接入持牌机构的合法数据源，避免违规数据流入知识库。第二，每日固定时段的全量更新任务，需配置精准的定时触发参数，避免与其他系统的行情同步任务冲突。第三，固定的结构化字段要求，部署时需预设schema映射规则，升级时需保留旧版字段的兼容逻辑，防止历史数据解析失败。此外，数据量随产品扩容逐步增长，部署时需预留向量数据库的存储扩容空间，避免升级后出现存储不足的问题。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `CRON_EXPRESSION` | `0 18 * * *` | 匹配专业服务日报的T+1更新节奏，避开市场交易高峰时段 |
| `PARSE_DATA_SCHEMA` | 预设金融产品收益数据标准schema | 贴合该品类固定的结构化字段要求 |
| `ENABLE_DATA_VALIDATION` | `true` | 满足金融数据的合规校验需求，过滤非法数据源 |
| `MAX_SYNC_WAIT_TIME` | `600 秒` | 适配全量历史数据同步的合理等待时长 |
| `VECTOR_DB_INDEX_BATCH_SIZE` | `500–1000 条` | 平衡同步效率与向量数据库的负载压力 |
| `LOG_RETENTION_DAYS` | `365 天` | 符合金融行业的监管数据留存要求 |

> 本页给出的参数取值均为常规建议，用于确定配置的起点。实际取值受材料形态、数据量与业务规则影响，具体问题需具体分析，建议在自有样本上实测后再定。

## 容易做错的三处
- 现象：启动后无法加载已配置的行情数据源索引，界面显示`500 Internal Server Error`，日志中出现`index not found`报错。原因：未在docker-compose的环境变量中配置`MONGODB_INDEX_AUTO_CREATE`为`true`，或未手动执行索引初始化脚本。
- 现象：进入容器执行`npm list mongoose`无输出，无法确认依赖版本，查看package.json可找到对应字段但无法通过npm命令查询。原因：FastGPT的docker镜像采用分层构建，依赖包未挂载到容器的可执行全局目录，或使用了非npm的包管理工具完成依赖安装。
- 现象：查看会话详情时出现`400 Bad Request`，报错文案显示`invalid log field`。原因：版本升级后未同步更新日志解析的schema规则，新增的收益数据字段未在配置中完成映射。

## 怎么确认配好了
- 触发一次手动数据同步，核对任务日志中无`validation failed`或`parse error`类报错，同步数据的字段与预设schema完全匹配。
- 进入容器执行`cat package.json | grep mongoose`，确认依赖版本字段存在，或查看容器内的node_modules目录确认mongoose文件存在。
- 查看会话日志详情页，确认所有字段均正常展示，无`400 Bad Request`或`field missing`报错。
- 检查定时任务的调度记录，确认每日固定时段自动触发同步任务，无延迟或跳过情况。
