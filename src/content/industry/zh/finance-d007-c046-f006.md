# 固废处理收益率的对话日志与审计

## 这个品类的数据长什么样
固废处理收益率与行情数据主要来自项目现场称重系统、财务核算模块及区域再生资源交易平台。数据更新节奏分为两类：全量日报数据每日02:00完成前一日归集，在线监测的处置效率数据每小时更新。数据文档为结构化CSV或JSON格式，包含项目唯一标识、统计周期、处置总重量、分类处置占比数值、单位处置成本、单位资源化收入、单位净收益等字段，单位统一为吨、元/吨、元。

## 这些特征在「对话日志与审计」这一环带来什么约束
固废处理数据的多维度字段与分时段更新特性，对对话日志与审计提出明确约束。首先，日志需完整记录每一次查询的字段筛选条件，包括项目标识、分类占比阈值等，确保审计时可核对查询逻辑与原始数据的匹配性。其次，每日固定时间更新的全量数据要求日志绑定查询时间戳，避免调用未更新的旧数据导致审计偏差。此外，实时监测的处置效率数据需在日志中标记数据来源的更新时间，确保多轮对话中使用的行情数据可追溯时效性。最后，项目唯一标识需与对话日志绑定，防止跨项目的审计混淆。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 前8条对话记录 | 固废处理收益率查询需关联项目历史筛选条件，8条可覆盖多轮对话的上下文需求，避免上下文过长导致模型调用超时 |
| `LOG_RETENTION_DAYS` | 180 天 | 符合行业合规审计的留存周期要求，覆盖完整的季度与半年度审计需求 |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600 秒 | 固废处理日报数据通常包含多项目汇总内容，解析耗时较长，600秒可覆盖绝大多数大文件的解析场景 |
| `WORKFLOW_NODE_TIMEOUT` | 120 秒 | 文本内容提取节点需处理多轮对话的历史记录，120秒可避免因数据量较大导致的超时失败 |
| `RECALL_CHAT_HISTORY_COUNT` | 前6条 | 结合通用配置与固废场景的多轮查询需求，平衡上下文完整性与调用效率 |
| `ENABLE_AUDIT_LOG` | 开启 | 满足合规审计要求，完整记录所有对话与工作流执行链路，便于后续溯源 |

> 本页给出的参数取值均为常规建议，用于确定配置的起点。实际取值受材料形态、数据量与业务规则影响，具体问题需具体分析，建议在自有样本上实测后再定。

## 容易做错的三处
- 现象：工作流中配置`文本内容提取`节点后，多轮对话无法保留历史查询条件。原因：未将聊天历史参数绑定至工作流的上下文传递链路，仅在节点内配置了召回条数，未同步到工作流输入参数。
- 现象：FastGPT v4.8.14版本中，工作流的`代码运行`节点输入包含自定义历史记录字段时，触发参数校验失败，无法保存工作流。原因：该版本对工作流节点的输入字段做了严格校验，未提前声明的自定义字段会被拦截。
- 现象：调用部署的大模型时，偶发`llm model response empty`报错，请求卡住10秒后终止。原因：大模型调用链路未配置超时重试机制，固废场景的结构化数据解析需消耗较多token，超出单次调用的token上限导致返回为空。

## 怎么确认配好了
- 进入FastGPT的审计日志管理页面，筛选对应项目的对话记录，核对每条日志包含的查询参数、调用时间、返回数据的时间戳，确认留存周期与配置的`LOG_RETENTION_DAYS`一致。
- 触发包含多轮筛选条件的固废收益率查询，查看工作流的执行日志，确认`文本内容提取`节点正确召回了指定条数的聊天历史。
- 上传一份包含多项目数据的固废处理日报文件，核对文件解析的实际耗时未超出配置的`PARSE_FILE_TIMEOUT_SECONDS`阈值，避免触发超时报错。
- 测试`代码运行`节点输入包含自定义历史记录字段，确认工作流可以正常保存并执行，无参数校验失败提示。
