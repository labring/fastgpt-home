# 旅游景区收益率的部署与升级

## 这个品类的数据长什么样
旅游景区的收益率数据核心来源于自有售票系统、入园闸机、商户POS终端及文旅监管平台接口。数据更新节奏为每日一次，于次日凌晨完成前一日全量数据的跑批汇总。单条数据以景区为唯一统计单位，包含景区标识、统计日期、当日售票总金额、入园总人次、单客平均营收、当日运营成本、当日净利润等字段，字段单位统一为人民币元或人次，无嵌套子文档结构。

## 这些特征在「部署与升级」这一环带来什么约束
每日固定时段的跑批需求要求部署时需配置与景区数据同步节奏对齐的定时任务，避免与核心业务跑批冲突。多源数据接入需提前完成接口鉴权与字段映射配置，不同景区的数据源格式差异会增加部署适配成本。数据量随景区运营规模增长，升级时需预留存储与计算资源扩容空间。跑批任务的原子性要求升级需在非核心业务时段完成，且需提前备份数据库与配置文件，防止升级中断导致数据丢失。另外，日报数据的校验逻辑需在部署阶段完成配置，避免异常数据流入最终报表。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `CRON_JOB_MAX_RUN_TIME` | `3600 秒` | 匹配景区日报跑批的常规耗时，避免任务中途被强制终止 |
| `RECALL_COUNT` | `前 10 条` | 景区收益率数据条目较少，召回过多会增加计算开销 |
| `SIMILARITY_THRESHOLD` | `0.75–0.85` | 过滤低匹配度的景区数据关联请求，提升报表准确性 |
| `UPLOAD_FILE_MAX_SIZE` | `2000 MB` | 容纳单景区全年度的历史收益率数据导入文件 |
| `LOG_RETENTION_DAYS` | `90 天` | 满足景区运营数据的合规留存要求，同时控制存储占用 |
| `DOCKER_RESTART_POLICY` | `unless-stopped` | 保障定时任务服务在异常退出后自动重启 |

> 本页给出的参数取值均为常规建议，用于确定配置的起点。实际取值受材料形态、数据量与业务规则影响，具体问题需具体分析，建议在自有样本上实测后再定。

## 容易做错的三处
- 现象：执行升级命令后出现`500 Internal Server Error`，无法完成版本切换。原因：未提前备份`docker-compose.yml`与`.env`配置文件，升级过程中覆盖了原有数据源映射配置。
- 现象：定时跑批任务执行后返回空结果，日志中显示`field not found`错误。原因：未针对不同景区的数据源字段差异完成映射配置，直接使用默认模板导入数据。
- 现象：调用语音识别接口返回`404 Not Found`错误，或无法获取识别结果。原因：未在FastGPT的模型配置中启用Whisper插件，或未正确配置接口访问地址。

## 怎么确认配好了
- 执行一次手动触发的日报跑批任务，核对任务日志中是否无异常报错，且生成的报表包含预期的景区数据字段。
- 调整配置项后重启服务，通过`docker ps`命令确认所有容器均处于正常运行状态，且重启策略符合预设要求。
- 向系统发起包含景区收益率关键词的查询请求，核对返回结果的召回条数与配置的`RECALL_COUNT`参数一致。
- 检查日志目录的磁盘占用情况，确认未因日志保留配置导致存储资源耗尽。
