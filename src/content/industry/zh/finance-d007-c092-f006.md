# 消费电子收益率的对话日志与审计

## 这个品类的数据长什么样
消费电子品类的收益率相关数据来源包括品牌官方供应链后台、主流电商平台交易接口、第三方消费电子行业监测数据库。更新节奏存在差异：线上渠道交易数据每小时更新，线下零售终端数据每日更新，新品上市后同步周期缩短至半小时。单条数据文档结构包含SKU唯一标识、产品型号、上市时间、销售渠道分类、当日终端售价、上一周期终端售价、渠道出货量数值、市场参考均价。售价与均价单位为元，出货量数值单位为台。

## 这些特征在「对话日志与审计」这一环带来什么约束
多源数据的混合接入要求对话日志需携带统一的SKU关联键，避免不同型号消费电子产品的日志混淆，审计环节需校验SKU标识的匹配一致性。不同更新频率的数据混合存储，要求日志按精确到分钟的时间戳排序，避免时序混乱导致的收益率计算错误。字段数量较多且包含跨渠道口径差异，审计环节需校验字段完整性，同时记录各数据来源的口径说明，避免不同渠道的售价统计歧义。此外，消费电子新品更新频繁，日志需支持快速关联新品的全链路数据，确保审计溯源的时效性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 前 80 条对话+10 条历史日志 | 消费电子品类数据字段较多，需保留足够上下文关联SKU与时间戳，避免截断关键匹配信息 |
| `LOG_RETENTION_DAYS` | 90 天 | 满足合规审计的季度级溯源要求，覆盖完整的销售周期与数据变更记录 |
| `SKU_MATCH_THRESHOLD` | 0.85 | 校验多源数据的SKU标识匹配度，避免不同型号消费电子产品的日志混淆 |
| `PARSE_MULTI_SOURCE_TIMEOUT` | 120 秒 | 适配电商、线下、供应链三类数据源的拉取耗时，预留足够的多源数据解析时间 |
| `MAX_LOG_ENTRY_PER_REQUEST` | 20 条 | 单次查询的日志返回条数适配消费电子多字段日志的展示与审计效率 |
| `AUDIT_ALERT_THRESHOLD` | 字段缺失率≥5% | 触发异常审计告警，及时发现数据缺失导致的播报错误 |

> 本页给出的参数取值均为常规建议，用于确定配置的起点。实际取值受材料形态、数据量与业务规则影响，具体问题需具体分析，建议在自有样本上实测后再定。

## 容易做错的三处
- 现象：v4.8.14版本的工作流中，“代码运行”节点输入包含“历史记录”关键词时，触发参数校验失败，无法正常保存或执行。原因：该版本代码运行节点的敏感词拦截逻辑未适配消费电子品类的日志关联场景，误将“历史记录”判定为系统保留关键词。
- 现象：调用企业自研大模型时偶发出现响应为空的情况，请求卡住约10秒后抛出空响应报错，oneapi接口测试未生成对应调用日志。原因：多源数据解析超时配置未匹配消费电子多数据源的拉取耗时，导致数据未完全加载时触发空响应，且未生成完整调用链路日志。
- 现象：对话日志的展示条数固定为50条，无法调整至更高数值用于全量审计。原因：未修改`maxContext`配置项的默认取值，默认限制为50条，未适配消费电子品类多字段日志的审计查看需求。

## 怎么确认配好了
- 进入平台日志管理页面，随机选取一条消费电子品类的对话日志，核对SKU标识、时间戳、字段完整性是否与配置的校验规则匹配。
- 触发一次多源数据拉取的测试请求，查看超时日志是否符合`PARSE_MULTI_SOURCE_TIMEOUT`的配置时长，确认无提前超时报错。
- 调整`maxContext`配置项后，查看对话历史展示条数是否符合预期，验证上下文保留长度符合审计需求。
- 配置字段缺失告警后，手动构造一条缺失关键字段的消费电子数据日志，确认是否触发对应审计告警。
