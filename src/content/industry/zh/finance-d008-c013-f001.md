# 保险智能尽调报告的HTTP 接口与外部系统

## 这个品类的数据长什么样
保险智能尽调报告的数据来源包括保险机构内部核保系统、投保人提交的财务与健康证明、行业监管披露文档。数据更新节奏分为两类，核保关联数据实时同步，历史理赔数据每日更新。文档结构包含投保人身份字段、健康告知明细、既往理赔记录、合规校验项、风险评级字段，部分文档为多页PDF格式，部分为结构化JSON格式。字段包含百分比、次数、评分等级等单位，部分字段为枚举值，例如风险等级分为低、中、高三类。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
数据来源分散且更新节奏不同，要求HTTP接口同时支持全量同步与增量拉取两种调用模式，适配不同的业务触发场景。字段包含枚举值与带单位的数值类型，接口需要预设严格的参数校验规则，拦截不符合格式的请求。单份报告的内容体量差异较大，接口需要支持分块传输或分页返回，避免单次请求超时。保险尽调数据涉及个人隐私与行业合规要求，接口需集成额外的身份鉴权与数据脱敏配置，确保数据传输与存储符合监管要求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `HTTP_REQUEST_TIMEOUT` | `600 秒` | 保险尽调报告通常包含多页结构化内容与大量校验逻辑，解析与传输耗时较长，600秒可覆盖多数场景的处理时长 |
| `API_REQUEST_AUTH_TYPE` | `API_KEY + IP_WHITELIST` | 保险机构内部系统需严格的访问控制，结合API密钥与IP白名单可降低未授权访问风险 |
| `RESPONSE_DATA_STRUCT` | `STRICT_JSON_SCHEMA` | 保险尽调报告的字段有严格的枚举与单位要求，严格JSON Schema校验可确保返回数据格式合规 |
| `UPLOAD_FILE_MAX_SIZE` | `500 MB` | 单份保险尽调报告可能包含多张附件图片与结构化文档，500 MB可覆盖多数常规报告的体量 |
| `PARSE_CHUNK_SIZE` | `800–1200 字符` | 保险尽调报告的文本内容包含大量专业术语与长段落，该区间可平衡解析精度与处理效率 |
| `HISTORY_MESSAGE_MAX_LENGTH` | `20000 字符` | 保险尽调的历史交互信息通常包含多轮校验记录，该长度可保存完整的上下文而不占用过多资源 |

> 本页给出的参数取值均为常规建议，用于确定配置的起点。实际取值受材料形态、数据量与业务规则影响，具体问题需具体分析，建议在自有样本上实测后再定。

## 容易做错的三处
- HTTP请求返回`400 Bad Request`，提示`invalid parameter name`或`missing required field`。未按照保险尽调报告的字段定义配置请求体的参数名与值，误将通用参数名替代了保险专属字段名，例如将`health_report`写为`general_data`。
- 调用外部数据库接口时返回`1045 Access denied`。未配置保险机构内部数据库的专属访问权限，使用了通用测试账号导致鉴权失败。
- 接口返回的尽调结果未关联历史交互信息，或提示`history parameter invalid`。未按照FastGPT的OpenAPI规范传递历史参数，错误地将历史消息放在请求体的非指定字段中，例如将`history`数组放在`query`字段下。

## 怎么确认配好了
- 发送测试请求，检查返回的HTTP状态码为`200 OK`，且响应体包含保险尽调报告的专属字段，例如`risk_rating`与`financial_debt_ratio`。
- 查看接口日志，确认请求的参数名与值与保险尽调报告的字段定义完全匹配，无格式错误。
- 模拟增量拉取场景，检查接口仅返回更新时间晚于指定时间戳的数据，符合更新节奏的配置。
- 触发数据脱敏校验，确认返回的敏感信息已被正确处理，符合合规要求。
