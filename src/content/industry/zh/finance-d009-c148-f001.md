# 酒店餐饮研报检索的HTTP 接口与外部系统

## 这个品类的数据长什么样
酒店餐饮研报的数据主要来自区域餐饮行业协会的公开调研、连锁品牌内部运营台账、第三方消费监测机构的门店客流统计。更新节奏分为三类：区域大盘研报按月更新，单门店运营研报按周更新，突发政策相关研报按日更新。文档结构包含区域消费趋势、单店营收拆解、供应链成本结构、节假日客流波动分析，字段包含门店编号、客单价、月客流量、食材成本占比，单篇文档长度差异较大，建议按自有样本统计或实测后再定。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
不同更新频率的研报数据，要求接口支持定时同步与实时拉取两种调用模式，适配月度、周度、日度的更新任务。文档篇幅较长，接口需支持分段上传与解析的参数配置，避免单次请求超时。多维度的细分字段，要求接口支持按门店编号、区域编码、统计周期等参数进行过滤召回。多源数据格式存在差异，接口需兼容CSV、JSON等多种输入格式的解析逻辑，适配不同渠道的研报接入。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `UPLOAD_FILE_MAX_SIZE` | `1000 MB` | 酒店餐饮研报单篇原始文档大小通常不超过200 MB，批量上传多份文档时需预留足够空间 |
| `PARSE_FILE_TIMEOUT_SECONDS` | `600 秒` | 长文档的解析需要较长处理时间，避免中途中断导致任务失败 |
| `apiCollection.filter_params` | `["门店编号", "区域编码", "统计周期"]` | 酒店餐饮研报的核心检索维度为门店、区域和时间，需按这些参数过滤召回结果 |
| `MAX_RECALL_NUM` | `前10 条` | 酒店餐饮细分场景下，单次检索的有效研报结果通常集中在10条以内 |
| `SESSION_KEEP_ALIVE` | `300 秒` | 酒店餐饮研报检索通常需要跨多个接口调用完成分析，保持会话可避免重复初始化 |
| `MULTIMODAL_FILE_MAX_SIZE` | `500 MB` | 部分研报包含门店照片、菜单图片等多模态内容，需限制单文件大小避免解析失败 |

> 本页给出的参数取值均为常规建议，用于确定配置的起点。实际取值受材料形态、数据量与业务规则影响，具体问题需具体分析，建议在自有样本上实测后再定。

## 容易做错的三处
- 调用`apiCollection`接口返回`Invalid URL, code: 500`，原因是上传的研报文件中包含未加入接口白名单的外部数据源链接。
- 接口返回`InternalError.Algo.InvalidParameter: Multimodal file size is`，原因是上传的酒店门店照片或菜单图片超出配置的多模态文件大小限制。
- MongoDB副本集主节点漂移后，接口断连无法重连，原因是未开启`MONGO_CHANGE_STREAM_RECONNECT`配置项。

## 怎么确认配好了
- 上传单篇酒店餐饮研报文件，核对接口返回的解析字段与预设的检索维度一致。
- 调用接口传入未配置白名单的外部链接，确认返回拦截报错，验证白名单配置正确。
- 手动触发MongoDB副本集主节点切换，检查接口是否自动恢复连接，验证重连配置生效。
- 连续发起两次API调用，核对两次调用的会话标识一致，验证会话保持配置生效。
