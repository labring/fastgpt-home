# 12345热线工单办理的办事咨询与答复：多轮对话与提示词

## 这个品类的数据长什么样
这个品类的数据主要来自12345热线平台、承办单位业务系统、官方知识库、回访评价数据及地方热线管理规范。日常产生的文档包含诉求登记单、派单记录、办理答复、回访记录、延期申请、退回说明及知识库条目。数据按日更新，覆盖从群众诉求到闭环处置的全流程，核心字段包含诉求编号、承办单位、办理状态、答复内容等。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源分散且覆盖全流程，要求多轮对话必须关联工单专属标识，避免上下文跨工单混淆；日更的知识库与业务数据，要求对话上下文需限制有效范围，避免加载过时或冗余信息；全流程文档的字段较多，提示词需明确限定调用对应业务字段，防止生成不符合工单规范的答复；同时，工单处理有明确时效要求，对话交互需匹配整体响应节奏，避免超时影响闭环。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定工单唯一编号 | 基于FastGPT v4.17.0的参数逻辑，实现单工单上下文持久化，避免跨工单交互混乱 |
| `messages` | 保留最近20条对话记录 | 覆盖工单从诉求提交到答复反馈的完整交互，避免丢失关键环节 |
| `variables` | 绑定诉求编号、承办单位、办理状态字段 | 自动填充业务上下文，减少人工输入的冗余操作 |
| 最大上下文长度 | 8000–12000 token | 适配工单全流程的文本长度，避免截断关键诉求或答复内容 |
| 对话超时阈值 | 600秒 | 匹配热线工单的响应时效要求，避免过长等待导致工单超期 |

## 容易做错的三处
- 现象：超过30天的历史对话无法恢复。原因：未设置`chatId`的持久化存储规则，导致旧上下文被自动清理。
- 现象：单轮对话响应耗时超过10秒。原因：未限制`messages`的保留条数，或未优化上下文提取逻辑，导致模型加载过多冗余数据。
- 现象：无法通过工单编号检索对应对话日志。原因：未将`variables`中的诉求编号作为日志检索的唯一标识，导致日志关联错误。

## 怎么确认配好了
- 发起一条模拟工单诉求，查看对话界面是否自动填充绑定的`variables`字段。
- 连续发起多轮交互，检查`chatId`是否保持一致，上下文是否完整保留历史对话内容。
- 模拟超期等待，查看系统是否触发超时提示，响应时长是否符合预设阈值。
- 检索指定工单编号的对话日志，确认日志完整且与工单关联正确。
