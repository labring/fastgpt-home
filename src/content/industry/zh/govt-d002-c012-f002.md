# 养老服务机构监管的办事咨询与答复：向量模型与索引

## 这个品类的数据长什么样
该品类的数据通常来自养老服务信息平台、民政统计系统、消防检查记录与机构运营台账。日常文档包含养老机构备案材料、运营补贴申请材料、服务质量检查表、安全隐患整改台账及老人入住档案。数据更新节奏为月度，单条文档多包含机构标识、床位数量、服务记录、监管整改结果等字段，不同来源的数据格式存在差异，需统一对齐后用于向量处理。

## 这些特征在「向量模型与索引」这一环带来什么约束
月度更新的频率决定了索引无需高频增量同步，可采用定时全量刷新的方式降低资源消耗。多来源异构数据需先完成格式对齐，否则向量嵌入会出现特征偏差，影响检索精准度。单条文档包含机构标识、床位数量等关联字段，分块时需保留上下文关联，避免拆分后丢失监管所需的关联信息。不同文档的字段差异要求索引环节设置统一的元数据映射规则，确保检索结果可匹配监管业务的查询逻辑。

## 配置怎么定

| 分块长度 | 800–1200 字符 | 适配养老监管文档的单块信息密度，避免拆分后丢失机构与床位的关联信息 |
| 重叠长度 | 100–150 字符 | 保留相邻分块的上下文关联，确保检索时可获取完整的监管记录片段 |
| `defaultToken` | 4096 token | 适配多数本地化向量模型的输入长度限制，覆盖养老文档的完整语义 |
| `maxToken` | 8192 token | 应对包含多页整改台账的长文档，避免截断关键监管信息 |
| 相似度阈值 | 0.75–0.85 | 平衡监管场景下的精准度与召回率，避免误匹配低相关的机构记录 |
| 单次召回上限 | 前 10 条 | 适配监管人员的查询需求，控制返回结果的信息量，避免信息过载 |

## 容易做错的三处
- 现象：部署后调用向量模型返回503状态码，提示当前分组下的embedding模型不可用。原因：未配置正确的向量模型分组，或模型服务超时未响应，未将embedding模型接入对应业务分组。
- 现象：Docker部署的知识库持续处于索引中状态，无进度更新。原因：未设置合理的分块长度与索引批次，或未配置正确的文档格式解析规则，导致解析环节卡住。
- 现象：无法加载本地化向量模型，或模型推理速度过慢。原因：未选择适配硬件配置的本地化模型，或未调整`maxToken`参数匹配模型的输入限制。

## 怎么确认配好了
- 检查向量模型接入配置，确认embedding模型已正确绑定到业务分组，无未生效的报错提示。
- 选取一份养老机构备案材料进行单文档索引测试，核对分块结果是否保留了机构名称、床位数量等关联字段的上下文。
- 发起模拟监管查询，例如“查看某养老机构的安全隐患整改记录”，核对返回结果的数量与匹配逻辑是否符合预设配置。
- 查看索引运行日志，确认无持续超时或解析失败的条目，符合FastGPT v4.17.0的日志输出规范。
