# 双随机、一公开监管检查的办事咨询与答复：向量模型与索引

## 这个品类的数据长什么样
该品类的典型数据来自“双随机、一公开”监管平台、企业信用信息公示系统、行业监管系统及执法人员名录库，日常文档包含抽查计划、检查对象名单、检查事项清单、现场检查记录、整改通知书、抽查结果公示等。数据更新频率为月度，核心维护环节包括检查事项与对象库更新、执法人员匹配任务生成、检查结果录入公示，数据字段多包含监管对象统一社会信用代码、检查事项编码、执法人员编号等标准化标识。

## 这些特征在「向量模型与索引」这一环带来什么约束
月度更新的批量数据要求索引支持增量同步，避免全量重建带来的性能损耗。多类型文档的混合存储需要索引适配不同字段的权重分配，比如抽查结果公示的文本权重应高于执法人员名录的结构化字段。检查对象名单与抽查计划的强关联属性，要求向量索引保留文档间的关联关系，避免检索时出现上下文割裂。单次处理的文档体量较大，需要限制单批次向量化的token数量，防止向量化服务超时，同时确保检索结果能覆盖监管执法所需的全量关联数据。

## 配置怎么定
仅作参考；请以目标 FastGPT 发布版本与部署文档核验。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配监管类文档的段落长度，避免单块内容过于分散或冗余 |
| 重叠长度 | 100–200 字符 | 保留跨块的上下文关联，确保检查记录的完整语义 |
| 相似度阈值 | 0.75–0.85 | 匹配监管事项与检查对象的精准度，避免误匹配或漏检索 |
| 单次搜索上限 | 前 10 条 | 控制检索结果的体量，适配执法人员的快速查阅需求 |
| `maxToken` | 8192 | 适配主流向量模型的输入上限，避免向量化服务报错 |
| 最大上下文 | 4000 字符 | 限制检索结果的总长度，符合办事咨询答复的文本长度要求 |

## 容易做错的三处
- 现象：向量化任务仅处理单文本切片，无法触发batch批处理。原因：未开启FastGPT的批量向量化配置，导致API仅传入单条文本数据，未适配向量化服务的批处理接收逻辑。
- 现象：调用API无法获取已分块的索引内容，检索时返回空结果。原因：分块时未设置合理的重叠长度，导致分块后的文档片段无法被正确索引关联，或未启用索引的增量同步机制。
- 现象：配置阿里multimodal-embedding-v1模型后，向量化服务返回格式错误。原因：未在FastGPT中正确配置多模态模型的输入格式，未适配文本与关联媒体数据的传递要求。

## 怎么确认配好了
- 查看FastGPT的向量化任务日志，确认是否存在多条文本切片同时传入的记录，验证批处理配置是否生效。
- 上传一份抽查计划文档，检索其中的检查事项关键词，核对返回结果是否包含正确的分块片段。
- 在向量模型管理页面，确认阿里multimodal-embedding-v1的接入配置已保存且无报错提示。
- 检索同一监管对象的关联文档，核对返回结果的去重情况，验证索引去重规则是否正常工作。
