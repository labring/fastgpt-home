# 学生资助与奖补审核的办事咨询与答复：多轮对话与提示词

## 这个品类的数据长什么样
数据来源包括全国学生资助管理信息系统、学校学籍系统、民政低保特困数据、财政支付系统，更新频率为学期。日常文档包含家庭经济困难认定表、资助申请表、奖助学金评审表、发放名单、公示材料，字段涵盖学生身份信息、家庭经济状况、资助申请内容、评审结果、银行卡信息等，涉及学籍号、资助金额、发放批次等单位。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
学期更新的节奏要求知识库需定期完成全量刷新，避免出现数据过期的情况。多源异构的数据来源需要统一对齐字段，防止对话中出现数据冲突或不一致的问题。文档包含评审、发放等多个环节的材料，提示词需引导对话聚焦资格核验、发放核对等核心业务环节。数据字段涉及敏感信息，多轮对话需限制上下文长度，防止信息泄露。同时，核心耗时环节的核验需求，要求检索优先召回学籍、评审类核心文档。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定当前咨询会话 | 确保多轮对话保留历史交互上下文，维持咨询连贯性 |
| `variables` | 绑定学生学号、学籍号字段 | 精准调用对应学生的资助相关数据，避免混淆不同咨询对象 |
| `messages` | 按会话历史拼接 | 确保多轮对话的上下文完整传递 |
| 分块长度 | 800–1200 字符 | 日常文档多为单条学生申请或评审材料，该长度可完整保留单条信息的核心字段 |
| 相似度阈值 | 0.75–0.85 | 区分相似的学生身份、资助金额等信息，避免误召回非目标文档 |
| 单次搜索上限 | 前 6 条 | 学期内核心文档数量集中，过多召回会增加上下文处理负担 |
| 最大上下文 | 4000–6000 token | 多轮对话需保留学生咨询、历史核验结果等信息，适配模型上下文限制 |

## 容易做错的三处
- 现象：上传家庭经济困难认定表、资助申请表等文档时提示报错，但文本输入对话正常。原因：未配置对应学生资助类文档的解析规则，或上传文件的格式超出平台支持范围。
- 现象：多轮对话响应速度偏慢。原因：单次搜索召回的文档数量超出配置上限，或上下文长度设置过大，导致平台处理负载增加。
- 现象：调用模型时出现`Unexpected end of JSON input`报错，使用`chatglm2`模型时高频出现。原因：模型返回的输出未正确完成拼接，或多轮对话的上下文token超出模型支持的最大长度导致内容截断。

## 怎么确认配好了
- 发起包含学生学籍号的咨询，确认后续多轮对话中可延续该学生的资助相关信息进行交互。
- 上传单份家庭经济困难认定表，确认文档可被正常解析并纳入检索范围。
- 发起连续5轮以上的咨询，检查是否出现响应延迟或`Unexpected end of JSON input`类报错。
- 调整单次搜索上限配置，核对召回的文档是否仅包含当前学期内的学生资助相关材料。
