# 政府信息依申请公开的办事咨询与答复：向量模型与索引

## 这个品类的数据长什么样
这个品类的数据来自政府信息公开平台、机关档案系统、公文系统、部门业务台账及相关规范文档。日常处理的文档包含政府信息公开申请表、补正告知书、征求第三方意见函、答复书、送达回证、行政复议答辩材料，均由政府办公室、政务公开办等主体生成维护。数据更新无固定周期，随申请办理进度、档案归档或政策调整同步更新，单份文档包含明确的申请主体、事项描述、办理流程及答复结果等字段。

## 这些特征在「向量模型与索引」这一环带来什么约束
数据来源分散且更新无固定周期，要求索引系统支持跨源增量同步，避免重复索引或遗漏最新文书。文档类型多样且结构差异明显，需适配不同文书的字段特征，不能采用统一的分块规则。个案办理的核心要求决定了检索需精准匹配申请事项的具体描述，因此对向量模型的语义理解精度有较高要求。同时，出错后果直接关联行政程序合规性，需保证检索召回的准确性与完整性，避免遗漏关键依据。

## 配置怎么定
以下配置适配FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配该品类政务文书的常规篇幅，保证单块内容覆盖完整的申请事项或答复要点，避免语义割裂 |
| 重叠长度 | 100–150 字符 | 保留文书段落间的逻辑衔接信息，防止分块后丢失关键上下文关联 |
| 相似度阈值 | 0.72–0.80 | 区分同类申请事项的细微差异，平衡召回率与精准度，避免误召回无关文书 |
| `defaultToken` | 4096 | 适配多数政务文书的向量生成长度需求，保证单轮检索的基础上下文完整 |
| `maxToken` | 8192 | 容纳多份相关文书的拼接内容，满足答复书起草所需的完整信息支撑 |
| 单次搜索上限 | 前 8 条 | 匹配个案申请的常规相关文书数量，避免过多冗余内容增加模型处理负担 |

## 容易做错的三处
- 现象：检索到相关文件，但大语言模型输出“未找到相关内容”。原因：未正确设置相似度阈值导致召回的文书语义匹配度过低，或上下文拼接时超出`maxToken`限制导致关键内容被截断。
- 现象：索引任务出现超时报错。原因：未根据政务文书的长度调整分块参数，单块内容过长导致向量生成耗时增加，超出系统处理阈值。
- 现象：召回结果包含大量非本次申请相关的主动公开信息。原因：未针对依申请公开的个案属性关联申请事项的特定描述字段，导致泛化召回无关内容。

## 怎么确认配好了
- 上传单份典型政务文书（如正式答复书），使用FastGPT v4.17.0版本的分块校验功能检查分块后的内容完整性，确认每块未割裂关键逻辑节点。
- 输入模拟的依申请公开事项描述，核对召回结果的数量与匹配程度，确认相似度阈值符合业务场景需求。
- 测试多份相关文书的拼接长度，确认未超出`maxToken`限制，避免关键内容被自动截断。
- 查看索引任务的运行日志，确认未出现向量生成失败、超时或重复索引的报错信息。
