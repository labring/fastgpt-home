# 政府信息依申请公开的办事咨询与答复：多轮对话与提示词

## 这个品类的数据长什么样
该品类的核心数据来自政府信息公开平台、机关档案系统、公文系统、部门业务台账及政府信息公开相关规范。日常处理的文档包含政府信息公开申请表、补正告知书、征求第三方意见函、答复书、送达回证、行政复议答辩材料等制式文书。数据更新频率不定期，随个案申请及档案归档节奏变动。数据字段以申请主体、申请事项、办理节点、答复内容为核心，无统一批量字段格式，均围绕单个申请人的个案请求展开。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
该品类的文档为制式化个案材料，且数据来源分散，要求多轮对话需精准绑定单个申请的上下文，避免跨会话混淆。数据更新不定期，需适配知识库的按需同步逻辑，避免过期数据干扰检索。核心办理环节依赖特定申请的关联信息，提示词需精准提取个案专属字段，不能泛化处理。同时，出错后果直接关联行政救济，要求多轮对话的信息准确性需严格匹配官方文书内容，不能出现信息偏差。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配该品类制式文书的段落长度，保留语义完整性，避免关键信息被截断 |
| 上下文窗口上限 | 模型原生窗口的 80%–90% | 预留空间承载多轮对话的`messages`历史内容，避免因窗口不足丢失上下文 |
| 会话ID绑定 | 绑定`chatId` | 确保同一场景下的多轮对话上下文连续，避免跨申请的会话混淆 |
| 单次召回文档数 | 前 3–5 条 | 聚焦该品类的核心检索需求，减少无关文档对模型判断的干扰 |
| 提示词变量配置 | 绑定`variables`中的申请编号、申请人信息 | 精准关联个案专属数据，确保答复内容匹配单个申请的具体要求 |
| 对话日志存储上限 | 1000 MB 按实测标定 | 适配该品类单会话的文档存储需求，避免存储资源过度占用 |

## 容易做错的三处
- 现象：多轮对话从第二个问题开始答非所问，原因：未正确绑定`chatId`导致会话上下文未被保留，或上下文窗口上限设置过低无法承载历史`messages`内容。
- 现象：上传的制式文书出现关键信息截断，原因：分块长度设置不符合该品类文档的段落结构，导致核心办理节点信息被拆分丢失。
- 现象：对话日志无法按行政办理周期自动清理，原因：未配置匹配该品类申请周期的保留时长规则，或未关联会话的申请状态逻辑。

## 怎么确认配好了
- 发起模拟政府信息公开申请对话，连续提出3个关联问题，验证模型能关联历史申请信息作答。
- 上传该品类的制式文书文档，检查分块后的内容无关键段落被截断。
- 查看会话的`messages`字段记录，确认同一会话的历史消息被完整保留且`chatId`一致。
- 配置提示词变量后发起测试，验证模型能正确提取并使用绑定的申请编号等专属信息。
