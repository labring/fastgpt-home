# 城市公交的办事咨询与答复：向量模型与索引

## 这个品类的数据长什么样
城市公交的办事咨询数据主要来自运营调度系统、线路台账、乘客咨询历史库、临时运营调整公告。结构化数据包含线路编号、站点名称、运营时段、票价标准，非结构化数据包含临时改道通知、票务政策说明。数据更新节奏不同：实时调度与临时调整随运营状态即时更新，线路时刻表每季度校准，乘客常见问题库每月迭代。文档包含纯文本说明、结构化表格两类，字段涉及时间、里程、价格等标准化单位。

## 这些特征在「向量模型与索引」这一环带来什么约束
城市公交数据的混合结构与多更新节奏，对向量索引环节提出多重约束。实时临时调整数据需支持增量索引，避免全量重建占用资源；结构化字段（如线路编号、站点名）的精准匹配需求，要求索引同时覆盖语义向量与关键词召回；短文本（如站点名、线路号）与长文本（如数百字的改道公告）并存，需适配可变长度的文本分块逻辑；高频口语化咨询内容，要求向量模型适配日常通勤场景的语义理解，避免匹配偏差。FastGPT v4.17.0的索引模块可适配上述特征的配置调整。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配城市公交公告、咨询回复的常见长度，避免单块过长丢失语义关联 |
| 重叠长度 | 100–150 字符 | 衔接相邻分块的上下文，避免改道公告等长文本的语义断裂 |
| `defaultToken` | 8192 | 适配多数开源向量模型的上下文窗口，覆盖城市公交多字段拼接后的总token数 |
| 相似度阈值 | 0.72–0.78 | 平衡乘客口语化咨询的召回精准度，避免误匹配相似线路或站点 |
| 单次搜索上限 | 前 8 条 | 公交咨询的答案通常集中在少数相关线路或公告，过多结果会干扰用户判断 |
| 最大上下文 | 3000–4000 字符 | 整合相关分块与原始问题，保证回复能覆盖线路、时间、调整细节等完整信息 |

## 容易做错的三处
- 知识库上传后状态长时间停留在索引中。原因：未开启增量索引开关，全量索引处理了大量历史公交运营数据，导致任务积压。
- 分块设置为3000字符时出现文本块丢失。原因：未适配城市公交长公告的段落分隔逻辑，分块时截断了未闭合的语义单元，导致部分内容未被索引。
- 向量模型调用出现超时报错。原因：未配置正确的模型调用参数，错误使用非适配的代理服务地址，导致请求无法正常完成。

## 怎么确认配好了
- 上传一份典型的公交改道公告文档，查看索引完成后的分块预览，确认分块长度与重叠设置符合预期。
- 发起一条贴合日常咨询的查询，核对返回结果的相关性，调整相似度阈值至符合业务需求的区间。
- 查看向量模型调用日志，确认`defaultToken`设置未触发模型上下文溢出报错。
- 上传批量历史运营数据，验证索引任务的完成时效，确认增量索引开关按需开启。
