# 港口航运的办事咨询与答复：多轮对话与提示词

## 这个品类的数据长什么样
港口航运办事咨询与答复的数据主要来源于直属海事局的政务公开平台、各港口的官方办事指南系统、口岸通关的官方公告文档。数据更新节奏随政策调整触发，比如新的通关政策发布、港口办事流程优化时同步更新。单份文档通常按办事事项拆分，结构包含事项名称、办理主体、所需材料清单、办理流程、收费标准、咨询渠道等字段，材料清单以“项”为单位，办理时限以“工作日”为单位，收费标准以“元/箱”或“元/吨”为单位。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源分散导致多轮对话需跨海事、港口、口岸等多个数据源召回关联信息，提示词需明确指定数据源范围以避免混淆。文档结构复杂且单份内容较长，多轮对话需跟踪用户当前咨询的具体办事环节，避免上下文混淆。字段包含多个子项，提示词需引导用户明确具体咨询维度，比如区分申报材料与办理时限。更新频率不固定，多轮对话需在回复中提示用户确认当前政策的时效性，避免引用过期信息。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 配置`chatId`参数 | 固定会话ID | 确保同一场景下的多轮对话共享上下文，避免每次会话重置对话状态 |
| 配置`messages`数组 | 仅保留最近10轮对话内容 | 减少冗余数据传入，降低模型处理负载，提升响应速度 |
| 绑定`variables`字段 | 港口代码字段 | 精准定位对应口岸的专属办事规则，避免跨港口的政策混淆 |
| 最大上下文长度 | 8000–12000 字符 | 匹配港口办事文档的单章节平均长度，避免截断关键流程与材料信息 |
| 单次召回条数 | 前6条 | 覆盖常见办事咨询的关联事项，避免信息过载 |
| 上下文保留时长 | 7200 秒 | 匹配用户办理一项港口业务的平均耗时，跨时段对话仍保留上下文 |

## 容易做错的三处
- 对话响应延迟明显。原因是未限制单次召回条数，过多的长文档分块被传入上下文，导致模型处理耗时增加。
- 出现Unexpected end of JSON input报错。原因是调用模型时传入的`messages`数组格式错误，比如遗漏收尾的括号，或包含未转义的特殊字符，在ChatGLM2模型调用时触发解析失败。
- 对话输出结果需手动在侧边栏打开，且每次对话需重新发起会话。原因是未正确配置`chatId`参数，未开启实时消息渲染，导致上下文无法跨会话保留。

## 怎么确认配好了
- 发起一项具体的港口办事咨询，比如“宁波港出口集装箱申报所需材料”，检查主对话框是否实时显示回复内容。
- 连续发起3个关联问题，比如先问申报材料，再问办理时限，再问收费标准，检查对话上下文是否被正确保留，无需重复提问前置信息。
- 尝试传入包含特殊字符的咨询内容，比如“集装箱申报需提供的<装箱单>与<提单>有什么区别”，检查是否触发JSON解析错误。
- 查看配置面板中的`variables`与`chatId`绑定状态，确认对应港口代码字段已正确关联。
