# 轨道交通装备的办事咨询与答复：向量模型与索引

## 这个品类的数据长什么样
轨道交通装备的办事咨询数据主要来源于设备运维手册、检修规程、运营调度记录、故障排查指南等文档。数据更新节奏随新设备上线、规程修订或运营调整按需触发，无固定周期。文档多为章节式结构，包含设备型号、编号、检修周期、故障代码、技术参数等字段，单位涵盖毫米、小时、公里、兆帕等专业工程单位，单份文档长度跨度较大，部分运维手册可达10M以上。

## 这些特征在「向量模型与索引」这一环带来什么约束
轨道交通装备的文档结构复杂、字段专业且长度跨度大，要求索引过程需保留字段级关联，避免拆分关键参数与单位。长文档的分块需适配章节逻辑，防止关键故障代码或检修步骤被截断。按需更新的数据特征要求索引支持增量更新，避免全量重建带来的资源浪费。专业术语密集的文档需确保向量模型能准确捕捉语义关联，索引时需优先关联设备编号、故障代码等核心字段，提升检索精准度。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 匹配轨道交通装备文档的单章节平均长度，避免截断专业段落与故障代码 |
| 重叠长度 | 100–150 字符 | 保留相邻chunk的上下文关联，防止关键检修步骤被拆分在不同块中 |
| maxToken | 8192 token | 适配主流开源向量模型的输入上限，匹配长文档分块后的token总量 |
| defaultToken | 2048 token | 设定基础检索上下文的token配额，满足单条设备参数的完整展示需求 |
| 单次索引上限 | 50 个文件 | 避免单批次索引负载过高，防止触发服务器资源过载 |
| 相似度阈值 | 按实测标定 | 结合轨道交通装备故障描述的语义相似度特征调整匹配精度 |

## 容易做错的三处
- 现象：上传10M以上的轨道交通运维手册时，部分chunk向量化后向量值为空，反复点击重试后恢复正常。原因：分块长度未适配文档的换行与章节结构，导致chunk包含未闭合的专业公式或代码块，触发向量模型的格式校验失败。
- 现象：批量索引多份设备文档导致服务器崩溃，重启后对应知识库状态显示“未就绪”，无法自动恢复索引。原因：未开启自动索引重试配置，批量索引任务的中断标记未被系统自动重置，需手动触发重置操作。
- 现象：升级FastGPT v4.17.0后，原有的轨道交通装备知识库无法返回检索结果。原因：新版本向量模型的嵌入维度发生变更，原有索引的向量库未重新生成，与当前模型的输入要求不匹配。

## 怎么确认配好了
- 上传单份10M以上的轨道交通检修规程文档，检查分块列表中是否存在无异常标记的chunk，确认分块逻辑适配文档结构。
- 批量上传50个以内的设备参数文档，观察索引任务的资源占用情况，确认未触发服务器过载提示。
- 输入包含故障代码或设备型号的咨询问题，检查检索结果是否包含设备编号、检修周期等核心字段，确认索引字段配置正确。
- 升级FastGPT v4.17.0对应的向量模型版本后，重新生成对应知识库的索引，确认检索结果与更新后的模型语义匹配。
