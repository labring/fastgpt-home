# 轨道交通装备的办事咨询与答复：工作流编排

## 这个品类的数据长什么样
轨道交通装备的业务数据主要来自车载运行记录仪、地面检修台账、运维工单系统与备件库存系统。数据更新节奏分为实时采集的运行参数、每日同步的检修记录、每月归档的维保报告三类。单份文档通常包含设备唯一编号、累计运行时长、故障代码、处置时长、适配备件型号等字段，字段单位涵盖小时、次、兆帕、毫米等，部分文档附带结构化的故障排查步骤文本。

## 这些特征在「工作流编排」这一环带来什么约束
实时运行参数的高频更新要求工作流支持动态变量拉取，避免使用静态缓存导致数据滞后。多字段带特定单位的文档结构，要求工作流配置变量提取规则时，需绑定单位校验逻辑，防止无效参数进入AI对话节点。不同数据源的更新节奏差异，需要为每个数据节点设置独立的拉取周期，避免重复拉取或数据过期。关联多设备的工单场景，要求工作流支持上下文跨节点传递，确保后续节点能获取前置节点的设备标识与故障信息。本页面配置基于FastGPT v4.17.0版本。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` | 绑定设备编号、故障代码字段，开启单位校验 | 匹配轨道交通装备数据的结构化字段与单位特征 |
| `nodeId` | 为运行数据、检修台账、工单系统分别分配唯一标识 | 实现多数据源的独立调用与上下文传递 |
| 单次搜索上限 | 前3条 | 匹配轨道交通装备故障案例的常见覆盖范围 |
| 最大上下文 | 1200–1800字符 | 适配单份维保文档的常规文本长度 |
| 超时时间 | 600秒 | 覆盖复杂故障排查的AI响应周期 |
| 循环节点 | 按实测标定 | 适配多步骤故障排查的循环处理逻辑 |

## 容易做错的三处
- 现象为工作流调试时代码节点成功移除思考标签，但正式运行时仍显示AI对话节点的think内容。原因是未在工作流的全局设置中开启代码节点的强制输出过滤，仅在调试环境生效。
- 现象为恢复项目备份后，知识库关联的智能体未在后台显示。原因是备份仅包含项目配置，未同步关联的知识库向量库文件，需手动重新绑定。
- 现象为工作流中多个AI对话节点的结果全部输出，未仅保留最后一个节点的内容。原因是未配置输出节点的上下文截断规则，未指定仅调用目标节点的输出结果。

## 怎么确认配好了
- 触发工作流运行，查看变量提取结果，确认提取的字段与源数据的字段名称、单位一致。
- 运行工作流并检查最终输出结果，确认仅保留指定节点的内容，无多余的前置对话或数据。
- 模拟数据源数据更新的场景，验证工作流会重新拉取最新的对应数据，不使用旧缓存。
- 触发超时测试，确认工作流在预设时长内完成运行，无异常中断或报错。
