# 通信铁塔与基础设施的办事咨询与答复：多轮对话与提示词
本页面基于FastGPT v4.17.0版本编写。

## 这个品类的数据长什么样
通信铁塔与基础设施的数据源来自中国铁塔运维台账、地方通信管理局备案数据库及日常巡检上报系统。备案类数据每月更新1次，运维巡检数据每日同步，故障告警数据实时接入。文档为结构化JSON格式，每个条目包含站点唯一编码、经纬度（十进制度，保留6位小数）、塔体高度（米）、承载频段（MHz）、最近巡检日期、当前运行状态等字段，字段均附带明确单位与业务含义。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据的多时效性维度要求多轮对话需区分不同数据的调用优先级，提示词需明确优先使用实时告警与当日巡检数据，旧备案数据仅作为补充参考。带单位的字段要求提示词必须强制保留单位输出，避免参数混淆。唯一的站点编码要求多轮对话需绑定唯一标识，避免不同站点的咨询上下文交叉干扰。结构化的字段结构要求提示词需引导用户输入明确的站点编码，否则无法精准召回对应数据，同时需限制上下文长度，避免冗余数据干扰核心信息提取。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` | `{ "target_site_code": "", "consult_scene": "standard" }` | 绑定站点编码与咨询场景，让提示词精准匹配对应品类的结构化数据 |
| `messages` | 前 10 轮对话上下文 | 通信铁塔的咨询多涉及单站点多维度问题，保留10轮可覆盖完整咨询链路 |
| `chatId` | 会话创建时自动生成的唯一标识 | 关联同一用户的多轮咨询，避免不同站点的咨询上下文混淆 |
| 最大上下文长度 | 800–1200 字符 | 通信铁塔数据字段简洁，过长上下文会干扰提示词对核心信息的提取 |
| 提示词模板 | 按实测标定 | 适配故障排查、备案查询、运维咨询等不同场景的专属提示词需求 |

## 容易做错的三处
- 现象：AI对话节点返回空字符串，触发`chat:LLM_model_response_empty`报错。原因：提示词未正确绑定`variables`中的目标站点编码，导致无法召回对应品类的结构化数据。
- 现象：输出内容末尾出现未闭合的半角引号，后续自动补全为规范引号。原因：提示词未明确限制输出标点格式，未要求使用全角引号或统一的输出规范。
- 现象：工作流中全局变量未生效，提示词无法获取指定的站点参数。原因：未在工作流节点中正确关联`variables`与会话输入参数，导致变量传递失败。

## 怎么确认配好了
- 发起针对已知通信铁塔站点的咨询，检查上下文是否保留之前输入的站点编码，确认`chatId`正确关联当前会话。
- 触发大模型调用，查看返回结果是否包含带单位的参数，如塔高、频段等，确认提示词的格式约束生效。
- 模拟针对两个不同站点的连续咨询，检查两次会话的上下文是否独立，确认`messages`的上下文截取逻辑正确。
- 查看工作流运行日志，确认`variables`中的站点编码与咨询场景参数被正确传递到提示词中。
