# 不动产登记的台账汇总与报告生成：向量模型与索引

## 这个品类的数据长什么样
本品类数据主要来自不动产登记信息系统、地籍调查数据库、房屋交易网签系统、税务系统及电子证照库，更新频率为每日更新。日常处理的文档包含登记申请书、权属证明、测绘成果、税费凭证、不动产权证书、登记簿等，数据字段涵盖权利人信息、不动产坐落位置、面积参数、权利类型、限制状态等，部分文档为结构化表单，部分为非结构化电子材料或扫描件。

## 这些特征在「向量模型与索引」这一环带来什么约束
每日更新的数据特征要求索引支持增量同步，避免全量重建带来的资源消耗。多源异构的文档类型，既有结构化表单也有非结构化电子材料，需要适配不同的分块规则以保留关键权属信息。核心字段的精准匹配需求，要求向量模型对专业术语的语义理解能力达标。同时，数据直接关联不动产权利归属，索引召回的准确性直接影响后续核验环节，需严格控制误召回比例。

## 配置怎么定
以下配置基于 FastGPT v4.17.0 版本
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配不动产登记文档的结构化字段与非结构化段落长度，保留完整的权属信息单元 |
| 重叠长度 | 100–200 字符 | 避免跨块的关键信息断裂，保障语义连贯性 |
| 相似度阈值 | 0.75–0.85 | 区分权属信息的相似表述，降低误召回概率，适配专业场景的严谨性要求 |
| 单次搜索上限 | 前 10 条 | 平衡召回效率与结果覆盖度，避免冗余数据干扰台账汇总 |
| `maxToken` | 16000 字符 | 适配不动产登记簿等长文档的上下文需求，满足报告生成的完整信息调用 |
| `defaultToken` | 按实测标定 | 适配不同环境的 token 消耗限制，避免索引过程中断 |

## 容易做错的三处
- 现象：导入飞书文件夹下的excel文件和多维文档后，索引状态始终显示未完成，无解析日志。原因：未针对不动产登记的结构化表单与非结构化文档配置差异化的分块规则，导致大文件解析超时或小文件分块异常。
- 现象：使用PG数据库docker部署时，索引建立失败，宿主机显示8c16G无GPU的资源占用正常。原因：未调整`maxToken`的取值适配低算力环境，导致向量生成时内存溢出。
- 现象：接入oneapi的embedding模型报错，无法单独配置索引模型。原因：未在系统设置中指定独立的索引模型接口，误将通用对话模型作为索引模型调用，导致参数不匹配。

## 怎么确认配好了
- 上传单份不动产权证书文档，查看解析后的分块结果，确认核心字段如权利人、坐落位置被完整保留。
- 发起台账汇总查询，核对召回结果的条数与预设的单次搜索上限一致，无冗余数据。
- 模拟每日增量更新的场景，执行索引同步操作，确认无报错且数据更新完成。
- 调用独立的索引模型接口，验证向量生成流程正常，无参数不匹配的报错。
