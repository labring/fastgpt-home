# 传染病信息报告与监测的台账汇总与报告生成：向量模型与索引

## 这个品类的数据长什么样
本品类数据来自中国疾病预防控制信息系统、医疗机构HIS与传染病报告系统、实验室检测系统，更新频率为每日。日常文档包含传染病报告卡、疫情分析报告、病例订正记录、聚集性疫情报告、流调报告，数据字段包含病例唯一标识、诊断时间、报告单位、法定传染病分类、订正状态等，单份文档长度跨度较大，从数百字符的报告卡到数万字符的流调报告均有覆盖。

## 这些特征在「向量模型与索引」这一环带来什么约束
每日高频更新的业务数据要求索引支持增量同步机制，避免全量重建带来的额外耗时，适配疾控日常的台账更新节奏。文档长度跨度大，需要适配灵活的分块规则以保留不同文档的关键信息。法定传染病分类、病例诊断等字段的合规性要求高，向量检索需优先关联结构化字段与非结构化文本的匹配关系。订正记录的版本差异需要索引支持多版本数据区分，避免召回旧版错误报告内容。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配本品类文档跨度，保留报告卡与流调报告的关键信息 |
| 重叠长度 | 100–150 字符 | 避免分块截断病例诊断、订正说明等连续关键内容 |
| `defaultToken` | 4096 token | 匹配主流嵌入模型的输入上限，适配长文本流调报告 |
| `maxToken` | 8192 token | 覆盖最长文档的分块后上下文拼接需求 |
| 相似度阈值 | 0.72–0.80 区间 | 过滤低匹配度的无关报告，保留法定传染病相关内容 |
| 单次召回上限 | 前10条 | 控制检索结果数量，适配疾控台账汇总的批量处理需求 |

## 容易做错的三处
- 每日执行全量索引重建时，服务器读写负载持续升高直至资源耗尽。原因是未启用增量索引机制，针对每日更新的疾控数据直接执行全量同步，产生过量的磁盘读写与内存占用请求。
- 升级FastGPT v4.17.0后，调用voyage索引接口返回400 status code no body。原因是未适配新版本的接口参数校验规则，`defaultToken`的取值未符合接口要求的有效区间。
- 本地部署使用m3e-large模型时，上传的流调报告或长文档卡在1组或2组索引中。原因是分块长度设置超出模型输入上限，索引任务无法完成分块处理，进入阻塞状态。

## 怎么确认配好了
- 手动上传一份标准传染病报告卡，查看系统索引任务的进度日志，确认分块长度与配置的取值一致。
- 发起针对法定传染病分类的检索请求，检查返回结果的数量是否符合单次召回上限的配置。
- 上传一份已订正的病例记录，验证检索结果是否优先召回最新版本的报告内容。
- 查看系统资源监控面板，确认增量索引任务执行时服务器负载未超出合理范围。
