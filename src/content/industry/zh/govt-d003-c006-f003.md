# 传染病信息报告与监测的台账汇总与报告生成：多轮对话与提示词

## 这个品类的数据长什么样
本品类的数据来源为中国疾病预防控制信息系统、医疗机构HIS和传染病报告系统、实验室检测系统。日常处理的文档包含传染病报告卡、疫情分析报告、病例订正记录、聚集性疫情报告、流调报告。数据按日更新，单条记录包含病例基本信息、诊断结果、报告时限、订正状态等字段，所有字段需符合法定传染病报告规范，无自定义单位。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据按日更新的要求，使得多轮对话需限定当前会话的时间范围，避免跨周期数据混淆。多类结构化文档的字段差异，要求提示词需明确区分传染病报告卡、流调报告等不同文档的提取规则。多系统来源的数据可能存在字段不统一的情况，多轮对话需逐步引导用户确认字段映射关系。针对核对病例诊断、订正重卡错卡的耗时环节，多轮对话需支持分步拆解任务，逐步获取待核对的记录信息。

## 配置怎么定
本配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文 | 前2000 token | 适配单条流调报告或传染病报告卡的字段量，避免超出模型上下文限制 |
| `messages` | 按会话历史保留前10轮 | 匹配疾控场景下多步骤核对的交互逻辑，减少冗余上下文占用 |
| `variables` | 预设法定报告字段变量 | 快速调用病例基本信息、报告时限等标准化字段，提升提示词复用性 |
| `chatId` | 绑定当日会话ID | 区分不同日期的台账数据，避免跨日数据混淆 |
| 单次交互响应上限 | 前3条记录 | 对应日常汇总的单次处理规模，避免单次返回过多数据导致超时 |
| 会话超时时间 | 300秒 | 适配复杂核对任务的思考时长，避免未完成交互被强制中断 |

## 容易做错的三处
- 上传台账文件后触发报错，文本对话功能正常。原因是未配置对应文件格式的解析模板，无法识别传染病报告卡的结构化字段。
- 对话过程中出现Unexpected end of JSON input报错，使用chatglm2模型时易触发。原因是模型返回的内容未完整生成，导致JSON格式断裂，未配置模型输出截断重试逻辑。
- 多轮对话响应速度偏慢。原因是未限定单次召回的记录条数，导致系统加载过多历史台账数据，占用过多计算资源。

## 怎么确认配好了
- 上传单份传染病报告卡文件，检查是否能正确提取预设的法定报告字段，确认无解析报错。
- 发起多轮核对请求，逐步输入待订正的病例信息，检查会话是否能保留历史交互的上下文，正确关联之前的输入内容。
- 等待会话完成，检查是否在预设的超时时间内返回结果，无格式断裂报错。
- 调整单次交互的记录条数上限，核对返回的结果条数是否符合预设的取值范围。
