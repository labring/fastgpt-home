# 信访事项办理的台账汇总与报告生成：向量模型与索引

## 这个品类的数据长什么样
本品类数据主要来自国家信访信息系统、地方信访系统、12345平台、基层治理平台及历史信访档案，更新频率为每日。日常文档包含信访登记表、受理告知书、转送交办函、办理意见书、复查复核申请、化解方案等，数据字段涵盖诉求主体、事项内容、办理进度、责任单位、复核结果等，无额外自定义单位，数据结构围绕信访事项办理的法定流程搭建。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源数据来自不同平台，格式存在差异，要求索引环节支持多格式文档的统一解析与分块。每日更新的频率要求索引支持增量同步，避免全量重建带来的资源消耗。不同文档类型的长度差异较大，从短表单到长文书均有覆盖，需要灵活调整分块策略以保留语义完整性。同时，数据围绕信访办理法定流程搭建，索引需保留各办理节点的关联语义，确保检索时能关联到对应环节的材料。

## 配置怎么定
以下配置基于 FastGPT v4.17.0 版本适配。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配信访类文档从短表单到长文书的长度范围，保留办理流程的语义完整性 |
| 重叠长度 | 100–150 字符 | 避免分块后关键办理节点的语义被截断，保障跨块检索的连贯性 |
| 相似度阈值 | 0.72–0.78 | 信访事项的诉求表述存在相似性，该区间可区分重复信访与相似诉求，减少误判 |
| 单次搜索上限 | 前 8 条 | 信访台账汇总需覆盖主要关联事项，过多结果会增加汇总冗余，过少则可能遗漏关联诉求 |
| `defaultToken` | 8192 | 适配信访报告生成的长上下文需求，保障办理意见、复核结果等多段内容可完整纳入 |
| `maxToken` | 16384 | 支持汇总多份办理材料的完整内容，满足台账汇总的信息容量要求 |

## 容易做错的三处
- 界面显示索引中状态长时间无变化。原因：未配置增量索引触发规则，全量索引处理多源历史信访档案时耗时过长。
- 自定义索引配置后检索结果无关联内容。原因：未针对信访文档的字段结构调整分块规则，导致关键诉求内容被分块截断。
- 接入本地m3e模型后索引任务超时。原因：未设置合理的模型调用超时参数，信访数据量较大时无法在预设时间内完成向量生成。

## 怎么确认配好了
- 上传单份信访办理意见书，查看索引生成的分块内容，确认核心办理节点的语义未被截断。
- 检索同一诉求的历史信访记录，核对返回结果的数量符合单次搜索上限的配置要求。
- 配置每日增量同步任务，次日查看索引更新日志，确认仅同步当日新增的信访数据。
- 调用向量生成接口，测试本地m3e模型的调用响应，确认未出现超时报错。
