# 信访事项办理的台账汇总与报告生成：知识库检索与召回

## 这个品类的数据长什么样
本品类数据主要来自国家信访信息系统、地方信访系统、12345平台、基层治理平台及历史信访档案，更新频率为每日。日常文档包含信访登记表、受理告知书、转送交办函、办理意见书、复查复核申请、化解方案等，数据字段涵盖诉求主体、事项内容、办理节点、责任单位、办理结果等，单条数据体量随事项流程推进逐步丰富。

## 这些特征在「知识库检索与召回」这一环带来什么约束
每日更新的海量信访数据要求检索召回环节支持增量同步与高频刷新，避免数据滞后影响台账汇总的时效性。多类型结构化与非结构化文档混合，需要适配不同文档格式的解析规则，确保信访事项的关键信息被准确提取。数据关联责任单位、办理流程等字段，要求检索时能按业务属性过滤召回结果，避免无关信访事项干扰台账整理。历史档案与实时数据并存，需区分当前办理事项与过往积案的检索优先级，保障基层办理人员的信息获取效率。数据错误或滞后可能引发重复信访、越级信访等后果，因此检索召回的准确性要求较高。

## 配置怎么定
仅作参考；请以目标 FastGPT 发布版本与部署文档核验。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `similarity` | 0.75–0.85 | 适配信访事项表述差异较大的特点，过滤低相关性召回结果，保障核心诉求匹配度 |
| `limit` | 前8–12条 | 控制单次召回结果数量，避免台账汇总时信息过载，符合基层办理人员的信息阅读习惯 |
| `searchMode` | hybrid | 结合关键词与语义检索，适配信访事项中既有固定格式文档又有自由文本诉求的场景 |
| `usingReRank` | 开启 | 对初始召回结果二次排序，优先匹配信访事项的办理流程、责任单位等关键字段 |
| `datasetSearchUsingExtensionQuery` | 开启 | 基于用户问题自动扩展相关表述，覆盖信访事项中常见的同义诉求与政策术语 |
| `collectionIds` | 按信访业务集合指定 | 限定检索范围仅为信访事项相关知识库集合，避免跨品类数据干扰 |

## 容易做错的三处
- 首次检索无法召回目标信访事项，第二次检索可正常返回。原因是初始检索未开启`datasetSearchUsingExtensionQuery`，未针对信访诉求的同义表述进行扩展，导致语义匹配偏差。
- 导入HTTP响应数据作为知识库引用后无匹配结果。原因是未将响应数据整理为信访事项的标准文档格式，未包含诉求主体、办理节点等关键业务字段。
- 检索结果包含非信访类业务数据。原因是未通过`collectionIds`限定检索范围，混入了其他业务集合的文档内容。

## 怎么确认配好了
- 导入一条历史信访档案数据，检索包含该事项关键诉求的问题，核对召回结果的匹配度与数量是否符合配置要求。
- 查看检索日志，确认`searchMode`、`usingReRank`参数已生效，检索范围仅覆盖指定的信访业务集合。
- 模拟每日增量数据同步，检查检索系统是否能及时召回新增的信访事项文档。
- 测试问题扩展功能，输入简化的信访诉求，确认系统自动扩展相关表述后可召回对应结果。
