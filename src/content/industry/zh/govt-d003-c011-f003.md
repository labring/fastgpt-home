# 养老、工伤、失业待遇核定的台账汇总与报告生成：多轮对话与提示词

## 这个品类的数据长什么样
本品类数据主要来自社会保险经办系统、个人权益记录、劳动关系和工伤认定系统、电子社保卡平台，每日更新。日常处理的文档包括待遇申领表、缴费年限证明、退休审批表、工伤认定材料、失业保险金申领材料，数据字段包含待遇类型、核定金额、申领人身份信息、审核状态、业务办理节点等，不同待遇类型对应专属的数据结构与校验逻辑。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
多系统来源的数据要求多轮对话流程支持跨数据源的动态调用，确保每次交互都能获取最新的经办系统、权益记录等信息。每日更新的频率要求对话环节设置实时数据拉取机制，避免使用过期的核定数据。多样的业务文档结构要求提示词针对不同材料预设解析规则，精准提取对应字段。多且细分的业务字段要求对话过程中明确字段定义，避免核定金额、申领信息等核心字段的匹配偏差，确保台账汇总的准确性。

## 配置怎么定
以下配置基于 FastGPT v4.17.0 版本适配。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 8000–12000 字符 | 适配多份社保业务文档的总文本长度，避免截断核心核定信息 |
| `variables` 绑定参数 | 绑定待遇类型、申领人ID | 精准拉取对应参保人的个人权益记录与经办数据，缩小查询范围 |
| `messages` 历史保留条数 | 前 20 条对话 | 保留核心业务交互逻辑，过滤冗余的非业务内容，避免干扰核定判断 |
| `chatId` 会话隔离规则 | 按业务批次隔离 | 区分不同待遇核定任务，防止不同批次的对话数据互相混淆 |
| 问题自动优化 | 开启 | 自动梳理用户的多轮诉求，明确核定所需的核心材料与校验参数 |

## 容易做错的三处
- 现象：调用http请求编排节点后，核定结果的输出字段未在对话界面展示。原因：未在对话节点配置将http返回内容绑定至`variables`参数，导致输出未接入对话上下文。
- 现象：多轮对话中重复出现相同的材料核验问题。原因：未限制`messages`历史保留条数，冗余的历史提示词重复触发核验逻辑。
- 现象：跨批次的待遇核定数据出现串用。原因：未按业务批次设置`chatId`隔离规则，导致不同会话的数据互相覆盖。

## 怎么确认配好了
- 发起一笔单批次的待遇核定测试对话，核对对话中调用的`variables`参数是否绑定了正确的申领人信息与待遇类型。
- 查看会话历史记录，确认`messages`参数保留的对话条数符合预设范围，无冗余的非业务交互内容。
- 启动两个不同批次的核定会话，确认`chatId`隔离规则生效，数据不会在会话间互相串用。
- 触发http编排节点后，检查对话界面是否展示了返回的核定结果相关字段。
