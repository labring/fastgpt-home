# 养老服务机构监管的台账汇总与报告生成：工具调用与插件

## 这个品类的数据长什么样
养老服务机构监管的台账数据通常来自养老服务信息平台、民政统计系统、消防检查记录、机构运营台账四类来源，更新频率为月度。日常涉及的文档包括备案材料、运营补贴申请、服务质量检查表、安全隐患整改台账、老人入住档案，核心字段包含机构名称、床位数量、检查日期、整改状态等，单位多为张、次、天等，部分非结构化文档需先完成格式转换后才可用于汇总分析。

## 这些特征在「工具调用与插件」这一环带来什么约束
由于数据来源分散且更新周期固定为月度，工具调用需支持跨系统数据拉取与定时触发配置；不同文档的字段格式存在差异，插件需支持自定义字段映射规则以适配备案、补贴、检查等多类台账；监管数据的核对环节耗时较长，工具调用需自动完成跨数据源的字段对比以减少人工工作量；同时因出错后果涉及补贴发放、安全监管等环节，插件需内置基础校验逻辑以过滤异常数据。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | 适配多源异构的监管数据拉取需求，自动选择合适的插件节点 |
| `functionCall` | `required` | 强制插件完成台账字段提取与汇总，避免遗漏核心监管数据 |
| 定时触发周期 | 每月1日 0点 | 匹配监管台账的月度更新频率 |
| 插件输入字段映射 | 按机构ID、床位数量、检查日期映射 | 匹配养老服务监管台账的核心字段标准 |
| 重试次数 | 3 次 | 应对跨系统数据拉取时的网络波动或接口临时异常 |
| 单次拉取数据上限 | 1000 条 | 适配单月养老机构监管数据的常规规模 |

## 容易做错的三处
- 现象：自定义插件添加到工作流后无输入输出参数栏，日志无报错信息。原因：未在插件配置中正确声明`functionCall`的参数结构，导致工作流无法识别插件输入输出项。
- 现象：上传养老服务台账文件后解析结果字段为空，无法完成后续汇总。原因：未将文档解析工具的输出路径正确传递给后续插件节点，导致数据链路断裂。
- 现象：调用台账汇总接口时出现超时错误，响应时长超出常规阈值。原因：未限制`toolChoice`的调用范围，导致多系统并行请求过多，超出接口承载能力。

## 怎么确认配好了
- 手动触发插件调用，检查返回结果是否包含机构名称、床位数量、检查日期等核心监管字段。
- 查看工作流运行日志，确认`functionCall`被正确触发且无参数校验报错。
- 测试定时触发任务，确认在每月1日0点自动拉取对应数据源的台账数据。
- 模拟跨系统数据拉取失败场景，检查插件是否自动触发预设次数的重试操作。
