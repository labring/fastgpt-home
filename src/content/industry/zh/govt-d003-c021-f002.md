# 国库集中支付与报销审核的台账汇总与报告生成：向量模型与索引

## 这个品类的数据长什么样
数据来源为国库集中支付系统、预算管理一体化系统、电子发票平台、合同管理系统，每日更新。日常处理的文档包括支付申请、用款计划、发票、合同、验收单、报销审批单、支付凭证，各类文档对应专属业务字段，如支付申请含申请单号、预算科目编码，发票含发票号码、开票金额，合同含合同编号、履约金额，所有数据均围绕单笔资金支付的全流程审核与执行展开。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源数据接入要求索引支持跨系统数据的统一映射，避免出现字段不匹配的问题；每日更新的频率要求配置增量索引策略，减少全量索引的重复计算开销；文档类型多样且长度差异较大，需要适配不同文档的分块规则，避免破坏业务逻辑；单笔资金审核的严谨性要求，决定了相似度匹配的阈值需严格控制，避免误匹配导致的合规风险；全流程数据的关联性要求索引需覆盖预算指标、经济分类、审批节点等核心审核字段，确保检索结果能支撑完整的合规校验。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配单份支付凭证、发票的常规长度，避免分块破坏业务关联信息 |
| 重叠长度 | 50–80 字符 | 保留跨分块的合同编号、支付单号等关键标识，确保检索时的上下文完整性 |
| 相似度阈值 | 0.75–0.85 | 适配财政数据的严谨性要求，降低误匹配概率，符合国库审核的合规标准；若使用国产向量模型，需根据模型的输出精度调整该区间 |
| 单次搜索上限 | 前10条 | 控制返回结果的数量，适配单笔支付审核的单次核对需求 |
| `defaultToken` | 2000 | 满足单批次台账汇总的上下文长度要求，确保核心审核字段完整传递 |
| `maxToken` | 8000 | 适配报告生成时的总token消耗限制，避免生成过程中出现截断报错 |

## 容易做错的三处
- 尝试通过MongoDB直接管理向量库时，无法同步业务系统的更新数据。未通过FastGPT官方的向量库管理接口操作，直接修改底层存储会破坏索引的一致性与完整性。
- 调用向量模型时返回403拒绝错误，curl测试正常。未配置FastGPT的向量模型访问白名单，或ollama部署的端口未开放到FastGPT服务所在网络。
- 知识库索引合并后仍存在重复的支付凭证记录。未开启索引去重配置，或去重阈值设置过高导致未识别到重复条目。

## 怎么确认配好了
本文基于FastGPT v4.17.0版本编写。
- 导入单份支付凭证文档，检查分块结果是否覆盖完整业务字段，无关键信息截断。
- 发起一笔报销审核的检索请求，核对返回结果的数量是否符合单次搜索上限的设置。
- 查看向量模型调用日志，确认`defaultToken`和`maxToken`的消耗未触发截断或报错。
- 执行一次索引合并操作，检查重复数据的识别结果是否符合预期阈值。
