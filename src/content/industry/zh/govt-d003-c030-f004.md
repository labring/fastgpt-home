# 建设工程质量安全监督的台账汇总与报告生成：工作流编排

## 这个品类的数据长什么样
本品类的数据主要来自工程质量安全监管系统、施工现场实名制平台、监理日志、检测报告四类渠道。日常生成的文档包含监督计划、监督检查记录、隐患整改通知书、质量问题处理单、竣工验收监督报告，各文档包含固定字段：监督计划含监督日期、监督范围、参建单位；监督检查记录含检查点位、问题描述、整改时限；隐患整改通知书含整改编号、整改内容、责任单位。数据更新频率为周度，单次汇总覆盖当周所有生成的文档，字段类型多为文本、日期、枚举值，无复杂嵌套结构。

## 这些特征在「工作流编排」这一环带来什么约束
本品类的数据多源分散、周度更新，要求工作流支持对接多类外部系统拉取数据，避免手动录入的误差。固定字段结构要求工作流配置统一的字段映射规则，将不同来源的异构数据转换为标准台账格式。跟踪隐患整改闭环的核心需求，要求工作流支持`variables`存储整改状态、验收进度等全局状态，跨节点传递数据。质量事故类的出错后果，要求工作流配置异常校验节点，对缺失字段、逾期数据触发告警。周度汇总的频率要求工作流配置定时触发机制，按固定周期自动启动执行。

## 配置怎么定
本配置基于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` | 按使用者ID隔离 | 区分不同监管人员的项目数据，避免跨用户数据混淆 |
| `nodeId` | 为每个外部数据源节点分配唯一标识 | 精准匹配跨节点传递的数据源，确保数据流向正确 |
| 定时触发周期 | 每周一 09:00 | 匹配周度数据更新的常规窗口，契合监管工作的日常节奏 |
| 全局变量存储上限 | 1000 MB | 存储单季度的周度台账、整改记录与验收数据，满足常规存储需求 |
| 字段映射长度 | 800–1200 字符 | 适配监管文档的常规文本长度，避免截断关键信息 |
| 异常校验阈值 | 前5条异常数据触发告警 | 优先处理最紧急的缺失字段或逾期数据，降低出错风险 |

## 容易做错的三处
- 现象：调用工作流API后，未加载历史台账数据，`variables`中存储的整改状态为空。原因：未在API请求中携带`variables`参数，或未配置工作流的上下文加载节点读取历史全局变量。
- 现象：多数据源节点拉取的数据出现交叉覆盖，最终台账数据混乱。原因：未为每个数据源节点配置唯一`nodeId`，导致跨节点数据传递时无法精准识别来源。
- 现象：AI回复后未生成定制化的整改引导语，仅显示默认提示。原因：未在工作流的AI回复节点后配置定制化引导语生成步骤，依赖系统默认的猜你想问功能。

## 怎么确认配好了
- 手动触发工作流一次，检查拉取的数据源是否与指定的工程质量安全监管系统、监理日志数据一致。
- 切换不同使用者ID登录，查看`variables`存储的全局变量，确认数据相互隔离无交叉。
- 模拟缺失字段的数据源数据输入，检查是否触发预设的异常告警机制。
- 等待定时触发周期到达，确认工作流自动启动并生成当周的台账汇总与报告。
