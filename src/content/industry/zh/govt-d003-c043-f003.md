# 特种设备安全监管的台账汇总与报告生成：多轮对话与提示词

## 这个品类的数据长什么样
本品类数据来自特种设备安全监察系统、检验检测机构系统、使用单位台账及作业人员证书库，更新频率为每月一次。日常文档包含使用登记证、定期检验报告、维保记录、隐患整改通知书、事故报告、作业人员证书，各文档包含设备编号、检验周期、维保单位、作业人员资质编号、整改状态等字段，数据以结构化台账和非结构化文档混合形式存储。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源分散，跨系统调取需多轮对话逐步对齐不同系统的字段差异；月度更新的特性要求提示词固定调用最新月度数据源，避免使用过期信息。设备相关文档字段命名存在差异，多轮对话需逐步引导明确设备类型与对应字段。隐患整改跟踪需跨多份文档核对销号状态，多轮对话需按环节梳理整改、验收、归档的关联信息。作业人员资质校验需结合最新证书库数据，提示词需限定调用月度更新的证书库内容。

## 配置怎么定
本文基于 FastGPT v4.17.0 版本配置

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `chatId` | 固定会话ID绑定专属监管台账 | 特种设备监管需长期关联同一监管对象，固定chatId可维持多轮对话的上下文一致性 |
| `messages` | 保留前6条对话上下文 | 监管场景需核对多环节的历史操作记录，6条上下文可覆盖单次监管任务的全流程信息 |
| `variables` | 传入设备编号、监管周期两个全局变量 | 快速定位对应台账数据，减少对话中重复询问的次数 |
| 最大上下文 | 8000–12000 token | 特种设备相关文档篇幅较长，需足够上下文容纳多份报告与台账内容 |
| 单次匹配上限 | 前3条匹配结果 | 监管数据需精准匹配，过多结果会干扰提示词的信息提取 |
| 超时阈值 | 600秒 | 跨系统调取多份台账数据需充足时间，避免因超时中断对话 |

## 容易做错的三处
- 现象：设置对话历史保留条数为6，但模型无法关联上一轮问题的上下文。原因：未正确绑定`messages`参数，或上下文存储配置未覆盖指定条数的对话记录。
- 现象：从台账数据中提取的关键信息显示为乱码。原因：未在提示词中指定标准化输出格式，未对跨系统返回的非标准化文本做统一编码处理。
- 现象：iframe嵌入聊天窗口后，闲置会话持续占用服务资源。原因：未配置会话闲置自动释放规则，导致未活跃的会话未被及时清理。

## 怎么确认配好了
- 发起一轮包含设备编号查询的对话，再发起一轮关联该设备的整改状态查询，核对模型是否能正确关联前一轮的设备信息。
- 导入一份特种设备维保记录文档，使用提示词提取关键字段，核对输出结果无乱码且字段完整。
- 发起闲置对话，等待预设的超时阈值后，核对会话是否被自动释放，服务资源未被持续占用。
- 传入`variables`参数中的设备编号，核对对话是否直接定位到对应台账数据，无需重复询问设备信息。
