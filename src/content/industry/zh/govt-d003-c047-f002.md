# 行政处罚案卷办理的台账汇总与报告生成：向量模型与索引

## 这个品类的数据长什么样
本品类数据来自市场监管、生态环境、交通运输等执法机构的行政执法办案系统、执法记录仪影像、国家企业信用信息公示系统及部门监管数据库。数据更新频率为每日，日常文档包含现场检查笔录、询问笔录、证据清单、行政处罚事先告知书、处罚决定书、送达回证等。数据字段包含执法主体、违法事实、处罚依据、文书编号、送达日期等，结构固定且需形成完整处罚证据链。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源数据类型带来的混合索引需求，需同时支持文本案卷与执法影像的向量提取。每日增量更新要求索引系统支持高效的增量同步与去重，避免重复存储相同案卷内容。固定结构的执法文书要求分块逻辑需贴合文书章节，避免割裂证据链相关内容。处罚案卷的严谨性要求索引匹配精度需严格控制，防止误关联无关案卷导致执法失误。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 贴合行政处罚文书单段内容的语义完整性，避免关键证据被截断 |
| 重叠长度 | 100–150 字符 | 衔接相邻分块的执法逻辑，防止证据链关键信息被分割在两个分块中 |
| `defaultToken` | 4096 token | 覆盖单份核心案卷的完整上下文，满足台账汇总的信息提取需求 |
| `maxToken` | 8192 token | 限制单次加载的总内容长度，避免批量索引时出现超时错误 |
| 相似度阈值 | 0.75–0.85 | 区分相似违法事实与重复案卷，减少误匹配的概率 |
| 单次搜索上限 | 前 8 条 | 匹配执法案卷的常规关联数量，覆盖核心证据与文书内容 |

## 容易做错的三处
- 现象：单份行政处罚案卷上传时显示分8段，后续查看索引记录变为13段且存在重复片段。原因：未开启索引去重校验，系统自动重新分块时未关联原有索引的分段记录。
- 现象：升级FastGPT v4.17.0后，原有可检索的案卷内容无法被正常查询。原因：版本迭代后索引格式发生更新，未执行全量重新索引操作。
- 现象：向量模型训练仅支持单文件调整参数后上传，无法批量执行训练任务。原因：未配置批量索引触发规则，系统默认按单文件提交训练任务。

## 怎么确认配好了
- 上传一份标准行政处罚决定书，检查分块预览数量与预期一致，无重复分段记录。
- 发起关联特定违法事实的检索请求，验证返回结果包含对应笔录、证据清单等关联文档。
- 调整`defaultToken`参数后提交批量索引任务，确认任务日志显示参数已按设定值生效。
- 查看每日增量索引的统计数据，确认更新数量与当日执法案卷的实际生成数量匹配。
