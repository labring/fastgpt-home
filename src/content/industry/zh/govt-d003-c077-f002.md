# 城市公交的台账汇总与报告生成：向量模型与索引

## 这个品类的数据长什么样
数据来源于公交运营调度系统、车载GPS终端、IC卡收费设备与场站管理系统。更新节奏按运营班次生成单条记录，每日汇总生成当日全线路台账文档。文档结构包含线路编号、班次编号、发车时刻、到站时刻、载客人次、行驶里程、停靠站点数、能耗消耗值等字段，时间单位为时分秒，里程单位为公里，载客量单位为人次，能耗单位为升或千瓦时。

## 这些特征在「向量模型与索引」这一环带来什么约束
台账按班次生成的单条记录体量小但批量大，每日汇总后的数据量增长稳定，索引构建需支持增量更新以匹配班次级的实时更新节奏，避免全量索引的重复计算。多字段包含不同业务语义与计量单位，向量模型需适配结构化字段的语义编码，避免不同单位字段的编码偏差影响检索准确性。台账数据存在明确的关联关系，如同线路、同驾驶员的班次，索引需支持基于字段的过滤检索，以快速定位目标范围的运营数据。

## 配置怎么定
本配置基于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 城市公交台账单条记录字段较多，分块长度覆盖单趟班次的完整运营信息，避免语义割裂 |
| 重叠长度 | 100–150 字符 | 保留相邻分块的重叠内容，保障同班次台账的语义连贯性 |
| 相似度阈值 | 0.75–0.85 | 区分同线路不同班次的运营差异，避免无关台账被误召回 |
| 单次搜索上限 | 前10条 | 台账汇总需覆盖核心班次数据，10条可覆盖主要运营场景 |
| `maxToken` | 8192 | 适配城市公交当日汇总台账的总长度，满足长文本的向量编码需求 |
| `defaultToken` | 按平台默认配置或自定义访问密钥 | 用于标识embedding模型的调用权限，适配不同模型的接入需求 |
| 最大上下文 | 3000–4000 字符 | 召回的台账数据需支撑报告生成的上下文需求，避免超出模型处理上限 |

## 容易做错的三处
- 现象：调用批量上传接口后界面长期显示索引中，无进度更新。原因：未配置增量索引的触发规则，全量索引加载了超出处理能力的历史台账数据，导致索引构建停滞。
- 现象：调用embedding相关功能时返回权限错误，提示指定模型无权使用。原因：未配置`defaultToken`的有效权限，或使用了未授权的模型标识。
- 现象：召回的台账数据与检索需求匹配度低，结果偏差过大。原因：相似度阈值设置不合理，过高导致召回结果过少，过低导致无关数据混入。

## 怎么确认配好了
- 上传单条当日台账数据，查看平台生成的索引日志，确认向量编码完成且无报错信息。
- 输入贴合业务的检索关键词，如“10路线路当日载客情况”，核对召回结果的字段与台账数据的实际内容一致。
- 调整相似度阈值后重新发起检索，确认召回结果的数量随阈值变化符合预期逻辑。
- 查看平台的索引统计面板，确认已索引的文档数量与上传的台账数量匹配。
