# 城市燃气的台账汇总与报告生成：数据库与运维

仅作参考；请以目标 FastGPT 发布版本与部署文档核验。

## 这个品类的数据长什么样
城市燃气的台账数据来源于管网压力监测终端、场站巡检设备、运维工单系统、用户缴费系统四类核心业务数据源。数据更新节奏覆盖实时（压力监测）、每小时（巡检记录）、随工单触发（运维记录）、每日（用户缴费台账）四种类型。单份台账文档包含管网节点ID、场站编号、巡检时间、压力值、泄漏检测结果、运维人员ID、工单状态等字段，其中压力值单位为kPa，巡检时间采用ISO 8601格式，工单状态为预设枚举值。

## 这些特征在「数据库与运维」这一环带来什么约束
多源异构的数据更新节奏带来混合读写压力，高频实时数据会占用大量数据库连接资源，需提前规划连接池容量。结构化与非结构化数据并存，需拆分存储以优化查询性能，同时需建立字段索引保障台账汇总时的关联查询效率。数据格式的不一致性要求前置清洗环节，避免脏数据进入汇总流程。长期留存的台账数据需规划扩容路径，保障历史数据可追溯。运维过程中需监控数据完整性，燃气相关数据异常可能影响后续业务决策。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://<user>:<pass>@<host>:27017/gas_ledger?authSource=admin&readPreference=secondaryPreferred` | 燃气巡检的非结构化记录适合MongoDB存储，使用副本集优先读取减轻主库写入压力，指定业务库避免数据混淆 |
| `PG_URL` | `postgresql://<user>:<pass>@<host>:5432/gas_ops?sslmode=require` | 结构化的工单、用户台账数据适合关系型存储，开启SSL保障传输安全 |
| `DB_MAX_LINK` | `20–30 个连接` | 单节点并发写入/查询峰值约15次/秒，预留冗余连接应对批量汇总任务 |
| `REDIS_URL` | `redis://<host>:6379/0?maxmemory-policy=allkeys-lru` | 缓存高频查询的管网节点基础信息，LRU策略避免内存溢出 |

## 容易做错的三处
- 现象：配置`MONGODB_URI`后出现认证失败或无法解析主机的报错，无法连接数据库。原因：未正确配置`authSource`参数，或本地部署时未开放MongoDB的默认端口，且未将绑定地址修改为0.0.0.0。
- 现象：批量台账汇总任务耗时过长，工作流TPS低于预期。原因：未设置合理的`DB_MAX_LINK`值，连接池不足导致任务排队等待，或未对管网ID、巡检时间字段创建联合索引，影响关联查询性能。
- 现象：工具调用后返回结果不符合预设逻辑，部分场景下未调用知识库直接返回固定回复，或未在知识库匹配到内容时触发指定回复。原因：未正确配置搜索触发条件，或未在工作流中绑定知识库与工具调用的关联关系，导致触发逻辑混乱。

## 怎么确认配好了
- 执行数据库客户端命令连接`MONGODB_URI`指定的业务库，验证是否能查询到预设的管网节点台账记录。
- 运行批量汇总测试脚本，观察数据库连接使用情况，确认连接数未达到`DB_MAX_LINK`设定的上限。
- 在FastGPT后台的数据库管理模块查看表模型，确认结构化台账的字段与预设结构一致。
- 触发一次完整的台账生成任务，检查系统日志中是否出现数据库连接超时或写入失败的报错。
