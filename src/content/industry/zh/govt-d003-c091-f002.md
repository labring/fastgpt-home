# 房建工程总承包的台账汇总与报告生成：向量模型与索引

## 这个品类的数据长什么样
房建工程总承包的台账数据主要来源于项目管理系统、材料进场单、进度周报、验收单据等。数据更新节奏随业务节点变化：材料进场时实时更新，进度周报每周更新，月度成本台账每月汇总。文档包含结构化表格与非结构化报告两类，结构化字段包含项目编号、工程名称、施工班组、材料用量（吨）、单体建筑面积（平方米）、验收状态等，部分文档附带现场拍摄的关联照片。

## 这些特征在「向量模型与索引」这一环带来什么约束
数据分散多源导致索引需支持跨系统聚合，避免遗漏跨部门的关联台账；更新节奏不均要求采用增量索引策略，仅对变更内容重新生成向量，降低计算成本；专业字段与单位的存在要求向量模型保留术语语义，不能破坏专业表述的完整性；单项目台账条目可达数百条，生成报告时需整合多类数据，对上下文窗口有明确要求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 房建台账单条条目多为数百字，过长分块会丢失上下文关联，过短会破坏专业术语完整性 |
| 重叠长度 | 100–150 字符 | 台账条目存在连续的专业字段，重叠可保留材料型号、用量等字段间的语义关联 |
| 相似度阈值 | 0.72–0.80 | 房建专业术语辨识度高，阈值过低会引入无关台账条目，过高会遗漏相关内容 |
| 单次搜索上限 | 前 8 条 | 单项目台账条目集中在数百条，前8条可覆盖核心关联内容，避免冗余数据干扰报告生成 |
| `maxToken` | 8000 token | 房建报告生成需整合多类台账数据，8000 token可容纳3-4份完整台账的核心内容 |
| `defaultToken` | 2000 token | 单条台账的向量生成所需token量，适配多数开源向量模型的输入限制 |

## 容易做错的三处
- 现象：索引生成时出现专业术语被拆分的情况，或检索结果中材料型号、面积等字段不完整。原因：未针对房建台账的专业字段调整分块长度，导致关键术语被拆分至不同分块。
- 现象：检索返回结果条数远低于预期，或生成报告时出现上下文溢出提示。原因：未合理设置`maxToken`，导致整合的台账数据超出模型上下文限制，系统自动截断关键内容。
- 现象：不同向量模型生成的检索结果差异过大，无法统一检索逻辑。原因：混用不同语义空间的向量模型，导致索引与查询的向量维度不匹配，无法形成统一的检索标准。

## 怎么确认配好了
- 上传单份房建材料进场台账，检查分块后的文本是否保留完整的材料型号、用量等专业字段，无强制截断情况。
- 输入“查看XX项目3月钢筋进场台账”类查询，核对返回结果的相似度分值是否落在0.72–0.80区间内。
- 生成单份项目进度报告，检查生成内容是否整合了所有关联的台账条目，无上下文缺失提示。
- 切换至FastGPT v4.17.0版本的不同向量模型测试，确认检索结果的语义一致性，无明显的结果偏差。
