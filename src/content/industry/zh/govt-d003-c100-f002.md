# 油田工程服务的台账汇总与报告生成：向量模型与索引

## 这个品类的数据长什么样
油田工程服务的台账数据主要来自现场施工日报、设备巡检记录、材料领用单据、安全检查台账及施工日志。数据按每日施工节点更新，单份文档既有结构化字段，如施工班组编号、设备型号、材料用量（单位为吨、立方米、小时）、巡检时间，也包含非结构化的现场工况描述与隐患整改记录。文档字段固定性强，部分字段存在固定枚举值，单份文档字符量跨度较大。

## 这些特征在「向量模型与索引」这一环带来什么约束
油田工程服务台账的结构化字段占比高且存在固定枚举值，无需对枚举字段执行向量索引，可直接通过精确匹配筛选数据，降低向量库的计算负载。数值型字段如材料用量带有明确单位，通用向量模型易混淆单位与数值的关联，需单独配置数值向量化规则。按施工节点更新的数据具备增量更新需求，需支持断点续传的增量索引流程，避免全量重建带来的资源消耗。非结构化施工日志的字符跨度较大，需适配灵活的分块边界规则，防止关键工况描述被截断。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配油田施工日志的字符跨度，避免单块过长或过短 |
| 重叠长度 | 100–200 字符 | 保留相邻分块的上下文关联，防止施工流程的断点信息丢失 |
| 相似度阈值 | 0.75–0.85 | 匹配设备编号、隐患等级这类枚举字段的精确匹配需求，避免误匹配 |
| `defaultToken` | 600 秒 | 配置向量索引的超时时间，适配增量更新的批量数据处理 |
| `maxToken` | 4096 | 适配主流embedding模型的输入长度限制，避免文本截断 |
| 单次搜索上限 | 前10条 | 兼顾召回效率与台账数据的批量查询需求 |

## 容易做错的三处
- 现象为docker部署环境下向量索引任务持续处于排队状态无进度，原因是未配置`defaultToken`的合理超时时间，导致批量增量索引任务被系统自动终止。
- 现象为向量召回结果中出现单位不匹配的材料用量数据，原因是未对数值型字段单独配置向量化规则，通用向量模型混淆了数值与单位的关联。
- 现象为长文本施工日志的索引结果存在关键信息缺失，原因是分块长度设置不合理，导致长文本被截断后丢失核心工况描述。

## 怎么确认配好了
- 查看向量索引任务的日志，确认增量更新仅处理新增的施工台账数据，不进行全量重建。
- 随机抽取一份施工日志文档，检查分块后的向量数据是否保留完整的上下文关联，无异常截断。
- 测试数值型字段的召回结果，确认匹配结果仅关联同单位的业务数据，无跨单位误判。
- 核对向量索引的超时配置，确认任务执行时长符合预设的合理范围，无强制中断情况。
