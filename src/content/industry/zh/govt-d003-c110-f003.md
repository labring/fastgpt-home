# 矿山采选的台账汇总与报告生成：多轮对话与提示词

## 这个品类的数据长什么样
数据来源包括采矿现场的传感器采集记录、选矿车间的班组手工台账、质检部门的物料检测记录。更新节奏为每班结束后汇总，或每日固定时点更新。文档多为结构化表格形式，单条记录包含作业时间、设备编号、处理量、原料品质检测值、精矿产出量等字段，处理量单位为吨，作业时长单位为小时，设备运行参数单位为千帕。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源分散且分属不同岗位产出，多轮对话中需明确区分不同上传文件的归属场景，提示词需预先定义文件分类规则。更新频率较高，每次汇总需限定时间范围，`messages`上下文需携带上一轮确认的时间区间参数，避免跨时段数据混淆。结构化字段多且单位不统一，提示词需明确指定字段提取的格式与对应单位，防止结果出现单位错误。单条记录量较大，多轮对话中需限制单次召回的记录条数，避免上下文过载。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文 | 8000–12000 token | 矿山采选台账单批次数据量较大，需保留足够上下文以关联多轮提问与历史数据，适配FastGPT v4.17.0版本的上下文上限要求 |
| 单次搜索上限 | 前20条 | 避免过多历史记录导致上下文过载，同时覆盖当班主要作业数据的查询需求 |
| 变量配置 | `variables` 中添加时间范围变量 | 需动态限定汇总数据的时段，适配不同班次或日期的查询需求，实现精准数据召回 |
| 问题优化 | 开启 | 将口语化的台账查询需求转换为结构化的字段提取指令，提升品类专属字段的识别准确率 |
| 单次上传文件数 | 5个以内 | 矿山采选的台账文件多为单班组或单车间的单类数据，过多文件会混淆分类逻辑，降低提取效率 |

## 容易做错的三处
- 现象：多轮对话中上传的传感器数据与手工台账无法被正确区分，提取字段时出现混淆。原因：未在提示词中预先定义不同上传文件的分类规则，未通过`variables`配置文件类型标识。
- 现象：对话过程中出现Cannot read properties of null (reading 'q)报错。原因：未正确配置`messages`上下文的格式，空值字段未做前置处理，导致模型调用时解析失败。
- 现象：工作流中问题分类结果与实际台账类型不符，识别准确率低。原因：提示词未结合矿山采选台账的专属字段（如设备编号、处理量单位）进行限定，通用分类逻辑无法适配品类特征。

## 怎么确认配好了
- 上传2份不同类型的矿山采选台账文件，检查提示词是否能分别提取对应字段，确认文件分类生效。
- 在`variables`中配置测试时间范围，发起多轮对话，检查返回结果是否仅包含该时段内的数据。
- 发起连续3轮不同的台账查询请求，检查上下文是否正确保留历史提问与结果，未出现上下文丢失。
- 触发报错场景，检查是否出现Cannot read properties of null (reading 'q)类错误，确认`messages`格式配置正确。
