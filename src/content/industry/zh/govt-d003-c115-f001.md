# 轨道交通装备的台账汇总与报告生成：HTTP 接口与外部系统

## 这个品类的数据长什么样
轨道交通装备的台账数据来源为列车走行部、制动系统、牵引系统的车载采集终端，以及运维班组提交的巡检、检修纸质或电子记录。更新节奏分为两类：实时运行数据每10秒同步一次，月度/年度汇总台账每日更新一次。文档结构为标准化JSON格式，核心字段包括装备编号、部件名称、累计运行时长（单位：小时）、检修次数（单位：次）、上次检修日期、故障记录条数，部分字段需关联车载传感器的原始采集值，无冗余非结构化内容。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
实时运行数据的高频更新要求接口轮询间隔不得超过10秒，否则无法获取最新的装备运行状态。结构化的固定字段要求接口返回时需精准过滤核心字段，避免传输冗余数据。轨道交通装备台账的多维度筛选需求，要求外部系统调用时需携带装备编号、时间范围等查询参数，因此需在接口配置中支持传入筛选条件。此外，单批次台账数据量较大，接口需支持分页查询，避免单次请求超时。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {替换为FastGPT v4.17.0生成的API密钥}` | 遵循平台的接口鉴权规范，确保请求合法 |
| `responseData` | `["equipmentId", "componentName", "runHours", "maintainCount", "lastMaintainDate"]` | 仅返回轨道交通装备台账的核心字段，减少无效数据传输 |
| 单次请求数据条数 | 前 100 条 | 适配单批次台账的合理规模，避免请求超时 |
| 接口超时时间 | 600 秒 | 覆盖数据汇总、清洗的常规耗时，适配轨道交通装备台账的处理周期 |
| `variables` | `{"equipmentType": "EMU", "queryDateRange": ["2024-05-01", "2024-05-31"]}` | 传入精准的筛选参数，匹配轨道交通装备台账的多维度查询需求 |

## 容易做错的三处
- 调用接口时提示event参数未定义，原因是未在`variables`中配置event字段的取值，未遵循接口文档的参数规范。
- 接口返回的台账数据字段缺失，原因是`responseData`配置的字段与实际轨道交通装备台账结构不匹配，遗漏了累计运行时长等核心字段。
- 向知识库上传轨道交通装备台账文档失败，返回参数格式错误，原因是未将Markdown格式的台账内容整理为符合接口要求的结构化文本，未通过`variables`传入正确的文档元数据。

## 怎么确认配好了
- 调用配置完成的HTTP接口，检查返回的HTTP状态码为200，确认请求鉴权通过。
- 对比`responseData`配置的字段与实际返回的JSON结构，确认所有核心字段均存在且单位符合轨道交通装备台账的规范。
- 传入指定的`variables`筛选参数，验证接口返回的台账数据仅包含对应装备类型和日期范围的记录。
- 模拟高频调用接口，确认未出现超时报错，验证超时时间设置合理。
