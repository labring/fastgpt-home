# 轨道交通装备的台账汇总与报告生成：向量模型与索引

## 这个品类的数据长什么样
轨道交通装备的台账数据主要来自设备运维管理系统、月度检修记录文档、备件库存台账、出厂质检报告。数据更新节奏分为三类：实时更新（单次检修完成后同步）、每日更新（备件库存变动）、月度更新（全设备汇总报表）。文档结构包含结构化字段与非结构化附件，结构化字段包括设备编号、检修日期、故障代码、更换备件型号，单位涉及台、运行小时、件、元等，附件多为数十页的现场检修照片与文字说明。

## 这些特征在「向量模型与索引」这一环带来什么约束
轨道交通装备的台账数据混合结构化字段与长文档附件，且更新节奏多样，要求索引支持增量同步与全量重建的灵活切换。单份文档长度跨度大，从短字段条目到数十页的检修报告，需要适配不同长度的文本分块需求。设备编号、故障代码等字段具备固定专业语义，向量模型需兼顾结构化字段与非结构化文本的编码一致性，避免专业术语的语义偏差。大量文档绑定同一设备ID，索引需支持按设备ID过滤召回，防止无关设备的台账内容干扰检索结果。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配轨道交通检修报告的单段语义完整性，避免拆分关键故障描述与处理步骤 |
| 重叠长度 | 100–150 字符 | 保留分块间的上下文衔接，防止长文档的跨块语义断裂，确保专业术语的完整识别 |
| 相似度阈值 | 0.72–0.85 | 适配轨道交通装备台账的专业术语语义相似度，过滤低相关的非目标设备台账 |
| 单次搜索上限 | 前 10 条 | 覆盖单设备多份台账的召回需求，避免遗漏关键检修记录与备件更换信息 |
| maxToken | 4000 token | 匹配FastGPT v4.17.0版本大语言模型的上下文窗口限制，确保召回内容可完整送入模型 |
| defaultToken | 2000 token | 作为默认召回上下文长度，适配常规台账汇总的信息需求，平衡检索效率与内容完整性 |

## 容易做错的三处
- 检索时召回的文档条数与设置的单次搜索上限不符，界面显示召回10条但实际仅返回4条，原因是未开启增量索引的实时同步开关，导致近期更新的检修文档未被纳入当前索引池。
- 大语言模型输出未引用召回的台账内容，反而提示无相关信息，日志显示已召回5份检修文档，但模型回复未提及文档内的故障处理步骤，原因是召回内容的`maxToken`设置超出模型上下文窗口，有效内容被截断后无法被正确读取。
- 索引构建耗时过长，批量导入台账数据时进度停滞超过600秒，原因是分块长度设置过大，导致单块向量计算耗时增加，同时未开启并行索引构建配置。

## 怎么确认配好了
- 上传一份标准轨道交通设备检修台账，查看分块预览界面，确认分块长度与重叠长度符合预设的取值区间。
- 发起针对特定设备编号的检索请求，核对召回文档的设备编号与检索条件匹配，确认相似度阈值生效，过滤了无关设备的台账内容。
- 查看索引构建日志，确认增量更新任务按预设节奏执行，无失败报错信息。
- 测试大语言模型的回复，确认召回的台账内容被完整引用，无上下文截断的提示。
