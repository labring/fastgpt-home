# 轨道交通装备的台账汇总与报告生成：多轮对话与提示词

## 这个品类的数据长什么样
轨道交通装备的台账数据主要来自车载运行传感器、线下检修记录系统、备件库存管理模块。数据更新节奏分为三类：车载传感器数据实时上传，检修记录每日同步，月度汇总台账每自然月末更新。单设备台账文档结构包含设备唯一编号、型号、累计走行公里数、年度检修次数、更换备件型号、故障代码对应详情等字段，单位涵盖千米、天、次等，部分字段需跨系统关联核对。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源分散导致用户需逐步明确设备编号、统计周期等核心参数，多轮对话需通过递进式提问引导用户补充必要信息，避免泛化请求。单设备月度台账文本长度可达数万字符，过长上下文会导致模型混淆不同设备的字段信息，需限制对话上下文的保留范围。字段单位不统一，提示词需明确要求输出结果严格匹配预设单位，避免出现单位转换错误。跨系统数据需关联核对，多轮对话需在生成报告前确认所有关联数据已完成同步。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `chatId` | 绑定当前会话的设备专属知识库ID | 确保对话上下文与对应设备的台账数据关联，避免跨设备数据混入 |
| `messages` | 保留最近12轮对话上下文，截断超出8000字符的旧消息 | 轨道交通装备单设备台账数据量大，过长上下文易导致模型混淆设备编号与字段信息 |
| `variables` | 预设设备编号、统计周期两个必填变量 | 台账汇总需明确目标设备和时间范围，避免生成跨设备或超范围的错误结果 |
| 最大上下文长度 | 8000–12000 token | 适配单设备月度台账的文本长度，避免上下文溢出导致对话中断 |
| 单次召回条数 | 前6条匹配的知识库条目 | 轨道交通装备台账字段固定，过多召回条目会干扰核心字段的提取与汇总 |
| 对话超时时间 | 60秒 | 避免因跨系统数据调取延迟导致对话失败 |

## 容易做错的三处
- 现象：对话返回结果中设备编号与用户指定不符，字段单位混乱。原因：未在`messages`中明确限定上下文仅保留当前设备的对话历史，提示词未强制要求匹配预设`variables`中的参数。
- 现象：调用API接口后返回空结果，状态码为400。原因：未正确传递`variables`中的必填参数，或`messages`格式不符合FastGPT v4.17.0的系统要求。
- 现象：生成的报告包含无关设备的台账数据。原因：未在提示词中明确要求仅使用当前设备的知识库条目，未对召回的知识库条目按设备编号进行过滤。

## 怎么确认配好了
- 手动触发一次对话，输入指定设备编号和统计周期，核对返回结果中是否仅包含该设备的台账数据。
- 查看对话日志，确认`messages`中仅保留当前会话的上下文，未混入其他设备的历史对话内容。
- 调用API接口时，检查`variables`参数是否包含必填的设备编号和统计周期字段，格式符合FastGPT v4.17.0的规范。
- 测试不同统计周期的请求，确认返回结果的时间范围与输入的`variables`参数一致。
