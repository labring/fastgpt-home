# 通信铁塔与基础设施的台账汇总与报告生成：多轮对话与提示词

## 这个品类的数据长什么样
通信铁塔与基础设施的台账数据来源包括基站运维巡检上报系统、铁塔资产确权登记平台、运营商资源管理库。更新节奏分为日常巡检实时更新、月度资产盘点批量更新两类。文档结构多为结构化Excel台账、JSON格式巡检报表、PDF格式资质文件。字段包含铁塔编号、经纬度、安装高度、承重参数、巡检日期、维护人员、故障状态，单位多为米、千克、平方米、标准日期格式。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
通信铁塔台账的多源结构化特征，要求多轮对话中明确区分巡检实时数据与月度盘点数据的上下文边界。字段包含带单位的物理参数，提示词需强制要求输出结果保留对应单位，避免经纬度、高度等参数混淆。多格式文档的处理，需要在多轮交互中逐步引导用户上传对应类型的文件，同时在提示词中限定字段提取的范围，防止跨品类数据混入。不同更新节奏的数据需在会话中标记时间属性，确保汇总报告的时效性准确。

## 配置怎么定
仅作参考；请以目标 FastGPT 发布版本与部署文档核验。
| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| `messages` | 按会话轮次追加，单轮保留不超过10条历史消息 | 通信铁塔台账数据量较大，限制历史消息条数避免上下文溢出 |
| `variables` | 绑定铁塔编号、巡检周期两个全局变量 | 快速定位对应品类的专属台账数据，减少重复输入 |
| `chatId` | 按不同巡检班组创建独立会话ID | 隔离不同班组的台账汇总任务，避免数据混淆 |
| 最大上下文长度 | 8000–12000 token | 适配多源台账文档的批量处理需求 |
| 提示词优化 | 按实测标定 | 针对铁塔台账的字段特征调整指令，确保字段提取准确 |
| 多轮会话超时 | 600 秒 | 避免长时间占用资源，适配复杂台账的汇总流程 |

## 容易做错的三处
- 现象为多轮对话中无法分别上传巡检报告与资产台账文件，原因是未为不同类型的台账文件配置独立的上传入口，导致会话中文件绑定混乱。
- 现象为对话框抛出Cannot read properties of null (reading 'q)报错，原因是`messages`参数中未正确填充用户提问字段，导致会话上下文解析失败。
- 现象为台账分类结果与实际巡检状态不符，原因是提示词未明确限定仅使用铁塔专属字段进行分类，混入了其他品类的参数规则。

## 怎么确认配好了
- 发起一轮测试对话，输入指定铁塔编号，核对`variables`绑定的全局变量是否自动填充对应参数。
- 上传两份不同类型的台账文件，确认会话自动识别文件类型并分配至对应上传入口。
- 检查`messages`参数的历史消息条数，确认未超过预设的单轮上限。
- 触发会话超时测试，确认600秒后会话自动终止且无残留数据。
