# 钢铁冶炼的台账汇总与报告生成：向量模型与索引

## 这个品类的数据长什么样
钢铁冶炼的台账数据来源于各工序实时采集系统与生产管理系统，覆盖炼钢、炼铁、轧钢等环节的单炉生产记录、班组汇总报表与月度统计文档。数据更新节奏分为实时（单炉冶炼过程每30秒生成参数记录）、班结（每班结束后生成班组汇总台账）、日结（每日生成全车间生产台账）三类。单份文档包含炉号、冶炼时长、各阶段温度、合金成分占比、能耗值、质检结果等字段，字段单位涵盖秒、摄氏度、百分比、吨、千瓦时等。

## 这些特征在「向量模型与索引」这一环带来什么约束
实时高频更新的单炉数据量较大，固定大分块会导致embedding语义稀释，全量索引耗时过长，无法适配班结、日结的更新节奏。多字段混合的文档结构要求分块时保留字段标识与上下文，否则检索时易混淆相似参数条目。不同粒度的更新需求需要适配增量与全量索引的混合策略，避免重复处理历史数据。字段单位与语义的强关联要求索引时优先关联字段名与对应数值，提升检索精准度。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配钢铁冶炼台账单条记录的内容长度，避免语义稀释或上下文丢失 |
| 重叠长度 | 150–200 字符 | 保留工序间的关联逻辑，比如升温与保温阶段的过渡信息 |
| `maxToken` | 8192 token | 处理汇总后的长台账文档，避免截断关键生产参数与质检结果 |
| `defaultToken` | 1024 token | 作为基础上下文的默认长度，适配单条台账的基础语义 |
| 单次搜索上限 | 前 10 条 | 覆盖多工序的关联数据，同时控制上下文长度不溢出 |
| 相似度阈值 | 0.72–0.78，按实测标定 | 区分相似工艺参数的台账条目，避免无关结果混入 |
| 重排 | 开启 | 优化检索结果的排序逻辑，匹配台账汇总的多维度关联需求 |

## 容易做错的三处
- 现象：索引构建任务队列长期堆积，界面显示等待时长超过预设阈值。原因：未启用增量索引模式，每次构建索引都扫描全量历史台账数据。
- 现象：检索结果中出现字段为空或参数混淆的条目，比如将“保温时长”误匹配为“冶炼时长”。原因：分块时未保留字段标识，拆分后的片段丢失了语义上下文。
- 现象：通过OpenAPI接口创建的文件集合检索时频繁超时，返回状态码504。原因：未调整分块长度与索引分片参数，单分片数据量过大导致处理耗时过长。

## 怎么确认配好了
- 查看FastGPT v4.17.0的索引管理页面，确认分片大小与分块长度的匹配关系，无明显数据堆积。
- 提交一份包含多工序参数的台账测试数据，检索结果中关联条目匹配度符合设定的相似度阈值范围。
- 调用OpenAPI批量上传10份历史台账文档，查看索引构建完成的耗时符合预期。
- 检查embedding模型的调用日志，确认无`maxToken`超限的报错信息。
