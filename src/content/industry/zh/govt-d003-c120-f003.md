# 铁路运营的台账汇总与报告生成：多轮对话与提示词

## 这个品类的数据长什么样
铁路运营的台账数据来源于现场作业终端、调度指挥平台、客票系统、货运管理系统及线路运维系统。数据更新节奏分为三类：行车调度相关数据实时更新，设备巡检记录按单次作业完成后更新，货运及票务台账按班次或每日更新。文档以结构化字段为主，包含线路编号、车次ID、作业节点、完成时长、异常代码等字段，单位涵盖公里、吨、小时、分钟等，单份台账文档长度随作业规模变化，通常包含数十至数百条结构化记录。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
结构化字段多且单位固定，要求提示词明确指定字段提取规则与单位保留要求，避免模型输出错误的字段或单位。实时数据与静态台账混合存在，多轮对话需传递历史上下文以确保模型能承接上一轮的查询范围。不同数据的更新节奏差异，要求提示词区分实时调用与静态调用的逻辑，避免使用过期数据。铁路作业术语专业性强，多轮对话的提示词需包含行业术语的定义与约束，提升模型理解准确性。同时，部分台账涉及敏感信息，提示词需明确过滤规则，避免泄露涉密内容。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `chatId` | 绑定当前用户的铁路作业工号作为唯一标识 | 确保每个用户只能查看权限内的台账数据，避免跨用户数据泄露 |
| `messages` | 保留最近10轮对话上下文，单轮上下文不超过2000字符 | 适配铁路台账的结构化内容量，避免过长上下文导致模型理解偏差 |
| `variables` | 预设线路编号、车次范围两个全局变量 | 快速限定查询范围，减少无效数据召回，提升多轮对话效率 |
| 最大上下文长度 | 8000–12000 token | 适配铁路多字段台账的内容长度，避免截断关键作业记录 |
| 问题优化 | 开启 | 优化铁路作业专业术语的理解，提升多轮追问的响应准确性 |
| 单次对话超时时间 | 600秒 | 适配铁路台账数据的召回与处理时长，避免因数据量过大导致超时 |

## 容易做错的三处
- 现象：多轮对话中无法承接上一轮的作业节点追问，模型返回无关的通用台账内容。原因：未正确配置`messages`参数，未传递上一轮对话的上下文，导致模型丢失历史作业信息。
- 现象：运行工作流后，所有`<ai对话>`节点的回复都出现在最终聊天对话中。原因：未配置节点的输出隐藏规则，所有节点的输出都被默认加入到对话展示列表。
- 现象：不同用户登录后看到的台账历史对话完全一致，无法区分个人作业记录。原因：未正确绑定`chatId`参数，使用了全局统一的会话ID，导致会话上下文共享。

## 怎么确认配好了
- 以不同铁路作业工号发起对话，核对会话数据的隔离性，确认每个用户只能查看权限内的台账内容。
- 发起连续追问，核对模型能否承接上一轮的查询条件，例如基于上一轮的车次ID追问后续作业节点，确认`messages`参数配置生效。
- 运行包含多个AI对话节点的工作流，核对指定需隐藏的节点输出未展示，其余节点的回复正常显示。
- 触发包含大量结构化台账数据的查询，核对对话是否在设定的超时时间内完成响应，未出现超时报错。
