# 桥梁病害识别的巡检监测与告警研判：多轮对话与提示词

## 这个品类的数据长什么样
来自巡检无人机拍摄的可见光与红外影像、结构应力传感器的实时采样数据、人工巡检的纸质或电子记录。更新节奏按巡检计划执行，单次巡检的影像数据按拍摄批次更新，传感器数据按固定采样周期推送。文档结构分为三类：影像类文件包含拍摄时间、拍摄坐标、巡检人员标识；传感器数据文件包含时间戳、应力值、环境温度值；巡检记录文件包含病害位置描述、初步判定结果。字段包括影像分辨率、坐标参考系WGS84、应力单位MPa、温度单位℃，无统一的文本格式要求。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
无人机影像单张体积较大，多轮对话中一次性传递过多影像会超出上下文限额，需分批次调用并在提示词中明确批次顺序。传感器数据为时序格式，多轮对话需按时间戳排序传递上下文，提示词需指定优先处理最新的告警数据。巡检记录为半结构化文本，不同巡检人员的描述格式不一致，提示词需包含字段提取的明确规则，确保后续分析的一致性。多源数据格式差异较大，多轮对话需先完成格式对齐，提示词需包含数据转换的引导步骤，避免因格式不匹配导致召回失败。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `messages` | 按每轮对话保留不超过20条历史消息 | 桥梁病害数据多为时序或多模态，过多历史消息会超出上下文限额，20条可覆盖常规巡检对话的上下文需求 |
| `variables` | 绑定病害位置、拍摄时间两个自定义变量 | 巡检数据需关联具体位置和时间，便于精准匹配知识库中的病害识别规范与历史案例 |
| `chatId` | 按巡检批次生成唯一chatId | 同一巡检批次的对话需共享上下文，不同批次的对话需隔离数据，避免上下文混淆 |
| 问题优化 | 开启，优化阈值按实测标定 | 巡检告警的描述通常带有口语化特征，优化后可提升知识库召回的准确率 |
| 单次搜索上限 | 前8条 | 桥梁病害的知识库条目多为影像标注和巡检规范，过多条目会导致上下文过载，影响研判结果的准确性 |
| 最大上下文 | 8000 token | 多轮对话需保留巡检历史和当前告警信息，8000 token可覆盖常规巡检对话的上下文需求 |

## 容易做错的三处
- 现象为升级FastGPT v4.17.0后上传巡检影像文件失败，接口返回413状态码。原因是未调整多轮对话的文件上传限额，桥梁病害的单张影像文件体积大于默认上传限制。
- 现象为多轮对话中无法指定特定病害数据集进行搜索，返回的知识库结果混杂无关内容。原因是未通过`variables`绑定目标数据集的标识参数，提示词未明确指定搜索范围。
- 现象为对话窗口提示上下文溢出，无法继续交互。原因是未限制`messages`的历史消息条数，保留了过多非必要的巡检历史数据。

## 怎么确认配好了
- 发起单轮对话，上传单张桥梁病害影像，核对`messages`中是否正确携带影像的拍摄时间、坐标等元数据。
- 设置`variables`绑定目标数据集标识，发起搜索，核对返回结果是否仅包含目标数据集的内容。
- 发起连续5轮对话，核对`chatId`是否保持一致，且上下文未出现丢失。
- 上传多批次巡检数据，核对不同`chatId`的对话上下文是否隔离，无跨批次的内容混杂。
