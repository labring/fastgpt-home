# 隧道告警过滤的巡检监测与告警研判：知识库检索与召回

## 这个品类的数据长什么样
数据来源于隧道沿线部署的应力、温感、振动、沉降等监测设备，以及通风、照明等运维设备的状态采集系统。更新节奏为每10秒至1分钟推送单条或聚合告警条目，文档多为结构化JSON或表格格式，包含告警ID、关联设备编号、告警类型、触发阈值、发生时间、对应隧道段、当前状态等字段，单位涵盖摄氏度、毫米每秒、毫米等物理量单位。

## 这些特征在「知识库检索与召回」这一环带来什么约束
隧道告警数据的结构化属性要求检索需精准匹配设备编号、告警类型等核心字段，避免无关召回。实时更新的采集节奏要求知识库需支持高频增量同步，否则召回结果无法覆盖最新的告警规则与设备状态。单条数据体量小但总条目随隧道里程增长逐步增加，需限制单次召回的结果数量，防止上下文溢出。告警类型覆盖多类物理异常，需结合业务规则过滤无效告警，因此检索环节需关联预设的过滤条件。

## 配置怎么定
仅作参考；请以目标 FastGPT 发布版本与部署文档核验。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `similarity` | 0.78–0.82 | 隧道告警需精准匹配设备编号、告警类型等核心字段，该区间可过滤无关告警同时保留有效匹配结果 |
| `limit` | 前10条 | 单条告警数据体量小，过多召回会超出上下文长度限制，过少则无法覆盖关联的历史告警规则 |
| `searchMode` | 混合检索 | 结合结构化字段与向量特征，适配告警数据的多字段属性 |
| `usingReRank` | 开启 | 可对初始召回结果按业务相关性二次排序，过滤误匹配的告警条目 |
| `datasetSearchUsingExtensionQuery` | 开启 | 可基于告警内容生成扩展查询词，覆盖同义词或专业术语的匹配场景 |
| `collectionIds` | 绑定专属告警知识库集合 | 避免与其他品类的知识库数据混淆，确保检索范围精准 |

## 容易做错的三处
- 现象：调用检索接口时返回`undefined model must match "^(text`报错。原因：未选择官方兼容的嵌入模型，隧道告警数据的结构化特征需适配支持向量检索的嵌入模型，未指定或选择非兼容模型会触发校验错误。
- 现象：检索结果中混杂大量非隧道告警的无关条目。原因：未绑定专属的告警知识库集合，检索范围覆盖了其他品类的文档，导致召回结果不符合业务场景。
- 现象：对话中未关联本地知识库，仍显示知识库引用内容。原因：未关闭对话的知识库引用展示开关，或检索配置中保留了默认的引用展示逻辑，导致无匹配知识库时仍强制展示占位内容。

## 怎么确认配好了
- 上传单条隧道告警测试数据，执行检索动作，核对召回结果是否包含匹配的告警规则文档。
- 调整`similarity`参数区间，观察召回结果的数量变化，确认参数对检索范围的控制符合预期。
- 关闭`usingReRank`配置，对比前后召回结果的排序逻辑，确认重排功能正常生效。
- 查看知识库集合的绑定状态，确认仅包含隧道告警相关的文档，无其他品类的冗余数据。
