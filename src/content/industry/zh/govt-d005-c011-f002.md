# 养老、工伤、失业待遇核定的政策与制度依据问答：向量模型与索引

## 这个品类的数据长什么样
本品类数据来自社会保险经办系统、个人权益记录、劳动关系和工伤认定系统、电子社保卡平台，更新频率为每日。日常处理的文档包括待遇申领表、缴费年限证明、退休审批表、工伤认定材料、失业保险金申领材料，文档多包含参保人身份信息、缴费年限、认定结果、待遇标准字段，单位涉及缴费月数、待遇金额、认定编号等，部分材料为结构化表单与非结构化文本混合。

## 这些特征在「向量模型与索引」这一环带来什么约束
每日更新的数据要求索引支持增量同步，避免全量重建占用过多系统资源。多类型混合文档需要分块策略适配结构化表单与非大段政策文本的拆分，保障语义完整性。参保人身份、缴费年限等核心业务字段的精准性要求高，向量召回需优先匹配此类字段的语义关联。待遇金额、认定编号等带单位的字段需避免向量偏差，需在预处理阶段规范字段格式。混合的文档格式也要求索引适配多源解析后的文本结构，确保不同类型文档的向量生成一致性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配本品类文档中缴费年限说明、政策条款等常见文本长度，避免语义断裂 |
| 重叠长度 | 100–150 字符 | 弥补分块切割带来的上下文断层，保障跨块的政策关联召回 |
| 相似度阈值 | 0.75–0.85 | 匹配社保政策问答的精准性需求，过滤低相关的政策条文 |
| 单次搜索上限 | 前 5 条 | 控制返回结果规模，适配待遇核定问答的业务场景 |
| `maxToken` | 8000 | 符合FastGPT v4.17.0的通用上下文上限，容纳多条政策依据与业务材料 |
| `defaultToken` | 1000 | 设定基础上下文窗口，保障基础问答的语义完整性 |

## 容易做错的三处
- 现象：检索结果中出现与养老、工伤、失业待遇核定无关的参保登记类政策条文。原因：未针对本品类的业务字段（如缴费年限、待遇标准）设置专属的向量召回过滤规则，导致通用召回覆盖了不相关品类的内容。
- 现象：索引更新失败，日志显示增量同步超时。原因：未配置适配每日更新频率的增量索引策略，全量重建索引占用过多资源导致超时。
- 现象：检索结果中出现字段缺失的政策条文。原因：未对结构化文档中的身份、缴费年限等字段进行格式标准化预处理，导致向量生成时丢失关键业务信息。

## 怎么确认配好了
- 上传一份本品类的典型文档（如工伤认定材料），测试分块后的文本长度与重叠度是否符合预设值。
- 输入一条标准咨询（如“如何核定养老待遇”），检查返回的检索结果条数是否在预设的单次搜索上限内。
- 查看索引更新日志，确认每日增量同步任务能够正常完成且无超时报错。
- 对比检索结果与原始政策文档，确认相似度阈值过滤后的结果与咨询内容高度相关。
