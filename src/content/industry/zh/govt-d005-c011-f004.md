# 养老、工伤、失业待遇核定的政策与制度依据问答：工作流编排

## 这个品类的数据长什么样
本品类数据来源为社会保险经办系统、个人权益记录、劳动关系和工伤认定系统、电子社保卡平台，更新频率为每日。日常处理的文档包括待遇申领表、缴费年限证明、退休审批表、工伤认定材料、失业保险金申领材料，数据字段包含参保累计时长、待遇核算基准参数、资格审核材料标识、待遇发放周期标识等，字段关联的单位涉及年度、发放次数等，单份业务文档的字段数量随业务类型略有差异。

## 这些特征在「工作流编排」这一环带来什么约束
本品类的数据来源分散、更新频率高且业务文档类型多样，对工作流编排带来多重约束。跨系统数据拉取节点需配置为同步获取多源业务数据，保障政策依据匹配的完整性；每日更新的要求需要设置定时同步环节，确保业务数据与政策文本的时效性匹配；多类型业务文档的分流处理，需通过`variables`定义不同业务场景的参数规则，避免字段混淆；资格审核环节的校验节点需嵌入工作流，拦截不符合政策要求的材料数据，降低后续出错风险。

## 配置怎么定
仅作参考；请以目标 FastGPT 发布版本与部署文档核验。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` | 按养老、工伤、失业三类业务分别定义参数，包含参保时长阈值、待遇核算基准、材料校验规则，取值按业务场景标定 | 本品类业务场景差异显著，需通过`variables`区分不同业务的政策匹配规则 |
| 节点触发条件 | 按业务类型触发对应政策匹配节点，如工伤业务触发工伤认定材料校验节点 | 不同业务的政策依据与审核规则存在差异，分流处理可提升匹配准确性 |
| 上下文长度限制 | 800–1200字符 | 业务文档与政策文本的核心信息集中在该区间，过长会引入无关内容，过短会丢失关键依据 |
| 单次搜索上限 | 前5条 | 政策依据的相关结果通常集中在前几条，过多结果会增加工作流处理负担 |
| 超时设置 | 600秒 | 跨系统拉取数据与政策匹配需要一定时长，该时长可覆盖多数正常业务流程 |
| 问题优化组件位置 | 用户输入节点之后 | 先对用户的待遇核定相关问题进行优化，明确核心诉求后再执行后续流程 |

## 容易做错的三处
- 现象：工作流对话日志显示为空，且无任何返回内容。原因：未配置跨系统数据拉取节点的触发规则，导致无法获取业务关联数据，工作流无法正常执行。
- 现象：模型单独测试正常，后台可收到模型响应日志，但工作流对话显示失败。原因：工作流节点间的`nodeId`配置错误，导致数据流转中断，无法将模型响应结果传递至后续节点。
- 现象：政策匹配结果与实际业务要求不符，出现待遇核算偏差。原因：未通过`variables`定义对应业务的参数规则，导致不同业务场景混用了统一的匹配逻辑。

## 怎么确认配好了
- 手动触发工作流，查看各节点的日志输出，确认`variables`参数按业务类型正确加载。
- 模拟养老、工伤、失业三类业务的用户输入，验证工作流是否触发对应政策匹配节点。
- 调整上下文长度限制的取值，核对匹配结果的核心信息是否完整，确认取值符合当前业务场景需求。
- 检查超时设置的取值，模拟跨系统数据拉取场景，确认工作流未出现无响应情况。
