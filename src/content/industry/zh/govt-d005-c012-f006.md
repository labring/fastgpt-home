# 养老服务机构监管的政策与制度依据问答：引用来源与溯源

## 这个品类的数据长什么样
该品类的数据通常来自养老服务信息平台、民政统计系统、消防检查记录与机构运营台账，更新节奏为月度。日常文档包含机构备案材料、运营补贴申请、服务质量检查表、安全隐患整改台账、老人入住档案，数据字段多涉及备案编号、床位规模、整改状态、补贴申请标识等，无统一固定的跨文档字段格式，部分文档需关联多系统数据才能完成校验。

## 这些特征在「引用来源与溯源」这一环带来什么约束
月度更新的数据要求溯源链路适配定期同步的数据源，避免引用过期的机构备案或补贴申请信息。多类文档的非统一字段格式，要求溯源时需匹配文档类型关联对应专属字段，无法直接通过通用字段完成映射。多系统来源的数据需要明确标注所属平台，避免混淆消防检查、民政统计等不同监管环节的记录。监管类数据的严谨性要求溯源信息需完整展示文档来源与更新时间，不能省略关键标识。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | 养老监管文档多为结构化与半结构化混合，该长度可覆盖单份核心文档的有效内容，避免截断关键备案或整改信息 |
| `responseData` | 包含文件名、所属平台与更新时间 | 监管数据需明确溯源来源，需标注所属系统与月度更新的时间戳，满足合规校验需求 |
| `detail` | 开启全字段展示 | 养老监管数据的字段无统一格式，需展示文档内的专属字段如备案编号、床位数量，便于人工核对 |
| 召回结果上限 | 前6条 | 月度更新的数据源数据量适中，前6条可覆盖主要监管环节的有效参考内容，避免冗余信息干扰 |
| 上下文拼接规则 | 按文档类型分组 | 不同类型的监管文档需单独拼接，避免混淆备案材料与安全整改记录的关联逻辑 |

## 容易做错的三处
- 现象：API调用返回结果中未包含源文档文件名与更新时间字段。原因：未开启`responseData`对应的源文档标识配置，未指定返回源文档的基础元数据。
- 现象：返回的引用结果未按监管场景的相关性排序展示内容。原因：未配置按内容匹配度重排的规则，默认召回顺序未适配养老监管的核心文档优先级。
- 现象：大模型输出的引用内容与实际备案或整改记录不符。原因：未在工作流中添加引用校验环节，未对召回内容与系统台账进行交叉核对。

## 怎么确认配好了
- 调用测试接口，查看返回结果中是否包含源文档的文件名、所属平台与更新时间字段。
- 提交包含多类监管文档的测试问题，核对返回的引用结果是否按文档类型分组展示。
- 配置`quoteMaxToken`为1000 token，测试读取长文档时是否未截断核心备案编号与床位数据。
- 触发引用校验工作流，输入与备案信息不符的测试问题，确认是否能识别并标注不合理引用。
