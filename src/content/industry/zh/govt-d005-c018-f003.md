# 参保登记与缴费核定的政策与制度依据问答：多轮对话与提示词

## 这个品类的数据长什么样
本品类的数据来自社会保险经办系统、税务社保费征收系统、市场主体登记信息及公安民政数据共享接口。日常文档包含参保登记表、缴费基数申报表、人员增减表、社保费核定单、个人权益记录，多为结构化表单或报表，字段覆盖单位主体标识、人员身份信息、缴费核算参数、人员异动状态等。数据更新频率为每日，需对接多业务系统完成实时同步。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
多部门日更数据源的特性，要求多轮对话需实时关联最新业务数据，避免引用过期信息。结构化文档的字段规则，要求提示词需明确指定匹配单位统一社会信用代码、人员身份证号等精准字段，避免模糊检索导致结果偏差。人员异动与缴费数据的敏感性，要求会话需通过`chatId`隔离不同用户的上下文，防止数据泄露。跨系统对账的需求，要求对话可关联多知识库完成数据交叉校验，需配置多源检索触发逻辑。同时，逐步核对身份与劳动关系的业务流程，要求多轮对话保留历史会话上下文，避免重复提问。

## 配置怎么定
以下配置适用于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 会话上下文保留时长 | 7200 秒 | 参保登记与缴费核定的业务流程多为跨步骤核对，需保留2小时内的历史对话上下文 |
| 多知识库关联开关 | 开启 | 需同时调用社保经办、税务征收两类数据源完成数据交叉校验 |
| 历史对话引用范围 | 前 20 条 `messages` | 多轮对话需逐步传递人员身份、异动信息，保留足够上下文避免重复提问 |
| 全局变量存储配置 | 绑定 `variables` 全局存储 | 需保留单位统一社会信用代码等固定不变的业务参数，避免每次会话重复输入 |
| 知识库检索触发阈值 | 按实测标定 | 结构化文档的字段匹配需精准，避免无关结果干扰政策依据问答 |
| 单次检索结果上限 | 前 10 条 | 参保相关文档数量可控，过多结果会延长检索耗时 |

## 容易做错的三处
- 现象：部分会话触发知识库检索，部分会话直接生成回答，无检索日志。原因：未配置强制检索触发规则，系统在上下文匹配度较高时跳过检索环节。
- 现象：会话内的临时变量在新轮次被清空，无法保留单位统一社会信用代码等固定业务参数。原因：未使用`variables`全局存储配置，仅使用会话临时变量，临时变量随对话轮次更新被覆盖。
- 现象：同一对话窗口随提问次数增加，检索耗时变长，新发起的会话则恢复正常。原因：未限制历史对话保留条数，过长的`messages`上下文导致每次检索都需加载大量历史数据，增加处理耗时。

## 怎么确认配好了
- 发起包含单位统一社会信用代码的提问，核对返回结果是否关联了参保登记表、缴费核定单等对应文档。
- 发起跨轮次提问，验证历史对话中的人员身份信息是否被系统自动引用，无需重复输入。
- 检查会话变量存储面板，确认`variables`中的全局参数未随对话轮次被修改或清空。
- 发起连续多轮提问，观察检索耗时是否保持稳定，无明显递增。
