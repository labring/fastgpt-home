# 国库集中支付与报销审核的政策与制度依据问答：向量模型与索引

## 这个品类的数据长什么样
该品类涉及的核心数据来自国库集中支付系统、预算管理一体化系统、电子发票平台与合同管理系统，覆盖支付申请、用款计划、发票、合同、验收单、报销审批单、支付凭证等日常文档。数据更新频率为每日，由预算单位财务、财政国库支付中心、主管部门财务审核岗等主体维护，聚焦单笔资金支付的合规审核环节，包含预算指标、经济分类、票据链条等核心字段。

## 这些特征在「向量模型与索引」这一环带来什么约束
多系统来源的文档格式存在差异，需统一字段映射后再进入索引环节，避免向量表征出现偏差。每日更新的数据要求索引支持增量同步，减少全量重建的资源消耗与时间成本。单笔支付关联多类文档的特性，要求分块时保留跨文档的关联上下文，避免拆分后丢失审核链条的关键信息。核心字段的合规性要求向量召回的精准度，需限制无关召回结果的干扰，保障审核依据的准确性与权威性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| 分块长度 | 800–1200 字符 | 该品类文档包含多字段关联内容，过长分块会导致向量表征冗余，过短则丢失审核链条的关联信息 |
| 重叠长度 | 100–200 字符 | 跨文档或跨段落的审核链条需要上下文衔接，重叠长度保障关联信息不被拆分 |
| `maxToken` | 4096 token | 适配政策类文档的文本长度，符合主流嵌入模型的输入限制 |
| `defaultToken` | 2048 token | 匹配日常政策问答的单次查询上下文长度需求 |
| 单次搜索上限 | 前 8 条 | 该品类需精准匹配政策依据，过多结果会增加审核岗的筛选负担 |
| 相似度阈值 | 0.75–0.85 按实测标定 | 保障核心字段匹配的精度，避免低相关结果干扰合规审核 |

## 容易做错的三处
- 现象为点击启用`defaultToken`配置的索引模型，填写自定义请求地址与apikey后点击测试直接报错。原因是未确认自定义接口的返回格式与FastGPT要求的向量输出格式匹配，或apikey权限未开放对应模型调用。
- 现象为知识库刷新后仍显示“检测到没有可用的索引模型”。原因是配置的索引模型未保存生效，或知识库关联的模型与全局设置的模型不匹配。
- 现象为检索结果无法匹配到对应政策依据，且分块记录显示文档被拆分为多个独立片段。原因是分块长度设置过小，将关联的审核链条文档拆分为多个块，导致向量召回时无法关联完整的政策依据。

## 怎么确认配好了
- 进入FastGPT v4.17.0版本的知识库设置页面，查看索引模型的启用状态是否为已启用，确认配置的模型与实际调用的模型一致。
- 上传单份该品类的测试文档，执行分块与索引操作，查看分块结果是否符合预设的长度与重叠规则。
- 发起针对政策依据的测试查询，查看检索结果是否包含该品类的核心文档字段，确认召回逻辑正常。
- 模拟每日增量数据的上传流程，查看索引是否正常更新，无报错提示。
