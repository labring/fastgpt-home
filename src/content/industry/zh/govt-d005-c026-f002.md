# 工程建设项目审批的政策与制度依据问答：向量模型与索引

## 这个品类的数据长什么样
本品类数据来自工程建设项目审批管理系统、施工图审查系统、企业资质库及信用平台，更新频率为每日。日常文档包含施工许可申请材料、施工图审查合格书、质量安全监督手续文件、竣工验收备案表等，结构以审批节点为核心，包含参建单位资质、人员信息、审批流程节点、合规要求字段，无统一固定单位，字段随审批环节差异变化。

## 这些特征在「向量模型与索引」这一环带来什么约束
多系统来源的数据格式差异，要求索引环节支持跨源数据的统一向量映射，避免不同系统文档的向量空间偏移。每日更新的特性，要求索引配置支持增量更新模式，减少全量重建的资源消耗。文档结构随审批节点变化，分块长度需适配不同文档的内容密度，避免过细分块导致语义断裂或过粗分块丢失关键合规条款。参建单位资质等字段的专业性，要求向量模型适配住建领域专业术语的语义编码。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 本品类文档包含专业合规条款，分块长度适配条款的语义完整性，避免拆分关键审批要求 |
| 重叠长度 | 100–150 字符 | 跨分块的审批流程关联信息需要保留上下文，避免语义断层 |
| 相似度阈值 | 0.72–0.80 | 本品类政策条款的专业性较强，需过滤低相关的检索结果，保障答案合规性 |
| 单次搜索上限 | 前 8 条 | 工程审批的政策依据通常集中在少量核心文件，过多结果会超出上下文窗口 |
| maxToken | 8000 token | FastGPT v4.17.0 的默认上下文窗口适配本品类的多文件拼接需求，保障完整引用审批条款 |
| defaultToken | 500 token | 单条检索结果的向量展示与上下文拼接的合理长度，避免冗余 |

## 容易做错的三处
- 现象：后台索引日志显示部分来源文档未被成功加载，检索结果条数与配置的单次搜索上限不符。原因：未正确关联跨系统数据的索引映射规则，导致部分数据源的文档未被纳入索引范围。
- 现象：后台日志显示检索到匹配的政策文件，但大语言模型回答称未找到相关依据。原因：未正确配置`defaultToken`或`maxToken`，导致检索到的文本片段未被完整传入大语言模型上下文，或上下文拼接顺序错误。
- 现象：向量检索结果的相似度分布分散，无法定位核心审批条款。原因：分块长度设置过短，将完整的合规条款拆分为多个语义不连贯的片段，导致向量编码丢失关键信息。

## 怎么确认配好了
- 上传单份施工许可申请文档，执行政策问答测试，核对检索结果的分块数量与分块长度配置一致。
- 调整相似度阈值，验证检索结果的相关性随阈值变化符合预期，无大量低匹配结果混入。
- 查看索引任务日志，确认每日增量更新任务正常执行，无全量重建的异常触发。
- 测试包含多系统来源数据的问答，验证跨源文档的检索结果均能被正确召回。
