# 防汛防灾与应急值守的政策与制度依据问答：向量模型与索引

## 这个品类的数据长什么样
该品类的数据主要来自气象预警系统、水文监测系统、应急指挥平台、基层报灾系统与视频监控，更新频率为每日。日常文档包含值班记录、预警通知、会商纪要、灾情速报、应急处置方案、物资调拨单，部分文档包含雨情水情数值、避险区域、物资品类与数量等字段，不同来源的文档格式与字段规范存在一定差异。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源异构的数据格式与字段差异，要求预处理环节完成统一的字段映射与格式标准化，避免索引时出现字段不匹配的问题。每日更新的数据规模要求增量索引的触发机制适配批量同步节奏，减少全量索引占用的服务器资源。不同文档的长度跨度较大，从短预警通知到长篇会商纪要，需要支持灵活的分块规则适配内容长度，避免语义断裂。同时应急场景的低延迟需求，要求索引的召回链路优化，减少检索耗时以保障快速响应。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxToken` | `8000–12000 token` | 适配多数会商纪要与政策文档的长度，避免截断关键政策依据内容 |
| 分块长度 | `800–1200 字符` | 兼顾短预警通知与长处置方案的内容完整性，减少分块后语义断裂 |
| 重叠长度 | `100–150 字符` | 保障相邻分块的语义连贯性，避免政策条款被分块割裂 |
| 单次搜索上限 | 前10条 | 应急场景下需快速获取核心政策依据，过多结果会增加后续处理耗时 |
| 重排模型 | 按实测标定 | 不同场景下的重排效果差异较大，需结合本地部署的模型验证适配性 |
| 最大上下文窗口 | `4000–6000 token` | 保障问答时能完整调用相关政策条文与历史会商记录 |

## 容易做错的三处
- 现象：设置的分块长度超出索引存储的单条数据上限，界面出现“分块过长无法索引”的报错，原因是未结合该品类文档的长度跨度调整分块参数，直接套用通用场景的配置值。
- 现象：部署向量库时出现PostgreSQL相关的依赖报错，无法正常启动服务，原因是误用了包含额外数据库依赖的compose文件，未适配该场景轻量化的索引部署需求。
- 现象：检索返回的政策依据与用户问题匹配度偏低，无法准确匹配对应制度条款，原因是未开启重排模型，仅依赖基础召回结果，未针对政策文本的语义相似度做进一步筛选。

## 怎么确认配好了
- 上传单篇最长的会商纪要与最短的预警通知，验证分块后的内容完整性与语义连贯性，确认分块参数适配文档跨度。
- 触发一次增量索引任务，查看FastGPT v4.17.0的索引更新日志，确认每日更新的灾情数据已成功同步到索引库。
- 输入典型的政策问答问题，核对检索返回的结果条数与相关性，确认单次搜索上限与重排配置符合业务需求。
- 测试`maxToken`参数的截断效果，确认政策条文未被意外截断，保留完整的制度依据内容。
