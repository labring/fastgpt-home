# 城市公交的政策与制度依据问答：工作流编排

## 这个品类的数据长什么样
城市公交的政策与制度依据数据主要来源于各地交通运输主管部门、市属公交集团的官方公开文件，更新随新政策发布、存量政策修订触发，无固定周期。单份文档多为带有明确字段的结构化文本，包含政策文号、发布单位、生效日期、适用线路范围、执行条款等字段，部分文件附带运营规范细则附件，字段均为纯文本格式，无嵌套结构化附件，单份文档长度跨度从数百字符到上万字符不等。

## 这些特征在「工作流编排」这一环带来什么约束
城市公交政策数据的分散来源与非标准化格式，要求工作流中加入数据源聚合与字段标准化节点，统一不同城市政策的文号、生效日期等字段格式。无固定更新周期则要求配置定时触发的数据源同步环节，确保调用的政策为最新版本。文档长度跨度大的特点，要求工作流中设置适配性的分块参数，避免长文本超出大模型上下文限制。适用线路范围的字段差异，则要求在检索环节加入线路匹配过滤，缩小召回范围。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本编写。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 问题分类 | 按政策核心场景（票价、线路调整、安全规范）划分 | 城市公交政策均围绕核心运营场景分类，可缩小召回范围 |
| `variables` | 绑定查询的城市名称、线路编号 | 精准匹配对应城市、线路的专属政策文档 |
| 最大上下文 | 800–1200 字符 | 适配城市公交政策核心条款的长度区间，避免冗余内容干扰 |
| 单次搜索上限 | 前3条 | 同场景政策文档多集中在3条以内，减少大模型处理负载 |
| 循环触发条件 | 当回答缺失政策生效日期时触发二次生成 | 用户提问常需明确政策执行时间，未覆盖时需补充完善 |
| `nodeId` | 为数据源同步节点分配固定标识 | 便于定时更新任务关联对应数据源节点 |

## 容易做错的三处
- 现象：对话明细中仅显示2条上下文，无法关联政策文档内容。原因：未将`variables`绑定的城市、线路参数加入上下文召回规则，导致系统默认召回通用上下文。
- 现象：工作流循环触发后无法正确终止。原因：未在循环节点中配置明确的终止条件，例如未校验AI回答是否包含完整政策条款。
- 现象：上传的政策文件未被正确解析为可检索文本。原因：未配置文件直接传入大模型的节点，仍使用系统默认的文本解析流程，导致格式丢失。

## 怎么确认配好了
- 运行测试工作流，输入包含城市、线路的政策提问，核对召回的文档是否匹配对应城市与线路。
- 查看工作流日志，确认`variables`参数已正确绑定当前查询的城市、线路信息。
- 触发定时更新任务，核对数据源节点是否按计划同步最新政策文件。
- 模拟循环场景，输入未包含生效日期的提问，确认工作流会触发二次生成并补充相关信息。
