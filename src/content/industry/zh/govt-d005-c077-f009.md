# 城市公交的政策与制度依据问答：模型接入与配置

## 这个品类的数据长什么样
城市公交的政策与制度依据数据主要来源于公交运营企业内部的运营细则、地方交通运输管理部门发布的行业规范性文件、以及国家层面的公共交通服务标准文档。数据更新无固定统一周期，地方政策调整时同步更新，内部运营细则则根据线路优化、票价调整等场景按需更新。单份政策文档通常包含政策编号、发布单位、生效日期、适用线路范围、具体执行条款等结构化字段，字段以条款、款、项为层级单位，部分文档附带配套的执行流程说明。

## 这些特征在「模型接入与配置」这一环带来什么约束
政策文档的结构化字段要求检索时需精准匹配字段属性与关键词，因此配置需支持基于字段的定向检索，避免泛化匹配导致的结果偏差。文档层级较多且单份长度较长，需调整上下文加载参数以完整获取文档内容，防止关键条款被截断。数据更新无固定周期，需配置适配增量同步的逻辑，确保知识库内容与最新政策保持一致。此外，政策内容具有强时效性，问答过程需关联生效日期等字段，因此配置需支持对文档元数据的识别与调用。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 城市公交政策文档单份长度较长，需完整加载上下文以确保问答时可覆盖全部相关条款 |
| `temperature` | 0.1–0.3 | 政策问答需严谨准确，低温度参数可减少模型生成发散性内容 |
| `quoteMaxToken` | 2000 字符 | 需保留足够长度的政策原文片段作为回答依据，确保用户可追溯政策原文 |
| `AIPROXY_API_ENDPOINT` | 按接入的模型服务商专属端点填写 | 适配不同模型的API调用路径，例如Azure OpenAI需填写专属的区域端点 |
| `AIPROXY_API_TOKEN` | 按服务商提供的密钥填写 | 完成API调用的身份验证，确保请求合法有效 |
| `toolChoice` | none | 政策问答仅需基于知识库内容生成回答，无需调用外部工具 |

## 容易做错的三处
- 现象：调用Azure OpenAI模型时返回400状态码，提示协议不匹配。原因：未将`AIPROXY_API_ENDPOINT`配置为Azure专属端点，仍使用通用OpenAI的标准端点。
- 现象：问答结果未引用政策原文片段，或引用片段长度不足。原因：`quoteMaxToken`取值过低，无法截取到符合要求的原文内容。
- 现象：生成的政策解读出现与原文不符的偏差内容。原因：`temperature`取值过高，导致模型过度生成非原文内容，破坏政策解读的严谨性。

## 怎么确认配好了
- 提交包含具体政策场景的测试问题，例如“某公交线路的老年人优惠政策是什么”，核对回答是否包含对应的政策原文片段。
- 查看FastGPT v4.17.0的API调用日志，确认`AIPROXY_API_ENDPOINT`与`AIPROXY_API_TOKEN`的配置与模型服务商提供的信息一致。
- 调整`temperature`参数的取值，对比不同取值下的回答内容，确认最终取值符合政策问答的严谨性要求。
- 上传一份更新后的政策文档，触发知识库同步流程，确认文档更新后可正常被检索与调用。
