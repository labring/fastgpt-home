# 城投平台的政策与制度依据问答：工作流编排

## 这个品类的数据长什么样
城投平台的政策与制度依据数据，来源包括内部合规档案库、省级财政与住建部门公开的城投运营政策文件、地方人大常委会发布的规范性文件。更新节奏为公开政策随发布实时同步，内部制度随修订即时更新。文档以结构化条目为核心，包含政策文号、发布主体、生效日期、适用场景、具体条款内容，字段涵盖政策分类、适用区域、责任部门，单位多为条款项、文件页数，日期采用标准年月日格式。

## 这些特征在「工作流编排」这一环带来什么约束
上述数据特征对工作流编排带来多重约束。公开与内部数据源分散的特点，要求工作流配置多源拉取节点，覆盖公开平台与内部档案库。政策文号的唯一性，要求工作流的`variables`需绑定政策文号参数实现精准召回。区域字段的存在，要求工作流添加适用范围过滤环节，避免跨区域政策被误召回。条款化的文档结构，要求分块逻辑按单条条款拆分，保障上下文完整性。更新无固定周期的特点，要求工作流支持灵活调整同步频率。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` | 传入政策文号、适用区域 | 城投政策需精准匹配文号与区域，避免跨场景召回 |
| `nodeId` | 24位十六进制字符 | FastGPT v4.17.0 要求工作流节点ID为该格式 |
| 数据源同步频率 | 每周1次 | 公开城投政策更新无固定周期，每周同步可覆盖多数更新 |
| 上下文长度 | 800–1200 字符 | 城投政策单条条款多为短段落，该长度可完整承载核心内容 |
| 超时设置 | 600 秒 | 多数据源拉取需较长响应时间，避免中途中断 |
| 结果排序 | 按政策生效日期倒序 | 城投平台需优先展示最新生效的政策依据 |

## 容易做错的三处
- 现象为调用工作流返回「无效节点标识」报错，原因是未使用24位十六进制字符格式的`nodeId`参数，或输入了非标准格式的节点ID。
- 现象为代码节点触发axioserror报错，原因是未在工作流中配置正确的API访问地址与密钥，或未将查询参数正确绑定到`variables`中。
- 现象为召回的政策文档与查询场景不匹配，原因是未在`variables`中绑定适用区域参数，导致跨区域政策被误召回。

## 怎么确认配好了
- 在FastGPT后台工作流管理页面，查看`nodeId`字段，确认格式为24位十六进制字符。
- 手动触发工作流，传入测试用的政策文号与区域参数，查看返回的上下文是否包含对应政策条款。
- 检查数据源同步日志，确认公开政策与内部文档的拉取任务按设定的每周1次频率执行。
- 模拟用户查询，验证召回的政策文档按生效日期倒序排列。
