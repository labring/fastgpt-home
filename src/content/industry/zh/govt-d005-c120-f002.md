# 铁路运营的政策与制度依据问答：向量模型与索引

## 这个品类的数据长什么样
铁路运营的政策与制度依据数据来源为国铁集团正式发布的运输安全、旅客服务、行车调度等规程，各铁路局发布的区域运营细则，以及随线路调整、应急需求发布的临时管控通知。更新节奏为正式规章按年度或重大政策调整更新，临时通知随运营需求即时发布。文档结构多包含文件文号、发布单位、生效日期、分章节条款，部分附带作业流程图或表格附件。字段包含文件编号、发布主体、生效时间、条款编号、适用场景等，单位以“条”“款”“项”标注条款层级，时间格式为标准公历日期。

## 这些特征在「向量模型与索引」这一环带来什么约束
铁路政策数据混合了长正式规章与短临时通知，分块需兼顾章节完整性与长度限制，避免拆分独立的核心条款。多字段元数据要求检索时需支持按生效时间、适用场景过滤，确保召回当前有效的政策内容。非固定更新频率要求索引支持增量同步，避免全量重复计算。专业术语密集的特性要求向量模型适配铁路运营领域的专用词汇，提升检索精准度。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配铁路政策文档的章节段落长度，避免拆分独立条款 |
| 重叠长度 | 150–200 字符 | 保留跨分块的条款上下文，防止专业术语被截断 |
| 相似度阈值 | 0.75–0.85 按实测标定 | 区分政策条款的相似程度，过滤无关的泛泛规章 |
| `maxToken` | 8000 token | 适配主流嵌入模型的输入上限，避免长文档向量化失败 |
| 单次搜索上限 | 前8条 | 匹配铁路政策多条款关联的查询场景，控制召回冗余量 |
| 重排 | 开启 | 对召回的政策条款按相关性排序，优先匹配用户问题的核心场景 |

## 容易做错的三处
- 导入政策文档后索引状态持续显示创建中。原因：未调整分块参数适配铁路政策的长段落，单分块超出嵌入模型的输入限制，导致索引进程阻塞。
- 向量计算得分异常偏高且多条结果得分一致。原因：未过滤已失效的旧政策文件，重复的旧条款与新规章同时参与向量化，导致相似度计算出现偏差。
- 向量化处理速度过慢。原因：未启用增量索引模式，每次更新都全量重新处理所有铁路政策文档，占用大量计算资源。

## 怎么确认配好了
- 上传单份典型铁路政策文档，检查分块后的片段是否保留完整条款，无专业术语截断情况。
- 模拟查询高频政策问题，核对召回结果的生效时间是否符合当前运营要求，无过期条款混入。
- 测试增量更新单份临时通知，确认索引仅处理新增文件，无全量重新索引的日志输出。
- 查看FastGPT v4.17.0的向量化日志，确认`maxToken`参数未触发截断警告，嵌入模型调用正常。
