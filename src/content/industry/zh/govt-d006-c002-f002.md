# “高效办成一件事”联办的文书与材料起草：向量模型与索引

## 这个品类的数据长什么样
通常包含联办事项清单、一次性告知单、联办申请表、材料流转单、并联审批意见、办结回执等文档。数据来源包括国家政务服务平台“一件事”专区、地方一体化政务服务平台、电子证照库以及各部门审批系统，更新频率为每日。文档字段包含跨部门事项关联标识、材料明细、办理状态、部门权责划分等，无统一固定格式，不同联办事项的字段结构存在差异。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源异构的数据来源要求索引支持跨平台数据的统一格式转换与字段对齐；每日更新的频率需要适配增量索引的定时更新机制，避免全量索引带来的性能损耗；多样的文档结构要求分块策略保留跨部门关联的上下文信息，防止事项拆解时出现逻辑断裂；跨部门的材料与审批关联要求相似度匹配的精度适配，避免出现材料错配或事项关联错误，影响联办流程推进。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 联办文档包含跨部门关联内容，保留足够上下文又避免分块冗余 |
| 重叠长度 | 200–300 字符 | 保留分块间的关联信息，防止跨部门事项的上下文断裂 |
| 相似度阈值 | 0.75–0.85 | 区分相似联办事项与准确匹配材料要求，适配政务场景的严谨性 |
| 单次搜索上限 | 前 10 条 | 联办事项涉及多个部门，返回适量结果供窗口人员参考 |
| `maxToken` | 8000 token | 联办文书的上下文长度较长，适配大模型的输入限制 |
| `defaultToken` | 1500 token | 生成单份联办材料的内容长度需求 |

## 容易做错的三处
- 现象：调用ollama接入的向量模型时FastGPT返回访问拒绝，但curl测试可正常获取向量结果。原因：ollama的跨域请求配置未放开，或FastGPT的向量模型接入地址未配置内网访问权限。
- 现象：无法通过MongoDB直接管理向量库的增删操作，仅能通过FastGPT内置界面操作。原因：未开启向量库的外部数据源同步权限，或未为对应角色配置向量库操作权限。
- 现象：知识库索引合并后仍存在重复的材料清单条目。原因：未开启索引合并时的字段匹配去重开关，或未设置跨文档的关联标识校验规则。

## 怎么确认配好了
- 查看FastGPT v4.17.0的向量模型配置页面，确认已添加的模型与实际使用的向量模型一致。
- 执行一次增量索引更新任务，查看系统日志中显示的更新条数与当日新增的联办文档数量匹配。
- 手动合并两个相似联办事项的索引，查看合并结果中无重复的材料明细条目。
- 调用向量检索接口，确认返回的结果条数符合单次搜索上限的配置要求。
