# 养老服务机构监管的文书与材料起草：向量模型与索引

## 这个品类的数据长什么样
该细分场景的核心数据来自民政养老服务信息平台、民政统计系统、消防检查记录及机构运营台账，日常处理的文档包含备案材料、运营补贴申请、服务质量检查表、安全隐患整改台账、老人入住档案。数据更新频率为月度，文档字段包含备案编号、床位数量、检查日期、整改时限等，单位涉及张、天、人次等，部分文档同时包含结构化表格与非结构化文本内容。

## 这些特征在「向量模型与索引」这一环带来什么约束
月度更新的数据集规模相对固定，无需高频实时索引，可采用定期全量更新的策略。多类型文档混合的结构要求切片逻辑兼顾结构化表格与非整段文本，避免割裂表格内的关联数据。多来源的数据存在字段重复的可能，索引环节需支持去重校验。同时，监管场景的出错后果直接关联公共服务合规性，要求向量召回的精准度需匹配业务审核的严谨性，不可过度放宽匹配阈值。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| 分块长度 | 800–1200 字符 | 覆盖备案材料、服务质量检查表等单页文档的核心信息，避免块内信息碎片化 |
| 重叠长度 | 100–150 字符 | 衔接跨块的老人入住档案、安全隐患整改记录等上下文，防止关键信息断裂 |
| 相似度阈值 | 0.75–0.85 | 过滤低匹配的冗余数据，同时保留养老补贴申请、机构备案材料的精准匹配结果 |
| 单次搜索上限 | 前10条 | 适配月度更新的数据集规模，避免返回过多无关的历史消防检查记录 |
| `maxToken` | 4000 token | 适配养老服务监管文书的上下文长度，确保召回内容可完整带入生成环节 |
| `defaultToken` | 按实测标定 | 适配本地部署的硬件资源，平衡嵌入向量生成的速度与精度 |

## 容易做错的三处
- 现象：启动FastGPT时弹出「embedding storage directory not found」报错。原因：未指定向量存储的有效路径，忽略了养老服务数据集的磁盘占用需求，未按照官方指引配置存储位置。
- 现象：检索养老补贴申请相关内容时，返回结果条数远少于预期。原因：将相似度阈值设置过高，过滤掉了部分符合业务匹配要求的申请材料，未结合监管场景的严谨性调整阈值。
- 现象：知识库占用磁盘空间远超原文件总大小。原因：未清理分割后的冗余文件块与重复嵌入向量，未针对月度更新的数据集设置定期清理策略，导致重复存储数据累积。

## 怎么确认配好了
- 查看向量存储目录的文件列表，确认已生成与分割后文件块数量匹配的嵌入向量文件。
- 输入一条监管场景的测试问题，例如「请核对某养老机构的备案材料与实际床位数据」，核对返回结果的匹配度符合预设的相似度阈值范围。
- 查看FastGPT v4.17.0的系统监控面板，确认嵌入向量生成任务的执行时长符合本地硬件的标定值。
- 手动触发一次全量索引更新，确认更新过程无超时报错，且更新耗时与月度数据集的规模匹配。
