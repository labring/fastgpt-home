# 医保费用结算审核的文书与材料起草：向量模型与索引

## 这个品类的数据长什么样
该品类的数据来源为全国医疗保障信息平台、医院HIS与医保接口、医保目录和编码库、异地就医结算平台。日常处理的文档包括医保结算清单、费用明细、病案首页、处方、拒付清单、结算对账单，包含诊疗项目编码、费用金额、参保人身份标识、结算状态等字段。数据更新频率为每日，需覆盖单笔或批量医疗费用支付相关的全量业务单据。

## 这些特征在「向量模型与索引」这一环带来什么约束
该品类的数据多源且每日全量更新，要求索引模块支持增量更新与去重逻辑，避免重复生成索引条目。文档包含诊疗编码、费用金额等结构化字段与自由文本描述，需兼顾结构化编码的精确匹配与自由文本的语义关联，因此向量模型需同时适配结构化与非结构化内容的嵌入。单笔业务单据的字段数量多、长度跨度大，分块处理时需避免切断编码与对应费用的关联，因此分块规则需适配文档结构特征。结算审核需关联多份关联单据（如处方与结算清单），索引需支持跨文档的关联召回，确保审核时的信息完整性。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 兼顾医保结算单据中诊疗编码与文本描述的完整性，避免分块截断关键匹配字段 |
| 重叠长度 | 100–200 字符 | 确保相邻分块覆盖同一诊疗项目或费用明细的关联内容，减少语义断裂 |
| `maxToken` | 8192 token | 适配主流嵌入模型的上下文上限，满足长结算清单的向量生成需求 |
| 相似度阈值 | 0.75–0.85 | 平衡费用匹配的召回准确率与漏检率，适配医保审核的严谨性要求 |
| 单次搜索上限 | 前 10 条 | 限制召回结果数量，避免审核时信息过载，符合日常业务的关联单据规模 |
| `defaultToken` | 按实测标定 | 适配业务文档的平均token消耗，优化索引生成的稳定性 |

## 容易做错的三处
- 现象：索引任务长时间卡在「索引中」状态，无进度更新，重启服务后仍未恢复。原因：未正确配置`maxToken`参数，长结算清单的向量生成超出模型支持范围，导致任务阻塞。
- 现象：数据集内的索引条目数量在无手动操作的情况下自动增加，出现重复的单据索引。原因：未配置增量索引的去重逻辑，每日全量更新时重复生成已有数据的索引条目。
- 现象：检索结果中无法匹配到对应的诊疗项目编码，或匹配结果准确率偏低。原因：分块长度设置过短，切断了诊疗编码与对应费用明细的语义关联，导致向量召回失效。

## 怎么确认配好了
- 查看FastGPT v4.17.0的索引生成日志，确认长结算清单的向量生成无`maxToken`超限报错，核对token消耗与配置值匹配。
- 手动触发一次增量索引任务，核对最终索引条目数量与当日新增单据数量一致，无重复条目。
- 输入一条待审核的费用明细，检索关联的结算清单与处方，确认召回结果的相似度符合业务严谨性要求。
- 检查索引模型与语言模型的绑定配置，确认两者的关联关系未被误删除，可正常调用嵌入与生成能力。
