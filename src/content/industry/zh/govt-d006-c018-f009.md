# 参保登记与缴费核定的文书与材料起草：模型接入与配置

## 这个品类的数据长什么样
本品类数据主要来自社会保险经办系统、税务社保费征收系统、市场主体登记信息及公安民政共享数据，更新频率为每日。日常处理的文档包含参保登记表、缴费基数申报表、人员增减表、社保费核定单、个人权益记录，文档字段多涉及统一社会信用代码、居民身份证号码、缴费基数、参保状态等，格式多为结构化表格或固定模板文档。

## 这些特征在「模型接入与配置」这一环带来什么约束
数据来源多为内部业务系统，存在字段格式不统一的可能，需模型准确识别结构化字段与非结构化说明文本；每日更新的高频数据要求模型接入配置支持准实时的数据调用，避免处理延迟；文档类型固定但字段校验规则严格，需配置限制模型输出无关内容，确保生成的文书符合社保经办的合规要求；跨系统数据关联需模型准确匹配不同来源的人员与单位信息，避免出现身份核对错误导致的权益问题。

## 配置怎么定
仅作参考；请以目标 FastGPT 发布版本与部署文档核验。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 需覆盖每日更新的多系统关联数据，确保上下文包含完整的单位与人员参保信息 |
| `maxTokens` | 2000–3000 token | 对应单份社保经办文书的常规生成长度，避免超出合理篇幅 |
| `quoteMaxToken` | 1500 token | 限定引用业务数据的长度，确保核心字段如缴费基数、身份证号不被截断 |
| `temperature` | 0.1–0.3 | 降低随机输出偏差，保证生成的文书格式与字段符合固定经办规范 |
| `toolChoice` | auto | 允许模型自动选择是否调用工具完成跨系统数据匹配，适配业务校验需求 |
| `vision` | 关闭 | 本品类处理的文档多为结构化文本，无需图像识别能力 |

## 容易做错的三处
- 生成的文书中残留think标签，且配置未关闭思考输出。原因是未正确配置模型的思考输出开关，导致非必要的标签混入最终文书。
- 在线召回测试未触发Rerank模型。原因是未在知识库索引环节同步开启Rerank配置，或未在应用环节关联对应重排模型。
- 生成的人员增减表出现身份匹配错误。原因是未配置`maxContext`覆盖完整的跨系统关联数据，导致模型无法准确核对公安民政共享的人员身份信息。

## 怎么确认配好了
- 进入应用的模型配置页面，检查`temperature`的取值区间，确认符合文书格式规范的要求。
- 发起单份参保登记表的生成测试，核对输出内容是否包含所有必填字段，且无额外的非业务内容。
- 模拟跨系统数据关联的查询，验证模型是否能正确匹配不同来源的单位与人员信息，确认工具调用配置生效。
- 查看知识库召回日志，确认Rerank模型的调用记录存在，验证索引与应用环节的配置同步。
