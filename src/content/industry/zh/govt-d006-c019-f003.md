# 双随机、一公开监管检查的文书与材料起草：多轮对话与提示词

本文基于FastGPT v4.17.0版本制定。

## 这个品类的数据长什么样
该细分品类的核心数据来自“双随机、一公开”监管平台、企业信用信息公示系统、执法人员名录库与行业监管系统。日常文档涵盖抽查计划、检查对象名单、检查事项清单、现场检查记录、整改通知书、抽查结果公示，包含统一社会信用代码、执法人员编号、检查事项条目、整改时限等结构化字段与自由文本内容。数据更新频率通常为月度，核心业务库需定期同步最新监管对象与执法人员信息。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源分散且需定期更新，要求多轮对话需支持动态注入月度更新的业务数据，避免使用过期的检查对象或执法人员信息。文档包含结构化字段与自由文本，提示词需明确区分必填字段校验与场景化描述生成的任务边界。执法文书的合规性要求严格，多轮对话需逐轮校验关键字段，避免出现漏公示、抽取不合规等问题。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 对话链路标识 | `chatId` | 用于关联多轮对话的历史上下文，确保执法场景的对话连贯性 |
| 上下文窗口上限 | 8000–12000 token | 该品类文档多为结构化清单与混合文本，需容纳多轮执法场景对话与历史记录 |
| `variables` | 预设「执法人员名录库」「检查事项清单」「抽查结果模板」等专属变量 | 需将固定业务数据注入对话上下文，避免重复调用外部接口 |
| `messages` | 按「系统提示→用户初始请求→中间校验→最终输出」的顺序编排 | 监管文书需严格遵循执法流程，明确每轮对话的角色与任务 |
| 单次对话最大轮次 | 6–8轮 | 单份检查文书的起草通常涵盖计划生成、对象匹配、结果录入三个核心环节，轮次过多会增加上下文冗余 |
| 知识库更新触发规则 | 按月触发全量同步 | 该品类核心数据更新频率为月度，匹配业务更新节奏 |

## 容易做错的三处
- 现象：通过HTTP请求编排的对话链路中，接口生成的文书内容未在前端对话窗口展示。原因：未通过`variables`配置输出字段的上下文注入规则，导致返回内容未被纳入对话上下文。
- 现象：使用本地部署的向量模型时，检查对象名单的索引召回无进度。原因：未针对结构化名单设置专属的分块策略，导致长文本拆分丢失统一社会信用代码等关键标识字段。
- 现象：对话环节上传的现场检查照片未被解析为有效输入。原因：未开启全模态对话配置，仅调用了纯文本交互接口。

## 怎么确认配好了
- 发起一轮包含「生成月度抽查计划」的对话，检查`messages`序列是否包含系统提示、用户请求与预设业务变量。
- 触发知识库同步任务，确认同步周期匹配月度更新节奏。
- 发起多轮对话，验证输出内容包含检查对象名单、执法人员信息等必填字段。
- 测试HTTP请求编排流程，确认返回的结构化文书内容可在对话窗口正常展示。
