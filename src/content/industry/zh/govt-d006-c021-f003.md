# 国库集中支付与报销审核的文书与材料起草：多轮对话与提示词

本文基于FastGPT v4.17.0版本，针对该细分场景梳理多轮对话与提示词的配置、约束与落地要点。

## 这个品类的数据长什么样
该品类的数据来自国库集中支付系统、预算管理一体化系统、电子发票平台、合同管理系统，更新频率为每日。日常处理的文档包含支付申请、用款计划、发票、合同、验收单、报销审批单、支付凭证，单笔业务对应多类关联文档。数据字段包含预算指标编码、经济分类代码、支付金额、票据编号、合同编号等，所有数据围绕单笔资金支付的合规审核展开，无额外统计性字段。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
多系统来源与每日更新的特性，要求多轮对话需实时同步最新的预算指标、票据状态等信息，避免使用过期数据导致审核失误。单笔业务对应多类关联文档的结构，要求提示词需明确关联当前业务的所有关联材料，防止遗漏审核环节。出错后果涉及资金退回、错付或财经纪律问题，要求多轮对话需逐步校验关键字段，避免单次判断失误。同时，该品类聚焦日常支付执行环节，对话需聚焦单笔业务，无需处理跨预算周期的批量数据，因此上下文范围需严格限定在当前业务内。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文 | 8000–12000 字符 | 单笔支付相关的支付申请、报销审批单等文档总长度通常在数千字符，需完整覆盖核心审核材料 |
| 问题优化 | 开启 | 将财务人员的口语化提问转化为标准化国库支付审核查询，提升系统数据检索准确性 |
| 单次搜索上限 | 前3条 | 国库支付审核仅需匹配当前单笔业务的系统数据，过多检索结果会干扰合规校验 |
| 对话ID（`chatId`） | 绑定单笔支付业务编号 | 确保多轮对话的上下文仅关联当前业务，避免跨单混淆 |
| 上下文消息（`messages`） | 仅保留当前业务的交互与关联数据 | 防止无关历史对话干扰当前审核的合规判断 |
| 自定义变量（`variables`） | 注入当前预算单位编码、经济分类代码 | 让模型直接使用业务系统的标准字段，减少人工输入误差 |

## 容易做错的三处
- 检索知识库返回图片格式的系统文档时，模型提示未找到答案。原因：未配置图片内容的解析流程，仅支持文本类知识库检索，无法提取图片中的支付凭证、合同等关键信息。
- 短时间内连续发送多笔报销审核请求，后续请求需等待前序生成完成。原因：未使用`chatId`绑定单笔业务编号，系统将所有请求归为同一对话上下文，导致请求排队执行，无法实现并发处理。
- 操作审核对话时提示“没有权限操作此对话记录”。原因：未将对话权限与当前审核岗的业务管辖范围绑定，仅允许访问对应预算单位的对话数据，超出权限范围的操作被拦截。

## 怎么确认配好了
- 发起单笔支付审核的提问，检查模型返回的检索结果是否仅关联当前业务的预算指标、合同等数据，无无关内容。
- 同时提交两笔不同业务的审核请求，确认两个对话的上下文相互独立，未出现数据混淆。
- 触发权限校验逻辑，使用无对应业务权限的账号访问对话，确认是否弹出权限拦截提示。
- 上传图片格式的报销凭证，确认模型可正常解析图片中的关键信息，未提示未找到答案。
