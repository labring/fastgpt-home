# 学生资助与奖补审核的文书与材料起草：引用来源与溯源

## 这个品类的数据长什么样
本品类涉及的数据主要来自全国学生资助管理信息系统、学校学籍系统、民政低保特困数据、财政支付系统。日常生成与核验的文档包含家庭经济困难认定表、资助申请表、奖助学金评审表、发放名单、公示材料。数据更新以学期为周期，每份文档包含学生身份标识、家庭经济状况认定结果、资助申请信息、发放明细等核心字段，需关联多系统数据完成交叉验证。

## 这些特征在「引用来源与溯源」这一环带来什么约束
跨系统的数据来源要求引用溯源环节需关联多个独立数据源，避免单一数据源的偏差。学期级的更新周期意味着知识库同步频率需匹配学期节奏，避免使用过期数据。文档类型覆盖认定表、评审表、发放名单等，不同文档的核心校验字段存在差异，需针对不同文档类型匹配对应的数据溯源规则。核验环节的出错后果直接关联学生资助资格与资金发放，要求溯源信息的准确性与可追溯性，确保每一项审核依据都能对应到原始数据节点。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文 | 8000–12000 token | 匹配跨系统学生资助数据的总长度，避免截断核心核验信息 |
| 知识库最大引用 | 前6条 | 覆盖多系统的核心数据源，避免冗余信息干扰审核逻辑 |
| `quoteMaxToken` | 1500–2000 字符 | 限制单条引用的长度，确保文书起草时引用内容清晰不冗余 |
| `responseData` | 开启 | 保留原始引用数据的字段，便于后续溯源核查 |
| `detail` | 开启 | 展示引用数据的来源系统与更新时间，匹配学期级数据的溯源需求 |
| 最大响应tokens | 3000–4000 token | 适配评审表、公示材料等长文档的起草需求 |

## 容易做错的三处
- 生成的文书中引用标记过多且杂乱。原因是未限制`quoteMaxToken`与知识库最大引用的取值，导致大量冗余数据源被拉入引用范围。
- 界面出现红色错误提示且引用内容为空。原因是未开启`responseData`配置，系统无法获取原始引用数据的有效字段，导致溯源信息无法正常展示。
- 生成的审核文书出现数据过期问题。原因是知识库同步频率未匹配学期更新周期，引用的学籍、低保数据为上一学期的旧数据，未完成最新周期的同步。

## 怎么确认配好了
- 测试生成一份家庭经济困难认定表的起草内容，检查引用标记的数量与来源系统是否匹配预设的知识库最大引用取值。
- 查看生成内容的引用详情，确认是否包含`detail`配置展示的来源系统与更新时间信息。
- 触发溯源校验流程，验证引用内容是否能关联至对应系统的原始数据节点。
- 调整`quoteMaxToken`的取值，观察单条引用内容的长度变化，确认配置生效。
