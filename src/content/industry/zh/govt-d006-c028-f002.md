# 市场主体登记与许可的文书与材料起草：向量模型与索引

## 这个品类的数据长什么样
本品类的日常文档包含设立登记申请书、章程、股东决议、住所证明、营业执照、食品经营许可申请等，数据来源于企业登记全程电子化系统、国家企业信用信息公示系统、电子营业执照系统与住所信息库。数据更新频率为每日，文档多为半结构化格式，包含主体名称、住所地址、股东信息、许可类型等固定字段，部分文档附带手写签字、盖章的图片附件与纯文本内容。

## 这些特征在「向量模型与索引」这一环带来什么约束
由于数据来源包含多个官方业务系统，不同系统导出的文档格式存在差异，索引构建时需要适配多格式文本的解析规则。每日更新的数据量需要适配增量索引机制，避免全量重建耗费过多资源。文档包含住所地址、股东信息、许可类型等垂直领域强语义字段，向量模型需要对这类细分场景的语义有较好的适配性。部分文档附带签字、盖章类附件，索引环节需要支持关联附件的文本提取与向量化流程。

## 配置怎么定
以下配置基于 FastGPT v4.17.0 版本。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxToken` | 8192 token | 适配市场主体登记类文书的平均长度，避免截断核心申请字段 |
| `defaultToken` | 2048 token | 作为默认上下文窗口，覆盖单份常见登记材料的文本长度 |
| 分块长度 | 800–1200 字符 | 保证登记类文书的单块语义完整性，避免拆分股东决议等连贯内容 |
| 重叠长度 | 100–200 字符 | 维持分块间的语义衔接，防止住所地址、股东信息等字段被割裂 |
| 相似度阈值 | 按实测标定 | 适配垂直领域的语义匹配标准，过滤无关的登记材料条目 |
| 单次搜索上限 | 前 10 条 | 覆盖常见关联登记材料的检索范围，避免冗余结果过多 |

## 容易做错的三处
- 现象：配置阿里千问text-embedding-v3模型时，界面提示default分组下无可用渠道。原因：未在OneAPI中配置对应模型的渠道映射，或分组权限未开放至default分组。
- 现象：知识库检索耗时过长，最终返回超时错误。原因：分块长度设置过大导致单块向量计算耗时增加，或单次搜索上限设置过高导致返回结果过多。
- 现象：检索结果中出现大量不相关的住所地址或股东信息条目。原因：相似度阈值设置过低，未过滤语义差异较大的无关文档，或分块重叠长度不足导致语义断裂。

## 怎么确认配好了
- 执行向量模型连通性测试，查看界面返回的模型列表中包含目标模型，无报错提示。
- 上传单份设立登记申请书，查看索引生成日志中无格式解析失败的记录。
- 发起检索测试，输入“食品经营许可申请”关键词，查看返回结果的语义匹配度符合业务预期。
- 查看增量索引任务的执行记录，确认每日更新的登记数据已成功同步至索引库。
