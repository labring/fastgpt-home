# 建设工程质量安全监督的文书与材料起草：引用来源与溯源

## 这个品类的数据长什么样
该品类的业务数据来自工程质量安全监管系统、施工现场实名制平台、监理日志、检测报告。日常起草的文书包括监督计划、监督检查记录、隐患整改通知书、质量问题处理单、竣工验收监督报告。数据按周更新，文档多包含现场检查项、整改闭环记录、验收核验参数等标准业务字段，无额外自定义统计单位，严格依托现有住建系统的规范格式。

## 这些特征在「引用来源与溯源」这一环带来什么约束
多源分散的业务数据要求引用溯源环节支持关联多个独立知识库，覆盖监管系统、现场平台、监理日志等不同数据源。周级更新节奏要求知识库同步周期匹配业务数据流转节奏，避免引用过时的整改或检查记录。固定格式的业务文档，要求引用时精准匹配对应字段，避免无关内容混入起草上下文。同时，质量与安全相关的文书溯源需严格对应原始记录，任何引用偏差都可能影响后续整改闭环或竣工验收流程。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文token数 | 8000–12000 token | 匹配单份竣工验收监督报告的常规内容长度，避免截断核心溯源信息 |
| `quoteMaxToken` 参数 | 2000–3000 token | 限定单条引用内容的长度，匹配现场检查记录、监理日志的典型篇幅 |
| 引用来源返回方式 | 按原文原样返回 | 确保溯源时可直接核对原始文档内容，符合监管业务的凭证属性 |
| `responseData` 开关 | 开启 | 强制返回知识库原文片段，满足直接输出原始内容的需求 |
| 单次召回结果上限 | 前6条 | 覆盖单份监督检查记录关联的典型原始资料，避免冗余信息干扰文书起草 |
| `detail` 模式 | 启用 | 保留引用内容的原始格式与业务字段，避免生成文书时的格式错乱 |

## 容易做错的三处
- 现象：生成的文书未附带知识库原文片段，仅显示AI改写后的内容。原因：未开启`responseData`开关，或配置的引用来源返回方式为非原文模式。
- 现象：单次检索返回的引用内容总长度超出模型承载上限，导致系统报错或超时。原因：未设置`quoteMaxToken`参数的上限值，或取值过大超出预设范围。
- 现象：引用的资料与当前起草的文书不匹配，上下文混入无关的历史整改记录。原因：单次召回结果上限设置过高，或未按文档字段进行精准匹配召回。

## 怎么确认配好了
- 起草一份监督检查记录，查看生成结果是否附带原始检测报告、监理日志的原文片段。
- 查看系统运行日志，确认每次检索返回的引用内容未超出`quoteMaxToken`参数设定的长度上限。
- 测试关联多个数据源的知识库，验证生成的隐患整改通知书可同时引用监管系统与实名制平台的记录。
- 调整单次召回结果上限，核对返回的引用条数是否符合预设的数量要求。
