# 社会救助与低保审核的文书与材料起草：向量模型与索引

## 这个品类的数据长什么样
本品类数据来自低收入人口动态监测平台、居民家庭经济状况核对系统及跨部门共享的公安、人社、医保、住建、税务数据。日常处理的文档包括低保申请表、家庭经济状况核对报告、入户调查表、民主评议记录、公示材料与救助审批表。数据更新频率为月度，文档结构多以结构化字段结合自由文本说明为主，包含家庭人员信息、收入财产明细、核对结论等核心内容。

## 这些特征在「向量模型与索引」这一环带来什么约束
本品类的数据特征对向量模型与索引环节带来多重约束。跨部门异构数据源导致字段格式不统一，需索引支持结构化与非结构化文本的适配嵌入。月度更新频率要求配置增量索引的定时同步逻辑，避免全量重建占用过多资源。文档包含短结构化字段与长自由文本内容，分块策略需兼顾不同长度的文本处理需求。核心数据关联家庭救助资格，索引召回的相关性需匹配业务审核的严谨标准。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配本品类文档中长文本入户调查记录与核对报告的内容长度，避免分块过碎丢失上下文或过长导致嵌入失败。 |
| 重叠长度 | 100–200 字符 | 衔接相邻分块的文本内容，保障长文档的语义连贯性，符合家庭经济状况类文本的逻辑关联性。 |
| `defaultToken` | 512 | 匹配本品类常用嵌入模型的输入token上限，平衡文本处理效率与语义完整性。 |
| `maxToken` | 4096 | 适配大模型上下文窗口要求，承载多份核对报告与审批材料的拼接内容。 |
| 单次搜索上限 | 前8条 | 覆盖本品类审核所需的关联数据量，避免召回过多无关信息干扰业务判断。 |
| 版本适配 | FastGPT v4.17.0 | 保障索引配置与平台功能的兼容性，避免版本差异导致的参数失效。 |

## 容易做错的三处
- 现象：导出的知识库dataset.csv仅含index字段无content字段。原因：未正确配置索引关联的数据源字段，未将文档解析后的文本内容映射至对应存储项。
- 现象：本地部署bge-large嵌入模型时，出现索引构建失败报错。原因：未预留足够的显存资源，或未正确指定模型加载的硬件适配参数，导致向量嵌入过程中断。
- 现象：自定义索引无法关联MongoDB对应表与字段。原因：未按照平台要求填写数据源的表名与字段映射路径，或字段类型与索引配置不匹配。

## 怎么确认配好了
- 执行单份低保申请表的文本解析与索引构建，检查解析后的content字段是否完整包含申请表内的所有结构化与非结构化内容。
- 发起家庭经济状况核对报告的向量检索，核对召回结果的条数与配置的单次搜索上限一致。
- 查看索引构建日志，确认增量同步任务按照月度周期自动触发，无连续失败记录。
- 测试跨数据源的字段关联检索，验证异构数据的嵌入结果符合业务逻辑。
