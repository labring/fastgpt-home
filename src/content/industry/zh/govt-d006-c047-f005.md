# 行政处罚案卷办理的文书与材料起草：工具调用与插件

本页面基于FastGPT v4.17.0版本编写。

## 这个品类的数据长什么样
执法机构办理行政处罚案卷的日常文档包含现场检查笔录、询问笔录、证据清单、行政处罚事先告知书、听证告知书、处罚决定书、送达回证。数据来源为行政执法办案系统、执法记录仪影像、国家企业信用信息公示系统、部门监管数据库，更新频率为每日。文档结构对应办案流程的不同环节，每个文档包含执法主体编号、违法事实描述、法律条款条目、送达地址等固定字段，按办案顺序归档。

## 这些特征在「工具调用与插件」这一环带来什么约束
多源且每日更新的数据要求工具调用支持并行拉取不同系统的执法数据，同时需要校验数据的时效性以避免使用过期信息。多种固定结构的执法文书要求工具调用适配不同文档的必填字段，避免生成不符合案卷格式的内容。执法案卷出错会导致处罚被撤销、行政复议败诉或案卷评查不合格，因此工具调用需要内置参数校验、失败重试与详细日志留存机制，保障生成内容的合规性与可追溯性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `toolChoice` | 指定固定函数列表 | 适配不同执法文书的固定生成逻辑，减少模型无效思考 |
| `functionCall` | 开启必填字段校验 | 确保生成的文书包含执法案卷要求的所有必填字段 |
| 最大上下文长度 | 8000–12000 token | 按实测标定，适配多源执法数据的加载需求 |
| 重试次数 | 2–3 次 | 应对接口临时波动，保障调用成功率 |
| 日志输出级别 | 全量详细日志 | 满足执法案卷的溯源审核要求 |
| 超时时间 | 600 秒 | 适配多数据源拉取的耗时上限 |
| 单次拉取数据上限 | 前 10 条 | 适配执法数据的单次加载规模 |

## 容易做错的三处
- 现象：工作流中工具调用节点无法添加连接线，界面无连接小圆圈。原因：未开启`functionCall`模式，或节点未绑定合法的MCP服务。
- 现象：MCP辅助模型生成任务耗时过长。原因：未通过`toolChoice`限制可选函数范围，导致模型遍历过多候选工具。
- 现象：HTTP工具调用无法接收文件入参。原因：未在工具配置中开启文件上传支持，未指定正确的文件参数类型。

## 怎么确认配好了
- 打开工具调用节点的配置界面，确认`toolChoice`已绑定对应执法文书的生成函数。
- 运行测试工作流，查看MCP服务的详细日志，确认调用过程被完整记录。
- 拖拽节点连接线，确认界面可正常添加连接点。
- 提交模拟执法数据作为入参，检查生成的文书是否包含所有必填字段。
