# 规范性文件合法性审核的文书与材料起草：工具调用与插件

## 这个品类的数据长什么样
本品类的核心数据来自官方法规规章库、上位法数据库、部门政策文件库及行政规范性文件备案系统，更新频率不定期。日常处理的文书与材料包含规范性文件草案全文、起草说明、合法性审核意见底稿、征求意见汇总表、备案报告等，单份文档通常包含完整的政策条文、起草背景说明、多部门反馈条目及审核结论框架。数据围绕文件合规性展开，涵盖文件主体、条文内容、制定权限依据、征求意见范围等核心信息，以文本条目和逻辑关联为主要数据形式，无固定标准化数值单位。

## 这些特征在「工具调用与插件」这一环带来什么约束
本品类的数据来源均为官方权威系统，因此工具调用需对接公开可访问的合法数据源，需配置访问白名单以保障数据安全性。日常文档多为长文本且结构复杂，工具调用需支持长上下文加载，确保完整的政策条文与配套材料可被完整处理。数据更新无固定周期，插件需支持按需刷新数据源缓存，仅在需要时更新本地存储的法规数据。最耗时的条文合法性比对环节，需触发专用的法规匹配插件，工具调用需具备自动识别合规审查需求的能力，避免遗漏关键比对节点。本品类聚焦抽象政策规则的合法性审查，不同于行政执法个案的合规校验，工具调用需重点围绕制定权限、程序与条文合法性展开。出错后果直接影响政策发布与执行，工具调用需配备失败重试与日志留存机制，确保审核过程可追溯。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | 自动匹配当前审核任务所需的工具，优先调用法规比对与合规校验插件 |
| 最大上下文长度 | `8000–12000 字符` | 适配规范性文件草案及配套材料的完整文本长度，确保所有审核相关内容可被完整加载 |
| `functionCall` | 当检测到法规比对需求时触发 | 仅在需要校验条文合法性时主动调用工具，避免无效调用消耗资源 |
| 插件调用超时时间 | `600 秒` | 满足法规库查询、上位法比对等耗时操作的时间需求 |
| 单次插件调用结果条数 | `前 10 条` | 获取最相关的上位法依据与政策参考，避免信息过载影响审核效率 |
| 插件调用配额 | `500 次/天` | 适配官方法规库的访问限制，避免超出接口调用额度 |

## 容易做错的三处
- 现象：调用法规库插件时返回路径无法访问的报错。原因：未配置插件的数据源访问白名单，或插件调用路径未绑定官方法规库的合法域名。
- 现象：传入自定义入参后插件无响应。原因：未按照FastGPT插件的入参格式传递字段，或未在配置中声明插件所需的必填参数。
- 现象：调用ollama模型时返回空结果，或无法通过openapi接口创建审核应用。原因：未正确配置模型部署地址与认证参数，或未调用FastGPT提供的应用创建api接口。

## 怎么确认配好了
- 发起一次规范性文件草案的审核测试，查看工具调用日志中是否存在法规库查询的成功记录，确认数据源访问正常。
- 传入预设的自定义入参调用插件，检查返回结果是否包含预期的上位法比对内容，验证入参配置的有效性。
- 调用ollama模型完成一段审核文本的处理，确认返回结果非空，调整模型配置参数以适配当前任务需求。
- 调用FastGPT的openapi接口尝试创建审核应用，确认接口返回正确的应用id，验证应用创建流程正常。
