# 道路运输经营许可的文书与材料起草：多轮对话与提示词

## 这个品类的数据长什么样
本品类数据来源于道路运政管理系统、全国道路运输车辆动态信息公共服务平台、车辆和从业人员数据库，更新频率为每日。日常涉及的文档包括经营许可申请、车辆技术档案、驾驶员从业资格材料、安全生产管理制度、道路运输经营许可证，核心字段包含车辆识别代号、从业资格证编号、安全生产制度条款、经营场地信息等，单篇材料长度跨度较大，部分档案类文档可达万字级别。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源多且分散，需要通过多轮对话逐步引导用户补充不同系统的关联信息，避免遗漏核心核验项。更新频率为每日，对话流程需实时拉取最新的车辆、人员状态数据，确保生成的文书符合当前有效信息。文档结构包含多个独立子项，提示词需拆分不同环节的生成逻辑，分别对应申请、档案、资质三类材料。字段数量多且业务属性强，需通过多轮追问补全缺失的特定字段，确保文书符合审批要求。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本适配：
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 8000–12000 字符 | 适配道路运输类文档的长文本特征，避免关键信息被截断 |
| 单次召回条数 | 前6条 | 覆盖车辆、人员、安全制度三类核心业务数据，满足基础审批需求 |
| `variables` 预设 | 绑定车辆识别代号、从业资格证编号等固定字段 | 减少重复录入，确保生成材料匹配企业真实资质 |
| `chatId` 绑定 | 关联会话唯一标识 | 区分不同企业的审批流程，避免上下文混淆 |
| 对话历史截断阈值 | 30 分钟内 | 适配道路运输许可审批的单日办理节奏，保留有效会话信息 |

## 容易做错的三处
- 调用API后返回的文书材料缺失核心字段，原因是未在请求中传入`variables`预设的业务字段，导致提示词无法匹配有效数据。
- 上传车辆技术档案后提示解析失败，原因是未设置适配长文本的分块规则，导致单块文本超出处理上限。
- 平台测试与API调用返回的结果不一致，原因是未在API请求中携带完整`messages`对话历史，导致上下文丢失。

## 怎么确认配好了
- 发起测试对话，输入对应业务场景的提问，检查返回内容是否包含预设的核心业务字段。
- 调用API传入包含多轮历史的`messages`参数，检查返回结果是否延续之前的对话逻辑。
- 上传单篇长文本的车辆档案文档，检查是否能正常解析并纳入对话上下文。
- 对比平台测试与API调用的配置参数，确认参数一致时返回结果无差异。
