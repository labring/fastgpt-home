# 食品安全监督抽检的文书与材料起草：向量模型与索引

## 这个品类的数据长什么样
本品类数据来自食品安全抽检监测系统、国家市场监管总局抽检结果查询系统、检验机构LIMS及企业台账，更新频率为月度。日常文档包含抽检计划、抽样单、检验报告、不合格食品核查处置报告、风险控制通告，文档字段包含抽样编号、检验项目、不合格项、处置措施等，部分文档包含数值型检测数据与标准化处置流程文本。

## 这些特征在「向量模型与索引」这一环带来什么约束
月度批量更新的数据规模较大，需控制单批次向量化任务的并发量，避免触发速率限制。多源文档包含结构化检测数值与非标准化处置文本，分块时需兼顾字段完整性与语义连贯性，避免将跨字段的关联信息拆分至不同块中。抽样单、检验报告的字段命名与格式相对统一，可通过结构化字段提取优化向量索引的召回精度，但需避免过度拆分导致语义断裂。同时，文档中包含大量专业术语与合规性文本，向量模型需适配领域术语的语义编码，索引需支持高召回率的检索以覆盖监管流程中的关键环节。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配抽检报告、处置通告的语义单元长度，避免拆分关键检测数据与关联字段 |
| 重叠长度 | 100–200 字符 | 保留跨分块的抽样编号、检验项目等关联信息，防止语义断裂影响检索精度 |
| embedding线程数 | 2–4 线程 | 降低单批次向量化速率，避免触发平台速率限制报错 |
| 单次召回条数 | 前 8 条 | 覆盖抽检流程中多环节的关联文档，同时控制检索开销 |
| `maxToken` | 4096 token | 适配主流领域模型的上下文窗口上限，避免截断关键处置流程文本 |
| `defaultToken` | 按实测标定 | 适配本地部署的模型token阈值，兼容不同硬件环境的内存限制 |

## 容易做错的三处
- 设置分块长度为3000字符时出现块丢失。原因：未考虑抽检报告中存在连续长文本的检测数据与字段绑定关系，过大的分块长度导致分块算法无法正确识别语义边界，遗漏部分关联文本。
- 向量化过程中触发速率限制报错。原因：未调整embedding线程数，单批次并发任务过多超出平台速率限制阈值。
- 知识库检索响应耗时较长。原因：未合理设置单次召回条数，或未针对月度批量更新的数据集优化索引分片策略，导致检索时遍历过多冗余分块。

## 怎么确认配好了
- 提交5份典型抽检文档样本进行向量化测试，检查日志中无速率限制报错，确认embedding线程数配置生效。
- 输入“不合格食品核查处置”相关查询词，核对召回结果中包含抽样单、检验报告、处置通告三类核心文档，确认单次召回条数的设置合理。
- 使用FastGPT v4.17.0的索引管理面板查看批量索引任务状态，确认任务在10分钟内完成索引就绪，无长时间挂起的进程。
- 验证检索结果中未出现文本截断现象，确认`maxToken`配置适配业务文档的长度需求。
