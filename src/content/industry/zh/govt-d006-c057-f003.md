# 食品安全监督抽检的文书与材料起草：多轮对话与提示词

## 这个品类的数据长什么样
本品类数据来源包括食品安全抽检监测系统、国家市场监管总局抽检结果查询系统、检验机构LIMS系统及食品生产经营者台账。数据更新频率为月度。日常处理的文档包含抽检计划、抽样单、检验报告、不合格食品核查处置报告、风险控制通告。文档字段包含抽样编号、检验项目、不合格判定依据、处置措施等，部分文档需关联抽样点位、检验批次等关联信息。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
月度更新的数据源要求对话上下文需限定当月有效数据范围，避免引用过期抽检信息。多类文档的差异化字段（如抽样单的抽样点位、检验报告的不合格判定依据）需要提示词明确区分不同文档的处理逻辑，防止字段混淆。关联数据的需求要求多轮对话中需主动确认当前处理的文档类型与关联批次，确保上下文匹配。基层监管所的使用场景要求对话流程轻量化，避免复杂参数配置，同时需保留可追溯的操作记录。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 上下文窗口大小 | 8000–12000 token | 适配抽检报告、处置报告等长文档的完整内容加载 |
| 单次召回结果数 | 前3条 | 匹配月度更新的有限数据源，避免冗余信息干扰 |
| `variables`配置 | 绑定抽样编号、检验批次字段 | 自动填充文档固定字段，减少手动输入 |
| `chatId`关联存储 | 开启会话历史绑定 | 方便回溯单批次抽检的全流程对话记录 |
| `messages`日志存储 | 开启完整对话记录 | 保留多轮交互的完整过程，便于问题排查 |
| 问题优化开关 | 开启 | 帮助整理监管人员的口语化抽检问题，转换为标准化查询指令 |

## 容易做错的三处
- 对话查看详情中无法显示应用内部详细记录。原因是未开启`messages`参数的完整日志存储配置，仅保存了最终回复内容。
- 本地部署后上传文件后数据处理为空。原因是未正确绑定品类专属数据源的访问权限，导致无法读取抽检系统导出的文档格式。
- 对话历史无法在mongodb中查询到。原因是未配置`chatId`与会话记录的关联映射，导致历史数据未按批次分类存储。

## 怎么确认配好了
仅作参考；请以目标 FastGPT 发布版本与部署文档核验。
- 发起单批次抽检的多轮对话，检查上下文窗口是否加载了对应批次的抽检计划、抽样单等文档内容。
- 调用变量替换功能，输入抽检编号，确认系统自动填充至`variables`配置的对应字段中。
- 查看会话记录，确认每条对话都通过`chatId`关联到当前抽检批次的完整流程。
- 触发问题优化功能，输入口语化的抽检问题，确认转换为标准化的查询指令。
