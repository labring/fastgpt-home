# 发电装备制造的文书与材料起草：多轮对话与提示词

## 这个品类的数据长什么样
发电装备制造的文书起草数据主要来自企业内部PLM系统、ERP运维日志、合规检验报告与项目技术文档。数据更新节奏随项目阶段变化，新机型研发阶段每周更新，常规运维项目每月更新。文档多为结构化格式，包含设备型号、运行参数、部件编号、检验日期等字段，参数带有专属单位，如汽轮机出力以MW为单位、锅炉蒸发量以t/h为单位，部分文档嵌套多层级技术说明。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
专业参数与单位的多样性要求多轮对话必须保留上下文内的设备专属标识，避免不同批次、型号的装备参数混淆。非固定更新频率要求提示词支持动态加载最新项目文档，多轮对话中需明确当前会话的项目范围。结构化文档的嵌套层级要求提示词引导模型按字段精准提取信息，避免遗漏关键单位与编号。不同项目的文档差异较大，多轮对话需固定当前会话的上下文边界，防止跨项目数据干扰生成结果。

## 配置怎么定
本配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 8000–12000 字符 | 发电装备文档包含大量长文本技术说明与参数，足够长度避免截断关键信息 |
| `messages` | 按对话历史自动拼接最近15条 | 保留多轮对话的上下文关联，确保模型理解连续的需求 |
| `variables` | 注入当前设备型号、批次号、检验标准 | 让提示词精准匹配当前起草文书的目标对象，避免参数错误 |
| 单次响应超时 | 60 秒 | 处理长文档关联的文书起草时，预留足够的模型生成与数据调用时间 |
| `chatId` | 绑定当前项目的唯一标识 | 确保同项目的多轮对话共享专属上下文，避免跨项目数据混淆 |

## 容易做错的三处
- 现象：首次发起对话时，首条响应延迟超过3秒，后续对话响应速度恢复正常。原因：首次对话需要加载当前项目关联的专业文档向量库，未提前预热上下文导致初始化耗时增加。
- 现象：多轮对话中生成的文书出现跨项目参数混淆，比如起草风电装备文档时引用了火电装备的参数。原因：未绑定`chatId`，导致不同会话的上下文被错误共享，模型无法区分当前项目的专属数据。
- 现象：生成的合规文书缺少强制要求的字段，比如未标注设备的批次号与检验日期。原因：未通过`variables`注入当前项目的必填字段变量，提示词未明确要求提取对应信息。

## 怎么确认配好了
- 发起新对话，输入当前项目的设备型号，核对模型是否能直接关联对应文档中的参数，无需重复询问基础信息。
- 发起多轮对话，修改一次设备参数后，验证后续生成的文书均使用更新后的参数，未保留旧参数。
- 等待首次对话响应，确认延迟符合预期后，检查生成的文书是否包含所有注入的`variables`字段。
- 切换到其他项目的会话，验证当前会话的上下文未被其他项目的文档干扰，生成的文书仅使用当前项目的数据。
