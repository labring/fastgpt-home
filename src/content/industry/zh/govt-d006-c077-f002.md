# 城市公交的文书与材料起草：向量模型与索引

## 这个品类的数据长什么样
城市公交的文书与材料主要来自日常运营台账、线路调整公告、安全检查报告、乘客服务规范、票务政策文件等。数据来源覆盖一线场站、调度中心与行政部门，更新节奏按需与定期结合，线路调整类文件随线路变动即时更新，运营报表按周或月归档。文档多为结构化格式，包含线路编号、执行日期、事项内容、审批节点等字段，单位涉及人次、运营公里、服务时长等。

## 这些特征在「向量模型与索引」这一环带来什么约束
城市公交的结构化文书与多更新节奏，对向量模型与索引环节带来多重约束。结构化字段多的场景下，需保留字段关联信息以避免语义割裂；按需更新的临时文件与定期归档的报表混合，要求索引支持增量刷新与全量重建的灵活切换；不同文书的长度差异大，从数十字的线路通知到数千字的安全报告，需适配灵活的分块逻辑；涉及人次、公里等多维度单位的内容，需通过向量归一化配置适配不同嵌入模型的输出特征。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配城市公交文书从短线路通知到长安全报告的长度跨度，避免单块语义断裂 |
| 重叠长度 | 100–200 字符 | 保留相邻分块的上下文关联，避免结构化字段被分块拆分导致语义丢失 |
| 相似度阈值 | 0.72–0.85 | 适配公交文书中专业术语与通用表述的语义区分度，过滤低相关检索结果 |
| 单次搜索上限 | 前 8 条 | 覆盖单篇公交文书的核心段落数量，同时控制单次检索的 token 消耗 |
| 最大上下文 | 30000 token | 符合 FastGPT v4.17.0 的通用上限，适配多份公交文书的拼接需求 |
| `defaultToken` | 按实测标定 | 适配城市公交文书的字段嵌入需求，匹配向量归一化配置要求 |

## 容易做错的三处
- 现象：检索返回了匹配的城市公交票务政策文件，但大语言模型输出未找到相关内容。原因：未开启上下文拼接的字段关联配置，导致检索到的分块与原始文档的字段信息脱节，模型无法识别内容归属。
- 现象：基础索引的检索召回率偏低，无法覆盖跨线路的运营通知内容。原因：未针对结构化字段设置专属的索引映射，导致专业术语的向量匹配精度不足。
- 现象：知识库查询流量过大时，单次请求的 token 消耗超出阈值导致超时。原因：未限制最大上下文的取值，直接使用较高的默认上限，导致每次请求推送过多文档内容。

## 怎么确认配好了
- 上传一份典型的城市公交安全检查报告，手动校验分块后的文本是否保留了核心字段与完整语义。
- 模拟多并发查询场景，观察检索返回的分块数量是否符合单次搜索上限的配置。
- 调用未归一化的嵌入模型，验证向量归一化配置是否生效，检查嵌入结果的向量模长是否统一。
- 上传新的线路调整通知，确认增量索引刷新的完成时间符合预期。
