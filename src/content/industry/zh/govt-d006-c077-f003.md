# 城市公交的文书与材料起草：多轮对话与提示词

## 这个品类的数据长什么样
城市公交的文书数据来源包括公交运营调度系统、票务结算系统、安全管理台账、线路调整公告、乘客服务记录等。日常运营数据每日更新，线路政策类文档按需更新，月度营收与安全汇总报表每月生成。文档包含结构化表格（如班次统计表、营收明细单）与非结构化文本（如安全整改通知书、乘客投诉回复函），字段包含线路编号、班次时段、载客人次、营收金额、投诉编号等，单位涉及人次、元、班次、公里等。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
结构化与非结构化文档混合的特征，要求多轮对话中先明确当前处理的文档类型，避免生成的文书格式混乱。数据来源分散且更新节奏不同，要求多轮对话初始环节确认数据的时间范围与来源范围，确保文书使用的是最新有效数据。字段数量多且有固定单位，要求多轮对话逐步引导用户补充必要字段，避免生成的文书缺项或单位错误。不同类型的文书有固定模板，要求提示词中先指定当前起草的文书类别，适配对应的格式要求。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 上下文窗口大小 | 前 8000–12000 字符 | 城市公交文书包含线路、班次等多字段信息，需要保留足够的多轮对话上下文避免关键信息丢失 |
| 变量绑定 | 绑定`variables`中的线路编号、班次时段、载客人次 | 对应城市公交文书的固定业务字段，减少多轮对话中重复询问的次数 |
| 对话上下文绑定 | 按`chatId`绑定对话历史 | 确保多轮对话的上下文信息连贯一致，避免重复询问用户相同信息 |
| 对话消息存储 | 按`messages`数组格式保存 | 完整保留每一轮对话的内容，支持后续的上下文回溯 |
| 回复格式约束 | 按指定JSON格式输出 | 方便后续将生成的文书自动导入公交运营管理系统 |
| 最大对话轮次 | 6 轮 | 适配公交文书起草的常规步骤，避免多轮对话过长导致上下文溢出 |
| 超时设置 | 300 秒 | 处理包含多字段的公交运营文书时，预留足够的信息整合与格式调整时间 |

## 容易做错的三处
-  尝试上传公交运营台账附件时提示`fail to create post presigned url`，原因是未正确配置S3存储的跨域访问规则，导致附件上传失败
-  要求AI按JSON格式回复但返回纯文本内容，原因是未在提示词中明确指定JSON的字段结构与必填项，或未正确绑定业务变量
-  升级版本后rag上传文件出现报错或对话窗口出现报错，原因是未正确迁移原有知识库与S3存储配置，导致上下文调用与附件上传功能异常

## 怎么确认配好了
-  发起测试对话，输入线路编号与班次时段，查看AI是否能自动关联绑定的业务变量
-  上传一份公交运营台账附件，确认上传成功且无报错提示
-  要求AI按指定JSON格式回复测试内容，检查返回结果是否符合预设格式要求
-  发起6轮以内的多轮对话，确认上下文信息未丢失，生成的文书包含所有必要的业务字段
