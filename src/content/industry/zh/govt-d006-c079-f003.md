# 城市燃气的文书与材料起草：多轮对话与提示词
本文档基于FastGPT v4.17.0版本编写。

## 这个品类的数据长什么样
城市燃气的文书与材料起草涉及的数据源主要来自燃气企业内部业务系统，包括报装申请、安全巡检、缴费通知、合规审批等文档。数据更新节奏随业务流程触发，报装申请提交、巡检完成或审批节点变更时同步更新。文档结构通常包含业务主体信息、用气地址、用气规模、审批节点、合规条款等模块，字段包含12位燃气报装编号、以立方米/小时为单位的用气负荷、以千帕为单位的管道压力、YYYY-MM-DD格式的巡检日期等，部分文档需匹配当地燃气管理的固定合规条款。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
燃气文书的字段带有明确业务属性与单位，多轮对话需严格匹配字段格式，避免混淆单位或生成不符合实际用气情况的内容。业务流程具有明确节点顺序，多轮提示词需跟踪当前审批环节，不能跳步生成超出当前节点的文书内容。数据随业务流程实时更新，对话上下文需同步最新的审批状态与现场数据，避免使用过期信息。部分文书需包含固定合规条款，提示词需预设对应条款的调用规则，确保生成内容符合当地燃气管理要求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` | 绑定报装编号、用气负荷、审批节点字段 | 城市燃气文书需精准匹配业务系统字段，避免生成不符合实际用气情况的内容 |
| `messages` | 保留最近5轮对话上下文 | 燃气审批流程有明确节点顺序，过多历史对话会干扰当前环节的合规判断 |
| `chatId` | 启用会话持久化，会话有效期7天 | 燃气报装、巡检整改流程通常跨1-3天，需通过会话ID跟踪完整流程 |
| 最大上下文长度 | 8000–12000 token | 单篇燃气文书通常在1000-3000字符，多轮对话需保留审批意见、现场数据等核心信息 |
| 超时设置 | 600秒 | 燃气业务数据查询通常需要连接内部系统，预留足够的接口调用时间 |

## 容易做错的三处
- 现象：工具调用结果未显示在对话框内，重新进入会话后可见但无工具返回内容。原因：未正确绑定`variables`关联业务数据，导致工具调用时无法获取燃气报装的最新参数，触发上下文匹配失败。
- 现象：iframe接入后界面显示为英文。原因：未配置会话语言绑定，默认加载FastGPT默认英文模板。
- 现象：对话过程中频繁出现Request Time报错。原因：超时设置取值低于业务系统接口响应时长，导致内部数据查询未完成即终止会话。

## 怎么确认配好了
- 发起报装文书起草对话，输入报装编号，检查生成的文书自动填充了对应用气地址和用气负荷字段。
- 发起跨3轮的审批流程对话，检查`chatId`未发生变更，历史审批意见被正确保留在上下文内。
- 发起包含复杂合规条款的对话，检查生成的文书包含当地燃气管理的必填条款。
- 测试超时场景，设置600秒超时，发起内部数据查询，确认未出现Request Time报错。
