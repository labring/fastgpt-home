# 基础电信运营的文书与材料起草：向量模型与索引

本文适配FastGPT v4.17.0版本。

## 这个品类的数据长什么样
基础电信运营的文书数据来源包括运维工单、客户服务函件、网络优化方案、制式标准文档、合作合同、资费公示文件等。更新节奏分为实时（运维工单、客户反馈）、每日（业务报表）、按需（合同修订、公示更新）三类。文档结构包含结构化元数据字段与非结构化正文，部分文档同时包含通信专业术语与通用说明文字，单位涉及分钟、GB、Mbps等。

## 这些特征在「向量模型与索引」这一环带来什么约束
混合了结构化元数据与非结构化正文，分块时需保留关联元数据以避免语义断裂，否则检索时无法精准匹配文档上下文。实时产生的运维工单与客户反馈要求索引支持增量更新，避免全量重建带来的性能损耗。文档长度跨度极大，从数百字符的客户投诉到数万字符的工程方案，需要适配灵活的分块策略。包含大量通信专业术语，向量模型需适配垂直领域语义，索引需保障高召回率以覆盖专业场景的检索需求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配基础电信文档的长度跨度，覆盖短投诉与长工程方案的语义完整性 |
| 重叠长度 | 100–150 字符 | 避免分块后上下文断裂，保留相邻块的语义关联 |
| `maxToken` | 8192 token | 匹配Qwen3-Embedding-8B的输入上限，保障长文本编码正常 |
| 相似度阈值 | 0.72–0.78 | 区分专业术语匹配与通用语义匹配，过滤低相关性结果 |
| 单次搜索上限 | 前 10 条 | 保障文书起草有足够参考素材，同时避免冗余信息干扰 |
| `defaultToken` | 512 token | 适配结构化元数据的向量编码需求，平衡精度与性能 |

## 容易做错的三处
- 启动向量库容器时报错“database “postgres” does not exist”，原因是使用了包含PostgreSQL依赖的非官方compose模板，未使用FastGPT官方适配的向量库配置。
- 检索返回结果包含大量无关的通用文档片段，原因是未设置合理的相似度阈值，未过滤低匹配度的内容。
- 向量编码任务超时，原因是分块长度超出`maxToken`的配置上限，导致嵌入模型无法正常处理长文本块。

## 怎么确认配好了
- 查看FastGPT的向量库连接日志，确认无数据库连接错误或权限异常。
- 上传一份典型的基础电信运维工单文档，验证分块后的文本片段保留了关联的结构化元数据。
- 发起一次文书起草的测试请求，核对检索返回的结果与当前任务的专业场景匹配。
- 查看模型配置页面，确认`defaultToken`与`maxToken`的取值与部署的嵌入模型参数一致。
