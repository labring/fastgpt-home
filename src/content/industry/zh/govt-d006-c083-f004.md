# 基础设施建设的文书与材料起草：工作流编排

## 这个品类的数据长什么样
基础设施建设的文书与材料主要来源于项目施工日志、招投标文件、变更签证、竣工验收报告等。数据更新节奏随项目推进节点调整，施工日志按日或周更新，进度台账按月更新，验收类文档在对应节点完成后一次性归档。单份文档结构包含项目编号、标段信息、施工日期、工程量、验收意见等字段，字段单位多为立方米、平方米、工作日、万元等，部分文档存在跨页字段关联的情况。

## 这些特征在「工作流编排」这一环带来什么约束
基础设施建设的文书数据来源分散且结构不统一，要求工作流需配置多源数据的字段映射规则，避免信息提取偏差。数据更新随项目节点触发，要求工作流的启动时机需与项目节点匹配，避免无效运行。单份文档篇幅较长且存在跨页字段关联，要求工作流需支持分段提取并保留字段上下文，同时需控制单轮处理的信息量，防止资源过载。全局核心字段如项目编号需在多环节工作流中复用，要求配置全局变量存储机制，确保跨节点数据一致性。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本适配。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 全局变量存储 | 开启并绑定项目ID为固定键 | 基础设施建设项目文书需跨节点复用标段、工程量等核心字段，避免会话重置导致变量丢失 |
| 工作流触发节点 | 按施工节点完成事件触发 | 匹配数据按项目节点更新的节奏，仅在有效数据产生时启动工作流 |
| 知识库召回上限 | 前8条 | 单份建设文书信息密度较高，控制召回结果数量以避免上下文过载 |
| 变量提取规则 | 绑定`variables`参数指定核心字段 | 精准提取文书中的工程量、验收意见等关键字段，避免无效信息混入 |
| 超时阈值 | 600秒 | 大型建设文书处理耗时较长，预留充足的处理时间 |
| 节点间数据传递 | 开启`nodeId`关联上下文 | 保留上一节点提取的变量，确保多环节工作流的数据连贯性 |
| 分块长度 | 800-1200字符 | 适配建设文书的字段密度，避免分块破坏跨页字段关联 |

## 容易做错的三处
- 现象：工作流运行后提取的工程量字段为空，日志中无对应字段的提取记录。原因：未绑定`variables`参数指定对应字段的提取规则，导致系统无法匹配文书中的目标字段。
- 现象：知识库搜索返回结果为空，界面显示“无匹配结果”。原因：未结合建设文书的项目编号、标段信息设置精准检索条件，仅使用泛化问题触发搜索。
- 现象：全局变量在会话结束后被重置，再次启动工作流时无法读取之前存储的项目ID。原因：未开启全局变量存储功能，仅使用会话级变量，导致会话结束后变量被清除。

## 怎么确认配好了
- 触发一次施工节点完成的模拟事件，检查工作流是否按预期启动。
- 查看变量面板，确认核心字段如标段信息、工程量是否被正确存储且未被重置。
- 发起一次文书检索，检查返回结果的条数是否符合预设的召回上限。
- 查看工作流运行日志，确认`variables`和`nodeId`参数是否被正确调用。
