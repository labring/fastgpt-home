# 基础设施建设的文书与材料起草：引用来源与溯源

## 这个品类的数据长什么样
基础设施建设的文书数据主要来源于施工日志、招投标文件、设计交底记录、竣工验收报告等项目产出文档。数据更新节奏随项目节点推进，单次提交的文档多为结构化与半结构化混合形式，包含项目编号、标段划分、施工日期、材料规格、验收结论等字段，单位多涉及立方米、米、吨等工程专用计量单元，单份文档长度跨度较大，从数百字符到数万字符不等。

## 这些特征在「引用来源与溯源」这一环带来什么约束
基础设施建设文档的长文本跨度要求溯源时需保留关键上下文，避免拆分后丢失工程逻辑关联。专用计量字段与单位的存在，要求溯源匹配需精准对应字段维度，不能仅依赖关键词命中。不定期的节点式更新，要求知识库溯源需关联对应项目版本，避免引用过期文档。同时多数内部项目文档未绑定公开网页链接，无法直接使用外部链接类溯源方式。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 单次搜索上限 | 前6条 | 基础设施建设文档多按标段分类，单次召回过多会导致上下文过载，6条可覆盖单标段核心文书 |
| 重排 | 开启 | 长文档拆分后易出现逻辑断裂，重排可优先召回与问题关联度更高的段落 |
| 最大上下文 | 8000–12000 token | 单份工程文档可能长达数万字符，足够的上下文可保留施工逻辑关联 |
| `quoteMaxToken` | 300–500 token | 用于限定引用片段的长度，匹配工程文书的单条款信息密度 |
| `responseData` | 开启溯源字段展示 | 可直接展示文档中的项目编号、标段等字段，替代泛泛的来源标注 |
| `detail` | 开启详细溯源 | 展示引用片段的上下文段落，便于核对工程参数的准确性 |

## 容易做错的三处
- 现象：配置后引用来源显示为外部网页链接，无法匹配内部工程文档。原因：基础设施建设的核心文书多为内部项目文件，未绑定公开网页或Notion链接，使用外部链接类溯源配置无法命中目标数据。
- 现象：返回的引用片段丢失工程专用单位或字段信息。原因：未开启`detail`配置或未设置足够的上下文长度，拆分文档时丢失了字段关联逻辑。
- 现象：召回的引用内容与提问的工程需求完全无关。原因：单次搜索上限设置过高，召回了非对应标段的文档，或未开启重排导致低关联片段被优先展示。

## 怎么确认配好了
- 上传一份典型的施工日志文档，发起包含具体工程参数的提问，查看返回结果的来源标注是否包含项目编号、标段等专属字段。
- 检查引用片段的上下文是否覆盖了施工日期、材料规格等关键信息，确认上下文长度适配当前文档的信息密度。
- 发起针对过期项目的提问，验证返回结果是否关联了最新的更新版本，确认知识库的版本溯源配置生效。
- 查看FastGPT v4.17.0版本的应用日志，确认`responseData`配置已开启，来源字段未出现空值或错误标识。
