# 民航机场的文书与材料起草：多轮对话与提示词

本文基于FastGPT v4.17.0版本编写，面向民航机场场景下的文书与材料起草需求，针对多轮对话与提示词环节的配置、约束与问题处理展开说明。

## 这个品类的数据长什么样
民航机场的文书与材料数据主要来自运行手册、空管报备模板、航班保障流程文件、旅客服务告知书、安检作业规范等。数据更新随航班换季每年两次，新航线开通或管制规则调整时会临时更新。文档多为固定格式，包含航班计划编号、起降时刻、机场三字码、保障设备型号等字段，单位涵盖小时、人次、米、千克等，单篇文档长度从数百到数千字符不等。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
民航机场文书的固定格式字段要求多轮对话中必须精准追踪机场三字码、航班号等专属实体，避免混淆不同航班或机场的信息。数据更新频率较高，提示词需加入版本校验逻辑，确保引用的运行手册或管制规则为最新版本。文档长度跨度大，多轮对话需要保留足够的历史上下文，避免截断关键的流程说明。临时管制或特殊保障的文书需要多轮确认细节，提示词需引导用户补充未明确的字段信息。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `messages` 历史长度 | 8000–12000 字符 | 民航机场文书多为长格式文档，需保留足够多的历史对话与引用内容，避免截断关键流程说明 |
| `variables` 绑定字段 | 机场三字码、航班计划编号、起降时刻 | 用于绑定民航场景专属实体，避免多轮对话中混淆不同航班或机场的信息 |
| `chatId` 会话隔离规则 | 按航班维度创建 | 确保同一航班的文书起草会话上下文不被其他会话干扰，避免跨航班的信息混淆 |
| 问题优化开关 | 开启 | 对模糊的文书需求自动补全必要的格式字段，引导用户补充未明确的信息 |
| 单次召回上限 | 前 3 条 | 机场文书多为标准流程文档，精准召回前序规范即可满足需求，避免引入无关内容 |
| 响应超时阈值 | 60 秒 | 适配机场运维人员的操作节奏，避免因等待过久出现超时报错 |

## 容易做错的三处
- 现象：对话过程中出现Request Time报错，状态码为408或504。原因：未设置合理的响应超时阈值，或绑定的`variables`字段过多导致上下文解析超时。
- 现象：对话中无法显示预设的表单输入项，交互字段为空。原因：未在`variables`配置中绑定民航场景专属字段，或会话未正确关联`chatId`导致上下文丢失。
- 现象：召回的文书内容与当前航班场景不匹配。原因：未按航班维度隔离`chatId`，导致不同航班的上下文被混淆，或单次召回上限设置过高引入无关文档。

## 怎么确认配好了
- 发起测试对话，输入“为PEK机场的CA1234航班起草起降保障申请”，检查对话中是否自动绑定了机场三字码和航班号的`variables`字段。
- 连续发起10轮关于不同航班的文书起草请求，确认每个会话的`chatId`隔离正确，上下文不会互相干扰。
- 等待60秒后查看对话响应，确认未出现超时报错。
- 上传一份机场运行手册文档，测试召回的内容是否与当前对话的文书需求匹配。
