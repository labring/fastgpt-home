# 煤电一体化的文书与材料起草：多轮对话与提示词

## 这个品类的数据长什么样
煤电一体化领域的文书与材料主要来源于内部生产台账、项目立项文档、安全检查报告、购销合同及机组运行报表。数据更新节奏分为两类：生产运行类数据按班次或每日更新，项目与合同类数据按需更新。文档结构多包含固定字段：项目编号、煤种热值、发电负荷、安全隐患等级、审批流程节点，单位涵盖吨、大卡/千克、兆瓦时、班次等专业计量标准，单份文档长度多在500至3000字符区间。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
煤电一体化文书的专业字段与单位要求，要求多轮对话中需明确传递字段定义，避免因术语歧义导致生成内容偏差。高频更新的生产数据，要求对话上下文需保留最新的实时参数，避免生成内容与当前业务状态脱节。长文档结构则要求限制上下文窗口的总长度，防止token溢出导致对话中断。同时，煤与电力两类业务的混合数据，要求提示词需明确限定文书的场景范围，防止混淆两类业务的专业规则。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文长度 | 8000–12000 token | 煤电一体化文书包含长段落与专业数据，需保留足够上下文避免关键信息丢失 |
| `variables` 绑定 | 绑定当日煤耗、机组负荷等预设变量 | 煤电业务数据实时更新，通过变量传递可确保生成内容匹配最新业务状态 |
| `messages` 历史截断 | 保留最近10轮对话 | 长对话易积累冗余信息，截断后可控制token消耗，避免触发超时 |
| 单次搜索上限 | 前6条 | 煤电文书需匹配精准的历史台账与规范，过多召回会干扰生成逻辑 |
| 问题优化 | 开启 | 专业术语较多，优化后可明确用户提问的核心需求，减少生成偏差 |
| `chatId` 标识 | 绑定唯一会话标识 | 确保多轮对话的上下文关联正确，避免不同会话的信息混淆 |

## 容易做错的三处
- 现象：调用API时返回格式不符合预设的JSON结构，报错文案显示“invalid schema”。原因：未通过`variables`参数绑定指定的JSON Schema，导致生成内容未匹配要求的格式。
- 现象：对话长时间无响应，后台日志显示超时记录。原因：未设置合理的最大上下文长度，长对话积累的煤电台账数据超出token限制，触发系统超时。
- 现象：生成的文书中混用煤种与电力的专业单位，例如将煤的热值标注为兆瓦时。原因：提示词未明确限定专业单位的使用规则，未绑定场景专属的字段校验逻辑。

## 怎么确认配好了
- 向对话输入包含煤电专业术语的提问，查看返回内容是否包含预设的`variables`字段对应的数据。
- 发起10轮连续对话，检查上下文是否被正确截断，未出现token溢出相关的报错提示。
- 调用API测试，确认返回的`messages`参数包含最近的对话历史，无冗余的旧会话数据。
- 输入包含专业单位的提问，检查生成内容是否匹配正确的计量规则。
