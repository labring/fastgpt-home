# 矿山采选的文书与材料起草：多轮对话与提示词

## 这个品类的数据长什么样
矿山采选的文书数据来源包括地质勘探报告、采掘作业计划单、安全巡检台账、选矿工艺参数记录、环保验收文件等，分散在不同业务系统。更新节奏为日常巡检记录每日更新，月度采掘计划每月更新，年度综合报告按季度或年度更新。文档结构多带有固定表头，包含项目编号、开采区域、作业时段、核心参数等字段，专业字段带有专属单位，如凿岩深度以米为单位、选矿回收率以百分比为单位、通风量以立方米每小时为单位。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源分散导致多轮对话需要关联不同系统的字段，提示词需明确字段关联规则，避免生成的文书参数脱节。部分文书内容较长，多轮对话的上下文窗口需限制在合理范围，避免内容溢出导致解析失败。专业字段带有专属单位，提示词需明确要求生成内容匹配对应单位，否则会出现参数不规范的问题。数据更新频率较高，会话历史需按项目维度过滤，避免不同项目的历史记录混淆影响生成结果。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文窗口 | 8000–12000 token | 匹配矿山采选文书的平均内容长度，避免多轮对话时上下文溢出 |
| 变量注入配置 | `variables`参数绑定专业字段 | 自动带入开采区域、矿石品位等业务参数，减少手动输入误差 |
| 对话消息格式 | 按`messages`数组结构组织 | 符合FastGPT的对话解析标准，确保多轮上下文连贯 |
| 会话标识关联 | `chatId`绑定项目编号 | 固定会话唯一标识，便于后续按项目检索历史对话 |
| 上下文过滤规则 | 按`chatId`匹配历史 | 区分不同项目的会话，避免历史记录交叉干扰 |

## 容易做错的三处
- 调用对话接口时返回404状态码。原因是未正确配置模型接入的地址或端口，导致无法连接到目标模型服务。
- 按项目检索历史会话时返回全部记录。原因是未在历史查询逻辑中正确绑定`chatId`参数，未执行有效的过滤操作。
- 生成的文书中残留think标签内容。原因是工作流中的代码运行节点仅在调试环境生效，正式运行时未正确执行内容清洗逻辑。

## 怎么确认配好了
- 发起测试对话，输入矿山项目的专业参数，检查生成的文书是否自动带入对应字段。
- 切换不同的`chatId`发起对话，检索历史记录，确认仅返回当前项目的会话内容。
- 查看生成的文书内容，确认无多余的思考标签残留。
- 调用接口发起请求，检查返回的状态码是否为200，无404类连接错误。
