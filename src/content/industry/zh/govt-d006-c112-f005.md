# 粮食储备的文书与材料起草：工具调用与插件

## 这个品类的数据长什么样
数据来源包括储备粮库存明细台账、轮换业务审批文件、仓储作业记录、政策性收储拨付凭证。文档结构多为结构化表格搭配段落说明，字段包含粮食品类、存储仓号、数量（单位为吨）、入库日期、质检等级、补贴核算基数等。更新频率随业务节点变化，日常作业数据每日更新，季度轮换计划提前15个工作日定稿，年度储备报告于次年1月底前完成。

## 这些特征在「工具调用与插件」这一环带来什么约束
结构化台账与审批文件混合的文档结构，要求工具调用时需精准匹配粮食品类、存储仓号等专属字段，避免泛化提取导致数据错位。特定单位（如吨）的字段校验需求，增加了参数提取的约束条件。多源数据联动的文书起草场景，要求插件支持同时调用库存数据库、补贴系统接口，提升了配置复杂度。固定格式的储备文书要求，需限制工具输出的结构与官方模板对齐，避免格式偏差。

## 配置怎么定
本配置基于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `toolChoice` | 设为`auto`，并指定仅调用粮食储备专用工具 | 适配文书起草需调用多业务工具的场景，避免无关工具干扰 |
| 数据库连接超时设置 | 300 秒 | 匹配粮食储备台账数据的批量查询耗时，避免因数据量较大导致超时 |
| 自定义字段映射规则 | 按粮食品类、存储仓号、数量（吨）映射 | 匹配储备数据的专属字段结构，确保提取数据准确 |
| `functionCall` | 开启强制参数校验 | 避免生成的文书出现单位错误或字段缺失 |
| 单次工具返回条数 | 前15条 | 控制返回数据量，避免超出上下文窗口限制 |
| 数据时间范围限定 | 近30天 | 适配日常文书起草的最新数据需求，避免调用过期业务数据 |

## 容易做错的三处
- 配置了MySQL数据库连接插件，执行库存数据查询时无返回结果，日志显示字段匹配失败。未按粮食储备专属字段（如存储仓号、粮食品类）配置映射规则，导致插件无法识别目标数据表。
- 配置自定义URL解析插件，上传储备库公开报表链接后无数据返回。未开启URL解析的文本提取开关，或未配置对应网站的访问权限白名单。
- 调用`functionCall`生成轮换申请报告时，输出内容未包含数量单位。未开启`functionCall`的强制参数校验，导致生成内容遗漏必填单位字段。

## 怎么确认配好了
- 手动触发一次库存数据查询工具，核对返回结果的字段是否包含粮食品类、存储仓号、数量等专属字段。
- 提交一份模拟的轮换申请需求，检查工具调用生成的文书格式是否与官方储备文书模板对齐。
- 同时发起两个不同的文书起草请求，验证插件是否能正常并行处理请求。
- 配置目标储备库的公开报表URL并触发解析，核对返回的文本是否包含报表核心数据。
