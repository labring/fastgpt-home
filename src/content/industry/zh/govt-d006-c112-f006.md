# 粮食储备的文书与材料起草：引用来源与溯源

## 这个品类的数据长什么样
粮食储备相关数据主要来自日常入库出库台账、轮换计划文档、质检报告、库存盘点报表及专项审计记录。数据更新节奏为：入库出库操作实时更新台账，月度盘点更新汇总报表，季度/年度专项报告按既定计划更新。文档结构包含批次编号、存储仓号、质检指标（水分、杂质率）、出入库数量、操作日期等字段，常用单位为吨、百分比、自然日。

## 这些特征在「引用来源与溯源」这一环带来什么约束
粮食储备数据的字段关联性强，引用溯源需精准匹配批次号、仓号等核心标识，否则无法准确定位原始记录。数据更新频率较高，需定期刷新知识库以避免引用过期的库存或质检信息。单份文档的核心信息长度较长，文书起草时需保留完整的质检、出入库关键数据，因此对引用token上限有明确要求。同时，文书起草常需整合多份关联文档，需确保检索结果能覆盖足够的关联条目。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 粮食储备文档的核心字段多为短段落，该长度可保留批次、仓号等关键关联信息 |
| 重叠长度 | 100–200 字符 | 避免跨块的批次号、操作日期等信息被截断，确保溯源时可完整关联 |
| 单次搜索上限 | 前 10 条 | 储备数据条目较多，过多结果会超出上下文窗口，优先返回高匹配度的核心记录 |
| 重排 | 开启 | 优先匹配批次号、存储仓号等核心检索条件，提升引用来源的准确性 |
| 最大上下文 | 8000–10000 token | 文书起草需整合多份关联的储备记录，该窗口可覆盖常用的整合需求 |
| `quoteMaxToken` | 1500–2000 token | 单份储备文档的核心信息长度多在该区间，可保留完整的质检、出入库关键数据 |

## 容易做错的三处
- 现象：配置`quoteMaxToken`为1500后，知识库中长度超1500的文档块仍被引用。原因：未开启分块强制截断，系统仅按全局上下文限制截断，未单独限制单条引用的token长度。
- 现象：检索到匹配的储备数据，但对话界面不显示引用来源，仅返回空引用字段。原因：未开启`responseData`配置中的元数据返回开关，导致检索结果未携带文档标识信息。
- 现象：工作流中检索结果传入HTTP请求后，AI对话无法正确关联引用。原因：未按要求返回包含批次号、存储仓号、文档标题的结构化数据，导致AI无法匹配溯源信息。

## 怎么确认配好了
- 上传一份标准的粮食储备入库台账文档，设置分块长度为1000字符，查看分块后的结果是否将长段落拆分为符合长度的块。
- 发起包含“2024年第1季度XX粮库轮换计划”的查询，核对返回的引用来源是否包含粮库编号、轮换批次等核心元数据。
- 配置单次搜索上限为8，发起多条件检索，查看返回的引用条数是否不超过8条。
- 在FastGPT v4.17.0版本中，检查知识库的“引用设置”模块，确认`detail`配置已开启，确保返回的引用信息包含完整的文档路径与元数据。
