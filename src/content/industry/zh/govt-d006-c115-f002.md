# 轨道交通装备的文书与材料起草：向量模型与索引

## 这个品类的数据长什么样
轨道交通装备的文书数据主要来自设计阶段的技术说明书、工艺规程、检验报告，运维阶段的工单记录、变更文档，以及商务阶段的合同附件。数据更新节奏分为项目启动时的批量导入，与日常运维中的单次增量更新。文档结构多为固定层级，包含设备型号、批次号、检验日期等专属字段，参数单位多为mm、kN、MPa等工业标准单位，单份文档篇幅跨度较大，部分整车技术文档可达数十页。

## 这些特征在「向量模型与索引」这一环带来什么约束
固定层级的文档结构要求分块逻辑匹配章节边界，避免将跨层级的技术参数拆分到不同块中。专属字段与单位的存在，要求索引需关联元数据以保障检索时的字段准确性。长文档与批量导入的更新模式，要求增量索引的触发逻辑需匹配项目与工单的更新节点，避免全量重复索引。专业术语的严谨性要求召回精度需高于通用场景，对相似度阈值与分块完整性提出更高约束。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的界面与参数逻辑。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 匹配轨道交通装备技术文档的单段内容长度，保障单块信息完整 |
| 重叠长度 | 150–200 字符 | 避免跨分块的关联技术参数被截断 |
| 最大段落深度 | 3 | 匹配技术文档的标准层级结构（总章-分章-小节） |
| `maxToken` | 4096 token | 适配多模态Embedding模型的输入长度上限 |
| 单次搜索上限 | 前6–10 条 | 平衡召回覆盖率与检索响应速度 |
| 相似度阈值 | 0.72–0.85 | 匹配轨道交通装备专业术语的匹配精度要求 |

## 容易做错的三处
- 接入多模态Embedding模型时返回`{"error":{"code":"Invalid`格式报错，原因是未将`maxToken`设置匹配模型输入上限，导致超长文档块无法完成向量化。
- 执行知识库重建索引后，历史文档的关联检索结果出现字段缺失，原因是未同步更新元数据映射规则，导致新旧索引的字段关联逻辑不一致。
- 分块预览显示段落识别混乱，将不同章节的内容合并到同一分块中，原因是最大段落深度设置超过文档实际层级，导致模型误判分块边界。

## 怎么确认配好了
- 上传一份轨道交通装备的典型技术说明书，查看分块预览是否按章节拆分，无跨层级内容混杂的情况。
- 调用检索接口，输入专业技术问题，查看返回结果的相似度分值是否处于设定的阈值区间内。
- 执行增量索引任务，验证新上传的运维工单是否被正确关联到对应项目的文档库中。
- 导出向量库的元数据列表，确认设备型号、批次号等专属字段已被正确索引并关联。
