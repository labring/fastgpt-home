# 轨道交通装备的文书与材料起草：多轮对话与提示词

## 这个品类的数据长什么样
轨道交通装备的文书与材料数据主要来源于研发设计文档、生产工艺文件、运维检修记录、合规报审材料及招投标文书。数据更新随研发节点、生产批次、运维周期动态调整，研发阶段文档更新频率随设计迭代变化，运维阶段按月度更新检修记录。文档多采用分章节结构，包含部件型号、生产编号、技术参数、合规标准编号等字段，单位涵盖毫米、千牛、运行小时等专业计量标识。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
专业字段与计量单位的存在，要求多轮对话的提示词需明确限定参数格式与单位，避免生成不符合行业规范的内容。动态更新的文档结构，要求多轮对话流程中需定期触发知识库同步，确保召回内容与当前装备状态匹配。分章节带唯一标识的文档结构，要求多轮对话中需先引导用户明确目标部件的型号或生产编号，缩小检索范围，避免跨部件信息混淆。运维记录按批次归档的特征，要求提示词需绑定批次维度，确保召回内容对应指定生产批次的装备数据。本配置基于FastGPT v4.17.0版本的功能逻辑。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 上下文窗口大小 | 8000–12000 token | 匹配轨道交通装备文书的长文本特征，避免截断关键技术参数 |
| `variables` | 预设「部件型号」「生产批次」「文档类型」变量 | 固定多轮对话中的核心检索维度，减少无效召回 |
| `messages` | 保留最近20条交互记录 | 平衡上下文连贯性与系统响应速度，适配多轮文书起草的迭代需求 |
| `chatId` | 绑定单个装备项目的唯一标识 | 隔离不同项目的文书数据，避免跨项目信息混淆 |
| 检索召回上限 | 前8条匹配结果 | 匹配单份文书的核心信息体量，避免输出内容冗余 |
| 提示词模板 | 按实测标定 | 适配轨道交通装备专业术语的格式要求，确保生成内容符合行业规范 |

## 容易做错的三处
- 现象：生成的文书内容超出知识库范围，包含非预设的外部专业信息。原因：未在提示词中明确限定LLM仅使用知识库召回的内容进行生成，导致LLM调用自身通用知识。
- 现象：生成的运维文档中附带知识库段落的部件编号与生产批次标识。原因：未在提示词中明确要求隐藏内部元数据字段，导致LLM直接引用检索结果中的非公开标识。
- 现象：自定义模型在对话界面与工作区的输出结果出现偏差。原因：未统一绑定`chatId`与项目专属的知识库集合，导致两个场景下的检索数据源不一致。

## 怎么确认配好了
- 发起一轮针对指定部件型号的文书起草请求，核对生成内容中是否包含目标部件的专业参数，且无内部标识字段。
- 上传一张专业技术图纸，确认对话框可正常加载并显示对应内容。
- 分别在对话界面与工作区使用同一自定义模型发起相同请求，核对两次输出结果的一致性。
- 调整`variables`变量的预设值，确认多轮对话中可实时更新检索维度并匹配对应文档。
