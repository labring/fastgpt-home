# 通信工程建设的文书与材料起草：多轮对话与提示词

## 这个品类的数据长什么样
通信工程建设的文书与材料数据主要来源于项目立项批复文件、施工图设计图纸、监理周报、竣工验收报告等官方交付文档。数据按项目实施节点更新，立项后同步基础信息，施工阶段按进度周报更新工程量，验收阶段同步最终验收标准。文档结构包含项目基本信息区、工程量清单区、材料参数区、施工工序区与验收标准区，字段包含工程编号、光缆芯数、基站高度、端口数等，单位多为米、公里、端口、套等工程专用单位。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
通信工程文书的单份文档长度较长且包含大量专用参数，多轮对话的上下文容易超出模型处理上限，需严格限制历史对话的保留范围。专用字段与单位的唯一性要求提示词必须明确绑定项目专属数据，避免模型混淆不同项目的参数。数据按节点更新的特性，要求多轮对话中需优先调用当前会话绑定的最新项目数据，确保使用的是当前项目的有效信息。复杂的文档结构也要求提示词需拆分任务，先确认项目基础信息再处理具体文书内容，避免生成结果偏离项目实际需求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 8000–12000 字符 | 通信工程单份文书常超5000字符，保留足够上下文避免截断关键参数 |
| 多轮对话历史保留条数 | 前 8 条 | 覆盖项目需求变更的关键对话，同时避免历史过长占用模型资源 |
| `variables` 绑定 | 绑定项目专属工程编号、材料规格字段 | 确保提示词调用时精准匹配当前项目的专用数据 |
| `chatId` 会话绑定 | 绑定当前项目的唯一会话标识 | 确保多轮对话的上下文仅关联当前项目，避免跨项目数据混淆 |
| 提示词问题优化 | 开启 | 自动将用户的口语化工程需求转化为标准化文书格式 |
| 最大响应超时 | 120 秒 | 复杂文书生成需足够时间处理工程量计算与格式调整 |

## 容易做错的三处
- 现象：生成的工程材料清单中配套的设备拓扑图显示不完整，仅展示局部。原因：提示词未明确要求嵌入完整的资源引用路径，或多轮对话中未保留图片占位符的上下文。
- 现象：升级至FastGPT v4.17.0后，对话返回结果末尾出现规则追溯展示符号。原因：未在系统提示词中配置关闭默认规则展示的指令。
- 现象：连续发起3次以上文书生成请求后出现响应延迟。原因：未限制单会话的并发请求上限，导致资源占用超出系统承载能力。

## 怎么确认配好了
- 发起包含项目工程编号、指定材料规格的测试对话，核对返回结果中是否精准匹配绑定的`variables`字段内容。
- 发起连续多轮对话，检查`messages`字段是否按设定的保留条数加载历史对话，未出现冗余内容。
- 生成一份完整的工程验收报告，核对结果末尾是否存在未预期的规则展示符号。
- 测试不同复杂度的文书生成请求，确认响应时间符合业务场景的预期要求。
