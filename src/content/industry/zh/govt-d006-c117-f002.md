# 通信铁塔与基础设施的文书与材料起草：向量模型与索引

## 这个品类的数据长什么样
通信铁塔与基础设施的文书数据主要来源于日常运维工单、塔基巡检报告、租赁合同、维护日志与合规检查文档。数据更新节奏存在差异：运维工单与实时巡检数据随事件触发更新，年度巡检报告与租赁合同按周期更新。单份文档结构包含唯一标识字段（如6位塔号）、物理属性字段（如塔高、倾斜度，单位为米、‰）、业务字段（如隐患等级、处理时长，单位为小时）与关联责任人信息。

## 这些特征在「向量模型与索引」这一环带来什么约束
该品类的多字段混合数据、差异化更新节奏与长文本占比，对向量模型与索引环节带来多重约束。数值型属性与文本语义需同时纳入向量化流程，避免仅依赖文本匹配导致的关联错误。增量数据与全量数据需区分处理，确保实时工单不会因全量索引延迟而无法被检索。长文档拆分需保留跨分块的关键标识，避免塔号、塔位地址等关联信息被割裂，影响召回精准度。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 匹配单份巡检报告、工单的平均文本长度，避免过度拆分或冗余 |
| 重叠长度 | 50–80 字符 | 保留跨分块的塔号、隐患等级等关键关联信息，防止语义断裂 |
| 相似度阈值 | 0.72–0.85 | 适配数值型字段与文本的混合语义匹配需求，平衡召回率与精准度 |
| 单次搜索上限 | 前6条 | 匹配单份文书所需的关联数据量，避免过多冗余结果干扰生成 |
| defaultToken | 4096 | 适配单份长文档的向量化上下文长度，确保完整语义捕获 |
| maxToken | 8192 | 满足多份关联文档拼接后的上下文需求，支持复杂文书起草的信息调用 |

## 容易做错的三处
- 搜索时所有结果相关性极低：未将塔号、塔位地址等唯一标识作为元数据绑定到分块文本，导致向量匹配无法关联正确的塔基业务数据。
- 索引中始终无数据：未配置增量索引触发规则，仅执行全量索引导致新增的运维工单、实时巡检报告未被录入索引库。
- 最后一组索引分块无法完成向量化：拆分长文档时未保留关联的数值型属性（如倾斜度、塔高），导致分块语义不完整，向量模型无法生成有效嵌入。

## 怎么确认配好了
- 上传单份塔基巡检报告至FastGPT v4.17.0，查看分块预览界面，确认塔号、隐患等级等关键信息未被跨块割裂。
- 发起针对特定6位塔号的搜索请求，验证召回结果包含该塔的所有关联工单、巡检报告与租赁合同。
- 提交长文档向量化任务，查看任务日志无上下文截断或超时报错。
- 调整相似度阈值，验证不同阈值下的召回结果符合业务匹配的合理范围。
