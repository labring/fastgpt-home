# 通信铁塔与基础设施的文书与材料起草：模型接入与配置

## 这个品类的数据长什么样
通信铁塔与基础设施的运维与合同数据主要来自三类来源：铁塔运维台账系统、基站巡检报告、场地租约档案。运维台账按月更新，包含铁塔ID、塔高、建设年份、维护记录等结构化字段，单位统一为米、元/年；巡检报告按周更新，包含巡检日期、铁塔倾斜度、螺栓紧固状态、现场拍摄照片；租约档案按季度更新，包含甲乙双方信息、租期、租金标准、违约责任等长文本内容。文档结构以结构化表格与非结构化图文混合为主，部分巡检报告单篇字数可达数千字符。

## 这些特征在「模型接入与配置」这一环带来什么约束
该品类的数据兼具结构化字段与非结构化图文，且单篇文档长度差异较大，要求模型接入配置需适配长文本解析与视觉信息识别。运维台账的固定字段单位需严格匹配，模型生成的文书不能出现单位混用。不同数据源的更新频率不同，批量处理文书时需适配不同的同步节奏，避免因数据滞后导致生成内容与当前运维状态不符。同时，铁塔ID等唯一标识需被模型准确识别，防止在多塔文书中出现混淆。FastGPT v4.17.0的配置逻辑需针对该品类的混合数据格式做针对性调整。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 通信铁塔的巡检报告、租约合同多为长文本，需容纳完整的历史台账与当前待起草文书的上下文，避免截断关键信息 |
| `maxTokens` | 2000–3000 token | 单份运维文书（如整改通知书、租约续签函）需覆盖全部整改项与合同条款，输出长度需匹配业务需求 |
| `temperature` | 0.2–0.4 | 文书需保持严谨性，避免生成与铁塔运维规范不符的内容，降低随机生成的偏差 |
| `vision` | 开启 | 巡检报告附带现场照片，需识别照片中的螺栓松动、倾斜等视觉信息，用于起草针对性的整改文档 |
| `AIPROXY_API_ENDPOINT` | 按部署服务商提供的专属地址填写 | 适配通信铁塔品类专用的模型调用链路，确保请求路由合法有效 |
| `AIPROXY_API_TOKEN` | 与部署绑定的专属密钥 | 保障调用权限，防止未授权访问运维与合同敏感数据 |

## 容易做错的三处
- 现象：调用模型返回404 status code (no body)。原因：未正确填写`AIPROXY_API_ENDPOINT`的路径，或`AIPROXY_API_TOKEN`无效，导致请求无法匹配模型服务的合法路由。
- 现象：部分上传的铁塔巡检文档未被模型自动解析用于文书起草。原因：未开启`vision`配置项，或文档长度超出默认解析阈值，导致模型跳过非结构化内容的解析。
- 现象：批量调整向量训练参数时仅支持单文件操作。原因：未将同品类的铁塔运维文档归类到同一知识库分组，或未启用批量向量更新的预设模式，无法实现批量同步。

## 怎么确认配好了
- 测试调用`AIPROXY_API_ENDPOINT`对应的模型接口，检查返回状态码为200，且响应体包含合法的模型输出内容。
- 上传一份带现场照片的铁塔巡检报告，确认生成的整改通知书中包含照片识别出的具体问题项。
- 批量上传同类型的铁塔运维文档，检查系统是否支持批量同步向量更新，无需单文件重复操作。
- 生成一份租约续签函，核对其中的塔高、租金等字段的单位与输入台账的单位保持一致。
