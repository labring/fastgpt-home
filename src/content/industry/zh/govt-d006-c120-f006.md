# 铁路运营的文书与材料起草：引用来源与溯源

## 这个品类的数据长什么样
铁路运营的文书与材料起草相关数据，主要来源于行车调度日志、线路维护周报、客票运营报表、临时调度指令等。数据更新节奏依类型区分：日常调度类文档实时或每小时更新，月度运营报表每月更新。文档结构固定包含作业编号、执行时间、线路区段、作业类别、关联人员编号等字段，单位多采用公里、人次、分钟等铁路行业标准单位。

## 这些特征在「引用来源与溯源」这一环带来什么约束
铁路运营数据的实时性、结构化字段与合规性要求，为引用溯源带来多重约束。实时更新的调度类文档要求检索节点优先召回最新条目，避免引用过期信息；固定的作业编号、线路区段等字段，要求溯源时需精准绑定对应字段值，仅依赖关键词匹配易混淆同类型不同作业的文档。篇幅差异较大的文档（从数百字的调度指令到数万字的月度报表），要求溯源环节需适配不同长度的源文档，避免截断关键合规信息。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `quoteMaxToken` | 4000–6000 token | 适配铁路运营文档的单篇平均长度，避免超出模型上下文限制，同时覆盖核心溯源信息 |
| `responseData` | 仅返回源文档片段 | 满足铁路运营文书的合规溯源要求，避免AI修改原始内容 |
| `detail` | 开启 | 保留源文档的作业编号、执行时间等字段，确保溯源信息完整 |
| 单次召回上限 | 前8条 | 匹配铁路运营日常作业的文档数量规模，避免过多冗余信息干扰检索 |
| 上下文拼接长度 | 按实测标定 | 适配大语言模型的上下文窗口，避免拼接后超出处理上限 |

## 容易做错的三处
- 现象：工作流中调用知识库节点时，全局变量datasetid未生效，节点返回空结果。原因：未在节点配置中绑定全局变量作用域，或变量命名与配置项内的参数名不匹配。
- 现象：AI返回的引用内容被二次修改，添加了非原文的修饰性表述。原因：未开启`responseData`配置项，导致大语言模型对源文档进行了重写。
- 现象：知识库检索返回的源文档条数超出预期，且查询耗时过长。原因：未设置合理的单次召回上限，同时未限制`quoteMaxToken`的取值，导致大量冗余数据被送入模型。

## 怎么确认配好了
- 进入FastGPT v4.17.0的知识库检索节点配置页面，检查`quoteMaxToken`的取值是否与业务文档长度匹配。
- 发起测试调用，查看返回结果中是否包含源文档的作业编号、执行时间等字段，确认`detail`配置已生效。
- 触发工作流运行，检查返回的引用内容是否与源文档完全一致，未出现额外修饰。
- 查看节点运行日志，确认全局变量datasetid已被正确加载，未出现未定义变量报错。
