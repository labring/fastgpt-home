# 12345热线工单办理的申报材料与案卷审核：向量模型与索引

## 这个品类的数据长什么样
本品类的数据主要来自12345热线平台、承办单位业务系统、内部知识库、回访评价数据及地方热线管理规范。数据更新频率为每日，涵盖诉求登记单、派单记录、办理答复、回访记录、延期申请、退回说明及知识库条目等文档类型。字段包含诉求编号、承办单位、诉求内容、办理状态、回访结果等，部分文档为结构化表单，部分为非结构化口语化文本。

## 这些特征在「向量模型与索引」这一环带来什么约束
每日更新的数据要求增量索引配置适配高频同步场景，避免全量重建带来的性能损耗。多类型文档的混合输入，要求向量模型与索引流程兼顾结构化字段的精准匹配与非结构化口语化文本的语义理解。分散的数据来源需要统一的预处理流程，确保不同来源的工单数据格式一致。同时，索引构建的稳定性直接影响工单办理效率，任何延迟或错误都可能导致工单超期或答复被退回。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配热线诉求的口语化文本长度，避免语义割裂 |
| 重叠长度 | 100–150 字符 | 保留跨分块的上下文关联，提升语义连贯性 |
| 相似度阈值 | 0.72–0.85 | 按实测标定，平衡召回准确率与召回覆盖范围 |
| 单次召回上限 | 前 10 条 | 控制单轮检索的计算量，适配热线工单的实时处理需求 |
| `defaultToken` | 10000 | 适配批量工单文档的总token上限，避免截断关键信息 |
| `maxToken` | 12000 | 匹配大模型的上下文窗口限制，确保完整语义输入 |

## 容易做错的三处
- 上传pdf格式的工单文档后，向量化任务耗时过长。原因是未针对短文本诉求优化分块策略，导致生成的分块数量超出预期。
- 导入十万条csv格式的工单数据后，向量化完成后仅显示九万条数据。原因是部分数据存在格式异常或空字段，未开启异常数据自动过滤配置。
- 创建集合显示创建成功，但页面上索引状态始终显示未建立。原因是容器环境与本地环境的向量模型依赖版本不一致，导致索引构建逻辑异常。

## 怎么确认配好了
- 上传单条典型的12345诉求文档，检查向量化耗时是否符合预设的性能预期。
- 导入固定规模的测试工单数据集，核对向量化完成后的数据条数与源数据完全一致。
- 发起针对特定诉求的检索请求，检查返回的索引结果与诉求内容的语义匹配度符合预设阈值。
- 在容器环境中运行批量向量化任务，确认结果与本地运行的一致性。
