# 信访事项办理的申报材料与案卷审核：工作流编排

## 这个品类的数据长什么样
本品类数据主要来自国家信访信息系统、地方信访系统、12345平台、基层治理平台及历史信访档案，更新频率为每日。日常涉及的文档包含信访登记表、受理告知书、转送交办函、办理意见书、复查复核申请、化解方案。数据主体为信访局、部门信访办、街道乡镇及责任单位办公室，文档结构围绕信访事项的受理、办理、复查复核全流程搭建，字段包含事项编号、诉求内容、办理主体、办理标识等。

## 这些特征在「工作流编排」这一环带来什么约束
数据来源的多样性要求工作流需配置多源数据同步节点，确保每日更新的信访数据完整接入。不同类型的信访文档结构差异较大，工作流需设置文档类型识别分支，匹配对应字段提取规则。信访事项办理的出错后果直接关联重复信访、越级信访或复查纠错，工作流需加入合规校验环节，对受理范围甄别、责任单位协调、办理意见形成等核心环节设置强制校验。同时，本品类需严格遵循法定办理程序，工作流节点需按流程顺序串联，不可随意调整节点顺序。

以下配置基于FastGPT v4.17.0版本。
## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 全局变量 | 存储信访事项编号、诉求内容、办理主体等核心字段 | 匹配信访文档的固定字段结构，便于跨节点调用 |
| 节点ID（`nodeId`） | 按节点功能命名，如「受理范围校验」「文档提取」 | 便于排查报错日志，快速定位异常环节 |
| 超时设置 | 600秒 | 适配信访数据同步与文档处理的常规耗时，避免长时间无响应 |
| 表单组件 | 配置事项编号、诉求描述、证明材料上传字段，单文件上限100 MB | 匹配信访申报的常规材料要求，避免超大文件阻塞流程 |
| 上下文窗口 | 前10条历史记录 | 适配信访事项办理的历史诉求与办理轨迹，避免上下文溢出 |
| 重试次数 | 2次 | 平衡接口调用成功率与处理耗时，避免重复触发导致的系统压力 |

## 容易做错的三处
- 工作流运行时出现gpt-4o-mini调用报错日志，未主动配置该模型调用。原因是工作流默认调用了未配置的模型节点，或未在`variables`配置中限制模型调用范围。
- 无法修改工作流中的全局变量历史记录。原因是未在`variables`配置中开启历史记录编辑权限，或跨节点变量传递未设置可修改属性。
- 无法提取信访事项中的证明材料文件。原因是表单组件未配置文件上传字段，或工作流节点未绑定文件提取逻辑，导致材料无法被正常识别与存储。

## 怎么确认配好了
- 检查工作流节点的`nodeId`命名，确认与配置项中的节点名称一致，可通过系统日志快速定位异常节点。
- 提交测试信访事项，确认全局变量中的核心字段可跨节点正常传递与修改。
- 上传测试信访证明材料，确认表单组件可正常接收并存储文件，无大小超限报错。
- 模拟超时场景，确认工作流在600秒内完成节点处理，超时后触发预设的重试逻辑。
