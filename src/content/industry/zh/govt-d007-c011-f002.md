# 养老、工伤、失业待遇核定的申报材料与案卷审核：向量模型与索引

## 这个品类的数据长什么样
本品类的核心数据来自社会保险经办系统、个人权益记录、劳动关系和工伤认定系统、电子社保卡平台四类渠道。日常处理的文档包括待遇申领表、缴费年限证明、退休审批表、工伤认定材料、失业保险金申领材料，各类文档包含参保年限、认定编号、申领人身份信息等固定字段。数据更新频率为每日，且需关联多系统的同步数据完成审核。

## 这些特征在「向量模型与索引」这一环带来什么约束
本品类的数据特征对向量模型与索引环节带来明确约束。多渠道来源的数据格式差异较大，需在切分前完成统一格式对齐，避免向量空间偏移。每日更新的全量数据量较大，需支持增量索引以降低处理耗时。文档包含的参保年限、认定编号等字段为审核核心依据，切分文档时需保留字段关联关系，避免核心信息被拆分破坏。同时，待遇核定的审核结果直接关联个人待遇支付，向量检索的准确性需严格匹配业务逻辑。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配社保类文档的字段长度与核心信息密度，避免单块包含过多无关内容 |
| 重叠长度 | 100–200 字符 | 保留相邻文档块的关联信息，避免缴费年限、认定编号等核心字段被拆分在不同块中 |
| maxToken | 4096 token | 匹配社保文档的平均内容长度，确保单块向量生成时完整覆盖核心信息 |
| defaultToken | 1024 token | 作为默认切分的基础单位，平衡向量生成的精度与处理效率 |
| 相似度阈值 | 按实测标定 | 适配社保审核的核心匹配逻辑，避免误判或漏判关键材料 |
| 单次搜索上限 | 前 5 条 | 控制返回结果的数量，聚焦最相关的申报材料与案卷内容 |

## 容易做错的三处
- 知识库中自定义切分的文档块重复后被自动删除，导致索引顺序与预期不符。原因是默认开启了文档去重配置，未针对社保申报材料多来源提交的场景关闭该开关。
- 配置自定义向量模型后，实际调用时仍使用大语言模型推理。原因是向量模型渠道未正确关联到知识库索引环节，仍绑定了默认的大语言模型接口。
- 知识库索引速度无法满足日更新需求。原因是未配置增量索引策略，每次索引均处理全量社保数据，未仅同步当日更新的内容。

## 怎么确认配好了
- 查看FastGPT v4.17.0的知识库设置页面，确认文档去重开关的状态与业务需求匹配。
- 上传单份社保申报文档，测试向量生成结果，确认返回的embedding数据格式符合预期。
- 模拟单次索引操作，验证索引完成的耗时与业务要求匹配。
- 调整相似度阈值后，输入审核相关问题，验证返回的搜索结果条数与相关性符合业务逻辑。
