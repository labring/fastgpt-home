# 养老服务机构监管的申报材料与案卷审核：向量模型与索引

## 这个品类的数据长什么样
通常服务于民政局养老服务科、街道乡镇及协同监管部门，日常处理的文档包含养老机构备案材料、运营补贴申请、服务质量检查表、安全隐患整改台账、老人入住档案等。数据主要来自养老服务信息平台、民政统计系统、消防检查记录与机构运营台账，更新频率为月度。文档兼具结构化表格与非结构化文本两类形式，字段包含机构名称、备案编号、床位数量、整改要求等，附带床位（张）、补贴金额（元）等单位标识。

## 这些特征在「向量模型与索引」这一环带来什么约束
养老服务监管数据的多来源、多格式特征，要求索引系统支持混合格式的文档解析与批量导入。月度更新的频率决定了需适配增量索引的配置，避免全量重建带来的资源消耗。结构化的床位、补贴等字段，要求索引保留元数据以区分字段属性，防止语义匹配时混淆不同类别的信息。十万级规模的csv台账数据，要求导入流程具备异常行过滤与断点续传能力，防止数据丢失。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配养老备案材料、整改台账等非结构化文档的语义完整性，避免分块过碎丢失跨段落的监管关联信息 |
| 重叠长度 | 100–150 字符 | 覆盖跨分块的关键内容，如安全隐患整改的跨页要求与机构备案的补充说明 |
| `maxToken` | 4096 token | 适配主流嵌入模型的输入长度限制，匹配养老文档分块后的平均语义量 |
| 相似度阈值 | 0.75–0.85 按实测标定 | 区分养老机构的有效匹配结果，避免误判相似的机构名称或床位数据 |
| 单次搜索上限 | 前 10 条 | 控制返回结果的数量，适配监管审核的批量核对需求 |
| `defaultToken` | 1024 token | 统一基础上下文的嵌入长度，保证不同文档的索引一致性 |

## 容易做错的三处
- 现象：导入十万条csv格式的机构运营台账后，索引完成后总条数少于源数据。原因：导入流程未配置格式异常行的跳过规则，部分包含空字段或特殊字符的台账行未被正确识别，导致索引时被自动过滤。
- 现象：向量化任务长时间处于索引中状态，无进度更新。原因：未配置合理的`defaultToken`长度，嵌入模型调用超时，且未开启批量导入的断点续传功能，导致任务中断后无法恢复。
- 现象：向量计算得分异常偏高且多条结果得分一致。原因：分块长度设置过大，导致多个不同文档的分块语义重叠度过高，匹配时无法区分不同机构的差异信息。

## 怎么确认配好了
- 随机抽取10条养老机构备案材料的分块，检查分块长度是否在预设的800–1200字符区间内，重叠部分是否覆盖备案编号、床位数量等关键监管字段。
- 导入100条测试用的机构床位数据csv文件，核对索引完成后的总条数与源数据一致，确认无异常数据过滤。
- 提交典型监管查询，如“核查某养老机构的安全隐患整改情况”，查看返回结果的相似度得分是否在预设的0.75–0.85区间内，无异常偏高的得分。
- 查看FastGPT v4.17.0的嵌入任务日志，确认未触发`maxToken`超限的报错提示，参数配置已生效。
