# 医保费用结算审核的申报材料与案卷审核：向量模型与索引
本页面基于FastGPT v4.17.0版本的向量模型与索引配置逻辑编写。

## 这个品类的数据长什么样
本品类数据来自全国医疗保障信息平台、医院HIS与医保接口、医保目录和编码库、异地就医结算平台。日常处理的文档包含医保结算清单、费用明细、病案首页、处方、拒付清单、结算对账单，数据按日更新。文档字段包含诊疗项目编码、药品耗材编码、费用明细、结算时间、参保人身份标识等，单笔结算数据关联多类业务单据，结构严谨且字段边界清晰。

## 这些特征在「向量模型与索引」这一环带来什么约束
数据按日更新的节奏要求索引支持定时同步或增量更新，避免全量重建带来的性能损耗。多类业务文档的混合输入，要求分块规则适配不同单据的结构，避免跨类型内容混淆。诊疗项目、药品耗材编码类字段与语义类内容并存，需要向量模型兼顾结构化编码匹配与自然语言语义理解，同时需确保`maxToken`设置匹配模型输入上限。单笔结算关联多类单据的特征，要求索引支持跨文档关联召回，确保审核依据完整。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配医保单据的单页文本长度，避免拆分破坏业务单据的语义完整性 |
| 重叠长度 | 100–200 字符 | 弥补长文本分块后的语义断层，确保关联字段的上下文不被截断 |
| 相似度阈值 | 按实测标定 | 需匹配医保审核的业务严谨性，避免误召回或漏召回 |
| 单次搜索上限 | 前 10 条 | 控制返回结果的规模，适配审核人员的查看效率 |
| maxToken | 4096 token | 适配主流向量模型的输入上限，确保完整加载审核所需的单据上下文 |
| defaultToken | 2048 token | 作为默认上下文窗口，平衡检索召回与推理效率 |

## 容易做错的三处
- 搜索测试时返回报错，提示索引匹配失败。原因是未将医保目录编码库的结构化数据同步至向量索引，仅同步了非编码类文本内容。
- 向量数据库中仅存储向量数据，无法直接关联原始单据内容。原因是未配置原始文档的存储路径与向量索引的关联映射，仅上传了向量化后的特征数据。
- 语义检索得分异常偏高，超出合理区间。原因是未对诊疗项目编码字段做单独的结构化处理，导致语义匹配被编码字段的强特征干扰。

## 怎么确认配好了
- 执行一次全量同步任务，检查同步日志中是否有医保单据类型的分类标记，确认分块规则适配了所有业务文档。
- 输入一条待审核的结算明细，核对检索返回的结果是否包含对应的处方、费用明细等关联单据，确认跨文档关联召回生效。
- 调整相似度阈值并执行多轮检索，观察返回结果的覆盖范围是否符合审核业务的严谨性要求，完成阈值标定。
- 检查向量数据库的存储配置，确认原始文档的存储路径与向量索引已建立关联映射，可通过向量ID回溯原始单据内容。
