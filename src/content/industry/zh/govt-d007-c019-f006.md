# 双随机、一公开监管检查的申报材料与案卷审核：引用来源与溯源

## 这个品类的数据长什么样
该品类数据主要来自“双随机、一公开”监管平台、企业信用信息公示系统、行业监管系统、执法人员名录库，更新频率为每月。日常文档包含抽查计划、检查对象名单、检查事项清单、现场检查记录、整改通知书、抽查结果公示，数据字段涵盖检查对象统一社会信用代码、执法人员编号、检查事项内容、整改完成情况、公示状态等，单条文档体量从数百字符到数千字符不等。

## 这些特征在「引用来源与溯源」这一环带来什么约束
数据来源分散，需配置多源数据的关联校验逻辑，确保引用的检查对象、执法人员等信息与外部系统数据一致。月度更新频率要求知识库定期同步全量数据，避免引用滞后的检查结果或对象信息。多类型文档且字段差异大，需针对抽查计划、现场记录、公示结果等不同文档配置差异化的召回规则。单条文档体量跨度大，需控制单条引用的token消耗，避免上下文溢出。核心的抽查结果公示环节，需确保引用的检查记录与公示信息完全匹配，满足监管溯源的合规要求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | 该品类单条文档体量跨度大，需控制单条引用的token消耗，避免上下文溢出 |
| `responseData` | 仅返回检查对象、执法人员、检查结果字段 | 该品类业务核心字段明确，减少冗余信息干扰，聚焦监管溯源所需的核心数据 |
| `detail` | 开启 | 需展示引用文档的原始来源标识，确保溯源可查 |
| 单次搜索上限 | 前5条 | 该品类检查对象与检查事项数量较多，控制召回条数避免上下文过载 |
| 知识库更新频率 | 每月 | 匹配业务数据月度更新的节奏，确保引用数据的时效性 |
| 最大上下文 | 4000 token | 适配多类型文档的总上下文拼接，符合FastGPT v4.17.0的模型上下文窗口限制 |

## 容易做错的三处
- 现象：知识库引用结果条数与配置的单次搜索上限不符，返回过多或过少的文档。原因：未结合该品类检查对象与检查事项的实际数量调整配置，导致召回逻辑不符合业务需求。
- 现象：引用的文档字段缺失或包含无关内容。原因：未正确配置`responseData`的返回字段，遗漏了监管溯源所需的检查对象统一社会信用代码等核心字段，或返回了非业务相关的冗余字段。
- 现象：文本提取组件无法从知识库引用中提取有效内容。原因：未开启`detail`配置，未启用原始来源标识或核心字段的返回，导致提取组件无法获取引用文档的有效信息。

## 怎么确认配好了
- 发起抽查计划审核场景的测试，查看引用结果的来源标识，确认是否显示原始文档的来源平台与更新时间。
- 调整单次搜索上限的配置，发起测试请求，确认返回的引用条数符合预设的前5条要求。
- 查看`quoteMaxToken`的配置，检查单条引用的token消耗，确认未超出FastGPT v4.17.0的模型上下文窗口限制。
- 触发知识库更新任务，确认更新频率匹配每月的配置要求，确保引用数据与业务系统的更新节奏一致。
