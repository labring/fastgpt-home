# 双随机、一公开监管检查的申报材料与案卷审核：部署与升级

## 这个品类的数据长什么样
该品类的日常文档包含抽查计划、检查对象名单、检查事项清单、现场检查记录、整改通知书、抽查结果公示。数据来源为“双随机、一公开”监管平台、企业信用信息公示系统、行业监管系统、执法人员名录库，更新频率为月度。核心数据围绕抽查任务与执法流程生成，需关联执法人员与监管对象信息，确保数据的关联性与时效性，日常维护需覆盖多类文档的同步与校验。

## 这些特征在「部署与升级」这一环带来什么约束
月度更新频率要求配置定时同步任务，适配多源监管数据的拉取节奏。多类型文档的解析需求，要求系统支持不同字段的提取规则配置，适配抽查计划、现场记录等不同格式的文档。执法人员与监管对象的关联数据，需要稳定的存储与查询能力，因此需配置合适的数据库连接参数。升级过程中需保留已有的抽查计划与检查结果数据，避免重复导入或数据丢失，需配置数据备份与增量同步逻辑。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://admin:123456@localhost:27017/regulatory?authSource=admin` | 存储执法人员名录库与检查对象库，支持关联查询，适配月度数据更新的存储需求 |
| `REDIS_URL` | `redis://:6379pass@127.0.0.1:6379/1` | 缓存月度同步的抽查计划数据，降低外部监管平台的接口调用频率 |
| `STORAGE_S3_ENDPOINT` | `https://s3-cn-south-1.tencentcloudapi.com` | 存储现场检查记录的视频、图片附件，匹配监管文档的附件存储规范 |
| `DB_MAX_LINK` | `15 个连接` | 限制数据库连接数，避免月度同步任务占用过多系统资源 |
| 定时同步周期 | `720 小时` | 匹配月度数据更新频率，平衡数据时效性与接口调用压力 |

## 容易做错的三处
- 现象：创建系统插件时，系统提示无法找到packages/plugins/register目录。原因：Docker部署时未将本地插件目录挂载到容器内的指定路径，导致插件注册文件缺失。
- 现象：本地部署的工作流配置界面中，添加超过10个节点后，输入文字出现明显延迟。原因：前端未启用节点懒加载，大量节点同时渲染占用浏览器内存与计算资源。
- 现象：导入抽查结果公示文档后，公示日期字段无法被正确提取。原因：未针对该文档类型配置专属的字段提取规则，导致解析引擎无法识别目标字段格式。

## 怎么确认配好了
- 执行数据库连接测试命令，验证`MONGODB_URI`与`REDIS_URL`的配置是否生效，查看系统日志无连接报错。
- 上传一份标准格式的抽查计划文档，触发解析任务，检查解析结果是否包含检查对象、检查事项等核心字段。
- 手动触发一次定时同步任务，查看数据源数据是否成功同步到系统内，无重复或遗漏条目。
- 访问FastGPT v4.17.0的系统插件管理页面，确认已加载的插件列表中包含监管数据同步相关插件。
