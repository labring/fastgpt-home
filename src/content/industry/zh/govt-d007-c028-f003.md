# 市场主体登记与许可的申报材料与案卷审核：多轮对话与提示词

## 这个品类的数据长什么样
本品类的日常文档包含设立登记申请书、公司章程、股东决议、住所证明、营业执照、食品经营许可申请等。数据来源为企业登记全程电子化系统、国家企业信用信息公示系统、电子营业执照系统与住所信息库，每日更新。文档结构多为固定格式表单与结构化附件，字段包含统一社会信用代码、住所地址、股东身份信息、许可前置后置条件等，无大量自定义非标准字段，单位多为地址字符、人数、经营范围文本。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
固定格式的申报文档要求提示词需严格匹配表单预设字段，避免提取非预期的冗余内容。每日更新的多源数据要求对话上下文需实时拉取最新公示信息，避免使用过期的主体资格或住所数据。多轮交互需覆盖补正、变更、注销等场景，需通过`messages`参数保留完整历史交互记录，确保上下文延续。标准化的字段结构要求变量引用需精准绑定对应表单项，避免参数错位导致的审核错误。同时，需限制单次对话的字段提取数量，匹配窗口人员的核验节奏。

## 配置怎么定
本配置说明基于FastGPT v4.17.0版本的界面逻辑。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 上下文窗口长度 | 前 800–1200 字符 | 匹配申报表单的单页标准长度，避免截断核心字段 |
| `variables` 绑定规则 | 按表单字段顺序绑定 | 匹配固定格式文档的字段排列，确保变量引用精准对应申报项 |
| `messages` 上下文整理规则 | 仅保留近3轮交互与核心文档片段 | 减少冗余上下文占用，提升审核响应速度 |
| 多轮交互轮次上限 | 前 5 轮 | 匹配单次审核的补正交互场景，避免过长上下文干扰审核逻辑 |
| `chatId` 关联配置 | 绑定单次审核任务ID | 确保对话日志与对应案卷数据的关联，便于后续溯源 |
| 提示词触发节奏 | 按单次表单提交触发 | 匹配窗口人员的分步核验节奏，避免一次性推送过多信息 |

## 容易做错的三处
- 现象为变量引用配置后，温度设置按钮消失，无法调整生成参数。原因是部分版本的变量绑定逻辑会隐藏非核心配置项，未预留温度参数的触发入口。
- 现象为调用工作流后，对话日志中的运行数据字段为空。原因是未通过`chatId`绑定任务上下文，导致工作流返回数据未关联到对应对话记录。
- 现象为向“文本内容提取”模块的提示词中传入代码块参数时，完整响应显示该代码块为未定义。原因是未通过`variables`参数提前声明代码块变量的格式，导致提取模块无法识别传入内容。

## 怎么确认配好了
- 发起一次模拟申报交互，核对绑定的变量是否与申报表单的字段一一对应。
- 查看对话日志，确认`chatId`关联的案卷数据是否同步出现在日志中。
- 触发两次补正交互，检查上下文是否保留前一轮的交互内容与文档信息。
- 调整提示词模板内容，确认更新后的规则在下次交互中正常生效。
