# 特种设备安全监管的申报材料与案卷审核：多轮对话与提示词

## 这个品类的数据长什么样
数据来自特种设备安全监察系统、检验检测机构系统、使用单位台账、作业人员证书库，更新频率为月。日常审核文档包含使用登记证、定期检验报告、维保记录、隐患整改通知书、事故报告、作业人员证书，各文档对应设备编号、检验周期、维保单位、作业人员资质编号等字段，无统一跨系统字段格式，单份案卷材料通常包含3至5类不同文档。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源分散且无统一格式，要求多轮对话需关联不同数据源的上下文以完成跨文档核对；月更的数据源要求提示词需定期校准数据时效性规则；多类文档的字段差异要求多轮对话需引导用户明确文档类型，提示词需指定字段匹配逻辑；最耗时的核对环节需留存前期核验的关键信息，避免重复输入。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 与案卷唯一编号绑定 | 案卷为独立审核单元，绑定后可留存同案卷的全流程多轮对话上下文，避免跨案卷数据混淆 |
| `messages` | 保留最近15–20条对话 | 特种设备审核需多轮核对设备信息、资质文件，该区间可覆盖前期核验的关键信息，按实测标定 |
| `variables` | 预设设备类型、检验周期字段 | 可自动关联系统内的设备台账数据，减少人工输入的重复环节 |
| 最大上下文长度 | 800–1200 字符 | 单案卷核心审核材料的信息密度集中在该区间，避免过长上下文导致模型偏离审核目标 |
| 历史文档召回上限 | 前5条 | 仅召回当前审核批次的关联材料，避免无关历史数据干扰当前核验 |

## 容易做错的三处
- 现象：本地化部署后无法按案卷维度清除对话历史，出现冗余数据。原因：未配置按案卷绑定`chatId`的规则，误将全局对话作为清理单元。
- 现象：模型输出的检验周期校验结果与台账不符，出现错误匹配。原因：未在提示词中限定仅使用`variables`预设的设备字段，引入了无关的历史数据。
- 现象：多轮对话中前期输入的作业人员证书编号无法复用，需要重复输入。原因：未保留足够的`messages`上下文，导致关键信息丢失。

## 怎么确认配好了
本核对流程基于FastGPT v4.17.0版本的功能逻辑。
- 发起单案卷的多轮对话，核对前期输入的设备编号是否在后续步骤中被自动复用。
- 检查`chatId`配置，确认与案卷唯一编号绑定，避免跨案卷上下文混淆。
- 查看上下文长度设置，确认未超过预设的最大上下文区间，无负载过高提示。
- 测试清除对话操作，确认仅当前会话的`messages`上下文被清理，不影响其他案卷。
