# 防汛防灾与应急值守的申报材料与案卷审核：引用来源与溯源

## 这个品类的数据长什么样
该品类的数据通常来自气象预警系统、水文监测系统、应急指挥平台、基层报灾系统与视频监控，更新频率为每日。日常处理的文档包含值班记录、预警通知、会商纪要、灾情速报、应急处置方案、物资调拨单，数据字段多包含雨情水情数值、转移避险人数、物资品类与库存数量等具体业务参数，部分文档为结构化表单，部分为半结构化文本，无统一固定格式。

## 这些特征在「引用来源与溯源」这一环带来什么约束
多源异构的数据来源要求溯源环节兼容不同格式的数据源接入，确保气象、水文、基层报灾等数据均可被精准关联。每日更新的频率要求索引构建与更新周期适配业务节奏，避免数据滞后于实时处置需求。半结构化与结构化混合的文档结构，需要灵活调整引用片段的提取规则，确保不同类型文档的原文片段均可被准确溯源。业务字段的特殊性要求溯源结果需匹配雨情、物资、人员等专属参数，避免泛化引用导致的信息偏差。

## 配置怎么定
以下配置基于 FastGPT v4.17.0 版本。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配会商纪要、灾情速报等文档的段落长度 |
| 重叠长度 | 100–200 字符 | 确保跨段落的业务逻辑不被拆分 |
| 单次搜索上限 | 前 8 条 | 匹配多源数据的召回需求，避免上下文溢出 |
| `quoteMaxToken` | 1500 token | 保留完整的物资调拨单或雨情数据原文片段 |
| `responseData` | 开启 | 直接返回数据库或知识库的原文片段用于溯源 |
| `detail` | 开启 | 展示数据源的具体来源路径与采集时间 |

## 容易做错的三处
- 现象：搜索返回的原文片段仅显示零散短句，无法覆盖完整的灾情速报或物资调拨单内容。原因：`quoteMaxToken` 取值过小，无法覆盖完整的业务文档段落。
- 现象：通过 Function CALL 调用 MySQL 数据后，大模型回答未附带数据库原文片段。原因：未开启 `responseData` 配置项，未启用原文返回功能。
- 现象：搜索召回的结果条数远超预设值，导致大模型上下文溢出。原因：单次搜索上限设置过高，未适配应急数据的实时性召回需求。

## 怎么确认配好了
- 上传一份典型的物资调拨单或雨情速报文档，触发知识库搜索，查看返回结果中是否包含完整的原文片段。
- 查看搜索结果的溯源栏，确认是否标注了数据来源的系统名称与采集时间。
- 调整单次搜索上限后，验证召回结果的条数是否符合预期设置。
- 检查配置页面中 `detail` 选项是否处于开启状态，确保溯源信息完整展示。
