# 医药流通的申报材料与案卷审核：向量模型与索引

## 这个品类的数据长什么样
医药流通的申报材料与案卷审核数据主要来源于药品经营资质申报文件、冷链运输全程案卷、药品流通台账、供应商资质证明四类来源。资质类文件按年度更新，台账与运输案卷随每批次流通业务实时更新。文档包含结构化字段与非结构化扫描件两类结构，结构化字段包含企业名称、国药准字编号、药品通用名、运输温度、审批文号等，非结构化内容多为多页PDF格式的审批报告与现场检查记录。

## 这些特征在「向量模型与索引」这一环带来什么约束
资质类文件的年度更新要求支持增量索引，避免全量重建带来的资源消耗。实时更新的台账与案卷则需要低延迟的索引同步能力。多页PDF的非结构化内容需保证分块后保留上下游业务关联，否则会影响语义匹配准确性。结构化字段中的国药准字编号等精准编码，需要向量模型同时兼顾语义匹配与精准字段匹配的能力，避免合规审核中的误判。同时，不同批次的台账数据格式相对统一，可通过固定字段的向量嵌入提升检索效率。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 医药流通申报材料多包含长段审批说明与台账记录，该长度可覆盖完整业务语义单元 |
| 重叠长度 | 100–200 字符 | 避免长文本分块后丢失上下游业务关联，适配案卷的连续审批流程 |
| 相似度阈值 | 0.75–0.85 | 区分资质类精准匹配与业务描述的语义匹配，适配医药流通的合规审核要求 |
| maxToken | 8192 token | 适配医药流通申报材料中批量批次号与温度记录的长文本输入 |
| defaultToken | 按实测标定 | 适配不同批次的资质文件与台账数据的语义一致性校验 |
| 单次搜索上限 | 前10条 | 覆盖多案卷的关联审核需求，避免遗漏跨批次的交叉合规信息 |

## 容易做错的三处
- 调用pushdata API的chunk模式上传后，界面长期显示「索引中」状态无更新。原因：分块长度设置过大，超出模型支持的maxToken限制，导致索引任务堆积无法完成。
- 接口返回「该令牌无权使用模型：text-embedding-3-large」的报错。原因：未正确配置defaultToken，或绑定的模型未在当前账号下开通对应权限。
- 无法接入指定的embedding模型（如bce-embedding-v1）。原因：未在系统设置中切换至非one API的模型调用路径，未正确填写模型接入地址与密钥。

## 怎么确认配好了
- 上传单份典型医药流通申报材料，查看索引完成耗时无异常堆积，符合业务预期。
- 测试嵌入指定的embedding模型，验证返回的向量数据格式符合FastGPT v4.17.0的标准要求。
- 检索已索引的案卷数据，确认返回结果的相似度处于预设阈值区间内。
- 检查defaultToken与maxToken的配置参数，与当前使用的embedding模型官方文档匹配。
