# 城市公交的申报材料与案卷审核：向量模型与索引

## 这个品类的数据长什么样
数据来源为城市公交企业的运营申报单、线路调整案卷、合规检查案卷，包含线路编号、运营里程、驾驶员资质编号、车辆载客量等结构化字段，单位涵盖公里、人次、年等。文档包含结构化表单与扫描件附件，更新节奏按申报批次推进，单次申报材料的篇幅从数行到数十页不等，每月有批量归档的合规案卷更新。

## 这些特征在「向量模型与索引」这一环带来什么约束
城市公交的申报数据兼具结构化字段与非结构化附件，要求向量模型同时适配短文本表单与长文本扫描件转写内容；按批次更新的数据需要索引支持增量同步，避免全量重建的资源消耗；不同案卷的长度差异较大，分块策略需兼顾短文本的完整性与长文本的语义连贯性；部分关联辅助数据（如过往驾驶员资质记录）需纳入索引范围，否则无法完成跨案卷的关联审核。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配城市公交申报材料的常见段落长度，符合FastGPT v4.17.0版本的分块逻辑 |
| 重叠长度 | 100–150 字符 | 避免跨块的案卷内容丢失语义关联，适配长附件的段落衔接 |
| `defaultToken` | 4096 | 适配多数单份申报案卷的总文本token上限，满足基础审核需求 |
| 相似度阈值 | 0.72–0.78 | 区分合规申报与不合格材料的语义边界，适配案卷审核的精准度要求 |
| 单次搜索上限 | 前 8 条 | 控制检索结果的信息量，避免超出审核人员的处理范围 |
| `maxToken` | 16384 | 容纳批量申报材料的总向量数据，适配服务器端的存储容量 |

## 容易做错的三处
- 现象：检索时无法召回关联的历史资质案卷，日志中无对应向量记录，原因：未将辅助数据（如过往驾驶员的申报记录）纳入向量索引范围。
- 现象：单条申报案卷生成多条独立检索结果，审核时出现重复匹配，原因：未正确配置分块重叠参数，导致单条数据生成多组向量后未绑定统一关联标识。
- 现象：上传本地向量化的案卷数据后，服务器端检索无匹配结果，原因：本地与服务器端使用了不同的向量模型，嵌入维度不匹配导致向量空间不一致。

## 怎么确认配好了
- 上传单份典型的线路调整案卷，查看向量生成日志，确认分块长度与预设参数一致。
- 导入一份关联的历史资质数据，执行关键词检索，确认关联案卷能被正常召回。
- 切换预设的向量模型，测试相似度计算结果是否符合预设的阈值区间。
- 批量导入一周内的申报数据，检查索引更新日志，确认无报错且数据同步完成。
