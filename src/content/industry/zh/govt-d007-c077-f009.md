# 城市公交的申报材料与案卷审核：模型接入与配置

## 这个品类的数据长什么样
城市公交的申报材料与案卷审核数据主要来自线路运营申报文档与日常运营案卷两类渠道。线路申报材料包括线路调整申请、票价核定报告、安全评估书等，多为结构化表格与PDF扫描附件混合；日常案卷包含乘客投诉工单、车辆故障记录、场站使用审批单等，以结构化文本为主。数据更新频率为：申报材料按单次业务周期更新，案卷数据每日同步。字段包含线路编号、运营时段、核定载客量（单位：人次）、线路长度（单位：千米）等标准化内容，部分材料附带手写批注或盖章的扫描件。

## 这些特征在「模型接入与配置」这一环带来什么约束
结构化与非结构化混合的数据特征，要求模型同时支持字段提取与通用文本理解能力，因此接入时需兼顾标准化字段解析与复杂场景理解。每日同步的案卷数据要求配置的上下文更新节奏匹配业务周期，避免延迟导致审核滞后。标准化字段的格式要求需严格对齐数据源，否则会引发模型输出的审核结论与实际业务规则不符。申报材料中的PDF扫描附件需配置视觉识别能力，以解析手写批注、盖章等非标准视觉元素。

## 配置怎么定
本文基于FastGPT v4.17.0版本的配置逻辑，以下配置项针对城市公交申报材料与案卷审核场景优化：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配城市公交申报材料与案卷的平均文本长度，避免上下文截断导致审核信息缺失 |
| `maxTokens` | 2000 token | 控制单轮审核输出的长度，确保审批意见清晰完整，符合内部文档规范 |
| `quoteMaxToken` | 1500 token | 保留足够的原文引用片段，用于支撑审核结论的依据说明 |
| `vision` | 开启 | 用于解析申报材料中的PDF扫描件、盖章文件等视觉类附件 |
| `temperature` | 0.2–0.4 | 降低随机输出，确保审核结论的严谨性，符合政务审批的标准化要求 |
| `AIPROXY_API_ENDPOINT` | 按部署节点填写专属地址 | 适配本地或私有云部署的网络访问规则，确保数据传输安全 |
| `AIPROXY_API_TOKEN` | 填写专属鉴权密钥 | 确保模型调用的权限合法性，避免未授权访问 |

## 容易做错的三处
- 现象：运行代码后生成的审核结果无法传入模型上下文，界面出现`chat:ai_input_is_e`类报错日志。原因：未将代码执行结果以指定的上下文变量格式注入模型输入队列，导致模型无法获取外部计算数据。
- 现象：本地部署Ollama模型后，通过Docker Compose部署的FastGPT无法调用该模型，返回连接超时错误。原因：未正确配置容器网络互通规则，导致FastGPT容器无法访问本地Ollama服务的监听端口。
- 现象：模型输出的审核意见与预设审批规则不符，调整通用提示词后无明显改善。原因：提示词未绑定城市公交审批的专属场景，未明确限定输出格式与审核维度，导致模型输出泛化内容。

## 怎么确认配好了
- 上传一份城市公交线路调整申报的PDF附件，验证模型是否能正确提取线路编号、运营时段等核心字段。
- 触发一次日常案卷审核流程，检查模型输出的审核意见是否包含原文引用片段，且未出现上下文截断。
- 查看模型调用日志，确认`AIPROXY_API_ENDPOINT`与`AIPROXY_API_TOKEN`的配置值与部署环境匹配，无连接错误。
- 调整`temperature`参数值，验证模型输出的严谨性是否符合预期，确保无过度发散的内容。
