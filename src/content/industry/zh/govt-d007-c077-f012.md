# 城市公交的申报材料与案卷审核：部署与升级

## 这个品类的数据长什么样
城市公交的申报材料与案卷审核数据，主要来自公交运营主体的内部审批系统、政务申报平台上传的电子文件。更新节奏随申报批次变动，单次申报周期内集中提交，日常案卷按周归档。单份文档多为PDF或Word格式，包含申报主体名称、项目类型、提交日期、审批状态、案卷编号、关联附件等字段，附件多为线路走向图、场站规划书等，单位多为字符、MB、日期格式。

## 这些特征在「部署与升级」这一环带来什么约束
该品类数据多为非结构化办公文档，需适配PDF、Word等多格式解析，部署时需配套对应格式解析组件。集中提交的申报批次会产生批量数据请求，需调整数据库连接上限以避免连接耗尽。案卷编号作为唯一标识字段，需配置数据库索引提升检索效率。政务类材料涉及合规存储需求，需确认数据持久化配置符合公共服务数据管理规范。批量文档的向量检索需求，也会影响向量数据库的选型与资源配置。

## 配置怎么定
仅作参考；请以目标 FastGPT 发布版本与部署文档核验。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `50–80 个连接` | 应对集中提交的批量数据请求，避免数据库连接耗尽 |
| `MONGODB_URI` | `mongodb://mongo:27017/fastgpt_bus_audit` | 单独创建数据库实例存储案卷元数据，隔离业务数据 |
| `PG_URL` | `postgresql://pguser:securepass@pg:5432/bus_vector` | 存储案卷的向量检索数据，与其他业务库分离 |
| `REDIS_URL` | `redis://redis:6379/1` | 缓存高频访问的案卷元数据，降低数据库查询压力 |
| `FILE_TOKEN_KEY` | `随机生成的32位字符串` | 保障申报附件的上传下载安全，符合公共服务数据安全要求 |
| `STORAGE_S3_ENDPOINT` | `http://192.168.1.100:9000` | 存储申报材料的附件文件，适配公共服务场景的数据合规存储要求 |

## 容易做错的三处
- 现象：启动容器后出现`MongoDB connection refused`报错，无法加载案卷元数据。原因：未按照`MONGODB_URI`的配置启动对应数据库容器，或连接参数格式错误。
- 现象：批量上传申报材料时，文件解析失败率偏高，部分附件无法提取文本内容。原因：未配套适配PDF、Word的格式解析组件，仅使用默认基础解析能力。
- 现象：从PG版本迁移至Milvus版本后，原有案卷向量数据无法读取。原因：未提前导出PG中存储的向量数据，或未配置正确的向量数据库连接地址。

## 怎么确认配好了
- 执行`docker ps`命令，确认MongoDB、PostgreSQL、Redis等依赖容器均处于运行状态。
- 上传一份测试用的公交线路调整申报PDF，查看文件解析结果是否包含申报主体、项目类型等关键字段。
- 发起一次模拟批量申报请求，查看数据库连接数未超过`DB_MAX_LINK`的配置值。
- 调用向量检索接口，传入测试案卷的关键词，确认返回结果条数符合预期配置。
