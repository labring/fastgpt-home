# 城投平台的申报材料与案卷审核：工作流编排

## 这个品类的数据长什么样
城投平台的申报材料与案卷审核数据主要来源于内部项目申报系统、档案管理平台及外部资质核验接口。数据更新节奏分为两类：项目申报阶段为批量上传触发，日常案卷归档为按月定期同步。单份文档结构包含申报书、资质扫描件、财务报表、审批流转单四类内容，核心字段包括项目编号、申报主体、申报金额（单位：万元）、审批状态、提交时间（格式：YYYY-MM-DD），单份附件文件大小通常在100 MB以内。

## 这些特征在「工作流编排」这一环带来什么约束
数据来源分散要求工作流需配置多源数据拉取节点，整合不同系统的申报材料与案卷信息；文档结构复杂且包含长文本附件，要求工作流适配分段解析与附件提取能力；核心字段存在固定单位与格式要求，需在工作流中加入字段校验环节，避免格式错误进入审核流程；批量申报与归档的更新节奏，要求工作流支持定时触发或事件触发模式，适配不同业务场景的执行时机。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配城投申报材料的单段文本长度，避免上下文窗口溢出 |
| 单次提问上限 | 前3条候选案卷 | 匹配城投单批次申报的常规案卷数量，减少冗余计算开销 |
| 上下文窗口 | 16000 token | 容纳完整的申报材料与审批流转全流程文本 |
| 变量作用域 | 用户级 | 对应不同申报专员的专属任务变量，避免全局变量冲突 |
| 节点超时时间 | 600 秒 | 适配大型案卷的解析与审核时长，防止任务中途中断 |
| 输出节点筛选 | 按`nodeId`指定 | 仅将目标AI对话节点的回复同步至聊天窗口，隐藏冗余节点输出 |

## 容易做错的三处
- 现象：工作流中多个AI对话节点的回复全部出现在最终聊天界面，无法隐藏指定节点的输出。原因：未通过`nodeId`配置输出筛选规则，所有节点的上下文均被同步至聊天窗口。
- 现象：每次仅能发起一次问题分类提问，无法实现多轮反问与追问。原因：工作流未设置循环触发节点，仅执行单次AI调用，未保留对话上下文。
- 现象：不同申报专员的任务变量出现覆盖，导致申报数据混淆。原因：未将`variables`的作用域设置为用户级，使用了全局变量配置。

## 怎么确认配好了
- 发起一次模拟申报任务，提交包含多份案卷的测试数据，检查聊天界面仅显示目标AI对话节点的回复内容。
- 切换不同的测试用户身份，提交相同名称的任务变量，确认各自的变量配置互不干扰，未出现数据覆盖。
- 上传单份10000字符的申报材料，检查工作流能正常完成分块解析与审核流程，无超时报错。
- 查看工作流节点日志，确认所有配置项的取值与预设一致，无异常参数触发。
