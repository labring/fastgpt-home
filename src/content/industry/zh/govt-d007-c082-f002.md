# 基础电信运营的申报材料与案卷审核：向量模型与索引
本文基于FastGPT v4.17.0版本编写，聚焦基础电信运营领域的申报材料与案卷审核场景，梳理向量模型与索引环节的落地配置、参数与失败处理细节。

## 这个品类的数据长什么样
基础电信运营的申报材料与案卷审核数据，主要来源于内部业务支撑系统、档案管理系统与OA办公平台。数据更新节奏随业务流程变动，日常随单份申报或案卷提交实时更新，每月会有批量归档的历史案卷导入。文档以结构化与半结构化混合为主，包含申报主体信息、业务参数、审批节点记录、转写附件文本等内容，字段涵盖申报编号、业务类型、办理时限、审核意见等，涉及通信专业单位如MHz、基站数量、用户规模、时长等。

## 这些特征在「向量模型与索引」这一环带来什么约束
混合结构的文档要求分块环节区分结构化字段与文本内容，避免字段值被错误嵌入向量语义，影响后续匹配精度。实时更新的申报材料需要索引支持增量更新，避免每次导入都执行全量重建，降低处理效率。包含通信专业术语的内容，要求向量模型适配行业语义，避免出现语义混淆的匹配结果。单份案卷包含多页转写文本的特征，需要合理控制分块长度，保证上下文语义的完整性，避免出现内容断裂。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 基础电信申报材料的单段业务描述长度集中，避免分块过短导致语义割裂或过长导致向量精度下降 |
| 重叠长度 | 100–150 字符 | 跨分块的审批节点记录需要保留上下文关联，保证审核逻辑的连贯性 |
| 相似度阈值 | 0.72–0.85 | 需要区分相似的申报编号与业务类型，避免误匹配相似但场景不同的案卷 |
| 单次搜索上限 | 前 10 条 | 案卷审核仅需参考相近的典型历史案例，过多结果会增加审核人员的筛选负担 |
| `defaultToken` | 2000 | 申报材料的上下文总长度通常在该区间内，保证完整加载审核所需的关联内容 |
| `maxToken` | 4000 | 单次审核请求的总token上限，避免超出模型的承载范围 |

## 容易做错的三处
- 现象：导入申报材料后，自动生成的向量块包含冗余的审批节点日志，包含核心业务描述之外的非必要内容。原因：未配置分块过滤规则，直接对全文档内容进行分块，未保留用户需要的核心审核内容。
- 现象：批量导入历史案卷时出现超时报错，导入进度停滞。原因：未开启增量索引模式，每次导入都执行全量重建，超出`defaultToken`的单次处理上限，导致系统超时。
- 现象：相似度匹配结果出现大量高度相似的同类型申报记录，无法区分具体业务场景。原因：相似度阈值设置过低，无法精准匹配业务差异较大的案卷内容。

## 怎么确认配好了
- 上传单份典型的基站建设申报材料，查看分块预览界面，确认分块长度符合预设区间，核心业务参数与审批意见未被割裂。
- 执行少量历史案卷的批量导入测试，查看系统日志，确认无超时报错，增量索引模式正常触发。
- 输入模拟的审核查询问题，查看召回结果条数，确认符合单次搜索上限的配置要求。
- 查看系统存储监控面板，确认向量存储占用量符合预设的资源规划范围，未出现异常增长。
