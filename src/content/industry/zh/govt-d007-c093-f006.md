# 政企信息化服务的申报材料与案卷审核：引用来源与溯源

## 这个品类的数据长什么样
政企信息化服务的申报材料与案卷审核数据，来源为国央企、政府部门的项目申报文档、审批案卷及配套附件。更新节奏为申报提交、审批节点触发更新，以及归档后定期同步。文档结构以结构化表单字段为主，搭配PDF、Word格式的附件文本为辅，字段包含申报主体、项目编号、提交时间、审核状态、附件内容等，单位涵盖字符、字节、ISO时间戳等，单份文档长度跨度较大。

## 这些特征在「引用来源与溯源」这一环带来什么约束
申报材料与案卷的结构化字段与附件文本关联紧密，引用溯源需精准匹配到具体字段及对应附件的具体段落，确保审核依据准确。文档更新依赖节点触发，需确保索引更新与审批流程同步，避免引用旧版数据。单份文档长度跨度大，需合理划分分块策略，避免丢失关键审核节点的信息。政企数据的合规性要求高，溯源信息需完整保留原始来源的标识，确保可追溯到具体提交的案卷条目。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `quoteMaxToken` | 2000–3000 token | 政企申报材料单份案卷内容较长，需保留足够上下文用于精准溯源 |
| `responseData` | 开启 | 需返回原始引用源数据，确保关联申报材料的具体字段与附件内容 |
| `detail` | 完整 | 需返回完整的溯源信息，包括案卷编号、提交时间等关键标识 |
| 单次搜索上限 | 前5条 | 政企申报案卷的相关条目集中在前5条，过多会增加系统延迟 |
| 分块长度 | 1000–1500 字符 | 覆盖核心审核节点内容，避免跨块丢失关键关联信息 |
| 重叠长度 | 100–200 字符 | 保留分块间的上下文关联，防止关键审核逻辑的连续性 |

## 容易做错的三处
- 现象：配置`quoteMaxToken`后，系统进程卡滞无响应，日志显示超时错误。原因：设置的token值超出当前部署的资源上限，或单次搜索上限取值过高。
- 现象：工作流代码运行节点中，无法选中知识库引用的变量，无法输出第一条搜索结果。原因：未开启`responseData`配置，或分块长度设置不符合文档结构。
- 现象：生成的审核答复未关联原始申报材料的内容，出现无关内容。原因：未将`detail`配置设为完整，仅返回摘要信息，无法溯源到具体案卷字段。

## 怎么确认配好了
- 进入FastGPT v4.17.0的知识库配置页面，检查`quoteMaxToken`的取值是否符合当前部署的资源允许范围。
- 提交一份测试申报材料，触发审核流程，查看返回结果中是否包含原始案卷的具体字段和附件路径。
- 查看工作流节点的变量列表，确认知识库引用的变量是否可被选中。
- 核对返回结果中是否包含`responseData`返回的原始源数据，确保溯源信息完整。
