# 煤炭运销的申报材料与案卷审核：引用来源与溯源

## 这个品类的数据长什么样
煤炭运销的申报与案卷审核数据，主要来源于业务系统的运销计划、过磅凭证、购销合同、完税发票，以及内部合规手册、过往审核案卷等文档。数据更新随业务批次触发，单次业务数据更新间隔从数小时到1天不等。文档以结构化表格和半结构化文本为主，包含煤种、运输吨位、结算金额、审核节点、经办人等字段，单位涉及吨、车次、元/吨等。

## 这些特征在「引用来源与溯源」这一环带来什么约束
煤炭运销的业务数据以结构化单据和半结构化文本为主，且需精准关联单据编号、煤种等核心字段，因此引用溯源时需保留文档的原始标识信息，避免分块破坏字段关联性。业务数据随批次更新，若知识库未同步最新单据，将导致溯源内容与当前业务脱节。单次审核涉及的案卷可能包含多份跨周期文档，需确保召回的来源能对应到具体业务环节，避免无关内容干扰审核判断。

## 配置怎么定
本配置基于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配煤炭运销单据的半结构化段落长度，保留煤种、吨位等核心字段的关联性 |
| 重叠长度 | 100–150 字符 | 避免跨分块的单据编号、审核节点等字段被拆分，确保溯源上下文完整 |
| `quoteMaxToken` | 前 2000 token | 限制引用的原文长度，避免审核时被冗余内容淹没，适配单批次案卷的内容规模 |
| 最大上下文 | 6000–8000 字符 | 承载多份跨周期单据的关联信息，满足全流程审核的溯源需求 |
| `detail` | 开启 | 强制返回引用来源的原始字段，如单据编号、过磅日期，便于审核人员快速核对 |
| `responseData` | 仅返回匹配文档 | 过滤无关内容，确保召回的来源均与煤炭运销审核业务直接相关 |

## 容易做错的三处
- 现象：输出内容未显示引用来源的单据编号或文档标题，字段为空。原因：未开启`detail`配置，未强制返回原始文档的标识字段。
- 现象：召回的来源文档与当前审核的煤炭批次无关，结果条数超出预期。原因：未设置合理的最大上下文长度，或分块长度过短导致字段关联丢失。
- 现象：上传新的运销单据至知识库后，审核请求未召回该文档，或显示旧版本内容。原因：未配置知识库定期同步业务系统的触发规则，导致知识库与业务数据不同步。

## 怎么确认配好了
- 发起一条针对某份具体煤炭运销过磅单的审核请求，检查输出内容是否包含该单据的编号、过磅日期等原始字段。
- 查看对话的引用来源面板，确认召回的文档均来自已关联的煤炭运销知识库，且数量符合预期。
- 上传一份新的运销合同至关联知识库，发起相关审核请求，确认新文档被正确召回并作为引用来源。
- 检查系统日志，确认`quoteMaxToken`配置生效，引用的原文片段长度符合设定值。
