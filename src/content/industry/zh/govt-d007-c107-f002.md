# 煤矿生产的申报材料与案卷审核：向量模型与索引

## 这个品类的数据长什么样
这个品类的数据主要来源于煤矿安全生产申报材料、井下作业案卷、安监审批档案及设备运维记录。数据更新随业务流转触发，单次申报批量提交，日常审批案卷按需更新。单份文档长度差异显著，短则数页的作业审批单，长则数十页的专项生产方案。字段包含申报主体、作业区域、设备编号、审批文号、整改时限，配套数值字段附带吨、米、小时等煤矿专用计量单位。

## 这些特征在「向量模型与索引」这一环带来什么约束
文档长度差异大，要求分块策略需适配短文本审批单与长文本方案的不同切分逻辑，避免短文本向量冗余或长文本语义断裂。多字段含专用计量单位，要求向量模型需兼容混合文本与数值字段的向量化处理，避免专业术语语义丢失。批量申报提交的高并发场景，要求索引支持增量更新与批量入库，避免单次入库超时。案卷审批文号作为唯一标识，要求索引需支持按特定字段精准召回，提升检索准确率。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配煤矿申报材料中长文本方案与短审批单的混合结构，平衡语义完整性与索引效率 |
| 重叠长度 | 100–150 字符 | 保留切分块之间的上下文关联，避免长文本跨块后语义断裂 |
| 向量模型选择 | bge-large-zh-1.5 | 适配煤矿专业中文术语，与申报材料的文本特征匹配度较高 |
| 相似度阈值 | 0.72–0.78 | 过滤低相关案卷内容，同时保障同类型申报材料的召回准确率 |
| `defaultToken` | 4096 | 适配长文本生产方案的向量化上限，避免关键内容被截断 |
| 单次召回上限 | 前10条 | 控制人工审核的信息负载，匹配案卷审核的精准检索需求 |

## 容易做错的三处
- 现象：检索结果包含未配置的辅助文档，原因：未将辅助数据从索引范围中排除，误将辅助文件纳入向量向量化与索引流程。
- 现象：单份申报材料返回多条重复向量结果，原因：未正确配置重叠长度参数，导致同一段文本被多次切分并生成重复向量，或未开启文档去重配置。
- 现象：上传的本地向量化文档无法在服务器端正常召回，原因：未统一向量模型版本与嵌入维度，服务器端使用的模型与本地切分文档时的模型不兼容，导致向量匹配失败。

## 怎么确认配好了
- 使用FastGPT v4.17.0版本的后台界面上传单份短文本审批单，核对向量切分块的数量与预期一致，调整分块长度至匹配文档长度。
- 导入包含煤矿专用术语的生产方案文档，核对检索结果中专业术语的语义匹配度符合审核需求，调整相似度阈值。
- 提交批量申报材料，核对索引入库的耗时与系统负载符合预期，调整`defaultToken`参数适配单份文档的最大长度。
- 切换向量模型为非bge-large-zh-1.5的版本，核对召回结果的专业术语匹配率下降，确认当前模型配置有效。
