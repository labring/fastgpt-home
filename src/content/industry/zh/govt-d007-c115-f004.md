# 轨道交通装备的申报材料与案卷审核：工作流编排

## 这个品类的数据长什么样
轨道交通装备申报材料与案卷的数据主要来源于研发设计图纸、型式试验报告、生产批次履历、合规资质证明四类核心来源，随单次申报项目批量更新，无固定日常更新节奏。单份案卷通常包含固定结构的申报书、多页试验数据表格、带编号的资质扫描件，字段涵盖轴重、运行时速、认证有效期、生产批次号等，对应单位为千牛、公里每小时、年月日、批次编号。

## 这些特征在「工作流编排」这一环带来什么约束
多模态与纯文本数据混合的结构，要求工作流需按数据类型拆分处理节点，避免冗余解析。固定字段与单位的强约束，要求工作流需嵌入参数校验环节，确保申报数据符合制式要求。批量申报的场景，要求工作流支持批量触发与节点权限分级，不同审核环节的节点需绑定对应审批角色。长文档与多模态数据的组合，也要求工作流的上下文承载能力需适配单份案卷的总数据量。

## 配置怎么定
本配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 单次搜索上限 | 前8条 | 轨道交通申报材料单份文档字数较多，需召回足够关联的合规与技术内容 |
| 上下文窗口 | 12000–15000 字符 | 覆盖完整申报案卷的核心审核逻辑与关联字段 |
| 超时时间 | 600 秒 | 适配长文档解析、多模态图纸处理的耗时需求 |
| 分块长度 | 800–1000 字符 | 平衡字段识别精度与跨块上下文的连贯性 |
| 重排 | 开启 | 优先匹配合规性、技术参数类的关键审核内容 |
| 变量校验 | 开启轴重、时速字段单位校验，基于`variables`字段校验 | 匹配申报材料固定字段的制式单位要求 |

## 容易做错的三处
- 工作流中未拆分多模态与纯文本处理节点，导致纯文本节点调用工具时触发冗余的多模态解析，最终返回结果不符合预期。原因是未基于输入数据的类型配置分支逻辑，未按`nodeId`绑定对应处理模型。
- 工作流调用知识库搜索时，返回结果条数与全局配置不一致。原因是误将全局知识库的引用上限套用至工作流节点，未单独调整工作流内的单次搜索上限参数。
- 长申报文档解析后出现字段截断或单位识别错误。原因是分块长度设置过短，导致跨块的字段与单位无法被完整关联识别。

## 怎么确认配好了
- 上传单份完整申报案卷，触发工作流，检查各节点的输入输出数据是否匹配预设的字段与格式要求。
- 分别传入纯文本申报书与多模态图纸文件，验证对应节点是否仅处理对应模态的数据。
- 查看工作流日志，确认超时时间设置后未出现频繁的节点超时报错。
- 手动修改申报材料中的单位字段，验证变量校验节点是否能触发异常提示。
