# 通信工程建设的申报材料与案卷审核：向量模型与索引

## 这个品类的数据长什么样
通信工程建设的申报材料与案卷审核数据，主要来源于项目立项申报书、现场勘验记录、材料报审表、竣工案卷等官方文档。数据随项目推进阶段性更新，从立项到验收的全流程分批导入。文档结构包含结构化工程量清单、带专业参数的长文本段落，字段涵盖项目编号、建设单位、施工单位、材料规格、验收结论等，单位涉及项、米、平方米、台套等工程类标准单位。

## 这些特征在「向量模型与索引」这一环带来什么约束
结构化工程量清单与长文本并存的文档结构，要求索引分块时兼顾表格语义完整性与长文本上下文关联；阶段性分批更新的数据特征，需要适配增量索引的配置逻辑；多类型工程单位与专业术语的存在，要求索引保留字段元数据以避免匹配混淆；不同格式的文档来源（如PDF、Word、Excel），需要配置兼容的解析规则，保障分块准确性。

## 配置怎么定
本配置基于FastGPT v4.17.0版本
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配通信工程文档中长施工方案、验收报告的文本长度，避免拆分破坏专业术语的语义完整性 |
| 重叠长度 | 100–150 字符 | 保留相邻分块的上下文关联，避免跨分块的工程术语断裂 |
| `maxToken` | 8192 | 适配多数通用embedding模型的token上限，兼容长文档解析后的分块token数 |
| 相似度阈值 | 0.75–0.85 按实测标定 | 区分申报材料中相似的工程量清单条目，避免误匹配 |
| 单次搜索上限 | 前10条 | 覆盖案卷审核中需要关联的多份关联材料，保证检索完整性 |
| `defaultToken` | 4096 | 配置系统默认的上下文token配额，适配通信工程审核的多文档关联查询 |

## 容易做错的三处
- 现象：Docker部署环境下，索引任务长时间处于运行中无进度，且对话功能可正常调用配置的大模型。原因：未针对通信工程的多格式文档（如CAD导出的PDF、带嵌套表格的Word）配置正确的文档解析规则，导致分块阻塞。
- 现象：向量检索返回结果条数与配置的单次搜索上限不符，部分相似案卷未被召回。原因：未保留文档的字段元数据，导致向量匹配时混淆了不同单位的工程量条目。
- 现象：索引任务报错提示token超限，无法完成分块入库。原因：未设置合理的`maxToken`参数，导致长文本分块后的token数超出模型上限。

## 怎么确认配好了
- 上传一份典型的通信工程施工方案文档，查看分块预览界面，确认长文本未被过度拆分且保留了专业术语的完整性。
- 发起一次案卷相似度检索，核对返回结果的数量与配置的单次搜索上限一致，且结果中包含关联的工程量清单条目。
- 查看系统日志，确认索引任务未出现token超限或解析失败的报错信息，且任务在300秒内完成分块入库。
- 调整相似度阈值后重新检索，观察返回结果的匹配精度变化，确认阈值配置符合业务审核需求。
