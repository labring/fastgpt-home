# 通信工程建设的申报材料与案卷审核：多轮对话与提示词

## 这个品类的数据长什么样
通信工程建设的申报材料与案卷数据主要来源于项目立项审批文件、工程量报审单、施工监理日志、竣工验收意见书等。数据更新节奏随项目节点推进，从立项到验收阶段分批提交。文档结构固定，包含工程编号、预算金额、施工周期、基站数量、链路带宽等字段，字段对应单位分别为无、万元、天、个、Mbps。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
通信工程申报材料与案卷的分阶段更新特性，要求多轮对话需绑定会话上下文以跟踪项目进度。字段附带专业单位的特征，要求提示词需明确指定单位识别规则，避免提取结果出现单位偏差。固定的文档结构要求提示词匹配预设字段提取逻辑，减少非必要信息干扰。分批提交的材料需在对话中明确关联对应项目批次，避免上下文混淆。

## 配置怎么定
本配置基于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 8000–12000 字符 | 匹配通信工程案卷单份材料的平均长度，避免截断关键专业字段 |
| `messages` 上下文窗口 | 保留最近10轮对话 | 跟踪项目阶段变化，避免混淆不同申报批次的材料内容 |
| `variables` 变量绑定 | 绑定工程编号、预算金额字段 | 自动带入专业参数，减少手动输入的失误概率 |
| `chatId` 会话绑定 | 固定会话标识 | 确保多轮对话的上下文连贯，避免会话上下文丢失 |
| 请求超时 | 600 秒 | 匹配通信工程案卷的平均处理时长，避免提前终止请求 |
| 单次搜索上限 | 前6条结果 | 匹配单项目申报材料的常规附件数量，避免冗余信息干扰 |

## 容易做错的三处
- 现象：对话返回的知识库引用字段为空，或格式不符合预设的字段列表。原因：未将申报材料的结构化字段绑定到`variables`参数，导致检索结果无法正确关联上下文。
- 现象：第二轮对话无法读取第一轮的输出内容，上下文出现断层。原因：未通过`chatId`绑定对话会话，导致上下文丢失。
- 现象：流式输出出现卡顿或提前终止，返回内容不完整。原因：未配置合理的超时参数，或未按通信工程案卷的文档长度调整上下文窗口。

## 怎么确认配好了
- 上传单份通信工程立项材料，测试对话提取工程编号、预算金额的结果，确认字段匹配文档结构。
- 发起两轮连续对话，查看`chatId`是否保持一致，确认上下文未丢失。
- 调用API发起流式请求，检查返回的数据流是否按对话轮次分段输出。
- 绑定`variables`变量后发起对话，确认专业单位如Mbps、万元被正确识别和展示。
