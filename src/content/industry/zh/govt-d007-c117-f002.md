# 通信铁塔与基础设施的申报材料与案卷审核：向量模型与索引

## 这个品类的数据长什么样
通信铁塔与基础设施的申报材料与案卷审核数据，主要来源于运维管理系统的日常勘查记录、项目申报平台的立项申请文档、审批部门的案卷归档文件。数据更新节奏分为两类：项目申报数据随立项进度实时更新，运维勘查数据每日同步，审批案卷则在审批完成后批量归档。文档结构包含标准化字段与非结构化内容：标准化字段包括项目编号、铁塔经纬度、塔高、承重阈值，单位多为米、千牛；非结构化内容包括现场照片说明、审批意见函、整改要求文本。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源数据来源要求索引环节需支持跨系统数据的元数据绑定，避免不同来源的同一项目数据被错误拆分。更新节奏差异则要求配置增量与全量两种索引模式，分别适配实时运维数据与批量归档案卷。文档中混合的标准化字段与非结构化文本，需要向量模型同时适配结构化参数的语义关联与大段描述的上下文连贯性。特定的单位字段则要求分块时保留单位信息，防止嵌入后丢失参数的精准语义。此外，案卷审核需关联多份跨周期的历史数据，索引需支持按项目编号进行分组召回。

## 配置怎么定
本页配置基于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配铁塔申报材料中常见的单份勘查记录、审批意见长度，完整保留核心参数与上下文 |
| 重叠长度 | 100–150 字符 | 避免跨块的语义断裂，保障塔高、经纬度等连续参数的嵌入语义连贯性 |
| `defaultToken` | 4096 token | 适配多数开源嵌入模型的默认token上限，满足单块数据的嵌入需求 |
| `maxToken` | 8192 token | 处理包含多份附件的批量案卷查询场景，覆盖长文本的嵌入需求 |
| 相似度阈值 | 0.75–0.85 | 过滤申报材料中重复出现的制式化模板文本，精准匹配核心审核内容 |
| 单次搜索上限 | 前 10 条 | 适配案卷审核的关联材料召回范围，覆盖常见的跨周期关联数据需求 |

## 容易做错的三处
- 现象：导入申报材料后，部分结构化参数（如塔高、经纬度）字段为空。原因：未开启结构化字段绑定配置，直接对全文档进行分块嵌入，导致元数据丢失。
- 现象：批量导入历史案卷时出现超时报错。原因：未配置增量索引策略，全量扫描所有历史数据，超出系统处理阈值。
- 现象：搜索结果中出现大量低匹配度的通用审批模板文本。原因：相似度阈值设置过低，未过滤制式化的冗余内容。

## 怎么确认配好了
- 上传单份铁塔勘查报告，检查分块后的文本是否完整包含核心参数，无截断或丢失。
- 执行批量增量索引测试，查看系统仅更新新增的案卷数据，未重复处理历史归档内容。
- 发起模拟审批查询，核对返回的关联文档数量符合预设的单次搜索上限要求。
- 查看嵌入模型的token消耗日志，确认`defaultToken`与`maxToken`的配置未超出模型支持范围。
