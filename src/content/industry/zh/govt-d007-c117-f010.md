# 通信铁塔与基础设施的申报材料与案卷审核：知识库检索与召回

## 这个品类的数据长什么样
本品类数据主要来源于通信铁塔运维档案、基站申报审批卷宗、现场勘查转写文档与基础设施台账。更新随新基站投用、运维变更触发，配合季度案卷归档完成批量同步。文档结构包含标准化申报表单（含塔高、经纬度、产权信息）、运维日志片段、案卷编号与审批节点记录，字段带有明确单位，如塔体高度以米为单位，经纬度采用十进制格式，案卷编号带有固定业务前缀。

## 这些特征在「知识库检索与召回」这一环带来什么约束
本品类数据包含结构化字段与非结构化文本混合内容，检索时需同时匹配文本语义与结构化元数据，避免仅依赖语义召回导致的非相关结果。案卷编号与塔体参数带有固定格式，检索时需保留字段级匹配逻辑，防止因格式差异丢失精准匹配项。单份案卷文档长度差异较大，短则数百字符的审批意见，长则数万字符的勘查报告，需适配不同长度的文本分块与召回逻辑。数据更新随业务变更触发，存在批次性波动，需配置增量同步规则，避免召回过期的运维与审批数据。

## 配置怎么定
仅作参考；请以目标 FastGPT 发布版本与部署文档核验。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `similarity` | 0.72–0.80 | 适配混合结构化参数与非结构化文本的匹配精度，避免召回无关的运维文档 |
| `limit` | 前8条 | 平衡召回覆盖率与上下文长度，适配单轮案卷审核的材料数量需求 |
| `searchMode` | hybrid | 同时支持语义检索与元数据字段匹配，满足塔高、经纬度等结构化参数的精准召回 |
| `usingReRank` | 开启 | 对初始召回结果进行重排序，修正语义匹配偏差，优先返回核心审批相关内容 |
| `datasetSearchUsingExtensionQuery` | 关闭 | 本品类数据格式固定，无需额外扩展查询词，避免引入无关干扰项 |

## 容易做错的三处
- 现象：检索返回的文本块未携带塔体编号、经纬度等元数据，无法关联到具体基站案卷。原因：未配置`searchMode`为hybrid模式，仅启用纯语义检索，未绑定元数据字段匹配逻辑。
- 现象：知识库召回的文档中，塔高数值与“米”单位之间出现多余空格，与原始录入格式不符。原因：未配置文本归一化处理规则，未对数字与单位间的空格进行自动修正。
- 现象：markdown格式的勘查报告传入知识库后，标题层级与从属逻辑丢失，导致检索时无法关联到对应章节的审批意见。原因：未开启文档结构识别配置，仅按纯文本分段，丢失了标题与内容的从属关系。

## 怎么确认配好了
- 提交一条包含塔高参数的测试查询，核对返回结果是否同时包含语义匹配的文本与对应元数据字段。
- 上传一份包含数字与单位的测试文档，核对召回结果中数字与单位间是否保留正确格式。
- 上传一份带层级标题的markdown测试文档，核对检索结果是否能关联到对应标题下的内容。
- 触发一次增量同步，核对知识库中是否仅更新了最新的申报案卷数据，未保留过期内容。
