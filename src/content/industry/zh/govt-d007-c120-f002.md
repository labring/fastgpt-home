# 铁路运营的申报材料与案卷审核：向量模型与索引

## 这个品类的数据长什么样
数据来源于铁路运营各环节的日常申报单据与归档案卷，包括客货运输申报单、行车调度申请、资质审核案卷等。数据更新随业务流程触发，单笔业务提交即生成新数据，归档案卷按季度批量整理。文档多为结构化表单与非结构化附件组合，包含申报编号、业务类型、提交时间、审核节点记录等字段，单位涉及车次、货票号、件数、吨级等。

## 这些特征在「向量模型与索引」这一环带来什么约束
结构化与非结构化混合的数据结构，要求向量模型与索引需支持多模态内容的分块与编码，避免结构化字段的标识信息被过度压缩。实时更新与批量归档并存的节奏，要求索引支持增量刷新与全量重建的双模式切换，适配不同业务场景的更新需求。包含车次、货票号等特定单位字段，要求向量模型在编码时保留单位与业务标识的语义关联，避免跨业务的语义混淆。单份案卷可能包含多份附件，要求分块策略按业务单元拆分，确保关联内容的语义完整性。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本制定。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配铁路申报材料中表单与附件的平均文本长度，避免单块内容过载 |
| 重叠长度 | 100–200 字符 | 保留跨块的上下文关联，适配审核意见等连贯文本的语义完整性 |
| `maxToken` | 8192 token | 匹配多数开源嵌入模型的上下文窗口上限，兼容铁路案卷的长文本附件 |
| 相似度阈值 | 0.72–0.80 | 区分有效审核关联与无关业务记录，适配铁路业务的精准匹配需求 |
| 单次搜索上限 | 前 20 条 | 覆盖单份案卷的关联审核记录数量，避免结果冗余 |
| `defaultToken` | 1024 token | 统一短文本字段的编码长度，确保申报编号等标识的语义一致性 |

## 容易做错的三处
- 现象：知识库搜索耗时超过30秒，界面显示加载超时。原因：未根据铁路案卷的批量数据调整单次搜索上限，导致单次召回过多冗余结果，增加向量检索耗时。
- 现象：配置嵌入模型渠道后，界面提示无可用向量渠道，日志返回400错误。原因：未校验嵌入模型的输入token长度与`maxToken`配置匹配，铁路长文本附件超出模型支持上限导致请求失败。
- 现象：审核案卷的关联结果中混入无关车次的申报材料。原因：未设置相似度阈值或阈值取值不符合业务匹配需求，导致低关联度的业务记录被召回。

## 怎么确认配好了
- 上传一份标准铁路货运申报单，检查分块后的文本片段是否保留了货票号、吨级等关键单位信息。
- 触发增量索引刷新，查看索引进度日志是否区分实时业务与归档案卷的更新节奏。
- 调用检索接口，核对返回结果的数量是否符合单次搜索上限的配置要求。
- 测试长文本附件的编码请求，确认未触发`maxToken`相关的报错提示。
