# 铁路运营的申报材料与案卷审核：引用来源与溯源

## 这个品类的数据长什么样
铁路运营的申报材料与案卷审核数据，主要来源于客货运申报系统、列车调度档案、安全检测台账、票务结算记录等业务系统。数据更新节奏分为两类：日常运营申报材料为实时生成，办结案卷则按月归档留存。文档结构包含结构化字段与非结构化文本，结构化字段含作业编号、车次号、审批人、审核时限等，非结构化文本含申报说明、整改报告、审核意见等。字段格式有固定规则，车次号以G/D/C前缀加数字标识，时间采用YYYY-MM-DD HH:MM:SS格式，案卷编号采用固定段式编码。

## 这些特征在「引用来源与溯源」这一环带来什么约束
铁路运营数据的结构化字段占比高，要求溯源时需精准匹配字段信息，避免出现跨车次、跨案卷的错误关联。实时更新的申报材料要求知识库支持增量同步，归档案卷则需保留版本记录，确保溯源时可调用对应时间点的原始数据。单篇申报材料与案卷的文本长度跨度较大，长文本可能超出默认引用限制，需调整配置适配内容完整性。多层级的审核流程会生成多轮关联数据，溯源时需按流程节点关联对应文档，避免混淆不同环节的材料。

## 配置怎么定
本页配置基于 FastGPT v4.17.0 版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |

| 返回源数据 | 开启 | 满足案卷审核中需直接引用原始材料的核心需求，确保溯源信息可验证 |
| 详情展示等级 | 完整字段 | 展示结构化业务字段，便于审核人员核对车次、时间等关键信息 |

| 上下文窗口 | 按实测标定 | 适配多层审核问题树的对话场景，避免上下文溢出导致异常 |
| 源数据版本控制 | 启用归档版本 | 匹配铁路案卷的历史版本管理要求，确保溯源可追溯至对应办结节点 |

## 容易做错的三处
- 现象：问答界面显示引用了源数据，但返回内容未包含原始案卷或申报单文本。原因：未开启返回源数据配置，或`quoteMaxToken`设置过小截断了源数据内容。
- 现象：发起多层递进式审核查询时，对话流程卡住无响应。原因：未限制单次召回上限或`quoteMaxToken`取值过大，导致系统资源占用过高引发超时。
- 现象：审核查询返回的内容与知识库中存储的问答对原文不一致，存在额外改写。原因：未关闭自动问题优化开关，或未将`detail`设置为仅返回源数据，导致模型对原文进行了加工。

## 怎么确认配好了
- 上传一份符合格式的铁路客货运申报单，发起审核查询，检查返回结果中是否包含完整的源文档字段与文本内容。
- 发起多层递进式的审核问题，确认对话流程可以正常流转，无超时或无响应情况。
- 查看系统日志，确认每次查询都正确召回了对应车次或案卷的源数据，无遗漏或重复召回的情况。
- 测试知识库中存储的标准问答对，确认返回内容与原文完全一致，无额外的语义加工或改写。
