# 养老服务机构监管的业务办理流程引导：模型接入与配置

## 这个品类的数据长什么样
该品类的核心数据通常来自养老服务信息平台、民政统计系统、消防检查记录与机构运营台账，更新频率为月度。日常处理的文档包含养老机构备案材料、运营补贴申请文件、服务质量检查表、安全隐患整改台账及老人入住档案，数据字段多涉及机构资质、床位数量、整改情况、补贴申请信息等，部分文档为扫描件与结构化表格混合的非标准化形式。

## 这些特征在「模型接入与配置」这一环带来什么约束
月度批量更新的多源异构数据会带来单次处理量较大的问题，需适配多格式文档的解析需求。备案材料与整改台账的非结构化特性，要求模型具备多模态内容解析能力。数据字段涉及机构资质、安全隐患等敏感监管信息，需严格控制上下文范围避免信息泄露。多部门协同的台账数据格式差异，会增加内容匹配的难度，需调整上下文关联逻辑。同时，审核补贴与整改材料的高风险属性，要求模型输出结果附带明确的引用来源，避免决策偏差。

以下配置基于FastGPT v4.17.0版本的逻辑制定：
## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配月度批量的多源文档总长度，避免截断关键监管数据与机构核心信息 |
| `maxTokens` | 4000 token | 控制单轮生成结果长度，适配补贴审核、整改评估等业务的短平快决策需求 |
| `quoteMaxToken` | 1500 token | 限制引用文档的单段长度，确保引用内容精准对应备案、整改等核心业务字段 |
| `temperature` | 0.1–0.3 | 降低生成随机性，确保监管类业务的判断结果符合民政部门的统一业务逻辑 |
| `toolChoice` | auto | 自动调用多模态工具解析扫描件格式的检查记录与台账，适配多类型文档输入 |

## 容易做错的三处
- 现象：使用多模态工具处理上传的养老机构备案扫描件时，处理耗时远超预期。原因：未针对月度批量的台账数据调整上下文截断参数，导致工具反复加载冗余文档片段。
- 现象：在配置`AIPROXY_API_TOKEN`时出现数据过长报错。原因：未限制令牌携带的上下文前缀长度，导致提交的请求参数超出数据库字段存储上限。
- 现象：召回的业务文档与当前审核的补贴申请匹配度偏低。原因：未调整`quoteMaxToken`参数，导致引用片段过长，无法精准匹配补贴额度、机构资质等核心字段。

## 怎么确认配好了
- 上传单份养老机构备案扫描件，检查多模态工具是否能正确提取机构名称、床位数量等核心字段。
- 提交月度批量的台账数据，查看处理耗时是否符合业务预期，无明显超时情况。
- 生成补贴审核结果，检查是否附带明确的文档引用来源，且生成结果无冗余无关内容。
- 调整`temperature`参数至0.2后，提交两份同类补贴申请，查看生成结果的逻辑是否保持一致。
