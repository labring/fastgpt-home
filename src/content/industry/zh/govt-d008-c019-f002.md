# 双随机、一公开监管检查的业务办理流程引导：向量模型与索引

## 这个品类的数据长什么样
通常涵盖市场监管、住建、生态环境、文旅、人社等监管部门的业务数据，来源为“双随机、一公开”监管平台、企业信用信息公示系统、行业监管系统及执法人员名录库。日常文档包含抽查计划、检查对象名单、检查事项清单、现场检查记录、整改通知书、抽查结果公示，数据更新频率为月度。数据字段多涉及监管对象统一社会信用代码、执法人员编号、检查事项类别等，部分为结构化表格，部分为非结构化文本记录。

## 这些特征在「向量模型与索引」这一环带来什么约束
月度更新的周期性数据，要求适配增量索引规则，避免全量重建占用过多资源。混合格式的文档（结构化表格与非结构化文本），需要索引支持多类型数据的分片处理。字段关联性强的执法人员名录、检查对象名单等数据，需保留字段级关联索引以支持精准匹配。抽查结果公示的时效性要求较高，需控制索引更新延迟，避免返回过时信息。专属业务字段的语义匹配，需配置针对性的向量映射规则，确保检索结果符合监管业务逻辑。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配监管文档的常见长度，保留检查事项、检查记录等核心语义单元 |
| 重叠长度 | 100–200 字符 | 避免分块破坏跨块语义的连贯性，确保关联字段的检索完整性 |
| 相似度阈值 | 0.75–0.85 | 过滤低匹配度的非监管相关内容，符合执法检查的精准性要求 |
| 单次搜索上限 | 前 10 条 | 控制返回结果的冗余度，适配监管业务的有限结果展示需求 |
| `defaultToken` | 1000 | 适配多数监管文档的单块长度，匹配基础向量编码的参数要求 |
| `maxToken` | 4000 | 适配FastGPT v4.17.0的上下文窗口上限，满足多块检索结果的拼接需求 |

## 容易做错的三处
- 索引任务持续处于训练中或重建状态，耗时超过一天。原因是未配置增量索引规则，全量索引月度更新的全量数据量较大，导致任务阻塞。
- 切换知识库索引时出现60秒超时。原因是单次搜索上限设置过高，或分块长度超出系统处理阈值，导致索引加载耗时过长。
- 某文件始终处于索引中无法完成。原因是该文件包含乱码或非标准格式的文本，向量模型无法完成有效编码，导致索引任务卡住。

## 怎么确认配好了
- 查看FastGPT v4.17.0的索引配置日志，确认分块长度、重叠长度等参数与设置一致。
- 测试检索监管对象名单相关问题，检查返回结果的相似度是否符合预设阈值范围。
- 触发一次增量索引任务，确认更新耗时符合月度数据的常规处理周期。
- 验证`defaultToken`与`maxToken`的配置是否适配当前知识库的最大文档长度。
