# 双随机、一公开监管检查的业务办理流程引导：工作流编排

## 这个品类的数据长什么样
这个品类的典型业务数据来自“双随机、一公开”监管平台、企业信用信息公示系统、执法人员名录库，更新频率为月度。日常文档包含抽查计划、检查对象名单、检查事项清单、现场检查记录、整改通知书、抽查结果公示，核心字段包括检查对象统一社会信用代码、执法人员编号、检查事项条目、整改完成状态等，格式与对应监管平台的标准接口对齐，无额外自定义字段。

## 这些特征在「工作流编排」这一环带来什么约束
月度更新的数据源要求工作流配置固定的同步周期，避免使用过短的拉取间隔浪费系统资源。多来源数据的整合需要校验重复项与合规性，防止出现监管对象抽取不合规的问题。检查对象与执法人员的动态匹配需实时拉取最新名录，否则会导致任务分配错误。检查结果公示环节需绑定官方公示渠道接口，确保流程结束后自动触发数据同步，避免漏公示。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 变量缓存 | 缓存时长设为7200秒 | 业务数据月度更新，2小时缓存可平衡实时性与调用性能，符合FastGPT v4.17.0版本的缓存配置逻辑 |
| 节点ID绑定 | 绑定执法人员名录库节点的`nodeId` | 动态匹配执法人员时需精准调用对应数据源节点，避免调用错误的名录数据 |
| 上下文变量 | 注入`variables`为检查对象名单、检查事项清单 | 将核心业务数据注入工作流节点，减少重复拉取数据源的操作 |
| 工作流超时 | 单次执行时长设为1800秒 | 复杂检查流程的录入、公示环节需充足执行时间，适配非流式请求的合理运行周期 |
| 数据源同步频率 | 同步周期设为每月1次 | 业务数据月度更新，匹配官方数据更新节奏 |
| 搜索结果上限 | 取前20条，按实测标定 | 过滤冗余的检查对象数据，提升工作流运行效率 |

## 容易做错的三处
- 变量引用后配置入口消失。现象：在工作流中使用`variables`绑定业务数据后，模型参数设置按钮无法调出。原因：未在变量绑定前完成模型参数配置，或变量引用覆盖了参数配置入口。
- 接口调用后运行数据为空。现象：调用工作流生成检查结果后，对话日志无对应执行记录。原因：未开启工作流日志存储开关，或数据源节点未正确挂载至主工作流。
- 子工作流无法完整执行。现象：主工作流调用整改通知书生成子工作流后，流程提前终止且无报错。原因：子工作流未配置结果回传节点，主工作流未等待子工作流执行完成即结束。

## 怎么确认配好了
- 触发一次模拟检查流程，核对工作流日志中是否包含检查对象名单、执法人员信息的变量引用数据。
- 查看工作流节点的超时设置，确认单次执行时长符合业务流程的合理执行周期。
- 调用子工作流后，检查主工作流是否接收到子工作流生成的整改通知书数据。
- 验证数据源节点的更新频率，确认与业务数据的月度更新节奏匹配。
