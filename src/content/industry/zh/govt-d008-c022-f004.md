# 土地使用权、矿业权与国有产权交易的业务办理流程引导：工作流编排

## 这个品类的数据长什么样
该品类的数据主要来源于全国公共资源交易平台、自然资源交易系统、产权交易所系统、国资监管系统，更新频率为每日。日常涉及的业务文档包括出让公告、交易须知、竞买申请、保证金凭证、成交确认书、挂牌结果公告、产权转让说明书。数据字段通常包含标的权属编号、限制条件、保证金金额、交易价款等，核心围绕资源资产权利的交易相关信息，与采购类项目的字段差异明显。

## 这些特征在「工作流编排」这一环带来什么约束
多系统来源要求工作流支持跨数据源拉取配置，需为不同系统的接口配置独立的节点适配规则。每日更新的频率要求工作流需配置定时同步变量的触发逻辑，确保下游节点使用最新数据。多样的业务文档类型要求工作流包含适配不同文档格式的解析节点，分别处理出让公告、成交确认书等内容。核心耗时环节的拆分要求将权属核对、挂牌竞价、材料审核等拆分为独立节点，便于单独调整与监控。严重的出错后果要求为每个关键节点配置失败分支，异常时自动触发人工审核流程。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 全局变量配置 | 绑定每日同步的交易数据，变量池容量不超过1000 MB | 数据更新频率为每日，且单批次交易数据量较大，需控制变量存储上限 |
| 节点ID映射 | 使用`nodeId`按交易环节命名，例如`nodeId: "check_ownership"` | 多环节拆分的工作流需清晰的节点标识，便于排查与调整 |
| 变量更新触发时机 | 在数据拉取完成后触发，延迟不超过600秒 | 需确保最新的交易数据同步到下游节点，避免使用过时信息 |
| 失败分支配置 | 当节点返回异常状态时，触发人工审核节点 | 交易环节出错后果严重，需及时介入处理 |
| 上下文调用上限 | 调用前5条核心业务文档 | 核心业务文档为出让公告、成交确认书等，过多会导致上下文过载 |
| 全局变量绑定 | 将代码运行节点的输出绑定到`variables`全局作用域 | 确保AI对话等下游节点可读取代码生成的校验结果 |

## 容易做错的三处
- 现象为工作流执行后，后续业务节点读取的`variables`仍为初始值，未更新为最新交易数据。原因是未在变量更新节点后添加显式的变量同步触发步骤，导致变量变更未传递到下游节点。
- 现象为导入工作流配置后，部分节点的配置项为空，无法正常启动执行。原因是导入时未匹配当前环境的`nodeId`映射规则，导致节点标识冲突无法加载配置。
- 现象为AI对话节点返回的结果未包含代码运行节点生成的权属校验内容。原因是未将代码运行节点的输出正确绑定到全局`variables`作用域，导致对话节点无法获取对应数据。

## 怎么确认配好了
- 手动触发一次数据拉取节点，查看`variables`中是否同步了最新的交易文档与标的信息。
- 模拟节点异常状态，检查是否触发预设的失败分支与人工审核流程。
- 导出并重新导入工作流配置文件，检查所有节点的配置项是否完整保留。
- 运行包含代码运行与AI对话的业务链路，检查对话节点是否能获取代码生成的校验结果。
