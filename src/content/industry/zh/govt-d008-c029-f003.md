# 市容环卫与城管执法案件的业务办理流程引导：多轮对话与提示词

## 这个品类的数据长什么样
该品类数据通常来自城管执法平台、城市运行网格平台、视频监控及群众投诉工单，每日更新。日常文档包含巡查记录、案件立案审批表、现场照片、责令改正通知书、处罚决定书、结案报告，核心字段涵盖案件编号、违法类型、责任主体、现场定位信息、整改执行状态等，单份文档同时包含结构化台账与非结构化的影像、文字说明材料。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
该品类的数据兼具结构化台账与非结构化影像、文字材料，且每日更新，要求多轮对话能自动区分不同来源的文档类型，避免混淆字段逻辑。核心业务环节耗时集中在现场取证定位、违法类型判定与整改跟踪，提示词需引导对话聚焦该三类关键动作，避免偏离业务流程。数据来源分散且涉及执法合规性，多轮对话需自动关联对应案件的历史记录，确保上下文匹配当前执法场景，防止出现证据缺失或责任主体判定错误的情况。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定当前案件的唯一编号 | 确保同案件的多轮对话上下文关联，避免跨案件混淆 |
| `messages` | 保留前20轮对话与关联文档片段 | 覆盖案件从立案到结案的核心流程节点，避免上下文丢失 |
| `variables` | 注入案件编号、责任主体字段、最新整改状态 | 让提示词能精准调用当前案件的专属数据，提升判定准确性 |
| 上下文保留时长 | 7天 | 匹配FastGPT v4.17.0默认的`CHAT_FILE_EXPIRE_TIME=7`规则，覆盖该品类常规案件办理周期 |
| 单轮token上限 | 8000–12000 token | 兼顾结构化文档与影像转文字内容的加载，避免单次调用超出模型承载范围 |

## 容易做错的三处
- 现象：对话调用时返回token超限报错，状态码为413。原因：未限制单轮对话的token上限，导致加载的案件文档与历史对话超出模型承载范围。
- 现象：超过7天后无法调取过往案件的对话上下文。原因：沿用FastGPT v4.17.0默认的`CHAT_FILE_EXPIRE_TIME=7`设置，未匹配该品类案件的实际办理周期。
- 现象：批量执行节点中多轮对话的执行结果出现上下文错乱。原因：未通过`chatId`绑定专属案件编号，导致不同案件的对话上下文互相覆盖。

## 怎么确认配好了
- 输入测试案件的唯一编号，查看对话是否自动关联对应案件的历史文档与专属字段。
- 调整上下文保留时长后，验证超过7天的测试案件是否仍可正常调取对话记录。
- 运行批量测试脚本，查看不同案件的对话是否保持上下文独立，无字段混淆。
- 查看单轮对话的token消耗统计，确认未超出预设的单轮上限。
