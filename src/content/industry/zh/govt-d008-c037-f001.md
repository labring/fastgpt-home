# 政府信息依申请公开的业务办理流程引导：HTTP 接口与外部系统

## 这个品类的数据长什么样
本品类数据来源于政府信息公开平台、机关档案系统、公文系统、部门业务台账及《政府信息公开条例》相关规范。日常处理的文档包含政府信息公开申请表、补正告知书、征求第三方意见函、答复书、送达回证、行政复议答辩材料等。数据更新无固定周期，随个案申请提交、档案归档及流程变动节奏调整，核心围绕特定申请人的个案信息公开请求生成与流转。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
由于数据来源分散，涉及多套内部业务系统与公开平台，HTTP接口需支持跨系统数据拉取的统一适配逻辑；文档类型多样且结构不统一，接口需兼容不同格式的申请材料与答复文书的传输与解析；数据更新无固定周期，接口需避免硬编码缓存逻辑，按需实时拉取最新数据；同时因出错后果涉及行政复议与司法程序，接口需具备完整的请求溯源与异常上报能力，保障每一次流程操作可追溯。

## 配置怎么定
以下配置基于 FastGPT v4.17.0 版本的接口设置逻辑制定。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `Authorization` | `Bearer {政务平台分配的专属API密钥}` | 遵循政务系统接口的身份鉴权标准，拦截未授权的接口请求 |
| `variables` | `{"applicant_id": "申请人唯一标识", "apply_keyword": "申请信息的检索关键词"}` | 传递业务专属参数，适配不同个案申请的个性化请求逻辑 |
| `responseData` | `仅返回申请受理状态、答复内容、送达凭证标识三个核心字段` | 遵循政务数据传输的最小必要原则，减少敏感数据暴露风险 |
| 接口超时设置 | `600 秒` | 政务办理涉及多环节审核与跨系统协同，预留充足的响应时间 |
| 重试触发规则 | `响应超时或返回 5xx 状态码时触发` | 应对政务系统偶发的临时维护或网络波动，保障调用稳定性 |

## 容易做错的三处
- 现象：调用接口后无有效返回数据，接口返回状态码为 401、403 或 500。原因：未正确配置`Authorization`参数，使用了无效或未授权的API密钥，或未正确绑定`variables`中的申请检索关键词，导致无法定位对应政务信息。
- 现象：接口返回的答复内容存在格式错乱，无法直接用于生成正式政务文书。原因：未适配不同政务系统返回的文档格式，未对`responseData`中的内容做标准化处理。
- 现象：接口调用完成后未触发后续的业务流程节点。原因：未将接口返回的申请状态映射到外部业务系统的流程逻辑，未完成状态同步。

## 怎么确认配好了
- 调用携带合法`Authorization`参数的测试接口，确认返回状态码为 200，且`responseData`中包含预设的核心业务字段。
- 传入不同的`variables`参数组合，验证接口是否能适配不同个案申请的检索需求，返回对应的数据结果。
- 模拟政务系统的临时维护场景，触发接口超时或 5xx 状态码，确认接口会按配置触发重试逻辑。
- 检查接口的异常上报日志，确认所有调用请求的溯源信息已完整记录，可追溯每一次请求的参数与返回结果。
