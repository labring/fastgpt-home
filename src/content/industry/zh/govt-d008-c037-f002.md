# 政府信息依申请公开的业务办理流程引导：向量模型与索引

本配置基于 FastGPT v4.17.0 版本。

## 这个品类的数据长什么样
本品类的数据主体来自政府办公室、部门政务公开办、法规处、档案室。日常处理的文档包括政府信息公开申请表、补正告知书、征求第三方意见函、答复书、送达回证、行政复议答辩材料。数据来源涵盖政府信息公开平台、机关档案系统、公文系统、部门业务台账及政府信息公开条例相关规范。数据更新频率为不定期，无固定批量更新周期。文档结构随类型差异明显，部分文档包含申请人身份信息、申请事项描述，部分包含公开属性判断依据与救济途径说明。

## 这些特征在「向量模型与索引」这一环带来什么约束
本品类的数据来源分散且格式多样，需适配不同系统导出的文档格式，对索引的预处理环节提出灵活适配要求。数据更新不定期，无法依赖固定周期的全量索引，需支持增量索引以避免重复处理历史文档。文档类型覆盖申请、答复、复议等多类业务文件，语义边界差异大，分块策略需兼顾单块语义完整性与跨块上下文连贯性。检索环节需精准匹配申请事项与已有信息，对相似度匹配的精度要求较高，避免无关文档干扰业务判断。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| 分块长度 | 800–1200 字符 | 适配本品类各类业务文档的常规篇幅，避免语义割裂 |
| 重叠长度 | 100–200 字符 | 保留跨分块的上下文信息，确保申请事项的完整匹配 |
| 相似度阈值 | 0.75–0.85 按实测标定 | 平衡检索召回率与精准度，适配政务办理的业务判断需求 |
| 单次搜索上限 | 前 10 条 | 控制返回内容规模，符合政务办理的有限上下文要求 |
| `maxToken` | 4096 token | 匹配主流开源嵌入模型的输入限制，避免截断关键业务信息 |
| `defaultToken` | 1024 token | 作为默认嵌入模型的输入阈值，适配短文本字段 |
| 重排 | 开启 | 优化检索结果的排序逻辑，提升与申请事项的匹配精度 |

## 容易做错的三处
- 现象：索引任务持续超过30分钟仍未完成，界面显示「索引中」状态无更新。原因：未配置增量索引策略，全量索引重复处理历史文档，导致耗时过长。
- 现象：检索结果返回大量不相关的档案材料，与申请事项的匹配度极低。原因：相似度阈值设置过低，召回了超出业务范围的非目标文档。
- 现象：嵌入模型调用返回报错，提示输入长度超限。原因：未设置合理的`maxToken`参数，未对超长文档进行前置截断处理。

## 怎么确认配好了
- 查看索引任务日志，确认仅新增或更新的文档被处理，无重复全量索引记录。
- 提交模拟的政府信息公开申请，核对检索结果是否包含对应类型的业务文档。
- 测试不同长度的申请文本，确认嵌入模型调用无长度超限报错。
- 调整相似度阈值，验证检索结果的匹配度变化符合业务预期。
