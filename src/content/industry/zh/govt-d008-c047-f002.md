# 行政处罚案卷办理的业务办理流程引导：向量模型与索引

## 这个品类的数据长什么样
本品类数据来自行政执法办案系统、执法记录仪影像、国家企业信用信息公示系统及部门监管数据库，更新频率为每日。日常文档包含现场检查笔录、询问笔录、证据清单、行政处罚事先告知书、听证告知书、处罚决定书、送达回证等，以违法事实与处罚决定为核心，需形成可追溯的处罚证据链与正式文书，字段多包含执法主体、违法情形、裁量依据、文书编号等。

## 这些特征在「向量模型与索引」这一环带来什么约束
数据来源多样且包含结构化、非结构化内容，需同时适配系统导出文书与执法影像转写文本，要求索引支持增量更新以匹配每日更新节奏。长文本类文档占比高，需向量模型适配较长上下文以完整捕获违法事实、裁量依据等核心信息。不同文书需关联形成证据链，要求索引可召回跨文档的关联内容，同时需避免无关执法记录干扰匹配结果。

## 配置怎么定
FastGPT v4.17.0 版本下的配置项如下：
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 匹配现场检查笔录、处罚决定书等日常文档的平均内容长度 |
| 重叠长度 | 100–200 字符 | 避免分块切割导致的上下文断裂，保留跨块的违法事实关联信息 |
| `defaultToken` | 8192 token | 适配单份长文书的向量编码需求，覆盖完整单篇文档内容 |
| `maxToken` | 16384 token | 支持拼接多份关联文书，完整构建证据链的上下文信息 |
| 相似度阈值 | 0.75–0.85 | 按实测标定，过滤无关执法记录，精准匹配处罚相关内容 |
| 单次搜索上限 | 前 10 条 | 覆盖足够的关联证据文档，避免遗漏关键裁量依据或违法事实 |

## 容易做错的三处
- 界面仅显示一种向量模型选择，但出现多组向量对应单份数据的情况。原因是未配置分块关联规则，导致单份长文档被切割为多个向量块后未绑定关联标识，无法统一召回。
- 本地使用自定义向量模型编码文档，上传至服务器后使用官方向量模型，出现匹配结果异常。原因是不同向量模型的嵌入维度不一致，导致向量空间不匹配，无法正确计算相似度。
- 单份执法笔录文件长时间处于索引中，进度无更新。原因是分块长度设置过大，超出向量模型的`maxToken`限制，导致编码过程超时未完成。

## 怎么确认配好了
- 上传单份典型执法笔录文档，查看分块后的向量数量，确认与分块长度设置匹配。
- 导入不同来源的测试数据，验证索引增量更新功能是否正常触发，符合每日更新节奏要求。
- 输入违法事实相关的查询，核对召回结果的文档类型与数量，确认相似度阈值与搜索上限的配置效果符合预期。
- 调用向量编码接口，检查返回的向量维度与配置的`defaultToken`对应模型的标准维度一致。
