# 医药流通的业务办理流程引导：多轮对话与提示词

## 这个品类的数据长什么样
医药流通业务的数据主要来自药品经营许可档案、购销台账、冷链运输监控记录、医保结算凭证四类来源。数据按每笔购销批次更新，单批次数据包含购销单号、药品通用名、生产批号、有效期、流通节点、经手人、冷链温度记录等字段，字段多为字符串或日期格式，需按批次号关联完整流通信息。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
医药流通业务的数据字段多且需按批次关联，导致多轮对话需持续跟踪当前会话的批次号，避免跨批次数据混淆。数据更新频率较高，对话中需实时拉取最新的台账或冷链数据，不能依赖过期的缓存上下文。专业术语较多，提示词需明确限定对话范围为当前业务办理流程，防止引入无关历史数据。工具调用参数需严格匹配当前会话字段，避免参数不匹配引发错误。

## 配置怎么定
以下配置项适用于FastGPT v4.17.0版本：
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `variables` | 存储当前购销批次号、冷链节点ID | 关联多轮对话中不同环节的药品流通数据，避免跨批次混淆 |
| `messages` | 按会话历史拼接上下文 | 确保多轮对话的上下文完整传递，无关键信息丢失 |
| 单次对话最大上下文 | 前1200–1500字符 | 覆盖单次业务办理的完整流程节点，避免上下文截断 |
| 工具调用超时时间 | 600秒 | 匹配医药流通业务中冷链核验、资质审核的常规耗时 |
| 工具调用次数上限 | 前5次 | 避免无限制调用工具导致的资源消耗 |
| 历史会话绑定 | 按`chatId`绑定当前会话 | 确保同一业务办理流程的对话上下文连贯，避免跨会话数据干扰 |

## 容易做错的三处
- 现象：调用MySQL工具时返回400 status code (no body)。原因：未在`variables`中配置数据库连接的必填字段，导致请求参数缺失。
- 现象：新对话中无法加载之前保存的全局变量。原因：未通过`chatId`绑定对应会话的变量存储，导致上下文无法关联。
- 现象：多轮对话中出现跨批次的药品数据混淆。原因：未在提示词中明确要求基于当前会话的`variables`中的批次号筛选数据。

## 怎么确认配好了
- 发起一笔模拟的医药购销业务办理对话，查看对话过程中是否自动带出当前批次的冷链运输数据。
- 触发工具调用，检查返回结果是否匹配预设的医药流通业务字段，无额外无关数据。
- 切换会话ID后，验证之前的全局变量不会被新会话加载，确保上下文隔离。
- 查看工具调用日志，确认超时时间设置符合业务耗时预期，无频繁超时报错。
