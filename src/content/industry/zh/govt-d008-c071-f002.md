# 发电集团的业务办理流程引导：向量模型与索引

## 这个品类的数据长什么样
发电集团的业务办理数据主要来自内部业务办理系统、线下办事指南手册、工单归档库。数据更新随业务政策调整、流程优化同步触发，日常按周同步增量数据。单篇文档多为结构化文本，包含流程步骤、所需材料清单、办理时限、咨询渠道等字段，单位多为工作日、份、人次等，部分文档附带附件扫描件的OCR识别文本。

## 这些特征在「向量模型与索引」这一环带来什么约束
发电集团的业务办理数据结构化程度高且包含时效性字段，要求索引支持按字段过滤过期流程文档。增量更新的同步节奏要求索引支持增量构建，降低资源占用。多来源的OCR附件文本与结构化正文混合，需要统一的向量化适配逻辑，避免不同来源文本的向量分布偏差。业务流程步骤的层级结构要求分块时保留上下文关联，避免拆分破坏流程逻辑，确保检索结果的步骤连贯性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 匹配发电集团业务文档的单段流程描述长度，避免拆分破坏步骤关联 |
| 重叠长度 | 100–150 字符 | 保留相邻分块的上下文衔接，确保流程步骤的逻辑完整 |
| 相似度阈值 | 0.72–0.85 按实测标定 | 适配发电集团业务术语的语义相似度分布，过滤低相关的流程文档 |
| 单次搜索上限 | 前 10 条 | 控制检索结果的返回数量，避免过多冗余信息干扰流程引导 |
| `maxToken` | 4096 token | 适配主流向量模型的输入长度限制，确保业务文档完整向量化 |
| `defaultToken` | 8192 token | 适配向量模型的默认输入上下文长度，覆盖大部分业务文档的向量化需求 |
| 最大上下文 | 3–5 条检索结果 | 匹配业务办理的单次咨询需求，避免上下文过长超出模型处理范围 |

## 容易做错的三处
-  新建知识库后卡在索引构建步骤，界面进度条停滞无变化。原因是未配置增量索引的触发规则，全量索引加载发电集团历史业务数据时占用过多磁盘与内存资源。
-  更换`bge-m3`向量模型后，搜索测试返回的结果语义匹配度异常偏高，出现大量不相关的流程文档。原因是未针对发电集团的专业术语调整相似度阈值，导致低相关的流程文档被误判为高匹配结果。
-  登录PostgreSQL数据库查询，仅能找到向量数据字段，无法检索到原始业务文档内容。原因是未开启原始文本存储开关，仅上传了向量化后的向量数据，未保留原始文档副本。

## 怎么确认配好了
-  上传一篇发电集团的业务办理指南文档，查看FastGPT v4.17.0的索引构建日志，确认分块长度与重叠长度符合预设配置。
-  输入业务办理相关的自然语言查询，验证检索结果包含匹配的流程步骤与材料要求，调整相似度阈值至符合业务需求的区间。
-  进入向量模型配置页面，确认已开启原始文本存储选项，检查数据库中是否同时存在向量数据与原始文档内容。
-  模拟增量更新业务数据，验证索引仅同步新增的流程文档，无需全量重建。
