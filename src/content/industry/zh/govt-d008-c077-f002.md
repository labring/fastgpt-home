# 城市公交的业务办理流程引导：向量模型与索引

## 这个品类的数据长什么样
城市公交业务办理的核心数据来源于城投公用事业旗下的公交运营管理系统，包含办卡挂失、线路查询、临时改线通知、网点办理流程等文档。数据更新节奏分为两类：常规线路调整、网点变更按每月同步，临时施工改线等紧急调整实时推送。文档结构固定为办理事项说明、所需材料、办理渠道、办理时限、咨询方式五个模块，字段包含事项名称、具体地点、办理时段、联系电话，单位涉及工作日、元、个等。

## 这些特征在「向量模型与索引」这一环带来什么约束
数据的实时更新要求索引支持增量同步，避免全量重建带来的资源消耗；结构化字段多且业务专有名词（如站点名、线路号）占比高，需要向量索引兼顾语义召回与结构化字段过滤；单篇文档的流程步骤连贯性强，分块时需避免破坏业务逻辑的完整性；部分紧急通知的更新频率无规律，需支持按需触发索引更新。这些特征要求向量模型需适配领域专有词汇的编码，索引架构需兼顾实时性与结构化数据的处理能力。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 公交办理流程文档多为步骤连贯的长文本，该长度可保留单条流程的完整逻辑，避免分块断裂 |
| 重叠长度 | 100–150 字符 | 弥补分块边界的语义断层，确保流程步骤的上下文连贯性 |
| 相似度阈值 | 0.72–0.80 | 公交业务办理的关键词辨识度较高，该区间可过滤无关召回结果 |
| 单次搜索上限 | 前 8 条 | 业务办理的可选渠道、步骤数量有限，过多召回会干扰用户判断 |
| 重排 | 开启 | 公交业务的语义相似度高的结果需按业务优先级排序，提升用户决策效率 |
| `maxToken` | 4096 | FastGPT v4.17.0 下该参数可覆盖多数公交业务文档的上下文长度需求 |

## 容易做错的三处
- 现象：Embedding模型调用第三方中转服务时返回连接失败或400报错，原因：未正确配置中转服务的API密钥与请求地址，或未兼容模型的输入格式要求。
- 现象：开启重排配置后，在线召回测试结果未按预期排序，原因：未将公交业务的地点、办理时限等结构化字段纳入重排的加权维度，导致语义排序不符合业务场景。
- 现象：索引构建时出现字段缺失报错，原因：未将公交办理文档中的“办理时限”“咨询电话”等必填字段纳入索引映射，导致向量存储时丢失业务关键信息。

## 怎么确认配好了
- 上传一份公交老年卡办理的示例文档，执行索引构建，查看系统日志中是否显示分块成功、向量生成正常的提示。
- 输入“临时改线的公交路线怎么查询”的查询，查看召回结果的条数与相似度是否符合预设阈值范围。
- 开启重排功能后，对比召回结果的排序逻辑，确认与公交网点的办理优先级匹配。
- 修改一条临时改线的公交信息，触发增量索引更新，查看索引是否同步完成。
