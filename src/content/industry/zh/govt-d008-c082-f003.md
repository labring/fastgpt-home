# 基础电信运营的业务办理流程引导：多轮对话与提示词

## 这个品类的数据长什么样
基础电信运营的业务办理数据来源于内部业务办理系统工单、在线交互日志、套餐配置库。实时业务请求秒级同步更新，套餐规则每日凌晨批量更新，历史交互日志按小时归档。单条业务数据包含用户标识、业务类型、当前办理节点、历史交互序列、提交时间戳、办理渠道字段，其中交互次数为整数、办理时长为分钟、业务编码为字符串格式。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
实时业务请求的秒级更新要求对话上下文同步频率匹配业务数据更新节奏，避免引用过期的套餐或进度信息。历史交互序列较长，需限制`messages`的上下文长度，防止超出模型处理上限。业务类型覆盖宽带、手机号、套餐等多类，提示词需绑定业务分类规则，确保引导匹配对应办理节点。不同办理渠道的交互格式存在差异，需通过`variables`传递渠道标识，适配不同场景的话术逻辑。多轮会话需通过`chatId`关联用户交互，避免跨用户会话混淆。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定用户办理业务的唯一会话标识 | 确保多轮对话关联同一用户的业务办理流程，避免会话混淆 |
| `messages` | 保留最近20条交互记录，单条不超过1000字符 | 适配基础电信业务办理的交互长度，防止上下文超出模型处理上限 |
| `variables` | 传递业务类型、办理渠道、当前进度节点三个核心参数 | 匹配基础电信业务的多维度分类需求，精准生成引导话术 |
| 最大上下文 | 8000–12000 token | 覆盖基础电信业务办理的完整交互流程，避免截断关键进度信息 |
| 会话过期时间 | 7天（对应FastGPT v4.17.0默认配置） | 匹配基础电信业务办理的常规周期，平衡存储成本与会话可用性 |

## 容易做错的三处
- 现象：多轮对话出现跨用户的业务进度信息，对话日志无法关联到具体办理用户。原因：未通过`chatId`绑定唯一会话标识，导致不同用户的交互数据被混同。
- 现象：对话中途出现套餐规则引用错误，引导步骤与当前办理业务不匹配。原因：未通过`variables`传递业务类型参数，提示词无法精准匹配对应业务的办理流程。
- 现象：批量执行接点中插入多轮对话分工数组后，执行顺序错乱。原因：未为每个对话分支分配独立的`chatId`，导致分支间会话数据互相干扰。

## 怎么确认配好了
- 发起一次模拟基础电信业务办理流程，查看对话上下文是否仅包含当前用户的交互记录，核对`chatId`是否与模拟会话标识一致。
- 调整`variables`传递的业务类型参数，验证引导话术是否匹配对应业务的办理步骤。
- 批量创建多个模拟会话，确认每个会话的`messages`上下文独立，无跨会话数据混杂。
- 等待会话过期时间设定的周期后，验证会话文件是否按配置规则归档或失效。
