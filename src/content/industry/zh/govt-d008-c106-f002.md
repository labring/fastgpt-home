# 煤电一体化的业务办理流程引导：向量模型与索引

## 这个品类的数据长什么样
煤电一体化的业务办理数据主要来源于生产调度台账、跨部门协同工单、电力并网审批文档、设备运维记录。数据更新节奏随业务节点触发，工单类数据随办理进度实时更新，生产台账按班次同步。单份文档包含流程节点序列、责任部门、办理时限、必备材料清单等字段，时限单位为工作日，材料数量单位为份，调度参数单位为吨、兆瓦。

## 这些特征在「向量模型与索引」这一环带来什么约束
业务数据随办理节点实时更新的特性，要求索引支持增量同步，避免全量重建导致的服务卡顿。多字段混合的文档结构，要求向量模型同时适配结构化数值与非结构化文本的语义关联，不能仅依赖通用文本嵌入逻辑。字段单位与业务属性绑定的特征，要求索引构建时保留字段元数据关联，避免检索时混淆不同业务场景的办理时限、材料要求等信息。同时，跨部门协同的流程文档，要求索引的召回逻辑优先匹配当前节点的上下文，仅召回与当前办理环节相关的内容。

## 配置怎么定
本文基于 FastGPT v4.17.0 版本编写。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 匹配单份业务文档的流程节点段落长度，避免切分破坏流程上下文 |
| 重叠长度 | 100–200 字符 | 保留相邻流程节点的语义关联，防止跨块的流程逻辑断裂 |
| `maxToken` | 8192 token | 适配煤电业务文档的平均长度，满足完整流程节点的嵌入需求 |
| `defaultToken` | 1024–4096 token | 适配短字段如办理时限、材料份数的嵌入，避免token溢出 |
| 单次搜索上限 | 前 8 条 | 平衡召回精度与检索效率，覆盖核心办理节点的关联信息 |
| 重排 | 开启 | 对召回结果按业务相关性排序，优先匹配当前办理环节的需求 |

## 容易做错的三处
- 现象：检索服务启动后长时间无响应，日志显示索引构建超时。原因：未针对煤电业务的实时更新数据配置增量索引策略，触发全量索引重建导致资源占用过高。
- 现象：配置索引模型后，语言模型的调用参数丢失，无法正常生成流程引导内容。原因：未在系统配置中同时绑定索引模型与语言模型的关联关系，导致索引构建后覆盖了语言模型的默认配置。
- 现象：检索结果中出现无关的设备运维数据，无法匹配当前业务办理的流程节点。原因：未在索引配置中过滤非业务办理类的文档，导致召回范围过大。

## 怎么确认配好了
- 查看索引构建日志，确认增量同步任务按业务更新节奏触发，无全量重建的重复记录。
- 测试嵌入煤电业务的流程文档，检查向量输出的 token 数量未超出配置的`maxToken`限制。
- 检索特定办理节点的关键词，核对召回结果包含对应的责任部门、办理时限等字段信息。
- 切换索引模型后，验证语言模型仍能正常调用，无参数丢失情况。
