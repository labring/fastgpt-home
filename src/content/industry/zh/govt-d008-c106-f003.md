# 煤电一体化的业务办理流程引导：多轮对话与提示词

## 这个品类的数据长什么样
煤电一体化的业务数据来源于矿井开采调度系统、电力生产监控平台、跨单位业务审批系统三类核心系统。数据更新节奏分为实时与定时两类：调度与监控数据随业务操作实时更新，业务审批报表数据每日定时同步。文档结构包含结构化业务表单、非结构化审批附件、流程节点说明文档三类。核心字段包含矿井编号、开采量、发电量、审批状态、办理时限，对应单位分别为吨、千瓦时、天。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
结构化表单与非结构化文档混合的数据特征，要求多轮对话需先明确业务类型，再逐步引导用户提供对应字段参数，避免一次性索要过多信息导致交互中断。实时更新的调度数据要求对话上下文需限制有效时长，防止调用过期数据影响流程引导准确性。多节点的流程说明文档要求提示词需按顺序匹配当前办理节点，确保每轮对话仅输出当前步骤的操作要求，避免混淆多轮历史中的流程节点。

## 配置怎么定
FastGPT v4.17.0 版本下的配置项如下：
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配煤电业务文档的段落长度，避免拆分破坏完整的流程节点说明 |
| 重叠长度 | 150–200 字符 | 保留跨块的流程关联信息，确保多轮对话中流程逻辑连贯 |
| 单次搜索上限 | 前 5 条 | 匹配煤电业务常见的关联审批文档数量，过滤无关内容干扰 |
| 最大上下文长度 | 4000–6000 token | 覆盖单业务办理的全量多轮对话历史，防止上下文溢出 |
| 用户会话超时 | 1800 秒 | 匹配煤电业务办理的平均耗时，避免会话提前中断 |
| `variables` 绑定 | 按业务字段映射 | 绑定矿井编号、发电量等专属字段，确保对话调用数据准确 |

## 容易做错的三处
- 调用对话接口返回422状态码。原因：`messages`参数格式不符合要求，例如缺少role字段或content为空，或`variables`未绑定必填的业务字段。
- 不同用户的对话记录与数据出现混淆。原因：未正确使用`chatId`区分独立会话，或公用密钥未绑定用户专属上下文标识。
- 对话返回的流程步骤缺失关键节点。原因：分块长度设置过短，拆分了完整的流程节点说明，导致上下文丢失关键信息。

## 怎么确认配好了
- 输入煤电业务的必填字段，例如矿井编号与办理类型，检查对话是否能正确调取对应业务数据。
- 发起多轮对话后间隔10分钟继续交互，检查会话是否未被提前中断。
- 查看接口日志，确认`variables`参数已正确传入绑定的业务字段。
- 测试不同业务场景，检查返回的流程步骤是否覆盖完整的办理节点。
