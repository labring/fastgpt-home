# 电网企业的业务办理流程引导：多轮对话与提示词

## 这个品类的数据长什么样
电网企业的业务办理数据主要来源于内部营销系统、线下办电台账与政务服务平台的办电流程公示信息。数据每日同步最新办电流程变更，每周更新常见问题与咨询话术库。单条业务数据按办电类型拆分，包含业务编码、办理电压等级、所需材料清单、办理步骤、办理时限、咨询渠道等字段，其中业务编码为12位数字格式，办理时限以工作日为单位，材料清单以结构化列表形式存储。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
电网业务数据按办电类型细分且存在严格的合规要求，多轮对话需先通过关键词匹配识别用户的具体办电场景，避免调用错误的流程数据。数据字段带有明确的单位与格式约束，提示词需严格遵循字段格式生成引导内容，例如要求用户提供12位业务编码或明确说明办理时限的工作日单位。由于数据更新频率较高，对话上下文需过滤过期的流程信息，同时`messages`参数需区分用户输入与系统提示内容，避免混淆交互逻辑。FastGPT v4.17.0的上下文管理机制需适配这类结构化数据的存储与调用。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文长度 | 8000–12000 token | 电网业务流程文档单条内容较多，需保留完整流程与历史交互信息 |
| 上下文保留轮次 | 近3–5轮对话 | 避免冗余旧数据干扰当前业务判断，适配多轮引导的交互场景 |
| 变量绑定配置 | 绑定`variables`中的业务类型字段 | 快速定位对应办电流程的专属知识库数据 |
| 对话触发规则 | 按电网办电关键词匹配业务分类 | 精准调用对应场景的流程与话术数据 |
| 会话超时设置 | 600秒 | 电网业务办理需用户补充材料，预留充足的交互时间 |
| 历史记录隔离 | 按`chatId`单独清理指定应用的对话 | 隔离不同业务场景的上下文，避免数据混淆 |

## 容易做错的三处
- 现象：调试预览中显示的历史对话字段为空，原因：未正确配置`messages`参数，未将用户输入与系统提示内容分开存储，导致上下文无法正常加载。
- 现象：不同业务的对话上下文互相干扰，返回的办电流程与当前业务不符，原因：未按`chatId`隔离不同应用的会话数据，导致不同业务的上下文被错误复用。
- 现象：无法将上一轮的业务结论作为下一轮提示词输入，原因：未通过`variables`传递历史交互结论，未在系统提示中声明上下文复用规则，导致对话无法延续业务逻辑。

## 怎么确认配好了
- 进入调试预览界面，输入电网办电业务关键词，查看上下文区域是否保留近3轮对话内容。
- 绑定`variables`字段后，输入特定业务类型关键词，验证对话是否匹配对应办电流程的专属数据。
- 复制指定`chatId`的会话标识，通过应用管理界面清理该会话的历史记录，验证调试预览中是否不再显示该会话的旧内容。
- 设置600秒超时后，暂停输入等待交互，验证对话是否在指定时间后触发超时提示。
