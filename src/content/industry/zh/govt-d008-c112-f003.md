# 粮食储备的业务办理流程引导：多轮对话与提示词

## 这个品类的数据长什么样
粮食储备业务数据主要来自各级粮库的库存台账、出入库单据、轮换计划文档及官方监管报表。数据更新节奏随业务节点变动，库存实时数据每日同步，轮换计划按季度更新，出入库单据随办理流程生成。单份文档多为结构化表格或标准化表单，包含粮食品种、存储等级、库存数量（单位：吨/公斤）、仓库编号、办理节点、审批状态等固定字段。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
结构化字段多且带明确单位的特征，要求多轮对话需严格匹配字段格式，避免混淆吨与公斤等单位差异，防止生成错误的办理指引。数据更新节奏分层，实时库存与季度轮换计划需在对话中区分调用，避免返回过期信息。标准化文档结构要求提示词需引导用户按固定节点依次提供信息，比如先确认办理类型，再补充粮食品种、数量等必填项，减少无效交互。多节点的办理流程也要求对话需按环节逐步推进，避免跳过关键审批步骤。

## 配置怎么定
本配置适用于 FastGPT v4.17.0

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文长度 | 8000–12000 字符 | 粮食储备业务文档多为结构化表格，单份文档长度适中，过长上下文会增加推理延迟 |
| 单次搜索上限 | 前6条 | 储备业务数据字段固定，少量召回即可覆盖所需办理信息 |
| 问题优化开关 | 开启 | 用户输入可能简化业务术语，优化后可精准匹配结构化字段 |
| `messages` 参数配置 | 保留前10轮交互 | 多轮办理流程中历史交互可明确当前节点，过多轮次会干扰当前推理 |
| `variables` 绑定规则 | 绑定对应粮食品种的业务变量 | 需精准调用对应品类的库存、单据数据，避免混淆不同粮食品种的信息 |
| `chatId` 传递规则 | 随每轮会话自动携带 | 确保多轮对话上下文连贯，避免会话中断或上下文丢失 |

## 容易做错的三处
- 现象：上传任何结构化文档都会报错，文本输入对话正常。原因：粮食储备的业务文档多为固定格式的表格，上传时未正确识别字段分隔符，导致系统无法解析内容。
- 现象：对话时出现Unexpected end of JSON input报错，使用chatglm2模型。原因：多轮对话中`messages`参数传递的上下文过长，超出模型支持的token上限，导致返回截断的不完整JSON。
- 现象：对话响应速度偏慢。原因：单次搜索上限设置过高，同时调用了多份过期的轮换计划文档，增加了检索与推理耗时。

## 怎么确认配好了
- 发起模拟粮食储备业务办理请求，检查对话是否按办理类型、粮食品种、库存数量、仓库编号的顺序依次询问必填字段。
- 查看知识库召回结果，确认仅返回当前粮食品种的相关数据，未混入其他品类的业务信息。
- 测试上传结构化表格文档，确认系统可正常解析并提取字段信息，无报错提示。
- 查看会话日志，确认`chatId`参数随每轮对话正确传递，会话上下文未出现丢失或混乱。
