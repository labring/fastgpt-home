# 轨道交通装备的业务办理流程引导：工作流编排

## 这个品类的数据长什么样
轨道交通装备的数据主要来自车载传感器实时采集的运行工况数据、生产环节的BOM清单、检修台账与运维日志。数据更新节奏分两类：车载实时数据按秒级推送，检修台账、配件更换记录随检修周期更新，产品BOM仅在型号迭代时调整。单条数据文档结构包含设备唯一编号、累计运行时长、故障代码、检修完成时间、更换配件型号与规格，字段单位涵盖小时、次、毫米、件等。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` | 按设备类型预设字段映射规则，覆盖累计运行时长、故障代码、配件型号3类核心字段 | 轨道交通装备数据字段多且单位分散，预设映射可避免运行时单位不匹配 |
| `nodeId` | 为实时数据触发节点、条件分支节点、批量处理节点分别分配唯一`nodeId` | 多节点并行时需通过`nodeId`定位执行状态，避免流程混乱 |
| 上下文窗口 | 800–1200 字符 | 轨道交通装备业务办理需覆盖设备全生命周期信息，窗口过小会丢失关键检修记录 |
| 批量处理上限 | 前 20 条 | 单批次检修台账数据量较大，限制条数可避免工作流超时 |
| API超时时间 | 60 秒 | 车载数据接口响应受网络波动影响，60秒超时可覆盖多数正常请求时长 |

## 容易做错的三处
- 现象：工作流执行后业务字段未更新，日志显示`variables`节点返回空值。原因：未在`variables`节点中配置待更新的字段映射规则，导致流程无法识别需要同步的业务数据。
- 现象：调用工作流API返回404状态码，接口地址填写为本地测试地址。原因：未将本地测试地址替换为部署环境的正式API地址，导致无法访问服务。
- 现象：工作流输出的业务办理引导内容缺失关键设备信息。原因：上下文窗口配置过小，未保留足够的历史业务数据，导致AI无法生成完整的办理引导。

## 怎么确认配好了
- 导入单条轨道交通装备的测试数据，触发工作流执行，检查`variables`节点的输出字段是否与预设映射规则一致。
- 模拟设备异常事件，触发条件分支节点，确认流程是否按故障代码自动分流至对应处理环节。
- 调用部署环境的工作流API，验证返回结果包含业务办理引导内容与更新后的字段信息。
- 调整上下文窗口配置，核对工作流是否能加载完整的设备历史业务数据。
