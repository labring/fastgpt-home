# 轨道交通装备的业务办理流程引导：模型接入与配置

## 这个品类的数据长什么样
轨道交通装备的业务办理数据主要来源于运维检修台账、配件申领工单、故障上报记录三类系统。数据更新分为实时和定时两种节奏：工单提交时实时更新，台账数据每日汇总更新。文档以结构化格式存储，包含装备编号（12位字母数字组合）、故障类型、发生时间、处理进度、配件型号、申领数量等字段，字段带有明确单位，如装备数量单位为“台”、时长单位为“小时”，且部分字段存在固定编码规则。

## 这些特征在「模型接入与配置」这一环带来什么约束
轨道交通装备的结构化数据与固定编码规则，要求模型接入配置需适配字段格式校验，避免生成不符合业务规范的引导内容。实时更新的工单数据需要足够的上下文容纳能力，确保多轮办理流程的连贯性。固定单位与编码规则进一步要求配置时需明确字段匹配逻辑，减少错误输出。同时，轨道交通装备业务数据多在内网部署，模型接入需适配内网访问环境，保障数据流转安全。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 轨道交通装备业务工单包含多轮办理记录、配件明细等长文本，需容纳足够上下文以准确引导流程 |
| `maxTokens` | 2000 token | 业务办理引导需输出清晰步骤，避免过长导致用户混淆，同时适配单轮响应时效 |
| `quoteMaxToken` | 1500 token | 需引用工单、台账等业务文档片段，限制引用长度以保证上下文整洁 |
| `toolChoice` | auto | 业务办理需调用配件查询、进度查询等工具，自动选择工具适配不同办理场景 |
| `temperature` | 0.3–0.5 | 业务办理需准确匹配流程规则，降低随机性以保证引导步骤的一致性 |
| `AIPROXY_API_ENDPOINT` | 内网部署节点的专属API地址 | 轨道交通装备数据多在内网流转，需使用内网端点保障数据安全 |
| `AIPROXY_API_TOKEN` | 部署生成的专属调用令牌 | 验证调用权限，避免未授权访问业务数据 |

## 容易做错的三处
- 现象：模型调用时GPU使用率持续低于30%，CPU单核占用率达100%。原因：未在模型部署环节指定GPU加速，仅使用CPU单线程处理长上下文数据，导致资源分配失衡。
- 现象：业务引导结果中出现不符合装备编码规则的字段值。原因：未配置模型对结构化字段的格式校验，导致生成不符合业务规范的引导内容。
- 现象：触发工具调用后返回空结果。原因：`toolChoice`设置为none，未触发工具调用逻辑，无法获取配件库存、工单进度等实时业务数据。

## 怎么确认配好了
在FastGPT v4.17.0版本中，可通过以下可执行动作核对配置是否生效：
- 提交模拟的轨道交通装备维保工单，查看模型输出的办理步骤是否匹配工单的装备编号、故障类型等字段。
- 查看FastGPT的调用日志，确认模型调用的GPU/CPU资源占比符合预期，无单核100%的异常情况。
- 触发配件查询、工单进度查询等工具调用动作，验证是否能返回正确的业务数据。
- 调整`temperature`参数值，确认输出内容的随机性变化符合预期，无过度偏离业务规则的情况。
