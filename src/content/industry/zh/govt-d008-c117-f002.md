# 通信铁塔与基础设施的业务办理流程引导：向量模型与索引

## 这个品类的数据长什么样
通信铁塔与基础设施的业务数据主要来自运维巡检记录、铁塔基础档案、业务办理申请材料与审批流程文档。数据来源覆盖铁塔的位置、塔高、占地面积等静态档案，以及每日更新的巡检日志、故障报修单、跨部门审批流转单等动态内容。文档结构通常包含铁塔唯一标识、经纬度坐标、办理环节节点、所需材料清单、审批时效等字段，单位涉及米、平方米、次、工作日等。

## 这些特征在「向量模型与索引」这一环带来什么约束
通信铁塔业务数据的静态档案包含带单位的精准坐标与尺寸信息，动态更新的巡检与审批文档则存在长文本、多节点关联的特点。这要求向量建模时需保留字段的单位与业务标识语义，避免因分块截断破坏流程节点的连贯性。大量跨铁塔的业务文档需要增量索引配置，适配每日更新的巡检数据，同时需针对多字段关联的检索需求，优化索引的关联匹配逻辑，避免出现跨铁塔的错误流程匹配。FastGPT v4.17.0的索引模块需适配这类多字段、多类型的文档结构。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 通信铁塔业务文档多包含完整流程节点与巡检细节，该长度可保留单环节的完整语义，避免拆分关键审批条件 |
| 重叠长度 | 150–200 字符 | 避免跨分块的业务节点被截断，保障流程引导时的上下文连贯性 |
| `defaultToken` | 1024 token | 匹配多数通用向量模型的输入上限，适配分块后业务文档的常规长度 |
| `maxToken` | 2048 token | 处理包含多环节审批的长文本分块，防止截断跨节点的关键办理规则 |
| 相似度阈值 | 0.72–0.78，按实测标定 | 区分铁塔唯一标识、业务节点的语义相似度，避免匹配错误的办理流程 |
| 单次搜索上限 | 前8条 | 通信铁塔业务办理的关联节点通常不超过7个，覆盖核心检索结果即可减少冗余信息 |

## 容易做错的三处
- 现象：上传10M以上文件时生成1000+chunk后出现部分chunk向量化异常，反复重试仍无法恢复。原因：未配置`defaultToken`适配长chunk的向量生成，超过模型输入上限导致异常。
- 现象：Ubuntu本地部署ollama后，重启服务器知识库显示未就绪，无法自动完成索引。原因：未开启增量索引的自动触发配置，重启后未加载未完成的索引任务队列。
- 现象：检索结果返回无关的铁塔巡检记录，未匹配到目标办理流程。原因：相似度阈值设置过低，匹配了语义相近但不属于同一业务流程的字段信息。

## 怎么确认配好了
- 上传单份包含铁塔ID、完整审批流程的测试文档，查看分块结果是否保留完整的业务节点，无截断情况。
- 运行向量生成任务，检查系统日志中无`defaultToken`超限报错，所有生成的chunk均显示向量化成功。
- 输入测试查询“XX铁塔的过户办理流程”，核对返回结果包含对应铁塔的审批节点信息，且排序符合业务相关性。
- 模拟服务器重启后，查看知识库状态是否自动变为就绪，无需手动触发索引操作。
