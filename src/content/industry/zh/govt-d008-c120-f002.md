# 铁路运营的业务办理流程引导：向量模型与索引

## 这个品类的数据长什么样
铁路运营的业务办理流程引导数据，主要来自官方票务规则文档、车站办理流程手册、列车运行调整公告及线上线下业务台账。数据更新节奏因内容而异：票务政策类按季度更新，运行图类每半年调整，临时业务通知实时推送。单篇文档多为结构化条目，包含业务编号、办理地点、所需材料、办理时限（单位为工作日）、咨询渠道等字段，部分流程类文档含分步操作说明，文本长度跨度较大。

## 这些特征在「向量模型与索引」这一环带来什么约束
铁路运营数据的文本长度跨度大、字段类型多样且更新节奏不一，对向量索引环节带来多重约束。首先，长短文本混合的场景下，固定分块长度难以适配全部内容，需针对不同文档类型调整分块策略。其次，包含业务编号、车次号等结构化字段的文档，需确保向量索引能区分核心业务实体与说明文本，避免召回无关内容。再者，实时更新的临时通知与低频更新的政策文档，需配置差异化的索引刷新周期，保障数据时效性与检索效率。

## 配置怎么定
仅作参考；请以目标 FastGPT 发布版本与部署文档核验。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配铁路业务文档的结构化条目长度，避免单块内容分散导致检索断裂 |
| 重叠长度 | 50–100 字符 | 保障流程步骤的上下文连贯性，避免分块切断连续的操作说明 |
| maxToken | 8192 | 适配主流向量模型的输入上限，避免超出模型处理范围 |
| 相似度阈值 | 0.72–0.80 | 过滤低匹配度的检索结果，聚焦核心业务流程与材料要求 |
| 单次搜索上限 | 前8条 | 控制检索结果数量，适配业务办理咨询的短平快需求 |
| defaultToken | 200 | 配置默认召回的上下文长度，保障流程说明的完整展示 |

## 容易做错的三处
- 现象：本地部署FastGPT后，检索铁路业务文档时弹出参数配置异常的报错。原因：未正确在环境变量中填写`defaultToken`的对应值，导致向量模型调用时缺少必要的上下文参数。
- 现象：导入铁路业务文档后，检索结果混杂列车时刻表与流程步骤内容。原因：未针对铁路文档的结构化字段设置分块规则，将不同类型的业务数据混合索引，导致召回内容偏离目标。
- 现象：检索业务办理流程时返回的结果条数远少于预期。原因：相似度阈值设置过高，过滤掉了部分匹配度符合业务咨询需求的内容。

## 怎么确认配好了
- 上传单篇铁路业务流程文档，执行检索测试，检查返回结果是否包含目标业务的步骤与材料要求。
- 查看向量索引的刷新日志，确认不同更新频率的文档（如政策类、临时通知类）按预设周期完成索引更新。
- 调用向量模型接口，检查返回的上下文长度是否符合`maxToken`与`defaultToken`的配置取值。
- 调整相似度阈值后，对比检索结果条数的变化，确认阈值配置符合业务检索的精准度需求。
