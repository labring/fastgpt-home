# 铁路运营的业务办理流程引导：知识库检索与召回

## 这个品类的数据长什么样
铁路运营的业务办理数据主要来源于官方运营手册、实时调度公告、窗口办理指引三类文档。数据更新节奏分为固定周期与临时触发：固定线路、常规业务按自然月更新，临时加开列车、站点调整等临时信息按小时同步。文档结构以业务大类为一级目录，每个大类下包含办理步骤、所需材料、时限要求、特殊情况处理四个核心字段，字段单位包含车次号、分钟、人次、证件类型等，单篇文档长度多在800–1500字符之间。

## 这些特征在「知识库检索与召回」这一环带来什么约束
铁路运营数据的多来源、分批次更新特征，要求检索环节支持按业务集合限定检索范围，避免跨业务无关内容干扰。固定与临时混合的更新节奏，要求召回机制支持增量同步与全量刷新两种模式，保障实时信息的时效性。文档的步骤化结构与多字段设计，要求检索匹配同时覆盖关键词与语义信息，避免仅匹配关键词导致的步骤遗漏。单篇文档长度适中的特征，要求分块时保留步骤完整性，避免将完整办理流程拆分为不连贯的片段。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本制定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `similarity` | 0.72–0.80 | 铁路业务办理流程的语义匹配需要较高阈值，过滤掉业务无关的相似内容 |
| `limit` | 前10条 | 铁路业务办理步骤较多，保留足够上下文的同时避免上下文溢出 |
| `searchMode` | 语义+关键词混合 | 兼顾业务流程的固定关键词与用户提问的语义表达 |
| `usingReRank` | 开启 | 对分块召回的结果进行重排，提升高相关性内容的展示优先级 |
| `collectionIds` | 按售票、安检、改签等业务集合指定 | 铁路业务分类明确，限定集合可缩小检索范围，降低响应耗时 |
| `datasetSearchUsingExtensionQuery` | 关闭 | 铁路业务提问多为精准流程咨询，无需额外扩展提问语义 |

## 容易做错的三处
- 现象为单次检索耗时超过6秒，界面显示加载超时提示。原因是未配置`collectionIds`，检索范围覆盖全量业务文档，导致匹配计算量过大。
- 现象为无法在指定的售票业务文件集合中搜索到相关结果。原因是未正确填写`collectionIds`参数，或参数格式不符合系统要求。
- 现象为召回结果包含安检业务的内容，而用户提问仅针对退票流程。原因是`similarity`阈值设置过低，匹配了语义相近但业务无关的文档片段。

## 怎么确认配好了
- 发起一条针对退票业务的提问，查看检索结果是否仅来自退票业务集合，核对`collectionIds`配置是否生效。
- 查看单次检索的耗时数据，确认耗时处于合理区间，验证`limit`与`similarity`的配置是否合理。
- 发起包含流程关键词与语义描述的混合提问，查看重排后的结果排序是否符合业务相关性，验证`usingReRank`是否开启。
- 导入一份临时加开列车的业务指引文档，发起相关提问，确认新文档被成功召回，验证增量更新配置是否生效。
