# 不动产登记的党建学习问答：向量模型与索引

## 这个品类的数据长什么样
本品类的数据来自不动产登记信息系统、地籍调查数据库、房屋交易网签系统、税务系统及电子证照库，更新频率为每日。日常处理的文档包括登记申请书、权属证明、测绘成果、税费凭证、不动产权证书及不动产登记簿，数据字段包含权利人身份信息、不动产坐落位置、权利类型、权属限制状态等，无统一的标准化文本长度，部分测绘成果文档篇幅较长。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配测绘成果、权属证明等较长文档的语义完整性，避免单块内容拆分过度导致语义断裂 |
| 重叠长度 | 100–150 字符 | 保证相邻分块的语义连贯性，防止跨块的关键信息被拆分 |
| `maxToken` | 4096 token | 匹配主流开源向量模型的输入上限，承载党建问答所需的上下文信息 |
| `defaultToken` | 512 token | 设定基础分块的token阈值，平衡单块语义完整性与索引密度 |
| 相似度阈值 | 0.75–0.85 | 保障召回结果与党建学习、不动产登记问题的相关性，过滤低匹配度的无关内容 |
| 单次搜索上限 | 前 10 条 | 限制召回结果数量，避免冗余信息干扰最终问答的准确性 |
| 向量模型选择 | 国产开源向量模型 | 符合国央企场景的合规要求，适配本品类权属信息的语义匹配需求 |

## 容易做错的三处
- 现象：调用ollama接入的向量模型时，FastGPT返回403拒绝访问，但curl测试可正常获取向量结果。原因：未配置正确的向量模型接口访问白名单，或FastGPT的请求头参数未与ollama的验证规则匹配。
- 现象：尝试通过MongoDB直接执行向量库的增删操作后，检索结果出现异常。原因：未启用FastGPT与外部数据库的同步映射机制，直接操作向量库会破坏源数据与向量索引的关联关系。
- 现象：知识库索引合并后仍存在重复的文档条目。原因：分块重叠长度设置不足，或未开启基于文档唯一标识的去重校验，导致同一份源文档的不同分块被重复索引。

## 怎么确认配好了
- 查看FastGPT的向量模型调用日志，确认`defaultToken`和`maxToken`的取值与配置一致。
- 执行一次增量索引测试，验证更新后的源数据是否能同步到向量索引中。
- 检索预设的党建学习相关不动产登记问题，核对召回结果的相似度是否符合设定的阈值范围。
- 执行索引合并操作，检查合并后的索引中是否存在重复的文档条目。
