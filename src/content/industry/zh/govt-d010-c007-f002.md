# 信访事项办理的党建学习问答：向量模型与索引

本文基于FastGPT v4.17.0版本编写。

## 这个品类的数据长什么样
本品类数据来自国家信访信息系统、地方信访系统、12345平台、基层治理平台及历史信访档案，日常文档包含信访登记表、受理告知书、转送交办函、办理意见书、复查复核申请、化解方案等。数据按日更新，单条数据多包含诉求主体、事项详情、办理流程节点、政策依据等字段，部分为结构化表单格式，部分为非结构化文字记录，无统一固定排版。

## 这些特征在「向量模型与索引」这一环带来什么约束
数据来源分散且格式不一，要求索引环节支持多源异构数据的统一向量化适配；按日更新的频率要求配置增量索引机制，避免全量重建占用过多计算资源；单条数据包含流程节点与政策依据，需针对不同字段设置差异化分块规则，确保诉求与政策关联内容被准确拆分；历史档案数据存在非标准化转写内容，需兼容低质量文本的向量化处理，同时需避免重复信访数据的重复索引。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| 分块长度 | 800–1200 字符 | 信访类文档包含结构化表单字段与非结构化流程描述，该区间可平衡语义完整性与索引密度 |
| 重叠长度 | 100–150 字符 | 避免分块后关键政策依据、诉求细节被截断，保障跨块语义关联 |
| `maxToken` | 4096 token | 信访办理意见书、化解方案类文档篇幅较长，需适配大模型上下文承载需求 |
| 相似度阈值 | 0.72–0.85，按实测标定 | 信访诉求表述差异较大，需兼顾召回精准度与历史相似事项覆盖范围 |
| 单次搜索上限 | 前10条 | 信访事项办理需关联多份历史办理记录与政策文件，少量结果不足以支撑完整判断 |
| `defaultToken` | 2048 token | 基础党建学习问答场景下的向量模型输入长度适配，保障短文本向量化效果 |

## 容易做错的三处
- 现象：硬件配置为8核64G内存+RTX2070时，知识库搜索响应缓慢，界面显示超时提示。原因：未针对按日更新的信访数据配置增量索引，全量重建索引占用过多CPU与显卡资源。
- 现象：新增自定义信访数据索引后，检索结果未包含新上传的文档。原因：未开启增量索引同步开关，系统仍使用旧的索引库完成检索。
- 现象：党建学习相关的政策问答无法准确匹配信访诉求。原因：未针对政策文本设置单独的分块规则，导致政策内容与诉求内容的向量表示关联性不足。

## 怎么确认配好了
- 上传1份测试用信访登记表与党建政策文档，查看索引生成进度，确认增量索引同步正常。
- 输入1条信访诉求，检索匹配结果，调整相似度阈值至符合业务判断的区间。
- 测试问答拆分功能，查看拆分后的文本块是否完整保留政策与诉求核心内容。
- 查看向量模型调用日志，确认`maxToken`与`defaultToken`的配置与实际输入长度匹配。
