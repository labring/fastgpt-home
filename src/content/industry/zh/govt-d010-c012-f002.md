# 养老服务机构监管的党建学习问答：向量模型与索引

## 这个品类的数据长什么样
通常，该品类的核心数据来自养老服务信息平台、民政统计系统、消防检查记录与机构运营台账。日常文档包含机构备案材料、运营补贴申请、服务质量检查表、安全隐患整改台账、老人入住档案。数据更新节奏为月度，文档结构多包含机构标识、床位数量、检查结果、整改要求等字段，无统一固定格式，部分文档为结构化表格形式。

## 这些特征在「向量模型与索引」这一环带来什么约束
月度更新的频率决定了索引无需高频实时同步，适合配置定时增量更新任务。结构化表格与多类型文档并存的特征，要求开启多向量支持以分别处理文本与表格字段。机构标识、床位编号等关键字段的精准匹配需求，要求调整相似度阈值避免误召回或漏检。监管场景下的安全与补贴审核要求，需要确保索引召回的文档完整覆盖关联业务数据，避免遗漏关键整改或补贴申请信息。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配养老服务类文档的段落长度，避免切割机构名称、床位数量等关键字段 |
| 重叠长度 | 100–200 字符 | 保留跨块的机构标识、整改编号等跨页关联信息 |
| 相似度阈值 | 0.75–0.85 | 平衡监管场景下的精准召回与漏检风险，避免无关机构数据混入结果 |
| 单次搜索上限 | 前 8 条 | 覆盖同一机构的备案、整改、补贴等多份关联文档 |
| `maxToken` | 4096 token | 适配党建问答的长上下文需求，确保政策原文与监管文档完整召回 |
| `defaultToken` | 按实测标定 | 适配自定义嵌入模型的请求限额，避免调用超限导致索引失败 |

## 容易做错的三处
- 界面显示“检测到没有可用的索引模型”，原因是未在知识库设置中绑定对应嵌入模型，或自定义请求地址、apikey配置错误导致模型调用失败。
- 表格数据无法启用多向量支持，原因是未在向量配置中开启表格多向量解析开关，未针对结构化表格字段单独生成向量。
- 点击嵌入模型测试直接报错，原因是自定义请求地址未指向合规的嵌入服务端点，或apikey权限不足无法调用模型。

## 怎么确认配好了
- 进入知识库的向量模型设置页，确认已选择并绑定目标嵌入模型，测试连接返回成功状态。
- 上传一份养老机构备案材料与整改台账的混合文档，查看分块预览中是否正确保留了机构名称、床位数量等关键字段。
- 发起一次党建学习相关的监管问答测试，查看返回结果中是否包含关联的政策文档与机构运营数据。
- 进入FastGPT v4.17.0的系统状态页，确认索引模型的可用状态为正常。
