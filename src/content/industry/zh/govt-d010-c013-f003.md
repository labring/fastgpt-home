# 内控评价、审计与整改的党建学习问答：多轮对话与提示词

## 这个品类的数据长什么样
本品类的数据主要来自中央企业内控部门、审计部、财务部、下属企业及外部审计机构的业务系统，涵盖内控自评报告、审计通知书、审计工作底稿、问题清单、整改台账、整改销号证明等文档。数据来源包含企业内控系统、ERP、财务共享系统、审计管理系统、采购合同项目系统，更新频率为年度。日常处理中抽取业务样本和凭证、形成审计问题与整改要求、跟踪整改佐证及销号环节耗时占比较高。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据更新频率为年度，意味着多轮对话的上下文无需频繁刷新历史全量数据，可固定调用年度归档数据集。文档结构包含问题清单、整改台账等带明确关联字段的内容，多轮对话需精准匹配上一轮对话的问题与对应整改环节，避免跨年度的无关数据干扰。数据来源分散于多套系统，提示词需明确指定数据源范围，防止跨品类数据混入。抽取样本凭证等环节的耗时特性，要求多轮对话中对历史对话的结论做缓存，减少重复调用底层数据的次数。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本，具体如下：
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 按审计业务批次生成唯一标识 | 确保同批次审计整改的对话上下文连贯，避免跨批次数据混杂 |
| `messages` | 保留最近15–20条对话记录 | 适配审计流程的多轮沟通逻辑，覆盖问题提出、整改反馈、销号确认等关键节点 |
| `variables` | 仅绑定当前应用专属数据集 | 限定数据范围为内控自评报告、审计工作底稿等品类专属文档，防止无关数据干扰 |
| 最大上下文长度 | 8000–12000 字符 | 匹配年度归档文档的总字符量，避免截断关键整改台账与问题清单内容 |
| 历史数据刷新频率 | 按每日凌晨同步 | 匹配年度更新的低频特性，无需高频刷新底层数据 |

## 容易做错的三处
- 现象：对话历史中残留非当前业务批次的记录，无法按指定应用批量清理。原因：未按业务批次生成唯一`chatId`，系统默认保留所有会话记录，导致跨批次数据混杂。
- 现象：多轮对话无法将上一轮的审计问题结论作为下一轮提示词输入，需重复输入核心信息。原因：未启用`messages`历史消息保留配置，未绑定上一轮结论到当前会话变量。
- 现象：对话组件的完成原因字段无法被后续组件引用，无法联动生成整改台账。原因：未将`messages`中的完成原因写入会话变量，导致后续组件无法读取对应字段。

## 怎么确认配好了
- 发起一次包含审计问题与整改要求的多轮对话，检查上下文是否仅保留本次会话的交互内容。
- 查看`variables`配置面板，确认仅绑定了内控自评报告、审计工作底稿等品类专属数据集。
- 生成唯一`chatId`发起新会话，确认历史记录中未出现其他批次的审计数据。
- 测试将上一轮的审计问题结论作为新问题的前置条件，检查对话是否延续该结论展开。
