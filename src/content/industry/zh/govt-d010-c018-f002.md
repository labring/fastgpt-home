# 参保登记与缴费核定的党建学习问答：向量模型与索引

## 这个品类的数据长什么样
典型数据主体为社保经办机构、人社局、税务部门、用人单位人事财务。日常文档包含参保登记表、缴费基数申报表、人员增减表、社保费核定单、个人权益记录。数据来源为社会保险经办系统、税务社保费征收系统、市场主体登记信息、公安民政共享数据。更新频率为每日，核心字段包含人员身份标识、劳动关系状态、缴费基数、人员增减状态、核定缴费金额等，文档以结构化表单为主，搭配少量非结构化说明文本。

## 这些特征在向量模型与索引环节带来什么约束
日更的数据更新要求索引环节支持增量更新，避免全量重建带来的耗时问题。多源异构的数据来源要求索引需适配不同系统的字段格式，需配置跨源字段对齐逻辑。结构化表单占比高的文档，向量分块需保留核心业务字段完整性，避免拆分破坏业务逻辑。高频变动的人员增减数据，需控制索引刷新间隔，保障数据时效性。同时，个人权益记录等敏感数据需配置专属的向量存储隔离规则，保障数据安全。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配参保登记类文档的结构化字段长度，避免拆分破坏人员身份、缴费基数等核心业务字段完整性 |
| 重叠长度 | 100–200 字符 | 保障跨分块的人员增减状态、缴费基数等连续字段的语义连贯性 |
| 相似度阈值 | 0.7–0.8 | 过滤低匹配度的非业务相关检索结果，适配社保数据的字段匹配精度要求 |
| `defaultToken` | 按实测标定 | 适配党建学习问答的上下文长度需求，保障政策解读、业务流程类问题的完整输入 |
| `maxToken` | 4000–6000 token | 匹配社保文档的批量检索上下文长度，避免截断核心业务数据 |
| 单次召回上限 | 前8条 | 平衡检索效率与参保缴费核定所需的多源数据覆盖度 |

## 容易做错的三处
- 创建知识库时文本理解模型下拉框无对应模型：现象为已在模型渠道添加ollama qwen2.5、bge-m3等模型，可用模型列表可见，但文本理解模型下拉框无对应选项。原因是未完成索引模型与文本理解模型的关联绑定，需在模型管理页面完成映射配置。
- 知识库出现重复索引：现象为单文档上传时显示分8段，就绪后变为13段，出现重复分块条目。原因是日更数据的增量索引触发逻辑未过滤临时缓存文件，导致分块重复计算。
- 无法批量重新训练向量模型：现象为仅支持单文件调整参数后重新上传，无批量训练入口。原因是未在系统设置中开启批量向量训练配置开关，需启用对应功能。

## 怎么确认配好了
- 进入模型管理页面，确认索引模型与文本理解模型已完成关联绑定，可在知识库创建页面的下拉框中看到对应模型。
- 上传单份参保登记表，查看分块预览界面，确认分块数量稳定，无重复分块条目。
- 发起党建学习相关的社保政策问答，核对检索结果的匹配度，确认相似度阈值符合业务要求。
- 上传当日更新的人员增减表，查看索引刷新日志，确认增量索引任务正常执行，无超时报错。
