# 市场主体登记与许可的党建学习问答：向量模型与索引

## 这个品类的数据长什么样
本品类的数据包含两类，日常业务文档为设立登记申请书、章程、股东决议、住所证明、营业执照、食品经营许可申请，党建学习问答素材为配套的政策解读与学习要点。数据来源为企业登记全程电子化系统、国家企业信用信息公示系统、电子营业执照系统、住所信息库，更新频率为每日。字段包含主体名称、住所、股东信息、许可类型、党建知识点等。

## 这些特征在「向量模型与索引」这一环带来什么约束
每日更新的业务数据要求索引支持增量同步，避免全量重建带来的资源消耗。多样的文档类型包含结构化证照与非结构化申请文书，需适配不同的分块规则以保留业务完整性。多源数据来自不同系统，需统一向量映射逻辑以确保跨源内容的匹配一致性。党建学习问答需关联业务文档与知识点，索引需支持跨类型内容的混合召回，同时避免业务细节与党建知识点的误匹配。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配登记许可文档的段落长度，避免拆分破坏业务逻辑 |
| 重叠长度 | 50–100 字符 | 保留跨块的上下文关联，便于匹配党建问答的连贯内容 |
| `defaultToken` | 4096 token | 匹配主流嵌入模型的输入上限，适配登记文档与党建素材的总长度 |
| `maxToken` | 8192 token | 支持长文档的完整向量生成，避免截断关键的许可申请材料 |
| 相似度阈值 | 0.75–0.85 按实测标定 | 区分党建问答的知识点与登记许可的业务细节，降低误匹配 |
| 单次搜索上限 | 前 5 条 | 匹配窗口工作人员的快速核验需求，避免信息过载 |

## 容易做错的三处
- 现象：调用知识库接口生成索引后，嵌入模型变为`embedding-3`，原匹配逻辑出现偏差。原因：未锁定嵌入模型配置，默认同步平台更新导致模型变更，未同步调整索引规则。
- 现象：通过OpenAPI创建的QA拆分文件集合，索引召回速度缓慢，单次查询出现超时。原因：未根据登记许可文档的长度调整分块长度与单次搜索上限，单批次处理数据量过大。
- 现象：更换嵌入模型后，已导入的知识库无法直接更新索引，需重新导入所有文件。原因：未执行向量重生成操作，旧向量仍基于原模型生成，未关联新模型的映射规则。

## 怎么确认配好了
- 执行一次测试查询，输入党建学习相关问题，核对返回结果的嵌入模型标识与配置一致。
- 导入单份登记许可文档，检查分块后的片段数量符合预期的分块长度设置。
- 调用知识库搜索接口，确认返回结果的条数不超过单次搜索上限的配置。
- 确认当前使用的FastGPT版本为v4.17.0，查看每日增量索引任务的运行日志无报错。
