# 建设工程质量安全监督的党建学习问答：向量模型与索引

## 这个品类的数据长什么样
本品类涉及住建质安站、施工、监理及建设单位，日常产生监督计划、监督检查记录、隐患整改通知书、质量问题处理单、竣工验收监督报告等文档。数据来源于工程质量安全监管系统、施工现场实名制平台、监理日志、检测报告，更新频率为每周一次。核心数据围绕施工现场监督流程生成，包含现场查验记录、整改闭环信息及验收相关材料，无额外统计类量化字段。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源异构的数据来源要求索引环节支持跨系统格式适配，避免因字段不统一导致嵌入偏差。每周固定更新的特性决定需优先配置增量索引逻辑，减少全量重建的资源消耗。文档围绕施工现场监督流程生成，包含现场查验、整改闭环等强关联内容，分块时需保留业务上下文完整性，避免拆分破坏整改通知书与对应检查记录的关联关系。同时，数据无额外统计类量化字段，需依赖文本语义匹配实现精准检索，且需适配`maxToken`的配置要求以容纳多份文档的拼接内容。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配本品类单份文档的平均字符占比，保留单条监督记录或整改通知书的完整语义 |
| 重叠长度 | 100–150 字符 | 衔接相邻分块的上下文，避免拆分破坏隐患整改相关的流程关联 |
| 相似度阈值 | 0.72–0.78 | 匹配本品类文档的语义相似度特征，过滤低相关的非监督类内容 |
| 单次召回上限 | 前 10 条 | 覆盖单轮党建学习问答所需的监督相关文档数量，避免冗余结果干扰 |
| `maxToken` | 4096 token | 适配党建问答的上下文长度需求，容纳多份监督文档的拼接内容 |
| `defaultToken` | 2048 token | 作为默认嵌入模型的输入长度限制，匹配本品类文档的平均语义单元长度 |

*本文基于FastGPT v4.17.0版本的配置逻辑编写*

## 容易做错的三处
- 索引过程特别慢，现象为后台索引任务日志显示耗时超过30分钟，任务状态长期处于处理中未完成，原因是未配置增量索引逻辑，每次更新均执行全量扫描多源系统的所有数据。
- 创建知识库时文本理解模型下拉框无对应模型，现象为模型渠道已添加ollama qwen2.5语言模型与bge-m3索引模型，但对应环节的下拉列表为空，原因是未将嵌入模型绑定到向量索引配置项，仅完成了语言模型的渠道配置。
- 商业版索引增强与图片自动索引效果未达预期，现象为上传隐患整改通知书的扫描件后，提取的文本存在缺失或错误，原因是未开启针对工程文档图片的OCR增强开关，或未配置图片元数据与文本分块的关联逻辑。

## 怎么确认配好了
- 手动上传1份标准监督检查记录，触发手动索引，查看索引任务的分块日志，确认分块字符数处于800–1200字符区间内。
- 输入党建相关的质量安全监督问题，查看检索结果返回的文档条数，确认符合单次召回上限的配置值。
- 进入模型配置页面，检查向量模型与语言模型的下拉列表，确认已添加的ollama qwen2.5与bge-m3模型均显示在对应环节的选项中。
- 等待1周后触发增量索引任务，查看索引日志，确认仅更新新增的检测报告与监理日志数据，未执行全量重建。
