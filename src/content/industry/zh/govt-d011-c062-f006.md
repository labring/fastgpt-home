# 会议纪要整理的公文辅助：引用来源与溯源

## 这个品类的数据长什么样
会议纪要整理的数据源主要来自线下会议的手写记录、线上会议的录音转写文件、参会人员提交的议题草稿，更新节奏为单次会议完成后生成单份文档，或按周批量处理往期会议归档材料。单份文档的结构通常包含会议主题、召开时间、参会人员清单、讨论议题、决议事项、后续跟进项等字段，字段单位多为整数（如参会人数）、时间单位（如分钟）、字符单位（如议题描述长度），单份文档长度跨度较大，从数百字符到数万字符不等，部分归档的长文档包含多轮讨论的完整记录。

## 这些特征在「引用来源与溯源」这一环带来什么约束
会议纪要的多源特性要求溯源功能同时关联手写记录、录音转写、议题草稿等不同格式的原始数据，需精准匹配字段对应的来源片段。文档长度跨度大的特点要求溯源功能可适配不同长度的上下文，避免长文档截断导致引用不完整。固定的字段结构要求溯源功能需按照预设字段提取对应来源，无法灵活适配无固定结构的自由文本。批量处理的更新节奏要求溯源功能可高效遍历归档的会议文档，快速定位目标引用片段，同时需保证不同批次文档的溯源逻辑统一。

## 配置怎么定
本配置规则适用于FastGPT v4.17.0版本，具体配置项如下：
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | 会议纪要单段核心引用内容通常在500-1000 token，该取值可覆盖大部分核心片段的完整引用 |
| `responseData` | 包含sourceTitle、sourceText、sourceTimestamp | 匹配会议纪要的文档标题、原始文本片段、时间戳等元数据，满足溯源需求 |
| `detail` | 高 | 会议纪要需精准关联原始讨论细节，高detail模式可返回更细粒度的原始来源片段 |
| 单次搜索上限 | 前6条 | 覆盖单次会议的主要讨论分支，避免返回过多冗余的非核心引用 |
| 分块重叠长度 | 150 字符 | 避免会议纪要的跨块讨论内容被分割，确保引用片段的上下文完整 |

## 容易做错的三处
- 返回结果中sourceText字段为空。原因是未正确配置`responseData`参数，未指定需要返回原始文本片段的元数据项。
- 引用片段被过度截断。原因是`quoteMaxToken`取值过小，未覆盖会议纪要核心引用段的完整长度。
- 无法关联到原始会议录音转写的具体时间戳。原因是未在`responseData`中配置包含时间戳的元数据字段，导致溯源仅返回文档标题而无具体位置信息。

## 怎么确认配好了
- 上传一份包含多字段的标准会议纪要测试文件，触发引用溯源功能，检查返回结果是否包含原始文本片段。
- 查看返回的元数据字段，确认包含sourceTitle、sourceText、sourceTimestamp等配置项指定的内容。
- 调整`quoteMaxToken`参数至不同取值，观察返回的引用片段长度是否随配置变化。
- 测试批量上传多份会议归档文档，确认系统可按配置返回对应来源的关联片段。
