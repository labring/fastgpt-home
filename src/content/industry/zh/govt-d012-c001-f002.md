# 12345热线工单办理的内部办公与员工服务：向量模型与索引

## 这个品类的数据长什么样
这个品类的数据主要来自12345热线平台、承办单位业务系统、内部知识库、群众回访评价数据及地方热线管理相关规范。日常处理的文档包含诉求登记单、派单记录、办理答复、回访记录、延期申请、退回说明与知识库条目。数据更新频率为每日，字段通常包含诉求编号、承办主体、诉求内容、办理进度、评价结果等。整体数据围绕群众诉求全流程流转，无固定法定格式，但需匹配各环节的业务流转逻辑。

## 这些特征在「向量模型与索引」这一环带来什么约束
该品类的数据多源分散，包含结构化业务记录与非结构化文本内容，且每日全量更新，要求索引环节需兼容多格式数据接入与增量更新逻辑。诉求相关文档围绕工单全流程流转，字段需关联诉求编号、承办单位等核心标识，因此索引需支持按业务标识进行分组检索，避免跨工单的信息混淆。同时，由于工单办理出错会直接影响群众评价与全流程效率，向量检索的召回范围需覆盖所有关键业务文档，不能遗漏延期、退回等异常环节的记录，确保内部员工可快速调取完整工单背景信息。通过`defaultToken`控制单块文本的token上限，避免单块内容过长导致模型编码失败。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| 分块长度 | 800–1200 字符 | 适配工单文档的单段业务描述长度，避免分块破坏诉求与答复的语义完整性，适配FastGPT v4.17.0版本的分块设置逻辑 |
| 重叠长度 | 100–200 字符 | 保留相邻分块的重叠内容，防止关键业务信息被分块截断，保障检索连贯性 |
| `maxToken` | 8192 | 适配多模态向量模型的输入上限，满足长文档的完整语义传递 |
| `defaultToken` | 2048 | 作为默认分块的最大token限制，平衡检索精度与计算效率 |
| 相似度阈值 | 0.72–0.78 按实测标定 | 过滤低关联的工单记录，避免内部员工被无关信息干扰 |
| 单次召回上限 | 前10条 | 控制单次检索返回的文档数量，适配内部办公的快速查阅需求 |

## 容易做错的三处
- 现象：索引过程耗时过长，单次处理超过30分钟仍未完成。原因：未针对工单数据的每日更新节奏配置增量索引，仍使用全量索引模式，导致每次索引都需遍历全量历史工单文档。
- 现象：在docker-compose部署环境中，新增索引数据源时出现配置项缺失报错。原因：未在docker-compose.yml文件中挂载本地知识库目录或开放向量服务端口，导致平台无法读取外部数据源文件。
- 现象：向量检索的语义匹配精度不足，无法准确区分不同诉求类型的工单内容。原因：未根据工单数据以文本为主的特征选择合适的向量模型，误用多模态向量模型处理纯文本工单数据，导致语义编码效率降低。

## 怎么确认配好了
- 查看向量索引的更新日志，确认每日增量更新任务已按预设周期自动触发。
- 随机选取一条历史工单编号，执行关联文档检索，确认所有该工单的相关业务记录均被纳入检索范围。
- 在部署环境中测试新增一个小型工单数据源，确认索引任务启动后无配置报错。
- 调整相似度阈值的测试参数，确认检索返回的结果条数随阈值调整发生对应变化。
