# 产权、资产与国有资本管理的内部办公与员工服务：多轮对话与提示词

## 这个品类的数据长什么样
本品类的数据来源于国资监管信息系统、企业资产管理系统、产权交易所系统、评估机构报告及财务报表，更新频率为月度。日常处理的文档包括产权登记表、资产评估报告、产权转让方案、进场交易公告、资产处置审批单，字段涵盖资产编号、权属主体、评估基准值、交易状态、审批节点等，单份文档篇幅跨度较大，从数百字符到数千字符不等。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
本品类的数据多源分散、更新周期固定且文档结构差异明显，对多轮对话与提示词配置带来多重约束。首先，多源数据需跨系统整合，多轮对话需准确关联不同来源的业务片段，避免上下文断裂导致的信息偏差。其次，月度更新频率要求知识库同步周期匹配业务数据更新节奏，防止使用过期的资产权属或交易数据。此外，不同文档的字段与格式差异较大，提示词需明确指定各文档的处理规则，确保LLM能正确识别资产编号、权属主体等核心业务字段。最后，核心业务环节的核对需求，要求多轮对话能逐步引导用户补充或验证关键数据，避免遗漏影响交易合规性的信息。

## 配置怎么定
本文适配FastGPT v4.17.0版本，以下为针对本品类的多轮对话与提示词配置建议：
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 8000–12000 token | 产权转让方案、资产评估报告等单份文档长度较长，需覆盖多轮对话的历史交互与关联业务数据 |
| 历史记录保存周期 | 30 天 | 匹配业务数据月度更新频率，避免过期数据干扰后续对话 |
| 单次召回文档数 | 前5条 | 匹配国资管理场景下的核心资产数据量，避免过多冗余信息干扰LLM推理 |
| `messages` 字段格式 | 按角色与时间戳排序 | 确保多轮对话的上下文逻辑清晰，便于LLM准确关联历史交互内容 |
| `variables` 调用规则 | 仅在触发知识库搜索后注入 | 确保提示词仅调用已验证的业务数据，减少无效输出 |
| `chatId` 持久化配置 | 绑定部门权限范围 | 符合国资管理的保密要求，限制跨部门的对话数据访问 |

## 容易做错的三处
- 无法在MongoDB中查看对话历史记录。原因是未配置`chatId`的持久化存储规则，或存储路径未匹配业务系统的权限管控要求。
- 知识库搜索在工作流调试正常，但AI对话中未参考知识库内容。原因是`messages`字段未正确携带知识库召回的上下文片段，或提示词未明确指定关联业务文档的规则。
- 无法将程序执行结果作为背景知识输入到下一个AI对话模块。原因是未通过`variables`将执行结果绑定到当前会话上下文，或未在提示词中声明引用该变量的格式。

## 怎么确认配好了
- 发起包含资产编号的多轮对话，检查`messages`字段是否按时间顺序记录所有交互内容，且包含关联的业务文档片段。
- 触发知识库搜索后，查看会话上下文是否包含对应品类的核心文档片段，如产权登记表或资产评估报告内容。
- 配置`variables`注入规则后，发起测试对话，验证LLM是否正确引用了预设的业务变量内容。
- 等待30天后，检索历史对话记录，确认记录仍可正常访问，匹配配置的保存周期。
