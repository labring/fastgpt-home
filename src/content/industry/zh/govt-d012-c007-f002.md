# 信访事项办理的内部办公与员工服务：向量模型与索引

## 这个品类的数据长什么样
这个品类的核心数据来自国家信访信息系统、地方信访系统、12345平台、基层治理平台及历史信访档案，更新频率为每日。日常处理的文档包括信访登记表、受理告知书、转送交办函、办理意见书、复查复核申请、化解方案，各文档包含诉求编号、办理主体、诉求内容、办理进度、复查状态等固定字段，覆盖从诉求提交到办结复核的全流程环节。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源异构的数据来源要求索引需支持不同系统导出格式的统一映射；日更的更新频率要求配置适配增量索引规则，避免重复处理全量数据；多样的文档类型需匹配不同长度的分块逻辑，防止割裂办理流程的上下文关联；信访事项的法定办理要求，需将受理范围、复查状态等关键字段纳入索引嵌入范围，确保搜索结果可支撑受理甄别与决策；数十万级的数据体量要求向量库的索引性能适配日常办公的搜索响应需求。

| ---- | ---- | ---- |

| `defaultToken` | `2048` | 匹配日常信访诉求文本的平均token占比，保障基础嵌入任务的稳定执行 |
| 分块长度 | `800–1200 字符` | 适配信访登记表、办理意见书等核心文档的信息完整性，避免单块内容过于零散 |
| 重叠长度 | `50–100 字符` | 保留跨分块的办理流程上下文，防止割裂转送交办函与后续办理意见的关联逻辑 |
| 相似度阈值 | `0.75–0.85` | 精准甄别信访受理范围，避免召回无关的历史信访数据引发重复信访 |
| 单次搜索上限 | `前10条` | 适配基层办公人员的信息查看负荷，避免返回过多冗余结果 |

## 容易做错的三处
- 现象：PGSQL向量库执行搜索时返回`query timeout`报错，状态码为504。原因：未针对日更的数十万条信访数据配置增量索引，全量索引的单次处理量超出`defaultToken`的处理上限。
- 现象：搜索结果无法准确甄别信访受理范围，返回大量非信访类诉求数据。原因：未将信访登记表中的诉求类型字段纳入索引嵌入范围，导致模型无法识别受理边界。
- 现象：部分复查复核申请的搜索结果未关联到原办理意见书。原因：分块重叠长度设置过小，未保留跨文档的诉求编号关联字段，导致上下文割裂。

## 怎么确认配好了
- 查看向量索引的字段映射配置，确认已包含信访登记表、办理意见书等核心文档的诉求编号、办理主体、诉求内容字段。
- 执行单条信访登记表的搜索测试，验证结果能准确匹配同诉求编号的办理意见书。
- 检查增量索引的触发日志，确认每日自动完成新增数据的索引更新。
- 调整相似度阈值，验证不同阈值下的召回结果符合信访受理甄别需求。
