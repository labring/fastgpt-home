# 公路养护与路产路权管理的内部办公与员工服务：多轮对话与提示词

## 这个品类的数据长什么样
该品类的日常数据主要来自公路养护管理系统、桥隧监测系统、路政巡查系统与交通流量监测数据，更新频率为每日。常见文档包含养护计划、巡查日志、病害处置单、涉路施工许可、路产损坏赔偿单，文档内包含路段标识、病害类型、处置流程编号、许可编号、赔偿金额等字段，单位涉及公里、平方米、工作日等。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
每日更新的数据要求多轮对话能够实时拉取最新的巡查、监测数据，避免使用过时信息。多类业务文档的存在，要求提示词能够区分养护、路政、许可等不同场景的上下文，精准匹配对应文档。文档内的固定字段较多，要求多轮对话能够准确提取字段信息，避免遗漏关键内容。同时，业务操作出错可能引发道路安全隐患或资金争议，要求提示词生成的内容需符合合规要求，不得生成超出权限的信息。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `chatId` | 绑定养护工单唯一编号 | 依据FastGPT v4.17.0的会话管理规则，通过工单编号区分不同会话上下文，避免跨工单的信息混淆 |
| `messages` | 保留前20轮对话内容 | 依据养护流程从巡查到验收的多步骤衔接需求，覆盖完整对话链路，确保上下文连贯 |
| `variables` | 预设路段编号、养护周期字段 | 依据日常文档的固定字段，减少重复输入，提升对话效率 |
| 单次搜索上限 | 前8条 | 依据单轮对话需覆盖的巡查、许可等多类文档的合理条数，避免信息过载 |
| 最大上下文长度 | 8000–12000 token | 按实测标定，适配多类文档的上下文拼接需求，避免内容截断 |
| 问题优化 | 开启 | 依据巡查日志等文本的专业术语较多的特点，优化用户提问的识别精度 |

## 容易做错的三处
- 现象：多轮对话返回的结果中出现未关联当前工单的巡查日志，原因：未通过`chatId`绑定对应工单编号，导致会话上下文调用了其他工单的文档
- 现象：系统提示词被截断，导致生成的回复遗漏关键要求，原因：未设置合理的最大上下文长度，系统提示词与对话上下文拼接后超出缓存上限
- 现象：对话调用的文档包含未授权的路产损坏赔偿细节，原因：未通过`variables`限定业务权限范围，导致上下文调用了超出角色的文档

## 怎么确认配好了
- 发起包含指定路段编号的提问，核对返回结果中是否包含对应路段的最新巡查日志
- 发起多轮连续提问，核对`chatId`绑定的工单编号是否始终一致，上下文未出现跨工单混淆
- 调整`messages`保留轮次，测试会话缓存是否在设定范围内，未出现溢出报错
- 触发完整提示词校验，核对生成的回复是否包含预设的`variables`字段要求
