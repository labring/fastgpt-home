# 参保登记与缴费核定的内部办公与员工服务：向量模型与索引

## 这个品类的数据长什么样
本品类数据来自社会保险经办系统、税务社保费征收系统、市场主体登记信息及公安民政数据共享，更新频率为每日。日常处理的文档包含参保登记表、缴费基数申报表、人员增减表、社保费核定单、个人权益记录，数据字段涵盖单位统一社会信用代码、人员身份标识、缴费核定基数、参保状态、核定单编号等，数据多为结构化导出的文本或表格格式，单条数据体量相对固定。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源异构的数据来源要求向量模型需适配不同格式的文档分块，避免破坏人员身份、缴费基数等关键结构化字段的完整性。日更的更新频率要求索引配置支持增量同步机制，避免全量索引更新占用过多系统资源。字段包含精准的身份与缴费参数，要求向量召回需兼顾语义匹配与字段关联的约束，防止低匹配度的无关数据进入内部办公流程。批量的结构化文档要求索引分片配置适配批量检索需求，保障内部办公的响应效率。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| 分块长度 | 800–1200 字符 | 适配参保登记表、缴费核定单等文档的结构化段落长度，避免分块破坏关键字段的完整性 |
| 重叠长度 | 100–200 字符 | 保障跨分块的人员身份、缴费明细等关键信息的语义连贯性 |
| 相似度阈值 | 0.85–0.95 | 需精准匹配人员身份与缴费参数，防止低匹配度的无关数据进入办公流程 |
| 单次搜索上限 | 前 10 条 | 适配内部办公快速定位核心文档的需求，避免过多结果增加人工核对成本 |
| `defaultToken` | 2000 token | 适配单批次核定单据的上下文长度，保障检索结果完整带入员工办公流程 |
| `maxToken` | 8000 token | 覆盖多份关联文档的拼接需求，满足人员增减与缴费对账的上下文整合 |

## 容易做错的三处
- 现象：向量检索结果中未包含图片形式的参保凭证，或图片无法被正常召回。原因：未配置多模态向量化与检索的关联设置，仅对文本数据生成了向量索引，未同步处理图片格式的参保资料。
- 现象：重复发起人员身份核对查询时，系统每次都触发向量数据库检索，无缓存复用。原因：未配置查询缓存机制，重复请求未被拦截，增加了向量数据库的负载压力。
- 现象：调用创建训练订单接口后，集合添加的参保数据未生成对应向量索引。原因：混淆了训练订单与集合数据添加的流程，训练订单用于批量数据的向量化调度，集合添加仅完成单条数据上传，未触发关联的向量化任务。

## 怎么确认配好了
- 查看 FastGPT v4.17.0 版本的索引更新日志，确认每日增量同步任务正常触发，无失败记录。
- 发起两次相同的人员身份查询请求，确认第二次请求的响应时间符合预期，无额外向量数据库调用开销。
- 上传一份参保登记表与对应缴费核定单，验证创建训练订单后，集合数据可正常生成向量索引并被检索到。
- 上传图片格式的参保凭证，验证检索结果可正常返回关联的文本与图片数据。
