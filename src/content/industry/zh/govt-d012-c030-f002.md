# 建设工程质量安全监督的内部办公与员工服务：向量模型与索引

## 这个品类的数据长什么样
本品类数据主要来自工程质量安全监管系统、施工现场实名制平台、监理日志、检测报告。日常生成的文档包括监督计划、监督检查记录、隐患整改通知书、质量问题处理单、竣工验收监督报告。数据更新频率为每周一次，单份文档包含监督主体标识、隐患等级描述、整改要求、验收状态等字段，无统一固定单位，字段随文档类型动态调整。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源异构的数据来源要求索引环节支持批量导入不同格式的文档，避免格式转换损耗。每周一次的更新频率允许采用增量索引策略，减少全量重建的资源消耗。多样的文档类型包含长文本检查记录与短文本整改通知书，需要适配不同的分块规则，避免语义割裂。数十万级的文档体量要求索引采用合理的分片策略，保障检索响应速度。同时，检索结果直接关联隐患整改与验收环节，需要保障检索的召回准确性，避免遗漏关键信息引发质量或安全事故。

## 配置怎么定
本配置基于 FastGPT v4.17.0 版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配监督检查记录、监理日志等长文本的语义完整性 |
| 重叠长度 | 100–200 字符 | 弥补分块导致的语义断层，保障跨块隐患描述的关联 |
| 相似度阈值 | 0.75–0.85 | 匹配关键文档的语义匹配精度，避免误召回或漏召回 |
| 单次搜索上限 | 前 10 条 | 适配内部办公快速检索需求，减少冗余结果 |
| `maxToken` | 4096 token | 适配长文档的向量编码上限，保障完整语义嵌入 |
| 问题优化 | 开启 | 优化员工查询表述，提升检索匹配效果 |

## 容易做错的三处
- 搜索响应超时，界面显示加载超过30秒。原因是未针对数十万级的监督类文档调整索引分片策略，导致向量检索时的遍历范围过大。
- 调用知识库时弹出向量模型调用失败的报错弹窗，且配置文件中已添加text-embedding-ada-002模型。原因是未将配置的向量模型正确关联至FastGPT的向量库渠道，或第三方调用渠道未开放该模型的调用权限。
- 增量索引未生效，新增的隐患整改通知书未被检索到。原因是未按照每周一次的更新频率配置增量索引触发规则，误设置为高频更新导致资源占用过高。

## 怎么确认配好了
- 导入单份监督计划文档，执行向量编码，查看任务日志中是否正常完成编码且无`maxToken`超限提示。
- 发起针对特定隐患类型的检索请求，核对返回结果的条数符合单次搜索上限的配置规则。
- 新增一份测试用的质量问题处理单，触发增量索引，等待配置的更新周期后执行检索，确认测试文档被正常召回。
- 查看向量库的索引统计信息，确认分片数量适配当前文档的总规模。
