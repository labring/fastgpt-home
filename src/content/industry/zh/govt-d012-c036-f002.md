# 政务服务事项目录与办事指南维护的内部办公与员工服务：向量模型与索引

本文档基于FastGPT v4.17.0版本编写。

## 这个品类的数据长什么样
该品类的核心数据来源于国家政务服务事项基本目录、行政许可事项清单、权责清单及地方政务服务事项库，日常维护的文档涵盖政务服务事项基本目录、实施清单、办事指南、标准材料目录、流程图与常见问题。数据更新周期为月度，单条事项通常包含事项名称、实施主体、受理条件、申请材料、办理流程等结构化字段，部分配套文档为非结构化的流程说明或常见问答文本。

## 这些特征在「向量模型与索引」这一环带来什么约束
月度更新的批量数据要求索引流程支持增量同步，避免全量重建带来的资源消耗。结构化与非结构化混合的数据类型，需要向量模型同时适配事项字段文本与自由问答内容的语义对齐。事项各字段间存在强业务关联，如受理条件与申请材料绑定，索引时需保留字段关联信息，避免语义割裂。数十万条级别的数据量，需要索引结构平衡召回精度与查询速度，同时适配PGSQL向量库的存储与检索特性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配政务事项字段与配套文档的文本长度，避免单块语义断裂 |
| 重叠长度 | 100–200 字符 | 保留相邻分块的语义关联，防止跨块业务信息丢失 |
| 相似度阈值 | 0.75–0.85 | 过滤低相关性召回结果，适配政务事项的强语义匹配需求 |
| 单次召回上限 | 前 20 条 | 平衡查询速度与召回覆盖范围，满足内部办公的批量校验场景 |
| `defaultToken` | 8192 | 适配当前主流向量模型的最大输入限制 |
| `maxToken` | 16384 | 适配长文本事项的向量生成需求 |

## 容易做错的三处
- 界面显示搜索耗时过长，误将性能瓶颈归因为向量模型。原因：未区分向量检索与大语言模型整合结果的耗时环节，政务事项的长文本向量召回后，大语言模型需拼接多块语义内容导致延迟。
- 调用知识库时弹出“无可使用的embedding模型”报错。原因：未将text-embedding-ada-002模型正确添加到API渠道，或配置文件中未配置对应模型的调用参数。
- 批量索引数据后，部分事项的检索结果与原文语义偏差较大。原因：分块长度设置过大导致单块内语义断裂，或重叠长度不足，丢失跨块业务关联信息。

## 怎么确认配好了
- 导入单条完整的政务办事指南文档，查看向量生成日志，确认`defaultToken`与`maxToken`的取值适配当前使用的向量模型。
- 针对特定受理条件发起查询，核对召回结果的匹配度，调整相似度阈值至符合业务校验要求。
- 触发一次增量数据同步，检查索引任务日志，确认月度更新的增量同步流程正常运行。
- 批量导入测试数据，验证单次召回上限的设置能够满足内部校验的结果数量需求。
