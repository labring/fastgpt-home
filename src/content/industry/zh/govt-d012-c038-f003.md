# 政府采购项目的内部办公与员工服务：多轮对话与提示词

## 这个品类的数据长什么样
本品类数据来源包括中国政府采购网、地方政府采购网、财政一体化系统、采购人预算系统及供应商信用记录，更新频率为每日。日常处理的文档涵盖采购需求、采购计划、招标文件、投标文件、评标报告、中标公告、采购合同、质疑答复等，对应采购人单位、财政部门政府采购监管处、采购代理机构、评审专家等主体的不同业务环节，数据字段围绕采购流程全环节设置，包含项目编号、供应商资质、评审结果等核心信息。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
每日更新的数据源要求对话上下文需同步最新的中标公告、质疑答复等动态信息，避免使用过期数据。多类文档的差异化结构要求提示词需适配不同业务场景，例如编制采购需求时需调用对应预算相关数据，核对供应商资质时需调取信用记录。业务环节的高出错风险要求多轮对话需精准承接历史查询，确保资质核对、质疑处理等环节的上下文连贯。同时，数据来源分散的特点要求对话需支持按项目标签精准召回对应文档，避免跨项目数据混淆。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定采购项目唯一标识作为固定值 | 确保多轮对话的上下文仅属于对应采购项目，避免跨项目会话混淆，符合FastGPT v4.17.0的会话管理规范 |
| `messages` | 按对话轮次保留前10–15轮上下文，单轮内容不超过2000字符 | 政府采购相关文档篇幅较长，过长上下文会增加推理延迟，保留核心历史对话可确保业务查询的连贯性 |
| `variables` | 绑定采购项目专属标签变量，如`[采购项目编号]`、`[供应商信用等级]` | 精准匹配对应项目的采购需求、投标文件等数据，避免跨项目调用无关文档，提升召回准确性 |
| 最大上下文 | 8000–12000 token | 覆盖完整的采购计划、评标报告等核心文档内容，同时控制推理开销，适配政府采购场景的文档长度 |
| 单次搜索上限 | 前6条 | 政府采购相关数据条目较多，过多结果会分散注意力，前6条可覆盖核心的中标公告、资格审查记录等业务所需内容 |
| 问题优化 | 按实测标定 | 政府采购场景提问多涉及专业术语，需结合实际业务场景调整优化规则，确保返回内容符合行业规范 |

## 容易做错的三处
- 调用`chat/completions`接口时返回400状态码，原因：未正确配置`messages`参数的角色与内容格式，或未绑定对应政府采购项目的知识库标签变量。
- 对话无法召回指定类别的政府采购文档，原因：未在请求中指定正确的知识库标签参数，或未在`variables`中配置项目专属标签，导致召回范围覆盖无关项目数据。
- 对话上下文丢失，无法承接上一轮的采购需求查询，原因：未正确设置`chatId`为固定的采购项目标识，导致每次请求生成新的会话上下文，丢失历史业务信息。

## 怎么确认配好了
- 发起包含采购项目编号的查询，核对返回结果是否仅包含对应项目的招标文件、中标公告等文档，无跨项目无关内容。
- 连续发起3轮关联提问，核对`messages`参数是否保留了历史对话的关键内容，未出现上下文丢失或跳转错误。
- 提交包含政府采购专业术语的提示词，核对返回结果是否符合相关文档的格式与内容要求，无逻辑偏差。
- 调用接口时检查返回的状态码是否为200，无参数格式错误提示，确保`chatId`、`messages`、`variables`等参数配置正确。
