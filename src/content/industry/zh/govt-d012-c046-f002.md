# 社会救助与低保审核的内部办公与员工服务：向量模型与索引

本文基于FastGPT v4.17.0版本的配置逻辑编写。

## 这个品类的数据长什么样
这个品类的核心数据来自民政局救助科、街道乡镇民政办、社区居委会、核对中心等主体的日常办公与业务系统，包含低保申请表、家庭经济状况核对报告、入户调查表、民主评议记录、公示材料、救助审批表等文档。数据主要来源于低收入人口动态监测平台、居民家庭经济状况核对系统，以及公安、人社、医保、住建、税务等跨部门共享数据，更新频率为月度。数据核心围绕家庭经济状况、成员关系、救助资格展开，涵盖结构化字段与非结构化佐证材料。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源跨部门的数据来源导致文档格式异构，需要索引配置适配不同类型的业务文档；月度更新的频率要求索引支持定期全量或增量更新的调度机制；核心数据涉及家庭收入、财产等敏感信息，索引的存储与调用需符合数据安全规范；不同文档的长度差异较大，从短表单到长报告均有覆盖，分块与召回策略需兼顾上下文完整性与检索效率；出错后果直接关联错保漏保与群众信访，因此索引召回的准确性需严格匹配业务判定逻辑。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配品类内典型文档的内容密度，平衡上下文完整性与检索精度 |
| 重叠长度 | 100–150 字符 | 避免跨块关键信息（如家庭成员关系、收入明细）被截断 |
| 相似度阈值 | 0.72–0.80 | 适配低保审核场景下的资格判定关联度要求，按实测标定 |
| `maxToken` | 8000 token | 覆盖单份审批材料的完整上下文，满足审核逻辑的上下文调用需求 |
| 单次搜索上限 | 前10条 | 平衡检索效率与召回覆盖度，避免过多无关数据干扰审核 |
| `defaultToken` | 4096 token | 适配日常检索的基础上下文长度，降低模型调用的资源消耗 |

## 容易做错的三处
- 导出索引数据时仅能获取整体知识库的文件，无法按业务分类（如低保申请、核对报告）单独导出。原因：未针对品类内多分类文档配置分层知识库目录，仅按整体知识库设置导出粒度。
- 外接向量模型后，arm软路由部署出现推理超时或卡顿。原因：未根据品类数据量调整`defaultToken`参数，或未限制单次检索的最大上下文长度。
- 导入飞书多维文档后，表格内的家庭收入字段无法被正确索引。原因：未开启针对结构化文档的解析开关，导致表格字段未被提取为可索引文本。

## 怎么确认配好了
- 执行一次全量索引任务，查看索引进度日志中是否显示所有品类内的文档类型被成功解析。
- 输入一条模拟的家庭收入或成员关系查询，核对检索结果的条数与匹配度是否符合预设的相似度阈值规则。
- 测试外接模型的调用链路，验证在目标架构设备上的响应时长是否符合业务运行要求。
- 导出指定业务分类的索引数据，确认导出文件包含对应品类的文档内容。
