# 行政处罚案卷办理的内部办公与员工服务：向量模型与索引

## 这个品类的数据长什么样
这个品类的数据主要来自行政执法办案系统、执法记录仪影像、国家企业信用信息公示系统及部门监管数据库，更新频率为每日。日常处理的文档包含现场检查笔录、询问笔录、证据清单、行政处罚事先告知书、听证告知书、处罚决定书、送达回证。单条案卷数据包含统一办案编号、执法主体信息、违法事实记录、裁量适用依据、最终处罚决定及各类文书附件，字段多关联执法流程节点，无统一跨部门通用格式。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源混合的数据来源要求向量模型适配不同格式的文本转录内容，包括执法记录仪的口语化记录与结构化文书文本。每日批量更新的特性要求索引支持增量构建，避免全量重建占用过多系统资源。案卷数据关联多份流程文书，索引需按办案编号进行分组关联，避免跨案卷的语义干扰。不同文书的语义重要性差异显著，处罚决定书与询问笔录的核心信息权重高于送达回证，需要针对性调整分块与检索规则。

## 配置怎么定
向量模型与索引环节的核心配置项包括`maxToken`、`defaultToken`等，以下为针对本品类的具体配置建议：

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| maxToken | 8192 token | 适配主流嵌入模型的输入上限，覆盖单份处罚决定书的常规文本长度 |
| 分块长度 | 800–1200 字符 | 匹配现场检查笔录、询问笔录的单页文本长度，避免语义断裂影响检索精度 |
| 重叠长度 | 100–200 字符 | 保留跨分块的执法流程关联信息，确保证据链的语义完整性 |
| 相似度阈值 | 按实测标定 | 需结合执法场景的语义匹配精度调整，适配违法事实、处罚依据的精准检索需求 |
| 单次搜索上限 | 前10条 | 匹配内部办公中法制审核环节的常规查阅量，避免过多冗余结果干扰审核效率 |
| defaultToken | 4096 token | 作为默认分块的基础单位，平衡语义完整性与检索响应速度 |

仅作参考；请以目标 FastGPT 发布版本与部署文档核验。

## 容易做错的三处
- 现象：更换嵌入模型后，界面显示知识库索引状态未更新，手动触发重建无响应。原因：未使用平台提供的批量索引重建功能，仍尝试逐个重新导入文档，导致索引未同步更新。
- 现象：配置非ada 002的嵌入模型时，弹出undefined model报错弹窗。原因：未在平台配置对应模型的API访问权限，或模型名称格式不符合平台校验规则。
- 现象：语义检索分数很高但结果未命中核心违法事实。原因：未针对笔录类文档调整分块规则，导致分块后丢失关键执法细节，语义匹配出现偏差。

## 怎么确认配好了
- 上传单份完整的处罚决定书，检查分块后的文本是否保留完整的违法事实与处罚依据，无明显语义断裂。
- 更换嵌入模型后，触发批量索引重建操作，确认索引进度条正常更新且无报错日志。
- 输入典型违法事实关键词，检查搜索结果的排序是否符合业务逻辑，核心案卷优先展示。
- 查看平台索引日志，确认无模型调用失败、分块异常或权限报错提示。
