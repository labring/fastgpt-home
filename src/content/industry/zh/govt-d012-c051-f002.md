# 道路运输经营许可的内部办公与员工服务：向量模型与索引

## 这个品类的数据长什么样
本品类涉及的主体包括交通运输局审批科、道路运输管理机构及运输企业，日常产生和处理的文档涵盖经营许可申请、车辆技术档案、驾驶员从业资格材料、安全生产管理制度、道路运输经营许可证等。数据主要来源于道路运政管理系统、全国道路运输车辆动态信息公共服务平台、车辆和从业人员数据库，更新频率为每日。单份文档包含主体资质、车辆参数、人员资质、安全规范等结构化字段与非结构化文本内容，字段多与道路运输经营资质相关，无跨品类通用的标准化字段单位。

## 这些特征在「向量模型与索引」这一环带来什么约束
每日更新的业务数据要求向量索引支持增量更新机制，避免全量重建占用过多计算资源。多类型文档混合存储，包括结构化表单、非合规文本等，要求索引可区分不同文档的业务属性，减少跨类型匹配的干扰。不同来源的数据格式差异较大，需向量模型适配多样的文本编码逻辑，确保不同文档的特征提取一致性。审批环节对数据准确性要求高，索引召回结果需关联原始文档的完整路径，方便后续核验追溯，避免出现许可被退回的情况。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本制定。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配道路运输类文档的平均段落长度，避免单块包含过多无关业务内容 |
| 重叠长度 | 100–150 字符 | 确保车辆号牌、驾驶员编号等关键信息不会被分块截断，保留上下文连贯性 |
| 相似度阈值 | 0.75–0.85 按实测标定 | 匹配道路运输审批材料的语义相似度要求，过滤低相关性的召回结果 |
| 单次搜索上限 | 前 6 条 | 适配审批环节的核验信息量，避免过多结果增加审核人员的负担 |
| `maxToken` | 4000 token | 匹配主流大模型的上下文窗口上限，承载召回的文档文本与查询内容 |
| `defaultToken` | 2000 token | 作为默认的单轮交互上下文长度，平衡信息完整性与响应速度 |

## 容易做错的三处
- 现象：界面中向量模型选项为空或无法选中，提交配置后报错“未选择有效索引模型”。原因：未正确配置本地向量模型的部署路径，或FastGPT未完成向量模型的容器挂载与初始化。
- 现象：召回的文本块未关联原始文档的来源信息，无法在回答中展示文档出处。原因：未开启“保留文档元数据”的配置项，或分块时未同步提取文档的路径、名称等元字段。
- 现象：部署DeepSeek相关模型后，向量召回结果不符合预期，或无法完成增量索引更新。原因：未将每日更新的道路运政系统数据转换为统一的文本格式，导致向量模型无法正确编码特征。

## 怎么确认配好了
- 上传一份典型的道路运输经营许可申请文档，执行分块与索引操作，查看分块结果是否符合预设的长度与重叠设置。
- 发起与道路运输审批相关的查询，核对召回结果的数量是否符合单次搜索上限的配置，且关联了原始文档的元数据。
- 测试增量更新功能，上传一份新的车辆技术档案数据，确认索引能自动识别新增内容并完成更新。
- 查看FastGPT的系统日志，确认向量模型的调用与索引构建过程无报错信息。
