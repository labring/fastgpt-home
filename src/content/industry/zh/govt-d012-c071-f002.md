# 发电集团的内部办公与员工服务：向量模型与索引

## 这个品类的数据长什么样
发电集团内部办公与员工服务的数据来源涵盖OA系统、报修工单平台、内部培训文档库、会议纪要系统及考勤统计模块。数据更新节奏存在差异：工单与咨询记录为工作日实时更新，培训材料与手册按周更新，考勤统计与月度报表按月更新。文档结构包含结构化字段（如员工工号、部门、服务类型）与非结构化文本（如问题描述、处理流程、会议内容），字段单位多为条、人次、小时。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源异构的数据来源要求向量模型需兼容不同格式的文本与元数据，避免嵌入时丢失结构化字段的关联信息。实时更新的工单与咨询记录，要求索引支持增量同步，降低系统资源占用。混合长短文本的文档结构，要求分块策略需兼顾短咨询的精准匹配与长文档的上下文保留。字段丰富的元数据，要求索引需支持按部门、服务类型等字段过滤召回结果，缩小搜索范围。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配发电集团内部办公文档的平均长度，保留上下文且避免分块过碎 |
| 重叠长度 | 100–200 字符 | 避免分块边界丢失关键关联信息，适配短咨询与长文档混合场景 |
| `defaultToken` | 按实测标定 | 匹配自建嵌入模型的访问凭证要求，避免令牌无效报错，适配FastGPT v4.17.0版本的配置逻辑 |
| 单次搜索上限 | 前8条 | 内部办公咨询多为常见问题，少量召回即可覆盖核心解决方案 |
| 重排 | 开启 | 过滤无关召回结果，提升员工服务的匹配精准度 |
| 最大上下文 | 4000–6000 字符 | 适配长文档的召回内容长度，保证对话上下文的完整性 |

## 容易做错的三处
- 界面返回“无可用渠道”报错，原因：未正确绑定自建嵌入模型的访问凭证，或`defaultToken`配置为空。
- 知识库搜索响应时长超过20秒，原因：分块长度设置过大，且未启用索引分片优化，导致硬件资源占用过高。
- 嵌入后的文本丢失末尾的工单处理记录字段，原因：`maxToken`取值小于模型支持的最大上下文长度，导致长文本被截断。

## 怎么确认配好了
- 上传一份真实的内部工单文档，检查分块后的文本未丢失员工工号、处理流程等关键字段信息。
- 发起一条员工常见咨询，查看召回结果的条数符合单次搜索上限的配置。
- 查看嵌入任务的运行日志，确认`defaultToken`已被正确加载，无令牌无效报错。
- 提交一条新增的报修工单，等待1分钟后发起相关咨询，确认召回结果包含该工单的最新内容。
