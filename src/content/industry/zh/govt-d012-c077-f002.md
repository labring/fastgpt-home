# 城市公交的内部办公与员工服务：向量模型与索引

## 这个品类的数据长什么样
城市公交内部办公与员工服务的数据主要来自内部排班系统、场站运维日志、员工岗位手册与票务结算系统。排班数据按周更新，运维日志实时生成，员工手册为静态文档，票务数据按日同步。文档结构分为结构化表格（如排班表含线路编号、班次时段、司机工号）、半结构化日志（如故障记录含场站ID、故障类型、处理时长）与纯文本规范（如应急处置流程）。字段包含运营里程、班次频次、工号等，单位多为公里、小时、班次。

## 这些特征在「向量模型与索引」这一环带来什么约束
结构化数据占比高且字段关联紧密，要求索引时保留字段级元数据，避免分块破坏业务关联；实时生成的运维日志需要配置增量索引逻辑，降低全量同步的资源消耗；文档长度跨度大，短则数十字符的故障记录，长则数千字的应急流程，要求分块策略适配不同文本长度；票务结算与排班数据的更新频率差异明显，需区分全量与增量索引的触发时机，避免资源浪费。部分字段存在固定单位，索引时可通过元数据标记辅助向量匹配，提升检索精度。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| 分块长度 | 800–1200 字符 | 适配公交文档长度跨度大的特征，兼顾短故障日志与长应急流程的分块合理性 |
| 重叠长度 | 100–150 字符 | 避免跨分块的业务逻辑被割裂，保障排班、运维流程的上下文完整性 |
| 相似度阈值 | 0.72–0.85 按实测标定 | 适配公交业务字段的语义匹配精度，区分有效检索与无效干扰 |
| 单次搜索上限 | 前 8 条 | 平衡检索效率与召回覆盖，适配内部办公的多场景检索需求 |
| `defaultToken` | 绑定自有向量渠道令牌 | 规避第三方令牌权限报错问题，符合FastGPT v4.17.0版本的配置逻辑 |
| `maxToken` | 4096 token | 适配多数向量模型的输入上限，保障长文本分块的有效编码 |

## 容易做错的三处
- 现象：界面提示「该令牌无权使用模型」或无可用向量渠道。原因：未绑定自有向量渠道的`defaultToken`，仍依赖默认的第三方令牌配置，导致权限校验失败。
- 现象：知识库搜索耗时超出合理范围，检索结果返回延迟。原因：未根据公交数据的更新频率配置增量索引，仍使用全量索引逻辑，导致每次检索扫描全量数据。
- 现象：检索结果无法匹配完整的业务流程，如排班表的跨分块班次信息丢失。原因：分块长度设置过小或重叠长度不足，导致长文本被切割破坏上下文关联。

## 怎么确认配好了
- 查看向量模型绑定状态，确认`defaultToken`对应的渠道已完成授权校验。
- 随机选取一条内部文档，执行检索测试，核对返回结果的分块长度与配置值是否匹配。
- 调整相似度阈值，观察检索结果的召回数量变化，确认阈值符合业务匹配需求。
- 查看系统日志，确认增量索引仅在排班、运维日志的更新周期内触发，未占用过多系统资源。
