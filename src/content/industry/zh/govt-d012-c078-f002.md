# 城市水务的内部办公与员工服务：向量模型与索引

## 这个品类的数据长什么样
城市水务内部办公与员工服务的数据来源包括管网巡检日志、水质检测报表、内部审批流程文档、员工岗位培训课件、报修工单记录等。数据更新节奏存在差异：巡检日志按班次上传，每日更新；水质报表按月度汇总更新；培训课件按季度更新；工单记录实时生成。文档结构包含结构化字段（如管网ID、检测点位、压力值单位MPa、浊度单位NTU、巡检人员工号）与非结构化文本（如巡检现场描述、审批意见），部分文档附带表格或图片数据。

## 这些特征在「向量模型与索引」这一环带来什么约束
结构化数据携带明确单位与业务标识，要求向量模型支持带字段元数据的文本编码，避免单位与专业词汇的语义丢失。数据更新频率差异大，实时工单与定期报表需分别适配增量索引与全量索引的更新策略，避免索引更新滞后或资源浪费。部分巡检报告与培训课件篇幅较长，需支持长文本分块与语义拼接，避免关键业务信息被截断。内部办公场景的查询多围绕水务专业术语，需索引适配领域词汇的召回精度，确保检索结果符合业务需求。多源异构数据（日志、报表、文档）需统一的解析与向量化流程，避免格式不兼容导致的索引缺失。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxToken` | `8192` | 适配水务领域长文本（如年度水质报告、完整巡检记录）的编码需求，避免截断关键业务信息 |
| 分块长度 | 800–1200 字符 | 平衡单块文本的语义完整性与索引检索的效率，适配水务文档的平均篇幅 |
| 重叠长度 | 100–150 字符 | 减少分块导致的语义断裂，确保跨块的专业术语（如管网管径、水质标准）被完整编码 |
| 相似度阈值 | 0.72–0.80 | 过滤低相关的检索结果，适配内部办公场景中对业务精准度的要求 |
| 单次搜索上限 | 前 8 条 | 控制返回结果的信息量，避免员工被过多冗余信息干扰 |
| `defaultToken` | 4096 | 适配日常员工咨询的上下文长度，如报修工单的历史记录、岗位培训的核心内容 |

仅作参考；请以目标 FastGPT 发布版本与部署文档核验。

## 容易做错的三处
- 现象：embedding生成结果与公开文档的预期表现不符，原因是未针对水务领域的专业术语调整文本预处理逻辑，直接使用通用分词规则处理管网、浊度等专属词汇。
- 现象：容器启动后无法连接向量数据库，原因是仅启动了向量数据库镜像，未同步启动MongoDB与Sandbox容器，缺少必要的依赖服务。
- 现象：相同查询多次触发向量数据库检索，响应延迟偏高，原因是未开启缓存优化配置，未对重复查询的结果进行复用。

## 怎么确认配好了
- 上传一份包含专业术语的水务巡检报告，检查分块后的文本长度是否落在配置的800–1200字符范围内。
- 发起相同的业务查询两次，确认第二次响应延迟明显低于第一次，验证缓存优化机制生效。
- 查看向量数据库的索引管理界面，确认已生成对应水务业务文档的向量索引条目。
- 测试包含管网、浊度等专业词汇的文本编码，确认生成的embedding结果符合设定的相似度阈值范围。
