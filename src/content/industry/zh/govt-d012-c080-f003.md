# 城投平台的内部办公与员工服务：多轮对话与提示词

本文基于 FastGPT v4.17.0 版本编写。

## 这个品类的数据长什么样
城投平台的内部办公数据主要来自自有OA系统、项目管理台账、员工考勤系统、财务报销模块。数据更新节奏分两类，结构化表单数据每日同步更新，非结构化文档如项目方案、内部通知由管理员手动上传后生效。文档结构包含固定字段与自由文本两部分，固定字段含员工工号、部门编码、项目编号、报销单号，单位涵盖元、天、人次等，自由文本多为项目进展描述与内部沟通纪要。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
城投平台的内部办公数据特征对多轮对话与提示词环节带来多重约束。结构化表单字段多且含固定编码规则，提示词需明确指定字段匹配逻辑，避免模糊识别导致的结果偏差。非结构化文档长度差异大，多轮会话需限制上下文总长度，防止超出模型处理上限。数据更新节奏存在差异，多轮会话需支持动态调用最新同步数据，不依赖静态缓存。不同业务场景的字段与业务逻辑差异显著，提示词需适配报销、项目管理、考勤查询等细分场景的调用规则。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定当前员工会话的唯一标识，持久化存储至会话结束 | 确保多轮对话的历史消息与当前请求关联，符合城投平台员工服务的上下文延续需求 |
| `messages` | 携带前 15 条历史对话消息，超出部分自动截断 | 城投平台内部办公的多轮交互通常不超过15轮，限制数量可降低模型计算负载，避免上下文溢出 |
| `variables` | 绑定员工工号、部门编码等权限变量，有效期为 8 小时 | 城投平台内部数据需关联员工权限，全局变量可在多轮会话间保持，无需重复输入身份信息 |
| 最大上下文长度 | 8000–12000 字符 | 适配城投平台内部文档的长度范围，避免因长文本导致的模型处理失败 |
| 会话超时时间 | 300 秒 | 匹配城投平台内部办公的常规交互节奏，防止无效会话占用资源 |

## 容易做错的三处
- 现象：调用接口时出现 `Cannot read properties of null (reading 'q')` 报错。原因：未正确传递`chatId`参数，导致会话上下文为空，模型无法读取对话历史的查询字段。
- 现象：工作流内的问题分类结果偏差较大。原因：提示词未适配城投平台内部办公的专属业务术语与字段规则，无法准确识别用户提问的业务场景。
- 现象：多轮会话中全局变量无法在上下文间保持。原因：未正确配置变量的绑定规则，导致会话切换后变量被重置。

## 怎么确认配好了
- 发起单轮测试请求，检查返回结果是否关联当前员工的部门与权限信息，确认变量绑定生效。
- 发起连续多轮对话，检查历史消息是否被正确携带，确认历史消息配置符合预期。
- 查看会话日志，确认`chatId`在同一会话的多次请求中保持一致，无异常变更。
- 触发超时场景，检查会话是否在设定时间后自动终止，确认超时配置生效。
