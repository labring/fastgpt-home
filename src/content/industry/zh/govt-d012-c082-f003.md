# 基础电信运营的内部办公与员工服务：多轮对话与提示词

## 这个品类的数据长什么样
基础电信运营的内部办公数据主要来自运维监控系统、计费结算平台、客服工单系统与基站状态采集终端。数据更新节奏覆盖实时（基站运行参数）、小时级（客服工单流转）与日级（月度计费报表）。文档包含结构化与非结构化两类，结构化字段包含工单号、信号强度（单位dBm）、流量消耗（单位GB）、用户号码，非结构化内容为运维故障描述与客服沟通记录。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
实时基站参数与客服工单的高频更新，要求多轮对话上下文需过滤过期数据，仅保留最近24小时内的有效内容。结构化字段的多样性，要求提示词需明确指定字段匹配规则，避免混淆信号强度与流量消耗的单位。非结构化故障描述的长文本占比高，会拉长单轮对话的处理耗时，需限制单次对话的上下文总字符数。会话关联需绑定唯一标识，否则无法实现跨轮对话的工单跟进。

## 配置怎么定
仅作参考；请以目标 FastGPT 发布版本与部署文档核验。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 800–1200 字符 | 匹配电信运维文档与工单的平均长度，避免超出模型处理上限 |
| 会话标识配置 | 启用`chatId`绑定 | 保留历史工单号与用户标识，支持连续跟进同一服务请求 |
| 提示词变量设置 | 绑定`variables`字段 | 动态传入当前工单号、基站编号等实时参数，适配多轮查询 |
| 对话历史管理 | 按`messages`字段保留最近3轮 | 控制上下文总长度，降低模型推理耗时 |
| 上下文刷新频率 | 每5分钟同步一次 | 适配实时基站数据的更新节奏，保证对话中使用最新参数 |
| 单轮输出限制 | 不超过500 字符 | 适配内部办公场景的短平快交互需求，避免信息过载 |

## 容易做错的三处
- 现象：对话响应耗时过长，界面出现加载延迟提示。原因：未限制上下文长度，带入了过多过期的基站日志与工单数据，超出模型处理能力。
- 现象：对话过程中弹出Unexpected end of JSON input报错，使用ChatGLM2模型时高频出现。原因：未对`messages`字段做格式校验，传入了未闭合的对话历史数组，导致模型接口解析失败。
- 现象：每次发起新对话后，历史工单信息无法被自动关联。原因：未启用`chatId`绑定配置，会话标识未持久化，导致每轮对话被识别为新请求。

## 怎么确认配好了
- 发起包含历史工单号的多轮对话，检查对话界面是否自动关联该工单号对应的工单数据。
- 连续发起3轮针对同一基站的参数查询，检查上下文是否保留前两轮的基站编号信息。
- 观察对话响应耗时，根据实际业务场景调整上下文长度阈值，确保耗时符合内部办公的交互要求。
- 模拟格式异常的对话历史输入，检查是否会触发Unexpected end of JSON input报错，确认格式校验逻辑已生效。
