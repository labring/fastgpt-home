# 基础设施建设的内部办公与员工服务：向量模型与索引

## 这个品类的数据长什么样
基础设施建设的内部办公与员工服务数据，主要来源于项目施工日志、设备运维记录、内部员工手册、招投标交底文档、班组任务单等。数据更新节奏分为三类：施工日志、任务单为每日更新，项目文档、交底文档随项目阶段更新，员工手册、制度文件为季度或年度更新。文档结构包含长文本与短文本，字段包含项目编号、施工段号、设备序列号、日期、责任班组等，附带工程专业单位如米、立方米、台班。

## 这些特征在「向量模型与索引」这一环带来什么约束
基建类文档包含大量专业术语与长句，分块时需保留完整语义单元，避免拆分专业术语或施工流程。多类数据更新节奏差异大，需同时支持增量索引与全量索引的灵活切换。文档附带结构化字段与工程单位，索引需兼顾非文本语义与结构化元数据的匹配。数据规模随项目推进逐步增长，索引需支持批次化处理以避免单次重建耗时过长。本章节的约束分析基于FastGPT v4.17.0版本的向量索引逻辑。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配基建专业文档的长句结构，保留完整语义单元 |
| 重叠长度 | 100–150 字符 | 避免长文档分块后出现施工流程、专业术语的语义断裂 |
| `maxToken` | 4096 token | 覆盖长文档分块后的最大上下文处理需求 |
| 相似度阈值 | 0.72–0.78，按实测标定 | 区分专业术语匹配与无关内容的匹配精度 |
| 单次搜索上限 | 前 8 条 | 适配基建内部办公查询聚焦特定项目的使用场景 |
| `defaultToken` | 2048 token | 匹配日常办公查询的常规上下文长度 |

## 容易做错的三处
- 现象：知识库内容量少但持续显示重建中，切换索引无响应。原因：未关闭自动重建开关，且未将新索引集合设置为活跃状态。
- 现象：批量添加索引时返回参数错误，部分元数字段为空。原因：未按照基建文档的专属字段（如项目编号、施工段号）配置批量请求的元数据参数。
- 现象：索引重建耗时超过预设时长，任务卡住无进度更新。原因：未对批量数据进行批次拆分，全量重建未适配基建文档的长文本体量。

## 怎么确认配好了
- 上传一份典型的基建施工日志文档，查看分块结果是否保留完整的专业语句，无明显语义断裂。
- 发起一次包含工程专业术语的查询，查看返回结果的匹配逻辑是否符合预设的相似度规则。
- 手动触发一次索引重建，查看任务执行节奏是否符合批次处理的预期。
- 尝试切换索引集合，确认操作可正常完成且后续查询指向新的索引集合。
