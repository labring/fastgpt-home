# 工程咨询监理的内部办公与员工服务：多轮对话与提示词

## 这个品类的数据长什么样
工程咨询监理的业务数据主要来源于项目现场的监理日志、旁站记录、分项工程验收报告、合同台账、整改通知单等。数据更新节奏随项目节点推进，日常巡检数据每日更新，验收类数据在验收完成后即时更新。单份文档包含结构化字段与非结构化文本，结构化字段包括监理单位、项目编号、验收部位、整改时限、验收结果等，单位涉及平方米、工作日、万元等，非结构化文本多为现场问题描述与处理意见。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
监理业务数据的结构化与非结构化混合特征，要求多轮对话需区分不同类型的上下文信息，提示词需明确指定结构化字段的输出格式与单位要求。数据按项目节点更新且存在明确的项目周期，对话上下文需过滤过期项目数据，避免跨项目的信息混淆。多轮对话的`messages`参数需绑定当前项目的专属字段，防止无关数据被纳入上下文范围。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 8000–12000 token | 适配监理文档的混合文本长度，避免内容截断 |
| 对话历史召回条数 | 前3–5轮 | 减少冗余上下文占用，聚焦当前项目的最新沟通内容 |
| `variables` 绑定 | 绑定项目ID、验收部位字段 | 限定对话仅使用当前项目的专属数据 |
| 输出格式校验 | 强制包含整改时限、验收结果字段 | 匹配监理业务的必填输出项 |
| `chatId` 绑定 | 绑定当前项目的唯一标识 | 隔离不同项目的对话上下文，防止数据混淆 |
| 上下文时间过滤 | 仅召回近30天的项目数据 | 过滤过期项目的历史记录，保证信息时效性 |

## 容易做错的三处
- 现象：模型输出Markdown表格时内容被截断，界面显示`...[hide 38432 char`。原因：未配置最大上下文长度，导致对话窗口不足以承载完整的表格内容。
- 现象：LLM回复内容超出知识库范围，包含未上传的监理数据。原因：提示词未明确限定仅使用已上传的监理日志、验收报告数据，未通过`variables`绑定专属业务字段。
- 现象：多轮对话中出现跨项目的监理数据。原因：未绑定`chatId`或项目ID字段，导致不同项目的上下文被混合召回。

## 怎么确认配好了
- 上传单份监理验收报告作为测试数据，发起包含验收部位、整改要求的提问，核对回答仅使用该测试数据的内容。
- 发起多轮对话，分别询问不同项目的监理进度，核对对话仅召回当前`chatId`绑定的项目数据。
- 测试Markdown格式的整改通知单输出，核对表格完整显示无截断。
- 上传音频测试文件，核对系统支持的音频格式与配置要求一致。
