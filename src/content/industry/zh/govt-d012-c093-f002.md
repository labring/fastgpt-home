# 政企信息化服务的内部办公与员工服务：向量模型与索引

## 这个品类的数据长什么样
政企信息化服务的内部办公与员工服务数据，主要来源于内部OA系统、员工服务工单、会议纪要、制度手册与培训课件。数据更新节奏覆盖实时（如用户提交的服务工单）、每日（如考勤与审批数据）、定期（如月度更新的制度文档）三类。单份文档多为结构化与半结构化混合，包含标题、正文、发布部门、生效时间、适用层级等字段，字段单位多为字符数、条目数、时间戳格式。

## 这些特征在「向量模型与索引」这一环带来什么约束
实时工单数据的高频新增要求索引支持增量更新与低延迟同步，避免全量重建带来的资源占用。半结构化字段如适用层级、发布部门，需单独作为元数据纳入索引规则，用于后续的权限过滤与精准召回。文档长度跨度大，从数十字符的工单到数万字符的制度手册，要求分块策略具备自适应调整能力，避免过短导致语义断裂或过长超出模型上下文限制。多源数据的格式差异，需统一预处理流程以保证向量生成的一致性。

## 配置怎么定
本配置基于FastGPT v4.17.0版本的参数逻辑。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配政企内部文档的语义完整性，避免短块丢失上下文，同时控制单块token数不超出模型限制 |
| 重叠长度 | 100–150 字符 | 弥补分块边界的语义断裂，保证跨块内容的连贯性 |
| 相似度阈值 | 0.72–0.85 | 适配内部办公数据的语义相似度分布，过滤低相关召回结果 |
| 单次搜索上限 | 前 8 条 | 平衡召回精度与上下文窗口占用 |
| `maxToken` | 4096 token | 匹配主流向量模型的输入上限，避免截断丢失关键信息 |
| `defaultToken` | 1536 维 | 适配通用向量模型的输出维度，保证索引存储与召回的一致性 |

## 容易做错的三处
- 现象：自定义索引配置后检索结果为空或与查询无关。原因：未将内部办公数据的元数据（如适用层级）纳入索引过滤规则，导致召回范围超出用户权限或业务范围。
- 现象：配置商用向量模型后无法生成有效向量。原因：未在渠道配置中正确填写模型专属的API密钥与区域参数，导致模型调用失败。
- 现象：接入第三方向量数据库后无法召回存量数据。原因：未将内部数据的字段格式统一为向量模型要求的输入结构，导致向量生成或匹配失败。

## 怎么确认配好了
- 上传单份典型内部文档（如完整制度手册），检查分块后的片段是否完整覆盖核心语义，无明显语义断裂。
- 发起一条针对内部员工服务的查询，核对检索结果的元数据是否包含正确的适用层级与发布部门，符合业务范围要求。
- 查看向量生成日志，确认所有输入文档的向量维度与`defaultToken`参数一致，无维度不匹配报错。
- 模拟提交一条新的服务工单，检查索引是否在预设时间内完成同步，无延迟或数据丢失情况。
