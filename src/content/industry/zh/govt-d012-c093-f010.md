# 政企信息化服务的内部办公与员工服务：知识库检索与召回

## 这个品类的数据长什么样
政企信息化服务的内部办公与员工服务数据，主要来源于内部OA系统、员工手册、部门制度文档、IT运维指南、福利通知等办公产出物。数据更新随内部制度修订、员工信息变动、办公流程优化按需触发，常规更新周期为每日或按周同步。文档结构包含标题、正文、发布部门、生效时间、适用岗位范围等字段，部分文档带有结构化元数据，如关联业务系统编号、审批流程节点标识。

## 这些特征在「知识库检索与召回」这一环带来什么约束
混合结构化元数据与非结构化正文的文档结构，要求检索同时支持语义召回与元数据过滤，精准匹配适用范围明确的内容。高频按需更新的特性，要求支持增量索引更新，避免全量重建带来的资源消耗。文档长度跨度较大，从短篇幅的福利通知到长篇幅的制度规范均有覆盖，要求分块策略适配不同长度的文本均衡召回。同时，内部文档的正式表述风格，要求检索模型过滤口语化的无关内容，保证召回结果的专业性。

## 配置怎么定
仅作参考；请以目标 FastGPT 发布版本与部署文档核验。

| 配置项 | 建议取法 | 这样取的依据 |
|---|---|---|
| `similarity` | 0.72–0.85 | 适配政企文档的正式表述风格，过滤低相关的口语化内容，按实测标定 |
| `limit` | 前10条 | 平衡召回覆盖度与上下文长度限制，适配内部办公文档的单条平均长度 |
| `searchMode` | hybrid | 结合语义匹配与关键词匹配，适配混合结构化与非结构化的政企文档结构 |
| `usingReRank` | 开启 | 过滤初步召回的冗余内容，提升高相关文档的排序优先级 |
| `datasetSearchUsingExtensionQuery` | 开启 | 优化员工提问的模糊表述，匹配内部文档的专业术语与缩写 |
| `collectionIds` | 按业务部门绑定的知识库集合 | 限定召回范围，避免跨部门无关文档被召回 |

## 容易做错的三处
- 现象：调用知识库索引生成接口后，召回结果与更换嵌入模型前差异显著。原因：仅更换模型未触发已导入文档的重索引操作，原有向量未同步更新。
- 现象：使用PostgreSQL存储向量时，单次召回结果条数不足预期，或查询出现超时。原因：未针对政企文档的混合结构优化向量索引的分片策略，未按部门元数据限定检索范围，导致扫描范围过大。
- 现象：知识库导入数据时弹出格式错误提示，无法完成索引创建。原因：导入的文档未包含发布部门、适用范围等必填元数据字段，或文档格式不符合平台要求的规范。

## 怎么确认配好了
- 发起一条包含特定部门关键词的测试提问，核对召回结果是否仅包含对应业务部门的文档。
- 查看检索日志，确认召回结果的相似度分值落在预设的`similarity`区间内。
- 触发一次增量同步任务，验证仅更新的文档被重新索引，未触发全量重建流程。
- 开启`usingReRank`功能后，对比开启前后的召回结果排序，确认高相关文档的位置得到优化。
