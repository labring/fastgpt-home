# 新能源开发的内部办公与员工服务：多轮对话与提示词

## 这个品类的数据长什么样
新能源开发的内部办公与员工服务数据，主要来源于场站运维日志、设备巡检台账、办公审批流记录、员工培训文档及项目会议纪要。数据更新节奏分为三类：场站运行参数每小时更新，审批流提交后实时更新，培训文档与会议纪要按季度更新。文档包含结构化与非结构化两种形式，结构化数据包含场站编号、设备ID、发电量、故障等级等字段，单位涵盖kW、小时、次；非结构化数据多为单篇1000–3000字符的运维报告或审批说明。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
场站运行参数的实时性要求多轮对话需绑定实时接口以获取最新数据。结构化数据的多字段属性要求提示词需明确指定目标提取字段，避免混淆不同场站的参数。非结构化文档的长度会占用大量上下文，需限制对话历史的轮次与长度，防止超出系统处理上限。不同员工的连续咨询需保留会话上下文，因此需持久化会话标识，避免每轮对话重新初始化上下文。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 上下文窗口大小 | 8000–12000 token | 适配新能源开发运维报告、审批文档的平均长度，避免上下文溢出 |
| `messages` 历史轮次限制 | 前10轮对话 | 减少冗余上下文占用，优化多轮对话的响应速度 |
| 动态`variables` 更新频率 | 每5分钟 | 匹配场站运行参数的实时更新节奏，保证对话调用最新数据 |
| 提示词字段约束 | 明确指定场站编号、故障等级、审批状态 | 匹配内部办公数据的标准字段结构，提升信息提取准确率 |
| `chatId` 会话持久化开关 | 开启 | 保留多轮对话的上下文关联，适配员工连续咨询场站问题的场景 |

## 容易做错的三处
- 现象：多轮对话输出结果为空，或自定义`output`字段无内容。原因：未在提示词模板中明确指定提取内部办公数据的目标字段，或动态`variables`未正确绑定场站数据接口。
- 现象：连续咨询不同场站的运维问题时，回答混淆场站编号与参数。原因：未限制`messages`的历史轮次，冗余上下文干扰了当前对话的字段匹配。
- 现象：多轮对话响应超时。原因：上下文窗口设置过大，同时加载了过多场站的历史数据，超出系统处理上限。

## 怎么确认配好了
- 发起连续3轮针对不同场站的运维咨询，核对每轮回答是否关联对应场站的参数。
- 提交长文档的问答请求，检查响应是否出现内容截断或异常报错。
- 触发多轮会话后退出系统，重新进入会话，检查是否保留了之前的对话上下文。
- 查看动态`variables`的返回结果，确认调用的数据与场站实时台账一致。
