# 煤炭运销的内部办公与员工服务：知识库检索与召回

## 这个品类的数据长什么样
煤炭运销的内部办公与员工服务数据，主要来源于运销调度台账、煤质检测报告、购销合同文档、员工岗位手册及日常办公通知。数据更新节奏覆盖多维度：每日更新的发运量、车次等实时调度数据，每批次更新的单矿煤质参数数据，定期更新的员工培训材料与合同归档数据。文档结构包含结构化表格（如含发运吨数、热值大卡、客户编号等字段的台账）、长文本通知与岗位操作指南，字段多绑定明确物理单位，如吨、大卡、车次。

## 这些特征在「知识库检索与召回」这一环带来什么约束
多更新节奏的数据源要求知识库支持增量同步与分批次更新，避免全量重导占用系统资源。结构化与非结构化文档混合的内容结构，要求检索同时兼顾语义匹配与精确字段匹配，避免遗漏结构化表格内的精准条目。明确的字段与单位要求检索支持按业务维度限定范围，例如仅检索当月发运台账或指定矿点的煤质检测数据，防止跨业务线的无关数据混入结果。员工服务场景下的口语化查询，要求检索优化能够将日常表述转换为匹配业务文档的精准关键词。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `similarity` | 0.72–0.80 | 煤炭运销的结构化字段匹配需要较高阈值，避免无关的煤质参数或历史合同混入结果 |
| `limit` | 前10–15条 | 内部办公与员工服务的检索结果无需过多，避免信息过载，同时覆盖主要的业务文档类型 |
| `searchMode` | hybrid | 兼顾结构化表格的精确匹配与长文本的语义召回，适配煤炭运销混合文档结构 |
| `usingReRank` | 开启 | 提升混合文档的排序相关性，尤其针对长文本通知与结构化表格的混合检索场景 |
| `datasetSearchUsingExtensionQuery` | 开启 | 优化员工的口语化查询，例如将“今天的发运计划”转换为匹配当日调度台账的关键词 |
| `collectionIds` | 按业务线限定，如运销台账库、煤质检测库的集合ID | 限定检索范围为指定业务数据集，避免跨业务线的无关数据召回 |

## 容易做错的三处
- 现象：无法限定检索范围为指定的入库文档，例如仅检索当月的煤炭发运台账，却召回了全量历史数据。原因：未正确配置`collectionIds`参数，或未限定检索的数据集范围，导致召回全量知识库内容。
- 现象：检索煤炭运销的结构化表格数据时，返回结果条数不足，例如台账内50项仅返回30余项。原因：未将`searchMode`设置为hybrid模式，仅依赖语义召回遗漏了精确匹配的结构化条目。
- 现象：执行检索时出现MongoServerError相关报错。原因：部署的FastGPT v4.17.0与MongoDB版本不兼容，未匹配支持的数据库版本要求。

## 怎么确认配好了
- 手动输入一条已知存在于指定业务数据集的查询，核对返回结果是否仅包含该数据集的文档。
- 上传一份测试用的煤炭运销台账表格，执行检索后核对返回的条目数量与表格内实际条目一致。
- 开启`usingReRank`后，对比开启前后的检索结果排序，确认相关度更高的条目排在前列。
- 调整`similarity`参数，验证返回结果的相关性是否符合业务预期，无需设置固定阈值。
