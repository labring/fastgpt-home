# 矿山采选的内部办公与员工服务：向量模型与索引
本文基于 FastGPT v4.17.0 版本编写

## 这个品类的数据长什么样
矿山采选的内部办公与员工服务数据主要来自采矿调度日志、设备运维记录、员工考勤排班、安全操作规程、选矿参数报表、工会活动通知等。更新节奏差异明显：调度日志与实时运维数据按分钟或班次更新，安全规程与政策文档为静态修订更新，考勤与活动通知按周或月度更新。文档结构包含标准化字段与自由文本：标准化字段如设备编号、运行时长、班次、隐患等级，单位涵盖吨、米、小时、班次等；自由文本如运维故障描述、安全培训心得等。

## 这些特征在「向量模型与索引」这一环带来什么约束
矿山采选的数据特征对向量模型与索引环节带来多重约束：首先，数据更新频率差异大，需支持全量索引与增量索引的混合配置，避免重复计算实时数据；其次，单条数据长度跨度大，从数十字符的考勤记录到数千字符的选矿规程，需适配动态分块参数；第三，内部办公数据常达十万级以上规模，需调整索引批量处理参数，避免构建超时，需调整`maxToken`参数适配模型输入上限；最后，字段包含数值型与文本型混合内容，需提前统一文本格式化规则，确保嵌入结果的一致性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配矿山采选的长文档（如选矿规程）与短文本（如运维日志）的平衡需求 |
| 重叠长度 | 100–200 字符 | 避免分块破坏上下文连贯性，适配设备运维记录的连续故障描述场景 |
| maxToken | 4096 token | 适配多数商用嵌入模型的输入上限，避免截断关键参数内容 |
| defaultToken | 2048 token | 作为默认上下文长度，满足员工服务类问题的常规信息检索需求 |
| 单次搜索上限 | 前10条 | 平衡检索效率与召回覆盖，适配内部办公的常用查询场景 |
| 相似度阈值 | 按实测标定 | 适配矿山安全隐患文本的匹配精度要求，避免误召回或漏召回 |

## 容易做错的三处
- 现象：导入十万条CSV格式的运维数据后，向量后数据量减少数千条。原因：部分文本字段包含不可解析的特殊字符（如矿山爆破记录中的爆破参数符号），未提前做文本清洗，导致嵌入失败被自动过滤。
- 现象：集合创建成功，但页面索引一直无法建立。原因：增量索引触发逻辑未正确绑定数据更新事件，或索引分片配置超出集群存储上限，导致后台索引构建任务阻塞未执行。
- 现象：本地运行向量索引正常，Docker打包部署后向量得分完全一致。原因：Docker镜像中未正确配置嵌入模型的API密钥环境变量，导致所有请求调用默认测试接口，返回固定向量结果。

## 怎么确认配好了
- 核对嵌入后的总数据量，与源数据量一致，无明显缺失。
- 测试不同类型的文本（如短考勤记录、长选矿规程）的分块效果，确认无过度截断或冗余分块。
- 对比本地与Docker部署环境下的向量得分差异，确认配置参数同步一致。
- 验证不同检索模式的响应时间，确认符合业务预期的性能阈值要求。
