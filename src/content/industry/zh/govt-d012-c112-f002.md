# 粮食储备的内部办公与员工服务：向量模型与索引

## 这个品类的数据长什么样
数据主要来自仓储管理系统的库存台账、日常巡检记录、员工考勤与培训文档、质检报告。更新节奏分为两类：库存台账与质检报告按入库批次更新，巡检与考勤记录每日更新。文档结构多为结构化字段，包含仓号、粮食品种、入库批次、库存数量、温湿度数据，单位为吨、公斤、批次号；员工相关文档则包含岗位、排班、培训内容等字段。

## 这些特征在「向量模型与索引」这一环带来什么约束
结构化字段占比高，需针对结构化字段设计向量绑定规则，避免无关字段参与向量生成。更新节奏存在差异，需配置按更新频率分批次构建索引，避免实时数据占用过多计算资源。文档字段包含单位与批次标识，需在索引时绑定元数据，便于后续检索时关联业务上下文。巡检记录含时序温湿度数据，需调整分块逻辑，确保单块数据的语义完整性，避免拆分破坏业务关联。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 粮食储备的台账、巡检文档的单块语义完整性 |
| `maxToken` | 4096 token | 仓储类文档的平均token占用量，适配业务文档长度 |
| `defaultToken` | 1024 token | 员工培训、考勤文档的常见内容长度 |
| 相似度阈值 | 0.72–0.78 | 匹配业务场景下的检索精度需求 |
| 单次搜索上限 | 前10条 | 内部办公场景的检索结果无需过多，聚焦核心信息 |
| 重排 | 开启 | 员工文档与仓储文档语义差异大，提升检索相关性 |

## 容易做错的三处
- 现象：索引构建失败，日志显示元数据绑定异常。原因：未将仓号、批次号等业务字段绑定至向量索引，导致检索无法关联业务上下文。
- 现象：调用embedding模型返回503状态码，提示无可用渠道。原因：未单独配置embedding模型，误用通用API密钥受限于渠道限制。
- 现象：docker部署后配置环境变量未生效。原因：未在docker-compose.yml中添加对应环境变量，且未重建容器加载新配置。

## 怎么确认配好了
- 查看FastGPT v4.17.0的索引构建日志，检查是否成功绑定仓号、批次号等业务元数据。
- 提交仓储相关检索请求，查看返回结果是否包含对应业务字段，相似度值落在设定阈值范围内。
- 提交员工服务相关检索请求，检查重排后的结果排序符合业务相关性逻辑。
- 进入docker容器环境变量列表，确认CHAT_API_KEY已正确加载。
