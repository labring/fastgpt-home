# 轨道交通装备的内部办公与员工服务：向量模型与索引

## 这个品类的数据长什么样
轨道交通装备内部办公与员工服务的数据主要来自设备运维台账、月度检修记录、员工岗位培训手册、办公流程规范文档、备件库存清单。数据更新节奏随业务节点变动：检修记录在每次设备维保完成后实时录入，培训文档在新车型研发或岗位调整时更新，库存清单每周同步。文档结构多为结构化字段与非结构化段落结合，包含设备编号、检修时段、故障描述、处理方案、备件型号等字段，字段单位多为标准工业编码、时间戳及物理计量单位。

## 这些特征在「向量模型与索引」这一环带来什么约束
轨道交通装备数据的结构化字段多、专业术语密度高，且部分数据例如检修记录更新频率不稳定，会对向量模型与索引环节带来多重约束。结构化字段需单独映射为可检索的向量维度，避免专业工业编码被通用模型误编码。长段落的故障分析文档需要适配长文本分块规则，防止关键运维信息被截断。增量更新的需求要求索引支持增量同步，避免全量重建带来的额外资源占用。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配轨道交通装备文档的长段落结构，保留完整的故障分析、操作流程等核心信息 |
| 重叠长度 | 100–200 字符 | 避免分块截断连续的业务上下文，如连贯的检修步骤说明 |
| 相似度阈值 | 0.72–0.85 | 区分专业工业术语的细微差异，减少无关设备记录的误召回 |
| 单次搜索上限 | 前 10 条 | 匹配内部办公场景的员工查询需求，避免过多召回结果增加上下文处理压力 |
| `maxToken` | 8000–12000 token | 适配长文档的向量索引与上下文召回，满足复杂运维问题的查询需求 |
| `defaultToken` | 500 token | 控制单条向量的生成资源占用，平衡检索精度与成本 |

本页面基于FastGPT v4.17.0版本编写。

## 容易做错的三处
- 导入的知识库仅包含部分文档内容，未覆盖预期的全部业务条目。原因是未开启自定义分块规则，系统默认按固定长度拆分时截断了部分结构化字段，如设备编号、备件型号等。
- 检索结果中出现大量无关的非轨道交通文档。原因是未针对工业专业术语调整相似度阈值，通用向量模型误召回了其他品类的业务文档。
- 向量生成任务频繁超时。原因是`maxToken`设置超出当前部署硬件的算力上限，导致单条向量生成耗时过长。

## 怎么确认配好了
- 上传单篇典型的设备检修记录文档，查看分块预览界面，确认每个分块都保留了核心的设备编号与故障描述字段。
- 发起一条针对特定设备编号的查询，核对检索结果的条数与匹配度，调整相似度阈值至符合业务需求的区间。
- 查看向量数据库的存储空间占用，确认索引生成的总数据量与预估的知识库容量匹配，无异常溢出。
- 测试增量更新功能，上传一份新的检修记录，确认系统仅同步新增内容，未触发全量索引重建。
