# 通信工程建设的内部办公与员工服务：多轮对话与提示词

## 这个品类的数据长什么样
通信工程建设的内部办公数据主要来源于项目管理系统、施工日志台账、物资库存系统、人员考勤记录与运维巡检报告。数据按单次施工节点或每日更新，文档多为结构化表格形式，包含项目编号、施工区段、材料规格、作业时长、验收状态等字段，单位涵盖米、立方米、工时、自然日等，部分非结构化数据为现场拍摄的施工照片与手写巡检记录。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
结构化数据的字段明确性要求提示词需指定固定字段提取规则，避免大模型输出模糊结果；非结构化的现场照片与巡检记录需要多轮对话逐步引导用户补充上下文，避免单次输入过载；按节点更新的数据需在对话中明确指定当前会话关联的项目ID与施工区段，确保调用的知识库数据为对应时段的最新内容；多轮对话的上下文需限制在当前项目的施工周期内，避免混入其他项目的历史数据干扰结果。

本配置基于FastGPT v4.17.0版本
## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `variables` | 绑定项目ID、施工区段字段 | 用于精准关联当前会话的专属项目数据，避免跨项目数据干扰 |
| `messages` | 保留前10轮核心对话内容 | 通信工程施工流程多为线性步骤，过多历史对话会干扰当前作业的提示词逻辑 |
| `chatId` | 绑定至当前项目的会话ID | 确保多轮对话的上下文仅关联当前项目，不会混入其他会话数据 |
| 最大上下文长度 | 8000–12000 token | 通信工程的项目文档多包含长段施工日志与材料清单，需保留足够多的历史对话与知识库召回内容 |
| 会话上下文过期时间 | 24小时 | 内部办公场景多以单日项目作业为对话周期，过期后自动清理历史上下文避免冗余 |
| 单次对话最大输入字符数 | 5000字符 | 现场巡检的非结构化记录多为长文本，需允许完整输入后再进行多轮处理 |

## 容易做错的三处
- 现象：对话中调用上传的项目施工日志后，结果未包含指定区段的内容。原因：未通过`variables`绑定当前会话的施工区段字段，大模型无法精准匹配对应知识库数据。
- 现象：调用本地大模型后对话响应卡顿超过600秒。原因：未调整最大上下文长度与会话上下文过期时间的匹配关系，导致过多历史数据被反复加载。
- 现象：对话中尝试展示上传的施工照片时，界面无图片展示。原因：未在提示词中指定图片的关联字段与展示规则，大模型未触发图片渲染逻辑。

## 怎么确认配好了
- 打开会话的配置面板，检查`variables`中是否绑定了当前项目的专属字段，确认绑定的字段与项目数据的字段一致。
- 测试发起一轮包含历史对话的提问，检查系统是否能正确召回对应时段的项目数据，验证`messages`的截断规则是否生效。
- 上传一份测试用的施工材料台账，发起提问要求提取指定字段的内容，确认上传的数据被正确纳入对话上下文。
- 等待24小时后重新发起同一会话，检查系统是否自动清理了历史上下文，验证会话过期时间的配置是否生效。
