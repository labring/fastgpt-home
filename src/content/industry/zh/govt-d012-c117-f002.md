# 通信铁塔与基础设施的内部办公与员工服务：向量模型与索引

本文基于FastGPT v4.17.0版本编写。

## 这个品类的数据长什么样
数据主要来自运维巡检日志、设备台账、员工办公文档、考勤记录与工单系统。更新节奏随数据类型差异明显，巡检日志按每日或每周更新，设备台账在硬件变更时同步更新，办公文档按需提交修订。单份文档包含专属字段，如铁塔编号、巡检点位、故障等级，附带单位如号、米、伏特，部分长文档包含多页巡检步骤与整改方案。

## 这些特征在「向量模型与索引」这一环带来什么约束
该品类数据包含结构化设备字段与非结构化巡检文档，且存在实时更新的巡检日志与低频变更的设备台账，同时单份文档可能包含多页专业内容。混合数据类型要求索引需同时适配结构化字段编码与非自然语言文本的向量生成；高频更新的日志数据要求索引支持增量同步，避免全量重建的资源消耗；长文档的专业内容则要求分块时保留点位与设备关联信息，防止语义割裂。需合理设置`defaultToken`与`maxToken`以适配不同长度的文档，兼顾语义完整性与资源消耗。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配巡检报告、设备台账等专业长文本的语义完整性，避免单块内容割裂 |
| 重叠长度 | 100–150 字符 | 保留分块间的上下文关联，防止跨块专业术语的语义丢失 |
| `defaultToken` | 1000 token | 匹配内部办公文档的平均长度，控制单轮向量生成的资源消耗 |
| `maxToken` | 4000 token | 覆盖单次召回的完整工单、巡检流程文档，满足上下文调用需求 |
| 相似度阈值 | 0.75–0.85 | 精准匹配设备故障、员工诉求的语义特征，降低非相关内容的召回率 |
| 单次搜索上限 | 前 20 条 | 平衡内部办公场景的召回全面性与接口响应速度 |

## 容易做错的三处
- 现象：调用上传文件API后接口返回成功，但无法通过界面或日志确认索引生成进度，部分场景出现索引未完成即触发搜索的报错。原因：未配置异步任务的状态监听逻辑，仅依赖上传接口的同步返回判断任务完成情况。
- 现象：向量召回结果出现专业术语割裂，如“铁塔镀锌层厚度检测”被拆分为两个无关联的语义片段。原因：分块长度设置低于800字符，未覆盖完整的专业语义单元。
- 现象：搜索返回的结果与员工诉求的匹配度极低，出现大量非相关的巡检日志。原因：相似度阈值设置高于0.85，过滤了部分语义相近但细节有差异的有效内容。

## 怎么确认配好了
- 上传单份完整的巡检报告文档，通过系统提供的异步任务接口查询进度，确认索引生成完成的状态反馈正常。
- 手动调整分块长度与重叠长度参数，导入包含专业术语的测试文档，验证召回结果未出现语义割裂的情况。
- 发起针对设备故障描述或员工日常诉求的模拟搜索，核对召回结果的匹配逻辑符合预设规则。
- 查看向量索引的存储统计，确认数据占用符合服务器资源的配置要求。
