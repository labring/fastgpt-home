# 钢铁冶炼的内部办公与员工服务：模型接入与配置

## 这个品类的数据长什么样
钢铁冶炼的业务数据主要来自高炉、转炉、连铸机等产线的实时传感器，以及班次生产报表、设备运维日志。数据来源分为实时时序流、批次生产记录两类，更新节奏覆盖毫秒级的炉温、压力数据，按班次生成的铁水成分检测记录，以及按日更新的检修台账。单条文档结构包含产线编号、检测时间、参数数值、设备状态标签，字段多为数值型，附带℃、MPa、吨等单位，部分文本型字段包含运维备注。

## 这些特征在「模型接入与配置」这一环带来什么约束
钢铁冶炼的业务数据特征，对模型接入与配置带来多项约束。实时产线传感器数据的毫秒级更新节奏，要求模型调用的响应延迟需适配内部办公的协同需求，避免延迟影响调度、运维的即时沟通。月度生产报表、季度检修台账等长文档，要求模型支持足够的上下文承载能力，完整解析文档内的多字段关联信息。多类型的结构化与非结构化混合数据，要求配置时需明确参数映射规则，避免字段不匹配导致的调用异常。同时内部办公场景需对接多部门的产线数据，要求接入配置支持灵活的数据源调用权限划分。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 适配钢铁冶炼月度生产报表、季度检修台账等长文档的平均长度，完整解析多字段关联信息 |
| `maxTokens` | 2000–3000 token | 匹配内部办公场景下员工查询的常规回复长度，避免输出内容被截断 |
| `quoteMaxToken` | 4000–6000 token | 保证可完整引用产线检测数据片段，用于回复员工的产线状态查询 |
| `temperature` | 0.2–0.4 | 降低回复的随机性，保证产线数据、运维规则类回复的准确性 |
| `AIPROXY_API_ENDPOINT` | 对接OneAPI的专属网关地址 | 统一管理多模型调用的路由与令牌，适配内部办公的多部门数据权限需求 |
| `AIPROXY_API_TOKEN` | 绑定对应产线数据权限的密钥 | 实现不同部门员工仅能访问授权范围内的产线数据，保障数据安全 |

## 容易做错的三处
- 配置`AIPROXY_API_TOKEN`时直接输入OneAPI的全局密钥，调用时报空或权限错误。未针对钢铁冶炼的产线数据权限划分专属令牌，导致接口调用时无法匹配对应数据源的访问规则。
- 测试模型时提示“Cannot read p”类截断报错。未根据钢铁冶炼长文档的特征调整`maxContext`参数，导致上下文超出模型承载上限。
- 引用索引模型后流程卡住无响应。未匹配钢铁冶炼的结构化数据字段与单位，导致索引构建时无法正确解析参数内容，触发循环等待。

## 怎么确认配好了
- 调用测试接口输入单条产线实时数据查询，检查返回结果是否包含正确的参数数值与单位，核对字段匹配度。
- 导入月度生产报表文档，检查模型是否能完整解析文档内的多段数据关联，无截断或缺失。
- 配置多数据源权限，使用不同部门的令牌调用，检查是否仅能访问对应产线的数据范围。
- 调整`temperature`参数后多次测试，检查回复内容是否保持稳定的准确性，无过度发散。
