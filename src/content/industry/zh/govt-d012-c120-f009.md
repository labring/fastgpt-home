# 铁路运营的内部办公与员工服务：模型接入与配置

## 这个品类的数据长什么样
铁路运营的内部办公与员工服务数据来源包含调度集中系统（TDCS）、客票发售系统、设备运维平台、内部OA系统四类。数据更新节奏分为三类：行车调度日志为分钟级实时更新，客运工单与设备巡检记录按事件触发更新，员工考勤与排班数据为每日更新。单条文档结构包含时间戳、编号、分类字段与附件，其中时间戳格式为YYYY-MM-DD HH:MM:SS，线路区段以公里标（如K123+456）为单位，附件支持图片与PDF格式，单张图片最大不超过10 MB。

## 这些特征在「模型接入与配置」这一环带来什么约束
不同来源的数据格式差异要求模型接入时需兼容多字段编码规则，因此需提前明确模型支持的输入格式。实时更新的行车数据要求模型调用的上下文更新频率匹配数据刷新节奏，避免处理过时信息。内嵌图片的巡检记录与客票凭证要求配置项支持多模态识别，否则无法解析附件内容。分散的系统数据源需通过私有代理传输，因此需配置专属的API端点与令牌，保障数据传输合规。长文档如月度调度总结需足够的token配额，否则会出现截断问题。

## 配置怎么定
以下配置逻辑适配FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `vision` | 开启 | 铁路运营内部数据包含设备巡检照片、客票图像凭证等多模态内容，需支持图像识别 |
| `maxContext` | 800–1200 字符 | 适配单条行车日志、客运工单的文本长度，避免上下文溢出 |
| `maxTokens` | 4000–6000 token | 满足月度调度总结、批量工单汇总等长文档的处理需求 |
| `quoteMaxToken` | 1500–2000 字符 | 限制引用内容的长度，避免冗余信息干扰模型输出 |
| `temperature` | 0.2–0.4 | 内部办公场景需稳定的标准化输出，不宜过度发散 |
| `AIPROXY_API_ENDPOINT` | 填写铁路内部私有部署的代理地址 | 保障内部数据传输安全，符合国央企数据合规要求 |
| `AIPROXY_API_TOKEN` | 按角色分配的专属令牌 | 实现权限隔离，避免跨部门数据泄露 |

## 容易做错的三处
- 现象：重启部署环境后，已配置的模型渠道与令牌信息丢失，需重新录入。原因：配置未持久化至本地存储目录，仅保存在临时运行内存中。
- 现象：启动FastGPT容器时出现架构不兼容报错，无法加载重排模型。原因：使用了适配AMD架构的镜像文件，未选择对应ARM架构的官方部署包。
- 现象：上传包含内嵌图片的PDF文档后，模型仅返回文本内容，未识别图片相关信息。原因：未开启`vision`配置项，或未接入支持多模态识别的模型接口。

## 怎么确认配好了
- 进入FastGPT v4.17.0的模型配置页面，确认`vision`开关处于开启状态，对应模型接口已标注支持多模态识别。
- 上传一条包含内嵌图片的测试PDF文档，触发模型调用，检查返回结果是否包含图片描述或解析内容。
- 重启部署环境，再次进入配置页面，确认已保存的API端点与令牌信息未丢失。
- 调用测试接口传入行车日志与巡检照片的混合数据，检查模型输出是否覆盖两类数据的解析结果。
