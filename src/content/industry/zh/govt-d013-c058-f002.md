# IT 服务台的员工服务台：向量模型与索引

## 这个品类的数据长什么样
IT服务台的员工服务台数据主要来源于员工提交的IT设备报修工单、系统权限申请记录、日常办公软件咨询日志、内部IT知识库文档。数据更新节奏分为实时与批量两类：实时更新对应即时提交的工单与咨询，批量更新为每日同步的历史归档数据。单条数据的结构包含工单唯一标识、提交人信息、问题描述、处理流程、解决结果、业务标签等字段，单位涉及工单编号、处理时长（分钟）、请求频次等，单条文档的长度差异较大，短则百余字的简单咨询，长则数千字的完整故障排查记录。

## 这些特征在「向量模型与索引」这一环带来什么约束
首先，实时与批量混合的更新节奏要求索引支持增量更新，避免全量重建带来的系统负载过高与延迟。其次，单条文档长度差异大的特点，要求分块策略具备灵活性，避免过碎的分块破坏上下文关联或过长的分块超出向量化限制。再者，多字段的文档结构要求明确指定需向量化的核心字段，避免冗余字段干扰向量计算精度。最后，高频的更新需求要求设置合理的索引刷新间隔，平衡实时性与系统资源消耗，防止索引滞后影响员工咨询的召回效果。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 匹配IT服务工单与咨询日志的平均内容长度，避免分块过碎导致上下文断裂，或过长导致向量化溢出 |
| 重叠长度 | 100–200 字符 | 保留工单前后步骤的关联信息，确保故障排查类长文档的向量召回覆盖完整流程 |
| `defaultToken` | 1500 token | 适配多数员工咨询问题的上下文长度，保障基础召回的完整性 |
| `maxToken` | 4000 token | 承载完整的故障排查流程与关联知识库内容，避免截断核心业务信息 |
| 单次召回上限 | 前 10 条 | 匹配IT服务台咨询的常见关联信息数量，避免过多冗余结果干扰员工判断 |
| 索引刷新间隔 | 300 秒 | 平衡实时性与系统负载，适配实时工单的更新需求 |

## 容易做错的三处
- 现象：索引重建任务持续超过24小时，界面显示「重建中」状态未结束。原因：未配置增量索引策略，全量重建全量历史工单数据，超出系统负载阈值。
- 现象：批量添加索引的请求返回参数错误，无法完成文档入库。原因：未正确设置`maxToken`参数，单条文档的分块内容超出token限制，导致向量化失败。
- 现象：搜索结果中出现多个不相关工单的混合内容，无法精准匹配目标工单。原因：未统一配置全局索引策略，采用单文档单索引的方式，未按照业务关联逻辑聚合索引分片，导致索引计算时无法精准关联目标工单的上下文。

## 怎么确认配好了
- 查看FastGPT v4.17.0的索引管理界面，确认各分片的索引任务状态均为完成，无堆积报错日志。
- 提交一条测试工单并等待索引刷新，执行相关关键词搜索，确认召回结果包含该工单的关联内容与处理流程。
- 检查向量化字段的配置项，确认仅包含问题描述、处理步骤等核心业务字段，无冗余字段参与向量计算。
- 查看系统定时任务日志，确认索引刷新间隔的触发逻辑符合预设的300秒配置，无异常触发或延迟情况。
