# IT资产盘点的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
本品类数据来源为资产管理系统、采购系统、财务固定资产模块、终端管理平台。日常产出资产台账、盘点表、领用归还单、报废申请四类标准化文档。数据更新节奏为月、季或年度周期。文档字段包含资产编号、设备名称、存放位置、使用人、采购日期、资产状态等，无自定义特殊单位，核心字段均为企业IT资产管理的通用业务字段。

## 这些特征在「上下文与 token」这一环带来什么约束
数据更新节奏偏慢，无需频繁触发知识库增量同步，可适当放宽上下文召回的时间范围。多类标准化文档的字段差异较大，需确保召回的上下文仅包含当前评审关联的资产相关字段，避免无关信息占用token配额。账实核对等核心环节依赖历史盘点数据，需保证足够的上下文长度覆盖完整业务链路，防止关键信息截断导致评审失误。资产权属与使用人字段为核心评审依据，需限制召回结果仅包含对应字段的有效内容，减少无效token消耗。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的界面与参数逻辑制定。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文 | 8000–12000 token | 覆盖多份资产台账、盘点表的核心字段内容，避免关键评审信息截断 |
| 单次引用最大token | 2000 token | 匹配单份资产文档的平均长度，防止单条引用占用过多上下文配额 |
| 搜索结果上限 | 前8条 | 限制召回的历史盘点记录数量，平衡上下文完整性与token消耗 |
| 上下文召回时间范围 | 近24个月 | 适配资产盘点的年度/季度更新周期，覆盖完整业务周期内的有效数据 |
| 重排开关 | 开启 | 优先召回与当前评审资产编号、使用人强相关的上下文，提升信息准确性 |

## 容易做错的三处
- 现象：离线部署的tokenizer服务请求外网资源报错，日志显示无法获取cl100k.tiktoken文件。原因：未配置本地tokenizer文件路径，系统默认尝试拉取外网资源。
- 现象：将单次搜索上限设置过高后，上下文无法正常发送给大模型。原因：过多的召回结果导致总token消耗超过配置阈值，系统自动过滤上下文内容。
- 现象：配置的最大上下文长度超过绑定大模型的支持上限后，大模型返回内容缺失或报错。原因：未匹配大模型的上下文窗口上限，超出部分被系统自动丢弃。

## 怎么确认配好了
- 进入FastGPT知识库的配置界面，核对上下文与token相关的设置项，确认参数取值符合预设规则。
- 提交一条资产盘点相关的评审请求，在大模型回复前的上下文预览区域，确认召回的内容包含当前评审的资产编号、使用人等核心字段。
- 检查系统运行日志，确认无token消耗超限、上下文截断或外部资源请求失败的报错记录。
- 调整单个配置项的取值，验证上下文召回的数量与总token消耗是否随配置变化。
