# Issue分拣与响应的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自GitHub或Gitee Issue、代码仓库版本日志、用户反馈的环境信息与问题复现说明。日常维护文档包含Issue模板、标签规则、历史回复记录与问题复现说明。数据更新频率通常为日或周，由社区提交的新Issue、代码变更与用户反馈触发更新。数据字段包含Issue标题、描述、标签、关联代码片段、用户环境信息与回复状态等。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据分散且token占用波动大，包含代码片段与用户环境信息，会导致上下文token占用难以预估。数据按日或周更新，要求上下文缓存需定期刷新以匹配最新的标签规则与代码变更。社区Issue数量较多，召回过多上下文会超出token上限，因此需要严格控制召回的上下文条数与单条数据的token配额。同时，Issue关联的代码片段长度差异显著，需根据关联模块的代码量调整上下文的token分配，避免影响问题分类与责任模块标记的准确性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文token配额 | 8000–12000 token | 匹配该品类单条Issue关联代码与描述的平均token占用，适配FastGPT v4.17.0的模型上下文上限 |
| 单次召回上下文条数 | 前3–5条 | 控制总token占用，防止冗余信息干扰Issue分类与责任模块标记 |
| 上下文刷新周期 | 每日1次 | 匹配数据日/周的更新频率，确保召回的标签规则与代码变更为最新版本 |
| 单条上下文最大token | 1500–2000 token | 适配Issue关联代码片段的长度波动，避免单条数据占用过多配额 |
| 召回内容过滤规则 | 仅关联当前Issue的代码与历史回复 | 缩小上下文范围，提升问题分类与复现信息补齐的准确性 |

## 容易做错的三处
- 现象：调整上下文召回条数后，仍未获取到对应Issue的历史回复，且出现无关领域的知识内容。原因：未开启仅关联当前Issue的上下文过滤配置，导致召回范围覆盖了全局知识库内容，干扰了Issue分拣的准确性。
- 现象：提交长代码关联的Issue时，任务执行失败并返回token超出上限的提示。原因：未限制单条上下文的最大token配额，导致总占用超出模型支持范围。
- 现象：配置刷新周期后，新添加的标签规则未被召回用于Issue分类。原因：设置的刷新周期与数据更新频率不匹配，未及时同步最新的标签与代码变更信息。

## 怎么确认配好了
- 提交测试Issue，查看召回的上下文是否仅包含该Issue关联的代码片段与历史回复，确认过滤规则生效。
- 调整配置项后，观察任务执行时的token占用日志，确认总占用未超出模型支持范围。
- 手动修改标签规则，等待配置的刷新周期结束后，查看召回的上下文是否包含最新的标签信息。
- 提交多条不同长度的Issue，确认单条上下文的token配额适配了不同长度的代码片段。
