# Pull Request评审的代码与变更评审辅助：工作流编排

## 这个品类的数据长什么样
该品类的数据主要来自代码仓库、CI流水线、Issue链接与贡献者提交的变更内容。日常关联文档包括PR说明、代码评审意见、CI结果与合并记录。数据字段包含PR编号、变更文件清单、评审意见状态、CI通过率、贡献者账号信息等。更新节奏通常为日度或周度，单次PR的评审数据随合并或驳回动作完成闭环。

## 这些特征在「工作流编排」这一环带来什么约束
数据来源分散要求工作流编排需对接代码仓库、CI系统等多类外部接口，需通过`nodeId`标记不同数据源节点的执行顺序。更新节奏限制了工作流的触发频次，仅应在PR创建、更新或合并请求发起时触发，避免无效执行。字段类型多样的特点要求工作流需通过`variables`统一存储跨节点的评审数据，便于后续环节调用。同时，最耗时的变更意图确认、测试结果检查等环节需拆分为独立子工作流，避免整体流程超时影响评审效率。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| 触发条件 | PR创建、更新或合并请求发起时 | 匹配PR评审的事件周期，避免无效执行 |
| 全局变量存储 | `variables`节点 | 统一管理跨环节的评审数据与字段映射 |
| 变更文件拉取上限 | 前10条 | 控制单次拉取的数据量，避免超时 |
| 流程超时阈值 | 600秒 | 适配CI流水线的常规执行时长 |
| 合并前置校验规则 | CI通过率100%、无未解决评审意见 | 符合常规PR合并的前置要求 |
| 二次评审触发条件 | 变更文件超过5个时 | 针对复杂变更增加额外校验环节 |
| 界面兼容配置 | FastGPT v4.17.0 版本标准节点 | 确保工作流与平台版本兼容 |

## 容易做错的三处
- 现象：工作流运行后未返回指定项目的分支差异内容。原因：未在工作流编排中添加代码仓库分支对比的数据源配置。
- 现象：工作流无法获取贡献者姓名，仅返回账号ID。原因：未通过`variables`节点映射代码仓库贡献者的公开信息字段。
- 现象：免登录对话窗口的思考过程展示无法关闭。原因：未在工作流的对话节点中配置隐藏思考过程的参数。

## 怎么确认配好了
- 手动创建一条测试PR，触发工作流执行，查看节点日志是否拉取了正确的变更文件与CI数据。
- 检查`variables`节点的存储内容，确认是否包含PR说明、评审意见等预期字段。
- 模拟变更文件超过5个的场景，确认工作流是否自动启动二次评审环节。
- 查看免登录对话窗口的配置，确认头像与思考过程开关已按需求设置。
