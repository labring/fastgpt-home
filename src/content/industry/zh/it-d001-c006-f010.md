# Pull Request评审的代码与变更评审辅助：引用来源与溯源

## 这个品类的数据长什么样
本品类的数据主要来自代码仓库、CI流水线、Issue链接与贡献者提交记录。日常关联文档包括PR说明、代码评审意见、CI执行结果与合并记录。数据更新节奏通常为日更或周更，核心字段包含变更代码范围、提交哈希值、评审意见ID、合并状态与关联Issue编号，无统一固定单位，随对应仓库与流水线的配置变化。

## 这些特征在「引用来源与溯源」这一环带来什么约束
数据多源分散的特征要求溯源环节需同时关联代码仓库、CI与Issue的唯一标识，避免跨数据源混淆。更新节奏的日/周特性要求溯源需匹配对应时间窗口内的最新提交与评审记录，防止引用过期数据。文档结构分散的特点要求溯源需按PR维度聚合关联信息，确保评审时可快速定位变更的完整来源。变更意图确认环节的高耗时属性，也要求溯源环节可快速追溯变更的原始提交与评审意见，减少重复核对的成本。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `quoteMaxToken` | 8000–12000 token | 适配PR评审中代码片段与关联文档的总长度，避免截断关键溯源信息 |
| `responseData` | 包含代码仓库地址、CI执行ID、Issue链接 | 覆盖PR评审所需的全部溯源数据源，确保可关联完整变更链条 |
| `detail` | 开启完整元数据模式 | 保留评审意见、提交记录的全部细节，便于快速定位变更来源 |
| 单次召回上限 | 前10条关联记录 | 控制溯源返回的信息量，避免过载影响评审效率 |
| 时间窗口匹配 | 按PR创建前后7天筛选 | 确保仅召回对应PR周期内的关联数据，排除过期信息 |

## 容易做错的三处
- 配置完成后仅返回引用内容，未生成代码评审辅助的分析内容。原因是`responseData`配置仅开启了数据源返回，未绑定对应的生成逻辑，导致仅展示溯源信息而无分析。
- 溯源结果中出现非当前PR的提交记录。原因是未设置按PR创建时间匹配的时间窗口，召回了跨周期的过期数据。
- 部分PR的溯源信息中缺少CI执行结果。原因是未在`responseData`的配置项中添加CI结果的召回规则，导致数据源覆盖不全。

## 怎么确认配好了
- 进入FastGPT v4.17.0的对应PR评审工作流配置页，查看`quoteMaxToken`的配置值是否在8000–12000 token区间。
- 触发一次测试PR评审，检查返回的溯源信息是否包含代码仓库、CI结果与Issue链接三类数据。
- 验证时间窗口配置，手动输入一个早于PR创建时间的日期，确认系统不会召回该时间段内的无关数据。
- 检查`detail`配置是否开启，确认评审结果中显示了提交哈希与评审意见的完整元数据。
