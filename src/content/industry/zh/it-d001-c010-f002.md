# 事件响应与故障处理的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
本品类的核心数据来自监控告警、日志平台、APM工具与用户反馈。日常处理的文档包含故障工单、事件时间线、应急预案、故障通报，核心字段包括事件标识、发生时间、影响范围、止损操作记录、通报对象等。数据更新节奏为实时同步告警信息，每次事件触发后生成完整的事件文档与处置记录，无固定批量更新周期，需优先关联最新的告警与处置数据以保障时效性。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类的数据实时更新且单次事件的关联文档体量随处置进度逐步扩大，上下文与token环节需适配动态变化的输入源。故障工单、时间线等文档的字段类型差异较大，需精准匹配关联字段提取有效信息，避免无关数据占用token配额。实时告警的高频推送可能导致上下文刷新频繁，需限制单次加载的有效数据量，防止token超限导致请求失败。同时，对外通报的合规性要求需确保上下文仅包含已确认的处置信息，避免未验证内容进入上下文影响决策准确性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 本品类单次事件的关联文档总量较大，需预留足够token容纳核心处置信息，避免截断关键的故障与止损内容 |
| `quoteMaxToken` | 1500–2000 字符 | 故障工单与时间线的单条记录长度差异大，限制单条引用的token占用，平衡上下文完整性与请求效率 |
| 单次加载的事件文档数 | 前3–5条 | 优先加载最新的告警与处置记录，减少非核心的历史数据占用token配额 |
| 上下文刷新间隔 | 按实测标定 | 适配实时告警的更新节奏，避免频繁刷新导致的token消耗波动 |
| 上下文内容过滤阈值 | 保留与当前事件关联度≥70%的内容 | 过滤无关的历史告警与非关联文档，降低token的无效占用 |

## 容易做错的三处
- 现象：调用时返回token超限错误，响应状态码为413。原因：未针对本品类的实时关联文档调整`maxContext`配额，导致单次请求的token占用超出预设限制。
- 现象：访问私有化部署的FastGPT应用时返回404错误。原因：未将应用访问上下文配置为`/fastgpt`，导致路由匹配失败，无法正常加载应用界面。
- 现象：搜索结果未关联当前故障事件的上下文信息。原因：未将实时告警与事件时间线的内容整合到搜索请求的上下文参数中，导致搜索仅基于通用问题生成结果，无法匹配当前事件的专属信息。

## 怎么确认配好了
- 登录FastGPT v4.17.0的应用管理后台，查看`maxContext`与`quoteMaxToken`的配置值，确认取值在预设的8000–12000 token、1500–2000字符范围内。
- 模拟触发一次测试告警，查看上下文加载的文档数量与内容，确认仅包含前3–5条最新的核心故障处置记录。
- 访问应用的`/fastgpt`路径，确认可以正常加载应用界面，无路由错误提示。
- 发起一次基于测试故障工单的请求，查看返回结果是否关联了当前测试事件的上下文信息，无无关内容混入。
