# 代码安全审计的代码与变更评审辅助：引用来源与溯源

## 这个品类的数据长什么样
该品类的数据主要来自源代码仓库、依赖清单、静态代码扫描（SAST）工具与公开漏洞库，更新节奏随项目版本或迭代周期推进。日常产出的文档包含代码审计报告、漏洞证明、修复建议与复测记录，各文档字段包含漏洞编号、影响范围、代码行号、修复代码片段与风险等级，无固定统一单位，仅按项目维度归档。

## 这些特征在「引用来源与溯源」这一环带来什么约束
数据来源分散且随版本更新，要求溯源时需关联对应版本的代码仓库快照与依赖版本清单，避免跨版本引用导致的信息错位。文档结构多样，需针对不同文档类型匹配不同的引用规则，防止混淆审计报告、漏洞证明与复测记录中的不同字段。更新频率较高，需确保引用的溯源信息与当前审计版本一致，防止出现过时数据。同时，高危漏洞的溯源需覆盖完整攻击路径，对上下文长度与召回范围提出更高要求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | 匹配代码审计报告与漏洞证明的平均长度，确保完整引用关键代码片段与风险说明，适配FastGPT v4.17.0的上下文处理逻辑 |
| `responseData` | 包含引用来源字段 | 要求返回结果中携带对应文档的来源路径、版本号与行号，同时支持将引用的知识库内容嵌入返回正文，满足溯源与展示需求 |
| `detail` | 开启全量详情 | 覆盖数据流追踪与修复方案复核的全量信息，避免遗漏关键审计节点的细节 |
| 最大上下文长度 | 16000 token | 适配多源数据拼接后的总长度，防止截断重要的审计环节描述 |
| 单次召回上限 | 前10条 | 覆盖常见的多漏洞场景，同时避免过多冗余信息干扰评审 |

## 容易做错的三处
- 发起请求后接口连通但无content返回值。原因是未正确配置`responseData`参数，未指定需要返回的引用来源与正文内容字段，导致返回结果仅包含空的响应体。
- 引用的审计文档内容排版杂乱。原因是未设置`quoteMaxToken`的合理区间，导致过长的代码片段被截断或拼接，破坏原文排版结构。
- 溯源结果出现乱码。原因是未匹配对应代码仓库的编码格式，未在引用配置中指定正确的字符集参数，导致读取源代码时出现编码错误。

## 怎么确认配好了
- 发起一次测试请求，检查返回结果中是否包含`responseData`字段，且字段内包含源代码仓库路径、漏洞编号等溯源信息。
- 查看返回的引用内容，确认代码片段未被过度截断，符合`quoteMaxToken`设置的长度范围。
- 模拟提交带非ASCII字符的代码片段，验证返回结果无乱码，确认字符集配置生效。
- 对比当前审计项目的版本号，检查引用的溯源信息与当前版本的代码仓库快照一致。
