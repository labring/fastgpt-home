# 代码评审与合并管理的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
本品类的数据主要来自Git仓库、CI流水线、静态扫描报告与缺陷库。日常关联文档包含合并请求、代码评审意见、提交记录与分支策略说明。数据更新节奏为每日或每次代码提交后触发，字段包含变更范围、提交哈希、评审人标识、缺陷关联编号等，无固定统计口径，仅随研发动作实时生成。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类的数据关联多源研发流程产出，单次变更的上下文可能包含多段提交代码、过往评审意见与关联缺陷详情，整体长度波动较大。高频更新的特性要求上下文需实时同步最新提交与评审记录，避免因数据滞后导致评审偏差。同时，多源数据的混合输入会占用较多token配额，若未合理限制，可能超出大模型上下文上限，影响变更影响判断与评审沟通效率。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 前10–15条合并请求上下文 | 本品类的核心上下文为近期合并请求与评审记录，过多旧数据会占用token配额，影响当前变更的语义判断 |
| `quoteMaxToken` | 8000–12000 token | 覆盖单次变更的代码片段、评审意见与关联缺陷的总长度，适配多数大模型的基础token上限 |
| 最大上下文刷新间隔 | 每提交后刷新 | 匹配本品类数据日/每提交的更新频率，确保上下文始终同步最新研发动作 |
| 上下文召回条数 | 前5条活跃评审记录 | 避免冗余数据干扰当前变更的评审判断，聚焦当前评审的业务范围 |
| 按实测标定 | 按团队合并请求的平均长度调整 | 适配不同规模团队的代码评审上下文需求 |

## 容易做错的三处
- 配置`maxContext`为20条以上时，出现上下文污染现象。原因是本品类的评审上下文包含多段独立的合并请求变更，过多旧数据会混入当前评审的语义范围，导致大模型混淆不同变更的业务逻辑。
- 对话明细中显示的上下文条数与设置值不符，例如设置30条仅显示2条。原因是未匹配本品类数据的更新节奏，上下文刷新间隔过长，未同步最新的评审记录与提交内容。
- 大模型提示上下文token数超标。原因是未限制`quoteMaxToken`的配额，单次输入的代码片段与评审意见总长度超出大模型支持的token上限。

## 怎么确认配好了
- 在FastGPT v4.17.0环境下，发起一次模拟合并请求评审，查看对话明细中显示的上下文条数是否与`maxContext`的设置值匹配。
- 提交包含多段代码与多条评审意见的变更，检查大模型是否能准确关联当前变更的业务语义，未出现无关旧上下文的干扰。
- 提交超出常规长度的代码变更，查看大模型是否返回合理的上下文处理结果，未出现token超标的报错。
- 触发一次新的代码提交，检查上下文是否自动刷新为最新的评审记录与提交内容。
