# 供应商与设备到货管理的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
该品类的数据通常来自项目采购对接的ERP系统、供应商发货单、物流跟踪信息、设备厂商后台管理端口。日常产出的文档包含采购订单、到货验收单、序列号清单、发票资料，字段覆盖采购单号、设备型号、序列号、到货日期、验收状态、供应商信息等。数据更新节奏以单项目交付为单位，单笔采购订单对应一次数据更新，常规批量到货场景下每周同步一次全量批次数据。

## 这些特征在「上下文与 token」这一环带来什么约束
多来源的数据格式差异要求上下文拼接时先完成字段对齐，避免混杂无效信息占用token配额。单项目单批次的更新节奏，要求上下文范围限定在当前待评审的采购或到货批次内，防止拉取过期的历史数据干扰评审。核心字段如设备型号、序列号、采购单号属于高优先级上下文内容，需优先保留，非关键的物流跟踪备注可做精简处理。批量到货场景下的多条目数据，要求上下文token分配适配单批次条目规模，避免单次加载过多数据超出上下文上限。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | `800–1200 字符` | 适配单批次到货数据的字段总量，避免超出模型token限制 |
| `quoteMaxToken` | `1500–2000 token` | 优先覆盖采购订单、序列号清单的核心字段，满足评审所需的上下文完整性 |
| 分块长度 | `300–500 字符` | 匹配单份文档（如单张到货验收单）的平均篇幅，避免分块过碎导致上下文断裂 |
| 重叠长度 | `50–100 字符` | 保证跨分块的关键信息（如设备型号）不会被拆分丢失 |
| 上下文过滤阈值 | 按实测标定 | 过滤掉与当前评审任务无关的历史批次数据，减少无效token消耗 |
| 单次召回条数 | 前3条 | 匹配单项目待评审的核心供应商与设备数据，避免召回过多冗余条目 |

本文基于FastGPT v4.17.0版本的配置逻辑编写。

## 容易做错的三处
- 配置`maxContext`时未设置上下文过滤，直接拉取全量历史数据，导致返回结果中出现重复的设备型号条目，触发数据库重复键错误。原因是未限定上下文范围为当前待评审批次，将过期数据纳入了上下文。
- 未调整分块长度，直接使用默认值处理Excel源数据，导致每个数据块token消耗过高，触发token超限报错。原因是分块长度未匹配该品类单条设备数据的平均字段长度，导致块内数据冗余。
- 未正确配置`quoteMaxToken`，导致在调用代理接口时，因token配额不足触发请求重试超限报错。原因是未根据核心文档的字段总量调整token配额，导致单次请求超出接口限制。

## 怎么确认配好了
- 导入单份采购订单文档，检查上下文拼接后的内容是否仅包含当前批次的核心字段，无过期历史数据。
- 提交变更评审任务，查看token消耗统计，确认`quoteMaxToken`的取值未超出当前模型的单次请求上限。
- 触发分块处理测试，检查每个数据块的长度是否符合预设的分块长度，无过度拆分或过长的块。
- 调用代理接口提交测试请求，确认接口返回结果无重复条目，且召回的内容与当前评审任务强相关。
