# 供应链安全与开源依赖治理的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
本品类服务于安全团队、研发效能团队与开源治理办公室，数据主要来自包管理器、代码仓库、公开漏洞库与许可证数据库，更新频率为每日或每软件版本发布时。日常产出的文档包含SBOM清单、依赖风险报告、许可证合规清单以及漏洞修复工单，数据字段涵盖组件名称、版本号、许可证类型、漏洞CVE编号、修复状态等，单位多为组件条目、版本号、风险等级标识。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类的数据分散来自多类外部源，字段格式差异显著，需精准匹配上下文片段以完成依赖识别与风险关联；更新频率为每日或每版本发布，要求上下文同步及时，避免引入过期依赖数据；日常文档包含多组件条目，单次处理的token消耗随组件数量增长，需合理限制上下文规模；修复工单关联代码变更与依赖风险，需优先分配token给高关联度的变更与风险片段，避免无效token占用。

## 配置怎么定
以下配置项适配FastGPT v4.17.0版本：
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 8000–12000 token | 适配SBOM清单与依赖报告的多组件条目规模，避免token超限 |
| 单段引用最大token数 | 1500–2000 字符 | 匹配单条依赖组件的完整信息长度，确保风险描述完整 |
| 分块重叠长度 | 200–300 字符 | 避免依赖组件的跨块拆分，保留版本与风险关联的上下文连续性 |
| 单次召回上限 | 前10条 | 聚焦高优先级的依赖风险条目，控制整体token消耗 |
| `maxContext` | 按实测标定 | 适配私有化部署的硬件资源与业务并发量 |
| `quoteMaxToken` | 1200–1800 token | 对齐单条漏洞报告或许可证详情的标准长度 |

## 容易做错的三处
- 现象：配置`maxContext`过大时，出现token超限报错或请求超时。原因：未结合SBOM的组件数量调整上下文长度，导致token占用超出平台限制。
- 现象：Excel格式的依赖清单导入后，依赖匹配结果缺失。原因：分块重叠长度设置过小，导致跨块的依赖版本与风险关联信息断裂。
- 现象：连续运行依赖识别任务后出现数据冲突相关报错。原因：未限制单次召回的条目数量，导致上下文重复加载同一依赖组件的信息，引发重复数据问题。

## 怎么确认配好了
- 导入一份标准SBOM清单，检查上下文加载的组件条目数量与原清单一致。
- 触发一次变更评审任务，查看token消耗统计，确认未超出预设的`maxContext`限制。
- 对比依赖风险报告的匹配结果，确认高风险组件的关联信息完整未被截断。
- 连续运行3次以上的依赖识别任务，检查无重复数据冲突报错。
