# 值班排班与交接的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
本品类的核心数据来自SRE团队与运维经理的日常运维产出，包括排班系统生成的值班表、故障工单关联的交接记录、组织通讯录导出的升级联系人清单，以及每日更新的值班日报。数据更新频率分为日度（值班表、值班日报）和周度（升级联系人清单），文档结构包含值班时段、交接事项、联系人联系方式、告警触发时间、未结工单编号等字段，不同来源的数据字段存在细微差异，无统一标准化格式。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类的数据来源分散且格式不统一，不同数据源的更新节奏差异较大，导致上下文拼接时需区分数据的时效性，避免过时的值班表或过期的交接记录占用token配额。未结事项关联的故障工单编号属于关键业务信息，需优先保留完整内容，防止token截断导致关键字段丢失。时序性的值班时段数据要求上下文按时间排序，确保评审时能按值班顺序关联对应事件。同时，数据量随团队规模增长，需严格控制上下文总长度，避免超出token限制导致调用失败。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配值班排班类文档的总长度，包含值班表、交接记录、升级清单等多份数据 |
| `quoteMaxToken` | 1500–2000 token | 优先保留未结交接事项、关联故障工单的完整内容，避免关键字段被截断 |
| 最大上下文排序 | 按时间倒序 | 匹配值班场景的时序数据特征，优先展示最新的交接记录与值班安排 |
| 上下文更新频率 | 按日同步 | 匹配值班表的日更新节奏，避免过时数据占用token配额 |
| 单次召回上限 | 前5条 | 控制token消耗，同时覆盖近一周的值班与交接核心数据 |

## 容易做错的三处
- 现象：内网部署后系统日志提示token校验失败，启动过程中出现异常重启。原因：未配置内网数据源的上下文同步白名单，系统尝试拉取外部资源触发默认token校验规则，导致调用失败。
- 现象：配置自定义openAPI token后，代码评审辅助的token消耗仍计入默认账户。原因：未在系统设置中绑定自定义token与值班排班场景的上下文调用权限，导致系统仍使用默认配额。
- 现象：代码评审辅助返回的交接记录缺失未结工单编号字段。原因：`quoteMaxToken`设置值过小，截断了包含关键字段的交接记录内容，导致核心业务信息丢失。

## 怎么确认配好了
- 查看FastGPT v4.17.0的系统配置日志，确认`maxContext`和`quoteMaxToken`的配置参数已正确加载。
- 手动触发一次交接记录检索任务，检查返回内容的token占用量符合预设的`quoteMaxToken`取值范围。
- 对比不同时段的上下文数据，确认检索结果按时间倒序排列，最新的值班安排与交接记录优先展示。
- 在内网环境测试数据源同步流程，确认未出现token校验相关的报错提示。
