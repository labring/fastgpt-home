# 关卡内容制作的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
关卡内容制作的日常数据来源包括关卡编辑器、美术资源库、玩家测试数据与缺陷系统。更新节奏为周度或每版本迭代一次，日常文档包含关卡设计稿、资源需求表、测试反馈单与版本提交记录。其中关卡设计稿包含路径节点坐标、资源ID、触发条件等结构化字段，测试反馈单包含卡关位置、玩家反馈内容等非结构化字段，版本提交记录则记录每次变更的内容与提交人信息。

## 这些特征在「上下文与 token」这一环带来什么约束
关卡内容数据的结构化与非结构化混合特征，要求上下文需区分结构化的版本提交记录与非结构化的测试反馈，避免无关数据占用token。周度/版本级的更新节奏，意味着上下文无需保留超过1-2个版本的历史数据，否则会导致token溢出且引入无效内容。大量的坐标、资源路径等长文本内容，会提升单次上下文的token消耗，需要严格控制上下文的总长度与召回条数，避免超出模型的token上限。同时，关卡内容的变更直接影响游戏体验，上下文必须精准匹配当前版本的有效数据，否则会导致变更评审的结果偏离实际需求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 关卡内容数据包含坐标、资源路径等长文本，单次上下文需覆盖1-2个版本的提交记录与测试反馈，按实测标定 |
| `quoteMaxToken` | 2000–3000 token | 需引用的关卡设计稿片段、测试反馈单内容较长，避免单条引用占用过多上下文空间 |
| 上下文召回条数 | 前6–10条 | 匹配最近的版本提交与测试反馈，避免过多旧数据消耗token |
| 历史上下文保留周期 | 每7天重置 | 关卡内容按周/版本更新，旧版本数据无需保留在当前上下文 |
| 内容相似度阈值 | 0.7–0.8 | 筛选与当前关卡任务强相关的文档，排除无关的美术资源库通用内容 |

## 容易做错的三处
- 现象：调用模型查询关卡数据时，FastGPT界面显示的token消耗与实际API调用的token消耗不一致。原因：界面统计的token包含上下文嵌入、预处理环节的消耗，而API仅统计模型推理的token消耗，两者统计范围存在差异。
- 现象：变更评审时返回的上下文包含大量旧版本关卡数据，导致模型输出偏离当前版本内容。原因：未配置历史上下文保留规则，旧版本的关卡设计稿、测试反馈被持续纳入上下文，占用过多token且引入无效信息。
- 现象：在工作流中配置MCP工具时，无法传递工作流全局变量的token。原因：未将全局token变量绑定到MCP工具的入参配置项，上下文变量未正确映射到工具调用参数。

## 怎么确认配好了
- 打开FastGPT v4.17.0的上下文预览面板，确认召回的文档均为当前版本的关卡设计稿、测试反馈单，无旧版本无关内容。
- 运行包含MCP工具的工作流，确认工作流全局变量的token可正常传递到工具的入参字段。
- 对比界面显示的token消耗与实际API返回的token消耗，确认两者的统计差异符合配置规则。
- 调整上下文相关配置后，验证变更评审的输出结果是否聚焦于当前关卡的变更内容，无冗余信息。
