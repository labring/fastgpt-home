# 关卡内容制作的代码与变更评审辅助：工作流编排

## 这个品类的数据长什么样
这个品类的数据主要来自关卡编辑器、美术资源库、玩家测试数据与缺陷系统。日常产出的文档包含关卡设计稿、资源需求表、测试反馈单与版本提交记录，数据字段涵盖关卡路径节点坐标、资源挂载标识、测试反馈的卡关节点编号、版本提交的变更哈希值等。数据更新节奏为每周迭代或每版本发布前同步，核心数据围绕具体地图布局、任务触发逻辑与资源摆放规则生成。

## 这些特征在「工作流编排」这一环带来什么约束
由于数据来源分散且更新节奏随版本波动，工作流编排需适配多源数据的格式对齐要求。关卡设计稿与版本提交记录的字段差异较大，需在编排中设置统一的数据映射规则。玩家测试数据与缺陷系统的反馈存在非结构化内容，需在工作流中加入预处理节点过滤无效信息。同时，版本提交的变更哈希值需与评审节点绑定，确保每一次评审都对应明确的代码或资源变更，避免评审内容与实际提交内容脱节。每周或每版本的集中更新节奏，要求工作流具备批量处理多份关联文档的能力，避免单次评审耗时过长影响版本交付进度。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 全局变量绑定 | 绑定`variables`中的布尔值字段 | 适配评审节点对关卡状态的判断需求，确保开关状态与当前版本的关卡配置同步 |
| 节点ID绑定 | 绑定`nodeId`字段 | 确保评审节点与具体变更条目一一对应，避免评审混淆 |
| 触发条件配置 | 按版本提交的变更哈希值触发 | 对应品类中每一次变更都需评审的业务规则，避免无效评审 |
| 多模态识别设置 | 开启图片识别 | 可识别关卡编辑器导出的布局截图，辅助评审人员快速定位资源摆放问题 |
| 工具输出处理 | 隐藏工具调用结果 | 避免评审流程中冗余信息干扰核心评审逻辑 |
| 重试阈值设置 | 3次重试，间隔60秒 | 应对MongoDB副本集主节点切换时的断连问题，保障数据拉取稳定性 |
| 批量处理上限 | 前10份关联文档 | 适配每周或每版本的更新节奏，避免单次工作流处理过载 |

以上配置项均基于FastGPT v4.17.0版本的功能逻辑制定。

## 容易做错的三处
- 工作流判断器节点无法正确识别`variables`中的布尔型全局变量状态。原因是未将目标变量绑定到判断节点的条件配置中，导致判断逻辑无法读取对应状态。
- 多模态识别节点开启图片识别后，返回无法提供图片内容的提示。原因是未在工作流中配置图片格式校验步骤，非标准格式的关卡布局截图无法被正确解析。
- 工作流运行时出现MongoDB连接中断且无法自动重连的报错。原因是未针对副本集主节点切换场景配置重连逻辑，主节点漂移后连接无法恢复。

## 怎么确认配好了
- 提交一份测试用的版本提交记录，检查工作流是否自动触发评审节点。
- 上传一张关卡编辑器导出的标准格式截图，确认多模态识别节点可以返回有效解析结果。
- 配置`variables`中的布尔型全局变量为不同取值，验证判断器节点的开关逻辑是否正确触发。
- 运行一次工具调用流程，确认调用结果未在界面中显示，仅保留核心评审内容。
