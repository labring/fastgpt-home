# 原型与交互设计的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
该品类的典型主体为产品设计师、交互设计师与前端产品小组，日常产出的文档包含交互原型、页面流程图、组件说明与评审记录。数据主要来源于Figma或Axure文件、团队内部设计系统、用户反馈与可用性测试记录，更新频率通常为每周或每版本迭代一次。文档结构以页面操作路径、组件属性、状态流转为核心字段，无统一强制的单位规范，仅按设计场景标注尺寸、交互逻辑说明等内容。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的文档以页面交互细节、组件属性为核心，单份内容跨度大且多为非代码类文本，在上下文与token处理环节需避免拆分后丢失页面级操作路径的关联逻辑。高频的周/版本级更新要求上下文同步机制适配增量修改，避免重复处理全量文档。同时，需合理设置`maxContext`与`quoteMaxToken`参数，适配设计文档的非标准化文本结构，确保评审关联的上下文不被截断，且过滤低关联的历史记录。

## 配置怎么定
本配置指南适配FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 800–1200 字符 | 适配交互原型、评审记录的单页内容长度，避免截断核心操作路径说明 |
| `quoteMaxToken` | 600–800 token | 适配组件说明、页面流程图的细节密度，确保评审关联的上下文完整 |
| 上下文召回条数 | 前3–5条 | 匹配设计师日常评审的关联文档范围，减少无关内容占用token |
| 上下文匹配阈值 | 按实测标定 | 适配设计文档的非标准化文本结构，过滤低关联的历史评审记录 |
| 单次更新处理量 | 1–2 个版本片段 | 适配周/版本级的更新频率，避免单次token消耗过高 |

## 容易做错的三处
- 现象：交互原型拆分后，相邻页面的操作路径上下文关联失效，评审时出现逻辑断层。原因：未按页面层级配置上下文召回规则，仅按单段文本拆分，导致拆分后的片段丢失跨页关联逻辑。
- 现象：变更评审时，历史修改记录未被正确关联到当前原型片段，分类结果偏向兜底类别。原因：未启用上下文同步机制，仅基于当前片段进行匹配，未引入历史评审的关联数据。
- 现象：处理Axure导出的大型文档时，出现token溢出报错，单次处理耗时过长。原因：未限制`maxContext`的取值上限，导致单份大体积原型文件占用过多token配额。

## 怎么确认配好了
- 导入一份典型的交互原型与评审记录，检查拆分后的片段是否保留页面级的操作路径关联。
- 发起一次变更评审请求，核对召回的上下文是否包含当前评审相关的历史记录与组件说明。
- 查看token消耗统计，确认单次处理的token用量符合平台的常规范围。
- 模拟一次高频更新场景，检查上下文是否能同步最新的修改内容。
