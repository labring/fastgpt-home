# 售前技术方案的代码与变更评审辅助：上下文与 token

本文档基于FastGPT v4.17.0版本编写。

## 这个品类的数据长什么样
该品类的核心数据来自客户访谈记录、公开招标文件、厂商产品资料及历史项目方案。日常产出的文档包含技术方案书、客户需求调研表、报价清单与演示脚本，单份文档的核心模块包括技术路线描述、实施边界界定、报价项明细与演示流程设计。数据更新以单售前项目为周期，通常每单或每周更新一次，不同项目间的文档结构与字段存在一定共性，但核心内容需匹配当前客户的具体需求。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据来源分散且存在重复内容，需通过精准的上下文筛选避免冗余信息占用token配额。单份售前文档的核心内容通常在数千到万级字符，过长的上下文会超出token限制导致关键信息截断，影响评审准确性。数据更新频率为单项目周期内的按需调整，无需长期留存跨项目的上下文，因此可通过会话级上下文管理减少token资源浪费。同时，文档的核心字段集中在技术路线与实施边界，上下文召回需优先匹配这些字段，避免无关内容干扰评审逻辑。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | `8000–12000 token` | 售前技术方案单份核心内容通常在6000-10000字符，匹配token限制避免截断关键评审信息 |
| `quoteMaxToken` | `3000–5000 token` | 单份引用的历史方案片段不宜过长，避免上下文过载影响评审效率 |
| 单次召回上限 | 前6条 | 售前方案的参考资料通常不超过6份核心历史方案与厂商资料，过多召回会占用过多token |
| 上下文刷新触发规则 | 按需求变更触发 | 售前方案仅在客户需求调整时更新，无需频繁刷新上下文 |
| 上下文保留时长 | 7天 | 单售前项目周期通常不超过7天，到期自动清理释放token资源 |
| 全局token配额调整 | 按函数调用动态分配 | 适配开源版灵活调整token配额的需求，匹配不同售前项目的资源占用规模 |

## 容易做错的三处
- 现象：内网离线部署后服务频繁重启，日志提示`failed`。原因：未针对离线环境调整`maxContext`的本地token分配，默认配置的token阈值超出离线容器的内存配额。
- 现象：配置自定义openapi token后，知识库搜索和问题优化仍产生扣费。原因：未将上下文关联的token调用绑定到自定义token配额，默认使用平台公共调用额度。
- 现象：无法清除会话上下文信息。原因：未设置上下文自动清理的触发条件，导致会话缓存持续占用token资源未释放。

## 怎么确认配好了
- 上传单份完整的售前技术方案文档，检查返回的代码与变更评审结果未出现核心技术路线或实施边界的内容截断，验证`maxContext`配置生效。
- 导入3份以上同类型历史项目方案文档，检查召回的参考片段长度符合`quoteMaxToken`的设定，验证引用token限制生效。
- 修改客户需求调研表中的核心字段，检查上下文是否按设定的触发规则完成更新，验证上下文刷新配置生效。
- 等待配置的上下文保留时长后，检查会话缓存是否自动释放，验证上下文清理规则生效。
