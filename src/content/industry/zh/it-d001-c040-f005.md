# 售前技术方案的代码与变更评审辅助：多轮对话与提示词

## 这个品类的数据长什么样
该品类的数据主要来源于客户访谈、招标文件、厂商产品资料与历史项目方案。日常产出的文档包含技术方案书、客户需求调研表、报价清单与演示脚本，数据以单售前项目为单位更新，更新频率为每单或每周。文档结构围绕客户需求、技术路线、实施边界与报价展开，核心字段包含客户名称、招标编号、方案版本与需求条目，无统一固定的量化单位，仅随单个项目的具体需求调整。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
单项目为单位的数据组织方式要求多轮对话必须绑定专属标识，避免跨项目数据混杂。每周一次的更新频率决定了上下文窗口不宜过长，否则易加载过期或无关的历史方案内容。围绕需求澄清、方案边界设计的核心业务环节，要求多轮对话需聚焦当前项目的需求条目，提示词需精准匹配当前项目的专属字段，避免生成脱离当前项目的通用内容。同时，单项目文档的非标准化结构，要求提示词需具备灵活适配不同文档类型的能力，确保评审逻辑与当前售前方案对齐。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文窗口 | 保留最近1200字符的对话与关联文档片段 | 适配单项目每周更新的节奏，避免加载过期或无关数据 |
| 会话历史过滤规则 | 按售前项目编号过滤历史记录 | 实现单项目会话隔离，避免跨项目数据混杂 |
| 提示词变量配置 | 注入客户名称、招标编号、方案版本号 | 让提示词精准匹配当前售前方案的专属信息 |
| 对话历史保留条数 | 仅保留最近15条有效对话 | 控制API调用时的数据传输量，提升响应速度 |
| 提问自动优化 | 开启自动优化用户提问 | 适配售前顾问的非标准化提问习惯，提升检索与评审准确性 |

## 容易做错的三处
- 现象：调用历史记录接口时返回全应用的会话数据，无法按项目编号过滤。原因：未配置会话历史过滤规则，或未绑定项目专属标识，导致会话隔离失效。
- 现象：对话响应超时，或返回结果为空。原因：未限制最大上下文窗口大小，加载了过多历史文档与对话片段，超出API处理上限。
- 现象：生成的售前方案内容与当前项目无关，混入了历史项目的信息。原因：未注入项目专属变量，提示词无法精准匹配当前项目的需求与边界。

## 怎么确认配好了
- 发起测试对话，输入预设的售前项目编号，查看历史记录接口返回的会话是否仅包含该项目的对话内容。
- 查看上下文窗口配置，确认加载的对话与文档片段长度未超过预设的字符限制。
- 检查提示词变量配置，确认已注入当前项目的专属字段，如客户名称、招标编号等。
- 发起多轮连续提问，验证系统是否能基于历史对话内容延续售前方案的评审逻辑。
