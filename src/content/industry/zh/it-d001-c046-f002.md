# 安全基线检查的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
本品类的数据来自服务器配置、中间件配置、安全设备策略及基线工具输出。日常产出基线检查表、配置核查记录、整改建议、例外审批单四类文档，字段包含配置项ID、合规状态、核查时间、整改要求等，无统一固定单位。数据更新频率为月或季度，随组织安全基准调整或合规审计周期同步更新，单次核查数据量随设备规模扩大而增加。

## 这些特征在「上下文与 token」这一环带来什么约束
安全基线检查的数据来源分散且格式各异，需整合多源配置信息作为上下文，会占用较多token配额；更新频率低但单次核查数据量较大，需控制上下文窗口避免溢出，同时覆盖跨周期的合规记录。文档类型多且字段分散，需精准匹配检索到的基线检查表、核查记录等内容，限制无效token消耗。审计场景下需关联历史例外审批单，上下文长度需兼顾完整性与token使用效率，避免因截断导致合规信息丢失。

## 配置怎么定
以下配置适用于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 安全基线检查需整合多台设备的配置数据与历史合规记录，该区间可覆盖单批次核查的核心上下文，避免关键配置项被截断 |
| `quoteMaxToken` | 2000–3000 token | 单份基线检查表或配置核查记录的核心字段内容集中在此区间，优先加载合规状态、整改要求等关键信息 |
| 单次搜索上限 | 前8条 | 安全基线数据的核心配置项约为5-7条/台设备，召回8条可覆盖多台设备的核查结果，避免冗余数据占用token |
| 检索结果重排 | 按合规优先级 | 优先召回未通过合规检查的配置项，减少非关键信息的token消耗，提升评审效率 |
| 问题优化开关 | 开启 | 针对基线检查的合规疑问自动优化提问表述，减少无效上下文的token占用 |

## 容易做错的三处
- 现象：调用时提示上下文token超限，返回内容截断或状态码429。原因：未根据安全基线数据的多源特性调整`maxContext`参数，加载了过多无关的历史配置记录，导致token配额耗尽。
- 现象：检索结果未匹配到基线检查表的核心合规字段，返回结果为空或不完整。原因：未设置`quoteMaxToken`参数限制单条引用的token长度，导致长文档被截断后无法匹配关键配置项。
- 现象：内网部署使用自定义模型时，仍产生默认token扣费。原因：未正确关联自定义模型的token计费逻辑，同时未关闭平台默认的token扣费开关，导致额外token消耗。

## 怎么确认配好了
- 上传一份完整的基线检查表文档，触发代码评审辅助功能，查看上下文加载的内容是否包含核心配置项与合规状态字段。
- 查看平台的token消耗日志，核对单次调用的token使用量是否符合预设的`maxContext`与`quoteMaxToken`参数区间。
- 模拟一次变更评审场景，输入待核查的配置项，检查检索结果是否优先返回未通过合规检查的内容。
- 在内网部署环境中，验证自定义模型的token计费逻辑是否生效，确认无额外默认token消耗。
