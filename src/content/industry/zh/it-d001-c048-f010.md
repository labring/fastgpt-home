# 安全监控与SOC值守的代码与变更评审辅助：引用来源与溯源

## 这个品类的数据长什么样
本品类的数据来自SIEM、EDR、NDR与威胁情报源，更新节奏为实时或每日。日常处理的文档包含告警处置单、值班记录、威胁情报通报、日报周报，其中涉及代码与变更评审的文档包含告警ID、关联代码变更ID、处置时间、关联威胁标签、处置结果等字段，部分文档需关联多源告警与代码变更记录，字段格式多为结构化文本与半结构化日志混合。

## 这些特征在「引用来源与溯源」这一环带来什么约束
数据来源多且格式混合，要求溯源链路需精准匹配数据源标识与代码变更ID等锚点字段，避免跨源混淆。实时更新的告警与代码变更数据要求溯源支持低延迟查询，否则会导致变更评审与告警研判滞后。多类型日常文档需按场景关联对应数据源，若溯源规则未绑定文档类型，会出现引用来源与实际处置依据不符的情况。关联代码变更ID等结构化字段需作为溯源锚点，若未配置字段映射，无法快速定位原始代码变更记录，增加误报排查与变更评审耗时。

## 配置怎么定
本文档适配FastGPT v4.17.0版本
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `quoteMaxToken` | 1000 token | 适配SOC场景下告警处置单、代码变更评审记录的内容长度，避免截断关键溯源信息 |
| `responseData` | 开启全量原始字段 | 满足分析师需要查看告警ID、代码变更ID、处置时间等原始字段的需求，符合日常研判与评审流程 |
| `detail` | 按数据源与变更ID分组展示 | 便于快速区分SIEM、EDR、NDR等不同来源的溯源数据，关联对应代码变更记录 |
| 单次引用上限 | 前 4 条 | 匹配多源告警与代码变更关联的场景，避免过多冗余信息干扰核心研判 |
| 溯源查询超时阈值 | 50 秒 | 适配实时告警与代码变更评审的节奏，确保溯源结果与当前任务同步 |

## 容易做错的三处
- 现象：引用结果未包含代码变更评审的完成原因字段，无法用于后续评审环节。原因：未开启`responseData`参数的全量原始字段返回，未保留字段的原始值。
- 现象：调用Function CALL获取的MySQL代码变更数据未被作为引用来源展示，仅以自然语言复述。原因：未配置`responseData`参数绑定原始数据源，未将查询结果纳入溯源链路。
- 现象：不同来源的溯源数据混合展示，无法区分SIEM告警与代码变更记录。原因：未配置`detail`参数的分组展示规则，未按数据源与变更ID进行分类。

## 怎么确认配好了
- 提交一条包含代码变更ID的测试告警数据，查看引用溯源模块是否展示了对应SIEM、EDR的原始字段与代码变更记录。
- 调整`quoteMaxToken`的取值，验证返回的溯源内容长度是否符合设定值，未出现截断关键信息的情况。
- 提交多源关联的告警与代码变更请求，确认溯源结果是否按数据源与变更ID分组展示。
- 模拟实时告警提交，检查溯源查询的响应时间是否符合设定的超时阈值，未出现超时错误。
