# 客户需求池管理的代码与变更评审辅助：上下文与 token
本文适配FastGPT v4.17.0版本。

## 这个品类的数据长什么样
该品类的核心数据来自工单系统、客户访谈记录、CRM系统及产品路线图，日常产出需求池清单、需求评估表、客户反馈记录与版本规划说明。数据更新频率为周度或每版本发布周期，字段包含需求来源、优先级、关联客户、预计研发工时等，无统一固定单位，需随具体需求场景调整。主要处理多客户反馈的筛选排序，区别于后续的需求分析与PRD管理环节。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据来源分散、格式差异大，不同来源的文档长度与字段复杂度不一，对上下文切片的精准度提出要求。数据更新频率为周度或每版本，上下文需定期同步以匹配最新需求状态，否则会出现需求信息过时的问题。需求池数据包含关联客户、优先级等细分字段，仅召回通用上下文无法支撑精准的需求评估与排期沟通，容易导致上下文冗余或缺失，增加不必要的token消耗。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文 | 12000–15000 token | 适配需求池多文档混合的内容体量，避免超出模型上下文窗口 |
| 分块重叠长度 | 200–300 字符 | 保障需求池内关联字段的上下文连贯性，避免需求信息断裂 |
| 单次召回上限 | 前5–7条匹配文档 | 匹配需求池数据的字段数量，控制token消耗在合理范围 |
| `maxContext` | 12000–15000 token | 与界面设置的最大上下文参数对齐，统一上下文承载上限 |
| 上下文召回阈值 | 0.72–0.85 按实测标定 | 精准筛选与当前需求相关的历史记录，减少无关客户反馈干扰 |

## 容易做错的三处
- 现象：知识库召回的上下文与当前需求无关，出现答非所问的结果。原因：未针对需求池的多字段特征调整召回阈值，误将无关客户反馈纳入上下文。
- 现象：调用工作流API时无法携带上下文，或连续追问后上下文丢失。原因：未在工作流节点中开启上下文同步配置，或未将需求池的历史文档绑定至会话上下文。
- 现象：文档上传后提示上下文超限，无法完成切片。原因：未根据需求池文档的平均长度调整分块参数，导致单块内容超出模型支持的token上限。

## 怎么确认配好了
- 上传一份完整的需求池清单文档，检查分块后的内容是否保留了客户、优先级等核心字段的连贯性。
- 发起两次连续追问，确认第二次提问能关联第一次的需求上下文，未出现信息断裂。
- 调用工作流API时，检查请求参数中是否携带了会话上下文标识，返回结果是否匹配需求池的历史记录。
- 查看配置页面的`maxContext`参数值，确认其未超出当前使用大模型的上下文窗口上限。
