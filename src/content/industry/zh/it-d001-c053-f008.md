# 客户需求池管理的代码与变更评审辅助：工作流编排

## 这个品类的数据长什么样
客户需求池管理的数据来自工单系统、客户访谈记录、CRM客户管理系统与产品路线图文档，更新频率为每周或每个版本发布前。日常产出的文档包含需求池清单、需求评估表、客户反馈汇总与版本规划说明，字段通常包含需求来源、关联客户标识、优先级评分、研发成本估算、排期节点与评估状态，无固定统一的标准化字段格式，需适配多来源的原始数据格式。本页面内容适配FastGPT v4.17.0版本。

## 这些特征在「工作流编排」这一环带来什么约束
由于数据来源分散且格式不统一，工作流编排需配置多节点分别拉取不同系统的原始数据，再进行格式统一处理。更新频率的周度或版本级要求，决定了工作流需支持定时触发或绑定版本发布事件触发。多文档的关联处理需求，要求工作流支持通过变量绑定不同文档的字段，避免手动复制粘贴带来的错误。重复需求归并与价值评估的耗时环节，需要在工作流中加入去重与评分校验节点，减少人工干预的工作量。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 变量引用设置 | 启用`variables`绑定需求池字段 | 适配多来源文档的字段格式，实现数据自动传递 |
| 超时阈值 | 600秒 | 覆盖跨系统拉取工单、CRM数据的平均耗时范围，适配FastGPT v4.17.0的节点超时配置 |
| 节点触发条件 | 按周定时或版本发布前触发 | 匹配需求池数据的周度/版本级更新频率 |
| 日志存储时长 | 30天 | 满足需求评审的事后追溯需求 |
| 返回数据条数 | 前10条 | 平衡数据加载效率与需求覆盖范围 |
| 失败重试次数 | 2次 | 避免单次系统波动导致工作流中断 |

## 容易做错的三处
- 现象：接口调用工作流后，对话日志中的运行数据为空。原因：未在`variables`中配置接口返回字段的绑定关系，导致数据未传递至后续节点。
- 现象：工作流A调用工作流B时，子工作流无法完整执行。原因：父工作流未通过`nodeId`指定子工作流的触发入口，且未传递需求池的关联参数。
- 现象：将AI对话修改为变量引用模式后，无法设置温度参数。原因：变量引用模式默认继承全局配置，未在工作流节点中单独配置参数调整项。

## 怎么确认配好了
- 手动触发一次工作流，查看运行日志是否包含完整的需求池字段数据，确认跨系统拉取正常。
- 检查变量引用节点的绑定配置，确认已关联需求池清单、评估表等文档的对应字段。
- 模拟系统超时场景，验证工作流是否触发失败重试机制，且重试后可正常完成流程。
- 查看嵌套调用的子工作流运行记录，确认子工作流的全部执行步骤均已完成。
