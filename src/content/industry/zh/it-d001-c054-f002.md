# 容器平台运维的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
该品类的数据通常来自Kubernetes API、镜像仓库、监控系统与CI流水线，日常产出集群变更单、命名空间配额表、部署记录与故障报告。数据更新节奏多为每日或随单次变更触发，文档结构多以结构化字段为主，包含集群ID、资源配额值、Pod状态、变更时间戳等，单位涉及核心数、内存容量、字符数与时间戳格式。典型使用者为平台工程师、Kubernetes管理员与SRE，核心处理场景围绕资源配额调整、Pod异常排查与集群升级验证展开。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据来源分散且更新频繁，随集群变更实时产生的配置与日志会快速累积，导致上下文窗口易混入过期信息。日常文档结构包含结构化配额字段与非结构化故障描述，单条数据长度差异较大，部分集群升级记录与故障报告可能超出基础token阈值。核心处理场景需关联多源数据，如将变更单与对应Pod部署记录绑定，对上下文召回的精准度与token分配合理性要求较高，同时需避免因上下文过载引发业务中断类风险。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 10–15 条关联记录 | 该品类需关联多源集群数据，10–15条可覆盖单次变更评审的核心关联信息，避免上下文过载 |
| `quoteMaxToken` | 8000–12000 token | 匹配容器平台运维常见的集群变更单、部署记录的总token量，适配大模型上下文窗口 |
| 分块长度 | 800–1200 字符 | 适配该品类结构化文档的字段长度，避免单块数据拆分后丢失关联逻辑 |
| 最大响应token | 按实测标定 | 需结合集群变更评审的详细程度调整，避免因响应过短遗漏配置细节 |
| 上下文召回阈值 | 0.75–0.85 | 过滤低关联度的监控日志与镜像仓库记录，聚焦资源配额、Pod状态等核心字段 |

## 容易做错的三处
- 上传部分集群配置文件时提示token超限，部分小文件却可正常上传。原因是该品类的配置文件包含大量结构化字段与长文本注释，实际token消耗远超肉眼估算的字符数，未按token单位调整分块策略。
- 配置最大上下文为3000以上token后，部分复杂变更评审的响应长度自动变为200。原因是系统自动截断了非核心的监控日志片段，未区分核心字段与冗余信息，导致关键配额配置被截断。
- 未明确设置分块长度单位，导致知识库分块与token计算逻辑不匹配。原因是混淆了字符数与token数的换算规则，未结合该品类文档的结构化特征选择对应单位。

## 怎么确认配好了
- 使用FastGPT v4.17.0版本的后台配置界面，导入一条典型的集群变更单，查看知识库分块预览，确认分块长度与设定值匹配。
- 发起一次Pod异常排查的评审请求，查看上下文召回列表，确认召回条数符合`maxContext`的设定范围。
- 测试长文本的故障报告导入，验证响应长度未被无故截断，符合`quoteMaxToken`的配置逻辑。
- 调整分块单位参数，对比字符数与token数的换算结果，确认与品类文档的结构化特征适配。
