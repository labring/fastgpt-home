# 容器平台运维的代码与变更评审辅助：工具调用与插件

本文档基于FastGPT v4.17.0版本编写。

## 这个品类的数据长什么样
该品类的典型数据来源包括Kubernetes API、镜像仓库、监控系统与CI流水线。日常产出的文档包含集群变更单、命名空间配额表、部署记录与故障报告，更新频率为每日或每次集群变更后触发。数据字段涵盖集群节点ID、Pod运行状态、资源配额阈值、变更执行时间等，单位涉及CPU核数、内存MB、变更次数等，不同文档的字段结构存在一定差异，无统一标准化格式。

## 这些特征在「工具调用与插件」这一环带来什么约束
多数据源的调用需求要求插件支持对接多种外部接口，需适配不同接口的认证与响应格式。非标准化的文档结构要求工具调用时需配置灵活的字段解析规则，避免因格式差异导致数据提取失败。更新频率的不确定性要求插件支持按需拉取数据，不依赖固定周期的缓存机制。高频耗时环节的特性要求工具调用优先覆盖资源配额调整、Pod异常排查与集群升级验证场景，同时需配置异常告警机制以应对业务中断风险。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | 自动匹配当前评审场景的可用工具，适配容器运维多数据源调用需求 |
| `functionCall` | `enabled` | 启用显式函数调用模式，确保变更评审流程严格按预设规则执行 |
| 插件超时时间 | 600 秒 | 匹配容器集群API常规响应时长，避免中断完整评审流程 |
| 工具调用重试次数 | 2–3 次 | 应对集群API临时波动导致的调用失败，减少评审阻塞 |
| 数据拉取时间范围 | 前 7 天 | 贴合容器运维变更评审的常规历史数据参考周期 |

## 容易做错的三处
- 现象：调用FastGPT的会话接口时未正确配置`functionCall`参数，导致工具未触发变更评审相关逻辑。原因：未明确启用显式函数调用模式，默认模式下未调用预设的容器运维插件。
- 现象：插件配置超时时间小于300秒，频繁出现调用超时报错。原因：未匹配容器集群API的常规响应时长，导致正常调用被误判为超时。
- 现象：将工作流编排逻辑直接写入插件配置，导致插件执行异常。原因：混淆了工作流与插件的职责边界，插件仅负责单次工具调用与数据获取，不负责完整流程编排。

## 怎么确认配好了
- 发起一次模拟集群变更评审请求，检查工具调用日志是否显示匹配的`toolChoice`和`functionCall`参数。
- 查看插件配置页面的超时时间设置，确认与容器集群API的常规响应时长一致。
- 测试拉取数据范围，确认仅返回近7天的变更记录与集群数据。
- 触发一次模拟的API调用失败场景，检查是否按配置执行重试逻辑。
