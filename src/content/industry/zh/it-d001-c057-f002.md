# 工单受理与问题分级的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
本品类的数据来源包括工单系统、聊天记录、产品日志、客户合同SLA，更新频率为日级或实时。日常处理的文档包含客户工单、问题分级表、处理记录、服务报告，数据字段涵盖工单标识、客户信息、问题描述、分级标签、响应时限、处理人、历史交互内容等，其中结构化数据以工单表和分级表为主，非结构化数据以聊天记录和处理日志为主。

## 这些特征在「上下文与 token」这一环带来什么约束
由于数据来源多样且更新实时，上下文加载需兼顾结构化字段与非结构化内容的优先级，避免无关日志占用过多token。工单数据的实时更新要求上下文窗口支持动态追加内容，同时需限制总token消耗以匹配模型承载能力。问题分级依赖核心工单信息，若上下文过长导致核心内容被截断，将直接影响分级准确性。SLA相关字段需优先纳入上下文，确保处理时限的合规性校验有足够数据支撑。

## 配置怎么定
本文档适配FastGPT v4.17.0版本，以下配置项可在平台对应模块中设置：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文窗口 | 8000–12000 token | 匹配工单与历史处理记录的平均内容总长度，适配通用大模型的token承载上限 |
| 引用内容最大token数 | 2000–3000 token | 确保单条工单或历史聊天记录的核心信息完整纳入，避免无关细节占用过多上下文 |
| 上下文召回优先级 | 按SLA剩余时长排序 | 优先纳入临近超时的工单数据，符合业务SLA合规要求 |
| 历史记录召回上限 | 前10条 | 控制总上下文token消耗，避免实时更新的大量日志导致token溢出 |
| `maxContext` | 按业务峰值token用量标定 | 适配实时更新的工单数据量，防止上下文加载失败 |
| `quoteMaxToken` | 按单条工单的平均字符数换算 | 确保核心问题描述与分级依据完整呈现 |

## 容易做错的三处
- 配置ACCESS_TOKEN后无法拉取工单数据，现象为接口返回空结果，原因是未正确配置上下文引用的权限规则，导致token校验失败。
- 工作流中多AI模型调用后总token超出限制，现象为返回结果被截断或报错，原因是未设置`maxContext`参数隔离各模型的上下文token消耗。
- 无网络环境下无法加载历史工单数据，现象为上下文为空，原因是未配置本地缓存上下文的参数，依赖网络拉取失败。

## 怎么确认配好了
- 导入单条完整工单与历史处理记录，查看平台上下文预览模块显示的内容长度是否符合配置的最大上下文范围。
- 模拟多模型编排调用，查看平台token消耗统计是否未超出`maxContext`设定值。
- 触发工单数据拉取，检查返回的有效内容是否未超出`quoteMaxToken`的限制。
- 验证SLA优先级排序的上下文召回，确认临近超时的工单数据优先被纳入上下文窗口。
