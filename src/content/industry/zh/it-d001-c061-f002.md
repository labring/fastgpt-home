# 性能测试与容量评估的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自压测平台、APM监控系统、数据库慢日志与生产流量基线。日常产出的文档包括压测方案、容量评估报告、压测数据记录与优化建议单。数据更新频率通常为每月一次或伴随重大版本发布。数据字段包含吞吐率、延迟值、资源占用率等指标，单位多为QPS、毫秒、百分比，文档结构多以指标清单、瓶颈分析、容量结论为核心模块。

## 这些特征在「上下文与 token」这一环带来什么约束
压测数据来源分散且单条指标数据量大，会导致上下文召回冗余，需要限制token消耗。日常文档结构固定，关键内容集中在瓶颈分析与容量结论模块，若上下文召回范围过宽，会混入无关的压测方案细节。生产流量基线随业务波动更新，需要控制上下文的时间范围，避免加载过时数据。同时，优化建议单与压测报告的关联内容需精准匹配，防止token被非核心字段占用。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 覆盖单份压测报告、容量评估报告及关联优化建议的总token消耗 |
| `quoteMaxToken` | 2000–3000 token | 匹配单条引用内容的长度，避免单条引用超出模型处理上限 |
| 关键词拆分控制 | 按文档模块保留完整内容 | 避免拆分压测指标、容量结论这类关键段落，保证上下文语义完整 |
| 上下文召回范围 | 近1个月的压测数据 | 匹配数据更新频率，过滤过时的历史压测记录 |
| 单次搜索引用上限 | 前6条 | 压测相关文档的核心关联条目通常不超过6条，减少冗余token |

本配置适用于FastGPT v4.17.0。

## 容易做错的三处
- 现象：配置`quoteMaxToken`为2000 token后，单次回答仍超出3000 token。原因：未同步调整`maxContext`的总上限，单条引用的token叠加后超出整体上下文限制。
- 现象：连续对话中上下文丢失，无法关联前序的压测指标讨论。原因：未开启上下文保留配置，或`maxContext`设置过小导致早期内容被自动清理。
- 现象：关键压测指标段落被拆分，导致上下文语义断裂。原因：未配置关键词拆分规则，系统默认拆分所有文档内容，破坏了指标与结论的关联。

## 怎么确认配好了
- 上传一份完整的压测报告与关联优化建议单，查看系统召回的上下文内容范围，确认符合预设的召回范围。
- 触发一次代码变更评审的模拟请求，查看返回内容的token消耗，确认未超出预设的`maxContext`上限。
- 检查知识库中关键文档的拆分结果，确认压测指标、容量结论等核心段落未被拆分。
- 发起连续对话，验证前序的压测指标讨论被系统正确关联，确认上下文保留配置生效。
