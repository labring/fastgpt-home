# 投放计划搭建的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
投放计划搭建的日常文档包含投放计划、定向设置、预算排期、转化追踪配置等结构化内容，字段包括定向标签、预算额度、转化事件ID等，单位涵盖元、人次、天。数据来源为广告投放平台API、内部预算表、用户行为画像库、归因统计工具，更新节奏为每日刷新或随投放活动触发更新，数据多为配置类结构化信息，无非结构化的自由文本内容。

## 这些特征在「上下文与 token」这一环带来什么约束
投放计划搭建的多源数据特征，要求上下文召回需关联不同来源的配置片段，增加了上下文窗口的长度需求。高更新频率要求上下文召回需及时同步最新配置，避免使用过期数据。结构化的配置字段要求上下文需精准匹配核心配置项，同时投放计划的变更评审需要关联历史版本，进一步提升了token消耗的压力，需合理分配上下文与token的资源。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 覆盖多源投放计划文档的总长度，包含历史变更记录、当前预算排期、定向配置等内容 |
| `quoteMaxToken` | 1500–2000 token | 优先保留投放计划中预算阈值、定向标签、转化事件ID等核心配置字段的上下文片段 |
| 上下文召回触发间隔 | 每12小时 | 适配投放计划的日更新节奏，确保召回数据与最新配置同步 |
| 上下文匹配阈值 | 按实测标定 | 匹配结构化的投放计划字段，避免召回无关的历史变更记录 |
| 工作流上下文缓存时长 | 72小时 | 覆盖单次投放活动的完整评审周期，支持连续追问的上下文关联 |

本配置指南适用于FastGPT v4.17.0版本。

## 容易做错的三处
- 现象：调用FastGPT工作流API时，连续第二个问题出现答非所问，无法关联前序投放计划配置。原因：未在工作流中配置`maxContext`参数，或上下文缓存时长设置过短，导致上下文未被正确保留。
- 现象：知识库召回的投放计划文档条数超出预期，出现大量无关的历史变更记录。原因：未设置合理的上下文匹配阈值，召回了超出本次评审范围的旧版本数据。
- 现象：单次变更评审请求触发token超限报错。原因：未限制`quoteMaxToken`的取值，导致核心配置片段占用过多token，挤压了问题处理的token空间。

## 怎么确认配好了
- 发起连续三次针对同一投放计划的评审请求，检查返回结果是否关联前序配置的定向、预算等信息。
- 查看FastGPT工作流日志，确认上下文缓存的更新频率与设置的触发间隔一致。
- 测试不同长度的投放计划文档，检查是否出现token超限报错，调整配置项取值至符合业务需求。
- 核对召回的文档条数，确认与设置的召回条数匹配，无冗余数据。
