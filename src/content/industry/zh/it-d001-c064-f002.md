# 投标文件编制的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
本品类的核心数据来自招标公告、招标文件、企业资质库与供应商报价，更新频率为每单专属更新。日常处理的文档包含投标文件、资格证明、商务偏离表、技术偏离表，文档结构多遵循招标方固定格式，包含条款响应项、资质编号、报价金额等结构化字段，以及无固定格式的补充说明内容。

## 这些特征在「上下文与 token」这一环带来什么约束
每单专属更新的特性要求上下文匹配需针对单次项目快速适配，无法依赖长期增量的知识库沉淀。固定格式的招标条款与响应内容需要精准关联，若数据块拆分不当，易出现跨条款的匹配偏差。结构化的资质与报价数据存在大量重复字段，若分块过大将导致token无效消耗，同时单份投标文件的核心内容较多，需控制上下文总长度避免超出token承载上限。此外，不同招标项目的格式差异要求上下文匹配需灵活适配不同字段组合，进一步增加了token管理的复杂度。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| 分块长度 | 800–1200 字符 | 匹配投标文件中条款响应段落的常规长度，避免块过大导致token溢出，同时避免块过碎破坏条款完整性 |
| 重叠长度 | 150–200 字符 | 保证跨块的招标条款与对应响应内容能被完整关联，避免出现匹配断层 |
| `maxContext` | 8000–12000 token | 覆盖单份投标文件的核心响应内容与对应招标要求，适配FastGPT v4.17.0的默认上下文承载上限 |
| `quoteMaxToken` | 2000–3000 token | 限制单条匹配内容的引用长度，避免冗余token消耗，确保核心响应内容优先被召回 |
| 单次搜索上限 | 前10条 | 控制召回的资质与报价数据数量，避免过多无关内容占用上下文token |

## 容易做错的三处
- 出现`E11000 duplicate key error collection`报错，原因是未为不同招标项目的投标文件数据创建独立的知识库分类，导致不同项目的文档标识重复。
- 处理Excel格式的供应商报价数据时，出现单块数据过大导致token消耗过高，界面提示上下文超限，原因是未针对结构化表格数据调整分块规则，将整表内容作为单个数据块处理。
- 召回的匹配内容无法精准对应招标条款，出现结果条数异常增多或为空，原因是重叠长度设置不合理，导致跨块的条款与响应内容无法被正确关联。

## 怎么确认配好了
- 上传单份典型投标文件，查看分块预览界面，确认每个数据块的长度在预设范围内。
- 发起一轮招标条款响应测试，查看上下文消耗统计，确认`maxContext`的取值未超出系统承载上限。
- 导入Excel格式的报价数据，查看分块结果，确认结构化表格被正确拆分为符合要求的小数据块。
- 触发知识库分类匹配任务，查看匹配结果条数，确认单次搜索上限的取值控制了召回数量。
