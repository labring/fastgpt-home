# 投标文件编制的代码与变更评审辅助：多轮对话与提示词

## 这个品类的数据长什么样
本品类的数据围绕投标全流程产生。核心文档包括投标文件、资格证明、商务偏离表、技术偏离表，数据来源为招标公告、公开招标文件、企业资质库与供应商报价库。每份投标项目的数据更新频率为单项目周期内单次更新，随招标要求调整内容。文档结构以招标方指定格式为核心，包含条款响应项、资质匹配项、报价核对项三类核心字段，无统一固定单位，需严格匹配招标方要求的字段规则。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源分散且随单项目调整，要求多轮对话需持续关联当前招标项目的专属上下文，避免跨项目数据混淆。文档结构依赖招标方指定格式，提示词需严格匹配招标方指定的字段名称，否则无法生成合规响应内容。更新频率为单项目单次，意味着对话上下文需在单项目周期内保留，超出后需重置。条款逐项响应的高耗时需求，要求多轮对话支持逐条款拆解与核对，避免一次性输入过多内容导致模型理解偏差。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的功能规则制定。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文长度 | 8000–12000 token | 匹配投标文档的单项目总字符量，避免上下文溢出 |
| `chatId` 绑定规则 | 单项目绑定唯一`chatId` | 隔离不同投标项目的对话上下文，防止数据串用 |
| `variables` 配置 | 预设招标编号、项目名称、资质库关键词 | 快速代入单项目专属数据，减少重复输入 |
| `messages` 历史截断阈值 | 保留最近30条对话记录 | 平衡上下文完整性与模型响应速度 |
| 单次回复最大长度 | 1500 字符 | 匹配单条款响应的常规内容长度，避免输出截断 |
| 问题优化开关 | 开启 | 自动拆解招标条款的复杂要求，适配逐条款响应需求 |

## 容易做错的三处
- 现象：回复中出现非当前投标项目的资质或报价数据，原因是未绑定专属`chatId`，导致不同项目的对话上下文被复用。
- 现象：返回“上下文超限”报错或响应内容被截断，原因是未设置合理的最大上下文长度与单次回复长度，超出模型处理阈值。
- 现象：仅能获取部分对话记录，无法查看完整会话历史，原因是未正确配置`messages`的历史保留参数，仅调用了部分会话片段。

## 怎么确认配好了
- 新建一个投标项目的对话，输入招标条款的响应要求，检查回复是否仅关联当前项目的预设`variables`数据，无无关跨项目内容。
- 输入较长的招标条款内容，检查模型是否能完整响应，无截断或报错，确认最大上下文长度与单次回复长度配置合理。
- 切换到不同投标项目的`chatId`，检查对话上下文是否完全隔离，无跨项目数据混杂。
- 调用对话记录接口，确认能获取当前`chatId`下的全部`messages`记录，无遗漏。
