# 数据库运维的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自数据库监控、审计日志、SQL执行计划与工单系统。日常关联文档包括数据库变更单、慢SQL报告、备份记录、权限申请单，由DBA、数据平台运维及后端团队维护。数据更新节奏为每日更新或随单次数据库变更同步更新，每条数据包含SQL语句、执行耗时、权限标识、变更内容等字段，无统一固定单位，随数据类型差异变化。

## 这些特征在「上下文与 token」这一环带来什么约束
数据库运维场景的上下文多为长文本SQL片段、变更单全文及历史操作记录，单条上下文长度易超出常规阈值。频繁的变更与日更数据要求上下文需及时同步最新工单与监控数据，避免关联过时信息。不同来源的数据格式差异大，需在上下文拼接时统一结构，否则易导致token超标或模型解析失败。同时，DBA评审时需关联多条历史变更与慢查询记录，上下文条数需匹配实际评审需求，过多会占用过多token，过少则无法覆盖关联逻辑。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `maxContext` | 前10-15条 | 数据库运维单次评审通常关联10条以内历史变更与监控数据，过多会占用过多token，影响模型响应速度 |
| `quoteMaxToken` | 8000-12000 token | 单条SQL执行计划或变更单全文通常不超过此范围，避免超出模型支持的token上限 |
| 上下文同步频率 | 随变更触发同步，日常每日1次 | 数据库变更时效性强，过时数据会导致评审偏差，需及时更新关联上下文 |
| 上下文筛选阈值 | 按实测标定 | 不同数据库实例的关联数据密度差异大，需匹配实际召回效果，避免无关数据混入 |
| 上下文拼接格式 | 统一为“来源+时间+内容”结构 | 确保模型可清晰识别不同类型的上下文数据，避免解析混乱 |

## 容易做错的三处
- 现象：对话明细中显示的上下文条数与配置值不符，例如配置30条仅显示2条。原因：上下文同步逻辑未正确关联工单系统与数据库监控数据源，仅召回了部分最新数据。
- 现象：AI回复出现非预期的JSON格式内容。原因：上下文拼接时未统一数据格式，混入了未结构化的审计日志原始内容，导致模型解析异常。
- 现象：触发上下文token数超标报错。原因：未限制`quoteMaxToken`取值，将超长SQL执行计划与多条变更单直接拼接，超出模型支持的token上限。

## 怎么确认配好了
- 查看上下文召回日志，确认召回的数据源包含数据库变更单、慢SQL报告等目标文档。
- 测试单次评审请求，检查返回的上下文条数与配置的`maxContext`取值匹配。
- 模拟超长SQL与多条历史数据拼接，验证未触发token超标报错。
- 手动修改一条历史变更单，确认后续评审请求可关联到更新后的内容。
