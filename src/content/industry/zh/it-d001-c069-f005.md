# 数据库运维的代码与变更评审辅助：多轮对话与提示词

## 这个品类的数据长什么样
数据库运维场景的数据通常来自数据库监控、审计日志、SQL执行计划与工单系统。日常关联文档包括数据库变更单、慢SQL报告、备份记录与权限申请单，其中变更单包含实例标识、变更语句、申请时间等字段，慢SQL报告包含响应时长、扫描行数等指标。数据更新频率为每日或每一次数据库变更，单次变更关联的数据量随实例规模波动，无固定统一阈值。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
由于数据来源分散且单次变更关联多类文档，多轮对话需要逐步整合不同来源的信息，避免遗漏关键约束。数据更新频率与变更同步，要求对话上下文需限定在当前变更的时间范围内，避免引入历史无关数据。文档结构差异较大，提示词需明确指定提取对应字段的规则，防止模型混淆不同文档的字段定义。同时，评审出错会导致数据损坏或权限越界，对话环节需加入多轮校验步骤，确保每一步的变更请求符合合规要求。

## 配置怎么定
本配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 上下文窗口大小 | 8000–12000 字符 | 依据数据库变更单的常规文档大小，避免上下文过载，同时覆盖单次评审的全部关键信息 |
| 变量绑定规则 | 仅绑定`variables`中当前工单的关联数据 | 依据需要隔离不同工单的权限与变更数据，防止上下文污染 |
| 对话触发逻辑 | 按`messages`的用户输入触发 | 依据贴合人工评审的交互节奏，仅在用户发起请求时触发模型响应 |
| 最大交互轮次 | 15 轮 | 依据复杂变更评审的排查步骤通常不超过15个，超时则终止对话避免资源占用 |
| 回复格式校验 | 启用JSON格式校验 | 依据运维评审结果需要结构化输出，便于后续工单系统集成 |
| 会话ID绑定 | 绑定`chatId`参数 | 依据确保多轮对话的上下文关联正确，避免会话混淆 |

## 容易做错的三处
- 对话上下文丢失，仅保留最近3条消息。原因是未正确配置上下文保留规则，仅加载了最新的交互内容，未关联`messages`参数的历史数据。
- 生成的JSON回复不符合预设格式，无法被工单系统解析。原因是未在提示词中明确指定字段约束，或未启用回复格式校验配置，导致输出格式混乱。
- 单轮对话响应超时，耗时超过30秒。原因是绑定了过多非关联的数据库监控数据，导致模型处理上下文过载，未设置合理的超时阈值。

## 怎么确认配好了
- 导入一条测试数据库变更单，发起首轮对话，检查对话历史是否保留了全部交互内容，验证`chatId`参数是否正确绑定了会话ID。
- 触发评审请求，检查生成的回复是否符合预设的JSON结构，确认`variables`仅加载了当前工单的关联数据。
- 模拟多轮交互，观察响应时间是否在合理范围内，确认最大交互轮次与超时阈值配置符合实际业务节奏。
- 输入一条越权的SQL语句，检查模型是否能正确识别并提示风险，验证配置的约束是否生效。
