# 文档站维护的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
这个品类的数据主要来自代码仓库、文档站构建日志、用户反馈与版本发布记录。日常维护的文档包含安装文档、API文档、迁移指南与FAQ，内容多包含代码片段、版本号、接口参数与操作步骤。数据更新频率多为每周或每版本发布时同步，文档结构通常按功能模块划分，单篇文档长度跨度较大，从数百字符到数万字符不等，部分文档包含可直接运行的代码块与配置示例。

## 这些特征在「上下文与 token」这一环带来什么约束
文档站维护的文档包含大量代码片段与结构化参数，长文本占比高，且更新频率随版本发布波动。代码片段的语义依赖上下文，若上下文截断不当会导致代码示例解读错误。单篇文档跨度大的特点要求上下文窗口需适配不同长度的文档块，避免遗漏关键配置信息。版本更新带来的内容变更，需要上下文关联历史版本与当前版本的差异，若token分配不合理，会导致新旧版本内容无法同时纳入上下文，引发文档维护中的版本混淆。另外，用户反馈类的短文本数据与长文档混合，需平衡上下文容纳的内容类型，避免短文本挤占长文档的token配额。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 适配单篇文档的平均长度与代码片段的上下文需求，避免截断关键配置信息 |
| `quoteMaxToken` | 1500–2000 token | 限制单段引用的代码或文档块的token数量，确保上下文语义完整且不超出窗口限制 |
| 分块长度 | 800–1200 字符 | 匹配文档中代码块与文本段落的平均长度，减少分块后的语义断裂 |
| 重叠长度 | 100–150 字符 | 保留相邻分块的重叠内容，避免代码片段被分块截断导致无法识别 |
| 最大召回上下文数 | 前6条 | 平衡召回内容的丰富度与token占用，适配文档站多模块内容的关联需求 |

## 容易做错的三处
- 现象：配置分块长度时选择token作为单位，导致分块后代码片段语法断裂。原因：文档站的代码片段的token计数与普通文本存在差异，按token分块会打乱代码的语法结构，引发后续评审与验证错误。
- 现象：上传包含多段代码的文档时提示上下文超限。原因：未合理设置`maxContext`参数，将过多长文档块纳入上下文，超出FastGPT v4.17.0的默认token限制。
- 现象：特定版本对比问题的回复长度突然变为200 token，远低于配置的上限。原因：上下文窗口被大量旧版本文档的召回内容挤占，剩余token不足以生成完整的版本差异说明。

## 怎么确认配好了
- 查看文档分块后的预览界面，确认代码片段未被截断，相邻分块的重叠内容符合设置的重叠长度。
- 上传单篇最长的文档，检查是否触发上下文超限报错，调整`maxContext`参数至符合实际需求。
- 测试版本对比类的查询，确认召回的上下文包含当前版本与历史版本的关键差异内容。
- 查看配置界面的参数值，确认`maxContext`与`quoteMaxToken`的取值与文档站的内容长度匹配。
