# 文档站维护的代码与变更评审辅助：多轮对话与提示词

## 这个品类的数据长什么样
该品类的数据主要来自代码仓库提交记录、文档站构建日志、用户使用反馈与提交的Issue、版本发布记录。日常产出的文档包含安装文档、API参考文档、版本迁移指南、常见问题解答。文档结构通常包含版本标识、操作步骤、参数说明、错误码对照表等字段。数据更新频率通常为每周一次或伴随每个版本发布同步更新。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源包含异构的代码、文档与反馈内容，多轮对话需明确区分不同类型的输入，提示词需定义清晰的上下文边界以避免混淆。更新频率随版本波动，需在对话中动态适配最新版本信息，提示词需包含版本校验逻辑以过滤过期内容。文档结构包含多类专业字段，多轮对话需按文档类型触发不同的检索与回答逻辑，确保回答匹配对应文档的表述习惯。用户反馈与Issue数据需关联到具体文档节点，提示词需支持关联溯源，确保回答指向准确的文档或代码位置。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 8000–12000 字符 | 适配多份文档与代码片段的总长度，避免超出FastGPT v4.17.0的处理上限 |
| 提示词模板 | 按文档类型分模板：安装文档模板、API文档模板、迁移指南模板 | 匹配不同品类文档的专业表述习惯，提升回答准确性 |
| 变量绑定 | 绑定当前版本号、文档构建时间 | 动态插入上下文信息，确保回答指向最新版本内容 |
| `chatId` 关联 | 绑定会话与指定文档仓库ID | 确保会话上下文仅关联对应文档站的数据源，避免跨仓库数据干扰 |
| 单次检索上限 | 前3条结果 | 避免过多内容干扰对话逻辑，聚焦核心信息 |
| 会话超时时间 | 600 秒 | 避免长对话无响应，适配文档站维护的多轮评审场景 |

## 容易做错的三处
- 现象为配置的提示词未对回答内容产生影响，回答未遵循预设规则。原因是提示词未正确绑定到对话流程的`messages`队列，未在会话初始化时加载。
- 现象为前端对话页面同时展示多个不相关模块的输出，无法区分对应文档类型的结果。原因是未通过`chatId`绑定会话与指定文档仓库，未按文档类型拆分对话上下文。
- 现象为对话中无法检索到历史用户反馈或Issue相关内容，搜索结果条数为0。原因是未配置会话上下文的关联逻辑，未启用会话ID的溯源绑定。

## 怎么确认配好了
- 发起包含版本号的查询，确认回答中自动插入了绑定的变量信息。
- 切换不同文档类型的问题，确认回答匹配对应文档的表述风格与内容。
- 开启会话后多次提问，确认会话关联的文档仓库数据被正确调用。
- 检查对话日志，确认`messages`队列按文档类型拆分了输入内容。
