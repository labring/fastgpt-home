# 文档站维护的代码与变更评审辅助：引用来源与溯源

## 这个品类的数据长什么样
该品类的数据通常来自代码仓库提交记录、文档站构建日志、用户反馈工单与版本发布记录。日常维护的文档包含安装指南、API接口说明、版本迁移手册与常见问题解答，文档结构多按功能模块划分，包含版本号、更新日期、示例代码字段与对应参数说明。数据更新频率为每周或随软件版本发布同步更新，单次更新内容多为接口变更、示例修正或过期内容清理。

## 这些特征在「引用来源与溯源」这一环带来什么约束
数据来源包含代码仓库的提交哈希与构建日志，要求溯源时需精准关联对应版本的代码片段与构建记录，避免溯源信息与实际代码变更脱节。日常文档的模块化结构要求溯源工具需按功能模块拆分关联信息，避免跨模块的无效关联干扰评审。更新频率的周期性意味着溯源环节需支持按版本过滤来源数据，确保引用的是当前生效的文档版本。用户反馈与Issue数据的非结构化特性，要求溯源工具需支持模糊匹配与标签关联，快速定位用户反馈对应的文档段落。出错后果的严重性要求溯源信息需保留完整的版本链路，避免引用过期内容导致用户误用接口或无法完成安装。

## 配置怎么定
FastGPT v4.17.0版本下的配置项可参考以下设置：

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `quoteMaxToken` | 1500–2000 token | 匹配文档站单篇文档的平均长度，避免截断溯源所需的完整段落信息 |
| `responseData` | 仅返回关联文档的元数据与原文段落 | 减少冗余数据传输，适配文档站维护的精准溯源需求 |
| `detail` | 开启完整溯源模式 | 保留代码仓库提交哈希、构建日志与版本发布记录的关联信息 |
| 版本匹配范围 | 当前主版本号区间 | 适配周/每版本的更新频率，确保引用的是当前生效的文档版本 |
| 关联召回上限 | 前3条 | 避免过多无关来源干扰评审，符合文档模块化的结构特征 |

## 容易做错的三处
- 现象：配置多文档知识库后，检索结果仅返回1条关联文档，引用计数显示为1条。原因：未开启多文档关联召回的配置项，仅使用单条召回的默认逻辑。
- 现象：配置模型后测试环节提示报错，但正式运行引用功能可正常执行。原因：测试环节未正确加载全量知识库元数据，仅校验了基础接口连通性，未触发完整的溯源关联逻辑。
- 现象：部分导入的文档未生成问答对，直接以原文形式写入知识库。原因：未开启文档拆分与问答对生成的关联配置，或拆分参数未适配文档站文档的长段落结构。

## 怎么确认配好了
- 发起一次针对API文档的检索，核对返回结果中包含的来源文档数量是否符合配置的召回上限。
- 查看检索结果的溯源信息，确认关联了代码仓库提交哈希与版本发布记录。
- 测试不同版本的文档查询，确认仅返回当前生效版本的文档内容。
- 触发一次文档更新后的检索，确认溯源信息同步了最新的构建日志与用户反馈标签。
