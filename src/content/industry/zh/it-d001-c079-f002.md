# 架构设计与技术方案的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
架构设计与技术方案的核心数据来自团队历史研发流量数据、服务拓扑图、线上监控指标、业务增长规划，更新节奏随月度迭代或重大架构需求调整。日常产出的文档包含结构化技术方案、可视化架构图、容量评估报告、技术评审纪要，字段多包含跨服务边界定义、资源阈值、依赖关系、评审意见等，无统一固定单位，随文档类型与内容复杂度变化。

## 这些特征在「上下文与 token」这一环带来什么约束
架构设计类文档通常体量差异较大，单份技术方案或架构图可能包含大量节点、依赖关系描述，容易快速占用上下文token配额；更新节奏不固定，每次重大评审前可能新增临时的业务增长数据或历史评审纪要，需要动态调整上下文容纳能力；文档内字段类型多样，需精准提取与当前评审相关的约束条件、边界定义，避免无关内容占用有效token；评审纪要包含多方讨论意见，需完整保留核心决策内容，不能随意截断关键信息。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token 按实测标定 | 架构设计文档通常关联多份历史资料，需覆盖足够的评审背景信息 |
| `quoteMaxToken` | 6000–8000 token | 重点保留技术方案、架构图的核心描述，避免冗余内容占用配额 |
| 单次召回上限 | 前8条 | 控制单次引入的评审纪要、历史方案数量，防止上下文过载 |
| 上下文截断阈值 | 90% | 当上下文接近配置上限时，自动截断非核心的历史讨论内容 |
| 动态上下文调整 | 随评审规模临时扩容 | 针对重大架构变更评审，临时扩大上下文窗口以覆盖全部关联资料 |

## 容易做错的三处
- 现象：配置`maxContext`过小，触发上下文溢出后返回空结果，界面显示LLM model response empty。原因：架构设计文档包含大量关联的历史评审数据，未预留足够token容纳核心内容。
- 现象：设置`quoteMaxToken`过高，导致单次请求token超过模型上限，触发rerank error。原因：未匹配架构文档的平均长度，盲目扩大引用token配额。
- 现象：单次召回上限设置过高，引入过多非核心的评审纪要，导致上下文过载，最终输出结果被截断或为空。原因：未考虑架构评审数据的体量差异，未按实际场景调整召回数量。

## 怎么确认配好了
- 上传一份典型的架构设计文档与关联评审纪要，查看上下文预览模块显示的总token数，确认未超过配置的`maxContext`上限。
- 发起一次模拟评审请求，检查返回结果是否包含核心的技术约束、架构边界信息，无关键内容缺失。
- 调整配置项后，对比不同体量的文档测试，确认token使用量符合预期，无频繁触发截断或溢出。
- 查看FastGPT v4.17.0系统日志，确认无rerank error或上下文相关的报错信息。
