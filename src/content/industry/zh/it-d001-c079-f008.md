# 架构设计与技术方案的代码与变更评审辅助：工作流编排

## 这个品类的数据长什么样
该品类的数据主要来自历史流量数据、服务拓扑、监控指标与业务增长计划。日常产出的文档包含技术方案、架构图、容量评估报告与技术评审纪要，数据字段通常包含方案版本号、约束条件清单、评审意见条目、跨服务边界定义与长期演进路线节点。数据更新频率为每月一次或伴随重大需求同步更新。

## 这些特征在「工作流编排」这一环带来什么约束
该品类的数据更新频率较低但变更影响范围广，因此工作流编排需支持多轮评审节点的串行或并行配置，确保约束条件收集、方案取舍论证等耗时环节的流程可追溯。由于日常文档结构差异较大，工作流需适配不同类型文档的解析节点顺序，同时需配置多源数据拉取环节，整合历史流量、服务拓扑等不同来源的信息。另外，该品类出错后果严重，工作流需内置失败后的回滚与告警触发配置，避免错误方案进入后续开发环节。

## 配置怎么定
本配置基于FastGPT v4.17.0版本的工作流编排功能。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 问题优化 | 仅在方案评审节点开启 | 架构设计类数据更新频率低，无需频繁优化，避免额外算力消耗 |
| 工具调用后处理 | 配置自定义代码抽取评审意见字段 | 适配工具调用结果不稳定的场景，提取结构化评审意见 |
| 最大上下文 | 8000–12000 token | 架构方案文档通常篇幅较长，需覆盖完整的历史评审与方案内容 |
| `variables` | 绑定业务增长计划与用户身份参数 | 用于动态加载业务数据与关联调用身份 |
| 工作流重试次数 | 2次 | 平衡失败恢复能力与资源消耗，避免重复调用导致的延迟 |
| 节点超时时间 | 600秒 | 架构评审相关的模型调用与文档解析通常耗时较长，需预留足够执行时间 |

## 容易做错的三处
- 现象：开启知识库插件的问题优化后，即使在最终回答插件中关闭该功能，工作流仍执行优化。原因：未在对应节点单独配置问题优化开关，混淆了全局配置与节点级配置的生效范围。
- 现象：将FastGPT应用嵌入业务系统后，发起工作流HTTP请求时身份关联失败，返回字段为空。原因：未在`variables`中绑定业务系统的用户身份参数，导致工作流无法获取合法调用身份。
- 现象：工具调用节点返回结果不稳定，无法提取结构化评审意见。原因：未配置工具调用后的自定义后处理步骤，未对返回的非结构化文本做针对性抽取。

## 怎么确认配好了
- 登录FastGPT v4.17.0的工作流编辑页面，检查每个节点的配置项，确认问题优化开关仅在方案评审节点开启。
- 查看`variables`参数的绑定内容，确认已包含业务增长计划的容量评估变量与业务系统的用户身份参数。
- 检查工作流配置中的`nodeId`参数，确认已正确绑定评审意见收集节点的唯一标识。
- 发起测试工作流请求，查看工具调用节点的返回结果，确认已通过自定义后处理提取出结构化评审意见字段。
- 检查工作流的超时与重试配置，确认节点超时时间设置为600秒，工作流重试次数设置为2次。
