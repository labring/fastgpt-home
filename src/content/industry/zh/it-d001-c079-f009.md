# 架构设计与技术方案的代码与变更评审辅助：工具调用与插件

## 这个品类的数据长什么样
这个品类的数据主要来自历史流量数据、服务拓扑、监控指标与业务增长计划，日常依托技术方案文档、架构图、容量评估表、技术评审纪要流转。数据更新频率为每月或每重大需求触发时，字段涵盖跨服务边界定义、资源配额、约束条件、演进路线等，部分字段以百分比、节点数、带宽值标注，无统一固定单位。

## 这些特征在「工具调用与插件」这一环带来什么约束
由于数据来源多为跨服务的拓扑与流量指标，工具调用需适配多源异构数据的格式转换，需提前定义字段映射规则。因更新频率不固定，插件需支持按需触发，且需兼容评审纪要的非结构化文本解析。架构设计的评审闭环依赖工具调用结果的可追溯性，需保留调用日志与参数记录。同时，架构方案的出错后果严重，工具调用的失败处理需设置多层重试与告警机制，避免影响后续评审流程。本配置适用于FastGPT v4.17.0版本。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | 适配架构方案评审中多类型工具调用的动态需求，无需手动指定工具 |
| 工具调用超时时间 | 120 秒 | 匹配架构数据的批量解析与跨服务查询的平均耗时上限 |
| `functionCall` | 开启 | 强制结构化输出工具调用参数，便于自动整理到评审纪要 |
| 单次工具调用最大token数 | 8000–12000 token | 适配架构方案文档的平均长度，避免上下文溢出 |
| 插件输入字段映射 | 按「服务拓扑→架构边界」「流量数据→容量评估」绑定 | 对齐架构方案文档的字段定义，确保数据准确传递 |
| 失败重试次数 | 2 次 | 平衡调用成功率与评审流程的等待时长，避免过度延迟 |

## 容易做错的三处
- 插件的输入数值无法传递到HTTP请求组件，出现`Request failed`类报错。原因是未将插件入参与架构方案文档中的对应字段完成映射绑定，导致请求携带空值或无效参数。
- 工具调用结果未按结构化格式输出，无法自动整理到技术评审纪要中。原因是未开启`functionCall`配置，导致工具返回非标准化的文本内容。
- 重试次数设置为0次，单次调用失败后无恢复机制，导致架构评审流程停滞。原因是未考虑跨服务数据查询的网络波动风险。

## 怎么确认配好了
- 上传一份测试用的架构方案文档，触发工具调用流程，检查插件输入字段是否正确加载文档中的对应数据。
- 查看工具调用日志，确认`toolChoice`与`functionCall`的配置参数与预设值一致。
- 模拟一次调用失败场景，验证是否触发预设的重试机制与告警通知。
- 检查工具调用结果的输出格式，确认是否为结构化的可直接导入评审纪要的内容。
