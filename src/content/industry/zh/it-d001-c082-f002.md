# 渠道归因与线索分发的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自广告平台、CRM系统、归因SDK与表单系统，用于代码与变更评审中的渠道参数核验、线索去重与归属判定。日常维护的文档包括归因规则配置表、线索分发表、渠道效果报表、异常线索核对单。数据更新节奏以日度或周度为主，字段包含渠道唯一标识、线索来源参数、销售归属账号、转化时间戳等，部分参数需匹配对应系统的格式要求。

## 这些特征在「上下文与 token」这一环带来什么约束
多源数据接入要求上下文需整合广告平台、CRM等不同系统的结构化与半结构化数据，不同来源的字段格式差异会增加代码评审中上下文拼接的复杂度，需限制单轮上下文的总token数量避免溢出。日度或周度的更新节奏要求上下文需定期刷新，避免使用过期的归因规则或线索数据影响变更评审的准确性。不同类型的业务文档长度差异较大，需针对不同文档类型配置差异化的token截取策略，确保核心业务字段不会被截断。

## 配置怎么定
本文档适用于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配多源业务文档的总长度，避免因token溢出丢失核心归因字段 |
| `quoteMaxToken` | 1500–2000 token/单文档 | 针对渠道报表、线索分发表等不同长度的业务文档，限制单文档引用的token上限 |
| 上下文刷新周期 | 每日1次或每周1次 | 匹配该品类数据的日度/周度更新节奏，确保上下文使用最新的归因规则与线索数据 |
| 文档分块重叠长度 | 100–200 字符 | 避免分块后丢失跨块的渠道参数与线索标识 |
| 最大单轮提问token | 3000 token | 限制连续提问的总token消耗，防止超出平台配额 |

## 容易做错的三处
- 现象：单轮上下文超出`maxContext`限制后，核心渠道参数被截断。原因：未针对多源业务文档的总长度调整`maxContext`配置，直接使用默认值。
- 现象：上下文未刷新，使用过期的归因规则导致渠道归属判定错误。原因：未配置与数据更新节奏匹配的上下文刷新周期，长期使用旧数据。
- 现象：离线接入reranker模型后出现rerank error报错。原因：未将reranker模型的token配额纳入总上下文token计算，导致token冲突。

## 怎么确认配好了
- 查看应用的上下文调用日志，确认每次调用的总token未超过`maxContext`的配置值。
- 触发数据更新后，检查上下文是否自动刷新为最新的归因规则与线索数据。
- 测试同时引用3份以上的渠道报表，确认所有文档的核心字段未被截断。
- 运行reranker模型测试，确认无rerank error报错，token消耗符合配置要求。
