# 游戏内容合规自查的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
本品类的数据主要来自游戏研发阶段的剧情脚本、游戏文本、美术资源说明，以及监管公开的合规要求。日常维护的文档包括内容自查表、敏感内容修改记录、用户协议、合规评审纪要。数据更新频率为每版本或每活动周期，单条合规评审数据包含文本内容、审核状态、修改轨迹、关联活动编号等字段，无固定统一格式，随研发进度动态调整。

## 这些特征在「上下文与 token」这一环带来什么约束
游戏内容合规自查的长文本、高频更新特征，对上下文与token配置带来多重约束。剧情脚本、长文本内容单段token占用较高，需严格限制上下文总token数避免调用超限。按版本/活动更新的数据要求上下文需关联对应周期的评审记录，召回范围需精准过滤无关历史数据。不同文档类型的token密度差异大，需针对性调整单文档召回的token上限，防止整体token溢出。同时合规自查需核对API调用成本，需明确区分输入输出token的统计维度。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文token数（`maxContext`） | 8000–12000 token | 游戏剧情脚本单段长度较高，需覆盖多轮评审上下文同时控制API调用成本 |
| 单文档最大召回token数（`quoteMaxToken`） | 2000–3000 token | 游戏文本、剧情脚本内容密度高，避免单文档占用过多上下文额度 |
| 上下文召回条数 | 前6条 | 合规评审纪要按版本/活动分组，过多召回会导致token溢出 |
| token统计显示 | 开启输入、输出分开统计 | 匹配合规自查的成本核算需求，便于核对额度使用情况 |
| 上下文过滤阈值 | 按实测标定 | 区分敏感内容与正常内容的召回优先级，避免无关文档占用token |

## 容易做错的三处
- 界面仅显示总token数，未区分输入、输出token。原因：未开启token统计显示配置，导致无法精准核对合规自查的API调用成本。
- 工作流中设置上下文数量为0后仍召回历史评审记录。原因：混淆了上下文召回条数与历史对话轮次的配置逻辑，未正确限定合规评审的上下文范围。
- 上下文引用中Markdown格式未正确渲染。原因：知识库文档切分时未保留格式标记，或`quoteMaxToken`配置过小导致格式片段被截断。

## 怎么确认配好了
- 查看FastGPT v4.17.0的AI调用日志，确认输入、输出token数分别展示，核对配置是否生效。
- 上传一段超过2000 token的剧情脚本，检查召回的上下文文档数量符合设定的召回条数。
- 测试将上下文数量设置为0，确认未召回历史合规评审记录。
- 上传带Markdown格式的内容自查表，检查上下文引用中格式正常显示。
