# 游戏服务器研发运维的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自游戏运行日志、实时在线人数监控、业务数据库及玩家反馈工单。日常产出的文档包含服务器架构说明、开服方案、合服方案与故障报告，文档字段多涉及服务器资源占用、在线用户数、数据校验条目等，单位涵盖核、GB、人次、数据条目等。数据更新频率多为每日同步，大型活动期间会按活动周期实时更新。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据高频且关联强业务逻辑，上下文需覆盖近期开服、合服的操作记录与故障排查日志，token消耗会随关联数据条目增多而上升。日常文档存在非标准化片段，若上下文未做合理限制，易引入冗余内容导致token超额。合服、开服的变更评审需要精准匹配历史配置与校验数据，若上下文范围过大，会干扰评审的核心判断，同时需避免因token不足丢失关键故障排查依据，影响后续问题定位。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 匹配游戏服务器变更评审需覆盖的近期操作与日志数据，避免单次请求token溢出 |
| `quoteMaxToken` | 1500–2000 token | 适配知识库切块5000token的场景，限制单次引用的切块token量，符合常规检索上限设置 |
| 分块长度 | 4000–5000 字符 | 匹配游戏服务器文档的单块内容密度，如开服方案、合服校验报告的分段内容 |
| 单次检索上限 | 前3–5条 | 减少冗余检索内容的token消耗，聚焦核心配置变更与故障排查记录 |
| 上下文历史保留时长 | 7 天 | 覆盖常规开服、合服的操作周期，避免过期数据干扰当前评审 |

## 容易做错的三处
- 现象：配置`quoteMaxToken`为1500后，仍出现检索切块超出限制的情况。原因：未同步调整知识库切块的匹配规则，或检索时未过滤非关联的游戏日志切块，导致超额token消耗。
- 现象：无法在界面查看单次问答的token使用情况。原因：未启用全局token统计开关，或未在对应日志采集路径中开启计数采集。
- 现象：工作流中无法按条件清空上下文历史。原因：未配置触发清空的规则节点，或未绑定对应条件的上下文变量，导致无法精准清理过期的开服、合服操作记录。

## 怎么确认配好了
- 查看FastGPT v4.17.0的全局统计页面，确认`maxContext`与`quoteMaxToken`的配置值与预设一致。
- 提交一份合服方案的变更评审请求，核对返回的上下文内容是否包含近7天的相关操作记录，且token消耗未超出预设上限。
- 模拟高频检索场景，检查是否出现token超额报错，验证单次检索上限的过滤效果。
- 触发工作流的清空条件，确认上下文历史中的过期数据被清理，无残留的非关联日志内容。
