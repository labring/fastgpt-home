# 游戏版号与出版申报的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
该品类的数据围绕单款游戏的出版申报全流程产生，日常文档包括申报请示文件、游戏申请表、著作权证明、审读报告等。数据来源涵盖国家新闻出版署办事服务平台、著作权登记档案、游戏包体文件及运营机构提交的资质材料。数据更新节奏随单款游戏申报进度不定期调整，每款游戏对应一套独立的申报数据集合，字段包含游戏基本信息、资质证明编号、审读修改记录等，无统一的批量更新周期。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据特征对上下文与token管理带来多重约束。单款游戏申报的关联文档类型多样，从结构化申请表到长篇审读报告均有覆盖，token消耗差异显著，需精准控制上下文窗口的token总量，避免超出模型处理上限。数据随申报进度不定期更新，上下文需支持动态加载最新提交的修改记录与资质材料，确保评审时使用的是当前有效版本。单款游戏对应一套独立数据集合，上下文需限定在当前申报项目范围内，防止跨游戏数据混入导致评审错误。申报环节需跨文档核对材料一致性，上下文需保留多份文档的关联信息，保障评审时可快速调取匹配内容。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `maxContext` | `8000–12000 token` | 该品类的单款申报文档总token量通常在该区间内，可覆盖核心申报材料与审读记录，适配FastGPT v4.17.0的常规模型窗口范围 |
| `quoteMaxToken` | `1500–2000 token` | 单份核心资质证明或审读报告的关键片段token量在此区间，可满足材料一致性核对的核心需求 |
| 上下文历史保留条数 | 前3–5条 | 申报流程的沟通记录集中在初审前的几轮，过多会占用过多token，影响核心评审内容的加载 |
| 文档分块长度 | `4000–5000 字符` | 该品类的文档多为结构化或半结构化，该长度可保证块内信息完整且token消耗合理 |
| 检索结果保留上限 | 前3–4条 | 申报材料的匹配内容通常集中在少量关键文档中，过多会超出上下文窗口的承载能力 |

## 容易做错的三处
- 现象：问答时返回的引用内容超过设置的`quoteMaxToken`限制，或日志中出现token超限报错。原因：未将检索到的文档切块内容按`quoteMaxToken`进行截断，直接将整块内容纳入上下文窗口。
- 现象：无法在界面或日志中找到每次问答的token消耗统计数据。原因：未开启FastGPT的token统计开关，或未在对应节点配置统计逻辑，无法追踪单轮调用的token使用情况。
- 现象：跨款游戏的申报数据被同时加载到上下文窗口，导致评审出现资质编号混淆或内容错配。原因：未将上下文窗口限定在当前申报项目的文档范围内，未添加项目ID作为上下文过滤条件。

## 怎么确认配好了
- 进入FastGPT的知识库配置页面，查看`maxContext`与`quoteMaxToken`的配置值，确认与预设的取值区间匹配。
- 发起一次模拟申报评审问答，查看返回的上下文内容是否仅包含当前申报项目的文档，无跨项目数据混入。
- 检查问答日志，确认每次调用的token消耗未超出预设的`maxContext`限制，且引用内容的token量符合`quoteMaxToken`的设置。
- 上传一份更新后的审读报告，再次发起问答，确认上下文加载的是最新版本的文档内容。
