# 游戏版号与出版申报的代码与变更评审辅助：多轮对话与提示词

## 这个品类的数据长什么样
本品类的数据围绕单款游戏出版申报全流程材料构成，包括申报请示文件、游戏申请表、著作权证明、审读报告等。数据来源包括国家新闻出版署办事服务指引、著作权登记文件、游戏包体及运营机构提交的资料。数据更新节奏为单款游戏申报周期内不定期更新，随申报环节推进补充材料，无固定批量更新周期。单份数据字段包含申报主体信息、游戏内容描述、著作权归属、审读意见等，需按申报要求匹配对应字段，无统一标准化单位。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
本品类的数据分散来自多个来源，且随申报环节不定期更新，要求多轮对话需逐步对齐不同阶段的材料。单款游戏的文档结构不统一，不同申报阶段提交的材料格式差异较大，提示词需适配不同阶段的字段要求。材料一致性核对环节耗时较长，多轮对话需逐步梳理材料间的差异。审批出错会导致审批不通过或上线延期，提示词需严格匹配申报要求的字段，避免遗漏关键信息。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定单款游戏申报的专属`chatId` | 实现会话隔离，避免不同申报项目的对话数据混淆，确保单款游戏申报的专属上下文 |
| `messages` | 保留前20条历史对话消息 | 适配单款游戏申报的对话上下文长度，避免超出模型限制，按实测标定 |
| 最大上下文 | 8000–12000 字符 | 本品类申报材料单份多为数千字符，需匹配单款游戏的申报材料总长度 |
| 单次召回上限 | 前5条召回结果 | 聚焦当前申报环节的关键材料，避免过多无关内容干扰审核 |
| `variables` | 绑定当前申报阶段的专属`variables` | 用于注入固定字段，如游戏名称、申报主体等 |

## 容易做错的三处
- 现象：对话界面提示未选择知识库，调试预览阶段正常。原因：`chatId`绑定的知识库未正确关联当前申报项目的知识库配置，导致正式调用时未加载对应知识库。
- 现象：多轮对话中上下文丢失，无法回溯之前的申报材料核对记录。原因：`messages`参数未正确保留足够的历史消息，导致上下文被提前截断，无法关联之前的申报材料信息。
- 现象：对话返回的材料字段与当前申报阶段不匹配。原因：`variables`未正确填充当前申报阶段的固定字段，导致提示词无法聚焦当前环节的审核要求。

## 怎么确认配好了
- 进入FastGPT v4.17.0的测试环境，输入单款游戏的申报材料字段，确认`chatId`绑定的知识库，验证会话隔离生效。
- 发起多轮对话，输入申报材料核对指令，查看历史消息区域，确认前20条历史对话被保留，上下文未被截断。
- 注入`variables`变量，查看对话输出中显示的申报固定字段，确认字段正确填充。
- 发起单次召回测试，确认召回结果数量符合前5条，聚焦当前申报环节的关键材料。
