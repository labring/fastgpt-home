# 游戏运营活动配置的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
游戏运营活动配置的核心数据来源于运营后台、玩家分群系统、付费数据平台与活动日志系统。日常产出的文档包含活动方案、奖励配置表、上线检查单与活动复盘记录，字段涵盖活动ID、奖励类型、发放阈值、生效时间与玩家分层规则等。数据更新频率多为周度，节假日临时活动会触发紧急更新。

## 这些特征在「上下文与 token」这一环带来什么约束
游戏运营活动配置的多源数据特征，对上下文与token处理带来多重约束。不同系统的字段格式差异大，直接拼接易出现上下文混乱；周度与临时结合的更新节奏，要求上下文支持动态刷新与临时扩容；奖励配置表与复盘文档的长文本属性，会快速消耗token配额；奖励核对与异常补偿等核心环节，需要完整的历史上下文支撑，不能出现关键信息截断。此外，出错后果直接关联玩家体验与营收，上下文的准确性与完整性要求高于通用场景。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 覆盖单周活动全量配置数据与3次历史复盘文档，避免截断关键核对信息 |
| `quoteMaxToken` | 1500–2000 字符 | 匹配奖励配置表单条记录的字段长度，确保数值核对时的上下文完整性 |
| 上下文刷新间隔 | 每12小时 | 适配周级更新节奏，避免加载过期的活动日志数据 |
| 临时活动上下文扩容阈值 | 按实测标定 | 应对节假日临时活动的突发数据量，触发时自动调整上下文上限 |
| 全局上下文绑定标识 | 活动ID | 确保不同活动的配置数据隔离，避免上下文混淆 |

## 容易做错的三处
- 界面显示上下文长度仅500 token，实际配置`maxContext`为8000 token。原因是混淆了模型输入token上限与系统上下文存储长度参数，未区分两类配置的作用范围。
- 无法在工作流全局变量、应用API请求头或普通模型管理页面配置AIPROXY_API_ENDPOINT与AIPROXY_API_TOKEN。原因是AIPROXY_API_ENDPOINT与AIPROXY_API_TOKEN为App/Admin服务端环境变量，需在服务部署阶段配置。
- 启动本地部署后报错提示AIPROXY_API_ENDPOINT与AIPROXY_API_TOKEN无效。原因是未配置必填的App/Admin服务端环境变量AIPROXY_API_ENDPOINT与AIPROXY_API_TOKEN，或配置的参数未匹配本地AI Proxy服务的实际根地址与管理员Token，或参数格式包含多余空格、引号等无效字符。

## 怎么确认配好了
- 上传单份奖励配置表与活动复盘文档，查看系统上下文预览面板的token消耗数值，确认未超过配置的`maxContext`上限。
- 发起一次代码变更评审请求，检查返回结果中是否包含历史活动的核对字段，确认全局上下文变量已正确加载。
- 测试节假日临时活动场景下的上下文加载，观察系统是否自动触发上下文扩容逻辑，无报错提示。
- 核对本地部署的App/Admin服务端环境变量，确认AIPROXY_API_ENDPOINT与AIPROXY_API_TOKEN无格式错误，与本地AI Proxy服务实际根地址与管理员Token一致。
