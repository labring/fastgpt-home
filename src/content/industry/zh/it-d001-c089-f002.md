# 漏洞扫描服务的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
本品类的数据主要来自漏洞扫描器、资产清单、CVE库与补丁公告，不同于渗透测试服务，本品类以工具化扫描与复扫闭环为核心。日常产出的文档包含扫描计划、漏洞清单、整改工单与复扫报告，各文档包含资产范围、漏洞编号、影响范围、整改状态等字段。数据更新频率为周度或月度，随扫描计划执行与补丁公告发布同步更新。核心数据围绕待评审代码关联的资产漏洞、变更影响范围展开，需覆盖变更前后的资产状态对比信息。

## 这些特征在「上下文与 token」这一环带来什么约束
数据来源分散且更新节奏不一，会导致上下文拼接时出现资产信息与漏洞数据的时间差，需要限制跨数据源的上下文加载范围。日常文档字段多且关联紧密，若无限制加载全量数据，会超出token上限导致模型截断关键信息。复扫报告与整改工单的关联核对需要跨文档上下文，若token分配不足，无法完整匹配变更前后的漏洞状态。同时，变更评审的代码片段与关联漏洞数据需精准绑定，过多无关的历史扫描数据会挤占有效上下文的token配额，影响评审准确性。

## 配置怎么定
以下配置适用于FastGPT v4.17.0版本：
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | `8000–12000 token` | 覆盖本品类单批次扫描计划、漏洞清单与变更代码片段的总数据量，避免模型截断关键评审信息 |
| `quoteMaxToken` | `2000–3000 token` | 保留漏洞编号、资产影响范围、整改工单编号等核心关联信息，为代码上下文预留足够配额 |
| 上下文刷新周期 | `7 天` | 匹配本品类周度或月度的数据更新节奏，保证加载的上下文与最新漏洞数据同步 |
| 关联文档召回上限 | `前 3 条` | 聚焦当前变更关联的最新扫描结果与整改工单，避免无关数据挤占token |
| 上下文过滤阈值 | 按实测标定 | 过滤与当前代码变更无关的历史扫描数据，提升有效上下文的token利用率 |

## 容易做错的三处
- 现象：界面提示上下文token超出限制，模型返回结果被截断。原因：未根据本品类的扫描数据量调整`maxContext`与`quoteMaxToken`的配额，导致总token占用超出模型上限。
- 现象：调用MCP工具后，当前代码变更与漏洞关联的上下文被清空。原因：未配置上下文自动保存参数，工具调用时未保留扫描计划与变更代码的绑定关系。
- 现象：HTTP请求读取上传的关联文件时返回404错误，文件路径末尾附带随机token字符串。原因：未对上传文件的路径进行token剥离处理，导致路径指向无效的临时存储地址。

## 怎么确认配好了
- 查看平台的上下文配额统计面板，确认当前配置的`maxContext`与`quoteMaxToken`数值与预设值一致。
- 执行一次模拟变更评审流程，检查关联的扫描计划、漏洞清单与整改工单是否完整加载，无截断或丢失。
- 触发MCP工具调用，验证上下文未被清空，可继续完成漏洞关联与代码评审的核对。
- 上传关联文件并发起HTTP请求，确认文件路径中的临时token已被正确剥离，服务可正常读取文件。
