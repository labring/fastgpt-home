# 版本发布与Release Notes的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
这个品类的典型数据来自Git标签、合并记录、CI制品与Issue里程碑，更新频率为每版本一次。日常产出的文档包括Release Notes、变更日志、版本标签与发布检查单，数据结构通常包含版本号、变更条目、破坏性变更说明、制品校验信息等字段。数据会随版本发布周期批量更新，单次版本的关联数据量通常覆盖该版本周期内的全部合并变更与关联任务。本页面基于FastGPT v4.17.0版本的配置逻辑编写。

## 这些特征在「上下文与 token」这一环带来什么约束
多源数据来源要求上下文需要整合Git代码变更、CI制品信息与Issue里程碑内容，需合理分配token以覆盖不同类型的关联数据。按版本更新的节奏意味着上下文无需高频刷新，但每次版本发布时需全量拉取当前周期的全部数据，需控制单批次上下文的token总量避免超出模型上限。变更条目与结构化字段的特征要求上下文召回需精准匹配变更类型，避免引入无关数据占用token，同时需保留变更条目的完整语义以确保评审逻辑连贯。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| 最大上下文token数 | `8000–12000 token` | 单版本Release Notes及关联数据的token总量通常在该区间内，避免超出主流大模型的上下文上限 |
| 引用最大token数 | `2000–3000 token` | 变更评审需聚焦核心变更条目，该取值可确保关键信息完整同时避免冗余 |
| 分块重叠长度 | `100–200 字符` | 变更条目通常具备连贯逻辑，重叠长度可避免分块导致的上下文断裂 |
| 上下文召回条数 | 前3–5 条 | 版本发布的核心变更通常集中在最近的合并请求中，该范围可平衡召回精度与token占用 |
| 自定义上下文开关 | 开启 | 支持通过API传入自定义版本变更数据，替代系统历史拼接的上下文逻辑 |

## 容易做错的三处
- 现象：召回的上下文片段与当前版本变更无法关联，出现变更归类错误。原因：分块时未保留变更条目的完整语义，分块长度过短导致上下文逻辑断裂。
- 现象：模型无法读取通过API传入的自定义版本变更数据，仍依赖系统历史对话拼接上下文。原因：未正确配置自定义上下文开关，默认启用了历史拼接逻辑。
- 现象：变更评审结果遗漏关键信息，比如未识别到破坏性变更说明。原因：引用最大token数设置过小，未完整召回核心变更条目导致信息缺失。

## 怎么确认配好了
- 查看知识库分块日志，确认每个变更条目作为一个完整分块，无断裂或截断情况。
- 发起测试请求，传入自定义版本变更数据，确认模型能正确关联并使用该上下文进行评审。
- 核对配置项的取值范围，确认最大上下文token数与当前版本数据的实际token总量匹配。
- 模拟变更评审场景，验证模型召回的上下文包含核心变更条目，无冗余无关内容。
