# 现场部署实施的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
现场部署实施的核心数据来自客户机房环境、设备清单、软件包、网络拓扑，日常配套文档包括部署手册、安装记录、配置清单、现场签到表。数据更新节奏为每单或每阶段，随现场安装、配置、排查环节动态新增内容。文档结构包含标准化字段，如部署手册的版本号、安装步骤，配置清单的IP地址、端口号，现场签到表的到场时间、客户确认签字等，无统一的跨项目固定字段格式。

## 这些特征在「上下文与 token」这一环带来什么约束
由于数据来源分散且随项目阶段动态更新，上下文召回需精准匹配当前环节的文档类型，避免加载无关的历史阶段数据，否则会快速消耗token并拖慢响应速度。现场部署实施的单阶段数据量有限但实时性要求高，上下文窗口需适配单项目的实际数据规模，不能套用通用场景的固定配置。同时，文档结构的非标准化特征要求对召回内容的长度做严格限制，防止过长的引用内容超出token上限导致截断或失败。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文 | `8000–12000 token` | 匹配现场部署实施单阶段的文档总数据量，避免超出FastGPT v4.17.0的默认模型窗口 |
| 召回匹配条数 | 前6条 | 对应现场部署的核心文档数量，减少无关token占用 |
| `quoteMaxToken` | 2000–3000 token | 限制单条引用内容的token占用，防止单条文档过长拖慢整体响应 |
| `maxContext` | 按单项目阶段数据量标定 | 适配每单/每阶段更新的数据特征，防止上下文过载 |
| 重排模型Token配额 | 1500 token/条 | 匹配部署文档的单页平均长度，提升召回内容的精准度 |

## 容易做错的三处
- 问答响应变慢且token消耗过高：现象为每次代码与变更评审的问答耗时超过10秒，后台日志显示token占用超出预设阈值，原因是未限制最大上下文范围，加载了全量客户机房环境、设备清单等非实时数据。
- 拉取Reranker模型ACCESS Token失败：现象为界面弹出Token无效报错，docker run命令执行后模型无法启动，原因是未正确配置模型访问凭证的挂载路径，或凭证权限未开放给部署容器。
- 知识库回答被截断：现象为简单模式对话可正常输出完整内容，但评审场景下内容提前终止，原因是`quoteMaxToken`设置过小，或`maxContext`超出模型支持的窗口上限。

## 怎么确认配好了
- 登录FastGPT后台配置页面，查看`maxContext`和`quoteMaxToken`的取值是否符合当前项目阶段的数据量范围。
- 发起一次模拟代码变更评审问答，检查响应耗时和token占用是否在预设区间内，无明显延迟或异常报错。
- 测试拉取Reranker模型，确认返回的Token校验结果正常，无无效凭证相关的报错信息。
- 触发知识库召回操作，检查返回的引用文档条数和单条内容长度是否符合配置要求，无过多无关内容或过长的单条引用。
