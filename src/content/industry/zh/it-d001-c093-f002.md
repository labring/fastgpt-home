# 用户增长与留存运营的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
该品类的核心数据来自用户行为日志、推送系统、实验平台与CRM系统。日常产出的文档包括增长实验方案、用户分层表、触达文案与留存分析报告。用户分层表包含用户ID、分层标签、触达频次等字段，触达文案标注了投放渠道与触发条件。数据更新频率分为日级与周级，日级数据多为实时采集的用户行为日志，周级数据则为汇总后的实验报告与分层报表。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据体量较大，单份Excel文件可达万行级别，且日级更新的用户行为日志会持续新增数据，若上下文拼接的颗粒度过粗，会导致token消耗过高。同时文档结构多样，既有结构化的用户分层表，也有长文本的实验方案，单一的分块规则难以适配所有文档类型，容易出现关键信息被截断或冗余内容混入上下文的情况。高频更新的数据要求上下文能够及时同步最新的用户分层与实验结果，否则会基于过时信息生成触达策略，引发用户反感。此外，该品类的核心目标是提升站内用户留存，召回的关联数据需精准匹配当前运营需求，过多无关的历史数据会额外占用token配额。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的界面与参数规则制定。
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| 分块长度 | 800–1200 字符 | 适配该品类结构化与非结构化文档混合的场景，避免单块过大导致token消耗超标 |
| 块重叠长度 | 100–200 字符 | 保留跨分块的字段关联，避免用户分层表的跨行列信息丢失 |
| `maxContext` | 8000–12000 token | 匹配该品类的运营文档与日志数据总量，控制整体上下文的token使用上限 |
| `quoteMaxToken` | 2000–3000 token | 聚焦触达文案与实验方案的核心内容，确保关键运营信息被完整召回 |
| 单次召回上限 | 前 8 条 | 减少冗余数据占用的token配额，精准匹配当前运营的咨询需求 |
| 重排开关 | 开启 | 提升召回内容的相关性，过滤无关的历史数据，降低无效token消耗 |

## 容易做错的三处
- 现象：设置分块长度过大时，单条数据块token消耗过高，出现`Reached the max retries per request limit`报错。原因是未适配该品类万行级Excel的小分块需求，默认参数的分块尺寸超出了接口限制。
- 现象：召回数据量过多，导致token消耗超出配额。原因是未设置合理的单次召回上限与`maxContext`参数，将无关的历史用户行为日志全部纳入上下文。
- 现象：用户分层表的跨行列信息丢失，触达策略匹配错误。原因是块重叠长度设置过小，未保留跨分块的字段关联信息。

## 怎么确认配好了
- 上传一份典型的万行级Excel用户分层表，查看分块后的预览内容，确认每个数据块的长度符合预设范围。
- 发起一次模拟运营咨询，查看上下文拼接的token消耗数据，确认未超出预设的`maxContext`配额。
- 测试触达文案的召回结果，确认核心文案内容与触发条件被完整纳入上下文。
- 查看知识库的更新日志，确认日级与周级数据的同步频率符合配置要求。
