# 用户验收测试支持的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
本品类的数据来源于需求规格文档、测试环境配置、客户业务样例素材及缺陷管理系统，更新节奏为每交付阶段或每版本迭代一次。日常产出的核心文档包含UAT用例、验收问题单、验收报告与签字确认单，文档字段覆盖业务场景描述、测试步骤、缺陷详情、验收结论等，无统一固定单位，随客户业务场景调整。核心关联代码变更评审的上下文多来自评审记录、测试脚本片段与客户反馈内容，数据体量随项目规模波动。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类的数据特征对上下文与token环节带来多重约束。多源分散的数据来源需整合需求、测试环境、缺陷系统等多类内容，提升了token的承载压力；阶段式的更新节奏要求上下文需随版本迭代刷新，需定期清理过期关联内容，避免无效token占用。日常文档结构非标准化，UAT用例、验收问题单等字段差异较大，上下文切片需适配多样文本格式。验收环节的合规文档需完整纳入上下文，不能随意截断，进一步限制了token分配额度。若上下文溢出，会直接阻断用例准备、问题归类等核心流程，引发验收延期风险。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 常规项目取`8000–12000 token`，大型验收项目取`15000–20000 token` | 适配本品类多源文档的体量需求，确保完整承载UAT用例、缺陷单等核心上下文，适配FastGPT v4.17.0的上下文处理逻辑 |
| `quoteMaxToken` | `2000–3000 token` | 代码变更评审的上下文片段多为测试脚本、缺陷描述，单段引用无需过长，避免占用过多总token额度 |
| 上下文切片重叠长度 | `200–300 字符` | UAT用例等文档存在连续业务逻辑，重叠切片可避免上下文断裂，保障评审逻辑连贯 |
| 上下文刷新周期 | 每阶段交付前1天 | 本品类数据按阶段更新，需在阶段开始前刷新上下文，确保关联最新的需求与缺陷内容 |

## 容易做错的三处
- 现象：调用代码评审相关工具时返回上下文溢出报错，或生成内容截断关键验收用例步骤。原因：未根据本品类的多源文档体量调整`maxContext`参数，token额度不足以承载完整的UAT用例与缺陷记录上下文。
- 现象：连续发起验收评审相关的追问后，后续回答无法关联前序的缺陷单信息，出现答非所问。原因：未配置合理的上下文刷新周期，或`maxContext`设置过小导致旧上下文被自动清理。
- 现象：上传客户业务样例文档后，关联的代码变更评审片段丢失部分业务场景描述。原因：上下文切片重叠长度设置不合理，导致关键业务逻辑被截断，未保留完整上下文关联。

## 怎么确认配好了
- 发起包含UAT用例、缺陷单内容的测试提问，核对回答是否覆盖前序关联的业务场景信息。
- 查看上下文展示模块，确认已纳入当前阶段的需求规格、测试环境配置等核心数据。
- 触发代码变更评审的上下文调用，检查返回内容是否包含完整的验收相关文档片段，无截断情况。
- 模拟多轮连续追问，确认后续回答可关联前序的验收问题单内容，无答非所问情况。
