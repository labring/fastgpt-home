# 社区举报处理的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
社区举报处理的核心数据来自举报系统、内容详情、用户历史记录与审核规则，更新频率为日级或实时。日常处理文档包含举报工单、处理记录、申诉单与用户通知模板，单条工单数据包含举报提交时间、涉事内容片段、用户标识、关联违规类型、处置状态等字段，每条工单会关联3到5条历史记录或规则条目，整体数据无统一标准化格式，需按字段提取关键信息。

## 这些特征在「上下文与 token」这一环带来什么约束
社区举报处理按单处理用户提交的具体内容，单条工单的关联数据量波动较大，需完整加载涉事内容、用户历史与审核规则才能完成有效性判断。实时更新的数据要求上下文需动态拉取最新信息，避免使用过期的审核规则或用户历史记录。非标准化的文档结构导致无法直接按固定长度分块，需按字段筛选核心信息，否则会引入无关token占用。单工单的上下文需求集中在短时间内的精准信息，无需加载全量社区数据，因此上下文配额需适配单条工单的实际规模，不参考通用内容池的配置标准。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的上下文与token管理逻辑。

| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `maxContext` | `8000–12000 token` | 适配社区举报工单关联的涉事内容、用户历史记录与审核规则的平均token总量，确保单条工单的完整上下文可被加载 |
| `quoteMaxToken` | `2000–3000 token` | 限制单次请求中引用的违规内容、处理记录的token长度，避免单条引用占用过多上下文配额 |
| 上下文过滤规则 | 仅保留举报ID、涉事内容、用户30天内历史记录、关联审核规则 | 过滤无关数据，减少非必要的token占用，聚焦举报处理的核心信息 |
| 实时数据拉取触发条件 | 按工单提交时间拉取最近1小时内的更新数据 | 匹配举报数据的实时更新频率，避免拉取过期或无关的历史记录 |
| 上下文截断优先级 | 优先保留涉事内容片段与审核规则条目 | 确保举报有效性判断的核心信息不被截断，保障处置建议的准确性 |

## 容易做错的三处
- 现象为界面提示“上下文token超出上限”，原因是未按单条举报工单的实际关联数据配置`maxContext`，错误使用了通用内容审核的大上下文配额，导致单条工单的完整信息无法加载。
- 现象为返回的处置建议中未包含用户历史举报记录，原因是未配置上下文过滤规则，或过滤规则错误排除了用户历史字段，导致关键关联信息未被纳入上下文。
- 现象为调用时返回token消耗异常偏高，原因是未设置`quoteMaxToken`限制，导致单次请求中重复引用了大量重复的审核规则内容，浪费token配额。

## 怎么确认配好了
- 导入单条典型举报工单，查看上下文预览界面，确认包含涉事内容、用户历史记录、关联审核规则的完整信息。
- 模拟发起10次连续请求，查看token消耗统计，确认单次请求的token量在配置的`maxContext`范围内。
- 修改`quoteMaxToken`的取值，观察返回内容的引用长度，确认引用内容的token数符合配置限制。
- 模拟触发实时数据拉取，查看系统日志确认仅拉取了工单提交时间范围内的更新数据，避免无效拉取。
