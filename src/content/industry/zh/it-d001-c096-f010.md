# 社区举报处理的代码与变更评审辅助：引用来源与溯源

## 这个品类的数据长什么样
该品类的数据通常来自社区举报系统、待审核内容详情页、用户历史行为记录与内置审核规则库。日常处理依托的文档包括举报工单、处置进度记录、用户申诉单与标准化通知模板。数据更新节奏以实时或日级为主，单条数据包含举报标识、关联内容ID、举报方与被举报方信息、违规类型标签、处置结果等字段，无统一固定单位，随单条内容与操作环节变化。

## 这些特征在「引用来源与溯源」这一环带来什么约束
由于该品类数据来源分散且单条工单关联多维度内容，引用溯源需覆盖举报原始内容、历史处置记录与内置审核规则，因此需要支持多来源数据的关联调用。实时或日级的更新节奏要求溯源环节具备低延迟的数据拉取能力，避免处置流程滞后。不同类型文档的字段差异，要求配置时统一数据提取的映射规则，防止字段不匹配导致的引用失效。同时按单处理的业务特性，需确保溯源结果仅关联当前举报工单，避免跨单数据混淆，影响处置准确性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大引用token数 | 800–1200 token | 适配单条举报工单关联的多文档内容总长度，避免超出模型上下文限制 |
| 数据拉取超时时间 | 600秒 | 适配实时更新的举报数据拉取需求，避免因数据延迟导致处置中断 |
| 返回数据范围 | 仅包含举报工单、处置记录、审核规则 | 聚焦当前品类的核心业务数据，减少无关内容占用资源 |
| 详情字段开关 | 开启完整字段展示 | 确保提取的字段覆盖举报标识、关联内容ID等关键信息，满足溯源校验 |
| 单次召回条数 | 前3条关联数据 | 匹配按单处理的业务特性，仅调用当前举报工单的关联数据，避免跨单干扰 |
| 上下文召回阈值 | 按实测标定 | 适配不同社区的内容密度与举报量，确保召回数据的相关性 |

## 容易做错的三处
- 现象：界面提示`quote type error`报错，无法完成引用配置。原因：未按照举报工单的字段格式配置数据映射，导致系统无法识别传入的变量类型。
- 现象：引用结果仅返回单条数据，无法覆盖多来源的举报关联内容。原因：未调整单次召回条数的配置，仅调用了单类数据，未覆盖工单、记录、规则等多维度内容。
- 现象：引用内容未包含关联文件的地址信息，或无法隐藏知识库来源展示。原因：未开启详情字段开关以提取内容详情中的文件地址字段，或未关闭默认的来源展示开关，导致冗余信息出现。

## 怎么确认配好了
- 确认当前使用的FastGPT v4.17.0版本支持所选配置项。
- 提交一条测试举报工单，查看回复内容是否包含工单ID、处置记录等核心字段。
- 检查系统日志，确认无`quote type error`类的字段匹配错误。
- 核对引用内容的token消耗，确保未超出配置的最大引用token数范围，且仅关联当前测试工单的关联数据。
