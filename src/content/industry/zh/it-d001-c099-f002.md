# 移动端开发的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
移动端开发团队的核心数据来自代码仓库的PR变更记录、应用商店后台的审核规则文档、崩溃监控平台的堆栈日志，以及机型覆盖数据平台的系统版本分布信息。日常产出的文档包含端版本发布单、多机型适配清单、崩溃分析报告和应用商店上架资料，数据更新随版本发布节奏执行，部分监控数据每日同步。单条PR变更可能包含跨iOS、Android的适配代码，应用商店资料包含多语言描述和权限声明，崩溃分析报告则包含设备型号、系统版本和错误堆栈等结构化字段。

## 这些特征在「上下文与 token」这一环带来什么约束
移动端开发的评审上下文需要覆盖代码变更、适配规则、历史崩溃数据等多类内容，单条上下文总长度普遍高于通用开发场景。多机型适配代码和完整的应用商店审核资料会占用大量token，若上下文长度不足会导致核心评审信息被截断。同时，数据更新随版本节奏，上下文需要支持按版本维度召回历史文档，避免跨版本的上下文混淆。此外，崩溃分析报告的结构化字段需要精准匹配，过长的上下文会降低召回精度，需平衡上下文长度与信息完整性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文长度 | 8000–12000 token | 移动端PR变更常包含跨iOS、Android的多机型适配代码，加上完整的版本发布单，单条上下文总长度较高 |
| `maxContext` | 按实测标定 | 不同团队的代码仓库规模、文档数量存在差异，需结合实际调用日志调整 |
| 引用最大token数 | 1500 字符 | 移动端机型适配的代码片段、权限配置文档的单条内容长度有限，需控制单条引用的token消耗 |
| `quoteMaxToken` | 2000–3000 token | 应用商店审核资料、崩溃分析报告的核心内容需完整召回，需匹配单条引用的token上限 |
| 上下文召回条数 | 前3–5条 | 移动端开发的变更评审仅需最近的版本发布单、适配清单及对应代码变更，过多会占用不必要的token |

## 容易做错的三处
- 调用MCP工具后模型上下文被清空：现象为每次调用外部工具获取机型权限或适配信息后，模型无法延续之前的评审话题，原因是未配置`maxContext`支持工具调用后的上下文保留机制。
- 上传文件路径携带额外token参数：现象为通过FastGPT上传的应用商店资料或崩溃报告文件路径，末尾附带随机token参数，无法直接通过http请求传递给后端处理服务，原因是未关闭文件上传的token附加配置。
- 误将上下文上限设为4000token：现象为长PR变更、完整的适配清单无法完整传入模型，导致评审时缺失核心适配规则或代码变更内容，原因是未根据移动端开发的文档特征调整token上限。

## 怎么确认配好了
- 提交包含多机型适配代码的PR变更，查看模型召回的上下文是否包含对应版本的适配清单与历史崩溃分析报告。
- 调用MCP工具获取机型权限信息，确认后续的评审对话可延续之前的上下文，未出现话题中断情况。
- 上传应用商店审核资料，检查后端接收的文件路径是否无额外token参数，可正常读取文件内容。
- 查看FastGPT v4.17.0的上下文配置面板，确认`maxContext`和`quoteMaxToken`的取值符合预设的配置标准。
