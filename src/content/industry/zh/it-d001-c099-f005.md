# 移动端开发的代码与变更评审辅助：多轮对话与提示词

## 这个品类的数据长什么样
移动端开发的代码与变更评审相关数据主要来自代码仓库、应用商店后台、崩溃监控平台、机型覆盖数据。数据更新频率为每日或每版本发布周期。日常关联文档包括端版本发布单、机型适配清单、崩溃分析报告、应用商店审核资料。数据字段包含机型系统版本号、权限申请状态、崩溃日志唯一标识、应用商店审核进度状态等，无统一固定格式，需根据不同评审场景提取对应字段。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
由于数据来源分散且更新频率不固定，多轮对话需通过唯一标识绑定当前评审任务，避免混淆不同会话的上下文。日常文档结构多样，提示词需明确指定引用的文档字段，确保模型能准确匹配评审需求，例如从机型适配清单中提取目标机型版本，从应用商店后台获取审核规则。移动端评审的核心关注点为机型适配与应用商店合规，多轮对话的上下文长度需控制在合理范围，避免因加载过多历史数据导致响应延迟，影响评审效率。同时，数据关联的出错后果直接影响应用上线，提示词需强化对权限调用、审核规则的校验逻辑，确保评审结果符合上线要求。

## 配置怎么定
本配置参考FastGPT v4.17.0版本的功能逻辑，具体参数与建议如下：

| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `chatId` | 绑定当前代码评审会话的唯一标识 | 确保多轮对话关联同一评审任务的上下文，避免不同评审任务的消息混淆 |
| `messages` | 保留最近 15–25 条对话消息 | 移动端评审的上下文通常集中在近期的代码变更与适配问题，过长会导致模型响应延迟 |
| `variables` | 传入当前评审的机型列表、应用商店审核要求、崩溃日志关键词 | 覆盖移动端开发评审的核心参考数据，提升模型评审的针对性 |
| 温度设置 | 0.6–0.8 | 平衡评审的严谨性与灵活性，适配代码规则校验与适配方案推导的需求 |
| 会话超时时间 | 600 秒 | 适配移动端评审任务的处理时长，避免中途中断会话导致数据丢失 |

## 容易做错的三处
- 现象为同一对话中修改的全局变量未在后续交互中生效，原因是未在配置中允许`variables`的会话内动态更新，仅保留了初始传入的变量值。
- 现象为无法区分不同轮次的用户提问与AI回复，原因是未通过`chatId`绑定唯一会话标识，导致消息列表混杂多个评审任务的内容。
- 现象为无法获取每一次的提问内容，原因是未正确配置`messages`参数的上下文提取规则，仅保留了最后一条消息，丢失了历史提问记录。

## 怎么确认配好了
- 发起首次代码评审提问，检查`messages`参数是否正确加载了历史上下文与当前提问内容。
- 修改全局变量后发起二次提问，验证变量值是否在模型响应中被正确引用。
- 通过`chatId`切换不同评审会话，检查会话间的上下文未发生混淆。
- 查看温度设置项，确认取值在0.6–0.8区间内，符合当前评审的需求。
