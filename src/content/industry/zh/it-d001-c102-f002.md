# 缺陷管理与回归测试的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
该品类的核心数据来自缺陷管理系统、测试报告、代码提交记录与用户反馈，更新频率为每日或每版本迭代周期。日常处理的文档包括缺陷单、回归清单、修复验证记录与缺陷统计报表，其中缺陷单包含复现步骤、优先级、关联代码片段等字段，回归清单关联测试用例与待验证缺陷，单份文档的文本长度从数百字符到数千字符不等，代码提交的diff片段则以行级代码块为基础单位。

## 这些特征在「上下文与 token」这一环带来什么约束
数据来源多样导致文本格式差异较大，需保留缺陷复现步骤、关联代码逻辑等关键上下文，避免拆分导致信息断裂。高频更新的特性要求token处理流程适配实时同步的缺陷与测试数据，防止因处理延迟导致评审滞后。不同文档的字段关联紧密，如缺陷单与代码提交需同时召回才能完成评审，因此上下文召回需兼顾多源数据的token占比，避免单一数据过载。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配缺陷单、回归清单的常规文本长度，避免拆分关键逻辑 |
| 重叠长度 | 100–200 字符 | 保留分块间的上下文关联，防止关键信息被截断 |
| `maxContext` | 4000–6000 token | 覆盖单次代码评审所需的缺陷、代码、测试数据总和 |
| `quoteMaxToken` | 1500 token | 限定召回的关联缺陷与代码片段的总token数，避免上下文过载 |
| 按实测标定 | 按实测标定 | 适配不同规模团队的缺陷与代码数据规模 |

## 容易做错的三处
- 现象：知识库录入数据后fullTextTokens字段为空，原因：未配置指定文本不拆分规则，系统强制拆分关键内容后无法生成有效token。
- 现象：调用代码评审功能时提示上下文超限报错，原因：`maxContext`取值超出适配团队数据的合理范围，未结合缺陷与代码的总token规模调整。
- 现象：分块处理后关键代码函数被拆分为多个片段，原因：混淆了分块长度的统计单位，未针对代码片段调整分块策略。

## 怎么确认配好了
- 查看知识库数据处理日志，确认分块后的文本未拆分缺陷复现步骤或核心代码函数。
- 进入FastGPT v4.17.0的知识库配置页面，核对`maxContext`与`quoteMaxToken`的取值与预设配置一致。
- 发起一次模拟代码变更评审，检查召回的关联缺陷与测试数据的总token数符合配置限定。
- 手动标记一段关键文本为不拆分内容，验证系统录入后fullTextTokens字段生成正常。
