# 账号封禁与申诉复核的代码与变更评审辅助：工作流编排

## 这个品类的数据长什么样
通常，该品类的核心数据来自风控系统、审核记录、用户行为日志、举报证据四类来源，更新节奏为日级或实时。日常处理的文档包含封禁记录、申诉材料、复核意见、用户通知四类。封禁记录包含账号标识、违规类型、处置时间、处置等级字段；申诉材料包含用户举证内容、提交时间、关联账号字段；复核意见包含审核结论、调整依据字段；用户通知包含触达渠道、发送时间字段。数据无固定统计口径，仅随业务流程实时或批量更新，不同场景下的字段命名与结构存在细微差异。

## 这些特征在「工作流编排」这一环带来什么约束
首先，数据来源分散且更新节奏差异大，工作流需要支持实时拉取风控系统的最新违规数据与批量导入历史审核记录两种模式，节点触发需匹配数据更新的时间窗口，避免处理过时数据。其次，核心文档包含多类结构化字段，工作流需通过参数绑定精准匹配对应账号的相关数据，避免跨账号拉取错误导致的误判。第三，最耗时的违规证据核对与申诉理由判断环节，要求工作流节点设置合理超时与重试机制，防止因单节点卡顿或数据拉取延迟导致整体流程中断。最后，出错后果直接关联账号权益与平台合规性，工作流需增加前置校验节点，确保数据匹配与处置逻辑的准确性，降低误封、违规账号回流等风险。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文 | 前20条会话记录 | 匹配账号申诉的多轮沟通场景，避免上下文过载影响执行效率 |
| 节点超时时间 | 300秒 | 适配违规证据核对的常规耗时，避免因单次节点卡顿中断流程 |
| 变量绑定 | 绑定`variables`中的账号ID字段 | 精准拉取对应账号的封禁记录与申诉材料，防止数据匹配错误 |
| 节点触发条件 | 按`nodeId`绑定的上游节点完成状态触发 | 确保工作流按数据流转顺序执行，避免前置节点未完成就启动后续处理 |
| 重试次数 | 2次 | 应对网络波动或临时数据拉取失败，减少人工介入成本 |

## 容易做错的三处
- 现象：工作流节点无法加载对应账号的申诉材料，原因是未在节点中绑定`variables`中的账号ID参数，导致拉取数据时匹配错误。
- 现象：工作流执行超时中断，原因是未设置合理的超时时间，直接使用默认配置，无法适配违规证据核对的耗时需求。
- 现象：工作流无法延续多轮对话，原因是未正确配置上下文传递规则，导致会话上下文在节点间传递时丢失，对应实际使用中常见的多轮对话异常问题。

## 怎么确认配好了
- 检查工作流中`variables`是否绑定了账号ID、违规类型等核心业务字段，确保数据拉取的精准性。
- 验证节点超时时间与重试次数的设置，模拟单次节点卡顿场景，确认流程不会直接中断。
- 触发多轮对话测试，确认会话上下文能够在工作流节点间正确传递，符合业务场景需求。
