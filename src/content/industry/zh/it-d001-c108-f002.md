# 质保期缺陷响应的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自客户提交的质保工单、系统运行日志、项目合同质保条款以及代码版本记录。日常流转的文档包括质保工单、缺陷确认单、修复记录与客户确认单，数据更新以每日同步或每单触发为主。数据字段包含工单编号、缺陷描述、责任归属、修复方案、客户反馈等，无统一强制格式，随项目交付的质保范围调整，不同项目的字段完整性存在差异。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据来源分散且格式不统一，包含非结构化的工单描述、结构化的日志字段与条款文本，对上下文召回的覆盖范围提出要求。数据按日或每单更新，需确保上下文同步最新的质保条款与工单状态，避免引用过期信息。不同文档的长度差异较大，从简短的缺陷确认到完整的版本记录不等，需合理分配token资源以平衡召回完整性与响应效率。责任边界判断环节需关联多源数据，上下文召回需覆盖足够的关联信息，同时防止token超限导致的内容截断。

## 配置怎么定
以下配置适配FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文 | 8000–12000 token | 适配质保工单、版本记录等多源文本的长度需求，避免截断核心质保条款与缺陷描述 |
| 知识库最大引用 | 前6条关联数据 | 覆盖责任边界判断所需的工单、日志与修复记录，平衡token占用与召回精度 |
| 最大响应tokens | 2000–3000 token | 确保输出的修复方案协调建议、客户确认指引等内容完整，无强制截断 |
| `maxContext` | 按实测标定 | 适配不同项目的质保范围与数据量，避免因固定值导致的上下文溢出或召回不足 |
| `quoteMaxToken` | 1500–2000 token per quote | 限制单条引用的token长度，防止单条数据占用过多上下文资源 |

## 容易做错的三处
- 现象：配置`maxContext`后仍出现上下文截断报错，状态码返回413。原因：未结合该品类的多源数据长度调整取值，固定使用过小的token阈值。
- 现象：知识库最大引用条数设置为前10条后，返回的关联数据中出现过期的质保工单。原因：未配置按更新时间过滤上下文的规则，导致召回非最新的缺陷记录。
- 现象：部署重排模型时未正确配置环境变量，导致上下文关联精度下降。原因：未参考该品类的文本类型调整模型参数，遗漏适配质保工单格式的配置项。

## 怎么确认配好了
- 提交一条典型质保工单，检查上下文召回的内容是否包含对应项目的质保条款与最新缺陷记录。
- 调整配置项取值后，测试不同长度的缺陷描述输入，确认无强制截断或token超限报错。
- 查看知识库引用的数据源更新时间，确认仅召回符合项目质保周期的有效数据。
- 触发代码变更评审辅助任务，检查返回的关联数据是否覆盖责任边界判断所需的全部字段。
