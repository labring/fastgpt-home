# 运维外包驻场服务的代码与变更评审辅助：上下文与 token

本文适配FastGPT v4.17.0版本。

## 这个品类的数据长什么样
该品类的典型使用主体为外包驻场工程师、服务经理与客户IT部门，日常处理的文档包括驻场日报、服务台工单、巡检报告与SLA月报。数据来源涵盖客户ITSM系统、监控平台、资产清单与值班记录，更新节奏为日度或月度，数据形态以结构化条目与非结构化文本混合为主，字段多包含工单编号、巡检项、服务响应记录等内容。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据来源分散且混合结构化与非结构化内容，上下文拼接时易产生冗余信息，需要严格限制总token量以避免超出模型处理上限。日度更新的工单与巡检数据时效性较强，上下文召回需优先筛选近期条目，同时控制单轮上下文的token消耗。SLA月报等文档篇幅较长，单次召回的知识库切块可能占用过多token配额，需要调整上下文的分配规则。此外，驻场服务涉及客户内部资产与服务细节，上下文的token统计需精准匹配文档实际长度，防止泄露无关敏感信息。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配驻场服务多文档拼接的上下文需求，避免超出主流大模型的上下文处理上限 |
| `quoteMaxToken` | 1500 token | 匹配巡检报告、服务工单等单文档的平均token长度，防止单条引用占用过多上下文空间 |
| 单次召回条目数 | 前6条 | 平衡信息完整性与token消耗，适配驻场服务多源数据的召回需求 |
| 召回数据时间范围 | 近30天 | 匹配日度/月度更新的数据周期，优先使用时效性强的驻场相关数据 |
| 知识库切块大小 | 按实测标定 | 适配驻场文档的结构特征，避免切块过大导致召回后token溢出 |

## 容易做错的三处
- 部分场景下响应内容突然变短，界面显示的响应token数为200，原因是上下文拼接占用了过多总token配额，触发了模型的单轮响应token上限限制。
- 云空间部署时无法找到单独的token配置字段，原因是云版本的token配置集成在应用密钥绑定环节，未单独暴露配置入口。
- 知识库切块设置为5000token但引用上限为1500时仍出现异常召回，原因是切块后的实际token统计与预设值存在偏差，未同步调整上下文的总token限制。

## 怎么确认配好了
- 查看应用的上下文统计面板，确认`maxContext`的配置值与实际显示的上下文token上限一致。
- 提交包含多份驻场文档的测试请求，检查返回内容的引用token数未超出`quoteMaxToken`的设置。
- 测试不同时间范围的文档召回，确认仅召回近30天内的驻场相关数据。
- 查看系统日志中的token统计字段，确认实际消耗的token与配置值匹配。
