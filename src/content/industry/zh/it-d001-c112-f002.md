# 问题管理与根因分析的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
这个品类的典型使用主体为SRE、技术负责人与质量团队，日常管理的文档包括RCA报告、问题单、复盘纪要、整改跟踪表。数据来源涵盖故障时间线、运行日志、监控指标、代码提交记录，更新频率为每次重大故障或每月一次。文档包含故障发生时间、根因描述、关联代码变更、整改项状态等固定字段，单份文档内容规模随故障复杂度波动，无统一统计阈值。本内容基于FastGPT v4.17.0版本编写。

## 这些特征在「上下文与 token」这一环带来什么约束
品类数据的多源混合特性要求上下文召回需覆盖日志、代码提交记录等不同格式内容，需针对性配置召回规则。月度级别的更新频率意味着无需高频刷新上下文缓存，可降低token消耗与计算资源占用。固定的文档字段结构要求上下文匹配聚焦根因、整改项等核心字段，避免无关内容占用token。最耗时的证据收集环节对应需召回多维度关联数据，需严格控制单轮上下文的token上限，防止超出模型承载能力。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `maxContext` | 前12条关联问题单与RCA报告 | 匹配月度更新的文档规模，避免单轮上下文token溢出 |
| `quoteMaxToken` | 8000 token | 适配主流大模型的单轮对话token上限 |
| 上下文召回阈值 | 相似度≥0.75 | 过滤低关联的非本次故障相关数据 |
| 单次召回上限 | 前6条监控指标与故障时间线 | 控制单轮上下文的总token消耗 |
| 上下文刷新周期 | 30天 | 匹配品类每月一次的重大故障更新频率 |

## 容易做错的三处
- 现象：界面提示token消耗超限，返回状态码413。原因：未限制`maxContext`的召回条数，将全量历史文档纳入单轮上下文。
- 现象：搜索结果与当前问题单无关联，返回的日志条目核心字段为空。原因：未设置合理的上下文召回阈值，召回了低关联的非本次故障数据。
- 现象：初始化root密码验证失败。原因：未正确配置docker-compose.yml中的INITIAL_ROOT环境变量，或部署后未更新对应配置。

## 怎么确认配好了
- 查看上下文召回日志，确认仅召回符合品类数据源的文档内容。
- 测试单轮对话的token消耗，确认未超过配置的`quoteMaxToken`上限。
- 验证root密码登录，确认环境变量配置与登录输入一致。
- 检查应用访问路径，确认符合预设的上下文访问规则。
