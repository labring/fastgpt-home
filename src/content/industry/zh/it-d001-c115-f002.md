# 项目实施计划管理的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
这个品类的数据通常由项目经理、实施经理及PMO维护，日常产出项目计划、里程碑清单、周报、风险问题清单四类核心文档。数据来源包括项目合同、工作分解结构（WBS）、客户日程及企业项目管理系统。数据更新节奏以周度或单里程碑节点为周期，文档结构多包含任务节点、关联责任人、交付物要求及时间节点字段，无统一强制格式，随项目规模动态调整。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据分散来自合同、WBS、项目管理系统等多源渠道，且更新周期以周或里程碑为单位，全量历史数据无需全部纳入上下文。不同文档的字段结构差异较大，核心信息分散在任务节点、责任人、交付要求等字段中，若直接全量导入会导致无效token占比过高。同时，跨方排期协调产生的文本量较大，单次上下文拼接若未做限制，会快速耗尽模型token配额，影响评审效率与稳定性。此外，项目计划的时效性较强，过期的历史任务数据无需长期保留在上下文中，需针对性限定`maxContext`的有效范围与召回边界。

## 配置怎么定
本页面基于FastGPT v4.17.0版本的配置逻辑编写，以下配置项适配该品类的核心数据特征：
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | `12000–15000 token` | 该品类单周更新的核心文档token总量通常处于该区间，可匹配多数通用大模型的上下文配额 |
| `quoteMaxToken` | `3000–4000 token` | 需优先保留任务节点、责任人、交付要求等核心评审信息，限制非核心文本的token占用 |
| 上下文召回范围 | 近1个里程碑周期内的文档 | 该品类数据更新以周或里程碑为周期，过期数据对评审辅助的价值较低 |
| 分块重叠长度 | `200–300 字符` | 项目计划的任务节点存在连续关联内容，重叠分块可避免关键信息被截断 |
| 上下文过滤规则 | 仅保留任务、风险、排期相关字段 | 该品类文档中非核心的格式说明、通用备注等内容无需纳入上下文 |

## 容易做错的三处
- 现象为启动时出现`failed to get gpt-3.5-turbo token encoder`异常，原因是未正确配置上下文的token限制，导致模型尝试加载超出兼容范围的token编码器。
- 现象为Markdown格式的评审结果被截断，展示内容末尾出现`...[hide X char]`提示，原因是未设置`quoteMaxToken`参数，导致核心评审内容超出模型输出token配额。
- 现象为问答响应缓慢且token消耗过高，原因是未限定上下文召回范围，将过期的历史项目文档全部纳入上下文，导致无效token占用过多。

## 怎么确认配好了
- 查看上下文预览界面，确认仅召回近1个里程碑周期内的项目文档，无过期的历史任务数据。
- 测试单次评审请求的token消耗，确认未超出当前使用模型的最大上下文配额。
- 导入一份完整的项目计划文档，检查分块后的内容是否保留了任务节点、责任人等核心字段，无关键信息丢失。
- 模拟跨方排期协调的评审场景，确认输出内容未出现异常截断情况。
