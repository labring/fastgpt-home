# 项目文档移交归档的代码与变更评审辅助：上下文与 token

## 这个品类的数据长什么样
该品类的核心数据来自项目文档库、配置清单、会议纪要、测试报告，通常由项目经理、实施顾问或客户档案管理员维护。日常产出的文档包括竣工文档、配置手册、培训记录、验收证书，文档结构涵盖结构化清单与非结构化文本两类。数据更新节奏为项目阶段节点或整体项目结束后，无高频实时更新需求，单份文档的内容跨度从单页说明到数十页交付材料不等。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的文档以阶段交付成果为主，内容关联性集中在同一项目的多阶段材料中，需优先召回同项目同版本的内容。由于文档更新频率低，知识库无需频繁刷新，但单批次评审需覆盖完整的项目交付证据链，对上下文的召回范围与token消耗有明确限制。同时，文档包含结构化配置清单与非结构化验收记录，需准确匹配不同类型内容的上下文权重，避免无关文档占用过多token额度。此外，评审过程需核对版本一致性，上下文召回需优先展示最新阶段的文档内容。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | `8000–12000 token` | 项目文档移交归档的单批次评审总token量通常处于该区间，可覆盖完整的项目交付证据链，避免超出模型上下文上限 |
| `quoteMaxToken` | `2000–3000 token` | 单份核心文档如竣工文档、验收证书的核心内容token量集中在该区间，确保关键评审依据被完整引用 |
| 单次召回上限 | 前8条 | 该品类的关联文档通常集中在少量核心交付材料中，过多召回会增加无效token消耗 |
| 上下文排序规则 | 按文档版本优先级 | 该品类需核对交付文档的版本一致性，优先召回最新阶段的内容以匹配评审需求 |
| 上下文过滤阈值 | 按实测标定 | 不同项目的文档关联度差异较大，需结合实际评审场景调整过滤标准 |

## 容易做错的三处
- 现象：上下文引用区域展示的内容未正确渲染Markdown格式，仅保留原始的#、*等标记符号。原因：未开启FastGPT内置的文档解析渲染开关，或配置的召回内容未保留原始格式标记。
- 现象：界面展示的上下文条数与实际发送到模型的token计数不一致，例如界面显示30条但日志中实际携带310条token。原因：上下文统计逻辑混淆了条目数与token计数，未按实际token消耗计算展示上限。
- 现象：知识库token计算结果与手动估算存在明显偏差，无法匹配实际调用时的token消耗。原因：未使用FastGPT v4.17.0内置的token计算规则，或未考虑文档分块后的重叠token损耗。

## 怎么确认配好了
- 上传单份典型竣工文档，触发代码与变更评审辅助流程，检查上下文引用区域的Markdown格式是否正确渲染。
- 查看模型调用日志，对比界面展示的上下文统计数据与日志中实际携带的token数量，确认统计逻辑一致。
- 调整配置项的取值，触发多次评审流程，验证上下文召回的文档是否按版本优先级排序。
- 手动估算核心文档的token总量，对比FastGPT内置的token计算结果，确认匹配度符合预期。
