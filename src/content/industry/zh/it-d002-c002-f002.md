# IT服务台工单处理的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
这个品类的数据来自企业ITSM系统、员工电话或聊天记录、资产台账系统及内部IT知识库。数据更新节奏为日级或实时，新提交的工单、处理进度更新会即时同步，月度归档的历史工单按自然日批量更新。单条数据包含工单编号、提交人信息、问题描述、分类标签、处理记录、用户满意度评分等字段，单份工单文档的长度从数百字符到数千字符不等。

## 这些特征在「上下文与 token」这一环带来什么约束
多源异构的数据结构要求上下文提取时需精准匹配工单相关字段，过滤冗余的资产台账字段或非关联聊天内容，避免无效token占用配额。实时更新的工单数据会持续新增token，需要限制上下文的刷新周期，防止高频更新导致token消耗超出预算。单份工单长度差异较大，过长的处理记录会快速消耗上下文token额度，需限定单条上下文的token上限。运营报告汇总需跨多工单聚合信息，需按工单维度拆分上下文，避免跨工单的无关内容混合导致token冗余。

## 配置怎么定
FastGPT v4.17.0 版本下的配置项如下：
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 适配IT工单数据的平均长度与主流大模型上下文窗口上限，避免单次调用超出模型限制 |
| `quoteMaxToken` | 1500–2000 字符 | 限定单条引用的工单内容长度，防止单条处理记录占用过多上下文token配额 |
| 上下文刷新频率 | 每小时一次 | 平衡数据时效性与token消耗，适配日级更新的历史工单汇总需求 |
| 上下文筛选阈值 | 0.75 相似度 | 基于工单问题描述的语义匹配度筛选相关上下文，过滤冗余的非关联工单数据 |

## 容易做错的三处
- 配置`maxContext`调大后，运营报告或工单回复中未体现预期的上下文内容。原因是未筛选与当前工单匹配的上下文，混入了无关的知识库内容或历史非关联工单的token。
- 运营报告的token消耗统计与估算值存在偏差。原因是未按工单维度聚合上下文，错误包含了非关联的字段或冗余的历史工单数据。
- 输入长工单上下文后出现token超限报错。原因是未设置`quoteMaxToken`限制单条引用长度，过长的工单处理记录超出模型token上限。

## 怎么确认配好了
- 查看上下文预览界面，确认仅包含当前工单及关联的处理记录，无无关的知识库内容或非关联工单数据。
- 模拟提交新工单，查看token消耗统计面板，确认单次上下文调用的token数未超出`maxContext`的预设额度。
- 调整`quoteMaxToken`参数至较小值，测试长工单的回复或报告生成，确认无token超限报错。
- 查看运营报告的生成日志，确认上下文筛选规则已生效，仅匹配对应分类的工单数据。
