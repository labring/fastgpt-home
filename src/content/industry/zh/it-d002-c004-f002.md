# IT采购与供应商管理的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自企业内部采购系统、供应商报价文档、预算表及合同系统，日常处理的文档包括采购申请单、比价记录、正式合同、验收单据。数据按每单采购流程更新，单次采购关联的文档包含采购单号、供应商资质、报价明细、合同条款、验收标准等字段，无统一固定的字段单位，随单据类型差异调整。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据分散在多个独立系统，单次采购流程需整合采购申请、比价记录、合同、验收单等多类文档，上下文需覆盖完整采购周期的关联内容，导致token消耗随单据数量增长。数据更新频率为每单/月，无需高频增量刷新，但单次上下文需完整覆盖单采购全流程信息，需限制上下文总token量避免溢出。不同文档的token占比差异明显，合同条款类文档token占比更高，需区分优先级分配token资源，同时避免因上下文过长导致调用超时或结果截断。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的界面参数。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文 | 覆盖30天内的单采购全流程文档 | 该品类数据按每单/月更新，需完整覆盖单采购周期的所有关联单据，避免遗漏关键信息 |
| `maxContext` | 12000–15000 token | 适配多类采购文档的总token消耗，避免单次调用超出模型上限 |
| `quoteMaxToken` | 单文档不超过3000 token | 合同条款类文档token占比高，限制单文档token避免上下文溢出 |
| 单文档分块长度 | 800–1200 字符 | 平衡文档拆分后的语义完整性与token使用效率 |
| 上下文召回上限 | 前8条关联单据 | 聚焦当前采购单的核心文档，避免无关数据占用token资源 |
| 上下文优先级 | 优先匹配合同、预算字段 | 该品类出错后果多与预算超支、合同风险相关，优先保障核心字段的召回 |

## 容易做错的三处
- 调用时返回ACCESS_TOKEN无效报错。原因：误将供应商接口密钥填入采购系统的上下文配置项，未使用FastGPT平台对应的API密钥。
- 多模型编排后总token超出限制，或单模型上下文丢失。原因：未配置`maxContext`限制总token，错误认为多模型token自动独立分配，未为每个模型单独设置上下文上限。
- 调用多次后仍返回Reached the max retries报错。原因：未根据采购文档的token消耗调整`maxContext`参数，上下文过长导致模型调用超时重试失败。

## 怎么确认配好了
- 上传单份采购合同文档，查看上下文召回的文档数量是否匹配当前采购单的关联单据，调整召回上限至合理范围。
- 模拟多模型编排流程，查看每个模型的上下文token消耗是否符合预设的`quoteMaxToken`限制。
- 检查配置项中是否绑定了当前采购单的流程ID过滤规则，确保召回的文档仅关联当前业务。
- 触发一次完整的发布说明汇总任务，查看返回结果是否包含所有核心单据的关键条款，无遗漏或截断。
