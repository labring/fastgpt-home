# Pull Request评审的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
该品类的数据来自代码仓库、CI流水线、Issue链接与贡献者提交记录。日常产出的文档包含PR说明、代码评审意见、CI执行结果、合并操作记录。数据更新节奏通常为日或周，单条数据包含PR编号、变更文件清单、评审意见条目、CI通过率、合并状态等字段。处理主体为项目维护者、模块Owner与贡献者，核心围绕可合并代码变更的评审与汇总展开，与Issue分拣类工作不同，该品类仅处理可合并的代码变更相关数据。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据来源分散，包含代码文本、CI日志、评审意见等不同格式内容，不同格式的token占用比例差异显著，需合理分配上下文token配额。单条PR数据包含多份变更内容与评审记录，上下文窗口需覆盖足够关联信息以准确汇总发布说明与运营报告。数据更新节奏为日或周，无需高频召回但需保证召回内容匹配最新合并与评审状态。变更意图确认、测试结果检查等核心环节依赖完整上下文，token配额不足会导致关键信息丢失，引发回归缺陷或主干不稳定，影响贡献者体验。

## 配置怎么定
以下配置适用于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | `8000–12000 token` | 该品类的PR数据包含多份变更与评审内容，该区间可覆盖典型PR的关联上下文 |
| `quoteMaxToken` | `1000–1500 字符` | 评审意见与CI日志的单段有效内容通常在此区间，避免占用过多上下文配额 |
| 上下文刷新周期 | 每日1次 | 数据更新频率为日或周，每日刷新可保证上下文匹配最新的合并与评审记录 |
| 召回关联内容数量 | 前6条 | 核心评审与变更内容通常集中在最近提交的6条记录内，可平衡召回效率与信息完整性 |
| 增量召回阈值 | 按实测标定 | 不同仓库的代码变更密度不同，需结合实际场景调整召回触发条件 |

## 容易做错的三处
-  配置`quoteMaxToken`后，返回的引用内容超出设定长度。原因是未明确参数的生效范围，部分场景下参数未绑定到对应引用类型的内容。
-  提交中文内容时触发报错，英文输入正常。原因是上下文配额未适配中文编码的token计算规则，导致token统计偏差触发限制。
-  生成的发布说明遗漏关键变更内容。原因是`maxContext`设置过小，未覆盖全部关联的PR变更与评审记录。

## 怎么确认配好了
-  导入一条典型PR数据，查看上下文召回的内容条数与长度，确认符合配置的取值范围。
-  提交包含中文与英文的测试内容，检查是否触发报错，验证token计算规则适配当前场景。
-  查看配置生效后的汇总结果，确认关键变更与评审记录均被纳入上下文。
-  等待一个更新周期后，检查上下文是否自动刷新为最新的PR数据与评审记录。
