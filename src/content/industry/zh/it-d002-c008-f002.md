# 专题活动运营的发布说明与运营报告汇总：上下文与 token

本文基于FastGPT v4.17.0版本的功能配置进行说明。

## 这个品类的数据长什么样
该品类的日常文档包含活动方案、资源位排期表、活动页面文案、活动复盘报告，数据来源于内部内容库、活动后台流量数据、用户反馈与活动执行记录。数据更新通常按周或节假日节点触发，文档字段包含活动周期、资源位编码、流量指标、用户反馈标签等，无固定强制单位，随文档类型与运营需求调整。

## 这些特征在「上下文与 token」这一环带来什么约束
活动类文档存在明确的活动周期与资源位绑定规则，上下文调用需限定在对应活动周期内，避免跨活动数据干扰核心逻辑。资源位排期表结构固定且字段较多，需严格控制上下文token总量，防止超出模型承载上限导致调用失败。数据更新随活动节点波动，上下文需支持动态加载最新的流量与用户反馈数据，同时需避免无关文档占用token配额，影响核心信息的调用效率。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文条数 | 前8-12条 | 匹配活动周期内的核心历史文档数量，避免冗余内容占用token配额 |
| 上下文引用最大token数 | 9000-11000 token | 适配主流大模型的上下文承载上限，符合活动类文档的总字符量 |
| 上下文关联范围 | 活动周期内的关联文档 | 限定数据来源，排除跨活动的无关内容 |
| 内容筛选规则 | 按活动标签匹配 | 仅调用同活动的方案、排期与复盘文档 |
| 上下文刷新时机 | 活动节点或每周更新 | 匹配数据更新频率，保证内容时效性 |

## 容易做错的三处
- 页面展示的上下文条数与实际传入API的条数不一致，原因是配置的上下文筛选规则未正确绑定活动专属标签，导致非活动相关的冗余文档被计入统计。
- 上下文引用中的文档无法正常渲染为Markdown格式，原因是文档切分环节未保留原格式标记，或上下文调用时未开启格式还原配置。
- 上下文token总量超出模型限制导致调用失败，原因是未设置`quoteMaxToken`的合理上限，导致大量活动方案与复盘文档占用过多token配额。

## 怎么确认配好了
- 查看上下文调用日志，确认仅包含活动周期内的关联文档，无跨活动的无关内容。
- 测试调用接口，核对传入的token总量与配置的上下文引用最大token数上限是否匹配。
- 检查上下文渲染结果，确认文档格式可正常还原为Markdown样式。
- 验证上下文刷新时机，确认数据更新后可及时加载最新的活动复盘与流量数据。
