# 代码安全审计的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
代码安全审计的典型使用主体为安全研发团队、安全服务商与企业研发团队，日常产出的文档包含代码审计报告、漏洞证明、修复建议、复测记录四类。数据来源涵盖源代码仓库、依赖清单、静态代码扫描（SAST）工具输出日志与公开漏洞库，更新频率为每个项目版本或单次审计任务完成后更新一次。数据字段包含危险函数定位结果、数据流追踪路径、修复方案细节与复测验证结果，无固定统一的单位格式，部分字段为纯代码片段，部分为结构化技术条目。

## 这些特征在「上下文与 token」这一环带来什么约束
代码安全审计的文档类型跨度较大，从短篇幅的漏洞证明到长篇的数据流追踪报告均有覆盖，且按项目版本更新意味着单次对话需要关联多份关联文档，容易超出模型token上限。源代码仓库的代码片段长度差异显著，长文件可能包含数千行代码，直接作为上下文会快速耗尽token配额。同时人工审查环节需要完整的业务逻辑与攻击路径上下文，不能随意截断关键信息，导致token消耗的精准管控难度提升，需要平衡上下文完整性与token使用效率。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文token | 8000–12000 token | 适配单项目审计的全量关联数据长度，避免单次对话超出模型token上限 |
| `quoteMaxToken` | 1500–2000 字符 | 匹配漏洞证明、修复建议这类单条文档的典型长度，防止单条引用占比过高 |
| 分块重叠长度 | 100–200 字符 | 保留代码片段、数据流路径的上下文关联，避免分块截断关键逻辑 |
| 单次召回上限 | 前6条 | 控制总token消耗，适配研发团队日常审计的单批次数据量 |
| `maxContext` | 按项目规模标定 | 小体量项目可设为6000 token，大体量项目可调整至15000 token |
| 单条引用最大token | 按文档类型调整 | 代码片段类文档设为1800 token，漏洞报告类设为1200 token |

## 容易做错的三处
- 现象：RAG分类匹配时数据块过大，界面显示上下文溢出报错，后台日志显示token消耗超出预设上限。原因：未针对代码审计报告的长文本调整分块长度，默认参数未适配结构化技术文档的字段密度，导致单块数据超出token限制。
- 现象：私有化部署后无法查看每次对话的token消耗明细，系统监控面板无对应统计字段。原因：未开启上下文token统计的配置开关，未正确关联日志采集链路到监控系统。
- 现象：对话返回Reached the max retries per request limit错误，响应超时无结果。原因：未限制单次召回的条目数，未通过`quoteMaxToken`控制单条引用的token上限，导致请求负载过高触发重试限制。

## 怎么确认配好了
1.  在FastGPT v4.17.0版本中，上传单份典型代码审计报告，测试分块后的总token数，确认未超过设置的最大上下文token值。
2.  发起一次漏洞复核对话，查看返回的上下文引用条数，确认符合单次召回上限的设置。
3.  检查系统运行日志，确认每次对话都包含token消耗的统计字段，无上下文溢出或重试超限的报错信息。
4.  调整`quoteMaxToken`参数后，上传长代码片段，验证分块后的单条数据长度符合预期设置。
