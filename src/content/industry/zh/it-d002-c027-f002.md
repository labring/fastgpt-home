# 内容审核规则运营的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
本说明基于FastGPT v4.17.0版本的上下文与token配置逻辑。本品类的数据来源为内容审核后台、用户举报渠道、行业法规政策文件、审核样本库。日常维护的文档包含审核规则条目、处置操作指南、申诉复核记录、月度质检报告。数据更新节奏为每日同步后台运营数据，随行业法规政策调整实时更新。数据字段包含规则编码、生效时效、匹配样本类型、处置等级等，单位多为字符、条目、时间区间。

## 这些特征在「上下文与 token」这一环带来什么约束
审核规则、申诉记录等文档格式、长度差异显著，上下文拼接时需按业务优先级筛选内容，避免无效token占用。每日或实时的更新节奏要求上下文窗口支持动态拉取最新规则条目，需限制单次传入的token总量以适配接口限制。多来源的字段特征要求token统计需关联对应业务字段的长度，避免因字段冗余导致token溢出。疑难样本判定环节需精准召回相关规则与样本，需控制召回上下文的数量与token占比，保障判定效率。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配审核规则、申诉记录的混合文本长度，避免超出接口的token配额限制 |
| `quoteMaxToken` | 2000–3000 token | 保障核心审核规则与匹配样本的完整传入，满足规则解释与样本判定的参考需求 |
| 上下文召回条数 | 前8–12条匹配样本 | 覆盖常见审核场景的规则参考范围，避免过多无效内容占用token资源 |
| 上下文更新周期 | 每日凌晨同步 | 匹配数据日更节奏，保障上下文始终使用最新的审核规则与处置指南 |
| token统计维度 | 按输入输出分别统计 | 对应审核场景下的规则调用与结果返回的token消耗，便于运营额度核算 |

## 容易做错的三处
- 现象：系统无法分别显示AI对话的输入token数量与输出token数量，仅展示合并统计值。原因：未配置按输入输出拆分的token统计维度，导致无法精准核算审核会话的token消耗。
- 现象：工作流中显示的上下文数量与实际传入的审核会话历史数量不符，设置`maxContext`为0时无历史数据传入。原因：错误将`maxContext`配置为0，截断了所有历史审核会话的上下文数据。
- 现象：上下文引用的审核规则文档未保留原markdown格式，仅显示纯文本内容。原因：未配置`quoteMaxToken`的合理取值，长文本被截断后丢失了格式标记。

## 怎么确认配好了
- 查看系统日志，确认输入与输出token的统计数据分别展示，无合并统计的情况。
- 测试设置`maxContext`为指定数值，检查传入的上下文数量与配置的召回条数一致。
- 提交一条包含长审核规则的测试请求，确认未触发token超限报错，且规则内容完整传入。
- 查看上下文引用模块，确认审核规则文档的格式标记被正确保留，无丢失情况。
