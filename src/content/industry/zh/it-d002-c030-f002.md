# 内部网络与WiFi运维的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自交换机控制台、无线控制器、办公区监控系统及用户报障渠道。日常产出的文档包括网络拓扑图、变更单、故障记录、无线覆盖巡检表。数据更新节奏为每日同步或每完成一次网络变更后更新。文档字段包含变更时间、端口编号、VLAN标识、设备MAC地址、覆盖区域等，端口编号为正整数，VLAN标识范围为1至4094，时间字段以自然日或小时为单位。

## 这些特征在「上下文与 token」这一环带来什么约束
多源异构的数据来源会导致不同格式的日志、巡检记录在上下文整合时产生格式差异，需要额外的格式对齐处理，增加token消耗。数据更新节奏分为每日同步与变更触发两种，要求上下文支持动态刷新，避免加载陈旧的网络配置数据。多样的文档结构需要适配不同长度的内容，拓扑图关联的文本说明与故障记录的短文本需差异化分配token额度。特定的字段规则要求上下文召回时限定匹配运维相关字段，防止无关token占用总限额。

## 配置怎么定
本章节配置对应FastGPT v4.17.0版本的`maxContext`与`quoteMaxToken`等核心参数，具体设置如下：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文窗口 | 前12000 token | 适配多源运维文档的总长度，符合FastGPT v4.17.0版本的模型适配范围 |
| 最大引用token数 | 3000–5000 token | 匹配单份运维文档（如变更单、巡检表）的典型长度，避免单条引用超出限额 |
| 上下文刷新周期 | 每日0点或变更触发后10分钟 | 适配数据更新的两种节奏，兼顾时效性与资源消耗 |
| 召回结果上限 | 前8条 | 限定上下文的召回范围，减少无效token占用 |
| 分块重叠长度 | 200–300字符 | 适配运维文档中字段关联的连贯性，避免内容截断丢失关键信息 |

## 容易做错的三处
- 现象：工具调用节点返回Invalid JSON: Bad control character报错，原因：上下文整合了交换机控制台导出的原始日志，其中包含不可见控制字符，超出JSON解析允许的token范围。
- 现象：多轮会话后返回的运维报告缺失最近的变更记录，原因：上下文刷新周期设置过长，未及时同步新的变更单数据。
- 现象：召回的无线覆盖巡检表内容碎片化，关键覆盖区域字段丢失，原因：分块重叠长度设置不足，导致跨分块的关联字段被截断。

## 怎么确认配好了
- 导入一份典型的运维文档（如变更单、故障记录），查看上下文召回的字段是否包含变更时间、端口编号等关键信息。
- 发起多轮连续的运维查询，检查会话过程中未出现上下文溢出报错，且内容未被无故截断。
- 调用工具节点测试，确认返回的JSON格式无控制字符异常，符合解析要求。
- 手动触发一次模拟网络变更，检查上下文是否在10分钟内自动刷新为最新的变更数据。
