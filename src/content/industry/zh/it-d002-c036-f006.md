# 原型与交互设计的发布说明与运营报告汇总：定时任务与自动化

## 这个品类的数据长什么样
该品类的数据通常来自Figma或Axure文件、团队内部设计系统、用户反馈与可用性测试记录。日常产出的文档包含交互原型、页面流程图、组件说明与评审记录，更新以周度或每版本发布为节奏。数据字段通常包含原型版本号、页面操作路径、交互节点规则、评审修改意见，无统一强制格式，随团队设计规范调整。

## 这些特征在「定时任务与自动化」这一环带来什么约束
该品类的数据更新以周度或版本发布为节奏，定时任务需匹配该节奏，避免高频触发占用设计团队的日常工作资源。不同来源的设计文件格式差异较大，自动化流程需适配Figma、Axure等多种解析规则，确保不同工具产出的文件均可被正常处理。数据字段无统一格式，需在任务中配置灵活的字段映射规则，适配不同团队的设计规范。异常场景补齐与评审修改环节耗时较长，自动化需预留重试空间，避免因单次任务失败中断整体的发布说明与运营报告汇总流程。

## 配置怎么定
本配置说明适用于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 任务触发时机 | 每周五18:00 | 匹配该品类周度或版本发布的更新节奏，避免干扰日常设计工作 |
| 文件解析范围 | 仅同步近7天更新的Figma/Axure文件 | 减少无效解析量，适配周度更新的频率 |
| 失败重试次数 | 3次 | 覆盖临时网络波动或文件解析异常的场景，避免单次失败直接终止任务 |
| 任务超时阈值 | 3600秒 | 适配多文件批量解析的耗时需求，避免长任务被强制中断 |
| 异常通知触发条件 | 任务失败或任意单文件解析失败 | 及时提醒设计团队处理异常场景，避免影响后续研发对齐 |
| 日志留存周期 | 30天 | 匹配评审记录的归档周期，便于后续回溯问题 |

## 容易做错的三处
- 现象：定时任务执行后解析的原型文件缺失，原因：未配置正确的团队共享设计文件路径，仅同步了本地临时目录的文件，无法覆盖全量设计资源。
- 现象：无法在搜索库中添加自定义文本理解模型，原因：未完成全局模型的环境变量配置，导致任务环节无法调用非默认的模型服务。
- 现象：任务执行后生成的汇总报告自动被提前清理，原因：未调整日志留存周期的配置，默认留存时长过短导致符合预期的日志被删除。

## 怎么确认配好了
- 手动触发一次定时任务，检查任务管理页面中是否显示执行成功的记录，且解析的文件数量与团队当前的设计资源数量匹配。
- 模拟一次单文件解析异常，检查是否收到对应异常通知，确认通知渠道配置生效。
- 查看全局模型配置页面，确认已添加的自定义模型在搜索库的模型选择列表中可见。
- 检查任务日志存储目录，确认近30天内的任务日志均正常留存，未被提前清理。
