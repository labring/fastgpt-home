# 安全漏洞披露处理的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
该品类的数据来自私密漏洞报告、代码仓库、CVE编号机构及官方发布渠道，核心文档包含安全公告、漏洞报告、修复补丁与CVE申请材料。每份文档包含CVE编号、披露时间、影响范围、补丁链接等固定字段，更新节奏以单次漏洞事件为单位，无固定周期。数据关联项目自身漏洞的全生命周期流程，从漏洞上报到公开披露的全环节信息均需纳入汇总范围。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据按单次漏洞事件更新，单事件关联的文档数量与字段复杂度较高，需严格限制上下文承载的内容总量，避免token超额溢出。由于包含私密漏洞报告与公开发布信息两类数据，上下文需区分权限范围，仅将已授权的内容纳入调用上下文。同时，漏洞披露的时效性要求高，上下文召回需精准匹配当前事件的关联文档，避免引入无关历史数据占用token，防止因上下文冗余导致披露流程延迟或信息泄露。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 12000–15000 token | 适配单漏洞事件关联的安全公告、补丁报告等文档总长度，避免token溢出 |
| `quoteMaxToken` | 2000–3000 token | 匹配单份漏洞报告或补丁说明的常规篇幅，确保单条引用内容完整且不占用过多上下文 |
| 上下文召回上限 | 前8条 | 覆盖当前漏洞事件的核心关联文档，避免引入无关历史数据 |
| 权限过滤开关 | 开启 | 过滤未公开的私密漏洞报告，仅将授权内容纳入上下文 |
| 事件上下文绑定 | 绑定当前漏洞ID | 确保召回的文档仅关联当前处理的漏洞事件，避免跨事件干扰 |

## 容易做错的三处
- 调用工作流API时返回的结果未包含当前漏洞事件的上下文信息。原因是未在API请求中绑定对应漏洞事件的上下文标识，或工作流内的上下文配置未关联该事件的专属文档源。
- 积分消耗远超日常用量。原因是未设置`maxContext`的合理取值，导致每次调用加载过多无关历史漏洞文档，占用超额token配额。
- 部署BGE重排模型后，上下文召回的关联文档条数不符合预期。原因是未在docker-compose.yml的environment字段中配置正确的关联参数，导致模型无法正确匹配漏洞报告与补丁的上下文关联。

## 怎么确认配好了
- 使用FastGPT v4.17.0版本发起一次测试调用，检查返回结果中是否包含当前漏洞事件的关联安全公告、补丁链接等核心信息。
- 查看API调用日志，确认`maxContext`与`quoteMaxToken`的实际取值符合配置要求，无超额token消耗。
- 验证权限过滤功能，尝试调用未公开的私密漏洞报告相关接口，确认返回结果中无未授权的私密内容。
- 检查BGE重排模型的运行日志，确认上下文召回的关联文档条数符合预设的召回上限。
