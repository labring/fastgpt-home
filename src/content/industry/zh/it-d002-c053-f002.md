# 客户需求池管理的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自工单系统、客户访谈记录、CRM客户管理系统、产品路线图文档。日常产出的文档包含需求池清单、需求评估表、客户反馈记录、版本规划说明。数据更新频率以周度或每产品版本为周期，每条数据包含需求编号、关联客户标识、优先级标签、提出时间、评估状态等基础字段，无统一强制单位，随单条需求的业务属性调整。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据来源分散且格式各异，不同系统导出的需求记录存在字段错位、格式不统一的问题，在拼接上下文时需额外做格式对齐，会占用额外token配额。数据更新频率较高，单次汇总的上下文范围需匹配周度或版本周期，过长的上下文会超出token限制，导致关键需求信息被截断。同时需求池内存在大量重复提交的同类反馈，冗余内容会进一步挤占有效token空间，需提前开展去重处理以优化上下文利用率。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `maxContext` | 1000–1500 token | 匹配周度需求池汇总的有效信息总量，避免超出FastGPT v4.17.0版本的模型上下文上限 |
| `quoteMaxToken` | 200–300 token/条 | 适配单条需求记录的典型长度，防止单条引用占用过多token配额 |
| 上下文去重开关 | 开启 | 过滤重复提交的同类需求，减少冗余内容对token的占用 |
| 上下文范围 | 近7天或当前版本周期 | 匹配该品类数据的更新频率，确保汇总信息的时效性 |
| 单条上下文提取上限 | 前20条有效记录 | 控制单次加载的需求数量，避免token溢出影响汇总结果 |

## 容易做错的三处
- 现象：启动后返回`AIPROXY_API_ENDPOINT`未配置或`AIPROXY_API_TOKEN`无效的报错，接口调用失败。原因：未配置`AIPROXY_API_ENDPOINT`（AI Proxy服务根地址，不得使用VLLM/Ollama/Xinference等单模型地址）或`AIPROXY_API_TOKEN`（AI Proxy管理员Token，不得使用应用API Key、模型供应商密钥等其他令牌，与服务端配置一致且非空），或`AIPROXY_API_ENDPOINT`格式错误、`AIPROXY_API_TOKEN`与AI Proxy服务端配置不一致或为空。
- 现象：上下文拼接后出现字段错位、格式混乱的需求记录。原因：未对多来源的需求文档做格式对齐，导致无效内容占用token配额。
- 现象：汇总报告中出现大量重复的同类需求条目。原因：未开启上下文去重配置，冗余需求占用过多token，导致关键信息被截断。

## 怎么确认配好了
- 检查App/Admin服务端的环境变量配置，确认`AIPROXY_API_ENDPOINT`（AI Proxy服务根地址，不得使用VLLM/Ollama/Xinference等单模型地址）和`AIPROXY_API_TOKEN`（AI Proxy管理员Token，不得使用应用API Key、模型供应商密钥等其他令牌）的取值与实际部署的代理服务一致。
- 生成单次周度需求汇总，查看上下文预览面板，确认有效需求记录占比符合预期。
- 触发一次需求池更新同步，检查是否出现重复键错误相关的日志提示。
- 调整`maxContext`参数后，验证上下文是否未出现截断丢失关键需求信息的情况。
