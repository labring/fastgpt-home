# 容器平台运维的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自Kubernetes API、镜像仓库、监控系统与CI流水线，更新节奏为每日或每次集群变更后生成。日常文档包含集群变更单、命名空间配额表、部署记录与故障报告，字段覆盖集群标识、变更时间、Pod运行状态、镜像版本、资源配额阈值等，格式随集群规模与运维规范调整，无统一强制要求。

## 这些特征在「上下文与 token」这一环带来什么约束
集群变更单、部署记录等文档的更新频率不均，单次变更产生的内容长度差异较大，会导致上下文窗口的负载波动。多来源数据的字段格式不统一，需要在上下文拼接时做格式对齐，否则会干扰token计数。每日批量生成的监控与CI数据会占用大量token配额，若未限制上下文条数，容易触发token超标报错。同时容器平台运维的上下文需关联集群标识与变更时间，避免跨集群上下文污染。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 前10-15条 | 匹配容器平台运维单次变更关联的部署记录、变更单数量，避免上下文过载 |
| `quoteMaxToken` | 8000-12000 token | 适配集群变更单、Pod日志的平均内容长度，防止触发token超标报错 |
| 上下文拼接触发时机 | 每变更后/每日0点 | 匹配该品类数据的更新频率，确保上下文包含最新运维数据 |
| 上下文格式校验 | 开启 | 对齐多来源数据的字段格式，减少token计数偏差 |
| 上下文过滤规则 | 仅保留近7天数据 | 避免历史冗余数据占用token配额，符合运维数据的有效周期 |

## 容易做错的三处
- 现象：对话明细中仅显示2条上下文，但配置了30条上下文。原因：未正确关联容器平台运维的集群标识字段，导致上下文过滤逻辑误截断有效内容。
- 现象：大模型返回格式混乱的Json内容。原因：未开启上下文格式校验，镜像仓库、CI流水线的原始数据格式未对齐，干扰大模型输出逻辑。
- 现象：集群升级时出现Error response from daemon: error from registr报错。原因：上下文拼接时未过滤过期的集群注册数据，导致token超标引发调用异常。

## 怎么确认配好了
- 查看FastGPT v4.17.0的上下文配置页面，确认`maxContext`的取值与运维变更单的平均关联条数匹配。
- 导入单条完整的集群变更单，测试`quoteMaxToken`的取值是否覆盖该文档的全部内容，无截断情况。
- 模拟一次集群变更操作，查看生成的上下文列表，确认仅包含近7天的运维数据，无跨集群冗余内容。
- 触发一次大模型调用，检查返回结果未出现上下文截断或格式混乱问题。
