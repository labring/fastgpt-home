# 广告合规留痕的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
本品类数据主要来自广告平台后台、客户资质文件、合同系统及监管公开规则。日常处理的文档包括广告审查表、资质附件、投放记录、整改通知。数据更新节奏按单次广告活动或月度周期推进，由广告合规、代理商法务、品牌市场相关岗位负责归集。数据字段包含投放时段、资质编号、审查结果、整改要求等，无统一固定格式，随单次活动的具体场景调整。

## 这些特征在「上下文与 token」这一环带来什么约束
数据来源分散导致单次需调用的多源文档数量不定，需合理限定上下文加载范围以避免token超额消耗。更新周期按活动或月度推进，单次上下文关联的文档数量随活动规模变化，需适配波动的token消耗节奏。文档无统一格式，非结构化内容较多，需避免冗余文本占用过多token。投放记录、整改通知等时效性较强的文档，需优先加载最新内容，防止token被过期数据占用。同时合规场景需留存完整证据链，不能随意删减有效上下文，需在token使用与证据完整性之间找到平衡。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本，具体如下：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配单次广告活动关联的多份合规文档总token消耗，平衡证据留存与平台token限额 |
| `quoteMaxToken` | 1500–2000 token | 匹配广告审查表、投放记录等单文档的常规长度，避免单文档占用过多上下文空间 |
| 上下文召回条数 | 前6条 | 覆盖单次活动的核心合规证据，避免过多冗余数据占用token |
| 单文档分块长度 | 1000–12000 字符 | 适配合规文档的常规段落结构，减少上下文拼接的token损耗 |
| token溢出处理规则 | 按实测标定 | 针对合规场景的证据留存要求，优先保留最新投放记录、审查结果与整改通知，截断非核心历史数据 |

## 容易做错的三处
- 现象：部署bge-reranker后，上下文关联的合规文档无法正确加载。原因：未在docker-compose.yml的environment下添加正确的配置参数，导致模型与上下文token配置不匹配，对应社区中docker部署相关的问题场景。
- 现象：上下文召回条数与配置不符，返回结果条数偏差较大。原因：未结合广告合规场景的证据覆盖需求调整召回阈值，误将通用场景的召回条数直接套用。
- 现象：切换团队后，token配置未同步更新。原因：未将token配置与团队数据绑定存储，导致不同团队的合规场景配置无法独立生效，对应社区中团队数据存储相关的问题场景。

## 怎么确认配好了
- 查看FastGPT平台的上下文加载日志，确认召回的文档与当前广告活动的审查表、投放记录匹配，核对召回条数是否符合配置要求。
- 发起一次合规场景的查询，检查token消耗数值是否在`maxContext`的设定范围内，无异常溢出提示。
- 切换不同团队账号，确认token配置随团队数据同步更新，无跨团队配置混淆情况。
- 上传单份合规文档，检查分块后的token长度是否符合`quoteMaxToken`的设定区间。
