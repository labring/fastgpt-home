# 投放计划搭建的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
该品类的日常文档通常包含投放计划、定向设置、预算排期、转化追踪配置四类核心文件。数据一般来自广告平台API、用户画像数据集、线下预算表、归因工具接口。更新节奏以每日或单次活动周期为准。字段多包含定向人群标签、预算额度、转化事件ID等，无统一强制单位，需匹配对应数据源的格式要求。核心操作环节集中在人群定向配置、预算分配与转化事件校验，操作失误可能导致预算浪费、转化数据缺失或投放无法启动。

## 这些特征在「上下文与 token」这一环带来什么约束
投放计划搭建的多源异构数据来源，要求上下文模块需兼容广告平台、预算表、归因工具等不同格式的输入，token分配需适配非标准化字段的长度差异。日常文档的更新节奏不固定，上下文缓存的刷新机制需支持按需触发，不使用固定周期。核心操作环节的字段校验依赖完整上下文，token上限需覆盖单份完整投放计划的内容长度，避免截断关键配置信息。同时，操作失误会直接导致投放失败，上下文召回的精准度需严格匹配定向标签、转化事件ID等业务字段，减少无效token消耗。

## 配置怎么定
FastGPT v4.17.0 版本下的配置项如下：
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配单份完整投放计划的文档总长度，覆盖定向设置、预算排期、转化追踪配置等核心内容 |
| `quoteMaxToken` | 单条召回内容不超过1500 token，总召回token不超过4000 token | 匹配投放校验环节所需的关联数据量，避免token过度占用导致上下文溢出 |
| 上下文刷新触发规则 | 按文档更新时间戳触发 | 适配该品类文档更新频率不固定的特征，避免无效缓存消耗 |
| 多源数据优先级 | 广告平台数据优先于预算表数据 | 符合投放计划搭建的业务校验逻辑，优先保障实时投放数据的准确性 |
| 临时输入token上限 | 不超过`maxContext`的20% | 预留足够空间处理临时追加的配置调整内容，避免覆盖核心上下文 |

## 容易做错的三处
- 现象：上下文召回结果中缺少定向设置的核心标签字段，导致投放计划校验失败。原因：未配置`quoteMaxToken`的单条内容长度限制，导致长字段被截断。
- 现象：多源数据合并后token总量超过`maxContext`，系统返回上下文溢出报错。原因：未设置多源数据的优先级排序规则，将非核心数据优先纳入上下文。
- 现象：团队切换后tokenLogin接口返回的团队数据未同步到上下文缓存，导致配置权限校验失败。原因：上下文刷新规则未绑定团队权限变更事件，未及时更新缓存内容。

## 怎么确认配好了
- 上传一份完整的投放计划文档，核对上下文模块显示的总token数是否在`maxContext`的配置范围内。
- 触发一次投放计划的校验流程，查看召回的关联数据是否包含广告平台、归因工具的核心字段。
- 修改一份投放计划的更新时间戳，验证上下文缓存是否在指定时间内完成刷新。
- 调整`quoteMaxToken`的配置值，测试长字段内容是否被完整召回未被截断。
