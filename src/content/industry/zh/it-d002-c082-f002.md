# 渠道归因与线索分发的发布说明与运营报告汇总：上下文与 token

本文档适用于FastGPT v4.17.0版本。

## 这个品类的数据长什么样
本品类的数据主要来自广告平台、CRM系统、归因SDK与表单系统。日常处理的文档包括归因规则、线索分发表、渠道报表与异常核对单，数据更新节奏以日度或周度为主。数据字段通常包含渠道标识、线索来源参数、归属销售信息与转化结果，核心处理环节涉及渠道参数核验、重复线索去重与销售归属确认，处理不当会引发渠道ROI失真、销售争议与预算错配。

## 这些特征在「上下文与 token」这一环带来什么约束
多源数据接入导致上下文整合时的token消耗提升，需合理控制上下文总长度。日度或周度的更新节奏要求上下文需定期同步最新数据，避免使用过期的归因规则与渠道报表。不同文档的格式差异，比如归因规则的参数定义与线索分发表的字段结构，要求上下文处理时需保留文本的原始语义，不宜过度拆分token。同时，多字段的核验与去重逻辑，需要在上下文内保留足够的历史匹配记录，防止token不足导致关键的渠道参数或归属信息丢失。

## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext`（最大上下文长度） | 8000–12000 token | 适配多源归因数据与线索报表的总长度，避免超出模型token上限 |
| `quoteMaxToken`（单引用最大token数） | 1500–2000 token | 限制单条渠道报表或归因规则的引用长度，防止单条内容占用过多上下文 |
| 上下文同步间隔 | 每日或每周 | 匹配数据的日度/周度更新节奏，确保上下文使用最新规则与报表 |
| 历史引用保留条数 | 前10条 | 聚焦近期关键线索的匹配记录，减少无效token消耗 |
| 异常记录上下文长度 | 3000–5000 token | 针对异常核对单的详细内容，预留足够token用于完整的核验逻辑 |

## 容易做错的三处
- 现象：设置`quoteMaxToken`为2000后，单条引用内容仍超出token限制。原因：未考虑原始文档的拆分逻辑，部分长渠道报表未提前分块，导致单引用内容超过配置上限。
- 现象：对话上下文丢失，无法实现连续对话。原因：未配置`maxContext`参数，或取值过小导致历史线索匹配记录被自动截断。
- 现象：特定归因规则未被正确识别。原因：强制拆分了包含渠道参数的关键文本，破坏了规则的语义完整性。

## 怎么确认配好了
- 查看上下文总长度的日志输出，确认`maxContext`的取值匹配当前整合数据的总token消耗。
- 测试单条长渠道报表的引用，检查`quoteMaxToken`的限制是否生效。
- 触发一次完整的线索分发流程，核对上下文是否包含最新的归因规则与渠道数据。
- 模拟异常核对场景，确认包含渠道参数的关键文本未被过度拆分，保留完整语义。
