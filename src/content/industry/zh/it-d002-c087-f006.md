# 游戏策划与数值设计的发布说明与运营报告汇总：定时任务与自动化

本页面适用于 FastGPT v4.17.0 版本。

## 这个品类的数据长什么样
游戏策划与数值设计的日常数据多来自玩家行为数据、竞品公开资料、战斗日志、版本反馈。数据更新节奏为周度或每版本周期，日常文档包含玩法策划案、数值表、版本需求单、平衡性测试记录。文档结构差异较大，数值表多为多列结构化数据，策划案多为规则描述文本，字段无统一固定单位，依具体设计需求包含伤害值、留存率、版本标识等不同类型的指标。

## 这些特征在「定时任务与自动化」这一环带来什么约束
品类的数据来源分散且更新节奏不固定，需要定时拉取多源异构数据，因此任务触发频率需匹配周度或版本节点，避免冗余执行或遗漏关键数据。文档结构多样，包含结构化数值表与非结构化策划文本，自动化处理需适配不同格式的拆分与解析逻辑。字段无统一单位，自动化处理前需做格式校验，避免数值解析错误。同时，该环节出错会导致玩法失衡、版本返工，因此需要配置失败重试与告警机制，保障任务稳定性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 任务触发周期 | 按周度或每版本节点触发，可选`168 小时`或按版本里程碑触发 | 匹配品类周/每版本的更新频率，避免冗余执行或遗漏关键数据 |
| 数据源拉取范围 | 拉取近7天或当前版本的战斗日志、玩家反馈数据 | 对应品类数据更新节奏，缩小处理范围提升执行效率 |
| 文档分块规则 | 按单条数值条目或单份策划案片段分块，单块长度`800–1200 字符` | 适配品类文档的数值表、策划案结构，避免拆分破坏规则完整性 |
| 失败重试次数 | 最多重试`3 次`，重试间隔`60 秒` | 应对临时网络波动或数据源临时不可用，避免重复执行导致数据混乱 |
| 告警触发阈值 | 连续2次任务执行失败时触发告警 | 及时发现任务异常，避免影响版本发布节奏 |
| 任务执行超时时间 | 设置为`1800 秒` | 适配多源数据拉取和文档处理的耗时需求，避免任务无限挂起 |

## 容易做错的三处
- 现象：多列数值表导入后分段混乱，单行列数据被拆分为多个片段。原因：未指定按行作为分块规则，使用默认自动分块逻辑破坏了数值表的结构完整性。
- 现象：调用工作流生成的发布说明接口返回空值。原因：任务触发时机早于数据源更新完成时间，未配置数据源就绪校验步骤。
- 现象：定时任务执行后未生成预期的运营报告。原因：未配置正确的数据源拉取范围，遗漏了当前版本的战斗日志或玩家反馈数据。

## 怎么确认配好了
- 手动触发一次测试任务，核对日志中拉取的数据源条目数是否符合预设的拉取范围。
- 查看生成的文档片段，确认数值表的每一行都被作为独立分块处理。
- 模拟任务执行失败的场景，确认告警机制正常触发。
- 检查任务输出的报告内容，确认包含当前版本所需的数值指标与玩法规则说明。
