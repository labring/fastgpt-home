# 社区贡献者治理的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
本品类的数据来源为代码仓库提交记录、社区论坛互动数据、贡献统计报表与治理会议纪要。更新节奏为月度或季度。日常文档包含贡献指南、行为准则、维护者名单与治理会议纪要，数据字段涵盖贡献者标识、贡献类型、权限层级、决议事项与执行节点，无统一固定的数值统计单位，仅按文档与记录的自然格式存储。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类的文档与数据分散在代码仓库、社区论坛等多类载体，单次上下文整合需覆盖贡献指南、维护者名单与治理决议等多份内容，因此需预留足够的token空间承载完整关联信息。月度或季度的更新节奏降低了高频刷新的需求，但每次调用前需校验最新的权限规则与贡献者状态，避免加载过期数据。贡献者相关字段多为文本标识，token消耗与加载的文档长度直接相关，需限制单次召回的历史记录数量，防止超出模型上下文上限。

## 配置怎么定
以下配置基于FastGPT v4.17.0 版本的上下文与token管理逻辑。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配社区治理相关文档、历史决议与贡献者名单的整合需求，避免截断关键规则信息 |
| `quoteMaxToken` | 2000–3000 token | 限制单条引用的社区文档的token消耗，防止单条内容占用过多上下文空间 |
| 最大上下文召回条数 | 前3–5条 | 匹配品类月度或季度的更新节奏，仅召回最新的治理内容与权限信息 |
| 上下文刷新间隔 | 720小时（30天） | 与品类的更新频率对齐，减少不必要的上下文刷新操作 |
| 贡献记录召回上限 | 前10–15条 | 覆盖月度贡献统计的核心数据，避免加载过多非必要的历史提交记录 |

## 容易做错的三处
- 配置`maxContext`为3000 token后，生成的治理报告出现内容截断，无法完整展示维护者名单与最新决议。排查项：检查`maxContext`配置是否适配社区文档实际长度，是否存在关键信息被模型截断的情况。
- 部分场景下响应长度自动变为200 token，无法输出完整的贡献者晋升评估内容。排查项：检查`maxContext`配置是否适配治理类任务的长内容生成需求。
- 调用时提示上下文token超限，无法加载完整的治理会议纪要。排查项：检查单次召回的上下文条数是否超出限制，token消耗是否符合配置的`maxContext`与`quoteMaxToken`范围。

## 怎么确认配好了
- 核对App/Admin服务端的环境变量配置，确认`AIPROXY_API_ENDPOINT`（AI Proxy服务的根地址，例如http://aiproxy:3000，不得附加/v1或/chat/completions等路径，非单模型地址）与`AIPROXY_API_TOKEN`（AI Proxy管理员Token，与AI Proxy服务端配置一致且不能为空，非应用API Key、模型供应商密钥等）已正确配置，不得在工作流全局变量、应用API请求头或普通模型管理页面配置此类变量。
- 发起一次社区治理报告生成请求，检查返回内容是否覆盖了贡献指南、维护者名单与最新治理决议，无关键信息截断。
- 查看模型调用日志，确认上下文token消耗符合配置的`maxContext`与`quoteMaxToken`限制。
- 等待30天后，验证上下文是否加载了最新的治理会议纪要与贡献统计数据。
