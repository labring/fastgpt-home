# 质保期缺陷响应的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来源于客户提交的质保工单、系统运行日志、合同质保条款与版本更新记录。日常处理的文档包括质保工单、缺陷确认单、修复记录、客户确认单四类，数据结构包含结构化字段（如工单编号、责任判定项）与非结构化文本（如缺陷描述、修复方案）。数据更新频率为每日或每单，随缺陷修复进度实时新增内容。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据来源多样且更新频繁，要求上下文召回需覆盖最近的关联文档，避免引入过时的历史信息。文档结构的差异要求上下文处理需兼顾结构化字段与非结构化文本的完整性，防止关键缺陷信息被拆分。单份文档的内容长度与关联文档的数量，决定了上下文的token占用上限，若未合理配置，易出现token溢出或关键信息丢失的问题。同时，责任边界判断需关联多份文档的上下文，对召回的精度与范围提出了较高要求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `maxContext` | `10000–12000 token` | 适配该品类单轮请求的平均上下文token占用，平衡召回范围与模型承载能力 |
| `quoteMaxToken` | `2000–2500 token` | 限定单份关联文档的最大token占用，避免单份文档过长导致上下文溢出 |
| 分块长度 | `800–1000 字符` | 匹配该品类日常文档的平均段落长度，兼顾召回精度与token利用率 |
| 重叠长度 | `150–200 字符` | 保留跨块的缺陷描述关联信息，防止上下文断裂 |
| 单次搜索上限 | `前6条` | 匹配该品类每日关联文档的平均数量，平衡召回范围与响应速度 |

## 容易做错的三处
- 现象：调用FastGPT工作流API时，返回结果无法关联历史问题，连续提问时出现答非所问。原因：未在工作流节点中配置上下文绑定规则，仅传入单轮请求参数，未携带历史会话的token与关联文档信息。
- 现象：上传质保工单文档后，模型召回的内容出现片段缺失，无法完整描述缺陷修复流程。原因：分块重叠长度设置过小，导致跨段落的缺陷关联信息被拆分，无法形成连贯上下文。
- 现象：检索返回的文档条数超出预期，且部分文档与当前问题无关。原因：单次搜索上限设置过大，引入了非关联的历史工单，干扰了上下文召回的精度。

## 怎么确认配好了
- 上传单份完整的质保工单文档，在FastGPT v4.17.0版本的知识库中发起提问，验证模型能否召回文档中的所有关键缺陷描述与修复记录。
- 发起连续3轮关联提问，验证每一轮回答都能关联前序问题中的缺陷信息，无答非所问情况。
- 调用工作流API，传入包含历史会话ID的请求参数，验证返回结果能关联历史上下文内容。
- 查看系统运行日志，确认召回的文档条数与`maxContext`设置的参数一致，无token溢出报错。
