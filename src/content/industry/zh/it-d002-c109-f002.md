# 身份账号与权限管理的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
本品类的核心数据来自IAM系统、HR系统、业务系统日志与审批系统，更新频率为每日或随人事变动触发。日常维护的文档包括账号申请单、权限矩阵、离职回收单与审计报告。账号申请单包含申请人ID、岗位、申请权限范围等字段；权限矩阵包含账号ID、关联系统、权限等级、生效时间等字段；离职回收单包含离职员工ID、回收权限列表、操作人等字段；审计报告包含权限变更记录、异常账号条目等内容。

## 这些特征在「上下文与 token」这一环带来什么约束
多源数据的整合会增加单条上下文的token占用，需限制单次加载的数据源数量，避免超出模型上下文上限。数据更新频率为每日或人事变动触发，要求上下文缓存的有效期匹配更新节奏，防止出现过期数据。不同文档的字段长度差异较大，权限矩阵单条内容可能较长，需为不同类型的上下文配置差异化的token上限。审计类文档包含敏感权限明细，需控制单条上下文的总token量，确保合规性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | `8000–12000 token` | 本品类核心文档如权限矩阵、审计报告的单条内容长度集中在该区间，适配FastGPT v4.17.0的模型上下文上限 |
| `quoteMaxToken` | `1500–2000 token` | 单条账号申请单、离职回收单的内容长度通常在此区间，确保引用内容完整且不占用过多总上下文 |
| 上下文缓存有效期 | 每12小时刷新 | 本品类数据更新频率为日/人事变动，12小时刷新可平衡数据时效性与token消耗 |
| 数据源过滤规则 | 仅加载近7天的权限变更日志 | IAM类数据的异常权限问题多集中在近7天，过滤旧数据可减少token占用 |
| 上下文拆分规则 | 按文档类型拆分 | 本品类不同文档的字段差异大，拆分后可精准配置各类型的token上限 |

## 容易做错的三处
- 现象：出现E11000重复键数据库报错，排查项：检查多套部署是否按环境隔离配置参数，避免共享同一数据库集合；该报错与`AIPROXY_API_ENDPOINT`（AI Proxy服务根地址，格式如http://aiproxy:3000，勿附加路径后缀）、`AIPROXY_API_TOKEN`（AI Proxy管理员Token，与服务端配置一致）环境变量配置无关。
- 现象：加载10000+行的Excel权限矩阵数据时，token消耗超出上限导致结果截断，排查项：检查上下文token配额配置是否适配本品类大体积源数据，确认是否沿用默认参数。
- 现象：新增员工账号时权限校验无匹配记录，排查项：检查数据源关联规则配置，确认是否加载HR系统的人事变动数据作为上下文。

## 怎么确认配好了
- 查看App/Admin服务端运行日志，确认`AIPROXY_API_ENDPOINT`（AI Proxy服务根地址，格式如http://aiproxy:3000，勿附加路径后缀）与非空`AIPROXY_API_TOKEN`（AI Proxy管理员Token，与服务端配置一致）环境变量加载正常，无连接超时报错。
- 导入1000行权限矩阵Excel测试数据，核对返回的上下文token占用量在配置的`maxContext`范围内。
- 模拟离职员工账号回收操作，确认系统能加载对应离职回收单的上下文并完成权限校验。
- 生成一份权限审计报告，核对上下文调用的token消耗符合预设的`quoteMaxToken`与`maxContext`配额。
