# 配置管理与CMDB维护的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
该品类的数据由运维资产管理员、SRE、ITSM平台管理员日常维护，核心文档包含配置项清单、服务组件关系拓扑、变更记录、资产盘点表。数据来源涵盖CMDB系统、云资源清单、自动发现工具及采购台账，更新频率按日或周执行。数据字段包含配置项唯一标识、组件类型、依赖关系、变更时间、盘点状态等，无统一固定单位，随数据类型变化。

## 这些特征在「上下文与 token」这一环带来什么约束
数据来源多样且更新频率存在差异，导致上下文需覆盖不同周期的配置数据，token消耗会随配置项数量、关系拓扑复杂度上升。配置项清单、变更记录等文档结构差异较大，需针对性拆分上下文片段，避免无效token占用。每日更新的实时数据与周更的盘点数据需区分加载优先级，防止token溢出。同时依赖关系字段关联性强，需精准控制召回的关联数据量，避免上下文过载。

## 配置怎么定
以下配置规则适配FastGPT v4.17.0版本：
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 12000–15000 token | 匹配CMDB配置项、变更记录等多文档合并后的平均token占用，避免单次请求token溢出 |
| `quoteMaxToken` | 2000–3000 字符 | 对应单条配置项或变更记录的标准长度，防止单段内容占用过多token |
| 上下文召回上限 | 前8条 | 限制关联配置项的召回数量，控制总上下文token消耗 |
| 实时数据加载优先级 | 优先加载 | 适配日更的变更记录，优先保障实时配置信息的上下文覆盖 |
| 周更数据加载方式 | 按批次拆分加载 | 适配周更的资产盘点表，拆分后降低单次请求的token占用 |

## 容易做错的三处
- 对话结果被截断，末尾显示`[hide 38432 char]`，且Markdown格式的配置说明无法正常渲染，原因是未合理设置`maxContext`与`quoteMaxToken`参数，导致上下文总token超出请求上限，被平台强制截断。
- 启动OneApi时出现`failed to get gpt-3.5-turbo token encoder`异常，原因是未正确关联CMDB配置数据的token编码规则，或上下文加载时混入了无法编码的非标准格式字段。
- 拉取Reranker模型的ACCESS Token失败，原因是未正确配置模型访问的token获取规则，或未校验token的有效期限。

## 怎么确认配好了
- 发起包含CMDB变更记录与配置项清单的测试请求，检查返回结果无截断现象。
- 查看单次请求的token消耗统计，确认未超过`maxContext`的设置值。
- 对比实时变更记录与周更资产盘点表的加载顺序，确认优先级配置生效。
- 触发Reranker模型的ACCESS Token获取流程，确认无异常报错。
