# 问题管理与根因分析的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
这个品类的数据围绕故障后根因分析与问题管理产生，日常文档包括RCA报告、问题单、复盘纪要、整改跟踪表，数据来源为故障时间线、运行日志、监控指标、代码提交记录。数据更新节奏为每次重大故障触发，月度更新频次稳定。数据字段包含故障发生时间、根因描述、整改措施、跟踪状态等，无统一固定单位，随文档类型调整。数据体量随故障复杂度提升，核心围绕故障全生命周期的复盘与整改信息。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据来源分散，需整合多源信息形成完整证据链，对上下文的token总量控制提出明确要求。数据更新频率为单次故障/月，单次数据体量波动较大，需灵活调整上下文召回的上限与token分配。日常文档结构差异显著，长文档如RCA报告段落密集，短文档如问题单条目清晰，需匹配不同场景的上下文拼接逻辑。根因分析依赖完整的历史证据，上下文缺失或截断会导致根因假设偏差，因此需明确上下文的召回范围与优先级，避免关键证据丢失。整改跟踪表的字段关联性强，上下文需保留跨文档的关联信息，token分配需优先保障核心复盘字段的完整性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配RCA报告、复盘纪要等长文档的上下文整合需求，避免关键根因证据被截断 |
| `quoteMaxToken` | 2000–3000 token | 保障问题单、整改跟踪表等短文档的核心字段完整，防止引用内容过载 |
| 上下文召回条数 | 前3–5条 | 故障数据月度更新，单次召回量无需过大，避免token超限 |
| 上下文拼接顺序 | 按故障时间线排序 | 根因分析依赖时间顺序的证据链，时间排序的上下文更贴合分析逻辑 |
| 上下文过滤规则 | 按实测标定 | 不同故障场景的核心证据差异大，需根据实际数据调整过滤阈值 |

## 容易做错的三处
- 现象：配置`maxContext`后仍出现上下文截断，根因分析结论缺失关键故障证据。原因：未根据RCA报告的实际长度调整`maxContext`取值，导致核心故障时间线数据被提前截断。
- 现象：多知识库问题分类时，分类结果固定匹配兜底类别。原因：未配置上下文召回规则，仅使用当前问题文本进行匹配，未引入历史问题与故障上下文，导致分类依据不足。
- 现象：手动调整文档分段后，上下文关联失效。原因：未匹配分段长度与`quoteMaxToken`限制，导致分段后的上下文无法完整关联原文档的根因逻辑。

## 怎么确认配好了
- 上传一份典型的RCA报告，查看上下文召回的内容是否包含故障时间线、核心日志片段等关键信息，调整`maxContext`取值至覆盖核心内容。本配置适用于FastGPT v4.17.0版本。
- 测试多知识库问题分类场景，输入带历史故障上下文的提问，确认分类结果匹配对应知识库的问题类别，调整上下文召回条数。
- 上传分段后的文档片段，验证关联的上下文是否完整保留原文档的根因描述，调整`quoteMaxToken`取值。
- 查看系统日志，确认未出现上下文token超限的报错，根据报错提示调整配置参数。
