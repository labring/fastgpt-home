# 需求分析与PRD管理的发布说明与运营报告汇总：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自客户访谈记录、工单系统、竞品公开页面与埋点看板，更新频率为周度或每版本发布周期。日常产出的文档包括需求调研纪要、PRD文档、用户故事清单与需求变更单，数据字段通常包含需求编号、关联业务目标、验收口径、变更时间等，文档结构以需求拆解、边界确认、变更跟踪为核心逻辑。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的文档长度差异显著，PRD文档可能包含数百字的业务逻辑描述，需求变更单则仅为数十字的条目，拼接上下文时需避免冗余内容占用过多token。高频更新的特性要求上下文与token统计需适配快速迭代的文档变化，同时多来源的数据格式差异可能导致token分配不均，需优先保留需求编号、验收口径等核心字段的上下文，避免非关键内容挤占token配额。本页面配置说明适配FastGPT v4.17.0版本。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | `8000–12000 token` | 该品类核心文档的总token通常在此区间，适配多数大模型的上下文配额 |
| `quoteMaxToken` | `2000–3000 token` | PRD等核心文档的关键段落token量集中在此范围，避免超出单段处理上限 |
| 相似度阈值 | `0.35–0.5` | 适配需求文档中业务术语的独特性，平衡匹配精度与召回范围 |
| 单次搜索上限 | `前6条` | 该品类的需求关联条目通常不超过6个核心项，避免冗余上下文 |
| 超时阈值 | `600 秒` | 该品类的需求查询通常在10分钟内完成处理，适配业务评审节奏 |
| 问题优化 | 启用 | 需求分析场景需将用户查询聚焦为标准化的需求匹配语句，提升召回精准度 |

## 容易做错的三处
- 现象为调用时返回「上下文token数超标」报错，原因是未根据该品类的文档长度调整`maxContext`配置，将配额设置过高或未过滤非核心的辅助文档。
- 现象为超长任务执行超时，原因是未限制单次搜索的条目数或超时阈值设置过低，导致拼接的上下文总长度超出模型处理上限或处理时间无法覆盖需求分析的完整逻辑。
- 现象为无法引用到目标需求内容，原因是相似度阈值设置过高，过滤了部分匹配度符合要求的需求文档条目，或未启用问题优化导致查询语句未聚焦核心需求关键词。

## 怎么确认配好了
- 查看当前配置的`maxContext`与`quoteMaxToken`数值，核对是否与该品类的平均文档token量匹配。
- 模拟提交一条需求变更查询，检查返回的上下文内容是否仅包含核心需求相关的文档片段。
- 调整相似度阈值，验证搜索返回的条目数是否符合该品类的需求关联逻辑。
- 提交高频更新的需求文档，确认上下文统计的更新频率与业务迭代节奏一致。
