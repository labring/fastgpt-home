# Pull Request评审的安全与合规材料审查：权限与数据隔离

## 这个品类的数据长什么样
Pull Request评审的数据通常来自代码仓库、CI流水线、Issue链接与贡献者提交。FastGPT v4.17.0 版本中，PR数据的存储表默认包含`teamId`与`tmbId`等身份与归属标识，日常文档包含PR说明、代码评审意见、CI结果与合并记录。更新频率按单次PR合并节奏或周度批量同步，单次PR关联的变更数据、评审记录会随流程推进实时更新，合并完成后归档至对应团队的存储库。不同主体可访问的数据范围与操作权限存在明确区分，数据结构以变更条目、评审意见、合并状态为核心。

## 这些特征在「权限与数据隔离」这一环带来什么约束
Pull Request评审的数据特征为权限与数据隔离带来明确约束。数据来源分散覆盖代码仓库、CI流水线等多系统，要求隔离规则需覆盖所有数据入口，避免跨系统数据泄露。更新频率实时或周度批量同步，权限校验需匹配数据更新节奏，防止未授权用户在PR变更过程中越权访问。数据包含`teamId`与`tmbId`等归属标识，缺失或未正确关联会直接导致权限校验失效，引发跨团队数据泄露。不同主体的操作权限存在差异，需严格限制权限范围，避免非授权人员修改主干代码。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 团队权限隔离规则 | 按`teamId`划分访问范围，仅允许成员访问绑定`teamId`的PR数据 | 匹配PR数据的团队归属标识，确保跨团队数据隔离 |
| 贡献者身份校验 | 关联`tmbId`验证提交者与评审者权限 | 确保仅授权贡献者能提交或评审对应PR |
| 历史版本字段补全 | 强制校验`tmbId`字段存在性，缺失则自动补全或拦截操作 | 修复较早版本存储表无`tmbId`导致的权限失效问题 |
| 内网MySQL连接配置 | 配置连接超时阈值为30 秒，白名单仅限内网网段 | 解决内网部署时的数据库连接拒绝问题 |
| 团队成员添加校验 | 按账号绑定`teamId`完成身份验证，仅允许有效账号加入 | 避免出现用户名无效的添加失败问题 |
| 评审聊天记录隔离 | 按`teamId`划分聊天存储分区，仅成员可查看自身团队的评审沟通数据 | 确保不同团队的评审沟通数据隔离 |

## 容易做错的三处
- 现象为历史版本的PR关联数据缺少`tmbId`字段，无法完成团队权限校验。原因是较早版本的MongoAppVersion表未同步`tmbId`字段，未配置自动补全规则。
- 现象为内网部署时出现数据库连接拒绝报错，日志显示MySQL正常启动。原因是未配置内网访问白名单，外部请求被数据库拦截。
- 现象为公开访问链接生成后，跨团队成员可查看非自身团队的PR评审数据。原因是未按`teamId`划分数据存储分区，权限隔离规则未生效。

## 怎么确认配好了
- 提交测试PR，验证非团队成员无法查看或评审该PR，确认`teamId`权限规则生效。
- 查看历史PR数据，确认每条记录均包含`tmbId`字段，无缺失情况。
- 在内网环境测试数据库连接，验证仅内网网段可访问MySQL实例，无外部连接报错。
- 添加团队成员并验证账号有效性，确认绑定`teamId`后可正常加入对应团队。
