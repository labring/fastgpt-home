# 众包标注人员管理的安全与合规材料审查：对话日志与审计

## 这个品类的数据长什么样
本品类的数据主要来自众包平台、标注质量反馈系统、人员培训考试记录与财务结算系统。数据更新频率通常为日度或月度，核心文档包含人员准入规则、岗前培训材料、月度绩效表与结算清单。数据字段一般包含人员唯一标识、关联标注任务编号、质检评分、培训考核结果、结算金额与周期等，整体围绕人员管理与标注业务的全流程流转。

## 这些特征在「对话日志与审计」这一环带来什么约束
由于数据来源分散且更新节奏不同，对话日志需同时关联人员标识、任务编号与财务结算字段，确保审计时可追溯标注全链路。人员准入与培训数据的静态性要求日志需留存历史版本，避免因人员信息变更导致追溯失效。结算数据的月度更新特性，要求审计日志需支持按结算周期筛选，同时需兼容日度质检数据的实时校验。此外，多源数据的字段差异，要求审计配置需统一映射不同系统的标识字段，避免出现关联断裂，影响审计准确性。

## 配置怎么定
本配置适用于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定人员ID与标注任务ID的复合前缀格式 | 本品类需同时追溯人员与任务，复合格式可实现双向关联，匹配多源数据的字段映射需求 |
| `responseChatItemId` | 保留完整会话链路的全量ID | 需记录单条标注对话的完整交互，全量ID可精准定位单条质检或结算关联的对话片段 |
| `detail` | 开启1000–2000字符的日志存储 | 本品类的标注对话包含任务指令与标注结果，足够长度可留存完整业务上下文，满足合规审计要求 |
| 日志存储周期 | 按结算周期的2倍时长，最长不超过365天 | 结算数据为月度更新，2倍周期可覆盖完整结算审计周期，符合行业通用留存要求 |
| 多源字段映射 | 预设人员ID、任务ID的标准化映射规则 | 本品类数据来自多系统，统一映射可避免日志关联断裂，提升审计效率 |

## 容易做错的三处
- 现象：在审计模块输入指定人员ID筛选历史对话日志时返回空结果。原因：未将`chatId`配置为关联人员ID与任务ID的格式，导致日志无法按人员标识完成筛选。
- 现象：调用接口生成工作流审计报告后，对话日志中的运行数据为空。原因：未开启`detail`配置项的全量日志采集，仅留存了基础会话标识，未记录工作流执行细节。
- 现象：单条对话的日志详情中`detail`字段内容不完整。原因：配置的日志存储字符长度低于标注对话的实际内容长度，导致合规审计时无法获取完整上下文。

## 怎么确认配好了
- 手动输入已知人员ID与关联任务ID，筛选对应对话日志，确认可返回匹配的结果列表。
- 查看单条对话的日志详情，确认`detail`字段包含完整的标注指令、交互内容与工作流执行细节。
- 调用审计接口，传入合法的`responseChatItemId`，确认返回的日志数据无字段缺失或截断。
- 检查日志存储时长配置，确认留存周期覆盖至少一个完整的月度结算周期。
