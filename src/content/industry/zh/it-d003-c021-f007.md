# 供应链安全与开源依赖治理的安全与合规材料审查：对话日志与审计

## 这个品类的数据长什么样
本品类的数据主要来自包管理器、代码仓库、漏洞库与许可证数据库。日常产出的文档包含SBOM清单、依赖风险报告、许可证清单与修复工单，字段通常包含第三方组件名称、版本号、关联漏洞编号、许可证类型、风险等级与修复状态。数据更新频率为每日或每版本发布时同步，不同组件的更新节奏存在差异，核心依赖的更新会优先触发全量校验。

## 这些特征在「对话日志与审计」这一环带来什么约束
数据来源分散且更新频繁，要求对话日志需完整记录每次依赖校验、漏洞匹配的调用链路与返回结果，避免遗漏跨系统交互的细节。多类型文档的关联查询需要审计日志保留组件与报告的映射关系，便于回溯合规审查的依据。每日或每版本的高频更新，要求审计日志支持按时间范围快速筛选，同时需限制单条日志的存储规模，防止占用过多资源。修复工单与风险报告的关联记录，要求日志中包含操作主体与触发时机，满足合规溯源的需求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `detail` | 开启全量日志 | 完整记录依赖校验的参数与返回结果，满足审计溯源需求，适配FastGPT v4.17.0的日志采集规则 |
| `chatId` | 绑定至SBOM清单的唯一标识 | 将对话日志与特定版本的依赖清单关联，便于回溯对应版本的合规审查过程 |
| `responseChatItemId` | 关联至漏洞匹配结果的ID | 快速定位单条依赖的审计详情，缩小排查范围 |
| 日志存储时长 | 30–90 天 | 满足合规审查的溯源周期要求，同时控制存储成本 |
| 日志采样规则 | 高危依赖场景全量记录，普通场景按 10% 采样 | 平衡审计完整性与资源占用，优先保障高风险场景的日志完整 |
| 日志筛选维度 | 按组件名称、更新时间、风险等级筛选 | 匹配日常审计的排查需求，快速定位异常环节 |

## 容易做错的三处
- 现象为工作流执行依赖校验节点时显示失败，但模型后台有响应日志。原因是未开启`detail`全量日志配置，导致工作流节点的执行日志未被完整记录，无法排查节点间的参数传递错误。
- 现象为应用对话触发依赖审计后，界面显示异常报错但无对应日志条目。原因是未配置按异常状态触发日志留存，仅记录正常交互的日志，导致报错场景的日志丢失。
- 现象为尝试获取上一次AI回复的对话记录ID时返回空值。原因是未绑定`responseChatItemId`与对话上下文，导致日志中未保留对应回复的唯一标识，无法关联查询。

## 怎么确认配好了
- 发起一次第三方组件依赖校验的测试对话，查看日志中是否包含`detail`字段对应的完整参数与返回结果。
- 触发一次高危依赖的审计操作，确认日志中生成了对应`chatId`的完整链路记录。
- 尝试通过组件名称筛选日志，确认筛选功能可正常匹配对应条目。
- 触发一次异常报错的依赖校验，确认日志中留存了报错的详细信息与触发时机。
