# 创作者激励结算的安全与合规材料审查：引用来源与溯源

## 这个品类的数据长什么样
该品类的日常文档包含激励规则、结算明细、申诉记录、付款清单，数据来源覆盖内容数据、广告分成系统、财务系统、账号后台，更新频率多为月度或单次活动周期。字段通常包含创作者标识、收益口径、付款状态、申诉事由等，以结构化表格类文档为主，部分规则类文档为纯文本格式。数据更新多为批量触发，无实时高频更新的场景。

## 这些特征在「引用来源与溯源」这一环带来什么约束
品类的多源数据来源要求溯源环节需关联不同系统的文档，确保引用内容与实际业务系统的记录一致。非实时的批量更新节奏，要求知识库的刷新周期匹配业务更新频率，避免引用过期的激励规则或结算数据。结构化的文档字段，要求溯源时精准匹配对应字段，避免混淆不同创作者或不同周期的结算数据。同时，出错后果直接关联结算争议与错付漏付，要求引用的来源必须可验证，确保每一笔结算的依据可追溯。

## 配置怎么定
本文基于FastGPT v4.17.0版本进行配置说明。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | 匹配结算明细、激励规则等单份文档的平均长度，避免截断关键结构化字段 |
| `responseData` | 仅返回核心业务字段 | 限定返回创作者ID、结算周期、付款金额等与结算直接相关的内容，过滤无关字段 |
| `detail` | 开启溯源详情展示 | 展示引用文档的来源系统与更新时间，便于验证时效性与来源合规性 |
| 单次搜索上限 | 前5条 | 匹配月度批量结算的单次关联数据量，避免召回过多历史文档导致过载 |
| 最大上下文 | 按实测标定 | 适配多系统文档的拼接长度，确保模型能完整处理关联的业务数据 |

## 容易做错的三处
-  配置`quoteMaxToken`取值过小，返回的结算明细文档被截断，界面显示的引用内容缺少关键收益口径字段。原因是未匹配品类文档的平均长度，未预留足够token承载结构化字段。
-  未限定`responseData`的返回范围，知识库返回与当前结算无关的历史申诉记录，导致提问时出现不相关结果。原因是未针对品类的结构化数据做字段过滤，召回了非本次结算周期的文档。
-  未开启`detail`配置，无法查看引用文档的更新时间，当结算规则更新后未同步知识库，导致沿用旧规则计算收益引发争议。原因是未关联文档的更新时间与品类的月度更新节奏，无法验证时效性。

## 怎么确认配好了
-  提交包含指定结算周期关键词的测试提问，查看返回的引用文档是否包含对应周期的结算明细字段。
-  检查引用来源的展示区域，确认是否显示文档的来源系统与更新时间。
-  上传更新后的激励规则文档，验证知识库搜索是否能召回最新版本的内容。
-  调整`quoteMaxToken`的取值，测试长度较长的结算文档是否被完整返回，无截断情况。
