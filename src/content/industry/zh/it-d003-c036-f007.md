# 原型与交互设计的安全与合规材料审查：对话日志与审计
本文基于FastGPT v4.17.0版本编写

## 这个品类的数据长什么样
通常服务于产品设计师、交互设计师与前端产品小组，日常产出的文档包含交互原型、页面流程图、组件说明与评审记录。数据来源多为Figma或Axure文件、团队设计系统、用户反馈与可用性测试记录，更新频率多为每周或每版本迭代一次。数据结构以页面操作路径、组件属性、评审意见为核心字段，无统一固定格式模板，需结合具体项目的设计规范调整。

## 这些特征在「对话日志与审计」这一环带来什么约束
由于数据来源依赖设计工具文件与评审沟通记录，对话日志需绑定对应原型项目的唯一标识，确保日志与实际设计内容可关联。更新频率与项目迭代同步，审计周期需匹配周度或版本级别的评审节奏，避免日志留存滞后。数据以操作路径与评审意见为核心，日志需完整记录对话中的prompt与响应内容，便于回溯设计偏差的产生链路。该品类数据出错会导致研发理解偏差、上线后操作路径不通甚至返工，因此日志需留存完整的会话链路，支持合规审查时的全流程追溯。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定当前原型项目的唯一标识 | 关联交互原型文件与对话日志，便于回溯设计评审的完整链路 |
| `responseChatItemId` | 为每个LLM评审响应生成唯一标识 | 精准定位单条评审对话的内容，避免不同会话的日志混淆 |
| `detail` | 开启全量日志记录 | 留存完整的prompt与响应内容，满足合规审查的全链路追溯要求 |
| 最大上下文 | 80–120条对话记录 | 匹配原型设计评审的常规对话轮次，避免上下文溢出或信息丢失 |
| 日志留存周期 | 6个月 | 匹配合规审查的常规留存周期，适配项目迭代的回溯需求 |
| 会话超时阈值 | 600秒 | 适配大型原型文件的审查耗时，避免因文件加载过久触发异常 |

## 容易做错的三处
- 工作流中代码运行输入包含历史记录时校验失败，现象为配置关联历史记录后工作流无法启动，触发校验报错。原因是未正确绑定`chatId`参数，导致历史记录的上下文关联校验不通过。
- 偶发LLM响应为空且卡住10秒后报错，现象为对话日志中`responseChatItemId`字段为空，伴随超时提示。原因是未开启全量`detail`日志记录，导致异常链路无法完整追溯。
- 对话日志仅显示固定条数的历史记录，超出部分无法查看，现象为聊天记录上限为50条，无法加载后续评审对话。原因是最大上下文配置取值过低，未匹配评审对话的实际轮次。

## 怎么确认配好了
- 查看任意会话的日志详情，确认每条对话都绑定了对应原型项目的`chatId`标识。
- 触发一次设计评审对话，检查`responseChatItemId`字段是否存在且唯一，无重复或空值情况。
- 导入超过50条的历史对话记录，验证日志是否能完整加载，确认最大上下文配置生效。
- 模拟工作流调用，输入包含历史记录的参数，确认无校验失败报错，工作流可正常启动。
