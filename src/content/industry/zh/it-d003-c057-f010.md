# 工单受理与问题分级的安全与合规材料审查：引用来源与溯源

## 这个品类的数据长什么样
工单受理与问题分级的核心数据来自工单系统、聊天记录、产品日志、客户合同SLA，更新频率为日或实时。日常处理涉及的文档包括客户工单、问题分级表、处理记录、服务报告，字段包含工单ID、客户标识、问题类型、分级等级、处理时限、关联SLA条款等，单条工单内容长度跨度较大，从简短咨询到完整故障排查记录不等。

## 这些特征在「引用来源与溯源」这一环带来什么约束
由于数据来源覆盖实时交互与结构化业务文档，溯源环节需绑定具体业务标识以确保可追溯到原始工单与处理节点。实时更新的工单数据要求引用的参考文档不能存在过期偏差，需同步关联最新的处理记录。工单内容跨度大的特征要求溯源配置需适配不同长度的业务信息，避免截断核心问题描述。同时，出错后果涉及响应超时与SLA违约，需确保溯源流程不额外增加处理耗时。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `quoteMaxToken` | `800–1200 token` | 工单内容包含结构化字段与非结构化描述，该区间可覆盖单条工单核心信息且不超出上下文上限，适配FastGPT v4.17.0的上下文限制 |
| `responseData` | 包含工单ID、处理记录ID | 工单品类需绑定具体业务标识，确保溯源可定位到原始工单与内部处理环节，避免引用来源与具体业务脱节 |
| `detail` | 开启 | 问题分级需关联原始分级表与处理记录的字段，开启后可展示分级依据的原始文档片段，满足合规审查要求 |
| 单次溯源召回上限 | 前3条 | 工单受理的问题分级通常依赖最相关的3份参考文档，过多会增加上下文负载，延长处理耗时 |
| 引用来源展示位置 | 工单详情页侧边栏 | 客服团队需在处理工单时快速查看溯源信息，侧边栏布局不干扰当前操作界面，符合日常使用习惯 |

## 容易做错的三处
- 引用来源仅展示在对话底部，未绑定对应工单ID。原因：未配置`responseData`参数绑定业务标识，仅默认展示知识库文档名称，无法关联到具体处理的工单。
- 非工具调用模式下，大模型输出未关联工单知识库的内容，仅返回通用回答。原因：未开启`detail`参数，或`quoteMaxToken`取值过小导致核心工单内容被截断，无法触发召回逻辑。
- 溯源时无法查看上传的原始文档片段，仅显示文档文件名。原因：未配置`responseData`参数关联原始文档存储路径，仅展示文档名称，无法定位到客户上传的原始工单内容。

## 怎么确认配好了
- 发起一条测试工单，查看引用来源区域是否同时展示工单ID与处理记录ID。
- 调整`quoteMaxToken`的取值，验证上下文长度变化是否符合预期，确认核心工单内容未被截断。
- 开启`detail`参数后，检查是否展示了原始工单的分级依据片段与处理记录细节。
- 提交工单后，确认引用来源展示位置符合团队日常操作的界面布局。
