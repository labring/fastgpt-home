# 社区举报处理的安全与合规材料审查：对话日志与审计

## 这个品类的数据长什么样
社区举报处理的核心数据来自举报系统、内容详情、用户历史记录与审核规则，日常文档包含举报工单、处理记录、申诉单与用户通知模板。数据更新节奏为日级或实时，每条数据包含举报唯一标识、举报内容、用户关联信息、审核判断结果与处置时间等字段，按单条举报工单的处理链路进行归集，无统一固定的批量统计口径。

## 这些特征在「对话日志与审计」这一环带来什么约束
由于数据按单条工单归集且更新实时，对话日志需精准绑定每条工单的唯一标识，避免不同工单的日志混淆。由于日常文档包含敏感的举报内容与处置细节，审计日志需留存完整链路，不得遗漏关键节点。由于出错后果可能引发用户投诉或社区冲突，日志与审计环节需具备可溯源性，确保每一条审核动作都能对应到具体的对话内容与处置结果。同时，需适配社区举报处理的实时响应需求，避免日志同步延迟导致审计失效。

## 配置怎么定
本文适用于FastGPT v4.17.0版本，以下配置基于该版本的功能逻辑：

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定举报工单唯一标识 | 每条社区举报工单对应独立对话链路，需将日志与工单精准关联 |
| `responseChatItemId` | 关联审核处置记录ID | 需将日志条目与具体的审核动作、处置结果绑定，便于溯源审计 |
| `detail` | 开启全量内容存储 | 需留存完整对话上下文、举报内容与审核反馈，满足合规审查要求 |
| 日志存储时长 | 30–90 天 | 适配社区举报处理的一般合规留存周期，覆盖常规追溯需求 |
| 日志拉取触发条件 | 按工单完成事件触发 | 匹配社区举报处理的实时更新节奏，避免无效日志堆积 |

## 容易做错的三处
- 现象：查看`detail`字段对应的日志详情时，多条举报工单的日志内容完全一致。原因：未绑定`chatId`参数，日志未关联对应工单的唯一标识，导致不同工单的日志被混淆。
- 现象：对话日志无法关联到具体的举报工单或审核记录。原因：未配置`responseChatItemId`与工单的关联规则，日志仅记录通用对话链路，未匹配具体的审核动作ID。
- 现象：审计日志仅留存部分对话摘要，无法提取违规证据。原因：未开启`detail`全量存储配置，仅保存了核心关键字段，遗漏了举报内容的完整细节。

## 怎么确认配好了
- 随机抽取一条已完成的举报工单，通过`chatId`检索对应日志，确认日志内容与工单的对话记录、举报内容完全匹配。
- 查看日志存储目录或审计数据库，确认每条日志条目均包含`responseChatItemId`与对应审核处置记录的关联ID。
- 手动触发一条测试举报工单，确认日志在工单标记为完成后立即生成并同步至审计系统，无延迟或丢失情况。
- 检查日志存储策略，确认日志留存周期符合预设的30–90天范围，无提前自动清理的异常配置。
