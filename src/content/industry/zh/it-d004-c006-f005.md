# Pull Request评审的客户技术支持与售前答疑：多轮对话与提示词

## 这个品类的数据长什么样
Pull Request评审的核心数据来自代码仓库、CI流水线、Issue链接与贡献者提交记录。日常关联的文档包括PR变更说明、代码评审意见、CI执行结果与合并历史记录。数据更新频率为每日或每周，随代码提交与流水线执行同步更新。数据字段包含变更代码范围、测试通过率、冲突文件列表、贡献者信息等，无统一固定格式，随仓库配置与项目规范调整。与Issue分拣品类不同，本品类处理的是可合并的代码变更请求，聚焦于代码变更的合规性与可合并性。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
由于数据来源分散且格式不统一，多轮对话需要先关联代码仓库、CI日志与PR上下文，避免跨数据源的信息割裂。更新频率的特性要求对话上下文需限定在最近的PR周期内，避免加载过期数据影响评审准确性。变更意图确认与冲突处理为最耗时环节，提示词需要设计分层追问逻辑，逐步引导补充变更细节与冲突解决方案。同时，出错后果直接影响主干分支稳定性，提示词需强制校验变更合规性与测试结果，防止未通过验证的代码合并导致项目质量下降。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本适配。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `messages` | 按当前PR关联的3条历史评审记录+当前变更内容填充 | 匹配PR评审的上下文依赖，避免冗余信息干扰 |
| 问题优化 | 开启，针对代码变更术语做意图拆解 | 适配代码领域的专业表述，优化提问准确性 |
| 最大上下文 | 8000–12000 token，按实测标定 | 覆盖PR关联的文档总长度，避免截断关键信息 |
| 单次搜索上限 | 前6条 | 匹配CI结果与评审意见的常规数量，减少无效召回 |
| `variables` | 绑定当前PR的仓库分支ID与变更文件列表 | 精准关联数据来源，确保对话调用的代码信息准确 |
| 输入引导 | 配置为「请补充PR的变更目标与测试范围」 | 引导贡献者提供完整评审所需信息 |

## 容易做错的三处
- 现象：大文件PR关联文档解析时对话超时，原因：未限制上下文长度，加载过多历史评审记录与代码片段。
- 现象：调试预览界面输入引导配置不生效，报错提示字段为空，原因：未正确配置自定义词库与对话引导的触发规则，未绑定关联知识库的API参数。
- 现象：问题优化环节耗时过长，原因：未限定优化范围，将无关的CI日志与合并记录纳入提示词处理流程。

## 怎么确认配好了
- 查看`chatId`是否绑定当前PR的仓库分支ID，确保对话上下文关联的是目标PR的信息。
- 触发测试对话，输入PR变更描述，核对返回的评审意见是否包含关联的CI结果与历史评审记录。
- 检查`variables`是否正确绑定了代码仓库的关联链接与变更文件列表，确保数据来源准确。
- 模拟上传10M以上的PR关联文档，查看解析与对话响应耗时是否符合预期。
