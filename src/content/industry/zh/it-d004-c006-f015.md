# Pull Request评审的客户技术支持与售前答疑：知识库检索与召回

## 这个品类的数据长什么样
该品类的数据来自代码仓库、CI流水线、Issue链接与贡献者提交内容，日常文档包含PR说明、代码评审意见、CI结果与合并记录。数据结构包含变更范围、关联Issue编号、构建状态、审批人、提交时间戳等字段，更新频率为日或周，由代码提交、流水线执行与合并操作触发更新。

## 这些特征在「知识库检索与召回」这一环带来什么约束
数据分散于代码仓库、CI流水线、Issue链接等多系统，需整合跨源索引以覆盖完整关联信息，避免检索遗漏关键细节。更新频率为日或周，需配置增量更新逻辑，降低全量索引的资源占用。日常文档包含代码变更说明、评审意见等，文本长度跨度大，需适配不同长度的语义匹配。关联Issue编号、审批人等元数据可用于精准过滤，但需保障元数据与内容同步更新，否则会出现检索匹配偏差。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的参数逻辑。

| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `similarity` | 0.72–0.80 | 匹配PR评审相关的代码与评审文本，该区间可过滤低相关的通用代码内容，保留与变更意图强相关的结果 |
| `limit` | 前12条 | 单次召回结果适配PR评审的多维度信息需求，避免过多结果导致上下文过载 |
| `searchMode` | hybrid | 结合语义与关键词匹配，覆盖代码变更的技术细节与关联Issue的文本信息 |
| `usingReRank` | 开启 | 对初始召回结果重排序，优先展示与当前PR变更意图最匹配的评审历史与CI结果 |
| `datasetSearchUsingExtensionQuery` | 开启 | 基于用户查询扩展关联的Issue、CI相关关键词，提升跨源信息的召回率 |
| `collectionIds` | 绑定对应项目的代码库、CI日志集合 | 限定检索范围至当前PR所属的项目数据，避免跨项目无关信息干扰 |

## 容易做错的三处
- 现象：检索返回的文档块顺序与原PR关联的提交记录顺序不一致，或出现重复的评审意见条目。原因：配置了全局去重规则，未保留PR评审场景下的文档块关联顺序，导致索引合并时破坏了原有匹配逻辑。
- 现象：检索结果仅覆盖代码文本，未召回关联的CI结果与Issue链接。原因：未开启`datasetSearchUsingExtensionQuery`，未扩展关联关键词以覆盖跨源数据。
- 现象：单次检索返回过多结果，导致评审时需要筛选大量无关信息。原因：未设置合理的`limit`参数，取值超出PR评审的上下文承载范围。

## 怎么确认配好了
- 发起针对当前PR变更内容的检索，核对返回结果是否包含PR说明、CI结果、关联Issue三类核心文档。
- 调整`similarity`参数区间，观察检索结果的相关度变化，确认匹配逻辑符合预期。
- 检查检索集合的绑定配置，确认仅包含当前PR所属项目的代码库、CI日志与评审记录集合。
- 测试包含重复内容的检索请求，确认结果的去重或保留逻辑符合业务场景需求。
