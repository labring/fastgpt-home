# Pull Request评审的客户技术支持与售前答疑：重排与混合检索

## 这个品类的数据长什么样
该品类的数据主要来自代码仓库、CI流水线、Issue链接与贡献者提交记录。日常文档包含PR说明、代码评审意见、CI执行结果与合并历史记录。数据更新频率通常为日或周，字段涵盖变更代码范围、CI通过率、合并冲突标记、贡献者标识等，无统一固定格式，随项目维护规则动态调整。

## 这些特征在「重排与混合检索」这一环带来什么约束
代码仓库的PR数据多为代码片段与文本说明混合，混合检索需同时匹配语义与代码结构特征，需兼顾文本与代码向量的融合权重。日/周级更新的数据需定期刷新索引，避免检索结果与最新变更脱节。多来源数据格式差异显著，重排环节需统一字段权重规则，否则易出现无关结果前置。评审核心的CI失败记录、冲突标记类数据需调整权重，确保核心信息优先展示，支撑变更意图确认与测试结果检查环节。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `usingReRank` | 开启 | 适配PR数据多源混合的特征，提升检索结果相关性 |
| `similarity` | 0.75–0.85 | 过滤低匹配度的非相关PR内容，避免冗余结果干扰评审 |
| `limit` | 前10条 | 匹配PR评审的常规查看范围，控制检索结果体量 |
| `searchMode` | hybrid | 同时覆盖文本语义与代码结构特征，适配PR数据混合属性 |
| 重排模型选择 | 虚拟机开源重排序模型 | 适配PR代码与文本混合数据的语义理解需求，支持本地部署 |

## 容易做错的三处
- 开启`usingReRank`后界面无法勾选重排模型，且检索结果顺序无变化。原因是未在config.js中正确配置重排模型参数，或配置的模型部署路径无效，导致重排环节未正常加载。
- 配置了多个重排模型后，检索结果未按预期重排。原因是未指定默认重排模型，或模型加载超时，导致重排逻辑未实际执行。
- 检索结果条数超出预设的`limit`范围。原因是未正确设置`limit`参数，或混合检索时的召回逻辑未过滤超出阈值的结果，导致冗余数据混入。

## 怎么确认配好了
- 查看FastGPT v4.17.0的后台配置界面，确认`usingReRank`开关处于开启状态，且重排模型已正确配置。
- 发起一次PR相关的检索请求，对比开启重排前后的结果顺序，确认排序逻辑已生效。
- 检查检索结果的条数是否符合`limit`参数的设置，确认无超出范围的冗余结果。
- 查看系统运行日志，确认重排模型已正常加载，无报错信息。
