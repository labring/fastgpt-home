# 代码评审与合并管理的客户技术支持与售前答疑：多轮对话与提示词

## 这个品类的数据长什么样
本品类的数据主要来自Git仓库、CI流水线、静态扫描报告与缺陷库，更新频率为每日或每提交一次。日常文档包含合并请求、代码评审意见、提交记录与分支策略说明，其中合并请求包含变更文件列表、关联分支名、评审状态字段，评审意见包含评论人、评论时间与修改建议字段。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据更新频繁且随提交实时变更，要求多轮对话上下文需支持实时拉取最新的Git提交记录与合并请求状态。文档类型多样，提示词需适配合并请求、评审意见等不同文档的检索逻辑，避免混淆字段含义。变更影响判断依赖多维度信息，多轮对话需按提交顺序、分支关联逐步拆解问题，逐步引导获取完整上下文，确保大模型能基于最新数据生成准确判断。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| 单次搜索上限 | 前 8 条 | 匹配合并请求关联的变更文件数量通常在5-10个区间，避免召回过多无关评审意见 |
| 最大上下文长度 | 8000–12000 字符 | 适配合并请求与多条评审意见的总内容长度，确保覆盖完整变更信息 |
| 多轮对话历史保留 | 最近 20 轮会话 | 匹配研发人员的评审沟通轮次，避免上下文冗余影响准确性 |
| `variables` 变量配置 | 绑定分支名、提交ID字段 | 精准过滤对应合并请求的相关数据，缩小检索范围 |
| 问题优化开关 | 开启 | 帮助将研发人员的口语化评审问题转换为标准化检索指令，提升召回精度 |
| 版本适配 | FastGPT v4.17.0 | 确保配置项与当前平台功能兼容 |

## 容易做错的三处
-  现象：配置单次搜索上限为2000后，大模型生成的评审建议未引用任何召回内容。原因：检索阈值与上下文长度不匹配，过多召回的非关联数据稀释了有效信息，导致大模型无法定位核心评审依据。
-  现象：对话界面无法显示静态扫描报告中的图片附件。原因：未配置文档解析时的图片提取规则，仅提取了文本内容未同步加载关联图片资源。
-  现象：检索返回的评审记录附带了非业务字段ID。原因：未在检索配置中排除元数据字段，导致无关标识被一同召回并发送至大模型。

## 怎么确认配好了
-  发起包含具体分支名的咨询，核对返回的评审意见是否仅关联该分支的变更内容。
-  测试多轮对话，连续发起3-5条关于评审意见的追问，确认上下文能正确关联之前的会话内容。
-  查看检索结果，确认返回的文档段落未包含非业务相关的元数据字段。
-  开启流式输出开关，发起咨询，确认对话界面按字符逐行展示评审建议内容。
