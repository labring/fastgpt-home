# 值班排班与交接的客户技术支持与售前答疑：多轮对话与提示词

## 这个品类的数据长什么样
典型主体为SRE团队、运维经理与技术支持二线，日常使用的文档包含值班表、交接记录、升级联系人清单与值班日报。数据来源为排班系统、故障工单、监控告警与组织通讯录，更新频率为日或周。数据字段包含值班时段、未结事项、升级联系人信息与值班时段内的告警记录，格式以结构化表格与纯文本记录为主，无额外自定义统计字段。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
由于数据更新频率为日或周，多轮对话的提示词需支持定期拉取最新的值班信息，避免使用过期数据。结构化的值班表与交接记录要求提示词能识别字段并关联对应对话上下文，多轮对话需保留不同班次的交接历史。同时，该品类的核心耗时环节为排班冲突协调与交接事项确认，提示词需优先处理这类高频查询，且需确保对话响应及时，避免因超时导致无人响应的后果。

## 配置怎么定
以下配置基于 FastGPT v4.17.0 版本的界面与参数逻辑制定。

| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `variables` | 绑定排班系统、组织通讯录的实时接口，拉取当日值班人员信息，更新频率设为 24 小时 | 匹配该品类数据的日更新频率，确保对话中使用的值班信息为最新 |
| `messages` | 保留最近 20 轮对话上下文，单轮对话内容不超过 1000 字符 | 适配值班交接的多轮对话场景，避免上下文溢出影响模型理解 |
| `chatId` | 绑定值班工单的唯一标识，关联对应班次的交接记录 | 实现不同值班班次的对话上下文隔离，确保交接信息的准确性 |
| 全局变量调用 | 加载预存的升级联系人清单与值班日报模板，更新频率设为 7 天 | 匹配该品类数据的周更新频率，减少不必要的接口调用 |
| 上下文窗口大小 | 8000–12000 token | 容纳值班表、交接记录与多轮对话的全部内容，符合FastGPT的token计算规则 |
| 超时设置 | 30 秒 | 适配客户技术支持的快速响应需求，避免因等待过长导致处理超时 |

## 容易做错的三处
- 现象为AI对话节点输出每段句末出现引用号乱码，后续自动变回标准引号。原因是提示词未对输出格式做强制约束，导致模型生成的文本混入未转义的特殊字符。
- 现象为`chatId`绑定后无法关联对应值班交接记录，对话上下文出现跨班次混淆。原因是未将`chatId`与值班工单的唯一标识正确映射，导致上下文隔离失效。
- 现象为大模型调用偶尔出现响应为空的情况。原因是未配置`variables`的 fallback 取值，当排班系统接口临时无响应时，变量为空触发模型生成空内容。

## 怎么确认配好了
- 触发一次值班排班查询动作，检查`variables`是否成功拉取到当日值班人员的完整信息。
- 发起两轮及以上的交接事项确认对话，检查`messages`是否保留历史对话的上下文内容。
- 模拟排班系统接口无响应的场景，检查是否触发预设的 fallback 取值，避免出现空输出。
- 查看对话日志，确认`chatId`与对应值班工单的唯一标识正确关联，无跨班次混淆情况。
