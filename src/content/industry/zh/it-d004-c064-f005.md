# 投标文件编制的客户技术支持与售前答疑：多轮对话与提示词

本文基于FastGPT v4.17.0版本，针对投标文件编制场景的客户技术支持与售前答疑环节，梳理多轮对话与提示词的落地规范。

## 这个品类的数据长什么样
本品类的数据围绕单次投标项目生成与更新，数据来源包括招标公告、招标文件、企业资质库与供应商报价。日常产出的文档包含投标文件、资格证明、商务偏离表、技术偏离表，核心字段涵盖招标要求的响应条款、资质编号、报价明细、格式校验项等。数据更新节奏为每单独立更新，仅针对当前投标项目的要求调整内容，无跨项目复用的固定数据集。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
本品类的数据特征对多轮对话与提示词配置带来明确约束。首先，单项目数据独立更新，要求多轮对话需通过`chatId`严格隔离不同投标项目的上下文，避免跨项目数据混淆。其次，文档存在固定格式（如商务偏离表需明确标注偏离类型），提示词需强制指定响应格式，确保输出符合招标要求。另外，核心耗时环节为条款逐项响应与资质核对，多轮对话需支持逐步拆解招标条款，分阶段收集对应资质与报价数据，避免一次性输入过多信息导致上下文溢出。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的界面与参数规则：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `chatId` | 与当前投标项目绑定的唯一字符串 | 确保不同投标项目的对话上下文完全隔离，避免跨项目数据干扰 |
| `messages` | 限制单轮对话上下文为当前项目的前10条交互记录 | 适配单项目数据量有限的特征，防止上下文溢出导致模型混淆 |
| `variables` | 绑定当前项目的招标文件编号、资质库ID | 快速调用项目专属数据，无需重复输入基础信息 |
| 最大上下文 | 8000–12000 token | 匹配投标文件单项目的内容长度，避免截断关键响应条款 |
| 问题优化 | 开启 | 自动拆解招标条款的复杂要求，将模糊提问转换为可直接响应的具体字段 |
| 单次搜索上限 | 前3条 | 聚焦当前项目的核心资质与报价数据，避免无关信息干扰 |

## 容易做错的三处
- 出现`Cannot read properties of null (reading 'q')`报错，原因是未正确绑定`chatId`参数，导致系统无法识别当前对话的上下文标识。
- 选择工作流问题分类模型时未适配投标文件的专业术语，导致分类结果无法匹配招标条款的具体要求。
- 未正确配置`variables`参数，导致全局变量无法在多轮会话间保持，重复输入项目基础信息引发交互混乱。

## 怎么确认配好了
- 发起新的投标项目对话，检查对话启动时是否自动绑定专属`chatId`，无跨项目数据残留。
- 输入一条模糊的招标条款提问，确认系统自动优化为具体的响应字段要求，无需额外拆解。
- 测试多轮交互，检查项目专属的资质编号、报价明细等`variables`参数是否在后续对话中自动调用。
- 触发未绑定`chatId`的测试场景，验证是否出现预期的空字段报错，确认上下文隔离逻辑生效。
