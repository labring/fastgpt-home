# 游戏版号与出版申报的客户技术支持与售前答疑：多轮对话与提示词

## 这个品类的数据长什么样
本品类的数据主要来自国家新闻出版署办事服务平台、著作权登记文件、游戏包体材料及运营机构提交的备案资料。数据更新频率按单款游戏申报流程不定期推进，日常处理的文档包含申报请示文件、游戏申请表、著作权证明、审读报告四类核心材料。数据关联的主体为出版单位、游戏发行法务人员及项目负责人，所有内容围绕单款游戏的出版申报全流程生成。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
本品类的数据特征对多轮对话与提示词配置带来明确约束。首先，单款游戏的申报数据按流程独立更新，多轮对话需通过`chatId`绑定单款游戏的唯一标识，避免跨项目上下文混淆。其次，核心文档多为结构化申报材料，`messages`需完整保留每轮核对的历史记录，防止关键材料信息丢失。此外，数据来源分散且格式各异，提示词需引导对话系统精准提取不同文档的专属字段，如著作权证明编号、审读报告修改意见等，确保多轮对话的内容对齐申报需求。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本编写。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 会话ID绑定 | 绑定单款游戏的唯一标识 | 依据申报业务按款独立管理的特性，避免跨游戏上下文混淆，对应`chatId`配置 |
| 上下文窗口长度 | 8000–12000 字符 | 覆盖单款游戏全申报流程的多轮对话内容，匹配日常申报文档的总长度范围 |
| 变量绑定 | 绑定当前申报项目的核心字段 | 确保`variables`传递游戏名称、申报阶段等专属信息，提升对话精准度 |
| 单次搜索上限 | 前3条匹配结果 | 依据申报材料的唯一性要求，避免冗余结果干扰材料核对工作 |
| 超时阈值 | 60 秒 | 匹配申报业务的响应节奏，避免过长等待影响沟通效率 |
| 问题优化开关 | 开启 | 适配多轮对话中用户表述可能存在的模糊性，优化后提升知识库召回准确性 |

## 容易做错的三处
-  对话返回含换行符导致JSON请求失败：现象为接口返回`Unexpected end of JSON input`报错，原因是未对对话返回内容的换行符进行转义处理，未遵循JSON格式规范。
-  上传申报文件报错但文本对话正常：现象为文件上传环节触发系统报错，文本输入无异常，原因是未配置适配申报文件格式的解析规则，或未设置合理的文件大小阈值。
-  多轮对话响应速度偏慢：现象为两次对话间隔超过10秒，原因是未限制单次知识库召回的结果条数，或未优化上下文窗口的加载逻辑。

## 怎么确认配好了
-  发起单款游戏的多轮核对对话，检查会话ID是否绑定该游戏的唯一标识，确保上下文不与其他申报项目混淆。
-  输入包含换行符的申报文本片段，确认接口请求未触发JSON格式报错，返回内容正常解析。
-  上传单份申报文档，确认文件可正常解析并关联至当前对话上下文，无报错提示。
-  发起连续三轮的材料核对请求，检查响应速度符合预设阈值，无明显延迟。
