# 版本发布与Release Notes的客户技术支持与售前答疑：知识库检索与召回

## 这个品类的数据长什么样
该品类的核心数据为版本发布相关文档，通常由开源维护者、发布经理、文档维护者维护，日常产出包括Release Notes、变更日志、版本标签、发布检查单。数据来源为Git标签、合并记录、CI制品、Issue里程碑，更新节奏为每版本一次。单条数据通常包含版本号、变更分类、破坏性变更说明、关联CI制品哈希、对应里程碑Issue编号等字段，无统一固定单位，仅随版本内容变化。

## 这些特征在「知识库检索与召回」这一环带来什么约束
该品类的数据来源依赖代码仓库与CI流程，要求检索支持按版本号、哈希值等结构化字段精准匹配；更新频率为每版本一次，要求知识库支持增量同步，避免全量重建带来的性能损耗；变更归类环节耗时较长，意味着检索需要支持按变更类型过滤；出错后果为用户升级失败或社区误解，要求召回结果的准确性与完整性更高，不能遗漏破坏性变更等关键内容。同时，数据结构随版本变化较大，要求检索模型能够适配不同长度的变更描述文本。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | 过滤低相关性的变更条目，避免干扰用户的售前或支持查询 |
| `limit` | 前10条 | 适配Release Notes单版本条目数量，避免超出上下文窗口 |
| `searchMode` | 向量检索+关键词混合 | 兼顾版本号、哈希值等结构化字段的精准匹配，以及变更描述的语义理解 |
| `usingReRank` | 开启 | 对召回的变更条目按相关性重新排序，突出破坏性变更等关键内容 |
| `datasetSearchUsingExtensionQuery` | 开启 | 将用户的自然语言查询扩展为包含版本号、变更类型的复合查询，提升召回准确性 |
| `collectionIds` | 绑定对应版本的Release Notes知识库集合 | 缩小检索范围，避免检索到其他品类的文档数据 |

## 容易做错的三处
- 现象：新建知识库目录后直接弹出报错提示，原因：未将目录关联到正确的Release Notes集合，导致检索时无法匹配到对应版本的文档数据。
- 现象：点击知识库新增文件夹后显示provider报错，原因：未配置数据源的访问权限，无法拉取Git标签、合并记录等Release Notes的原始数据。
- 现象：通过API同步知识库集合时提示身份验证不通过，原因：未在API请求中指定正确的`collectionIds`参数，或使用的密钥未获得对应集合的访问权限。

## 怎么确认配好了
- 执行一次针对具体版本号的精准查询，核对返回结果是否包含对应版本的Release Notes条目。
- 触发一次包含“破坏性变更”关键词的查询，核对召回结果是否优先展示相关内容。
- 查看FastGPT v4.17.0的知识库更新日志，确认是否按照每版本的节奏同步了最新的Release Notes数据。
- 调用检索接口，核对返回结果的数量是否符合配置的`limit`取值。
