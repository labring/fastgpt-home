# 社区举报处理的客户技术支持与售前答疑：重排与混合检索

## 这个品类的数据长什么样
该品类的数据主要来自社区举报系统、待审核内容详情、用户历史举报记录与官方审核规则。数据更新频率分为日更与实时更新，日常处理依托的文档包括举报工单、处置进度记录、用户申诉单及标准化用户通知模板。数据字段包含举报ID、内容链接、举报类型、提交用户信息、审核状态等，无统一固定的单位字段，核心围绕单条举报事件的全流程信息展开。

## 这些特征在「重排与混合检索」这一环带来什么约束
单条举报事件的信息体量较小但关联性强，需快速匹配对应审核规则与历史处置案例，因此检索范围需限定在当前社区的举报相关数据集内，避免无关内容干扰。实时更新的举报数据要求检索链路支持低延迟响应，混合检索的多源召回需适配短周期数据同步的时效性要求。举报工单的结构化字段需与检索参数精准绑定，确保召回内容与当前举报的类型、场景高度匹配，同时需避免因召回过多非核心信息拉长处理耗时。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 重排开关 | 开启 | 社区举报处理需精准匹配违规判定规则与历史处置案例，重排可过滤低相关性召回结果，提升判断效率 |
| 相似度阈值 | 0.72–0.85 | 过滤与当前举报场景无关的历史工单与审核规则，确保召回内容的语义匹配度符合业务需求 |
| 单次召回上限 | 前10条 | 单条举报的关联信息体量有限，过多召回结果会拉长处理耗时，适配社区运营的快速响应要求 |
| 检索模式 | 混合检索 | 需同时召回结构化审核规则与非结构化的历史处置记录，覆盖举报处理的全维度参考依据 |
| 检索超时时间 | 8–10 秒 | 适配社区举报处理的实时性需求，避免因等待过长影响运营人员的处理节奏 |
| 重排结果截取量 | 前5条 | 聚焦最相关的处置参考，减少运营人员的信息筛选成本 |

## 容易做错的三处
- 现象：开启重排功能后出现`rerank error fastgpt | { message: { detail: '`类报错。原因：未正确配置重排模型的API调用路径或权限，或本地部署的重排模型未完成初始化加载。
- 现象：混合检索的响应时长超过10秒，超出单条举报处理的合理耗时范围。原因：未设置合理的单次召回上限与相似度阈值，召回了过多无关内容，或重排模型的调用超时参数配置过松。
- 现象：重排模型调用后GPU显存占用快速增长至6-7G且多GPU同时占用。原因：未限制单请求调用的重排文本长度，或未配置多GPU的负载均衡策略，导致资源被过度占用。

## 怎么确认配好了
- 查看检索链路的运行日志，确认重排模型的调用请求与响应正常，无报错信息。
- 模拟提交一条举报工单，核对混合检索与重排后的召回结果数量与相关性符合业务预期。
- 测试不同举报类型的检索请求，确认响应时长符合预设的实时性要求。
- 查看GPU资源监控面板，确认重排模型的显存占用处于合理区间，无异常飙升情况。
