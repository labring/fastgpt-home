# Issue分拣与响应的技术文档与接口问答：文档解析与分块

## 这个品类的数据长什么样
该品类的数据主要来自GitHub或Gitee的Issue、版本日志、用户环境信息、代码仓库。日常处理的文档包括Issue模板、标签规则、回复记录、问题复现说明。数据更新频率为日或周，单条数据包含问题描述、复现步骤、环境信息、关联标签等结构化字段，批量导入数据多为表格或批量导出的文本格式。

## 这些特征在「文档解析与分块」这一环带来什么约束
该品类的数据以问题类短文本和结构化批量数据为主，更新频率较高，要求解析与分块流程具备高效性。结构化字段如复现步骤、环境信息需要保留上下文关联，避免拆分破坏语义完整性。批量导入的表格数据需按行拆分，确保每条Issue记录独立可检索。同时，大体积的版本日志或批量Issue文件会带来解析耗时压力，需适配合理的超时与大小限制。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chunkSize` | 800–1200 字符 | 适配Issue文本的语义完整性，避免拆分破坏问题描述与复现步骤的关联 |
| `chunkSplitter` | 语义分割 | 适配该品类文档中存在的结构化段落，保留不同模块的上下文关联 |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | 兼容大体积的版本日志或批量Issue导出文件，满足日常导入需求 |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600 秒 | 应对批量Issue解析的耗时，避免超时中断解析流程 |
| `chunkSettingMode` | 手动配置 | 适配该品类的特定文档结构，灵活调整分块规则与分割逻辑 |

## 容易做错的三处
- 现象：Excel导入的批量Issue数据被合并为单个分块，单条记录未被独立拆分。原因：未将`chunkSplitter`配置为按行分割模式，或未启用自定义分隔符适配表格行格式。
- 现象：单份超过10MB的版本日志文件解析超时，解析任务失败。原因：`PARSE_FILE_TIMEOUT_SECONDS`取值低于实际解析耗时，或未调整`UPLOAD_FILE_MAX_SIZE`适配大文件。
- 现象：Issue的复现步骤被拆分为多个分块，检索时无法关联完整的复现流程。原因：`chunkSize`取值过小，导致单块无法覆盖完整的复现流程描述。

## 怎么确认配好了
- 上传单条标准Issue格式的测试文本，检查分块结果是否保留完整的问题描述与复现步骤。
- 上传预设的大体积测试文件，确认解析过程未触发超时错误。
- 导入Excel格式的批量Issue数据，验证每条记录被拆分为独立的分块单元。
- 查看FastGPT v4.17.0的后台解析日志，确认配置项的取值与预设一致。
