# Pull Request评审的技术文档与接口问答：向量模型与索引

## 这个品类的数据长什么样
这个品类的数据主要来自托管的代码仓库、配套CI流水线、关联Issue链接以及贡献者提交的变更内容。日常生成的文档结构包含PR说明文本、代码评审意见详情、CI执行结果日志、合并记录元数据。数据更新节奏通常为每日或每周，单次数据条目包含变更描述、文件变更清单、评审打分、测试通过率等字段，无固定统一的单位标准，随变更内容动态生成。

## 这些特征在「向量模型与索引」这一环带来什么约束
代码仓库的变更内容包含大量代码片段与技术术语，会对向量模型的分词适配性提出要求。CI结果日志存在大量结构化日志文本，索引构建时需区分结构化与非结构化数据的分块规则。数据更新节奏为日/周，索引增量更新的触发时机需匹配变更提交节奏，避免全量重建带来的资源消耗。PR评审的关联数据存在强关联关系，如同一PR的说明与评审意见需在索引中保留关联标识，确保检索时的上下文完整性。单次数据条目长度差异较大，从简短的合并说明到数百字符的评审意见，需适配可变长度的分块策略。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的向量索引模块编写。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配PR说明与评审意见的常见长度，避免单块内容过载 |
| 重叠长度 | 100–200 字符 | 保留相邻分块的上下文关联，减少跨块检索的信息断裂 |
| maxToken | 4096 token | 匹配多数商用向量模型的输入上限，适配长评审意见的嵌入处理 |
| 相似度阈值 | 0.75–0.85 | 过滤低关联的代码变更与评审意见，提升检索精准度 |
| 单次搜索上限 | 前 10 条 | 控制检索结果的返回规模，适配PR评审的快速上下文确认需求 |
| 增量更新触发 | 按提交时间戳 | 匹配数据日/周的更新节奏，避免全量索引重建的资源浪费 |

## 容易做错的三处
- 索引创建显示成功但页面无法加载：现象为集合创建接口返回成功标识，但前端页面始终显示索引未就绪。原因是增量更新触发逻辑未匹配PR提交的实际时间戳，导致索引文件未正确写入存储路径。
- 本地运行正常但Docker镜像部署后向量得分一致：现象为本地环境检索结果符合预期，容器化部署后所有文本的嵌入得分完全相同。原因是容器内未正确挂载向量模型的缓存目录，导致每次嵌入都重新拉取模型参数，出现特征丢失。
- 混合检索耗时超出预期：现象为单次检索耗时超过10秒，远超本地运行的耗时。原因是未限制单次搜索的返回条数，导致大量低关联结果参与重排流程，增加了计算开销。
- 索引构建停滞在最后一组：现象为索引构建进度条始终停留在最后一批数据，无报错信息。原因是分块长度设置过大，超出向量模型的处理上限，导致最后一组数据无法完成嵌入。

## 怎么确认配好了
- 查看向量嵌入日志，确认单条数据的分块数量符合预期，无异常报错信息。
- 执行模拟检索，输入PR说明文本，检查返回结果是否包含关联的评审意见与代码变更内容。
- 对比全量索引与增量更新后的索引条目数量，确认更新节奏与数据提交节奏匹配。
- 测试不同长度的PR文本，确认嵌入结果无明显的特征丢失或截断情况。
