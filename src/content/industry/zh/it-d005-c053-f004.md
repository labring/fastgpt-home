# 客户需求池管理的技术文档与接口问答：向量模型与索引

## 这个品类的数据长什么样
该品类的核心使用主体为产品运营、客户成功与产品经理，数据主要来自工单系统、客户访谈记录、CRM系统与产品路线图文档。日常处理的文档包括需求池清单、需求评估表、客户反馈记录及版本规划说明，数据更新节奏为每周或每产品版本更新一次。文档通常包含需求编号、客户标识、需求描述、优先级、评估成本、关联版本等字段，格式以结构化或半结构化文本为主，无统一强制规范。

## 这些特征在「向量模型与索引」这一环带来什么约束
该品类的数据来源分散且更新周期不固定，要求向量索引支持增量更新以适配周或版本级的同步节奏；文档类型多样且字段不统一，需兼容半结构化与非结构化文本的分块逻辑；核心业务环节依赖重复需求归并，对向量模型的相似度召回精度有明确要求；字段包含客户标识与需求优先级，索引需保留字段关联能力以支持后续定向筛选。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配需求池文档中单条需求描述的常见长度，避免块内关键信息割裂 |
| 重叠长度 | 100–200 字符 | 保留跨块的需求上下文与关联字段信息，防止评估逻辑被截断 |
| 相似度阈值 | 0.75–0.85 | 用于重复需求归并，平衡误判与漏判的业务风险 |
| 单次搜索上限 | 前 20 条 | 覆盖同类型需求的常见聚集数量，避免遗漏潜在重复项 |
| `maxToken` | 4096 token | 适配主流嵌入模型的输入长度限制，保障完整需求文本的嵌入效果 |
| `defaultToken` | 按实测标定 | 处理无明确字段的零散客户反馈文本，补充基础上下文信息 |

## 容易做错的三处
- 配置嵌入模型渠道后出现无可用渠道报错，原因是未在系统中正确绑定对应模型的服务地址或密钥，或渠道类型选择与实际部署的模型不匹配。
- 知识库搜索耗时过长，原因是分块长度设置过大导致单块嵌入计算量增加，或单次搜索上限设置过高超出硬件处理能力，如RTX2070显卡需控制单批次处理块数。
- 问答拆分处理结果不符合预期，原因是混淆了向量模型与大语言模型的分工，误将向量模型用于语义分句拆分，或未配置合适的分块重叠长度导致上下文断裂。

## 怎么确认配好了
- 导入两条内容高度相似的需求样本，验证系统是否能按设置的相似度阈值匹配到对应条目，检查匹配结果的排序合理性。
- 查看系统嵌入任务的运行日志，确认`maxToken`设置未触发模型输入长度超限报错，且嵌入耗时符合硬件适配的预期范围。
- 手动触发一次增量同步任务，验证系统是否能按周或版本级的更新节奏同步最新的需求池数据，无遗漏或重复同步的条目。
- 测试包含客户标识字段的搜索请求，确认系统是否能按字段筛选需求池内的相关条目，保留字段关联的检索能力。
