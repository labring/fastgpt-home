# 容器平台运维的技术文档与接口问答：引用来源与溯源

## 这个品类的数据长什么样
容器平台运维的核心数据来源于Kubernetes API、镜像仓库、监控系统与CI流水线，更新频率为每日或每一次集群变更。日常使用的文档包括集群变更单、命名空间配额表、部署记录与故障报告，数据字段包含集群ID、命名空间、Pod状态、镜像版本、资源配额阈值等，单位涉及核、GiB、时间戳与操作人标识，单条数据长度差异较大，从数百字符到数千字符不等。

## 这些特征在「引用来源与溯源」这一环带来什么约束
多源异构的数据来源要求溯源环节需精准匹配数据的原始来源标识，避免跨集群、跨仓库的数据混淆。高频更新的特性要求溯源信息包含准确的时间戳与版本号，确保引用的是最新生效的配置与记录。固定字段结构的文档需在溯源时关联特定字段（如命名空间、Pod名称），方便快速定位异常来源。数据长度差异大的特点要求控制引用总量，防止上下文溢出影响大模型响应，同时避免因引用不足导致排查依据缺失。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `quoteMaxToken` | 8000–12000 token | 容器平台运维单条数据通常占300-800 token，该取值可覆盖5-10条典型数据的拼接需求，适配多源数据整合场景 |
| `responseData` | with_source_meta | 需保留Kubernetes API返回的资源版本、更新时间等核心溯源字段，确保引用可追溯至原始集群资源 |
| `detail` | true | 需返回引用数据的完整元信息，用于人工核对与异常排查时快速定位问题根源 |
| 单次召回条数 | 前10条 | 容器平台运维数据条目较多，该取值可控制上下文长度，同时覆盖主要异常排查与配额调整场景 |
| 文件编码 | UTF-8 | 容器平台运维的配置文件与日志默认采用UTF-8编码，避免导入时出现乱码 |

## 容易做错的三处
- 上传CSV格式的运维文档后显示乱码，调用相关接口时出现异常。原因：未指定文件编码为UTF-8，容器平台运维的配置文件与日志默认使用UTF-8编码，未正确配置时会导致解析失败。
- 设置`quoteMaxToken`为3000后，大模型未收到上下文数据。原因：配置的token上限过低，容器平台运维的多源数据拼接后总token数超过设置值，导致上下文被完全截断。
- 配置HTTP响应数据作为引用后无效果。原因：未将响应数据转换为结构化格式，容器平台运维的API响应通常为JSON格式，需提取指定字段后再导入知识库。

## 怎么确认配好了
- 上传一条典型的集群变更单文档，查看知识库的引用预览，确认显示的字段包含集群ID、变更时间与操作人等溯源信息。
- 调用FastGPT v4.17.0的相关接口测试，检查返回的`responseData`字段是否包含资源版本、更新时间等元数据。
- 调整`quoteMaxToken`的取值，观察上下文拼接后的总长度是否符合预期，无明显截断或溢出情况。
- 模拟Pod异常排查场景，验证引用的故障报告数据是否能准确关联到对应Pod的监控指标与部署记录。
