# 广告账户开户审核的技术文档与接口问答：向量模型与索引

## 这个品类的数据长什么样
该品类的数据主要来自广告平台后台、国家企业信用信息公示系统、客户提交的开户申请材料、行业准入规则。日常处理的文档包括开户申请单、营业执照扫描件、对应行业资质文件、历史开户审核记录。数据更新节奏为每日批量同步或随单次开户申请触发更新，字段包含主体名称、统一社会信用代码、投放行业类目、审核状态、补正需求等，无统一固定的单位属性，仅部分资质文件存在格式要求。

## 这些特征在「向量模型与索引」这一环带来什么约束
多来源多格式的数据会要求向量分块适配结构化的开户申请字段、半结构化的资质扫描件文本与非结构化的审核记录内容。按申请触发的实时更新与每日批量更新并存的节奏，需要索引支持增量更新与全量重建的灵活切换。主体名称、统一社会信用代码这类核心标识字段的唯一性要求，需要在索引构建时加入去重校验逻辑。不同文档的长度差异较大，从几十字符的审核状态到数千字符的行业规则文本，需要分块参数适配不同长度的文本片段。

以下配置适用于 FastGPT v4.17.0。
## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配营业执照、行业资质等文档的常见文本长度，避免单块内容过载 |
| 重叠长度 | 100–200 字符 | 保证跨分块的上下文连贯性，覆盖资质字段的跨块关联信息 |
| 相似度阈值 | 0.75–0.85 | 匹配主体资质核验的严格程度，过滤低相关的历史审核记录 |
| 单次搜索上限 | 前 20 条 | 适配单开户申请的审核参考数据量，避免冗余信息干扰判断 |
| `maxToken` | 4096 | 适配大模型上下文窗口，承载多份资质文档的向量拼接内容 |
| `defaultToken` | 按实测标定 | 适配不同格式文档的 token 转换精度，平衡召回效率与准确性 |

## 容易做错的三处
-  配置外部索引模型后出现接口超时报错。原因是未调整`defaultToken`适配外部模型的请求限制，导致单次请求超出模型支持的 token 上限。
-  从 PGSQL 迁移到 Zilliz 后出现资质字段召回缺失。原因是迁移时未保留主体统一社会信用代码的索引映射，导致核心字段的向量匹配失效。
-  开启重排模型后审核结果无明显变化。原因是未设置合理的相似度阈值，导致重排模型仅处理了极少量召回结果，无法体现优化效果。

## 怎么确认配好了
-  上传一份标准营业执照文档，检查分块后的文本片段是否符合设定的长度区间。
-  发起一次模拟开户申请的检索，确认返回的历史审核记录数量符合单次搜索上限的配置。
-  查看向量索引的更新日志，验证实时申请触发的增量更新是否正常完成。
-  调用接口测试`maxToken`参数，确认拼接后的向量文本未超出模型支持的最大长度。
