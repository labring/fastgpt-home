# 游戏版号与出版申报的技术文档与接口问答：向量模型与索引

## 这个品类的数据长什么样
该品类的数据来源包括国家新闻出版署办事服务平台、著作权登记系统、游戏包体元数据、运营机构备案资料。日常处理的文档包含申报请示文件、游戏申请表、著作权证明、审读报告四类，每份文档包含申报主体、作品名称、著作权人、审核意见等结构化字段。数据更新频率为每款游戏不定期，随单款游戏的申报进度触发新增或修改，无固定批量更新周期。文档多为结构化文本，少量关联包体的元数据字段，整体数据体量随申报项目数量线性增长。

## 这些特征在「向量模型与索引」这一环带来什么约束
该品类的数据特征对向量模型与索引环节带来多项约束：数据来源分散且更新无固定周期，要求索引支持增量重建与全量重建两种模式，适配单款游戏申报的临时新增需求；文档包含多类结构化字段，分块时需避免跨字段拆分，保证检索时的字段关联性；每份申报材料的审批关联性强，检索结果需精准匹配字段内容，避免无关结果干扰审核流程；出错后果直接影响审批进度，要求索引的稳定性与容错能力达标，避免因索引异常导致申报流程中断。在FastGPT v4.17.0中，需针对这些约束调整索引的分块、重建与检索配置。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配申报类文档的字段长度，避免拆分跨字段内容 |
| 重叠长度 | 100–150 字符 | 保证分块间的上下文连贯性，覆盖字段间的关联信息 |
| `maxToken` | 4096 token | 适配主流向量模型的输入上限，兼容单份申报文档的分块内容 |
| `defaultToken` | 1024 token | 匹配单条基础申报字段的平均长度，减少无效截断 |
| 相似度阈值 | 0.75–0.85 | 按实测标定，过滤低匹配度的无关材料，保证审批检索的精准性 |
| 单次搜索上限 | 前 10 条 | 符合审批核对的常规需求，避免过多结果增加人工核对成本 |

## 容易做错的三处
- 执行全量知识库索引重建时出现服务器读写撑爆，每日定时发生。原因是未按申报批次拆分重建任务，全量处理多批次的游戏版号申报材料，导致内存与磁盘IO占用过高。
- 升级到FastGPT v4.17.0后，调用voyage索引接口报400状态码且无返回体。原因是未适配新版索引的字段校验规则，未将游戏申请表的必填字段加入索引映射配置。
- 上传著作权证明文件时，偶尔卡在1组索引或2组索引的进度中。原因是本地部署使用m3e-large模型时，未限制单批次处理的文件数量，并发请求过多导致内存溢出。

## 怎么确认配好了
- 上传单份游戏申请表文档，查看分块后的片段是否完整覆盖申请表的所有字段，无跨文档或跨字段的拆分情况。
- 发起审读报告的关键词检索，检查返回结果的相似度分值是否落在预设的阈值区间内。
- 执行全量索引重建任务，观察服务器的CPU、内存与磁盘IO占用未超过预设阈值。
- 调用接口创建知识库向量，检查返回的索引ID与文档元数据是否匹配，无异常空字段。
