# 游戏版号与出版申报的技术文档与接口问答：知识库检索与召回

## 这个品类的数据长什么样
本品类的数据来源包括国家新闻出版署办事服务文件、著作权登记证明、游戏包体及运营机构资料。文档类型涵盖申报请示文件、游戏申请表、著作权证明、审读报告等，单款游戏的申报材料包含申报主体、游戏名称、著作权编号、审读意见等固定字段。数据更新频率为每款游戏申报周期不定期，单次申报的材料集合规模随项目复杂度有所差异，无固定批量更新节奏。

## 这些特征在「知识库检索与召回」这一环带来什么约束
数据来源分散导致不同文档格式存在差异，需适配多源数据的统一检索逻辑；不定期更新要求配置增量同步机制，避免旧数据覆盖或新数据遗漏。单款游戏的申报材料存在跨文档关联，检索需精准匹配当前项目的专属材料，防止跨游戏的无关结果干扰。出错后果直接关联审批进度与运营资格，要求检索结果具备高置信度，同时需控制检索耗时以适配材料核对的高频业务场景。

## 配置怎么定
本文档基于FastGPT v4.17.0版本编写，具体配置项及建议如下：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `similarity` | 0.75–0.85 | 政务文档语义严谨，需过滤低相关结果，避免误召回非对应游戏的申报材料 |
| `limit` | 前10条 | 单款游戏申报材料数量有限，过多结果会增加上下文处理负担，适配业务场景的文档规模 |
| `usingReRank` | 开启 | 政务文档存在大量近似表述，重排可提升高相关结果的排序优先级，适配审读报告等长文本的语义匹配 |
| `datasetSearchUsingExtensionQuery` | 开启 | 申报文档常包含简称、官方全称混用，扩展查询可覆盖更多同义表述，提升召回完整性 |
| `collectionIds` | 绑定对应游戏申报专属数据集 | 避免跨品类数据干扰，确保检索范围仅覆盖当前项目的申报材料 |
| `searchMode` | 语义检索模式 | 政务文档的关键词匹配易受格式干扰，语义检索可精准匹配申报需求的核心语义 |

## 容易做错的三处
- 现象：检索单份申报材料耗时超过30秒。原因：未限定`collectionIds`，检索范围覆盖了全量数据集，导致召回数据量过大。
- 现象：多知识库绑定后仅返回单个知识库的答案。原因：未配置多结果合并逻辑，或未启用多知识库权重分配规则。
- 现象：检索结果出现大量与当前游戏无关的申报材料。原因：`similarity`阈值设置过低，导致低相关结果被召回，违反政务文档的严谨性要求。

## 怎么确认配好了
- 提交包含游戏名称与审读关键词的测试查询，验证检索耗时符合业务预期，确认`collectionIds`限定了正确的专属数据集。
- 测试绑定两个及以上知识库的场景，确认多个知识库的相关结果均被返回，且排序符合预设的权重规则。
- 调整`similarity`参数，验证高相关结果的排序优先级变化，确认`usingReRank`功能正常生效。
- 提交包含游戏简称的查询，验证`datasetSearchUsingExtensionQuery`是否覆盖了同义表述的召回结果。
