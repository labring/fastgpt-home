# 版本发布与Release Notes的技术文档与接口问答：向量模型与索引

## 这个品类的数据长什么样
该品类的数据主要来自Git仓库标签、合并提交记录、CI/CD流程生成的制品包、项目Issue里程碑。日常产出的文档包括版本发布说明、变更日志、版本标签元数据、发布检查单。数据结构包含版本号、变更归类标签、破坏性变更说明、关联提交哈希、制品校验值等字段。更新节奏为每发布一个正式版本即生成并更新一次完整数据集，无日常增量更新。

## 这些特征在「向量模型与索引」这一环带来什么约束
该品类的数据更新节奏为每版本一次，无需高频增量索引，可采用全量重建的方式维护索引。数据包含结构化字段与自然语言描述，需同时支持按结构化字段过滤与语义检索。单条数据长度差异显著，短至版本号等极简元数据，长至数千字符的变更汇总，需适配多长度文本的分块处理。部分字段如破坏性变更说明对检索置信度要求较高，需调整向量召回的权重规则。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配Release Notes中变更汇总的平均长度，避免单块内容过载 |
| 重叠长度 | 100–200 字符 | 保留跨块变更的上下文关联，避免语义断裂 |
| `defaultToken` | 2000 | 适配单条向量请求的最大token限制，避免截断关键变更信息 |
| `maxToken` | 4096 | 匹配多数开源嵌入模型的输入token上限，保证检索内容完整 |
| 相似度阈值 | 0.72–0.78 | 平衡检索准确率与召回率，适配版本变更描述的语义相似度分布 |
| 单次召回上限 | 前 8 条 | 单版本数据量通常有限，过多召回会增加上下文处理负担 |

## 容易做错的三处
- 现象：向量模型接入后提示无可用渠道，界面显示配置异常。原因：未在对应分组中开启指定嵌入模型的访问权限，或API密钥未绑定至当前使用的分组。
- 现象：检索结果条数与预期不符，仅返回少量匹配内容。原因：分块长度设置过大，导致单条数据被拆分为过少块，或相似度阈值设置过高，过滤了有效匹配结果。
- 现象：检索后重排环节耗时过长。原因：未限制单次召回的结果条数，或分块设置过小导致总块数过多，加重了重排模型的计算负担。

## 怎么确认配好了
- 在FastGPT v4.17.0版本的系统中，上传单条版本变更日志样本，检查向量生成状态是否正常，无报错提示。
- 发起包含版本号关键词的检索，确认返回结果包含对应版本的变更内容。
- 查看向量索引的更新日志，确认全量重建任务已按版本更新节奏完成。
- 测试不同长度的变更文本输入，确认`maxToken`设置未触发截断报错。
