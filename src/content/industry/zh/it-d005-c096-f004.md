# 社区举报处理的技术文档与接口问答：向量模型与索引

## 这个品类的数据长什么样
该品类的数据主要来自社区举报系统、待审核内容详情、用户历史举报记录与官方审核规则。日常处理的文档包括举报工单、处置记录、申诉单据与用户通知模板，数据字段包含举报标识、内容关联ID、举报类型、审核状态等。数据更新节奏为日更或实时推送，单条数据体量较小但单批次处理量随社区活跃程度波动，需适配高频次的索引更新需求。

## 这些特征在「向量模型与索引」这一环带来什么约束
社区举报处理的数据来源分散，需对接多系统接口拉取举报工单、待审核内容详情、用户历史记录与审核规则，要求向量索引支持多数据源的统一接入。数据以日更或实时频率更新，需适配高频次的索引同步需求，避免全量重建带来的资源消耗。单条数据体量较小但单批次处理量波动明显，需控制索引分片大小以提升检索效率。举报内容与审核规则涉及敏感信息，向量存储需适配隐私加密要求。不同举报类型的语义特征差异明显，且举报有效性判断依赖语义匹配结果，需按类别拆分索引以优化召回精度，减少无效检索耗时。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 匹配举报工单与内容详情的单段有效信息长度，避免块内举报理由、证据信息断裂 |
| 重叠长度 | 100–200 字符 | 保留块间上下文关联，防止跨块的举报关联内容被拆分丢失 |
| `maxToken` | 4000–6000 token | 适配举报处理的多字段拼接上下文，避免截断关键审核规则与申诉内容 |
| 相似度阈值 | 0.75–0.85 | 平衡误判与漏判，适配举报内容的语义匹配精度要求 |
| 单次搜索上限 | 前 10 条 | 控制返回的历史举报与审核记录数量，避免上下文过载影响判定效率 |
| `defaultToken` | 按实测标定 | 适配私有化部署的重排模型输入限制，兼容不同硬件环境的 token 承载能力 |

## 容易做错的三处
- 现象：调用接口时返回“重排模型参数不兼容”报错，状态码为 400。原因：未在配置中指定`defaultToken`的适配值，或未匹配`maxToken`的长度限制，导致私有化重排模型无法正常接收输入数据。
- 现象：搜索返回的历史举报记录与当前待审核内容关联度极低，结果条数不符合预期。原因：相似度阈值设置过高或过低，未适配不同举报类型的语义特征差异。
- 现象：索引更新延迟超过1小时，无法实时同步最新的审核规则。原因：未开启增量索引模式，仍使用全量索引更新流程，导致资源占用过高，无法适配实时更新需求。

## 怎么确认配好了
- 查看 FastGPT v4.17.0 后台的向量索引管理页面，确认分块长度与重叠长度的设置与配置项一致。
- 输入一条测试举报内容的关键词，检索历史举报记录，核对返回结果的数量与关联度符合阈值要求。
- 提交一条临时审核规则更新，检查索引更新日志是否显示增量同步完成。
- 调用私有化重排模型的测试接口，确认能正常接收向量召回的结果并完成排序。
