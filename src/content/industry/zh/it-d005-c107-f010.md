# 账号封禁与申诉复核的技术文档与接口问答：引用来源与溯源

## 这个品类的数据长什么样
该细分品类的核心数据来自风控系统、审核记录、用户行为日志、举报证据四类来源，更新节奏为日更或实时同步。日常产出的文档包含封禁记录、申诉材料、复核意见、用户通知四类结构，字段通常包含账号唯一标识、违规类型编码、处置时间戳、申诉状态、关联证据ID等，无统一固定的单位体系，仅以字符、时间戳、数字标识各字段内容。

## 这些特征在「引用来源与溯源」这一环带来什么约束
多源数据的关联要求溯源环节必须精准匹配账号ID、证据ID等唯一标识，避免跨账号的错误关联。实时或日更的更新节奏要求溯源接口支持动态拉取最新数据，无法依赖静态缓存。文档结构的多样性要求溯源配置需适配不同类型的业务文档，不能采用统一的分块规则。最耗时的违规证据核对环节，要求溯源结果需直接关联原始证据，减少大模型的二次加工步骤。同时，误封、违规账号回流等出错后果，要求溯源结果必须具备可追溯的原始数据源，确保每一次引用都可核对。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 单次搜索上限 | 前3条 | 匹配账号封禁场景下核心证据的数量，避免冗余信息干扰复核判断 |
| 最大上下文长度 | 800–1200 字符 | 适配封禁记录、申诉材料的单条文档常规长度 |
| `quoteMaxToken` | 4000 token | 控制单次溯源的token消耗，避免超出大模型输入上限 |
| 引用来源开关 | 开启 | 强制关联风控系统、审核记录等原始数据源，避免大模型生成虚假内容 |
| `detail` | 完整模式 | 展示账号ID、违规时间、处置状态等核心业务字段，满足复核需求 |
| `responseData` | 原始格式 | 保留原始文档的排版与字段，确保溯源结果可直接核对 |

## 容易做错的三处
- 现象：AI输出的知识库原文被添加修饰性内容，未保留原始格式。原因：未开启强制引用原始内容的配置项，默认启用了大模型的摘要优化逻辑。
- 现象：溯源结果的条数与配置的单次搜索上限不符，出现条数过少或过多的情况。原因：未考虑系统召回的实际阈值，设置的上限超出了数据源的可返回范围。
- 现象：接口返回超时错误。原因：`quoteMaxToken`设置过大，导致大模型处理时间超出系统限制。

## 怎么确认配好了
- 发起一次针对特定账号的封禁申诉查询，检查返回结果中是否包含原始文档的完整内容，无额外的修饰或改写。
- 查看溯源结果的条目数，确认与配置的单次搜索上限一致，无异常的条数偏差。
- 检查返回结果中是否包含账号ID、违规类型等核心业务字段，匹配预设的业务数据结构。
- 查看接口返回的`responseData`与`detail`字段，确认包含原始数据源的关联信息与完整业务字段。
- 在FastGPT v4.17.0版本的调试面板中，触发一次测试查询，查看引用来源的弹窗是否正确展示原始文档链接与内容。
