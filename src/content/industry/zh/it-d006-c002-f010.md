# IT服务台工单处理的测试用例与缺陷分析：引用来源与溯源

## 这个品类的数据长什么样
本品类数据来源于企业ITSM系统、电话或在线聊天记录、内部资产系统与官方知识库，更新节奏为日更或实时。日常生成的文档包含服务请求单、事件工单、处理记录、用户满意度表，字段涵盖工单唯一标识、提交时间、处理人、问题分类、响应时长、用户评分等，数据结构相对规整，无过多自定义非标准字段。

## 这些特征在「引用来源与溯源」这一环带来什么约束
数据来源分散且更新节奏存在差异，实时更新的聊天记录与日更的工单数据需匹配不同的索引刷新频率，避免溯源时出现数据过期的情况。文档字段相对固定但覆盖多系统，引用溯源需关联工单ID、处理人等跨系统唯一标识，否则无法准确匹配原始工单条目。不同文档的长度差异明显，短对话记录与长处理报告需适配不同的内容长度限制，防止溯源时丢失关键上下文信息。

本文适配FastGPT v4.17.0版本。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | 匹配IT服务台工单的平均内容长度，确保溯源时包含完整的上下文信息 |
| 单次召回上限 | 前5条 | 覆盖单工单关联的多类文档，避免遗漏关键处理记录 |
| `responseData` | 返回工单ID、提交时间、处理人字段 | 聚焦跨系统溯源所需的唯一标识字段，简化下游匹配逻辑 |
| `detail` | 开启 | 允许返回原始文档的完整内容，便于测试用例验证排障流程 |
| 重排开关 | 按实测标定 | 针对长聊天记录优化召回顺序，提升溯源准确性 |
| 上下文缓存时长 | 24小时 | 匹配日更类工单的更新节奏，避免溯源时使用过期数据 |

## 容易做错的三处
- 仅返回引用标识而无具体内容，现象为对话界面仅展示工单ID链接，无原始处理记录详情，原因是`detail`参数未开启或配置为关闭状态。
- 检索结果与工单不匹配，现象为召回的文档关联错误的工单ID，原因是`responseData`配置未包含唯一标识字段，导致溯源匹配失败。
- 工作流调用时报错，现象为HTTP请求处理后调用AI对话环节返回参数错误，原因是`responseData`返回的字段格式不符合FastGPT要求的输入规范。

## 怎么确认配好了
- 提交一条模拟IT服务台工单，触发检索与溯源流程，核对返回的引用是否包含正确的工单唯一标识。
- 查看检索结果的内容长度，确认`quoteMaxToken`的取值覆盖了目标文档的核心上下文。
- 检查工作流的参数传递，确认`responseData`返回的字段符合下游AI对话环节的输入要求。
- 模拟不同更新频率的文档触发检索，确认溯源结果与文档的最新状态一致。
