# IT采购与供应商管理的测试用例与缺陷分析：引用来源与溯源

## 这个品类的数据长什么样
这个品类的数据通常来自采购系统、供应商报价、预算表、合同系统。日常处理的文档包括采购申请、比价记录、合同、验收单，各文档包含采购单号、供应商名称、报价金额、合同条款、验收日期等字段，单位涵盖元、天等。数据更新节奏为每单或每月，单条采购相关数据结构相对固定，但多源数据的关联关系较为复杂，不同文档间的关联依赖于采购单号等统一标识。本品类服务企业内部长期采购和供应商关系，与供应商与设备到货管理的侧重方向不同。

## 这些特征在「引用来源与溯源」这一环带来什么约束
多源数据的特性要求溯源环节能够关联采购系统、供应商报价等不同来源的文档，因此需要配置能够返回元数据的参数。按单或每月的更新节奏，要求引用的时效性匹配数据更新周期，避免引用过期的比价记录或合同内容。不同文档的字段差异，要求溯源时能够区分采购申请与合同条款的不同权重，确保引用的准确性。同时，采购场景的出错后果直接关联企业预算与合规风险，因此溯源环节的准确性要求较高，需避免错误关联来源或截断关键内容。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本制定：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `quoteMaxToken` | `800–1200 token` | 采购相关文档的单条内容token数通常处于该区间，避免截断关键合同条款或报价细节 |
| `responseData` | `包含来源文档元数据` | 需返回采购单号、供应商名称等元数据，实现多源数据的关联溯源 |
| `detail` | `开启` | 需展示具体的比价记录、合同条款等细节，匹配采购场景的溯源需求 |
| 单次搜索上限 | `前6条` | IT采购的关联数据通常不超过6条，过多会干扰上下文理解 |
| 引用标记格式 | `仅显示来源标识` | 避免输出中出现冗余的标记字样，符合业务场景的输出要求 |

## 容易做错的三处
-  输出内容中出现“引用标记：［1］”字样。原因是未调整引用标记的显式输出配置，直接将系统默认的标记格式输出到了正文。
-  溯源结果无法关联到具体的采购合同或验收单。原因是未配置`responseData`参数返回元数据，仅返回文本内容无法匹配来源文档的唯一标识。
-  生成的引用内容截断了关键的采购条款。原因是`quoteMaxToken`取值过小，无法容纳完整的采购条款或报价细节。

## 怎么确认配好了
-  发起包含采购申请、比价记录的测试查询，检查输出是否包含清晰的来源标识，无冗余的标记字样。
-  查看溯源结果的元数据字段，确认包含采购单号、供应商名称等关键信息。
-  核对引用内容的长度，确认完整覆盖了采购条款或报价细节，无截断情况。
-  模拟单条采购订单的查询，确认返回的溯源结果数量符合配置的单次搜索上限。
