# Issue分拣与响应的测试用例与缺陷分析：模型接入与配置

## 这个品类的数据长什么样
该品类的核心数据来源于GitHub或Gitee Issue、代码仓库版本日志、用户反馈的环境信息与问题复现说明。日常维护文档包含Issue提交模板、标签规则库、历史回复记录等内容。数据更新频率以日或周为单位，单次数据体量从单条数十字符的简单提问到数百字符的完整复现步骤不等。典型使用者为开源项目维护者、社区运营人员与核心贡献者，需依托这些数据完成问题分类、优先级标记与响应分配。

## 这些特征在「模型接入与配置」这一环带来什么约束
该品类的数据以非结构化自然语言文本为主，且格式差异较大，要求模型具备灵活的文本理解与分类能力。数据更新频率与社区活跃程度绑定，峰值时段的调用量会出现波动，需配置适配的并发与超时参数。数据中包含复现步骤、标签字段等关键信息，模型需准确识别并映射到预设的分拣规则中。同时，错误处理需覆盖网络连接异常、参数格式错误等场景，避免因单条Issue处理失败导致整体流程积压。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000-12000 token | 匹配Issue包含的完整复现步骤、标签说明与历史回复等上下文内容，避免关键信息被截断 |
| `maxTokens` | 2000-3000 token | 适配分拣响应的输出长度需求，兼顾分类结果与补充说明的内容量 |
| `temperature` | 0.3-0.5 | 保持分类结果的稳定性，减少随机波动，符合Issue分拣的标准化规则要求 |
| `AIPROXY_API_ENDPOINT` | 按部署环境填写AI Proxy服务的根地址，例如 http://aiproxy:3000 | 适配Docker或本地部署的网络配置，确保AI Proxy服务调用链路正常，请勿附加 /v1 或 /chat/completions 路径 |
| `AIPROXY_API_TOKEN` | 填写与AI Proxy服务端配置一致的非空管理员Token | 完成AI Proxy服务的身份验证，确保调用权限合法 |

## 容易做错的三处
- 现象：调用模型时返回连接超时错误，日志显示`ECONNREFUSED`状态码；排查项：检查`AIPROXY_API_ENDPOINT`是否配置为AI Proxy服务的正确根地址，`AIPROXY_API_TOKEN`是否配置正确且非空，部署环境是否可访问AI Proxy服务端点。
- 现象：在Docker部署环境中添加火山引擎DeepSeek-R1模型后，渠道列表中无对应条目；原因：未在配置文件中正确绑定模型标识与代理端点，或部署后未重启服务使配置生效。
- 现象：本地部署更新FastGPT v4.17.0后，上传测试用例附件后模型无响应；排查项：检查`AIPROXY_API_ENDPOINT`与`AIPROXY_API_TOKEN`是否已正确配置，`maxContext`参数是否符合要求，部署服务是否已重启。

## 怎么确认配好了
- 手动提交一条模拟GitHub Issue，包含复现步骤与缺陷描述，查看模型返回的分类标签是否符合预设的标签规则。
- 检查服务端部署配置的`AIPROXY_API_ENDPOINT`与`AIPROXY_API_TOKEN`是否已正确配置，格式符合AI Proxy服务的要求。
- 查看系统运行日志，确认连续10分钟内无模型调用失败的报错记录。
- 上传一份标准测试用例文档，验证模型能否正确提取复现步骤与缺陷字段，并生成对应的分拣建议。
