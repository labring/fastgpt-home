# Pull Request评审的测试用例与缺陷分析：工作流编排

## 这个品类的数据长什么样
本品类的典型使用主体为项目维护者、模块Owner与贡献者，数据主要来自代码仓库、CI流水线、Issue链接与贡献者提交记录。日常关联文档包括PR说明、代码评审意见、CI执行结果与合并操作记录。数据更新频率通常为日或周，核心字段包含PR变更范围、关联Issue编号、CI通过率、评审意见条数、贡献者提交信息等，用于支撑测试用例与缺陷分析的工作流编排。

## 这些特征在「工作流编排」这一环带来什么约束
数据来源分散导致工作流需配置跨系统节点拉取信息，避免手动汇总的误差。更新频率与触发时机绑定，需适配PR提交、CI完成等事件节点，或按日/周定时同步数据。文档格式不统一要求配置变量提取规则，标准化核心字段用于测试用例匹配。核心耗时环节需嵌入自动化校验节点，减少人工重复操作。缺陷风险需配置失败告警与回滚分支，避免影响主干稳定性。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 触发时机 | 按PR提交、CI完成事件触发，辅以日度全量同步 | 匹配PR评审的核心时间节点，兼顾遗漏场景的补全 |
| `variables` | 提取PR标题、变更文件列表、CI通过率、关联Issue编号 | 覆盖测试用例与缺陷分析的核心字段，支撑自动化校验 |
| 评审意见校验规则 | 按评审意见条数≥3条或CI通过率<90%触发校验 | 聚焦高风险变更，减少无效校验开销 |
| 节点超时设置 | 600秒 | 适配代码拉取、CI结果拉取的常规耗时，避免长时间阻塞工作流 |
| 失败处理策略 | 触发告警并暂停合并流程 | 对应出错后果，防止缺陷流入主干分支 |
| `nodeId` | 绑定代码仓库、CI流水线的对应节点ID | 精准拉取对应数据源的信息，避免数据混淆 |

## 容易做错的三处
- 创建工作流模板后进入编辑界面报错，原因是未正确绑定代码仓库或CI流水线的数据源节点，导致基础配置缺失。
- 在其他工作流引用插件后点击输入框报错，原因是`variables`配置未包含插件所需的必填字段，参数映射不完整。
- 本地部署后进入工作流提示Cannot read properties of undefined，原因是`nodeId`配置错误或部署包的配置文件未正确加载数据源关联信息。

## 怎么确认配好了
- 手动触发一次工作流，查看拉取的PR数据是否包含变更文件列表、CI结果等核心字段。
- 模拟高风险PR场景，确认校验节点是否正常触发。
- 检查告警配置，触发失败场景后确认告警通知是否正常推送。
- 核对`nodeId`与数据源的绑定关系，确认拉取的数据来源与配置一致。
