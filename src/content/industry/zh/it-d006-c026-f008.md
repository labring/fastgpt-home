# 关卡内容制作的测试用例与缺陷分析：工作流编排

## 这个品类的数据长什么样
关卡内容制作的日常文档包含关卡设计稿、资源需求表、测试反馈单、版本提交记录，数据来源为关卡编辑器、美术资源库、玩家测试数据与缺陷系统。数据更新节奏为周度或每版本更新，核心字段包含关卡ID、资源路径、测试节点编号、缺陷等级与修复状态，数据规模随关卡设计规模动态变化。

## 这些特征在「工作流编排」这一环带来什么约束
数据来源分散在关卡编辑器、美术资源库、玩家测试系统与缺陷管理平台，要求工作流支持多数据源的拉取与整合。数据更新节奏为周度或每版本，需适配按版本提交触发的执行逻辑，避免无效重复运行。核心字段随关卡设计动态变化，需通过可配置的变量传递参数。最耗时的可玩性调试环节依赖多节点串联的测试流程，需将缺陷捕获与修复逻辑嵌入对应工作流节点，同时适配资源库缓存的规模限制。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 触发方式 | 按版本提交标签触发 | 匹配周度或每版本的更新节奏 |
| 重试次数 | 2 次 | 应对单次工具调用的临时网络波动 |
| `variables` 配置 | 传入关卡ID、缺陷等级字段 | 适配日常文档的核心字段结构 |
| 节点超时时间 | 600 秒 | 覆盖关卡资源加载、测试数据拉取的耗时 |
| 单次召回结果条数 | 前5条 | 匹配测试反馈单的常规反馈数量 |
| 资源库缓存大小 | 1000 MB | 适配当前关卡的美术资源规模 |
| `nodeId` 标记 | 为每个测试环节分配固定`nodeId` | 便于后续缺陷数据的链路追溯 |

## 容易做错的三处
- 工作流中工具调用模块返回空结果，未触发工具调用。原因是未绑定对应关卡的专属数据源，导致无法匹配到有效调用内容。
- 代码执行模块报错提示找不到import的依赖库。原因是未在FastGPT容器的系统依赖目录中安装对应库文件。
- 工作流执行失败后未生成对应缺陷记录。原因是未配置错误捕获节点，未通过`variables`传递错误日志字段用于缺陷归档。

## 怎么确认配好了
- 手动触发工作流，检查是否能拉取对应关卡的测试反馈单与资源库数据。
- 执行代码执行模块，验证import的依赖库可正常加载无报错。
- 模拟节点执行失败，检查是否触发错误捕获机制并生成对应缺陷记录。
- 核对`nodeId`标记，确认每个测试环节的节点ID与设计文档一致。
