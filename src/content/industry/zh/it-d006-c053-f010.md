# 客户需求池管理的测试用例与缺陷分析：引用来源与溯源

## 这个品类的数据长什么样
客户需求池管理的核心数据来自工单系统、客户访谈记录、CRM系统及产品路线图，更新频率为每周或每版本发布周期。日常产出的文档包括需求池清单、需求评估表、客户反馈记录与版本规划说明，数据字段包含需求来源标识、关联客户信息、优先级标签、版本排期项等，由产品运营、客户成功及产品经理共同维护。

## 这些特征在「引用来源与溯源」这一环带来什么约束
由于客户需求池的数据来源分散且更新节奏随版本调整，引用溯源环节需支持跨系统数据关联，确保每个引用的需求均能追溯至原始工单、访谈记录或CRM条目。日常文档类型多样，需明确标注引用内容所属的具体文档类型与版本，避免混淆不同周期的需求评估结果。同时，需求归并与排期沟通的高频环节，要求溯源链路可快速定位重复需求的原始提交记录，减少信息偏差。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | 匹配客户需求池单条完整记录的平均长度，避免截断关键溯源信息 |
| `responseData` | 仅返回需求来源、关联客户字段 | 聚焦溯源所需的核心标识，减少非必要数据传输 |
| `detail` | 开启全链路溯源 | 支持展示需求从原始工单到版本规划的完整追踪路径 |
| 超时等待时长 | 300 秒 | 适配客户需求池数据的跨系统查询耗时，避免因等待过久导致工作流中断 |
| 缓存有效期 | 7 天 | 匹配客户需求池的周更新频率，确保引用的始终是最新版本的需求数据 |
| 变量引用触发规则 | 按实测标定 | 适配动态指定知识库的需求，匹配客户需求池的多数据源特性 |
| 单次返回溯源条数 | 前 3–7 条 | 控制返回数据量，避免因过多关联记录导致页面加载延迟 |

## 容易做错的三处
- 现象：工作流中知识库搜索节点的引用变量下拉框为空，无法选择动态知识库。原因：未在全局变量配置中创建与客户需求池数据源关联的变量，或变量作用域未覆盖当前工作流。
- 现象：测试用例执行后，缺陷分析结果中出现冗余的非需求池来源引用。原因：未配置`responseData`参数过滤无关字段，导致混入其他系统的非目标数据。
- 现象：引用溯源时返回的内容被截断，无法查看完整需求记录。原因：`quoteMaxToken`取值过小，未覆盖单条需求池记录的完整字符长度。

## 怎么确认配好了
本核对流程基于FastGPT v4.17.0版本。
- 进入工作流的知识库搜索节点，查看引用变量下拉框，确认已关联的客户需求池数据源变量可被选中。
- 触发测试用例执行，查看缺陷分析结果中的溯源信息，确认仅包含需求池相关的来源字段。
- 调整`quoteMaxToken`参数后，验证返回的溯源内容未出现截断情况。
- 模拟多需求归并场景，确认溯源链路可快速定位原始提交的客户反馈记录。
