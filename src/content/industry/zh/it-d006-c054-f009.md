# 容器平台运维的测试用例与缺陷分析：工具调用与插件

## 这个品类的数据长什么样
该品类的数据主要来自Kubernetes API、镜像仓库、监控系统与CI流水线，日常关联的运维文档包含集群变更单、命名空间配额表、部署记录与故障报告。数据更新频率为每日或随集群变更触发，核心字段包含命名空间标识、Pod状态码、资源配额阈值、镜像版本号与故障排查日志，字段与单位随数据源类型灵活变化，无统一固定格式。

## 这些特征在「工具调用与插件」这一环带来什么约束
数据来源分散且随集群变更实时更新，要求工具调用需支持多数据源并行拉取，避免单次调用超时。日常运维文档结构差异较大，需插件支持自定义字段映射，适配不同集群的配额表、变更单格式。最耗时的Pod异常排查与集群升级验证环节，需要工具自动关联多源数据并聚合上下文，插件需具备结构化数据解析能力。出错后果直接影响业务，要求调用失败时触发告警并保留完整调用链路日志，便于后续缺陷回溯。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | 适配容器平台运维中多工具按需调用的场景，自动匹配集群数据拉取、故障排查等工具 |
| `functionCall` | 按结构化格式拼接 | 适配Kubernetes API返回的标准化数据，便于后续缺陷分析环节解析字段 |
| 工具调用超时时间 | 600 秒 | 覆盖大规模集群变更、多Pod异常排查的单次调用耗时，避免因数据量大导致调用中断 |
| 单次返回数据条数 | 前 20 条 | 控制返回数据量，避免超出下游模型的上下文承载上限 |
| 数据缓存有效期 | 24 小时 | 适配每日更新的集群数据，避免缓存过期导致调用拉取旧数据 |
| 调用失败重试次数 | 3 次 | 应对监控系统、镜像仓库的临时网络波动，降低单次调用失败的影响 |

## 容易做错的三处
- 现象：工具调用返回结果为空且无明确报错信息。原因：未配置多数据源并行拉取，仅调用单一监控系统接口，无法获取完整的Pod异常排查数据。
- 现象：工具拉取的原始集群配置数据被直接输出给终端用户。原因：未设置内容过滤规则，将未加工的工具返回内容直接返回，违反测试用例的信息隔离要求。
- 现象：定时触发的工具调用频繁超时中断。原因：未设置合理的超时时间，容器平台大规模集群变更的数据拉取耗时超过预设阈值。

## 怎么确认配好了
- 执行模拟集群变更的测试用例，检查工具是否自动拉取对应命名空间的配额表与部署记录。
- 触发Pod异常排查的测试场景，确认工具调用返回的结构化数据可被正确解析为缺陷分析报告。
- 手动触发工具调用失败，检查是否生成完整的调用链路日志并触发告警。
- 验证内容过滤规则，确认仅将经过加工的缺陷分析结果返回给下游模型。
