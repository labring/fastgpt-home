# 容器平台运维的测试用例与缺陷分析：引用来源与溯源

## 这个品类的数据长什么样
该品类的数据主要来自Kubernetes API、镜像仓库、监控系统与CI流水线。日常产出的文档包括集群变更单、命名空间配额表、部署记录与故障报告。数据字段包含集群标识、命名空间名称、Pod运行状态、镜像版本、变更执行时间、资源配额阈值等，更新频率为每日或每次集群变更后。数据结构以结构化表格与日志条目为主，部分监控指标采用时序格式，无统一的跨系统元数据标识。

## 这些特征在「引用来源与溯源」这一环带来什么约束
该品类的数据分散于多个异构系统，引用溯源时需完成跨系统的元数据关联，否则无法匹配到正确的知识库来源。数据更新频率随集群变更灵活调整，需校验引用内容的时间戳，避免使用过期的集群变更单或部署记录。日常文档的字段多为运维专用标识，需匹配容器平台特有的字段格式才能完成关联。同时，溯源结果的准确性直接影响故障排查与变更验证，错误的引用可能导致后续运维决策偏差，甚至引发业务中断。

## 配置怎么定
本配置适用于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `quoteMaxToken` | 800–1200 token | 匹配容器平台运维文档的单块内容长度，避免截断集群ID、Pod状态等关键字段 |
| `responseData` | 开启元数据绑定 | 确保返回内容关联对应的Kubernetes API日志或CI流水线变更记录 |
| `detail` | 完整模式 | 保留故障报告中的详细排查步骤与资源配额调整记录 |
| 单次召回来源条数 | 前5条 | 匹配日常运维文档的单次变更关联条目数量，避免过多冗余信息干扰排查 |
| 上下文窗口时长 | 600 秒 | 匹配集群变更的平均执行周期，确保引用的变更记录与当前问题的时间线对齐 |

## 容易做错的三处
- 现象：返回的容器平台故障排查答案与关联的知识库引用内容无关联。原因：未完成跨系统元数据的映射配置，导致召回的来源条目未匹配当前集群的实际变更记录。
- 现象：配置工作流可见度时，无法单独控制部分内容的引用展示。原因：未区分`responseData`参数的绑定层级，导致所有引用统一展示或隐藏。
- 现象：知识库拆分后部分部署记录未生成问答对。原因：未匹配容器平台运维文档的专用字段格式，导致拆分工具无法识别资源配额、Pod状态等关键信息。

## 怎么确认配好了
- 提交包含Pod异常排查或集群变更验证的查询，核对返回答案中关联的引用来源是否包含对应的Kubernetes API日志与故障报告。
- 检查答案下方的引用列表，确认每条来源的字段与当前集群的实际配置一致。
- 调整`quoteMaxToken`参数后，验证返回内容未截断关键的集群标识或配额数值。
- 切换`detail`参数模式，确认完整模式下展示的故障排查步骤与原始文档内容匹配。
