# 数据库运维的测试用例与缺陷分析：工作流编排

## 这个品类的数据长什么样
该品类的数据主要来源于数据库监控系统、审计日志、SQL执行计划与工单系统。日常产出的文档包括数据库变更单、慢SQL报告、备份记录与权限申请单，其中变更单包含实例标识、操作类型与SQL语句字段，慢SQL报告记录执行耗时与扫描行数，备份记录包含恢复时效与存储路径。数据更新频率为每次数据库变更触发或每日生成一次，无固定统计周期。

## 这些特征在「工作流编排」这一环带来什么约束
在FastGPT v4.17.0版本中，多源数据来源要求工作流需支持接入不同类型的数据源节点，适配监控指标、日志文本与结构化工单的格式差异。数据更新的非固定频率要求工作流需同时支持事件触发与定时触发两种模式。多样的文档结构要求工作流需配置分支判断规则，适配不同类型的运维工单。数据处理环节的高风险特性要求工作流需内置失败重试与异常告警机制，避免数据损坏或权限越界问题。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 触发方式 | 按数据库变更事件触发 / 每日凌晨6点定时触发 | 匹配数据更新频率为日/每变更的业务特征 |
| 并行节点数 | 2-4个 | 适配数据库实例并发连接上限的常规范围 |
| 分支判断规则 | 按工单类型、SQL执行计划标签匹配 | 适配多类型数据库运维文档的结构差异 |
| 失败重试次数 | 2次 | 应对日志拉取、数据查询的临时波动 |
| 节点超时时间 | 300秒 | 覆盖慢SQL分析、备份恢复验证的常规耗时 |
| 节点与变量配置 | 使用`nodeId`按实例ID+节点类型命名，全局使用`variables`传递核心业务数据 | 便于多分支工作流定位异常，跨节点传递数据库实例ID、SQL语句等信息 |

## 容易做错的三处
- 现象：文本分类提取节点返回空结果，无法生成工作流基准测试数据。原因：未通过`variables`传递待分类的SQL语句或日志内容，或未配置存储基准数据的变量，导致节点无有效输入或无法开展对比实验。
- 现象：配置并行分支节点后工作流执行超时。原因：未匹配数据库实例的并发连接上限，并行节点数超出常规承载范围。
- 现象：工作流执行完成后重复进入问题分类节点。原因：分支判断规则未设置终止条件，导致循环触发分类逻辑。

## 怎么确认配好了
- 触发工作流，核对`variables`中传递的核心业务数据是否与输入的运维工单内容一致。
- 查看工作流执行日志，确认分支判断规则正确匹配对应类型的运维文档，触发指定分支。
- 模拟临时异常场景，确认失败重试机制触发并生成异常记录。
- 检查所有节点的`nodeId`标识，确保每个节点的命名唯一且可快速识别所属业务环节。
