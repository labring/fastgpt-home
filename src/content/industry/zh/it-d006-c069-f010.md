# 数据库运维的测试用例与缺陷分析：引用来源与溯源

## 这个品类的数据长什么样
该品类的数据主要来自数据库监控、审计日志、SQL执行计划与工单系统，日常产出数据库变更单、慢SQL报告、备份记录、权限申请单等文档。数据更新节奏为每日同步或随数据库变更实时更新，文档字段包含变更时间、影响实例、执行语句、权限范围、备份路径等，无统一标准化格式，部分字段随运维场景动态调整。

## 这些特征在「引用来源与溯源」这一环带来什么约束
数据库运维的数据源多为结构化运维日志与工单，且文档格式不统一，导致引用溯源时需适配多类数据结构，无法直接使用通用的文本分块规则。变更单与慢SQL报告的更新频率差异较大，需动态调整溯源的时间范围匹配机制。权限申请单涉及敏感数据，引用时需额外校验数据脱敏状态，避免泄露权限信息。同时，数据库运维数据的字段关联性强，需确保溯源时能关联到对应实例的完整变更链路，提取单条文本片段不足以覆盖完整信息。

## 配置怎么定
本页适配FastGPT v4.17.0版本的配置逻辑。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 引用最大Token数 | 800–1200 token | 对应`quoteMaxToken`，匹配数据库运维文档的单块内容长度，避免截断关键变更语句或SQL执行计划 |
| 响应数据格式 | 结构化溯源模式 | 对应`responseData`，适配多类运维文档的字段关联，便于提取实例、时间与权限信息 |
| 细节展示开关 | 开启 | 对应`detail`，展示完整的溯源文档路径与执行时间，满足慢查询定位与变更审核需求 |
| 单次搜索上限 | 前5条 | 匹配日常运维的核心变更与慢SQL数量，避免冗余结果干扰分析 |
| 上下文缓存时长 | 12–24 小时 | 适配日更与实时变更的不同更新节奏，平衡响应速度与数据新鲜度 |
| 敏感数据校验 | 开启 | 过滤权限申请单中的敏感账号与路径信息，符合运维数据安全规范 |

## 容易做错的三处
- 现象：返回结果显示引用了知识库内容，但实际内容与专业运维文档无关。原因：未将知识库搜索范围限定为数据库运维专属数据源，通用知识模块覆盖了部分专业内容。
- 现象：引用的慢SQL语句被截断，无法看到完整执行逻辑。原因：`quoteMaxToken`设置过低，截断了长文本的关键部分。
- 现象：通过动态参数绑定知识库搜索后，AI回答未展示任何引用内容。原因：未将动态参数正确关联到知识库搜索的数据源配置中，导致搜索范围为空。

## 怎么确认配好了
- 上传一份测试用的慢SQL报告，发起包含“查询该实例慢SQL原因”的提问，检查返回结果中是否关联到对应文档的路径与执行时间。
- 发起包含“查看某权限申请单详情”的提问，检查返回内容中是否过滤了敏感的权限账号与服务器路径信息。
- 调整单次搜索上限的取值，观察返回结果的引用条数是否符合设置的范围。
- 触发一次数据库变更的模拟提问，检查溯源内容是否覆盖了变更单、审计日志与执行计划的完整链路。
