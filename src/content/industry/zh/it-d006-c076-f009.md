# 日志平台与可观测性的测试用例与缺陷分析：工具调用与插件

## 这个品类的数据长什么样
本品类的数据主要来自日志系统、Trace平台、Metrics系统与应用SDK。日常配套文档包含日志采集规范、链路追踪说明、指标字典与看板配置记录。数据更新频率为每日或随应用版本迭代更新。数据字段包含时间戳、服务标识、日志级别、链路ID、指标数值与单位等，不同来源的数据格式与字段命名存在差异，需通过标准化流程对齐。

## 这些特征在「工具调用与插件」这一环带来什么约束
数据来源分散且格式不统一，要求`toolChoice`需支持多数据源的适配解析，插件需内置通用字段映射规则。更新频率的不确定性，要求工具调用需支持增量拉取配置，避免全量同步占用过多资源。配套文档的分散性，要求插件需关联对应数据源的官方文档入口，便于调用时参考字段定义。链路ID等关联字段的缺失会导致排查失效，要求`functionCall`需强制校验关联字段的存在性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `toolChoice` | 自动模式 | 适配多数据源的动态解析场景 |
| `functionCall` | 强制链路字段校验 | 确保排查所需的关联信息完整 |
| 插件超时阈值 | 600 秒 | 覆盖全量日志拉取与链路关联的耗时 |
| 增量同步间隔 | 1 天 | 适配每日更新的数据同步节奏 |
| 单次召回日志条数 | 前 500 条 | 平衡数据加载速度与分析精度 |
| 单次召回链路条数 | 前 10 条 | 聚焦核心排查关联信息 |
| 数据源映射规则 | 按实测标定 | 适配不同环境的日志字段命名差异 |

## 容易做错的三处
- 配置`functionCall`后出现字段为空的报错，原因是未关联对应数据源的字段映射规则，导致关键链路ID无法被提取。
- 部署FastGPT v4.17.0后添加Doc2X插件出现报错，原因是未在插件配置中填写正确的API密钥与服务地址，或依赖的第三方服务未正常启动。
- 工作流中引用插件后点击输入无响应，原因是未设置合理的超时阈值，导致插件请求长时间挂起未返回结果。

## 怎么确认配好了
- 触发插件调用后，查看返回结果中是否包含链路ID、服务名等预期字段，验证字段解析是否生效。
- 提交测试用例后，检查插件执行日志是否有报错信息，确认超时阈值与映射规则是否正常生效。
- 对比插件拉取的日志数据与源系统的日志条目，验证召回条数与更新频率是否符合配置要求。
- 查看插件关联的文档入口是否能正常跳转至对应数据源的官方说明，确认文档关联配置正确。
