# 漏洞扫描服务的测试用例与缺陷分析：引用来源与溯源

## 这个品类的数据长什么样
漏洞扫描服务的核心数据来源于漏洞扫描器、企业资产清单、公开CVE库与官方补丁公告。日常产出的文档包括扫描计划、漏洞清单、整改工单与复扫报告，各文档包含漏洞ID、关联资产IP、扫描执行时间、风险等级、补丁状态等固定字段。数据更新频率以周或月为周期，单次扫描任务的结果会随复扫流程同步更新，不同资产的扫描结果会按扫描批次分类归档。

## 这些特征在「引用来源与溯源」这一环带来什么约束
多源数据的混合使用要求溯源环节需明确区分漏洞扫描器原始数据、CVE库标准信息与补丁公告的不同引用格式，避免混淆不同来源的字段定义。固定周期的更新节奏要求溯源时需匹配数据的更新时间戳，确保引用的漏洞信息与当前最新扫描结果一致。固定字段结构则要求引用需携带漏洞ID、资产IP等唯一标识，便于快速定位原始文档。同时，误报排除与复扫核对的高耗时特性，要求溯源能直接关联到复扫报告与整改工单，减少人工核对成本。

## 配置怎么定
以下配置适用于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | 匹配单条漏洞扫描描述的平均长度，避免截断关键溯源信息 |
| `responseData` | 仅返回关联知识库数据 | 确保输出内容仅来自漏洞扫描相关文档，排除无关通用内容 |
| `detail` | 开启 | 展示引用来源的具体字段，如漏洞ID、扫描执行时间与资产IP |
| 单次搜索上限 | 前3条 | 匹配单扫描计划的关联漏洞数量，避免冗余引用 |
| 问题优化 | 关闭 | 避免模型改写原始扫描数据，保留溯源所需的原始字段与格式 |
| 最大上下文 | 10000 字符 | 容纳多份扫描报告、CVE库条目与补丁公告的完整内容 |

## 容易做错的三处
- 现象：返回内容未关联知识库中的漏洞扫描数据，仅生成通用漏洞描述。原因：未开启`responseData`的仅关联数据开关，或配置的最大上下文长度不足以容纳扫描报告内容。
- 现象：引用来源仅显示文档类型，无具体漏洞ID或资产IP信息。原因：未开启`detail`配置项，或未在知识库中配置漏洞数据的字段映射规则。
- 现象：引用条数超出预期，导致日志冗余且溯源效率降低。原因：单次搜索上限配置过高，未匹配单扫描计划的实际关联漏洞数量。

## 怎么确认配好了
- 发起针对已知漏洞ID的查询，检查返回内容是否包含该漏洞的CVE编号、扫描时间等来自知识库的字段。
- 查看系统日志，确认引用来源的文档类型为扫描计划、漏洞清单或复扫报告，无无关数据源。
- 调整`quoteMaxToken`配置为较小值，验证长漏洞描述是否被截断，确认配置生效。
- 测试关闭`detail`配置，确认引用来源的详细字段不再显示，验证配置生效。
