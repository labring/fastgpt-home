# 版本发布与Release Notes的测试用例与缺陷分析：工作流编排

## 这个品类的数据长什么样
该品类的数据围绕版本发布全流程生成，来源包括Git仓库的版本标签、合并提交记录、CI流水线生成的制品包，以及关联的Issue里程碑条目。日常产出的文档包含Release Notes、变更日志、版本标签说明、发布检查单，字段涵盖变更类型、影响范围、关联Issue编号、制品哈希值。数据更新节奏为每正式版本发布一次，单次更新包含该版本周期内所有已合并的变更内容。

## 这些特征在「工作流编排」这一环带来什么约束
版本发布数据的批量性与版本绑定特性，要求工作流需按版本周期触发执行，避免跨版本混淆变更内容。数据来源分散在Git、CI、Issue系统，工作流需配置多源数据拉取节点，统一整合为结构化内容。单次更新的内容量随版本规模波动，工作流需支持动态调整处理节点的执行阈值。发布检查单的校验逻辑需与制品哈希、变更类型强绑定，确保校验项不遗漏关键环节。出错后果直接影响社区信任，工作流需配置失败告警与回滚校验环节。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 全局变量 | 绑定`variables`中的版本周期、关联Issue标签 | 适配版本发布数据的批量拉取与分类 |
| 节点ID | 指定`nodeId`为测试用例校验节点 | 确保工作流分支跳转指向正确的校验环节 |
| 失败重试次数 | 3次 | 应对CI制品拉取的临时网络异常 |
| 超时阈值 | 1200秒 | 适配多源数据整合的处理时长 |
| 单次拉取变更条目数 | 前50条 | 适配版本周期内的常规变更规模 |
| 变更内容截断阈值 | 800-1200字符 | 适配Release Notes的排版要求 |

## 容易做错的三处
- 现象：工作流的全局变量配置面板中，可选参数仅剩余两个，无法调用历史版本配置的全局变量。原因：FastGPT v4.17.0中全局变量的加载逻辑调整，需在工作流初始化节点手动绑定对应版本的变量池。
- 现象：执行工作流时报错“Key is error. You need to use the app key rather than the account key”。原因：未正确配置工作流的API密钥类型，误用账号密钥替代应用密钥。
- 现象：工作流中途调用指定回复节点输出HTML代码，运行时未显示对应内容，直接进入下一节点。原因：指定回复节点未开启原始内容输出开关，默认转义了HTML标签导致内容无法正常渲染。

## 怎么确认配好了
- 触发一次Git标签推送模拟事件，检查工作流是否正常拉取对应版本的合并记录与Issue数据。
- 查看工作流的`variables`配置面板，确认已绑定当前版本所需的所有全局参数。
- 运行测试用例校验节点，验证是否能正确关联变更类型与预设的测试用例覆盖率规则。
- 模拟CI制品拉取失败场景，检查是否触发预设的告警通知与重试逻辑。
