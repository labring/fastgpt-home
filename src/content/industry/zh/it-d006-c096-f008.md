# 社区举报处理的测试用例与缺陷分析：工作流编排

## 这个品类的数据长什么样
该品类的数据主要来自举报系统、内容详情页、用户历史行为记录与审核规则库。日常产出的文档包括举报工单、举报处理记录、用户申诉单、标准化用户通知模板。数据更新节奏为实时或每日更新，核心字段包含工单唯一标识、举报内容链接、涉事用户ID、举报类型、处置状态与处置结果。本页面基于FastGPT v4.17.0版本编写。

## 这些特征在「工作流编排」这一环带来什么约束
由于数据更新节奏为实时或每日，工作流编排需支持动态拉取最新举报内容与审核规则，避免使用过期数据。多类文档的字段差异要求工作流配置变量映射规则，适配举报工单、申诉单等不同文档的字段提取。涉及用户通知的环节，需绑定标准化模板的变量替换逻辑。同时，处置环节的异常可能引发社区冲突，需配置明确的失败处理分支与告警触发条件。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` 字段映射 | 匹配举报工单的核心字段 | 适配品类特有的文档结构 |
| 节点触发时机 | 按举报工单创建事件触发 | 匹配数据实时更新的节奏 |
| 异常分支超时阈值 | 600 秒 | 覆盖常规举报处理的耗时上限 |
| 单次数据拉取上限 | 前 20 条 | 控制工作流的单次处理负载 |
| `nodeId` 命名规则 | 按节点功能标识 | 便于测试用例的定位与调试 |
| 通知模板变量绑定 | 关联预设的用户通知模板 | 标准化处置结果的触达内容 |

## 容易做错的三处
- 创建工作流模板后进入编辑界面弹出报错提示，原因是未正确配置`variables`字段的映射规则，导致系统无法识别举报工单的核心字段。
- 在工作流中引用自定义插件后接入代码运行节点，点击输入配置时弹出报错，原因是未绑定品类专属的举报数据源，导致变量无法正常加载。
- docker部署环境下进入工作流页面提示Cannot read properties of undefined (reading 'incl')，原因是`nodeId`存在重复命名或非法字符，导致系统无法解析节点标识。

## 怎么确认配好了
- 手动触发一条测试举报工单，查看工作流是否自动启动并拉取对应工单的核心数据。
- 模拟数据源超时的异常场景，确认工作流是否触发预设的异常分支与告警通知。
- 检查`variables`字段的映射是否与举报工单的字段完全匹配，无缺失或错误绑定。
- 查看`nodeId`的命名是否符合规则，无重复或非法字符，便于后续测试用例的定位与调试。
