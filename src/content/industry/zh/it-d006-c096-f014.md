# 社区举报处理的测试用例与缺陷分析：模型接入与配置

## 这个品类的数据长什么样
该品类的数据主要来自举报系统、涉事内容详情页、用户历史行为记录及审核规则库。日常处理文档包含举报工单、处置记录、申诉单与用户通知模板，字段涵盖举报唯一标识、涉事内容ID、举报与被举报用户标识、违规类型标签、处置状态等。数据更新节奏多为实时或按日同步，单次处理涉及单条或批量举报内容的全链路信息流转。

## 这些特征在「模型接入与配置」这一环带来什么约束
由于该品类按单处理用户提交的具体举报内容，模型接入需支持低延迟的单条内容推理，避免批量任务阻塞处理流程。举报工单、申诉单等结构化文档与自然语言描述结合的输入形式，要求配置支持混合格式的上下文处理。实时更新的审核规则与用户历史数据，要求配置可动态调整且不中断现有服务，同时需适配多来源数据的字段对齐需求，降低处理偏差风险。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 适配举报内容、历史记录及审核规则的混合上下文长度，避免截断关键违规判定信息 |
| `maxTokens` | 1500–2000 token | 匹配单条举报处置结果的输出长度需求，平衡响应速度与内容完整性 |
| `temperature` | 0.2–0.4 | 降低生成结果的随机性，确保违规判定与处置建议的一致性，符合审核规则的标准化要求 |
| `vision` | 开启 | 支持对举报内容中的图片、截图等视觉证据进行识别，补充违规判定的依据 |
| `AIPROXY_API_ENDPOINT` | 按部署环境填写AI Proxy服务的根地址（例如http://aiproxy:3000，不要附加/v1或/chat/completions，非单模型地址） | 确保App/Admin服务与AI Proxy服务的路由正确，适配不同部署架构的访问需求 |
| `AIPROXY_API_TOKEN` | 按与AI Proxy服务端配置一致的管理员Token填写（不能为空） | 完成App/Admin服务与AI Proxy服务之间的身份验证，保障接口调用的安全性 |

## 容易做错的三处
- 未配置AIPROXY_API_ENDPOINT或AIPROXY_API_TOKEN：现象为App/Admin服务启动校验失败，无法正常启动。排查项：检查服务端环境变量是否已正确配置这两个必填项。
- 多模态模型无法识别举报内容中的内嵌图片：现象为模型输出未包含图片相关的识别描述。原因是未开启`vision`配置项，或未对PDF等格式的举报内容进行图片提取预处理。
- 模型调用出现超时错误：现象为请求返回超时状态码。排查项：检查AI Proxy服务运行状态、网络连通性、上游模型服务状态。

## 怎么确认配好了
- 检查App/Admin服务端的环境变量配置，确认已正确设置AIPROXY_API_ENDPOINT和AIPROXY_API_TOKEN，验证服务启动校验通过。
- 上传包含图片的举报测试样本，触发模型调用，确认返回结果包含图片内容的识别描述，验证`vision`配置生效。
- 调整`temperature`配置后发起测试，对比两次生成结果的差异，确认配置对模型输出的影响符合预期。
- 查看App/Admin服务端日志，确认已正确携带AIPROXY_API_TOKEN向AI Proxy服务发起请求，验证路由与身份验证正确。
