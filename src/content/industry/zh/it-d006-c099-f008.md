# 移动端开发的测试用例与缺陷分析：工作流编排

## 这个品类的数据长什么样
移动端开发测试相关的数据主要来自代码仓库、应用商店后台、崩溃监控平台、机型覆盖数据。日常产出的文档包含端版本发布单、机型适配清单、崩溃分析报告、应用商店审核资料。数据更新频率为每日或每版本发布周期，字段包含版本号、机型型号、崩溃日志ID、适配状态、审核进度等，单条数据长度随具体测试场景变化。

## 这些特征在「工作流编排」这一环带来什么约束
数据源分散导致工作流需要集成多节点拉取不同平台的信息，适配移动端开发的跨系统数据需求。版本发布的周期特性要求工作流支持按版本更新触发，避免频繁无效执行。日常文档的结构化差异，要求工作流可灵活绑定不同文档的字段作为测试用例的执行参数。崩溃数据的实时性要求，需要工作流支持失败节点的快速告警与重试机制，降低审核被拒或崩溃率上升的风险。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` | 绑定应用包名、机型型号为全局变量 | 匹配移动端开发测试用例的核心执行维度，统一跨节点的测试参数 |
| 触发节点配置 | 按版本发布单更新触发，延迟600秒 | 适配版本发布的审批周期，避免与人工审核流程冲突 |
| 上下文保留设置 | 单节点对话保留前3轮上下文 | 匹配移动端崩溃日志分析的短上下文需求，减少冗余信息干扰 |
| 文件解析节点 | 支持解析APK安装包日志，最大处理1000 MB文件 | 覆盖移动端安装包的常规体积范围，适配多数测试场景 |
| 失败重试配置 | 节点失败后重试2次，间隔30秒 | 适配崩溃监控平台的临时接口波动，降低单次调用失败的影响 |

## 容易做错的三处
- 工作流调用应用链接时，通过`data=1123`传递的变量未被`variables`全局变量捕获，原因是未在工作流初始化节点配置变量接收规则，未将传入参数映射到全局变量池。
- 同一个ID多次调用双AI节点工作流时，第一个节点的上下文残留影响第二个节点的输出，原因是未为每个AI节点单独配置上下文保留规则，默认复用全局上下文设置。
- 本地部署FastGPT v4.17.0后启用文件上传节点解析移动端日志时出现报错，原因是未正确配置`CUSTOM_READ_FILE_URL`环境变量指向本地文件存储路径，导致解析节点无法读取上传的日志文件。

## 怎么确认配好了
- 触发一次版本发布单更新的工作流，检查全局变量面板中是否正确加载了对应应用包名和机型型号。
- 调用两次同一ID的工作流，验证第一个AI节点的上下文仅保留指定轮次，无额外历史对话残留。
- 上传符合测试体积的APK日志文件，确认解析节点无报错并生成有效分析结果。
- 查看环境变量配置页面，确认`CUSTOM_READ_FILE_URL`指向正确的本地文件存储目录。
