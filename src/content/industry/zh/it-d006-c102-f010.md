# 缺陷管理与回归测试的测试用例与缺陷分析：引用来源与溯源

## 这个品类的数据长什么样
本品类的数据来自缺陷管理系统、测试报告、代码提交记录与用户反馈。日常产出的文档包括缺陷单、回归清单、修复验证记录、缺陷统计报表，其中缺陷单包含缺陷ID、复现步骤、优先级、关联测试用例编号等字段，回归清单标注测试用例编号、执行结果与执行时间。数据更新频率为每日或每版本发布周期，字段多为枚举值、字符串或时间戳格式，单篇文档长度多在500至1000字符区间。

## 这些特征在「引用来源与溯源」这一环带来什么约束
本品类数据的多源分散特性要求溯源时需关联不同系统的关联ID，避免孤立检索导致的信息不完整。固定字段格式要求检索时需匹配字段维度，提升精准度。高频更新特性要求配置适配增量同步逻辑，避免检索到过期数据。缺陷单与回归清单的强关联关系，要求溯源时需同时关联对应测试用例与修复验证记录，确保溯源链路完整。用户反馈的非结构化内容需与结构化缺陷单对齐，进一步增加了溯源时的字段匹配复杂度。

## 配置怎么定
本文档适配FastGPT v4.17.0版本

| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| 相似度阈值 | 0.6–0.8 | 本品类文档字段多为枚举或固定格式，该区间可过滤不相关内容，保留有效关联记录 |
| 单次搜索召回条数 | 前3–5条 | 本品类单知识库关联缺陷与用例数量有限，过多召回会引入冗余信息 |
| `quoteMaxToken` | 800–1200 token | 本品类核心文档单篇长度多在500–1000 token，该区间可完整保留关联溯源信息 |
| 响应数据包含字段 | 缺陷ID、测试用例编号、执行时间、修复状态 | 匹配本品类日常文档的核心字段，确保溯源信息完整 |
| `detail` | 开启 | 本品类溯源需复现步骤与关联记录，开启后可返回完整文档片段 |
| `responseData` | 启用关联ID映射 | 本品类数据多源分散，启用后可自动关联不同系统的关联字段，完善溯源链路 |

## 容易做错的三处
- 现象：批量上传的缺陷单、回归清单等文档中，半数文件显示训练异常，重新上传后仍出现引用重复。原因：未配置文档去重校验逻辑，上传时未验证文件哈希或关联ID，导致异常文件未被正确过滤，重复上传后仍保留冗余索引。
- 现象：设置相似度阈值为0.4后，无法检索到所需的缺陷关联内容。原因：本品类文档字段多为枚举或固定格式，阈值过低会引入大量不相关的非缺陷类文档，反而覆盖有效匹配结果。
- 现象：仅通过API调用语料生成回答时，未返回对应缺陷单或测试用例的出处信息。原因：未启用`responseData`配置项，未指定需要返回的溯源字段，导致API响应未包含引用来源数据。

## 怎么确认配好了
- 上传单篇缺陷单文档，发起关联测试用例的查询，核对响应结果中是否包含对应文档的关联ID与核心字段。
- 调整相似度阈值后，发起高优先级缺陷的查询，核对召回结果的相关性是否符合预期。
- 开启`detail`配置项后，查询修复验证记录，核对响应结果是否返回完整的文档片段内容。
- 批量上传同一缺陷的多份文档，核对知识库索引列表中是否存在重复的关联ID条目。
