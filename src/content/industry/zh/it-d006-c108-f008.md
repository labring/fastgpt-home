# 质保期缺陷响应的测试用例与缺陷分析：工作流编排

## 这个品类的数据长什么样
质保期缺陷响应的业务数据围绕项目交付后的保修服务生成，数据来源包括客户提交的质保工单、系统运行日志、合同约定的质保条款、软件版本更新记录。日常流转的文档包含质保工单、缺陷确认单、修复记录、客户确认单，各文档包含缺陷编号、责任主体、修复进度、客户反馈等固定字段。数据更新频率为每日或按单提交触发，每笔缺陷处理流程都会生成新的记录条目。

## 这些特征在「工作流编排」这一环带来什么约束
品类数据的多来源特性要求工作流需对接多个数据节点，分别拉取工单信息、日志记录、合同条款等内容，避免单一数据源的信息偏差。固定的文档字段结构要求工作流需绑定对应字段的变量，确保流程中传递的信息精准匹配业务需求。按日或按单的更新频率要求工作流需配置灵活的触发规则，适配不同业务场景的更新节奏。最耗时的责任边界判断、修复方案协调、客户确认闭环三个环节，需要在工作流中设置独立的处理节点，保障流程的清晰可控。

## 配置怎么定
以下配置基于 FastGPT v4.17.0 版本制定，适配质保期缺陷响应场景的工作流编排需求：
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` | 绑定质保工单ID、缺陷确认单编号、客户反馈字段 | 匹配品类文档的固定字段，精准关联每笔缺陷处理的核心数据 |
| 触发节点 | 按单提交触发，或按每日定时触发 | 匹配品类数据日/每单的更新频率，适配不同业务的处理节奏 |
| `nodeId` | 绑定责任判断节点、修复协调节点、客户确认节点 | 覆盖品类最耗时的三个业务环节，实现流程的完整闭环 |
| 上下文窗口 | 前 3 条历史处理记录 | 减少无效信息干扰，聚焦当前缺陷的最新处理状态 |
| 重试次数与间隔 | 3 次，间隔 600 秒 | 应对日志拉取、工单同步的临时异常，保障流程的稳定性 |

## 容易做错的三处
- 现象：工作流中代码运行节点无法执行Python代码，界面报错提示「不支持指定运行环境」。原因：未正确配置`variables`绑定运行环境参数，未匹配品类所需的代码执行权限范围。
- 现象：本地部署版本中，文件解析节点无任务执行，节点状态显示「待触发」。原因：未按品类数据更新节奏配置触发规则，未绑定质保工单的文件上传触发条件。
- 现象：工作流节点可见度配置后，部分客户确认单的引用内容无法隐藏。原因：未区分不同节点的权限配置范围，未针对敏感文档设置单独的可见度规则。

## 怎么确认配好了
- 提交一条模拟质保工单，检查工作流是否自动启动，对应节点是否按预期执行。
- 查看工作流的`variables`参数面板，确认质保工单ID、缺陷确认单编号等字段已正确绑定。
- 查看每个核心节点的执行日志，确认责任边界判断、修复协调、客户确认环节均按流程推进。
- 模拟一次日志拉取超时，检查重试机制是否按配置触发，流程是否自动进入异常处理环节。
