# 质保期缺陷响应的测试用例与缺陷分析：工具调用与插件

## 这个品类的数据长什么样
该品类的数据来源包括客户反馈的质保工单、系统运行日志、合同质保条款、项目版本更新记录。日常流转的文档包含质保工单、缺陷确认单、修复记录、客户确认单，各文档分别对应工单编号、缺陷描述、触发时间、责任判定结果、修复版本、客户闭环确认标识。数据更新频率为每日或随单触发，核心字段随缺陷处理进度实时更新。

## 这些特征在「工具调用与插件」这一环带来什么约束
数据来源分散且包含非结构化、半结构化格式，要求工具调用链路支持多源文档的自动拉取与字段映射。更新频率较高的特性要求工具触发时机匹配单工单处理或每日批量同步的节奏，避免延迟或重复调用。多文档的字段差异要求工具调用需预设明确的参数规则，确保不同来源的数据能被统一用于缺陷分析。缺陷处理的出错后果直接关联客户权益，要求工具调用结果可溯源，且需结合质保条款辅助责任边界判断。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `toolChoice` | `auto` | 适配不同缺陷工单的自动工具调用需求，无需手动指定调用类型 |
| `functionCall` | `[{"name":"query_quality_clause","parameters":{}}]` | 预设调用质保条款查询工具，辅助快速完成责任边界判断，基于FastGPT v4.17.0版本的插件调用规则配置 |
| 单次召回结果上限 | 前3条 | 避免过多冗余信息干扰缺陷分析，聚焦核心质保条款与缺陷记录 |
| 最大上下文长度 | 8000–12000 token | 容纳多份文档的内容，包括工单、日志、合同条款等，确保分析维度完整 |
| 问题优化开关 | 开启 | 将模糊的缺陷描述转化为可被工具识别的标准查询语句，提升工具调用准确率 |

## 容易做错的三处
- 调试工具调用节点时，日志中出现两次独立的大模型思考日志。原因：未通过`toolChoice`配置为强制工具调用模式，大模型先尝试生成自然语言回复，再触发工具调用流程。
- 开启工具调用后无法检索到知识库内容。原因：工具调用配置优先调用外部接口，未保留知识库检索的插件调用链路，或未将知识库作为可选工具纳入配置范围。
- 调用本地部署的大模型时出现参数格式报错。原因：混淆了线上API与本地部署的参数校验逻辑，未适配本地模型的输入格式约束。

## 怎么确认配好了
- 提交一条测试质保工单，查看工具调用日志，确认是否按配置触发了质保条款查询插件。
- 检查大模型回复中是否包含从知识库拉取的质保条款内容，无冗余或缺失的关键条款信息。
- 验证本地大模型调用时，输入参数与线上API的配置差异已完成适配，无格式类报错。
- 查看工具调用的返回结果是否被正确映射到缺陷确认单的责任判定字段中，无字段错位问题。
