# 质保期缺陷响应的测试用例与缺陷分析：引用来源与溯源

## 这个品类的数据长什么样
该品类的数据主要来源于客户提交的质保工单、系统运行日志、项目合同质保条款、软件版本更新记录。日常产生的文档包括质保工单、缺陷确认单、修复记录、客户确认单，数据更新频率为每日或随每单业务推进更新。数据字段包含工单编号、缺陷描述、责任判定依据、修复版本、客户确认状态等，无统一标准化格式，需按业务单据类型关联匹配。

## 这些特征在「引用来源与溯源」这一环带来什么约束
由于数据来源分散且无统一格式，引用溯源需同时关联多类业务单据，避免责任边界判断偏差。高更新频率要求溯源环节实时拉取最新数据，无法依赖静态缓存。不同文档的字段差异要求溯源时需匹配对应单据的专属字段，如质保工单的缺陷描述字段与修复记录的版本字段不可混用。同时，溯源结果直接影响质保争议判定，需确保每一条引用都能精准对应到原始业务单据，不能泛泛关联无关数据。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的参数规则。
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `quoteMaxToken` | `800–1200 token` | 覆盖单份完整质保工单或缺陷确认单的核心内容 |
| `responseData` | 开启 | 保留原始业务数据的原文片段，支持直接引用数据库或知识库的原始内容 |
| `detail` | 开启 | 保留数据的原始字段信息，便于匹配质保工单、修复记录等不同单据的专属字段 |
| 单次召回上限 | 前3–5条 | 避免过多冗余数据干扰大模型对缺陷责任的判断 |
| 数据源过滤规则 | 按质保工单、缺陷确认单分类 | 匹配该品类特有文档结构，避免关联无关业务数据 |

## 容易做错的三处
- 现象：大模型返回的回答未关联具体业务单据的原文片段，仅给出概括性结论。原因：未开启`responseData`配置，未配置数据源过滤规则，无法拉取原始业务数据。
- 现象：搜索返回的引用条数超出预期，无法通过配置调节。原因：未正确设置`quoteMaxToken`或单次召回上限，未按品类文档结构过滤数据源。
- 现象：切换向量模型后，溯源结果无法匹配质保工单的专属字段。原因：未针对品类特有数据结构调整向量模型适配规则，未校验数据来源的一致性。

## 怎么确认配好了
- 发起一条针对特定质保缺陷的测试查询，检查返回结果中是否包含原始业务单据的字段片段，如工单编号、修复版本。
- 查看配置项的当前取值，确认`quoteMaxToken`、`responseData`、`detail`的设置符合预设规则。
- 切换向量模型后发起测试查询，验证溯源结果仍能匹配该品类的特有数据结构。
- 调整单次召回上限的取值，验证返回的引用条数符合设定的范围。
