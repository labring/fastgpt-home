# 运维外包驻场服务的测试用例与缺陷分析：工作流编排

## 这个品类的数据长什么样
运维外包驻场服务的业务数据主要来自客户ITSM系统、监控平台、资产清单及值班记录。日常产出的文档包含驻场日报、服务台工单、巡检报告、SLA月报，文档字段涵盖工单编号、巡检项、服务响应时长、SLA达标率等。数据更新频率分为日更与月更，日更数据多为现场工单处理记录、值班日志，月更数据则为SLA统计汇总报表。

## 这些特征在「工作流编排」这一环带来什么约束
由于业务数据来源分散且更新节奏不同，工作流需适配多源数据的定时拉取与实时同步节点，避免数据滞后影响测试用例执行。日常文档字段差异较大，工作流需配置统一的字段映射规则，将不同来源的工单、巡检数据标准化为测试用例所需的格式。现场工单处理耗时占比高，工作流需设置优先级判断节点，优先处理高优先级缺陷工单。SLA月报的汇总逻辑复杂，工作流需内置统计汇总节点，确保数据符合合同交付要求。同时驻场人员轮换可能带来配置变更，工作流需支持权限分级调整，避免流程中断。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` | 绑定驻场工单ID、巡检项ID等核心字段 | 确保工作流关联正确的业务数据 |
| 聊天历史调用 | 前6条聊天记录 | 适配测试用例对话的上下文需求 |
| `nodeId` | 绑定文本内容提取节点的唯一标识 | 确保插件节点正常调用 |
| 环境变量配置 | 按FastGPT v4.17.0版本的官方指引添加 | 适配本地开源部署的环境依赖 |
| 工作流触发规则 | 按工单状态变更触发 | 匹配现场工单的处理节奏 |
| 上下文窗口 | 800–1200 字符 | 平衡上下文完整性与处理效率 |

## 容易做错的三处
- 工作流触发后多轮对话上下文丢失，现象为用户后续提问无法沿用之前选定的知识库。原因是未在`variables`中绑定聊天历史变量，导致上下文未被传递到后续节点。
- 文本内容提取插件节点无返回结果，现象为节点输出字段为空。原因是未开启聊天历史提取开关，或设置的聊天历史条数超出工作流允许的上下文范围。
- 工作流执行超时，现象为节点状态显示超时错误。原因是未根据工单处理的实际耗时调整超时阈值，导致高频工单触发时流程中断。

## 怎么确认配好了
- 手动触发工作流，传入测试用的工单数据，核对节点输出是否包含正确的字段映射结果。
- 发起多轮测试对话，验证后续提问是否能正确沿用之前的上下文与选定的知识库。
- 检查环境变量配置页面，确认所有依赖项已按FastGPT v4.17.0版本的指引添加完成。
- 模拟工单状态变更，验证工作流是否能按预设规则自动触发执行。
