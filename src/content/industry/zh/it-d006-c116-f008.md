# 项目文档移交归档的测试用例与缺陷分析：工作流编排

## 这个品类的数据长什么样
项目文档移交归档场景的数据主要来源于项目文档库、配置清单、会议纪要、测试报告。日常处理的文档包括竣工文档、配置手册、培训记录、验收证书，数据更新节奏为项目阶段节点或整体项目结束时。文档结构通常包含关联项目标识、版本编号、签章校验字段、移交时间戳，部分文档附带测试用例关联ID与缺陷记录编号，无统一固定的单位字段，仅按文档类型区分存储格式。

## 这些特征在「工作流编排」这一环带来什么约束
由于数据来源分散且更新节奏不固定，工作流编排需支持多数据源并行拉取节点，避免单一数据源阻塞整体流程。日常文档类型多样，需配置节点对不同文档格式做适配校验，确保完整性检查环节覆盖所有要求文档。关联的测试用例与缺陷数据需绑定项目标识，工作流需通过`variables`传递项目ID完成数据关联，否则易出现跨项目数据混淆。签章归档环节需等待校验节点完成，流程需设置串行依赖，防止未校验文档进入归档环节。需限制单次拉取上限为前100条，适配项目文档库的单次返回限制，避免节点超时。同时，该品类关注交付证据与后续可维护性，工作流需额外校验文档的版本一致性与签章有效性，避免后续运维无资料或验收不通过。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| 变量绑定 | 绑定`variables`中的projectId字段 | 关联测试用例、缺陷数据与对应项目文档，避免跨项目数据混淆 |
| 节点ID配置 | 为每个数据源节点设置唯一`nodeId` | 区分不同来源的文档与测试数据，便于流程分支判断 |
| 触发时机设置 | 按项目阶段节点触发 | 匹配数据更新节奏，减少无效流程运行 |
| 重试次数配置 | 3次，间隔60秒 | 应对文档拉取时的临时网络波动或权限校验延迟 |
| 超时阈值配置 | 600秒 | 适配大型项目文档的拉取与校验时长，避免流程无故中断 |
| 校验规则配置 | 覆盖全部要求文档类型 | 确保文档完整性检查覆盖竣工文档、配置手册等交付项 |

## 容易做错的三处
- 现象：工作流中引用`variables`传递的关联字段时，测试用例与缺陷数据匹配错误，或绑定知识库节点报错。原因：未在`variables`中配置对应项目的关联标识，或`nodeId`配置重复导致数据路由错误。
- 现象：Http请求后输出多组变量，无法将指定变量绑定到对应知识库。原因：未通过`nodeId`区分不同变量的来源节点，未在工作流中配置变量与知识库的映射规则。
- 现象：判断知识库是否为空时，无论数据是否存在均返回异常结果。原因：未配置正确的触发节点依赖，或校验逻辑未绑定项目关联字段，导致读取了无关项目的知识库数据。

## 怎么确认配好了
- 触发一次测试流程，检查各数据源节点是否按配置拉取对应类型的文档，确认数据来源正确。
- 传入测试用的项目ID，验证`variables`绑定的字段是否正确关联到对应测试用例与缺陷数据。
- 模拟单类文档缺失的场景，检查校验节点是否触发异常告警，确认校验规则覆盖全部要求文档类型。
- 模拟临时网络波动的场景，检查流程是否按配置的重试次数与间隔自动重试，确认超时阈值适配当前流程时长。
