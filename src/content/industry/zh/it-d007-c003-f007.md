# IT资产盘点的线上故障排查与复盘：对话日志与审计

## 这个品类的数据长什么样
本品类的数据源包括资产管理系统、采购系统、财务固定资产模块、终端管理平台。更新节奏为月、季或年周期。日常产出的文档包含资产台账、盘点表、领用归还单、报废申请，单份文档包含资产编号、名称、规格型号、使用人、所在位置、采购日期、使用状态等字段，数据多为批量同步后静态存储，无实时自动更新的独立字段。

## 这些特征在「对话日志与审计」这一环带来什么约束
数据源分散要求对话日志采集需适配多系统的接口格式，需分别对接资产管理、采购、财务等系统的返回结构。更新周期较长意味着无需高频拉取数据，但需保留至少一个完整盘点周期的全量记录以满足审计溯源需求。文档结构多样要求审计环节需识别不同文档类型的关键字段，比如通过资产编号关联对话中的终端或资产排查记录。字段无统一实时更新属性，需在对话日志中标记数据同步时间戳，避免使用过期资产信息开展故障排查。同时，审计需覆盖资产领用、归还、报废全流程的对话交互，确保每一步操作可追溯。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 对话日志存储时长 | `12 个月` | 本品类数据更新周期为月/季/年，需保留至少一个完整盘点周期的全量日志用于审计 |
| `chatId`关联字段 | 资产编号字段 | 资产台账中资产编号为唯一标识，可直接关联对话中的终端或资产排查记录 |
| 审计日志过滤规则 | 仅保留含资产编号、使用人字段的日志 | 本品类文档核心字段为资产编号与使用人，过滤后可缩小审计范围 |
| `detail`日志详情开关 | 开启 | 需完整记录对话中的资产状态变更、盘点核对细节，满足审计溯源要求 |
| 日志检索时间范围 | `近 3 个盘点周期` | 本品类数据更新周期多为月/季，覆盖近3个周期可满足常规故障排查与复盘需求 |
| `responseChatItemId`关联规则 | 绑定资产台账的唯一ID | 确保每一条对话回复都能对应到具体资产的审计记录 |

## 容易做错的三处
- 现象：对话中调用历史资产盘点记录无响应，返回结果为空。原因：未配置`chatId`与资产编号的关联规则，导致历史记录无法按资产维度匹配。
- 现象：审计日志检索时出现大量无关的非资产类对话内容。原因：未设置审计日志过滤规则，未过滤掉不含资产核心字段的交互记录。
- 现象：Docker部署后服务启动失败，无明确报错日志。原因：未开启`detail`日志详情开关，无法捕获容器启动时的具体错误信息，导致排查无依据。

## 怎么确认配好了
- 进入FastGPT v4.17.0的对话日志管理页面，检索指定资产编号的对话记录，确认能匹配到对应周期的交互内容。
- 触发一次资产盘点相关的对话，检查日志中是否包含`detail`字段的完整交互细节，确认日志详情开关已生效。
- 配置审计过滤规则后，检索非资产类对话，确认规则已生效，无关内容未被纳入审计范围。
- 查看`chatId`与资产编号的关联映射表，确认每一条对话记录都已绑定对应的资产唯一标识。
