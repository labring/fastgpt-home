# Issue分拣与响应的线上故障排查与复盘：HTTP 接口与外部系统

## 这个品类的数据长什么样
该品类的数据主要来源于GitHub或Gitee Issue、代码仓库版本日志、用户上报的环境信息与复现说明。日常维护的文档包括Issue提交模板、标签分类规则、历史回复记录、标准化的问题复现说明文档。数据更新频率为日度或周度，典型使用主体为开源项目维护者、社区运营人员与核心贡献者。日常处理中最耗时的环节为问题分类、有效复现信息补齐与责任模块标记，出错后易引发问题积压、用户流失或缺陷定位延迟。

## 这些特征在『HTTP 接口与外部系统』这一环带来什么约束
该品类的数据分散来源与结构化特征，要求HTTP接口需支持多源数据拉取与标准化字段解析。日/周的更新频率要求接口调用频次需匹配数据刷新节奏，避免过度请求或延迟获取最新Issue内容。Issue的标签、复现步骤等结构化字段，要求接口需支持按指定维度筛选返回结果。同时，社区运营人员的使用场景，要求接口配置需轻量化，减少非必要参数调整，便于快速接入现有社区运维流程。另外，问题分类与责任模块标记的核心需求，要求接口返回数据需包含可直接用于分拣的分类字段，无需额外二次处理。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `Authorization` | `Bearer {社区API密钥}，固定前缀为Bearer且保留空格` | 符合FastGPT v4.17.0的HTTP接口认证标准，适配GitHub/Gitee等平台的API认证要求 |
| `variables` | 包含仓库地址、Issue标签过滤规则的键值对，如`{"repo":"owner/repo","labels":["bug","urgent"]}` | 可灵活配置不同开源项目的分拣规则，适配多仓库运维场景 |
| `responseData` | 仅返回Issue编号、标题、创建时间、标签、复现步骤字段 | 减少无效数据传输，提升接口调用效率，匹配Issue分拣的核心数据需求 |
| 单次请求返回条数 | 前20条 | 避免单次返回过多数据导致超时，适配社区日常Issue量的常规处理规模 |
| 接口超时时间 | 30-60秒 | 预留足够时间完成多源数据拉取与字段解析，适配开源平台API的响应延迟范围 |

## 容易做错的三处
- 现象：调用接口后返回空数据或提示无权限。原因：`Authorization`参数未添加Bearer前缀，或密钥配置错误，不符合HTTP认证标准。
- 现象：外部调用发布后的工作流接口时，全局变量无法传递。原因：未在接口请求体中正确配置`variables`参数，未将外部传入的变量映射到工作流的全局变量配置中。
- 现象：接口返回数据量过大导致调用超时。原因：未限制单次请求返回条数或`responseData`指定的返回字段，未匹配社区日常Issue处理的合理数据规模。

## 怎么确认配好了
- 调用接口并查看返回结果，确认返回的字段包含配置的`responseData`指定内容，且数量符合预期。
- 携带正确的`Authorization`参数发起请求，确认返回状态码为200，无认证相关报错。
- 向外部调用接口的请求体中传入测试`variables`参数，确认工作流可正确读取并使用传入的变量。
- 模拟常规频次的调用，确认接口响应符合业务需求，无频繁超时情况。
