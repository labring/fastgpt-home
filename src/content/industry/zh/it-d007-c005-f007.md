# Issue分拣与响应的线上故障排查与复盘：对话日志与审计

## 这个品类的数据长什么样
该品类的数据主要来源于GitHub或Gitee Issue、代码仓库版本日志、用户上报的环境信息与问题复现说明。日常维护的文档包含Issue提交模板、标签规则库、历史回复记录、问题复现流程说明。数据更新频率按日或周更新，核心字段包括Issue编号、问题分类标签、复现步骤、关联代码提交记录，单位以条目、字符、时间戳为主，服务于开源维护者、社区运营与核心贡献者的日常分拣与响应工作。

## 这些特征在「对话日志与审计」这一环带来什么约束
数据来源分散在多平台与文档中，要求对话日志审计需覆盖Issue交互、代码提交关联记录的完整链路，避免审计范围遗漏。日/周级的更新频率意味着审计环节需支持增量同步，无需全量拉取全量历史数据，降低资源消耗。多类型文档与字段的差异，要求审计配置需适配不同来源的数据格式，例如区分Issue文本与代码仓库提交信息的解析规则。同时，问题分类、复现信息补齐等耗时环节的审计，需保留操作轨迹用于回溯，确保责任模块标记的可追溯性，避免出现问题积压或用户流失的风险。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 历史记录保留条数 | 前20条 | 覆盖大多数Issue的完整交互周期，适配品类数据的更新频率 |
| `chatId`绑定规则 | 绑定对应Issue编号 | 确保每一条对话日志与业务Issue一一对应，匹配品类数据来源的颗粒度 |
| 审计日志导出范围 | 按Issue维度筛选 | 适配品类数据以Issue为核心的文档结构，便于运维人员回溯单条问题的处理全流程 |
| `detail`字段采集开关 | 开启 | 保留用户上报的环境信息与复现步骤，满足故障排查与复盘的核心需求 |
| 超时重试间隔 | 300秒 | 适配GitHub API的调用频率限制，避免审计环节出现频繁报错 |
| `responseChatItemId`关联规则 | 绑定回复记录的唯一标识 | 完整保留每一次分拣响应的操作轨迹，便于责任追溯 |

## 容易做错的三处
- 导出的对话日志缺失关联Issue编号。原因：未配置`chatId`与Issue编号的绑定规则，导致日志无法匹配对应业务条目。
- 全局变量历史记录无法按需求修改。原因：审计配置中限制了历史记录的保留条数，超出范围的记录无法被编辑或调整。
- 携带历史记录的故障排查响应无效果。原因：未开启`detail`字段采集，缺失用户上报的环境信息与复现步骤，导致上下文不足，无法触发正确的响应逻辑。

## 怎么确认配好了
- 登录FastGPT v4.17.0平台，生成一条测试Issue，提交后查看对话日志是否自动绑定对应Issue编号，确认`chatId`配置生效。
- 导出指定时间范围的审计日志，检查是否包含`detail`字段的完整内容，确认采集开关开启。
- 修改历史记录的保留条数配置，验证超过保留上限的旧日志是否被归档，确认规则生效。
- 模拟携带历史记录的排查请求，检查响应是否能关联之前的Issue上下文，确认配置生效。
