# 代码安全审计的线上故障排查与复盘：对话日志与审计

## 这个品类的数据长什么样
该品类的数据主要来源于源代码仓库、依赖清单、静态应用安全测试（SAST）工具与公开漏洞库，按项目版本或单次审计任务更新。日常产出的文档包含代码审计报告、漏洞证明、修复建议与复测记录，核心字段包括漏洞编号、风险等级、关联代码片段、修复状态与复测结果，无统一固定单位，随审计对象的代码体量与漏洞数量变化。

## 这些特征在「对话日志与审计」这一环带来什么约束
数据来源分散且关联多工具输出，要求对话日志需完整记录审计工具调用参数、代码片段关联信息与漏洞判定依据，避免日志碎片化。按项目版本更新的特性，要求日志需绑定对应审计项目ID与版本号，便于回溯历史审计流程。文档结构包含多类型输出，要求日志字段需覆盖报告生成、漏洞复核等环节的操作痕迹，确保故障排查时可完整还原审计全链路。同时，单次审计数据量随代码体量波动，需预留足够的日志存储与检索空间，避免因数据过载导致检索延迟。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 与审计项目ID绑定，取值为审计任务生成的唯一标识 | 确保对话日志与对应代码审计任务绑定，便于按项目回溯故障流程 |
| `detail` | 开启全量记录模式 | 覆盖代码片段、漏洞判定细节与修复建议等核心审计数据，满足完整回溯需求 |
| `responseChatItemId` | 绑定人工复核的会话标识 | 关联漏洞复核环节的操作痕迹，便于定位修复方案的复核偏差 |
| 对话日志保存时长 | 90–180 天 | 匹配代码安全审计的项目周期，按实测标定可灵活调整 |
| 单项目日志存储阈值 | 1000 MB | 适配单次审计的数据体量波动，避免存储资源溢出 |
| 单次日志检索上限 | 前 100 条 | 平衡检索效率与数据完整性，避免单次返回过多内容导致加载延迟 |

## 容易做错的三处
- 现象：调用日志检索接口返回400状态码，提示`chatId`参数缺失。原因：未将日志与审计项目ID绑定，导致检索时无法匹配对应任务的日志数据。
- 现象：部分审计会话的对话日志在7天后自动消失，无法回溯历史审计结果。原因：错误将日志保存时长配置为7天，未匹配代码安全审计的项目周期需求。
- 现象：检索到的日志中未包含代码片段细节，无法定位危险函数调用路径。原因：未开启`detail`全量记录模式，仅保存了简化的会话摘要信息。

## 怎么确认配好了
- 检索任意已完成的代码审计任务的对话日志，确认`chatId`与项目ID一致，验证绑定关系生效。
- 查看单条日志的详情内容，确认包含代码片段、漏洞判定细节等信息，验证全量记录模式开启。
- 检查系统存储监控面板，确认单项目日志占用未超过预设阈值，验证存储配置合理。
- 调整日志保存时长后，等待对应周期验证，确认会话日志的保留周期符合预期，验证时长配置生效。
