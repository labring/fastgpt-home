# 代码评审与合并管理的线上故障排查与复盘：对话日志与审计

## 这个品类的数据长什么样
该品类的数据主要来自Git仓库、CI流水线、静态扫描报告与缺陷库，更新节奏为每日或每提交一次。日常产出的文档包括合并请求、代码评审意见、提交记录与分支策略说明。单条合并请求数据包含变更文件列表、评审人标记、提交哈希值、CI执行状态字段；代码评审意见则带有评论者标识、评论时间戳与评审结论标签。

## 这些特征在「对话日志与审计」这一环带来什么约束
由于数据来源覆盖代码仓库、流水线工具与缺陷管理系统，对话日志与审计环节需要关联多源异构数据，确保排查时可追溯完整的变更链路。高频更新的特性要求审计日志支持实时同步，避免因延迟导致故障排查时缺失最新的评审或合并记录。不同类型文档的字段差异，要求上下文拼接时优先关联合并请求的变更范围与评审意见的核心结论，减少无效信息干扰。同时，缺陷进入主干的严重后果，要求审计日志留存完整的评审、合并与回滚全流程数据，不可截断关键环节。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `chatId` | 绑定合并请求ID，留存时长 180–365 天 | 合并请求的审计周期通常覆盖其完整生命周期，绑定后可通过Git仓库的合并请求ID快速检索对应对话日志 |
| `responseChatItemId` | 为每条评审评论生成唯一标识，按提交顺序递增 | 可精准追溯单条评审意见的对话上下文，避免混淆多轮评审的内容 |
| `detail` | 存储完整的CI扫描结果、评审评论与合并状态，不截断超过 2000 字符的内容 | 完整的细节可支撑故障排查时的变更影响判断，避免因截断丢失关键信息 |
| 审计日志同步触发规则 | 按提交触发同步，延迟不超过 60 秒 | 匹配该品类的高频更新节奏，确保故障排查时可获取最新的评审与合并记录 |
| 对话日志检索上限 | 返回前 20 条关联记录 | 避免过多无效数据干扰排查，同时覆盖大部分合并请求的评审轮次 |

## 容易做错的三处
- 现象：对话详情页无法查看应用内部的评审沟通记录，页面返回空内容。原因：未将`chatId`绑定合并请求ID，导致检索时无法关联对应数据源。
- 现象：MongoDB 集合中无对话历史记录。原因：未开启审计日志的持久化配置，或留存时长设置为 0 天导致数据被自动清理。
- 现象：构建索引时提示内容超出长度限制。原因：未配置`detail`字段的截断规则，直接存储了过长的合并请求变更文件列表或评审评论。

## 怎么确认配好了
- 登录FastGPT v4.17.0的管理后台，进入对应代码评审与合并管理的应用配置页，检查`chatId`是否绑定了合并请求ID字段。
- 发起一次模拟代码提交并触发合并请求，查看审计日志列表，确认能检索到对应`responseChatItemId`的评审评论记录。
- 进入MongoDB数据库，检查对应集合中是否存在包含`detail`字段的对话日志数据，且字段内容未被过度截断。
- 在合并请求的详情页，点击关联的对话日志链接，确认能跳转至完整的评审沟通记录页面。
