# 单元测试与组件测试的线上故障排查与复盘：定时任务与自动化

## 这个品类的数据长什么样
本品类的数据主要来自代码仓库、测试框架报告、需求说明与接口定义，更新频率为每日或每次代码提交后。日常产出的文档包含测试用例、覆盖率报告、Mock说明与缺陷单，数据字段覆盖测试用例ID、执行状态、耗时、覆盖率数值、缺陷等级等，无统一固定单位，随具体测试框架与项目要求调整。最耗时的环节为测试数据构造与边界条件补齐，失败用例定位也会消耗较多精力，单次复杂测试任务的执行时长存在较大波动。

## 这些特征在「定时任务与自动化」这一环带来什么约束
本品类的数据绑定代码提交与日常更新节奏，因此定时任务需适配代码提交钩子触发或每日固定周期执行，避免过度占用资源。测试用例、覆盖率报告等文档的结构化格式存在差异，自动化任务需适配不同测试框架的输出格式，才能准确读取与分析数据。测试数据构造与失败用例定位耗时较长，定时任务需拆分执行步骤，避免单次运行超时。局部逻辑缺陷漏测的后果会提升回归成本，因此自动化任务需配置失败告警与重试机制，降低缺陷累积风险。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 触发时机 | 代码提交后触发 / 每日凌晨2点触发 | 匹配数据更新频率，避免重复执行未变更的测试任务 |
| 单次执行超时阈值 | 600–1200 秒 | 适配测试用例执行的平均耗时，避免因单任务超时阻塞后续流程 |
| 失败重试次数 | 2–3 次 | 应对临时网络波动或测试环境不稳定的情况，避免误判任务失败 |
| 任务执行并发数 | 2–4 个并行任务 | 匹配测试环境的资源上限，避免占用过多服务器资源影响业务 |
| 告警触发条件 | 任务连续失败2次 / 覆盖率偏离预设范围 | 及时通知相关团队处理异常，避免缺陷累积 |

## 容易做错的三处
- 现象：单次测试任务执行时长超过1200秒，触发平台超时拦截。原因：未合理拆分测试用例集，将大量关联测试任务合并为单次执行，超出定时任务的超时阈值。
- 现象：测试覆盖率报告字段为空，自动化分析任务失败。原因：未适配对应测试框架的输出格式，无法正确读取覆盖率报告中的结构化数据。
- 现象：批量上传测试用例后，重复用例未被自动去重，导致冗余测试执行。原因：未配置测试用例的唯一标识校验规则，未关联代码仓库的提交哈希进行去重。

## 怎么确认配好了
- 在FastGPT v4.17.0版本的任务管理页面中，手动触发一次测试任务，查看任务执行日志是否匹配配置的触发时机与超时阈值。
- 检查自动化任务的告警配置，模拟一次任务失败，确认告警通知是否正常触发。
- 对比测试用例的唯一标识与代码提交哈希，确认重复用例的去重逻辑是否生效。
- 查看定时任务的执行记录，确认任务在代码提交后或每日固定时间自动启动。
