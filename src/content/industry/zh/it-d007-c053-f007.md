# 客户需求池管理的线上故障排查与复盘：对话日志与审计

## 这个品类的数据长什么样
通常，客户需求池管理的数据来源为工单系统、客户访谈记录、CRM系统与产品路线图，更新频率为周度或每版本发布周期。日常关联文档包含需求池清单、需求评估表、客户反馈记录与版本规划说明，数据字段一般包含需求编号、关联客户标识、反馈内容、优先级标签、排期状态与响应时限，仅按业务流程自然流转，无额外自定义统计口径。

## 这些特征在「对话日志与审计」这一环带来什么约束
数据来源分散意味着对话日志需要整合API调用、页面交互、工作流执行的多源记录，避免遗漏跨系统的需求沟通内容；更新频率不固定，审计周期需匹配周度或版本周期，确保覆盖完整的需求迭代链路；多类型关联文档要求日志字段需绑定需求编号、客户标识等唯一标识，便于快速回溯对应评估与排期记录；需求承诺失真的风险要求审计需覆盖从需求收集到排期沟通的全对话链路，确保每一步业务承诺均有可追溯的对话记录。FastGPT v4.17.0 版本下的审计配置需适配这些特征，避免日志与业务数据脱节。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `chatId` 绑定规则 | 按需求编号绑定 | 客户需求池数据以需求编号为唯一标识，绑定后可快速关联对应需求的全对话链路 |
| `responseChatItemId` 映射规则 | 与需求评估表的需求ID字段对齐 | 需求评估表包含核心需求信息，对齐后可直接匹配对话中的评估沟通内容 |
| 对话日志保留时长 | 30–90 天 | 需求更新频率为周度或每版本，保留周期覆盖至少一个完整版本周期 |
| 单次日志导出条数 | 500–1000 条 | 适配需求池数据的单次检索量，避免接口超时 |
| 审计日志缓存大小 | 200–500 MB | 适配需求池数据的存储量，避免磁盘溢出 |
| 工作流日志输出路径 | 指定需求池专属目录 | 客户需求池数据需独立归档，专属目录便于快速检索与审计 |
| `detail` 字段采集范围 | 包含需求编号与客户标识 | 需匹配需求池文档的核心字段，确保日志可直接关联业务文档 |
| 多用户对话隔离 | 按客户标识隔离 | 不同客户的需求沟通需独立记录，避免数据混淆 |

## 容易做错的三处
- 现象：API创建的对话记录无法在页面日志中查看，原因：未将`chatId`与需求编号绑定，导致日志未关联到对应需求池数据条目。
- 现象：工作流中代码运行模块的console.log日志无法在审计面板中找到，原因：未开启`detail`字段的工作流日志采集配置，导致控制台输出未被纳入审计范围。
- 现象：对话预览中Human字段显示为null，原因：未在请求参数中携带需求标识相关的上下文信息，导致日志解析时无法匹配对应内容。
- 现象：手动清理对话日志后无法回溯历史需求沟通记录，原因：保留时长设置短于需求更新周期，导致跨版本的审计记录被提前删除。

## 怎么确认配好了
- 执行单条API创建对话请求，携带需求编号参数，核对日志中是否存在绑定的`chatId`与需求编号关联记录。
- 运行包含代码模块的工作流，检查审计面板中是否包含对应console.log输出内容。
- 发起多用户对话请求，核对不同用户的对话日志是否按权限隔离，仅可查看自身交互记录。
- 检查日志保留时长设置是否覆盖至少一个完整的需求更新周期，确保跨版本的审计记录不会提前丢失。
