# 游戏版号与出版申报的线上故障排查与复盘：数据库与运维

## 这个品类的数据长什么样
这个细分品类的日常数据包含申报请示文件、游戏申请表、著作权证明、审读报告等，数据来源涵盖国家新闻出版署办事服务、著作权登记系统、游戏包体及运营机构资料。数据按单款游戏申报项目为单位生成，更新频率为每款不定期，随初审修改流程动态调整。单套申报数据包含结构化字段如申报编号、著作权登记号，以及非结构化的审读报告文本，整体数据结构随申报环节逐步完善。

## 这些特征在「数据库与运维」这一环带来什么约束
多源数据接入需求要求数据库支持跨系统同步，需兼容结构化与非结构化混合存储模式。单款数据随流程动态增长且更新无固定周期，需配置动态适配的连接池避免资源耗尽。材料一致性核对环节对数据实时性要求高，需保障查询响应速度。数据出错将直接导致审批不通过，需严格保障数据一致性，禁止脏数据流入流程。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `PG_URL` | `postgresql://username:password@host:5432/fastgpt_game_approval` | 存储结构化申报表单、审批记录，适配PostgreSQL的事务一致性特性，适配FastGPT v4.17.0的数据库对接逻辑 |
| `MONGODB_URI` | `mongodb://username:password@host:27017/fastgpt_game_docs` | 存储非结构化的审读报告、著作权证明等文档，支持灵活的文档结构 |
| `DB_MAX_LINK` | `15–25 个连接` | 适配宿主机8c16G的资源上限，避免连接过多耗尽内存，按实测标定 |
| `REDIS_URL` | `redis://:password@host:6379/0` | 缓存申报状态、检索结果，加速跨环节的数据查询 |
| 重排 | `前3–5条` | 申报相关文档数量有限，过多重排会增加响应延迟 |
| 问题优化 | 按实测标定 | 需匹配申报文档的语义特征，避免过度优化偏离业务内容 |

## 容易做错的三处
- 现象：PG数据库docker部署时知识库索引无法建立，日志显示连接超时。原因：`PG_URL`配置未指向游戏申报专用库，且`DB_MAX_LINK`设置过低导致连接池耗尽。
- 现象：修改数据库密码后服务无法启动，报错提示认证失败。原因：未同步更新`PG_URL`和`MONGODB_URI`中的密码参数。
- 现象：开启问题优化和结果重排后，单条查询响应时间超过30秒。原因：重排配置设置为`前10条以上`，且未调整`DB_MAX_LINK`适配高并发检索请求。

## 怎么确认配好了
- 执行数据库连接测试脚本，验证`PG_URL`和`MONGODB_URI`可正常建立连接，无认证或网络报错。
- 提交一份测试申报文档，观察索引建立进度，确认无超时或失败日志。
- 开启问题优化和结果重排功能，测试单条查询响应时间，确认符合业务预期阈值。
- 调整`DB_MAX_LINK`参数后，查看宿主机内存与CPU占用，确认连接数未超出资源上限。
