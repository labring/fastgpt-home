# 移动端开发的线上故障排查与复盘：对话日志与审计

## 这个品类的数据长什么样
移动端开发场景的对话日志与审计数据，来源覆盖代码仓库、应用商店后台、崩溃监控平台、机型覆盖数据。数据更新节奏为每日同步或每版本发布时归档，日常关联的文档包括端版本发布单、适配清单、崩溃分析报告、应用商店资料。日志字段通常包含`chatId`、`responseChatItemId`、`detail`，以及应用版本号、设备型号、系统版本、操作路径、崩溃堆栈片段等内容，无固定统一的字段顺序，需按版本与设备维度进行分类整理。FastGPT v4.17.0版本支持该场景的多源日志关联配置。

## 这些特征在「对话日志与审计」这一环带来什么约束
由于数据来源分散且需关联多平台信息，对话日志需通过`chatId`实现跨源数据的绑定，避免排查时出现信息割裂。数据更新节奏为日更或按版本归档，要求审计环节支持按版本周期进行日志回溯与留存。移动端机型与系统版本差异大，日志需包含`detail`字段中的设备与系统信息，才能精准定位适配类问题。同时，日常文档与日志的强关联需求，要求配置项需支持绑定应用版本号，匹配端侧发布的审计流程。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `chatId`绑定规则 | 关联应用版本号与匿名化设备标识 | 匹配端版本发布单与机型覆盖数据，实现跨平台日志关联 |
| `responseChatItemId`保留上限 | 前20条会话 | 覆盖单版本内典型故障的排查周期，避免存储冗余 |
| `detail`字段配置 | 包含设备型号、系统版本、崩溃堆栈片段 | 适配移动端机型差异大的排查需求，快速定位系统适配问题 |
| 日志同步频率 | 每6小时同步一次 | 匹配数据日更节奏，兼顾实时性与存储成本 |
| 会话日志保留时长 | 90天 | 覆盖至少3个版本的复盘周期，满足端侧发布的审计要求 |
| 日志存储上限 | 1000 MB | 适配移动端日志的轻量化存储需求，避免占用过多服务器资源 |

## 容易做错的三处
- 免登录窗口无历史记录但日志可见：会话列表页无法查看过往对话，后台日志可检索到对应`chatId`，原因是未配置免登录用户的`chatId`关联规则，未将匿名会话绑定到设备标识。
- 新建模型测试时报错cannot read properties of undefined：查看会话日志详情时弹出对应报错，原因是`detail`字段未正确捕获请求参数，导致日志解析失败。
- 会话日志查看报错：点击会话详情页触发系统报错，原因是`responseChatItemId`未正确关联会话上下文，导致索引匹配异常。

## 怎么确认配好了
- 导入一条端版本发布单数据，验证`chatId`是否自动关联对应应用版本号字段。
- 生成一条测试会话，查看`detail`字段是否包含设备型号与系统版本信息。
- 检查日志同步任务，确认每6小时自动拉取崩溃监控平台的日志数据。
- 检索指定`responseChatItemId`，验证是否能返回对应会话的完整内容。
