# 质保期缺陷响应的线上故障排查与复盘：对话日志与审计

## 这个品类的数据长什么样
数据来自客户提交的质保工单、系统运行日志、合同质保条款、版本记录。日常文档包括质保工单、缺陷确认单、修复记录、客户确认单。更新频率为每日或每单生成。数据字段包含工单编号、缺陷描述、关联版本、责任方判定、修复内容、客户反馈等，单位以工单条、日志条目、版本号为基础，覆盖从缺陷上报到闭环的全流程信息。

## 这些特征在「对话日志与审计」这一环带来什么约束
由于数据来源包含多类文档与日志，对话日志需同时关联工单编号与日志条目，确保审计时可追溯到具体缺陷。更新频率的差异要求审计流程支持按单或按日触发，避免冗余数据堆积。字段中的责任方判定需与对话日志中的沟通内容交叉验证，确保边界判断准确。不同文档的格式差异要求审计工具支持多源数据的字段映射，避免信息错位，影响后续的责任界定与客户确认。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的功能设计。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 历史对话召回条数 | 前 8 条 | 适配单质保工单的常规沟通轮次，避免无关信息干扰审计 |
| 日志存储时长 | 180 天 | 匹配多数项目的质保周期，覆盖全流程审计需求 |
| 会话关联规则 | 绑定质保工单编号 | 确保每段对话日志对应唯一的质保服务工单，便于通过`chatId`快速定位 |
| 全量交互存储开关 | 开启 | 覆盖所有交互环节，满足责任边界追溯与修复验证的需求，完整记录`responseChatItemId` |
| 详细日志采集范围 | 包含系统报错与客户反馈 | 匹配日常文档的缺陷描述与修复记录字段，确保`detail`字段信息完整 |
| 审计触发条件 | 按缺陷状态变更触发 | 匹配缺陷确认、修复、闭环的关键节点，减少无效审计操作 |

## 容易做错的三处
- 现象：工作流历史记录中未显示指定回复组件的输出内容。原因：未开启对应交互环节的日志采集开关，导致`detail`字段未完整记录组件返回结果。
- 现象：FastGPT容器返回`common:code_error.error_message.403`报错。原因：未配置正确的日志存储权限，导致审计流程无法访问对应数据目录。
- 现象：清理调试预览历史记录后，关联质保工单的审计日志同步丢失。原因：未区分调试会话与正式服务会话的日志存储路径，导致批量清理误删正式数据。

## 怎么确认配好了
- 生成一条测试质保工单，发起完整沟通流程，检查对话日志是否包含所有交互环节的记录。
- 查看日志存储目录，确认对应工单的日志文件已按设定时长保留。
- 触发一次缺陷状态变更，检查审计流程是否自动生成对应审计报告。
- 导出单条工单的日志，确认导出格式符合预设要求。
