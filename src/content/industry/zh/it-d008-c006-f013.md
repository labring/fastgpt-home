# Pull Request评审的运维值班与内部工单问答：权限与数据隔离

## 这个品类的数据长什么样
Pull Request评审的数据主要来自关联的代码仓库、CI流水线、Issue链接以及贡献者提交的变更内容。日常生成的文档包含PR说明、代码评审意见、CI执行结果、合并记录等。数据更新节奏通常为日级或周级，每条数据关联对应变更的提交者、变更范围、测试状态等字段，无统一固定单位，随变更内容动态生成。

## 这些特征在「权限与数据隔离」这一环带来什么约束
Pull Request评审的数据关联多角色提交与评审主体，且来源分散，要求权限配置需匹配不同角色的操作范围。数据更新节奏随代码变更频率波动，需支持增量权限校验以适配实时或定时同步的变更内容。不同PR关联的代码仓库、CI流水线分属不同项目组或部门，需严格隔离跨组数据访问，避免非授权人员查看未关联的评审内容与工单信息。同时，合并记录与评审意见属于敏感变更信息，需限制仅项目维护者与对应模块Owner可查看完整内容。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 团队权限组 | 按项目组划分，每组对应唯一`teamId` | 匹配Pull Request评审数据按项目组隔离的需求 |
| 成员角色绑定 | 为维护者分配管理员角色，贡献者分配普通贡献角色 | 区分不同主体的操作与查看权限 |
| 数据范围隔离 | 限定仅同组成员可访问对应`teamId`的PR数据 | 适配数据来源分散的跨组隔离约束 |
| API调用鉴权 | 绑定`tmbId`校验调用方身份 | 防止未授权API调用访问PR评审数据 |
| 权限同步周期 | 每24小时同步一次 | 适配PR数据日级的更新节奏 |
| 会话过滤配置 | 按会话关联的`teamId`返回对应数据 | 确保运维值班人员仅查看负责项目的工单与PR |

## 容易做错的三处
- 现象：调用关联PR评审数据的API返回无权限报错。原因：未绑定对应`teamId`配置调用方的访问权限。
- 现象：非项目成员可查看所有PR评审记录。原因：未开启数据范围隔离配置，未限定仅同组成员可访问对应`teamId`的数据。
- 现象：不同部门的运维工单与PR数据互相可见。原因：未按项目组划分团队权限组，导致跨组数据未隔离。

## 怎么确认配好了
- 登录FastGPT v4.17.0后台，切换不同角色账号，验证仅对应角色可查看关联`teamId`的PR评审数据。
- 调用关联PR数据的API，使用未绑定`teamId`的调用方身份，确认返回无权限提示。
- 查看权限同步日志，确认每日按配置周期同步团队权限与PR数据范围。
- 切换不同项目组的账号，验证仅可查看对应项目组的PR评审与工单信息。
