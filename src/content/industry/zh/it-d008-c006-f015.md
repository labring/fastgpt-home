# Pull Request评审的运维值班与内部工单问答：知识库检索与召回

## 这个品类的数据长什么样
该品类的数据主要来自代码仓库、CI流水线、关联Issue链接及贡献者提交内容。日常文档包含PR说明文档、代码评审意见、CI执行结果、合并操作记录。数据更新频率通常为日度或周度，单条数据包含PR编号、变更文件清单、评审意见详情、CI状态标签、合并时间戳等字段，所有内容均围绕代码变更评审的核心流程展开，无额外非相关字段。

## 这些特征在「知识库检索与召回」这一环带来什么约束
数据来源包含代码变更文件与CI结果，要求检索需同时关联技术代码内容与流水线状态信息，避免召回无关的非代码类文档。日度或周度的更新节奏，要求知识库同步任务需匹配该频率，保障召回内容与最新变更同步。单条数据包含多维度字段，检索时需限定关联字段范围，避免冗余召回。PR评审的内容多为技术评审类文本，检索召回需优先匹配与代码变更意图相关的内容，减少无关结果的干扰。

## 配置怎么定
FastGPT v4.17.0版本下，以下配置项可针对PR评审场景进行定制：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `similarity` | `0.75–0.85` | 适配PR评审的技术文本相似度匹配需求，过滤低相关召回结果 |
| `limit` | `前10条` | 平衡检索召回量与后续上下文长度，适配PR评审的多关联文档查看场景 |
| `searchMode` | `综合排序` | 优先匹配PR说明与变更意图相关的内容，符合评审时的核心检索目标 |
| `usingReRank` | `开启` | 针对多维度的PR相关文档，通过重排优化结果排序逻辑，修正初始召回的顺序偏差 |
| `datasetSearchUsingExtensionQuery` | `开启` | 自动扩展PR关联的Issue、CI记录等延伸内容，提升召回的完整性 |
| `collectionIds` | `指定PR评审专属知识库集合ID` | 隔离PR评审相关的知识库数据，避免召回其他品类的无关文档 |

## 容易做错的三处
- 现象：开启`usingReRank`后检索结果排序无变化，初始召回的低相关内容仍排在前列。原因：未正确配置重排模型的关联参数，或知识库集合内的PR相关文档向量特征差异过小，导致重排无法生效。
- 现象：检索结果中CI流水线的结果文档未被优先召回，不符合评审时的预期排序。原因：未将`searchMode`设置为适配PR评审的综合排序模式，错误使用了仅匹配标题的检索模式。
- 现象：执行知识库同步时出现`getaddrinfo EAI_AGAIN mongo`报错，重启后仍无法恢复。原因：未配置知识库同步的重试机制，或MongoDB连接参数未适配PR评审知识库的高频同步需求，导致连接超时无法建立。

## 怎么确认配好了
- 手动提交一条与PR变更意图相关的检索query，查看召回结果的`similarity`分值是否落在预设的区间内。
- 开启`usingReRank`后，对比开启前后的结果排序，确认高相关的PR评审文档位置发生变化。
- 检查知识库同步任务的日志，确认每日/周度的PR相关文档已被完整同步至指定集合中。
- 查看检索返回的结果条数，确认与`limit`配置的取值一致，无额外或缺失的召回内容。
