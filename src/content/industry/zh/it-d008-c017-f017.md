# 代码评审与合并管理的运维值班与内部工单问答：部署与升级

## 这个品类的数据长什么样
该品类的数据主要来自Git仓库、CI流水线、静态扫描报告与缺陷库。日常产出的文档包含合并请求、代码评审意见、提交记录与分支策略说明，每条数据包含变更代码块、评审人标注、提交哈希、分支关联信息等字段。数据更新频率为每日或随代码提交实时更新，核心数据围绕代码变更的人工评审与合并流程展开，区别于静态代码扫描的自动化规则校验，包含人工业务语义判断的相关记录。

## 这些特征在「部署与升级」这一环带来什么约束
该品类的数据来源分散且随代码提交实时更新，部署阶段需配置适配Git仓库拉取、CI流水线日志解析的对接权限与端口，升级时需保证数据同步链路不中断，避免评审流程阻塞。合并请求、评审记录的字段结构随团队分支策略调整可能变化，部署阶段需预留字段映射的可配置项，避免因字段缺失导致流程异常。数据更新频率高，部署时需配置足够的并发处理资源，升级需采用滚动更新方式，防止全量重启引发的内部工单堆积。数据异常会直接引发严重后果，部署阶段需集成缺陷库的告警联动配置，升级前需备份全量评审与合并数据。

## 配置怎么定
以下配置说明基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `DB_MAX_LINK` | `80–150 个连接` | 适配实时代码提交带来的并发查询需求，避免数据库连接池耗尽 |
| `REDIS_URL` | `redis://:自定义密码@内网Redis地址:6379/1` | 存储临时评审缓存、合并请求状态与用户会话，内网部署保障数据安全 |
| `STORAGE_S3_ENDPOINT` | `内网对象存储服务地址` | 存储合并请求附件、评审意见附件等大文件，适配团队内部存储规则 |
| `ROOT_KEY` | `随机生成的32位字符串` | 配置系统最高权限访问密钥，避免使用默认密钥引发的安全漏洞 |
| `FE_DOMAIN` | `内网部署的IP:端口或自定义域名` | 生成评审通知链接与内部工单跳转地址，适配内网访问场景 |

## 容易做错的三处
- 现象：Docker build过程中出现`EMFILE: too many open files`报错。原因：未配置Docker容器的最大文件打开数限制，并发处理代码评审数据时耗尽系统文件句柄。
- 现象：内网部署后合并请求附件无法正常读取。原因：未正确配置`STORAGE_S3_ENDPOINT`指向内网对象存储地址，或权限配置错误导致无法访问存储资源。
- 现象：代码评审数据同步延迟超出合理范围。原因：`DB_MAX_LINK`配置值过低，数据库连接池无法支撑实时提交的并发查询请求，导致数据同步阻塞。

## 怎么确认配好了
- 执行Docker镜像构建与容器启动命令，检查启动日志中无数据库连接、存储访问相关的报错信息。
- 提交一条测试合并请求，查看系统是否能正常拉取Git仓库的代码变更、生成评审工单并完成同步。
- 访问配置的`FE_DOMAIN`地址，确认前端页面可正常加载且内部工单跳转链接有效。
- 连接`REDIS_URL`对应的缓存服务，确认临时评审状态数据可正常写入与读取。
