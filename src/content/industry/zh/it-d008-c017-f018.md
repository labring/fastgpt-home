# 代码评审与合并管理的运维值班与内部工单问答：重排与混合检索

## 这个品类的数据长什么样
该品类的典型使用主体为研发团队、Tech Lead与开源项目维护者，核心数据来源于Git仓库、CI流水线、静态扫描报告与缺陷库。日常产生的文档包括合并请求、代码评审意见、提交记录与分支策略说明。数据更新频率为每日或随代码提交实时更新，每条数据包含变更内容、评审意见、关联CI结果等字段，不同类型文档的字段结构存在差异，例如合并请求包含目标分支、变更文件列表，提交记录包含提交哈希与提交说明，无统一固定单位。

## 这些特征在「重排与混合检索」这一环带来什么约束
该品类的数据来源分散且更新频繁，要求重排与混合检索需支持实时同步Git仓库的最新提交与合并请求，避免检索到过时的变更记录。数据字段结构多样，混合检索需同时匹配代码语义、评审意见与运维工单的业务问题，例如运维值班工单询问某变更是否会引发线上服务异常，需关联对应合并请求的变更文件、评审意见与CI扫描结果。由于该品类包含人工判断的业务语义，重排环节需优先排序与运维问题直接相关的评审意见与变更影响分析，仅依赖代码相似度无法覆盖业务关联需求。此外，高频更新的数据要求检索与重排的响应速度需适配运维值班的实时性需求，避免过长等待时间。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `usingReRank` | 开启 | 该品类数据存在大量语义相似的变更记录与评审意见，重排可过滤低相关结果，提升运维工单问答的精准度 |
| `similarity` | 0.75–0.85 | 合并请求的变更内容语义差异较大，该阈值可过滤无关的提交记录与静态扫描报告，保留高匹配度的目标数据 |
| `limit` | 前10条 | 运维值班工单通常聚焦少量相关的合并请求与评审记录，过多结果会超出上下文窗口，增加模型处理负担 |
| `searchMode` | 混合检索模式 | 需同时召回Git仓库的代码数据、CI流水线结果与静态扫描报告，结合代码语义与运维业务问题完成匹配 |

## 容易做错的三处
- 现象：开启`usingReRank`后，应用内检索返回空结果，但知识库单独测试时结果正常。原因：未将重排模型关联至该场景绑定的知识库，仅在知识库测试环节加载了重排模型，应用调用时未触发重排逻辑。
- 现象：检索结果条数远少于预期的合并请求与评审记录。原因：`similarity`阈值设置过高，过滤了部分语义匹配度符合业务需求的相关数据。
- 现象：升级至FastGPT v4.8.20版本后，离线部署的重排模型配置失败。原因：未在离线环境中预下载重排模型依赖包，或配置文件中未指定本地模型的完整路径。

## 怎么确认配好了
- 进入FastGPT后台该场景的配置页，检查`usingReRank`为开启状态，`similarity`、`limit`与`searchMode`的取值符合预设配置，适配FastGPT v4.17.0版本的配置逻辑。
- 进入绑定的知识库测试页，输入运维值班相关的工单问题，验证检索结果包含合并请求、提交记录与静态扫描报告等目标数据，且重排后的结果排序符合业务预期。
- 在关联的应用中触发一次工单问答请求，查看返回的上下文是否包含正确的检索结果，无空返回或异常报错。
- 查看系统运行日志，确认重排模型的调用状态为正常，无超时或模型加载失败的记录。
