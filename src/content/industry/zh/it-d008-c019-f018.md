# 众包标注人员管理的运维值班与内部工单问答：重排与混合检索

## 这个品类的数据长什么样
本品类的数据主要来自众包平台后台、标注质量统计报表、标注人员培训考试记录、财务结算系统，服务于众包平台运营、项目主管、质检负责人等角色。日常维护的文档包括人员准入规则、标准化培训材料、月度绩效表、结算明细清单。数据更新节奏以日度和月度为主，字段包含人员唯一标识、标注任务类型、合格率、结算金额、培训考核得分等，部分为结构化表格，部分为纯文本文档。

## 这些特征在「重排与混合检索」这一环带来什么约束
多源异构的数据来源要求混合检索同时整合结构化的绩效数据、文本类的培训文档与财务结算数据，需兼顾语义匹配与关键词匹配的结合。日度更新的实时标注绩效数据要求检索链路支持增量同步，月度结算数据则适配批量处理需求。不同格式的数据要求重排环节需适配结构化字段与文本字段的权重分配，确保人员筛选、质量排名环节的检索结果匹配业务逻辑，避免因数据格式不统一导致的检索偏差，同时保障结算核对环节的结果准确性，避免错付漏付、项目延期等风险。

## 配置怎么定
本配置基于FastGPT v4.17.0版本的标准参数：
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `similarity` | 0.78–0.82 | 匹配人员准入规则、绩效数据的语义相似度阈值 |
| `limit` | 前8条 | 控制返回结果数量，适配运维工单的快速响应 |
| `searchMode` | hybrid | 结合向量检索与关键词检索的混合模式，适配多源异构数据 |
| `usingReRank` | 开启 | 对召回结果进行重排，提升高匹配度结果的优先级 |
| 召回上限 | 20条 | 覆盖足够的候选数据集，避免遗漏关键人员信息 |

## 容易做错的三处
- 现象：仅返回单条最高相似度结果。原因：错误将`limit`参数设置为1，截断了多源候选数据。
- 现象：混合检索响应时长超过12秒。原因：未限制初始召回的`limit`上限过高，多源数据并行检索未做流量控制。
- 现象：`usingReRank`开启后GPU显存占用稳定在6-7G。原因：未限制单批次重排的候选条数，批量调用导致显存占用过高。

## 怎么确认配好了
- 检查`searchMode`参数设置为hybrid，确认检索结果同时包含关键词匹配与语义匹配的内容。
- 查看`usingReRank`参数开启，确认重排后的结果排序符合人员绩效、资质等业务字段的权重优先级。
- 测试检索响应时长在10秒以内，确认混合检索配置未超出硬件负载上限。
- 核对`similarity`参数设置在0.75–0.85区间，确认相似度阈值符合业务匹配精度要求。
