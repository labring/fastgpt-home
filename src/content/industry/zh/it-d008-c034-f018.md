# 办公系统流程配置的运维值班与内部工单问答：重排与混合检索

## 这个品类的数据长什么样
该品类的数据主要来自企业OA系统、组织架构库、内部制度文件及用户反馈工单。日常维护的文档包括流程配置单、审批节点表、表单字段说明与变更记录。数据更新节奏随流程变更触发，平均每月至少一次。数据字段包含审批节点权限、表单校验规则、流程流转路径等，无统一固定单位，随具体配置项变化调整。

## 这些特征在「重排与混合检索」这一环带来什么约束
办公系统流程配置的数据来源分散且结构非标准化，混合检索需同时匹配结构化审批节点与非结构化制度文本，需兼顾向量召回的召回率与重排的精准性。数据更新频率随业务变更波动，需支持增量更新的检索适配，避免全量重建带来的资源消耗。数据字段无固定单位，重排模型需兼容多类型字段的语义匹配，无法依赖单一维度的数值权重。运维场景下需快速响应工单，检索延迟需控制在合理范围，混合检索的资源占用需适配企业现有硬件条件。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `usingReRank` | 开启 | 办公系统流程配置数据包含结构化与非结构化内容，重排可提升审批规则匹配的精准度 |
| `similarity` | 0.72–0.85 | 适配流程配置单的语义相似度匹配区间，过滤低相关的节点配置内容 |
| `limit` | 前8条 | 平衡检索召回量与运维工单的响应速度，避免过多冗余数据进入上下文 |
| `searchMode` | hybrid | 结合向量检索与关键词检索，覆盖结构化审批节点表与非结构化制度文本的召回需求，适配FastGPT v4.17.0版本的混合检索逻辑 |
| 重排模型显存配额 | 6–7 GB per GPU | 适配bge-reranker模型的实际显存占用，避免单GPU资源耗尽 |
| 重排触发阈值 | 召回前10条后触发 | 适配办公系统流程配置的数据量级，减少不必要的重排资源消耗 |

## 容易做错的三处
- 现象：混合检索响应时长超过10秒，部分工单处理超时。原因：未限制`limit`参数的召回条数，或未配置重排模型的触发阈值，导致过多数据进入检索链路。
- 现象：重排后仅保留最高相似度结果，审批规则匹配遗漏低相关但关键的节点配置。原因：错误配置`limit`参数仅返回1条结果，未保留足够候选集供重排筛选。
- 现象：重排模型调用后GPU显存占用过高，触发系统资源告警。原因：未限制单GPU的重排模型并发调用数，或未按实测标定显存配额，导致多GPU同时占用大量显存。

## 怎么确认配好了
- 执行模拟运维工单查询，检查检索结果的条数与`limit`参数设置一致。
- 查看重排模型的调用日志，确认`usingReRank`功能已正常开启，结果排序符合语义匹配逻辑。
- 测试混合检索与纯向量检索的响应时长，确认混合检索的延迟在合理范围内。
- 查看GPU资源监控面板，确认重排模型的显存占用未超过预设配额。
