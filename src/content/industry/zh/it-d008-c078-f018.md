# 机柜上架与布线的运维值班与内部工单问答：重排与混合检索

## 这个品类的数据长什么样
该品类的数据主要来自DCIM系统、内部资产系统、网络拓扑文档与客户提交的工单。日常产生的文档包括机柜上架申请单、机柜布线图、端口标签对照表、设备施工记录。数据更新以单次工单或每日为节奏，字段包含机架位编号、线缆规格、端口映射关系、施工验收状态等，无统一批量更新周期，仅随实际施工与工单流转同步更新。

## 这些特征在「重排与混合检索」这一环带来什么约束
该品类数据分散于多个异构系统与文档类型，混合检索需跨数据源召回，对多源数据的格式对齐与召回精度提出约束。数据随工单实时更新，要求检索链路需匹配最新的机架位、端口映射信息，避免召回过期数据。不同文档的字段差异显著，上架申请单含申请信息，布线图含物理位置信息，重排环节需针对机架位编号、端口标签等核心字段调整排序权重，同时需平衡检索延迟与召回数量，避免因多源召回与重排模型调用导致的响应超时。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 相似度阈值 | 0.72–0.85 | 过滤与当前工单机架位无关的召回结果，确保核心匹配度 |
| 单次召回上限 | 前10条 | 减少重排环节的计算量，适配运维场景的快速响应要求 |
| 检索模式 | 混合检索 | 结合向量检索与关键词检索，覆盖结构化DCIM数据与非结构化施工记录 |
| 重排开关 | 开启 | 对召回结果按工单关联的机架位、端口标签重新排序 |
| 重排召回条数 | 前6条 | 聚焦高匹配度的结果，避免过多计算导致延迟 |
| 模型调用超时 | 600秒 | 适配API调用的延迟情况，避免因模型响应超时中断检索流程 |

本配置适用于FastGPT v4.17.0版本。

## 容易做错的三处
- 现象：开启混合检索后响应时长超过10秒，超出运维工单的可接受延迟。原因：未限制单次召回上限，召回结果过多导致重排环节计算量过大，同时多源检索跨多个系统拉取数据，叠加延迟。
- 现象：调用重排模型后，GPU显存占用快速增长至6-7G且每个GPU均被占用。原因：未配置重排模型的并发调用限制，同时未指定单GPU承载的模型实例数量，导致多个请求同时加载模型权重。
- 现象：离线接入reranker模型时返回rerank error，提示detail字段为空或格式错误。原因：未按照FastGPT文档配置模型的本地部署路径与端口，或模型文件缺失必要的依赖包，导致模型启动失败。

## 怎么确认配好了
- 查看检索日志，确认召回结果的数量与配置的单次召回上限一致。
- 测试提交关联特定机架位的工单，核对重排后的结果是否将该机架位的文档排在前列。
- 检查模型调用日志，确认重排环节的响应时长符合预期，未出现超时报错。
- 查看系统状态面板，确认重排模型的GPU显存占用未出现异常增长。
