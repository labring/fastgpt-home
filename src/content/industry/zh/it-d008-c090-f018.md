# 版本发布与Release Notes的运维值班与内部工单问答：重排与混合检索

## 这个品类的数据长什么样
本品类数据主要来自Git仓库标签、合并提交记录、CI构建制品与Issue里程碑。日常产出文档包含版本发布说明、变更日志、版本标签清单与发布检查单。数据按版本周期更新，每份文档包含版本号、变更类型、影响范围、关联Issue编号、制品校验值等字段，无统一固定格式，随项目维护习惯略有差异。

## 这些特征在「重排与混合检索」这一环带来什么约束
本品类数据按版本周期更新，单次检索的数据集随版本迭代逐步扩容，需通过召回上限控制检索效率。文档格式随项目维护习惯存在差异，混合检索需兼容结构化元数据与非结构化变更描述。变更类型包含破坏性变更、功能新增等多类，重排环节需优先匹配运维值班关注的高影响条目。关联Issue与制品校验值等元数据，要求混合检索同时覆盖文本内容与字段信息，避免遗漏关键关联信息。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `searchMode` | 混合检索 | 适配本品类多源异构的变更与元数据内容，覆盖文本与字段信息 |
| `limit` | 前20条 | 控制检索数据集规模，适配版本发布类数据的单次更新体量 |
| `similarity` | 0.75–0.85 | 过滤低相关的变更条目，聚焦高匹配度的运维关注内容 |
| `usingReRank` | 开启 | 优先排序高影响的破坏性变更与核心发布项，符合运维值班的优先级需求 |
| 重排召回上限 | 前10条 | 平衡重排计算开销与结果准确性，适配单版本的变更条目数量 |
| 上下文窗口 | 按实测标定 | 适配不同版本发布文档的长度，避免截断关键信息 |

## 容易做错的三处
- 现象：配置`usingReRank`为开启后，返回结果仍未按优先级排序，重排开关状态显示为关闭。原因：未在知识库绑定的检索配置中保存启用重排的设置，或配置未同步至检索引擎。
- 现象：混合检索返回结果与语义检索差异较小，未覆盖关联Issue与制品的元数据条目。原因：未正确配置混合检索的元数据匹配规则，仅启用了文本语义检索。
- 现象：检索结果条数超出预期上限，导致页面加载缓慢。原因：`limit`配置值过大，未适配本品类单版本变更条目的平均体量。

## 怎么确认配好了
- 进入FastGPT v4.17.0的知识库配置页面，检查`searchMode`、`limit`、`similarity`与`usingReRank`的设置是否与配置表一致。
- 发起测试检索，输入包含版本号与变更类型的查询词，核对返回结果的排序是否符合高影响条目优先的规则。
- 查看检索日志，确认单次召回条数与重排召回上限的取值符合配置要求。
- 对比语义检索与混合检索的返回结果，确认混合检索覆盖了元数据关联的条目。
