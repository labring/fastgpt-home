# IT服务台工单处理的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据来自企业ITSM系统、电话或在线聊天记录、资产系统及内部知识库。日常生成的文档包含服务请求单、事件工单、处理记录与用户满意度表。数据更新频率为日级或实时，字段涵盖工单编号、问题分类、处理进度、用户反馈等，仅保留业务原生的记录字段与关联标识，无额外自定义统计数值。

## 这些特征在「上下文与 token」这一环带来什么约束
工单数据的实时更新要求上下文需同步抓取最新处理记录，避免依赖过时信息。多来源的数据结构差异较大，需要统一上下文的字段映射规则，防止无效token消耗。服务请求单与处理记录的关联字段较多，上下文召回需精准匹配关联ID，避免无关内容占用配额。知识库的日级更新节奏要求定期同步上下文引用的排障文档，防止调用过期内容。同时，工单的单条长度差异大，需通过`maxContext`和`quoteMaxToken`限制总token占比，避免超出模型的单轮调用上限。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 前8–12条 | 匹配IT服务台工单的历史处理记录数量，平衡上下文完整性与token消耗 |
| `quoteMaxToken` | 1800–2200 token | 适配服务请求单与处理记录的典型长度，避免单条内容超出模型限制 |
| 上下文同步频率 | 实时 | 匹配工单数据的日级/实时更新要求，确保调用最新的处理记录 |
| 关联匹配精度 | 85% | 精准匹配工单编号与处理记录的关联ID，减少无效召回内容 |
| 冗余内容过滤 | 开启 | 排除无关联的历史工单记录，减少无效token占用 |

## 容易做错的三处
- 现象：调用时返回额度不足的报错，与oneapi显示的已用额度不符。原因：未正确配置token统计规则，导致输入与输出token的计算逻辑与oneapi的计费规则不匹配。
- 现象：工作流中设置上下文数量为0，但实际仍有历史工单内容传入API。原因：未关闭系统默认的上下文召回开关，或关联的知识库自动同步了历史处理记录。
- 现象：界面无法分别显示AI对话的输入tokens数量和输出tokens数量。原因：未开启对话token统计的配置项，或使用的FastGPT版本低于v4.17.0。

## 怎么确认配好了
- 查看工作流的上下文预览面板，确认传入API的内容与设置的上下文条数一致。
- 调用测试工单处理流程，核对界面显示的输入与输出tokens数量与实际计算的结果匹配。
- 检查oneapi的计费日志，确认token消耗与FastGPT的统计结果对齐。
- 验证当设置上下文数量为0时，API请求中无冗余的历史工单内容。
