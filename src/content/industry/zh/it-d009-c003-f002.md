# IT资产盘点的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
IT资产盘点的数据来自资产管理系统、采购系统、财务固定资产模块、终端管理平台，日常产出资产台账、盘点表、领用归还单、报废申请四类文档。文档字段包含资产编号、名称、使用人、存放位置、权属状态等，更新频率多为月、季或年度。数据处理主体为IT资产管理员、财务资产岗及桌面支持人员，核心聚焦资产的权属、位置与使用人信息。

## 这些特征在「上下文与 token」这一环带来什么约束
IT资产盘点的多源异构数据来源、固定更新周期及强关联字段特征，对上下文与token配置带来明确约束。月度或季度更新的资产数据无需高频刷新上下文，但单次调用需覆盖完整盘点周期内的台账、盘点表等多份文档，易导致token超额消耗。资产编号、使用人、存放位置等强关联字段，要求上下文保留字段间的关联关系，分段处理时若未保留完整字段组，会出现上下文关联断裂的问题。不同来源文档的字段格式差异，会增加token计算的冗余量，需提前对齐字段结构以优化token使用效率。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文token数 | 8000–12000 token | 覆盖单盘点周期内的台账、领用单、报废申请等多份文档的核心字段，避免token不足截断关键关联信息 |
| 上下文分块长度 | 1000–1500 字符 | 匹配资产文档单条记录的字段总量，确保每个分块包含完整的资产信息组，避免字段关联断裂 |
| 上下文重叠长度 | 100–200 字符 | 保留相邻分块间的资产编号、使用人等关键字段，解决分段后上下文关联不上的问题 |
| `quoteMaxToken` | 500–800 token | 限定单条引用片段的token上限，避免单条引用占用过多上下文空间 |
| `maxContext` | 按实际文档总量标定 | 适配月度/季度更新的资产数据规模，确保单次调用可加载完整的盘点相关文档集合 |

## 容易做错的三处
- 现象：调用时出现token超出限制的系统报错，或返回结果被截断。原因：未根据月度/季度更新的资产文档总量调整上下文token配置，设置值低于单盘点周期内所有关联文档的总token消耗。
- 现象：资产信息匹配结果中，资产编号与使用人、存放位置无法对应。原因：上下文分块长度设置过小，或重叠长度不足，导致相邻分块未保留完整的资产关联字段组。
- 现象：多知识库联合调用时，仅匹配当前问题的资产记录，未关联历史领用、报废记录，导致分类结果偏向兜底类别。原因：未开启历史上下文加载配置，未将历史盘点文档纳入当前调用的上下文范围。

## 怎么确认配好了
- 上传单份资产台账文档，触发上下文调用，核对返回结果是否包含完整的资产编号、使用人、存放位置字段。
- 上传多份关联文档（如台账+领用归还单），核对上下文调用是否能覆盖所有上传文档的核心信息。
- 调整上下文分块与重叠长度参数，测试不同配置下的字段关联完整性，确认无字段断裂问题。
- 使用FastGPT v4.17.0版本的系统日志查看功能，核对单次调用的token消耗情况，确保未超出预设上限。
