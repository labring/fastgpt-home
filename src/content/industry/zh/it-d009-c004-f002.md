# IT采购与供应商管理的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据通常来自企业内部采购系统、供应商报价文件、预算表及合同系统。日常产出的文档包含采购申请单、比价记录表、正式合同与验收单据，字段多包含采购编号、供应商资质、预算额度、交付周期、条款细则等。数据更新以每笔采购订单为周期，月度累计更新量随采购规模波动，单份文档结构规整但字段关联度高，跨文档的关联信息多集中在供应商履约、预算执行等环节。

## 这些特征在「上下文与 token」这一环带来什么约束
采购类文档的字段关联度高，单份文档的有效信息分布较散，若按默认粒度分块，易割裂采购编号、供应商信息与条款的关联关系，导致召回信息不完整。数据更新以单订单为周期，新增数据的格式与存量数据高度一致，无需频繁调整分块规则，但单次召回需覆盖同订单下的多份关联文档，容易超出token上限。同时，供应商报价与合同条款的文本长度差异较大，长文本块会占用过多token，短文本块则会增加召回冗余，提升token消耗。

## 配置怎么定
本文基于FastGPT v4.17.0版本编写，以下配置适配该品类的业务特征：
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 匹配采购类文档的单字段组长度，避免割裂采购编号、供应商名称等关联信息 |
| 重叠长度 | 150–200 字符 | 保留跨分块的关键关联字段，确保召回信息的完整性 |
| `maxContext` | 8000–10000 token | 覆盖单订单下3-4份关联文档的总token消耗，符合企业采购流程的常规信息范围 |
| `quoteMaxToken` | 1500–2000 token | 限制单条召回文本的长度，避免长合同条款或大额报价表占用过多上下文空间 |
| 单次召回上限 | 前6条 | 匹配月度采购订单的平均关联文档数量，减少无效召回的token消耗 |

## 容易做错的三处
- 现象：默认分块参数下，Excel格式的供应商报价表被拆分为过大的数据块，召回结果冗余且token消耗过高。原因：未针对采购类文档的字段结构调整分块长度与`quoteMaxToken`参数，默认分块未匹配采购单的字段组长度。
- 现象：调用时出现Reached the max retries per request limit报错。原因：未限制单次召回的文档数量，导致单次请求的token超限，触发重试上限。
- 现象：对话中返回的上下文信息超出当前采购流程的实际需要。原因：未设置合理的`maxContext`参数，将无关的历史采购订单信息纳入当前上下文。

## 怎么确认配好了
- 上传单份采购申请单与关联的比价记录，检查分块后的文本是否保留了采购编号与供应商名称的关联信息。
- 发起包含采购需求的查询，核对召回的文档数量与单条文本的token占比，调整参数至符合当前流程的信息范围。
- 查看token消耗日志，确认单次对话的token消耗未超出预设的业务阈值，无不必要的长文本召回。
- 测试多订单关联查询，确认召回的上下文仅包含当前采购流程的相关文档，未混入无关历史数据。
