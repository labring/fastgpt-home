# Issue分拣与响应的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自GitHub或Gitee Issue、代码仓库版本日志、用户提交的环境信息与问题复现说明。日常维护的文档包含Issue模板、标签规则、历史回复记录、责任模块映射表。数据更新频率为日更或周更，单条数据包含问题标题、描述、关联代码片段、上报时间、用户标签等字段，以文本、标识类内容为主，无固定量化单位字段。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据以非结构化文本为主，包含代码片段、环境日志与详细复现步骤，单条数据的token占用差异显著。Issue的上报频率随项目热度波动，高峰时段单日内会产生大量新数据，需要在上下文召回环节控制单轮处理的token总量，避免超出模型上限。同时，数据需关联代码仓库的责任模块信息，若上下文召回范围过大，会引入无关内容，影响分拣的精准度。若未针对短Issue做最小上下文配置，或未限制`quoteMaxToken`的取值，会浪费token配额，导致长Issue的有效信息无法完整召回。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 相似度阈值 | 0.35–0.45 | 匹配该品类的Issue文本与知识库内容的关联度，避免召回无关的历史回复或标签规则 |
| `quoteMaxToken` | 8000–12000 token | 适配该品类单条Issue的平均token占用，同时预留空间给模型的分拣逻辑 |
| `maxContext` | 14000–16000 token | 匹配FastGPT v4.17.0的基础上下文上限，避免超出模型的总token限制 |
| 单次召回条数 | 前3–5条 | 控制单轮上下文的总token占用，避免引入过多无关的历史Issue数据 |
| 上下文截断策略 | 按内容重要性排序截断 | 优先保留Issue的复现步骤、责任模块标记等核心信息，丢弃非关键的冗余内容 |

## 容易做错的三处
- 现象：设置相似度阈值为0.4后，仍无法召回所需的标签规则或历史回复记录。原因：未结合该品类的Issue文本特征调整阈值，阈值过低会召回无关内容，过高则遗漏相关匹配项。
- 现象：模型输出在12288 token时被截断，界面显示超出回复限制。原因：未将`maxContext`配置为匹配模型的总token上限，同时未限制`quoteMaxToken`的取值，导致上下文总占用超出模型支持范围。
- 现象：单轮处理时返回的关联Issue数量过多，导致处理耗时增加。原因：未限制单次召回条数，引入了大量非必要的历史数据，占用过多token配额。

## 怎么确认配好了
- 查看单条Issue的token占用日志，确认`maxContext`的配置未超出模型的总token限制。
- 测试不同长度的Issue提交，检查上下文召回的内容是否包含核心的复现步骤与责任模块信息。
- 对比调整配置前后的召回结果，确认相似度阈值的取值符合当前知识库的内容特征。
- 检查输出日志，确认未出现token超出限制的报错提示。
