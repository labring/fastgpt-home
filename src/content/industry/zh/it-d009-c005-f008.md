# Issue分拣与响应的需求与设计文档起草：工作流编排

## 这个品类的数据长什么样
该品类的数据主要来自GitHub或Gitee Issue、代码仓库版本日志、用户环境信息与代码仓库提交记录。日常维护的文档包括Issue处理模板、标签规则库、历史回复记录与问题复现说明文档。数据更新频率为日或周，核心字段包含Issue编号、标签、优先级、复现步骤、关联代码模块与处理状态，未包含额外统计类量化指标。

## 这些特征在「工作流编排」这一环带来什么约束
数据来源绑定外部代码仓库，要求工作流支持对接GitHub/Gitee的事件接口实现实时触发；数据更新频率为日或周，要求工作流配置合理的重试与超时机制避免单次调用失败。日常文档包含固定字段与规则，要求工作流可绑定对应字段实现自动分类与标记。核心耗时环节为问题分类、复现信息补齐与责任模块标记，要求工作流内置自动化节点覆盖这些环节，同时配置异常告警避免问题积压影响处理效率。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 触发规则 | 按GitHub Issue创建/更新事件触发 | 依据数据来源为GitHub/Gitee Issue，需实时响应新提交的问题 |
| `variables` | 绑定Issue编号、标签、复现步骤字段 | 依据日常文档包含标签、Issue编号与复现说明，用于工作流转分支判断 |
| `nodeId` | 绑定分类节点、告警节点的唯一标识 | 依据工作流需要按节点执行不同的处理逻辑 |
| 重试次数 | 3次 | 依据数据更新频率为日/周，避免单次接口调用失败导致流程中断 |
| 超时阈值 | 600秒 | 依据对接外部代码仓库接口的常规响应时长 |
| 单次同步Issue数量 | 前20条 | 依据GitHub API的分页默认上限，避免单次请求过载 |
| 消息输出格式 | 标准Markdown | 依据需要生成可复用的问题处理文档 |

## 容易做错的三处
- 工作流配置`variables`时未绑定SQL查询结果字段，导致AI对话框未展示查询到的Issue分拣结果，原因是未将查询数据集映射到工作流的输出变量。
- 无外网私有化部署后工作流编辑界面显示客户端报错，原因是未配置本地静态资源的加载路径，导致前端依赖无法正常加载。
- 使用Qwen2.5模型时工具调用失败，原因是未将`nodeId`正确绑定到工具调用节点，导致模型无法识别触发逻辑。

## 怎么确认配好了
- 手动触发GitHub Issue的创建事件，验证工作流是否自动启动并生成对应标签分类记录。
- 查看工作流的`variables`绑定字段，确认Issue编号、标签等核心数据已正确映射到流程节点。
- 在FastGPT v4.17.0版本的无外网测试环境中，验证工作流编辑界面是否正常加载。
- 配置工具调用节点，验证模型是否能按预期触发对应执行分支逻辑。
