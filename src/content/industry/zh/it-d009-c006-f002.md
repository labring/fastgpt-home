# Pull Request评审的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的数据主要来自代码仓库、CI流水线、Issue链接与贡献者提交内容，更新频率多为日或周。日常关联文档包含PR说明、代码评审意见、CI结果与合并记录，涉及主体为项目维护者、模块Owner及贡献者。数据字段包含变更范围、测试通过状态、关联Issue编号、提交者信息等，无统一固定格式，随项目协作规则调整。

## 这些特征在「上下文与 token」这一环带来什么约束
数据来源分散的特性要求上下文聚合时需覆盖代码变更、评审意见、CI结果等多类内容，避免遗漏关键决策信息。更新频率为日或周，意味着上下文同步无需高频触发，可按项目迭代周期配置刷新节奏，减少冗余资源消耗。文档结构不统一，分块处理时需适配PR说明、评审记录等不同格式的文本，避免分块断裂破坏内容连贯性。字段多样性则要求上下文召回时优先匹配变更意图、测试状态等核心字段，减少无关内容占用token配额，提升上下文精准度。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配PR评审相关多源文档的总长度，避免超出模型上下文上限 |
| `quoteMaxToken` | 1500–2000 token | 限定单条召回内容的token占用，平衡召回数量与单条内容的信息量 |
| 上下文同步周期 | 每日凌晨2点 | 匹配多数项目的日更迭代节奏，减少不必要的资源消耗 |
| 召回内容优先级 | 先PR说明、再评审意见、最后CI结果 | 贴合PR评审的核心决策逻辑，优先保障变更意图相关内容的召回 |
| 单次召回上限 | 前8条内容 | 控制总token消耗，避免上下文过载影响模型响应效率 |

## 容易做错的三处
- 出现「上下文token超出模型限制」报错，且日志显示召回内容总长度超过配置值。原因是未正确设置`maxContext`参数，或未限制单条召回内容的token配额。
- 搜索结果无法结合PR历史上下文，返回内容与当前变更意图无关。原因是未将PR说明、评审记录等核心数据纳入上下文召回范围，仅使用了孤立的搜索query。
- 私有化部署后访问路径无法匹配预设上下文，导致应用无法正常加载。原因是未在部署配置中正确配置应用访问的上下文路径，或未同步更新反向代理规则。

## 怎么确认配好了
- 查看FastGPT v4.17.0的应用配置页面，确认`maxContext`、`quoteMaxToken`参数的取值与预设配置一致。
- 提交一条模拟PR变更，触发上下文召回流程，检查召回结果是否包含PR说明、评审意见等核心内容。
- 访问私有化部署的应用路径，确认是否能正常加载应用且上下文路径配置生效。
- 查看系统监控面板，确认上下文同步任务按预设周期执行，无异常报错。
