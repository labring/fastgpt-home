# Pull Request评审的需求与设计文档起草：表单与交互

## 这个品类的数据长什么样
该品类的数据主要来自代码仓库、CI流水线、Issue链接与贡献者提交。日常产出的文档包含PR说明、代码评审意见、CI结果与合并记录。数据更新频率为日或周，核心字段包括变更范围、关联Issue编号、测试状态、合并前置条件与评审人信息。典型使用主体为项目维护者、模块Owner与贡献者，数据围绕可合并的代码变更流转，区别于Issue分拣与响应类任务。

## 这些特征在「表单与交互」这一环带来什么约束
数据来源分散要求表单需覆盖代码变更范围、关联Issue、测试结果等多类信息，避免遗漏核心评审依据。核心字段的缺失会直接导致评审延迟或合并出错，因此需设置必填校验规则。典型评审主体的角色明确，需限定`userSelect`节点的可选用户范围以确保评审专业性。变更意图确认是最耗时的环节，表单需提供引导文案以统一信息收集标准，降低跨角色沟通成本。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 表单输入节点 `formInput` | 测试示例：从Pull Request评审字段中选 3 个作为必填输入，实际字段按任务确定 | 该节点收集用户输入；缺必填项时需排查交互状态，避免后续节点无法获得完整输入 |
| 用户选择节点 `userSelect` | 测试示例：设置 2 个业务选项，逐项检查对应分支 | 该节点处理用户选择；Pull Request评审相关记录的查询、筛选需由后续接口或外部系统实现 |
| 提交后字段传递 | 测试示例：准备 10 条Pull Request评审输入样本，覆盖完整填写、缺必填项和取消操作 | 对照输入与节点输出，核对后续节点是否收到对应字段；结果阈值按实际任务确定 |
| 外部实施项：输入引导文案 | 需由外部系统另行实现；由外部业务系统提供变更意图、测试验证、文档更新三类引导内容 | 针对变更意图确认环节，统一信息收集标准，引导内容由外部系统实现 |
| 外部实施项：表单提交超时控制 | 需由外部系统另行实现；测试示例值设为600秒，由外部工作流环境实现 | 适配CI流水线执行周期，避免表单提交阻塞外部工作流 |
| 外部实施项：必填项校验 | 需由外部系统另行实现；关联Issue编号、测试结果链接为必填字段 | 规避合并冲突与回归缺陷等出错后果 |

## 容易做错的三处
- 调试预览时出现`quote type error`报错，可核对表单字段的变量引用语法是否匹配预设格式，是否使用了正确的引用规则。
- 表单未正常显示引导文案，可核对是否已正确配置外部引导内容，是否保存了表单节点的配置变更。
- 跨分支调用表单节点失败，可核对是否正确配置了外部工作流分支关联，是否正确传递了节点参数至后续节点。

## 怎么确认配好了
- 提交一条测试用表单，检查`formInput`节点收集的关联Issue编号与代码变更范围信息是否正确传递至后续节点。
- 尝试提交未填写关联Issue编号的表单，确认系统触发必填校验提示。
- 触发`userSelect`节点时，确认外部权限管理系统提供的可选用户范围仅包含项目维护者与模块Owner。
- 进入调试预览模式，验证输入引导文案正常显示在表单顶部。

所有核对动作均基于FastGPT v4.17.0版本的功能逻辑。
