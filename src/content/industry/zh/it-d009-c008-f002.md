# 专题活动运营的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据通常来自活动后台的排期数据、内容库的活动文案素材、流量平台的活动曝光数据，以及用户反馈的活动参与记录。日常产出的文档包含活动整体方案、资源位排期表、活动页面宣传文案、事后复盘报告。数据更新节奏以周为单位，重大节假日前后会临时调整更新频率。文档结构通常包含活动目标、执行节点、资源分配、效果预估等字段，无统一强制格式，随活动规模调整。

## 这些特征在「上下文与 token」这一环带来什么约束
活动类文档具有明确的周期属性，活动前的文案与排期数据需在短时间内整合，上下文窗口需覆盖活动全周期的关联素材，避免跨周期数据干扰。活动文案的长度差异较大，从短标题到长复盘报告都有，token分配需适配不同文档的长度区间。资源位排期涉及多部门协调的关联数据，上下文召回需优先匹配同活动周期内的资源信息，防止跨活动资源混淆。活动数据的更新频率波动大，上下文的刷新机制需适配临时调整的流量数据，避免使用过期的活动效果数据。

## 配置怎么定
以下配置项在FastGPT v4.17.0版本中可直接在应用编辑页面完成调整：
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 4000-6000 token | 覆盖单场活动的核心方案、文案与排期数据，适配活动文档的总长度范围 |
| `quoteMaxToken` | 3000-5000 token | 适配活动复盘报告与长文案素材的token需求，避免长文档被截断 |
| 单次搜索上限 | 前8-12条关联文档 | 活动类文档多按活动周期分组，限定召回条数可避免token溢出 |
| 相似度阈值 | 0.75-0.85 | 区分同周期内的活动关联数据与无关内容，防止召回冗余信息 |
| 重排规则 | 按活动周期排序 | 优先召回当前正在执行或即将执行的活动数据，符合运营的使用逻辑 |

## 容易做错的三处
- 现象：配置`quoteMaxToken`或单次搜索上限数值过大时，上下文无法正常发送至大模型。原因：活动类文档的总token超出大模型的上下文承载上限，导致系统截断或丢弃关联数据。
- 现象：离线部署的向量模型调用时出现外网请求报错，日志显示尝试访问cl100k.tiktoken。原因：本地部署的tokenizer依赖未正确配置，未使用本地缓存的token规则文件。
- 现象：配置的并发与token处理速率超出硬件承载范围时，活动文案的生成或上下文召回出现卡顿。原因：未根据活动运营的实时数据量调整硬件资源分配，导致token处理队列积压。

## 怎么确认配好了
- 上传一份完整的活动方案文档，查看上下文预览中是否包含同周期的排期、文案等关联数据。
- 调整`maxContext`或`quoteMaxToken`参数至不同区间，测试长文档的召回与拼接是否正常，无明显截断。
- 模拟高并发的活动数据查询，检查上下文的召回速度与token处理是否符合预期。
- 查看系统日志，确认无tokenizer相关的外网请求报错。
