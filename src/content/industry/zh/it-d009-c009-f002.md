# 个人信息保护合规的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
数据来自业务系统、App权限清单、隐私政策、用户请求记录，更新频率为季度或每次产品版本变更时。日常产出的文档包含个人信息清单、处理规则、影响评估报告、用户授权文本，文档包含结构化字段与非结构化文本段落，字段涵盖信息类型、处理目的、接收主体、授权范围等，单份文档的字符跨度存在较大差异。

## 这些特征在「上下文与 token」这一环带来什么约束
数据来源的多样性导致上下文拼接时的内容复杂度提升，需兼顾结构化字段与长文本段落的完整保留。更新频率不固定，每次产品变更后需重新加载全量合规文档，对上下文窗口的加载效率有直接要求。文档覆盖个人信息全处理链路，需保留场景与授权的关联信息，不能随意截断关键合规逻辑。字段的多样性要求上下文匹配时需保留字段关联，避免token被无效占用，同时需确保合规文档的处理逻辑不被破坏。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 8000–12000 字符 | 覆盖单份合规文档的核心内容，避免截断关键合规条款 |
| `maxContext` 加载上限 | 10000 字符 | 匹配合规文档的平均字符规模，适配FastGPT v4.17.0的基础加载能力 |
| `quoteMaxToken` 配额 | 4000–6000 token | 预留足够token用于合规文档的场景梳理与合法性确认 |
| 上下文召回条数 | 前 4–6 条 | 平衡信息完整性与token消耗，避免超出模型输入限制 |
| 上下文格式校验 | 开启控制字符过滤 | 避免合规文档中的特殊符号导致工具调用格式异常 |

## 容易做错的三处
- 工具调用节点返回Invalid JSON报错，日志显示Bad control character，原因是合规文档中的非结构化段落包含未转义的控制字符，未在上下文拼接前做格式校验。
- 模型提示上下文长度不足，界面显示token占用超限，原因是配置的`maxContext`取值未匹配合规文档的实际字符规模，导致核心合规条款被截断。
- 全局token变量无法传递到聊天流程，导致上下文调用缺失指定合规文档，原因是未在全局配置中绑定合规文档的token关联参数，未完成变量映射。

## 怎么确认配好了
- 上传单份典型合规文档，测试上下文拼接功能，确认未出现关键条款截断。
- 运行工具调用节点，检查输出的JSON格式是否符合要求，无控制字符报错。
- 配置全局token变量，发起测试调用，确认上下文加载包含指定的合规文档内容。
- 调整`maxContext`与`quoteMaxToken`的取值，验证token消耗与模型响应的匹配度。
