# 云账单与成本核算的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
这个品类的核心数据来自云计费系统、标签数据、订单系统与资源监控工具，日常产出账单明细、成本分摊表、资源利用率报表、优化建议单四类文档。数据更新节奏通常为日度或月度，字段包含计费项、资源ID、归属标签、费用金额、使用时长等，单位多为元、小时、GB等。核心处理环节聚焦标签归属核对、异常费用排查与成本分摊解释，需关联多系统的异构数据。该品类文档聚焦费用口径的资源消耗解释，与资源扩缩容类文档的核心方向不同。

## 这些特征在「上下文与 token」这一环带来什么约束
云账单与成本核算的文档多为结构化明细数据，且需关联多系统的异构信息，上下文窗口需承载跨源的标签、费用、资源标识等字段。日度/月度更新的批量数据会带来长上下文的加载压力，若上下文长度不足，会导致成本分摊解释时缺失关键关联项。同时，异常费用排查需回溯历史账单数据，过长的上下文会占用过多token配额，影响文档起草的效率与准确性。此外，账单明细的字段多为数值与编码类内容，token统计需精准匹配结构化数据的字段长度，避免token分配失衡。

## 配置怎么定
本页配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 适配云账单多字段关联的上下文需求，避免丢失标签、费用关联信息 |
| `quoteMaxToken` | 1500–2000 token | 匹配单条账单明细的字段长度，确保引用数据完整 |
| 单次搜索上限 | 前6条 | 平衡异常费用排查的回溯范围与token占用，避免过多历史数据加载 |
| 分块长度 | 4000–5000 字符 | 适配云账单单页数据量，减少分块后的上下文碎片 |
| 问题优化 | 开启 | 优化成本分摊解释类查询的表述，减少无效token消耗 |

## 容易做错的三处
- 设置`quoteMaxToken`为1500后，仍检索到超出该长度的切块数据，原因是未同步调整知识库分块长度与上下文窗口的关联配置，导致切块数据未按引用阈值截断。
- 工作流中无法触发上下文历史清空，原因是未针对账单查询的特定场景配置触发条件，导致重置逻辑未生效。
- 无法查看单轮问答的token使用明细，原因是未在全局配置中启用token统计功能，导致日志中无对应字段。

## 怎么确认配好了
- 上传单条账单明细文档，查看检索结果的引用长度是否符合`quoteMaxToken`的设置值。
- 运行包含多轮账单查询的工作流，验证上下文历史是否在触发指定条件后被清空。
- 查看问答日志面板，确认是否存在token使用量的统计字段。
- 调整`maxContext`的取值，观察上下文加载的文档数量是否对应变化。
