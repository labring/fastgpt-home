# 代码评审与合并管理的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
这个品类的数据来自Git仓库、CI流水线、静态扫描报告、缺陷库，更新频率为每日或每次代码提交后。核心文档包括合并请求、代码评审意见、提交记录、分支策略说明。合并请求包含变更文件列表、提交哈希、评审人清单与变更描述；提交记录包含commit信息、变更时间与作者信息；静态扫描报告包含代码违规项与严重等级。数据结构随提交实时更新，单次变更的关联数据量随项目规模变化。

## 这些特征在「上下文与 token」这一环带来什么约束
多源异构的数据需要关联匹配，上下文需同时覆盖代码变更、评审意见与扫描结果，token消耗随关联数据量增长。每次提交的实时更新要求上下文能快速加载最新数据，过长的上下文会导致处理超时。合并请求的变更范围差异较大，小变更仅需少量关联数据，大变更则需要更多上下文，需避免无关数据占用token配额。评审意见与提交记录存在强关联，上下文需保留这种关联关系，否则会导致变更判断出现偏差。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 适配代码评审场景下合并请求关联的变更记录、评审意见总token量，按实测标定 |
| `quoteMaxToken` | 2000 token | 限制单条评审意见或提交记录的最大截取长度，避免单条内容过长占用过多上下文配额 |
| 分块长度 | 1500 字符 | 适配Git提交记录、评审意见的常规内容长度，平衡上下文完整性与token消耗 |
| 重叠长度 | 200 字符 | 保留分块间的上下文关联，避免关键变更描述被截断 |
| 单次召回上限 | 前6条关联记录 | 匹配合并请求的核心变更源，减少无关数据占用token |
| 适配版本 | FastGPT v4.17.0 | 适配当前版本的上下文处理逻辑，确保配置生效 |

## 容易做错的三处
- 调用时返回“invalid api key”或“endpoint not found”报错，排查项为`AIPROXY_API_ENDPOINT`（AI Proxy服务的根地址）或`AIPROXY_API_TOKEN`（AI Proxy管理员Token）配置错误，变量值包含多余空格、格式错误，或误用AI Proxy管理员Token作为应用API Key；未配置必填变量会导致启动校验失败。
- 处理合并请求时出现token耗尽报错，原因是未限制`maxContext`的取值，将全量Git仓库历史或无关提交记录纳入上下文。
- 处理大体积评审意见文档时出现超时或结果截断，原因是分块长度设置过大，导致单块token消耗超过系统阈值。

## 怎么确认配好了
- 查看系统运行日志，确认上下文调用时的token消耗量在`maxContext`配置的范围内，无异常溢出。
- 提交一条测试合并请求，检查关联的变更记录、评审意见是否被正确截取与召回，无冗余或关键信息丢失。
- 验证服务端环境变量`AIPROXY_API_ENDPOINT`（AI Proxy服务的根地址）与`AIPROXY_API_TOKEN`（AI Proxy管理员Token）的加载状态，确认无格式错误且已生效。
- 触发一次完整的代码评审流程，检查返回的变更影响判断结果是否包含核心变更信息，符合预期。
