# 众包标注人员管理的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
通常，众包标注人员管理的核心数据来自众包平台、标注质量数据、培训考试记录与财务系统。日常关联文档包含人员准入规则、培训材料、绩效表与结算清单，数据更新频率多为日更或月更。该品类聚焦人力组织与绩效结算，数据涵盖结构化的人员绩效、财务结算条目，以及非结构化的培训与规则文本，最耗时的环节集中在人员筛选、质量排名与结算核对。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据类型多样，既有结构化的绩效、结算条目，也有长文本的规则与培训材料，不同文档的长度差异较大。数据更新频率的日更或月更特性，要求上下文缓存需匹配更新节奏，避免使用过期的人员绩效或结算数据。同时，最耗时的筛选、排名与结算核对环节，依赖完整的上下文信息，若token配置不当，可能截断关键的准入条件、绩效分数或结算金额，引发质量波动、错付漏付或项目延期。此外，与文本标注项目不同，该品类的上下文需覆盖多类文档，对token的总量与单条引用长度提出了更高要求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文token数 | 8000–12000 token | 需覆盖人员准入规则、培训材料、多份绩效表与结算清单的总长度，避免截断核心管理信息 |
| `quoteMaxToken` | 1500–2000 token 仅作试配示例 | 这是知识库引用内容的 token 总预算，不是每份绩效表或每条引用的独立长度限制 |
| 单次搜索引用上限 | 前6条 | 对应日常需同步的人员筛选、质量排名数据条目数，避免上下文过载 |
| 外部业务缓存策略 | 24小时仅作测试示例，按实际更新要求调整 | 若集成层自行缓存业务结果，需单独实现过期与失效机制；不把它描述为 FastGPT 原生上下文缓存时长开关 |
| `maxContext` | 按实测标定 | 适配不同项目的人员规模与文档总量，避免超出模型上下文窗口限制 |

## 容易做错的三处
- 现象：设置`quoteMaxToken`为2000后，搜索返回的结算清单内容被截断，超出设定的token限制。排查时需核对引用内容的总 token 预算、实际召回片段与模型窗口，不能把总引用预算等同于单份文档的分段长度。
- 现象：对话上下文丢失，无法延续连续对话。应分别检查请求实际携带的对话历史、检索结果与 token 总量。`maxContext` 表示 LLM 最大上下文长度，本身不负责自动保存或恢复会话。
- 现象：录入的人员准入规则文本被强制拆分。先在所用版本的实际导入界面检查分段设置，并查看解析后的数据；不能假定存在统一的“自动分块开关”。

## 怎么确认配好了
- 导入单份结算清单，在知识库搜索后检查引用内容是否完整显示，无截断提示。
- 发起连续对话，验证历史交互内容与关联的人员管理文档片段被正确纳入当前上下文。
- 导入人员准入规则全文，确认无自动拆分导致的段落断裂。
- 查看所用版本知识库中的实际解析与分段结果，对照原文确认准入条件完整，不假定某个内部字段即可证明未拆分。
- 若使用外部业务缓存，核对缓存失效策略，并在源记录变更后测试重新检索是否取得最新内容。
