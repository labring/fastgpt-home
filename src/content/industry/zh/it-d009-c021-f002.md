# 供应链安全与开源依赖治理的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自包管理器、代码仓库、漏洞库与许可证数据库。日常产出的文档包含SBOM清单、依赖风险报告、许可证清单与修复工单，字段涵盖组件名称、版本号、漏洞编号、许可证类型、修复状态等，单位多为组件数量、漏洞等级、许可证分类标识。数据更新频率为每日或每版本发布时同步，依赖资产识别、漏洞版本匹配环节会产生大量增量关联数据。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的文档与数据存在多字段关联、增量更新频繁的特征，对上下文与token管理带来多重约束。SBOM清单与风险报告的组件信息需完整关联，单轮召回的上下文需覆盖至少3个关联字段，避免信息割裂。高频更新的数据会导致上下文池快速膨胀，需通过`maxContext`限制单轮调用的总token消耗，通过`quoteMaxToken`限制单条引用的文本长度，防止超出模型承载上限。同时修复工单的关联依赖信息需精准匹配，过长的上下文会导致token消耗超标，影响响应效率。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的逻辑制定。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文token数 | 8000–12000 token | 匹配该品类单轮召回的SBOM、风险报告等多文档的总token量，避免超出通用模型的上下文承载上限 |
| 引用最大token数 | 1500–2000 字符 | 限制单条依赖组件的上下文引用长度，适配漏洞描述、许可证条款的常规文本长度 |
| 单次上下文召回上限 | 前10条 | 控制单轮调用的依赖数据总量，防止token消耗过快导致请求中断 |
| 上下文同步周期 | 每6小时 | 适配该品类数据日/每版本的更新频率，平衡数据时效性与token管理开销 |
| 上下文缓存阈值 | 200 MB | 限制本地缓存的上下文数据总量，避免私有化部署环境的存储资源过载 |

## 容易做错的三处
- 现象：调用时返回`[hide 38432 char]`截断内容，原因：未限制单条上下文的引用token数，导致超出模型承载上限后自动截断。
- 现象：启动关联模型服务时抛出`failed to get gpt-3.5-turbo token encoder`异常，原因：未正确配置上下文的token编码匹配规则，导致依赖数据的文本无法被正确解析。
- 现象：单轮召回的依赖数据条数超出预期，原因：未设置单次上下文召回上限，导致批量拉取全量历史数据消耗过多token。

## 怎么确认配好了
- 上传一份标准SBOM清单进行测试，查看召回的上下文是否包含组件名称、版本号、漏洞编号等核心字段，且无明显截断。
- 查看系统运行日志，确认单轮调用的token消耗量未超出配置的`maxContext`数值。
- 触发一次依赖风险报告的生成流程，检查上下文同步周期是否符合预设的更新频率。
- 测试关联模型的调用，确认无token编码相关的异常日志输出。
