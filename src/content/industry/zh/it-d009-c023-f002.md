# 信息化预算与项目组合管理的需求与设计文档起草：上下文与 token

本文基于FastGPT v4.17.0版本的配置逻辑展开。

## 这个品类的数据长什么样
该品类的数据通常来自财务系统、项目管理系统、合同台账及业务部门提报的需求。日常产出的文档包括年度预算表、项目立项书、项目组合看板与投资复盘报告，文档字段多涉及预算金额、项目周期、资源占比、优先级排序等，单位包含万元、天、人月等。数据更新节奏多为月度、季度或年度，单次文档体量随企业项目组合规模波动，核心内容围绕项目立项、预算分配与收益复盘展开。

## 这些特征在「上下文与 token」这一环带来什么约束
来自多系统的异构数据格式不统一，会增加上下文整理的token消耗。月度或季度更新的批量文档会导致单次上下文token总量出现波动，需提前限制单轮输入的token上限。文档中的结构化字段若未做裁剪，会导致非核心内容占用过多token，挤压关键优先级信息的空间。需求收口环节的多轮交互会累积上下文token，若未限制历史会话的token占用，会快速超出模型支持范围。项目组合看板的多维度数据会拉长上下文长度，需明确token的截取规则，避免核心决策信息丢失。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 匹配年度预算表、项目组合看板的常规文档体量，避免token溢出 |
| `quoteMaxToken` | 2000–3000 token | 适配单份项目立项书或投资复盘报告的核心内容长度 |
| 历史会话token上限 | 5000 token | 控制需求收口环节多轮交互的上下文累积 |
| 上下文裁剪阈值 | 按实测标定 | 针对异构系统导入的结构化数据，过滤非核心冗余字段 |
| 单次召回条数 | 前3条 | 匹配项目优先级排序的核心参考文档数量 |

## 容易做错的三处
- 出现400状态码的InternalError.Algo.InvalidParameter报错，提示token范围非法。原因是未配置`maxContext`或`quoteMaxToken`参数，导致系统无法限制单轮输入的token上限，触发参数校验失败。
- 离线部署环境下出现请求外网资源的报错。原因是未配置本地tokenizer文件路径，系统默认尝试拉取公开的cl100k.tiktoken文件，导致离线环境下请求失败。
- 多轮需求沟通后出现上下文溢出导致的内容截断。原因是未设置历史会话token上限，累积的交互内容超出模型支持的token范围，丢失前期的预算优先级信息。

## 怎么确认配好了
- 上传一份典型的年度预算表，查看系统展示的上下文token消耗数值，确认符合配置的`maxContext`范围。
- 触发多轮需求收口的模拟交互，查看历史会话的token占用情况，确认未超出设置的历史会话上限。
- 测试离线部署环境下的文档导入，确认无外网请求相关的报错日志。
- 调整引用内容的token上限，验证单份项目立项书的核心内容是否被完整纳入上下文。
