# 值班排班与交接的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的核心数据来自排班系统、故障工单、监控告警与组织通讯录，更新频率为每日或每周。日常产出的文档包括值班表、交接记录、升级联系人清单与值班日报，字段包含值班时段、未结待办事项、升级链路联系人、告警响应状态等，核心关联信息围绕值班人员权责与故障处理流程展开。

## 这些特征在「上下文与 token」这一环带来什么约束
由于数据更新频率为日或周，且核心信息随值班轮换动态变化，上下文召回需优先过滤过期数据，避免引入过时的值班安排或未生效的升级链路。文档字段覆盖时段、待办、联系人等多维度，需精准匹配查询的场景范围，防止无关信息占用token配额。同时，交接记录与值班日报的单次调用内容较长，需限制上下文总token量，避免超出模型支持上限导致截断或报错。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文总token | 8000–12000 token | 适配本品类文档的平均内容规模，确保完整召回关键值班与交接信息 |
| `maxContext` | 按业务文档总长度的1.2倍标定（FastGPT v4.17.0） | 匹配平台上下文处理上限，避免内容被强制截断 |
| 上下文召回token上限 | 2000–3000 token | 聚焦核心的值班安排与交接事项，过滤冗余的历史告警信息 |
| `quoteMaxToken` | 1500 token | 限制单条召回文档的token消耗，防止单条内容过长挤占整体上下文空间 |
| 单次召回条目数 | 前3条 | 匹配每日或每周更新的文档数量，避免过多条目占用token配额 |

## 容易做错的三处
- 现象：日志中出现“context length exceeded”报错，界面显示token消耗超出预设阈值。原因：未针对本品类高频更新的文档调整上下文召回规则，召回了多周期的冗余值班记录与交接内容。
- 现象：搜索返回的升级联系人与当前值班轮值人员不匹配，无法直接用于故障响应。原因：未启用上下文的时间过滤配置，召回了跨周期的旧升级联系人清单。
- 现象：调用后返回空的上下文关联内容，未加载任何值班相关文档。原因：错误设置`quoteMaxToken`的取值为0，导致无法召回任何符合要求的关联文档。

## 怎么确认配好了
- 上传近7天的值班表、交接记录与升级联系人清单，触发一次值班安排查询，查看召回的文档是否为近7天内的内容。
- 查看调用日志中的token消耗统计，确认单次调用的token量未超出配置的最大上下文总token取值。
- 测试不同值班时段的查询，确认返回的升级联系人与当前值班人员的权责范围匹配。
- 检查私有化部署的访问路径配置，确认应用访问路径符合预设的上下文规则。
