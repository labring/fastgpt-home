# 值班排班与交接的需求与设计文档起草：多轮对话与提示词

## 这个品类的数据长什么样
该品类的数据来自排班系统、故障工单、监控告警、组织通讯录，更新频率为日或周。日常产出的文档包含值班表、交接记录、升级联系人清单、值班日报，字段涵盖值班时段、交接未结事项、升级联系人信息、告警响应级别等，单份文档的内容结构固定，无复杂嵌套格式，单条记录长度多在数百字符区间。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源分散且更新频率为日或周，要求多轮对话需在每轮交互中实时拉取最新的排班、告警数据，避免使用过期信息。日常文档结构固定且字段明确，提示词需精准指定提取对应字段的规则，防止生成无关内容。值班表与交接记录的关联性强，多轮对话需保留历史交互的上下文，确保排班冲突协调、交接事项确认的逻辑连贯。此外，数据出错会直接导致运维响应延误，要求对话流程需加入校验环节，确认排班无冲突、交接事项无遗漏。

## 配置怎么定
以下配置基于 FastGPT v4.17.0 版本制定。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `chatId` | 固定会话ID或动态生成 | 确保多轮对话的上下文绑定到唯一会话，避免跨会话数据混淆 |
| 分块长度 | 800–1200 字符 | 匹配值班表单条记录的常规长度，避免拆分完整的值班时段条目 |
| 重叠长度 | 150–200 字符 | 保留相邻分块的交接事项关联信息，防止跨块的未结事项被截断 |
| 单次搜索上限 | 前 5 条 | 匹配运维团队日常关注的最新5条告警或排班变更记录，减少无关召回内容 |
| 最大上下文窗口 | 4000 token | 容纳3–5轮的排班协调对话上下文，确保历史交互的逻辑连贯 |
| `variables` | 绑定值班表、升级联系人清单文档 | 直接调用预设的企业级文档数据，无需重复上传 |
| `messages` | 保留历史交互的角色与内容 | 支持多轮排班冲突协调的上下文联动 |

## 容易做错的三处
- 现象：对话中提示未上传文件，无法读取系统提示词中指定的值班表文档。原因：未将目标文档绑定到`variables`参数，或提示词未明确指定读取`variables`中的文档内容。
- 现象：工作流中无法在对话过程中实时切换知识库。原因：未配置`messages`参数的上下文联动逻辑，未在每轮对话中动态更新知识库关联规则。
- 现象：知识库召回的值班表内容零散，无法完整读取整周排班信息。原因：使用#、##等标题层级作为分隔符，未匹配值班表的时段换行或固定条目分隔规则。

## 怎么确认配好了
- 上传一份测试用的值班表文档，绑定到`variables`参数后发起多轮对话，检查是否能正确提取值班时段、交接未结事项等指定字段。
- 发起多轮排班协调对话，修改初始的排班需求，检查是否能基于历史交互的上下文调整排班方案。
- 配置单次搜索上限为前5条后，发起包含多条告警记录的对话，检查召回的内容数量符合预期。
- 部署私有部署版本后，修改前端弹窗组件的对应代码，重新编译部署后检查新对话弹窗是否按预期移除。
