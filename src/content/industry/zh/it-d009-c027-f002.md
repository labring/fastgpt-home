# 内容审核规则运营的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的核心数据来自内容审核后台、用户举报、法规政策与审核样本库。日常产出的文档包含审核规则、处置指南、申诉记录与质检报告，其中审核规则文档包含触发阈值、处置动作字段，申诉记录包含申诉理由、复核结果字段。数据更新频率为每日常规样本更新，遇政策变更则即时同步规则文档。业务主体为内容安全运营、审核质检与平台治理团队，日常需围绕多源数据完成规则解释、疑难样本判定与申诉复核工作。

## 这些特征在「上下文与 token」这一环带来什么约束
多源数据来源决定上下文需覆盖审核后台规则、用户举报记录、政策文件与历史申诉样本，易产生token消耗超标的问题。高频更新的特性要求上下文可快速加载最新版本的规则与政策内容，避免使用过时信息。多样的文档结构要求上下文需区分不同类型数据的字段属性，确保召回内容与当前审核任务匹配。耗时的规则解释与申诉复核环节，要求上下文精准召回相关历史样本与规则条款，减少冗余内容占用token资源。同时，需支持自定义传入上下文，适配多源数据的批量处理需求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 覆盖审核规则、申诉记录、政策文件等多源数据的总token消耗，适配FastGPT v4.17.0版本的上下文配置逻辑 |
| `quoteMaxToken` | 2000–3000 token | 匹配单条审核规则或历史申诉样本的平均长度，避免单条引用内容占用过多token |
| 上下文召回数量 | 前5–7条 | 基于多源数据的相关性排序，召回最相关的规则与历史样本，平衡召回精度与token消耗 |
| 上下文更新时效 | 实时 | 适配本品类数据日更或政策变更即时更新的特性，确保上下文始终使用最新规则与政策内容 |
| 上下文传入方式 | 支持API自定义传入 | 适配多源数据批量处理的需求，无需依赖系统自动拼接的历史上下文 |

## 容易做错的三处
- 现象：审核规则分类时仅匹配当前输入，未关联历史申诉记录或规则解释，导致分类错误；原因：未启用上下文召回功能，仅使用单条当前输入生成内容，未加载历史审核数据。
- 现象：审核规则文档分段后，上下文无法关联对应处置条款；原因：分段长度未匹配规则文档的完整语义单元，导致上下文断裂，无法召回完整规则内容。
- 现象：服务出现token encoder相关报错并无限重启；原因：未限制`maxContext`的取值范围，导致token消耗超出模型支持上限，触发编码错误。

## 怎么确认配好了
- 导入单条审核规则文档，检查上下文召回结果是否包含该规则对应的处置指南内容。
- 提交包含历史申诉记录的查询，确认返回结果是否关联对应复核结果与规则条款。
- 查看配置项的取值，确认`maxContext`与`quoteMaxToken`的取值符合预设区间。
- 模拟政策变更后的规则更新，检查上下文是否加载最新版本的规则内容。
