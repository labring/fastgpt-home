# 创作者入驻与认证的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
创作者入驻与认证的日常文档包含入驻申请、身份资质材料、认证审核记录、合作协议。数据来源为创作者后台、企业信用信息系统、账号历史库与合同管理系统，更新频率为每日或每申请提交时。文档字段通常包含账号ID、资质编号、审核状态、合作期限等，单份材料长度从数百字符到数千字符不等，多源数据需整合后用于审核判断。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的多源数据来源决定了上下文需覆盖创作者后台记录、企业信用信息、历史审核结果等多类内容，总token消耗较高。更新频率为每日或每申请触发，要求上下文能实时拉取最新的资质与审核数据。最耗时的资质核验与账号风险判断环节，需确保所有关键字段不被截断，否则可能导致虚假认证或权益错配。同时，单份材料的长度差异较大，需限制单条引用的token量以避免上下文溢出，影响审核逻辑的完整性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| maxContext | 8000–12000 token | 创作者入驻与认证的全量申请材料、历史审核记录的总token量通常在此区间，确保所有关键字段不被截断 |
| quoteMaxToken | 1500–2000 token | 单份资质材料、合作协议片段的长度通常不超过此值，避免单条引用溢出上下文 |
| 上下文召回条数 | 前6条 | 创作者相关的历史账号记录、资质核验结果通常为6条以内，过多会增加不必要的token消耗 |
| 单次请求超时时间 | 600 秒 | 资质核验、风险判断环节耗时较长，需匹配实际处理时长 |
| 召回关联度阈值 | 0.75 | 确保召回的账号历史、企业信用信息与当前申请的关联度符合审核要求 |

## 容易做错的三处
- 若出现调用/api/core/dataset/collection/create或/api/core/dataset/create后，上下文未按预期关联历史审核记录的现象，可排查是否未将`maxContext`配置为覆盖历史记录与当前申请的总token量，导致关键历史数据被截断。
- 若出现资质核验结果未被纳入上下文、仅返回当前申请内容的现象，可排查是否`quoteMaxToken`设置过小，单份资质材料的token超出限制被过滤。
- 若出现审核请求返回504超时状态码的现象，可排查是否`maxContext`设置过大，导致模型处理时间超出预设阈值，未调整超时配置匹配实际处理时长。

## 怎么确认配好了
- 上传一份完整的创作者入驻申请材料，查看上下文预览中是否包含所有上传的资质、历史记录与协议片段。
- 发起模拟审核请求，检查返回结果中是否包含召回的关联账号历史数据与企业信用信息。
- 查看FastGPT v4.17.0版本的服务端启动日志，确认未出现AIPROXY_API_ENDPOINT（AI Proxy服务根地址）或AIPROXY_API_TOKEN（AI Proxy管理员Token）缺失的校验报错。
- 调整`maxContext`的取值，验证上下文预览的总token数是否随配置变化。
