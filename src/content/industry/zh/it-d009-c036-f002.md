# 原型与交互设计的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
通常该品类的核心数据来自Figma或Axure源文件、团队维护的设计系统、用户反馈与可用性测试记录。日常产出的文档包含交互原型、页面流程图、组件说明与设计评审记录，更新节奏以周或每版本迭代为周期。数据字段多围绕页面结构、操作路径、组件属性与评审意见展开，无统一标准化格式，需根据项目需求调整文档结构，核心内容多为可视化操作说明与文字描述结合的形式。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的文档特征对上下文与token配置带来多重约束：首先，交互原型与流程图包含大量可视化操作路径描述，内容长度普遍较长，需适配足够的token配额避免关键信息截断；其次，更新频率较高，需频繁同步最新原型与评审内容，上下文缓存需适配快速迭代的更新节奏，避免使用过时数据；再者，数据来源分散，需整合多类文件内容，token分配需兼顾不同文档类型的权重，优先保留核心操作路径与评审意见。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 适配交互原型、流程图等富文本文档的平均内容长度，避免关键操作路径信息被截断 |
| `quoteMaxToken` | 1500–2000 token | 匹配组件说明与评审记录的单段内容长度，确保引用的设计细节完整 |
| 上下文更新间隔 | 12 小时 | 适配周/每版本的更新节奏，平衡同步效率与资源消耗 |
| 单次召回上下文条数 | 前 3 条 | 聚焦核心原型与最新评审记录，避免冗余内容占用token配额 |
| 上下文关联阈值 | 按实测标定 | 过滤低关联的历史评审记录，优化token使用效率 |

## 容易做错的三处
- 现象：返回400 <400> InternalError.Algo.InvalidParameter: Range of max_tokens相关报错，且界面无对应配置入口。原因：未针对原型文档的内容长度配置`maxContext`或`quoteMaxToken`参数，导致系统自动分配的token范围超出模型限制。
- 现象：离线部署后出现请求外网cl100k.tiktoken的日志报错。原因：未提前将tokenizer文件同步至本地部署环境，导致系统无法本地计算token配额，强制请求外部资源。
- 现象：上下文召回结果包含大量过时的历史评审记录，导致关键操作路径信息被覆盖。原因：未设置合理的上下文过滤阈值与更新间隔，未优先召回最新的原型与评审文档。

## 怎么确认配好了
- 在FastGPT v4.17.0版本中，上传单份完整的交互原型文档，检查系统返回的上下文召回结果是否包含最新的组件说明与评审意见。
- 触发token计算测试，确认返回的token数与预设的`maxContext`、`quoteMaxToken`参数范围匹配。
- 查看离线部署环境的日志，确认无请求外部tokenizer资源的报错信息。
- 调整配置参数后，验证异常场景补齐的生成结果是否包含完整的操作路径描述。
