# 发布管理与版本验收的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本文适用于FastGPT v4.17.0版本的发布管理与版本验收场景。该品类的核心数据来自版本经理、研发运维团队、产品负责人的日常工作产出，包括发布计划、上线清单、验收报告、回滚预案四类核心文档。数据来源涵盖CI流水线、变更系统、测试报告、监控看板，更新频率为周度或每版本一次。核心字段包含版本号、发布项清单、上线窗口、回滚触发条件、验收标准等，无统一的标准化格式，需从多系统中整合关联。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据特征对上下文与token配置带来多重约束。首先，多来源的异构数据要求上下文需支持跨系统文档的整合召回，避免单一数据源的信息缺失，影响发布项核对的完整性。其次，周/每版本的更新频率要求上下文的有效期需与版本周期匹配，避免引入历史版本的冗余数据，干扰当前版本的决策。第三，核心文档的长度差异较大，发布计划与回滚预案通常篇幅较长，需合理限制单轮上下文的token占用，避免超出大模型承载上限导致报错。最后，出错后果直接影响生产环境稳定性，要求上下文必须精准关联当前版本的有效数据，避免上下文污染引发错误的发布或回滚决策。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 前10–15条 | 匹配单版本的核心文档数量，覆盖发布计划、上线清单、验收报告等核心内容 |
| `quoteMaxToken` | 8000–12000 token | 适配发布计划、回滚预案等单文档的平均长度，避免token溢出报错 |
| 上下文召回相似度阈值 | 0.75–0.85 | 过滤低关联的历史版本数据，避免上下文污染 |
| 上下文更新频率 | 每版本触发一次 | 匹配数据的周/每版本更新节奏，确保上下文始终关联当前发布项 |
| 单次上下文召回上限 | 前5个文档源 | 限制从CI、变更系统等多来源召回的文档数量，避免token过载 |

## 容易做错的三处
- 现象：设置`maxContext`为30条，但对话明细仅显示2条上下文，且回复无法关联历史发布数据。原因：未正确配置单次上下文召回上限，导致仅召回了最新的零散变更记录，未完整拉取当前版本的核心文档。
- 现象：发布管理的上下文出现旧版本的上线清单内容，导致AI推荐错误的回滚预案。原因：未配置按版本周期更新上下文的规则，保留了历史版本的冗余数据，引发上下文污染。
- 现象：调用时出现token超标报错，部分场景伴随Error response from daemon相关异常。原因：未限制`quoteMaxToken`的取值，导致单轮上下文整合的token数超出大模型的允许承载范围。

## 怎么确认配好了
- 查看上下文召回日志，确认召回的文档均属于当前正在处理的版本范围，无历史版本的冗余数据。
- 触发一次发布项核对的问答，检查AI回复未出现格式异常，且关联的内容均来自当前版本的上线清单与验收报告。
- 模拟包含多份发布文档的上下文输入，确认未触发token超标报错，且`quoteMaxToken`的配置未超出大模型的允许范围。
- 验证上下文更新机制，在新版本发布后，确认旧版本的文档不再被召回至当前上下文。
