# 发布管理与版本验收的需求与设计文档起草：多轮对话与提示词

## 这个品类的数据长什么样
该品类的数据主要来自CI流水线、变更管理系统、自动化测试报告与生产环境监控看板，主要使用主体为版本经理、研发运维团队与产品负责人。日常产出的文档包含发布计划、上线核对清单、版本验收报告与回滚预案，字段覆盖版本标识、变更内容条目、上线窗口信息、回滚触发条件等。数据更新节奏为每周或每版本发布周期一次，每次更新会关联当前版本的全量变更与验证结果。本页面适配FastGPT v4.17.0版本。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
该品类的文档结构固定且关联强关联的生产变更数据，多轮对话需要持续对齐当前版本的已验证项与未完成环节。数据更新频率较高，对话上下文需要及时同步最新的变更清单与验证结果，避免引用过期信息。同时，不同文档的字段存在明确的业务关联，提示词需要引导对话按发布管理的标准字段生成内容，确保生成的文档符合团队的统一格式要求。另外，回滚预案的内容需要严格匹配生产环境的实际配置，对话生成的内容不能脱离已有的监控与变更数据支撑，否则会影响上线后的应急处理能力。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 上下文窗口大小 | `8000–12000 token` | 该品类的文档包含多份关联的发布相关文件，需要保留足够上下文以对齐当前版本的全量变更与验证信息 |
| `chatId` 绑定规则 | 绑定当前发布版本的唯一标识 | 确保多轮对话始终对齐同一发布版本的数据，避免跨版本混淆 |
| 历史消息存储规则 | 仅保留`messages`中与当前版本相关的对话 | 聚焦当前发布环节的内容，过滤无关的历史对话，提升处理效率 |
| 历史对话截断阈值 | 前20条对话 | 该品类的对话聚焦当前版本的特定环节，过长的历史会干扰内容生成的准确性 |
| `variables` 绑定字段 | 绑定发布计划、上线清单的预设字段 | 自动填充品类专属的文档字段，确保生成内容符合团队统一的格式要求 |
| 单次输出最大长度 | `3000–5000 字符` | 该品类的文档通常包含多段详细的环节描述，需要保证输出能覆盖完整的内容 |

## 容易做错的三处
- 现象：对话无法持续对齐当前版本的变更数据，出现上下文丢失的情况。原因：未正确绑定`chatId`到当前发布版本的唯一标识，导致每次对话重新初始化上下文，无法保留历史会话的版本信息。
- 现象：工作流运行速度比单独在调试界面运行慢。原因：未设置合理的历史对话截断阈值，加载了过多不相关的历史对话数据，增加了模型的处理负载。
- 现象：生成的回复不符合预设的JSON格式，例如出现非预期的字段或格式错误。原因：未在提示词中明确说明`json_schema`的使用规则，或未正确配置回复格式的校验参数，导致生成内容不符合品类文档的标准结构。

## 怎么确认配好了
- 发起一次测试对话，输入当前版本的变更清单，检查生成的发布计划是否包含所有预设的`variables`绑定字段。
- 连续发起多轮对话，检查`chatId`是否始终绑定同一发布版本的标识，对话上下文是否持续对齐当前版本的数据。
- 触发工作流运行，对比工作流运行耗时与单独调试的耗时，确认未因上下文加载过多导致性能下降。
- 生成一份验收报告，检查回复格式是否符合预设的JSON结构，字段是否符合品类的文档要求。
