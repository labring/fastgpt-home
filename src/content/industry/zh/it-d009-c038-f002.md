# 变更管理与发布窗口的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的核心数据来自变更管理系统、CI流水线、监控数据、业务日历四类来源。日常产出的文档包括变更申请、风险评估、上线窗口计划、回退方案四类。数据更新频率为周度或单次变更触发。文档字段包含变更唯一标识、生效时间窗口、影响业务范围、风险等级、审批状态、回退触发条件等，其中时间类字段以小时或天为单位，风险等级字段为标准化分级标签。

## 这些特征在「上下文与 token」这一环带来什么约束
多源数据来源要求上下文需整合不同系统的结构化与非结构化内容，直接提升token消耗上限需求。周度或单次变更的更新频率，要求上下文需按变更周期刷新，避免使用过期的监控或审批数据。多类文档结构要求上下文召回需精准匹配当前起草的文档类型，例如起草回退方案时需优先召回对应变更的风险评估内容。字段的多样性要求上下文需聚焦核心决策字段，减少非关键信息的token占用，避免模型被冗余内容干扰。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 变更管理场景需整合多源文档，该区间可覆盖单次完整变更流程的核心内容 |
| `quoteMaxToken` | 2000–3000 token | 单份变更申请或风险评估文档的核心内容长度区间 |
| 上下文刷新规则 | 每变更周期 | 匹配该品类周度或单次变更的数据更新频率 |
| 召回内容优先级 | 生效时间、风险等级优先 | 变更管理决策核心依赖时间窗口与风险评级信息 |
| 非核心字段过滤 | 开启 | 减少变更ID、操作日志等非关键内容的token占用 |

## 容易做错的三处
- 现象：生成的变更风险评级与实际监控数据不符，原因：未配置核心字段的召回优先级，导致模型未获取到最新的监控数据。
- 现象：配置`maxContext`后仍出现token溢出报错，原因：未开启非核心字段过滤，将大量非决策相关的日志内容纳入上下文。
- 现象：上线窗口计划的生效时间被模型忽略，原因：未将时间字段加入优先召回列表，导致上下文丢失关键时间信息。

## 怎么确认配好了
在FastGPT v4.17.0版本中，可通过以下可执行动作核对配置效果：
- 导入1份完整的变更管理文档，测试上下文召回结果，确认生效时间、风险等级等核心字段被优先召回。
- 查看token消耗统计，确认非核心字段的占用比例符合预期，无过度占用情况。
- 模拟触发一次变更流程，确认上下文按预设的每变更周期完成刷新。
- 验证模型输出的文档内容包含回退方案、审批状态等与当前起草场景匹配的核心信息。
