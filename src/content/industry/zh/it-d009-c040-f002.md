# 售前技术方案的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
通常，该品类的核心使用者为系统集成商售前顾问、解决方案架构师与销售团队。日常产出的文档包含技术方案书、客户需求调研表、报价清单与演示脚本，数据来源涵盖客户访谈记录、公开招标文件、厂商产品资料及历史项目方案。文档更新频率以单项目为周期，通常每单或每周更新一次。核心业务流程中，需求澄清、方案边界设计与报价配置核对为最耗时环节，配置失误可能导致投标失分、承诺超范围或项目亏损。该品类文档以业务章节为核心结构，包含技术路线、实施范围、资源配置等明确字段，无统一强制格式要求。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据来源分散且格式各异，需要整合多源信息完成需求与设计文档起草，导致上下文内容的token消耗波动较大。单份售前技术方案内容体量较大，多章节结构易引发上下文溢出风险。同时，需求澄清环节需反复调用历史项目方案、客户需求等数据，若上下文管理不当，会出现冗余信息占用token资源，或关键历史记录被截断的问题。此外，业务失误后果严重，要求上下文与token配置需精准匹配业务场景，避免因配置错误导致方案生成不完整或超出合理范围。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 适配售前技术方案单份文档的平均内容长度，匹配FastGPT v4.17.0的上下文窗口默认范围 |
| `quoteMaxToken` | 2000–4000 token | 限制单条引用内容的token消耗，防止单段厂商资料或客户访谈内容过长导致上下文溢出 |
| 最大上下文保留轮次 | 前10轮 | 匹配售前方案起草的多轮需求澄清场景，保留关键交互记录与历史方案参考 |
| 上下文拼接阈值 | 按实测标定 | 适配多源数据整合的需求，避免冗余内容占用过多token资源 |

## 容易做错的三处
- 现象：配置了`maxContext`为10000 token，但实际生成的方案出现上下文截断。排查项：确认`maxContext`配置值符合业务场景，且未超出FastGPT上下文窗口上限。
- 现象：界面显示的上下文条数与实际发送给上游模型的条数不符。排查项：确认`AIPROXY_API_ENDPOINT`和`AIPROXY_API_TOKEN`为App/Admin服务端环境变量，未在应用配置页面、工作流全局变量中填写，且未将`AIPROXY_API_TOKEN`用作应用API Key。
- 现象：手动调整文档分段后，上下文关联仍出现偏差。原因：未针对售前方案的章节结构优化分段逻辑，导致分段边界破坏了业务上下文的完整性。

## 怎么确认配好了
- 检查App/Admin服务端的环境变量，确认`AIPROXY_API_ENDPOINT`（AI Proxy服务根地址）和`AIPROXY_API_TOKEN`（AI Proxy管理员Token）已正确配置且非空。
- 在FastGPT的应用配置页面，查看上下文与token相关配置项的取值，确认与预设方案一致。
- 发起一次测试调用，查看日志中上报的上下文token数与配置值是否匹配。
- 导入一份典型的售前技术方案文档，验证生成的方案内容未出现不必要的截断或冗余。
