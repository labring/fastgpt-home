# 安全事件应急响应的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的典型使用主体为安全运营中心、应急响应工程师、客户安全负责人。日常产出与使用的文档包括应急响应报告、取证记录、处置方案、通报材料。数据主要来源于SIEM、EDR、防火墙日志、主机镜像，更新频率为实时或每事件一次。核心耗时环节涉及攻击路径还原、隔离处置、证据链整理，若处理不当可能引发数据泄露扩大、业务停摆、监管报告滞后等后果。

## 这些特征在「上下文与 token」这一环带来什么约束
实时或每事件一次的更新节奏，要求上下文能够快速加载最新的日志与取证数据，避免因延迟导致处置滞后。取证记录、SIEM日志等数据通常长度较长，容易超出大模型的token上限，需要精准裁剪有效内容。证据链整理需要关联多源日志的上下文信息，若上下文召回范围不足，会导致攻击路径还原不完整。监管报告的时效性要求上下文数据必须准确对应事件周期，否则会影响报告的合规性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 前8–12条 | 依据应急响应单事件关联的日志条目数，避免过多冗余数据占用token |
| `quoteMaxToken` | 12000–15000 token | 依据取证记录、SIEM日志的单事件总长度，适配大模型上下文窗口 |
| 上下文召回条数 | 前6条 | 依据攻击路径还原所需的关联日志数量，确保覆盖关键证据链 |
| 单次上下文加载时长 | 60秒 | 依据实时数据的更新延迟，避免超时中断处置流程 |
| 上下文过滤阈值 | 按实测标定 | 依据应急响应文档的字段相关性，过滤无关日志数据 |

## 容易做错的三处
- 现象：配置`maxContext`为30条，但对话明细仅显示2条上下文，无法关联历史处置记录。原因：未开启上下文持久化存储，或配置的上下文窗口未绑定应急响应事件的专属会话ID。
- 现象：大模型提示上下文token数超标，生成响应失败。原因：未限制`quoteMaxToken`取值，直接导入全量SIEM日志导致token溢出。
- 现象：超长取证分析任务执行超时。原因：未设置合理的上下文加载超时阈值，且未对日志数据进行分块裁剪。

## 怎么确认配好了
- 在FastGPT v4.17.0中导入单事件的SIEM、EDR日志样本，检查上下文展示条数与配置的`maxContext`取值一致。
- 上传最长的取证记录文档，查看大模型是否能正常解析且未触发token超限报错。
- 模拟实时日志推送，验证上下文更新频率与事件处理的实时性匹配。
- 查看应用维度的token统计数据，确认单事件处理的token消耗处于合理区间。
