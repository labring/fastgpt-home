# 安全产品规则运营的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自WAF、IDS、防火墙及威胁情报平台。日常产出的文档包括规则变更单、拦截日志、误报分析报告、策略回滚记录。数据更新频率为每日或随防护事件触发更新。文档字段包含规则ID、生效时间、拦截请求次数、误报样本数量、回滚操作人等，单位多为条、次、个。安全运营工程师需基于这些数据起草规则优化、变更的需求与设计文档，支撑防护策略的迭代与复核工作。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的文档多为结构化的运维类数据，单次起草需求文档需关联的历史规则、拦截日志、误报分析内容较多，容易超出模型的上下文窗口配额。数据更新频率较高，需确保上下文能及时同步最新的策略变更与事件记录，避免使用过期数据生成不符合当前防护状态的文档。误报分析样本的粒度较细，需保留足够的上下文细节以支撑规则优化的需求，但过多的历史数据会增加token消耗，导致调用成本上升或响应超时。同时，文档中的字段多为标识类内容，需精准匹配上下文的召回范围，避免无关数据占用token配额。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文窗口 | 8000–12000 token | 适配FastGPT v4.17.0版本的模型调用上限，满足安全产品多源日志、规则文档的总token消耗需求 |
| `maxContext` | 按业务关联的历史文档数量标定 | 匹配安全运营需关联的规则变更、拦截日志的总长度，避免超出模型限制 |
| 最大引用token | 2000–3000 字符 | 确保单条关键日志或规则文档的内容完整载入，不截断核心信息 |
| `quoteMaxToken` | 按误报分析样本的平均长度调整 | 覆盖典型误报样本的文本长度，支撑规则优化的上下文需求 |
| 上下文召回条数 | 前6条 | 匹配日常需复核的规则变更、拦截日志的常见数量，平衡信息完整性与token消耗 |
| 单次调用token上限 | 15000 token | 适配多环节文档拼接后的总token消耗，避免触发模型调用限制 |

## 容易做错的三处
- 现象：生成的需求文档中出现过期的策略回滚记录，内容与最新的防护策略不符。原因：未配置实时上下文同步机制，调用时使用了缓存的旧数据，未拉取当日更新的规则变更单与拦截日志。
- 现象：模型调用报错提示token超出限制，或生成的文档被强制截断。原因：未合理设置`maxContext`与`quoteMaxToken`的取值，一次性载入了过多的历史规则与事件数据，超出模型的token配额。
- 现象：界面展示的在线模型运行时间仅为首token耗时，离线模型显示总耗时，与实际业务统计逻辑不符。原因：混淆了在线与离线模型的token计算与耗时统计规则，未针对安全产品规则运营的多源数据场景调整配置。

## 怎么确认配好了
- 核对配置项的取值是否与品类的文档更新频率匹配，确保上下文能同步当日或实时的规则变更、拦截日志数据。
- 测试调用时，检查生成的需求文档是否包含最新的误报分析、策略回滚记录，无过期或缺失的核心字段。
- 查看模型调用的token消耗统计，确认未超出预设的`maxContext`与`quoteMaxToken`限制，无频繁的token溢出报错。
- 对比在线与离线模型的耗时展示逻辑，确保符合安全产品规则运营的业务统计需求，无异常的显示差异。
