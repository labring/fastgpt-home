# 安全漏洞披露处理的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的数据由项目安全响应小组、维护者及安全研究员产出，日常文档包括安全公告、漏洞报告、修复补丁与CVE申请材料。数据来源涵盖私密漏洞报告、项目代码仓库、CVE编号机构公开信息及官方发布渠道，按单事件更新，每份文档包含漏洞编号、影响范围、补丁链接、披露时间、受影响版本等字段。不同于供应链安全与开源依赖治理，本品类聚焦本项目自身漏洞的公开与修复流程。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类的数据按单事件更新，且包含私密与公开两类信息，要求上下文需按单次漏洞处理任务隔离，避免跨事件数据混淆与私密信息泄露。长文本类的漏洞报告、CVE申请材料会带来较大的token消耗，需限制单条引用的token上限，防止超出模型支持范围。同时，影响评估环节需快速关联历史漏洞数据，过多的上下文召回会增加token消耗与任务耗时，若处理超时可能导致补丁抢跑，影响项目信誉。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本适配：
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文条数 | 3–5 条 | 该品类数据按事件更新，单事件仅需关联同项目历史漏洞记录，过多会导致token超标 |
| 单条引用最大token数 | 1000–1500 token | 漏洞报告、CVE申请材料多为长文本，限制单条引用避免整体token溢出 |
| 上下文数据来源范围 | 仅公开漏洞数据+本项目授权的私密报告 | 防止未授权的私密漏洞信息泄露，符合安全披露规范 |
| 上下文召回匹配阈值 | 按实测标定 | 需平衡召回准确率与token消耗，适配不同漏洞的影响范围差异 |
| 任务超时阈值 | 600 秒 | 覆盖漏洞影响评估、补丁准备等最耗时环节的正常执行时长 |

## 容易做错的三处
- 现象：在FastGPT v4.17.0的AI节点中配置了30条上下文，但对话明细仅展示2条历史上下文，生成回复未关联对应漏洞数据。原因：未按事件维度划分上下文存储，系统默认按全局对话累积上下文，导致仅保留最新的少量对话内容。
- 现象：大模型返回上下文token数超标报错，或生成结果被截断。原因：未限制单条引用最大token数，直接引用完整长文本漏洞报告，超出模型支持的token上限。
- 现象：漏洞影响评估环节的任务执行超时，无返回结果。原因：未拆分长文本漏洞报告为合理片段，且未配置上下文召回的批量处理阈值，导致单次任务加载过多数据。

## 怎么确认配好了
- 查看FastGPT v4.17.0的AI节点配置页面，确认「最大上下文条数」「单条引用最大token数」等配置项的取值符合预设值。
- 导入一条历史漏洞报告作为测试数据，发起关联查询，核对对话明细中展示的上下文条数与配置一致。
- 提交包含长文本的CVE申请材料，检查生成的回复是否关联了对应漏洞的历史数据，未出现token超标报错。
- 模拟多次连续的漏洞处理任务，确认任务执行无超时，且上下文未跨任务混淆。
