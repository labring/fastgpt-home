# 安全漏洞披露处理的需求与设计文档起草：多轮对话与提示词
本文档基于FastGPT v4.17.0版本编写。

## 这个品类的数据长什么样
本品类的数据来源于私密漏洞报告、代码仓库、CVE编号机构及官方发布渠道，按单次漏洞事件更新。核心文档包含安全公告、漏洞报告、修复补丁与CVE申请材料，字段涵盖漏洞编号、影响范围、修复状态、披露时间、CVE标识等，数据仅对项目安全响应小组、维护者及合规安全研究员开放。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
由于数据包含敏感的未公开漏洞细节，多轮对话需严格隔离不同漏洞事件的上下文，避免信息泄露。单次漏洞事件的数据更新频率固定，需通过`chatId`绑定对应事件的对话流程，确保上下文仅关联当前处理的漏洞。核心文档存在固定字段要求，提示词需明确指定输出格式，多轮对话可逐步引导补充缺失的漏洞编号、影响范围等信息。同时需整合来自代码仓库、CVE机构的分散数据，在对话中完成信息校验与对齐，确保生成的文档符合合规要求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定当前漏洞事件的唯一标识，格式为`CVE编号+项目名`，每事件分配唯一字符串 | 确保多轮对话上下文仅关联当前漏洞事件，避免跨事件信息混淆，符合私密数据隔离要求 |
| `messages` | 限制上下文窗口为前10轮对话+当前漏洞基础数据，取值为`前10条` | 避免过多私密漏洞信息溢出，同时保留足够的对话历史用于上下文对齐 |
| `variables` | 预设4-6个固定字段变量，包括漏洞编号、影响范围、修复状态、披露时间 | 强制对齐业务文档的固定字段要求，确保输出符合CVE申请材料格式 |
| 最大上下文长度 | 800–1200 token，按实测标定 | 平衡敏感数据存储与上下文完整性，适配单次漏洞事件的信息体量 |
| 提示词触发规则 | 按漏洞处理流程分阶段触发，先收集漏洞详情再评估影响最后生成文档 | 贴合安全漏洞披露处理的标准化工作流，引导多轮对话按步骤完成文档起草 |
| 历史对话筛选 | 仅保留当前`chatId`下的对话记录 | 严格隔离不同漏洞事件的对话数据，符合私密数据管理要求 |

## 容易做错的三处
- 现象：调用API发起对话后，响应记录预览中`Human`字段为空。原因：未在`messages`参数中正确传入用户侧的提问内容，仅传入了系统提示词，导致对话历史缺失用户侧输入。
- 现象：通过`chatId`关联对话后，不同用户无法查看各自的漏洞处理历史。原因：未将`chatId`与具体用户的漏洞处理权限绑定，仅按事件维度绑定上下文，导致权限隔离失效。
- 现象：生成的CVE申请材料格式不符合要求，字段缺失或顺序混乱。原因：未通过`variables`参数预设固定字段模板，多轮对话未按要求引导补充完整字段，导致输出格式不规范。

## 怎么确认配好了
- 发起测试对话，检查`chatId`是否仅关联当前漏洞事件的上下文，无其他事件的历史信息。
- 查看`messages`参数的上下文配置，确认仅保留当前漏洞处理的对话记录，数量符合预设范围。
- 生成测试文档，检查输出是否包含`variables`参数预设的所有必填字段，格式与业务文档要求一致。
- 调用API获取对话记录，确认仅能获取当前`chatId`下的对话数据，无跨事件或跨用户的信息。
