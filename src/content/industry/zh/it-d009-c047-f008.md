# 安全漏洞披露处理的需求与设计文档起草：工作流编排

## 这个品类的数据长什么样
本品类的数据来自私密漏洞报告、代码仓库提交记录、CVE编号机构公开数据、项目官方发布渠道。更新节奏为单个漏洞事件触发一次更新。日常产出的文档包含安全公告、漏洞报告、修复补丁、CVE申请材料，字段涵盖漏洞唯一标识、影响范围、补丁关联哈希、披露计划时间、影响评估结果等，数据结构随漏洞严重程度和披露流程阶段动态调整。

## 这些特征在「工作流编排」这一环带来什么约束
本品类的数据按单个漏洞事件独立更新，要求工作流需绑定唯一的事件上下文，避免不同漏洞的流程数据混淆。私密漏洞报告的敏感属性要求工作流配置权限隔离节点，仅项目安全组成员可访问。CVE编号机构数据的时效性要求工作流集成定时校验节点，确保披露前的编号准确性。多关联文档的特性要求工作流支持跨节点的变量传递，关联不同环节的文档字段。最耗时的漏洞影响评估和披露协调环节，要求工作流配置可自定义的超时与人工审批节点，适配不同漏洞的处理周期。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `variables` | `{"cve_id": "", "impact_scope": "", "patch_hash": ""}` | 匹配漏洞文档的核心字段，便于跨节点传递 |
| `nodeId` | `event_{timestamp}` | 确保每个漏洞事件的工作流实例拥有唯一标识，避免冲突 |
| 超时阈值 | 漏洞评估环节`12 小时`，披露协调环节`24 小时` | 适配该品类最耗时的两个环节的实际处理周期 |
| 变量传递范围 | 仅当前工作流实例 | 防止不同漏洞事件的变量数据交叉污染 |
| 权限校验 | 仅项目安全组成员可触发 | 匹配私密漏洞报告的敏感数据访问要求 |
| 失败重试 | 最多3次，间隔`5 分钟` | 应对临时网络或数据源波动，避免流程中断 |

## 容易做错的三处
- 现象：工作流中通过代码节点更新`variables`后，后续AI对话节点无法获取到更新后的变量内容。原因：未启用FastGPT v4.17.0工作流的全局变量实时同步开关，变量仅在工作流启动时加载一次。
- 现象：导入预设的漏洞披露工作流后，CVE数据源节点无法拉取到有效数据。原因：未配置对应CVE机构的API权限，或`nodeId`与数据源绑定的节点标识不匹配。
- 现象：漏洞披露协调环节未触发人工审批节点。原因：超时阈值设置过短，未匹配该环节的实际处理周期，流程提前触发终止。

## 怎么确认配好了
- 触发测试工作流，查看全局变量面板是否显示当前测试漏洞事件的CVE编号、影响范围等预设字段。
- 检查每个节点的`nodeId`配置，确认与预设的`event_{timestamp}`格式一致。
- 模拟超时场景，验证工作流是否在设定的超时阈值后触发告警或人工干预节点。
- 使用非项目安全组成员的账号尝试触发工作流，确认无法正常启动。
