# 安全监控与SOC值守的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自SIEM、EDR、NDR及威胁情报源，更新节奏分为实时与日更两类。日常使用与产出的文档包含告警处置单、值班记录、威胁情报通报、日报周报，文档结构以告警ID、处置时间、关联IP、威胁等级等字段为核心，单条告警数据体量较小但整体数据量随告警频次波动，无统一固定的长文本格式。

## 这些特征在「上下文与 token」这一环带来什么约束
实时更新的告警数据要求上下文窗口能快速同步最新信息，避免研判滞后；日更的周报、通报类文档则需要稳定的长上下文加载能力。告警处置单等短文本为主的文档，需精准控制token消耗，避免冗余内容占用配额。多源数据的混合调用，要求上下文能区分不同数据源的字段属性，防止混淆关联信息。误报排除、升级派单等耗时环节依赖完整上下文，token超限会导致研判信息缺失，引发真实攻击漏报或误报堆积。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 适配SOC场景下多源告警、值班记录的混合上下文加载需求，匹配主流大模型的上下文上限 |
| `quoteMaxToken` | 2000–3000 token | 限制单条引用文档的token消耗，避免单告警研判时token占用超出配额 |
| 相似度阈值 | 0.5–0.7 | 适配告警处置单等短文本的匹配精度，过滤低相关的威胁情报内容 |
| 单次召回条数 | 前3–5条 | 控制上下文总token占用，防止加载过多历史数据导致超限 |
| 上下文刷新间隔 | 实时 / 1 小时 | 实时告警场景下同步最新数据，日更文档场景下按1小时刷新平衡性能与时效性 |

## 容易做错的三处
- 现象为设置相似度阈值为0.4后，仍无法召回所需的告警处置单内容。原因为阈值过低，引入大量低相关的历史告警数据，挤占上下文token配额，导致目标内容未被优先召回。
- 现象为绑定16384 token上限的大模型时，输出在12288 token时被截断，界面提示超出回复限制，日志显示输入输出比为31945/12288。原因为`maxContext`配置超出大模型的输出token上限，且未限制单次召回的总token数，导致上下文总token叠加后超出配额。
- 现象为无法按告警应用维度统计token消耗。原因为未开启上下文维度的token统计配置，或未关联告警应用的标识字段，导致token消耗无法按业务维度拆分。

## 怎么确认配好了
- 上传单份告警处置单，查看召回的关联文档条数是否在3-5条范围内。
- 提交长文本的威胁情报通报，检查输出是否未被截断，且后台日志显示的总token未超出绑定大模型的上限。
- 调整相似度阈值为0.6，验证低相关的冗余内容是否被过滤，召回结果的匹配度有所提升。
- 查看FastGPT v4.17.0的后台统计面板，确认token消耗可按告警应用维度拆分统计。
