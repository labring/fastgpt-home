# 安全监控与SOC值守的需求与设计文档起草：多轮对话与提示词

## 这个品类的数据长什么样
该品类的数据来源为SIEM、EDR、NDR及各类威胁情报源，更新节奏分为实时与日更两类。日常产出与使用的文档包括告警处置单、值班记录、威胁情报通报、日报周报，字段覆盖告警ID、处置时间、研判结论、派单对象等，单份文档的信息密度随告警量级变化。典型使用主体为SOC分析师、安全运营外包团队与企业安全中心。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
多源实时数据要求对话上下文需实时拉取最新告警与情报，避免依赖过期信息。多类文档的差异化字段要求提示词需明确对应告警处置单、值班记录等不同文档的格式与字段规则。高频次的告警研判与误报排除场景，要求多轮对话的上下文窗口需限定在合理范围，防止冗余信息干扰研判逻辑。同时，出错后果直接关联安全风险，提示词需强化对真实攻击特征的识别约束，避免误报堆积或漏报。

## 配置怎么定
以下配置适用于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 提示词模板 | 聚焦告警研判、误报排除、派单升级三个环节 | 匹配SOC值守最耗时的核心流程 |
| 上下文窗口大小 | 前6-10条历史对话 | 避免冗余信息干扰实时研判 |
| `messages` 参数 | 按告警ID关联历史处置记录 | 确保多轮对话上下文精准关联对应告警 |
| `chatId` 参数 | 绑定单值守班组的会话 | 隔离不同班组的告警处置上下文 |
| `variables` 参数 | 注入当日SIEM告警汇总数据 | 补充实时更新的数据源信息 |
| 最大上下文长度 | 3000-5000 token | 适配多源数据的信息密度，防止会话超时 |

## 容易做错的三处
- 调用`/api/v1/chat/completions`时未正确配置`messages`参数，返回结果与当前告警无关。原因是未按告警ID关联历史处置记录，上下文未绑定对应业务场景。
- 未设置`chatId`参数，不同告警的对话上下文混淆，出现误报堆积。原因是未隔离不同值守会话的上下文数据。
- 尝试使用通用全局key发起与特定应用的对话，接口返回权限不足或数据源未关联的报错。原因是未绑定对应应用的会话标识，权限与数据源关联失效。

## 怎么确认配好了
- 发起测试对话，输入某条告警ID，核对返回内容是否关联对应告警的历史处置记录。
- 切换不同值守班组的会话，确认对话上下文不会跨班组共享。
- 调用接口时传入`variables`参数，核对返回内容是否包含预设的当日威胁情报数据。
- 检查会话返回的错误日志，确认未出现上下文溢出或参数缺失的报错。
