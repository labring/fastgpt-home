# 客户开通与租户初始化的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
这个品类的核心数据来自CRM、合同订单、身份管理系统、产品后台四类系统，更新频率为每单或每日。日常产出的文档包括开通申请单、租户配置表、管理员账号清单、交付确认单，数据字段包含客户编号、租户标识、管理员账号列表、权限配置项、开通状态等，单位涵盖账号个数、配置条目数、时间戳等。数据围绕单次客户开通与租户初始化流程产生，关联主体为SaaS实施顾问、客户成功经理、运维开通人员。

## 这些特征在「上下文与 token」这一环带来什么约束
多源数据来源要求上下文需整合CRM、合同订单等四类系统的字段，未合理裁剪会导致token占用过高。按单/日的更新频率要求上下文绑定单次流程的专属数据，避免加载跨周期的冗余信息。固定的文档结构要求上下文提取匹配文档字段优先级，优先加载管理员账号、租户配置等核心内容，减少无效token消耗。最耗时的客户信息核对环节要求上下文优先加载已核对的有效数据，避免重复处理未确认信息，提升token使用效率。

## 配置怎么定
本配置适用于FastGPT v4.17.0。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文窗口 | 8000–12000 token | 匹配租户初始化场景的多源数据整合需求，避免token溢出 |
| 引用最大token数 | 2000–3000 token | 优先加载核心文档的关键字段，控制单次上下文的token消耗 |
| 上下文刷新触发条件 | 按开通单提交后触发 | 匹配数据每单/日的更新频率，避免无效刷新 |
| 上下文加载优先级 | 按管理员账号清单、租户配置表顺序加载 | 贴合日常文档的核心字段优先级，减少无效token占用 |
| 上下文过滤阈值 | 按实测标定 | 不同客户的开通数据字段差异较大，需适配实际场景 |

## 容易做错的三处
- 现象为调用FastGPT工作流API时返回的上下文为空，即使工作流已配置上下文。原因：未在流程中绑定租户初始化场景的专属数据源，导致系统无法匹配对应客户的开通数据。
- 现象为积分消耗出现异常波动，超出预期额度。原因：未限制上下文加载的token上限，导致多源数据整合时token消耗超出计费标准。
- 现象为团队切换接口返回的团队数据未同步更新。原因：上下文未实时关联身份管理系统的最新团队数据，导致token携带的旧数据未完成刷新。

## 怎么确认配好了
- 提交一条测试开通申请单，检查系统自动加载的上下文是否包含对应客户的CRM信息、合同订单数据。
- 调用租户初始化相关的工作流API，确认返回结果中携带的上下文未出现无关的冗余字段。
- 查看产品后台的token消耗记录，确认单次初始化流程的token消耗处于预设的配置区间内。
- 验证管理员账号清单的上下文加载顺序是否与配置的优先级保持一致。
