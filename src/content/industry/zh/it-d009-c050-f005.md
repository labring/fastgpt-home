# 客户开通与租户初始化的需求与设计文档起草：多轮对话与提示词

## 这个品类的数据长什么样
这个品类的数据通常来自CRM系统、合同订单库、身份管理系统与产品后台。日常产出的文档包含开通申请单、租户配置表、管理员账号清单与交付确认单，数据更新节奏为每单或每日更新。数据字段包含租户唯一标识、管理员账号数量、基础权限配置项状态等，无统一强制格式，需匹配企业内部身份管理与合同流程的字段规则。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
该品类的数据分散在多套系统中，多轮对话需依次拉取CRM客户信息、合同配置项与身份系统账号数据，需限定每次对话的上下文拉取范围，避免冗余数据干扰。数据更新频率为每单或每日，提示词需明确仅使用当前会话周期内的最新数据，防止调用过期的租户配置信息。同时，日常文档包含多种格式的字段，多轮对话需按文档类型匹配字段提取规则，避免混淆管理员账号清单与租户配置表的字段定义。此外，该品类的出错后果直接影响客户登录与合同验收，多轮对话需增加校验环节，确保提取的字段无遗漏。

## 配置怎么定
本配置适用于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `chatId` | 与租户ID绑定的唯一字符串 | 确保多轮对话绑定指定租户的上下文，避免跨租户数据串扰 |
| `messages` | 保留近3轮用户与助手对话、2条系统预设提示 | 该品类的需求起草围绕单租户单次开通流程，过多历史消息会增加上下文冗余 |
| `variables` | 注入租户ID、管理员账号数量、合同生效日期3个核心字段 | 匹配该品类日常文档的核心数据项，提升提示词的字段提取精准度 |
| 最大上下文token数 | 8000–12000 token | 该品类的文档包含多份表单内容，需容纳至少3份核心文档的完整文本 |
| 对话超时阈值 | 600秒 | 该品类需跨CRM、身份管理系统拉取数据，需预留足够的接口调用时长 |
| 单次对话变量上限 | 前5个注入变量 | 避免过多变量干扰提示词的上下文聚焦，符合该品类的核心字段数量 |

## 容易做错的三处
- 现象：调试预览对话时返回固定短回复，响应token自动降至200以内。原因：未限制`messages`的历史轮次，过多旧对话占用了全部上下文token，导致后续回复被截断。
- 现象：部分租户的开通配置未生效，交付确认单出现字段为空的情况。原因：未在`variables`中注入租户ID，提示词无法匹配对应租户的专属配置数据。
- 现象：对话过程中错误将通用权限项写入管理员账号清单。原因：未按文档类型区分字段提取规则，混淆了租户配置表与管理员账号清单的字段定义。

## 怎么确认配好了
- 发起一次模拟开通流程的对话，检查绑定的`chatId`是否与测试租户ID一致，确认上下文绑定正确。
- 调用变量注入环节，验证`variables`中是否包含当前租户的核心字段，确认数据注入完整。
- 触发一次跨系统拉取数据的场景，检查对话是否在设定的超时阈值内返回结果，确认超时配置生效。
- 查看调试日志，确认多轮对话的上下文仅保留指定轮次的消息，无冗余数据干扰。
