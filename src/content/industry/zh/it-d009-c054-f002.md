# 容器平台运维的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
容器平台运维的日常文档包含集群变更单、命名空间配额表、部署记录、故障报告四类核心内容。数据主要来源于Kubernetes API、镜像仓库、监控系统与CI流水线，更新频率为每日或每次集群变更时更新。集群变更单包含变更时间、影响集群范围、资源调整项等字段；命名空间配额表标注namespace名称、CPU与内存配额单位；部署记录与故障报告则关联具体Pod、节点ID与时间戳。

## 这些特征在「上下文与 token」这一环带来什么约束
运维文档的多源异构特征决定了上下文召回需精准匹配字段与场景，频繁的更新节奏要求上下文不能包含过期数据。单份关联文档的token总量较高，若未限制上下文范围，易超出模型的token承载上限。多类文档并行存储时，若未关联历史上下文，易出现跨场景的内容混淆，例如将Pod异常排查的请求错误归类为资源配额调整。同时，分段式文档的上下文关联依赖严格的分段规则，手动调整分段易破坏上下文的逻辑完整性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 容器平台运维的单组关联文档（集群变更单、配额表、故障报告）总token量通常在此区间，避免超出模型上下文上限 |
| `quoteMaxToken` | 2000–3000 token | 单条运维文档片段的有效信息token上限，确保召回内容精准匹配需求 |
| 单次搜索上限 | 前6条 | 日常运维关联的变更记录、部署记录数量通常不超过6条，避免冗余上下文干扰 |
| 上下文召回相似度阈值 | 0.75–0.85 | 区分集群资源配额调整、Pod异常排查等不同场景的运维文档，降低误召回概率 |
| 历史上下文保留时长 | 按实测标定 | 匹配运维数据的日/每变更更新频率，避免使用过期的集群状态数据 |

## 容易做错的三处
- 生成的运维需求文档出现分段上下文混乱，跨集群的配额配置与变更单内容混淆。原因：未设置合理的上下文召回范围，将不相关的历史集群数据纳入当前生成上下文。
- 运维需求分类时，将Pod异常排查请求错误归类为兜底分类。原因：未启用历史上下文关联，仅基于当前问题关键词匹配，未结合之前的集群状态记录。
- 调用文档生成接口时出现token溢出报错，生成内容被强制截断。原因：未限制`maxContext`或`quoteMaxToken`的取值，导致召回的文档总token量超出模型支持上限。

## 怎么确认配好了
- 导入一份集群变更单与关联的命名空间配额表，检查召回的上下文仅包含该变更对应的集群数据，无无关的历史集群记录。
- 提交包含历史集群异常记录的连续问题，检查分类结果匹配历史上下文的场景，未跳转到兜底分类。
- 生成一份完整的运维需求文档，检查总内容未出现强制截断或token溢出报错。
- 查看FastGPT v4.17.0的配置日志，确认`maxContext`与`quoteMaxToken`的取值已按配置生效。
