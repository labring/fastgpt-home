# 容量规划与资源扩缩容的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的典型数据来自云账单、监控系统、业务预测报告、压测结果。日常产出的文档包括容量规划报告、扩容申请单、资源利用率报表、预算测算表，更新频率多为周度或月度。文档结构通常包含当前资源使用情况、峰值负载预测数据、扩容调整方案、对应预算测算内容，字段涵盖资源使用量、峰值负载阈值、申请资源规格、采购预算额度等，无固定统一格式，需匹配企业内部运维文档规范。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类的数据来源分散且字段多样，整合多源数据时会产生较大的token消耗，对上下文窗口容量提出较高要求。文档更新频率为周度或月度，无需高频刷新上下文，但需要稳定存储历史周期内的资源数据与测算结果。文档结构无统一规范，需灵活适配不同格式的运维文档内容，增加了上下文提取的复杂度。同时，峰值预测、预算测算等核心环节的内容需优先保留，需合理分配token配额以避免关键信息被截断。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本适配，针对本品类的运维文档场景调整：

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文窗口 | 8000–12000 token | 匹配本品类周度/月度数据的整合需求，避免核心测算内容被截断 |
| 引用最大token数 | 3000–5000 token | 优先保留压测报告、云账单等核心数据源的完整内容 |
| 上下文提取阈值 | 0.75–0.85 | 过滤低相关的历史资源数据，减少无效token消耗 |
| 历史数据召回上限 | 前6条 | 匹配本品类文档的更新频率，避免召回过多过期的资源数据 |
| 分块重叠长度 | 100–200 字符 | 适配运维文档的段落结构，减少上下文拼接时的信息丢失 |
| 单次搜索上限 | 前5条 | 控制上下文总token消耗，避免超出平台单轮任务限制 |

## 容易做错的三处
- 现象：调用时提示“Reached the max retries”，且上下文召回结果条数不足。原因：未合理设置历史数据召回上限，导致频繁重试获取数据，超出重试阈值。
- 现象：生成的容量规划报告中预算测算内容缺失。原因：未设置合理的引用最大token数，导致云账单、预算数据被截断。
- 现象：多模型编排时token消耗超出预期。原因：未限制单轮对话的最大上下文窗口，导致各模型重复占用token资源。

## 怎么确认配好了
- 导入一份典型的容量规划报告文档，核对上下文提取后保留的核心字段是否完整。
- 模拟多源数据整合场景，检查总token消耗是否符合预设的最大上下文窗口限制。
- 触发一次扩容申请单的生成流程，确认召回的历史数据条数符合设置的召回上限。
- 查看平台的token消耗统计，确认单轮任务的token使用量未出现异常波动。
