# 工单受理与问题分级的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据来源于工单系统、聊天记录、产品日志及客户合同SLA，更新频率为日级或实时。日常产出的文档包含客户工单、问题分级表、处理记录与服务报告，工单字段包含客户标识、问题描述、提交时间、优先级，问题分级表包含分级规则、响应时限要求，处理记录包含分派对象、处理进度与结果。数据围绕客户反馈入口展开，未涉及产品缺陷的回归验证环节。

## 这些特征在「上下文与 token」这一环带来什么约束
工单数据的实时更新要求上下文同步最新的客户反馈与处理进度，避免使用过期信息导致分级错误。多源数据（工单、聊天记录、日志）需要整合为统一上下文，需控制token消耗以避免超出模型上限。问题分级表与SLA合同是核心参考依据，需将其作为固定上下文片段纳入，同时需限制非必要历史工单的token占用。实时更新的特性要求上下文刷新频率匹配数据更新节奏，否则会出现响应超时或SLA违约风险。另外，客户工单的字段多样性可能导致上下文长度波动，需精准配置token阈值以平衡信息完整性与调用成本。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文长度 | 8000–12000 token | 匹配工单、聊天记录、分级表整合后的常规token消耗，避免模型截断核心信息，适配FastGPT v4.17.0的上下文处理逻辑 |
| 引用最大token | 2000–3000 token | 限定问题分级表、SLA合同等核心参考文档的token占用，防止覆盖客户实时反馈内容 |
| 上下文刷新间隔 | 15–30 分钟 | 匹配数据日级/实时更新的节奏，平衡同步成本与信息时效性 |
| 历史工单召回条数 | 前3–5条 | 仅召回与当前问题相关的历史处理记录，控制上下文总token消耗 |
| 核心文档引用阈值 | 按实测标定 | 适配团队内部问题分级表的文档长度，确保核心规则完整加载 |
| 全局上下文开关 | 关闭 | 避免工作流节点调用时加载无关的历史会话数据，贴合工单受理的专属上下文需求 |

## 容易做错的三处
- 无法准确统计单条工单受理流程的模型tokens消耗数量。原因是未启用上下文token统计配置，导致无法获取精准的消耗数据。
- 启动上下文同步时提示`AIPROXY_API_ENDPOINT or AIPROXY_API_TOKEN is not set`报错。原因是未配置App/Admin服务端的环境变量AIPROXY_API_ENDPOINT和AIPROXY_API_TOKEN，导致启动校验失败。
- 工作流节点调用时加载了全局无关会话的上下文数据。原因是未关闭全局上下文同步开关，导致节点调用时混入非当前工单的历史信息。

## 怎么确认配好了
- 查看上下文预览界面，确认召回的历史工单条数与预设的前3–5条一致。
- 测试触发工单受理流程，检查是否出现token超限报错，确认上下文长度符合配置要求。
- 验证核心参考文档（如问题分级表）是否完整加载到上下文片段中，未被截断。
- 检查服务端环境变量配置，确认`AIPROXY_API_ENDPOINT`与`AIPROXY_API_TOKEN`已正确配置，无空值。
