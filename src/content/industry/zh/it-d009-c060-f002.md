# 广告账户开户审核的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据通常来自广告平台后台、国家企业信用信息公示系统、客户提交的开户申请材料、行业准入规则。日常处理的文档通常包括开户申请单、营业执照扫描件、对应行业的经营资质文件、历史开户审核记录。数据更新节奏为每日同步或随单提交更新，文档结构包含主体身份信息、行业类目、资质有效期、审核节点记录等字段，无统一固定单位，随材料类型变化。

## 这些特征在「上下文与 token」这一环带来什么约束
多源异构的数据格式包含结构化表单、文本说明、扫描件转写内容，通常要求上下文处理需适配不同格式的token分配规则。随单更新的高频小批量数据，通常要求上下文窗口可灵活调整，避免冗余token占用。时效性较强的资质有效期、行业准入规则内容，通常需要限制上下文的时间范围，防止过期数据干扰审核判断。历史审核记录的数据量随申请单递增，需严格控制上下文token总量，避免超出模型处理上限。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文窗口 | 8000–12000 token | 适配单份开户审核材料+近30天历史3条审核记录的总token量，符合FastGPT v4.17.0的常规处理阈值 |
| 引用最大token限制 | 1500–2000 token | 确保从多源材料中提取的有效资质信息不超出模型处理上限，避免截断关键字段 |
| 上下文时间范围 | 近30天 | 过滤过期的行业规则与历史审核记录，减少无效token占用 |
| 上下文分块长度 | 800字符 | 匹配开户材料的常见段落长度，降低分块后的token碎片化程度 |
| `maxContext` | 按实测标定 | 适配不同广告平台的后台接口返回数据量，避免因数据超限报错 |
| `quoteMaxToken` | 按实测标定 | 适配不同格式的资质材料转写后的token长度，优化提取精度 |

## 容易做错的三处
- 现象：配置广告平台接口时出现ACCESS_TOKEN相关报错。原因：误将其他平台的API密钥填入广告平台接口的令牌字段，未使用对应广告平台的授权令牌。
- 现象：多模型编排的审核工作流中，token占用超出单次上限，导致审核结果截断。原因：未为每个模型节点设置独立的上下文参数，多个模型的上下文数据叠加后超出窗口限制。
- 现象：上下文窗口过大导致服务处理超时。原因：未限制上下文的时间范围，拉取了过量的历史审核记录，占用过多token导致处理延迟。

## 怎么确认配好了
- 导入单份完整的开户申请与资质材料，检查上下文加载后是否显示所有字段，无截断提示。
- 运行多模型编排的测试工作流，查看每个节点的token消耗统计，确认各节点的上下文参数独立生效。
- 配置`quoteMaxToken`后，提取资质材料的关键字段，验证转写内容未被提前截断。
- 模拟无网络环境下的本地测试，确认服务启动时无`maxContext`相关的数据源报错。
