# 性能测试与容量评估的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的数据主要来源于压测平台、APM监控系统、数据库慢日志与生产流量基线。日常产出的文档包括压测方案、容量评估报告、压测数据记录与优化建议单，字段包含吞吐率、延迟时长、资源使用率、容量阈值等，单位分别为每秒事务数（tps）、毫秒、百分比、GB。数据更新频率为每月一次或每重大软件版本发布时更新，单次更新的数据量随版本规模调整。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类的数据多源异构，不同来源的格式与字段存在差异，整合时需要精准匹配上下文关联关系，导致上下文token的占用量较高。数据更新频率不固定，重大版本发布时会产生大量新增压测数据，需动态调整上下文窗口的容纳上限。日常文档的字段与单位多样，筛选有效上下文片段时需兼顾信息密度与token消耗，避免无效数据占用过多配额。此外，压测场景的上下文需关联历史测试记录与当前方案，而压测模型设计是最耗时的环节，进一步增加了对上下文召回精准度的要求。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本，适配性能测试与容量评估的文档起草场景。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配压测方案、历史压测记录与容量报告的总数据长度，避免上下文溢出 |
| `quoteMaxToken` | 2000–3000 token per quote | 限定单条引用的压测数据片段长度，平衡信息密度与token占用 |
| 上下文召回条数 | 前8–12条 | 匹配月度更新的压测数据规模，覆盖关键历史测试场景 |
| 上下文加载超时阈值 | 60 秒 | 适配压测平台数据查询的常规响应周期，防止加载失败 |

## 容易做错的三处
- 现象：压测数据引用时出现token超限报错，接口返回状态码413。原因：未限制`quoteMaxToken`的取值，单条引用数据过长导致上下文总token超出`maxContext`的配置配额，与社区中常见的token消耗异常问题一致。
- 现象：搜索结果返回无关的历史测试数据，无法关联当前压测场景的上下文。原因：上下文召回阈值设置过低，引入了不相关的压测记录，增加无效token消耗。
- 现象：上下文加载超时，界面显示加载失败提示。原因：单次上下文加载时长设置过短，未匹配压测平台的数据查询响应周期。

## 怎么确认配好了
- 导入1–2份历史压测方案与容量评估报告，检查上下文窗口是否正确加载指定数量的文档片段。
- 触发测试场景，查看token消耗统计，确认总token未超出`maxContext`的配置值。
- 模拟异常压测数据输入，检查是否仅召回与当前场景相关的历史数据。
- 验证上下文加载时长，确认在60秒内完成多源数据的整合与加载。
