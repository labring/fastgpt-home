# 数据库云服务运维的需求与设计文档起草：上下文与 token
本文基于FastGPT v4.17.0版本编写。

## 这个品类的数据长什么样
该品类的数据主要来自云数据库控制台、慢查询日志、性能监控指标与工单系统。日常产出的文档包括实例变更单、备份恢复记录、性能诊断报告与参数调整记录。数据更新频率随变更触发或按日更新，单份文档长度跨度较大，从数百字符的参数调整记录到数万字符的慢SQL定位报告均有覆盖。部分字段关联多租户实例标识，需严格区分不同客户的运维数据边界。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据特征对上下文与token处理带来多重约束。首先，文档长度跨度大，短则数百字符长则数万字符，直接拼接会快速超出token上限。其次，慢查询日志、性能诊断报告等数据包含大量结构化与半结构化内容，token密度较高，单次召回的有效内容易快速消耗配额。另外，多租户实例标识要求上下文严格绑定对应运维实例，跨实例的上下文拼接会导致数据混乱，同时增加token占用。最后，高频变更的运维数据要求上下文能实时拉取最新记录，需平衡召回效率与token消耗。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| maxContext | 8000–12000 token | 适配云数据库运维文档的平均总长度，避免单次上下文拼接超出模型限制 |
| quoteMaxToken | 1500–2000 token | 匹配单份运维文档的典型片段长度，防止单条引用占用过多上下文配额 |
| 单次搜索引用上限 | 前6条 | 对应日常运维文档的平均召回数量，平衡信息完整性与token消耗 |
| 上下文实例绑定开关 | 启用 | 严格隔离多租户运维数据，避免跨实例token混乱 |
| 实时数据召回间隔 | 10–30 分钟 | 匹配运维数据的更新频率，兼顾实时性与系统负载 |

## 容易做错的三处
- 现象：将`quoteMaxToken`设置为2000后，系统返回的回答token数仍超过3000，且日志中显示上下文拼接的总token超出限制。原因：未考虑多条引用的token会叠加，未同步调整`maxContext`的总配额。
- 现象：连续对话中无法保留上一轮的运维上下文，每一轮回答均需重新提问基础信息。原因：未启用实例绑定开关，或`maxContext`的配额设置过小，导致上一轮上下文被自动截断。
- 现象：录入慢SQL日志后，系统自动拆分导致关键SQL语句被截断，无法完整定位性能问题。原因：未针对长文本运维文档配置合理的上下文截断规则，默认拆分逻辑未保留完整的SQL代码块。

## 怎么确认配好了
- 导入一份典型的实例变更单，触发上下文召回，查看系统返回的token计数，确认总token未超出`maxContext`的配置值。
- 发起连续对话，依次询问同一实例的参数调整与备份恢复问题，检查每一轮回答是否关联了上一轮的上下文信息。
- 查看`quoteMaxToken`的配置，测试单条引用片段的token数，确认未超过设定的配额。
- 导入两个不同租户的运维数据，发起跨租户的查询请求，检查系统是否正确隔离了数据，未出现跨租户的上下文混淆。
