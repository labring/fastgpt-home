# 数据库运维的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
通常数据库运维的需求与设计文档数据来自数据库监控、审计日志、SQL执行计划、工单系统。日常产出的文档包含数据库变更单、慢SQL报告、备份记录、权限申请单，各文档包含实例名称、SQL语句、变更时间、权限等级、备份路径等字段，更新频率多为每日或每次数据库变更后。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据来源分散且格式各异，不同文档的token消耗差异明显，慢SQL报告等长文本内容可能占用大量token。更新频率的不确定性要求上下文需要支持动态加载近期数据，避免过期信息干扰。多类型文档的关联查询需要保留跨文档的上下文关联，若token分配不合理，可能导致关键信息被截断。此外，工单系统的关联条目较多，单次召回的内容量容易超出token上限，影响查询准确性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| 分块长度 | 800–1200 字符 | 匹配数据库变更单、慢SQL报告的典型段落长度，避免单块token超限 |
| 重叠长度 | 100–200 字符 | 保留跨块的SQL语句、变更步骤上下文，防止逻辑断裂 |
| `maxContext` | 8000–12000 token | 适配多份工单、监控日志的关联查询需求，覆盖典型运维文档的总token量 |
| `quoteMaxToken` | 2000–3000 token | 限制单条召回内容的token消耗，避免上下文过载 |
| 单次召回上限 | 前6条 | 匹配数据库运维工单的关联条目数量，平衡召回精度与token消耗 |
| 重排优先级 | 按变更时间倒序 | 优先召回近期的权限申请、备份记录，符合运维日常排查逻辑 |

## 容易做错的三处
- 配置`maxContext`时设置为2000 token，导致慢SQL报告的完整执行计划无法被完整读取，系统提示上下文长度不足。原因是未结合数据库运维文档的长文本特征调整参数，默认值不足以覆盖单份长报告的token需求。
- 未调整分块长度，直接使用默认配置，导致Excel格式的慢SQL报告被拆分为过小的块，出现重复匹配、颗粒度太粗的问题。原因是未针对该品类的结构化表格类文档调整分块规则，导致数据块无法完整对应单条慢SQL条目。
- 未正确配置AIPROXY_API_ENDPOINT（AI Proxy服务的根地址，例如http://aiproxy:3000，不得附加/v1或/chat/completions等路径）和AIPROXY_API_TOKEN（AI Proxy管理员Token，需与AI Proxy服务端配置一致且不能为空），会导致App/Admin服务启动校验失败或API调用返回401未授权、连接超时错误。原因是未在App/Admin服务端部署时配置必填环境变量，或填写了错误的代理根地址、与服务端不匹配的管理员Token。

## 怎么确认配好了
- 上传一份典型的慢SQL报告，查看分块预览界面，确认每个数据块的长度符合设定的分块长度区间。
- 发起一次权限申请单的关联查询，检查召回结果的条数与单次召回上限的设置一致。
- 查看系统日志，确认App/Admin服务启动时加载了正确的AIPROXY_API_ENDPOINT和AIPROXY_API_TOKEN环境变量，无启动校验失败或API调用401、超时报错。
- 测试变更单的上下文关联查询，确认召回的相关工单、监控数据的token总量未超过`maxContext`的设置值。
