# 数据清洗与质检的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的数据来源为原始数据集、ETL日志、标注平台及抽样结果，更新频率为每日或每批次。日常产出的文档包含清洗规则、质检抽样表、异常数据清单与交付报告，字段涵盖数据标识、异常类型、处理状态、抽样结果等，无专属单位，数据体量随业务批次变化。

## 这些特征在「上下文与 token」这一环带来什么约束
原始数据集体量随业务批次波动，需匹配上下文窗口容纳多批次数据关联信息；ETL日志与抽样结果的高频更新，要求上下文可实时加载最新校验记录；清洗规则、异常数据清单等文档的字段复杂度较高，会提升单条上下文的token消耗；每日或每批的更新节奏，需避免上下文缓存过期导致校验逻辑失效；数据不可用的出错后果，要求token配置预留冗余空间，防止因上下文截断丢失关键质检依据。

## 配置怎么定
在FastGPT v4.17.0中，可通过`maxContext`、`quoteMaxToken`等配置项调整上下文与token相关参数，具体配置如下：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 本品类数据随业务批次波动，需容纳多批次关联信息与异常记录，预留冗余避免上下文截断 |
| `quoteMaxToken` | 1500–2000 token | 清洗规则、异常数据清单等文档字段复杂度较高，需完整加载关键校验依据 |
| 上下文缓存有效期 | 6–12 小时 | 本品类数据更新频率为每日或每批次，缓存时长匹配更新节奏避免过期失效 |
| 单批次数据加载上限 | 前 1000 条 | 重复数据识别、异常值处理的核心数据集中在单批次前序样本，过多加载会增加token消耗 |
| 异常数据关联召回数 | 按实测标定 | 抽样质检环节需覆盖异常样本的关联信息，避免遗漏关键校验项 |

## 容易做错的三处
- 现象：界面弹出“上下文token超限”报错，或输出结果被截断。原因：未调整`maxContext`预留足够的上下文窗口，导致关键异常记录或清洗规则被截断。
- 现象：质检结果出现前后不一致，异常数据清单加载为空。原因：上下文缓存有效期设置过短，未匹配本品类每日或每批的数据更新节奏，导致最新校验记录未被加载。
- 现象：token消耗统计与实际业务不符，出现异常的输入输出token差值。原因：未将ETL日志、抽样结果等关联数据源纳入上下文统计范围，导致统计值偏离实际。

## 怎么确认配好了
- 导入单批次典型原始数据集，查看上下文加载的字段是否覆盖清洗规则、异常数据清单的核心内容。
- 模拟每日或每批的数据更新，检查上下文缓存是否能自动加载最新的抽样结果与ETL日志。
- 运行重复数据识别、异常值处理任务，核对输出结果是否包含完整的关联校验依据。
- 查看token消耗统计面板，确认统计范围包含本品类的所有关联数据源。
