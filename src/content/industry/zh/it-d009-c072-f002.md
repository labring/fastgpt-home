# 数据采集任务设计的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的数据主要来自客户需求、公开数据源、采集工具及自有样本库，更新节奏以单项目或周为单位。日常产出的文档包含采集方案、样本规格、授权说明与任务排期，文档字段通常包含样本范围、采集字段、合规要求、排期节点等。数据未经过清洗或标注，仅为原始待采集的需求定义与规则文档，未做预拆分或加工。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类的文档多为结构化的规则定义，单份文档长度差异较大，部分采集方案可能包含多页合规说明与样本细则。由于数据来源分散且更新频繁，上下文关联需覆盖跨文档的需求逻辑与历史规则。token消耗受样本范围定义的字段数量、合规文本长度影响，若未限制上下文与token配额，易出现单次调用超出模型上限，或因未关联历史采集规则导致配置偏差。同时，原始数据未经过预拆分，需在上下文处理中准确匹配需求与对应采集规则，避免token溢出。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本，适配本品类的业务特征：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 匹配本品类单项目下采集方案、样本规格等关联文档的总长度，避免单次调用超出模型限制 |
| 历史引用上限 | 前6条任务配置 | 匹配本品类按项目更新的节奏，避免上下文过载影响调用效率 |
| `quoteMaxToken` | 1500–2000 token | 适配本品类单份样本规格文档的典型长度，确保核心采集规则被完整纳入上下文 |
| 上下文刷新触发条件 | 按项目节点执行 | 匹配本品类每项目/周的更新频率，避免使用过期的历史采集规则 |
| 单条召回token上限 | 2000 token | 限制单条采集规则的token消耗，防止因文档未拆分导致的token溢出 |

## 容易做错的三处
- 现象：调用时出现`LLM model response empty`报错。原因：未限制`maxContext`配额，上下文总token超出模型支持范围，模型无法生成有效响应。
- 现象：配置`quoteMaxToken`为2000 token后，系统提示单轮调用token超限。原因：未同步调整`maxContext`的总配额，单条引用的token叠加后超出整体上下文限制。
- 现象：连续对话中无法关联历史采集任务的规则，导致配置偏差。原因：未设置按项目节点触发的上下文刷新逻辑，使用了过期的历史配置。

## 怎么确认配好了
- 核对单份采集方案与关联文档的总长度，调整`maxContext`取值覆盖当前项目的典型文档规模。
- 测试包含3条历史任务配置的调用场景，确认单条引用的token未超出`quoteMaxToken`的限制。
- 触发一次项目节点更新，确认上下文配置自动刷新为最新的任务规则。
- 查看系统运行日志，确认未出现token超限或响应为空的报错记录。
