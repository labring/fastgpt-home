# 文档站维护的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
这个品类的典型主体为技术写作者、文档站维护者与开发者关系团队，日常产出的文档包含安装文档、API文档、迁移指南与FAQ。数据通常来自代码仓库、文档站构建日志、用户反馈与版本发布记录，更新频率为每周或每版本发布时同步。文档结构多包含版本标识、操作步骤、参数说明三类核心字段，最耗时的环节为示例验证、版本差异同步与过期内容清理，数据更新后需同步匹配对应版本的文档内容。

## 这些特征在「上下文与 token」这一环带来什么约束
文档站维护的多类型文档结构，要求上下文匹配需覆盖版本标识、操作步骤等核心字段，避免遗漏关键信息。每周或每版本发布的更新节奏，要求上下文窗口需适配快速迭代的内容变更，防止引用过期文档片段。多来源的数据需通过上下文筛选，区分代码仓库的技术细节与用户反馈的常见问题，避免上下文混杂导致模型误解。长期可查的使用说明属性，要求token分配需优先保障核心文档的召回优先级，减少非必要内容占用上下文空间。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| 最大上下文 | 单轮不超过128000 token | 适配FastGPT v4.17.0的主流模型上下文上限，覆盖多文档批量召回的需求 |
| 知识库最大引用 | 前8条匹配结果 | 匹配文档站单页面内容的常见长度，平衡召回范围与上下文负载 |
| 最大响应tokens | 4000至8000 token | 覆盖安装步骤、API参数说明等常见文档内容的输出长度 |
| `maxContext` | 按文档站单版本总token数的60000至115200 token | 适配周更/版本级更新的内容同步需求 |
| `quoteMaxToken` | 单条引用内容不超过2000 token | 避免单条文档片段过长占用过多上下文空间 |

## 容易做错的三处
-  知识库图片输出地址被截断：现象为生成的回复中图片链接显示不完整，仅保留部分路径。原因是`quoteMaxToken`设置过小，导致图片链接所在的文档片段被提前截断，未完整加载完整地址。
-  模型上下文理解准确性不足：现象为回复中出现过期的安装步骤或错误的API参数说明。原因是未按版本更新频率调整`maxContext`的召回范围，导致旧版本文档片段被优先召回。
-  响应内容超出预期长度：现象为回复被提前截断或超出模型输出限制。原因是最大响应tokens设置过低，未覆盖完整的文档内容输出需求。

## 怎么确认配好了
-  上传单份典型文档（如安装指南），触发问答测试，核对回复中是否包含完整的文档内容与版本标识。
-  查看上下文日志，确认召回的文档片段均为当前版本的有效内容，无过期文档混入。
-  调整配置项后，对比不同配置下的回复长度与召回条数，确认符合业务需求。
-  测试包含图片链接的文档问答，确认图片地址完整显示，无截断情况。
