# 日志平台与可观测性的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的核心数据来自日志系统、Trace平台、Metrics系统与应用SDK，日常产出的文档包括日志采集规范、链路追踪说明、指标字典、看板配置记录。数据更新频率为每日或随版本迭代，文档结构多包含字段定义、采集规则、链路关联逻辑、指标维度与看板配置项，字段多包含日志级别、Trace ID、指标名称、时间戳等，单位涵盖毫秒、字节、百分比等。

## 这些特征在「上下文与 token」这一环带来什么约束
日志采集规范、链路追踪说明等文档通常篇幅较长，且包含大量结构化字段与关联信息，易超出单轮AI上下文长度。数据来源多为实时或近实时的系统数据，需结合最新的采集配置与链路信息生成文档，对上下文的时效性要求较高。不同文档的字段与单位差异明显，需准确匹配上下文内的字段定义，避免因token截断导致字段信息缺失。并发处理多份文档时，需合理分配token与上下文资源，防止单任务占用过多导致其他任务无法正常加载上下文。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 匹配日志采集规范、链路追踪说明等文档的平均篇幅，避免核心内容被截断 |
| `quoteMaxToken` | 2000–3000 字符 | 对应单条日志片段或Trace节点的典型长度，确保引用的结构化信息完整 |
| 上下文召回条数 | 前3–5 条 | 聚焦核心的字段定义与关联规则，减少非必要token占用 |
| 上下文刷新周期 | 每日或版本更新后 | 匹配数据日更或随版本迭代的更新频率，保证上下文时效性 |
| 单轮输出token上限 | 4000 token | 控制单任务输出规模，适配多数开源模型的token限制 |
| 并发路数 | 按服务器内存与CPU占用标定 | 避免单节点资源耗尽，适配离线或本地部署的硬件条件 |

## 容易做错的三处
- 生成的需求文档出现字段缺失或链路关联逻辑不连贯，原因是未调整`maxContext`参数至匹配文档长度的区间，导致上下文被提前截断。
- 单任务处理多份日志数据时频繁触发上下文溢出报错，原因是未合理设置`quoteMaxToken`参数，单条引用片段占用过多token资源。
- 离线部署FastGPT v4.17.0时出现AI proxy报错，提示get tiktoken dial tcp lookup失败，原因是离线环境未提前下载tiktoken依赖包，或未配置本地镜像源导致无法拉取token计算依赖。

## 怎么确认配好了
- 上传一份典型的日志采集规范文档，检查生成的输出是否包含完整的字段定义与采集规则，无明显截断内容。
- 发起多任务并发测试，观察各任务的上下文调用状态，确认无频繁的上下文溢出报错。
- 调整数据更新时间后，触发文档生成流程，检查输出是否包含最新的配置项与字段说明。
- 离线环境下手动验证tiktoken依赖是否已本地部署，确认无网络依赖报错。
