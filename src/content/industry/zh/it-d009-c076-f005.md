# 日志平台与可观测性的需求与设计文档起草：多轮对话与提示词

## 这个品类的数据长什么样
该品类的数据主要来自日志系统、Trace平台、Metrics系统与应用SDK。日常产出的文档包含日志采集规范、链路追踪说明、指标字典、看板配置记录。数据更新频率为每日或每版本发布时。数据字段包含时间戳、日志级别、服务来源、traceID、spanID、指标数值与关联标签等，部分字段需匹配标准化格式要求。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
多源数据的混合输入要求多轮对话需按数据源分类整理上下文，避免不同系统的字段混淆，例如区分日志字段与链路追踪字段的校验规则。高频更新的数据与文档需要对话流程支持实时同步最新版本的内容，避免引用过时的采集规范或看板配置，确保需求文档的时效性。多样的文档结构要求提示词预设不同场景的检索规则，适配日志字段校验、链路关联排查、看板配置记录等不同任务的起草需求。标准化字段的要求则需要在对话中嵌入格式校验逻辑，确保输出的文档字段符合系统的统一规范，避免后续运维中的配置错误。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `chatId` | 绑定专属对话ID | 区分不同的可观测性需求起草任务，避免上下文混淆 |
| `messages` | 保留前 8 轮对话内容 | 覆盖当前需求起草的历史交互，避免上下文丢失 |
| `variables` | 绑定日志服务地址、指标字典ID | 自动替换提示词中的业务占位符，减少手动输入 |
| 分块长度 | 800–1200 字符 | 适配单条日志或链路记录的典型长度 |
| 单次召回条数 | 前 5 条 | 匹配日常排查的常用证据量 |
| 最大上下文 token 数 | 7000–9000 token | 适配主流大模型的上下文限制 |

## 容易做错的三处
- 上传可观测性相关文档后提示上传失败，但纯文本输入对话可正常运行。原因是未配置对应文档类型的解析规则，或上传文件的格式超出平台支持范围。
- 对话过程中出现`Unexpected end of JSON input`报错，使用ChatGLM2模型时更频繁。原因是上下文窗口设置过大，导致大模型返回的内容被截断，无法生成完整的JSON格式响应。
- 多轮对话生成需求文档的速度偏慢。原因是单次召回的文档条数过多，或上下文窗口包含了过多历史无效对话，增加了大模型的推理负载。

## 怎么确认配好了
- 在FastGPT v4.17.0版本的平台上，上传一份日志采集规范文档，等待解析完成后发起对话，检查是否能正确引用文档中的字段要求。
- 发起包含多轮交互的测试对话，查看`messages`配置是否保留了最近的有效交互内容，未被无关历史覆盖。
- 测试上传不同格式的可观测性文档，确认无上传失败的情况，验证配置的解析规则生效。
- 调整上下文窗口的token数，发起长对话测试，确认未出现JSON截断报错。
