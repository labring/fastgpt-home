# 机柜上架与布线的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
通常服务于IDC运维工程师、网络工程师与设备实施人员，日常处理的文档包含上架申请单、机柜布线图、端口标签表、施工记录等。数据主要来自DCIM系统、企业资产系统、网络拓扑图与客户服务工单，更新频率为每单/日。文档字段包含机位编号、机架单位（U）、线缆类型、端口号、施工日期等，部分文档为结构化表格形式，部分为拓扑类图形关联文本。

## 这些特征在「上下文与 token」这一环带来什么约束
由于数据来源包含多套系统的结构化与半结构化内容，且更新频率为每单/日，上下文召回需同时关联资产、拓扑与工单数据，对token总量与单条召回长度提出明确要求。机柜相关文档的核心字段如机位编号、线缆规格等需优先保留，避免因token限制被截断。同时单工单关联的文档总内容量存在波动，需通过上下文配置适配不同量级的召回数据，防止出现内容缺失或上下文溢出的问题。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文 | `8000–12000 token` | 覆盖单工单关联的上架申请、布线图、端口标签表等多份文档的总内容量 |
| 引用最大token | `2000–3000 token` | 限定单条召回内容的token占用，优先保留机位规划、线缆类型等核心字段 |
| 单次召回上限 | 前5条 | 匹配每日单工单的关联数据量级，避免过多历史数据占用上下文token |
| 上下文同步频率 | 按工单提交时间 | 匹配每单/日的更新节奏，确保召回最新的施工记录与资产系统数据 |

## 容易做错的三处
- 配置`maxContext`后仍出现上下文截断报错，提示token超出限制。原因：未结合机柜文档的实际总内容量调整取值，误使用通用场景的小窗口配置。
- 调用时出现`failed to get gpt-3.5-turbo token encoder`异常日志。原因：未正确关联本地模型的token配置，或模型版本与FastGPT v4.17.0不兼容。
- 生成的需求文档中端口标签信息缺失。原因：`quoteMaxToken`取值过小，导致端口编号、线缆规格等核心字段内容被截断。

## 怎么确认配好了
- 上传一份机柜上架申请文档，查看上下文召回的关联数据是否包含DCIM资产信息与历史施工记录。
- 测试生成需求文档时，检查返回内容是否包含完整的机位编号、线缆类型等核心字段，无截断情况。
- 查看系统日志，确认无token超限或编码器异常报错。
- 调整配置项后，对比前后召回的内容量变化，验证配置生效。
