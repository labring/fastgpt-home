# 架构设计与技术方案的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
通常，该品类的核心数据来自架构师、技术负责人及平台研发组的日常产出，包含技术方案文档、架构拓扑说明、容量评估表、技术评审纪要等。数据来源涵盖历史业务流量数据、服务部署拓扑、运行监控指标以及业务中长期增长计划。文档更新频率多为月度或伴随重大业务需求调整，单次文档体量差异较大，长文本技术方案可达数万字符，结构化评审纪要则多为零散片段。最耗时的环节集中在约束条件收集、方案取舍论证与评审意见闭环，数据结构兼具半结构化文本与量化指标两类形式。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据特征直接影响上下文与token的配置逻辑。首先，文档体量差异大且包含长文本内容，要求上下文窗口需适配不同长度的输入，避免关键架构描述被截断。其次，数据来源包含结构化监控指标与零散评审纪要，需精准控制单条引用的token消耗，防止冗余数据挤占上下文空间。再者，跨服务边界的架构设计内容需要保留关联上下文，避免拆分后丢失关键约束信息，同时需平衡召回内容的数量与token消耗，防止单次问答的token开销过高。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | `8000–12000 token` | 适配架构设计文档的平均长度，避免超出模型上下文上限导致内容截断，FastGPT v4.17.0版本支持该参数的灵活调整 |
| `quoteMaxToken` | `1500–2000 字符` | 限定单条引用文档的token消耗，防止长文本技术方案片段挤占整体上下文空间 |
| 分块长度 | `1000–1500 字符` | 匹配技术方案的段落结构，平衡上下文召回精度与token使用效率 |
| 重叠长度 | `100–200 字符` | 保留分块间的上下文关联，避免关键约束条件被拆分后丢失 |
| 单次搜索上限 | `前 8 条` | 匹配架构设计文档的关联信息密度，避免过多冗余数据占用token配额 |

## 容易做错的三处
- 现象：生成的Markdown表格无法正常渲染，内容被截断。原因：未限定`quoteMaxToken`的合理取值，导致引用的技术方案片段过长，超出模型表格渲染的token承载上限。
- 现象：单次问答响应耗时过长，token消耗超出预期。原因：未设置合理的`maxContext`配额，召回了过多历史流量、服务拓扑等冗余数据，挤占整体上下文空间。
- 现象：技术评审纪要中的关联约束条件未被完整召回。原因：分块长度设置过小且重叠长度不足，导致拆分后的文档块丢失关键关联信息。

## 怎么确认配好了
- 上传一份典型的技术方案文档，核对生成的需求文档是否覆盖所有核心架构边界描述，无内容截断情况。
- 查看平台的上下文token消耗记录，确认单轮对话的token量处于配置的`maxContext`范围内。
- 测试召回历史监控指标相关的内容，确认关联的容量评估与评审纪要片段未被遗漏。
- 生成包含表格的输出内容，确认格式可正常展示，无渲染异常。
