# 渗透测试服务的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自目标系统日志、公开漏洞库、自动化扫描器输出、红队手工验证记录。日常产出的文档包括测试授权书、渗透测试报告、漏洞复现记录、整改建议。数据更新以单个测试项目为周期，或在目标系统重大版本迭代时同步。数据字段包含测试范围、漏洞编号、利用路径、风险评级、整改要求等，无统一固定单位，随单个项目的文档结构调整。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据多源且按项目隔离，上下文需严格绑定单个测试项目的授权书、报告等专属数据，避免跨项目上下文污染。数据包含结构化扫描结果与非结构化手工验证记录，混合格式会增加token处理复杂度，单次上下文token消耗波动范围较大，需通过`maxContext`控制整体上下文的token上限，通过`quoteMaxToken`限制单条引用的token长度。数据更新随项目进度调整，上下文的有效范围需与项目周期对齐，避免引用过期的扫描或验证数据。同时，涉及授权合规与风险评级的关键信息，需保证足够的token长度以完整保留，防止关键字段被截断。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 渗透测试文档包含多份报告与验证记录，需保留足够上下文以关联测试范围与漏洞细节 |
| `quoteMaxToken` | 2000–3000 token | 单条引用的漏洞报告或扫描结果需控制token长度，避免单次请求过载 |
| 单次召回条数 | 前3–5条 | 渗透测试数据按项目聚合，过多召回会增加token消耗，过少则可能遗漏关键漏洞路径 |
| 上下文重排 | 开启 | 需优先召回与当前测试任务相关的高风险漏洞数据，提升上下文准确性 |
| 问题优化 | 开启 | 渗透测试任务的需求描述多为技术细节，优化后可更精准召回相关文档 |
| 上下文绑定周期 | 按项目周期标定 | 需与单个测试项目的生命周期对齐，避免跨项目数据被误纳入上下文 |

## 容易做错的三处
- 现象：单次请求返回的token消耗远超配置的`maxContext`上限，或出现“上下文过长”的报错提示。原因：未按单个测试项目隔离上下文，将多个项目的授权书、报告数据同时纳入上下文，导致token超额堆积。
- 现象：MCP工具调用时无法获取工作流中的全局变量token。原因：未将全局变量token配置为上下文参数，未在工具调用节点中绑定项目专属上下文变量。
- 现象：知识库召回的文档包含过期的扫描结果，或未优先召回高风险漏洞的复现记录。原因：未设置上下文与项目周期的绑定规则，导致过期数据被纳入上下文。

## 怎么确认配好了
- 查看FastGPT v4.17.0版本的上下文日志，确认每次请求的上下文token值在配置的`maxContext`范围内。
- 发起测试任务，检查MCP工具调用节点的参数配置，确认已传入工作流中的全局变量token。
- 切换不同的测试项目，验证知识库召回的文档仅属于当前项目，无跨项目数据混入。
- 调整单次召回条数，发起测试请求，确认召回的文档数量与配置值一致，且优先显示高相关的漏洞数据。
