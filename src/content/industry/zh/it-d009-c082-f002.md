# 渠道归因与线索分发的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的核心数据来自广告平台、CRM系统、归因SDK与表单系统，日常产出的文档包括归因规则、线索分发表、渠道报表与异常核对单。数据更新频率通常为日度或周度，单份文档包含渠道ID、线索ID、转化时间、归属销售ID等核心字段，不同系统的字段格式存在细微差异，需统一对齐后才可用于上下文处理。单批次的渠道报表数据token总量通常较高，直接处理易超出模型上下文限制。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类的数据来源分散且格式存在差异，需在上下文处理中统一字段规则，否则会导致线索归属判断错误，影响最耗时的渠道参数核验、重复线索去重与销售归属确认环节。由于数据按日/周更新，上下文需保留最近批次的报表与规则数据，避免引入过时信息。单份文档的token总量较大，直接上传会超出模型上下文限制，需按文档结构切片后再处理。同时，连续追问需关联线索ID与渠道ID等核心字段，否则无法完成任务要求的关联校验。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---|---|--- |
| `maxContext` | `8000–12000 token` | 覆盖单批次归因规则、渠道报表与线索分发表的总token量，避免核心字段被截断 |
| `quoteMaxToken` | `2000–3000 token` | 匹配单条线索的归因数据与归属规则的token需求，确保引用内容完整 |
| 上下文切片长度 | `800–1200 字符` | 适配归因规则、线索分发表的单块内容粒度，减少跨块关联的误差 |
| 上下文召回条数 | 前3条 | 渠道归因数据按日/周更新，无需过多历史数据干扰当前任务 |
| 上下文切片重叠比例 | 10%–15% | 保留相邻切片的渠道ID、线索ID等核心字段信息，避免跨块分割导致的关联失败 |

## 容易做错的三处
- 现象：上传完整的渠道报表后，系统提示上下文溢出，仅加载前半部分内容，渠道ID字段丢失。原因：未配置上下文切片参数，直接上传超出模型支持的token总量的文档。
- 现象：调用FastGPT工作流API时，无法关联上下文，第二次提问开始返回无关内容，且工作流面板已配置上下文。原因：未在工作流的上下文模块中绑定全局会话存储，或`maxContext`参数设置过小导致历史会话数据被自动截断。
- 现象：配置上下文召回后，返回的引用内容包含大量无关的异常核对单数据，干扰当前的渠道参数核验任务，导致后续ROI计算失真。原因：未限制`quoteMaxToken`参数，召回的内容超出当前任务的匹配范围，混入了非本次所需的文档片段。

## 怎么确认配好了
- 上传单份完整的渠道报表与归因规则文档，检查系统加载后的内容是否完整，无自动截断或上下文溢出提示。
- 发起连续两次关联同一线索ID的提问，检查第二次提问是否能正确关联第一次提到的线索归属信息。
- 进入FastGPT v4.17.0的上下文配置面板，确认所有设置项的取值与预设范围一致。
- 触发一次重复线索去重的测试任务，检查返回的引用内容仅包含当前任务所需的归因规则与线索数据，无无关的异常核对单内容。
