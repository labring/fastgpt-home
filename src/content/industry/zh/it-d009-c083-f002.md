# 游戏内容合规自查的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的数据主要来自游戏研发阶段的剧情脚本、游戏内文本、美术资源说明，以及监管公开的合规要求。日常产出的文档包括内容自查表、敏感内容修改记录、用户协议、合规评审纪要。数据更新随游戏版本迭代或大型活动上线节奏推进，每份文档包含待审核内容、修改痕迹、评审意见等字段，无统一固定单位，随审核环节的具体需求动态调整。

## 这些特征在「上下文与 token」这一环带来什么约束
游戏内容合规自查的审核内容包含多模态文本与关联美术信息，单次审核需关联多轮评审纪要与历史修改记录，因此上下文承载的内容复杂度更高。按版本或活动的更新节奏，上下文需覆盖单周期内的全量待审核素材，token消耗随审核内容规模线性增长。合规文档的字段包含敏感内容标记、评审意见等非标准化文本，需精准召回历史上下文以确保审核一致性，同时需避免无关历史内容占用token配额，影响单轮审核的响应效率。多模型编排场景下，需明确各环节的token分配规则，避免跨模型的token配额冲突。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文窗口 | 8000–12000 token | 覆盖单版本游戏剧情脚本、内容自查表等核心审核素材的总token需求，匹配每版本更新的审核规模 |
| 单条引用最大token | 1000–1500 字符 | 匹配合规文档中单条待审核文本、剧情片段的长度范围，避免单条引用占用过多上下文配额 |
| 上下文召回条数 | 前5–7条 | 覆盖单周期内的敏感内容修改记录、合规评审纪要，确保审核时能参考历史处理逻辑 |
| `maxContext` | 7000–11000 token | 适配FastGPT v4.17.0的平台默认上下文上限，匹配单活动周期的审核内容规模 |
| `quoteMaxToken` | 800–1200 字符 | 限制单条引用内容的token消耗，优化多轮编排时的token共享效率 |

## 容易做错的三处
- 现象：多模型编排工作流中触发重试失败，日志显示`Reached the max retries p`。原因：未配置`quoteMaxToken`限制单条引用的token消耗，多轮对话中上下文累计token超出平台承载上限，触发重试机制失效。
- 现象：审核结果未关联历史敏感内容修改记录。原因：未设置合理的上下文召回范围，仅召回少量历史文档，无法覆盖单版本或活动的全量合规评审痕迹。
- 现象：单轮审核响应超时。原因：未限制`maxContext`的取值，将上下文窗口设置过大，导致平台加载过多历史内容，超出响应时间阈值。

## 怎么确认配好了
- 查看工作流的上下文配置面板，确认`maxContext`与`quoteMaxToken`的取值匹配当前审核周期的内容规模。
- 发起一轮测试审核，检查返回结果是否包含历史评审纪要与修改记录，确认上下文召回范围符合预期。
- 运行多模型编排测试，观察token消耗日志，确认单轮对话的token占用未超出预设配额。
- 模拟多轮审核流程，检查是否出现重试报错或响应超时，确认配置的合理性。
