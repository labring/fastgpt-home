# 游戏服务器研发运维的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的日常产出文档包含服务器架构说明、开服方案、合服方案与故障报告，数据主要取自游戏运行日志、在线人数监控数据、业务数据库及玩家提交的工单。数据更新节奏多为每日更新或随游戏活动节点同步，核心文档字段包含服务器节点配置、在线峰值阈值、合服数据校验规则等。处理的数据涉及实时在线状态、历史玩家行为记录，需关联多来源的结构化与半结构化信息。

## 这些特征在「上下文与 token」这一环带来什么约束
游戏服务器相关文档涉及的上下文包含多维度的运行数据与配置规则，单份核心文档的token长度通常较高，需限制整体上下文的token总量避免超出模型上限。多来源的混合数据容易导致上下文冗余，需精准筛选与当前需求匹配的内容。活动期间的高频更新数据会导致上下文过期，需定期清理过时的工单与日志数据。合服、开服场景的文档需关联跨节点的配置信息，上下文召回需覆盖多个关联文档片段，同时避免引入无关的故障历史干扰当前任务。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 游戏服务器的开服、合服方案单份长度较高，结合关联的架构说明文档，整体上下文需控制在该区间避免模型输出截断 |
| `quoteMaxToken` | 1500 token | 单条召回的文档片段需匹配核心配置字段的长度，避免冗余占用token |
| 上下文刷新周期 | 每24小时 | 匹配该品类数据的日更节奏，确保上下文使用最新的在线监控与工单数据 |
| 召回文档条数 | 前3–5条 | 该品类的核心需求通常关联3–4份关联文档，召回过多会增加token消耗且引入无关内容 |
| 过期上下文清理 | 活动结束后7天内 | 匹配游戏活动的更新周期，清理过时的活动相关数据与历史工单 |

本配置适用于FastGPT v4.17.0版本。

## 容易做错的三处
- 现象：模型返回的开服方案内容被截断，仅显示部分服务器节点配置。原因：`maxContext`配置过低，未匹配该品类文档的实际token长度，导致高token的配置内容被模型截断。
- 现象：上下文残留过期的活动工单数据，导致新的开服容量估算出现偏差。原因：未配置过期上下文清理规则，或清理周期设置长于数据更新节奏，导致过时数据未被及时清除。
- 现象：召回的文档片段包含大量无关的历史故障报告，无法精准匹配当前合服校验需求。原因：召回文档条数配置过多，引入了非核心关联的文档内容，增加了token消耗且干扰模型判断。

## 怎么确认配好了
- 上传一份典型的开服方案与关联的架构说明文档，测试模型输出是否完整覆盖核心配置参数，确认未出现内容截断。
- 手动导入过期的活动工单数据，检查系统是否按配置的清理规则自动清除该类数据。
- 发起合服数据校验的需求，检查模型召回的文档片段是否仅包含当前关联的合服方案与数据库配置内容。
- 发起三次连续的相关提问，检查上下文是否按配置的上限进行管理，未出现无意义的冗余叠加。
