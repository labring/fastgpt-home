# 游戏版号与出版申报的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
这个品类的数据来自国家新闻出版署办事服务、著作权登记、游戏包体、运营机构资料，日常文档包含申报请示文件、游戏申请表、著作权证明、审读报告，由出版单位、游戏发行法务、项目负责人维护，更新频率为每款游戏不定期，单款申报材料包含固定格式的申请字段与配套证明文件，不同文档的字段关联度较高。

## 这些特征在「上下文与 token」这一环带来什么约束
多来源的文档格式存在差异，拼接上下文时需区分不同类型的申报材料字段，避免无效内容占用token；单款申报材料的更新无固定周期，知识库同步时机需匹配申报进度，否则会导致上下文内容过时或token消耗异常；单款材料的字段数量较多，核心内容的token总量接近常规上下文上限，需严格控制召回的文档范围与token用量，避免超出`maxContext`与`quoteMaxToken`的配置限制；审批环节需核对多文档的一致性，上下文需精准召回对应字段，冗余的上下文会增加审读与修改的成本。

以下配置建议适用于FastGPT v4.17.0版本。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | 单款游戏申报材料的核心文档拼接后约6000-10000 token，预留合理冗余空间 |
| `quoteMaxToken` | `3000–5000 token` | 审读报告、游戏申请表等核心申报文件的有效内容占比约60%，控制单轮引用的token总量 |
| 单次搜索上限 | 前4条 | 该品类核心申报文档分为4类，过多召回会增加无效token消耗与上下文冗余 |
| 问题优化 | 按申报字段拆分查询 | 不同来源文档的字段关联度高，优化查询语句可提升精准召回，减少无效上下文 |
| 重排 | 启用 | 对召回的多来源文档进行相关性排序，优先返回与申报需求匹配度高的内容，降低token浪费 |
| 上下文更新触发 | 按单款游戏申报周期 | 该品类更新频率为每款不定期，按单款申报进度触发同步可避免无效token占用 |

## 容易做错的三处
- 现象：调用FastGPT应用API时返回的上下文为空，或未包含历史申报材料的关联内容。原因：未正确配置`maxContext`参数的取值范围，或未开启上下文拼接的自动同步开关，导致历史文档未被纳入上下文池。
- 现象：单轮查询的token消耗远超预设值，导致接口超时或返回内容被截断。原因：未设置`quoteMaxToken`参数，或取值过大，导致知识库召回的所有文档直接拼接进上下文，超出token限制。
- 现象：工作流中调用MCP工具时，无法获取全局变量中的申报token。原因：未将全局变量绑定到上下文传递环节，或配置中未开启全局变量的上下文引用权限，导致token无法随上下文传递。

## 怎么确认配好了
- 查看应用的上下文日志，确认召回的文档类型与数量符合预设的单次搜索上限。
- 调用API获取上下文内容，核对拼接后的token总量未超过`maxContext`的配置值。
- 模拟一次完整的申报文档查询，检查返回的内容仅包含与当前申报需求相关的字段，无冗余内容。
- 测试工作流中的全局变量传递，确认MCP工具可正常获取到绑定的上下文token。
