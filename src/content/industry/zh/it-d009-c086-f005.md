# 游戏版号与出版申报的需求与设计文档起草：多轮对话与提示词

## 这个品类的数据长什么样
该品类的数据来源包括国家新闻出版署办事服务要求、著作权登记文件、游戏包体材料、运营机构备案资料。数据更新节奏为每款游戏申报周期内不定期更新，随审批环节补充材料动态调整。日常核心文档包含申报请示文件、游戏内容申请表、著作权权属证明、内容审读报告，字段涵盖申报主体资质、游戏题材分类、著作权登记号、审读修改意见等，无统一固定格式模板，需贴合每次申报的具体要求调整。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源分散且随审批环节动态更新，要求多轮对话需跟踪不同阶段的补充材料，避免上下文丢失。文档无固定格式，提示词需适配多种文档结构，引导对话生成符合申报要求的结构化内容。每款游戏的申报数据独立，需通过`chatId`区分不同会话上下文，防止跨申报的信息混淆。审读报告与申请表的字段需严格对应，多轮对话需反复核对字段一致性，避免出现信息偏差导致审批不通过。同时，申报材料的专业性较强，提示词需包含行业专属术语的引导，确保生成内容符合官方审核标准。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本适配。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 单次搜索上限 | 前 8 条 | 匹配申报材料的核心字段分类，覆盖资质、内容、审读三类核心数据 |
| 最大上下文长度 | 4000–6000 字符 | 适配单款游戏申报文档的总长度，避免超出模型处理上限 |
| 问题优化 | 按实测标定 | 针对申报文档的专业术语优化提问逻辑，提升检索准确性 |
| `chatId` | 绑定单款游戏申报 ID | 区分不同申报项目的会话上下文，防止信息串用 |
| `variables` | 注入固定申报主体字段 | 减少重复输入，确保申报主体信息的一致性 |
| `messages` | 按审批环节分段存储 | 拆分不同阶段的申报对话内容，便于后续核对与追溯 |

## 容易做错的三处
- 对话返回包含换行符导致json请求失败。现象为接口返回报错提示包含格式异常相关内容，原因是未对返回内容做转义处理，换行符破坏了json格式的语法结构。
- 上传申报材料文件时触发报错，文本对话正常。现象为文件上传操作后弹出报错弹窗，原因是未配置对应文件类型的解析规则，或上传文件大小超出允许范围。
- 对话出现`Unexpected end of JSON input`报错，使用chatglm2模型。现象为对话中途中断并返回该报错文案，原因是模型返回内容不完整，或上下文长度超出模型支持阈值导致截断。

## 怎么确认配好了
- 新建单款游戏的申报会话，检查`chatId`是否绑定了对应申报的唯一标识，避免与其他项目混淆。
- 输入一段申报文档片段，测试对话返回是否包含正确的字段，验证`variables`注入的主体信息是否生效。
- 上传一份小型申报材料，测试文件上传是否正常，无报错提示。
- 发起多轮提问，检查`messages`是否保留了前几轮的申报信息，未出现上下文丢失的情况。
