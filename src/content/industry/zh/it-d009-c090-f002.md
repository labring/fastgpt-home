# 版本发布与Release Notes的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
通常，该品类的典型主体为开源维护者、发布经理与文档维护者。日常产出的文档包括Release Notes、变更日志、版本标签、发布检查单，数据来源涵盖Git标签、合并提交记录、CI制品、Issue里程碑，更新频率为每版本一次。数据字段通常包含版本号、变更类型、关联提交哈希、破坏性变更说明、制品校验值等，整体结构按版本迭代周期线性组织，单版本内容量随项目规模存在差异。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据关联多类代码与运维元数据，上下文需要覆盖版本关联的全链路信息，因此对上下文的召回范围与token分配提出明确要求。每版本一次的更新节奏要求上下文需随版本发布同步刷新，避免召回过时的历史数据。结构化的变更条目需要按关联度分配token，核心变更需优先承载，非关键内容需合理压缩。同时，数据出错会直接导致用户升级失败、社区误解，因此上下文的准确性与完整性要求较高，token配置需兼顾召回范围与内容完整性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 12000–15000 token | 匹配单版本Release Notes的平均内容长度，适配FastGPT v4.17.0的上下文承载上限 |
| `quoteMaxToken` | 3000–4000 token | 覆盖单条核心变更记录的完整表述，避免关键变更信息被截断 |
| 上下文刷新触发规则 | 与版本发布动作绑定 | 确保关联Git标签、CI制品的上下文数据随版本更新同步刷新 |
| 关联数据召回上限 | 前10条合并提交记录 | 聚焦当前版本的核心变更内容，避免上下文过载 |
| 上下文匹配阈值 | 0.75–0.85 | 过滤低关联度的历史变更信息，提升上下文精准度 |

## 容易做错的三处
- 模型输出内容被截断，末尾显示`...[hide 38432 char`。原因是`maxContext`配置值小于当前版本Release Notes的总token数，上下文承载不足。
- 出现`failed to get gpt-3.5-turbo token encoder`类异常。原因是未正确适配上下文token的编码规则，导致token计数异常。
- 无法召回对应版本的CI制品关联信息。原因是未配置与版本发布周期同步的上下文刷新规则，上下文数据未随版本更新同步更新。

## 怎么确认配好了
- 导入单版本的Release Notes文档，检查上下文召回的关联合并提交、Git标签数量符合预期配置。
- 触发文档起草流程，查看输出内容无截断，无`[hide char`类隐藏标记。
- 模拟版本发布动作，确认上下文数据自动刷新，关联的CI制品信息正确更新。
- 查看FastGPT v4.17.0的系统日志，无token编码相关的异常报错。
