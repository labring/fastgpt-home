# 版本发布与Release Notes的需求与设计文档起草：多轮对话与提示词

## 这个品类的数据长什么样
该品类的核心使用主体为开源维护者、发布经理与文档维护者，日常维护的文档包括Release Notes、变更日志、版本标签与发布检查单。数据来源通常为Git仓库标签、合并提交记录、CI构建制品以及Issue里程碑条目，更新频率随软件版本发布周期而定。文档结构一般包含版本号、变更归类条目、破坏性变更说明、制品校验信息等字段，无统一强制单位，字段内容随项目规模与发布规范调整，通常面向已完成合并的变更集合进行整理。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
该品类的数据分散在多个系统中，多轮对话需要跨源拉取关联数据，因此`messages`上下文需要包含不同来源的元数据标识以保证逻辑连贯。更新频率随版本发布，对话需要适配临时的版本节点触发，需限制上下文窗口避免冗余内容干扰。文档字段无统一规范，提示词需要支持动态适配不同项目的变更归类规则。面向公开发布的特性要求对话生成内容需规避未合并的变更，需在提示词中加入校验逻辑。变更归类与破坏性变更说明的耗时环节，需要对话支持分步拆解任务，避免单次请求超出处理上限。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `messages` | 按版本周期内的合并记录、Git标签、CI制品顺序拼接，不超过8000字符 | 适配该品类多源数据的拼接逻辑，符合FastGPT v4.17.0的上下文处理上限 |
| `variables` | 注入当前版本号、项目仓库地址、最近3条里程碑标题 | 补充发布文档所需的元数据，减少人工输入步骤 |
| `chatId` | 绑定当前版本发布的专属会话ID | 隔离不同版本的对话上下文，避免数据混淆 |
| 最大上下文长度 | 6000–10000 字符 | 适配版本发布相关文档的常规内容长度，平衡处理效率与信息完整性 |
| 上下文过滤规则 | 仅保留已合并的提交记录与已打标签的制品 | 符合该品类面向已合并变更公开发布的核心要求 |

## 容易做错的三处
- 现象：调用后返回对话报错，提示上下文格式异常。原因：未按版本周期的时间顺序拼接`messages`中的多源数据，导致上下文逻辑混乱。
- 现象：无法获取全量版本相关的对话记录。原因：未绑定专属`chatId`，导致会话上下文被其他版本的请求覆盖。
- 现象：生成的Release Notes包含未合并的提交内容。原因：未开启上下文过滤规则，未筛选已合并的变更记录。

## 怎么确认配好了
- 手动触发一次对话，检查生成内容是否仅包含已合并的变更记录与已打标签的制品。
- 查看会话列表，确认存在绑定当前版本的专属`chatId`会话条目。
- 注入测试变量，检查生成文档中是否自动补充了版本号、仓库地址等元数据。
- 模拟跨版本发起对话请求，确认不同版本的对话上下文不会互相干扰。
