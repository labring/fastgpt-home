# 玩家客服与舆情处理的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
这个品类的数据主要来自游戏客服系统、社区论坛、应用商店评论及游戏日志。日常产出的文档包括玩家工单、补偿申请单、舆情日报与标准化处理话术。数据更新节奏多为日更或实时同步，单条玩家反馈通常包含账号标识、问题描述、反馈时间与来源渠道，舆情数据则会标注情绪倾向与传播节点，整体文档以结构化字段搭配自由文本内容为主。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据多源且更新实时，同时包含结构化字段与长文本自由内容，会对上下文与token的处理逻辑带来多重约束。多源数据拼接时会快速消耗token配额，需精准控制召回内容的长度。玩家工单与舆情数据常关联历史交互记录，完整上下文才能支撑账号核验、补偿规则判断等核心操作，截断关键信息会直接影响处理准确性。高频实时更新的内容也要求上下文同步逻辑适配快速变化的反馈流，避免使用过期数据。

## 配置怎么定
以下配置基于 FastGPT v4.17.0 版本的界面与参数逻辑。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 8000–12000 token | 适配多源工单、舆情数据的拼接需求，避免截断玩家历史交互与补偿相关信息 |
| `maxContext` | 按实测召回总量调整 | 匹配品类内单次处理所需的完整历史数据规模 |
| `quoteMaxToken` | 1000–1500 字符 | 限制单条召回内容的token消耗，防止整体上下文超出模型上限 |
| 上下文召回条数 | 前4–6条 | 平衡信息完整性与token占用，覆盖玩家近期核心反馈与舆情关键节点 |
| 实时数据同步间隔 | 5–10 分钟 | 适配舆情与工单的实时更新节奏，避免使用过期的玩家反馈数据 |
| 长文档预处理截断长度 | 2000–3000 字符 | 处理超过上下文限制的长文档，避免触发400错误 |

## 容易做错的三处
- 离线部署时出现`get tiktoken dial tcp`报错，原因是未配置本地tokenizer依赖或代理地址，导致无法正常加载token计数工具。
- 高显存硬件下上下文上限仅为6656，原因是未正确调整`maxContext`参数，或显存利用率设置过高导致模型无法分配足够内存加载上下文数据。
- 工作流中传入token值后无法触发外部接口，原因是未将token作为上下文变量正确绑定到外部接口调用节点，导致参数传递失败。

## 怎么确认配好了
- 上传单条长玩家工单，检查上下文拼接后的总token数是否在设定范围内，无异常截断提示。
- 运行模拟舆情数据处理流程，确认实时同步的最新评论已被纳入上下文，无数据过期情况。
- 触发工作流中的外部接口调用，检查传入的参数是否与预设值一致，接口返回正常。
- 调整`quoteMaxToken`参数后，验证单条召回内容的token消耗符合预期，无异常溢出。
