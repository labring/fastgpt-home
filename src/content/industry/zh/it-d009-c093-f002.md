# 用户增长与留存运营的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
这个品类的日常文档包含增长实验方案、用户分层表、触达文案、留存分析报告。数据来源为用户行为日志、推送系统、实验平台、CRM系统，更新频率为日或周。文档字段包含用户ID、触达时间、实验分组、留存率等，单位涉及人次、天、条等，不同来源的数据格式存在一定差异，需整合后用于分析与运营，且主要聚焦站内用户生命周期的运营动作。

## 这些特征在「上下文与 token」这一环带来什么约束
品类数据多源且格式存在差异，上下文拼接时需整合多类数据，对参数的容错性与转义规则提出要求。数据更新频率为日或周，上下文刷新周期需匹配该节奏，否则会导致数据滞后。日常文档包含多源整合的分析内容，单份上下文的token占用量较高，需合理控制上下文总长度与引用片段的token占比，避免超出模型限制。用户分群、触达节奏设计等核心环节依赖精准的上下文匹配，召回范围需聚焦核心维度，避免无关数据占用token资源。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的逻辑制定。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 品类日常文档包含多源整合的留存分析报告、用户分层表，单份上下文整合数据量较大 |
| `quoteMaxToken` | 3000–5000 token | 触达文案、实验方案的核心信息占比有限，需控制引用片段的token占用 |
| 上下文刷新周期 | 按日更新 | 品类数据更新频率为日/周，按日刷新可匹配最新的用户行为与实验数据 |
| 召回上下文条数 | 前3–5条 | 用户分群、触达节奏设计的核心维度集中，过多召回会额外占用token资源 |

## 容易做错的三处
- 出现Invalid JSON格式报错：现象为工具调用节点返回Bad control character相关的错误提示，原因是未对多源数据中的换行、特殊符号做预处理，拼接上下文时生成非法JSON结构。
- 上下文长度超限报错：现象为模型返回上下文超出限制的提示，原因是未根据品类数据特征调整`maxContext`参数，默认配置无法承载多源整合的分析文档。
- 工作流上下文不一致：现象为不同环节调用的用户分群数据存在差异，原因是未按数据更新周期配置上下文刷新，导致缓存数据未及时同步最新信息。

## 怎么确认配好了
- 查看上下文拼接日志，确认多源数据的特殊字符已完成转义，无非法JSON片段。
- 测试调用留存分析报告相关的上下文，确认模型可正常加载完整数据，无上下文超限报错。
- 对比不同工作流环节的用户分群数据，确认数据一致性符合业务预期。
- 检查`maxContext`、`quoteMaxToken`等参数的取值，确认匹配品类数据的实际token占用量。
