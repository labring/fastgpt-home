# 用户验收测试支持的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的典型参与主体为实施顾问、测试经理、客户业务代表。日常产出与使用的文档包括UAT用例、验收问题单、验收报告、签字确认单。数据来源涵盖需求规格文档、测试环境配置、客户业务样例、缺陷跟踪系统。数据更新节奏为每阶段或每版本一次，最耗时的工作环节为用例准备、问题复现归类、验收结论确认。出错后果包括验收延期、尾款延迟、需求范围争议。

## 这些特征在「上下文与 token」这一环带来什么约束
UAT用例、验收问题单等文档的核心内容为业务场景与验收标准，因此上下文召回需优先匹配具体业务场景，避免无关信息干扰。数据按阶段或版本更新，要求上下文缓存需同步刷新，确保召回内容为最新版本。单份文档的长度差异较大，从简短的问题单到完整的UAT用例集不等，需合理分配token以避免截断核心验收依据。最耗时的用例准备环节依赖精准的上下文召回，需减少重复整理文档的工作量。严重的出错后果要求上下文不能丢失关键的验收依据字段，token阈值需适配大模型的输入限制。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本适配：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配多份UAT文档的批量拼接，满足大模型对完整验收场景的理解 |
| `quoteMaxToken` | 1500 token | 限定单条引用的token消耗，平衡上下文完整性与模型输入限制 |
| 单次召回上限 | 前8条 | 覆盖单阶段验收的核心用例与问题，避免上下文过载 |
| 上下文刷新时机 | 每版本更新后触发 | 匹配数据每阶段/每版本的更新节奏，确保召回内容为最新验收依据 |
| 单条引用最大长度 | 1200–1800 字符 | 匹配UAT用例步骤、问题描述的常规长度，保留完整业务场景 |

## 容易做错的三处
- 配置`maxContext`超过当前大模型的输入上限后，上下文无法完整发送给大模型，表现为知识库预览显示存在上下文但模型输出未关联相关内容，对应配置引用上限过大导致上下文不发送的问题。
- 离线部署环境中未配置本地tokenizer，调用时尝试请求外网cl100k.tiktoken资源，触发网络连接报错，表现为curl请求返回资源未找到或超时。
- 未按阶段或版本更新上下文缓存，召回旧版本的UAT用例或缺陷记录，表现为问题复现归类时匹配到已关闭的旧条目，导致验收结论出现偏差。

## 怎么确认配好了
- 上传一份完整的UAT用例文档，检查上下文预览中是否包含用例步骤、预期结果等核心字段，确认召回内容匹配业务场景。
- 发起与验收场景相关的提问，查看模型输出是否关联到对应的验收问题单或缺陷记录，确认上下文被正确传递。
- 模拟离线部署环境，查看运行日志，确认tokenizer调用未请求外网资源，无相关报错信息。
- 调整`quoteMaxToken`为较小值，验证单条引用的内容是否会被截断，确认token分配符合预期。
