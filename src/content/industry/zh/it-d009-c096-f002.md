# 社区举报处理的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
社区举报处理的数据主要来自举报系统、涉诉内容详情、用户历史行为记录及官方审核规则，更新节奏为日级或实时。日常产出的文档包括举报工单、举报处理记录、用户申诉单、标准化用户通知模板，数据字段通常包含举报唯一标识、涉诉内容ID、举报发起用户ID、举报类型标签、处置状态及关联内容快照，无额外固定统计类字段。

## 这些特征在「上下文与 token」这一环带来什么约束
社区举报处理的数据特征会对上下文与token配置带来多重约束。举报工单与处理记录的实时更新属性，要求上下文需同步拉取最新处置状态，避免引用过期数据导致处置偏差。涉诉内容快照的长度跨度大，从短文本举报到长图文详情均有覆盖，需适配不同长度的上下文加载逻辑。单条举报数据关联多维度来源，需严格限制上下文token总量，防止超出模型处理上限。用户通知模板的复用性要求上下文需精准匹配当前举报场景的变量，避免冗余token消耗。在FastGPT v4.17.0中，这些约束会直接影响检索召回与上下文拼接的参数设置。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | `8000–12000 token` | 社区举报数据包含工单、涉诉内容、历史记录等多维度内容，总token消耗需适配模型窗口上限 |
| `quoteMaxToken` | `1500–2000 token` | 单条举报的核心证据片段长度通常在该区间，可精准覆盖关键审核规则与涉诉内容 |
| 单次检索召回条数 | 前3–5条 | 社区举报的有效关联数据集中在少量条目内，过多召回会增加不必要的token消耗 |
| 上下文同步频率 | 实时 | 举报处置状态更新实时性要求高，需保证上下文始终加载最新的工单与处理记录 |
| 知识库分块长度 | 4000–5000 token | 社区审核规则与举报工单的内容长度跨度较大，该分块区间可平衡召回精度与token占用 |
| 上下文历史保留时长 | 24小时 | 社区举报的历史数据通常按日归档，保留24小时可覆盖单次举报处置的全流程上下文 |

## 容易做错的三处
- 现象：配置`quoteMaxToken`为1500 token，但仍加载超出该上限的知识库内容。原因：未对检索召回的分块内容按`quoteMaxToken`做二次截断，直接将完整分块纳入上下文，导致引用token超出预设值。
- 现象：无法在举报处理工作流中清空上下文历史记录。原因：未在工作流节点中绑定触发清空的举报场景条件，或触发逻辑未关联到申诉提交、处置完成等特定举报状态。
- 现象：无法查看单次举报处理问答的token使用明细。原因：未开启FastGPT的token日志采集功能，或日志采集的配置未覆盖举报处理相关的问答请求。

## 怎么确认配好了
- 提交一条测试举报工单，触发问答请求，查看上下文加载的内容是否包含最新的举报处置状态与涉诉内容快照。
- 调整`quoteMaxToken`参数后，验证检索召回的内容长度是否符合预设的token上限要求。
- 开启token日志采集功能，核对单次问答的token消耗是否与配置的`maxContext`、`quoteMaxToken`参数匹配。
- 触发举报处置完成的工作流节点，验证上下文历史记录是否按配置的保留时长被自动清理或保留。
