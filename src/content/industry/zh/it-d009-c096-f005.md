# 社区举报处理的需求与设计文档起草：多轮对话与提示词
本文基于FastGPT v4.17.0版本编写。

## 这个品类的数据长什么样
社区举报处理的数据来源为举报系统、内容详情、用户历史记录与审核规则，更新节奏为日级或实时。日常产出的文档包含举报工单、处理记录、申诉单与用户通知模板，各文档字段包含举报ID、涉诉内容链接、用户历史违规记录、审核规则条目、处置结果等，无额外统一统计单位，数据体量随社区活跃程度波动。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
社区举报处理的数据特征对多轮对话与提示词配置带来多重约束。举报工单需关联举报系统、内容详情、用户历史记录等多源数据，多轮对话需支持逐步调取不同来源的信息，需固定上下文关联规则以避免信息错位。实时更新的审核规则与用户历史记录要求对话链路能实时拉取最新数据，避免使用过期规则。不同文档的字段差异要求提示词明确指定各文档的调用优先级与输出格式，防止字段混淆。处置结果需匹配用户通知模板的固定结构，提示词需约束输出字段的顺序与类型，确保生成的通知与工单字段对齐。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 匹配举报工单与内容详情的单条文本长度，避免截断关键违规证据 |
| 重叠长度 | 100–200 字符 | 确保跨块的违规描述不会被拆分丢失，维持上下文连贯性 |
| 单次搜索上限 | 前 3 条 | 限制返回的知识库条目数量，适配举报处理的单条工单审核场景 |
| 最大上下文长度 | 4000 token | 容纳多轮举报对话的历史记录与关联数据，避免上下文溢出 |
| `chatId` | 绑定举报工单ID | 确保每轮对话关联唯一工单，便于回溯处理记录 |
| `variables` | 传入当前举报ID与用户历史违规标记 | 动态加载对应工单的专属数据，提升审核准确性 |

## 容易做错的三处
- 现象：对话接口返回结果中未携带知识库关联ID。原因：未在`variables`中传入知识库绑定的举报工单ID，导致无法关联对应知识库条目。
- 现象：本地部署场景下，知识库中以URL存储的图片无法被模型输出。原因：提示词未明确要求提取并格式化图片URL，且未配置上下文加载图片链接的规则。
- 现象：对话生成的处置通知与预设模板格式不符。原因：未在提示词中指定输出字段的顺序与必填项，导致生成的内容与申诉单、通知模板不匹配。

## 怎么确认配好了
- 发起模拟举报工单对话，检查返回结果中是否携带绑定的工单ID，确认`chatId`配置生效。
- 上传包含图片URL的测试知识库，发起关联工单的对话，验证模型是否能正确提取并输出图片链接。
- 查看对话日志，确认每次搜索返回的知识库条目数量符合预设的单次搜索上限。
- 检查`messages`字段是否正确传递了历史举报对话记录，确认上下文加载逻辑正常。
