# 社区举报处理的需求与设计文档起草：工作流编排

## 这个品类的数据长什么样
社区举报处理的核心数据来源于举报系统、涉事内容详情、用户历史举报记录与审核规则，更新频率覆盖实时与日更两类。日常产出的标准化文档包括举报工单、处理记录、申诉单与用户通知模板，核心字段包含举报唯一标识、涉事内容ID、举报分类标签、处置结果、申诉状态与通知回执。数据按单独立流转，每个工单对应专属处理链路，无默认批量聚合逻辑。

## 这些特征在「工作流编排」这一环带来什么约束
实时与日更的更新节奏要求工作流启动与执行需匹配数据流转的时效性，避免延迟导致工单积压。按单处理的特性要求每个工作流实例绑定单个工单的唯一标识，防止不同工单的数据串扰。多类型文档与字段的存在，要求工作流节点间需稳定传递核心字段，保障分类、处置等环节的准确性。出错后果关联用户投诉与社区冲突，因此需配置失败重试与异常告警节点，降低处置失误的影响。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 触发节点 | 按举报工单创建事件触发 | 匹配数据实时更新的节奏，确保工作流在工单生成后立即启动 |
| 分类分支节点 | 按举报类型拆分执行分支 | 对应举报工单的分类标签字段，实现不同违规类型的差异化处理 |
| 上下文调用上限 | 前3条用户历史举报记录 | 基于用户历史记录的数据来源，避免上下文过载影响处理效率 |
| 超时阈值 | 600秒 | 匹配实时处理的更新要求，防止工作流因节点阻塞长时间停滞 |
| 举报内容截取 | 800-1200字符 | 匹配社区内容的常规审核长度，避免过长内容阻塞节点 |
| 变量绑定 | `variables`字段绑定工单核心字段 | 传递举报ID、涉事内容链接等关键信息，保障节点间数据流转的准确性 |

## 容易做错的三处
- 文本分类提取节点返回空值，原因是未将举报内容字段正确绑定至节点输入参数，导致节点无有效处理数据。
- 工作流执行后重复进入分类节点，原因是未在AI对话返回节点后配置分支跳转终止逻辑，导致流程循环触发。
- 工作流导入失败，原因是未匹配新版本的`nodeId`参数规则，旧版配置的节点ID与FastGPT v4.17.0系统不兼容。

## 怎么确认配好了
- 触发一条测试举报工单，查看工作流是否自动启动并进入对应分类分支。
- 进入节点日志页面，确认`variables`字段中绑定的工单核心字段已正确传递至下游知识库调用与AI对话节点。
- 模拟不同举报类型的输入，验证各分类分支是否执行对应逻辑，无分支跳转异常。
- 手动触发节点超时场景，确认失败处理节点是否正常触发并记录异常工单信息。
