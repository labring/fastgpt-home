# 社区贡献者治理的需求与设计文档起草：上下文与 token
本页面适配FastGPT v4.17.0版本。

## 这个品类的数据长什么样
本品类的数据围绕社区贡献者治理的人员与规则生成，日常文档包含贡献指南、行为准则、维护者名单、治理会议纪要四类核心文件。数据来自代码仓库提交记录、社区论坛互动数据、贡献统计报表、线下线上治理会议记录。更新频率为月度或季度，文档字段包含角色权限细则、贡献者晋升标准、治理决策流程等，无统一量化单位，仅按具体治理场景划分条目。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类数据来源分散，包含非结构化的会议纪要与论坛讨论内容，需限定上下文召回的范围，避免混入无关的代码提交日志。文档更新频率较低但内容具有时效性，需控制上下文缓存的留存时长，防止调用过时的治理规则。文档字段侧重角色与规则，上下文召回需优先匹配权限、晋升相关的关键词，聚焦核心治理内容。此外，治理场景出错后果严重，需限制单次调用的token消耗，避免因上下文过长导致调用失败引发治理争议。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 8000–12000 token | 覆盖社区治理类文档的平均总长度，适配通用大模型的上下文上限 |
| `quoteMaxToken` | 1500–2000 token | 限制单条召回文档片段的长度，确保治理规则的核心内容完整且不占用过多token |
| 上下文召回条数 | 前5–7条 | 匹配本品类常见的治理场景需求，避免冗余数据导致上下文过载 |
| 上下文缓存时长 | 7–30天 | 匹配月度或季度的文档更新频率，平衡规则时效性与缓存效率 |
| `maxContext` | 按社区文档库总token数的70%–80%标定 | 预留处理空间，避免因上下文过长触发调用失败 |
| 上下文召回相似度阈值 | ≥0.75 | 优先召回与当前治理问题强相关的规则文档，过滤无关的社区论坛闲聊内容 |

## 容易做错的三处
- 现象：调用时触发token超限报错，日志显示上下文总长度超出模型限制。原因：未根据社区治理文档的实际总长度调整`maxContext`配置，直接使用默认值导致上下文过载。
- 现象：返回的治理规则内容不完整，关键权限条款被截断。原因：设置的`quoteMaxToken`取值过小，提前截断了核心文档片段。
- 现象：调用后返回旧版的贡献者晋升规则，未同步更新的治理文档内容。原因：上下文缓存时长设置过长，未匹配月度或季度的文档更新节奏。

## 怎么确认配好了
- 上传全部社区治理文档，执行单次上下文召回测试，核对召回的文档条数与配置的召回条数一致。
- 查看调用日志，确认上下文总长度未超出预设的`maxContext`限制，无token超限报错。
- 等待文档更新后，触发上下文调用，核对返回内容为最新版的治理规则，确认缓存时长配置生效。
- 测试不同长度的治理问题提问，确认召回的文档片段长度符合`quoteMaxToken`的设置。
