# 缺陷管理与回归测试的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的数据主要来自缺陷管理系统、测试报告、代码提交记录与用户反馈。日常产出的文档包含缺陷单、回归清单、修复验证记录与缺陷统计报表。缺陷单包含缺陷ID、优先级、复现步骤、关联代码片段与报错日志；回归清单按版本梳理测试用例与关联缺陷；数据更新频率为每日或每版本发布周期。数据字段多为结构化标识与非结构化的步骤、日志内容，单条内容的长度差异较大。

## 这些特征在「上下文与 token」这一环带来什么约束
品类数据中非结构化的复现步骤、报错日志与代码片段占比高，单条内容的token消耗波动大。数据更新频率高，需在上下文内保留最新版本的缺陷状态与回归验证结果，避免引用过时信息。数据间存在强关联，如缺陷单关联对应测试用例与修复代码，上下文召回需精准匹配关联关系，否则会引入无关内容。同时单轮任务需处理多份文档，token总用量易超出模型限额，需严格控制上下文与召回内容的token上限。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配缺陷管理与回归测试的多文档上下文需求，平衡内容完整性与模型token限额 |
| `quoteMaxToken` | 1500–2000 token | 匹配品类中单条缺陷或测试用例的典型内容长度，避免单条召回内容溢出限额 |
| 最大上下文token数 | 按实测标定 | 适配部署环境的模型token上限与业务数据的实际规模 |
| 单次召回内容token上限 | 1000–1500 token | 控制单轮召回的非结构化日志与步骤的总token消耗 |
| 上下文刷新间隔 | 每日 | 匹配品类数据的更新频率，确保上下文包含最新缺陷与回归状态 |

## 容易做错的三处
- 配置`quoteMaxToken`小于单条缺陷文档的实际token长度，导致检索到符合相似度的切块但无法完整引用，出现召回内容被截断或丢弃的现象。原因是未匹配品类中单条文档的实际内容长度，错误使用通用知识库的切块参数。
- 未正确配置`maxContext`，导致上下文包含过多历史缺陷记录与回归验证日志，触发模型token溢出报错。原因是未按品类数据的更新频率调整上下文保留范围。
- 未配置上下文关联匹配规则，导致召回的测试用例与当前处理的缺陷无关联，出现无效内容占用token限额的现象。原因是未启用上下文与当前任务的关联过滤机制。

## 怎么确认配好了
- 检查App/Admin服务端的环境变量配置，确认`AIPROXY_API_ENDPOINT`（AI Proxy服务的根地址，例如 http://aiproxy:3000，不得附加 /v1 或 /chat/completions，不得为单模型地址）与`AIPROXY_API_TOKEN`（AI Proxy管理员Token，与AI Proxy服务端配置一致且不能为空，不得为应用API Key、模型供应商密钥等）已正确设置，且未在工作流全局变量、应用API请求头或普通模型管理页面配置，符合FastGPT v4.17.0及以上版本的要求。
- 触发一次缺陷文档起草任务，查看返回内容的token使用统计，确认`maxContext`与`quoteMaxToken`的实际生效范围。
- 模拟检索包含长日志的缺陷单，验证召回内容的token长度未超出`quoteMaxToken`的设置值。
- 等待一个更新周期后，确认上下文已按配置的刷新间隔更新了最新的缺陷状态与回归验证结果。
