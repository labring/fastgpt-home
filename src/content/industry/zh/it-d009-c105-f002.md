# 许可证合规与版权声明的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的数据主要来自代码仓库、依赖清单、许可证文本、贡献记录。日常产出的文档包含LICENSE文件、NOTICE文件、依赖许可证清单、版权声明。数据更新频率为每版本发布或每依赖变更时更新。文档结构包含纯文本许可证条款、结构化依赖列表、带归属信息的贡献记录等，不同文档的字段与长度差异显著，单批次处理的内容规模随项目依赖数量波动。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类的数据特征直接约束上下文与token的处理逻辑。首先，多来源的零散数据与波动的内容规模，导致单批次处理的token消耗量不稳定，容易超出模型上下文限制。其次，不同文档的格式差异，使得统一的token统计与分块策略难以适配所有场景，可能出现部分内容被截断或冗余token占用过多空间。最后，高频更新的数据需要频繁触发合规核对流程，增加了上下文管理与token计算的资源消耗，若未合理配置参数，易引发处理超时或溢出问题。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | `8192–16384 token` | 适配多数开源项目单批次合规处理的总token需求，FastGPT v4.17.0版本支持该区间配置 |
| `quoteMaxToken` | `2048 token per entry` | 单个依赖的许可证文本通常不超过该长度，避免单条数据占用过多上下文空间 |
| 上下文分块长度 | `1000–1500 字符` | 匹配许可证文本的自然段落长度，平衡token计算精度与分块处理效率 |
| 单次召回上限 | 前10条 | 多数合规核对仅需核心依赖的许可证数据，过多条目易超出上下文限制 |
| 最大响应token | `4096–8192 token` | 满足生成完整依赖许可证清单或版权声明的输出长度需求 |

## 容易做错的三处
- 现象：配置`maxContext`后仍出现上下文溢出报错，原因是未提前统计多依赖许可证文本的累加token量，导致实际处理内容超出设定的上下文上限。
- 现象：离线部署时出现`get tiktoken`报错，原因是未正确加载本地token计算依赖，无法准确统计上下文的token数量，引发流程中断。
- 现象：GPU显存利用率达标但上下文长度受限，原因是未将模型原生上下文窗口与`maxContext`配置对齐，仅调整显存利用率未限制实际处理的token上限。

## 怎么确认配好了
- 上传一份包含10个核心依赖的许可证清单，核对系统显示的上下文token统计值是否在配置的`maxContext`区间内。
- 启动离线部署的服务，检查token计算相关日志是否无报错，确认本地token依赖正常加载。
- 调整`maxContext`为较小值，触发上下文溢出提示，验证配置是否生效。
- 生成一份版权声明文档，核对输出内容的长度是否符合配置的最大响应token范围。
