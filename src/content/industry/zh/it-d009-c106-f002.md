# 语音标注与转写的需求与设计文档起草：上下文与 token

本文基于FastGPT v4.17.0版本编写，面向语音标注与转写场景下的需求与设计文档起草环节，聚焦上下文与token的配置与落地。

## 这个品类的数据长什么样
该品类的数据主要来源于音频文件、标注平台导出的标注记录、专有词表以及抽检样本。日常关联文档包含转写规范、音频任务清单、质检报告、说话人标注表。数据更新节奏按日或按单批次任务推进，单批次数据量随任务规模浮动。数据字段包含音频时长、说话人标识、转写文本片段、标注置信度、噪声区间标记等，无统一固定单位，需随具体任务配置调整。

## 这些特征在「上下文与 token」这一环带来什么约束
语音标注转写产生的结构化文本片段长度差异较大，单条长音频的完整转写结果可能超出单轮AI上下文上限，导致关键内容被截断。专有词表、抽检样本等辅助数据需随任务同步纳入上下文参考范围，增加了上下文总token消耗。按日或按批次更新的数据需要在每次任务启动时加载对应数据集，若未合理控制上下文token配额，会导致任务启动延迟或资源占用过高。说话人区分、噪声判断等环节的标注规则文档，需作为上下文参考，进一步提升了上下文的token占用需求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 语音标注转写的上下文需包含转写规范、音频清单、历史标注样本，该区间可覆盖多数单批次任务的文档与数据总量，避免内容截断 |
| `quoteMaxToken` | 2000–3000 token | 专有词表、抽检样本等引用数据需单独控制token消耗，避免占用主上下文配额，保障核心任务逻辑的正常运行 |
| 单条转写文本分片长度 | 按实测标定 | 单条长音频转写结果需合理分片，适配`maxContext`的配额设置，避免单条内容超出上下文上限 |
| 历史参考文档加载数量 | 前3条 | 历史质检报告可作为当前任务的参考标准，过多批次会增加上下文token消耗，过少则无法覆盖典型质检规则 |
| 上下文更新触发规则 | 按任务批次更新 | 数据按日或按批次更新，按批次触发可避免频繁加载数据导致的资源浪费 |

## 容易做错的三处
- 现象：任务运行时提示上下文长度超限，返回结果截断部分转写文本。原因：未根据单批次语音标注数据的总token量调整`maxContext`配置，导致超出AI模型的上下文承载上限。
- 现象：离线部署环境中出现Ai proxy报错，提示get tiktoken dial tcp lookup失败。原因：未配置本地tiktoken资源，或网络策略限制了对外部token计算服务的访问，导致上下文token统计失败。
- 现象：并发任务执行时出现资源抢占，部分任务响应超时。原因：未合理设置上下文加载的并发配额，导致多任务同时加载大量音频转写数据时，token统计与上下文匹配环节占用过多资源。

## 怎么确认配好了
- 查看任务配置页面的上下文相关参数，确认`maxContext`、`quoteMaxToken`等配置项的取值与当前任务的数据规模匹配。
- 提交小批量测试任务，检查转写结果是否完整，无截断情况，验证上下文配置是否适配当前数据量。
- 查看离线部署环境的运行日志，确认无tiktoken相关的网络报错，验证token统计功能正常运行。
- 模拟多任务并发提交，检查各任务的上下文加载与处理环节无异常，验证并发配置的适配性。
