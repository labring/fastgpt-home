# 账号封禁与申诉复核的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自风控系统、审核记录、用户行为日志、举报证据，更新频率为日级或实时。日常产出的文档包含封禁记录、申诉材料、复核意见、用户通知四类，其中封禁记录包含账号标识、违规触发规则、处置时间字段；申诉材料包含申诉人信息、举证内容、申诉诉求字段；复核意见包含复核结论、调整后的处置等级字段；用户通知包含通知对象、发送时间、通知内容字段。

## 这些特征在「上下文与 token」这一环带来什么约束
多源异构的数据来源要求上下文需整合不同系统的字段信息，避免单一数据源的信息缺失。实时或高频更新的数据要求上下文加载需控制总长度，防止因数据过载导致模型响应超时。不同类型的文档结构要求上下文需按业务优先级排序，优先加载违规证据与申诉举证内容。账号级的业务属性要求上下文需绑定账号标识进行过滤，避免召回无关账号的历史数据。严重的出错后果要求上下文需精准召回核心证据，防止因信息遗漏导致误封或违规账号回流。

## 配置怎么定

| 配置项               | 建议取法                | 这样取的依据 |
| ----------------------|-------------------------|------------------------------------------------------------------------------ |
| `maxContext`         | `12000–15000 token`     | 整合多源文档的总长度，匹配FastGPT v4.17.0的主流模型上下文上限 |
| `quoteMaxToken`      | `3000–4000 token`       | 优先保留违规证据、申诉理由的核心内容，避免冗余信息占用上下文空间 |
| 分块重叠长度         | `200–300 字符`          | 拆分封禁记录、申诉材料时避免割裂关键证据链，确保上下文的完整性 |
| 单次召回上限         | `前8条`                 | 匹配账号级历史记录的常规数量，避免无关数据干扰模型判断 |
| 上下文排序规则       | 按证据优先级排序        | 优先加载违规触发日志、申诉举证材料，再加载复核意见与用户通知 |

## 容易做错的三处
- 现象：搜索结果未关联当前账号的历史封禁记录，原因是未将账号ID作为上下文过滤条件绑定到搜索请求，导致搜索范围覆盖全量数据。
- 现象：模型返回报错提示上下文长度超限，原因是未限制`maxContext`的取值，导致加载的上下文总长度超出模型支持范围。
- 现象：申诉复核时召回的证据与当前账号无关，原因是未按账号标识过滤召回的历史记录，导致混淆不同账号的业务数据。

## 怎么确认配好了
- 导入单条账号封禁与申诉的完整文档，查看系统召回的上下文内容是否包含该账号的所有相关记录。
- 触发搜索查询，确认返回的结果仅关联当前账号的历史数据，无无关账号的信息。
- 调整`maxContext`参数，观察系统加载上下文的耗时变化，确认取值符合业务响应要求。
- 查看模型生成的复核建议，确认引用的证据均来自配置的上下文范围，无无关内容混入。
