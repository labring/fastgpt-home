# 质保期缺陷响应的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据主要来自客户提交的质保工单、系统运行日志、项目合同质保条款、软件版本更新记录。日常产出的文档包括质保工单、缺陷确认单、修复记录、客户确认单。数据更新节奏为每日或随每单业务推进更新，文档字段包含工单编号、缺陷详情、责任边界判定结果、修复执行记录、客户确认状态等，无统一固定的单位类强制字段，仅随业务场景匹配对应标识。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的多源数据特征会对上下文与token配置带来多重约束。不同来源的质保相关数据长度差异显著，短文本的工单描述与长文本的运行日志、合同条款需适配不同的上下文截取规则。高频更新的业务数据要求上下文实时关联最新的工单、修复记录，避免使用过期的质保条款或状态数据。多字段的文档结构要求检索时精准匹配责任边界、客户确认状态等核心字段，需限制无关内容的token占用，防止无效数据挤占有效上下文配额。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | `8000–12000 token` | 适配多源质保数据的整合需求，平衡上下文完整性与token消耗上限 |
| `quoteMaxToken` | `1500–2000 token/单条引用` | 控制单条质保文档的token占用，避免单条数据过度挤占上下文配额 |
| 单次搜索上限 | 前8条 | 匹配该品类核心文档的数量规模，避免过多低相关数据消耗token |
| 上下文实时刷新 | 开启 | 适配高频更新的质保工单、修复记录，确保检索使用最新业务数据 |
| 问题优化 | 按实测标定 | 该品类的需求描述多含专业术语，需通过实测调整优化策略适配检索精度 |

## 容易做错的三处
- 现象：检索时单次上下文token消耗接近或超过设定上限，导致查询超时或返回不完整内容。原因：未合理限制`maxContext`的取值，将多源质保数据无节制纳入上下文。
- 现象：工作流中调用工具时，无法获取全局变量中的token参数，导致工具调用失败。原因：未在上下文配置中开启全局变量透传开关，未将全局token纳入上下文传递范围。
- 现象：调用模型查询关联数据时，消耗的token和实际API返回的token不一致。原因：未精准配置上下文的截取规则，导致无效内容被纳入token统计。

## 怎么确认配好了
- 查看FastGPT v4.17.0的检索日志，核对单次上下文的token消耗是否在设定的`maxContext`范围内，调整取值直至消耗符合预期。
- 模拟提交质保工单查询，检查返回的上下文是否包含最新的修复记录与客户确认状态，验证实时刷新配置生效。
- 调用工具测试，确认全局变量中的token参数可被正常传递，验证上下文透传配置正确。
- 统计检索返回的文档数量，确认符合单次搜索上限的设定，调整匹配规则直至返回内容贴合业务需求。
