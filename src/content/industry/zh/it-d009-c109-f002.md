# 身份账号与权限管理的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的数据来自IAM系统、HR系统、业务系统日志与审批系统，更新频率为每日或随人事变动触发。日常产出的文档包括账号申请单、权限矩阵、离职回收单与审计报告，文档字段包含账号ID、员工姓名、所属部门、权限范围、生效与失效时间等，单份文档的条目数跨度较大，数据以结构化文本为主，部分包含原始业务日志的非格式化内容。

## 这些特征在「上下文与 token」这一环带来什么约束
多源数据的更新节奏差异要求上下文需匹配实时同步的节点，例如人事变动触发的权限调整需及时刷新上下文，避免使用过期数据。文档结构的多样性要求上下文召回需区分不同文档类型的字段优先级，例如权限矩阵的核心字段需优先召回。数据字段的敏感性要求上下文的token占用需严格限制，避免越权信息被意外召回。同时，原始日志中的非格式化字符可能破坏token拆分逻辑，需额外处理。

## 配置怎么定
本配置基于FastGPT v4.17.0版本的界面与参数逻辑。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 匹配IAM类文档的字段数量与单轮会话的信息承载量，适配多份权限文档的拼接需求 |
| `quoteMaxToken` | 1500–2000 token | 适配权限矩阵、审计报告等单文档的核心内容长度，避免单条引用超出token限制 |
| 上下文刷新间隔 | 每12小时 | 匹配数据日更新或人事变动的同步节奏，确保会话使用最新的权限数据 |
| 单次召回上下文条数 | 前6条 | 控制整体token占用，平衡信息完整性与会话性能 |
| 非法字符过滤 | 启用 | 处理原始业务日志中的换行符等特殊字符，避免token拆分时生成非法内容 |

## 容易做错的三处
- 会话中出现Invalid JSON报错，且日志显示包含未转义的换行符。原因：未启用非法字符过滤配置，导致从IAM原始日志中召回的内容破坏了token拆分的JSON结构。
- 多轮会话后返回的权限信息与最新人事变动不符。原因：未配置上下文刷新间隔，沿用初始导入的旧数据，未同步HR系统的更新内容。
- 会话召回了已离职员工的权限数据。原因：未限制单次召回上下文条数，导致召回了超出当前会话关联范围的历史账号数据。

## 怎么确认配好了
- 导入一份包含在职与离职员工权限的文档，发起关联部门的权限查询，确认召回结果仅包含在职员工的有效权限条目。
- 模拟一次人事变动操作，等待设定的上下文刷新间隔后发起查询，确认返回的权限信息已更新为最新状态。
- 发起包含多份IAM文档的复杂查询，检查会话的token占用未超过`maxContext`的配置上限。
- 查看系统报错日志，确认未出现因非法字符导致的Invalid JSON报错。
