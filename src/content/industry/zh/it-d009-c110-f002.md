# 运维外包驻场服务的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据通常来自客户ITSM系统、监控平台、资产清单与值班记录，日常产出驻场日报、服务台工单、巡检报告、SLA月报四类文档。数据更新节奏以日度和月度为主，核心字段包含工单编号、巡检项、SLA达标率、驻场人员值班时段等，无统一强制格式，需贴合客户IT部门的交付要求。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据来源分散且格式不统一，不同系统导出的工单、巡检报告等文档字段差异较大，上下文拼接时需额外做字段对齐，否则会浪费token配额。日度更新的现场工单、驻场日报需要高频加载，token调用频率需适配高频业务场景，避免触发平台调用限制。文档长度跨度大，短至百字的巡检记录与长至数千字的SLA月报并存，上下文窗口需灵活适配不同长度的输入内容。同时，因信息缺失会直接导致客户扣罚，需避免关键业务字段被token截断。

## 配置怎么定
本配置适用于FastGPT v4.17.0版本。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 适配驻场日报、服务工单、SLA月报等混合文档的输入长度，避免核心业务字段被截断 |
| `quoteMaxToken` | 1500–2000 token | 限制单条引用文档的token占用量，防止单条长文档占用过多上下文配额 |
| 上下文召回条数 | 前3–5条 | 匹配运维外包驻场服务的日常业务数据规模，减少冗余token消耗 |
| 引用相似度阈值 | 0.75–0.85 | 过滤低相关的巡检记录或工单，精准匹配需求与设计文档的起草需求 |
| 单次调用token上限 | 10000 token | 适配日度高频的文档起草任务，避免单次调用超出平台配额限制 |

## 容易做错的三处
- 配置`maxContext`后仍出现上下文截断报错：原因是未同步调整`quoteMaxToken`参数，单条引用文档占用的token超出了全局上下文的剩余配额，导致关键业务字段被截断。
- 上下文召回结果条数与配置不符：原因是未设置合理的引用相似度阈值，低相关的巡检记录被误召回，占用了召回配额，导致核心工单数据未被纳入上下文。
- 调用MCP工具时无法传递全局变量token：原因是未在工作流中配置上下文变量映射，未将全局token变量绑定到MCP工具的输入参数中，导致工具无法获取所需的认证信息。

## 怎么确认配好了
- 导入一份典型的驻场日报、服务工单和SLA月报，测试上下文拼接效果，查看是否包含核心业务字段且无明显截断。
- 发起一次需求与设计文档起草的模拟调用，核对返回的上下文内容是否与配置的召回条数、相似度阈值匹配。
- 查看平台的token消耗日志，确认单次调用的token用量未超出预设的单次调用上限。
- 配置MCP工具的输入参数，绑定全局变量token，发起测试调用，确认工具可正常获取并使用该变量。
