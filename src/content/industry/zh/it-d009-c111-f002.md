# 配置管理与CMDB维护的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据来自CMDB、云资源清单、自动发现工具与采购台账，更新频率为日度或周度。日常产出的文档包含配置项清单、服务组件关系拓扑、变更记录与资产盘点表，核心字段包括配置项唯一标识、资产分类、上下游依赖关系、最后更新时间与责任人，单位均为标准IT运维字段，无自定义非标准单位。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据多源且更新节奏差异明显，上下文召回需优先匹配最新的日度更新数据，避免引入过期的配置项信息。服务组件的依赖关系是核心内容，token分配需优先保留上下游关联的拓扑字段，防止截断关键链路信息。结构化文档占比高，上下文召回需聚焦配置项ID、依赖关系等核心字段，减少非必要文本的token占用。当配置项总量较大时，需限制上下文召回的总token量，避免超出模型支持上限。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 前 15–25 条关联数据 | 适配CMDB的配置项数量规模，避免上下文token超出模型限制 |
| `quoteMaxToken` | 6000–10000 token | 匹配该品类结构化文档的平均token长度，覆盖核心配置与依赖信息 |
| 上下文时间过滤阈值 | 7 天内 | 匹配该品类日度/周度的更新频率，过滤过期的配置项数据 |
| 召回字段范围 | 仅包含配置项ID、资产类型、依赖关系 | 减少非必要文本的token占用，聚焦核心业务字段 |
| 单次搜索关联上限 | 前 3 层拓扑关系 | 避免过度召回冗余的依赖链路，控制总token消耗 |

## 容易做错的三处
- 现象：上下文召回的token消耗远超预期，界面显示单次调用token超出模型上限。原因：未限制`maxContext`的召回条数，将全量CMDB数据纳入上下文。
- 现象：搜索结果无法结合配置项的依赖关系，返回的内容与当前配置场景无关。原因：未限定召回字段范围，召回了大量非核心的冗余文本。
- 现象：私有化部署后访问应用时自定义上下文路径未生效，无法通过指定路径访问。原因：未在部署配置中正确设置上下文路径参数，导致路由匹配失败。

## 怎么确认配好了
- 调用测试脚本生成需求文档，查看返回内容中是否包含当前配置项的依赖关系与最新更新时间，确认核心字段被正确召回。
- 查看token消耗统计，确认单次调用的token值处于预设的`quoteMaxToken`范围内，无异常溢出。
- 检查部署配置中的上下文路径参数，验证指定路径可以正常访问应用，确认路由配置生效。
- 模拟过期数据场景，确认超过设定时间的配置项数据未被纳入上下文，验证时间过滤规则生效。
