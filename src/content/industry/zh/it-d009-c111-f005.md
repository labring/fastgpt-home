# 配置管理与CMDB维护的需求与设计文档起草：多轮对话与提示词

本文适配FastGPT v4.17.0版本。

## 这个品类的数据长什么样
这个品类的核心数据来自CMDB、云资源清单、自动发现工具及采购台账，更新频率为日或周。日常产出的文档包含配置项清单、服务组件关系拓扑、变更记录与资产盘点表，文档字段包含配置项唯一标识、依赖关系、变更时间、采购批次等，无统一固定单位，需按具体资产类型匹配。核心使用主体为运维资产管理员、SRE与ITSM平台管理员，日常最耗时的工作为配置项采集、关系核对与变更后数据更新，数据偏差会直接影响故障定位与资产账实一致性。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
多源数据来源要求多轮对话需支持跨数据源的字段匹配，提示词需明确指定配置项ID、依赖关系等专属字段。日/周级别的更新频率要求对话上下文需同步最新的CMDB变更记录，避免使用过期数据。文档结构的多样性要求提示词需适配配置项清单、拓扑图等不同格式的输入，拆分长文本以适配模型上下文。最耗时的采集与核对环节要求多轮对话可辅助提取关键配置项，减少人工重复操作。数据偏差的严重后果要求对话输出需附带校验逻辑，确保配置项与依赖关系的准确性。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 固定会话ID，关联当前CMDB变更上下文 | 保持多轮对话的上下文一致性，绑定资产变更的历史记录 |
| `messages` | 按CMDB文档结构拆分的多轮历史，单轮不超过800字符 | 适配CMDB文档的字段长度，避免模型上下文溢出 |
| `variables` | 传入配置项ID、变更时间范围，共2-3个变量 | 缩小对话检索范围，精准匹配CMDB的核心数据字段 |
| 单次搜索上限 | 前6条匹配结果 | 聚焦核心配置项与依赖关系，避免冗余信息干扰对话逻辑 |
| 最大上下文 | 1200-1500 token | 覆盖CMDB清单、拓扑图的核心字段，不超出模型处理上限 |

## 容易做错的三处
- 现象：工作流执行至一半终止，仅返回单次AI回复结果。原因：未配置`chatId`的持久化上下文，多轮对话未保留CMDB变更的中间配置项状态。
- 现象：对话超时无响应。原因：未限制`messages`的单轮输入长度，传入过长的CMDB拓扑文档导致模型处理超时。
- 现象：插件仅触发一次，无法继续多轮提示词交互。原因：未开启`variables`的动态更新配置，未绑定CMDB的实时变更字段。

## 怎么确认配好了
- 传入测试用的配置项ID，检查`variables`是否正确加载对应的CMDB数据字段。
- 模拟多轮对话，查看`chatId`是否保持一致，上下文是否保留前一轮的配置项核对结果。
- 提交包含CMDB变更记录的长文本，检查`messages`的拆分逻辑是否符合预设长度限制。
- 触发插件调用，确认可以连续发起多轮提示词请求，无单次触发限制。
