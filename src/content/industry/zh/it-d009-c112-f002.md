# 问题管理与根因分析的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
本品类的数据围绕故障后的根因分析与问题闭环展开，日常文档包括RCA报告、问题单、复盘纪要、整改跟踪表。数据来源为故障时间线、系统日志、监控指标、代码提交记录，更新频率为每次重大故障或每月一次。数据字段包含故障发生时间、根因描述、整改措施、跟踪状态等，无统一固定单位，随文档类型灵活调整，单次故障相关数据通常覆盖数小时至数天的日志与记录。

## 这些特征在「上下文与 token」这一环带来什么约束
本品类的数据特征对上下文与token处理环节带来多重约束。数据来源分散且单次体量随故障规模变化，需严格控制上下文加载的总token数，避免超出模型处理上限。更新频率非实时，上下文无需频繁刷新，可按故障周期或文档更新触发同步。日常文档包含结构化与半结构化内容，长文档如完整故障时间线需要合理拆分token，同时保留关键关联信息。根因分析依赖跨源数据关联，上下文需覆盖相关日志、监控与代码记录，需明确召回范围以避免无关信息干扰。

## 配置怎么定
在FastGPT v4.17.0版本中，可通过以下配置项调整上下文与token处理逻辑：

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | `8000–12000 token` | 本品类单次分析需覆盖故障时间线、日志、监控等多源数据，该取值可容纳典型故障的关键关联信息，同时适配多数开源模型的上下文上限 |
| `quoteMaxToken` | `1500–2000 字符` | 日常文档如RCA报告、复盘纪要的单段关键内容通常在该范围内，可保留完整语义且避免过度拆分 |
| 最大上下文召回条数 | 前6条 | 根因分析需关联关键证据，过多召回会引入无关数据，6条可覆盖主要故障相关的日志与监控记录 |
| 完整段落保留配置 | 按文档块标记保留 | 部分关键内容如故障时间线的连续记录不宜拆分，该配置可避免关键词拆分破坏语义完整性 |
| 上下文刷新触发条件 | 按故障闭环完成更新 | 本品类数据更新频率为每次重大故障或每月一次，按故障节点更新可保证上下文时效性 |

## 容易做错的三处
- 现象：对话无法保留连续故障分析的上下文，后续提问无法关联之前的根因假设。原因：未正确配置`maxContext`参数，或召回条数设置过少，未加载关键历史数据。
- 现象：关键段落如完整故障时间线被拆分为多个token块，导致语义断裂。原因：未开启完整段落保留配置，系统自动拆分了不宜拆分的长文本。
- 现象：尝试配置`maxContext`为2000 token后，无法加载足够的故障日志数据。原因：未结合本品类的数据体量调整参数，2000 token不足以覆盖典型故障的多源关联信息，且未在对应界面正确修改配置项。

## 怎么确认配好了
- 导入一份典型的RCA报告与关联故障日志，检查系统加载的上下文内容是否包含报告中的根因描述与日志关键片段。
- 尝试发起连续对话，提问包含故障时间、根因假设等关联内容，确认后续提问可正确关联历史上下文。
- 查看系统返回的token使用统计，确认实际使用的token数未超出配置的`maxContext`上限，且未出现不必要的长文本拆分。
- 触发一次模拟故障更新，确认上下文内容按配置的触发条件完成刷新。
