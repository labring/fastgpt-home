# 需求分析与PRD管理的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
通常该品类的核心数据来自客户访谈记录、工单系统、竞品公开页面与埋点看板，日常产出需求调研纪要、PRD文档、用户故事清单、需求变更单四类文件。数据更新频率多为每周或每版本迭代一次，文档通常包含业务目标、验收口径、功能边界、变更记录等字段，无统一强制单位，字段内容随需求阶段动态调整。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的异构多源数据、分阶段更新频率与细分字段特征，会对上下文与token配置带来多重约束。多来源的访谈、工单、埋点数据格式差异较大，需统一上下文召回规则以避免无效token消耗；周或每版本的更新节奏要求上下文窗口限定在近期迭代周期内，防止调用过期需求内容；文档包含业务目标、验收口径等细分字段，需精准匹配对应片段，避免无关内容占用token配额；需求变更的动态性要求上下文可灵活调整召回范围，防止过时变更记录干扰分析。

## 配置怎么定
本配置基于FastGPT v4.17.0版本
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文窗口 | 8000–12000 token，按实测标定 | 适配PRD文档多字段、多来源的上下文内容，避免单次调用token超限 |
| 单段上下文token上限 | 1000–1500 token | 拆分需求文档为合理片段，确保单段内容完整覆盖单个需求模块 |
| 上下文召回条数 | 前3–5条 | 匹配需求分析的高频关联内容，避免过多无关片段占用资源 |
| 上下文时间范围 | 近1–2个版本周期 | 适配周/每版本的更新频率，过滤过期的需求变更记录 |
| `maxContext` | 与最大上下文窗口保持一致 | 遵循平台原生参数规则，确保配置生效 |
| `quoteMaxToken` | 1200 token | 限制单条召回上下文的token占用，平衡召回精度与资源消耗 |

## 容易做错的三处
- 报错显示Reached the max retries p，原因是上下文窗口配置过小，多次召回仍无法覆盖完整需求分析所需的内容，触发重试上限。
- 召回的上下文包含过期的需求变更单，原因是未限定上下文的时间范围，召回了超过版本周期的旧数据，干扰当前需求判断。
- 长PRD文档无法正常拆分，原因是未配置单段上下文token上限，导致超出平台token限制的片段无法被处理。

## 怎么确认配好了
- 上传一份完整的PRD文档，查看上下文召回结果中是否包含近期的需求变更记录，验证时间范围配置生效。
- 查看控制台日志，确认单次调用的token消耗未超过配置的最大上下文窗口，验证token配额设置合理。
- 测试多轮需求对话，查看是否能正确关联之前的需求调研纪要内容，验证上下文召回逻辑生效。
- 检查报错日志，确认未出现Reached the max retries相关提示，验证上下文配置满足需求分析的内容覆盖需求。
