# 需求分析与PRD管理的需求与设计文档起草：多轮对话与提示词

## 这个品类的数据长什么样
该品类的数据主要来自客户访谈记录、内部工单系统、竞品公开需求页面、产品埋点看板。日常产出的文档包括需求调研纪要、正式PRD文档、用户故事清单、需求变更单，数据更新频率为每周或每个版本迭代周期一次。文档结构通常包含需求编号、业务目标、验收口径、关联业务场景、变更版本标识等字段，通常无统一强制格式，需匹配团队内部的研发流程规范。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源的多样性要求多轮对话需适配口语化访谈记录、结构化工单内容等不同输入格式，避免提示词仅适配单一文本类型。高频更新的需求变更单会带来上下文膨胀问题，需限制对话上下文的有效范围。非统一的文档结构要求提示词支持自定义字段的提取与校验，无法依赖固定模板。同时，需求边界确认的高耗时场景，需要多轮对话逐步引导用户补充未明确的业务规则，避免单次输出遗漏关键信息。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文长度 | 8000–12000 字符 | 适配单篇PRD文档的常规长度，覆盖最近3次的需求变更与核心访谈内容，适配FastGPT v4.17.0版本的上下文处理上限 |
| 对话记录保存时长 | 30 天 | 匹配需求变更的常规迭代周期，保留完整的需求沟通轨迹，便于后续回溯验收依据 |
| 提示词变量 | 使用`variables`传入当前项目的PRD标识 | 快速关联对话对应的专属需求素材，避免跨项目上下文混淆，提升需求分析的精准度 |
| 知识库召回上限 | 前 3 条 | 需求分析的核心参考内容通常为少量核心访谈纪要与历史PRD，过多召回会干扰边界条件的确认 |
| 项目专属`chatId` | 绑定对应产品的唯一`chatId` | 隔离不同产品的需求对话上下文，防止跨项目的需求信息互相干扰 |

## 容易做错的三处
- 现象：跨项目的需求对话内容互相混入，或对话记录提前被清除，原因：未配置专属`chatId`隔离项目上下文，或未正确设置对话记录保存时长。
- 现象：召回的知识库内容包含非授权的团队素材，原因：未针对PRD文档配置专属的知识库权限组，导致对话可调用全量知识库内容。
- 现象：长文本需求分析任务报错「The value of "offset" is out of range」，原因：未限制单次对话的`messages`数组长度，导致上下文溢出触发偏移量校验错误。

## 怎么确认配好了
- 查看对话配置页面，确认最大上下文长度的取值符合团队当前PRD文档的平均长度。
- 测试传入`variables`参数，验证对话可自动关联对应项目的PRD素材，无无关内容混入。
- 发起包含多轮需求变更的对话，检查上下文仅保留有效迭代内容，无冗余历史信息干扰。
- 触发包含长文本PRD的分析任务，确认无偏移量相关的报错日志输出。
