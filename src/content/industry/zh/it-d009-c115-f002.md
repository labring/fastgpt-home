# 项目实施计划管理的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
该品类的数据通常来自项目合同、工作分解结构（WBS）、客户确认的日程安排及企业项目管理系统。日常产出的文档包含项目整体计划、里程碑节点清单、周度进度周报、风险与问题跟踪清单。数据更新频率多为每周一次或按单个里程碑节点触发，核心字段包括任务拆解项、责任人分配、排期节点、风险等级与应对措施，无固定统一的标准化格式，会随项目阶段动态调整。

## 这些特征在「上下文与 token」这一环带来什么约束
该品类的数据分散且格式不统一，跨来源的信息需要完整上下文关联才能准确还原项目全貌，对上下文召回的完整性提出要求。数据按周或里程碑更新，增量更新的内容需要被纳入上下文范围，避免遗漏最新的进度调整与风险记录。核心文档包含多类项目相关条目，单条文档的token占用量较高，若未合理限制上下文与引用token上限，易触发模型输出截断或调用超时。同时，项目排期与任务拆解依赖前后关联信息，上下文截断会导致排期逻辑断裂，影响需求与设计文档的准确性。

## 配置怎么定
本文基于FastGPT v4.17.0版本的配置逻辑编写。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–10000 token | 覆盖项目计划、周报、风险清单等多类核心文档的关联信息，避免关键排期与任务内容被截断 |
| `quoteMaxToken` | 单条引用不超过1200 token，总引用不超过3000 token | 项目类文档单条内容较长，限制单条与总引用长度，避免上下文过载 |
| 最大响应tokens | 2000–2500 token | 需求与设计文档起草需要输出完整的任务拆解、排期说明，足够的响应长度覆盖完整文档内容 |
| 上下文更新触发时机 | 按周或单个里程碑节点完成后触发 | 匹配该品类数据的常规更新节奏，确保上下文包含最新的进度与风险记录 |
| 相似度匹配阈值 | 0.75–0.85 | 过滤低关联的非项目核心文档，避免无关信息干扰需求文档的起草逻辑 |

## 容易做错的三处
- 生成的需求文档中部分项目排期逻辑断裂，上下文召回的历史任务信息不完整。原因是`maxContext`取值过低，截断了前序里程碑的排期关联信息，导致模型无法还原完整的项目进度脉络。
- 生成的文档输出被中途截断，或部分图片引用地址无法正常展示。原因是`quoteMaxToken`或最大响应tokens取值过高，导致上下文占用过多模型token配额，或资源路径信息被截断。
- 模型调用失败，提示无法连接指定模型接口。原因是未正确配置`ai proxy api`的地址与密钥，或未在环境变量中正确设置模型调用参数。

## 怎么确认配好了
- 导入该品类的典型项目文档，包括项目计划、周报与风险清单，测试生成需求与设计文档，检查核心内容是否完整覆盖。
- 查看模型调用日志，确认上下文召回的文档总长度未超出`maxContext`的预设取值，单条引用长度符合`quoteMaxToken`的限制。
- 调整上下文更新触发时机，对比更新前后生成的文档内容，确认最新的项目进度与风险记录已被纳入上下文。
- 测试生成包含图片引用的文档，检查图片地址是否完整未被截断，确认知识库资源的引用逻辑符合配置要求。
