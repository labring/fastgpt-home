# 项目文档移交归档的需求与设计文档起草：上下文与 token

## 这个品类的数据长什么样
通常，项目文档移交归档的数据来自项目全周期产出的竣工文档、配置手册、培训记录、验收证书，以及配套的配置清单、会议纪要、测试报告。数据更新节奏随项目阶段或整体项目结束触发，单次更新覆盖单项目全量归档文档。文档以单项目为单位聚合，包含文档编号、版本号、签署人、生成时间等结构化字段，部分文档附带二进制附件。数据主体关联项目经理、实施顾问与客户档案管理员的日常操作，无统一固定的单条数据单位，按项目维度归集。

## 这些特征在「上下文与 token」这一环带来什么约束
项目文档移交归档的数据以单项目为归集单位，且更新节奏随项目阶段变动，要求上下文关联范围严格限定在当前项目的文档集合内。文档包含二进制附件与结构化字段，会增加token消耗，需限制单轮调用的token总量。部分文档的签署人、版本号等字段需精准匹配，若上下文混入其他项目的文档，会引发版本一致性核对错误。归档文档的完整性检查依赖全量关联数据，若token配额不足导致截断，会遗漏关键校验项。另外，跨项目的文档移交操作需隔离上下文，避免数据污染。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文窗口 | 按单项目归档文档总token数的80%标定 | 避免单次调用超出系统token上限，适配单项目文档的归集规模 |
| `maxContext` | 12000–15000 token | 覆盖单项目核心归档文档的token消耗，预留10%的交互余量 |
| 引用最大token数 | 单文档最大token数的90% | 确保单文档完整纳入上下文，避免截断导致的完整性检查失败 |
| `quoteMaxToken` | 3000–4000 token | 匹配竣工文档、验收证书等核心归档文件的平均token长度 |
| 单次召回上限 | 前8条匹配文档 | 控制token消耗，同时覆盖单项目的主要归档文档类型 |

## 容易做错的三处
- 现象：调用MCP工具时模型上下文被强制打断，交互中断。原因：未按项目维度隔离上下文，跨项目的文档数据被意外纳入当前调用的上下文范围，触发系统上下文重置机制。
- 现象：上传的归档文件路径附带额外token参数，无法通过HTTP请求直接传递给后端处理。原因：FastGPT生成的文件相对路径未正确剥离内置token校验参数，导致路径携带冗余信息。
- 现象：AI回复出现不符合格式要求的JSON内容，或上下文出现其他项目的文档数据。原因：未配置项目维度的上下文隔离规则，导致多项目的归档文档被混合纳入上下文，引发数据污染与格式异常。

## 怎么确认配好了
- 上传单项目的核心归档文档，触发上下文关联测试，检查召回的文档均属于当前项目范围。
- 调用MCP工具执行文档完整性检查，观察上下文未混入其他项目的文档数据，无强制中断现象。
- 上传附带二进制附件的归档文档，确认文件路径未携带额外token参数，可正常传递至后端处理。
- 升级至FastGPT v4.17.0版本后，验证上下文配置项可正常保存并生效，无启动报错。
