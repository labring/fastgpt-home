# 钢材轧制与精整的供应商与过程质量审核：引用来源与溯源

## 这个品类的数据长什么样
本品类主体为热轧、冷轧、型钢、钢管生产企业，日常文档涵盖轧制计划、加热制度、轧制规程、板形厚度记录、表面质量报告、质保书。数据来源包括板坯/钢坯批次信息、加热炉参数、轧机自动控制系统、在线测厚测宽设备、表面检测装置、MES系统，更新频率为每卷或每支钢产品的生产节点实时更新。数据字段包含批次编号、厚度公差（mm）、表面缺陷等级、加热温度（℃）、轧制速度等，单卷数据关联上游板坯与下游质检记录。

## 这些特征在「引用来源与溯源」这一环带来什么约束
本品类的数据特征对引用溯源环节带来三项核心约束。其一，实时且按卷/支更新的生产数据，要求溯源必须精确到单个钢卷或钢支的批次编号，无法使用模糊的时间段匹配。其二，多源异构的数据来源，包括轧机自控系统、在线检测设备、MES系统，要求引用环节需关联不同系统的字段，确保返回的原始数据对应同一生产节点。其三，文档类型多样且单卷数据量较大，要求分块与引用配置需适配轧制规程、质保书等不同文档的结构与长度，避免拆分或引用时丢失关键信息。

## 配置怎么定
本配置基于FastGPT v4.17.0版本，针对钢材轧制与精整场景的溯源需求调整如下：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `quoteMaxToken` | 800–1200 token | 单卷的质量记录、轧制规程等文档长度较长，需保留足够的原始引用文本 |
| `responseData` | 开启批次关联字段 | 需关联板坯批次、轧机参数等溯源数据，确保引用内容与生产批次一一对应 |
| `detail` | 开启完整引用 | 需完整展示板形厚度、表面检测等原始记录，确保审核人员可获取全部关键信息 |
| 分块长度 | 1000–1500 字符 | 适配轧制计划、质保书等文档的单段内容长度，避免拆分时破坏数据关联性 |
| 单次搜索上限 | 前6条 | 单卷钢产品关联的上游板坯、下游质检记录数量通常不超过6组，覆盖全部关联数据 |
| 重排 | 按生产时序排序 | 溯源结果需按生产节点顺序展示，确保审核人员可清晰追踪生产流程 |

## 容易做错的三处
- 现象：调用后返回内容仅包含引用片段，无整合后的自然语言回答。原因：`responseData`配置为仅返回原始数据，未启用自然语言生成逻辑。
- 现象：无法单独控制部分文档的引用展示权限，所有文件的查看原文按钮状态一致。原因：未针对轧制规程、质保书等不同文档类型分别配置引用可见度规则。
- 现象：知识库拆分后，部分质保书文件未生成问答对，直接写入原文。原因：分块长度未适配质保书的长文本结构，导致拆分时触发异常逻辑。

## 怎么确认配好了
- 上传单卷钢产品的轧制计划与质保书，发起“该批次的质量情况”查询，核对返回结果包含对应卷号的原始数据片段。
- 检查`quoteMaxToken`的配置取值，确认返回的引用文本长度符合预期。
- 验证不同文档类型的引用可见度，确认可单独控制部分文件的查看原文权限。
- 查看知识库拆分日志，确认所有轧制类文档均生成了正确的问答对。
