# 钢铁冶炼与连铸的供应商与过程质量审核：向量模型与索引

## 这个品类的数据长什么样
这个品类的数据来自铁水与废钢采集系统、L2过程控制终端、化验室报告、生产执行系统（MES）、能源介质监控平台与设备状态监测节点。日常生成的文档包含炉次计划、配料单、转炉冶炼记录、成分报告、连铸工艺记录、板坯判定单。数据更新节奏为每炉次生成核心冶炼与连铸记录，关键工艺参数实时同步，班组级汇总报表按每班更新。数据字段包含冶炼批次标识、原料配比参数、实时温度值、浇铸速率、成分检测结果与缺陷判定结果，无统一固定格式，随产线调整存在细微差异。

## 这些特征在「向量模型与索引」这一环带来什么约束
高频更新的业务特征对索引环节带来多重约束。每炉次生成的独立记录与实时同步的工艺参数，要求索引支持增量写入与局部刷新，避免全量重建带来的资源占用。非统一格式的文档与多样字段，要求分块逻辑需适配不同文档结构，无法采用固定长度的一刀切分块。班组级汇总报表与实时数据的混合更新，要求索引的刷新策略可灵活配置，兼顾实时性与存储开销。冶炼批次与浇次的强耦合关系，要求索引需保留批次间的关联标识，避免检索时割裂工艺链路。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 按文档类型适配，炉次记录取300–500字符，报表类取800–1200字符 | 不同文档的信息密度差异，避免语义割裂或块度过大，适配钢铁冶炼与连铸的多样文档格式 |
| 重叠长度 | 50–80字符 | 保留跨块的工艺关联信息，避免冶炼流程的上下文断裂 |
| 相似度阈值 | 按实测标定 | 钢铁工艺参数的波动范围较窄，需适配业务场景的匹配精度要求 |
| 单次索引上限 | 前20条 | 平衡检索效率与召回覆盖，适配每炉次的记录量级 |
| `maxToken` | 8000 token | 适配长文档的上下文拼接，满足连铸工艺全流程的检索需求 |
| `defaultToken` | 200 token | 适配单条记录的基础检索长度，避免无效token占用资源 |

## 容易做错的三处
- 现象：索引构建过程停滞在最后一组数据，界面无进度更新，日志显示资源占用峰值过高。原因：未配置增量索引策略，全量重建时因高频更新的冶炼与连铸数据量过大，触发系统资源耗尽。
- 现象：新增自定义embedding模型后，可正常生成索引但搜索测试返回报错或无匹配结果。原因：未针对钢铁冶炼的数值型工艺参数调整向量编码逻辑，导致生成的向量无法匹配业务特征。
- 现象：批量上传文档后，仅最后一组文件完成索引，其余文件状态始终为待索引。原因：单次索引上限配置过低，批量任务被截断，未适配钢铁冶炼文档的批量上传需求。

## 怎么确认配好了
- 上传单条转炉冶炼记录，验证索引生成进度正常完成，无停滞或报错。
- 输入包含特定工艺参数的检索词，核对返回结果的关联批次标识是否与业务逻辑一致，调整匹配规则至符合需求。
- 查看系统索引监控面板，确认增量更新任务可按预设频率触发，未出现异常的全量重建操作。
- 检查自定义embedding模型的加载日志，确认与钢铁冶炼数据适配的编码规则已生效。
