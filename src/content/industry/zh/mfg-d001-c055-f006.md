# 铸造（砂型、精密、压铸）的供应商与过程质量审核：引用来源与溯源

## 这个品类的数据长什么样
该品类的数据来源包括ERP物料主数据、熔炼炉与测温仪、光谱仪、MES炉次记录、模具管理系统、客户图纸与技术条件。日常生成的文档涵盖铸造工艺卡、配料单、炉次记录、模具履历、首件检验记录、材质报告、不合格品评审单。数据更新节奏为每炉次、每批或每日，字段包含合金成分占比、熔炼温度、浇注参数、模具模次、缺陷类型等，附带对应物理量单位。

## 这些特征在「引用来源与溯源」这一环带来什么约束
由于数据按炉次、每批更新，引用溯源需绑定唯一炉次或模次标识，避免跨批次混淆。多源异构数据来自设备、系统与图纸，需明确各来源的字段映射规则，确保引用的配料比例、温度参数与原始记录完全匹配。专业字段如合金成分占比、浇注温度带单位，需保留原始单位以保证溯源准确性。同时，不合格品评审单关联炉次与模次，溯源需覆盖从缺陷到生产环节的完整链路，避免追溯断层。高频更新的数据需实时拉取最新版本，防止引用过期的炉次记录或配料单。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本适配，具体取值可根据实际业务场景微调：

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文 | 10000–14000 token | 适配铸造类文档单条平均长度，容纳多源关联数据的拼接需求 |
| 单次搜索上限 | 前6–10条 | 覆盖单炉次的工艺卡、炉次记录、模具履历等核心关联文档 |
| `quoteMaxToken` | 2500–4500 token | 限制单条引用的字符长度，避免超长字段破坏上下文结构 |
| `responseData` | 开启原始字段保留 | 确保引用内容附带炉次号、模次号等唯一标识，支撑精准溯源 |
| `detail` | 开启完整元数据 | 保留文档的更新时间、来源系统信息，完善溯源链路的可追溯性 |
| 分块重叠长度 | 100–150 字符 | 保留跨炉次、跨模次的关联字段，避免关键信息被分块截断 |

## 容易做错的三处
- 现象：界面显示的上下文条数与实际发送到调用端的条数不符，例如界面显示30条但实际发送310条。原因：未正确配置`quoteMaxToken`与最大上下文的匹配关系，系统截断逻辑与前端展示逻辑未对齐。
- 现象：知识库中超过设定引用上限的文档块被错误引用。原因：分块长度设置未覆盖超长文档的拆分，或未适配长文本处理逻辑，导致大块内容被直接截断引用。
- 现象：引用的合金配料比例与原始炉次记录不符。原因：未开启`responseData`的原始字段保留，系统自动拼接的字段丢失了炉次号与模次号的关联映射，导致溯源错误。

## 怎么确认配好了
- 查看引用日志，确认每条引用内容都附带炉次号、模次号等唯一标识，验证`responseData`的开启状态。
- 测试导入单条超长铸造工艺卡，检查分块后的内容是否保留了关键的熔炼温度、配料比例字段，验证分块重叠长度的设置效果。
- 发起一次质量审核查询，对比界面展示的上下文条数与调用端接收的参数，验证最大上下文与`quoteMaxToken`的配置匹配度。
- 查看元数据面板，确认每条引用的文档都显示了更新时间与来源系统，验证`detail`的开启状态。
