# 仓储、批次与厂内物流的工艺文件与异常报告起草：文档解析与分块

## 这个品类的数据长什么样
通常，该品类的主体涉及原材料库、线边库、成品库及物流物控部门，日常产生的文档包括收货单、上架单、领退料单、移库单、盘点表、批次台账、先进先出与效期记录等。数据来源涵盖ERP/WMS系统、条码或RFID设备、采购与工单信息、库位数据、AGV或输送系统、称重数据等。数据更新频率覆盖实时、每日汇总及月度盘点周期，文档多为结构化表单，包含批次号、库位编码、效期日期、物料数量、重量等固定字段，部分异常报告包含非结构化的现场描述与整改建议。

## 这些特征在「文档解析与分块」这一环带来什么约束
由于仓储物流文档包含大量关联字段，如批次号与效期绑定、库位与物料数量对应，分块时需避免拆分这些关联信息，否则会影响后续工艺文件与异常报告的起草准确性。实时更新的单据需要快速解析，避免影响物流配送的时效性；月度盘点的批量文档则要求系统能处理较大文件量，防止解析超时。同时，部分文档可能来自不同系统导出，格式存在细微差异，需要解析规则具备一定的适配性，而异常报告中的非结构化内容需保留上下文逻辑，确保起草时的信息完整性。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本适配：
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chunkSize` | 800–1200 字符 | 适配仓储文档的字段长度，避免拆分批次号、库位编码等关联字段，确保单块内信息完整 |
| `chunkSplitter` | 按段落+语义分块 | 保留异常报告中的现场描述与整改建议的上下文关联，避免破坏工艺步骤的逻辑连贯性 |
| `customPdfParse` | 启用OCR辅助解析 | 处理部分扫描版的盘点表或纸质单据扫描件，确保印刷或手写的字段可被正确识别 |
| `UPLOAD_FILE_MAX_SIZE` | 1000 MB | 适配月度盘点的批量文档上传需求，避免因文件过大导致上传失败 |
| `PARSE_FILE_TIMEOUT_SECONDS` | 600 秒 | 应对大批次台账的解析耗时，防止因超时中断解析流程 |
| `chunkSettingMode` | 手动配置 | 针对仓储文档的固定字段结构，调整分块规则以匹配业务需求 |

## 容易做错的三处
- 部署后提示显存不足，或无法识别CUDA 12.8环境。原因是未在docker启动命令中挂载GPU设备，或未指定与显卡驱动匹配的CUDA运行时版本。
- 解析后的批次台账字段缺失，或库位编码被拆分到不同分块。原因是`chunkSize`设置过小，导致关联字段被强制拆分，破坏了信息的完整性。
- 上传带图片的异常报告后，解析得到的markdown文档中图片链接丢失域名前缀。原因是未配置自定义文件解析规则，未保留图片的原始上传路径中的域名信息。

## 怎么确认配好了
- 上传一份标准收货单PDF，检查解析后的分块是否保留了批次号、库位编码的完整关联，未出现字段拆分的情况。
- 测试批量上传月度盘点表，确认解析流程未出现超时中断，耗时符合预期。
- 上传带图片的异常报告，检查解析后的markdown文档中图片链接是否保留了原始域名前缀。
- 查看系统运行日志，确认GPU资源被正常调用，未出现显存溢出或设备识别失败的报错信息。
