# 有色金属冶炼与电解的工艺文件与异常报告起草：多轮对话与提示词

## 这个品类的数据长什么样
该品类的业务数据来自精矿与辅料分析、DCS系统、槽电压电流监测、化验室检测、能源与环保监测等渠道。日常文档包含配料单、熔炼记录、电解槽况记录、化验报告、阳极阴极质量记录、环保台账等，涵盖原料成分、设备运行参数、检测结果、台账信息等字段，单位涵盖质量、电压、电流、时间等类型。数据更新频率按每批原料、每炉或每槽、实时不等，无固定统一周期。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
多源且实时更新的数据要求多轮对话需保留对应批次的上下文，避免跨批次数据混淆；复杂的文档结构要求提示词需明确指定需提取的字段范围，确保生成的工艺文件或异常报告包含完整的业务信息；按批次更新的特性要求对话流程需绑定当前批次的专属参数，防止不同批次的数据交叉干扰；耗时的成分平衡、炉况控制环节要求多轮对话需逐步引导用户补充必要参数，避免一次性输入过多内容超出上下文限制。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本适配。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` | 绑定当前批次的精矿成分、槽况数据 | 匹配该品类按批次更新的业务特征，确保对话调用的是实时对应批次的参数 |
| `messages` | 保留最近30条对话历史 | 适配多轮起草工艺文件时的逐步调整需求，避免上下文过载 |
| 最大上下文长度 | 800–1200 字符 | 匹配单批次工艺文档的核心字段长度，防止加载过多历史数据导致超时 |
| 单次对话返回上限 | 前5条 | 限制异常报告提取的记录条数，避免冗余数据干扰起草 |
| `chatId` | 绑定当前应用会话ID | 确保多轮对话的上下文仅在本次会话内生效，避免跨批次数据混淆 |
| 问题优化开关 | 开启 | 针对复杂的成分平衡、槽况控制类问题，优化用户输入的表述以匹配业务逻辑 |

## 容易做错的三处
- 现象：输入包含多批次数据的JSON文件后，对话返回结果条数不符合预期。原因：未设置合理的单次对话返回上限，导致加载过多数据超出上下文限制。
- 现象：调试预览界面可正常调用本地部署的模型，但正式应用中模型被自动替换为其他类型。原因：未通过`variables`绑定模型调用的专属配置，导致会话上下文被默认参数覆盖。
- 现象：对接外部对话界面后，仅能与第一个对话节点交互，无法延续多轮上下文。原因：未正确绑定`chatId`到会话标识，导致每次交互都重置上下文。

## 怎么确认配好了
- 触发一次多轮对话流程，检查对话历史保留的条数是否符合预设的范围。
- 上传对应批次的业务数据，验证绑定的`variables`是否正确关联了当前批次的参数。
- 调用本地模型后，查看会话日志确认模型类型未被自动替换。
- 输入包含指定字段的测试数据，确认生成的文档包含所有需要的业务字段。
