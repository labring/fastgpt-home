# 服装裁剪与缝制的工艺文件与异常报告起草：多轮对话与提示词

## 这个品类的数据长什么样
服装裁剪与缝制环节的生产数据多来自订单与尺码表、CAD样板、面辅料检验记录、车间吊挂系统、验针机数据及客户封样。日常产出的文档包含工艺单、样板、排料图、裁剪单、首件封样、工序质量表、包装配码单。数据更新节奏为每订单、每款、每批，不同订单的面料色号、裁片数量、工序要求差异明显，文档字段包含尺码规格、面料批次、裁片数量、包装配码比例等，无统一固定的标准化字段模板。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
由于该品类款式多、季节性强且裁片不可逆，多轮对话需精准匹配当前订单的专属参数，避免跨批次数据混淆。频繁的订单更新要求每次对话需实时传入最新的生产数据，因此需绑定独立的会话变量。密集的工艺与质检参数要求上下文长度需控制在合理区间，避免冗余信息干扰核心分析。同时，工序拆解与异常判定需逐步引导模型调用对应文档，无法通过单次提示词完成全量逻辑覆盖。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` | 绑定当前订单的尺码表、面料批次号、包装配码规则 | 实现专属生产数据的精准传入，适配每订单每款的差异化参数 |
| `messages` | 限制历史对话轮次为前3轮 | 过滤冗余的历史对话信息，避免干扰当前工艺或异常报告的核心分析逻辑 |
| `chatId` | 开启持久化存储 | 保留会话状态，支持多轮对话的回溯与延续 |
| 最大上下文长度 | 800–1200 字符 | 适配服装工艺参数的密集性，避免内容溢出或截断 |
| 会话超时设置 | 600 秒 | 预留足够时间调取CAD样板、质检记录等多源数据完成分析 |
| 上下文变量触发规则 | 按当前订单ID触发 | 确保每个会话仅调用对应订单的专属生产数据，避免跨订单混淆 |

## 容易做错的三处
- 现象：工作流对话显示失败，但模型后台有响应日志。原因：未将`variables`绑定的订单专属数据正确传入模型上下文，导致模型无法匹配当前批次的工艺参数。
- 现象：对话日志为空，无法回溯历史配置。原因：未开启`chatId`的持久化存储，导致会话状态随会话结束丢失。
- 现象：相同提示词下回复效果比原生模型差。原因：未限制历史对话轮次，冗余的过往对话内容干扰了当前工艺分析的核心逻辑。

## 怎么确认配好了
- 测试绑定单个订单的`variables`参数，检查模型是否能输出对应尺码的裁剪工艺要求与包装配码规则。
- 开启`chatId`持久化存储后，发起两轮以上对话，确认历史消息可正常加载并参与当前分析。
- 提交异常报告起草请求，检查输出是否包含当前批次的面料色号、裁片数量等专属信息。
- 调整上下文长度至800–1200 字符区间，确认回复无内容截断或溢出情况。
