# 水泥熟料与粉磨的工艺文件与异常报告起草：向量模型与索引

## 这个品类的数据长什么样
水泥熟料与粉磨的业务数据来源涵盖在线成分分析、DCS系统、化验室记录、窑磨设备传感数据、原燃料台账与能源计量报表。数据更新节奏分为实时（设备传感与DCS数据）、每班（设备巡检与窑操作记录）、每日（化验报告与质量控制通知单）。日常文档包含生料配料方案、窑操作日志、熟料强度化验报告、设备巡检单、能源消耗报表等，字段包含原燃料成分数值、设备运行参数、质量指标读数，无固定统一格式的标准化文档结构。

## 这些特征在「向量模型与索引」这一环带来什么约束
多源异构的数据来源要求索引支持结构化与半结构化数据的混合导入，避免丢失原燃料台账的字段关联。实时更新的设备传感数据需要配置增量索引策略，避免全量索引的耗时问题。不同更新频率的文档需对应不同的索引刷新周期，确保异常报告能及时被检索。文档字段包含关键质量指标与热工参数，分块时需保留字段上下文，防止拆分后丢失关键关联信息，保障异常报告的精准召回。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配生料配料方案、窑操作记录的单段内容长度，避免跨关键参数拆分 |
| 重叠长度 | 100–150 字符 | 保留相邻分块的字段关联，例如配料方案的前后参数衔接 |
| 相似度阈值 | 0.72–0.80 | 匹配水泥强度、热工制度这类关键指标的召回精度，适配异常报告的特征匹配 |
| 单次搜索上限 | 前8条 | 覆盖每班巡检记录、每日化验报告的典型条目数，避免冗余召回 |
| `maxToken` | 4000 | 符合FastGPT v4.17.0的模型输入限制，适配多份工艺文档的拼接需求 |
| `defaultToken` | 1024 | 生成工艺文件草稿时的基础输出长度，匹配单份报告的常规篇幅 |

## 容易做错的三处
- 现象：索引过程耗时远超预期，状态显示为“处理中”超过30分钟。原因：未针对实时更新的DCS数据配置增量索引，全量索引扫描了全量历史数据。
- 现象：创建知识库时文本理解模型下拉框无对应ollama qwen2.5选项。原因：未将模型渠道的语言模型关联至知识库的文本理解环节，仅配置了索引模型。
- 现象：召回结果中缺失关键异常报告条目，结果条数远低于预期。原因：分块长度设置过小，将包含设备巡检异常描述的段落拆分为多个无关联片段，导致相似度匹配失效。

## 怎么确认配好了
- 执行一次小批量测试索引，选取10份典型的生料配料方案与异常报告，核对索引完成耗时是否符合业务预期。
- 在知识库的模型配置页面，确认已添加的ollama qwen2.5与bge-m3模型均显示在对应下拉框中。
- 输入一条异常报告关键词，核对召回结果的条数与内容匹配度是否符合业务场景的需求。
- 查看索引日志，确认增量索引仅处理了更新时间晚于上次索引的文档，未重复扫描全量数据。
