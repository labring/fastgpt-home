# 汽车整车总装的工艺文件与异常报告起草：引用来源与溯源

## 这个品类的数据长什么样
汽车整车总装场景的数据来源包含ERP/MES系统、VIN与车辆配置系统、供应商批次管理系统、拧紧工具终端、EOL下线检测线、质量追溯系统。日常文档涵盖生产订单、VIN清单、装配作业指导书、拧紧扭矩数据、下线检测报告、返修记录、一致性放行文件。数据更新节奏为每车实时生成、每班汇总归档，单台车辆的关联文档包含数百项配置与检测字段，核心字段包括VIN码、扭矩值（单位牛·米）、检测项编号、供应商批次号、工位编码等。

## 这些特征在「引用来源与溯源」这一环带来什么约束
以VIN为单车主线的混线生产模式，要求引用溯源必须精准绑定单台车辆的专属配置与生产数据，避免跨车辆的文档混淆。实时更新的拧紧数据与下线检测报告，要求召回逻辑支持动态匹配最新生成的文档。单台车辆关联文档数量较多的特征，要求限制召回范围与上下文长度，避免引入无关数据导致生成结果冗余。同时，总装场景的合规性要求，必须保留原始文档的元数据关联，确保每一处引用都可追溯到具体的生产环节与数据来源。

## 配置怎么定
本文基于FastGPT v4.17.0版本的配置说明
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `quoteMaxToken` | `8000–12000 token` | 汽车总装的工艺文件与异常报告包含多段拧紧数据、VIN关联配置信息，需要足够的上下文承载溯源所需的完整字段，避免截断关键追溯信息 |
| `responseData` | 返回原始文档元数据 | 起草的异常报告与工艺文件需要关联具体的拧紧工具编号、检测工位号、供应商批次等字段，返回元数据可确保引用内容的可追溯性 |
| `detail` | 开启完整溯源模式 | 完整溯源模式可保留原始文档的全部关联信息，满足总装场景下对单台车辆生产数据的追溯要求 |
| 单次召回文档数 | 前8条 | 混线生产下每台车辆的专属文档数量有限，过多召回会引入无关数据，影响生成结果的准确性 |
| 上下文窗口 | `16000–20000 token` | 需要同时承载VIN匹配的配置文档、拧紧数据、异常报告原始内容，避免上下文溢出导致生成中断 |

## 容易做错的三处
- 配置模型测试时弹出报错提示，强行忽略后运行可生成内容但引用条数不足：未配置按VIN标签过滤召回结果的规则，导致召回范围覆盖全量知识库文档，仅匹配到第一条关联数据。
- 工作台知识库应用每次仅检索到单条文档：未绑定车辆专属的筛选条件，仅触发了全局知识库的默认召回逻辑，未匹配到该VIN对应的全部关联文档。
- 知识库引用上限不足：未调整`quoteMaxToken`或单次召回文档数的配置，导致可承载的引用文档数量无法满足总装场景下多字段溯源的需求。

## 怎么确认配好了
- 输入特定VIN码，检索返回的文档列表包含该VIN对应的装配作业指导书、拧紧扭矩数据与下线检测报告。
- 生成的工艺文件或异常报告中，每一处引用都附带原始文档的元数据字段，如工位编码、供应商批次号。
- 测试调用时无报错提示，生成内容的引用标记与原始文档的编号一一对应。
- 更换VIN码后，召回的文档列表自动更新为新VIN对应的专属生产数据，无冗余无关文档混入。
