# 生产计划与车间排程的工艺文件与异常报告起草：向量模型与索引

## 这个品类的数据长什么样
该品类的核心数据来自ERP订单与库存、BOM和工艺路线、设备产能、人员班次、在制品和供应商到货。日常处理的文档包含销售订单、主生产计划、物料需求计划、周日排产表、工单、缺料清单、交期变更单，数据字段涵盖订单号、物料编码、产能数值、班次时段、工序要求等，单位涉及件、小时、天等。数据更新频率涵盖每日、每周，以及订单或异常发生时的实时更新。

## 这些特征在「向量模型与索引」这一环带来什么约束
由于数据来源分散且更新节奏差异大，索引需要支持增量更新以适配实时异常报告的召回需求；日常文档包含表格类排产表与文本类工单，分块规则需要适配不同格式的文本结构；字段多且带有特定业务单位，向量模型需要准确识别结构化字段的语义关联；突发的异常报告需要快速召回最新数据，因此索引的召回效率需要适配高频查询场景。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配工单、排产表等日常文档的平均字符长度，避免分块过碎或丢失上下文 |
| 重叠长度 | 100–150 字符 | 保留相邻分块的语义关联，避免跨分块的工序、排程信息断裂 |
| 相似度阈值 | 0.75–0.85 | 过滤低关联的库存、设备数据，聚焦与排程、工单相关的结果 |
| 单次搜索上限 | 前 20 条 | 控制召回数据量，降低混合检索的耗时压力 |
| `maxToken` | 8192 token | 适配长文档如完整主生产计划的向量化需求，避免截断关键信息 |
| `defaultToken` | 按实测标定 | 适配日常短文档的默认向量化参数，平衡精度与效率 |

## 容易做错的三处
- 现象：Docker部署后向量得分一致，原因：未正确配置分块规则，导致所有上传文档被统一截断后向量化，丢失了排程表、工单的差异化信息。
- 现象：混合检索耗时超过10秒，原因：未设置合理的单次搜索上限，召回过多无关数据导致后续重排环节耗时增加。
- 现象：索引构建停在最后一组，原因：未调整`maxToken`参数，超长的主生产计划文档无法完成向量化，导致构建流程卡住。

## 怎么确认配好了
- 上传一份典型的工单文档，查看分块后的片段是否覆盖工单编号、工序要求、交付时间等关键字段。
- 发起包含排产表关键词的检索，确认返回结果的相似度得分存在合理差异，无全部分数一致的情况。
- 新增一份交期变更单，触发增量索引更新，验证新增文档能在合理时长内被检索到。
- 查看FastGPT v4.17.0的向量索引日志，确认无`maxToken`超限或分块异常的报错信息。
