# 电镀与化学表面处理的工艺文件与异常报告起草：引用来源与溯源

## 这个品类的数据长什么样
本品类的典型主体为电镀厂、五金件表面处理车间，日常文档包含槽液分析记录、工艺参数卡、挂具记录、膜厚与附着力报告、危废台账、废水监测记录。数据来源涵盖客户表面处理规范、槽液化验结果、整流器运行数据、在线水质监测数据、危废管理台账。数据更新频率为每槽次、每班或按监测要求，单份文档包含具体参数与单位，如槽液pH值、电流密度（A/dm²）、膜厚（μm）等，不同文档的字段与更新节奏差异明显。

## 这些特征在「引用来源与溯源」这一环带来什么约束
高频更新的多类文档要求溯源时匹配最新的生产周期数据，避免引用过期的槽液或监测记录。多类型文档的差异化字段需要溯源系统区分文档类别，确保引用的参数与当前生产场景对应。在线监测数据与离线台账的混合来源，要求溯源时标注数据的获取方式与更新时间，保障异常分析的准确性。出错后果严重的业务属性，要求溯源必须精准对应到具体槽次或监测时段，防止因引用错误引发批量返工或环保处罚。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `quoteMaxToken` | 1500–2000 token | 匹配该品类单份工艺文档或监测记录的平均长度，避免截断关键参数与单位 |
| `responseData` | 开启 | 要求返回引用来源的元数据，包含文档类型、更新时间与槽次编号 |
| 单次搜索上限 | 前6条 | 覆盖异常报告起草时需要参考的槽液、工艺、挂具等多类文档的数量需求 |
| 重排 | 开启 | 按相关性对引用来源排序，优先展示与当前工艺调整或异常问题最相关的记录 |
| `detail` | 完整 | 返回引用文本的完整片段，包含所有检测参数与单位信息 |
| 最大上下文 | 8000 字符 | 容纳多份关联文档的内容，保障异常分析时的上下文完整性 |

## 容易做错的三处
- 现象：返回的引用来源未标注文档的更新时间或槽次编号。原因：未开启`responseData`配置，未要求返回元数据字段，导致无法追溯对应生产周期的记录。
- 现象：搜索返回的引用条数不足，无法覆盖异常报告需要的全部工艺参数。原因：单次搜索上限设置过低，未匹配该品类多类文档的参考需求。
- 现象：引用的槽液数据与当前生产槽次不匹配，引发异常分析结论错误。原因：未按文档的更新时间（每槽次/每班）进行过滤，错误引用了历史槽次的槽液记录，可能导致镀层起泡或批量返工。

## 怎么确认配好了
- 发起包含槽液参数查询的测试请求，检查返回结果中是否包含引用来源的文档类型与更新时间。
- 触发异常报告起草的工作流，查看返回的引用列表数量是否符合预设的单次搜索上限。
- 导入一份过期的槽液分析记录，验证搜索结果是否优先展示最新的监测数据。
- 查看接口返回的`responseData`字段，确认包含完整的引用文本片段与元信息。
