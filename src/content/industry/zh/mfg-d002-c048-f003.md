# 设备点检与预防维修的工艺文件与异常报告起草：多轮对话与提示词

## 这个品类的数据长什么样
本品类数据来自EAM/CMMS系统、设备传感终端、操作员点检记录、维修历史台账、备件库存清单与特种设备法定检验档案。数据更新节奏覆盖每班点检提交、日/周/月保养计划更新、故障发生时的实时上报。日常文档包含设备台账、点检检查表、分级保养计划、维修工单、故障分析报告、备件申领单等，字段包含设备编号、点检项编码、异常代码、备件型号、检验有效期等，单位涵盖台、次、天、件等资产与运维相关标准单位。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据来源分散且更新节奏差异大，要求多轮对话必须绑定唯一会话标识，避免不同设备的运维记录混淆。文档字段多且关联紧密，提示词需精准指定可调用的字段范围，避免AI生成无关内容。实时触发的故障数据要求对话上下文保留最新的维修记录，不能仅依赖静态历史数据。设备台账与法定检验档案的合规性要求，提示词需嵌入专属校验逻辑，确保起草的报告符合运维规范。此外，品类文档的字符长度差异较大，需限制上下文规模以避免输入超限。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定设备编号+会话创建时间戳 | 区分不同设备的运维会话，避免上下文交叉混淆 |
| `variables` | 预设设备ID、点检周期、异常代码模板 | 精准传递品类专属字段，减少AI冗余输出 |
| `messages` | 按会话顺序拼接最近的5条运维记录 | 确保AI调用的上下文符合多轮对话的逻辑顺序 |
| 最大上下文长度 | 800–1200 字符 | 适配点检表、维修工单的单批次文档长度，避免输入超限 |
| 输入超限拦截 | 按实测标定 | 匹配品类文档的平均字符量，提前拦截超出模型输入上限的请求 |

## 容易做错的三处
- 现象：对话日志无法关联到具体设备或维修班组。原因：未绑定`chatId`到设备编号与班组标识，导致会话归属模糊。
- 现象：AI无法解析上传的jpg格式点检照片。原因：未配置支持图片解析的工具节点，仅在AI对话模块中调用文本类运维数据。
- 现象：输入超长的设备保养计划时，AI返回空结果或触发系统报错。原因：未设置输入超限拦截逻辑，请求超出模型输入上限后未提前终止处理。

## 怎么确认配好了
- 发起一次针对特定设备的点检会话，查看对话日志是否包含绑定的设备编号与班组信息，确认`chatId`配置生效。
- 上传jpg格式的点检记录表，验证AI是否能识别并提取表格中的点检项与异常描述。
- 输入超出预设长度的保养计划文本，确认系统是否提前弹出输入超限提示并拦截请求。
- 发起会话删除操作，验证对应对话记录是否被正确清理，符合运维数据隐私要求。
