# 锻造与模锻的工艺文件与异常报告起草：多轮对话与提示词
本文基于 FastGPT v4.17.0 版本编写

## 这个品类的数据长什么样
该品类的数据来源包括原材料质保书、加热炉系统、压力机采集数据、MES系统、无损检测仪、客户锻件图。数据更新节奏为每件锻件、每生产批次或每炉次。日常文档涵盖锻造工艺规程、下料卡、加热炉记录、锻造过程卡、模具寿命记录、热处理委托单、超声检测报告，包含锻造比、纤维方向、炉批号、锻件尺寸、检测结果等字段，单位涉及毫米、摄氏度、吨等。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
该品类的数据更新频率高且按单批次、单炉次生成，要求多轮对话上下文需精准绑定对应生产批次的原始数据，避免跨批次数据混淆。多源异构的数据来源，要求提示词明确指定各文档的专属字段规则，确保调用数据时匹配正确的锻造比、炉批号等关键项。单份文档体积较大且字段专业，要求对话环节限定上下文提取范围，避免冗余信息干扰生成结果。异常报告起草需快速关联加热、压力机采集的实时参数，提示词需固定检索维度以缩短响应时间。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配锻造工艺规程的单段落专业内容长度，避免块内信息断裂 |
| 重叠长度 | 100–200 字符 | 保留相邻块的炉批号、锻造比等关键字段，防止跨块检索遗漏 |
| 单次搜索上限 | 前 5 条 | 匹配单炉次生产关联的文档数量，避免引入无关批次数据 |
| 问题优化 | 开启 | 针对专业术语多的锻造场景，优化用户输入的工艺查询表述，匹配知识库内的标准文档 |
| 最大上下文 | 6000 token | 限制单轮对话加载的文档总量，适配锻造类文档的专业内容密度 |
| `chatId` | 绑定当前生产批次ID | 确保多轮对话始终关联对应批次的原始数据，避免上下文混乱 |

## 容易做错的三处
- 对话返回结果包含无关炉次的文档内容：原因是未绑定`chatId`到当前生产批次ID，检索时未限定批次范围，混入了其他炉次的数据。
- 大体积Word文档解析耗时过长：原因是分块长度设置过大，超出了单块解析的合理范围，导致单块处理压力集中。
- 异常报告生成的锻造比数值错误：原因是提示词未明确指定从对应炉次的原材料质保书中提取数据，误调用了其他批次的参数。

## 怎么确认配好了
- 发起基于某炉次加热记录的对话，检查上下文是否仅包含该炉次的关联文档，无其他批次数据。
- 上传单份10M左右的锻造工艺规程，观察解析耗时是否符合预期，无明显卡顿。
- 输入包含专业术语的查询，确认系统能正确识别锻造比、纤维方向等字段并匹配对应文档。
- 查看对话的`messages`参数，确认每次会话的上下文均绑定了当前批次的专属标识。
