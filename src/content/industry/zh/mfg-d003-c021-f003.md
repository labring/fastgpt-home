# 家具与木制品制造的工艺规程与技术标准问答：多轮对话与提示词

## 这个品类的数据长什么样
该品类数据主要来自定制家居、板式/实木家具、木门企业的订单设计系统、板材与木材批次台账、数控开料钻孔设备、ERP/MES系统及含水率检测记录。日常文档包含拆单图、开料清单、封边与钻孔程序、涂装工艺规范、五金物料清单、试装及包装记录。数据更新随定制订单生成、每日设备运行日志更新、每批次原材料进场同步更新，文档字段多包含板件编号、尺寸参数、物料型号、工艺参数等内容。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
定制化订单驱动的生产模式导致单订单板件数量多，多轮对话需完整保留订单相关的板件尺寸、五金配置等上下文，避免信息丢失。数据来源分散且更新节奏不同，提示词需明确指引对话调用对应来源的最新数据，例如从板材批次台账获取当前可用物料的含水率参数。单订单数据量大，需限制对话上下文的有效范围，防止冗余信息干扰回答准确性。同时，工艺参数错误会直接导致生产偏差，对话需支持逐轮核对关键工艺字段，确保与文档内容一致。

## 配置怎么定
以下配置基于 FastGPT v4.17.0 版本。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定当前定制订单的唯一业务标识 | 确保多轮对话上下文严格关联对应订单，避免跨订单数据混淆 |
| `messages` | 按对话时序追加历史记录，保留前15–20轮有效交互 | 适配单订单多板件的多轮工艺查询需求，控制上下文总长度 |
| `variables` | 注入当前订单的板材批次号、五金清单ID、涂装工艺版本 | 让对话可直接调用对应批次的最新工艺与物料参数 |
| 最大上下文长度 | 8000–12000 字符 | 匹配单订单拆单文档、工艺记录的总字符量，防止上下文溢出 |
| 对话超时时间 | 600 秒 | 匹配单订单工艺查询的平均响应时长，避免长时间等待导致生产流程中断 |
| 问题优化 | 开启 | 自动整理用户的工艺查询，关联之前提及的板件尺寸、安装位置等信息 |

## 容易做错的三处
- 调用`/api/v1/chat/completions`接口时未返回预期的工艺标准结果，现象为接口返回结果未关联预设的家具涂装、开料规范。原因是未在`messages`参数中正确注入系统提示词，或提示词未限定当前品类的工艺范围。
- 多轮对话中后续查询无法关联之前提及的板件尺寸或订单信息，现象为对话上下文丢失。原因是未绑定当前订单的`chatId`，会话上下文未持久化到对应订单。
- 使用通用全局key发起跨应用对话时，出现订单数据混淆，现象为不同应用的对话上下文被共享。原因是未为每个应用绑定独立的`chatId`前缀，导致会话上下文被错误关联。

## 怎么确认配好了
- 发起一次测试对话，传入测试订单的`chatId`，查看对话上下文是否保留前序交互的板件参数。
- 调用接口时检查`variables`参数是否注入了当前订单的板材批次号、五金清单等专属信息。
- 发起多轮连续查询，确认后续提问可关联前序提及的工艺细节，无需重复说明订单信息。
- 查看接口返回结果的上下文长度，确认未超出预设的最大范围，无冗余无关数据。
- 等待600秒内确认接口返回结果，验证对话超时时间配置生效。
