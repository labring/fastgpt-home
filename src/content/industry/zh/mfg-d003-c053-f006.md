# 钢铁冶炼与连铸的工艺规程与技术标准问答：引用来源与溯源

## 这个品类的数据长什么样
钢铁冶炼与连铸的生产数据来自铁水与废钢投料记录、L2过程控制系统、化验室成分报告、MES生产管理系统、能源介质监控系统与设备状态监测模块。日常生产文档包含炉次计划、配料单、转炉冶炼记录、连铸工艺参数记录、板坯质量判定单等，单份文档包含炉次号、浇次号、实时温度、成分含量、操作时间等字段，更新频率覆盖每炉次、实时与每班周期，单炉次的冶炼与连铸数据存在强耦合关系。

## 这些特征在「引用来源与溯源」这一环带来什么约束
由于数据按炉次、实时更新且强耦合，溯源环节需要精准关联到具体生产批次，避免跨炉次数据混淆。多系统来源的文档格式存在差异，需要保证溯源时能匹配到原始数据的采集模块与时间戳。高温连续生产流程无法承受过长的响应延迟，溯源环节的配置不能占用过多实时计算资源。同时，工艺问答的引用错误会直接导致炉次降级或报废，溯源的准确性直接影响生产决策的可靠性。

## 配置怎么定
以下配置适配FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 匹配单份炉次工艺记录的典型长度，避免分块时跨炉次数据混杂 |
| 重叠长度 | 150 字符 | 保留炉次号、浇次号等关键标识，防止分块后丢失跨工序的关联信息 |
| `quoteMaxToken` | 6000–10000 token | 适配多份冶炼、连铸记录的总token量，保证问答上下文覆盖完整工艺逻辑 |
| `responseData` | 包含源文档路径、炉次号、采集时间 | 满足溯源到具体生产批次与数据来源的核心需求 |
| `detail` | 开启 | 展示完整的成分、温度等工艺字段，便于生产人员验证引用内容的准确性 |
| 单次召回上限 | 前5条 | 控制上下文规模，避免冗余数据干扰实时问答的响应速度 |

## 容易做错的三处
- 现象：批量上传100份工艺文档后，知识库召回的引用内容出现跨炉次混杂，原因：分块长度设置过小，导致单块包含多个炉次的工艺数据，溯源时无法精准匹配单炉次。
- 现象：在变量引用模式下无法找到大模型温度的设置入口，原因：未在对话组件中正确绑定变量引用的高级配置面板，或未开启对应参数的显示开关。
- 现象：引用溯源时显示的id为空或无法关联到原始文档，原因：未配置`responseData`返回源文档的唯一标识字段，导致系统无法匹配知识库中的原始生产数据。

## 怎么确认配好了
- 上传单份完整的炉次工艺记录，发起对应工艺问题的问答，检查引用来源是否标注了炉次号与采集时间。
- 批量上传多份同类型的生产文档，发起跨炉次的对比问答，检查召回的引用内容是否按炉次分类，无跨批次混杂。
- 在变量引用模式下，测试发起对话并调整温度参数，验证问答结果随参数变化产生对应调整。
- 触发异常上传场景，查看知识库的异常日志，确认重新上传的文档会自动去重，无重复引用记录。
