# 烘焙与方便食品的技术文档交叉审查：引用来源与溯源

## 这个品类的数据长什么样
典型主体为面包糕点、饼干、方便面、速冻面点工厂，日常文档包含配方与投料单、生产记录、烘烤或蒸煮曲线、金属检测记录、清洁消毒记录、出厂检验报告。数据来源涵盖原辅料合格证明、ERP/MES系统、称量系统、烤炉或油炸线、实验室检测数据、食品追溯台账。更新频率按生产批次、班次或每日更新，文档字段包含过敏原标识、投料量、烘烤温度与时长、包装日期、保质期等，部分文档带有数值型参数与格式要求。

## 这些特征在「引用来源与溯源」这一环带来什么约束
该品类的高频更新特性要求引用溯源可实时关联最新生产数据，避免使用过时的静态文档。多类文档与特定字段的需求，要求溯源功能需精准匹配过敏原、投料量等核心校验字段，确保交叉审查的准确性。换线频繁的场景下，需关联清洁消毒记录与当前批次生产文档，避免过敏原交叉污染的风险。出错后果涉及产品召回风险，要求溯源可直接定位到原始数据节点，无法依赖模糊的关联信息。

以下配置基于FastGPT v4.17.0版本的功能逻辑。
## 配置怎么定

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `quoteMaxToken` | 300–500 token per quote | 控制单条引用的长度，完整覆盖投料量、烘烤温度等核心校验字段，避免截断关键信息 |
| `responseData` | 包含文档路径、更新时间、批次号 | 匹配食品追溯台账的溯源需求，快速关联原始生产节点与数据来源 |
| `detail` | 开启原始格式保留 | 还原烘烤曲线、投料单的排版细节，避免出现无格式的纯文本引用 |
| 最大上下文token数 | 800–1200 token | 适配单批次关联的多份文档总长度，确保所有关联文档可被完整纳入上下文 |
| 单次召回引用条数 | 前6条 | 覆盖单批次涉及的原辅料合格证明、生产记录、金属检测记录等多类文档 |

## 容易做错的三处
- 上下文引用中出现无格式的纯文本，丢失原文档的表格或换行排版。原因：未正确开启`detail`配置的原始格式保留项，导致切分后的文档格式被剥离。
- 部分提问无法返回对应的知识库引用文档。原因：单次召回引用条数设置过低，未覆盖当前批次关联的全部文档类型，或最大上下文token数不足导致关键文档被截断。
- 无法移除非关联的引用展示内容。原因：未正确配置`responseData`的返回范围，误将不相关批次的文档纳入引用列表。

## 怎么确认配好了
- 上传单批次的配方单、生产记录、金属检测报告，发起交叉审查请求，查看上下文引用是否保留原始的Markdown格式（如表格、分段）。
- 检索特定过敏原字段，验证返回的引用文档中包含对应批次的清洁消毒记录与投料单信息，确保字段匹配精准。
- 查看每条引用的附加信息，确认包含文档来源路径与更新时间，可直接定位到原始数据节点。
- 调整单次召回引用条数的配置，验证返回的引用数量是否符合预设的取值范围。
