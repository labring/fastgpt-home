# 烘焙与方便食品的技术文档交叉审查：模型接入与配置

## 这个品类的数据长什么样
该品类的典型主体为面包糕点、饼干、方便面及速冻面点工厂。日常文档包含配方与投料单、生产记录、烘烤或蒸煮曲线、金属检测记录、清洁消毒记录、出厂检验报告。数据来源覆盖原辅料合格证明、ERP/MES系统、称量系统、烤炉/油炸线设备、实验室数据及食品追溯台账。更新频率按每批、每班或每日更新，文档字段包含物料名称、用量、工艺参数、检测结果、保质期等，部分文档需匹配过敏原标识、生产批次等关联信息。

## 这些特征在「模型接入与配置」这一环带来什么约束
该品类的高频多批次文档、频繁换线的特性，要求模型接入需适配短周期高频的调用场景。多类型异构文档的存在，要求配置需兼容不同文档结构的解析逻辑。过敏原与异物控制的严格需求，要求模型上下文需覆盖全批次关联数据，避免截断关键信息。每日/每批的更新节奏，要求配置需支持动态加载最新台账数据，且需适配多源数据的格式对齐。同时，直接食用的属性放大了错误后果，要求配置需提升结果的精准度，避免遗漏关键校验项。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `maxContext` | 8000–12000 token | 覆盖单批次全链路文档的关联信息，避免截断过敏原、生产批次等关键校验内容 |
| `maxTokens` | 2000–3000 token | 适配单批次审查的输出长度需求，保证完整输出校验结果与依据 |
| `quoteMaxToken` | 1500–2000 字符 | 限定引用文档的长度，匹配烘焙与方便食品文档单条记录的典型长度 |
| 工作流/API 工具选择配置 | auto | 自动选择是否调用工具完成交叉校验，适配多文档关联的审查场景 |
| `temperature` | 0.1–0.3 | 降低随机误差，保证过敏原、保质期等关键信息的校验准确性 |
| `AIPROXY_API_ENDPOINT` | 按实际部署的模型地址填写 | 适配工厂内部docker部署的自定义模型，匹配内部网络访问规则 |

## 容易做错的三处
- 调用docker部署的reranker模型时返回连接超时，原因是未将`AIPROXY_API_ENDPOINT`填写为容器的本地网络地址，错误使用了公网域名或外部地址。
- 调用MCP工具后模型上下文被无故截断，原因是`maxContext`配置值过低，未预留工具调用后新增的上下文空间，导致关键校验信息被覆盖。
- 模型响应速度过慢，原因是`maxTokens`配置值超出模型单次处理上限，或未限定`quoteMaxToken`的引用长度，导致冗余的历史数据参与计算。

## 怎么确认配好了
- 进入FastGPT v4.17.0的模型配置页面，核对`AIPROXY_API_ENDPOINT`与部署的模型地址一致，可通过本地curl命令测试地址连通性。
- 上传单批次的配方与生产记录文档，触发交叉审查任务，查看返回结果中是否包含过敏原、生产参数等业务关注的关键校验项。
- 调用MCP工具完成一次文档关联校验，查看上下文是否完整保留前置审查的关键信息，未出现无故截断。
- 调整`temperature`参数并对比两次审查结果，确认参数调整后结果的一致性符合业务校验需求。
