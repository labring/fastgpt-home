# 纺纱与织造的技术文档交叉审查：引用来源与溯源

## 这个品类的数据长什么样
这个品类的日常文档包含配棉或配料单、工艺上机单、设备运转记录、纱线检验单、坯布检验单、疵点记录等。数据来源涵盖原纤维检验报告、ERP系统、纺机与织机实时数据、条干仪检测结果、验布机采集数据、订单规格文件。数据更新节奏随生产批次、班组班次、单匹坯布推进，每批原料、每班作业、每匹成品布均会生成对应文档与数据条目，文档字段包含纤维指标、纺纱捻度、织造组织参数、疵点类型与位置等，部分字段带有tex、m等行业专属单位。

## 这些特征在「引用来源与溯源」这一环带来什么约束
该品类的数据多源且更新频率高，每批原料、每班作业、每匹成品布均生成独立数据条目，这要求引用溯源环节需精准匹配数据的生成时间与生产批次，避免引用过期的配棉或工艺参数。文档包含行业专属字段与单位，需确保知识库分块完整保留纤维指标、捻度、疵点位置等细节，否则溯源时无法对应到具体生产环节的原始记录。同时，多源数据存在格式差异，离线文档与实时采集数据的结构不同，需在配置中明确不同数据源的结构化处理规则，防止不同类型文档的引用逻辑混淆。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ------ | -------- | ----------- |
| `quoteMaxToken` | `2000–3000 token` | 该品类文档字段密集、单条内容较长，需足够token承载完整引用内容，避免关键参数被截断 |
| `responseData` | 启用结构化解析 | 该品类日常文档多为结构化的工艺单、检验记录，启用后可精准提取纤维指标、疵点类型等专属字段，便于溯源匹配 |
| `detail` | 开启 | 需保留引用文档的原始字段与行业专属单位，确保溯源时可核对具体生产参数的原始记录 |
| 单次搜索引用上限 | 前8–12条 | 该品类单批次生产对应多条数据条目，过多引用会导致上下文过载，过少则无法覆盖核心工艺参考内容 |
| 数据源时间范围 | 近7天 | 该品类数据随生产批次实时更新，近7天范围可覆盖当前生产周期的核心参考文档，避免引用过期数据 |

## 容易做错的三处
- 现象：配置`quoteMaxToken`为3000 token后，界面显示配置成功，但大模型未接收到任何引用上下文。原因：FastGPT v4.17.0中，`quoteMaxToken`的取值若超出系统默认上下文总上限，会触发内容丢弃逻辑，导致引用内容无法传入大模型。
- 现象：将HTTP接口返回的设备运转数据直接上传为知识库文档，配置引用后未匹配到相关结果。原因：未对HTTP响应数据进行结构化整理，原始数据未符合FastGPT的索引格式要求，导致无法被正确识别。
- 现象：界面显示已引用知识库内容，但大模型输出未包含纱线捻度、坯布疵点等专业参数。原因：未开启`detail`配置，导致引用文档仅保留摘要内容，丢失了行业专属的关键字段信息。

## 怎么确认配好了
- 查看知识库索引日志，确认已上传的配棉单、工艺上机单等文档均被正确解析，行业专属字段已被提取。
- 发起测试提问，输入包含纱线细度、织造组织参数的问题，核对大模型输出是否附带引用来源的文档名称与生成时间。
- 调整`quoteMaxToken`的取值，测试不同取值下的上下文加载状态，确认未出现上下文丢失的情况。
- 验证HTTP响应数据上传后的索引结果，确认结构化字段可被正常检索与引用。
