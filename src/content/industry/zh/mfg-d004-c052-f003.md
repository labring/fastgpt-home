# 钢材轧制与精整的技术文档交叉审查：多轮对话与提示词

## 这个品类的数据长什么样
钢材轧制与精整的业务数据来源于板坯或钢坯批次、加热炉、轧机自动控制、在线测厚测宽设备、表面检测系统与MES系统。日常产生的文档包括轧制计划、加热制度、轧制规程、板形厚度记录、表面质量报告、质保书，包含批次标识、温度参数、厚度公差、表面缺陷等级等字段，单位涵盖摄氏度、毫米、百分比等。数据更新频率为每卷或每支钢料实时生成，单批次数据体量随生产节奏动态变化。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
该品类的数据实时更新且按批次绑定，要求多轮对话必须严格隔离不同批次的上下文，避免过期数据干扰当前查询。文档类型多样且字段专业性强，提示词需明确区分不同文档的使用场景，防止将加热制度与表面质量报告的参数混淆。单批次数据体量动态变化，多轮对话的上下文窗口需适配不同长度的文档内容，同时避免因上下文过长导致响应延迟。此外，轧制数据出错后果严重，提示词需增加批次一致性校验的逻辑，确保查询仅使用当前批次的有效文档。

## 配置怎么定
本页面基于FastGPT v4.17.0版本编写。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 绑定钢卷批次唯一标识 | 确保每批次轧制数据的对话上下文隔离，避免跨批次数据混淆 |
| `messages` | 保留最近15–20轮对话 | 轧制数据更新频繁，过多历史对话会引入过期批次的错误数据 |
| `variables` | 预设`轧制批次号`、`检测时间`、`缺陷等级`变量 | 匹配钢材轧制与精整的核心业务字段，快速定位对应文档 |
| 问题优化 | 开启 | 帮助将工程师的口语化查询转化为匹配轧制文档字段的精准指令 |
| 最大上下文 | 8000–12000 token | 平衡多轮对话的上下文完整性与响应速度，适配多份轧制规程与检测报告的内容长度 |

## 容易做错的三处
- 现象：接口调用工作流后，对话日志中的运行数据为空。原因：未在`variables`中绑定工作流返回的批次数据字段，导致对话上下文无法捕获运行参数。
- 现象：多轮对话中出现跨批次的轧制数据混淆。原因：未将钢卷批次唯一标识配置为`chatId`，导致不同批次的对话上下文交叉。
- 现象：文本内容提取时提示代码块未定义。原因：在提示词中使用未提前通过`variables`配置的变量名，导致系统无法识别变量内容。

## 怎么确认配好了
- 发起针对指定钢卷批次的查询，核对对话上下文是否仅包含该批次的轧制计划、检测报告等文档。
- 修改`variables`预设字段，验证对话是否能自动匹配对应业务字段的查询意图。
- 调用接口后，检查对话日志是否捕获到工作流返回的运行数据。
- 测试多轮连续查询，确认上下文不会引入过期批次的错误数据。
