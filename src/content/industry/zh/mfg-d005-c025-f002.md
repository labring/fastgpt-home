# 工装夹具与检具制造的投标文稿与报价编制：向量模型与索引

## 这个品类的数据长什么样
本品类的日常文档包含工装需求书、定位基准方案、夹具图、检具操作书、验收报告、校准记录、变更履历。数据来源包括产品数模与GD&T、工艺路线、三坐标数据、现场试用反馈、计量系统。更新按单个项目推进，伴随每次产品变更触发更新，同时按固定周期完成校准记录的同步。文档结构覆盖结构化参数、几何图纸说明、计量数值与流程文本，字段包含GD&T公差值、三坐标测量偏差、校准周期、变更版本号等，单位涉及毫米、微米、天等。

## 这些特征在「向量模型与索引」这一环带来什么约束
品类文档的多类型结构要求向量分块需兼顾文本描述与结构化参数的完整性，避免割裂关联信息。按项目与变更的更新节奏，要求索引支持增量式更新，降低重复处理历史数据的资源消耗。数据中包含GD&T公差、三坐标测量值等高精度计量信息，要求向量模型需能捕捉数值关联与几何定位逻辑，确保检索结果匹配业务需求。投标场景下的精准召回需求，要求索引需支持按业务标签筛选相关文档，避免无关的历史校准记录干扰检索结果。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配工装需求书、夹具图说明等文档的长度，保留GD&T参数与定位基准的完整关联 |
| 重叠长度 | 100–150 字符 | 保留跨块的变更履历与校准记录的关联信息，避免分块后丢失上下文 |
| 相似度阈值 | 0.75–0.85 | 过滤无关的历史校准记录，精准匹配投标所需的定位方案与验收报告 |
| 单次搜索上限 | 前 15 条 | 控制检索返回的文档数量，平衡召回覆盖率与响应速度 |
| `defaultToken` | 512 | 适配结构化参数的嵌入长度，确保GD&T公差等数值信息被完整编码 |
| `maxToken` | 4000 token | 符合FastGPT v4.17.0的上下文窗口限制，避免截断关键的工艺路线与变更记录 |

## 容易做错的三处
- 现象：Docker容器部署后，所有向量检索结果的得分完全一致；原因：容器内未正确传递业务专属的嵌入请求参数，导致所有文本生成了相同的默认嵌入向量。
- 现象：索引构建任务持续停留在最后一批文档的处理环节，无进度更新；原因：增量索引的触发规则未适配按项目更新的节奏，仅执行全量索引，未处理新增的变更履历文档。
- 现象：混合检索请求响应耗时超过10秒，单次搜索无有效结果返回；原因：未限制单次搜索的召回文档数量，导致加载过多的三坐标测量数据与夹具图纸文本，超出系统资源上限。

## 怎么确认配好了
- 上传一份典型的工装需求书与夹具图，检查分块后的文本块是否保留了GD&T参数与定位基准的完整关联信息。
- 发起检索请求，验证返回结果的得分存在明显差异，不存在完全一致的情况。
- 查看索引构建日志，确认新增的校准记录与变更履历文档被正确纳入索引队列。
- 测试混合检索的响应时长，确认符合业务需求的阈值设定。
