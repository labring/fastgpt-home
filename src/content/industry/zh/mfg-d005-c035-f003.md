# 热处理的投标文稿与报价编制：多轮对话与提示词

## 这个品类的数据长什么样
热处理相关数据来源于材料牌号、客户技术条件、温控仪表、炉温均匀性测试、硬度计与金相设备、MES系统。数据更新频率为每炉次、每批，日常文档包含热处理工艺卡、装炉图、炉温曲线、硬度与金相报告、设备点检表、异常处置单。数据字段包含材料牌号、加热温度、保温时长、冷却速率、硬度值等，对应单位为摄氏度、小时、HV等。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
每炉次的高频更新要求对话上下文需绑定唯一项目与炉次标识，防止不同批次数据串用。多类型专业文档需要提示词明确区分不同文档的使用场景，避免模型混淆工艺参数与检测结果。字段与专业单位的特殊性要求提示词强制模型严格遵循格式规范，防止出现单位错误或参数偏差。同时，出错后果严重的特性要求多轮对话中需增加参数核对环节，确保加热保温冷却制度、装炉位置等核心信息准确无误。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文长度 | 8000–12000 token | 热处理单批投标涉及多份工艺文档与参数，需容纳完整对话与业务数据 |
| 单次搜索上限 | 前5条 | 单批次热处理相关数据条目有限，过多结果会分散模型注意力 |
| `variables` | 绑定当前项目的材料牌号、客户技术要求 | 通过预设变量传递固定业务参数，避免重复输入且保证数据准确性 |
| `messages` | 保留前3轮核心交互内容 | 过多历史对话会稀释当前报价编制的关键信息，前3轮可覆盖需求确认与参数核对 |
| `chatId` | 绑定当前投标项目的唯一标识 | 通过对话ID隔离不同项目的上下文，防止数据串用 |
| 问题优化开关 | 开启 | 针对专业术语较多的热处理参数，优化提问表述以提升模型理解精度 |

## 容易做错的三处
- 现象：对话过程中无流式输出，界面仅显示最终完整结果，未逐字展示生成进度。原因：未开启流式响应配置，或模型调用链路未正确启用流式传输。
- 现象：模型输出的投标文稿中出现多余空格、字母大写错误，与原始文档的字符格式不符。原因：提示词未明确要求严格遵循原始文档的字符与格式规范，或知识库匹配时引入了无关格式数据。
- 现象：无法调起文件解析工具读取热处理工艺卡、炉温曲线等文档内容。原因：未配置对应文档类型的解析规则，或文件上传格式超出平台支持范围。

## 怎么确认配好了
- 在FastGPT v4.17.0环境下，发起包含单炉次热处理参数的测试对话，检查模型是否能准确调用预设的`variables`参数生成符合要求的报价初稿。
- 测试流式输出功能，确认对话过程中逐字显示生成内容，无延迟或卡顿现象。
- 导入一份热处理工艺卡与炉温曲线，检查模型是否能正确解析文档内容并匹配当前业务需求。
- 查看历史对话记录，确认非业务交互的插件调用内容未被纳入上下文记忆。
