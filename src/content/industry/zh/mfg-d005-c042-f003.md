# 石油炼制的投标文稿与报价编制：多轮对话与提示词

## 这个品类的数据长什么样
石油炼制业务的数据来源覆盖DCS/APC控制系统、LIMS化验系统、罐区计量系统、原油评价数据库、设备管理系统与能源管理系统。数据更新节奏包含实时工艺参数、每班交接班记录、每日生产方案与物料平衡报表。日常文档涵盖操作规程、装置联锁台账、馏出口质量报告、变更管理文件等，不同文档对应生产运行、工艺、调度等部门的使用需求，字段包含原油密度、装置负荷、产品馏程、罐区液位等带明确单位的参数。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
由于数据来源分散且更新节奏差异明显，多轮对话需区分实时调用的工艺参数与历史归档的台账文档，避免混淆不同周期的数据。多类型文档的结构差异要求提示词需适配不同字段的提取规则，例如从原油评价报告中提取密度参数与从联锁台账中提取设备编号需不同的引导逻辑。多套装置通过物流与能源网络耦合的业务特性，要求对话上下文需持续跟踪装置间的物料流转关系，确保投标报价中的负荷协调与成本核算准确。每日更新的生产方案与变更文件，要求对话上下文的有效周期需匹配业务更新频率，避免使用过期数据生成投标内容。

## 配置怎么定
本配置基于FastGPT v4.17.0版本设定。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文长度 | 8000–12000 token | 适配炼油业务多文档拼接后的总长度，避免超出模型输入限制 |
| 历史消息保留条数 | 前20条对话 | 匹配每班交接班记录的更新周期，过滤冗余历史干扰当前投标计算 |
| `variables`绑定 | 绑定实时工艺参数与罐区计量字段 | 确保多轮对话中可调用最新的原油性质、装置负荷等动态数据 |
| `messages`上下文过滤 | 仅保留近72小时的交互记录 | 匹配每日更新的生产方案与变更管理文件的有效周期 |
| 附件上传超时 | 120秒 | 适配大型原油评价报告、联锁台账等大文件的上传需求 |
| 对话回复格式 | 强制JSON结构 | 便于投标报价系统自动提取关键参数与成本数据 |

## 容易做错的三处
- 对话历史多出一条额外记录 | 未正确使用`chatId`参数绑定固定会话，每次API调用生成独立上下文，导致历史记录重复累加。
- 对话回复无法按要求返回JSON格式 | 提示词未明确指定JSON结构的字段要求，或未在配置中开启强制格式校验，导致回复格式不符合业务系统提取规则。
- 附件上传提示`fail to create post presigned url` | 从4.13.0升级到4.14.3后未重新配置附件存储的权限参数，或上传的原油评价报告等文件超出当前允许的大小范围。

## 怎么确认配好了
- 发起两次连续的API调用，检查`messages`参数返回的历史记录条数是否符合设定的保留规则，无额外累加的会话内容。
- 上传一份模拟原油评价报告，确认附件上传无报错，且在后续对话中可正确引用报告中的参数内容。
- 发送要求返回JSON格式的指令，验证回复内容符合指定的字段结构，可被业务系统自动解析。
- 点击对话回复的点赞按钮，检查业务系统是否能接收到对应的反馈数据，完成记录同步。
