# 钢材轧制与精整的投标文稿与报价编制：向量模型与索引

## 这个品类的数据长什么样
该品类数据来源于板坯或钢坯批次、加热炉、轧机自动控制系统、在线测厚测宽设备、表面检测装置与MES系统。日常文档包含轧制计划、加热制度、轧制规程、板形厚度记录、表面质量报告、质保书，字段涵盖卷号、批次号、加热温度、压下率、厚度偏差、表面缺陷等级等，单位涉及摄氏度、毫米、微米等。数据更新频率为每卷或每支实时更新，单份文档体量随轧制批次规模变化。

## 这些特征在「向量模型与索引」这一环带来什么约束
实时更新的单卷级数据要求索引支持增量同步，避免全量重建带来的性能损耗。多字段的工业专业术语与专用单位，要求向量模型适配轧制相关的专业语义，确保嵌入精度。投标文稿需关联轧制计划、质保书等多类文档，索引需支持跨文档的关联检索逻辑。单份文档体量随批次变化，分块策略需适配不同长度的轧制相关文档，避免分块过碎或过长影响检索效果。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配单卷轧制记录的文档长度，避免分块过碎丢失专业语义关联 |
| 重叠长度 | 100–150 字符 | 保留相邻分块的轧制批次上下文，防止跨分块的专业逻辑断裂 |
| 相似度阈值 | 0.72–0.80 按实测标定 | 过滤低匹配度的非轧制相关文档，确保检索结果贴合投标需求 |
| 单次搜索上限 | 前 10 条 | 控制检索结果体量，适配投标文稿的多文档关联检索场景 |
| `defaultToken` | 2048 | 适配轧制规程等长文档的嵌入长度，满足专业术语的完整语义 |
| `maxToken` | 按所选嵌入模型/服务支持的最大输入 token 数设置 | `maxToken` 表示所选嵌入模型/服务支持的最大输入 token 数；请按模型或服务配置核对，参见 [FastGPT v4.17.2 模型字段说明](https://github.com/labring/FastGPT/blob/v4.17.2/document/content/self-host/config/model/intro.mdx)。它不是检索/LLM 上下文，也不是 FastGPT 全局固定上限。 |

## 容易做错的三处
- 出现503状态码，提示当前分组下text-embedding-v3无可用渠道。原因是未正确配置嵌入模型的渠道资源，或渠道配额使用完毕。
- 启动后无法调用向量模型，提示API密钥缺失。原因是未通过docker-compose配置CHAT_API_KEY环境变量，仅需重启容器即可生效，无需重建镜像。
- 检索结果无法关联到具体轧制批次的质保书。原因是未设置合理的重叠长度，导致跨分块的批次关联信息丢失。

## 怎么确认配好了
- 进入FastGPT v4.17.0的向量索引管理页面，查看索引的分块长度与重叠长度是否与配置一致。
- 提交一条包含轧制温度关键词的测试查询，查看返回结果的相似度分布是否符合设置的阈值区间。
- 导入一份单卷轧制记录文档，验证索引是否支持增量更新，无需全量重建即可完成同步。
- 检查容器环境变量配置，确认CHAT_API_KEY已正确加载，无503类的模型渠道报错。
