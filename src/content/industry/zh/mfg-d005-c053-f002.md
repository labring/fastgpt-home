# 钢铁冶炼与连铸的投标文稿与报价编制：向量模型与索引

## 这个品类的数据长什么样
本品类数据来自铁水与废钢数据台账、L2过程控制系统、化验室成分报告、MES生产管理系统、能源介质监控系统及设备状态监测终端。日常文档包含炉次计划、配料单、转炉冶炼记录、成分检测报告、连铸工艺参数记录、板坯质量判定单。数据更新节奏为每炉次实时生成，关键工艺参数随生产进程同步更新，每班汇总归档。文档字段包含碳含量、出钢温度、浇次编号、板坯厚度等，附带对应检测单位与工艺参数单位。

## 这些特征在「向量模型与索引」这一环带来什么约束
数据实时更新且按炉次、浇次生成，要求索引支持增量同步，避免全量重建，减少生产间隙的时间占用。文档包含大量工业专业术语与带单位的工艺参数，要求向量模型适配工业流程文本语义，避免通用模型的语义偏差。数据字段关联强且存在明确的生产时序，要求索引支持按炉次编号、浇次时间等元数据过滤检索，缩小召回范围。单次投标涉及多炉次、多浇次的历史数据，要求索引的召回效率匹配投标编制的时间要求。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配单炉次工艺记录的文本长度，避免单块包含跨炉次的无关数据 |
| 重叠长度 | 50–100 字符 | 保留相邻炉次记录的关联语义，防止关键工艺参数被分块截断 |
| 相似度阈值 | 0.75–0.85 | 过滤低匹配度的历史数据，避免投标文稿混入无关炉次记录 |
| 单次搜索上限 | 前 10 条 | 控制召回数据量，适配投标编制的快速检索需求 |
| `maxToken` | 4096 token | 适配工业专业文本的嵌入长度要求，避免语义截断 |
| `defaultToken` | 按实测标定 | 适配当前部署的向量模型的默认上下文参数，保证嵌入一致性 |

本页面适配 FastGPT v4.17.0 版本。

## 容易做错的三处
- 现象：配置千问text-embedding-v3模型后，界面提示无可用渠道，日志显示分组default下的API调用失败。原因：未在OneAPI中配置对应模型的渠道权限，或分组default未绑定该模型的API密钥。
- 现象：知识库问答环节检索耗时过长，重排后结果返回延迟。原因：分块长度设置过大导致单块文本过长，或`maxToken`配置不合理，增加了向量检索与重排的计算量。
- 现象：检索结果中混入非连铸工序的板坯判定单数据。原因：未配置按工序类型、炉次编号的元数据过滤规则，导致召回范围过大。

## 怎么确认配好了
- 上传单条典型转炉冶炼记录，执行向量嵌入测试，查看嵌入日志无文本截断报错，确认嵌入配置适配当前文本长度。
- 发起包含特定炉次编号的检索请求，查看召回结果是否仅包含对应炉次的关联文档，确认元数据过滤规则配置生效。
- 配置测试用的向量模型，发起批量嵌入测试，查看同步耗时是否适配生产间隙的时间窗口，确认增量同步配置有效。
- 查看系统嵌入模型管理界面，确认目标模型已绑定至当前使用分组，无渠道异常提示。
