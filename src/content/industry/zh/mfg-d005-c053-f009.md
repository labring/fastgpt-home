# 钢铁冶炼与连铸的投标文稿与报价编制：模型接入与配置

## 这个品类的数据长什么样
该品类的数据来源于铁水与废钢投料记录、L2过程控制系统数据、化验室成分报告、制造执行系统（MES）、能源介质监控系统及设备状态台账。日常文档包含炉次计划、配料单、转炉冶炼日志、钢水成分报告单、连铸工艺参数记录、板坯质量判定单。数据更新频率覆盖每炉次生成的实时记录、每班汇总的调度数据，字段包含炉号、钢种、成分含量、目标温度、浇次时长等，单位涵盖吨、摄氏度、百分比、分钟等。

## 这些特征在「模型接入与配置」这一环带来什么约束
数据来源分散且更新频率差异大，实时炉次数据需快速接入，需适配多系统的字段格式差异，避免数据错位。文档结构固定但字段数量较多，需精准匹配投标文稿所需的冶炼、连铸参数，防止无关数据混入上下文影响内容准确性。高温连续流程的业务特性要求模型响应不能出现过长延迟，否则影响投标报价的时效性，且该场景下炉次与浇次耦合性强，模型生成的内容需严格关联对应炉次信息，避免引发后续生产调度的连锁问题。板坯判定单等质量数据需严格关联对应炉次信息，模型接入时需保留字段关联关系，防止数据错位导致报价偏差。同时，投标场景需整合多源业务数据生成合规文稿，对模型的上下文承载能力与数据筛选能力提出了明确要求。

## 配置怎么定
本页配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `maxContext` | 8000–12000 token | 需容纳多炉次的配料、冶炼、连铸历史数据，支撑投标报价的工艺参数参考，避免关键业务上下文被截断 |
| `maxTokens` | 3000–4000 token | 适配投标文稿与报价单的标准篇幅需求，平衡生成速度与内容完整性 |
| `temperature` | 0.2–0.4 | 保持报价与文稿的严谨性，避免生成不符合钢铁工艺规范的随意内容 |
| `toolChoice` | auto | 自动调用内部工具检索实时工艺与原料数据，适配投标时的动态参数调整需求 |
| `vision` | 关闭 | 该场景主要基于结构化业务数据与文本文稿，无需多模态图像或视频识别功能 |
| `AIPROXY_API_ENDPOINT` | 按企业内网部署地址填写 | 适配钢铁企业内部数据安全要求，避免外部接口泄露核心工艺数据 |

## 容易做错的三处
- 现象：模型生成的SQL查询语句无法正确关联炉次数据，查询结果包含无关字段。原因：未针对钢铁行业的炉次、浇次字段配置精准的检索规则，导致SQL生成逻辑不符合业务需求。
- 现象：工具调用的中间执行日志直接出现在最终投标文稿中。原因：未正确配置工具调用的输出隐藏规则，非预期的中间步骤被包含在生成结果内。
- 现象：开启多模态功能后无法识别板坯照片中的缺陷标识，或联网检索无法获取内网原料价格数据。原因：未关闭`vision`参数且模型未适配工业图像格式，或未关闭联网检索配置导致无法访问内网专用接口。

## 怎么确认配好了
- 导入单炉次的配料单与成分报告，核对生成的文稿是否准确匹配对应字段的数值与单位。
- 发起模拟投标报价请求，查看工具调用日志是否仅显示最终结果，无中间执行步骤。
- 测试多源数据接入，确认生成的文稿中未混入无关炉次的工艺数据。
- 验证内部接口访问权限，确认核心生产数据未被外部接口泄露。
