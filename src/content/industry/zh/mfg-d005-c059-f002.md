# 预拌混凝土生产的投标文稿与报价编制：向量模型与索引

## 这个品类的数据长什么样
预拌混凝土生产的核心数据来自商品混凝土搅拌站、工程项目试验室及质量调度部门，日常文档包含配合比通知单、开盘鉴定、生产运输单、原材料检验报告、试块记录与强度报告。数据来源涵盖工程订单、砂石水泥外加剂检验结果、骨料含水率测定数据、搅拌站控制系统记录与试验室台账。数据更新频率为每车生产记录、每批原料检验批次、每日台账汇总，字段涉及骨料含水率、用水量、浇筑方量、试块强度值等，单位匹配行业通用的立方米、千克、兆帕等标准计量方式。

## 这些特征在「向量模型与索引」这一环带来什么约束
预拌混凝土生产的高频更新特性要求索引支持增量入库，避免全量重索引带来的资源消耗。多类型文档的混合存储（结构化表格与半结构化文本）要求分块逻辑适配不同文档结构，防止拆分关键业务参数。投标文稿需关联订单、生产、检验多维度数据，索引需支持跨文档关联检索，确保报价参数的完整性。单批次数据量随工程规模扩大而增长，需平衡入库效率与检索准确性，避免因批量处理过载导致的任务失败。本页面适配FastGPT v4.17.0版本。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 匹配配合比通知单、生产运输单的单页内容长度，避免拆分关键参数 |
| 重叠长度 | 50–80 字符 | 保留跨块的坍落度、含水率等关键参数，防止检索断档 |
| `defaultToken` | 4096 | 适配投标文稿汇总后的长文本上下文，满足多文档拼接需求 |
| `maxToken` | 按所选嵌入模型/服务支持的最大输入 token 数设置 | `maxToken` 表示所选嵌入模型/服务支持的最大输入 token 数；请按模型或服务配置核对，参见 [FastGPT v4.17.2 模型字段说明](https://github.com/labring/FastGPT/blob/v4.17.2/document/content/self-host/config/model/intro.mdx)。它不是检索/LLM 上下文，也不是 FastGPT 全局固定上限。 |
| 单次入库上限 | 500 条/次 | 匹配每批次原料检验、生产记录的批量更新节奏，降低入库压力 |
| 相似度阈值 | 0.75–0.85 | 区分合格与异常的试块强度、配料数据，确保投标报价的参数准确性 |

## 容易做错的三处
- 现象：向量入库耗时过长，页面加载进度停滞超10分钟。原因：未调整分块长度与单次入库上限，批量处理超量的每车生产记录导致资源占用过高。
- 现象：上传10万条csv格式的原料检验数据后，向量入库后仅显示9万余条，缺失数千条记录。原因：部分记录包含未转义的特殊字符（如原料名称中的破折号），导致解析失败未入库，未开启csv格式校验开关。
- 现象：本地运行向量索引正常，打包为Docker镜像后所有检索结果的相似度得分完全一致。原因：镜像中未正确挂载向量模型的缓存文件，导致所有文本调用了默认的随机向量生成逻辑，未加载实际模型参数。

## 怎么确认配好了
- 上传单份配合比通知单文档，执行关联检索，检查返回结果是否包含对应的原材料检验记录与生产运输单。
- 批量上传当日的生产记录与检验数据，核对入库条数与源数据条数是否一致，确认无记录缺失。
- 模拟投标报价的检索请求，检查返回的参数（如用水量、骨料含水率）是否符合业务逻辑，无明显断档或截断。
- 启动Docker容器后，执行向量模型加载测试，确认控制台无模型缺失报错，检索结果的相似度得分存在合理差异。
