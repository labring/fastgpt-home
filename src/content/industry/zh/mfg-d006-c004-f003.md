# 仓储、批次与厂内物流的检验与过程记录审核：多轮对话与提示词

## 这个品类的数据长什么样
该品类的数据通常来自ERP/WMS系统、条码或RFID采集设备、采购工单、库位台账、AGV输送系统与称重设备。日常文档包含收货单、上架单、领退料单、移库单、盘点表、批次台账与效期记录。数据更新节奏分为实时（如库位变动、称重数据）、每日（如领退料统计）与月度（如全盘库存）。核心字段包含物料编码、批次号、库位号、检验状态、效期与库存数量，单位涵盖件、千克、立方米等。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
该品类数据来源分散且更新节奏不一，多轮对话需同时关联ERP的批量台账与实时采集的库位变动数据，需通过上下文记录当前工单与批次的关联关系。文档字段多且格式不统一，提示词需明确指定需提取的字段与校验规则，避免混淆不同单据的信息。跨工序的物料流向管理要求对话保留历史检验与移库记录，过长的上下文会增加推理负担，需合理截断非核心历史内容。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本。
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文长度 | 8000–12000 字符 | 该品类需覆盖批次台账、库位记录、领退料单等多份历史文档的信息，足够的上下文可确保对话逻辑连贯 |
| `chatId` 绑定规则 | 绑定当前工单关联的对话ID | 需限定对话上下文仅关联当前工单的批次与库位数据，避免跨工单的信息干扰 |
| `variables` 加载范围 | 加载前3条历史对话的全局变量 | 该品类核心变量为批次号、库位号与效期，少量历史变量可平衡上下文完整性与推理效率 |
| `messages` 上下文截断阈值 | 超过10轮对话自动截断最早的非核心记录 | 厂内物流数据更新频繁，过长的对话历史会降低响应速度，截断非核心单据可优化性能 |
| 提示词模板字段校验 | 按实测标定 | 需匹配收货单、盘点表等不同单据的字段格式，确保提取的信息准确对应业务需求 |

## 容易做错的三处
- 现象：调用MySQL工具时返回400 status code (no body)，原因：未正确绑定ERP/WMS数据源的全局变量，导致请求参数缺失。
- 现象：免登录链接用户删除对话后，后台日志同步清除，原因：未开启对话日志持久化配置，导致历史检验记录无法追溯。
- 现象：多轮对话中无法加载历史全局变量，原因：未将`variables`绑定范围限定为当前工单，导致跨对话的批次与库位信息混淆。

## 怎么确认配好了
- 发起包含指定物料编码与批次号的查询，确认对话能返回对应库位、效期与检验状态的历史记录。
- 测试删除单条对话内容，检查后台日志是否保留该对话的完整操作记录。
- 调用MySQL工具，确认能正常获取ERP系统中的批次台账与库存数据。
- 发起跨工单的多轮查询，确认对话不会混淆不同工单的物料与库位信息。
