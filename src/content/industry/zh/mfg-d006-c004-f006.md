# 仓储、批次与厂内物流的检验与过程记录审核：引用来源与溯源

## 这个品类的数据长什么样
该品类数据主要来自ERP、WMS系统、条码/RFID设备、采购工单、库位档案、AGV输送系统与称重设备。日常文档包含收货单、上架单、领退料单、移库单、盘点表、批次台账、先进先出与效期记录，字段涵盖物料编码、批次号、库位号、检验状态、效期、数量单位等。数据更新节奏分为实时（如库位变动、称重数据）、每日（如领退料记录）与月度盘点（如库存对账数据）。

## 这些特征在「引用来源与溯源」这一环带来什么约束
多源异构的数据来源要求引用溯源环节能关联ERP的工单数据、WMS的库位记录与硬件采集的条码信息，避免单源数据的片面性。批次与效期相关的字段较多，需要在溯源时精准匹配批次号、检验状态等关键属性，确保物料流向可追溯。不同更新节奏的数据需要适配的索引策略，实时变动的库位数据需即时更新索引，月度盘点数据则需定期同步，保障溯源结果的时效性。同时，错料、停线等出错后果要求溯源环节的引用必须完整覆盖关联单据，不能遗漏关键记录。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的界面逻辑。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 最大上下文 | 8000–12000 token | 适配多源单据的文本长度，覆盖收货单、批次台账等文档的完整内容 |
| 知识库最大引用 | 前6条 | 匹配仓储场景下单工单关联的单据数量，避免冗余信息干扰 |
| `quoteMaxToken` | 1500–2000 字符 | 限制单条引用的文本长度，确保响应内容聚焦关键物料与批次信息 |
| 最大响应tokens | 3000–4000 token | 平衡溯源结果的完整性与响应速度，适配多单据的汇总说明 |
| `responseData` | 开启 | 保留引用来源的元数据，便于后续核对物料的检验状态与批次信息 |
| `detail` | 开启 | 展示引用文档的具体字段，如库位号、效期等，满足仓储场景的精准溯源需求 |

## 容易做错的三处
- 配置`quoteMaxToken`取值过小，导致单条引用被截断，出现部分批次号、效期字段缺失的现象，原因是未适配仓储单据的文本长度要求。
- 未合理配置元数据保留规则，导致返回结果中携带无关的搜索日志字段，用户反馈引用信息碍事，原因是未明确保留必要的引用来源范围。
- 知识库选择时未配置变量引用，导致无法动态匹配工单对应的批次号，出现搜索结果与当前业务场景不匹配的现象，原因是未绑定工单变量与知识库检索条件。

## 怎么确认配好了
- 输入一个真实的物料批次号，检索关联的单据，检查返回结果中是否包含批次台账、领退料单等对应文档的引用。
- 查看响应内容的元数据部分，确认是否包含引用来源的文档类型、字段信息，验证`responseData`与`detail`配置是否生效。
- 调整`quoteMaxToken`的取值，测试不同长度的单据引用是否被完整展示，确认取值符合当前业务的文档长度需求。
- 绑定工单变量到知识库检索条件，测试动态匹配不同批次号的检索结果是否正确。
