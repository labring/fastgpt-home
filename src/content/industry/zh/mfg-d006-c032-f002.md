# 汽车整车总装的检验与过程记录审核：向量模型与索引

## 这个品类的数据长什么样
这个品类的核心数据以车辆识别码（VIN）为唯一主线，数据来源包括ERP、MES系统、VIN与配置系统、拧紧工具、EOL检测线及质量追溯系统。日常文档涵盖生产订单、VIN清单、装配作业指导书、拧紧数据、下线检测报告、返修记录与一致性放行文件。数据更新频率为每车实时生成、每班批量汇总，单份整车关联文档包含数百项配置与检测字段，部分字段带有明确单位，如扭矩值单位为牛米，检测阈值单位为百分比。

## 这些特征在「向量模型与索引」这一环带来什么约束
以VIN为核心的单车主线数据要求索引需支持按VIN快速过滤关联文档，避免跨车辆数据干扰。实时更新的生产与检测数据要求索引支持增量同步，避免全量重建带来的性能损耗，使用固态硬盘存储向量索引可进一步降低实时检索的性能损耗。单车辆数百项配置与检测字段的文档结构，要求分块逻辑需贴合工位或工序划分，避免跨内容的向量混淆。同时，检验与审核环节的出错后果严重，要求向量检索的召回率与匹配精度需满足业务校验标准，不能出现漏配、错配的检索结果。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本的界面与参数逻辑，其中`maxToken`与`defaultToken`用于控制检索上下文的长度。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 贴合装配作业指导书、拧紧数据单条内容的平均长度，避免单块内容跨工序 |
| 重叠长度 | 100–200 字符 | 覆盖跨工位的工序关联信息，保证检索时能关联到前后工位的操作记录 |
| `maxToken` | 4000 token | 匹配单份整车下线检测报告的最大内容长度，保证完整上下文被纳入检索 |
| `defaultToken` | 1500 token | 适配单工位拧紧数据、返修记录的常规内容长度，平衡检索效率与信息完整性 |
| 相似度阈值 | 0.75–0.85 | 按实测标定，匹配检验审核环节对配置匹配、缺陷识别的精度要求 |
| 单次搜索上限 | 前20条 | 对应单VIN关联的配置项、检测项数量上限，避免无效结果过多 |

## 容易做错的三处
- 现象：混合检索响应时间超过10秒，单次检索耗时明显高于纯向量检索。原因：未针对VIN为核心的单车主线数据优化索引分片，且未使用固态硬盘存储向量索引，混合检索同时调用多数据源向量库导致计算负载过高。
- 现象：建索引过程卡在最后一组索引步骤，长时间无进度更新。原因：未开启增量索引模式，全量索引时批量导入了单批次全量VIN数据，超出系统单任务处理阈值。
- 现象：知识库无法正确导入拧紧数据、下线检测报告等文件。原因：未提前配置对应文件类型的解析插件，仅支持了通用文档格式。

## 怎么确认配好了
- 查看系统检索日志，确认单条VIN相关的检索响应时间符合预期。
- 测试导入单份VIN清单、拧紧数据文件，确认索引创建过程无卡顿。
- 验证不同文件类型的解析结果，确认VIN码、扭矩值等核心字段完整提取。
- 调整相似度阈值，检索结果的匹配精度符合业务检验与审核的校验需求。
