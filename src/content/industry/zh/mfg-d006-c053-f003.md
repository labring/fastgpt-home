# 钢铁冶炼与连铸的检验与过程记录审核：多轮对话与提示词

## 这个品类的数据长什么样
钢铁冶炼与连铸的过程数据来源包括铁水与废钢录入数据、L2过程控制实时数据、化验室成分报告、MES系统调度记录、能源介质与设备状态数据。数据更新节奏按炉次、实时、每班划分，日常文档涵盖炉次计划、配料单、转炉冶炼记录、成分报告、连铸工艺记录、板坯判定单。文档字段包含炉次号、浇次编号、终点温度、成分含量、拉速参数、缺陷类型等，单位涉及摄氏度、毫克每升、米每分钟等。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据按炉次、实时、每班更新，要求多轮对话需绑定`chatId`关联对应炉次的上下文，避免跨炉次数据混淆。文档包含大量专业冶金字段，提示词需明确限定检索范围为指定的冶炼与连铸专属文档，防止引入无关的非流程数据。单炉次数据随流程推进逐步累积，需限制对话上下文的token长度，防止超出模型处理上限。实时数据的时效性要求，提示词需优先召回最新的L2过程控制数据，确保审核结果匹配当前生产状态。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `chatId` | 绑定当前炉次的唯一16位标识字符串 | 确保多轮对话仅关联对应炉次的过程记录，避免跨炉次数据干扰 |
| `messages` | 限制上下文为前10轮对话+当前炉次的核心文档 | 防止上下文过长超出模型处理能力，同时保留关键对话与过程数据 |
| `variables` | 注入当前炉次的炉号、浇次号、计划成分范围 | 让模型精准匹配当前冶炼环节的参数，缩小检索范围 |
| 最大上下文长度 | 8000–12000 token | 适配单炉次从配料到连铸的完整过程数据量，避免截断关键信息 |
| 单次召回文档数 | 前6条匹配文档 | 平衡召回精度与模型处理耗时，符合钢铁冶炼流程的实时性要求 |
| 提示词模板 | 限定仅检索钢铁冶炼与连铸的专属文档，返回结果需附带来源片段 | 确保对话内容仅基于指定业务数据，提升审核准确性 |

## 容易做错的三处
- 现象：刷新页面后弹出“检测到没有可用的索引模型”报错。原因：未将钢铁冶炼与连铸的专属文档库绑定至当前对话agent，或索引更新未完成。
- 现象：对话返回结果未附带来源文档的原文片段与关联信息。原因：未在配置中开启来源引用展示，或提示词未明确要求返回对应文档的字段与来源。
- 现象：跨炉次调用对话时，返回了非当前炉次的过程记录数据。原因：未通过`chatId`绑定当前炉次的唯一标识，导致上下文调用了历史炉次的文档数据。

## 怎么确认配好了
- 发起针对当前炉次配料单的提问，验证返回结果包含对应炉号的配料比例与铁水成分数据。
- 检查对话历史中是否附带每条结果的来源文档名称与片段，确认来源展示功能正常。
- 切换至其他炉次的`chatId`发起提问，验证返回数据仅关联当前炉次的过程记录。
- 在FastGPT v4.17.0版本的环境中，等待10分钟后再次发起相同提问，验证实时更新的L2过程数据是否被正确召回。
