# 钢材轧制与精整的生产台账汇总与报告生成：知识库检索与召回

## 这个品类的数据长什么样
典型主体包含热轧、冷轧、型钢、钢管企业，日常文档涵盖轧制计划、加热制度、轧制规程、板形厚度记录、表面质量报告、质保书。数据来源为板坯或钢坯批次、加热炉、轧机自动控制、在线测厚测宽、表面检测、MES系统。更新频率为每卷或每支、实时。数据字段包含批次号、加热温度、轧制速度、厚度偏差、表面缺陷等级、质保书编号等，单位涵盖摄氏度、米每秒、毫米、平方米等，卷级追溯特征明显，单条记录常关联多工序的连续数据。

## 这些特征在「知识库检索与召回」这一环带来什么约束
卷级实时更新的特性要求知识库支持增量同步与精准批次关联，避免跨批次数据混淆。多工序关联的文档结构要求检索需同时覆盖精确字段（如批次号）与语义描述（如轧制规程），单一检索模式无法满足需求。单卷数据量较大且更新频繁，需限制单次检索的结果条数与上下文长度，避免超出模型处理上限。部分文档如表面质量报告、质保书的文本长度较长，需适配长文本的分块与召回逻辑。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `similarity` | 0.75–0.85 | 匹配轧制规程、厚度记录这类专业文档，保证召回精度同时覆盖同批次的关联数据 |
| `limit` | 前10条 | 单卷台账关联的文档数量较多，限制条数避免上下文拼接超出模型承载上限 |
| `searchMode` | `embedding` | 使用语义/向量召回；精确字段、元数据、批次和文档类型条件需另行配置过滤，不能由该模式保证。 |
| `usingReRank` | 开启 | 对初始召回的结果按相关性重排，过滤无关的表面质量报告或非本批次数据 |
| `datasetSearchUsingExtensionQuery` | 开启 | 自动扩展批次号相关的检索词，关联同批次的加热、轧制、检测等全工序数据 |
| `collectionIds` | 按轧制工序分组的知识库集合 | 区分热轧、冷轧、型钢等不同工序的文档，缩小检索范围，提升召回效率 |

## 容易做错的三处
- 现象：设置单块文本上限为1500字符后，超过该长度的轧制台账文档块仍被召回并参与上下文引用。原因：未正确配置分块策略，或检索时未按块大小过滤，导致超长块直接进入上下文拼接。
- 现象：批量导入多批次台账数据时，系统卡住，Ollama日志显示“try reducing the size of the batch”。原因：批量导入的单批次数据量过大，未调整批量处理参数，导致内存溢出。
- 现象：将知识库检索结果传入HTTP接口处理后，AI对话无法正确引用检索到的文档内容。原因：未传递检索结果的文档ID、原文片段、相似度得分等核心字段，格式不符合要求。

## 怎么确认配好了
- 上传单卷完整的轧制规程文档，输入对应批次号进行检索，验证能召回同批次的加热制度、板形厚度记录等关联文档。
- 查看检索日志，确认召回结果的条数不超过配置的`limit`值，且重排后的结果相关性符合预期。
- 触发批量导入10卷以上的台账数据，检查是否出现批量处理卡住的情况，确认批量参数适配当前数据规模。
- 上传一段长度超过2000字符的表面质量报告，验证检索时能正确分块并参与上下文拼接，不会出现截断报错。
