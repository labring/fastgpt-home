# 预制混凝土构件的生产台账汇总与报告生成：向量模型与索引

## 这个品类的数据长什么样
本品类数据来自预制混凝土构件工厂，涵盖PC构件、管桩、桥梁构件及市政制品等产品。日常产生的文档包括构件深化图、钢筋下料单、模具检验记录、浇筑振捣记录、养护记录及脱模出厂检验报告。数据来源覆盖BIM或深化设计文件、钢筋与混凝土批次信息、模台与养护窑运行数据、试验室检测结果及二维码追溯系统。数据更新频率按单件、每批或每窑执行，单份文档包含构件尺寸、用料参数、生产流程记录等多维度字段。

## 这些特征在「向量模型与索引」这一环带来什么约束
多来源的异构文档类型要求向量索引需按文档类别分类存储，避免深化图与下料单的语义混淆。按单件、每批或每窑的高频更新节奏，需要配置增量索引更新策略，避免全量重建带来的资源占用与耗时。单份深化图的长文本内容，要求分块规则需适配长文档拆分，避免语义断裂影响检索精度。关键字段如预埋位置、强度参数的向量表示需精准匹配业务逻辑，否则会导致台账汇总错误，引发后续生产问题。

## 配置怎么定
本配置基于FastGPT v4.17.0版本制定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `defaultToken` | `2048` | 预制混凝土构件的深化图、下料单等单页文档的token量适配该参数上限，避免文本截断 |
| `maxToken` | `4096` | 生产台账汇总需容纳多份构件的关联记录，该参数适配长上下文的汇总需求 |
| 分块长度 | `800–1200 字符` | 适配预制混凝土构件文档的平均字符量，拆分后可保留完整的构件尺寸、用料等语义单元 |
| 相似度阈值 | `0.75–0.85` | 精准匹配同批次、同构件的台账数据，避免误关联不同模台或养护窑的生产记录 |
| 单次召回上限 | `前10条` | 单批次构件的台账记录数量有限，该取值可平衡检索效率与召回完整性 |
| 索引更新策略 | 按批次触发 | 匹配数据按单件、每批、每窑的更新频率，平衡索引实时性与系统资源占用 |

## 容易做错的三处
- 批量添加索引时返回参数错误，状态码为400。原因是未按照预制混凝土构件台账的字段结构配置批量请求参数，误将单文档参数用于集合级别的批量索引操作。
- 检索结果包含跨养护窑的构件记录，部分字段为空。原因是未配置按模台、养护批次的过滤规则，导致统一索引下的不同生产批次数据被误召回。
- 通过MongoDB直接管理向量库时出现索引同步延迟。原因是未配置向量库与MongoDB的同步机制，直接修改MongoDB中的生产记录未触发向量索引的自动更新。

## 怎么确认配好了
- 上传单份构件深化图，检查分块后的文本片段与原文档的语义匹配度，确认分块长度符合配置要求。
- 发起批量索引请求，检查返回结果的参数格式与配置项一致，无报错信息返回。
- 检索同批次构件的台账记录，确认召回结果仅包含目标批次的数据，无跨批次的无关记录。
- 修改MongoDB中的某条养护记录，等待指定时长后检查向量索引是否同步更新，确认索引更新策略生效。
