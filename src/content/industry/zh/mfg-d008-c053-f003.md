# 钢铁冶炼与连铸的设备点检与维修问答：多轮对话与提示词

## 这个品类的数据长什么样
该品类数据来源于铁水与废钢录入数据、L2过程控制数据、化验室成分报告、MES系统炉次计划、能源介质监控数据及设备状态传感数据。数据更新频率覆盖每炉次、实时及每班周期，日常文档包含炉次计划、配料单、转炉冶炼记录、成分报告、连铸工艺记录、板坯判定单。数据字段包含铁水温度（℃）、碳含量（%）、连铸拉速（m/min）、设备振动幅值（mm/s）等专业参数，单份炉次文档数据量约为1500-3000字符。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
数据实时性强且按炉次聚合，要求对话上下文需绑定当前炉次标识，避免跨炉次数据混淆。多类文档来源要求提示词需明确指定引用文档的类型与字段范围，防止检索到无关数据。每班更新的频率使得过长的历史对话会引入过时信息，需限制上下文窗口长度。出错后果严重的业务特性，要求提示词需加入异常处置的优先级判断逻辑，优先响应连铸中断、炉次报废类风险场景。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 最大上下文窗口 | 前20轮对话或8000字符，按实测标定 | 匹配单炉次文档数据量，避免引入过时的跨炉次信息 |
| 历史对话保留时长 | 7天 | 覆盖完整班次周期，满足跨班点检追溯需求 |
| `chatId` | 绑定当前炉次唯一标识 | 解决炉次耦合强的业务特性，避免不同炉次的对话数据混淆 |
| `messages` | 按炉次ID分组存储 | 便于按炉次检索历史对话记录，匹配业务数据的聚合逻辑 |
| `variables` | 填入当前炉次的配料单、成分报告字段 | 为提示词提供场景化专属参数，提升回复的针对性 |
| 上下文召回数量 | 前5条最新设备点检记录 | 匹配实时更新的设备数据特性，优先调用最新状态信息 |

## 容易做错的三处
- 现象：调用工作流后对话日志为空。原因：未通过`chatId`绑定当前炉次会话，导致会话标识混乱，日志未正确归档。
- 现象：相同提示词下回复效果与预期存在差异。原因：未在`variables`中填入当前炉次的专属工艺记录与成分数据，导致提示词缺乏场景化参数。
- 现象：配置后无法保留对话历史。原因：未设置历史对话保留时长，或系统存储路径未正确关联会话数据。

## 怎么确认配好了
- 发起新对话，输入当前炉次的点检问题，查看上下文是否包含前5轮的对话内容。
- 检查`variables`字段是否已填入当前炉次的配料单、成分报告等专属数据。
- 查看会话存储目录，确认对应`chatId`的日志文件已生成且包含近7天的对话记录。
- 调用工作流后，验证返回结果是否关联了当前炉次的工艺文档数据。
