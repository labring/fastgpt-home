# 钢铁冶炼与连铸的设备点检与维修问答：工作流编排
FastGPT v4.17.0

## 这个品类的数据长什么样
数据来源包括铁水与废钢数据、L2过程控制、化验室、MES、能源介质系统、设备状态。日常文档包含炉次计划、配料单、转炉冶炼记录、成分报告、连铸工艺记录、板坯判定单。更新频率为每炉次、实时、每班。字段包含炉次号、成分含量、设备运行参数、缺陷类型等，单位涉及温度（℃）、成分百分比、压力（MPa）、时间（小时）等。

## 这些特征在「工作流编排」这一环带来什么约束
多源且更新频率差异大的数据，要求工作流支持并行拉取不同来源的实时数据，避免单一节点阻塞整体流程。炉次与浇次强耦合的特性，要求工作流节点间具备强时序依赖，确保冶炼流程与连铸流程的节奏匹配。高频更新的文档要求工作流每次触发时拉取最新版本，避免使用过期数据影响点检与维修判断。高温连续流程无法随意停机的特性，要求工作流具备断点续跑能力，异常时保留执行状态，恢复后继续完成流程。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `variables` | 绑定炉次号、设备ID、当前班次 | 匹配钢铁冶炼按炉次、设备、班次管理的业务逻辑，精准拉取对应业务数据 |
| `nodeId` | 按冶炼-连铸-质检的顺序分配唯一ID | 匹配流程工业的强时序依赖，确保节点执行顺序符合生产流程 |
| 单次触发节点数 | 前3条 | 避免同时调用多源数据导致系统过载，适配实时更新的数据节奏 |
| 超时阈值 | 600秒 | 覆盖从数据拉取到缺陷判定的典型处理时长，避免中断高温连续流程 |
| 上下文窗口 | 800–1200字符 | 适配单炉次相关文档的平均长度，确保覆盖关键点检与维修信息 |
| 数据缓存时长 | 按实测标定的2小时 | 适配每班更新的文档节奏，避免频繁拉取增加系统负担 |

## 容易做错的三处
- 现象：工作流执行时节点顺序颠倒，导致连铸流程无法匹配炉次计划。原因：未按冶炼-连铸-质检的时序分配`nodeId`，违反强时序依赖约束。
- 现象：工作流拉取数据时返回空字段，无法生成维修建议。原因：未绑定`variables`中的炉次号，未拉取对应炉次的冶炼记录。
- 现象：工作流执行超时触发系统中断。原因：超时阈值设置过短，未覆盖高温流程的数据处理实际时长。

## 怎么确认配好了
- 触发一次工作流，查看返回的节点日志，确认节点执行顺序符合冶炼-连铸-质检的流程逻辑。
- 检查工作流的变量绑定配置，确认包含炉次号、设备ID、当前班次等核心业务字段。
- 模拟数据拉取延迟场景，验证工作流的异常处理与断点续跑能力。
- 核对工作流的超时与缓存设置，确保阈值与业务处理的实际时长匹配。
