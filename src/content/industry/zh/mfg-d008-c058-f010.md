# 预制混凝土构件的设备点检与维修问答：知识库检索与召回

## 这个品类的数据长什么样
预制混凝土构件的数据来源于BIM或深化设计文件、钢筋与混凝土批次记录、模台与养护窑运行数据、试验室检验报告以及二维码追溯系统。日常文档包含构件深化图、钢筋下料单、模具检验记录、浇筑振捣记录、养护记录、脱模与出厂检验报告。数据更新频率为每件构件、每批物料、每一窑养护批次对应更新，字段包含构件编号、钢筋规格、养护温度、脱模强度等，单位涵盖毫米、兆帕、摄氏度、小时等。

## 这些特征在「知识库检索与召回」这一环带来什么约束
预制混凝土构件的专属数据特征对检索召回环节形成多重约束：首先，高频次的单件、批次级更新要求检索索引支持近实时更新，避免召回过时的养护或检验数据；其次，混合了结构化表格（如钢筋下料单）与非结构化图纸（如深化图）的文档类型，需要兼顾关键词与语义的双重召回能力；再者，专业术语密集（如套筒预埋位置、振捣密实度），要求检索匹配具备精准的专业语义识别能力；最后，构件与现场吊装位置一一对应的关联属性，要求召回结果需绑定对应构件编号，避免跨构件的无关数据混入。

## 配置怎么定
本配置基于FastGPT v4.17.0版本制定，针对预制混凝土构件的业务特征优化如下：
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `similarity` | 0.72–0.88 | 适配预制构件专业术语的匹配精度，避免低匹配度的无关文档混入，同时覆盖专业词汇的语义偏差 |
| `limit` | 前6–10条 | 覆盖单台设备点检涉及的关联文档数量，避免上下文过长超出模型处理上限 |
| `searchMode` | `mixedRecall` | 适配深化图、下料单等结构化与非结构化文档混合的场景，兼顾关键词精准匹配与语义召回能力 |
| `usingReRank` | 开启 | 对初始召回结果进行二次排序，修正专业术语的语义匹配偏差，提升结果相关性 |
| `datasetSearchUsingExtensionQuery` | 开启 | 自动扩展点检维修相关的同义词，例如将“模台点检”扩展为“模具台检查”，覆盖更多专业表述的检索需求 |
| `collectionIds` | 按工厂专属集合配置 | 隔离不同工厂的预制构件数据，避免跨租户的无关数据被召回 |

## 容易做错的三处
- 上传钢筋下料单等表格文档后，检索“钢筋套筒位置”时无匹配结果。原因是未为表格数据开启多向量支持，仅对纯文本内容进行了向量化，无法提取表格内的结构化字段信息。
- 通过接口向知识库添加养护记录时返回参数错误。原因是未按照预制构件文档的元数据要求传入构件编号、养护窑编号等必填字段，导致接口校验失败。
- 检索结果中混入了其他工厂的预制构件数据。原因是未指定专属的`collectionIds`，导致跨租户的知识库数据被纳入召回范围。

## 怎么确认配好了
- 上传一份预制构件的钢筋下料单，检索“钢筋套筒位置”，查看检索结果是否包含表格内的对应字段内容，确认多向量支持已生效。
- 调用知识库添加接口，传入一条养护记录的元数据与文本内容，查看接口返回状态是否为成功，确认参数配置符合要求。
- 切换至不同的知识库集合，检索同一设备点检关键词，查看结果是否仅包含当前工厂的预制构件数据，确认`collectionIds`配置正确。
- 发起一次设备点检的查询，查看召回结果的数量是否在6–10条区间内，确认`limit`配置符合预期。
