# 冲压与板材成形的质量问题追溯与不良分析：数据库与运维

## 这个品类的数据长什么样
冲压与板材成形场景的数据来源包含钢卷标签与质保书、冲床和送料机运行数据、模具管理系统记录、MES系统工单、三坐标或检具的尺寸检验数据。日常关联文档包括冲压作业指导书、材料利用率表、模具点检表、首末件记录、换模台账。数据更新节奏为每卷原料、每批生产工单、每次模具更换时触发，字段涵盖原料牌号与厚度、设备运行压力与节拍、模具使用次数、检验偏差值等，单位包含毫米、牛顿、次等。

## 这些特征在「数据库与运维」这一环带来什么约束
多源异构的数据来源要求数据库同时支持时序结构化数据、非结构化文档与半结构化质检报告的存储与关联查询。高频更新节奏带来持续的写入与查询压力，需要运维环节适配连接池的动态调整。不同批次与换模操作带来的数据关联性需求，要求数据库支持跨表关联以实现不良品与原料、模具、生产参数的快速追溯。同时，质量追溯需留存长期历史数据，需规划合理的存储扩容与冷数据归档策略。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://fastgpt:pass@stamping-db:27017/fastgpt?authSource=admin` | 存储冲床运行数据、模具使用日志等时序结构化数据，适配FastGPT v4.17.0的多源数据存储框架 |
| `PG_URL` | `postgresql://fastgpt:pass@stamping-pg:5432/stamping_qc?schema=public` | 存储尺寸检验报告、换模记录等带关联关系的结构化数据，支持跨表查询追溯不良原因 |
| `DB_MAX_LINK` | `150–250 个连接` | 适配每卷料、每次换模的高频数据写入与查询请求，避免连接耗尽，取值按实测标定调整 |
| `REDIS_URL` | `redis://:stamping-redis@stamping-redis:6379/1` | 缓存高频访问的材料牌号对应参数、首末件检验基准数据，降低数据库负载 |

## 容易做错的三处
- 执行`docker build -f ./projects/app/Dockerfile`构建镜像时出现依赖包缺失报错，原因是本地开发环境的基础镜像版本与官方文档指定的FastGPT v4.17.0构建环境不一致，未预装工业数据解析相关依赖。
- 启动服务后出现 MongoDB 查询或连接错误。`mongo:4.4.29` 是 FastGPT v4.17.2 官方部署配置为不支持 AVX 的 CPU 标注的回退版本，不是通用默认值；该版本默认使用 5.0.32。若聚合查询报错，应核对完整 MongoDB 错误和实际查询，不要仅凭版本号归因（见[官方部署配置](https://github.com/labring/FastGPT/tree/v4.17.2/deploy/version/main)）。
- 重复发起相同不良分析查询时响应延迟过高，原因是未配置Redis缓存，每次请求都直接读取全量历史数据，未复用已查询过的结果集。

## 怎么确认配好了
- 登录数据库管理工具，使用`MONGODB_URI`对应的连接字符串验证实例可正常连接并写入测试用的冲床运行数据。
- 执行PG数据库的`\dt`命令，确认`PG_URL`指向的库包含换模记录、尺寸检验报告的对应数据表。
- 查看Redis监控面板，确认`REDIS_URL`对应的实例存在缓存命中的请求记录。
- 模拟单次换模后的10分钟高频数据写入，检查服务未出现连接耗尽类的报错。
