# 化妆品生产的质量问题追溯与不良分析：数据库与运维

## 这个品类的数据长什么样
该品类数据来自注册备案配方、原料安全资料、称量乳化等生产设备、ERP/MES系统、实验室检测记录及包材版本信息。日常文档包含配方工艺单、称量投料记录、乳化或灌装日志、清场清洁记录、半成品与成品检验报告、标签审核单。数据更新随每批生产、每次换线触发，核心字段包含原料批次号、乳化温度、均质时长、成品批号、备案配方编号、限用物质含量，单位涵盖摄氏度、分钟、批次编号等。

## 这些特征在「数据库与运维」这一环带来什么约束
每批换线的高频更新要求数据库支持低延迟写入与查询，避免生产流程阻塞。多源异构数据需兼容结构化的ERP字段、设备时序数据及非结构化的检验报告，需提前规划索引与数据映射规则。备案配方与实际生产数据的强一致性要求，需开启事务级写入校验，防止配方与备案不一致的风险。感官与稳定性检测的多维度数据，需支持按批次关联全链路溯源，需为批次号建立唯一索引。错标召回的追溯需求，需保留全流程数据的不可篡改副本，运维环节需定期校验数据完整性。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本规范。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://user:pass@host:27017/cosmetic_prod?replicaSet=rs0` | 适配化妆品生产的副本集部署需求，支持主节点漂移时的自动重连，匹配多源数据存储的高可用要求 |
| `PG_URL` | `postgresql://user:pass@host:5432/mes_data?sslmode=require` | 存储结构化的配方、批次、检验数据，SSL模式保障备案数据的传输安全 |
| `DB_MAX_LINK` | `20–30 个` | 匹配每批生产的并发写入查询量，避免连接池耗尽导致生产环节阻塞 |
| `REDIS_URL` | `redis://:pass@host:6379/0?maxmemory-policy=allkeys-lru` | 缓存高频查询的备案配方、批次映射信息，降低数据库负载 |
| 数据备份周期 | 每批次生产结束后 + 每日凌晨 2 点 | 覆盖换线与日常数据更新，保障全链路数据可追溯，满足召回时的快速查询需求 |
| 索引配置 | 为批次号、备案配方编号建立唯一索引 | 加速按批次的全链路溯源查询，避免数据重复写入导致的一致性问题 |

## 容易做错的三处
- 部署pgvector、Milvus的配置文件启动失败，返回配置参数错误的报错文案。原因是配置文件中未正确匹配数据库用户名与实际部署的账号信息，未添加副本集连接标识。
- MongoDB副本集主节点漂移后，数据同步中断，无法读取最新的生产记录。原因是未开启自动重连配置，导致Change Streams无法在主节点切换后恢复连接。
- 私有化迁移时出现数据字段为空的情况，无法关联成品批号与备案配方。原因是迁移过程中未校验数据映射规则，遗漏了化妆品生产特有的备案配方编号字段。

## 怎么确认配好了
- 执行批量写入测试数据，查看数据库连接池的活跃连接数，确认连接数未超过配置的`DB_MAX_LINK`上限。
- 触发一次主节点漂移模拟，检查MongoDB的同步状态，确认Change Streams可以自动恢复连接。
- 导入一批生产数据，通过批次号查询全链路记录，确认所有关联字段均能正常返回。
- 执行数据备份恢复测试，确认备份文件可以正常加载，数据完整性符合业务要求。
