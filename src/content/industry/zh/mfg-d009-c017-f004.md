# 喷涂与涂装的质量问题追溯与不良分析：工作流编排

## 这个品类的数据长什么样
本品类的数据覆盖涂装全流程，来源包括涂料供应商提供的TDS/SDS文件、喷房与烘炉的实时运行数据、色差仪与膜厚仪的检测结果、车间环境监测数据及MES系统记录。日常文档包含涂装工艺卡、涂料批次单、调漆记录、膜厚色差报告、烘炉曲线、缺陷返修单、VOCs台账。数据更新节奏随生产批次、班次变化，部分运行参数为连续采集。

## 这些特征在「工作流编排」这一环带来什么约束
数据来源分散且更新节奏不均，要求工作流需支持多数据源的异步拉取与格式统一；多类型文档的字段差异大，需配置节点对不同文档的字段做标准化映射；连续采集的实时数据与批次级文档需分别处理，避免数据混淆；VOCs台账与生产数据的关联要求工作流保留完整的链路追溯字段，确保不良分析时可溯源到对应生产窗口。同时，涂装缺陷的分析需匹配前处理、喷涂、固化的时间窗口，工作流需支持按批次或时间区间关联多节点数据。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本制定。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 数据源触发条件 | 按批次号匹配后执行 | 涂装生产数据按批次归集，避免跨批次数据干扰分析 |
| 上下文窗口大小 | 800–1200 字符 | 适配涂装工艺卡、调漆记录等文档的单页内容长度，避免截断关键参数 |
| 全局变量绑定 | `variables` 绑定批次ID | 统一存储当前批次的涂料批号、烘炉温度等核心参数，供后续分析节点调用 |
| 节点执行超时时间 | 600 秒 | 适配烘炉曲线、连续采集数据等大体积数据的解析与关联查询 |
| 结果去重规则 | 按缺陷类型+批次号去重 | 避免同一缺陷在喷涂、固化等多个环节被重复识别 |
| 失败重试次数 | 3 次 | 应对实时数据采集的临时中断或接口波动 |

## 容易做错的三处
- 现象：工作流执行时提示工具调用失败，查看日志发现`nodeId`未正确绑定批次参数。原因：未在数据源节点配置`variables`绑定对应批次ID，导致后续节点无法获取正确的上下文数据。
- 现象：工作流处理多批次数据时，返回结果包含历史批次的缺陷记录。原因：未配置按批次号的去重规则，导致不同批次的数据被混淆关联。
- 现象：上传涂装相关文档时，解析节点自动加载历史上传的文件内容。原因：未在文件上传节点配置仅处理当前会话附件的规则，导致历史文件被重复纳入解析范围。

## 怎么确认配好了
- 手动触发单批次工作流，检查数据源节点仅拉取对应批次的涂料批次单、烘炉曲线等数据，确认无历史批次数据混入。
- 查看`variables`节点存储的参数，确认当前批次的核心字段已正确绑定，可在后续分析节点正常调用。
- 模拟数据采集中断的场景，确认工作流在超时后按配置的重试次数自动重试，未直接触发失败流程。
- 上传单份涂装工艺卡，确认解析节点仅处理当前上传文件，未加载历史上传的文档内容。
