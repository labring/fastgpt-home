# 烘焙与方便食品的质量问题追溯与不良分析：多轮对话与提示词

## 这个品类的数据长什么样
该品类主体为面包糕点、饼干、方便面及速冻面点工厂，日常文档包含配方与投料单、生产记录、烘烤/蒸煮曲线、金属检测记录、清洁消毒记录、出厂检验报告。数据来源涵盖原辅料合格证明、ERP/MES系统、称量系统、烤炉/油炸线设备、实验室检测数据及食品追溯台账，更新频率按生产批次、班次或每日更新，核心字段包含过敏原物料清单、烘烤/油炸温度与时长、异物检测结果、包装日期等。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
该品类产品换线频繁且配方多样，多轮对话需快速隔离不同批次的上下文，避免跨批次数据混淆；过敏原与清洁切换要求高，对话需保留历史清洁、过敏原核对记录，确保不良分析的精准性；数据按批次更新且关联多环节文档，提示词需绑定批次相关变量，减少重复输入；直接食用的属性要求追溯结果无误差，多轮对话需完整加载全环节生产与检测数据，支撑全链路分析。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本编写。
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `chatId` | 按生产批次绑定唯一`chatId` | 烘焙与方便食品换线频繁，需隔离不同批次的对话上下文，避免数据混淆 |
| `messages` | 保留前20条历史对话消息 | 批次追溯需关联多环节的检测、生产记录，足够的历史上下文可支撑跨环节关联分析 |
| `variables` | 预设批次号、过敏原物料清单、烘烤曲线参数为全局变量 | 该品类需频繁核对配方与生产参数，变量绑定可减少重复输入 |
| 最大上下文长度 | 8000–12000 token | 多环节数据文档较长，需完整加载批次相关的生产、检测记录 |
| 对话日志保留时长 | 按批次归档后保留180天 | 食品追溯需留存批次全周期数据，符合行业溯源要求 |
| 工具调用默认模型 | 按业务场景绑定对应模型 | 不同大模型的输出格式与精度适配不同分析需求，确保提示词效果匹配业务目标 |

## 容易做错的三处
- 现象：调用API创建应用后，多轮对话上下文丢失，回复无法关联历史生产记录。原因：未按生产批次绑定唯一`chatId`，不同批次的对话被混淆到同一上下文窗口。
- 现象：接入指定大模型后，使用相同提示词提问的回复效果与原生平台不符。原因：未在对话配置中绑定对应模型的`variables`参数，提示词未适配模型的输出格式要求。
- 现象：docker容器重启后，之前保存的对话日志丢失且无法恢复。原因：未将日志挂载到持久化存储卷，且未按批次归档日志，容器本地文件随重启被清空。

## 怎么确认配好了
- 发起新对话并输入某批次的批次号，检查对话界面是否自动加载该批次关联的配方、生产记录等预设变量。
- 连续发起3轮关于同一批次的异物检测、烘烤参数的提问，检查回复是否关联历史对话中的批次信息，无上下文断裂。
- 重启docker容器后，检查之前保存的对话日志是否仍可在工作台中检索到。
- 切换大模型后，使用相同的过敏原核对提示词提问，检查回复格式是否符合预设的字段输出要求。
