# 热处理的质量问题追溯与不良分析：多轮对话与提示词

## 这个品类的数据长什么样
热处理场景的数据来源包含材料牌号、客户技术条件、温控仪表、炉温均匀性测试设备、硬度计与金相设备、MES系统，更新按每炉次、每批频次执行。日常文档涵盖热处理工艺卡、装炉图、炉温曲线、硬度与金相报告、设备点检表、异常处置单，数据字段包含材料牌号、炉温参数、保温时长、硬度值、金相组织类型等，单位涉及温度、时长、硬度等级等。

## 这些特征在「多轮对话与提示词」这一环带来什么约束
由于数据按炉次、批次更新，多轮对话需绑定唯一的炉批次ID，避免跨批次数据混淆。文档类型包含图表与结构化报表，提示词需引导识别图表关联的文本字段，确保不良分析可关联装炉位置、炉温曲线等非纯文本数据。多源数据来自设备、MES与客户要求，需通过多轮对话逐步对齐不同来源的参数，防止出现数据冲突。

## 配置怎么定
以下配置基于 FastGPT v4.17.0 版本。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配热处理工艺卡、炉温曲线的文本结构，避免拆分破坏参数完整性 |
| 重叠长度 | 150–200 字符 | 保留炉号、批次ID等跨块关联信息，保障多轮对话的数据溯源连贯性 |
| 单次搜索上限 | 前 6–10 条 | 覆盖单炉次的多类文档，确保不良分析可调用全量相关数据 |
| 最大上下文 | 5000–7000 token | 容纳单炉次的全量文档片段与多轮对话历史，避免上下文截断 |
| `variables` 绑定 | 绑定炉批次ID与设备编号 | 确保对话仅调用当前批次的热处理数据，隔离跨批次的干扰信息 |
| 问题优化 | 按实测标定 | 适配热处理专业术语，优化不良分析的提问引导逻辑 |

## 容易做错的三处
- 现象：对话详情页仅展示简化问答内容，无法查看应用内部的详细处理步骤。原因：未开启完整`messages`日志存储配置，仅缓存了最终交互结果。
- 现象：本地部署后上传知识库文件，数据处理环节显示为空。原因：分块长度设置超出文档解析适配范围，或未正确绑定`variables`对应的炉批次参数，导致数据无法关联入库。
- 现象：MongoDB数据库中无法查询到对话历史记录。原因：`chatId`生成逻辑错误或存储路径配置不当，导致对话数据未写入指定集合。

## 怎么确认配好了
- 上传单炉次的热处理工艺卡与炉温曲线，发起对话询问当前批次的工艺参数，核对返回结果是否包含对应文档的完整字段。
- 发起两轮连续对话，分别询问炉温数据与硬度检测结果，核对两次对话的上下文是否关联当前炉批次的信息。
- 查看应用的日志模块，确认`variables`绑定的炉批次参数与`chatId`已正确写入会话存储。
- 模拟异常场景发起对话，核对系统是否能触发不良分析的引导逻辑，未出现参数不匹配的报错。
