# 生产计划与车间排程的质量问题追溯与不良分析：向量模型与索引

## 这个品类的数据长什么样
这个品类的日常文档包含销售订单、主生产计划、物料需求计划、周日排产表、工单、缺料清单、交期变更单。数据来源为ERP订单与库存、BOM和工艺路线、设备产能、人员班次、在制品和供应商到货。更新节奏通常为每日、每周，或随订单、异常情况触发更新。文档多包含订单号、物料编码、工序编号、产能数值、班次时间、在制品数量等字段，单位涵盖件、小时、天等。

## 这些特征在「向量模型与索引」这一环带来什么约束
品类数据来源多样且更新频繁，要求索引支持增量同步与定时刷新，匹配每日、异常触发的更新节奏。文档多为多字段拼接的半结构化内容，拆分时需避免破坏业务关联逻辑，需针对性设置分块规则。字段数量多且存在跨文档关联，向量模型需适配多维度语义拼接，同时索引需支持按关联字段快速召回。此外，排程、工单类文档长度差异较大，需预留足够的上下文处理空间。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| 分块长度 | 800–1200 字符 | 适配工单、排程表等完整业务单元的文本长度，避免拆分破坏工序、物料等关联字段的业务逻辑 |
| 重叠长度 | 100–150 字符 | 覆盖跨块的关联字段，保证上下文语义的完整性，避免出现业务片段断裂 |
| `maxToken` | 8192 | 适配bge-large模型的最大上下文限制，容纳多字段拼接后的完整业务文本 |
| 相似度阈值 | 0.72–0.78 | 区分相似排程工单与异常工单的语义差异，精准召回与质量问题相关的历史数据 |
| 单次搜索上限 | 前 8 条 | 车间排程数据关联多维度信息，少量高相关结果即可支撑质量追溯与不良分析的业务需求 |

## 容易做错的三处
- 现象：导入的dataset.csv仅包含index字段无content字段。原因：未正确拼接工单、排程表等文档的业务字段，仅导出了索引元数据未关联实际业务文本内容。
- 现象：本地部署bge-large模型时出现显存不足报错。原因：未限制`defaultToken`的批量处理参数，同时未关闭非必要的模型并行加载，占用了显卡的全部显存资源。
- 现象：自定义索引无法匹配MongoDB对应表字段。原因：未将排程表、工单等文档的关联字段映射到索引配置的元数据字段，导致索引与数据库表字段不匹配。

## 怎么确认配好了
- 上传一份测试用的周日排产表，查看解析后的文本块是否保留了完整的工序、产能、班次信息，无截断或拆分错误。
- 运行一次质量追溯查询，核对返回的结果是否包含对应工单的关联文档，且字段匹配预设的业务逻辑。
- 查看向量模型的资源占用情况，确认未超出单张3090显卡的显存限制，无持续报错。
- 检查FastGPT v4.17.0的索引更新日志，确认每日或异常触发的排程数据能够自动同步到索引库中。
