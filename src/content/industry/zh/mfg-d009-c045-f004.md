# 纺纱与织造的质量问题追溯与不良分析：工作流编排
本文基于FastGPT v4.17.0版本编写。

## 这个品类的数据长什么样
纺纱与织造品类的主体为棉纺、化纤纺、机织和针织企业，日常产生的文档包含配棉或配料单、工艺上机单、设备运转记录、纱线检验、坯布检验、疵点记录。数据来源涵盖原纤维检验报告、ERP系统、纺机与织机实时数据、条干仪检测结果、验布机记录、订单规格参数。数据更新频率随每批原料、每班生产、每匹布产出同步更新，配棉单包含纤维品级、混配比例字段，工艺单标注捻度、织造组织参数，检验记录记录疵点类型、位置、对应批次号，单位涵盖支数、克重、米数等。

## 这些特征在「工作流编排」这一环带来什么约束
多源异构的数据来源要求工作流需配置统一的全局变量映射规则，将不同系统的字段对齐至统一格式。高频次的更新节奏要求工作流需绑定批次、设备编号等触发变量，实现按生产节点自动触发。文档类型多样且单批次数据量随设备头数增长，要求工作流需支持多文档批量处理与节点串联。疵点可沿生产链路连续传播的特性，要求工作流需关联全链路的原料、设备、检验数据，覆盖从配料到成品检验的全部环节。

## 配置怎么定
| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 全局变量`variables` | 绑定批次号、原料批次、设备编号 | 匹配每批原料、每班的更新频率，统一多源系统的字段映射 |
| 节点触发`nodeId` | 绑定检验节点、配料节点、设备数据节点 | 实现按生产环节串联工作流，覆盖全链路数据采集 |
| 单次处理文档数 | 前10条 | 适配每匹布的检验记录常规数量，避免工作流过载 |
| 超时阈值 | 600秒 | 覆盖设备数据拉取、多文档汇总的常规耗时需求 |
| 多文档处理模式 | 逐节点循环 | 实现每份上传文档的逐一提取与汇总，匹配多文档处理需求 |
| 输出格式 | 分段Markdown | 适配对话窗口的内容展示，简化后续渠道转发格式 |

## 容易做错的三处
- 现象：多文档上传后仅提取第一份文档内容，其余未完成信息提取。原因：未将多文档处理模式设为逐节点循环，未通过`variables`绑定每份文档的独立标识。
- 现象：工作流执行超时，返回504状态码。原因：未设置合理的超时阈值，直接使用默认配置，未适配纺纱设备数据拉取的耗时需求。
- 现象：单次对话仅输出一条消息，无法触发多条回复。原因：未在编排中配置多输出节点，未通过`nodeId`绑定两个独立的对话输出节点。

## 怎么确认配好了
- 上传多份涵盖配棉单、坯布检验记录的文档，核对每个文档是否被逐一提取并完成字段映射。
- 触发工作流并查看执行日志，确认整体耗时未超过设定的600秒阈值，无超时报错。
- 运行SQL查询节点，确认查询结果已通过`variables`映射至对话窗口的输出内容中。
- 调用API传入指定批次号参数，确认工作流自动绑定对应全局变量并匹配该批次的全链路数据。
