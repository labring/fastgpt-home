# 钢铁冶炼与连铸的质量问题追溯与不良分析：数据库与运维

## 这个品类的数据长什么样
该品类数据涵盖铁水与废钢投料数据、L2过程控制参数、化验室成分报告、MES生产调度记录、能源介质消耗数据及设备运行状态。日常文档包含炉次计划、配料单、转炉冶炼台账、连铸工艺参数记录、板坯质量判定单。数据更新频率覆盖每炉次、实时采集及每班汇总，数据字段包含温度、成分占比、设备负载等带单位的量化指标，生产流程为高温连续式，炉次与浇次强耦合，无法随意中断生产。

## 这些特征在「数据库与运维」这一环带来什么约束
该品类的高实时性、多源异构数据特征，对数据库运维带来多重约束。每炉次及实时产生的高频数据，要求数据库支持高并发写入与低延迟查询。多源数据来自L2系统、化验室、MES等不同平台，格式与字段标准存在差异，需要支持灵活的数据结构适配。炉次与浇次强耦合的生产逻辑，要求数据关联查询需覆盖跨表关联与时序关联，同时生产流程无法停机，要求数据库运维具备零停机扩容与动态调整能力。高精度量化指标的存储需求，也要求数据库预留足够的字段精度与存储空间。

## 配置怎么定
本页面适用于 FastGPT v4.17.0 版本。

| 配置项 | 建议取法 | 这样取的依据 |
| ---- | ---- | ---- |
| `MONGODB_URI` | `mongodb://fastgpt:securepass@db-host:27017/steel_trace?authSource=admin&readPreference=nearest` | 适配多源异构时序数据的高并发写入，就近读取降低跨地域延迟 |
| `PG_URL` | `postgresql://fastgpt:securepass@pg-host:5432/fastgpt_mes?sslmode=require` | 支持复杂跨炉次、跨浇次的关联查询，满足质量追溯的关联分析需求 |
| `DB_MAX_LINK` | `200–300 个连接` | 匹配每炉次实时写入、多部门并发查询的连接数需求，按实测标定 |
| `REDIS_URL` | `redis://:securepass@redis-host:6379/0?maxmemory-policy=allkeys-lru&maxmemory=16 GB` | 缓存实时炉次状态与高频查询结果，降低核心数据库的负载压力 |

## 容易做错的三处
- 现象：数据库写入请求堆积，磁盘读写占用率持续偏高，日志出现`connection timeout`报错。原因：未根据每炉次实时写入的高频特征调整连接池上限，导致连接耗尽无法处理新请求。
- 现象：部分板坯判定单的关联数据缺失，查询结果返回空字段。原因：未配置多源数据的时序关联规则，导致不同系统的炉次数据未正确绑定。
- 现象：磁盘持续高读写，存储空间短时间内快速耗尽，极端场景下出现硬盘损坏。原因：未启用历史数据归档策略，未按炉次批次清理过期的冶炼与工艺记录，导致冗余数据无限制累积。

## 怎么确认配好了
- 执行数据库连接测试脚本，验证`MONGODB_URI`与`PG_URL`的连通性，确认连接数可覆盖预设的并发请求规模。
- 导入单炉次的全量关联数据，验证跨表关联查询可正确返回炉次、浇次、质量判定的完整关联结果。
- 查看磁盘存储监控指标，确认历史数据归档策略按预设规则触发，存储空间增长速率符合预期。
- 模拟多部门并发查询请求，确认`DB_MAX_LINK`的配置可支撑并发访问，无连接超时报错。
