# 预拌混凝土生产的质量问题追溯与不良分析：向量模型与索引

## 这个品类的数据长什么样
数据来源涵盖工程订单、砂石等原材料检验记录、搅拌站运行控制系统、项目试验室检测报告，日常生成的文档包含配合比通知单、开盘鉴定、生产运输单、原材料检验单、试块记录与强度报告。数据更新按每车生产、每批原料进场、每日汇总的节奏生成，字段包含生产批次、原材料型号、含水率测定值、试块抗压强度数值、坍落度参数等，由搅拌站、项目试验室及质量调度部门共同维护。

## 这些特征在「向量模型与索引」这一环带来什么约束
高频次的小批量数据写入要求索引支持实时增量更新，避免全量重建带来的耗时损耗。多来源、多格式的数据需要统一字段映射规则，确保嵌入向量提取时的一致性，防止关联信息错位。单条数据体量较小但整体数据量随生产规模快速增长，需适配小批量高频写入的索引策略。试块强度报告等滞后检测数据需与对应生产批次、运输环节关联，索引需支持跨文档的多字段联合检索，用于快速追溯质量问题的源头环节。

## 配置怎么定
以下配置基于FastGPT v4.17.0版本制定。

| 配置项 | 建议取法 | 这样取的依据 |
| --- | --- | --- |
| 分块长度 | 800–1200 字符 | 适配配合比通知单、试块记录等单文档的平均长度，避免块内信息割裂 |
| 重叠长度 | 100–200 字符 | 覆盖生产批次、原材料编号等跨块关联字段，防止关键信息被截断 |
| `maxToken` | 8192 token | 适配主流嵌入模型的输入上限，避免数据截断丢失核心生产参数 |
| `defaultToken` | 按实测标定 | 用于处理无明确嵌入需求的短字段，适配不同数据源的字段长度差异 |
| 单次召回上限 | 前 20 条 | 匹配质量追溯时需要关联的生产、运输、检验环节的历史数据量级 |
| 相似度阈值 | 0.75–0.85 | 区分同批次生产与相似参数的不同批次数据，避免误关联 |

## 容易做错的三处
- 现象：使用chunk模式调用pushdata API上传数据后，界面长期显示“索引中”状态，无进度更新。原因：未配置合理的分块长度与重叠长度，导致单块数据超出嵌入模型输入上限，嵌入任务阻塞。
- 现象：调用嵌入模型时返回指定报错，提示令牌无权使用目标模型。原因：未正确配置模型调用权限，或选择了未在当前账号下开通的商用嵌入模型。
- 现象：检索结果仅返回少量关联数据，无法覆盖完整的质量追溯链条。原因：单次召回上限设置过低，未匹配预拌混凝土生产多环节关联数据的检索需求。

## 怎么确认配好了
- 上传单份配合比通知单数据，检查索引进度是否在合理时间内完成，无长期阻塞情况。
- 输入坍落度参数、生产批次等检索词，核对返回结果的关联字段是否匹配预拌混凝土生产的业务逻辑。
- 查看嵌入模型调用日志，确认未出现令牌权限报错或输入长度超限提示。
- 调整分块长度与重叠长度参数后，对比检索结果的完整性，确认关联信息未被截断。
