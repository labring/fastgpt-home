# 平台店铺评价与体验分维护的商品资料与选型问答：文档解析与分块

## 这个品类的数据长什么样

平台店铺评价与体验分维护处理售后履约后的消费者反馈，主要数据来自抖店体验分、天猫服务指标、京东售后评价与客服系统，典型文档包括差评处理记录、体验分明细、服务诊断报告与整改台账。这些材料的共同点是同一店铺、同一指标期间内存在多份互相引用的记录，一份差评处理记录往往同时指向订单、客服会话与整改条目。资料更新频率为日或周，解析与分块需要保证指标名称、统计周期、店铺主体在拆分后仍能回指原文档，否则检索到的片段无法支撑选型问答中的条件判断。

## 这些特征在「文档解析与分块」这一环带来什么约束

FastGPT 中知识库由库、集合和数据三部分组成，最小搜索单位是库，集合仅作分类管理，与搜索效果无关。向量原数据存于 MongoDB 的 `dataset.datas` 表，`indexes` 字段记录对应向量 ID，一组数据可对应多个向量；向量存于 PostgresSQL 的 `vector` 字段，检索时先召回向量再按 ID 回 MongoDB 取原数据，命中同一组原数据则合并并取最高得分。分段时应让条件、说明与被约束内容保持在同一数据块内，避免把体验分口径与例外条件拆到不同块。

假设演练样本：材料原文为“示例店铺A 2025年3月体验分明细：3月1日至3月31日，物流体验分口径为发货及时率与揽收时长，差评处理记录编号 C-0312 归属该期间，状态为待客服主管复核。”待判定拟稿句为“示例店铺A 2025年3月差评处理记录 C-0312 已完成整改并关闭。”该拟稿句的主体、对象、期间与材料一致，但材料只载明待复核，未载明整改完成或关闭，属于未获支持。

## 配置怎么定

| 配置或核对项 | 取值或状态 | 与本页材料的关系 |
| --- | --- | --- |
| 搜索模式 | 混合检索 | 体验分口径含专有名词，差评编号需精确命中 |
| 引用上限 | 本次假设试验起点 3000 tokens | 差评记录与诊断报告块长差异大，按 tokens 控制比 top k 稳定；与 2000、4000 两个起点比较引用完整性 |
| 最低相关度 | 本次假设试验起点 0.4 | 仅在语义检索或结果重排时生效，与 0.3、0.5 比较误召与漏召 |
| 问题优化 | 按实际效果决定是否开启 | 连续追问“该编号状态”需补全指代，开启会增加一次模型调用 |
| 分段核对 | 人工核对 | 确认指标期间、店铺主体、编号未被拆离 |
| 训练状态核对 | 人工核对 | 资料变更后核对实际训练与索引状态，上传成功不等于检索已更新 |

## 容易做错的三处

1. 把上传成功当作检索已更新。`dataset.datas` 与 `vector` 的写入状态需分别核对，仅凭表单提交无法判断索引是否生成。
2. 把待复核写成已完成整改。样本材料仅载明“待客服主管复核”，拟稿句写成“已完成整改并关闭”，属于把未获支持当作已确认。
3. 用相似度阈值代替主体与期间过滤。最低相关度是过滤阈值，不承担店铺或期间隔离，跨店铺记录可能因语义相近被召回。

对应检查：
- 输入样本材料原文与拟稿句，比较“待复核”与“已完成整改并关闭”是否同字段互斥，出现后者即判未获支持。
- 输入差评编号 C-0312，分别用全文检索与语义检索，观察编号是否命中同一数据块，未命中则核对分段是否拆离编号。
- 输入同一店铺不同期间的体验分明细，观察返回块是否携带期间标识，缺失期间标识则记录分段缺口。

## 怎么确认配好了

用样本原文与拟稿句执行三项验证。
- 第一，输入“示例店铺A 2025年3月差评处理记录 C-0312 状态”，比较返回块是否含“待客服主管复核”，含该状态即满足预期，返回“已完成整改”则判失败。
- 第二，输入“体验分 物流体验分 口径”，比较返回块是否与 3 月期间同块，同块即满足，跨期间混入则需重新分段。
- 第三，输入空查询 `[]` 核对下游设计，观察下游是否按空结果处理，不预设虚构规则一定返回空。重排须具备模型并按设置启用，图片检索须有图像输入与相应模型能力，两者不因本页配置而默认执行。跨不同向量模型的库不可共同关联，先核对库标识并排除不符合者，记录实际观察，不推断漏召回或冗余结果。
