# Temu半托管卖家运营的订单履约与售后答疑：HTTP 接口与外部系统

## 这个品类的数据长什么样
半托管卖家自行维护境外库存并完成发货，履约单、海外库存表与物流轨迹分属不同系统，日常还需处理商品申报表与价格申报。订单履约与售后答疑因此依赖跨系统取数：平台履约单决定发货时限，境外仓库存决定可发数量，采购成本表只用于内部核算。数据按日或每单更新，接口读取时点与人工台账时点可能错位，核对时须以同一单据、同一字段为准。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
HTTP 模块按外部接口文档确定地址与方法，Params、Headers、Body 分别核对，变量可引用全局变量、系统变量与前方节点输出，地址同样可引用变量。返回值通过 JSON path 提取，输出类型选择字符串时会把对应 key 的值转成 json 字符串。鉴权凭证经安全配置注入，不写入公开样例。chatId 与 responseChatItemId 在测试模式下不存在，调试时的空值属于环境特征。接口取回的库存或轨迹数值只代表查询结果，不等于平台已确认发货，也不构成对订单的授权处置。

假设演练样本：供核对的材料原文为“海外库存表 A 行：SKU-甲，可发数量 12，更新日期 2025-03-01”“平台履约单 B：SKU-甲，要求发货数量 12，状态待发货”。待判定的拟稿句为“库存充足，可直接发货并回传物流单号”。该句把库存查询结果当作发货授权，材料未载明发货审批与物流回传责任方，判定为未获支持。

## 配置怎么定
| 配置项 | 本次假设试验起点 | 核对方式 |
| --- | --- | --- |
| 请求地址 | 外部接口文档给出的地址 | 与文档逐字符比对，含变量占位 |
| 请求方法 | 文档标注的方法 | 与文档一致，不凭经验改换 |
| Headers 鉴权 | Bearer 加安全配置注入的凭证 | 样例中不出现明文凭证 |
| Body 结构 | 按文档字段名与类型书写 | 引用变量时字符串加引号 |
| 返回值提取 | 按 JSON path 取所需字段 | 与接口响应结构比对 |
| 输出类型 | 字符串或对象 | 与下游节点接收格式比对 |

## 容易做错的三处
1. 把库存查询结果直接当作发货授权。输入为库存表可发数量与履约单待发货状态，比较两者是否同 SKU 同期，观察结果是状态字段仍为待发货，未出现审批记录。
2. 在 Body 中引用字符串变量时漏加引号。输入为拟传入的字符串变量，比较声明与文档示例，观察结果是解析后的类型与接口契约不符。
3. 把测试模式下 chatId 为空当作接口故障。输入为测试模式请求，比较系统变量说明，观察结果是该字段在测试模式下本就不存在。

## 怎么确认配好了
1. 用假设样本核对拟稿句：输入库存表 A 行与履约单 B，比较“可直接发货”表述与材料中的待发货状态，只有材料出现同主体同期的发货确认，该表述才成立，否则记为未获支持。
2. 用假设样本核对变量引用：输入拟传入的字符串变量，比较 Body 声明与文档示例，只有解析结果类型与接口契约一致才满足条件。
3. 用纸面输入 [] 核对空结果承接：输入空数组，比较下游节点是否按空值处理，只有下游不产生业务动作才满足条件；实际检索返回内容须另行观察，不作保证。
