# 一般贸易出口报关的订单履约与售后答疑：多轮对话与提示词

## 这个品类的数据长什么样

在一般贸易出口报关的订单履约与售后答疑中，本页说明FastGPT的多轮对话与提示词如何衔接资料。将申报处理、货物交付和售后请求分开追问，核实每次回答实际承接的单据。所用场景为自拟文字测试。

## 这些特征在「多轮对话与提示词」这一环带来什么约束

自拟追问先提供一份出口申报处理记录，写明某票资料被退回补充说明，随后询问“客户的售后怎么办”。退回针对申报资料，不说明货物已经交付或客户提出了什么服务要求。提示词应把缺少的客户请求、订单对应和交付材料列清。若回答直接安排退换货，应回查历史是否真的包含该请求；只看到申报退回便延伸业务结论，会使售后依据无法核实。

## 配置怎么定

| 对话核对项 | 本次申报与售后材料 | 验收动作 |
| --- | --- | --- |
| 初始范围 | 申报资料退回补件 | 不推定客户退换货要求 |
| 新增请求 | 邮件要求更正装箱描述 | 核票次与所需动作 |
| 指代检查 | 这次指哪份邮件或申报 | 比对原问和优化问 |
| 缺项定位 | 未取邮件与传入遗漏分开 | 分别补资料或排查输入 |
| 处理边界 | 回答整理后续待办 | 另核业务状态实际更新 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |

| `提示词与任务` | 说明资料、任务和缺证据处理。 |
| `历史记录` | 核实际提交的历史输入。 |
| `问题优化` | 指代消除与问题扩展需复核。 |
| `模型与长度` | 上下文与回复长度分别核对。 |

## 容易做错的三处

- 申报退回补件被改成客户要求退换货：回查客户请求、订单及交付原文，保留申报记录与新增处理句，不能从资料退回推出商品售后要求。

- 装箱描述更正被优化成退款，或“这次”串到另一票：并列原问、优化问和票次，查实际历史承接，不靠扩大上下文自动纠正事项。

- 客户邮件已经取得却未进入输入：比对资料选择与实际请求查传递；邮件从未取得则补源，不能把两种缺项统称模型记忆不足。

## 怎么确认配好了

验收可分别使用空历史、仅有申报记录和补齐客户邮件三种输入，检查答案能否区分所缺证据。邮件内容未被纳入输入时，应定位传入步骤；原文从未取得时，则向责任人补取，不把两者都解释成模型记忆不足。回答可以整理已知材料与待办，不能把草拟的后续动作写成申报状态或售后状态已经更新。
