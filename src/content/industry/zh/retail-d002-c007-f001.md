# 一般贸易进口报关的订单履约与售后答疑：HTTP 接口与外部系统

## 这个品类的数据长什么样

一般贸易进口报关围绕完税价格、运保费和税费缴纳展开，每单处理进口报关单、商业发票、装箱单、提单和合同。订单履约与售后答疑环节需要把外部系统的状态回传给业务人员，供其核对成交方式、运保费填报和查验配合进度。这些材料按每单更新，HTTP 接口承担的是把外部系统返回的字段接入对话流程，不承担申报或缴税动作。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向指定地址发送请求，Params 多用于 GET，Body 多用于 POST/PUT，Headers 传递特殊信息，三者均可通过 `{{}}` 引用全局变量、系统变量和前方节点输出，URL 同样可以引用变量。返回值配置的是解析方式，通过 JSON path 从响应中提取值，输出类型选择字符串时会把对应 key 的值转为 json 字符串。测试模式下 chatId 与 responseChatItemId 不存在，调试时取不到这两个值属于模式差异。

假设演练样本：一份商业发票原文写明“卖方：A 贸易公司；买方：B 进口公司；成交方式：CIF；发票金额：USD 120,000；合同号：HT-2024-018”。一条待判定的交接请求为“请依据该发票把订单状态更新为已清关并通知客户”。发票原文只载明买卖双方、成交方式、金额和合同号，未载明清关状态，也未载明授权该请求执行状态更新或对外通知。该请求中的状态更新与客户通知均未获支持，需要另行核实清关结果与通知授权。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 核对方式 |
| --- | --- | --- |
| 请求地址 | 外部系统提供的接口地址，可引用变量 | 与外部接口文档逐字符比对 |
| 请求方法 | 按外部接口文档选择 GET 或 POST | 与文档标注的方法比对 |
| Headers | 键为 Authorization，值为 Bearer 加凭证 | 核对凭证来源为安全配置 |
| Body | 按外部接口契约写 JSON，字符串加引号 | 对照契约检查字段与类型 |
| 返回值 key | 按响应结构填写 JSON path | 用响应示例验证提取结果 |
| 输出类型 | 字符串时转为 json 字符串 | 观察输出内容与预期结构 |

起点数值来自本次假设演练样本的字段，未在文档中标注默认值。

## 容易做错的三处

1. 把测试模式下 chatId 与 responseChatItemId 不存在当成业务故障。输入为测试模式请求，比较返回中是否含这两个字段，可观察到的结果是测试模式返回中不含这两个值。
2. 在 Body 中引用字符串变量时漏掉外层引号。输入为含字符串变量的 Body 声明，比较最终解析结果，可观察到的结果是字符串被当作 JSON 结构解析而报错。
3. 把返回值 key 当作接口本身的返回值。输入为一段响应与一个 key，比较提取结果与响应原文，可观察到的结果是 key 只决定提取哪一部分，不改变接口返回内容。

## 怎么确认配好了

1. 用假设样本发票原文与交接请求作为输入，比较请求中“已清关”与发票原文载明的成交方式、金额、合同号，发票原文未载明清关状态，可观察到的结果是该状态更新未获支持，需另行核实清关结果。
2. 用假设样本发票原文与交接请求作为输入，比较“通知客户”与原文载明的买卖双方，原文未载明通知授权，可观察到的结果是该通知请求未获支持，保留证据缺口。
3. 用一段含字符串变量的 Body 声明作为输入，比较最终解析结果与变量原值，可观察到的结果是带引号的字符串按字符串解析，不带引号的字符串解析失败，据此判断引号是否补齐。
