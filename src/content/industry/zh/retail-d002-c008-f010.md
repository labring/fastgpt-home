# 亚马逊FBA备货运营的订单履约与售后答疑：引用来源与溯源

## 这个品类的数据长什么样

在亚马逊FBA备货运营的订单履约与售后答疑中，本页说明FastGPT的引用来源与溯源如何衔接资料。本批计划与等待接收状态不能借用旧批结果。所用场景为自拟文字测试。

## 这些特征在「引用来源与溯源」这一环带来什么约束

自拟FBA售后查件资料包含入库计划“计划已建立”、库存状态“等待接收”和历史收货记录“旧批已接收”。用户问本批是否已入库时，计划建立只能说明安排，等待接收仍是本批现有状态，旧批记录不能迁移到本批。引用来源的批次身份比标题相同更关键；需要把计划、当前状态和历史结果分别标清，避免把不同批次的片段拼成完成结论。旧批已接收也不能证明本批会沿用相同接收流程或结果，只能作为历史来源供定位。若要报告本批进展，应优先读取带本批身份的记录，并保留状态记录所指阶段，不能用历史结果补当前证据缺口。

## 配置怎么定

| 本题核对项 | 材料条件 | 取证动作 |
| --- | --- | --- |
| 计划状态 | 本批计划已建立 | 限于安排层面。 |
| 当前记录 | 本批等待接收 | 保留本批身份。 |
| 历史结果 | 旧批已接收 | 不迁移到本批。 |
| 完成依据 | 本批缺实际接收凭据 | 补核本批结果材料。 |
| 限定保留 | 片段可能省掉批次 | 对照传入文字与原文。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `关联的知识库` | 同一检索节点关联的库需使用相同向量模型。 |
| `引用内容输出` | 输出为数组，可为空且继续传递。 |
| `引用输入承接` | 核回答环节实际接收的引用。 |
| `引用展示核对` | 逐项回查展示来源与原文。 |
| `资料时效核对` | 资料身份和有效版本分别核对。 |

## 容易做错的三处

常见错误是数组引用了旧批收货记录，回答却省掉批次直接说已接收；另一种风险是只传入计划建立句，让回答补写实际到仓。前者应核被引记录与本题批次的对应关系，后者要查实际接收凭据。FastGPT可以呈现引用内容，但来源存在不代表对应本批。等待接收也不能单独证明货物从未发出，运输与仓内接收属于不同核验范围。

## 怎么确认配好了

验收应分别问计划是否建立、当前库存记录写什么、本批是否有实际接收证据。答案可引用前两项明确状态，并将第三项保留为待补本批记录；历史已接收只作为旧批信息。逐句核引用与来源身份，检查实际传入内容是否丢失批次限定。空引用时先查搜索范围和片段传递，不能直接认定计划不存在或本批必定未到仓。
