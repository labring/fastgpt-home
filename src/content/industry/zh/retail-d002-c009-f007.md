# 亚马逊FBM自发货运营的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样

亚马逊FBM自发货运营的履约与售后由卖家自行完成，退货地址、承运商选择与跟踪号确认都在卖家侧处理，平台仓检验环节不参与。这一差异决定对话日志与审计需要同时承载订单拣货单、发货确认单、退货地址设置、物流追踪表四类材料的核对线索。数据来源包括Amazon Seller Central、承运商系统、ERP订单与客服邮件，更新节奏为每单与每日，因此日志核对以单笔订单为最小单元。出错后果涉及订单取消、A-to-z索赔与店铺绩效下降，日志留存的完整性直接影响后续对账与申诉时的证据链。

## 这些特征在「对话日志与审计」这一环带来什么约束

对话身份需要结合chatId核对目标对话与业务记录，不同入口的会话不能混算。运行详情按官方契约通过detail参数获取，非流式结果保存在responseData中，流式结果通过event区分。字段含义以接口实际返回为准，未返回的业务数据不能推定已完整留存。测试模式与正式调用的身份字段可能不同，需分别核对输入、历史与返回内容。对账、留存与合规要求由完整业务方案另行落实，日志存在不表示合规审计已完成。检索或表单收集值不构成授权执行。

假设演练样本：一份供核对的材料原文为“订单号 114-XXXXXXX-XXXXXXX，承运商为本地承运商A，跟踪号已录入物流追踪表，发货确认单状态为已确认，退货地址设置为海外仓B”。一条待判定的拟稿句为“该订单已完成发货并进入售后阶段，退货地址已生效”。判定需比较材料中主体、对象、状态与有效范围，材料未载明退货地址生效时间与售后阶段起始条件，该拟稿句的“已进入售后阶段”与“已生效”属于未获支持。

## 配置怎么定

| 配置项 | 类型/来源 | 说明与本次核对方式 |
| --- | --- | --- |
| appId | 官方字段 | 应用 ID，核对日志归属的应用范围 |
| chatId | 官方字段 | 会话 ID，长度小于250，核对目标对话 |
| dataId | 官方字段 | 对话 ID，核对单条对话记录 |
| detail | 官方字段 | 设为 true 获取中间值与完整结果 |
| source | 官方字段 | 设为 api 获取通过 API 创建的会话 |
| loadCustomFeedbacks | 官方字段 | 读取自定义反馈，按需开启 |

本次假设试验起点：将detail设为true，用于获取responseData中的模块状态与完整结果，比较对象为detail为false时的返回结构，确认中间值是否出现。

## 容易做错的三处

1. 将chatId不同的会话合并统计。输入为两个不同chatId的会话记录，比较对象为各自chatId下的对话列表，可观察结果为合并后总数与分别统计之和不一致。
2. 把detail为false的返回当作完整运行详情。输入为detail为false的响应，比较对象为responseData字段是否存在，可观察结果为该字段缺失，不能据此推断模块未运行。
3. 将检索结果或表单提交视为业务授权。输入为一次检索返回的quoteList与表单填写内容，比较对象为是否存在明确的授权字段或审批状态，可观察结果为两者均不包含授权信息。

## 怎么确认配好了

1. 输入假设样本中的材料原文与拟稿句，比较拟稿句中的状态描述与材料载明的字段，可观察结果为“已进入售后阶段”在材料中无对应字段，判定为未获支持。
2. 输入两个不同chatId的会话记录，比较各自chatId下的对话列表与合并统计，可观察结果为合并总数与分别统计之和一致时，说明未发生跨会话混算。
3. 输入detail为true的请求，比较responseData中是否包含模块状态与完整结果，可观察结果为该字段存在且包含模块信息，说明运行详情已按契约获取。若responseData为空或缺失，记录为未获取，不推断模块未运行。
