# 仅退款争议处理的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样
仅退款争议常没有退件入仓，证据重点落在发货签收与商品价值。售后后台的申请记录、承运商轨迹、客服聊天、仓库出库记录共同构成核对材料。数据按每单、每日更新，日常文档包括仅退款申请、发货凭证、签收证明、申诉材料。对话日志与审计环节要处理的是：同一笔争议在客服会话里如何被记录、能否按 chatId 找回对应会话、运行详情里保留了什么、哪些业务结论仍需另行核对。

## 这些特征在「对话日志与审计」这一环带来什么约束
对话身份以 chatId 为准，一个应用下某一段会话对应一个 chatId，dataId 指向该会话下某一条对话。核对时应把 chatId 与业务记录绑定，不同入口的会话分别计算。需要运行详情时按官方契约设置 detail=true，非流式结果保存在 responseData，流式结果通过 event 区分，flowResponses 携带节点完整响应。接口实际返回哪些字段，就以哪些字段为准；业务数据未在返回中出现，不能推定已完整留存。日志存在与合规审计完成是两件事，对账、留存与合规要求由完整业务方案另行落实。检索与相似度只影响召回排序，不承担权限或实体隔离，检索结果不能当作授权依据。

假设演练样本：某笔仅退款申请，主体为售后主管，对象为订单 A 的买家会话，状态为“仅退款申请待审核”，有效范围为 2026 年 3 月 1 日至 3 月 7 日。材料原文为：“订单 A 已于 3 月 2 日出库，承运商轨迹显示 3 月 4 日签收。买家 3 月 5 日发起仅退款申请，理由为未收到货。客服会话 chatId 为 test-chat-001，dataId 为 test-data-001。”待判定拟稿句为：“该订单已完成签收，仅退款申请应予驳回。”此句把签收事实直接等同于驳回结论，签收与商品价值、争议判定之间的证据缺口仍未补齐。

## 配置怎么定
| 配置或核对项 | 取值与来源 | 用途与边界 |
| --- | --- | --- |
| appId | 请求体传入，官方参数 | 定位目标应用，不代替会话身份 |
| chatId | 假设样本 test-chat-001，长度小于 250 | 绑定目标会话，不同入口分别核对 |
| dataId | 假设样本 test-data-001 | 定位该会话下某条对话 |
| detail | 设为 true 时返回中间值 | 非流式看 responseData，流式看 event |
| responseChatItemId | 传入时作为响应消息 ID | 同一 chatId 下需唯一 |
| loadCustomFeedbacks | 读取对话列表时可选 | 读取自定义反馈，不改变业务状态 |

## 容易做错的三处
1. 把 chatId 相同当作业务记录已对齐。输入两个不同入口的会话，比较 chatId 与业务单据的绑定关系，观察是否出现同一 chatId 对应多笔争议。
2. 把检索命中当作权限或实体过滤。输入无关查询，比较返回条目与目标业务范围，观察是否出现不属于该争议的记录。
3. 把签收轨迹直接写成驳回结论。输入样本材料原文与拟稿句，比较签收事实与争议判定所需证据，观察拟稿句是否缺少商品价值或申请理由的核对。

## 怎么确认配好了
1. 输入样本 chatId=test-chat-001、dataId=test-data-001，比较会话记录与业务单据的主体、对象、期间，观察三者是否指向同一笔争议；不一致时记录缺口。
2. 输入 detail=true 的请求，比较 responseData 或 flowResponses 中实际返回字段与核对所需字段，观察缺失字段是否被标注为未知；不把未返回字段当作已留存。
3. 输入拟稿句“该订单已完成签收，仅退款申请应予驳回”，比较其与材料原文的表述范围，观察结论是否超出签收事实所能支持的范围；超出时保留待核实状态。
