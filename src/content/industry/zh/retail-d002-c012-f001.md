# 仓内拣货复核打包的订单履约与售后答疑：HTTP 接口与外部系统

## 这个品类的数据长什么样
拣货复核打包处理订单出库，不处理供应商到货，数据来源为 WMS、订单系统、电子面单平台与称重设备。波次拣货单、复核记录、面单、包装耗材单按每单或小时更新，一次错发漏发会直接进入售后赔付。这些材料在 HTTP 接口与外部系统这一环，主要作为请求参数、请求体字段或返回值解析目标被引用，接口本身不改变拣货、复核、打包的作业结论。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
HTTP 模块向指定地址发送请求，Params 多用于 GET，Body 多用于 POST/PUT，Headers 传递特殊信息，三类数据与 URL 均可通过 `{{}}` 引用全局变量、系统变量、前方节点输出。返回值按 JSON path 语法提取，出参格式化以 json 转字符串为主。对话接口用 APIKey 鉴权，`chat/completions` 推荐在请求体传 `body.appId`，也支持 `Authorization: Bearer <apiKey>-<appId>`；传入的 `model`、`temperature` 无效；`chatId` 为空时不使用上下文，非空时取数据库会话并以 messages 最后一条为用户问题；`responseChatItemId` 需在当前 `chatId` 下唯一；`detail=true` 才返回中间值。测试模式下 `chatId` 与 `responseChatItemId` 不存在。

假设演练样本：供核对的波次拣货单原文为「波次 W-0715，订单 O-2231，商品 A 两件，拣货员已扫描，状态：待复核」。复核记录原文为「O-2231，复核员已核对数量，状态：复核通过，时间 2025-07-15」。拟判定交接请求为「依据上述两份记录，向外部订单系统发送 O-2231 已完成打包的 HTTP 请求」。两份原文均未载明打包完成，也未载明外部系统授权。

## 配置怎么定
下表为本次假设试验起点，非官方默认值。

| 配置项 | 本次起点 | 选择理由与比较对象 |
| --- | --- | --- |
| 请求地址 | 外部订单系统接口地址，通过变量引用 | 与外部接口文档给出的地址比对 |
| 请求方法 | POST | 与外部接口文档声明的方法比对 |
| Headers | Authorization 引用凭证变量 | 与鉴权规范要求的字段比对 |
| Body 字段 | 引用波次号、订单号变量 | 与外部接口契约字段逐项比对 |
| 返回值提取 key | 按响应结构配置 JSON path | 与接口响应示例结构比对 |
| detail | 需要中间值时置 true | 与是否需要 responseData 比对 |

## 容易做错的三处
1. 把拣货单「待复核」当成复核通过，据此发送打包完成请求。检查：输入两份原文，比较状态字段与请求内容，只有复核记录状态为复核通过且存在打包完成证据时才满足发送条件。
2. 把 `responseChatItemId` 在测试模式下的空值当成业务故障。检查：输入测试模式请求，比较返回值与文档说明，确认该字段在测试模式下不存在即属预期。
3. 把返回值提取 key 写成外部接口原始字段名，忽略 FastGPT 转化后的格式。检查：输入接口响应示例，比较配置 key 与转化后结构，字段路径一致才满足。

## 怎么确认配好了
1. 针对假设样本，输入波次拣货单与复核记录原文，比较拟发送请求的 Body 字段与两份原文，只有字段值均能在原文中找到对应证据才满足。
2. 针对鉴权配置，输入 Headers 配置，比较 Authorization 取值方式与文档说明的两种方式，符合其中一种才满足。
3. 针对返回值提取，输入接口响应示例，比较配置的 key 与 JSON path 提取结果，提取值与示例一致才满足。以上均为纸面核对，未实际调用接口。
