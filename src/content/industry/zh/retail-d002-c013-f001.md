# 便利店加盟门店督导的订单履约与售后答疑：HTTP 接口与外部系统

## 这个品类的数据长什么样

在便利店加盟门店督导的订单履约与售后答疑中，本页说明FastGPT的HTTP 接口与外部系统如何衔接资料。本店通知和检查标准需要对上当前事项，读取结果仍须区分发送、接收与复核。所用场景为自拟文字测试。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

加盟门店服务咨询可先问整改通知、标准和本次反馈分别提供哪些依据。自拟输入只有巡店发现及通知，没有本店接收或复核记录，不从通知已发推定问题解决。拟通过HTTP读外部督导资料时，先核真实契约是否支持本店、本次事项和适用版本，再确定地址、方法及变量，不能预设督导APP已经存在可用查询接口或包含全部处理状态。

## 配置怎么定

| 售后读取核对 | 本题自拟资料 | 所需证据 |
| --- | --- | --- |
| 本店对象 | 巡店发现与通知身份 | 响应不是其他门店 |
| 通知阶段 | 已发送无接收依据 | 未写成门店已收到 |
| 版本适用 | 标准原句及检查范围 | 发送条件匹配本次 |
| 补证复问 | 本次接收或复核材料 | 解释实际使用新增来源 |
| 业务结果 | 整改关闭或回写另验 | 查询未替代受理记录 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `请求地址与方法` | 请求地址与方法遵循外部契约。 |
| `Params与Headers` | 参数、请求头及鉴权分别核对。 |
| Body | 采用JSON请求体时按外部契约核结构。 |
| `变量引用` | 可引用全局、系统或前序输出变量。 |
| `调试身份字段` | 测试时无chatId及responseChatItemId。 |

## 容易做错的三处

门店响应错配：若返回属于另一门店，应核请求对象和来源身份后移出；发通知冒已接收：若通知只记已发送却被回答为已收到，应另取本店接收依据；标准版本不适用：若返回标准版本不适用于本次检查，应查原文适用说明与发送条件，修正后再读。三项分别核对象、阶段和版本，HTTP有响应不证明这些关系已经正确。

## 怎么确认配好了

验收并列保留门店、事项、标准范围、实际请求与返回，补本次接收或复核资料后重复问题，核新增依据是否参与解释。Params、Headers和适用Body按真实契约分别核，鉴权不进公开文字。整改回写、工单关闭或外部提交另验权限及业务回执；读取结束不证明门店已接受通知、已经整改或责任判断已获批准。
