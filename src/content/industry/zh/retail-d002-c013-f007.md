# 便利店加盟门店督导的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样

加盟督导场景下，对话日志的核对对象是总部与加盟店主之间围绕订货、履约、售后形成的记录。资料显示，该品类主要数据来源包括督导APP、POS销售、加盟系统与门店照片，日常文档涉及巡店表、加盟合同、整改通知与陈列标准。这些材料的更新频率为周、月，因此对话日志与业务单据之间往往存在时间差，核对时需要先确认同一期间。

本页只处理订单履约与售后答疑中的对话日志与审计，不把检索结果或表单提交当作业务授权。日志记录存在，与业务动作是否完成、是否获得批准，属于不同事实。

## 这些特征在「对话日志与审计」这一环带来什么约束

对话身份需要结合 chatId 核对目标对话与业务记录，不能把不同入口的会话混算。需要运行详情时，按官方契约设置 detail，并检查 responseData 中的实际返回字段。未返回的业务数据不能推定已完整留存。

假设演练样本（纸面材料，用于核对，未实际执行）：

材料原文一：“2024年9月，区域督导在督导APP内向加盟店主发出整改通知，要求就某门店陈列标准不符项于9月20日前反馈。”材料原文二：“同一期间，加盟系统显示该门店订货单处于待审核状态。”拟稿句：“该门店已确认整改完成，订货单已获批准。”

核对要点：材料一的主体是区域督导与加盟店主，对象是陈列整改，状态是“要求反馈”，未载明整改已确认；材料二的状态是“待审核”，待审核不证明已批准。拟稿句把未获支持的状态写成了已完成与已批准。

## 配置怎么定

下表围绕上述样本，只列与本功能、主任务相关的官方已说明设置或实施核对项。数值为本次假设试验起点，非官方默认。

| 配置项 | 本次假设起点 | 选择理由与比较方法 |
| --- | --- | --- |
| chatId | 假设填入“JC-202409-001” | 用于核对目标对话与业务记录，与材料一、二的期间比对 |
| detail | 假设设为 true | 需要运行详情时按官方契约设置，检查 responseData 是否含所需字段 |
| messages 最后一条 | 假设为“整改是否已确认” | 官方说明 chatId 非空时以最后一条为问题，其余被忽略 |
| responseChatItemId | 假设为“R-202409-001” | 官方要求同一 chatId 下唯一，用于定位本次响应 |
| source | 假设设为“api” | 获取会话列表时区分 API 创建来源，避免混入页面会话 |
| loadCustomFeedbacks | 假设设为 true | 读取对话列表时按官方可选参数核对反馈字段 |

## 容易做错的三处

1. 把“待审核”当作“已批准”。样本中加盟系统显示订货单处于待审核状态，拟稿句写成“已获批准”。核对时应比较同一订货单在同一期间的 status 字段，只有明确载明批准取值才满足条件。
2. 把“要求反馈”当作“已确认整改”。材料一只写要求于9月20日前反馈，未载明反馈结果。拟稿句写成“已确认整改完成”，属于未获支持。
3. 把日志存在当作合规审计完成。日志留存与对账、合规要求由完整业务方案另行落实，日志存在不等于完成合规审计。

## 怎么确认配好了

1. 输入样本材料一与材料二，比较拟稿句中的“已确认整改完成”与材料一的“要求反馈”，比较“已获批准”与材料二的“待审核”。只有材料明确载明对应状态取值，才满足条件；否则记录为未获支持。
2. 输入假设 chatId“JC-202409-001”，按官方契约设置 detail 为 true，检查 responseData 是否返回所需运行字段。若未返回，记录为未完整留存，不推定已留存。
3. 输入假设 messages 最后一条“整改是否已确认”，比较返回内容是否与材料一、二的状态一致。若返回内容出现材料未载明的批准或完成表述，记录为与材料不一致，保留证据缺口。
