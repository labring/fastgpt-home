# 便利店鲜食订货的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样
便利店鲜食按短保质期高频订货，门店店长在班次内完成下单，总部订货系统、POS销售、门店库存与冷链温控记录构成主要数据来源。对话日志与审计要处理的对象是订货单、报损单、临期处理表与温度记录在售后答疑中的往来记录。这些记录按日或按班次更新，订货单与报损单的日期范围、门店与班次标识成为核对的基本单位。日志存在只说明会话内容被记录，对账、留存期限与合规判断需要完整业务方案另行落实。

## 这些特征在「对话日志与审计」这一环带来什么约束
对话身份以 chatId 区分。同一应用下不同入口产生的会话属于不同 chatId，核对业务记录时先比对 chatId 与目标对话，避免把不同入口的会话合并计算。需要运行详情时，按官方契约设置 detail，并在 responseData 中查看模块响应；未返回的字段不能推定已经完整留存。检索模块返回的相似度数值只表示文本相关程度，不能当作门店、区域或权限的过滤条件。

假设演练样本：某便利店门店店长在 2025 年 6 月 10 日早班提交一份鲜食订货单，单据编号 XD-20250610-07，对象为三明治与饭团，状态为已提交待总部确认。同日售后对话记录中，一条拟稿回复写为“该订货单已确认并进入配送”。该拟稿句缺少总部确认的证据，订货单状态仍为待确认，拟稿句与材料原文不一致。

## 配置怎么定
配置围绕上述样本核对，不把数据库内部实现当作每页必配项。需要数值时明确为本次假设试验起点，并说明比较对象。

| 配置项 | 本次假设试验起点 | 核对方式 |
| --- | --- | --- |
| chatId | 样本会话 ID 取 HY-20250610-A | 与订货单 XD-20250610-07 的售后会话标识比对 |
| detail | 取 true | 检查 responseData 是否出现模块级响应 |
| 会话来源 source | 取 api | 与 getHistories 返回的 source 字段比对 |
| 响应消息 ID responseChatItemId | 取 R-20250610-01 | 检查该 chatId 下是否唯一 |
| 运行详情 dataId | 取样本对话 ID | 与 getResData 返回的 dataId 比对 |

上述起点仅用于本次纸面核对，不是官方默认值。检索库之间的向量模型标识需先核对，标识不一致的库不执行共同关联，只记录实际观察。

## 容易做错的三处
1. 把不同 chatId 的会话合并计算。样本中售后会话为 HY-20250610-A，若与另一入口会话混算，订货单 XD-20250610-07 的往来记录会被错误归并。检查方式：输入两个 chatId，比较各自返回的 dataId 列表，观察是否出现交叉。
2. 把相似度数值当作权限过滤。样本中检索返回的 score 只反映文本相关度，不能据此认定该记录属于该门店。检查方式：输入同一查询，比较返回记录的 dataset_id 与目标库标识，观察是否混入其他库记录。
3. 把待确认状态写成已确认。样本拟稿句“该订货单已确认并进入配送”与单据状态“已提交待总部确认”不一致。检查方式：输入拟稿句与单据原文，比较状态字段取值，观察是否出现互斥取值。

## 怎么确认配好了
1. 输入样本 chatId HY-20250610-A 与订货单编号 XD-20250610-07，比较 getHistories 返回的 chatId 与目标值，返回列表中该 chatId 唯一出现时满足条件；出现其他 chatId 混入时记录为不符。
2. 输入样本拟稿句与单据原文，比较“已确认”与“已提交待总部确认”两个状态表述，拟稿句未出现已确认结论时满足条件；出现已确认结论时记录为不符。
3. 输入 detail=true 的请求，比较返回结构中是否含 responseData，含模块级响应时满足条件；仅返回 choices 而无 responseData 时记录为未获支持，保留待核实。
