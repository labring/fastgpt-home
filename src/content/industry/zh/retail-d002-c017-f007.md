# 加盟费与保证金结算的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样

加盟费与保证金结算围绕资金和违约扣款展开，不承担政府备案职责。日常材料包括加盟费发票、保证金台账、扣款通知、合同付款计划，来源涉及财务系统、加盟合同、银行流水与门店违规记录。出错后果集中在资金争议、加盟诉讼与保证金退还纠纷。

订单履约与售后答疑中，加盟商常就扣款事由、账期、发票开具进度发起追问。对话日志与审计需要把每一次追问的输入、运行详情与返回内容对应到具体会话，避免不同入口的会话被混算。日志存在本身只说明记录被保存，对账、留存与合规审计要求由完整业务方案另行落实。

## 这些特征在「对话日志与审计」这一环带来什么约束

会话身份以 chatId 区分。chatId 非空时，系统从数据库取会话，messages 数组最后一个内容作为用户问题，其余 message 被忽略。responseChatItemId 在当前 chatId 下需唯一。运行详情需要按官方契约设置 detail，非 stream 模式的中间结果保存在 responseData，stream 模式通过 event 区分。测试模式与正式调用的身份字段可能不同，输入、历史与返回内容需分别核对。

假设演练样本：某加盟商就一笔扣款发起追问。供核对的材料原文为“扣款通知载明扣款事由为门店违规，扣款金额与合同付款计划第 3 期对应，通知落款日期为 3 月 5 日。”待判定的拟稿句为“该笔扣款已经财务确认并从保证金台账扣除。”材料只说明扣款事由、金额对应关系与通知日期，未载明财务确认与台账扣减状态，该拟稿句属于未获支持，需记录证据缺口。

## 配置怎么定

| 核对项 | 输入 | 比较与观察 |
| --- | --- | --- |
| 会话身份 | 请求中的 chatId 与业务记录中的会话标识 | 两者指向同一会话，不同入口的会话分别统计 |
| 运行详情 | detail 设为 true 后的 responseData | 检查模块响应字段是否与本次追问对应 |
| 响应消息标识 | responseChatItemId | 在当前 chatId 下唯一，重复时记录实际返回 |
| 反馈记录 | userGoodFeedback 或 userBadFeedback | 与 dataId 对应，取消时不填该参数 |
| 对话列表 | offset、pageSize、loadCustomFeedbacks | 分页读取记录，核对是否读取自定义反馈 |
| 授权边界 | authProxy 开启状态与代理身份权限 | 代理身份仍需具备目标应用和会话权限 |

上表数值未在文档中给出默认值，均为本次假设试验起点，选择理由是可覆盖单次追问的核对范围，比较对象为实际请求与返回字段。

## 容易做错的三处

1. 把 chatId 非空时的会话取用当作完整上下文。系统只用 messages 最后一个内容作为用户问题，其余 message 被忽略，核对时需确认输入与历史来源。
2. 把日志存在当作合规审计完成。对账、留存与合规要求需另行落实，日志记录不承担该职责。
3. 把检索或表单当作授权执行。表单收集值，业务验证、审批、数据库写入与外部同步需有对应下游实现。

## 怎么确认配好了

1. 输入假设样本中的扣款通知原文与拟稿句，比较拟稿句是否出现材料未载明的财务确认与台账扣减表述，出现即判定为未获支持。
2. 输入同一 chatId 下重复的 responseChatItemId，比较实际返回内容，确认是否出现与唯一性要求不符的现象。
3. 输入 detail=true 的请求，比较 responseData 中模块响应与本次追问的对应关系，确认运行详情是否可定位到该次对话。以上均为纸面核对，未实际执行。
