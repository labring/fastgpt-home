# 即时零售门店履约的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样

即时零售门店履约按分钟处理线上订单，数据来源包括抖音即时零售、美团或京东到家后台、门店库存与骑手轨迹，日常文档为即时订单、拣货清单、缺货报备与配送异常单。对话日志与审计这一环要处理的，是这些业务对话在接口层留下的会话标识、对话记录与运行详情。订单按每单产生，日志随之逐单累积，审计核对需要把对话记录与对应订单材料放在同一会话范围内比照。

## 这些特征在「对话日志与审计」这一环带来什么约束

对话身份以 chatId 为会话标识、dataId 为会话下某条对话的标识，appId 指向应用。核对目标对话与业务记录时，需要结合这些标识定位，不能把不同入口的会话混算。需要对话接口运行详情时，按官方契约设置 detail，并检查 responseData；detail 为 false 时中间值不返回。日志与接口实际返回的字段构成核对依据，未返回的业务数据不能推定已完整留存。

假设演练样本：某商超到家门店在 2025 年 3 月 12 日 14 时 05 分处理一笔即时订单，拣货清单原文写「订单 A 需拣 3 件商品，其中 1 件缺货，已向顾客发起替换询问」。客服系统导出的对话记录原文写「会话 chatId 为 c-0312-1405，顾客回复：接受替换为同规格另一品牌」。一条待判定的交接请求写「将该会话标记为缺货赔付已完成，并关闭售后」。该请求缺少赔付执行与关闭操作的授权记录，属于待核实事项。

## 配置怎么定

配置围绕上述样本，只列与本功能、主任务相关的官方已说明设置或实施核对项。下表中的「本次假设试验起点」为纸面核对选定的起始值，用于与样本材料比较，属于假设设定。

| 配置项 | 官方已说明内容 | 本次假设试验起点及理由 |
| --- | --- | --- |
| appId | 应用 ID，可在应用详情路径获取 | 样本应用标识，用于限定会话归属 |
| chatId | 非空字符串时从数据库取会话，长度小于 250 | 样本会话 c-0312-1405，用于定位该笔订单对话 |
| dataId | 会话下某条对话的 ID | 取该会话内顾客回复那条记录 |
| detail | 是否返回中间值与完整结果 | 设为 true，用于取得 responseData 核对 |
| source | 会话来源，source=api 获取 API 创建的会话 | 设为 api，限定核对范围 |
| loadCustomFeedbacks | 是否读取自定义反馈 | 设为 true，用于检查该对话反馈字段 |

## 容易做错的三处

1. 把会话标识当成业务授权。样本中 chatId 只用于定位对话，不能据此认定赔付已完成或售后可关闭；赔付执行与关闭操作需要另行取得授权记录。
2. 把检索或表单当成授权执行。在对话记录中查到替换询问，不等于顾客同意已生效，也不等于缺货报备已提交；表单收集值，业务确认与写入需下游实现。
3. 把相关度分数当成权限或实体过滤。similarity、score 只表示检索相关程度，不排除无关业务或未授权记录；检索不是授权。

## 怎么确认配好了

1. 输入样本拣货清单原文与对话记录原文，比较会话 chatId 是否一致、顾客回复是否落在同一会话内。若 chatId 一致且回复内容可定位，则对话身份核对满足条件；若 chatId 缺失或指向其他会话，记录为未获支持。
2. 输入 detail=true 的请求与返回的 responseData，比较返回字段是否包含该对话的运行详情。若 responseData 含对应节点记录，则运行详情核对满足条件；若 detail 为 false 或字段缺失，记录为未返回，不推定已留存。
3. 输入待判定交接请求「标记缺货赔付已完成并关闭售后」，比较材料中是否存在赔付执行记录与关闭授权。若两者均缺失，记录为待核实；若出现同主体、同期间、同字段的互斥取值，才记为矛盾。
