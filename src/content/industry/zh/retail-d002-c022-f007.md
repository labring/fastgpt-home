# 品牌全渠道库存调拨的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样

品牌全渠道库存调拨处理货品在门店与仓之间的流动，数据来源包括 ERP 库存、门店 POS、电商订单与 WMS，日常文档为调拨申请、库存快照、门店缺货清单与调拨物流单。订单履约与售后答疑中，对话日志需要把这些业务文档与具体会话对应起来，才能支撑后续核对。调拨业务按日、周更新，日志核对按实际会话发生时间进行，不引入交易触发的批量同步机制。

## 这些特征在「对话日志与审计」这一环带来什么约束

会话由 chatId 标识，对话由 dataId 标识，应用由 appId 标识。核对时必须把同一 chatId 下的 dataId 与对应业务记录关联，不同入口的会话不能混算。需要运行详情时按官方契约设置 detail，在非流式响应中检查 responseData，流式响应中通过 event 区分节点状态与完整响应。接口实际返回的字段构成日志留存范围，未返回的业务数据不能推定已完整留存。日志存在不等于完成合规审计，对账、留存与合规要求由完整业务方案另行落实。检索或表单收集值属于输入动作，业务验证、审批、数据库写入与外部同步需要各自的下游实现。

假设演练样本：某品牌供应链值班人员提交一条交接请求，材料原文为“调拨申请单 T-0417，主体为华东仓与杭州湖滨店，对象为三件春季外套，状态为待审核，日期范围为 2025 年 4 月 17 日”。拟稿句为“该调拨申请已审批通过，可安排发货”。核对时需比较材料原文中的状态字段与拟稿句的表述。

## 配置怎么定

| 核对项 | 官方已说明设置或实施核对项 | 与样本的关联 |
| --- | --- | --- |
| 应用标识 | body.appId 或 Authorization 中 apiKey-appId | 确认请求归属目标应用 |
| 会话标识 | chatId 为唯一非空字符串，长度小于 250 | 定位样本所属会话 |
| 对话标识 | responseChatItemId 在当前 chatId 下唯一 | 关联本次响应与对话记录 |
| 运行详情 | detail=true 时检查 responseData | 获取节点状态与完整结果 |
| 会话来源 | source=api 获取 API 创建的会话 | 区分入口，避免混算 |
| 反馈字段 | userGoodFeedback、userBadFeedback 可选 | 记录用户反馈状态 |

本次假设试验起点为 pageSize 取 20，选择理由是该值可覆盖样本会话的近期记录，与响应中 total 字段比较后判断是否需继续分页。该值不是官方默认值，仅用于本次纸面核对。

## 容易做错的三处

1. 把不同 chatId 的 dataId 混入同一业务记录核对。检查输入为两个不同 chatId 的会话列表，比较 dataId 归属，观察是否出现跨会话拼接。
2. 把 detail=false 的响应当作包含完整运行详情。检查输入为一次 detail=false 请求，比较返回字段与 responseData 是否存在，观察运行详情是否缺失。
3. 把材料原文中“待审核”状态直接写成“已审批通过”。检查输入为样本原文与拟稿句，比较状态字段取值，观察拟稿句是否与原文一致。

## 怎么确认配好了

1. 使用样本原文与拟稿句，输入为“待审核”状态字段，比较拟稿句“已审批通过”，观察两者是否一致；不一致时记录为未获支持，保留证据缺口。
2. 使用同一 chatId 下的 dataId 列表，输入为两个不同 chatId 的会话，比较 dataId 归属，观察是否出现跨会话混算；出现混算则记录为需排除的不符合项。
3. 使用 detail=true 的请求，输入为样本会话，比较 responseData 中是否包含节点状态与完整结果，观察运行详情是否可获取；未返回时记录为未知，不推断系统报错或自动业务动作。
