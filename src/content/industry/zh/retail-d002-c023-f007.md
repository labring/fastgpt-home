# 品牌售后维修服务的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样

品牌售后维修围绕保修责任与线下维修网点展开，与平台退款型售后存在差别。售后系统、门店订单、维修网点反馈与国家三包目录共同构成主要数据来源。日常文档包括保修卡、维修工单、检测报告与换货审批。判断保修范围、协调维修备件、审批换退属于耗时环节，出错会带来消费者投诉、维修超时以及赔偿或换货。这些事实决定对话日志与审计环节需要把会话身份、运行详情与业务单据分开核对。

## 这些特征在「对话日志与审计」这一环带来什么约束

对话接口文档说明，chatId 为非空字符串时，系统从数据库取会话，并以 messages 数组最后一个内容作为用户问题；不传入 chatId 时不使用上下文功能。responseChatItemId 传入后会作为本次响应消息 ID 存入数据库，并要求在当前 chatId 下唯一。需要运行详情时设置 detail=true，非流式结果保存在 responseData 中，流式按 event 区分。对话 CRUD 文档说明，source=api 只获取通过 API 创建的会话，清空应用会话只清空通过 API Key 创建的会话。日志存在与完成合规审计属于两件事，对账、留存与合规要求由完整业务方案另行落实。

假设演练样本：某品牌售后中心 2025 年 3 月 10 日受理一单维修，保修卡记载购买日期 2024 年 11 月 2 日、整机保修一年，维修工单记载故障为屏幕碎裂、网点判定人为损坏，检测报告尚未出具，换货审批状态为待审核。拟稿句为「检测报告已确认人为损坏，换货审批已通过，可安排换货」。

## 配置怎么定

| 项目 | 本页相关设置或核对项 | 与样本的对应 |
| --- | --- | --- |
| 会话标识 | chatId 为非空字符串时取数据库会话，最后一个 message 作为用户问题 | 核对本单会话与工单是否同一 chatId |
| 响应标识 | responseChatItemId 在当前 chatId 下唯一 | 核对回复记录与工单对应关系 |
| 运行详情 | detail=true 时非流式结果在 responseData，流式按 event 区分 | 核对节点响应是否含检测与审批节点 |
| 会话来源 | source=api 只取 API 创建的会话 | 核对日志范围是否覆盖本单来源 |
| 清空范围 | 清空应用会话只清空 API Key 创建的会话 | 核对清理是否触及非 API 会话 |
| 反馈字段 | userGoodFeedback、userBadFeedback 可选 | 核对反馈是否挂在本单 dataId 上 |

## 容易做错的三处

1. 将拟稿句中的「检测报告已确认人为损坏」当作已发生事实。样本原文写明检测报告尚未出具，该表述缺少依据。
2. 将「换货审批状态为待审核」读成审批已通过。待审核属于未完成状态，不构成授权执行。
3. 用 source=api 的会话列表推断全部入口会话均已留存。文档说明该来源不获取页面上的会话，范围有限。

## 怎么确认配好了

1. 输入样本原文与拟稿句，比较「检测报告尚未出具」与「检测报告已确认人为损坏」，拟稿句与原文不符时判为未获支持。
2. 输入换货审批状态字段，比较「待审核」与「已通过」，状态未变为已通过时不得输出可安排换货。
3. 输入 source=api 的会话列表与页面会话，比较两者范围，列表未覆盖页面会话时记录留存缺口，不推定全部留存。
