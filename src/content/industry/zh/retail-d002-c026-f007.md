# 品牌直营门店运营的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样

品牌直营门店由品牌直接雇佣和核算，不通过加盟合同管理，订单履约与售后答疑的对话记录因此直接归属品牌主体。门店日常产生的日销售报表、排班表、陈列照片、库存调拨单，与对话日志分属不同系统，日志本身不携带这些单据的业务状态。日更或每单更新的资料只说明节奏，不构成批量同步或交易触发机制。

## 这些特征在「对话日志与审计」这一环带来什么约束

对话接口的 chatId 标识一个应用下的会话，dataId 标识会话下的对话。核对履约与售后事项时，需要把 chatId 与对应业务记录对齐，不能把不同入口的会话合并计算。需要运行详情时按官方契约设置 detail，检查 responseData；未返回的业务字段不能推定已完整留存。日志存在不表示对账、留存或合规审计已经完成，这些由完整业务方案另行落实。

假设演练样本：某品牌直营门店 3 月 12 日一笔订单申请退货，门店在对话中说明「退货申请已登记，等待区域经理审核」。拟稿句为「该订单退货已审核通过，退款将在三个工作日内完成」。原文只显示登记与等待审核，未出现审核通过或退款执行的记录。该拟稿句超出原文支持范围，属于待核实，不能作为已完成的售后结论输出。

## 配置怎么定

| 核对项 | 官方已说明内容 | 本样本核对动作 |
| --- | --- | --- |
| 会话标识 | chatId 标识应用下会话，dataId 标识对话 | 用 chatId 对齐该门店对话，用 dataId 定位退货登记那条 |
| 运行详情 | detail 返回中间值，非 stream 模式存于 responseData | 按需设置 detail，检查 responseData 实际字段 |
| 上下文 | 传入 chatId 时取数据库会话，messages 末条作为问题 | 确认待判定句所在会话的 chatId 一致 |
| 反馈字段 | userGoodFeedback、userBadFeedback 记录点赞点踩 | 检查该对话是否带反馈，反馈不表示审核状态 |
| 交互节点 | 交互配置只返回 type 与 params | 若退货流程含交互节点，核对其展示配置 |
| 业务分工 | 日志接口不承载对账、留存、合规审计 | 审核与退款状态另查业务系统，日志不替代 |

## 容易做错的三处

1. 把 chatId 相同当作业务同一。不同入口可能产生不同 chatId，样本中退货登记与审核记录若分属两个 chatId，直接合并会错配。检查输入为两个 chatId 及其对话内容，比较是否指向同一订单，观察结果应是同一订单号且状态连续。
2. 把日志存在当作审核完成。样本原文只有登记与等待审核，拟稿句写成已审核通过。检查输入为原文两句与拟稿句，比较是否出现审核通过字样，观察结果应是原文未载明该状态。
3. 把反馈字段当作授权或审批。userGoodFeedback 只记录点赞，不表示退款获批。检查输入为该对话反馈值与退款状态字段，比较两者是否同一事实，观察结果应是反馈与审批分属不同字段。

## 怎么确认配好了

- 验证一：输入样本原文「退货申请已登记，等待区域经理审核」与拟稿句「该订单退货已审核通过」。比较拟稿句是否出现原文未载明的审核通过表述。出现即判定超出支持范围，属待核实。

- 验证二：输入两个 chatId 及其各自对话内容。比较两者是否指向同一订单号与同一退货事项。指向一致且状态衔接，才满足同主体同期间核对条件；不一致则记录为待核实。

- 验证三：输入该对话的 userGoodFeedback 值与业务系统退款状态。比较两者是否描述同一事实。反馈字段有值而退款状态为空，观察结果为反馈不构成审批证据，缺口保留。
