# 品牌自播直播间运营的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样

品牌自播由品牌自己承担话术、库存和售后，达人佣金不构成主要成本结构，这一分工决定了履约与售后答疑的对话记录需要落在品牌自己的应用与数据范围内。主要数据来源包括抖店罗盘、巨量千川、直播间评论和成交明细，其中成交明细与售后工单是核对订单状态的外部依据，对话日志本身只反映交互过程。出错后果集中在虚假宣传投诉、库存拍超和转化下滑，因此对话日志的审计重点在于确认某次答疑的输入、运行详情与反馈是否可追溯，而不在于替代订单系统判定履约结果。数据更新频率为每场、每小时，本页功能不依赖该频率，故不展开。

## 这些特征在「对话日志与审计」这一环带来什么约束

对话身份以 chatId 为会话标识，dataId 为某会话下某条对话的标识，两者与业务订单记录之间没有文档说明的自动关联，需要人工按主体、时间与内容比对。需要运行详情时，按官方契约在请求中设置 detail，非流式结果保存在 responseData，流式结果通过 event 区分；未设置 detail 时中间值不返回，不能据此推定业务数据已完整留存。测试模式与正式调用的身份字段可能不同，需分别核对输入、历史与返回内容。日志存在不等于完成合规审计，对账、留存与合规要求由完整业务方案另行落实。

假设演练样本：某品牌自播团队在 2025 年 3 月 12 日一场直播后，从抖店罗盘导出订单明细，其中一笔订单备注为“已拍下，待发货，买家申请改地址”。团队拟向该买家发送一句答疑拟稿：“订单已确认，地址修改已同步仓库，今日发出。”供核对的材料原文为：订单明细显示“待发货”，售后工单显示“改地址申请审核中”，直播脚本中无地址修改承诺条款。待判定的交接请求为：请确认该拟稿句是否可直接发送。

## 配置怎么定

| 配置或核对项 | 与本页文档的关系 | 假设演练中的处理 |
| --- | --- | --- |
| appId 与 chatId | 对话接口以 appId 定位应用，chatId 定位会话 | 取本次售后答疑所用应用与会话标识，与订单明细中的买家会话比对 |
| detail 设置 | 需要运行详情时按官方契约设置 detail | 本次假设试验起点设为 true，理由是需要 responseData 核对节点输出；与 false 时无中间值的情形比较 |
| responseChatItemId | 传入后作为响应消息 ID 存入数据库，同一 chatId 下需唯一 | 假设试验起点为按订单号生成，检查是否与既有值重复 |
| source=api 的会话列表 | 获取会话列表时 source=api 只取 API 创建的会话 | 核对本次答疑会话是否出现在该列表，页面会话不在其中 |
| loadCustomFeedbacks | 获取对话列表时可选读取自定义反馈 | 本次假设试验起点设为 true，用于核对点赞点踩记录是否随对话返回 |
| 交互节点返回字段 | 交互节点只返回 type 与 params，内部运行态字段不返回 | 核对表单输入是否以对象序列化字符串作为 messages 值 |

## 容易做错的三处

1. 把 detail=false 的返回当作完整运行详情。detail=false 时中间值与完整结果不返回，输入为一次 detail=false 的响应，比较对象为所需节点输出，可观察结果是 responseData 缺失，此时不能声称业务数据已留存。
2. 把检索或表单提交当作授权执行。输入为一次表单输入交互，比较对象为订单明细中的售后状态，可观察结果是表单仅收集值，业务验证、审批与数据库写入需下游实现，待审核不等于已批准。
3. 把相似度分数当作权限或实体过滤。输入为一次带 score 的检索返回，比较对象为买家身份与订单归属，可观察结果是 score 只表示相似程度，不排除无关业务或未授权记录。

## 怎么确认配好了

1. 输入假设样本中“待发货”的订单明细与“改地址申请审核中”的工单，比较拟稿句“地址修改已同步仓库，今日发出”与材料原文，可观察结果是材料未载明同步完成或当日发出，该句未获支持，应记录为待核实。
2. 输入一次 detail=true 的对话请求，比较返回的 responseData 中模块输出与请求参数，可观察结果是节点状态与完整结果出现；若改为 detail=false，同一比较下 responseData 缺失，据此区分两种设置的实际差异。
3. 输入一次 chatId 相同的两次请求，比较 responseChatItemId 是否重复，可观察结果是重复值违反唯一要求；若 chatId 不同，则同一值不构成冲突，需按会话分别核对。
