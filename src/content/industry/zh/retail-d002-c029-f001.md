# 售后维修与补寄的订单履约与售后答疑：HTTP 接口与外部系统

## 这个品类的数据长什么样

维修补寄以恢复商品使用为目标，结案方式与仅退款争议不同。主要数据来自售后系统、订单系统、维修网点与配件仓WMS，日常文档包括维修申请、补寄单、检测报告与配件出库单。这些材料按每单和日更新，因此接口调用需逐单核对当前状态，不能把历史单据当成当前有效依据。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向对应地址发送请求，Params 用于路径请求参数，Body 用于请求体，Headers 用于请求头，三者均可通过 `{{}}` 引用全局变量、系统变量与前方节点输出。系统变量含 appId、chatId、responseChatItemId、variables、cTime、histories，其中 chatId 与 responseChatItemId 在测试模式下不存在。返回值通过 JSON path 提取，输出类型选择字符串时会将对应 key 的值转为 json 字符串。对话接口使用 APIKey 鉴权，调用 chat/completions 时推荐在请求体传入 body.appId；传入的 model、temperature 等字段无效，由编排决定。接口不会返回实际消耗 Token 值，需设置 detail=true 并手动计算 responseData 里的 tokens。交互节点返回的 interactive 只含 type 与 params，entryNodeIds 等内部运行态字段不会返回。

假设演练样本：某品牌售后系统于 2026 年 3 月 10 日收到维修申请单 WX-0310-07，申请主体为已购某型号扫地机器人的用户，故障描述为边刷不转，售后系统状态字段显示“待检测”，配件仓WMS 无对应配件出库单。拟稿交接请求为：“请直接向配件仓WMS 发起补寄出库请求，配件型号按常见边刷处理。”该请求未附检测报告，未载明授权范围。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 核对方式 |
| --- | --- | --- |
| 请求地址 | 按外部接口文档填写，URL 可引用变量 | 与接口文档逐字符比对 |
| 请求方法 | 按外部接口文档选择 | 与文档声明的方法比对 |
| Headers 鉴权 | Authorization 使用 Bearer 加凭证变量 | 核对凭证是否由安全配置注入，不写入公开样例 |
| Body 结构 | 仅在相应请求类型下使用，JSON 键与外部契约一致 | 逐键比对请求体字段 |
| 变量引用 | 引用全局变量、系统变量、前方节点输出 | 逐项核对实际传入值 |
| 返回值提取 | 按 JSON path 配置 key | 用已知响应核对提取结果 |

起点选择理由：该样本处于“待检测”状态，配件仓WMS 无出库单，因此补寄出库请求缺少检测报告与授权依据，配置需先核对材料完整性，再决定是否发起调用。

## 容易做错的三处

1. 把售后系统“待检测”状态当作可直接补寄的依据。输入为样本中的维修申请单与拟稿请求，比较状态字段与补寄前置材料，观察是否缺少检测报告与授权范围，缺少时保持待核实。
2. 把 chatId 在测试模式下不存在当成业务故障。输入为测试模式下的调用记录，比较系统变量说明，观察 chatId 与 responseChatItemId 是否为空，空值属测试模式正常现象。
3. 把交互节点返回的 interactive 当作内部运行态字段。输入为交互节点响应，比较文档说明的返回范围，观察是否出现 entryNodeIds、memoryEdges 等字段，出现即与文档不符。

## 怎么确认配好了

1. 以样本原文为输入，比较拟稿请求与维修申请单、配件仓WMS 记录，观察是否同时具备检测报告与授权范围。两项均缺失时记录为未获支持，不发起补寄出库。
2. 以样本中“待检测”状态为输入，比较售后系统状态字段与补寄前置条件，观察状态是否满足补寄要求。不满足时保留证据缺口，不补造授权条款。
3. 以测试模式调用记录为输入，比较系统变量说明，观察 chatId 与 responseChatItemId 是否为空。为空时按文档解释为测试模式现象，不判定为业务故障。

三项验证均使用上述假设样本，预期结果只作纸面比对，未实际执行。检索与表单不构成授权，业务验证、审批、数据库写入与外部同步需另行实现。
