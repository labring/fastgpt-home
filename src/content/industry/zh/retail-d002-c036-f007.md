# 多仓分仓与库存同步的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样
多仓分仓决定订单从哪个仓发货，发生在订单路由阶段。主要数据来自 WMS、OMS、ERP 库存与平台库存接口，日常文档包括分仓规则、库存同步表、调拨单与缺货预警。数据更新频率为日或小时。对话日志与审计要处理的，是这些业务环节在客服问答中留下的会话记录、运行详情与反馈字段。日志存在仅说明接口返回了内容，对账、留存与合规要求由完整业务方案另行落实。

## 这些特征在「对话日志与审计」这一环带来什么约束
结合 chatId 核对目标对话与业务记录，不把不同入口的会话混算。需要运行详情时按官方契约设置 detail，检查 responseData 中的模块状态与完整结果。核对日志与接口实际返回字段，未返回的业务数据不能推定已完整留存。测试模式的身份字段可能不同，分别核对输入、历史与返回内容。

假设演练样本：某供应链计划员在 2025 年 3 月 10 日提交一条交接请求，原文为“3 月 10 日 A 仓可售库存 120 件，B 仓 80 件，分仓规则优先级 A 仓高于 B 仓，请确认 3 月 11 日订单 001 从 A 仓发货”。拟稿句为“订单 001 已确认从 A 仓发货”。该请求处于待判定状态，不构成发货执行或库存扣减。

## 配置怎么定
| 配置项 | 本次假设起点 | 核对方式 |
| --- | --- | --- |
| chatId | 假设样本用 chat-001 | 与业务记录逐条比对，确认同一会话 |
| detail | 假设设为 true | 检查 responseData 是否含模块状态 |
| responseChatItemId | 假设用 resp-001 | 确认在当前 chatId 下唯一 |
| source | 假设取 api | 仅取 API 创建的会话，不混页面会话 |
| loadCustomFeedbacks | 假设设为 true | 读取自定义反馈字段 |
| pageSize | 假设取 10 | 与 offset 配合分页取记录 |

上述数值为本次纸面演练起点，不是官方默认值。选择理由为便于小样本核对，比较对象是官方文档中对应字段的说明与本次样本记录。

## 容易做错的三处
1. 把 chatId 不同的会话合并统计。输入为两个 chatId，比较是否同一会话，观察结果应为分别列出。
2. 把 detail=false 的响应当作含运行详情。输入 detail=false，比较 responseData 是否存在，观察结果应为该字段缺失。
3. 把交互节点返回的表单配置当作已提交。输入为 interactive 展示配置，比较是否含用户输入值，观察结果应为仅含 type 与 params。

## 怎么确认配好了
1. 输入假设样本原文与拟稿句，比较拟稿句是否出现“已确认从 A 仓发货”的完成表述，观察结果应为待核实，不判定为已执行。
2. 输入 chat-001 与另一 chatId，比较两次返回的会话标识，观察结果应为各自独立，不合并计算。
3. 输入 detail=true 的请求，比较 responseData 中模块字段与接口实际返回，观察结果应为字段对应，未返回的业务数据记录为缺失。
