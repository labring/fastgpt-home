# 快递面单与揽收交接的订单履约与售后答疑：HTTP 接口与外部系统

## 这个品类的数据长什么样

快递交接发生在包裹离仓节点，责任判断依赖承运商扫描记录。电子面单、交接清单、揽收扫描记录、异常件登记构成核对材料。数据按每批与日更新，售后答疑需要把这些材料与外部系统的请求记录对齐。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向指定地址发送请求，Params、Headers、Body 分别承载路径参数、请求头与请求体，URL 与三类数据均可通过 `{{}}` 引用全局变量、系统变量和前方节点输出。返回值通过 JSON path 提取，输出类型选择字符串时会把对应值转成 json 字符串。对话接口以 APIKey 鉴权，调用 `chat/completions` 时推荐在请求体传入 `body.appId`，也支持 `Authorization: Bearer <apiKey>-<appId>`。`chatId` 为空时不使用平台上下文，非空时以 messages 数组最后一个内容作为用户问题。`chatId` 与 `responseChatItemId` 在测试模式下不存在。传入的 `model`、`temperature` 由编排决定，不随 API 参数改变。detail 为 true 时可取得 responseData 中间值。

假设演练样本：某仓库发运组在 2025 年 3 月 11 日交接一批包裹，交接清单记录“包裹 12 件，承运商网点已到场”，揽收扫描记录显示“已扫描 9 件”，异常件登记为“3 件待查”。拟稿句为“本批 12 件已全部由承运商揽收”。判定该句需要同主体、同批次的扫描记录支持，现有材料只支持 9 件已扫描，3 件状态待核实。

## 配置怎么定

| 配置项 | 本页用途 | 核对方式 |
| --- | --- | --- |
| 请求地址与方法 | 对接承运商揽收查询接口 | 按外部接口文档选择，地址可引用变量 |
| Headers | 传递鉴权凭证 | 凭证经安全配置注入，不写入公开样例 |
| Body | 提交批次查询条件 | 仅在相应请求类型下生效，核对 JSON 结构 |
| 变量引用 | 传入批次号与日期 | 逐项核对实际传入值 |
| 返回值提取 | 取得扫描件数与状态 | 按 JSON path 配置 key |
| 输出类型 | 决定返回值格式 | 选择字符串时转为 json 字符串 |

## 容易做错的三处

1. 把交接清单的 12 件当作揽收完成数。清单只记录交接动作，扫描记录才反映承运商责任节点，两者字段不同。
2. 把测试模式下 `chatId` 为空当成业务故障。该字段在测试模式下不存在，属于文档说明的行为。
3. 把 HTTP 请求成功当作外部系统已写入业务结果。请求返回只说明接口响应，数据库写入与外部同步需要下游实现。

对应检查：第一项比较交接清单件数与扫描记录件数，两者一致才支持全部揽收的表述；第二项比较运行模式与字段是否存在，测试模式下缺失不构成异常；第三项比较接口响应与业务系统记录，响应存在而记录缺失时业务结果待核实。

## 怎么确认配好了

- 验证一：输入假设样本的交接清单与扫描记录，比较 12 件与 9 件，拟稿句“已全部揽收”不获支持，需改为已扫描 9 件、3 件待核实。

- 验证二：输入测试模式下的请求，比较 `chatId` 是否存在，字段缺失符合文档说明，不判定为故障。

- 验证三：输入接口返回的扫描件数，与交接清单件数比较，两者相等时该批次扫描数量一致；返回为空数组时下游设计按空结果处理，不推断为全部揽收。

以上均为纸面核对，未执行实际请求，未取得承运商系统返回值，未发生业务写入或同步。
