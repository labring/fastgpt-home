# 投诉举报与监管回复的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样
投诉举报与监管回复面向平台或监管机关，需要正式证据与整改文字，与售后维修补寄的日常处理不同。数据来源包括12315平台、平台投诉中心、客服聊天与订单系统，日常文档为投诉工单、监管询问函、订单证据与整改报告。本页只处理该品类在订单履约与售后答疑中的对话日志与审计，不把日志存在等同于已完成合规审计。资料给出的更新频率为不定期、每案，本页不据此推导批量同步、实时或交易触发机制。

## 这些特征在「对话日志与审计」这一环带来什么约束
对话身份需要结合 chatId 核对目标对话与业务记录，不同入口的会话不混算。需要运行详情时按官方契约设置 detail，检查 responseData 中实际返回的字段；未返回的业务数据不能推定已完整留存。检索与相似度只承担召回与排序，不承担权限或实体隔离，检索结果不构成授权。对账、留存与合规要求由完整业务方案另行落实。交互节点返回的 interactive 只含 type 与 params，内部运行态字段不返回；继续运行需保持 chatId 一致，表单输入以对象序列化字符串作为 messages 内容。

假设演练样本：某店铺客服主管收到一份监管询问函，编号假设为 XF-2024-001，涉及订单假设编号 DD-2024-001，投诉人称客服曾承诺补寄。供核对材料原文为：“本店客服于2024年3月1日在会话中表示可补寄，补寄发出时间以后续通知为准。”拟判定句为“该会话已完成补寄并已通知投诉人”。该句含完成补寄与已通知两个事实，材料仅载明可补寄的表示，未载明补寄是否发出、是否通知。

## 配置怎么定
下表围绕本页样本，列出官方已说明设置或实施核对项。假设试验起点仅用于本次纸面核对，不作为官方默认值。

| 配置项 | 本次假设起点 | 核对方式 |
| --- | --- | --- |
| appId | 假设填 XF-APP-001 | 与监管询问函所指向应用比对，确认同主体 |
| chatId | 假设填 XF-CHAT-001 | 与客服聊天记录中该会话标识比对 |
| detail | 假设设为 true | 检查 responseData 是否含节点响应，未含则记录缺口 |
| messages | 假设末条为投诉人原话 | 与客服聊天原文比对，确认同字段同期间 |
| responseChatItemId | 假设填 XF-RESP-001 | 在当前 chatId 下核对唯一性 |
| source | 假设填 api | 与获取会话列表的 source 说明比对，区分入口 |

## 容易做错的三处
1. 把检索命中当作授权。输入为相似度较高的历史会话，比较对象为当前投诉人的身份与订单归属，观察结果为是否出现跨主体记录。相似度不排除无关业务或未授权记录。
2. 把可补寄表示写成已完成补寄。输入为上述材料原文，比较对象为拟判定句中的“已完成补寄”，观察结果为材料是否载明发出与通知。未载明即未获支持。
3. 把待审核当作已批准。输入为交接请求中的“待审核”状态，比较对象为审批完成证据，观察结果为是否存在批准记录。待审核不证明缺少操作权限，也不等于批准。

## 怎么确认配好了
1. 输入假设材料原文与拟判定句，比较“可补寄”与“已完成补寄并已通知”，观察拟判定句是否超出原文范围。超出即不满足。
2. 输入 chatId 假设值 XF-CHAT-001，比较客服聊天记录中该会话标识，观察两者是否指向同一会话。一致才满足同主体核对。
3. 输入 responseData 假设为空数组 []，比较下游设计对空引用的承接条件，观察下游是否按空结果处理。不声称虚构规则检索必返回空。
