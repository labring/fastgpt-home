# 拼多多低价活动店铺运营的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样

拼多多低价活动店铺运营围绕活动资源位、活动库存与退款率波动展开，日常材料包括活动报名表、商品成本测算表、售后退款单与平台站内信。订单履约与售后答疑环节需要把买家会话、退款单状态与活动报名信息放在同一时间线上核对。对话日志与审计在此处的作用，是保留会话与接口返回的可核对记录，供运营交接时确认某条答复对应哪个会话、哪个对话。

## 这些特征在「对话日志与审计」这一环带来什么约束

会话由 chatId 标识，对话由 dataId 标识，二者与业务单据的对应关系需要人工核对。对话接口在 chatId 非空时从数据库取会话，并以 messages 数组最后一条内容作为用户问题，其余 message 被忽略。需要中间值时设置 detail=true，非流式结果保存在 responseData 中。日志中未返回的字段属于未提供，不能据此推断业务数据已完整留存。检索与相似度不承担权限判断，检索库同向量模型的要求不扩展到外部系统。审计对账、留存与合规由完整业务方案另行落实。

假设演练样本：某店铺 3 月 12 日一场低价活动结束后，运营交接材料含两句原文——“售后退款单编号 A-0312-07，状态：待商家处理，商品：活动款短袖，数量 2 件，申请时间 3 月 12 日”“平台站内信：该活动资源位库存核对截止 3 月 13 日 18 时”。待判定拟稿句为“A-0312-07 已处理完毕，买家已收到退款”。核对对象是退款单状态字段与拟稿句的完成表述，主体为同一退款单，期间为 3 月 12 日至 13 日。

## 配置怎么定

| 核对项 | 本次假设试验起点 | 比较方法与依据 |
| --- | --- | --- |
| 会话标识 chatId | 沿用交接单登记的会话标识 | 与接口返回的 chatId 逐字比较，确认指向同一会话 |
| 对话标识 dataId | 由会话记录列表取得 | 与 getResData 请求中的 dataId 比较，确认指向同一轮对话 |
| detail 取值 | 需要运行详情时设为 true | 非流式响应中检查 responseData 是否出现，未设则该项未知 |
| 响应消息标识 responseChatItemId | 本次假设起点为交接单登记值 | 在同一 chatId 下比较唯一性，重复则记录为待核实 |
| 中间值与最终回答 | 分别取自 responseData 与 choices | 逐字段比较，未返回的字段保留为缺失 |
| 会话来源 source | 交接核对时取 api | 与历史列表返回的会话来源比较，页面会话不计入本次范围 |

以上数值为本次纸面演练起点，选值理由是可逐字比对；比较对象为接口实际返回字段，不作默认值声明。

## 容易做错的三处

1. 把相似度或检索结果当作权限判断，用 score 高低推断某条记录属于该店铺或已被授权。检查方式：输入为一次带 score 的检索返回，比较对象为该记录的 datasetId 与业务归属登记，观察结果为二者是否一致；不一致时记录为待核实。
2. 把“待商家处理”的退款单写成已处理完毕。检查方式：输入为退款单 A-0312-07 的状态字段原文，比较对象为拟稿句中的完成表述，观察结果为状态取值与完成表述是否互斥；互斥则判定拟稿句未获支持。
3. 把交互节点的展示配置当作已提交。检查方式：输入为 event=interactive 返回的 type 与 params，比较对象为后续是否再次发起会话并传入选择结果，观察结果为是否存在该次请求；仅收到配置时记录为等待状态。

## 怎么确认配好了

- 验证一：输入拟稿句“A-0312-07 已处理完毕，买家已收到退款”，比较对象为退款单状态字段“待商家处理”，观察结果为二者是否互斥。互斥时该拟稿句未获支持，需保留状态缺口，不能补造授权或处理记录。

- 验证二：输入一次 chatId 非空的会话请求与一条 messages 末尾问题，比较对象为返回中该 chatId 对应的会话记录，观察结果为问题与记录是否指向同一轮对话；其余 message 是否被忽略以实际返回为准。

- 验证三：输入一次设置 detail=true 的非流式请求，比较对象为响应中 responseData 与 choices 两部分，观察结果为运行详情字段是否出现；未出现时该项为未知，不推断原因，也不断言存在某错误码或自动动作。
