# 渠道应收账款催收的订单履约与售后答疑：HTTP 接口与外部系统

## 这个品类的数据长什么样
渠道应收账款催收发生在赊销之后，核心是授信与现金回收。主要数据来自财务系统、银行回单、经销商订单和销售合同，日常处理的文档包括应收账龄表、催款函、授信协议和发货冻结通知。这类数据更新以周、月为周期，订单履约与售后答疑环节需要把账龄、授信余额、发货冻结状态与外部接口的请求值对应起来。HTTP 接口在此承担向外部业务服务发起请求、解析返回值并交回工作流的作用，接口本身不完成授信判断、审批或数据库写入，这些动作需要下游服务实现。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
HTTP模块向指定地址发送请求，URL、Params、Body与Headers支持 `{{}}` 引用全局变量、系统变量或前方节点输出。响应按JSON path解析，选字符串输出时值转为json字符串。chatId及responseChatItemId是会话系统变量，测试模式下不存在；外部授信接口响应按其契约核。FastGPT对话API的appId及运行态字段不作为外部服务通用参数；业务判断、审批或写入需对应的下游实现。

假设演练样本：某品牌财务在 2025 年 3 月核对经销商 A 的发货冻结状态。材料原文为「授信协议约定经销商 A 的信用额度为 50 万元，账期 30 天；截至 2025 年 3 月 20 日，应收账龄表显示经销商 A 逾期金额 12 万元；发货冻结通知草稿载明拟对经销商 A 暂停发货，审批栏为空」。待判定拟稿句为「经销商 A 已超授信，本次发货冻结已生效」。判定需要同主体、同期间、同一字段的证据，审批栏空白只说明现有草稿缺少批准记录，实际审批阶段及冻结生效状态待核，不推定待审核或已拒绝。

## 配置怎么定
| 配置项 | 本次假设试验起点 | 核对方式与依据 |
| --- | --- | --- |
| 请求地址 | 外部授信查询服务地址，含 `{{}}` 变量占位 | 按外部接口文档选择地址与方法，地址可引用已提供的变量 |
| Headers 鉴权 | Authorization 使用 Bearer 加凭证变量 | 凭证通过安全配置注入，公开样例不写入实际值 |
| Body 结构 | 经销商标识、期间等均按真实授信契约核 | 不把FastGPT应用appId当成外部通用必填项，字段与类型待核 |
| 变量引用 | 引用前方节点输出的账龄金额与授信额度 | 引用全局变量、系统变量和前方节点输出，核对实际传入值 |
| 返回值解析 | 配置 key 提取授信余额与冻结状态字段 | 按 JSON path 提取，输出类型选择字符串时转为 json 字符串 |
| 调试身份 | 测试模式下 chatId 与 responseChatItemId 为空 | 空值属于测试模式差异，不当作业务故障 |

## 容易做错的三处
1. 把返回值解析配置当成接口返回值的开关。输入是接口响应 JSON，比较对象是配置的 key 与 JSON path 提取结果，可观察现象是 key 未命中时对应输出为空。错误在于认为配置了 key 就代表接口已返回该字段。
2. 把交互节点的表单提交当作业务审批完成。输入是表单收集的经销商标识与金额，比较对象是审批栏状态与提交记录，可观察现象是审批栏仍为空。表单只收集值，审批与写入需要下游实现。
3. 从外部响应缺少chatId推断故障。直接核节点运行模式及系统变量来源，测试模式按文档没有该变量；外部响应应包含什么由授信接口契约决定。

## 怎么确认配好了
1. 输入额度50万元、逾期12万元及冻结通知草稿，分别核总授信占用、逾期余额和冻结生效证据。12万元不是总占用，总占用未给，无法判是否超授信；审批栏空白也不证明未批准，冻结生效依据缺失，两项主张分别待核。
2. 对一次 HTTP 请求，输入为配置了 key 的返回值解析。比较接口响应 JSON 与提取结果，确认 key 命中时输出与响应字段一致，key 未命中时输出为空并记录该缺口，不推断接口报错原因。
3. 对一次交互节点表单提交，输入为表单收集的经销商标识与金额。比较提交值与审批栏状态，确认表单值进入下游前审批栏仍为空，业务审批与数据库写入属于需另接系统实现的动作，不因表单提交而视为已完成。
