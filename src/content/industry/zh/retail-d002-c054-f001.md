# 渠道窜货稽查的订单履约与售后答疑：HTTP 接口与外部系统

## 这个品类的数据长什么样

渠道窜货稽查处理区域与价格秩序，不处理返利金额。数据来源包括防伪码系统、电商平台价格、经销商发货记录与市场巡检。日常文档为窜货投诉单、防伪码记录、处罚通知与调查照片。这些材料在订单履约与售后答疑环节进入 HTTP 接口时，通常以投诉单编号、防伪码、店铺链接、发货记录字段和照片链接的形式出现。数据更新频率为周和不定期，因此接口调用多由人工在受理投诉或答复经销商时触发，不由定时任务驱动。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向指定地址发送请求，Params、Body、Headers 与 URL 均可通过 `{{}}` 引用变量，变量来自全局变量、系统变量和前方节点输出。系统变量包含 appId、chatId、responseChatItemId、variables、cTime 与 histories。chatId 与 responseChatItemId 在测试模式下不存在，调试时出现的空值不能当作业务故障。调用 chat/completions 时，appId 优先级为 body.appId、`<apiKey>-<appId>`、apikey 关联的 appId。传入的 model、temperature 等字段无效，由编排决定。detail=true 时可在 responseData 的 tokens 中自行计算消耗。authProxy 需团队所有者开启，代理身份仍需具备目标应用和会话权限。HTTP 请求本身不构成对窜货事实、处罚权限或退款资格的确认，检索与表单收集不产生授权。

假设演练样本：一份窜货投诉单原文写「投诉单编号 XC-2024-0312，被投诉店铺为某平台店铺 A，投诉商品防伪码 8801 于 2024 年 3 月 5 日在华东区域外扫码，随附调查照片两张，经销商发货记录显示该码批次发往华南」。一条待判定拟稿句为「该店铺窜货事实成立，同意按处罚通知执行扣款」。此样本中，投诉单仅记录扫码地点与批次流向，未载明处罚审批意见，拟稿句将待核实事实写成已成立并直接执行扣款，超出材料支持范围。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 请求地址 | 按外部防伪码系统文档填写的查询地址 | 与外部接口文档给出的路径逐字符比对 |
| 请求方法 | 查询用 GET，提交用 POST | 与外部接口契约声明的方法比对 |
| Params | 填入防伪码字段引用 `{{code}}` | 与投诉单原文的防伪码值比对 |
| Headers | Authorization 用 Bearer 引用凭证变量 | 检查凭证是否来自安全配置，未写入样例 |
| Body | POST 时按外部契约构造 JSON | 与外部接口文档字段名和类型逐项比对 |
| 返回值提取 | 按 JSON path 配置 key | 与接口响应实际结构比对，确认取到目标值 |

上述起点为本次假设试验的取值，不属官方默认值。数值类配置未在文档中给出默认，此处不指定。

## 容易做错的三处

1. 把调试模式下不存在的 chatId 或 responseChatItemId 空值当成接口故障。检查方式：确认当前是否为测试模式，对比系统变量说明中标注的「测试模式下不存在」条件，观察该字段是否仅在测试态为空。
2. 把投诉单中的扫码地点记录当作窜货事实成立。检查方式：将拟稿句与投诉单原文逐句比对，原文未载明处罚审批意见时，判定为未获支持。
3. 把 HTTP 返回的查询结果当作已授权执行处罚。检查方式：核对返回内容是否仅为数据查询结果，与处罚通知的审批状态字段比对，确认无审批记录时不得进入执行。

## 怎么确认配好了

1. 输入假设样本中的投诉单原文与拟稿句，比较拟稿句是否引入原文未载明的「事实成立」与「执行扣款」，观察拟稿句在原文无审批意见时是否被标为待核实。
2. 输入防伪码字段引用 `{{code}}`，比较实际传入值与投诉单原文的防伪码 8801，观察提取结果是否与原文一致。
3. 输入 detail=true 的请求，比较 responseData 中是否出现 tokens 字段，观察能否据此手动计算消耗；若返回为空数组，则按纸面输入核对下游设计，不推断虚构规则必然返回空。

以上均为纸面核对，未实际调用接口，未产生审批、扣款或同步动作。
