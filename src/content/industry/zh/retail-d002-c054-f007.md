# 渠道窜货稽查的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样

窜货稽查围绕区域与价格秩序展开，材料来自防伪码系统、电商平台价格、经销商发货记录与市场巡检。日常文档包括窜货投诉单、防伪码记录、处罚通知与调查照片，更新频率为周与不定期。对话日志与审计这一环要处理的，是订单履约与售后答疑过程中产生的会话记录：谁在什么时间问了哪一单的履约或售后问题、系统返回了什么、这些记录能否与业务单据对应。

与返利核算不同，本环节不处理返利金额，只处理会话与业务记录的对应关系。日志留存本身不构成合规审计，对账与留存要求由完整业务方案另行落实。

## 这些特征在「对话日志与审计」这一环带来什么约束

会话身份依靠 chatId 区分。不传入 chatId 时不使用平台上下文，完全由 messages 构建；传入非空字符串时从数据库取会话，并以 messages 数组最后一个内容作为用户问题，其余 message 被忽略。chatId 需自行保证唯一且长度小于 250。responseChatItemId 若传入，须在当前 chatId 下唯一。

需要运行详情时按官方契约设置 detail。stream 模式下中间值通过 event 区分，非 stream 模式结果保存在 responseData 中。模块名、模块类型、运行时间、tokens、quoteList 等字段是否出现，以实际返回为准；未返回的业务数据不能推定已完整留存。

假设演练样本：材料原文为「投诉单号 TS-0417 记录经销商甲于 4 月 12 日提交窜货投诉，涉及防伪码 A 段；系统会话 chatId 为 demo-0417，该会话内一条 AI 回复内容为『该防伪码查询记录已受理』；处罚通知尚未签发。」待判定拟稿句为「该窜货投诉对应的处罚已执行完毕。」核对要点：材料只有投诉受理与查询记录，处罚通知处于未签发状态，拟稿句超出材料范围，属未获支持。

## 配置怎么定

| 配置项 | 本页取值或核对项 | 依据与说明 |
| --- | --- | --- |
| appId | 假设起点为演示应用标识 demo-app | 用于定位应用，与 chatId 组合核对会话归属 |
| chatId | 假设起点为 demo-0417 | 长度须小于 250，须自行保证唯一 |
| detail | 假设起点为 true | 需要运行详情时启用，非 stream 模式结果在 responseData |
| stream | 假设起点为 false | 与 detail 组合决定中间值获取方式 |
| loadCustomFeedbacks | 按需读取 | 获取对话列表时可选，用于读取自定义反馈 |
| 运行详情核对 | 人工比对 responseData 字段 | 字段是否出现以实际返回为准，不推定完整留存 |

以上数值均为本次假设演练的起点，选择理由是便于在纸面样本中逐项对照，并非官方默认值。

## 容易做错的三处

1. 把 chatId 当作可省略的字段。不传入 chatId 时不使用平台上下文，历史会话不会被自动取用；若把两种入口的会话混算，同一投诉单的对话记录会与另一入口的记录合并。检查方式：输入同一 chatId 的两条请求与不传 chatId 的一条请求，比较返回中是否出现历史对话内容，观察不传时是否仅由 messages 构建上下文。
2. 把 detail 设为 false 后仍期待 responseData。detail 为 false 时中间值不返回，非 stream 模式结果保存在 responseData 的前提是 detail 为 true。检查方式：分别以 detail 为 true 与 false 请求，比较响应中是否存在 responseData 字段，观察 false 时该字段缺失。
3. 把会话记录存在等同于合规审计完成。日志留存与对账、合规要求由完整业务方案另行落实。检查方式：对照假设样本，检查拟稿句是否引用了材料中不存在的处罚签发事实，观察该句是否超出投诉受理与查询记录范围。

## 怎么确认配好了

1. 会话身份核对。输入假设样本中的 chatId demo-0417 与另一 chatId，比较返回的会话内容是否分别对应该投诉单，观察两者是否未混算。预期为各自独立，未实测。
2. 运行详情核对。输入 detail 为 true 的请求，比较 responseData 中出现的模块名与运行时间字段，观察字段是否与官方契约描述一致。字段缺失时记录缺口，不推定留存完整。
3. 拟稿句范围核对。输入假设样本材料原文与拟稿句「该窜货投诉对应的处罚已执行完毕」，比较拟稿句是否引用了处罚通知签发这一材料未载明的事实，观察该句是否应判定为未获支持。预期为未获支持，未实测。
