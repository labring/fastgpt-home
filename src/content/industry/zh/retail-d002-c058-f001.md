# 生鲜供应商索赔的订单履约与售后答疑：HTTP 接口与外部系统

## 这个品类的数据长什么样

生鲜供应商索赔追究到货质量责任，不处理门店自然损耗。质量异常单、照片证据、扣款通知与索赔对账单分别来自质检系统、WMS 验收、供应商合同与财务对账，每批与每月两种节奏并存。订单履约与售后答疑要回答的是：某批到货的质量异常处于什么状态、谁在什么授权下可以推动扣款或补货。质检结论、验收记录与合同条款分属不同系统，HTTP 接口只能传递字段值，不能替代业务判定。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向指定地址发送请求，Params 用于路径参数，Body 用于请求体，Headers 用于请求头，三者均可用 `{{}}` 引用全局变量、系统变量与前方节点输出，URL 同样可引用变量。返回值通过 JSON path 或 JS 对象取值规则提取，出参可选择字符串类型。系统变量中 chatId 与 responseChatItemId 在测试模式下不存在，调试时取不到值属于预期现象。对话接口以 APIKey 鉴权，推荐在请求体传入 body.appId；appId 优先级为 body.appId、`<apiKey>-<appId>`、apikey 关联的 appId。传入的 model、temperature 等参数字段无效，由编排决定。detail=true 可返回 responseData 中间值，token 需自行计算。authProxy 代理团队成员身份需团队所有者开启，代理身份仍需目标应用与会话权限。接口返回的 interactive 只是展示配置，用户选择或表单输入需要再次发起会话才能继续运行。

假设演练样本：某批叶菜到货验收记录载明“2025 年 3 月 12 日，批次 A，验收发现叶片萎蔫比例超出合同附件约定，质检已出具质量异常单，扣款金额待供应商确认”。一张拟稿交接单写“该批扣款已执行，供应商已同意补货”。材料只显示质量异常单已出具、扣款金额待确认，未显示供应商同意，也未显示扣款执行记录。拟稿句的两项断言均未获支持。

## 配置怎么定

| 配置项 | 本次假设起点 | 依据与比较方法 |
| --- | --- | --- |
| 请求地址与方法 | 按外部接口文档填写，地址引用 `{{BaseUrl}}` 变量 | 与外部接口契约逐项比对路径与方法 |
| Headers 鉴权 | Authorization 引用 `Bearer {{token}}` | 与密钥使用规范比对，凭证不写入公开样例 |
| Body 结构 | 按外部接口契约声明 JSON 字段 | 与外部接口文档字段名、类型逐项比对 |
| 返回值提取 | 按接口响应实际结构配置 key | 与 JSON path 语法及实际响应比对 |
| chatId 使用 | 传入非空字符串以使用会话上下文 | 长度小于 250，与唯一性要求比对 |
| detail 取值 | 需要中间值时设为 true | 与响应结构说明比对，token 需自行计算 |

## 容易做错的三处

1. 把质量异常单已出具当成扣款已执行。输入是材料原文“质检已出具质量异常单，扣款金额待供应商确认”，比较对象是拟稿句“该批扣款已执行”，观察结果是材料未载明扣款执行记录，拟稿句该断言未获支持。
2. 把待供应商确认当成供应商已同意。输入是“扣款金额待供应商确认”，比较对象是“供应商已同意补货”，观察结果是材料未载明同意记录，该断言未获支持。
3. 把测试模式下 chatId 为空当成业务故障。输入是测试模式调用，比较对象是系统变量说明中 chatId 在测试模式下不存在的记载，观察结果是该空值属于文档已说明现象，不能据此判定外部系统异常。

## 怎么确认配好了

1. 输入假设样本材料原文与拟稿句，比较拟稿句两项断言与材料载明状态，观察结果是两项断言均标记为未获支持，材料缺口记录为扣款执行记录与供应商同意记录。
2. 输入一条引用 `{{token}}` 的 Headers 配置，比较实际请求头与密钥使用规范，观察结果是鉴权凭证未出现在公开样例中，引用关系与规范一致。
3. 输入一条 detail=true 的请求，比较响应中 responseData 与文档说明的中间值结构，观察结果是中间值字段按文档结构返回，token 数值由调用方自行计算，不依赖接口直接返回。
