# 生鲜称重分拣的订单履约与售后答疑：HTTP 接口与外部系统

## 这个品类的数据长什么样
称重分拣在仓内履约环节完成，核心数据是重量与规格，主要来源为 WMS、电子秤、订单系统与质检照片。分拣任务单、称重标签、少称补偿单、质检记录按每单生成，日维度汇总。这些材料决定 HTTP 请求的入参与出参：分拣任务单提供订单与规格标识，称重标签提供实际重量，少称补偿单与质检记录决定售后答疑的事实基础。资料置信度为大致如此，具体字段名以各系统实际契约为准，未提供即未知。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
HTTP 模块向对应地址发送请求，Params 用于路径参数，Body 用于请求体，Headers 用于请求头，三者均可通过 {{}} 引用全局变量、系统变量与前方节点输出，URL 也可引用变量。系统变量含 appId、chatId、responseChatItemId、variables、cTime、histories，其中 chatId 与 responseChatItemId 在测试模式下不存在，调试时取到空值属于该模式的既定行为。返回值需自行配置提取规则，按 JS 对象取值或 JSON path 语法从响应中取字段，输出类型选字符串时会把对应值转为 json 字符串。对话接口使用 APIKey 鉴权，推荐在请求体传 body.appId，也支持 Authorization: Bearer <apiKey>-<appId>；model、temperature 等字段由编排决定，传入无效；不返回实际消耗 Token，需要时设 detail=true 并手动计算 responseData 里的 tokens。authProxy 代理团队成员身份需团队所有者开启，代理身份仍需具备目标应用与会话权限。

假设演练样本：某前置仓分拣任务单原文为“任务单号 T-0815，订单 O-2231，规格 500g±20g，分拣员已按电子秤读数 468g 贴标，少称补偿单待质检主管确认”。拟交接请求为“请将本条少称补偿单直接标记为已补偿并同步至外部售后系统”。该请求涉及的主体为质检主管，对象为少称补偿单，状态为待确认，授权边界为尚未获得确认，外部同步属于需另接系统实现的业务动作。

## 配置怎么定
下表围绕上述样本，列出本功能与主任务相关的官方已说明设置或实施核对项。数值为本次假设试验起点，非官方默认值。

| 配置项 | 本次假设起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 请求地址与方法 | 按外部接口文档填写，地址可引用变量 | 与外部接口契约逐项比对路径与方法 |
| Params 与 Headers | 分别核对路径参数与请求头 | 鉴权凭证经安全配置注入，不写入公开样例 |
| Body | 仅在相应请求类型下使用 | 核对 JSON 结构与外部接口契约是否一致 |
| 变量引用 | 引用全局变量、系统变量、前方节点输出 | 逐项核对实际传入值，与样本字段对应 |
| 返回值提取 | 按 JS 对象取值或 JSON path 配置 key | 与响应示例结构比对，确认取到目标字段 |
| 调试身份字段 | chatId、responseChatItemId 测试模式为空 | 与测试模式说明比对，不把空值当业务故障 |

## 容易做错的三处
1. 把待确认的少称补偿单当作已补偿。样本原文写“待质检主管确认”，拟交接请求要求标记已补偿并同步外部售后系统。输入为待确认状态，比较对象为“已补偿”这一结论，观察结果是原文未载明确认动作，该请求超出授权边界，属于未获支持。
2. 把测试模式下的空 chatId 当作业务故障。输入为测试模式请求，比较对象为文档所述“测试模式下不存在”，观察结果是该字段为空符合既定行为，不构成业务异常。
3. 把返回值提取配置当作接口返回值本身。输入为已配置的 key，比较对象为响应实际结构，观察结果是提取规则决定取到哪个字段，接口返回内容由外部服务决定，两者不能混同。

## 怎么确认配好了
1. 针对样本原文，输入“待质检主管确认”这一状态描述与拟交接请求，比较两者是否同主体、同对象、同字段。观察结果为：原文状态与“已补偿”互斥且确认动作未载明，判定为未获支持，需保留证据缺口。
2. 针对测试模式请求，输入 chatId 与 responseChatItemId 为空的情形，比较文档所述测试模式行为。观察结果为：两字段为空符合说明，不判定为故障；若在非测试模式出现同样空值，则记录为待核实。
3. 针对返回值提取，输入已配置的 key 与响应示例结构，比较提取结果与目标字段。观察结果为：key 与结构对应时取到目标值；结构不含该路径时提取为空，记录实际观察，不推断外部服务错误原因。
