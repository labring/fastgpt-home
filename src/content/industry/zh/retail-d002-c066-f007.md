# 短视频挂车分销运营的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样

短视频挂车分销的成交来自内容长期曝光后的商品链接点击，订单履约与售后答疑往往发生在视频发布数日之后，客服与运营需要回看当时挂车商品、佣金计划与违规反馈的对应关系。该品类的数据来源包括精选联盟、短视频播放数据、商品成交数据与平台规则，日常文档为短视频脚本、挂车商品清单、佣金计划与违规反馈。这些材料分散在不同系统，对话日志与审计环节要把一次答疑或一次履约沟通还原到具体会话、具体对话与具体订单上下文。

## 这些特征在「对话日志与审计」这一环带来什么约束

对话身份依靠 chatId 区分。chatId 为 `非空字符串` 时，FastGPT 从数据库取该会话，并以 messages 数组最后一个内容作为用户问题，其余 message 被忽略；chatId 不传入时，不使用平台上下文，完全由传入 messages 构建。因此核对履约沟通时，须先确认 chatId 对应的是目标会话，不能把不同入口的会话混算。

需要运行详情时，调用对话接口设置 `detail=true`。`stream=false` 时中间值保存在 `responseData`，`stream=true` 时通过 `event` 区分，其中 `flowResponses` 承载节点完整响应。日志与接口实际返回哪些字段，就以哪些字段为准；未返回的业务数据不能推定已完整留存。

假设演练样本（纸面材料，未实际执行）：短视频脚本原文为「本品为厨房收纳架，挂车链接对应精选联盟商品 A，佣金比例按 3 月计划执行」。挂车商品清单原文为「商品 A，上架日期 3 月 1 日，状态在售」。违规反馈原文为「该视频标题含极限词，待修改，未下架」。待判定的交接请求为「请按上述材料确认商品 A 的订单履约状态并回复用户已处理」。

## 配置怎么定

| 核对项 | 本页相关设置或动作 | 与样本的对应 |
| --- | --- | --- |
| 对话身份 | 传入非空 chatId，取该会话并以最后一条 message 为问题 | 确认答疑会话是否即目标会话 |
| 运行详情 | 设 `detail=true`，非流式看 `responseData`，流式看 `event` | 查看是否存在履约相关节点响应 |
| 会话列表 | `source=api` 只取 API 创建的会话 | 区分接口会话与页面会话 |
| 对话列表 | 按 appId、chatId 取分页记录，可设 `loadCustomFeedbacks` | 回看该会话下历史对话 |
| 单条详情 | 按 dataId 取该对话运行详情 | 定位某次答疑的运行记录 |
| 反馈字段 | 用 `userGoodFeedback`、`userBadFeedback` 记录反馈 | 标记售后答疑质量 |

本样本未涉及数值型起点，不设假设初始值。授权方面，`authProxy` 代理团队成员身份须由团队所有者开启，代理身份仍需具备目标应用和会话权限；检索与日志读取本身不构成业务授权。

## 容易做错的三处

1. 把 chatId 省略时的无上下文调用，当成已读取该会话历史。检查：输入为不传 chatId 的请求，比较返回内容是否含历史对话，若仅由当次 messages 构成，则未使用平台上下文。
2. 把 `detail=false` 的返回当作含中间值。检查：输入 `detail=false` 的请求，比较是否出现 `responseData`，若未出现，则节点级信息未返回。
3. 把待修改的违规反馈当成已下架。检查：输入样本违规反馈原文，比较状态字段是否为「已下架」，原文写「待修改，未下架」，因此下架未获支持。

## 怎么确认配好了

1. 取样本脚本原文与挂车清单原文，输入为 chatId 与 `detail=true` 的请求，比较 `responseData` 中是否出现与该会话对应的节点记录。出现对应记录且 chatId 一致，才算身份与详情两项对齐。
2. 取样本待判定交接请求，输入为按 dataId 取运行详情的请求，比较返回的 query 或 historyPreview 是否包含该请求内容。包含则说明该对话可定位；不包含则记录为缺口。
3. 取样本违规反馈原文，输入为对话列表分页请求，比较该会话记录中是否出现对应反馈字段。出现且取值与原文一致，才算反馈留存可核对；未出现时保持未知，不推定已留存或已处理。
