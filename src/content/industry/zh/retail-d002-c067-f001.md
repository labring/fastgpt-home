# 社区团购团长运营的订单履约与售后答疑：HTTP 接口与外部系统

## 这个品类的数据长什么样

在社区团购团长运营的订单履约与售后答疑中，本页说明FastGPT的HTTP 接口与外部系统如何衔接资料。社区提货售后查询应核成员需求与提货点对应，清单或公告可读不证明商品已到或客户已领。所用场景为自拟文字测试。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

自拟咨询问本次能否提货，拟查询输入只给社区名称，提货点未说明，公告又只写等待通知。接 HTTP 前先确认外部实际能按什么对象读取，再核请求条件如何由原句取得。社区同名不能补具体点位，返回名单也不证明货已到；如果结果只是通知草稿，不可将起草阶段改成消息已送达客户。

## 配置怎么定

| 社区提货读取 | 自拟查询状态 | 所需核对 |
| --- | --- | --- |
| 需求来源 | 只给社区名 | 补具体提货点 |
| 公告原句 | 等待通知 | 非已经送达 |
| 名单返回 | 只说明列名 | 不证货已到 |
| 请求范围 | 按实际服务能力 | 核真实发送 |
| 空结果 | 先查权限范围 | 不否认客户需求 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `请求地址与方法` | 请求地址与方法遵循外部契约。 |
| `Params与Headers` | 参数、请求头及鉴权分别核对。 |
| Body | 采用JSON请求体时按外部契约核结构。 |
| `变量引用` | 可引用全局、系统或前序输出变量。 |
| `调试身份字段` | 测试时无chatId及responseChatItemId。 |

## 容易做错的三处

点位强配：若社区名称代替实际提货点，应核需求原句与发送条件；名单冒到货：若可见名单变为商品已备，应取本次实际供应或接收；草稿冒送达：若通知文本被写成客户已知，应查真正发送及接收依据。三项分别核对象、货物阶段和信息阶段，不由正常响应决定。

## 怎么确认配好了

验收保留实际请求与返回原文，补提货点对应后重查，看响应是否覆盖同次需求。读取为空时先查范围和权限，不能说该客户没有需求。正式采购、提货登记与通知发送需要另接流程核权限及回执；HTTP变量按实际来源引用，不从测试中的缺省信息推定真实业务不存在，查询结果也不替团长作交付承诺。
