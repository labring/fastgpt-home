# 连锁总部选址开店的订单履约与售后答疑：HTTP 接口与外部系统

## 这个品类的数据长什么样

选址开店发生在门店营业前，核心是租赁和工程交付，日常材料包括选址评估表、租赁意向书、装修预算和开业排期。这些材料按店产生，更新不定期。拓展人员测算租金销售比、谈判租赁条款、协调装修节点，任一环节的日期或金额引用错误都会带来押金损失或延期交付。HTTP 接口把外部系统的地址、请求参数、请求头和请求体作为配置项，地址和请求体字段均可引用全局变量、系统变量或前方节点输出，因此同一份选址材料在流转中会被拆成多个变量值传递。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向配置的地址发送请求，Params 多用于 GET，Body 多用于 POST/PUT，Headers 传递特殊信息。变量来自全局变量、系统变量和前方节点输出，`{{}}` 引用在三种数据中均可用，URL 也可引用变量。返回值通过 JSON path 提取，输出类型选字符串时会把对应值转成 json 字符串。测试模式下 chatId 与 responseChatItemId 不存在，调试空值不构成业务故障。对话接口的鉴权使用 APIKey，推荐在请求体传入 body.appId，也支持 Authorization: Bearer 形式；传入的 model、temperature 等字段无效，由编排决定。

假设演练样本：某连锁总部拓展部处理一份租赁意向书，材料原文为「意向书编号 YX-2024-031，承租方为某连锁品牌区域开发组，标的为某商圈一层铺位，意向租期自 2024 年 6 月 1 日起，意向书状态为待房东确认，签署栏为空」。另有一条待判定交接请求草稿：「该意向书已生效，请据意向租期排定装修进场日并生成开业排期」。判断所需的主体是承租方区域开发组，对象是上述铺位，状态是待房东确认且签署栏为空，有效范围是意向租期起点。

## 配置怎么定

| 配置项 | 取值或核对内容 | 依据与说明 |
| --- | --- | --- |
| 请求地址与方法 | 按外部接口文档填写地址与方法，地址可引用变量 | 文档说明 URL 可通过 `{{}}` 引用变量 |
| Params 与 Headers | 分别核对请求参数与请求头，鉴权凭证经安全配置注入 | 文档说明两者用法与 Postman 基本一致 |
| Body | 仅在相应请求类型下使用，核对 JSON 结构与外部契约 | 文档说明 Body 只在特定请求类型下生效 |
| 变量引用 | 逐项核对全局变量、系统变量、前方节点输出的实际值 | 文档说明变量来自这三类来源 |
| 返回值提取 | 按 JSON path 语法配置 key，输出类型按需选择 | 文档说明提取规则遵守 JS 对象取值规则 |
| 调试身份字段 | 测试模式下 chatId 与 responseChatItemId 不存在 | 文档说明二者在测试模式下不存在 |

## 容易做错的三处

1. 把意向书状态「待房东确认」当作已生效，进而据意向租期安排装修进场。输入是上述意向书原文与交接请求草稿；比较对象是材料状态字段与草稿所依赖的生效前提；观察结果是二者不一致，草稿的生效前提未获材料支持。
2. 在 GET 请求中填写 Body，或在 Body 中引用字符串时漏掉外层引号。输入是配置的请求方法与 Body 声明；比较对象是文档所述 Body 仅在特定请求类型下生效、字符串引用需加 `""`；观察结果是声明与实际请求类型或引用写法不符。
3. 把测试模式下缺失的 chatId 或 responseChatItemId 记为接口故障。输入是测试模式下的请求与响应；比较对象是文档所述二者在测试模式下不存在；观察结果是该缺失属于文档已说明情形。

## 怎么确认配好了

1. 取上述意向书原文与交接请求草稿，核对材料状态字段与草稿所依赖的生效前提是否一致。预期现象是识别出状态为待房东确认、签署栏为空，草稿的生效前提未获材料支持，记录为待核实。
2. 取配置的请求方法与 Body 声明，逐项对照文档所述 Body 生效条件与字符串引用需加 `""` 的写法。预期现象是发现不一致项并列出，未发现时记录实际观察。
3. 取测试模式下的请求与响应，核对 chatId 与 responseChatItemId 是否按文档所述不存在。预期现象是该缺失被归入文档已说明情形，不记为业务故障。

本页只解决连锁总部选址开店的订单履约与售后答疑中 HTTP 接口与外部系统这一环。检索与表单收集不构成授权，业务验证、审批、数据库写入与外部同步需另接实现。材料未载明的字段保持未知。
