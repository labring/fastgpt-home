# 连锁总部选址开店的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样

选址开店发生在门店营业之前，核心工作围绕租赁与工程交付展开。日常材料包括选址评估表、租赁意向书、装修预算和开业排期，数据来源涉及商圈客流、地图 POI、POS 历史店型与房东资料。这些材料按店、不定期更新，出错后果是开店亏损、延期交付或押金损失。对话日志与审计这一环要处理的是：总部拓展人员、区域开发和工程经理在订单履约与售后答疑场景中产生的会话记录，以及这些记录能否被定位、核对和留存。材料分散在多个入口，会话身份若不与业务记录对齐，后续对账就缺少可靠锚点。

## 这些特征在「对话日志与审计」这一环带来什么约束

会话身份以 chatId 为锚点。chatId 为非空字符串时，FastGPT 从数据库取会话，messages 数组最后一个内容作为用户问题，其余 message 被忽略；chatId 不传入时，不使用上下文功能，完全由 messages 构建上下文。responseChatItemId 传入后作为本次响应消息 ID 存入数据库，需在当前 chatId 下唯一。对话接口的 model、temperature 等参数无效，由编排决定。detail 控制是否返回中间值：非 stream 模式结果在 responseData 中，stream 模式通过 event 区分。会话管理接口可获取、修改标题与置顶、删除单个或清空 API Key 创建的会话；对话管理接口按 dataId 获取运行详情、删除对话、更新点赞或点踩反馈。这些是记录定位与读取能力，业务对账、留存与合规审计需由完整业务方案另行落实。

假设演练样本：一份选址评估表原文写有“对象：某商圈临街铺位；阶段：意向沟通；有效期至 2025 年 3 月 31 日；授权范围：区域开发可发起租赁意向书草拟”。同批材料中一份租赁意向书原文写有“状态：待房东签署；押金条款：以最终合同为准”。一条拟交接请求写为“该铺位租赁已确认，可安排装修排期”。待判定点：拟交接请求中的“租赁已确认”是否有材料支持。

## 配置怎么定

| 配置项 | 取值或核对方式 | 与样本的关系 |
| --- | --- | --- |
| chatId | 非空字符串，长度小于 250，同一会话保持一致 | 定位该铺位相关会话 |
| responseChatItemId | 当前 chatId 下唯一 | 标记本次响应消息 |
| detail | true 时非 stream 结果在 responseData | 核对运行详情字段 |
| source | 会话列表取 api 源 | 区分 API 创建会话 |
| dataId | 按会话下对话 ID 获取运行详情 | 定位单条对话 |
| loadCustomFeedbacks | 可选，读取自定义反馈 | 核对反馈字段 |

## 容易做错的三处

1. 把 chatId 不传入时的无上下文行为，当成同一会话的延续。输入为不传 chatId 的请求，比较其 messages 构建方式与传入 chatId 时的取会话行为，观察是否混用两种上下文来源。
2. 把交互节点返回的展示配置当成授权结果。样本中租赁意向书状态为待房东签署，拟交接请求写“租赁已确认”，比较两者状态字段，观察是否存在把待签署读成已确认。
3. 把 detail=true 的 responseData 字段当成业务数据完整留存。输入为一次 detail=true 请求，比较返回字段与业务对账所需字段，观察未返回字段是否被推定已留存。

## 怎么确认配好了

1. 输入样本中的选址评估表原文与拟交接请求，比较“意向沟通”“有效期至 2025 年 3 月 31 日”与“租赁已确认”，若拟交接请求超出有效期或把意向沟通写成已确认，则判定为未获支持。
2. 输入样本中的租赁意向书原文，比较“待房东签署”与“租赁已确认”，若两者状态不一致，则记录证据缺口，不判定为已生效。
3. 输入一份纸面空结果 [] 与下游设计，比较下游是否按空结果处理，观察是否出现无依据的业务动作；检索检查只记录实际观察，不保证首条命中或全部召回。
