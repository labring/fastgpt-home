# 连锁统采统配的订单履约与售后答疑：对话日志与审计

## 这个品类的数据长什么样

连锁统采统配的对话日志围绕总部采购与配送展开，数据来源包括 ERP 采购、WMS、门店 POS 与供应商交货数据。一次订单履约问答可能同时涉及集采合同、补货计划、配送单与门店要货单，核对时需要把对话身份与具体业务单据对应起来。更新频率以日、周为主，本页不涉及批量同步机制。

## 这些特征在「对话日志与审计」这一环带来什么约束

对话接口按 chatId 区分会话，按 dataId 区分会话下的对话。需要运行详情时设置 detail=true，中间结果保存在 responseData 中；detail=false 时只有最终回答。日志字段以接口实际返回为准，未返回的业务数据不能推定已完整留存。检索与相似度只影响召回排序，不承担权限或实体隔离。

假设演练样本：某连锁供应链中心配送专员在 2025 年 3 月 10 日通过 API 提交一条会话，chatId 为 "peisong-20250310-01"，messages 内容为「3 月 12 日 A 仓到 B 门店的配送单是否已确认？」。供核对的材料原文为：集采合同 HT-2025-031 载明「本批次配送以配送单确认状态为准」；补货计划 BH-2025-0309 载明「B 门店 3 月 12 日到货，待配送单确认」。拟稿句为「配送单已确认，门店可按时收货」。材料只说明待确认状态，拟稿句把待确认写成已确认，属于超出原文的判断。

## 配置怎么定

| 配置项 | 本页用途 | 核对方式 |
| --- | --- | --- |
| appId | 定位目标应用 | 与请求体 body.appId 一致 |
| chatId | 定位目标会话 | 与配送单业务编号对应 |
| dataId | 定位会话下对话 | 从获取对话列表结果读取 |
| detail | 取得运行详情 | 设为 true 后检查 responseData |
| loadCustomFeedbacks | 读取自定义反馈 | 在获取对话列表时按需传入 |
| source | 过滤会话来源 | 取 api 时只取 API 创建会话 |

## 容易做错的三处

1. 把假设样本中「待配送单确认」的补货计划当作配送单已确认。检查时比较材料原文与拟稿句的状态描述，原文为待确认，拟稿句写已确认，两者不一致。
2. 用相似度分数排除其他门店或供应商的对话。检查时比较返回记录中的 chatId 与目标业务编号，分数高低不构成权限过滤。
3. 把交互节点返回的表单配置当作业务授权已完成。检查时比较交互返回的 type 与 params 同实际提交内容，表单只收集值，审批与写入需下游实现。

## 怎么确认配好了

1. 输入假设样本的 chatId 与 messages，并设置 detail=true，比较返回的 responseData 中 moduleName 与 moduleType 是否对应本次请求节点，出现对应节点且状态可读为满足。
2. 输入拟稿句与材料原文，比较状态字段取值，原文为待确认、拟稿句为已确认时判定不一致，需修改拟稿句。
3. 输入 detail=true 与 detail=false 两次请求，比较返回结构中 responseData 是否存在，detail=true 时存在、detail=false 时不存在为符合预期。以上均为纸面核对，未实际执行。
