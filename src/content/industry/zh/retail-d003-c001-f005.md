# B2B平台撮合交易的商品与营销文案起草：多轮对话与提示词

## 这个品类的数据长什么样

在B2B平台撮合交易的商品与营销文案起草中，本页说明FastGPT的多轮对话与提示词如何衔接资料。区分采购方提出的定制需求、供应方已有说明与文案仍缺的产品依据。所用场景为自拟文字测试。

## 这些特征在「多轮对话与提示词」这一环带来什么约束

B2B文案可另拟一份询报价文字，记录采购方希望按规格定制，但没有提供成品的技术说明。提示词应先区分提出需求与已经具备能力，不能把采购期望写成供应商现成功能。比较本轮原文与实际历史，检查草稿中的“可实现”之类说法来自哪里。若只有需求、没有对应产品依据，就无法核实能力描述，应保留待补状态，而不因多次追问把设想升级为事实。

## 配置怎么定

| 对话或实施核对项 | B2B文案中的条件 | 验收对象 |
| --- | --- | --- |
| 需求与事实 | 采购定制期望并非现成功能依据 | 能力描述是否有产品来源 |
| 主体承接 | 当前供应商与历史主体分开 | 原问、历史和优化问全文 |
| 未知标识 | 材料未提供时保持未确定 | 不由指代优化补写既有主体 |
| 阅读清单 | 原文、需求和缺项分别核对 | 不当作软件新增字段 |
| 结构化承接 | 按下游需要选格式 | 解析与字段来源分别验证 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `提示词与任务` | 说明资料、任务和缺证据处理。 |
| `历史记录` | 核实际提交的历史输入。 |
| `问题优化` | 指代消除与问题扩展需复核。 |
| `模型与长度` | 上下文与回复长度分别核对。 |
| `回复格式` | json_schema需给格式并验解析。 |

## 容易做错的三处

- 采购方希望定制被写成供应商现成功能：并列询报价需求与草稿能力句，查产品依据；期望不提供技术或交付证明。

- “这家”“同款”补成历史另一供应商：保存原问、实际历史和优化全文，核未知标识从哪来，主体错后不能沿用旧文案。

- 新增规格已提供却未进入本轮，结构化稿仍沿用旧值：核实际输入和每项值的原文，解析成功不说明来源更新，需补传再复测。

## 怎么确认配好了

可把原文明确内容、采购需求和待补资料分别列为阅读清单，用于检查草稿有无跨越支持范围；这些是提出的核对栏目，不是软件新增字段。若需要结构化承接，按实际下游要求选择格式，使用json_schema时核配置与解析，再查每项值的来源。缺少产品条件不能由返回结构齐全弥补，新资料补入后还需记录实际进入本轮的内容。
