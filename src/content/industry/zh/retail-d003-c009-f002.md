# 亚马逊FBM自发货运营的商品与营销文案起草：上下文与 token

## 这个品类的数据长什么样

在亚马逊FBM自发货运营的商品与营销文案起草中，本页说明FastGPT的上下文与 token如何衔接资料。预订提醒和排期草稿不能变成当前现货承诺。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

FBM营销文案自拟运营备注“可登记预订意向；现货状态待确认”，排期页眉写草稿。用户要求写购买提醒时，输入需要保留意向、待确认与草稿三个状态。登记意向不等于接受订单或锁定库存，排期草稿也不证明发出时间已定。文案可以说明可咨询登记，但具体供应条件缺少确认，不应为让购买动作明确而写成现货可立即安排。

## 配置怎么定

| 上下文核对对象 | 具体文字条件 | 验收线索 |
| --- | --- | --- |
| 登记对象 | 预订意向 | 核意向未裁掉。 |
| 库存状态 | 现货待确认 | 不改为即时供应。 |
| 排期身份 | 草稿 | 核页眉与正文一起进入。 |
| 历史期间 | 旧现货消息 | 核时点是否适用。 |
| 购买提醒 | 状态、期间与确认动作 | 验证完整解析。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

常见错误是摘要留下可登记，却把意向省掉，输出变成可直接下单；另一种失败是历史某次现货消息被当前提醒继承。排查应核登记对象、当前库存依据和排期身份，分别定位文字裁剪与期间混用。回复长度需容纳待确认状态，模型上下文容量按实际能力核验；上下文中有旧消息并不代表它当前仍有效。引用上限应检查状态词是否留全，不能仅看商品名返回。第三处是把草稿排期写成已经确认的发出安排。应核排期版本与实际确认依据，并检查提醒中的状态动词；登记意向、现货确认与发出安排不能互相代替。

## 怎么确认配好了

验收分别起草登记说明、供应状态和排期提示，核输出是否仍是意向登记、现货待确认与草稿安排，不补数量或时间保证。相同任务在空历史与旧现货历史下比较，记录承诺从哪段输入增加。固定格式用于页面或客服承接时，应核状态、适用期间与待确认动作完整解析。取得新库存材料后还要核其对象与时点，不能把计划更新写成已经发货。
