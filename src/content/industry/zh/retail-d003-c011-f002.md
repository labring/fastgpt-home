# 仅退款争议处理的商品与营销文案起草：上下文与 token

## 这个品类的数据长什么样

在仅退款争议处理的商品与营销文案起草中，本页说明FastGPT的上下文与 token如何衔接资料。核当前争议的待核条件与历史订单，避免进度稿串用处理结果。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

仅退款争议相关说明稿，可采用自拟客服备注：“已收到买家描述，处理结论待核；本文不代表退款已经完成。”本题只让起草一段进度说明。上下文检查要确认对象是当前争议、输入含待核条件，历史中是否另有已经结案的不同订单。这里不写真实客户经历，也不提供平台处理规则。拟稿需要区分收到描述与完成退款，不能把旧轮中的完成说法借给当前记录；问题改为写一段简短公告后，这个事实边界仍应保留。

## 配置怎么定

| 上下文核对项 | 本题材料 | 取证动作 |
| --- | --- | --- |
| 当前对象 | 争议仍待核的备注 | 不借旧订单已结案状态。 |
| 完整输入 | 收到描述与待核条件 | 原备注对照实际请求。 |
| 历史比较 | 本轮相同，历史有无不同 | 追查指代和新增完成说法。 |
| 两类长度 | 引用token与回复上限分开 | 查缺句，不仅加长输出。 |
| 结构验收 | 先解析后核状态依据 | 可解析不等于业务已执行。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

- 待核句没进入请求，收到描述被写成接受退款时，保留原备注、实际请求与稿件，定位条件丢失。

- 历史旧订单已结案被借给当前争议时，固定本轮备注比较有无历史输入，核“这笔”所指订单。

- 输入仍含待核条件，结构化结果却填已完成时，先验解析，再核状态原文；可解析不说明退款已执行。

## 怎么确认配好了

验收时逐句标出进度稿中的对象、已发生动作和仍待核事项，再回到实际收到的文字检查支持。若稿件被要求输出为结构化结果，先验结构能否解析，再查其中处理状态的来源；格式正确不代表退款已执行。补入真正处理结论后重用原题，记录是资料变动还是历史设置改变导致表述变化。记录缺失时可以形成待补材料清单，不能让文案补写一个业务结果。对外发送与争议处理仍需实际后续动作，本次测试没有发布公告或改变订单。
