# 便利店鲜食订货的商品与营销文案起草：上下文与 token

## 这个品类的数据长什么样

在便利店鲜食订货的商品与营销文案起草中，本页说明FastGPT的上下文与 token如何衔接资料。把本轮上新计划、供应状态与历史现货稿的日期基准分开。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

便利店鲜食上新稿可另拟素材：“明日拟增加南瓜面包，实际供货待确认；展示图仅为试制样品。”“明日”以该计划材料日期为基准；历史宣传稿的现货另按其所列期间核。当前任务应明确是拟上新、哪一日的计划及样品身份，不能让历史现货状态覆盖新计划。原材料没有正式配料说明、供应确认或检测结果，因此只能围绕已给的产品描述起草，不能由样品照片补出成分或食用效果。图片是否真正被读取也需按实际输入核，普通图示说明不是完整图像内容。

## 配置怎么定

| 上下文核对项 | 本题材料 | 取证动作 |
| --- | --- | --- |
| 计划日期 | 明日拟上新 | 旧周现货不能替本轮状态。 |
| 样品身份 | 展示图来自试制样品 | 不推定交付规格及成分。 |
| 条件缺失 | 供货仍待确认 | 完整素材比对实际请求。 |
| 历史对象 | 追问这个是否仍在卖 | 核日期及商品指代。 |
| 材料补充 | 供货与配料说明各有作用 | 记录各自改变的句子。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

- 供货待确认被裁掉、稿件承诺到店时，对照完整素材、实际请求及相关句，先找条件缺失。

- 追问“这个还在卖吗”串用历史现货时，核当前计划日、旧资料适用期间及商品指代，不把取得资料的日期当供货日期。

- 仅有试制图说明却写出具体成分时，查实际输入是否有配料资料或读到相应图像；商品名与展示说明不能补出成分。

## 怎么确认配好了

验收逐句核明日计划、试制样品及供应待确认，若返回结构化结果，先测能否解析，再查供应状态是否有原文依据。新供货通知或配料说明取得后，分别补入并用原题复测，不把两项资料视为互相替代。记录哪个来源改变了哪句话，避免只比较文案是否更像广告。缺乏实测时保留相关证据缺口；本测试不确认商品适售、不提交门店订货，也没有发布任何鲜食宣传。
