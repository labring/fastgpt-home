# 信用证审单交单的商品与营销文案起草：上下文与 token

## 这个品类的数据长什么样

在信用证审单交单的商品与营销文案起草中，本页说明FastGPT的上下文与 token如何衔接资料。核本票发票改写及尚缺的银行意见，不借另一票结果补结论。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

信用证审单工作的介绍文案，可先拟工作记录：“商业发票商品描述已改写，银行具体意见尚未取得。”另一段草稿只介绍单据整理步骤。本轮任务说明已进行的文字整理，不评判实际单据是否获接受。上下文需同时保留改写对象和银行意见缺口；发票描述变了，不说明实物规格变了，也不说明交单结果已确定。历史若包含另一票业务的接受记录，应让当前主体与那票材料分开，不能将其作为本次文案的结果。

## 配置怎么定

| 上下文核对项 | 本题材料 | 取证动作 |
| --- | --- | --- |
| 改写对象 | 仅商业发票描述已改 | 不等于实物或审单结果变化。 |
| 反馈缺口 | 具体银行意见尚未取得 | 条件随素材进入请求。 |
| 历史分票 | 另一票接受记录单独留存 | 不借给当前业务作结果。 |
| 长度范围 | 窗口、引用与回复分开核 | 分别核模型能力及配置、本次实际传入；单次成功不证明完整窗口。 |
| 新增意见 | 本票对应材料补入 | 原题核主体与状态引用。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

- 输入丢掉尚缺银行意见，稿件把整理完成写成审单通过时，对照原记录、请求和答复，追查新增结论。

- 追问“这一票完成了吗”串用历史另一票接受记录时，固定本票身份比较实际上下文，核主体与处理阶段。

- 发票描述改写被写成实物规格已经一致时，核新旧文字及实物依据；文字改了不说明货物变了，也不提供一致性结果。

## 怎么确认配好了

验收按发票文字改写、单据整理和银行意见三类说法逐句对照来源，结构化摘要先核解析再核各状态。取得对应意见后，新增来源并重复原问题，确认输出引用的确属本票材料，另核历史有没有串入。若修改的商品描述与原规格无法对应，应把两份文字留给业务核查，不能由生成文案宣称单证和货物已一致。本测试只处理资料范围及输入检查，没有执行审单、交单或银行处理，也不提供银行接受的预测。
