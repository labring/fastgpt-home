# 信用证审单交单的商品与营销文案起草：多轮对话与提示词

## 这个品类的数据长什么样

信用证审单交单服务于银行付款条件，核对重点是单证一致，材料来自开证行通知、UCP600条款、货代提单和银行交单记录。商品与营销文案起草环节要写的内容，需要与信用证、商业发票、提单、保险单、汇票上的既有表述保持同一口径，文案里的品名、数量、金额、装运信息一旦偏离单据，后续审单就可能出现不符点。这个品类的数据每单更新，文案起草因此按单进行，不沿用上一单的措辞。

## 这些特征在「多轮对话与提示词」这一环带来什么约束

多轮对话要区分新会话与继续会话。传入非空 chatId 时，系统自动从数据库取会话，messages 数组最后一个内容作为用户问题，其余 message 被忽略；不传 chatId 时完全由 messages 构建上下文。提示词需要写明资料范围、回答任务和缺证据时的处理方式，不让模型补写业务事实。回复格式按后续承接选择，选择 json_schema 时需填写对应格式要求。记忆轮数控制参考前面多少轮聊天，数值越大带入内容越多，可能增加消耗并影响响应速度。

假设演练样本：某信用证项下商业发票原文三句为「品名：不锈钢保温杯」「数量：2000 只」「装运港：宁波」。一条待判定拟稿句为「本产品已通过国际权威认证，适合全球高端市场」。核对时，原文含主体（该批货物）、对象（品名、数量、装运港）、状态（已列明），拟稿句中的认证与高端市场表述在原文中没有对应字段。该句属于未获支持，需要补充材料或改写为与发票一致的描述，不能直接采用。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 记忆轮数 | 保留少量历史轮数 | 按单起草，前文参考需求有限；与默认值比较后决定是否调整 |
| 温度 | 偏低 | 文案需与单据口径一致，稳定优先；与偏高值比较输出波动 |
| 回复上限 | 按文案长度需要设定 | 文案较短时调低，较长说明时调高；与截断现象比较 |
| 回复格式 | 默认 | 普通文案起草无需固定结构；后续流程需要读取时才改 |
| 模型 | 选择支持所需上下文长度的模型 | 核对最大上下文与单据文本长度；与长文档场景比较 |
| 思考配置 | 默认 | 不涉及复杂推理；与更高思考强度比较是否必要 |

以上数值为本次假设试验起点，不是官方默认值。配置弹窗根据模型能力显示可用项，模型不支持多模态时不显示对应选项。

## 容易做错的三处

1. 把拟稿句中的认证表述当作已有事实。输入是发票原文三句与拟稿句，比较的是原文是否含认证字段，可观察结果是原文无该字段，判定为未获支持。
2. 继续会话时误以为全部 message 都参与上下文。输入是带 chatId 的多条 message，比较系统实际取用的最后一条，可观察结果是其余 message 被忽略。
3. 选择 json_schema 后未填写格式要求。输入是格式配置与返回内容，比较返回结构是否符合要求，可观察结果是结构不符时需补齐格式要求。

## 怎么确认配好了

1. 用样本发票原文与拟稿句核对。输入为上述三句原文和拟稿句，比较认证字段是否存在，出现原文无对应字段即满足未获支持的判定条件。
2. 用继续会话请求核对上下文取用。输入为带 chatId 的多条 message，比较实际作为问题的最后一条内容，出现其余 message 未被采用即符合文档说明。
3. 用 json_schema 配置核对返回结构。输入为已填写格式要求的配置，比较返回内容结构，出现结构与格式要求一致即满足条件。以上均为纸面核对，未实际执行。空结果承接可用明确的纸面输入 [] 核对下游设计，不声称虚构规则检索一定返回空。检索与相关度不承担权限或实体隔离，跨不同向量模型的库不可共同关联，需先核标识并排除不符合者。
