# 即时零售门店履约的商品与营销文案起草：上下文与 token

## 这个品类的数据长什么样

在即时零售门店履约的商品与营销文案起草中，本页说明FastGPT的上下文与 token如何衔接资料。核演示拣货说明、历史闭单与当前库存依据，保留门店宣传素材的时间和对象。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

即时零售门店介绍稿可拟素材：“本段演示拣货步骤；送达记录未提供，当前可售品项另核。”历史稿写的是另一单已经闭单的过程。当前任务介绍演示，不播报实时库存，也不报告新订单结果。先将演示身份、订单对象和资料所列期间一起核入实际请求，再看历史带入了哪些事件。文案可以描述给出的步骤，不能把演示完成扩为订单送达，也不能由一次拣货说明拼出门店当前可售目录。

## 配置怎么定

| 上下文核对项 | 本题材料 | 验收动作 |
| --- | --- | --- |
| 素材身份 | 演示拣货步骤 | 不改作真实履约结果。 |
| 订单指代 | 历史另一单已闭单 | 核本轮这单所指。 |
| 库存范围 | 可售品项另核 | 逐项追状态依据。 |
| 事件时点 | 素材期间与取得时间分开 | 不借检索日期判进度。 |
| 结构结果 | 演示与事实分列 | 解析后检查各自来源。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

- 演示身份从请求丢失，稿件把步骤展示写成真实履约完成时，核原说明、实际输入与完成措辞。

- 追问“这单完成了吗”串用另一单闭单记录时，固定当前素材比较有无历史，检查订单身份及事件时点。

- 没有当前库存来源却列出可售品项时，逐项查名称和状态依据；演示商品出现不证明它此刻可售。

## 怎么确认配好了

验收分别核演示做了什么、哪一单有结果以及当前库存依据是否提供，逐句回查实际输入。补送达记录或库存材料时分别核对象和期间，不把取得材料较晚当作事件发生较晚。引用上限与回复长度分开检查；实际模型能力和上下文配置有其依据，单次成功调用不测出完整窗口。若输出结构化门店介绍，先验解析，再查演示与业务事实是否仍分开。本测试不提交订单或发布宣传，记录缺口保持可见。
