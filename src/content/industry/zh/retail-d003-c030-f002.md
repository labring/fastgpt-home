# 商超供应商进场结算的商品与营销文案起草：上下文与 token

## 这个品类的数据长什么样

在商超供应商进场结算的商品与营销文案起草中，本页说明FastGPT的上下文与 token如何衔接资料。供应商服务介绍应区分交单协助、双方核账与已结算结果。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

商超供应商服务稿可拟业务便笺“协助整理交货原件目录”，说明页“正式对账由双方另行核对”，旧会话记录过另一账户的结算通知。当前要写服务简介，整理目录不是确认账目无差异，正式核对也未形成已结算结果。起草请求应保留三个行为的对象和阶段，只保留协助交单会让服务范围模糊。旧结算样本能作为文风参考，但不能替当前账户补凭据或承诺。

## 配置怎么定

| 材料核对项 | 本题具体条件 | 实施取证 |
| --- | --- | --- |
| 协助对象 | 原件目录 | 不扩对账完成。 |
| 核对主体 | 双方 | 查独立记录。 |
| 阶段条件 | 另行核对 | 保留原句。 |
| 旧通知 | 另一账户期间 | 隔离当前事实。 |
| 输入缺证 | 无当前结算通知 | 不判未结算。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

第一处是目录整理被成稿扩为完成对账，应核动作及材料对象，查是否存在双方核对记录。第二处是另行核对条件在短稿中被省掉，应从说明页追到实际请求，再看回复是否遗漏。第三处是历史账户结算进入当前服务介绍，应核账户和期间，比较去掉历史的起草结果。三项分别追行为依据、限制传递和记录归属，不靠扩大回复空间得到结算事实。

## 怎么确认配好了

验收让稿件明确协助什么、谁核什么、哪些结果尚无当前依据，并逐句标注所用材料。token相关设置应分别记录引用、历史和回复，模型实际窗口另核。此处不提供金额或真实账户，也不执行交单、对账或结算。补来新通知要核主体、期间和具体状态后才能更新介绍；未在输入看见通知不能写成未结算，当前证据只支持整理及后续核对范围。
