# 大促仓配排产的商品与营销文案起草：上下文与 token

## 这个品类的数据长什么样

在大促仓配排产的商品与营销文案起草中，本页说明FastGPT的上下文与 token如何衔接资料。大促排班说明只呈现拟定人手与待确认事项，不生成实到或产能承诺。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

大促仓配介绍可拟排班纸稿“晚班拟安排打包岗”，备注“人员名单待领班确认”，一份旧日报记的是上次白班实到。当前写协作提示，需要区分拟定岗位、待核名单和已有实到证据。若起草请求只带晚班安排，回复可能写成全部到岗；历史白班数字或经历也不能证明这次晚班已执行。此处不提供人员数量或真实效率，重点是把计划与观察分别送入写作材料。

## 配置怎么定

| 材料核对项 | 本题具体条件 | 实施取证 |
| --- | --- | --- |
| 排班动作 | 拟安排 | 核输出时态。 |
| 名单状态 | 待确认 | 追备注覆盖。 |
| 确认主体 | 领班 | 保留责任对象。 |
| 旧日报 | 上次白班 | 核班次日期。 |
| 能力判断 | 未做现场测试 | 不推产能。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

第一处是拟安排改成已到岗，应对排班稿和成稿时态，找本班实际记录再说执行。第二处是名单待确认在短回复中省掉，应追备注从引用到输入再到输出，核谁仍需确认。第三处是上次白班实到移入本次晚班，应核班次和日期，比较空历史。三项分别查阶段、责任主体和记录时段，不能由提高回复上限推出真实人手或仓配能力。

## 怎么确认配好了

验收让提示写清岗位拟定、名单状态及确认对象，逐句核实际请求内支持。材料引用量、历史和回复长度分别记，模型真实上下文容量另核；条件未进入时先修输入。补到本班记录后才能按对应时段更新，不从别班推本班。本练习不排实际班、不通知员工或测试劳动能力，也不承诺大促处理效果，成稿完整并不证明人员到位或现场任务已经完成。
