# 平台店铺评价与体验分维护的商品与营销文案起草：上下文与 token

## 这个品类的数据长什么样

评价维护的数据来自抖店体验分、天猫服务指标、京东售后评价与客服系统，日常文档包括差评处理记录、体验分明细、服务诊断报告与整改台账。起草商品与营销文案时，这些材料提供的是售后履约后的消费者反馈事实，文案中的宣传句需要与材料原文对应。数据更新频率为日、周，该频率影响材料版本选择，不改变本页功能的配置方式。上下文与 token 环节的核心约束在于：模型单次请求可参考的内容长度由模型能力决定，回复上限控制单次回答长度，知识库引用上限按 token 控制引用内容量，三者是不同层面的限制。

## 这些特征在「上下文与 token」这一环带来什么约束

起草文案时，模型需要同时参考体验分明细中的指标字段、差评处理记录中的处理状态、服务诊断报告中的诊断结论与整改台账中的整改动作。这些材料长度不一，单段可能超过引用上限，导致关键字段被裁剪。历史输入会影响模型对当前问题的理解，相同问题在空历史与带历史下可能得到不同回答。若使用固定回复格式，字段齐全与解析成功需要单独验证，文本长度合格不代表结构正确。

假设演练样本：材料原文为“某店铺 2025 年 3 月体验分明细显示，物流体验得分 4.2，服务体验得分 4.5，商品体验得分 4.1；差评处理记录载明 3 月 12 日一笔差评已完成联系补充凭证，处理状态为待审核；服务诊断报告结论为物流时效为主要扣分项；整改台账记录 3 月 15 日已提交整改方案，尚未收到审核结果。”待判定拟稿句为“本店物流体验优秀，所有差评均已处理完毕，整改方案已获通过。”该句涉及三个待核实点：物流体验得分 4.2 是否支持“优秀”表述、处理状态“待审核”是否等于“处理完毕”、整改方案“已提交”是否等于“已获通过”。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| AI 模型 | 选择支持所需上下文长度的模型 | 比较模型最大上下文与材料总 token 估算值，确保材料不被截断 |
| 回复上限 | 设为能容纳依据与处理动作的长度 | 与拟稿句所需字段数量比较，过短会截断依据部分 |
| 引用上限 | 按 token 设置，覆盖单段最长材料 | 与材料各段 token 数比较，确保关键字段不被裁剪 |
| 记忆轮数 | 保留少量历史轮数 | 比较多轮追问场景下空历史与带历史的输入差异 |
| 回复格式 | 需要固定结构时选择 json_schema | 比较字段齐全与解析结果，文本长度合格不代表结构正确 |
| 最低相关度 | 按语义检索或重排生效条件设置 | 该值为过滤阈值，不承担权限或实体隔离功能 |

## 容易做错的三处

1. 将回复上限当作完整上下文窗口。模型最大上下文与回复上限是两个独立配置，回复上限只控制单次回答长度，不决定可参考的材料总量。核对时比较模型最大上下文数值与材料总 token 估算值。
2. 将处理状态“待审核”判定为“处理完毕”。差评处理记录中状态字段为待审核时，该事实尚未完成。核对时比较材料原文状态字段与拟稿句表述，状态字段未载明完成时记录为未获支持。
3. 将整改方案“已提交”判定为“已获通过”。整改台账记录提交动作与审核结果属于不同事实。核对时比较台账中提交日期与审核结果字段，审核结果缺失时保留证据缺口。

## 怎么确认配好了

1. 输入假设演练样本中的材料原文与拟稿句，比较拟稿句中“物流体验优秀”与体验分明细中物流体验得分 4.2 的对应关系。材料未载明优秀判定标准时，该表述为未获支持，需记录缺口。
2. 输入差评处理记录原文，比较处理状态字段“待审核”与拟稿句“处理完毕”。两者为同一字段的不同取值，状态为待审核时拟稿句表述与材料矛盾，应判定为不成立。
3. 输入整改台账原文，比较提交日期与审核结果字段。台账仅记录提交动作、审核结果未载明时，拟稿句“已获通过”为待核实，不能判定为通过。若使用固定回复格式，另需比较返回字段是否齐全、解析是否成功。空结果承接可用纸面输入空数组核对下游设计，不声称虚构规则检索一定返回空数组。
