# 生鲜冷链到店验收的商品与营销文案起草：模型接入与配置

## 这个品类的数据长什么样

在生鲜冷链到店验收的商品与营销文案起草中，本页说明FastGPT的模型接入与配置如何衔接资料。核对资料实际支持的范围及其引用。所用场景为自拟文字测试。

## 这些特征在「模型接入与配置」这一环带来什么约束

本页自拟两份冷链文案测试材料：送货说明列商品名称、包装形态与清蒸建议，验收附页另给烧烤建议；两份均未提供营养检测、品质等级或认证凭证。名称用于辨认商品，包装说明介绍所给形态，两种做法建议各保留原文对象和条件。这些文字足以构成有范围的介绍素材，不必因为缺少专门卖点栏就视为无法起草。接入时分别检查两份文件及其内容是否送达，再看草稿有没有把一种建议改成商品保证；文案安排更顺并不会改变原文能证明什么。此为纸面练习，不是实际食品验收或营养评价。

## 配置怎么定

| 文案需保留什么 | 哪份文字提供 | 复核时看什么 |
| --- | --- | --- |
| 名称与包装 | 自拟送货说明提供名称与包装 | 介绍不增加检测或品质等级 |
| 清蒸建议 | 同一送货说明中的清蒸建议 | 不改写为唯一做法 |
| 烧烤说明 | 自拟验收附页中的烧烤建议 | 保留该页身份与适用对象 |
| 营养及认证 | 送货说明与验收附页均未给证明 | 新增承诺须回到独立依据 |
| 卖点栏空缺 | 已有名称包装仍是可用素材 | 不能把未预制文案当成没有事实 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `AI Proxy依赖` | 按实际版本核服务、渠道与应用。 |
| `AIPROXY_API_ENDPOINT` | 使用AI Proxy服务根地址。 |
| `AIPROXY_API_TOKEN` | 管理员Token非空且与服务端一致。 |
| `模型能力` | 按实际输入路径验证所需能力。 |
| `应用参数` | 接口同名字段未必覆盖应用设置。 |

## 容易做错的三处

- 验收附页未传入，却声称两份文件共同核了烹饪描述：保存送货说明、验收附页的材料清单与实际请求，先查烧烤建议所在文件的遗漏，不将单方输出当成双源结果。

- 送货说明的清蒸建议与验收附页的烧烤建议均送达，却被写成唯一可用方式：并列两份原文及返回，核是否错误排斥，模型选择不承担裁决适用做法的责任。

- 名称包装被扩成营养或认证结论：将新增句回指原文及凭证，缺预制卖点字段不等于无素材，也不能补出未给事实。

## 怎么确认配好了

没有预先写好的卖点提炼字段，不等于所有文案素材都不存在。应先分别列出送货说明与验收附页已经提供的事实，再逐项检查草稿新增了什么：仅复述名称与包装不同于承诺营养价值、品质或特定受众。额外表述需要相应产品资料。补充后保持原题与设置，检查新增原文是否送达以及文案采用了哪些内容，不能以生成更流畅推定事实支持已经充分。
