# 直播售后集中处理的商品与营销文案起草：上下文与 token

## 这个品类的数据长什么样
直播售后集中处理常在一场流量结束后集中爆发，退款申请、补发单与订单清单同时涌入，客服需要统一解释主播当时的承诺。文案起草因此依赖三份材料：直播订单清单、退款申请、话术模板。它们决定一段宣传句能引用哪些事实。数据按每场后、日更新，文案核对须以同一场次、同一订单范围为准。

## 这些特征在「上下文与 token」这一环带来什么约束
上下文与 token 环节决定模型一次能读入多少材料、引用多少知识库内容、保留多少历史轮数。材料越长，越容易触及模型最大上下文；引用上限按 token 控制，超出部分会被裁剪，导致拟稿句失去依据。历史轮数过大会带入无关对话，过小则无法利用前文承诺。回复上限只限制输出长度，与完整上下文窗口是两个量。

假设演练样本：材料原文为“本场直播订单范围 2025-06-01 20:00 至 23:00，订单号段 A1001 至 A1200。主播在 21:15 说明该批次赠品随主商品同发。仓库补发单 B-07 记录 6 月 3 日已为 A1032 单独补发赠品。”待判定拟稿句为“本场所有订单赠品均已随主商品同发。”该句与材料中 A1032 单独补发的事实不一致，属于未获支持。

## 配置怎么定
下表围绕上述样本，列出与本功能、主任务相关的官方已说明设置或实施核对项。数值为本次假设试验起点，用于与样本材料比较，不作为官方默认值。

| 配置项 | 本次假设试验起点及理由 | 核对方式 |
| --- | --- | --- |
| AI 模型最大上下文 | 选择可容纳三份材料的模型，按弹窗显示数值比较 | 将材料与拟稿句一并输入，观察是否被截断 |
| 记忆轮数 | 设为少量轮数，客服场景通常保留少量历史即可 | 比较空历史与带历史下同一问题的输入差异 |
| 回复上限 | 保留足以表达依据与处理动作的长度 | 检查回复是否在依据句之前被截断 |
| 引用上限 | 按 token 控制，结合单段长度与问题样本 | 核对引用内容是否覆盖订单号段与补发单 |
| 最低相关度 | 仅在语义检索或结果重排时生效 | 观察低相关片段是否被过滤，不视为权限过滤 |
| 回复格式 | 需要固定字段时选择 json_schema 并填写格式要求 | 验证字段齐全与解析成功，不只看文本长度 |

## 容易做错的三处
1. 把回复上限当作完整上下文窗口。输入材料超出模型最大上下文时，拟稿句依据被裁剪，输出仍可能看似完整。检查：比较输入材料总长度与弹窗显示的最大上下文，观察依据句是否完整出现。
2. 把引用上限写成 top k 或固定条数。引用上限按 token 控制，不同 chunk 长度差距大。检查：用同一问题比较不同单段长度下的引用内容，观察是否按 token 裁剪。
3. 把最低相关度当作权限或实体过滤。该值只过滤低相关结果，不排除无关业务或未授权记录。检查：输入含无关业务的查询，观察返回内容是否仍可能包含非目标订单，记录实际观察而不推断必然为空。

## 怎么确认配好了
1. 输入上述假设材料原文与拟稿句，比较拟稿句“所有订单赠品均已随主商品同发”与材料中 A1032 单独补发的事实。若输出指出该句未获支持或要求补充范围，则满足条件；若输出直接认可该句，则不满足。
2. 将同一问题分别在空历史与带历史下输入，比较两次输入内容差异。若带历史时引入了前文承诺且未超出记忆轮数，则满足条件；若历史未生效或超出上下文，则不满足。
3. 使用固定回复格式时，输入材料与拟稿句，检查返回字段是否齐全并可解析。若字段齐全且解析成功，则满足条件；若字段缺失或解析失败，则不满足。空结果承接可用明确的纸面输入 [] 核对下游设计，不声称虚构规则检索一定返回 []。
