# 直播间违规申诉的商品与营销文案起草：上下文与 token

## 这个品类的数据长什么样

直播间违规申诉处理的是已经发生的平台处罚，材料围绕违规通知、直播录屏、商品资质与申诉说明展开。商品与营销文案起草这一环节，需要把处罚指向的具体宣传句与资质材料逐条对齐，判断拟稿句是否有材料支撑。

材料更新不定期，每次违规单独成组。同一场直播的录屏片段、商品资质文件与违规通知条款之间，存在时间、主体与字段三重对应关系。上下文与 token 的约束由此产生：模型单次请求能参考的内容长度有限，材料过长时会被裁剪，裁剪位置决定拟稿句能否看到对应证据。

## 这些特征在「上下文与 token」这一环带来什么约束

模型单次请求可参考的内容长度由最大上下文决定，回复上限只限制输出长度，两者不能互相替代。知识库引用上限按 token 控制每次搜索最多引用的内容量，长片段会挤占其他片段的引用空间。历史输入会占用上下文，同一问题在空历史与带历史下送入模型的输入不同。使用固定回复格式时，字段齐全与解析成功需要单独核对，文本长度不能作为替代。

假设演练样本（纸面材料，非真实记录）：

材料原文一：违规通知载明「2025年3月12日场次，商品A宣传句『该成分可替代药物治疗』，判定为功效违规」。

材料原文二：商品资质文件载明「商品A为普通食品，备案类别为固体饮料，备案日期2025年1月8日，备案主体为某食品生产企业」。

材料原文三：直播录屏文字稿载明「主播于2025年3月12日21时14分口播『这个成分能替代药物』」。

待判定拟稿句：「商品A的该成分可辅助改善，相关表述已按普通食品备案范围调整。」

判定所需字段为宣传句内容、商品类别、备案范围与口播时间。材料原文二只载明备案类别与日期，未载明该成分的具体功能表述范围，拟稿句中的「辅助改善」在该材料中未获支持，属于待核实项，不构成与备案内容的矛盾。

## 配置怎么定

| 配置项 | 本页相关取值或核对项 | 与样本的对应关系 |
| --- | --- | --- |
| AI 模型最大上下文 | 按实际模型能力核对，不把回复上限当作完整上下文窗口 | 三句材料加拟稿句需完整落入单次请求 |
| 回复上限 | 结合任务调整，保留足以表达依据与处理动作的内容 | 拟稿句与判定理由需完整输出 |
| 知识库引用上限 | 按 token 控制引用，结合单段长度与问题样本核对内容是否被裁剪 | 核对材料原文二是否被裁剪 |
| 记忆轮数 | 比较相同问题在空历史与带历史下的输入差异 | 排除历史带入的无关场次内容 |
| 回复格式 | 使用 json_schema 时验证字段齐全与解析成功 | 判定字段需与材料字段同名 |
| 思考强度 | 按模型支持的档位选择，思考预算与引用 token 上限分属不同配置 | 复杂证据链比对可选较高档位 |

引用上限采用 token 单位，不采用 top k，原因是不同 chunk 长度差距大。最低相关度仅在语义检索或结果重排时生效，属于过滤阈值，不承担权限或实体隔离功能。

## 容易做错的三处

1. 把回复上限当作完整上下文窗口。回复上限限制输出长度，材料原文一至三与拟稿句的输入长度由最大上下文约束。核对时比较三句材料加拟稿句的总长度与该模型显示的最大上下文，观察材料是否在输入侧被裁剪。

2. 引用上限设置过小，材料原文二未进入引用内容。核对时比较引用上限的 token 值与三句材料的实际 token 量，观察返回引用中是否包含备案类别与备案日期字段。缺失时记录为未获引用，不推断为材料不存在。

3. 用带历史输入核对拟稿句，历史带入其他场次内容。核对时对同一拟稿句分别构造空历史与带历史输入，比较两次送入模型的材料集合，观察带历史输入是否混入非2025年3月12日场次的表述。

## 怎么确认配好了

1. 输入材料原文一至三与待判定拟稿句，比较拟稿句中「辅助改善」与材料原文二的备案类别、备案范围字段，观察输出是否将「辅助改善」标为待核实，材料原文二未载明该功能表述范围时不得判为已获支持。

2. 输入同一拟稿句的空历史版本与带历史版本，比较两次引用内容中出现的场次日期，观察带历史版本是否出现2025年3月12日以外的场次表述。出现即记录为历史带入，需在核对记录中标注。

3. 输入明确的纸面空引用结果，核对下游节点对空引用的承接设计，观察下游是否输出「未检索到可引用材料」并保留字段结构。该核对只验证承接设计，不声称检索一定返回空结果。

以上核对均为纸面推演，未实际执行，不构成对任何模型、库或下游系统的运行结论。
