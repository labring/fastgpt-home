# 直播间违规申诉的商品与营销文案起草：多轮对话与提示词

## 这个品类的数据长什么样

直播间违规申诉围绕已经发生的平台处罚展开，需要复盘证据链。主要材料来自平台违规中心、直播回放、客服记录和商品资质库。数据更新不定期，每次违规触发一轮处理。日常文档包括违规通知、直播录屏、商品资质和申诉说明。最耗时的环节是定位违规片段、补充证据、撰写申诉理由。这些特征意味着多轮对话要能承接前几轮已确认的材料范围，提示词要明确回答任务和缺证据时的处理方式，不让模型补写业务事实。

## 这些特征在「多轮对话与提示词」这一环带来什么约束

多轮对话依赖会话历史。对话接口文档说明，传入非空 chatId 时自动从数据库取会话，messages 数组最后一个内容作为用户问题，其余 message 被忽略。新会话不传 chatId 时完全通过 messages 构建上下文。历史记录需核对实际带入的上下文，区分新会话和继续会话的输入。问题优化需要知识库连续对话时核对指代消除及问题扩展，不假设所有短问题都适用。模型与长度需核对模型支持的上下文和回复设置，测试长文档与追问组合。回复格式按后续承接选择，选择 json_schema 时填写对应格式要求并验返回结构。

假设演练样本：材料原文为「违规通知载明：2025年3月12日场次，商品A的讲解片段出现『全网最低价』表述，处罚状态为商品禁播，申诉截止日期为2025年3月19日。」「商品资质库记录：商品A的备案主体为某供应链公司，备案有效期至2025年12月31日。」待判定拟稿句为「商品A已取得完整备案，本次处罚应予以撤销。」该拟稿句把备案有效与处罚撤销混为同一事实，备案状态不构成撤销依据，属于未获支持。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| AI 模型 | 选用支持长上下文的对话模型 | 与申诉材料长度比较，核对最大上下文是否覆盖违规通知与资质文本 |
| 记忆轮数 | 设为能覆盖违规通知、资质、拟稿句三轮 | 与继续会话实际带入的历史比较，确认前轮材料范围未被截断 |
| 回复上限 | 设为可容纳申诉说明完整段落 | 与拟稿句长度比较，观察是否出现提前截断 |
| 温度 | 设为偏低 | 与规则明确场景比较，观察拟稿句是否稳定引用材料原文 |
| 回复格式 | 保持默认 | 与后续承接方式比较，仅在需要读取固定结构时改用 json_schema |
| 多模态识别 | 按模型能力决定是否开启图片识别 | 与直播录屏截图输入比较，核对模型能力过滤后是否发送 |

## 容易做错的三处

1. 把检索相似度当作权限或实体过滤。相似度分数不排除无关业务或未授权记录，检索不承担授权职责。检查输入为一次带 chatId 的继续会话请求，比较返回的 quoteList 与材料范围，观察是否混入非本场次记录。
2. 把备案有效写成处罚撤销依据。拟稿句「已取得完整备案，处罚应予以撤销」把两个不同事实合并。检查输入为该拟稿句与备案原文，比较主体、对象、状态是否同一字段，观察是否出现未载明的撤销结论。
3. 把交互节点的展示配置当成已执行业务动作。交互返回仅含 type 和 params，待审核不证明缺少操作权限。检查输入为一次 detail=true 的交互响应，比较 entryNodeIds 等内部字段是否返回，观察是否把展示配置误读为审批完成。

## 怎么确认配好了

1. 输入假设样本中的违规通知原文与拟稿句，比较拟稿句是否只引用通知载明的场次、商品、表述和处罚状态，观察输出是否出现通知未载明的撤销结论。满足条件为拟稿句保留证据缺口。
2. 输入一次新会话请求与一次带 chatId 的继续会话请求，比较两次实际带入的上下文范围，观察继续会话是否只取 messages 最后一个内容作为用户问题。满足条件为历史轮数与材料范围一致。
3. 输入一条含图片链接的追问，比较模型多模态能力与提取链接条件，观察不支持的类型是否在请求前被过滤。满足条件为发送内容与模型能力一致，未支持类型不发送。
