# 社区团购预售集单的商品与营销文案起草：多轮对话与提示词

## 这个品类的数据长什么样

预售集单先收订单再组织采购履约，商品文案与营销文案的起草依赖预售商品表、集单结果、采购计划与截单通知。这些材料按日或按场更新，文案里出现的规格、数量范围、截单时间与履约口径需要与当次材料一致。多轮对话用于在起草过程中追问和修订，历史记录会把前文带入后续轮次，因此每轮引用的材料版本要能对应到同一场次。

## 这些特征在「多轮对话与提示词」这一环带来什么约束

提示词需要写明资料范围、起草任务与缺证据时的处理方式。资料未载明的规格、时效或承诺，模型不得补写为业务事实。继续会话时，系统按 chatId 从数据库取会话，并以 messages 数组最后一个内容作为用户问题，其余 message 被忽略；新会话不传入 chatId 时完全由传入的 messages 构建上下文。问题优化面向知识库连续对话，用于指代消除与问题扩展，短问题是否适用需按实际配置核对。模型与长度方面，需核对模型支持的最大上下文与回复上限，并测试长文档与追问组合。回复格式按后续承接选择，选择 json_schema 时需填写对应格式要求并验证返回结构。

假设演练样本：材料原文为“本场预售商品为散装土豆，规格为每袋5千克，截单时间为本场当日18时；集单结果以小程序订单为准，采购计划在截单后编制。”拟稿句为“本场土豆每袋5千克，今日18时截单，下单后即可安排采购。”需判定“下单后即可安排采购”是否被材料支持。

## 配置怎么定

| 配置或核对项 | 本页用途 | 本次假设试验起点与比较方法 |
| --- | --- | --- |
| AI 模型 | 承担文案起草与追问回答 | 选择弹窗中显示支持所需上下文长度的模型，与拟稿句所需材料长度比较 |
| 记忆轮数 | 控制带入前文轮数 | 假设起点为保留少量历史轮数，与仅本轮材料起草的结果比较 |
| 回复上限 | 限制单次回复长度 | 假设起点为可容纳完整拟稿句，与截断现象比较 |
| 温度 | 控制措辞稳定程度 | 假设起点为偏低，与同一材料多次起草结果的一致性比较 |
| 回复格式 | 承接后续读取 | 需要固定结构时选择 json_schema 并填写格式要求，与返回结构比较 |
| 多模态识别 | 读取商品图或海报 | 模型支持时按需开启，与未开启时的输入内容比较 |

以上数值为本次假设试验起点，选择理由是与文案起草需要稳定、可核对的结果相符，比较对象为同材料下的实际输出。

## 容易做错的三处

1. 把材料未载明的履约承诺写入拟稿句。输入为上述材料原文与拟稿句，比较“下单后即可安排采购”与“采购计划在截单后编制”，材料只说明截单后编制，未说明下单即可安排，该句未获支持。
2. 继续会话时误以为全部 messages 参与。输入为带 chatId 的请求与多条 messages，比较实际带入的上下文，系统仅以最后一条内容作为用户问题，其余被忽略。
3. 把相关度分数当作权限或实体过滤。输入为检索返回的 score，比较其定义，score 表示相似程度，不承担业务授权或实体隔离。

## 怎么确认配好了

1. 输入上述材料原文与拟稿句，比较拟稿句中的时间与履约表述是否能在原文找到对应字段，预期结果是“下单后即可安排采购”标记为未获支持，截单时间与规格可对应。
2. 输入带 chatId 的继续会话请求与多条 messages，比较实际用于回答的用户问题，预期结果是仅最后一条内容被采用，其余 message 被忽略；若结果不符，检查 chatId 与 messages 组织方式。
3. 输入纸面空结果 [] 与下游承接设计，比较下游在空引用时的输出，预期结果是下游按空引用处理，不产生无来源的业务结论；检索是否返回空需按实际观察记录，不作保证。
