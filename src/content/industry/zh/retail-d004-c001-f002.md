# B2B平台撮合交易的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在B2B平台撮合交易的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。合同限制在长文与连续追问的实际输入中是否仍被保留？所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

自拟合同把服务范围限定在当前批次的蓝色款，后文注明其他颜色需要另行确认。核对长文输入时，应先标出这两处原文，再查看模型实际接收的内容中是否仍有该批次和颜色限制。模型上下文、知识引用token上限及回复长度分别约束不同阶段，需要对照真实输入判断条件在哪里丢失。测试不能只看回答够不够长；若限制在进入模型前已经缺失，增加回复长度也不能补回原文。

## 配置怎么定

| 核对项 | 本次输入检查 | 验收线索 |
| --- | --- | --- |
| 模型上下文 | 按实际模型核可接收范围 | 批次、蓝色款与其他颜色条件仍在输入 |
| 回复长度 | 单独核回复设置 | 没有用输出长度掩盖缺失的合同依据 |
| 知识库引用上限 | 以token检查引用裁剪 | 服务范围和例外条件成对保留 |
| 历史输入核对 | 比较空历史与带红色款历史的同一追问 | 没有把旧材料的条件移用于本题 |
| 结构化承接 | 解析检查与事实回查分别进行 | 签收凭证缺失时不生成交付事实 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

- 当前蓝色款合同的批次和其他颜色另核条件没进入请求时，对照完整原文与实际输入，查条件在哪一步缺失，延长回复不能补回。

- 历史红色款条件被移给黑色款追问时，固定当前合同比较空历史和带历史输入，检查颜色、批次与指代。

- 没有签收凭证，结构化结果却填已收货时，先验解析再核字段来源；格式正确不能提供实际交付事件。

## 怎么确认配好了

合同没有签收凭证，无法支持已经收到货物的事实判断。验收应把缺少凭证与输入长度问题分别列出，再检查回复有没有自行补写交付事件。需要结构化承接时，先验证返回是否可解析、必要字段是否齐全，随后逐项核对字段内容的原文依据。补齐凭证后再复测原问题和追问，并记录新增资料与长度设置各自的变化，避免把格式正确或文字完整当成事实已经得到支持。
