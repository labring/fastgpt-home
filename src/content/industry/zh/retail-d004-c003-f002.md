# Shopify独立站订单履约的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在Shopify独立站订单履约的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。柜体楼下交接与入户搬运分别保留服务范围。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

Shopify交易比对可自拟服务说明“柜体送至楼下交接；入户搬运另议”，沟通备注写“和上次一样送上门”，本组没有上次订单。用户问是否含入户时，楼下、入户和另议需要一起进入当前输入。送上门在备注中没有定义，不能直接替换明确的楼下交接；也不能据缺少上次订单，反向判定双方从未约过搬运，只能指出当前材料尚未给出该项确认。

## 配置怎么定

| 上下文核对对象 | 具体文字条件 | 验收线索 |
| --- | --- | --- |
| 当前地点 | 楼下交接 | 核地点原句完整传入。 |
| 额外服务 | 入户搬运另议 | 保留条件及待确认动作。 |
| 历史口语 | 送上门未定义 | 不替换明确地点。 |
| 对象指代 | 配件与整柜可能混指 | 对照当前对象与历史。 |
| 工单承接 | 地点、服务范围与待核项 | 核实际格式和解析结果。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

常见错误是引用裁剪只留下送至楼下前的商品名，回答依靠历史口语补成入户；另一处风险是把上一段谈配件的它误指为整柜，将服务范围也随之迁移。排查时对照实际输入中的对象、交接地点和指代，不仅看回复是否流畅。应分开记录哪些字句未传入、哪些历史对象被带入。上下文容量与回复上限分别核，不能通过增大回复长度恢复缺失的交接条件。第三处是把上次订单的搬运条件直接移给当前交易。应另核旧订单与本单的明确适用关系，不仅比较送上门这句口语；同一买家和同样柜体都不能自行建立服务沿用依据。

## 怎么确认配好了

验收可将问题写成“当前文字是否包含把柜体搬入室内”，先用空历史，再加入送上门备注比较依据。输出需要保留楼下交接原句、入户另议条件和待补确认，不把简短的含或不含当成完整比对。若约定格式用于后续工单，应核地点与待核动作都被解析出来。额外取得上次订单后，还要核它与当前交易是否有明确适用关系，不能仅因同一买家就迁移服务。
