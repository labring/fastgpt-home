# 一般贸易出口报关的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在一般贸易出口报关的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。装运前核对稿与正式签认单据需要保留文档阶段。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

出口交易比对自拟条款“装运前提交核对稿；正式单据另行签认”，装箱清单页眉写核对稿，邮件回复仅写已收到。有人问单据是否已经确认，输入需要保留核对稿身份、正式签认条件及邮件接收动作。收到文件与确认内容不是同一个事项；本组也没有实际装运记录。不能从装运前这个时间关系反推货物已经装运，或把收件回复扩成正式认可。

## 配置怎么定

| 上下文核对对象 | 具体文字条件 | 验收线索 |
| --- | --- | --- |
| 稿件身份 | 页眉为核对稿 | 核页眉是否进入输入。 |
| 确认条件 | 正式单据另行签认 | 保留阶段限制。 |
| 收件动作 | 邮件仅写已收到 | 不扩为内容认可。 |
| 历史建议 | 可提交不等于已签认 | 比较建议与实际动作。 |
| 交单准备 | 阶段、动作、待核材料 | 核固定输出完整解析。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

一种失败条件是页眉在引用中丢失，草稿正文被回答当成正式单据；另一处风险是历史讨论过可提交，当前回答把建议当成已签认。应核实际输入里的文档阶段、动作与主体，再对照完整来源定位变化。正式单据没有提供时，增大上下文额度不能增加该证据；回复长度只决定输出表达空间。较长的核对稿仍要按实际片段检查是否保留另行签认这一限制。第三处是把邮件已收到当成正式签认。应查实际签认材料及其对应单据，区分接收文件和确认内容两个动作；不能仅因回信存在，就用它填满正式确认这一缺项。

## 怎么确认配好了

验收分别问稿件已到哪一步、邮件证明哪种动作、还缺什么确认材料。答案应保持已提交或已收的原文范围，并列出正式签认尚待核；不能简单写文件流程已完成。相同问题带入旧讨论后再核依据是否改变，保留两次实际输入。固定回复若供交单准备使用，应核稿件阶段、已见动作和待办均完整解析，且没有将文件准备进度写成货物实际运输结果。
