# 亚马逊FBA备货运营的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在亚马逊FBA备货运营的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。托盘方案待确认与散箱另议，不能被会议建议合并。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

FBA交易比对自拟约定“托盘方案须在送仓前确认；散箱方案另议”，会议摘录写“可考虑散箱”，计划备注写“待确认”。问能否直接照散箱送仓时，输入应保留托盘和散箱两种方案各自的条件。可考虑属于讨论建议，待确认属于计划状态，本组没有最终确认；不能将两个片段接成已经选定散箱，更不能从送仓前这个时点倒推送仓动作已发生。

## 配置怎么定

| 上下文核对对象 | 具体文字条件 | 验收线索 |
| --- | --- | --- |
| 方案主体 | 托盘与散箱分开 | 逐方案保留条件。 |
| 建议语气 | 可考虑散箱 | 不改为已选定。 |
| 确认对象 | 计划仍待确认 | 核最终确认覆盖范围。 |
| 旧批历史 | 别批方案可能已执行 | 不迁移本批可执行结论。 |
| 分案输出 | 建议、待核动作及原文 | 核方案身份和解析。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

常见错误是摘要只留下散箱方案而丢了另议，或历史中某批散箱已用过，当前回答迁移为本批可执行。应核会议句的建议语气、计划对象和历史批次，分别定位条件裁剪与方案迁移。托盘方案确认并不自动确认散箱，两个对象都需明确。模型可用上下文与回复长度分别按实际设置核，不用增加输出篇幅替代确认材料，也不把材料进入输入当作方案批准。

## 怎么确认配好了

验收分别问已讨论哪些方案、每种方案尚缺什么、本批是否已有确认。用相同问题对照空历史与带旧批记录的输入，确保本批条件仍可见。输出可逐方案列已见建议、待核动作与对应原文，核固定格式是否保留方案身份并解析成功。后续取得确认时仍需核它明确覆盖哪种方案；一句同意不能脱离被确认的对象，被扩成所有包装与入仓条件均已满足。
