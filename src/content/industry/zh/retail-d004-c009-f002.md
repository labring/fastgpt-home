# 亚马逊FBM自发货运营的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在亚马逊FBM自发货运营的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。补寄先核主件型号，地址变更另需确认，两条条件各有对象。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

FBM交易比对自拟条款“配件补寄前先核主件型号；地址变更另需确认”，服务备注写“红色款，照旧”，历史聊天谈过另一型号。用户问能否直接照旧补寄时，输入必须保留主件型号核对与地址变更两个条件。红色是颜色描述，本组未说明它能唯一定位型号；照旧也没有明确指向哪次地址或方案。不能让口语指代替代实际确认，更不能补造收件信息。

## 配置怎么定

| 上下文核对对象 | 具体文字条件 | 验收线索 |
| --- | --- | --- |
| 型号依据 | 红色未证明唯一型号 | 核主件实际对象。 |
| 补寄条件 | 先核主件型号 | 保留前置动作。 |
| 地址条件 | 变更另需确认 | 核引用是否截断。 |
| 历史对象 | 另一型号的旧讨论 | 对照实体是否迁入。 |
| 售后承接 | 主件、配件与待确认项 | 核成对关系和解析。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

一种失败是历史型号进入当前答案，红色款被自动对应成旧型号；另一处是引用裁掉地址变更条件，输出据照旧声称地址已经确认。应保留当前主件、历史对象及被截断条件，分别核实体混用和信息缺失。上下文窗口核实际模型能力，回复长度按比对任务留足条件和待办。增加历史并不一定增加依据，也可能引入另一个对象，需要用空历史对照定位影响。第三处是仅按红色认定主件型号已核。应查颜色与型号之间是否有本组可回指的对应资料；颜色相同并不自动唯一定位，不能在没有映射依据时把补寄前置核对标为完成。

## 怎么确认配好了

验收将型号依据、补寄前置动作、地址状态分开询问，检查输出是否明确红色尚不足以确定型号，照旧尚无清晰指向。固定格式用于售后承接时，可核主件对象、配件对象与待确认事项是否成对保留并可解析。相同问题带入另一型号历史后，答案不应未经核对替换当前对象。取得实际确认后仍需逐项核覆盖范围，不能以型号确认一项推成地址亦已确认。
