# 京东POP第三方店铺运营的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在京东POP第三方店铺运营的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。送修收件范围与检测后的维修方式不能合并成已定方案。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

京东POP交易比对自拟指引“送修前核收件范围；检测后确定维修方式”，收件说明写“本次仅收主机，线缆不随寄”。用户问是否整套寄回并直接更换时，输入要同时保留本次范围、线缆除外和检测后确定。主机收件与更换决策属于不同阶段；材料未提供检测结论或实际维修方案，不能从已安排送修推定直接更换，也不能把不随寄解释成线缆无需任何服务。

## 配置怎么定

| 上下文核对对象 | 具体文字条件 | 验收线索 |
| --- | --- | --- |
| 本次范围 | 仅收主机 | 核当前对象和本次限定。 |
| 除外部件 | 线缆不随寄 | 核否定条件保留。 |
| 决策顺序 | 检测后确定维修方式 | 不提前补更换结论。 |
| 历史建议 | 曾讨论更换 | 核是否跳过当前前置条件。 |
| 服务输出 | 收件、除外与待核方案 | 验证完整解析。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

常见错误是引用裁去线缆除外，回答把整套作为送修对象；另一种失败是历史讨论过更换，当前答案跳过检测条件直接沿用。应核实际输入中的收件对象与决策顺序，并把已见指引和历史建议分开。模型上下文核实际能力，回复不能为简短只保留寄回主机而省略后续待核动作。更长回复同样无法填入未提供的检测结果，缺项需要明确列出。

## 怎么确认配好了

验收分别问本次收什么、哪些不随寄、维修方式何时确定，以对应原句核输出。空历史与带更换讨论历史使用相同问题，检查是否改变本次范围或跳过检测阶段。固定格式若承接服务事项，应将收件主机、除外线缆与待检测后确认的方案都完整解析。取得新检测材料时再核其对象和建议效力，不将检测建议自动写成已完成维修，也不替客户作责任或费用判断。
