# 便利店加盟门店督导的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在便利店加盟门店督导的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。门店整改依据中的店型、期间和排除条件不能被摘要合并。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

门店交易比对可拟本店附页“端架方案待复核”、标准说明“仅供宽通道店参考”和旧验收“另一门店已确认”。当前本店为窄通道练习设定，问题是能否按旧方案直接认定完成。输入需要同时呈现店型与参考范围，不把宽通道参考页作为所有加盟店的统一要求。长历史可能一直讨论另一门店，保留的材料应明确本轮对象，不能因同一区域或同一方案名就沿用旧验收。

## 配置怎么定

| 上下文材料核对 | 输入与表达条件 | 验收动作 |
| --- | --- | --- |
| 店型条件 | 窄与宽通道分开 | 核限制入实际请求。 |
| 参考地位 | 仅供参考 | 不提升统一要求。 |
| 历史主体 | 另店旧验收 | 核摘要及本轮指代。 |
| 本店状态 | 待复核 | 输出不省略。 |
| 容量归因 | 先看实际缺文 | 不预设模型原因。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

第一处是仅供宽通道店参考被裁掉后当本店要求，应核标准原句到实际输入的覆盖，查限制是否真实送达。第二处是旧验收的另一店身份在历史摘要中丢失，应对原对话与当前请求，并用空历史同题核本店指代。第三处是输出只写方案已确认而省掉本店待复核，应逐项核状态与店别表达，必要时调整回复长度再复测。三项分别查限制、历史主体和回答状态，不把更长输出当实际复核已经完成。

## 怎么确认配好了

验收可分别问参考页适用于谁、本店现有状态、旧验收属于谁，保存输入与回答原句。引用token预算要让店型限定和状态文字能一同核对，实际是否丢失应由请求内容证明，不能预先归因模型容量。若缺本店复核记录，应列来源待补。模型窗口与回复上限分别依实际能力和任务核验，测试不执行巡店或验收，也不把自拟参考页称真实公司制度。
