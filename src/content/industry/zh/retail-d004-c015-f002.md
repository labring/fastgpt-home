# 信用证审单交单的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在信用证审单交单的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。长单据比较中的修改范围、引用附页和结果阶段需要留在同一问题输入。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

审单文字练习可拟原说明“商品描述见清单”、修改页“只调整包装表述”和复核稿“数量项目另核”。当前问题是能否说所有项目已经一致。输入要保留只调整及另核，不把修改页压成全文都已修改，也不将复核稿当终局结果。长背景可包含旧题的数量讨论，但不得据此填本题数量项目。本页不引入真实信用证条件或银行要求，只核自拟材料各自支持的比较范围。

## 配置怎么定

| 上下文材料核对 | 输入与表达条件 | 验收动作 |
| --- | --- | --- |
| 修改范围 | 仅包装 | 输入保留仅字。 |
| 未核项目 | 数量另核 | 答复逐项保留。 |
| 题目身份 | 历史旧题 | 核本题清单。 |
| 文书阶段 | 复核草稿 | 不当正式结果。 |
| 附页送达 | 实际输入可回查 | 先查缺失环节。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

第一处是修改范围被摘要扩成全部项目，应核原修改句与实际送达文字，保留只调整包装。第二处是历史旧题数量被接成本题答案，应对题目、清单和实际请求，并用空历史同题作对照。第三处是回复只写一致却省掉数量另核，应核答复逐项覆盖及长度，不能以结论简洁掩盖未核项目。三项分别查范围、题目身份和结果表达，不把更多上下文或更长回复当正式审单结果。

## 怎么确认配好了

验收分别问修改动了什么、哪些内容仍需核、结果文书属于什么阶段，保存请求与输出。引用token限制下，要查看清单身份及修改限定是否真的保留；若附页没进输入，先追查来源和传递。模型窗口根据实际能力确认，回复上限不等于可送入全部文书。调整后重复同组问题，记录依然缺少的材料。本练习不交单、不判断银行接受，也不从文本比较宣称所有要求已满足。
