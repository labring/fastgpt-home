# 加盟费与保证金结算的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在加盟费与保证金结算的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。保证金结算中的申请类别、办理对象和状态词不能被长摘要合并。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

加盟结算可拟保证金台账“资料待补”、服务费通知“说明已发送”和门店申请“请核保证金处理进度”。当前问题只问保证金。实际输入要保持三份材料的款项身份，不能把服务费说明已发送的动作拼成保证金已处理。长历史若讨论过另一家门店的退回结果，也不适用于当前申请。没有金额和实际审核结果的自拟文本，只能用于核类别与进度，不因结算材料篇幅长就自行推定同笔事项。

## 配置怎么定

| 上下文材料核对 | 输入与表达条件 | 验收动作 |
| --- | --- | --- |
| 款项身份 | 保证金与服务费 | 核摘要未合并。 |
| 进度词 | 待补与已发分开 | 核对象匹配。 |
| 历史店别 | 他店退回 | 不移用当前。 |
| 回答待办 | 资料缺口 | 留足表达内容。 |
| 预算限制 | 不能产生审核结果 | 核真实原文。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

第一处是服务费与保证金在摘要中统一成费用，应查原文名称、来源身份与实际请求的对应，恢复被省的类别。第二处是另一门店的历史结果被当当前状态，应核店别和申请，使用空历史同题比较送达材料。第三处是答复只保留已发送而遗漏资料待补，应对输出状态与各自对象，调整长度也需保留待办。三项分别查类别、历史归属和状态表达，不用回复流畅代替本次处理证据。

## 怎么确认配好了

验收先问台账缺什么、通知发了什么、申请针对什么，再核每句是否来自实际输入。引用token预算应保留类别及待补条件，不能只看返回条数或总结长度。实际模型上下文窗口和回复上限分别核验；若台账原文没有结果，增加预算也不补出批准或支付。本练习不决定可退条件、不执行结算，不将资料已发送写成退款已到账，真实处理结果仍需对应记录。
