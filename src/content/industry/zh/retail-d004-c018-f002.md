# 区域经销商库存补货的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在区域经销商库存补货的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。经销补货的询问、预留和正式订单要在输入中保持不同对象。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

经销合同比对可拟询问“想看短袖基础款”、仓库备注“为展样预留”和订单页“长袖已确认”。当前问短袖是否已确认补货。实际输入需要保留短袖与长袖、展样与销售订单的区别；预留没有说明用于本轮供货。历史若一直聊长袖订单，问题里的这款也要重新定位。不能把材料缩成基础款有预留已确认，否则两个商品和两种用途会被混成不存在的单一确认。

## 配置怎么定

| 上下文材料核对 | 输入与表达条件 | 验收动作 |
| --- | --- | --- |
| 预留用途 | 展样 | 核输入未省。 |
| 商品区别 | 短袖与长袖 | 状态分别回指。 |
| 提问指代 | 这款需定位 | 比原题及优化题。 |
| 答复归属 | 确认只属长袖 | 保留短袖待核。 |
| 来源缺项 | 短袖无本轮订单 | 不由窗口补证。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

第一处是展样用途从预留备注中丢失，应核原句与实际请求，保留预留对象及用途，不直接归为真实库存可售。第二处是历史长袖被代入当前短袖，应对优化前后提问、历史指代及本轮商品，再用空历史同题比较。第三处是答复只列已确认而省掉它属于长袖，应逐项核商品与状态，回复需要足够表达未确认部分。三项分别查用途、指代和结论归属，不用更大窗口替代短袖订单依据。

## 怎么确认配好了

验收分别问短袖询问到了哪里、预留用于什么、订单确认哪款，保存实际输入与回答原句。token引用预算要核限定是否保留，不能以三个文件都返回就认定内容完整。模型上下文和回复长度分别按实际能力及任务核，短袖无确认时仍待补。本次文字测试不创建订单、不执行调拨，也不从预留或长袖成交推当前短袖供货与履约状态，实际结果需独立记录。
