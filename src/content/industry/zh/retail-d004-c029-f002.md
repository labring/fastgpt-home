# 售后维修与补寄的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在售后维修与补寄的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。补寄材料中的申请部件、备件说明和收件反馈需保留具体对象。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

维修补寄可拟申请“缺的是杯盖上的硅胶塞”、备件说明“盖体与塞分别登记”和顾客留言“说明文件已收”。历史曾有整只杯盖补寄完成。当前问硅胶塞是否已经寄到。输入需要保留塞与盖体分开的关系，以及收件针对说明文件；不能把整盖历史或文件收件接成当前配件到货。现有申请只说明请求对象，备件说明也不提供库存、发货或物流事实。

## 配置怎么定

| 上下文材料核对 | 输入与表达条件 | 验收动作 |
| --- | --- | --- |
| 部件粒度 | 硅胶塞非整盖 | 核实际输入。 |
| 历史补寄 | 整盖旧事项 | 不移用本次。 |
| 收件对象 | 说明文件 | 不当实物配件。 |
| 物流缺项 | 本次记录未给 | 答复明确待核。 |
| 新增记录 | 申请与部件对应 | 核身份再用。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

第一处是硅胶塞被摘要成整个杯盖，应核申请原句、部件关系与实际请求，恢复具体对象。第二处是历史整盖完成被代为本次塞已寄，应对申请、商品和部件身份，空历史同题比较输入。第三处是答复把文件已收写成配件已收，应核反馈动作对象与输出句，留足空间说明当前缺发货证据。三项分别查部件粒度、历史归属和收件对象，不由更多上下文补物流记录。

## 怎么确认配好了

验收分别问申请缺什么、备件怎样分列、留言收到了什么，保存实际输入及输出。引用token预算应保留塞与盖体区分和文件字样，不能以收件片段返回就推实物已到。实际模型窗口与回复长度分别核；若物流未给，增加预算仍无到货依据。新增自拟记录也须核本次部件和申请。本练习不生成补寄单、不调用仓库或承运系统，也不认定商品已恢复使用，实际结果需相应凭证。
