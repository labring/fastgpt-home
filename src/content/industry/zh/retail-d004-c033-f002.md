# 外汇收结汇与贸易名录的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

收结汇与贸易名录场景中，合同与交易材料比对围绕收汇水单、贸易合同、发票、外汇业务登记资料展开，核对主体、金额、币种、货物描述与登记状态是否一致。资料更新频率为每单与月，比对结论随单据逐笔形成。银行退单、外汇分类异常、资金无法入账是出错后的常见后果，因此比对需要保留可追溯的原文依据。

## 这些特征在「上下文与 token」这一环带来什么约束

模型单次请求可参考的内容长度由最大上下文决定，回复上限只约束输出长度，两者不能互相替代。知识库引用上限按 token 控制，单段材料较长时可能被裁剪，需结合问题样本核对引用内容是否完整。记忆轮数决定参考的历史轮数，相同问题在空历史与带历史下的输入不同，比对前应确认上下文差异。选择 json_schema 等固定回复格式时，需验证字段齐全与解析成功，仅检查文本长度不足以确认结构可用。

假设演练样本：材料原文为“境内 A 公司于 2026 年 3 月 10 日与境外 B 公司签订货物出口合同，合同号 HT-2026-0310，金额 120000 美元，结算方式为电汇。A 公司于 2026 年 3 月 18 日收到银行收汇水单，付款方为境外 C 公司，金额 120000 美元，附言注明对应合同 HT-2026-0310。”另一份材料为发票，载明买方为境外 B 公司，金额 120000 美元。待判定拟稿句为“收汇主体与合同签约主体一致，贸易背景已核实”。该拟稿句涉及主体一致性判断，水单付款方与合同签约方名称不同，需核对是否属于同一集团或代付安排。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较对象 |
| --- | --- | --- |
| AI 模型 | 选用支持长上下文的模型 | 与材料原文长度比较，确认单次请求可容纳合同与水单全文 |
| 记忆轮数 | 设为 2 轮 | 与单笔比对所需前文比较，避免带入无关历史 |
| 回复上限 | 设为中等长度 | 与拟稿句所需依据说明比较，保留主体、金额、状态字段 |
| 引用上限 | 按 token 设定中等值 | 与单段材料长度比较，核对水单与合同是否被完整引用 |
| 回复格式 | 选用 json_schema | 与下游字段解析需求比较，确认主体、金额、状态字段齐全 |
| 最低相关度 | 保持默认 | 与语义检索结果比较，观察低相关片段是否被过滤 |

## 容易做错的三处

1. 将回复上限当作完整上下文窗口，导致长合同被截断后仍按完整材料判断。检查方式：输入合同全文与水单全文，比较请求中实际包含的 token 与材料总 token，观察是否出现截断。
2. 在空历史与带历史两种输入下使用同一问题，未核对上下文差异即认定结论一致。检查方式：分别以空历史和带两轮历史提交同一比对问题，比较两次输入内容，观察结论是否因历史信息而变化。
3. 使用固定回复格式时仅检查文本长度，未验证字段齐全与解析成功。检查方式：提交拟稿句生成请求，比较返回结构中的主体、金额、状态字段，观察解析是否成功。

## 怎么确认配好了

1. 输入假设样本中的合同原文、水单原文与拟稿句，比较拟稿句所称“收汇主体与合同签约主体一致”与原文中付款方 C 公司、签约方 B 公司的名称，观察是否出现主体不一致的提示。若拟稿句直接断言一致，则未满足条件。
2. 输入同一组材料，将引用上限设为较小值后再次提交，比较两次返回的引用内容，观察水单附言中合同号是否仍被包含。若合同号缺失，说明引用被裁剪，需调整上限。
3. 输入空结果场景，以明确的纸面输入 `[]` 核对下游承接设计，比较下游节点在无引用内容时的输出，观察是否出现无依据的结论。若下游仍生成主体一致性判断，则承接设计需修正。

检索结果不承担权限或实体隔离功能，同一向量模型的要求仅适用于检索库内部关联，不扩展至外部系统。RRF 是混合结果融合过程，不作为独立开关。思考预算用于控制模型思考强度，与引用 token 上限无关。待审核状态不证明缺少操作权限，签署、合作达成与合同生效是三个不同事实，证据缺口应如实保留。
