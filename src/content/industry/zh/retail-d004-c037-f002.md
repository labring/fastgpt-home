# 大促仓配排产的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

大促仓配排产围绕短期峰值产能和人车场安排展开，主要数据来源包括历史大促订单、平台活动报名、WMS产能和快递揽收能力。这一品类每场大促、每日更新资料，日常要处理大促预测表、人员排班、快递保障方案和异常日报。合同与交易材料比对任务中，这些文档的字段口径差异直接影响比对结论：预测表里的单量区间、排班表里的临时人员到岗日期、快递保障方案里的车辆承诺数量，分属不同文档、不同字段，只有在同一主体、同一期间、同一字段下才能判断是否矛盾。数据更新频率为每场、每日，不由此推出批量同步或交易触发机制。

## 这些特征在「上下文与 token」这一环带来什么约束

比对任务需要把多份材料放入模型上下文进行字段级核对。模型单次请求可参考的内容长度由最大上下文决定，回复上限只限制输出长度，两者不能混用。知识库引用上限按 token 控制，单段材料过长时可能被裁剪，导致比对依据不完整。历史轮数设置会影响相同问题在不同对话历史下的输入差异。使用 json_schema 固定回复格式时，字段齐全和解析成功需要单独核对。

假设演练样本：材料A（大促预测表）原文为“本次大促期间，华东一号仓预计出库单量区间为每日八万至十万单，活动日期为十一月一日至十一月十一日。”材料B（人员排班）原文为“华东一号仓十一月一日至十一月十一日临时人员排班每日到岗一百二十人，其中分拣岗位八十人。”待判定拟稿句为“华东一号仓在本次大促期间每日出库单量不低于八万单，人员排班已覆盖该产能需求。”该拟稿句将预测区间下限表述为确定下限，并将排班与产能需求的匹配关系作为已确认事实。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| AI 模型 | 选用支持所需上下文长度的模型 | 按材料A、材料B及拟稿句总长度核对最大上下文，与模型显示值比较 |
| 回复上限 | 假设设为足够容纳依据与处理动作的长度 | 比较拟稿句输出是否被截断，确认依据字段完整 |
| 知识库引用上限 | 假设按 token 设置，覆盖两份材料关键段落 | 比较检索返回内容与原文，确认单段未被裁剪 |
| 记忆轮数 | 假设保留少量历史轮数 | 比较空历史与带历史下相同问题的输入差异 |
| 回复格式 | 需要固定字段时选用 json_schema | 核对字段齐全与解析成功，不只看文本长度 |
| 最低相关度 | 假设仅在语义检索或重排时生效 | 该值为过滤阈值，不承担权限或实体隔离 |

## 容易做错的三处

1. 将材料A的预测区间下限“八万至十万单”直接写成“不低于八万单”，把区间表述转为确定下限。检查时输入材料A原文与拟稿句，比较“八万至十万单”与“不低于八万单”的字段取值，观察拟稿句是否改变了原文的区间含义。
2. 将材料B的排班人数直接认定为已覆盖产能需求，把两份文档的独立字段合并为匹配结论。检查时输入材料B原文与拟稿句，比较排班人数与产能需求是否在同一文档、同一字段下建立对应关系，观察是否存在原文未载明的匹配依据。
3. 将知识库检索返回的引用内容当作授权或审批依据，忽略检索不承担权限过滤。检查时输入检索返回内容与拟稿句，比较检索结果是否包含授权状态字段，观察拟稿句是否把检索命中当作已获授权。

## 怎么确认配好了

1. 输入材料A原文、材料B原文和拟稿句，比较拟稿句对“八万至十万单”的表述是否与原文区间一致，观察拟稿句是否将区间下限改写为确定下限。满足条件为拟稿句保留区间表述或明确标注待核实。
2. 输入材料B原文和拟稿句，比较排班人数与产能需求是否在同一文档、同一字段下对应，观察是否存在原文未载明的匹配结论。满足条件为拟稿句不将排班人数直接认定为已覆盖产能需求。
3. 输入检索返回内容和拟稿句，比较检索结果是否包含授权状态字段，观察拟稿句是否将检索命中当作已获授权。满足条件为拟稿句不把检索或表单当作授权执行，授权状态缺失时保留为待核实。
