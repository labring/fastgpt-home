# 大卖场生鲜联营柜台的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

大卖场生鲜联营柜台常由供应商驻场经营并按销售分成，合同条款与每日交易材料因此必须逐项对照。日销售报表、损耗单、食品进货查验记录按日或按批产生，联营合同则约定分成比例、损耗承担与结算口径。合同与交易材料比对的核心动作，是把合同中的主体、期间、字段与交易材料中的对应值放在同一上下文中判断是否一致。上下文与 token 直接决定比对时能同时装入多少材料原文，以及模型能否看到判断所需的全部依据。

## 这些特征在「上下文与 token」这一环带来什么约束

比对需要同主体、同期间、同一字段。合同写明某供应商在某月的分成比例，报表给出该供应商该月的销售额，两者才可对照。上下文窗口不足时，材料被裁剪，判断可能只看半句。引用上限按 token 控制，单段材料过长会挤占其他材料的空间。回复上限只限制输出长度，与模型可用上下文不是同一数值。历史输入会改变同一问题在空历史与带历史下的输入内容，核对时须固定历史条件。

假设演练样本：供核对的合同原文为「甲方某某生鲜部与乙方某某水产供应商签订联营合同，期限为二〇二五年三月一日至二〇二六年二月二十八日，乙方柜台当月销售额按百分之十二计算分成，损耗由乙方承担百分之三十。」待判定的拟稿句为「该供应商二〇二五年三月损耗全部由门店承担。」比对输入为上述合同原文与一份标注同一供应商、同一月份的损耗单。判定关注主体、期间、字段三项是否一致，损耗承担比例属合同载明字段，拟稿句与合同取值互斥。

## 配置怎么定

| 配置或核对项 | 本页相关取值或动作 | 说明与比较方法 |
| --- | --- | --- |
| AI 模型最大上下文 | 按所选模型实际显示值 | 与合同原文加交易材料的合计长度比较，判断是否需分段 |
| 回复上限 | 本次假设试验起点设为能容纳判定理由与依据引用的长度 | 与拟稿句判定所需输出比较，过短会截断依据 |
| 引用上限 | 按 token 控制，本次假设起点取能覆盖合同关键条款与损耗单字段的值 | 与单段材料长度比较，观察关键条款是否被裁剪 |
| 最低相关度 | 仅在语义检索或结果重排时生效 | 与召回结果比较，过滤低相关片段，不承担权限过滤 |
| 问题优化 | 连续追问且问题含指代时开启 | 比较开启前后检索词，判断指代是否被消除 |
| 结构化承接 | 使用 json_schema 时核对字段齐全 | 检查主体、期间、字段三项是否返回并可解析 |

## 容易做错的三处

1. 把回复上限当作完整上下文窗口。错误表现：按回复上限估算可装入的材料长度，导致合同条款被裁剪。检查：读取模型显示的最大上下文，与合同原文加损耗单合计长度比较，观察关键条款是否完整进入输入。
2. 用语义相关度代替权限或实体隔离。错误表现：认为相似度设置会排除其他供应商的记录。检查：核对检索范围与记录标识，确认返回内容是否属于同一供应商、同一期间。
3. 把待审核状态当成已有操作权限。错误表现：依据一份待审核的交接请求判定损耗承担已变更。检查：比较请求状态字段与合同载明条款，观察是否存在已生效的变更依据。

## 怎么确认配好了

- 验证一：输入上述合同原文与标注同一供应商、同一月份的损耗单，比较合同载明的损耗承担比例与损耗单字段取值，若两者同字段取值互斥，则判定拟稿句未获合同支持。

- 验证二：在空历史与带历史两种条件下输入同一比对问题，比较两次实际送入模型的输入内容，若历史条件改变导致材料被裁剪，则记录上下文差异，不据此判定合同条款。

- 验证三：用明确的纸面输入空结果核对下游承接设计，比较下游节点在收到空引用时的输出，观察是否出现无依据的损耗承担结论；检索结果是否为空须以实际观察记录，不预设虚构规则必然返回空。

检索检查记录实际观察与失败分支，不保证首条命中或全部召回。跨不同向量模型的库不可共同关联，须先核对标识并排除不符合者，记录实际观察，不推断运行结果。
