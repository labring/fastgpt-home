# 客服咨询知识库维护的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在客服咨询知识库维护的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。核服务协议中的登记职责与承接决定方，检查当前条款是否完整进入比较输入。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

客服协议比对练习可拟本期条款“店铺负责转交维修诉求；是否承接由指定服务商另行回复”，知识说明稿只写可协助登记。历史对话谈另一家门店已经安排检修。比较当前协议与知识说明时，要先核本期完整条款、门店和服务商身份是否进入请求；若引用只保留负责转交，角色边界便缺了一半。登记、转交与承接是不同动作，不能由说明稿中协助登记推出店铺承诺维修，也不能把另一店的安排直接带进本事项。

## 配置怎么定

| 合同上下文核对 | 本题材料 | 实际检查 |
| --- | --- | --- |
| 职责条款 | 转交诉求与服务商另回 | 核请求保留完整角色边界。 |
| 说明稿用途 | 仅协助登记 | 不扩成承担维修。 |
| 历史门店 | 另一店已安排检修 | 固定当前输入查这家的指代。 |
| 责任对照表 | 登记、转交、承接决定方 | 解析后逐项核原句主语。 |
| 新增回复 | 服务商本事项答复 | 核身份再更新阶段。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

- 指定服务商另行回复从本次输入被裁去时，对照协议原文、实际引用及请求，定位决定方缺失，不先凭答复完整认定材料齐全。

- 追问“这家已经安排了吗”借用另一店历史时，固定当前条款比较空历史和带历史的输入，核门店与事项指代。

- 责任对照表可解析却把登记方写成维修承接方时，逐项回查条款主语；结构齐全不证明职责映射正确。

## 怎么确认配好了

验收分别问谁登记、谁转交、谁还需决定承接，追查实际输入与回答对应句。补入服务商本事项回复后，先核门店和事项，再看新增依据改变了哪项职责或阶段。引用上限按token检查，回复长度另核，模型上下文能力以实际配置和可接收范围为依据。缩短输出或增加窗口都不能补出未传入的服务条款。所用文本是自拟职责练习，不表示真实服务已经安排。
