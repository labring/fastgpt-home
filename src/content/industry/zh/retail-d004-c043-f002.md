# 平台多店铺矩阵管理的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在平台多店铺矩阵管理的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。检查多店协议的适用店铺与附件继受范围，防止旧店条款在追问中覆盖新店。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

多店协议练习可拟甲店补充条款“本附页仅适用甲店本次补货，乙店事项另议”，乙店拟稿只说沿用表格样式。历史讨论曾确认甲店另一笔交接。比较甲乙两店资料时，表格相同不代表条款内容承接；本次补货和历史交接也不是同一事项。应在实际请求中保留店铺、事项和仅适用限定，再看追问“这家也照办吗”指向哪里。不能让较早的甲店确认变成乙店本次已同意，或从格式复用补出合同适用范围。

## 配置怎么定

| 多店合同上下文 | 本题限定 | 实际核对 |
| --- | --- | --- |
| 店铺范围 | 仅甲店本次补货 | 请求内保留完整限定。 |
| 乙店拟稿 | 只沿用表格样式 | 不扩大为条款全承接。 |
| 历史事项 | 甲店另一笔交接 | 核这家与该次指代。 |
| 责任表 | 门店、事项、条款归属 | 解析后逐项回原文。 |
| 新增乙店附件 | 主体事项和版本 | 同追问检查适用范围。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

- 仅适用甲店本次补货被上下文裁成适用补货时，核完整附页、实际传入和输出对象，定位店铺事项限定丢失。

- 乙店追问沿用了甲店历史交接时，固定当前拟稿比较有无历史，核这家、该次等指代与原事项。

- 沿用表格样式被责任表写成沿用全部条款时，逐项核拟稿动词和附件引用，格式继受不能补内容承诺。

## 怎么确认配好了

验收分别问哪店、哪次、沿用的是格式还是具体约定，比较实际输入和对照表逐句依据。取得乙店正式附件后先核主体、事项和版本，再用同一追问检查新增范围，不从文件日期新就推整份替代。知识引用token预算与回复长度单独核，模型实际上下文范围也需有据。结构化输出先验解析，再查店铺和条款归属，资料之间的业务适用仍按其原文说明。

| --- | --- |
| 文档类型 | 店铺授权清单、价格管控表、窜货投诉单、月度销售报表 |
