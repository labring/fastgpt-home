# 平台店铺评价与体验分维护的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在平台店铺评价与体验分维护的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。对照评价维护委托中的回复草拟、发布确认与内部记录，保留店铺和评价对象。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

评价维护委托可自拟“受托方整理争议点并草拟回复；公开回复由店铺逐条确认”，另附内部归因便笺，未附发布确认单。对话前文讨论的是另一条物流评价，已经有店铺回复。当前条款若只截取草拟回复，就可能失去公开前的确认动作；便笺提出的可能原因也不能直接变成对消费者的事实陈述。比较的对象应是本条评价及其委托附件，不是整家店所有争议。材料不足时可列出待确认的句子，不必把未知写成过错已认定或评价已撤回。

## 配置怎么定

| 评价委托上下文 | 自拟材料限定 | 复核依据 |
| --- | --- | --- |
| 起草任务 | 只整理争议点并拟回复 | 不替代逐条发布确认。 |
| 公开确认 | 本条确认单尚缺 | 核输入保留确认前提。 |
| 前文评价 | 另一条物流评价 | 以评价标识隔开状态。 |
| 内部便笺 | 只列可能原因 | 保留不确定语气。 |
| 新增确认单 | 具体文字与版本 | 原题核授权范围改变。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

第一处是逐条确认的前提没有进入请求，应并列委托全文、引用片段和本次输入，核回复草稿是否被扩大为发布许可。第二处是前文物流评价的处理状态覆盖当前商品评价，应标明评价标识，比较空历史与带历史的同一问题，查状态串入的位置。第三处是内部便笺的猜测进入可公开回复字段，应逐句对照原文的可能语气和可用证据，解析成功后仍不能把猜测改成已查明。三项分别涉及授权范围、评价对象和陈述依据，核对记录不能相互替代。

## 怎么确认配好了

验收先问谁起草、谁确认、当前哪条评价有确认记录，再检查实际送达的条款与回答引用。补入本条确认单时，核被确认的具体文字及版本，仅有签名图片还不够。知识引用以token预算核是否保留必要前提，回复长度和模型实际上下文范围分别记录。缩短回答可能改变表达，却不会补齐公开许可；较长窗口也不能使另一条评价的历史记录自动适用于本条。此为自拟文书练习，不声明真实发布、撤评或体验分变化。
