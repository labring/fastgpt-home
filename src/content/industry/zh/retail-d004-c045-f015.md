# 平台店铺评价与体验分维护的合同与交易材料比对：知识库检索与召回

## 这个品类的数据长什么样
评价与体验分维护发生在售后履约之后，材料围绕差评处理记录、体验分明细、服务诊断报告、整改台账展开。这些资料按日或按周更新，常被客服主管与质检专员用于归因差评、联系补充凭证、跟踪整改后指标。合同与交易材料比对这一任务，要求把差评记录中的订单事实、售后处理状态与合同或交易材料逐字段核对，判断某条拟稿描述是否获得原文支持。检索环节因此承担的是定位可用原文的职责，检索结果本身不构成授权，也不代表合同已生效或整改已完成。

## 这些特征在「知识库检索与召回」这一环带来什么约束
知识库搜索节点可关联一个或多个使用相同向量模型的知识库；语义检索、全文检索与混合检索按测试问题分别比较，不预设一种模式适合全部资料。混合检索通过 RRF 融合多路结果，RRF 是融合过程，不是可开启的开关。引用上限以 token 为单位，最低相关度仅在语义检索或使用结果重排时生效。问题优化用于指代消除和问题扩展，会增加一次模型调用。图片检索需要图像输入及相应模型能力，重排需要具备模型并按设置启用。相似度得分不承担权限或实体隔离职责，跨不同向量模型的库不可共同关联，只能核对标识并排除不符合者。

假设演练样本：某店铺质检岗在2025年6月10日核对一条差评工单，订单号 A-20250601-017，买家于6月3日申请退货退款，售后状态记录为“退货已签收，退款处理中”。合同材料摘录原文：“本订单适用七日无理由退货，退货签收后三个工作日内完成退款审核。”待判定拟稿句：“该订单退款已于6月5日完成。”检索输入为上述两段原文，比较对象是拟稿句中的“已完成”与原文的“处理中”“完成退款审核”。原文未载明退款到账时间，该拟稿句属于未获支持，需记录证据缺口。

## 配置怎么定
| 配置项 | 本样本取值或核对项 | 依据与比较方法 |
| --- | --- | --- |
| 关联的知识库 | 仅关联同一向量模型的评价维护库 | 核对库的向量模型标识一致，排除不同模型库 |
| 搜索模式 | 先用全文检索查订单号，再用语义检索查状态描述 | 订单号属精确编号，状态描述属自然语言，分别比较命中情况 |
| 引用上限 | 本次假设试验起点为800 token | 因原文含合同条款与工单两段，用更长与更短资料比较内容是否完整 |
| 最低相关度 | 本次假设试验起点为0.3 | 先标注相关与无关样本，再比较过滤后是否保留条款原文 |
| 问题优化 | 本样本问题含明确订单号，暂不开启 | 比较原问题与优化后问题，核对主体是否被改错 |
| 结果重排 | 按实际具备的重排模型决定启用 | 重排得分可用于过滤，需与语义得分比较 |

## 容易做错的三处
1. 把检索命中当作退款已完成的证据。输入是拟稿句“退款已于6月5日完成”，比较对象是原文“退款处理中”与“完成退款审核”，观察结果是原文未载明到账时间，判定为未获支持。
2. 把最低相关度当作权限或实体过滤。输入是一条无关店铺的差评记录，比较对象是相关度阈值与记录归属，观察结果是阈值只影响排序与过滤，不排除未授权记录，需另行核对访问权。
3. 把不同向量模型的知识库共同关联。输入是两个向量模型标识不同的库，比较对象是节点关联要求，观察结果是标识不一致即排除，不执行跨模型检索来比较漏召回。

## 怎么确认配好了
1. 输入假设样本的订单号与合同原文，比较全文检索与语义检索的返回内容，观察是否同时定位到条款与工单两段原文；若只命中一段，记录缺口并调整引用上限。
2. 输入拟稿句“该订单退款已于6月5日完成”，比较其与原文“处理中”“完成退款审核”的字段取值，观察是否出现同主体、同期间、同字段的互斥取值；未载明到账时间时判定为待核实。
3. 输入明确纸面空结果[]，比较下游节点对引用长度为0的处理，观察输出链路是否走通；不声称虚构规则检索必然返回空数组。
