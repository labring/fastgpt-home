# 平台退款退货处理的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在平台退款退货处理的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。对照退货协作约定中的登记、核件与退款指令，保留包裹身份及各阶段证据。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

退货协作文本可自拟“客服登记申请，仓库核对退件后另给处理意见，退款按本单确认指令办理”，目前只有申请登记表与包裹送达提示，没有核件意见和确认指令。历史对话曾谈另一单已处理。比较委托与登记表时，登记、物流送达、核件、退款指令是不同动作，不能因出现退货二字就合成一条完成记录。包裹送达提示也未说明箱内商品情况。长对话整理需要保留本单标识及另给意见的前提，不以回复连贯代替阶段证据。

## 配置怎么定

| 退货约定上下文 | 已给或缺少材料 | 对应检查 |
| --- | --- | --- |
| 登记阶段 | 当前申请登记表 | 只支持登记动作。 |
| 物流阶段 | 包裹送达提示 | 不替代箱内核件。 |
| 仓库意见 | 当前尚缺 | 请求保留另给意见前提。 |
| 历史单据 | 另一单已处理 | 核订单与包裹标识。 |
| 退款执行 | 指令及执行记录均未给 | 阶段表保持待核。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

第一处是仓库核对后另给意见在请求中被裁去，应对全文、实际传入和阶段表，定位缺失前提，不能把送达改成核件完成。第二处是本单追问借用了另一单已处理的历史，应固定登记材料核两组历史输入，逐项追单据与包裹身份。第三处是可解析退款字段由申请表直接填成已执行，应查当前确认指令与实际执行记录是否存在，字段有值不创造资金动作。三项分别核阶段、对象与执行依据，不由任何单一状态补齐全过程。

## 怎么确认配好了

验收分别问已知哪一步、该步属于哪个包裹、尚缺哪份记录。后补仓库意见时只更新它能证明的核件情况，退款仍依对应指令及执行记录另核。知识引用token与输出长度分开检查，实际模型接受的上下文范围也需留据；增加预算不能生成未提供的仓库结论。此练习不规定退款条件、时限或金额，也不宣称真实款项进出，输出只给自拟材料之间的对应关系和待核阶段。
