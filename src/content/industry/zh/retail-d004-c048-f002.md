# 快递面单与揽收交接的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在快递面单与揽收交接的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。保留揽收协作附页对清单、实物交接与异常记录的不同用途，不让面单生成代替揽收。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

揽收协作练习可拟附页“面单清单供预排，实物数量以双方交接页核对；异常包件另列”，附件仅有已制面单列表及一段司机到场留言，没有双方交接页。历史谈话中昨天另一批已完成交接。本题要比对清单和协作附页，先确认附页后半句与异常范围进入上下文。面单生成、司机到场与实物移交各有证据，清单行数不能直接当作实交数量；本例不给实际件数，也不判断运输责任或签收效力。

## 配置怎么定

| 揽收附页上下文 | 材料用途 | 验收动作 |
| --- | --- | --- |
| 面单列表 | 仅用于预排 | 不把行数当实交件数。 |
| 到场留言 | 只说明司机到场 | 不扩为接件完成。 |
| 双方交接页 | 本例未附 | 引用保留核对条件。 |
| 历史批次 | 昨天另一批 | 用批次标识查指代。 |
| 异常包件 | 需另列对应项 | 解析后保留待核分组。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

第一处是以双方交接页核对的条件从引用中被删去，应逐段核附页原文和实际输入，查预排清单是否被升级为实交依据。第二处是今天这批的追问沿用昨天另一批状态，应以批次标识固定当前清单比较历史，查到场、接件和交接各自指向。第三处是异常另列的包件被结构化合进正常交接，应对异常记录、清单对应项与输出分组，解析后核是否丢失待核身份。三个核法分别找前提、批次和分组，不能只看总表齐整。

## 怎么确认配好了

验收先列哪些材料证明制单、哪些只说明到场、哪些能说明该批实物交接。补入交接页后，核双方记录对象及异常对应关系，再重复本批问题；不由补件时间替换原事件时间。知识引用预算检查必要条款是否送达，回复长度和模型窗口另记。较大的上下文能够容纳的实际内容仍需从请求确认，不凭界面显示的额度判断已送齐；没有交接页时，实交情况保持未知，也不能补成未交接。
