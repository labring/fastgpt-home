# 投诉举报与监管回复的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在投诉举报与监管回复的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。将回复代拟委托、事实附件和受理通知分开比对，检查摘录是否保留核实责任及投诉对象。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

投诉回复练习可自拟委托“受托方依据已核事实代拟说明，事实确认仍由门店负责”，附件仅有投诉人的叙述与受理通知，尚缺门店核实记录。历史谈话曾讨论另一位投诉人的处理结果。本题比较委托和拟议回复，受理说明收到事项，不等于确认投诉全部属实；投诉人陈述也是需要按其身份引用的材料。上下文中必须保留已核事实这一前提和门店确认角色，不能把代拟职责扩大为调查结论。此例不引用真实监管程序、责任划分或办理时限。

## 配置怎么定

| 回复委托上下文 | 材料身份 | 逐项核法 |
| --- | --- | --- |
| 代拟前提 | 只依已核事实 | 检查实际请求保留前提。 |
| 投诉叙述 | 投诉人的单方陈述 | 不能改称已查明。 |
| 受理通知 | 只说明事项收到 | 回读通知动作。 |
| 历史事项 | 另一投诉处理结果 | 以受理标识核指代。 |
| 新增核实 | 门店对应事实记录 | 只更新覆盖事实。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

第一处是依据已核事实从实际输入中被裁掉，应对完整委托、摘录和请求，查未经核实的叙述为何被当成确定事实。第二处是当前投诉的追问复用了另一事项处理结果，应固定受理标识及投诉对象比较历史输入，不以相同门店归并事件。第三处是受理通知在结构化对照中被填成事实认定材料，应回读通知原文动作与回复引用；表格解析通过仍不能改变材料用途。三项分别核陈述前提、事项身份和通知性质。

## 怎么确认配好了

验收分别问谁陈述、谁核实、哪份材料只证明受理，并查每条回复采用了什么来源。补入门店核实记录后，核对应投诉及覆盖事实，再重复问题；尚未核实的部分保留待核。检查知识引用token预算是否保留关键限定，回复长度与实际模型上下文范围另核。扩大窗口不能把陈述变成核实，也不能补出正式认定。自拟文本只演示材料边界，未提交回复、联系投诉人或宣称真实事项办结。
