# 投诉举报与监管回复的合同与交易材料比对：文档解析与分块

## 这个品类的数据长什么样
投诉举报与监管回复面向平台或监管机关，材料需要正式证据与整改文字，来源包括12315平台、平台投诉中心、客服聊天与订单系统。日常文档为投诉工单、监管询问函、订单证据与整改报告。该品类数据更新不定期、每案发生，材料围绕单个案件聚合。合同与交易材料比对的核心，是把订单、聊天、工单、询问函中的同一事实按主体、时间、字段对齐。文档解析与分块决定这些材料能否被检索到：分段若把条件与所约束内容拆开，比对时容易把不同阶段的表述当成同一事实。典型从业主体为客服主管、法务合规与店铺负责人，出错后果包括行政调查、平台处罚与品牌舆情。

## 这些特征在「文档解析与分块」这一环带来什么约束
FastGPT 中知识库由库、集合和数据组成，最小搜索单位是库，集合仅作分类管理。MongoDB 的 dataset.datas 表存储向量原数据，indexes 字段记录对应向量 ID，一组数据可对应多个向量。PostgresSQL 的 vector 字段存储向量，索引为 HNSW，检索时先召回向量，再按向量 ID 去 MongoDB 寻找原数据，同一组原数据合并，向量得分取最高得分。分段应按材料自身结构切分，保留能回指原文的文档身份与版本，避免条件、说明与所约束内容被拆离。语义检索依赖向量相似度，全文检索适合编号、型号、专有名词，混合检索通过 RRF 融合。最低相关度仅在语义检索或使用结果重排时生效，是过滤阈值，不承担权限或实体隔离。引用上限以 tokens 计，不采用 top k。检索结果不构成授权，表单收集值，业务核验、审批、数据库写入与外部同步需要各自的下游实现。

## 配置怎么定
以下围绕假设演练样本列出与本页功能相关的设置或核对项。样本：某店铺收到投诉工单，投诉人称订单 A 在2025年3月10日签收后未收到发票；客服聊天记录显示2025年3月12日客服答复“发票将于3月15日前寄出”；订单系统显示该订单开票状态为“未开票”。待判定拟稿句：“本店已于2025年3月15日前完成发票寄出。”该句与聊天记录中的承诺日期同字段，但订单系统状态字段与拟稿句所述完成事实不一致，需按同一主体、同一期间、同一字段核对。

| 配置或核对项 | 本页相关取值或做法 | 依据与比较方法 |
| --- | --- | --- |
| 搜索模式 | 编号、订单号类查询用全文检索或混合检索 | 官方说明全文检索适合编号、型号、专有名词 |
| 最低相关度 | 本次假设试验起点设为0.3，与0.5比较观察召回变化 | 该值仅在语义检索或结果重排时生效，起点为假设，非默认值 |
| 引用上限 | 本次假设试验起点设为2000 tokens，与4000比较 | 官方以 tokens 控制引用上限，起点为假设 |
| 分段核对 | 按工单、聊天、订单三段分别保留原文与版本 | 官方说明分段应保持结构与语义完整 |
| 索引核对 | 确认入库后 indexes 是否生成对应向量 ID | 官方说明一组数据可对应多个向量 |
| 更新后复核 | 资料变更后核对实际训练与索引状态 | 上传成功不等同于检索已更新 |

## 容易做错的三处
1. 把聊天记录中的承诺日期当作寄出完成事实。输入为“发票将于3月15日前寄出”，比较对象是拟稿句“已于3月15日前完成发票寄出”，两者字段不同，前者是承诺，后者是完成状态，不能等同。
2. 把最低相关度当作权限或实体过滤。输入为一次语义检索请求，比较对象是返回结果是否只含本店铺记录，相关度分数不识别主体归属，越权记录不会被该阈值排除。
3. 把上传成功当作检索已更新。输入为资料变更后立即检索，比较对象是实际索引状态，需核对训练与索引是否完成，未完成时检索结果可能仍为旧分段。

## 怎么确认配好了
1. 使用假设样本原文核对分段。输入工单原文、聊天原文与订单状态原文，比较拟稿句是否与原文同主体、同期间、同字段。若订单系统状态字段为“未开票”，而拟稿句称已完成寄出，则该句未获支持，应记录证据缺口，不判定为冲突。
2. 使用编号与自然语言分别检索。输入订单号与“发票寄出时间”两类查询，比较返回分段是否覆盖工单、聊天与订单三段。若编号查询未命中订单段，检查是否使用全文检索或混合检索；若自然语言查询未命中聊天段，检查分段是否把承诺句与上下文拆离。空结果可用明确的纸面输入[]核对下游设计，不声称某规则必然返回[]。
3. 变更后复核索引状态。输入变更后的资料与同一查询，比较变更前后返回分段是否一致。若仍返回旧分段，记录实际观察，核对训练与索引状态，不推断自动同步已完成。跨不同向量模型的库不可共同关联，先核标识并排除不符合者，不执行跨模型检索来比较漏召回。
