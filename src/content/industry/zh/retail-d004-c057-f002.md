# 生鲜临期折价处理的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在生鲜临期折价处理的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。核临期处理协作文字中的候选清单、折价建议与批准范围，保留批次和检查阶段。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

临期处理练习可拟协作说明“列出待检批次并提出折价建议，实际处理依本批批准页；未经核查项单列”，附件只有候选清单和建议便笺，没有批准页及当前实物检查记录。历史中另一批曾获处理意见。本题比较说明与清单，候选不等于已检结论，提出建议也不代表已调整售价或处置商品。需要在实际请求保留本批批准和未经核查的条件，不能因为标题写临期就推所有列项具有相同状态。这里不给真实食品标准、期限或折价数值。

## 配置怎么定

| 临期处理上下文 | 当前文本限制 | 对应核查 |
| --- | --- | --- |
| 候选清单 | 含待检项目 | 不当已检结果。 |
| 建议便笺 | 只提出折价建议 | 不充作已执行记录。 |
| 本批批准 | 当前尚缺 | 核批次商品及范围。 |
| 历史意见 | 另一批事项 | 不直接套用本批。 |
| 未核项目 | 需要单列 | 请求及输出保留分组。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

第一处是未经核查项单列的要求从输入丢失，应对完整说明、候选分组和引用，查待检项目为何进入可处理组。第二处是这批能按旧意见办吗借用另一批历史，应固定本批标识比较历史条件，核意见针对的商品及检查范围。第三处是折价建议在结构化表中被标为已执行，应核建议动作、批准页及实际操作记录，解析成功不改变执行阶段。三项分别核待检分组、批次适用和动作完成情况，不以表格有价格栏代批准。

## 怎么确认配好了

验收分别问列出的是何种候选、哪份批准覆盖本批、当前材料能说明哪个操作阶段，逐项读实际输入。补入批准页后核对应商品和范围，它支持批准内容，真实执行与实物情况仍需相应记录。引用token预算、回复长度与模型窗口分开检查，不让更长回答代替来源送达证据。此自拟练习不判商品可售、不改变价格或销毁库存，未有批准页也不能证明从未获准，仍需保留未知并指出对应材料。
