# 生鲜供应商索赔的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

在生鲜供应商索赔的合同与交易材料比对中，本页说明FastGPT的上下文与 token如何衔接资料。分开比对供应商异议通知、待议原因和数量附件，检查索赔草稿是否越过原件支持范围。所用场景为自拟文字测试。

## 这些特征在「上下文与 token」这一环带来什么约束

供应商索赔材料可自拟协作条款“代整理异议项目，原因与责任依双方对应记录另核，附件数量暂供核对”，当前仅有到货异议通知和数量摘录，没有双方确认原因或本批核定记录。历史谈话涉及另一批已接受异议。比较条款与草稿时，提出异议、核数量、确定原因和责任不是同一步；数量摘录的用途也不能直接变成真实损失。请求须保留另核及暂供核对，不能将材料齐整误写成对方已认可。本例不给索赔金额或真实责任结论。

## 配置怎么定

| 索赔草稿上下文 | 自拟材料用途 | 实际核对 |
| --- | --- | --- |
| 异议通知 | 只提出到货异议 | 不等同对方认可。 |
| 数量摘录 | 暂供核对 | 不扩成核定损失。 |
| 待议原因 | 双方记录尚缺 | 保留另核阶段。 |
| 历史回复 | 另一批已接受 | 核本批对应对象。 |
| 新增双方确认 | 明确覆盖的项目 | 其余仍标待核。 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `模型上下文` | 以实际模型可接收范围为准。 |
| `回复长度` | 回复上限不同于上下文窗口。 |
| `知识库引用上限` | 知识引用上限按token计。 |
| `历史输入核对` | 比较空历史与带历史的输入。 |
| `结构化承接` | 先验解析，再核字段事实依据。 |

## 容易做错的三处

第一处是附件数量暂供核对从引用中被裁去，应对条款、完整附件及实际请求，查摘录数字为何被扩大为核定损失。第二处是本批认可了吗借用另一批已接受异议的历史，应固定到货和批次标识比较历史，追对方回复的适用对象。第三处是待议原因在结构化草稿中填成责任确定，应回读双方记录与原因措辞，解析后核哪些只是主张、哪些确有对应确认。三项分别核数量用途、批次指代与因果归责依据。

## 怎么确认配好了

验收分别问异议提出了什么、数量附件能支持什么、原因责任尚缺哪份对应记录，逐句查输入与草稿。新增双方确认时，核覆盖批次及确认项目，只更新明确部分；没有确认的项目继续待核。检查引用token预算是否保留附件用途，回复长度与模型实际上下文范围另记，不用草稿生成成功证明争议办结。此为自拟文书核对，不发送索赔、不认定损失或操作资金，材料缺失也不证明供应商拒绝承担责任。
