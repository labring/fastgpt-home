# 生鲜称重分拣的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样
生鲜称重分拣发生在仓内履约环节，核心是重量与规格，主要材料来自分拣任务单、称重标签、少称补偿单与质检记录。这些材料的更新频率为每单与日，比对时需把同一订单的称重数值、规格描述与补偿状态放在同一上下文里核对。合同与交易材料比对任务要求模型同时读取多份短材料，上下文长度直接影响能否完整纳入任务单、标签与补偿单的对应字段。回复上限控制单次输出长度，知识库引用上限按 token 控制每次搜索最多引用的内容，两者共同决定比对结论能否保留足够的依据与处理动作。

## 这些特征在「上下文与 token」这一环带来什么约束
材料短小但份数多，若引用上限过低，单段材料可能被裁剪，导致主体或状态缺失。历史输入会影响同一问题在空历史与带历史下的检索结果，需分别核对。结构化承接要求字段齐全，仅检查文本长度无法确认解析成功。语义召回与相关度得分不承担权限或实体隔离职责，检索库同向量模型的要求不能扩展为外部系统也要同模型。RRF 是混合结果融合过程，不是可开启的开关。thinking budget 是思考预算，不能移作引用 token 上限。

假设演练样本：供核对的材料原文为“分拣任务单 A-0715 载明订单甲、规格 500g±20g、数量 2 件、分拣员乙、日期 2025-07-15。称重标签 A-0715-1 载明实际重量 486g、贴标时间 2025-07-15 09:12。少称补偿单 A-0715-C 载明订单甲、补偿数量 1 件、状态待审核、提交时间 2025-07-15 10:00。”待判定的拟稿句为“订单甲已完成少称补偿，补偿单已生效。”该句把待审核状态写成已生效，属于未获支持的判定。

## 配置怎么定
| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 引用上限 | 假设起点 2000 tokens | 材料总长约 150 字，2000 tokens 足以容纳三份材料；与材料实际 token 数比较，观察是否出现裁剪 |
| 最低相关度 | 假设起点 0.3 | 用于过滤低相关片段；与返回片段的得分比较，观察无关片段是否被排除 |
| 回复上限 | 假设起点 500 tokens | 需容纳依据与处理动作；与拟稿句加依据的实际长度比较 |
| 记忆轮数 | 假设起点 2 轮 | 比对任务通常单轮，保留少量历史用于核对连续追问；与空历史结果比较 |
| 回复格式 | json_schema | 需固定字段承接比对结论；解析后检查字段是否齐全 |
| 问题优化 | 开启 | 材料名称含编号，优化后可补全指代；与关闭时检索结果比较 |

以上数值均为本次假设试验起点，不来自官方默认值。引用上限按文档说明以 token 为单位，不采用 top k。图片检索须有图像输入及模型能力，重排须具备模型且按设置启用，文档总流程图列出的可选路径不代表每次请求全部执行。

## 容易做错的三处
1. 把待审核状态写成已生效。输入为少称补偿单 A-0715-C 的状态字段“待审核”，比较对象为拟稿句“已完成少称补偿，补偿单已生效”，观察结果为状态字段与拟稿句不一致，判定为未获支持。
2. 把回复上限当作完整上下文窗口。输入为模型的最大上下文说明，比较对象为回复上限设置值，观察结果为两者数值不同，判定为混淆。
3. 用相关度得分排除无关业务。输入为最低相关度设置，比较对象为返回片段的业务归属，观察结果为得分不承担权限过滤，判定为错误归因。

## 怎么确认配好了
1. 输入假设样本中的三份材料原文与拟稿句，比较拟稿句中的补偿状态与少称补偿单 A-0715-C 的状态字段，观察结果为拟稿句被标记为未获支持，满足条件。
2. 输入同一问题在空历史与带 2 轮历史下的请求，比较两次检索返回的引用内容，观察结果为引用内容存在差异，需记录差异并核对上下文影响。
3. 输入明确的纸面空结果 `[]` 与下游承接设计，比较下游是否按空结果处理，观察结果为下游未把空结果当作有内容处理，满足条件。跨不同向量模型的库不可共同关联，只核标识并排除不符者，记录实际观察。
