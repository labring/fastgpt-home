# 跨境平台结算与汇兑的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样
跨境平台结算与汇兑处理已成交订单的资金归集，材料包括平台结算单、汇率表、服务费发票、收款对账表，更新频率为周或月。合同与交易材料比对要求把结算单、发票、对账表放在同一上下文内核对主体、期间与字段。单份结算单常含多笔订单扣费，逐段长度差异大，引用上限按 token 控制，长段落可能被裁剪，比对依据随之缺失。

## 这些特征在「上下文与 token」这一环带来什么约束
上下文窗口按实际模型能力核对，回复上限不构成完整上下文窗口。知识库引用上限以 token 计，需结合单段长度与问题样本核对内容是否被裁剪。语义检索与重排得分只反映相关度，不承担权限或实体隔离，检索本身不构成授权。同一向量模型的库才可共同关联，跨模型先核标识并排除不符合者，不执行跨模型检索来比较漏召回。RRF 是混合结果的融合过程，不是可开启的开关。

## 配置怎么定
假设演练样本：材料原文为“甲方海岳供应链有限公司与乙方星洲支付服务有限公司于 2025 年 3 月 1 日签署《跨境结算服务协议》，约定 2025 年 3 月结算周期服务费按每笔 0.8% 计收，协议自双方签署之日起生效。”待判定拟稿句为“双方合作已达成，服务费自 3 月起按 0.8% 执行。”该句把签署与生效混为合作达成，且未核对结算单实际扣费字段。

| 配置项 | 本页取值或核对动作 | 依据与比较方法 |
| --- | --- | --- |
| 引用上限 | 本次假设试验起点 3000 tokens | 与结算单单段长度比较，观察是否裁剪 |
| 最低相关度 | 本次假设试验起点 0.5 | 与重排得分比较，观察低分是否被过滤 |
| 回复上限 | 保留足以表达依据与处理动作 | 与拟稿句完整度比较，观察是否截断 |
| 记忆轮数 | 保留少量历史轮数 | 比较空历史与带历史下同一问题的输入 |
| 回复格式 | 需要固定字段时选 json_schema | 验证字段齐全与解析成功，不只看长度 |
| 思考强度 | 按问题复杂度选择档位 | 思考预算为推理预算，与引用 token 上限无关 |

## 容易做错的三处
1. 把回复上限当作完整上下文窗口。输入为拟稿句与材料原文，比较模型最大上下文与回复上限两个字段，观察是否把回复长度误当上下文容量。
2. 用相关度得分代替权限判断。输入为检索结果与得分，比较得分与授权状态，观察是否把高分结果直接当作可执行依据。
3. 把签署当作合作达成或合同生效。输入为材料原文中的签署日期与生效条款，比较三个事实，观察拟稿句是否在缺证据时给出确定结论。

## 怎么确认配好了
1. 输入材料原文与拟稿句，比较“签署”“生效”“合作达成”三个字段，拟稿句须改为与原文一致的表述，或标注待核实，才满足条件。
2. 输入同一问题在空历史与带历史下的请求，比较两次输入内容，引用内容与拟稿句结论一致且未引入历史中不存在的授权，才满足条件。
3. 输入纸面空结果 []，核对下游承接设计是否按空引用处理；检索是否返回空结果不做保证，只记录实际观察。待审核状态不证明缺少操作权限，缺失证据保留为缺口。
