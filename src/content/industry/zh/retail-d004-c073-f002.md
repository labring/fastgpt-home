# 跨境独立站支付风控的合同与交易材料比对：上下文与 token

## 这个品类的数据长什么样

支付风控围绕卡组织争议和收款账户展开，处理对象包含支付拒付通知、欺诈订单清单、发票、物流签收证明。这些材料由 Stripe 或 PayPal 后台、Shopify 订单、承运商签收记录、客服邮件汇入，更新频率为日或每单。合同与交易材料比对需要把发票、订单、签收证明放到同一上下文中核对主体、金额、时间与状态。材料分散在不同系统，同一字段的取值可能来自多个来源，比对时须先确认字段来源与版本。

## 这些特征在「上下文与 token」这一环带来什么约束

上下文窗口由所选模型决定，回复上限只约束输出长度，不能当作完整上下文容量。知识库引用上限按 token 控制，单段材料较长时可能被裁剪，核对前应确认关键字段是否落在引用范围内。历史轮数影响连续追问的输入内容，同一问题在空历史与带历史下输入不同，比对结论可能因此变化。使用固定回复格式时，字段齐全与解析成功需要单独验证。

假设演练样本：某独立站商家收到一笔拒付通知，拟核对发票与签收证明。材料原文为“发票号 INV-2024-0871，开票日期 2024 年 3 月 12 日，金额 428.00 美元，买方 A 公司，订单号 SO-2024-0455。”签收证明原文为“承运商签收记录：订单号 SO-2024-0455，签收日期 2024 年 3 月 18 日，签收人 B 公司仓库。”待判定拟稿句为“发票与签收证明指向同一订单，交付已完成。”该句涉及订单号一致、签收事实，但发票买方与签收人不一致，交付是否完成未获支持。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 模型上下文 | 按所选模型显示的最大上下文核对 | 与材料总 token 比较，确认关键字段未被截断 |
| 回复上限 | 保留足以写出依据与处理动作的长度 | 与拟稿句所需字段数比较，过短会截断依据 |
| 知识库引用上限 | 按 token 设定，覆盖单段材料关键字段 | 与单段材料 token 比较，观察字段是否被裁剪 |
| 记忆轮数 | 保留少量历史轮数 | 与空历史输入比较，确认追问是否改变比对结果 |
| 回复格式 | 需要固定字段时选择 json_schema | 检查字段齐全与解析成功，不只看文本长度 |
| 最低相关度 | 按语义检索或重排生效时设定 | 与召回结果比较，过滤低相关片段 |

## 容易做错的三处

1. 把回复上限当作完整上下文窗口，导致长材料被截断后仍按完整材料比对。检查方式：输入同一材料，比较回复上限调整前后的引用内容，观察关键字段是否仍在。
2. 把检索命中当作授权或业务确认，认为召回发票即代表交付完成。检查方式：核对签收证明是否载明交付状态，未载明时记录为待核实。
3. 把不同主体字段当作同一字段矛盾，例如发票买方与签收人不一致直接判为冲突。检查方式：确认两字段是否指向同一主体，主体不同时记录为未获支持。

## 怎么确认配好了

1. 输入上述假设样本，比较发票与签收证明中的订单号，两者一致时满足订单号核对条件；买方与签收人不一致时，拟稿句“交付已完成”未获支持，应记录为待核实。
2. 输入同一问题在空历史与带历史两种上下文，比较输入内容差异，确认历史轮数设置是否改变比对结论；若结论不同，说明历史输入影响核对，需明确以哪一版为准。
3. 使用 json_schema 时，输入拟稿句，检查返回字段是否包含订单号、金额、签收状态；字段缺失时解析失败，不能仅凭文本长度判断格式正确。
