# 仅退款争议处理的库存采购与供应商资料：定时任务与自动化

## 这个品类的数据长什么样

仅退款争议常没有退件入仓，证据重点是发货签收与商品价值。库存采购与供应商资料在此承担两件事：证明争议商品确实由某供应商供货并已出库，以及把供应商侧的采购凭证、出库记录与平台售后单对应起来。这一品类的主要数据来源包括平台售后后台、承运商轨迹、客服聊天和仓库出库记录，日常要处理的文档是仅退款申请、发货凭证、签收证明和申诉材料。定时任务与自动化在此的用途是把这些材料的读取、请求与核对按固定节奏组织起来，减少人工逐单翻找。

## 这些特征在「定时任务与自动化」这一环带来什么约束

触发责任需要明确：由应用定时能力触发，还是由外部调度触发，须按实际版本核对可用入口。外部数据由已配置接口读取，定时触发本身不建立业务系统连接。HTTP 请求的方法、请求头、请求体与变量输入按外部接口文档核对。去重、幂等与业务写入需在接口或后续流程明确设计。执行记录要核对触发时间、真实输入、返回结果与业务状态，任务存在不等于执行成功。

假设演练样本：某供应商资料页记录“供应商编号 S-1042，供货商品 A 型保温杯，出库日期 2024 年 3 月 12 日，出库数量 200 件，对应平台售后单号 R-7781，出库单状态为已出库”。另有一份仅退款申请写明“买家主张未收到货，申请仅退款”。拟提交的交接请求为“请定时任务自动把该供应商的采购合同推送给平台申诉”。该请求中的采购合同未在样本材料中出现，授权状态也未载明。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 核对方式 |
| --- | --- | --- |
| 触发方式 | 外部调度按日触发 | 与实际版本可用入口核对，确认由谁发起 |
| 请求方法 | POST | 按外部接口文档核对方法、请求头与请求体 |
| 请求体字段 | 引用供应商编号与售后单号 | 按 {{key}} 引用规则核对变量来源 |
| 返回值提取 | 提取出库单状态字段 | 按 JSON path 语法核对提取结果 |
| 去重与幂等 | 以售后单号为业务键 | 在接口或后续流程核对是否已设计 |
| 执行记录 | 记录触发时间、输入、返回结果 | 与业务状态逐项比对 |

上述数值为本次假设试验起点，选取理由是样本中已给出供应商编号与售后单号，可与返回值提取结果对照。

## 容易做错的三处

1. 把定时触发当成已建立业务系统连接。样本中出库单状态为已出库，触发任务读取该字段，读取成功不表示采购合同已存在或已获授权推送。
2. 把拟提交的交接请求当成已执行。样本请求提到推送采购合同，材料中该合同未出现，授权状态未载明，该请求处于待核实状态。
3. 用返回值提取结果替代业务判断。提取到出库单状态字段，只说明接口返回了该值，不说明该供应商与售后单的对应关系已获确认。

## 怎么确认配好了

1. 输入样本中的供应商编号 S-1042 与售后单号 R-7781，比较请求体引用结果与样本记录是否一致，一致时满足条件。
2. 输入样本中的出库单状态字段，比较返回值提取结果与样本“已出库”是否相同，相同且可追溯时满足条件。
3. 输入拟提交的交接请求，比较请求内容与样本材料，若采购合同与授权状态均未在材料中出现，则记录为未获支持，不得判定为已授权或已执行。
