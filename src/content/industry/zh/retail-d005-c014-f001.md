# 便利店鲜食订货的库存采购与供应商资料：HTTP 接口与外部系统

## 这个品类的数据长什么样

便利店鲜食订货由门店按短保质期高频订货，数据来源包括 POS 销售、总部订货系统、门店库存和冷链温控记录。日常文档是鲜食订货单、报损单、临期处理表和温度记录。这些资料按日或按班次更新。本页处理的环节是库存采购与供应商资料，通过 HTTP 模块对接外部系统。订货单与报损单的字段取值决定请求体内容，供应商资料决定请求发往哪个地址。若接口把过期或临期数量写错，后续补货判断会偏差。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向指定地址发送请求，Params 用于路径参数，Body 用于请求体，Headers 用于请求头。三类数据均可用 `{{}}` 引用变量，变量来自全局变量、系统变量和前方节点输出。地址也可引用变量。返回值配置不表示接口返回值本身，而是按 JSON path 提取响应值。出参类型选字符串时，对应 key 的值转为 json 字符串输出。

系统变量中，chatId 与 responseChatItemId 在测试模式下不存在，调试时取到空值属于环境差异，不能当作业务故障。appId 为应用 ID。对话接口推荐在请求体传 body.appId，鉴权使用 APIKey。传入的 model、temperature 由编排决定，API 参数不改变它们。

假设演练样本：某便利店区域督导在纸面核对一份鲜食订货单，原文为「门店 A，2025 年 3 月 10 日，鲜食订货单编号 XD-0310，饭团 120 个，三明治 80 份，状态：待审核」。拟判定句为「该订货单已通过审核，可向供应商系统提交采购请求」。核对时比较单据状态字段与「待审核」这一取值，并确认 HTTP 请求的 Body 中订货数量是否与原文一致。待审核不表示审核通过，提交动作需要另行确认。

## 配置怎么定

| 配置项 | 设置方式 | 核对要点 |
| --- | --- | --- |
| 请求地址 | 按外部接口文档填写，可引用变量 | 与供应商系统提供的地址一致 |
| 请求方法 | 按外部接口文档选择 | 与接口契约要求的方法一致 |
| Headers | 填写 Authorization 等键值 | 鉴权凭证通过安全配置注入 |
| Body | 仅在对应请求类型下使用 | JSON 结构与订货单字段对应 |
| 返回值提取 | 配置 key 按 JSON path 提取 | 提取字段与响应结构对应 |
| 变量引用 | 引用全局变量、系统变量或前方节点输出 | 逐项核对实际传入值 |

本次假设试验起点：在 Body 中引用订货单数量变量，取值为 120。选择该值的原因是样本原文写明饭团 120 个，用于与响应中回显数量比较。该值属于本次纸面核对起点，不是官方默认值。

## 容易做错的三处

1. 把测试模式下的空 chatId 当成会话丢失。系统变量 chatId 在测试模式下不存在，输入为测试模式请求，比较 chatId 取值与「不存在」这一文档说明，观察结果为测试模式下该字段为空，属于环境差异。
2. 把待审核状态当作审核通过。输入为样本原文状态「待审核」，比较拟判定句中的「已通过审核」，观察结果为两者取值不同，拟判定句未获支持。
3. 把返回值提取配置当作接口返回值。输入为配置的 key 与 JSON path，比较响应结构与提取结果，观察结果为提取值来自响应，配置本身不产生接口返回值。

## 怎么确认配好了

1. 输入样本原文中的订货数量 120 与 Body 中引用的变量值，比较两者是否一致，观察结果为数值相同则引用正确。
2. 输入样本原文状态「待审核」与拟判定句「已通过审核」，比较状态取值，观察结果为取值不同则拟判定句待核实。
3. 输入测试模式请求与正式请求，比较 chatId 字段是否存在，观察结果为测试模式下不存在、正式请求下存在，据此区分环境差异与业务故障。
