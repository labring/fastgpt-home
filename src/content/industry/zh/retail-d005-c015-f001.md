# 信用证审单交单的库存采购与供应商资料：HTTP 接口与外部系统

## 这个品类的数据长什么样

信用证审单交单服务于银行付款条件，审核重点落在单证一致。库存采购与供应商资料这一任务里，需要比对采购合同、供应商发票、装箱单与信用证条款之间的对应关系，本页以这些单证为核对底本。主要数据来源包括开证行通知、UCP600 条款、货代提单与银行交单记录，日常处理的文档为信用证、商业发票、提单、保险单、汇票。数据按每单更新，单证员、银行国际结算岗位与出口商共同参与。

这些材料进入 HTTP 接口环节时，通常需要从外部采购系统或供应商门户读取订单号、物料编码、数量与金额，再与信用证条款逐项核对。接口返回的字段是否与单证字段同名同义，直接决定后续比对能否成立。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向指定地址发送请求，实际操作与 Postman、ApiFox 类似。Params 为路径请求参数，GET 请求中居多；Body 为请求体，POST/PUT 请求中居多；Headers 为请求头，用于传递特殊信息。URL 与三种数据均可通过 `{{}}` 引用变量，变量来自全局变量、系统变量与前方节点输出。系统变量包含 appId、chatId、responseChatItemId、variables、cTime、histories，其中 chatId 与 responseChatItemId 在测试模式下不存在。返回值通过 JSON path 语法提取，输出类型选择字符串时会将对应 key 的值转成 json 字符串。

假设演练样本：某外贸单证员收到一份信用证，编号与日期留空，条款写明“受益人须提交由开证申请人指定代表签署的检验证书”。采购合同显示供应商为“华东某机械配件厂”，合同数量 500 件，交货期 2025 年 3 月。单证员拟通过 HTTP 接口从供应商系统读取该合同项下的发货记录，拟稿句为：“供应商系统返回的发货数量 500 件与信用证要求的检验证书数量一致，可直接交单。”该拟稿句只核对了数量字段，未核对检验证书的签署主体与信用证条款是否对应，也未经银行审单确认。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 请求地址 | 供应商系统公开接口地址 | 按外部接口文档选择，地址可引用已提供变量 |
| 请求方法 | POST | 读取发货记录用请求体传递合同号，与外部契约一致 |
| Headers 鉴权 | Authorization 引用已配置变量 | 凭证通过安全配置注入，不写入公开样例 |
| Body 结构 | 合同号、物料编码、日期范围 | 核对 JSON 结构与外部接口契约逐字段对应 |
| 返回值提取 | 数量、发货日期、签署状态 | 按 JSON path 提取，输出类型选字符串 |
| 调试身份 | chatId 与 responseChatItemId 留空 | 测试模式下不存在，不把空值当业务故障 |

## 容易做错的三处

1. 把接口返回的数量字段直接当作信用证审单结论。数量一致只表示该字段匹配，检验证书的签署主体、有效期与信用证条款仍需人工核对。
2. 在测试模式下因 chatId 为空而判定接口异常。文档明确 chatId 与 responseChatItemId 在测试模式下不存在，空值属于调试环境特征。
3. 用相似度分数代替权限或实体过滤。相关度分数只反映检索排序，不承担供应商身份校验或授权判断。

## 怎么确认配好了

1. 输入假设样本中的拟稿句与供应商系统返回的发货记录，比较数量字段与检验证书签署主体字段，只有两个字段都与信用证条款逐项对应，才满足交单前的核对条件。
2. 输入一条 chatId 为空的测试请求，观察返回结构中 chatId 与 responseChatItemId 是否缺失，缺失属于文档说明的测试模式特征，不据此判定接口故障。
3. 输入一条包含相似度分数的检索结果，比较分数与供应商授权字段，分数高低不改变授权状态，授权仍需下游系统实现或人工核对。
