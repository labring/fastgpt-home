# 加盟费与保证金结算的库存采购与供应商资料：HTTP 接口与外部系统

## 这个品类的数据长什么样

加盟费与保证金结算围绕资金和违约扣款展开，不承担政府备案职能。主要数据来源为财务系统、加盟合同、银行流水和门店违规记录。日常文档包括加盟费发票、保证金台账、扣款通知和合同付款计划。库存采购与供应商资料在本品类中属于结算依据类材料：采购入库数量、供应商名称与付款计划共同决定应结金额与扣款事由。数据按月及每次扣款更新。本页只处理这些材料经 HTTP 模块与外部系统对接时的请求构造、变量引用与返回值提取，不构造授权、审批或写库动作。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向指定地址发送请求，Params 用于路径参数，Body 用于请求体，Headers 用于请求头，三者均可用 `{{}}` 引用全局变量、系统变量和前方节点输出。URL 同样可引用变量。系统变量包括 appId、chatId、responseChatItemId、variables、cTime、histories；histories 默认最多取 10 条且无法修改长度。测试模式下 chatId 与 responseChatItemId 不存在，调试空值不构成业务故障。返回值通过 JSON path 或 JS 对象取值规则提取，输出类型选字符串时会把对应 key 的值转为 json 字符串。检索与相似度不承担权限或实体隔离职责，HTTP 调用本身也不构成授权。

假设演练样本：一份供应商资料原文为「供应商：华岭办公用品有限公司；对象：A 区门店 2024 年 10 月办公耗材采购；状态：合同付款计划已登记，扣款通知尚未开具；有效范围：2024 年 10 月 1 日至 10 月 31 日」。一条待判定的拟稿句为「该供应商 10 月采购款已完成扣款并开具扣款通知」。判定时比较拟稿句与原文的状态字段：原文只载明付款计划已登记，扣款通知未开具，拟稿句所称已完成扣款与开具通知在该字段上未获支持，属于待核实，不构成否定或冲突。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 核对方式与理由 |
| --- | --- | --- |
| 请求地址 | 外部结算服务地址，路径含门店编号变量 | 按外部接口文档选择地址与方法，地址可引用已提供变量 |
| Params | 门店编号、结算期间 | 逐项核对实际传入值是否与供应商资料原文一致 |
| Headers | Authorization 以 Bearer 加令牌变量注入 | 鉴权凭证通过安全配置注入，不写入公开样例 |
| Body | JSON 含供应商名称、对象、状态字段 | 仅在相应请求类型下使用，核对结构与外部接口契约 |
| 返回值提取 | 取状态字段与金额字段 | 按 JSON path 提取，输出类型选字符串时转为 json 字符串 |
| 调试身份字段 | chatId、responseChatItemId 留空 | 测试模式下这两个字段不存在，空值不作为业务故障 |

## 容易做错的三处

1. 把拟稿句中的「已完成扣款」当作原文已载明事实。输入为上述供应商资料原文与拟稿句；比较两者状态字段；原文只写付款计划已登记、扣款通知尚未开具，可观察结果是该表述未获支持。
2. 在 Body 中引用字符串变量时漏加引号。输入为含供应商名称变量的 Body 声明；比较最终解析结果与预期 JSON；可观察结果是解析出的类型与外部接口契约不符。
3. 把测试模式下缺失的 chatId 判为业务故障。输入为测试模式请求；比较系统变量说明与请求实际取值；可观察结果是该字段本就不存在，无需按故障处理。

## 怎么确认配好了

1. 输入上述供应商资料原文与拟稿句，比较状态字段取值，拟稿句所称扣款与通知事项在原文中未获支持即满足核对条件。
2. 输入含供应商名称变量的 Body 声明，比较解析后 JSON 的字段类型与外部接口契约，类型一致即满足条件。
3. 输入测试模式请求，比较 chatId 与 responseChatItemId 的实际取值与系统变量说明，两者缺失属预期现象即满足条件。
