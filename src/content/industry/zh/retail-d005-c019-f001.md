# 即时零售门店履约的库存采购与供应商资料：HTTP 接口与外部系统

## 这个品类的数据长什么样

即时零售门店履约按分钟处理线上订单，库存采购与供应商资料因此要跟得上每单节奏。主要数据来自抖音即时零售、美团或京东到家后台、门店库存与骑手轨迹，日常文档包括即时订单、拣货清单、缺货报备和配送异常单。库存采购与供应商资料在本环节的核心诉求，是把采购单、到货记录、供应商资质与门店库存之间通过 HTTP 接口对接，让外部系统按契约回传结果。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向对应地址发送请求，Params 为路径请求参数，Body 为请求体，Headers 为请求头，三者均可用 `{{}}` 引用变量；URL 也可引用变量。变量来自全局变量、系统变量和前方节点输出。系统变量含 appId、chatId、responseChatItemId、variables、cTime、histories，其中 chatId 与 responseChatItemId 在测试模式下不存在。返回值通过 JSON path 提取，输出类型选字符串时会把对应 key 的值转成 json 字符串。对话接口以 APIKey 鉴权，推荐在请求体传 `body.appId`，也支持 `Authorization: Bearer <apiKey>-<appId>`；`model`、`temperature` 等字段无效，由编排决定。插件调用默认 detail 模式，无需 chatId 与 messages，通过 variables 传输入，通过 pluginOutput 取输出。

假设演练样本：某门店交接材料原文为“采购单 PO-2024-0517，供应商为鲜达商贸，品类为叶菜，到货日期 2024-05-17，数量 120 件，状态为已下单，尚未收货”。一条待判定拟稿句为“该采购单已完成收货并可计入本期库存”。材料只写到已下单，未载明收货动作，拟稿句超出原文范围。

## 配置怎么定

| 配置项 | 本次假设起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 请求地址与方法 | 按外部接口文档给定地址，方法取 POST | 地址可引用变量，需与接口契约逐字核对 |
| Headers 鉴权 | 使用 `Authorization: Bearer {{token}}` | 凭证经安全配置注入，与请求头字段名比对 |
| Body 结构 | 按接口契约声明采购单字段 | 核对 JSON 结构与外部契约是否一致 |
| 变量引用 | 引用前方节点输出的采购单号 | 逐项核对实际传入值与材料原文 |
| 返回值提取 | 以 JSON path 提取状态字段 | 与接口响应示例比对提取结果 |
| 输出类型 | 字符串输出转 json 字符串 | 与下游文本加工所需格式比对 |

上表数值均为本次假设试验起点，不是官方默认值。

## 容易做错的三处

1. 把测试模式下不存在的 chatId、responseChatItemId 当成业务故障。检查输入为测试模式请求，比较该字段是否被引用，观察是否误报。
2. 把材料中“已下单”当成“已收货”。检查输入为样本原文，比较拟稿句与原文状态字段，观察拟稿句是否超出原文范围。
3. 把检索或表单当成授权执行。检查输入为交接请求，比较请求是否载明授权边界，观察是否把待审核当成已批准。

## 怎么确认配好了

1. 输入样本原文与拟稿句，比较“已下单”与“已完成收货”是否同主体同字段，观察拟稿句是否未获支持。
2. 输入测试模式请求，比较 chatId 是否被引用，观察是否把调试空值当成业务故障。
3. 输入交接请求，比较是否载明授权边界与生效状态，观察是否把待审核当成已批准。
