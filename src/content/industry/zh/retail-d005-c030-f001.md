# 商超供应商进场结算的库存采购与供应商资料：HTTP 接口与外部系统

## 这个品类的数据长什么样
本类别以购销或代销账款为主，不一定伴随驻场经营。采购合同、送货验收单、返利协议与对账单构成核对主线，数据来自 ERP 采购、供应商门户、POS 销售与财务系统。账款争议、供应商停供与公平交易要求，使接口调用必须能回溯到具体单据。资料更新频率为周或月，本页不据此推断批量同步、全量同步或交易触发机制。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
HTTP 模块可重复添加、手动配置、触发执行，向目标地址发送请求。Params 多用于 GET，Body 多用于 POST/PUT，Headers 传递特殊信息，三类数据与 URL 均可通过 {{}} 引用全局变量、系统变量和前方节点输出。返回值需按 JSON path 提取。对话接口用 APIKey 鉴权，推荐在请求体传 body.appId，也支持 Authorization: Bearer <apiKey>-<appId>；appId 优先级为 body.appId、<apiKey>-<appId>、apikey 关联的 appId。authProxy 需团队所有者开启，代理身份仍需具备目标应用和会话权限。传入的 model、temperature 无效。chatId 与 responseChatItemId 在测试模式下不存在，调试空值不构成业务故障。交互节点返回的 interactive 仅为展示配置，entryNodeIds、memoryEdges、nodeOutputs、nodeResponseId 不返回。表单收集值，业务核验、审批、数据库写入与外部同步需要各自的下游实现。

假设演练样本：某商超采购方与某供应商签订购销采购合同，约定送货验收单数量为对账依据。纸面材料原文为：采购合同载明“结算以经收货方签收的送货验收单为准”；送货验收单载明“签收数量 120 箱，签收日期 4 月 8 日”；返利协议载明“返利按季度结算”。待判定拟稿句为“本期对账数量以供应商发货数量 150 箱为准”。该句与验收单签收数量 120 箱不一致，且合同约定以签收单为准。

## 配置怎么定
| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 请求地址 | 外部接口文档给出的采购单查询地址 | 地址取自文档，与文档所列路径逐字比较 |
| 请求方法 | 按文档选择 GET | 与文档标注方法比较，不一致即记录 |
| Headers 鉴权 | Authorization 引用安全配置注入的凭证 | 与文档鉴权规范比较，凭证不写入公开样例 |
| Body 结构 | 按文档 JSON 契约书写字段 | 与文档字段名、层级逐项比较 |
| 返回值提取 | 按 JSON path 提取签收数量字段 | 与接口响应实际结构比较 |
| 变量引用 | 引用前方节点输出的验收单号 | 与节点输出实际值比较 |

以上数值均为本次假设试验起点，非官方默认值。

## 容易做错的三处
1. 把供应商发货数量当作对账数量。输入为发货数量 150 箱，比较对象为验收单签收数量 120 箱，可观察结果为两者不等且合同约定以签收单为准。
2. 把测试模式下不存在的 chatId 或 responseChatItemId 空值判断为接口故障。输入为测试模式请求，比较对象为文档说明的“测试模式下不存在”，可观察结果为该字段缺失属于预期。
3. 把交互节点的 interactive 展示配置当作包含内部运行态字段。输入为交互节点响应，比较对象为文档列出的仅返回 type 与 params，可观察结果为 entryNodeIds 等字段不出现。

## 怎么确认配好了
1. 输入假设样本中的合同原文、验收单原文与拟稿句，比较拟稿句数量与验收单签收数量及合同约定依据，当拟稿句与签收数量一致且依据指向签收单时，判定为通过。
2. 输入一条引用前方节点验收单号的请求，比较实际传入值与节点输出值，当两者逐字一致时，判定变量引用正确；不一致时记录差异，不推断失败原因。
3. 输入 detail=true 的请求，比较响应中 responseData 是否包含模块状态与完整结果，当字段按文档出现时，判定解析配置可用；缺失时记录缺口，不声称接口异常。检索与相似度不承担权限或实体隔离，未载明字段保持未知。
