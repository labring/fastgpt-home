# 多仓分仓与库存同步的库存采购与供应商资料：定时任务与自动化

## 这个品类的数据长什么样

多仓分仓发生在订单路由阶段，决定从哪个仓发货，与快递交接环节不同。主要数据来源包括 WMS、OMS、ERP 库存和平台库存接口，典型角色是供应链计划、WMS 管理员和电商运营。出错后果为超卖退款、跨区运费增加和发货延迟。日常文档包括分仓规则、库存同步表、调拨单和缺货预警。本页围绕这些文档，说明库存采购与供应商资料中定时任务与自动化的实施条件与核对步骤。

## 这些特征在「定时任务与自动化」这一环带来什么约束

定时任务与自动化需要明确触发责任：由应用定时能力触发，还是由外部调度触发，应按实际版本核对可用入口。外部数据由已配置接口读取，定时触发不会自动建立业务系统连接。HTTP 请求须按外部接口文档核对方法、请求头、请求体及变量输入。去重、幂等与业务写入需在接口或后续流程明确设计。执行记录应核对触发时间、真实输入、返回结果与业务状态，任务存在不等于执行成功。

假设演练样本：某供应链计划员在纸面演练中写下：“分仓规则文件 A 规定华东订单优先由甲仓发货；库存同步表 B 记录甲仓可售库存 120 件；调拨单 C 载明甲仓向乙仓调拨 30 件，状态为待审核。”拟稿句为：“甲仓可售库存充足，本次调拨已获批准，定时任务将自动执行。”待判定请求为：“请确认该拟稿句是否可直接用于供应商资料交接。”

## 配置怎么定

| 配置项 | 本次假设试验起点 | 核对方法 |
| --- | --- | --- |
| 触发方式 | 外部调度触发，因纸面样本未说明应用内定时入口 | 核对实际版本可用入口，与样本声明比较 |
| 接口 URL | 填写接口文档给出的地址 | 与接口文档逐字比较 |
| 请求方法 | 按接口文档选择 GET 或 POST | 与接口文档比较 |
| 请求头 Authorization | 使用 Bearer {{token}} | 与接口文档要求比较 |
| 请求体字段 | 引用库存同步表字段名 | 与样本字段逐项比较 |
| 执行记录 | 记录触发时间、输入与返回结果 | 与样本状态比较 |

上述起点为本次假设试验的起始值，不属官方默认值。变量引用遵循 {{key}} 语法，返回值按 JSON path 提取。

## 容易做错的三处

1. 将待审核调拨单当作已批准。输入为调拨单 C 状态“待审核”，比较对象为“已批准”，观察结果是状态字段取值不同，拟稿句缺少批准依据。
2. 将定时任务存在当作执行成功。输入为任务配置，比较对象为执行记录中的触发时间与返回结果，观察结果是记录缺失或结果为空。
3. 将相似度分数当作权限过滤。输入为检索返回的相似度数值，比较对象为授权范围，观察结果是分数高低与记录是否属于授权范围无对应关系。

## 怎么确认配好了

1. 针对拟稿句“本次调拨已获批准”，输入调拨单 C 原文，比较“待审核”与“已批准”，观察结果为状态字段不匹配，该句未获支持。
2. 针对“定时任务将自动执行”，输入任务配置与执行记录，比较触发时间与返回结果是否存在，观察结果为记录缺失时不能判定执行成功。
3. 针对“甲仓可售库存充足”，输入库存同步表 B 的 120 件与调拨单 C 的 30 件，比较可售数量与调拨数量，观察结果为数量关系需结合分仓规则 A 的优先级条件判断，单凭数字不能得出充足结论。

以上均为纸面核对，未实际运行。缺失证据保持缺失，待审核不构成批准，任务存在不构成执行成功。
