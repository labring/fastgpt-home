# 大卖场生鲜联营柜台的库存采购与供应商资料：向量模型与索引

## 这个品类的数据长什么样

大卖场生鲜联营柜台常由供应商驻场经营并按销售分成，库存采购与供应商资料因此同时牵涉联营合同、供应商送货单、食品进货查验记录、日销售报表和损耗单。这些材料按日或每批产生，用于核对进货凭证与损耗分摊。向量模型与索引要处理的对象正是这批文档，检索结果供内部核对引用，检索本身不构成对供应商资质、结算金额或退货责任的确认。

## 这些特征在「向量模型与索引」这一环带来什么约束

FastGPT 的知识库由库、集合和数据组成，最小搜索单位是库。向量存储采用 PostgresSQL 的 PG Vector 插件，索引为 HNSW；MongoDB 的 dataset.datas 表保存向量原数据，indexes 字段记录对应的向量 ID，一组数据可对应多个向量。检索时先召回向量，再按向量 ID 回 MongoDB 找原数据，同一组原数据被多路命中则合并，向量得分取最高分。关联检索的知识库须使用相同向量模型，不同向量模型的库不可共同关联，需先核模型标识并排除不符合者。图片检索还取决于入库时是否生成图片描述或图片向量索引，仅有查询端图片输入不足以命中。

假设演练样本：某门店生鲜部留存一份联营供应商送货单，正文为“供应商甲于2025年3月10日向本店配送冷鲜猪肉80公斤，随附食品进货查验记录编号JH-0310，验收人签字齐全”。同批资料另有一份损耗单，正文为“2025年3月10日冷鲜猪肉报损3公斤，原因记录为解冻血水渗出”。待判定拟稿句为“该供应商本批次货物已完成全部查验且损耗由供应商承担”。该拟稿句超出原文载明范围，原文只记录配送数量、查验记录编号与签字，损耗单只记录报损数量与原因，未载明责任归属。

## 配置怎么定

| 配置项 | 本页相关取值或核对项 | 说明与假设依据 |
| --- | --- | --- |
| 向量模型 | 同一库内各集合使用同一向量模型 | 关联检索要求相同向量模型，先核实际模型标识 |
| 索引字段 | indexes 记录向量 ID，可为数组 | 一组原数据可对应多组向量，索引与原文分别核对 |
| 索引内容 | 以完整且聚焦的文本建立索引 | 索引长度与检索覆盖需结合样本权衡 |
| 图片索引 | 入库时确认是否生成图片描述或图片向量 | 图片检索取决于入库索引，非仅查询端 |
| 引用上限 | 本次假设试验起点设为若干 tokens | 选此起点为便于比较不同设置下的引用原文，与相邻取值对照 |
| 最低相关度 | 语义检索或结果重排时生效的 0-1 阈值 | 该值为过滤阈值，不作为排序规则 |

## 容易做错的三处

1. 把拟稿句“损耗由供应商承担”当作原文已载明事实。原文只记录报损数量与原因，责任归属未载明，比较时须逐字对照原文范围，缺载内容记为待核实。
2. 将不同向量模型的库直接共同关联。应先核模型标识，排除不符合者并记录实际观察，不据此推断漏召回或冗余等运行结果。
3. 把检索命中当作授权或结算依据。检索返回引用内容，供应商资质确认、损耗分摊审批与结算需另接系统实现，检索不承担该职责。

## 怎么确认配好了

1. 输入上述送货单与损耗单原文，比较拟稿句与原文载明字段。若拟稿句出现原文未载明的责任归属表述，则该句未获支持；若逐字限于配送数量、查验编号与报损数量，则与原文一致。
2. 输入两份不同向量模型的知识库标识，比较模型字段。若标识不一致，则排除该组合并记录；若一致，方可进入检索配置核对。
3. 输入一份纯图片查询，比较入库时是否生成图片描述或图片向量索引。若入库未建立对应索引，则图片检索不可用；若已建立，再核对查询端模型能力。空结果承接可用明确的纸面输入空数组核对下游设计，不据此断言检索一定返回空。
