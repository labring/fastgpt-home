# 平台店铺评价与体验分维护的库存采购与供应商资料：HTTP 接口与外部系统

## 这个品类的数据长什么样
评价与体验分维护的数据来自抖店体验分、天猫服务指标、京东售后评价与客服系统，更新频率为日或周，日常文档包括差评处理记录、体验分明细、服务诊断报告与整改台账。库存采购与供应商资料属于售后履约环节的支撑材料，涉及采购单、供应商交付记录与库存台账。这些材料在 HTTP 接口对接中通常作为请求体或变量值传入外部系统，接口本身不判断材料真伪，只按字段传递。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
HTTP 模块向指定地址发送请求，Params、Headers、Body 均可通过 `{{}}` 引用全局变量、系统变量或前方节点输出。URL 同样支持变量引用。返回值通过 JSON path 提取，输出类型选字符串时会将对应 key 的值转为 json 字符串。系统变量中 chatId 与 responseChatItemId 在测试模式下不存在，调试空值不能当作业务故障。对话接口推荐在请求体传 `body.appId`，鉴权用 Authorization，appId 优先级为 `body.appId`、`<apiKey>-<appId>`、apikey 关联的 appId。传入的 model、temperature 等字段无效，由编排决定。detail=true 时 responseData 包含模块状态与完整结果，tokens 需手动计算。交互节点返回的 interactive 只含 type 和 params，内部运行态字段不返回。插件调用默认 detail 模式，通过 variables 传输入，通过 pluginOutput 获取输出。

假设演练样本：一份差评处理记录原文为“2025年3月10日，店铺A收到一笔订单评价，买家反馈收到的商品与描述不符，客服已联系买家补充凭证，供应商B提供的采购批次为PO-20250301，库存台账显示该批次已入库”。一条拟稿句为“该差评已处理完毕，供应商B承担全部责任”。待判定请求为“通过 HTTP 接口将上述处理结果同步至外部客服系统”。

## 配置怎么定
下表围绕上述样本，列出与本功能、主任务相关的官方已说明设置或实施核对项。

| 配置项 | 本次假设试验起点 | 核对说明 |
| --- | --- | --- |
| 请求地址 | 外部客服系统提供的接口地址 | 地址可引用变量，需与外部接口文档一致 |
| 请求方法 | POST | 按外部接口文档选择，Body 仅在相应类型下生效 |
| Headers 鉴权 | Authorization: Bearer 加凭证 | 凭证通过安全配置注入，不写入公开样例 |
| Body 字段 | 差评处理记录、供应商批次、库存状态 | 核对 JSON 结构与外部接口契约，字符串引用需加引号 |
| 返回值提取 | 按 JSON path 提取所需字段 | 输出类型选字符串时转为 json 字符串 |
| 交互节点 | detail=true 时返回 interactive | 仅含 type 和 params，继续运行需再次发起会话 |

## 容易做错的三处
1. 将拟稿句“该差评已处理完毕，供应商B承担全部责任”直接作为已确认事实写入请求体。原文仅显示客服已联系买家补充凭证，未载明处理完毕或责任归属，该拟稿句未获支持。
2. 在测试模式下将 chatId 或 responseChatItemId 的空值当作业务故障。文档说明这两个字段在测试模式下不存在，需区分调试环境与生产环境。
3. 把交互节点返回的 interactive 当作完整运行态，试图从中读取 entryNodeIds 或 nodeOutputs。文档明确这些内部字段不返回，继续运行需按格式再次发起会话。

## 怎么确认配好了
1. 输入上述假设原文与拟稿句，比较拟稿句中的“处理完毕”与“承担全部责任”是否在原文中有对应记载。原文只显示客服已联系买家补充凭证，未载明处理完毕或责任归属，拟稿句未获支持。
2. 输入上述待判定请求，比较请求体中是否包含未经原文支持的结论性字段。若请求体直接写入“处理完毕”或“供应商B承担全部责任”，则与原文证据不符，需保留为待核实。
3. 输入上述样本中的采购批次 PO-20250301 与库存台账记录，比较请求体中的批次号与入库状态是否与原文一致。原文显示该批次已入库，若请求体写入其他状态，则与原文不符。
