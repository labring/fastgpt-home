# 平台退款退货处理的库存采购与供应商资料：定时任务与自动化

## 这个品类的数据长什么样

普通平台退款退货按订单持续发生，不一定关联单场直播承诺，因此库存采购与供应商资料在定时任务中面对的是逐单累积的退款申请、退货物流单、质检照片与退款审批。数据来源分散在平台售后后台、客服聊天、WMS收货与支付退款记录，更新频率为每单与每日。定时任务需要按外部接口文档读取这些材料，不能假定触发动作自动建立业务系统连接。采购与供应商资料属于另一侧输入，退款责任判定结果可能影响补货或向供应商追偿，但该联动须由接口或后续流程明确设计。

## 这些特征在「定时任务与自动化」这一环带来什么约束

定时触发不产生授权。退款审批处于待审核状态，不证明缺少操作权限；退货物流单已签收，不等于质检结论已出。HTTP 模块按配置的方法、请求头、请求体发送请求，变量来自全局变量、系统变量或前方节点输出，URL 也可通过 `{{}}` 引用变量。返回值需通过 JSON path 提取，例如 `data.user.name`。触发时间、真实输入、返回结果与业务状态须分别核对，任务存在不能替代执行成功。

假设演练样本：一份退款申请原文写“订单 A-2201，买家于 3 月 4 日申请退货，退货物流单 SF-7788 显示 3 月 7 日签收，质检照片编号 Q-045 记录外包装破损，退款审批单号 R-0912 状态为待审核”。一条拟稿句为“R-0912 已批准退款，可通知供应商补货”。该拟稿句的判定对象是审批状态字段，原文仅载明待审核。

## 配置怎么定

| 配置项 | 本页取值或核对项 | 依据与边界 |
| --- | --- | --- |
| 触发方式 | 核对由应用定时能力还是外部调度触发 | 按实际版本核对可用入口 |
| 请求方法 | 按外部接口文档核对 GET 或 POST | 方法由接口文档规定 |
| 请求头 | 配置 `Authorization` 为 Bearer `{{token}}` | token 来自全局变量 |
| 请求体 | 按接口文档声明字段，字符串加引号 | 引用变量用 `{{key}}` |
| 返回值提取 | 用 JSON path 配置 key，如 `data.user.name` | 输出类型可选字符串 |
| 执行记录 | 核对触发时间、输入、返回与业务状态 | 任务存在不等于执行成功 |

本页假设试验起点：将返回值 key 设为 `data.user.name`，因样本响应含该字段路径，与 `data.user` 整体值比较以确认提取粒度。

## 容易做错的三处

1. 把待审核当作已批准。样本中 R-0912 状态为待审核，拟稿句却写“已批准退款”，输入为审批状态字段，比较对象是原文“待审核”与拟稿“已批准”，两者同主体同字段且互斥，构成矛盾。
2. 把签收当作质检完成。样本仅载明 SF-7788 于 3 月 7 日签收，未载明质检结论，若拟稿写“质检合格可退款”，该结论未获支持。
3. 把检索结果当作授权。检索到退款申请不表示已获退款执行权限，授权状态须另行核对。

## 怎么确认配好了

1. 输入样本原文与拟稿句“R-0912 已批准退款”，比较审批状态字段：原文为待审核，拟稿为已批准，两者互斥即判定矛盾；若原文未载明状态，则记为未获支持。
2. 输入样本中 SF-7788 签收记录，比较是否存在质检结论字段：原文未载明，判定为待核实，不写成否定。
3. 输入一次纸面空结果 `[]`，核对下游设计是否将空结果与“无退款”区分；空结果承接须由下游明确处理，不声称虚构规则检索必返回空。
