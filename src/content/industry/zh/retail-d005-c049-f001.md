# 批发市场档口交易的库存采购与供应商资料：HTTP 接口与外部系统

## 这个品类的数据长什么样

批发市场档口交易围绕现场议价与托运展开，进货单、手写销售单、摊位租赁合同、货款收据构成日常文档主体，数据按日或按单更新。档口库存与供应商资料往往分散在纸质单据、微信收款记录和托运单之间，同一批货的到货数量、结算金额、尾款状态可能分别落在不同材料上。这一特征决定了 HTTP 接口对接的重点落在单据字段的逐项核对，以及外部系统返回值与档口实际业务状态的对应关系。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向目标地址发送请求，Params 用于路径请求参数，Body 用于请求体，Headers 用于请求头，三者均可通过 `{{}}` 引用全局变量、系统变量和前方节点输出。返回值通过 JSON path 提取，输出类型选择字符串时会把对应 key 的值转成 json 字符串。系统变量中，chatId 与 responseChatItemId 在测试模式下不存在，不能把调试空值当作业务故障。变量引用错误、Body 结构与外部接口契约不一致、返回值提取路径与响应结构不匹配，都会让下游拿不到预期的进货单或供应商字段。

假设演练样本：档口老板提供一份手写销售单，原文为“3 月 12 日，A 供应商，土豆 200 斤，单价 1.2 元，已付 100 元，尾款 140 元，货已由顺达托运发出”。另有一条拟提交给外部系统的交接请求：“将本单尾款状态标记为已结清，并同步供应商资料。”该请求未附结清凭证，也未说明同步范围与授权人。按现有材料，尾款状态为未结清，交接请求超出材料可支持的范围。

## 配置怎么定

| 配置项 | 假设起点 | 说明与核对方式 |
| --- | --- | --- |
| 请求地址 | 外部系统提供的接口地址 | 地址可引用变量，核对地址与外部接口文档一致 |
| 请求方法 | 按外部接口文档选择 | 方法决定 Params、Body 是否生效，逐项核对 |
| Headers | Authorization 使用 Bearer 加凭证 | 凭证通过安全配置注入，不写入公开样例 |
| Body | 按外部接口契约构造 JSON | 仅在相应请求类型下使用，核对字段名与类型 |
| 变量引用 | 引用前方节点输出或全局变量 | 逐项核对实际传入值，确认来源节点已执行 |
| 返回值提取 | 按 JSON path 语法配置 key | 核对提取路径与响应结构，输出类型按需选择 |

表中“假设起点”为本次纸面演练的起始配置，选此起点是为了让样本中的销售单字段有明确落点，与外部接口文档核对后调整。

## 容易做错的三处

1. 把样本中“已付 100 元，尾款 140 元”直接当作结清状态提交。输入为手写销售单原文，比较项为尾款字段与结清凭证，观察结果是材料中无结清凭证，状态应保持未结清。
2. 在 Body 中引用字符串变量时未加引号。输入为 `"{{string}}"` 与 `{{string}}` 两种写法，比较项为外部接口收到的 JSON 结构，观察结果是未加引号时字符串被解析为其他类型。
3. 把测试模式下不存在的 chatId 或 responseChatItemId 当作业务故障排查。输入为测试模式下的请求记录，比较项为系统变量说明，观察结果是这两个字段在测试模式下不存在，需在正式会话中核对。

## 怎么确认配好了

1. 输入假设样本中的手写销售单原文与拟提交的交接请求，比较尾款字段与请求中的结清标记，观察结果是两者不一致，请求应被判定为超出材料支持范围。
2. 输入 Body 中字符串变量的两种写法，比较外部接口实际收到的 JSON 结构与预期结构，观察结果是加引号的写法保持字符串类型，未加引号的写法类型不符。
3. 输入一次正式会话请求与一次测试模式请求，比较 chatId 与 responseChatItemId 的取值，观察结果是测试模式下这两个字段不存在，正式会话中按实际传入值核对。

配置完成后，返回值提取路径与外部响应结构的对应关系需逐项核对，变量来源节点是否已执行需确认。检索或表单收集到的值不构成业务授权，尾款结清、供应商资料同步、数据库写入与外部系统同步均需另行确认实现与授权边界。
