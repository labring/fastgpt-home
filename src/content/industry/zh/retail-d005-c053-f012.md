# 渠道应收账款催收的库存采购与供应商资料：文档解析与分块

## 这个品类的数据长什么样

渠道应收账款催收发生在赊销之后，核心是授信与现金回收，主要数据来源包括财务系统、银行回单、经销商订单和销售合同。日常处理的文档集中在应收账龄表、催款函、授信协议和发货冻结通知四类。库存采购与供应商资料属于其中一类需要进入知识库的业务材料，涉及采购订单、供应商对账记录、入库单、供应商资质文件等。这些材料的更新频率大致为周或月，资料发生变化后需要重新核对解析与索引状态。

## 这些特征在「文档解析与分块」这一环带来什么约束

FastGPT 的知识库由库、集合和数据三部分组成，最小搜索单位是库，集合仅用于分类管理。一组数据可以对应多个向量索引，检索时先召回向量，再根据向量 ID 去 MongoDB 的 dataset.datas 表中寻找原数据，同一组原数据被多路命中时合并并取最高得分。这意味着分块时需要让每个数据块的结构和语义尽量完整单一，条件、说明与其约束的内容不能拆散到不同块中。

假设演练样本：某经销商与品牌方签署的授信协议节选原文为「甲方授予乙方信用额度人民币八十万元，账期为发货后六十日。乙方超授信发货需经甲方书面批准，未经批准的冻结通知于发出之日起生效。」另有一条待判定的拟稿句：「该经销商已获甲方批准超授信发货，冻结通知尚未生效。」此样本的主体是甲方与乙方，对象是信用额度与冻结通知，状态是「未经批准」与「尚未生效」，有效范围是协议约定的账期与发货条件。拟稿句与原文在「是否已获批准」这一字段上取值相反，属于同主体、同期间、同字段的互斥取值。

## 配置怎么定

下表围绕上述样本列出与本功能相关的官方已说明设置或实施核对项。

| 配置项 | 设置或核对内容 | 与本页样本的关系 |
| --- | --- | --- |
| 搜索模式 | 语义检索、全文检索或混合检索 | 样本含「八十万元」「六十日」等精确值，混合检索可同时覆盖语义与关键词 |
| 最低相关度 | 0-1 数值，仅在语义检索或结果重排时生效 | 本次假设试验起点设为 0.3，理由是样本问题主体明确，需与 0.5 比较观察召回范围变化 |
| 引用上限 | 每次搜索最多引用的 tokens 数 | 样本原文较短，需确认引用上限能容纳完整条款而不截断条件句 |
| 问题优化 | 检索前进行指代消除与问题扩展 | 样本问题若含「该协议」等指代，开启后可补全主体 |
| 结果重排 | 使用 ReRank 模型二次排序 | 样本条款候选较多时，重排得分可用于过滤 |
| 索引状态 | 确认资料变更后实际训练与索引是否更新 | 授信协议版本变更后，需核对新条款是否已生成索引 |

## 容易做错的三处

1. 将「未经批准」直接判定为「已批准」。样本原文明确写「超授信发货需经甲方书面批准」，拟稿句写「已获甲方批准」，两者在同一字段上取值互斥。若只看到「冻结通知」字样就推断批准状态，属于把未载明信息当作已载明。
2. 将上传成功当作索引已更新。资料上传到知识库后，训练与索引生成需要单独确认。样本中授信协议若发生版本变更，旧索引可能仍指向旧条款，检索结果会返回过期内容。
3. 将检索结果当作授权依据。检索到授信协议条款，不代表该经销商当前已获批准或冻结通知已生效。批准与生效属于业务事实，需要人工核对或下游系统确认，检索环节不承担授权判定。

## 怎么确认配好了

1. 输入样本原文与拟稿句，比较「是否已获批准」这一字段。若检索结果返回的条款包含「需经甲方书面批准」且未出现批准记录，则拟稿句的「已获批准」表述不成立，应标记为待核实。
2. 输入样本中的精确值「八十万元」与「六十日」，使用全文检索或混合检索，观察返回结果是否包含完整条款。若返回内容缺失账期或额度条件，说明分块将条件与约束拆离，需要调整分段。
3. 输入一个明确不包含在库中的纸面查询，例如空引用列表 `[]`，核对下游设计对空结果的处理。若系统返回空结果，记录为观察现象；若返回无关内容，记录为待排查，不推断具体原因。

以上三项验证均基于假设演练样本，未实际执行，仅说明预期比较方法与观察现象。
