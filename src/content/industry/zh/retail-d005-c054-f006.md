# 渠道窜货稽查的库存采购与供应商资料：定时任务与自动化

## 这个品类的数据长什么样

渠道窜货稽查围绕区域与价格秩序展开，主要材料来自防伪码系统、电商平台价格、经销商发货记录与市场巡检，日常文档包括窜货投诉单、防伪码记录、处罚通知与调查照片。库存采购与供应商资料是其中一类核对对象，用于把货源批次、采购凭证与供应商信息同窜货线索对应起来，判断某批货的流转是否落在授权范围之内。资料更新频率为周与不定期，本页不据此推出批量同步或实时机制。

## 这些特征在「定时任务与自动化」这一环带来什么约束

定时触发只负责在设定时间启动流程，外部数据仍由已配置的 HTTP 请求读取，触发不会自动建立业务系统连接。请求方法、Headers、Body 与变量引用按外部接口文档逐项核对，返回值通过 JSON path 提取。去重、幂等与业务写入需在接口或后续流程单独设计。执行记录应能核对触发时间、真实输入、返回结果与业务状态，任务存在不等于执行成功。

假设演练样本：一份待核对的经销商发货记录原文为“2025年3月，华东区域经销商甲向某网店发出批次A商品200件，采购凭证编号CG-2025-0312，供应商为乙公司，授权销售范围为华东区域”。一条待判定拟稿句为“该批货已构成跨区窜货，应执行处罚”。原文只载明发货对象与授权范围，未载明该网店实际收货地区与转售去向，拟稿句的结论未获支持，处罚执行更无依据。

## 配置怎么定

| 配置项 | 本页取值或核对项 | 与本文档的关系 |
| --- | --- | --- |
| 触发方式 | 本次假设起点：每周一09:00由应用定时能力触发一次 | 该数值为演练起点，用于与上次执行记录中的触发时间比较 |
| 请求方法 | 按外部接口文档填写，本样本假设为 POST | 方法取自接口文档，不取自本页 |
| Headers | 按接口要求填写，如 Authorization 使用 Bearer 加 token | 变量来自全局变量或前方节点输出 |
| Body | 引用发货记录字段，字符串需加引号，数字与布尔不加 | 引用方式遵循 `{{key}}` 规则 |
| 返回值提取 | 用 JSON path 提取所需字段，输出类型按需要选字符串 | 提取规则遵循 JS 对象取值 |
| 执行记录 | 记录触发时间、输入、返回结果与业务状态 | 用于核对，不替代业务写入 |

## 容易做错的三处

1. 把定时触发当成已连接业务系统。触发只启动流程，读取外部数据仍需已配置的 HTTP 请求；未配置接口时，任务运行也不产生业务数据。核对时比较请求配置是否存在与执行记录中的实际返回。
2. 把拟稿句的结论当作已核实事实。样本原文只写到发货对象与授权范围，拟稿句直接判定跨区窜货并执行处罚，缺少收货地区与转售去向。核对时比较原文载明字段与拟稿句所依赖字段，缺失即记为未获支持。
3. 把返回值提取当成授权或写入。JSON path 只解析响应内容，不校验权限，也不落库。核对时比较提取结果与后续流程是否另有写入设计，无设计则业务状态不变。

## 怎么确认配好了

1. 输入样本原文与拟稿句，比较拟稿句结论所依赖的字段是否在原文中出现。原文未载明收货地区与转售去向，拟稿句的窜货判定与处罚执行均未获支持，应记录证据缺口，不补造授权条款。
2. 输入一次假设触发记录，比较记录中的触发时间与设定起点、真实输入与样本原文是否一致。若返回结果为空或字段缺失，记录实际观察，不推断为接口故障或逻辑错误。
3. 输入提取配置与后续流程配置，比较提取出的字段是否被下游写入或校验环节引用。仅提取而无写入设计时，业务状态保持未知，不能宣称处罚已执行或数据已同步。
