# 生鲜供应商索赔的库存采购与供应商资料：定时任务与自动化

## 这个品类的数据长什么样
生鲜供应商索赔追究到货质量责任，不处理门店自然损耗，这一差别决定了数据围绕批次质量异常展开。主要数据来自质检系统、WMS验收、供应商合同与财务对账，日常文档为质量异常单、照片证据、扣款通知、索赔对账单。最耗时的固定证据、计算扣款、协商补货或赔付三个环节，通常发生在批次到货后至月度对账之间。这些材料是否具备可核对的授权状态，比材料数量更影响交接。

## 这些特征在「定时任务与自动化」这一环带来什么约束
定时触发只能按配置向外部地址发送请求，外部数据由已配置接口读取，不能假定定时触发自动建立业务系统连接。HTTP请求的方法、请求头、请求体与变量输入须按外部接口文档核对。去重、幂等与业务写入需在接口或后续流程明确设计。执行记录须核对触发时间、真实输入、返回结果与业务状态，任务存在不等于执行成功。

假设演练样本：某供应商合同约定“到货批次抽检不合格可发起索赔”，质检记录写“2025年3月10日批次A抽检不合格”，WMS验收写“2025年3月10日批次A已入库”。拟判定句为“该批次已具备索赔条件，可自动生成扣款通知”。此句涉及主体、对象、日期与状态，但合同是否载明自动扣款、扣款金额如何计算，样本未提供，属待核实。

## 配置怎么定
下表为本次假设试验起点，非官方默认值。选择理由是比较触发时间与人工核对时间是否一致，比较对象为执行记录中的真实输入。

| 配置项 | 本次假设起点 | 与什么比较 |
| --- | --- | --- |
| 触发入口 | 应用定时能力或外部调度 | 实际版本可用入口 |
| 请求方法 | POST | 外部接口文档 |
| 请求头 | Authorization Bearer {{token}} | 接口文档要求 |
| 请求体 | 引用批次、日期变量 | 样本原文字段 |
| 返回值提取 | 按 JSON path 取 message | 实际响应结构 |
| 执行记录 | 触发时间与返回结果 | 业务状态 |

## 容易做错的三处
1. 把定时触发当成自动写入数据库。检查输入是否为已配置接口，比较是否出现业务写入，观察结果仅为请求返回。
2. 把待审核当成缺少操作权限。检查样本是否载明授权状态，比较同主体同期间同一字段，观察是否只有相关阶段证据。
3. 把相似度当成权限或实体过滤。检查检索范围标识，比较向量模型标识，观察是否排除不符合者。

## 怎么确认配好了
1. 输入样本原文与拟判定句，比较合同是否载明自动扣款，观察是否仅能得出待核实。
2. 输入空结果[]，比较下游设计是否承接空值，观察是否出现虚构规则检索必返[]的断言。
3. 输入跨向量模型的两个库标识，比较标识是否一致，观察是否只记录排除结果，不执行跨模型检索比较漏召回。
