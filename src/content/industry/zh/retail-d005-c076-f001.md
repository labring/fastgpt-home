# 达人佣金结算与扣佣的库存采购与供应商资料：HTTP 接口与外部系统

## 这个品类的数据长什么样

达人佣金结算与扣佣发生在成交之后，核对重点是有效推广订单与售后扣佣，主要数据来自精选联盟后台、订单售后数据、财务系统和达人合同。库存采购与供应商资料这一任务，需要把采购单据、供应商档案与结算账单、退款扣佣明细、发票放在同一核对链条上。HTTP 接口与外部系统环节的作用，是把这些资料按外部接口契约传入传出，并按 JSON path 提取返回值。佣金设置记录、结算账单、退款扣佣明细、发票的更新频率为周或月，接口调用按实际业务发生时点发起，不由此推出批量同步或实时触发机制。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向对应地址发送请求，实际操作与 Postman、ApiFox 这类工具接近。Params 为路径请求参数，GET 请求中用得居多；Body 为请求体，POST/PUT 请求中用得居多；Headers 为请求头。三种数据均可通过 `{{}}` 引用变量，URL 也可引用变量。变量来自全局变量、系统变量、前方节点输出。系统变量包括 appId、chatId、responseChatItemId、variables、cTime、histories，其中 chatId 与 responseChatItemId 在测试模式下不存在。返回值通过 JSON path 语法提取，出参格式化以 json 转字符串为主。

假设演练样本：一份纸面交接材料写明，某供应商档案记录的主体为“华东某包装材料供应商”，对象为“2025 年 3 月批次纸箱采购”，状态为“采购单已提交，供应商资料待补充开户信息”，有效范围为“仅限本次采购对账使用”。同批材料附一条待判定的交接请求：“请通过 HTTP 接口把该供应商的开户信息写入结算系统，并按结算账单自动扣佣。”材料未载明该供应商已通过资质审核，未载明结算系统已开通写接口，未载明扣佣授权范围。该请求处于待核实状态，不构成已批准或已执行的业务动作。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 请求地址 | 外部接口文档给出的地址，地址中引用变量 | 与接口文档逐字符比较，确认路径与方法一致 |
| Params | 按接口文档列出的路径参数逐项填写 | 与文档参数表比较键名与取值来源 |
| Headers | Authorization 通过安全配置注入 | 与接口文档鉴权要求比较，不写入公开样例 |
| Body | 仅在 POST/PUT 下按契约写 JSON | 与接口响应示例的结构比较字段层级 |
| 变量引用 | 引用全局变量、系统变量、前方节点输出 | 逐项核对实际传入值，测试模式下 chatId 不存在 |
| 返回值提取 | 按 JSON path 配置 key | 与接口响应示例比较提取结果 |

## 容易做错的三处

1. 把待补充开户信息的供应商档案当成已通过资质审核，直接发起写入请求。检查方式：输入上述假设材料原文，比较“待补充开户信息”与“已通过资质审核”是否同一字段的互斥取值，观察材料中是否存在审核通过记录；缺失时记录为未获支持。
2. 把待判定的交接请求当成已批准的扣佣授权。检查方式：输入该请求句，比较其中是否载明授权主体、授权范围与生效状态，观察是否存在签署或审批记录；待审核不证明缺少操作权限，也不等于已授权。
3. 把 JSON path 提取到的返回值直接当成业务写入已完成。检查方式：输入接口响应示例，比较提取值与下游写入动作是否分属两个环节，观察是否存在下游实现说明；返回值提取与数据库写入、外部同步是不同事实。

## 怎么确认配好了

1. 针对假设材料原文，输入“采购单已提交，供应商资料待补充开户信息”，比较材料是否载明资质审核通过，观察是否出现审核通过记录。预期为未获支持，记录证据缺口。
2. 针对待判定交接请求，输入“请通过 HTTP 接口把该供应商的开户信息写入结算系统，并按结算账单自动扣佣”，比较请求是否载明授权边界与接口开通状态，观察是否出现授权或开通记录。预期为待核实，不判定为已批准或已执行。
3. 针对返回值提取配置，输入接口响应示例与所配 key，比较提取结果与响应中对应字段，观察提取值是否与示例一致。预期为按 JSON path 得到对应值，不据此断言下游写入已完成。

以上均为纸面核对，未实际发起请求、未实际写入、未实际扣佣。
