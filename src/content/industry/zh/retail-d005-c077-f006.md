# 进出口许可证件办理的库存采购与供应商资料：定时任务与自动化

## 这个品类的数据长什么样

许可证办理发生在申报之前，决定货物能否合法进出口，这一环节的库存采购与供应商资料因此带有前置约束。主要数据来自商务主管部门系统、海关商品编码、供应商资料与客户用途说明，日常文档包括自动进口许可证、两用物项许可证、合同和产品说明。最耗时的工作是判断监管证件、准备用途说明、跟进审批状态。这些资料按每票不定期更新，定时任务只能按已配置的接口读取外部数据，不能假定触发即自动建立业务系统连接。

## 这些特征在「定时任务与自动化」这一环带来什么约束

定时触发责任需要明确：由应用定时能力触发还是由外部调度触发，按实际版本核对可用入口。HTTP 请求按外部接口文档核对方法、请求头、请求体及变量输入，URL、Params、Headers、Body 均可通过 {{}} 引用全局变量、系统变量或前方节点输出。返回值解析使用 JSON path 语法，出参格式化在 v4.6.8 后加入，输出类型选择字符串时会把对应 key 的值转成 json 字符串。

假设演练样本：某外贸合规岗在 2025 年 3 月 10 日收到一份自动进口许可证申请材料，原文为「供应商甲于 2025 年 3 月 8 日提交两用物项出口管制清单内产品说明，合同编号 HT-2025-031，客户用途说明载明用于检测设备，申请状态为材料已受理」。拟交接请求为「请定时任务在审批状态变为已批准后自动写入采购库存表并同步供应商资料」。该请求涉及的状态变更是业务动作，需下游实现，定时任务本身不产生批准结果。

## 配置怎么定

| 配置项 | 本次假设起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 触发方式 | 外部调度按每票提交后触发一次 | 与接口文档核对触发入口，比较是否由应用定时能力提供 |
| 请求方法 | POST | 按外部接口文档核对，与 GET 读取场景区分 |
| Headers | Authorization 为 Bearer {{token}} | 按接口文档核对请求头，比较 token 来源是否来自全局变量 |
| Body 字段 | appointment 引用前方节点输出的 json 字符串 | 按文档示例核对，比较字段名是否与接口一致 |
| 出参 key | data.user.name | 按 JSON path 规则核对，比较输出类型是否为字符串 |
| 执行记录 | 记录触发时间、真实输入、返回结果与业务状态 | 核对任务存在与执行成功的差别 |

## 容易做错的三处

1. 把检索结果当作授权依据。检索库同向量模型要求只适用于库间关联，不能扩展为工商网站或外部系统也要同模型，也不能把相似度当作权限或实体过滤。
2. 把待审核状态当作缺少操作权限。样本中申请状态为材料已受理，未载明批准，属于未获支持或待核实，不能判定为否定或冲突。
3. 把定时触发当作业务写入完成。样本请求要求批准后写入库存表并同步供应商资料，批准、写入、同步是三个不同事实，需下游接口实现。

## 怎么确认配好了

1. 输入样本原文与拟稿句，比较申请状态字段是否载明已批准，观察输出是否为未获支持，若出现已批准判定则不符合。
2. 输入样本请求，比较请求中是否包含批准后自动写入的动作，观察输出是否标注需下游实现，若直接输出已同步则不符合。
3. 输入空结果 [] 的纸面输入，比较下游设计是否承接空结果，观察是否输出无记录提示，若虚构规则返回空则不符合。
