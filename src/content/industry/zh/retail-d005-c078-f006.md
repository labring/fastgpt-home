# 连锁总部选址开店的库存采购与供应商资料：定时任务与自动化

## 这个品类的数据长什么样
选址开店发生在门店营业前，核心是租赁和工程交付，资料按每店不定期更新。库存采购与供应商资料围绕选址评估表、租赁意向书、装修预算、开业排期展开，主体是连锁总部拓展、区域开发和工程经理，出错会导致开店亏损、延期交付或押金损失。这些资料没有统一批量同步节奏，定时任务只能按每店实际提交的文档触发，不能假定全量或实时机制。

## 这些特征在「定时任务与自动化」这一环带来什么约束
定时触发与业务系统连接是两件事。HTTP 模块向对应地址发送请求，Params 为路径请求参数，Body 为请求体，Headers 为请求头，三者均可用 {{}} 引用全局变量、系统变量或前方节点输出。系统变量包括 appId、chatId、responseChatItemId、variables、cTime、histories，其中 histories 默认最多取 10 条且无法修改长度。返回值通过 JSON path 提取，例如 data.user.name 取用户名。去重、幂等与业务写入需在接口或后续流程明确设计，不能宣称自动具备。检索与相似度不承担授权或实体隔离职责。

假设演练样本：某连锁总部拓展部提交一份租赁意向书摘录，原文为“甲方为某商业管理公司，乙方为某连锁总部，意向租赁期限自 2026 年 3 月 1 日起 36 个月，意向书自双方盖章之日起生效，签署状态为待乙方盖章”。另有一条待判定拟稿句：“该意向书已生效，可据此排定装修节点。”样本仅用于说明核对方法，不代表任何真实主体或已发生业务。

## 配置怎么定
| 配置项 | 本次假设试验起点 | 核对方式 |
| --- | --- | --- |
| 触发来源 | 外部调度按每店提交时间发起 | 对照实际提交时间与请求记录，判断触发是否对应该店 |
| 请求方法 | POST | 与外部接口文档所列方法逐项比对 |
| Headers 中的 Authorization | Bearer {{token}} | 核对 token 来源与接口文档要求是否一致 |
| Body 字段 | 引用 {{appId}} 与文档标识 | 核对引用变量在本次请求中是否已赋值 |
| 返回值提取 | data.user.name | 对照接口响应示例确认路径存在 |
| 重复触发处理 | 待接口或后续流程明确 | 记录同一店是否出现多次请求及处理结果 |

起点数值仅为本次假设试验设定，选值理由是对照接口文档逐项核对，不与任何官方默认值混同。

## 容易做错的三处
1. 把定时触发当成业务系统已连接。触发只表示请求发出，数据库写入与外部同步需另行实现。检查方式：输入触发记录，比较是否出现对应业务写入结果，观察两者是否同时存在。
2. 把待盖章状态读成已生效。样本原文写明签署状态为待乙方盖章，拟稿句称已生效。检查方式：输入意向书原文与拟稿句，比较签署状态字段，观察拟稿句是否与原文一致。
3. 用相似度分数排除无关业务。相似度不是实体或权限过滤。检查方式：输入一次检索请求，比较返回记录与请求主体的授权范围，观察是否出现未授权记录。

## 怎么确认配好了
- 验证一：输入样本原文与拟稿句，比较“待乙方盖章”与“已生效”两个表述，拟稿句与原文一致才满足条件，否则记录为未获支持。

- 验证二：输入一次 HTTP 请求记录，比较请求方法与接口文档所列方法，两者一致才满足条件；方法字段缺失时记录为待核实。

- 验证三：输入一次检索返回，比较返回记录与请求主体的授权范围，未出现越权记录才满足条件；空结果用明确纸面输入 [] 核对下游设计，不声称虚构规则一定返回空。
