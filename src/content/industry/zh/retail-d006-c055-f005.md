# 特许加盟备案管理的门店服务与内部培训：多轮对话与提示词

## 这个品类的数据长什么样

特许加盟备案管理围绕商业特许经营信息管理系统、企业证照、门店清单与合同台账展开，日常处理特许经营合同、操作手册、备案材料与信息披露文件。门店服务与内部培训这一环，多轮对话需要把合同条款、手册步骤、披露口径分开承载，回答里出现的“两店一年”条件、备案主体、披露时点都来自具体材料，材料未载明的内容保持未知。资料更新不定期且按年，配置不必为同步频率设计额外机制。

## 这些特征在「多轮对话与提示词」这一环带来什么约束

多轮对话的上下文来自 chatId 关联的历史，messages 数组最后一个内容作为用户问题，其余 message 被忽略；不传 chatId 时不使用平台上下文，完全由传入 messages 构建。提示词需要写明资料范围、回答任务与缺证据时的处理方式，不让模型补写业务事实。问题优化面向知识库连续对话时核对指代消除与问题扩展，短问题是否适用由实际配置决定。模型与长度按最大上下文和回复上限核对，长手册与追问组合需要实测。回复格式按后续承接选择，选择 json_schema 时填写对应格式要求并验返回结构。检索与相似度只影响召回排序，不承担权限或实体隔离。

假设演练样本：供核对的材料原文为“甲方为特许人，乙方为加盟商。本合同签署日期为2024年3月1日，备案材料清单列明特许经营合同与操作手册。信息披露文件载明披露时点为签约前三十日。”一条待判定拟稿句为“本合同已于2024年3月1日生效，备案已完成。”该拟稿句中的“生效”与“备案已完成”在原文中没有对应记载，属于未获支持，需要保留证据缺口，不能改写成否定结论。

## 配置怎么定

下表围绕上述样本，列出与本功能相关的官方已说明设置或实施核对项。数值为本次假设试验起点，写明选择理由与比较对象，不作为官方默认值。

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| AI 模型 | 选用支持所需上下文长度的模型 | 与样本中合同、手册、披露文件合计长度比较，确认最大上下文覆盖 |
| 记忆轮数 | 先保留少量历史轮数 | 与门店服务追问场景比较，观察更早轮次是否影响回答 |
| 回复上限 | 打开并设中等长度 | 与披露口径说明的完整度比较，避免提前截断 |
| 温度 | 设偏低 | 与备案口径稳定性要求比较，保持回答一致 |
| 回复格式 | 保持默认 | 与后续承接比较，需要固定结构时再改 |
| 思考配置 | 使用默认 | 与问题复杂度比较，简单问答不提高强度 |

## 容易做错的三处

1. 把检索相似度当作权限或实体过滤。输入为样本中披露文件与无关加盟商记录，比较对象是召回结果是否只含授权范围，观察结果是相似度高低与授权无关，需要另行实现权限校验。
2. 把待审核当作已批准或把签署当作生效。输入为样本中签署日期，比较对象是原文是否载明生效条件，观察结果是原文只写签署日期，生效属于未获支持。
3. 把不传 chatId 当作仍使用平台上下文。输入为不传 chatId 的请求，比较对象是 messages 是否被完整使用，观察结果是平台不取数据库会话，上下文完全由传入 messages 构建。

## 怎么确认配好了

1. 输入样本原文与拟稿句“本合同已于2024年3月1日生效，备案已完成。”，比较拟稿句是否能在原文找到生效与备案完成记载，观察结果是原文只有签署日期与材料清单，判定为未获支持，保留缺口。
2. 输入一条含指代的短追问与 chatId，比较问题优化后的指代是否指向正确对象，观察结果是优化结果与样本对象一致才满足条件；未配置问题优化时记录为未启用。
3. 输入空引用列表 [] 与下游承接设计，比较下游是否按空结果分支处理，观察结果是下游给出明确空结果承接才满足条件；不声称虚构规则检索一定返回 []。跨模型库先核标识并排除不符合者，记录实际观察，不执行跨模型检索比较漏召回。
