# B2B平台撮合交易的经营报表与异常复盘：知识库检索与召回

## 这个品类的数据长什么样

B2B平台撮合交易的企业认证资料、询报价单、电子合同与平台结算单，共同支撑经营报表与异常复盘中的检索核对。在线认证与电子合同较多，交易主体、合同状态与结算金额分散在不同文档中，检索时需要同主体、同期间、同字段地比对。资料更新频率为日与每单，检索结果反映的是入库时已建立的索引状态。

## 这些特征在「知识库检索与召回」这一环带来什么约束

知识库搜索节点可关联一个或多个使用相同向量模型的知识库。语义检索依赖向量距离，全文检索依赖关键词命中，混合检索通过 RRF 融合两路结果，结果重排使用 ReRank 模型进行二次排序。引用上限以 token 为单位控制单次搜索引用的内容量，最低相关度仅在语义检索或使用结果重排时生效。问题优化用于指代消除与问题扩展，会在检索前增加一次模型调用。检索本身不承担权限或实体隔离，相似度得分不区分企业身份、授权状态或合同生效与否。空结果以数组形式输出，长度可以为 0。

假设演练样本：材料原文为“供应商甲于2025年3月提交企业认证资料，审核状态为待审核；同期询报价单载明报价有效期至2025年4月30日；电子合同文本标注签署方为供应商甲与采购方乙，签署日期栏为空。”待判定拟稿句为“供应商甲已完成认证，合同已生效。”核对时需比较认证资料中的审核状态字段与拟稿句的“已完成认证”，比较合同签署日期栏与拟稿句的“已生效”。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较对象 |
| --- | --- | --- |
| 关联知识库 | 仅关联使用相同向量模型的一个库 | 跨模型库不可共同关联，先核向量模型标识再排除不符者 |
| 搜索模式 | 语义检索与全文检索各跑一次 | 分别比较自然语言问法与编号类问法的召回差异 |
| 引用上限 | 设为覆盖最长单份结算单全文的 token 量 | 与最短询报价单对比，观察内容是否被截断 |
| 最低相关度 | 暂不启用，先观察原始召回 | 待标注相关与无关样本后再决定是否用于过滤 |
| 问题优化 | 先关闭，用完整问句测试 | 与开启后的补全结果对比，核对主体是否被改错 |
| 结果重排 | 暂不启用 | 待确认候选数量与问题完整度后再评估 |

## 容易做错的三处

1. 把待审核状态当作已完成认证。输入为认证资料中“审核状态为待审核”，比较对象为拟稿句“已完成认证”，两者同主体同字段但取值互斥，属于矛盾。检索结果中出现该资料不代表认证已通过。
2. 把签署方标注当作合同生效。输入为电子合同“签署日期栏为空”，比较对象为拟稿句“合同已生效”，签署、合作达成与合同生效是三个不同事实，缺失生效证据时只能记为待核实。
3. 把报价有效期当作供货期限。输入为询报价单“报价有效期至2025年4月30日”，比较对象为任何关于供货截止时间的表述，两者字段不同，报价有效期不表示供货期限。

## 怎么确认配好了

1. 输入假设样本中的认证资料原文与拟稿句“供应商甲已完成认证”，比较审核状态字段取值与拟稿句表述。当检索命中该资料且审核状态显示为待审核时，拟稿句不获支持；若检索未命中，记录为证据缺口，不判定为否定。
2. 输入假设样本中的电子合同原文与拟稿句“合同已生效”，比较签署日期栏与生效相关字段。当签署日期栏为空且无其他生效记录时，该拟稿句待核实；不得补造授权或生效条款来获得确定答案。
3. 输入一个明确的纸面空结果 `[]`，核对下游设计是否按引用长度为 0 的链路走通。该核对只验证空结果承接方式，不声称任何虚构规则检索一定返回 `[]`。
