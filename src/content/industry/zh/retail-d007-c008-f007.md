# 亚马逊FBA备货运营的经营报表与异常复盘：对话日志与审计

## 这个品类的数据长什么样

FBA备货把库存前置到平台仓，入仓计划、箱唛、库存报告与赔偿申请构成日常文档主线，出错代价集中在断货降权、仓储费增加与索赔失败。对话日志与审计这一环处理的输入是应用下按 chatId 归集的会话记录与按 dataId 定位的单条对话运行详情，输出是可核对的字段与状态，不承担库存判断本身。

数据来源包括 Amazon Seller Central、FBA 库存报告、货代轨迹与 ERP 采购单，这些业务数据是否写入对话记录，取决于实际编排与接口返回，日志存在不等于业务数据已完整留存。

## 这些特征在「对话日志与审计」这一环带来什么约束

会话列表接口按 appId、offset、pageSize 与 source 取数，source=api 只取通过 API 创建的会话。对话运行详情需要 GET 请求携带 appId、chatId、dataId。对话接口在 detail=true 时返回 responseData，非流式结果保存在其中，流式按 event 区分。Token 消耗不直接返回，需设置 detail=true 后手动计算 responseData 里的 tokens。

假设演练样本：某跨境卖家的补货应用收到一条会话，材料原文为「入仓计划 FBA-2025-0417，计划入库 600 件，目的仓为美西仓，创建日期 2025 年 4 月 17 日，状态为草稿，尚未提交平台审核」。同一 chatId 下另有一条记录，原文为「箱唛文件已生成，对应入仓计划 FBA-2025-0417，生成日期 2025 年 4 月 18 日」。待判定的拟稿句为「入仓计划 FBA-2025-0417 已于 4 月 17 日通过平台审核，箱唛已同步至货代」。

判定要点：材料只写状态为草稿且未提交审核，「通过平台审核」未获支持；箱唛生成不等于同步至货代，同步动作需另接系统实现，材料未载明。

## 配置怎么定

| 配置项 | 本页取值或核对方式 | 依据与边界 |
| --- | --- | --- |
| 会话取数范围 | 请求体传 appId、offset、pageSize，source 传 api | 仅取 API 创建的会话，页面会话不进入该列表 |
| 运行详情开关 | 对话请求体设 detail=true，非流式读 responseData | 流式按 event 区分，detail 为本次核对所需 |
| Token 计算起点 | 本次假设试验起点：手动累加 responseData 中 tokens，与提示词与补全之和比较 | 接口不返回实际消耗，起点仅为本次核对设定 |
| 会话身份字段 | 核对 chatId 与 dataId 是否同属目标 appId | 不同入口会话不混算 |
| 交互节点返回 | 需要交互配置时设 detail=true，读 data.interactive 的 type 与 params | 内部运行态字段不返回 |
| 插件输出位置 | 查 responseData 中 moduleType=pluginOutput 的 pluginOutput | 插件默认 detail 模式，无需 chatId |

## 容易做错的三处

1. 把草稿状态读成已审核。假设样本原文写「状态为草稿，尚未提交平台审核」，若拟稿句写「已通过平台审核」，输入是同一入仓计划编号与同一状态字段，比较草稿与已通过审核两个互斥取值，观察到拟稿句与原文不一致即为错误。
2. 把箱唛生成当作已同步货代。原文只写箱唛文件已生成，未写同步动作与接收方，拟稿句的「已同步至货代」在原文中无对应字段，属未获支持。
3. 用相似度分数代替权限或实体过滤。运行详情中 score 只反映召回排序，不构成对目标业务记录的授权，检索不产生授权效果。

## 怎么确认配好了

1. 取假设样本第一条原文，请求运行详情并核对 dataId 对应的 query 与 answer 字段，比较记录中的状态描述是否与「草稿、未提交审核」一致，出现「已通过审核」即判定拟稿句与原文不符。
2. 取假设样本第二条原文，检查记录中是否存在同步动作字段或接收方字段，比较后若两者均未出现，判定「已同步至货代」为未获支持，保留证据缺口。
3. 对同一 chatId 下的会话列表请求，核对返回项的 chatId 与 appId 是否与目标应用一致，比较后若出现其他 appId 的会话，判定取数范围不符，需修正请求参数后重新核对。
