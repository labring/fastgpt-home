# 便利店加盟门店督导的经营报表与异常复盘：HTTP 接口与外部系统

## 这个品类的数据长什么样

加盟督导的数据围绕总部对加盟商执行标准的监督展开。主要来源包括督导APP、POS销售、加盟系统与门店照片，日常文档为巡店表、加盟合同、整改通知和陈列标准。这些材料跨系统分散，经营报表与异常复盘需要把巡店记录、订货核对和整改追踪串起来。数据更新频率为周和月，接口调用以周期汇总为主，不涉及实时交易触发。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向对应地址发送请求，Params 用于路径请求参数，Body 用于请求体，Headers 用于传递特殊信息。URL、Params、Headers、Body 均可通过 `{{}}` 引用全局变量、系统变量和前方节点输出。返回值通过 JSON path 提取，输出类型选择字符串时会将对应 key 的值转为 json 字符串。对话接口使用 APIKey 鉴权，调用 chat/completions 时推荐在请求体传入 body.appId，也支持 Authorization: Bearer <apiKey>-<appId>。chatId 与 responseChatItemId 在测试模式下不存在，调试空值不能当作业务故障。传入的 model、temperature 等字段无效，由编排决定。detail=true 时中间值保存在 responseData 中。

假设演练样本：某加盟督导在纸面核对中持有一份巡店表原文，内容为“2024年3月第2周，门店A，陈列标准检查项：端架商品与总部陈列图一致，检查结果：待整改；整改通知编号：ZL-2024-031，整改期限：2024年3月20日；加盟合同编号：JM-2023-088，合同有效期至2025年12月31日。”拟交接请求为“将门店A的整改通知状态更新为已完成，并同步至加盟系统”。该请求缺少整改完成确认材料，待判定。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 核对方法 |
| --- | --- | --- |
| 请求地址 | 外部接口文档给出的地址 | 核对地址与方法是否与接口契约一致 |
| Params | 按接口文档填写路径参数 | 逐项对照接口文档的参数名与值 |
| Headers | Authorization 使用 Bearer 注入 | 核对鉴权凭证通过安全配置传入 |
| Body | 按 JSON 结构填写请求体 | 核对字段与外部接口契约一致 |
| 变量引用 | 引用全局变量或前方节点输出 | 核对实际传入值与来源节点输出 |
| 返回值提取 | 按 JSON path 配置 key | 核对提取路径与响应结构对应 |

## 容易做错的三处

1. 把 chatId 在测试模式下的空值当作业务故障。检查方式：输入测试模式请求，比较 chatId 是否存在，观察返回是否因测试模式缺少该字段。
2. 在 Body 中引用字符串变量时未加引号，导致 JSON 解析异常。检查方式：输入含字符串变量的 Body，比较加引号与不加引号的解析结果，观察字段值类型是否变化。
3. 将整改通知的“待整改”状态直接当作“已完成”同步至加盟系统。检查方式：输入巡店表原文与拟交接请求，比较整改完成确认材料是否存在，观察请求是否具备执行条件。

## 怎么确认配好了

- 验证一：输入假设演练样本中的巡店表原文与拟交接请求，比较请求中“整改通知状态更新为已完成”与原文“检查结果：待整改”是否一致，观察是否缺少整改完成确认材料。若缺少，该请求不具备执行条件。

- 验证二：输入测试模式下的对话请求，比较 chatId 与 responseChatItemId 是否存在，观察返回中这两个字段是否缺失。缺失属于测试模式下的正常现象，不构成业务故障。

- 验证三：输入含字符串变量与数值变量的 Body，比较引用时是否分别加引号与不加引号，观察最终解析结果中字段值类型是否与预期一致。字符串变量未加引号时解析结果不符合预期。
