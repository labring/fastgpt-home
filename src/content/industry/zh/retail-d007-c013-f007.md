# 便利店加盟门店督导的经营报表与异常复盘：对话日志与审计

## 这个品类的数据长什么样

在便利店加盟门店督导的经营报表与异常复盘中，本页说明FastGPT的对话日志与审计如何衔接资料。核对资料实际支持的范围及其引用。所用场景为自拟文字测试。

## 这些特征在「对话日志与审计」这一环带来什么约束

门店督导复盘可先定位哪次对话解释了哪份巡店资料。自拟输入只有陈列标准与整改通知的问答，没有后续现场核查凭证。chatId可结合门店和材料身份回看目标交流，不表示照片、整改执行或全部督导过程都已保存在日志。标准解释、发现问题和整改通过需要各自依据，不能从一次答复结束推定门店已经合格。

## 配置怎么定

| 核对对象 | 本题自拟记录 | 应查证据 |
| --- | --- | --- |
| 目标会话 | 本店巡店与标准解释 | chatId及来源对象对应 |
| 错店混合 | 其他门店相似问题 | 核输入和返回后移出 |
| 复核缺口 | 有通知无现场结果 | 未推定整改已通过 |
| 详情契约 | detail请求和responseData | 以实际返回范围为准 |
| 业务审查 | 关闭处罚及留存另落实 | 日志未替代督导完成 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `对话身份` | 将目标会话与资料身份对应。 |
| `运行详情` | 按接口契约查看运行详情。 |
| `字段含义` | 以实际返回字段为准。 |
| `调试与正式调用` | 核调试与正式调用的输入差别。 |
| `业务审计分工` | 对账及留存需方案另行落实。 |

## 容易做错的三处

若不同门店的相似陈列问题被合并，应排查会话身份、输入原文及返回所指门店，不能靠问题相似借用结果。若要求证明整改完成，但responseData没有复核记录，应登记业务缺证；按官方契约设置detail并检查实际返回，不由参数已设置推定细节齐全，也不从未返回字段猜现场状态。 若日志可见就宣称督导资料留存已满足要求，应将实际可回读的标准、照片和复核范围与项目留存安排逐项对照，缺来源仍列缺口；可见会话不替代完整审计方案。

## 怎么确认配好了

验收保留本店对话、标准版本、通知范围与复核缺口，补对应现场依据后再核解释怎样变化。调试及正式调用分别对照输入、历史与返回，不将测试身份补成正式会话。整改关闭、处罚、对账留存及合规审计需完整业务方案另行落实；本次日志回看只支持检查交流证据，不证明这些业务动作或正式督导审查已经完成。
