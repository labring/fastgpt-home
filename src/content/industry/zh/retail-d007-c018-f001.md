# 区域经销商库存补货的经营报表与异常复盘：HTTP 接口与外部系统

## 这个品类的数据长什么样

区域经销商库存补货属于日常滚动订单，数据来源包括经销商ERP、品牌订货系统、仓库库存与销售回款，更新频率为周或月。日常文档有补货申请、库存周转表、出库单、回款计划。经营报表与异常复盘需要把这些文档中的字段与外部系统返回值逐项对齐。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向外部地址发送请求，Params、Headers、Body 三处均可用 `{{}}` 引用全局变量、系统变量或前方节点输出。地址同样可引用变量。返回值通过 JSON path 提取，输出类型选字符串时会把对应键值转成 json 字符串。系统变量中 chatId 与 responseChatItemId 在测试模式下不存在，调试时出现的空值属于该模式的已知状态。

假设演练样本：某品牌渠道经理收到一份补货申请，原文为“申请方：华东一区经销商；补货对象：A 型号；申请数量：200 件；申请日期：2025 年 3 月 10 日；授权状态：待品牌渠道经理审核”。同时有一条拟稿句“该补货申请已获批准，可安排出库”。核对时比较申请原文的授权状态与拟稿句的批准表述，原文只载明待审核，拟稿句的批准结论未获支持。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 请求地址 | 外部系统文档给出的补货查询地址 | 按接口文档填写，与文档地址逐字符比较 |
| 请求方法 | POST | 与接口文档声明的方法比较，不一致时核对文档 |
| Headers 鉴权 | Authorization 引用注入的凭证变量 | 与外部系统凭证配置比较，不写入公开样例 |
| Body 结构 | 包含申请方、对象、数量、日期字段的 JSON | 与补货申请原文逐字段比较 |
| 返回值提取 | 提取授权状态字段的 JSON path | 与原文授权状态比较，确认是否一致 |
| 输出类型 | 字符串 | 与下游文本加工所需格式比较 |

上述起点为本次假设试验的设定，不属官方默认值。

## 容易做错的三处

1. 把补货申请原文的“待审核”直接写成“已批准”。错误在于把待审核状态当作批准结论，输入是申请原文，比较对象是授权状态字段，可观察结果是拟稿句出现批准表述而原文无对应依据。
2. 把测试模式下 chatId 或 responseChatItemId 的空值当成业务故障。错误在于混淆调试身份字段缺失与真实请求异常，输入是测试模式请求，比较对象是系统变量说明，可观察结果是排查方向偏离接口契约。
3. 把 JSON path 提取到的值直接当作已核验的业务事实。错误在于跳过与补货申请原文的比对，输入是接口返回值，比较对象是申请原文对应字段，可观察结果是报表数值与文档不一致却未被发现。

## 怎么确认配好了

1. 输入假设样本的补货申请原文与拟稿句，比较原文授权状态“待审核”与拟稿句“已获批准”，预期现象是识别出批准结论未获支持，保留证据缺口。
2. 输入测试模式下的请求，比较 chatId 与 responseChatItemId 的存在情况与系统变量说明，预期现象是判定为空值属测试模式已知状态，不列为业务故障。
3. 输入接口返回值与补货申请原文，比较提取字段与原文对应字段，预期现象是逐字段列出差异，未载明项标注为待核实。
