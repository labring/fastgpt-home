# 即时零售门店履约的经营报表与异常复盘：HTTP 接口与外部系统

## 这个品类的数据长什么样

即时零售门店履约按分钟处理线上订单，与周期性盘库的节奏不同。主要数据来自抖音即时零售、美团或京东到家后台、门店库存与骑手轨迹，更新频率为分钟级、每单。日常文档包括即时订单、拣货清单、缺货报备、配送异常单。经营报表与异常复盘要把这些文档中的字段，经 HTTP 模块送到外部系统，或从外部系统取回状态。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向对应地址发送请求，Params 为路径请求参数，Body 为请求体，Headers 为请求头，三处均可通过 `{{}}` 引用变量。变量来自全局变量、系统变量、前方节点输出。系统变量含 appId、chatId、responseChatItemId、variables、cTime、histories；chatId 与 responseChatItemId 在测试模式下不存在。返回值通过 JSON path 语法提取，输出类型选字符串时会把对应 key 的值转成 json 字符串。对话接口用 APIKey 鉴权，推荐在请求体传 `body.appId`，也支持 `Authorization: Bearer <apiKey>-<appId>`；appId 优先级为 `body.appId`、`<apiKey>-<appId>`、apikey 关联的 appId。传入的 model、temperature 等字段无效。detail=true 时 `responseData` 保存中间值，stream 模式通过 event 区分。交互节点返回的 interactive 只含 type 和 params，内部运行态字段不返回。

假设演练样本：某商超到家门店 2025 年 6 月 3 日 14 时 20 分，拣货员提交缺货报备单，单号 QH-0603-014，对象为门店 A 的常温奶 250ml，状态为已提交待值班主管审核。外部系统回传字段 status 值为 pending。拟交接句为“该缺货报备已审核通过，可回传平台”。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 请求地址 | 外部系统文档给出的缺货报备查询地址 | 与文档给出的地址逐字比较 |
| 请求方法 | 文档标注的 GET 或 POST | 与文档标注方法比较 |
| Headers 鉴权 | `Authorization: Bearer {{token}}` | 与文档鉴权说明比较，凭证不写入公开样例 |
| Body 字段 | 单号 QH-0603-014 与门店标识 | 与外部接口契约字段名比较 |
| 返回值提取 | `$.status` | 与响应示例中字段路径比较 |
| 输出类型 | 字符串 | 与下游文本加工需要比较 |

以上数值为本次假设试验起点，非官方默认值。

## 容易做错的三处

1. 把 status 为 pending 当成审核通过。输入为样本回传的 pending，比较对象为“已审核通过”这一状态描述，观察到的结果是两者不一致，判定为待核实。
2. 把测试模式下 chatId 与 responseChatItemId 不存在当成业务故障。输入为测试模式请求，比较对象为文档说明的测试模式字段缺失，观察到的结果是字段为空，判定为调试环境现象。
3. 把交互节点返回的展示配置当成完整运行态。输入为 interactive 仅含 type 与 params，比较对象为文档说明的内部字段不返回，观察到的结果是缺少 entryNodeIds 等字段，判定为展示配置。

## 怎么确认配好了

1. 输入样本原文“单号 QH-0603-014，状态已提交待值班主管审核”，以及拟交接句“该缺货报备已审核通过”。比较拟交接句与原文的状态字段，原文只写已提交待审核，未写审核通过。观察到拟交接句与原文不一致时，判定为未获支持，需保留证据缺口。
2. 输入样本回传的 status 值 pending，比较该值与“审核通过”的取值是否互斥。观察到 pending 与审核通过不是同一字段的互斥取值时，判定为待核实，不写成否定。
3. 输入一条本次假设的查询请求，请求体含单号 QH-0603-014，比较返回值提取路径 `$.status` 与响应中实际字段。观察到响应中无该字段时，记录为缺失，不推断系统报错原因；观察到字段存在时，记录实际取值。
