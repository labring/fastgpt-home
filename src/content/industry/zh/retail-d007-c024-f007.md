# 品牌商场专柜运营的经营报表与异常复盘：对话日志与审计

## 这个品类的数据长什么样

商场专柜接受商场统一收银与扣点结算，销售数据先进入商场 POS，再与品牌 ERP、财务系统核对。日更与月结并存，联营扣点合同、商场活动函、销售小票、月结对账单是异常复盘时反复调用的材料。对话日志与审计环节要面对的是：同一天销售可能分散在商场 POS 与品牌 ERP 两处，扣点费用与活动资源在月结时才集中暴露，日志能否支撑追溯取决于接口实际返回的字段。

## 这些特征在「对话日志与审计」这一环带来什么约束

对话接口以 appId 定位应用，chatId 标识一个会话，dataId 标识会话下某条对话。detail=true 时返回 responseData，其中含模块名、模型、tokens、runningTime 等；detail=false 时不返回中间值。插件应用默认 detail 模式，无需 chatId 与 messages，通过 variables 传输入，从 moduleType=pluginOutput 的元素取 pluginOutput。交互节点返回的 interactive 只含 type 与 params，entryNodeIds、memoryEdges、nodeOutputs、nodeResponseId 不返回。日志存在不等于完成合规审计，对账、留存与合规要求由完整业务方案另行落实。

假设演练样本：某专柜 3 月 1 日至 3 月 31 日的联营扣点合同写明扣点比例为 18%，商场活动函载明 3 月 15 日至 3 月 17 日促销期间扣点按 15% 执行。月结对账单列示 3 月 15 日销售 12000 元、3 月 16 日销售 8000 元，均按 18% 计扣。拟稿句为“3 月 15 日至 17 日活动期扣点已按 15% 结算”。该拟稿句与活动函、对账单存在同期间同字段的取值差异，需先核对原始小票与结算明细，未获支持的部分保留为待核实。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| appId | 假设填入本次专柜报表应用的 appId | 与获取会话列表返回的 appId 比较，确认同一应用 |
| chatId | 假设填入本次复盘会话的 chatId | 与 getHistories 返回的 chatId 比较，确认同一会话 |
| dataId | 假设填入待核对对话的 dataId | 与 getPaginationRecords 返回的 dataId 比较 |
| detail | 假设设为 true | 与 detail=false 的返回比较，确认是否含 responseData |
| source | 假设设为 api | 与页面来源会话比较，确认仅取 API 创建会话 |
| loadCustomFeedbacks | 假设设为 true | 与不传该参数时的返回比较，确认自定义反馈是否读出 |

以上数值为本次假设试验起点，非官方默认值。

## 容易做错的三处

1. 把 detail=false 的返回当作完整运行详情。输入为一次 detail=false 的请求，比较返回中是否出现 responseData，观察结果为未出现，则不能据此推断模块运行状态。
2. 把 interactive 的展示配置当作内部运行态。输入为一次命中交互节点的响应，比较返回中是否含 entryNodeIds、memoryEdges、nodeOutputs、nodeResponseId，观察结果为未返回，则不能据此推断这些字段已留存。
3. 把日志存在当作对账或合规审计完成。输入为一条已留存对话，比较其字段是否覆盖扣点比例、活动期间、结算金额，观察结果为未覆盖，则对账结论仍待核实。

## 怎么确认配好了

1. 输入假设样本中的拟稿句与活动函、对账单原文，比较三者的主体、期间、扣点比例字段，观察结果为活动函 15% 与对账单 18% 在同一期间同一字段上取值不同，则该拟稿句未获支持。
2. 输入一次 detail=true 的请求，比较 responseData 中是否含 moduleName、model、tokens、runningTime，观察结果为含这些字段，则运行详情可读出；未含则记录缺口。
3. 输入一次插件应用的请求，比较返回中 moduleType=pluginOutput 元素的 pluginOutput，观察结果为可取出插件输出；未返回则记录缺口，不推断插件未运行。
