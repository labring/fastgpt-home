# 品牌自播直播间运营的经营报表与异常复盘：HTTP 接口与外部系统

## 这个品类的数据长什么样

品牌自播由品牌自己承担话术、库存和售后，直播脚本、商品讲解卡、排班表与直播复盘是日常文档。经营报表与异常复盘环节要把每场、每小时的成交明细与流量转化整理成可核对记录。品牌自播的关键差别在于主体是品牌团队，场控、主播、投流专员共同产生数据，出错后果包括虚假宣传投诉、库存拍超与转化下滑。这些材料需要在外部系统之间传递时，HTTP 接口承担调用职责，接口本身不判断业务授权。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向对应地址发送请求，Params 为路径请求参数，Body 为请求体，Headers 为请求头。自定义变量可以接收前方节点输出，三种数据均可通过 `{{}}` 引用变量，URL 也可引用变量。变量来自全局变量、系统变量与前方节点输出。系统变量包括 appId、chatId、responseChatItemId、variables、cTime 与 histories，其中 chatId 与 responseChatItemId 在测试模式下不存在，调试空值不构成业务故障。返回值通过 JSON path 提取，输出类型选择字符串时会把对应 key 的值转成 json 字符串。对话接口使用 APIKey 鉴权，调用 chat/completions 时推荐在请求体传入 body.appId，也支持 Authorization: Bearer 形式。传入的 model、temperature 等字段无效，由编排决定。detail=true 可返回中间值，非 stream 模式结果保存在 responseData。插件类型应用默认 detail 模式，无需 chatId 与 messages，通过 variables 传输入，通过 pluginOutput 取输出。

假设演练样本：某品牌自播团队在 2025 年 6 月 12 日一场直播后，将成交明细与流量转化整理为复盘材料。材料原文为：“本场直播时段 20:00 至 23:00，成交明细由场控导出，商品讲解卡版本为当日排品表所附版本。复盘结论待运营负责人确认后归档。”一条待判定的交接请求为：“请将本场复盘结论通过 HTTP 接口同步至外部报表系统，并标记为已确认。”按原文，复盘结论处于待确认状态，该请求要求的“已确认”标记缺少依据，需要运营负责人完成确认后才具备相应状态。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 请求地址 | 使用外部接口文档给出的地址 | 地址可引用变量，核对实际传入值是否与文档一致 |
| 请求方法 | 按外部接口文档选择 | 与文档声明的方法逐项比较 |
| Headers 鉴权 | 通过安全配置注入凭证 | 不写入公开样例，核对注入值非空 |
| Body 结构 | 按外部接口契约组织 JSON | 仅在相应请求类型下生效，核对字段与契约 |
| 变量引用 | 引用全局变量与前方节点输出 | 逐项核对实际传入值，确认与来源一致 |
| 返回值提取 | 按 JSON path 配置 key | 输出类型选择字符串时转成 json 字符串 |

## 容易做错的三处

1. 把待确认状态当作已确认。样本中复盘结论待运营负责人确认，交接请求要求标记已确认。输入是材料原文与请求，比较对象是原文状态与请求标记，可观察结果是两者不一致。若直接执行标记，状态依据缺失。
2. 把测试模式空值当作业务故障。chatId 与 responseChatItemId 在测试模式下不存在。输入是测试模式调用，比较对象是文档说明与观察到的空值，可观察结果是空值符合文档描述。若据此判定接口异常，结论超出文档。
3. 把插件调用当作对话调用。插件类型应用无需 chatId 与 messages，通过 variables 传输入。输入是插件请求，比较对象是文档规定的参数集合与请求实际参数，可观察结果是多余参数出现。若沿用对话参数结构，输入传递可能不符契约。

## 怎么确认配好了

1. 针对样本原文，输入材料原文与交接请求，比较原文状态与请求标记，若两者不一致则判定请求缺少依据，记录待确认状态。预期不声称已实测。
2. 针对测试模式，输入一次测试模式调用，比较文档说明与观察到的 chatId、responseChatItemId 值，若为空则符合文档描述，不作为故障。预期保留观察记录。
3. 针对插件调用，输入一次插件请求，比较文档规定的参数集合与请求实际参数，若出现 chatId 或 messages 则不符契约，需按 variables 传递输入。预期以文档为准核对。
