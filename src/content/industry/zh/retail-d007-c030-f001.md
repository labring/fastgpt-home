# 商超供应商进场结算的经营报表与异常复盘：HTTP 接口与外部系统

## 这个品类的数据长什么样
供应商进场结算以购销或代销账款为主，不一定有驻场经营。主要数据来自 ERP 采购、供应商门户、POS 销售和财务系统，更新频率为周或月。日常文档包括采购合同、送货验收单、返利协议和对账单。经营报表与异常复盘需要把这些文档中的字段与外部接口返回的数据逐项对齐。核对验收数量、计算返利扣点、处理退货差异是最耗时的环节，HTTP 接口承担从外部系统取数与回写状态的任务。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
HTTP 模块向指定地址发送请求，Params 用于路径参数，Body 用于 POST/PUT 请求体，Headers 传递鉴权等信息。变量来自全局变量、系统变量和前方节点输出，通过 `{{key}}` 引用。返回值通过 JSON path 提取，出参可选择字符串类型并自动格式化。系统变量中 chatId 与 responseChatItemId 在测试模式下不存在，不把调试空值当成业务故障。对话接口的 model、temperature 等参数由编排决定，传入无效。detail=true 时可在 responseData 中查看模块状态与完整结果。检索与相似度不承担权限或实体隔离职责，接口调用不构成业务授权。

假设演练样本：某商超与供应商签订采购合同，约定月度对账。送货验收单记录 2025 年 3 月 5 日到货 200 箱，验收合格 198 箱，破损 2 箱。对账单草稿写“本月验收数量 200 箱，返利按 3% 扣点”。拟提交的接口请求为向供应商门户发送 POST，Body 含 `{"period":"2025-03","acceptedQty":198}`，Headers 含 Authorization 占位符。该请求处于待审核状态，尚未获得结算负责人授权。

## 配置怎么定
围绕上述样本，只列出与本页任务相关的设置或核对项。

| 项目 | 本次假设起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 请求地址 | 供应商门户对账接口地址 | 按外部接口文档确定，与合同约定的对账周期比对 |
| 请求方法 | POST | 与门户文档声明的方法一致，方法不符时记录差异 |
| Headers 鉴权 | Authorization 占位符 | 凭证通过安全配置注入，与门户要求的鉴权方式比对 |
| Body 字段 | period、acceptedQty | 与对账单草稿的期间和验收数量逐项比对 |
| 返回值提取 | 按 JSON path 提取对账状态 | 与门户返回结构比对，提取失败时记录实际响应 |
| 变量引用 | 引用前方节点输出的验收数量 | 与送货验收单原文比对，确认传入值一致 |

## 容易做错的三处
1. 把对账单草稿中的“验收数量 200 箱”直接当作已确认数据写入 Body。输入是草稿原文，比较对象是送货验收单的合格数量 198 箱，可观察结果是两者不一致时仍提交。
2. 把待审核的接口请求当作已获授权执行。输入是拟提交请求，比较对象是授权状态记录，可观察结果是未获批准即发送。
3. 把测试模式下 chatId 为空当作业务故障。输入是测试模式请求，比较对象是文档说明的测试模式行为，可观察结果是误报会话异常。

## 怎么确认配好了
1. 输入假设样本的对账单草稿与送货验收单，比较验收数量字段，观察 Body 中 acceptedQty 是否与合格数量 198 一致。预期为一致；不一致时记录差异，不判定为已确认。
2. 输入拟提交的接口请求与授权状态记录，比较请求是否处于已批准状态，观察是否在未获授权时发送。预期为授权后才发送；待审核状态记录为未获授权。
3. 输入测试模式下的请求，比较 chatId 与 responseChatItemId 是否为空，观察是否将空值报告为业务故障。预期为识别测试模式行为；空值不构成业务故障证据。
