# 大卖场生鲜联营柜台的经营报表与异常复盘：HTTP 接口与外部系统

## 这个品类的数据长什么样
大卖场生鲜联营柜台常由供应商驻场经营并按销售分成，日销售报表、损耗单、食品进货查验记录与联营合同共同构成核对基础。POS 称重销售与供应商送货单分属两套记录，日销售报表与损耗单按日或每批更新，核对时需要把销售、送货、损耗、查验凭证放在同一主体、同一期间、同一字段下比较。HTTP 模块在这一环承担向外部系统取数或送数的动作，请求地址与方法按外部接口文档选择，地址可通过 `{{}}` 引用变量。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
HTTP 模块可重复添加、手动配置、触发执行。Params 为路径请求参数，GET 请求中居多；Body 为请求体，POST/PUT 请求中居多；Headers 用于传递特殊信息。三者均可用 `{{key}}` 引用变量，URL 同样可以。变量来自全局变量、系统变量、前方节点输出。系统变量含 appId、chatId、responseChatItemId、variables、cTime、histories，其中 histories 默认最多取 10 条且无法修改长度。chatId 与 responseChatItemId 在测试模式下不存在，调试时取到空值属于测试模式特性，不构成业务故障。返回值通过 JSON path 语法提取，输出类型选择字符串时会把对应 key 的值转成 json 字符串。

假设演练样本：某联营供应商驻场柜台的日销售报表原文为「2025年3月10日，A 供应商在 B 门店生鲜联营柜台销售 1200 元，损耗 30 元，当日进货查验记录已登记」。拟提交的交接请求为「将 2025年3月10日 A 供应商销售 1200 元、损耗 30 元推送至外部对账系统」。该请求涉及主体、对象、期间与金额，但未载明推送授权、目标系统字段契约与生效确认，属于待核实状态。

## 配置怎么定
| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 请求地址 | 外部对账系统提供的对账接口地址 | 按外部接口文档选择，与文档给出的路径逐字比较 |
| 请求方法 | POST | 该请求含结构化数据，与文档中 POST 用于请求体的说明比较 |
| Headers 鉴权 | `Authorization: Bearer {{token}}` | 按文档示例引入变量，核对凭证是否由安全配置注入 |
| Body 结构 | `{"date":"{{date}}","supplier":"{{supplier}}","sales":{{sales}},"loss":{{loss}}}` | 按文档 Body 示例核对字符串加引号、数值不加引号 |
| 出参提取 | `$.data.result` | 按文档 JSON path 提取示例核对返回结构 |
| 输出类型 | 字符串 | 按文档自动格式化说明，将提取值转为 json 字符串 |

## 容易做错的三处
1. 把测试模式下 chatId 与 responseChatItemId 不存在当成业务故障。检查方式：输入测试模式请求，比较返回中这两个字段是否缺失，缺失属于文档说明的测试模式特性。
2. 在 Body 中引用字符串变量时未加引号。检查方式：输入含 `{{supplier}}` 的 Body，比较解析后该字段是否仍为字符串，未加引号会导致结构解析异常。
3. 把检索或表单提交当成授权执行。检查方式：输入上述拟提交的交接请求，比较是否附带推送授权与目标系统字段契约，未载明时记录为待核实，不判定为已获授权。

## 怎么确认配好了
1. 输入假设样本中的日销售报表原文与拟提交请求，比较请求 Body 中 date、supplier、sales、loss 四个字段是否与原文数值一致，一致才满足条件。
2. 输入测试模式请求，比较返回中 chatId 与 responseChatItemId 是否缺失，缺失符合文档说明，不记为故障。
3. 输入含字符串变量的 Body 声明，比较解析结果中该字段是否保持字符串类型，保持字符串才满足条件；解析异常时记录实际观察，不推断具体错误码。
