# 大卖场生鲜联营柜台的经营报表与异常复盘：对话日志与审计

## 这个品类的数据长什么样
大卖场生鲜联营柜台常由供应商驻场经营并按销售分成，因此经营报表与异常复盘同时牵涉商超生鲜部、联营供应商和门店店长三类主体。日销售报表、损耗单、食品进货查验记录与联营合同分属不同来源，销售数据来自POS系统，送货与损耗信息来自供应商送货单和门店盘点。核对称重销售、处理损耗分摊、查验进货凭证是日常最耗时的环节，食安处罚、毛利争议与顾客索赔是出错后的主要后果。这些材料按日或按批形成，对话日志与审计需要把某一轮问答准确挂到对应的会话与业务记录上。

## 这些特征在「对话日志与审计」这一环带来什么约束
对话身份依靠 chatId 区分。chatId 为非空字符串时，系统从数据库取该会话，并以 messages 数组最后一个内容作为用户问题，其余 message 被忽略；chatId 不传时，完全依靠传入的 messages 构建上下文，不调用 FastGPT 的上下文功能。responseChatItemId 传入后作为本次响应消息的 ID 存入数据库，需在当前 chatId 下唯一。运行详情需要设置 detail，非流式结果保存在 responseData 中，流式通过 event 区分；detail 为 true 时 responseData 含模块名、tokens、quoteList、completeMessages 等，不同版本具体值可能有差异。日志存在只说明接口返回了这些字段，对账、留存与合规审计要求由完整业务方案另行落实。

假设演练样本：某门店生鲜部保存一份联营合同摘录，原文为“甲方为某商超门店，乙方为某联营供应商，柜台为生鲜联营柜台，结算按当月POS销售金额与约定分成比例执行，损耗分摊以门店盘点单为准”。另有一份日销售报表摘录，原文为“2025年3月1日至3月31日，该柜台POS销售金额为若干，损耗单编号为若干”。一条待判定的拟稿句为“本月损耗已由供应商全额承担，无需门店分摊”。

## 配置怎么定
下表只列与本页功能及主任务相关的官方已说明设置或实施核对项。数值一栏为本次假设试验起点，说明选择理由及比较对象。

| 配置项 | 本次假设起点 | 核对与比较方式 |
| --- | --- | --- |
| chatId | 使用该柜台当轮对话的会话 ID | 与业务记录中的会话标识比对，确认同一会话 |
| responseChatItemId | 每轮响应指定唯一值 | 在同一 chatId 下检查是否重复 |
| detail | 设为 true 以取得运行详情 | 与仅取最终回答的调用比较，确认 responseData 存在 |
| stream | 按调用方式选择 | 流式看 event，非流式看 responseData |
| variables | 传入 uid、name 等模块变量 | 与模块输入框中的 [key] 对照 |
| source | 取 api 以限定 API 创建的会话 | 与页面会话列表区分 |

## 容易做错的三处
1. 把不同 chatId 的会话合并计算。输入为两个不同 chatId 的会话记录，比较对象是业务记录中的会话标识，可观察结果是同一柜台的两轮问答被归入同一会话。
2. 把未返回字段当作已留存。输入为 detail 为 false 的响应，比较对象是 responseData 是否存在，可观察结果是运行详情缺失却被写成已审计。
3. 把检索命中当作授权。输入为一次知识库检索结果，比较对象是授权边界，可观察结果是检索返回了内容却被当成已获批准执行。

## 怎么确认配好了
1. 取上述假设演练样本中的合同摘录与日销售报表摘录，输入为两份材料原文及拟稿句“本月损耗已由供应商全额承担，无需门店分摊”。比较对象是合同摘录中损耗分摊以门店盘点单为准的表述。可观察结果是拟稿句与原文不一致时判定为未获支持，需保留证据缺口。
2. 取同一 chatId 下的两轮请求，输入为两次调用记录。比较对象是 responseChatItemId 是否重复。可观察结果是重复时该响应 ID 不满足唯一要求。
3. 取 detail 为 true 的响应，输入为 responseData。比较对象是其中是否含 quoteList、completeMessages 等字段。可观察结果是字段缺失时记录为未返回，不推定已完整留存。
