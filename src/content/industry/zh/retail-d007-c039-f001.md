# 天猫旗舰店日常运营的经营报表与异常复盘：HTTP 接口与外部系统

## 这个品类的数据长什么样

天猫旗舰店的经营报表与异常复盘，素材来自天猫商家后台、ERP订单表、客服聊天记录，日常文档包括商品发布页、品牌授权书、发货承诺记录和售后工单。与京东POP店相比，天猫旗舰店更强调品牌授权、旗舰店身份和天猫积分赔付规则，这一差别直接影响接口取数的字段口径：同一笔订单在授权状态、发货承诺和赔付记录上，可能对应不同文档，接口请求需要明确取哪一份。数据按日、按单更新，接口核对以单条记录为最小单位。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向指定地址发送请求，Params 用于路径参数，Body 用于 POST/PUT 请求体，Headers 用于请求头，三者均可用 `{{}}` 引用全局变量、系统变量和前方节点输出。返回值通过 JSON path 提取，输出类型选字符串时会把对应值转成 json 字符串。系统变量中 chatId 与 responseChatItemId 在测试模式下不存在，调试时取到空值属于预期现象，不能据此判定业务故障。对话接口传入的 model、temperature 等字段无效，由编排决定；需要 token 消耗时设置 detail=true 并手动计算 responseData 中的 tokens。检索或表单只负责收集与返回数据，业务授权、审批、数据库写入和外部同步需要另行实现的系统承担。

假设演练样本：一份待核对的发货承诺记录原文为“订单号 A1001，商品为某品牌旗舰店主推款，承诺 48 小时内发货，当前状态为已发货，物流单号已回传”。一条待判定的接口请求拟稿为：以该订单号查询售后工单，请求体写入 `{"orderId":"A1001","action":"get"}`，并在 Headers 中引用 `Authorization` 变量。该请求是否具备对应该订单的查询范围，需要与授权材料逐项比对，样本本身不构成授权结论。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较方法 |
| --- | --- | --- |
| 请求地址 | 外部接口文档给出的订单查询地址 | 与文档地址逐字符比对，地址中变量引用核对实际传入值 |
| 请求方法 | POST | 与接口文档标注的方法比对，方法不一致时以文档为准 |
| Headers 鉴权 | 引用 `Authorization` 变量 | 核对变量来源为安全配置，不写入公开样例 |
| Body 结构 | 含 orderId 与 action 两个键 | 与接口契约逐键比对，缺失键或类型不符即记录差异 |
| 返回值提取 | 按 JSON path 配置 key | 与接口响应示例比对，观察提取结果是否为预期字段 |
| 输出类型 | 字符串 | 与下游节点所需类型比对，类型不一致时调整提取方式 |

## 容易做错的三处

1. 把测试模式下 chatId、responseChatItemId 的空值当成业务数据缺失。检查方式：输入为测试模式请求，比较系统变量说明中“测试模式下不存在”的条件，观察返回值中该字段是否为空；为空属于文档已说明的情况，不构成业务异常。
2. 把接口返回的相似度或检索结果当成权限判定。检查方式：输入为一条只包含订单号 A1001 的查询请求，比较授权材料中该订单的可查范围，观察返回记录是否落在该范围内；相似度分值与权限无关，越界记录需要另行核实授权来源。
3. 把表单收集到的值当作已完成的业务动作。检查方式：输入为拟稿请求中的 `{"orderId":"A1001","action":"get"}`，比较该请求是否携带授权依据，观察是否产生数据库写入或外部同步；未携带授权依据时，该请求只处于待核实状态。

## 怎么确认配好了

1. 输入为假设样本中的发货承诺记录原文与拟稿请求，比较请求体键名与接口契约，观察 orderId、action 是否与契约一致；一致时提取结果可进入下一步核对，不一致时记录差异字段。
2. 输入为假设样本中的订单号 A1001，比较授权材料中该订单的可查范围，观察返回记录是否全部落在范围内；范围外记录保留为待核实，不据此判定查询成功或失败。
3. 输入为 detail=true、stream=false 的请求，比较返回结构中 responseData 的模块项，观察是否包含所需节点响应；未包含时记录缺口，不推断具体报错原因。
