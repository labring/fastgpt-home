# 平台多店铺矩阵管理的经营报表与异常复盘：HTTP 接口与外部系统

## 这个品类的数据长什么样

平台多店铺矩阵管理通常同时面对多个平台商家后台、ERP 渠道价、品牌防伪系统与经销商报表。与单店广告投放相比，这类品类更关注跨店授权与价格秩序。日常文档包括店铺授权清单、价格管控表、窜货投诉单与月度销售报表，数据更新频率为日与月。经营报表与异常复盘环节需要把上述材料对齐后判断某条记录是否处于有效授权状态。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向对应地址发送请求，Params 用于路径参数，Headers 用于请求头，Body 在特定请求类型下生效。三种数据均可通过 `{{}}` 引用变量，URL 同样可以引用。变量来自全局变量、系统变量与前方节点输出。返回值通过 JSON path 提取，出参可选择字符串类型并自动格式化为 JSON 字符串。对话接口使用 APIKey 鉴权，调用 `chat/completions` 时推荐在请求体传入 `body.appId`。`chatId` 与 `responseChatItemId` 在测试模式下不存在，调试空值不代表业务故障。传入的 `model`、`temperature` 等字段由编排决定，不随 API 参数改变。

假设演练样本：材料原文为“店铺授权清单第 12 行：主体 A 授权店铺 S 销售品牌 B 产品，授权有效范围 2025-01-01 至 2025-06-30；价格管控表第 8 行：店铺 S 对品牌 B 产品标价与渠道价一致；窜货投诉单第 3 条：投诉对象为店铺 S，投诉日期 2025-04-10，状态为待核实。”待判定拟稿句为“店铺 S 在 2025-04-10 处于品牌 B 有效授权范围内”。该句需要与授权清单的有效范围逐项比对，投诉单状态为待核实，不构成对授权状态的否定。

## 配置怎么定

| 核对项 | 本页样本对应设置 | 比较方式 |
| --- | --- | --- |
| 请求地址 | 按外部接口文档选择，地址可引用已提供变量 | 与外部接口文档所列地址逐字符比对 |
| Params 与 Headers | 分别填写路径参数与请求头，鉴权凭证通过安全配置注入 | 与外部接口契约所列键名比对 |
| Body | 仅在相应请求类型下使用，核对 JSON 结构 | 与外部接口契约字段逐项比对 |
| 变量引用 | 引用全局变量、系统变量或前方节点输出 | 与变量来源清单逐项比对实际传入值 |
| 返回值提取 | 按 JSON path 提取所需字段，输出类型选择字符串 | 与接口响应示例结构比对 |
| 调试身份字段 | 测试模式下 `chatId` 与 `responseChatItemId` 不存在 | 与正式调用记录比对，区分调试空值 |

## 容易做错的三处

1. 把检索结果或表单填写当成授权执行。输入为样本中店铺 S 的授权清单记录，比较对象为授权有效范围，观察结果是拟稿句是否落在 2025-01-01 至 2025-06-30 之内。检索与表单只收集值，授权状态需要另行核对。
2. 把待核实投诉单当作已完成认定。输入为窜货投诉单第 3 条状态“待核实”，比较对象为授权清单有效范围，观察结果是投诉单未载明对授权状态的结论。待核实不证明缺少授权。
3. 把测试模式下的空 `chatId` 当作业务故障。输入为测试模式调用记录，比较对象为正式调用记录中的 `chatId`，观察结果是测试模式下该字段不存在。该现象属于文档说明的调试条件。

## 怎么确认配好了

1. 输入样本中店铺 S 的授权清单原文与拟稿句，比较授权有效范围起止日期，观察拟稿句日期是否落在范围内。预期为落在范围内时拟稿句获得支持，否则为未获支持。
2. 输入样本中窜货投诉单第 3 条状态字段，比较其取值与授权状态字段，观察两者是否指向同一主体、同一期间、同一字段。预期为不同字段不构成矛盾，记录为待核实。
3. 输入一条测试模式调用记录，比较其中 `chatId` 与 `responseChatItemId` 是否存在，观察测试模式下两字段均不存在。预期为正式调用记录中两字段存在，测试记录中不存在，据此区分调试条件与业务故障。
