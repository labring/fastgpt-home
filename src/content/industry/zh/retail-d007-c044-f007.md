# 平台广告投放与站内流量的经营报表与异常复盘：对话日志与审计

## 这个品类的数据长什么样

广告投放按流量和转化实时调价，投放专员需要把巨量千川、京东快车、阿里妈妈等来源的消耗与店铺成交数据对齐，核对投放计划、关键词报表、人群包说明与转化归因表。对话日志与审计环节处理的是应用侧会话记录：会话标题、对话列表、单条对话运行详情、反馈标记。这些记录能反映某次归因问询或异常复盘的对话过程，不能替代投放平台自身的消耗与成交数据。数据按日、按小时更新，本页不涉及批量同步或实时触发机制。

## 这些特征在「对话日志与审计」这一环带来什么约束

会话按 appId 与 chatId 定位，对话按 dataId 定位。核对投放对账问询时，须先确认目标会话属于哪个应用、哪个入口，避免把不同入口的会话混算成同一批业务记录。需要运行详情时，按官方契约在对话接口请求中设置 detail，并从 responseData 读取模块状态与完整结果；非流式结果保存在 responseData，流式结果通过 event 区分。接口实际返回哪些字段，就以哪些字段为准，未返回的业务数据不能推定已完整留存。测试模式下的身份字段可能与正式调用不同，须分别核对输入、历史与返回内容。日志存在只说明记录可查，对账、留存与合规要求仍由完整业务方案另行落实。

假设演练样本。材料原文一：某应用 appId 为 A1，会话 chatId 为 C9，该会话由 API 创建，对话列表返回两条记录，其中 AI 记录的 totalRunningTime 为 2.42。材料原文二：该会话下一条对话 dataId 为 D7，其运行详情 responseData 含一个 moduleType 为 chatNode 的元素，query 为“本周快车消耗与成交差异”，runningTime 为 1.22。待判定拟稿句：“C9 会话已完整留存本周快车全部消耗明细，可直接用于预算调整审批。”核对材料未载明消耗明细字段，也未载明审批授权，该句未获支持。

## 配置怎么定

| 核对项 | 设置或动作 | 与样本的关系 |
| --- | --- | --- |
| appId 与 chatId | 请求中传入目标应用与会话标识 | 定位样本 A1、C9 |
| detail | 需要运行详情时设为 true | 读取 D7 的 responseData |
| stream | 按采集方式选择，流式经 event 区分 | 决定结果存放位置 |
| source | 会话列表请求传 api，只取 API 创建的会话 | 判断 C9 是否属于该来源 |
| loadCustomFeedbacks | 对话列表请求中按需读取自定义反馈 | 核对反馈是否留存 |
| pageSize 与 offset | 本次假设试验起点取 20 与 0，因样本仅两条记录，与列表 total 比较 | 仅用于本次纸面核对 |

## 容易做错的三处

1. 把 C9 会话的对话记录当成投放消耗明细。输入为对话列表返回的 title 与 totalRunningTime，比较对象是拟稿句所称“完整留存消耗明细”，列表字段不含消耗明细，该主张未获支持。
2. 把检索或表单收集当成授权执行。输入为 D7 运行详情中的 query 字段，比较对象是“可直接用于预算调整审批”这一授权结论，运行详情不构成审批授权，结论待核实。
3. 把不同入口会话混算。输入为 source=api 的会话列表结果，比较对象是页面会话或其他来源会话，样本只覆盖 API 来源，其余来源状态未知。

## 怎么确认配好了

1. 输入样本 A1、C9 的会话列表请求，比较返回 list 中 chatId 与 updateTime，出现 C9 且来源为 api 才满足定位条件。
2. 输入样本 D7 的运行详情请求，比较 responseData 中 moduleType 与 query，出现 chatNode 且 query 为“本周快车消耗与成交差异”才满足读取条件；未出现则记录缺口。
3. 输入拟稿句全文，比较其“完整留存消耗明细”与“可直接用于预算调整审批”两项主张，材料未载明对应字段与授权，判定为未获支持，保留证据缺口。
