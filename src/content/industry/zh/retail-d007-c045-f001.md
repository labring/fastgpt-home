# 平台店铺评价与体验分维护的经营报表与异常复盘：HTTP 接口与外部系统

## 这个品类的数据长什么样

评价维护围绕售后履约后的消费者反馈展开，主要材料包括差评处理记录、体验分明细、服务诊断报告与整改台账。数据来源涉及抖店体验分、天猫服务指标、京东售后评价与客服系统，更新频率为日或周。经营报表与异常复盘需要把上述材料中的指标变化、处理状态与责任人对应起来，HTTP 接口与外部系统承担的是把外部接口返回的数据取回、解析并交给后续节点的职责。接口取回的数据本身不构成对差评归因结论的确认，也不代表整改已执行。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向目标地址发送请求，Params 用于路径请求参数，Body 用于请求体，Headers 用于传递特殊信息，三者均可通过 `{{}}` 引用变量。变量来自全局变量、系统变量与前方节点输出。系统变量包括 appId、chatId、responseChatItemId、variables、cTime、histories，其中 chatId 与 responseChatItemId 在测试模式下不存在。返回值通过 JSON path 提取，出参格式化可将 JSON 转为字符串。对话接口使用 APIKey 鉴权，调用 chat/completions 时推荐在请求体传入 body.appId，也支持 Authorization: Bearer <apiKey>-<appId>。传入的 model、temperature 等字段无效。检索或接口返回不构成授权，业务核验、审批、数据库写入与外部同步需要各自的下游实现。

假设演练样本：某店铺运营人员在 2025 年 6 月 10 日整理体验分明细时，发现一条差评处理记录原文写着“该订单售后已完成，消费者反馈已记录，处理状态为待补充凭证”。同日的整改台账写着“对应整改项状态：待审核”。现拟一条交接请求：“请通过 HTTP 接口把该差评处理记录同步至外部客服系统，并标记为已完成整改。”该请求涉及的主体是运营人员，对象是上述差评处理记录，当前状态为待补充凭证与待审核，授权边界未载明。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 核对方式 |
| --- | --- | --- |
| 请求地址与方法 | 按外部接口文档填写，地址可引用变量 | 与外部接口契约逐项比对 |
| Params 与 Headers | Authorization 使用 Bearer 加凭证引用 | 核对凭证注入位置，不写入公开样例 |
| Body | 仅在对应请求类型下使用，核对 JSON 结构 | 与接口文档字段逐项比对 |
| 变量引用 | 引用全局变量、系统变量或前方节点输出 | 逐项核对实际传入值 |
| 返回值提取 | 按 JSON path 语法配置 key | 与接口响应结构比对 |
| 调试身份字段 | chatId 与 responseChatItemId 在测试模式下不存在 | 区分调试空值与业务故障 |

数值起点仅用于本次假设演练，选此起点是为便于与接口文档字段逐项比对，不代表官方默认值。

## 容易做错的三处

1. 把待补充凭证与待审核直接当作已完成整改。样本中处理状态为待补充凭证，整改项状态为待审核，拟稿句却写“标记为已完成整改”，输入与拟稿句在状态字段上不一致，比对结果为拟稿句未获材料支持。
2. 把接口返回数据当作授权执行。样本中未载明运营人员具备同步至外部客服系统的授权，拟稿句直接要求同步，输入缺少授权依据，比对结果为授权边界待核实。
3. 把测试模式下的空 chatId 或空 responseChatItemId 当成业务故障。文档说明这两个字段在测试模式下不存在，输入若来自测试模式，比对时应记录为调试环境差异，不判定为接口异常。

## 怎么确认配好了

1. 输入样本原文“处理状态为待补充凭证”与拟稿句“标记为已完成整改”，比较两者在同一状态字段上的取值，拟稿句取值与材料取值不一致时，判定拟稿句未获支持。
2. 输入样本原文“对应整改项状态：待审核”与拟稿句“标记为已完成整改”，比较整改项状态字段，材料为待审核，拟稿句为已完成，判定拟稿句与材料状态不符。
3. 输入拟稿句“请通过 HTTP 接口把该差评处理记录同步至外部客服系统”，比较材料中是否载明同步授权，材料未载明授权时，判定授权边界待核实，不执行同步动作。以上均为纸面核对，不声称已实测、已部署或已获批准。
