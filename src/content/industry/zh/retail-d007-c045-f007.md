# 平台店铺评价与体验分维护的经营报表与异常复盘：对话日志与审计

## 这个品类的数据长什么样

评价与体验分维护依赖售后履约后的消费者反馈，主要来源包括抖店体验分、天猫服务指标、京东售后评价与客服系统。这些数据按日或按周更新，日常要处理的文档是差评处理记录、体验分明细、服务诊断报告与整改台账。对话日志与审计在这一品类里承担会话身份核对与运行详情留痕的职责，为经营报表提供可追溯的对话依据，并支撑异常复盘时的责任定位。最耗时的环节是归因差评、联系补充凭证与跟踪整改后指标，这些环节都需要把对话记录与业务单据对齐。

## 这些特征在「对话日志与审计」这一环带来什么约束

会话身份依靠 chatId 与 dataId 区分：chatId 标识一个应用下某个会话，dataId 标识一个会话下某条对话。不同入口创建的会话在来源上分开，source=api 只获取通过 API 创建的会话，不获取页面上的会话。运行详情需要按官方契约设置 detail，非流式结果保存在 responseData 中，流式结果通过 event 区分。接口返回的字段决定日志里实际有什么，未返回的业务数据不能推定已完整留存。测试模式与正式调用的身份字段可能不同，输入、历史与返回内容需分别核对。日志存在不等于完成合规审计，对账、留存与合规要求由完整业务方案另行落实。

假设演练样本：某店铺运营在 2026 年 3 月 10 日的差评处理记录中写道：“订单 A 的买家在会话中提出退款诉求，客服当日回复将转交售后核实。”同日整改台账记：“订单 A 待补充凭证，状态为待审核。”现有一条拟交接请求：“请依据上述对话日志，确认该差评已完成整改并可直接用于体验分申诉。”样本材料只表明转交与待审核状态，未载明整改完成或申诉授权。

## 配置怎么定

| 核对项 | 官方已说明的设置或实施核对 | 与本页样本的关系 |
| --- | --- | --- |
| 会话身份 | chatId 标识某应用下会话，dataId 标识某会话下对话 | 用 chatId 与 dataId 定位订单 A 的对话 |
| 会话来源 | source=api 只取 API 创建的会话 | 核对订单 A 会话是否来自 API 入口 |
| 运行详情 | 按契约设置 detail，非流式结果在 responseData | 取订单 A 对话的节点响应 |
| 插件输出 | 查 moduleType=pluginOutput 的元素取 pluginOutput | 若会话含插件节点，按此定位输出 |
| 反馈字段 | userGoodFeedback 与 userBadFeedback 记录点赞点踩 | 核对订单 A 对话是否有点踩记录 |
| 授权边界 | authProxy 需团队所有者开启，代理身份仍需目标应用与会话权限 | 确认交接人是否具备该会话权限 |

假设试验起点：将 pageSize 设为 20 用于本次纸面核对，理由是该值能覆盖订单 A 当日会话量，比较对象为实际返回条数与台账记录条数，该值不是官方默认值。

## 容易做错的三处

1. 把待审核状态读成整改完成。样本中整改台账写“待补充凭证，状态为待审核”，这是流程未走完的状态，不能作为已完成整改的证据。检查方式：输入整改台账原文，比较状态字段取值与“已完成”类取值，观察是否存在互斥取值，若只有待审核则判定为未获支持。
2. 把检索结果当成授权执行。用 chatId 取到会话记录只说明记录存在，不说明交接人具备申诉权限。检查方式：输入交接请求与 authProxy 说明，比较代理身份是否被所有者开启且具备目标应用与会话权限，观察权限字段是否缺失，缺失即记录为待核实。
3. 把测试模式身份字段与正式调用混用。测试模式的身份字段可能与正式调用不同。检查方式：分别输入测试与正式调用的请求体，比较 appId 与 chatId 的取值来源，观察两组取值是否一致，不一致时不得合并计算。

## 怎么确认配好了

1. 会话身份核对。输入样本中订单 A 的 chatId 与 dataId，比较返回记录中的 chatId、dataId 与台账所记是否同主体同期间，观察是否指向同一会话与同一对话，指向一致才满足核对条件。
2. 运行详情核对。输入订单 A 的 dataId 并按契约设置 detail，比较 responseData 中的 moduleName、moduleType 与台账记录的节点名称，观察节点响应是否与差评处理记录所述环节对应，对应一致才满足核对条件。
3. 授权边界核对。输入拟交接请求与 authProxy 说明，比较交接人是否被所有者开启代理且具备目标应用与会话权限，观察权限说明是否覆盖该会话，覆盖才满足核对条件；未覆盖或未载明时保留为证据缺口，不判定为已获授权。
