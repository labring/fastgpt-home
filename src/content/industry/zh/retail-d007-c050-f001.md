# 投诉举报与监管回复的经营报表与异常复盘：HTTP 接口与外部系统

## 这个品类的数据长什么样
投诉举报与监管回复围绕投诉工单、监管询问函、订单证据、整改报告展开，面向平台或监管机关，需要正式证据与整改文字。数据来源包括12315平台、平台投诉中心、客服聊天与订单系统，更新频率为不定期、每案。本页只处理经营报表与异常复盘中的HTTP接口与外部系统环节：把工单状态、回复进度、证据包提交情况经HTTP模块送入外部系统或取回结果，用于复盘异常。资料未说明的数据项保持未知。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束
HTTP模块向对应地址发送请求，Params、Body、Headers与URL均可通过{{}}引用变量，变量来自全局变量、系统变量、前方节点输出。系统变量含appId、chatId、responseChatItemId、variables、cTime、histories（默认最多取10条，无法修改长度）。返回值通过JSON path提取，输出类型选字符串时会转成json字符串。对话接口调用时推荐在请求体传入body.appId；appId优先级为body.appId、<apiKey>-<appId>、apikey关联的appId。传入的model、temperature无效，由编排决定。detail=true可返回responseData，据此手动计算tokens。authProxy代理身份需团队所有者开启，代理身份仍需具备目标应用和会话权限。

假设演练样本：材料原文为“投诉工单编号TS-2024-0312，主体为某店铺，对象为2024年3月5日订单，状态为已提交监管询问函回复，回复日期2024年3月12日。”待判定拟稿句为“该工单已完成整改并结案。”该句与原文状态不一致：原文只载明已提交回复，未载明整改完成或结案，属未获支持。

## 配置怎么定
下表围绕上述样本，只列官方已说明的设置或实施核对项，数值为本次假设试验起点。

| 配置项 | 本次起点 | 选择理由与比较对象 |
| --- | --- | --- |
| 请求地址与方法 | 按外部接口文档填写 | 与外部接口契约比较，核对路径与方法一致 |
| Headers 鉴权 | Authorization Bearer 变量注入 | 与密钥规范比较，不写入公开样例 |
| Body 结构 | 按请求类型构造 JSON | 与外部接口契约逐字段比较 |
| 变量引用 | appId、chatId 等系统变量 | 与前方节点实际输出比较 |
| 返回值提取 | 配置 key 与 JSON path | 与接口响应示例比较 |
| detail 取值 | 假设起点 true | 需中间值时选 true，与 false 响应结构比较 |

## 容易做错的三处
1. 把调试身份字段当成业务故障。测试模式下chatId与responseChatItemId不存在，输入为测试模式请求，比较实际传入值与系统变量说明，观察是否误判为空值故障。
2. 把检索或表单当成授权执行。输入为带交互节点的请求，比较返回的interactive展示配置（仅type与params）与授权状态，观察是否把表单收集值当作已批准。
3. 把未载明状态当作否定结论。输入为样本原文与拟稿句，比较原文状态“已提交回复”与拟稿“已完成整改并结案”，观察是否出现无依据的确定结论。

## 怎么确认配好了
1. 输入样本原文与拟稿句，比较原文状态字段与拟稿断言，仅当原文明确载明整改完成与结案时该句才获支持；本次观察为未获支持。
2. 输入detail=true的请求，比较responseData中tokens字段与手动计算值，观察是否可据此核算；不声称已实测。
3. 输入空结果[]的纸面响应，比较下游节点对空数组的承接设计，观察是否出现虚构规则返回[]的断言；缺失证据保持缺失。
