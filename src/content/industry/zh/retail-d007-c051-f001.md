# 抖音小店货架运营的经营报表与异常复盘：HTTP 接口与外部系统

## 这个品类的数据长什么样

抖音小店货架运营围绕商品卡与店铺体验分展开，与直播间运营的单场节奏不同，日常材料集中在商品资质页、体验分明细、发货违规申诉和店铺公告。这些材料按日和每单更新，缺货无货、资质补充、体验分维护构成主要工作量。经营报表与异常复盘要把这些材料与外部系统对齐，HTTP 接口承担取数与回传的通道角色。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向对应地址发送请求，Params 用于路径请求参数，Body 用于请求体，Headers 用于传递特殊信息。三类数据均可通过 `{{}}` 引用变量，URL 同样可以。变量来自全局变量、系统变量和前方节点输出。系统变量包含 appId、chatId、responseChatItemId、variables、cTime、histories，其中 histories 默认最多取 10 条且无法修改长度。返回值配置的是解析方式，通过 JSON path 提取响应值；输出类型选择字符串时，会把对应 key 的值转成 json 字符串。对话接口使用 APIKey 鉴权，调用 chat/completions 时推荐在请求体传入 body.appId，也支持 Authorization: Bearer <apiKey>-<appId>。传入的 model、temperature 等字段无效，由编排决定。detail=true 时返回中间值，非 stream 模式结果保存在 responseData。检索与相似度只影响内容匹配，不承担权限或实体隔离职责。

假设演练样本：某抖店商家运营在 2024 年 10 月 13 日整理 10 月 12 日的体验分明细与发货违规申诉材料，拟通过 HTTP 模块把当日异常条目回传至外部工单系统。供核对的材料原文为：“10 月 12 日店铺体验分明细显示物流体验项低于前一日；当日缺货无货订单 3 笔，其中 2 笔已提交发货违规申诉，状态为待审核。”待判定的拟稿句为：“3 笔缺货订单的申诉均已通过，异常已闭环。”该拟稿句与原文在申诉状态字段上取值不同，原文只载明待审核，未载明通过。

## 配置怎么定

| 配置项 | 本次假设起点 | 核对方式 |
| --- | --- | --- |
| 请求地址 | 外部工单系统提供的接收地址 | 与外部接口文档逐字比对路径与方法 |
| Headers 鉴权 | Authorization 引用已注入的凭证变量 | 确认凭证不写入公开样例 |
| Body 结构 | 按外部契约声明异常条目字段 | 对照接口文档核对 JSON 键名与类型 |
| 变量引用 | 引用前方节点输出的日期与条目 | 逐项确认实际传入值非空 |
| 返回值解析 | 用 JSON path 提取受理编号 | 与响应示例的层级逐级比对 |
| 输出类型 | 字符串 | 确认对象值转成 json 字符串后下游可读 |

上述起点为本次假设试验设定，选择理由是便于与外部接口文档逐字段对照，并非官方默认值。

## 容易做错的三处

1. 把待审核写成已通过。输入是材料原文的“状态为待审核”，比较对象是拟稿句的“均已通过”，可观察结果是两者在申诉状态字段上取值不同，拟稿句未获支持。
2. 把调试空值当成业务故障。输入是测试模式下不存在的 chatId 与 responseChatItemId，比较对象是正式会话的取值，可观察结果是测试模式下这两项为空，正式会话中才有值。
3. 把相似度当成权限过滤。输入是检索返回的 score 字段，比较对象是目标记录的授权归属，可观察结果是 score 只反映内容匹配程度，不反映记录是否属于当前主体。

## 怎么确认配好了

1. 用样本原文核对拟稿句。输入“状态为待审核”，比较拟稿句“均已通过”，仅当原文载明通过时才满足条件；本次现象为未获支持，需记录证据缺口。
2. 用响应示例核对解析配置。输入接口返回的 JSON 结构，比较配置的 JSON path 层级，仅当提取值与示例中对应字段一致时才满足条件。
3. 用空结果承接核对下游设计。输入明确的纸面空数组，比较下游节点对空值的处理设计，仅当设计说明空值分支时才满足条件，不推断虚构规则的实际返回。
