# 渠道窜货稽查的经营报表与异常复盘：对话日志与审计

## 这个品类的数据长什么样
窜货稽查围绕区域与价格秩序展开，处理对象是货源码、低价店铺与处罚通知，不涉及返利金额核算。主要材料来自防伪码系统、电商平台价格、经销商发货记录与市场巡检，日常文档包括窜货投诉单、防伪码记录、处罚通知和调查照片。这些材料按周或不定期更新，单份投诉单与一次巡检记录各自独立成档。经营报表与异常复盘需要把某一对话的日志与这些业务材料对齐，核对对话身份、运行详情与字段留存范围，确认哪些内容已进入可查记录。

## 这些特征在「对话日志与审计」这一环带来什么约束
对话日志以 chatId 标识一个应用下的会话，以 dataId 标识会话下的具体对话。结合 chatId 核对目标对话与业务记录，可避免把不同入口的会话混算。需要运行详情时，按官方契约在对话接口设置 detail，并在非流式响应的 responseData 中检查模块状态与完整结果；流式响应通过 event 区分 answer、flowNodeStatus、flowResponses 等取值。日志与接口实际返回的字段是核对依据，未返回的业务数据不能推定已完整留存。测试模式与正式调用的身份字段可能不同，应分别核对输入、历史与返回内容。对账、留存与合规要求由完整业务方案另行落实，日志存在不等于完成合规审计。

假设演练样本：某品牌渠道管控人员留存一份纸面材料，内容为“2025年3月10日，华东区域经销商A的发货记录显示货源码段H-0301至H-0350发往江苏；同日电商巡检记录显示某店铺以低于区域指导价销售该码段商品；3月12日形成窜货投诉单，状态为待核实。”同批材料中另有一条拟稿句：“该店铺已完成处罚，窜货事实成立。”需判定该拟稿句是否与材料一致。材料只显示投诉单处于待核实，未载明处罚决定或执行结果，拟稿句中的“已完成处罚”与“事实成立”均未获支持。

## 配置怎么定
| 配置或核对项 | 本页用途 | 取值与核对方式 |
| --- | --- | --- |
| appId 与 chatId | 定位目标应用与会话 | 按官方契约传入，核对会话归属，不混算不同入口 |
| dataId | 定位会话下具体对话 | 与业务材料逐条对应，核对对话记录范围 |
| detail | 获取运行详情 | 需要中间值时设为 true，非流式在 responseData 检查 |
| responseData 字段 | 核对模块状态与结果 | 逐字段比对实际返回，未返回项记为未知 |
| source=api | 获取 API 创建的会话 | 获取会话列表时传入，区分页面会话 |
| loadCustomFeedbacks | 读取自定义反馈 | 需要反馈信息时传入，按返回内容核对 |

上述取值为本次假设试验起点，选择理由是与本页样本的对话核对需求对应；实际取值与官方文档或所在环境返回结果比较，不视为官方默认。

## 容易做错的三处
1. 把不同 chatId 的会话合并统计。输入为两个不同 chatId 的会话列表，比较会话归属字段，若合并后总量与各会话分别计数之和不一致，则出现混算；应分别核对。
2. 未设置 detail 却期望获得 responseData。输入为 detail=false 的请求，比较返回结构中是否存在 responseData，若不存在则无法取得模块状态；应改为按契约设置 detail 后再核对。
3. 把待核实的投诉单当作已完成处罚。输入为样本中“状态为待核实”的投诉单与拟稿句“已完成处罚”，比较状态字段与处罚结果字段，若处罚结果未载明，则拟稿句未获支持；应保留证据缺口。

## 怎么确认配好了
1. 输入样本中 chatId 与 dataId 对应的会话与对话记录，比较会话列表返回的 chatId 与业务材料标注的会话标识，若一致则对话身份核对通过；不一致时记录差异，不推定归属。
2. 输入 detail=true 的非流式请求，比较 responseData 中是否存在模块名称与运行时间字段，若存在则运行详情可读；缺失时记录为未获取，不推断原因。
3. 输入样本拟稿句与投诉单原文，比较“待核实”状态与“已完成处罚”表述，若处罚结果字段未载明，则判定拟稿句未获支持；需补充处罚通知原文后再核对。
