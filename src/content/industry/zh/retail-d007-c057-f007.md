# 生鲜临期折价处理的经营报表与异常复盘：对话日志与审计

## 这个品类的数据长什么样
临期折价处理围绕货架库存生命周期运转，数据来源包括 POS 库龄、门店巡检、ERP 库存与质检记录，更新频率为日或班次。经营报表与异常复盘需要把临期清单、折价审批、报损单、促销价签四类文档与对话记录对应起来。这些文档各自有主体、对象与状态，核对时须保持同主体、同期间、同一字段。对话日志与审计这一环只处理会话身份、运行详情与字段留存的核对，不承担审批、报损或价签执行。日志存在不等于完成合规审计，对账与留存要求由完整业务方案另行落实。

## 这些特征在「对话日志与审计」这一环带来什么约束
对话身份依靠 chatId 区分不同会话，核对目标对话与业务记录时不能把不同入口的会话混算。需要运行详情时按官方契约设置 detail，并检查 responseData 中的模块状态与完整结果；detail=false 时不返回中间值。未返回的业务数据不能推定已完整留存。测试模式与正式调用的身份字段可能不同，须分别核对输入、历史与返回内容。

假设演练样本：门店 A 于 2026 年 3 月 10 日提交一份临期清单，原文为「门店 A，2026-03-10 班次，对象为冷藏酸奶批次 Y-0310，状态为待审批折价，有效范围仅限当日 18 时前」。同一 chatId 下另有一条拟稿交接句：「该批次已审批通过，请按新价签执行并同步报损单。」判定所需的主体、对象、状态与有效范围已在原文给出；审批通过这一状态在材料中未载明，属于待核实。

## 配置怎么定
下表围绕上述样本，列出与本页功能相关的官方已说明设置或实施核对项。数值为本次假设试验起点，用于与样本实际值比较，不代表官方默认。

| 配置项 | 本次假设起点 | 核对方式与理由 |
| --- | --- | --- |
| appId | 样本应用标识 | 与 chatId 一并核对，确认会话归属同一应用 |
| chatId | 样本会话标识 | 长度小于 250，确保唯一，区分不同入口会话 |
| detail | true | 需要 responseData 中间值时设置，false 时不返回 |
| stream | false | 非流式下结果保存在 responseData，便于逐字段比对 |
| responseChatItemId | 样本响应标识 | 当前 chatId 下唯一，用于定位本次对话记录 |
| loadCustomFeedbacks | true | 读取自定义反馈，核对对话记录中的反馈字段 |

## 容易做错的三处
1. 把不同 chatId 的会话合并计算。样本中门店 A 的清单与另一入口的会话若共用统计口径，主体与期间就会错位。检查时输入两个 chatId，比较各自返回的 dataId 与内容，观察是否被归入同一会话。
2. 将 detail=false 的返回当作完整运行详情。此时 responseData 缺失，无法核对模块状态。检查时对同一请求分别以 detail=true 与 false 调用，比较返回结构中是否存在 responseData 及其模块字段。
3. 把拟稿句中的「已审批通过」当作既成事实。样本原文只写「待审批折价」，审批状态未载明。检查时输入拟稿句与清单原文，比较状态字段，观察两者是否同主体、同期间、同一字段；不一致时记录为待核实。

## 怎么确认配好了
1. 输入样本原文与拟稿句，比较主体、对象、状态与有效范围四项字段。预期现象：主体与对象一致，状态字段在原文为待审批、在拟稿句为已审批，二者不同，判定为未获支持，不得作为执行依据。
2. 以 detail=true、stream=false 调用样本 chatId，检查 responseData 中是否包含模块状态与完整结果。预期现象：返回结构含 responseData 数组，可逐项比对模块名与运行时间；若缺失，则本次调用不满足运行详情核对条件。
3. 对样本 chatId 调用对话列表接口，比较返回的 dataId 与 responseChatItemId。预期现象：两者对应同一对话记录，反馈字段按 loadCustomFeedbacks 设置返回；若标识不匹配，则记录缺口，不推定记录已完整留存。
