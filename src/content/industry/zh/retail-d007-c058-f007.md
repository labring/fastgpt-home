# 生鲜供应商索赔的经营报表与异常复盘：对话日志与审计

## 这个品类的数据长什么样

生鲜供应商索赔追究到货质量责任，不处理门店自然损耗，这一差别决定了对话日志与审计的核对对象。索赔依据来自质检系统、WMS 验收、供应商合同与财务对账，日常文档为质量异常单、照片证据、扣款通知与索赔对账单。数据按每批与按月更新。经营报表与异常复盘要回答的问题，是某批到货的质量异常是否被记录、扣款通知是否与索赔对账单一致、协商补货或赔付的沟通是否留有可查对话。日志与审计在此承担的是把对话记录与业务单据对应起来的核对工作，不承担授权、审批或财务入账。

## 这些特征在「对话日志与审计」这一环带来什么约束

对话接口的 chatId 用于标识一个应用下的会话，dataId 标识一个会话下的对话。核对索赔沟通时，需以 chatId 与 dataId 定位目标对话，不把不同入口的会话混算。需要运行详情时按官方契约设置 detail，非流式结果保存在 responseData 中，流式模式通过 event 区分。日志中未返回的业务字段不能推定已完整留存。测试模式与正式调用的身份字段可能不同，需分别核对输入、历史与返回内容。检索与相似度不构成权限或实体隔离，日志存在不等于完成合规审计，对账、留存与合规要求由完整业务方案另行落实。

假设演练样本：某生鲜采购方与供应商就一批叶菜到货质量异常沟通。供核对的材料原文为三句：“质量异常单载明：2025年3月10日到货批次 YC-0310，验收判定叶片萎蔫，数量 120 箱。”“扣款通知载明：就批次 YC-0310 拟扣款，金额待对账确认。”“供应商回复：同意补货 120 箱，扣款金额请以对账单为准。”待判定的拟稿句为：“供应商已确认扣款金额并完成赔付。”该拟稿句与原文比较：原文只有同意补货与请以对账单为准，未载明确认金额，也未载明赔付完成，因此该句未获支持。

## 配置怎么定

| 配置或核对项 | 与本页文档的关系 | 实施核对方式 |
| --- | --- | --- |
| appId | 对话接口与应用标识 | 核对请求体 appId 与目标索赔沟通应用一致 |
| chatId | 会话标识，长度小于 250 | 核对同一批次沟通使用同一 chatId |
| dataId | 会话下对话标识 | 核对目标对话与质量异常单批次对应 |
| detail | 是否返回中间值 | 需要运行详情时设为 true，检查 responseData |
| stream | 流式与非流式返回方式 | 非流式查 responseData，流式查 event |
| loadCustomFeedbacks | 读取自定义反馈 | 需要反馈时按参数说明传入 |

## 容易做错的三处

1. 把不同 chatId 的沟通合并统计同一批次索赔。输入为两个不同 chatId 的对话列表，比较批次标识，若批次相同而 chatId 不同，仍属不同会话，合并计算会混淆责任归属。
2. 把供应商“同意补货”当作“赔付完成”。输入为供应商回复原文，比较是否出现金额确认与赔付完成表述，原文只有补货意向与待对账，判定为未获支持。
3. 把 detail 未开启时的返回当作完整运行记录。输入为 detail=false 的响应，比较 responseData 是否存在，该响应不含中间值，不能据此认定节点未运行。

## 怎么确认配好了

1. 输入假设样本三句原文与拟稿句，比较拟稿句是否出现原文未载明的金额确认与赔付完成，若拟稿句含未载明内容，判定为未获支持。
2. 输入同一批次的两条不同 chatId 对话记录，比较批次标识与会话标识，若批次相同而 chatId 不同，判定为不可合并统计。
3. 输入 detail=true 与 detail=false 两次请求的返回，比较 responseData 字段是否存在，若 detail=false 返回无 responseData，判定为运行详情不完整，需以 detail=true 重新核对。
