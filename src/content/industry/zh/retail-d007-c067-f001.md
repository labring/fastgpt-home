# 社区团购团长运营的经营报表与异常复盘：HTTP 接口与外部系统

## 这个品类的数据长什么样

团长运营管理社区节点和佣金，不直接做冷链质检，主要数据来自社区团购后台、团长社群、订单明细与售后记录。日常文档包括团长协议、佣金表、提货清单和社群公告，更新频率为日或每团。经营报表与异常复盘要把这些材料里的订单、佣金、提货和售后状态对应到外部接口的请求与响应上，社区投诉和团长流失往往源于错漏发与佣金核对偏差。

## 这些特征在「HTTP 接口与外部系统」这一环带来什么约束

HTTP 模块向对应地址发送请求，Params 用于路径请求参数，Body 用于请求体，Headers 用于请求头，三者均可通过 `{{}}` 引用全局变量、系统变量和前方节点输出，URL 同样可以引用变量。系统变量包含 appId、chatId、responseChatItemId、variables、cTime、histories，其中 chatId 与 responseChatItemId 在测试模式下不存在。返回值通过 JSON path 语法提取，输出类型选择字符串时会转成 json 字符串。对话接口使用 APIKey 鉴权，调用 chat/completions 时推荐在请求体传入 body.appId，也支持 Authorization: Bearer <apiKey>-<appId>；传入的 model、temperature 等字段无效，由编排决定。detail=true 时非流式结果保存在 responseData 中，流式通过 event 区分；交互节点返回的 interactive 只含 type 和 params，entryNodeIds、memoryEdges、nodeOutputs、nodeResponseId 不返回。检索或表单收集值不构成授权，业务核验、审批、数据库写入和外部同步需要各自的下游实现。

假设演练样本：某团长协议原文载明“本协议自双方签署之日起生效，佣金按自然月结算，结算依据为平台后台订单明细”。一张 3 月佣金表列出团长 A 的订单 120 单、佣金 600 元，状态栏为“待审核”。一份 3 月 5 日提货清单列出 30 件商品，签收栏空白。拟稿句为“团长 A 的 3 月佣金已确认，可发起打款”。待判定请求为“请通过外部接口把团长 A 的 3 月佣金状态更新为已结算”。

## 配置怎么定

| 配置项 | 本次假设试验起点 | 选择理由与比较对象 |
| --- | --- | --- |
| BaseUrl | 外部接口文档给出的地址 | 与接口文档核对，出现 404 时可补充 v1 重试 |
| Authorization | Bearer 加密钥 | 与密钥使用规范核对，密钥不写入公开样例 |
| Params | 按外部接口文档填写路径参数 | 与接口契约逐项核对键名 |
| Body | 按请求类型填写 JSON 结构 | 与外部接口契约核对字段与类型 |
| 变量引用 | 引用前方节点输出与全局变量 | 与实际传入值逐项核对 |
| 返回值提取 | 按 JSON path 配置 key | 与接口响应示例核对取值路径 |

## 容易做错的三处

1. 把待审核当成已确认。佣金表状态栏为“待审核”，拟稿句写“已确认，可发起打款”，两者在同一字段上取值互斥，属于矛盾。
2. 把空白签收当成已签收。提货清单签收栏空白，缺少签收证据，不能据此认定错漏发或已完成提货。
3. 把检索或表单当成授权执行。待判定请求要求更新佣金状态，表单只收集值，更新状态需要下游实现，请求本身不构成授权。

对应检查：第一，输入佣金表原文与拟稿句，比较状态字段取值，若出现“待审核”与“已确认”并存，则判定矛盾。第二，输入提货清单原文，比较签收栏是否有值，若为空则记录证据缺口，不判定错漏发。第三，输入待判定请求与授权材料，比较是否存在授权边界说明，若缺失则记录待核实，不执行状态更新。

## 怎么确认配好了

- 验证一：输入团长协议原文与拟稿句，比较协议生效条件与拟稿句的“已确认”表述，若协议只写签署生效、未写佣金确认流程，则判定未获支持。

- 验证二：输入 3 月佣金表原文，比较订单数与佣金金额的对应关系，若两者无法从原文推导，则记录待核实，不补造计算规则。

- 验证三：输入待判定请求与提货清单，比较请求中的状态更新与清单签收状态，若签收栏空白，则判定证据不足，不执行更新。

三项验证均以假设样本为输入，预期结果为判定矛盾、证据缺口或未获支持，不声称已实测。空结果可用纸面输入 [] 核对下游设计，不声称虚构规则检索一定返回 []。检索与相关度不负责权限或实体隔离，跨不同向量模型的库不可共同关联，只核标识并排除不符者。
