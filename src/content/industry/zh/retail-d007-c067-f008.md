# 社区团购团长运营的经营报表与异常复盘：工作流编排

## 这个品类的数据长什么样

在社区团购团长运营的经营报表与异常复盘中，本页说明FastGPT的工作流编排如何衔接资料。团长运营报告应区分通知、提货安排与真实接收，协作协议不能证明每个社区已履约。所用场景为自拟文字测试。

## 这些特征在「工作流编排」这一环带来什么约束

自拟报告原文写公告已发、提货名单待确认、接收凭据缺，却在结论称服务已落实。流程可收各项的社区范围和资料性质，让人员选择补接收或核公告覆盖。已发公告支持传播动作，不证明社区成员看过或收到商品；团长协议只说明协作安排，不能补出具体提货执行，也不在本题展示佣金和效果数值。

## 配置怎么定

| 团长运营报告 | 自拟资料状态 | 分别检查 |
| --- | --- | --- |
| 公告发送 | 仅说明发出 | 不代表成员已知 |
| 提货名单 | 仍待确认 | 另取交付记录 |
| 社区范围 | 某区域有材料 | 不扩成全部区域 |
| 协作协议 | 安排非执行 | 不补实际提货 |
| 补证路径 | 按提货点传原文 | 仅更新有证事项 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `表单输入节点` | 提交收集值后传给后续步骤。 |
| `用户选择节点` | 沿所选项连接的分支继续。 |
| `交互状态核对` | 检查等待与提交后的状态。 |
| `输出承接核对` | 逐项比较前后步骤传值。 |
| `外部操作分工` | 外部业务操作需另接实现。 |

## 容易做错的三处

通知冒接收：若公告发送被当成员已知，应查本次实际接收依据；名单冒履约：若提货安排变成完成，应取对应交付记录；社区混用：若某社区资料支持全部区域，应核原始覆盖与下游文字。三项分别核信息到达、货物阶段和范围，不能由同一团长承担而合并。

## 怎么确认配好了

验收沿补接收分支核社区对象与材料原句，再看核公告路径是否保留实际覆盖。补入某提货点交付后，只更新该点，其他待确认名单仍列缺项。正式群发、采购交付和对账处理需要另接业务步骤核权限及回执，选择被记录不代表成员已收到消息或货品，流程报告也不自动成为履约凭证。
