# 连锁门店价格与陈列稽核的经营报表与异常复盘：对话日志与审计

## 这个品类的数据长什么样

价格陈列稽核发生在日常经营期，督导系统、POS价格表、门店摄像与总部促销档期按周、按月汇总。巡店照片、价签清单、陈列标准与整改通知构成主要文档。经营报表与异常复盘要回答的问题是：某次巡店记录与某条对话日志能否对应同一门店、同一档期、同一字段。对话日志与审计环节的价值在于把会话标识、运行详情与业务记录对齐，使异常复盘有可核对的痕迹。

## 这些特征在「对话日志与审计」这一环带来什么约束

会话标识 chatId 用于区分某一应用下的不同会话，dataId 用于区分某会话下的某条对话。核对时须确认目标对话与业务记录属于同一 chatId，不能把不同入口的会话混算。需要运行详情时按官方契约设置 detail，并检查 responseData 中的模块响应；detail 为 false 时中间值不返回，日志中缺少的业务字段不能推定已完整留存。

假设演练样本：某运营人员提交一份巡店材料，原文两句为「2025年3月第2周，A区门店价签抽查记录：促销价签与POS价格表一致。」「同批次陈列标准执行照片已归档。」另附一条待判定交接请求：「请把本周对话日志中的异常问答直接作为整改依据下发。」

该请求把日志存在与整改下发混为一谈。日志存在不等于完成合规审计，对账、留存与合规要求由完整业务方案另行落实。表单收集值，业务验证、审批、数据库写入与外部同步需要各自的下游实现。检索结果不构成授权，相似度不承担实体或权限隔离。

## 配置怎么定

下表围绕上述样本，列出与本功能、主任务相关的官方已说明设置或实施核对项。数值一栏为本次假设试验起点，仅用于人工比对，不表示官方默认值。

| 核对项 | 官方已说明内容 | 本次实施核对方式 |
| --- | --- | --- |
| 会话标识 chatId | 非空字符串时使用数据库会话，以 messages 最后一条为用户问题 | 假设起点为样本门店当周唯一 chatId，与巡店材料日期比对 |
| 响应标识 responseChatItemId | 传入后作为本次响应消息 ID 存入数据库，同一 chatId 下须唯一 | 假设起点为样本请求单号，核对是否与该 chatId 下已有值重复 |
| 运行详情 detail | 为 true 时返回中间值与完整结果，非流式保存在 responseData | 假设起点为 true，逐条比对 responseData 中模块字段与材料字段 |
| 变量 variables | 对象形式替换模块输入中的 [key] | 假设起点为门店编号与档期两个键，核对替换后内容是否与材料一致 |
| 会话来源 source | source=api 时仅获取通过 API 创建的会话 | 核对样本会话来源，来源不符者排除后再比对 |
| 交互节点 interactive | 返回展示配置，仅含 type 与 params，内部运行态字段不返回 | 核对返回结构中是否存在待判定请求所需的审批字段 |

## 容易做错的三处

1. 把不同 chatId 的对话合并统计。输入为两条来自不同门店会话的日志，比较二者 chatId 是否相同，若不同则不得并入同一门店的异常计数。
2. 把 detail 为 false 的响应当作完整留存。输入为 detail 未开启的返回，比较其中是否缺少 responseData 字段，缺少时记录为未获支持，不推断业务数据已留存。
3. 把待判定交接请求当作已批准执行。输入为样本中的交接请求，比较其中是否载明审批主体与生效范围，未载明时记录为待核实，不认定整改已下发。

## 怎么确认配好了

1. 输入样本材料原文与样本 chatId，比较材料日期与 chatId 对应会话的 updateTime 是否落在同一档期，二者一致且材料字段能在 responseData 中找到对应项时满足条件。
2. 输入样本交接请求，比较请求中是否出现审批主体、生效范围与执行动作三类信息，三类齐备且指向同一门店同一档期时满足条件；缺失任一类的记录为待核实。
3. 输入一条 detail 为 true 的假设返回与一条 detail 为 false 的假设返回，比较二者 responseData 字段是否存在，前者存在且后者不存在时，说明运行详情依赖该设置，不据此断言业务数据是否留存。

以上均为纸面核对，未执行实际调用，也未发生审批、整改或同步。检索检查只观察返回与失败分支，不保证首条命中或全部召回。空结果可用明确的纸面输入 [] 核对下游设计，不声称某规则检索必然返回空数组。
