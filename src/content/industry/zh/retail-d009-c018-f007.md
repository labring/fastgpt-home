# 区域经销商库存补货的运营权限与交接管理：对话日志与审计

## 这个品类的数据长什么样

库存补货属于日常滚动订单，经销商仓库、品牌渠道经理与销售内勤围绕补货申请、库存周转表、出库单、回款计划反复往来。数据来自经销商ERP、品牌订货系统、仓库库存与销售回款，更新频率为周或月。对话日志与审计在本环节的作用，是把这些材料在交接时的授权状态固定下来：谁在什么范围提出补货请求、哪些字段由表单收集、哪些动作仍需下游系统执行。

## 这些特征在「对话日志与审计」这一环带来什么约束

会话身份以 chatId 区分，同一应用下不同入口的会话不合并计算。需要运行详情时按官方契约设置 detail，并检查 responseData；detail 为 false 时不返回中间值。接口返回的 tokens 字段可自行计算，接口本身不返回实际消耗 Token 值。日志存在不等于完成合规审计，对账、留存与合规要求由完整业务方案另行落实。

假设演练样本：某区域经销商销售内勤在 chatId「replenish-2405-a」下提交一条拟稿句「请按本周库存周转表补货 SKU-1001 共 200 件，出库单待品牌渠道经理确认后生成」。随附材料原文两句：「补货申请单号 RA-2405-017，申请人：销售内勤岗，状态：待品牌渠道经理审核。」「库存周转表 2405 版显示 SKU-1001 期末库存 40 件，周均出库 90 件。」该请求的授权边界为：销售内勤可提交申请，审核与出库单生成不在本次请求内完成。

## 配置怎么定

| 配置或核对项 | 取值或做法 | 说明 |
| --- | --- | --- |
| 会话标识 chatId | 本次假设起点「replenish-2405-a」 | 因样本需区分该会话与同应用其他入口会话，比较对象为同 chatId 下的记录 |
| 运行详情 detail | 本次假设起点 true | 需核对 responseData 中的模块状态，比较 detail=false 时不返回中间值 |
| 会话来源 source | 本次假设起点 api | 获取会话列表时用于区分通过 API 创建的会话与页面会话 |
| 交互节点返回范围 | 按文档核对 | 返回的 interactive 仅含 type 与 params，entryNodeIds 等内部字段不返回 |
| 插件输出获取 | 按文档核对 | 查找 moduleType=pluginOutput 的元素，其 pluginOutput 为插件输出 |
| 业务授权动作 | 人工核对 | 审核、出库单生成、回款跟催需下游系统实现，日志不构成授权 |

## 容易做错的三处

1. 把表单收集的补货数量当成已获授权。样本中补货申请单号 RA-2405-017 状态为待品牌渠道经理审核，表单值只表示已收集，未表示审核通过。
2. 把 detail=false 的响应当作完整运行记录。detail=false 时不返回 responseData，模块状态与完整结果无从核对，不能据此认定留存完整。
3. 把 chatId 相同的会话与另一入口的会话混算。不同来源的会话需按 source 区分，混算会导致交接范围错误。

## 怎么确认配好了

1. 输入样本 chatId「replenish-2405-a」与 detail=true，比较返回中是否存在 responseData 数组及其中 moduleName 字段。出现 responseData 且含模块名，满足核对条件；未出现则记录为未获支持。
2. 输入样本拟稿句与补货申请单号 RA-2405-017，比较材料原文「状态：待品牌渠道经理审核」与拟稿句中「出库单待品牌渠道经理确认后生成」。两者主体与对象一致，状态字段明确为待审核，判定为待核实，不判定为已授权。
3. 输入样本库存周转表 2405 版数据，比较期末库存 40 件与周均出库 90 件，核对拟稿句「补货 200 件」是否与材料同一字段。材料未载明补货上限或安全库存规则，该数量与材料的关系为未获支持，保留证据缺口。
