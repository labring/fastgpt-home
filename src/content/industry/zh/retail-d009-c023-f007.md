# 品牌售后维修服务的运营权限与交接管理：对话日志与审计

## 这个品类的数据长什么样

品牌售后维修围绕保修责任和线下维修网点展开，处理平台退款之外，还要核对保修卡、维修工单、检测报告与换货审批。这类数据按每单产生，部分按日汇总。售后系统、门店订单、维修网点反馈与国家三包目录共同构成材料来源，售后中心、门店客服与维修网点是典型从业主体。

对话日志与审计环节关注的是：运营交接时，哪些材料、操作和请求处于什么授权状态。日志记录本身属于系统行为，对账、留存与合规要求需要完整业务方案另行落实。日志存在不等于完成合规审计。

## 这些特征在「对话日志与审计」这一环带来什么约束

会话身份需要结合 chatId 核对目标对话与业务记录，不同入口的会话不能混算。需要对话接口运行详情时，按官方契约设置 detail 并检查 responseData。日志与接口实际返回字段需要逐项核对，未返回的业务数据不能推定已完整留存。测试模式的身份字段可能与正式调用不同，输入、历史与返回内容需要分别核对。

假设演练样本。 以下内容为纸面假设，不指向任何真实客户、公司或身份编号。

材料原文一：「工单 W-2024-0871，品牌售后中心受理，客户报修洗衣机异响，保修卡显示购机日期 2024 年 3 月，整机保修期一年，维修网点为城东服务点，受理日期 2024 年 9 月 12 日。」

材料原文二：「检测报告 D-2024-0871，城东服务点出具，结论为电机轴承磨损，建议更换电机总成，报价 480 元，客户尚未确认。」

待判定拟稿句：「城东服务点已获授权更换电机总成，费用 480 元由保修承担。」

交接请求：「将工单 W-2024-0871 的换货审批权限由门店客服移交品牌售后中心。」

## 配置怎么定

| 核对项 | 官方已说明的设置或实施核对点 | 与样本的关联 |
| --- | --- | --- |
| 会话标识 | chatId 用于定位某一会话，长度小于 250，需自行确保唯一 | 核对 W-2024-0871 对应会话时，确认 chatId 指向目标对话 |
| 运行详情 | detail=true 时中间值与完整结果保存在 responseData | 核对检测报告相关节点是否实际返回，未返回即记录缺口 |
| 身份代理 | authProxy 需团队所有者开启，代理身份仍需目标应用与会话权限 | 交接权限时核对代理身份是否具备目标应用权限 |
| 会话来源 | source=api 只获取通过 API 创建的会话 | 核对交接涉及会话是否属于 API 来源，页面会话另计 |
| 反馈字段 | loadCustomFeedbacks 控制是否读取自定义反馈 | 核对日志中反馈数据是否随请求加载 |
| 变量替换 | variables 为对象，替换模块输入框中的 [key] | 核对交接请求中的工单号是否作为变量正确传入 |

本次假设试验起点：将 detail 设为 true，理由是需要核对中间节点是否返回；与 detail=false 的返回内容比较，观察 responseData 是否出现。

## 容易做错的三处

1. 把检测报告的建议更换当作已授权执行。材料原文二写明客户尚未确认，这是待核实状态。检查方式：输入检测报告原文与拟稿句，比较「建议更换」与「已获授权」是否同一字段的互斥取值，观察拟稿句是否超出原文支持范围。

2. 把交接请求当作权限已移交。请求文本只表达移交意向，未载明审批完成。检查方式：输入交接请求原文，比较其中是否出现审批完成、生效日期等字段，观察是否只有请求动作而无授权结果。

3. 把会话列表中的记录当作完整审计留存。getHistories 返回 chatId、title、updateTime 等字段，未返回业务处理结果。检查方式：输入会话列表响应与工单材料，比较字段范围，观察业务数据是否在日志中缺失。

## 怎么确认配好了

- 验证一：输入材料原文一、材料原文二与拟稿句。比较拟稿句中「已获授权」与原文二「客户尚未确认」是否同一字段的互斥取值。满足条件为：识别出拟稿句缺少授权证据，判定为未获支持，保留证据缺口。

- 验证二：输入交接请求原文。比较请求中是否载明审批完成、生效日期或授权范围。满足条件为：确认请求处于待处理状态，不属于已完成移交，不推定权限已变更。

- 验证三：输入会话列表响应与工单材料。比较响应字段与业务处理字段是否重合。满足条件为：确认日志字段不包含换货审批结果，记录为审计缺口，需另接系统实现业务动作。

三项验证均为纸面核对，未实际执行。
