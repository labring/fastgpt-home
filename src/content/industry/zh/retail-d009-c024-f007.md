# 品牌商场专柜运营的运营权限与交接管理：对话日志与审计

## 这个品类的数据长什么样

商场专柜与品牌直营街店的关键差别在于统一收银与扣点结算：销售小票由商场POS产生，品牌ERP与财务系统另行记录，月结对账单需要与商场数据逐笔核对。日常文档包括联营扣点合同、商场活动函、销售小票和月结对账单。数据更新频率为日与月，对账差异可能带来活动资源减少或专柜撤场。在对话日志与审计环节，这些特征意味着：日志中的会话身份、运行详情和引用记录需要与上述业务材料对应，才能支撑运营权限与交接的核对。日志存在本身不证明对账完成或合规审计完成，业务审计分工由完整业务方案另行落实。

## 这些特征在「对话日志与审计」这一环带来什么约束

对话身份需要结合 chatId 核对目标对话与业务记录，不同入口的会话不能混算。需要对话接口运行详情时，按官方契约设置 detail 并检查 responseData；detail=false 时不返回中间值。核对日志与接口实际返回字段时，未返回的业务数据不能推定已完整留存。测试模式的身份字段可能与正式调用不同，需要分别核对输入、历史与返回内容。检索或表单收集的值不构成授权，业务验证、审批、数据库写入和外部同步需要各自的下游实现。

假设演练样本：某品牌专柜店长交接时，提供一份纸面材料，内容为“2025年3月1日至3月31日，本专柜在商场POS的销售小票共120笔，品牌ERP同期记录118笔，差异2笔待核对；联营扣点合同约定扣点率为18%，月结对账单尚未收到。”另有一条待判定拟稿句：“交接已完成，全部销售数据一致，扣点费用已结清。”核对对象为上述材料原文与拟稿句，判断拟稿句是否获得材料支持。材料仅显示差异2笔待核对、月结对账单未收到，拟稿句的“全部一致”“已结清”未获支持。

## 配置怎么定

| 配置项 | 本次假设起点或核对项 | 理由与比较方法 |
| --- | --- | --- |
| chatId 使用 | 交接样本中每个对话入口使用独立 chatId | 核对不同入口会话是否混算，比较各入口 chatId 是否唯一 |
| detail 设置 | 需要运行详情时设为 true | 与 detail=false 返回比较，确认 responseData 是否出现 |
| 日志字段核对 | 核对接口实际返回的 moduleName、tokens、quoteList 等字段 | 与业务材料字段逐项对照，缺失字段记录为缺口 |
| 测试与正式身份 | 分别核对测试模式与正式调用的输入、历史与返回 | 比较两者身份字段是否一致，不一致时分别记录 |
| 交接授权状态 | 核对材料中差异笔数与对账单状态 | 待核对与未收到不构成授权执行，记录为待核实 |
| 检索范围 | 核对目标检索范围是否含所需资料 | 资料缺失时记录缺口，不推定已完整留存 |

## 容易做错的三处

1. 将日志存在等同于合规审计完成。日志记录对话内容，对账、留存与合规要求由完整业务方案另行落实，两者不能互相替代。
2. 将检索或表单收集的值当作授权。检索结果和表单输入只提供信息，业务验证、审批和数据库写入需要各自的下游实现。
3. 将待核对状态写成已完成。样本中差异2笔待核对、月结对账单未收到，拟稿句写成“全部一致”“已结清”，属于未获支持的判定。

## 怎么确认配好了

1. 输入样本材料原文与拟稿句，比较拟稿句的“全部一致”与材料中“差异2笔待核对”，观察是否出现未获支持的判定结果。预期为未获支持，不声称已实测。
2. 输入 chatId 分别为两个入口的会话记录，比较两条记录的 chatId 与业务材料对应关系，观察是否出现混算。预期为分别记录，不将不同入口合并计算。
3. 输入 detail=true 与 detail=false 两次请求的返回，比较 responseData 是否出现，观察字段差异。预期为 detail=true 时出现 responseData，detail=false 时不出现，具体字段以实际返回为准。
