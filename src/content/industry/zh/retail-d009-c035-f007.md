# 外贸退运与索赔的运营权限与交接管理：对话日志与审计

## 这个品类的数据长什么样

退运索赔处理的是出口后的逆向物流与责任认定，材料来自客户邮件、质检报告、海关系统与保险理赔系统，更新不定期、每案一批。日常文档包括退运协议、索赔函、质量报告、退运报关单。同一条对话记录可能同时牵涉退运原因确认、申报办理与索赔证据提交三个环节，运营交接时若只凭对话内容判断某一步已获授权，容易把讨论当成决定。

## 这些特征在「对话日志与审计」这一环带来什么约束

对话接口以 chatId 定位某个应用下的会话，以 dataId 定位会话下的某条对话。运营交接需要结合这两个标识核对目标对话与对应业务记录，不同入口创建的会话不合并计算。获取会话列表时 source=api 只返回通过 API 创建的会话，页面会话不在其中；清空应用会话同样只清 API Key 创建的会话。需要运行详情时按官方契约设置 detail，非流式结果保存在 responseData，流式结果按 event 区分，节点完整响应在 flowResponses。接口返回字段构成日志留存的实际范围，未返回的业务数据不能推定为已完整留存。对账、留存与合规要求由完整业务方案另行落实，日志存在不等于完成合规审计。authProxy 用于代理团队成员身份，需要团队所有者创建或编辑该 key 时开启，代理身份仍需具备目标应用和会话权限；该能力仅适用于 FastGPT >= v4.15.0。

假设演练样本：某外贸售后人员在内部应用发起会话，chatId 为 "case-2201"，其中一条对话 dataId 为 "rec-07"。供核对的材料原文为：「2024年3月5日，质检报告 Q-0305 载明批次 B-77 存在尺寸偏差，客户于 3月8日邮件提出退运意向。退运协议尚未签署，索赔函处于草稿状态。」一条待判定的交接请求为：「请将 case-2201 中 rec-07 标记为退运协议已签署并转入索赔提交。」该请求中的状态与材料原文不符，属于待核实或未获支持。

## 配置怎么定

| 核对项 | 官方已说明的设置或实施核对点 | 与本页样本的关系 |
| --- | --- | --- |
| 会话定位 | 以 appId 与 chatId 确定目标会话 | 核对 case-2201 归属的应用 |
| 对话定位 | 以 dataId 确定会话下的对话 | 核对 rec-07 是否属于该会话 |
| 会话来源 | source=api 只取 API 创建的会话 | 判断该会话是否出现在 API 列表 |
| 运行详情 | 需要中间值时设置 detail=true | 检查 responseData 中实际返回字段 |
| 身份代理 | authProxy 需所有者开启，且仍需应用与会话权限 | 核对交接人是否具备目标会话权限 |
| 留存边界 | 接口返回字段即日志可见范围 | 未返回的签署状态不作为已留存证据 |

detail 取值属于本次假设试验起点，选择 true 是为了获得 responseData 中的节点响应，与仅取最终回答的 false 结果比较。接口不返回实际消耗 Token 值，需要时设置 detail=true 并手动计算 responseData 里的 tokens。

## 容易做错的三处

1. 把材料中的退运意向当作退运协议已签署。输入是材料原文与交接请求，比较的是「尚未签署」与「已签署」两种状态，观察结果是两者不一致，请求未获支持。
2. 把对话记录存在当作合规审计已完成。输入是日志可见字段与业务留存要求，比较的是接口返回范围与审计所需材料，观察结果是缺口仍待核实。
3. 把检索或表单填写当作授权执行。输入是交互节点返回的展示配置，比较的是展示配置与人工授权记录，观察结果是表单收集值不构成审批。

## 怎么确认配好了

1. 输入假设样本中 chatId 为 "case-2201"、dataId 为 "rec-07" 的会话与对话标识，比较二者归属关系，观察结果应能确认该对话属于该会话；若查询返回空列表，记录缺口而不判定为不存在。
2. 输入材料原文中「退运协议尚未签署」与交接请求中「已签署」，比较同一字段的状态取值，观察结果应为状态不一致，请求判定为待核实。
3. 输入 detail=true 的请求，比较 responseData 中实际返回的模块字段与业务所需字段，观察结果应列出缺失字段并保留为未知，不推断系统报错原因。
