# 平台多店铺矩阵管理的运营权限与交接管理：对话日志与审计

## 这个品类的数据长什么样
多店矩阵的对话数据分散在各店铺入口，同一业务对话可能来自页面、分享链接或 API。行业资料把店铺授权清单、价格管控表、窜货投诉单、月度销售报表列为日常文档，对话日志需要与这些文档对齐主体与期间。资料给出日更与月更两种节奏，本页只按资料写日、月，不推导批量同步或实时机制。对话身份依靠 chatId 区分，不同入口的会话不能混算。

## 这些特征在「对话日志与审计」这一环带来什么约束
运营交接时，材料、操作与请求各自处于不同状态。检索命中、表单填写、交互节点返回都属于过程信息，不构成授权执行。官方文档说明：调用 chat/completions 时 model、temperature 等参数字段无效，由编排决定；detail=true 时中间值与完整结果保存在 responseData；会话列表按 source=api 只取 API 创建的会话；清空应用会话只清 API Key 创建的会话。日志存在不等于完成合规审计，对账、留存与合规要求由完整业务方案另行落实。

假设演练样本（纸面，无真实主体）：材料原文一「店铺A授权清单：授权对象为经销商甲，授权店铺为A店，有效期2025年1月1日至2025年6月30日。」原文二「窜货投诉单：投诉对象为A店，投诉日期2025年3月10日，状态为待核实。」拟判定交接请求：「A店在2025年3月的对话日志可移交经销商甲查阅。」需比较：授权对象与店铺是否匹配、投诉状态、期间是否落在有效期。

## 配置怎么定
下表为本次假设试验起点与核对项，不表示官方默认值。

| 配置项 | 本次假设起点 | 选择理由与比较对象 |
| --- | --- | --- |
| body.appId | 填入目标应用 ID | 与 chatId 同应用核对，判断会话归属 |
| chatId | 长度小于250的唯一串 | 与业务记录中的对话标识逐条比对 |
| detail | 设为 true | 需 responseData 时按官方契约开启 |
| source | 取 api | 只取 API 创建的会话，与页面会话分开 |
| 授权范围 | 按授权清单原文填写 | 与投诉单状态、有效期比较 |
| 审计分工 | 标记为另接系统实现 | 与日志留存区分，不视为已完成 |

## 容易做错的三处
1. 把检索命中当作授权通过。输入一条查询，比较返回记录与授权清单主体，返回记录含无关店铺即说明检索未做权限隔离。
2. 把待核实投诉当作已确认窜货。输入投诉单状态字段，比较状态取值，只有明确互斥取值才构成矛盾，未载明即待核实。
3. 把交互节点返回当作提交完成。输入交互配置，比较是否出现后续请求，未出现继续调用即流程仍处等待。

## 怎么确认配好了
1. 输入假设样本原文一与拟判定请求，比较授权对象、店铺、期间三项字段，三者同主体同期同字段一致才满足移交条件，否则记录证据缺口。
2. 输入 chatId 与 source=api 的会话列表请求，比较返回列表是否只含 API 会话，出现页面来源会话即不满足。
3. 输入 detail=true 的请求，比较响应是否含 responseData 及其中 tokens 值，缺失即记录未返回，不推定已完整留存。
