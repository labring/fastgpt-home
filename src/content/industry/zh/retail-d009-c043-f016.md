# 平台多店铺矩阵管理的运营权限与交接管理：表单与交互

## 这个品类的数据长什么样

在平台多店铺矩阵管理的运营权限与交接管理中，本页说明FastGPT的表单与交互如何衔接资料。多店铺交接应保留店铺授权范围与投诉对象，名单存在不等于当前人员具有所有店铺操作权限。所用场景为自拟文字测试。

## 这些特征在「表单与交互」这一环带来什么约束

自拟交接有店铺授权清单、待查渠道投诉和某店月报说明，却没有当前操作人的权限依据。表单可收各段所指店铺与待办，人员选择核授权范围或补投诉来源；这里的选项不是店铺身份认证，也不自动切换真实账号。某店资料不能代表整个矩阵，名称相近不足以合并，内部价格控制文件只作为相关来源，不填数值。

## 配置怎么定

| 多店交接核对 | 自拟范围 | 需核关系 |
| --- | --- | --- |
| 授权清单 | 名单非当前权限 | 查真实人员授权 |
| 投诉个案 | 限定店铺 | 排除其他店 |
| 月报说明 | 报告非处理结果 | 取对应业务记录 |
| 选择路径 | 核授权或补来源 | 不切真实账号 |
| 结果范围 | 只更新本店事项 | 不扩全矩阵 |

### 固定版本条件

| 文档项或实施核对项 | 条件 |
| --- | --- |
| `表单输入` | 收集输入并在提交后传值。 |
| `必填信息核对` | 业务必填与缺项处理需另设计。 |
| `用户选择` | 选择结果对应已连接的分支。 |
| `交互状态` | 分别核等待和完成交互状态。 |
| `后续处理分工` | 校验、审批及写入另核结果。 |

## 容易做错的三处

名单冒权限：若列名变成当前人员可操作，应查真实授权关系；他店投诉混入：若另一店个案用于本店，应核投诉对象与接收文本；月报冒处置：若报告记录被写成投诉已解决，应取实际处理结果。三项分别核身份权限、业务归属和执行，不能由一次选择确定。

## 怎么确认配好了

验收比较提交与接收中的店铺说明，沿核授权或补投诉路径查看对应待办。补本店投诉原句后，只更新个案事实，操作权限仍需独立核验。账户操作、对外回复和投诉关闭需另接流程核实际权限及回执，交互被记录不证明已经授权或已办完，也不将一店处理结果扩为全矩阵结论。
