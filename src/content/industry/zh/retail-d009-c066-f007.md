# 短视频挂车分销运营的运营权限与交接管理：对话日志与审计

## 这个品类的数据长什么样
短视频挂车分销以内容长期曝光和商品链接转化为主，不依赖实时讲解，主要数据来自精选联盟、短视频播放数据、商品成交数据和平台规则，典型主体包括内容运营、达人BD和商品分销专员。这些特征在对话日志与审计环节的影响集中在三点：会话以 chatId 区分，同一应用下不同入口的会话不能混算；运行详情需要按官方契约设置 detail 并检查 responseData；接口实际返回的字段决定日志能核对到什么，未返回的业务数据不能推定已完整留存。日志存在不等于完成合规审计，对账、留存与合规要求由完整业务方案另行落实。

## 这些特征在「对话日志与审计」这一环带来什么约束
运营交接时，会话、对话与运行详情分属不同层级：chatId 标识一个会话，dataId 标识会话下某一条对话，appId 标识应用。source=api 的会话列表只覆盖通过 API 创建的会话，页面会话不在其中。detail=true 时响应包含 responseData，其中模块的 moduleName、moduleType、tokens、quoteList 等字段可供核对；detail=false 时不返回这些中间值。authProxy 代理团队成员身份需团队所有者创建或编辑 key 时开启，代理身份仍需具备目标应用和会话权限。检索与相似度不承担权限或实体隔离职责。

假设演练样本：某短视频挂车分销团队的内容运营在交接清单中写道“达人BD 已把 3 月挂车商品清单和佣金计划交给商品分销专员，对话日志按 chatId 归档，交接完成”。拟判定句为“本次交接已获得运营权限并完成执行”。材料原文只说明材料移交和归档方式，未载明授权范围、生效时间或执行确认，因此该拟判定句未获支持，授权状态待核实。

## 配置怎么定
| 配置项 | 本页用途 | 核对方式 |
| --- | --- | --- |
| appId | 定位目标应用，区分同一 key 下不同应用 | 请求体传入 appId，或使用 Authorization: Bearer apiKey-appId |
| chatId | 定位会话，长度小于 250，需自行确保唯一 | 与业务记录中的会话标识逐条比对 |
| dataId | 定位会话下某条对话 | 通过获取对话列表接口读取后核对 |
| detail | 决定是否返回中间值 | 需要运行详情时设为 true，检查 responseData |
| source | 限定会话来源 | source=api 时只返回 API 创建的会话 |
| loadCustomFeedbacks | 控制是否读取自定义反馈 | 按需传入，核对返回的 customFeedbacks |

本页假设试验起点：detail 取 true，因为需要核对 responseData 中的模块字段；source 取 api，因为交接范围限定为 API 创建的会话。这两个取值是本次假设演练的起点，不是官方默认值，需与官方文档说明的条件逐项比较后确认。

## 容易做错的三处
1. 把材料移交当作授权完成。样本中“已交给商品分销专员”只说明移交动作，未载明授权范围与生效时间，判定为交接已获权限属于未获支持。
2. 用相似度或检索结果代替权限判断。quoteList 中的 score 只反映相关度，不构成实体或权限过滤，不能据此认定某条记录属于某位运营。
3. 把 detail=false 的响应当作完整日志。detail=false 不返回 responseData，模块级 tokens、quoteList 等字段缺失，据此断言日志完整留存缺少依据。

## 怎么确认配好了
1. 输入样本中的交接清单原文与拟判定句，比较“已交给”与“已获授权”是否同主体、同期间、同字段；只有出现明确授权范围与生效时间的记录，才满足判定条件。
2. 输入样本中的 chatId 与业务记录中的会话标识，比较两者是否一致；只有逐条一致且 source=api 覆盖范围内，才满足归档核对条件。
3. 输入 detail=true 的请求与返回的 responseData，比较模块的 moduleName、moduleType 是否与预期节点对应；只有字段实际出现且可读，才满足运行详情核对条件。以上均为纸面预期，未实际执行测试。
