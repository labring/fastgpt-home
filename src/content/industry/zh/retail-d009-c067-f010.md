# 社区团购团长运营的运营权限与交接管理：引用来源与溯源

## 这个品类的数据长什么样

社区团购团长运营围绕社区节点和佣金展开，不直接承担冷链质检。主要数据来自社区团购后台、团长社群、订单明细与售后记录，日常文档包括团长协议、佣金表、提货清单和社群公告。招募团长、核对提货、处理邻里售后是三个耗时环节。日更或每团更新的节奏，意味着交接时若引用旧版佣金表或旧版公告，可能把已失效的费率或提货安排当成当前依据。引用来源与溯源要解决的是：某条交接结论所依据的材料，究竟是哪一份、哪一版、处于什么状态。

## 这些特征在「引用来源与溯源」这一环带来什么约束

知识库搜索节点可选择多个相同向量模型的知识库作为检索范围，输出为引用内容数组，长度可以为 0，空数组同样走通输出链路。检索结果交给回答环节后，回答与引用原文需逐条核对。语义召回与相关度只反映内容相似程度，不承担权限、主体或实体隔离；检索本身不构成授权。同一向量模型是共同关联的前提，该要求只适用于知识库关联，不能扩展为其他外部系统也要同模型。混合检索通过 RRF 融合多路结果，重排需具备模型并按设置启用，二者都不代表每次请求全部路径执行。

假设演练样本：材料原文为「团长协议（编号 T-0417）第 3 条：团长可查看本团订单明细，佣金费率以当期佣金表为准。当期佣金表（版本 2024-06）载明 A 类团佣金费率为 8%。社群公告（2024-06-20）通知：A 类团提货时间调整为每周三。」待判定拟稿句为「团长可自行修改本团佣金费率，并按公告调整后的时间提货。」核对对象是协议第 3 条、佣金表版本与公告日期，判断该拟稿句是否获得原文支持。

## 配置怎么定

| 配置或核对项 | 本次假设试验起点 | 选择理由与比较对象 |
| --- | --- | --- |
| 关联知识库 | 选取存放团长协议与佣金表的知识库 | 需同一向量模型才可共同关联，先核标识 |
| 引用上限 | 起点设为覆盖一份协议加一份佣金表 | 与单份材料实际长度比较，非官方默认 |
| 最低相关度 | 起点设为中等，观察召回范围 | 与拟稿句核对所需的召回完整度比较 |
| 引用内容输出 | 承接引用数组，含长度为 0 的情况 | 与下游回答环节的输入设计比较 |
| 资料版本核对 | 以 2024-06 佣金表与 2024-06-20 公告为准 | 与历史版本比较，确认是否仍有效 |
| 人工核对动作 | 逐条比对回答与引用原文 | 与拟稿句逐字段比较主体、对象、状态 |

## 容易做错的三处

1. 把检索命中当成授权依据。输入是拟稿句与引用原文，比较的是原文是否载明修改费率的权限，观察结果是原文只写「可查看本团订单明细」，未载明修改权限，该拟稿句未获支持。待审核状态不证明缺少操作权限，只能记为待核实。
2. 把不同版本的佣金表混用。输入是版本 2024-06 与历史版本，比较同一字段的费率取值，观察结果是两版费率不同，需以当期版本为准，不能据旧版得出当前费率。
3. 把空引用数组当成流程中断。输入是明确的纸面输入 `[]`，比较下游设计是否承接零长度输出，观察结果是链路走通，不能据此断言检索必然返回空或必然报错。

## 怎么确认配好了

1. 输入假设样本中的协议第 3 条与拟稿句，比较拟稿句是否超出原文载明的查看权限，观察结果是拟稿句含原文未载明的修改权限，判定为未获支持。
2. 输入佣金表版本 2024-06 与历史版本，比较同一费率字段，观察结果是版本间取值不一致，确认以当期版本为核对基准，历史版本仅作对照。
3. 输入明确纸面输入 `[]` 与下游设计，比较零长度引用是否被承接，观察结果是输出链路走通；检索是否命中、是否全部召回均保持未知，不作保证。
