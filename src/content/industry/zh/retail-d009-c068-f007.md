# 社区团购预售集单的运营权限与交接管理：对话日志与审计

## 这个品类的数据长什么样

预售集单先收订单再组织采购履约，这一顺序决定了对话日志承载的内容与团长关系维护场景不同。小程序订单、供应商库存、团长反馈与仓配排线在一天内多次变化，预售商品表、集单结果、采购计划与截单通知构成日常文档主线。运营交接需要核对的是：某场次在某时间点的订单归属、截单状态、采购是否已下、分拣波次是否已排。日志只能反映系统调用与返回，业务状态须回到上述文档本身。

## 这些特征在「对话日志与审计」这一环带来什么约束

对话身份结合 chatId 核对目标对话与业务记录，不同入口的会话不可混算。需要运行详情时按官方契约设置 detail 并检查 responseData；detail=true 时模块状态、完整结果保存在 responseData 中，stream 模式通过 event 区分。字段含义以接口实际返回为准，未返回的业务数据不能推定已完整留存。测试模式的身份字段可能与正式调用不同，分别核对输入、历史与返回内容。对账、留存与合规要求由完整业务方案另行落实，日志存在不等于完成合规审计。

假设演练样本：材料原文为「预售商品表 P-0417 第 3 场，截单时间 2025-04-17 20:00，集单结果 214 单，采购计划状态：待审核。」以及「截单通知已发出，仓配排线未开始。」拟判定句为「本场已完成采购下采，可交接分拣波次。」该句与原文比较：原文采购计划状态为待审核，未载明下采完成，判定为未获支持。

## 配置怎么定

| 项目 | 本页相关设置或核对项 | 核对方式与边界 |
| --- | --- | --- |
| 对话身份 | chatId 与目标业务场次对应关系 | 逐条比对 chatId 与场次记录，不合并不同入口会话 |
| 运行详情 | detail=true 时读取 responseData | 检查模块状态与完整结果字段，未返回项记为未知 |
| 会话历史 | 按 appId、chatId 取记录 | 核对 dataId 与对话内容，确认来源为 api 或页面 |
| 反馈字段 | loadCustomFeedbacks 控制读取 | 需要时开启，不将反馈视为业务审批 |
| 交接请求 | 拟交接句与材料原文逐字段对照 | 状态、对象、期间一致才可判定，缺失保留缺口 |
| 数值起点 | 本场 214 单为假设试验起点 | 与集单结果文档值比较，非官方默认值 |

## 容易做错的三处

1. 将待审核当作已下采。输入为采购计划状态「待审核」，比较对象是拟交接句中的「已完成下采」，观察结果是两者状态字段不一致，判定为未获支持。
2. 混算不同入口会话。输入为两个 chatId 的记录，比较对象是同一场次订单归属，观察结果是会话来源不同却合并计数，须分别核对。
3. 以检索结果代替授权。输入为检索返回的引用列表，比较对象是交接请求的授权状态，观察结果是引用存在但无审批字段，判定为待核实。

## 怎么确认配好了

1. 取假设样本原文与拟交接句，逐字段列出主体、对象、状态与期间，比较采购计划状态与拟句陈述，仅当状态字段一致且期间相同才判为一致，否则记为未获支持。
2. 取两个不同 chatId 的会话记录，比较其 appId、chatId 与场次归属，观察是否被合并计数，若来源不同则分别列出，不执行跨入口汇总。
3. 取一次 detail=true 的返回，检查 responseData 中模块状态与完整结果字段，与材料原文对照，未返回的业务数据记为未知，不推定已留存。
