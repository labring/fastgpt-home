# 社区团购预售集单的运营权限与交接管理：引用来源与溯源

## 这个品类的数据长什么样

预售集单先收订单再组织采购履约，与团长关系维护型运营的差别在于，运营交接需要把预售商品表、集单结果、采购计划、截单通知这四类材料连同其引用来源一起移交。这些材料按日和每场更新，交接时若只移交结论而不移交来源，接手人无法判断某条集单数量来自哪一版商品表、哪一次截单通知。引用来源与溯源这一环的任务，是让运营权限与交接管理中的每条关键结论都能回到具体文档版本与具体字段。

## 这些特征在「引用来源与溯源」这一环带来什么约束

检索环节的引用内容以数组输出，长度可以为 0，空数组不代表工作流报错终止。关联知识库要求向量模型相同，跨模型的知识库不能共同关联，核对时先核标识并排除不符者。最低相关度是过滤阈值，不承担权限或实体隔离功能；检索结果不构成授权。以下样本用于纸面核对。

假设演练样本：材料原文为“预售商品表 V3 载明：2025-06-10 场次，A 仓菠菜 200 份，截单时间 18:00。截单通知 N-0610 载明：该场次菠菜按 200 份下采，采购计划 P-0610 已生成，状态为待审核。”待判定拟稿句为“采购计划 P-0610 已批准，菠菜 200 份可执行下采。”

该拟稿句与原文的差异在于：原文只写待审核，拟稿句写成已批准；原文未载明批准主体与批准时间。待审核不证明缺少操作权限，也不等于批准。判定按同主体、同期间、同一字段进行，状态字段只有明确互斥取值才构成矛盾，此处属于未获支持。

## 配置怎么定

| 配置或核对项 | 本次假设起点 | 选择理由与比较对象 |
| --- | --- | --- |
| 关联知识库 | 仅选向量模型相同的预售资料库 | 与另一向量模型不同的库比较标识，不符者排除 |
| 搜索模式 | 混合检索 | 与语义检索比较编号类字段命中情况 |
| 引用上限 | 假设起点 3000 tokens | 与 1500 tokens 比较引用条数是否够覆盖四类材料 |
| 最低相关度 | 假设起点 0.4 | 与 0.2 比较无关片段是否减少 |
| 引用内容承接 | 检索输出交给回答环节 | 逐条核对回答与引用原文 |
| 资料时效核对 | 用当前版与历史版商品表各一份 | 比较同一场次数量字段是否一致 |

## 容易做错的三处

1. 把待审核状态写成已批准。输入为样本原文，比较状态字段取值，可观察结果是拟稿句出现原文没有的批准结论。
2. 把检索命中当作操作授权。输入为一次检索返回的引用数组，比较引用内容与授权字段，可观察结果是引用中没有批准主体或授权范围。
3. 把不同向量模型的知识库共同关联。输入为两个库的向量模型标识，比较标识是否一致，可观察结果是不一致的库被排除。

## 怎么确认配好了

1. 输入样本原文与拟稿句，比较状态字段，只有拟稿句保留待审核且不添加批准结论，才满足条件。
2. 输入一份纸面引用数组 `[]`，比较下游回答环节的设计，只有下游按空引用继续走通且不虚构来源，才满足条件。
3. 输入两个向量模型标识不同的库，比较标识，只有不符者被排除且未执行跨模型检索，才满足条件。以上均为纸面核对，未实际执行。
