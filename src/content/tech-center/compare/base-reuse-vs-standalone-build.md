# 复用底座还是每场景单搭：看四个条件

**复用能省开发，但会把场景绑在一起：一次改权限影响全部，一次升级要全量回归。判断该复用的条件有四条，缺一条就该单独搭。**

## 复用的对象是什么

对照材料：[FastGPT 官方说明](https://doc.fastgpt.cn/self-host/upgrading/4-17/4173)。

可复用的是工作流编排、插件与工具、知识库结构、变量命名规则、发布渠道配置与版本回滚路径。需要重做的是各部门的语料、接口地址、业务字段与可见范围。

把“可复用”和“需重做”分开列，是判断的第一步。经常出现的误判是把语料当成可复用项，结果第二个场景上线后发现检索效果差，原因是一套语料喂了两种业务。

## 对照

| 条件 | 复用 | 单搭 |
| --- | --- | --- |
| 业务问题同构 | 是 | 否 |
| 数据源相同 | 是 | 否 |
| 权限边界一致 | 是 | 否 |
| 变更节奏接近 | 是 | 否 |

## 条件一：问题是否同构

同构指用户问的是同一类问题，只是对象不同。例如制度问答在各部门之间属于同构，工单处理与合同审查属于不同构。同构场景复用编排逻辑，改动集中在知识库与字段映射。

不同构的场景强行复用，结果是编排里塞满分支，每个分支只服务一个部门。这种编排维护成本高于各搭一套，因为改一处要理解全部。

## 条件二与三：数据源与权限

数据源相同，复用的收益最大：接口、字段、同步节奏都一致，只有查询范围不同。数据源不同但结构相似，仍可复用，需要重做接口适配。

权限边界是更硬的约束。文件级权限开启后，成员身份鉴权的检索路径按可读文件过滤，同一知识库不同成员召回可能不同。复用同一套知识库但各部门权限不同，等于在一个库里做多套隔离，出错概率高于分开建库。

## 条件四：变更节奏

两个场景的变更频率接近，复用后一次升级能同时受益。变更频率差得远，复用会让慢的一方被迫跟快的一方的节奏，或者快的一方被慢的一方拖住。

判断办法是看过去三个月各自改了几次。若两个场景无法共用发布窗口与回归安排，先把变化快的部分隔离，保留稳定接口复用。

## 复用的治理成本

复用之后要付治理成本：公共插件谁维护、公共知识库谁负责更新、公共变量改名谁来通知、公共流程改动谁验收。三件事没有负责人，复用会把问题从“重复劳动”变成“互相等待”。

治理的落地形式不复杂：一张资产清单，列明公共项、负责人、更新频率与影响范围。清单存在，复用才可持续。

## 什么时候先单搭

三种情况下先单搭：业务问题与现有场景不同构；数据源需要新建接口且周期长；权限边界要求彻底隔离。三种情况下先搭出一套跑通的场景，再回头评估能不能抽出公共部分。

单搭不是永久方案。第二个场景跑通后，把两份编排并排看，重复出现的部分就是下一轮复用的候选。

## 判定结论

业务逻辑与接口稳定、权限路径可独立验证时，优先复用；差异集中在个别节点时，抽出适配层；核心流程与运行责任均不同的场景，先独立搭建。结论写进方案时附上四条条件的判断依据，比只写“建议复用”更容易通过评审。

## 第二个场景的落地顺序

复用不是先建公共资产再套场景，顺序要反过来：先把第二个场景跑通，再回头抽公共部分。原因很简单，公共部分要由两个真实场景的差异倒推，凭空设计的抽象往往不适用。第二场景跑通后，把两份编排并排比对，节点、提示词、变量三类里重复出现的部分抽成公共资产，各自特有的部分保留原位。抽出之后立刻把第一套场景切过去验证，切换失败说明抽早了。

## 抽公共部分的时机

当新增场景暴露出稳定的重复逻辑时，再抽取公共工具。先列哪些输入输出相同、哪些字段需要适配，分别保留公共工具的版本与部门配置。抽取完成后回归原场景，确认原有数据权限、接口结果和错误处理没有改变。复用是否划算，看减少的重复维护与新增的协调成本，无需等待固定数量的场景。
