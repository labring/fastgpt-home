# 跟版本升级还是冻结：先看三件事

**冻结版本不是保守，升级也不是激进。真正的判断依据是三件事：安全补丁能不能单独拿、镜像能不能成套、变更窗口排不排得出来。三件事答完，策略自然清楚。**

## 两种策略的实际差别

对照材料：[FastGPT 官方说明](https://doc.fastgpt.cn/zh-CN/self-host/upgrading/4-17/4173)。

跟版本升级意味着每个稳定版本都跟，好处是缺陷修复、安全补丁与新能力持续到位，坏处是每次升级都要安排窗口、做回归、核回填。冻结版本意味着停在某个版本长期运行，好处是环境稳定、变更少，坏处是缺陷与补丁要靠回移，越往后回移成本越高。

两种策略的分水岭是“能不能拿到补丁”。如果冻结的版本仍能通过维保拿到安全补丁，冻结就是可行的；拿不到补丁，冻结等于把风险留在系统里。

## 对照

| 项 | 跟版本升级 | 冻结版本 |
| --- | --- | --- |
| 缺陷修复 | 随版本获得 | 依赖回移或维保 |
| 安全补丁 | 随版本获得 | 需确认能否单独提供 |
| 兼容性验证 | 每次升级做一次 | 环境、依赖或接口变化后复查 |
| 变更窗口 | 按版本节奏安排 | 按需安排 |
| 主要风险 | 升级引入新问题 | 漏洞与依赖老化 |

## 镜像能不能成套

升级的硬约束在镜像。启用 Agent 沙盒时，主服务、Agent 沙盒与预览代理须使用配套版本，应用与专业版、插件、代码沙盒、AI Proxy 四类镜像要对应到同一套版本。这意味着升级要整套替换镜像，只换一个不够，回滚也要整套回滚。

冻结版本同样受这条约束影响：如果只给某一个镜像打补丁而不动其他镜像，理论上可行，实际操作中容易造成版本错配。选择冻结策略时，把“只升单镜像”的做法排除掉，能减少一类故障。

## 回填任务怎么核

升级之后有后台任务要跑。以 v4.17.3 为例，启动依赖完成后会执行三项回填：沙盒团队归属、目录祖先路径、系统模型价格换算，最多三个并发，失败项修数据后可重试。其中价格迁移未完成时，系统模型在该版本下暂按免费处理，账单会对不上。

这决定了升级后的第一件事是对账。三项回填的结果要逐项查看，价格迁移要看系统模型是否已按百万单位写入，团队归属要看成员能否看到自己的实例。三项都过，升级才算完成。

## 变更窗口怎么排

窗口长度由三块决定：镜像替换与启动、回填任务执行、回归验证。前两块时间相对固定，第三块取决于集成面的大小。集成接口多的部署，回归时间长，窗口要按最坏情况排。

推荐做法是先在测试环境演练一次，记录三块各花多久，再按记录排生产窗口。凭经验拍的时间通常偏短，尤其是回填任务在数据量大时会拉长。

## 什么时候必须跟

三种情况下必须跟版本：所用版本存在影响业务的缺陷且无回移补丁；合规要求跟进安全补丁；需要用到只有新版本才有的能力。三种情况之外，冻结一个经过验证的版本并保持补丁可得，属于合理策略。

反过来，跟版本的代价要提前算：每次升级的窗口、回归人力、可能的返工。把这些写进年度运维计划，比每次临时协调更省事。

## 判定结论

先问补丁能否单独获取，再问镜像能否成套，最后问窗口能否排出。三个答案组合起来，就是策略：补丁可得且窗口排得出，跟版本；补丁可得但窗口排不出，冻结并保持补丁通道；补丁不可得，无论如何要升。

## 回滚也是升级的一部分

回滚方案要写清四件事：镜像回到哪一套、数据是否兼容、回填任务是否需要回退、回滚后如何验证。四件里数据兼容最容易出问题，新版本写入的数据结构未必能被旧版本读取，回滚前先确认这一点，否则回滚会把可用状态变成不可用状态。回滚演练与升级演练同等对待，演练一次的成本远低于生产事故。
