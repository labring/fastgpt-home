# 用对话接口接入应用：会话、历史记录与运行详情的获取方案

## 这件事在什么时候变成问题
当企业将对话能力集成到外部业务系统时，基础的单次调用往往无法满足长期业务需求。仅实现单次问答调用时，无法保留用户多轮对话的上下文，无法复用历史交互记录，也无法追踪单次运行的具体节点执行情况。当业务需要支撑多用户并发会话、留存完整交互链路、排查调用异常时，原有的简单调用逻辑就会暴露局限性。

比如企业内部的客服助手系统，需要为每个用户分配独立的对话会话，保留用户的历史提问与助手回复，方便后续回溯；又比如运维自动化工具，需要在调用对话接口后，查看模型生成回答的具体节点、知识库召回片段、工具调用结果等细节，定位执行异常。此时，如何管理chatId与会话历史、如何正确传递业务变量、如何获取单次运行的详细节点信息，就成为必须解决的核心问题。这些问题不会在单次独立调用中显现，但在规模化、持久化的业务集成场景中，会直接影响系统的稳定性与可维护性。

## 需要先定下来的判据
| 判据 | 取什么值 | 依据 |
|---|---|---|
| chatId使用规则 | 按业务场景选择复用或新建 | 官方文档发起会话参数说明 |
| variables传递方式 | 按应用编排定义的变量名传递 | 官方文档发起会话参数说明 |
| detail参数配置 | 调试场景设为true，生产场景按需开启 | 官方文档发起会话注意事项 |
| 会话历史拉取范围 | 按分页参数控制偏移与数量 | 官方文档对话管理接口说明 |
| 运行详情获取方式 | 开启detail=true或调用日志接口 | 官方文档响应示例与日志接口 |
| 鉴权方式选择 | 优先使用body.appId+APIKey组合 | 官方文档密钥使用规范 |

上述判据的取舍需结合业务实际需求确定。chatId复用适合需要保留多轮上下文的场景，新建chatId则适用于单次独立对话。variables的传递必须与目标应用的编排配置完全匹配，否则参数无法被正确识别。detail参数开启后会增加响应数据的体积，生产环境若无需调试节点详情，可关闭以降低网络传输成本。鉴权方式的选择需结合使用的SDK兼容性，body.appId的优先级更高，无需在APIKey中嵌入appId，部分旧版SDK可能需要调整BaseUrl路径补充v1前缀以避免404错误。

## 具体怎么做
### 会话与历史记录管理
首先确定chatId的生成规则，需确保其为非空字符串且长度小于250，可直接使用外部系统的对话框ID或用户唯一标识。若需使用FastGPT内置的上下文功能，调用发起会话接口时传入chatId，此时接口会自动从数据库加载对应会话的历史消息，仅将请求体中messages数组的最后一个内容作为当前用户问题，其余历史消息会被忽略。

若需获取现有会话的基本信息，可调用GET接口`/core/chat/init`，传入appId与chatId参数，返回结果包含会话的配置变量、应用信息等内容。若需拉取会话的历史对话记录，可调用POST接口`/core/chat/record/getPaginationRecords`，传入appId、chatId、offset与pageSize参数，支持按偏移量分页获取历史消息，还可通过loadCustomFeedbacks参数控制是否加载自定义反馈内容。若需获取当前应用下所有API创建的会话列表，可调用POST接口`/core/chat/history/getHistories`，传入appId、offset、pageSize，并将source参数设为api，即可返回符合条件的会话列表，包含chatId、更新时间、会话标题等信息。

### variables参数传递
variables参数用于向对话应用传递业务变量，需严格按照目标应用编排中定义的变量名作为key，传入对应的值。在普通对话场景中，variables参数需放在请求体的根层级，与appId、chatId等参数同级。若调用的是插件类型的应用，则无需传入chatId与messages参数，仅通过variables传递插件的输入参数即可，插件的输出结果可通过响应中`responseData`数组里`moduleType=pluginOutput`的元素获取。

需要注意的是，传入的model、temperature等参数不会生效，这些配置由应用的编排逻辑决定，无法通过API参数修改。若需传递多模态内容，可将messages数组中content字段替换为数组格式，包含text、image_url或file_url类型的内容，其中文件需提前上传至对象存储并获取公开链接。

### 单次运行详情获取
若需获取单次对话运行的节点详情，需在发起会话请求时将detail参数设为true。此时响应的`responseData`数组会包含每个执行节点的详细信息，包括nodeId、moduleName、moduleType、消耗的tokens、运行时间、上下文预览等内容。普通对话应用的节点信息会包含AI对话节点的执行详情，插件应用的响应中则会额外包含插件输出节点的结果。

对于非流式请求，完整的节点详情会直接包含在响应体中；对于流式请求，可通过监听`event=flowNodeStatus`与`event=flowResponses`的事件流，获取实时的节点执行状态与详情。若需获取应用的整体运行统计数据，可调用日志接口`/proApi/core/app/logs/getTotalData`与`/proApi/core/app/logs/getChartData`，分别获取累积的用户数、对话数、积分消耗，以及按时间维度划分的统计图表数据。

## 怎么验收
1. 发起包含合法chatId的会话请求，验证后续同chatId的调用会自动加载历史对话，新的用户消息会被追加到会话历史中。
2. 传递与应用编排匹配的variables参数，调用接口后确认应用正确接收并使用传入的变量值，无参数缺失或识别错误。
3. 开启detail=true参数发起请求，验证响应体中包含`responseData`数组，数组元素包含moduleType、tokens、runningTime等节点执行相关字段。
4. 调用获取会话列表接口，确认返回结果中仅包含通过API创建的会话，且会话的updateTime与实际调用时间一致。
5. 调用分页获取历史记录的接口，验证offset与pageSize参数生效，返回的记录数量符合配置的pageSize值，且按时间顺序排列。
6. 调用修改会话标题或置顶状态的接口，验证会话的自定义标题或置顶状态会被正确更新，后续获取的会话信息包含修改后的内容。

## 边界：什么情况下这套做法不成立
当部署的FastGPT版本低于v4.15.0时，authProxy代理团队成员身份的功能无法使用，且部分API参数的优先级规则与新版存在差异。若同一chatId在短时间内收到大量并发调用，MongoDB可能会触发WriteConflict错误，导致会话更新失败，此时需要调整调用频率或优化数据库配置。

当应用需要处理多模态输入，但部署环境未配置支持多模态的模型或对象存储权限异常时，图片与文件请求可能无法正常解析。插件类型的应用默认仅支持单次运行，无法通过传入chatId实现多轮会话，若需多轮插件调用需额外开发会话管理逻辑。

若使用的SDK不兼容FastGPT的API格式，比如未正确设置BaseUrl路径或请求头，可能会出现404或鉴权失败的错误。未完成版本升级的Sandbox数据迁移，会导致部分会话的文件资源无法正常访问，影响依赖文件的对话执行。此外，当应用开启了严格的权限控制，且调用方未获得目标应用与会话的访问权限时，接口调用会被拒绝。
