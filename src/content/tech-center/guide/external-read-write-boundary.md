# 外部查询和写入怎么划界

在 FastGPT 中与外部系统交互时，需要明确区分只读查询与包含写入的操作。这个界限的划分取决于多个技术因素，包括外部接口的能力、数据校验责任的归属，以及交互流程的设计。选择合适的实现路径，可以有效管理数据一致性与操作风险。

## 实现路径决策

与外部系统集成时，首要任务是根据业务需求和技术条件，选择合适的交互模式。不同的模式在数据处理流程、责任边界和实现复杂性上存在显著差异。

第一种模式是“只读查询”。此模式适用于仅需从外部获取信息的场景。实现时，应用通过 HTTP 接口向外部系统发起请求，获取数据后用于后续的对话或处理流程。这种方式不改变外部系统的任何状态，技术关注点在于正确构造请求和解析响应。例如，查询订单状态或获取产品信息。

第二种模式是“先确认后写入”。当操作需要人工介入决策时，可采用此模式。应用首先通过查询获取相关信息并呈现给用户，待用户确认后，再调用外部的写入接口执行操作。这种模式将决策责任交给了用户，需要设计清晰的交互流程来收集确认指令，并处理可能的操作失败或超时情况。

第三种模式是“委托外部系统校验并写入”。对于业务逻辑复杂或对数据一致性要求高的场景，可以将校验和写入的责任完全委托给外部系统。应用仅负责调用一个封装了完整业务逻辑的接口，由外部系统负责处理所有校验、去重、幂等性判断和状态变更。这种方式简化了应用端的逻辑，但要求外部接口具备完善的事务处理能力。

| 比较维度 | 只读查询 | 先确认后写入 | 委托外部系统校验并写入 |
| --- | --- | --- | --- |
| 主要目的 | 从外部系统获取信息，不产生副作用。 | 在执行有副作用的操作前，获得人工确认。 | 将复杂的业务逻辑和状态管理交由外部系统处理。 |
| 外部接口要求 | 提供稳定、已授权的查询接口。 | 分别或组合提供查询和写入接口。 | 提供封装了完整业务逻辑（含校验）的单一接口。 |
| 数据一致性责任 | 不涉及写入，无此责任。 | 应用需处理确认指令与实际写入操作之间的状态同步。 | 外部系统承担完整的事务和数据一致性责任。 |
| 交互设计 | 重点在于信息展示和引导。 | 需要设计明确的确认、取消和异常处理交互流程。 | 交互相对简单，主要关注最终结果的通知。 |
| 适用组合 | 可作为“先确认后写入”或“委托外部-校验并写入”模式的前置步骤。 | 可与“只读查询”组合，使用查询结果作为确认依据。 | 可与“先确认后写入”组合，将人工确认作为调用外部系统的触发条件。 |

## 技术实现考量

在具体实现层面，无论是使用 HTTP 接口模块还是工具调用（插件），都需要关注配置的准确性。

对于直接使用 HTTP 接口模块的场景，配置时需严格参照外部接口的文档。请求地址和方法必须匹配，地址中可以引用流程中已定义的变量。请求的 Params、Headers 和 Body 结构也需精确对应。鉴权凭证这类敏感信息，应通过安全配置注入，避免直接写入配置中。在调试时需要注意，测试模式下 chatId 和 responseChatItemId 等字段可能不存在，这属于正常现象，不应视为业务故障。

对于使用工具调用的场景，核心在于为模型提供清晰的“工具介绍”。介绍内容用于告知模型工具的用途，应写明输入条件以及不应调用的情况。工具的参数，无论是系统内置还是插件自定义的，都需仔细核对。缺少适合的必须参数时模型可能不调用；可通过交互补全并核对实际请求。在高级编排中，需要将定义好的工具连接到工具调用模块，建议从少量工具开始调试，逐步增加复杂性。流程中的终止节点会结束本次工具调用，此时模型也不再调用 AI 来总结工具结果。

## 验证方法的建议

验证集成时，需要对照节点执行、外部业务返回与数据流转三类记录，逐项确认实际处理到了哪一步。为辅助验证，可准备一组说明性的阅读样例，并检查其数据来源是否可追踪。验证过程可以从有明确答案的场景开始，逐步过渡到信息不完整或存在冲突的场景。当出现预期外的行为时，应记录完整的请求路径、传入变量的实际值以及外部系统的原始返回，以便定位问题。验证本身不能证明外部业务规则、操作权限或商业承诺已完全满足。
