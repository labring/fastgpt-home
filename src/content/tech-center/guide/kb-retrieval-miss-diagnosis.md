# 知识库内容存在却检索不到：从检索词到引用的逐层排查指南

## 这件事在什么时候变成问题
当企业将知识库作为业务流程的核心信息支撑，比如运维排障、客户服务、研发文档查询等场景，单次检索失败会直接导致流程中断。当重复尝试调整检索词、重新上传文档仍无法获取结果时，该问题会从临时不便升级为需要系统性解决的故障。此时，技术与运维负责人需要明确，检索失败往往同时牵涉检索配置、模型参数、存储逻辑等多个环节，需要通过分层排查定位根源，避免盲目调整参数或重建知识库带来的额外成本。当混合检索、重排等高级配置开启时，故障点更隐蔽，普通的关键词调整无法解决问题，此时结构化的排查方法尤为重要。此外，当团队依赖知识库输出关键决策信息时，检索失败可能导致决策偏差，进一步放大问题的影响范围，需要及时介入处理。当检索失败的频次增加，影响到多个业务团队时，该问题会成为需要纳入优先级的技术问题，需要按照标准化流程进行排查。

## 需要先定下来的判据
| 判据 | 取什么值 | 依据 |
| --- | --- | --- |
| 检索词原始输入 | 记录用户实际输入的检索文本 | 官方文档搜索测试参数说明 |
| 检索模式配置 | 核对当前使用的searchMode类型 | 官方文档搜索测试参数说明 |
| 最低相关度阈值 | 按实测场景从低到高逐步验证 | 社区反馈关于最低相关度不生效的问题 |
| 重排模型启用状态 | 核对是否开启重排及对应服务状态 | 官方文档重排模型部署说明 |
| 单次检索token上限 | 核对配置的limit参数取值 | 官方文档搜索测试参数说明 |
| 历史上下文携带规则 | 检查是否引入非当前查询的内容 | 社区反馈关于工作流重排带入历史的问题 |

这些判据的取舍需要结合业务场景的优先级。检索词是排查的起点，优先验证原始输入是否存在拼写或语义偏差，避免因输入错误导致检索失败。检索模式的选择决定了召回的底层逻辑，语义检索依赖向量嵌入结果，适合语义匹配类查询；全文检索基于关键词匹配，适合明确关键词的查询；混合检索结合两者，适用于复杂查询场景。最低相关度阈值的调整需要平衡召回率与准确率，过低会引入无关内容，过高会遗漏有效结果，需通过实际测试确定合适的取值。重排模型的状态直接影响结果排序的准确性，当出现结果相关性混乱时，需优先核对重排服务的运行情况。单次检索token上限决定了召回内容的总量，超出上限会导致有效内容被截断。历史上下文的携带规则会干扰当前检索的准确性，在工作流场景中需明确是否需要保留历史输入。所有判据的验证均需通过可观测的界面或日志数据完成，避免依赖主观判断。

## 具体怎么做
首先开展检索词与检索方式的排查。使用官方提供的搜索测试接口，传入目标知识库ID与用户实际输入的检索文本，获取原始召回结果。核对searchMode参数，该参数支持embedding、fullTextRecall、mixedRecall三种模式，需确认与业务查询类型匹配。若使用全文检索，需确认分词配置是否符合业务场景，比如中文场景下是否启用jieba分词。若检索词存在优化需求，可开启datasetSearchUsingExtensionQuery参数，通过问题优化模型生成更匹配的检索词，同时核对datasetSearchExtensionModel与datasetSearchExtensionBg是否配置正确。若未开启问题优化，需确认原始检索词的语义与知识库内容的匹配度，避免因词形差异导致召回失败。

接下来验证相似度与重排环节。对于开启语义检索的场景，需核对similarity参数的取值，该参数为0到1之间的数值，仅在语义检索或重排开启时生效。若出现返回结果相关性低于预期的情况，可通过搜索测试工具调整similarity阈值，逐步验证符合业务需求的最低标准。若开启重排功能，需检查usingReRank参数是否正确配置，同时核对重排模型的部署状态，若重排服务出现异常，可能导致结果排序混乱或引用为空。此外，需注意重排模型的输入token限制，超出限制会导致重排失败，需调整单次召回的内容数量。若发现重排结果异常，可临时关闭重排功能，验证是否为模型服务导致的问题。

然后开展引用预算与工作流取数环节的排查。核对limit参数的取值，该参数代表单次检索的最大token数量，官方文档说明该值最多为20000 tokens，需根据业务需求调整，避免因token不足导致有效内容被截断。在工作流场景中，需检查是否携带历史对话内容参与检索，部分配置会默认带入多组历史记录，导致当前检索的相关性被干扰，可通过关闭历史上下文携带或调整历史记录数量来解决。此外，需核对知识库的元数据过滤配置，若配置了collectionId过滤或metadata筛选，需确认过滤条件是否正确，避免误过滤有效内容。若使用Milvus向量库，需确认系统版本符合要求，否则全文检索会切换失败，导致无法召回内容。

最后通过日志与系统指标验证排查结果。查看检索接口的响应日志，核对返回的score字段是否符合预期的相关性阈值，若返回的score低于设置的similarity参数，说明相似度过滤未生效。检查数据库的全文索引是否正常更新，若知识库内容更新后未同步到索引，会导致新内容无法被检索到。对于Milvus向量库场景，需确认版本是否为2.5.16或更高，否则系统会终止启动，无法使用全文检索功能。同时，查看系统资源使用情况，若向量库或重排模型出现资源耗尽的情况，会导致检索失败，需调整资源配置或优化检索参数。

## 怎么验收
1. 调用官方搜索测试接口，传入目标知识库ID与用户实际输入的检索词，验证返回结果中包含预设的预期内容。
2. 核对检索模式配置参数，确认与业务查询类型匹配，语义检索场景下返回结果的score字段符合设置的最低相关度阈值。
3. 开启重排功能时，验证返回结果的排序逻辑符合相关性要求，高相关内容的排名优先于低相关内容。
4. 核对单次检索的token上限配置，确认返回结果的总token数未超出设置的limit参数值。
5. 在工作流场景中，验证检索结果仅包含与当前对话检索词相关的知识库内容，未引入非当前对话的历史内容。
6. 查看检索接口的运行日志，确认无报错信息，返回的score字段与配置的最低相关度阈值匹配。
7. 对于使用Milvus向量库的部署，验证系统启动时无版本不兼容报错，全文检索功能正常启用。

## 边界：什么情况下这套做法不成立
这套排查方法依赖于知识库索引的正常生成与存储服务的稳定运行。当向量库或全文检索存储出现故障时，比如Milvus版本低于要求的2.5.16，或MongoDB的全文索引损坏，检索流程会直接失败，此时需优先修复存储服务，这套分层核对方法在存储恢复之前用不上。当知识库内容未完成索引同步，比如分块上传失败、元数据配置错误导致内容未被正确写入索引，本方法无法定位未生成索引的内容。当嵌入模型、重排模型出现服务宕机或资源耗尽的情况，检索结果会出现异常，此时需先验证模型服务的运行状态，再开展后续排查。工作流场景中，若检索节点的权限配置错误，导致无法访问目标知识库，本方法的排查结果会受权限限制，需先完成权限排查。此外，当知识库内容的索引同步存在延迟，新上传的内容未及时更新到索引中，检索结果会遗漏新内容，需等待同步完成或手动触发同步流程。当系统存在未修复的已知bug，比如全文检索多知识库时排序得分异常，本方法的排查结果可能无法覆盖此类场景，需结合版本更新说明确认是否存在已知问题。
