# 私有化部署核对：数据流向、模型调用与分级访问怎么验

**私有化部署只解决“软件放在哪”，采购要回答的是一张更细的表：哪些数据在哪个环节落地、模型调用走本地还是外部、谁能看到哪一类资料。这三件事各自有配置位置和验收动作，任一项没落到纸面，上线后都会被安全评审重新问一遍。**

## 先分开三张表再谈合规

私有化部署的授权形态先说清楚：以单台服务器 License 为基础授权，分标准版、专业版、旗舰版三档，租户上限分别是 100、1000 和不限，专业版起支持 SSO 单点登录与 OA 系统集成，旗舰版另加独立开票与支付板块。商业版由社区版镜像与商业版镜像组成，商业版镜像需要 License 启动，社区版部分可由客户修改，商业版镜像不支持修改。

授权形态决定核对范围：许可覆盖的是约定期限、版本和范围内的一台服务器使用权，不是软件所有权转让。因此采购文件里要同时写明三样东西的边界——服务器数量、版本范围、期限。少写一样，后面加服务器或升版本都要临时补授权。

三张表分别是数据流向表、模型调用表、访问分权表。三张表分开的原因是三者由不同人维护：数据流向表由实施方画，模型调用表由运维方填，访问分权表由业务与 IT 共同确认。混在一张表里，改一处就要拉三方重签。

## 数据流向：从上传到召回的四个落点

知识库类系统的数据落点通常有四处：上传原文件、解析后的文本块、向量化后的索引、检索与对话产生的记录。私有部署的价值在于这四处的存储介质都在客户可控环境内，具体路径取决于客户选择的向量库与对象存储。

核对动作是拿一份真实文档走完全流程，在每一处确认落地位置。原文件看上传目录或对象存储桶，文本块看数据库表，索引看向量库集合，对话记录看会话表。四处都要能指到具体环境，只答“在内网”不够，因为内网也有多个网段和多套存储。

解析环节容易被忽略。文档解析支持多种办公格式，解析过程会抽取正文与内嵌图片，图片会被单独提取并保留引用关系。这条链路意味着一次上传产生的不止一份文件，编制数据流向表时要把提取出来的图片和附件一并计入。

检索库的选择直接改变流向。系统支持 PG、OceanBase、Milvus 等检索库，选型不同，索引数据落在哪套数据库也不同。做安全评审时，方案里要写明用的是哪一套，评审方按那一套的运维规范检查，口径才对得上。

## 模型调用：本地与外部走两条路

模型调用是私有化项目里最需要单独确认的出网环节。系统支持多家模型服务与本地模型接入，可按接口协议扩展；是否出网取决于客户实际配了哪些模型渠道，与是否私有化部署没有直接关系。

核对动作是列出每一个已配置的语言模型、向量模型、重排模型、语音合成与语音识别模型，逐个标注调用地址属于内网、专有云还是公网。五类模型各自绑定不同环节，漏掉向量模型会低估出网面——使用向量检索时，查询通常需要经过向量模型编码，纯全文检索走不同路径。

外部模型若必须保留，就要在调用链上留出入口说明：哪些业务允许触发外部调用、调用时携带什么内容、失败时是否回退到本地模型。回退策略要写成条件句，写明触发条件与回退目标，不接受“自动切换”这类没有条件的描述。

完全离线的部署形态要求模型本地化，模型文件与推理服务的版本随部署环境固定。此时升级节奏由客户掌握，模型版本表要和应用版本表分开维护，回滚时分别核对模型接口、向量维度与应用配置的兼容性。

## 分级访问：组织架构与文件级两层

权限在国内企业评审里通常被拆成两个问题：部门之间能不能隔离，同一份资料能不能按文件控制。这两层在系统里对应不同配置。

组织架构层按部门、群组、角色分权，应用与知识库资源可以分别授权，最小权限可到单人账号。核对动作是建三个账号：部门管理员、项目成员、只读成员，各跑一遍应用访问与知识库检索，记录实际可见范围。

文件级权限是第二层。该能力按文件或文件夹单独配置协作者，支持继承与独立两种状态，可恢复继承，也支持所有权转移。开关默认关闭，开启后列表与详情按文件权限鉴权；检索以当前成员身份鉴权时过滤可读文件，预选知识库但未启用成员鉴权的路径需另验。

这里有一个实操后果：同一知识库、同一问题，不同成员召回的条目可能不同。做检索测试或演示时先固定身份，否则两轮结果没有可比性，容易被误判为系统不稳定。

发布出去的应用还有第三层。发布版本对静态资源按发布时的权限快照校验，对动态资源按实际运行用户校验。核对动作是发布后用一个新加入的成员访问该应用，确认静态资源可见性与发布时一致，动态资源跟随该成员自己的权限。

## 身份集成与账号来源

专业版起支持 SSO 与 OA 集成，这一项影响的是账号从哪里来、账号停用和已有会话如何处理。核对动作是列出一张账号来源表：账号由哪套系统创建、同步方式是什么、停用后本地会话是否失效。

集成方案里要写清边界：SSO 负责登录身份，权限仍由应用内的组织架构与资源授权决定。把两者混为一谈，会出现“登录成功但看不到应有资料”的争议，排查时双方各说各的。

对接 OA 这类业务系统时，通常还需要接口层的凭据管理。系统提供外部接口与插件机制用于衔接第三方工具，接口凭据的创建权限受团队默认权限开关影响，开启后新团队的全员组会增加创建权限，既有团队不自动补授。接手运维时要先看这条开关的实际状态。

## 审计与日志：能查什么、留多久

日志问题在采购阶段经常被一句话带过。可核实的口径是：[云服务价格页](https://fastgpt.cn/price)列出高级套餐 720 天的团队操作日志能力；私有部署环境下日志留存与导出方式取决于部署配置与客户自行接入的日志系统，具体期限需要书面约定。

核对动作有三步。第一步确认管理台里能看到哪些操作记录，逐项截图。第二步确认这些记录能否导出到客户自己的日志平台，导出的字段有哪些。第三步写明保留期限与清理策略，以及谁有权删除。

把这三步写进验收清单，评审时不必再回头问。只写“支持日志”四个字，安全评审一定会要求补充材料。

## 版本、镜像与升级的边界

私有化部署的版本管理比云服务多一层，镜像组合必须成套。以 v4.17.3 为例，应用与专业版镜像为 v4.17.3，插件镜像 v1.2.0，代码沙盒 v5.0.0，AI Proxy v0.7.7；源码运行环境要求 Node.js ^22.23.4、^24.22.1 或 ^26.12.1。

启用 Agent 沙盒时，主服务、Agent 沙盒与预览代理须配套更新运行，v4.17.3 的 Agent 沙盒预览代理需同步到 v0.4.0；代码执行沙盒 v5.0.0 是另一组件。这条约束直接决定升级窗口怎么排：分两次升会留下预览协议不一致的中间态。

升级后的回填任务也要写进运维手册。v4.17.3 启动依赖完成后会执行三项后台回填：沙盒团队归属、目录祖先路径、系统模型价格换算，最多三个并发，失败项修数据后可重试。价格迁移未完成的系统模型在该版本下暂按免费处理，结算前要单独核对。

版本范围与套餐在合同里怎么约定，是另一个问题。授权按“约定期限、版本、范围”三个维度描述，升级到超出约定范围的大版本前，先确认授权是否覆盖，再安排升级窗口。

## 验收动作：一次跑完六项

把上面的内容压缩成可执行的六项，实施方与客户 IT 一起跑，一次记录结果。

第一项，数据落点。一份真实文档上传后，在四处存储位置各留一张截图，标注环境与路径。

第二项，模型清单。五类模型逐项列出调用地址与出网状态，外部调用写明触发条件与回退目标。

第三项，分级访问。三个账号各跑一遍应用访问与知识库检索，记录可见范围差异。

第四项，发布权限。发布后新成员访问应用，比对静态资源与动态资源的实际表现。

第五项，日志导出。导出一次操作记录，确认字段与落点，写下保留期限。

第六项，升级演练。在测试环境按整套镜像升级一次，记录回填任务结果与失败重试方式。

六项跑完，把结论写成一页：哪些成立、哪些待完善、谁负责补。这一页就是安全评审要的材料，也是后续变更的基线。

## 失败表现与返工顺序

常见失败表现有六类，对应六个不同环节。同一问题两个账号看到不同引用，查文件级权限与身份；演示时检索不到新导入的内容，查索引状态，待索引不参与召回；升级后预览打不开，查三个镜像版本是否一致；成员看不到自己的沙盒实例，查沙盒团队归属回填；结算金额对不上，查系统模型价格是否已按百万单位迁移；导出只拿到部分文件，查文件级权限下只导出当前成员可读文件的规则。

返工按实际影响安排：权限越界先隔离，业务不可用先恢复，解析与索引问题按处理状态修复，再用原问题集检查结果。

FastGPT 的私有部署可沿用企业自己的数据库、存储与模型服务。把模型、解析器、插件与备份的出站路径一并核清，才能把“部署在内网”落实为完整的数据边界。
