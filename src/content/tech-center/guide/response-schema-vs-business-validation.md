# 回复格式和业务校验怎么分工

在 FastGPT 应用中，模型生成的回复需要满足特定格式，其内容也需要符合业务规则。这两种需求可以通过不同方式实现：一种是利用模型本身的能力生成结构化文本，另一种是通过 HTTP 接口调用外部系统进行校验。选择哪种方式，或如何组合，取决于接收回复的系统、现有接口的能力以及对业务事实准确性的要求。

## 不同实现路径的关注点

当接收方是按自然语言阅读的用户或简单文本处理程序时，可以直接在提示词中明确回复任务、信息范围以及在证据不足时的处理方式。这种方法的重点是引导模型依据提供的资料作答，不自行编撰业务事实。其生成内容为普通文本，不承诺固定的机器可读结构。

若下游应用需要固定的字段和数据类型，可以要求模型按指定的 JSON Schema 格式回复。实施时，需要在 FastGPT 中提供具体的格式定义，并验证返回结果是否符合该结构。此方法用于生成结构正确的回复，但结构正确不代表内容符合业务逻辑。例如，模型可能生成一个格式有效但业务状态不正确的订单对象。这种结构化输出可以作为调用外部业务系统前的标准输入。

对于需要严格业务规则校验的场景，例如检查库存、核实用户身份或更新订单状态，应当通过 HTTP 接口调用专门的外部业务系统。FastGPT 负责根据对话上下文，准备并发送请求至指定的接口地址。外部系统根据自身逻辑执行校验或操作，并返回结果。这种方式将业务逻辑与语言模型分离，由最合适的组件负责各自的任务。HTTP 请求可以传递普通文本，也可以传递由模型生成的结构化数据。

## 路径选择与组合考量

下表比较了三种处理路径在不同维度的区别。这些路径可以独立使用，也可以组合。例如，可以先让模型生成符合 JSON Schema 的结构化数据，再将此数据作为 HTTP 请求的 Body 发送给外部接口进行业务校验。选择组合方案时，需要明确各环节的职责边界，避免功能重叠或遗漏校验环节。

| 比较维度 | 提示词引导（普通文本） | JSON Schema 结构化回复 | HTTP 接口外部校验 |
| --- | --- | --- | --- |
| 主要目标 | 生成符合任务描述的自然语言回复 | 生成机器可读的、有固定结构的文本 | 执行外部系统的业务规则与状态变更 |
| 实现方式 | 在提示词中详细描述回复要求 | 在模型配置中提供 JSON Schema 定义 | 配置 HTTP 节点，按外部接口契约发送请求 |
| 校验重点 | 回复内容是否忠于给定资料 | 返回的 JSON 结构、字段和类型是否正确 | 外部接口返回的业务处理结果是否成功 |
| 适用场景 | 问答、摘要、内容解释等文本生成任务 | 需要将回复集成到自动化流程或前端展示 | 需要与已有业务系统交互，如查询、创建、更新数据 |
| 局限性 | 不承诺固定的输出结构，不利于程序解析 | 仅校验格式，不校验业务事实的有效性 | 依赖外部接口的可用性、性能和鉴权机制 |

## 实施中的具体核对项

在具体实施任一路径时，都需要核对输入和上下文的准确性。例如，在多轮对话中，在多轮对话中，应核对传入模型的历史记录，并确认问题优化功能是否按预期解析了指代关系。当使用 HTTP 接口时，必须仔细核对请求地址、方法、请求头和请求体是否与外部接口文档一致。鉴权凭证等敏感信息应通过安全配置注入，不写入公开的节点配置中。此外，FastGPT 在测试模式下提供的 chatId 与 responseChatItemId 字段在实际调用中不存在，设计时不应依赖这些调试期特有的信息。
