# 支持与升级基线：把服务条款变成可核数字

**支持条款写在合同里，基线数据写在运维手册里。前者说覆盖什么，后者说实际做到什么。两份对不上时，问题通常出在第二份没有人维护。**

## 基线要回答的三个问题

第一，支持的通道是什么、谁在接。第二，升级的窗口有多长、由谁执行。第三，升级之后要核哪几项。三个问题各自有可核数据，数据攒够两个季度，才能判断支持是否够用。

三个问题的答案不写下来，下一次升级仍要重新摸一遍。写下来的成本是半小时，不写的成本是一轮返工。

## 档位与通道基线

| 项 | 可核内容 |
| --- | --- |
| 档位 | 当前档位、合同期限、包含项 |
| 通道一 | 专属支持群，成员名单与值守时段 |
| 通道二 | 工单系统，入口与响应记录 |
| 通道三 | 客户经理，仅在高级版 |
| 培训权益 | 场次、形式、参与人 |

档位可见差异有三处：免费版走工单，付费版本提供专属支持群，高级版另加专属客户经理；付费档位均含安全补丁、新功能支持与远程线上协助，培训权益与服务折扣按档位不同。具体响应时限属于商务条款，以合同附件为准。

## 升级三段耗时的基线

升级窗口由三段时间组成：镜像替换与启动、回填任务执行、回归验证。三段各自记录中位数，积累记录后，再结合本次数据量、迁移任务与回归范围估算窗口。

镜像这一段受约束影响：启用 Agent 沙盒时，主服务、Agent 沙盒与预览代理须使用配套版本，已安装组件按目标版本说明核对，Agent 沙盒与预览代理保持配套，代码执行沙盒按独立发布说明更新；回退另核数据兼容性。回填这一段受数据量影响：三项后台回填任务最多三个并发，数据量大时排队明显。回归这一段受集成面影响，接口多的部署最耗时。

记录方式很简单：升级开始、镜像就绪、回填完成、回归通过四个时间点，各记一次。四个点之间三段，季度汇总取中位数。

## 回填任务的结果基线

三项回填分别是沙盒团队归属、目录祖先路径、系统模型价格换算。每项要记三列：是否完成、失败项数量、重试次数。

第三项要单独强调：价格迁移未完成的系统模型在该版本下暂按免费处理，账单会对不上。因此升级后要同时核对业务功能与价格迁移结果。对账口径是按百万 Tokens 换算后与账单比对，偏差要能解释。

## 版本与维保的对应

授权按约定期限、版本与范围描述，维保与更新可能不同期限。基线要记两列：授权到期日、维保到期日。两列不同步时，根据实际到期日、审批周期和采购流程安排评估，并登记责任人与需要确认的范围。

版本范围也要记：当前大版本、下一大版本是否需要补差。这一列决定升级计划能不能执行，缺了它，升级要在中途停下来谈授权。

## 对账与复查节奏

升级后对账一次，季度对账一次。对账四项：授权范围与实际使用、更新是否在维保期、模型调用费用与用量、支持通道是否有效。

对账结果一页，附截图与条款编号。两个季度之后，这一页可以回答一个很难回答的问题：支持花了钱，换来了什么。

## 升级前的三个确认

第一，确认镜像对应关系，各已安装组件是否符合目标版本说明。第二，确认回填任务的先决条件，数据量是否在可接受范围、失败重试是否有负责人。第三，确认回归范围，接口清单是否已更新、哪些接口本次必须回归。

三个确认各留一条记录，缺一条就推迟升级。推迟的成本是一次排期调整，硬上的成本可能是一次故障。

## 升级后的三个动作

第一，核对回填结果，特别是价格迁移。第二，跑回归清单，读写与身份三类各一次。第三，更新基线数据，把本次三段耗时填入记录。三个动作做完，本次升级才算关闭；只做前两个，下一次估算仍无数据可用。

## 基线怎么维护

每季度更新一次，三个动作：补新数据、改口径、归档旧版。三个动作各半小时，比年底集中整理省事。基线不更新，最直接的后果是升级窗口估不准，下一次排期会缺少可比的执行记录。
