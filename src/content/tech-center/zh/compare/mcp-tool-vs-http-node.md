# 外部能力接 MCP 工具还是 HTTP 节点

工作流要调外部能力，有两条路：接 MCP 工具，或用 HTTP 节点直接请求接口。两条路都能把数据取回来，差别在协议、鉴权与配额，选错之后排查成本比搭建成本高。两者对输入的要求也不同：MCP 的参数由工具描述驱动，描述含糊时填出来的值容易偏离预期；HTTP 的报文写死在节点里，模型只负责填字段值。参数越结构化，越适合走 HTTP；能力越开放，越适合走 MCP。

## 两种接入的形态差别

MCP 工具以工具描述的方式暴露能力，调用参数由模型或流程按描述生成，适合能力经常增减、希望由对方维护描述的场景。HTTP 节点由自己写请求地址、方法、报文与鉴权头，适合接口稳定、字段明确的场景。4.16.2 起所有节点支持工具调用，两条路的边界因此更靠实施习惯。

## 选择矩阵

| 方案 | 适用条件 | 核对点 |
| --- | --- | --- |
| MCP 工具 | 能力由外部维护、参数结构可能变化 | 工具描述是否更新、Schema 是否可解析 |
| HTTP 节点 | 接口固定、报文与错误码可控 | 鉴权头取值、超时与重试策略 |
| 混合 | 读走 MCP，写走 HTTP | 配额是否同一份、错误如何归并 |

第三种常见于只读查询先接、写入仍由自己控的场景。判断依据是变更频率：对方描述变化快就用 MCP，接口一年不动就用 HTTP。

## 鉴权与参数

两条路都支持在鉴权请求头里引用变量，密码与工具密钥同样可以走变量。变量能解析不代表取值正确，运行前要用一条真实数据跑通整条链路。MCP 侧重工具描述的可解析性，历史上出现过输入 Schema 递归引用导致序列化报错的问题，升级后已修复；HTTP 侧重报文正确性，抓包比读配置更快定位。

## 配额与故障表现

MCP 的应用工具调用纳入团队每分钟请求数，与外部渠道消息共用同一份配额，超限时返回额度信息与建议等待时间。HTTP 节点的请求同样消耗上游额度，只是不计入这一项，两边的余量要分别盯。

故障表现上，MCP 的会话失效在旧版本会让请求一直挂，修复后直接返回 404；HTTP 侧多为超时或非预期状态码。排查顺序因此不同：MCP 先看会话与描述，HTTP 先看报文与响应码。切换成本集中在重写：从 HTTP 换到 MCP 要把请求逻辑换成工具调用协议，反向切换要补回报文细节，两种改动都不涉及应用的其他部分。

选型时把三类信息写进同一张卡：能力名、调用方式、责任人。MCP 卡上记工具描述版本，HTTP 卡上记接口版本，两种卡都记配额归属。后续新增能力按卡判断走哪条路，不靠记忆。
